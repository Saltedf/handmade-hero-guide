
# 09G-4 · 认证与 TRC/TCR

## 0 · 你做完 Beta 提交了,然后收到一封 200 条问题的邮件

把你拉回 [09G-3](09G-3-alpha-beta-and-content-pipeline.md) 走完 Beta 的那个时刻。bug 率压到每小时 1 以下,内容冻结了,你打包出 release candidate 1(RC1),提交到平台方——可能是 Steam,也可能(假设性地)是某个主机平台。你心里说:"游戏终于做完了。"

三天后平台方回邮件,后面挂着一份报告:**200 个 issue,修完才能上架。** 你点开扫了一遍,世界观开始崩塌——"按手柄 Home 键必须能在 2 秒内回到主菜单"、"存档失败必须弹模态对话框,不能静默"、"窗口最小化时音频必须暂停"、"1280×720 分辨率下 UI 不能超出安全边距"、"网络断开时玩家不能卡死"、"退出游戏前必须确认未保存进度"。其中一半你**根本不知道存在过**,另一半你以为"功能上做了就行"。最让你崩溃的是其中一条:"连续运行 24 小时,崩溃次数超过阈值。" 你自己测过最长的一次也就 4 小时。

你撞上的,是"做完"和"可以上架了"之间的一道真实存在的闸——**certification(认证),简称 cert**。这一篇讲的就是这道闸:它是什么、它查什么、为什么它的规则几乎都是"过去某个游戏出过的真实事故"沉淀出来的、以及最重要的——**怎么从 day 1 就为它设计,让 cert 从"灾难性的最后一刻返工"变成"走流程"**。读完你会发现,9A([09A-4](09A-4-fuzz-determinism-and-regression.md) 的 fuzz/回归)、9E(网络断连)、9F([09F-2](../phase-8/deep-dives/savegame-and-serialization.md) 的版本化存档、[09F-3](09F-3-cross-platform-and-portability.md) 的 PAL 抽象)那几篇埋的伏笔,**全都是为 cert 准备的**。这一篇就是把它们拧成一股绳。

## 1 · 认证是什么,以及它不是什么

先把概念钉死,因为新手对 cert 的最大误解是把它当成"质量评审"。**它不是。**

cert 是这样一个流程:平台持有者(platform holder,主流四家是 Sony、Microsoft、Nintendo、Valve)在你提交游戏后,用一个或一组**公开的、规则化的、确定性的检查清单**逐条核对你的游戏,只有所有"必须(mandatory)"条款通过,平台才允许你在它上面发售。这个核对的执行者通常是平台方的 QA 团队,他们会真的拿着手柄、按一份几百项的清单逐条走流程——不是测试好不好玩,是测试**"在你这台机器上,这游戏按规定规矩办了吗"**。

这是 cert 和 quality review 的本质差别,务必分清。**quality review 问"这游戏好吗"**(评分、impressions、好不好玩),Steam 也有 Early Access 不评质量、仅做基本合规;而 **cert 问"这游戏在我们这台机器上守规矩了吗"**(它崩了吗、它响应系统事件了吗、它弄坏玩家存档了吗、它的 UI 守我们平台的交互规范了吗)。一个游戏可以 cert 全过但玩家觉得"不好玩"——这是合法的,cert 不评玩;反之,一个"好玩但 cert 不过"的游戏**上不了架**——平台不会因为它好玩而给你破例。这条对 indie 极重要:你花两年做出一个好游戏,但 cert 不让你上架,玩家就**永远买不到它**。所以 cert 是"做完"和"能卖"之间的真实闸门,而不是某种虚的"质量认证"。

cert 为什么是这种"合规而非质量"的形态?因为平台方有自己的利益:它要保护自己平台的**生态系统(ecosystem)**。一台 PlayStation 玩家买了游戏回去玩了十分钟崩溃了三次,他骂的不是这家 indie 工作室,他骂的是"PlayStation 上买的游戏都这么烂"——平台品牌受损。所以平台用一份确定的、提前公开的清单,**把"什么样的游戏能上架"变成可机械验证的规则**,而不是某个审核员的主观品味。这机制对你其实是好事:**cert 的规则是公开的、可读的、可提前准备的**——它不是黑箱,是题目公开的考试。业余者把 cert 当黑箱抱怨,职业者把 cert 清单下载下来,从 production 第一天就把它贴在墙上当作 to-do。

那么这份清单长什么样?下一节我们看它的主体内容——通称 **TRC / TCR**。

## 2 · TRC、TCR、以及它们的桌面等价物

清单本身各家有不同的名字。**TRC**(Technical Requirements Checklist)是 Sony 的叫法,**TCR**(Technical Certification Requirements)是 Microsoft 的叫法,Nintendo 也有自己的等价文档(通常只说"Lot Check",历史词,源自当年卡带检验)。Valve 这边桌面端叫得没那么正式,内部叫 **Steam 上架检查 / Steam Deck Verified 检查**,公开度更高。本文下面统一用"TRC"指代"任何平台方的技术要求清单",并在涉及具体平台时点明。

讲清楚一件事再往下走:**TRC 不是一份统一的文件**,它是**几百到上千条独立规则**的集合,每条规则独立编号、独立验证、独立判定 pass/fail,且每条规则标记了它的强度——大致三档:**mandatory**(必须过,不过不能上架)、**conditional**(满足触发条件时必须过)、**recommended**(建议,不过不致命但平台可能扣印象分)。绝大多数 cert 失败集中在 mandatory 那批。下面我把 TRC 涉及的几个大类别用 prose 讲一遍——**讲类别时我会给具体规则示例,但请把它当作"那一类规则的典型代表"而不是"完整清单"**。真实 TRC 每家几百页、随版本更新、且大部分受 NDA(主机端),你拿不到完整版,但你不需要完整版也能理解它的**精神**——因为所有规则的根源是同一个:**这条规则是因为过去某个游戏出过事才加进来的**。

**第一类:稳定性(stability)。** 这是 TRC 的地基。典型规则:连续运行 N 小时(主机端常见是 24 小时)内崩溃次数不超过阈值、内存峰值不超过系统预留外的部分、长时间运行不出现明显内存泄漏、过场动画期间不掉帧、加载时间不超过某阈值。听起来抽象,翻译成你 HH 项目的语言就是:**你的 fuzz 测试网([09A-4](09A-4-fuzz-determinism-and-regression.md))能不能在 24 小时内把游戏跑崩**。cert 阶段做这件事时,平台方 QA 用的是真手柄、真存档、真玩家行为路径,不是你设计的 happy path——他们就是来制造你以为不可能的崩溃的。这一类的防御只有一条:**从 production 第一天就把 fuzz + 回归测试网搭起来,把它当作 ship gate**。等到 cert 阶段才发现"我们游戏 24 小时必崩",你修这个崩溃通常意味着重写某段核心代码——因为长跑暴露的几乎总是深层 bug(资源泄漏、状态机死锁、整数溢出累积),它们不是补丁能解决的。

**第二类:存档(save handling)。** 存档是玩家最敏感的数据,TRC 在这里规则最多最严。典型规则:存档失败必须给玩家**明确的模态提示**(不能静默吞掉)、覆盖已有存档前必须**确认**(玩家在 slot 1 有进度,选"新游戏"又存到 slot 1,系统必须问"覆盖?")、存档**不能损坏**(读写过程中断电/强杀后必须能恢复到一致状态,常用 WAL 或原子写)、自动存档(autosave)必须在游戏内有明确**视觉反馈**(右上角"Saving..."图标)、存档**大小受限**(主机每用户云存档配额有限,存档过大 cert 不过)、系统层"删除存档"功能必须能正确清掉游戏所有存档不留残骸。这一类直接对接 [09F-2 / phase-8 savegame-and-serialization](../phase-8/deep-dives/savegame-and-serialization.md) 讲的版本化存档——如果你当初做了 schema versioning + migrate,**这里几乎所有规则自动满足**;如果你当初图省事直接 `serde_json::to_writer` 一把梭,cert 阶段你大概率要重写存档系统。

**第三类:手柄与输入行为(controller behavior)。** 主机端最细的规则集之一。典型规则:每一个游戏内功能都必须能用手柄独立完成(不能"必须用键盘才能打开某菜单")、Home / PS / Nexus 按钮按下必须在 N 秒内弹出系统菜单(不能拦截)、所有可点击 UI 元素必须能用手柄方向键导航 + 确认键激活(不能鼠标专属)、rumble(震动)行为必须遵循系统级"震动开关"设置(玩家在系统层关了震动,游戏不能震)、控制器断开和重连必须正确处理(详见下文断连)、双手柄双人游戏切换玩家顺序必须正确。这一类在桌面(Steam)上同样存在但强度低:Steam 要求"基本控制器支持",Steam Deck Verified 要求手柄操作完整覆盖。

**第四类:显示(display)。** 主机端:必须支持平台所有标准分辨率、UI 元素必须在"安全边距(safe margin)"内(老式 CRT 的概念延伸,以防超扫描 overscan 切掉)、HDR/SDR 都必须正确渲染、宽高比切换正确。桌面(Steam)上更现实:窗口模式/全屏/无边框全屏都支持、分辨率切换不崩、多显示器情况下窗口不能跑到看不见的屏幕外、HDR 在支持的显示器上自动启用、Steam Deck(1280×800 16:10)UI 不能错位。

**第五类:网络(networking)。** 网络连接的游戏这部分规则极重。典型规则:网络断开时游戏**不能崩溃、不能软锁、不能数据丢失**,必须给玩家明确提示("连接已断开,正在重试..."),并在断开后能优雅回到上一状态(或主菜单);玩家中途退出多人游戏不能影响其他玩家继续;matchmaking 失败要有 fallback(本地 AI、Bot);联机数据要尊重玩家隐私设置。这一类直接对接 9E 网络序列——[09E-1](09E-1-reliable-udp-transport.md) 讲的可靠传输、断连检测,[09E-2](09E-2-authoritative-server-and-state-sync.md) 讲的状态同步,在断连那一刻的所有行为,TRC 几乎逐条对照检查。你在 9E 写的"3 秒没收到心跳判离线 + 进入重连 grace period" 逻辑,在这里就是一条 pass;如果你当初没写,玩家拔网线游戏就 freeze,cert 立刻挂。

**第六类:平台集成与一致性(platform integration & UX)。** 主机端:必须支持平台的成就(achievement)系统(玩家达成条件必须立刻上报)、截图/录屏按钮要工作、待机/恢复(suspend/resume)必须正确(系统挂起游戏后回来不能崩、不能丢进度、不能错乱音频)、系统通知不要被游戏覆盖。桌面 Steam:Steam Overlay 必须能正常打开(Shift+Tab)、成就必须在玩家达成那一刻**立即**触发(不能延迟到下一关、不能批量触发)、Steam Cloud 必须能正确同步存档、Steam Input(Steam 的控制器抽象层)必须支持。这一类大部分是"接 SDK 然后正确调用"的工作量,但有一条极容易被忽略:**Steam Overlay 兼容性**——很多游戏因为渲染管线和 overlay 不兼容,Shift+Tab 后 overlay 闪一下就消失,cert 直接挂。修复通常意味着调整 swapchain / present 路径,如果在 PAL 里设计好了很简单,如果是后期硬塞进来的痛苦。

**第七类:无障碍基线(accessibility baseline)。** 这是近年所有平台都加重的一类。典型规则:必须支持系统级文字大小设置、必须支持色盲模式(关键 UI 不能仅靠颜色区分)、字幕必须可开关且字号可调、按键自定义必须支持(不能锁死按键映射)、闪光频率限制(防光敏性癫痫,著名的" Harding Test")、不能仅靠声音传达关键信息(听障玩家要能玩)。这一类很多 indie 觉得"是 nice-to-have",但 2026 年的主流平台已经把这些列为 mandatory 的越来越多——你不做,cert 不过。

讲完七类,你应该已经感受到一件事:**TRC 几乎覆盖了一款游戏"对玩家友好"的每一个面向**。它不是凭空冒出来的官僚障碍,它的每一条都对应历史上某个真实游戏的真实事故——某游戏存档损坏导致大量差评、某游戏 Home 键无响应被玩家投诉、某游戏网络断开直接崩被退款潮。**TRC 是事故的化石**。读懂它的方式不是去死记每条规则,而是理解每条规则背后"它在防什么"——一旦你理解了"防什么",你在写代码时自然会规避那个坑,不需要查清单也知道正确做法。

## 3 · 常见的 cert 失败,以及它们对应的你 9A/9E/9F 的伏笔

抽象地讲完类别不够,这一节我把"最常导致 cert 挂掉的具体问题"列出来,并标注每个问题你之前在哪一篇已经学过防御。读完你会发现:**几乎每一条 cert 失败,都对应你 9A/9E/9F 阶段本应做对的一件事**。cert 难不是因为题目新,是因为题目多、且你没有从 day 1 防备。

**第一,硬崩溃(hard crash)。** 这是 cert 第一杀手。表现形式:玩家做某个动作游戏退出 / segfault / 卡死无响应。常见根源:未初始化内存访问、整数溢出、空指针解引用、栈溢出(过深递归)、资源竞争(data race)。你的防御武器就是 [09A-4](09A-4-fuzz-determinism-and-regression.md) 那一整套:**fuzz 测试**自动生成玩家行为路径去触发未知崩溃、**property test** 验证边界不变量、**address-sanitizer / miri** 在 CI 里抓内存安全 bug、**回归测试网**保证修了不再犯。cert 阶段做崩溃测试和你在 9A 做的 fuzz 是**同一件事**,只是更系统、更长时间。一个在 9A 阶段把 fuzz 网搭扎实的项目,cert 阶段的崩溃率会低到几乎为零;反过来,9A 没做、cert 阶段才补的项目,几乎一定挂——因为长跑崩溃的根源(内存泄漏、状态机死锁)需要几周才能定位和修复,而 cert 留给你的窗口通常只有一两周。

**第二,存档损坏(save corruption)。** 第二杀手。表现形式:玩家退出再进,存档打不开 / 读出来数据错误 / 进度归零。常见根源:写存档过程中断电或强杀(写了一半)、存档格式版本不兼容(升级游戏后旧存档无法加载)、并发写(同时多个进程写同一存档)、磁盘满了写失败但游戏当成功。你的防御武器就是 [phase-8 savegame-and-serialization](../phase-8/deep-dives/savegame-and-serialization.md) 讲的:**原子写**(先写临时文件再 rename,POSIX 保证 rename 原子)、**schema versioning**(每个存档带版本号,加载时按版本 migrate)、**写后回读校验**(写完读回来对比 hash,确认磁盘一致)、**写失败必须抛错并提示玩家**(不能静默)。这些机制在 production 早期就建立好,cert 阶段这一类规则自动 pass;等到 cert 才发现"我们存档写一半会坏",你修复它要改整个存档系统的写路径——此时游戏已经 ship 前夕,改动风险极大。

**第三,软锁(soft-lock)。** 第三杀手且最隐蔽。表现形式:玩家进入某个状态,既不能继续游戏也不能回到菜单——比如过场动画卡住跳不过、暂停菜单被某个 UI 完全遮挡、对话触发后 NPC 不回应玩家也无法退出对话、加载画面永远不结束。根源通常是**状态机(state machine)的死状态(dead state)**——某个组合的输入让状态机进入设计者没考虑的分支。软锁比崩溃还致命,因为崩溃至少给玩家一个明确的"游戏死了"信号,软锁让玩家**以为游戏还在跑只是自己不会操作**,然后他白等十分钟才发现卡死了,愤怒值翻倍。防御武器:**穷举测试状态机的所有可达状态**,以及一个**保底的"长按 Home / 退出键强制回菜单"机制**(玩家永远有一个 escape hatch)。穷举状态机可以用 model checking 或简单地用 fuzz 给状态机喂随机输入然后断言"任何状态下,玩家都能在 N 步内到达主菜单"。

**第四,断连处理不当(poor disconnect handling)。** 网络游戏的杀手。表现形式:玩家拔网线游戏 freeze / 联机对手退出后我方卡住 / 服务器关闭后客户端崩溃 / matchmaking 超时无 fallback。根源是网络代码假设"连接永远在",没设计断连路径。你的防御武器就是 9E 全套:[09E-1](09E-1-reliable-udp-transport.md) 的心跳检测和 grace period、[09E-2](09E-2-authoritative-server-and-state-sync.md) 的权威服务器对客户端断连的判定、[09E-3](09E-3-interest-management-and-replication.md) 的状态回滚、[09E-4](09E-4-matchmaking-nat-relay-lobby.md) 的 matchmaking 超时处理。如果你 9E 把"拔网线"作为一种正常事件设计了——心跳超时进入"重连中"状态、重连失败优雅回主菜单——cert 这一关自动过;如果你 9E 假设网络永远稳定,cert 时模拟拔网线 QA 一秒触发崩溃。

**第五,显示与分辨率问题。** 看起来低级却极常见。表现形式:Steam Deck 上 UI 错位、4K 显示器上 UI 太小、窗口拖到第二显示器后黑屏、HDR 显示器上颜色错误、多显示器切换主副屏时游戏崩。根源是渲染代码硬编码了某个分辨率 / 假设了单显示器 / 不响应 DPI 变化。防御武器:[09F-3](09F-3-cross-platform-and-portability.md) 的 PAL 抽象——把"窗口尺寸变化""DPI 变化""显示器切换"作为事件让游戏正确响应,而不是假设一次性配置。Steam Deck Verified 检查就是桌面端这一类的 cert 等价物,会逐项验证。

**第六,Steam 集成问题(桌面专属)。** Steam Overlay 打不开 / 闪退、成就不触发或延迟触发、Steam Cloud 不同步、Steam Input 控制器映射错乱、游戏时间统计不准。根源是 Steamworks SDK 集成不规范——比如成就用了一个错误的回调时机、Cloud 没设置正确的冲突解决策略。这类问题修复工作量不大但容易遗漏,所以 cert 前必须**逐条对照 Steam 上架检查清单**实测一遍。

读完这六类你应该有个强烈的感受:**这些问题没有一个是"新问题"**,每一个都是你在前面几篇 phase-9 文章里被反复警告过、被给了对应工具的。**cert 不是新挑战,cert 是你之前那些工程纪律的最终验收。** 这就是为什么我反复强调"从 day 1 为 cert 设计"——它不是最后一道额外的坎,它就是"你之前有没有认真做工程"的总账单。

## 4 · 桌面 / Steam 的 cert:轻但真实

主机 cert 的恐怖在 indie 圈是都市传说级别,但绝大多数读这篇的人**不会立刻上主机**——你的第一个发布平台几乎肯定是桌面(PC),具体说是 **Steam**(2026 年仍占 PC 游戏市场约 75%)。所以这一节专门讲桌面 cert 的实际形态,它比主机轻但**绝对不是没有**。

Steam 的 cert(他们内部叫"上架审核"和"Steam Deck Verified",官方文档公开在 partner.steamgames.com)分两层。**第一层是上架审核(基本合规)**:这一层非常轻,主要检查游戏不违反 Steam 的内容政策(不含违法内容、不盗用版权)、商店页要素齐全(capsule 图、trailer、描述、系统要求)、二进制能正常启动不立即崩溃、不恶意。这一层绝大多数游戏一两次就过,indie 真正栽跟头的不在这里。

**第二层是 Steam Deck Verified(可玩性认证)**,这才是桌面端真正的 cert,2026 年已成为 indie 必须关注的门槛——玩家越来越以"Deck Verified"作为购买决策依据。它有四档结果:Verified(完全可玩,所有功能正常)、Playable(基本可玩,有些小问题但能玩通)、Unsupported(关键功能不可用,如需要键盘鼠标)、Unknown(还没测)。你的目标是至少 Playable,理想是 Verified。Verified 的检查覆盖几个维度,我用 prose 讲一遍而不是列清单(规则会更新,理解维度更重要)。

**接口兼容性(Interface)。** Steam Deck 没有键盘鼠标,只有自带控制器(类似 Xbox 手柄布局)+ 触摸屏 + 触摸板。所有游戏内 UI、菜单、对话框、命名输入,都必须能用控制器完成。如果你的"角色命名"界面需要弹出虚拟键盘,你必须在 Steam Deck 上调起系统虚拟键盘(SDL 的 `SDL_StartTextInput` 或 Steam Input 的对应 API),不能假设有物理键盘。窗口里的每一个可点击元素,在手柄导航模式下必须能高亮、能确认。

**控制器输入(Input)。** 必须支持 Steam Input(Valve 的控制器抽象层),玩家能自定义按键映射。你的游戏不应硬编码"Xbox 手柄 button A",而应通过 Steam Input 的"动作(action)"抽象——玩家把"跳跃"绑到任何他想要的按键,你收到的是"jump 动作触发"事件。这条规则的精神和 [09F-3](09F-3-cross-platform-and-portability.md) PAL 的精神完全一致:**不要假设具体硬件,通过抽象层访问**。

**显示(Display)。** Steam Deck 是 1280×800 16:10 屏幕(不是常见的 16:9),你的 UI 在 16:10 比例下不能拉伸错位、不能切掉关键元素。字号在小屏上要可读。HDR(Deck OLED 版本支持)、SDR 都要正确。窗口/全屏切换要工作。如果你 PAL 设计好了分辨率响应,这一项轻松过。

**无缝性(Seamlessness)。** 玩家随时可以按 Steam 按钮(Deck 上是左侧快捷键)弹出 Steam 界面、随时按电源键让 Deck 睡眠、随时被通知打断——这些事件之后,游戏必须能正确恢复,不崩、不丢进度、不错乱音频。这就是 [09F-3](09F-3-cross-platform-and-portability.md) §5 讲的"主机挂起/恢复"在桌面端的等价物——只是主机是 mandatory,Deck 是 Verified 强烈推荐。这一项是绝大多数 indie 栽跟头的地方,因为他们从来没测过"游戏中按电源键睡眠 5 分钟再唤醒"。

**性能(Performance)。** Deck 的 APU 性能大约是中端笔记本,你的游戏在 Deck 上要能稳定跑——Verified 推荐至少 30 FPS,理想 60 FPS。如果你的游戏在 Deck 上跑 15 FPS,会被判 Unsupported。这要求你的渲染管线有"动态画质"机制([09F-3](09F-3-cross-platform-and-portability.md) §6 移动端的同款机制)——检测到帧率掉,自动降分辨率、关效果。

除了 Deck Verified,Steam 还有些**功能集成 cert** 要注意:**成就**必须在玩家达成的瞬间触发(用 `SteamUserStats()->SetAchievement`,不能攒着批量发)、**Steam Cloud** 必须正确配置存档同步路径(玩家在 Deck 玩了进度,在 PC 上要能接着玩)、**Steam Overlay**(Shift+Tab)必须能正常弹出——这条意味着你的渲染管线不能独占 swapchain、要给 overlay 留 hook。这三项是桌面 indie 最常遗漏的"软 cert"——不会让你上不了架,但会让玩家体验差、评分低、影响销量。

总结一句:桌面 cert 比主机轻一个量级,但**它真实存在,且 Steam Deck Verified 已经接近主机 cert 的严格度**。把桌面 cert 当回事,你这关过;不当回事,挂着 Verified Unknown 卖不动,和你 cert 挂了效果差不多。

## 5 · 从 day 1 为 cert 设计:业余和职业的分水岭

讲完 cert 是什么、查什么,这一节讲最重要的一件事:**怎么避免在 cert 阶段手忙脚乱地修 200 条**。答案只有一句话,但它需要被反复说透——**从 production 第一天就把 TRC 当设计约束,而不是 ship 前的检查表**。

业余者的典型流程是这样:埋头做游戏,直到 Beta 末尾才想起"哦要上架得过 cert",下载 TRC 清单一看,"哇存档要原子写,我没做"、"哇断连要处理,我没做"、"哇分辨率切换要响应,我硬编码了"。然后 cert 阶段变成灾难——存档系统要重写、网络代码要补断连分支、渲染管线要重构成响应式。每一项都是几周工作量,叠在一起就是延期半年,而此时游戏内容已经冻结、不能动,只能在工程层硬改。**业余者把 cert 当成最后一道坎,所以这道坎显得特别高**。

职业者的流程完全不同:production 启动会第一项议程是"过 TRC 清单",团队一起读一遍(哪怕只读公开摘要),把每条 mandatory 规则标记成"我们怎么设计来满足它"。存档要原子写?OK,存档系统从第一行代码就用 `tempfile + rename` 模式;断连要处理?OK,网络状态机从第一天就有"disconnected"状态;分辨率要响应?OK,窗口事件从第一天就在 PAL 里。**这些设计在 day 1 加进去几乎零成本**——你本来就要写存档系统、网络代码、PAL,只是"按 cert 要求的形态"写。等到 cert 阶段,这些规则**自动满足**,你需要做的只是"验证它们真的满足",而不是"返工让它们满足"。

更妙的是,TRC 的精神——"对玩家友好、对平台友好"——和"好游戏设计"高度重合。存档不损坏,这本身是玩家想要的;断连不崩,这本身是网络代码该有的健壮性;UI 在各种分辨率下不乱,这本身是 UX 该做的。**为 cert 设计,等价于为质量设计**——你做的每件让 cert 满意的事,也让玩家体验更好。这是 TRC 的"隐藏福利":它逼着你做你以为"麻烦但应该做"的事,而那些事恰恰是区分业余和职业的分水岭。

那么具体怎么从 day 1 把 TRC 集成进流程?我给三条可操作的动作。

**动作一,TRC 矩阵。** 拿到目标平台的 TRC 清单(主机端需要授权,但 Steam 上架检查和 Deck Verified 检查完全公开;主机公开摘要也够用),建一个表(这里破例用文字描述结构而非表格):每条规则一行,字段是"规则号 / 简述 / 强度(mandatory/conditional/recommended)/ 我们怎么满足(设计决策)/ 验证方法(怎么测)/ 负责人 / 当前状态(done/in-progress/blocked)"。这份文档**和 GDD 同等重要**,从 production 第一天存在,每次团队会议过一遍 in-progress 和 blocked 的条目。这份文档本身就是你 cert 阶段的"自查清单"。

**动作二,把 TRC 验证自动化。** 很多规则可以写成自动化测试——"24 小时无崩溃"写成 CI 里跑的 long-running fuzz、"存档原子性"写成写存档过程中 SIGKILL 然后验证能恢复、"断连处理"写成 fuzz 模拟随机断连、"UI 不超安全边距"写成渲染截图后程序化检查关键元素位置。把能自动化的规则都写进 CI,每次 push 自动跑——这就是 [09F-1](../phase-8/shipping-appendix.md) 讲的 CI 的延伸应用。不能自动化的(如"手柄按下 Home 必须弹系统菜单")写到人工测试脚本里,每个 RC 出来人工跑一遍。**自动化覆盖越多,cert 越省心**。

**动作三,内部 cert pre-submission(提交前内部预演)。** ship 前两周,做一次完整的内部 cert——一个不参与开发的团队成员(朋友、家人、临时 QA),拿着 TRC 清单逐条走流程,模拟平台方 QA。发现的失败,在真提交前修。这一步往往能抓住 80% 的"你以为过了其实没过"的规则——因为开发者自己测总带盲区(你知道"必须先按 A 再按 B 才会触发那个 bug",所以你从来不会先按 A 再按 B;陌生 QA 会)。这次内部 cert 是你提交前的"最后一道防线",过了它再提交,真 cert 一次过的概率大幅提高。

这三条做完,cert 从"灾难"变成"流程"。你不再是收到平台方 200 条 issue 的那刻才意识到有这么多规则,而是**你心里早就知道这 200 条、并且其中 190 条已经做过、剩下 10 条正在收尾**。这种感觉是职业制作人的标志。

## 6 · 提交流程:pass,或拿到报告再修

讲完准备,讲提交流程本身——一旦你提交了,cert 是怎么走的。

你提交的内容是 **release candidate(RC)**——一个完整的、可运行的、自包含的 build,带所有最终内容、最终代码、最终资产,通过 [09F-1](../phase-8/shipping-appendix.md) 讲的 reproducible build 流程产出。RC 不是"差不多行"的版本,它是"如果 cert 过了,这就是上架版"的版本——所以你提交前必须自己先过一遍 §5 的内部 cert,确保万无一失。

提交之后,平台方 QA 拿你的 RC 开始走 TRC 清单。这个周期:桌面 Steam 通常 1-3 个工作日(短),主机端 1-4 周(长,主机规则多且 QA 流程正式)。期间你什么都做不了,只能等——所以提交前一定要 ready,不要"提交了再改"。

**最理想的结果:一次过(pass)。** 平台方 QA 走完所有 mandatory 规则,全部 pass,conditional 规则要么满足要么合理豁免,recommended 规则可能扣印象分但不影响上架。结果:你的 RC 被认证为 **gold master**(母版,详见 [9G-5](09G-5-gold-and-post-launch.md)),可以上架了。这是最好的结局,但它只属于"从 day 1 准备 cert"的团队——业余团队几乎不可能一次过。

**更常见的结果:拿到报告(report)。** 平台方回一份详细报告,列出**未通过的 mandatory 规则**,每条带:规则号、问题描述、复现步骤、严重度。比如:"TRC-3.4.2: 在主菜单按手柄 PS 按钮后,系统菜单未在 5 秒内弹出。复现:启动游戏 → 主菜单 → 按 PS 按钮 → 计时,实测 8 秒。" 拿到这份报告,你的工作就是:**逐条修复**。

修复流程是迭代的。一份报告可能 5 条、20 条、50 条失败(超过 50 通常意味你完全没准备,平台方可能直接驳回让你重做)。每条失败对应一个 bug,按 [09G-3](09G-3-alpha-beta-and-content-pipeline.md) §5 讲的 triage 流程排优先级(A 级 cert blocker 必须修),修完每条 bug 配一个回归测试(确保下次不再犯),全部修完后 build RC2,**重新提交**。

RC2 走同样的 cert 流程。平台方 QA 这次重点检查你报告里那些失败条目(已修?),同时也会重新跑一遍其他规则(确认你没引入新问题)。理想情况 RC2 全过;不理想 RC2 又发现 3 条新失败(往往是 RC1 修 bug 引入的 regression),修完 build RC3 再提交。这个 **RC → cert → 报告 → 修 → RC** 循环,就是 [09G-3](09G-3-alpha-beta-and-content-pipeline.md) §7 提到的"RC 循环",它在 [9G-5](09G-5-gold-and-post-launch.md) 会详讲 gold master 制作。

这里有两条经验值得记住。**第一,每次 RC 之间务必跑全套回归测试网([09A-4](09A-4-fuzz-determinism-and-regression.md))**。RC2 修了 5 条 cert 失败,如果引入 10 条 regression,你下次 cert 又挂更多——回归测试网就是防止这种"修一个坏三个"。**第二,在 RC 循环中,bug 率应单调下降**——RC1 失败 20 条,RC2 应失败 ≤5 条,RC3 应失败 0。如果 RC3 失败条数比 RC2 多,说明你的修复引入了大量新 bug,流程出问题了,要停下来反思(通常是 triage 不严、急着修没配测试)。

最终,某一版 RC 通过所有 mandatory 规则,平台方签字——这就是 **gold master**。gold master 是 production 的终点:从这一刻起,游戏代码冻结,进入 manufacturing(主机端压盘)或上架准备(PC 端准备商店页、定价、发售日)。下一篇 [9G-5](09G-5-gold-and-post-launch.md) 就讲这一刻的工程细节。这一篇你只需知道:**cert 是 gate,gold 是 gate 那头的东西**。

最后一句关于心态:cert 不是敌人。indie 圈常把平台方当"找麻烦的官僚",这是误解。平台方的 QA 不是来刁难你,他们是来**确保你的游戏不会伤害玩家和平台**——存档损坏、崩溃、软锁,这些事伤害玩家也伤害平台品牌。cert 报告里的每一条 issue,都是平台方在**替你拦截一次差评和退款**。带着这种心态读 cert 报告,你会感谢它而不是怨恨它——这是职业开发者对 cert 的成熟态度。

## 7 · 在你 HH 项目里动手(做中学红线)

理论讲完了,这一节是"做中学红线"——我建议你在你的 HH 项目上具体做下面的事,把 cert 从概念变成验证过的事实。桌面端 cert(Steam 上架检查 + Deck Verified 维度)是核心,主机端概念性覆盖(你没有 devkit,但可以模拟规则)。这一节产出**一份 HH 项目的 TRC 风格清单 + 一次内部 cert 走查 + 修复发现的问题**,做完你的 HH 项目就有了"cert-ready for desktop"的状态。

**第一步,写一份 HH 项目的 TRC 风格清单。** 不需要照搬主机 TRC 几百条,基于这一篇 §2 讲的七类,为你的 HH 项目定制一份**符合桌面真实约束**的清单。我给一份骨架,你按你的项目情况增删(用 prose 描述结构,不用表格):

清单分七节对应七类。每节下若干条规则,每条规则格式:"**规则号 · 简述 · 强度 · 验证方法**"。例如稳定性类下:"**STAB-01 · 连续运行 4 小时不崩溃 · mandatory · 启动游戏挂机 4 小时后检查进程仍在且无 panic 输出**";存档类下:"**SAVE-01 · 存档写入过程中 SIGKILL 不损坏 · mandatory · 写存档时 kill -9,重启游戏验证存档可加载且数据一致**";输入类下:"**INPT-01 · 手柄按下 Steam/PS 按钮后 2 秒内弹系统菜单 · mandatory · 实测计时**";显示类下:"**DISP-01 · 1280×720 下所有 UI 元素在安全边距内 · mandatory · 在 720p 下截图,程序化检查关键 UI 坐标**";网络类(如适用)下:"**NET-01 · 拔网线 5 秒内进入'重连中'状态,不崩溃 · mandatory · 测试时拔网线观察行为**"。先写出**约 30-50 条**规则——比真 TRC 少,但覆盖七类且每类有代表条目。这一步的核心价值不是规则数量,而是**强迫你把"cert 要查什么"具象化成你自己游戏的条款**——一旦具象化,准备 cert 就变成"逐条 to-do"而不是模糊的焦虑。

**第二步,跑稳定性 cert 走查(STAB 类)。** 这是 fuzz 风格的压力测试。启动你的 HH 游戏,挂机运行 4 小时(短于主机 24 小时但足以暴露明显泄漏),结束后检查:`journalctl` / 任务管理器看进程是否还在、内存占用是否持续增长(泄漏)、有没有 panic 输出到 stderr。同时用 §3 提到的 fuzz 思路——写一个简单脚本(或用 [09A-4](09A-4-fuzz-determinism-and-regression.md) 的 fuzz 工具)给游戏喂随机输入几小时,统计崩溃次数。**目标:4 小时挂机 + 1 小时 fuzz 内,崩溃次数为 0**。不为 0,记下每个崩溃的复现路径,修。这是 cert 的地基,挂了其他都白搭。

**第三步,跑存档 cert 走查(SAVE 类)。** 这是验证你的存档系统是否 cert-ready。三个具体测试。**测试 A(原子性)**:在游戏写存档的瞬间 `kill -9` 杀进程(可以写个脚本:循环启动游戏 → 等随机时间 kill → 重启验证存档能加载且数据一致 → 重复 20 次)。如果任何一次重启后存档损坏,你的存档不是原子写,修。**测试 B(版本兼容)**:用旧版本游戏存一个档,升级到新版本(改 schema version),验证新版本能加载旧存档且正确 migrate。**测试 C(空间不足)**:模拟磁盘满(用 `fallocate` 把磁盘塞满再启动游戏存档),验证游戏存档失败时**弹模态对话框**而不是静默吞错——这是 SAVE 类最常挂的一条。三个测试都过,你的存档系统对 cert 的 SAVE 类规则基本 ready。

**第四步,跑"拔手柄"测试(INPT/NET 类,如适用)。** 这一条覆盖"控制器断连"和"网络断连"两个相关规则。具体做法:**测试 A(拔手柄)**:游戏运行中拔掉手柄(USB 或蓝牙断开),观察游戏行为——正确做法是暂停游戏并提示"控制器已断开,请重新连接",错误做法是 freeze / 崩溃 / 继续游戏但角色失控。**测试 B(拔网线,如 HH 是网络游戏)**:游戏联机中拔网线,观察——正确做法是 5 秒内进入"重连中"状态([09E-1](09E-1-reliable-udp-transport.md) 心跳检测),30 秒重连失败后回主菜单;错误做法是 freeze 或崩溃。每条都对照你 §1 写的清单验证。这一步是 9E 网络代码和输入处理的最终验收——9E 写得好这里轻松过。

**第五步,跑显示 / 分辨率走查(DISP 类)。** 把游戏在不同分辨率下跑一遍——1280×720(最小目标,Deck 是 1280×800 类似)、1920×1080(主流)、2560×1440、3840×2160(4K)。每个分辨率下检查:UI 不超出安全边距(理论上保留 5% 边距)、文字可读、没有元素错位或拉伸、窗口/全屏切换不崩。同时检查**多显示器**:把窗口从主屏拖到副屏,验证不黑屏不崩(这是 Steam Deck Verified 和桌面 cert 都查的)。同时检查**睡眠/唤醒**:游戏运行中让系统睡眠(合上笔记本盖 / 按 Deck 电源键),5 分钟后唤醒,验证游戏正确恢复不崩不丢进度——这一项是 §4 讲的桌面 cert 最常挂的,务必测。每条修复后,跑一遍回归测试网确认没引入新 bug。

**第六步,跑一遍内部 pre-submission cert。** 上面五步是分类走查,这一步是**整体模拟提交**。找一个没参与 HH 项目的朋友(任何不玩游戏的人更好),把你的清单给他,让他**逐条走流程**——他不知道"必须先按 A 再按 B 才不崩"这种开发者盲区,他会按字面意思走,你的盲区就在这里暴露。记录他遇到的每条失败,按 [09G-3](09G-3-alpha-beta-and-content-pipeline.md) §5 的 triage 流程排优先级(A 级 cert blocker 先修),修完跑回归测试网,再请他过一遍失败的条目(确认真修了)。这一步的价值在于**外部视角**——你自己测过的游戏,陌生人第一次玩总能找出你意想不到的崩溃和软锁,这正是平台方 QA 会做的事。

做完六步,你的 HH 项目就有了**一份自己的 TRC 清单 + 验证过的 cert-ready 状态**。这份清单可以一直维护,后续 RC 出来都对照它走一遍。**这一节的核心 take-away 不是"cert 难",而是"cert 可准备"**——一份清单 + 一套自动化测试 + 一次外部走查,你就能从"对 cert 一无所知的业余者"变成"cert-ready 的职业者"。剩下的真提交流程,等你的 HH 真要上架那天自然会走通,因为你已经知道它要什么了。

## 8 · 练习

**练习一(Lv1,概念题)。** 用你自己的话回答:(a) cert 和 quality review 的本质区别是什么?为什么一个"好玩但 cert 不过"的游戏上不了架,而一个"cert 过但不好玩"的游戏能上架?(b) 为什么说"TRC 是事故的化石"?举一个 TRC 规则(本文提到的或你自己想的)的例子,解释它可能源于什么历史事故。(c) 业余者把 cert 当"最后一道坎",职业者把 cert 当"设计约束"——这两种心态在存档系统的设计上具体会怎么体现差别?

**练习二(Lv2,动手实践)。** 完成 §7 第一步——为你的 HH 项目写一份 TRC 风格清单(七类、约 30-50 条规则,每条带验证方法)。然后挑其中**稳定性(STAB)和存档(SAVE)两类**,实际跑一遍走查(§7 第二步、第三步),记录发现的失败。产出:一份清单文档 + 一份走查报告(每条规则 pass/fail,fail 的带复现步骤)。这是把这一篇落到你项目上的最低门槛。

**练习三(Lv3,进阶工程)。** 完成 §7 第六步——找一位不参与你项目的朋友,给他你的清单(练习二的产出),让他逐条走流程,你只观察记录。这一步几乎一定会暴露你自己测不到的失败——可能是某个状态下他找不到"退出"按钮、某个 UI 他在 720p 下看不全、某个操作组合触发了你没见过的崩溃。把这些失败 triage、修复、跑回归测试网、再让他验证。这一步的价值在于让你切身体会"平台方 QA 会找出你什么盲区"。

**练习四(Lv4,设计题)。** 假设你的 HH 项目要从桌面扩展到主机(假设你拿到了 devkit 和授权,但 NDA 限制你不能说细节)。设计一份"从 day 1 为主机 cert 设计"的工程计划:(a) TRC 矩阵怎么维护?哪些角色参与?(b) 哪些规则必须在架构层面 day 1 就做(后期改不了)?具体到你的 HH 项目哪几个子系统要改?(c) 哪些规则可以自动化验证?分别接到 CI 的哪个 job?(d) 提交前内部 pre-submission cert 流程怎么跑?多久一次?写成两页文档,不需要代码。考你能不能把这一篇的概念综合成"上主机"这个真实场景下的可执行计划。

## 9 · 延伸阅读与下一篇

cert 这一块的中文资料极稀缺,主要参考是英文。**Steam 官方文档**(partner.steamgames.com 的 "Steam Deck Verified" 和 "Store Page Requirements" 章节)是桌面端最权威的 cert 参考资料,完全公开,务必通读。**Sony / Microsoft / Nintendo 的公开开发者门户**(developer.playstation.com / developer.microsoft.com / developer.nintendo.com)各自有 TRC/TCR/Lot Check 的公开摘要,完整版需授权但摘要已足以建立心智模型。**Jason Gregory《Game Engine Architecture》第三版**关于主机引擎架构的章节,从引擎设计角度讲"为什么 TRC 规则要求架构层面支持",对理解"day 1 设计"极有价值。

工程实践方面,**GDC Vault 上 "Shipping on Console" 主题演讲**是工业最有价值的一手资料,大量资深制作人讲他们 cert 的血泪故事——尤其推荐前 Sony、Microsoft first-party 工作室工程师的演讲,他们能讲公开层面最深的细节。**Game Developer(gamedeveloper.com)的 postmortem 栏目**有大量"我们 cert 挂了 5 次终于过了"的项目复盘,每篇都是 cert 教训。

本仓库内,这一篇的主题和以下几篇强相关,推荐连读:[09G-3](09G-3-alpha-beta-and-content-pipeline.md) 讲的 Beta/RC 阶段纪律,是 cert 的前置;[09A-4](09A-4-fuzz-determinism-and-regression.md) 的 fuzz 和回归测试网,是 cert 稳定性类的防御武器,在某种意义上 **cert 就是 9A 测试网的最终形态**;[09F-2 / phase-8 savegame-and-serialization](../phase-8/deep-dives/savegame-and-serialization.md) 的版本化存档,直接对接 cert 的 SAVE 类规则;[09F-3](09F-3-cross-platform-and-portability.md) 的 PAL 抽象,是 cert 的 INPT/DISP 类规则在架构层面的兑现(详见 §5 主机概念);[09E-1 到 09E-4](09E-1-reliable-udp-transport.md) 的网络序列,是 cert NET 类规则的工程基础;[phase-8 shipping-appendix](../phase-8/shipping-appendix.md) 的发布附录,从平台分发角度补全这一篇没细讲的"商店页要素、定价、SDK 集成"等桌面细节——这一篇和它强互补,建议两篇一起读;[phase-8 savegame-and-serialization](../phase-8/deep-dives/savegame-and-serialization.md) 详讲了存档版本化和原子写的技术细节,这一篇 SAVE 类规则就是它的应用。

写到这里,9G 序列从"预制作"([9G-1](09G-1-preproduction-and-prototype.md))、"垂直切片"([09G-2](09G-2-vertical-slice.md))、"量产"([09G-3](09G-3-alpha-beta-and-content-pipeline.md))走到了"认证"(这一篇)。你已经知道一款游戏从"做完了"走到"可以上架了",要穿过 cert 这道闸——它查稳定性、存档、输入、显示、网络、平台集成、无障碍,几乎每一条都对应你之前在 9A/9E/9F 阶段该做对的工程纪律。下一篇 [9G-5](09G-5-gold-and-post-launch.md) 离开"过闸",进入"过闸之后那一刻"——**gold master(母版)制作**:当 cert 终于签了字,你怎么把那个 RC build 锁定成不可改的母版、怎么签 release notes、怎么准备 manufacturing(主机压盘)或商店上架(PC)、怎么归档 build 供日后补丁溯源。这是 production 的真正终点,也是把"做完一款游戏"变成"卖出一款游戏"的临门一脚。
