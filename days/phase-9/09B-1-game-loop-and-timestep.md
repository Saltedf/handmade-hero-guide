# 9B-1 · 游戏循环与固定步长

## 0 · 你把游戏发给了用高刷屏的朋友

你跟完 667 天,在 60 Hz 的显示器上把游戏调得手感完美。角色跑得刚好,跳跃弧线优美,碰撞反馈清脆。你满意地把 build 发给一个朋友。朋友用的显示器是 144 Hz 的。十分钟后他给你回消息:你的人物怎么跑得这么快,跳起来能上天。

你的第一反应大概是不信——同一份代码,怎么会跑得不一样快?但你去查,发现朋友说得对。你在一台 144 Hz 的机器上跑了一下,角色确实像打了鸡血。这就是几乎所有游戏开发者职业生涯里都会遇到至少一次的 bug:帧率依赖。它不是偶发的,它是你的代码结构里一颗定时炸弹,只是你的 60 Hz 屏幕刚好让它没炸。

这个 bug 的根源,藏在你那行看起来天经地义的代码里:`pos += vel * dt`。这行本身是对的——速度乘以时间得到位移,物理课本这么教。问题在于,你的游戏里不是每一处都这么规矩。总有一些地方,你写的是 `pos.x += 0.5`,忘了乘 dt。在 60 Hz 的屏幕上,这行每秒执行 60 次,角色每秒多走 30;到了 144 Hz 的屏幕上,每秒执行 144 次,角色每秒多走 72。帧越多,加得越多,角色就越快。你那些乖乘了 dt 的代码帧率无关,你那些忘乘 dt 的代码帧率相关——两者混在一起,游戏在不同刷新率上就表现得不一样。

这是"每帧 dt"这种业余写法的第一个坑。这一篇要讲的是职业引擎怎么彻底绕开这个坑。绕法听起来朴素,但它是你从"能跑的游戏"到"能在任何机器上行为一致的游戏"之间的分水岭。而且它的影响远不止帧率无关——它还是物理稳定、存档可复现、联机可同步的共同前提。一份改造,四处回报。

## 1 · Handmade Hero 的循环,和它没解决的那些事

先看一眼 Casey 在 HH 里用的循环是什么样的。简化掉细节,它的骨架是:测一下从上一帧到现在过了多久,把这个时间差当作 dt,用它推进一切,然后渲染。这个循环教会了你一件根本的事——**游戏就是一个不断更新和渲染的循环**——这件事 Casey 讲得非常清楚,是他的一大功劳。但这个循环没有解决一个更深层的问题:它的 dt 是**浮动的**,跟着真实时间走。

dt 浮动会带来三个层次的麻烦,我们一个一个感受。最浅的一层,就是你刚遇到的那個——帧率依赖。如果游戏里到处都乖乖乘 dt,这层麻烦其实可以避免。但人总会忘,代码总会乱,所以"靠纪律保证每处乘 dt"是脆弱的。

第二层麻烦就严重了,涉及到物理的稳定性。游戏里的物理——弹簧、约束、碰撞响应——本质上是微分方程的数值求解。数值求解有一个特性:每一步的误差,和 dt 的平方相关。dt 小,误差小,求解稳定;dt 大,误差大,求解会发散。如果 dt 是浮动的,你的物理就是一会儿用小步长(稳)、一会儿用大步长(不稳),误差不一致,累积起来就会出现弹簧莫名抖动、物体互相穿透,甚至数值爆炸成 NaN 把整个画面拖垮。这就是为什么你一旦掉帧,物理往往先崩。

第三层麻烦最隐蔽,但最致命,关系到回放和联机。假设你想加个"录像回放"功能——记录玩家的按键,重放时按这些按键模拟,应该能复现完全一样的过程。或者你想做联机,两台机器按同样的输入模拟,状态必须始终保持一致。但你用的 dt 是墙上时钟测的——两台机器的时钟、负载、浮点运算顺序稍有不同,dt 就有微小差异,模拟出来的状态就慢慢分叉,几分钟后彻底 desync。回放复现不了,联机对不上,你查 bug 查到怀疑人生。

这三个麻烦——帧率依赖、物理不稳、无法复现——根子是同一个:你的游戏时间模型是浮动的,跟着现实世界飘。要根治,得让你的游戏逻辑不再依赖现实世界的节拍。

## 2 · 关键的洞察:把模拟时间和真实时间分开

职业引擎的解法,核心是一个听起来很简单的洞察:**让游戏逻辑按自己的固定节拍走,不要管现实世界过了多久。** 但游戏又不能完全无视现实——玩家是在现实时间里玩的,你得让游戏世界的时间和现实时间大致同步,不然游戏就会越走越慢或越走越快。怎么平衡这两个矛盾的要求?

办法是,把时间分成两层,让它们各司其职。一层是**真实时间**,就是墙上时钟——它只负责一件事:测量现实过了多久,然后把这些时间"喂"给游戏。另一层是**模拟时间**,这是游戏逻辑真正使用的时间,它的步长是**固定的**,永远是比如 1/60 秒,不管现实过了多久。

你可以把它想象成拍定格动画。摄影师拍定格动画,是每隔固定的一小段时间,挪一下模型、拍一帧。这个"每隔固定一小段时间"就是模拟时间的步长——固定,不随拍摄现场忙不忙而变。但播放的时候,你可以用任何刷新率的屏幕——24 Hz、60 Hz、144 Hz——来显示这些帧,屏幕和帧之间用插值(补帧、运动模糊)来平滑。拍摄节奏和播放节奏,是两件独立的事。

游戏循环也是这样。你的游戏逻辑(物理、AI、规则)就是"定格拍摄",按固定的 1/60 秒一步步推进。你的渲染就是"播放",跟着显示器的刷新率走——60 Hz 的屏幕一帧,144 Hz 的屏幕也一帧,但它们渲染的内容,是从逻辑最近的两个状态插值出来的。逻辑按固定节拍自顾自地走,渲染按屏幕节拍自顾自地画,两者通过插值联系起来。**逻辑的速率恒定,渲染的速率自由,这就是帧率无关的根源。**

为什么这能同时解决前面那三个麻烦?因为逻辑现在永远用同一个 dt(比如 1/60),你再也不用担心"哪处忘乘 dt"——dt 是常数,乘不乘,行为都是帧率无关的。物理也稳定了,因为每一步的 dt 都一样,误差一致,数值方法在固定 dt 下有数学保证。回放和联机也通了,因为固定 dt 意味着"同样的输入、同样的顺序、同样的 dt"——这三样齐了,模拟出来的状态就完全一样,确定性有了。一份架构,三个回报。

## 3 · 把这个洞察写成代码:累加器和插值

光有洞察不够,得落到代码。我们写一个最小的版本,你能看到它的每一个部分是怎么解决问题的。

先建一个累加器,它是一个累积"现实喂进来的时间"的容器。每一帧,你测一下现实过了多久,把这个时间加到累加器里。然后你检查累加器:如果它攒够了 1/60 秒,就跑一次逻辑步进(用固定的 1/60 推进一次),同时从累加器里扣掉 1/60;如果还攒着没扣完的,就再跑一步,直到累加器里剩下的不够一步为止。最后,你渲染——但渲染时,逻辑的状态是"刚刚跑完若干步之后的状态",它落后现实时间最多一个 1/60 秒。为了画面平滑,你用累加器里剩下的那点时间,在"上一步状态"和"当前状态"之间做线性插值,得到当前这一帧应该画的画面。

代码大概长这样:

```rust
use std::time::Instant;

const FIXED_DT: f32 = 1.0 / 60.0;
const MAX_FRAME: f64 = 0.25;

fn main() {
    let mut state = State::new();
    let mut prev_state = state.clone();
    let mut accum: f64 = 0.0;
    let mut last = Instant::now();

    loop {
        let now = Instant::now();
        let mut frame = now.duration_since(last).as_secs_f64();
        last = now;
        if frame > MAX_FRAME { frame = MAX_FRAME; }
        accum += frame;

        while accum >= FIXED_DT as f64 {
            prev_state = state.clone();
            step(&mut state, FIXED_DT);   // 永远用 FIXED_DT 推进
            accum -= FIXED_DT as f64;
        }

        let alpha = (accum / FIXED_DT as f64) as f32;
        render_lerped(&prev_state, &state, alpha);

        if should_quit() { break; }
    }
}

fn step(s: &mut State, dt: f32) {
    s.pos += s.vel * dt;   // 逻辑永远用固定 dt
}
```

注意这里几个细节,每一个都是踩过坑才留下来的。第一,累加器我用了 f64 而不是 f32。这不是随便选的——游戏长时间运行后,累加器会变成一个不小的数,而 dt 是个很小的数(0.0166)。f32 的精度有限,大数加小数会出现"小数被吃掉"的精度问题,累加到一定程度,加 dt 等于没加,模拟就停摆了。f64 精度高得多,能扛很久。这种坑你不会在第一小时遇到,但游戏跑几个小时就发作,极其难查。从一开始就用 f64 存累加器。

第二,那个 `MAX_FRAME` 看起来突兀,但它是救命的东西。想象你的游戏卡了一下,某一帧真实耗时了 0.5 秒(可能是系统调度、可能是垃圾回收)。如果没有 MAX_FRAME,这 0.5 秒会一次性塞进累加器,导致 `while` 循环里要跑 30 次模拟来追上现实。30 次模拟又很耗时,导致下一帧又卡更久,塞进更多模拟步——这就是所谓的"死亡螺旋"(spiral of death),几帧之内游戏就彻底卡死。MAX_FRAME 的作用是:一旦单帧现实时间超过 0.25 秒,就把它截断成 0.25 秒。代价是游戏会暂时变慢动作(模拟追不上实时),但这比卡死好太多。这是个工程权衡——宁可在卡顿时让游戏慢半拍,也不能让它崩溃。

第三,插值。你在渲染时,逻辑状态落后现实最多一个 FIXED_DT。如果你直接画当前状态,画面会有点抖——因为渲染速率(可能 144 Hz)和模拟速率(60 Hz)不对齐。插值就是,用累加器里剩下的比例 alpha,在 prev_state 和 state 之间做线性插值,得到一个"介于上一步和这一步之间"的中间状态来画。这样画面就平滑了,玩家看到的运动是连续的。注意,这个插值只用来画,不影响真实的状态——真实状态永远是模拟跑出来的整数步。插值是纯渲染层的欺骗手段。

## 4 · 那个最反直觉的事:游戏会主动变慢

讲到 MAX_FRAME,我得停下来讲一件特别反直觉、但你必须接受的事——**一个写得好的游戏循环,在卡顿的时候会主动让游戏变慢。**

新手第一次看到这个现象,通常会觉得是 bug:我电脑卡了一下,游戏里的动作就慢动作了几秒,然后恢复正常。这不就是掉帧吗?不完全是。普通的"掉帧",是渲染速率降低,但游戏逻辑还在按真实时间走,结果是游戏看起来卡顿,但玩法速度没变(只是不流畅)。而我们这里的"变慢",是模拟主动放慢——逻辑不再按现实时间走,而是按它能跟上的速度走,结果是游戏画面可能还流畅(因为渲染是另一层),但玩法时间变长了。

为什么要这样?因为唯一的替代方案就是死亡螺旋。要么"卡时变慢",要么"卡时崩溃",没有第三选项。所有严肃的游戏都选变慢。你在玩 3A 大作时偶尔遇到的"突然慢动作一下",很多时候就是这个机制在工作——它在救你的存档不被物理爆炸毁掉。

接受这件事之后,你就理解了 MAX_FRAME 不是 hack,是循环设计的必要部分。它的值要权衡:设太小,轻微卡顿就触发慢动作,体验差;设太大,卡顿时模拟步太多,有死亡螺旋风险。0.25 秒是个常见的经验值——意味着单帧卡顿不超过 0.25 秒时,游戏正常追上;超过的,变成慢动作。

## 5 · 插值和外推的取舍

渲染插值还有一个更深的取舍值得讲。我说"在 prev 和 state 之间插值",这种做法叫**插值**(interpolation),它的好处是安全——你画的每一帧都是真实模拟出来的状态插值得到,不会出现"不可能的状态"。它的代价是,画面会比现实**落后**最多一个 FIXED_DT,大约 16 毫秒。对大多数游戏,16 毫秒延迟玩家根本感觉不到,插值是首选。

但有些场景对延迟极度敏感——比如竞技射击游戏,几十毫秒的延迟就影响手感;又比如网络延迟补偿,你需要"预测"玩家现在在哪。这些场景会用另一种叫**外推**(extrapolation)的方法:不是在两个已知状态间插值,而是从当前状态、用当前速度,**往前推算** alpha 步,猜出"现在应该在哪"。外推的好处是画面"实时",没有那 16 毫秒落后;坏处是它是在**猜**——如果玩家这一瞬间撞了墙,外推会把他画到墙里一帧,下一帧真实模拟把他弹回来,画面就抽搐一下。

一般的建议是:除非你有明确的理由(竞技、网络补偿),否则用插值。外推是高级技巧,用不好比插值差。HH 这种节奏的游戏,插值完全够。

## 6 · 把它接到上一篇的可测架构上

讲到这里,你应该已经感觉到,这一篇和上一篇 9A-1 是天然搭档。在固定步长架构里,`step` 函数接收一个状态、一个固定 dt、一些输入,返回新状态——它就是一个纯函数。它不碰墙上时钟(墙上时钟在循环的累加器那一层,不在 step 里),不碰随机(随机作为参数注入),不碰渲染(渲染在另一个函数里)。这意味着 step 可以被上一篇的方法测试:你可以给它喂固定种子、固定输入,断言它产出的状态。

你甚至可以给它写 property test。比如数值积分有一个半群性质:跑两次小步,和跑一次大步(步长是小步的两倍),在步长足够小时,结果应该接近。写成 property:`step(step(s, dt), dt)` 应该约等于 `step(s, 2*dt)`,在 dt 小的时候。这条性质一旦不成立,说明你的积分器有问题。这不是我编的——职业物理库会用这类 property 测自己的积分器。

所以你看,固定步长不只是解决了帧率问题,它还把你的游戏逻辑变成了上一篇喜欢的那个形状——纯函数、可测、可回放。这两篇是同一个大思想的两面:**把决策和外部世界分开**。上一篇教你把决策和副作用分开,这一篇教你把决策和现实时间分开。合起来,你的游戏逻辑就住在了一个干净的、自己自足的小世界里,外界(玩家输入、墙上时钟、显示器刷新率)只能在边缘影响它,不能污染它。

## 7 · 行业是怎么走到这一步的

固定步长这个做法,不是某个人天才发明的,是被现实一步步逼出来的。八十年代的主机游戏(NES 那一代)根本不操心这件事——它们假设硬件永远以固定频率跑(NTSC 制式 60 Hz),所以游戏逻辑天然"帧率固定",不存在帧率依赖问题。那个年代的招数简单粗暴:直接把游戏逻辑绑死在硬件刷新率上。代价是游戏和硬件深度绑定,换个制式(PAL 的 50 Hz)就得重新调。

到了 PC 时代,麻烦来了——PC 的刷新率五花八门,玩家的硬件性能天差地别,帧率依赖 bug 大爆发。开发者们开始意识到要乘 dt,但大多数人用的是浮动 dt,也就是 HH 那种。问题只解决了一半。真正的转折,是物理引擎在 2000 年代兴起——Havok、PhysX 这些物理中间件,**要求**使用者用固定步长,否则它们不保证稳定性。这就把固定步长从"可选"变成了"必须",职业引擎纷纷跟进。

但真正把这套做法普及到独立开发者层面的,是 Glenn Fiedler 那篇著名的文章《Fix Your Timestep!》。那篇文章用非常朴实的语言把累加器、插值、死亡螺旋讲透了,网上一搜就有,我应该算是这一篇的祖师爷之一——如果你觉得我讲得还有点绕,强烈建议去读原文,它更短、更直接。从那以后,固定步长 + 累加器 + 插值,就成了职业游戏循环的事实标准。现代引擎在这个基础上又发展出了**子步**(substep,固定步长内部再细分,提升物理稳定性)和**预测-回滚**(rollback,用于联机,见 9E),但底子还是这一篇讲的那些。

## 8 · 把它用到你的 HH 项目上

现在轮到你把 HH 的循环改造成固定步长了。这是这一篇的做中学红线,也是检验你有没有真懂的关键。

打开你的主循环代码,它可能藏在 `main.rs` 或者某个 platform 层里。找到它测量 dt 的地方——大概率是用 `Instant::now()` 算上一帧到现在的差。现在你要做的,是在这个循环里引入累加器和固定步长。加一个 f64 类型的累加器 `accum`,定义 `FIXED_DT` 为 `1.0/60.0`,定义 `MAX_FRAME` 为 0.25。

关键的改造是把原来的 `update(dt)` 拆成两层。把里面真正属于"逻辑"的部分——物理、AI、游戏规则——挪进一个新的 `step(state, FIXED_DT)` 函数,这个函数永远用固定 dt。把渲染留在循环里,每帧都画。然后在累加器够一个 FIXED_DT 时,跑一次 step——可能一帧跑零次(累加器还没攒够)、一次、或多次,取决于真实帧时长和 FIXED_DT 的比值。

加 MAX_FRAME 截断。加渲染插值——先用最简单的,只对位置插值(角度和动画以后再说),在 prev_state 和 state 之间按 alpha 线性插值。

然后做四个验证,每一个都对应前面讲的一个点。第一,如果你有高刷屏或者能调刷新率,确认角色在 60 Hz 和 144 Hz 上跑得一样快——帧率无关。第二,故意在循环里 `sleep(0.5)` 模拟一次卡顿,确认游戏变成慢动作而不是物理爆炸——MAX_FRAME 生效。第三,临时关掉插值再打开,对比画面的平滑度——插值生效。第四,固定随机种子,跑同一个输入序列两次,确认状态完全一致——确定性生效,这是 9A-1 那个"确定性元测试"在循环层面的体现。

做完这四个验证,你的 HH 游戏就跨过了帧率依赖这道业余门槛。它现在物理稳定、可回放、理论上可联机。这是个值得 commit 的里程碑——提交信息可以写"migrate to fixed-timestep loop with accumulator and interpolation",以后回看,这是你从"能跑"到"能在任何机器上行为一致"的关键一步。

## 9 · 练习

练习一,概念辨析。有人问:"我换了 144 Hz 显示器,为了更流畅,我把 FIXED_DT 设成 1/144 行不行?"想清楚为什么不行——FIXED_DT 决定的是模拟的节拍,不是画面的流畅度。画面的流畅度由渲染插值保证,你的渲染照样可以吃满 144 Hz。把 FIXED_DT 设成 1/144 只会让 CPU 每秒多模拟很多次,增加负担,而画面并不会更流畅(流畅靠插值)。FIXED_DT 该设多少,看的是物理需要多细,不是屏幕能画多快。

练习二,动手实践。完成前面 §8 的改造,提交 commit。

练习三,迁移设计。给你的游戏加一个"子弹时间"功能——按住一个键,游戏变 0.3 倍速。在固定步长架构下,正确的做法是**改累加器喂时间的速率**,也就是 `accum += real_frame * time_scale`,而不是改 FIXED_DT,也不是改 step 内部的 dt。想清楚为什么——改 time_scale 是在"现实时间流入模拟时间"的关口上做缩放,模拟本身依然是固定 1/60 一步步走,只是每秒走得少了;而改 FIXED_DT 或 step 的 dt,会破坏物理稳定性和确定性。理解这个区别,你就真正理解了"两层时间"。

练习四,开源贡献。给 Bevy 或者某个开源游戏引擎,补一个"跨帧率确定性"测试——在模拟的 30 Hz、60 Hz、120 Hz、240 Hz 下,跑同一个输入序列,断言最终状态完全一致。这种测试在开源项目里特别稀缺,因为大家都不愿意写,但价值极高——它能抓住"这个引擎到底是不是真的帧率无关"这种根本性问题。
