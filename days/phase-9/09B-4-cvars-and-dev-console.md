# 09B-4 · 控制台变量与开发控制台

## 0 · 你为了调一个数字,编译了四十秒

你做的角色跳跃,起跳速度是 12.0。你跑游戏,试了一下,觉得太飘。你改成 11.5,重新 `cargo build --release`,等了四十秒编译。再跑,又觉得太重。改回 11.8,再编译四十秒。就这样,你为了找到一个舒服的跳跃数值,花了一整个下午,大部分时间在盯着编译进度条。

这种事在游戏开发里天天发生。手感数值、物理参数、渲染选项、调试开关——你一整天都在反反复复地改数字、编译、试玩、再改。如果一个游戏开发者把他的工作日拍成快进视频,你会发现他一半以上的时间在等编译。这不是开发者无能,是工具不行——你把"调参"和"编译"耦合在了一起,每次调参都付出一次完整编译的代价。

这一篇讲的东西,解决的就是这个痛点。它叫 CVar(控制台变量)系统,配套一个开发控制台。它的想法简单到让你生气自己没早点做:**把所有你想调的参数,从代码里挪出来,让它们在运行时可改。** 你跑着游戏,按一个键打开控制台,输入"jump_velocity 11.8",回车,角色立刻用新数值。不用编译,不用重启,实时生效。四十秒的编译循环,变成瞬间的实时调整。

这个东西看起来不起眼,但它是职业引擎最被开发者依赖的基础设施之一。Quake 的开发者们(包括 John Carmack)早在九十年代就发明了它,从此每个像样的引擎都有自己的版本——Source 引擎的 `sv_gravity`、Unreal 的 `r.SSAO`、Unity 的设置面板,都是这个思想的子孙。一个引擎有没有好的 CVar 系统,直接决定了调参的效率,而调参效率直接决定了游戏手感的好坏——因为好手感是试出来的,试的频率越高,手感越好。CVar 把"试一次"的成本从四十秒降到零点几秒,你的迭代速度提升两个数量级,手感打磨自然更精细。

## 1 · CVar 的核心思想:参数和代码分离

在讲实现之前,我把 CVar 背后的思想讲透,因为它不只是一个工具,它是一种关于"什么该写进代码、什么该放进数据"的设计哲学。

你的游戏代码里,有两种截然不同的"数字"。一种是**逻辑常数**——比如"角色的最大生命值是 100",这个数字定义了游戏的基本规则,它在整个游戏生命周期里基本不变,把它硬编码在代码里是合理的。另一种是**调参常数**——比如"跳跃的初始速度"、"摄像机跟随的阻尼系数"、"环境光的强度"。这类数字的特点是:它们的"正确值"你一开始不知道,你必须试才知道;而且就算你定了,后面美术/策划/测试反馈还会反复改。把这类数字硬编码在代码里,意味着每次改都要重编译——但你本来就是要反复试它们,于是你陷入了"改一次编译一次"的泥潭。

CVar 的洞察是:**调参常数不该是代码,它们该是数据。** 代码里只保留一个"引用"(CVar 的名字,比如 `jump_velocity`),真正的值存在一个可变的、运行时可查可改的地方。代码运行时,需要这个值时去查 `cvars.get("jump_velocity")`,拿到当前值。控制台可以改这个值,改了立刻对所有查询生效。更进一步,这些值可以从一个配置文件加载(游戏启动时读 `config.txt`),也可以在游戏里改完后存回去。这样,调参彻底从编译循环里解脱出来——你改的是数据文件和控制台命令,不是代码。

这个"参数即数据"的思想,一旦你内化它,会影响你整个引擎的设计。你会发现,游戏里大量原本"硬编码"的东西,其实都该是数据:关卡布局、敌人属性、UI 布局、按键绑定。把它们数据化,你得到了一个**数据驱动**的引擎——策划和美术可以不碰代码、通过编辑数据和配置就改变游戏,而程序员专注于"系统",内容通过"数据"注入。这是职业引擎和业余项目的根本分野之一。CVar 是这种思想的最小、最具体的起点——它把"调参"这件最频繁发生的事数据化了。

## 2 · 一个最小的 CVar 系统

我把一个最小可用的 CVar 系统写出来,你能看清它的工作机制。

核心是一个全局的、线程安全的映射表,存 CVar 名字到值。值需要支持多种类型(浮点、整数、布尔、字符串),所以用一个枚举:

```rust
use std::collections::HashMap;
use std::sync::RwLock;

#[derive(Clone, Debug)]
pub enum CVarValue {
    Float(f32),
    Int(i32),
    Bool(bool),
    Str(String),
}

pub struct CVarRegistry {
    map: RwLock<HashMap<String, CVarValue>>,
}

impl CVarRegistry {
    pub fn set(&self, name: &str, value: CVarValue) {
        self.map.write().unwrap().insert(name.into(), value);
    }

    pub fn get_float(&self, name: &str) -> Option<f32> {
        match self.map.read().unwrap().get(name)? {
            CVarValue::Float(f) => Some(*f),
            _ => None,
        }
    }
    // get_int / get_bool / get_str 同理
}
```

游戏代码里,凡是原本硬编码调参的地方,改成查询:

```rust
// 改之前:
const JUMP_VELOCITY: f32 = 12.0;
fn jump(player: &mut Player) { player.vel.y = JUMP_VELOCITY; }

// 改之后:
fn jump(player: &mut Player, cvars: &CVarRegistry) {
    player.vel.y = cvars.get_float("jump_velocity").unwrap_or(12.0);
}
```

注意那个 `unwrap_or(12.0)`——这是 CVar 系统的一个好习惯:给每个查询一个默认值。这样,即使某个 CVar 还没被设置(比如游戏第一次跑、配置文件还没生成),代码也不会崩,而是用默认值。这让 CVar 系统对缺失值是健壮的,你可以渐进地把硬编码值迁移成 CVar,不必一次全改。

启动时,从配置文件加载所有 CVar。配置文件用最简单的格式就行——一行一个 `name = value`,比如:

```
jump_velocity = 11.8
camera_damping = 4.5
enable_shadows = true
fov = 75
```

游戏启动时读这个文件,逐行解析、set 进 registry。游戏关闭时(或玩家手动保存时),把 registry 当前值写回文件。这样,玩家(开发者)在控制台改的值,下次启动还在——这是"调参累积"的关键,你今天调好的值不会因为重启丢失。

到这一步,你就有了 CVar 系统的核心。接下来配套一个开发控制台,让玩家能运行时改这些值。

## 3 · 开发控制台:CVar 的交互界面

CVar registry 是后端,开发控制台是前端。它是一个你在游戏里按某个键(通常是 ` 或 ~,Quake 传统)呼出的覆盖层,玩家可以在里面输入命令。

最基础的控制台支持两类输入。一类是赋值,比如 `jump_velocity 11.8`,意思是把 jump_velocity 设成 11.8。另一类是查询,比如 `jump_velocity`,不带值,意思是打印当前值。实现这两类,你就有了一个可用的控制台:解析输入、如果是"名字 + 值"就调 set、如果是"名字"就调 get 并打印。

但一个真正好用的控制台,会在这两个基础之上做很多让交互丝滑的事。它会支持命令历史(上下方向键翻之前输过的命令)、自动补全(输入 `jump_` 按 Tab,列出所有以 `jump_` 开头的 CVar)、帮助(`help jump_velocity` 显示这个 CVar 的含义和取值范围)、命令别名(`god` 是 `player_invincible = true` 的快捷)。这些细节单独看都很小,合起来决定了控制台是"开发者天天想用的工具"还是"摆设"。Quake/Source 的控制台之所以被神化,就是因为这些细节做得极好,玩家可以用控制台做几乎任何调试和作弊。

这里有一个对游戏体验影响巨大的进阶用法:**把 CVar 绑到快捷键和滑块上**。控制台输入适合精确设值,但调手感时你往往想"边玩边连续微调"——这时一个绑定到键盘的"调大/调小"快捷键,或者一个绑定到鼠标的滑块,比输入数字高效得多。比如你把 jump_velocity 绑到 `[` 和 `]` 键,边玩边按,实时感受不同跳跃高度。这种"边玩边调"的能力,是打磨手感的杀手锏——你不再需要"改值→编译→重玩→再改"的慢循环,你在一个连续的试玩过程中,用快捷键实时逼近最佳值。Carmack 说过类似的话:开发工具的响应速度,直接决定了你能达到的手感精细度。CVar 加快捷键,把响应速度提到了极致。

## 4 · CVar 在四个场景里的威力

讲清了机制,我讲四个 CVar 系统特别值钱的具体场景,你会看到它不只是"调数字"这么简单。

第一个,手感打磨,前面已经讲了。跳跃速度、加速度、摩擦系数、摄像机阻尼、攻击判定窗口——这些手感核心参数,全是 CVar。你用一个开发模式,边玩边调,几十分钟就能锁定一套舒服的值。这些值最后会写进配置文件,成为发布版的默认值。好手感是试出来的,CVar 让试的成本趋近于零。

第二个,调试。你怀疑某个敌人 AI 行为不对。你不必在代码里加 print 然后重编译——你打开控制台,`ai_debug enemy_42`,游戏立刻在敌人头上画它的状态、目标、感知范围。你怀疑渲染问题,`r_show_normals 1`,立刻看到所有表面的法线。这些"调试可视化"由 CVar 开关,随时呼出随时关。一个引擎的调试生产力,很大程度上取决于它有多少这种 `xxx_debug` 的 CVar 开关。

第三个,性能排查。`r_shadows 0` 关掉阴影,看帧率涨多少——你就知道阴影占多少。`physics_substeps 4` 改成 1,看帧率涨多少。用 CVar 逐个开关子系统,你能快速定位"是哪个子系统拖慢了帧率",这比上 profiler 还快(虽然 profiler 更精确,见 phase-4/profiling-with-tracy)。CVar 是性能排查的第一道工具。

第四个,开发作弊。`god` 无敌,`fly` 穿墙飞行,`give all` 给所有道具。开发者要快速测试游戏的后半段内容,不想每次从头玩;作弊让测试者瞬间到达任何场景、获得任何状态。这些作弊本质也是 CVar(或基于 CVar 的命令),它们只在开发版存在,发布版编译时移除。

这四个场景,合起来说明了为什么 CVar 是职业引擎的命脉——它贯穿了开发、调试、优化、测试四个环节。Casey 的 HH 没有这个东西(他用的是修改代码重编译),这是 HH 工作流低效的一个主因。你补上它,你的开发效率立刻翻倍。

## 5 · CVar 系统的工程细节和坑

讲完价值,我讲几个工程细节,它们决定了你的 CVar 系统是"好用"还是"累赘"。

首先是**类型安全**。最朴素的 CVar 系统用字符串做值,任何东西都是字符串,读取时再解析。这简单但危险——你 `cvars.set("fov", "seventyfive")`,代码不会报错,但运行时解析失败,fov 变成默认值或 NaN。更好的设计用强类型(前面那个 `CVarValue` 枚举),set 时类型必须匹配,get 时类型检查。Rust 的类型系统在这里特别有用,你甚至可以更进一步,用泛型让每个 CVar 在编译期就有类型:`CVar<f32>`、`CVar<bool>`,这样类型错误在编译期就抓住。这是 Rust 引擎相对 C++ 引擎的一个优势——CVar 的类型安全可以做到编译期。

其次是**性能**。CVar 看起来是"每次查询都要查 hashmap",似乎有开销。但实际上,查询的频率不高(每帧每个 CVar 查询一次,几十次每帧),hashmap 查询的纳秒级开销完全可以忽略。真正在乎性能的热路径(顶点变换、像素着色),它们的常数本来就该硬编码,不该是 CVar。CVar 是给"调参常数"用的,这些地方本来就不在热路径。如果你发现某个 CVar 查询真的在热路径,那说明你把一个**逻辑常数**错误地当成了**调参常数**,把它移回硬编码。

还有一个坑:**多线程下的 CVar 一致性**。如果游戏逻辑线程和渲染线程都读 CVar,而控制台(在主线程)改了 CVar,其他线程什么时候看到新值?最简单的做法是用 `RwLock`,读多写少,锁开销很小。但要注意,你不能在一个帧的中间改 CVar——那会让游戏逻辑用旧值算一半、新值算一半,产生不一致状态。好的做法是:CVar 的修改在帧边界生效——控制台改值只是提交一个"待应用"的变更,真正生效在下一帧开始时,这样一帧内所有查询看到的是同一个一致的值。这是一个细节,但它保证了 CVar 调参时游戏行为的可预测。

最后,**发布版要清理**。开发作弊、调试可视化、内部参数,这些 CVar 不该出现在发布版(作弊会破坏游戏,调试开关浪费性能,内部参数会让玩家困惑)。职业做法是用编译期 feature:`#[cfg(feature = "dev")]` 包住所有开发 CVar,发布版编译时不带 `dev` feature,这些 CVar 整个不存在。Rust 的条件编译让这件事非常干净。

## 6 · 把 CVar 系统用到你的 HH 项目上

这一篇的做中学,是一个性价比极高的工程——你投入一两天,换回整个开发周期里几十甚至上百小时的迭代加速。我建议你尽快做。

第一步,实现前面 §2 那个最小 CVar registry。几十行代码,你半天就能写完。加一个最简单的配置文件读写(用 serde + 一个简单的格式,或者手写逐行解析)。

第二步,实现一个最小开发控制台。在你已有的 immediate-mode UI(phase-5/immediate-mode-ui)基础上,加一个文本输入框 + 历史显示。解析输入,支持"名字 值"赋值和"名字"查询。绑到一个键(比如 ` 键)呼出/收起。

第三步,把你 HH 项目里最常调的几个参数迁移成 CVar。跳跃速度、移动速度、摄像机参数、任何你觉得"老是改、老要重编译"的数字,全部改成从 CVar 查询。这一步你会立刻感受到回报——你边玩边在控制台改这些值,不用编译,手感调整变得极其流畅。

第四步,加几个调试 CVar。比如 `debug_show_hitboxes 1` 显示所有碰撞框、`debug_show_fps 1` 显示帧率、`debug_free_camera 1` 自由摄像机。这些开关让你在调试时随时呼出信息,平时关掉。

第五步(进阶),把常用的手感 CVar 绑到快捷键或滑块上,实现"边玩边连续微调"。用这一步,你会第一次体会到"工具响应速度决定手感精细度"那句话的分量——你的调参变得像调音台一样实时,你能调出之前根本调不出来的手感。

做完这一步,你的开发效率会有一个质的飞跃。这件看似不起眼的基础设施,会成为你 HH 项目里被你依赖最多的工具之一。

## 7 · 练习

练习一,概念辨析。什么样的数字应该是 CVar,什么样的不该?简单标准:如果这个数字你会反复调、它的正确值需要试出来,它就是 CVar;如果这个数字是游戏规则的固定部分、定下来基本不变,它就是硬编码常数。边界情况(比如角色生命值,既是规则又可能要调)按你的实际迭代频率决定。培养这个判断力,你的代码会自然地分成"稳定的逻辑"和"灵活的数据"两层。

练习二,动手实践。完成前面 §6 的 CVar 系统和控制台。提交 commit。把至少 10 个你最常调的参数迁移成 CVar,体验实时调参。

练习三,迁移设计。给你的游戏加一个"调试摄像机"模式——一个 CVar `debug_free_camera 1` 启用后,玩家用 WASD + 鼠标自由飞行看场景,不受游戏逻辑约束。这个功能在调关卡布局、检查渲染问题时极其有用。它需要你把摄像机从"游戏控制"切换到"调试控制",这是 CVar 驱动行为分支的一个典型例子。

练习四,开源贡献。给一个开源游戏或引擎,补一个缺失的调试 CVar 或控制台命令。这类贡献门槛低、价值高、特别受欢迎——因为它是"开发者自己天天会用的东西"。

## 8 · 延伸阅读与序列收口

CVar 和开发控制台没有太多专门的文献,因为它们是"实践出来的"工具,传承自 Quake 一脉。如果你想看活生生的实现,Bevy 的 `bevy_dev_tools`、Source 引擎的开发者控制台(网上有很多 wiki 文档)、Unreal 的 `cvar` 系统,都是参考。直接看任何一个开源游戏(比如 RTS 或 FPS 的开源项目)的控制台实现,能让你对"一个好控制台长什么样"有具体感受。

写到这里,9B 引擎架构序列的四篇就收口了。回头看,它们是从最底层往上搭的:9B-1 给你**稳定的心跳**(固定步长游戏循环),9B-2 给你**规整的器官**(子系统分层、模块化、插件、生命周期、反射),9B-3 给你**会自我组织的渲染**(frame graph),9B-4 给你**掌控一切的手**(CVar 与控制台)。这四层合起来,你的引擎就有了职业级的骨架——它不再是 HH 那个过程式的一大坨,它是一个有层次、可替换、可调度、可实时掌控的结构。

这个骨架,接下来会被两个序列狠狠地用起来。下一篇开始 9C(Vulkan)序列,会用到 frame graph(9B-3)做渲染抽象、用到子系统分层(9B-2)把 Vulkan 后端做成可插拔插件;9A(测试)序列织的安全网,让你敢做大刀阔斧的架构改造;9G(制作交付)序列会用 CVar(9B-4)和测试,把你的游戏打磨到上架品质。你在这里搭的骨架,是后面一切的地基。
