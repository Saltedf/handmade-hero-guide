
# 09G-2 · 垂直切片:用一段最终品质的游戏,证明整条管线跑得通

## 0 · 灰盒子里那个"挺好玩"的核心

你在 [09G-1](09G-1-preproduction-and-prototype.md) 里把原型做出来了。它跑得动,你给朋友玩,他们咧嘴笑了——核心是 fun 的,这件事被证实了,这是整个项目最危险的赌博之一,你已经赢下来了。

但你打开项目,看着那个原型:角色是个白色的立方体,敌人是红色的立方体,地面是一张平的灰色贴图,跳跃没有 squash & stretch,落地没有尘土粒子,音效是你临时找的免费 wav,UI 是 ImGui 默认风格的几行字,掉帧时整个画面会撕裂一下,而内存用量是峰值的两倍,因为资产加载还没做真正的策略。你心里清楚,虽然核心是 fun 的,但这个东西**还不是一个游戏**。它是一个"fun 的核心被装在灰盒子里"的 demo。

现在的问题是:你能把它变成一个真正的、可以发售的游戏吗?你能不能把这个灰盒子,变成有美术、有音频、有 UI、有手感、有性能、在真实引擎上跑的最终品质?——你能做一个核心,但你能不能**做整个游戏**?这个问题,光靠"fun 的核心"是回答不了的。回答它需要一个**证明**,这个证明就是**垂直切片(vertical slice)**。这一篇就讲清楚切片是什么、为什么它是 production 之前最关键的一步、它在你 HH 项目里长什么样。

## 1 · 切片到底是什么:一个词的精确定义

"垂直切片"这个词在游戏行业里被滥用了,所以我要先把它讲精确——因为如果定义模糊,你后面所有判断都会跟着模糊。

垂直切片是一段**小而完整**的游戏:通常是 10 到 30 分钟的实际游玩内容,但这段内容里的**每一个系统都达到了最终品质**——最终美术、最终音频、最终 UI、最终手感、最终性能,全部跑在你真正的引擎上,没有一个是占位的,没有一个标着"以后再修"。用一句行业里反复出现的话说,叫 "**one of each thing, done properly**"——每一样东西有一个,而且做好。

它叫"垂直",是因为它**垂直地切穿所有层**——美术层、音频层、代码层、设计层、UI 层、性能层——每一层都被这一刀切到、并且都在最终品质。它不是"水平的(horizontal)"——水平切是"我做完了一整层",比如"美术层我做完了 50 个关卡"(但没有最终玩法、没有最终音频)。水平切片听起来进展很快,但它没法回答"整条管线能不能跑通"这个问题,因为它只在**一个层**上有进展。垂直切片正好相反:它在所有层上都有进展,但只覆盖**很窄**的一段游戏内容。它深度深、宽度窄,像一根垂直的探针插进游戏里。

举一个具体的形状。假设你的 HH 游戏最终有 50 个关卡、20 种敌人、5 个 boss、完整的故事、多人模式。垂直切片**不是**"做完所有关卡里挑一个给你看"。垂直切片是:做完**1 个**关卡,做完**1 种**敌人,做完**1 个** boss(或者 boss 的 1 个阶段),做完**核心机制**(移动+战斗),做完这一关用到的**所有**美术(场景、角色、特效),做完这一关用到的**所有**音频(BGM、SFX、自适应层),做完这一关的 UI(血条、暂停菜单、关卡完成的结算),做完这一关的**手感和性能调优**(60fps 稳定,输入响应到位)。这一个关卡里,**每一种东西都做到了一个、而且做好了**。这就是垂直切片。

## 2 · 为什么需要切片:它的三个功能

理解切片的价值,要从"它是干什么的"入手。切片有三个不可替代的功能,我把它们一个一个讲。

**第一个功能:证明整条管线能跑通**。这是切片最硬核的价值,也是最容易被忽略的。你在原型里证明了核心 fun,但你没证明"我能把这个 fun,通过一整条生产线——从美术资产到材质到场景到渲染到音频到 UI 到打包到在目标硬件上跑——以最终品质做出来"。这条生产线里有几十个环节,任何一个环节卡住(美术风格统一不了、材质管线有 bug、音频和玩法对不上、UI 性能拖垮帧率、目标机器跑不动),整个游戏就出不来。切片就是**用最小的代价,逼这条整条生产线跑一遍,看它在哪一环卡死**。如果你连一段 5 分钟的最终品质内容都做不出来,那你绝对做不出 50 小时的最终品质游戏——这不是悲观,这是工程现实。切片的价值恰恰是:**它把"我做不出来"这个失败,从 production 中段(那时已经烧了大量预算)提前到 production 之前**。越早发现做不出来,损失越小。

**第二个功能:让团队对"done"对齐**。如果你的团队大于一个人,这个功能至关重要。什么叫"这个游戏做完了"?什么叫"这个美术风格对了"?什么叫"这个手感到位了"?这些问题,如果你只写在 GDD(游戏设计文档)里、口头描述,每个人脑子里的画面是不一样的。美术觉得风格是 A,程序觉得是 B,策划觉得是 C——等到 production 进行到一半,大家发现画面根本对不上,返工的代价是灾难性的。切片消除这个分歧:**它是一个可玩的、可见的、可听的"done"的实物标准**。每个人都看一眼切片,心里就知道"哦,这就是我们要做的东西的样子的,每一样东西都要做到这个水准"。这一个对齐,能省下 production 阶段无数的扯皮。即使你是单人开发,这个功能也在——你自己脑子里"done"的画面,经常在切片做完之后被证伪,你会发现"原来我以为这是 done,但其实这点远没到位"。

**第三个功能:卖**。如果你的项目需要找发行商(publisher)投钱、找发行商发行、上 Kickstarter 给玩家看、做 Steam 的 coming soon 页面吸引 wishlist——你拿什么给他们看?拿一个灰盒子原型?对方会说"我相信这能变好玩,但我不投钱,因为我不确定你能不能把它做完"。拿切片呢?切片就是"我能以最终品质做出来"的**铁证**。发行商看到切片,他评估的就不再是"这个 idea 行不行",而是"这个团队能不能 deliver"——而切片本身就是 deliver 的证据。很多独立游戏的发行合约、众筹的爆红、Steam 上 wishlist 的爆发,就是靠一个扎实的切片。切片是项目"从要钱变到给钱"的转折点。

## 3 · 为什么独立开发者对切片有争议:一个诚实的权衡

讲到这儿,我得讲一个行业里的争议——切片对独立开发者(尤其是单人开发)是不是必要。因为如果你盲目地照搬大厂流程,你可能会把宝贵的预算烧在不该烧的地方。

争议的核心是切片的**成本**。做切片,意味着你要把一些系统**提前打磨到最终品质**——但你后面在 production 阶段会做大量同类内容(100 个关卡、50 个敌人),而做第一个的时候,你经常会发现"这条路不对",于是你要重写。换句话说,**切片里你打磨过的东西,有一部分会在 production 时被推翻重做**。这部分就是切片的"沉没成本",也是反对者最大的论据。

反对派(主要是 indie 圈子)的主张是:独立开发者跳过切片,直接进 production,**边做边迭代**——做完第一个关卡,做完发现不对就改,改完再做第二个,在 production 里持续地打磨和重写。他们认为这比"先做一个切片再开始 production"更省事,因为 indie 通常是一个人或两三个人,沟通对齐成本几乎为零(对齐功能在团队大时才值钱,单人没意义),而且 indie 的发行压力通常更轻(没有发行商逼着要 demo),所以切片的"卖"功能也用不上。这个论据有它的道理。

支持派(主要是大厂和有团队的 indie)的反驳是:**没有切片就进 production,几乎一定翻车**。原因是,如果你没逼自己把整条管线以最终品质跑通,你就不知道这条管线在哪里会卡。结果就是,你做到 production 中段,30 个关卡做完了,突然发现美术风格统一不了(因为你没在切片阶段逼自己统一风格),或者发现某个核心系统在加大量内容后性能崩了(因为你没在切片阶段逼自己上目标硬件跑),或者发现整个项目没有一个统一的"done"标准,每个人做出来的东西质量参差。这种翻车的代价,远高于切片本身的沉没成本。

我给你一个诚实的折中判断,不站队:**切片的价值,取决于"对齐"和"卖"这两个功能对你有多重要**。如果你是一个 5 人以上的团队,需要让大家对 done 标准对齐,或者你需要拿一个 demo 去找发行商/众筹——切片是必须的,沉没成本是值得的代价。如果你是一个纯单人开发,没有团队对齐需求,也不需要找钱,自己出钱自己卖——你可以用一个**轻量版**的切片替代,行业里叫 "**first playable level**":做完第一个真正完整的关卡,但不要求每个系统都到 100% 的最终品质,允许少量占位,只要"玩起来像一个真游戏"就行。这是 indie 的中间路线。但对这个 HH 学习路线,我推荐你做**完整的切片**——因为你的目的不是发售 HH,而是**学习整条管线跑通是什么感觉**,这个学习只有在完整切片里才能完成,first playable level 给不了你这种体验。

## 4 · "最终品质"在每个系统上具体长什么样

切片的纪律,核心就是"每个系统都到最终品质"这句话。但这句话太抽象,我要把它在每个系统上拆开讲——因为"最终品质"在渲染、音频、UI、手感、性能上,各自的含义是不一样的,而且都很容易被你用占位偷懒掉。

**渲染上,最终品质意味着用你真正的 frame graph,不是临时 hack**。这一条对应 [09B-3](09B-3-frame-graph.md) 的帧图。原型阶段你可能为了快速看到效果,绕过 frame graph,直接硬编码几个 pass。但切片里**不允许**这种 hack——切片的渲染必须跑在你最终要交付的那条帧图上,G-Buffer、光照、阴影、TAA、后处理、半透明合成、UI 合成,每一环都按 [09B-3](09B-3-frame-graph.md) 的方式声明式地组织,资源生命周期由帧图自动管,barrier 自动插。为什么这么严?因为如果你切片里绕过帧图,到 production 加大量内容时,你的帧图(那条最终管线)从来没被真正跑过,它一定有 bug——你只是把 bug 推到了 production 阶段爆发,代价更大。切片的纪律就是:**最终要用什么,现在就用什么**。

**音频上,最终品质意味着用你真正的自适应音频系统,不是临时塞几个 wav**。这一条对应 [phase-7 的自适应音频](../phase-7/deep-dives/adaptive-audio-and-3d.md)。原型里你可能直接 `play_sound("jump.wav")`,音量写死,没有 mix 分层,没有自适应强度。切片里不允许——切片的音频必须跑在你最终的 mix bus 架构上(BGM bus、SFX bus、对话 bus,各自有 ducking、有实时参数),必须支持 3D 空间音源(敌人脚步声随距离衰减),必须用真正的中间层格式(不是裸 wav,而是带元数据的、能被 mix 系统理解的资产)。一个常见的偷懒是"音频我用免费的音效库,先把位置占上"——这种占位在切片里不合格,因为最终音频不是"换几个 wav"的事,它是"一套 mix + 自适应 + 空间"的工程,你不在这套工程上跑过一次,你就不知道它和你的玩法、和你的渲染、和你的性能怎么互相影响。

**UI 上,最终品质意味着用你真正的 UI 架构,不是 ImGui 占位**。原型里你用 [phase-7 的 immediate mode editor](../phase-7/deep-dives/immediate-mode-editor.md) 画血条、画菜单,这是开发期工具——快速、方便,但不是最终游戏 UI。最终游戏 UI 要的是**retained mode** 的、有动画、有过渡、有数据绑定的 UI 架构(对应 [phase-7 的 UI 数据绑定](../phase-7/deep-dives/ui-data-binding-short.md))。切片的血条、暂停菜单、结算画面,必须用这个最终架构做,不能是 ImGui。因为 ImGui 是工具,不是游戏 UI——它的字体渲染管线、它的输入处理、它的样式系统、它在 console 手柄上的可用性,都不满足最终游戏 UI 的要求。切片逼你把"游戏 UI 架构"这一环从工具状态升级到产品状态。

**手感(game-feel)上,最终品质意味着调过**。这一条对应 [phase-2 的 game-feel short](../phase-2/deep-dives/game-feel-short.md)。手感不是"功能完成",手感是"参数调到位"——跳跃的曲线、加速度、土狼时间(coyote time)、输入缓冲、命中停顿(hit stop)、屏幕震动、粒子反馈、相机跟随的 deadzone 和弹簧。原型的手感通常是"功能通了但参数是默认值",切片的手感必须是"调过几十遍、玩起来真的爽"。这一个环节特别耗时间——它没有可以抄的代码,只有反复玩反复改。但它是 fun 核心(09G-1 验证过的)和"实际玩起来爽"之间的桥梁,切片必须把这座桥搭好,因为 production 阶段会基于这个"爽的手感"做大量同类内容。

**性能上,最终品质意味着在目标硬件上达到目标帧率**。如果你目标是 60fps on Steam Deck,那切片就必须在 Steam Deck 上稳定 60fps,不能用"反正后面再优化"搪塞。性能问题有个特性:它**很难在后期补救**。如果切片在目标机器上跑 30fps,那你 production 加了 50 倍内容之后,大概率还是 30fps 甚至更糟——因为性能瓶颈往往在架构里(draw call 数量、内存带宽、状态切换),而不是在"内容多了之后才出现"。切片逼你**在架构层面**就把性能问题解决掉,这正是它最值钱的地方之一。配合 [09B-1 的固定时间步](09B-1-game-loop-and-timestep.md),切片要验证的不只是平均帧率,还有**最坏情况帧率**(那一帧有大量敌人、爆炸、特效时,会不会掉)。

## 5 · 切片是 [9A-3](09A-3-integration-and-snapshot-testing.md) 快照测试真正发挥威力的地方

讲到这里我要插一句关于测试的——因为 [9A-3](09A-3-integration-and-snapshot-testing.md) 讲的快照测试,在切片这个节点上,正好发挥它最大的价值。这是时间和场景的精确匹配,你不该错过。

快照测试的核心思想是:把一个**应该稳定不变**的输出(一帧渲染、一段序列化的存档、一次 ECS 状态的导出),保存成基准快照,以后每次跑测试都和基准对比——一旦偏离,测试就红。这件事有一个前提:**你需要一个"稳定不变是对的"的输出作为基准**。在原型阶段,你还没有这种稳定——你每天都在改东西,基准天天变,快照测试一直在更新,价值不大。在 production 后期,基准已经被 100 个关卡覆盖了,再加快照价值也有限,因为大部分 bug 已经在过程中暴露过。

而**切片正好是建立快照基准的最佳时刻**。原因有二。第一,切片做完之后,那一段游戏的"最终品质"已经被所有人(你、你的团队、你的发行商)确认是"对的"——这就是你想要的基准。第二,production 阶段的所有工作,就是"在不破坏切片质量的前提下,加更多同类内容"。所以切片做完的那一刻,你立刻对切片做快照:**渲染快照**(切片里那一帧的画面)、**序列化快照**(切片的存档)、**ECS 状态快照**(切片某一刻的世界状态)、**音频 mix 快照**(某一刻所有 bus 的参数)。建立这组基准之后,production 阶段你做的任何一次修改(改了渲染 pass、改了组件布局、改了 mix 参数),如果意外地动了切片的输出——快照测试立刻红,你立刻知道"我刚才那个改动,不只是加了新内容,还改了切片那部分"。这就是把切片当作"质量锚点"的工程化用法。

具体到 Rust,你可以这样落地。假设你切片的某一帧画面,跑 [09A-3](09A-3-integration-and-snapshot-testing.md) 的 headless 渲染(用 software renderer 或者抓 swapchain),把这一帧的像素存成 PNG 当基准。每次 CI 跑测试,重新渲染这一帧,做像素级(或者带容差的)对比,差异超过阈值就报错。代码上,它可能长这样:

```rust
// tests/vertical_slice_render_snapshot.rs
use insta::Settings;

#[test]
fn slice_climax_frame_matches_baseline() {
    let mut app = build_slice_app();           // 加载切片的关卡、敌人、特效
    app.tick_for(Duration::from_secs(180));    // 推进到切片的高潮帧
    let frame = app.render_headless_frame();   // 软件渲染一帧
    let png = frame.encode_png();

    let mut settings = Settings::new();
    settings.set_snapshot_suffix("climax_frame");
    settings.add_filter(r"\d{4}-\d{2}-\d{2}", "<date>");  // 时间戳不参与对比
    settings.bind(|| insta::assert_binary_snapshot!("climax.png", png));
}
```

这一个测试,把你切片里那个"所有人都确认对的画面",钉死成了基准。后面 production 阶段,无论你做什么改动,只要这一帧变了——你都得解释为什么。这就是切片作为质量锚点的力量,它把"看不见的回归"变成"看得见的红线"。

## 6 · 切片做完了之后:production 是什么

理解切片的最后一个角度,是看它做完之后,production(对应 [09G-3 alpha/beta](09G-3-alpha-beta-and-content-pipeline.md))会变成什么样。因为切片的价值,很大程度上体现在"它让 production 变成了什么"。

切片做完之后,production 在理想情况下,不再是"做新的工程"——而变成了"把切片里做过的事,再做 100 遍"。100 个关卡?每个关卡都按切片那一关的流程做:同样的美术管线、同样的渲染管线、同样的音频管线、同样的 UI 架构、同样的手感调校流程。50 种敌人?每种都按切片那一关的敌人的流程做:同样的动画管线、同样的 AI 框架、同样的碰撞、同样的音效触发。换句话说,**production 是 content scaling(内容规模放大),不是 new engineering(新工程)**。这是一个极其关键的认知转变——如果你的切片做得好,production 阶段你雇佣的主要不再是程序员,而是美术、设计师、音频师;程序员的活从"造新管线"变成"维护管线、做工具支持内容生产"。

当然,理想归理想,实际上 production 一定会有新的工程任务——加新的 boss 机制需要新代码,加多人模式需要新网络层,优化大量内容下的内存占用需要新的资源管理。但**这些新工程,是在一个已经被证明跑通的管线基础上加的,不是从零搭的**。切片保证了这个基础——它就是那个"被证明跑通的管线"。所以你能在 production 阶段比较有信心地说"我们是在加内容,不是在赌能不能做出来",这种信心,正是切片最值钱的回报之一。

这也反向定义了切片做好的标准:**做完切片后,你能指着那一段内容说"剩下的就是按这个套路做 100 倍"**。如果你做完切片后,心里还是没底"剩下 99 个内容,真的能按这个套路做吗?"——那你的切片还没做好,某一个系统还藏着没解的问题,你应该回头把那个系统打磨到位,而不是急急忙忙进 production。这是切片作为"production 闸门"的作用——它过不去,你就不该进 production;它过去了,你进 production 就有了工程上的底气。

## 7 · 在你 HH 项目里动手(做中学红线)

这一篇的做中学,我设计成一次诚实的"自我打脸"练习。它的目的是让你亲身感受到——你以为你离一个游戏很近,实际上你离一个游戏还很远,这个差距就是切片要补的工作。

第一步,从你的 HH 游戏里,挑**一段 5 分钟的切片**。建议是一个关卡(从进入到通关),加上**一种**敌人类型,加上你的核心机制(移动+战斗)。把范围卡死在"5 分钟、一关、一种敌人",不要贪多——切片的核心是"窄而深",不是"宽而浅"。

第二步,对这段切片里的**每一个系统**做一次诚实的盘点,问自己"这个系统到了最终品质吗?"。我列一个清单,你逐项打勾:

- 渲染:这一关的渲染,是跑在你的最终 frame graph([09B-3](09B-3-frame-graph.md))上吗?有没有任何"为了快速看到效果"的硬编码 pass?如果有,改成走帧图。
- 音频:这一关的 BGM、SFX,是跑在你最终的自适应 mix 系统([phase-7 自适应音频](../phase-7/deep-dives/adaptive-audio-and-3d.md))上吗?有没有临时塞的裸 wav?如果有,接到 mix bus 上。
- UI:血条、暂停菜单、关卡结算,是用你最终的 UI 架构([phase-7 UI 数据绑定](../phase-7/deep-dives/ui-data-binding-short.md))做的吗?还是 ImGui 占位?如果是占位,用 retained-mode UI 重做。
- 手感:跳跃曲线、加速度、土狼时间、命中反馈、屏幕震动、相机跟随——这些参数是调过的,还是默认值?([phase-2 game-feel](../phase-2/deep-dives/game-feel-short.md))。如果是默认值,花一两天反复调,调到你玩起来真爽。
- 性能:在你目标硬件(没有目标硬件就用你机器的最差配置模拟)上,这段切片能稳定 60fps 吗?有没有哪一帧掉了?是哪个 pass 慢?([09B-1 固定时间步](09B-1-game-loop-and-timestep.md))。修到稳。
- 资产:这一关的美术、模型、贴图、动画,是你"打算发售时用的"那个品质吗?还是 placeholder?如果是 placeholder,换成最终品质的(可以量少,但品质要对)。

第三步,把你发现的所有"还没到最终品质"的点,列成一个清单。**这个清单,就是你"原型"和"游戏"之间的真实距离**。我跟你打赌,这个清单会比你想的长得多——大多数人做完原型后,会高估自己离游戏的距离。这个清单不是让你沮丧的,它是让你**清醒**的:你现在看到的是真实的工程量,而不是被 fun 核心掩盖的虚幻乐观。

第四步,把这份清单**做完**——把切片里每一个系统,真的打磨到最终品质。这一步会很慢,可能比原型本身还慢几倍。这就是切片的本质——它**就是** production 难度的真实样本,你做这一个关卡的速度,乘以你最终内容数,就是 production 阶段的总工作量。所以你在做这一步时,要计时——"做这一个关卡的最终品质,我花了多久"——这个时间 × 你最终关卡数,就是你 production 阶段的预估工作量(再乘 1.5 到 2 作为安全系数)。

第五步,做完之后,把这个切片拿给一个不知道你项目的朋友玩,看他的反应。如果他说"嗯,有点意思"——你的切片还没到位。如果他说"卧槽,这个真的好玩,什么时候发售?"——你的切片到位了。这种从"有点意思"到"什么时候发售"的反应转变,是切片品质的客观指标。

## 8 · 练习

练习一(Lv1,概念辨析)。一个团队同时拿出了两个 demo:demo A 做完了 50 个关卡,但每个关卡的美术是占位、音频是临时 wav、UI 是 ImGui;demo B 只做完了 1 个关卡,但这一个关卡的所有系统都到了最终品质。哪一个更接近一个可以发售的游戏?写出你的理由(提示:从"整条管线是否被验证过"的角度论证)。这个练习帮你把"垂直 vs 水平"的内化掉。

练习二(Lv2,设计判断)。假设你是单人开发,没有团队,也没有发行压力,完全自费做 HH。基于 §3 讲的争议,你应该如何选择——做完整切片,还是做轻量的 first playable level?写出你的判断和理由。如果你判断要做轻量版,具体说明你会从"完整切片"的要求里砍掉哪些、保留哪些、为什么。这道题没有标准答案,考的是你对切片"成本/价值"权衡的内化。

练习三(Lv3,动手实践)。完成 §7 的完整流程。具体地:挑一段 5 分钟切片,做系统盘点,列出清单,做完打磨,找朋友玩。把这段切片的"打磨前"和"打磨后"录成两个视频(side by side),提交到你的项目仓库。在 commit message 里说明你打磨了哪些系统、各花了多久。这个练习是这个 module 的核心,做完它,你对"切片是什么"的理解会从抽象变成肌肉记忆。

练习四(Lv4,工程化)。完成 [§5](#5--切片是-9a-3-快照测试真正发挥威力的地方) 描述的快照测试落地。具体地:对你切片里的某一帧,写一个 headless 渲染的快照测试(参考 §5 的 Rust 代码),在 CI 里跑起来。然后**故意**改一个无关的渲染细节(比如改一个材质参数),确认快照测试变红——这验证你的快照真的能捕捉到回归。把这个测试加入你的 CI 流水线([09F-1](09F-1-ci-cd-and-build-engineering.md))。这一步是把切片"质量锚点化"的关键,production 阶段它会救你无数次。

关于切片和快照测试的结合,[9A-3](09A-3-integration-and-snapshot-testing.md) 那一篇本身是基础——如果你还没完全消化它,值得回看。关于切片里每个系统的"最终品质"标准,[09B-3](09B-3-frame-graph.md)(渲染)、[phase-7 自适应音频](../phase-7/deep-dives/adaptive-audio-and-3d.md)、[phase-7 UI 数据绑定](../phase-7/deep-dives/ui-data-binding-short.md)、[phase-2 game-feel](../phase-2/deep-dives/game-feel-short.md) 分别给了每个系统的"职业级"长什么样,在打磨切片时它们是你的对照表。

下一篇 [09G-3](09G-3-alpha-beta-and-content-pipeline.md) 讲**production、alpha、beta**——也就是切片做完之后,你如何把"切片的那一套"扩展到整个游戏。production 是内容规模放大的阶段,它有自己的工程问题:如何管 100 个关卡的内容生产,如何在 100 倍内容量下保持质量和性能,什么时候算 alpha、什么时候算 beta、什么时候算 gold(可发售)。切片做完了,你拿到了"做整条游戏的工程底气";9G-3 讲的是,怎么把这份底气,变成一个真正发售出去的游戏。
