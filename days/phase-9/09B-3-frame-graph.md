# 09B-3 · 帧图:让复杂渲染管线自我组织

## 0 · 你的渲染 main,长成了一团意大利面

你在 phase-6 做了延迟渲染,phase-6 又加了后处理,加上阴影、TAA、半透明 pass、UI 合成。你的渲染主函数,一开始只是"清屏、画几何、显示",现在变成了一长串彼此依赖的 pass:先画阴影深度图,再用它画 G-Buffer,再用 G-Buffer 算光照,再 TAA(需要上一帧的历史),再后处理(需要上一 pass 的输出),最后合成 UI。每一个 pass 都需要特定的输入纹理,产出特定的输出纹理,有些纹理要在 pass 之间传,有些只用一次就该释放,有些要在 GPU 和 CPU 之间同步。

一开始你还管得过来。但 pass 越多,你越力不从心。你会发现你花在"管理纹理的创建和释放、pass 的执行顺序、资源的屏障(barrier)"上的时间,超过了你花在"渲染效果本身"上的时间。更糟的是,这个领域极度容易出错——一个屏障放错位置,要么画面撕裂,要么性能暴跌;一个纹理忘了释放,显存一点点泄漏,半小时后崩。而且每次你想加一个新效果,你都得小心翼翼地把它插进这个已经很脆弱的链条里,生怕碰坏别的。

这不是你水平不够,是这个问题的**复杂度超出了人脑能直接管理的范围**。现代渲染管线有几十个 pass、上百个临时资源、错综复杂的依赖,手动管理它,就像手动管理一个有上千行的电子表格里的每一个公式——能做,但极其脆弱。这一篇讲的 frame graph(帧图),就是职业引擎为了对付这个复杂度发明出来的工具。它让你从"手动编排每一步"解脱出来,变成"声明我要做什么",剩下的让图自己算。

## 1 · 核心洞察:把渲染从"怎么做"提升到"做什么"

frame graph 解决问题的方式,背后有一个深刻的转变,值得单独讲,因为它会改变你对渲染编程的整个心智。

在你的意大利面 main 里,你写的是"怎么做"——先做这个、再做那个、这个纹理传给那个 pass、在这里插一个屏障。你扮演一个调度员,事无巨细地指挥每一步。这种命令式风格,在管线简单时很直接,在管线复杂时就是灾难——因为每加一个 pass,你都得重新审视整个调度,确保新东西和旧东西不打架。

frame graph 让你换一种写法:你写的是"做什么"——你声明"我有一个 pass 叫算光照,它需要 G-Buffer 和阴影图作为输入,它产出一个光照结果纹理"。你不写这个 pass 在什么时候执行、纹理什么时候创建什么时候释放、屏障在哪插。你只描述这个 pass 的**意图和它的资源依赖**。然后,你把所有 pass 的这种声明,交给 frame graph。graph 把它们组成一张有向图(pass 是节点,资源依赖是边),然后由 graph 的编译器去算出:每个 pass 实际该在什么时候执行、每个资源该在什么时候创建和销毁、哪些资源可以共用同一块显存(因为它们的生命周期不重叠)、屏障该插在哪里。

这个转变的价值,和数据库的 SQL 是同一个道理。SQL 让你声明"我要什么数据"(select 哪些、join 什么、where 什么条件),数据库的查询优化器去算"怎么最高效地拿到这些数据"(用什么索引、什么 join 顺序)。你不用关心执行计划,优化器替你管。frame graph 是渲染的 SQL——你声明渲染的意图,图编译器替你算执行计划。一旦你接受这个抽象,你就再也回不去手动调度了,就像你写完 SQL 不想回去手写查询循环一样。

## 2 · 帧图的两个关键收益:资源别名和自动屏障

光说"它替你管"不够具体,我讲两个 frame graph 给你带来的、靠人手根本管不好的具体收益,你会立刻感受到它的价值。

第一个是**资源别名**(resource aliasing),也叫内存别名。你的渲染管线里,有大量临时纹理——阴影图只在阴影 pass 用、G-Buffer 只在几何 pass 和光照 pass 之间用、某些中间后处理纹理只在相邻两个 pass 之间用。这些纹理的生命周期大多不重叠。如果你为每个纹理单独分配显存,你的显存占用是所有纹理大小的总和,可能好几个 GB。但实际上,生命周期不重叠的纹理,可以**共用同一块显存**——因为它们不会同时存在。这就叫别名。问题在于,手工算"哪些纹理的生命周期不重叠、可以共用一块内存",在有几十个纹理时,是一个复杂的区间调度问题,人手算极易出错。frame graph 知道每个资源的确切生命周期(它从图的依赖关系算出来的),所以它能自动地做别名——把不重叠的资源叠在同一块显存上,你的显存占用可能从 4GB 降到 1GB。这是一个你自己根本管不过来的优化,frame graph 替你白送。

第二个是**自动屏障**。GPU 上,资源在不同用途之间切换(从"可写"变成"可读"、从"渲染目标"变成"着色器资源"),需要插屏障——屏障告诉 GPU"在这个点,确保前面的操作都完成了,后面的才能开始"。屏障插少了,出现数据竞争,画面错误;屏障插多了,GPU 被迫频繁停顿,性能暴跌。手动管理屏障是 Vulkan/D3D12 编程里最痛苦的部分(9C 你会深切体会到),因为资源在 pass 之间流转,你要追踪它的每个状态转换。frame graph,因为知道每个资源的整个生命旅程,能自动算出屏障该插在哪、插什么类型,既保证正确又最小化停顿。这一项,就让 9C 的 Vulkan 编程从"噩梦"降级到"可控"。

这两个收益合起来,意味着 frame graph 不只是"让代码整齐",它直接决定了你的渲染能不能在现代显式 API(Vulkan/D3D12)上高效运行。没有 frame graph(或类似的抽象),用 Vulkan 写一个有十几个 pass 的渲染管线,人手管理屏障和显存,是一个需要专家级 GPU 程序员几个月的工作。有 frame graph,这件事变成声明十几个 pass 的依赖,剩下自动完成。这就是为什么 Unreal、Unity、Godot 4、Bevy 全都内置了某种形式的 render graph——它不是可选优化,它是现代渲染引擎的标配基础设施。

## 3 · 一个最小的 frame graph 长什么样

我给你画一个最小的 frame graph,你能看清它的结构,以及"声明式"在代码里到底长什么样。

假设你的渲染管线有三个 pass:几何 pass(产出 G-Buffer)、光照 pass(读 G-Buffer,产出光照结果)、后处理 pass(读光照结果,产出最终画面)。在 frame graph 里,你这样声明:

```rust
let gbuffer = graph.create_texture("gbuffer", GBUFFER_DESC);
let lit     = graph.create_texture("lit",     COLOR_DESC);

graph.add_pass("geometry", |pass| {
    pass.write(gbuffer);              // 这个 pass 写 G-Buffer
    pass.render_meshes();             // 实际渲染逻辑(回调)
});

graph.add_pass("lighting", |pass| {
    pass.read(gbuffer);               // 读 G-Buffer
    pass.write(lit);                  // 写光照结果
    pass.compute_lighting();          // 实际光照计算
});

graph.add_pass("post", |pass| {
    pass.read(lit);                   // 读光照结果
    pass.write_to_swapchain();        // 写到屏幕
    pass.tone_map_and_present();      // 色调映射 + 呈现
});
```

注意你**完全没写**的东西:你没写"先 geometry 再 lighting 再 post"的顺序——graph 从 read/write 关系里自己推出这个顺序;你没写 G-Buffer 什么时候创建、什么时候释放——graph 知道它从 geometry pass 开始存在、到 lighting pass 之后没人再读就释放;你没写任何屏障——graph 知道 gbuffer 从"被写"变成"被读"需要屏障,自动插。

你写的就是"有哪些资源、每个 pass 读什么写什么、每个 pass 实际做什么"。这是渲染的意图,不是渲染的执行。graph 编译完之后,会给你一张完整的执行计划,大概可以理解成:"按顺序创建 gbuffer、执行 geometry、插屏障、执行 lighting、释放 gbuffer(后面没人用了)、插屏障、执行 post、释放 lit、呈现"。你甚至可以让 graph 把这张计划打印出来给你看,调试时极其有用——你能一眼看出资源被创建和销毁的时序,屏障插在哪。

这个抽象还有一个隐藏的好处:**它让渲染管线变得可复用、可组合**。你想加一个 TAA pass?声明一个 TAA pass,read 光照结果、write 一个新纹理,然后把后处理 pass 的 read 指向 TAA 的输出。整个管线的其余部分一行不改。你想临时关掉某个效果调试?注释掉那个 pass 的 add 调用,graph 自动重算,不会留下悬空引用。这种"声明式、可组合"在复杂管线上的开发效率,是命令式调度永远比不了的。

## 4 · 瞬态资源和持久资源,以及一个微妙的设计点

讲到这里,有一个设计细节值得单独讲,因为它决定了你的 frame graph 是真好用还是只是一个花架子:资源的**瞬态**与**持久**之分。

你的渲染管线里,大部分资源是瞬态的——一帧内创建、一帧内销毁,下一帧重新来。G-Buffer、阴影图、中间后处理纹理,都是这种。frame graph 对这类资源做别名、自动管理,效果显著。但有一小部分资源是持久的——它们跨帧存在。TAA 需要上一帧的历史纹理;动态环境贴图每隔几帧更新一次,但中间几帧要一直留着;阴影缓存可能跨帧复用。这些资源不能被 frame graph 当作一帧内销毁的瞬态资源处理。

一个设计良好的 frame graph,必须显式区分这两类资源。瞬态资源由 graph 全权管理(创建、别名、销毁);持久资源由 graph 登记但不自动销毁(它的生命周期跨帧,graph 只保证"在需要时可读")。这个区分听起来琐碎,但它是一个非常关键的设计决策——一个把所有资源都当瞬态的 frame graph,无法表达 TAA 这种需要历史帧的效果;一个把所有资源都当持久的 frame graph,享受不到别名带来的显存节省。成熟的实现(Unreal RDG、Bevy render graph)都明确支持这两类。

这个设计点背后,是一个更通用的工程智慧:**好的抽象,要让"常见情况极简,罕见情况可达"**。瞬态资源是渲染的常见情况(90%),frame graph 让你几乎不用想就处理了;持久资源是罕见情况(10%),它需要你多写一点代码(显式登记),但它可达。如果为了那 10% 把抽象做得繁琐,常见情况就遭殃;如果完全不管那 10%,效果就被限制。frame graph 的这个权衡,是这种智慧的一个漂亮范例。

## 5 · frame graph 和 Vulkan 的特殊关系

这一篇是 9B 引擎架构序列的一部分,但它和下一篇开始的 9C Vulkan 序列有极深的联系,我必须在这里点出来,免得到 9C 你觉得"为什么要学这个鬼东西"。

Vulkan 和 D3D12 这种**显式** GPU API,把资源管理和同步的**全部责任**交给了程序员。在 OpenGL 里,驱动替你管了很多(屏障自动、内存管理不透明)——这省心,但也意味着你管不了性能,驱动替你做的决策常常不是最优的。Vulkan 把这些责任还给你,代价是你必须显式地管每一个屏障、每一块显存、每一次同步。这种"极致的控制力"换"极致的复杂度",在有几十个 pass 的渲染管线上,复杂度直接爆炸——你不可能手写几百个屏障还不出错。

frame graph 恰恰是治这个爆炸的药。你声明渲染意图,graph 替你算出 Vulkan 需要的所有屏障、所有显存别名、所有同步。换句话说,**frame graph 是让你用 Vulkan 这种显式 API 还能保持理智的关键中间层**。这就是为什么这一篇紧跟在 9B-2(子系统/模块)之后、又在 9C(Vulkan)之前——它既是引擎架构的深化,又是 Vulkan 的前置准备。等你到 9C,亲手写 Vulkan 的屏障和同步,你会回来感激这一篇让你有了 frame graph 这个盾牌。没有它,Vulkan 的几十个 pass 的管线,几乎是不可维护的。

## 6 · 把 frame graph 用到你的 HH 项目上

这一篇的做中学是一次比较大的工程,但它的影响是结构性的——你的渲染器从"手动调度"升级到"声明式",这对后面所有渲染工作(包括 9C)都是地基。我建议你做一个**最小**版本,而不是一步到位,因为 frame graph 的完整实现是个不小的工程,最小版本能让你抓住核心思想。

第一步,梳理你 HH 渲染器现有的 pass。你大概有几何 pass、光照 pass(如果你做了 phase-6)、可能还有简单的 UI 合成。把这些 pass 列出来,标清每个 pass 读什么纹理、写什么纹理。

第二步,设计一个最小的 frame graph 数据结构。你需要:一个资源描述表(资源名 + 描述)、一个 pass 列表(每个 pass 有名字、read 的资源、write 的资源、一个回调函数)。先不实现别名和屏障,只实现"拓扑排序"——根据 read/write 关系,算出 pass 的执行顺序,并验证没有循环依赖(循环依赖说明你声明错了)。

第三步,把你的渲染器改成用这个最小 frame graph。原来的手动顺序执行,变成"声明 pass + graph 编译 + graph 执行"。这一步的产物是:你的渲染代码从"一串命令",变成了"一组声明"。验证渲染结果和之前完全一致。

第四步(进阶),加上资源生命周期管理——graph 在资源第一次被 write 之前创建,在最后一次被 read 之后销毁。再加上屏障(如果你在 Vulkan/Metal 上;OpenGL 的屏障很弱可暂时跳过)。到这一步,你就有了 frame graph 的核心能力。

第五步(可选,但能让你震撼),让 graph 能打印出它编译出的执行计划——每一步、每个资源的创建销毁时序、每个屏障的位置。把这个计划和你手算的"理想计划"对比,体会 graph 替你省了多少脑力。这个打印功能也是日后的关键调试工具——任何渲染问题,先看 graph 编译出的计划,往往问题立刻显现。

做这个练习时,你一定会卡在某些设计决策上(怎么表达持久资源、怎么处理 swapchain 这种特殊资源、回调怎么写最舒服)。这些卡点本身就是学习——它们逼你想清楚 frame graph 的设计取舍。我建议你参考 Bevy 的 `bevy_render::render_graph`,它是一个完整的、生产级的 frame graph 实现,你的卡点很可能它已经优雅地解决了。

## 7 · 练习

练习一,概念辨析。frame graph 和 ECS 里的"系统调度"有什么异同?两者都是"声明节点 + 依赖关系 + 自动调度",但 ECS 调度的是游戏逻辑系统(关注数据竞争和并行),frame graph 调度的是渲染 pass(关注资源生命周期和 GPU 同步)。理解它们的同构,你能把一套直觉迁移到另一套——这就是 9A-1 讲的"发现同构"的实战例子。

练习二,动手实践。完成前面 §6 的最小 frame graph,把你的几何 + 光照 + UI 三 pass 渲染改成基于 frame graph。提交 commit。

练习三,迁移设计。你的管线要加 TAA(需要上一帧历史)。在 frame graph 里怎么表达?——历史纹理是一个持久资源(跨帧),你需要让 graph 知道它"上一帧 write 的,这一帧 read,这一帧再 write 供下一帧"。想清楚怎么在你的最小 frame graph 里支持持久资源,然后加一个 TAA pass。这个练习让你直面"瞬态 vs 持久"的设计点。

练习四,开源贡献。给 Bevy 的 render graph 补一个文档/示例,或者给某个渲染 pass 写一个基于 render graph 的实现。Bevy 的 render graph 文档相对稀缺,这类贡献很受欢迎。

## 8 · 延伸阅读与下一篇

frame graph 的思想源头,是 Yuriy O'Donnell 在 GDC 2017 的演讲《FrameGraph: Extensible Rendering Architecture in Frostbite》,那是这个概念的奠基性介绍,强烈推荐找来读/看。之后 Unreal 的 Render Dependency Graph(RDG)、Unity 的 SRP、Godot 4 的 RenderingDevice graph、Bevy 的 render graph,都是这个思想的各种实现,各有取舍。读其中一个的实现源码,比读十篇博客都管用。

下一篇 [09B-4](09B-4-cvars-and-dev-console.md) 讲一个看似小、但职业引擎必备的基础设施——CVars(控制台变量)和开发控制台。它让你在不重编译的情况下、在运行时调整任何参数,是打磨游戏手感、调试问题、做开发作弊的核心工具。它也是这一篇 frame graph 的好朋友——你可以用 CVar 在运行时开关 frame graph 的某个 pass,实时看效果。9B 序列到下一篇就收口,你的引擎架构骨架就完整了。
