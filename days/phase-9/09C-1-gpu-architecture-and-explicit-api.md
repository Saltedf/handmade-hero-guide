
# 09C-1 · GPU 真相与显式 API 哲学

## 0 · 你打开 Vulkan 教程,看到第一个三角形要五百行代码

你在 phase-5 学了 OpenGL,画一个三角形几十行代码,清屏、设顶点、画。你觉得你懂 GPU 编程了。然后你决定升级到 Vulkan——现代、专业、所有职业引擎在用的 API。你打开一个 Vulkan 教程,翻到"画一个三角形"那一章,发现要五百行代码。你要创建 instance、physical device、logical device、queue、command pool、command buffer、render pass、framebuffer、pipeline layout、graphics pipeline、swapchain、image view、semaphore、fence……每一个都要好几行设置,每一个之间都有依赖,搞错任何一个都是黑屏或崩溃。

你的第一反应大概是:**这是在开玩笑吗?一个三角形五百行?** 你甚至怀疑自己是不是不适合做图形。然后你可能会退缩,觉得 OpenGL 够用了,干嘛要折腾这个。

这一篇就是来回答你这个怀疑的。我要告诉你,五百行不是 Vulkan 在折磨你,五百行是 GPU 编程的**真相**。OpenGL 那几十行,不是 GPU 编程简单,是 OpenGL 的驱动在背后替你做了那另外的四百多行——而且替你做的方式不一定对、不一定快,你还管不了。Vulkan 把那四百多行还给你了,代价是你要亲手写,回报是你获得了 OpenGL 给不了的控制力和性能。

但你要写好这四百多行,你得先真正理解一件事:**GPU 到底是什么。** 大多数开发者,包括学过 OpenGL 的,对 GPU 的认知是错的——他们把 GPU 当成"一个特别快的 CPU"。这个错误认知,是理解 Vulkan 所有繁琐设计的最大障碍。这一篇就是来纠正这个认知的。一旦你真正理解了 GPU 是什么,Vulkan 的每一个看似变态的设计,都会变得"哦,只能这样"。这是整个 Vulkan 序列(9C,八个 module)的地基,值得你慢下来,把它想透。

## 1 · GPU 不是快的 CPU,它是另一种东西

这是这一篇最重要的几段,请慢读。

CPU 和 GPU 设计哲学完全相反。CPU 被设计成"用所有手段让单线程跑得快"——复杂的分支预测、深流水线、大缓存、乱序执行、推测执行,这些都在做一件事:最小化单线程的延迟。一个 CPU 核心极强,但极复杂、极耗电、芯片面积大,所以一颗 CPU 只能放几个到几十个这样的核心。

GPU 走的是另一条路。它被设计成"用海量并行吞吐压倒延迟"。一个 GPU 核心很弱、很简陋,但 GPU 上能放几千个这样的核心。GPU 处理一帧画面,要算两百万个像素的颜色——它根本不在乎单个像素算多快(单线程延迟),它在乎的是"我能不能同时塞进尽可能多的像素,让吞吐量爆炸"。所以 GPU 砍掉了 CPU 上那些复杂的延迟优化(分支预测、推测执行都几乎没有),把省出来的晶体管全用来堆更多的核心。

这个设计的直接后果,是 GPU 的执行模型和 CPU 完全不同,业界叫它 SIMT(Single Instruction, Multiple Threads)。CPU 你写一个线程,它执行一个指令流。GPU 你写一个 shader,它**同时**在几十上百个"线程"(GPU 叫 warp 或 wavefront)上执行同一条指令。这几十个线程,必须**步调一致**——它们在同一时刻执行同一条指令,只是处理不同的数据(不同的像素、不同的顶点)。这就是 SIMT:单指令、多线程。

这个模型有一个极其重要的推论,你必须刻在脑子里:**如果这几十个线程,在某条指令上走了不同的分支(if/else),GPU 会让两边都执行**。一半线程走 if 分支时,另一半线程被闲置(掩码掉);然后反过来。这叫 warp divergence(线程束分叉),它让你的 shader 在分支处慢一倍。所以 GPU 编程有一个反直觉的规则:**在热路径上,宁可多用数学(用 step/mix/select 这些无分支运算),也少用 if/else**。这不是什么高级优化技巧,这是 GPU 的 SIMT 本性决定的、你必须从第一天就接受的事实。

你可能会问:这和 Vulkan 的繁琐有什么关系?关系极大。Vulkan 之所以要求你显式地声明一切,正是因为它假设你理解你的代码会在这种 SIMT 机器上跑,它把所有能影响性能的决策——数据怎么布局、线程怎么分组、内存怎么放——都交给你,因为它知道这些决策在 GPU 上的影响是决定性的,驱动没法替你做对。OpenGL 屏蔽了这些,你也失去了优化空间。Vulkan 暴露这些,你要先懂 GPU 才能用好。

## 2 · 显存层次:为什么"内存在哪"这么重要

理解了 SIMT,你理解了 GPU 的计算模型。但 Vulkan 还有一个让你头疼的主题——内存。Vulkan 把内存管理几乎全交给了你:你要选择分配哪块内存、把资源绑定到哪、什么时候让 CPU 和 GPU 各自看到更新。要理解为什么 Vulkan 这么执着于让你管内存,你得先理解 GPU 的显存层次。

CPU 的内存模型你熟悉:寄存器最快最小,然后 L1/L2/L3 缓存,然后主存。GPU 也有层次,但它更复杂,因为 GPU 要和 CPU 共享数据。一个典型的 GPU 内存层次长这样:最里面有大量的寄存器(每个线程私有)、然后是共享内存/L1(同一个线程组共享,极快)、然后是 L2 缓存、然后是显存(VRAM,GPU 板上的大内存)、然后是系统主存(CPU 那边,通过 PCIe 总线访问,极慢)。

这里的关键洞察是:**数据放在哪一层,直接决定了访问它的速度,差距是几十倍到几百倍。** 把一个经常访问的纹理放在 VRAM 里,GPU 几十个周期就能读到;如果它不小心还在系统主存里(比如 CPU 刚映射过来的、没拷到 VRAM),每次访问要走 PCIe,几百上千个周期。GPU 程序的性能,很大程度上取决于数据在不在该在的层。

这就引出了 GPU 编程的一条铁律:**合并访问(coalesced access)**。当 SIMT 的几十个线程同时读内存时,如果它们读的是**连续的**地址(线程 0 读第 0 个元素、线程 1 读第 1 个……),GPU 可以把它们合并成一次大事务,极快。如果它们读的是**分散的**地址(线程 0 读第 0 个、线程 1 读第 1000 个),每次都要单独访存,慢几十倍。这条规则,是 9A-1 / phase-4 反复强调的"数据布局影响性能"在 GPU 上的终极版本——在 GPU 上,数据布局(连续 vs 分散)能造成几十倍的性能差。这就是为什么 phase-4 讲的 SoA(Structure of Arrays)布局在 GPU 编程里是命脉——它天然让相邻线程访问相邻数据,合并访问成立。

现在你能理解 Vulkan 为什么让你管内存了。Vulkan 给你显式控制"资源绑到哪块内存、CPU 和 GPU 怎么同步对它的访问",是因为这件事在性能上决定一切。OpenGL 把这些藏在驱动里,驱动尽力而为,常常次优。Vulkan 说:你懂你想要什么,你来管。代价是繁琐,回报是极致性能。

## 3 · 为什么 GPU 需要"同步"——以及为什么这是 Vulkan 最难的部分

讲完了 SIMT 和显存层次,最后一块拼图是**同步**。这是 Vulkan 学习者最痛苦的部分,但理解了它为什么存在,你的痛苦会从"莫名其妙"变成"我知道它要干嘛"。

一台机器上,GPU 和 CPU 是两个独立的处理器,它们各自有自己的时钟、各自并行地工作。CPU 提交给 GPU 一堆工作("画这个"),然后 CPU 继续往下跑,去准备下一帧。GPU 在后面异步地执行那些工作。这里就有一个根本问题:**CPU 怎么知道 GPU 什么时候做完了一项工作,可以安全地读取它的结果?** 以及反过来:**GPU 怎么知道 CPU 已经写完了一块内存,可以安全地读?**

这个问题在单处理器编程里不存在——你执行 x = f(); y = g(x); 编译器保证 f 先做完。但跨 CPU 和 GPU,没有这种自动保证。CPU 提交"画这个,结果写到纹理 T",然后立刻提交"读纹理 T 做后处理"——如果什么都不做,GPU 可能在 T 还没画完时就执行后处理,读到垃圾。你必须显式地告诉 GPU:"这两件事有依赖,第二件必须等第一件完成"。

这就是同步。Vulkan 提供了几种同步原语,每一种对应一类同步需求。Semaphore(信号量)用于 GPU 内部不同队列之间的同步(比如图形队列等传输队列完成拷贝)。Fence(栅栏)用于 CPU 等 GPU(比如 CPU 等 GPU 画完一帧,好重新用那块 command buffer)。Barrier(屏障,在 command buffer 内)用于 GPU 自己的执行顺序和缓存刷新——它说"在这个点,保证前面的 pass 写完、缓存刷对,后面的 pass 才能读"。Pipeline barrier 是 Vulkan 里最常用也最容易出错的同步工具,因为它要精确描述"什么资源的什么状态转换到什么状态"。

Vulkan 的同步之所以难,不是因为它概念多,而是因为**错了不报错**。你少插一个 barrier,GPU 不警告你,它可能恰好还能跑(因为时序碰巧对),也可能画面撕裂、也可能验证层报错。你多插一个 barrier,GPU 不警告你,它就硬等,性能莫名其妙跌一半。同步 bug 是隐形的、时序相关的、不可复现的,是 Vulkan 编程最折磨人的部分。这也是为什么 9B-3 的 frame graph 那么重要——它替你自动算出正确的 barrier,让你从这种折磨里解脱出来。如果你跳过了 9B-3,在学 Vulkan 时你会非常痛苦,强烈建议回过头先理解 frame graph 的精神。

## 4 · 显式 API 哲学:用繁琐换控制,用控制换性能

现在你能完整理解 Vulkan 的设计哲学了。我用一句话概括:**Vulkan 把驱动替你做的所有决策,都还给了你,因为它相信你比你机器里的通用驱动更懂你的具体需求。**

OpenGL 的驱动,被设计成"能处理任何场景的通用优化器"。但通用优化器的问题是,它对你的具体场景的猜测常常是错的。你明明知道这块纹理只读一次,驱动却给它分配了完整的管理结构;你明明知道这两个 pass 没有依赖,驱动却保守地插了同步。这些"通用但保守"的决策累积起来,OpenGL 的性能天花板比 Vulkan 低很多。而且,OpenGL 的驱动复杂、bug 多、不同厂商实现差异大——同样的 OpenGL 代码,在 NVIDIA 和 AMD 上行为可能不同,因为驱动替你做的决策不同。

Vulkan 的赌注是:**如果你愿意亲手、显式地声明每一个决策(资源怎么放、pass 怎么排、什么时候同步),我就给你一个极薄的驱动,几乎不替你做任何决策,但你获得极接近硬件的控制力和一致的跨厂商行为。** 这就是"显式"的含义——所有意图,显式表达,没有隐藏的自动行为。

这个赌注的回报是双重的。第一,**性能**。一个精心写的 Vulkan 程序,比同样的 OpenGL 程序快几倍,因为没有任何保守的自动决策拖累。第二,**可预测性**。Vulkan 的行为在不同 GPU 厂商间高度一致(因为驱动几乎不做决策),你的代码在 NVIDIA 跑通了,在 AMD 大概率也跑通,这在 OpenGL 里是不敢想的。

赌注的代价就是你一开始感受到的那个——**繁琐**。画一个三角形五百行,因为你要显式声明:用哪个 GPU、哪些能力、资源放哪、pass 怎么组织、怎么同步。这些在 OpenGL 里驱动替你猜,在 Vulkan 里你亲自写。但繁琐不等于难,繁琐等于"显式"。一旦你建立了对 GPU 的正确心智模型(SIMT、显存层次、同步),这些繁琐就变成了一种冗长但可预测的声明性工作——你按清单填,不会出错。Vulkan 的难,主要在前置的心智模型;心智模型建立后,剩下的就是工程量。

## 5 · 这个序列会怎么带你爬这座山

这是 Vulkan 序列的第一篇,接下来的七个 module,会一步一步带你从"完全不懂 Vulkan"爬到"能把 HH 渲染的一个 pass 迁到 Vulkan"。我先把路线图给你,让你心里有数。

下一篇 09C-2,我们创建 Vulkan 的"入口"——instance、physical device、logical device、swapchain。这是你用 Vulkan 的第一个窗口,你能在上面……还画不出东西,但你能确认 Vulkan 接管了显示。09C-3 是整个序列最难的一篇——command buffer 和同步。你要理解 GPU 的异步执行模型,学会用 semaphore 和 fence 协调 CPU 和 GPU。这一篇你会卡很久,卡住是正常的,因为这是 GPU 编程和 CPU 编程分道扬镳的地方。09C-4,你终于画出第一个三角形——创建 graphics pipeline、写第一个 vertex/fragment shader、提交 command buffer,屏幕上出现那个著名的三角形。09C-5,你学会用 descriptor 和 uniform buffer 把数据(变换矩阵)从 CPU 传到 GPU,这样你的三角形能动起来。09C-6,加纹理和采样器,三角形有了贴图。09C-7,加深度缓冲和 mesh 加载,你能在 3D 空间里画一个真正的模型。09C-8 是整个序列的毕业——把你 HH 渲染器里的一个真实 pass(比如几何 pass 或光照 pass)从 OpenGL 迁到 Vulkan,作为你的 Vulkan 能力的证明。

整个序列你会反复感受到一个矛盾:Vulkan 的单步都很冗长,但每一步都让你更理解 GPU。爬完这八个 module,你不只是"会用 Vulkan",你是真正理解了 GPU 这个奇妙的机器——这个理解会让你在所有图形工作(无论是写 shader、优化渲染、还是读 Unreal/Bevy 的源码)上都受益。这是图形支柱的"深度攀登",它把你从"会调 OpenGL"提升到"真正懂实时渲染的金属层面"。

一个重要建议,贯穿整个序列:**一定要开 Vulkan validation layers(验证层)**。Vulkan 有官方的验证层,它在你开发时动态检查"你有没有违反 Vulkan 的规则",一旦违反,立刻打印详细错误。没开验证层写 Vulkan,等于盲飞——你的错误不会报错,只会黑屏或崩溃,你完全不知道哪里错了。开了验证层,大部分错误立刻被精确指出。这是 Vulkan 学习和开发的命脉,我们下一篇会讲到怎么开。很多人 Vulkan 学得痛苦,是因为他们没开验证层。

## 6 · 在你开始之前:心态和工具

这个 module 没有动手环节,因为它是概念奠基——你要先想清楚 GPU 是什么,再动手。但有两件事我建议你现在就做。

第一件,装好 Vulkan 的 SDK 和工具。在 Arch 上,`sudo pacman -S vulkan-devel vulkan-tools`,然后用 `vulkaninfo` 确认你的 GPU 和驱动支持 Vulkan。你应该能看到你的 GPU 的能力、内存类型、队列家族。这些信息在 09C-2 你选 physical device 时会逐项用到。现在扫一眼 `vulkaninfo` 的输出,看看 GPU 的"显存堆"有几块、每块多大——你已经在接触"显存层次"这个概念了。

第二件,调整心态。Vulkan 不会让你"快速画三角形",它会让你"慢下来,理解每一步,然后获得极致控制"。第一个三角形要五百行,这是设计的,不是你笨。当你卡在某个概念(command buffer、barrier、descriptor)上几个小时时,记住这是 GPU 编程的真实复杂度,OpenGL 把它藏起来了,Vulkan 把它摊开给你看。卡住是学习,不是失败。而且,我们有 9B-3 的 frame graph 作为最终的解脱——你现在忍受的繁琐,爬到序列末尾后,会被 frame graph 自动处理。短期的痛苦,长期的掌控力,这就是 Vulkan 的交易。

## 7 · 练习

练习一,概念辨析。你的 fragment shader 里写了 `if (dot > 0) color = red; else color = blue;`,在 GPU 上跑。假设同一个 warp 里的 32 个线程,有 16 个 dot>0、16 个 dot≤0。这个 if/else 会怎么执行?——两个分支都会执行,先执行 if 分支(那 16 个不该走的线程被掩码闲置),再执行 else 分支(反过来),warp divergence 让这一段慢了一倍。怎么避免?用无分支的数学:`color = mix(blue, red, step(0.0, dot))`。培养这个"无分支思维"是 GPU 编程的关键技能。

练习二,概念辨析。为什么 GPU 编程偏爱 SoA(Structure of Arrays)布局,AoS(Array of Structures)不合适?因为 SIMT 的相邻线程处理相邻数据时,SoA 让它们读连续内存(合并访问,极快),而 AoS 让它们读跨步内存(分散访问,慢几十倍)。这是 phase-4 SoA 内容在 GPU 上的延续——在 GPU 上,数据布局的性能差是数量级的。

练习三,准备工具。装好 Vulkan SDK,跑 `vulkaninfo`,找到你 GPU 的内存堆信息,试着回答:你的 GPU 有几种内存类型(比如 DEVICE_LOCAL 的、HOST_VISIBLE 的)、每种的用途是什么。这些概念下一篇会用到,先有个感性认识。

练习四,读源码。找一个开源的 Vulkan 项目(比如 `vulkan-tutorials` 的 Rust 版、或者 vkguide),只读它画三角形的代码,不要求懂,数一数它创建了哪些对象(instance、device、queue、command pool、pipeline……)。建立"一个 Vulkan 程序有哪些组成部分"的粗略地图,这样下一篇你逐个学这些对象时,知道它们在整张地图里的大致位置。
