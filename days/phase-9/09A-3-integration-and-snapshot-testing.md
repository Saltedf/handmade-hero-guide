
# 9A-3 · 集成测试与快照测试

## 0 · 那个让你怀疑单元测试的时刻

前两篇你把架构改干净了,给纯函数写了单元测试,又用 property test 喂了上千个随机输入。你的测试套件一跑,全绿,几百个 case,几十毫秒。你觉得自己已经站在测试的制高点上了。

然后你把游戏跑起来,玩了两分钟,角色还是穿墙了。

这种感觉是非常打击人的。你盯着那堵被穿过去的墙,回想你那一片绿的测试,会冒出一个尖锐的问题:我这么多测试都过了,为什么游戏还是坏的?

答案不在你的测试写得不对,而在一个单元测试根本覆盖不到的盲区。你的 `aabb_overlap` 函数单元测试全过——它确实能正确判断两个矩形是否重叠。你的 `resolve_x` 也全过——它确实能把一个矩形推出去。但你游戏里角色穿墙的那一帧,问题不在任何一个单独的函数里,问题在**它们怎么被串起来**:物理系统算出了一帧的位移,碰撞系统用上一帧的位置判断有没有撞,两者之间有一个一帧的时间差,角色速度足够快时,这个时间差就让角色"跨"过了墙。每一个函数单独看都对,串起来就错。这种 bug,你拆成多少个单元测试都抓不到,因为它不在任何一个单元里。

这就是为什么要有集成测试。单元测试保证每个零件合格,集成测试保证零件组装起来能工作。一个像样的测试网,两层都不能少。这一篇讲集成测试,讲怎么测"几个系统协作",然后讲一个游戏开发里特别迷人的东西——**渲染快照测试**,它能抓住一类单元和集成都抓不到的 bug:你看不到的视觉回归。

## 1 · 集成测试测的是什么

集成测试的心智模型很简单,但要讲清楚它和单元测试的边界,免得你写到一半糊涂。

单元测试是把一个函数**孤立**出来测,你给它输入、看输出,理想情况下它不知道世界上还有别的函数存在。集成测试恰恰相反,它故意把好几个模块**放在一起**跑,看它们协作时整体行为对不对。你不是在测"碰撞函数对不对",你是在测"物理推一步,然后碰撞响应一步,然后角色控制器吃这个响应,整个链条产出的角色位置合不合理"。

这两层抓的 bug 是不同的。单元测试抓"零件坏了",集成测试抓"零件之间接错了"。一个角色穿墙的 bug,几乎一定是"接错了"——要么是物理和碰撞的执行顺序错了(先推后判,还是先判后推),要么是两个系统对"角色位置"的理解不一致(一个用中心点,一个用包围盒角),要么是某个系统在另一个系统更新之前就读了状态。这些都是接口层的 bug,藏在模块的缝隙里,只有把模块拼起来跑,才会暴露。

所以集成测试的组织方式和单元测试不同。单元测试你写一个个独立的 `#[test]`,互不相干。集成测试更像"搭一个小型的游戏场景,让它跑几帧,看结果"。你构造一个最小的世界——一个角色、一堵墙、一个初始速度——让循环跑十帧,然后断言角色没有穿墙。这个测试本身可能只断言一件事,但它驱动了一整条系统链路,任何一个环节接口错了,它都会失败。

Rust 里集成测试通常放在项目根的 `tests/` 目录下,和 `src/` 平级。这个位置有讲究——`tests/` 里的代码只能用你库的公开 API,就像一个外部用户。这逼着你的集成测试通过公开接口去驱动系统,而不是扒开内部去摸私有字段。这恰好契合上一篇讲的"测契约不测实现"——集成测试天然就是契约级的。

## 2 · 写一个能抓住穿墙 bug 的集成测试

我们来写一个具体的集成测试,就用刚才那个穿墙场景。这个例子能让你看清集成测试是怎么工作的,以及它和单元测试的根本区别。

先想清楚穿墙 bug 怎么用测试抓住。角色的速度是每秒 20 米,墙厚 1 米。如果每帧固定步长是 1/60 秒,角色每步移动 0.33 米,这远小于墙厚,正常情况下不会穿。但如果某一帧因为某种原因,位移变得很大(比如物理出了一次大冲量),角色可能一步从墙左边跨到墙右边。你单元测碰撞函数时,你不会想到测"角色一步位移 2 米穿过 1 米的墙"这种组合——因为它不在碰撞函数的职责里,它在"位移 + 碰撞"的协作里。

集成测试就把这个协作直接跑出来。你构造一个角色在墙左边、给一个很大的初始速度、跑一帧,然后检查:角色要么被墙挡住(还在左边),要么没碰到墙(速度方向不对)——但**绝不能在墙右边**。如果在右边,就是穿了。把这个断言写成测试:

```rust
// tests/physics_collision_integration.rs
use my_game::{World, step, Vec2};

#[test]
fn fast_moving_player_does_not_tunnel_through_wall() {
    let mut world = World::test_fixture();      // 最小场景:角色 + 墙
    world.set_player_at(Vec2::new(0.0, 0.0));
    world.set_wall_at(Vec2::new(1.0, 0.0), 1.0);  // 墙在 x∈[1,2]
    world.set_player_vel(Vec2::new(50.0, 0.0));   // 极快向右

    for _ in 0..5 {                               // 跑 5 个固定步
        step(&mut world, 1.0 / 60.0);
    }

    let px = world.player_pos().x;
    assert!(px < 1.0 + world.player_half_width(),
        "player tunneled through wall! player_x = {px}");
}
```

注意这个测试的几个特征。它没有 mock 任何东西——它用的是真实的物理、真实的碰撞、真实的角色控制器,只是搭了一个最小场景。它跑了好几步,不是单次调用。它的断言是"整体行为合理"(角色不能在墙右边),而不是"某个内部字段等于什么"。它通过公开 API(`World::test_fixture`、`set_player_at`、`step`、`player_pos`)驱动整个系统。

这个测试今天应该过(假设你的碰撞处理对了)。但它的价值在于:以后任何时候,有人重构了物理或碰撞的执行顺序,或者改了步长,或者"优化"了碰撞检测,导致穿墙回归——这个测试立刻红。它就是那张网,接住单元测试接不住的、接口层的回归。

`World::test_fixture` 是一个值得你专门设计的辅助。它是"测试用的世界构造器",帮你几行代码搭起一个最小但真实的场景。职业代码库里这种 fixture 很多——它们不是测试本身,它们是让集成测试写得动的脚手架。花点时间设计好你的 fixture,你的集成测试就能写得又快又清楚。

## 3 · 那个迷人得多的东西:渲染快照测试

集成测试能抓住"逻辑"层面的回归,但游戏有一大类 bug,它根本不是逻辑错——逻辑全对,但画面变了。这类 bug 你光靠单元和集成测试永远抓不到,因为它们不测画面。这一节讲怎么测画面,也就是渲染快照测试。这是图形开发独有的测试手段,一旦你用过,你就离不开它。

想象这个场景。你优化了一下光照 shader,逻辑上等价,你觉得只是更快了。你跑游戏,肉眼看了一下,画面好像还行,你就提交了。三天后,美术跑过来,说你把整个场景弄暗了半档,他调了两天的颜色全废了。你打开 git,对比那次的改动,shader 看起来确实等价——但你忘了某个中间值的精度从 f32 降到了某处,光照累积下来,整体暗了那么一点点。这种"肉眼一时看不出,但确实变了"的视觉回归,是渲染开发里最烦人的 bug。你不可能每次改 shader 都逐像素对比。

快照测试的想法非常直接:你渲染一帧,把结果存成一张基准图,提交到代码库。以后每次跑测试,重新渲染同一帧,把新结果和基准图逐像素对比。如果差异超过一个阈值,测试失败,告诉你"画面变了"。你看到失败,要么承认"我改坏了,得修",要么"我是故意改的,基准图更新成新的"。这样,每一次画面变化都被强制审视,不再有"偷偷变暗"这种事。

不过这件事做起来有个绕不开的麻烦,你必须从一开始就正视它:**GPU 渲染不是逐像素确定的**。同一个场景,在同一台机器上渲染两次,结果可能有微小差异——驱动版本、抗锯齿的采样模式、不同厂商 GPU 的浮点精度,都会让像素值差几个位。如果你做严格的逐像素对比,GPU 的这种固有抖动会让你天天收到误报,最后你会烦得把快照测试关掉。所以快照测试在游戏里几乎从不做严格的逐像素相等。它做的是"差异在容忍范围内"——比如允许一定比例的像素有一定程度的偏差,或者用感知哈希先粗筛、再细比。你要花心思调这个阈值:太严,天天误报;太松,漏掉真正的回归。

Rust 生态里做这事最顺手的库是 `insta`,它原本是给结构化数据(序列化结果)做快照的,但也能配合图像做视觉对比。思路是:你把渲染结果(或者它的某种摘要,比如降采样后的低分辨率版本、或者感知哈希)交给 insta,第一次跑它存基准,以后跑它对比。还有些团队直接用专门的视觉回归工具,或者干脆把渲染结果降采样到很小(比如 64×64)再逐像素比——降采样本身就把高频噪声平均掉了,对比更稳。

这里有个特别实用的工程技巧,值得单独讲。你存基准图的时候,**不要存全分辨率的最终渲染**——那样太脆,任何一个像素的微小变化都触发失败,而且基准图文件巨大。相反,你存一个"降采样 + 容差"后的摘要。比如把 1920×1080 的画面降采样到 32×18,每个块取平均色,这样你只对比 576 个"色块",每个块容忍小幅偏差。这种粗粒度的对比,既能抓住"整个场景暗了一档"这种大面积回归,又能容忍"某个边缘抗锯齿差了一个像素"这种无害抖动。这是一个典型的"用信息损失换鲁棒性"的工程权衡,你以后在很多地方都会再遇到它。

## 4 · 快照测试的哲学:基准图就是规约

讲完操作层面,我想讲一个更深的东西,因为它会改变你对快照测试的看法。

你可能觉得快照测试有点"低级"——它不就是在比对图片嘛,不像 property test 那么有思想。但换个角度:快照测试的基准图,**其实就是这一帧渲染的规约**。当你把一张基准图提交到代码库,你是在声明:"这,就是正确渲染的样子。" 以后任何人改了渲染,如果画面偏离了这个基准,系统就要求他停下来,要么修复,要么显式地更新基准(并因此承认、并让 reviewer 看到画面变了)。

这个"强制审视每一次变化"的机制,才是快照测试真正的价值。它不是在"测正确性"——画面好不好看是主观的,机器判不了。它在测**不变性**:在你没有明确意图的情况下,画面不应该变。这个不变性约束,把所有无意的、偷偷的、顺手改的视觉变化,都变成了显式的、需要被审视的事件。在一个有美术、有设计师、有 render 程序员协作的项目里,这个约束极其宝贵——它让"谁改坏了画面"这件事永远可追溯。

从这个角度,你能理解为什么快照测试在 CI 里特别有价值。本地开发时,你盯着屏幕,能肉眼看变化。但 CI 不看屏幕——如果没有快照测试,一个远端 CI 跑过的 PR,可能悄悄改了画面,merge 进主干,几天后才被发现。有了快照测试,任何画面变化都在 CI 上变成一个红叉,强制 PR 作者处理。它把视觉回归从"几天后发现"提前到"merge 前发现"。

不过你也得接受快照测试的代价。最大的代价是**基准图维护**。基准图会过期——你故意改了渲染(比如美术调了色调),基准就得更新。在一个快速迭代的项目里,更新基准会变成一件频繁的、烦人的事。缓解的办法是:只对"相对稳定"的场景做快照(比如一个固定的测试关卡,而不是天天变的开发关卡),把快照测试集中在那些"不该变"的地方。快照测试不是越多越好,它是"在关键不变性上设岗哨"。

## 5 · 快照测试的一个微妙陷阱:确定性

快照测试要成立,有一个前提常常被忽略,直到它咬你一口:被测的渲染本身必须是确定的。如果你的渲染里混了上一篇 9A-1 反复强调的"外部源"——比如时间相关的动画、每帧不同的随机——那你存的基准图,下次重跑根本对不上,因为渲染出的画面每帧都不一样。

这把我们绕回到了 9A-1 和 9B-1 的核心思想。你要做快照测试,就必须让测试场景下的渲染是确定的:动画用固定时间,随机用固定种子,相机角度固定。也就是说,快照测试强制你把"决策和外部源分开"——这又是一次"可测架构"的回报。你看,这三篇 9A 是一个紧密的整体:9A-1 给你架构,9A-2 让你能测纯函数,9A-3 让你能测集成和画面,而它们全都建立在你愿意把游戏逻辑做成"确定、可控"的之上。你不会在一份过程式、状态满天飞的代码上做出靠谱的快照测试——这件事从架构层面就被决定了。

这也是为什么 Casey 的 HH 风格代码几乎不可能做快照测试——它的渲染混了太多浮动状态。而你的 HH 项目,经过 9A-1 改造、9B-1 固定步长之后,已经具备了这个前提。所以当你做这一篇的练习时,你会真切感受到:前面打的架构地基,现在开始持续回报你。

## 6 · 把集成测试和快照测试用到你的 HH 项目上

动手时间。这一篇的做中学有两条线,我建议你都做,因为它们测的东西完全不同。

第一条线,写一个集成测试抓住一个真实的接口层 bug。在你 HH 项目里,找一个"物理 + 碰撞"或者"输入 + 移动"的协作链条。搭一个最小的 fixture(一个角色、一个障碍、一个初始条件),让循环跑几帧,断言一个"整体合理"的性质——比如"角色不会穿过障碍"、"角色停在悬崖边不会掉下去"、"连续两次 step 的结果和分两次 step 一样"。这个测试今天应该过。然后,为了验证它真的在守这个性质,故意把物理和碰撞的执行顺序对调(或者改个步长),确认测试变红——证明它在守接口层。改回来。

第二条线,给你的渲染写第一个快照测试。这一条更折腾,但也更值。你需要先准备一个"确定的测试场景":一个固定的关卡(几个固定的几何体、固定的相机、固定的光照),所有动画和随机都用固定值。渲染一帧到一张离屏纹理(FBO,见 phase-5 的 fbo-and-render-to-texture),把这张图降采样到一个很小的尺寸(比如 32×32),存成基准。第一次跑,确认基准生成。然后故意改一个 shader——比如把环境光暗一档——重跑,确认快照测试红。这能让你亲眼看到"偷偷改了画面"被抓住了。改回来,确认又绿。

做第二条线时,你一定会撞上 GPU 不确定性的问题——同一帧渲染两次,某些像素差一两点。别沮丧,这正是这一篇讲"用容差和降采样换鲁棒性"的原因。调你的对比阈值,让无害抖动不触发失败,同时保留对"大面积变暗"这种回归的敏感度。调阈值的过程本身,是极好的工程训练。

如果你卡在"怎么在测试里离屏渲染"这一步,回想 phase-5 你做 OpenGL context 的时候——headless context(无窗口 context)是做 GPU 测试的基础,它让你能在 CI 的无显示环境里跑渲染。这个基础设施如果当时没做,现在补也不晚,它还是 9D GPU 调试的基础。

## 7 · 练习

练习一,概念辨析。有人觉得"我的单元测试覆盖率达到 90%,不需要集成测试了"。这个想法错在哪?单元测试覆盖率再高,测的都是零件。零件全合格,不代表组装起来能工作——接口契约的不一致、执行顺序的错误、状态在不同系统间的误解,都只会在集成时暴露。90% 的单元覆盖率,可能对应 0% 的接口覆盖。集成测试的存在不是为了重复单元测试,是为了覆盖单元测试的结构性盲区。

练习二,动手实践。完成前面 §6 的两条线——一个集成测试,一个渲染快照测试。提交两个 commit。在快照测试的 commit message 里,写下你调阈值时遇到的 GPU 抖动现象和你最终的阈值,这个记录对三个月后的你非常有价值。

练习三,迁移设计。你的游戏有存档功能(关联 phase-8/savegame-and-serialization)。设计一个"存档往返"的集成测试:构造一个游戏状态,存档,读档,断言读回来的状态和存的完全一致。如果发现不一致(比如某个字段忘了序列化),这个测试会替你抓住。再进阶一步,把它变成 property test——对随机生成的状态,往返都该一致。这是上一篇讲的"round-trip"抓手在存档上的应用。

练习四,开源贡献。给一个有渲染的开源项目(bevy 的某个 example、某个渲染库),补一个渲染快照测试。很多开源项目恰恰缺这个——视觉回归全靠人眼。你的快照测试会成为他们 CI 里宝贵的守门员。

## 8 · 延伸阅读与下一篇

集成测试的通用实践,任何一本软件工程的书都会讲,但游戏特有的"fixture 设计"和"渲染快照"这两块,最好的学习是从现有项目里偷师。bevy 的 `tests/` 里有很多集成测试的范例,值得逐个读。视觉回归工具方面,Rust 生态的 `insta` 是主力,它的文档对结构化快照讲得很好,图像快照部分稍弱但能用。

这一篇反复强调的"确定性是快照测试的前提",和下一篇 [09A-4](09A-4-fuzz-determinism-and-regression.md) 的主题完全交汇。下一篇讲两件事:**fuzz 测试**(给解析器喂随机垃圾,确保不崩)和**确定性回放**(录输入、重放、比对状态哈希)。fuzz 是你的 PNG/glTF/存档解析器在恶意输入下的保险;确定性回放是把你这一篇的"单帧快照"升级成"整局过程的快照"——你能录下整局游戏的输入,几个月后重放,确认状态完全一致。这两个加上本篇的渲染快照,你的回归测试网就织成了。下一篇是 9A 序列的收尾,把测试网铺满。
