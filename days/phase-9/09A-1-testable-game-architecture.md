# 9A-1 · 可测试的游戏架构

## 0 · 你坐下来写第一个测试的那一天

想象一下:你跟完了 667 天 Handmade Hero,信心满满地坐下来,要给你的 HH 游戏写第一个测试。你挑了碰撞检测——它看起来最"纯逻辑",应该最好测。你写下 `assert!(collides(player, wall))`,跑 `cargo test`,然后——

它崩了。不是因为碰撞算错了,而是因为 `collides` 函数内部会去取一个全局的 `World`,`World` 又拽着一个 `Renderer`,`Renderer` 要一个 OpenGL context,而你的测试里根本没有窗口。你花了两个小时想"怎么在不开窗的情况下造一个 World",最后放弃了,顺便得出结论:游戏代码大概就是测不了。

这个故事不是虚构的,它是每一个试图给 Handmade Hero 风格代码补测试的人都会撞上的墙。 Casey 自己从来没撞上,因为他从来不写测试。但你要比 Casey 更职业,所以你得正面撞这堵墙,然后理解它为什么存在、怎么拆掉它。

这一篇要讲的就是这件事。但我不会给你一张"可测架构的四大原则"清单让你背——那种东西背了也没用。我要带你从"为什么测不动"开始,一步步推出"测得动"的代码长什么样,以及为什么它不只是更好测,它本身就是更好的代码。

## 1 · 一个函数"测得动"到底意味着什么

在我们谈怎么改之前,先把"测得动"这个词想清楚。很多人模糊地以为"测得动"就是"我能跑它",但这是个太弱的标准——你能跑 HH 整个游戏,但你不能说它"可测"。一个函数真正"可测",意思是:**你能不启动它周围那一大堆东西,就单独验证它对不对。**

把这句话拆开,它其实是在要求三件事。第一,你给它什么输入,它就吃什么输入——它不能偷偷自己去找别的数据。第二,你给它同样的输入,它每次得给你同样的输出——它不能今天高兴给你 3、明天给你 5。第三,它跑完不能顺手把世界改得面目全非,以至于你测下一个函数时得先猜它干了什么。

这三条,如果你用计算机科学的行话说,合起来就是"纯函数"。但我故意没用这个词开头,因为我想让你先感受到:这三条不是某个学术定义,它们就是"我能不能在不头疼的情况下测它"的直接翻译。一个函数测不动,几乎一定是因为它违反了这三条里的某一条——它要么偷偷摸了全局状态,要么偷偷用了墙上时钟或随机数,要么顺手做了渲染、播音这种没法回滚的事。

现在回头看 HH 那段 `collides` 为什么测不动。它违反了第一条:它不接收 World 作为参数,而是去抓一个全局的 World。这一抓,就把 World 背后那一长串依赖(Renderer、context、音频引擎)全拽出来了。你的测试想喂给它一个输入,但它根本不看你喂的输入,它要的是"整个游戏已经搭起来"。这就是为什么你造不出 World——你根本不该造 World,问题出在 `collides` 根本不该去抓它。

至此你已经抓住了这篇 module 的核心洞察:**可测性不是测试技巧问题,是架构问题。** 一个函数测不动,责任不在写测试的人,在写函数的人——他在写的那一刻,就决定了这段代码能不能被单独验证。Casey 写 HH 时从没考虑过这件事(他的目标是把思路讲清楚,不是产出可测代码),所以 HH 测不动。这不是 Casey 的错,但你不能继承这个限制。接下来我们看看,把"测不动"改成"测得动",具体发生了什么。

## 2 · 带你改一遍:从一个测不动的函数说起

我给你一段典型的 HH 风格代码。它做的事很简单:判断玩家和墙有没有重叠,有就把玩家推出去。但它的写法,踩满了我们前面说的所有雷。

```rust
pub fn resolve_collision_bad(w: &mut World) -> bool {
    let now = SystemTime::now().duration_since(UNIX_EPOCH).unwrap().as_nanos();
    w.seed = w.seed.wrapping_add(now as u64);

    let overlap_x = (w.player.x + w.player.w > w.wall.x) && (w.player.x < w.wall.x + w.wall.w);
    let overlap_y = (w.player.y + w.player.h > w.wall.y) && (w.player.y < w.wall.y + w.wall.h);
    let hit = overlap_x && overlap_y;
    if hit { w.player.x = w.wall.x - w.player.w; }
    hit
}
```

我们不急着改。先花点时间看清楚它到底哪里坏。你第一眼可能注意不到 `SystemTime::now()` 那一行——Casey 用墙上时钟当随机种子的习惯,在 HH 里随处可见。但就是这一行,让整个函数变成了"这次跑和下次跑结果不一样"。你的测试里写 `assert!(resolve_collision_bad(&mut w))`,这次过,过两秒再跑,种子变了,可能就不过了。这就是违反了第二条——同输入不同输出。

再看函数签名:`&mut World`。它要一整个可变的 World,意味着你测试前得先造一个 World,测试后 World 被改了、影响后面的测试。更糟的是,真正想测的逻辑(那几行 `overlap_x`/`overlap_y` 的几何判断)被埋在"改 World"的副作用里——你没法只测几何,你必须连着 World 的可变性一起测。

现在我们有了一个清晰的改造方向:把"算几何"这件纯逻辑的事,从"改 World、读时钟"这些副作用里剥出来。

第一步,把重叠判断单独抽成一个函数,只接收两个矩形,只返回一个布尔值。你读这个签名 `fn aabb_overlap(a: &Rect, b: &Rect) -> bool` 就知道,它什么都不依赖,只看两个矩形——这下它测得动了。这不是什么高深技巧,但你体会一下:仅仅是把"判断"和"改状态"分开,函数就从一个"必须开着游戏才能测"的东西,变成了"给它两个矩形就能测"的东西。架构变了,可测性就变了。

第二步,处理那个墙上时钟。注意我们没有"删掉随机",那不现实——游戏确实需要随机。我们做的是:不再让函数自己去抓时钟,而是把随机源作为参数传进来。函数签名变成 `fn step(s: &State, dt: f32, rng: &mut impl Rng)`——随机和时间都成了显式参数。在真正的游戏里,你传一个真随机的 rng;在测试里,你传一个固定种子的 rng。同一个函数,生产用真随机,测试用假随机,代码一行没改。这就是"依赖注入"——不是设计模式书上那个吓人的词,它就是把"函数偷偷抓的东西"变成"别人喂给它的东西"。

改完之后,代码长成这样:

```rust
pub fn aabb_overlap(a: &Rect, b: &Rect) -> bool {
    let ox = (a.x + a.w > b.x) && (a.x < b.x + b.w);
    let oy = (a.y + a.h > b.y) && (a.y < b.y + b.h);
    ox && oy
}

pub fn resolve_x(player: &Rect, wall: &Rect) -> f32 {
    if aabb_overlap(player, wall) { wall.x - player.w } else { player.x }
}

// 执行层:薄,负责可变状态
pub fn step(world: &mut World) -> bool {
    let hit = aabb_overlap(&world.player, &world.wall);
    if hit { world.player.x = resolve_x(&world.player, &world.wall); }
    hit
}
```

然后你给它写测试,几毫秒就跑完了,不需要窗口、不需要 World、不需要时钟:

```rust
#[test]
fn overlapping_rects_are_detected() {
    let a = Rect { x: 0.0, y: 0.0, w: 2.0, h: 2.0 };
    let b = Rect { x: 1.0, y: 1.0, w: 2.0, h: 2.0 };
    assert!(aabb_overlap(&a, &b));
}
```

这里我要让你注意一个你可能觉得多余、但其实特别值钱的测试。除了测"重叠判断对不对",再写一个测试,把同一个函数跑一百遍,断言一百遍结果完全一样:

```rust
#[test]
fn resolve_x_is_deterministic() {
    let player = Rect { x: 1.0, y: 0.0, w: 2.0, h: 2.0 };
    let wall   = Rect { x: 2.0, y: 0.0, w: 2.0, h: 2.0 };
    let first = resolve_x(&player, &wall);
    for _ in 0..100 { assert_eq!(resolve_x(&player, &wall), first); }
}
```

你可能觉得这是废话——纯函数当然每次一样。但这正是它的价值:这个测试**不是为了验证功能**,是为了**抓住"有人不小心又把墙上时钟或全局随机塞回去了"**。游戏代码会反复被人改,有人下次重构手一滑,又写了 `SystemTime::now()`,这个测试立刻红。它是一个自动的"确定性守门员"。把它记住,这是游戏测试特有的、特别有用的招数。

## 3 · 从一次改造里长出来的直觉

你可能已经感觉到,前面那次改造里反复出现的几个动作——把判断和副作用分开、把外部依赖变成参数、把随机和时间显式化——它们不是孤立的技巧,它们背后是同一个思想。我现在把这个思想讲透,因为它比任何"原则清单"都重要。

这个思想是:**把你的游戏想象成一个三明治。** 中间那层最厚,是所有的"决策"——给定现在的状态和输入,下一步状态是什么。这一层必须是纯的,因为它要被反复跑、被测试、被录下来回放、被同步到别的机器。面包上下两片很薄,是"和现实世界打交道"的地方:上面那片负责把现实(玩家按键、墙上时钟、真随机)翻译成输入喂给中间层;下面那片负责把中间层算出来的新状态,变成屏幕上的像素、扬声器里的声音、硬盘里的存档。

为什么必须这么切?因为决策和副作用,根本就是两种截然不同的东西。决策是可重复的——同一个状态和输入,永远得到同一个新状态;副作用是不可逆的——你没法"取消"一次已经发出来的声音。把它们混在一起(像 HH 那样,`update` 里又算物理又渲染又播音),你就既失去了可测性(测决策得扛着副作用),也失去了可重复性(回放时副作用没法精确重演)。把它们切开,决策层自己就变得干净、可测、可回放、可同步——可测性只是副产品,顺带你还得到了联机的能力(决策确定 => 可以锁步同步,见 phase-5 的 netcode)。

这就是为什么我说"可测架构本身就是好架构"。你不是为了测试去扭曲代码,你是把代码组织成了它本来该有的样子——决策在中间、I/O 在边缘。测试只是第一个告诉你"你切对了"的回报。后面 9E 做联机的时候,你会发现同一套切法让你省了巨大的力气;9A-4 做确定性回放的时候也是。**一份架构,三份回报。**

剩下的两个动作——依赖注入和确定性隔离——都是这个"三明治"思想的具体落实。依赖注入回答的是"中间层需要的服务(比如日志、音频)怎么办":答案是不让它自己去抓,由上层通过 trait 喂给它,这样测试时你能喂一个假的(替身),生产时喂真的。确定性隔离回答的是"中间层偷偷用了时钟/随机怎么办":答案是把这些外部源全部参数化,让中间层只接受"已经喂进来的时间值和随机源"。你看出模式了吗?所有这些动作都在做同一件事——**把中间层做得越来越"纯"、越来越不依赖外部世界**,直到它可以被任意次重跑而不改变结果。

## 4 · 测试该钉住什么,不该钉住什么

讲完架构,还有一个容易栽的坑要讲,因为它会让你的测试在几周后变成负担。这个坑是:测试钉错了地方。

新手写测试,常常去钉实现的内部细节——比如断言"调了这个函数后,`world.entities[3].internal_dirty_flag` 变成了 true"。这测试今天过。但两周后你重构 `World`,把 `internal_dirty_flag` 这个字段删了、换成别的事件机制,你的测试全碎——尽管游戏行为完全没变。于是你得出结论"测试维护成本太高",把它们删了。这几乎是所有团队放弃测试的标准剧本。

问题不在测试,在于测试钉错了层级。好的测试钉的是**公开行为**——"这个函数承诺,给定这种输入,产生这种可观察的结果",而不是"这个函数内部用这个字段干那个"。前面那个例子,你不该去读 `internal_dirty_flag`,你应该测"调了 update 之后,再去查这个实体,它报告自己是 dirty 的"——通过公开的查询接口,而不是扒开内部。这样,内部怎么重构都行,只要公开行为没变,测试就稳定。

记住这个区分:**测契约,不测实现。** 契约是你的函数对世界的承诺(给什么输入、出什么可观察结果),实现是它内部怎么兑现承诺。契约稳定,实现天天变。测试跟着契约走,你就能放心重构;测试跟着实现走,重构一次碎一次。这条比任何测试工具都重要。

## 5 · 别人是怎么做的,以及行业是怎么走到这一步的

讲了这么多原则,你可能想知道职业引擎实际长什么样。Rust 生态里最好的例子是 Bevy。它的 ECS 把每个系统(system)写成一个接近纯函数的东西:`fn(query: Query<...>, time: Res<Time>, ...) -> Commands`。系统从 `Query` 读状态、往 `Commands` 写变更,真正的副作用(改世界)由调度器在系统跑完后统一执行。时间不是 `Instant::now()` 偷偷抓的,而是一个 `Time` 资源——你想测一个依赖时间的系统,就往测试用的 App 里塞一个固定的 `Time`。这正是我们前面讲的"外部源参数化"的工业实现,只是做得很优雅。读 Bevy 的 `bevy_ecs/tests/` 你会看到大量这种"搭一个最小 App、塞固定资源、update 一次、查结果"的测试模式——它之所以能这么写,是因为架构本身把决策和副作用切干净了。

行业并不是一开始就接受测试的。九十年代的游戏几乎全靠 QA 手动玩,理由听上去也合理——"游戏太特殊、测不了"。那个年代产出的经典游戏,后遗症很多:存档损坏、平衡性 bug、补丁引入新 bug,根源都是没法回归测试。真正让游戏行业开始认真测试的,是 2010 年代在线游戏的兴起——服务端逻辑如果不测,每次更新都炸服,代价是真金白银。于是出现了一个有趣的现象:服务端先测,客户端后跟。再后来 ECS 流行起来,大家发现一件意外的事——ECS 的系统函数天然接近纯函数,可测性比老式 OOP 引擎好太多。Bevy、Flecs 这些 ECS 引擎的测试覆盖率,普遍高过传统的 Unity/Unreal 代码。这不是因为写 ECS 的人更爱测试,是因为 ECS 的架构本身鼓励决策与副作用分离。又一次印证了我们前面的话:**可测性是好架构的副产品。**

## 6 · 你会在实践中栽的几个坑

讲了理想情况,现在讲现实里你会踩的坑,这样你不至于第一次撞墙就怀疑这套方法。

第一个坑,你已经把所有依赖都参数化了,跑测试还是不确定。你 `println!` 调试,发现某个被调用的辅助函数里还藏了一个 `thread_rng()`——你忘了它也需要参数化。游戏代码里这种"漏网的外部源"特别多,靠记忆难免漏。实用的办法是做一次"确定性审计":用 grep 把代码里所有 `random`、`SystemTime`、`Instant::now`、`std::fs`、`std::net` 找出来,逐个确认它们都在三明治的边缘层、没有藏在你要测的决策层里。我们前面那个 `is_deterministic` 元测试也能自动抓住一部分。

第二个坑,你照"测契约不测实现"写了测试,但还是太脆。这通常是因为你的"契约"暴露了太多内部结构。比如你虽然没测私有字段,但你测的公开 API 返回了一个巨大的、带内部顺序的列表,内部顺序一变测试就碎。解法是让你的公开 API 返回的是"可观察的结果"(比如一个集合,你只断言"包含某些元素",不断言顺序),而不是"内部的快照"。

第三个坑,你为了可测,把所有东西都抽象成 trait,代码变得啰嗦到你自己都看不下去。这是过度抽象。trait 有成本(认知成本,有时还有运行时成本),不该万物皆 trait。务实的标准是:**只为"测试时需要被替换的东西"做 trait**——随机源、时钟、音频、文件 I/O、网络。普通的值类型(向量、状态结构)直接传值就行,别 trait 化。Rust 的泛型让你在需要的地方零成本抽象,在不需要的地方保持简单。

## 7 · 把这套用到你的 HH 项目上

现在轮到你自己动手了。这一节是做中学红线——不是读完就完,是改完你的代码才算完。

打开你 HH 项目的源码,找一个"本该是纯逻辑、但你现在测不动"的函数。碰撞检测、向量数学、AI 的某个决策函数,都合适。找到之后,别急着改,先做一次诊断:grep 它以及它调用的所有函数,看里面有没有 `random`、`Instant`、`SystemTime`、`std::fs`、全局可变 static。把找到的每一个记下来——这些都是阻碍它可测的外部依赖。

然后开始改造。把它的核心逻辑抽成一个纯函数,接收状态和输入作为参数,返回新状态或结果,所有外部源(rng、dt、now)都作为显式参数。原来的函数保留,但现在它只做两件事:调用那个纯函数,以及触发副作用(改全局、调渲染)。这一步的核心是"把决策挪进纯函数,把副作用留在执行层"。

纯函数抽出来之后,给它写至少三个测试:一个正常输入,一个边界输入(零、负数、极值),再加一个我们前面强调的确定性测试(跑一百遍结果不变)。跑 `cargo test`,看到绿。然后做我前面说过、但再强调一次的一步——**故意把纯函数改错**(比如 normalize 漏掉除以 len),确认测试变红。这一步不是为了折腾自己,是为了证明你的测试真的在测这个函数,不是一个永远绿的废测试。看到红、改回来、看到绿,这个测试才算立住了。

最后体会一下你得到了什么:你可以在不开整个游戏的情况下,几毫秒验证这段逻辑的正确性。Casey 做不到这件事,他每次得编译整个游戏、开窗、用手玩。你比他快了几万倍。这就是可测架构给你的回报,而且这只是第一个——后面 9A-2 的 property test、9A-4 的确定性回放,都建立在你现在打好的这个地基上。

进阶一步,如果你愿意:把你全游戏的随机源统一成一个 `GameRng` 类型,封装一个固定种子的 RNG,让全游戏只有一个种子入口。这件事现在看起来不起眼,但到了 9A-4 做确定性回放的时候,你会感谢现在的自己——因为整游戏的随机性都从一个可控的口子进来,回放才可能。

## 8 · 练习

练习一,概念辨析。下面这个函数测得动吗,为什么:`fn is_night() -> bool { SystemTime::now()... }`。测不动,因为它把判断和墙上时钟焊死了。怎么改?把时间作为参数传进来——`fn is_night(now: Duration) -> bool`——测试里传一个固定时间。这个练习看起来 trivial,但它就是这一整篇的缩影:把外部源从"函数内部抓"变成"参数喂进来"。

练习二,动手实践。完成前面 §7 的改造,在你 HH 项目里提交一个"重构加测试"的小 commit。这次 commit 的 message 可以写"extract pure collision logic, add first unit test",以后你回看版本历史,这就是你走向职业化的第一个脚印。

练习三,迁移设计。你的游戏有个伤害计算函数,大概是 `damage = weapon.base * (1 - armor/100) + rand(0..5)`。把它改造成纯函数 `compute_damage(weapon, armor, rng) -> f32`,然后给它设计一个 property test——断言"对所有合法的武器和护甲,伤害非负且不超过某个合理上界"。property test 的具体写法下一篇 9A-2 会系统讲,这里你先体会一下"性质"这个概念:你不是测一个具体输入,你是在声明一条对所有输入都该成立的规则。

练习四,开源贡献。去 Rust 生态找一个你用过的游戏相关 crate——glam、nalgebra、rapier 都行——看它的 `tests/` 目录,找一个没被测试覆盖的公开函数,给它补一个测试,提 PR。这种贡献对项目维护者是实实在在的帮助,而且是你"给真实开源项目贡献代码"的起点,正是这份教程培养你的"开源极客"方向。

## 9 · 延伸阅读与下一篇

如果你被"怎么给老代码补测试"这个问题困扰,Michael Feathers 的 *Working Effectively with Legacy Code* 是这个领域的圣经——Handmade Hero 的代码对你就属于"legacy code",这本书教的就是怎么在不破坏的前提下给老代码织出测试网。Jason Gregory 的 *Game Engine Architecture* 第三章讲工业引擎怎么看模块化与可测,值得对照读。如果你更喜欢看活代码,直接去翻 Bevy 的 `bevy_ecs/src/system/` 和 `bevy_ecs/tests/`,那是可测架构的活教材。

本序列下一篇 [9A-2](09A-2-unit-and-property-testing.md) 会在这个可测地基上,系统讲两件事:单元测试的组织(怎么写得不像草稿),以及 property testing——给你的数学函数喂上千个随机输入,自动找出你做梦也想不到的边界 bug。那是一种一旦用上就回不去的测试方式。

另外,这一篇反复强调的"确定性",在 [phase-8/determinism-and-replay](../phase-8/deep-dives/determinism-and-replay.md) 和 [phase-5/network-multiplayer-models](../phase-5/deep-dives/network-multiplayer-models.md) 里有更深的应用——确定性既是测试的基础,也是联机的基础。这份架构,三处都用得上。
