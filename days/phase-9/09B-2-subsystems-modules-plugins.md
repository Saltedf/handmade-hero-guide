
# 09B-2 · 子系统、模块、插件与生命周期

## 0 · 你的 main.rs 长到了八千行

你跟完 HH,某天打开你的主源文件,发现它已经几千上万行了。里面什么都有——开窗、读输入、跑物理、画图、播音、加载资产、调音量、读配置。一个文件,全部揉在一起。你加个新功能,要翻遍全文件找该插哪儿;你改一个子系统,不知道会不会碰坏另一个;你想让渲染器能换(比如 9C 要做 Vulkan 后端),发现渲染代码和游戏逻辑死死焊在一起,根本拔不出来。

这是过程式代码长大的必然结局。Casey 的 HH 就是这么写的——一个文件,从顶到底,顺着叙事推进。教学上它让你看清了"一个游戏是怎么从零搭起来的",这个价值很大。但这种结构有一个不可逾越的上限:它**无法规模化**。商业引擎有几十万到上百万行代码,如果都揉在一个文件、一个 main 循环里,没人能维护。

这一篇讲怎么把你的引擎从"一坨",变成有层次的、模块化的、可插拔的结构。这件事没有任何神秘的——它的核心就是几条朴素的工程原则,加上把它们一条条落到代码里。但落完之后,你的引擎就有了"器官"——渲染器官、物理器官、音频器官——每个器官各司其职,通过清晰的接口协作,可以单独替换、单独测试、单独开关。这是 9B-1 那个稳定心跳之上,让引擎真正"长得规整"的一步。

## 1 · 先想清楚:子系统为什么要分层

在动手之前,我想先讲一个比"怎么分"更重要的问题——"为什么要分"。因为如果你不理解为什么,你会为了分而分,造出一堆没必要的抽象,最后代码更乱了。

子系统分层的动机,来自一个非常具体的痛点:**循环依赖**。想象你的渲染器需要查物理系统(为了做某些视觉效果),同时你的物理系统又需要查渲染器(为了做某些调试可视化)。两个子系统互相依赖,谁也离不开谁,谁也没法单独测试、单独替换。这种"两个器官长在一起、分不开"的状态,在医学上叫粘连,在工程上叫紧耦合,它是一切维护噩梦的根源。

分层(layering)就是治这个的。你规定一个依赖方向:**上层可以依赖下层,下层不能反向依赖上层**。这样依赖关系永远单向流动,永远不会形成环。比如,游戏逻辑层可以调用物理层(游戏需要物理),但物理层不能调用游戏逻辑层(物理不知道也不该知道"游戏"是什么,它只管算刚体)。物理层如果需要通知上层某件事,它不直接调用,而是发一个"事件"或者通过回调,让上层自己决定怎么处理——这样物理层保持了独立,可以被任何游戏复用,甚至可以单独发布成一个库。

你一旦建立这个"依赖单向流动"的纪律,就会发现一件神奇的事:每个子系统变得可以单独测试、单独替换了。你的物理层不知道游戏存在,所以你可以在测试里只用物理层,造几个刚体,模拟几步,不用开整个游戏——这正是 9A-1 说的可测架构,在这里又一次兑现。你的渲染层不知道游戏逻辑,所以你可以换一个渲染后端(从 OpenGL 换到 Vulkan,也就是 9C 要做的事),游戏逻辑一行不改。分层不只是"代码整齐",它给你的是可测性、可替换性、可复用性——这三个属性,是职业引擎区别于业余项目的根本。

## 2 · 一个最小的分层长什么样

我把一个典型游戏引擎的分层讲一遍,你体会一下依赖是怎么流动的。最底下是平台层——它包装操作系统(winit 开窗、cpal 音频、gilrs 手柄),对上层暴露统一的、跨平台的接口。平台层不知道上面有什么,它只提供能力。再往上是核心层——内存分配器(9B 之后会深讲)、容器、数学库、事件系统。这层是最底层的"引擎基础设施",其他所有东西都站在它上面。再往上是各个功能子系统——渲染、物理、音频、输入、动画,它们依赖核心层,但彼此之间尽量不直接依赖(比如渲染和物理不互相调用,需要协作时通过上层调度)。最上面是游戏逻辑层——它知道游戏的具体规则、玩法、内容,它调用下面的所有子系统,但没有谁调用它。

你注意这个结构的关键:**依赖永远向下,游戏逻辑在最顶**。这意味着,如果你把"游戏逻辑层"整个删掉,剩下的应该是一个**可复用的、不带任何具体游戏内容的引擎**——这个引擎理论上可以用来做另一个完全不同的游戏。Casey 的 HH 之所以做不出这个切分,是因为它的"游戏逻辑"和"引擎"从头就长在一起。而你,现在要主动地把它们分开。这个分离带来的直接回报,就是你以后写第二个、第三个游戏时,可以直接复用这个引擎——而 Casey 的代码,只能服务 HH 这一个游戏。

那么子系统之间需要协作时(它们当然需要),怎么办?答案是显式的、向下的协作机制,而不是直接互调。两个常见的机制:一是事件系统——一个子系统产生事件,放进一个队列,另一个子系统从队列里读,两者不直接认识;二是中央调度——在最上层(游戏逻辑层)有一个调度器,它依次调用各子系统(先物理、再动画、再渲染),由调度器决定顺序和传参,子系统之间不直接见面。Bevy 的 ECS 就是后者的极致形式——系统之间通过共享的组件和资源间接协作,不直接互调。这两种机制,本质都是把"谁依赖谁"变成"谁都依赖中央/都依赖事件总线",从而切断直接耦合。

## 3 · 服务定位:解决"我需要一个全局服务,但又不想硬编码"

分层解决了子系统之间的耦合,但有一个现实问题会冒出来:有些东西几乎所有子系统都需要——日志器、内存分配器、配置、时间。如果每个子系统都在构造时接收这些依赖(构造函数参数),你的构造代码会变得极其啰嗦,每创建一个子系统都要传一堆同样的东西。这是依赖注入的真实代价。

业界对这个的解法叫服务定位器(service locator)或者注册表(registry)。它的思路是:有一个全局可访问的"服务注册表",每个子系统启动时把自己的服务注册进去,需要时从注册表里查。这样,子系统不再是"在构造时接收所有依赖",而是"在需要时去注册表查"。这看起来像全局变量,但它有一个关键区别——你查到的是一个**trait 对象**(接口),不是具体类型,所以你可以替换实现(测试时换 mock,生产时换真的)。

但服务定位器是个有争议的模式,我得把它的坑讲清楚,不然你会滥用。它的最大风险是:**它让依赖关系变得隐式了**。一个函数表面不接收任何依赖参数,但它内部偷偷去注册表查了一个日志器、一个时间源——这让函数的依赖不透明,违反了 9A-1 讲的"依赖显式化"原则。所以服务定位器要慎用——它适合"真正全局、真正到处都用、且不常变化"的基础服务(日志、内存、时间),不适合业务逻辑。一个折中且更安全的做法是:服务定位器在引擎**初始化**时用(把所有服务注册进去),但具体子系统还是通过构造函数接收它需要的服务——这样初始化方便,但运行时依赖仍然显式。这是 Bevy 的 `App` + `Resource` 模式的精神:Resources 存在 App 里(像注册表),但系统通过参数显式声明它需要哪些 Resource。

## 4 · 插件:让子系统可插拔

分层和服务定位给了你"子系统解耦",但还有一步更进一步的抽象——插件。插件解决的问题是:你能不能让一个子系统**整个地可选**?比如你的游戏支持"有物理"和"无物理"两种模式(无物理用于菜单画面),或者你想让渲染后端可换(OpenGL vs Vulkan),或者你想让用户(模组作者)给游戏加新功能而不改源码。

插件的思路是:把每个子系统封装成一个**自包含的单元**,它知道自己怎么初始化、怎么注册到引擎、怎么更新、怎么关闭。引擎维护一个"插件列表",启动时遍历它、逐个初始化;运行时遍历它、逐个更新;关闭时反向遍历、逐个关闭。要加一个功能,就把对应插件加进列表;要去掉,就移除。整个引擎的行为,就是它启用了哪些插件的总和。

Bevy 的 `Plugin` trait 是这个模式的教科书级实现。每个插件实现一个 `build` 方法,在里面把自己需要的系统、资源、事件注册到 `App` 里。一个 Bevy 游戏的 `main`,就是把一系列插件加进 App:加 `CorePlugin`(基础)、加 `WindowPlugin`(窗口)、加你要的渲染后端插件、加你的游戏逻辑插件。要换渲染后端?换个插件。要禁用物理?不加物理插件。这种"组合出引擎"的能力,让 Bevy 极其灵活——同一个引擎核心,能做 2D 游戏、3D 游戏、工具软件、甚至非游戏的实时应用,全靠启用的插件不同。

插件化的代价是它要求你的子系统真的解耦——每个插件不能假设别的插件一定存在(它可能被禁用)。这逼着你设计清晰的接口和可选依赖,短期看是负担,长期看是巨大的灵活性。如果你 HH 项目的渲染和游戏逻辑死焊在一起(很可能如此),插件化它就是一次痛苦但值得的重构——你会被迫把它们切开,而切开的回报是,9C 的 Vulkan 后端可以作为一个可插拔的渲染插件存在,游戏逻辑完全不感知。

## 5 · 生命周期:初始化和关闭的顺序陷阱

讲到子系统组织,有一个特别阴险的坑必须单独讲,就是**初始化和关闭的顺序**。这个坑不会让你的代码编译失败,但会让它运行时神秘崩溃,而且极难定位。

初始化的顺序问题长这样。假设你的渲染子系统初始化时,需要从资产管线加载一个默认材质;而资产管线初始化时,需要一个内存分配器。如果你不小心先初始化了渲染,再初始化资产管线,再初始化内存——渲染在初始化时去找资产管线,资产管线还没准备好,要么 panic,要么拿到一个空状态,后面某帧崩溃。这种 bug 的难缠之处在于,崩溃点离错误点(初始化顺序错)可能隔了几千行代码、几秒钟的运行时间,你盯着崩溃栈,根本看不出是初始化顺序的锅。

关闭的顺序问题是镜像的,但更阴险,因为它涉及资源泄漏和 use-after-free。如果你先关闭了内存分配器,再关闭渲染子系统——渲染在关闭时还要释放显存里的一些东西,可能触发对已释放内存的访问,直接段错误。正确的关闭顺序必须和初始化顺序**严格相反**——后初始化的先关闭,先初始化的后关闭,像一个栈。这个"栈式生命周期"是工程上的铁律,因为依赖关系决定了它:被依赖的东西必须活得比依赖它的东西久。

处理这个,职业做法是**集中式生命周期管理**——有一个中央的初始化器,它维护一个有序的子系统列表,按顺序逐个初始化,把每个子系统的"关闭句柄"压栈;关闭时从栈顶逐个弹出来关闭。这个集中管理消除了"到处手动调 init/shutdown、顺序靠记忆维护"的脆弱。更先进的做法是用 Rust 的**所有权**让编译器帮你管——子系统之间的依赖通过 ownership 表达(渲染器 own 资产管线的一个引用,资产管线 own 内存分配器),这样 Rust 的生命周期检查器会**强制**保证:被引用的东西不会先于引用者被销毁。这是 Rust 在引擎架构上的一个独特优势——很多 C++ 引擎里需要靠纪律维护的生命周期顺序,Rust 让编译器替你管。

## 6 · 反射:让数据驱动成为可能

这一篇最后一个主题是反射(reflection),它听起来抽象,但它是后面好几个东西的基础——数据驱动设计、序列化、脚本、编辑器——所以值得在这里讲透。

先说反射要解决的问题。你在 Rust 里定义一个 `struct Player { health: f32, pos: Vec2, name: String }`。编译之后,类型信息就没了——运行时,程序只知道这是一块内存,不知道它有哪些字段、字段叫什么名字、什么类型。这通常没问题,但有些场景你需要这些信息:你想在编辑器里显示玩家的所有字段让人改,你需要一个**通用**的"显示任意 struct 的字段"的能力;你想把任意 struct 序列化成 JSON 存档,你需要一个**通用**的"遍历任意 struct 的字段"的能力;你想让脚本(Mods)访问任意游戏对象的字段,你同样需要这种能力。这些场景的共同点是:它们想**泛型地、数据驱动地**操作你定义的结构,而不是为每个 struct 手写一遍。

反射就是给运行时的程序,提供"它自己的类型结构"的信息。在 C#/Unity 或 C++ 的反射宏里,这是语言级特性。Rust 没有内建反射(出于性能和简洁的哲学),但有几个实现方式。最常见的是**派生宏**——你给 struct 加 `#[derive(Reflect)]`,宏在编译时生成一个"字段表",运行时可以查这个表知道这个 struct 有哪些字段。bevy_reflect 就是这么做的,它让 Bevy 的 ECS、场景序列化、编辑器都能泛型地操作任意组件。

反射的回报是数据驱动。一旦你的 struct 可反射,你就能写一遍"把任意 struct 存成 JSON"的代码,所有 struct 都受益;你就能在编辑器里自动列出任意组件的所有字段供策划修改;你就能让脚本代码通过字段名访问任意游戏对象。这种"数据驱动"是职业引擎和业余项目的分水岭——业余项目里,你每加一个游戏对象类型,都要手写它的序列化、编辑器面板、脚本绑定;职业引擎里,你加一个 struct,这些全都自动有了,因为它们是泛型地基于反射工作的。这是前期投资(搭反射系统)、后期持续回报(每个新类型自动获得一堆能力)的典型。

不过反射有代价。反射信息有内存开销,反射调用比直接调用慢,派生宏增加编译时间。所以职业引擎通常只在"需要数据驱动的地方"(组件、配置、脚本可见的类型)用反射,内部热路径(数学、物理)用普通 struct,不反射。Rust 的哲学也是"反射 opt-in",不像 Java/C# 一切都带反射。这个权衡你要心里有数——别万物反射,只在值得的地方反射。

## 7 · 把这些用到你的 HH 项目上

这一篇的做中学是一次较大的重构,但它的影响深远。我建议分几步做,每步验证。

第一步,给你的引擎画一张分层图。拿出纸,把你 HH 项目的所有模块分类:哪些属于平台层(开窗、输入、音频),哪些属于核心层(内存、数学、事件),哪些是功能子系统(渲染、物理、动画),哪些是游戏逻辑。画完之后,检查依赖方向——是不是都向下流动?有没有反向依赖或循环依赖?如果发现渲染调用游戏逻辑,或者物理调用渲染,标记出来——这些是要解开的耦合。

第二步,解开你发现的最严重的循环依赖。挑一个,比如"渲染直接调用游戏逻辑的某个函数"。用事件或调度把它解开——让游戏逻辑把渲染需要的数据,通过一个共享的结构或事件传给渲染,而不是渲染反向去查游戏逻辑。这一步可能很别扭,因为过程式代码里这种反向调用往往很深,但每解开一处,代码就更职业化一分。

第三步,引入集中式生命周期管理。把你的所有子系统的初始化,收拢到一个 `init_subsystems` 函数里,按依赖顺序排好;关闭顺序严格反向。如果你用 Rust,尽量让子系统的依赖通过 ownership 表达,让编译器帮你检查生命周期。重构完之后,故意把某个子系统的初始化顺序弄错,确认游戏在启动时给出清晰的错误(而不是神秘崩溃),再改回来——这验证你的生命周期管理是健壮的。

第四步(可选但推荐),把你的一个子系统(渲染是最佳候选,为 9C 铺路)插件化。定义一个 `Renderer` trait,把现有 OpenGL 后端实现成 `OpenglRenderer`,让游戏逻辑只依赖 trait,不依赖具体实现。这样 9C 的 Vulkan 后端就可以作为一个新的 `VulkanRenderer` 实现插进来。这一步是 9C 的前置——如果你不在这一步把渲染抽象成 trait,9C 会非常痛苦。

这几步做完,你的引擎就有了清晰的层次、可替换的子系统、健壮的生命周期。这是从"过程式的一大坨"到"职业引擎架构"的关键跃迁。

## 8 · 练习

练习一,概念辨析。服务定位器看起来很方便,为什么不能用它替代所有的依赖注入?因为服务定位器让依赖变得**隐式**——一个函数内部偷偷去注册表查依赖,函数签名看不出它依赖什么,这违反了可测性和可推理性(9A-1)。它只适合"真正全局、稳定的基础服务",不适合业务逻辑。理解这个边界,你就不会滥用它。

练习二,动手实践。完成前面 §7 的分层图和至少一处循环依赖解开。提交 commit。在 commit message 里说明你解开了哪处耦合、用的什么机制(事件/调度/共享数据)。

练习三,迁移设计。把你 HH 项目的资产加载,改造成一个可反射的"组件"——给资产类型加 `#[derive(Reflect)]`(或手写一个字段表),然后写一个通用的"把任意资产打印成树状结构"的调试工具。这个工具以后在 9B-4 的 dev console 里会直接派上用场——你能实时查看任何资产的内容。

练习四,开源贡献。给 Bevy 找一个子系统,阅读它的 `Plugin` 实现,理解它怎么注册系统、资源、事件。然后试着给某个 Bevy 生态的 crate 写一个简单的 Plugin(把几个系统打包成一个可复用的插件),提 PR。插件贡献是 Bevy 生态的主流贡献方式。

这一篇的主题——子系统分层、模块化、生命周期、反射——Jason Gregory 的《Game Engine Architecture》花了大量篇幅讲,那本书的第三到第五章和"游戏玩法系统"相关章节,是这一主题最系统的参考,值得放在手边反复翻。Bevy 的源码是另一个活教材——它的 `App`、`Plugin`、`bevy_reflect` 是这一篇所有概念的工业级实现,读它的 `crates/bevy_app/` 和 `crates/bevy_reflect/` 比读任何书都直观。

下一篇 [09B-3](09B-3-frame-graph.md) 讲渲染层的、一个特别现代的架构模式——**frame graph**(帧图)。它是这一篇分层思想在渲染上的深化:你用声明式的方式描述"这一帧我要做哪些渲染 pass、它们之间怎么传递资源",frame graph 自动算出资源的生命周期、屏障、内存复用。它解决了"渲染管线越来越复杂后,手动管理 pass 顺序和资源变得不可能"的问题。学完它,你的渲染器就有了现代引擎的心智,这是 9C 的 Vulkan 要高效运转所必需的架构。
