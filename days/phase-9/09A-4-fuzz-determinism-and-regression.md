# 09A-4 · 模糊测试、确定性与回归网

## 0 · 一个被损坏的存档,毁掉了玩家的三十小时

想象一个让所有游戏开发者后怕的场景。一个玩家玩了你的游戏三十小时,存了档。第二天他读档,游戏崩了。他给你发了崩溃报告,你打开存档文件一看——里面有一个字节的值是 0xFF,本该是 0x01。可能是上次保存时磁盘出了点小问题,可能是某种传输错误,总之存档坏了那么一个字节。而你的读档代码,在遇到这个不合法的字节时,做了一个越界访问,游戏直接炸了。三十小时存档,废了。

这种 bug 的可怕之处在于,它根本不来自你的逻辑错——你的存档逻辑、读档逻辑都是对的,前提是"存档文件是合法的"。问题是,现实世界的存档文件可能不合法。磁盘会出错,玩家会手动改存档作弊,恶意玩家会故意构造畸形存档攻击你的游戏(这在联机里尤其严重)。你的代码面对的是**不可信的外部输入**,而你从来没测过"遇到不合法输入会怎样"。

这一篇要讲的第一个东西,就是专门治这个的——**模糊测试**(fuzz testing)。它的想法简单到粗暴:让你的程序吃成千上万个随机生成的、怪诞的、畸形的输入,看它会不会崩。这一篇的第二个主题是**确定性回放**——把你这一整个 9A 序列铺下的网,从"测一帧"升级成"测一整局"。最后我们把这一篇的回归测试和前三篇的所有测试收拢成一个完整的"回归网",说说这套网怎么在 CI 里持续保护你。

## 1 · 模糊测试和属性测试,是一对兄弟

上一篇你可能注意到了,我说模糊测试是属性测试的"暴力兄弟"。在讲怎么用之前,值得把这两个的关系讲清楚,免得你混。

属性测试关心的是"性质成不成立"——你声明一条规则,框架喂随机输入,检查规则。它的输入是你**写的生成器**产出的,是"合法但随机"的,目的是在合法输入空间里找逻辑错。

模糊测试关心的完全不同,它只关心**程序崩不崩、内存安不安全**。它不检查性质,它就是疯狂喂输入,只要程序不 panic、不越界、不 use-after-free、不除以零,就算过。它的输入是**完全随机甚至刻意畸形**的字节流,目的是在"程序作者压根没想到会出现的输入"里找崩溃。

它们的分工是这样的:属性测试测数学和逻辑的正确性(你的 normalize 对不对),模糊测试测健壮性(你的 PNG 解码器遇到乱七八糟的字节会不会崩)。两者互补——一个抓"算错",一个抓"炸掉"。游戏里需要模糊测试的,是所有**吃外部数据**的代码:PNG/JPEG 解码、glTF 解析、存档反序列化、网络协议解析、配置文件读取。这些代码的共同点是面对不可信输入,而不可信输入是崩溃和安全漏洞的温床。

模糊测试之所以强大,是因为它替你覆盖了"你根本想不到去测的输入"。人写测试,本能地只写"合理输入"。模糊测试不带这个偏见——它会喂空文件、喂一个 4GB 的文件、喂全是 0xFF 的文件、喂头部声明长度是负数但数据很短的文件。这些恰恰是触发 bug 的输入,但人不会主动想到它们。

## 2 · Rust 里的模糊测试:cargo fuzz

Rust 的模糊测试工具链非常成熟,这得感谢 Rust 的内存安全保证——fuzz 找到的崩溃,在 Rust 里基本都是 panic 或逻辑越界(因为 use-after-free、缓冲区越界这些 C/C++ 里 fuzz 的主战场,Rust 在编译期就防住了),所以 Rust 项目的 fuzz 更聚焦、更有价值。主流工具是 `cargo-fuzz`,它底层用 libFuzzer,自动做输入变异和缩小。

工作流程是这样的。你写一个 fuzz target,它是一个函数,接收一个任意字节流作为输入,把它喂给你想测的代码。然后 cargo-fuzz 反复调用这个函数,每次喂不同的随机字节流,看你的代码会不会崩。一旦崩了,fuzzer 会自动缩小那个触发崩溃的输入,给你一个最小复现。

举个例子,假设你想 fuzz 你的存档反序列化。fuzz target 长这样:

```rust
// fuzz/fuzz_targets/load_save.rs
#![no_main]
use libfuzzer_sys::fuzz_target;
use my_game::savefile;

fuzz_target!(|data: &[u8]| {
    // 喂任意字节流给读档,忽略返回的 Result
    // 我们只关心:它崩不崩
    let _ = savefile::deserialize(data);
});
```

就这么几行。你声明"把任意字节流喂给 deserialize,不管它返回什么,只要不崩就算过"。然后 `cargo fuzz run load_save`,它开始疯狂喂随机字节,可能跑几分钟、几小时、几天,累积测试几千万个输入。一旦 deserialize 在某个输入上 panic,它停下来,缩小那个输入,告诉你"这 23 个字节的存档文件,会让你的读档崩"。

你拿到这个最小输入,复现崩溃,修 bug——通常是一个 `unwrap` 不该用、一个 `Vec` 索引没做边界检查、一个整数转换溢出。修完之后,把这个触发崩溃的输入存成一个**回归测试**(下一节细讲),保证以后不会再犯。这就是 fuzz 的完整闭环。

这里有一个 Rust 特有的细节值得讲。Rust 的模糊测试,往往要区分两个目标:一个是测"会不会 panic",一个是测"会不会触发 undefined behavior"。前者 `cargo fuzz` 直接能抓;后者需要 `miri`(Rust 的 UB 检测器,跑在 MIR 层),它比 fuzz 慢得多,但能抓到 fuzz 抓不到的、Rust 编译器也漏掉的 unsafe 代码里的 UB。如果你写了 unsafe(比如 FFI、手写的 SIMD),你一定要用 miri 跑一遍,这是职业 Rust 的标配。这把你 9B 的 unsafe、FFI 也罩进了安全网。

## 3 · 确定性回放:把单帧快照升级成整局快照

模糊测试是这一篇的前半。后半是确定性回放,它把你这一整个 9A 序列推到一个新的高度——从"测一帧、测一个函数"升级到"测一整局游戏"。

想法是这样的。你在一整局游戏里,记录下所有的输入(每一帧的按键、鼠标、随机种子、甚至网络包)。然后过几天,你重放这局游戏——按记录的顺序、把同样的输入喂给游戏,让游戏从头模拟到尾。如果游戏是确定的(回到 9B-1 的固定步长、9A-1 的外部源隔离),那么重放出来的最终状态,应该和当初那局完全一样。

你怎么验证"完全一样"?你不可能逐字段比较整个游戏状态——太大、太脆。职业做法是算一个**状态哈希**:每一帧(或每隔 N 帧),把关键状态序列化、算一个哈希,记录下来。重放时,同样算每帧的哈希,和记录的对比。哈希一旦在某一帧不一致,你就知道"从这一帧起,确定性破了",而且你能精确定位到是哪一帧 desync 的。

这个东西的价值,在你第一次追查 desync bug 时会彻底显现。联机游戏(9E)最恐怖的 bug 是 desync——两台机器同样的输入,状态慢慢分叉,玩家看到完全不同的游戏世界,体验崩坏。这种 bug 极难追,因为它是"累积的、延迟显现的"。但如果你有确定性回放,你可以录下两台机器的输入(它们应该一样),分别在开发机上重放,逐帧比哈希,找到第一个不一致的帧,然后深入那一帧的模拟,找出哪个浮点运算分叉了。没有确定性回放,这种 bug 你只能干瞪眼。有了它,你能精准定位。

确定性回放还有一个意想不到的副产品:**它本身就是一个巨型回归测试**。你录下几十局代表性游戏过程,把它们当作回归测试套件。每次改代码,重放这些局,如果任何一局的哈希变了,你就知道这次改动改变了模拟行为。这能抓住"我重构了 AI,顺手改变了它的某个微小决策,导致整局演化不同"这种深层回归——这种回归单元测试和集成测试都抓不到,因为它们不跑整局。

这里有个你必须正视的工程现实:做到位级确定性,比想象中难。浮点运算的顺序在不同编译器、不同优化级别下可能不同,导致结果有最后一位的差异,累积成 desync。Rust 里 `a + b + c` 和 `c + b + a` 在浮点下可能不相等。要做到真正的确定性,你可能要禁用某些会重排浮点运算的优化、用确定性的数学库、甚至在某些地方用定点数代替浮点。这是为什么很多竞速/策略联机游戏(需要严格锁步)干脆用定点数——牺牲一点精度,换取位级确定。这些是 9E 联机的深水区,这里你先知道"确定性回放存在、它极其有用、但它要求你的模拟是位级确定的"就够了。

## 4 · 回归测试:把每一个修过的 bug 钉死

fuzz 和确定性回放会替你**发现**很多 bug。但发现只是第一步,真正让测试网越来越牢的,是你怎么**处理**这些发现。这就是回归测试的用武之地,它是这一篇的第三块,也是把整个 9A 序列收口的关键。

回归测试有一条铁律,简单但极其重要:**每当你修了一个 bug,你必须在修的同时,写一个能复现这个 bug 的测试,让它失败(红),然后修到它通过(绿),并永远保留这个测试。** 这条铁律的智慧在于:bug 是会复发的。同一个 bug,半年后有人重构,很可能又写出来。如果你当时写了回归测试,这次复发会被测试立刻抓住;如果你没写,它就又得在玩家那里炸一次才被发现。

这条铁律适用于 9A 序列里所有层级发现的 bug。单元测试发现一个数学错——修完写个单元测试钉住。集成测试发现穿墙——修完写个集成测试钉住。fuzz 发现一个崩溃——修完把那个最小输入存成测试钉住。确定性回放发现 desync——修完把那局的输入录存成测试钉住。你发现的每一个 bug,都变成测试网上的一个新结点,让它永远不会再次偷偷回来。

时间一长,你的回归测试套件会越来越厚。这听起来像负担,但实际上它是你最宝贵的资产。一个厚实的回归网,意味着你敢做大刀阔斧的重构——因为任何行为变化,网都会告诉你。HH 的代码之所以不敢动,就是因为它没这张网;你的代码之所以敢动,是因为你在织这张网。这又回到了 9A-1 的主题——可测性给你的是"敢改代码"的自信。

## 5 · 把这张网织进 CI

测试写了不跑,等于没写。本地你跑 `cargo test` 觉得过了就 push,但别人不会主动跑你的测试。唯一的办法,是让一台机器在每次提交时自动跑全部测试,这就是 CI(持续集成)。这一节我快速讲一下怎么把 9A 这四篇的测试都塞进 CI,因为这是它们真正持续保护你的方式。

CI 的配置本身不难(phase-0/17 讲过基础),你要在这里想清楚的是每种测试在 CI 里的"跑法"。单元测试、集成测试跑得快,每次 push 都跑,几分钟内给反馈。property test 适中,跑,但锁种子,避免 flaky。快照测试要跑,但基准图存在仓库里,CI 比对,失败时让 PR 作者决定是修还是更新基准。fuzz 跑得久,不全跑——通常 CI 里跑短时间(几分钟)的 fuzz 做冒烟,长时间(几小时、几天)的 fuzz 放到单独的、不那么频繁的任务里跑。确定性回放,把录好的代表性局存仓库,每次 push 重放,比哈希。

这里有个 CI 设计的智慧值得讲。不是所有测试都要在每个 commit 上全跑。一个常见的分层是:PR 提交时跑"快测试"(单元、集成、property、短 fuzz、快照),几分钟出结果,挡住明显的破坏;merge 到主干后,后台跑"慢测试"(长 fuzz、全量回放、跨平台构建),这些可能要几十分钟到几小时,不阻塞开发者,但会标记潜在问题。这个分层让 CI 既快又全——快的部分挡住日常破坏,慢的部分深挖隐蔽问题。

还有一个 CI 实践特别值得强调:**flaky 测试是 CI 的毒药,必须零容忍**。一个时好时坏的测试,会让团队对整个 CI 失去信任——红叉出来,大家第一反应是"又是那个 flaky",直接重跑,真正的回归就这么被忽略。一旦发现 flaky(比如 property test 偶发失败、快照因 GPU 抖动偶发失败),必须立刻修——锁种子、调阈值、或者隔离——不能让它在 CI 里腐烂。这是职业 CI 的纪律。

## 6 · 把这一篇用到你的 HH 项目上

这一篇的做中学有三件事,对应三个主题。

第一,fuzz 你的解析器。挑你 HH 项目里一个吃外部数据的代码——PNG 解码(如果你做了 phase-7 的手写 PNG)、glTF 加载、或者存档反序列化。给它写一个 fuzz target,`cargo fuzz run` 跑几分钟。你很可能在头几分钟内就找到一个崩溃——大多数手写解析器在随机字节流下都撑不了多久。拿到最小复现,修 bug,然后把那个最小输入存成回归测试。这个练习会让你第一次真切感受到"我的代码面对恶意输入有多脆弱"。

第二,给你的游戏加一个最小确定性回放。在游戏循环里加一个"录制"模式:每帧记录输入(按键 + 你注入的随机源的种子),存到一个文件。再加一个"回放"模式:读这个文件,按记录喂输入,模拟整局。每隔 N 帧算一个状态哈希,存下来。然后回放一次,比哈希。如果一致——恭喜,你的游戏是确定的,你拥有了最强的回归测试基础设施之一。如果不一致——更好,你抓到了一个 desync,深挖它,通常是某个忘了参数化的外部源。修完,把那局录存成回归测试。

第三,建立回归测试的纪律。从今天起,每修一个 bug,写一个回归测试。哪怕这个 bug 很小。把这条变成肌肉记忆。几个月后你会发现,你的回归套件厚实了,你改代码的胆子也大了——这两个变化是同源的。

做完这三件事,9A 序列的测试网就在你 HH 项目里铺成了。你有:纯函数单元测试(9A-1 的改造让它们成为可能)、property test 喂数学(9A-2)、集成测试和渲染快照(9A-3)、fuzz 和确定性回放和回归纪律(9A-4)。这套网持续运行在 CI 里。你不再像 Casey 那样"改代码靠肉眼和祈祷",你有了职业级的保护。这是你从"跟完教程"到"职业游戏工程师"的、第一次实质性的跃迁。

## 7 · 练习

练习一,概念辨析。fuzz 和 property test 都"喂随机输入",它们到底差在哪?再强调一次,免得混:property test 检查一条你声明的性质对不对,输入来自你写的、合法的生成器,目的是抓逻辑错;fuzz 只检查"不崩不 UB",输入是任意字节流,目的是抓健壮性。给数学函数用 property,给解析器用 fuzz,这是分工。

练习二,动手实践。完成前面 §6 的 fuzz 你的解析器,提交一个"修崩溃 + 回归测试"的 commit。这个 commit 的历史价值特别高——它记录了你的代码第一次被 fuzz 锤炼。

练习三,迁移设计。把 §6 的确定性回放,扩展成一个"幽灵玩家"系统:录制你自己的游戏过程,存下来。下次开发时,你的游戏里可以有一个"回放幽灵"——你上次的录象,作为对手或参考。这其实就是赛车游戏的"幽灵车"功能,它的技术基础就是确定性回放。一个测试基础设施,顺带成了游戏功能,这种一鱼两吃在设计良好的架构里经常出现。

练习四,开源贡献。给一个 Rust 游戏相关 crate(解析器、序列化库)补一个 fuzz target,跑出一个崩溃,修了,提 PR。fuzz 贡献在开源项目里特别受欢迎,因为没人爱写但大家都受益。你贡献的 fuzz target 会持续在那个项目的 CI 里运行,保护所有人。

## 8 · 延伸阅读与序列收口

模糊测试的权威参考是 libFuzzer 的文档和 AFL 的论文,它们讲清楚了覆盖率引导的 fuzz 怎么工作。Rust 特有的部分,`cargo-fuzz` 的文档和 `miri` 的文档是必读——前者管 fuzz,后者管 unsafe 的 UB 检测,两者配合是 Rust 的安全双保险。确定性回放方面,Gaffer on Games 上有专门讲游戏录象和 desync 追查的文章,实战经验非常宝贵,等做 9E 联机时你会回来重读。

写到这里,9A 序列的四篇就收口了。回头看,它们不是四个孤立的测试技巧,它们是一个完整的、从下到上的测试体系:9A-1 给你**可测的架构**(纯函数核心、依赖注入、确定性),这是地基,没有它后面什么都谈不上;9A-2 让你测**纯函数**(单元 + property,后者用随机输入替你覆盖你没想到的边界);9A-3 让你测**协作和画面**(集成测试抓接口 bug,渲染快照抓视觉回归);9A-4 让你测**健壮性和整局**(fuzz 抓崩溃,确定性回放抓 desync,回归纪律把所有发现的 bug 永久钉死)。这四层合起来,就是一份职业级的游戏测试体系。

这一整个序列,反复出现一个词:**确定性**。从 9A-1 的"纯函数不藏外部源",到 9A-2 的 property test 依赖确定性输入,到 9A-3 的快照需要确定场景,到 9A-4 的回放需要位级确定——确定性是贯穿整个测试体系的红线。而确定性,你也从 9B-1 知道,是固定步长游戏的天然属性,也是 9E 联机的地基。所以你在这里打下的底,不只是为了测试,它在联机、回放、录像各个地方都会回报你。这就是为什么可测架构是好架构——它一次设计,处处受益。

下一篇 [09B-2](09B-2-subsystems-modules-plugins.md) 离开测试主题,回到引擎架构——在 9B-1 那个稳定的 loop 之上,讲怎么组织引擎的子系统分层、模块化、插件,以及 init/shutdown 的生命周期。如果你觉得 9A 是给游戏织安全网,那 9B 就是给游戏搭骨架。两者合起来,你的引擎才真正"职业"。
