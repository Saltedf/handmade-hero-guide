# Day 135 · 类型化资产数组

> Day 133 把资产分组,Day 134 加 tag 映射。今天把这两步的成果**固化**:每个资产类型有独立的类型化数组(`Vec<Bitmap>`、`Vec<Sound>`),asset store 通过统一的 trait 接口管理多类型。这是 Casey 把 Day 133 的"散装 Vec"演化成"系统化资产管理"的关键一步。

## 0 · 为什么要有这一天

Day 133 你写:

```rust
struct AssetStore {
    bitmaps: Vec<Bitmap>,
    sounds: Vec<Sound>,
    fonts: Vec<Font>,
}
```

每加一种新类型(sprite sheet、animation clip、material...)你都要:
- 在 struct 里加字段
- 实现 `add_xxx`、`get_xxx`
- 加 tag 映射 `xxx_tags`
- 复制粘贴大量代码

**今天的核心**:把"每种类型一套方法"抽象成"trait + 泛型"。一个 `AssetPool<T>` 容器通用,所有类型用同一个 API:

```rust
let bitmaps: AssetPool<Bitmap> = ...;
let sounds: AssetPool<Sound> = ...;

bitmaps.add(bmp);  // 通用 API
sounds.add(snd);   // 同 API
```

Rust 的泛型 + trait 让这种抽象零成本(编译期 monomorphization)。

心理锚点:做完今天你能(1)用 Rust trait + 泛型写一个通用 AssetPool<T>;(2)理解为什么"每种类型独立 Vec"比"统一 Vec<Asset>"好;(3)在你的引擎里加新类型只需实现 trait,不改 AssetStore;(4)说出 monomorphization 和 dynamic dispatch 的差别。

## 2 · 心智模型

### 类比:Excel 表 vs 文件夹

Day 133-134 的资产管理像文件夹:每种类型一个文件夹,手动管理。

Day 135 的 AssetPool<T> 像 Excel 表模板:你定义一次"表格格式",每种资产填一张表。改"表格格式"(比如加 tag 功能),所有表自动获益。

### 严谨原理:Rust 泛型 + trait

```rust
// 通用资产池
struct AssetPool<T> {
    items: Vec<T>,
    tags: HashMap<String, u32>,
}

impl<T> AssetPool<T> {
    fn new() -> Self {
        Self { items: Vec::new(), tags: HashMap::new() }
    }

    fn add(&mut self, item: T) -> u32 {
        let id = self.items.len() as u32;
        self.items.push(item);
        id
    }

    fn get(&self, id: u32) -> &T {
        &self.items[id as usize]
    }

    fn add_with_tag(&mut self, tag: &str, item: T) -> u32 {
        let id = self.add(item);
        self.tags.insert(tag.to_string(), id);
        id
    }

    fn lookup(&self, tag: &str) -> Option<u32> {
        self.tags.get(tag).copied()
    }
}

// AssetStore 用多个 AssetPool
struct AssetStore {
    bitmaps: AssetPool<Bitmap>,
    sounds: AssetPool<Sound>,
    fonts: AssetPool<Font>,
}
```

加新类型只需:
```rust
struct AssetStore {
    // ...
    sprite_sheets: AssetPool<SpriteSheet>,  // 新加
}
```

无需重写 add / get / lookup——所有类型用同一套代码。

### 关键概念:monomorphization

Rust 的泛型在编译期展开(monomorphization)。`AssetPool<Bitmap>` 和 `AssetPool<Sound>` 在编译后是**两个独立的类型**,各有自己的 `add` / `get` 代码。运行时零开销,如同手写每类型独立代码。

对比 dynamic dispatch(trait object,`Box<dyn Asset>`):
- monomorphization:编译期展开,静态分派,零开销
- dynamic dispatch:运行时分派,有 vtable 开销(几个 ns),但代码体积小

性能敏感场景用 monomorphization。Casey 在 C 里用宏(等价 monomorphization)。

### 类型化 ID 的泛型化

```rust
// PhantomData 让 Id 携带类型信息,编译期防混用
struct AssetId<T> {
    id: u32,
    _ty: PhantomData<fn() -> T>,  // invariant phantom
}

impl<T> AssetPool<T> {
    fn add(&mut self, item: T) -> AssetId<T> {
        let id = self.items.len() as u32;
        self.items.push(item);
        AssetId { id, _ty: PhantomData }
    }
    fn get(&self, asset_id: AssetId<T>) -> &T {
        &self.items[asset_id.id as usize]
    }
}

// 使用:
let bmp_id: AssetId<Bitmap> = bitmaps.add(bmp);
let snd_id: AssetId<Sound> = sounds.add(snd);
bitmaps.get(bmp_id);  // OK
bitmaps.get(snd_id);  // 编译错!类型不匹配
```

`AssetId<T>` 是 phantom type——编译期有类型,运行时只占 u32 大小(4 字节)。这是 Rust 表达"类型化索引"的优雅方式。

### 3.1 · 🎮 游戏编程视角

游戏开发里"通用资产池"模式常见:

- **Unreal**:`UAssetManager` + `FStreamableHandle`,generic API
- **Unity**:`Addressables.LoadAssetAsync<T>()`,generic
- **Bevy**:`Assets<T>` resource,per-type storage

所有引擎都用泛型 / trait object 抽象资产操作。Casey Day 135 走同样路径。

游戏开发圈的进一步抽象:

**Asset reference**:Handle<T> 持有 Arc<AssetCell<T>>,自动 refcount。Casey 后期(Phase 5+)会用。

**Asset dependency**:资产 A 依赖资产 B(比如模型依赖纹理),自动级联加载 / 卸载。商业引擎标配,HH 不做。

**Asset variants**:同一资产不同参数版本(高/低 LOD,不同语言音频)。商业引擎有,HH 不做。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核里类似抽象:

**file_operations struct**:每种文件系统(ext4、xfs、nfs)实现 `file_operations`,VFS 层用统一接口调用。这就是 trait object 的 C 版本。

```c
struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*open)(struct inode *, struct file *);
    int (*release)(struct inode *, struct file *);
    // ...
};
```

VFS 调用 `file->f_op->read(file, buf, len, off)`,具体走哪个文件系统的 read 由函数指针决定。等价于 Rust 的 `dyn Trait`。

Linux 也有"monomorphization"风格——例如 `list_head` 通用链表,通过宏生成不同类型的 list(`struct list_head` + 宏 `LIST_HEAD(name)`),编译期展开。

### 3.3 · 🦀 Rust 生态视角

Rust 表达"通用资产池"的几种风格:

#### 流派 1:AssetPool<T>(推荐教学)

```rust
struct AssetPool<T> { items: Vec<T>, tags: HashMap<String, u32> }
```

每类型一个 AssetPool<T>,AssetStore 持有多个。零开销,编译期类型安全。

#### 流派 2:trait object(Box<dyn Asset>)

```rust
trait Asset: Any {
    fn type_name(&self) -> &'static str;
}
struct AssetStore {
    assets: HashMap<TypeId, Box<dyn Asset>>,
}
```

灵活,但 dynamic dispatch + Box 分配,有运行时开销。不推荐 hot path 用。

#### 流派 3:Bevy Assets<T>

Bevy 用 generic + Resource trait:

```rust
// Bevy 风格
struct Assets<T: Asset> { storage: HashMap<AssetId<T>, T> }
impl<T: Asset> Resource for Assets<T> {}

// 使用
fn system(images: Res<Assets<Image>>) {
    // ...
}
```

每个 T 独立的 Resource,Bevy 的 ECS 知道如何注入。

#### 流派 4:macro 生成代码

```rust
macro_rules! define_asset_type {
    ($name:ident) => {
        pub struct ${concat($name, Id)}(u32);
        // ... 一堆自动生成
    };
}
define_asset_type!(Bitmap);
define_asset_type!(Sound);
```

C 风格 macro。Rust 里能用,但不如泛型优雅。

Casey 在 C 里用流派 4(宏)。Rust 教学版用流派 1(泛型)。

## 5 · 对照与变奏

### 静态分派 vs 动态分派

```rust
// 静态分派(monomorphization)
fn add<T>(pool: &mut AssetPool<T>, item: T) -> u32 { ... }
// 编译期展开 AssetPool<Bitmap>::add / AssetPool<Sound>::add
// 运行时无开销

// 动态分派
fn add(pool: &mut dyn AssetPoolTrait, item: Box<dyn Asset>) -> u32 { ... }
// 运行时通过 vtable 找函数
// 每次调用多一次 vtable 查找
```

游戏开发优先静态分派(性能)。如果实在需要运行时多态(如脚本系统),才用 dynamic。

### PhantomData 用法

`PhantomData<T>` 让 struct "携带"类型信息但不占空间:

```rust
struct AssetId<T> {
    id: u32,
    _ty: PhantomData<T>,
}
// size_of::<AssetId<Bitmap>>() == 4(只有 u32)
```

`_ty: PhantomData<T>` 不占字节,但让编译器把 `T` 当作"被使用"。否则 unused type parameter 报错。

选择 `PhantomData<fn() -> T>`(不是 `PhantomData<T>`)的原因:前者是 invariant(防止 lifetime 协变导致问题),后者是 covariant。对于 id 类型,invariant 更安全。

### 历史演化

- **1970s**:C 用 `void*` + cast 表达"通用容器"。无类型安全
- **1980s**:C++ template,真正泛型
- **1990s**:Java / C# generic(但 type erasure),折中
- **2010s**:Rust trait + 泛型,静态分派 + 类型安全
- **2020s**:更精细的 GAT / async fn in trait

Casey 在 C 用宏。Rust 教学版用泛型。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:

1. Rust 的泛型在编译后变成什么?有运行时开销吗?
2. `AssetId<T>` 用 `PhantomData<fn() -> T>` 而不是 `PhantomData<T>`,差别是什么?
3. trait object(Box<dyn Asset>)和泛型(asset: T)的主要差别?各自适合什么场景?
4. 加一种新资产类型(SpriteSheet),Day 133 风格 vs Day 135 风格,各要改几处?

**参考解答**:
1. Rust 泛型通过 monomorphization 编译期展开。`AssetPool<Bitmap>` 和 `AssetPool<Sound>` 编译后是两个独立的、具体的类型,各有自己的代码。运行时零开销,如同手写。
2. `PhantomData<T>` 是 covariant(随 T 协变),`PhantomData<fn() -> T>` 是 invariant(不变)。对于 id 类型,如果 T 带 lifetime,covariant 可能导致"长 lifetime 的 id 被当短 lifetime 用"——虽然 id 本身和 lifetime 无关,但类型系统约束。invariant 更严格、更安全。Rust API guideline 推荐 id type 用 invariant。
3. trait object:运行时通过 vtable 分派,有 ns 级开销;Box 分配在堆;代码体积小;适合"运行时才知道具体类型"(脚本系统、插件)。泛型:编译期展开,零开销;栈分配;代码体积大(monomorphization);适合"编译期就知道类型"。
4. Day 133 风格:加字段 `sprite_sheets: Vec<SpriteSheet>`、加方法 `add_sprite_sheet`、`get_sprite_sheet`、加 tag map,大约 30-50 行代码。Day 135 风格:加字段 `sprite_sheets: AssetPool<SpriteSheet>`,1 行。改动量差 30 倍。

### Lv2 · 动手实践

**题**:Rust 实现泛型 AssetPool<T>。

要求:
1. `struct AssetId<T> { id: u32, _ty: PhantomData<fn() -> T> }`
2. `struct AssetPool<T> { items: Vec<T>, tags: HashMap<String, u32> }`
3. 方法:`add`、`get`、`add_with_tag`、`lookup`(都泛型)
4. `AssetStore { bitmaps: AssetPool<Bitmap>, sounds: AssetPool<Sound> }`
5. main:加几个 bitmap 和 sound,验证 `bitmaps.get(snd_id)` 编译错

完成标准:`cargo run` 用类型化 id 取资产,且 `bitmaps.get(snd_id)` 编译失败。

**参考解答**:

```rust
use std::collections::HashMap;
use std::marker::PhantomData;

// 类型化 id,编译期防混用
struct AssetId<T> {
    id: u32,
    _ty: PhantomData<fn() -> T>,
}
impl<T> Copy for AssetId<T> {}
impl<T> Clone for AssetId<T> { fn clone(&self) -> Self { *self } }
impl<T> std::fmt::Debug for AssetId<T> {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        write!(f, "AssetId({})", self.id)
    }
}
impl<T> PartialEq for AssetId<T> {
    fn eq(&self, other: &Self) -> bool { self.id == other.id }
}
impl<T> Eq for AssetId<T> {}

// 通用资产池
struct AssetPool<T> {
    items: Vec<T>,
    tags: HashMap<String, u32>,
}

impl<T> AssetPool<T> {
    fn new() -> Self {
        Self { items: Vec::new(), tags: HashMap::new() }
    }
    fn add(&mut self, item: T) -> AssetId<T> {
        let id = self.items.len() as u32;
        self.items.push(item);
        AssetId { id, _ty: PhantomData }
    }
    fn get(&self, aid: AssetId<T>) -> &T {
        &self.items[aid.id as usize]
    }
    fn add_with_tag(&mut self, tag: &str, item: T) -> AssetId<T> {
        let id = self.add(item);
        self.tags.insert(tag.to_string(), id.id);
        id
    }
    fn lookup(&self, tag: &str) -> Option<AssetId<T>> {
        self.tags.get(tag).map(|&id| AssetId { id, _ty: PhantomData })
    }
}

// 具体资产类型
struct Bitmap { width: u32, height: u32, pixels: Vec<u32> }
struct Sound { samples: Vec<f32>, sample_rate: u32 }

// AssetStore
struct AssetStore {
    bitmaps: AssetPool<Bitmap>,
    sounds: AssetPool<Sound>,
}

fn main() {
    let mut store = AssetStore {
        bitmaps: AssetPool::new(),
        sounds: AssetPool::new(),
    };

    // 加 bitmaps
    let sword_bmp = Bitmap { width: 64, height: 64, pixels: vec![0xff0000ff; 64*64] };
    let sword_id = store.bitmaps.add_with_tag("sword", sword_bmp);
    println!("Added sword bitmap: {:?}", sword_id);

    // 加 sounds
    let bgm = Sound { samples: vec![0.5; 44100], sample_rate: 44100 };
    let bgm_id = store.sounds.add_with_tag("bgm", bgm);
    println!("Added bgm sound: {:?}", bgm_id);

    // lookup
    let sword_id2 = store.bitmaps.lookup("sword").unwrap();
    assert_eq!(sword_id, sword_id2);

    // 取资产
    let bmp = store.bitmaps.get(sword_id);
    println!("Got bitmap via id: {}x{}", bmp.width, bmp.height);

    let snd = store.sounds.get(bgm_id);
    println!("Got sound via id: {} samples @ {} Hz", snd.samples.len(), snd.sample_rate);

    // 编译期验证(取消注释会编译错):
    // let _ = store.bitmaps.get(bgm_id);
    // error: expected AssetId<Bitmap>, found AssetId<Sound>
}
```

## 8 · Rust / Arch 落地代码

完整可跑见 Lv2。benchmark 验证 monomorphization 零开销:

```rust
// 测试:泛型 vs trait object
trait GetLen { fn len(&self) -> usize; }
impl GetLen for Vec<u32> { fn len(&self) -> usize { Vec::len(self) } }

fn bench_generic(v: &Vec<u32>) -> usize { v.len() }
fn bench_dyn(v: &dyn GetLen) -> usize { v.len() }

fn main() {
    let v: Vec<u32> = vec![0; 1000];
    let start = std::time::Instant::now();
    for _ in 0..1_000_000 {
        std::hint::black_box(bench_generic(&v));
    }
    let g = start.elapsed();
    let start = std::time::Instant::now();
    for _ in 0..1_000_000 {
        std::hint::black_box(bench_dyn(&v as &dyn GetLen));
    }
    let d = start.elapsed();
    println!("Generic: {} ns/iter", g.as_nanos() / 1_000_000);
    println!("Dyn:     {} ns/iter", d.as_nanos() / 1_000_000);
}
```

**预期**:
```
Generic: 1 ns/iter
Dyn:     3 ns/iter
```

dynamic dispatch 每次调用多 1-3 ns(vtable 查找 + indirect call)。Hot path 大量调用时累加。

## 10 · 深度推导:从重复代码到泛型抽象

今天 Casey 把 Day 133-134 的重复代码抽象成泛型 AssetPool<T>。这听起来像简单重构,但背后是一整套 Rust 类型系统的高级用法。这一节把这些用法讲透。

### 10.1 起点:Day 134 的重复代码

Day 134 的 AssetStore 长这样:

```rust
struct AssetStore {
    bitmaps: Vec<Bitmap>,
    sounds: Vec<Sound>,
    bitmap_tags: HashMap<String, u32>,
    sound_tags: HashMap<String, u32>,
}

impl AssetStore {
    fn add_bitmap(&mut self, bmp: Bitmap) -> BitmapId { ... }
    fn get_bitmap(&self, id: BitmapId) -> &Bitmap { ... }
    fn add_bitmap_with_tag(...) { ... }
    fn lookup_bitmap(...) -> Option<BitmapId> { ... }

    fn add_sound(&mut self, snd: Sound) -> SoundId { ... }
    fn get_sound(&self, id: SoundId) -> &Sound { ... }
    fn add_sound_with_tag(...) { ... }
    fn lookup_sound(...) -> Option<SoundId> { ... }
}
```

每加一种类型(SpriteSheet / Animation / Font / Material...),要复制粘贴 4 个方法 + 2 个字段。10 个类型 = 40 个方法 + 20 个字段。**代码爆炸**。

更糟:每个方法实现几乎一样,只有类型名变。这是典型的"重复代码"——bad smell。

### 10.2 第一层抽象:AssetPool<T>

把"Vec<T> + tags map"打包成独立 struct:

```rust
struct AssetPool<T> {
    items: Vec<T>,
    tags: HashMap<String, u32>,
}

impl<T> AssetPool<T> {
    fn add(&mut self, item: T) -> u32 {
        let id = self.items.len() as u32;
        self.items.push(item);
        id
    }
    fn get(&self, id: u32) -> &T {
        &self.items[id as usize]
    }
    fn add_with_tag(&mut self, tag: &str, item: T) -> u32 {
        let id = self.add(item);
        self.tags.insert(tag.to_string(), id);
        id
    }
    fn lookup(&self, tag: &str) -> Option<u32> {
        self.tags.get(tag).copied()
    }
}

struct AssetStore {
    bitmaps: AssetPool<Bitmap>,
    sounds: AssetPool<Sound>,
    // 加新类型只需一行:
    // fonts: AssetPool<Font>,
}
```

代码量从"每类型 4 方法"变成"一行 struct 字段"。**这就是泛型的价值**——一份代码服务多类型。

### 10.3 第二层:类型化 AssetId<T>

上面用 u32 作 id。但 `pool.get(u32)` 没有类型安全——你可以传 bitmaps 的 u32 给 sounds.get,编译器不阻止。

修复:用 phantom type 包装 u32:

```rust
use std::marker::PhantomData;

struct AssetId<T> {
    id: u32,
    _ty: PhantomData<fn() -> T>,
}

impl<T> AssetPool<T> {
    fn add(&mut self, item: T) -> AssetId<T> {
        let id = self.items.len() as u32;
        self.items.push(item);
        AssetId { id, _ty: PhantomData }
    }
    fn get(&self, aid: AssetId<T>) -> &T {
        &self.items[aid.id as usize]
    }
}
```

现在 `bitmaps.get(snd_id)` 编译错误:`expected AssetId<Bitmap>, found AssetId<Sound>`。编译期阻止跨类型混用。

### 10.4 PhantomData 的细节

`PhantomData<T>` 看起来没用(占 0 字节),但告诉编译器"这个 struct 在概念上持有 T"。这对 drop 检查、lifetime 推断、variance 都重要。

为什么用 `PhantomData<fn() -> T>` 而不是 `PhantomData<T>`?

- `PhantomData<T>` 让 AssetId<T> 对 T 协变(covariant)。如果 T 是带 lifetime 的引用,T 变化时 AssetId 也跟着变,可能产生 lifetime 漏洞。
- `PhantomData<fn() -> T>` 是 invariant。AssetId<T> 不随 T 变。对 ID 类型,这是更安全的语义。

Rust API guidelines 推荐:"Id types should be invariant"。

### 10.5 第三层:trait 约束

如果你想给 AssetPool 加 "save / load" 功能,要约束 T 实现 Serializable:

```rust
trait Serializable {
    fn serialize(&self) -> Vec<u8>;
}

impl<T: Serializable> AssetPool<T> {
    fn save_all(&self, path: &str) {
        let mut data = Vec::new();
        for item in &self.items {
            data.extend(item.serialize());
        }
        std::fs::write(path, data).unwrap();
    }
}
```

只有 Serializable 的 T 才能用 save_all。Bitmap 实现了 Serializable 就能用,Sound 没实现就不能用。编译期约束。

### 10.6 完整代码骨架

```rust
use std::collections::HashMap;
use std::marker::PhantomData;
use std::fmt;

// 类型化 ID
pub struct AssetId<T> {
    id: u32,
    _ty: PhantomData<fn() -> T>,
}

impl<T> AssetId<T> {
    pub fn raw(&self) -> u32 { self.id }
}

impl<T> Copy for AssetId<T> {}
impl<T> Clone for AssetId<T> {
    fn clone(&self) -> Self { *self }
}
impl<T> PartialEq for AssetId<T> {
    fn eq(&self, other: &Self) -> bool { self.id == other.id }
}
impl<T> Eq for AssetId<T> {}
impl<T> fmt::Debug for AssetId<T> {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "AssetId({})", self.id)
    }
}
impl<T> Hash for AssetId<T> {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.id.hash(state);
    }
}

// 通用 AssetPool
pub struct AssetPool<T> {
    items: Vec<T>,
    tags: HashMap<String, u32>,
}

impl<T> AssetPool<T> {
    pub fn new() -> Self {
        Self {
            items: Vec::new(),
            tags: HashMap::new(),
        }
    }

    pub fn add(&mut self, item: T) -> AssetId<T> {
        let id = self.items.len() as u32;
        self.items.push(item);
        AssetId { id, _ty: PhantomData }
    }

    pub fn get(&self, aid: AssetId<T>) -> &T {
        &self.items[aid.id as usize]
    }

    pub fn get_mut(&mut self, aid: AssetId<T>) -> &mut T {
        &mut self.items[aid.id as usize]
    }

    pub fn add_with_tag(&mut self, tag: &str, item: T) -> AssetId<T> {
        let id = self.add(item);
        self.tags.insert(tag.to_string(), id.id);
        id
    }

    pub fn lookup(&self, tag: &str) -> Option<AssetId<T>> {
        self.tags.get(tag).map(|&id| AssetId { id, _ty: PhantomData })
    }

    pub fn len(&self) -> usize {
        self.items.len()
    }
}

// 用法
struct Bitmap { width: u32, height: u32, pixels: Vec<u32> }
struct Sound { samples: Vec<f32> }

struct AssetStore {
    bitmaps: AssetPool<Bitmap>,
    sounds: AssetPool<Sound>,
}

fn main() {
    let mut store = AssetStore {
        bitmaps: AssetPool::new(),
        sounds: AssetPool::new(),
    };

    let bmp_id = store.bitmaps.add_with_tag("sword",
        Bitmap { width: 64, height: 64, pixels: vec![0xff0000ff; 64*64] });
    let snd_id = store.sounds.add_with_tag("bgm",
        Sound { samples: vec![0.5; 44100] });

    let bmp = store.bitmaps.get(bmp_id);
    let snd = store.sounds.get(snd_id);
    println!("Bitmap {}x{}, Sound {} samples", bmp.width, bmp.height, snd.samples.len());

    // 编译错误演示(取消注释):
    // let _ = store.bitmaps.get(snd_id);
    // error[E0308]: expected `AssetId<Bitmap>`, found `AssetId<Sound>`
}
```

这就是 Day 135 的核心产出。完整 + 类型安全 + 零运行时开销。

## 11 · 工业级的额外考量

### 11.1 Generational ID(防 use-after-free)

```rust
pub struct AssetId<T> {
    index: u32,
    generation: u32,  // slot 重用时 generation++
    _ty: PhantomData<fn() -> T>,
}

struct Slot<T> {
    item: Option<T>,
    generation: u32,
}

pub struct AssetPool<T> {
    slots: Vec<Slot<T>>,
    free_list: Vec<u32>,
}
```

free 一个 slot 后,generation++。旧 id 的 generation 不匹配,get 返回 None。这防止 use-after-free——经典 slotmap 设计。

### 11.2 异步加载 + weak handle

```rust
pub struct Handle<T> { id: AssetId<T>, refcount: Arc<AtomicU32> }
pub struct WeakHandle<T> { id: AssetId<T>, refcount: Weak<AtomicU32> }
```

Strong handle 让 asset 保持 loaded,weak handle 不阻止 unload。这是 Bevy 的 `Handle<T>` / `WeakHandle<T>` 设计。

### 11.3 Reflection:运行时类型查询

```rust
trait Asset: 'static {
    fn type_id(&self) -> TypeId;

// 用 TypeId 做 runtime 查询
let pool: &dyn Any = self.get_pool(TypeId::of::<Bitmap>());
let bitmap_pool = pool.downcast_ref::<AssetPool<Bitmap>>().unwrap();
```

Reflection 慢但灵活。Bevy 的 ECS 大量用。Casey 不用,因为 HH 是静态类型。

### 11.4 ECS 集成

Bevy 自动注入 `Res<Assets<T>>` 到系统。这是 ECS + asset system 的标准集成。
