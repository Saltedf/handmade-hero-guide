# Day 147 · 定义资产文件

> 你的游戏有 200 个精灵、50 个声音、20 个字体——以前散落在 `assets/` 目录里 200 个 BMP + 50 个 WAV + 20 个 TTF。Windows 上读它们要 200 次 `CreateFile`,启动慢、磁盘碎片化、用户能随便改你的资产。今天 Casey 要做的是把所有资产打包成**一个 .hha 文件**(Handmade Hero Asset),自己定义格式。

## 0 · 为什么要有这一天

游戏发行版本几乎从来不是"一堆散文件 + exe"。业界标准是 **打包成单一文件**(或几个):

- **Half-Life** 用 `.pak`
- **Doom 3** 用 `.pk4`(实际是 zip)
- **Quake** 用 `.pak`
- **Unity** 用 `.assets` / `.bundle`
- **Unreal** 用 `.pak` / `.uasset`
- **Godot** 用 `.pck`

为什么?6 个理由:

1. **启动快**:1 次 `open` + `mmap` 一整个文件比 200 次分别 `open` 快得多(每次 `open` 是 syscall,系统调用开销 ~微秒级)
2. **磁盘碎片少**:一个大文件顺序写,内部分配连续;散文件容易碎片化
3. **防篡改**:玩家不能直接改资产改皮肤 / 删音乐。你想做 DLC 锁,也需要打包
4. **压缩空间**:整文件压缩比散文件高(共享字典)
5. **跨平台统一**:Windows / Mac / Linux 用同一份 .hha,不用分别处理路径大小写 / 分隔符
6. **校验**:加 hash 校验防止数据损坏

今天的核心工作是**定义 .hha 文件格式**——文件头是什么、字段顺序、字节序、对齐。这不是写代码,是设计。**Casey 用一整集讨论"为什么这样设计"**,这是工程化的核心环节:文档化你的数据。

定义文件格式要决定的几件事:

1. **字节序**:大端还是小端?(x86/ARM 都是小端,选小端最自然)
2. **对齐**:字段是否需要 4/8 字节对齐?(对齐让 SIMD/mmap 友好)
3. **版本号**:格式以后会变,要 version 字段
4. **魔法数(magic number)**:文件开头一个独特字节序列,用来"识别这是 .hha 不是 .png"
5. **TLV(type-length-value)还是固定 layout**:固定 layout 简单但僵硬;TLV 灵活但代码复杂

Casey 选**固定 layout + magic + version**,简单且够用。

心理锚点:看完今天,你能设计一个简单的二进制文件格式,并能用 Rust 写出对应的读写代码骨架。

## 1 · Casey 今天做了什么

Casey 在白板上画 .hha 的结构,讨论每个字段:

```
+--------------------------------+
| magic: "HHA2"        (4 bytes) |
+--------------------------------+
| version: u32         (4 bytes) |
+--------------------------------+
| tag_count: u32       (4 bytes) |
+--------------------------------+
| asset_count: u32     (4 bytes) |
+--------------------------------+
| tags:    Tag[tag_count]        |
+--------------------------------+
| assets:  Asset[asset_count]    |
+--------------------------------+
| asset data blob (变长)         |
+--------------------------------+
```

每个 Tag(标签,用来按"剑"、"敌人"等查询):

```
struct Tag {
    id: u32,         // 标签 ID(预定义枚举)
    value: f32,      // 标签值(如 "weight" = 10.0)
}
```

每个 Asset:

```
struct Asset {
    type: u32,       // AssetType 枚举:Bitmap / Sound / Font
    first_tag_index: u32,
    one_past_last_tag_index: u32,
    data_offset: u64,  // 在文件中的字节偏移
    data_size: u64,
}
```

Casey 反复强调:

- **所有字段固定大小**(u32 / u64),不存 String。字符串用预先约定的 enum ID,跨平台一致
- **asset data 在文件末尾的 blob 段**,前面只存索引。这样加载时可以先 mmap 索引,asset 按需读
- **magic 必须独特**,Casey 用 `HHA2`(HHA = Handmade Hero Asset,2 = 版本)
- **版本字段**让以后改格式可以兼容(检测旧版本,做转换)

## 2 · 心智模型

### 类比:图书馆

一个图书馆有几万本书。两种组织方式:

**方式 A:散文件**:每本书一个文件夹,书号 / 书名 / 作者 / 摘要都写在 README.txt 里。找一本书要遍历所有文件夹。

**方式 B:索引 + 内容**:开头有一个**卡片目录柜**(card catalog),每个抽屉是一类(科幻 / 文学 / 历史)。卡片上写书号 + 简介 + 在书架第几排第几层。书本身按书号顺序排在书架上。

打开图书馆:

1. 先看目录柜(几秒)
2. 找到要的书号,知道在书架 3 排 5 层
3. 直接走到那个位置取书(几秒)

总计时间 < 1 分钟。比翻遍所有文件夹快几千倍。

.hha 文件就是方式 B:**前半部分是卡片目录(index),后半部分是书架(data blob)**。

### 严谨模型:文件格式设计原则

#### 原则 1:magic number

文件开头 4-8 字节是独特的字节序列。读者加载时先检查 magic,不匹配则报错。

```rust
const HHA_MAGIC: [u8; 4] = *b"HHA2";
```

`*b"HHA2"` 是把字符串字面量转成 `[u8; 4]`。`b"..."` 是字节字符串。

为什么需要 magic?用户可能误把 .png 改成 .hha,你的代码要检测出来而不是崩溃。

#### 原则 2:版本字段

```rust
const HHA_VERSION: u32 = 2;
```

读文件时:

```rust
if version != HHA_VERSION {
    panic!("unsupported version {}", version);
}
```

未来版本 3 改格式,你可以同时支持 2 和 3,做兼容。

#### 原则 3:固定大小 header

固定大小 = 你一次 `read` 就能读完整个 header,不需要"读到 N 个 tag"再决定读多少。

Casey 的设计:header 是固定 4 × 4 = 16 字节(magic + version + tag_count + asset_count)。

#### 原则 4:对齐

所有 u32 字段 4 字节对齐,u64 8 字节对齐。Casey 在 Rust 用:

```rust
#[repr(C)]
struct HhaHeader {
    magic: [u8; 4],       // offset 0
    version: u32,         // offset 4
    tag_count: u32,       // offset 8
    asset_count: u32,     // offset 12
}
// 总大小 16 字节
```

`#[repr(C)]` 让 Rust 用 C 的内存布局(每个字段按自然对齐),不重新排列。这是读写二进制文件的必需。

#### 原则 5:字节序

x86/ARM 都是小端,所以 Casey 选小端。Rust:

```rust
let n: u32 = 0x12345678;
let bytes = n.to_le_bytes();  // [0x78, 0x56, 0x34, 0x12]
```

LE = little endian。大端(BE)网络字节序常用,但本机字节序几乎都是 LE。

#### 原则 6:offset + size 而非 inline data

资产数据存在文件末尾的 blob,前面只存 (offset, size) 索引。这样:

- 加载索引快(只读 header + 几 KB 索引)
- 实际资产按需读
- 容易 mmap:把整个文件映射到内存,通过 offset 索引访问

### TLV vs 固定 layout

另一种设计是 Type-Length-Value:

```
| type (1B) | length (4B) | value (length B) |
```

TLV 优点:灵活(可加新类型不破坏旧版)。缺点:每个字段多 5 字节 overhead,代码复杂。

Casey 不用 TLV,因为他的 asset 类型固定(Bitmap/Sound/Font),未来不会爆炸增长。**用对的工具**——TLV 适合 JSON / XML / protobuf 这种"任意结构",固定 layout 适合"我知道有什么"。

### 二进制 vs 文本格式

| | 二进制(.hha) | 文本(JSON) |
|---|---|---|
| 大小 | 紧凑 | 大 2-10 倍 |
| 读写速度 | 快(直接 memcpy) | 慢(解析) |
| 可读性 | 差(要 hex 工具) | 好 |
| 版本演化 | 难(改字段就破坏兼容) | 容易(加字段不破坏) |
| 编辑 | 需要 build 工具 | 文本编辑器即可 |

游戏发行用二进制;开发期用文本(JSON)或工程内部格式,build 时转二进制。Casey 是教学,直接二进制。

## 3 · 四域深入

### 3.1 · 游戏编程视角

工业级 asset 文件格式实例:

- **ZIP** / **gzip** —— 通用,Unity/Unreal 都支持
- **OBB** (Opaque Binary Blob) —— Android 应用扩展
- **pak** (id Tech) —— Quake/Half-Life/Doom
- **cas** (CASC) —— 暴雪游戏(WoW/StarCraft)
- **bsa** (Bethesda) —— 上古卷轴/辐射

它们都有共同设计:magic + version + index + blob。

游戏 build 流程:

```
美术资产(PSD, WAV, FBX) 
  → 中间格式(PNG, OGG, glTF) 
  → build asset pack(.hha / .pak / .bundle)
  → 游戏运行时加载
```

每步可能转码 / 压缩 / 优化。**Casey 在 build 期把 BMP 转 RGB565 / RGBA8 把 WAV 转原始 PCM**,运行时直接 memcpy。这是为什么 build 流程不能省。

### 3.2 · Linux 系统编程视角

Linux 上读 .hha 的方式:

1. **`read(2)`**:打开 → 读 header → 读索引 → 读 asset 数据。简单但每个 asset 多次 syscall。
2. **`mmap(2)`**:整个文件映射到虚拟内存,通过指针访问。**内核按需 page in**。最快的方式。

```rust
use std::fs::File;
use memmap2::Mmap;

let file = File::open("game.hha")?;
let mmap = unsafe { Mmap::map(&file)? };
let header: &HhaHeader = unsafe { &*(mmap.as_ptr() as *const HhaHeader) };
let asset_data = &mmap[asset.data_offset as usize..][..asset.data_size as usize];
```

**关键**:mmap 后访问数据时,内核按需读盘。第一次访问某 page 触发缺页中断,内核读 4 KB;后续访问已是 resident page,纯内存速度。

### 3.3 · Rust 生态视角

Rust 表达二进制格式:

- **`#[repr(C)]`** —— 保证字段按声明顺序、自然对齐。
- **`std::mem::size_of`** / **`align_of`** —— 编译期算大小和对齐。
- **`bytemuck::cast_slice`** / **`cast_ref`** —— 安全地把 `&[u8]` 转 `&T`,要求 `T: Pod`(plain old data)。
- **`zerocopy`** crate —— 类似 bytemuck,泛型更友好。

读 header:

```rust
use bytemuck::{from_bytes, Pod, Zeroable};

#[repr(C)]
#[derive(Copy, Clone, Pod, Zeroable)]
struct HhaHeader {
    magic: [u8; 4],
    version: u32,
    tag_count: u32,
    asset_count: u32,
}

fn read_header(data: &[u8]) -> &HhaHeader {
    assert!(data.len() >= std::mem::size_of::<HhaHeader>());
    from_bytes(&data[..std::mem::size_of::<HhaHeader>()])
}
```

`Pod` trait 表示"内存里就是字节,可以直接 reinterpret"。无 Drop,无 padding(或 padding 字节定义明确)。

### 3.4 · 数据结构视角

Casey 的 asset 文件本质是:

- 一个 **fixed header**(16 字节)
- 一个 **array of tags**
- 一个 **array of assets**(每个 asset 有 tag range,表示"这个 asset 有哪些 tag")
- 一个 **blob of data**(实际字节)

这是一个 **关系数据库**(relational database)的最简版:asset 表通过 tag_index 关联到 tag 表。

更复杂的设计:

- **B-tree 索引**:asset_count 上百万时,二分查找 tag 字典更快
- **multiple file packs**:每个 DLC 一个 pack,运行时合并
- **diff pack**:增量更新,只改动的 asset

Casey 不做这些(数据量小),但思路对工业级有用。

## 5 · 对照与变奏

### 不同文件格式的 magic

| 格式 | magic | ASCII |
|---|---|---|
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `\x89PNG\r\n\x1a\n` |
| JPEG | `FF D8 FF` | (binary) |
| GIF | `47 49 46 38` | `GIF8` |
| ZIP | `50 4B 03 04` | `PK\x03\x04` |
| ELF | `7F 45 4C 46` | `\x7fELF` |
| PE(Windows exe) | `4D 5A` | `MZ` |
| Mach-O | `FE ED FA CE` | `\xfe\xed\xfa\xce` |
| HHA(本日) | `48 48 41 32` | `HHA2` |

PNG 的 magic 特别有意思:它包含 `\r\n` 和 `\x1a\n`,用来防止早期 FTP / 邮件系统把二进制当文本处理(转 CR/LF,或截断到 \x1a = Ctrl+Z EOF)。设计 magic 时要考虑传输层损坏。

### 大端 vs 小端

| 字节序 | 表示 0x12345678 | 主要用户 |
|---|---|---|
| LE(小端) | `78 56 34 12` | x86, ARM(默认), Rust 默认 |
| BE(大端) | `12 34 56 78` | 网络(signed integer), IBM mainframe, Java JVM |

**为什么网络用大端?** 历史原因——早期 ARPANET 的主机很多是大端,协议固化下来。所以叫"network byte order"。

Rust:

- `to_le_bytes` / `from_le_bytes` —— 小端
- `to_be_bytes` / `from_be_bytes` —— 大端
- `to_ne_bytes` / `from_ne_bytes` —— 本机序

设计文件格式推荐小端(主流平台都是),跨平台用大端(网络兼容)。

### FlatBuffers vs Protobuf

进阶读者关心的对比:

| | Protobuf | FlatBuffers |
|---|---|---|
| 读取 | 需要解析整个消息 | 零拷贝(直接访问 buffer) |
| 大小 | 紧凑(变长 int) | 较大(对齐 + offset 表) |
| schema | 必须 | 必须 |
| 适合 | RPC, 持久化 | 游戏, 高频 |

游戏 asset 适合 FlatBuffers(类似 .hha 但更通用)。但自己写 .hha 学习价值高。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 的 `Tag` 结构存 `id: u32` 而不是 `name: String`?

**参考解答**:

1. **跨平台一致**:u32 在所有平台字节序、大小都固定;String 要处理 UTF-8、长度变长。
2. **空间小**:u32 是 4 字节,String 平均 10-20 字节 + 长度字段。
3. **比较快**:u32 一条指令比较;String 是 memcmp。
4. **本地化**:不用改字符串就有翻译(ID 不变,显示文本单独存)。
5. **防篡改**:用户改 .hha 文件里的 String 可能破坏索引;改 ID 让游戏找不到 asset,容易检测。

### Lv2 · 动手实践

**题**:用 Rust 定义 .hha 的全部结构(HhaHeader, HhaTag, HhaAsset, AssetType),用 `#[repr(C)]`。写一个函数 `write_header(file: &mut File, h: &HhaHeader)`,用 `to_le_bytes` 一字节一字节写。验证:写一个 magic=`HHA2`、version=2、tag_count=3、asset_count=5 的 header,用 `xxd` 看十六进制。

完成标准:`xxd` 输出开头是 `4848 4132 0200 0000 0300 0000 0500 0000`。

**参考解答**:

```rust
use std::fs::File;
use std::io::{Write, BufWriter};

#[repr(C)]
#[derive(Copy, Clone, Debug)]
pub struct HhaHeader {
    pub magic: [u8; 4],
    pub version: u32,
    pub tag_count: u32,
    pub asset_count: u32,
}

#[repr(C)]
#[derive(Copy, Clone, Debug)]
pub struct HhaTag {
    pub id: u32,
    pub value: f32,
}

#[repr(C)]
#[derive(Copy, Clone, Debug)]
pub struct HhaAsset {
    pub asset_type: u32,    // 0=Bitmap, 1=Sound, 2=Font
    pub first_tag_index: u32,
    pub one_past_last_tag_index: u32,
    pub data_offset: u64,
    pub data_size: u64,
}

pub const ASSET_TYPE_BITMAP: u32 = 0;
pub const ASSET_TYPE_SOUND: u32 = 1;
pub const ASSET_TYPE_FONT: u32 = 2;

pub const HHA_MAGIC: [u8; 4] = *b"HHA2";
pub const HHA_VERSION: u32 = 2;

fn write_header(file: &mut File, h: &HhaHeader) -> std::io::Result<()> {
    file.write_all(&h.magic)?;
    file.write_all(&h.version.to_le_bytes())?;
    file.write_all(&h.tag_count.to_le_bytes())?;
    file.write_all(&h.asset_count.to_le_bytes())?;
    Ok(())
}

fn main() -> std::io::Result<()> {
    let mut f = BufWriter::new(File::create("test.hha")?);
    let header = HhaHeader {
        magic: HHA_MAGIC,
        version: HHA_VERSION,
        tag_count: 3,
        asset_count: 5,
    };
    write_header(&mut f, &header)?;
    f.flush()?;
    println!("wrote test.hha, {} bytes", std::mem::size_of::<HhaHeader>());
    Ok(())
}
```

```bash
cargo run && xxd test.hha
# 预期输出:
# 00000000: 4848 4132 0200 0000 0300 0000 0500 0000  HHA2............
```

## 8 · Rust / Arch 落地代码

完整 .hha 写入 + 读取示例:

```rust
// Cargo.toml
// [dependencies]
// bytemuck = "1"
// memmap2 = "0.9"

use bytemuck::{Pod, Zeroable, from_bytes, bytes_of};
use std::fs::File;
use std::io::{Write, BufWriter, Read};

#[repr(C)]
#[derive(Copy, Clone, Debug, Pod, Zeroable)]
pub struct HhaHeader {
    pub magic: [u8; 4],
    pub version: u32,
    pub tag_count: u32,
    pub asset_count: u32,
}

#[repr(C)]
#[derive(Copy, Clone, Debug, Pod, Zeroable)]
pub struct HhaAsset {
    pub asset_type: u32,
    pub first_tag_index: u32,
    pub one_past_last_tag_index: u32,
    pub data_offset: u64,
    pub data_size: u64,
}

const HHA_MAGIC: [u8; 4] = *b"HHA2";
const HHA_VERSION: u32 = 2;

fn main() -> std::io::Result<()> {
    // === 写入 ===
    {
        let mut f = BufWriter::new(File::create("demo.hha")?);

        // 1. Header(16 bytes)
        let header = HhaHeader {
            magic: HHA_MAGIC,
            version: HHA_VERSION,
            tag_count: 0,
            asset_count: 2,
        };
        f.write_all(bytes_of(&header))?;

        // 2. 2 个 asset 描述(在文件 offset 16,每个 24 bytes)
        let assets = [
            HhaAsset {
                asset_type: 0,            // bitmap
                first_tag_index: 0,
                one_past_last_tag_index: 0,
                data_offset: 16 + 2 * std::mem::size_of::<HhaAsset>() as u64,
                data_size: 100,           // 假装 100 字节图像数据
            },
            HhaAsset {
                asset_type: 1,            // sound
                first_tag_index: 0,
                one_past_last_tag_index: 0,
                data_offset: 16 + 2 * std::mem::size_of::<HhaAsset>() as u64 + 100,
                data_size: 200,
            },
        ];
        for a in &assets {
            f.write_all(bytes_of(a))?;
        }

        // 3. 数据 blob(假装 300 字节)
        let blob = vec![0xAAu8; 300];
        f.write_all(&blob)?;
        f.flush()?;
    }

    println!("wrote demo.hha");

    // === 读取 ===
    {
        let mut f = File::open("demo.hha")?;
        let mut buf = Vec::new();
        f.read_to_end(&mut buf)?;

        // 1. 读 header(直接 cast)
        let header_size = std::mem::size_of::<HhaHeader>();
        let header: &HhaHeader = from_bytes(&buf[..header_size]);

        if header.magic != HHA_MAGIC {
            panic!("not a HHA file");
        }
        if header.version != HHA_VERSION {
            panic!("version mismatch: {}", header.version);
        }
        println!("HHA v{}, {} assets", header.version, header.asset_count);

        // 2. 读 assets 数组
        let asset_size = std::mem::size_of::<HhaAsset>();
        for i in 0..header.asset_count as usize {
            let start = header_size + i * asset_size;
            let end = start + asset_size;
            let a: &HhaAsset = from_bytes(&buf[start..end]);
            println!("  asset[{}]: type={} offset={} size={}",
                i, a.asset_type, a.data_offset, a.data_size);

            // 3. 访问 asset 数据
            let off = a.data_offset as usize;
            let sz = a.data_size as usize;
            let data = &buf[off..off + sz];
            println!("    first byte: 0x{:02x}", data[0]);
        }
    }

    Ok(())
}
```

**关键 Rust**:

- `bytes_of(&t)` —— bytemuck 提供,把 `&T` (T: Pod) 转 `&[u8]`。
- `from_bytes(&buf)` —— 反过来,把 `&[u8]` 转 `&T`。要求长度正好。
- `Pod + Zeroable` —— bytemuck 的 trait,表示"内存里就是字节"。
- `std::mem::size_of::<T>()` —— 编译期大小,Casey 风格的"绝不魔法数"。

  asset[1]: type=1 offset=164 size=200

**Troubleshooting**:
- `size_of::<HhaAsset>` 不是 24 —— 你忘了 `#[repr(C)]`,Rust 默认布局可能加 padding。
- `from_bytes` panic —— buffer 长度不对,检查 `start..end`。
