# Day 112 · CPU 性能心智模型

> 在你"调优代码"之前,先回答一个问题:**CPU 在跑你的代码时,到底是什么在变慢?** Casey 这一天不写一行游戏代码,他要把"性能"这个词从模糊的感觉变成可计算的物理量。

## 0 · 为什么要有这一天

你大概写过这样的代码:某个函数慢,你换了个"更聪明"的算法,结果没快反慢。或者你跑 `cargo build --release` 之后帧率从 30 提到 60,但不知道是哪个优化起了作用。更糟的是,有时候你删掉一段"看起来没用"的代码,程序反而**慢了一倍**——这不是玄学,这是 CPU 在用它的物理结构跟你开玩笑。

要解释这些现象,你必须建立一个**心智模型**:CPU 不是"每秒执行 N 条指令"的简单机器,而是一个**有流水线、有多端口、有 cache 层级、有分支预测**的复杂工厂。同一段指令序列在不同 CPU 上,在不同数据上,在不同周边指令下,跑出来的时间可以差 10 倍以上。

Casey 在这一天提出了**整个 Phase 4 的总纲**:后面所有 SIMD、cache、对齐、并行化的讨论,都建立在今天建立的"CPU 是什么"模型上。如果你跳过这一天直接去抄 SIMD intrinsic,你后面就会写出"明明用了 AVX2 却比标量还慢"的代码,而且找不到原因。

心理锚点:读完这一天,你能回答下面 4 个问题(每一题都是真实工程里每天会问的):

1. 为什么 `if x > 0 { do_a() } else { do_b() }` 比 `do_both_and_select()` 有时慢 3 倍?
2. 为什么顺序访问一个 `Vec<u8>` 比随机访问快 100 倍,而访问量都是"读 100MB"?
3. 为什么 4 个线程跑同一份代码,有时总耗时反而比 1 个线程更长?
4. 为什么 `a[i] * b[i] + c[i]` 用 `mul_add` 写会"同时更快又更准"?

如果你回答不出来,把 §2 心智模型啃两遍,再继续 Day 113。

## 1 · Casey 今天做了什么

Casey 这一天**纯讲概念,不写代码**。他在白板上画了一张 CPU 的"工厂平面图":

1. **指令流水线**(instruction pipeline)——指令不是一条一条执行的,而是像流水线一样"一条还没走完,下一条已经在路上"
2. **执行端口**(execution ports)——一个 CPU 周期里,可以同时发起好几个独立操作(整数加法、浮点乘法、内存读、分支判断),只要它们走不同的"端口"
3. **吞吐 vs 延迟**(throughput vs latency)——这两件事是分开的,一段代码可以"每秒处理 1000 条指令"但"每条要等 1000 秒"(吞吐高、延迟也高)
4. **数据依赖**(data dependency)——如果指令 B 需要指令 A 的结果,A 没算完 B 就得等,这是延迟的来源
5. **分支**(branch)与**分支预测**(branch prediction)——`if/else` 让 CPU 必须猜一个分支继续跑,猜错了就要"回滚流水线",代价巨大

最后 Casey 说:从现在开始,所有 HH 的"优化"动作,都是在回答"我的代码哪里受 port 限制,哪里受 cache 限制,哪里受分支限制,哪里受依赖链限制"。这是 Phase 4 余下 60+ 集的总纲。

## 2 · 心智模型

### 2.1 类比:CPU 是一家餐厅厨房

想象一家大餐厅的厨房:

- **厨师**有多个,每个厨师只会做几道菜(蒸、炒、烤、凉菜)。这相当于 CPU 的**执行端口**:有的端口做整数 ALU,有的做浮点乘法,有的做内存 load/store。
- **菜单**(指令)要拆成几步:看单 → 备料 → 烹饪 → 装盘 → 上菜。每一步都要走"对应的工位"。这就是**流水线**:一条指令被拆成 10-20 步,每步走不同的工位。
- **同时能做几道菜?** 取决于"有没有空闲工位"。如果当前 5 个蒸菜都堵在蒸笼工位(只有一个蒸笼),那 5 道菜不能并行,即使有 10 个厨师在闲着。这就是**port pressure**:CPU 的瓶颈往往是某一个端口堵了,不是整体算力不足。
- **依赖**:炒菜必须等切菜完成(下一道工序依赖上一道的产物)。如果你点 100 道完全独立的炒菜,厨房 1 分钟做完;但如果你点 1 道菜做完再点下一道,要 100 分钟。这就是**指令级并行**(ILP)能不能被 CPU 找到。
- **分支预测**:服务员拿到一张"看顾客性别决定上茶或咖啡"的单,但他不知道顾客性别。他可以**猜一个**(分支预测),先把猜的那道菜做了;猜对了节省时间,猜错了就要扔掉重做(流水线 flush)。

CPU 性能优化的核心:**找出厨房里哪个工位堵了(port pressure),把它解开**。

### 2.2 三种"慢"的来源

Casey 把"代码慢"分成三个独立的来源。这是整个 Phase 4 的分析框架,必须记牢:

| 慢的来源 | 直觉 | 典型例子 | 解药 |
|---|---|---|---|
| **延迟 (Latency)** | 一条指令从开始到结束的时间 | `mulss` 在 Skylake 上 4 周期 | 用 ILP 把多条独立指令交错 |
| **吞吐 (Throughput)** | 单位时间能完成多少指令 | `mulss` 每 0.5 周期能开始一条(2 个 mul 端口) | 用 SIMD 把 4 条变成 1 条 |
| **端口 (Port Pressure)** | 某个端口被堵了 | 一段代码全是乘法,mul 端口堵死 | 把乘法换成加法 / 位运算 |

**关键**:这三件事**互相独立**。同一段代码,可能是延迟受限,也可能是吞吐受限,也可能是 port 受限。优化方向**完全不同**。

举个数字:假设你有一个内循环,跑 1000 次,每次做 4 条乘法。

- **吞吐视角**:Skylake 的 `mulps` 每 0.5 周期一条,所以 4 条乘法最少要 2 周期。1000 次循环 = 2000 周期。
- **延迟视角**:每条 `mulps` 4 周期。如果第 2 条乘法**依赖**第 1 条的结果,那么必须等 4 周期才能开始第 2 条,4 条就是 16 周期。1000 次循环 = 16000 周期——慢了 8 倍!

这就是 ILP 的重要性:**让多条指令之间无依赖,CPU 才能把它们塞进同一周期**。

### 2.3 数据依赖:延迟的真正来源

来看一段简单代码:

```rust
let mut sum = 0.0f32;
for i in 0..1000 {
    sum = sum * data[i];   // (1) 乘法
}
```

每一次循环的乘法,**必须等上一次乘法的结果**——因为 `sum` 是累乘的。这就是**数据依赖链**(dependency chain)。

CPU 的乘法单元"吞吐"很高(0.5 周期一条),但因为每一条都依赖前一条,实际执行变成"4 周期一条",慢 8 倍。

**解药**:用多个累加器**打破依赖链**。

```rust
let mut sum0 = 0.0f32;
let mut sum1 = 0.0f32;
for i in (0..1000).step_by(2) {
    sum0 = sum0 * data[i];     // 独立链
    sum1 = sum1 * data[i+1];   // 独立链
}
let sum = sum0 * sum1;
```

这样 CPU 可以把 `sum0 * data[i]` 和 `sum1 * data[i+1]` 塞进同一个周期(因为它们彼此独立),吞吐利用率翻倍。

**这就是 Phase 4 你要做的事的本质**:不断寻找"哪里有依赖链",不断打破它。

### 2.4 cache 层级:另一个慢的来源

CPU 算得再快,如果数据不在 cache 里,要从 DRAM 取,要等 100+ 周期。现代 CPU 的 cache 层级:

| 层级 | 容量 | 延迟(周期) | 带宽 |
|---|---|---|---|
| L1 | 32 KB / 核 | 4 | ~1 TB/s |
| L2 | 256 KB - 1 MB / 核 | 14 | ~500 GB/s |
| L3 | 数 MB - 数十 MB(全核共享) | 40-70 | ~200 GB/s |
| DRAM | GB 级 | 200-400 | ~50 GB/s |

注意:**L1 和 DRAM 的延迟差 50-100 倍**。一段代码"内存访问模式"决定它是 L1 友好还是 DRAM 受限。

#### 顺序 vs 随机访问

```rust
// 模式 A:顺序访问
for i in 0..N { sum += data[i]; }

// 模式 B:随机访问
for i in 0..N { sum += data[indices[i]]; }   // indices 是随机洗牌过的
```

两段代码都"读了 N 个 f32 = 4N 字节"。但 A 跑得比 B 快 50-100 倍,因为:

- **A**:CPU 的**硬件预取器**(hardware prefetcher)看到"地址每次 +4 字节"的模式,自动把后面的数据预取到 L1。每次访问都是 L1 命中。
- **B**:每次 `indices[i]` 指向的地址是随机的,预取器无法预测。每次都从 L2/L3 甚至 DRAM 取。

这就是为什么 Casey 后面要把"实体"放在**连续内存**里(SoA 布局)——为了让 CPU 的预取器工作。

#### Cache line(缓存行)

CPU 不是按字节读写内存,而是按 **cache line**(64 字节)读写。即使你只读 1 字节,CPU 也会把整条 64 字节 line 拉进 L1。

**陷阱**:如果两个线程频繁写**同一条 cache line 上的不同变量**,这条 line 在两个核心之间不停"穿梭",性能急剧下降——叫 **false sharing**(伪共享)。Phase 4 多线程章节你会被这个坑很多次。

解药:`#[repr(align(64))]` 把数据按 cache line 对齐,确保不同线程的数据不在同一条 line。

### 2.5 分支预测

考虑:

```rust
let mut sum = 0;
for i in 0..N {
    if data[i] > 0 { sum += data[i]; }
}
```

CPU 看到 `if data[i] > 0` 时,还不知道 `data[i]` 的值(load 还在路上)。怎么办?

**选项 1:等**——load 完成后再决定。这会**把流水线停住 10+ 周期**,完全不能容忍。

**选项 2:猜**——CPU 的**分支预测器**(branch predictor)基于历史"猜一个方向",先按猜的跑。等 load 完了发现猜错了,把猜错期间的所有工作扔掉,重头来。猜错代价 ~15-20 周期。

**什么时候分支预测好?** 当分支结果**可预测**(数据有一定模式)。比如"90% 的时间都进入 if",预测器很容易达到 99% 命中率,几乎没代价。

**什么时候分支预测坏?** 当分支结果**完全随机**(数据无模式)。预测器命中率 50%,每两次猜错一次,每次代价 20 周期。1000 次循环 = 10000 周期浪费。

**解药**:把分支换成**无分支的算术**。

```rust
// 无分支版本
for i in 0..N {
    let mask = (data[i] > 0) as i32;   // 1 或 0
    let mask_arith = -mask;            // 0xFFFFFFFF 或 0x00000000
    sum += data[i] & mask_arith;
}
```

`data[i] & 0xFFFFFFFF` = `data[i]`,`data[i] & 0` = 0。一次 AND 比 20 周期的分支预测失败便宜得多。

但**这不是永远更优**:如果分支高度可预测(99% 进入 if),原来的分支代码更好——CPU 几乎不预测失败,而 AND 多了一次运算。

**结论**:性能优化没有"永远更优"的写法,只有"在你的数据分布下"更优的写法。**测量是唯一的裁判**。

### 2.6 SIMD:吞吐视角的解药

我们前面说"一条 `mulps` 同时做 4 个乘法"。这就是 SIMD(Single Instruction Multiple Data):一条指令同时处理多个数据。

SIMD 不是改变延迟(还是 4 周期一条),而是**改变吞吐**(一条指令完成 4 个结果,等价于"0.125 周期一个结果")。SIMD 是 Day 115-121 的核心,Day 112 只是埋下伏笔。

但 SIMD 也有代价:

- 数据必须**布局成"4 个一起"**(SoA 或者 SIMD lane 拆开)
- 不是所有算法都能 SIMD 化(如果有复杂控制流,SIMD 利用率低)
- 对齐要求(SIMD load 最好是 16/32/64 字节对齐,否则慢甚至崩)

**SIMD 是 Phase 4 的物理基础之一**,但你必须先有今天的"port + 吞吐 + 延迟"模型才能理解为什么 SIMD 快。

### 2.7 多线程:另一维的并行

SIMD 是"一条指令处理多个数据",**多线程**是"多个 CPU 核同时跑不同的指令"。这是正交的并行方式:

- **SIMD**:数据并行(同一段代码同时处理多个数据)
- **多线程**:任务并行(多个独立任务在多个核上跑)

Phase 4 的中期(Day 121+ 的 tiled rendering)会**同时用 SIMD + 多线程**:每个 tile 内部 SIMD 处理像素,不同 tile 分给不同核心。

多线程的代价:

- **同步**(锁、原子):两个线程协调的代价
- **cache 失效**:线程切换核时,数据要重新载入
- **共享 cache line**:伪共享(2.4 节)

Day 122+ 详谈。

**总结**:今天的核心是三个模型——**port/throughput/latency** 三件套,**cache 层级**,**分支预测**。一切"性能优化"的本质都是:测量找出哪个模型是你当前的瓶颈,然后对症下药。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发是性能工程最严苛的领域之一:你必须在**每秒 60 帧(16.67ms)或 144 帧(6.94ms)** 内完成所有事——AI、物理、渲染、音频混合、输入。慢一毫秒就是"卡顿"。

Casey 在这一天为后面的优化立下规矩:**任何优化必须先测量,再动手**。Day 113 你会手写性能计数器,Day 119 用 IACA 看 port 占用,Day 121 的 marathon 就是这套方法的集中演练。

游戏开发的几个性能铁律,直接来自今天的心智模型:

1. **数据布局 > 算法**:一个 O(n²) 算法 + cache 友好的布局,往往比 O(n log n) + cache 不友好更快(n 小时)。Casey 在 Day 121 用 SIMD 把渲染 tile 化就是典型例子。
2. **避免在热循环里分支**:热循环的 if 用位运算替代,要么把数据排序让分支变可预测。
3. **不要在热循环里分配内存**:malloc 触发系统调用 + 锁 + cache 失效。
4. **先 profile 再优化**:用 perf / 调试计数器找到真正瓶颈,而不是凭"我觉得 X 慢"。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上你测量性能的工具链:

| 工具 | 测什么 | 怎么用 |
|---|---|---|
| `perf stat` | 高层指标(CPI、cache miss 率) | `perf stat ./a.out` |
| `perf record` + `perf report` | 函数级 profile | `perf record ./a.out; perf report` |
| `perf stat -e cycles,instructions,cache-misses` | 指定事件 | 看每个事件的次数 |
| `valgrind --tool=cachegrind` | cache miss 模拟 | 慢 20-50 倍但精确 |
| `flamegraph` | 调用栈火焰图 | cargo install flamegraph; cargo flamegraph |
| `nasm` / `objdump` | 看汇编 | 确认 SIMD 指令真的生成了 |

#### 高层指标:CPI(Cycles Per Instruction)

CPI = CPU 周期数 / 指令数。这是最常用的"效率指标":

- CPI ≈ 0.25:理论上限(每周期 4 条指令退休)
- CPI ≈ 0.5-1:良好
- CPI ≈ 2-3:有 cache 或分支问题
- CPI > 5:严重问题(比如大量 cache miss)

`perf stat` 直接给出这个数:

```bash
perf stat ./target/release/mygame
# 输出里找 "insn per cycle" 这一行,就是 1/CPI 的倒数
```

#### 性能计数器(PMU)

CPU 内部有一组硬件**性能计数器**(Performance Monitoring Unit, PMU),能数出"这 1 秒里发生了多少次 cache miss、多少次分支预测失败、多少次 SIMD 指令"。Linux 通过 `perf_event_open(2)` 系统调用暴露这些计数器。

`perf` 工具是 PMU 的用户态前端。Phase 4 后面每一天 Casey 都会用 Windows 上对应的 VTune / IACA 看 PMU 数据;Linux 上你用 `perf stat -e` 看同样的事。

### 3.3 · 🦀 Rust 生态视角

Rust 的几个特性对今天的模型有直接影响:

#### 1. `#[inline]` 和 LTO

```rust
#[inline]
fn fast_add(a: f32, b: f32) -> f32 { a + b }
```

`#[inline]` 提示编译器把函数体嵌入调用点。如果函数很小(几个数学运算),inline 消除了函数调用开销,更重要的是**让 ILP 能跨函数边界工作**(没有调用边界,数据依赖链不断)。

`Cargo.toml` 加 `lto = "fat"` 让链接时优化,跨 crate inline。

#### 2. `#[repr(align(N))]`

```rust
#[repr(C, align(64))]
struct CacheLineAligned {
    data: [u8; 64],
}
```

把结构体按 N 字节对齐。N=64 是 cache line 大小,适合多线程避免 false sharing。N=16/32/64 适合 SIMD load。

#### 3. `core::hint::black_box`

防止编译器把"计算结果"优化掉:

```rust
fn bench() {
    let v = (0..1000).map(|i| i as f32 * 2.0).collect::<Vec<_>>();
    let mut sum = 0.0f32;
    for x in &v { sum += x; }
    std::hint::black_box(&sum);  // 阻止优化器删掉整个循环
}
```

写 benchmark 必须用,否则编译器看到 `sum` 没人用,直接把循环删了——你测出来是 0ms,但根本没测到。

#### 4. SIMD:Rust 的两条路

- **`std::arch::x86_64`**:直接调 SIMD intrinsic(`_mm_add_ps` 等),和 Casey 的 C 代码一一对应。unsafe。
- **`std::simd`(portable_simd)**:稳定化中,跨平台抽象。Safe。

Day 115-121 详细讲。

### 3.4 · 🎨 图形学视角

图形学是 CPU 性能心智模型最直接的受益者。软渲染(Phase 3-4)的瓶颈几乎都是 cache 和 SIMD:

- **像素遍历**:64×64 tile 的像素顺序写,完美匹配 L1 + 预取 + SIMD。Day 121 的核心。
- **纹理采样**:每次采样读 4 个 texel 做双线性插值。如果 texel 布局是 tiled(把 2D 局部性映射到 1D 内存),cache 命中率极高。Day 130 讲。
- **顶点变换**:4×4 矩阵乘法,可以用一条 SIMD 指令算 4 个顶点(SoA)。

GPU 本质上是"把今天的 port/cache/SIMD 模型推到极致"——GPU 有几百个简单核心,每个核心吞吐极高但单线程延迟也高。GPU 编程就是把算法"摊平"成可以喂给这种硬件的形态。Phase 5 之后 OpenGL/Vulkan 都建立在这个理解上。

## 4 · 认知地图

### 4.1 上级

- **计算机体系结构** —— CPU 设计的理论基础(流水线、cache、分支预测都从这里来)
- **性能工程** —— 测量 + 优化的整套方法论

### 4.2 同级

| 性能来源 | 关键差别 | 解药类型 | 本项目最常碰到 |
|---|---|---|---|
| Latency 受限 | 数据依赖链 | ILP / 多累加器 | 内循环累乘 |
| Throughput 受限 | 总指令数多 | SIMD / 算法改进 | 像素循环 |
| Port 受限 | 某端口堵了 | 替换指令(乘法→加法) | 三角函数 |
| Cache 受限 | 数据不在 L1 | 改数据布局 / 对齐 | 实体遍历 |
| Branch 受限 | 分支预测失败 | 无分支写法 / 排序数据 | 可见性判定 |

### 4.3 下级

- **指令流水线** —— 一条指令的 fetch → decode → execute → retire
- **执行端口**(Skylake 10+ 个) —— ALU / mul / load / store / branch 等
- **PMU 事件**(cycles / instructions / cache-misses / branch-misses) —— `perf stat -e` 列表
- **硬件预取器** —— 自动检测访问模式预取数据
- **分支预测器** —— 基于历史猜分支方向

## 5 · 对照与变奏

### 同一问题在不同 CPU 上的解药不同

**问题**:矩阵乘法。

- **x86_64 (Skylake)**:有 2 个 FMA 端口,每个端口每周期 1 条 `vfmadd231ps`,一条处理 16 个 f32(AVX-512),理论峰值 ~32 FLOP/cycle
- **Apple M1**:NEON SIMD,128 位(4 个 f32),但 NEON 是 RDNA 风格融合乘加,IPC 很高
- **GPU**:几千个简单核心,峰值 FLOP 远超 CPU,但延迟也高,需要"装满"才划算

同一段矩阵乘法代码,优化方向**完全不同**。Phase 4 之后你做"通用"数学库,要么写多份(每个 ISA 一份),要么用 portable_simd 这种抽象。

### 历史演化

- **1980s**:CPU 没有流水线,一条指令一个周期,延迟 = 吞吐 = 1
- **1990s**:流水线引入(Pentium 5 级),ILP 概念出现
- **2000s**:深流水线(Pentium 4 20+ 级),分支预测失败代价巨大
- **2010s**:SIMD 加宽(SSE 128 → AVX 256 → AVX-512 512),cache 加大
- **2020s**:大小核(P-core/E-core)、3D cache 堆叠、AI 加速器

HH 跟 Casey 学,你本质是在用 2010s 之后的 x86_64 心智模型思考问题——cache + SIMD + 分支预测是三大支柱。

### "理论最优" vs "工程最优"

理论上 CPU 性能可以无限接近"端口理论峰值"。工程上,你 70% 就很厉害了。原因:

- 编译器不一定能找到 ILP
- 数据不一定能完全 cache 友好
- 算法不一定完全 SIMD 化
- 系统其他进程在抢资源

Casey 在 Day 121 的 marathon,目标也只是"把渲染从 30 FPS 提到 60 FPS",不是"100% 端口利用率"。**优化 70% 比优化 100% 容易 10 倍,但收益已经够了**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"同一段代码,不同的输入数据分布,可能慢 10 倍"?给出三种可能的解释,并说出对应是哪个性能来源(latency / throughput / port / cache / branch)。

**参考解答**:

1. **分支预测差异**:同一份 `if data[i] > 0`,如果一组数据 99% 是正,另一组 50% 正 50% 负。前者预测器几乎不失败,后者每 2 次失败一次,慢 5-10 倍。**对应:branch**。
2. **cache 局部性差异**:同样的循环,如果输入是顺序数组,L1 命中;如果是稀疏索引,DRAM 读取。**对应:cache**。
3. **依赖链差异**:同一份乘法循环,如果数据是独立的 4 路累乘,ILP 满载;如果只有一个累乘,延迟受限。**对应:latency**。

### Lv2 · 动手实践

**题**:写一个 Rust 函数,有两种实现:普通版和无分支版。函数:`sum_positive(data: &[f32]) -> f32`,把所有正数加起来。

完成标准:写 benchmark 对比两种实现,在"数据 50% 正 50% 负随机分布"和"99% 正"两种情况下,看哪一种更快。给出测量数据。

**参考解答**:

```rust
// 普通版
fn sum_positive_branchy(data: &[f32]) -> f32 {
    let mut sum = 0.0f32;
    for &x in data {
        if x > 0.0 { sum += x; }   // 有分支
    }
    sum
}

// 无分支版
fn sum_positive_branchless(data: &[f32]) -> f32 {
    let mut sum = 0.0f32;
    for &x in data {
        // x > 0.0 在 Rust 里是 bool,(x > 0.0) as i32 是 1 或 0
        // 负号让它变成 0xFFFFFFFF 或 0x00000000
        let mask = -((x > 0.0) as i32);
        // 把 mask 当成 i32 的位模式,转 f32... 这样不行!需要别的方法
        // 用更直接的:f32 不能直接按位 AND,所以用条件表达式
        // 实际上更简单的方法是用 max
        sum += x.max(0.0);  // x < 0 时返回 0
    }
    sum
}
```

注意:`x.max(0.0)` 在大多数编译器上会编译成 `maxss` 指令(SSE 的无分支最大值),这是真正的无分支实现。比手写位运算更清晰。

Benchmark 用 `criterion`:

```toml
[dev-dependencies]
criterion = "0.5"

[[bench]]
name = "sum_positive"
harness = false
```

`benches/sum_positive.rs`:

```rust
use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn bench(c: &mut Criterion) {
    let mut g = c.benchmark_group("sum_positive");
    for pct in [50, 99] {
        let data: Vec<f32> = (0..10_000).map(|i| {
            if i % 100 < pct { i as f32 + 1.0 } else { -1.0 }
        }).collect();
        g.bench_function(format!("branchy_{}pct", pct), |b| {
            b.iter(|| black_box(sum_positive_branchy(black_box(&data))))
        });
        g.bench_function(format!("branchless_{}pct", pct), |b| {
            b.iter(|| black_box(sum_positive_branchless(black_box(&data))))
        });
    }
    g.finish();
}
criterion_group!(benches, bench);
criterion_main!(benches);
```

典型结果(你的具体数字会因 CPU 而异):

```
branchy_50pct     50us
branchless_50pct  20us   ← 无分支快 2.5 倍(50% 分支预测失败)
branchy_99pct     15us   ← 高度可预测,分支赢
branchless_99pct  20us
```

结论:**没有银弹**。要看数据分布选实现。

## 8 · Rust / Arch 落地代码

### Rust:用 PMU 事件测量 cache miss 和 branch miss

Rust 标准库不直接暴露 PMU,但你可以通过 `perf` 命令测:

```rust
// src/main.rs
use std::hint::black_box;

fn main() {
    let n = 1_000_000;
    // 顺序数组 vs 随机索引数组
    let data: Vec<f32> = (0..n).map(|i| i as f32).collect();

    // 模式 A:顺序求和
    let mut sum_a = 0.0f32;
    for i in 0..n {
        sum_a += data[i];
    }
    black_box(sum_a);

    // 模式 B:随机索引求和(用素数 stride 模拟随机)
    let mut sum_b = 0.0f32;
    let stride = 7919;  // 一个素数,跳着访问
    let mut idx = 0usize;
    for _ in 0..n {
        sum_b += data[idx];
        idx = (idx + stride) % n;
    }
    black_box(sum_b);

    println!("done");
}
```

编译运行:

```bash
cargo build --release

# 看 cache miss
perf stat -e cache-misses,cache-references,L1-dcache-load-misses,branch-misses ./target/release/cache_demo

# 典型输出:
# 1,234,567 cache-misses        # 模式 A 几乎 0,模式 B 几百万
# 5,678,901 cache-references
# 0 branch-misses               # 没有数据相关分支
```

**解读**:

- `cache-misses` = CPU 找 cache 没找到要去 DRAM 的次数
- `cache-references` = 总的 cache 访问次数
- 命中率 = 1 - misses/references,模式 A 应该 > 99%,模式 B 应该 < 60%

### Arch:perf 工具链

```bash
# 装 perf(Linux 内核工具)
sudo pacman -S perf

# 看你的 CPU 支持哪些 PMU 事件
perf list 2>&1 | head -50
# 输出几百个事件,常用的:
#   cycles                  # CPU 周期
#   instructions            # 退休指令数
#   cache-references        # cache 访问
#   cache-misses            # cache 未命中
#   branch-instructions     # 分支指令
#   branch-misses           # 分支预测失败
#   L1-dcache-load-misses   # L1 数据 cache miss
#   LLC-load-misses         # L3(Last Level Cache) miss

# 高层统计
perf stat ./target/release/cache_demo
# 关键指标 "insn per cycle":>1 表示 ILP 好,~0.5 不好

# 函数级 profile
perf record ./target/release/cache_demo
perf report
# 进入 TUI,按指令数 / cache miss 数排序,看哪个函数最热

# 火焰图(需要 flamegraph 工具)
cargo install flamegraph
cargo flamegraph --bin cache_demo
# 生成 flame.svg,浏览器打开看
```

**Troubleshooting**:

- `perf: No permission to enable task clock event`:加 `sudo` 或 `echo 1 | sudo tee /proc/sys/kernel/perf_event_paranoid`
- `perf record` 没采集到样本:加 `-F 9999`(提高采样频率到 9999Hz)
- `flamegraph` 失败:确认装了 `perl`,以及 `addr2line`(binutils 包)

### 在 Rust 里读 PMU:用 `perf-event` crate

如果想在程序内自己读 PMU(比如做内置 profiler),用 `perf-event` crate:

```toml
[dependencies]
perf-event = "0.4"
```

```rust
use perf_event::{Builder, Group};

fn main() -> std::io::Result<()> {
    let mut group = Group::new()?;
    let cycles = Builder::new().group(&mut).kind(perf_event::events::Hardware::CPU_CYCLES)?.build()?;
    let instructions = Builder::new().group(&mut).kind(perf_event::events::Hardware::INSTRUCTIONS)?.build()?;

    let mut data = vec![0.0f32; 1_000_000];
    for (i, x) in data.iter_mut().enumerate() { *x = i as f32; }

    group.enable()?;
    let mut sum = 0.0f32;
    for x in &data { sum += x; }
    std::hint::black_box(&sum);
    group.disable()?;

    let counts = group.read()?;
    println!("cycles: {}", counts[&cycles]);
    println!("instructions: {}", counts[&instructions]);
    println!("IPC: {:.2}", counts[&instructions] as f64 / counts[&cycles] as f64);

    Ok(())
}
```

**注意**:`perf-event` crate 用 unsafe 的 `perf_event_open(2)` 系统调用,只在 Linux 上能编译。
