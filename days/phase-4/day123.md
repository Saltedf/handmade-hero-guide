> 昨天你看了多线程的大图。今天深入一个具体工具:**原子操作**(atomic / interlocked)。这是多线程里最底层、最便宜、也最容易误用的同步方式。Casey 在 HH 后面的 work queue 全靠它。

## 0 · 为什么要有这一天

回到 Day 122 的 data race 例子:

```rust
static mut COUNTER: i32 = 0;
// 线程 1 / 2 都做 1M 次 COUNTER += 1
```

问题:`+= 1` 不是原子的,它是 3 步(读、加、写)。两个线程交错就出错。

**Mutex 解决**:把 `+= 1` 包在 lock 里,但 lock 慢(几百 ns)。

**Atomic 解决**:用一条 CPU 指令同时做"读、加、写",硬件保证不可打断。这叫 atomic operation 或 interlocked operation(Windows 术语)。

Atomic 比 mutex 快 5-50 倍。但只能用在一个变量的简单操作(add、sub、swap、compare_exchange)。复杂操作还是要 mutex。

## 2 · 心智模型

### 2.1 类比:邮局的"取号机"

取号机给每个客人一个唯一号码。两个客人同时按按钮,如果机器是普通 CPU,可能两人拿到同一个号(读 + 加 + 写交错)。如果机器是 atomic,两个客人保证拿到不同号。

atomic 操作的硬件保证:**整个"读改写"序列不可被打断**。

### 2.2 atomic 的硬件实现

x86 用 `lock` 前缀让指令变原子:

```asm
lock add dword [counter], 1
```

`lock` 让 CPU 在执行这条指令时**锁住 cache line**(或总线),其他 CPU 不能同时修改这条 cache line。

ARM 不用前缀,用 `ldrex` / `strex` 对(load-exclusive + store-exclusive)做 CAS。

#### CAS:Compare-And-Swap

最基础的 atomic 操作是 **CAS**:

```
CAS(addr, expected, new):
    if *addr == expected:
        *addr = new
        return true
    else:
        return false
```

整个 CAS 不可打断。x86 的 `cmpxchg` 指令就是 CAS。

所有其他 atomic 操作都可以用 CAS 实现:

```
atomic_fetch_add(addr, val):
    loop:
        old = *addr
        new = old + val
        if CAS(addr, old, new):
            return old
```

#### x86 atomic 指令一览

| 指令 | 干什么 |
|---|---|
| `lock add` | 加(返回旧值需要额外步骤) |
| `lock xadd` | fetch_add:返回旧值,加新值 |
| `lock cmpxchg` | CAS |
| `lock xchg` | swap |
| `lock inc / dec` | 自增 / 自减 |

Rust 的 `AtomicI32::fetch_add` 编译成 `lock xadd`,fetch_or 编译成 `lock or`,等等。

### 2.3 Rust 的 atomic API

Rust 标准库 `std::sync::atomic` 提供:

- `AtomicBool`
- `AtomicI8 / I16 / I32 / I64 / Isize`
- `AtomicU8 / U16 / U32 / U64 / Usize`
- `AtomicPtr<T>`

每个类型的方法:

| 方法 | 干什么 | 对应 x86 |
|---|---|---|
| `load(order)` | 原子读 | `mov`(aligned 自然原子) |
| `store(val, order)` | 原子写 | `mov` |
| `swap(val, order)` | 原子交换 | `xchg` |
| `compare_exchange(...)` | CAS | `lock cmpxchg` |
| `compare_exchange_weak(...)` | 弱 CAS(可能假失败) | `lock cmpxchg` |
| `fetch_add/sub/and/or/xor` | 读改写 | `lock xadd/sub/and/or/xor` |
| `fetch_max/min` | 读改写(CAS 循环) | CAS loop |

#### 用法

```rust
use std::sync::atomic::{AtomicI32, Ordering};

let counter = AtomicI32::new(0);
let old = counter.fetch_add(1, Ordering::Relaxed);  // 返回旧值
// counter 现在 1,old 是 0

// CAS
match counter.compare_exchange(1, 100, Ordering::SeqCst, Ordering::SeqCst) {
    Ok(_) => println!("swapped to 100"),
    Err(actual) => println!("CAS failed, current is {}", actual),
}
```

### 2.4 compare_exchange 详解

```rust
fn compare_exchange(
    &self,
    current: i32,        // 期望值
    new: i32,            // 新值
    success: Ordering,   // CAS 成功时的 ordering
    failure: Ordering,   // CAS 失败时的 ordering
) -> Result<i32, i32>;
```

返回:

- `Ok(prev)`:成功,prev 是 CAS 前的值(等于 current)
- `Err(actual)`:失败,actual 是当前值(不等于 current)

#### Weak 版本

`compare_exchange_weak` 可能在不应该失败的时候也失败(spurious failure)。这是 ARM / POWER 架构的 CAS 实现导致的。x86 上两者一样。

**何时用 weak**:在循环里用。即使偶尔假失败,循环会重试。比 `compare_exchange` 略快。

```rust
// 正确写法:用 weak + loop
let mut current = atomic.load(Ordering::Relaxed);
loop {
    let new = current + 1;
    match atomic.compare_exchange_weak(current, new, Ordering::Relaxed, Ordering::Relaxed) {
        Ok(_) => break,
        Err(actual) => current = actual,  // 更新 current,重试
    }
}
```

### 2.5 fetch_add 之外的"读改写"

#### fetch_or / fetch_and / fetch_xor

```rust
let flags = AtomicI32::new(0b0001);
flags.fetch_or(0b0100, Ordering::Relaxed);  // 设第 3 位
// flags = 0b0101
```

#### fetch_max / fetch_min

```rust
let max = AtomicI32::new(0);
max.fetch_max(5, Ordering::Relaxed);  // max 现在 5
max.fetch_max(3, Ordering::Relaxed);  // 5 还是 5(3 < 5 不变)
max.fetch_max(10, Ordering::Relaxed); // max 现在 10
```

底层是 CAS 循环(没有单条 CPU 指令)。

### 2.6 Ordering 实战

#### Relaxed:最便宜,最弱保证

```rust
counter.fetch_add(1, Ordering::Relaxed);
```

只保证这一次 fetch_add 是原子的(不会丢更新),不保证和其他变量 / 操作的顺序。

适合:**统计计数器**(我只关心总数对不对,不关心谁先谁后)。

#### Release / Acquire:发布订阅

```rust
// 线程 A:写数据,然后设 flag
data.write(...);
flag.store(true, Ordering::Release);

// 线程 B:读 flag,如果 true 则读数据
if flag.load(Ordering::Acquire) {
    let d = data.read();
    // d 一定是线程 A 写的值
}
```

`Release.store` 保证:**之前的所有写**(data.write)在所有看到这个 flag=true 的线程里都可见。
`Acquire.load` 保证:**之后的所有读**(data.read)看到 Release 之前的写。

#### SeqCst:全局顺序

```rust
flag.store(true, Ordering::SeqCst);
```

比 Release / Acquire 更强:**所有 SeqCst 操作有一个全局顺序**。

适合:**多个变量需要协调的复杂协议**(如 Dekker 算法、双线程协议)。

代价:比 Acquire / Release 慢,比 Relaxed 慢得多。

#### AcqRel:RMW 操作

`fetch_add(val, Ordering::AcqRel)` 既是 Acquire(看到别人的 Release),又是 Release(让别人看到我的写)。

适合:RMW(read-modify-write)操作。

### 2.7 atomic 的代价

atomic 不是免费的:

- `Relaxed load`:1 周期(就是普通 load)
- `Relaxed store`:1 周期
- `Release store`:1 周期 + 内存屏障(几周期)
- `Acquire load`:1 周期 + 内存屏障
- `SeqCst`:几周期到几十周期(可能触发 cache 同步)
- `lock cmpxchg`(CAS):20-50 周期

CAS 比 mutex 便宜很多(mutex ~几百周期),但比简单 atomic op 贵。

### 2.8 ABA 问题

经典 lock-free bug:

```rust
// 线程 1
let v = atomic.load();  // v = A
// ... 此时被抢占 ...
// 线程 2 把 A 改成 B,又改回 A
// 线程 1 醒来
atomic.compare_exchange(A, C);  // 成功!但 B 中间的状态丢了
```

线程 1 以为"atomic 没变过",其实中间变了 A→B→A。

**解药**:用"带版本号"的 atomic(叫 `AtomicU64` 装 ptr + version)。或者用 `crossbeam_epoch`(基于 epoch 的内存回收)。

ABA 是 lock-free 编程的经典陷阱。Day 125-126 写 work queue 时要注意。

### 2.9 atomic 的对齐要求

`AtomicI32` 必须是 4 字节对齐。即使 i32 在 Rust 里只要求 4 字节对齐(基本上就是 i32 的自然对齐),atomic 也强制要求对齐,因为某些 CPU 要求 atomic 操作的地址对齐(否则触发对齐异常)。

```rust
// 错误!
let bytes: [u8; 4] = [0; 4];
let atomic = unsafe {
    let p = bytes.as_ptr() as *const AtomicI32;
    &*p
};
// 这里 p 可能不是 4 字节对齐,atomic 操作可能 crash

// 正确
#[repr(align(4))]
struct Aligned4([u8; 4]);
let a = Aligned4([0; 4]);
// 现在 a 是 4 字节对齐
```

Rust 的 `AtomicI32` 编译期检查对齐,所以你不会真的写出上面的 bug。但 FFI 时要注意。

### 3.3 · 🦀 Rust 生态视角

#### Send + Sync trait

Rust 的 atomic 都自动 `Send + Sync`(可跨线程共享)。但**普通 `Cell<T>` 不是 Sync**(因为非 atomic,跨线程会 data race)。

```rust
use std::cell::Cell;

let c = Cell::new(0);
// std::thread::spawn(move || { c.set(1); });  // 编译错误!Cell 不是 Sync
```

这是 Rust 的" fearless concurrency"——编译期就阻止 data race。

#### `AtomicPtr<T>`

无锁数据结构的基石。指向堆数据的原子指针。

```rust
use std::sync::atomic::{AtomicPtr, Ordering};

let head = AtomicPtr::new(std::ptr::null_mut());

// push 一个节点到 lock-free stack
let node = Box::into_raw(Box::new(Node { next: std::ptr::null(), data: 42 }));
loop {
    let current = head.load(Ordering::Acquire);
    unsafe { (*node).next = current; }
    if head.compare_exchange_weak(current, node, Ordering::Release, Ordering::Relaxed).is_ok() {
        break;
    }
}
```

#### `AtomicUsize` 作 lock-free queue 的 index

```rust
use std::sync::atomic::{AtomicUsize, Ordering};

struct Queue {
    buffer: Vec<i32>,  // 固定大小环形 buffer
    head: AtomicUsize,
    tail: AtomicUsize,
}
```

这是 Day 126 work queue 的核心。

### Lv2 · 动手实践

**题**:用 atomic 实现一个无锁的"单生产者单消费者环形队列"。要求:

- `push(val)`:生产者调用
- `pop() -> Option<T>`:消费者调用
- 单线程生产,单线程消费,队列容量固定
- 用 `AtomicUsize` 作 head/tail

完成标准:多线程测试,1M 条数据正确传递。

**参考解答**:

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

const SIZE: usize = 1024;

struct SPSCQueue<T: Copy + Default> {
    buffer: Box<[T; SIZE]>,
    head: AtomicUsize,  // consumer 读
    tail: AtomicUsize,  // producer 写
}

impl<T: Copy + Default> SPSCQueue<T> {
    fn new() -> Self {
        let buffer = Box::new([T::default(); SIZE]);  // 注意:大型 array 可能 stack overflow,实际用 Vec
        Self {
            buffer,
            head: AtomicUsize::new(0),
            tail: AtomicUsize::new(0),
        }
    }

    fn push(&self, val: T) -> bool {
        let tail = self.tail.load(Ordering::Relaxed);
        let next_tail = (tail + 1) % SIZE;
        if next_tail == self.head.load(Ordering::Acquire) {
            return false;  // 队列满
        }
        unsafe {
            *(&self.buffer[tail] as *const _ as *mut T) = val;
        }
        self.tail.store(next_tail, Ordering::Release);
        true
    }

    fn pop(&self) -> Option<T> {
        let head = self.head.load(Ordering::Relaxed);
        if head == self.tail.load(Ordering::Acquire) {
            return None;  // 队列空
        }
        let val = self.buffer[head];
        self.head.store((head + 1) % SIZE, Ordering::Release);
        Some(val)
    }
}
```

注意:大型 `[T; SIZE]` 实际不能用 `Box::new` 直接初始化(stack overflow),要用 `vec![T::default(); SIZE].into_boxed_slice()` 然后 transmute 或 unsafe 构造。这里简化了。

## 8 · Rust / Arch 落地代码

### Rust:完整 atomic demo

```rust
use std::sync::atomic::{AtomicI32, AtomicBool, Ordering};
use std::sync::Arc;
use std::thread;

fn main() {
    // Relaxed 计数器
    let counter = Arc::new(AtomicI32::new(0));
    let handles: Vec<_> = (0..8).map(|_| {
        let c = counter.clone();
        thread::spawn(move || {
            for _ in 0..1_000_000 {
                c.fetch_add(1, Ordering::Relaxed);
            }
        })
    }).collect();
    for h in handles { h.join().unwrap(); }
    println!("Counter: {}", counter.load(Ordering::Relaxed));
    // 应该 8000000

    // Release / Acquire 发布订阅
    let data = Arc::new((AtomicI32::new(0), AtomicBool::new(false)));
    let (d, ready) = &*data;
    let data2 = data.clone();
    let t = thread::spawn(move || {
        let (d, ready) = &*data2;
        while !ready.load(Ordering::Acquire) {
            std::hint::spin_loop();
        }
        println!("Reader sees: {}", d.load(Ordering::Relaxed));
    });
    d.store(42, Ordering::Relaxed);
    ready.store(true, Ordering::Release);
    t.join().unwrap();

    // CAS
    let a = AtomicI32::new(1);
    match a.compare_exchange(1, 100, Ordering::SeqCst, Ordering::SeqCst) {
        Ok(_) => println!("CAS succeeded: a = {}", a.load(Ordering::Relaxed)),
        Err(_) => println!("CAS failed"),
    }
}
```

## 10 · 深度推导:从硬件到 Rust atomic

今天 Casey 教的是 atomic。但 Rust 的 `AtomicI32` 背后有一条从晶体管到类型系统的长链路。这一节走通这条链路——你才真正懂为什么 `fetch_add(1, Ordering::Release)` 不会出错。

### 10.1 第一层:硬件为什么需要"原子"指令?

CPU 一个指令"看起来原子",但内部其实是多 cycle 操作。比如 `i += 1` 在 x86 上是 3 步:

```
1. mov eax, [mem]   ; load
2. add eax, 1       ; increment
3. mov [mem], eax   ; store
```

每个步骤单独成原子,但**3 步组合不是**——另一个线程可以在 step 1 和 step 2 之间改 `[mem]`,你的 step 3 写回时覆盖了对方的修改。这就是 **data race**。

x86 提供了一个修复:`lock` 前缀。给指令加 `lock`,CPU 保证"该指令整体原子":

```asm
lock add [mem], 1   ; 整个 read-modify-write 原子
```

`lock` 实现机制:CPU 锁定 cache line(如果是 cache 命中)或锁总线(如果未命中),保证别的 core 不能中间插入。这是 x86 atomic 的硬件基础。

ARM 没有这种"前缀"——它用 `ldxr/stxr`(load-exclusive / store-exclusive)对:

```asm
loop:
    ldxr w0, [x1]      ; exclusive load
    add  w0, w0, #1
    stxr w2, w0, [x1]  ; exclusive store(返回 0 表示成功)
    cbnz w2, loop       ; 失败重试
```

ARM 的思路是"乐观并发"——先试着 load-store,失败就重试。比 x86 lock 更精细(cache line 不必锁),但代码更复杂。

Rust 的 `fetch_add` 在 x86 编译成 `lock xadd`,在 ARM 编译成 ldxr/stxr 循环。**一份源码,两个 ISA 的最优实现**。

### 10.2 第二层:5 种 Ordering 推导

`fetch_add(1, Ordering::?)` 的 `?` 可以是 5 种。为什么需要 5 种?因为不同的内存序语义适用于不同场景。

#### Relaxed:不保证顺序,只保证原子

```rust
counter.fetch_add(1, Ordering::Relaxed);
```

只承诺"这次加 1 是原子的",不承诺"加 1 之前/之后的内存读写顺序"。适合**纯计数器**——你只关心总数,不关心其他数据的可见性。

性能:relaxed 不插任何 fence,在 x86 上几乎免费(因为 x86 TSO 模型本来就强)。在 ARM 上需要 `dmb ishld` 类 barrier 部分情况下避免。

#### Release:写发布

```rust
data.store(42, Ordering::Release);
flag.store(true, Ordering::Release);
```

承诺:**这次 store 之前的所有读写,在别人看到这次 store 之前都完成**。等价于"我把数据准备好了,告诉别人可以读"。

适合"发布数据"——你写完 data(普通 store),然后发布 flag(Release),别的线程看到 flag=true 后,一定能看到 data=42。

#### Acquire:读获取

```rust
while !flag.load(Ordering::Acquire) { spin() }
println!("{}", data.load(Ordering::Relaxed));
```

承诺:**这次 load 之后的所有读写,在这次 load 之前不能 reorder**。等价于"我看到 flag=true,那么后面读到的 data 是最新的"。

Release-Acquire 是一对:producer 用 Release 写 flag,consumer 用 Acquire 读 flag,两者之间形成 happens-before 关系。这是 lock-free 编程最常用的 ordering。

#### AcqRel:同时 Acquire + Release

`fetch_add` 这种"读改写"操作可能既要 acquire(读旧值)又要 release(写新值)。AcqRel = Acquire + Release。

适合"RMW 操作且这个 RMW 是 publish/consume 关键点"。

#### SeqCst:全局顺序

最强的 ordering。除了 Acquire + Release,还保证**所有 SeqCst 操作有全局一致顺序**。

性能:在 x86 上,SeqCst store 是 `xchg`(隐式 mfence),比 Release 的普通 store 慢。在 ARM 上 SeqCst 要 `dmb ish` 重 fence,慢得多。

适合"需要全局事件顺序"的场景,比如多线程 signales / flags。但**90% 的代码不需要 SeqCst**,Release/Acquire 够。

### 10.3 第三层:Happens-before 关系

内存序的本质是建立 **happens-before** 关系:线程 A 的某些操作"在前面",线程 B 的某些操作"在后面",A 的修改 B 能看到。

具体规则:

```
线程 A:
    data = 42;                       // 普通写
    flag.store(true, Ordering::Release);  // Release 屏障

线程 B:
    while !flag.load(Ordering::Acquire) {}  // Acquire 屏障
    print(data);  // 看到 42
```

Release-Acquire 配对时:**A 中 Release 之前的所有写,B 中 Acquire 之后都能看到**。

这是为什么"读 flag 必须 Acquire"——否则编译器/CPU 可能把"读 data"reorder 到"读 flag"之前,你读到的 data 可能是旧值(0 而不是 42)。

#### 没有 happens-before 的灾难

```rust
// 错误代码
data.store(42, Ordering::Relaxed);     // 错!应该是 Release
flag.store(true, Ordering::Relaxed);

// 另一线程
while !flag.load(Ordering::Relaxed) {}
println!("{}", data.load(Ordering::Relaxed));  // 可能是 0!
```

CPU 可能"重排"data 写和 flag 写,即便源码顺序 data 在前。Relaxed 不阻止重排。

x86 TSO 模型几乎不重排 store,所以这段代码在 x86 上"碰巧"工作。但**ARM 上会失败**——ARM 弱模型允许重排。你的代码在 x86 测试通过,移植到 ARM / Apple Silicon 偶发崩溃,这是工业级"跨平台并发 bug"的典型来源。

### 10.4 第四层:ABA 问题

经典 lock-free 陷阱。考虑 lock-free stack:

```rust
fn push(node: Node) {
    loop {
        let head = self.head.load(Acquire);
        node.next = head;
        if self.head.compare_exchange(head, node, Release, Relaxed).is_ok() {
            break;
        }
    }
}

fn pop() -> Node {
    loop {
        let head = self.head.load(Acquire);
        let next = unsafe { (*head).next };
        if self.head.compare_exchange(head, next, Release, Relaxed).is_ok() {
            return *head;
        }
    }
}
```

ABA 场景:

1. 线程 A 读 head = X,准备 pop
2. 线程 A 看见 X.next = Y
3. **线程 B** pop X,pop Y,然后 push X 回来(head 还是 X)
4. 线程 A 的 CAS(head==X) 成功(因为 head 还是 X)
5. 线程 A 把 head 设为 Y,但 Y 已经被 freed → **use-after-free**

ABA 是 CAS-based 算法的根本问题。修复:

- **Tagged pointer**:在指针高位塞 version counter,每次修改 version++,CAS 比较 pointer + version
- **Hazard pointer**:延迟 free,等所有 reader 离开
- **Epoch-based reclamation**:批量 GC,所有线程都过了某个 epoch 才 free

Rust 的 `crossbeam_epoch` 实现 epoch-based,`arc-swap` 实现 tagged。这是 lock-free 编程的高阶话题。

### 10.5 第五层:Rust 类型系统的角色

Rust 用 Send / Sync trait 把并发安全做进类型系统:

- `Send`:类型可以跨线程转移所有权
- `Sync`:类型可以跨线程共享引用(&T)

`AtomicI32` 自动 Sync + Send。`Cell<i32>` 不是 Sync(因为它的内部可变性靠"单线程假设")。`Rc<T>` 不是 Send(引用计数不是 atomic,跨线程计数会出错)。

编译期检查:

```rust
let rc = Rc::new(0);
thread::spawn(move || {  // 编译错误!Rc 不是 Send
    println!("{}", *rc);
});
```

编译器直接拒绝。这就是 Rust 的 "fearless concurrency"——你在编译期就排除了 80% 的并发 bug。Day 122-125 你写的代码全靠这套类型系统保护。

## 11 · 一个完整可跑的 lock-free SPSC 队列

把今天学的综合成可跑代码。SPSC = Single Producer Single Consumer,是最简单的 lock-free 队列。

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;

const SIZE: usize = 1024;
const MASK: usize = SIZE - 1;  // SIZE 必须是 2 的幂

struct SPSCQueue {
    buffer: Box<[u64; SIZE]>,
    head: AtomicUsize,  // consumer 写
    tail: AtomicUsize,  // producer 写
}

impl SPSCQueue {
    fn new() -> Self {
        // 用 Vec 然后 leak 成 Box<[u64; SIZE]>,避免 stack overflow
        let v: Vec<u64> = vec![0; SIZE];
        let buffer = unsafe { Box::from_raw(v.leak().as_mut_ptr() as *mut [u64; SIZE]) };
        Self {
            buffer,
            head: AtomicUsize::new(0),
            tail: AtomicUsize::new(0),
        }
    }

    fn push(&self, val: u64) -> Result<(), u64> {
        let tail = self.tail.load(Ordering::Relaxed);
        let next_tail = tail.wrapping_add(1);
        // Acquire head,看是否有空间
        if next_tail.wrapping_sub(self.head.load(Ordering::Acquire)) > SIZE {
            return Err(val);  // 满了
        }
        unsafe {
            *(&self.buffer[tail & MASK] as *const _ as *mut u64) = val;
        }
        // Release tail,让 consumer 看到新数据
        self.tail.store(next_tail, Ordering::Release);
        Ok(())
    }

    fn pop(&self) -> Option<u64> {
        let head = self.head.load(Ordering::Relaxed);
        // Acquire tail,看是否有数据
        if head == self.tail.load(Ordering::Acquire) {
            return None;  // 空了
        }
        let val = unsafe { *(&self.buffer[head & MASK] as *const _ as *const u64) };
        // Release head,让 producer 看到空间
        self.head.store(head.wrapping_add(1), Ordering::Release);
        Some(val)
    }
}

fn main() {
    let q = Arc::new(SPSCQueue::new());
    let q2 = Arc::clone(&q);

    let producer = thread::spawn(move || {
        for i in 0..1_000_000u64 {
            while q2.push(i).is_err() {
                std::hint::spin_loop();
            }
        }
    });

    let q3 = Arc::clone(&q);
    let consumer = thread::spawn(move || {
        let mut sum = 0u64;
        let mut count = 0;
        while count < 1_000_000 {
            if let Some(v) = q3.pop() {
                sum += v;
                count += 1;
            } else {
                std::hint::spin_loop();
            }
        }
        println!("Consumer sum = {}, expected = {}", sum, 499999500000u64);
    });

    producer.join().unwrap();
    consumer.join().unwrap();
}
```

跑起来:

```bash
RUSTFLAGS="-C opt-level=3" cargo run --release
# 输出:Consumer sum = 499999500000, expected = 499999500000
```

注意几个关键点:

1. **head 由 consumer 独占写,producer 只读**——单写者,无需 CAS,普通 store 就够。
2. **tail 由 producer 独占写,consumer 只读**——同样无需 CAS。
3. **Acquire-Release 配对**:producer Release 写 tail,consumer Acquire 读 tail。建立 happens-before:producer 的 `buffer[tail] = val` 在 consumer 的 `buffer[head]` 读之前完成。
4. **Relaxed 用于"自己的"变量**:producer 写自己的 tail 用 Relaxed(不需要 happens-before),读 consumer 的 head 用 Acquire。

这是 lock-free SPSC 的教科书实现。Linux kernel 的 `kfifo`、DPDK 的 rte_ring 都是类似设计。
