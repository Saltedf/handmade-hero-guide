
# Day 133 · 资产初步组织

> Day 132 实现了 asset streaming,但资产还没"类型化"——所有资产都当 `Vec<u8>` 看。Day 133-137 五天逐步把"裸字节"演化成有类型、有 tag、可查询的资产系统。今天第一步:把资产按类型分组。

## 0 · 为什么要有这一天

Day 132 你有一个 `HashMap<AssetId, AssetSlot>`,每个 slot 存 `Vec<u8>`。这种"啥都装"的容器有个问题:

- 想要一张 bitmap,你必须从 HashMap 拿 AssetSlot,然后**手动**把 `Vec<u8>` 解析成 bitmap(宽度、高度、像素数据)
- 想要一个 sound,同样手动解析
- 不同资产的解析逻辑混在调用方代码里,重复且易错
- 没有类型安全——你可能把一个 sound 的 AssetId 传给需要 bitmap 的函数,运行时才崩

**今天的核心**:把资产按类型分组。Bitmap 一组,Sound 一组,Font 一组。每组独立管理,有自己的解析逻辑。AssetId 类型化(`BitmapId`、`SoundId`),编译期防止混用。

这是工程化资产管理的基础。后面 Day 134-137 会在分组上加"映射""tag""周期匹配",逐步演化成完整的资产系统。

心理锚点:做完今天你能(1)用 newtype 在 Rust 里实现"编译期防混用"的 AssetId;(2)理解为什么"按类型分组"比"全 HashMap"好;(3)在你的引擎里给每种资产类型建一个独立的存储。

## 1 · Casey 今天做了什么

Casey 把 Day 132 的 `HashMap<AssetId, AssetSlot>` 重构:

1. 定义 `AssetType` enum(Bitmap / Sound / Font / ...)
2. 给每种类型建独立数组:`Vec<Bitmap>`、`Vec<Sound>`、`Vec<Font>`
3. AssetId 变成 typed newtype:`BitmapId(u32)`、`SoundId(u32)`、`FontId(u32)`
4. 类型化查询:`get_bitmap(BitmapId) -> &Bitmap`、`get_sound(SoundId) -> &Sound`
5. 加载时根据资产类型分派到对应解析器

这一天的核心:**把"无类型容器"演化为"按类型分组容器"**,为后面的 tag 系统铺路。

## 2 · 心智模型

### 类比:杂乱抽屉 vs 分类收纳盒

**Day 132 的 HashMap** 像杂乱抽屉:什么都往里塞,要找一把螺丝刀得翻遍所有东西。

**Day 133 的类型化分组** 像分类收纳盒:每个盒子放一类(螺丝刀一盒、扳手一盒、钳子一盒)。要螺丝刀直接去螺丝刀盒,不用翻其他。

类型化让"找东西"从 O(N) 变成 O(1),且不会找错。

### 严谨原理:newtype 模式

Rust 的 newtype 是零成本抽象:

```rust
struct BitmapId(u32);
struct SoundId(u32);
```

这两个类型编译后都是 `u32`(零额外开销),但**编译器认为它们是不同类型**。你无法把 `SoundId` 当 `BitmapId` 用——编译器报错:

```rust
fn draw_bitmap(id: BitmapId) { ... }
let s = SoundId(5);
draw_bitmap(s);  // 编译错误!expected BitmapId, found SoundId
```

这就是"编译期防混用"。Casey 在 C 里用 typedef,但 typedef 只换名字不换类型,不防混用。Rust 的 newtype 真换类型。

### 类型化资产管理

```rust
struct AssetStore {
    bitmaps: Vec<Bitmap>,
    sounds: Vec<Sound>,
    fonts: Vec<Font>,
}

struct Bitmap {
    width: u32,
    height: u32,
    pixels: Vec<u32>,
}

struct Sound {
    samples: Vec<f32>,
    sample_rate: u32,
}

struct Font {
    glyphs: HashMap<char, Glyph>,
}

#[derive(Copy, Clone)]
struct BitmapId(u32);  // index into bitmaps

impl AssetStore {
    fn get_bitmap(&self, id: BitmapId) -> &Bitmap {
        &self.bitmaps[id.0 as usize]
    }
    fn get_sound(&self, id: SoundId) -> &Sound {
        &self.sounds[id.0 as usize]
    }
}
```

API 类型安全:`get_bitmap(BitmapId)` 只接 BitmapId。游戏代码 push 一个 bitmap 到 store,拿到 BitmapId,后续用这个 id 取回 bitmap——绝不可能拿到 sound。

### 分组的好处

| 维度 | HashMap<AssetId, Vec<u8>> | 分组 Vec<Bitmap> / Vec<Sound> |
|---|---|---|
| 类型安全 | 无 | ✅ 编译期 |
| 内存局部性 | 所有资产挤一起 | 同类型连续,cache 友好 |
| 查询速度 | HashMap O(1) | 索引 O(1) |
| 内存开销 | HashMap 每元素额外 32-64 字节 | Vec 仅数组 |
| 扩展性 | 加新类型要改 HashMap | 加新类型加新 Vec |

类型化分组全面胜出,但有一个**潜在缺点**:如果资产数量极多(几百万),每个 Vec 单独存可能造成内存碎片。解决办法:把所有资产合并到一个大 Vec,用 `range` 索引(每个类型知道自己的 range)。Casey 不做,因为资产数量在几千级别,Vec 足够。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发里"类型化资产"是标配:

- **Unreal Engine**:`UTexture2D`、`USoundWave`、`UStaticMesh`,每个类型独立 class
- **Unity**:`Texture2D`、`AudioClip`、`Mesh`,C# 类型系统
- **Bevy**:`Handle<Image>`、`Handle<AudioSource>`、`Handle<Mesh>`,Rust generic

每个引擎都把资产按类型分。Casey Day 133 开始走这条。

游戏开发圈的另一个常见做法:**ECS 风格的资产管理**。每个资产是一个 entity,附加多个 component(Texture component、Sound component)。Bevy 在 ECS 基础上加了 AssetStore,本质上还是类型化分组。

### 3.2 · 🦀 Rust 生态视角

Rust 表达类型化资产有几种方式:

#### 流派 1:newtype + Vec(推荐教学)

```rust
#[derive(Copy, Clone)]
struct BitmapId(u32);
struct Store { bitmaps: Vec<Bitmap> }
impl Store {
    fn get(&self, id: BitmapId) -> &Bitmap { &self.bitmaps[id.0 as usize] }
}
```

简单,编译期防混用。缺点:删除资产后 index 失效(要用 generation index 解决)。

#### 流派 2:slotmap(代际索引)

```toml
[dependencies]
slotmap = "1"
```

```rust
use slotmap::{SlotMap, new_key_type};
new_key_type! { struct BitmapKey; }
let mut sm: SlotMap<BitmapKey, Bitmap> = SlotMap::with_key();
let k = sm.insert(bmp);
sm.remove(k);  // 之后用 k 取会 None,不会拿到新插入的资产
```

`slotmap` crate 提供代际索引——删除后 index 复用,但旧 index 失效(不会错误地取到新资产)。工业级推荐。

#### 流派 3:typed-index-collections

```toml
[dependencies]
typed-index-collections = "0.1"
```

类似 newtype + Vec,但提供 `TiVec` 类型安全的索引容器。

#### 流派 4:Bevy 的 `Handle<T>`

```rust
type Handle<T> = Arc<AssetCell<T>>;  // 简化
let handle: Handle<Image> = asset_server.load("sword.png");
```

generic,类型安全。每个 T 独立存储。

Casey 教学版用流派 1。生产代码流派 2(slotmap)或流派 4(Bevy Handle)。

### 3.3 · 数据布局考虑

类型化分组让"同类型资产连续存储"。这对性能有利:

```rust
// 主线程渲染时遍历所有 bitmap
for bmp in &store.bitmaps {
    if bmp.is_visible() {
        render(bmp);
    }
}
```

bitmaps 连续存储,cache line 友好,SIMD 友好。如果用 `HashMap<AssetId, Asset>` 装所有类型,遍历时类型混乱,cache 命中率下降。

数据导向设计(Mike Acton)第一条:**数据布局决定性能**。类型化分组是这条原则的应用。

### 3.4 · 类型分派

资产加载时根据类型分派:

```rust
enum AssetType { Bitmap, Sound, Font }

fn load_asset(path: &str, ty: AssetType) -> Result<(), Error> {
    let raw = std::fs::read(path)?;
    match ty {
        AssetType::Bitmap => {
            let bmp = parse_bitmap(&raw)?;
            store.bitmaps.push(bmp);
        }
        AssetType::Sound => {
            let snd = parse_sound(&raw)?;
            store.sounds.push(snd);
        }
        AssetType::Font => {
            let fnt = parse_font(&raw)?;
            store.fonts.push(fnt);
        }
    }
    Ok(())
}
```

`match` 强制处理所有类型,加新类型时编译器报错让你补。这是 enum 的好处。

## 5 · 对照与变奏

### newtype 在不同语言

| 语言 | newtype 实现 |
|---|---|
| Rust | `struct BitmapId(u32);` 真换类型 |
| C | `typedef u32 BitmapId;` 仅换名,不防混用 |
| C++ | `enum class BitmapId : u32 {};` 强类型 enum |
| Haskell | `newtype BitmapId = BitmapId Int` 真换类型 |
| OCaml | `type bitmap_id = int` 不防混用;抽象类型才防 |

Rust 和 Haskell 的 newtype 最优雅。Casey 在 C 用 typedef,在 Rust 翻译时升级成 newtype。

### 历史演化

- **1970s**:C typedef,不防混用
- **1990s**:C++ enum class,部分防混用
- **2000s**:Haskell newtype,Rust newtype,真正类型安全
- **2010s**:游戏引擎(Bevy、Unreal)内置类型化资产

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:

1. Rust newtype 和 C typedef 都给类型起别名,差别是什么?各自能不能防混用?
2. 为什么把 bitmaps 和 sounds 分两个 Vec 存,而不是 `Vec<Asset>` 装 enum?
3. 用 `AssetType` enum 分派加载,加新资产类型时编译器会怎么帮你?
4. 类型化分组的一个潜在缺点是什么?什么时候不用它?

**参考解答**:
1. C typedef 仅给现有类型起别名,`typedef u32 BitmapId;` 后 BitmapId 和 u32 完全等价,可以互相赋值。Rust newtype `struct BitmapId(u32);` 创建了新类型,BitmapId 和 u32 不兼容,必须显式 `.0` 取出内部值。typedef 不防混用,newtype 防混用。
2. 分 Vec 的好处:(a)同类型连续存储,cache 友好;(b)API 类型安全(`get(BitmapId) -> &Bitmap`);(c)加新类型加新 Vec,扩展性好。`Vec<Asset>` 装 enum 的问题:(a)enum 大小 = 最大 variant,小 variant 浪费空间;(b)取出来要 match,运行时分派。
3. enum 的 match 强制处理所有 variant。加新 variant 时,所有 match 编译报错让你补。这是"exhaustive matching"的好处。
4. 缺点:类型多时 Vec 数量多,代码膨胀。如果资产类型在 100 种以上,可以用 `HashMap<TypeId, Box<dyn Asset>>` 配合 trait object。HH 资产类型少(< 10),分组好用。

### Lv2 · 动手实践

**题**:Rust 实现类型化资产存储。

要求:
1. newtype:`BitmapId(u32)`、`SoundId(u32)`
2. `Bitmap { width: u32, height: u32, pixels: Vec<u32> }`
3. `Sound { samples: Vec<f32>, sample_rate: u32 }`
4. `AssetStore { bitmaps: Vec<Bitmap>, sounds: Vec<Sound> }`
5. `add_bitmap(&mut self, bmp) -> BitmapId` / `get_bitmap(&self, id) -> &Bitmap`
6. 同 sound
7. main:加 2 个 bitmap + 1 个 sound,验证 get_bitmap 不能传 SoundId(编译错)

完成标准:`cargo run` 打印资产信息,且 `get_bitmap(SoundId(0))` 编译失败(注释掉验证)。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, PartialEq, Eq)]
struct BitmapId(u32);

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
struct SoundId(u32);

struct Bitmap {
    width: u32,
    height: u32,
    pixels: Vec<u32>,
}

struct Sound {
    samples: Vec<f32>,
    sample_rate: u32,
}

struct AssetStore {
    bitmaps: Vec<Bitmap>,
    sounds: Vec<Sound>,
}

impl AssetStore {
    fn new() -> Self { Self { bitmaps: Vec::new(), sounds: Vec::new() } }

    fn add_bitmap(&mut self, bmp: Bitmap) -> BitmapId {
        let id = BitmapId(self.bitmaps.len() as u32);
        self.bitmaps.push(bmp);
        id
    }
    fn get_bitmap(&self, id: BitmapId) -> &Bitmap {
        &self.bitmaps[id.0 as usize]
    }
    fn add_sound(&mut self, snd: Sound) -> SoundId {
        let id = SoundId(self.sounds.len() as u32);
        self.sounds.push(snd);
        id
    }
    fn get_sound(&self, id: SoundId) -> &Sound {
        &self.sounds[id.0 as usize]
    }
}

fn main() {
    let mut store = AssetStore::new();

    let sword_bmp = Bitmap {
        width: 64, height: 64,
        pixels: vec![0xff0000ff; 64 * 64],  // 红色 64x64
    };
    let tree_bmp = Bitmap {
        width: 32, height: 32,
        pixels: vec![0x00ff00ff; 32 * 32],  // 绿色 32x32
    };
    let sword_id = store.add_bitmap(sword_bmp);
    let tree_id = store.add_bitmap(tree_bmp);
    println!("Bitmaps: sword={:?}, tree={:?}", sword_id, tree_id);

    let bgm = Sound {
        samples: vec![0.5; 44100],  // 1 秒 0.5 振幅
        sample_rate: 44100,
    };
    let bgm_id = store.add_sound(bgm);
    println!("Sound: bgm={:?}", bgm_id);

    // 取资产
    let bmp = store.get_bitmap(sword_id);
    println!("Sword bitmap: {}x{}, first pixel = 0x{:08x}", bmp.width, bmp.height, bmp.pixels[0]);

    let snd = store.get_sound(bgm_id);
    println!("BGM: {} samples at {} Hz", snd.samples.len(), snd.sample_rate);

    // 编译期验证(取消注释会编译错):
    // let _ = store.get_bitmap(bgm_id);
    // error[E0308]: mismatched types, expected BitmapId, found SoundId
}
```

## 8 · Rust / Arch 落地代码

完整 Rust 项目(见 Lv2)+ benchmark:

```rust
// 在 Lv2 基础上加 benchmark
use std::time::Instant;
use std::collections::HashMap;

// 对照:HashMap<AssetId, Box<dyn std::any::Any>>
fn bench_typed_vs_hashmap() {
    let n = 10_000;
    // typed
    let mut store = AssetStore::new();
    let start = Instant::now();
    for i in 0..n {
        store.add_bitmap(Bitmap {
            width: 1, height: 1, pixels: vec![i as u32],
        });
    }
    for i in 0..n {
        std::hint::black_box(store.get_bitmap(BitmapId(i as u32)));
    }
    let typed_t = start.elapsed();

    // hashmap
    let mut hm: HashMap<u32, Bitmap> = HashMap::with_capacity(n);
    let start = Instant::now();
    for i in 0..n {
        hm.insert(i as u32, Bitmap { width: 1, height: 1, pixels: vec![i as u32] });
    }
    for i in 0..n {
        std::hint::black_box(hm.get(&(i as u32)).unwrap());
    }
    let hm_t = start.elapsed();

    println!("Typed Vec: {} us", typed_t.as_micros());
    println!("HashMap:   {} us", hm_t.as_micros());
    println!("Speedup:   {:.2}x", hm_t.as_secs_f64() / typed_t.as_secs_f64());
}
```

**预期输出**:
```
Typed Vec: 250 us
HashMap:   1800 us
Speedup:   7.20x
```

类型化 Vec 比 HashMap 快 5-10 倍(无 hash 计算,直接索引)。

## 10 · 深度推导:从 Vec<u8> 到 typed asset system

今天 Casey 把"裸字节"演化成"有类型的资产"。这不是简单的"加个 enum"——背后是一整套数据导向设计的考量。这一节走通这个演化。

### 10.1 起点:Day 132 的 Vec<u8>

Day 132 你有一个简单的 asset storage:

```rust
struct AssetStorage {
    slots: HashMap<AssetId, AssetSlot>,
}

struct AssetSlot {
    data: Vec<u8>,
    state: AssetState,  // Loading / Loaded / Failed
}
```

听起来够用,但很快遇到问题:

**问题 1:每次用都要 parse**。你加载一个 sprite,要 `parse_png(&slot.data)`。每次渲染都 parse,白浪费 CPU。要缓存解析结果——但缓存什么类型?

**问题 2:类型不安全**。`AssetId` 是 u32,你可以 `get_texture(id)` 但 id 实际上是 sound,编译器不阻止。运行时 panic。

**问题 3:Release 时无法 drop**。`Vec<u8>` 不知道里面是 PNG / WAV / TGA / OBJ,如何 drop?对所有 asset 一视同仁(直接 free buffer),但你无法调用类型的 Drop impl。

### 10.2 第一层演化:枚举区分类型

```rust
enum AssetData {
    Texture(RgbaImage),
    Sound(WavData),
    Mesh(MeshData),
    Bitmap(BitmapData),
    Raw(Vec<u8>),
}

struct AssetSlot {
    data: AssetData,
    state: AssetState,
}
```

类型安全 + 自动 drop。但有个问题:**enum 占用 = max(variants)**。Texture 可能 1 KB(W * H * 4 字节的小图),Sound 可能 1 MB(60s 音频)。每个 slot 至少占 1 MB(因为 Sound variant)。

加载 1000 个 texture = 1000 slot × 1 MB = 1 GB,即便 texture 总共才 500 KB。**enum 体积爆炸**。

### 10.3 第二层演化:Box<enum> 缩小

```rust
struct AssetSlot {
    data: Box<AssetData>,
    state: AssetState,
}
```

Box<AssetData> 只占指针大小(8 字节),实际数据在堆。1000 slot × 8 字节 = 8 KB,合理。

但 Box 带来 **indirection**——每次访问要 deref。性能略损。

### 10.4 第三层演化:分类型存储(SoA)

回到本日的核心思路:**每种类型一个 HashMap**。

```rust
struct AssetStorage {
    textures: HashMap<AssetId, RgbaImage>,
    sounds: HashMap<AssetId, WavData>,
    meshes: HashMap<AssetId, MeshData>,
    metadata: HashMap<AssetId, AssetMeta>,  // 所有 id 的元信息
}
```

好处:

- **每个 HashMap 紧凑**:texture 全挨在一起,cache friendly。
- **类型 100% 安全**:你不可能把 sound id 传给 `get_texture`,API 签名拒绝。
- **没有 enum 浪费**:texture 在 textures HashMap 里就是 RgbaImage,不多占字节。

代价:

- **API 多**:每种类型一个 getter。
- **跨类型操作麻烦**:"unload 所有 asset" 要遍历每个 HashMap。

工业级引擎(Bevy / Unity / Unreal)都用分类型存储。

### 10.5 第四层演化:typed AssetId(类型安全的 ID)

普通 `AssetId(u32)` 还是不够安全——你可以混用。Rust 用 newtype pattern:

```rust
pub struct TextureId(u32);
pub struct SoundId(u32);
pub struct MeshId(u32);

impl AssetStorage {
    fn get_texture(&self, id: TextureId) -> &RgbaImage { ... }
    fn get_sound(&self, id: SoundId) -> &WavData { ... }
}
```

现在 `get_texture(sound_id)` 编译错误,因为 TextureId 和 SoundId 是不同类型。**编译期 100% 类型安全**。

更进一步:用 generational index(slotmap 模式):

```rust
pub struct TextureId(u32, u32);  // (index, generation)
```

generation 让"已 free 的 id"无法被错误使用——free 一个 slot 后 generation++,旧 id 的 generation 不匹配,get 返回 None。

这是 slotmap / heapless / bevy_ecs 的 Entity id 的标准设计。

### 10.6 完整代码骨架

```rust
use std::collections::HashMap;
use std::path::Path;

pub struct TextureId(pub u32);
pub struct SoundId(pub u32);
pub struct MeshId(pub u32);

pub struct RgbaImage {
    pub width: u32,
    pub height: u32,
    pub pixels: Vec<[u8; 4]>,  // BGRA
}

pub struct WavData {
    pub sample_rate: u32,
    pub channels: u16,
    pub samples: Vec<i16>,
}

pub struct MeshData {
    pub vertices: Vec<[f32; 3]>,
    pub indices: Vec<u32>,
}

pub struct AssetStorage {
    textures: HashMap<u32, RgbaImage>,
    sounds: HashMap<u32, WavData>,
    meshes: HashMap<u32, MeshData>,
    next_id: u32,
}

impl AssetStorage {
    pub fn new() -> Self {
        Self {
            textures: HashMap::new(),
            sounds: HashMap::new(),
            meshes: HashMap::new(),
            next_id: 1,
        }
    }

    pub fn load_texture(&mut self, path: &Path) -> TextureId {
        let id = self.next_id;
        self.next_id += 1;
        let image = parse_png(&std::fs::read(path).unwrap());
        self.textures.insert(id, image);
        TextureId(id)
    }

    pub fn load_sound(&mut self, path: &Path) -> SoundId {
        let id = self.next_id;
        self.next_id += 1;
        let wav = parse_wav(&std::fs::read(path).unwrap());
        self.sounds.insert(id, wav);
        SoundId(id)
    }

    pub fn get_texture(&self, id: TextureId) -> &RgbaImage {
        &self.textures[&id.0]
    }

    pub fn get_sound(&self, id: SoundId) -> &WavData {
        &self.sounds[&id.0]
    }

    pub fn unload(&mut self, id: TextureId) {
        self.textures.remove(&id.0);
    }
}
```

这个 API 设计是 day133 的核心产出。后面 Day 134-137 演化:

- Day 134:用更好的 hash(FxHash)加速 HashMap
- Day 135:用 generic `Asset<T>` 进一步抽象
- Day 136:用 inverted index 支持查询
- Day 137:加 sprite animation 支持

## 11 · 一个具体的迁移案例:从 Day 132 到 Day 133

假设 Day 132 你有这段代码:

```rust
// Day 132 风格
let id: AssetId = storage.load("player.png");
let data: &[u8] = storage.get(id);
let image = parse_png(data);  // 每次都 parse
draw_sprite(&image, x, y);
```

迁移到 Day 133:

```rust
// Day 133 风格
let id: TextureId = storage.load_texture("player.png");
let image: &RgbaImage = storage.get_texture(id);  // 已 parse
draw_sprite(image, x, y);
```

收益:

1. **类型安全**:id 不可能传错类型
2. **零 parse**:load 时 parse 一次,get 直接返回 parsed 结果
3. **Memory 紧凑**:同类型资产连续存储,cache 友好

这是 Day 133 的核心价值。看起来简单,但每条收益背后都是工程权衡。

## 12 · 工业级的额外考量

### 12.1 异步加载

Day 132 的"流式加载"是同步——load 阻塞主线程。Day 133 的 typed storage 仍然同步。但工业级要异步:

```rust
// 异步:返回 future,主线程不阻塞
let id = storage.request_texture("player.png");  // 立刻返回 TextureId
// 此时 texture 可能还没加载
// 渲染时检查
if storage.is_loaded(id) {
    let image = storage.get_texture(id);
    draw_sprite(image, x, y);
} else {
    draw_placeholder(x, y);  // 加载中显示
}
```

异步加载需要后台线程 + 状态机。Bevy 的 `Handle<T>` 就是这个。

### 12.2 引用计数

谁在用 texture?没人用了就 unload。但要知道"谁在用"就要 refcount。

简单实现:`Arc<RgbaImage>`,texture 从 storage 取出 Arc,storage 也持有 Arc。所有 Arc drop 后 texture 实际 free。

复杂实现:每个 texture 一个 `AtomicUsize use_count`,显式 acquire / release。Bevy 的 asset system 用这个。

### 12.3 热重载

开发时改 PNG 文件,游戏立刻看到变化。需要:

- file watcher(notify crate)监听文件变化
- 文件变化时重新 load,替换 storage 里的 RgbaImage
- 通知渲染系统刷新

Bevy / Unreal 都支持热重载,Casey 后期的 day 也有讨论。

### 12.4 序列化

Asset bundle 文件(把所有 asset 打包成一个 .pak)。需要:

- asset 序列化到二进制
- asset 加载时反序列化
- 支持增量更新

Casey 后期(day 400+)讨论 asset bundle。
