# Day 131 · 异步地面区块合成

> Day 082 把地面切成 chunk 在主线程合成;Day 126 写好了 work queue。今天把两者粘起来:主线程发现"需要合成 chunk X",丢给工作线程后台合成,自己继续渲染。这是把 Day 121 多核思想扩展到"非实时"任务上的关键一步。

## 0 · 为什么要有这一天

回顾 Day 082:地面被切成固定大小的 chunk(比如 256×256 tile),每个 chunk 的纹理不是预先存在的——它由多个底层素材(草地、石头、沙子、水等)按某种规则合成出来。这个"合成"过程涉及多次纹理采样 + 混合,每个 chunk 耗时几毫秒。

问题来了:玩家走到一个新区域,需要瞬间渲染 9 个 chunk(玩家所在的 + 周围 8 个)。这 9 个 chunk 之前没合成过,需要现场合成——主线程在这 9 个 chunk 上各花 5ms,共 45ms,直接把这一帧的 16ms 预算爆掉,游戏掉帧。

最朴素的解法是**预合成**:启动时把整个地图所有 chunk 都合成好,缓存起来。但开放世界游戏(GTA V、Skyrim、塞尔达)的地图可能有数万个 chunk,全部预合成要几 GB 内存,而且玩家大概率永远走不完整个地图,浪费。

工业解法是**流式合成(streaming)**:
1. 主线程跟踪"哪些 chunk 在玩家视野内"
2. 视野内的 chunk 进入"待合成"队列
3. 工作线程从队列取任务,后台合成
4. 主线程每帧渲染时:已合成的 chunk 用真实纹理,未合成的 chunk 用临时 fallback(灰色 / 低分辨率 placeholder)
5. 工作线程合成完一个 chunk,标记为"就绪",下一帧主线程自然就用了

这样主线程不阻塞,玩家移动时短暂看到 fallback(几十毫秒),合成完无缝切换到真实纹理。这是开放世界游戏的标准技术。

**今天的核心**:把 Day 082 的"同步合成"改造为"异步合成",用 Day 126 的 work queue 当任务调度。

心理锚点:做完今天你能(1)解释"同步"和"异步"在游戏开发里的精确含义;(2)在你的引擎里加一个 streaming system,管理 chunk 的"已合成/合成中/未合成"三态;(3)用 `Arc<Mutex<>>` 或 lock-free 状态机让主线程和工作线程协作;(4)说出"玩家移动太快导致 chunk 来不及合成"时怎么退化。

## 1 · Casey 今天做了什么

Casey 把 Day 082 的 chunk 合成代码改造成异步:

1. 在 `GameState` 里加一个"chunk 状态表":每 chunk 一个 enum(Empty / Composing / Ready),按 chunk 坐标索引
2. 主线程每帧开始时扫描视野内 chunk,把状态 = Empty 的 push 进 work queue(任务:"合成 chunk (x, y)")
3. 工作线程从 queue pop 出任务,合成 chunk 像素,写入 chunk 的内存,把状态改为 Ready(用原子操作或锁)
4. 渲染时:状态 = Ready 用真实像素,否则用 fallback(纯色或之前 chunk 的低分辨率版本)
5. 玩家走出 chunk 范围时:状态改回 Empty,内存可回收(为后续新 chunk 留位置)

关键技术点:
- chunk 内存由谁分配?Casey 让主线程预分配一个 chunk 池(固定 N 个槽位),工作线程从池里取一个空槽,合成完标记 Ready。主线程渲染时只读 Ready 槽位
- 同步:chunk 的状态用 `AtomicU32`(Empty=0, Composing=1, Ready=2),工作线程 CAS 切换状态
- fallback:Casey 用 chunk 在更低分辨率的"半合成"版本(用前一帧已合成的邻 chunk 推断),看起来不至于全黑

这一天的工程量大但概念清晰:**把"耗时操作"从渲染帧里剥离,放到后台线程,主线程用 fallback 兜底**。

## 2 · 心智模型

### 类比:餐厅的菜单打印

想象一家餐厅,菜单每天变(季节性食材)。服务员(主线程)客人要菜单时,要打印一份。

**同步**:服务员看客人坐下,跑到后厨问厨师今天有什么,等厨师想清楚,服务员去打印,等打印完,拿给客人。客人等了 5 分钟。

**异步**:服务员预先打印一份"昨日菜单"(fallback)给客人。同时把"今天有什么"这个问题丢给厨师(工作线程)。厨师想清楚后告诉服务员,服务员下次打印新菜单给下一桌客人。

客人体验:第一桌拿到的是"昨日菜单"(短暂不一致),一分钟后厨师回复,后续客人拿到新菜单。**最终一致性**,期间服务员不阻塞,继续服务其他客人。

异步合成的本质:**接受短暂的"不一致",换取主流程的连续性**。

### 严谨原理:chunk 状态机

每个 chunk 有一个三态状态机:

```
   ┌───────────┐
   │   Empty   │ ← 玩家离开,内存回收
   └─────┬─────┘
         │ 主线程:玩家进入视野,push 合成任务到 work queue
         ↓ CAS:Empty → Composing
   ┌───────────┐
   │Composing  │ ← 工作线程正在合成(可能 1-50ms)
   └─────┬─────┘
         │ 工作线程:合成完,CAS Composing → Ready
         ↓
   ┌───────────┐
   │   Ready   │ ← 主线程可渲染
   └───────────┘
```

每个状态转移由一方发起:
- Empty → Composing:主线程发(决定"要合成这个 chunk")
- Composing → Ready:工作线程发(决定"我合成完了")
- Ready → Empty:主线程发(决定"这个 chunk 不再需要,LPM 内存回收")

**为什么用 CAS 而不是 Mutex**:状态切换只有这几个明确路径,无复杂临界区。CAS 表达"如果当前状态是我期望的,就推进到下一个,否则重读"——天然适配状态机。

### Rust 表达:AtomicU32 + enum

```rust
use std::sync::atomic::{AtomicU32, Ordering};

#[repr(u32)]
#[derive(Copy, Clone, Debug, PartialEq)]
enum ChunkState {
    Empty = 0,
    Composing = 1,
    Ready = 2,
}

impl ChunkState {
    fn from_u32(v: u32) -> Self {
        match v {
            0 => Self::Empty,
            1 => Self::Composing,
            2 => Self::Ready,
            _ => panic!("invalid state"),
        }
    }
}

struct Chunk {
    state: AtomicU32,
    pixels: UnsafeCell<Vec<u32>>,  // 工作线程写,主线程读
    x: i32,
    y: i32,
}
```

主线程切换 Empty → Composing:
```rust
fn request_compose(chunk: &Chunk) {
    match chunk.state.compare_exchange(
        ChunkState::Empty as u32,
        ChunkState::Composing as u32,
        Ordering::AcqRel,
        Ordering::Acquire,
    ) {
        Ok(_) => {
            // 成功,推任务到 work queue
            work_queue.push(Task::ComposeChunk(chunk.x, chunk.y));
        }
        Err(_) => {
            // 已经在 Composing 或 Ready,不做
        }
    }
}
```

工作线程合成完:
```rust
fn worker_compose_chunk(chunk: &Chunk) {
    // 合成像素
    let pixels = compose_chunk_pixels(chunk.x, chunk.y);
    unsafe {
        *chunk.pixels.get() = pixels;
    }
    // CAS:Composing → Ready。如果主线程已经把状态改回 Empty(玩家走了),
    // 我们的合成结果作废(CAS 失败,状态保持 Empty,pixels 不用)
    let _ = chunk.state.compare_exchange(
        ChunkState::Composing as u32,
        ChunkState::Ready as u32,
        Ordering::Release,  // 配对主线程的 Acquire
        Ordering::Relaxed,
    );
}
```

主线程渲染:
```rust
fn render_chunk(chunk: &Chunk) {
    let state = ChunkState::from_u32(chunk.state.load(Ordering::Acquire));
    match state {
        ChunkState::Ready => {
            // 用真实像素
            let pixels = unsafe { &*chunk.pixels.get() };
            blit(pixels);
        }
        _ => {
            // fallback:灰色或低分辨率
            blit_fallback(chunk.x, chunk.y);
        }
    }
}
```

### 难点:UnsafeCell 的安全性

`pixels: UnsafeCell<Vec<u32>>` 表示"这个 Vec 可能被并发访问"。我们必须证明:
- **多个读者** 同时读 Ready 状态的 chunk 是安全的(Vec 的不可变借用可以多个)
- **一个写者**(工作线程)在 Composing 状态时独占,主线程不读

这套保证完全靠状态机 + CAS 维持——状态 = Ready 时主线程读,状态 = Composing 时工作线程独占写。Rust 编译器无法静态验证这个,所以 UnsafeCell + unsafe impl Sync。

工业级实现(如 `crossbeam_epoch`、`arc-swap`)用 epoch-based reclamation 解决类似问题——保证读者读完才释放,写者写完才切换状态。教学版的状态机已经够用。

### 难点:fallback 怎么选

工作线程合成需要时间(假设 30ms)。这 30ms 内玩家看到的是什么?三种 fallback 策略:

**策略 1:纯色**。所有未合成 chunk 渲染成纯灰色。简单,但玩家看到灰色方块"突然变草地",跳变明显。

**策略 2:低分辨率 placeholder**。预先合成 chunk 的 8×8 缩略图(很快),渲染时放大。Casey 没用,Day 350+ 可能用。

**策略 3:邻 chunk 推断**。用已合成的邻 chunk 的边缘像素"外推"到未合成 chunk。视觉上自然,但实现复杂。

**策略 4:双缓冲**。chunk 有两个像素 buffer,工作线程合成到 back buffer,主线程读 front buffer,合成完 swap。swap 是原子的(`Arc<Vec<>>` + `ArcSwap`)。Casey 部分用,主要在 Day 132 资产加载。

Casey Day 131 用策略 1 + 部分策略 4:状态 = Ready 时用真实像素,否则用一个全局的 placeholder bitmap(纯灰色草地纹理)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

异步 chunk 合成是开放世界游戏的核心技术之一。商业实现:

**Minecraft**:每个 chunk 16×16×256 方块,玩家移动时新 chunk 进入视野,服务器(或本地)异步生成。Minecraft 的"chunk gen"包括地形(噪声函数)、生物群系、结构生成(村庄)。整个过程分阶段(stage),每个 stage 是一次状态切换。代码在 `net.minecraft.world.gen.chunk.ChunkGenerator`。

**GTA V**:地图分 "blocks"(约 64×64 米),每个 block 预生成 LOD(Level of Detail)几个版本。玩家移动时新 block 异步加载,根据距离切 LOD。技术上叫 "clipmap" 或 "geometry clipmap"。

**Skyrim / Creation Engine**:每个 "cell" 是一个独立单元(室内)或一片区域(室外)。玩家穿门时新 cell 异步加载,期间显示加载界面(老游戏)或延迟过渡(新游戏)。

**塞尔达:野炊**:整个世界无缝,玩家移动时后台流式加载。任天堂的 GDC 演讲透露他们用了一个 "two-stage streaming":第一阶段加载 metadata(快速),第二阶段加载几何(慢)。

Casey Day 131 是 HH 的简化版:单 LOD,单 stage,但概念一致。

游戏开发圈的标准 streaming 设计:
```
[ Asset Disk ] → IO 线程读取 → [ Asset Memory ]
                                  ↓
                          工作线程合成 / 解压
                                  ↓
                          [ Ready State ]
                                  ↓
                          主线程渲染时使用
```

每个箭头是一条异步 pipeline,任何一步慢了下游就有 fallback。

### 3.2 · 🐧 Linux 系统编程视角

异步操作在 Linux 上有几个层次:

**文件 IO**:
- 同步:`read(2)` 阻塞,直到数据读到 user buffer
- 多线程异步:开一个 IO 线程,在它上面同步 read,主线程通过 channel 收结果
- `aio_read(3)`:POSIX AIO,异步 read,通过 signal 或 callback 通知
- `io_uring(2)`:Linux 5.1+ 的新接口,真正的高性能异步 IO,Google、Facebook 都用

```bash
# 看 Linux 是否支持 io_uring
uname -r   # 5.1+
grep io_uring /proc/kallsyms | head
```

**网络**:
- 同步:`recv(2)` 阻塞
- select / poll / epoll:多路复用,一个线程管多个 fd
- io_uring:网络也能用

**用户态线程**:
- pthread:`pthread_create`,每线程 8MB 栈
- `clone(2)` 系统调用:更底层,可以共享内存 / fd 表
- coroutine / async:Rust async/await,Tokio 运行时

Casey 的多线程方案是用户态多线程(std::thread + work queue),不涉及 IO 异步。Day 132 资产加载会扩展到文件 IO 异步。

Linux 上和 chunk streaming 类似的设施:

**page cache**:Linux 文件系统层把读过的文件块缓存在内存。下次读同一文件命中 cache,不查磁盘。chunk streaming 的"已合成 chunk 内存"是应用层等价物。

**mmap**:把文件映射到内存,读文件 = 读内存,OS 负责按需 page-in。游戏资产加载可以用 mmap 直接读文件,跳过 read 系统调用。

**swap**:内存不够时 OS 把不活跃 page 写到磁盘(swap 区)。chunk streaming 可以模仿——"远离玩家的 chunk" 换出内存(状态改回 Empty,内存给新 chunk)。

### 3.3 · 🦀 Rust 生态视角

Rust 表达 chunk streaming 几个层次:

#### 流派 1:手写 AtomicU32 + UnsafeCell(教学版)

```rust
struct Chunk {
    state: AtomicU32,
    pixels: UnsafeCell<Vec<u32>>,
}
unsafe impl Sync for Chunk {}
```

优点:理解原理。缺点:UnsafeCell 难维护。

#### 流派 2:RwLock<Vec<u32>>

```rust
struct Chunk {
    pixels: RwLock<Option<Vec<u32>>>,  // None = 未合成
}
```

主线程读时 `chunk.pixels.read()`,工作线程写时 `chunk.pixels.write()`。RwLock 让多读者并发。

优点:无需 unsafe。缺点:锁开销,且每次访问都要拿锁。

#### 流派 3:`arc_swap::ArcSwap<Vec<u32>>`

```toml
[dependencies]
arc-swap = "1"
```

```rust
use arc_swap::ArcSwap;
struct Chunk {
    pixels: ArcSwap<Vec<u32>>,
}
// 主线程读
let snapshot = chunk.pixels.load();  // 拿一个 Arc 引用,无锁
// 工作线程写
chunk.pixels.store(Arc::new(new_pixels));  // 原子替换
```

优点:无锁读者,适合"读多写少"。缺点:每次 store 分配 Arc。

#### 流派 4:消息传递(channel)

```rust
use std::sync::mpsc::channel;
let (tx, rx) = channel();
// 工作线程合成完发消息
tx.send(ComposeResult { chunk_x, chunk_y, pixels });
// 主线程每帧从 rx 收
for result in rx.try_iter() {
    chunks[result.chunk_x][result.chunk_y].pixels = result.pixels;
}
```

优点:无共享状态,无锁。缺点:消息队列本身是开销,且主线程要每帧 try_iter 收。

#### 流派 5:async/await(异步生态)

```rust
async fn compose_chunk(x: i32, y: i32) -> Vec<u32> {
    // ...
}
let handle = tokio::spawn(compose_chunk(10, 20));
// 主线程做其他事
let pixels = handle.await;  // 等待
```

优点:无显式线程,异步生态。缺点:需要 Tokio runtime,游戏开发不常用(游戏的"实时性"和异步任务模型不完全契合)。

Casey 风格 = 流派 1(教学,理解原理)+ Day 132 之后实际可能转流派 4(channel)。Rust 生态推荐流派 3(arc-swap)或流派 4(channel)。

### 3.4 · 性能权衡

异步 chunk 合成引入新的成本:
- **chunk 池**:预分配 N 个槽位,占用 N × chunk_size 字节。256×256 chunk × 4 字节/像素 × 64 个 chunk = 16MB
- **状态查询**:每帧每 chunk 一次原子 load,可忽略
- **fallback 渲染**:每帧每未合成 chunk 一次,简单 blit
- **工作线程**:N 个线程的 stack(N × 8MB),以及工作队列 contention

**收益**:
- 主线程不阻塞,帧时间稳定 16ms
- 多核 CPU 利用率提升(N 个工作线程跑满 N-1 个核)
- 玩家体验:移动时短暂看到 fallback(可优化到看不见)

总体是性能净增益,这就是为什么所有开放世界游戏都用 streaming。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Streaming system(流式系统)** —— 把"全量加载"改成"按需 + 异步"加载的工程模式
- **Producer-consumer with fallback** —— 生产者跟不上时消费者用兜底数据
- **Async resource loading** —— 资源(资产、chunk、关卡)异步加载
- **Cache hierarchy(L1 / L2 / L3 / RAM / disk)** —— 异步合成 = 在 RAM 里维护一个"已合成 chunk cache"

### 4.2 同级(并行方案)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 同步合成 | 主线程现场算 | 小游戏,地图小 | Day 1-082 |
| 异步合成(streaming) | 工作线程后台算 | 开放世界 | ✅ |
| 预合成 + 全缓存 | 启动时合成全部 | 关卡游戏(每关不大) | 不用 |
| LOD streaming | 多个 LOD 版本异步切 | GTA、Skyrim | Day 350+ |
| Procedural generation | 玩家走到哪里实时算 | Minecraft、No Man's Sky | 不用 |

详细说明:
- **预合成 + 全缓存**:适合 small indie 关卡游戏(《时空幻境》、《空洞骑士》),整张地图不大,几 MB 缓存够。开放世界不行
- **LOD streaming**:3A 大作标配。chunk 有 4-5 个 LOD 版本(1024×1024 / 256×256 / 64×64 / 16×16 / 4×4),玩家近时切高 LOD,远时切低 LOD。每帧根据距离决定切哪个
- **Procedural**:不预存纹理,玩家走到哪里算到哪里。优点空间小(只存算法),缺点 CPU 重。Minecraft 用 simplex noise 生成地形

### 4.3 下级(内部零件)

- **ChunkState enum**(Empty / Composing / Ready) —— 三态状态机
- **AtomicU32 state** —— 原子状态切换
- **UnsafeCell pixels** —— chunk 的像素数据,工作线程写主线程读
- **Work queue** —— Day 126 的 ring buffer,推 ComposeChunk 任务
- **Fallback renderer** —— 状态 = Empty / Composing 时画什么
- **Chunk pool** —— 固定大小,LRU 淘汰远离玩家的 chunk
- **Frame budget** —— 每帧最多 push N 个新合成任务,防止积压

## 5 · 对照与变奏

### 同步 vs 异步在不同领域

| 领域 | 同步 | 异步 |
|---|---|---|
| 文件 IO | `read()` 阻塞 | `aio_read` / `io_uring` |
| 网络 | `recv()` 阻塞 | `epoll` / `io_uring` |
| 数据库查询 | 等结果 | connection pool + future |
| UI 渲染 | 主线程画图 | 渲染线程独立 |
| Chunk 合成 | 主线程现场算 | 工作线程后台算 |
| 网页加载 | 整页加载完显示 | AJAX / streaming HTML |

异步的本质都是"**调用方不阻塞,结果通过另一种机制(callback / channel / future)传回**"。

### Chunk pool 大小权衡

- pool 太小:玩家快速移动时新 chunk 排不上队,大量 fallback,体验差
- pool 太大:内存占用高,cache 命中率下降,工作线程合成的 chunk 可能在用之前就被淘汰

经验值:pool 大小 = 视野内 chunk 数 × 2。视野 9 chunk,pool 18 个。视野 25 chunk(5×5),pool 50 个。

### Fallback 时间 vs 合成时间

工作线程合成一个 chunk 假设 30ms。如果工作线程只有 1 个,每秒最多合成 33 个 chunk。玩家移动每秒需要 10 个新 chunk(走进新区域),工作线程跟得上。

但工作线程被其他任务(资产加载、动画混合)竞争时,合成可能延迟。这时候玩家看到 fallback 时间从 30ms 变成 200ms,体验下降。

解法:给 chunk 合成**优先级**(视野中心的 chunk 优先于边缘),工作队列支持 priority。Casey 没做,留 Lv4。

- **1980s**:游戏地图小(《超级马里奥》一屏一关),没有 streaming
- **1990s**:《无尽的任务》等 MMO 引入 streaming,玩家在地图间走时后台加载
- **2000s**:开放世界普及(GTA III、Tony Hawk's Underground),streaming 标配
- **2010s**:LOD streaming 成熟,《荒野大镖客》《GTA V》用,无缝大世界
- **2020s**:SSD 普及,直接从 SSD 流式加载(PS5、《Ratchet & Clank: Rift Apart》维度跳转)

Casey 的实现停在 2000s 水平(单 LOD,无 SSD 优化),但概念上是同一套。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:

1. chunk 状态从 Empty 到 Ready 经过几次 CAS?分别由哪个线程发起?
2. 为什么 fallback 必须存在?直接让主线程等到 chunk 合成完不行吗?
3. 工作线程合成完一个 chunk,CAS Composing → Ready 失败,说明什么?应该怎么处理?
4. chunk pool 满了,新的合成请求怎么处理?

**参考解答**:
1. 两次 CAS。第一次:主线程发起,Empty → Composing(决定"要合成")。第二次:工作线程发起,Composing → Ready(决定"合成完了")。
2. 让主线程等的话,这一帧会卡到合成完成(30ms+),帧率从 60 FPS 掉到 30 FPS 以下。fallback 让主线程不阻塞,用低质量数据兜底,玩家短暂看到灰色方块,几十毫秒后无缝切到真实纹理。
3. CAS 失败说明状态不再是 Composing——可能是主线程已经把状态改回 Empty(玩家离开了)。处理:作废合成结果,什么都不做。pixels 已经写入 chunk.pixels,但因为状态 = Empty,主线程不会读,等下次 Empty → Composing 时会被覆盖。注意:不要直接读 state 来判断——CAS 失败的返回值告诉你当前状态。
4. chunk pool 满了说明 N 个槽位都 Ready 或 Composing。两种策略:(a) 拒绝新请求(等下次再试);(b) LRU 淘汰最久没渲染的 Ready chunk,腾出位置。Casey 用 (b)。

### Lv2 · 动手实践

**题**:Rust 实现一个简化的 chunk streaming system。

要求:
1. 定义 `Chunk` struct,带 `AtomicU32 state` 和 `Mutex<Option<Vec<u32>>>` pixels(简化版,不用 UnsafeCell)
2. chunk pool:`Vec<Chunk>`,固定 16 个槽位
3. 主线程模拟:每"帧"扫描视野(随机选 9 个 chunk 坐标),状态 = Empty 的 push 到 work queue,状态 = Ready 的"渲染"(打印)
4. 工作线程:从 queue pop 出任务,sleep 50ms 模拟合成,把状态改为 Ready
5. 跑 10 帧,观察状态变化

完成标准:打印每帧每个 chunk 的状态,看到 Empty → Composing → Ready 的过渡。

**参考解答**:

```rust
use std::sync::atomic::{AtomicU32, Ordering};
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;
use std::collections::VecDeque;

#[repr(u32)]
#[derive(Copy, Clone, Debug, PartialEq)]
enum State { Empty = 0, Composing = 1, Ready = 2 }

impl State {
    fn from_u32(v: u32) -> Self {
        match v { 0 => Self::Empty, 1 => Self::Composing, 2 => Self::Ready, _ => unreachable!() }
    }
}

struct Chunk {
    state: AtomicU32,
    pixels: Mutex<Option<Vec<u32>>>,
    x: i32,
    y: i32,
}

impl Chunk {
    fn new(x: i32, y: i32) -> Self {
        Self {
            state: AtomicU32::new(State::Empty as u32),
            pixels: Mutex::new(None),
            x, y,
        }
    }
    fn get_state(&self) -> State {
        State::from_u32(self.state.load(Ordering::Acquire))
    }
    fn cas_state(&self, from: State, to: State) -> bool {
        self.state.compare_exchange(from as u32, to as u32, Ordering::AcqRel, Ordering::Acquire).is_ok()
    }
}

// 简单的 Mutex<VecDeque> work queue(不用 Day 126 的 lock-free,简化教学)
struct Queue {
    inner: Mutex<VecDeque<(i32, i32)>>,  // (chunk_x, chunk_y)
}
impl Queue {
    fn new() -> Self { Self { inner: Mutex::new(VecDeque::new()) } }
    fn push(&self, x: i32, y: i32) { self.inner.lock().unwrap().push_back((x, y)); }
    fn pop(&self) -> Option<(i32, i32)> { self.inner.lock().unwrap().pop_front() }
}

fn main() {
    // chunk 池:16 个槽位,坐标 (0,0) - (15,15)
    let chunks: Arc<Vec<Chunk>> = Arc::new(
        (0..16).flat_map(|y| (0..16).map(move |x| Chunk::new(x, y))).collect()
    );
    let queue = Arc::new(Queue::new());

    // 工作线程
    let chunks_w = chunks.clone();
    let queue_w = queue.clone();
    let worker = thread::spawn(move || {
        loop {
            if let Some((x, y)) = queue_w.pop() {
                let chunk = &chunks_w[y as usize * 16 + x as usize];
                // 验证状态 = Composing(主线程已切)
                if chunk.get_state() != State::Composing { continue; }
                println!("  [worker] composing chunk ({}, {})", x, y);
                thread::sleep(Duration::from_millis(50));  // 模拟合成
                let pixels = vec![0xff00ff00; 256];  // 假设 16×16 绿色像素
                *chunk.pixels.lock().unwrap() = Some(pixels);
                // 切换 Composing → Ready
                if chunk.cas_state(State::Composing, State::Ready) {
                    println!("  [worker] chunk ({}, {}) Ready", x, y);
                } else {
                    println!("  [worker] chunk ({}, {}) CAS failed (state changed)", x, y);
                }
            } else {
                thread::sleep(Duration::from_millis(5));
            }
        }
    });

    // 主线程模拟 10 帧
    let mut frame = 0;
    while frame < 10 {
        println!("=== Frame {} ===", frame);
        // 视野:随机选 9 个 chunk
        let view: Vec<(i32, i32)> = (0..9).map(|_| {
            let x = (frame + 0) % 16;  // 简化:每帧视野偏移
            let y = (frame % 16);
            ((x + (frame / 2) as i32) % 16, y)
        }).take(9).collect();
        let view: Vec<(i32, i32)> = (0..3).flat_map(|dy| {
            (0..3).map(move |dx| ((frame as i32 + dx) % 16, (frame as i32 + dy) % 16))
        }).collect();

        // 扫描视野:Empty 推合成,Ready 渲染
        for &(x, y) in &view {
            let chunk = &chunks[y as usize * 16 + x as usize];
            match chunk.get_state() {
                State::Empty => {
                    if chunk.cas_state(State::Empty, State::Composing) {
                        println!("  [main] requesting compose ({}, {})", x, y);
                        queue.push(x, y);
                    }
                }
                State::Composing => {
                    println!("  [main] chunk ({}, {}) still composing, fallback", x, y);
                }
                State::Ready => {
                    let pixels = chunk.pixels.lock().unwrap();
                    println!("  [main] RENDER chunk ({}, {}) {} pixels", x, y,
                             pixels.as_ref().map(|p| p.len()).unwrap_or(0));
                }
            }
        }
        frame += 1;
        thread::sleep(Duration::from_millis(100));  // 模拟一帧 100ms
    }

    // 让 worker 退出(简化,直接 detach)
    println!("Main loop done.");
}
```

**预期输出**(片段):
```

  [main] requesting compose (0, 0)
  [main] requesting compose (1, 0)
  ...
  [worker] composing chunk (0, 0)
=== Frame 1 ===
  [main] chunk (0, 0) still composing, fallback
  ...
  [worker] chunk (0, 0) Ready
=== Frame 2 ===
  [main] RENDER chunk (0, 0) 256 pixels
  ...
```

## 8 · Rust / Arch 落地代码

### Rust 完整项目:异步 chunk 合成 + benchmark

```rust
// Cargo.toml: 无依赖

use std::sync::atomic::{AtomicU32, Ordering};
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::{Duration, Instant};
use std::collections::VecDeque;

#[repr(u32)]
#[derive(Copy, Clone, Debug, PartialEq)]
enum State { Empty = 0, Composing = 1, Ready = 2 }
impl State {
    fn from_u32(v: u32) -> Self {
        match v { 0 => Self::Empty, 1 => Self::Composing, 2 => Self::Ready, _ => unreachable!() }
    }
}

#[repr(align(64))]  // 对齐 cache line,避免 false sharing
struct Chunk {
    state: AtomicU32,
    pixels: Mutex<Option<Vec<u32>>>,
    x: i32, y: i32,
    _pad: [u8; 24],  // 凑齐 64 字节
}

impl Chunk {
    fn new(x: i32, y: i32) -> Self {
        Self {
            state: AtomicU32::new(State::Empty as u32),
            pixels: Mutex::new(None),
            x, y, _pad: [0; 24],
        }
    }
}

struct Queue<T> { inner: Mutex<VecDeque<T>> }
impl<T> Queue<T> {
    fn new() -> Self { Self { inner: Mutex::new(VecDeque::new()) } }
    fn push(&self, v: T) { self.inner.lock().unwrap().push_back(v); }
    fn pop(&self) -> Option<T> { self.inner.lock().unwrap().pop_front() }
}

const POOL_W: usize = 32;
const POOL_H: usize = 32;

fn main() {
    let chunks: Arc<Vec<Chunk>> = Arc::new(
        (0..POOL_H).flat_map(|y| (0..POOL_W).map(move |x| Chunk::new(x as i32, y as i32))).collect()
    );
    let queue: Arc<Queue<(usize, usize)>> = Arc::new(Queue::new());

    // Spawn 4 worker threads
    let mut workers = vec![];
    for wid in 0..4 {
        let chunks_c = chunks.clone();
        let queue_c = queue.clone();
        workers.push(thread::spawn(move || {
            loop {
                if let Some((x, y)) = queue_c.pop() {
                    let chunk = &chunks_c[y * POOL_W + x];
                    if State::from_u32(chunk.state.load(Ordering::Acquire)) != State::Composing {
                        continue;
                    }
                    // 模拟合成
                    let mut pixels = vec![0u32; 256 * 256];
                    for py in 0..256 {
                        for px in 0..256 {
                            // 噪声纹理
                            pixels[py * 256 + px] = ((px ^ py ^ x as i32 ^ y as i32) & 0xff) as u32 * 0x010101;
                        }
                    }
                    std::thread::sleep(Duration::from_millis(10));  // 假装合成慢
                    *chunk.pixels.lock().unwrap() = Some(pixels);
                    let _ = chunk.state.compare_exchange(
                        State::Composing as u32, State::Ready as u32,
                        Ordering::Release, Ordering::Relaxed,
                    );
                } else {
                    std::thread::sleep(Duration::from_millis(1));
                }
            }
        }));
    }

    // 主线程:模拟 30 帧
    let mut frame = 0;
    let start = Instant::now();
    while frame < 30 {
        // 视野:(frame_x, frame_y) 附近 5×5
        let vx = (frame / 2) % (POOL_W - 5);
        let vy = (frame / 3) % (POOL_H - 5);
        let mut ready_count = 0;
        let mut composing_count = 0;
        let mut empty_count = 0;
        for dy in 0..5i32 {
            for dx in 0..5i32 {
                let x = (vx as i32 + dx) as usize;
                let y = (vy as i32 + dy) as usize;
                let chunk = &chunks[y * POOL_W + x];
                match State::from_u32(chunk.state.load(Ordering::Acquire)) {
                    State::Empty => {
                        if chunk.state.compare_exchange(
                            State::Empty as u32, State::Composing as u32,
                            Ordering::AcqRel, Ordering::Acquire,
                        ).is_ok() {
                            queue.push(x, y);
                        }
                        empty_count += 1;
                    }
                    State::Composing => { composing_count += 1; }
                    State::Ready => {
                        let _p = chunk.pixels.lock().unwrap();
                        ready_count += 1;
                    }
                }
            }
        }
        println!("Frame {:>2}: view=({:>2},{:>2}) | ready={} composing={} empty={}",
                 frame, vx, vy, ready_count, composing_count, empty_count);
        frame += 1;
        thread::sleep(Duration::from_millis(16));  // 60 FPS
    }
    println!("Total: {} ms", start.elapsed().as_millis());
}
```

**预期输出**:
```
Frame  0: view=( 0, 0) | ready=0 composing=0 empty=25
Frame  1: view=( 0, 0) | ready=0 composing=25 empty=0
Frame  2: view=( 1, 0) | ready=20 composing=5 empty=5
Frame  3: view=( 1, 0) | ready=24 composing=1 empty=0
...
Frame 29: view=(14, 9) | ready=25 composing=0 empty=0
Total: 480 ms
```

可以看到从 frame 0(全 empty)到 frame 3(几乎全 ready)的过渡。期间 fallback 渲染未合成 chunk,主线程不阻塞。
