# Day 121 · 分 tile 渲染(马拉松)

> 这是 Handmade Hero 全 667 集里**最长的一集**(几小时马拉松)。Casey 把整个软渲染器**拆成 tile**(64×64 像素的小块),每个 tile 内部 SIMD 处理,这是软渲染 SIMD + 多线程化的巅峰。Phase 4 前 10 天的所有理论,在这集综合演练。

## 0 · 为什么要有这一天

你的软渲染器现在长这样:一帧渲染,从左上角到右下角,一行一行扫,每个像素画一下。简单,但有几个问题:

1. **cache 不友好**:屏幕 1920×1080,framebuffer 8MB,远超 L1(32KB) / L2(256KB)。每行扫描跨 cache line,效率低
2. **无法多线程**:整个渲染是单一 for 循环,所有像素串行,加多核没用
3. **SIMD 利用率低**:像素之间有依赖(比如透明像素叠加),SIMD 没法一次处理 4 个

Casey 这一天做的事是**重构整个渲染**:把屏幕切成 64×64 的 tile,每个 tile:

- 64×64 = 4096 像素 = 16KB(u32)正好放 L1
- tile 内部用 SIMD,4 像素一组,完美匹配 cache line
- 不同 tile 给不同 CPU 核(多线程,Day 122+ 详谈)

这集是**所有 Phase 4 知识的整合**:Day 112 的 port 模型、Day 113 的 profiler、Day 115-120 的 SIMD 优化,全用到。

心理锚点:读完这一天(可能要分几次),你能:

- 解释"为什么 64×64 是理想的 tile 大小"
- 设计一个 tile-based 软渲染器架构
- 在 tile 内部用 SIMD 处理像素
- 准备好 Day 122+ 把 tile 分给多线程

## 1 · Casey 今天做了什么

Casey 这一天**不打开游戏**,纯重构:

1. 把 `RenderWeirdGradient` / `DrawBitmap` / `DrawEntity` 等所有渲染函数**重写**
2. 新的渲染流程:
   - 把 framebuffer 切成 64×64 tile

## 2 · 心智模型

### 2.1 类比:大画布上的方格画家

想象一面 10 米 × 5 米的大墙要画壁画。一个画家拿着调色板和刷子,从左上角开始画,逐行扫描。问题:

- 他要不停走到调色板处取颜料(= 从 L3 取 framebuffer)
- 他不知道下一行画什么,要回到工头那里问(= 跨 sprite 边界)
- 1 个画家 1 天画 1 平米(= 单线程)

新做法:把墙切成 1m × 1m 的小方格,每个方格派一个画家(= 多线程)。每个画家:

- 一次拿够颜料,够画整个 1m²(= L1 cache)
- 1m² 内画 100 个细节,颜料都在手边(= SIMD 处理同质像素)
- 多个画家并行(= 多核)

这就是 tile-based 渲染。

### 2.2 为什么是 64×64

64×64 = 4096 像素,每像素 4 字节(u32)= 16KB。正好是**L1 cache 一半**(典型 L1 是 32KB / 48KB)。

为什么不是 128×128?那要 64KB,超出 L1。

为什么不是 32×32?那只要 4KB,L1 用不满。tile 太小也有问题:管理开销大(每 tile 元数据),且 SIMD 操作的并行度低。

**经验值**:

- L1 = 32KB → tile 16KB(64×64 u32)→ 留 16KB 给其他数据
- L1 = 48KB → tile 32KB(128×128 u16 或 64×64 u32+其他)

游戏行业主流是 64×64 或 128×128。Casey 选 64×64。

### 2.3 tile 内部 SIMD

一个 64×64 tile 有 4096 像素。SIMD 4 像素一组,需要 1024 次 SIMD 操作。每次:

- load 4 个 dst 像素
- load 4 个 src 像素(纹理采样)
- blend(用 Day 117-118 的方法)
- store 4 个 dst 像素

这 1024 次操作,数据都在 L1,cache 命中率 ~100%。SIMD 充分利用。

### 2.4 tile 之间的数据传递

不同 tile 之间不共享数据,所以可以独立处理。但有些"全局"信息:

- 实体列表(sprite 位置)
- 相机参数
- 时间

这些是 read-only,所有 tile 共享读,不需要同步。

### 2.5 渲染流程的对比

#### 标量版本(重构前)

```rust
fn render(fb: &mut Framebuffer, sprites: &[Sprite]) {
    for y in 0..fb.height {
        for x in 0..fb.width {
            // 对每个像素,遍历所有 sprite 看哪个影响它
            for sprite in sprites {
                if sprite.contains(x, y) {
                    let color = sprite.sample(x, y);
                    blend_pixel(fb, x, y, color);
                }
            }
        }
    }
}
```

问题:每个像素扫所有 sprite(N × W × H 次),效率低。

#### tile 版本(重构后)

```rust
fn render(fb: &mut Framebuffer, sprites: &[Sprite]) {
    let tiles_x = fb.width / 64;
    let tiles_y = fb.height / 64;
    for ty in 0..tiles_y {
        for tx in 0..tiles_x {
            render_tile(fb, tx, ty, sprites);
        }
    }
}

fn render_tile(fb: &mut Framebuffer, tx: usize, ty: usize, sprites: &[Sprite]) {
    // 找到所有和这个 tile 相交的 sprite
    let tile_x = tx * 64;
    let tile_y = ty * 64;
    let relevant: Vec<&Sprite> = sprites.iter()
        .filter(|s| s.intersects(tile_x, tile_y, 64, 64))
        .collect();

    // 在 tile 内部 SIMD 处理 4 像素一组
    for py in (0..64).step_by(1) {
        for px in (0..64).step_by(4) {
            render_4_pixels(fb, tile_x + px, tile_y + py, &relevant);
        }
    }
}
```

#### 关键改进

1. **filter 阶段**减少 sprite 数量:大多数 tile 不需要处理大部分 sprite(只在屏幕某区域)
2. **SIMD 4 像素**:一次处理 4 个像素
3. **数据局部性**:整个 tile 在 L1,cache 命中率高

### 2.6 SIMD 4 像素处理

```rust
#[target_feature(enable = "sse4.1")]
unsafe fn render_4_pixels(fb: &mut Framebuffer, x: usize, y: usize, sprites: &[&Sprite]) {
    let dst_base = y * fb.width + x;

    // 读 4 个 dst 像素
    let mut dst = _mm_loadu_si128(fb.pixels.as_ptr().add(dst_base) as *const __m128i);

    // 对每个 sprite,blend
    for sprite in sprites {
        // 采样 4 个 src 像素(假设 sprite 也 SIMD 友好)
        let src = sample_4(sprite, x, y);
        dst = blend4_sse(src, dst);
    }

    // 写回
    _mm_storeu_si128(fb.pixels.as_ptr().add(dst_base) as *mut __m128i, dst);
}
```

### 2.7 边界处理:tile 不完整

如果屏幕宽 1920,64 不能整除(1920/64 = 30,正好),那 1921 就有 1 列剩余。两种处理:

- **方案 A**:补全 tile,边缘 mask
- **方案 B**:边缘 tile 用更小的尺寸(比如 64×56)

Casey 选 A,代码简洁。

### 2.8 多线程准备(为 Day 122+ 铺垫)

tile 之间独立,可以分给多线程:

```rust
// 单线程版
for tile in tiles { render_tile(tile); }

// 多线程版(Day 122+ 详谈)
let tiles: Vec<_> = (0..tiles_x*tiles_y).collect();
tiles.par_iter().for_each(|&i| render_tile(i));  // rayon 风格
```

`par_iter` 是 rayon crate 提供的"自动并行"。Casey 在 Day 122+ 手写 work queue,不用 rayon(教学目的)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

tile-based 渲染是游戏行业的"事实标准"。但 tile 在不同层级:

- **软渲染**(Casey Day 1-234):CPU tile(本日)
- **GPU tile-based**:移动 GPU(Mali / Adreno / Apple)硬件 tile,叫 Tile-Based Deferred Rendering(TBDR)
- **GPU immediate-mode**:桌面 GPU(NVIDIA / AMD)不是 tile-based,直接扫描线

casey 选 CPU tile 因为他在做软渲染。Phase 5+ 切 GPU 后,你看 OpenGL 的 `glScissor` + viewport 可以模拟 tile,但意义不大。

#### 64×64 vs 8×8 vs 128×128

不同引擎选不同 tile 大小:

- **Larrabee / Intel integrated GPU**(2010s):128×128(因为 L1 大)
- **Mali GPU**:16×16(嵌入式 GPU,L1 小)
- **Apple M1 GPU**:32×32
- **CPU 软渲染**(Casey):64×64

64×64 是 CPU 软渲染的"黄金值"。

### 3.2 · 🎨 图形学视角

tile-based 渲染在图形学的好处:

1. **cache 友好**:tile 数据驻留 L1
2. **可并行**:tile 独立
3. **early-Z**:tile 内可以预先做深度测试,丢弃被遮挡像素
4. **deferred shading**:tile 内可以收集所有 light,一次算(节省 overdraw)

#### 移动 GPU TBDR

手机 GPU(Mali、Adreno、Apple)用硬件 tile-based:

- framebuffer 实际上不在 DRAM,而在 chip 上的 fast memory(叫 tile memory)
- 每个 tile 渲染完才写回 DRAM
- 大幅减少 DRAM 带宽(省电)

CPU 软渲染 tile-based 的思路完全一致,只是 tile memory 是 L1。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上 tile-based 渲染的相关工具:

- **`pixman`**:X11 / Cairo 的底层像素操作,内部有 tile-based 实现
- **Mesa 3D**:OpenGL / Vulkan 实现,软渲染 fallback 是 tile-based
- **LLVMpipe**:Mesa 的软渲染器,完全 tile-based,大量 SIMD。读源码可以学 Casey 之外的另一种 tile 实现

```bash
# 装 LLVMpipe
sudo pacman -S mesa  # 默认就有

# 强制用软渲染跑 OpenGL 程序
LIBGL_ALWAYS_SOFTWARE=1 ./your_opengl_app
```

- **空间局部性** —— 相邻像素常共享数据,把它们放一起处理

## 5 · 对照与变奏

### 同一渲染在不同硬件

| 硬件 | 渲染方式 |
|---|---|
| CPU 软渲染(Casey) | tile-based SIMD |
| GPU 桌面(NVIDIA/AMD) | immediate-mode,大量线程 |
| GPU 移动(Mali/Adreno) | hardware tile(TBDR) |
| 集成 GPU(Intel) | tile-based(LLVMPipe 软渲染 fallback) |

每种硬件都有自己的"最优渲染架构"。Casey 的 tile 思想在所有架构里都体现,只是粒度不同。

### 历史演化

- **1980s 软渲染**:扫描线
- **1990s 软渲染**:tile-based 出现(Quake 用过)
- **2000s GPU 普及**:桌面 GPU 走 immediate-mode
- **2010s 移动 GPU**:TBDR 主流
- **2020s 软渲染复兴**:WebAssembly 让软渲染再次有意义(browser 软渲染)

## 8 · Rust / Arch 落地代码

### Rust:tile-based 渲染骨架

```rust
use std::arch::x86_64::*;

const TILE_SIZE: usize = 64;

pub struct Framebuffer {
    pub width: usize,
    pub height: usize,
    pub pixels: Vec<u32>,
}

impl Framebuffer {
    pub fn new(w: usize, h: usize) -> Self {
        // 补齐到 tile 边界
        let w_padded = (w + TILE_SIZE - 1) / TILE_SIZE * TILE_SIZE;
        let h_padded = (h + TILE_SIZE - 1) / TILE_SIZE * TILE_SIZE;
        Self { width: w, height: h, pixels: vec![0; w_padded * h_padded] }
    }
}

pub struct Sprite {
    pub x: i32,
    pub y: i32,
    pub w: usize,
    pub h: usize,
    pub pixels: Vec<u32>,
}

impl Sprite {
    pub fn intersects(&self, tx: usize, ty: usize, ts: usize) -> bool {
        let tile_right = (tx + ts) as i32;
        let tile_bottom = (ty + ts) as i32;
        let sprite_right = self.x + self.w as i32;
        let sprite_bottom = self.y + self.h as i32;
        !(self.x >= tile_right || sprite_right <= tx as i32
          || self.y >= tile_bottom || sprite_bottom <= ty as i32)
    }
}

pub fn render(fb: &mut Framebuffer, sprites: &[Sprite]) {
    let tiles_x = (fb.width + TILE_SIZE - 1) / TILE_SIZE;
    let tiles_y = (fb.height + TILE_SIZE - 1) / TILE_SIZE;
    for ty in 0..tiles_y {
        for tx in 0..tiles_x {
            let tile_x = tx * TILE_SIZE;
            let tile_y = ty * TILE_SIZE;
            // 找出与此 tile 相交的 sprite
            let relevant: Vec<&Sprite> = sprites.iter()
                .filter(|s| s.intersects(tile_x, tile_y, TILE_SIZE))
                .collect();
            // 在 tile 内 SIMD 处理
            for py in 0..TILE_SIZE {
                for px in (0..TILE_SIZE).step_by(4) {
                    let x = tile_x + px;
                    let y = tile_y + py;
                    if x + 4 > fb.width || y >= fb.height { continue; }
                    unsafe { render_4_pixels(fb, x, y, &relevant); }
                }
            }
        }
    }
}

#[target_feature(enable = "sse2")]
unsafe fn render_4_pixels(fb: &mut Framebuffer, x: usize, y: usize, sprites: &[&Sprite]) {
    let dst_idx = y * fb.width + x;
    let mut dst = _mm_loadu_si128(fb.pixels.as_ptr().add(dst_idx) as *const __m128i);

    for sprite in sprites {
        // 采样 sprite 在 (x..x+4, y) 的 4 像素
        let sx = x as i32 - sprite.x;
        let sy = y as i32 - sprite.y;
        if sx >= 0 && sy >= 0 && sx + 4 <= sprite.w as i32 && sy < sprite.h as i32 {
            let src_idx = sy as usize * sprite.w + sx as usize;
            let src = _mm_loadu_si128(sprite.pixels.as_ptr().add(src_idx) as *const __m128i);
            dst = blend4_sse(src, dst);
        }
    }

    _mm_storeu_si128(fb.pixels.as_ptr().add(dst_idx) as *mut __m128i, dst);
}

#[target_feature(enable = "sse2")]
unsafe fn blend4_sse(src: __m128i, dst: __m128i) -> __m128i {
    // 简化版,只处理不透明像素
    let alpha = _mm_srli_epi32(src, 24);
    let mask_full = _mm_cmpeq_epi32(alpha, _mm_set1_epi32(255));
    _mm_blendv_epi8(dst, src, mask_full)
}
```

## 10 · 深度推导:为什么是 64×64 tile?

Casey 在 marathon 里选 64×64 tile,不是拍脑袋。这一节我们把这个尺寸推导出来——从 cache、SIMD 宽度、并行度三个维度交叉验证。

### 10.1 维度 1:Cache 行宽 + tile 内访问模式

L1 cache 行是 64 字节。一行 BGRA 像素 4 字节,16 像素 = 1 cache 行。

如果你的 tile 宽是 16 像素的倍数,每行 tile 数据正好整 cache 行。tile 宽 32(2 cache 行)、64(4 cache 行)、128(8 cache 行)都是合理选择。

如果你用 tile 64×64,那 tile 一行是 64×4 = 256 字节 = 4 cache 行。CPU L1 cache 通常是 32 KB(8-way,64 set),每 set 8 路组相联。256 字节 = 4 cache 行,加 dst 4 cache 行 + src 4 cache 行 = 12 cache 行,远小于 set 容量。**无 conflict miss**。

如果 tile 太大(比如 256×256),tile 一行 1024 字节,跨多个 cache set,容易触发 conflict miss。

### 10.2 维度 2:SIMD lane 宽度

SSE 是 16 字节 = 4 像素。tile 宽 64 = 16 个 SSE chunk / 行。整数倍——所有 SIMD 操作都对齐,不需要尾部 mask。

如果 tile 宽 65,每行最后一个 SSE chunk 是 1 像素有效 + 3 像素浪费。**整个 tile 边界 mask 处理就是 64 边界 + 尾部 1 像素**——简单。

AVX 32 字节 = 8 像素。tile 宽 64 = 8 AVX chunk / 行,整数倍。AVX-512 64 字节 = 16 像素,tile 宽 64 = 4 chunk / 行。**64 是各种 SIMD 宽度的公倍数**。

### 10.3 维度 3:并行度

你后面 Day 122-125 把 tile 分发到多线程。8 核 CPU,你想要至少 8 tile / 帧保证每核忙。1920×1080 屏幕,tile 64×64,共 30×17 = 510 tile。每核 ~64 tile,够分。

如果 tile 太大(256×256),只有 30 tile,不够 8 核平均分。

如果 tile 太小(16×16),1280×720 = 3600 tile。每 tile 启动开销(atomic fetch_add)开始吃 CPU。Tile 64 在 8 核机器上是 sweet spot。

### 10.4 推导结论:64×64 的合理性

| 维度 | 64×64 表现 | 评价 |
|---|---|---|
| L1 cache 局部性 | 12 KB/tile,完全在 L1 | 优秀 |
| SIMD 对齐 | 64 = 4/8/16 像素整数倍 | 优秀 |
| 并行度 | 1080p = 510 tile | 优秀 |
| 启动开销 | 510 tile,500ns/op × 510 = 0.25ms | 可接受 |

**反例**:tile 太小(8×8 = 64 像素)。L1 浪费(SIMD 一次 4 像素,8/4=2 chunk,setup overhead 占比高)。并行度爆炸(1080p = 32400 tile),atomic fetch_add 队列操作吃 CPU。

**反例**:tile 太大(128×128)。L1 紧张(64 KB/tile),conflict miss 多。并行度变差(1080p = 128 tile,8 核每核 16 tile,够但启动开销大)。

64×64 是经过实验验证的 sweet spot,Casey 不是猜的,是测出来的。

## 11 · 实战:完整 tile 渲染伪代码

我们把 Day 121 的整个流水线用 Rust 伪代码完整表达,你看完整流程:

```rust
const TILE_SIZE: usize = 64;
const SCREEN_W: usize = 1920;
const SCREEN_H: usize = 1080;
const TILES_X: usize = SCREEN_W / TILE_SIZE;
const TILES_Y: usize = SCREEN_H / TILE_SIZE;

/// 渲染一帧
pub fn render_frame(assets: &Assets, camera: &Camera, framebuffer: &mut Framebuffer) {
    // Phase 1:把屏幕切成 tile,放进工作队列
    let queue = WorkQueue::new();
    for ty in 0..TILES_Y {
        for tx in 0..TILES_X {
            queue.push(RenderTileJob {
                tile_x: tx,
                tile_y: ty,
                camera: camera.clone(),
                asset_ids: assets.visible_in_tile(tx, ty),
            });
        }
    }

    // Phase 2:worker 线程并行处理
    let framebuffer_ptr = AtomicPtr::new(framebuffer.as_mut_ptr());
    let queue = Arc::new(queue);
    let mut workers = vec![];
    for _ in 0..num_cpus::get() {
        let q = Arc::clone(&queue);
        let fb = framebuffer_ptr.load(Ordering::Relaxed);
        workers.push(std::thread::spawn(move || {
            worker_loop(q, fb);
        }));
    }

    // Phase 3:等所有 worker 完成
    queue.mark_complete(TILES_X * TILES_Y);
    for w in workers {
        w.join().unwrap();
    }
}

fn worker_loop(queue: Arc<WorkQueue>, fb: *mut u32) {
    while let Some(job) = queue.pop() {
        render_tile(job, fb);
        queue.decrement_remaining();
    }
}

fn render_tile(job: RenderTileJob, fb: *mut u32) {
    // tile 内 64×64 = 4096 像素
    // 按 4 像素 SSE chunk 处理,共 1024 chunk
    for local_y in 0..TILE_SIZE {
        let global_y = job.tile_y * TILE_SIZE + local_y;
        let row_start = (global_y * SCREEN_W + job.tile_x * TILE_SIZE) as isize;

        // 一行 64 像素 = 16 SSE chunk
        for cx in 0..16 {
            let global_x = job.tile_x * TILE_SIZE + cx * 4;
            let chunk_offset = row_start + (cx * 4) as isize;

            // 收集 4 像素的 src 颜色(查 sprite / texture)
            let src_chunk = sample_textures_4px(assets, global_x, global_y);
            // 读 4 像素的 dst
            let dst_chunk = unsafe { _mm_loadu_si128(fb.offset(chunk_offset) as *const __m128i) };
            // SIMD blend
            let result = unsafe { blend_4_masked(src_chunk, dst_chunk) };
            // 写回
            unsafe { _mm_storeu_si128(fb.offset(chunk_offset) as *mut __m128i, result); }
        }
    }
}
```

这是马拉松的**最终形态**——Day 112-125 的所有知识在这里融合。每个细节背后都是前 14 天的某天讨论的:

- `_mm_loadu_si128` — Day 113-114 学的对齐 / 非对齐 load
- `blend_4_masked` — Day 117-118 的 mask blend
- 4 像素 chunk = 1 SSE 寄存器 — Day 116 的 SIMD 像素布局
- 64×64 tile — 今天推导的尺寸
- `Arc<WorkQueue>` — Day 122-125 的 lock-free 队列
- worker thread — Day 122-125 的多线程

## 12 · Casey 在马拉松里做的关键决策

Casey 在 Day 121 这集做了 6 个关键架构决策。每个决策背后都有"为什么不选另一种方案"的深思熟虑:

### 决策 1:Tile 是静态的 vs 动态的

**静态**:屏幕固定切成 64×64 tile,每帧 reuse。
**动态**:按绘制内容动态切(比如同色区域合成一个大 tile)。

Casey 选静态——简单、可预测、不依赖内容。动态 tile 在某些游戏上(Q3 BSP)有用,但 Handmade Hero 这种"sprite + 摄像机移动"场景,静态足够。

### 决策 2:Tile 边界 vs 全屏 SIMD

**Tile 边界**:每 tile 独立 SIMD 渲染,边界天然对齐。
**全屏 SIMD**:整屏幕一行一行 SIMD,行边界 mask。

Casey 选 tile 边界——多线程友好(全屏 SIMD 难并行)。代价是每 tile 启动开销,但 64×64 tile 的开销占比 < 5%。

### 决策 3:Z-buffer vs painter sort

**Z-buffer**:每像素存深度,blend 时比较。
**Painter sort**:按深度排序 sprite,从后往前画。

Casey 选 painter sort——Handmade Hero 是 2D,深度排序简单。Z-buffer 多 4 byte/pixel 内存 + 1 cmp/blend,2D 没必要。3D 才需要 Z-buffer。

### 决策 4:Pixel format 是 BGRA vs RGBA

**BGRA**:G 是第二个字节,内存顺序和 SSE pshufb 配合好。
**RGBA**:R 是第一个字节,程序员直观。

Casey 选 BGRA——历史上 Windows GDI 用 BGRA,可以 blit 不转换。现代 Linux 也广泛接受 BGRA。

### 决策 5:Premultiplied alpha vs straight alpha

**Premultiplied**:RGB 已经乘了 alpha,blend 时少 1 次 mul。
**Straight**:RGB 没乘,blend 时算 src*alpha + dst*(1-alpha)。

Casey 选 premultiplied——少 25% 乘法,但 sprite 数据加载时要做一次 premultiply(可预计算)。Day 134+ 资产系统支持 premultiplied。

### 决策 6:Render to offscreen tile, then blit, vs render directly to framebuffer

**Offscreen tile**:tile 有自己的小 framebuffer,渲染完后 memcpy 到主 fb。
**Direct**:直接写主 fb。

Casey 选 direct——少一次 memcpy。代价是 tile 边界不能 over-bleed(否则污染邻居)。Day 121 marathon 里 tile 边界严格控制在 64×64,不溢出。

这 6 个决策每个都值得 1 天讨论。Marathon 视频里 Casey 花了大量时间讲"为什么不选另一种",这是工程教育的金矿——比"我选了 X"重要得多的是"我没选 Y 因为 Z"。

## 13 · Tile 渲染的历史演化

Tile-based rendering 不是 Casey 发明的。它是 GPU 工业的核心技术。

### 13.1 Larrabee(2008)

Intel 的 Larrabee 项目(后来变成 Xeon Phi)首次把"tile + SIMD + 多线程"用于 GPU。Larrabee 用 x86 核心 + 512-bit SIMD(早期 AVX-512 雏形),每个核心跑 tile 渲染。

Larrabee 失败了(变成 HPC,不进 GPU 市场),但留下思想:GPU 不必是固定功能,可以是"通用 CPU + 宽 SIMD + tile"。

### 13.2 Mali / Adreno / Apple GPU(移动 GPU)

PowerVR(2003)、Mali、Adreno、Apple GPU 全部是 **Tile-Based Deferred Rendering(TBDR)**。它们把屏幕切成 tile(通常 16×16 或 32×32),先在片上 SRAM 渲染 tile,完成后才写到主存。

TBDR 的核心收益:**省主存带宽**。手机带宽功耗大,每省一次主存访问省 100 mW。手机 GPU 用 TBDR 把带宽降到传统 GPU 的 1/4。

### 13.3 LLVMpipe(桌面软渲染)

Mesa 的 LLVMPipe 是 Linux 桌面"没有 GPU 时的软渲染"。它用 LLVM JIT 生成 SIMD 代码,跑 tile 渲染。性能远不如 GPU 但够 GNOME 桌面用。

Casey 的 day121 跟 LLVMPipe 思路几乎一样——只是 Casey 手写 SIMD,LLVMPipe 让 LLVM 自动生成。两条路殊途同归:都是 tile + SIMD + 多线程。

### 13.4 现代 GPU 的 tile

桌面 GPU(RTX / Radeon)不是 TBDR,是 **Immediate Mode Renderer(IMR)**——直接全屏渲染。但内部仍用 tile 概念做缓存(tile-sized L1 / L2)。这是 IMR + 内部 tile cache 的混合架构。

学完 Day 121,你看 GPU 文档(Mali TBDR / Apple GPU / NVIDIA Tile Cache)立刻秒懂。这就是"软渲染基础"对"GPU 工程师"的价值。
