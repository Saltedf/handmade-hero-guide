
# Day 152 · 新 Win32 文件 API 实现

> Day 151 设计了 FileApi trait。Casey 在 Win32 上实现它,包装 `CreateFileW`/`ReadFile`/`GetFileSizeEx`/`CloseHandle`。本日在 Rust + Linux 视角下是个"反向对照":Casey 怎么在 Windows 上做事,Linux 上对应什么 syscall,为什么 Casey 选这些 API 而不是其他。

## 0 · 为什么要有这一天

Windows 和 Linux 的文件 API 看起来一样(都是 open/read/write/close),实际有 5 个深刻差异:

1. **路径编码**:Windows 用 UTF-16(`wchar_t*`),Linux 用 UTF-8(`char*`)。Rust `Path` 内部是 `OsStr`,跨平台。
2. **错误返回**:Windows API 返回 `BOOL` 或 `DWORD`,详细错误要 `GetLastError()`。Linux 直接返 -1 + errno。Rust `Result` 抽象掉。
3. **handle 类型**:Windows `HANDLE`(opaque pointer),Linux `int fd`(< 1024)。
4. **异步**:Windows IOCP(complex),Linux io_uring(更 modern)。Rust 异步运行时抽象。
5. **文件锁**:Windows LockFile/LockFileEx,Linux fcntl(F_SETLK)。

Casey 今天写 Win32 实现,我们 Rust + Linux 用户的关键学习是:

- **Rust `std::fs` 已经把这一切抽象掉了**——你写 `File::open(path)`,Rust 在 Windows 上调 `CreateFileW`,在 Linux 上调 `open(2)`
- **但理解底层很重要**——你的代码出问题时,你要知道看 Windows API 文档还是 Linux man page

心理锚点:看完今天,你能解释 Windows 和 Linux 文件 API 的 3 个关键差异,知道为什么 Rust `std::fs::File` 是 cross-platform 抽象。

## 1 · Casey 今天做了什么

Casey 写 Win32 实现 `platform_file_api`:

```c
static PLATFORM_OPEN_FILE(Win32OpenFile) {
    HANDLE h = CreateFileW(
        wide_path,                // LPWSTR
        GENERIC_READ,             // 读权限
        FILE_SHARE_READ,          // 允许其他进程读
        0,                        // security attrs
        OPEN_EXISTING,            // 必须已存在
        FILE_ATTRIBUTE_NORMAL,    // 普通属性
        0                         // template handle
    );
    if (h == INVALID_HANDLE_VALUE) return 0;
    return (platform_file_handle)h;
}

static PLATFORM_READ_FILE(Win32ReadFile) {
    DWORD bytes_read;
    if (ReadFile((HANDLE)h, buf, size, &bytes_read, 0)) {
        return bytes_read;
    }
    return 0;
}

// ... GetFileSizeEx / CloseHandle / WriteFile
```

视频里 Casey 解释每个 flag 的含义:

- **`GENERIC_READ`** —— 读权限(对应 Linux `O_RDONLY`)
- **`FILE_SHARE_READ`** —— 允许其他进程同时读(Linux 默认就允许)
- **`OPEN_EXISTING`** —— 文件必须已存在(对应 `O_RDONLY` 不含 `O_CREAT`)
- **`FILE_ATTRIBUTE_NORMAL`** —— 无特殊属性

Casey 还提到几个 Windows 特有坑:

- **路径前缀 `\\?\`**:绕过 MAX_PATH(260 字符)限制,但要求绝对路径
- **UTF-16 BOM**:有些工具会加 BOM,代码要识别
- **file locking on Windows**:默认独占,要 `FILE_SHARE_*` 才共享

## 2 · 心智模型

### 类比:同样的菜,不同厨房

你要做"番茄炒蛋"。一个厨房(Windows)用电气炉、不粘锅、单手铲;另一个(Linux)用煤气炉、铁锅、双手铲。原料一样,工具不同,做出来的菜一样。

文件操作也是:抽象上都是"打开/读/写/关",但 Windows 和 Linux 的具体 API 工具不同。

### 严谨模型:Windows vs Linux 文件 API 对照

| 操作 | Windows | Linux | Rust |
|---|---|---|---|
| Open | `CreateFileW(path, access, share, ...)` | `open(path, flags, mode)` | `File::open` / `File::create` |
| Read | `ReadFile(h, buf, n, &out, overlapped)` | `read(fd, buf, n)` | `Read::read` |
| Write | `WriteFile(h, buf, n, &out, overlapped)` | `write(fd, buf, n)` | `Write::write` |
| Seek | `SetFilePointerEx(h, li, &out, method)` | `lseek(fd, off, whence)` | `Seek::seek` |
| Sync | `FlushFileBuffers(h)` | `fsync(fd)` | `File::sync_all` |
| Size | `GetFileSizeEx(h, &li)` | `fstat(fd, &st); st.st_size` | `Metadata::len` |
| Close | `CloseHandle(h)` | `close(fd)` | `Drop` 自动 |
| Async | IOCP (`ReadFileEx`+OVERLAPPED) | `io_uring` / `aio` | `tokio::fs` |

**关键差异**:

1. **Windows handle 是 pointer**(64-bit),Linux fd 是 int(通常 < 1024)
2. **Windows 错误码**用 `GetLastError()`,Linux 用 `errno`(thread-local)
3. **Windows 异步**是 callback 风格,Linux 是 completion queue

### Windows 路径与 UTF-16

Windows API 有两个版本:`CreateFileA`(ANSI / UTF-8)和 `CreateFileW`(Wide / UTF-16)。推荐 W 版本,因为:

- ANSI 版本受 locale 限制(不同地区行为不同)
- Wide 版本总是 UTF-16,一致

Rust 标准 `File::open(path)` 在 Windows 上自动转 UTF-16:

```rust
let path = std::path::Path::new("café.txt");
let file = std::fs::File::open(path)?;
// Rust 内部转 CreateFileW(L"café.txt" as UTF-16)
```

`Path` 内部用 `OsStr`,在 Windows 上是 WTF-8(允许 surrogate pairs),在 Linux 上是 bytes。Rust 把所有平台差异封了。

### Linux 文件描述符(fd)

Linux 内核为每个进程维护一个 **fd table**:

```
fd 0 → stdin
fd 1 → stdout
fd 2 → stderr
fd 3 → (第一个 open 的文件)
fd 4 → ...
```

`open` 返回新 fd(从 3 开始)。`close(fd)` 释放,该 fd 数字可被下次 open 复用。

**fd limit**:每个进程默认 1024(`ulimit -n`)。游戏开几千个文件可能撞限。解决:

```bash
ulimit -n 65536  # 当前 shell
# 或永久:/etc/security/limits.conf
```

Windows handle 没这个限制(用 64-bit pointer)。

### IOCP vs io_uring

异步 I/O 的两个流派:

**Windows IOCP**(1995+):

- 提交"读请求"到 completion port
- 完成后内核把结果放到队列
- 应用从队列消费
- 适合服务器(大量并发连接)

**Linux io_uring**(2019+,kernel 5.1+):

- 共享两个 ring buffer(SQ 提交,CQ 完成)
- 零拷贝、批量提交
- 比 IOCP 性能高 30-50%
- Rust crate `tokio-uring` / `rio`

游戏文件 I/O 量级不大,异步通常用线程池模拟(tokio 风格),不直接用 IOCP/io_uring。Casey 也是同步 + 工作线程。

## 3 · 四域深入

### 3.1 · 游戏编程视角

跨平台游戏引擎的文件 API 抽象:

- **Unreal**:`IPlatformFile`(接口)+ `FPhysicalFileSystemFile` / `FPakFile`(实现)
- **Unity**:`AssetBundle` + 平台 backend
- **Bevy**:直接 `std::fs`(简单粗暴,Web 用 `bevy_asset`)
- **HH**:platform_file_api struct

抽象的目标一致:**游戏代码不关心底层 OS**。

### 3.2 · Linux 系统编程视角

Linux syscall 直击:

```c
// 直接 syscall(绕过 libc)
long fd = syscall(SYS_open, "/path", O_RDONLY);
long n = syscall(SYS_read, fd, buf, size);
syscall(SYS_close, fd);
```

或通过 libc:

```c
int fd = open("/path", O_RDONLY);
ssize_t n = read(fd, buf, size);
close(fd);
```

Rust 标准库用 libc 路径(`std::fs::File::open` → `libc::open`)。

### 3.3 · Rust 生态视角

Rust 的 `std::fs`:

```rust
use std::fs::File;
let f = File::open("foo.txt")?;
// 在 Windows:CreateFileW
// 在 Linux:open(2)
// 在 macOS:open(2)(同 BSD)
```

`File::open` 内部:

```rust
// 简化
pub fn open(path: &Path) -> io::Result<File> {
    let file = sys::fs::File::open(path)?;  // 平台特定
    Ok(File { file })
}
```

`sys::fs::File` 在 Windows 上是 `std::sys::windows::fs::File`,调 `CreateFileW`。在 Unix 上是 `std::sys::unix::fs::File`,调 `open(2)`。

这就是 Rust 的"零开销跨平台抽象":你的代码一份,Rust 自动选择 OS 实现。

### 3.4 · 性能视角

文件 I/O 性能关键:

- **buffer 大小**:`read`/`write` syscall 每次固定开销 ~1μs。buffer 太小(如 1B)syscall 频繁。推荐 4-64 KB。
- **顺序 vs 随机**:HDD 随机慢 100x,SSD 慢 2-10x。设计访问模式尽量顺序。
- **page cache**:重复读同一文件,第二次走 cache,几乎免费。
- **mmap**:大文件只读 mmap 最快(内核管 cache)。

游戏加载策略:

- 启动时大块顺序读(< 100ms)
- 运行时按需小读(每 asset 几 KB)
- 用 mmap 整个 .hha 是最优(常驻 page cache)

## 5 · 对照与变奏

### 错误处理对比

| | Windows | Linux | Rust |
|---|---|---|---|
| API 返回 | BOOL / INVALID_HANDLE_VALUE | -1 | `Result` |
| 错误详情 | `GetLastError()` → DWORD | `errno`(thread-local) | `io::Error` |
| 错误码 | Win32 error codes(WinError.h) | errno constants(E*宏) | `io::ErrorKind` |

Rust 把所有平台错误码统一映射到 `io::ErrorKind`(NotFound, PermissionDenied, ...)。

### 文件锁

| | Windows | Linux |
|---|---|---|
| 共享锁(读) | `LockFileEx(LOCKFILE_EX_FAIL_IMMEDIATELY \| LOCKFILE_EX_SHARED_LOCK)` | `fcntl(F_SETLK, struct flock l_type=F_RDLCK)` |
| 独占锁(写) | `LockFileEx(... \| LOCKFILE_EX_EXCLUSIVE_LOCK)` | `l_type=F_WRLCK` |
| 自动释放 | 进程退出 | 进程退出或显式 unlock |

Linux 的 fcntl 锁是 advisory(其他进程不强制遵守),Windows 的 LockFile 是 mandatory(其他进程 open 失败)。

### 异步 I/O 历史

| 时代 | Windows | Linux |
|---|---|---|
| 1990s | overlapped I/O | select/poll(只通知) |
| 2000s | IOCP | AIO(不好用) |
| 2010s | IOCP | epoll(只通知) |
| 2020s | IOCP + io_uring(WSA) | io_uring |

Linux io_uring 是 2019 后的革命,让 Linux 异步 I/O 第一次达到 / 超过 Windows IOCP。

### Lv1 · 概念辨析

**题**:Windows 用 UTF-16,Linux 用 UTF-8。Rust 的 `String` / `PathBuf` 用什么?为什么不会出问题?

**参考解答**:Rust `String` 是 UTF-8。`PathBuf` 内部是 `OsString`,在 Linux 上是 bytes(任何字节,因为 Linux 文件名是 bytes),在 Windows 上是 UTF-16(`Vec<u16>`)。

调用 `File::open(path)` 时:

- Linux:`OsStr::as_bytes()` → 传给 `open(2)`
- Windows:`OsStr::encode_wide()` → 传给 `CreateFileW`

Rust 把平台差异封装在 `OsStr` 内部。你的代码用 `&str` 或 `&Path`,自动正确转换。

## 8 · Rust / Arch 落地代码

Linux 版 FileApi 实现对比 Windows API(教学用):

```rust
use std::fs::File;
use std::io::{Read, Seek, SeekFrom};
use std::os::unix::io::AsRawFd;

/// Linux 文件 API,直接对应 Win32 函数
pub struct LinuxFile {
    inner: File,
}

impl LinuxFile {
    /// 对应 Win32 CreateFileW(GENERIC_READ, OPEN_EXISTING)
    pub fn open_read(path: &str) -> std::io::Result<Self> {
        let f = File::open(path)?;
        Ok(Self { inner: f })
    }

    /// 对应 Win32 CreateFileW(GENERIC_WRITE, CREATE_ALWAYS)
    pub fn create_write(path: &str) -> std::io::Result<Self> {
        let f = std::fs::OpenOptions::new()
            .write(true)
            .create(true)
            .truncate(true)
            .open(path)?;
        Ok(Self { inner: f })
    }

    /// 对应 Win32 ReadFile
    pub fn read(&mut self, buf: &mut [u8]) -> std::io::Result<usize> {
        self.inner.read(buf)
    }

    /// 对应 Win32 WriteFile
    pub fn write(&mut self, buf: &[u8]) -> std::io::Result<usize> {
        use std::io::Write;
        self.inner.write(buf)
    }

    /// 对应 Win32 SetFilePointerEx
    pub fn seek(&mut self, offset: u64) -> std::io::Result<u64> {
        self.inner.seek(SeekFrom::Start(offset))
    }

    /// 对应 Win32 GetFileSizeEx
    pub fn size(&self) -> std::io::Result<u64> {
        Ok(self.inner.metadata()?.len())
    }

    /// 对应 Win32 FlushFileBuffers
    pub fn flush(&self) -> std::io::Result<()> {
        self.inner.sync_all()
    }

    /// 对应 Win32 CloseHandle(隐式 Drop)
    pub fn raw_fd(&self) -> i32 {
        self.inner.as_raw_fd()  // 对应 HANDLE 转 int
    }
}

/// 当 Drop 时自动 close(对应 CloseHandle)
impl Drop for LinuxFile {
    fn drop(&mut self) {
        // self.inner 是 File,自动 close
        // 等价 close(fd) syscall
    }
}

fn main() {
    // Linux 等价 Win32 CreateFileW
    let mut f = LinuxFile::open_read("/etc/hostname").expect("open");
    println!("fd = {}", f.raw_fd());
    println!("size = {}", f.size().unwrap());

    // ReadFile
    let mut buf = [0u8; 64];
    let n = f.read(&mut buf).unwrap();
    let s = std::str::from_utf8(&buf[..n]).unwrap().trim();
    println!("content: {:?}", s);

    // Drop 时自动 close
}
```

### A.5 Phase 4 的核心概念回顾

Phase 4 涉及的核心概念:

**1. Ownership + borrowing**:
- 编译时保证无 use-after-free

**2. RAII(Drop)**:
- 资源自动释放
- 无 double-free 风险

**3. Trait 抽象**:
- 接口稳定
- 多态安全

**4. Atomic / Arc**:
- 多线程共享
- 零开销

**5. Error handling(Result)**:
- 显式错误
- 类型安全

**6. Memory allocator**:

### A.7 工业 Rust 代码示例

让我提供一个具体的工业 Rust 代码示例,综合 phase-4 的概念:

```rust
use std::sync::Arc;
use std::sync::RwLock;
use std::collections::HashMap;
use std::path::Path;

/// Asset storage with sharded locking and async loading.
pub struct AssetStorage<T> {
    shards: Vec<RwLock<HashMap<u32, Arc<T>>>>,
    loader: Box<dyn Fn(u32) -> Result<T, AssetError> + Send + Sync>,
}

impl<T: Send + Sync + 'static> AssetStorage<T> {
    pub fn new<F>(loader: F) -> Self
    where
        F: Fn(u32) -> Result<T, AssetError> + Send + Sync + 'static,
    {
        let num_shards = 16;
        let mut shards = Vec::with_capacity(num_shards);
        for _ in 0..num_shards {
            shards.push(RwLock::new(HashMap::new()));
        }
        Self {
            shards,
            loader: Box::new(loader),
        }
    }
    
    pub fn get(&self, id: u32) -> Result<Arc<T>, AssetError> {
        let shard_idx = (id as usize) % self.shards.len();
        
        // Fast path: read lock
        {
            let shard = self.shards[shard_idx].read().unwrap();
            if let Some(asset) = shard.get(&id) {
                return Ok(Arc::clone(asset));
            }
        }
        
        // Slow path: load and insert
        let asset = (self.loader)(id)?;
        let arc = Arc::new(asset);
        
        let mut shard = self.shards[shard_idx].write().unwrap();
        let entry = shard.entry(id).or_insert(Arc::clone(&arc));
        Ok(Arc::clone(entry))
    }
    
    pub fn evict_unused(&self) {
        for shard in &self.shards {
            let mut shard = shard.write().unwrap();
            shard.retain(|_, arc| Arc::strong_count(arc) > 1);
        }
    }
}

#[derive(Debug)]
pub enum AssetError {
    NotFound(u32),
    Io(std::io::Error),
    Invalid(String),
}

// 用法
fn main() {
    let storage: AssetStorage<Vec<u8>> = AssetStorage::new(|id| {
        Ok(vec![id as u8; 100])
    });
    
    let a = storage.get(42).unwrap();
    let b = storage.get(42).unwrap();
    assert!(Arc::ptr_eq(&a, &b));
}
```

这是工业级 Rust asset storage 的完整骨架——分桶 RwLock + Arc + lazy loading + eviction。

use std::sync::{Arc, RwLock};
use std::collections::HashMap;
use std::path::{Path, PathBuf};

// === Arena allocator ===
pub struct Arena {
    buffer: Vec<u8>,
    offset: usize,
}

impl Arena {
    pub fn new(capacity: usize) -> Self {
        Self {
            buffer: vec![0u8; capacity],
            offset: 0,
        }
    }
    
    pub fn alloc<T>(&mut self, value: T) -> &mut T {
        let size = std::mem::size_of::<T>();
        let align = std::mem::align_of::<T>();
        
        // Align offset
        let aligned_offset = (self.offset + align - 1) & !(align - 1);
        self.offset = aligned_offset + size;
        
        assert!(self.offset <= self.buffer.len(), "arena overflow");
        
        let ptr = unsafe { self.buffer.as_mut_ptr().add(aligned_offset) as *mut T };
        unsafe { ptr.write(value) };
        unsafe { &mut *ptr }
    }
    
    pub fn reset(&mut self) {
        self.offset = 0;
    }
}

// === Asset Storage ===
pub struct AssetStorage<T: Send + Sync + 'static> {
    shards: Vec<RwLock<HashMap<u32, Arc<T>>>>,
    loader: Box<dyn Fn(u32) -> Result<T, AssetError> + Send + Sync>,
}

impl<T: Send + Sync + 'static> AssetStorage<T> {
    pub fn new<F>(loader: F) -> Self
    where F: Fn(u32) -> Result<T, AssetError> + Send + Sync + 'static {
        let mut shards = Vec::with_capacity(16);
        for _ in 0..16 {
            shards.push(RwLock::new(HashMap::new()));
        }
        Self { shards, loader: Box::new(loader) }
    }
    
    pub fn get(&self, id: u32) -> Result<Arc<T>, AssetError> {
        let shard_idx = (id as usize) % self.shards.len();
        {
            let shard = self.shards[shard_idx].read().unwrap();
            if let Some(a) = shard.get(&id) {
                return Ok(Arc::clone(a));
            }
        }
        let asset = (self.loader)(id)?;
        let arc = Arc::new(asset);
        let mut shard = self.shards[shard_idx].write().unwrap();
        let entry = shard.entry(id).or_insert(Arc::clone(&arc));
        Ok(Arc::clone(entry))
    }
}

#[derive(Debug)]
pub enum AssetError {
    NotFound(u32),
    Io(std::io::Error),
}

// === Particle system (parallel) ===
use rayon::prelude::*;

pub struct Particle {
    pub pos: [f32; 3],
    pub vel: [f32; 3],
    pub life: f32,
}

pub fn update_particles(particles: &mut [Particle], dt: f32, gravity: [f32; 3]) {
    particles.par_iter_mut().for_each(|p| {
        p.vel[0] += gravity[0] * dt;
        p.vel[1] += gravity[1] * dt;
        p.vel[2] += gravity[2] * dt;
        p.pos[0] += p.vel[0] * dt;
        p.pos[1] += p.vel[1] * dt;
        p.pos[2] += p.vel[2] * dt;
        p.life -= dt;
    });
}

// === Main ===

    let mut arena = Arena::new(1024);
    let x: &mut u32 = arena.alloc(42);
    println!("Arena allocated: {}", x);
    
    let storage: AssetStorage<String> = AssetStorage::new(|id| {
        Ok(format!("asset_{}", id))
    });
    let a = storage.get(1).unwrap();
    println!("Asset: {}", a);
    
    let mut particles: Vec<Particle> = (0..1000).map(|_| Particle {
        pos: [0.0; 3], vel: [0.0, 0.0, 1.0], life: 5.0,
    }).collect();
    update_particles(&mut particles, 0.016, [0.0, -9.8, 0.0]);
    println!("Updated {} particles", particles.len());
}
