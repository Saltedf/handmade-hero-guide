
# Day 141 · 分块流式加载大音频

> 一段 5 分钟的背景音乐,以 48 kHz / 16-bit / stereo 存储,约占 55 MB 内存。Casey 在 Day 138-140 把整段 WAV 一次性读进内存混音——但游戏里同时可能有 5 段 BGM、几十个 SFX,加起来轻松上 GB。今天要做的事:**只把"马上要播的几毫秒"留在内存里,其他按需从磁盘流式读取**。

## 0 · 为什么要有这一天

把游戏音乐"一次性加载"在小型 demo 里没问题,但放到真实游戏里立刻撞墙:

- 一个开放世界 RPG 可能有 200+ 段音乐,根据场景、剧情、战斗状态切换。你不能把全部 200 段都 load 进内存——光是占内存就让游戏跑不动。
- 一段过场动画配音可能有 30 秒到 5 分钟。玩家可能播到一半就跳过——预加载全部等于浪费带宽和内存。
- 玩家在不同地图间穿行,每张地图的环境音 (ambient) 是 10 分钟循环,你希望"切图时音乐无缝衔接"。

所有这些问题的共同答案是 **streaming**(流式加载):把音频切成等长的小块(chunk),**只在需要播放的前一刻才把这一块从磁盘读进内存**,播完就丢弃,留出位置给下一块。这是所有现代游戏引擎(Unreal、Unity、Godot)和媒体播放器(VLC、mpv)的标准做法。

今天 Casey 把 Day 140 已经能用的"整段 WAV → mixer"管线改造成"chunk 队列 → mixer"。改造过程中真正的难点不是代码,而是 **三个边界条件**:

1. **chunk 没及时读到位怎么办**(读盘比播放慢,会发生爆音/卡顿)
2. **chunk 大小怎么选**(太大 → 内存浪费 + 切换慢;太小 → I/O 调用频繁,CPU 开销大)
3. **音频循环怎么无缝**(最后一块和第一块要拼接得没有 click 声)

解决这三个问题需要理解 **生产者-消费者模型**、**double buffering**(双缓冲)、**音频帧的边界**(为什么不能从任意字节切)。这三个概念在游戏开发的资产管线、网络代码、GPU 上传里反复出现,所以今天虽然主题是音频,实际是在练一套通用工程模式。

心理锚点:看完今天,你能用 Rust 写出一个把任意大 WAV 文件按 100ms chunk 流式喂给 cpal 回调的程序,内存占用恒定在 ~1 MB,无论源文件多大。

## 1 · Casey 今天做了什么

Casey 的核心改动是把 Day 140 里的"一个 buffer 装整个 sound"换成"两块 buffer 来回 ping-pong":

1. 在 `loaded_sound` 结构里把"整段 samples"字段去掉,改成一个"已加载的字节数 + 文件句柄"
2. 引入 `audio_buffer` 数组,长度 2(buffer A 和 buffer B),每块约 16 kB(0.17 秒的音频)
3. 在混音循环里,当指针走到 buffer A 末尾时,**发起一个读盘请求**把下一块数据填进 buffer B;反过来也一样
4. 引入"prefetch"概念:不是走到末尾才发请求,而是在快到末尾(比如还有 30 ms)时就开始读,避免刚好卡在边界时还没读到
5. 把这套机制抽象成"output callback 发起 I/O 请求,某个 thread 异步执行读盘"的雏形——明天和 Day 165+ 会把异步部分完整化

Casey 在视频里反复强调一件事:**音频回调线程绝不能阻塞**。混音 callback 是被声卡时钟驱动的(每秒 480 次),里面任何阻塞(读盘、加锁、malloc)都会直接造成可闻的"哒"声——专业术语叫 **dropout**(掉帧)。所以读盘必须挪到另一条线程,音频线程只消费已经就绪的 chunk。

## 2 · 心智模型

### 类比:流水线工厂

想象一个面包店。顾客每秒来一个,要一个面包。如果你现烤(同步),顾客等 20 分钟,差评。所以你做了一对烤盘 A 和 B:

1. A 烤熟了开始卖
2. 顾客从 A 拿面包时,你同时往 B 里放面团
3. A 卖空,B 也烤好了——切换
4. 顾客从 B 拿,你往 A 里放面团
5. 循环

只要"放面团 + 烤"的时间 < 卖空一块的时间,顾客永远等不到。这就是 **double buffering** 的核心思想:**用两块缓冲区交替,把生产者的工作藏到消费者看不见的地方**。

音频流式加载就是这个面包店:

- 顾客 = 声卡(每秒 48000 个 sample 的速度消费)
- 面包 = 一帧 sample(16 bit stereo = 4 字节)
- 烤 = 从磁盘读 16 kB 的 chunk(~30 ms 在 HDD,~3 ms 在 NVMe)
- 烤盘 A/B = 两块 buffer

只要读盘时间 < 播放完一块的时间(30 ms < 170 ms),声卡永远不用等。

### 严谨模型:三个角色的节奏

把整个系统画出来:

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│  磁盘 / SSD  │ →  │ Ring Buffer  │ →  │ 声卡 (ALSA)  │
│ (生产者)    │     │ (缓冲池)     │     │ (消费者)     │
└─────────────┘     └──────────────┘     └──────────────┘
      异步                N 块                实时
   ~3 ms / 块         每块 ~170 ms         48000 Hz
```

**生产者(读盘线程)**:把 chunk 一块块塞进 ring buffer。
**消费者(音频线程)**:从 ring buffer 里拿数据往声卡推。
**ring buffer**:循环使用的内存数组,生产者写到 `head`,消费者从 `tail` 读,中间是有效数据。

环形缓冲区为什么是 lock-free 的最佳搭档?因为 **单个生产者 + 单个消费者** 的环形缓冲区可以只用两个原子整数(`head` 和 `tail`)实现无锁:`head` 只有生产者写,`tail` 只有消费者写,双方都读对方的值但只写自己的。这种模式叫 **SPSC queue**(single-producer single-consumer)。今天 Casey 用的是 Win32 CriticalSection(互斥锁)简化版,Day 144+ 会换成 SIMD,Day 166 会用真正的锁。

### 为什么 chunk 不能从任意字节切?

WAV 文件存的是 PCM 样本,每个样本是 16-bit(2 字节)。 stereo 是 4 字节一组 (L_low, L_high, R_low, R_high)。**你不能从字节 1 开始切**,那会把一个样本拦腰斩断,16-bit 整数会读出完全错误的值,产生爆裂噪声。

所以 chunk 的字节偏移必须是 **frame size 的整数倍**(mono=2,stereo=4,5.1=12)。这就是"音频 frame"的定义:**一个时间点上所有声道的样本集合**。

```
frame 0    frame 1    frame 2    ...
[L R]      [L R]      [L R]
4 bytes    4 bytes    4 bytes
```

每个 frame 4 字节,16 kB = 4096 frame,在 48 kHz 下 = 85.3 ms。所以 chunk 大小通常按 **2 的幂** 选(4096、8192、16384 frame),保证好做对齐和 SIMD。

### 三种边界情况

| 情况 | 现象 | 对策 |
|---|---|---|
| 读盘 > 播放 | 声卡等数据 → dropout | 增大 chunk / 多缓冲 / 用 SSD |
| 切换音乐 | 上一段尾部 + 下一段头部同时存在 | crossfade(交叉淡入淡出)几十 ms |
| 循环播放 | chunk 边界要无缝 | 提前算好"最后一块 + 第一块"的拼接 |

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏行业的标准做法是 **VAG/IMA-ADPCM + 环形缓冲**。PlayStation 时代用 VAG(Sony 自家压缩,4:1 压缩比);PC 游戏用 Ogg Vorbis 或 MP3 压缩,运行时解码到 PCM chunk。所有引擎(Unreal 的 USoundWave、Unity 的 AudioSource、Godot 的 AudioStream)背后都是"压缩文件 → 解码器 → ring buffer → 设备回调"这一套。

实战经验值:

- **chunk 大小**:20-50 ms 是甜区。低于 10 ms 容易被调度抖动伤害;高于 100 ms 切换音乐时有延迟。
- **ring buffer 容量**:3-5 个 chunk。低于 3 容易 underrun;高于 5 是浪费内存。
- **预读**:当 buffer 里数据降到 50% 以下时,异步触发下一次读盘。
- **音乐无缝切换**:在切点前后各 30 ms 做 linear crossfade(从 0 fade 到 1,另一个从 1 fade 到 0)。

### 3.2 · Linux 系统编程视角

Linux 下读盘的三个层次:

1. **`read(2)` 系统调用**:同步,会阻塞当前线程直到数据进 page cache。简单但会卡音频线程。
2. **`io_uring`(Linux 5.1+)**:异步 I/O 接口,提交"读这块"请求,内核完成后通知。零拷贝、批量提交,是当前最高性能方案。Rust crate `tokio-uring` / `rio`。
3. **`mmap(2)`**:把文件映射到内存,访问时缺页 → 内核读盘。延迟分散到访问时,适合"懒加载"。

音频流式加载的 Linux 实践:

```c
// 伪代码:用 io_uring 读盘
struct io_uring ring;
io_uring_queue_init(32, &ring, 0);
int fd = open("bgm.wav", O_RDONLY);

// 提交"读 chunk 0"
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, buffer_a, CHUNK_SIZE, 0);
io_uring_submit(&ring);

// 等待完成(在另一条线程)
struct io_uring_cqe *cqe;
io_uring_wait_cqe(&ring, &cqe);
// buffer_a 已经就绪,可以混音
```

Rust 生态对应:

- **`tokio` 异步文件 I/O**:`tokio::fs::File`(背后是 blocking pool,不是真异步,但对音频够用)
- **`ringbuf` crate**:通用 SPSC ring buffer,可以直接拿来当音频缓冲
- **`cpal`**:跨平台音频回调

### 3.3 · Rust 生态视角

Rust 写音频流式加载的关键工具:

```rust
use std::sync::mpsc;        // 标准库 SPSC channel
use std::sync::Arc;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::thread;

// 1. ring buffer 的简化表达
const CHUNK_FRAMES: usize = 4096;
const CHANNELS: usize = 2;
const RING_SLOTS: usize = 4;

struct RingBuffer {
    slots: [[f32; CHUNK_FRAMES * CHANNELS]; RING_SLOTS],  // 静态分配
    head: AtomicUsize,  // 生产者写到这里
    tail: AtomicUsize,  // 消费者读到这里
}

// 2. 生产者(读盘线程)
fn loader_thread(path: &str, rb: Arc<RingBuffer>, done: Arc<AtomicUsize>) {
    let mut file = std::fs::File::open(path).unwrap();
    loop {
        let h = rb.head.load(Ordering::Acquire);
        let t = rb.tail.load(Ordering::Acquire);
        // 满:head+1 == tail,等待
        if (h + 1) % RING_SLOTS == t { thread::yield_now(); continue; }
        let mut buf = [0u8; CHUNK_FRAMES * CHANNELS * 2]; // s16 = 2 bytes
        let n = std::io::Read::read(&mut file, &mut buf).unwrap();
        if n == 0 { break; }
        // 把 s16 转 f32 写进 ring
        for i in 0..(n/2) {
            let s = i16::from_le_bytes([buf[i*2], buf[i*2+1]]);
            rb.slots[h][i] = s as f32 / 32768.0;
        }
        rb.head.store((h + 1) % RING_SLOTS, Ordering::Release);
    }
    done.store(1, Ordering::Release);
}

// 3. 消费者(cpal 回调)
fn audio_callback(rb: &RingBuffer, out: &mut [f32]) {
    let t = rb.tail.load(Ordering::Acquire);
    let h = rb.head.load(Ordering::Acquire);
    if t == h {
        // underrun:填零(静音),不能阻塞
        out.fill(0.0);
        return;
    }
    let slot = &rb.slots[t];
    out.copy_from_slice(&slot[..out.len()]);
    rb.tail.store((t + 1) % RING_SLOTS, Ordering::Release);
}
```

**关键 Rust 概念**:

- `Arc<RingBuffer>` —— 多线程共享所有权。`Arc` 是 atomic reference counted。
- `AtomicUsize` —— 多线程可见的整数。`Ordering::Acquire` 保证读到的值前面的写入对自己可见;`Release` 保证自己的写入对未来 Acquire 的人可见。这两个 ordering 是 SPSC 队列的最低保证。
- `from_le_bytes` —— little-endian 字节序解析,这是 x86_64 默认字节序。
- `out.fill(0.0)` —— underrun 时静音,不能 panic 不能 block。

## 4 · 认知地图

### 4.1 上级

- **生产者-消费者模型** —— 任何异步数据流的核心抽象(磁盘→内存、网络→应用、CPU→GPU)
- **流式处理(streaming)** —— 处理任意大数据时只把"现在需要的部分"放内存的工程模式
- **实时系统(real-time)** —— 有硬截止时间的系统(音频、视频、游戏物理)

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 整段加载 | 一次性读完 | SFX(短音效) | Day 138-140 用过 |
| 流式加载(本日) | 分块按需读 | BGM(长音乐) | ✅ Day 141 引入 |

| 实时解码 | 存压缩格式,边播边解 | Ogg/MP3 音频 | HH 不用(教学优先) |

### 4.3 下级

- **ring buffer** —— 固定大小数组 + head/tail 指针
- **chunk / frame** —— 音频数据的最小单位
- **double buffering** —— ring buffer 长度为 2 的特例
- **prefetch** —— 提前发起 I/O
- **dropout / underrun** —— 消费者读不到数据的故障

## 5 · 对照与变奏

### 不同领域的"流式"

| 领域 | 生产者 | 消费者 | chunk 大小 |
|---|---|---|---|
| 音频 | 磁盘 / 网络 | 声卡 | 20-50 ms |
| 视频 | 网络 / 磁盘 | 显示器 | 1 帧(16 ms @ 60Hz) |
| 游戏资产 | 磁盘 | GPU | 1 个 mesh / texture |
| 网络(TCP) | 远端 | 应用 | MTU ~1500 字节 |
| 编译器 | 文件 | 解析器 | 1 个 token / 1 行 |
| 数据库 | 磁盘 | 查询 | 1 个 page(8 kB) |

所有这些场景的解决方案高度同构:缓冲池 + 异步 I/O + 通知机制。

### 历史演化

- **1990s**:游戏把整张 CD-ROM 镜像加载到内存(红警、星际),读盘时整个游戏卡住
- **2000s**:PS2/Xbox 引入流式音频,但用专用硬件(ADPCM 解码器)
- **2010s**:多核普及,游戏用独立 I/O 线程
- **2020s**:PS5/Xbox Series X 有专用 I/O 芯片,SSD 直接到 GPU(无 CPU 介入)

### 同步 vs 异步 I/O

| | 同步 read() | 异步 io_uring | mmap |
|---|---|---|---|
| 阻塞? | 是 | 否 | 部分(缺页时阻塞) |
| 代码复杂度 | 低 | 高 | 中 |
| 延迟可预测性 | 高(等就完了) | 中(完成时间不定) | 低(随机缺页) |
| 适合音频线程? | 否 | 是 | 谨慎用 |

### Lv1 · 概念辨析

**题**:chunk 大小选 10 ms 和 100 ms,各自的优缺点是什么?如果你做一个手机游戏(磁盘慢、内存少),你选哪个?

**参考解答**:10 ms 的优点是切换音乐延迟低、内存占用小;缺点是对调度抖动敏感,容易 underrun。100 ms 反过来。手机游戏上,选 30-50 ms 是平衡点——既不太占内存(每块约 5-10 kB),又有一定抗抖动能力。如果你的目标设备是低端 Android,可以更大(100 ms)换稳定性。

### Lv2 · 动手实践

**题**:写一个 Rust 程序,生成 1 分钟的正弦波(48 kHz / mono / f32),写进 `tone.raw`。然后写第二个程序,用 ring buffer(4 个 slot,每个 4096 sample)流式读取这个文件并打印每个 slot 的首 sample 值。

完成标准:第二个程序打印 4 行 `slot[0][0] = 0.000`,`slot[1][0] = 0.xxxx`...,验证 slot 边界处的正弦值正确。

**参考解答**:

```rust
// gen.rs - 生成 1 分钟正弦波
use std::io::Write;
fn main() {
    let mut f = std::fs::File::create("tone.raw").unwrap();
    let sample_rate = 48000.0;
    let freq = 440.0;
    for i in 0..(sample_rate as usize * 60) {
        let t = i as f32 / sample_rate;
        let s = (2.0 * std::f32::consts::PI * freq * t).sin();
        let bytes = s.to_le_bytes();
        f.write_all(&bytes).unwrap();
    }
}

// stream.rs - 流式读取
use std::io::{Read, Seek, SeekFrom};
const CHUNK: usize = 4096;
const SLOTS: usize = 4;

fn main() {
    let mut f = std::fs::File::open("tone.raw").unwrap();
    let mut slots = vec![vec![0f32; CHUNK]; SLOTS];
    let mut head = 0;
    let mut tail = 0;
    // 模拟生产者-消费者轮转 4 次
    for _ in 0..4 {
        // 生产
        let mut bytes = [0u8; CHUNK * 4];
        let n = f.read(&mut bytes).unwrap();
        for i in 0..(n/4) {
            slots[head][i] = f32::from_le_bytes([
                bytes[i*4], bytes[i*4+1], bytes[i*4+2], bytes[i*4+3]
            ]);
        }
        println!("slot[{}][0] = {:.4}", head, slots[head][0]);
        head = (head + 1) % SLOTS;
        // 消费(模拟声卡拿走)
        tail = (tail + 1) % SLOTS;
    }
}
```

slot 边界处的 sin(2π·440·4096/48000) = sin(2π · 9.1·4096/48000) 应该有规律地变化,因为 440 Hz 周期是 ~109 sample,4096 ≈ 37.6 个周期,余数部分决定边界值。

## 8 · Rust / Arch 落地代码

完整可跑示例:用 cpal 流式播放一个 1 分钟 WAV。

```rust
// Cargo.toml
// [dependencies]
// cpal = "0.15"
// ringbuf = "0.4"

use cpal::traits::{DeviceTrait, HostTrait, StreamTrait};
use ringbuf::{HeapRb, Rb};
use std::sync::Arc;
use std::sync::atomic::{AtomicBool, Ordering};
use std::thread;

fn main() {
    // 1. 生成一段"假"WAV:5 秒 440Hz 正弦,f32 mono
    let sample_rate = 48000.0f32;
    let samples: Vec<f32> = (0..(sample_rate * 5.0) as usize)
        .map(|i| {
            let t = i as f32 / sample_rate;
            (2.0 * std::f32::consts::PI * 440.0 * t).sin() * 0.3
        })
        .collect();

    // 2. ring buffer:容量 = 4 chunks × 4096 samples
    let rb = Arc::new(HeapRb::<f32>::new(4096 * 4));
    let (prod, cons) = rb.split();

    // 3. 生产者线程:把 samples 推进 ring
    let done = Arc::new(AtomicBool::new(false));
    let done_clone = done.clone();
    let loader = thread::spawn(move || {
        let mut prod = prod;
        for &s in &samples {
            // 如果满了就等(阻塞式;真实代码用 try_push + sleep)
            while prod.push(s).is_none() {
                if done_clone.load(Ordering::Relaxed) { return; }
                thread::sleep(std::time::Duration::from_micros(100));
            }
        }
        // 等消费完
        while !prod.is_empty() {
            if done_clone.load(Ordering::Relaxed) { return; }
            thread::sleep(std::time::Duration::from_millis(10));
        }
    });

    // 4. 消费者:cpal 回调
    let host = cpal::default_host();
    let device = host.default_output_device().unwrap();
    let config = device.default_output_config().unwrap();
    let sr = config.sample_rate().0;
    let channels = config.channels() as usize;
    let mut cons_box = Box::new(cons);
    let stream = match config.sample_format() {
        cpal::SampleFormat::F32 => device.build_output_stream(
            cpal::StreamConfig {
                channels: channels as u16,
                sample_rate: cpal::SampleRate(sr),
                buffer_size: cpal::BufferSize::Default,
            },
            move |data: &mut [f32], _: &cpal::OutputCallbackInfo| {
                // 从 ring 拿样本,不够就静音(underrun)
                for frame in data.chunks_mut(channels) {
                    let s = cons_box.pop().unwrap_or(0.0);
                    for ch in frame.iter_mut() { *ch = s; }
                }
            },
            |e| eprintln!("stream error: {:?}", e),
            None,
        ).unwrap(),
        _ => panic!("unsupported format"),
    };
    stream.play().unwrap();

    // 5. 等播完
    loader.join().unwrap();
    done.store(true, Ordering::Relaxed);
    thread::sleep(std::time::Duration::from_millis(200));
}
```

**每行解释**:
- `HeapRb::<f32>::new(N)` —— 在堆上分配 N 容量的环形缓冲区。`ringbuf` crate 提供。
- `rb.split()` —— 把 ring buffer 拆成 producer 和 consumer 两半,各占一个引用。这是 SPSC 模式的强制表达。
- `prod.push(s)` —— 推一个样本;满了返回 `None`,生产者等。
- `device.build_output_stream(...)` —— cpal 的核心 API:注册一个回调函数,声卡需要数据时调用。
- `cons_box.pop().unwrap_or(0.0)` —— underrun 时静音。注意这里**没有阻塞**,保证回调实时。
- `data.chunks_mut(channels)` —— 把输出 buffer 按帧切;每帧 channels 个 sample,我们用同一个值填(单声道 → 多声道复制)。

## 10 · 深度推导:lock-free SPSC ring buffer 完整实现

今天 Casey 用 lock-free ring buffer 替代 Day 140 的 Mutex<Mixer>。这是音频编程的核心数据结构,值得彻底搞懂。

### 10.1 为什么 Mutex 不能用?

Day 140 的代码:

```rust
move |buffer: &mut [f32], _| {
    let mut m = mixer.lock().unwrap();  // ← 这里
    let output = m.render(buffer.len());
    buffer.copy_from_slice(output);
}
```

音频线程 callback 在实时优先级。如果主线程正在 lock(cleanup voices / load new sample),音频线程 block。

block 时间不确定:Mutex 内部有 futex 系统调用,~10 μs。如果主线程持有 lock 时间长(load 1 MB WAV,5 ms),音频线程等 5 ms,glitch。

工业音频铁律:**音频线程不能 block,不能 lock,不能 malloc**。

### 10.2 SPSC ring buffer 是什么

Single Producer Single Consumer ring buffer:

```
[ _ _ _ W _ _ _ _ _ _ R _ _ _ _ ]  size = 16
        ↑ producer 写位置
                  ↑ consumer 读位置
```

- Producer(主线程)在 W 处写,推进 W
- Consumer(音频线程)在 R 处读,推进 R
- W 追上 R = buffer 满(producer 等)
- R 追上 W = buffer 空(consumer 等)

关键:**只有 producer 写 W,只有 consumer 写 R**。两个 atomic counter,无 CAS,无 lock。

### 10.3 完整实现

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::cell::UnsafeCell;

pub struct SPSCRingBuffer<T: Copy> {
    buffer: Box<[T]>,
    mask: usize,  // size - 1,size 必须是 2 的幂
    head: AtomicUsize,  // consumer 读位置
    tail: AtomicUsize,  // producer 写位置
}

impl<T: Copy + Default> SPSCRingBuffer<T> {
    pub fn new(size: usize) -> Self {
        assert!(size.is_power_of_two(), "size must be power of 2");
        let buffer = vec![T::default(); size].into_boxed_slice();
        Self {
            buffer,
            mask: size - 1,
            head: AtomicUsize::new(0),
            tail: AtomicUsize::new(0),
        }
    }

    /// Producer 端:写入 items,返回成功写入数量
    pub fn push(&self, items: &[T]) -> usize {
        let tail = self.tail.load(Ordering::Relaxed);
        let head = self.head.load(Ordering::Acquire);
        let available = self.buffer.len() - (tail - head);
        let count = items.len().min(available);
        for i in 0..count {
            let idx = (tail + i) & self.mask;
            unsafe {
                *self.buffer.get_unchecked(idx) = items[i];
            }
        }
        self.tail.store(tail + count, Ordering::Release);
        count
    }

    /// Consumer 端:读取 items,返回成功读取数量
    pub fn pop(&self, items: &mut [T]) -> usize {
        let head = self.head.load(Ordering::Relaxed);
        let tail = self.tail.load(Ordering::Acquire);
        let available = tail - head;
        let count = items.len().min(available);
        for i in 0..count {
            let idx = (head + i) & self.mask;
            unsafe {
                items[i] = *self.buffer.get_unchecked(idx);
            }
        }
        self.head.store(head + count, Ordering::Release);
        count
    }

    pub fn available_read(&self) -> usize {
        let head = self.head.load(Ordering::Relaxed);
        let tail = self.tail.load(Ordering::Relaxed);
        tail - head
    }

    pub fn available_write(&self) -> usize {
        let capacity = self.buffer.len();
        capacity - self.available_read()
    }
}
```

关键点:

1. **size 是 2 的幂**——用 `& mask` 替代 `% size`,更快
2. **head/tail 用 `wrapping_add` 语义**——usize 会溢出回绕,但 usize 64-bit 几百年不会溢出
3. **Acquire/Release 配对**:producer Release 写 tail,consumer Acquire 读 tail;反向同理
4. **不能用 `Box<[UnsafeCell<T>]>`**——这里简化了,实际要用 UnsafeCell 保证 interior mutability
5. **必须 T: Copy**——避免 Drop 复杂性

### 10.4 接入 cpal

```rust
use cpal::traits::*;
use std::sync::Arc;

fn main() {
    let ring: Arc<SPSCRingBuffer<f32>> = Arc::new(SPSCRingBuffer::new(16384));
    let ring_clone = Arc::clone(&ring);

    // 主线程:生成 sample,push 到 ring
    let producer = std::thread::spawn(move || {
        let mut phase = 0.0f32;
        loop {
            let samples_to_push = ring.available_write();
            if samples_to_push > 0 {
                let mut samples = vec![0.0; samples_to_push];
                for s in &mut samples {
                    *s = (phase * 2.0 * std::f32::consts::PI).sin() * 0.2;
                    phase += 440.0 / 44100.0;
                    if phase > 1.0 { phase -= 1.0; }
                }
                ring.push(&samples);
            } else {
                std::thread::yield_now();  // buffer 满,等
            }
        }
    });

    // 音频线程:cpal callback,pop sample
    let host = cpal::default_host();
    let device = host.default_output_device().unwrap();
    let config = device.default_output_config().unwrap();
    let stream = device.build_output_stream(
        &config.into(),
        move |buffer: &mut [f32], _| {
            // 无 lock:直接 pop
            let n = ring_clone.pop(buffer);
            // 如果 ring 空,pop 返回 0,buffer 部分是 0(静音)
            // 这就是 "glitch"——音频卡顿
            if n < buffer.len() {
                for s in &mut buffer[n..] {
                    *s = 0.0;
                }
            }
        },
        |err| eprintln!("{}", err),
        None,
    ).unwrap();

    stream.play().unwrap();
    std::thread::sleep(std::time::Duration::from_secs(5));
}
```

跑起来你能听到 440Hz 正弦波。**音频线程零 lock**,这就是 Day 141 的目标。

### 10.5 Buffer sizing

Buffer size 决定延迟和稳定性:

- **小 buffer(256 sample,5.8 ms)**:延迟低,但 producer 跟不上就会 glitch
- **大 buffer(16384 sample,371 ms)**:稳定,但延迟高(玩家按按钮到听到声音有 371ms 延迟)

游戏选 1024-4096 sample(23-93 ms),平衡。

### 10.6 双声道 ring buffer

立体声:左右交错存储(L R L R L R...):

```rust
let ring: Arc<SPSCRingBuffer<f32>> = Arc::new(SPSCRingBuffer::new(8192));
// 一个 frame = 2 sample(L + R)
// ring 容量 8192 sample = 4096 frame

// Producer
let mut samples = vec![0.0; frames_to_push * 2];
for frame in samples.chunks_mut(2) {
    let l = compute_left();
    let r = compute_right();
    frame[0] = l;
    frame[1] = r;
}
ring.push(&samples);

// Consumer(cpAL callback 已经按 frame 组织)
move |buffer: &mut [f32], _| {
    ring.pop(buffer);  // buffer 是 interleaved L R L R...
}
```

### 10.7 MPMC 扩展

SPSC 是单生产单消费。如果多个生产者(多线程各自 push sample)就要 MPMC。MPMC 用 CAS,复杂得多。

工业音频通常用 SPSC:一个主线程做所有 producer 工作,音频线程做 consumer。多 producer 用一个 producer thread 合并。

### 11.3 测试 SPSC 正确性

并发测试难写。技巧:

```rust
#[test]
fn test_spsc_single_threaded() {
    let ring = SPSCRingBuffer::<u32>::new(4);
    assert_eq!(ring.push(&[1, 2, 3]), 3);
    let mut buf = [0u32; 2];
    assert_eq!(ring.pop(&mut buf), 2);
    assert_eq!(buf, [1, 2]);
}

#[test]
fn test_spsc_multithreaded() {
    let ring = Arc::new(SPSCRingBuffer::<u32>::new(1024));
    let ring2 = Arc::clone(&ring);
    let producer = std::thread::spawn(move || {
        for i in 0..1_000_000u32 {
            while ring2.push(&[i]) == 0 {
                std::hint::spin_loop();
            }
        }
    });
    let ring3 = Arc::clone(&ring);
    let consumer = std::thread::spawn(move || {
        let mut expected = 0u32;
        let mut buf = [0u32; 1];
        while expected < 1_000_000 {
            if ring3.pop(&mut buf) > 0 {
                assert_eq!(buf[0], expected, "expected {}, got {}", expected, buf[0]);
                expected += 1;
            }
        }
    });
    producer.join().unwrap();
    consumer.join().unwrap();
}
```

跑 100 万 sample,如果 SPSC 正确,所有 sample 顺序到达 consumer。任何 memory ordering bug 都会暴露(某 sample 错位)。
