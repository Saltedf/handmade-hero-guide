# Day 114 · 为优化准备一个函数

> 你昨天写好了性能计数器,今天要拿它来"练手"——挑一个真实的函数,做"优化前的准备"。Casey 这天反复强调一件事:**优化不是改代码,优化是先证明"这段代码现在有多慢,为什么慢",再动手**。这就是工程化的优化方法论。

## 0 · 为什么要有这一天

很多程序员"优化"代码的方式是这样的:

1. 觉得某段代码慢
2. 改一改(换算法 / 加 SIMD / 加 cache)
3. 跑一遍,感觉变快了
4. commit,push

这套流程的问题:

- **感觉不准**:你"感觉"快了,实际可能没快,甚至慢了(因为新代码破坏了 cache)
- **不知道为什么变快**:即使真的变快,你也说不清原因。下次类似问题你不会迁移
- **没有 baseline**:没"改之前多快"的精确数据,没法说"我提速了 30%"
- **可能引入 bug**:优化常常引入微妙的边界 bug,没测试就发现不了

Casey 这一天给你建立**工程化的优化流程**:

1. 选一个热点函数(用 Day 113 的 profiler 找到)
2. 把它独立成"可单独测量的 unit"(micro-bench)
3. 写测试,确保优化后**功能不变**
4. 测量当前性能(baseline)
5. **找瓶颈**(用 Day 112 的模型分析:latency / throughput / cache / branch?)
6. 设计针对性的优化方案
7. 实现优化
8. 再次测量,对比 baseline
9. 如果真快了,提交;否则回滚

这 9 步看起来繁琐,但每一步都有理由。跳过任何一步,你后面都会后悔。

心理锚点:读完这一天,你能:

- 把"游戏里某个函数"独立成"benchmark 单元"
- 写"功能等价"的测试,确保优化不破坏正确性
- 测量 baseline,记录数据
- 分析瓶颈,想出至少 2 个优化方案再动手

## 1 · Casey 今天做了什么

Casey 在 HH 里挑了一个具体函数:Day 113 的 `DrawBitmap`(画精灵到 framebuffer)。他做的事:

1. 把这个函数从内联的代码里"独立"出来,变成单独可调用的函数
2. 加打印:`printf("DrawBitmap took %llu ns\n", elapsed);`
3. 把函数隔离到一个 micro-bench:不停调它 1000 次,取平均
4. 用 Day 112 的模型分析:为什么这段慢?
   - **数据依赖**?——画像素的循环里,每次写一个像素,下一次写下一个像素,无依赖
   - **吞吐**?——每次循环 ~10 条指令(算地址、算颜色、blend、写),throughput 受限
   - **cache**?——读 bitmap 是顺序访问,OK;写 framebuffer 是顺序,OK
   - **分支**?——blend 里如果 alpha == 0 或 == 255,可能有提前退出的分支
5. 列出可能的优化方向:
   - SIMD 化(一次处理 4/8 像素)
   - 减少分支(用位运算替代 alpha blend 的 if)
   - 内存对齐(让 framebuffer 行宽对齐 64 字节)
6. 但是——**今天不动手优化**,只把"基线测量 + 瓶颈分析"做扎实

这集的实际产出是 **0 行优化代码**,但准备工作完整,后面 Day 115-120 都是在这天的基础上动手。

## 2 · 心智模型

### 2.1 类比:科学家做实验

物理学家做一个新实验,标准流程是:

1. **写下假设**(我猜 X 会影响 Y)
2. **设计实验装置**(让 X 可控,让 Y 可测)
3. **跑基线**(X 取默认值,记录 Y 的基线值)
4. **改变 X,记录 Y**(只改 X,其他不变)
5. **分析结果**(Y 变了没?为什么?)
6. **写报告**(可重复,别人能复现)

代码优化的流程几乎一模一样:

1. **假设**(我猜 cache miss 是瓶颈)
2. **实验装置**(把函数抽成 micro-bench)
3. **基线**(改之前耗时 X ms)
4. **改变一个变量**(改 cache 布局 / 加 SIMD),记录新耗时
5. **分析**(快了?慢了?为什么?)
6. **报告**(commit message / PR 描述写清"基线 X ms,新 Y ms,因为 Z")

这种"科学方法"是工程师区别于"碰运气调参"的关键。**Casey 反复强调:任何没有 baseline 的优化都是耍流氓**。

### 2.2 micro-bench 是什么

**micro-bench**(微基准)是把"一小段代码"从大程序里抽出来,单独反复跑,测它的性能。

为什么需要 micro-bench?

- **可重复**:跑 1000 次取均值,噪音被平均掉
- **快速**:不用启动整个游戏,几秒就跑完
- **隔离**:知道"就是这段代码的耗时",不被其他代码干扰
- **可对比**:今天的版本 vs 昨天的版本,数字直接比较

micro-bench 的反例:**在游戏里看帧率**。帧率受系统状态、其他进程、磁盘 IO 等影响,变化大,且测的是"整帧"不是"某段代码"。

### 2.3 隔离的步骤

把一段代码做成 micro-bench,标准 5 步:

**步骤 1:抽出函数**。如果代码内联在 `update()` 里,把它独立成一个 `fn draw_bitmap(...)`。

**步骤 2:准备测试数据**。固定输入(同一个 bitmap,同一个目标 framebuffer),不依赖外部状态。

**步骤 3:写正确性测试**。把当前函数的输出"存档"(比如 dump framebuffer 到 PNG),后面每次改后重新生成,对比是否一致。

**步骤 4:写 bench**。循环 N 次,总时间 / N = 单次耗时。

**步骤 5:取统计量**。均值 / 中位数 / 标准差 / 异常值。

```rust
// 步骤 4 的骨架
fn bench<F: FnMut()>(name: &str, mut f: F, iters: usize) {
    // warmup(让 CPU 调频稳定)
    for _ in 0..100 { f(); }

    // 真测
    let start = Instant::now();
    for _ in 0..iters {
        std::hint::black_box(&mut f);
        f();
    }
    let elapsed = start.elapsed();

    let per_iter_ns = elapsed.as_nanos() as f64 / iters as f64;
    println!("{}: {:.2} ns/iter ({:.2} ms total)", name, per_iter_ns, elapsed.as_secs_f64() * 1000.0);
}
```

#### 为什么需要 warmup?

CPU 启动时频率低(省电模式),跑几次后频率提升到最高(`turbo`)。如果不 warmup,前几次迭代特别慢,污染均值。warmup 100 次后,CPU 已经在最高频率,后续测量稳定。

### 2.4 正确性测试:优化的护身符

优化常引入微妙 bug:

- SIMD:lane 顺序错了,某些像素颜色错
- 位运算:边界值(alpha=0、alpha=255)处理错
- 算法替换:浮点误差累积,结果差几个像素

**护身符**:有一个"golden output"——把当前正确版本输出存档,每次优化后对比新输出和 golden output,差异不能超过容忍阈值。

```rust
// 步骤 3 的骨架
#[test]
fn draw_bitmap_matches_golden() {
    let mut fb = Framebuffer::new(640, 480);
    let bmp = Bitmap::load("test_data/test.bmp");

    draw_bitmap(&mut fb, 100, 100, &bmp);

    let golden = include!("test_data/golden_draw_bitmap.txt");  // 预先存的"正确输出"
    assert_eq!(fb.pixels, golden.pixels);
    // 或者用容差:
    // for (a, b) in fb.pixels.iter().zip(golden.pixels.iter()) {
    //     assert!((a.r as i32 - b.r as i32).abs() <= 1);  // 1 个像素值容忍
    // }
}
```

**重要**:`cargo test` 在每次优化后**必须**先跑通,才能 commit。否则优化引入的 bug 一周后才发现,定位就难了。

### 2.5 分析瓶颈:用 Day 112 的模型

测出 baseline 后,回到 Day 112 的模型。问自己 5 个问题:

1. **数据依赖**?——这段代码里有没有"前一次结果影响后一次"?有的话,latency 受限。
2. **吞吐**?——这段代码每秒能完成多少"基本运算"?是不是已经接近 CPU 峰值?
3. **端口占用**?——主要在算什么?(乘法 → port 0/1;加法 → port 0/1/5;load → port 2/3)。
4. **cache**?——访问的数据多大?能不能放进 L1?访问模式是顺序还是随机?
5. **分支**?——有多少 `if`?分支结果可预测吗?

针对每个问题,可能的优化:

| 瓶颈 | 优化方向 |
|---|---|
| 数据依赖 | 多累加器打破链 |
| 吞吐 | SIMD(每指令处理 4-16 个数据) |
| 端口 | 换指令(乘→加、除→乘倒) |
| Cache | 改数据布局(SoA)、预取 |
| 分支 | 无分支写法、排序数据 |

注意:**可能多个瓶颈并存**。比如同时 cache 受限 + 分支受限,你只解决一个,效果有限。

### 2.6 "至少两个方案"原则

Casey 在这一天的核心原则:**动手前,想出至少 2 个不同的优化方案,记录在笔记本上**。

为什么?

- **强迫你思考**:写下来才知道你想没想清
- **避免"锤子综合症"**:如果你只想到 SIMD,可能漏掉"其实问题是 cache,不是 SIMD"
- **后续对比**:实施 A 方案后,可以再试 B,看哪个更好

每个方案要回答:

1. **针对哪个瓶颈**?
2. **预期收益**?(比如"提速 2x"?)
3. **实现成本**?(几行代码?是否引入 unsafe?)
4. **风险**?(可能引入 bug?可能让其他代码变慢?)

### 2.7 测量基线时的注意事项

#### 不要测优化模式关掉的版本

`cargo build` 是 debug,没开 `-O`,代码慢 10 倍。一定要 `cargo build --release` 才测。

#### 不要测"零迭代"

如果代码很简单(< 100ns),`Instant::now()` 的开销(20ns)就不能忽略。**至少跑 1,000,000 次**,总耗时 > 1ms,测量才准。

#### 多次跑取最小值

CPU 频率波动 / 系统调度会让单次测量偏大。跑 5 次取最小值(不是平均),因为"最小"最接近"无干扰的真实性能"。

criterion 默认就是这样:多次跑,取统计量,排除异常值。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发里 micro-bench 是日常工具。专业引擎都有"unit test + micro-bench + integration test"三层:

- **unit test**:测某个函数对错
- **micro-bench**:测某个函数多快
- **integration test**:整个系统组合起来工作

Casey 这一天建立的是"micro-bench 文化"。后面 Day 115-120 的 SIMD 优化,每一步都伴随一个 micro-bench。

#### 游戏行业的 frame budget

每个阶段有"预算"(frame budget):

- **30 FPS 预算**:33.3ms / 帧
- **60 FPS 预算**:16.67ms / 帧
- **120 FPS 预算**:8.33ms / 帧
- **144 FPS 预算**:6.94ms / 帧

子阶段典型分配(60 FPS):

| 阶段 | 预算 |
|---|---|
| 输入 | 0.1ms |
| AI | 2ms |
| 物理 | 2ms |
| 渲染 CPU 端 | 4ms |
| 渲染 GPU 端 | 6ms |
| 音频 | 0.5ms |
| 提交 / swap | 0.5ms |
| OS / 调度裕量 | 1.5ms |

如果你某天发现 `AI` 跑了 5ms(超预算 150%),就要看 AI 的 micro-bench,找具体函数。Casey 这一天就是在为这种 drill 做准备。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上做 micro-bench 的工具链:

#### `taskset` 绑核

```bash
taskset -c 0 ./target/release/my_bench
```

强制程序只在 CPU 0 上跑。好处:

- 避免 CPU 间切换(cache miss)
- 减少调度抖动

#### `nice -n -19` 高优先级

```bash
sudo nice -n -19 ./target/release/my_bench
```

`nice -19` 是最高优先级,减少被其他进程抢占。需要 root。

#### 关闭 CPU 调频(短暂)

```bash
sudo cpupower frequency-set -g performance
# 跑 bench
sudo cpupower frequency-set -g powersave
```

`performance` governor 锁 CPU 在最高频率,避免动态调频导致的测量抖动。

#### HyperThreading 的陷阱

如果 CPU 是 HyperThreaded(每核 2 个逻辑核),同一个物理核上的两个线程**竞争同一个 execution port**。如果你的 micro-bench 跟另一个进程"撞核",测量会被拖累。

`taskset -c 0` 绑定逻辑核 0,但逻辑核 0 和核 32 可能共享物理核(具体看 `/proc/cpuinfo`)。严格起见用 `taskset -c 0,16` 之类明确"不冲突"的核。

### 3.3 · 🦀 Rust 生态视角

#### `criterion` 完整用法

```toml
# Cargo.toml
[dev-dependencies]
criterion = { version = "0.5", features = ["html_reports"] }

[[bench]]
name = "draw_bitmap"
harness = false  # 用 criterion 自己的 main,不要默认的 #[bench]
```

`benches/draw_bitmap.rs`:

```rust
use criterion::{black_box, criterion_group, criterion_main, Criterion, BenchmarkId};
use my_crate::{draw_bitmap, Framebuffer, Bitmap};

fn bench_draw(c: &mut Criterion) {
    let mut group = c.benchmark_group("draw_bitmap");
    // 测不同尺寸
    for size in [16, 64, 256, 1024].iter() {
        let mut fb = Framebuffer::new(*size, *size);
        let bmp = Bitmap::test_pattern(*size, *size);
        group.bench_with_input(BenchmarkId::from_parameter(size), &bmp, |b, bmp| {
            b.iter(|| {
                // black_box 防止编译器优化
                draw_bitmap(black_box(&mut fb), black_box(0), black_box(0), black_box(bmp));
            });
        });
    }
    group.finish();
}

criterion_group!(benches, bench_draw);
criterion_main!(benches);
```

```bash
cargo bench
# 输出:
# draw_bitmap/16       time:   [120.34 ns 120.51 ns 120.71 ns]
# draw_bitmap/64       time:   [1.8012 µs 1.8034 µs 1.8057 µs]
# ...
# 还生成 HTML 报告在 target/criterion/report/index.html
```

criterion 的优点:

- **统计严谨**:多次跑,取中位数 + 置信区间
- **异常值检测**:统计学方法剔除
- **跨运行对比**:第二次跑会自动对比上次,告诉"快了/慢了 X%"
- **HTML 报告**:可视化

#### `iai`(Instruction-Accounted)

`iai` 是 criterion 的替代品,**数指令数而不是测时间**。优点:不受 CPU 频率影响,完全可重复。缺点:不反映 cache / branch / port 真实影响。

适合 CI 里做"指令数回归检测"。`cargo install iai && cargo bench`。

#### `divan`

更新的 micro-benchmark 库,设计更现代。`cargo add divan --dev`。

#### `#[bench]`(内置,已废弃)

Rust 1.x 早期有内置 `#[bench]`,但需要 nightly。criterion 是事实标准。**不要用 `#[bench]`**。

### 3.4 · 🎨 图形学视角

图形学里 micro-bench 的经典对象:

- **像素 blend**(本日 Casey 选的)
- **纹理采样**
- **顶点变换**
- **三角形设置**
- **深度测试**

每个都有 micro-bench。优化图形管线就是"逐函数 bench + 优化 + 集成"。

#### 关键的"等价性"测试

图形代码常有"看起来一样,实际差几个像素"的问题。所以正确性测试要用**容差**:

```rust
#[test]
fn draw_matches_reference() {
    let mut fb1 = test_fb();
    let mut fb2 = test_fb();
    draw_baseline(&mut fb1);
    draw_optimized(&mut fb2);

    let mut max_diff = 0;
    for (a, b) in fb1.pixels.iter().zip(fb2.pixels.iter()) {
        let dr = (a.r as i32 - b.r as i32).abs();
        let dg = (a.g as i32 - b.g as i32).abs();
        let db = (a.b as i32 - b.b as i32).abs();
        max_diff = max_diff.max(dr).max(dg).max(db);
    }
    assert!(max_diff <= 1, "max diff {} too large", max_diff);
}
```

容差 1 像素值(0-255 中)是常见的"无视觉差异"阈值。

## 5 · 对照与变奏

### 同一问题的不同尺度

**问题**:测量 `draw_bitmap` 的性能。

| 尺度 | 方法 |
|---|---|
| 单次调用 | `Instant::now()` 前后打卡 |
| 多次调用求均值 | 手写循环 |
| 统计严谨 | criterion |
| 整帧 / 整个游戏 | Day 113 的 frame profiler |
| 生产环境 | Tracy / 自制 telemetry |

每个尺度都有自己的工具,不可替代。

### 历史演化

- **1980s**:性能靠 `printf("%d", time(NULL))`,秒级
- **1990s**:RDTSC 出现,周期级,但每个 CPU 频率不同
- **2000s**:`gettimeofday` 微秒级,跨平台
- **2010s**:criterion 等工具成熟,统计学方法引入
- **2020s**:CI 集成 bench,自动检测性能回退

Casey 用的是 1990s-2000s 风格的手写计数器,因为 HH 是教学项目。生产代码你应该用 criterion / tracy。

### "优化过的代码"不一定快

一个反直觉的现象:**经过"优化"的代码,在某些数据分布下可能比原始代码慢**。比如:

- SIMD 代码在小数据(< 16 个元素)上,启动开销大于收益,比标量慢
- 无分支代码在分支可预测时,比有分支慢

所以"优化"永远是"在你的真实数据分布下"的优化。**没有 silver bullet**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 这一天不写一行"优化"代码,只做"准备"。为什么?如果直接跳过准备开始改 SIMD,最坏会发生什么?

**参考解答**:三个理由:

1. **没有 baseline 无法证明变快**:你说"我加了 SIMD,变快了",但拿不出数字。可能其实慢了,你只是"感觉"快了。
2. **没有正确性测试无法证明没坏**:SIMD 容易引入微妙 bug(像素颜色错位、边界像素错)。如果不先建 golden output,你不会发现这些 bug。
3. **没有瓶颈分析会做无效优化**:你可能花 3 天写 SIMD,但实际瓶颈是 cache miss,SIMD 没用。

最坏情况:你 push 了"优化",游戏看起来快了一点(其实是测量误差),但实际引入了 bug,一周后被用户报"角色变成紫色"。回滚后才发现"优化"实际还慢了。

**参考解答**(以 `Vec2::length` 为例):

```rust
// src/lib.rs
#[derive(Copy, Clone, Debug)]
pub struct Vec2 { pub x: f32, pub y: f32 }

impl Vec2 {
    pub fn length(self) -> f32 {
        (self.x * self.x + self.y * self.y).sqrt()
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn length_correct() {
        let v = Vec2 { x: 3.0, y: 4.0 };
        let len = v.length();
        assert!((len - 5.0).abs() < 1e-6, "expected 5.0, got {}", len);
    }

    #[test]
    fn length_zero() {
        let v = Vec2 { x: 0.0, y: 0.0 };
        assert_eq!(v.length(), 0.0);
    }
}
```

```rust
// benches/vec_length.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion};
use my_crate::Vec2;

fn bench(c: &mut Criterion) {
    let v = Vec2 { x: 3.0, y: 4.0 };
    c.bench_function("length", |b| {

    });
}

criterion_main!(benches);
```

Baseline 测量(假设):

```
length                 time:   [1.20 ns 1.21 ns 1.23 ns]
```

1.21ns 大约 4 个 CPU 周期(3GHz),正好对应 `mulss` + `addss` + `sqrtss` 的延迟。

2 个优化方案:

**方案 A**:`mul_add`

```rust
pub fn length(self) -> f32 {
    self.x.mul_add(self.x, self.y * self.y).sqrt()
}
```

- **针对**:减少一条 mulss 指令(mul_add 是单条 fused 指令)
- **预期收益**:0-10%,因为 `length` 已经很快了,主要瓶颈是 sqrtss 延迟
- **风险**:低,mul_add 语义等价

**方案 B**:批量 SIMD(处理 4 个 Vec2)

```rust
pub fn lengths4(vs: &[Vec2; 4]) -> [f32; 4] {
    // SIMD:一次算 4 个 length
}
```

- **针对**:throughput
- **预期收益**:3-4x(每指令处理 4 个)
- **风险**:中等,需要 unsafe SIMD intrinsic
- **何时用**:只有当你**真的有 4 个 Vec2 要算 length** 才有意义;单个 Vec2 没收益

```rust
// src/lib.rs
/// 简单的 framebuffer
pub struct Framebuffer {
    pub width: usize,
    pub height: usize,
    pub pixels: Vec<u32>,  // 0x00RRGGBB
}

impl Framebuffer {
    pub fn new(w: usize, h: usize) -> Self {
        Self { width: w, height: h, pixels: vec![0; w * h] }
    }
}

/// 简单的 bitmap
pub struct Bitmap {
    pub width: usize,
    pub height: usize,
    pub pixels: Vec<u32>,  // 0xAARRGGBB
}

impl Bitmap {
    pub fn solid(w: usize, h: usize, color: u32) -> Self {
        Self { width: w, height: h, pixels: vec![color; w * h] }
    }
}

/// 待优化的函数:把 bitmap blit 到 framebuffer
pub fn draw_bitmap_baseline(fb: &mut Framebuffer, dx: usize, dy: usize, bmp: &Bitmap) {
    for y in 0..bmp.height {
        for x in 0..bmp.width {
            let src = bmp.pixels[y * bmp.width + x];
            let alpha = (src >> 24) & 0xff;
            if alpha == 0xff {
                // 不透明,直接覆盖
                let dst_idx = (dy + y) * fb.width + (dx + x);
                fb.pixels[dst_idx] = src & 0xffffff;
            } else if alpha > 0 {
                // 半透明,做 alpha blend
                let dst_idx = (dy + y) * fb.width + (dx + x);
                let dst = fb.pixels[dst_idx];
                let a = alpha as u32;
                let r = ((src >> 16) & 0xff) * a + ((dst >> 16) & 0xff) * (255 - a);
                let g = ((src >> 8) & 0xff) * a + ((dst >> 8) & 0xff) * (255 - a);
                let b = (src & 0xff) * a + (dst & 0xff) * (255 - a);
                fb.pixels[dst_idx] = 0xff000000 | ((r / 255) << 16) | ((g / 255) << 8) | (b / 255);
            }
            // alpha == 0 不画
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn solid_bitmap_fills() {
        let mut fb = Framebuffer::new(16, 16);
        let bmp = Bitmap::solid(8, 8, 0xff_ffffff);
        draw_bitmap_baseline(&mut fb, 4, 4, &bmp);
        // 检查 (4,4) 处的像素是白色
        assert_eq!(fb.pixels[4 * 16 + 4], 0xff_ffffff);
        // 检查 (0,0) 处的像素是黑色(没画过)
        assert_eq!(fb.pixels[0], 0);
    }

    #[test]
    fn transparent_bitmap_no_change() {
        let mut fb = Framebuffer::new(16, 16);
        let bmp = Bitmap::solid(8, 8, 0x00_ffffff);  // alpha = 0
        draw_bitmap_baseline(&mut fb, 4, 4, &bmp);
        // 没有变化
        assert_eq!(fb.pixels[4 * 16 + 4], 0);
    }
}
```

```rust
// benches/draw.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion};
use dbb::*;

fn bench_draw(c: &mut Criterion) {
    let mut group = c.benchmark_group("draw_bitmap");
    for size in [16, 64, 256] {
        let mut fb = Framebuffer::new(size, size);
        let bmp = Bitmap::solid(size / 2, size / 2, 0xff_ff0000);
        group.bench_function(format!("size_{}", size), |b| {
            b.iter(|| {
                draw_bitmap_baseline(
                    black_box(&mut fb),
                    black_box(0),
                    black_box(0),
                    black_box(&bmp),
                );
            });
        });
    }
    group.finish();
}

criterion_group!(benches, bench_draw);
criterion_main!(benches);
```

**Troubleshooting**:

- bench 数字波动大:看上面的"稳定测量环境",全部做一遍
- `cargo bench` 报错找不到 criterion:确认 `Cargo.toml` 里 `criterion` 在 `[dev-dependencies]`
- HTML 报告不生成:criterion 默认生成,在 `target/criterion/report/index.html`,用浏览器打开
- 改了代码 bench 数字没变:确认你测的是 `--release`(cargo bench 默认是 release),确认 `black_box` 用对了(没有 black_box,编译器可能把整个循环删了)
