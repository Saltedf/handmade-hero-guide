# Day 166 · 给资产操作加锁

> Day 165 修了紧急 bug(全局大锁)。今天 Casey **细化锁**:把不同操作分开锁,减少 contention。读 / 写分开,asset 类别分开,让多线程更顺畅。

## 0 · 为什么要有这一天

全局大锁的问题:**所有线程排队**。10 个 streaming 线程同时访问 cache,9 个等。性能回到单线程。

细化锁策略:

1. **读写分离**:读多用 RwLock 共享,写少独占
2. **分桶锁**:cache 按 hash 分 N 个桶,每桶独立锁。同一桶内串行,不同桶并行
3. **读时无锁**(RCU):读线程不锁,写时复制
4. **lock-free**:用原子操作代替锁

Casey 今天用 1 和 2(分桶 + RwLock)。Day 200+ 可能用 4。

细化锁的关键问题:**锁的粒度**——粗了等于没细化,细了死锁风险高。

经验值:

- 4-16 个分桶锁对中等规模 cache 好
- 锁粒度 = "访问局部性"的对应量
- 永远不在锁里做 I/O(磁盘 / 网络)

心理锚点:看完今天,你能给 asset cache 加分桶锁,benchmark 验证多核加速。

## 1 · Casey 今天做了什么

Casey 把 AssetStorage 改造:

```rust
struct AssetStorage {
    buckets: Vec<RwLock<HashMap<u32, Arc<LoadedAsset>>>>,  // N 个分桶
    // ref_count 单独 atomic
}

impl AssetStorage {
    fn get(&self, id: u32) -> Arc<LoadedAsset> {
        let bucket_idx = (id as usize) % self.buckets.len();
        // 读锁
        {
            let b = self.buckets[bucket_idx].read().unwrap();
            if let Some(a) = b.get(&id) {
                return Arc::clone(a);
            }
        }
        // 慢路径:加载
        let asset = self.load(id);
        // 写锁
        let mut b = self.buckets[bucket_idx].write().unwrap();
        b.entry(id).or_insert(Arc::new(asset));
        Arc::clone(b.get(&id).unwrap())
    }
}
```

Casey 讨论:

- **分桶数选 8 或 16**:经验值,大于 CPU 核数即可
- **桶选 hash**:简单 `% N` 或 `hash(id) % N`
- **RwLock 比 Mutex 快**:读多场景
- **要避免 false sharing**:多个桶的锁不要在同一 cache line(否则锁变量互相干扰)

### False Sharing

```rust
// 坏:多个 Mutex 紧挨
struct Bad {
    m1: Mutex<u64>,
    m2: Mutex<u64>,  // 和 m1 在同一 cache line(64 字节)
}

// 好:padding
#[repr(C)]
struct Good {
    m1: Mutex<u64>,
    _pad1: [u8; 56],  // 让 m2 在下一个 cache line
    m2: Mutex<u64>,
}
```

Rust crate `crossbeam::CachePadded` 自动加 padding。

## 2 · 心智模型

### 类比:多入口停车场

停车场有 1 个入口时,所有车排队。开 8 个入口,每车按车牌尾号选入口(0-7),8 路并行。

只要车牌尾号分布均匀,8 入口 → 8 倍吞吐。

asset 分桶也是:`bucket_idx = id % N`,N 路。

### 严谨模型:锁粒度

```
全局锁(Mutex<HashMap>):       并发度 = 1
分桶锁(Vec<RwLock<HashMap>>):  并发度 = N(读) / 1(写)
lock-free:                    并发度 = ∞(理论)
```

实际 N=8-32 已饱和(受内存带宽限制)。

### RwLock 内部

`RwLock` 维护:

- reader count(原子)
- writer flag(原子)

读时:原子增 reader count。如果 writer flag = 0,放行;否则 spin / sleep。
写时:原子 cas writer flag。已 reader 在,等所有 reader 完。

Rust `std::sync::RwLock` 用 OS 实现(`pthread_rwlock_t`)。`parking_lot::RwLock` 用 futex,更快。

### 死锁避免

细化锁的风险:**lock ordering**。两个线程以不同顺序拿两把锁,可能死锁。

避免规则:**全局固定顺序**(如按地址、按 id)拿锁。

```rust
// 坏:可能死锁
fn transfer(a: &Account, b: &Account, amount: u64) {
    let _la = a.lock();
    let _lb = b.lock();  // 不同调用顺序不同锁顺序
    // ...
}

// 好:按地址排序
fn transfer(a: &Account, b: &Account, amount: u64) {
    let (first, second) = if a as *const _ < b as *const _ { (a, b) } else { (b, a) };
    let _l1 = first.lock();
    let _l2 = second.lock();
    // ...
}
```

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 RwLock 在"读多写少"时比 Mutex 快?写多时反而慢?

**参考解答**:RwLock 允许多读并发。读时只增 reader count(原子),不阻塞其他读。所以读吞吐 = N(线程数)。

写时要等所有 reader 完成,期间新 reader 也要等(防饿死)。所以写时吞吐 = 1。

写多时:每次写都要等读,频繁切换,实际比 Mutex 慢(管理 reader count 开销)。

### Lv2 · 动手实践

**题**:把 Day 165 的 cache 改成 8 分桶 RwLock。Benchmark 对比单 Mutex 的吞吐。

**参考解答**:

```rust
use std::collections::HashMap;
use std::sync::{Arc, RwLock};
use std::thread;
use std::time::Instant;

const NUM_BUCKETS: usize = 8;

struct ShardedCache {
    buckets: Vec<RwLock<HashMap<u32, Arc<String>>>>,
}

impl ShardedCache {
    fn new() -> Self {
        let mut buckets = Vec::with_capacity(NUM_BUCKETS);
        for _ in 0..NUM_BUCKETS {
            buckets.push(RwLock::new(HashMap::new()));
        }
        Self { buckets }
    }

    fn get(&self, id: u32) -> Arc<String> {
        let idx = (id as usize) % NUM_BUCKETS;
        {
            let b = self.buckets[idx].read().unwrap();
            if let Some(a) = b.get(&id) {
                return Arc::clone(a);
            }
        }
        // 慢路径
        let asset = Arc::new(format!("asset_{}", id));
        let mut b = self.buckets[idx].write().unwrap();
        b.entry(id).or_insert_with(|| Arc::clone(&asset));
        Arc::clone(b.get(&id).unwrap())
    }
}

fn main() {
    let cache = Arc::new(ShardedCache::new());
    let num_threads = 8;
    let ops_per_thread = 100_000;

    let start = Instant::now();
    let mut handles = Vec::new();
    for t in 0..num_threads {
        let c = Arc::clone(&cache);
        handles.push(thread::spawn(move || {
            for i in 0..ops_per_thread {
                let id = ((i + t * 7) % 1000) as u32;  // 模拟热点
                c.get(id);
            }
        }));
    }
    for h in handles { h.join().unwrap(); }
    let elapsed = start.elapsed();
    println!("time: {:?}", elapsed);
    println!("throughput: {:.0} ops/s",
        (num_threads * ops_per_thread) as f64 / elapsed.as_secs_f64());
}
```

## 8 · Rust / Arch 落地代码

```rust
use std::collections::HashMap;
use std::sync::{Arc, RwLock};
use std::thread;
use std::time::Instant;

const NUM_SHARDS: usize = 16;

struct ShardedAssetCache {
    shards: Vec<RwLock<HashMap<u32, Arc<String>>>>,
    hits: std::sync::atomic::AtomicU64,
    misses: std::sync::atomic::AtomicU64,
}

impl ShardedAssetCache {
    fn new() -> Self {
        let mut shards = Vec::with_capacity(NUM_SHARDS);
        for _ in 0..NUM_SHARDS {
            shards.push(RwLock::new(HashMap::new()));
        }
        Self {
            shards,
            hits: 0.into(),
            misses: 0.into(),
        }
    }

    fn shard_idx(&self, id: u32) -> usize {
        // 简单 hash
        let h = id.wrapping_mul(0x9E3779B9);
        (h as usize) % NUM_SHARDS
    }

    fn get(&self, id: u32) -> Arc<String> {
        let idx = self.shard_idx(id);
        // 读锁
        {
            let shard = self.shards[idx].read().unwrap();
            if let Some(a) = shard.get(&id) {
                self.hits.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
                return Arc::clone(a);
            }
        }
        // 慢路径
        self.misses.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
        let asset = format!("asset_{}", id);
        let mut shard = self.shards[idx].write().unwrap();
        // 二次检查
        let entry = shard.entry(id)
            .or_insert_with(|| Arc::new(asset));
        Arc::clone(entry)
    }
}

fn main() {
    let cache = Arc::new(ShardedAssetCache::new());

    // benchmark
    let num_threads = 8;
    let ops_per_thread = 200_000;
    let range = 1000u32;  // 1000 个不同 id

    let start = Instant::now();
    let mut handles = Vec::new();
    for t in 0..num_threads {
        let c = Arc::clone(&cache);
        handles.push(thread::spawn(move || {
            let mut state = t as u32;
            for _ in 0..ops_per_thread {
                state = state.wrapping_mul(1664525).wrapping_add(1013904223);
                let id = state % range;
                c.get(id);
            }
        }));
    }
    for h in handles { h.join().unwrap(); }
    let elapsed = start.elapsed();

    println!("threads: {}", num_threads);
    println!("ops/thread: {}", ops_per_thread);
    println!("total ops: {}", num_threads * ops_per_thread);
    println!("range: {} unique ids", range);
    println!("time: {:?}", elapsed);
    println!("throughput: {:.0} ops/s",
        (num_threads * ops_per_thread) as f64 / elapsed.as_secs_f64());

    println!("hits: {}", cache.hits.load(std::sync::atomic::Ordering::Relaxed));
    println!("misses: {}", cache.misses.load(std::sync::atomic::Ordering::Relaxed));
}
```

**关键 Rust**:
- `RwLock::read()` / `RwLock::write()` 返回 guard
- `AtomicU64::fetch_add` 原子增加
- `Ordering::Relaxed` 只保证原子性,不保证跨线程顺序
- `wrapping_mul` 整数乘法溢出 wrap

## 10 · 补充材料:锁粒度的深入讨论

### A.1 全局大锁的真实代价(量化)

让我们严肃量化"全局 Mutex 让 8 核退化为单核"这件事。

设:
- N = 8(线程数)
- 每线程每秒调用 cache.get 100,000 次
- 每次 get 平均耗时 50 微秒(包括锁等待)
- 8 线程 × 100,000 ops/秒 = 800,000 ops/秒
- 800,000 × 50 μs = 40 秒(每秒)

但 CPU 实际只有 8 线程秒/秒。所以多出来的 32 秒 = **锁等待**。8 个线程同时调 get,只有一个能拿锁,其他 7 个 spin 或 sleep。

这是 Amdahl's Law 的极端例子。串行部分(锁)限制总加速。不管你有多少核,实际并发度 = 1。

### A.2 不同锁策略的并发度对比

| 策略 | 并发度 | 吞吐量(8 线程) | 备注 |
|---|---|---|---|
| 全局 Mutex | 1 | ~100k ops/s | 完全串行 |
| 单 RwLock(读多) | N(读)/1(写) | ~730k ops/s | 90% 读时 |
| 8 分桶 Mutex | min(N, num_shards) | ~700k ops/s | 桶均匀时 |
| 8 分桶 RwLock | min(N, num_shards) | ~750k-1M ops/s | 读多时最优 |
| 16 分桶 RwLock | min(N, num_shards) | ~780k ops/s | 边际收益递减 |
| lock-free(dashmap) | N(理论) | ~1-2M ops/s | 受内存带宽限制 |

### A.3 False sharing 详解(补充)

CPU cache 的最小单位是 **cache line**(64 字节)。当 CPU 修改一个变量,整个 cache line 标记为"修改",其他核的同一 cache line 失效。

如果两个独立 RwLock 在同一 cache line:

```rust
// 坏:多个 Mutex 紧挨,可能在同一 cache line(64 字节)
struct Bad {
    m1: Mutex<u64>,   // 24 字节
    m2: Mutex<u64>,   // 同 cache line
}
```

CPU 1 锁 m1 → m1 修改 → cache line 标记 modified → CPU 2 的 m2 同 line → CPU 2 必须重新加载 → 即便 m2 没动。

这叫 **false sharing**——变量看起来独立,cache 层面互相干扰。性能可能差 5-10×。

修复:padding 让 m1 和 m2 在不同 cache line:

```rust
#[repr(C)]
struct Good {
    m1: Mutex<u64>,
    _pad1: [u8; 56],  // 让 m1 占满 64 字节 cache line
    m2: Mutex<u64>,
}
```

或用 `crossbeam::CachePadded<T>`:

```rust
use crossbeam::CachePadded;

struct Good {
    m1: CachePadded<Mutex<u64>>,
    m2: CachePadded<Mutex<u64>>,
}
```

工业 Rust 并发原语(dashmap、crossbeam)几乎都用 CachePadded。

### A.4 parking_lot vs std::sync 的选择

Rust 标准库的 `std::sync::Mutex` 在 contention 时调用 OS futex syscall,慢。`parking_lot::Mutex` 实现自己的 futex,~2x 更快。

```toml
[dependencies]
parking_lot = "0.12"
```

```rust
use parking_lot::{Mutex, RwLock};

let data = RwLock::new(HashMap::new());
let guard = data.read();  // 不返回 Result(不 poison)
```

parking_lot 优势:
- 不 poison(panic 后锁仍可用)
- 不调 syscall 无 contention 时
- 更小的内存占用
- 提供 `RwLockReadGuard::map`(部分借用)

工业 Rust 几乎默认选 parking_lot。

### A.5 死锁的 Coffman 四条件

死锁发生的四个必要条件(Coffman 1971):

1. **互斥**(Mutual Exclusion):资源不可共享(锁本身)
2. **持有并等待**(Hold and Wait):持有锁 A,等锁 B
3. **不可剥夺**(No Preemption):锁不能强制释放
4. **循环等待**(Circular Wait):线程 1 等 2 持有的锁,2 等 1 持有的锁

只要打破任意一条,死锁不会发生。最常用的策略是**打破循环等待**——固定锁顺序。

**坏例子**(可能死锁):

```rust
fn transfer(a: &Account, b: &Account, amount: u64) {
    let _la = a.lock();     // 锁 A
    let _lb = b.lock();     // 锁 B
    // 转账逻辑
}

// 线程 1: transfer(x, y, 100) → lock(x), lock(y)
// 线程 2: transfer(y, x, 50)  → lock(y), lock(x)
// 死锁!
```

**好例子**(固定锁顺序):

```rust
fn transfer(a: &Account, b: &Account, amount: u64) {
    // 按地址排序,永远先锁地址小的
    let (first, second) = if a as *const _ < b as *const _ {
        (a, b)
    } else {
        (b, a)
    };
    let _l1 = first.lock();
    let _l2 = second.lock();
    // 转账
}
```

### A.6 锁粒度的经验法则

**何时该细化锁**:
- profiler 显示锁 contention 占总时间 > 5%
- 多核 CPU 没充分利用(top 显示单核 100%,其他 0%)
- 关键路径(渲染、物理)有锁等待

**何时 NOT 该细化锁**:
- 单线程代码(锁没用)
- contention 占总时间 < 1%(优化收益小)
- 死锁风险高(复合操作多)

**桶数经验**:
- 4-16 个分桶适合中等规模(1k-100k entries)
- 64-256 个分桶适合大规模(100k-10M entries)
- 桶数 > 线程数 × 2(避免热点)
- 桶数 = 2 的幂(模运算快,`x & (N-1)` 等价 `x % N`)

**永远不在锁里做的事**:
- I/O(磁盘、网络):几毫秒到几秒,所有等待线程卡死
- 长时间计算:同上
- 调用其他锁:死锁风险
- 分配内存(分配器可能有自己的锁)

### A.7 工业级实现的进一步选项

如果 8-16 分桶 RwLock 仍不够快,下一层是:

**lock-free 并发容器**:
- `dashmap`:并发 HashMap,内部 lock-free
- `crossbeam::SkipMap`:无锁 skip list
- `arc-swap`:原子 Arc 替换(适合读多写极少的配置)

**job system**:
- `rayon`:数据并行(work-stealing)
- `bevy_tasks`:Bevy 的 task 系统
- `tokio`:异步 task

**通信代替共享**:
- `crossbeam::channel`:多生产者多消费者 channel
- `flume`:更现代的 channel
- `tokio::sync::mpsc`:异步 channel

工业游戏(Unreal、Unity DOTS、Naughty Dog)更倾向于"通信代替共享"——避免锁的复杂性。

### A.8 Linux 内核锁机制参考

Linux 内核的锁机制丰富,游戏开发者可以学:

**spinlock**(自旋锁):

```c
spinlock_t lock = SPIN_LOCK_UNLOCKED;
spin_lock(&lock);
// 临界区
spin_unlock(&lock);
```

特点:忙等(spin),不睡眠。**只能用于短期持锁**(几微秒)。在不可睡眠上下文(中断处理)用。

**mutex**(互斥锁):

```c
DEFINE_MUTEX(my_mutex);
mutex_lock(&my_mutex);
// 临界区(可睡眠,如 I/O)
mutex_unlock(&my_mutex);
```

特点:持锁期间可睡眠(被调度走)。适合长期持锁(几毫秒)。

**rwlock**(读写锁):

```c
rwlock_t rwlock;
read_lock(&rwlock);
// 读临界区(多读)
read_unlock(&rwlock);

write_lock(&rwlock);
// 写临界区(独占)
write_unlock(&rwlock);
```

**seqlock**(序列锁):读不锁,写时序列号 +1,读完后检查序列号。如果变了,重读。适合"写极少,读无限"场景。

**RCU**(Read-Copy-Update):读完全无锁(直接读指针),写时复制。Linux 内核大量用(路由表、namespace 等)。

```c
// 读
rcu_read_lock();
struct foo *p = rcu_dereference(global_ptr);
// 使用 p
rcu_read_unlock();

// 写
struct foo *new = create_new();
struct foo *old = rcu_dereference_protected(global_ptr, ...);
rcu_assign_pointer(global_ptr, new);
synchronize_rcu();  // 等所有读者退出
free(old);
```

RCU 是 Linux 的杀手锏,允许极高效的读。但实现极复杂,只有内核用。

**futex**(Fast Userspace Mutex):Linux 用户态锁的基础。`std::sync::Mutex` 内部用 futex。

```c
// 简化原理
int lock_state = 0;  // 0 = 空闲,1 = 占用

lock() {
    while (true) {
        // 用户态 CAS
        if (atomic_cas(&lock_state, 0, 1) == 0) return;
        // 失败,调 syscall 在内核等
        futex(&lock_state, FUTEX_WAIT, 1);
    }
}

unlock() {
    atomic_set(&lock_state, 0);
    // 唤醒等待者
    futex(&lock_state, FUTEX_WAKE, 1);
}
```

futex 在无 contention 时纯用户态(快),有 contention 才 syscall(慢但正确)。

### A.9 Rust 锁的生态层次

Rust 锁的生态层次清晰:

**第 1 层:标准库**。
- `std::sync::Mutex<T>`:基本互斥锁
- `std::sync::RwLock<T>`:读写锁
- 内部基于 OS futex,跨平台

```rust
use std::sync::{Mutex, RwLock, Arc};

let data = Arc::new(Mutex::new(HashMap::new()));
let guard = data.lock().unwrap();  // 返回 Result(可能 poison)
```

**第 2 层:parking_lot**(更快的实现,工业默认)。

**第 3 层:async 锁**(tokio / async-std)。

```rust
use tokio::sync::Mutex;

let data = Mutex::new(HashMap::new());
let guard = data.lock().await;  // 异步,不阻塞 executor
```

异步锁不能跨 await 持有(否则死锁)。`tokio::sync::Mutex` 处理这个。

**第 4 层:lock-free**。
- `crossbeam`:无锁 queue / stack / skip list
- `dashmap`:并发 HashMap
- `arc-swap`:原子 Arc 替换

```rust
use dashmap::DashMap;

let map = DashMap::new();
map.insert(1, "hello");  // 无显式锁
let v = map.get(&1);
```

DashMap 内部分桶(类似 Casey 的实现),但用 lock-free 算法。

**第 5 层:spin**(自旋锁,谨慎用)。

```rust
use spin::Mutex;

let data = Mutex::new(0);
let guard = data.lock();  // 纯 spin,无 syscall
```

只在"持锁极短"(几纳秒)时用。否则浪费 CPU。SMP 内核空间常用,用户态慎用。

**反模式**:
- ❌ 自己实现 lock-free 算法——99% 写错,用 `crossbeam`
- ❌ 用 `RefCell` 跨线程——编译错,但 `Mutex` 才对
- ❌ 持锁跨 await——死锁
- ❌ 在锁里调磁盘 I/O——所有线程等
- ❌ 用 `unsafe` 绕过 Mutex——失去 Rust 安全保证

### A.10 工业游戏引擎的并发设计

**Unity**(老式):用全局 GIL 风格的锁,主线程 + worker 线程用 job system。Job 是只读数据快照,worker 处理后写回主线程。**避免锁**,通过"数据拷贝"换并行。

**Unreal Engine 5**:用 **Task Graph** 系统。开发者声明 task 依赖(task A 依赖 task B 的输出),引擎调度器自动并行执行无依赖的 task。底层用细粒度锁,但开发者不直接接触锁。

**Bevy**:Rust 生态旗舰。用 ECS + system 并行。Bevy 的 system 声明它读 / 写哪些 resource,引擎根据依赖图并行执行无冲突的 system。冲突的 system 串行。**编译时检查**(Rust 借用检查器 + Bevy 的 system trait)保证安全。

**Naughty Dog**(Sony 第一方,Uncharted / Last of Us):GDC 演讲经典。他们的方案是 **lock-free job system**——完全无锁,用 atomic queue + job 依赖。复杂但极快。

**Casey 的 HH**:教学项目,自己实现细粒度锁。Day 166 是分桶 + RwLock 的标准方案。

**工业级 job system 的核心思想**:
- 不共享状态,task 之间用消息传递
- 数据按 archetype 分组(SoA layout,cache friendly)
- 依赖图自动调度

如果你写 Rust 游戏,考虑用 `rayon`(数据并行)+ `bevy_tasks`(job system)+ `dashmap`(并发 HashMap)。不用自己写细粒度锁。

### A.11 测量锁竞争(Linux 工具链)

**测量 contention**:

```bash
# perf 看锁等待
sudo perf stat -e sched:sched_contention,sched:sched_switch ./my_program

# 看 futex 调用
sudo perf stat -e syscalls:sys_enter_futex ./my_program

# 用 eBPF 跟踪锁等待
sudo bpftrace -e 'tracepoint:sched:sched_contention { @[comm] = count(); }'
```

**测量 cache miss**(false sharing 检测):

```bash
sudo perf stat -e cache-misses,L1-dcache-load-miss ./my_program
# 如果 miss 率高,可能 false sharing
```

**测量实际并发度**:

```bash
# 用 htop 看 CPU 使用率,理想是所有核接近 100%
htop -p $(pgrep my_program)
```

如果只有 1 个核 100%,其他 0%,说明锁竞争严重。所有核 100% 才是好并行。

**ThreadSanitizer 检测 race condition**:

```bash
# Rust nightly + TSan
RUSTFLAGS="-Zsanitizer=thread" cargo +nightly run
```

TSan 能检测 race condition 和死锁,工业 Rust 项目 CI 必跑。

**helgrind(valgrind 工具)检测锁问题**:

```bash
valgrind --tool=helgrind ./my_program
# 检测 race condition、死锁、锁顺序违反
```

helgrind 慢(20-50x),但能发现极难调试的并发 bug。

### A.12 死锁诊断真实案例

**案例 1:简单死锁(2 锁循环)**

```rust
// 线程 1
let a = lock(A);
let b = lock(B);  // 等 B

// 线程 2(同时)
let b = lock(B);
let a = lock(A);  // 等 A
// 死锁!
```

诊断:`gdb` attach 进程,看 backtrace。线程 1 在 `lock(B)` 等待,线程 2 在 `lock(A)` 等待。

**案例 2:隐蔽死锁(锁顺序违反)**

```rust
// 函数 A 调用函数 B,各自持锁
fn function_a() {
    let _g = mutex_a.lock();
    function_b();  // 调 B,B 也拿锁
}

fn function_b() {
    let _g = mutex_b.lock();
    // 如果 B 同时拿 A,死锁
}

// 另一线程:
fn function_c() {
    let _g = mutex_b.lock();
    function_d();  // 调 D,D 拿 A
}

fn function_d() {
    let _g = mutex_a.lock();
}
```

诊断:画"锁依赖图",发现环。

**案例 3:隐蔽死锁(Rust async)**

```rust
async fn bad() {
    let _g = mutex.lock().await;
    other_async_op().await;  // 持锁跨 await!
}
```

async runtime 可能复用同一 worker 线程,持锁跨 await 会死锁。

修复:不在锁里 await,或者用 `tokio::sync::Mutex`。

### A.13 性能优化的"测量不要猜"原则

Casey 在视频里反复强调:**测量比猜测可靠**。

错误优化流程(猜):
1. "我觉得 RwLock 慢"
2. 改成 lock-free
3. 一周后发现没快多少
4. 重读代码,发现 bottleneck 是别处

正确流程(测):
1. `cargo flamegraph` 看 CPU 时间分布
2. 发现 80% 时间在 `Mutex::lock` 等待
3. 改成分桶锁
4. 再测,看到 lock 等待降到 10%
5. 看下一个 bottleneck

```bash
# 装 flamegraph 工具
cargo install flamegraph

# 跑
cargo flamegraph --release
# 生成 SVG flamegraph,浏览器打开
```

Flamegraph 让你**视觉化**看到 CPU 时间花在哪。横轴 = 调用栈,纵轴 = 函数层级,宽度 = CPU 时间占比。

宽的"火焰"就是 hotspot。优化宽的,忽略窄的。这是工业优化的核心工具。
