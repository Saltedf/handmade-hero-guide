# Day 148 · 写资产文件头部

> 昨天 Day 147 设计了 .hha 的格式。今天开始写**打包器**(packer):一个独立的程序,读散文件 BMP/WAV,输出 .hha。第一步是写文件头部——把 magic、version、tag_count、asset_count 写进文件开头 16 字节。看起来简单,但里面藏着 4 个工程细节:endianness、padding、错误处理、build 集成。

## 0 · 为什么要有这一天

打包器(asset builder)是游戏工程化最容易被忽视的角色。它本身不是游戏的一部分,运行时不会跑;但它决定:

1. **游戏启动时间**:打包器没把 asset 排好序,游戏读时磁盘寻道多,启动慢
2. **build 时间**:大游戏 asset 几十 GB,打包器慢,每次 build 几小时,开发节奏受影响
3. **文件大小**:打包器做压缩 / 去重,最终 .hha 大小决定下载时间
4. **跨平台**:Windows / Mac / Linux 各自的字节序、对齐、路径分隔符,打包器要统一

专业游戏团队的 build 工程师是个独立岗位,负责:

- 资产管道(asset pipeline):美术资产 → 中间格式 → 平台专用格式
- 增量构建:只重新打包改动的资产
- 分布式构建:多机器并行打包
- 平台变体:Windows / PS5 / Xbox / Switch 各一份

今天 Casey 写的是教学版打包器,但思路对工业级有用。重点是:**写头部**这件事看起来 5 行代码,但里面有 4 个具体决策:

1. **字节序**:LE 还是 BE?写文件用哪个?
2. **padding**:结构体自然对齐 vs 紧凑?
3. **错误处理**:写失败怎么办?磁盘满怎么办?
4. **build 集成**:打包器作为独立 exe 还是 cargo build 一部分?

心理锚点:看完今天,你能写一个 Rust 程序读一个空目录,生成一个 16 字节的合法 .hha 文件,用 `file` / `xxd` 验证它符合 Day 147 设计的规范。

## 1 · Casey 今天做了什么

Casey 在 HH 里创建了 `handmade_asset_builder.cpp`(独立 exe),功能是:

1. 接受一个输出文件路径(`test1.hha`)
2. 打开文件(`CreateFile` Windows API)
3. 写 16 字节头部:
   - `HHA2` magic
   - version = 1
   - tag_count = 0(还没填)
   - asset_count = 0(还没填)
4. 关闭文件

视频里 Casey 重点讨论:

- **为什么要独立 exe?**——打包器只在 build 时跑,不进游戏 exe。这样减小游戏体积,且**修改打包器逻辑不需要重编游戏**。
- **`asset_count` 一开始写 0,因为还不知道总数**:Day 149 会重新打开文件,在所有 asset 写完后回头更新 count。或者今天 Casey 用另一种思路——先扫描目录得到 count,再写 header。两种都可以,Casey 选了"两阶段写"。
- **Windows vs Linux 文件 API**:Windows 用 `CreateFile`/`WriteFile`/`CloseHandle` 三件套,Linux 用 `open`/`write`/`close`。Rust 的 `std::fs::File` 跨平台抽象。

## 2 · 心智模型

### 类比:写合同

一份合同要先有**封面**(标题、版本、签约方),然后是**正文**(条款),最后是**签字**。

你写合同时:

- **方案 A**:从头到尾顺序写。写到正文时,你不知道里面会有多少条,所以"条款数"先空着,最后填。
- **方案 B**:先写完整草稿,数清楚条数,再正式誊写。

方案 A 是 Casey 用的"两阶段写"。优点:不用先扫一遍。缺点:文件中间要 seek 回去改 header(但 16 字节小,几乎免费)。

方案 B 是 "先遍历,再生成"。优点:header 一次写对。缺点:遍历两次。

工业级 asset 打包通常用方案 B,因为还有更复杂的元数据(每个 asset 的 hash、tag 索引等)需要预扫。

### 严谨模型:文件写入的几个原语

```rust
use std::fs::File;
use std::io::{Write, Seek, SeekFrom};

let mut f = File::create("out.hha")?;

// 写 4 字节
f.write_all(&magic)?;                    // cursor 移到 4

// 写 u32
f.write_all(&version.to_le_bytes())?;    // cursor 移到 8

// seek 到 0
f.seek(SeekFrom::Start(0))?;

// 重写 header(覆盖)
f.write_all(&new_header)?;
```

关键 Rust trait:

- `Write` —— 提供 `write_all(&[u8])`,顺序写
- `Seek` —— 提供 `seek(SeekFrom::Start(n))` / `Current(n)` / `End(n)`
- `File` 同时实现 Write 和 Seek

**为什么需要 BufWriter?** `File::write_all` 每次调用都是 syscall,字节级写 syscall 开销大。`BufWriter::new(file)` 包装一层 8 KB 缓冲,攒够再 syscall,速度 10-100 倍。

### Endianness 和 to_le_bytes

Rust 的 `u32::to_le_bytes()` 返回 `[u8; 4]`,小端字节序。`write_all(&[u8])` 接受任意 `[u8]`。组合起来:

```rust
let n: u32 = 0x12345678;
f.write_all(&n.to_le_bytes())?;
// 文件里:78 56 34 12(低字节在前)
```

为什么不用 `bincode`?Casey 教学,直接字节写更透明。Rust 生态里 `bincode` 是更高级的选择,但你不懂字节序就用了它,会留下盲区。

### Padding 的坑

`#[repr(C)]` 的结构在 Rust 里**可能仍有 padding**:

```rust
#[repr(C)]
struct Bad {
    a: u8,    // offset 0
    // padding: 1-3 bytes
    b: u32,   // offset 4
}
// size = 8
```

如果直接 `bytes_of(&bad)` 写文件,你写了 8 字节(包括 3 字节 padding,值未定义)。**读回来时 padding 可能不同**(不同编译器、不同平台)。

解决:要么 packed(`#[repr(C, packed)]`,但访问字段变成 unsafe),要么显式写出每个字段(没有 padding)。Casey 用后者。

### 错误处理的三个层次

1. **panic**:不可恢复,`unwrap()` / `expect("msg")`。打包器里可以用——build 失败就该停。
2. **Result<T, E>**:可恢复。返回 `Result<(), io::Error>`,让调用者决定。
3. **自定义 Error**:多个错误源(io + 解析 + 验证),用 `thiserror` crate。

打包器用 Result 即可,build 失败简单报错退出。

## 3 · 四域深入

### 3.1 · 游戏编程视角

工业级打包器架构:

```
[美术源文件]    →  [导入器 Importer](转中间格式)
                      ↓
                  [处理器 Processor](压缩、mipmap、 LOD)
                      ↓
                  [打包器 Packer](写 .hha / .pak)
                      ↓
                  [游戏运行时]
```

每一步可能缓存(增量构建)、并行(多核)、分布式(多机器)。

Unreal 的 `UnrealPak`、Unity 的 `AssetBundleBuilder`、Godot 的 `godot --export-pack` 都是这套架构。

**关键概念:asset import vs asset processing**。import 把美术格式转运行时格式(BMP → RGBA8);processing 改变内容(mipmap、压缩、LOD)。两者分开让 build 灵活。

### 3.2 · Linux 系统编程视角

Linux 文件 I/O 速查:

| syscall | 含义 | Rust 对应 |
|---|---|---|
| `open(path, flags)` | 打开文件 | `File::create` / `File::open` |
| `read(fd, buf, n)` | 读 | `Read::read` |
| `write(fd, buf, n)` | 写 | `Write::write` |
| `lseek(fd, offset, whence)` | 移动文件指针 | `Seek::seek` |
| `close(fd)` | 关闭 | `Drop::drop` |
| `fsync(fd)` | 刷盘 | `File::sync_all` |
| `ftruncate(fd, len)` | 改文件大小 | `File::set_len` |
| `mmap(...)` | 映射 | `memmap2::Mmap::map` |

**fsync 很重要**:write 只把数据写到内核 page cache,断电会丢。fsync 强制刷到磁盘。打包器写完最后要 fsync,否则 build 完立刻断电,.hha 是空的。

```rust
use std::os::unix::io::AsRawFd;
let f = File::create("out.hha")?;
f.write_all(&data)?;
f.sync_all()?;          // fsync(2)
// 或更直接:libc::fsync(f.as_raw_fd())
```

### 3.3 · Rust 生态视角

Rust 的文件写入风格对比:

**方式 A:bytes_of + write_all(本日 Casey 风格)**

```rust
use bytemuck::bytes_of;
f.write_all(bytes_of(&header))?;
```

简单透明,但要求 `T: Pod`,且**有 padding 风险**。

**方式 B:逐字段 write_all**

```rust
f.write_all(&header.magic)?;
f.write_all(&header.version.to_le_bytes())?;
f.write_all(&header.tag_count.to_le_bytes())?;
f.write_all(&header.asset_count.to_le_bytes())?;
```

啰嗦但**零 padding 风险**,字节序显式。

**方式 C:serde + bincode**

```rust
use bincode::serialize_into;
serialize_into(&mut f, &header)?;
```

最简洁,但隐藏了字节序(默认 LE,可配置)。黑盒。

教学阶段推荐 B(透明);生产用 C(简洁)。Casey 在 HH 用 A 的等价 C 版本(C-style struct + 直接 fwrite)。

### 3.4 · build 系统视角

打包器怎么集成进 build?

**方案 1:独立 exe + 手动调用**

```bash
# 终端
./asset_builder output.hha input_dir/
```

**方案 2:build.rs(cargo 编译时)**

```rust
// build.rs
fn main() {
    println!("cargo:rerun-if-changed=assets/");
    std::process::Command::new("./target/debug/asset_builder")
        .arg("target/game.hha")
        .arg("assets/")
        .status()
        .unwrap();
}
```

每次 cargo build 都会跑 asset_builder。`rerun-if-changed` 让 cargo 只在 assets/ 变化时重跑。

**方案 3:Just / Makefile**

```makefile
game.hha: $(wildcard assets/*)
    ./asset_builder $@ assets/
```

独立、可控、调试方便。

Casey 在 HH 用方案 1 + Windows batch script。Rust 推荐方案 3(Just 是 Rust 写的现代 Make)。

## 5 · 对照与变奏

### 文件写入历史

| 时代 | API | 特点 |
|---|---|---|
| 1970s Unix | open/write/close | 系统调用 |
| 1980s C stdio | fopen/fwrite/fclose | 带 buffer |
| 1990s Win32 | CreateFile/WriteFile | Windows 专用 |
| 2000s async I/O | io_uring / IOCP | 高并发 |
| 2020s Rust | std::fs::File + traits | 安全 + 跨平台 |

Rust 的 `File` 接近 Unix API,提供零开销抽象。

### 不同 build 系统的 asset 处理

| 引擎 | 工具 | 输出 |
|---|---|---|
| Unreal | UnrealPak | .pak |
| Unity | ScriptablePipeline | .bundle |
| Godot | export preset | .pck |
| Casey HH | asset_builder.exe | .hha |
| Bevy | 直接目录 | (无打包) |

Bevy 没打包,直接读散文件——简化开发,部署时再考虑。Casey HH 教学需要,做了 .hha。

### Padding 在不同语言的解决

| 语言 | 工具 |
|---|---|
| C | `#pragma pack(1)` 或 `__attribute__((packed))` |
| Rust | `#[repr(C, packed)]` 或显式字段 |
| Go | `binary.Write` (逐字段) |
| Python | `struct.pack` (格式字符串) |
| Java | `ByteBuffer.order(LITTLE_ENDIAN).putInt(x)` |

Rust `#[repr(C, packed)]` 访问未对齐字段是 undefined behavior(UB),要用 `addr_of!` 读。生产代码推荐显式逐字段写。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:写 .hha 文件时,如果不调用 `fsync`,build 完立刻断电,文件可能丢失部分内容。为什么?Linux 默认多长时间刷一次 page cache?

**参考解答**:`write` 把数据写到内核 page cache,不强制刷盘。Linux 默认有个内核线程 `pdflush`(现代叫 `flush` / `kworker`),周期性(~30 秒)扫描脏页刷到磁盘。如果断电发生在 write 后 30 秒内,数据丢失。`fsync` 强制立即刷盘,保证数据已持久化。

打包器写完 .hha 后调一次 `fsync` 是工程规范——build 系统经常在 build 后立刻进入下一步,如果资产没刷盘,后续步骤可能读到旧版本或损坏数据。

### Lv2 · 动手实践

**题**:写一个 Rust 程序,创建 `empty.hha`,内容是一个合法 header(magic=HHA2, version=2, tag_count=0, asset_count=0)。要求:

1. 用 `BufWriter`
2. 用逐字段 `write_all` + `to_le_bytes`(方式 B)
3. 最后 `fsync`
4. 用 `xxd` 验证内容是 `4848 4132 0200 0000 0000 0000 0000 0000`

**参考解答**:

```rust
use std::fs::File;
use std::io::{BufWriter, Write};

const HHA_MAGIC: [u8; 4] = *b"HHA2";
const HHA_VERSION: u32 = 2;

fn main() -> std::io::Result<()> {
    let file = File::create("empty.hha")?;
    let mut w = BufWriter::new(file);

    w.write_all(&HHA_MAGIC)?;
    w.write_all(&HHA_VERSION.to_le_bytes())?;
    w.write_all(&0u32.to_le_bytes())?;  // tag_count
    w.write_all(&0u32.to_le_bytes())?;  // asset_count

    w.flush()?;                          // 把 BufWriter 缓冲刷到 File
    drop(w);                             // 关闭 BufWriter(交还内部 buffer)

    // fsync
    let file = File::open("empty.hha")?;
    file.sync_all()?;

    println!("wrote empty.hha (16 bytes)");
    Ok(())
}
```

验证:

```bash
cargo run
xxd empty.hha
# 00000000: 4848 4132 0200 0000 0000 0000 0000 0000  HHA2............
stat -c%s empty.hha
# 16
```

## 8 · Rust / Arch 落地代码

完整打包器骨架(只写 header,Day 149 会扩展):

```rust
// Cargo.toml: 纯 std

use std::fs::{File, OpenOptions};
use std::io::{BufWriter, Write, Seek, SeekFrom};
use std::path::Path;

#[repr(C)]
#[derive(Copy, Clone, Debug)]
pub struct HhaHeader {
    pub magic: [u8; 4],
    pub version: u32,
    pub tag_count: u32,
    pub asset_count: u32,
}

pub const HHA_MAGIC: [u8; 4] = *b"HHA2";
pub const HHA_VERSION: u32 = 2;

impl HhaHeader {
    pub fn zero() -> Self {
        Self { magic: HHA_MAGIC, version: HHA_VERSION, tag_count: 0, asset_count: 0 }
    }

    /// 逐字段写(零 padding 风险)
    pub fn write_to<W: Write>(&self, w: &mut W) -> std::io::Result<()> {
        w.write_all(&self.magic)?;
        w.write_all(&self.version.to_le_bytes())?;
        w.write_all(&self.tag_count.to_le_bytes())?;
        w.write_all(&self.asset_count.to_le_bytes())?;
        Ok(())
    }

    /// 逐字段读
    pub fn read_from<R: std::io::Read>(r: &mut R) -> std::io::Result<Self> {
        let mut magic = [0u8; 4];
        r.read_exact(&mut magic)?;
        if magic != HHA_MAGIC {
            return Err(std::io::Error::new(
                std::io::ErrorKind::InvalidData,
                format!("bad magic: {:?}", magic),
            ));
        }

        let mut buf4 = [0u8; 4];
        r.read_exact(&mut buf4)?;
        let version = u32::from_le_bytes(buf4);

        r.read_exact(&mut buf4)?;
        let tag_count = u32::from_le_bytes(buf4);

        r.read_exact(&mut buf4)?;
        let asset_count = u32::from_le_bytes(buf4);

        if version != HHA_VERSION {
            return Err(std::io::Error::new(
                std::io::ErrorKind::InvalidData,
                format!("unsupported version {}", version),
            ));
        }

        Ok(Self { magic, version, tag_count, asset_count })
    }
}

/// 打包器入口:扫描 input_dir,生成 .hha
pub fn build_asset_file(output: &Path, _input_dir: &Path) -> std::io::Result<()> {
    // 1. 创建输出文件
    let file = File::create(output)?;
    let mut w = BufWriter::new(file);

    // 2. 写"占位" header(counts 还不知道,先写 0)
    HhaHeader::zero().write_to(&mut w)?;
    w.flush()?;

    // TODO Day 149: 扫描 input_dir,写每个 asset 的描述,然后更新 counts

    // 3. 回头更新 header(演示 seek 用)
    let header_size = std::mem::size_of::<HhaHeader>();
    let mut file = OpenOptions::new().write(true).open(output)?;
    file.seek(SeekFrom::Start(0))?;
    let final_header = HhaHeader {
        magic: HHA_MAGIC,
        version: HHA_VERSION,
        tag_count: 0,    // TODO Day 149
        asset_count: 0,
    };
    final_header.write_to(&mut file)?;
    file.sync_all()?;

    println!("built {} ({} bytes)", output.display(), header_size);
    Ok(())
}

fn main() -> std::io::Result<()> {
    let out = Path::new("test1.hha");
    let input = Path::new("assets/");
    std::fs::create_dir_all(input)?;
    build_asset_file(out, input)?;

    // 读回来验证
    let mut f = File::open(out)?;
    let header = HhaHeader::read_from(&mut f)?;
    println!("read back: {:?}", header);
    Ok(())
}
```

**关键 Rust**:
- `OpenOptions::new().write(true).open(path)` —— 已存在文件只写打开。和 `File::create`(会 truncate)不同。
- `SeekFrom::Start(0)` —— 绝对位置 0。`Current(0)` 是相对当前。`End(0)` 是从末尾。
- `read_exact(&mut buf)` —— 读满 buf 字节,不够则 EOF error。比 `read` 安全(后者可能返回少于请求的字节)。
- `file.sync_all()` —— Linux 上调 `fsync(2)`,保证数据已写入物理介质。

**预期输出**:
```
built test1.hha (16 bytes)
read back: HhaHeader { magic: [72, 72, 65, 50], version: 2, tag_count: 0, asset_count: 0 }
```

```bash
# 用 file 命令(虽然不识别 .hha,但能看到是 data)
file test1.hha
# test1.hha: data
```

**Troubleshooting**:
- `Permission denied` —— 当前目录不可写,`chmod +w .` 或换目录。
- `read back` 报 bad magic —— 字节序错(`to_be_bytes` 而不是 `to_le_bytes`)。
- 文件大小不是 16 —— 漏写一个字段或 padding,检查 `write_to` 4 个 write_all。
- `fsync` 失败 —— 文件系统不支持(如 tmpfs 部分配置),忽略或换目录。

### A.16 性能优化的层次(L1-L5)

**L1: 算法选择**
- O(N²) → O(N log N)
- 例: bubble sort → quicksort

**L2: 数据布局**
- AoS → SoA
- 例: Vec<Voxel> → struct { Vec<u8> materials, ... }

**L3: Micro**
- inline、branchless、SIMD
- 例: SIMD 4-wide float

**L4: 并行**
- multi-thread、SIMD、GPU
- 例: rayon par_iter

**L5: 架构**
- streaming、incremental、async
- 例: chunked world

每层收益递减难度递增。Proflier 决定优化哪层。
