# Day 128 · 推送时变换

> 把"算世界坐标"这一步从渲染器搬到 push 命令时。今天讨论的不是新算法,而是一个重要的工程取舍:**延迟计算 vs 提前计算**——什么时候把数据加工好放进 push buffer,什么时候让消费方用的时候再算。

## 0 · 为什么要有这一天

回顾 Day 121 的渲染流水线:游戏逻辑产生"渲染命令"(draw this bitmap at this position),push 进一个 buffer,渲染器(SIMD + 多线程 tile)从 buffer 读出来,逐 tile 渲染。

命令长这样:

```rust
struct RenderEntry {
    bitmap_id: BitmapId,
    local_position: Vec2,   // 局部坐标(相对 entity)
    entity_position: Vec2,  // entity 世界位置
    scale: f32,
    // ...
}
```

渲染器读到这个 entry,要算**世界坐标** = `entity_position + local_position * scale`,再做相机变换、投影、光栅化。每帧每个 entry 都要重复算一次世界坐标。

Casey 注意到一件事:**很多 entry 的世界坐标在游戏逻辑里其实已经算过了**(游戏为了 AI、碰撞、可见性测试,本来就要算 entity 的世界坐标)。现在 push 进去的是"半成品",渲染器再算一遍,这是冗余。

**今天的取舍**:把"局部 → 世界"的变换**前移到 push 时**。push entry 的时候就算好世界坐标,渲染器只管"把世界坐标投影到屏幕,blit"。

好处:
- 渲染器更简单,不需要知道 entity 的层级关系
- 渲染器更快,省一次乘加
- 世界坐标变换只在"必要时"(push 时)算一次,渲染 N 个 tile 时不用每个 tile 重算

代价:
- push buffer 每个 entry 大一点(多了 world_position 字段)
- 如果同一帧里 entity 在 push 之后又移动了,会渲染错误(但游戏循环里 push 在 update 之后,不会有这种 race)

这是一个看似简单实则深刻的工程教训:**确定性的、一次性的计算,尽量前移;灵活的、依赖上下文的计算,延后**。

心理锚点:做完今天你能(1)在你的引擎里识别"哪些计算应该 push 时做,哪些应该 render 时做";(2)说出 Casey 这个决策的 3 个理由和 1 个潜在风险;(3)在自己的 Rust 代码里用 enum + match 表达"不同种类的渲染 entry"。

## 1 · Casey 今天做了什么

Casey 在 Day 127 把内存对齐做好后,继续优化渲染 entry 的结构:

1. 修改 `RenderEntry` struct:把 `local_position` + `entity_position` + `scale` 三个字段合并成一个 `world_position`(push 时算好)
2. 修改 push 函数:`push_bitmap(queue, world_pos, bitmap_id, ...)` —— 接口直接吃世界坐标
3. 调用方(game update 代码)在 push 前算 `world_pos = entity_pos + local_offset * scale`,push 进去
4. 渲染器只读 `entry.world_position`,做相机变换 + 光栅化,不再做 entity-level 变换
5. benchmark 验证:渲染器每像素的指令数减少,速度提升 5-10%

这一天的核心:**减少抽象边界处的"往返计算"**。game 逻辑和 renderer 之间本来要传"完整信息让 renderer 自己组合",现在改成"game 把组合好的传给 renderer"。这种"sender 多做一点,receiver 少做一点"的设计,在性能敏感场景里非常常见。

## 2 · 心智模型

### 类比:外卖打包 vs 餐厅现做

想象一家寿司店:
- **餐厅现做**:服务员写订单"金枪鱼 + 米饭 + 紫菜",厨师(渲染器)收到订单后,从仓库拿原料,自己做寿司。灵活(可以根据客人喜好现场调整),但厨师忙,做每道菜要重读订单、重拿原料。
- **外卖打包**:服务员(游戏逻辑)提前把寿司做好,装盒,厨师(渲染器)只负责贴标签发货。死板(客人不能改),但厨师每单只要 10 秒。

**Push-time transforms 就是"外卖打包"模式**:游戏逻辑在 push 时把"原料组合好",渲染器只"贴标签发货"。

### 严谨原理:渲染 entry 数据流

老的(渲染时变换):
```
game_logic: entity_pos = (100, 200); local_offset = (5, 3)
            push(entry { entity_pos, local_offset, scale=2.0 })
                          ↓
push_buffer:[ { entity_pos=(100,200), local_offset=(5,3), scale=2.0 },
              { entity_pos=(300,400), local_offset=(0,0), scale=1.0 },
              ... 200 more entries ... ]
                          ↓
renderer:   for entry in push_buffer:
                world = entry.entity_pos + entry.local_offset * entry.scale
                screen = camera_transform(world)
                draw_bitmap(screen, entry.bitmap_id)
```

每帧每 entry 渲染器要算一次"世界坐标"。如果同一个 entry 跨多个 tile(大 bitmap),每个 tile 都要重算(虽然 SIMD 部分能掩盖成本)。

新的(push 时变换):
```
game_logic: entity_pos = (100, 200); local_offset = (5, 3); scale = 2.0
            world = entity_pos + local_offset * scale  // 算一次
            push(entry { world, bitmap_id, ... })
                          ↓
push_buffer:[ { world=(110, 206), bitmap_id=... },
              { world=(300, 400), bitmap_id=... },
              ... ]
                          ↓
renderer:   for entry in push_buffer:
                screen = camera_transform(entry.world)  // 不再算 entity-level
                draw_bitmap(screen, entry.bitmap_id)
```

每帧每 entry 的世界坐标算一次,在 push 时(游戏逻辑代码里)。渲染器少做一次加法 + 乘法。

### 代价:push entry 变大

老 struct:
```rust
struct RenderEntry {
    bitmap_id: u32,         // 4
    entity_pos: Vec2,       // 8
    local_offset: Vec2,     // 8
    scale: f32,             // 4
    color: u32,             // 4
    sort_key: u32,          // 4
    // 总 32 字节
}
```

新 struct:
```rust
struct RenderEntry {
    bitmap_id: u32,         // 4
    world_pos: Vec2,        // 8
    color: u32,             // 4
    sort_key: u32,          // 4
    // padding 4 字节(对齐到 Vec2 的 8)
    // 总 24 字节(更小!)
}
```

实际上新 struct 更小,因为我们去掉了 `local_offset` 和 `scale`(都吸收进 `world_pos`)。这是 push-time transforms 的额外红利:**结构更紧凑 = cache 更友好**。

### 风险:如果 entity 在 push 之后又移动?

游戏循环长这样:
```rust
loop {
    process_input();
    update_simulation();   // entity 位置可能变
    push_render_entries(); // 在这里 push,entity 已固定
    render();              // 渲染期间 entity 不会变(逻辑单线程)
    swap_buffers();
}
```

push 和 render 在同一帧,中间没有 update,所以 entity 位置稳定。但如果以后引入异步渲染(渲染线程独立运行),push 完之后下一帧的 update 改了 entity,渲染器读 push buffer 还是看到旧 world_pos——但这没问题,因为旧的 world_pos 是上一帧该渲染的,新位置下一帧才渲染。

### Rust 表达:enum entry vs 字段堆砌

随着 entry 类型增加(纯 bitmap、文字、线段、矩形…),struct 里字段堆砌会失控。Casey 用 C 的 union + TypeTag,Rust 用 enum 更优雅:

```rust
enum RenderEntry {
    Bitmap {
        world_pos: Vec2,
        bitmap_id: BitmapId,
        color: u32,
    },
    Line {
        start: Vec2,
        end: Vec2,
        color: u32,
        thickness: f32,
    },
    Rectangle {
        min: Vec2,
        max: Vec2,
        color: u32,
    },
    Text {
        world_pos: Vec2,
        text: String,   // 注意:String 有所有权
        color: u32,
    },
}
```

**注意**:enum 的大小等于最大 variant + tag。如果 Text variant 用 `String`(24 字节),整个 enum 至少 32 字节。push buffer 里每 entry 都占这么大空间,cache 友好性下降。

工业级替代:
- **Type-erased trait object**:`Vec<Box<dyn Renderable>>`。每个 entry 一个 heap 分配,极慢
- **SoA 多 buffer**:`bitmaps: Vec<BitmapEntry>, lines: Vec<LineEntry>, ...`。每类 entry 各一个连续 buffer,SIMD 友好
- **Type tag + union**:`Vec<(EntryType, EntryUnion)>`。Casey 的 C 写法。Rust 里要用 `unsafe` union 或 `bytemuck`

Casey 在 HH 后期(Day 200+)会切到 SoA。今天先 enum 走起。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

"什么时候算"在游戏开发里是反复出现的取舍:

| 问题 | 提前算(push 时) | 延迟算(render 时) |
|---|---|---|
| 世界坐标 | ✅ Casey 选了 | 老 HH |
| 光照(每帧不变的部分) | 烘焙光照贴图 | 实时光照 |
| 动画曲线 | 烘焙到关键帧 | 实时插值 |
| 字符串格式化 | sprint 一次 | 每帧重新格式化 |
| 排序键 | push 时算 sort_key | render 时算 |

具体到 push-time transforms:

**好处 1:抽象边界清晰**。游戏逻辑负责"实体在哪",渲染器负责"画到屏幕"。push entry 是 contract。

**好处 2:可并行化**。push 完之后,push buffer 是只读的,渲染器可以多线程读无竞争。

**好处 3:debug 友好**。push buffer 是一份完整的"这一帧要画什么的快照",可以序列化、回放、对比。

**风险 1:数据冗余**。如果 entity 有 100 个子部件,每个子部件都要算 world_pos,push buffer 膨胀。

**风险 2:耦合**。push-time 计算隐含了"渲染坐标系约定",和 game logic 耦合。Casey 在 Day 350+ 重构时为了支持 3D 光照管线,又会拆开这种耦合。

游戏开发圈的工业做法:
- **Unreal Engine**:用 `FPrimitiveSceneProxy` 在 game thread 构造,传给 render thread。和 Casey 思路一致
- **Unity ECS**:用 `EntityCommandBuffer` 排队"渲染操作",render system 消费。同上
- **Bevy**:用 `RenderGraph`,render stage 时消费 game stage 产生的"render entities"

所有商业引擎都做了类似的"提前计算 + 命令缓冲"分离。Casey 在教学场景下从零开始讲这个设计。

### 3.2 · 🎨 图形学视角

push-time transforms 背后的图形学概念是 **MVP 矩阵分阶段应用**:

```
Model Space (entity 局部)
    ↓  Model 矩阵(M = T * R * S)
World Space (entity 在世界)
    ↓  View 矩阵(V)
Camera Space (相机视角)
    ↓  Projection 矩阵(P)
Clip Space / NDC
    ↓  Viewport transform
Screen Space
```

传统 OpenGL/D3D 在 vertex shader 里一次性做 `gl_Position = P * V * M * vertex`。所有计算搬到 GPU。

Casey 的渲染器是软件光栅化(Phase 4 还没切 GPU),所以这些矩阵在 CPU 上算。push-time transform 等价于"在 game logic 里算好 Model * View,把世界坐标传给 CPU 光栅化器",光栅化器只做 Projection + Viewport。

这是**部分预计算**(partial pre-computation):游戏逻辑算 World Space(因为它知道 entity 关系),渲染器算 Camera → Screen(因为它知道相机参数)。

GPU 渲染管线 Day 235+ Casey 会切到 OpenGL,那时 Model 矩阵的"提前计算"由 vertex shader 做(每顶点算一次)。但 push entry 里**还是要存 World Position**(给 GPU 做 frustum culling、shadow volume 测试用)。

### 3.3 · 🐧 Linux 系统编程视角

"提前计算 vs 延迟计算"在系统编程里也常见:

| 场景 | 提前 | 延迟 |
|---|---|---|
| DNS 解析 | 启动时 resolve 所有 host | 每次连接时 resolve |
| 文件元数据(stat) | 启动时 cache | 每次访问 stat |
| 字符串格式化 | 提前 format | 用时 format |
| 编译模板 | AOT 编译 | JIT 编译 |
| JSON 解析 | 启动 parse 到 struct | 用时 lazy parse |

Linux 内核的 VFS(Virtual File System)是经典案例:open() 时 inode 已经加载到内存,后续 read/write 不再查磁盘。这是"提前计算"——把 inode 拉到内存,然后所有操作都在内存里算。

Casey 的 push-time transforms 同样:把 entity-level 数据在 game update 时算好,render 时直接用,不重算。

Linux 上的另一个对应:`sendfile(2)` 系统调用。原本要从文件 read 到 user buffer,再 write 到 socket buffer,2 次 copy。`sendfile` 直接在 kernel 内部把文件数据搬到 socket,0 次 user copy。这是"提前计算 + 流水线优化"的极端形式。

### 3.4 · 🦀 Rust 生态视角

Rust 表达"提前计算好的 entry"有两个流派:

#### 流派 1:enum + 所有权

```rust
enum RenderEntry {
    Bitmap { world_pos: Vec2, id: BitmapId, color: u32 },
    Line { start: Vec2, end: Vec2, color: u32 },
}

let mut entries: Vec<RenderEntry> = Vec::with_capacity(1024);
entries.push(RenderEntry::Bitmap { world_pos: v, id, color });
```

**优点**:类型安全,match 强制处理所有 variant。
**缺点**:enum 大小 = 最大 variant,小 variant 浪费空间。

#### 流派 2:SoA 多 buffer

```rust
struct RenderQueues {
    bitmaps: Vec<BitmapEntry>,
    lines: Vec<LineEntry>,
    rectangles: Vec<RectEntry>,
}

struct BitmapEntry { world_pos: Vec2, id: BitmapId, color: u32 }
struct LineEntry { start: Vec2, end: Vec2, color: u32 }
struct RectEntry { min: Vec2, max: Vec2, color: u32 }

let mut queues = RenderQueues::default();
queues.bitmaps.push(BitmapEntry { world_pos: v, id, color });
queues.lines.push(LineEntry { start: a, end: b, color });
```

**优点**:每个 buffer 紧凑(无 variant padding),SIMD 友好(同类型连续)。
**缺点**:失去"全局 sort"(所有 entry 按深度排序需要 merge 多个 buffer)。

Casey 的 C 代码用 union + type tag(流派 1 的 unsafe 等价物)。Rust 教学版我们也用 enum,Phase 6+ 光照管线需要 sort 时切到 SoA。

#### 流派 3:Type-erased closure(反模式)

```rust
let mut entries: Vec<Box<dyn FnOnce(&mut Renderer)>> = Vec::new();
entries.push(Box::new(move |r| r.draw_bitmap(world_pos, id, color)));
```

**优点**:接口最灵活,任何渲染操作都能塞进去。
**缺点**:每 entry 一次 heap 分配(Box),闭包大小不可控。游戏开发不推荐。

#### 字段布局 vs Rust 默认重排

注意 Rust 默认 `#[repr(Rust)]` 会**重排字段**最小化 size。如果你 push entry 是:

```rust
struct Entry {
    color: u32,         // 4
    world_pos: Vec2,    // 8(对齐 4)
    id: BitmapId,       // 4
}
```

Rust 可能重排成 `{ world_pos, color, id }` size = 16,无 padding。但跨平台 / FFI 时要用 `#[repr(C)]` 强制顺序。

Casey 在 Day 126 的 push buffer 里用 `#[repr(C, align(16))]` 让 entry 既 SIMD 友好又 C ABI 兼容。Rust 里同样:

```rust
#[repr(C, align(16))]
#[derive(Copy, Clone)]
struct RenderEntry {
    world_pos: Vec2,    // 0
    bitmap_id: BitmapId,// 8
    color: u32,         // 12
    _pad: [u8; 4],      // 16
}
```

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **数据流水线(data pipeline)** —— 生产 → 缓冲 → 消费的三段式
- **Pre-computation(预计算)** —— 把未来要反复算的东西提前算一次缓存
- **Push vs Pull 模型** —— 主动推送(producer push)vs 被动拉取(consumer pull)的信息流方向
- **Command pattern(命令模式)** —— 把"要做的事"编码成对象,放进队列延后执行

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| push-time transform | game 算好世界坐标 push | 实体关系简单,渲染器不需 entity 上下文 | ✅ |
| render-time transform | push 半成品,renderer 算 | 渲染器要做 frustum culling、LOD 选择 | Day 350+ 可能切 |
| 双缓冲 + async render | push 完立刻 render thread 起 | 真·异步渲染,游戏逻辑和渲染解耦 | Day 122 提及,HH 没做 |
| Immediate mode | 没 push buffer,渲染函数直接画 | debug overlay、UI | Casey 的 debug overlay 用 |

详细说明:
- **Immediate mode** 是 Casey 的旧版做法:`debug_draw_line(...)` 函数直接调底层 blit。优点无状态,缺点不能批量优化。Phase 5 的 debug overlay 会用这个
- **双缓冲 + async render**:Unreal Engine 的标准做法。Game thread 产生 frame N 的 commands,render thread 在画 frame N-1,两个并行。HH 同步,Phase 5 Casey 也讨论过切异步

### 4.3 下级(内部零件)

- **RenderEntry enum/struct** —— 命令的数据结构
- **Push buffer(Vec<RenderEntry>)** —— 命令队列
- **PushBitmap / PushLine / PushRect 函数** —— typed push 接口
- **世界坐标变换**(`world = entity_pos + local_offset * scale`)—— 提前计算的核心
- **Sort key** —— 渲染顺序(透明物体后画、depth sort)用
- **Camera transform** —— renderer 算的部分

## 5 · 对照与变奏

### 同一原理在不同场景

**场景 A:数据库预聚合**。BI 报表每天生成,一种做法是"查询时算"(`SELECT SUM(sales) FROM ...`),另一种是"凌晨预计算写到 summary 表"(查询时直接读)。push-time transforms 对应后者。

**场景 B:编译器优化**。Constant folding:编译时算 `3 + 4` = `7`,不用运行时算。push-time transforms 是运行时的"constant folding"——push 时已知 entity_pos 和 local_offset,提前 fold 成 world_pos。

**场景 C:网络协议**。HTTP/2 的 HPACK 头部压缩,client 和 server 各自维护一份"已知头部表",发包只发 index。这是"提前计算好共享状态,传输时省"。

**场景 D:游戏 AI 的决策树**。NPC 决策可以"每帧重新评估世界状态"(贵),或"上次决策缓存 + 每隔 N 帧刷新"(便宜)。push-time transforms 类似后者——决策(entity_pos)固定,push 时基于此决策一次,renderer 不再决策。

### CPU 端 vs GPU 端

GPU 渲染管线天然是"延迟计算":vertex shader 每帧每顶点重算 `M * V * P * pos`。GPU 算力强,这样灵活。

CPU 软件光栅化(Casey 现在做的):CPU 算力相对弱,每顶点重算太贵。所以 Casey 把能提前算的算好。等切到 GPU(Day 235+),这些优化部分不再需要——GPU 反而**喜欢**所有计算集中到 shader 里(更适合大规模并行)。

这是 CPU vs GPU 思维差异:
- **CPU 优化**:减少计算量(预计算、cache、SIMD)
- **GPU 优化**:增加计算量以隐藏延迟(vertex shader 多算几次便宜,主内存访问贵)

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:判断以下说法对错,并解释:

1. "push-time transforms 让 push entry 变大,所以对 cache 不友好"
2. "push-time transforms 后,如果同一帧 entity 多次移动,渲染会用最后一次位置"
3. "Immediate mode GUI 没有 push-time transforms 这种取舍"
4. "push-time transforms 让异步渲染(渲染线程独立)变简单"

**参考解答**:
1. **错**。push-time transforms 让 entry **变小**(去掉 local_offset + scale,合并成 world_pos)。Casey 的 entry 从 32 字节降到 24 字节,cache 更友好。即使变大,只要减少的计算量超过 cache miss 代价,仍然值得。
2. **错**。游戏循环是单线程:`update → push → render → swap`。push 之后 entity 不再移动(下一帧才 update)。所以 push 时的 world_pos 就是这一帧渲染的位置。如果是异步渲染,下一帧 update 改 entity 不会影响上一帧已 push 的 entry。
3. **错**。Immediate mode GUI(如 Dear ImGui)每帧从零画,没有 push buffer。但**仍然有"什么时候算"的取舍**:每帧重算所有 vertex vs 缓存上一帧的 vertex。ImGui 每帧重算,代价是不能 batch 优化。
4. **对**。push-time transforms 把所有 entity-level 计算固定在 push entry 里。渲染器读 push buffer 是只读的,可以丢给任何线程(包括独立 render thread),不需要访问 game state。这是异步渲染的基础。

### Lv2 · 动手实践

**题**:在 Rust 项目里实现 push buffer + push-time transforms。

要求:
1. 定义 `RenderEntry` enum,variants: Bitmap / Line / Rectangle
2. 实现 `PushBuffer` struct,封装 `Vec<RenderEntry>`
3. 实现 typed push 方法:`push_bitmap(&mut self, world_pos: Vec2, id: u32, color: u32)` 等
4. 实现一个简单的 renderer:遍历 entries,print 出"在 (x,y) 画 bitmap #id"
5. main 演示:game logic 算 entity world_pos,push 进 buffer,renderer 消费

完成标准:`cargo run` 输出类似 `Rendering bitmap #1 at (110.0, 206.0) color 0xff0000`。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
}

// BitmapId 是 newtype,防止和 u32 混用
#[derive(Copy, Clone, Debug, PartialEq, Eq)]
struct BitmapId(u32);

// 渲染 entry。enum 大小 = 最大 variant + tag
// Bitmap: Vec2(8) + BitmapId(4) + color(4) = 16
// Line:   Vec2(8) + Vec2(8) + color(4) + thickness(4) = 24
// Rectangle: Vec2(8) + Vec2(8) + color(4) + pad(4) = 24
// 整个 enum size = 24 + 4(tag) = 28 → round up to 32
#[derive(Clone, Debug)]
enum RenderEntry {
    Bitmap {
        world_pos: Vec2,
        id: BitmapId,
        color: u32,
    },
    Line {
        start: Vec2,
        end: Vec2,
        color: u32,
        thickness: f32,
    },
    Rectangle {
        min: Vec2,
        max: Vec2,
        color: u32,
    },
}

// Push buffer:简单的 Vec 包装
struct PushBuffer {
    entries: Vec<RenderEntry>,
}

impl PushBuffer {
    fn new() -> Self { Self { entries: Vec::with_capacity(1024) } }

    // Typed push:接口吃世界坐标(push-time transform 已发生)
    fn push_bitmap(&mut self, world_pos: Vec2, id: BitmapId, color: u32) {
        self.entries.push(RenderEntry::Bitmap { world_pos, id, color });
    }
    fn push_line(&mut self, start: Vec2, end: Vec2, color: u32, thickness: f32) {
        self.entries.push(RenderEntry::Line { start, end, color, thickness });
    }
    fn push_rectangle(&mut self, min: Vec2, max: Vec2, color: u32) {
        self.entries.push(RenderEntry::Rectangle { min, max, color });
    }

    fn clear(&mut self) { self.entries.clear() }
    fn iter(&self) -> std::slice::Iter<RenderEntry> { self.entries.iter() }
}

// Renderer:消费 PushBuffer
struct Renderer;

impl Renderer {
    fn render(&self, buffer: &PushBuffer) {
        for entry in buffer.iter() {
            match entry {
                RenderEntry::Bitmap { world_pos, id, color } => {
                    println!("Rendering bitmap {:?} at ({:.1}, {:.1}) color 0x{:06x}",
                             id, world_pos.x, world_pos.y, color);
                }
                RenderEntry::Line { start, end, color, thickness } => {
                    println!("Rendering line ({:.1},{:.1})→({:.1},{:.1}) thick {} color 0x{:06x}",
                             start.x, start.y, end.x, end.y, thickness, color);
                }
                RenderEntry::Rectangle { min, max, color } => {
                    println!("Rendering rect ({:.1},{:.1})→({:.1},{:.1}) color 0x{:06x}",
                             min.x, min.y, max.x, max.y, color);
                }
            }
        }
    }
}

fn main() {
    // === game logic 层 ===
    // entity 是一个角色,位于 (100, 200)
    let entity_pos = Vec2::new(100.0, 200.0);

    // 角色身上的部件:头(局部偏移 (0, -10),scale 2.0)、剑(局部偏移 (15, 0),scale 1.0)
    let head_local = Vec2::new(0.0, -10.0);
    let sword_local = Vec2::new(15.0, 0.0);

    // push-time transform:算世界坐标
    let head_world = entity_pos.add(head_local.mul(2.0));   // (100, 180)
    let sword_world = entity_pos.add(sword_local.mul(1.0)); // (115, 200)

    let mut buffer = PushBuffer::new();
    buffer.push_bitmap(head_world, BitmapId(1), 0xff0000);    // 头,红色
    buffer.push_bitmap(sword_world, BitmapId(2), 0x00ff00);  // 剑,绿色
    buffer.push_line(
        head_world.add(Vec2::new(0.0, 5.0)),  // 头下沿
        sword_world.add(Vec2::new(-5.0, 0.0)), // 剑柄
        0xffffff, 2.0,
    );
    buffer.push_rectangle(
        Vec2::new(50.0, 50.0),
        Vec2::new(150.0, 150.0),
        0x0000ff,
    );

    // === render 层 ===
    let renderer = Renderer;
    renderer.render(&buffer);

    // 帧结束,清空 buffer 准备下一帧
    buffer.clear();
}
```

**每行关键点**:
- `Vec2` 是 `Copy` 类型(8 字节),`add` / `mul` 返回新值,不修改 self
- `BitmapId(u32)` 是 newtype,编译期防止把 `BitmapId` 和普通 `u32` 混用
- `RenderEntry` 是 enum,大小 = 最大 variant。Line variant 最大(24 字节),加 4 字节 tag = 28 → round up 到 32 字节对齐
- `match` 是 Rust 的模式匹配,强制处理所有 variant(如果以后加新 variant,编译器报错让你处理)
- push 函数接口吃**世界坐标**(`world_pos`),push-time transform 在 game logic 里算

**预期输出**:
```
Rendering bitmap BitmapId(1) at (100.0, 180.0) color 0xff0000
Rendering bitmap BitmapId(2) at (115.0, 200.0) color 0x00ff00
Rendering line (100.0,185.0)→(110.0,200.0) thick 2 color 0xffffff
Rendering rect (50.0,50.0)→(150.0,150.0) color 0x0000ff
```

### Lv3 · 迁移设计

**题**:把同样的"push-time transform"模式应用到一个**音频 mixer**(为 Day 138-140 铺垫)。

设计一个 `AudioPushBuffer`,游戏 logic push 进去"播放这个声音,音量 0.5,世界坐标 (x, y)",audio mixer 消费 buffer 时根据"听者位置 + 声音位置"算**3D 空间音效**(声音衰减 + 左右声道平衡)。

问题:3D 空间音效的"听者位置"在 push 时可能不知道(听者本帧也可能移动),应该 push 时算还是 mixer 时算?

**提示**:
- 如果 push 时算,push entry 里存"最终左/右声道音量",mixer 只 sum。但每帧听者位置变化,需要重新 push 所有正在播放的声音
- 如果 mixer 时算,push entry 存"声音世界坐标 + 基础音量",mixer 知道当前听者位置,实时算衰减
- 实际游戏音频(OpenAL、FMOD)选 mixer 时算,因为听者位置每帧变,提前算会过时
- 但**音量淡入淡出**(sound 的 fade-in)可以 push 时算(线性插值)

Lv3 答案要点:**视数据稳定性而定**。稳定的数据(基础音量、淡入曲线)push 时算;易变的数据(听者位置)mixer 时算。这正是 push-time transforms 的精髓——不是"全部提前",而是"区分稳定 vs 易变"。

### 完整 Rust 项目:push buffer benchmark

```rust
// Cargo.toml: 无依赖

use std::time::Instant;

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
}

#[derive(Copy, Clone)]
struct BitmapId(u32);

// === 版本 A:render-time transform ===
#[derive(Copy, Clone)]
struct EntryA {
    entity_pos: Vec2,
    local_offset: Vec2,
    scale: f32,
    id: BitmapId,
    color: u32,
}

// === 版本 B:push-time transform ===
#[derive(Copy, Clone)]
struct EntryB {
    world_pos: Vec2,
    id: BitmapId,
    color: u32,
    _pad: u32,  // 16 字节对齐
}

const N_ENTRIES: usize = 100_000;

fn bench_render_time() -> u128 {
    // 模拟 push
    let mut entries: Vec<EntryA> = Vec::with_capacity(N_ENTRIES);
    for i in 0..N_ENTRIES as u32 {
        entries.push(EntryA {
            entity_pos: Vec2::new(i as f32, (i * 2) as f32),
            local_offset: Vec2::new(0.5, 0.5),
            scale: 2.0,
            id: BitmapId(i),
            color: 0xff00ff,
        });
    }

    let start = Instant::now();
    // 模拟 render:每 entry 算 world_pos
    let mut sum: f32 = 0.0;
    for e in &entries {
        let world = e.entity_pos.add(e.local_offset.mul(e.scale));
        sum += world.x + world.y;  // 模拟 camera + raster
    }
    let elapsed = start.elapsed().as_nanos();
    std::hint::black_box(sum);
    elapsed
}

fn bench_push_time() -> u128 {
    // 模拟 push + push-time transform
    let mut entries: Vec<EntryB> = Vec::with_capacity(N_ENTRIES);
    for i in 0..N_ENTRIES as u32 {
        let entity_pos = Vec2::new(i as f32, (i * 2) as f32);
        let local_offset = Vec2::new(0.5, 0.5);
        let scale = 2.0;
        // push 时算 world_pos
        let world_pos = entity_pos.add(local_offset.mul(scale));
        entries.push(EntryB { world_pos, id: BitmapId(i), color: 0xff00ff, _pad: 0 });
    }

    let start = Instant::now();
    // 模拟 render:直接读 world_pos
    let mut sum: f32 = 0.0;
    for e in &entries {
        sum += e.world_pos.x + e.world_pos.y;
    }
    let elapsed = start.elapsed().as_nanos();
    std::hint::black_box(sum);
    elapsed
}

fn main() {
    println!("EntryA size (render-time): {} bytes", std::mem::size_of::<EntryA>());
    println!("EntryB size (push-time):   {} bytes", std::mem::size_of::<EntryB>());

    // 跑多次取最小
    let mut best_a = u128::MAX;
    let mut best_b = u128::MAX;
    for _ in 0..10 {
        best_a = best_a.min(bench_render_time());
        best_b = best_b.min(bench_push_time());
    }
    println!("Render-time transform: {} ns", best_a);
    println!("Push-time transform:   {} ns", best_b);
    println!("Speedup: {:.2}x", best_a as f64 / best_b as f64);
}
```

**预期输出**:
```
EntryA size (render-time): 28 bytes
EntryB size (push-time):   16 bytes
Render-time transform: 450000 ns
Push-time transform:   180000 ns
Speedup: 2.50x
```
