# Day 164 · 用 Windows 字体处理资产

> Day 163 你用 stb_truetype 栅格化字体——能跑,但小字号 (12-16px) 看着糊,字符 "g" 的曲线断成像素感很重的锯齿。Casey 不满意,改用 **Win32 GDI** API:`GetGlyphOutline` 让操作系统帮你栅格化。Windows 的字体引擎做了 30 年优化,处理 hinting、ClearType、亚洲字体、变体字体的复杂度,stb_truetype 望尘莫及。今天我们站在 Linux 视角看等价物——**FreeType + HarfBuzz + FontConfig**,这套组合是 Linux 桌面的字体引擎,所有 GTK / Qt / Firefox / Chrome / LibreOffice 都用它。

## 0 · 为什么要有这一天

让我们严肃讨论一下:**为什么自解析字体(stb_truetype)不够,要请出系统字体引擎**?

你跟着 Handmade Hero 走到 Day 163。stb_truetype 是个单文件库,优点是"扔进项目就能用",缺点是它**只解析 TrueType/OpenType 文件格式**,不做"高质量栅格化"。具体说,stb_truetype 缺失以下工业级特性:

**第一,hinting(字形微调)**。TrueType 字体里有"hinting 程序"——字节码指令,告诉栅格化器"在小字号下应该把这一笔稍微往左挪半像素,避免消失"。这些指令是字体设计师手工调出来的(stb_truetype 是 Sean Barrett 单文件写的,没实现 TrueType 字节码解释器)。所以 stb 在 12-16px 下,字符 "g" 的曲线会"塌掉"——本来圆润的曲线在小字号变成几个离散像素。

Windows GDI、Linux FreeType 都实现了 TrueType 字节码解释器(叫 "truetype interpreter" 或 "TT interpreter")——它们能执行字体内置的 hinting 指令,栅格化质量高一个量级。

**第二,复杂脚本不支持**。stb_truetype 假设"字符 = glyph"一一对应。这对 ASCII 拉丁字符成立,但对**复杂脚本**(complex scripts)完全不成立:

- **阿拉伯文**:字符 "ه"(heh)在词首、词中、词尾、独立四种位置变形——同字符不同 glyph。stb 不知道这个,把所有位置的 "ه" 渲染成同一个形状。
- **印度文(Devanagari)**:字符序列 "क" + "ष" 应该**融合**成 "क्ष"——一个新 glyph。stb 看到两个字符就画两个 glyph,中间留空。
- **连字(ligature)**:拉丁字符也有 "fi" / "fl" 这种连字 glyph。stb 把它们画成两个独立字符,中间有缝。

复杂脚本需要 **shaping**——把 Unicode 字符序列通过 OpenType 表转换为 glyph 序列。工业级 shaping 引擎是 **HarfBuzz**(Linux)、**DirectWrite**(Windows)、**Core Text**(macOS)。

**第三,kerning(字间距)**。某些字符对("AV"、"To"、"Wa")需要特殊间距——它们的字形互相"嵌合",默认间距太宽。字体文件里有 "kerning table" 存这些对。stb_truetype 解析一部分 kerning,但有些字体的 OpenType 高级 kerning(GPOS 表)stb 不解析。

**第四,彩色彩表情(emoji)**。彩色 emoji 是 PNG/SVG 嵌入字体的(COLR/CPAL 或 SVG 表)。stb_truetype 完全不支持。系统字体引擎支持。

**第五,字体回退(fallback)**。你写代码用 "Arial",但用户 Linux 机器没装 Arial。stb_truetype 找不到文件直接报错。系统字体引擎自动 fallback——找最相似的字体(DejaVu Sans)替代,玩家体验一致。

所以当你的游戏要支持:
- 小字号 UI(< 16px)
- 非拉丁字符(中文 / 阿拉伯 / 印度文)
- 高质量渲染(精品游戏的字面)
- 跨平台一致(Windows GDI vs Linux FreeType)

**你必须用系统字体引擎**。stb_truetype 留给"够用就行"的场景(开发期 debug overlay、内置字体)。

Casey 的 Day 164 是从"够用"切换到"工业级"的拐点。今天我们站在 Linux 视角,**用 FreeType 替代 Win32 GDI**——架构完全对应。Linux 字体栈的完整图景:

```
应用层:    你的游戏 / Firefox / LibreOffice
              ↓
文本布局:   Pango(GTK)/ Qt text  ←→  HarfBuzz(shaping)
              ↓
栅格化:     FreeType ←→ FontConfig(字体查找)
              ↓
渲染:       Cairo / Skia / OpenGL / 你的 framebuffer
```

工业级 Linux 字体栈是 5 层。Casey 用 Win32 等价于 "栅格化" 一层(GDI `GetGlyphOutline`)。Linux 上对应 FreeType。

**学完今天,你应该能**:
- 解释为什么 stb_truetype 不够工业级
- 用 Rust + FreeType 栅格化 ASCII glyph(等价 Win32 GDI)
- 理解 hinting / shaping / kerning / fallback 各自解决什么问题
- 用 FontConfig 查找系统字体(用户没装 Arial 自动 fallback)
- 知道什么时候用纯 Rust 库(ab_glyph)什么时候用系统库(FreeType)

## 1 · Casey 今天做了什么

Casey 在 Win32 写了一段 GDI 调用,我把它逐行翻译——你会看到每个参数对应字体工程的哪个概念。

```c
// 1. 获取一个 DC(Device Context),Win32 绘图的入口
HDC dc = GetDC(NULL);  // NULL = 整个屏幕的 DC

// 2. 创建 logical font(逻辑字体描述)
HFONT font = CreateFontW(
    24,                  // nHeight: 字高 24 像素
    0,                   // nWidth: 0 = 由系统根据 aspect ratio 算
    0,                   // nEscapement: 文本基线角度(0 = 水平)
    0,                   // nOrientation: 字符角度(0 = 水平)
    FW_NORMAL,           // nWeight: 400 = normal(0-900,FW_BOLD=700)
    FALSE,               // bItalic: 不斜
    FALSE,               // bUnderline: 不下划线
    FALSE,               // bStrikeOut: 不删除线
    DEFAULT_CHARSET,     // charset: 默认(西欧 + 系统默认)
    OUT_TT_PRECIS,       // 输出精度: 优先 TrueType
    CLIP_DEFAULT_PRECIS, // 裁剪精度: 默认
    ANTIALIASED_QUALITY, // 质量: 抗锯齿(还有 CLEARTYPE_QUALITY / NONANTIALIASED_QUALITY)
    FF_DONTCARE,         // pitch family: 不指定(系统选)
    L"Arial"             // 字体名
);

// 3. 把 font 选进 DC,后续 GDI 调用用这个字体
SelectObject(dc, font);

// 4. 对每个字符,栅格化
for (char c = 32; c < 127; c++) {  // 32=' ' 到 126='~',ASCII 可打印字符
    // GLYPHMETRICS: 字形的几何信息(advance, bearing, 尺寸)
    GLYPHMETRICS metrics;
    
    // MAT2: 2x2 变换矩阵,用 fixed-point 表示
    // identity = {{0,1},{0,0},{0,0},{0,1}}
    // 因为 Win32 fixed-point 是 (frac, int) 对
    MAT2 mat = {{0, 1}, {0, 0}, {0, 0}, {0, 1}};
    
    // 第一次调用:传 0 size,问"我需要多大 buffer?"
    DWORD size_needed = GetGlyphOutlineW(
        dc,                    // 设备上下文
        c,                     // 字符(也可以是 glyph index)
        GGO_GRAY8_BITMAP,      // 格式:8-bit grayscale
        &metrics,              // 输出:metrics
        0,                     // buffer size: 0 = 查询
        NULL,                  // buffer: NULL = 查询
        &mat                   // 变换矩阵
    );
    
    // 分配 buffer
    BYTE* buf = malloc(size_needed);
    
    // 第二次调用:真正栅格化
    GetGlyphOutlineW(
        dc, c, GGO_GRAY8_BITMAP,
        &metrics, size_needed, buf, &mat
    );
    
    // buf 现在是 8-bit grayscale bitmap
    // 数值 0-64(不是 0-255!),GDI 用 6-bit 抗锯齿(64 级)
    // metrics.gmBlackBoxX / gmBlackBoxY: 实际像素尺寸
    // metrics.gmCellIncX: advance 宽度
}
```

**GDI 帮你做的事**(对应 stb_truetype 不做的事):
1. **hinting**:Windows TrueType 解释器执行字体内置 hinting 指令
2. **抗锯齿**:GGO_GRAY8 = 6-bit (64 级) grayscale 抗锯齿
3. **subpixel positioning**:glyph 在像素边界内亚像素对齐(更清晰)
4. **metrics 完整**:advance / bearing / kerning 全给

视频里 Casey 讨论 GDI 的格式选项:
- `GGO_GRAY8_BITMAP`:8-bit grayscale(64 级灰度,数值 0-64)。**Casey 的选择**,平衡质量 / 大小。
- `GGO_METRICS`:只拿 metrics,不栅格化。用于"先扫一遍算布局,再栅格化"。
- `GGO_GLYPH_BITMAP`:1-bit bitmap(monospace)。质量最差但最小。
- `GGO_NATIVE`:字体原始 outline(Bezier 曲线),让你自己栅格化。
- `GGO_BEZIER`:Bezier 曲线 + GDI 包装。

Casey 选 GGO_GRAY8——这是大多数 Windows 应用的选择(包括 Notepad、写字板)。

**Linux 等价**:Win32 GDI 的 `GetGlyphOutline` 等价于 Linux FreeType 的 `FT_Load_Glyph` + `FT_Render_Glyph`。FreeType 的格式选项:
- `FT_RENDER_MODE_NORMAL`:8-bit grayscale(256 级,比 GDI 的 64 级更精细)
- `FT_RENDER_MODE_MONO`:1-bit monochrome
- `FT_RENDER_MODE_LCD`:subpixel(ClearType),用 RGB 子像素
- `FT_RENDER_MODE_LIGHT`:轻量抗锯齿(更快但糊)

Casey 用 GGO_GRAY8 对应 FreeType 的 `FT_RENDER_MODE_NORMAL`。

## 2 · 心智模型

### 2.1 类比:打印店 vs 家用打印机

让我打个比方把"系统字体引擎 vs 自解析"钉在脑子里。

你要打印一份简历。两个选择:

**家用打印机**(等价 stb_truetype):自己买纸、自己装墨、自己排版、自己控制色彩。优点是"独立"——任何设备都能跑,不依赖外部。缺点是"质量参差"——你家里的色彩校准没做,墨水可能过期,纸可能皱,出来的简历颜色不准、字略偏。

**专业打印店**(等价 Windows GDI / Linux FreeType):交给专业设备和技师。他们有:
- **校准过的显示器和打印机**(等价 hinting 程序)
- **专业的纸张和墨水**(等价 subpixel rendering)
- **多年调优的工艺**(等价 OpenType 表支持)
- **知道哪个客户用哪种纸最好**(等价字体 fallback)

打印店出来的简历,字更清晰、颜色更准、纸更挺括。但你要按打印店的"规矩"提交文件(PDF 而不是 Word)——你不能完全控制每个细节。

字体引擎也是这样:
- stb_truetype = 家用打印机:简单、独立、跨平台一致,但质量参差
- FreeType = 打印店:专业、高质量,但要遵守它的 API、依赖系统库

工业级游戏用"打印店"路线。精品游戏(《对马岛之魂》《控制》)的字体看起来惊艳,是因为它们用了平台字体引擎(FreeType / DirectWrite / Core Text),配合字体设计师手工调过的 hinting。

### 2.2 第一性原理:字体从字符到屏幕的链路

让我把"字符 → 像素"的完整链路拆开,你会看到每一步都涉及一个专业领域。

**步骤 1:Unicode → glyph index**。

每个字符在 Unicode 里有个 code point(如 `U+0041` = 'A')。但字体文件不是按 Unicode 索引 glyph,而是按 **glyph index**(整数 0, 1, 2, ...)。Unicode 和 glyph index 的映射存在字体的 `cmap` 表里。

```rust
let glyph_index = face.get_char_index('A' as u64);
// 'A' 的 code point 0x41,字体 cmap 查到 glyph index 比如 36
```

这一步 stb_truetype 也做,但只支持简单的 cmap 格式(format 4)。系统引擎支持所有 cmap 格式(0, 1, 2, ..., 14)。

**步骤 2:shaping(可选,复杂脚本必需)**。

Unicode 字符序列 → glyph 序列。简单情况下"字符 = glyph",但复杂脚本:

```
阿拉伯 "خ" + "و" + "ش" + "ت" + "ن" → 5 个 glyph(各自变形)
印度文 "क" + "्" + "ष" → 1 个 glyph(融合)
英文 "f" + "i" → 1 个 glyph(连字)
```

shaping 引擎(HarfBuzz)查 OpenType 表(GSUB / GPOS),做这些变换。Casey 的 HH 只处理 ASCII,不需要 shaping。工业级游戏必须。

**步骤 3:outline(轮廓)**。

每个 glyph 的形状由 Bezier 曲线描述(TrueType 用 quadratic,OpenType CFF 用 cubic)。这是矢量数据——理论可以任意放大不失真。

```rust
face.load_glyph(glyph_index, LoadFlag::NO_BITMAP)?;
let outline = face.glyph().outline();  // Bezier 控制点
```

**步骤 4:hinting**。

outline 是"理想形状",直接栅格化会有锯齿。hinting 程序(字体里的字节码)调整 outline——把控制点对齐到像素网格、强制笔画宽度统一。

```rust
face.load_glyph(glyph_index, LoadFlag::RENDER)?;
// RENDER flag 触发 hinting + 栅格化
```

hinting 程序的执行:
- **stb_truetype**:不执行(忽略 hinting 指令),outline 直接栅格化
- **FreeType + autohinter**:FreeType 自己的轻量 hinting(跨字体通用)
- **FreeType + TT interpreter**:执行字体内置 TrueType 字节码(质量最高)
- **Win32 GDI**:同 FreeType + TT interpreter

**步骤 5:栅格化(rasterization)**。

outline(矢量)→ bitmap(像素)。把 Bezier 曲线"涂"到像素网格上,做抗锯齿。

```rust
let bitmap = face.glyph().bitmap();
let buf = bitmap.buffer();  // 8-bit grayscale,256 级
```

抗锯齿:每个像素的灰度 = 该像素被 outline 覆盖的面积比。0 = 全白,255 = 全黑,128 = 半覆盖。

**步骤 6:subpixel rendering(可选)**。

LCD 屏幕每个像素有 R/G/B 三个子像素。传统抗锯齿把像素当原子单位,subpixel 把像素拆成 3 个子像素,水平分辨率翻 3 倍。这就是 ClearType。

```
传统:   [■][■][▒][▒][░][░][ ][ ]
subpixel:[R][G][B][R][G][B]...
```

FreeType 支持(FT_RENDER_MODE_LCD),但要正确显示需要知道 LCD 子像素排列(RGB vs BGR、水平 vs 垂直)。

**步骤 7:metrics 提取**。

每个 glyph 有:
- **advance**:画完这个 glyph 后,光标前进多少
- **bearing_x/y**:glyph 左上角相对于光标的偏移
- **width/height**:glyph bitmap 的尺寸
- **kerning pairs**:某些字符对的特殊间距

```rust
let metrics = glyph.metrics();
let advance = metrics.horiAdvance as f32 / 64.0;  // 26.6 fixed-point
```

(metrics 用 26.6 fixed-point:整数部分 26 bit,小数部分 6 bit。除以 64 转浮点。)

这 7 步是工业级字体渲染的完整链路。stb_truetype 做 1, 3, 5, 7,但不做 2(shaping)、4(hinting)、6(subpixel)。系统字体引擎全做。

### 2.3 FreeType 在 Rust 里的核心 API

Rust 的 FreeType binding 是 `freetype-rs`(由 Servo 团队维护)。

```rust
// Cargo.toml: freetype = "0.7"
use freetype::{Library, Face, face::LoadFlag};

// 1. 创建 FreeType library(全局字体引擎状态)
let lib = Library::init()?;

// 2. 加载字体文件,得到 Face
let mut face: Face = lib.new_face("/usr/share/fonts/TTF/DejaVuSans.ttf", 0)?;
//                                                    文件路径             face index

// 3. 设置字号(像素)
face.set_pixel_sizes(0, 24)?;  // width=0 表示自动算,height=24

// 4. Unicode → glyph index
let glyph_index = face.get_char_index('A' as u64);

// 5. 加载并栅格化 glyph
face.load_glyph(glyph_index, LoadFlag::RENDER)?;
//                           ^^^^^^^^^^^^^^^^
//                           RENDER flag = hint + rasterize

// 6. 提取结果
let glyph = face.glyph();
let bitmap = glyph.bitmap();
let buffer = bitmap.buffer();  // 8-bit grayscale Vec<u8>
let width = bitmap.width();    // u32
let rows = bitmap.rows();      // u32

// 7. metrics(用于布局)
let metrics = glyph.metrics();
let advance_x = metrics.horiAdvance as f32 / 64.0;  // 26.6 fixed → f32
let bearing_x = metrics.horiBearingX as f32 / 64.0;
let bearing_y = metrics.horiBearingY as f32 / 64.0;
```

每行解释:
- `Library::init()`:创建 FreeType 库实例。一个程序通常只创建一个,全局共享。
- `lib.new_face(path, 0)`:加载字体文件,face index 0 是默认(TTC 文件可以有多 face,如 bold + regular 在一个文件)。
- `set_pixel_sizes(0, 24)`:24 像素字高,width=0 让 FreeType 根据 aspect ratio 自动算。
- `get_char_index`:Unicode → glyph index 查表。
- `load_glyph(idx, RENDER)`:加载并栅格化。`RENDER` flag 等价于"调用 hinting + 调用 rasterizer"。
- `glyph.bitmap()`:得到栅格化后的位图。
- `metrics.horiAdvance`:水平 advance,26.6 fixed-point(64 = 1.0)。

### 2.4 Hinting 质量对比

让我严肃对比不同引擎在小字号下的质量差异。字符 "g"(小写)在 12px 栅格化:

| 引擎 | hinting | 边缘平滑 | 字形清晰 |
|---|---|---|---|
| stb_truetype | 无 | 中(简单抗锯齿) | 差(曲线塌) |
| ab_glyph | 无 | 中 | 差 |
| FreeType + autohinter | 轻量 | 高 | 高 |
| FreeType + TT interp | 字体内置 | 极高 | 极高 |
| Win32 GDI | 字体内置 | 极高 | 极高 |

差异主要在 12-16px,这是 UI 字号最常用范围。在 32px 以上,所有引擎看起来差不多。

Arch Linux 上验证:

```bash
# 看 FreeType 是否启用了 TT interpreter
cat /etc/profile.d/freetype2.sh 2>/dev/null
# 输出包含:export FREETYPE_PROPERTIES="truetype:interpreter-version=40"
# 40 = TrueType VM version 40(默认,稳定)

# 切换 hinting 模式
export FREETYPE_PROPERTIES="truetype:interpreter-version=35"  # 旧版(更激进)
export FREETYPE_PROPERTIES="truetype:interpreter-version=40"  # 默认
unset FREETYPE_PROPERTIES  # 禁用 TT interp
```

不同版本对渲染质量有微妙影响,Arch Wiki "Font configuration" 页详细讨论。

### 2.5 FontConfig:字体查找与 fallback

Linux 用户可能没装你游戏期望的字体。FontConfig 解决:

```rust
use fontconfig::FontConfig;

let fc = FontConfig::new()?;
let font_path = fc.find("Arial", None);  // 返回最匹配的字体文件
// 用户没装 Arial,FontConfig 自动 fallback 到 DejaVu Sans / Liberation Sans
```

FontConfig 的查找逻辑:
1. 扫描 `/usr/share/fonts/`,建索引
2. 查询时,按 family / style / weight 匹配
3. 找不到精确匹配,用 fallback 规则(Liberation Sans 替代 Arial,Noto Sans CJK 替代亚洲字体)
4. 返回最匹配的文件路径

命令行工具:

```bash
fc-list                    # 列出所有已安装字体
fc-match Arial             # 查找"Arial"的最匹配
# 输出: Arial.ttf: "Arial" "Regular"
# 或:   LiberationSans-Regular.ttf: "Liberation Sans" "Regular"(fallback)

fc-match -v Arial          # 详细查询
# 输出包含 file, family, style, weight 等所有属性

fc-match ":lang=zh"        # 查找支持中文的字体
fc-match ":lang=zh family=Noto Sans CJK"  # 组合查询
```

Arch Linux 的字体索引在 `/var/cache/fontconfig/`,每次 pacman 安装新字体自动更新。

Windows 没有 fontconfig,用 GDI `EnumFontFamiliesEx`。macOS 用 Core Text 的 `CTFontDescriptorCreateWithNameAndOptions`。

### 2.6 Shaping:复杂脚本的关键

最后讲讲 shaping。简单 ASCII 不需要,但你的游戏要支持中文 / 阿拉伯 / 印度文就必须。

**HarfBuzz 用法**(Rust binding `harfbuzz_rs`):

```rust
use harfbuzz_rs::*;

let face = Face::from_file("/usr/share/fonts/noto/NotoSansArabic-Regular.ttf", 0)?;
let font = Font::new(face);

let text = "سلام";  // 阿拉伯 "hello"
let unicode_chars: Vec<u32> = text.chars().map(|c| c as u32).collect();

// Shaping: Unicode 字符 → glyph 序列
let output = shape(&font, &unicode_chars, &[]);

for item in output.glyph_infos() {
    println!("glyph id: {}", item.codepoint);  // codepoint 字段在这里是 glyph id
}
for item in output.glyph_positions() {
    println!("advance: ({}, {})", item.x_advance, item.y_advance);
}
```

shaping 算法查 OpenType 表:
- **GSUB**(glyph substitution):字符 → glyph 的变换(融合、变形、连字)
- **GPOS**(glyph positioning):glyph 的位置调整(kerning、标记定位)

工业级 shaping 是 HarfBuzz 团队多年研发成果,处理几十种语言,几百条 OpenType feature 标签(`liga`, `kern`, `calt`, `ccmp` 等)。自己写 shaping = 几年工作。直接用 HarfBuzz 是唯一理性选择。

### 3.1 · 🎮 游戏编程视角

游戏工业的字体方案分两派:**"够用"派**和**"工业级"派**。

**"够用"派**(独立游戏、Web 游戏):用纯 Rust 库 `ab_glyph` 或 `rusttype`。优点:跨平台一致(Windows / Mac / Linux / WebAssembly 渲染相同)、无 C 依赖、易打包。缺点:无 hinting、无 shaping。适合拉丁字符 UI。

代表游戏:Hollow Knight(早期)、Celeste、Stardew Valley 的 mod 工具链。

**"工业级"派**(3A 游戏、商业引擎):用平台原生字体引擎。每个平台写一份 binding。优点:质量最高、支持所有字符。缺点:平台分支多、C 依赖、易打包麻烦。

代表游戏:The Last of Us Part II(DirectWrite + 自定义 shaping)、Cyberpunk 2077(FreeType + HarfBuzz + 自定义布局)、原神(每个平台单独处理)。

**引擎方案对比**:

- **Unreal Engine**:用 FreeType + HarfBuzz(Slate UI 字体系统)。所有平台一致(UE 不用 DirectWrite / Core Text,统一 FreeType)。代价:macOS 用户觉得字"和原生应用略不同"(因为不用 Core Text)。
- **Unity**:用 Unity 自研 TextCore(2020+),基于 FreeType + HarfBuzz。老版本用其他方案。
- **Godot 4**:用 HarfBuzz + FreeType,通过 `TextServer` 接口抽象。每平台可选不同后端。
- **Bevy**:用 `ab_glyph`(简单)或 `cosmic-text`(完整,基于 swash + rustybuzz)。`cosmic-text` 是 Rust 全栈文本布局,目标是无 C 依赖的工业级方案。

**Casey 的选择**:HH 是教学项目,Day 164 切到 Win32 GDI 是为了演示"工业级字体引擎"的用法。Linux 移植对应 FreeType。如果你想真正跨平台一致,推荐用 `swash`(纯 Rust,基于 harfbuzz 算法重写,无 C 依赖)。

**迁移建议**:你写 Rust 游戏:
- 拉丁字符 UI:`ab_glyph`(零依赖,质量够)
- 多语言 UI:`cosmic-text` 或 `swash`(纯 Rust 工业级)
- 极致质量:每平台单独写(Win32 / Core Text / FreeType binding)

### 3.2 · 🎨 图形学视角

字体栅格化在图形学里是独立子领域,有完整的算法理论。让我讲几个核心概念。

**Bezier 曲线栅格化**。glyph 的 outline 由 Bezier 曲线(quadratic 或 cubic)描述。栅格化是把这些曲线转换成像素覆盖。

经典算法:
- **扫描线算法**(scanline fill):对每行像素,算曲线和该行的交点,在交点之间填色。O(n × m),n = outline 段数,m = 像素行数。
- **signed distance field**(SDF):预计算每个像素到 outline 的有符号距离,渲染时按距离阈值填色。Valve 2007 论文。优点:任意放大不失真。
- **GPU tessellation**:把曲线转成三角形,GPU 渲染。现代方法,快。

FreeType 用扫描线 + hinting,stb_truetype 用扫描线(无 hinting),Valve Source 引擎用 SDF,现代 Web 引擎(Skia、Direct2D)用 GPU tessellation。

**抗锯齿数学**。理想抗锯齿 = 像素覆盖率,数学上 = outline 内的面积 ÷ 像素面积。

精确计算需要数值积分(慢)。工业实现用近似:
- **超采样**:每像素采 N×N 子点,统计被覆盖的比例(N=4 是典型,16 个子点)
- **覆盖率查找表**:预计算常见形状(线段、Bezier)的覆盖率,运行时查表
- **analytical**(解析):对简单形状(直线)用数学公式直接算

FreeType 用超采样 + 查表混合,质量高。

**Hinting 的本质**。Hinting 程序的目的是"对齐到像素网格"。具体说:
- **stem darkening**:垂直笔画在小字号下会因为不在像素中心而"瘦"。hinting 程序把笔画宽度对齐到整数像素,并稍微加粗。
- **grid fitting**:glyph 的关键点对齐到整数像素,避免半像素抖动。
- **delta hinting**:字体设计师手工指定"这个 glyph 在 12px 下,把第 5 个控制点向上挪 0.3 像素"。

这些是字体设计师在字体里写的字节码,TrueType VM 执行。FreeType 实现了 TrueType VM,可以执行这些字节码。stb_truetype 没有。

**Subpixel rendering(ClearType)**。LCD 屏幕每像素有 RGB 子像素,水平排列。传统抗锯齿把像素当原子,subpixel 把像素拆 3 个,水平分辨率翻 3 倍。

代价:色彩失真(子像素边缘有彩色 fringe),需要知道子像素排列(RGB vs BGR)。在 OLED 屏幕子像素排列不规整(PenTile),ClearType 失效。

FreeType 支持 LCD rendering(`FT_RENDER_MODE_LCD`),Linux 桌面默认开启(在 `/etc/profile.d/freetype2.sh`)。

**SDF rendering**。现代游戏引擎的"小字号"用传统栅格化,"大字号"用 SDF。SDF 在 GPU 上用 shader 渲染,极快。Valve 的论文里 SDF 用 64x64 texture 存一个 glyph,所有字号共享,内存小。

```glsl
// SDF 渲染 fragment shader(简化)
float dist = texture(sdf_texture, uv).r;
float alpha = smoothstep(0.45, 0.55, dist);
frag_color = vec4(text_color, alpha);
```

`smoothstep` 的 0.45 / 0.55 是 SDF 阈值,控制字符边缘锐利度。

### 3.4 · 🦀 Rust 生态视角

Rust 字体 crate 分四层,各有定位:

**第 1 层:纯 Rust 解析 + 栅格化**。
- **`ab_glyph`**:stb_truetype 的 Rust 版,纯 Rust,无 C 依赖。质量中等(无 hinting)。
- **`rusttype`**:ab_glyph 前身,Deprecated,但仍能用。
- **`glyph_brush`**:基于 ab_glyph,专为游戏 UI 优化(批渲染)。

适合:简单 UI、WebAssembly、跨平台一致。

**第 2 层:Rust binding 到 C 字体库**。
- **`freetype-rs`**:FreeType Rust binding,Servo 团队维护。
- **`harfbuzz_rs`**:HarfBuzz Rust binding。
- **`servo-fontconfig`**:FontConfig Rust binding。

适合:Linux 工业级、需要最高质量。

**第 3 层:Rust shaping 实现**(纯 Rust 替代 HarfBuzz)。
- **`rustybuzz`**:HarfBuzz 算法的 Rust 重写,无 C 依赖。
- **`swash`**:完整的纯 Rust 字体栈(解析 + shaping + 栅格化)。

适合:Rust-only 项目、嵌入系统。

**第 4 层:完整文本布局**。
- **`cosmic-text`**:基于 swash + rustybuzz,完整文本布局(对齐、换行、阴影)。
- **`etagere`**:glyph atlas packing(把多个 glyph 打包到一张纹理)。

适合:Rust GUI 框架(Iced、egui 部分用)。

**真实代码示例**——用 swash 栅格化(纯 Rust 工业级):

```rust
// Cargo.toml: swash = "0.1"
use swash::scale::{Scale, Stretch, Weight};
use swash::scale::Source;
use swash::shape::Shaper;
use swash::text::Script;
use swash::FontRef;

fn main() {
    let font_data = std::fs::read("/usr/share/fonts/TTF/DejaVuSans.ttf").unwrap();
    let font = FontRef::from_index(&font_data, 0).unwrap();
    
    // Shaping(用 swash 内置 shaper)
    let shaper = Shaper::new(&font, Script::Latin);
    let mut glyph_ids = Vec::new();
    shaper.shape_with("Hello", &mut |cluster| {
        for g in cluster.glyphs {
            glyph_ids.push(g.id);
        }
    });
    
    // 栅格化每个 glyph
    let scaler = Scale::new(&font);
    for gid in &glyph_ids {
        let image = scaler.scale_glyph(*gid, 24.0, 24.0, Source::Outline);
        if let Some(img) = image {
            println!("glyph {}: {}x{}", gid, img.placement.width, img.placement.height);
        }
    }
}
```

swash 没有 C 依赖,纯 Rust,适合 Rust-only 项目。

**反模式**:不要这样写:
- ❌ 把整个字体文件加载到内存,自己解析 cmap 表——直接用 `freetype-rs` 或 `swash`
- ❌ 用 stb_truetype 然后抱怨"中文不显示"——stb 不支持 CJK 布局,换 swash
- ❌ 在 60 FPS 循环里栅格化 glyph——预栅格化 ASCII(128 个 glyph),缓存到 atlas
- ❌ 不用 FontConfig,硬编码字体路径——用户机器可能没那个字体,FontConfig fallback

## 8 · Rust / Arch 落地代码

```rust
// Cargo.toml: freetype = "0.7"

use freetype::{Library, Face, face::LoadFlag};

struct FontGlyph {
    char: char,
    width: u32,
    height: u32,
    advance: f32,
    bearing_x: i32,
    bearing_y: i32,
    pixels: Vec<u8>,
}

fn rasterize_ascii(path: &str, size: u32) -> Vec<FontGlyph> {
    let lib = Library::init().expect("freetype init");
    let mut face: Face = lib.new_face(path, 0).expect("load font");
    face.set_pixel_sizes(0, size).expect("set size");

    let mut glyphs = Vec::new();
    for c in 32u8..128u8 {
        face.load_char(c as usize, LoadFlag::RENDER).expect("load");
        let glyph = face.glyph();
        let bitmap = glyph.bitmap();
        let w = bitmap.width() as u32;
        let h = bitmap.rows() as u32;
        let buf = bitmap.buffer().to_vec();
        let metrics = glyph.metrics();
        glyphs.push(FontGlyph {
            char: c as char,
            width: w,
            height: h,
            advance: metrics.horiAdvance as f32 / 64.0,
            bearing_x: metrics.horiBearingX as i32,
            bearing_y: metrics.horiBearingY as i32,
            pixels: buf,
        });
    }
    glyphs
}

fn main() {
    let path = "/usr/share/fonts/TTF/DejaVuSans.ttf";
    let glyphs = rasterize_ascii(path, 24);
    println!("rasterized {} glyphs", glyphs.len());

    // 找 'A',打印尺寸
    if let Some(g) = glyphs.iter().find(|g| g.char == 'A') {
        println!("'A': {}x{}, advance {}",
            g.width, g.height, g.advance);

        // ASCII art
        let w = g.width as usize;
        let h = g.height as usize;
        for y in 0..h {
            let mut line = String::new();
            for x in 0..w {
                let v = g.pixels[y * w + x];
                let c = if v > 192 { '#' }
                    else if v > 128 { '*' }
                    else if v > 64 { '.' }
                    else { ' ' };
                line.push(c);
            }
            println!("{}", line);
        }
    }

    // advance 总和(模拟 "Hello")
    let text = "Hello";
    let total: f32 = text.chars()
        .filter_map(|c| glyphs.iter().find(|g| g.char == c))
        .map(|g| g.advance)
        .sum();
    println!("'{}' total advance: {:.1}", text, total);
}
```
