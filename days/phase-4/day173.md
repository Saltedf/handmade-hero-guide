
# Day 173 · 精确字体对齐

> 你在游戏主菜单画一行 "Press Start"。字小,12 像素。鼠标拖动窗口,字符位置在不同 cursor 下应该一致。但你看到的:字符宽度不一致——"Start" 的 "S" 和 "t" 之间隔 7 像素,"t" 和 "a" 之间隔 8 像素——视觉上"抖动"。放大单字符看:每个字符的边缘锯齿明显,小圆点变成阶梯。原因是文本渲染默认**截断到整数像素**:cursor 是浮点,但 blit 时 `cursor as i32` 丢掉小数部分。Day 168-172 都是这套"差不多对齐"。今天 Casey 改用**亚像素对齐**:保留 cursor 的小数部分,blit 时按覆盖率分配到相邻两个像素。结果:小字号文本立刻清晰 2-4 倍,字符间距均匀,视觉效果像从 1080p 升到 4K。

## 0 · 为什么要有这一天

让我们严肃讨论**为什么"截断到整数像素"对文本是灾难**,而其他场景(贴图 blit)却能接受。

文本渲染的特殊性在于**信息密度**。一个 12 像素字符的"骨架"只有 7-9 像素宽,每像素的灰度承载信息(字的形状)。如果你把 cursor 截断到整数,等于"丢掉 1 像素的精度"——对 100 像素的贴图无所谓(1% 误差),但对 7 像素的字符致命(14% 误差)。

具体场景重现:

```rust
// 你以为的文本渲染
fn draw_text(text: &str, x: f32, y: f32) {
    let mut cursor = x;
    for c in text.chars() {
        let glyph = get_glyph(c);
        let dst_x = cursor as i32;  // 截断,丢掉小数
        blit(glyph, dst_x, y as i32);
        cursor += glyph.advance;   // advance 是浮点(如 7.3)
    }
}
```

看起来没问题,直到你追踪 cursor 的演化:

```
字符 0: cursor = 0.0, blit at 0
字符 1: cursor = 0.0 + 7.3 = 7.3, blit at 7
字符 2: cursor = 7.3 + 7.3 = 14.6, blit at 14
字符 3: cursor = 14.6 + 7.3 = 21.9, blit at 21  ← 这里跳了 7
字符 4: cursor = 21.9 + 7.3 = 29.2, blit at 29
字符 5: cursor = 29.2 + 7.3 = 36.5, blit at 36  ← 跳 7
字符 6: cursor = 36.5 + 7.3 = 43.8, blit at 43
字符 7: cursor = 43.8 + 7.3 = 51.1, blit at 51  ← 跳 8
```

字符之间间距是 7, 7, 7, 7, 7, 8, ...——**不均匀**。视觉上"波浪起伏",字看起来像在呼吸。

更糟的是:**同一文本在不同起始 cursor 下渲染不同**。"Press Start" 从 cursor=0 和 cursor=0.5 开始,渲染出来的字间距不同(因为每次截断丢的小数部分不同)。这让动画(如打字机效果)看起来"抖"。

更更糟的是:**kerning(字间距)被破坏**。"AV" 这种 kerning pair 本来字符间距应该是 6.7(紧凑),你截断成 6 或 7——不是想要的紧凑,而是默认间距。视觉效果"AV" 不再嵌合,中间有缝。

解决方案有三种,各有 trade-off:

**方案 1:hinting(字体引擎量化)**。让字体栅格化时把 advance 强制对齐到整数像素。比如 advance 7.3 → 字体引擎算成 7 或 8。代价:字符宽度失真(本来 7.3 变成 7 或 8)。但**累积误差消失**——所有字符都整数像素位置。这是 Windows GDI + hinting 的传统方案。

**方案 2:subpixel positioning(亚像素定位)**。保留 advance 的浮点值,blit 时按覆盖率分配到相邻两像素。比如 cursor=7.3 时,7 像素得 70% 覆盖,8 像素得 30% 覆盖。这是 Casey 今天用的方案。

**方案 3:超采样 + downsample**。在 4x 分辨率栅格化文本,然后 downsample 到 1x。质量极高,但 16x 内存 + 16x 计算。用于专业排版(InDesign),游戏太贵。

Casey 选方案 2(亚像素),理由:
- 保留字体设计意图(advance 是浮点)
- 不需要字体引擎配合(任何 glyph 都能 subpixel blit)
- 性能可接受(blit 多 50-100% 计算,但文本不是 hot path)

**亚像素定位的核心思想**:

LCD 屏每个物理像素由 RGB 3 个子像素组成(水平排列)。传统渲染把"像素"当原子单位——一个像素要么全亮要么全暗。亚像素渲染把像素拆成 3 个独立单元,水平分辨率翻 3 倍。

但 Casey 今天做的是**更基础的亚像素定位**(不是 ClearType):用 grayscale 像素的"部分覆盖"模拟亚像素。具体说,cursor=7.3 时:
- 像素 7 得到 70% 强度的 glyph(模拟"70% 覆盖像素 7")
- 像素 8 得到 30% 强度的 glyph(模拟"30% 覆盖像素 8")

视觉效果:glyph 看起来"在像素 7.3 位置",虽然实际数据存在像素 7 和 8 里。这是 grayscale 亚像素,不需要利用 RGB stripe。

完整的 ClearType 进一步把 RGB stripe 也利用上——R 子像素、G 子像素、B 子像素独立 alpha,水平分辨率再翻 3 倍。但 ClearType 在 OLED 屏(PenTile 排列)失效,在 HiDPI 屏收益降低。今天 Casey 不做 ClearType,只做 grayscale 亚像素。

**学完今天,你应该能**:
- 解释为什么 cursor 截断对文本渲染致命
- 实现 grayscale subpixel blit(覆盖率分配)
- 区分 subpixel positioning 和 ClearType(利用 RGB stripe)
- 理解为什么 HiDPI 屏亚像素收益降低
- 在自己游戏里选择"是否做亚像素"(性能 vs 质量的权衡)

## 1 · Casey 今天做了什么

Casey 这一天的核心改动是 blit 函数。从"整数位置直接画"改成"亚像素位置按覆盖率分配"。

**改动前**:

```rust
fn draw_text(text: &str, x: f32, y: f32) {
    let mut cursor = x;
    for c in text.chars() {
        let glyph = get_glyph(c);
        let dst_x = cursor as i32;  // ← 关键 bug:截断
        blit_nearest(glyph, dst_x, y as i32);
        cursor += glyph.advance;
    }
}

fn blit_nearest(glyph: &Glyph, dst_x: i32, dst_y: i32) {
    for y in 0..glyph.height {
        for x in 0..glyph.width {
            let alpha = glyph.bitmap[y * glyph.width + x];
            if alpha == 0 { continue; }
            // 直接画到 (dst_x + x, dst_y + y)
            draw_pixel(dst_x + x, dst_y + y, alpha);
        }
    }
}
```

**改动后**:

```rust
fn draw_text(text: &str, x: f32, y: f32) {
    let mut cursor = x;
    for c in text.chars() {
        let glyph = get_glyph(c);
        // 保留 cursor 的整数 + 小数部分
        blit_subpixel_horizontal(glyph, cursor, y);
        cursor += glyph.advance;
    }
}

fn blit_subpixel_horizontal(glyph: &Glyph, dst_x_f: f32, dst_y: i32) {
    let dst_x = dst_x_f.floor() as i32;
    let frac = dst_x_f - dst_x_f.floor();  // 小数部分 0-1
    
    for y in 0..glyph.height {
        for x in 0..glyph.width {
            let alpha = glyph.bitmap[y * glyph.width + x];
            if alpha == 0 { continue; }
            
            // 关键改动:alpha 按覆盖率分配到相邻两像素
            let left_alpha = alpha as f32 * (1.0 - frac) / 255.0;
            let right_alpha = alpha as f32 * frac / 255.0;
            
            draw_pixel(dst_x + x, dst_y + y, left_alpha);
            draw_pixel(dst_x + x + 1, dst_y + y, right_alpha);
        }
    }
}
```

**改动量**:50 行代码,但视觉效果巨大。

视频里 Casey 强调的几个细节:

**1. 亚像素只对水平方向有用**。原因:LCD 的 RGB stripe 是水平排列,人眼对水平细节敏感度高于垂直。垂直亚像素没有 LCD 子像素支持,收益不明显。

**2. 垂直亚像素无明显改善**。理论上也能做(coverage 按 y 分配),但视觉收益低。工业实现通常跳过垂直亚像素。

**3. 代价**:blit 慢 2 倍。原来每像素 1 次 draw,现在每像素 2 次(left + right)。但对文本(每帧几百到几千字符),总开销几毫秒,可接受。

**4. frac 计算**:`frac = cursor - cursor.floor()`。Rust 的 `floor()` 返回不超过 x 的最大整数(浮点表示)。`frac` 是 0-1 之间的浮点。

Casey 在视频里展示了几个对比截图——12 像素文本在 subpixel 下明显比 nearest 清晰,字符间距均匀。

## 2 · 心智模型

### 2.1 类比:精密刻章

让我打个比方把"亚像素精度"钉在脑子里。

刻章师傅刻小字,有粗放和精密两种工法:

**粗放工法**:刀每切 1 毫米一刀,刀刃 1 毫米宽。刻出来的字,笔画的边缘是阶梯——本该是斜线,变成 90 度的台阶。小字看起来"糊",细节丢失。

**精密工法**:刀每切 0.25 毫米一刀,刀刃 0.25 毫米宽。同样大小的字,边缘平滑得多。原来 1 毫米的台阶,现在是 0.25 毫米的微台阶,4 倍精细度。

数字字体完全类似:
- **粗放(整数像素位置)**:glyph 边缘必须落在整数像素边界。1 像素的阶梯明显。
- **精密(亚像素位置)**:glyph 边缘可以"落在像素之间"。两个相邻像素分担边缘,视觉上"边缘连续"。

这个比方的核心洞察:**精度的提升是 step → continuous 的转变**。整数像素是 step function(突变),亚像素是 continuous function(渐变)。视觉系统对渐变更友好——它把"边缘"识别为连续边界,而不是阶梯。

### 2.2 第一性原理:为什么 coverage 加权有效

让我严肃推导"coverage 加权"为什么视觉上等于"亚像素精度"。这是图形学的核心数学。

设 glyph 的某个像素在理想坐标系下位置是 (x_ideal, y_ideal),其中 x_ideal 是浮点(如 7.3)。我们想把这个"理想像素"画到离散的屏幕像素网格上。

**朴素方案**(nearest neighbor):取 `floor(x_ideal) = 7`,把整像素画到 (7, y)。代价:丢失 0.3 像素的信息,glyph 边缘看起来"卡在像素 7"。

**Bilinear 方案**:把 ideal 像素按 coverage 分配到 floor 和 floor+1:
- 像素 7 得到 `1 - frac = 0.7` 的覆盖
- 像素 8 得到 `frac = 0.3` 的覆盖

视觉效果:两个像素的亮度按比例分配,加起来等于原 ideal 像素的亮度。从远处看,这个 ideal 像素看起来"在 7 和 8 之间"——因为亮度重心在 7.3 位置。

**数学证明**(信号处理视角):screen 函数 s(x) 是 glyph 函数 g(x) 与 dirac comb(像素采样函数)的卷积。Bilinear 等价于 g(x) 与 triangle function(双线性核)卷积——这是低通滤波,过滤掉高频 aliasing,保留低频信号。

**数学公式**:
```
s[i] = ∫ g(x) * h(i - x) dx
```
其中 h 是 reconstruction kernel(h = 1 - |x| for |x| < 1,否则 0,即 triangle)。i 是离散像素索引。

离散化:
```
s[i] = Σ_x g(x) * (1 - |i - x|)  for |i - x| < 1
```

当 g(x) 在像素 i 附近非零(理想像素 x = 7.3):
```
s[7] = g(7.3) * (1 - |7 - 7.3|) = g(7.3) * 0.7
s[8] = g(7.3) * (1 - |8 - 7.3|) = g(7.3) * 0.3
```

这就是 Casey 的 `left_alpha = alpha * (1 - frac)` 和 `right_alpha = alpha * frac`。

**结论**:coverage 加权是数学正确的低通滤波,消除 aliasing,保留视觉信息。这是所有抗锯齿算法的数学基础——MSAA、SSAA、FXAA 都是它的变体。

### 2.3 RGB stripe 和 ClearType

Casey 今天不做 ClearType,但讲清楚 ClearType 的原理能让你理解为什么"亚像素"在不同屏幕上效果不同。

LCD 物理结构:每物理像素由 R、G、B 三个子像素组成,水平排列。

```
物理像素 0:    [R][G][B]
物理像素 1:    [R][G][B]
物理像素 2:    [R][G][B]
...
```

传统渲染把物理像素当原子——R/G/B 一起调亮。ClearType 把子像素当独立单元:

```
传统(白色像素): RGB 全亮 = [255][255][255]
ClearType(亚像素边缘):
  - 边缘"偏左":R 亮,G/B 不亮 = [255][0][0] 看起来红,但搭配邻居 [0][255][255] 看起来是"左偏的白"
  - 边缘"偏中":R/G 亮,B 不亮 = [255][255][0] 黄,搭配 [0][0][255] 蓝 = 白
  - 边缘"偏右":RGB 都亮 = 白
```

ClearType 的核心洞察:虽然子像素单独看是彩色的,但人眼"模糊"了 RGB 子像素,把它们当成"一个亮度的位置"。所以你可以让"亮度"在子像素之间连续过渡,等效水平分辨率 3 倍。

代价:边缘有彩色 fringe(仔细看有红/蓝 fringe)。在普通观察距离看不到,放大镜看明显。

**ClearType 在不同屏幕的表现**:
- **标准 RGB stripe LCD**:效果最好
- **BGR stripe**:算法要镜像
- **PenTile OLED**(三星屏):子像素排列不规整,ClearType 失效
- **HiDPI(Retina)屏**:每物理像素更小,亚像素收益降低
- **垂直旋转屏**:stripe 变垂直,ClearType 算法要切换

Apple 在 Retina 屏默认关 ClearType,选 grayscale AA——因为 Retina 分辨率已够清晰,ClearType 的彩色 fringe 比收益更明显。Windows 在标准 LCD 默认开 ClearType。

Linux 上 FreeType 的 LCD rendering 等价 ClearType:

```bash
# 启用 LCD rendering
export FREETYPE_PROPERTIES="truetype:interpreter-version=40,cff:no-stem-darkening=1"

# fontconfig 配置
# /etc/fonts/local.conf:
# <match target="pattern">
#   <edit name="rgba"><const>rgb</const></edit>  <!-- 告诉 FreeType 是 RGB stripe -->
#   <edit name="lcdfilter"><const>lcddefault</const></edit>
# </match>
```

### 2.4 实现:grayscale subpixel blit

让我们逐行实现 grayscale subpixel blit。这是 Casey 的核心改动。

```rust
/// Blit glyph 到 framebuffer,使用水平亚像素 coverage。
///
/// # 参数
/// - `fb`:framebuffer(u32 per pixel,ARGB)
/// - `fb_w`:framebuffer 宽度
/// - `glyph`:要画的 glyph(grayscale alpha bitmap)
/// - `dst_x_f`:目标 x 位置(浮点,允许小数)
/// - `dst_y`:目标 y 位置(整数,不做垂直亚像素)
/// - `color`:文本颜色(RGB)
fn blit_subpixel_horizontal(
    fb: &mut [u32],
    fb_w: u32,
    glyph: &Glyph,
    dst_x_f: f32,
    dst_y: i32,
    color: [u8; 3],
) {
    // 拆 dst_x_f 为整数部分 + 小数部分
    let dst_x = dst_x_f.floor() as i32;       // 整数部分
    let frac = dst_x_f - dst_x_f.floor();      // 小数部分,0.0-1.0
    
    // 遍历 glyph 每个像素
    for y in 0..glyph.height {
        for x in 0..glyph.width {
            // glyph 在 的 alpha(0-255)
            let alpha = glyph.bitmap[(y * glyph.width + x) as usize];
            if alpha == 0 { continue; }  // 透明像素跳过
            
            // 这个 glyph 像素在屏幕上的"理想位置"是 dst_x + x + frac
            // 等价于"屏幕像素 dst_x + x 得到 (1-frac) 覆盖,
            //          屏幕像素 dst_x + x + 1 得到 frac 覆盖"
            
            let left_alpha = alpha as f32 * (1.0 - frac) / 255.0;
            let right_alpha = alpha as f32 * frac / 255.0;
            
            // 画 left
            blend_pixel(fb, fb_w,
                dst_x + x as i32,
                dst_y + y as i32,
                color, left_alpha);
            
            // 画 right(只在 frac > 0 时有意义)
            if frac > 0.0 {
                blend_pixel(fb, fb_w,
                    dst_x + x as i32 + 1,
                    dst_y + y as i32,
                    color, right_alpha);
            }
        }
    }
}

/// 把 color 以 alpha 混合到 framebuffer 的 像素
fn blend_pixel(
    fb: &mut [u32],
    fb_w: u32,
    x: i32, y: i32,
    color: [u8; 3],
    a: f32,
) {
    // 边界检查
    if x < 0 || y < 0 || x >= fb_w as i32 { return; }
    let y_u = y as u32;
    let idx = (y_u * fb_w + x as u32) as usize;
    if idx >= fb.len() { return; }
    
    // 读取当前像素
    let dst = fb[idx];
    let dst_r = ((dst >> 16) & 0xFF) as f32;
    let dst_g = ((dst >> 8) & 0xFF) as f32;
    let dst_b = (dst & 0xFF) as f32;
    
    // Alpha 混合:out = src * a + dst * (1 - a)
    let new_r = color[0] as f32 * a + dst_r * (1.0 - a);
    let new_g = color[1] as f32 * a + dst_g * (1.0 - a);
    let new_b = color[2] as f32 * a + dst_b * (1.0 - a);
    
    fb[idx] = (255 << 24)
            | ((new_r as u32) << 16)
            | ((new_g as u32) << 8)
            | (new_b as u32);
}
```

**关键行解释**:
- `dst_x_f.floor() as i32`:`floor` 返回不超过 x 的最大整数(浮点表示),`as i32` 转 i32。对正数等价于 `as i32`(截断),对负数 `-1.5 → -2`(向负无穷方向取整)。
- `frac = dst_x_f - dst_x_f.floor()`:0-1 之间的小数。
- `alpha as f32 * (1.0 - frac) / 255.0`:alpha 是 0-255 的 u8,转 f32 后乘 coverage,再除 255 归一化到 0-1。
- `if frac > 0.0`:frac=0 时 right_alpha=0,blend 是 no-op,跳过省时间。

**性能分析**:
- Nearest blit:每像素 1 次 blend,1 次读 + 1 次写
- Subpixel blit:每像素 2 次 blend,2 次读 + 2 次写
- 1000 字符 × 100 像素/字符 = 100K 像素
- Subpixel 多 ~100K op = ~0.5ms(2.5GHz CPU)

可接受。

### 2.5 何时该用 / 不该用亚像素

**该用**:
- 小字号(8-16px)UI 文字——肉眼可见的清晰度提升
- 静态文本(不动画的菜单文字)——稳定性
- 主菜单 / HUD 标题——视觉品质

**不该用**:
- 大字号(> 32px)——亚像素收益降低,nearest 够清晰
- HiDPI 屏——原生分辨率已高,亚像素不必要
- 动画文本(打字机效果)——亚像素让字符"渐变出现",看起来怪
- 性能 critical 路径(每帧 10000+ 字符的 MMO 名称)——subpixel 多 50% 开销

工业实现通常是**可选**——开发者按需启用。Unity 的 TextMeshPro 有 subpixel 选项,Unreal 的 Slate 也有。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业的文本渲染方案分两派,各有取舍。

**性能优先派**(大多数游戏):grayscale AA,不做 subpixel。理由:
- 文本不是 hot path,够清晰就行
- HiDPI 屏越来越普及,亚像素收益降低
- Subpixel 的彩色 fringe 在某些屏看起来怪
- 跨平台一致很重要(避免 Windows / Linux / Mac 渲染不同)

代表:Unity 默认 Text、Unreal Slate 默认、大部分独立游戏。

**质量优先派**(精品游戏):subpixel + 字体引擎精心调优。理由:
- 视觉品质是卖点(《对马岛之魂》《控制》《Hades》)
- 主菜单 / NPC 对白用 subpixel,大字号 UI 不需要
- 投入美术时间调字体大小 / hinting / subpixel 组合

代表:The Last of Us Part II 的 UI 文本、Hades 的对白文字、Cyberpunk 2077 的 codex 文本。

### 3.2 · 🎨 图形学视角

图形学对"采样"和"重建"有完整的理论。让我严肃讲讲 anti-aliasing 的数学。

**Aliasing(走样)的本质**。当你把连续信号(理想 glyph)采样到离散网格(像素),高频细节会"折叠"到低频,产生 moire pattern / 锯齿 / 闪烁。

数学上,采样是连续信号 g(x) 与 dirac comb Ш(x) 相乘:
```
sampled(x) = g(x) · Ш(x)
```
其中 Ш(x) = Σ δ(x - i),i 是整数。

频域上,采样是 g 的频谱与 Ш 的频谱(也是 Ш)卷积。如果 g 有高于 Nyquist 频率(0.5 / pixel)的成分,这些成分会"折叠"到低频——这是 aliasing。

**Anti-aliasing 的两条路**:
1. **Pre-filtering**(采样前滤波):先用低通滤波去掉 g 的高频成分,再采样。质量最好,但需要"知道 g 的连续形式"。Glyph 的 coverage 计算就是 pre-filtering。
2. **Post-filtering**(采样后滤波):先 nearest 采样,再用低通滤波。质量差(aliasing 已发生),但简单。MSAA、FXAA 是这类。

**Glyph 的 coverage 计算**是 pre-filtering。每个像素的 alpha 等于"该像素被 glyph outline 覆盖的面积比"。这要求 outline 是连续的(矢量),不是离散的。

```
像素 (i, j) 的 alpha = ∫∫_{pixel (i,j)} outline_coverage(x, y) dx dy
```

这是 FreeType、stb_truetype 在栅格化时算的。Casey 的 Day 173 假设 glyph 已经栅格化成 alpha bitmap,亚像素定位是另一回事——**位移动画时的 anti-aliasing**。

**位移动画的 anti-aliasing**。glyph bitmap 是"理想位置"的栅格化。当你想"把它画到 cursor=7.3 位置",这个位置不是它原始栅格化的位置。如果直接 nearest blit,等于"二次采样",引入 aliasing。

Casey 的 coverage 加权 = **再次 low-pass filter**——把 glyph bitmap 看作"信号",在水平方向重新采样(从 integer 到 7.3),用 bilinear 核滤波。这消除了二次 aliasing。

**理论极限**:
- 1× coverage(horizontal):消除水平 aliasing,垂直仍可能有
- 2× coverage(horizontal + vertical):消除两个方向
- RGB stripe(ClearType):水平分辨率 3 倍
- Super-sampled(SSAA 4×):全方向 4 倍精度,内存 4 倍

工业 GPU 渲染通常 MSAA 4×(几何 AA)+ grayscale AA(文本)+ FXAA/TAA(后处理 AA)。Casey 的 HH 是 CPU 渲染,Day 173 只做文本水平 AA。

use ab_glyph::{Font, FontRef, Glyph, PxScaleFont};

let font = FontRef::try_from_slice(font_data)?;

**Rust 实现 subpixel blit 的最佳实践**:

```rust
// 缓存:每 glyph + 每 subpixel offset(0/0.25/0.5/0.75)
// 缓存 4 个版本,避免每次 blit 算 coverage
struct GlyphCache {
    cache: HashMap<(char, u8), Arc<Glyph>>,  // (char, subpixel_quarter)
}

impl GlyphCache {
    fn get(&mut self, c: char, subpixel_quarter: u8) -> Arc<Glyph> {
        // subpixel_quarter: 0=0.0, 1=0.25, 2=0.5, 3=0.75
        // 预计算 4 个版本,避免实时算
        self.cache.entry((c, subpixel_quarter))
            .or_insert_with(|| pre_rasterize(c, subpixel_quarter))
            .clone()
    }
}
```

预栅格化 4 个 subpixel 版本,blit 时查表。这是工业文本渲染的标准优化——MacOS、Chrome、Firefox 都用。

**反模式**:
- ❌ 每帧重新栅格化每个 glyph——慢,预栅格化缓存
- ❌ 用 `f32::round()` 而不是 `f32::floor()`——round 在 .5 时向上,引入偏移
- ❌ 把 cursor 的 frac 丢掉——就回到了 nearest,失去 subpixel 优势

## 8 · Rust / Arch 落地代码

```rust
struct Glyph {
    bitmap: Vec<u8>,    // grayscale
    width: u32,
    height: u32,
    advance: f32,
}

impl Glyph {
    fn block(w: u32, h: u32) -> Self {
        let mut bitmap = vec![0u8; (w * h) as usize];
        for y in 0..h {
            for x in 0..w {
                let cx = w as f32 / 2.0;
                let cy = h as f32 / 2.0;
                let dx = x as f32 - cx;
                let dy = y as f32 - cy;
                let d = (dx * dx + dy * dy).sqrt();
                bitmap[(y * w + x) as usize] = if d < (w as f32 / 3.0) { 200 } else { 0 };
            }
        }
        Self { bitmap, width: w, height: h, advance: w as f32 + 1.0 }
    }
}

fn blend_pixel(fb: &mut [u32], fb_w: u32, x: i32, y: i32, color: [u8; 3], a: f32) {
    if x < 0 || y < 0 || x >= fb_w as i32 { return; }
    let idx = (y as u32 * fb_w + x as u32) as usize;
    if idx >= fb.len() { return; }
    let dst = fb[idx];
    let r = (color[0] as f32 * a + ((dst >> 16) & 0xFF) as f32 * (1.0 - a)) as u32;
    let g = (color[1] as f32 * a + ((dst >> 8) & 0xFF) as f32 * (1.0 - a)) as u32;
    let b = (color[2] as f32 * a + (dst & 0xFF) as f32 * (1.0 - a)) as u32;
    fb[idx] = (255 << 24) | (r << 16) | (g << 8) | b;
}

fn blit_nearest(fb: &mut [u32], fb_w: u32,
                g: &Glyph, dst_x: i32, dst_y: i32, color: [u8; 3]) {
    for y in 0..g.height {
        for x in 0..g.width {
            let alpha = g.bitmap[(y * g.width + x) as usize];
            if alpha == 0 { continue; }
            let px = dst_x + x as i32;
            let py = dst_y + y as i32;
            let a = alpha as f32 / 255.0;
            blend_pixel(fb, fb_w, px, py, color, a);
        }
    }
}

fn blit_subpixel_horizontal(fb: &mut [u32], fb_w: u32,
                            g: &Glyph, dst_x_f: f32, dst_y: i32, color: [u8; 3]) {
    let dst_x = dst_x_f.floor() as i32;
    let frac = dst_x_f - dst_x_f.floor();  // 0-1
    for y in 0..g.height {
        for x in 0..g.width {
            let alpha = g.bitmap[(y * g.width + x) as usize];
            if alpha == 0 { continue; }
            let left_alpha = alpha as f32 * (1.0 - frac) / 255.0;
            let right_alpha = alpha as f32 * frac / 255.0;
            blend_pixel(fb, fb_w, dst_x + x as i32, dst_y + y as i32, color, left_alpha);
            blend_pixel(fb, fb_w, dst_x + x as i32 + 1, dst_y + y as i32, color, right_alpha);
        }
    }
}

fn main() {
    let fb_w = 128u32;
    let fb_h = 32u32;
    let mut fb = vec![0xFF000000u32; (fb_w * fb_h) as usize];
    let glyph = Glyph::block(8, 10);
    let color = [255u8, 255, 255];

    // nearest 版本,cursor advance 7.3 → 取整
    let mut cursor = 5.0f32;
    for _ in 0..10 {
        blit_nearest(&mut fb, fb_w, &glyph, cursor as i32, 5, color);
        cursor += 7.3;
    }

    // subpixel 版本,保留 frac
    let mut cursor = 5.0f32;
    for _ in 0..10 {
        blit_subpixel_horizontal(&mut fb, fb_w, &glyph, cursor, 18, color);
        cursor += 7.3;
    }

    // 输出 PPM 看
    use std::io::Write;
    let mut f = std::fs::File::create("subpixel.ppm").unwrap();
    writeln!(f, "P3\n{} {}\n255", fb_w, fb_h).unwrap();
    for y in 0..fb_h {
        for x in 0..fb_w {
            let p = fb[(y * fb_w + x) as usize];
            write!(f, "{} {} {}  ", (p >> 16) & 0xFF, (p >> 8) & 0xFF, p & 0xFF).unwrap();
        }
        writeln!(f).unwrap();
    }
    println!("wrote subpixel.ppm");
    println!("nearest at y=5, subpixel at y=18");
}
```

**预期**:PPM 文件,两行圆点。Nearest 行可能错位累积,subpixel 行间距均匀。
