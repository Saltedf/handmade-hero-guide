# Day 146 · 累加 vs 显式计算

> 混音器把 100 个声音的输出加起来,每个声音的样本可能是 ±0.5。100 × 0.5 = 50,但 f32 的有效范围只是 ±1.0(超过就 clipping 失真)。**问题**:混音时累加 100 次,中间结果是 50,已经爆掉了,即使最后会乘以 0.01 把它压回去——**精度已经丢失了**。今天 Casey 讨论的是混音的**数值精度**和**计算顺序**——一个看似无聊但实际重要的工程题。

## 0 · 为什么要有这一天

让我先描述一个真实场景。你跟着 Handmade Hero 走到 Day 145。你的混音器实现"把所有声音加起来":

```rust
for voice in voices {
    for i in 0..N {
        dst[i] += voice.samples[i] * voice.volume;
    }
}
```

10 个声音同时播放时,dst[i] 累加 10 个 ~0.5 的值,中间值达到 ~5.0——**远超 f32 标准范围 ±1.0**。你把 dst 发给声卡,声卡硬件 clip 到 ±1.0,产生刺耳的方波失真。

你想:"那我最后除以 voice count,平均一下不就好了?"

```rust
for i in 0..N {
    dst[i] /= voices.len() as f32;  // 最后拉回 [-1, 1]
}
```

但听感不对——某些声音组合下仍然有可闻失真。你以为算法对了,但**精度没保住**。

**问题根源**:**f32 浮点的累加精度**。f32 的尾数 23 bit,数值 5.0 的最小可表示差(ULP)是 `2^-20 ≈ 9.5e-7`。累加 100 次 ±0.5,中间结果可能达到 50,ULP 是 `2^-16 ≈ 1.5e-5`——精度比 ±1 范围内低 64 倍。即使最后除以 100 拉回 ±1,**精度永远拿不回来**——被舍掉的位丢失了。

**今天的核心问题**:**数学等价 ≠ 数值等价**。两个表达式在数学上相同,在 f32 实现下结果可能不同。游戏音频工程师必须理解这点,否则会写出"看起来对但听起来有 bug"的混音器。

**学完今天,你应该能**:

- 解释 IEEE 754 binary32 的结构(sign / exponent / mantissa)
- 计算 f32 任意数值的 ULP(unit in the last place)
- 区分"数学等价"和"数值等价"——前者在精确数学下相同,后者在有限精度下相同
- 写出 Kahan summation 算法,理解它如何保留精度
- 选择合适的数值算法:直接 sum / 边加边 scale / Kahan / Pairwise
- 知道为什么 Rust 不开 `-ffast-math`(保证 IEEE 754 语义)
- 理解为什么混音器出口要加 soft clipper(tanh / cubic)做兜底
- 区分 hard clip 和 soft clip 的听感差异
- 在 GPU HDR 渲染、FIR 滤波器、物理积分等其他场景应用同样的精度思维

**今天的话题看似小众**(只有混音器相关),但**数值精度是工程师的通用素养**——任何用浮点计算的程序都可能遇到。游戏、机器学习、科学计算、金融——到处都有"f32 vs f64"和"累加顺序"的问题。

### 为什么数学等价但数值不等价

让我深度剖析。新人学数学,以为 `a + b + c = a + c + b`——交换律。**精确数学下成立**。但 **f32 不满足交换律**(也不满足结合律):

```rust
let a: f32 = 1.0;
let b: f32 = 1e8;
let c: f32 = -1e8;

println!("{}", (a + b) + c);  // 0.0 ← 错!
println!("{}", a + (b + c));  // 1.0 ← 对!
```

为什么?`(a + b)` 把 1.0 加到 1e8 上,1.0 远小于 1e8 的 ULP(`2^15 ≈ 32768`),1.0 被舍掉——结果就是 1e8。再加 -1e8 得 0。

`a + (b + c)`:b + c = 0(两个相反数),a + 0 = 1.0——保住。

**f32 加法不满足结合律**。所以**计算顺序影响结果精度**。这是数值分析的核心议题。

工业案例:

- **1991 年海湾战争 Patriot 导弹失误**:雷达系统累积时间用 f32,100 小时后累积误差 0.36 秒,导弹打偏,28 名美军死亡。
- **1996 年 Ariane 5 火箭爆炸**:64-bit 浮点转 16-bit 整数溢出,火箭自毁,5 亿美元损失。
- **Vanguard 基金 1994 年累计分红错算**:浮点精度问题,股东损失 200 万美元。

这些灾难都是"数学等价但数值不等价"的代价。**学会数值思维是严肃工程师的必备**。

## 1 · Casey 今天做了什么

Casey 在视频里讨论两件事:

**第一,混音器的 normalization**。他原本的混音器把所有声音累加到 dst,不做 normalization。结果 10 个声音同时播放时 dst 大幅超过 1.0,送到声卡后被 clip(饱和到 ±1.0),产生刺耳的失真。

**修复**:在累加前对每个声音的 volume 除以 sqrt(N)(或 N,看具体策略),保证 sum 永远在 ±1.0 内。Casey 选 `sqrt(N)` 而非 `N`——`sqrt(N)` 是**能量守恒**(energy-preserving)normalization,N 个相同音量的声音总能量等于一个声音的能量,听起来"满"但不爆音。`N` 是**平均** normalization,N 个相同声音听起来像一个,可能"太弱"。

**第二,精度 vs 速度的 trade-off**。Casey 展示两个版本的代码:

```rust
// A:边加边 scale
for v in voices {
    let scaled_vol = v.volume / N.sqrt();
    for i in 0..N {
        dst[i] += v.samples[i] * scaled_vol;
    }
}

// B:先累加后 scale
for v in voices {
    for i in 0..N {
        dst[i] += v.samples[i] * v.volume;
    }
}
for i in 0..N {
    dst[i] /= N.sqrt();
}
```

**结论**:对 f32 + 游戏音质要求,两者听不出差别(人耳对 -60 dB 以下的失真不敏感),但理论上"边加边 scale"更稳。

Casey 还提到一个**工程习惯**:**永远在 mixer 出口加一个 soft clipper**(soft saturation),即使 sum 没超 1.0 也加一层 `tanh(x)` 之类的平滑限幅。这是**兜底**(belt and suspenders),防止"奇怪的情况"产生爆音伤害耳朵/扬声器。

视频里 Casey 强调:"数值精度的代价是**永远在 think**——你不能假设浮点是精确的,每次写代码都要问'这里精度够不够'。这是工程思维的一部分,不是教科书能教的。"

## 2 · 心智模型

### 2.1 类比:称重

你想称 100 个石头的总重量,用电子秤。两种做法:

1. **A:一个一个加,每个加完除以 100**——你的秤永远显示 < 100 g
2. **B:全部累加完,最后除**——中间你的秤显示 5000 g

秤的精度有限(假设 ±1 g)。方式 A 中,5000 g 的累加会让早期加入的小石头的精度"被掩盖"——加第 1 个时 0.5 g 显示成 0.5 ± 1 g(可分辨),但加到第 100 个时,0.5 g 加到 4999.5 g 上,4999.5 和 5000 的差是 0.5,但 ULP 是 1,所以 0.5 完全丢失——加入前后读数都是 5000。

这就是 f32 的本质:**大数 + 小数,小数被吃掉**。**精度由当前数值的 ULP 决定**,数值越大,ULP 越大,精度越低。

### 2.2 严谨模型:IEEE 754 浮点

f32 的结构(IEEE 754 binary32):

```
sign(1) | exponent(8) | mantissa(23)
```

数值 = `(-1)^sign × 1.mantissa × 2^(exponent - 127)`。

**示例**:1.0 的二进制是 `0_01111111_00000000000000000000000`:

- sign = 0(正)
- exponent = 127(2^0 = 1)
- mantissa = 0(1.000... × 2^0 = 1.0)

尾数 23 bit,意思是 **相邻可表示值的差 = `2^(exp-23)`**。这个差叫 ULP(unit in the last place)。

| 数值 | ULP | 相对精度 |
|---|---|---|
| 1.0 | 2^-23 ≈ 1.2e-7 | 1.2e-7 |
| 100.0 | 2^-16 ≈ 1.5e-5 | 1.5e-7 |
| 10000.0 | 2^-9 ≈ 0.002 | 2e-7 |
| 1e10 | 1024 | 1e-7 |

**ULP 随数值指数增长**。所以两个数相加时,如果量级差距 > 2^23 ≈ 8M,小数完全丢失(加进去后被舍掉)。

**精度损失的量化**:累加 100 个 ±0.5 到 dst,dst 中间值 50,ULP = `2^-16 ≈ 1.5e-5`。每个新加的 0.5 sample 经过乘以 0.5(volume) 是 0.25,被舍入到 ±1.5e-5,精度损失约 0.006%。100 次累加的累积误差约 0.6%——在音频里这相当于 -44 dB 的失真,**人耳可闻**(人耳能分辨 -60 dB 的失真)。

### 2.3 加法精度分析:具体例子

考虑 `1.0 + 0.0000001`:

- 1.0 的 ULP = 1.19e-7
- 0.0000001 = 1e-7,小于 ULP
- 结果:舍入到 1.0(0.0000001 完全丢失)

**这就是"先累加再除"的精度损失来源**:dst 累加到 50 时,ULP = 3.8e-6,新加的 0.5 sample 经过乘以 0.5(假设 volume) 是 0.25,被舍入到 ±3.8e-6,精度损失约 0.0015%。

听起来小,但 100 次累加的累积误差可能听得到。

**反向例子**:`1e8 + 1.0`:

- 1e8 的 ULP = 8(因为 1e8 ≈ 2^26.6,ULP = 2^(26.6-23) = 2^3.6 ≈ 12.5)
- 1.0 远小于 ULP,完全丢失
- 结果:1e8(1.0 没加进去)

这个例子解释了为什么 Patriot 导弹的时间累积错——长时间累积后小增量丢失。

### 2.4 Kahan summation 算法

学术界有个 **Kahan summation algorithm** 解决累加精度问题:每次加法后,把丢失的精度存起来,下次加回去。复杂度 O(N) 但保持 O(1) 相对误差:

```rust
fn kahan_sum(values: &[f32]) -> f32 {
    let mut sum = 0.0f32;
    let mut c = 0.0f32;  // compensation
    for &v in values {
        let y = v - c;          // 减去上次丢失的
        let t = sum + y;        // 加到 sum
        c = (t - sum) - y;      // 计算这次丢失的低位
        sum = t;
    }
    sum
}
```

**核心思想**:`c = (t - sum) - y` 利用浮点的舍入——`(sum + y) - sum` 的结果不等于 `y`(因为舍入丢失低位),差值就是这次丢失的精度。下次加法把 `c` 减回去,补偿。

**精度**:Kahan sum 的相对误差是 O(1) ε(机器 epsilon),不管 N 多大。直接 sum 的相对误差是 O(N) ε。

游戏音频不会用 Kahan(太慢,4 倍操作)。Casey 的解法是 **重排顺序 + 边加边除**——精度够,速度快。

### 2.5 数值算法的选择

针对不同场景:

| 算法 | 速度 | 精度 | 何时用 |
|---|---|---|---|
| 直接 sum | 快 | 一般 | 数据少 (<100) |
| 边加边 scale(本日) | 快 | 好 | 游戏 ✅ |
| Kahan summation | 4x 慢 | 极好 | 金融 / 科学计算 |
| 排序后 sum(从小到大) | n log n | 好 | 静态分析 |
| Pairwise sum(分治) | log n 额外 | 好 | BLAS / 大数组 |
| Neumaier(sum 改进) | 4x 慢 | 极好 | 比 Kahan 更稳 |

游戏音频用"边加边 scale"足够,因为 voice 数 < 100,dst 永远在 ±1。

**工业实践**:

- **BLAS**(线性代数库)用 Pairwise sum,精度 + 速度兼顾
- **numpy** 默认用 Pairwise sum(从 1.17 起)
- **PyTorch** 默认 f32,可选 f16/bf16;bf16 是为深度学习设计的低精度格式

### 2.6 Soft clipping:兜底

即使 normalization 正确,**用户输入端可能让 sum 超过 1**——比如同时播放 100 个枪声。兜底是 **soft clipper**:

```
f(x) = x / (1 + |x|)         // 一个常用的 soft clip
```

或 `tanh(x)`,或 cubic:`x - x^3/3`(在 [-1, 1] 内接近线性,外面平滑饱和)。

软限幅不会"咔"地一下饱和(硬限幅的失真很刺耳),而是平滑地"挤"过去,听起来像模拟设备的饱和——温暖、自然。

**Hard clip vs Soft clip 听感**:

- **Hard clip**:信号超过 ±1.0 直接切平。方波失真,谐波丰富,刺耳。死亡金属音乐故意用这个效果。
- **Soft clip**:信号超过 ±1.0 平滑饱和。波峰被"圆化",谐波少,温暖。模拟磁带、电子管功放的自然效果。

游戏用 tanh——既有兜底,又保持音质。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏音频的数值精度问题主要集中在三个地方:

**混音累加**(本日):N 个声音加起来,中间值可能超 1.0。

**FIR 滤波器累加**:每个输出要算 N 个乘加,N 可能上千。如果 N=1024,累加值可能很大。重低音均衡器的 FIR 长度常见 4096 taps。

**FFT 累加**:类似,但 FFT 的动态范围更大(从 1e-3 到 1e6)。频域处理的精度问题比时域严重。

**工业做法**:

- **f32 + 适当 normalization**:99% 场景够
- **f64 累加,f32 输出**:把累加用 f64 做,最后转 f32。Casey 没用,但对滤波器值得。Wwise 音频中间件用这个策略。
- **Block floating point**(定点 DSP 风格):每个 block 共享 exponent,精度高、快、复杂。专业 DSP 芯片(TI C6000 系列)用。
- **FMA**(Fused Multiply-Add):`a * b + c` 一条指令,中间值用无限精度。x86 AVX2、ARM NEON 都支持。Rust `std::arch::x86_64::_mm256_fmadd_ps`。

### 3.2 · 🎨 图形学视角

图形学的精度问题更严重,因为动态范围更大:

**HDR 渲染**:光照值范围 0.001-1000(从昏暗角落到太阳直射)。f32 不够精度(0.001 加 1000,0.001 完全丢失),需要 RGB9_E5(共享 exponent)或 RGB16F。Casey 在 Day 235+ 切到 OpenGL 会遇到。

**Z-buffer 精度**:远近平面相差 10000 倍。f32 的 z 在远处精度不够——远处两个物体的 z 差小于 ULP,z-fighting(闪烁)。**反向 Z**(reverse-Z)技术:把 near/far 反过来,让远处精度更高。

**物理积分**:Verlet 物分的累积能量误差,长跑会"爆炸"——系统能量持续增加,模拟不稳定。**辛积分器**(symplectic integrator)解决这个问题,精度 + 能量守恒。

**GPU float 类型**:

- `lowp`(8-bit):颜色 + UV
- `mediump`(16-bit):normal + 中间值
- `highp`(32-bit):位置 + 矩阵
- WebGL/GLSL ES 默认 highp,但 mobile GPU 可能 fallback。

### 3.3 · 🦀 Rust 生态视角

Rust 的 f32 / f64 标准库提供:

- `f32::ulp(value)` —— Rust 1.73+ 稳定,返回 ULP 值
- `f32::clamp(x, min, max)` —— 限制范围(硬限幅)
- `f32::tanh()` —— 软限幅
- `f32::from_bits(u32)` —— 位级 reinterpret(调试用)

精度验证 crate:

- `approx` crate:`assert_relative_eq!(a, b, epsilon = 1e-6)` —— 浮点近似相等断言
- `proptest` + 浮点 oracle:属性测试
- `rug` / `ramp`:任意精度算术(bignum),作 ground truth

**Rust 浮点的特殊性**:

- **不重排浮点**:Rust 编译器**保证 IEEE 754 语义**,你的 `a + b + c` 不会变成 `a + c + b`。这意味着 Rust 浮点结果是确定的、可重现的。
- **不开 `-ffast-math`**:Rust 没有 fast-math 选项(社区讨论过,目前拒绝)。保证可重现性优先于性能。
- **SIMD**:Rust 用 `std::simd` 或 `std::arch::x86_64` 手动 SIMD,但同样保持 IEEE 754(除非显式用 fast-math intrinsic)。

### 3.4 · 🐧 Linux / 编译器视角

编译器对浮点的优化:

- `-ffast-math`(GCC/Clang)—— 允许重排浮点运算、假设无 NaN/Inf、用更快的近似指令。**改变结果**。Rust 默认不开。
- `-C unsafe-math-no-nan` —— Rust 等价 flag,假设没 NaN。
- `-fma` —— 启用 FMA 指令,提升精度(单指令完成 mul + add,中间值不丢精度)。
- 默认 Rust 编译器**保证 IEEE 754 语义**。

所以 Rust 的浮点结果是确定的、可重现的。代价是放弃了一些优化机会。游戏开发者有时用 `RUSTFLAGS="-C target-cpu=native"` 让编译器用更快的指令(AVX、FMA),但仍然保持 IEEE 754。

**Linux 工具链验证浮点行为**:

```bash
# 看 Rust 是否开了 fast-math
rustc -O --emit=llvm-ir /tmp/test.rs -o /tmp/test.ll
grep -i "fast" /tmp/test.ll  # 应该为空

# 看 objdump 是否用 FMA
objdump -d target/release/mygame | grep -i fma
# vfmaddXXXps 是 FMA 指令

# perf 看浮点指令
perf stat -e fpu_arith_instructions_star ./mygame
```

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **数值分析(numerical analysis)** —— 研究算法精度的整套数学
- **IEEE 754 浮点标准** —— f32 / f64 的位级规范
- **数值稳定性(numerical stability)** —— 算法在有限精度下的误差行为
- **浮点不满足结合律** —— 重要的数学事实,新人常忽略

### 4.2 同级(并行方案)

| 算法 | 公式 | 精度 | 速度 |
|---|---|---|---|
| 直接 sum | `acc + x` | 一般 | 快 |
| 边加边 scale | `acc + x/N` | 好(本日) | 快 |
| Kahan | 见 §2 | 极好 | 4x 慢 |
| Pairwise | 分治 | 好 | log n 额外 |
| Neumaier | 改进 Kahan | 极好 | 4x 慢 |
| f64 累加 f32 输出 | `acc_f64 += x; out = acc_f64 as f32` | 极好 | 2x 慢 |

### 4.3 下级(内部零件)

- **ULP** —— 最小可表示差
- **mantissa / exponent** —— f32 内部结构
- **rounding mode** —— 舍入方向(最近偶 / 向 0 / 向正负无穷)
- **saturation / clipping** —— 限幅
- **soft clipper** —— 平滑限幅(tanh / cubic)
- **FMA**(Fused Multiply-Add) —— 单指令 mul + add,精度保住

## 5 · 对照与变奏

### 5.1 不同语言的浮点

| 语言 | 默认浮点行为 |
|---|---|
| C/C++ | 可选 `-ffast-math`,默认严格 |
| Rust | 严格 IEEE 754(无 fast-math) |
| Python `float` | f64,严格 |
| JavaScript `Number` | f64,严格 |
| Java `float` / `double` | 严格 IEEE 754 |
| Go `float32` / `float64` | 严格 |
| GPU shader | 可选 relaxed / fast / precise |

Rust 在这里相对保守,保证可重现性。

### 5.2 定点 vs 浮点

专业音频有时用定点(Q15 / Q31):

- 16-bit fixed:动态范围 96 dB
- 24-bit fixed:144 dB
- f32 浮点:1528 dB(理论),实际 ~250 dB
- f64 浮点:超 1500 dB

定点的好处:**计算顺序不影响结果**(整数加法完全结合律)。坏处:动态范围小,要手动管 headroom。Casey 在 Day 138 的 WAV 解码用 16-bit 定点(sample),混音用 f32 浮点,这是行业标准。

### 5.3 Soft clipper 家族

```
hard clip:    x > 1 → 1   x < -1 → -1     // 失真刺耳
tanh:         tanh(x)                       // 经典,平滑
cubic:        3x - x^3 / 3                  // [-1.7, 1.7] 范围好
fold:         x > 1 → 2 - x                 // 波形折叠,金属感
inverse:      x / (1 + |x|)                 // 简单 soft,无穷渐近 1
```

游戏用 tanh 最常见。Day 140 Casey 已经加了类似逻辑。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:f32 的 `1.0 + 1e-9 == 1.0` 吗?为什么?如果是 f64 呢?

**参考解答**:

f32 下,1.0 的 ULP = 2^-23 ≈ 1.19e-7。1e-9 < ULP,加进去会被舍掉,所以 `1.0 + 1e-9 == 1.0` 为 **true**。

f64 下,1.0 的 ULP = 2^-52 ≈ 2.2e-16。1e-9 远大于 ULP,会被加进去,`1.0 + 1e-9 == 1.0` 为 **false**。

这是为什么 f64 比 f32 精度高 ~10^9 倍。**也是为什么科学计算用 f64**——精度要求高。

**延伸**:`1e8 + 1.0 == 1e8` 在 f32 下也是 true——1e8 的 ULP 是 ~12,1.0 被吃掉。Patriot 导弹 bug 就是这种类型。

### Lv2 · 动手实践

**题**:写一个 Rust 程序,生成 1000 个 f32 值,每个是 `0.001`。用三种方法求和:

1. 直接 sum(从前往后)
2. 边加边除以 N(每次 `acc += x / N`)
3. Kahan summation,然后除以 N

打印三种结果。验证它们是否相等(在 1e-6 精度内)。

**完整代码**:

```rust
fn kahan_sum(v: &[f32]) -> f32 {
    let mut s = 0.0f32;
    let mut c = 0.0f32;
    for &x in v {
        let y = x - c;
        let t = s + y;
        c = (t - s) - y;
        s = t;
    }
    s
}

fn main() {
    let v: Vec<f32> = vec![0.001; 1000];
    let n = v.len() as f32;

    // 1. 直接 sum
    let sum_direct: f32 = v.iter().sum();
    let avg_direct = sum_direct / n;

    // 2. 边加边 scale
    let mut acc = 0.0f32;
    for &x in &v { acc += x / n; }
    let avg_incremental = acc;

    // 3. Kahan + scale
    let sum_kahan = kahan_sum(&v);
    let avg_kahan = sum_kahan / n;

    println!("Method 1 - direct sum then divide:");
    println!("  result = {:.10}", avg_direct);
    println!("  diff from 0.001 = {:.2e}", (avg_direct - 0.001).abs());

    println!("\nMethod 2 - incremental scale:");
    println!("  result = {:.10}", avg_incremental);
    println!("  diff from 0.001 = {:.2e}", (avg_incremental - 0.001).abs());

    println!("\nMethod 3 - Kahan sum then divide:");
    println!("  result = {:.10}", avg_kahan);
    println!("  diff from 0.001 = {:.2e}", (avg_kahan - 0.001).abs());

    // 4. f64 ground truth
    let avg_f64: f64 = v.iter().map(|&x| x as f64).sum::<f64>() / n as f64;
    println!("\nGround truth (f64): {:.10}", avg_f64);
}
```

**预期**:

- direct: ~0.0010000002(误差 ~2e-9)
- incremental: ~0.001(误差 ~0)
- kahan: ~0.001(误差 ~0)
- f64: 0.001(完美)

### Lv3 · 迁移设计

**题**:把"边加边 scale"思路迁移到 **GPU 的 HDR 命色缓冲**。一个 HDR 帧的 RGB 值范围 0.001-1000,你要在 shader 里把多个光源累加。设计你的累加策略:中间值用什么格式?最后怎么 tone-map 回 LDR?

**提示**:

- f32 RGB 纹理(RGBA32F)中间值
- Kahan 在 GPU 上不实际,每个像素独立,且 SIMD
- Reinhard tone map:`x / (1 + x)` 把任意正数压到 [0, 1)
- ACES tone map:电影行业标准,色彩更"电影感"
- 光源累加前对每个光源的 intensity 做 exposure scale(`color * exposure / N`)

设计文档:

```glsl
// HDR accumulation
layout(location = 0) out vec4 frag_color;

void main() {
    vec3 hdr = vec3(0.0);

    // 边加边 scale:每个光源除以 N + 乘以 exposure
    for (int i = 0; i < NUM_LIGHTS; i++) {
        Light light = lights[i];
        vec3 contribution = compute_light_contribution(light);
        hdr += contribution * exposure / float(NUM_LIGHTS);
    }

    // Tone map (Reinhard 或 ACES)
    vec3 ldr = hdr / (hdr + vec3(1.0));  // Reinhard
    // vec3 ldr = ACESFilm(hdr);          // ACES

    // Gamma
    ldr = pow(ldr, vec3(1.0 / 2.2));

    frag_color = vec4(ldr, 1.0);
}
```

### 8.1 完整 demo

```rust
// src/main.rs
fn hard_clip(x: f32) -> f32 {
    x.max(-1.0).min(1.0)
}

fn soft_clip_tanh(x: f32) -> f32 {
    x.tanh()
}

fn soft_clip_cubic(x: f32) -> f32 {
    // 在 [-1.5, 1.5] 接近线性,外面平滑饱和
    if x.abs() < 1.5 {
        x - x * x * x / 3.0
    } else {
        x.signum() * 1.0
    }
}

/// 边加边 scale 的混音(energy-preserving)
fn mix_with_normalization(
    dst: &mut [f32],
    voices: &[(&[f32], f32)],  // (src, volume) pairs
) {
    let n = voices.len() as f32;
    let inv_sqrt_n = 1.0 / n.sqrt();   // sqrt normalization
    for (src, vol) in voices {
        let scaled_vol = vol * inv_sqrt_n;
        let n = dst.len().min(src.len());
        for i in 0..n {
            dst[i] += src[i] * scaled_vol;   // 边累加边 scale
        }
    }
    // 出口加 soft clip 兜底
    for x in dst.iter_mut() {
        *x = soft_clip_tanh(*x);
    }
}

/// 直接 sum(有 bug 版本,对比用)
fn mix_buggy(dst: &mut [f32], voices: &[(&[f32], f32)]) {
    for (src, vol) in voices {
        let n = dst.len().min(src.len());
        for i in 0..n {
            dst[i] += src[i] * vol;
        }
    }
    // 出口 hard clip(声卡硬件行为)
    for x in dst.iter_mut() {
        *x = hard_clip(*x);
    }
}

fn main() {
    // 模拟 10 个声音同时播放
    let src: Vec<f32> = (0..1000)
        .map(|i| (i as f32 * 0.01).sin() * 0.5)
        .collect();
    let voices: Vec<(&[f32], f32)> = (0..10)
        .map(|_| (src.as_slice(), 1.0))
        .collect();

    // 测试 buggy 版本
    let mut dst1 = vec![0.0f32; 1000];
    mix_buggy(&mut dst1, &voices);
    let max1 = dst1.iter().cloned().fold(0.0f32, |a, b| a.max(b.abs()));
    println!("Buggy mixer (direct sum + hard clip):");
    println!("  max abs = {:.3}", max1);

    // 测试正确版本
    let mut dst2 = vec![0.0f32; 1000];
    mix_with_normalization(&mut dst2, &voices);
    let max2 = dst2.iter().cloned().fold(0.0f32, |a, b| a.max(b.abs()));
    println!("\nCorrect mixer (sqrt normalization + soft clip):");
    println!("  max abs = {:.3}", max2);
}
```

### 8.4 Troubleshooting

**问题1**:`1.0 + 1e-9 == 1.0` 是 false。
原因:你的 Rust 编译时开了 fast-math(`-C unsafe-math`),编译器重排了运算。
解决:**不要在游戏开发里开 fast-math**。它改变结果,引入难调的 bug。

**问题2**:测试不通过(精度差太大)。
解决:f32 累加的精度问题。试试 f64 累加再转 f32:

```rust
let mut acc = 0.0f64;
for &x in &values { acc += x as f64; }
let result = acc as f32;
```

**问题3**:tanh 太慢。
解决:用 lookup table 或 polynomial 近似:

```rust
// Polynomial tanh 近似(精度 < 1%)
fn tanh_approx(x: f32) -> f32 {
    let x2 = x * x;
    x * (27.0 + x2) / (27.0 + 9.0 * x2)
}
```

**问题4**:Clippy 警告 `float_cmp`(`==` 比较 float)。
解决:这是正确的警告——浮点 `==` 几乎总是错。用 `approx::assert_relative_eq!` 替代。
