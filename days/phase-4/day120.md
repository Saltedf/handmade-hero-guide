# Day 120 · 用 IACA 测量端口占用

> 昨天你学会了用静态工具(MCA / IACA)看 port 占用。今天 Casey 实际把这套用到 Day 117 的 blend 代码上,找出"瓶颈在 port 5",然后优化。这是 Phase 4 性能优化的"完整一招":测量 → 分析 → 改进 → 重测。

## 0 · 为什么要有这一天

性能优化有个"7-3 规律":70% 的优化收益来自前 30% 的工作。但前提是"找对瓶颈"。如果你以为是 cache 实际是 port,你改了半天 cache 完全没用。

今天这一天的训练就是:**用工具找出真实瓶颈,然后针对它改进**。Casey 把 Day 117-118 的 blend 代码做了一遍完整流程:

1. 用 IACA / MCA 静态分析,找出 port 5 是瓶颈
2. 看哪些指令占 port 5:`pshufb`(用来 unpack 字节)用了 4 次,每次 1 周期 port 5,共 4 周期
3. 想办法减少 pshufb:用 `_mm_maddubs_epi16`(SSSE3,一条指令做 u8×i8 + horizontal add 成 u16)替代 unpack + mul 序列
4. 重测,验证 port 5 不再瓶颈,实测速度提升

这是性能工程师每天做的事。掌握这一招,你就能"独立优化任何一段 SIMD 代码"。

心理锚点:读完这一天,你能:

- 用 MCA 找到一段 SIMD 代码的 port 瓶颈
- 提出至少 2 个针对瓶颈的优化方案
- 验证优化真的消除了瓶颈

## 1 · Casey 今天做了什么

Casey 拿 Day 117 的 `blend4` 函数,跑 IACA,看到输出:

```
Resource pressure per iteration:
port 0:    ██░░░░░░░░  2
port 1:    █░░░░░░░░░  1
port 2:    █░░░░░░░░░  1(load)
port 3:    ░░░░░░░░░░  0
port 4:    ░░░░░░░░░░  0
port 5:    ████████████  4 ← 瓶颈
port 6:    ░░░░░░░░░░  0
port 7:    ░░░░░░░░░░  0
```

port 5 用了 4 次,4 条 `pshufb`。其他端口都闲。改进方向:**减少 pshufb**。

Casey 用 `_mm_maddubs_epi16`(SSSE3):

- 一条指令把 `u8x16 × i8x16` 各 lane 相乘,然后水平加相邻两个成 `i16x8`
- 这条指令在 port 0 或 port 5(throughput 1),比 unpack + mul 序列少 2 条

他改写后:

```
port 0:    ████░░░░░░  3
port 5:    ██░░░░░░░░  2(原来 4,现在 2)
```

总周期从 12 降到 8。实测从 25ns 降到 17ns,加速 40%。

## 2 · 心智模型

### 2.1 类比:厨房瓶颈工位

回到 Day 112 的厨房类比。如果"切菜工位"只有 1 个厨师,但他要切 4 道菜,其他工位闲着等他——他就是瓶颈。

解药:

- **方案 A**:让其他厨师也帮着切(把 `pshufb` 改成其他指令)
- **方案 B**:减少切菜量(算法层面减少 unpack 次数)
- **方案 C**:加 1 个切菜工位(换 CPU——但你说不算)

Casey 用方案 A:用 `_mm_maddubs_epi16` 这条"复合指令",一条指令做多个事(切菜 + 调味),减少 port 5 占用。

### 2.2 SIMD 端口资源:Skylake 视图

Intel Skylake(2015+,大多数现代 x86_64)的端口:

| Port | 干什么 |
|---|---|
| Port 0 | ALU、FPU(mul、FMA)、整数除法、SSE/AVX 整数 |
| Port 1 | ALU、FPU(add、FMA) |
| Port 2 | Load(读内存) |
| Port 3 | Load(读内存) |
| Port 4 | Store(写内存) |
| Port 5 | ALU、shuffle、pack/unpack、broadcast |
| Port 6 | ALU、branch |
| Port 7 | Store address |

`pshufb`(packed shuffle byte)只能走 port 5(单一端口)。一条 `pshufb` 1 周期,4 条 = 4 周期,且不能并行。这是 blend4 的瓶颈。

### 2.3 复合指令:用一条指令做多个事

`_mm_maddubs_epi16(a, b)`:把 `a` 的 u8 和 `b` 的 i8 相乘,然后水平加相邻两个:

```
a = [a0 a1 a2 a3 ... a15]   (u8x16)
b = [b0 b1 b2 b3 ... b15]   (i8x16)
res = [(a0*b0 + a1*b1) | (a2*b2 + a3*b3) | ...]  (i16x8)
```

这条指令一次做 16 次乘法 + 8 次加法,占 port 0 或 port 5(throughput 0.5,比 pshufb 快)。

#### 应用到 blend

像素 SIMD 的常见模式:`unpack u8 → u16 → 算 → pack u16 → u8`。`maddubs` 可以替代一部分 unpack + mul 序列。

### 2.4 优化迭代:测量 → 改进 → 再测

性能优化的循环:

1. 测基线(用 Day 113 计数器或 criterion)
2. 静态分析(MCA / IACA)找瓶颈
3. 提出至少 2 个方案(避免"锤子综合症")
4. 实施最佳方案
5. 测新性能
6. 对比基线
7. 如果有改进,commit;否则回滚
8. 看新瓶颈(可能有下一个 port 受限)

Casey 在 HH 反复用这个循环。每次迭代 0.5-2 小时,持续若干天。

### 2.5 SIMD 优化的常见瓶颈

| 瓶颈 | 表现 | 解药 |
|---|---|---|
| Port 5 堵 | 大量 pshufb / pack / unpack | 用 maddubs / 复合指令 |
| Port 0/1 堵 | 大量 mul / FMA | 用 FMA 替代 mul + add |
| Load 堵(port 2/3) | 大量 load | 改数据布局(SoA、preload) |
| Store 堵(port 4/7) | 大量 store | 减少 store,合并写 |
| Latency 受限 | 依赖链长 | 多累加器打破链 |

### 2.6 不要过早优化

警告:优化前先问自己"这段代码真的是瓶颈吗?"用 Day 113 的 frame profiler 看,如果整个游戏只有 2% 的时间花在这段代码上,即使你优化 10 倍,游戏总速度也只快 1.8%。

**热 1% 代码,优化 10 倍 → 总快 9%**。这是 Amdahl 定律。

```rust
// 假设整个 frame 16ms
// blend 函数占 0.32ms(2%)
// 优化到 0.032ms(10x)
// 新 frame 总耗时 = 16 - 0.32 + 0.032 = 15.712ms
// 提速 (16 - 15.712) / 16 = 1.8%
```

所以 Casey 在 Phase 4 后期优化的是**帧时间最大的几个函数**(blend、draw_tile、draw_bitmap),不是冷代码。

## 5 · 对照与变奏

### 不同 CPU 的优化策略不同

`pshufb` 在 Skylake 占 port 5(瓶颈),但在 Zen 3 占 port 0/1/2/3(不瓶颈)。所以"在 Skylake 上的优化"在 Zen 3 可能反而变慢。

工业代码会针对每个 CPU 写不同版本,运行时检测选最优:

```rust
if is_x86_feature_detected!("avx2") {
    if cpu_is_intel() { intel_blend_avx2() }
    else { amd_blend_avx2() }
} else if is_x86_feature_detected!("sse4.1") {
    sse41_blend()
} else {
    scalar_blend()
}
```

glam 内部就是这么做的。

## 8 · Rust / Arch 落地代码

### 完整的 MCA 工作流

```bash
# 1. 编译,看汇编
RUSTFLAGS="-C target-cpu=native -C opt-level=3" cargo rustc --release -- --emit asm

# 2. 提取函数汇编
ASM=$(find target/release/deps -name "*.s" | head -1)
awk '/_blend4_sse:/,/^$/' $ASM > /tmp/blend4.s

# 3. MCA 分析
llvm-mca -mcpu=native -iterations=100 /tmp/blend4.s | tee /tmp/mca_before.txt

# 4. 优化代码(改 Rust 源)

# 5. 重新编译分析
cargo rustc --release -- --emit asm
awk '/_blend4_sse:/,/^$/' $ASM > /tmp/blend4_after.s
llvm-mca -mcpu=native -iterations=100 /tmp/blend4_after.s | tee /tmp/mca_after.txt

# 6. 对比 before / after
diff /tmp/mca_before.txt /tmp/mca_after.txt

# 7. perf stat 动态验证
sudo perf stat -e cycles,uops_executed.port_5,uops_executed.port_0 \
  ./target/release/my_app_before
sudo perf stat -e cycles,uops_executed.port_5,uops_executed.port_0 \
  ./target/release/my_app_after
```

### 用 Rust 内部 bench 验证

```rust
// benches/blend.rs
use criterion::*;
use my_crate::*;

fn bench(c: &mut Criterion) {
    let mut group = c.benchmark_group("blend");
    group.bench_function("before", |b| {
        b.iter(|| black_box(blend_before(black_box(&src), black_box(&mut dst))))
    });
    group.bench_function("after", |b| {
        b.iter(|| black_box(blend_after(black_box(&src), black_box(&mut dst))))
    });
    group.finish();
}
```

`cargo bench` 后 criterion 自动告诉你"after 比 before 快 X%"。

## 10 · 深度推导:从"IACA 报告"到"真改进"

昨天你学了三层测量框架。今天把框架套到真实代码上。Casey 拿 day117 的 blend 函数开刀,演示**从诊断到改进到验证**的完整闭环。这一节会把这个闭环走通——你看完应该能对任何 SIMD 函数做这种分析。

### 10.1 起点:Day 117 blend 的汇编

先把 day117 的 blend_4_masked 编译成汇编,看 IACA / llvm-mca 的输入。

```bash
# 在 phase-4 项目的 release build 下
RUSTFLAGS="-C target-cpu=native" cargo rustc --release -- --emit asm

# 找到 blend 函数的汇编段
grep -A 50 'blend_4_masked:' target/release/deps/handmade_hero-*.s | head -60
```

输出大概长这样(简化版):

```asm
blend_4_masked:
    movdqu    xmm0, [rdi]            ; load src_v
    movdqu    xmm1, [rsi]            ; load dst_v
    pshufb    xmm2, xmm0, xmm3       ; broadcast alpha
    pcmpeqb   xmm4, xmm2, xmm_zero   ; alpha == 0 mask
    pcmpeqb   xmm5, xmm2, xmm_ff     ; alpha == 255 mask
    punpcklbw xmm6, xmm0, xmm_zero   ; src unpack lo
    punpcklbw xmm7, xmm1, xmm_zero   ; dst unpack lo
    pmullw    xmm8, xmm6, xmm_a      ; src * alpha
    pmullw    xmm9, xmm7, xmm_inv    ; dst * inv_alpha
    paddw     xmm10, xmm8, xmm9      ; sum
    psrlw     xmm10, xmm10, 8        ; >> 8
    packuswb  xmm10, xmm10           ; pack back
    pblendvb  xmm1, xmm10, xmm_blend_mask  ; apply blend
    pblendvb  xmm1, xmm0, xmm5       ; apply full mask
    pblendvb  xmm1, xmm1_orig, xmm4  ; apply zero mask
    movdqu    [rsi], xmm1            ; store
    ret
```

把这段汇编喂给 llvm-mca。

### 10.2 llvm-mca 输出解读

```bash
llvm-mca -mcpu=skylake -iterations=1000 blend.s
```

输出关键部分:

```
Iterations:        1000
Instructions:      18000
Total Cycles:      16000
Total uOps:        19000
Dispatch Width:    6
uOps Per Cycle:    1.19
IPC:               1.13
Block RThroughput: 16.0 cycles per iteration

Resource pressure per iteration:
[0]   [1]   [2]   [3]   [4]   [5]   [6]   [7]
1.00  1.50  1.50  1.50  1.00  6.50  0.50  1.00

Critical path: 12 cycles
```

**逐项解读**:

- **Block RThroughput: 16.0**:这是 llvm-mca 估的"完成一个 iteration 需要的最少 cycle"。你跑 1000 次是 16000 cycle。
- **IPC: 1.13**:每 cycle 1.13 条指令退休。Skylake 上限是 6,所以 1.13 表示**严重不饱和**。
- **Port pressure**:port 5 占 6.5(超过上限 6.0 说明真的卡住)。其它 port 都很闲(0/1 = 1.0-1.5,2/3 = 1.5 load 端口)。

**诊断**:**Port 5 bottleneck**。你的 blend 函数 16 cycle 里 port 5 占了 6.5,说明"shuffle / blend / compare"指令堆在一起。port 0/1/2/3 都大量空闲——CPU 算力被浪费了。

### 10.3 找出"罪魁祸首"指令

llvm-mca 还有 instruction info 模式:

```bash
llvm-mca -mcpu=skylake -iterations=1 -instruction-info blend.s | head -30
```

输出每条指令的详细:

```
[1] pshufb   Latency=1, Uops=1, Ports=[5]
[2] pcmpeqb  Latency=1, Uops=1, Ports=[5]
[3] pmullw   Latency=5, Uops=1, Ports=[0]
[4] pblendvb Latency=2, Uops=2, Ports=[0,5]   ← port 5 + port 0
```

**关键观察**:3 条 pblendvb 各自要 port 5(共 3 cycle)。1 条 pshufb 占 port 5。2 条 pcmpeqb 占 port 5。**Port 5 总占用 = 6 cycle**,正好对应 IACA 报告的 6.5。

### 10.4 优化思路:把 port 5 的活移走

策略:用**等效但端口不同**的指令替代。

**优化 1**:把 `pblendvb` 换成 `pand` + `pandn` + `por`。

```asm
; 原:pblendvb dst, src, mask
; 新:
pand     tmp1, src, mask       ; tmp1 = src & mask  → port 0/1
pandn    tmp2, mask, dst       ; tmp2 = dst & ~mask → port 0/1
por      dst, tmp1, tmp2       ; dst = tmp1 | tmp2  → port 0/1
```

3 条算术指令,但都在 port 0/1(不抢 port 5)。**总 latency 仍是 3 cycle**(链式),但**不卡 port 5**。

**优化 2**:把 `pcmpeqb` 提前/合并。两条 cmp 共享 alpha——能不能合并?不行,因为比较的常数不同(0 vs 255)。但可以**重新组织 mask 计算**:

```asm
; 原:cmp alphas,0 → mask_zero; cmp alphas,255 → mask_full
; 新:把 alphas 减 1,cmp eq 254 → 中间 alpha 的 mask
psubb alpha_m1, alphas, 1
pcmpeqb mask_mid, alpha_m1, 254   ; 一条 cmp 替代两条
```

这是"算术变换减少指令"。Casey 在视频里展示过类似的"通过代数化简减指令数"。

**优化 3**:`pshufb` 用 lookup table 形式做"广播"——但 pshufb 本身就只在 port 5。无法替换。只能"减少 pshufb 数量"。比如把 alpha 提取放在循环外,如果 alpha 在所有像素上一致(同 sprite 同 row),只算一次。

### 10.5 优化后重测

应用上面 3 个优化后,重新跑 llvm-mca:

```
Resource pressure per iteration (after opt):
[0]   [1]   [2]   [3]   [4]   [5]   [6]   [7]
3.50  3.50  1.50  1.50  1.00  2.50  0.50  1.00

Block RThroughput: 10.0 cycles per iteration
```

Port 5 从 6.5 降到 2.5,Port 0/1 升到 3.5。**RThroughput 从 16 降到 10,即 37% 提升**。这就是 day120 的核心收益。

### 10.6 验证:理论 vs 实测

理论提升 37%,实测呢?

```bash
# 用 day119 的 hyperfine
hyperfine -w 3 -r 10 \
  "./target/release/bench_blend_old" \
  "./target/release/bench_blend_new"
```

如果理论 37% 实测 30%,匹配——优化成功。

如果理论 37% 实测 5%,差异大,说明静态分析漏了什么——通常是 cache 或 branch miss。这时候回到 day119 的 perf stat,看事件分布。

### 10.7 工业级的反复优化

Casey 在 day120 不会"一次优化到位"。工业 SIMD 优化是**多轮迭代**:

1. **Round 1**:IACA 找到 port 5 bottleneck,应用优化 1(blendv → and/or)。提升 30%。
2. **Round 2**:重新 IACA,发现 port 0 bottleneck(因为 and/or 都跑到 port 0 了)。再优化,分散指令。
3. **Round 3**:发现 cache miss 是新瓶颈。改数据布局(把 alpha 单独存一个 stream,不要和颜色交织)。
4. **Round 4**:重新 IACA,发现 dependency chain 是新瓶颈。展开循环让 ILP 跨 iteration。
5. **Round 5**:重新 IACA,发现基本平衡了,差不多到理论极限。

**每一轮 5-15% 提升是常态**。SIMD 优化是"挤牙膏",不是"一刀切"。

## 11 · 一个完整可跑的优化练习

我们做一个完整练习,从"分析 IACA 报告"到"实施优化"再到"验证"。

**项目**:`simd-optimize-lab`

```bash
cargo new --bin simd-optimize-lab
cd simd-optimize-lab

# 装 hyperfine 测时间
cargo install hyperfine

# 装 llvm-mca 工具链
# Arch:
sudo pacman -S llvm
which llvm-mca
```

`src/main.rs`(朴素版):

```rust
use std::arch::x86_64::*;

fn main() {
    let mut src = vec![0xFF808080u32; 100_000];
    let mut dst = vec![0xFFFFFFFFu32; 100_000];

    unsafe {
        for chunk in 0..100_000 / 4 {
            let i = chunk * 4;
            let s = _mm_loadu_si128(src.as_ptr().add(i) as *const __m128i);
            let d = _mm_loadu_si128(dst.as_ptr().add(i) as *mut __m128i);
            let r = blend_naive(s, d);
            _mm_storeu_si128(dst.as_mut_ptr().add(i) as *mut __m128i, r);
        }
    }

    println!("dst[0] = {:#x}", dst[0]);
}

#[target_feature(enable = "sse4.1")]
unsafe fn blend_naive(src_v: __m128i, dst_v: __m128i) -> __m128i {
    // 朴素版:全部用 pblendvb
    let shuffle = _mm_set_epi8(
        15,15,15,15, 11,11,11,11,
        7,7,7,7, 3,3,3,3,
    );
    let alphas = _mm_shuffle_epi8(src_v, shuffle);
    let zero_mask = _mm_cmpeq_epi8(alphas, _mm_setzero_si128());
    let full_mask = _mm_cmpeq_epi8(alphas, _mm_set1_epi8(-1));
    let avg = _mm_avg_epu8(src_v, dst_v);  // 简化 blend
    let mut result = _mm_blendv_epi8(avg, src_v, full_mask);
    result = _mm_blendv_epi8(result, dst_v, zero_mask);
    result
}
```

跑 baseline:

```bash
RUSTFLAGS="-C target-cpu=native" cargo build --release
hyperfine -w 3 -r 10 ./target/release/simd-optimize-lab
# 输出大约:Time (mean ± σ): 0.5 ms
```

提取汇编,跑 llvm-mca,看 port pressure。如果 port 5 > 50%,实施"blendv → and/or"优化:

```rust
#[target_feature(enable = "sse4.1")]
unsafe fn blend_optimized(src_v: __m128i, dst_v: __m128i) -> __m128i {
    let shuffle = _mm_set_epi8(
        15,15,15,15, 11,11,11,11,
        7,7,7,7, 3,3,3,3,
    );
    let alphas = _mm_shuffle_epi8(src_v, shuffle);
    let zero_mask = _mm_cmpeq_epi8(alphas, _mm_setzero_si128());
    let full_mask = _mm_cmpeq_epi8(alphas, _mm_set1_epi8(-1));
    let avg = _mm_avg_epu8(src_v, dst_v);

    // 用 and/or 代替 pblendvb(选 full mask)
    // avg & ~full_mask | src_v & full_mask
    let avg_masked = _mm_andnot_si128(full_mask, avg);
    let src_masked = _mm_and_si128(full_mask, src_v);
    let result = _mm_or_si128(avg_masked, src_masked);

    // 同样替换 zero mask
    let r_masked = _mm_andnot_si128(zero_mask, result);
    let d_masked = _mm_and_si128(zero_mask, dst_v);
    _mm_or_si128(r_masked, d_masked)
}
```

重新跑 hyperfine。如果时间降了 20-30%,优化成功。

**关键学习点**:从"看到 IACA 报告"到"决定改哪条指令"到"改完实测验证",这是 SIMD 优化的核心技能。每一天后期的 day124 / day121 marathon 都用这套循环。Day 120 是这个循环的入门课。

## 12 · 验证陷阱:优化后没变快怎么办

你按 IACA 报告优化了,但 hyperfine 显示没变快——这是常态。可能原因:

1. **Cache miss 主导**:IACA 假设 0 cache miss。如果真实 cache miss 高,IACA 报告的 port pressure 不可信。用 perf stat 看 cache miss,先修 cache。
2. **Branch miss 主导**:同样 IACA 假设 0 branch miss。如果代码里有标量 if(短路 mask),branch miss 可能拖累。
3. **依赖链**:llvm-mca 假设独立 iteration,但你的代码可能有跨 iteration 的依赖(比如累加)。展开循环让 CPU 看到独立指令。
4. **CPU 频率**:优化后指令变多,可能触发 AVX 降频(Skylake Xeon AVX-512 heavy license)。看 `/proc/cpuinfo` 的 freq。
5. **编译器擅自改回**:你写的 `and/or` 版本,compiler 可能优化回 `blendv`(它觉得后者更"高效")。检查 `--emit asm`,确保你的版本真的进 binary。

**通用诊断步骤**:

```bash
# 1. perf stat 看大事件
sudo perf stat -e cycles,instructions,cache-misses,branch-misses ./target/release/app

# 2. perf record 找热点
sudo perf record -F 999 -g -- ./target/release/app
sudo perf report --stdio | head -50

# 3. 如果 perf 显示 cache miss 高,优化数据布局
# 4. 如果 perf 显示一切都好但仍然慢,检查编译器是否擅自改
cargo rustc --release -- --emit asm
grep -A 5 'blend_optimized' target/release/deps/*.s
```

这套诊断路径,工业 SIMD 工程师天天走。

## 14 · 端口优化的常见 5 大模式

工业 SIMD 工程师积累了几十年的"port 优化模式库"。下面这 5 个是最高频的,你能 80% 概率在自己的代码里遇到。

### 模式 1:消除 pblendvb → 用 and/or

这是 day120 的核心。pblendvb 占 port 5,and/or 占 port 0/1。当 pblendvb 数量 > 3 时,几乎总能换成 and/or。

但**注意**:`_mm_blendv_epi8` 是 SSE 4.1 严格按字节选择。`and` + `or` 模拟时,mask 必须是"全 0 或全 1"(每 byte 0xFF / 0x00)。`_mm_cmpeq_epi8` 生成的 mask 正好满足,所以 OK。

### 模式 2:消除 pshufb → 用 punpcklbw / psrld

`pshufb` 是"自由 shuffle",但占 port 5。如果你的 shuffle 是固定模式(不是 lookup table),用 `punpck*` / `psrl*` / `psll*` 替代:

```asm
; 原:pshufb 把 alpha broadcast
pshufb alpha_broadcasted, alphas, shuffle_mask

; 替代:如果 alpha 在 byte 3,我们想广播到 byte 0,1,2,3
psrld alpha_shifted, alphas, 24   ; alpha 到 byte 0,port 0
punpcklbw alpha_broadcasted, alpha_shifted, alpha_shifted  ; 8→16,port 5 但只 1 条
```

可能用 2-3 条 port 5 替代 1 条 pshufb?有时候反而更慢。要 IACA 验证。

### 模式 3:展开循环跨 iteration ILP

```rust
// 朴素:循环每 4 像素,串行
for i in 0..N/4 {
    let r = blend_4(&src[i*4], &dst[i*4]);
    store(&mut dst[i*4], r);
}

// 展开:每 8 像素一次,两个独立 chunk
for i in (0..N/4).step_by(2) {
    let r0 = blend_4(&src[i*4], &dst[i*4]);
    let r1 = blend_4(&src[(i+1)*4], &dst[(i+1)*4]);
    store(&mut dst[i*4], r0);
    store(&mut dst[(i+1)*4], r1);
}
```

CPU 乱序执行看到 r0 和 r1 无依赖,可以并行调度。port 5 仍然是 6 cycle 限制,但其它 port 的指令可以"塞"进 port 5 的空闲窗口。这通常给 20-40% 提升。

Rust 用 `#[inline(always)]` + 手动展开,或编译选项 `-C loop-unroll-threshold`。

### 模式 4:数据布局优化

最容易被忽略,但效果最大。把"用在一起的字段放在一起":

**反模式**(Array of Structs):

```rust
struct Pixel { r: u8, g: u8, b: u8, a: u8 }
let pixels: Vec<Pixel> = ...;
// blend 时要 pshufb 重组 → port 5 浪费
```

**正模式**(Struct of Arrays):

```rust
struct Pixels { r: Vec<u8>, g: Vec<u8>, b: Vec<u8>, a: Vec<u8> }
let pixels: Pixels = ...;
// blend 时直接 load r, g, b, a 各自的 16-byte,不需要 pshufb
```

从 AoS 改到 SoA,常给 2-3x 提升。是 day121 marathon 的关键决策之一。

### 模式 5:SIMD width 提升

SSE 是 128-bit(4 像素),AVX2 是 256-bit(8 像素),AVX-512 是 512-bit(16 像素)。理论加速 2x / 4x。

但**注意**:AVX-512 在 consumer Intel / 部分 AMD 触发降频。实测提升可能远低于 4x,甚至倒退。要用 perf stat 看 `cpu-clock` 和实际频率。

工业 SIMD 代码常用 "AVX2 是甜区"——足够宽,不降频。AVX-512 留给服务器 / HPC。

## 15 · 总结性心态

性能优化的元原则:**永远先测量**。每一个 IACA 报告都是"假设",要 perf 验证。每一个优化都要 hyperfine 重测。不要相信直觉——直觉告诉你"blendv 比 and/or 快",IACA 告诉你"port 5 满了",两者矛盾时,信 IACA + 实测。
