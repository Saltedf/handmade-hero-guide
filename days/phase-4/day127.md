# Day 127 · 对齐渲染内存

> SIMD 要 16 字节对齐,cache line 是 64 字节对齐,跨线程共享的 per-thread state 不能在同一个 cache line —— 今天把"对齐"这件事讲透,搞清楚 Day 121 的多核 tile 渲染为什么必须把每个工作线程的本地数据 64 字节对齐。

## 0 · 为什么要有这一天

Day 121 马拉松把屏幕分成 64×64 tile,每个 tile 渲染独立。Day 122-126 把多线程基础设施搭起来。现在你能 spawn 8 个工作线程,每个线程从共享 work queue pop 一个 tile task。

但是写完一跑 benchmark,你发现加速只有 2-3 倍,而不是理论上的 8 倍。你的 8 核 CPU,`htop` 看每个核都满载,但帧时间没掉到 1/8。问题在哪?

**问题在"false sharing"(伪共享)**。8 个工作线程各自的"渲染本地状态"(当前 tile 起点坐标、采样计数、当前 Z buffer 指针……)被你随手写在一个 struct 里:

```rust
struct WorkerState {
    tile_x: u32,
    tile_y: u32,
    sample_count: u32,
    // ...
}
let states: [WorkerState; 8] = [...];
```

`WorkerState` 大小可能是 32 字节。8 个 state 总共 256 字节,占 4 个 cache line(每 line 64 字节)。也就是说,**两个工作线程的 state 可能在同一个 cache line 里**。

线程 A 改自己的 `tile_x`,这条 store 让该 cache line 在 B、C、D... 所有其他核的 L1 cache 里 invalidate。其他核下次读自己的 state 时 miss,要从 L2/L3 重新加载——这就是 **MESI 协议的 ping-pong**,虽然 A 和 B 在改完全无关的变量,但物理上同处一个 cache line,代价等于强耦合。

**今天的核心**:把每个工作线程的本地状态 64 字节对齐(单独占一个 cache line),消除 false sharing。同时,把 SIMD 操作的 buffer 16 字节对齐(因为 `movaps` 指令要求),把 per-frame 全局数据放在不会跨核的地方。

心理锚点:做完今天你能(1)用 `#[repr(align(N))]` 把任何类型对齐到 N 字节;(2)解释为什么 N=64 而不是 N=16 或 N=128;(3)用 `perf c2c`(Linux 的 false sharing 探测工具)找出代码里的 cache line 争用;(4)在 Rust 里用 `crossbeam_utils::CachePadded<T>` 优雅地表达这个意图。

## 1 · Casey 今天做了什么

Casey 在 Day 126 的 ring buffer 之上,注意到工作线程的本地状态布局有问题。具体动作:

1. 给"每个工作线程一份"的渲染状态 struct 加 `__declspec(align(64))`(MSVC 写法)或 `__attribute__((aligned(64)))`(GCC/Clang),让编译器在数组布局时把每个元素放独立 cache line
2. 给 SIMD 用的 tile 像素 buffer 加 `__declspec(align(16))`,满足 `_mm_load_ps` 的对齐要求
3. 在主线程的"任务完成计数"和"任务目标计数"附近补 padding,避免这两个原子变量(频繁更新)和其他数据同 line
4. benchmark 验证:false sharing 消除后,8 核加速从 2.5x → 5.5x(理论 8x,剩下的损失是工作队列 contention 和 frame barrier)

这一天的核心思想一句话:**对齐不是 SIMD 的特殊要求,而是多核性能的基本卫生**。

## 2 · 心智模型

### 类比:画室 vs 公共更衣室

**SIMD 对齐(16 字节)** 像画室的规矩:画板必须是 A4(16 字节)规格,你拿个非 A4 的纸来,老师就不让你用滑动画架(SIMD 指令)。你可以用普通画架(`movups`,未对齐版本),但慢一点。

**Cache line 对齐(64 字节)** 像公共更衣室:每个 locker 是 64 字节宽。你和你朋友各自有一个 locker,如果你们的 locker 是物理上分开的(各自独占一格),你们同时拿东西互不干扰。如果你们的 locker 共用一个大柜子(cache line),一个人开门所有人都要回头(mesi invalidate)。

**Page 对齐(4096 字节)** 像房间:操作系统按页管理内存,跨页访问可能触发缺页中断,做 mmap 时 4KB 对齐能让边界清晰。

### 严谨原理:CPU cache hierarchy

x86_64 CPU 的内存层级:

```
        寄存器(0 周期)
            ↓ load/store
        L1 cache(32KB,4 周期)   ← 每核私有,cache line = 64 字节
            ↓ miss
        L2 cache(256KB-1MB,12 周期)  ← 每核私有
            ↓ miss
        L3 cache(8-32MB,40 周期)     ← 全核共享
            ↓ miss
        主内存(GB,200+ 周期)         ← 全部核共享,通过内存控制器
```

**Cache line 是 CPU 读内存的最小单位**。即使你只读 1 字节,CPU 也会把该字节所在的整个 64 字节 line 读进 L1。这是因为局部性原理:如果你读了字节 X,大概率你马上要读 X+1、X+2,所以一次读完整个 line,后续命中。

**MESI 协议**(Modified/Exclusive/Shared/Invalid)是多核 cache 一致性的基础。每个 cache line 在每个核的 L1 里都有一个 MESI 状态:

- **M(Modified)**:只有我有最新版本,主内存过期
- **E(Exclusive)**:只有我有,和主内存一致
- **S(Shared)**:多个核都有,内容一致,只读
- **I(Invalid)**:我的副本过期,要读必须重新 fetch

**False sharing 场景**:线程 A 在 cache line L 上写字节 X(L 变成 M),线程 B 在 L 上读字节 Y(发现 L 是 M,必须把 L 写回主内存再读),B 现在拿到 L 的 S,A 的 L 变 I。然后 A 又写 X(B 的 L 又变 I)…… 这种"乒乓"导致每次访问都 miss,实际性能可能比单核还慢。

### SIMD 的 16 字节对齐要求

x86 SSE 指令集引入了 `__m128`(128 位向量寄存器),装 4 个 f32 或 16 个 u8。配套指令:

| 指令 | 要求 | 用途 |
|---|---|---|
| `movaps` (aligned packed store) | **16 字节对齐,否则段错** | 快,标准用法 |
| `movups` (unaligned packed store) | 不要求对齐 | 慢,救急用 |
| `movdqa` (aligned double quadword) | **16 字节对齐,否则段错** | 整数 SIMD |
| `movdqu` (unaligned ...) | 不要求 | 慢 |

CPU 在执行 `movaps` 时,硬件检查地址 `% 16 == 0`。如果不是,CPU 触发 #GP(General Protection)异常,Linux 转换成 SIGSEGV(段错误),程序崩溃。

**注意**:AVX(`__m256`,32 字节)和 AVX-512(`__m512`,64 字节)的对齐加载指令(`vmovaps` 等)在硬件层面对未对齐访问已经不报错了(从 Haswell 起),但**对齐访问仍然更快**(避免跨 cache line)。所以工业代码仍然坚持对齐。

### 为什么是 64 字节

主流 x86_64 处理器(Intel Core / AMD Zen)的 cache line 是 64 字节。ARM 服务器(Graviton)也是 64 字节。老的 Intel Pentium 4 是 128 字节(已经被淘汰)。Apple Silicon 是 128 字节(但兼容 64)。

**通用规则**:`#[repr(align(64))]` 在所有现代 CPU 上都是安全的(都是 cache line 的整数倍),而且兼容未来的 128 字节 line(虽然浪费一些空间)。

如果你写跨平台的高性能库,可以用:
```rust
#[cfg(any(target_arch = "x86_64", target_arch = "aarch64"))]
const CACHELINE: usize = 64;
#[cfg(target_arch = "aarch64")]
const CACHELINE: usize = 128; // Apple M1
```

或者直接用 `crossbeam_utils::CachePadded`,它内部已经为每个 target 算好了。

### 验证对齐:Rust 和汇编层面

Rust 用 `#[repr(align(N))]` 表达对齐要求(N 必须是 2 的幂):

```rust
#[repr(align(64))]
struct AlignedTile {
    data: [u32; 64 * 64],
}
```

这告诉 rustc:"这个类型的实例必须放在地址是 64 倍数的地方"。`std::mem::align_of::<AlignedTile>() == 64`。

数组 `[AlignedTile; 8]` 自动每个元素对齐——rustc 会在元素之间加 padding 让每个都对齐 64 字节(即使 struct 大小本身不是 64 的倍数,编译器自动 round up)。

验证编译器真的做了对齐:

```bash
# 写个简单程序,打印地址
cat > /tmp/align_test.rs << 'EOF'
#[repr(align(64))]
struct A { x: u32 }
fn main() {
    let arr: [A; 4] = [A{x:0}, A{x:1}, A{x:2}, A{x:3}];
    for (i, a) in arr.iter().enumerate() {
        println!("arr[{}] @ {:p}, offset from 64-align = {}", i, a as *const A, (a as *const A as usize) % 64);
    }
    println!("size_of::<A>() = {}", std::mem::size_of::<A>());
}
EOF
rustc -O /tmp/align_test.rs -o /tmp/align_test && /tmp/align_test
```

预期输出:
```
arr[0] @ 0x7fff..., offset from 64-align = 0
arr[1] @ 0x7fff..., offset from 64-align = 0
arr[2] @ 0x7fff..., offset from 64-align = 0
arr[3] @ 0x7fff..., offset from 64-align = 0
size_of::<A>() = 64
```

`size_of` 是 64(虽然只有 4 字节的数据,但 align 64 让 rustc round up 到 64),所以数组里每个元素自动 64 字节对齐。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏里"对齐"出现在每一层:

| 层 | 对齐 | 为什么 |
|---|---|---|
| SIMD buffer | 16/32/64 | `movaps` 等指令要求 |
| Per-thread state | 64(cache line) | 避免 false sharing |
| Texture mipmap | 4(WHOLE TEXEL) | GPU 纹理压缩(DXT/BC)要求 4×4 块对齐 |
| Vertex buffer | 4 或 16 | GPU DMA 高效读取 |
| Constant buffer(D3D)/UBO(GL) | 16 或 256 | GPU shader uniform 对齐 |
| Asset file(.hha) header | 4 或 8 | 文件 IO 块对齐,readahead 高效 |
| Stack frame | 16(x86_64 ABI) | 函数调用约定 |

具体到 Day 121 的 tile 渲染:

```rust
// 错误:false sharing 高发
struct ThreadContext {
    tile_origin_x: i32,       // 4 字节
    tile_origin_y: i32,       // 4 字节
    sample_count: u32,        // 4 字节
    pixels_drawn: u32,        // 4 字节
}
let contexts: [ThreadContext; 8] = [...];
// 8 个 context 共 8 × 16 = 128 字节,挤在 2 个 cache line 里
// 每 4 个线程共享一个 cache line,false sharing 严重
```

```rust
// 正确:每个 context 独占 cache line
#[repr(align(64))]
struct ThreadContext {
    tile_origin_x: i32,
    tile_origin_y: i32,
    sample_count: u32,
    pixels_drawn: u32,
    // 编译器自动补 48 字节 padding 到总大小 64
}
let contexts: [ThreadContext; 8] = [...];
// 8 × 64 = 512 字节,占 8 个 cache line,每个线程独占一个
```

Casey 在 Day 127 之后所有多核代码都遵守这个规则。Day 165 修一个资产系统 bug 时,bug 根因就是漏了对齐。

游戏开发圈的工业实践:
- **Data-Oriented Design**(Mike Acton)第一条:数据布局优先。包括对齐
- **Naughty Dog 的 job system**:每个 job 的 context 单独 cache line
- **Frostbite 的 `JobSystem`**(EA DICE):同上
- **Unity ECS**:每个 archetype 的 chunk 16KB 对齐,内部组件按 alignment 紧凑排列

### 3.2 · 🐧 Linux 系统编程视角

Linux 上对齐相关的 API 和工具:

**`posix_memalign` / `aligned_alloc`**:分配对齐内存。
```c
void *ptr;
posix_memalign(&ptr, 64, 1024);   // 分配 1024 字节,起始地址对齐 64
// 或 C11:
void *ptr = aligned_alloc(64, 1024);
```

Rust 的 `std::alloc::Layout` + `alloc` 是对齐内存的标准 API:
```rust
use std::alloc::{alloc, Layout};
let layout = Layout::from_size_align(1024, 64).unwrap();
unsafe {
    let ptr = alloc(layout);  // 返回 NonNull<u8>,对齐到 64
    // ... 用 ptr
    dealloc(ptr, layout);
}
```

**`mmap` 的对齐**:`mmap` 返回的地址默认是 page 对齐(4096 字节),已经满足所有 cache line 需求。

**`getconf LEVEL1_DCACHE_LINESIZE`**:Linux 命令查 cache line 大小:
```bash
getconf LEVEL1_DCACHE_LINESIZE
# 64
```

或读 sysfs:
```bash
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
# 64
```

**`perf c2c`**(Linux 4.x+):**最强大的 false sharing 探测工具**。它采样 cache line 的 HITM(Hit Modified)事件,告诉你哪些 cache line 在核之间被频繁传递(= false sharing 嫌疑)。

```bash
sudo perf c2c record ./target/release/my_game
sudo perf c2c report
# 会显示一个表格:
# ====================================================
#                Trace Event Information
# ====================================================
#   Total HITM          : 12345
#   RMT HITM (cross-socket)  : 100
#   LCL HITM (same-socket)   : 12245
# ====================================================
#   Most affected cache lines:
#     0x7fab12345000: 5000 HITMs
#       variables: my_crate::WORKER_STATES  ← 找到凶手
```

如果你看到自己的 worker state 数组在 most affected 列表里,说明 false sharing 严重,加上 `#[repr(align(64))]` 再跑一次,HITM 应该大幅下降。

**`valgrind --tool=cachegrind`**:模拟 cache 行为,显示 miss 率。比 perf c2c 慢 20-100 倍,但精确。

### 3.3 · 🦀 Rust 生态视角

Rust 的对齐表达分几个层次:

#### `#[repr(align(N))]` —— 类型级

```rust
#[repr(align(64))]
struct CachePadded64<T>(T);
```

告诉 rustc:这个类型的对齐要求是 N 字节。N 必须是 2 的幂,且不能小于类型本身的自然对齐。`size_of` 自动 round up 到 N 的倍数(为了让数组里每个元素都对齐)。

#### `#[repr(C, align(N))]` —— 复合

`#[repr(C)]` 保证字段顺序和 C 一致(无重排),`align` 加对齐。组合用于 FFI 兼容 + 对齐。

#### `#[repr(packed)]` —— 反向操作

`#[repr(packed)]` 取消所有对齐 padding,字段紧贴。**极不推荐**,因为未对齐访问在某些架构上(ARMv5、MIPS)会段错,在 x86 上慢。Rust 中访问 packed 字段必须用 `addr_of!`,因为直接 `&packed.field` 可能产生未对齐引用(UB)。

#### `core::mem::align_of` —— 编译期查询

```rust
const ALIGN: usize = align_of::<u64>();  // 8
assert_eq!(align_of::<[u8; 16]>(), 1);   // 数组对齐 = 元素对齐 = 1
```

#### `std::alloc::Layout` —— 动态分配

```rust
let layout = Layout::array::<u32>(1024).unwrap();  // 1024 个 u32,对齐 4
let ptr = unsafe { alloc(layout) };
// ptr 对齐 4,大小 4096
```

#### `crossbeam_utils::CachePadded<T>` —— 工业级 cache line 对齐

```toml
[dependencies]
crossbeam-utils = "0.8"
```

```rust
use crossbeam_utils::CachePadded;
let v: [CachePadded<u64>; 8] = [
    CachePadded::new(0), CachePadded::new(1), /* ... */
];
// 每个 CachePadded 独占一个 cache line(64 字节)
```

`CachePadded` 内部就是 `#[repr(align(64))] struct CachePadded<T>(T)`,但它在不同 target 上自动调整(ARM 用 128)。生产代码用它,不用自己写。

#### `bytemuck::Pod` 和 `zerocopy::AsBytes` —— 安全 transmute

当你想把 `[u8; N]` 转 `[f32; N/4]`,必须保证对齐一致(u8 数组对齐 1,f32 数组对齐 4)。`bytemuck` 提供 `from_bytes` / `cast_slice`,内部检查对齐。

### 3.4 · SIMD 16 字节 vs cache line 64 字节

这两件事不矛盾,但容易混:

- **16 字节对齐**:`movaps` 等指令的硬件要求。让 SIMD 指令不报错。
- **64 字节对齐**:cache line 边界。让 SIMD load 不跨 line。

如果一个 SIMD load 跨 cache line(地址不是 64 倍数),CPU 要做两次内存读再拼接,慢 2 倍。所以**最优 SIMD 数据布局是 64 字节对齐**(同时也满足 16,因为 64 是 16 的倍数)。

```rust
#[repr(align(64))]  // 同时满足 cache line 和 SIMD
struct SimdBuffer {
    data: [f32; 16],  // 一个 __m128 × 4,共 64 字节
}
```

## 5 · 对照与变奏

### SIMD 对齐在不同架构上的差异

| 架构 | SIMD 寄存器宽度 | 对齐要求 |
|---|---|---|
| x86 SSE | 128 bit (__m128) | 16 字节(`movaps`) |
| x86 AVX | 256 bit (__m256) | 32 字节(`vmovaps`),但允许未对齐 |
| x86 AVX-512 | 512 bit (__m512) | 64 字节(建议) |
| ARM NEON | 128 bit (uint32x4_t) | 16 字节(`vld1q_u32`) |
| ARM SVE | 可变长度 | 取决于实现 |
| WASM SIMD | 128 bit (v128) | 16 字节 |

工业代码用 `std::simd`(Rust 的 portable SIMD,还在 nightly)或 `wide` crate 跨平台兼容:

```rust
use wide::f32x4;  // 自动适配 SSE/NEON
let v = f32x4::from([1.0, 2.0, 3.0, 4.0]);
```

### 历史演化

- 1990s:对齐是"性能优化",x86 还能未对齐访问(慢但能用)
- 2000s:SSE 引入,`movaps` 必须对齐;游戏引擎大改对齐
- 2010s:多核普及,cache line false sharing 成主要问题
- 2020s:RISC-V、ARM 服务器崛起,跨平台对齐库(`crossbeam-utils`)成基础设施

| | 你的版本 | crossbeam / rayon |

| 验证 | `assert_eq!(addr % 64, 0)` | `debug_assert!` 内置 |
| 测量 | 手动 perf c2c | CI 里集成 cachegrind |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:回答以下对齐相关问题:

1. `std::mem::size_of::<u8>() == 1`,`align_of::<u8>() == 1`。`size_of::<[u8; 5]>() == 5`,那 `align_of::<[u8; 5]>() == ?`
2. 一个 struct `{ a: u8, b: u32, c: u8 }`,`#[repr(Rust)]`(默认),`size_of` 是多少?`#[repr(C)]` 呢?为什么不同?
3. `#[repr(align(64))] struct W { x: u8 }`。`size_of::<W>() == ?`,为什么?
4. 一个原子变量 `AtomicU64` 在多核场景下被频繁修改,要不要对齐 64 字节?为什么?

**参考解答**:
1. `align_of::<[u8; 5]>() == 1`。数组的对齐 = 元素的对齐 = 1。数组本身不需要额外对齐。
2. `#[repr(Rust)]`(默认):rustc 会**重排字段**优化大小。可能重排成 `{ b: u32, a: u8, c: u8 }`,size = 8,align = 4。`#[repr(C)]`:按声明顺序,字段间加 padding。`{ a: u8, _pad: [0; 3], b: u32, c: u8, _pad: [0; 3] }`,size = 12,align = 4。Rust 默认重排省 4 字节,但失去 C ABI 兼容性。
3. `size_of::<W>() == 64`。`align(64)` 要求对齐 64 字节,而数组 `[W; N]` 要每个元素都对齐 64,所以 size 必须 round up 到 64 的倍数,最小是 64(虽然实际数据只占 1 字节,63 字节是 padding)。这看起来浪费,但消除 false sharing 的代价就是空间换性能。
4. **要**。原子操作本身是原子的(不会读到半截),但**同一个 cache line 里的多个原子变量会互相 false-share**。例如 `[AtomicU64; 8]` 默认是 8 × 8 = 64 字节,挤在一个 cache line 里,8 个核同时各自更新一个原子变量,会导致 cache line 在核之间疯狂 ping-pong。正确做法:`[CachePadded<AtomicU64>; 8]`,每个独占 64 字节。

### Lv2 · 动手实践

**题**:写一个 Rust 程序,验证 `#[repr(align(64))]` 真的影响性能。

要求:
1. 定义 `struct Counter { value: AtomicU64 }`(默认对齐)和 `#[repr(align(64))] struct CounterAligned { value: AtomicU64 }`
2. 创建 8 个 counter(`[Counter; 8]` 和 `[CounterAligned; 8]`),8 个线程各自只递增自己的 counter 1000 万次
3. 对比两种版本的总耗时

完成标准:对齐版本应该比未对齐版本快 1.5x-3x(取决于 CPU 核数和 L1 大小)。

**参考解答**:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Arc;
use std::thread;
use std::time::Instant;

// 未对齐版本
struct Counter {
    value: AtomicU64,
}
unsafe impl Sync for Counter {}

// 对齐到 cache line
#[repr(align(64))]
struct CounterAligned {
    value: AtomicU64,
    // 编译器自动补 56 字节 padding 到 size 64
}
unsafe impl Sync for CounterAligned {}

const N_THREADS: usize = 8;
const N_INCR: u64 = 10_000_000;

fn bench_unaligned() -> u128 {
    let counters: Arc<[Counter; N_THREADS]> = Arc::new([
        Counter { value: AtomicU64::new(0) },
        Counter { value: AtomicU64::new(0) },
        Counter { value: AtomicU64::new(0) },
        Counter { value: AtomicU64::new(0) },
        Counter { value: AtomicU64::new(0) },
        Counter { value: AtomicU64::new(0) },
        Counter { value: AtomicU64::new(0) },
        Counter { value: AtomicU64::new(0) },
    ]);
    let start = Instant::now();
    let mut handles = vec![];
    for i in 0..N_THREADS {
        let c = counters.clone();
        handles.push(thread::spawn(move || {
            for _ in 0..N_INCR {
                c[i].value.fetch_add(1, Ordering::Relaxed);
            }
        }));
    }
    for h in handles { h.join().unwrap(); }
    start.elapsed().as_millis()
}

fn bench_aligned() -> u128 {
    let counters: Arc<[CounterAligned; N_THREADS]> = Arc::new([
        CounterAligned { value: AtomicU64::new(0) },
        CounterAligned { value: AtomicU64::new(0) },
        CounterAligned { value: AtomicU64::new(0) },
        CounterAligned { value: AtomicU64::new(0) },
        CounterAligned { value: AtomicU64::new(0) },
        CounterAligned { value: AtomicU64::new(0) },
        CounterAligned { value: AtomicU64::new(0) },
        CounterAligned { value: AtomicU64::new(0) },
    ]);
    let start = Instant::now();
    let mut handles = vec![];
    for i in 0..N_THREADS {
        let c = counters.clone();
        handles.push(thread::spawn(move || {
            for _ in 0..N_INCR {
                c[i].value.fetch_add(1, Ordering::Relaxed);
            }
        }));
    }
    for h in handles { h.join().unwrap(); }
    start.elapsed().as_millis()
}

fn main() {
    println!("size_of::<Counter>() = {}", std::mem::size_of::<Counter>());
    println!("size_of::<CounterAligned>() = {}", std::mem::size_of::<CounterAligned>());
    // Counter 是 8 字节,8 个挤在 1 个 cache line
    // CounterAligned 是 64 字节,每个独占 1 个 cache line

    let t1 = bench_unaligned();
    println!("Unaligned: {} ms", t1);

    let t2 = bench_aligned();
    println!("Aligned:   {} ms", t2);

    println!("Speedup:   {:.2}x", t1 as f64 / t2 as f64);
}
```

**预期输出**(8 核 x86_64):
```
size_of::<Counter>() = 8
size_of::<CounterAligned>() = 64
Unaligned: 480 ms
Aligned:   180 ms
Speedup:   2.67x
```

**关键点**:
- `Ordering::Relaxed` 因为只关心原子性,不关心和其他变量的顺序
- 8 个 Counter 共 64 字节,正好挤在一个 cache line。8 个核同时改,MESI ping-pong 严重
- 8 个 CounterAligned 共 512 字节,8 个 cache line。每个核独占自己的 line,无 false sharing

### Lv3 · 迁移设计

**题**:你写一个事件计数器,记录游戏中 16 种不同事件(玩家死亡、怪物击杀、跳起、落地……)的发生次数。最自然的写法是:

```rust
struct EventCounts {
    counts: [AtomicU64; 16],
}
```

这个 `counts` 数组共 16 × 8 = 128 字节,占 2 个 cache line。多线程场景下(玩家线程 + 物理线程 + AI 线程同时各自递增不同事件),会有 false sharing。

设计一个 `EventCounts` 类型,要求:
1. 每个事件的 counter 独占 cache line(避免 false sharing)
2. 提供安全的 API:`inc(event_type: usize)` 和 `get(event_type: usize) -> u64`
3. 类型大小合理(不要因为过度对齐浪费太多空间)

**提示**:
- `crossbeam_utils::CachePadded<AtomicU64>` 是 64 字节
- 16 个 CachePadded = 1024 字节,占 16 个 cache line
- 用 `Index` trait 或 `Deref` 提供 `counts[event_type]` 接口

## 8 · Rust / Arch 落地代码

### Rust 完整可跑:对齐的 tile buffer

```rust
// Cargo.toml: 无依赖

use std::alloc::{alloc, dealloc, Layout};

const TILE_SIZE: usize = 64;

// 16 字节对齐(SIMD 友好)
#[repr(align(16))]
struct TilePixels16 {
    pixels: [u32; TILE_SIZE * TILE_SIZE],
}

// 64 字节对齐(cache line 友好,兼容 SIMD)
#[repr(align(64))]
struct TilePixels64 {
    pixels: [u32; TILE_SIZE * TILE_SIZE],
}

// 256 字节对齐(更激进的 future-proof)
#[repr(align(256))]
struct TilePixels256 {
    pixels: [u32; TILE_SIZE * TILE_SIZE],
}

fn main() {
    // 打印对齐信息
    println!("=== 自然对齐 ===");
    println!("align_of::<u8>()  = {}", std::mem::align_of::<u8>());
    println!("align_of::<u32>() = {}", std::mem::align_of::<u32>());
    println!("align_of::<[u32; 4096]>() = {}", std::mem::align_of::<[u32; 4096]>());

    println!("\n=== 显式对齐 ===");
    println!("align_of::<TilePixels16>() = {}", std::mem::align_of::<TilePixels16>());
    println!("align_of::<TilePixels64>() = {}", std::mem::align_of::<TilePixels64>());
    println!("align_of::<TilePixels256>() = {}", std::mem::align_of::<TilePixels256>());

    println!("\n=== Size(注意 padding) ===");
    println!("size_of::<TilePixels16>() = {}", std::mem::size_of::<TilePixels16>());  // 16384
    println!("size_of::<TilePixels64>() = {}", std::mem::size_of::<TilePixels64>());  // 16384(已是 64 倍数)

    // 动态分配对齐内存
    println!("\n=== 手动 alloc 对齐 64 ===");
    let layout = Layout::from_size_align(1024, 64).unwrap();
    unsafe {
        let ptr = alloc(layout);
        println!("allocated at {:p}", ptr);
        println!("address % 64 = {}", ptr as usize % 64);  // 应该是 0
        dealloc(ptr, layout);
    }

    // 验证 Box<[T]> 也尊重对齐
    println!("\n=== Box<T> 的对齐 ===");
    let boxed: Box<TilePixels64> = Box::new(TilePixels64 { pixels: [0; TILE_SIZE * TILE_SIZE] });
    let addr = &*boxed as *const TilePixels64 as usize;
    println!("Box<TilePixels64> at 0x{:x}, % 64 = {}", addr, addr % 64);  // 0
}
```

**预期输出**:
```
=== 自然对齐 ===
align_of::<u8>()  = 1
align_of::<u32>() = 4
align_of::<[u32; 4096]>() = 4

=== 显式对齐 ===
align_of::<TilePixels16>() = 16
align_of::<TilePixels64>() = 64
align_of::<TilePixels256>() = 256

=== Size(注意 padding) ===
size_of::<TilePixels16>() = 16384
size_of::<TilePixels64>() = 16384

=== 手动 alloc 对齐 64 ===
allocated at 0x7f...
address % 64 = 0

=== Box<T> 的对齐 ===
Box<TilePixels64> at 0x7f..., % 64 = 0
```
