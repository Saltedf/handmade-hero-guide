### 重构在工业里的真实地位

GitLab 2023 年开发者调查:**职业程序员平均 30% 时间花在重构**。Google 内部有专门的"refactoring sprint"——每季度一周,所有人停下功能开发,专心改代码。Linux 内核有"patch series"文化——一个大重构拆成 20 个小 patch,每个独立 review。

不重构的后果:技术债复利,最终代码"看似能跑但谁都不敢动"。这种代码叫 **legacy code**(Michael Feathers 定义:**没有测试的代码**)。Legacy code 是 IT 行业最大的成本——美国每年因 legacy code 维护损失 850 亿美元(2018 年 Stripe 调查)。

Casey 今天演示的是**避免 legacy code 的日常纪律**。每写完一段功能,马上花一天重构,代码永远干净。

视频里 Casey 反复强调几条原则:

- **重构 = 不改行为**:任何重构后游戏看起来一样、玩起来一样、性能一样。如果改了行为,那不是重构,是改造。
- **先测**:重构前必须先跑通游戏(或单元测试),确认基线行为正确。否则重构后没法判断"是对了还是破了"。
- **持续重构**:不是"等忙完了再重构",而是"代码乱就重构"。每写 50 行就停下来看 30 秒,问"这段还能更好吗"。

## 2 · 心智模型

### 2.1 类比:整理房间

房间用了一周,东西乱放:袜子在桌上、书在床上、杯子在沙发上、电池在抽屉、剪刀在衣柜。整理时:

- 袜子 → 抽屉(衣物区)
- 书 → 书架(阅读区)
- 杯子 → 厨房(餐饮区)
- 电池 → 抽屉(杂物区)
- 剪刀 → 抽屉(杂物区)

整理后房间结构变了(东西位置变),但**物品种类和数量不变**。你能更快找到东西、空间更宽敞、心情更好。

代码重构完全一样。变量名更清楚(把 `tmp1` 改成 `player_position`)、函数更短(把 200 行函数拆成 5 个 40 行)、模块更合理(把 asset 代码从 `main.rs` 移到 `assets.rs`)——**行为不变,可读性和可维护性提升**。

整理房间的关键纪律:**东西放回原位 + 标签清楚**。代码也一样:**函数在合理位置 + 名字准确表达意图**。

### 2.2 严谨模型:重构的核心操作

Martin Fowler 1999 年《Refactoring: Improving the Design of Existing Code》总结了 60+ 种重构操作。我把工业里最常用的 9 类列出来:

**1. Extract Function(提取函数)**:一段代码太长,把其中一段独立逻辑提取成函数。
```rust
// before
fn update_player(p: &mut Player) {
    // ... 30 行 player 移动
    // ... 40 行 player 渲染
}

// after
fn update_player(p: &mut Player) {
    move_player(p);
    render_player(p);
}
```

**2. Inline Function(内联函数)**:函数体太简单(一行),内联到调用点。反操作。
```rust
// before
fn is_adult(age: u32) -> bool { age >= 18 }
if is_adult(user.age) { ... }

// after
if user.age >= 18 { ... }
```

**3. Rename(改名)**:变量 / 函数 / 模块改更好的名字。
```rust
// before
fn proc(d: &Data) -> i32 { ... }

// after
fn calculate_score(player: &Data) -> i32 { ... }
```

**4. Extract Variable(提取变量)**:复杂表达式提取成临时变量,加名字。
```rust
// before
if (player.x - camera.x).abs() < 100 && (player.y - camera.y).abs() < 100 { ... }

// after
let dx = (player.x - camera.x).abs();
let dy = (player.y - camera.y).abs();
let is_near_camera = dx < 100 && dy < 100;
if is_near_camera { ... }
```

**5. Move Function(移动函数)**:函数移到更合适的模块。
```rust
// before: render_text 在 font.rs,但用了 renderer.rs 的 BlitCommand
// after: render_text 移到 renderer.rs,自然能用 BlitCommand
```

**6. Change Function Declaration(改签名)**:加参数、删参数、改返回类型。
```rust
// before
fn load(path: &str) -> Bitmap

// after
fn load(path: &Path) -> Result<Bitmap, LoadError>
```

**7. Encapsulate Variable(封装变量)**:public 字段改 getter/setter。
```rust
// before
pub struct Player { pub health: i32 }

// after
pub struct Player { health: i32 }
impl Player {
    pub fn health(&self) -> i32 { self.health }
    pub fn damage(&mut self, n: i32) { self.health = (self.health - n).max(0); }
}
```

**8. Replace Magic with Constant(魔法数字提常量)**:重复的硬编码数字提常量。
```rust
// before
if score > 1000 { level_up(); }
// ... 另一处
if data.len() > 1000 { truncate(); }

// after
const MAX_LIST_SIZE: usize = 1000;
if score > MAX_LIST_SIZE as i32 { level_up(); }
```

**9. Consolidate Conditional(合并条件)**:多个 if-else 分支合并成单一表达式。
```rust
// before
if status == 1 { return "loading"; }
else if status == 2 { return "ready"; }
else if status == 3 { return "error"; }
else { return "unknown"; }

// after
match status {
    1 => "loading",
    2 => "ready",
    3 => "error",
    _ => "unknown",
}
```

**每个操作都"很小"**——几行代码改动。但小操作累积,代码结构大幅改善。Fowler 的核心洞察:**重构不是大手术,是无数次微整形**。

### 2.3 重构 vs 重写:工业成本对比

新人最容易犯的错:**代码一乱就想"推翻重写"**。这几乎总是错的。

| 维度 | 重构 | 重写 |
|---|---|---|
| 行为 | 不变 | 改变(可能更好/更差) |
| 风险 | 低(小步前进) | 高(从零开始,新 bug) |
| 时间 | 短(每次几分钟到几小时) | 长(周/月/年) |
| 测试 | 必须先有 | 重写后再写 |
| 用户感知 | 0 | 可能断服务 |
| 历史信息 | 保留(commit log) | 丢失 |

**Joel Spolsky(Stack Overflow 创始人)经典文章《Things You Should Never Do, Part I》**:Netscape 4.0 决定重写浏览器,花了 3 年,期间 IE 抢占市场,Netscape 死了。Microsoft 也曾重写 Office,**险些杀掉这个产品**。重写是"软件工程里最危险的单一错误"。

工业数据(2020 IEEE Software 调查):**重写平均比重构贵 5-10 倍**,且 70% 的重写项目最终结果比原代码更糟(更多 bug、性能更差、维护更难)。

**何时重写**:

- 原架构根本性错误(如不适合新需求:从单线程改多线程,数据流模型不对)
- 性能天花板无法突破(原架构有 fundamental bottleneck)
- 没人能维护(原作者全离职,代码无人懂)
- 业务方向大变(原代码假设的前提全错)

**何时重构**(默认):

- 代码乱但能跑
- 想加新功能但耦合太重
- 想优化但代码看不懂
- bug 频发想根治

**经验法则**:**除非你能用一句话说清楚为什么必须重写,否则重构**。

### 2.4 Rust 特定重构

Rust 编译器比其他语言更严格,反而让重构**更安全**:

**模块重组**:`mod foo;` 移到不同文件,编译器报错逐个修。
**trait 提取**:多个 struct 共同方法 → trait + impl。编译器告诉你哪里不匹配。
**泛型化**:具体类型 → `<T>`。lifetime 同步显式化。
**enum 替代 bool**:多状态用 enum 更安全,编译器强制 match 全部分支。
**`#[deprecated]`**:旧 API 标记 deprecated,警告使用者迁移。

**Rust 工具链重构支持**:

```bash
cargo fmt        # 自动格式化(空白、缩进、行宽)
cargo clippy     # 400+ 条 lint,从风格到正确性
cargo fix        # 自动修 lint 建议
cargo fix --clippy  # 自动修 clippy 警告
# rust-analyzer 在 IDE 里:
#   F2:rename(全局,跨文件)
#   Ctrl+.:show actions(自动 fix,extract function,inline)
#   safe delete:删之前检查没有引用
```

**clippy 的几个常用 lint 例子**:

```rust
// before(clippy::map_clone)
let v: Vec<i32> = vec.iter().map(|x| *x).collect();
// after
let v: Vec<i32> = vec.iter().copied().collect();

// before(clippy::needless_collect)
let v: Vec<i32> = iter.collect::<Vec<_>>();
let sum: i32 = v.iter().sum();
// after
let sum: i32 = iter.sum();

// before(clippy::single_match)
match x {
    Some(v) => println!("{}", v),
    _ => {},
}
// after
if let Some(v) = x { println!("{}", v); }
```

Clippy 是工业 Rust 工程师每天用的工具。**装好让它跑,你会学到很多 Rust 惯用法**。

### 2.5 什么时候不该重构

知道"不该重构"和"该重构"一样重要。几个反模式:

**发布前一周**:重构改了行为(即便你以为是"等价"),引入新 bug,来不及测。**冻结期**原则。

**没测试的代码**:重构前必须有测试做安全网。没测试先写测试。**Michael Feathers 的 legacy code 定义就是"没测试的代码"**。

**hot path**:CPU-bound 的 inner loop,改一次行为不变但性能可能掉。重构前用 `cargo bench` 建基线。

**不懂代码**:你看不懂的代码不要重构。先读懂(加注释、画图),再改。

**大重构 + 加新功能同时**:做一件事。要么重构(行为不变),要么加功能(结构不动)。两件混在一起出 bug 难定位。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏代码的重构挑战是行业特有的:

**大文件**:Handmade Hero 的 `handmade.cpp` 到 Day 175 接近 5 万行。Unreal Engine 的某些 .cpp 文件超过 10 万行。IDE 加载慢、git diff 慢、code review 看不完。

**跨模块依赖**:游戏逻辑紧密耦合(玩家碰敌人 → 敌人受伤 → 敌人死亡 → 给玩家分数 → 分数触发 UI 更新)。一个 struct 改字段影响 20 个文件。

**缺乏测试**:游戏输出是图形,难自动化测试。手工测试覆盖不全,重构引入回归很难发现。

**快速迭代**:Game jam 一周内做出游戏,每周加新功能,没时间重构。

工业方案:

- **单元测试**对非图形代码(物理、AI、状态机)——这部分能像普通软件一样测。
- **可视化 snapshot 测试**:渲染一帧,保存截图。下次跑对比像素差异。工具:`insta`(Rust snapshot)、`reg-suit`(图像对比)。
- **CI 强制 coverage**:新代码必须 80% 覆盖(用 `tarpaulin` / `cargo-llvm-cov`)。
- **定期重构 sprint**:每月最后一周专门重构,不加新功能。Bevy、Unreal 都这么做。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核的重构哲学给所有软件工程师上的一课:

- **Never break userspace**(Linus Torvalds 名言):用户空间可见行为**永远不能改**。一个 syscall 的语义、一个 /proc 文件的格式,改动可能让数百万用户的应用崩溃。
- **小步前进**:patch series,每步独立可 review。20 个 patch 的重构 = 20 次小改动,每次几分钟 review。
- **review before merge**:每个 patch 至少 1 人 review 才能 merge。
- **git bisect 友好**:每个 commit 都能 build、能 boot、能跑。如果某个 commit 引入 bug,git bisect 能找到。

Rust 重构思想类似:**不破坏 API**(对外接口稳定)、**小步前进**(每步 cargo test 通过)、**git history 清晰**(每个 commit 一个改动)。

**Linux 重构案例**:2020 年 Linus 把 `wait_for_atomic` 函数(等 atomic 操作完成)重构成 `wait_for_atomic_*_timeout` 系列,加了 timeout 参数。改动只动了内部实现,syscall 行为不变。**这就是教科书级重构**。

### 3.3 · 🦀 Rust 生态视角

Rust 编译器**主动帮你重构**:

- 改 struct 字段名 → 编译器告诉你所有引用点
- 删字段 → 编译器告诉你哪里还在用
- 改函数签名 → 所有调用点报错,逐个修
- 改 trait → 所有 impl 报错,逐个修
- 加 `#[deprecated]` → 警告使用者迁移

这是 Rust 相对 C / Python 的**重构优势**——编译器做静态分析, refactor 不会"忘了改某处"。

**rust-analyzer IDE 集成**:

```bash
# Arch 装
sudo pacman -S rust-analyzer

# VS Code 装 "rust-analyzer" extension

# IDE 操作:
# F2:rename(跨文件,跨模块,跨 crate)
# Ctrl+Shift+O:文件内符号列表
# Ctrl+T:工作区符号搜索
# Ctrl+.:code action(自动 fix, extract, inline, generate)
# K:悬浮显示类型 / 文档
# gd:跳转定义
# gr:查找引用
```

rust-analyzer 2024 已经接近 IntelliJ IDEA Rust 插件的体验。**refactor-heavy 项目应该用 IDE 而不是手改**。

### 3.4 · 测试视角

重构前置:**好测试**。Michael Feathers 的 legacy code 工作法:

1. 给无测试代码加测试(characterization test)
2. 测试覆盖核心行为
3. 重构(此时有安全网)
4. 持续维护测试

测试金字塔:

```
       ╱ E2E ╲         少量,慢,覆盖完整流程
      ╱───────╲
     ╱  集成   ╲       中量,中速,覆盖模块间
    ╱───────────╲
   ╱    单元     ╲     多量,快,覆盖单个函数
  ╱───────────────╲
```

游戏 asset 模块的测试:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_load_text() {
        let mut s = MockStorage::new();
        s.add(0, "hello".to_string());
        assert_eq!(s.get(0).unwrap(), "hello");
    }

    #[test]
    fn test_release_unloads() {
        let mut s = AssetStorage::new();
        let _ = s.get(1);
        s.release(1);
        assert_eq!(s.loaded_count(), 0);
    }

    #[test]
    fn test_double_release_safe() {
        let mut s = AssetStorage::new();
        let _ = s.get(1);
        s.release(1);
        // 第二次 release 不应 panic(防 use-after-free)
        s.release(1);
    }

    #[test]
    fn test_concurrent_access() {
        // 多线程同时 get/release
        use std::sync::Arc;
        use std::thread;
        let s = Arc::new(std::sync::Mutex::new(AssetStorage::new()));
        let handles: Vec<_> = (0..8)
            .map(|_| {
                let s = Arc::clone(&s);
                thread::spawn(move || {
                    for i in 0..100 {
                        let _ = s.lock().unwrap().get(i);
                        s.lock().unwrap().release(i);
                    }
                })
            })
            .collect();
        for h in handles { h.join().unwrap(); }
    }
}
```

这套测试覆盖了正常路径、错误路径、并发场景。重构时跑一遍,通过就放心改。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **重构(refactoring)** —— 不改行为改结构。今天讨论的核心。
- **技术债(technical debt)** —— 不重构的代价,带利息的复利。
- **测试驱动开发(TDD)** —— red-green-refactor,重构的安全网。
- **持续集成(CI)** —— 每次重构后跑全测,自动验证不破坏。

### 4.2 同级(并行操作)

| 操作 | 何时用 |
|---|---|
| Extract Function | 函数太长,有独立逻辑段 |
| Inline Function | 函数体太短(一行),名字不增价值 |
| Rename | 名字模糊或不准确 |
| Move | 函数放在错误的模块 |
| Extract Variable | 复杂表达式难读 |
| Magic → Constant | 数字/字符串重复出现 |
| Consolidate Conditional | if-else 链可简化 |
| Trait 提取 | 多个 struct 有共同方法 |
| Enum 替代 bool | 多状态用 bool 不安全 |

### 4.3 下级(工具与零件)

- `cargo fmt` —— 格式化
- `cargo clippy` —— 400+ lint
- `cargo fix --clippy` —— 自动修
- `cargo test` —— 验证不破坏
- `cargo bench` —— 性能不退化
- rust-analyzer rename(F2)/ code action(Ctrl+.) —— IDE 操作
- git bisect —— 二分定位回归

## 5 · 对照与变奏

### 5.1 重构的"度"

过度和不足都有害:

| | 不足 | 适度 | 过度 |
|---|---|---|---|
| 频率 | 几年一次 | 持续小步 | 一周一次大重构 |
| 范围 | 不敢动 | 单文件 / 单模块 | 跨项目 |
| 测试 | 没 | 覆盖核心 | 100% 强迫 |
| commit | 大爆炸 | 小步多 commit | 一行一 commit |

**适度重构**的标志:git log 看起来是"add feature / rename X to Y / extract function Z / fix typo"——很多小 commit,每个意图清晰。

### 5.2 不同语言的重构工具

| 语言 | 工具 | 评估 |
|---|---|---|
| Java | IntelliJ IDEA 重构菜单 | 最强(20 年积累) |
| C# | Visual Studio / Rider | 强 |
| Rust | rust-analyzer + cargo + clippy | 强(2024 接近 IntelliJ) |
| TypeScript | tsserver / VS Code | 强 |
| Go | gopls / VS Code | 中等 |
| Python | rope / Jedi / Pylint | 中等(动态类型限制) |
| C++ | CLion / clang-refactor | 中等(模板/C 风格难) |
| JavaScript | ESLint + Prettier | 风格强,重构弱(动态) |

静态类型语言(Rust / Java / C# / TypeScript)重构工具远强于动态语言——编译器知道类型,refactor 不会"猜错"。

### 5.3 历史演化

- **1980s**:OOP 兴起,开始关注代码组织。Smalltalk IDE 第一个 rename 重构。
- **1990s**:Martin Fowler《Refactoring》出版(1999),奠定术语和方法论。
- **2000s**:IDE 重构普及(IntelliJ 2001、Eclipse 2003、Visual Studio 2005)。
- **2010s**:CI / code review 集成重构,GitHub PR 文化推广小步重构。
- **2020s**:AI 辅助重构(Copilot、Cursor)。AI 看代码建议 refactor,人 review。

每一步工具进步,都让重构更便宜、更安全。今天的 rust-analyzer + clippy 是这个进化的当代顶峰。

### 5.4 AI 时代的重构

GitHub Copilot / Cursor 已经能做基础重构:

- "把这个函数提取出来"——AI 看代码,生成 Extract Function 改动。
- "把这个 struct 重命名"——AI 全局替换(但不如 IDE rename 可靠)。
- "找代码里的 magic number"——AI 扫描,列出常量化建议。

但 AI 重构有风险:**AI 可能改行为**。它不理解"重构 = 不改行为"的微妙边界。**最佳实践**:AI 建议 + 人 review + 跑测试。**不要无 review 接受 AI 的重构 PR**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:重构和重写有什么区别?什么时候选哪个?

**参考解答**:

- **重构**:小步、不改行为、保留测试。适合"代码乱但能跑"。
- **重写**:从零、改行为、新测试。适合"代码乱且改不动,有重大架构错误"。

经验:**优先重构**。只有当原架构有根本问题(如不适合新需求、性能无法达标)才重写。重写的代码 70% 比原来的更糟(Brooks 定律)。

## 8 · Rust / Arch 落地代码

```rust
// === 重构前 ===
mod before {
    pub struct AssetStore {
        pub data: std::collections::HashMap<u32, String>,
        pub flag: bool,         // unused!
        pub legacy_max: u32,    // unused!
        pub magic: u32,         // magic number
    }

    impl AssetStore {
        pub fn get(&mut self, id: u32) -> Option<String> {
            // 重复逻辑
            if self.data.contains_key(&id) {
                Some(self.data[&id].clone())
            } else {
                let v = format!("asset_{}", id);
                self.data.insert(id, v.clone());
                Some(v)
            }
        }
    }
}

// === 重构后 ===
mod after {
    use std::collections::HashMap;

    const ASSET_PREFIX: &str = "asset_";

    /// 资产存储:lazy load + cache。
    /// 重构自 Day 158 的 AssetStorage,去掉冗余字段,
    /// 提取 prefix 为常量,合并 if/else。
    pub struct AssetStore {
        cache: HashMap<u32, String>,
    }

    impl AssetStore {
        pub fn new() -> Self {
            Self { cache: HashMap::new() }
        }

        pub fn get(&mut self, id: u32) -> String {
            // entry API 比 contains_key + insert 更简洁
            self.cache.entry(id)
                .or_insert_with(|| format!("{}{}", ASSET_PREFIX, id))
                .clone()
        }

        pub fn loaded_count(&self) -> usize {
            self.cache.len()
        }
    }

    #[cfg(test)]
    mod tests {
        use super::*;

        #[test]
        fn get_loads_on_first_access() {
            let mut s = AssetStore::new();
            assert_eq!(s.get(1), "asset_1");
            assert_eq!(s.loaded_count(), 1);
        }

        #[test]
        fn get_returns_cached() {
            let mut s = AssetStore::new();
            let a = s.get(1);
            let b = s.get(1);
            assert_eq!(a, b);
            assert_eq!(s.loaded_count(), 1);  // 没重复加载
        }

        #[test]
        fn different_ids_dont_collide() {
            let mut s = AssetStore::new();
            s.get(1);
            s.get(2);
            assert_eq!(s.loaded_count(), 2);
        }
    }
}

fn main() {
    let mut s = after::AssetStore::new();
    println!("{}", s.get(1));
    println!("{}", s.get(2));
    println!("{}", s.get(1));
    println!("loaded: {}", s.loaded_count());
}
```

**关键重构**:

1. **删除 `flag`, `legacy_max`, `magic`**:未用字段
2. **`ASSET_PREFIX` 常量**:代替重复字符串
3. **`entry().or_insert_with()`**:代替 `contains_key` + `insert`,更 Rust 风格
4. **doc comment**:解释结构用途
5. **测试**:保证行为不变
