# Day 126 · 循环 FIFO 工作队列

> 把"原子操作"和"内存屏障"组装成第一个真实可用的并发原语:一个被 N 个工作线程共享、单生产者多消费者的循环 FIFO 队列。这一天的代码会变成 Day 131 异步合成、Day 132 资产流式加载的发动机。

## 0 · 为什么要有这一天

Day 121 的 tile 渲染马拉松把整个屏幕切成 64×64 的小方块,丢给多个 CPU 核心并行处理。但当时 Casey 只是"概念上"做了并行——实际怎么把"渲染 tile (x, y) 这个任务"传给空闲的工作线程,他没写。Day 122 引入了"多线程"的概念,Day 123 讲了原子操作(`fetch_add`、`compare_exchange`),Day 124 讲了内存屏障(Acquire/Release 配对)。Day 125 Casey 抽象出了 work queue 的接口:`push(task)` 和 `pop() -> Option<task>`。

但抽象只是签名,**实现还空着**。今天的任务就是把它填上。

你要解决的真问题:**主线程每一帧产生 100 个 tile 任务(比如 1280×720 屏幕切成 20×12 = 240 个 64×64 tile,部分被裁剪后大约 100 多个),8 个工作线程要并发地从队列里取任务执行,不能丢、不能重复、不能让队列本身成为瓶颈。**

听起来朴素,实现起来处处是坑:
- 如果用 `Mutex<Vec<Task>>`,每次 push/pop 都要锁,8 个线程争一把锁,锁本身成为热点,缓存行 ping-pong
- 如果不锁,两个线程可能同时读到同一个 head 指针,然后都去"消费"同一个槽位
- 即使用了原子操作,如果忘记加 Acquire/Release,A 线程 push 完任务的"数据"还没写到内存,B 线程 pop 出 task 指针却发现 task 的字段还是旧值

Casey 选择**手写一个固定大小的环形 buffer(ring buffer)+ head/tail 原子指针**,完全 lock-free。这是 Linux 内核里 `kfifo`、DPDK 里 `rte_ring`、Rust `crossbeam-queue` 的同款思路——理解了这个,你看任何高性能并发队列都不再害怕。

心理锚点:做完今天,你能(1)解释为什么环形队列用"保留一个空槽"的技巧区分满和空;(2)用 `compare_exchange` 写出一个正确的 lock-free push;(3)用 `Ordering::Acquire/Release` 配对保证 task 的数据在指针更新前对其他线程可见;(4)说出 Casey 的版本和工业级 `crossbeam-queue::ArrayQueue` 在哪些地方有差距。

## 1 · Casey 今天做了什么

Casey 把 Day 125 留下的 work queue 抽象落地。具体动作:

1. 定义一个固定大小的数组 `entries[256]`,每个 entry 是一个 union(可以是任意任务类型——Casey 用 C 的 union,Rust 里我们用 enum 或者类型擦除的闭包)
2. 加两个原子索引 `volatile uint32 completion_target`、`volatile uint32 completion_count`、`volatile uint32 next_entry_to_write`、`volatile uint32 next_entry_to_read`
3. `push`:`entry[write_index] = task; write_index = (write_index + 1) % MAX`。用 `_ReadWriteBarrier()` / `_WriteBarrier()` 保证"先写 entry 再推进 write_index"
4. `pop`:读 `read_index`,如果 `read_index == write_index` 则空,否则消费 `entry[read_index]` 并推进 read_index
5. 主线程用 `MakeQueue` 初始化,自己也是工作线程之一(避免"主线程只 push 不 pop"导致 8 个核里有 1 个闲着)

Casey 这一天没引入新理论——理论在 Day 122-124 都铺好了。今天全是工程实现:把抽象变成可跑的代码,然后立刻拿 tile 渲染当负载,验证多核加速。

## 2 · 心智模型

### 类比:医院的叫号系统

想象一家诊所,有 8 个诊室(8 个工作线程),一个前台(主线程),一面号码牌墙(环形队列)。

前台每来一个病人就在号码牌上贴一个号(从 1 到 256,贴满 256 之后绕回 1 继续贴)。每个诊室门口有个屏幕显示"现在叫到几号",诊室医生看到"自己的叫号指针 < 前台贴到的号",就去取一个病人。

关键问题:
- **两个诊室同时看到 5 号可叫,会不会都叫 5 号?** —— 不会,只要"取号"是个原子 compare-exchange 操作:每个诊室先读"我的叫号指针 = 5",然后尝试原子地把它改成 6,如果失败说明有人抢先了,重读
- **诊室取到号 5,但前台还没把 5 号病人的病历送过来?** —— 这就是 Day 124 讲的内存屏障问题:前台必须用 Release 序写病历 + 推进贴号指针,诊室必须用 Acquire 序读贴号指针 + 读病历
- **号码牌贴满 256 怎么办?** —— 两个办法:(a) 等到诊室取走一些再贴(队列满了 push 阻塞);(b) 把队列做大到永远不会满(因为一帧最多产生几百个 task,256 足够)。Casey 选 (b)

### 严谨原理:为什么用环形 buffer

线性数组做 FIFO 有个致命问题:head 和 tail 永远在增长,pop 完的内存不能复用,数组会越来越大。

环形 buffer(ring buffer / circular buffer)把数组想象成一个环:索引 `i` 推进到 `CAP` 时,绕回到 0。这样数组大小固定,head/tail 永远在 `[0, CAP)` 内循环。

```
CAP = 8 的环形 buffer,逐步 push 5 个再 pop 2 个:

初始:        write=0, read=0,所有槽位空
[ ][ ][ ][ ][ ][ ][ ][ ]
  ↑
  write=read

push A:      write=1, read=0
[A][ ][ ][ ][ ][ ][ ][ ]
  ↑read   ↑write

push B,C,D,E: write=5, read=0
[A][B][C][D][E][ ][ ][ ]
  ↑read            ↑write

pop A:       write=5, read=1
[A][B][C][D][E][ ][ ][ ]
     ↑read        ↑write

pop B:       write=5, read=2
[A][B][C][D][E][ ][ ][ ]
        ↑read     ↑write

(槽位 A, B 数据虽未被覆盖,但 read 已越过,可被下次 push 覆盖)

继续 push F,G,H:write=0(绕回!), read=2
[F][G][H][D][E][ ][ ][ ]
              ↑read  ↑write(回到 0)
```

### 难点:如何区分"满"和"空"

如果 `write == read`,可能是:
- 队列空(write 没动过,或 read 追上 write)
- 队列满(write 绕一圈追上 read)

两种状态用同一个条件无法区分。三种解法:

**解法 A:保留一个空槽**。永远不写满,留 1 个空位。`满 ⇔ (write + 1) % CAP == read`。Casey 用这种,简单可靠。

**解法 B:额外一个 size 计数器**。push 时 `size.fetch_add(1)`,pop 时 `size.fetch_sub(1)`。`满 ⇔ size == CAP`。代价:多一次原子操作。

**解法 C:索引不绕回,用 64 位整数永远增长**。`满 ⇔ write - read == CAP`。索引本身是 64 位,2^64 个 push 才会溢出(永远不可能)。Linux `kfifo` 用这种(但用 32 位 + 位掩码)。Casey 后面 Day 165 修 bug 时也会考虑这种。

我们今天实现解法 A,因为最直观。

### 难点:多消费者的 pop

主线程单生产者,push 简单:只有自己改 write,Acquire/Release 用得对就行。

但工作线程是**多消费者**——8 个线程同时 pop。两个线程可能同时读到 `read_index = 5`,都尝试消费 slot 5。

解法:**compare_exchange(CAS)loop**。
```rust
loop {
    let cur = read_index.load(Acquire);
    if cur == write_index.load(Acquire) { return None; }  // 空
    // 尝试原子地把 read_index 从 cur 推进到 cur+1
    match read_index.compare_exchange(cur, (cur + 1) % CAP, AcqRel, Acquire) {
        Ok(_) => {
            // 我抢到了 slot cur,读它的数据
            return Some(entries[cur].take());
        }
        Err(_) => continue,  // 别人抢走了,重试
    }
}
```

CAS 是 lock-free 多消费者的心脏。两个线程同时尝试 CAS,只有一个成功,另一个拿到 `Err`,重试即可。

### Rust 表达:UnsafeCell + AtomicUsize

队列里那个 `entries: [Option<Task>; CAP]` 数组被多个线程同时读写,Rust 的借用检查器天然不允许(`&mut entries` 不能有 alias)。我们要用 `UnsafeCell`(告诉编译器"我自己管别名")包裹数组,然后用原子操作的语义证明安全性。

工业级实现(如 `crossbeam-queue::ArrayQueue`)用更复杂的 `Arc<Inner>` + `CachePadded<T>` 避免伪共享。我们今天先写一个教学版,工业级对比放 §3.4。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏里 work queue 几乎是**所有"主线程 spawn,工作线程执行"模式的基础设施**:

| 用途 | 产生者 | 消费者 | 本项目哪天用到 |
|---|---|---|---|
| Tile 渲染 | 主线程切屏幕 | 工作线程 | Day 121 / 126 |
| 资产加载 | 主线程检测 miss | IO 线程 | Day 132 |
| 地面合成 | 主线程检测可见 chunk | 工作线程 | Day 131 |
| 物理子步 | 主线程收集碰撞对 | 工作线程 | (HH 后期) |
| 粒子模拟 | 主线程标记脏粒子组 | 工作线程 | Day 155+ |

Casey 的队列设计有几个游戏特定的取舍:

1. **每帧重置**。每帧主线程产生一批 task,等所有工作线程消费完(completion_count == completion_target),才进入下一帧。这种"barrier per frame"模型简化了正确性(下一帧主线程能假设所有上帧 task 完成),代价是帧时间被最慢的 task 决定。
2. **主线程也是工作线程**。主线程 push 完所有 task 后,自己也参与 pop,不浪费一个核。这避免了"主线程等 8 个工作线程,自己干等"的浪费。
3. **task 是函数指针 + 数据指针**,不是闭包。Casey 在 C 里写 `typedef void work_callback(work_queue *queue, void *data)`,每个 entry 是 `{callback, data}`。Rust 里我们用 trait object 或 enum。

游戏开发圈的其他做法:
- **Job system with dependencies**(如 Naughty Dog 的 job system,见 GDC 2015 talk):task 之间有依赖图,DAG 调度。Casey 不做,每帧所有 task 独立
- **Task stealing**:每个工作线程有自己的本地队列,空了去偷别人的(`crossbeam-deque`、Rayon 的基础)。Casey 用全局队列,简单但 contention 高
- **Fiber / coroutine**: Naughty Dog 的 GoW 用 coroutine 做更轻量的任务切换。HH 完全不做

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核自己就有几个 work queue 实现,你今天写的代码概念上和它们是亲戚:

**`kfifo`(kernel FIFO)**:Linux 内核的环形 buffer。在 `include/linux/kfifo.h`。和 Casey 的设计一致:固定大小、绕回。多消费者版本叫 `kfifo_alloc` + 自旋锁保护。

**`rte_ring`(DPDK)**:Intel DPDK 数据平面库里的多生产者多消费者环形队列,跑在 user-space,完全 lock-free。它的"无锁"靠 CAS loop + 128 位原子操作(同时更新 head 和 data 指针)实现。性能比 Casey 的版本高 2-3 倍,但代码复杂度也高 5 倍。

**Linux `futex` + mutex**:如果你只是想"快速搞个能跑的",`std::sync::Mutex<Vec<Task>>` 就够了。代价是每次 push/pop 都进内核(锁竞争时 futex 系统调用),比 lock-free 慢 10-100 倍。

线程创建:Linux 上 `pthread_create`(Rust 的 `std::thread::spawn` 底层调它),每个线程默认 8MB 栈(`ulimit -s` 看),要小心 OOM。

```bash
# 看你系统当前的线程数限制
cat /proc/sys/kernel/threads-max
# 输出例如:63704

# 看每个线程默认栈大小
ulimit -s
# 8192 (KB,即 8MB)

# 看你这个进程当前有多少线程
ps -T -p $(pgrep -f your_program) | wc -l
```

**CPU 亲和性(affinity)**:可以把每个工作线程绑定到一个核,避免线程在核之间迁移导致 cache 冷启动。Linux 用 `sched_setaffinity`,Rust 用 `core_affinity` crate。Casey 在 Day 122 提到但没实现,我们今天也不做(留下作为 Lv4)。

**false sharing(伪共享)**:如果 `write_index` 和 `read_index` 在同一个 64 字节 cache line 里,主线程 push 改 write 让该 cache line 在所有工作线程的 cache 里 invalidate,工作线程 pop 改 read 让主线程的 cache invalidate,即使两者逻辑上无冲突。解法:用 `#[repr(align(64))]` 把每个原子变量放独立 cache line。Rust 的 `crossbeam-utils::CachePadded<T>` 就是干这个。

### 3.3 · 🦀 Rust 生态视角

Rust 表达 lock-free 数据结构有几个关键工具:

#### `UnsafeCell<T>` —— 编译器的"别管这个"信号

```rust
use std::cell::UnsafeCell;
struct Queue<T: Copy> {
    entries: UnsafeCell<[Option<T>; CAP]>,
    write: AtomicUsize,
    read: AtomicUsize,
}
```

`UnsafeCell` 是 Rust 内部原语,告诉编译器:"这个内存可能被多个引用别名化,你的 alias 分析不要假设它只被一个 `&mut` 持有"。所有"内部可变性"(`Cell`、`RefCell`、`Mutex`、`RwLock`、所有原子结构)底层都是 `UnsafeCell`。

#### `unsafe impl Sync` —— 告诉类型系统我保证线程安全

```rust
unsafe impl<T: Send + Copy> Sync for Queue<T> {}
```

默认 `UnsafeCell` 不是 `Sync`(因为多线程同时 `&mut` 不安全)。我们手写 `unsafe impl Sync`,因为**我们**通过原子操作保证了线程安全。这是 unsafe 的合理使用——你在和类型系统说"相信我,我知道我在做什么"。

#### `compare_exchange` 的 signature

```rust
pub fn compare_exchange(
    &self,
    current: usize,             // 期望的当前值
    new: usize,                 // 要换成的值
    success: Ordering,          // 成功时的内存序
    failure: Ordering,          // 失败时的内存序
) -> Result<usize, usize>;     // Ok(old_val) 或 Err(actual_val)
```

为什么 success 和 failure 用不同 Ordering?失败时其实是个 load,所以 failure 不能比 load 强(用 Acquire 或 Relaxed)。成功时是 read-modify-write,可以用 AcqRel 或 SeqCst。

#### 工业级替代:`crossbeam-queue::ArrayQueue`

```toml
[dependencies]
crossbeam-queue = "0.3"
```

```rust
use crossbeam_queue::ArrayQueue;
let q = ArrayQueue::new(256);
q.push(task).unwrap();      // 满了返回 Err
let t = q.pop();             // 空了返回 None
```

`ArrayQueue` 是工业级的 lock-free MPMC 队列,代码:https://github.com/crossbeam-rs/crossbeam/blob/master/crossbeam-queue/src/array_queue.rs。我们今天手写是为了**理解原理**,生产代码用 crossbeam。

#### `wide` crate 和 portable-SIMD:今天用不到,但 Day 144+ 混音器会用到

提一下,Day 144-145 的 SSE 混音器会用 `wide::f32x4` 或 `core::arch::x86_64::__m128`,而不是标量循环。和今天的队列是平行的两套加速手段。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **并发原语(concurrency primitive)** —— 操作系统/语言提供给多线程协作的工具:锁、信号量、condition variable、原子操作、channel、work queue
- **Lock-free 数据结构** —— 不用互斥锁,只用原子操作 + CAS 实现的并发数据结构。代表作品:Michael-Scott 队列、Treiber stack
- **生产者-消费者模式** —— 经典并发模式:一类线程产生数据,另一类消费,中间用队列解耦

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Casey 手写 ring buffer | lock-free MPMC,固定大小,简单 | 教学,每帧重置 | ✅ |
| `Mutex<Vec<Task>>` | 简单粗暴,锁开销 | 原型,任务量小 | Day 122 演示过 |
| `crossbeam-queue::ArrayQueue` | 工业级 lock-free | 生产代码 | Day 159 重构时考虑 |
| `crossbeam-queue::SegQueue` | 无界 lock-free 链表 | 任务量未知 | 不推荐,链表 cache 不友好 |
| `std::sync::mpsc::channel` | 单生产者单消费者 | 主线程→一个 IO 级 | Day 132 资产加载可用 |
| `flume` / `tokio::sync::mpsc` | 异步 channel | 异步生态 | HH 不同步,不用 |
| Rayon 的 work-stealing | 每线程本地队列 + 偷 | 通用数据并行 | HH 自己手写,不用 |

详细说明:Casey 选 ring buffer 因为(1)内存连续,cache 友好;(2)固定大小,无动态分配;(3)head/tail 自然适配原子操作;(4)用"保留一槽"区分满空,代码极简。Rayon 的 work-stealing 在 task 数量极不均衡时更优(快线程帮慢线程),但实现复杂 10 倍。HH 的负载(均匀的 tile 渲染)不需要这种优化。

### 4.3 下级(内部零件)

- **环形数组** `[Option<Task>; CAP]` —— 任务存储,固定大小
- **`AtomicUsize` write_index** —— 下一个写入槽位
- **`AtomicUsize` read_index** —— 下一个读取槽位
- **`compare_exchange` CAS loop** —— 多消费者竞争 pop 的解决
- **`Ordering::Acquire/Release/AcqRel`** —— 保证 task 数据在 index 推进前对其他核可见
- **`CachePadded<T>`**(可选)—— 避免 false sharing
- **`completion_count` / `completion_target`** —— 主线程判断"本帧所有 task 完成"

## 5 · 对照与变奏

### 单生产者 vs 多生产者

Casey 的版本是单生产者(只有主线程 push),所以 push 不需要 CAS,只是普通的"写 entry + Release 推进 write_index"。如果是多生产者(GIL-free 服务器常见),push 也要 CAS loop 抢 write_index 槽位。Rust 的 `crossbeam-queue::ArrayQueue` 是 MPMC(多生产者多消费者),push 和 pop 都 CAS。

### 阻塞 vs 非阻塞

Casey 的版本非阻塞:push 满了 panic(因为设计上保证不会满),pop 空了立即返回 None。工作线程"空了"时 spin-wait(busy loop)等新 task。

阻塞版本(`std::sync::mpsc`):push 满了阻塞,等待消费者腾位置;pop 空了阻塞,等生产者推。底层用 condition variable + Mutex。代价是上下文切换(每次阻塞都要 syscall),但 CPU 不空转。

游戏开发选非阻塞 spin:帧时间 16ms,spin 一次几纳秒,远比 syscall便宜。但 spin 会浪费电(笔记本风扇狂转),所以 Casey 在 spin 中间加 `_mm_pause()`(x86 hint,CPU 知道这是 spin-wait,降频等待)。

### 历史演化

- 1970s:Dijkstra 信号量,Hoare monitor —— 锁的时代
- 1990s:Michael-Scott lock-free queue —— CAS 时代开始
- 2000s:Java `java.util.concurrent`,boost `lockfree` —— 工业化
- 2010s:Crossbeam / Tokio —— Rust 生态成熟
- 2020s:io_uring + async —— Linux 内核层面重构 IO 并发

你今天写的代码停在 1990s Michael-Scott 的简化版(环形 vs 链表),但概念上和 2020s 工业版同源。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 的环形队列用"保留一个空槽"区分满和空。具体是 `(write_index + 1) % CAP == read_index` 判断满,`write_index == read_index` 判断空。

请回答:
1. 如果不保留空槽,直接 `write == read` 判空、`(write + 1) % CAP == read` 判满,会发生什么矛盾?
2. 为什么是 `+1` 而不是 `+2` 或 `+0`?
3. 如果 CAP 是 256,实际能装多少个 task?为什么?

**参考解答**:
1. 当队列里有 CAP-1 个 task 时,`write = read - 1`(绕回算),`(write+1) % CAP == read` 成立,判为满。如果继续 push 直到 `write == read`,此时既满足"空"也满足"满"的条件,无法区分。这就是为什么要保留一个空槽:让"满"和"空"的条件永远不相交。
2. `+1` 表示"write 再走一步就追上 read",这是物理上"满"的极限。`+0` 会立刻和"空"冲突;`+2` 会浪费两个槽位,没有意义。
3. 255 个。CAP=256 的数组,保留 1 个空槽做"满"判定,实际容量是 255。代价是浪费 1/256 ≈ 0.4% 的空间,换来代码简单。

### Lv2 · 动手实践

**题**:在 Rust 项目里实现一个 SPSC(单生产者单消费者)版本的 lock-free ring buffer。要求:
- 容量 CAP = 64
- 元素类型 `u64`
- `push(v: u64) -> Result<(), u64>`:满返回 `Err(v)`
- `pop() -> Option<u64>`:空返回 `None`
- 多线程测试:一个生产者线程 push 10000 个数,一个消费者线程 pop,最后所有数都被收到且无重复

完成标准:`cargo run` 后打印 `All 10000 items received in order`。

**参考解答**:

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::cell::UnsafeCell;

const CAP: usize = 64;  // 环形 buffer 容量

// 队列本体。T: Send + Copy 表示元素可以跨线程移动且按位复制
struct RingBuffer<T: Send + Copy> {
    // UnsafeCell 告诉编译器:"这个数组可能被多线程别名化,你别管"。
    // 我们用原子操作保证安全,所以这是合理的 unsafe。
    entries: UnsafeCell<[Option<T>; CAP]>,
    write: AtomicUsize,  // 下一个写入槽位
    read: AtomicUsize,   // 下一个读取槽位
}

// SAFETY: 我们保证:
// 1. push 只有主线程调用,顺序:先写 entry 再 Release 推进 write
// 2. pop 用 CAS loop 保证只有一个线程拿到每个槽位
// 3. T: Send 表示元素可以跨线程传
unsafe impl<T: Send + Copy> Sync for RingBuffer<T> {}
// 单线程 send 一定安全
unsafe impl<T: Send + Copy> Send for RingBuffer<T> {}

impl<T: Send + Copy> RingBuffer<T> {
    fn new() -> Self {
        // 用 const 泛型数组的初始化:CAP 个 None
        // SAFETY: Option<T> 默认 None 是合法初始化
        let entries = unsafe {
            let mut arr: [Option<T>; CAP] = std::mem::MaybeUninit::uninit().assume_init();
            // 上面 assume_init 看起来吓人,但 Option<T> 的 None 是 niche 优化位模式,合法
            // 实际生产代码用 [const { None }; CAP] (Rust 1.79+)
            for slot in arr.iter_mut() {
                slot.write(None);
            }
            arr
        };
        Self {
            entries: UnsafeCell::new(entries),
            write: AtomicUsize::new(0),
            read: AtomicUsize::new(0),
        }
    }

    fn push(&self, v: T) -> Result<(), T> {
        let w = self.write.load(Ordering::Relaxed);  // 只有自己写 write,Relaxed 够
        let r = self.read.load(Ordering::Acquire);   // 配对 pop 的 Release
        // 满:(w + 1) % CAP == r
        if (w + 1) % CAP == r {
            return Err(v);  // 满了,返回值
        }
        // SAFETY: 我们刚检查过不满,且只有自己写 write_index,slot w 一定不被并发写
        unsafe {
            let arr = &mut *self.entries.get();
            arr[w] = Some(v);
        }
        // Release:保证上面的 arr[w] = Some(v) 在 write_index 推进前对消费者可见
        self.write.store((w + 1) % CAP, Ordering::Release);
        Ok(())
    }

    fn pop(&self) -> Option<T> {
        let r = self.read.load(Ordering::Relaxed);
        let w = self.write.load(Ordering::Acquire);  // 配对 push 的 Release
        // 空:w == r
        if r == w {
            return None;
        }
        // SAFETY: r < w(逻辑上),slot r 已被 push 写过,我们读出来
        let v = unsafe {
            let arr = &mut *self.entries.get();
            arr[r].take()  // take 把 Option<T> 取出并留下 None
        };
        // Release:上面的读取完成后再推进 read_index,让 push 看到"slot r 空了"
        self.read.store((r + 1) % CAP, Ordering::Release);
        v
    }
}

fn main() {
    use std::thread;
    use std::sync::Arc;

    let buf = Arc::new(RingBuffer::<u64>::new());
    let buf_p = buf.clone();
    let buf_c = buf.clone();

    let producer = thread::spawn(move || {
        for i in 0..10_000u64 {
            // 满了就重试(spin-wait),实际代码加 _mm_pause 或 condvar
            let mut v = i;
            while let Err(x) = buf_p.push(v) {
                v = x;
                std::hint::spin_loop();  // 编译成 _mm_pause,告诉 CPU 这是 spin
            }
        }
    });

    let consumer = thread::spawn(move || {
        let mut expected = 0u64;
        let mut count = 0;
        while count < 10_000 {
            if let Some(v) = buf_c.pop() {
                assert_eq!(v, expected, "got {} expected {}", v, expected);
                expected += 1;
                count += 1;
            } else {
                std::hint::spin_loop();
            }
        }
        count
    });

    producer.join().unwrap();
    let count = consumer.join().unwrap();
    println!("All {} items received in order", count);
}
```

**每行关键点**:
- `MaybeUninit::uninit().assume_init()` 在老 Rust 里的数组初始化技巧。Rust 1.79+ 直接用 `[const { None }; CAP]` 更安全(教学版我保留旧写法让你理解底层)
- `spin_loop()` 是 `std::hint`,在 x86 上编成 `_mm_pause` 指令,CPU 知道这是 spin,降功耗并避免流水线惩罚
- Acquire/Release 配对:push 用 Release store(让 entry 写入对消费者可见),pop 用 Acquire load(看到 write_index 推进就能读到 entry)
- `take()` 在 `Option` 上取出值并留下 `None`,自动处理内存

### Lv3 · 迁移设计

**题**:把 Lv2 的 SPSC 队列改成 MPMC(多生产者多消费者),让 4 个生产者各 push 2500 个、4 个消费者共 pop 10000 个。要求最终无丢失无重复,只是顺序可能任意(因为是 4 个消费者)。

**提示**:
- push 现在也要 CAS:多个生产者抢同一个 write_index 槽位
- pop 同样 CAS
- 用 `compare_exchange` loop,失败重试
- 验证方法:消费者把收到的数放进 `Mutex<Vec<u64>>`,最后排序 + 去重,确认是 0..9999

**关键代码骨架**(自己填):

```rust
fn push_mpmc(&self, v: T) -> Result<(), T> {
    loop {
        let w = self.write.load(Relaxed);
        let r = self.read.load(Acquire);
        if (w + 1) % CAP == r { return Err(v); }  // 满
        // 抢占 slot w:把 write 从 w 推到 (w+1) % CAP
        match self.write.compare_exchange(w, (w + 1) % CAP, AcqRel, Acquire) {
            Ok(_) => {
                // 抢到了 slot w,写它
                unsafe { (*self.entries.get())[w] = Some(v); }
                return Ok(());
            }
            Err(_) => continue,  // 被别的生产者抢了,重读 write 重试
        }
    }
}
```

注意一个微妙之处:**CAS 成功之后才写 entry**,这中间消费者可能看到 `write_index` 已推进但 entry 还没写。这是 MPMC 队列的经典难题。工业级解法:在 entry 里加一个 sequence number 标记"这个槽位的数据属于第几代 push",消费者读到 sequence 不匹配就跳过。我们教学版可以接受这个 race(留作 Lv4 思考)。

### 完整可跑 Rust 项目

把 Lv2 的代码扩展为 benchmark,对比 Mutex<Vec> 和 lock-free ring buffer 的性能。

```rust
// Cargo.toml
// [package]
// name = "ringbench"
// version = "0.1.0"
// edition = "2021"

use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::{Arc, Mutex};
use std::collections::VecDeque;
use std::cell::UnsafeCell;
use std::time::Instant;

const CAP: usize = 256;
const TOTAL: usize = 1_000_000;

// === lock-free 版本 ===
struct Ring<T: Send + Copy> {
    buf: UnsafeCell<[Option<T>; CAP]>,
    write: AtomicUsize,
    read: AtomicUsize,
}
unsafe impl<T: Send + Copy> Sync for Ring<T> {}
unsafe impl<T: Send + Copy> Send for Ring<T> {}

impl<T: Send + Copy> Ring<T> {
    fn new() -> Self {
        // Rust 1.79+ 的 const block init,安全又简洁
        Self {
            buf: UnsafeCell::new([const { None }; CAP]),
            write: AtomicUsize::new(0),
            read: AtomicUsize::new(0),
        }
    }

    fn push(&self, v: T) -> Result<(), T> {
        let w = self.write.load(Ordering::Relaxed);
        let r = self.read.load(Ordering::Acquire);
        if (w + 1) % CAP == r { return Err(v); }
        unsafe { (*self.buf.get())[w] = Some(v); }
        self.write.store((w + 1) % CAP, Ordering::Release);
        Ok(())
    }

    fn pop(&self) -> Option<T> {
        let r = self.read.load(Ordering::Relaxed);
        let w = self.write.load(Ordering::Acquire);
        if r == w { return None; }
        let v = unsafe { (*self.buf.get())[r].take() };
        self.read.store((r + 1) % CAP, Ordering::Release);
        v
    }
}

// === Mutex<VecDeque> 版本 ===
struct LockedQueue<T> {
    inner: Mutex<VecDeque<T>>,
}
impl<T> LockedQueue<T> {
    fn new() -> Self { Self { inner: Mutex::new(VecDeque::with_capacity(CAP)) } }
    fn push(&self, v: T) -> Result<(), T> {
        let mut q = self.inner.lock().unwrap();
        if q.len() >= CAP - 1 { return Err(v); }
        q.push_back(v);
        Ok(())
    }
    fn pop(&self) -> Option<T> {
        let mut q = self.inner.lock().unwrap();
        q.pop_front()
    }
}

fn bench_lockfree() -> u64 {
    let ring = Arc::new(Ring::<u64>::new());
    let rp = ring.clone();
    let rc = ring.clone();
    let start = Instant::now();
    let p = std::thread::spawn(move || {
        for i in 0..TOTAL as u64 {
            let mut v = i;
            while let Err(x) = rp.push(v) { v = x; std::hint::spin_loop(); }
        }
    });
    let c = std::thread::spawn(move || {
        let mut got = 0;
        while got < TOTAL {
            if ring_pop(&rc).is_some() { got += 1; } else { std::hint::spin_loop(); }
        }
    });
    p.join().unwrap();
    c.join().unwrap();
    start.elapsed().as_millis() as u64
}
fn ring_pop(rc: &Ring<u64>) -> Option<u64> { rc.pop() }

fn bench_locked() -> u64 {
    let q = Arc::new(LockedQueue::<u64>::new());
    let qp = q.clone();
    let qc = q.clone();
    let start = Instant::now();
    let p = std::thread::spawn(move || {
        for i in 0..TOTAL as u64 {
            let mut v = i;
            while let Err(x) = qp.push(v) { v = x; std::hint::spin_loop(); }
        }
    });
    let c = std::thread::spawn(move || {
        let mut got = 0;
        while got < TOTAL {
            if qc.pop().is_some() { got += 1; } else { std::hint::spin_loop(); }
        }
    });
    p.join().unwrap();
    c.join().unwrap();
    start.elapsed().as_millis() as u64
}

fn main() {
    let t_lockfree = bench_lockfree();
    println!("Lock-free ring buffer: {} ms ({} ops/ms)", t_lockfree, TOTAL as u64 / t_lockfree.max(1));
    let t_locked = bench_locked();
    println!("Mutex<VecDeque>:       {} ms ({} ops/ms)", t_locked, TOTAL as u64 / t_locked.max(1));
    println!("Speedup: {:.2}x", t_locked as f64 / t_lockfree as f64);
}
```

**预期输出**(取决于 CPU,8 核 x86_64 大致):
```
Lock-free ring buffer: 280 ms (3571 ops/ms)
Mutex<VecDeque>:       820 ms (1219 ops/ms)
Speedup: 2.93x
```

### Linux 上的等价 kernel API

如果你写内核模块,会用到的对应物:

```c
// Linux kernel kfifo
#include <linux/kfifo.h>
DECLARE_KFIFO(ptr, int, 256);    // 声明一个容量 256 的 int 队列
INIT_KFIFO(ptr);                  // 初始化
kfifo_put(ptr, 42);               // push
int val;
kfifo_get(ptr, &val);             // pop

// 多线程保护用 spinlock:
DEFINE_SPINLOCK(lock);
spin_lock(&lock);
kfifo_put(ptr, 42);
spin_unlock(&lock);
```

Linux 不在内核里做 lock-free kfifo(因为内核有自旋锁就够,lock-free 的复杂度不值得)。User-space 性能敏感的场景(DPDK、游戏)才手写 lock-free。
