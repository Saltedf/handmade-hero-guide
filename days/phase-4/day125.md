# Day 125 · 抽象出 work queue

> 你学了 atomic、学了 semaphore、学了 memory barrier。今天 Casey 把这些组合成一个真实有用的工具:**work queue**(任务队列)。主线程把"tile 渲染"task 放进队列,worker 线程从队列取 task 执行。这是 Day 121 tile 渲染多线程化的基础设施。

## 0 · 为什么要有这一天

回到 Day 121:你把屏幕切成 64×64 tile,逐个渲染。但所有 tile 在主线程串行跑。CPU 有 8 个核,只用 1 个。

要并行,你需要一个**分发机制**:主线程把 tile 放进队列,8 个 worker 线程并发取。

听起来简单?但里面有大量细节:

- 多个 worker 同时取任务,怎么避免取到同一个?
- 主线程怎么知道所有任务完成?
- 任务里需要的数据(sprite 列表、framebuffer 引用)怎么传?
- worker 线程怎么"休眠"避免空转烧 CPU?
- 怎么让架构足够通用,不只是渲染 tile,还能做物理、AI 等?

今天 Casey 把这些抽象成一个通用的 `work_queue` 接口。Day 126 实现具体细节(ring buffer),Day 127+ 应用到渲染。

心理锚点:读完这一天,你能:

- 设计 work queue 的 API

## 2 · 心智模型

### 2.1 类比:外卖配送中心

外卖店有 1 个调度员(主线程)+ N 个骑手(worker)。调度员把订单一张张贴到公告板(queue)。骑手从公告板取一张订单去送货。

**关键问题**:

1. **多个骑手同时取**:不能两个骑手拿到同一张订单(atomic + CAS)
2. **公告板空了**:骑手要睡觉,等新订单(sema wait)
3. **新订单来**:调度员要叫醒一个睡着的骑手(sema post)
4. **订单全送完**:调度员要等所有骑手回来(join / 等待完成标志)
5. **公告板满了**:需要 ring buffer,或者动态扩展

work queue 就是这个外卖配送中心的代码化。

### 2.2 主线程 vs worker 线程

- **主线程(main)**:驱动游戏循环。每帧把任务塞进 queue,然后等所有任务完成,渲染,下一帧
- **worker 线程**:启动后进入"取任务 → 执行"循环。空闲时休眠(避免烧 CPU)

worker 线程数量 = CPU 核数 - 1(留 1 个核给主线程)。

### 2.3 task 是什么

最简单的 task 是一个函数指针 + 一个 void* 参数:

```rust
type Callback = unsafe fn(*mut std::ffi::c_void);

struct Task {
    callback: Callback,
    data: *mut std::ffi::c_void,
}
```

worker 取到 task,调用 `callback(data)`。

**Rust 风格**:用 trait object 或闭包:

```rust
type Task = Box<dyn FnOnce() + Send>;

struct Task {
    work: Box<dyn FnOnce() + Send>,
}
```

`FnOnce + Send` 是"能跨线程调用一次"的闭包。Casey 用 C 风格函数指针(简单),我们 Rust 用闭包更自然。

### 2.4 work queue 的 API

```rust
pub struct WorkQueue {
    // 内部细节(Day 126 实现)
}

impl WorkQueue {
    pub fn new(worker_count: usize) -> Self { ... }

    /// 主线程:把任务塞进队列
    pub fn add(&self, task: Box<dyn FnOnce() + Send>) { ... }

    /// 主线程:等待所有任务完成
    pub fn complete_all(&self) { ... }
}
```

主线程用法:

```rust
let queue = WorkQueue::new(7);  // 8 核 CPU,7 worker + 1 main

for tile in tiles {
    let tile = tile.clone();
    queue.add(Box::new(move || {
        render_tile(tile);
    }));
}
queue.complete_all();  // 等所有 tile 完成
```

### 2.5 worker 主循环

```rust
fn worker_loop(queue: Arc<WorkQueue>) {
    loop {
        if let Some(task) = queue.try_take() {
            task();  // 执行 task
            queue.task_done();  // 通知主线程"又完成一个"
        } else {
            queue.wait_for_task();  // sema wait
        }
        if queue.is_shutting_down() {
            break;
        }
    }
}
```

关键点:

- **try_take**:非阻塞尝试取任务,空了就 wait
- **wait_for_task**:semaphore wait,worker 休眠
- **task_done**:atomic decrement 完成计数

### 2.6 主线程等待

```rust
impl WorkQueue {
    pub fn complete_all(&self) {
        // 等所有任务被 worker 完成
        while self.outstanding.load(Ordering::Acquire) > 0 {
            std::hint::spin_loop();  // 自旋
            // 或者:做点别的有用的事
        }
    }
}
```

主线程在等的时候可以"帮忙"做 task(work-stealing 思想),或者纯自旋(简单)。

### 2.7 关闭 worker

程序退出时,要告诉 worker 停止:

```rust
impl WorkQueue {
    pub fn shutdown(&self) {
        self.shutting_down.store(true, Ordering::Release);
        self.sem.post();  // 唤醒所有 worker
        for handle in &self.worker_handles {
            handle.join().unwrap();
        }
    }
}
```

注意:Rust 的 `Drop` 习惯:

```rust
impl Drop for WorkQueue {
    fn drop(&mut self) {
        self.shutdown();
    }
}
```

### 2.8 几个常见变体

#### 1. 阻塞 add(queue 满了等)

```rust
pub fn add_blocking(&self, task: Task) {
    while !self.try_add(task) {
        std::hint::spin_loop();
    }
}
```

适合:有限内存,不能让 queue 无限大。

#### 2. 非阻塞 add(返回 Result)

```rust
pub fn try_add(&self, task: Task) -> Result<(), Task> { ... }
```

适合:queue 满时丢弃或重试。

#### 3. work-stealing

每个 worker 有自己的本地 queue,空了去偷别人的。性能更好但实现复杂(rayon 用这个)。

#### 4. priority queue

不同优先级的任务,高优先级先做。

Casey 用最简单的:单队列,固定容量,主线程阻塞等。Day 126 实现。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:主线程在 `complete_all()` 时自旋(spin_loop)等。为什么不用 mutex + condvar 等?

**参考解答**:

1. **延迟**:自旋 ~10ns 唤醒,mutex/condvar ~1µs。游戏帧时间敏感,自旋更优
2. **简单**:自旋不用锁,无死锁风险
3. **代价**:自旋烧 CPU,但如果"等的时间短"(几 ms),烧 CPU 比睡眠划算
4. **混合**:实际系统用"自旋一段时间,然后睡眠"(parking_lot 这么做)

### Lv2 · 动手实践

**题**:用 std::thread + Arc<Mutex<Vec<Task>>> 写一个简单 work queue(性能不要求)。8 worker,主线程塞 1000 个 task(每个 sleep 1ms),测试总耗时。

完成标准:

- 单线程跑 ~1000ms
- 多线程跑 ~125ms(8x 加速)

参考实现:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

type Task = Box<dyn FnOnce() + Send + 'static>;

struct SimpleQueue {
    tasks: Arc<Mutex<Vec<Task>>>,
    outstanding: Arc<std::sync::atomic::AtomicUsize>,
}

impl SimpleQueue {
    fn new(worker_count: usize) -> Self {
        let tasks = Arc::new(Mutex::new(Vec::new()));
        let outstanding = Arc::new(std::sync::atomic::AtomicUsize::new(0));
        for _ in 0..worker_count {
            let tasks = tasks.clone();
            let outstanding = outstanding.clone();
            thread::spawn(move || loop {
                let task_opt = {
                    let mut tasks = tasks.lock().unwrap();
                    tasks.pop()
                };
                if let Some(task) = task_opt {
                    task();
                    outstanding.fetch_sub(1, std::sync::atomic::Ordering::Release);
                } else {
                    std::thread::sleep(std::time::Duration::from_micros(100));
                }
            });
        }
        Self { tasks, outstanding }
    }

    fn add(&self, task: Task) {
        self.outstanding.fetch_add(1, std::sync::atomic::Ordering::Release);
        self.tasks.lock().unwrap().push(task);
    }

    fn complete_all(&self) {
        while self.outstanding.load(std::sync::atomic::Ordering::Acquire) > 0 {
            std::hint::spin_loop();
        }
    }
}
```

注意:这个简单版用 Vec.pop(),worker 空了就 sleep poll(忙等待)。Day 126 用 sema 改进。

## 8 · Rust / Arch 落地代码

### Rust:work queue 骨架(Day 126 填充细节)

```rust
use std::sync::Arc;
use std::sync::atomic::{AtomicUsize, AtomicBool, Ordering};
use std::sync::{Condvar, Mutex};
use std::thread::{self, JoinHandle};

type Task = Box<dyn FnOnce() + Send + 'static>;

pub struct WorkQueue {
    tasks: Mutex<Vec<Task>>,           // 简化:用 Vec,Day 126 改 ring buffer
    task_count: AtomicUsize,           // 待完成任务数
    sem_count: Mutex<usize>,           // 待处理任务数(用于 condvar)
    sem_cond: Condvar,
    shutting_down: AtomicBool,
    workers: Vec<JoinHandle<()>>,
}

impl WorkQueue {
    pub fn new(worker_count: usize) -> Arc<Self> {
        let q = Arc::new(Self {
            tasks: Mutex::new(Vec::new()),
            task_count: AtomicUsize::new(0),
            sem_count: Mutex::new(0),
            sem_cond: Condvar::new(),
            shutting_down: AtomicBool::new(false),
            workers: Vec::new(),
        });

        // 启动 workers
        let q_ref = q.clone();
        let mut workers = Vec::new();
        for _ in 0..worker_count {
            let q_clone = q.clone();
            workers.push(thread::spawn(move || {
                q_clone.worker_loop();
            }));
        }
        // 这里有个借用问题,演示用,q.workers = workers;
        // 实际需要 unsafe 或 OnceLock
        let q = q_ref;
        q
    }

    fn worker_loop(&self) {
        loop {
            // 1. sema wait
            {
                let mut count = self.sem_count.lock().unwrap();
                while *count == 0 && !self.shutting_down.load(Ordering::Acquire) {
                    count = self.sem_cond.wait(count).unwrap();
                }
                if self.shutting_down.load(Ordering::Acquire) && *count == 0 {
                    break;
                }
                *count -= 1;
            }

            // 2. 取 task
            let task = {
                let mut tasks = self.tasks.lock().unwrap();
                tasks.pop()
            };

            // 3. 执行
            if let Some(t) = task {
                t();
                self.task_count.fetch_sub(1, Ordering::Release);
            }
        }
    }

    pub fn add(&self, task: Task) {
        self.task_count.fetch_add(1, Ordering::Release);
        self.tasks.lock().unwrap().push(task);
        // sema post
        let mut count = self.sem_count.lock().unwrap();
        *count += 1;
        self.sem_cond.notify_one();
    }

    pub fn complete_all(&self) {
        while self.task_count.load(Ordering::Acquire) > 0 {
            // 主线程也可以帮忙做 task
            let task = self.tasks.lock().unwrap().pop();
            if let Some(t) = task {
                t();
                self.task_count.fetch_sub(1, Ordering::Release);
            } else {
                std::hint::spin_loop();
            }
        }
    }
}

impl Drop for WorkQueue {
    fn drop(&mut self) {
        self.shutting_down.store(true, Ordering::Release);
        // 唤醒所有 worker
        {
            let mut count = self.sem_count.lock().unwrap();
            *count = 10000;  // 大数确保所有 worker 退出
        }
        self.sem_cond.notify_all();
        // worker_handles join... (略,实际需要 unsafe / OnceLock)
    }
}

fn main() {
    let q = WorkQueue::new(7);

    let counter = Arc::new(AtomicUsize::new(0));
    for _ in 0..1000 {
        let c = counter.clone();
        q.add(Box::new(move || {
            c.fetch_add(1, Ordering::Relaxed);
            std::thread::sleep(std::time::Duration::from_millis(1));
        }));
    }
    q.complete_all();
    println!("Done: {}", counter.load(Ordering::Relaxed));
}
```

注意:这个 demo 有借用 / lifetime 简化,实际能编译运行的版本需要更多 Arc / 内部可变性。Day 126 完整实现。

## 10 · 深度推导:work queue 的演化路径

今天 Casey 把"task push/pop + worker loop"抽象成 work queue API。但 work queue 不是一种设计,是 5 种演化的产物。这一节走通这 5 种,你才理解 Day 126 的 ring buffer 为什么这样设计。

### 10.1 V1:朴素 Vec + Mutex

```rust
struct WorkQueueV1 {
    tasks: Mutex<Vec<Task>>,
}

impl WorkQueueV1 {
    fn push(&self, t: Task) {
        self.tasks.lock().unwrap().push(t);
    }
    fn pop(&self) -> Option<Task> {
        self.tasks.lock().unwrap().pop()
    }
}
```

这是最简单的 work queue。问题:

- **每次 push/pop 都 lock**——8 worker × 60 fps × 510 tile = 244K lock/frame × 60 = 14.6M lock/s。mutex ~50ns/op,总 730 ms/s 浪费。
- **Cache bouncing**:Mutex 内部 atomic,8 核争抢,cache line bouncing 严重。

V1 只够 demo,生产不行。

### 10.2 V2:Mutex + Condvar(worker 不忙等)

V1 的 worker `pop()` 返回 None 后立刻 retry,100% CPU 空转。V2 加 condvar:

```rust
struct WorkQueueV2 {
    tasks: Mutex<Vec<Task>>,
    cv: Condvar,
}

fn push(&self, t: Task) {
    let mut tasks = self.tasks.lock().unwrap();
    tasks.push(t);
    self.cv.notify_one();
}

fn pop(&self) -> Option<Task> {
    let mut tasks = self.tasks.lock().unwrap();
    while tasks.is_empty() {
        tasks = self.cv.wait(tasks).unwrap();
    }
    tasks.pop()
}
```

worker 空队列时 sleep,主线程 push 时 notify。CPU 不空转。

问题:

- **notify 浪费**:notify_one 唤醒一个 worker,但如果有多个 task 在 queue,只有一个 worker 醒。其他 task 要等下次 notify。
- **Lock 还在**:每次 push/pop 仍 lock,只是少了忙等。
- **Thief 不友好**:worker 想从别人那里偷任务时,要 lock 别人的 mutex。

V2 是 80% 项目的选择。简单可靠。

### 10.3 V3:Semaphore + Mutex(分离信号和锁)

```rust
struct WorkQueueV3 {
    tasks: Mutex<Vec<Task>>,
    sem: Semaphore,
}

fn push(&self, t: Task) {
    self.tasks.lock().unwrap().push(t);
    self.sem.post();  // 信号量 +1
}

fn pop(&self) -> Option<Task> {
    self.sem.wait();  // 等信号量 > 0
    self.tasks.lock().unwrap().pop()  // 此时必有 task
}
```

sem 和 mutex 分离。好处:

- sem.wait 在 task 不可用时立刻 block,无 lock-unlock 浪费
- sem.post 不需要 lock,只有 fetch_add

工业实现常用这种。Casey 的 Day 125 接近 V3,Day 126 进一步用 futex 加速 sem。

### 10.4 V4:Lock-free ring buffer(单生产者)

```rust
struct WorkQueueV4 {
    buffer: Box<[MaybeUninit<Task>; SIZE]>,
    head: AtomicUsize,  // consumer 写
    tail: AtomicUsize,  // producer 写
}
```

SPSC 场景(一个 producer,一个 consumer)能完全 lock-free。但 tile 渲染是 **MPMC**(主线程 push,8 worker pop),SPSC 不行。

V4 用于"音频流"(单线程产生样本,单线程消费)。Day 142+ 用。

### 10.5 V5:Work stealing(每 worker 自己 queue)

每个 worker 有自己的 deque:

```rust
struct Worker {
    local_queue: Deque<Task>,  // 本地 queue
    peers: Vec<Arc<Worker>>,
}

fn worker_loop(&self) {
    loop {
        // 1. 优先本地 queue(LIFO,last in first out,cache 热)
        if let Some(t) = self.local_queue.pop_back() {
            t.run();
        }
        // 2. 本地空了,从 peers 偷(FIFO,oldest task)
        else {
            for peer in &self.peers {
                if let Some(t) = peer.local_queue.pop_front() {
                    t.run();
                    break;
                }
            }
        }
    }
}
```

收益:

- **本地 queue 无 contention**(单线程访问)
- **偷任务罕见**(只有空闲 worker 才偷)
- **Cache 友好**(本地 task cache 热)

代价:

- **复杂**(双层 queue + stealing 协议)
- **Steal 时仍需 lock 或 atomic**(用 Chase-Lev deque 算法)

V5 是 rayon / crossbeam-deque / bevy_tasks 的实现方式。Casey 的 Day 125 是 V3,但他在视频里讨论了 V5 的可能。

### 10.6 决策:V1 / V2 / V3 / V4 / V5 选哪个?

| 版本 | 复杂度 | 性能 | 适用场景 |
|---|---|---|---|
| V1 | 简单 | 慢 | demo / prototype |
| V2 | 简单 | 中等 | 大部分项目 |
| V3 | 中等 | 好 | 游戏引擎生产 |
| V4 | 中等 | 极快(单线程) | SPSC 场景(音频) |
| V5 | 复杂 | 极快(MPMC) | rayon / 大型引擎 |

Casey 在 Day 125 用 V3,Day 126 演化到 V4 风格的 ring buffer(用 sem 实现 MPMC)。学习顺序:V1 → V3 → V5 是 industrial career path。

## 11 · 一个完整可跑的 work queue(简化版)

把 V3 思路实现成最小可跑版本:

```rust
use std::sync::{Arc, Mutex, Condvar};
use std::sync::atomic::{AtomicBool, AtomicUsize, Ordering};
use std::thread;

type Task = Box<dyn FnOnce() + Send + 'static>;

pub struct WorkQueue {
    tasks: Mutex<Vec<Task>>,
    pending: Mutex<usize>,
    cv: Condvar,
    outstanding: AtomicUsize,
    shutdown: AtomicBool,
    workers: Mutex<Vec<thread::JoinHandle<()>>>,
}

impl WorkQueue {
    pub fn new(num_workers: usize) -> Arc<Self> {
        let q = Arc::new(Self {
            tasks: Mutex::new(Vec::new()),
            pending: Mutex::new(0),
            cv: Condvar::new(),
            outstanding: AtomicUsize::new(0),
            shutdown: AtomicBool::new(false),
            workers: Mutex::new(Vec::new()),
        });

        let mut handles = Vec::new();
        for _ in 0..num_workers {
            let q_clone = Arc::clone(&q);
            handles.push(thread::spawn(move || {
                q_clone.worker_loop();
            }));
        }
        *q.workers.lock().unwrap() = handles;
        q
    }

    fn worker_loop(&self) {
        loop {
            // 等 task
            let task = {
                let mut pending = self.pending.lock().unwrap();
                while *pending == 0 && !self.shutdown.load(Ordering::Acquire) {
                    pending = self.cv.wait(pending).unwrap();
                }
                if self.shutdown.load(Ordering::Acquire) && *pending == 0 {
                    return;
                }
                *pending -= 1;
                let mut tasks = self.tasks.lock().unwrap();
                tasks.pop()
            };

            if let Some(t) = task {
                t();
                self.outstanding.fetch_sub(1, Ordering::Release);
            }
        }
    }

    pub fn add(&self, task: Task) {
        self.outstanding.fetch_add(1, Ordering::Release);
        self.tasks.lock().unwrap().push(task);
        let mut pending = self.pending.lock().unwrap();
        *pending += 1;
        self.cv.notify_one();
    }

    pub fn complete_all(&self) {
        while self.outstanding.load(Ordering::Acquire) > 0 {
            // 主线程可以帮忙做 task
            let task = {
                let mut tasks = self.tasks.lock().unwrap();
                let mut pending = self.pending.lock().unwrap();
                if *pending > 0 {
                    *pending -= 1;
                    tasks.pop()
                } else {
                    None
                }
            };
            if let Some(t) = task {
                t();
                self.outstanding.fetch_sub(1, Ordering::Release);
            } else {
                std::hint::spin_loop();
            }
        }
    }
}

impl Drop for WorkQueue {
    fn drop(&mut self) {
        self.shutdown.store(true, Ordering::Release);
        // 唤醒所有 worker 让他们看到 shutdown
        *self.pending.lock().unwrap() = 99999;
        self.cv.notify_all();
        // join workers
        let handles = std::mem::take(&mut *self.workers.lock().unwrap());
        for h in handles {
            h.join().unwrap();
        }
    }
}

fn main() {
    let q = WorkQueue::new(8);
    let counter = Arc::new(AtomicUsize::new(0));

    for i in 0..1000 {
        let c = Arc::clone(&counter);
        q.add(Box::new(move || {
            c.fetch_add(1, Ordering::Relaxed);
            println!("task {} on {:?}", i, thread::current().id());
        }));
    }

    q.complete_all();
    println!("Done: {} (expected 1000)", counter.load(Ordering::Relaxed));
    // Drop 时 worker 全部 join
}
```

跑起来:

```bash
cargo run --release
# 看到 task 0-999 由不同 thread::id() 处理(8 个 worker thread)
# Done: 1000 (expected 1000)
```

这个 work queue 是 Day 125 的核心产出。Day 126 把 Mutex<Vec> 换成 ring buffer,性能再上一个台阶。

## 12 · work queue 的工业级考量

工业代码的 work queue 还要考虑这些:

### 12.1 优先级

不同 task 优先级不同。比如"音频 task"必须 5ms 内完成,"渲染 task"可以慢。

简单实现:多个 queue(高 / 中 / 低),worker 优先 pop 高 queue。

复杂实现:priority queue(bin heap),但 lock-free priority queue 难写。

### 12.2 亲和性(affinity)

某些 task 想"在同一 worker 上连续跑"——cache 热数据(比如某 tile 的物理模拟)。

简单实现:task 带一个 "affinity_id",push 时塞进对应 worker 的本地 queue。

### 12.3 取消

task push 后想 cancel。但 task 可能在 worker 上跑,无法 cancel。

简单实现:task 内部检查 cancel flag,worker 跑到一半发现 cancel 就提前 return。

复杂实现:tracking + async cancel。

### 12.4 监控

监控 work queue 深度,深度过深说明 worker 跟不上,要扩 worker。

```rust
let depth = q.tasks.lock().unwrap().len();
metrics::gauge!("work_queue.depth", depth as f64);
```

工业代码常见 Prometheus / Datadog 上报。

### 12.5 测试

并发测试难写。常见 trick:

- TSan(ThreadSanitizer)跑测试,捕获 data race
- 模型检查器(loom crate)模拟多线程交错
- 长跑压测(72 hours,看是否有偶发 bug)

loom 是 Rust 特有的并发测试工具,Day 165+ 详细讨论。
