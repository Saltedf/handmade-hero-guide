# Day 124 · 内存屏障与信号量

> atomic 只解决"单变量原子性",没解决"多变量之间的顺序"。这就是 memory barrier 的事。今天 Casey 把内存序、屏障、信号量彻底讲透——这是 Phase 4 最难的一集之一,但也是关键。

## 0 · 为什么要有这一天

回到 Day 123 的发布订阅例子:

```rust
data.write(...);
flag.store(true, Ordering::Release);
```

为什么需要 `Release`?因为 CPU / 编译器可能**重排**:

- 编译器看 `data.write` 和 `flag.store` 没依赖,可能交换顺序
- CPU 看两条 store 没依赖,可能让它们以"乱序"出现在内存里

结果:`flag=true` 先生效,`data` 还没写,另一个线程看到 `flag=true` 但读到旧 data。

**Memory barrier**(内存屏障)就是阻止这种重排的指令。`Ordering::Release` 内部插入了屏障。

理解屏障,你能写出**正确的**多线程代码(不只是"看起来对的")。不理解,你写的代码在 x86 上"碰巧能跑",在 ARM 上随机崩。

今天 Casey 还讲了 **semaphore**(信号量)——另一个经典同步原语,后续 day 用到。

心理锚点:读完这一天,你能:

- 解释为什么 x86 是"强内存模型"(TSO),ARM 是"弱内存模型"
- 用 `Ordering::Release/Acquire` 正确实现发布订阅
- 解释 `fence` 指令的作用
- 知道 semaphore 和 mutex 的差别

## 2 · 心智模型

### 2.1 类比:邮局收发室

邮局收发室有个公告板。员工(线程)放信(写数据)和看公告(读数据)。

#### 没有秩序(弱内存模型,ARM)

每个员工放信时,**不一定按顺序**放:他可能先放第 2 封,再放第 1 封。其他员工看公告时,**不一定按顺序看到**。

所以"我先写了 data,再写了 flag=true"这句话**不是承诺**——别人可能先看到 flag=true,后看到 data。

#### 有秩序(TSO,x86)

x86 有"Total Store Order"承诺:**每个 CPU 自己的 store 顺序一致**(自己写的顺序,别人看到的顺序一致)。但 load 可以重排。

所以 x86 上"data 写完,flag 写 true"通常没问题——别人看到 flag=true 时,data 一定写了。但 load 重排还是可能搞事。

#### 有秩序(SeqCst)

最强:全局顺序。所有线程都看到同样的操作顺序。

### 2.2 编译器重排

编译器优化时,**可能交换指令顺序**:

```c
int a = 0, b = 0;

void thread1() {
    a = 1;
    b = 2;
}
```

编译器可能把 `b = 2` 提前到 `a = 1` 前(因为 `b = 2` 不依赖 `a`):

```c
void thread1_optimized() {
    b = 2;
    a = 1;
}
```

单线程看,效果一样(没人看 a 和 b 的中间状态)。但多线程看,可能问题:

```c
void thread2() {
    while (b != 2) ;
    assert(a == 1);  // 可能失败!
}
```

thread2 等 b 变 2 后,以为 a 一定是 1。但 thread1 可能先写 b 再写 a,thread2 看到 b=2 时 a 还是 0。

**阻止编译器重排**:

- C:用 `asm volatile("" ::: "memory")`(GCC)或 `_ReadBarrier` / `_WriteBarrier`(MSVC)
- Rust:`AtomicX::store(_, Ordering::SeqCst)` 隐式阻止;或 `compiler_fence(Ordering::Release)`

### 2.3 CPU 重排

即使编译器没重排,CPU 也可能重排。

#### 乱序执行(Out-of-Order Execution)

现代 CPU 是"超标量乱序"的:取多条指令,看哪条能立即执行(没有依赖),先执行。如果两条 store 没依赖,CPU 可能让它们以"非程序顺序"出现在内存里。

#### Store Buffer

每个 CPU 核心有个 store buffer(写缓冲)。store 先进 buffer,稍后才"提交"到 cache。多个 store 在 buffer 里可能被合并或重排。

#### Load 也可以重排

CPU 读内存时,可能从 store buffer 读(自己刚写的还没提交的值),或从 cache 读。如果 cache 有更新,可能读到的顺序和程序顺序不一致。

### 2.4 Memory Barrier:阻止 CPU 重排

`mfence`(memory fence)是 x86 的内存屏障指令。它告诉 CPU:

- 在 mfence 之前的所有 load/store,必须先于 mfence 之后的所有 load/store 完成对其他 CPU 的可见

Rust 的 `Ordering::SeqCst` 会插入 `mfence`(在某些操作周围)。`Ordering::Release/Acquire` 插入更轻的屏障(x86 上几乎免费,因为 TSO 已经保证)。

#### Rust 的 `fence`

```rust
use std::sync::atomic::fence;
use std::sync::atomic::Ordering;

fence(Ordering::Release);  // 不操作具体变量,只插屏障
```

`fence` 和 atomic 操作上的 Ordering 区别:fence 是"独立的"屏障,不绑定到某个变量。用于"我对非 atomic 变量的写,要让其他线程看到"的场景(谨慎使用!)。

### 2.5 x86 内存模型:TSO

x86 是 **TSO**(Total Store Order):

- **store-store 不重排**:你的两条 store,在别的 CPU 看来顺序一致
- **load-load 不重排**:你的两条 load 顺序一致
- **load-store 不重排**:load 后的 store 不重排
- **store-load 可重排**:store 后的 load 可能被提前到 store 之前

所以 x86 上:

- `Ordering::Relaxed` load/store 几乎和普通 load/store 一样
- `Ordering::Release/Acquire` 在 x86 上几乎免费(TSO 已保证)
- `Ordering::SeqCst` 才需要真正的 `mfence`(因为 store-load 要避免重排)

### 2.6 ARM 内存模型:Weak

ARM 是**弱内存模型**:

- 几乎所有重排都允许(store-store、load-load、load-store、store-load)
- 程序员必须显式插 `dmb`(data memory barrier)指令

所以同一段 Rust 多线程代码:

- x86:可能跑得没问题(TSO 已经保证了大部分顺序)
- ARM:可能随机失败

**这就是为什么 Rust 的 atomic + Ordering 重要**:它跨架构保证语义,编译器在每个架构上插对应的屏障。

### 2.7 经典例子:双重检查锁定(DCLP)

```rust
// 错误!可能 data race
static mut INSTANCE: Option<Box<Data>> = None;

fn get() -> &'static Data {
    if unsafe { INSTANCE.is_none() } {  // (1) check
        let _lock = LOCK.lock();
        if unsafe { INSTANCE.is_none() } {  // (2) double check
            unsafe { INSTANCE = Some(Box::new(Data::new())); }  // (3) init
        }
    }
    unsafe { INSTANCE.as_ref().unwrap() }
}
```

问题:

- 步骤 (3) "构造 Data + 写 INSTANCE" 不是原子的,可能被重排成"先写 INSTANCE(指向未初始化内存),再构造 Data"
- 步骤 (1) 看 INSTANCE 是 Some,但 Data 还没构造好

正确做法用 atomic + Release/Acquire:

```rust
use std::sync::atomic::{AtomicPtr, Ordering};

static INSTANCE: AtomicPtr<Data> = AtomicPtr::new(std::ptr::null_mut());

fn get() -> &'static Data {
    let p = INSTANCE.load(Ordering::Acquire);
    if !p.is_null() {
        return unsafe { &*p };
    }
    let _lock = LOCK.lock();
    let p = INSTANCE.load(Ordering::Relaxed);  // 双重检查
    if !p.is_null() {
        return unsafe { &*p };
    }
    let new_data = Box::into_raw(Box::new(Data::new()));
    INSTANCE.store(new_data, Ordering::Release);
    unsafe { &*new_data }
}
```

`Release.store` 保证:Data::new() 的初始化在所有看到 store 的线程里都生效。

Rust 标准库的 `Once` / `OnceLock` 已经封装好了这种模式,日常不用自己写。

### 2.8 Semaphore(信号量)

Semaphore 是经典同步原语。它有个"计数":

- `wait()`(P 操作):计数 -1。如果计数 = 0,阻塞,直到别人 post
- `post()`(V 操作):计数 +1。唤醒一个等待者

#### Mutex vs Semaphore

- **Mutex**:计数始终是 0 或 1。lock = wait,unlock = post
- **Semaphore**:计数可以是任意非负数。可以一次让 N 个线程进入

#### Semaphore 的用途

1. **资源池**:N 个数据库连接,semaphore 计数 = N,每个线程 wait 取连接,用完 post 还
2. **生产者消费者**:queue 满了 producer 等,空了 consumer 等
3. **限流**:semaphore 计数 = 100,最多 100 并发请求

#### Rust 里的 Semaphore

Rust 标准库没直接提供 Semaphore,但用 Mutex + Condvar 实现:

```rust
use std::sync::{Mutex, Condvar};

struct Semaphore {
    count: Mutex<i32>,
    cond: Condvar,
}

impl Semaphore {
    fn new(n: i32) -> Self {
        Self { count: Mutex::new(n), cond: Condvar::new() }
    }

    fn wait(&self) {
        let mut count = self.count.lock().unwrap();
        while *count <= 0 {
            count = self.cond.wait(count).unwrap();
        }
        *count -= 1;
    }

    fn post(&self) {
        let mut count = self.count.lock().unwrap();
        *count += 1;
        self.cond.notify_one();
    }
}
```

或者用 `parking_lot` 提供的更高效实现。

### 2.9 异步 vs 同步原语

注意:**这些原语是同步的**——线程阻塞,等到条件满足。它们和 `async / await` 不兼容(async 不能阻塞,要 await)。

Rust 的 async 生态有专门的 async 同步原语:

- `tokio::sync::Mutex`
- `tokio::sync::Semaphore`
- `tokio::sync::mpsc::channel`

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:下面代码在 x86 上跑"看起来对",在 ARM 上随机失败。为什么?怎么修?

```rust
static DATA: AtomicI32 = AtomicI32::new(0);
static READY: AtomicBool = AtomicBool::new(false);

// thread 1
DATA.store(42, Ordering::Relaxed);
READY.store(true, Ordering::Relaxed);

// thread 2
while !READY.load(Ordering::Relaxed) {}
println!("{}", DATA.load(Ordering::Relaxed));  // ARM 可能读到 0!
```

**参考解答**:Relaxed 不保证顺序。即使 thread 1 先 store DATA 再 store READY,thread 2 看到 READY=true 时,DATA 可能还没刷到 cache(ARM 弱内存模型允许这种重排)。

修法:用 Release / Acquire:

```rust
// thread 1
DATA.store(42, Ordering::Relaxed);
READY.store(true, Ordering::Release);  // Release:DATA 的写在所有看到 READY=true 的线程里都生效

// thread 2
while !READY.load(Ordering::Acquire) {}
println!("{}", DATA.load(Ordering::Relaxed));  // 一定 42
```

## 8 · Rust / Arch 落地代码

### Rust:完整 fence 用法

```rust
use std::sync::atomic::{AtomicI32, AtomicBool, Ordering, fence};
use std::thread;

fn main() {
    let data = AtomicI32::new(0);
    let ready = AtomicBool::new(false);

    let t = thread::spawn(|| {
        // thread 1:用 fence(不绑定到具体 atomic)
        // 注意:这种用法 unsafe,因为 data 是 atomic 但写是非 atomic 模式
        // 真实代码请用 atomic store + Release
        // 这里只是演示 fence 的概念
        unsafe {
            // 假装我们用非 atomic 方式写(实际不会这么写)
            // ...
        }
        fence(Ordering::Release);
        ready.store(true, Ordering::Relaxed);
    });

    // 实际安全的写法:用 atomic + Release/Acquire
    let data2 = AtomicI32::new(0);
    let ready2 = AtomicBool::new(false);

    let t2 = thread::spawn({
        let data2 = &data2;
        let ready2 = &ready2;
        move || {
            data2.store(42, Ordering::Relaxed);
            ready2.store(true, Ordering::Release);
        }
    });

    while !ready2.load(Ordering::Acquire) {
        std::hint::spin_loop();
    }
    println!("Data: {}", data2.load(Ordering::Relaxed));

    t.join().unwrap();
    t2.join().unwrap();
}
```

### Rust:Semaphore 完整实现

```rust
use std::sync::{Mutex, Condvar};

pub struct Semaphore {
    count: Mutex<i32>,
    cond: Condvar,
}

impl Semaphore {
    pub fn new(n: i32) -> Self {
        Self { count: Mutex::new(n), cond: Condvar::new() }
    }

    pub fn wait(&self) {
        let mut count = self.count.lock().unwrap();
        while *count <= 0 {
            count = self.cond.wait(count).unwrap();
        }
        *count -= 1;
    }

    pub fn post(&self) {
        let mut count = self.count.lock().unwrap();
        *count += 1;
        self.cond.notify_one();
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::sync::Arc;
    use std::thread;

    #[test]
    fn sem_limits_concurrency() {
        let sem = Arc::new(Semaphore::new(2));
        let active = Arc::new(Mutex::new(0));
        let max_active = Arc::new(Mutex::new(0));

        let handles: Vec<_> = (0..10).map(|_| {
            let sem = sem.clone();
            let active = active.clone();
            let max_active = max_active.clone();
            thread::spawn(move || {
                sem.wait();
                {
                    let mut a = active.lock().unwrap();
                    *a += 1;
                    let mut m = max_active.lock().unwrap();
                    if *a > *m { *m = *a; }
                }
                std::thread::sleep(std::time::Duration::from_millis(10));
                {
                    let mut a = active.lock().unwrap();
                    *a -= 1;
                }
                sem.post();
            })
        }).collect();

        for h in handles { h.join().unwrap(); }
        assert!(*max_active.lock().unwrap() <= 2);
    }
}
```

## 10 · 深度推导:从 CPU cache 到 memory barrier

今天讲 memory barrier。但你如果不理解 CPU cache 协议(MESI),barrier 看起来就是"魔法指令"。这一节把 cache 协议讲清,你才明白 barrier 到底做了什么。

### 10.1 MESI 协议:CPU cache 怎么协同

每个 CPU core 有自己的 L1/L2 cache。多个 core 缓存同一内存地址时,需要协议保证一致性。x86 用 MESI(Modified / Exclusive / Shared / Invalid)协议:

- **M(Modified)**:这个 core 独占 + 已修改(主存的值过时)
- **E(Exclusive)**:这个 core 独占 + 未修改(和主存一致)
- **S(Shared)**:多个 core 共享,都未修改
- **I(Invalid)**:这个 cache line 失效

状态机:

```
core A 读 X:cache miss,从主存 fetch,I → E(独占)
core B 读 X:发 inquire,A 的 E → S,新 core B I → S
core A 写 X:发 invalidate,所有 S → I,A 的 S → M
core B 读 X:cache miss,从 A 的 cache fetch(因为 M),A 的 M → S,B 的 I → S
```

MESI 让 cache 协同正确,但有个**致命问题**:**写操作延迟**。core A 写 X 时,要发 invalidate message 给所有 B, C, D, 等他们 ack。每个 ack 几十 ns。如果 A 等 ack,ALU 闲置。

### 10.2 Store buffer:隐藏 invalidate 延迟

CPU 加了 store buffer:写操作先写 store buffer,立刻继续执行。Store buffer 异步发 invalidate,等 ack 后再 commit 到 cache。

```
core A 写 X = 1:
1. 写 store buffer(立即返回)
2. 继续执行下一条指令
3. (异步)发 invalidate 给其他 core
4. 收到所有 ack,把 store buffer 的值刷入 cache
```

问题来了:**别的 core 在 store buffer 还没刷入时,读到的是旧值**。这就是内存序问题的根源——store 不立即可见。

### 10.3 Memory barrier 的硬件实现

`mfence`(x86)指令告诉 CPU:**等 store buffer 全部 flush 到 cache,再继续**。这强制了"前面的写在 fence 之前完成"。

```asm
mov [x], 1     ; 写 store buffer
mov [y], 2     ; 写 store buffer
mfence         ; 等 store buffer flush
mov eax, [z]   ; 此时 x=1, y=2 已经可见
```

没有 mfence,CPU 可以"乱序"把 [z] 读提前到 [x] flush 之前。mfence 阻止这种 reorder。

ARM 的 `dmb ish`(data memory barrier, inner shareable)做同样的事,但 ARM 是弱模型——很多场景都要显式 dmb,而 x86 TSO 只在 SeqCst 时需要 mfence。

### 10.4 5 种 Ordering 对应的指令

把 Rust 的 Ordering 翻译成汇编:

| Ordering | x86(Skylake) | ARM(Cortex-A78) |
|---|---|---|
| Relaxed | 普通 mov | 普通 ldr/str |
| Release | 普通 mov(store 不重排,x86 TSO) | stlr(release store) |
| Acquire | 普通 mov(load 不重排,x86 TSO) | ldar(acquire load) |
| AcqRel | 普通 mov + (可能) mfence | ldaxr/stlxr 对 |
| SeqCst | mov + mfence(or xchg) | ldar/stlr + dmb ish |

观察:

- **x86 上 Release/Acquire 几乎免费**——x86 TSO 模型不允许 store-store / load-load / load-store 重排,所以普通 mov 就够。这是为什么 Casey 在 x86 上写的 lock-free 代码"碰巧"工作。
- **ARM 上 Release/Acquire 有真实开销**——stlr/ldar 比普通 ldr/str 慢约 5-10 ns。
- **SeqCst 在 x86 上仍然贵**——mfence 约 10-20 cycle,所有 SeqCst store 都付出这个代价。

### 10.5 Double-Checked Locking Pattern(DCLP)经典案例

历史上有名的内存序 bug。1990s C++ 程序员写 lazy singleton:

```cpp
// 错误版
Singleton* get_instance() {
    if (instance == nullptr) {          // 1
        lock_guard g(mutex);
        if (instance == nullptr) {      // 2
            instance = new Singleton(); // 3
        }
    }
    return instance;
}
```

step 3 的 `new Singleton()` 实际是两步:
- a. allocate 内存
- b. 调用构造函数初始化

编译器/CPU 可以把 3 重排成"先存指针后构造"——别的线程看到 instance != null 但对象还没初始化,使用就崩溃。

修复(C++11):

```cpp
std::atomic<Singleton*> instance;
Singleton* get_instance() {
    Singleton* p = instance.load(std::memory_order_acquire);  // Acquire
    if (!p) {
        lock_guard g(mutex);
        p = instance.load(std::memory_order_relaxed);
        if (!p) {
            p = new Singleton();
            instance.store(p, std::memory_order_release);  // Release
        }
    }
    return p;
}
```

Release-Acquire 配对,保证"构造完成"在 instance 写之前发生,读 instance 的线程一定看到构造完的对象。

Rust 的 `once_cell` / `std::sync::Once` 内部就是这个,但用 SeqCst + fence,更保险。这就是 Rust 用户很少直接处理 DCLP——库已经包好。

### 10.6 一个完整的 happens-before 推导案例

考虑下面代码:

```rust
static mut DATA: i32 = 0;
static READY: AtomicBool = AtomicBool::new(false);

fn thread_a() {
    unsafe { DATA = 42; }
    READY.store(true, Ordering::Release);
}

fn thread_b() {
    while !READY.load(Ordering::Acquire) {
        std::hint::spin_loop();
    }
    let val = unsafe { DATA };
    assert_eq!(val, 42);
}
```

happens-before 关系:

1. thread_a 的 `DATA = 42` happens-before `READY.store(true, Release)`(源码顺序)
2. thread_a 的 `READY.store(Release)` happens-before thread_b 的 `READY.load(Acquire)` 看到 true(Release-Acquire 配对建立)
3. thread_b 的 `READY.load(Acquire)` happens-before `DATA` 读(源码顺序)

链式传递:`DATA = 42` happens-before thread_b 的 `DATA` 读。所以 thread_b 一定看到 42。

**如果用 Relaxed**:第 2 步的 happens-before 不存在,链断。thread_b 可能读到 0(或 42,看 CPU 心情)。x86 上"碰巧"看到 42(因为 TSO 模型),ARM 上偶发看到 0。

### 10.7 fence() vs atomic 操作的 ordering

`fence()` 函数和 atomic 的 Ordering 参数容易混淆。区别:

- **Atomic Ordering**:作用于"该次原子操作"。比如 `Release store` 表示"这次 store 之前的写在 store 完成前完成"。
- **fence()**:不绑定具体操作,作用域更大。`fence(Release)` 表示"fence 之前的写在 fence 之后任何 atomic 操作可见"。

fence 用得少,通常 atomic + Ordering 已经够。fence 用于"非 atomic 内存 + atomic 同步"的混合场景,比如 SeqLock 实现:

```rust
// SeqLock 风格(简化)
let seq = SEQ.load(Relaxed);
fence(Acquire);
let data = unsafe { *DATA };  // 非 atomic 读
let seq2 = SEQ.load(Relaxed);
if seq != seq2 || seq & 1 != 0 {
    // 读期间 writer 改了,重试
}
```

这里 fence 在 atomic load 和非 atomic load 之间建立 ordering。

## 11 · Semaphore 的工业实现

今天 Casey 教 semaphore。Rust 标准库没 semaphore(只有 mutex + condvar),工业实现要看 libparking_lot / libstd:

### 11.1 朴素 semaphore(Mutex + Condvar)

```rust
pub struct Semaphore {
    count: Mutex<i32>,
    cond: Condvar,
}

impl Semaphore {
    pub fn new(initial: i32) -> Self {
        Self {
            count: Mutex::new(initial),
            cond: Condvar::new(),
        }
    }

    pub fn wait(&self) {
        let mut count = self.count.lock().unwrap();
        while *count <= 0 {
            count = self.cond.wait(count).unwrap();
        }
        *count -= 1;
    }

    pub fn post(&self) {
        let mut count = self.count.lock().unwrap();
        *count += 1;
        self.cond.notify_one();
    }
}
```

每次 wait/post 都 lock + unlock,~100ns。但简单可靠,90% 场景够用。

### 11.2 futex-based semaphore(Linux)

Linux 的 futex(fast userspace mutex)让 semaphore 更快:

- **fast path**:count > 0,atomic dec,直接返回,~10ns
- **slow path**:count == 0,syscall futex(FUTEX_WAIT),进 kernel sleep

Rust 的 `libc::syscall(SYS_futex, ...)` 调用。或用 `linux-futex` crate。Casey 在 HH 用 Windows 的相似原语(Slim Reader/Writer Lock 的 semaphore 模式)。

### 11.3 用 semaphore 做"限流 worker pool"

经典模式:

```rust
let sem = Arc::new(Semaphore::new(8));  // 限制 8 并发

for task in tasks {
    let sem = Arc::clone(&sem);
    thread::spawn(move || {
        sem.wait();
        // ... 执行 task
        sem.post();
    });
}
```

任意时刻最多 8 个 task 同时跑。其余 worker 在 sem.wait 阻塞。这是 worker pool 的标准模式。
