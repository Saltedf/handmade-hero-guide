# Day 136 · 基于标签的资产检索

> Day 134 的 tag 系统是"一对一"(一个 tag 对应一个资产)。今天升级为"多对多":一个资产多个 tag(剑既是"weapon"也是"sharp"),一个 tag 匹配多个资产(所有 "weapon" 类资产)。这是数据库式查询在游戏资产系统的应用。

## 0 · 为什么要有这一天

Day 134 你写:

```rust
let sword = store.lookup_bitmap("sword").unwrap();
```

游戏代码能通过 tag 找到剑。但游戏里你想:

```rust
// 找所有 "weapon" 类资产(剑、斧头、弓)
let weapons = store.lookup_all("weapon");

// 找既 "weapon" 又 "sharp" 的(剑、斧头,不含弓)
let sharp_weapons = store.lookup_all(&["weapon", "sharp"]);

// 找 "sword" 的所有变体(普通剑、魔法剑、生锈的剑)
let sword_variants = store.lookup_all("sword");
```

这种"按 tag 查询"的需求在游戏开发无处不在:

- 玩家装备武器 → 系统查所有 weapon tag 的资产,随机选一个
- 渲染粒子效果 → 查所有 particle tag 的资产
- 播放受伤音效 → 查所有 "sfx_hurt" tag 的资产,随机播一个

Day 134 的"一对一"映射做不了这种查询。今天升级为"多对多":

- 每个资产有 `Vec<String>` tags(多 tag)
- 每个 tag 有 `Vec<AssetId>` assets(多资产)
- 提供 `find_all(tag) -> Vec<AssetId>`、`find_matching(tags) -> Vec<AssetId>` 等查询 API

这就是数据库式查询的基础——你相当于在资产管理里实现了一个 mini 数据库。

心理锚点:做完今天你能(1)设计多对多的 tag 系统;(2)实现 `find_all(tag)`、`find_all_match(tags)` 查询;(3)理解为什么 tag 查询要 cache 结果(避免每帧重查);(4)说出 ECS 里的 archetype 查询和这个的关系。

## 1 · Casey 今天做了什么

Casey 在 Day 134-135 的基础上重构 tag 系统:

1. 每资产维护 `Vec<String> tags` 而不是单 tag
2. 反向索引:`HashMap<String, Vec<AssetId>>` 从 tag 查所有匹配资产
3. 查询 API:`find_all(tag) -> &[AssetId]`、`find_first(tag) -> Option<AssetId>`
4. 多 tag 交集查询:`find_matching(&["weapon", "sharp"]) -> Vec<AssetId>`
5. 加资产时指定 tags 列表:`add_with_tags(&["sword", "weapon", "sharp"], bmp)`

这一天的核心:**把资产管理从"key-value 字典"演化成"标签索引数据库"**。后面 Day 137 加周期标签匹配,完成完整查询能力。

## 2 · 心智模型

### 类比:图书馆主题标引 vs 文件名

**Day 134 单 tag** 像文件名:每本书一个唯一文件名,精确但单一维度。

**Day 136 多 tag** 像图书馆主题标引(Library of Congress Subject Headings):一本书《剑的演化》同时归类到 "weapon" / "history" / "metalwork"。读者可以查"所有 weapon 书"或"所有 history 书"或"既是 weapon 又是 history 的书"。

### 严谨原理:正向索引 vs 反向索引

**正向索引**:`AssetId → Vec<Tag>` —— "资产 X 有哪些 tag"。
**反向索引**:`Tag → Vec<AssetId>` —— "tag T 匹配哪些资产"。

两个索引都要维护,因为查询方向不同:

```rust
struct AssetPool<T> {
    items: Vec<T>,
    forward: Vec<Vec<String>>,              // 正向:items[i] 的 tags
    reverse: HashMap<String, Vec<u32>>,     // 反向:tag → asset indices
}
```

加资产:
```rust
fn add_with_tags(&mut self, tags: &[&str], item: T) -> AssetId<T> {
    let id = self.items.len() as u32;
    self.items.push(item);
    let tags_vec: Vec<String> = tags.iter().map(|s| s.to_string()).collect();
    self.forward.push(tags_vec.clone());
    for tag in tags_vec {
        self.reverse.entry(tag).or_default().push(id);
    }
    AssetId { id, _ty: PhantomData }
}
```

查询:
```rust
fn find_all(&self, tag: &str) -> Vec<AssetId<T>> {
    self.reverse.get(tag).map(|ids| {
        ids.iter().map(|&id| AssetId { id, _ty: PhantomData }).collect()
    }).unwrap_or_default()
}

fn find_matching(&self, tags: &[&str]) -> Vec<AssetId<T>> {
    // 交集:同时满足所有 tags 的资产
    if tags.is_empty() { return vec![]; }
    let mut result: Option<HashSet<u32>> = None;
    for tag in tags {
        let matching: HashSet<u32> = self.reverse.get(*tag)
            .map(|ids| ids.iter().copied().collect())
            .unwrap_or_default();
        result = Some(match result {
            None => matching,
            Some(prev) => prev.intersection(&matching).copied().collect(),
        });
    }
    result.map(|set| {
        set.into_iter().map(|id| AssetId { id, _ty: PhantomData }).collect()
    }).unwrap_or_default()
}
```

### 多对多的代价

每加一个资产,要更新正向 + 反向索引。每加一个 tag,反向索引可能要新增 entry。内存开销:

- 正向索引:N 资产 × 平均 M tags × 24 字节(String)= N×M×24
- 反向索引:所有 unique tag 数 × (24 + Vec 开销)

1000 资产 × 5 tag 平均 = 5000 (asset, tag) 对。内存 ~120KB,可接受。

### cache 查询结果

tag 查询是 cold path(启动时、关卡切换时)。但有些查询每帧执行(比如 UI 显示所有 weapon):

```rust
// 慢:每帧查询
fn render() {
    let weapons = store.find_all("weapon");  // 每帧 hash + lookup
    for w in &weapons { ... }
}

// 快:缓存结果
struct GameState {
    weapon_ids: Vec<AssetId<Bitmap>>,  // 启动时查一次
}
fn init(state: &mut GameState) {
    state.weapon_ids = store.find_all("weapon");
}
fn render(state: &GameState) {
    for &w in &state.weapon_ids { ... }  // 直接用缓存
}
```

资产变化(加载、卸载)时刷新缓存。Casey Day 136 之后所有查询都用缓存模式。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

多 tag 系统在游戏开发里是标配:

- **Unreal Engine**:`UPrimaryDataAsset` + FGameplayTag,标签系统由 GameplayTagsManager 管理
- **Unity Addressables**:`IResourceLocator` + label,资产可以多个 label
- **Bevy**:`AssetLoader` 可以加自定义元数据,标签通过 Reflect 暴露

游戏开发圈的 tag 系统演化:

**阶段 1**:路径引用(`load("sword.png")`)
**阶段 2**:单 ID(`BitmapId(42)`)
**阶段 3**:单 tag(`"sword"`)
**阶段 4**:多 tag(`["sword", "weapon"]`)← Day 136
**阶段 5**:结构化 tag(`weapon.melee.sword`,层级)

商业引擎到阶段 5。Casey Day 136 到阶段 4。

### 3.2 · 🎨 图形学视角

tag 系统在 shader / material 系统里也常见:

- **Shader keywords**:Unity 的 `#pragma multi_compile _ _EMISSION`,shader 可以有多个 keyword,运行时切换
- **Material flags**:Unreal 的 material 有 `BLEND_OPAQUE` / `BLEND_TRANSLUCENT` 等 tag,渲染管线根据 tag 选 blend mode
- **Texture channels**:RMAO(Red=Metallic,Green=Roughness,Blue=AO)pack 是约定俗成的 tag

这些"按 tag 选择 shader variant"和 Casey 的"按 tag 查资产"同构。

### 3.3 · 🐧 Linux 系统编程视角

Linux 里类似 tag 系统的设施:

**udev rules**:设备按属性(PRODUCT、VENDOR、SUBSYSTEM)匹配规则。每个设备多个属性,规则可以多个 attribute。

```bash
# udev 规则示例:同时匹配 vendor 和 product
SUBSYSTEM=="usb", ATTRS{idVendor}=="046d", ATTRS{idProduct}=="c52b", SYMLINK+="logitech_receiver"
```

**systemd unit dependencies**:`WantedBy=`、`Requires=`、`After=` 等多个 tag,systemd 按这些 tag 决定启动顺序。

**ext4 extended attributes**:`setfattr -n user.tag -v weapon file.png`,文件可以多个 xattr,用户按 xattr 查询。

这些都和 Casey 的多 tag 资产系统同构——**多对多映射 + 查询**。

### 3.4 · 🦀 Rust 生态视角

Rust 表达多 tag 系统的几种方式:

#### 流派 1:Vec<Vec<String>> + HashMap<String, Vec<u32>>

如上所示。简单,直接。

#### 流派 2:`BitSet` 表示 tag 集合

```rust
struct TagSet(u128);  // 最多 128 种 tag
// 每个 bit 代表一个 tag(bit 0 = "weapon", bit 1 = "sharp", ...)
fn matches(&self, query: TagSet) -> bool {
    (self.0 & query.0) == query.0  // 包含所有查询 bit
}
```

查询极快(整数 AND 操作),但 tag 总数限制 128。ECS 系统(bevy_ecs、specs)用 BitSet 表示 component set,Casey 可以借鉴但 HH 不需要这么复杂。

#### 流派 3:`IndexSet<String>` 共享 string

```toml
[dependencies]
indexmap = "2"
```

```rust
use indexmap::IndexSet;
struct AssetPool<T> {
    tags_interned: IndexSet<String>,  // string 共享
    // ...
}
```

string 在 IndexSet 里只存一次,资产持有索引(u32)而不是 String。内存省 10-100 倍。

#### 流派 4:Bevy 风格 ECS query

```rust
// Bevy ECS 风格
fn system(query: Query<&Transform, With<Enemy>>) {
    // 查询所有带 Enemy component 的 Transform
}
```

`With<Enemy>` 是 ECS 的 tag 表达。Casey 的多 tag 系统是 ECS query 的简化版。

## 5 · 对照与变奏

### 数据库式查询 vs 硬编码

游戏代码要"装备所有 weapon"。两种写法:

```rust
// 数据库式查询(灵活)
let weapons = store.find_all("weapon");
for w in weapons { equip(w); }

// 硬编码(快速但死板)
equip(SWORD_ID);
equip(AXE_ID);
equip(BOW_ID);
```

查询版灵活——美工加新 weapon,游戏代码自动支持。硬编码版快——但加新 weapon 要改代码、重新编译、重新发布。

商业游戏混合:大部分用查询(动态资产),少数关键资产硬编码(角色、第一关 boss)。

### 倒排索引 vs 全文搜索

倒排索引:`tag → asset_ids`。精确匹配。
全文搜索:`关键词 → asset_ids with fuzzy match`。模糊匹配,带评分。

游戏资产管理通常用倒排索引(精确)。但有些游戏(如 Skyrim 的 mod 搜索)用全文搜索。

### 历史演化

- **1970s**:数据库 inverted index(IBM DB2)
- **1990s**:搜索引擎(Lucene、ElasticSearch)
- **2000s**:游戏资产 tag 系统(Unity、Unreal)
- **2010s**:ECS archetype query(bevy_ecs、Unity DOTS)
- **2020s**:更精细的 query(数据导向设计)

Casey Day 136 在 2000s 水平。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:

1. 一个资产有 3 个 tags("sword", "weapon", "sharp"),正向索引和反向索引各存什么?
2. `find_matching(&["weapon", "sharp"])` 返回什么?用集合操作解释。
3. 为什么 `find_all` 的返回类型是 `Vec<AssetId>` 而不是 `&[AssetId]`?
4. 1000 资产 × 5 tags,反向索引内存大约多少?

**参考解答**:
1. 正向索引:`assets[i].tags = ["sword", "weapon", "sharp"]`(i 是资产 index)。反向索引:`reverse["sword"] = [i]`、`reverse["weapon"] = [i, j, k, ...]`、`reverse["sharp"] = [i, j, ...]`(每个 tag 列出所有匹配资产)。
2. 返回同时满足 "weapon" AND "sharp" 的资产。集合操作:`find_all("weapon") ∩ find_all("sharp")`。剑(sword)同时有 weapon 和 sharp,在结果里。斧头(axe)同。弓(bow)有 weapon 但没 sharp,不在结果里。
3. 因为查询可能要排序、过滤、组合,返回 Vec 让调用方自由操作。返回 &[AssetId] 会限制调用方(不能修改、不能扩展)。代价是分配 Vec(几十字节),cold path 可忽略。
4. 反向索引:1000×5 = 5000 个 (tag, asset_id) 对。每 String 平均 6 字符 = 12 字节 + Vec<u32> entry 4 字节 + HashMap 元数据 32 字节。总大约 240 KB。

### Lv2 · 动手实践

**题**:在 Day 135 的 AssetPool<T> 上加多 tag 系统。

要求:
1. `forward: Vec<Vec<String>>` 正向索引
2. `reverse: HashMap<String, Vec<u32>>` 反向索引
3. `add_with_tags(tags: &[&str], item: T) -> AssetId<T>`
4. `find_all(tag: &str) -> Vec<AssetId<T>>`
5. `find_matching(tags: &[&str]) -> Vec<AssetId<T>>`(交集)
6. main:加 5 个资产(剑、斧、弓、盾、头盔),每个多 tag,测试 find_all / find_matching

完成标准:find_all("weapon") 返回剑、斧、弓;find_matching(&["weapon", "sharp"]) 返回剑、斧(不含弓)。

**参考解答**:

```rust
use std::collections::{HashMap, HashSet};
use std::marker::PhantomData;

struct AssetId<T> { id: u32, _ty: PhantomData<fn() -> T> }
impl<T> Copy for AssetId<T> {}
impl<T> Clone for AssetId<T> { fn clone(&self) -> Self { *self } }
impl<T> std::fmt::Debug for AssetId<T> {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        write!(f, "AssetId({})", self.id)
    }
}

struct AssetPool<T> {
    items: Vec<T>,
    forward: Vec<Vec<String>>,
    reverse: HashMap<String, Vec<u32>>,
}

impl<T> AssetPool<T> {
    fn new() -> Self {
        Self {
            items: Vec::new(),
            forward: Vec::new(),
            reverse: HashMap::new(),
        }
    }

    fn add_with_tags(&mut self, tags: &[&str], item: T) -> AssetId<T> {
        let id = self.items.len() as u32;
        self.items.push(item);
        let tags_vec: Vec<String> = tags.iter().map(|s| s.to_string()).collect();
        for tag in &tags_vec {
            self.reverse.entry(tag.clone()).or_default().push(id);
        }
        self.forward.push(tags_vec);
        AssetId { id, _ty: PhantomData }
    }

    fn get(&self, aid: AssetId<T>) -> &T {
        &self.items[aid.id as usize]
    }

    fn find_all(&self, tag: &str) -> Vec<AssetId<T>> {
        self.reverse.get(tag).map(|ids| {
            ids.iter().map(|&id| AssetId { id, _ty: PhantomData }).collect()
        }).unwrap_or_default()
    }

    fn find_matching(&self, tags: &[&str]) -> Vec<AssetId<T>> {
        if tags.is_empty() { return vec![]; }
        let mut result: Option<HashSet<u32>> = None;
        for tag in tags {
            let matching: HashSet<u32> = self.reverse.get(*tag)
                .map(|ids| ids.iter().copied().collect())
                .unwrap_or_default();
            result = Some(match result {
                None => matching,
                Some(prev) => prev.intersection(&matching).copied().collect(),
            });
        }
        result.map(|set| {
            let mut v: Vec<u32> = set.into_iter().collect();
            v.sort();  // 稳定顺序
            v.into_iter().map(|id| AssetId { id, _ty: PhantomData }).collect()
        }).unwrap_or_default()
    }

    fn tags_of(&self, aid: AssetId<T>) -> &[String] {
        &self.forward[aid.id as usize]
    }
}

struct Item { name: &'static str }

fn main() {
    let mut pool: AssetPool<Item> = AssetPool::new();

    let sword = pool.add_with_tags(&["weapon", "sharp", "sword"], Item { name: "Iron Sword" });
    let axe = pool.add_with_tags(&["weapon", "sharp", "axe"], Item { name: "Battle Axe" });
    let bow = pool.add_with_tags(&["weapon", "bow"], Item { name: "Long Bow" });
    let shield = pool.add_with_tags(&["armor", "shield"], Item { name: "Wooden Shield" });
    let helmet = pool.add_with_tags(&["armor", "helmet"], Item { name: "Iron Helmet" });

    println!("All assets:");
    for &id in &[sword, axe, bow, shield, helmet] {
        println!("  {:?} {:?} tags={:?}", id, pool.get(id).name, pool.tags_of(id));
    }

    println!("\nfind_all('weapon'):");
    for id in pool.find_all("weapon") {
        println!("  {:?} = {}", id, pool.get(id).name);
    }

    println!("\nfind_all('armor'):");
    for id in pool.find_all("armor") {
        println!("  {:?} = {}", id, pool.get(id).name);
    }

    println!("\nfind_matching(['weapon', 'sharp']):");
    for id in pool.find_matching(&["weapon", "sharp"]) {
        println!("  {:?} = {}", id, pool.get(id).name);
    }

    println!("\nfind_matching(['weapon', 'bow']):");
    for id in pool.find_matching(&["weapon", "bow"]) {
        println!("  {:?} = {}", id, pool.get(id).name);
    }

    println!("\nfind_matching(['armor', 'sharp']):");  // 没有同时满足的
    let empty = pool.find_matching(&["armor", "sharp"]);
    println!("  {} matches", empty.len());
}
```

```rust
use std::time::Instant;

// 1M 资产 × 5 tags,看 find_all 性能
fn main() {
    let mut pool: AssetPool<Item> = AssetPool::new();
    for i in 0..1000 {
        let tags: Vec<&str> = vec!["weapon", &format!("variant_{}", i % 10)];
        pool.add_with_tags(&tags, Item { name: "x" });
    }
    let start = Instant::now();
    let result = pool.find_all("weapon");
    println!("find_all('weapon') returned {} in {:?}", result.len(), start.elapsed());

    let start = Instant::now();
    let result = pool.find_matching(&["weapon", "variant_3"]);
    println!("find_matching(['weapon','variant_3']) returned {} in {:?}", result.len(), start.elapsed());
}
```

## 10 · 深度推导:倒排索引的工程细节

今天 Casey 引入倒排索引。这是搜索引擎和数据库的核心技术。这一节把倒排索引的所有工程细节讲透。

### 10.1 倒排索引是什么?

普通字典(HashMap)是"key → value"。倒排索引是"从 value 反查 key":

```
Document 1: tags = [weapon, sharp, sword]
Document 2: tags = [weapon, sharp, axe]
Document 3: tags = [weapon, bow]
Document 4: tags = [armor, shield]
```

倒排索引:

```
weapon → [1, 2, 3]
sharp → [1, 2]
sword → [1]
axe → [2]
bow → [3]
armor → [4]
shield → [4]
```

查询"所有 weapon 的文档",直接查 `weapon` 这个 key,得到 `[1, 2, 3]`。不用扫所有文档。

这就是 Google / Lucene / Elasticsearch 的核心技术。Casey 在游戏资产系统里实现的就是这个。

### 10.2 集合交集:多 tag 查询的核心

查询"weapon AND sharp":

1. 查 `weapon → [1, 2, 3]`
2. 查 `sharp → [1, 2]`
3. 求交集:`[1, 2]`(同时出现在两个列表的)

集合交集算法:

- **朴素**:O(N×M),每 N 个元素扫 M 次
- **排序后双指针**:O(N+M),适合两个排序数组
- **Hash set**:O(N+M),用 HashSet

Day 136 用 HashSet.intersection。Lucene 用 SkipList(高级数据结构,支持 O(log N) 跳过)。

### 10.3 增量更新:加资产时维护索引

加新资产:

```rust
fn add_with_tags(&mut self, tags: &[&str], item: T) -> AssetId<T> {
    let id = self.items.len() as u32;
    self.items.push(item);
    for tag in tags {
        self.reverse.entry(tag.to_string()).or_default().push(id);
    }
    self.forward.push(tags.iter().map(|s| s.to_string()).collect());
    AssetId { id, _ty: PhantomData }
}
```

每加一个资产,要 O(M) 操作(M = tag 数)。1000 资产 × 5 tag = 5000 操作。可接受。

### 10.4 删除资产:复杂操作

```rust
fn remove(&mut self, aid: AssetId<T>) {
    let tags = std::mem::take(&mut self.forward[aid.id as usize]);
    for tag in &tags {
        if let Some(list) = self.reverse.get_mut(tag) {
            list.retain(|&x| x != aid.id);
            if list.is_empty() {
                self.reverse.remove(tag);
            }
        }
    }
    // items[aid.id] 怎么处理?逻辑删除(留空)还是物理删除(移除)?
}
```

复杂点:

- 删除 asset 后,items[index] 是空洞。要么标"已删除"(下次 lookup 跳过),要么 swap_remove(把最后一个搬过来,这样所有 index 紧凑,但其他 asset 的 index 变了——需要更新所有索引)。
- 上述代码用"逻辑删除"——items[aid.id] 留下旧值,但 forward 和 reverse 不再引用。lookup find_all 时跳过 deleted 标记。
- 工业实现常用 **generational index**:每个 slot 有 generation,删除时 generation++,新 id 用新 generation,旧 id 的 generation 不匹配 → lookup 返回 None。

### 10.5 内存估算

1000 资产 × 5 tag 平均,每个 tag 6 字符:

- forward:1000 × 5 × (24 字节 String) = 120 KB
- reverse:5000 (tag, asset_id) 对 = 5000 × (24 字节 String + 4 字节 u32 + 32 字节 HashMap metadata) = 300 KB
- 总 ~420 KB

对游戏可接受,但比直接 Vec<Asset>(1000 × 80 字节 = 80 KB)多 5 倍。代价是查询能力。

### 10.6 缓存查询结果(关键优化)

每次 `find_all("weapon")` 都要 HashMap lookup + Vec 分配。在 hot path 这太贵。

工业模式:启动时查询,缓存结果:

```rust
struct GameState {
    weapon_ids: Vec<AssetId<Bitmap>>,
    armor_ids: Vec<AssetId<Bitmap>>,
}

    state.weapon_ids = store.bitmaps.find_all("weapon");
    state.armor_ids = store.bitmaps.find_all("armor");
}

fn render(state: &GameState, store: &AssetStore) {

    }
}
```

### 10.7 完整代码示例

```rust
use std::collections::{HashMap, HashSet};
use std::marker::PhantomData;

pub struct AssetId<T> { id: u32, _ty: PhantomData<fn() -> T> }
impl<T> Copy for AssetId<T> {}
impl<T> Clone for AssetId<T> { fn clone(&self) -> Self { *self } }

pub struct AssetPool<T> {
    items: Vec<T>,
    forward: Vec<Vec<String>>,
    reverse: HashMap<String, Vec<u32>>,
    deleted: HashSet<u32>,  // 标记已删除
}

impl<T> AssetPool<T> {
    pub fn new() -> Self {
        Self {
            items: Vec::new(),
            forward: Vec::new(),
            reverse: HashMap::new(),
            deleted: HashSet::new(),
        }
    }

    pub fn add(&mut self, tags: &[&str], item: T) -> AssetId<T> {
        let id = self.items.len() as u32;
        self.items.push(item);
        let tag_vec: Vec<String> = tags.iter().map(|s| s.to_string()).collect();
        for tag in &tag_vec {
            self.reverse.entry(tag.clone()).or_default().push(id);
        }
        self.forward.push(tag_vec);
        AssetId { id, _ty: PhantomData }
    }

    pub fn find_all(&self, tag: &str) -> Vec<AssetId<T>> {
        self.reverse.get(tag).map(|ids| {
            ids.iter()
                .filter(|&&id| !self.deleted.contains(&id))
                .map(|&id| AssetId { id, _ty: PhantomData })
                .collect()
        }).unwrap_or_default()
    }

    pub fn find_matching(&self, tags: &[&str]) -> Vec<AssetId<T>> {
        if tags.is_empty() { return vec![]; }
        let mut sets: Vec<HashSet<u32>> = tags.iter().map(|t| {
            self.reverse.get(t).map(|v| v.iter().copied().collect()).unwrap_or_default()
        }).collect();

        let mut result = sets.remove(0);
        for s in sets {
            result = result.intersection(&s).copied().collect();
        }
        result.into_iter()
            .filter(|id| !self.deleted.contains(id))
            .map(|id| AssetId { id, _ty: PhantomData })
            .collect()
    }

    pub fn get(&self, aid: AssetId<T>) -> &T {
        &self.items[aid.id as usize]
    }

    pub fn remove(&mut self, aid: AssetId<T>) {
        self.deleted.insert(aid.id);
        // 注意:forward 和 reverse 不动,find_all 过滤 deleted
    }
}
```
