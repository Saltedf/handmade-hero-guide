# Day 134 · 资产映射到位图

> Day 133 把资产按类型分组后,今天加一层"映射":一个抽象的 AssetTag(比如 "sword")映射到具体的 BitmapId。这让游戏代码用语义名字("sword")而不是数字(BitmapId(42))引用资产。

## 0 · 为什么要有这一天

Day 133 你有了 `BitmapId(u32)`、`SoundId(u32)` 这种类型化 ID。但游戏代码里到处看到:

```rust
let sword_bmp = store.get_bitmap(BitmapId(42));
```

`42` 是什么?几个月后回来看,谁知道 42 是剑的图标还是斧头的图标?游戏开发圈叫这个"magic number 地狱"。

更糟的是,如果美工调整资产顺序(把 sword.png 从第 42 个挪到第 50 个),所有 `BitmapId(42)` 都要改成 `BitmapId(50)`。

**今天的核心**:加一层抽象。让游戏代码用语义名字引用资产:

```rust
let sword_bmp = store.get_bitmap_by_tag("sword");
```

资产系统维护一个 `"sword" -> BitmapId(42)` 的映射表。美工调整顺序时,只改映射表,游戏代码不动。

这就是 Day 134 的核心:**把 ID 数字隐藏到一层 string-to-id 映射之后**。Day 136 会扩展为 tag 系统(一个资产可以多个 tag,一个 tag 可以匹配多资产),今天是单对单基础版。

心理锚点:做完今天你能(1)在你的资产系统加 string-to-id 映射;(2)理解为什么 string lookup 不要在 hot path(渲染循环)里;(3)用 newtype + HashMap 实现"name -> BitmapId";(4)解释 magic number 的工程问题。

## 1 · Casey 今天做了什么

Casey 在 Day 133 的类型化分组之上加映射:

1. 定义 `AssetTag`(C 里用 string,Rust 里用 `String` 或 `&'static str`)
2. `AssetStore` 加字段 `bitmap_tags: HashMap<String, BitmapId>`、`sound_tags: HashMap<String, SoundId>`
3. 加资产时同时注册 tag:`add_bitmap_with_tag(bmp, "sword")`
4. 查询:`get_bitmap_by_tag("sword") -> Option<&Bitmap>`
5. 游戏代码从 `BitmapId(42)` 改为 `"sword"`,可读性提升

Casey 还做了一个微优化:**tag 查询只在加载时做**,查询后游戏代码缓存 BitmapId,后续渲染循环直接用 BitmapId 不走 HashMap。这样 hot path 没有 hash 计算。

## 2 · 心智模型

### 类比:电话簿 vs 直接拨号

**Day 133 的 BitmapId** 像电话号码:精确但难记。你给小王打电话 `BitmapId(42)`,几个月后忘了 42 是谁。

**Day 134 的 tag** 像电话簿:翻 "小王" 找到电话号码,然后拨号。第一次查慢,后续记住号码直接拨。

游戏的 "tag 查询 → 缓存 BitmapId" 模式 = 电话簿 → 记住号码。

### 严谨原理:string-to-id 映射

```rust
struct AssetStore {
    bitmaps: Vec<Bitmap>,
    sounds: Vec<Sound>,
    bitmap_tags: HashMap<String, BitmapId>,  // 新增
    sound_tags: HashMap<String, SoundId>,    // 新增
}

impl AssetStore {
    fn add_bitmap_with_tag(&mut self, tag: &str, bmp: Bitmap) -> BitmapId {
        let id = self.add_bitmap(bmp);
        self.bitmap_tags.insert(tag.to_string(), id);
        id
    }

    fn lookup_bitmap(&self, tag: &str) -> Option<BitmapId> {
        self.bitmap_tags.get(tag).copied()
    }

    fn get_bitmap_by_tag(&self, tag: &str) -> Option<&Bitmap> {
        self.lookup_bitmap(tag).map(|id| self.get_bitmap(id))
    }
}
```

游戏代码:
```rust
// 加载时
let store = ...;
store.add_bitmap_with_tag("sword", sword_bmp);
store.add_bitmap_with_tag("tree", tree_bmp);

// 游戏初始化时(冷启动)
let sword_id = store.lookup_bitmap("sword").unwrap();

// 渲染循环(hot path)
for frame in 0..N {
    let sword = store.get_bitmap(sword_id);  // 直接用 BitmapId,无 hash
    render(sword);
}
```

### hot path vs cold path

游戏开发的核心区分:

| | Cold path(冷路径) | Hot path(热路径) |
|---|---|---|
| 频率 | 启动 / 关卡切换时一次 | 每帧每像素 |
| 例子 | 资产加载、tag 查询 | 像素 blit、矩阵乘 |
| 可接受 | 100 ms | 0.016 ms(60 FPS / 1000 像素) |
| 数据结构 | HashMap、Vec、Box | 紧凑数组、SIMD |

string-to-id 映射是 **cold path**——只在启动时查一次,缓存 id。hot path 直接用 id 跳过 hash。这是高性能游戏的基本卫生。

### Rust 表达

`HashMap<String, BitmapId>` 简单直接。但有几个 Rust 特定优化:

#### 流派 1:`&'static str` 作为 key

如果 tag 是编译期常量(硬编码在代码里):

```rust
fn lookup_bitmap(&self, tag: &'static str) -> Option<BitmapId> {
    self.bitmap_tags.get(tag).copied()
}
```

`&'static str` 是 `'static` 生命周期,不需要 String 分配。HashMap lookup 速度更快(无堆访问)。但只适用于编译期已知的 tag。

#### 流派 2:interned strings

如果 tag 是运行时产生的(比如从 JSON 读),用 `String` 会每次 lookup 都 hash 一次。优化:`string_interner` crate。

```toml
[dependencies]
string_interner = "0.1"
```

```rust
use string_interner::StringInterner;
let mut interner = StringInterner::new();
let sword_sym = interner.get_or_intern("sword");  // 返回 Symbol(u32)
// 后续用 Symbol 比较,无需 hash 字符串
```

把 string 转 u32 symbol,后续比较 symbol 比较字符串快。编译器、解释器、游戏引擎常用。

#### 流派 3:hash-once + cached hash

如果不想引入 interner,可以 cache hash:

```rust
struct CachedStr {
    s: String,
    hash: u64,
}
impl Hash for CachedStr { ... }
```

但实现复杂,不推荐。

Casey 用 `&'static str`(流派 1)因为 HH 的 tag 都是硬编码。Rust 教学版同。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发里"用名字引用资产"是标配:

- **Unreal Engine**:`ConstructorHelpers::FObjectFinder<UTexture2D>(TEXT("Texture2D'/Game/Assets/Sword.Icon'"))`,加载时按路径找,缓存 pointer
- **Unity**:`Resources.Load<Texture2D>("sword")`,路径转 asset
- **Bevy**:`asset_server.load("sword.png")`,path 转 Handle<T>`

所有引擎都是"启动时 string lookup → 后续用 handle"。Casey 走同样模式。

游戏开发圈的 tag 系统演化:

- **第一阶段**(Day 133):无 tag,直接 BitmapId
- **第二阶段**(Day 134):单 tag(string-to-id)
- **第三阶段**(Day 135):多 tag(一个资产多个名字,如 "sword" / "weapon" / "icon")
- **第四阶段**(Day 136):反向 tag(id-to-tags,按 tag 查找所有匹配资产)
- **第五阶段**(Day 137):周期 tag("attack_frame_1" / "attack_frame_2" / ...,动画循环)

商业引擎到第四阶段为止。HH Day 137 还做周期 tag,因为他的 2D 角色动画是手动管理 frame。

### 3.2 · 🐧 Linux 系统编程视角

Linux 里也有"string-to-id"模式:

**inode number**:文件路径 → inode number。文件系统启动时建 dentry cache(path → inode),后续访问走 inode 直接操作。

```bash
# 看 inode
ls -i /tmp/foo.txt
# 1234567 /tmp/foo.txt
```

**system call number**:syscall 名字(`read`)→ number(`0` 在 x86_64)。glibc 启动时建查找表,后续直接用 number。

**ELF symbol**:函数名 → 地址。动态链接器(ld-linux.so)启动时建 PLT/GOT 表。

这些和 Casey 的 tag-to-id 映射同构:**string 给人,number 给机器,中间一层映射在启动时建好**。

### 3.3 · 🦀 Rust 生态视角

Rust 的 HashMap 默认是 SipHash(抗 hash 碰撞攻击,但慢)。性能敏感场景换 FxHash 或 AHash:

```toml
[dependencies]
rustc-hash = "0.1"  # FxHash
```

```rust
use rustc_hash::FxHashMap;
let map: FxHashMap<String, BitmapId> = FxHashMap::default();
```

FxHash 比 SipHash 快 2-3 倍,但不抗攻击(游戏开发无所谓,资产 tag 都是内部的)。

Bevy 内部用 `bevy_utils::HashMap`(基于 AHash)。Casey 用 SipHash 默认。

### 3.4 · 内存开销

`HashMap<String, BitmapId>` 占多少内存?

- String 本身:堆分配,每 string 24 字节 + UTF-8 bytes
- HashMap entry:32-64 字节(键 + 值 + 控制字节)
- 1000 个资产 tag:大约 100KB

对游戏不算大,但要注意 hot path 别走它。

## 5 · 对照与变奏

### 单向 vs 双向映射

单向(tag → id):HashMap<String, BitmapId>。只能从 tag 找 id。
双向:加 HashMap<BitmapId, String>。从 id 找 tag(debug 时显示资产名)。

商业引擎用双向,方便 debug。Casey 单向,Day 136 加 tag 系统时变多对多。

### string 路径 vs opaque id

另一种常见设计:不用 string tag,用 opaque id(Handle)。游戏代码:

```rust
let sword: Handle<Image> = asset_server.load("sword.png");
```

加载时 string lookup 一次,Handle 内部是 u32(或 Arc<u32>)。后续用 Handle 操作。和 Casey 的 BitmapId 同构,只是 API 风格不同。

Bevy 用这种风格。Casey 用 `BitmapId(u32)` 直接暴露,因为他是 C 背景习惯。

### 历史演化

- **1980s**:游戏直接 hardcode 索引(`sprite[42]`)
- **1990s**:路径引用(`load("sword.png")`)
- **2000s**:统一资产系统 + 路径(Unity、Unreal)
- **2010s**:tag / label 系统 + 引用计数 Handle(Bevy)
- **2020s**:asset variants + procedural(同一资产不同参数版本)

Casey Day 134 走 1990s 风格(string lookup),后续 Day 136 升级到 2010s 风格(tag 系统)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:

1. 为什么 hot path 不应该用 string lookup,而用 BitmapId?
2. 一个 HashMap<String, BitmapId> 有 10000 个条目,内存大约多少?Lookup 一次多少 ns?
3. 为什么 Rust 默认用 SipHash 而不是 FxHash?游戏开发要换吗?
4. tag 系统让游戏代码更"灵活",代价是什么?

**参考解答**:
1. string lookup 需要 hash 字符串(SipHash 100+ ns)+ HashMap 探测(几十 ns)。每像素 0.1 微秒,1M 像素 = 100ms,直接爆帧。BitmapId 是 u32,数组索引 1 ns。差 100 倍。所以启动时 lookup 一次,缓存 id,hot path 直接用 id。
2. 10000 条目 × (24 字节 String + 4 字节 BitmapId + 16 字节 HashMap 元数据) ≈ 440 KB。Lookup 大约 200-500 ns(取决于 hash 速度和 cache 状态)。
3. SipHash 抗 hash 碰撞攻击(DoS 防御),适合处理来自网络的 string。FxHash 快但不抗攻击。游戏开发所有 tag 都是内部的(美工和程序员写的),没有攻击面,可以换 FxHash 提速 2-3 倍。
4. 代价:(a)额外的 HashMap 内存;(b)启动时 lookup 一次的 CPU;(c) tag 拼写错误运行时才发现(不如编译期 BitmapId 安全)。换来的好处:可读性、可维护性、灵活性。

### Lv2 · 动手实践

**题**:在 Day 133 的 AssetStore 基础上加 tag 系统。

要求:
1. `AssetStore` 加 `bitmap_tags: HashMap<String, BitmapId>`、`sound_tags: HashMap<String, SoundId>`
2. `add_bitmap_with_tag(tag: &str, bmp: Bitmap) -> BitmapId`
3. `lookup_bitmap(tag: &str) -> Option<BitmapId>`
4. `get_bitmap_by_tag(tag: &str) -> Option<&Bitmap>`
5. main:加 3 个 bitmap 用 tag("sword" / "shield" / "tree"),lookup 验证

完成标准:`cargo run` 用 tag 取出 bitmap,且 lookup 不存在的 tag 返回 None。

**参考解答**:

```rust
use std::collections::HashMap;

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
struct BitmapId(u32);

struct Bitmap {
    width: u32,
    height: u32,
    pixels: Vec<u32>,
    name: String,  // debug 用,反查 tag
}

struct AssetStore {
    bitmaps: Vec<Bitmap>,
    bitmap_tags: HashMap<String, BitmapId>,
}

impl AssetStore {
    fn new() -> Self {
        Self { bitmaps: Vec::new(), bitmap_tags: HashMap::new() }
    }

    fn add_bitmap_with_tag(&mut self, tag: &str, bmp: Bitmap) -> BitmapId {
        let id = BitmapId(self.bitmaps.len() as u32);
        self.bitmaps.push(bmp);
        self.bitmap_tags.insert(tag.to_string(), id);
        println!("  registered tag '{}' -> {:?}", tag, id);
        id
    }

    fn lookup_bitmap(&self, tag: &str) -> Option<BitmapId> {
        self.bitmap_tags.get(tag).copied()
    }

    fn get_bitmap_by_tag(&self, tag: &str) -> Option<&Bitmap> {
        let id = self.lookup_bitmap(tag)?;
        Some(&self.bitmaps[id.0 as usize])
    }

    fn get_bitmap(&self, id: BitmapId) -> &Bitmap {
        &self.bitmaps[id.0 as usize]
    }
}

fn main() {
    let mut store = AssetStore::new();

    // 加 3 个 bitmap
    store.add_bitmap_with_tag("sword", Bitmap {
        width: 64, height: 64,
        pixels: vec![0xff0000ff; 64*64],
        name: "sword".into(),
    });
    store.add_bitmap_with_tag("shield", Bitmap {
        width: 48, height: 48,
        pixels: vec![0x0000ffff; 48*48],
        name: "shield".into(),
    });
    store.add_bitmap_with_tag("tree", Bitmap {
        width: 32, height: 32,
        pixels: vec![0x00ff00ff; 32*32],
        name: "tree".into(),
    });

    // tag lookup
    println!("\nLookup 'sword': {:?}", store.lookup_bitmap("sword"));
    println!("Lookup 'tree':   {:?}", store.lookup_bitmap("tree"));
    println!("Lookup 'missing': {:?}", store.lookup_bitmap("missing"));

    // 通过 tag 取资产
    if let Some(bmp) = store.get_bitmap_by_tag("shield") {
        println!("\n'shield' bitmap: {}x{}, {} pixels",
                 bmp.width, bmp.height, bmp.pixels.len());
    }

    // hot path 演示:lookup 一次,缓存 id,后续用 id
    let sword_id = store.lookup_bitmap("sword").unwrap();
    println!("\nHot path simulation (cached id):");
    for frame in 0..5 {
        let bmp = store.get_bitmap(sword_id);  // 直接索引,无 hash
        println!("  Frame {}: render sword {}x{}", frame, bmp.width, bmp.height);
    }
}
```

## 8 · Rust / Arch 落地代码

完整可跑见 Lv2。benchmark:

```rust
use std::collections::HashMap;
use std::time::Instant;

fn bench_lookup() {
    let n = 10_000;
    let mut store = AssetStore::new();
    for i in 0..n {
        let tag = format!("asset_{}", i);
        store.add_bitmap_with_tag(&tag, Bitmap {
            width: 1, height: 1, pixels: vec![i as u32], name: tag.clone(),
        });
    }
    let lookup_tag = "asset_5000";
    let lookup_id = store.lookup_bitmap(lookup_tag).unwrap();

    // hot path:用 id
    let start = Instant::now();
    for _ in 0..1_000_000 {
        std::hint::black_box(store.get_bitmap(lookup_id));
    }
    let id_t = start.elapsed();

    // cold path:用 tag(每次 hash)
    let start = Instant::now();
    for _ in 0..1_000_000 {
        std::hint::black_box(store.lookup_bitmap(lookup_tag));
    }
    let tag_t = start.elapsed();

    println!("1M lookups by BitmapId: {} ms", id_t.as_millis());
    println!("1M lookups by tag:      {} ms", tag_t.as_millis());
    println!("Slowdown: {:.1}x", tag_t.as_secs_f64() / id_t.as_secs_f64());
}
```

**预期输出**:
```
1M lookups by BitmapId: 1 ms
1M lookups by tag:      250 ms
Slowdown: 250.0x
```

string lookup 比 id lookup 慢 100-500 倍,所以 hot path 一定要缓存 id。

## 10 · 深度推导:tag 系统的工程价值

今天 Casey 加了 string-to-id 映射。看起来简单,但背后有几个深层工程决策。这一节走通这些决策的"为什么"。

### 10.1 为什么 string tag 比直接用 enum 好?

直觉说 enum 更快(编译期常量,无 hash):

```rust
enum AssetTag {
    Sword,
    Shield,
    Tree,
    // ...
}
```

但 enum 有几个问题:

**问题 1:每次加资产要改代码**。美工加了 "potion" 图标,程序员要改 enum 加 Potion 变体,重新编译。不能从数据驱动。

**问题 2:跨模块 import 麻烦**。AssetTag 在哪个 crate?子模块怎么用?Rust 的 enum 跨 crate 需要 public re-export。

**问题 3:序列化难**。enum 要 serde 派生,序列化成字符串("Sword")还是数字(0)?字符串可读但慢,数字快但难 debug。

string tag 全部解决:

- 美工加 "potion" → 写代码 `"potion"`,不需改 enum
- 跨模块直接用 string literal
- 序列化天然是字符串

代价是 string lookup 比 enum match 慢。但 Casey 的模式是"启动时 lookup 一次,缓存 id",所以 hot path 没有这个代价。

### 10.2 为什么 tag 不用 const u32?

折中方案:

```rust
const SWORD_TAG: u32 = hash("sword");
```

启动时建立 `HashMap<u32, BitmapId>`,游戏代码用 SWORD_TAG 查询。string lookup 变 u32 lookup,快很多。

**但有问题**:hash 碰撞。两个不同 string 哈希成同一个 u32,会冲突。要处理碰撞就要存原始 string,退化为 string-to-id。

工业方案:**string interning**。所有 string 在启动时收集到表里,分配唯一 u32 symbol:

```rust
let sword_sym = interner.get_or_intern("sword");  // Symbol(42)
let map: HashMap<Symbol, BitmapId> = ...;
let bmp = map.get(&sword_sym);
```

Symbol 是 u32,无碰撞(interner 保证)。`string_interner` crate 实现完整方案。

Bevy 的 `AssetPath` 内部就是 interned symbol。Casey 没走这么远,因为 HH 的 tag 数量小,直接 string lookup 就够。

### 10.3 Tag 拼写错误的防御

string tag 的最大痛点:**拼错要运行时才发现**。

```rust
store.lookup_bitmap("sowrd");  // typo! 返回 None,渲染时 panic
```

防御方案:

**方案 1:编译期检查**。用 macro 把 string 转成 BitmapId const:

```rust
asset_path!("sword");  // 编译期检查 "sword" 是否在 asset manifest
```

需要 build script 扫描 asset 目录生成 manifest。复杂但最安全。

**方案 2:启动时 verify**。load 时检查所有 hardcoded tag 是否存在,缺失就 panic:

```rust
fn verify_tags(store: &AssetStore) {
    for tag in ["sword", "shield", "tree"] {
        if store.lookup_bitmap(tag).is_none() {
            panic!("Missing required asset tag: {}", tag);
        }
    }
}
```

启动失败比运行时 panic 好——你立刻知道资产漏了。

**方案 3:测试覆盖**。每个 tag 在测试里 lookup 一次,缺失则测试失败。

工业代码组合 2 + 3。Bevy 的 `AssetServer::get_handle` 在 release 不检查(性能),在 debug 检查。

### 10.4 Tag 与反射

tag 系统天然适合反射——通过 string name 访问数据。游戏 debug overlay 大量用:

```rust
// Debug overlay:显示所有 "player_*" tag 的资产
for tag in store.tags_starting_with("player_") {
    let bmp = store.get_bitmap_by_tag(tag).unwrap();
    draw_debug_thumbnail(bmp);
}
```

这种"按 prefix 查找"是 day136+ 的 inverted index。今天 Casey 只做了 1-1 映射,但骨架已经搭好。

### 10.5 hot path / cold path 的具体数字

我用 Day 134 Lv2 的 bench 给个实测数字:

- 1M BitmapId lookup:**~1 ms**(数组索引,~1 ns/op)
- 1M tag lookup:**~250 ms**(hash + HashMap 探测,~250 ns/op)

差距 **250x**。如果 hot path 用 tag lookup,60 FPS × 1000 sprite = 60000 lookup/frame × 250 ns = 15 ms/frame,**直接卡到 30 FPS**。这是为什么 Casey 反复强调"hot path 用 id,cold path 用 tag"。

### 10.6 完整的 tag 系统代码

```rust
use std::collections::HashMap;
use std::time::Instant;

#[derive(Copy, Clone, Debug, Eq, PartialEq, Hash)]
pub struct BitmapId(pub u32);

pub struct Bitmap {
    pub width: u32,
    pub height: u32,
    pub pixels: Vec<u32>,
    pub debug_name: String,
}

pub struct AssetStore {
    bitmaps: Vec<Bitmap>,
    tags: HashMap<String, BitmapId>,
}

impl AssetStore {
    pub fn new() -> Self {
        Self {
            bitmaps: Vec::new(),
            tags: HashMap::new(),
        }
    }

    pub fn add(&mut self, tag: &str, bmp: Bitmap) -> BitmapId {
        let id = BitmapId(self.bitmaps.len() as u32);
        if self.tags.insert(tag.to_string(), id).is_some() {
            eprintln!("Warning: duplicate tag '{}', overwriting", tag);
        }
        self.bitmaps.push(bmp);
        id
    }

    pub fn lookup(&self, tag: &str) -> Option<BitmapId> {
        self.tags.get(tag).copied()
    }

    pub fn get(&self, id: BitmapId) -> &Bitmap {
        &self.bitmaps[id.0 as usize]
    }

    pub fn get_by_tag(&self, tag: &str) -> Option<&Bitmap> {
        self.lookup(tag).map(|id| self.get(id))
    }

    /// 启动时验证:所有必需 tag 都存在
    pub fn verify_tags(&self, required: &[&str]) -> Result<(), String> {
        for tag in required {
            if !self.tags.contains_key(*tag) {
                return Err(format!("Missing required tag: {}", tag));
            }
        }
        Ok(())
    }
}

fn main() {
    let mut store = AssetStore::new();

    // 启动时加 asset
    store.add("sword", Bitmap {
        width: 64, height: 64,
        pixels: vec![0xff0000ff; 64 * 64],
        debug_name: "sword_icon".into(),
    });
    store.add("shield", Bitmap {
        width: 48, height: 48,
        pixels: vec![0x0000ffff; 48 * 48],
        debug_name: "shield_icon".into(),
    });

    // 验证必需 tag
    store.verify_tags(&["sword", "shield"]).unwrap();

    // 启动时 lookup 一次,缓存 id(hot path 用 id)
    let sword_id = store.lookup("sword").expect("sword must exist");

    // hot path:用 id,~1 ns/lookup
    let start = Instant::now();
    for _ in 0..1_000_000 {
        std::hint::black_box(store.get(sword_id));
    }
    println!("1M BitmapId lookups: {:?}", start.elapsed());

    // cold path:用 tag,~250 ns/lookup
    let start = Instant::now();
    for _ in 0..1_000_000 {
        std::hint::black_box(store.lookup("sword"));
    }
    println!("1M tag lookups:      {:?}", start.elapsed());
}
```

跑起来你能直观看到 hot/cold path 的差异。这是 Day 134 的核心教学点。

## 11 · 工业级的额外考量

### 11.1 Localization:多语言 tag

```rust
// 多语言 tag
let sword_en = store.lookup("sword_en");
let sword_zh = store.lookup("sword_zh");
let sword_jp = store.lookup("sword_jp");
// 按 locale 选
let current_sword = match locale {
    Locale::EN => sword_en,
    Locale::ZH => sword_zh,
    Locale::JP => sword_jp,
};
```

或者更优雅:`HashMap<(String, Locale), BitmapId>`,key 是 (tag, locale) pair。

### 11.2 Asset variants

同一 tag 多个变体(高质量 / 低质量):

```rust
let sword_hq = store.lookup("sword@hq");
let sword_lq = store.lookup("sword@lq");
```

按设备性能选 variant。商业游戏(console vs PC vs mobile)常用。

### 11.3 Hot reload

改 PNG 文件后,store 自动重新加载。tag 映射不变,只是 BitmapId 对应的 Bitmap 数据更新。

```rust
// file watcher 检测变化
notify::watch(...).on_modify(|path| {
    let tag = path_to_tag(path);
    let new_bmp = parse_png(path);
    let id = store.lookup(tag).unwrap();
    store.bitmaps[id.0 as usize] = new_bmp;  // 替换数据
});
```

Bevy 内置这套。
