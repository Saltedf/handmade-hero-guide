## 0 · 为什么要有这一天

CPU 单核速度过去 20 年没怎么提升(Pentium 4 3GHz 和现在的 i9 5GHz,IPC 提升靠 cache / SIMD,不是频率)。但**核心数从 1 涨到 16**,继续涨。

要利用多核,你必须**并行写代码**。但并行编程极难:

- **数据竞争**(data race):两个线程同时写同一个变量,值不确定
- **死锁**(deadlock):两个线程互相等锁,永久卡住
- **活锁**(livelock):两个线程互相避让,谁都没进展
- **竞态条件**(race condition):结果依赖线程调度顺序

这些 bug 的特点是:**单线程跑没问题,多线程随机崩,且每次崩的地方不一样**。调试极难。一个项目从单线程切多线程,如果没有充分准备,可能要花数周 debug。

心理锚点:读完这一天,你能:

## 2 · 心智模型

### 2.1 类比:办公室协作

想象一个办公室,有 8 个员工(= 8 个 CPU 核)。每个员工有自己的:

- 大脑(= 寄存器 + L1 cache)
- 桌面(= L2 cache)
- 公共白板(= 共享内存 / DRAM)

#### 单线程 = 1 个人工作

所有任务由 1 个人做。简单,但慢:办公室效率只用了 1/8。

#### 多进程 = 8 个独立办公室

8 个员工在 8 个独立办公室,各自工作,通信要"打电话"(= IPC,inter-process communication,如管道、socket、共享内存)。

优点:隔离好,一个办公室出问题不影响别的。
缺点:通信开销大,启动办公室慢(进程启动 = 几十毫秒)。

#### 多线程 = 1 个办公室 8 个人

8 个员工共享一个公共白板。所有人能看 / 写白板。

优点:通信快(直接读写白板),启动快(线程启动 = 几十微秒)。
缺点:**白板上写冲突**(= data race)。

游戏开发几乎全用多线程(性能要求高,通信密集)。

### 2.2 线程是什么

Linux 上,线程和进程**本质相同**(都是 task),区别在于是否共享内存:

- **进程**:独立内存空间(`fork()` 创建子进程,`exec()` 加载新程序)
- **线程**:共享父进程的内存空间(`pthread_create` 或 `clone()` 创建)

Linux 内核里都用 `task_struct` 表示,只是 `clone()` 时传的 flag 不同:

- `clone(CLONE_VM | CLONE_FS | ...)`:共享内存 → 线程
- `clone(...)` 不带 `CLONE_VM`:不共享 → 进程

#### 用户态线程 vs 内核态线程

Linux 的"1:1 模型":每个用户线程对应 1 个内核线程。调度由内核做。

其他操作系统有 M:N 模型(M 个用户线程在 N 个内核线程上跑,如 Go 的 goroutine、Erlang 的 process、Rust 的 async task)。但 HH 用 1:1(简单、可预测)。

### 2.3 数据竞争

```rust
// 错误代码!data race
static mut COUNTER: i32 = 0;

fn main() {
    let t1 = std::thread::spawn(|| {
        for _ in 0..1000000 { unsafe { COUNTER += 1; } }
    });
    let t2 = std::thread::spawn(|| {
        for _ in 0..1000000 { unsafe { COUNTER += 1; } }
    });
    t1.join().unwrap();
    t2.join().unwrap();
    println!("counter: {}", unsafe { COUNTER });  // 应该 2000000,实际可能 1342112
}
```

为什么?`COUNTER += 1` 不是原子操作,它是 3 步:

1. 读 COUNTER 到寄存器
2. 寄存器 +1
3. 写回 COUNTER

两个线程可能交错:

```
Thread 1: read COUNTER (= 0)
Thread 2: read COUNTER (= 0)
Thread 1: reg = 1
Thread 2: reg = 1
Thread 1: write COUNTER = 1
Thread 2: write COUNTER = 1
```

最终 COUNTER = 1,而不是 2。这就是 data race。

### 2.4 同步原语

#### Mutex(互斥锁)

```rust
use std::sync::Mutex;

let counter = Mutex::new(0);
let t1 = std::thread::spawn({
    let counter = counter.clone();  // 实际需要 Arc
    move || {
        for _ in 0..1000000 {
            let mut c = counter.lock().unwrap();
            *c += 1;
        }
    }
});
```

`Mutex::lock()` 等待其他线程 unlock,然后获取锁。被锁住的代码段同一时刻只能 1 个线程进入。

问题:**mutex 慢**。一次 lock + unlock 几百纳秒,如果热循环里每加 1 都 lock,严重拖慢。

#### Atomic

```rust
use std::sync::atomic::{AtomicI32, Ordering};

let counter = AtomicI32::new(0);
let t1 = std::thread::spawn({
    let counter = std::sync::Arc::new(counter);  // Arc 共享
    move || {
        for _ in 0..1000000 {
            counter.fetch_add(1, Ordering::Relaxed);
        }
    }
});
```

`AtomicI32::fetch_add` 是**原子操作**:不可被打断的"读 + 修改 + 写"。硬件保证 atomic。

速度比 mutex 快很多(10-50ns vs 几百 ns)。但只能用在单个变量的简单操作。

#### Condition Variable

```rust
use std::sync::{Condvar, Mutex};

let pair = Mutex::new(false);
let cond = Condvar::new();

// 线程 A:等待
let mut started = pair.lock().unwrap();
while !*started {
    started = cond.wait(started).unwrap();
}

// 线程 B:通知
*pair.lock().unwrap() = true;
cond.notify_one();
```

`Condvar::wait` 释放锁 + 睡眠,`notify_one` 唤醒等待者。用于"等条件成立"的场景。

#### Semaphore

Semaphore 是更通用的同步原语(允许 N 个线程同时进入某段)。Rust 标准库没有直接提供,但可以用 Mutex + Condvar 实现。`parking_lot` crate 提供。

### 2.5 内存序(Memory Ordering)

这是多线程最难的概念。先看问题:

```rust
// 线程 1
data = 42;          // (A) 写数据
ready = true;       // (B) 标志

// 线程 2
if ready {          // (C) 读标志
    print(data);    // (D) 读数据 —— 一定是 42 吗?
}
```

直觉上,D 应该读到 42。**但实际可能读到 0!**

原因:

1. **CPU 重排**:CPU 和编译器可能把 A 和 B 重排(B 先执行,A 后执行)
2. **缓存可见性**:线程 1 写 A 到自己的 L1,但还没刷到 L2/L3,线程 2 看不到

要保证"D 一定读到 42",需要正确的**内存序**。

#### Rust 的 5 个 Ordering

`AtomicI32::store` / `load` / `fetch_add` 都接受 `Ordering` 参数:

| Ordering | 含义 | 何时用 |
|---|---|---|
| `Relaxed` | 只保证本操作原子,不保证和其他操作的顺序 | 计数器(fetch_add) |
| `Release` | 写操作。本操作之前的所有写,对其他线程的 Acquire 操作可见 | 发布数据 |
| `Acquire` | 读操作。本操作之后的所有读,看到 Release 之前的写 | 读数据 |
| `AcqRel` | 同时是 Acquire + Release(read-modify-write) | RMW |
| `SeqCst` | 全局顺序,最强保证 | 需要全局一致性时 |

回到上面例子,正确的写法:

```rust
// 线程 1
data = 42;
ready.store(true, Ordering::Release);  // Release:之前的写在所有看到 ready=true 的线程里都生效

// 线程 2
if ready.load(Ordering::Acquire) {     // Acquire:看到 ready=true 后,后续读看到 Release 之前的写
    print(data);  // 一定是 42
}
```

`Release + Acquire` 是经典的"发布 - 订阅"模式。

#### 为什么不全部 SeqCst

SeqCst 最强,但代价最大(可能 5-10 倍 atomic 操作开销)。Relaxed 最便宜,但不保证顺序。

**经验**:从 Relaxed 开始,看场景升级。

- 计数器(stats):Relaxed
- 发布数据:Release
- 等待数据:Acquire
- 跨线程复杂协议:SeqCst

Day 124 详细讲。

### 2.6 lock-free vs wait-free

- **blocking**(mutex):线程可能被阻塞(等其他线程 unlock)
- **lock-free**:至少 1 个线程能进展(用 CAS、atomic)
- **wait-free**:所有线程都能进展(更强的保证)

HH 的 work queue(Day 125+)是 lock-free。性能比 blocking 高,但实现复杂。

### 2.7 多线程的代价

虽然多核能加速,但也有开销:

- **同步开销**:lock / atomic / fence 周期
- **cache 失效**:线程切换核时,数据要重新加载
- **false sharing**:两个线程写同一条 cache line,导致 cache line 不停"穿梭"
- **scheduler 开销**:OS 调度线程有成本

所以**不是越多线程越快**。HH 用"核心数"线程(8 核 CPU 用 8 线程),不多不少。

## 4 · 认知地图

### 4.1 上级

- **并行计算** —— 多个任务同时进行
- **并发编程**(concurrent programming)—— 多个任务的"逻辑"同时,可能物理上交替执行

#### 并行 vs 并发

- **并行**(parallel):物理同时执行(多核)
- **并发**(concurrent):逻辑同时,可能交替(单核时间片)

单核 CPU 也能"并发"(时间片轮转),但不能"并行"。多核 CPU 两者都行。

### 4.2 同级

| 同步原语 | 关键差别 | 何时用 |
|---|---|---|
| Mutex | 阻塞,简单 | 大部分场景 |
| Atomic | 非阻塞,简单操作 | 计数器、flag |
| Condvar | 等条件成立 | 生产者-消费者 |
| Channel | 消息传递 | actor 模型 |
| SeqLock | 读多写少 | 统计数据 |
| RCU | 读极多写极少 | Linux 内核 |

### 4.3 下级

- **线程 / 进程** —— 执行单元
- **共享内存** —— 线程间的"祸根"
- **原子指令**(x86:lock 前缀、cmpxchg)—— atomic 的硬件基础
- **内存屏障**(mfence、lfence、sfence)—— 内存序的硬件基础
- **CPU 缓存层级** —— cache coherence 协议(MESI)

### Lv1 · 概念辨析

**题**:下面代码有什么 bug?

```rust
let mut data = vec![1, 2, 3, 4];
let t = std::thread::spawn(|| {
    println!("{:?}", data);
});
t.join().unwrap();
```

**参考解答**:`data` 是 `&mut`,线程闭包要 `move ||` 才能拿走所有权。否则编译错误(E0373)。即使加了 `move`,如果 main 提前 drop 了 data(理论上不会,join 在前),也会有 UAF。

正确:

```rust
let data = vec![1, 2, 3, 4];
let t = std::thread::spawn(move || {
    println!("{:?}", data);
});
t.join().unwrap();
```

## 8 · Rust / Arch 落地代码

### Rust:多线程基础

```rust
use std::sync::Arc;
use std::sync::atomic::{AtomicI32, Ordering};
use std::sync::Mutex;
use std::thread;

fn main() {
    // 方式 1:Mutex
    let counter_mutex = Arc::new(Mutex::new(0));
    let handles: Vec<_> = (0..8).map(|_| {
        let c = counter_mutex.clone();
        thread::spawn(move || {
            for _ in 0..1_000_000 {
                let mut g = c.lock().unwrap();
                *g += 1;
            }
        })
    }).collect();
    for h in handles { h.join().unwrap(); }
    println!("Mutex: {}", *counter_mutex.lock().unwrap());

    // 方式 2:Atomic Relaxed
    let counter_atomic = Arc::new(AtomicI32::new(0));
    let handles: Vec<_> = (0..8).map(|_| {
        let c = counter_atomic.clone();
        thread::spawn(move || {
            for _ in 0..1_000_000 {
                c.fetch_add(1, Ordering::Relaxed);
            }
        })
    }).collect();
    for h in handles { h.join().unwrap(); }
    println!("Atomic Relaxed: {}", counter_atomic.load(Ordering::Relaxed));

    // 方式 3:scoped(简化代码)
    let mut data = vec![0i32; 8];
    thread::scope(|s| {
        for i in 0..8 {
            s.spawn(|| {
                for _ in 0..1_000_000 {
                    data[i] += 1;  // 每线程写不同 index,无竞争
                }
            });
        }
    });
    println!("Scoped: {:?}", data.iter().sum::<i32>());
}
```

## 10 · 深度推导:从单线程到多线程的迁移路径

你今天开始多线程化 tile 渲染。这不是"加个线程就行"——从单线程架构到多线程,有 6 个具体决策要做。这一节把这 6 个决策走通,你才真正理解 Casey 为什么做这些选择。

### 10.1 决策 1:多少个线程?

直觉说"有几核就开几线程"。但这个直觉有三个偏差:

**偏差 1**:CPU 报告的核数 = 物理核 + 超线程。8 核 i7 报 16 个,但超线程不给你 2x 算力——只 ~1.3x(共用 ALU / cache)。所以你应该开"物理核数"线程,不是"逻辑核数"。

**偏差 2**:操作系统调度。你开 8 线程,但 OS 给你"8 线程分享 7 个 slot"——因为别的进程也占 CPU。所以开 8 线程的实测可能只 7x 加速,不是 8x。

**偏差 3**:CPU frequency。所有核同时跑满,CPU 散热吃紧,turbo 降频。8 核全开可能跑 4 GHz,单核跑 5 GHz。所以 8 核加速比可能 < 8x(实际 6-7x)。

Casey 的选择:**开 N = 物理核数线程**。8 核 i7 开 8 线程。Rust 用 `num_cpus::get_physical()`:

```rust
let num_workers = num_cpus::get_physical();
// 警告:有些 CPU 报告不准。Linux 看 /proc/cpuinfo 的 "core id" 唯一值数。
```

### 10.2 决策 2:用什么同步原语?

**朴素方案**:全局 mutex 包住"取下一个 tile"。Worker lock-unlock-lock-unlock... 但 mutex 至少 ~50ns/op,510 tile = 25 μs。看起来小,但每帧 25 μs × 60 fps = 1.5 ms/s 浪费 CPU。

**条件变量方案**:worker 在 condvar 上 sleep,主线程 notify_one。每次 notify ~5 μs(kernel 调度)。比 mutex 好,但仍不便宜。

**Semaphore 方案**:semaphore 内部用 futex(fast userspace mutex),空队列时不进 kernel。Rust 的 `crossbeam::deque` 或自实现都是这思路。

**Lock-free atomic 方案**:`AtomicUsize` 作为 next tile index,worker `fetch_add(1)` 拿下一个。fetch_add 空 queue 时只 5-10 ns,完全 userspace。**这是 Casey 用的方案**。

为什么 mutex 不能用?不是性能——是因为 mutex 阻塞,而你想 worker 永远跑(fetch_add 永远返回,即便值是 N+1,worker 检查 "out of range" 自己退出)。这是 lock-free 的本质:**不阻塞,靠原子操作 + 协议**。

### 10.3 决策 3:工作怎么分配?

**Static split**:把 510 tile 预分成 8 份,每份 64 tile,worker i 处理第 i 份。简单,但**负载不均**——某些 tile 有很多 sprite 要画(复杂),某些 tile 是空地(简单)。复杂 tile 拖累整个 frame。

**Dynamic dispatch**:全局 work queue,worker fetch_add 拿下一个。**负载自均衡**——忙 worker 自动慢 fetch,闲 worker 自动多 fetch。这是 Casey 用的方案。

**Work stealing**:每个 worker 有自己的本地 queue,worker 优先处理本地,本地空时去"偷"别人的。比 dynamic dispatch 更进一步,但实现复杂。Rayon 用这套,Casey 的 day125 也演化到这。

### 10.4 决策 4:Worker 线程是"per-frame 创建"还是"持久"?

**Per-frame 创建**:每帧 spawn 8 线程,等他们结束。简单但**线程创建开销 ~50 μs × 8 = 400 μs/frame × 60 fps = 24 ms/s 浪费**。不能接受。

**持久线程池**:启动时 spawn 8 线程,他们阻塞在 condvar 上等任务。主线程 push 任务到 queue,notify_all,worker 跑完后阻塞等下一帧。**这是工业标准**。

Casey 用持久线程池。Rust 标准库 `std::thread::scope` 或 `rayon::ThreadPool` 都提供这个。

### 10.5 决策 5:怎么知道所有 worker 完成?

主线程 push 510 task,worker 处理。主线程怎么知道"全部完成"?

**朴素 join**:主线程 join 所有 worker 线程。但 worker 是持久的——你不希望它们结束。

**Counter**:AtomicUsize counter = 510。worker 每完成一个 task,fetch_sub(1)。counter 到 0 时主线程 condvar.notify。主线程 wait condvar。

**Future**:每个 task 返回 future,join_all。最优雅但内存开销大。

Casey 用 counter 方案。简单可靠。

### 10.6 决策 6:数据怎么共享?

主线程有 assets 数据,sprite 数据,framebuffer。worker 要访问这些。

**Clone**:每个 worker 复制一份数据。简单但内存爆炸——10 GB assets × 8 worker = 80 GB。不行。

**Arc<Mutex>**:全局共享,worker lock 然后 read。但 mutex 慢。

**Arc + immutable**:数据是 immutable 的(assets 不会改),worker 通过 Arc 共享只读。**这是 Casey 的方案**。Arc 让多线程持有共享 ref,immutable 让无锁读取。

只有 framebuffer 是 mutable。但每个 tile 有自己的区域,worker A 写 tile 0,worker B 写 tile 1,互不冲突。所以 framebuffer 用 `UnsafeCell` + 协议保证"不重叠写"。

### 10.7 综合:这 6 个决策汇总成完整代码骨架

```rust
pub struct TileRenderer {
    workers: Vec<JoinHandle<()>>,
    queue: Arc<WorkQueue>,
    next_frame_signal: Arc<(Mutex<bool>, Condvar)>,
    completion: Arc<AtomicUsize>,
}

impl TileRenderer {
    pub fn new(assets: Arc<Assets>) -> Self {
        let queue = Arc::new(WorkQueue::new());
        let completion = Arc::new(AtomicUsize::new(0));
        let signal = Arc::new((Mutex::new(false), Condvar::new()));

        let num_workers = num_cpus::get_physical();
        let mut workers = Vec::with_capacity(num_workers);
        for _ in 0..num_workers {
            let q = Arc::clone(&queue);
            let c = Arc::clone(&completion);
            let s = Arc::clone(&signal);
            let a = Arc::clone(&assets);
            workers.push(thread::spawn(move || {
                worker_main(q, c, s, a);
            }));
        }
        Self { workers, queue, next_frame_signal: signal, completion }
    }

    pub fn render_frame(&self, camera: &Camera, framebuffer: &mut Framebuffer) {
        // 重置 completion counter
        self.completion.store(0, Ordering::Release);
        let total = push_all_tiles(&self.queue, camera, framebuffer);
        // 唤醒所有 worker
        let (lock, cvar) = &*self.next_frame_signal;
        let mut done = lock.lock().unwrap();
        *done = true;
        cvar.notify_all();
        // 等所有 tile 完成
        while self.completion.load(Ordering::Acquire) < total {
            // 自旋等待(或 condvar wait)
            std::hint::spin_loop();
        }
        // 下一帧前重置 signal
        *done = false;
    }
}

fn worker_main(
    queue: Arc<WorkQueue>,
    completion: Arc<AtomicUsize>,
    signal: Arc<(Mutex<bool>, Condvar)>,
    assets: Arc<Assets>,
) {
    loop {
        // 等待主线程 signal
        let (lock, cvar) = &*signal;
        let mut started = lock.lock().unwrap();
        while !*started {
            started = cvar.wait(started).unwrap();
        }
        // 跑 task 直到 queue 空
        while let Some(task) = queue.pop() {
            task.run(&assets);
            completion.fetch_add(1, Ordering::Release);
        }
    }
}
```

这个骨架是 Day 122-125 的演化目标。今天(day122)你只做了前一半(线程池 + signal),Day 123 加 memory ordering,Day 124 加 happens-before 关系,Day 125 把 queue 抽象出来。

## 11 · 多线程化的 5 个常见陷阱

工业级多线程代码踩过的坑,你也会踩。提前知道:

### 陷阱 1:False sharing

两个线程修改"相邻内存"会触发 cache line bouncing。即便它们修改不同变量:

```rust
struct Counters {
    a: AtomicU64,   // 线程 0 写
    b: AtomicU64,   // 线程 1 写
}
// a 和 b 在同一 cache line(64 字节),写 a 让 b 的 cache invalid,
// 线程 1 要从主存重新读 b,慢 100x。
```

修复:用 `#[repr(align(64))]` 让每个 counter 独占 cache line。

### 陷阱 2:Lock-free 不是免费

```rust
let next = queue.head.fetch_add(1, Ordering::Relaxed);
```

fetch_add 是原子操作,5-10 ns。但**510 tile × 5 fetch_add/tile = 2550 ops/frame × 60 fps = 153K ops/s**。看起来小,但 cache bouncing 让多核 fetch_add 慢 3-10x。Worker 越多,bouncing 越严重。

解决:work stealing(每 worker 自己 queue,跨线程操作少)。

### 陷阱 3:Memory ordering 错误

```rust
// 错误:用了 Relaxed 但需要 Release/Acquire
self.completion.store(0, Ordering::Relaxed);  // 这里应该是 Release
worker 读 completion 用 Acquire
```

Relaxed 不建立 happens-before。如果 store 用 Relaxed,worker 可能"看到 completion=0 但旧数据"(因为 cache 重排)。**Day 123-124 专门讨论这个**。

### 陷阱 4:ABBA deadlock

主线程 lock A,worker lock B,然后主线程要 lock B,worker 要 lock A——deadlock。

防御:全局 lock 顺序。Casey 用 lock-free queue 完全避免 lock,但 condvar 还是要 lock。确保 condvar lock 不和 queue 操作嵌套。

### 陷阱 5:Worker spawn 失败

`std::thread::spawn` 在 Linux 默认 stack 8 MB。如果你开 100 worker,虚拟内存吃 800 MB。虚拟内存不消耗实际 RAM 但 ulimit 可能限制。

修复:用 `thread::Builder::new().stack_size(256.kb()).spawn(...)` 减小 stack。
