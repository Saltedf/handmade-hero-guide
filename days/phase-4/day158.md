
# Day 158 · 跟踪资产使用

> 玩家进入关卡,加载了 50 MB asset——贴图、模型、音效、字体。玩家通关,退出关卡回到主菜单。你打开任务管理器,游戏还占着 1.8 GB 内存——关卡卸载了,asset 没释放。再进再出三次,内存涨到 3.2 GB,系统开始 swap,游戏帧率从 144 掉到 22。今天 Casey 给 AssetStorage 加 **asset usage tracking**:每个 loaded asset 挂一个引用计数,谁用谁 inc,不用 dec,计数归零就 unload。再进再出一万次,内存稳定在 350 MB。

## 0 · 为什么要有这一天

让我们先把这个问题**还原成一个具体场景**,然后再讨论为什么这件事"难"。

你跟着 Handmade Hero 走到 Day 157。你的 AssetStorage 大概长这样:

```rust
struct AssetStorage {
    bitmaps: Vec<LoadedBitmap>,
    sounds: Vec<LoadedSound>,
    fonts: Vec<LoadedFont>,
}
```

游戏代码用 asset 时,直接 `storage.bitmaps[player_texture_id]` 拿到一份 `&LoadedBitmap`。加载和卸载完全由你手工控制——你写 `load_texture("player.png")`,它返回一个 index,你存到玩家结构体里。问题来了:**什么时候 unload**?

第一反应是"关卡退出时 unload 关卡所有 asset"。听起来合理,但马上撞到三个真实工程问题:

**第一,asset 共享**。玩家的"开火音效"和敌人 NPC 的"开火音效"是同一个 asset(`sound/fire.wav`)。玩家先在关卡里用了——index 7。关卡退出时你想 unload——但玩家不在关卡里时,主菜单的"按钮点击音效"还在用 index 7?你给每个 asset 标个"哪个系统在用"的标志?那 N 个系统 × M 个 asset = N*M 个标志,状态爆炸。

**第二,异步 streaming**。Day 156 你做了 asset streaming——背景线程加载 asset,主线程消费。当主线程"想用"一个 asset 时,可能:(a) 已加载完,直接拿;(b) 正在加载,要等;(c) 还没排队加载,要排队。这三种状态组合 × 多个引用方,手工管理 inc/dec 几乎不可能不出错。

**第三,double-free / use-after-free**。最隐蔽的 bug。两个系统都持有 index 7。系统 A 觉得"我用完了"调 unload。系统 B 这时还在用——读到 garbage data,崩溃。或者更糟:不崩溃,渲染出几张错乱的纹理,玩家截图发推特嘲笑你。

工业界的标准答案叫 **reference counting**(引用计数)。每个 loaded asset 挂一个数字 `ref_count`,语义是"目前有多少处代码在用我"。规则极简:
- 谁要用,**先 inc**(计数 +1)
- 谁用完了,**dec**(计数 -1)
- 计数归零,**unload**

这个方案的优雅之处在于**完全分布式**——没有任何一个全局函数知道"现在谁在用 asset 7"。每个使用者只管自己:拿到时 inc,放下时 dec。系统不会知道"我退出时该 unload 哪些 asset",因为它从一开始就没"unload"——它只是 dec,dec 到 0 自然 unload。

引用计数有三种实现风格,各有 trade-off:

**Style 1 — Manual inc/dec**:游戏代码显式调用 `storage.inc_ref(id)` / `storage.dec_ref(id)`。C 程序员的日常。优点是零开销、完全显式。缺点是**极易出错**——忘 dec 就 leak;double dec 就 underflow(use-after-free);多线程下 inc/dec 不原子就 race。Casey 在 Handmade Hero 原版 C 代码用的就是这套,他自己也经常在视频里抱怨"我又忘了 release 那个 sound"。

**Style 2 — RAII(C++ / Rust)**:用 `Arc<T>`(Rust)或 `std::shared_ptr<T>`(C++)这种"智能指针",编译器在每个引用方 drop 时自动 dec。优点是**忘不了**——只要持有 `Arc`,计数就不会归零;只要 drop 触发,计数必然 dec。缺点是 atomic 操作有 ~5ns 开销(多线程时),并且对 cycle 引用无能为力(A 引用 B,B 引用 A,两者永不到 0)。

**Style 3 — Scope-based**:某些语言(Python 的 `with`、C# 的 `using`、Rust 的 `{ let _h = storage.get(id); ... }`)在 scope 退出时自动 release。本质是 Style 2 的语法糖,但限制是引用不能"逃出 scope"——你必须明确知道 asset 在哪个 scope 用完。这对游戏代码很不方便,因为"玩家拿的武器贴图"这种 asset 跨越多帧、跨越函数调用,不属于任何单一 scope。

Rust 的标准答案是 **Style 2**——`Arc<LoadedAsset>` + RAII Drop。Casey 在 HH 原版用 Style 1(因为 C),Rust 移植版会自然用 Style 2。今天我们就走 Style 2 的路子。

但 Style 2 自己也有一个微妙的 trap:**slot 复用导致 stale handle**。设想:

1. 你 `get(texture_id=7)`,storage 给你 `Arc` 指向 slot 7,里面是 "player.png"
2. 所有引用方 drop,ref_count=0,slot 7 unload
3. 你加载新 asset "enemy.png",storage 复用 slot 7(因为 7 是空闲的)
4. 某个旧代码(比如一个延迟的 callback)还持有旧的 `AssetHandle { id: 7 }`,去 get,storage 返回 "enemy.png"——**完全错的 asset**!

这就是为什么工业实现还要加一层 **generation**(代际号)。每个 slot 有个 generation 计数,每次 unload 时 +1。Handle 不只存 `id`,还存创建时的 generation。get 时检查 slot 当前 generation == handle 的 generation,不一致就返回 None(stale handle)。

所以今天我们要建立四层心智:
1. **Reference counting**——核心机制
2. **RAII Drop 自动 dec**——防忘性 bug
3. **LRU eviction**(可选)——防止抖动
4. **Generation**——防 slot 复用导致的 stale handle

这一层套一层看起来复杂,但每一层都解决一个具体的真实 bug。学完今天,你应该能:
- 解释为什么"手工 unload"在游戏工程里不可行
- 用 Rust 的 `Arc<T>` 实现一个引用计数 asset cache
- 解释 LRU 相比"立即 unload"的优势
- 用 generation 防止 stale handle bug
- 看懂工业引擎(Unreal、Unity Addressables、Bevy Handle)的 asset 管理代码

## 2 · 心智模型

### 2.1 类比:图书馆借书

让我打个比方,把这套抽象钉在你脑子里。

你是一个大学图书馆管理员。馆里有 1 万本书,但书架只有 1000 个位。书的命运分两种:

- **热书**:学生借出、归还、又借出,循环不止
- **冷书**:几个月没人借

图书馆的物理约束:书架满时,新书进不来。所以管理员有一套**自动驱逐策略**——每隔几天扫一遍,把"几个月没人借"的书从书架撤下,放回地下仓库。仓库是无限的,但取书慢(要花 30 秒从地下层取上来)。

学生借书时:
- 如果书在书架上(热):1 秒拿到,在借书卡上记一笔(引用 +1)
- 如果书在仓库(冷):管理员从仓库取,放回书架,30 秒
- 书架上没人借这本书(引用 0):管理员标记为 "evictable",下次驱逐时可能撤下

学生还书时:
- 在借书卡上勾掉一笔(引用 -1)
- 如果引用归零,书变成 evictable,但**不立刻撤**——可能明天还有人借,留在书架上等驱逐策略触发

这套机制完美映射到 asset cache:
- **图书馆** = AssetStorage
- **书** = LoadedAsset(texture / sound / font)
- **书架** = RAM 中的 cache
- **仓库** = 磁盘(asset 原始文件)
- **借书卡计数** = ref_count
- **书架空位** = memory budget
- **驱逐策略** = LRU

这个比方的核心洞察:**借书 / 还书是学生自治的**——图书馆员从不"问学生还用不用"。学生借时自己刷卡,还时自己刷卡。图书馆员只看汇总的借书卡计数,决定驱逐。

代码也是这样。AssetStorage 不"问"游戏系统"你还用不用这个贴图"。游戏代码用 `Arc` 持有 asset,Drop 时自动 dec。AssetStorage 只看 ref_count 汇总,决定何时驱逐。这种"分布式 ownership"是引用计数的精髓。

### 2.2 第一性原理推导:为什么不能用别的方案?

你可能问:为什么非要用引用计数?**别的方案不行吗**?让我严肃讨论三个替代方案,你会看到为什么它们都败给 ref count。

**替代一:GC(垃圾回收)**。Java / Go / C# 的方案。GC 周期性扫描整个堆,识别"不可达"对象并释放。

游戏不能用的原因有三条。第一,**pause**。GC stop-the-world 时,游戏主循环停 50ms,玩家直接感知卡顿。即便 Go 的低延迟 GC(亚毫秒级 pause),也难以保证 16.67ms 帧预算稳定。第二,**不可预测的内存峰值**。GC 触发时机不确定,可能在玩家激战正酣时触发,而触发前堆已经涨到峰值——这峰值可能让 4 GB 内存机器直接 OOM。第三,**asset 不是普通对象**。GC 管的是托管堆上的对象,但 asset 的真实存储是 GPU VRAM / audio buffer——GC 看不到这些,管理不了。所以即便是 Unity(C# 引擎)也要自己实现 asset ref count,不能用 C# 的 GC。

**替代二:手动 unload**。最朴素的方案。"我知道这个 asset 啥时候用完,我自己 unload"。C 风格。

为什么不行前面已经讨论——**共享 asset** + **异步 streaming** + **多入口** 三个组合让"手动跟踪谁还在用"变成不可能。一个生产级游戏有几千个 asset、几十个系统、几百个加载点。手动管理等于维护一份巨大的 mental model:"这个 sound 现在被 5 个系统持有,我退出关卡时要 unload 5 次"。一个 PR 引入 bug,这份 mental model 就碎了。

**替代三:arena / region-based**。一次性 alloc 一大块,scope 退出时整块释放。Casey 在 HH 里大量用 arena(见 Day 157)。

为什么 asset 不能用 arena?arena 适合**短生命周期、scope 内**的对象(一帧的临时数据、一次 draw call 的 vertex buffer)。但 asset 的生命周期**跨越 scope**——玩家武器的贴图不属于任何函数 scope,它属于"玩家持有武器"这个游戏状态,可能持续几分钟到几小时。Arena 的"scope 退出释放"语义对 asset 不适用。

所以你只剩下 ref count 这一条路。这不是"它最好",是"其他都不行"。

### 2.3 严谨模型:从 inc/dec 到 Arc

让我们从最朴素的 manual inc/dec 开始,一步步推导到 Rust 的 `Arc`。

**版本 0:朴素 manual**

```rust
struct AssetStorage {
    loaded: Vec<Option<LoadedAsset>>,
    ref_count: Vec<u32>,
}

impl AssetStorage {
    fn get(&mut self, id: u32) -> &LoadedAsset {
        self.ref_count[id as usize] += 1;
        if self.loaded[id as usize].is_none() {
            self.loaded[id as usize] = Some(self.load_from_disk(id));
        }
        self.loaded[id as usize].as_ref().unwrap()
    }

    fn release(&mut self, id: u32) {
        self.ref_count[id as usize] -= 1;
        if self.ref_count[id as usize] == 0 {
            self.loaded[id as usize] = None;  // unload
        }
    }
}
```

游戏代码:
```rust
storage.get(TEXTURE_PLAYER);  // rc = 1
// ... 用 ...
storage.release(TEXTURE_PLAYER);  // rc = 0, unloaded
```

**Bug 列表**(都能在生产中遇到):
1. 忘 `release` → 内存 leak
2. `release` 两次 → ref_count underflow,u32 underflow 成 `u32::MAX`,永远不到 0,asset 永远不 unload
3. `get` 返回 `&LoadedAsset`,但 borrow checker 要求借用期间不能 mut self——下一次 get 编译失败
4. 多线程下 race——两个线程同时 `get(id)`,`+= 1` 不是原子,可能丢失更新

**版本 1:用 `AssetHandle` 封装 release**

```rust
pub struct AssetHandle<'a> {
    id: u32,
    storage: &'a mut AssetStorage,
}

impl<'a> Drop for AssetHandle<'a> {
    fn drop(&mut self) {
        self.storage.release(self.id);
    }
}
```

问题:`&'a mut AssetStorage` 让你**一次只能持有一个 handle**。游戏代码经常需要"同时持有玩家贴图和敌人贴图",borrow checker 拒绝。

**版本 2:用 `Rc<RefCell<AssetStorage>>` 共享所有权**

```rust
pub struct AssetHandle {
    id: u32,
    storage: Rc<RefCell<AssetStorage>>,
}

impl Drop for AssetHandle {
    fn drop(&mut self) {
        self.storage.borrow_mut().release(self.id);
    }
}
```

`Rc` 允许多个 handle 共享 storage。`RefCell` 允许运行时借用检查。这能跑,但**单线程**——Rc 不能跨线程。asset streaming 在背景线程,必须 Arc。

**版本 3:Rust 的标准答案 `Arc<LoadedAsset>`**

```rust
pub struct AssetStorage {
    cache: HashMap<u32, Arc<LoadedAsset>>,  // Weak 这里更好,见下
}

impl AssetStorage {
    pub fn get(&mut self, id: u32) -> Arc<LoadedAsset> {
        if let Some(a) = self.cache.get(&id) {
            return Arc::clone(a);  // 不重新加载,只增计数
        }
        let a = Arc::new(self.load_from_disk(id)?);
        self.cache.insert(id, Arc::clone(&a));
        a
    }
}
```

游戏代码持有 `Arc<LoadedAsset>`,Drop 时自动 dec。Cache 里也持一份 `Arc`,所以 cache 不主动 unload——除非你限制 cache 大小。

这套方案在 Rust 里零 boilerplate。每个持有方写 `let tex = storage.get(id);`,用完自然 drop。`Arc` 内部的 `AtomicUsize` 处理原子计数。

### 2.4 LRU eviction:防止"抖动"

简单 ref count 有个问题:**抖动**(thrashing)。设想场景:

- 主菜单背景音乐 `music_menu.mp3` 持续播放
- 玩家点"开始游戏" → 主菜单场景 unload → 音乐 drop → ref count 归零 → 立即 unload
- 玩家在游戏里玩了 10 秒,点"返回主菜单" → 主菜单场景 reload → 音乐重新加载

每次进出主菜单都重新加载音乐(几 MB 文件,几十毫秒)。如果玩家频繁切换(比如调试时),FPS 会掉到个位数。

**LRU(Least Recently Used)策略**解决这个问题:

- ref_count = 0 时不立刻 unload,只标记 "evictable"
- Cache 有大小上限(比如 512 MB)
- 满时,从 evictable 中选**最久没 access** 的驱逐

这样,主菜单音乐 drop 后还会在 cache 里"驻留",下次需要时秒取。直到 cache 满了,才被某个更老的 evictable asset 顶出去。

LRU 的数据结构:**HashMap + 双向链表**。HashMap 提供 O(1) 查找,双向链表维护 access order。每次 access 把节点移到表头,驱逐从表尾。

Rust 的 `lru` crate 现成实现。工业引擎(Unreal / Unity / Bevy)都内置 LRU cache。

### 2.5 Generation:防止 stale handle

最后一个陷阱——slot 复用。最隐蔽的 bug,90% 的业余项目都会踩。

**场景**:
1. 加载 texture A,storage 给它 slot 7,generation = 1
2. A unload,slot 7 空闲,generation += 1 = 2
3. 加载 texture B,storage 复用 slot 7,generation = 2
4. 某个延迟 callback 还持有 `AssetHandle { id: 7, generation: 1 }`,去 get
5. Storage 返回 slot 7 的当前内容(B),**完全错的 asset**!

修复:handle 带 generation,get 时检查。

```rust
struct AssetSlot {
    asset: Option<LoadedAsset>,
    generation: u32,  // 每次 unload 时 +1
}

struct AssetHandle {
    id: u32,
    generation: u32,  // 创建时的 generation
}

fn get(&self, h: AssetHandle) -> Option<&Asset> {
    let slot = &self.slots[h.id as usize];
    if slot.generation == h.generation {
        slot.asset.as_ref()
    } else {
        None  // stale handle,告诉调用方"你持有的引用已过期"
    }
}
```

Rust 的 `slotmap` crate 完整实现了这套机制——代际索引 + slot 管理。生产级 asset cache 几乎都用 slotmap 或类似方案。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业引擎的 asset 引用计数,每个流派不同。让我详细对比,你会看到 Casey 今天学的方案处于生态哪个位置。

**Unreal Engine 5**:用 `TStrongObjectPtr<T>` 和 `TWeakObjectPtr<T>` 二分。`TStrongObjectPtr` 是强引用——持有它时 asset 不会 unload。`TWeakObjectPtr` 是弱引用——不影响 ref count,但 get 时可能返回 null(asset 已 unload)。Unreal 还有一套"软引用" `TSoftObjectPtr`——只是 path 字符串,需要时才请求加载。三级引用体系(强 / 弱 / 软)让 Unreal 能精细控制 asset 生命周期。Unreal 的 `StreamableManager` 处理 async loading + ref count,代码在 `Engine/Source/Runtime/Engine/Private/Streaming`。

**Unity Addressables**:Unity 2018 之后推出的现代 asset 系统。每个 asset 有个 addressable name(字符串),你 `Addressables.LoadAssetAsync<Texture>("player")` 拿到一个 `AssetReference`。`AssetReference` 内部 ref count,你 `Addressables.Release(reference)` 时 dec。Unity 的特色是 addressable 是"全局"的——一个 asset 可以被多个 scene 引用,Addressables 自动 dedupe,确保只加载一份。这把 dedupe 责任从开发者挪到引擎,大幅减少"同一贴图加载两次"的 bug。

**Bevy**:Rust 生态旗舰。Bevy 的 `Handle<T>` 是强引用(类似 Arc),`HandleUntyped` 是弱引用。Bevy 的 asset system 在 `bevy_asset` crate,核心 struct 是 `Assets<T>`——一个 typed container,内部用 `Arc<LoadedAsset>` + HashMap。Bevy 的特色是**所有 handle 都是 RAII**——Drop 时自动 dec,完全没有 manual release 调用。这符合 Rust 的 ownership 哲学。

**Godot**:用 `RefCounted` 基类。继承 `RefCounted` 的类自动 ref count。`Resource` 类(asset 的基类)继承 `RefCounted`,所以所有 Godot resource 都是 ref counted。Godot 用 C++ 实现,但暴露给 GDScript 的接口看起来像 GC——你赋值给变量就 inc,变量离开 scope 就 dec。底层是 manual ref count + RAII。

Casey 的 HH 代码用最朴素的 manual ref count——一个 `u32` 数组当 ref_count,自己 inc / dec。这是 C 风格,无运行时支持。Rust 移植版会自然用 `Arc<T>` + Drop trait,接近 Bevy 的方案。

**迁移建议**:你写 Rust 游戏,优先用 `Arc<LoadedAsset>`,辅以 `Weak<LoadedAsset>`(cache 内部用 Weak,使用者用 Arc,这样 cache 不阻止 unload)。如果你做大型项目(1000+ asset),考虑 `slotmap` 替代裸 u32 id,获得 generation 保护。

### 3.2 · 🎨 图形学视角

图形程序员对 asset ref count 有特殊敏感度,因为 GPU resource 占用的是 VRAM,不是 RAM——管理错了代价更大。

GPU resource 的 ref count 特殊之处:

**第一,VRAM 紧张**。一个 4K texture = 16 MB VRAM。中端 GPU 总 VRAM 4 GB,装 250 个 4K texture 就满。VRAM 满 → driver 要 evict 别的 resource → 性能崩。所以 GPU ref count 比 RAM 更需要"积极 unload"。

**第二,卸载 GPU resource 慢**。删除一个 GL texture 是 `glDeleteTextures(1, &id)`,内部 driver 要等 GPU 完成所有 pending draw call 用到这个 texture,才能真的释放。一个删 texture 操作可能 block 5 ms。如果你一帧删 100 个 texture,就是 500 ms 卡顿。所以工业实现会**批量延迟删**——把要删的 texture 收集起来,在 frame end 一次性删(driver 内部能并行处理)。

**第三,driver 可能 lazy allocate**。某些 driver(Hyper-V、VMware)的 GPU 是软件模拟,texture 实际在 RAM。这时 ref count 的"VRAM 压力"评估全错。所以工业实现要做 `GL_GPU_MEMORY_INFO_CURRENT_AVAILABLE_VRAM_NVX` 这种扩展查询,实际测 VRAM 占用,而不是估算。

**第四,GPU resource 有 dependency**。Mipmap chain 是一组 texture,cube map 是 6 个 texture,bindless resource 是 array。你不能"单独 unload 一个 mipmap level"——必须整组 unload。所以 GPU ref count 通常 per "resource group",不是 per texture id。

具体到代码,Rust 图形社区的标准做法:

```rust
use std::sync::Arc;

struct GpuTexture {
    inner: Arc<wgpu::Texture>,
}

impl Drop for GpuTexture {
    fn drop(&mut self) {
        // wgpu 内部 ref count,Arc drop 时自动释放
        // 不需要手动 glDeleteTextures
    }
}
```

`wgpu::Texture` 内部已经是 `Arc` 包装,Drop 时自动释放。你只需要保证自己持有的 `GpuTexture` 正确 drop——Rust 的 ownership 系统会帮你。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核本身的 asset 管理大量用 ref count。最典型的是 `struct file`(打开的文件描述符)——多个进程 fork 后共享同一个 `struct file`,ref count 在 `f_count` 字段。close 时 dec,归零时真的释放。

Linux 的 ref count 实现细节值得学:

**第一,`atomic_long_t` 而非 `atomic_int`**。内核用 64-bit ref count,防止"极端长生命周期对象"在 32-bit 上溢出。比如一个长期打开的 socket,可能累积几十亿次 inc/dec,32-bit u32 会溢出。64-bit 几乎不可能溢出(2^64 次操作 = 几亿年)。

**第二,`get_file_rcu` / `fput` 是 RCU-safe 的**。Linux 内核的 ref count 操作要在 RCU(read-copy-update)安全上下文里做。RCU 是内核的"无锁读"机制——读不加锁,写要等所有读者退出。Ref count inc 必须保证"在读者持有时不会真的释放"。这导致内核 ref count 实现比用户态复杂。

**第三,ref count leak 的检测**。Linux 内核有 `DEBUG_REFCOUNT` 配置,打开后每个 ref count 操作都被记录,shutdown 时报告 leak。游戏工程没这么成熟,但 Casey 在 HH 里手动加 `total_loads` / `total_unloads` 计数,差值就是 leak 量。

用户态的 Rust 工具链:

```bash
# 用 Valgrind 检测 leak(Linux 上跑 Rust 程序)
valgrind --leak-check=full --show-leak-kinds=all ./target/release/my_game

# 用 AddressSanitizer(Rust nightly + -Zsanitizer=address)
RUSTFLAGS="-Zsanitizer=address" cargo +nightly run

# 用 heaptrack 看内存分配模式
heaptrack ./target/release/my_game
heaptrack_print heaptrack.my_game.12345.gz
```

Valgrind 报告里 `definitely lost` 是 leak,`indirectly lost` 是被 leak 持有的 leak,`still reachable` 是程序结束时还没释放但 OS 会回收的(不算 bug,但应该改)。

对 Rust 程序,Valgrind 通常报"无 leak"——因为 Rust 的 ownership 系统在编译时保证 drop。但 `Arc` cycle(A 持 B,B 持 A)会 leak,Valgrind 能检测到。

### 3.4 · 🦀 Rust 生态视角

Rust 的 ref count 工具栈,让我详细剖析每个的语义和 trade-off。

**`Rc<T>`** — 单线程引用计数。内部用 `Cell<usize>` 计数(非原子)。零开销,但**绝对不能跨线程**。`Rc` 没实现 `Send`,编译器拒绝跨线程传递。

**`Arc<T>`** — 多线程引用计数。`AtomicUsize` 计数。原子操作 ~5ns,比 `Cell` 的 ~1ns 慢,但多线程安全。游戏主线程 + 背景加载线程的标准选择。

**`Weak<T>`** — 弱引用。`Weak` 持有 `Weak<AllocInner>`,不阻止 unload。需要用时调 `weak.upgrade()` 得 `Option<Arc<T>>`——None 表示已被 unload。Cache 内部用 Weak,使用者用 Arc:这样 cache 不阻止 unload,使用者 drop 时真的释放。

```rust
struct AssetCache {
    cache: HashMap<u32, Weak<LoadedAsset>>,
}

impl AssetCache {
    fn get(&mut self, id: u32) -> Arc<LoadedAsset> {
        if let Some(weak) = self.cache.get(&id) {
            if let Some(strong) = weak.upgrade() {
                return strong;  // 还在 cache,直接用
            }
        }
        // Weak 死了或没有,重新加载
        let asset = Arc::new(self.load_from_disk(id));
        self.cache.insert(id, Arc::downgrade(&asset));
        asset
    }
}
```

这个模式叫 **"weak-value cache"**——cache 用 Weak,使用者用 Arc。Cache 不持有强引用,使用者全 drop 后 asset 真的释放。Cache 只是"加速重复访问",不保活。

**`memuse` / `arc-swap` / `triomphe`** — 这些是 Rust 社区对 Arc 的优化变体。`arc-swap` 用于"原子地替换整个 Arc"(读取无锁)。`triomphe` 是 Servo 出的 Arc,API 兼容但无 weak pointer(更快)。游戏开发一般用标准 `Arc`,除非 profile 显示 bottleneck。

**`slotmap`** — 代际索引容器。前面提到的 generation 机制,slotmap 现成实现。

```rust
use slotmap::SlotMap;

slotmap::new_key_type! {
    pub struct AssetKey;
}

let mut assets: SlotMap<AssetKey, LoadedAsset> = SlotMap::new();
let key: AssetKey = assets.insert(LoadedAsset::new("player.png"));

// key 自带 generation,slot 复用时旧 key 自动失效
let asset = assets.get(key);  // Option<&LoadedAsset>
```

slotmap 的 key 内部是 `(slot_index, generation)`,16+16 bit 或 32+32 bit。slot 复用时 generation += 1,旧 key 自动失效。这是工业 asset cache 的标配。

**`sharded-slab`** — 多线程优化的 slab allocator。比 slotmap 更适合"高并发 inc/dec"。Rayon / Tokio 内部用。

**反模式**:不要这样写 Rust asset code:
- ❌ `&'a mut AssetStorage` 当参数传——borrow checker 会让你哭
- ❌ `unsafe { *const LoadedAsset }` 当 handle——丢了 Drop 保证
- ❌ 自己写 `u32 ref_count` 数组——直接用 Arc / slotmap,几十年的 bug 修复你别重造
- ❌ `Arc<Mutex<HashMap<u32, Arc<LoadedAsset>>>>`——Mutex 在 hot path 慢,改 `DashMap` 或 `RwLock`

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么用 `Arc<LoadedAsset>` 而不是 `Rc<LoadedAsset>`?

**参考解答**:asset 加载可能在背景线程(streaming),游戏代码在主线程使用。跨线程共享必须 `Arc`(原子计数)。`Rc` 单线程,跨线程 UB。

如果 asset 加载完全在主线程同步完成,`Rc` 够用且更快。但实际工业代码总是 streaming,所以 `Arc`。

### Lv2 · 动手实践

**题**:写一个 RefCountedCache<K, V>,用 `Arc<V>` 存值。`get(k)`:有则返回 clone,无则用 closure 加载并 cache。`size()` 返回 cache size。验证多次 get 同 key 返回同一 `Arc`(指针相同)。

**参考解答**:

```rust
use std::collections::HashMap;
use std::sync::Arc;

pub struct RefCountedCache<K, V, F>
where K: std::hash::Hash + Eq + Clone, F: Fn(&K) -> V {
    cache: HashMap<K, Arc<V>>,
    loader: F,
}

impl<K, V, F> RefCountedCache<K, V, F>
where K: std::hash::Hash + Eq + Clone, F: Fn(&K) -> V {
    pub fn new(loader: F) -> Self {
        Self { cache: HashMap::new(), loader }
    }

    pub fn get(&mut self, k: &K) -> Arc<V> {
        if let Some(v) = self.cache.get(k) {
            return Arc::clone(v);
        }
        let v = Arc::new((self.loader)(k));
        self.cache.insert(k.clone(), Arc::clone(&v));
        v
    }

    pub fn size(&self) -> usize { self.cache.len() }
}

fn main() {
    let mut cache: RefCountedCache<u32, String, _> =
        RefCountedCache::new(|k| format!("val_{}", k));

    let a = cache.get(&1);
    let b = cache.get(&1);
    assert!(Arc::ptr_eq(&a, &b));  // 同一 Arc
    println!("cache size: {}", cache.size());  // 1

    let c = cache.get(&2);
    println!("cache size: {}", cache.size());  // 2

    drop(a);
    drop(b);
    drop(c);
    // cache 仍持 Arc,数据还在
}
```

## 8 · Rust / Arch 落地代码

```rust
use std::collections::HashMap;
use std::sync::Arc;
use std::sync::atomic::{AtomicU32, Ordering};

pub struct AssetStorage {
    cache: HashMap<u32, Arc<String>>,
    ref_counts: HashMap<u32, AtomicU32>,
    pub total_loads: u64,
}

impl AssetStorage {
    pub fn new() -> Self {
        Self {
            cache: HashMap::new(),
            ref_counts: HashMap::new(),
            total_loads: 0,
        }
    }

    pub fn get(&mut self, id: u32) -> Arc<String> {
        // 第一次访问:加载
        if !self.cache.contains_key(&id) {
            let val = format!("loaded_asset_{}", id);
            self.cache.insert(id, Arc::new(val));
            self.ref_counts.insert(id, AtomicU32::new(0));
            self.total_loads += 1;
        }
        let arc = Arc::clone(self.cache.get(&id).unwrap());
        self.ref_counts.get(&id).unwrap().fetch_add(1, Ordering::Relaxed);
        arc
    }

    pub fn release(&mut self, id: u32) {
        if let Some(rc) = self.ref_counts.get(&id) {
            let prev = rc.fetch_sub(1, Ordering::Relaxed);
            if prev <= 1 {
                // ref count 到 0,unload
                self.cache.remove(&id);
                println!("[unload] asset {} evicted", id);
            }
        }
    }

    pub fn loaded_count(&self) -> usize { self.cache.len() }
}

fn main() {
    let mut storage = AssetStorage::new();

    // 模拟游戏代码
    let a1 = storage.get(1);
    let a2 = storage.get(1);  // 不重新加载
    println!("after get(1) twice: {} loaded, {} total_loads",
        storage.loaded_count(), storage.total_loads);

    let b1 = storage.get(2);
    println!("after get(2): {} loaded", storage.loaded_count());

    // 释放
    storage.release(1);
    storage.release(1);
    println!("after release 1 twice: {} loaded", storage.loaded_count());

    storage.release(2);
    println!("after release 2: {} loaded", storage.loaded_count());

    // 再次 get(1),应重新加载
    let _ = storage.get(1);
    println!("after get(1) again: {} total_loads", storage.total_loads);
}
```

**预期**:
```
after get(1) twice: 1 loaded, 1 total_loads
after get(2): 2 loaded
[unload] asset 1 evicted
after release 1 twice: 1 loaded
[unload] asset 2 evicted
after release 2: 0 loaded
after get(1) again: 2 total_loads  # 重新加载
```
