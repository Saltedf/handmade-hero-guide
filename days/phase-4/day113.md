
# Day 113 · 简单性能计数器

> 昨天你学了"性能是 latency/throughput/cache/branch 的混合",今天 Casey 把这套理论变成**代码里能直接用的工具**:在每个阶段记一个开始时间、结束时间,差值就是这一段花了多久。简单到惊人,但这是后面所有性能调试的基础设施。

## 0 · 为什么要有这一天

你写完一段渲染代码,跑游戏发现"感觉变卡了"。你要怎么定位?

最朴素的方法是"凭感觉":改一处代码,跑一遍,看帧率表。但这种方法的问题:

1. **眼睛不靠谱**:60 FPS 和 50 FPS 都是"流畅",你看不出区别
2. **一帧里有几十个子阶段**(输入、AI、物理、渲染、音频混合),卡的可能只是其中之一
3. **变化不连续**:同一份代码跑两次,帧时间可能差 5-10%(系统其他进程干扰)

**你需要的不是"凭感觉",而是一个能在游戏里持续输出"每个阶段耗时"的工具**。这就是性能计数器(performance counter)。

注意:**性能计数器不是 CPU 的 PMU**(那是 Day 112 的 cache-miss / branch-miss)。性能计数器是**你自己写的代码**,在每个阶段插桩记录时间。简单、可移植、足够 Casey 用了一整本书。

Casey 这一天就是给你写一个 30 行的"游戏内性能计数器"——能在游戏窗口实时显示"AI 阶段 3.2ms / 物理 1.8ms / 渲染 8.5ms"。

心理锚点:读完这一天,你能:

- 在 Rust 里读到纳秒级时间戳
- 把"开始/结束"包装成 RAII guard,自动统计一个 scope 的耗时
- 在游戏画面或终端输出"每帧每阶段耗时"
- 知道为什么不能直接用 `SystemTime::now()`(精度不够)

## 1 · Casey 今天做了什么

Casey 在游戏里加了一个简单的 `DEBUG_PLATFORM_GET_TIME` 平台函数,返回当前时间戳(纳秒)。然后在游戏循环里:

```c
u64 start = get_time();
do_ai();
u64 after_ai = get_time();
do_physics();
u64 after_physics = get_time();
do_render();
u64 after_render = get_time();
// 输出 / 显示 after_ai - start, after_physics - after_ai, ...
```

没什么花活,就是把"每段代码耗时"算出来。他做了一个简单的 ring buffer 存最近 30 帧的数据,在屏幕角落画柱状图。

关键决策:

1. **用纳秒(ns)而不是浮点秒**:避免浮点累积误差,整数运算精确
2. **用平台特定的"高精度时钟"**:Windows 上是 `QueryPerformanceCounter`,Linux 上是 `clock_gettime(CLOCK_MONOTONIC)`
3. **不是 `time()` 那种秒级时钟**:那玩意精度太低

## 2 · 心智模型

### 2.1 类比:厨房的"工时打卡器"

回到 Day 112 的厨房类比。现在厨房经理想知道:**每道菜从下单到上桌,中间每一步(看单、备料、烹饪、装盘)各花了多久**。

最简单的做法:在每个工位贴一个时钟,厨师**做完每一步打一次卡**。然后经理看时间戳:

```
10:00:00.000  看单
10:00:00.500  备料(花 500ms)
10:00:01.800  烹饪(花 1.3s)
10:00:02.100  装盘(花 300ms)
10:00:02.150  上桌(花 50ms)
```

经理立刻看到"烹饪"占了 65% 的时间,要优化就要看烹饪工位为什么慢。

性能计数器就是这件事:在代码里"打卡",记录每个阶段开始/结束的时间戳。

### 2.2 时间从哪里来:CPU 的时钟源

Linux 上你有几种"现在是什么时间"的方式,精度和特性不同:

| API | 精度 | 单调性 | 性能 |
|---|---|---|---|
| `time(NULL)` | 秒 | 不单调(系统时间可调) | 快 |
| `gettimeofday()` | 微秒(µs) | 不单调 | 快 |
| `clock_gettime(CLOCK_MONOTONIC)` | 纳秒(ns) | 单调(只增不减) | 快(~20ns) |
| `clock_gettime(CLOCK_MONOTONIC_RAW)` | 纳秒 | 单调,不经过 NTP 调整 | 快 |
| `std::time::Instant::now()` | 纳秒(Rust 包装) | 单调 | 快 |

**关键术语**:

- **单调(monotonic)**:时间戳只增不减。系统时钟(`time(NULL)`)会被 NTP 校准前后跳,不能用来测时间差——可能得到负数!
- **精度(precision)**:时钟能区分的最小时间间隔。现代 x86_64 用 TSC(Time Stamp Counter),精度是纳秒级。
- **分辨率(resolution)**:实际返回的粒度。Rust 的 `Instant` 在 Linux 上用 `clock_gettime(CLOCK_MONOTONIC)`,分辨率是 1ns。

### 2.3 TSC:CPU 内部的"周期计数器"

x86_64 CPU 里有一个特殊寄存器叫 **TSC**(Time Stamp Counter),每来一个 CPU 周期就 +1。`rdtsc` 指令读 TSC,只需几个时钟周期。

- 3 GHz CPU:1 秒 = 30 亿个周期 = TSC 增加 3,000,000,000
- 1ns = 3 个周期
- `rdtsc` 本身大概 20-30 周期 = ~10ns

所以"读时间戳"本身有 ~10ns 开销。如果你测的东西只有 50ns,这个开销不能忽略。

**Invariant TSC**:较新的 CPU(invariant / constant TSC)保证 TSC 频率不随 CPU 频率调节(涡轮增压 / 省电)变化。老 CPU 没这保证,TSC 在 CPU 降频时会变慢,不能用来跨睡眠测时间。

`clock_gettime(CLOCK_MONOTONIC)` 在 Linux 上会自动用 TSC(如果是 invariant TSC),并做正确的频率换算。

### 2.4 Rust 的 `std::time::Instant`

Rust 标准库提供了一个跨平台的"单调高精度时钟":`Instant`。

```rust
use std::time::Instant;

let start = Instant::now();
// ... do work ...
let elapsed = start.elapsed();
println!("{:?}", elapsed);  // 1.234ms
```

`Instant::now()` 在 Linux 上是 `clock_gettime(CLOCK_MONOTONIC)` 的薄包装,精度 1ns,开销 ~20ns。

**Duration 类型**:`Instant::elapsed()` 返回 `Duration`,内部是 `{ secs: u64, nanos: u32 }`,所以可以表达 0ns 到 ~584 亿年。够用了。

#### 转换

```rust
let d = start.elapsed();
let nanos = d.as_nanos() as u128;  // 总纳秒数(整数)
let micros = d.as_micros() as u128;
let millis = d.as_millis() as u128;
let secs = d.as_secs_f64();        // 浮点秒
```

游戏开发里,**毫秒(ms)是最常用的单位**:60 FPS 一帧 16.67ms,144 FPS 一帧 6.94ms,人眼对 1ms 级别的变化敏感。

### 2.5 RAII 自动计时

手写"开始时间、结束时间、做差"很容易忘。Rust 的 RAII 模式非常适合:

```rust
struct TimerGuard<'a> {
    start: Instant,
    output: &'a mut u64,  // 累加到这个变量
}

impl<'a> Drop for TimerGuard<'a> {
    fn drop(&mut self) {
        let elapsed_ns = self.start.elapsed().as_nanos() as u64;
        *self.output += elapsed_ns;
    }
}

fn time_section(output: &mut u64) -> TimerGuard<'_> {
    TimerGuard { start: Instant::now(), output }
}

// 用法
let mut ai_time_ns = 0u64;
{
    let _g = time_section(&mut ai_time_ns);
    do_ai();
}   // _g 在这里 drop,自动记录耗时到 ai_time_ns
```

**术语解释**:

- **RAII**(Resource Acquisition Is Initialization):资源的获取和释放绑定到对象的生命周期。`{` 创建 `}`,自动 `Drop`。
- **guard**:一个对象,存在期间"持有"某种状态(这里是"计时中"),析构时清理(记录耗时)。
- **`Drop` trait**:Rust 表达"析构时做什么"的方式。

这种写法的好处:**永远不可能忘记关掉计时器**。即使函数 `?` 提前返回,`_g` 也会析构。

### 2.6 累积统计:不止"一次多少 ms"

一次测量的意义有限(可能有抖动)。更有用的是**累积统计**:

- **总耗时**(最近 N 帧累加)
- **平均耗时**(总 / N)
- **最大 / 最小耗时**(找异常)
- **百分位**(P50 / P95 / P99)

Casey 在这一天做了一个简单的 ring buffer 存最近 N 帧的耗时,在屏幕上画柱状图。后面 Day 119+ 他会扩展成完整的"frame profiler"。

### 2.7 测量的陷阱

#### 1. 测量影响被测量者

读 `Instant::now()` 有 20ns 开销。如果你在 1ms 的内循环里每 100ns 读一次时间,你测到的"循环时间"有一半是"读时间本身"。

**对策**:**只在粗粒度边界处打卡**,不要在内循环里读时间。

#### 2. 编译器优化掉"无用工作"

```rust
let start = Instant::now();
let mut sum = 0u64;
for i in 0..1_000_000 { sum += i; }
let elapsed = start.elapsed();
println!("{}", elapsed);
// 问题:编译器看到 sum 没人用,可能把循环删了!elapsed ≈ 0
```

**对策**:用 `std::hint::black_box`:

```rust
let mut sum = 0u64;
for i in 0..1_000_000 { sum += i; }
std::hint::black_box(&mut sum);   // 告诉编译器:sum 是"被用"的
```

#### 3. CPU 频率调节

笔记本 / 台式机的 CPU 会动态调频(从 1GHz 到 5GHz)。同样的代码,在不同的频率下"周期数"差几倍。但**墙钟时间(wall-clock time,纳秒)是稳定的**——`Instant::now()` 不受 CPU 频率影响(它用 TSC 但换算成 ns)。

所以**游戏开发里测"墙钟时间(ms)"比测"CPU 周期数"更可重复**。

#### 4. 系统调度

Linux 不是实时系统,你的进程可能被调度器抢占几百微秒到几毫秒。这种"被切走"的时间会算进你的测量里。

**对策**:测多次取中位数;或排除异常值(> 平均的 5 倍就丢掉)。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上读时间的系统调用:

#### `clock_gettime(2)`

```c
#include <time.h>
struct timespec ts;
clock_gettime(CLOCK_MONOTONIC, &ts);
// ts.tv_sec = 秒数,u64
// ts.tv_nsec = 纳秒数(<1 秒的部分),u32
```

对应的 Rust 直接调用(不用 std):

```rust
use std::os::raw::*;

extern "C" {
    fn clock_gettime(clk_id: c_int, tp: *mut timespec) -> c_int;
}

#[repr(C)]
struct timespec { tv_sec: i64, tv_nsec: i64 }

fn now_ns() -> u64 {
    let mut ts = timespec { tv_sec: 0, tv_nsec: 0 };
    unsafe { clock_gettime(1, &mut ts); }  // CLOCK_MONOTONIC = 1
    (ts.tv_sec as u64) * 1_000_000_000 + (ts.tv_nsec as u64)
}
```

`CLOCK_MONOTONIC = 1` 是 Linux 的常量。其他常用的:

- `CLOCK_REALTIME = 0`:系统时钟,可被 NTP 调整
- `CLOCK_MONOTONIC = 1`:单调,不受 NTP 影响,但受 Suspend/Resume 影响
- `CLOCK_MONOTONIC_RAW = 4`:基于 raw hardware,完全不受 NTP / suspend 影响
- `CLOCK_PROCESS_CPUTIME_ID = 2`:本进程的 CPU 时间(不包括睡眠)
- `CLOCK_THREAD_CPUTIME_ID = 3`:本线程的 CPU 时间

游戏开发用 `CLOCK_MONOTONIC` 就够了。如果你需要"绝对时间"(比如打 log 时间戳),用 `CLOCK_REALTIME`。

#### `clock_getres(2)` 查分辨率

```c
struct timespec res;
clock_getres(CLOCK_MONOTONIC, &res);
// res.tv_nsec = 1(纳秒级分辨率)
```

#### Rust 标准库的实现

`std::time::Instant::now()` 在 Linux glibc 上调 `clock_gettime(CLOCK_MONOTONIC)`,在 musl 上也一样。你可以放心用,不需要手写 FFI。

### 3.3 · 🦀 Rust 生态视角

#### `std::time::Instant` vs `std::time::SystemTime`

- `Instant`:单调时钟,**只用于测时间差**。永远只增。
- `SystemTime`:墙钟时间,可以"现在几点",可能向后跳(NTP 调整)。

```rust
use std::time::{Instant, SystemTime};

let i1 = Instant::now();
let i2 = Instant::now();
assert!(i2 > i1);  // 永远成立

// SystemTime 不能保证
let s1 = SystemTime::now();
// ... 系统 NTP 调整时钟 ...
let s2 = SystemTime::now();
// s2 可能 < s1
```

#### `Duration` 的内部表示

```rust
pub struct Duration {
    secs: u64,
    nanos: u32,  // 0 <= nanos < 1_000_000_000
}
```

这是显式的"秒 + 纳秒"组合,不是单个 u128 纳秒。好处:**转换成人类可读时间(`{:02}:{:02}:{:03}`)很快**;坏处:**算时间差要做进位**(但 Rust 帮你做了)。

#### 用 `RwLock<HashMap<String, u64>>` 做全局计数器

如果你想"按名字"记录多个计数器(比如 `"ai"`、`"physics"`、`"render"`),用全局 `RwLock`:

```rust
use std::sync::RwLock;
use std::collections::HashMap;
use std::time::Instant;

lazy_static::lazy_static! {
    static ref COUNTERS: RwLock<HashMap<String, u64>> = RwLock::new(HashMap::new());
}

struct ScopeTimer { name: String, start: Instant }

impl ScopeTimer {
    fn new(name: &str) -> Self {
        Self { name: name.to_string(), start: Instant::now() }
    }
}

impl Drop for ScopeTimer {
    fn drop(&mut self) {
        let ns = self.start.elapsed().as_nanos() as u64;
        let mut map = COUNTERS.write().unwrap();
        *map.entry(self.name.clone()).or_insert(0) += ns;
    }
}

macro_rules! time_scope {
    ($name:expr) => {
        let _timer = ScopeTimer::new($name);
    };
}

// 用法
fn game_frame() {
    time_scope!("ai");
    do_ai();
    // _timer 在 scope 结束时 drop,自动累加到 "ai" 计数器
}
```

`lazy_static` 是个 crate,提供"全局静态变量初始化"。Rust 1.80+ 内置 `std::sync::LazyLock`,可以不用 lazy_static:

```rust
use std::sync::LazyLock;
static COUNTERS: LazyLock<RwLock<HashMap<String, u64>>> =
    LazyLock::new(|| RwLock::new(HashMap::new()));
```

#### `criterion` crate

如果你要做严肃的 micro-benchmark(不是"游戏内 frame profiler"),用 `criterion`:

```toml
[dev-dependencies]
criterion = { version = "0.5", features = ["html_reports"] }

[[bench]]
name = "my_bench"
harness = false
```

`benches/my_bench.rs`:

```rust
use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn my_func(n: usize) -> u64 {
    (0..n as u64).sum()
}

fn bench(c: &mut Criterion) {
    c.bench_function("my_func 1000", |b| {
        b.iter(|| black_box(my_func(black_box(1000))))
    });
}

criterion_group!(benches, bench);
criterion_main!(benches);
```

```bash
cargo bench
# criterion 会:
#   1. 多次运行函数,取统计
#   2. 检测异常值
#   3. 生成 HTML 报告(target/criterion/report/index.html)
#   4. 跨运行对比(检测性能回退)
```

Casey 这一天**不用 criterion**,他要的是"游戏内 frame profiler",不是 micro-bench。但你在 Lv4 / 优化某个函数时,criterion 是利器。

#### GPU 端的计时

GPU 是异步的——你 `submit()` 一个绘制命令,GPU 不立即执行。如果你在 CPU 端 `Instant::now()` 包住 `submit()`,测到的只是"提交命令的时间",不是"GPU 执行的时间"。

GPU 计时要专门的 API:

- **OpenGL**:`GL_TIME_QUERY`(`glQueryCounter`)
- **Vulkan**:`vkCmdWriteTimestamp`
- **Direct3D 11/12**:`ID3D11Asynchronous` / `ID3D12CommandAllocator`

Phase 5+ OpenGL 之后你会碰到。Phase 4 全 CPU 软渲染,不需要 GPU 计时。

## 5 · 对照与变奏

### 同一问题在不同上下文的解法

**问题**:测量一段代码的耗时。

| 上下文 | 工具 |
|---|---|
| 游戏内 per-frame | Casey 的简单计数器 / Tracy |
| Rust micro-bench | `criterion` |
| Linux 系统调用 | `strace -T` / `ltrace` |
| 整个进程的 CPU 热点 | `perf record` + `perf report` |
| 内核空间 | `ftrace` / `bpftrace` |
| Web 前端 | `performance.now()` + DevTools |
| GPU 命令 | `glQueryCounter` / Vulkan timestamp |

所有这些工具本质都在做"开始 / 结束 / 差值",只是适用层不同。

### 历史演化

- **1960s**:硬件时钟是周期的"嘀嗒",精度毫秒级
- **1990s**:TSC 出现(x86),纳秒级读时钟
- **2000s**:TSC 不稳定(频率跟随 CPU 变),Linux 引入 `clock_gettime` 抽象
- **2010s**:Invariant TSC 普及,TSC 再次可靠
- **2020s**:ARM 也有类似的虚拟计数器(`cntvct_el0`)

Casey 用 `QueryPerformanceCounter`(Windows)是 1990s 的设计;Linux 上等价物是 `clock_gettime`。两者都内部用 TSC。

### "测量影响被测量者"的极限情况

物理学家有"海森堡测不准原理"——你不能同时精确知道粒子的位置和动量,因为测量本身会扰动粒子。

性能测量也有类似现象:**任何测量都有开销**。你可以测到 ns 级,但测本身要花 20ns。测得越精确,扰动越大。

Casey 的策略:**只在粗粒度边界打卡**(每帧几十次,不是每像素)。这样总开销 ~1µs/帧,可以忽略。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:下面 4 种测量方案,各自能告诉你什么信息?各自不能告诉你什么?

1. `Instant::now()` 在函数前后打卡
2. `perf stat -e cache-misses ./a.out`
3. `cargo bench` 用 criterion
4. `valgrind --tool=callgrind ./a.out`

**参考解答**:

1. **本日方法**:能告诉你"这段代码总耗时"。**不能**告诉你为什么慢(cache?分支?)。
2. **PMU cache-miss**:能告诉你"这段代码 cache miss 次数"。**不能**告诉你是哪一行代码导致的(除非配合 `perf record`)。
3. **criterion**:能告诉你"这个函数的统计分布(均值/方差/异常值)"。**不能**告诉你在真实游戏中、与其他模块一起运行时的耗时(它是隔离 micro-bench)。
4. **callgrind**:能精确告诉你"每条指令的指令数 / cache 模拟"。**不能**给你真实墙钟时间(valgrind 是模拟器,跑得慢 20-50 倍)。

### Lv2 · 动手实践

**题**:写一个 Rust 程序,实现:

1. 一个 `FrameProfiler` 结构,可以 `begin("name")` 和 `end("name")`
2. 一个 RAII helper `Section` 自动 end
3. 一个 `report()` 打印当前帧每个 section 的毫秒数
4. main 里模拟一个游戏循环 60 帧,每帧有 ai/physics/render 三段,各自 sleep 不同时间

完成标准:`cargo run` 输出每帧每个 section 的耗时,总计应该接近 60 FPS 的 16.67ms。

**参考解答**:

```rust
use std::collections::HashMap;
use std::thread::sleep;
use std::time::{Duration, Instant};

struct FrameProfiler {
    sections: HashMap<String, Duration>,
    starts: HashMap<String, Instant>,
}

impl FrameProfiler {
    fn new() -> Self {
        Self { sections: HashMap::new(), starts: HashMap::new() }
    }

    fn begin(&mut self, name: &str) {
        self.starts.insert(name.to_string(), Instant::now());
    }

    fn end(&mut self, name: &str) {
        if let Some(start) = self.starts.remove(name) {
            let dur = start.elapsed();
            *self.sections.entry(name.to_string()).or_insert(Duration::ZERO) += dur;
        }
    }

    fn report(&self) {
        let total: Duration = self.sections.values().sum();
        print!("  frame: ");
        for (name, dur) in &self.sections {
            print!("{}={:.2}ms ", name, dur.as_secs_f64() * 1000.0);
        }
        println!("total={:.2}ms", total.as_secs_f64() * 1000.0);
    }

    fn reset(&mut self) {
        self.sections.clear();
    }
}

struct Section<'a> {
    profiler: &'a mut FrameProfiler,
    name: String,
}

impl<'a> Section<'a> {
    fn new(p: &'a mut FrameProfiler, name: &str) -> Self {
        p.begin(name);
        Self { profiler: p, name: name.to_string() }
    }
}

impl<'a> Drop for Section<'a> {
    fn drop(&mut self) {
        self.profiler.end(&self.name);
    }
}

fn main() {
    let mut p = FrameProfiler::new();
    for frame in 0..60 {
        p.reset();

        {
            let _s = Section::new(&mut p, "ai");
            sleep(Duration::from_millis(2));
        }
        {
            let _s = Section::new(&mut p, "physics");
            sleep(Duration::from_millis(3));
        }
        {
            let _s = Section::new(&mut p, "render");
            sleep(Duration::from_millis(10));
        }

        if frame % 10 == 0 {
            print!("Frame {}: ", frame);
            p.report();
        }
    }
}
```

输出大致:

```
Frame 0:   frame: ai=2.00ms physics=3.00ms render=10.00ms total=15.00ms
Frame 10:  frame: ai=2.00ms physics=3.00ms render=10.00ms total=15.00ms
...
```

每行 ~15ms,接近 60 FPS 的预算。

- 后台线程用 `Arc<Mutex<VecDeque<...>>>` 共享,定时 lock + clone 出来再算

### Rust:完整的 frame profiler 加上 ring buffer

```rust
use std::collections::VecDeque;
use std::time::{Duration, Instant};

const HISTORY_LEN: usize = 60;  // 存最近 60 帧

#[derive(Default, Clone)]
struct FrameTimings {
    ai_ns: u64,
    physics_ns: u64,
    render_ns: u64,
    total_ns: u64,
}

struct Profiler {
    current: FrameTimings,
    starts: FrameTimings,  // 当前段的开始时间(用 0 表示未开始)
    history: VecDeque<FrameTimings>,
}

impl Profiler {
    fn new() -> Self {
        Self {
            current: FrameTimings::default(),
            starts: FrameTimings::default(),
            history: VecDeque::with_capacity(HISTORY_LEN),
        }
    }

    fn begin(&mut self, field: &mut u64, time: Instant) {
        *field = time.elapsed().as_nanos() as u64;  // 复用 field 临时存开始
        // 注意:这里我用了一个偷懒的方法,实际生产代码用单独 starts 结构更清晰
    }
}

// 更清晰的实现:
struct Prof2 {
    current: FrameTimings,
    ai_start: Option<Instant>,
    physics_start: Option<Instant>,
    render_start: Option<Instant>,
    history: VecDeque<FrameTimings>,
}

impl Prof2 {
    fn new() -> Self {
        Self {
            current: FrameTimings::default(),
            ai_start: None,
            physics_start: None,
            render_start: None,
            history: VecDeque::with_capacity(HISTORY_LEN),
        }
    }

    fn start_ai(&mut self) { self.ai_start = Some(Instant::now()); }
    fn end_ai(&mut self) {
        if let Some(s) = self.ai_start.take() {
            self.current.ai_ns = s.elapsed().as_nanos() as u64;
        }
    }
    // 类似 start_physics / end_physics / start_render / end_render

    fn end_frame(&mut self) {
        self.current.total_ns = self.current.ai_ns
            + self.current.physics_ns
            + self.current.render_ns;
        if self.history.len() == HISTORY_LEN {
            self.history.pop_front();
        }
        self.history.push_back(self.current.clone());
        self.current = FrameTimings::default();
    }

    fn report_avg(&self) -> FrameTimings {
        let n = self.history.len().max(1) as u64;
        let sum = self.history.iter().fold(FrameTimings::default(), |acc, t| FrameTimings {
            ai_ns: acc.ai_ns + t.ai_ns,
            physics_ns: acc.physics_ns + t.physics_ns,
            render_ns: acc.render_ns + t.render_ns,
            total_ns: acc.total_ns + t.total_ns,
        });
        FrameTimings {
            ai_ns: sum.ai_ns / n,
            physics_ns: sum.physics_ns / n,
            render_ns: sum.render_ns / n,
            total_ns: sum.total_ns / n,
        }
    }
}

fn main() {
    let mut p = Prof2::new();
    for frame in 0..60 {
        p.start_ai();
        std::thread::sleep(Duration::from_micros(2000));
        p.end_ai();

        p.start_physics();  // 假设这两个方法存在
        std::thread::sleep(Duration::from_micros(3000));
        // p.end_physics();  // 略

        // ...

        p.end_frame();
    }
    let avg = p.report_avg();
    println!("avg: ai={}µs physics={}µs render={}µs total={}µs",
        avg.ai_ns / 1000, avg.physics_ns / 1000, avg.render_ns / 1000, avg.total_ns / 1000);
}
```

(注:上面 `start_physics` / `end_physics` 等需要你照 `ai` 的样子补全,完整代码留作练习。)

use std::time::Instant;
use std::hint::black_box;
fn main() {
    let mut total = 0u64;
    let n = 1_000_000;
    for _ in 0..n {
        let t = Instant::now();
        black_box(t);
        total += 1;
    }
    black_box(total);
}
EOF
# 编译运行
rustc -O /tmp/bench_now.rs -o /tmp/bench_now
perf stat -e cycles,instructions /tmp/bench_now
# 看 cycles / n 得到每次 Instant::now() 的周期数
# 现代 x86_64 大概 50-100 cycles = 15-30 ns

**Troubleshooting**:

- 时间戳跳来跳去:确认你用 `Instant` 而不是 `SystemTime`
- 程序跑得越久越慢:可能是 `history` 没限制长度,内存增长;用 `VecDeque` + 固定长度
- 多线程下计时错乱:`Instant` 本身线程安全,但你的 Profiler struct 不是;用 `Mutex<Profiler>` 或每线程独立 profiler
