# Day 064 · 引用映射:世界与模拟的双向 ID

> 昨天 Casey 搭了 sim region,但留下一个问题:sim region 内的怪想"追玩家",它怎么找到玩家的 sim entity?它在 world 里的 ID 是 #42,在 sim Vec 里的下标是 7。两个数字都是"它",哪个用?今天 Casey 解决这个**双视图状态**问题。

## 0 · 为什么要有这一天

第 063 集后,你的世界有两份"视图":

- **World 视图**:`HashMap<EntityId, Entity>`,Id 是全局唯一(比如 #42 表示玩家)
- **Sim 视图**:`Vec<SimEntity>`,每个 entity 在 Vec 里有 local index(0, 1, 2, ...)

问题来了。怪(sim 视图下标 7)要追玩家。怪 AI 写:

```rust
fn update_monster(monster: &mut SimEntity, target: ???, dt: f32) {
    let dir = target.pos.sub(monster.pos).normalize();
    monster.pos += dir * SPEED * dt;
}
```

`target` 是什么类型?
- 如果是 `&SimEntity`,从哪来?怪的 target 字段存的是**哪个** SimEntity 的引用?
- 如果是 `EntityId`(world ID),怎么查到对应的 SimEntity?
- 如果是 `usize`(sim index),每帧 sim 重建后,index 会变,怪存的旧 index 就指向错的 entity

这是 **双视图状态的引用问题**。游戏开发每次引入"多份视图"就会撞到。

数据库 / ORM / 网络协议都有同构问题:
- 数据库:行的物理 ID(PID) vs 主键 ID vs ORM 对象引用
- 网络:客户端 ID vs 服务器内部 ID vs session ID

解决方式都类似:**维护映射表**。今天 Casey 在游戏里实现这个。

读完今天,你要做到:
- 理解"双视图"的引用问题(为什么不能直接用引用)
- 能写出 world_to_sim 的 HashMap 映射
- 知道映射表什么时候 build、什么时候 discard
- 理解这种模式在数据库 / 网络 / ORM 的对应物

如果你卡在"为什么 sim 内不能用引用",回去看 §2.1——Rust 的 ownership 不允许自引用结构。

## 1 · Casey 今天做了什么

Casey 第 64 集做的事:

1. 在 SimRegion struct 加 `world_to_sim: HashMap<EntityId, usize>` 字段
2. unpack 时同步 build 映射:`sim.world_to_sim.insert(world_id, sim.entities.len()); sim.entities.push(...)`
3. sim 内的 entity 引用其他 entity 时,存 world_id(EntityId)
4. 需要实际访问时:`let target_idx = sim.world_to_sim[&target_world_id]; let target = &sim.entities[target_idx];`
5. pack 时**丢弃映射**(下一帧重新 build)

视频里 Casey 强调:"这个映射表是临时的——每帧 build,discard。不要持久化。如果持久化,就引入了 stale index 的 bug(下次 unpack 后 index 变了,旧映射指向错的 entity)。"

## 2 · 心智模型

### 2.1 类比:中学生的"班级座次表"

学校有两个 ID 系统:
- **学号**:每个学生有唯一学号(全校范围,不变)
- **班级座次**:每个班有自己的座次(1-50),每学期重排

老师上课(在班级里)用座次:"第 3 排第 5 个,你回答问题。" 但学籍系统里这个学生是 #20231234。

每学期开学,老师**重新排座次**,生成新的座次表(学号 → 当前座次)。

- 学号 = world EntityId(全局,持久)
- 座次 = sim Vec index(局部,临时)
- 座次表 = world_to_sim 映射(每学期重建)

如果老师**记住了"座次 5 是张三"**,下学期排座后,座次 5 可能变成李四——老师搞错了。这就是 stale index 的 bug。

正确做法:每学期重新看座次表,根据学号查现在哪个座次。**永远不持久化"座次 → 学号"的反向记忆**。

### 2.2 为什么 sim 内不能存引用

最直觉但**错误**的 Rust 写法:

```rust
// 错误!
struct SimEntity {
    pos: Vec2,
    target: Option<&SimEntity>,  // 引用另一个 SimEntity
}

struct SimRegion {
    entities: Vec<SimEntity>,
}
```

问题:`&SimEntity` 借用 SimRegion 自己(self-referential struct)。Rust 编译器拒绝,因为:
- Vec push 新元素时可能 realloc(把所有 SimEntity move 到新内存)
- 移动后,旧 `&SimEntity` 悬空
- Rust 的 ownership 模型无法表达"自引用 + 可 realloc"

即使绕过编译器(用 unsafe + Pin),运行时也容易出 bug——每次 push 都要重新 pin 所有引用。

**正确做法**:存 ID(数字),需要时查表。

```rust
struct SimEntity {
    pos: Vec2,
    target_id: Option<EntityId>,  // 用 ID,不是引用
}

struct SimRegion {
    entities: Vec<SimEntity>,
    world_to_sim: HashMap<EntityId, usize>,  // 查表
}

impl SimRegion {
    fn get_target(&self, target_id: EntityId) -> Option<&SimEntity> {
        let idx = *self.world_to_sim.get(&target_id)?;
        self.entities.get(idx)
    }
}
```

ID 是 `u32`(4 字节),无借用。即使 Vec realloc,ID 还在,下次 lookup 找到新位置。

### 2.3 Build 时机

```rust
fn unpack(world: &World, sim: &mut SimRegion) {
    sim.entities.clear();
    sim.world_to_sim.clear();
    for (id, e) in &world.entities {
        if sim.contains(e.pos) {
            let sim_idx = sim.entities.len();
            sim.world_to_sim.insert(*id, sim_idx);
            sim.entities.push(SimEntity::from_world(*id, e));
        }
    }
}
```

**关键**:`world_to_sim.clear()` 每帧 unpack 开始时调,**丢弃上一帧的映射**。然后重新 build。

如果不清,会有 stale entry——某 entity 上一帧在 sim_idx=5,这一帧 sim 重建后变成 sim_idx=3,但映射还指向 5(错的)。

### 2.4 Pack 时机

```rust
fn pack(world: &mut World, sim: &SimRegion) {
    for se in &sim.entities {
        if let Some(we) = world.entities.get_mut(&se.world_id) {
            *we = WorldEntity::from_sim(se);
        }
    }
    // 不需要清 world_to_sim——下一帧 unpack 会清
}
```

pack 后**不需要立即清映射**——下一帧 unpack 开头会清。映射只在 sim region 寿命内有意义。

### 2.5 查询模式

sim 内代码访问 target:

```rust
fn update_monster(monster_idx: usize, sim: &mut SimRegion, dt: f32) {
    // 读 target_id(只读 monster 自己)
    let target_id = sim.entities[monster_idx].target_id;
    if let Some(tid) = target_id {
        // 查 sim 内位置
        let target_idx = match sim.world_to_sim.get(&tid) {
            Some(&i) => i,
            None => return,  // target 不在 sim region 内,跳过
        };
        // 读 target 位置(只读)
        let target_pos = sim.entities[target_idx].pos;
        // 改 monster 位置(只读 target 后改 monster)
        let monster_pos = sim.entities[monster_idx].pos;
        let dir = target_pos.sub(monster_pos).normalize();
        sim.entities[monster_idx].pos = monster_pos.add(dir.mul(SPEED * dt));
    }
}
```

注意 Rust 的借用规则:
- 不能同时 `&sim.entities[monster_idx]`(读)和 `&mut sim.entities[monster_idx]`(写)
- 解决:先 copy 出来(pos / target_id 是 Copy),mutable 操作时重新索引

或者:

```rust
// 用 split_at_mut 同时借两个不同 index 的可变引用
let (left, right) = sim.entities.split_at_mut(monster_idx);
let monster = &mut left[monster_idx];  // 怪自己
if let Some(&target_idx) = sim.world_to_sim.get(&tid) {
    let target = &right[target_idx - monster_idx - 1];  // 目标
    // 同时 mutable 操作 monster 和 target
}
```

`split_at_mut` 是 Rust 标准库方法,把 Vec 切成两半,各自可变借用,不冲突。

### 2.6 边界情况:target 不在 sim region

如果怪的 target(玩家)不在 sim region 内(玩家走出 sim region 边界),`world_to_sim.get(&tid)` 返回 None。怪怎么办?

**Casey 的处理**:skip 这帧 update(不动)。下一帧玩家重新进入 sim region,继续追。

更复杂的处理:
- 增加 sim region 大小,确保 target 总在内
- 用 world 视图查 target 位置(但这样失去 cache 优势)
- "失去目标"——怪转 Idle 状态

Casey 选最简单的——skip。够用。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

"双视图 + ID 映射"在游戏开发普遍出现:

- **客户端 / 服务器**:客户端有 entity 列表(本地 index),服务器有 entity 列表(network ID)。两边要映射
- **存档 / 运行时**:存档时 entity ID 序列化为字符串,load 时重建映射
- **多 sim region**(Phase 4+):每个 sim region 有自己的 index,但全局 ID 不变
- **Editor / Runtime**:编辑器里 entity 有 GUID,运行时用 local index

**Unity 的 Instance ID vs Entity ID**:Unity 内部每个对象有 Instance ID(运行时)和 GUID(序列化)。两者通过 `EditorUtility.InstanceIDToGUID` 等映射。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核有大量"双 ID 系统":

- **PID vs TID**:进程 ID(主线程的 ID)vs 线程 ID(每个线程的 ID)。在 NPTL 下,TID == 主线程 PID,但子线程的 TID 是独立的。需要映射
- **fd vs file description**:fd 是进程级别的整数(3, 4, 5),file description 是内核级的 struct file *。多个 fd 可以指向同一个 file description(dup)。映射:`current->files->fdt[fd] = file`
- **虚拟地址 vs 物理地址**:进程看虚拟地址,CPU 看物理地址。页表是双向映射(虚拟→物理)
- **inode number vs dentry**:文件系统内 inode 唯一,但目录树里 dentry 包含文件名 → inode 映射

这些都是"两个 ID 系统 + 映射表"模式。今天的 world_to_sim 是同构。

### 3.3 · 数据库视角(额外)

数据库:
- **物理行 ID(PostgreSQL ctid)**:行的物理位置(页号 + 偏移)
- **主键**:用户定义的逻辑 ID
- **索引**:主键 → 物理行 ID 的映射(B+ tree)

查询时:
1. 用户写 `SELECT * FROM users WHERE id = 42`
2. 索引查找:`id=42 → ctid=(5, 3)`
3. 物理读:从 page 5, offset 3 读行

这和 sim region 完全一样:
- 主键 = world EntityId(用户引用的 ID)
- 物理行 ID = sim Vec index(内部访问的位置)
- 索引 = world_to_sim HashMap

**理解 sim region 的引用映射,你理解了数据库索引的核心思想**。

### 3.4 · 🦀 Rust 生态视角

Rust 表达"双视图 + 映射"的几种方式:

#### 方案 A:HashMap(今天 Casey 用)

```rust
struct SimRegion {
    entities: Vec<SimEntity>,
    world_to_sim: HashMap<EntityId, usize>,
}
```

简单直接。HashMap lookup ~50 ns。

#### 方案 B:SlotMap(代际索引)

```rust
use slotmap::SlotMap;
slotmap::new_key_type! { struct SimKey; }

struct SimRegion {
    entities: SlotMap<SimKey, SimEntity>,
}
```

SlotMap 给每个 entity 一个 SimKey,通过 SimKey 访问。SimKey 是 (index, generation) 复合,删除后 generation 增加,旧 key 自动失效。**比 HashMap 更安全**(检测 stale key)。

#### 方案 C:每个 SimEntity 自带 world_id,线性查找

```rust
impl SimRegion {
    fn find_by_world_id(&self, id: EntityId) -> Option<&SimEntity> {
        self.entities.iter().find(|e| e.world_id == id)
    }
}
```

线性查找 O(N)。N=几百时还 OK,但比 HashMap O(1) 慢。

#### 推荐方案

教学阶段(Phase 2):方案 A,理解映射思想
生产阶段(Phase 4+):方案 B(SlotMap),自动检测 stale

## 4 · 认知地图

### 4.1 上级

- **Multi-view state** —— 同一份逻辑数据有多种"视图"(空间 / 时间 / 网络拓扑)
- **Reference mapping** —— 视图间通过映射表关联
- **Stale reference problem** —— 旧映射指向新数据的 bug

### 4.2 同级

| 方案 | 关键差别 | 何时用 |
|---|---|---|
| HashMap 映射(今天) | 简单,但 stale entry 要手动清 | 小规模映射 |
| SlotMap(代际) | 自动检测 stale,代际自增 | 中规模,需要安全 |
| Arena + generational index | 自定义 SlotMap | 需要控制布局 |
| 直接存引用 | Rust 不允许 self-referential | (不可行) |
| Rc<RefCell<>> | 引用计数 + 内部可变 | Rust 黑魔法,不推荐游戏 hot loop |

### 4.3 下级

- **EntityId(u32)** —— 全局唯一
- **sim Vec index(usize)** —— 局部临时
- **world_to_sim HashMap** —— 临时映射
- **Build on unpack** —— 每帧重建
- **Discard on next unpack** —— 不持久化

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 world_to_sim 映射不能持久化(跨帧保留)?

**参考解答**:每帧 unpack 时,sim Vec 是按"遍历 world.entities 的顺序"构建的。这个顺序可能因 HashMap 迭代顺序 / entity 加入退出而变。

举例:
- 第 1 帧:玩家 world_id=42,sim_idx=0(unpack 时玩家先被遍历到)
- 第 2 帧:某 entity 被删除,HashMap 迭代顺序变,玩家 world_id=42,sim_idx=3

如果保留旧映射 `42 → 0`,第 2 帧查 `world_to_sim[42]` 返回 0,但 sim.entities[0] 是另一个 entity。bug。

正确做法:每帧 unpack 时**清空并重建**映射。映射只在一帧内有效。

### Lv2 · 动手实践

**题**:在 day063 基础上加 world_to_sim 映射。验证:
1. 玩家(world_id=1)是怪(world_id=2)的 target
2. unpack 时,怪在 sim.entities 某个 index,玩家在另一个
3. 怪 update 时,通过 `target_id=1` 查 `world_to_sim`,拿到玩家 index,读玩家位置,追玩家
4. 模拟 1 秒,怪和玩家距离应该减小

**完成标准**:模拟前后,怪离玩家距离减小 > 50%。

**参考解答**:

```rust
use std::collections::HashMap;

type EntityId = u32;

#[derive(Clone, Copy, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn add(self, o: Self) -> Self { Self { x: self.x + o.x, y: self.y + o.y } }
    fn mul(self, k: f32) -> Self { Self { x: self.x * k, y: self.y * k } }
    fn sub(self, o: Self) -> Self { Self { x: self.x - o.x, y: self.y - o.y } }
    fn length(self) -> f32 { (self.x * self.x + self.y * self.y).sqrt() }
    fn normalize(self) -> Self {
        let l = self.length();
        if l > 1e-6 { Self::new(self.x / l, self.y / l) } else { Self::new(0.0, 0.0) }
    }
}

#[derive(Clone, Debug)]
struct WorldEntity {
    id: EntityId,
    pos: Vec2,
    vel: Vec2,
    target_id: Option<EntityId>,
}

#[derive(Clone, Debug)]
struct SimEntity {
    world_id: EntityId,
    pos: Vec2,
    vel: Vec2,
    target_id: Option<EntityId>,
}

struct World {
    entities: HashMap<EntityId, WorldEntity>,
    next_id: EntityId,
}

impl World {
    fn new() -> Self { Self { entities: HashMap::new(), next_id: 1 } }
    fn spawn(&mut self, pos: Vec2, target: Option<EntityId>) -> EntityId {
        let id = self.next_id;
        self.next_id += 1;
        self.entities.insert(id, WorldEntity { id, pos, vel: Vec2::new(0.0, 0.0), target_id: target });
        id
    }
}

struct SimRegion {
    entities: Vec<SimEntity>,
    world_to_sim: HashMap<EntityId, usize>,
}

impl SimRegion {
    fn new() -> Self { Self { entities: vec![], world_to_sim: HashMap::new() } }
}

fn unpack(world: &World, sim: &mut SimRegion) {
    sim.entities.clear();
    sim.world_to_sim.clear();
    for (id, e) in &world.entities {
        let idx = sim.entities.len();
        sim.world_to_sim.insert(*id, idx);
        sim.entities.push(SimEntity {
            world_id: *id, pos: e.pos, vel: e.vel, target_id: e.target_id,
        });
    }
}

const MONSTER_SPEED: f32 = 50.0;

fn simulate(sim: &mut SimRegion, dt: f32) {
    let n = sim.entities.len();
    for i in 0..n {
        let target_id = sim.entities[i].target_id;
        if let Some(tid) = target_id {
            // 通过 world_to_sim 查 sim 内 index
            if let Some(&target_idx) = sim.world_to_sim.get(&tid) {
                if target_idx >= sim.entities.len() { continue; }
                let monster_pos = sim.entities[i].pos;
                let target_pos = sim.entities[target_idx].pos;
                let dir = target_pos.sub(monster_pos).normalize();
                sim.entities[i].pos = monster_pos.add(dir.mul(MONSTER_SPEED * dt));
            }
        }
    }
}

fn pack(world: &mut World, sim: &SimRegion) {
    for se in &sim.entities {
        if let Some(we) = world.entities.get_mut(&se.world_id) {
            we.pos = se.pos;
            we.vel = se.vel;
        }
    }
}

fn main() {
    let mut world = World::new();
    let player = world.spawn(Vec2::new(500.0, 500.0), None);
    let monster = world.spawn(Vec2::new(100.0, 100.0), Some(player));
    println!("player id = {}, monster id = {}", player, monster);

    let dist_before = {
        let p = &world.entities[&player];
        let m = &world.entities[&monster];
        m.pos.sub(p.pos).length()
    };
    println!("dist before: {:.1}", dist_before);

    let mut sim = SimRegion::new();
    let dt = 1.0 / 60.0;
    for frame in 0..180 {  // 3 秒
        unpack(&world, &mut sim);
        simulate(&mut sim, dt);
        pack(&mut world, &sim);
    }

    let dist_after = {
        let p = &world.entities[&player];
        let m = &world.entities[&monster];
        m.pos.sub(p.pos).length()
    };
    println!("dist after: {:.1}", dist_after);

    assert!(dist_after < dist_before * 0.5, "monster should have approached player");
    println!("OK");
}
```

### Lv3 · 迁移设计

**题**:多 sim region 场景。两个玩家 P1 在 (100, 100)、P2 在 (900, 900),各自一个 sim region。P1 的怪追 P1,P2 的怪追 P2。但中间地带的怪可能被两个 sim region 同时模拟。

如何避免:
- 同一个 entity 在两个 sim region 都被 update,导致速度翻倍?
- pack 时两个 sim region 都写回,谁覆盖谁?

**提示**:
- 给每个 entity 一个 "owning_sim" 字段
- unpack 时,只把没有 owner 的 entity 加进 sim region
- pack 时,clear owner

## 8 · Rust / Arch 落地代码

### 关键 Rust 特性

#### HashMap::get / get_mut

```rust
let idx: Option<&usize> = sim.world_to_sim.get(&tid);
let we: Option<&mut WorldEntity> = world.entities.get_mut(&se.world_id);
```

`get` 返回 `Option<&V>`(不可变),`get_mut` 返回 `Option<&mut V>`(可变)。Rust 的 HashMap 不像 C++ 的 `[]` 自动插入——避免无意的"空 key 创建"。

#### Index 借用规则

```rust
let monster_pos = sim.entities[i].pos;  // 复制(Vec2 是 Copy)
let target_pos = sim.entities[target_idx].pos;
sim.entities[i].pos = ...;  // 这里 mutable 借用
```

如果直接 `&sim.entities[i]` 和 `&mut sim.entities[i]` 在同一作用域,borrow checker 报错。Workaround:
1. Copy 字段先复制出来
2. 用 `split_at_mut` 切两个 mut 引用
3. 收集要改的 index,循环外统一改

#### split_at_mut

```rust
let (left, right) = sim.entities.split_at_mut(i);
let monster = &mut left[i];  // 错!left.len() == i,left[i] 越界
```

正确用法:

```rust
// 假设 monster_idx < target_idx
let (left, right) = sim.entities.split_at_mut(target_idx);
// left = entities[0..target_idx]
// right = entities[target_idx..]
let monster = &mut left[monster_idx];
let target = &right[0];
```

或者:

```rust
// 任意顺序
let (a, b) = if monster_idx < target_idx {
    let (l, r) = sim.entities.split_at_mut(target_idx);
    (&mut l[monster_idx], &r[0])
} else {
    let (l, r) = sim.entities.split_at_mut(monster_idx);
    (&r[0], &mut l[target_idx])
};
```

复杂,但有时必要。Casey 用 `Vec<SimEntity>` + index,避免 split_at_mut,直接 Copy + mutable reassign。
