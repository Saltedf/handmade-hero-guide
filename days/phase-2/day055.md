# Day 055 · 基于哈希的世界存储

> 游戏世界是稀疏的——10000×10000 tile 但大部分空旷。如果用 `Vec<Tile>` 直接存,需要 1 亿个 slot(几百 MB)。Day 055 Casey 手写一个**哈希表**,只存"有 entity 的 tile"。key 是 `(tile_x, tile_y)`,value 是 entity 数据。核心是 hash function + bucket 数组 + chaining。

## 0 · 为什么要有这一天

游戏世界地图可能很大。HH 的最终地图 100000 × 100000 tile(10¹⁰ 个 tile)。如果用 `Vec<Tile>` 直接存,即使每个 tile 只 1 字节,需要 10 GB——不可能。

**实际地图是稀疏的**:99% 的 tile 是空(玩家没去过 / 没生成)。只有少数 tile 有 entity(玩家附近、已生成的房间)。

**解决**:用哈希表存。key = tile 坐标,value = entity。只存"有 entity 的 tile"。10⁵ 个有 entity 的 tile vs 10¹⁰ 个总 tile——节省 10⁵ 倍内存。

但 std::HashMap 已经做了这件事,为什么 Casey 自己写?**教学**:

1. 理解哈希表内部原理(以后用 std 时心里有数)
2. 控制内存布局(固定 bucket 数,无动态分配)
3. 自定义 hash function(针对 tile 坐标优化)

Day 055 是 HH 第一次"重新发明轮子"。Casey 强调"理解原理后用 std 的更放心"。

**核心概念**:

- **Hash function**:把 key `(i32, i32)` 映射到 bucket 索引 `[0, N)`
- **Bucket 数组**:固定大小 N,每个 bucket 存"hash 到这个 bucket 的所有 (key, value)"
- **Chaining**:bucket 是 Vec 或链表,存多个 entry
- **Collision**:不同 key 映射到同一 bucket,用 chaining 解决
- **Load factor**:元素数 / bucket 数,> 0.7 时性能下降

**Magic number**:`0x9e3779b9`(黄金分割常数),Casey 用它做 hash 乘法因子,让 key 均匀分布。

心理锚点:做完今天,你应该:

2. 理解 std::HashMap 内部原理(桶数组 + 链表 / 开放寻址)

## 2 · 心智模型

### 费曼类比:邮政编码 + 邮筒

想象一个邮政系统:

- **每个地址**有一个唯一编码(邮政编码 + 详细地址)
- **邮筒**(bucket)是分组的:邮政编码 100000 的信都进 100 号邮筒
- **多个地址可能映射到同一邮筒**(collision)——邮筒里有多封信
- **邮递员**(lookup)根据邮政编码找到邮筒,然后逐封看是不是要找的

哈希表完全类似:

- **key** = 地址
- **hash function** = 邮政编码 → 邮筒号 的映射规则
- **bucket** = 邮筒
- **collision** = 多个 key 映射到同一 bucket
- **chaining** = 邮筒里有多封信,逐封比对

**好的哈希函数**让信均匀分布到所有邮筒(没有邮筒塞爆)。**差的哈希函数**让所有信挤到一个邮筒(退化成链表)。

### 严谨定义:哈希表

**哈希表**(hash table / hash map)是关联数组(associative array)的实现,提供 O(1) 平均时间的插入 / 查找 / 删除。

**核心数据结构**:

```rust
pub struct HashTable<K, V> {
    buckets: Vec<Vec<(K, V)>>,  // bucket 数组,每个 bucket 是 Vec(separate chaining)
    size: usize,
}
```

**核心操作**:

```rust
impl<K: Hash + Eq, V> HashTable<K, V> {
    pub fn insert(&mut self, key: K, value: V) {
        let bucket_idx = self.hash(&key);
        let bucket = &mut self.buckets[bucket_idx];
        // 检查 key 是否已存在
        for entry in bucket.iter_mut() {
            if entry.0 == key {
                entry.1 = value;
                return;
            }
        }
        bucket.push((key, value));
        self.size += 1;
    }

    pub fn get(&self, key: &K) -> Option<&V> {
        let bucket_idx = self.hash(key);
        self.buckets[bucket_idx].iter()
            .find(|entry| &entry.0 == key)
            .map(|entry| &entry.1)
    }

    fn hash(&self, key: &K) -> usize {
        use std::collections::hash_map::DefaultHasher;
        use std::hash::Hasher;
        let mut hasher = DefaultHasher::new();
        key.hash(&mut hasher);
        (hasher.finish() as usize) % self.buckets.len()
    }
}
```

### Hash Function 的设计

**任务**:把任意 key 均匀映射到 [0, N)。

**差的 hash**(模 N):

```
hash(x) = x % N
```

如果 key 是 `1, 2, 3, ..., N`,均匀。但如果 key 是 `N, 2N, 3N, ...`,全部 hash 到 0——collision 爆炸。

**Knuth 乘法 hash**(用黄金分割):

```
hash(x) = (x * 0x9e3779b9) >> (32 - log2(N))
```

0x9e3779b9 = 2654435769 ≈ 2³² / φ(φ = (1+√5)/2 ≈ 1.618,黄金比例)。

**为什么黄金分割?** Knuth 在《The Art of Computer Programming》卷三证明:用 1/φ 作为乘法因子,让连续 key 在 hash 空间均匀分布。这是数学最优。

**0x9e3779b9 推导**:

```
φ = (1 + sqrt(5)) / 2 ≈ 1.6180339887...
1/φ ≈ 0.6180339887...
frac(1/φ) ≈ 0.618...
2^32 * frac(1/φ) ≈ 0.618 * 4294967296 ≈ 2654435769
                                       = 0x9e3779b9
```

### 针对	tile 坐标的 hash

Casey 的 HH 用 `(i32, i32)` 作为 key。hash function:

```rust
fn hash_tile(x: i32, y: i32) -> u32 {
    // 把 x 和 y 混合,用黄金分割
    let h = (x.wrapping_mul(0x9e3779b9) as u32)
          .wrapping_add(y.wrapping_mul(0x85ebca6b) as u32);
    h
}

fn bucket_index(x: i32, y: i32, bucket_count: usize) -> usize {
    (hash_tile(x, y) as usize) % bucket_count
}
```

- x 乘一个常数,y 乘另一个常数,加起来。两个不同的常数避免"x = y" 的 collision
- 用 wrapping_mul 避免溢出 panic(i32 乘法可能溢出)

### Bucket 数组

```rust
pub struct TileHashTable {
    buckets: Vec<Vec<((i32, i32), TileData)>>,
}

impl TileHashTable {
    pub fn new(bucket_count: usize) -> Self {
        Self {
            buckets: vec![Vec::new(); bucket_count],
        }
    }

    pub fn insert(&mut self, x: i32, y: i32, data: TileData) {
        let idx = self.bucket_index(x, y);
        let bucket = &mut self.buckets[idx];
        // 检查重复
        for entry in bucket.iter_mut() {
            if entry.0 == (x, y) {
                entry.1 = data;
                return;
            }
        }
        bucket.push(((x, y), data));
    }

    pub fn get(&self, x: i32, y: i32) -> Option<&TileData> {
        let idx = self.bucket_index(x, y);
        self.buckets[idx].iter()
            .find(|entry| entry.0 == (x, y))
            .map(|entry| &entry.1)
    }

    pub fn remove(&mut self, x: i32, y: i32) -> Option<TileData> {
        let idx = self.bucket_index(x, y);
        let bucket = &mut self.buckets[idx];
        if let Some(position) = bucket.iter().position(|entry| entry.0 == (x, y)) {
            Some(bucket.remove(position).1)
        } else {
            None
        }
    }

    fn bucket_index(&self, x: i32, y: i32) -> usize {
        let h = hash_tile(x, y);
        (h as usize) % self.buckets.len()
    }
}
```

### Collision 处理:Separate Chaining

**Separate chaining**(分离链):每个 bucket 是一个链表 / Vec。Collision 的 key 加到同一 bucket 的链表里。

```
buckets[0] → [(k1, v1)] → [(k5, v5)] → null
buckets[1] → [(k2, v2)] → null
buckets[2] → null
buckets[3] → [(k3, v3)] → [(k7, v7)] → [(k9, v9)] → null
...
```

**优点**:简单,容易实现。**缺点**:链表跳转不 cache-friendly。

**Open addressing**(开放寻址):collision 时找下一个空 bucket。Cache-friendly 但删除复杂。std::HashMap(Rust)用 Robin Hood hashing(开放寻址变体)。

### Load Factor

**Load factor**(装载因子)= 元素数 / bucket 数。

```
load_factor = size / bucket_count
```

**性能影响**:

- load_factor < 0.5:每个 bucket 平均 < 0.5 个元素,查找快
- load_factor = 0.7:每个 bucket 平均 0.7 个元素,有 collision 但 OK
- load_factor > 0.9:collision 频繁,查找变慢(O(N) 退化)
- load_factor > 1.0:不可能(chaining 容纳所有,但极慢)

**Casey 的选择**:固定 bucket 数(比如 4096),不 rehash。简单但可能退化(如果游戏发展后元素超 4000)。

**std::HashMap 的做法**:load_factor > 0.875 时自动 rehash(扩大 bucket 数组 + 重 hash 所有元素)。安全但有 rehash 开销。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的哈希表应用:

**1. 稀疏 tile map**(Day 055):大世界,只存有内容的 tile。

**2. Entity lookup**:用 EntityId 作为 key 快速查 entity(替代 Vec 线性查找)。

**3. Asset cache**:用路径作为 key,缓存已加载的资产(避免重复加载)。

**4. Spatial hash**(Day 057):用 tile 坐标作为 key,值是"该 tile 内的所有 entity"。加速碰撞检测。

**5. Network packet dedup**:服务器用包 ID 作为 key,去重客户端重传的包。

#### 哈希表 vs 数组

| | 数组 (Vec) | 哈希表 (HashMap) |
|---|---|---|
| 索引 | 整数 `[0, N)` | 任意 hashable 类型 |
| 查找 | O(1) | O(1) 平均,O(N) 最坏 |
| 内存 | 紧凑 | 有 bucket 开销 |
| Cache | 友好 | 不友好(随机访问) |
| 适合 | 密集数据 | 稀疏数据 |

游戏用数组存"密集数据"(entity 数组),哈希表存"稀疏数据"(tile map)。

### 3.2 · 🎨 图形学视角

图形学的哈希应用:

**1. Texture cache**:GPU 用 texture ID 作为 key,缓存已上传的纹理。

**2. Shader cache**:用 shader 源码 hash 作为 key,缓存编译后的 shader。

**3. Mesh instance**:用 mesh ID 作为 key,批量渲染相同 mesh 的 instance。

**4. Light grid**(cluster forward rendering):把屏幕分成 3D 网格,每个 cell 存影响它的光源列表。本质是 spatial hash。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的哈希应用:

**1. inode cache**(VFS):用 inode 号作为 key,缓存已读取的 inode。

**2. dcache**:用路径作为 key,缓存目录项。

**3. page cache**:用文件 offset 作为 key,缓存文件页。

**4. process table**:用 PID 作为 key,查进程。

**5. socket hash**:用 (src_ip, src_port, dst_ip, dst_port) 作为 key,网络包快速路由。

#### Rust 的 HashMap

#### 测试

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_insert_get() {
        let mut table = TileHashTable::new(64);
        table.insert(5, 5, TileData { wall: true });
        let data = table.get(5, 5);
        assert!(data.is_some());
        assert!(data.unwrap().wall);
    }

    #[test]
    fn test_get_missing() {
        let table = TileHashTable::new(64);
        assert!(table.get(100, 100).is_none());
    }

    #[test]
    fn test_collision_correctness() {
        let mut table = TileHashTable::new(4);  // 很小,强制 collision
        table.insert(0, 0, TileData { wall: true });
        table.insert(1, 1, TileData { wall: false });
        table.insert(2, 2, TileData { wall: true });
        table.insert(3, 3, TileData { wall: false });
        // 4 个 entry 进 4 个 bucket,collision 必然
        // 但应该都能正确 get
        assert!(table.get(0, 0).unwrap().wall);
        assert!(!table.get(1, 1).unwrap().wall);
        assert!(table.get(2, 2).unwrap().wall);
        assert!(!table.get(3, 3).unwrap().wall);
    }

    #[test]
    fn test_overwrite() {
        let mut table = TileHashTable::new(64);
        table.insert(5, 5, TileData { wall: true });
        table.insert(5, 5, TileData { wall: false });  // 覆盖
        assert!(!table.get(5, 5).unwrap().wall);
    }

    #[test]
    fn test_remove() {
        let mut table = TileHashTable::new(64);
        table.insert(5, 5, TileData { wall: true });
        assert!(table.remove(5, 5).is_some());
        assert!(table.get(5, 5).is_none());
    }

    #[test]
    fn test_distribution() {
        // 验证 hash function 均匀分布
        let mut counts = vec![0u32; 64];
        let table = TileHashTable::new(64);
        for x in 0..1000 {
            for y in 0..10 {
                let idx = table.bucket_index(x, y);
                counts[idx] += 1;
            }
        }
        // 每个 bucket 应该有合理数量(不是全部挤一个)
        let max_count = *counts.iter().max().unwrap();
        let avg_count = (1000 * 10) / 64;
        // max 不应该超过 avg 的 5 倍
        assert!(max_count < (avg_count * 5) as u32,
                "max={}, avg={}", max_count, avg_count);
    }
}

### 4.1 上级

## 5 · 对照与变奏

### 不同 collision 处理方案

| 方案 | 实现 | 优点 | 缺点 | 用 |
|---|---|---|---|---|
| Separate chaining | bucket 是链表 / Vec | 简单 | 不 cache-friendly | Casey |
| Open addressing(线性探查)| collision 找下一个空 bucket | cache-friendly | 删除复杂 | Python dict |
| Robin Hood hashing | open addressing + "劫富济贫" | 极 cache-friendly | 实现复杂 | Rust std |
| Cuckoo hashing | 两个 hash function,两个表 | 查找 O(1) 严格 | 插入复杂 | BloomFilter 替代 |
| Hopscotch hashing | open addressing + 限制范围 | cache-friendly + 简单 | 较新 | 部分数据库 |

### Hash function 演化

- **1970s**:简单 mod / 乘法
- **1990s**: cryptographic hash(MD5 / SHA)
- **2000s**: MurmurHash、CityHash、FarmHash(Google)
- **2010s**: SipHash(抗攻击)、xxHash(极快)
- **2020s**: SIMD 加速 hash、硬件 CRC32

```bash

```

### 2D vs 高维 key

Casey 用 `(i32, i32)` 作 key。如果是 3D:`(i32, i32, i32)`,hash function 推广:

```rust
fn hash_3d(x: i32, y: i32, z: i32) -> u32 {
    (x.wrapping_mul(0x9e3779b9) as u32)
        .wrapping_add(y.wrapping_mul(0x85ebca6b) as u32)
        .wrapping_add(z.wrapping_mul(0xc2b2ae35) as u32)
}
```

三个不同常数,避免对称 collision。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:0x9e3779b9 这个 magic number 是什么?为什么用它做 hash 因子?

**参考解答**:

**0x9e3779b9 = 2654435769(十进制)**,这是黄金分割常数 2³² / φ 的整数部分(φ = (1+√5)/2 ≈ 1.618,黄金比例)。

**为什么用黄金分割?**

Knuth 在《The Art of Computer Programming》卷三证明:**用 1/φ 作为乘法 hash 因子,让连续 key 在 hash 空间均匀分布**。这是数学最优。

**直觉**:黄金比例 φ 是"最无理数"——它的连分数展开全是 1(`[1; 1, 1, 1, ...]`),最难被有理数近似。所以 `k * φ` 对所有 k 都"远离整数"——hash 后分布最均匀。

**实际效果**:对 key `1, 2, 3, ..., N`,简单 mod hash 让 `N, 2N, 3N, ...` 全 hash 到 0。乘以 0x9e3779b9 让这些 key 散开到不同 bucket。

**Rust 例子**:

```rust
let phi_frac = 0x9e3779b9u32;
for k in [1, 2, 3, 100, 1000, 10000] {
    let hash = (k as u32).wrapping_mul(phi_frac) >> (32 - 6);  // 6 = log2(64)
    println!("k={} → bucket={}", k, hash);
}
// 输出:每个 k 映射到不同 bucket,均匀分布
```

**生产代码**:`std::collections::hash_map::DefaultHasher` 用更复杂的 SipHash(抗攻击),但原理类似。

```rust
// src/tile_hash.rs
use std::collections::HashMap;

const PHI_FRAC: u32 = 0x9e3779b9;
const PHI_FRAC_ALT: u32 = 0x85ebca6b;

#[derive(Clone, Debug, PartialEq)]
pub struct TileData {
    pub wall: bool,
    pub entity_count: u32,
}

pub struct TileHashTable {
    buckets: Vec<Vec<((i32, i32), TileData)>>,
}

impl TileHashTable {
    pub fn new(bucket_count: usize) -> Self {
        // bucket_count 必须是 2 的幂(用 & 替代 %)
        let bucket_count = bucket_count.next_power_of_two();
        Self {
            buckets: vec![Vec::new(); bucket_count],
        }
    }

    pub fn insert(&mut self, x: i32, y: i32, data: TileData) {
        let idx = self.bucket_index(x, y);
        let bucket = &mut self.buckets[idx];
        for entry in bucket.iter_mut() {
            if entry.0 == (x, y) {
                entry.1 = data;
                return;
            }
        }
        bucket.push(((x, y), data));
    }

    pub fn get(&self, x: i32, y: i32) -> Option<&TileData> {
        let idx = self.bucket_index(x, y);
        self.buckets[idx].iter()
            .find(|e| e.0 == (x, y))
            .map(|e| &e.1)
    }

    pub fn remove(&mut self, x: i32, y: i32) -> Option<TileData> {
        let idx = self.bucket_index(x, y);
        let bucket = &mut self.buckets[idx];
        if let Some(pos) = bucket.iter().position(|e| e.0 == (x, y)) {
            Some(bucket.remove(pos).1)
        } else {
            None
        }
    }

    pub fn len(&self) -> usize {
        self.buckets.iter().map(|b| b.len()).sum()
    }

    pub fn is_empty(&self) -> bool {
        self.len() == 0
    }

    pub fn load_factor(&self) -> f32 {
        let total = self.len();
        let bucket_count = self.buckets.len();
        total as f32 / bucket_count as f32
    }

    fn bucket_index(&self, x: i32, y: i32) -> usize {
        let h = hash_tile(x, y);
        // 用 & 替代 %(bucket_count 是 2 的幂)
        (h as usize) & (self.buckets.len() - 1)
    }
}

fn hash_tile(x: i32, y: i32) -> u32 {
    let x_h = (x as u32).wrapping_mul(PHI_FRAC);
    let y_h = (y as u32).wrapping_mul(PHI_FRAC_ALT);
    x_h.wrapping_add(y_h)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_insert_get() {
        let mut t = TileHashTable::new(64);
        t.insert(5, 5, TileData { wall: true, entity_count: 0 });
        let data = t.get(5, 5);
        assert!(data.is_some());
        assert!(data.unwrap().wall);
    }

    #[test]
    fn test_get_missing() {
        let t = TileHashTable::new(64);
        assert!(t.get(100, 100).is_none());
    }

    #[test]
    fn test_collision_correctness() {
        let mut t = TileHashTable::new(4);  // 极小,必 collision
        t.insert(0, 0, TileData { wall: true, entity_count: 0 });
        t.insert(1, 1, TileData { wall: false, entity_count: 1 });
        t.insert(2, 2, TileData { wall: true, entity_count: 2 });
        t.insert(3, 3, TileData { wall: false, entity_count: 3 });

        assert!(t.get(0, 0).unwrap().wall);
        assert!(!t.get(1, 1).unwrap().wall);
        assert_eq!(t.get(2, 2).unwrap().entity_count, 2);
        assert_eq!(t.get(3, 3).unwrap().entity_count, 3);
    }

    #[test]
    fn test_overwrite() {
        let mut t = TileHashTable::new(64);
        t.insert(5, 5, TileData { wall: true, entity_count: 0 });
        t.insert(5, 5, TileData { wall: false, entity_count: 10 });
        assert!(!t.get(5, 5).unwrap().wall);
        assert_eq!(t.get(5, 5).unwrap().entity_count, 10);
    }

    #[test]
    fn test_remove() {
        let mut t = TileHashTable::new(64);
        t.insert(5, 5, TileData { wall: true, entity_count: 0 });
        assert!(t.remove(5, 5).is_some());
        assert!(t.get(5, 5).is_none());
    }

    #[test]
    fn test_distribution() {
        let t = TileHashTable::new(64);
        let mut counts = vec![0u32; 64];
        for x in 0..1000 {
            for y in 0..10 {
                let idx = t.bucket_index(x, y);
                counts[idx] += 1;
            }
        }
        let total: u32 = counts.iter().sum();
        let avg = total / 64;
        let max = *counts.iter().max().unwrap();
        // max 不应超过 avg 的 3 倍(均匀分布)
        assert!(max < avg * 3, "max={}, avg={}", max, avg);
    }

    #[test]
    fn test_load_factor() {
        let mut t = TileHashTable::new(64);
        for i in 0..32 {
            t.insert(i, 0, TileData { wall: true, entity_count: 0 });
        }
        // 32 个元素 / 64 个 bucket = 0.5
        assert!((t.load_factor() - 0.5).abs() < 0.01);
    }
}
```

**关键决策解释**:

- `bucket_count.next_power_of_two()`:让 bucket 数是 2 的幂,可以用 `& (n - 1)` 替代 `% n`。位运算快于除法。
- 两个不同常数(0x9e3779b9, 0x85ebca6b)避免 `(0, 5)` 和 `(5, 0)` 等 collision。

### Lv3 · 迁移设计

**题**:实现**LRU 缓存**(Least Recently Used):当缓存满时,删除最久没用的 entry。

要求:

1. 用 HashMap + 双向链表实现
2. `get(key)`:返回 value,标记为最近用
3. `put(key, value)`:如果满,删除最久未用,再加新的
4. 测试:连续 put + get,验证 LRU 行为

**提示**:

- HashMap 存 key → 链表节点指针
- 双向链表维护"使用顺序",head 是最近用,tail 是最久未用
- get 时把节点移到 head
- put 时如果满,删除 tail,新节点加到 head

为什么这个练习有价值?LRU 是经典面试题,实际用于浏览器 cache、CPU cache、数据库 buffer pool。理解 LRU = 理解 cache 系统。

fn main() {
    println!("=== 哈希表演示 ===\n");

    let mut table = TileHashTable::new(64);

    // 插入稀疏数据
    println!("--- 插入稀疏数据 ---");
    for x in 0..100 {
        for y in 0..100 {
            if (x + y) % 7 == 0 {  // 稀疏:7% 的位置有数据
                table.insert(x, y, TileData {
                    wall: (x * y) % 2 == 0,
                    entity_count: (x + y) as u32,
                });
            }
        }
    }
    println!("插入了 {} 个 entry", table.len());
    println!("bucket 数:64");
    println!("load factor:{:.3}", table.load_factor());

    // 查找
    println!("\n--- 查找 ---");
    for (x, y) in [(0, 0), (1, 6), (5, 2), (100, 100)] {
        match table.get(x, y) {
            Some(data) => println!("  ({}, {}): wall={}, entities={}",
                                   x, y, data.wall, data.entity_count),
            None => println!("  ({}, {}): 不存在", x, y),
        }
    }

    // 删除
    println!("\n--- 删除 ---");
    let removed = table.remove(0, 0);
    println!("删除 (0, 0):{:?}", removed);
    println!("现在 len = {}", table.len());

    // 对比 Vec 内存
    println!("\n--- 内存对比 ---");
    let dense_size = 1000 * 1000 * std::mem::size_of::<TileData>();
    let sparse_size = table.len() * (std::mem::size_of::<((i32, i32), TileData)>());
    println!("如果用 Vec(1000×1000):{} bytes({:.1} KB)",
             dense_size, dense_size as f64 / 1024.0);
    println!("哈希表(稀疏):{} bytes({:.1} KB)",
             sparse_size, sparse_size as f64 / 1024.0);
    println!("节省:{}x", dense_size / sparse_size.max(1));

    // 哈希函数均匀分布
    println!("\n--- Hash 均匀分布验证 ---");
    let mut dist = vec![0u32; 8];
    for i in 0..10000i32 {
        // 简化:用 i, i+1 做 key
        let bucket = ((
            (i as u32).wrapping_mul(0x9e3779b9)
                .wrapping_add((i+1) as u32)
        ) >> (32 - 3)) as usize;  // 取高 3 位 = 8 个 bucket
        dist[bucket] += 1;
    }
    println!("10000 个 key 分布到 8 个 bucket:");
    for (i, count) in dist.iter().enumerate() {
        println!("  bucket[{}] = {}", i, count);
    }
    // 每个 bucket 应该接近 1250
}

### Troubleshooting

**问题 1**:哈希表查找慢(O(N) 而不是 O(1))

原因:hash function 差,所有 key 挤一个 bucket。

修复:用 0x9e3779b9 黄金分割常数,验证分布均匀。

**问题 2**:load_factor 高,性能下降

原因:bucket 数太少,元素太多。

修复:扩大 bucket 数,或自动 rehash(检测 load_factor > 0.7 时扩大 2 倍)。

**问题 3**:删除后查找错乱

原因:删除时没正确维护 chaining 链表。

修复:`Vec::remove(position)` 正确处理索引,不会跳过元素。

**问题 4**:wrap_add 溢出报错

原因:i32 / u32 乘法溢出 panic(debug 模式)。

修复:用 `wrapping_mul`、`wrapping_add` 显式说明允许溢出。
