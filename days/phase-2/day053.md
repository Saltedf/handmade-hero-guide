
# Day 053 · 环境元素作为实体

> Day 028 你定义了 TileMap(Wall / Floor / Water),Day 029 玩家和 Wall tile 碰撞。Day 053 Casey 做一个架构转折:**门、宝箱、按钮**这种"有状态的环境元素"从 tile 改成 entity。理由:tile 没状态(墙永远墙),而门需要"打开 / 关闭"状态。统一成 entity 后,所有游戏对象一个接口(update + render)。

## 0 · 为什么要有这一天

回看 Day 028 的 TileValue 枚举:

```rust
pub enum TileValue {
    Empty, Wall, Floor, Water, Door, Chest, ...
}
```

每个 tile 是一个变体。问题:**Door / Chest 需要状态**(打开 / 关闭,捡过 / 没捡),但 enum 变体不存状态。

变通方案 1:**两个枚举**:

```rust
pub enum TileValue { Wall, Floor, Water, Door, Chest }
pub enum DoorState { Closed, Open }
// tile.get(x, y) 返回 TileValue
// door_state.get(x, y) 返回 Option<DoorState>
```

但每个有状态的 tile 都要额外维护状态 map,代码冗长。

变通方案 2:**所有 tile 都存状态**(浪费):

```rust
pub struct Tile { value: TileValue, state: Option<TileState> }
```

大部分 tile(Wall / Floor)的 state 永远是 None,浪费内存。

**Casey 在 Day 053 的决定**:**把有状态的环境元素(门、宝箱、按钮、触发器)从 tile 改成 entity**。tile 只表示"完全静态的地形"(Wall / Floor / Water),有状态的对象都是 entity。

**好处**:

1. **统一接口**:所有 entity 都 update + render
2. **状态自然**:entity 字段存状态(`Door { open: bool }`)
3. **碰撞一致**:所有碰撞用 Day 050 的 AABB,不用区分 tile vs entity

**代价**:entity 数量从几十(玩家 + 怪物)暴涨到几千(加门、宝箱、装饰)。性能可能成问题,但 Day 057 spatial partition 解决。

这是游戏行业常见的**架构演化**:从"地形 + 实体"二元 → "全是实体"。Unity / Unreal 都用 actor(类似 entity)为中心。

心理锚点:做完今天,你应该:

1. 理解"有状态对象 vs 无状态对象"的架构区分
2. 能设计 `EntityKind` 枚举覆盖所有游戏对象
3. 知道 tile-based → entity-based 演化的动机和代价

## 2 · 心智模型

### 费曼类比:舞台剧的道具

舞台剧的元素分两类:

**布景**(scenery):墙壁、地板、天花板。整个剧不变。一次性搭好,观众无视。

**道具**(props):门、椅子、宝箱。演员(玩家、怪物)可以与之互动——开门、坐椅子、开宝箱。道具有"状态"(门开 / 关、宝箱空 / 满)。

**Casey 的设计**:

- **Tile** = 布景(Wall、Floor)。无状态,只渲染。
- **Entity** = 道具 + 演员(Door、Chest、Player、Monster)。有状态,update + render。

游戏世界 = 布景(tile,静态)+ 道具和演员(entity,动态)。

### 严谨定义:Entity 数据结构

```rust
#[derive(Clone, Debug)]
pub enum EntityKind {
    Player,
    Monster,
    Projectile,
    Door { open: bool, locked: bool },
    Chest { opened: bool, contents: Vec<Item> },
    Button { pressed: bool, target: EntityId },
    Decoration { kind: DecorationKind },
    // 后续可以加更多
}

pub struct Entity {
    pub id: EntityId,  // 唯一 ID
    pub pos: Vec2,
    pub half_size: Vec2,  // 用于 AABB 碰撞
    pub kind: EntityKind,
}
```

**关键字段**:

- `id`:每个 entity 唯一标识(代际索引,Day 055+ 学)
- `pos`:世界坐标
- `half_size`:AABB 半宽,用于碰撞
- `kind`:具体类型 + 状态

**EntityKind 是带数据的 enum**(Rust 的 tagged union)。不同变体带不同字段。

### 渲染统一

```rust
impl Entity {
    pub fn render(&self, render_buf: &mut RenderBuf) {
        match &self.kind {
            EntityKind::Player => self.render_player(render_buf),
            EntityKind::Monster => self.render_monster(render_buf),
            EntityKind::Door { open } => {
                let bitmap = if *open { DOOR_OPEN_BMP } else { DOOR_CLOSED_BMP };
                render_buf.push_bitmap(self.pos, bitmap);
            }
            EntityKind::Chest { opened, .. } => {
                let bitmap = if *opened { CHEST_OPEN_BMP } else { CHEST_CLOSED_BMP };
                render_buf.push_bitmap(self.pos, bitmap);
            }
            EntityKind::Button { pressed, .. } => {
                let bitmap = if *pressed { BUTTON_PRESSED_BMP } else { BUTTON_NORMAL_BMP };
                render_buf.push_bitmap(self.pos, bitmap);
            }
            EntityKind::Decoration { kind } => {
                let bitmap = decoration_bitmap(*kind);
                render_buf.push_bitmap(self.pos, bitmap);
            }
            EntityKind::Projectile => self.render_projectile(render_buf),
        }
    }
}
```

**match 强制穷尽**:加新 EntityKind 时编译器提示所有 match 加新分支。这是 Rust enum 的强项。

### Update 统一

```rust
impl Entity {
    pub fn update(&mut self, world: &mut World, input: &GameInput, dt: f32) {
        match &mut self.kind {
            EntityKind::Player => self.update_player(input, dt),
            EntityKind::Monster => self.update_monster(world, dt),
            EntityKind::Projectile => self.update_projectile(dt),
            EntityKind::Door { open, .. } => {
                // 门不主动 update,等待玩家触发
            }
            EntityKind::Chest { opened, .. } => {
                // 宝箱同上,等待玩家触发
            }
            EntityKind::Button { pressed, target } => {
                // 按钮检查玩家是否站上来
                // 如果是,pressed = true,触发 target
            }
            EntityKind::Decoration { .. } => {
                // 装饰可能动画(旗帜摆动),但极轻
            }
        }
    }
}
```

**触发交互**:玩家靠近门时,调 `door.kind = Door { open: true, .. }`。门本身被动 update,状态由外部改。

### 碰撞规则按 kind

不同 EntityKind 有不同碰撞行为:

| Kind | 与玩家碰撞 | 与投射物碰撞 |
|---|---|---|
| Player | (本身) | (本身) |
| Monster | 攻击玩家 | 投射物伤害怪物 |
| Projectile | (本身) | (本身) |
| Door(关) | 阻挡 | 阻挡 |
| Door(开) | 不阻挡 | 不阻挡 |
| Chest | 阻挡 | 阻挡 |
| Button | 不阻挡(踩上去) | 不阻挡 |
| Decoration | 看种类(墙装饰阻挡,草不阻挡) | 看种类 |

Day 069 的 pairwise collision rules 详细做这个。

```rust
impl Entity {
    pub fn blocks_player(&self) -> bool {
        match &self.kind {
            EntityKind::Door { open, .. } => !open,  // 关门阻挡,开门不挡
            EntityKind::Chest { .. } => true,
            EntityKind::Monster => true,
            EntityKind::Button { .. } => false,  // 玩家可以踩
            _ => false,
        }
    }
}
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对"什么算 entity"的设计:

**1. Tile-based**(老 RPG、Pokemon):几乎全是 tile,极少 entity。性能极好但灵活性差。

**2. Hybrid**(超级马里奥、Zelda):tile 做地形,entity 做有状态物体。Casey HH 是这种。

**3. Pure entity**(Unity、Unreal):没有 tile 概念,全是 entity。墙体也是 entity。灵活但性能需优化。

**4. ECS**(Bevy、Overwatch):数据驱动,组件化。entity 是 ID,组件是数据,system 是逻辑。Phase 5+ 才讨论。

**演化趋势**:从 tile-based → pure entity → ECS。每步都是灵活性换性能,然后性能优化找回。

#### 实战坑点

**坑 1:entity 数量爆炸**。10000 个墙块都做成 entity,内存和 update 成本高。

修复:用 spatial partition(Day 057)+ sim region(Day 063)。或者保留 tile 做地形,只让有状态的做 entity(Casey 选这个)。

**坑 2:碰撞规则复杂**。不同 entity 组合有不同规则。

修复:用 collision matrix(N×N 表,查表得到行为)。

**坑 3:序列化**。entity 数组保存到存档,需要序列化所有字段。

修复:Rust 的 serde crate 自动 derive Serialize/Deserialize。

### 3.2 · 🎨 图形学视角

图形学里 entity 概念:

**1. Scene graph**:3D 场景图,节点是 entity,边是父子关系。

**2. Mesh instance**:每个 mesh 实例是 entity。GPU 用 instanced rendering 批量画。

**3. Light source**:光源也是 entity(方向光、点光、聚光)。

**4. Camera**:相机也是 entity(可以有多个,分屏游戏)。

Unity / Unreal 的"GameObject"/"Actor"是统一抽象——所有可渲染、可更新的对象都是。

### 3.3 · 🐧 Linux 系统编程视角

Linux 的"统一抽象":

**1. 一切皆文件**(everything is a file):普通文件、设备、网络套接字、管道都是"文件",用 read/write 操作。

**2. 一切皆进程**:线程、进程、子进程,统一调度。

**3. 一切皆对象**(OOP):Java、Smalltalk。

Casey 的"一切皆 entity"是游戏版的统一抽象。这种"统一"让代码简洁(一套接口服务所有),但可能掩盖差异(某些 entity 不需要 update,仍调 update)。

### 3.4 · 🦀 Rust 生态视角

#### Rust 实现 EntityKind

```rust
#[derive(Clone, Debug)]
pub enum EntityKind {
    Player { hp: i32, attack: i32 },
    Monster { hp: i32, ai_state: AiState },
    Projectile { damage: i32, lifetime: f32 },
    Door { open: bool, locked: bool },
    Chest { opened: bool },
    Button { pressed: bool },
    Decoration(DecorationKind),
}

#[derive(Clone, Copy, Debug)]
pub enum AiState { Idle, Chasing, Attacking, Fleeing }

#[derive(Clone, Copy, Debug)]
pub enum DecorationKind { Torch, Statue, Plant, Sign }
```

**带数据的 enum**:每个变体可有不同字段。Rust 自动管理 tag + payload。

**内存布局**:enum 大小 = max(变体大小) + tag(几字节)。如果 Player 占 8 字节,Projectile 占 12 字节,Door 占 2 字节,enum 总大小约 12 + 4(tag) = 16 字节。

#### Serialize

```rust
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Clone, Debug)]
pub enum EntityKind { ... }

// 保存到 JSON
let json = serde_json::to_string(&entity.kind).unwrap();
// 从 JSON 加载
let kind: EntityKind = serde_json::from_str(&json).unwrap();
```

游戏存档用 serde + serde_json,几行代码搞定序列化。

## 5 · 对照与变奏

### 不同游戏的"有状态环境"

**超级马里奥**:旋转的齿轮(可踩)、移动的平台、上下管的植物。都是有状态环境 entity。

**Zelda**:开关、按钮、可推动的方块、火把(可点燃)。都是 entity。

**Hollow Knight**:存档台(坐上去存档)、商店 NPC、Boss 门(需要钥匙打开)。

**Minecraft**:熔炉(状态:燃烧时间、内容物)、箱子(9 格物品)、活塞(可推方块)。

所有这些游戏的"有状态环境"都是 entity。Day 053 的设计原则通用。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么把门从 tile 改成 entity?如果用"两个枚举"方案(TileValue + DoorState),会有什么问题?

**参考解答**:

**改成 entity 的动机**:门需要状态(打开 / 关闭),tile 是无状态值类型。强行让 tile 存状态,代码复杂。

**两个枚举方案的问题**:

1. **数据冗余**:大部分 tile 没有 door 状态,但每个 tile 都要查 `door_state.get(x, y)`,内存和查询成本。
2. **代码分散**:门的渲染、update、碰撞分散在 tile 代码 + door_state 代码,难维护。
3. **加新有状态对象困难**:加宝箱要再加 ChestState map,加按钮要再加 ButtonState map,每种都重复工作。
4. **碰撞规则不一致**:tile 碰撞(Day 029)和 entity 碰撞(Day 050)用不同算法,门"作为 tile" 用一种,"作为有状态" 用另一种,代码混乱。

**统一成 entity 后**:

- 所有有状态对象一个接口(update + render + collide)
- 加新对象 = 加新 EntityKind 变体
- 碰撞用统一 AABB 算法
- 状态直接在 entity 字段里

**代价**:entity 数量增加,需要 spatial partition 优化(Day 057)。但这是值得的——简洁的架构 > 微优化。

```rust
// src/entity.rs
use crate::math::Vec2;

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub struct EntityId(pub u32);

#[derive(Clone, Debug)]
pub enum EntityKind {
    Player { hp: i32 },
    Monster { hp: i32 },
    Projectile { damage: i32 },
    Door { open: bool },
    Chest { opened: bool },
    Button { pressed: bool },
    Decoration,
}

#[derive(Clone, Debug)]
pub struct Entity {
    pub id: EntityId,
    pub pos: Vec2,
    pub half_size: Vec2,
    pub kind: EntityKind,
}

impl Entity {
    pub fn blocks_player(&self) -> bool {
        match &self.kind {
            EntityKind::Player => false,  // 自己不挡自己
            EntityKind::Monster => true,
            EntityKind::Projectile => false,
            EntityKind::Door { open } => !open,  // 关门挡,开门不挡
            EntityKind::Chest { .. } => true,
            EntityKind::Button { .. } => false,
            EntityKind::Decoration => false,
        }
    }

    pub fn color(&self) -> u32 {
        match &self.kind {
            EntityKind::Player { .. } => 0xFF00FF00,  // 绿
            EntityKind::Monster { .. } => 0xFFFF0000,  // 红
            EntityKind::Projectile { .. } => 0xFFFFFF00,  // 黄
            EntityKind::Door { open } => {
                if *open { 0xFF884400 }  // 棕(开)
                else { 0xFF442200 }  // 深棕(关)
            }
            EntityKind::Chest { opened } => {
                if *opened { 0xFF888888 }  // 灰(已开)
                else { 0xFF886600 }  // 金(未开)
            }
            EntityKind::Button { pressed } => {
                if *pressed { 0xFFFF00FF }  // 紫(按下)
                else { 0xFF880088 }  // 深紫
            }
            EntityKind::Decoration => 0xFF444444,  // 深灰
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    fn make_entity(kind: EntityKind) -> Entity {
        Entity {
            id: EntityId(0),
            pos: Vec2::ZERO,

            kind,
        }
    }

    #[test]
    fn test_door_blocks_when_closed() {
        let closed = make_entity(EntityKind::Door { open: false });
        assert!(closed.blocks_player());
    }

    #[test]
    fn test_door_not_blocks_when_open() {
        let open = make_entity(EntityKind::Door { open: true });
        assert!(!open.blocks_player());
    }

    #[test]
    fn test_chest_always_blocks() {
        let closed = make_entity(EntityKind::Chest { opened: false });
        let opened = make_entity(EntityKind::Chest { opened: true });
        assert!(closed.blocks_player());
        assert!(opened.blocks_player());
    }

    #[test]
    fn test_button_never_blocks() {
        let button = make_entity(EntityKind::Button { pressed: false });
        assert!(!button.blocks_player());
    }

    #[test]
    fn test_monster_blocks() {
        let m = make_entity(EntityKind::Monster { hp: 10 });
        assert!(m.blocks_player());
    }

    #[test]
    fn test_color_distinct_per_kind() {
        let door = make_entity(EntityKind::Door { open: false });
        let chest = make_entity(EntityKind::Chest { opened: false });
        let player = make_entity(EntityKind::Player { hp: 100 });
        assert_ne!(door.color(), chest.color());
        assert_ne!(chest.color(), player.color());
    }
}
```

**提示**:

- 楼梯需要"玩家踩上去触发"(状态变化:进入下一层)
- 但楼梯本身没有"打开 / 关闭"状态
- 楼梯可以看成"玩家踩 → 触发事件"

**讨论**:有人把楼梯做成 tile(永久静态),有人做成 entity(可触发)。两种都有道理。你会怎么选?为什么?

为什么这个练习有价值?因为它逼你思考"什么算有状态"的边界。楼梯是边界 case(状态是"是否触发过",但触发后基本没意义)。理解这个,你能设计灵活的架构。

```rust
mod math;
mod entity;

use math::Vec2;
use entity::{Entity, EntityId, EntityKind};

fn main() {
    println!("=== 环境元素作为 Entity 演示 ===\n");

    // 构造游戏场景
    let mut entities: Vec<Entity> = vec![
        Entity {
            id: EntityId(0),
            pos: Vec2::new(100.0, 100.0),
            half_size: Vec2::new(16.0, 16.0),
            kind: EntityKind::Player { hp: 100 },
        },
        Entity {
            id: EntityId(1),
            pos: Vec2::new(200.0, 100.0),
            half_size: Vec2::new(16.0, 16.0),
            kind: EntityKind::Monster { hp: 50 },
        },
        Entity {
            id: EntityId(2),
            pos: Vec2::new(300.0, 100.0),
            half_size: Vec2::new(16.0, 32.0),
            kind: EntityKind::Door { open: false },
        },
        Entity {
            id: EntityId(3),
            pos: Vec2::new(400.0, 100.0),
            half_size: Vec2::new(16.0, 16.0),
            kind: EntityKind::Chest { opened: false },
        },
        Entity {
            id: EntityId(4),
            pos: Vec2::new(500.0, 100.0),
            half_size: Vec2::new(16.0, 16.0),
            kind: EntityKind::Button { pressed: false },
        },
    ];

    println!("--- 初始状态 ---");
    for e in &entities {
        println!("  Entity {:?}: pos={:?} kind={:?} blocks?{} color=0x{:08X}",
                 e.id, e.pos, e.kind, e.blocks_player(), e.color());
    }

    // 模拟玩家开门
    println!("\n--- 玩家打开门 ---");
    if let Some(door) = entities.iter_mut().find(|e| matches!(e.kind, EntityKind::Door { .. })) {
        if let EntityKind::Door { open } = &mut door.kind {
            *open = true;
        }
    }

    // 模拟玩家开宝箱
    if let Some(chest) = entities.iter_mut().find(|e| matches!(e.kind, EntityKind::Chest { .. })) {
        if let EntityKind::Chest { opened } = &mut chest.kind {
            *opened = true;
        }
    }

    // 模拟玩家踩按钮
    if let Some(button) = entities.iter_mut().find(|e| matches!(e.kind, EntityKind::Button { .. })) {
        if let EntityKind::Button { pressed } = &mut button.kind {
            *pressed = true;
        }
    }

    println!("\n--- 状态变化后 ---");
    for e in &entities {
        println!("  Entity {:?}: kind={:?} blocks?{}",
                 e.id, e.kind, e.blocks_player());
    }
}
```

### Troubleshooting

**问题 1**:加新 EntityKind 后所有 match 编译报错

原因:Rust enum match 强制穷尽,加新变体必须加新分支。

修复:按编译错误提示,在所有 match 里加新分支。

**问题 2**:entity 数量太多,update 慢

原因:所有 entity 每帧 update,即使是静态的(门、宝箱)。

修复:

- 静态 entity update_period = 60(Day 051)
- 或者用 spatial partition(Day 057)+ sim region(Day 063)只 update 附近的

**问题 3**:Rust 编译时间长(因为 enum 太多变体)

原因:Rust 编译 enum + match 是 O(变体数 × match 数)。

修复:用 macro 简化,或拆成多个小 enum。
