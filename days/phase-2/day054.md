# Day 054 · 移除休眠实体概念

> Day 051 你做了频率分层,每个 entity 有 update_period。但 Casey 用了一集发现"管理 dormant / active 状态切换太复杂,性能收益不明显"。Day 054 他**推翻** Day 051 的设计,删除 dormant 概念。这是 YAGNI 原则的经典演示——做了发现不需要,推翻。

## 0 · 为什么要有这一天

软件工程的最大陷阱之一:**预先想象需求**。你在写代码时想"将来可能要 X",加了一层抽象。但"将来"可能永远不来,抽象反而成了累赘。

Casey 在 Day 051 加频率分层时,想的是"10000 个 entity 时需要优化"。但实际游戏只有几十个 entity(玩家 + 几个怪物 + 几个门),频率分层收益微小。代价是:

1. **状态管理复杂**:dormant vs active 切换逻辑繁琐
2. **bug 风险**:状态切换错可能导致 entity "睡死"或"失眠"
3. **代码冗余**:每个 entity 多一个 update_period 字段,每次 update 多一次 mod 检查

Casey 在 Day 054 毅然删除这个抽象。这需要**心理勇气**——很多程序员不愿意删自己的代码(沉没成本谬误)。Casey 演示了**反沉没成本**的工程态度:**对就是对了,错就是错了,不感情用事**。

Day 054 的重要不在删了什么(几行代码),在**演示了探索式开发的核心**:

> "你的代码不神圣。错了就推翻,不要为了"曾经写过"而保留。"

后面 Casey 还会多次推翻设计(Day 308 / 419 / 568 都有)。Day 054 是这个工作方式的第一次明确展示。

心理锚点:做完今天,你应该:

1. 看到"过度抽象"时敢删,不感情用事
2. 知道 YAGNI 原则的具体应用
3. 理解 Casey 的探索式开发哲学
4. 能解释为什么 Day 063 的 sim region 比 Day 051 的频率分层好

## 1 · Casey 今天做了什么

Casey 在 day054 视频里做了四件事:

## 2 · 心智模型

### 费曼类比:做菜的"预处理"

你做大餐前,可能预处理食材(切好、腌上)。但如果只是炒个鸡蛋,预处理就是浪费——5 分钟预处理 vs 30 秒直接炒。

频率分层就是"预处理"——为 10000 个 entity 的未来优化做铺垫。但如果游戏实际只有 50 个 entity,预处理就是浪费。

**Casey 的觉悟**:看实际需求,不为想象中的未来过度准备。

### 严谨定义:YAGNI 原则

**YAGNI**(You Aren't Gonna Need It,你不需要它)是 Extreme Programming 的核心原则之一:

> "永远只实现当前需要的功能,不为想象中的未来加功能。"

**理由**:

1. **预测错误**:你猜的"未来需要"可能永远不会来
2. **维护成本**:多余代码占维护时间
3. **复杂度**:多余抽象增加系统复杂度
4. **拖延**:为"完美设计"花时间,真正需要的功能没做

**反例**(违反 YAGNI):

```rust
// 反例:写 Vec2 时加 4D 支持,因为"将来可能用"
struct Vec2<T = f32, const N: usize = 2> {
    data: [T; N],
}
```

如果游戏是 2D,4D 永远不用。代码复杂度增加,但收益 0。

**正例**(遵守 YAGNI):

```rust
struct Vec2 { x: f32, y: f32 }
// 后面真要 3D 时,加 Vec3。需要时才加。
```

### Casey 的探索式开发

Day 027 Casey 讨论过"探索式架构":

> "不要预先设计。先写最简单的能跑的版本,发现问题再重构。"

Day 051 是"尝试",Day 054 是"反思 + 推翻"。这是探索式开发的循环:

```
写代码 → 玩一会儿 → 发现哪里别扭 → 重构(可能推翻)
```

**为什么这种开发方式适合游戏**?

1. **游戏设计在演化**:玩家反馈决定方向,预先设计往往错
2. **重构成本可控**:Casey 个人项目,重构是几小时事
3. **学习驱动**:每次重构理解更深,代码越来越好

**反例(BDUF,Big Design Up Front)**:

> "先写完整设计文档,再编码。"

瀑布模型的核心理念。Casey 反对这种。BDUF 适合航空、医疗(需求稳定),不适合游戏(需求变化快)。

### 推翻的具体操作

Casey 在 Day 054 删除:

```c
// Day 051 加的:
struct Entity {
    int update_period;  // 删除
    bool is_dormant;    // 删除
    // ...
}

// Day 051 加的更新逻辑:
if (frame_counter % e->update_period == 0) {  // 删除
    UpdateEntity(e, dt * e->update_period);    // 改为 UpdateEntity(e, dt)
}
```

简化为:

```c
struct Entity {
    // 没有 update_period
    // ...
}

for (int i = 0; i < entity_count; i++) {
    UpdateEntity(&entities[i], dt);  // 直接 update
}
```

**代码减少 ~20 行,逻辑大幅简化**。

### 探索式开发 vs 过度设计的对比

| | 过度设计 | 探索式 |
|---|---|---|
| 决策时机 | 预先 | 边写边定 |
| 代码量 | 多 | 少 |
| 抽象层数 | 多 | 少 |
| 灵活性 | 设计内固定 | 容易推翻 |
| 适合场景 | 需求稳定 | 需求变化 |
| 团队规模 | 大团队(需协调) | 个人 / 小团队 |

Casey 是单人项目,适合探索式。大公司团队适合 BDUF。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的 YAGNI 案例:

**1. Casey 的 HH**(本日):删除频率分层。

**2. Jonathan Blow 的 Braid**:最初想 100 个机制,最后只做 8 个。YAGNI 让游戏更精致。

**3. Stardew Valley**:作者最初想 100 个 NPC,实际只有 30+ 个。

**4. Minecraft**:Notch 最初想"复杂的经济系统",后来发现"挖矿 + 建造"足够好玩,删除经济。

**5. Cyberpunk 2077**:CDPR 加了大量"想象中需要"的功能(复杂黑客、车辆改装、第二人生),结果发布时大部分未完成。反 YAGNI 的教训。

#### 反 YAGNI 的代价

- **代码膨胀**:维护成本高
- **bug 多**:代码多 = bug 多
- **发布延迟**:做无用功能浪费时间
- **设计模糊**:功能太多,核心不突出

#### Casey 的反思方法

Casey 经常问自己:

- "这个功能我现在需要吗?"
- "如果删了,游戏会崩溃吗?"
- "加这个抽象节省的时间,值得吗?"

如果三个都"不",删。

### 3.2 · 🎨 图形学视角

图形学的 YAGNI:

**1. shader 系统**:不要预先写"通用 shader 框架",写当前游戏需要的 shader 就好。

**2. 渲染管线**:不要做"100 种后处理"的扩展点,做当前需要的几种。

**3. 资产格式**:不要支持所有格式(BMP / TGA / PNG / JPEG / WebP / ...),只支持游戏实际用的。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的 YAGNI:

**1. 系统调用**:Linux 不加"未来可能用"的系统调用,只加"现在需要"的。

**2. 配置选项**:Linux 配置选项极多,但每个都"现在有人在用"。不存在"为未来准备"的配置。

**3. 模块化**:Linux 内核模块化,不需要的功能不编译(节省内存)。

```bash
# 看 Linux 内核模块
$ lsmod
# 看"当前没加载的模块"
$ modprobe -l | head
```

### 3.4 · 🦀 Rust 生态视角

Rust 社区的 YAGNI:

**1. std::collections**:只有 Vec / HashMap / BTreeMap 等基本容器。 specialised 容器(VecDeque、LinkedList)在 std,但很少用。其他(跳表、Trie)用外部 crate。

**2. feature flags**:Rust crate 用 feature 控制"是否编译某功能"。默认最小,按需启用。

**3. trait 设计**:Rust 倾向"小 trait"(Iterator、Clone),不倾向"大 trait"(Java 的 Object)。YAGNI 在类型系统的体现。

#### 重构的勇气

Casey 在 Day 054 删代码,演示了**重构的勇气**。新手经常不愿删自己的代码(沉没成本谬误),Casey 的态度是:

> "代码不神圣。错了就推翻,不要为了'曾经写过'而保留。"

Rust 的类型系统让重构更安全——改了结构,编译器报错所有调用点,你按报错修。**Rust 是重构友好的语言**。

#### 测试驱动重构

```rust
// 重构前:有测试
#[test]
fn test_entity_update() { ... }

// 重构中:删 update_period,改 update 逻辑
// 运行测试,如果还通过,说明行为一致

// 测试是重构的"安全网"——你敢改,因为测试告诉你有没有破坏行为
```

## 4 · 认知地图

### 4.1 上级

- **YAGNI**(You Aren't Gonna Need It)—— 不做想象中的功能
- **探索式开发**(evolutionary architecture)—— 边写边定
- **沉没成本谬误**(sunk cost fallacy)—— 不因"已经做过"而保留
- **KISS**(Keep It Simple, Stupid)—— 简单优先

### 4.2 同级(并行原则对比)

| 原则 | 内容 | 何时用 |
|---|---|---|
| YAGNI | 不做想象中的功能 | 大部分时候 |
| OCP(开闭原则) | 加新功能不改老代码 | 当真的需要扩展时 |
| KISS | 简单优先 | 默认 |
| DRY(Don't Repeat Yourself) | 不重复 | 看到第 3 次重复时 |
| BDUF(Big Design Up Front) | 先设计再实现 | 需求极稳定时 |

YAGNI 和 OCP 看似矛盾(YAGNI 反对预先抽象,OCP 鼓励抽象),实际互补:**Day 017 的 GameController 抽象是对的**(Day 046 证明),**Day 051 的频率分层是错的**(Day 054 推翻)。区别:GameController 解决了真问题(多输入设备),频率分层解决了假问题(想象中的 10000 entity)。

### 4.3 下级

- **删除多余字段** — update_period
- **简化 update 逻辑** — 直接 update,不 mod 检查

### 行业的"反 YAGNI"教训

**1. Mozilla Servo**:最初设计为"完美并行浏览器引擎",加了很多抽象。实际开发慢,被 Firefox 部分采用。

**2. Google Wave**:Google 的"邮件 + IM + 协作"混合体,功能超多,用户找不到核心。被关停。

**3. HealthCare.gov**:奥巴马医改网站,初始加了大量功能,发布时崩溃。简化后才稳定。

**共同教训**:**少即是多**。YAGNI 是反"feature creep"的解药。

### Rust 社区的 YAGNI 实践

Rust 编译器会拒绝"过度通用":

```rust
// 过度通用:泛型 + 多 trait bound,但只有一个 T 用过
fn add<T: Add + Copy + Default>(a: T, b: T) -> T::Output { ... }

// YAGNI 版本:具体类型
fn add(a: i32, b: i32) -> i32 { a + b }
```

Rust 的"零成本抽象"让泛型无运行时开销,但**编译时间和代码可读性**仍有代价。YAGNI 在 Rust 仍然适用。

**题**:Casey 为什么推翻自己 Day 051 的频率分层设计?这是不是说明 Casey"想错了"?

**参考解答**:

**原因**:

Day 054:发现方案不必要 / 有更好替代,推翻

### Lv2 · 动手实践

**题**:在你的 HH Rust 项目里:

1. **撤销 Day 051**:从 Entity 删除 update_period 字段
2. **简化 update**:所有 entity 每帧 update,不 mod 检查
3. **运行测试**:确保游戏行为不变

完成标准:测试通过,代码更简洁。

**参考解答**:

```rust
// 之前(Day 051):
pub struct Entity {
    pub update_period: u32,
    pub pos: Vec2,
    pub vel: Vec2,
    pub kind: EntityKind,
}

impl World {
    pub fn update(&mut self, dt: f32) {
        self.frame_counter = self.frame_counter.wrapping_add(1);
        for e in &mut self.entities {
            let period = e.update_period.max(1);
            if self.frame_counter % period == 0 {
                let effective_dt = dt * period as f32;
                e.update(effective_dt);
            }
        }
    }
}

// 之后(Day 054):
pub struct Entity {
    // 删除 update_period
    pub pos: Vec2,
    pub vel: Vec2,
    pub kind: EntityKind,
}

impl World {
    pub fn update(&mut self, dt: f32) {
        // 删除 frame_counter
        for e in &mut self.entities {
            e.update(dt);  // 直接 update,不 mod 检查
        }
    }
}
```

测试不变(因为行为不变):

```rust
#[test]
fn test_entity_moves_at_constant_speed() {
    let mut e = Entity {
        pos: Vec2::ZERO,
        vel: Vec2::new(100.0, 0.0),
        kind: EntityKind::Monster,
    };
    let dt = 1.0 / 60.0;
    for _ in 0..60 {
        e.update(dt);
    }
    assert!((e.pos.x - 100.0).abs() < 1.0);
}
```

重构后测试仍通过——行为不变,代码更简洁。

### Lv3 · 迁移设计

**题**:你在写一个**命令行工具**(CLI),最初想支持:

- 文件操作(复制、移动、删除)
- 网络操作(下载、上传)
- 压缩(zip、tar)
- 加密(AES、RSA)
- 数据库(SQLite)

你预先做了"通用插件系统"(每个功能是插件)。但实际只用文件操作。**怎么用 YAGNI 简化**?

**提示**:

- 删除"插件系统",直接写文件操作
- 网络操作 / 压缩 / 加密 / 数据库 等到真需要时再加
- 简化后,代码量减少 90%

**反思**:你的"通用性"是真需求还是想象?如果游戏只有 10 个关卡,真的需要"无限关卡"支持吗?如果只支持单人,真的需要多人网络吗?

为什么这个练习有价值?因为它让你看到 YAGNI 在任何工程中都适用。新手最容易犯的错就是"过度通用化"。理解这个,你写的代码会更简洁、更可维护。

### Lv4 · 开源贡献

**题**:找一个 Rust crate 或 Linux 工具,看它的源码里有没有"过度抽象"的痕迹(被注释掉的代码、未使用的 feature flag、为未来准备但未启用的 API)。

**示例**:GitHub 上搜 `grep "TODO: add when needed\|reserved for future\|unused but kept for"` 找未使用的代码。

**可能的贡献**:

- 提 issue 建议清理未使用代码
- 提 PR 删除死代码
- 改进 doc 说明"为什么保留这些代码"

写下 PR 描述:

```

文件:src/feature.rs(或类似)
动机:这个 feature 在最近 50 个 release 中没有任何用户使用,
     且增加了维护成本。

验证:cargo test 全部通过。cargo build 不报错。
```

          e.update(dt * period);
      }

  struct Entity { ... }  // 没 update_period
  update(){
      for e in entities { e.update(dt); }
  }

  → 性能差异微小(几十个 entity)
  → 后续 Day 063 用 sim region 真正解决大世界问题

### Troubleshooting

**问题 1**:删除字段后所有构造 Entity 的代码都报错

原因:struct 字段变化,所有 `Entity { update_period: 1, ... }` 都要改。

修复:用 `..Default::default()` 或全删除 `update_period` 字段引用。

**问题 2**:测试失败,因为 frame_counter 不再存在

原因:测试可能直接用 frame_counter。

修复:删测试里对 frame_counter 的引用。

**问题 3**:重构后行为不一致(entity 速度变了)

原因:可能在 update 里残留 `dt * period` 的代码,但 period 已删。

修复:用 `dt` 而不是 `dt * period`。

### Casey 的反思方法(详细)

Casey 在视频中提到三个反思问题:

**问题 1:这个功能我现在需要吗?**

频率分层的"假想需求"是 10000 个 entity。但实际只有 50 个。答案:**不需要**。

**问题 2:如果删了,游戏会崩溃吗?**

删除 update_period 后,所有 entity 60Hz update。50 个 entity × 60Hz = 3000 次/秒,远低于性能预算(60 万次)。答案:**不会崩溃**。

**问题 3:加这个抽象节省的时间,值得吗?**

频率分层节省的 CPU 时间(假设)几微秒/帧。代价是 dormant 切换 bug 风险 + 代码维护成本(每次加新 entity 都要设 update_period)。答案:**不值得**。

三个问题都"否",删。

### Rust 的重构工具

Rust 提供的工具让重构更安全:

1. **cargo check**:快速检查语法,不生成代码(秒级反馈)
2. **cargo clippy**:lint,提示代码坏味道
3. **cargo test**:运行单元测试,保证行为不变
4. **rust-analyzer**:IDE 集成,实时类型检查 + 重命名 + 跳转

**重构流程**:

```
1. cargo test  # 确保当前测试通过
2. 改代码(删 update_period)
3. cargo check  # 编译器报错所有调用点
4. 按报错修改调用点
5. cargo test  # 确保行为不变
6. cargo clippy  # 检查代码风格
7. git commit
```

Rust 的强类型 + 工具链让"大规模重构"成本极低。这是 Rust 比动态语言(Python、JavaScript)的优势——重构 1 万行代码不怕。
