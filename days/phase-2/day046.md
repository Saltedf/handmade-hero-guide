
# Day 046 · 基础多人支持

> Day 017 你抽象了 GameController(键盘 + 手柄统一接口),当时看起来"单人游戏为什么需要多 controller?"。Day 046 揭晓答案:加一个本地第二个玩家,代码改动只有 3 行。这是软件工程里"开闭原则"最直观的演示。

## 0 · 为什么要有这一天

回忆 Day 017 你写的输入抽象:

```rust
struct GameInput {
    controllers: [GameController; 4],  // 4 个 controller 槽位
}

struct GameController {
    is_connected: bool,
    move_up: ButtonState,
    move_down: ButtonState,
    // ...
}
```

当时你可能会想:"我的游戏就一个玩家,为什么搞 4 个 controller?" 投入产出比看起来很低——多写了一层数组,多写了一些 for 循环,只为"将来可能加第二个玩家"。

**Day 046 揭晓**:加第二个玩家几乎免费。

```rust
// 之前(单人):
player.update(&input.controllers[0], dt);

// 加第二个玩家(双人):
players[0].update(&input.controllers[0], dt);  // 键盘
if input.controllers[1].is_connected {
    players[1].update(&input.controllers[1], dt);  // 手柄
}
```

**Player 类一行没改**。Day 017 的"过度抽象"现在变成"完美抽象"——它没有锁死你只能单人,加多玩家不改 Player。

这就是**开闭原则**(Open-Closed Principle,OCP):**对扩展开放,对修改封闭**。Day 017 的 GameController 设计让"加玩家"变成扩展(加 controller 配置),而不是修改 Player 类。如果当时你硬编码"键盘控制玩家",Day 046 加手柄玩家就要重写 Player——典型的反 OCP。

Casey 在这集用很少的代码演示这个原则,但教学价值很大:他展示了一个**好的抽象怎么"未卜先知"**。Day 017 看起来过度抽象,Day 046 证明价值。这是软件设计的核心智慧——**在合适的地方引入间接层**,既不强行通用化(YAGNI),也不锁死未来(OCP)。

心理锚点:看完今天,你应该能用一句话回答"OCP 是什么":"软件实体(类、模块、函数)应该对扩展开放,对修改封闭。加新功能不改老代码,只加新代码。" 如果答不出,回头把 §2 的 OCP 段落再看一遍。

## 2 · 心智模型

### 费曼类比:插线和插槽

想象你的游戏主机有 4 个手柄插槽(controller ports)。每个插槽独立,谁插谁用。游戏代码不关心"哪个手柄是哪个玩家的",它只问"插槽 0 有手柄吗?插槽 1 有手柄吗?"。

每个玩家绑定一个插槽:

- 玩家 1 → 插槽 0(默认键盘)
- 玩家 2 → 插槽 1(手柄)
- 玩家 3 → 插槽 2(第二个手柄)
- 玩家 4 → 插槽 3

加新玩家 = "新手柄插入空插槽 + 绑定到一个空玩家槽"。**Player 代码不变**,因为 Player 接收的输入是 GameController,不管 GameController 后面是键盘还是手柄。

### 严谨定义:GameController 抽象

Day 017 的 GameController 是**抽象接口**(abstraction)。它定义了"任何输入设备都提供的功能":

```rust
pub struct GameController {
    pub is_connected: bool,
    pub move_left: ButtonState,
    pub move_right: ButtonState,
    pub move_up: ButtonState,
    pub move_down: ButtonState,
    pub action_1: ButtonState,    // 跳跃 / 攻击
    pub action_2: ButtonState,    // 互动 / 防御
    // ...
}

pub enum ButtonState {
    Released,
    JustPressed,  // 这一帧刚按下
    Pressed,      // 持续按住
    JustReleased, // 这一帧刚松开
}
```

**ButtonState** 是个 enum(枚举),表示按键的 4 种状态。JustPressed/JustReleased 边沿触发,Pressed/Released 电平触发。这覆盖了所有按键逻辑:

- JustPressed → 跳跃(一次性,边沿触发)
- Pressed → 移动(持续,电平触发)
- JustReleased → 防御结束
- Released → 默认

**抽象的层次**:GameController 不暴露"键盘 W 键"或"手柄 A 键"——它只暴露"move_up"。底层是键盘还是手柄由 winit / gilrs 转换。

### 开闭原则(Open-Closed Principle)

**Robert C. Martin(Bob 大叔)的定义**:"软件实体(类、模块、函数)应该对扩展开放,对修改封闭。"

**翻译成人话**:

- **对扩展开放**:可以加新功能(新代码)
- **对修改封闭**:不改已有代码(老代码)

**为什么重要?** 因为改已有代码有风险:

- 老代码可能在别处被使用,改了可能引入回归 bug
- 改老代码需要重新测试所有依赖它的代码
- 团队协作时,改公共代码可能冲突

加新代码就安全:

- 新代码独立,不影响已有路径
- 测试只需测新功能
- 团队协作时,新代码在独立分支

**Casey 在 Day 017 应用 OCP**:

- Player 类接收 GameController(抽象),不接收具体键盘事件
- 加新玩家 = 加新 GameController(扩展),不改 Player(封闭)

**反例(违反 OCP)**:

```rust
// 反例:Player 直接读键盘
impl Player {
    fn update(&mut self, keyboard: &KeyboardState, dt: f32) {
        if keyboard.w_pressed { self.pos.y -= ...; }
        // ...
    }
}

// 加手柄玩家(双人):必须改 Player
impl Player {
    fn update(&mut self, keyboard: &KeyboardState, gamepad: Option<&Gamepad>, dt: f32) {
        // 加了一个参数,所有调用都要改
        if keyboard.w_pressed || gamepad.map_or(false, |g| g.dpad_up) {
            self.pos.y -= ...;
        }
    }
}
```

每加一个输入设备,Player 都要改。这是反 OCP——修改而非扩展。

### 三个输入设备统一抽象

Day 017 的真正威力是**多设备统一**:

```rust
// Win32 / winit:键盘事件 → GameController[0]
fn translate_keyboard(event: KeyboardEvent, controllers: &mut [GameController]) {
    let kb = &mut controllers[0];  // 键盘默认占 slot 0
    match event.key {
        Key::W => kb.move_up.update(event.pressed),
        Key::A => kb.move_left.update(event.pressed),
        // ...
    }
}

// gilrs:手柄事件 → GameController[1..4]
fn translate_gamepad(event: GamepadEvent, controllers: &mut [GameController]) {
    let slot = event.gamepad_id + 1;  // 手柄从 slot 1 开始
    let controller = &mut controllers[slot as usize];
    match event.button {
        Button::DPadUp => controller.move_up.update(event.pressed),
        // ...
    }
}
```

游戏代码只看 `controllers[i]`,不关心后面是什么物理设备。**抽象层**(translate_*)处理设备差异。

### Player 数组的代码骨架

```rust
pub struct GameState {
    pub players: [Player; 4],  // 最多 4 个玩家
    pub num_active_players: usize,
}

impl GameState {
    pub fn update(&mut self, input: &GameInput, dt: f32) {
        // 遍历所有可能的玩家槽
        for i in 0..self.num_active_players {
            if input.controllers[i].is_connected {
                self.players[i].update(&input.controllers[i], dt);
            }
        }
    }
}
```

**加第二个玩家的具体步骤**:

1. 主循环开始时检测手柄是否连接
2. 如果是,设置 `input.controllers[1].is_connected = true`
3. `num_active_players = 2`
4. 主 update 自然遍历两个玩家

**Player 类零修改**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的多人模式类型:

**1. 本地多人**(local multiplayer,Day 046):同一台机器,多个手柄。超级马里奥兄弟、Super Smash Bros、Castle Crashers。

**2. 分屏多人**(split-screen):同一台机器,屏幕分成几块。Mario Kart、GoldenEye、Halo 1-3。

**3. 在线多人**(online multiplayer):多台机器,网络同步。Fortnite、英雄联盟、所有 MMO。

**4. 大逃杀**(battle royale):100+ 玩家在线。PUBG、Apex Legends。

每种模式架构不同:

| 模式 | 复杂度 | 主要挑战 |
|---|---|---|
| 本地多人 | 低 | 多 controller,渲染 |
| 分屏 | 中 | 多相机,多 viewport |
| 在线 | 高 | 状态同步,延迟补偿 |
| 大逃杀 | 极高 | 服务器架构,anti-cheat |

Casey Day 046 是最低复杂度的本地多人,后面不深入在线(那是 Phase 8+ 的话题)。

#### 本地多人的渲染问题

两个玩家同一屏幕,相机怎么放?

**A. 单一相机,所有玩家同屏**(Mario Bros):相机跟随玩家中点,所有玩家在视野内。如果玩家走远了相机被拉扯——通常游戏有"玩家距离限制"(太远会卡死或死亡)。

**B. 分屏**(Mario Kart):屏幕分两半,每个玩家一个相机。

**C. 动态切换**(Lego 系列):玩家近时同屏,远时分屏。

Casey 的 HH 这集只做 A(同屏),因为简单。

### 3.2 · 🎨 图形学视角

多人游戏的图形学问题:

**1. 多相机**:每个相机独立渲染,写到 framebuffer 的不同区域。OpenGL 用 viewport(`glViewport(x, y, w, h)`),Vulkan 用 scissor。

**2. 多 viewport**:WebGPU / DirectX 12 有显式 viewport 数组,一次 draw call 渲染到多个 viewport(SLV, single-pass stereo)。

**3. UI 区分**:每个玩家的 UI(血条、得分)用不同颜色,放在屏幕角落。HUD 设计要避免遮挡视野。

Casey Day 046 不深入这些,但 Phase 5+ 切 OpenGL 时会遇到。

### 3.3 · 🐧 Linux 球编程视角

Linux 上的多人输入:

**1. 多键盘**:Linux 支持"multiseat"(多座位),多个键盘鼠标独立工作。需要 systemd-logind 配置。

**2. 多手柄**:Linux 内核 evdev 天然支持。每个手柄一个 `/dev/input/event*` 设备。`udev` 规则负责命名和权限。

```bash
# 看连了几个手柄
$ ls /dev/input/by-id/ | grep -i joystick
usb-SONY_DualSense_Wireless_Controller-joystick

# 看 evdev 设备
$ ls /dev/input/event*
/dev/input/event0  /dev/input/event1  /dev/input/event2 ...

# evtest 工具看手柄事件
$ sudo pacman -S evtest
$ sudo evtest /dev/input/event12
Input driver version is 2.1.0
Input device ID: bus 0x3 vendor 0x54c product 0xce6 version 0x100
Event: type EV_KEY, code BTN_SOUTH(南方按钮 = A 按钮)
```

**3. SDL / gilrs**:Rust 生态用 gilrs(游戏手柄库),内部用 evdev。SDL 也能用,但 SDL 是 C 库,Rust 绑定是 sdl2 crate。

```rust
// gilrs 监听手柄
use gilrs::{Gilrs, Event};

let mut gilrs = Gilrs::new().unwrap();
loop {
    while let Some(Event { id, event, time }) = gilrs.next_event() {
        println!("Gamepad {}: {:?}", id, event);
    }
}
```

每个手柄有独立 id,你把 id 映射到 controller slot。

### 3.4 · 🦀 Rust 生态视角

#### Rust 写多人游戏的注意事项

**所有权**:Player 数组属于 GameState。update 函数 `&mut self`(可变借用 self),所有 Player 在一个借用下。

```rust
impl GameState {
    pub fn update(&mut self, input: &GameInput, dt: f32) {
        for i in 0..self.num_active_players {
            self.players[i].update(&input.controllers[i], dt);
            // self.players[i] 是 &mut Player
            // input.controllers[i] 是 &GameController
        }
    }
}
```

**借用规则**:循环里每次只借一个 Player,迭代器自动释放。不冲突。

**问题:玩家互撞**:如果 P1 撞 P2,需要同时 &mut 两个 Player。Rust 借用规则禁止。

```rust
// 错误:不能同时 &mut self.players[0] 和 self.players[1]
let p1 = &mut self.players[0];
let p2 = &mut self.players[1];
p1.collide(p2);  // 编译报错

// 正确方案 1:split_at_mut
let (left, right) = self.players.split_at_mut(1);
collide_players(&mut left[0], &mut right[0]);

// 正确方案 2:索引访问
fn collide_players(players: &mut [Player; 2]) {
    let p1 = &players[0];
    let p2 = &players[1];
    // 算碰撞,结果暂存
    let result = compute_collision(p1, p2);
    // 应用结果
    players[0].apply_collision(&result.0);
    players[1].apply_collision(&result.1);
}
```

**正确方案 3:用 ECS**(Phase 5+ Casey 不用 ECS,但商业游戏都用)。bevy_ecs 提供 `Query<&mut Player>`,内部安全处理借用。

#### 测试多人游戏

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn make_input(controllers: &[bool]) -> GameInput {
        let mut input = GameInput::default();
        for (i, &connected) in controllers.iter().enumerate() {
            input.controllers[i].is_connected = connected;
        }
        input
    }

    #[test]
    fn test_single_player_unchanged() {
        let mut state = GameState::new();
        state.num_active_players = 1;
        let input = make_input(&[true, false, false, false]);

        let initial_pos = state.players[0].pos;
        state.update(&input, 1.0 / 60.0);
        // players[0] 应该有移动
        assert!(state.players[0].pos != initial_pos);
        // players[1] 应该没动
        assert_eq!(state.players[1].pos, Player::default().pos);
    }

    #[test]
    fn test_two_players_both_update() {
        let mut state = GameState::new();
        state.num_active_players = 2;
        // 模拟两个 controller 都按右键
        let mut input = make_input(&[true, true, false, false]);
        input.controllers[0].move_right = ButtonState::Pressed;
        input.controllers[1].move_right = ButtonState::Pressed;

        state.update(&input, 1.0 / 60.0);
        // 两个玩家都应该向右移动
        assert!(state.players[0].pos.x > 0.0);
        assert!(state.players[1].pos.x > 0.0);
    }

    #[test]
    fn test_disconnected_controller_skipped() {
        let mut state = GameState::new();
        state.num_active_players = 2;
        // 只有 controller 0 连接
        let input = make_input(&[true, false, false, false]);

        state.update(&input, 1.0 / 60.0);
        // players[1] 不应该 update
        assert_eq!(state.players[1].pos, Player::default().pos);
    }
}
```

测试覆盖:单人、双人、断开连接的 controller。

## 4 · 认知地图

### 4.1 上级

- **开闭原则(OCP)** —— SOLID 五原则之一,加新功能不改老代码
- **依赖倒置(DIP)** —— 高层(Player)不依赖低层(键盘 / 手柄),都依赖抽象(GameController)
- **接口隔离(ISP)** —— 不强迫用户依赖不用的方法(GameController 只暴露游戏相关按键,不暴露原始 scancode)
- **策略模式(Strategy pattern)** —— GameController 是策略,Player 是上下文

### 4.2 同级(并行方案对比)

| 多人模式 | 复杂度 | 通信延迟 | 典型游戏 |
|---|---|---|---|
| 本地同屏 | 低 | 0(同机) | 马里奥、HH Day 046 |
| 本地分屏 | 中 | 0(同机) | Mario Kart |
| 局域网(LAN) | 中 | <10ms | CS 局域网 |
| 在线 P2P | 高 | 50-200ms | 早期 RTS |
| 在线 C/S | 极高 | 50-200ms | 所有 MMO |
| 大厅制匹配 | 极高 | 50-500ms | LoL、Dota |

Casey Day 046 选最低复杂度的本地同屏。Phase 8+ 才考虑网络。

### 4.3 下级

- **GameController 抽象** —— 统一键盘 / 手柄 / 触摸
- **ButtonState enum** —— 按键 4 种状态
- **Player 数组** —— 多玩家存储
- **is_connected 标志** —— 检测设备热插拔
- **num_active_players** —— 避免遍历空槽

## 5 · 对照与变奏

### 不同游戏类型的多人设计

**格斗游戏**(Street Fighter):两个玩家共享屏幕,双方都能看见对方所有动作。复杂度低。

**MOBA**(LoL):10 个玩家,每个看自己视野(fog of war 隐藏对方)。需要服务器计算可见性。

**FPS**(CS:GO):每个玩家第一人称,看自己视野。需要服务器防止 wallhack(透视挂)。

**MMO**(WoW):上千玩家同服,服务器分区域(zone),每个 zone 独立进程。极复杂。

每种类型的多人都基于"独立 controller"这个抽象,只是上层(渲染、网络)不同。Day 046 的本地双人是最简版本。

### Controller 的演化历史

**1980s**:红白机(NES)2 个手柄插槽。游戏硬编码"1P / 2P"。

**1990s**:SNES、Genesis 支持 4 个手柄(需要 multitap 适配器)。游戏开始抽象 controller。

**2000s**:PS2、Xbox 内置多 controller 支持,USB 接口。无线手柄出现。

**2010s**:蓝牙手柄普及,PC / 主机统一 HID 标准。

**2020s**:云游戏(Stadia、GFN),controller 通过网络传到云端。延迟是新挑战。

Casey 的 HH 用现代抽象(GameController),所以兼容从红白机到云游戏的所有输入方式。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey Day 046 加第二个玩家"几乎免费"(几行代码)。这背后的设计原则是什么?如果 Day 017 你直接写"键盘控制 Player",Day 046 加手柄玩家会变成什么样?

**参考解答**:

**背后原则**:开闭原则(OCP)。Day 017 的 GameController 抽象让"加新玩家"= "加 controller 配置"(扩展),不改 Player(封闭)。

**反例(硬编码键盘)**:

```rust
// Day 017 反例
impl Player {
    fn update(&mut self, kb: &Keyboard, dt: f32) {
        if kb.w { self.move_up(dt); }
        if kb.s { self.move_down(dt); }
    }
}

// Day 046 加手柄玩家:必须改 Player
impl Player {
    fn update(&mut self, kb: Option<&Keyboard>, gp: Option<&Gamepad>, dt: f32) {
        // 加了参数,所有调用都要改
        if kb.map_or(false, |k| k.w) || gp.map_or(false, |g| g.dpad_up) {
            self.move_up(dt);
        }
    }
}
```

每加一种输入设备(键盘 / 手柄 / 触屏 / 体感 / 眼动),Player 都要改签名。改了签名,所有调用点都要改。改动成本指数增长。

**正例(GameController 抽象)**:

```rust
// Day 017 正例
impl Player {

// src/game_state.rs
use crate::math::Vec2;
use crate::player::Player;
use crate::input::{GameInput, GameController};

pub struct GameState {
    pub players: [Player; 2],
    pub num_active_players: usize,
}

impl Default for GameState {
    fn default() -> Self {
        Self {
            players: [Player::default(), Player::default()],
            num_active_players: 1,
        }
    }
}

impl GameState {
    pub fn update(&mut self, input: &GameInput, dt: f32) {
        for i in 0..self.num_active_players {
            // 检查这个 controller 是否连接
            if input.controllers[i].is_connected {
                self.players[i].update(&input.controllers[i], dt);
            }
        }
    }

    pub fn render(&self, render_buf: &mut [u32]) {
        // 两个玩家用不同颜色画
        let colors = [0xFF00FF00, 0xFFFF0000];  // P1 绿,P2 红
        for i in 0..self.num_active_players {
            self.players[i].render(render_buf, colors[i]);
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use crate::input::{GameInput, GameController, ButtonState};

    fn make_controller(move_right: bool) -> GameController {
        let mut c = GameController::default();
        c.is_connected = true;
        if move_right {
            c.move_right = ButtonState::Pressed;
        }
        c
    }

    #[test]
    fn test_single_player_only_first_moves() {
        let mut state = GameState::default();
        state.num_active_players = 1;
        let mut input = GameInput::default();
        input.controllers[0] = make_controller(true);

        let p0_before = state.players[0].pos;
        let p1_before = state.players[1].pos;

        state.update(&input, 1.0 / 60.0);

        assert!(state.players[0].pos != p0_before, "P0 should move");
        assert_eq!(state.players[1].pos, p1_before, "P1 should not move");
    }

    #[test]
    fn test_two_players_both_move() {
        let mut state = GameState::default();
        state.num_active_players = 2;
        // 两个 controller 都按右键
        let mut input = GameInput::default();
        input.controllers[0] = make_controller(true);
        input.controllers[1] = make_controller(true);

        state.update(&input, 1.0 / 60.0);

        // 两个玩家都向右移动了
        assert!(state.players[0].pos.x > 0.0);
        assert!(state.players[1].pos.x > 0.0);
    }

    #[test]
    fn test_disconnected_controller_skipped() {
        let mut state = GameState::default();
        state.num_active_players = 2;
        let mut input = GameInput::default();
        // 只有 controller 0 连接
        input.controllers[0] = make_controller(true);
        input.controllers[1].is_connected = false;

        let p1_before = state.players[1].pos;
        state.update(&input, 1.0 / 60.0);

        // P1 不应该 update(controller 断开)
        assert_eq!(state.players[1].pos, p1_before);
    }
}
```

**关键决策解释**:

- `colors = [0xFF00FF00, 0xFFFF0000]` —— P1 绿色,P2 红色,让玩家分辨自己的方块。多人游戏的 UX 基础。
- 测试覆盖三种情况:单人正常、双人正常、断开连接。这是 OCP 的"行为契约"——加新玩家不改老玩家行为。

### Lv3 · 迁移设计

**题**:你之前给游戏加了"作弊码"(cheat code):输入"↑↑↓↓←→←→BA"激活无敌。现在你要让 2P 也能用各自作弊码。怎么设计?

要求:

- 每个玩家的作弊码独立(2P 不能触发 1P 的无敌)
- 作弊码监听器不直接耦合 Player(避免改 Player 类)
- 加新作弊码不改已有作弊码

**提示**:

- 用 trait `CheatCodeListener`,每个作弊码实现这个 trait
- Player 持有一个 `Vec<Box<dyn CheatCodeListener>>`,update 时遍历调用
- 加新作弊码 = 加新 struct + impl trait = 扩展,不改老代码

为什么这个练习有价值?因为它逼你应用 OCP 到"加作弊码"这种游戏常见需求。如果你写 `if input == UP_UP_DOWN_DOWN ... { god_mode = true }`,加新作弊码就要改这行——违反 OCP。用 trait + Vec,扩展自然。

### Troubleshooting

**问题 1**:加第二个玩家后,P1 的颜色和 P0 一样(都是绿色)

原因:渲染代码没区分玩家颜色。

修复:`render(&self, buf: &mut [u32], color: u32)`,每个玩家传不同颜色。

**问题 2**:Rust 报 "cannot borrow `self.players` as mutable more than once"

原因:你试图同时 &mut 两个 Player(玩家互撞处理)。

修复:用 `split_at_mut` 或先算碰撞结果再批量应用(参考 §3.4)。

**问题 3**:手柄断开重连后,游戏认不出

原因:gilrs 的 GamepadId 在断开重连后会变。

修复:用 gilrs 的 `gamepad.uuid()` 跟踪物理设备,而不是 id。

**问题 4**:玩家 1 移动时玩家 2 也跟着动

原因:GameInput 的 controllers 数组共享了。你可能在某处把 controllers[0] 和 [1] 都设了同一个值。

修复:检查 GameInput 初始化代码,确保每个 controller 独立。
