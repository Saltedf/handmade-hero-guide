
# Day 029 · 基础瓦片地图碰撞检测

> Day 028 你画了一张 tile map,但没有碰撞——玩家(绿方块)能穿墙、过水、走出地图外。Day 029 给世界加上"存在感":方块碰到 Wall tile 就停住。看似简单(检查 tile 类型),但里面藏着一个游戏手感的灵魂技巧——**分轴碰撞(wall sliding)**。没有这个技巧,玩家会被墙"黏住",体验极差。

## 0 · 为什么要有这一天

你想想,没有碰撞的游戏是什么样的?

- 玩家穿过墙壁,从地图边缘走出去,在虚空中漫游
- 走进水里不停留,鱼在陆地上游
- 怪物和玩家重叠,谁也打不到谁
- 跳跃后落不到地面,无限下坠

这种游戏没有"世界感"——所有地方都一样,玩家分不清"哪里能走哪里不能走"。**碰撞是游戏世界"存在感"的基础**。

经典 2D 游戏的"世界感"全靠碰撞:

- **超级马里奥**:马里奥踩在平台上不掉下去(向下被平台挡),头顶撞砖块弹回(向上被砖块挡)
- **塞尔达**:林克被墙挡住,贴着墙能滑动但不能穿墙
- **宝可梦**:玩家不能走出草丛边界,撞到树会停下

这些都是碰撞在起作用。今天 Casey 加碰撞,从最简单的 "entity vs tile" 碰撞开始——玩家(一个 AABB)和 tile map(2D 网格)的碰撞。

但 Casey 这集**最大的贡献不是碰撞本身**,而是一个叫 **wall sliding**(贴墙滑行)的技巧。先看一个常见的失败案例:

**失败版**:玩家斜向右上走,右边有墙。代码把"右移"和"上移"合成一次位置更新,检查新位置是否撞墙。结果:撞墙,新位置非法,**整个一帧不动**。玩家被"黏"在原地——明明上面没墙却不走。这游戏体验是垃圾。

**成功版**:把"右移"和"上移"**分开检查**。先尝试右移,撞墙就 x 不动;再尝试上移,不撞墙就 y 动。结果:玩家 x 不动,y 动——**贴着墙向上滑**。这就是 wall sliding。

所有好的 2D 游戏都有 wall sliding。超级马里奥贴着砖块滑、塞尔达沿墙走、星之卡比挤过窄缝——都是分轴碰撞的结果。Casey 这集把这件事讲透。

心理锚点:看完这集,你应该能:

- 用一句话解释"为什么不能同时检查 x 和 y 碰撞,要分轴"
- 在白板上画出一个斜向移动的玩家碰到 L 形墙后的真实轨迹
- 写出一个 `try_move` 函数,接受任意 `(dx, dy)`,实现 wall sliding

如果你做不到,反复看 §2 的"分轴碰撞"部分——这是 Day 029 的灵魂,后面 Day 050(Minkowski 碰撞)和 Day 045(连续碰撞)都建立在它之上。

## 2 · 心智模型

### 类比:在窄走廊里侧身通过

想象你在一个窄走廊里,右边是墙,你想往前走。如果你**侧着身子**(只关心前后方向),你能贴着墙走;如果你**正着身子**(同时关心前后和左右),你撞到右墙就卡住,不能前进了。

游戏里的玩家方块也是这样:

- "侧着身子" = 分轴检查(先 x 后 y):能贴墙滑行
- "正着身子" = 同时检查 x 和 y:撞墙就卡住

### AABB(轴对齐矩形)碰撞

玩家是一个 AABB(Axis-Aligned Bounding Box,轴对齐包围盒)。**轴对齐**意思是矩形四条边分别平行于 x 轴和 y 轴——没有旋转。这让碰撞计算极简,只比较坐标。

AABB 用左上角 + 宽高定义:

```
       (px, py)
          ┌──────────┐
          │          │
          │  玩家    │  height = 32
          │          │
          └──────────┘
             width = 32
```

两个 AABB 重叠 ⟺ x 方向重叠 且 y 方向重叠:

```
A 和 B 在 x 方向重叠 ⟺ A.left < B.right 且 A.right > B.left
A 和 B 在 y 方向重叠 ⟺ A.top  < B.bottom 且 A.bottom > A.top

两个同时成立 ⟺ AABB 重叠
```

### entity vs tile 碰撞(不是 entity vs entity)

Casey 这集不做"两个 entity 互相碰撞",做的是"entity vs tile map"。**为什么选这个**:

- entity vs entity 碰撞:每个 entity 要和其他所有 entity 比较,O(n²) 复杂度
- entity vs tile 碰撞:tile 是网格,查 tile 只需 `map.get(tile_x, tile_y)`,O(覆盖 tile 数)——通常 4-9 个 tile

Casey 选后者,因为 tile 网格本身就是一种**空间分区**——告诉你"哪里有墙"不用遍历所有墙。

### 算法 1:can_move_to

判断"AABB 放在 (new_x, new_y) 这个位置,会不会撞 Wall tile":

```rust
const TILE_SIZE: i32 = 32;

fn can_move_to(map: &TileMap, new_x: i32, new_y: i32, size: i32) -> bool {
    // AABB 覆盖哪些 tile?
    // 左边在 new_x,右边在 new_x + size - 1(注意 size=32 时,右边 = new_x + 31)
    let tile_left  = new_x / TILE_SIZE;
    let tile_right = (new_x + size - 1) / TILE_SIZE;
    let tile_top    = new_y / TILE_SIZE;
    let tile_bottom = (new_y + size - 1) / TILE_SIZE;

    // 遍历覆盖的所有 tile
    for ty in tile_top..=tile_bottom {
        for tx in tile_left..=tile_right {
            if map.get(tx, ty) == TileValue::Wall {
                return false;  // 撞墙了
            }
        }
    }
    true  // 所有覆盖的 tile 都不是 Wall
}
```

**关键细节**:

- `new_x + size - 1` 不是 `new_x + size`。如果 size=32,new_x=0,那 AABB 占像素 0..31(不含 32)。所以右边的像素是 new_x + 31 = new_x + size - 1。这是 off-by-one 的关键。
- `/ TILE_SIZE` 对正数等价于 floor。`31 / 32 = 0`、`32 / 32 = 1`。所以 AABB [0, 31] 落在 tile 0,AABB [32, 63] 落在 tile 1。
- `..=` 是 Rust 的"包含右端"范围。`tile_top..=tile_bottom` 包含 tile_bottom。

### 算法 2:同时检查 x 和 y(失败版)

```rust
fn update_player_failed(map: &TileMap, player: &mut Player, input: &GameInput, dt: f32) {
    let speed = 200.0;  // 像素/秒
    let dx = if input.move_right { speed * dt } else { 0.0 };
    let dy = if input.move_up { -speed * dt } else { 0.0 };  // y 向下,up 是负

    let new_x = (player.pos.x + dx) as i32;
    let new_y = (player.pos.y + dy) as i32;

    // ❌ 同时检查 x 和 y
    if can_move_to(map, new_x, new_y, PLAYER_SIZE) {
        player.pos.x = new_x as f32;
        player.pos.y = new_y as f32;
    }
    // 否则:整个一帧不动
}
```

**问题演示**:

### 算法 3:分轴检查(wall sliding 成功版)

```rust
fn update_player_sliding(map: &TileMap, player: &mut Player, input: &GameInput, dt: f32) {
    let speed = 200.0;
    let dx = if input.move_right { speed * dt } else { 0.0 };
    let dy = if input.move_up { -speed * dt } else { 0.0 };

    // ✓ 先尝试 x 方向
    let new_x = (player.pos.x + dx) as i32;
    let cur_y = player.pos.y as i32;
    if can_move_to(map, new_x, cur_y, PLAYER_SIZE) {
        player.pos.x = new_x as f32;  // x 方向能走,更新
    }
    // 否则:x 方向撞墙,player.pos.x 不变

    // ✓ 再尝试 y 方向(用更新后的 x)
    let cur_x = player.pos.x as i32;
    let new_y = (player.pos.y + dy) as i32;
    if can_move_to(map, cur_x, new_y, PLAYER_SIZE) {
        player.pos.y = new_y as f32;  // y 方向能走,更新
    }
    // 否则:y 方向撞墙,player.pos.y 不变
}
```

**效果演示**(同样场景):

```
初始:玩家在 (100, 100),按 D+W
       ┌─────────────────────┐
       │                     │
       │   玩家(100,100)    │
       │        ╔═══╗        │
       │        ║ P ║        │
       │        ╚═══╝        │
       │                     │
       │                  ┌──┐
       │                  │ W│
       │                  │  │
       │                  └──┘
       └─────────────────────┘

step 1:尝试 x 方向
  new_x = 150(撞墙),can_move_to(map, 150, 100) = false
  → player.pos.x 保持 100

step 2:尝试 y 方向(用 cur_x = 100)
  new_y = 50,can_move_to(map, 100, 50) = true(上方无墙)
  → player.pos.y 更新为 50

结果:玩家从 (100, 100) 移到 (100, 50)
      —— x 被墙挡住,y 正常移动
      = 贴着墙向上滑!
```

这就是 wall sliding。**所有好的 2D 游戏都用这个技巧**。

### 顺序问题:先 x 还是先 y?

Casey 这集选**先 x 后 y**。这两种顺序在某些边缘场景下行为不同:

```
玩家斜向走,撞到 ┐ 形墙角(右上角):

       ┌──┐
       │ W│
       └──┘
   ┌─── 
   │玩家
   └─── 

先 x 后 y:右移撞墙(x 不动)→ 上移通过(y 动)
   = 玩家向上滑

先 y 后 x:上移撞墙(y 不动)→ 右移通过(x 动)
   = 玩家向右滑
```

不同顺序产生不同行为。Casey 这集选"先 x 后 y"是因为水平移动更"主导"(玩家通常左右移动多于上下)。商业引擎常让玩家可选——比如《空洞骑士》向上贴墙滑,但向下落时按住下方向能"贴墙速降"。

### 边界情况:角落卡住

玩家 32×32,墙是 32×32 tile。考虑下面场景:

```
   ┌──┐
   │W │
   └──┘
   ┌──┐
   │W │
   │玩家(右上角贴墙)
   │W │
   └──┘
```

玩家想向右上方斜移:右撞墙、上撞墙。两个轴都不动,**完全卡住**。

Casey 这集不解决(说"以后会处理")。实际游戏中,**玩家应该感受到"被卡住"是合理的**——你确实被两面墙夹住了。但如果玩家只是想往右走,这种"卡住"会让玩家烦躁。

**Day 050 Minkowski 碰撞**会改进——把玩家看作一个点,把墙扩大(玩家宽度),变成"点和扩大的墙的碰撞"。这能消除"同时撞两面墙"的奇怪行为,因为扩大的墙是单个矩形,玩家不可能"同时撞到"它的两个面。

### 高速穿墙(tunneling)

如果玩家速度很快(比如 3000 像素/秒),一帧 dt=0.016 秒,移动 48 像素。墙是 32 像素厚。看下面:

```
帧 N:玩家在 (0, 50),墙在 (50, 50) 到 (82, 50+32)
帧 N+1:玩家在 (48, 50)(还没穿墙)

继续加速:
帧 N+5:玩家在 (200, 50)——已经过了墙!
```

中间帧:**玩家位置直接从墙前跳到墙后**,从来没有"和墙重叠"的瞬间。`can_move_to` 检查的是终点,终点不在墙里,所以认为"能移动"——但实际穿墙了!

**Day 045 的 temporal search** 解决:把一段大移动拆成多个小步(每步 < tile_size),每步检查。具体:每步移动不超过 tile_size / 2(16 像素),这样任何一帧的位置都在墙的某一边,不会跳过。

Casey 这集**不解决** tunneling,因为玩家速度默认很低(200 像素/秒 × 0.016 = 3.2 像素/帧,远小于 tile size)。教学简化,Day 045 再补。

### 一个完整的"player update"函数

```rust
struct Player {
    pos: Vec2,    // 玩家左上角世界坐标
    vel: Vec2,    // 当前速度
}

impl Player {
    fn update(&mut self, map: &TileMap, input: &GameInput, dt: f32) {
        // 1. 根据输入设置速度
        let speed = 200.0;
        let mut vx = 0.0;
        let mut vy = 0.0;
        if input.move_left  { vx -= speed; }
        if input.move_right { vx += speed; }
        if input.move_up    { vy -= speed; }   // y 向下,up 是负
        if input.move_down  { vy += speed; }

        // 2. 计算这一帧的位移
        let dx = vx * dt;
        let dy = vy * dt;

        // 3. 分轴碰撞(wall sliding)
        // x 方向
        let new_x = self.pos.x + dx;
        if can_move_to(map, new_x as i32, self.pos.y as i32, PLAYER_SIZE) {
            self.pos.x = new_x;
        }
        // y 方向(用更新后的 x)
        let new_y = self.pos.y + dy;
        if can_move_to(map, self.pos.x as i32, new_y as i32, PLAYER_SIZE) {
            self.pos.y = new_y;
        }
    }
}
```

**注意**:`PLAYER_SIZE` 是常量 32。Casey 在 Day 030+ 把它做成 Player 字段(玩家和怪物不同大小)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

Wall sliding 是 2D 游戏开发的**核心技巧**。每个 2D 游戏开发者都要学一遍。

**为什么必须 wall sliding**:玩家用键盘 / 手柄输入时,经常**同时按多个方向键**(比如 D+W)。如果游戏不分轴检查,玩家撞到墙就完全卡住,即使另一个方向能走也不让走。这是反直觉的——"我明明按了向上,为什么不动?"

**Wall sliding 是"玩家意图的合理猜测"**:玩家按 D+W,他的意图是"如果右能走就走右,如果上能走就走上"。Wall sliding 完美执行这个意图。

**Wall sliding 的"反面":墙的物理摩擦**。某些游戏(比如真实物理模拟)让贴墙滑动有摩擦减速——贴墙时间越长,速度越慢。Casey 这集不模拟摩擦(简化),Day 100+ 加物理时才考虑。

**不同游戏的碰撞风格**:

| 游戏 | 风格 | 实现 |
|---|---|---|
| 超级马里奥 | 平台跳跃,贴墙滑 | 分轴 + 重力 |
| 塞尔达(俯视角) | 8 方向移动,贴墙滑 | 分轴 + 8 方向输入 |
| Pokemon | 网格移动(一次走一格) | 完全不同的离散移动 |
| Hollow Knight | 平台跳跃,贴墙滑 + 抓墙 | 分轴 + 状态机 |
| Enter the Gungeon | 俯视角,贴墙滑 | 分轴 + 滚动躲避 |

### 3.2 · 🎨 图形学视角

碰撞本身不是图形学概念,但和图形学有交集:

- **可视碰撞框**:debug 模式下把碰撞框画出来,Casey 在 Day 35+ 加 debug overlay
- **碰撞框 vs 渲染框**:玩家的碰撞框可能比贴图小(让游戏更宽容)。比如玩家贴图 32×32,但碰撞框 24×24(贴图边缘 4 像素不参与碰撞)——这样玩家擦边走时不会因为贴图边角而撞墙
- **碰撞框 vs 视觉感受**:玩家觉得"擦边过",但碰撞框其实没碰到。这是"游戏手感"(game feel)的核心——让玩家感觉舒服,而不是物理精确

Casey 在 Day 100+ 会把碰撞框独立出来(`collision_half_size`),让玩家碰撞比贴图小。

### 3.4 · 🦀 Rust 生态视角

Rust 表达"碰撞检查"的几种方式:

**方式 1:函数 + if**

```rust
fn can_move_to(map: &TileMap, x: i32, y: i32, size: i32) -> bool { ... }

if can_move_to(map, new_x, cur_y, size) { player.pos.x = new_x; }
```

简单直接。Casey 用这种。

**方式 2:返回碰撞信息(不只是 bool)**

```rust
struct CollisionInfo {
    hit_wall: bool,
    hit_tile_x: Option<i32>,  // 撞到哪个 tile
    hit_tile_y: Option<i32>,
}

fn check_collision(map: &TileMap, x: i32, y: i32, size: i32) -> CollisionInfo { ... }
```

更详细。Day 050+ Casey 用类似这种(碰撞时还要知道撞到哪边,用于反弹 / 触发器)。

**方式 3:ECS query**

```rust
// Bevy 风格
fn player_collision_system(
    mut player: Query<(&mut Transform, &Player)>,
    map: Res<TileMap>,
) {
    for (mut transform, _) in &mut player {
        // 碰撞逻辑
    }
}
```

把碰撞作为一个 system,数据(Component)和行为(System)分开。HH 不用 ECS,但 Bevy 用这种。

**Rust 的所有权和分轴碰撞**:

```rust
// ✓ 这段代码合法:player 是 &mut,map 是 &
player.update(map, input, dt);

// ✗ 这段代码非法:player.update 内部需要 &mut player,
//                同时函数外面有 &player 借用——双重借用冲突
let pos_ref = &player.pos;
player.update(map, input, dt);
println!("{}", pos_ref.x);  // 编译错误
```

Rust 的所有权系统**强制**你"一次只能有一个可变借用"。在碰撞代码里,这意味着你不能在 update 中"借出 player.pos 给别人用,同时改它"。Casey 的代码自然满足这个约束,但如果你不小心写出"读 player.pos 改 player.vel"的代码,Rust 会拦你。

## 4 · 认知地图

### 4.1 上级

- **AABB collision**(轴对齐包围盒碰撞)—— 用矩形近似物体,最简单的碰撞检测
- **Discrete collision detection**(离散碰撞检测)—— 每帧检查一次(对比连续碰撞)
- **Wall sliding**(贴墙滑行)—— 让玩家贴墙平滑移动的技巧
- **Tile-based collision** —— 利用 tile 网格做碰撞,本质是空间分区

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 分轴 AABB(这集) | 先 x 后 y,wall sliding | 2D 网格游戏 | ✅ Casey 选了 |
| 同时 AABB(失败版) | 一次性检查 x+y | 几乎不用 | 反面教材 |
| Continuous Collision Detection | 扫描起点到终点路径 | 高速物体(子弹) | Day 045+ |
| Sphere-AABB | 玩家是圆 vs tile 矩形 | 边缘圆滑的游戏 | HH 不用 |
| SAT(Separating Axis Theorem) | 通用凸多边形 | 旋转物体 | Day 050+ 部分 |

### 4.3 下级

- **AABB 四角 → tile 索引转换** —— `tile_x = pixel_x / TILE_SIZE`
- **Tile loop** —— 遍历覆盖的 tile(`for ty in top..=bottom`)
- **Per-axis check** —— 分轴检查的核心
- **Wall sliding 行为** —— 分轴检查的结果,玩家贴墙滑
- **can_move_to / try_move 函数** —— 碰撞接口

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:物体 A 不能穿过物体 B。

| 语境 | A | B | 算法 |
|---|---|---|---|
| 2D tile 游戏 | 玩家方块 | Wall tile | AABB vs tile(这集) |
| 2D 自由布局 | 玩家方块 | 怪物方块 | AABB vs AABB |
| 3D 游戏 | 玩家胶囊 | 场景几何 | 胶囊 vs 多边形(GJK) |
| 物理 sandbox | 圆形 | 圆形 | 距离比较(r1+r2 < dist) |
| UI 拖拽 | 鼠标光标 | UI 元素 | 点 vs 矩形 |

核心思想相同:**检查几何重叠**。差别在物体形状(圆 / 矩形 / 胶囊 / 多边形)和性能(网格加速 / 空间分区)。

### 历史演化

- **1970s**:碰撞用整数比较(吃豆人:玩家和怪物的 tile 坐标相等就是碰撞)
- **1980s**:AABB 出现,2D 游戏标配
- **1990s**:3D 碰撞需要新算法(GJK 1990, SAT 1995)
- **2000s**:Continuous Collision Detection 兴起(防止高速穿墙)
- **2010s**:GPU 加速碰撞检测(对比 GPU 光栅化)
- **2020s**:机器学习辅助碰撞预测(实验性)

Casey 在 HH 里走 70 年代的路——从最简单的 tile 碰撞开始,逐步加复杂度。这是教学最优路径。

### 离散 vs 连续碰撞

| | 离散(这集) | 连续(Day 045) |
|---|---|---|
| 检查时机 | 每帧一次 | 沿移动路径多次 |
| 复杂度 | O(1) per frame | O(移动距离 / tile_size) |
| 高速穿墙 | **会穿** | **不会穿** |
| 实现难度 | 简单 | 复杂 |
| 适合 | 慢速玩家 | 高速子弹 |

90% 游戏用离散就够了(玩家速度不会高到穿墙)。少数场景(子弹、超高速移动)用连续。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 的 `can_move_to` 检查"AABB 在新位置是否撞 Wall tile"。如果玩家是 32×32,tile 也是 32×32,玩家正好放在 tile (0, 0) 上(左上角对齐 tile 边界)。`can_move_to(map, 0, 0, 32)` 会检查哪些 tile?

**参考解答**:

```
AABB: 左上 (0, 0),宽高 32,所以占据像素 (0..31, 0..31)
tile_left  = 0 / 32 = 0
tile_right = (0 + 32 - 1) / 32 = 31 / 32 = 0
tile_top    = 0 / 32 = 0
tile_bottom = 31 / 32 = 0

检查范围:ty in 0..=0, tx in 0..=0
检查的 tile:只有 (0, 0)
```

只检查 1 个 tile。这是正确的——32×32 的方块正好覆盖 1 个 tile。

**延伸**:如果玩家是 33×33(略大于 tile),`can_move_to(0, 0, 33)` 会检查 4 个 tile:

```
tile_right = (0 + 33 - 1) / 32 = 32 / 32 = 1
tile_bottom = 32 / 32 = 1

检查范围:tx in 0..=1, ty in 0..=1
检查的 tile:(0,0), (1,0), (0,1), (1,1)
```

AABB 跨越了 2×2 = 4 个 tile,所以检查 4 个。这是 `size - 1` 的妙处——避免多检查一行/列。

如果写错成 `tile_right = (new_x + size) / TILE_SIZE`(漏了 -1),玩家 32×32 会检查 2 个 tile(0 和 1),即使 tile 1 完全不被覆盖。Bug 难发现——游戏看似正常,但有时撞墙过早。

**题**:实现一个完整的 tile map + 玩家 + 碰撞 demo。要求:

1. 64×64 tile 地图,有 Grass 和 Wall
2. 玩家 32×32,初始在世界中央
3. WASD 移动玩家,200 像素/秒

5. 每秒导出一个 PPM 文件,看玩家轨迹

完成标准:玩家不能穿墙,贴墙能滑动。导出的 PPM 序列里能看到玩家从中央移动到边缘,沿墙滑动的过程。

**参考解答**:

```rust
// src/main.rs
// cargo new --bin collision_demo && cd collision_demo

use std::time::{Duration, Instant};

const TILE_SIZE: i32 = 32;
const SCREEN_WIDTH: i32 = 640;
const SCREEN_HEIGHT: i32 = 480;
const MAP_WIDTH: i32 = 64;
const MAP_HEIGHT: i32 = 64;
const PLAYER_SIZE: i32 = 32;

#[derive(Copy, Clone, Debug, PartialEq)]
enum TileValue { Empty, Grass, Wall }

struct TileMap {
    tiles: Vec<TileValue>,
    width: i32, height: i32,
}

impl TileMap {
    fn new(width: i32, height: i32) -> Self {
        Self {
            tiles: vec![TileValue::Grass; (width * height) as usize],
            width, height,
        }
    }
    fn get(&self, tx: i32, ty: i32) -> TileValue {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height {
            return TileValue::Wall;  // 越界当墙
        }
        self.tiles[(ty * self.width + tx) as usize]
    }
    fn set(&mut self, tx: i32, ty: i32, v: TileValue) {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height { return; }
        self.tiles[(ty * self.width + tx) as usize] = v;
    }
}

#[derive(Copy, Clone, Default, Debug)]
struct Vec2 { x: f32, y: f32 }

#[derive(Default)]
struct Player { pos: Vec2 }

fn can_move_to(map: &TileMap, x: i32, y: i32, size: i32) -> bool {
    let tl = x / TILE_SIZE;
    let tr = (x + size - 1) / TILE_SIZE;
    let tt = y / TILE_SIZE;
    let tb = (y + size - 1) / TILE_SIZE;
    for ty in tt..=tb {
        for tx in tl..=tr {
            if map.get(tx, ty) == TileValue::Wall {
                return false;
            }
        }
    }
    true
}

#[derive(Default, Clone, Copy)]
struct Input { left: bool, right: bool, up: bool, down: bool }

fn update_player(map: &TileMap, player: &mut Player, input: Input, dt: f32) {
    let speed = 200.0_f32;
    let dx = (input.right as i32 - input.left as i32) as f32 * speed * dt;
    let dy = (input.down as i32 - input.up as i32) as f32 * speed * dt;

    // 分轴碰撞 - wall sliding
    let new_x = player.pos.x + dx;
    if can_move_to(map, new_x as i32, player.pos.y as i32, PLAYER_SIZE) {
        player.pos.x = new_x;
    }
    let new_y = player.pos.y + dy;
    if can_move_to(map, player.pos.x as i32, new_y as i32, PLAYER_SIZE) {
        player.pos.y = new_y;
    }
}

fn write_ppm(filename: &str, map: &TileMap, player: &Player, cam_x: i32, cam_y: i32) {
    use std::io::Write;
    let mut f = std::fs::File::create(filename).unwrap();
    writeln!(f, "P6\n{} {}\n255", SCREEN_WIDTH, SCREEN_HEIGHT).unwrap();
    let mut bytes = Vec::with_capacity((SCREEN_WIDTH * SCREEN_HEIGHT * 3) as usize);
    for py in 0..SCREEN_HEIGHT {
        for px in 0..SCREEN_WIDTH {
            let wx = px + cam_x;
            let wy = py + cam_y;
            // 玩家像素?
            let in_player = wx >= player.pos.x as i32
                && wx < player.pos.x as i32 + PLAYER_SIZE
                && wy >= player.pos.y as i32
                && wy < player.pos.y as i32 + PLAYER_SIZE;
            let color = if in_player {
                [0xFF, 0x00, 0x00]  // 红
            } else {
                let tx = wx / TILE_SIZE;
                let ty = wy / TILE_SIZE;
                match map.get(tx, ty) {
                    TileValue::Grass => [0x44, 0xAA, 0x44],
                    TileValue::Wall => [0x88, 0x88, 0x88],
                    _ => [0, 0, 0],
                }
            };
            bytes.extend(color);
        }
    }
    f.write_all(&bytes).unwrap();
}

fn main() {
    // 构造地图:周围一圈墙 + 中央一个十字墙
    let mut map = TileMap::new(MAP_WIDTH, MAP_HEIGHT);
    for i in 0..MAP_WIDTH {
        map.set(i, 0, TileValue::Wall);
        map.set(i, MAP_HEIGHT - 1, TileValue::Wall);
    }
    for i in 0..MAP_HEIGHT {
        map.set(0, i, TileValue::Wall);
        map.set(MAP_WIDTH - 1, i, TileValue::Wall);
    }
    // 中央 L 形墙
    for i in 20..40 { map.set(i, 30, TileValue::Wall); }
    for i in 20..35 { map.set(30, i, TileValue::Wall); }

    let mut player = Player::default();
    player.pos.x = 10.0 * TILE_SIZE as f32;
    player.pos.y = 10.0 * TILE_SIZE as f32;

    let dt = 0.0167_f32;
    let mut frame = 0;
    let mut sim_time = 0.0;

    // 模拟一段固定输入序列
    let sequence = [
        (0.0..2.0, Input { right: true, ..Default::default() }),       // 右走 2s
        (2.0..4.0, Input { right: true, up: true, ..Default::default() }), // 右上斜走 2s
        (4.0..6.0, Input { up: true, ..Default::default() }),          // 上走 2s
    ];

    for (range, input) in sequence {
        while sim_time < range.end {
            let in_range = sim_time >= range.start;
            let cur_input = if in_range { input } else { Input::default() };
            update_player(&map, &mut player, cur_input, dt);
            sim_time += dt;
            frame += 1;
            if frame % 60 == 0 {
                let filename = format!("frame_{:03}.ppm", frame / 60);
                let cam_x = (player.pos.x as i32) - SCREEN_WIDTH / 2;
                let cam_y = (player.pos.y as i32) - SCREEN_HEIGHT / 2;
                write_ppm(&filename, &map, &player, cam_x, cam_y);
                println!("{}: player at ({:.1}, {:.1})",
                    filename, player.pos.x, player.pos.y);
            }
        }
    }
}
```

**关键代码解释**:

- `(input.right as i32 - input.left as i32)` —— 把两个 bool 转成 +1/0/-1。`true as i32 = 1`、`false as i32 = 0`。所以右键按下=+1,左键按下=-1,都不按=0。这让"同时按 A 和 D"得到 0(不移动),合理。
- `(0.0..2.0, Input { ... })` —— Rust 的范围语法。`0.0..2.0` 是 RangeInclusive 不,实际是 Range(不含 end)。我用 `sim_time < range.end` 检查。
- `..Default::default()` —— struct update 语法。其他字段用 Default 填。

const TILE_SIZE: i32 = 32;

#[derive(Copy, Clone, Debug, PartialEq)]
enum TileValue { Empty, Wall }

#[derive(Default)]
struct TileMap {
    tiles: Vec<TileValue>,
    width: i32,
    height: i32,
}

impl TileMap {
    fn new(width: i32, height: i32) -> Self {
        Self {
            tiles: vec![TileValue::Empty; (width * height) as usize],
            width, height,
        }
    }
    fn get(&self, tx: i32, ty: i32) -> TileValue {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height {
            return TileValue::Wall;
        }
        self.tiles[(ty * self.width + tx) as usize]
    }
    fn set(&mut self, tx: i32, ty: i32, v: TileValue) {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height { return; }
        self.tiles[(ty * self.width + tx) as usize] = v;
    }
}

fn can_move_to(map: &TileMap, x: i32, y: i32, size: i32) -> bool {
    let tl = x / TILE_SIZE;
    let tr = (x + size - 1) / TILE_SIZE;
    let tt = y / TILE_SIZE;
    let tb = (y + size - 1) / TILE_SIZE;
    for ty in tt..=tb {
        for tx in tl..=tr {
            if map.get(tx, ty) == TileValue::Wall { return false; }
        }
    }
    true
}

/// 分轴移动 - wall sliding
/// 返回 (实际移动的 x, 实际移动的 y)
fn try_move(map: &TileMap, x: i32, y: i32, dx: i32, dy: i32, size: i32) -> (i32, i32) {
    // x 方向
    let new_x = if can_move_to(map, x + dx, y, size) { x + dx } else { x };
    // y 方向,用 new_x
    let new_y = if can_move_to(map, new_x, y + dy, size) { y + dy } else { y };
    (new_x, new_y)
}

**Troubleshooting**:

- `error: cannot multiply f32 by i32` —— 类型不匹配。Rust 不自动转换 f32 / i32。手动 `as f32` 或 `as i32`。
- 测试失败,实际值和预期差 1 —— 检查 `size - 1` 的边界。如果是 32×32 AABB,右边像素是 new_x + 31,不是 new_x + 32。
- tunneling 测试不通过 —— 检查 wall 在哪个 tile。tile_x = pixel_x / 32,所以 pixel 160..191 是 tile 5(160/32=5)。
