# Day 032 · 统一的位置表示

> Day 031 你定下了坐标系约定,玩家位置用 `Vec2` 表达。但 Casey 在 Day 032 提出一个隐藏问题:**f32 在大世界里会精度爆炸**。一个 100 万 tile 宽的世界,玩家位置 wx 可能是 32,000,000.0——f32 在这个范围的精度只有 ~2 像素,玩家位置帧间抖动,渲染闪烁。Day 032 的解决方案是 **WorldPos**:tile 整数坐标 + tile 内浮点 offset + map_id。

## 0 · 为什么要有这一天

先看一个让人崩溃的 bug。假设你做一个开放世界游戏,世界尺寸 100 公里 × 100 公里。1 像素 = 1 厘米,所以世界是 10,000,000 × 10,000,000 像素。玩家在世界中央,坐标 (5,000,000, 5,000,000)。

你写代码:

```rust
player.pos.x += vel.x * dt;
```

跑起来发现:

- 玩家位置帧间抖动,看起来"在抖"
- 玩家从 (5,000,000, 5,000,000) 走到 (5,000,001, 5,000,000),位置看起来"瞬移"——因为 f32 在这个范围精度只有 ~0.5 像素,所以 5,000,000.5 和 5,000,000.0 在 f32 里可能相等
- 渲染时摄像机抖动,画面"在抖"
- 物理碰撞检测精度下降,玩家穿墙

这个 bug 叫 **floating point precision loss**(浮点精度丢失)。**根因**:f32 只有 23 位尾数(2^23 ≈ 8 百万),所以 f32 在 8,388,608 以上的整数精度就开始丢失。

**f32 的精度边界**:

| 数值范围 | f32 精度 |
|---|---|
| 0 - 16,777,216 (2^24) | 1 像素 |
| 16,777,216 - 33,554,432 | 2 像素 |
| 33,554,432 - 67,108,864 | 4 像素 |
| 67,108,864 - 134,217,728 | 8 像素 |
| ... | 越大越糟 |

对一个 1280×720 屏幕的游戏,玩家如果走到世界 x = 16,777,216(2^24),他的位置已经无法精确到 1 像素。这是个**灾难**。

Casey 在 Day 032 提出的解决方案叫 **floating point origin**(浮点原点)或 **hierarchical coordinates**(分层坐标)。**核心思想**:把"绝对位置"拆成"粗粒度 + 细粒度"两层:

- **粗粒度**:tile 整数坐标(精确,无精度问题)
- **细粒度**:tile 内浮点 offset(范围 [0, 32),f32 在这个范围精度极高)

玩家位置不再是 `(wx, wy)`,而是 `(tile_x, tile_y, offset_x, offset_y, map_id)`。位置加减时,如果 offset 超过 [0, TILE_SIZE),就**进位/借位**到 tile 坐标。这样:

- tile 坐标永远精确(整数无精度问题)
- offset 永远小范围(f32 精度高)
- 总位置 = tile * TILE_SIZE + offset

这是 game dev 的经典模式。**Minecraft** 用 chunk(16×16×256)+ block + offset。**No Man's Sky** 用 sector + planet + local。粒度由游戏规模决定。

心理锚点:看完这集,你应该能:

- 解释 f32 在大世界为什么不够用
- 写出 WorldPos 结构 + normalize 函数
- 解释 Minecraft 的 chunk 系统和 Casey 的 WorldPos 的共同点

如果你做不到,反复看 §2 的"精度问题"和"WorldPos 结构"部分。Day 049 会调试 WorldPos 的 bug(offset 没 normalize 导致位置跳跃),Day 033 的虚拟化大世界依赖这套表示。

## 2 · 心智模型

### 类比:地图上的"省 + 市 + 详细地址"

你寄快递,地址写成:

```
中国
  └ 北京市
      └ 海淀区
          └ 中关村大街 1 号
```

这是**层级地址**——大区域到小区域逐级精确。你不会写"中国第 14 亿 567 万 8923 号居民",因为:

- 大数字精度难维护(谁谁是第几亿人,容易数错)
- 层级结构便于查找(按省 / 市 / 区索引)

WorldPos 也是这样:

```
WorldPos:
  map_id: u32         ← 哪张地图(类似"省")
  tile_x: i32         ← tile 整数坐标(类似"市")
  tile_y: i32
  offset_x: f32       ← tile 内偏移(类似"街道地址")
  offset_y: f32
```

- map_id 标识"在哪个地图"
- tile 坐标是精确的整数,无精度问题
- offset 是小范围浮点(0-32 像素),f32 精度极高

### f32 精度问题演示

```rust
fn main() {
    let big = 16_777_216.0_f32;  // 2^24
    let a = big;
    let b = big + 1.0;
    println!("a = {}", a);
    println!("b = {}", b);
    println!("a == b: {}", a == b);  // true!
    println!("a + 2.0 = {}", big + 2.0);  // 16777218(跳过 16777217)
}
```

输出:

```
a = 16777216
b = 16777216
a == b: true
a + 2.0 = 16777218
```

**a + 1 居然等于 a**——这就是 f32 的精度丢失。在 2^24 以上,f32 无法表示每个连续整数。

游戏世界里:玩家如果走到 x = 16,777,216(2^24),他的位置每次 +1 都不变,看起来"卡住"。游戏体验是垃圾。

**f32 精度边界**(再列一次,加深印象):

| 数值 | f32 精度 |
|---|---|
| 0 - 2^23 ≈ 8M | < 1 像素(超精度) |
| 2^23 - 2^24 ≈ 16M | 1 像素 |
| 2^24 - 2^25 ≈ 33M | 2 像素(开始抖动) |
| 2^25 - 2^26 ≈ 67M | 4 像素 |
| 2^26 - 2^27 ≈ 134M | 8 像素(明显抖) |
| 2^30 ≈ 1G | 64 像素(灾难) |

对一个 100km × 100km 的世界(像素尺度),玩家在世界中央就在 2^23 - 2^24 范围,精度只够 1-2 像素。**不能用 f32 表示绝对位置**。

### WorldPos 结构

```rust
#[derive(Copy, Clone, Debug)]
struct WorldPos {
    map_id: u32,        // 哪张地图
    tile_x: i32,        // tile 整数坐标
    tile_y: i32,
    offset_x: f32,      // tile 内偏移,范围 [0, TILE_SIZE)
    offset_y: f32,
}
```

**关键不变量(invariant)**:

- `offset_x` 必须在 [0, TILE_SIZE) 范围内,即 [0, 32)
- `offset_y` 必须在 [0, TILE_SIZE) 范围内
- 任何修改 WorldPos 的操作后,必须调 `normalize()` 维持不变量

### normalize 函数

```rust
impl WorldPos {
    fn normalize(&mut self) {
        // 把 offset 超出 [0, TILE_SIZE) 的部分进位/借位到 tile
        // 例:offset_x = 35,tile_x += 1,offset_x -= 32 = 3
        // 例:offset_x = -5,tile_x -= 1,offset_x += 32 = 27

        while self.offset_x >= TILE_SIZE {
            self.offset_x -= TILE_SIZE;
            self.tile_x += 1;
        }
        while self.offset_x < 0.0 {
            self.offset_x += TILE_SIZE;
            self.tile_x -= 1;
        }
        while self.offset_y >= TILE_SIZE {
            self.offset_y -= TILE_SIZE;
            self.tile_y += 1;
        }
        while self.offset_y < 0.0 {
            self.offset_y += TILE_SIZE;
            self.tile_y -= 1;
        }
    }
}
```

**while 不是 if**:offset 可能比 TILE_SIZE 大很多(比如 offset = 100,要进位 3 次)。用 while 循环直到稳定。

**优化版**(避免循环):

```rust
fn normalize(&mut self) {
    let extra_x = (self.offset_x / TILE_SIZE).floor() as i32;
    self.tile_x += extra_x;
    self.offset_x -= extra_x as f32 * TILE_SIZE;

    let extra_y = (self.offset_y / TILE_SIZE).floor() as i32;
    self.tile_y += extra_y;
    self.offset_y -= extra_y as f32 * TILE_SIZE;
}
```

一步完成。但**循环版更易读**,Casey 教学用循环版,生产代码可以用优化版。

### WorldPos 加减位移

```rust
impl WorldPos {
    /// 在当前位置加一个位移
    fn add_offset(&mut self, dx: f32, dy: f32) {
        self.offset_x += dx;
        self.offset_y += dy;
        self.normalize();
    }
}

// 用法
let mut pos = WorldPos { map_id: 0, tile_x: 5, tile_y: 3, offset_x: 20.0, offset_y: 10.0 };
pos.add_offset(15.0, 0.0);
// 加完后:
//   offset_x = 35 → normalize → tile_x = 6, offset_x = 3
//   最终: tile (6, 3) offset (3, 10)
```

注意:**位移用 f32**(因为玩家速度是浮点),位置用 WorldPos(精度安全)。

### WorldPos → 世界坐标(只为渲染)

```rust
impl WorldPos {
    /// 转成世界坐标 f32。注意:在大世界会精度丢失!
    /// 只用于渲染(渲染层接受小范围误差)。
    fn to_world_x(&self) -> f32 {
        self.tile_x as f32 * TILE_SIZE + self.offset_x
    }
    fn to_world_y(&self) -> f32 {
        self.tile_y as f32 * TILE_SIZE + self.offset_y
    }
}
```

**警告**:这个函数在大世界会精度丢失。**只能局部用**(比如玩家相对相机的位置——相对位置是小的)。

### 渲染时的技巧:相对相机

为了在渲染时**避免精度问题**,使用"相对相机"的坐标:

```rust
fn render_entity(entity_pos: &WorldPos, camera_pos: &WorldPos, fb: &mut [u32]) {
    // 不要:let wx = entity_pos.to_world_x();  // 精度丢失!
    //     let sx = wx - camera_pos.to_world_x();

    // 正确:直接在 WorldPos 层算相对位置
    let rel = relative_pos(entity_pos, camera_pos);  // 见下面
    let sx = rel.x;
    let sy = rel.y;
    draw_at(sx, sy, fb);
}

fn relative_pos(a: &WorldPos, b: &WorldPos) -> Vec2 {
    // a 相对 b 的位置(都是 WorldPos)
    // 假设 a 和 b 在同一 map_id
    assert_eq!(a.map_id, b.map_id);

    // tile 差 × TILE_SIZE + offset 差
    let dx = (a.tile_x - b.tile_x) as f32 * TILE_SIZE + (a.offset_x - b.offset_x);
    let dy = (a.tile_y - b.tile_y) as f32 * TILE_SIZE + (a.offset_y - b.offset_y);
    Vec2::new(dx, dy)
}
```

`relative_pos` 返回的是**相对位置**——如果 a 和 b 都在大世界中央,但 a 在 b 右边 5 像素,那 relative_pos 返回 (5, 0),是个小数字,f32 精度高。

这就是 floating origin 技巧的精髓:**永远不直接计算"绝对世界坐标",而是计算"相对坐标"**。

### 玩家移动用 WorldPos

```rust
struct Player {
    pos: WorldPos,  // ← 改成 WorldPos,不再是 Vec2
    vel: Vec2,      // 速度还是 Vec2(位移是小数字,f32 够用)
}

impl Player {
    fn update(&mut self, map: &TileMap, input: &GameInput, dt: f32) {
        let speed = 200.0;
        let dx = ...;  // 计算这一帧的 x 位移(浮点)
        let dy = ...;

        // 尝试 x 方向移动
        let mut new_pos = self.pos;
        new_pos.add_offset(dx, 0.0);
        if can_move_to_worldpos(map, &new_pos) {
            self.pos = new_pos;
        }

        // 尝试 y 方向移动(wall sliding)
        let mut new_pos = self.pos;
        new_pos.add_offset(0.0, dy);
        if can_move_to_worldpos(map, &new_pos) {
            self.pos = new_pos;
        }
    }
}

fn can_move_to_worldpos(map: &TileMap, pos: &WorldPos) -> bool {
    // 玩家 AABB 是 PLAYER_SIZE × PLAYER_SIZE
    // 左上角 tile = pos.tile,左上角 offset = pos.offset
    // 右下角 tile = ?(取决于 PLAYER_SIZE 是否跨 tile)

    // 简化:假设 PLAYER_SIZE = TILE_SIZE,AABB 大致占一个 tile
    // 实际要算 tile_left = floor((pos.offset_x) / TILE_SIZE) + pos.tile_x
    //                  tile_right = floor((pos.offset_x + PLAYER_SIZE - 1) / TILE_SIZE) + pos.tile_x
    // 复杂!Casey 在 Day 032 之后逐步简化这块
    let tile_x = pos.tile_x;
    let tile_y = pos.tile_y;
    map.get(tile_x, tile_y) != TileValue::Wall
}
```

**注意**:`can_move_to_worldpos` 比 `can_move_to` 复杂,因为 WorldPos 的 offset 可能让 AABB 跨越多个 tile。Casey 在 Day 032 简化教学,Day 050+ 完整版处理跨 tile。

### WorldPos vs Vec2 的取舍

| 场景 | 用什么 | 原因 |
|---|---|---|
| 玩家 / 怪物位置 | WorldPos | 大世界精度安全 |
| 速度 / 加速度 | Vec2 | 位移是小数字,f32 够 |
| 相对位移(玩家到怪物的距离) | Vec2 | 差值是小数字 |
| 渲染时屏幕坐标 | Vec2(或 i32) | 屏幕大小有限,f32 够 |
| tile 坐标 | (i32, i32) | 整数,无精度问题 |

**原则**:**绝对位置用 WorldPos,相对位置 / 位移用 Vec2**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

WorldPos / floating origin 是大世界游戏开发的**核心技术**。主流实现:

**Minecraft 的 chunk 系统**:

- 世界分成 16×16×256 的 chunk
- 每个 chunk 内部用 0-15 的 block 索引(精确)
- 玩家位置 = (chunk_x, chunk_y, chunk_z, block_x, block_y, block_z)
- chunk 是加载/卸载单位(玩家走远后,远 chunk 卸载,内存释放)

**Outer Wilds 的 star system**:

- 每个 star system 是独立坐标空间
- 玩家在 star system 内用 local coords
- 切换 star system 时,坐标完全重置

**Kerbal Space Program**:

- 早期版本(1.0 之前)用裸 f32,导致"远距离航天器抖动"
- 后期版本引入 floating origin,所有航天器相对玩家原点,精度问题消失

**Star Citizen**(在制品):

- 用 f64 而不是 WorldPos(f64 精度比 f32 高 10^9 倍)
- 但 f64 计算慢,有性能成本
- 业界争论:f64 vs WorldPos 哪个更好

**Casey 的选择**:WorldPos + f32(部分用 f64 计算中间结果)。这是经典方案,工业上证明可行。

### 3.2 · 🎨 图形学视角

图形学里**坐标精度**是个隐藏的大问题。OpenGL / Vulkan 内部用 f32,所以即使你的 game 代码用 WorldPos,渲染时还是要转回 f32——而 f32 在大世界会精度丢失。

**GPU 渲染的精度技巧**:

1. **相对相机渲染**(floating origin for GPU):所有 vertex 在上传 GPU 前,**减去相机位置**,变成相对相机的坐标。这样 GPU 收到的坐标都是小数字,f32 精度够。
2. **分层投影**:近处用高精度 f32 渲染,远处用低精度 + 偏移。复杂但效果好。
3. **f64 GPU 计算**:某些 GPU 支持 double precision(主要是计算卡,游戏卡不支持),可以避免精度问题。但游戏卡用 f64 极慢。

Casey 在 Day 1-234 软渲染,Day 235+ OpenGL 后用 floating origin(相对相机坐标)解决。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核也有类似的"层级坐标"问题——**虚拟内存地址**。

32 位系统的虚拟地址空间是 0 - 4GB。但物理内存可能更大(服务器 64GB+),怎么办?

**Linux 的解决方案**:页表(page table)。把虚拟地址拆成"页目录 + 页表 + 页内 offset":

```
32 位虚拟地址:
  [ 10 bit 页目录索引 | 10 bit 页表索引 | 12 bit 页内 offset ]

- 页目录索引:哪个 4MB 区域(粗粒度)
- 页表索引:那个区域里的哪个 4KB 页(中粒度)
- 页内 offset:页内的字节(细粒度)
```

这就是 Linux 的"层级坐标"——和 WorldPos 思想一致(粗 + 细)。

**64 位系统**:地址 48 位有效,分成 5 层(4 级页表 + offset):

```
48 位虚拟地址:
  [ 9 | 9 | 9 | 9 | 12 ]
   PML4 PDPT PD PT offset
```

更深的层级。Casey 的 WorldPos 是 2 层(tile + offset),Linux 页表是 5 层——但思想相同。

**Linux 工具验证**:

```bash
# 看你的系统页大小
getconf PAGE_SIZE
# 4096(典型 x86_64)

# 看一个进程的虚拟内存映射
cat /proc/$$/maps
# 输出每行:起始地址-结束地址 权限 偏移 设备 inode 文件
# 地址看起来连续,但物理上是页粒度管理

# 看页表
sudo cat /proc/$$/pagemap | xxd | head
# (需要 root,输出二进制)
```

### 3.4 · 🦀 Rust 生态视角

Rust 表达 WorldPos 有几个考虑:

**用 struct + impl**(Casey 风格):

```rust
#[derive(Copy, Clone, Debug)]
struct WorldPos {
    map_id: u32,
    tile_x: i32, tile_y: i32,
    offset_x: f32, offset_y: f32,
}

impl WorldPos {
    fn normalize(&mut self) { ... }
    fn add_offset(&mut self, dx: f32, dy: f32) { ... }
}
```

简单直接,完全控制布局。

**用 generic(泛型)**:

```rust
struct HierarchicalPos<Coarse, Fine> {
    coarse: Coarse,
    fine: Fine,
}

type WorldPos = HierarchicalPos<(i32, i32), (f32, f32)>;
```

更通用,但教学不需要这种抽象。

**Rust 所有权 + WorldPos**:

WorldPos 是 Copy 类型(都是 i32 / u32 / f32),所以可以按值传递,无 ownership 问题:

```rust
// ✓ WorldPos 是 Copy,可以直接传值
fn update_player(player: &mut Player) {
    let new_pos = player.pos;  // Copy
    new_pos.add_offset(5.0, 0.0);
    if can_move_to(&new_pos) {
        player.pos = new_pos;  // Copy 回去
    }
}
```

无借用问题。

**Rust trait 表达"有位置的"**:

```rust
trait HasWorldPos {
    fn pos(&self) -> WorldPos;
    fn set_pos(&mut self, pos: WorldPos);
}

impl HasWorldPos for Player { ... }
impl HasWorldPos for Monster { ... }
impl HasWorldPos for Projectile { ... }

fn move_entity<E: HasWorldPos>(entity: &mut E, dx: f32, dy: f32) {
    let mut pos = entity.pos();
    pos.add_offset(dx, dy);
    entity.set_pos(pos);
}
```

把"移动"抽象成 trait method,任何 entity 都能用。Casey 不用 trait(他更喜欢具体函数),但生产代码这种抽象合理。

## 4 · 认知地图

### 4.1 上级

- **Hierarchical coordinates**(层级坐标)—— 大区域 + 小偏移的分层表示
- **Floating point origin**(浮点原点)—— 永远以"当前位置"为原点,避免远距离精度问题
- **Coordinate normalization**(坐标归一化)—— 维护坐标的合法范围
- **Invariant programming**(不变量编程)—— 数据结构有"必须满足的条件",由专门函数维护

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 裸 f32 坐标 | 简单但大世界精度丢 | 小世界游戏 | HH 早期用 |
| WorldPos(tile + offset) | 精度安全,多层结构 | 大世界游戏 | ✅ Day 032+ Casey 选 |
| f64 坐标 | 精度高但内存翻倍 | 中等世界,性能不敏感 | HH 不用 |
| Chunk + local(Minecraft) | WorldPos 的更复杂版 | 巨大世界(无限世界) | HH Day 033+ 接近 |
| Sector + local(太空游戏) | 多个独立坐标系 | 跨星系游戏 | HH 不用 |

### 4.3 下级

- **map_id** —— 标识哪个地图
- **tile_x, tile_y** —— 整数 tile 坐标
- **offset_x, offset_y** —— 浮点 tile 内偏移,范围 [0, TILE_SIZE)
- **normalize()** —— 维持 offset 在合法范围
- **to_world() / from_world()** —— WorldPos ↔ Vec2 转换(只在局部用)
- **relative_pos()** —— 两个 WorldPos 的相对距离(精度安全)

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:大范围连续空间,需要精确表达任意位置。

| 语境 | "层级"叫法 | 粒度 |
|---|---|---|
| 2D 游戏 | tile + offset | tile = 32 像素 |
| Minecraft | chunk + block | chunk = 16×16×256 |
| 太空游戏 | sector + local | sector = 1 光年 |
| Linux 虚拟内存 | page table + offset | page = 4KB |
| GPS | 度 + 分 + 秒 | 度 = 111km |
| 邮政地址 | 国 + 省 + 市 + 街道 | 国 = 千万 km |
| 时间 | 年 + 月 + 日 + 时 + 分 + 秒 | 年 = 31M 秒 |

所有这些场景的核心思想:**层级表达 + 每层精度可控**。

### f32 vs f64 vs WorldPos

| | f32 | f64 | WorldPos |
|---|---|---|---|
| 精度(2^N 整数范围) | 2^24(16M) | 2^53(9 quadrillion) | 任意(tile 整数 + offset) |
| 内存 | 4 字节 | 8 字节 | 20 字节(2i32 + 2f32 + u32) |
| 计算速度 | 快(SIMD 友好) | 中(慢于 f32) | 慢(每次操作要 normalize) |
| 适合 | 小世界 | 中等世界 | 任意大世界 |

Casey 选 WorldPos——大世界游戏的标准选择。

### 历史演化

- **1980s**:游戏世界小(几百 tile),f32 够
- **1990s**:GTA / Skyrim 等开放世界出现,f32 开始不够用
- **2000s**:floating origin 技术普及
- **2010s**:Minecraft chunk 系统展示分层坐标威力
- **2020s**:Star Citizen 用 f64 探索另一条路

Casey 在 Day 032 教 floating origin,是 2014 年的视频,但至今仍是主流方案。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 的 WorldPos 把 offset 限制在 [0, TILE_SIZE) 范围。为什么不限制在 [-TILE_SIZE/2, TILE_SIZE/2)?后者看起来更"对称"(负 offset 表示"tile 中心偏左")。

**参考解答**:**因为 tile 索引要从 offset 推出来**,而 [0, TILE_SIZE) 让这件事最简单:

```
offset 在 [0, 32) ⟺ offset / 32 = 0 ⟺ offset 对应"当前 tile"
offset 在 [32, 64) ⟺ offset / 32 = 1 ⟺ offset 对应"下一个 tile"
```

如果 offset 是 [-16, 16),那 offset = -5 表示"当前 tile 的左半"还是"上一个 tile 的右半"?有歧义——offset 在 [-16, 0) 时,要 floor(offset / 32) = -1(上一个 tile),offset 在 [0, 16) 时 floor = 0(当前 tile)。**逻辑变复杂**,容易写错。

[0, TILE_SIZE) 是**单射**——每个 offset 对应唯一的 tile 偏移。Casey 选这个简化逻辑。

延伸:**有些游戏用 center-relative**(offset 范围 [-TILE_SIZE/2, TILE_SIZE/2)),因为"玩家位置 = AABB 中心"的设定下,offset = 0 表示"在 tile 正中心",对称。但 Casey 用 left-top representation,所以 [0, TILE_SIZE)。

### Lv2 · 动手实践

**题**:实现完整的 WorldPos 结构,带单元测试。要求:

1. WorldPos 结构(map_id, tile_x, tile_y, offset_x, offset_y)
2. `normalize` 函数(offset 超出范围时进位/借位)
3. `add_offset` 函数(加位移后自动 normalize)
4. `relative_pos` 函数(两个 WorldPos 的相对距离)
5. 至少 5 个单元测试,覆盖正常位置、超范围 offset、负 offset、跨多 tile offset、相对距离

**参考解答**:

```rust
// src/main.rs
// cargo new --bin worldpos && cd worldpos

const TILE_SIZE: f32 = 32.0;

#[derive(Copy, Clone, Debug, PartialEq)]
struct WorldPos {
    map_id: u32,
    tile_x: i32,
    tile_y: i32,
    offset_x: f32,
    offset_y: f32,
}

impl WorldPos {
    fn new(map_id: u32, tile_x: i32, tile_y: i32) -> Self {
        Self { map_id, tile_x, tile_y, offset_x: 0.0, offset_y: 0.0 }
    }

    fn normalize(&mut self) {
        // 处理 x
        let extra_x = (self.offset_x / TILE_SIZE).floor() as i32;
        self.tile_x += extra_x;
        self.offset_x -= extra_x as f32 * TILE_SIZE;
        // 处理 y
        let extra_y = (self.offset_y / TILE_SIZE).floor() as i32;
        self.tile_y += extra_y;
        self.offset_y -= extra_y as f32 * TILE_SIZE;
    }

    fn add_offset(&mut self, dx: f32, dy: f32) {
        self.offset_x += dx;
        self.offset_y += dy;
        self.normalize();
    }

    fn to_world_x(&self) -> f32 {
        self.tile_x as f32 * TILE_SIZE + self.offset_x
    }
    fn to_world_y(&self) -> f32 {
        self.tile_y as f32 * TILE_SIZE + self.offset_y
    }
}

fn relative_pos(a: &WorldPos, b: &WorldPos) -> (f32, f32) {
    assert_eq!(a.map_id, b.map_id, "cannot compute relative pos across maps");
    let dx = (a.tile_x - b.tile_x) as f32 * TILE_SIZE + (a.offset_x - b.offset_x);
    let dy = (a.tile_y - b.tile_y) as f32 * TILE_SIZE + (a.offset_y - b.offset_y);
    (dx, dy)
}

fn main() {
    println!("Run cargo test to verify WorldPos behavior.");
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn new_worldpos_has_zero_offset() {
        let pos = WorldPos::new(0, 5, 3);
        assert_eq!(pos.offset_x, 0.0);
        assert_eq!(pos.offset_y, 0.0);
    }

    #[test]
    fn normalize_handles_overflow() {
        let mut pos = WorldPos::new(0, 5, 3);
        pos.offset_x = 50.0;  // 超过 TILE_SIZE
        pos.normalize();
        assert_eq!(pos.tile_x, 6);     // 进位
        assert!((pos.offset_x - 18.0).abs() < 0.001);  // 50 - 32 = 18
    }

    #[test]
    fn normalize_handles_negative_offset() {
        let mut pos = WorldPos::new(0, 5, 3);
        pos.offset_x = -10.0;  // 负数
        pos.normalize();
        assert_eq!(pos.tile_x, 4);     // 借位
        assert!((pos.offset_x - 22.0).abs() < 0.001);  // -10 + 32 = 22
    }

    #[test]
    fn normalize_handles_multiple_overflow() {
        let mut pos = WorldPos::new(0, 0, 0);
        pos.offset_x = 100.0;  // 100 / 32 = 3.125 → 3 个 tile
        pos.normalize();
        assert_eq!(pos.tile_x, 3);
        assert!((pos.offset_x - 4.0).abs() < 0.001);  // 100 - 96 = 4
    }

    #[test]
    fn add_offset_normalizes_automatically() {
        let mut pos = WorldPos::new(0, 5, 3);
        pos.add_offset(40.0, 0.0);
        // offset_x 0 + 40 = 40,超过 32,normalize
        assert_eq!(pos.tile_x, 6);
        assert!((pos.offset_x - 8.0).abs() < 0.001);
    }

    #[test]
    fn relative_pos_computes_distance() {
        let a = WorldPos::new(0, 5, 3);
        let b = WorldPos::new(0, 3, 3);
        let (dx, dy) = relative_pos(&a, &b);
        assert_eq!(dx, 64.0);  // 2 tile 差
        assert_eq!(dy, 0.0);
    }

    #[test]
    fn relative_pos_with_offsets() {
        let mut a = WorldPos::new(0, 5, 3);
        a.offset_x = 10.0;
        let mut b = WorldPos::new(0, 5, 3);
        b.offset_x = 4.0;
        let (dx, _) = relative_pos(&a, &b);
        assert!((dx - 6.0).abs() < 0.001);  // 10 - 4
    }

    #[test]
    #[should_panic(expected = "cannot compute relative pos across maps")]
    fn relative_pos_panics_across_maps() {
        let a = WorldPos::new(0, 0, 0);
        let b = WorldPos::new(1, 0, 0);
        relative_pos(&a, &b);
    }

    #[test]
    fn to_world_recovers_original() {
        let mut pos = WorldPos::new(0, 5, 3);
        pos.offset_x = 10.5;
        pos.offset_y = 20.3;
        let wx = pos.to_world_x();
        let wy = pos.to_world_y();
        // 5 * 32 + 10.5 = 170.5,3 * 32 + 20.3 = 116.3
        assert!((wx - 170.5).abs() < 0.001);
        assert!((wy - 116.3).abs() < 0.001);
    }
}
```

```rust
// src/main.rs
// cargo new --bin worldpos_demo && cd worldpos_demo

const TILE_SIZE: f32 = 32.0;

#[derive(Copy, Clone, Debug, PartialEq)]
struct WorldPos {
    map_id: u32,
    tile_x: i32,
    tile_y: i32,
    offset_x: f32,
    offset_y: f32,
}

impl WorldPos {
    fn new(map_id: u32, tile_x: i32, tile_y: i32) -> Self {
        Self { map_id, tile_x, tile_y, offset_x: 0.0, offset_y: 0.0 }
    }

    fn normalize(&mut self) {
        let extra_x = (self.offset_x / TILE_SIZE).floor() as i32;
        self.tile_x += extra_x;
        self.offset_x -= extra_x as f32 * TILE_SIZE;
        let extra_y = (self.offset_y / TILE_SIZE).floor() as i32;
        self.tile_y += extra_y;
        self.offset_y -= extra_y as f32 * TILE_SIZE;
    }

    fn add_offset(&mut self, dx: f32, dy: f32) {
        self.offset_x += dx;
        self.offset_y += dy;
        self.normalize();
    }

    fn to_world_x(&self) -> f32 {
        self.tile_x as f32 * TILE_SIZE + self.offset_x
    }
    fn to_world_y(&self) -> f32 {
        self.tile_y as f32 * TILE_SIZE + self.offset_y
    }
}

fn demo_f32_precision_problem() {
    println!("=== f32 Precision Problem ===\n");

    // 模拟一个 100km × 100km 世界,1 像素 = 1cm
    // 世界尺寸 10M × 10M 像素
    let world_size = 10_000_000.0_f32;

    println!("World size: {} pixels", world_size);
    println!("2^24 = {}", 2_u32.pow(24) as f32);
    println!();

    // 玩家走到世界中点 (5M, 5M)
    let player_x = 5_000_000.0_f32;
    println!("Player at x = {}", player_x);
    println!("Player at x + 1 = {}", player_x + 1.0);  // 还是 5M!
    println!("Player at x + 1 == player_x: {}", (player_x + 1.0) == player_x);  // true!

    println!();
    println!("This means: player tries to move 1 pixel, but f32 can't represent it.");
    println!("Player appears stuck. Bad gameplay.");
}

fn demo_worldpos_solution() {
    println!("\n=== WorldPos Solution ===\n");

    // 玩家在大世界中央:tile = 156250 (= 5M / 32),offset = 0
    let mut pos = WorldPos::new(0, 156_250, 156_250);
    println!("Start: {:?}", pos);
    println!("Equivalent world x: {} (lossy!)", pos.to_world_x());

    // 玩家移动 1 像素
    pos.add_offset(1.0, 0.0);
    println!("\nAfter moving 1 pixel right:");
    println!("  {:?}"
, pos);
    println!("  offset_x = {} (still precise!)", pos.offset_x);

    // 玩家移动 100 像素(跨多 tile)
    pos.add_offset(100.0, 0.0);
    println!("\nAfter moving 100 more pixels right:");
    println!("  {:?}", pos);

    // 验证 WorldPos 的精度
    println!("\n=== Precision Comparison ===\n");
    let big_x = 5_000_000.0_f32;
    let mut small_offset = 0.0_f32;
    for _ in 0..10 {
        small_offset += 1.0;
    }
    println!("f32 big_x + 10 = {} (vs big_x = {}, equal: {})",
        big_x + 10.0, big_x, (big_x + 10.0) == big_x);

    let mut wp = WorldPos::new(0, 156_250, 0);
    let wp_initial_offset = wp.offset_x;
    for _ in 0..10 {
        wp.add_offset(1.0, 0.0);
    }
    println!("WorldPos offset after 10 moves: {} (initial: {}, diff: {})",
        wp.offset_x, wp_initial_offset, wp.offset_x - wp_initial_offset);
    println!("WorldPos preserves precision!");
}

fn main() {
    demo_f32_precision_problem();
    demo_worldpos_solution();
}
```
