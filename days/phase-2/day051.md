
# Day 051 · 按更新频率分离实体

> Day 050 你做完了 Minkowski 碰撞,游戏有玩家 + 几个怪物。但如果游戏世界有 10000 个 entity(门、宝箱、装饰、远处 NPC),每帧 60Hz update = 60 万次/秒,大部分是浪费——门不需要每帧更新(它根本不动)。Casey 在 Day 051 引入"频率分层":不同 entity 用不同 update 频率。

## 0 · 为什么要有这一天

游戏里**不是所有 entity 都需要 60Hz 更新**:

- **玩家** — 60Hz:输入要即时响应,动作要流畅
- **近处怪物** — 60Hz:战斗 AI 要精确
- **远处怪物** — 30Hz:走路 AI 慢半拍玩家不会注意
- **粒子特效** — 30Hz:烟、火花不需要每帧
- **门、宝箱** — 5Hz:几乎不动,只在玩家靠近时反应
- **装饰物** — 1Hz:云彩飘动、旗帜摆动
- **存档点** — 0Hz:完全静态

10000 个 entity × 60Hz = 60 万次 update/秒。如果分层(假设平均 10Hz),总 update = 10 万次,**6 倍 CPU 节省**。

**频率分层**(frequency tiering)是性能优化的一种。但 Casey 在 Day 054 会**推翻**这个设计(YAGNI 原则),改用 Day 063 的 sim region——"不限制频率,只限制范围"。Day 051 是教学——演示"做了再发现不必要"的探索式开发。

为什么学一个会被推翻的设计?因为:

1. **学习思路**:频率分层在物理引擎(Box2D)、UI 框架、Web 前端(react 的 shouldComponentUpdate)都用
2. **理解 sim region**:Day 063 的 sim region 解决同一问题(远处不模拟),但思路不同。理解 Day 051 才能对比 Day 063
3. **真实工程**:就算 Casey 推翻,你以后做其他项目可能需要频率分层(比如 ECS 框架)

心理锚点:做完今天,你应该:

1. 能用 Rust 实现"按频率调度 update"的框架
2. 知道 dt 补偿(低频 entity 用 `dt * period`)的原因
3. 能对比频率分层 vs sim region 的优劣
4. 理解 Casey 在 Day 054 推翻设计的 YAGNI 思想

## 1 · Casey 今天做了什么

Casey 在 day051 视频里做了三件事:

1. **观察性能问题**:游戏有 1000+ entity,每帧 update 全部,CPU 占用高。但 80% entity 不需要 60Hz。
2. **加 update_period 字段**:每个 entity 加 `int update_period`(周期,1 = 每帧,2 = 每两帧,12 = 每 12 帧)。
3. **改造主循环**:

   ```c
   for (int i = 0; i < entity_count; i++) {
       Entity* e = &entities[i];
       if (frame_counter % e->update_period == 0) {
           // update this entity
           UpdateEntity(e, dt * e->update_period);  // 补偿 dt
       }
   }
   ```

关键细节:**dt 补偿**。低频 entity 的 dt 要乘 update_period——否则它们运动速度只有高频的 1/period。例:玩家(60Hz)每帧 dt=1/60,位移 1 像素;门(5Hz,period=12)每 12 帧 update 一次,dt=12/60=1/5,位移 12 像素——等效 60Hz 共走 12 像素。速度一致。

Casey 还讨论了"什么时候触发 update"——固定 frame_counter % period == 0,还是按时钟?他选固定(简单),保证确定性。

## 2 · 心智模型

### 费曼类比:餐厅的厨师分工

餐厅厨房有 10 个厨师,但不是每道菜都要每秒做一次:

- 主菜(牛排) — 60Hz 每分钟出
- 配菜(沙拉) — 30Hz 每 2 分钟出
- 甜点 — 10Hz 每 6 分钟出
- 装饰(雕花) — 5Hz 每 12 分钟出

如果所有厨师都 60Hz,效率低(雕花厨师忙不过来,主菜厨师闲)。**按频率分工**——雕花厨师 5Hz,主菜厨师 60Hz,整体效率最高。

游戏的 entity 也一样:静态物体低频,动态物体高频。

### 严谨定义:频率分层调度

**调度器**(scheduler)决定每个 entity 何时 update。

```rust
pub struct Entity {
    pub update_period: u32,  // 1=每帧,2=每两帧,12=每12帧
    pub pos: Vec2,
    pub vel: Vec2,
    // ...
}

pub struct World {
    pub entities: Vec<Entity>,
    pub frame_counter: u32,
}

impl World {
    pub fn update(&mut self, input: &GameInput, dt: f32) {
        self.frame_counter += 1;

        for e in &mut self.entities {
            if self.frame_counter % e.update_period == 0 {
                let effective_dt = dt * e.update_period as f32;  // 补偿
                e.update(input, effective_dt);
            }
        }
    }
}
```

### 为什么必须 dt 补偿

**没有 dt 补偿**:低频 entity 运动速度只有高频的 1/period。

```
高频(period=1):60 帧/秒,每帧 dt=1/60,位移 speed/60 像素
                1 秒后总位移:speed 像素

低频(period=12):5 帧/秒(每 12 帧 update 一次),每帧 dt=1/60(如果不补偿)
                1 秒后位移:5 × speed/60 = speed/12 像素  ← 速度慢了 12 倍!
```

**有 dt 补偿**:

```
低频(period=12):5 次 update/秒,每次 dt = 1/60 × 12 = 1/5
                1 秒后位移:5 × speed × 1/5 = speed 像素  ← 和高频一致!
```

`dt 补偿 = dt × update_period`,保证任意频率的 entity 在相同时间内运动一致。

### 完整代码

```rust
pub struct Entity {
    pub update_period: u32,
    pub pos: Vec2,
    pub vel: Vec2,
    pub kind: EntityKind,
}

#[derive(Clone, Copy)]
pub enum EntityKind {
    Player,       // update_period = 1(60Hz)
    NearMonster,  // 1
    FarMonster,   // 2
    Door,         // 12
    Decoration,   // 60
}

impl Default for EntityKind {
    fn default() -> Self { Self::Decoration }
}

impl Entity {
    pub fn update(&mut self, input: &GameInput, dt: f32) {
        match self.kind {
            EntityKind::Player => {
                // 玩家逻辑(响应输入)
                if input.controllers[0].is_connected {
                    // ... 应用加速度等
                }
            }
            EntityKind::NearMonster | EntityKind::FarMonster => {
                // AI 逻辑
                self.pos += self.vel * dt;
            }
            EntityKind::Door => {
                // 门只在玩家靠近时反应
                // ...
            }
            EntityKind::Decoration => {
                // 装饰只摆动动画
                // ...
            }
        }
    }
}

pub struct World {
    pub entities: Vec<Entity>,
    pub frame_counter: u32,
}

impl World {
    pub fn update(&mut self, input: &GameInput, dt: f32) {
        self.frame_counter = self.frame_counter.wrapping_add(1);

        for e in &mut self.entities {
            if e.update_period == 0 || self.frame_counter % e.update_period == 0 {
                let effective_dt = dt * e.update_period.max(1) as f32;
                e.update(input, effective_dt);
            }
        }
    }
}
```

### update_period 的选择

**period = 1**(60Hz):玩家、近处怪物、投射物
**period = 2**(30Hz):远处怪物、粒子
**period = 6**(10Hz):门、宝箱
**period = 12**(5Hz):装饰、远处动画
**period = 60**(1Hz):存档点、计时器

**为什么不用任意值?** 整数 period 让 frame_counter % period 简单。浮点 period 难调度(需要累加器)。

**注意**:`frame_counter.wrapping_add(1)` 用 wrapping 防止溢出 panic。u32 最大约 40 亿,60Hz 跑 2 年才溢出,但 wrapping 是好习惯。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的频率分层应用:

**1. 物理引擎**:固定时间步(fixed timestep)。游戏 60Hz 渲染,物理 60Hz/120Hz/240Hz。子步进保证精度。

**2. UI 框架**:`shouldComponentUpdate`(React)决定组件是否更新。低优先级组件可以跳过。

**3. 网络同步**:服务器 30Hz 模拟,客户端 60Hz 渲染。中间插值。

**4. 资源加载**:LOD(level of detail),远处物体低精度,近处高精度。

**5. AI 思考**:简单 AI 每帧决策,复杂 AI 每 0.5 秒"深度思考"一次。

#### Casey 后来的反思

Casey 在 Day 054 推翻这个设计。原因:

- **管理复杂**:dormant vs active 状态切换逻辑繁琐
- **性能差异不明显**:大部分 entity update 极轻,频率分层收益小
- **sim region 更简单**(Day 063):不管频率,只限制模拟范围

**教训**:**YAGNI**(You Aren't Gonna Need It)。Day 051 是预先想象需求,Day 054 发现不需要,推翻。

### 3.2 · 🎨 图形学视角

图形学的频率分层:

**1. LOD**(Level of Detail):远处用低精度模型(少三角形),近处用高精度。每帧根据距离切换。

**2. 阴影更新**:静态物体阴影预渲染(baked),动态物体实时。

**3. 反射**:玩家附近的反射每帧更新,远处反射每 N 帧更新。

**4. 后处理**:HDR、bloom 每帧,SSAO 每 2 帧,TAA 累积多帧。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的频率分层:

**1. Timer wheel**:不同精度的定时器分层。高频定时器(microsecond)少,低频定时器(second)多。内核用层级化 wheel 减少检查开销。

**2. 进程调度**:CFS 不分层,但 RT 调度器(SCHED_FIFO)和普通进程(SCHED_NORMAL)有不同优先级。

**3. I/O 调度**:不同 I/O 优先级(nice for I/O)。Casey 的频率分层是 I/O 优先级的游戏版。

```bash
# 看 Linux 的 timer
```

### 3.4 · 🦀 Rust 生态视角

#### Rust 实现注意事项

**所有权**:`World::update` 用 `&mut self`,所有 entity 在一个借用下。OK。

**迭代器**:可以用 `for e in &mut self.entities` 迭代 + filter:

```rust
for e in self.entities.iter_mut().filter(|e| {
    self.frame_counter % e.update_period.max(1) == 0
}) {
    e.update(input, effective_dt);
}
```

但这样 effective_dt 难算(e.update_period 在 filter 里看不到)。所以用普通 for 循环。

**并发**:Day 051 是单线程。如果 entity update 互相独立,可以用 rayon 并行:

```rust
use rayon::prelude::*;

self.entities.par_iter_mut().for_each(|e| {
    if should_update(e, self.frame_counter) {
        e.update(...);
    }
});
```

但 frame_counter 是 `&self`(共享),用 `AtomicU32`。Phase 4 多线程深入。

### 4.1 上级

- **调度算法**(scheduling algorithm)—— 决定何时执行任务

- **YAGNI 原则** —— 别做未必要的功能

### 4.2 同级(并行方案对比)

| 方案 | 复杂度 | 性能收益 | Casey 选择 |
|---|---|---|---|
| 频率分层(Day 051) | 中(状态管理) | 中等 | Day 054 推翻 |

- **子步进**:物理引擎专用,游戏逻辑不适用
- **异步**:现代 ECS(Bevy)的趋势,但 HH 不用

### 4.3 下级

- **update_period** — 每 N 帧 update
- **dt 补偿** — `effective_dt = dt * period`
- **frame_counter** — 全局帧计数器
- **mod 调度** — `counter % period == 0`
- **EntityKind** — 不同 kind 不同频率

## 5 · 对照与变奏

### 不同领域的频率分层

| 领域 | 应用 | 频率 |
|---|---|---|
| 游戏 | entity update | 1Hz - 60Hz |
| 操作系统 | 进程调度 | 100Hz - 1000Hz |
| 数据库 | WAL 刷盘 | 10Hz - 100Hz |
| Web 前端 | re-render | 60Hz |
| 物联网 | sensor 上报 | 0.1Hz - 1Hz |
| 心率监测 | 数据采集 | 1Hz |
| 股票市场 | 报价 | 1Hz - 1000Hz |

所有领域都有"按重要性分配频率"的需求。Day 051 的思想是通用的。

### 频率 vs 优先级

**频率**(frequency):多久跑一次。

**优先级**(priority):多个任务同时 ready,先跑哪个。

游戏主要关心频率(update_period),操作系统两者都关心(nice + 调度)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Day 051 的低频 entity(update_period = 12)怎么保证运动速度和高频(period = 1)一样?如果不做 dt 补偿会怎样?

**参考解答**:

**dt 补偿**:`effective_dt = dt × update_period`。低频 entity 用更大的 dt,补偿"少 update"。

**没有 dt 补偿的后果**:

```
高频(period=1, dt=1/60):
  1 秒(60 帧)总位移 = 60 × (speed × 1/60) = speed

低频(period=12, dt=1/60 不补偿):
  1 秒(5 次 update)总位移 = 5 × (speed × 1/60) = speed/12
```

低频 entity 速度只有 1/12——明显不对。

**修复**:

```
低频(period=12, effective_dt = 12 × 1/60 = 1/5):
  1 秒(5 次 update)总位移 = 5 × (speed × 1/5) = speed
```

正确。

**直觉**:dt 是 update 的"步长"。频率低 → 步长应该大,否则总位移少。

```rust
    Player,
    NearMonster,
    FarMonster,
    Door,
    Decoration,
}

#[derive(Debug)]
pub struct Entity {
    pub update_period: u32,
    pub pos: Vec2,
    pub vel: Vec2,
    pub kind: EntityKind,
}

impl Default for Entity {
    fn default() -> Self {
        Self {
            update_period: 1,
            pos: Vec2::ZERO,
            vel: Vec2::ZERO,
            kind: EntityKind::Decoration,
        }
    }
}

impl Entity {
    pub fn update(&mut self, dt: f32) {
        self.pos += self.vel * dt;
    }
}

pub struct World {
    pub entities: Vec<Entity>,
    pub frame_counter: u32,
}

impl Default for World {
    fn default() -> Self {
        Self { entities: Vec::new(), frame_counter: 0 }

}

impl World {
    pub fn update(&mut self, dt: f32) {
        self.frame_counter = self.frame_counter.wrapping_add(1);

        for e in &mut self.entities {

            if self.frame_counter % period == 0 {
                let effective_dt = dt * period as f32;
                e.update(effective_dt);

    }
}
```

### Lv3 · 迁移设计

**题**:你在做**Web 服务器**,有 10000 个客户端连接。每个客户端的"心跳"频率不同:

- 活跃客户端(最近有数据):每 1 秒检查
- 半活跃(过去 10 秒有数据):每 5 秒检查
- 空闲(过去 1 分钟无数据):每 30 秒检查

设计 Rust 数据结构 + 调度算法,让总检查次数最少。

**提示**:

- 用 HashMap<ClientId, Client> 存所有客户端
- 每个客户端有 next_check_time 字段
- 主循环:遍历所有客户端,检查 current_time > next_check_time,触发心跳
- 触发后更新 next_check_time = current_time + period

为什么这个练习有价值?因为它把 Day 051 的"频率分层"思想用到真实场景(Web 后端)。理解这个,你能优化任何"周期性任务"系统。

## 8 · Rust / Arch 落地代码

### 完整可跑示例

**src/main.rs**:

```rust
mod math;
mod world;

use math::Vec2;
use world::{World, Entity, EntityKind};

fn main() {
    println!("=== 频率分层演示 ===\n");

    let mut world = World::default();

    // 添加不同频率的 entity
    world.entities.push(Entity {
        update_period: 1,  // 60Hz
        pos: Vec2::new(0.0, 0.0),
        vel: Vec2::new(100.0, 0.0),
        kind: EntityKind::Player,
    });
    world.entities.push(Entity {
        update_period: 6,  // 10Hz
        pos: Vec2::new(0.0, 10.0),
        vel: Vec2::new(100.0, 0.0),
        kind: EntityKind::FarMonster,
    });
    world.entities.push(Entity {
        update_period: 12,  // 5Hz
        pos: Vec2::new(0.0, 20.0),
        vel: Vec2::new(100.0, 0.0),
        kind: EntityKind::Door,
    });
    world.entities.push(Entity {
        update_period: 60,  // 1Hz
        pos: Vec2::new(0.0, 30.0),
        vel: Vec2::new(100.0, 0.0),
        kind: EntityKind::Decoration,
    });

    println!("初始位置:");
    for (i, e) in world.entities.iter().enumerate() {
        println!("  Entity {}: pos={:?}, period={}({:.1}Hz)",
                 i, e.pos, e.update_period, 60.0 / e.update_period as f32);
    }

    // 模拟 1 秒(60 帧)
    let dt = 1.0 / 60.0;
    for _ in 0..60 {
        world.update(dt);
    }

    println!("\n1 秒后位置(所有应该移动 100 像素):");
    for (i, e) in world.entities.iter().enumerate() {
        println!("  Entity {}: pos.x = {:.2}(预期 100)",
                 i, e.pos.x);
    }

    // 性能对比
    println!("\n--- 性能对比 ---");
    let mut update_count = 0u32;
    let mut frame_counter = 0u32;
    for _ in 0..60 {
        frame_counter = frame_counter.wrapping_add(1);
        for e in &world.entities {
            let period = e.update_period.max(1);
            if frame_counter % period == 0 {
                update_count += 1;
            }
        }
    }
    println!("频率分层:1 秒内总 update 次数 = {}", update_count);
    println!("不分层:1 秒内总 update 次数 = {}(4 entity × 60 帧)",
             4 * 60);
    println!("节省:{}", 4 * 60 - update_count);
}
```

### Troubleshooting

**问题 1**:低频 entity 速度比高频慢

原因:没做 dt 补偿。

修复:`effective_dt = dt * update_period as f32`。

**问题 2**:update_period = 0 导致除零

原因:用户错误数据。

修复:`let period = e.update_period.max(1);` 防护。

**问题 3**:frame_counter 溢出 panic

原因:debug 模式整数溢出 panic。

修复:用 `wrapping_add(1)` 而不是 `+= 1`。

**问题 4**:某些 entity 在第一帧不 update

原因:frame_counter = 0 时,0 % N == 0 任何 N,所有 entity 都 update。但 frame_counter = 1 时,只有 period=1 的 update。

修复:从 1 开始计数,或者在 update 内部判断 `if counter % period == 0` 不依赖起始值。
