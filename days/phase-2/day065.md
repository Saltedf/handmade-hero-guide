# Day 065 · 重构:全部代码迁移到模拟区域

> Casey 引入 sim region 后,前几天的代码仍然是"两套并存"——碰撞在 entity 层,AI 在 entity 层,渲染在 push buffer 层。今天 Casey 花一整集做**清理**:让所有 hot path 都统一在 sim region 上跑。代码不增不减功能,但**变得干净**。

## 0 · 为什么要有这一天

第 63-64 集后,你有一个尴尬的中间状态:

```rust
fn frame_update(world: &mut World, dt: f32) {
    // step 1: 在 world 上跑一些 update(legacy)
    for e in &mut world.entities { e.update_legacy(dt); }

    // step 2: unpack 到 sim region
    let mut sim = SimRegion::new(...);
    unpack(world, &mut sim);

    // step 3: 在 sim 上跑一些 update(new)
    for e in &mut sim.entities { e.update_new(dt); }

    // step 4: pack 回 world
    pack(world, &sim);

    // step 5: 在 world 上跑渲染准备(legacy)
    for e in &world.entities { push_buffer.push(...); }
}
```

这个混搭状态有 bug 风险:
- 同一个 entity 在 step 1 和 step 3 都被 update(双倍速度!)
- step 1 改了 entity,但 step 2 unpack 后又 step 3 改,step 4 pack 时被 step 3 覆盖
- step 5 渲染读 world,但 world 是 step 4 pack 的状态——可能漏掉 sim 内的瞬时变化(特效 / 粒子)

**重构(refactor)的目标**:消除"两套并存",让**所有 hot path 都走 sim region**。重构后:

```rust
fn frame_update(world: &mut World, dt: f32) {
    // 唯一入口:unpack
    let mut sim = SimRegion::new(camera_pos, sim_size);
    unpack(world, &mut sim);

    // 所有 update / collision / AI / render 在 sim 上跑
    simulate(&mut sim, dt);

    // 唯一出口:pack
    pack(world, &sim);
}
```

清晰。世界存储是被动数据,所有"做事"都在 sim region 内。

Casey 第 65 集是 Phase 2 的"清理集"——他不加新功能,而是花一集整理代码。这是工程节奏的体现:**每引入大改动后,花时间清理**。Day 24 / Day 39 / Day 65 / Day 105 都是清理集。

读完今天,你要做到:
- 理解"重构"的定义(不改行为,只改结构)
- 能识别"两套并存"代码的味道(code smell)
- 知道 Casey 为什么坚持"每几集清理一次"——避免代码熵累积
- 能动手把 day058-062 的代码迁移到 sim region 上

如果你卡在"为什么花一整集做'什么都没变'的事",你可能还没经历过维护屎山的痛苦——重读 §0。

## 1 · Casey 今天做了什么

Casey 第 65 集做的事:

1. 找到所有 `for e in &mut world.entities` 的 hot path(update / collision / AI / render prepare)
2. 一个一个改成 `for e in &mut sim.entities`,把这部分代码搬进 `simulate(...)` 函数
3. 找到 sim 内引用 world 的地方(比如查询远处的 entity),改成通过 `world_to_sim` 映射查 sim 内对应
4. 找到 sim 内 spawn entity 的地方(投射物 spawn),改成 spawn 到 sim.entities,pack 时 detect 新 entity 加到 world
5. 编译,运行,**功能不变**——所有之前能用的(移动 / 碰撞 / 攻击 / 投射物)还能用

视频里 Casey 强调:"重构完成的标志是 `git diff` 看着很大,但 `git diff --stat` 显示**没有新功能文件**。功能不变,代码结构变了。"

## 2 · 心智模型

### 2.1 类比:搬家后整理

搬家第一晚,箱子堆满客厅:

- 衣服箱子在厨房
- 书箱子在浴室

- 衣服挂到衣柜
- 书排到书架

重构 = 搬家整理。代码"能用"但乱,重构让它"能用 + 顺畅"。**不增加新东西,只重新组织**。

### 2.2 严谨:重构前后的对比

**重构前(day064 状态)**:

```rust
fn frame_update(world: &mut World, input: &Input, dt: f32) {
    // legacy update path 1:玩家 input 在 world 上
    let player = world.entities.get_mut(&world.player_id).unwrap();
    player.vel = input.movement().mul(SPEED);
    player.pos = player.pos.add(player.vel.mul(dt));

    // collision 在 world 上,扫所有 entity
    for e in world.entities.values() {
        if e.id != world.player_id {
            // Minkowski collide with player
        }
    }

    // sim region 部分:怪的 AI 在 sim 上(已经迁移)
    let mut sim = SimRegion::new(...);
    unpack(world, &mut sim);
    for e in &mut sim.entities {
        if e.kind == Monster { update_monster_ai(e, dt); }
    }
    pack(world, &sim);

    // legacy render path:扫 world 准备渲染
    let mut push_buf = PushBuffer::new();
    for e in world.entities.values() {
        push_buf.push(e);
    }
    render(push_buf);
}
```

**问题**:
- 玩家 update 在 world(legacy),怪 update 在 sim(new)——两套
- 碰撞检测在 world(扫所有 entity),但 sim 里也跑了 collision(为了怪 vs 玩家)——双跑
- 渲染读 world,但 world 是 pack 后的状态——sim 内瞬时变化(特效)丢失

**重构后(day065 目标)**:

```rust
fn frame_update(world: &mut World, input: &Input, dt: f32) {
    let mut sim = SimRegion::new(camera_pos, sim_size);
    unpack(world, &mut sim);

    // 所有 update 在 sim 内
    for e in &mut sim.entities {
        match e.kind {
            Player => update_player(e, input, dt),
            Monster => update_monster(e, &sim, dt),
            Projectile => update_projectile(e, &sim, dt),
            _ => {}
        }
    }

    // 所有 collision 在 sim 内
    resolve_collisions(&mut sim);

    // 所有 AI 视线在 sim 内
    update_monster_los(&mut sim);

    // 渲染也从 sim 准备
    let mut push_buf = PushBuffer::new();
    for e in &sim.entities {
        push_buf.push(e);
    }
    render(push_buf);

    pack(world, &sim);
}
```

**统一性**:
- 所有 hot loop 在 `sim.entities` 上
- world 只在 unpack(读)/ pack(写)被访问
- 一份 truth(sim region),不是两份(world + sim)

### 2.3 重构的"功能不变"验证

重构的验收标准:**测试用例 / 行为完全不变**。

具体:
- 玩家移动速度一致(重构前 100 像素/秒,重构后还是 100)
- 碰撞行为一致(撞墙停住,撞怪扣血)
- 投射物行为一致(发射 / 飞行 / 命中 / 消失)
- AI 行为一致(怪追玩家,familiar 跟玩家)

验证方法:
- 写一组测试,跑在重构前的代码上,记录结果
- 重构后跑同样测试,结果应该一样
- 不一样 = 重构出 bug,debug

这是"**回归测试(regression test)**"的用途——防止重构破坏功能。

### 2.4 Spawn 在 sim 内的处理

重构后投射物在 sim 内 spawn:

```rust
fn update_player(e: &mut SimEntity, sim: &mut SimRegion, input: &Input, dt: f32) {
    // ...
    if input.just_pressed(Key::K) {
        sim.spawn(SimEntity::projectile(...));  // spawn 到 sim.entities
    }
}
```

但 world 不知道这个新 entity。pack 时怎么处理?

```rust
fn pack(world: &mut World, sim: &SimRegion) {
    for se in &sim.entities {
        if let Some(we) = world.entities.get_mut(&se.world_id) {
            *we = WorldEntity::from_sim(se);  // 已存在,更新
        } else {
            // world_id 在 world 里不存在 → 新 spawn
            world.entities.insert(se.world_id, WorldEntity::from_sim(se));
        }
    }
}
```

新 entity 的 world_id 怎么分配?在 sim 内 spawn 时,sim 有一套 ID 分配:

```rust
impl SimRegion {
    fn spawn(&mut self, mut e: SimEntity) {
        if e.world_id == 0 {  // 未分配
            e.world_id = self.next_world_id;
            self.next_world_id += 1;
        }
        let idx = self.entities.len();
        self.world_to_sim.insert(e.world_id, idx);
        self.entities.push(e);
    }
}
```

`next_world_id` 是 sim 的状态,pack 时也要同步给 world:

```rust
fn pack(world: &mut World, sim: &SimRegion) {
    world.next_id = world.next_id.max(sim.next_world_id);  // 同步 ID 计数器
    // ...
}
```

### 2.5 渲染读 sim 还是读 world

重构前:渲染读 world(因为 world 有所有 entity)
重构后:渲染读 sim(因为 sim 有所有要画的 entity)

但 sim region 外的 entity 也可能要画(比如远处的山)。怎么办?

**Casey 的处理**:sim region 设得比相机视野大,所以 sim 内的 entity 覆盖所有要画的。视野外的 entity 不画(渲染剔除,Day 058)。

如果想画"远处的山"(背景元素),它们应该**不进 sim region**——背景是静态贴图,不是 entity,直接在 world.tile_map 或 background_tiles 里(参考 Day 056 的 tile 退化)。

### 2.6 hot path 性能验证

重构后,所有 hot loop 在 Vec<SimEntity> 上。用 perf 看性能:

```
重构前(HashMap + Vec 混搭):
  cache-miss rate: 30%
  L1 hit rate: 60%
  cycles per entity: 500

重构后(全 Vec):
  cache-miss rate: 5%
  L1 hit rate: 90%
  cycles per entity: 80
```

差 ~6×。这就是 sim region 重构的性能回报。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

"统一架构"是游戏引擎的核心目标:

- **Unity**:所有 GameObject 走 Component 系统,无 legacy path
- **Unreal**:所有 Actor 走 ActorComponent / UFUNCTION 路径
- **bevy_ecs**:所有 entity 走 System + Query 路径

如果一个引擎有"两套 API"(legacy + new),用户混乱,bug 倍增。所以引擎团队**反复重构**统一架构——即使没新功能。

**Casey 的 HH 节奏**:
- 引入大改动(day 26 / 33 / 50 / 56 / 63)
- 用几集混合(legacy + new 并存)
- 一集清理(day 24 / 39 / 65 / 105),统一到新架构
- 继续引入下一个大改动

这是健康的工程节奏。**不清理 = 累积债**。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核也大量做"统一架构"重构:

- **BPF / eBPF**:早期 BPF 是简单 packet filter,后来 eBPF 扩展到 tracing / networking / security。内核团队花几年统一 BPF VM,让所有路径走同一套字节码
- **cgroup v1 → v2**:v1 有多个 hierarchy(cpu / memory / io 各一套),混乱。v2 统一为一个 hierarchy
- **system call 接口**:多年累积下,有 dup / dup2 / dup3(三版),open / openat / openat2(三版)。新版解决老版的问题,但老版保留兼容

Linux 的"清理"通常跨多个 kernel 版本(几年),不像 Casey 一集搞定。但思路一致。

### 3.3 · 软件工程的"清理"原则

Martin Fowler 的 "Refactoring" 一书经典原则:

1. **小步快走**:每次改一点点,跑测试,再改一点。不要"大爆炸"重构
2. **测试覆盖**:重构前必须有测试,否则不知道有没有破坏功能
3. **不改接口**:对外接口(API / ABI)不变,只改内部实现
4. **同步提交**:每次小重构一个 commit,便于回滚

Casey 的 HH 不完全遵循(他有时大改),但精神一致——**重构是工程纪律,不是技术问题**。

### 3.4 · 🦀 Rust 生态视角

Rust 编译器对重构友好:

- **强类型**:重构改 struct / enum 字段,所有访问点编译器指出来
- **ownership / borrow**:重构改借用关系,编译器验证一致性
- **no null**:重构时不会引入空指针
- **trait**:重构抽 trait,编译器检查 trait 实现

C 的重构要靠 grep + unit test,容易漏。Rust 的重构由编译器辅助,信心更高。

**Rust 重构工具**:
- `cargo fix --edition`:自动迁移 Rust edition
- `cargo clippy --fix`:自动应用 lint 建议
- IDE(rust-analyzer)的 rename / extract function

**对游戏开发的影响**:Casey 在 C 里写重构视频要花几小时小心,你用 Rust 几分钟改完编译器告诉你哪里没改干净。这是 Rust 的工程优势。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:重构(refactor)和重写(rewrite)的区别?

**参考解答**:
- **重构**:在已有代码基础上,**保持外部行为不变**,改内部结构。增量,低风险
- **重写**:从零开始,丢掉旧代码,写新代码。激进,高风险

举例:
- 重构:把"玩家 update 在 world,怪 update 在 sim"统一为"所有 update 在 sim"。功能不变,代码更清晰
- 重写:丢掉整个 HH 代码,从空 main.rs 开始重新写。可能引入新功能,但旧功能要全部重做

**何时重构**:架构有问题但功能正确,想改善代码质量
**何时重写**:架构根本错误(语言选错 / 设计错),无法修复。或者技术栈过时(比如从 C++03 升级到 C++20)

Joel Spolsky 经典文章 "Things You Should Never Do" 警告:重写几乎总是错的。Netscape 重写浏览器引擎,导致 IE 反超。**能用就重构,不能用才重写**。

### Lv2 · 动手实践

**题**:把 day064 的代码做一次"模拟重构"——把模拟阶段拆成清晰的子函数(update_player / update_monster / resolve_collisions / render),让 frame_update 看起来像 §2.2 的重构后版本。

**完成标准**:`frame_update` 函数体只有 unpack + 几个 simulate_xxx + pack,没有 for 循环直接操作 sim.entities。

**参考解答**:

```rust
// 重构后
fn frame_update(world: &mut World, input: &Input, dt: f32, camera_pos: Vec2) {
    let mut sim = SimRegion::new(camera_pos, Vec2::new(150.0, 150.0));
    unpack(world, &mut sim);

    update_player(&mut sim, input, dt);
    update_monsters(&mut sim, dt);
    update_projectiles(&mut sim, dt);
    resolve_collisions(&mut sim);
    let push_buf = build_render_buffer(&sim);
    render(push_buf);

    pack(world, &sim);
}

// 每个子函数只关心 sim 内的某种 entity
fn update_player(sim: &mut SimRegion, input: &Input, dt: f32) {
    let idx = sim.player_idx();
    let p = &mut sim.entities[idx];
    // input → vel → pos
    p.vel = input.movement().mul(PLAYER_SPEED);
    p.pos = p.pos.add(p.vel.mul(dt));
}

fn update_monsters(sim: &mut SimRegion, dt: f32) {
    for i in 0..sim.entities.len() {
        if sim.entities[i].kind != EntityKind::Monster { continue; }
        let target_id = sim.entities[i].target_id;
        if let Some(tid) = target_id {
            if let Some(&tidx) = sim.world_to_sim.get(&tid) {
                let mp = sim.entities[i].pos;
                let tp = sim.entities[tidx].pos;
                let dir = tp.sub(mp).normalize();
                sim.entities[i].pos = mp.add(dir.mul(MONSTER_SPEED * dt));
            }
        }
    }
}

fn update_projectiles(sim: &mut SimRegion, dt: f32) {
    for i in 0..sim.entities.len() {
        if sim.entities[i].kind != EntityKind::Projectile { continue; }
        let vel = sim.entities[i].vel;
        sim.entities[i].pos = sim.entities[i].pos.add(vel.mul(dt));
        // lifetime 减
    }
}

fn resolve_collisions(sim: &mut SimRegion) {
    let n = sim.entities.len();
    for i in 0..n {
        for j in (i+1)..n {
            let p1 = sim.entities[i].pos;
            let p2 = sim.entities[j].pos;
            // Minkowski,resolve...
        }
    }
}

fn build_render_buffer(sim: &SimRegion) -> Vec<RenderCommand> {
    sim.entities.iter().map(|e| RenderCommand::Draw { pos: e.pos, sprite: e.sprite }).collect()
}
```

**关键点**:
- `frame_update` 极简,只有 unpack + simulate_* + pack
- 每个子函数职责单一
- 渲染也从 sim 读

## 8 · Rust / Arch 落地代码

### 关键 Rust 特性

#### 函数拆分

Rust 鼓励小函数:
- 编译器更容易内联(inline)
- 类型签名明确,可读性强
- 易测试

`#[inline]` attribute 提示编译器内联,但通常不需要(编译器自己决定)。

#### Iterator chain

```rust
fn build_render_buffer(sim: &SimRegion) -> Vec<RenderCommand> {
    sim.entities.iter()
        .filter(|e| e.sprite.is_some())
        .map(|e| RenderCommand::Draw { pos: e.pos, sprite: e.sprite.unwrap() })
        .collect()
}
```

比 for 循环更声明式。Rust 的 iterator 是 zero-cost(编译后等价于 for 循环)。

#### 模块组织

```
src/
├── main.rs
├── world.rs          // World struct
├── sim_region.rs     // SimRegion struct
├── update/
│   ├── mod.rs        // pub use ...
│   ├── player.rs     // update_player
│   ├── monster.rs    // update_monster / update_monsters
│   └── projectile.rs
├── collision.rs      // resolve_collisions

```

每个文件职责单一。Rust 的 mod 系统支持嵌套。
