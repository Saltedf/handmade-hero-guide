# Day 045 · 几何搜索 vs 时间搜索

> Day 029 你做了"撞墙就停"的碰撞检测。但你的玩家加速到 3000 像素/秒时,一帧位移 50 像素——直接穿过 32 像素厚的墙,屏幕上看起来像瞬移。Casey 在 Day 045 解决这个"高速穿墙"问题:把一帧的位移拆成多个小步,每步检查碰撞,即"temporal search"(时间搜索)。

## 0 · 为什么要有这一天

回到 Day 029 的碰撞代码:

```rust
let new_x = player.x + vel.x * dt;
if can_move_to(map, new_x, player.y, SIZE) {
    player.x = new_x;
}
```

这段代码假设:**玩家一帧走的距离,比墙薄**。如果玩家速度 200 像素/秒,dt = 1/60 秒,一帧走 3.3 像素——比墙薄(32 像素),没问题。

但游戏不是恒定速度的:

- **平台跳跃游戏**(Mario):玩家高速冲刺,瞬时速度可能 600-1000 像素/秒
- **赛车游戏**:车速 2000+ 像素/秒
- **子弹 / 投射物**:3000-5000 像素/秒常见
- **lag spike**(网络卡顿):某一帧 dt 突然变成 0.1 秒(正常 0.0167 秒的 6 倍),位移瞬间巨大

任何一个场景下,玩家 / 子弹可能"起点和终点都不在墙内,但中间穿过墙"。这就是 **tunneling**(隧道效应)——经典 bug。

**Tunneling 的真实案例**:

- **Call of Duty 早期**:玩家快速跑过门,会被门夹住一半(碰撞检测没追上)
- **Minecraft**:玩家挖地道快速移动,可能穿墙进入未加载区域
- **Dark Souls**:玩家奔跑撞门,有概率穿过去(Boss 跳过)

这些 bug 都是 discrete collision(终点碰撞)的固有缺陷。**Temporal search**(时间搜索)是解决方案之一:把一帧的位移拆成多个小时间步,每步检查碰撞,保证"每步移动 < 墙厚度"。

Casey 在这集做了**对比实验**:先用 Day 029 的 discrete 版本,看到 tunneling bug;然后改成 temporal search,bug 消失。这个对比让你看到**算法选择对正确性的影响**——同一个功能,不同实现可能有截然不同的边界行为。

心理锚点:做完今天,你应该能解释"为什么 60 FPS 游戏也可能穿墙",知道 temporal search 怎么解决这个问题,以及它的代价(多次 can_move_to 调用)。这是判断"你懂游戏物理"还是"你只会调 API"的标志。

## 2 · 心智模型

### 费曼类比:高速激光 vs 慢速激光

想象你用激光照射墙壁,问"光会不会被墙挡住"。

**慢速激光**(球的速度小):你慢慢移动激光,墙的阻挡效果直接可见——激光在墙边停住。

**高速激光**(球的速度大):你瞬间把激光从 A 点移到 B 点(扫过墙的位置),怎么知道中间有没有撞墙?

两种方法:

**A. 几何法**(geometric):数学上,激光是一条线段 A→B,墙是一个矩形。算"线段和矩形相交吗",一次计算,精确。

**B. 时间法**(temporal):你把 A→B 拆成 N 个小段,每段检查"这一小段的终点在墙内吗"。如果段足够小(每段 < 墙厚度),总有一个段会"卡住墙"——这时就检测到了。

**几何法**是精确数学,**时间法**是工程近似。Casey 选时间法因为简单(复用 can_move_to),代价是精度(段越细越精确,但计算越多)。

### 严谨定义:tunneling 的数学

**Tunneling 的数学定义**:

- 玩家在帧 N 的位置:`P_start`
- 玩家在帧 N+1 的位置:`P_end = P_start + v * dt`
- 墙的 AABB:`W`

**Discrete collision**(检查终点):

- 如果 `P_end ∈ W`,检测到碰撞(玩家撞墙)
- 如果 `P_end ∉ W`,认为没碰撞

**Tunneling 场景**:`P_start ∉ W`,`P_end ∉ W`,但线段 `P_start → P_end` 穿过 W。

```
P_start ●─────────────────● P_end
                │
              ┌─┴─┐
              │ W │  (墙)
              └───┘
```

起点和终点都不在墙内,discrete collision 误判"无碰撞"。但实际上线段穿过了墙。

### 几何解法:线段 vs AABB 相交

数学公式直接算"线段 AB 是否和矩形 W 相交"。算法:

1. 算线段参数方程:`L(t) = A + t*(B - A)`,t ∈ [0, 1]
2. 算线段和矩形 4 条边的相交(Day 048 会详讲)
3. 任何一个相交 → 碰撞

这种方法**一步到位**,精确。但代码复杂,需要写线段相交函数。Casey 在 Day 048 才做这个,Day 045 选了更简单的方案。

### 时间解法:temporal search

**核心思想**:把总位移拆成多个小步,每步用已有 discrete collision 检查。

```rust
fn move_with_collision(player: &mut Player, map: &TileMap, dt: f32) {
    let total_dx = player.vel.x * dt;
    let total_dy = player.vel.y * dt;

    // 关键:max_step 决定步长上限
    let max_step = TILE_SIZE as f32 * 0.5;  // 半个 tile,16 像素

    // 算需要多少步
    let max_dist = total_dx.abs().max(total_dy.abs());
    let steps = ((max_dist / max_step).ceil() as i32).max(1);

    let step_dx = total_dx / steps as f32;
    let step_dy = total_dy / steps as f32;

    for _ in 0..steps {
        // 每步用 Day 029 的 discrete + 分轴
        let new_x = player.pos.x + step_dx;
        if can_move_to(map, new_x, player.pos.y, PLAYER_SIZE) {
            player.pos.x = new_x;
        }
        let new_y = player.pos.y + step_dy;
        if can_move_to(map, player.pos.x, new_y, PLAYER_SIZE) {
            player.pos.y = new_y;
        }
    }
}
```

**为什么 max_step = TILE_SIZE / 2?** 因为墙是 1 个 tile 厚(TILE_SIZE)。如果一步 ≤ 半个 tile,玩家不可能跨过整个墙——总会在墙的"一半位置"被检测到。

**严格说**:如果墙只有 1 个 tile 厚,玩家从一侧出发,一步 < tile 厚度,要么停在墙外,要么停在墙内(被检测到)。不可能"从一侧跳到另一侧"。

**数字例子**:玩家速度 3000 像素/秒,dt = 1/60 秒,一帧位移 50 像素。

- max_step = 32 / 2 = 16 像素
- steps = ceil(50 / 16) = 4 步
- 每步位移 12.5 像素 < 32(墙厚)
- 玩家在第 2 或 3 步碰到墙,停下来

**对比 discrete**:

- 直接检查终点:终点是 P_start + 50 像素(墙的另一侧),不在墙内,误判无碰撞
- temporal search:4 步每步 12.5 像素,某步终点在墙内,检测到

### 选 max_step 的技巧

**max_step 太大**(比如 TILE_SIZE * 2):步长 > 墙厚度,可能 tunneling。**错误**。

**max_step = TILE_SIZE**:刚好等于墙厚度。如果玩家从 tile 边缘出发,一步正好走到下一个 tile 边缘——既不在墙内也不在墙外。**边界情况,可能漏检**。

**max_step = TILE_SIZE / 2**:步长 ≤ 半个 tile。最坏情况,玩家在 tile 中间,一步最多到 tile 边缘的另一半——肯定在墙内被检测。**安全**。

**max_step 太小**(比如 1 像素):每步 1 像素,3000 像素/秒需要 3000 步——CPU 爆炸。**过保守**。

**Casey 的选择**:`TILE_SIZE / 2`(16 像素)。安全 + 性能平衡。

### 与 Day 029 分轴碰撞的整合

Day 029 的 wall sliding(分轴碰撞)需要保留——它在每一步内部生效。temporal search 只是把"一步"切成多个小步,每步内部仍然是分轴。

```rust
// 完整版本(整合 Day 029 + Day 045)
fn move_player(player: &mut Player, map: &TileMap, dt: f32) {
    let total_dx = player.vel.x * dt;
    let total_dy = player.vel.y * dt;
    let max_step = TILE_SIZE as f32 * 0.5;
    let max_dist = total_dx.abs().max(total_dy.abs());
    let steps = ((max_dist / max_step).ceil() as i32).max(1);
    let step_dx = total_dx / steps as f32;
    let step_dy = total_dy / steps as f32;

    for _ in 0..steps {
        // 分轴:先 x 后 y(墙滑行)
        let nx = player.pos.x + step_dx;
        if can_move_to(map, nx, player.pos.y, PLAYER_SIZE) {
            player.pos.x = nx;
        } else {
            // x 撞墙,清 vx(防止持续推墙)
            player.vel.x = 0.0;
        }
        let ny = player.pos.y + step_dy;
        if can_move_to(map, player.pos.x, ny, PLAYER_SIZE) {
            player.pos.y = ny;
        } else {
            player.vel.y = 0.0;
        }
    }
}
```

每一步内部分轴,整个 for 循环遍历多个时间步。这就是 Casey 在 Day 045 的最终实现。

### 三种方案的对比

| 方案 | 公式 | 优点 | 缺点 | 何时用 |
|---|---|---|---|---|
| Discrete collision(Day 029) | 检查终点 | 最快 | tunneling | 慢速物体 |
| Temporal Search(Day 045) | 拆步 + discrete | 简单,复用 | 多次调用 | 中速物体(Casey 用) |
| Swept AABB(Geometric) | 线段 vs AABB | 精确 | 公式复杂 | 高速物体 / 物理引擎 |
| Sub-stepping | 固定拆步 | 通用 | 调参困难 | 物理引擎(Box2D) |

**Casey 选 Temporal Search** 因为最简单。后面 Day 048(线段相交)开始铺路 swept AABB,但 HH 全程不切换——temporal search 够用。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对 tunneling 的解决方案:

**1. Sub-stepping**(子步进):物理引擎(Box2D、PhysX)用固定 dt,但每帧跑多个物理子步。比如游戏 60 FPS,物理 240 Hz(每帧 4 个物理步)。这保证每步位移小。

**2. Continuous Collision Detection**(CCD,连续碰撞检测):物理引擎的高级功能。对每个高速物体,算"从 t=0 到 t=dt 的轨迹",直接和障碍物做几何相交。Bullet、PhysX 都支持。

**3. Raycasting**(射线投射):对子弹这种极高速物体,直接用射线(Day 422+)。子弹本质是"瞬间从 A 到 B 的射线",不做物理模拟。

**4. Velocity capping**(限速):简单粗暴——把最大速度限制到 < TILE_SIZE / dt,这样不会 tunneling。Casey 的 HH 用了限速 + temporal search 双保险。

#### 实战坑点

**坑 1:temporal search + 分轴的顺序**。每步内部分轴(x 先 y 后),不能颠倒,否则墙滑行失效。

**坑 2:撞墙后清速度**。如果不清 vx,玩家持续按右键,vel.x 不断累加,即使 pos.x 没动。下一帧 vel.x 巨大,temporal search 步数爆炸。所以撞墙时 `vel.x = 0`(参考代码里的 else 分支)。

**坑 3:对角线 tunneling**。如果只检查总位移的 max(|dx|, |dy|),玩家可能斜着穿过墙的角落。修复:把 dx 和 dy 分别算 steps,取较大值(代码里的 `max_dist` 已经这么做)。

**坑 4:dt 突变**。如果某帧 dt 突然变大(系统卡顿),steps 巨大,性能问题。修复:钳制 dt:`let dt = dt.min(0.05);`(最多 50ms 一帧)。

### 3.2 · 🎨 图形学视角

图形学里类似问题:**抗锯齿**(anti-aliasing)。像素是离散的,三角形是连续的——三角形边缘可能"穿过"像素中心(被采样)或不穿过(不被采样)。导致锯齿。

**MSAA**(多重采样抗锯齿):每个像素采多次(4x MSAA = 4 个子采样点),平均得到颜色。本质就是 temporal search——把一个像素拆成多个子像素,每个子像素独立判断。

**TAA**(时间抗锯齿):跨帧累积,把"上一帧 + 这一帧"的子像素结果合并。这是 temporal search 的"跨时间"版本。

**Ray tracing** 的反走样:每个像素发射多条射线,平均颜色。

**统一的思想**:连续信号在离散网格上采样,会有走样(aliasing)。解决:多次采样(空间 / 时间)取平均。游戏物理的 tunneling 和图形学的锯齿是同一个数学问题(连续 vs 离散),解决方案也是同一族思想。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里类似 temporal search 的概念:**Timer wheel + high-resolution timers**。

内核定时器本质是"在某个时间点触发回调"。如果定时器精度低(比如 10ms 一次 tick),短时定时器(1ms)无法精确触发——内核等到下一个 tick 才检查。这是 discrete 时间的问题。

**High-resolution timers**(hrtimer):Linux 2.6.16 引入。硬件提供纳秒级定时器,内核不再依赖 tick,直接调度精确时间。这相当于把 discrete 时间(粗粒度)升级为 temporal search(细粒度)。

```bash
# 看 hrtimer 是否启用
$ zcat /proc/config.gz | grep CONFIG_HIGH_RES_TIMERS
CONFIG_HIGH_RES_TIMERS=y

# 看当前 tickless 配置
$ zcat /proc/config.gz | grep NO_HZ
CONFIG_NO_HZ=y
CONFIG_NO_HZ_IDLE=y
```

**信号传递的 temporal 问题**:信号可能在内核态到达,但用户态才处理。内核用 `TIF_SIGPENDING` 标志位记录"有待处理信号",在系统调用返回时检查。这是 coarse 粒度(每次系统调用才检查),如果系统调用长(读大文件),信号延迟。Linux 提供 `O_NONBLOCK` 和 `EINTR` 缓解。

### 3.4 · 🦀 Rust 生态视角

#### Rust 实现 temporal search 的注意事项

**所有权**:can_move_to 接收 `&TileMap`(只读借用)。temporal search 调用多次,每次都借用,不冲突。

```rust
fn move_player(player: &mut Player, map: &TileMap, dt: f32) {
    //                                ^ 只读借用,可以反复调用
    for _ in 0..steps {
        if can_move_to(map, ...) { ... }  // OK
    }
}
```

## 4 · 认知地图

### 4.1 上级

- **离散 vs 连续**(discrete vs continuous)—— 数学和计算的根本张力
- **走样与抗走样**(aliasing & anti-aliasing)—— 采样理论(Nyquist)
- **碰撞检测算法家族**(collision detection algorithms)—— discrete / continuous / hybrid
- **微分方程的数值积分** —— Day 043 Euler 积分的精度问题

### 4.2 同级(并行方案对比)

| 方案 | 复杂度 | 精度 | 性能 | 何时用 | 本项目选 |
|---|---|---|---|---|---|
| Discrete | O(1) | 低(tunneling) | 最快 | 慢速物体 | Day 029 |
| Temporal search | O(N),N=位移/步长 | 中(步长决定) | 中 | 中速,Casey 选 | ✅ Day 045 |
| Swept AABB | O(1) | 高(精确) | 中(公式复杂) | 高速,物理引擎 | Day 048 铺路 |
| Sub-stepping | O(N),N 固定 | 中 | 中 | 物理引擎标准 | Box2D |
| Raycasting | O(1) per ray | 高 | 快 | 子弹 / 射线武器 | Day 422+ |

详细说明:

- **Discrete**:1 次 can_move_to 调用。最快,但 tunneling。
- **Temporal**:N 次 can_move_to,N = 总位移 / 步长。Casey 选。
- **Swept**:1 次"线段 vs AABB"几何计算,精确但代码复杂。Day 048 学线段相交后会写。
- **Sub-stepping**:物理引擎用固定小 dt(比如 1/240 秒),每帧 4 步。比 temporal search 更系统化,但需要分离物理步和渲染步。

## 5 · 对照与变奏

### 不同游戏类型的碰撞精度需求

| 游戏类型 | 典型速度 | 碰撞精度 | 方案 |
|---|---|---|---|
| 慢节奏 RPG(Pokemon) | 100 px/s | 低 | discrete |
| 平台跳跃(Mario) | 600 px/s | 中 | temporal search |
| 动作游戏(Celeste) | 800 px/s | 高(精确) | temporal + edge cases |
| 竞速游戏(赛车) | 2000+ px/s | 高 | swept / raycast |
| 射击游戏(子弹) | 3000+ px/s | 极高 | raycast |
| 物理沙盒(Minecraft) | 不定 | 中 | sub-stepping |

Casey 的 HH 是平台 / 动作游戏,temporal search 够用。

### CPU 物理 vs GPU 物理

**CPU 物理引擎**(Box2D、Chipmunk、rapier):跑在 CPU,适合复杂逻辑(关节、约束)。每帧物理步 1-10 ms,10-1000 个物体。

**GPU 物理引擎**(PhysX、FleX):跑在 GPU,适合大规模粒子(几万个)。CUDA / Compute Shader 实现。

游戏开发趋势:CPU 物理用于"少量精确",GPU 物理用于"大量近似"。

### 2D 碰撞 vs 3D 碰撞

| | 2D | 3D |
|---|---|---|
| 基本形状 | AABB(矩形)、Circle、Polygon | AABB(立方体)、Sphere、OBB、Mesh |
| 碰撞算法 | Minkowski、SAT、GJK | 同 2D + 维度增加 |
| 高速问题 | Tunneling | 同 |
| 解决方案 | Temporal / Swept / Raycast | 同 |

3D 碰撞更复杂(三角形 mesh vs mesh),但 temporal search 思想一样适用。Day 50 的 Minkowski 推广到 3D 也能用。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:temporal search 的 max_step 应该是多少?如果你设 max_step = TILE_SIZE(等于墙厚度),会怎样?

**参考解答**:

**正确**:`max_step = TILE_SIZE / 2`(半个 tile)。

**max_step = TILE_SIZE 的问题**:玩家从 tile A 的左边缘出发,一步走 TILE_SIZE 像素,正好到 tile A 的右边缘 = tile B 的左边缘。如果 tile B 是墙,玩家"卡在墙的边缘上"——既不在墙内(discrete 检测通过)也不在墙外(实际位置在墙的边界)。

最坏情况:玩家从 tile A 中心出发,一步正好到 tile B 中心(墙)。但下一步又跳到 tile C——跳过整个墙!这就是 tunneling。

**max_step = TILE_SIZE / 2** 保证:玩家任何位置出发,一步最多走到下一个 tile 的一半,肯定在某个 tile 内部(被检测)。**安全**。

**直觉**:步长应该 < 最薄墙的厚度。如果墙都 1 tile 厚,步长 < tile 厚度。Casey 选半个 tile,留 2 倍裕量。

### Lv2 · 动手实践

**题**:在你的 HH 项目里实现 temporal search:

1. 复用 Day 029 的 `can_move_to` 和 Day 043 的 Player 结构
2. 实现 `move_player_with_collision(&mut player, &map, dt)`
3. 关键参数:`MAX_STEP = TILE_SIZE as f32 * 0.5`
4. **测试场景**:玩家速度 3000 px/s,墙在右侧 50 像素外。一帧 dt=1/60。
5. 验证:玩家应该停在墙边,而不是穿过去

完成标准:运行测试,玩家不穿墙。

**参考解答**:

```rust
use crate::math::Vec2;
use crate::tile_map::{TileMap, TileValue, TILE_SIZE};

const PLAYER_SIZE: f32 = 32.0;
const MAX_STEP_FACTOR: f32 = 0.5;  // 半个 tile

pub fn move_player_with_collision(
    player: &mut Player,
    map: &TileMap,
    dt: f32,
) {
    // 钳制 dt,防止 lag spike
    let dt = dt.min(0.05);

    let total_dx = player.vel.x * dt;
    let total_dy = player.vel.y * dt;

    let max_step = TILE_SIZE as f32 * MAX_STEP_FACTOR;
    let max_dist = total_dx.abs().max(total_dy.abs());
    let steps = ((max_dist / max_step).ceil() as i32).max(1);
    let step_dx = total_dx / steps as f32;
    let step_dy = total_dy / steps as f32;

    for _ in 0..steps {
        // 分轴:先 x 后 y(wall sliding)
        let new_x = player.pos.x + step_dx;
        if can_move_to(map, new_x, player.pos.y, PLAYER_SIZE) {
            player.pos.x = new_x;
        } else {
            // 撞墙,清速度防止持续推墙累积
            player.vel.x = 0.0;
        }

        let new_y = player.pos.y + step_dy;
        if can_move_to(map, player.pos.x, new_y, PLAYER_SIZE) {
            player.pos.y = new_y;
        } else {
            player.vel.y = 0.0;
        }
    }
}

fn can_move_to(map: &TileMap, x: f32, y: f32, size: f32) -> bool {
    let left = (x / TILE_SIZE as f32) as i32;
    let right = ((x + size) / TILE_SIZE as f32) as i32;
    let top = (y / TILE_SIZE as f32) as i32;
    let bottom = ((y + size) / TILE_SIZE as f32) as i32;

    for ty in top..=bottom {
        for tx in left..=right {
            if map.get(tx, ty) == TileValue::Wall {
                return false;
            }
        }
    }
    true
}
```

**测试**:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn make_test_map() -> TileMap {
        // 100x1 tile,前 5 tile 空,后面都是墙
        let mut map = TileMap::new(100, 1);
        for x in 0..5 {
            map.set(x, 0, TileValue::Floor);
        }
        for x in 5..100 {
            map.set(x, 0, TileValue::Wall);
        }
        map
    }

    #[test]
    fn test_no_tunneling() {
        let map = make_test_map();
        let mut player = Player {
            pos: Vec2::new(100.0, 0.0),  // 在第 3 tile
            vel: Vec2::new(3000.0, 0.0),  // 高速向右
        };

        // 一帧 dt=1/60,位移 = 50 像素
        // 玩家原本应该走到 x=150(第 5 tile,墙!)
        move_player_with_collision(&mut player, &map, 1.0 / 60.0);

        // 应该被墙挡住,停在 x ≈ 5*TILE_SIZE - PLAYER_SIZE
        let wall_left = 5.0 * TILE_SIZE as f32;
        let expected_max = wall_left - PLAYER_SIZE;
        assert!(player.pos.x <= expected_max + 0.001,
                "tunneling! player.x={} should <= {}",
                player.pos.x, expected_max);
    }

    #[test]
    fn test_slow_no_split() {
        let map = make_test_map();
        let mut player = Player {
            pos: Vec2::new(100.0, 0.0),
            vel: Vec2::new(50.0, 0.0),  // 慢速
        };

        move_player_with_collision(&mut player, &map, 1.0 / 60.0);
        // 慢速,一步到位
        let expected = 100.0 + 50.0 / 60.0;
        assert!((player.pos.x - expected).abs() < 0.5);
    }
}
```

**关键决策解释**:

- `dt.min(0.05)` 钳制 dt,防止系统卡顿时 dt 突然变大,steps 爆炸。
- 撞墙时 `vel = 0`,防止持续推墙累积速度。
- `expected_max + 0.001` 容忍浮点误差。

### Lv3 · 迁移设计

**题**:你在做**子弹系统**,子弹速度 5000 像素/秒。temporal search 需要多少步?

1. 算:dt = 1/60,位移 = 5000/60 ≈ 83 像素,steps = ceil(83/16) = 6 步
2. 1000 个子弹 × 6 步 = 6000 次 can_move_to/帧,够吗?
3. 设计一个**优化**:对子弹用 raycasting(线段 vs tile),一次精确计算,不走 temporal search

**提示**:

- raycast:从子弹起点发射射线,算第一个撞到的 tile
- 用 Bresenham 直线算法(画线算法)遍历 tile,或 DDA(Digital Differential Analyzer)
- 一次 raycast ≈ 10-20 次 tile 查询(直线长度 / tile 厚度)
- 比较两种方案的复杂度:temporal(6 步 × 4 tile 查询 = 24)vs raycast(20 查询)

为什么这个练习有价值?因为不同问题需要不同工具。temporal search 是通用方案,raycast 是高速专用方案。理解两者的 trade-off,你才能给具体场景选最优算法。

### Troubleshooting

**问题 1**:玩家低速也走不动,卡在原地

原因:你的 `steps = ((max_dist / max_step).ceil() as i32).max(1)`,即使低速也至少 1 步——但这步是 `step_dx = total_dx / 1 = total_dx`,应该正常移动。检查别的逻辑。

修复:调试 can_move_to,确认它在空地上返回 true。

**问题 2**:玩家高速还是穿墙

原因:max_step 设置太大(比如 TILE_SIZE * 2),或者 steps 计算用整数除法截断。

修复:max_step = TILE_SIZE as f32 * 0.5。用 `ceil()` 不是 `as i32` 直接截断。

**问题 3**:玩家撞墙后卡死,vel 一直是 0

原因:撞墙时 `vel.x = 0`,但下次按键时 `acc.x` 是 0(因为按右键时 acc.x 应该 > 0,但可能你清零的逻辑把 acc 也清了)。

修复:只清 vel 不清 acc。每帧 acc 从输入重新计算。

**问题 4**:性能很差,帧率掉到 30

原因:1000 个 entity 每个都 temporal search,每个 6 步,每步 can_move_to 遍历几个 tile = 6000 × 几个 = 几万次查询。

修复:

1. 用空间网格(Day 057)加速 can_move_to
2. 对低速 entity 跳过 temporal search(检查 vel 长度)
3. 限制 max_step 不要太小
