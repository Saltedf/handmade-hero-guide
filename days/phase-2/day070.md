### 关键设计决策(每个都有"为什么")

#### 决策 1:平台/游戏分离

为什么?让游戏代码不依赖任何特定平台 API。换平台(桌面 → Web → 手机)只改平台层,游戏层零改动。Day 026 引入,Day 029 完成。

#### 决策 2:cdylib 热重载

为什么?改游戏代码不用重启程序。开发体验从"改一行 → 编译 → 重启 → 走到对应场景"变成"改一行 → 编译 → 自动生效"。Day 026-029。

#### 决策 3:稀疏数组 + generation 索引

为什么?entity 经常创建销毁(火球、特效),用 Vec 会留洞,用 HashMap 慢。稀疏数组 O(1) 访问 + generation 防止 use-after-free。Day 051-058。

#### 决策 4:Minkowski 差碰撞

为什么?把"两 AABB 是否相交"转化为"点是否在 AABB 内",公式对称简单,O(1) 复杂度。Day 050。

#### 决策 5:Sim Region(局部模拟)

为什么?大世界里只有相机附近的 entity 需要更新(远处的不动)。sim_region 是"相机附近的矩形",只更新 region 内的 entity。CPU 消耗从 O(全部 entity)降到 O(可见 entity)。Day 061-065。

#### 决策 6:碰撞规则表(类型对 → 行为)

为什么?数据驱动设计。加新 entity 类型只改表,不改碰撞代码。Day 069。

#### 决策 7:Hash 表做世界存储

为什么?大世界没法全部装内存。用 hash 把 `(chunk_x, chunk_y)` 映射到 chunk 数组,只加载相机附近的 chunk。Day 055。

#### 决策 8:速度 clamp 防穿墙

为什么?离散碰撞检测在高速 entity 上失败(一帧穿墙)。clamp 把每帧位移限制在 tile 半宽内,从源头避免问题。Day 068。

**这些决策加起来,就是 Phase 2 的"设计哲学":**

1. **数据驱动** —— 碰撞规则、entity 类型、tile 数据,都是"表",不是"代码"
2. **分层 + 接口** —— 平台层和游戏层通过 GameMemory 解耦
3. **空间局部性** —— sim region 只算可见的,cache 友好
4. **简单优先** —— Euler 积分、Minkowski AABB、稀疏数组,都是"够用就行"
5. **可演化** —— 每个"简单"方案都留了升级路径(clamp → sub-stepping,sparse → ECS)

### 为什么 Casey 从软渲染开始?

Casey 在 Phase 3-4 用 CPU 软件光栅化,**不用 OpenGL**。Phase 5 才切 OpenGL。为什么?

1. **教学价值**:软渲染让你**理解每一个像素怎么来的**。GPU 是黑盒——你 `glDrawArrays` 看不到中间。CPU 软渲染你能 `printf` 每个像素。
2. **可调试**:CPU 代码能 gdb 单步。GPU shader 调试是另一门学问(renderdoc / printf hack)。
3. **架构清晰**:软渲染强迫你想清楚"渲染管线是什么"。Phase 5 切 GPU 时,你已经知道管线了,只是把每步搬到 shader。
4. **避免 API 战争**:OpenGL / Vulkan / DirectX / Metal 各有 API。学完软渲染,你能在任何 GPU API 上重写。
5. **后期能加 GPU 加速**:用 compute shader 加速软渲染,这是 Casey 在 Day 500+ 的实验方向。

**这是 HH 的核心教学哲学:先理解原理,再用工具**。

### 3.4 · Rust 生态视角

Phase 2 你用到的 Rust 特性:

- 所有权 + 借用(全程)
- lifetime(FFI 边界)
- `unsafe`(libloading、raw pointer)
- enum + match(状态机、规则表)

- Copy / Clone 语义(值类型)

## 5 · 对照与变奏

### 业界做法对比

**商业引擎架构**(Unity / Unreal)比 HH 复杂 100 倍,但**核心思想完全一样**:

| HH 概念 | Unity 对应 | Unreal 对应 |
|---|---|---|
| Entity | GameObject | Actor |
| Entity kind + components | GameObject + Components | Actor + Components |
| Collision rule table | Physics Material + Collision Matrix | Collision Profile |
| Sim region | Scene streaming (World Partition) | Level streaming |
| Sparse array + generation | GameObject instance ID | Actor instance ID |
| Hash chunk world | Addressable Assets | World Composition |
| Hot reload | Domain Reload | Live Coding |
| GameMemory | ScriptableObject (persistent) | GameInstance |

差别只是抽象层次和易用性。**HH 教你"原理层",Unity / Unreal 教你"使用层"**。两个都要懂。

### Rust 生态对比

| HH Rust 翻译 | Rust 生态对应 |
|---|---|
| Vec2 手写 | glam / nalgebra / cgmath |
| Sparse array + generation | slotmap / slotmapd |
| Hash world | ahash + chunked storage |
| cdylib hot reload | libloading + cargo-watch |
| Arena | bumpalo / typed-arena |
| Collision detection | rapier / avian |
| Asset pipeline | bevy_asset / assets_manager |

每个 crate 你都可以读源码学,然后在 HH 框架里手动重写。**这是开源贡献的天然方向**——你读懂 crate 的实现,找到 doc/test/example 的不足,提 PR。

### 历史演化:HH 的"位置"

HH 是 Casey 在 2014-2018 录制,代码风格属于"90 年代 id Software"(John Carmack 风格)。当时游戏业界已经在用 ECS / data-oriented design,但 Casey 故意选保守风格——因为他的目标是**教学**,不是"用最新潮的技术"。

你看 HH 时记住:

- Casey 的代码不是"最佳实践",是"最易懂"
- 现代游戏引擎(Bevy ECS、Unity DOTS)比 HH 走得更远
- 但**理解 HH 才能理解 Bevy 为什么那样设计**

HH 是"基础课",Bevy 是"专业课"。基础课学好,专业课才看得懂。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 为什么 Phase 3-4 用软渲染(CPU),Phase 5 才切 OpenGL(GPU)?至少给 3 个理由。

**参考解答**:
1. **教学价值**:软渲染让你看到每个像素怎么来的,GPU 是黑盒。学图形学先理解原理再用工具。
2. **可调试**:CPU 代码 gdb 单步,GPU shader 调试难。
3. **API 战争**:OpenGL / Vulkan / DirectX / Metal 各有 API,学完软渲染你能在任何 GPU API 上重写,不被绑架。
4. **架构清晰**:软渲染强迫你想清楚"渲染管线是什么",Phase 5 切 GPU 只是搬管线到 shader。
5. **后期能加 GPU 加速**:用 compute shader 加速软渲染,这是 Casey 在 Day 500+ 的实验方向。

### Lv2 · 动手实践

**题**:给 Phase 2 项目加一个 **debug overlay**(右上角显示文字):

```
FPS: 60
Entities: 42
Memory: 145MB / 200MB
Sim Region: 1280x720
```

完成标准:运行后右上角看到上述文字,FPS 数字每秒更新一次。

**提示**:
- 用 Phase 1 的字体渲染(或简单画方块代替字符,显示进度条)
- 每秒更新一次 FPS,不要每帧更新(会闪烁)
- 用 `RwLock<DebugStats>` 或全局 `AtomicUsize` 在游戏层和平台层共享数据

**参考解答**(框架):

```rust
// 游戏层维护
pub struct DebugStats {
    pub fps: f32,
    pub entity_count: usize,
    pub memory_used: usize,
    pub memory_budget: usize,
}

impl GameMemory {
    pub fn update_debug_stats(&mut self, dt: f32) {
        // FPS 用指数平滑(避免抖动)
        let alpha = 0.1; // 平滑系数
        let current_fps = 1.0 / dt.max(1e-6);
        self.debug.fps = self.debug.fps * (1.0 - alpha) + current_fps * alpha;
        // entity_count 直接数
        self.debug.entity_count = self.entities.iter().filter(|e| e.alive).count();
        // memory_used 由 Arena 提供
        self.debug.memory_used = self.arena.used();
    }

    pub fn render_debug(&self, buf: &mut GameOffscreenBuffer) {
        // 在右上角画文字 / 进度条
        draw_text(buf, 1280 - 200, 20, &format!("FPS: {:.0}", self.debug.fps));
        draw_text(buf, 1280 - 200, 40, &format!("Entities: {}", self.debug.entity_count));
        draw_text(buf, 1280 - 200, 60,
            &format!("Memory: {}MB / {}MB",
                self.debug.memory_used / 1024 / 1024,
                self.debug.memory_budget / 1024 / 1024));
    }
}

fn update_and_render(memory: &mut GameMemory, input: &GameInput, dt: f32,
                     buf: &mut GameOffscreenBuffer) {
    memory.update(input, dt);
    memory.render(buf);
    memory.update_debug_stats(dt);
    memory.render_debug(buf);
}
```

这是 Phase 5 debug overlay 的雏形。

### Troubleshooting

- **热重载不工作** —— 确认 cdylib 编译到和可执行文件同目录,或者 `LD_LIBRARY_PATH` 包含 target/release
- **valgrind 报错** —— Rust 默认会用 jemalloc/system malloc,valgrind 可能误报。加 `--suppressions=valgrind-rust.supp` 或用 `RUSTFLAGS="-C debug-assertions"` 重新构建
- **flamegraph 没符号** —— 加 `[profile.release] debug = 1`
- **cargo bench 失败** —— 确认 `harness = false` 和 `criterion` 在 dev-dependencies
