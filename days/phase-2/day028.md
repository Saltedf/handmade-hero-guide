
# Day 028 · 绘制瓦片地图

> Day 026 立了"逻辑/渲染分层"的规矩,Day 027 立了"探索式开发"的方法论。Day 028 终于开始写**实际游戏内容**——把一张 tile map(瓦片地图)画到屏幕上。这是你做的第一个真正的"游戏世界",后面 600 集所有的关卡、地图、场景都从这个雏形长出来。

## 0 · 为什么要有这一天

你大概玩过《超级马里奥》《塞尔达传说》《星之卡比》《宝可梦》。这些经典 2D 游戏有一个共同点:**整个游戏世界是由小方块拼成的**。马里奥的砖块、林克的草丛、卡比的果冻——每个图形元素都是一个固定大小的方块,这些方块按 2D 网格拼起来,形成你看到的世界。

这种"小方块拼世界"的设计叫 **tile map**(瓦片地图),它有四个无可替代的优点:

1. **省内存**:一张草地纹理可以重复铺满整个屏幕,不需要存 1920×1080 像素的草地大图
2. **好编辑**:地图就是一个 2D 数组,改地图就是改数组的值
3. **天然支持碰撞**:墙是 Wall tile,空地是 Empty tile,撞墙判断就是"目标 tile 是不是 Wall"
4. **可复用**:同一张 tile set 可以拼出无数张不同的地图

但 tile map 也有几个**非平凡**的设计决策,Casey 这集要逐一定下来:

- **tile 大小**:8×8、16×16、32×32、64×64?大小直接影响"细节 vs 性能"的权衡
- **坐标系**:tile 坐标(整数)和世界坐标(浮点像素)怎么转换?tile (3, 5) 对应世界哪个像素?
- **可见区域剔除**:世界可能 10000×10000 tile,但屏幕只显示 1920×1080,怎么只画看得见的 tile?
- **相机(Camera)**:玩家移动时,世界相对屏幕"滚动"——这个"滚动"在代码里怎么表达?

这些决策听起来是"实现细节",但它们**一旦定下来,后面 600+ 集的代码都基于此**。Casey 这集的目标是把这些决策讲清楚,写出一个能跑的 tile map 渲染。Day 029 会基于这套基础设施做碰撞检测,Day 030 加多地图切换,Day 031-035 演化坐标系统和内存布局。**Day 028 是整个 Phase 2 的"基础设施日"**。

## 2 · 心智模型

### 类比:乐高积木拼成的地板

把 tile map 想象成**一张用乐高积木拼成的地板**。每个乐高积木是固定大小的小方块(比如 32×32 像素),整张地板是这些小积木按 2D 网格拼起来。

```
   tile(0,0)  tile(1,0)  tile(2,0)  tile(3,0)
  ┌────────┬────────┬────────┬────────┐
  │ Grass  │ Grass  │ Stone  │ Stone  │  ← 第 0 行(世界 y=0..32)
  ├────────┼────────┼────────┼────────┤
  │ Grass  │ Water  │ Water  │ Stone  │  ← 第 1 行(世界 y=32..64)
  ├────────┼────────┼────────┼────────┤
  │ Grass  │ Water  │ Water  │ Stone  │  ← 第 2 行(世界 y=64..96)
  └────────┴────────┴────────┴────────┘
   ↑        ↑        ↑        ↑
   tile(0,0) tile(1,0) ...
```

每个 tile 是一种"贴图"(Grass=绿色,Stone=灰色,Water=蓝色)。整张地图就是这些 tile 拼起来。

### 决策 1:tile 大小

Casey 选 **32×32 像素**。这是有取舍的:

| tile 大小 | 优点 | 缺点 |
|---|---|---|
| 8×8 | tile 数量多,细节丰富(老 RPG) | 同屏 tile 数量爆炸(1920×1080 屏幕 = 32400 个 tile),渲染压力大 |
| 16×16 | 中等细节,经典 RPG(塞尔达 GB) | 中等 |
| **32×32** | **细节够用,渲染量适中** | **主流 2D 游戏标准** |
| 64×64 | HD 细节(现代游戏) | 单 tile 大,一张地图 tile 数少,大世界显得"颗粒粗" |
| 128×128 | 极致细节 | tile 数量极少,大地图显得空 |

**为什么选 32 不是 16**:32 在 1920×1080 屏幕上 = 60×34 个 tile = 约 2000 tile/屏,渲染开销很小(后面算)。同时 32 像素够画一张"有细节的小图"(草地有草叶纹路、石头有裂纹)。

**为什么选 32 不是 64**:64 像素的单 tile 太大,玩家角色(典型 32 像素高)走在 64 像素 tile 上像"蚂蚁爬大砖头",比例不协调。

**32 的另一个理由:2 的幂**。32 = 2^5,这意味着:

- 浮点除法 `wx / 32.0` 可以用整数 `wx >> 5` 替代(位运算比除法快)
- 32 字节对齐是 CPU cache line(64 字节)的一半,2 个 tile 拼起来正好一个 cache line
- GPU 上传纹理时,2 的幂大小有性能优势(虽然 HH 在 Day 235 才用 GPU)

Casey 没在这集讲这些细节,但 32 是个"经得起深挖"的选择。

### 决策 2:坐标系

**世界坐标**(world coordinates)是浮点数,单位像素:
- (0.0, 0.0) 在世界左上角
- x 向右增加,y 向下增加(屏幕坐标,不是数学课的 y 向上)
- 范围:[0.0, world_width_pixels) × [0.0, world_height_pixels)

**tile 坐标**(tile coordinates)是整数,单位 tile:
- tile (0, 0) 占据世界 [0, 32) × [0, 32) 像素
- tile (3, 5) 占据世界 [96, 128) × [160, 192) 像素
- tile (tx, ty) 的左上角世界坐标 = (tx × 32, ty × 32)

**转换公式**:

```
世界 → tile: tile_x = floor(world_x / 32), tile_y = floor(world_y / 32)
tile → 世界(左上角): world_x = tile_x × 32, world_y = tile_y × 32
tile → 世界(中心):   world_x = (tile_x + 0.5) × 32, world_y = (tile_y + 0.5) × 32
```

**为什么 y 轴向下**:显示器硬件传统。CRT(阴极射线管)显像管从屏幕左上角开始,从上到下一行行扫描。framebuffer 的第 0 行对应屏幕最上面。游戏代码用 y 向下 = 渲染时不用翻转 = 代码直观。

**为什么不学数学课的 y 向上**:数学课的 y 向上是从笛卡尔坐标系来的(为了符合右手定则)。但游戏代码"和屏幕一致"比"和数学课一致"重要——因为最终要画到屏幕上。

**踩坑预警**:Day 235 切 OpenGL 时,OpenGL 默认 y 向上(数学传统),Casey 要处理"游戏 y 向下 → OpenGL y 向上"的转换。Day 026 的"逻辑/渲染分离"让这次转换只影响渲染层,逻辑层 y 向下不变。这是分层架构的红利之一。

### 决策 3:Camera(相机)

世界可能很大(比如 10000×10000 tile = 320000×320000 像素),但屏幕只有 1920×1080。**Camera 是世界里的一个"窗口"**——它定义了"屏幕左上角对应世界的哪个位置"。

```
世界(328×328 tile = 10496×10496 像素):
┌─────────────────────────────────────────────┐
│                                             │
│       camera (200, 150)  ← 屏幕左上角在世界 (200, 150)
│       ┌──────────────────┐                  │
│       │                  │                  │
│       │   屏幕显示的内容  │  ← 1920×1080     │
│       │                  │                  │
│       └──────────────────┘                  │
│                                             │
└─────────────────────────────────────────────┘

世界坐标 → 屏幕坐标的转换:
  screen_x = world_x - camera.x
  screen_y = world_y - camera.y

例:玩家在世界 (250, 200),camera 在 (200, 150)。
    玩家在屏幕 (250-200, 200-150) = (50, 50)。
```

**Camera 的意义**:玩家移动 = camera 移动,世界相对屏幕滚动。这是 2D 滚动游戏(超级马里奥)和俯视角 RPG(塞尔达)的核心机制。

### 决策 4:可见性剔除(Culling)

世界有 10000×10000 tile = 1 亿 tile。每帧画 1 亿 tile 不现实——大部分 tile 在屏幕外,看不见。

**可见性剔除**:只画屏幕上看得见的 tile。

```rust
// 屏幕上能放多少 tile?
let tiles_per_screen_x = SCREEN_WIDTH / TILE_SIZE + 1;  // 1920 / 32 + 1 = 61
let tiles_per_screen_y = SCREEN_HEIGHT / TILE_SIZE + 1; // 1080 / 32 + 1 = 35

// camera 对应哪个 tile?
let cam_tile_x = (camera.x / TILE_SIZE as f32) as i32;  // 向下取整
let cam_tile_y = (camera.y / TILE_SIZE as f32) as i32;

// 只迭代屏幕上的 tile
for ty in 0..tiles_per_screen_y {
    for tx in 0..tiles_per_screen_x {
        let world_tx = cam_tile_x + tx;
        let world_ty = cam_tile_y + ty;
        // 查 tile 值,画出来...
    }
}
```

`+1` 是为了处理"camera 不在 tile 边界"的情况——camera 在 (50, 50),屏幕左上角的 tile 是 (1, 1) 而不是 (0, 0),但 tile (1, 1) 只有一半在屏幕上,另一半被剪掉。`+1` 保证不漏画边缘的 tile。

### 渲染 tile 的代码

把上面所有决策组合起来:

```rust
const TILE_SIZE: i32 = 32;
const SCREEN_WIDTH: i32 = 1280;
const SCREEN_HEIGHT: i32 = 720;

#[derive(Copy, Clone, Debug, PartialEq)]
enum TileValue {
    Empty,
    Grass,
    Stone,
    Water,
}

struct TileMap {
    tiles: Vec<TileValue>,  // 1D 数组模拟 2D,行优先
    width: i32,
    height: i32,
}

impl TileMap {
    fn new(width: i32, height: i32) -> Self {
        Self {
            tiles: vec![TileValue::Empty; (width * height) as usize],
            width, height,
        }
    }

    // 2D 坐标 → 1D 索引(行优先 row-major)
    // 第 ty 行的第 tx 个 = ty * width + tx
    fn get(&self, tx: i32, ty: i32) -> TileValue {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height {
            return TileValue::Empty;  // 越界当空地
        }
        self.tiles[(ty * self.width + tx) as usize]
    }

    fn set(&mut self, tx: i32, ty: i32, v: TileValue) {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height {
            return;  // 越界忽略
        }
        self.tiles[(ty * self.width + tx) as usize] = v;
    }
}

// 把 tile 画到 framebuffer 上,screen_x/screen_y 是屏幕像素坐标
// framebuffer 是 [u32; SCREEN_WIDTH * SCREEN_HEIGHT],每像素 0x00RRGGBB
fn draw_tile(
    framebuffer: &mut [u32],
    screen_x: i32, screen_y: i32,
    value: TileValue,
) {
    let color = match value {
        TileValue::Empty => 0x000000,   // 黑
        TileValue::Grass => 0x44AA44,   // 绿
        TileValue::Stone => 0x888888,   // 灰
        TileValue::Water => 0x4444AA,   // 蓝
    };
    // 双 for 填充 32×32 像素块
    for dy in 0..TILE_SIZE {
        for dx in 0..TILE_SIZE {
            let px = screen_x + dx;
            let py = screen_y + dy;
            if px < 0 || py < 0 || px >= SCREEN_WIDTH || py >= SCREEN_HEIGHT {
                continue;  // 屏幕外跳过
            }
            framebuffer[(py * SCREEN_WIDTH + px) as usize] = color;
        }
    }
}

// 渲染整个 tile map(只画屏幕可见部分)
fn render_tiles(
    map: &TileMap,
    camera_x: i32, camera_y: i32,
    framebuffer: &mut [u32],
) {
    let cam_tile_x = camera_x / TILE_SIZE;  // 整数除法自动 floor(对正数)
    let cam_tile_y = camera_y / TILE_SIZE;
    let tiles_per_screen_x = SCREEN_WIDTH / TILE_SIZE + 1;
    let tiles_per_screen_y = SCREEN_HEIGHT / TILE_SIZE + 1;

    for ty in 0..tiles_per_screen_y {
        for tx in 0..tiles_per_screen_x {
            let world_tx = cam_tile_x + tx;
            let world_ty = cam_tile_y + ty;
            let value = map.get(world_tx, world_ty);
            // 世界坐标 → 屏幕坐标
            let screen_x = world_tx * TILE_SIZE - camera_x;
            let screen_y = world_ty * TILE_SIZE - camera_y;
            draw_tile(framebuffer, screen_x, screen_y, value);
        }
    }
}
```

**关键代码细节**:

- `Vec<TileValue>` 用 1D 数组存 2D 数据。这是**行优先(row-major)**——第 0 行的所有元素连续在内存里,然后第 1 行,以此类推。对比列优先(column-major)——第 0 列的所有元素连续。绝大多数语言和库默认行优先,因为遍历行更直观。
- `ty * width + tx` 是把 (tx, ty) 转成 1D 索引。`tx` 是内层循环变量(变化快),`ty` 是外层(变化慢)。这种"行优先遍历"对 CPU cache 友好——访问 framebuffer[t] 和 framebuffer[t+1] 时,t+1 在 cache 里(L1 cache 一次读 64 字节,16 个 u32)。
- `camera_x / TILE_SIZE` 对**正数** camera 等价于 floor。负数 camera 在 Rust 里 `/` 是 truncate-towards-zero(`-1 / 32 = 0` 不是 `-1`),后面 Day 031 会修正。
- 屏幕坐标 = 世界坐标 - camera。这是滚动的核心——玩家移动 = camera 移动 = 所有 tile 自动平移。

### 性能估算

1920×1080 屏幕,tile 32×32,大约 60×34 = 2040 tile。每个 tile 32×32 = 1024 像素。总像素 = 2040 × 1024 ≈ 2M 像素。每个像素一次写入,2M 次内存访问。CPU 一帧 16ms(60 FPS),能做几亿次内存访问,2M 完全够。

但 Casey 在这集**不优化**——双 for 直接画,跑 60 FPS 没问题。Day 034+ 讲数据布局时才考虑"如何更快"。这是 Day 027 探索式架构的体现:**先简单跑通,profiler 说慢再优化**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

Tile map 是 2D 游戏最经典的关卡表示法。主流变体:

**1. 单层 tile map(这集)**:整个地图一个 tile 数组。简单,但**只能表示静态背景**——动态元素(玩家、怪物、子弹)需要另外的数据结构。

**2. 多层 tile map(超级马里奥世界用)**:背景层 + 实体层 + UI 层。背景层是 tile map,实体层是 entity list,UI 层独立。Day 038+ Casey 会演化到这种结构。

**3. 等距 tile map(Isometric, Diablo 2 / 文明)**:tile 不是正方形,是菱形(45° 角)。视觉上是 2.5D。坐标系复杂(菱形 tile 索引),但视觉很漂亮。HH 不做这种。

**4. Hex tile map(文明 5 / 六边形战棋)**:tile 是六边形。坐标系统用"立方坐标"或"轴坐标",比方形 tile 复杂。HH 不做。

**5. Voxel(Minecraft)**:3D 版本的 tile,叫 voxel(体素)。每个 voxel 是 1×1×1 立方体。Day 277+ Casey 简单讨论。

Casey 在 Phase 2 做"单层 + 多层混合"——背景 tile map 是静态的,entity list 是动态的。Day 053+ 加"环境作为 entity",让 tile 和 entity 在某种意义上统一。

**tile 编辑器**:大型项目有专门的 tile map 编辑器(最著名是 **Tiled**,https://www.mapeditor.org/)。HH 不用编辑器,Casey 直接在代码里硬编码地图(教学清晰)。商业项目用 Tiled 导出 JSON / XML / TMX 格式,游戏代码加载解析。

### 3.2 · 🎨 图形学视角

Tile map 在图形学里属于**图集(Atlas)+ 实例化(Instancing)**的范畴:

- **图集**:把所有 tile 贴图拼到一张大图(叫 tileset / spritesheet),GPU 上传一次,渲染时根据 tile 类型选 atlas 中的子区域
- **实例化**:同样形状(32×32 矩形)大量重复,只变换位置——GPU 的 instanced rendering 一次绘制几千个

Casey Day 1-234 用 CPU 软渲染,所以这两步都用不上。Day 235+ 切 OpenGL 后,这两步是性能关键。

**抗锯齿问题**:tile 边界是数学上的硬边界(整数像素),没有抗锯齿。当 camera 在非整数位置(比如 100.5)时,tile 的"贴图"会跨像素——CPU 软渲染要么舍入要么插值。Casey 在 Day 037+ 用整数 camera(避免插值),Day 094 加子像素精度时引入双线性插值。

**纹理重复**:Grass tile 在屏幕上出现几百次,但内存里只存一份。这就是 tile 设计的核心红利——重复使用。GPU 上的实现叫 sampler repeat mode,Day 240+ 详谈。

### 3.3 · 🐧 Linux 系统编程视角

Tile map 数据存在哪?

**选项 1:硬编码在源代码里**(Casey Day 028 选这个)

```rust
const TEST_MAP: &[(i32, i32, TileValue)] = &[
    (0, 0, TileValue::Grass),
    (1, 0, TileValue::Grass),
    // ... 几百行
];
```

优点:简单,无 IO。缺点:改地图要重新编译。

**选项 2:外部文件(JSON / TOML / 自定义格式)**

```rust
let map_data = std::fs::read_to_string("assets/level1.json")?;
let map: TileMap = serde_json::from_str(&map_data)?;
```

优点:设计师改地图不用动代码。缺点:要解析(增加启动时间)、要管 IO 错误。

**选项 3:mmap(内存映射)**(Day 029 会详细讲)

```rust
let file = std::fs::File::open("assets/level1.bin")?;
let mmap = unsafe { memmap2::Mmap::map(&file)? };
let map: &TileMap = bincode::deserialize(&mmap[..])?;
```

优点:大文件加载快(OS 按需读页)。缺点:复杂,平台相关。

Casey 在 Phase 2 早期用选项 1(教学清晰),Day 055+ 加资产系统后切到选项 2/3。

**Linux 文件系统视角**:Tile map 数据本身不大(一张 100×100 tile map = 10000 byte,几 KB),`read` 整个文件到内存是最简单的。但大世界(10000×10000 tile = 100 MB)就要 mmap 了。Day 029 详细对比 `read` vs mmap。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 tile map 的几种方式:

**方式 1:`Vec<TileValue>`(Casey 选这个)**

```rust
struct TileMap {
    tiles: Vec<TileValue>,
    width: i32, height: i32,
}
```

优点:简单,内存连续(cache 友好)。缺点:稀疏地图浪费内存(后面 Day 035 解决)。

**方式 2:`Vec<Vec<TileValue>>`(双层 Vec)**

```rust
struct TileMap { tiles: Vec<Vec<TileValue>> }
```

**这是反模式**,因为每行是独立的 Vec 分配,内存不连续,cache 不友好。Casey 永远不用这种。新手容易犯这个错——记住:**2D 数组永远用 1D + index 计算**。

**方式 3:二维数组 `[[TileValue; W]; H]`**

```rust
struct TileMap { tiles: [[TileValue; 128]; 128] }
```

固定大小。优点:栈分配,极快。缺点:大小编译时定,不能动态调整。适合"地图大小固定"的小游戏。

**方式 4:`ndarray::Array2<TileValue>`(科学计算库)**

```rust
use ndarray::Array2;
let map: Array2<TileValue> = Array2::zeros((128, 128));
```

优点:支持切片、广播、矩阵运算。缺点:依赖重,游戏不需要这种通用性。

Casey 选方式 1 是教学最优——足够简单,足够快,后面升级(HashMap、稀疏存储)也容易。

**越界检查的 Rust 陷阱**:

```rust
fn get(&self, tx: i32, ty: i32) -> TileValue {
    self.tiles[(ty * self.width + tx) as usize]  // ⚠ 危险
}
```

如果 tx/ty 是负数,`as usize` 会变成巨大的正数(underflow wrap),`self.tiles[巨大数]` 会 panic。Casey 的代码加了边界检查:

```rust
fn get(&self, tx: i32, ty: i32) -> TileValue {
    if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height {
        return TileValue::Empty;
    }
    self.tiles[(ty * self.width + tx) as usize]
}
```

`if tx < 0` 等价于"越界返回默认值"。这让游戏代码不需要每次 `get` 都检查边界——查地图外区域自然返回 Empty(空地),不会 panic。

**性能 vs 安全的权衡**:Rust 标准库的 `Vec::operator[]` 在 debug 模式检查越界,release 模式也检查(Rust 默认安全)。Casey 的 `get` 函数手动检查,可以**比 Vec 自带检查更快**(因为合并了多个分支)。这是 systems programming 的日常——为 hot path 写专门的安全检查。

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:把世界分成网格管理。

| 语境 | "网格"叫法 | 网格大小 |
|---|---|---|

| | Tile map | Free-form(矢量 / 像素画自由摆放) |

| 视觉 | "格子感"明显 | 自然 |
| 代表 | 超级马里奥、塞尔达 | Braid、Limbo |

现代游戏常混合:大背景是 tile,小细节(树、石头)是 free-form sprite。Casey 在 Day 053+ 也走到这种混合。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 选 tile 大小 32×32,但屏幕分辨率是 1920×1080。1920 不能被 32 整除(1920 / 32 = 60,正好整除;但 1080 / 32 = 33.75,不能整除)。这个"不能整除"会带来什么问题?Casey 怎么解决?

**参考解答**:**会带来"屏幕底部有一条不完整的 tile"**。

具体:1080 / 32 = 33.75,意味着屏幕垂直方向能放 33 个完整 tile,剩下 0.75 × 32 = 24 像素的高度,只能显示第 34 行 tile 的上半部分。

Casey 在 Day 028 的代码里用 `tiles_per_screen_y = SCREEN_HEIGHT / TILE_SIZE + 1`——`+1` 多画一行 tile,让第 34 行被画出来,然后由 `draw_tile` 函数里的边界检查剪掉屏幕外的部分。

这就是为什么 `draw_tile` 必须有边界检查(`if py >= SCREEN_HEIGHT { continue; }`)——不只是为了 tile map 完全在屏幕外的情况,也是为了处理"部分在屏幕外"。

**延伸**:如果屏幕分辨率能动态变(窗口 resize),`tiles_per_screen` 也要重算。Casey 在 Day 040 加全屏支持时讨论这个。

### Lv2 · 动手实践

**题**:写一个最小的 tile map 渲染程序,要求:

1. 一个 64×64 tile 的地图(共 4096 tile),手动填一些 Grass / Stone / Water
2. 用 WASD 移动 camera(每帧 5 像素)

4. 把 framebuffer 输出到一个 PPM 文件(简单图像格式),用 `feh` 或 `eog` 打开看

**参考解答**:

```rust
// src/main.rs
// cargo new --bin tile_map_demo && cd tile_map_demo

const TILE_SIZE: i32 = 32;
const SCREEN_WIDTH: i32 = 640;   // 缩小屏幕让 PPM 文件小一点
const SCREEN_HEIGHT: i32 = 480;
const MAP_WIDTH: i32 = 64;
const MAP_HEIGHT: i32 = 64;

#[derive(Copy, Clone, Debug, PartialEq)]
enum TileValue { Empty, Grass, Stone, Water }

struct TileMap {
    tiles: Vec<TileValue>,
    width: i32, height: i32,
}

impl TileMap {
    fn new(width: i32, height: i32) -> Self {
        Self {
            tiles: vec![TileValue::Empty; (width * height) as usize],
            width, height,
        }
    }
    fn get(&self, tx: i32, ty: i32) -> TileValue {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height {
            return TileValue::Empty;
        }
        self.tiles[(ty * self.width + tx) as usize]
    }
    fn set(&mut self, tx: i32, ty: i32, v: TileValue) {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height { return; }
        self.tiles[(ty * self.width + tx) as usize] = v;
    }
}

// 把当前 framebuffer 写成 PPM 文件(最简单的图像格式)
fn write_ppm(filename: &str, framebuffer: &[u32]) -> std::io::Result<()> {
    use std::io::Write;
    let mut f = std::fs::File::create(filename)?;
    // PPM 头:P6 / width height / max_value / 二进制像素
    writeln!(f, "P6")?;
    writeln!(f, "{} {}", SCREEN_WIDTH, SCREEN_HEIGHT)?;
    writeln!(f, "255")?;
    // 每像素 3 字节 RGB
    let mut bytes = Vec::with_capacity((SCREEN_WIDTH * SCREEN_HEIGHT * 3) as usize);
    for &pixel in framebuffer {
        let r = (pixel >> 16) & 0xFF;
        let g = (pixel >> 8) & 0xFF;
        let b = pixel & 0xFF;
        bytes.push(r as u8);
        bytes.push(g as u8);
        bytes.push(b as u8);
    }
    f.write_all(&bytes)?;
    Ok(())
}

fn render_tiles(map: &TileMap, cam_x: i32, cam_y: i32, fb: &mut [u32]) {
    let cam_tx = cam_x / TILE_SIZE;
    let cam_ty = cam_y / TILE_SIZE;
    let n_tx = SCREEN_WIDTH / TILE_SIZE + 1;
    let n_ty = SCREEN_HEIGHT / TILE_SIZE + 1;

    for ty in 0..n_ty {
        for tx in 0..n_tx {
            let wtx = cam_tx + tx;
            let wty = cam_ty + ty;
            let value = map.get(wtx, wty);
            let color = match value {
                TileValue::Empty => 0x000000,
                TileValue::Grass => 0x44AA44,
                TileValue::Stone => 0x888888,
                TileValue::Water => 0x4444AA,
            };
            let sx = wtx * TILE_SIZE - cam_x;
            let sy = wty * TILE_SIZE - cam_y;
            // 画 32×32 像素块
            for dy in 0..TILE_SIZE {
                for dx in 0..TILE_SIZE {
                    let px = sx + dx;
                    let py = sy + dy;
                    if px < 0 || py < 0 || px >= SCREEN_WIDTH || py >= SCREEN_HEIGHT {
                        continue;
                    }
                    fb[(py * SCREEN_WIDTH + px) as usize] = color;
                }
            }
        }
    }
}

fn main() {
    // 构造一个测试地图:左上 Grass,右下 Water,中间 Stone 边框
    let mut map = TileMap::new(MAP_WIDTH, MAP_HEIGHT);
    for ty in 0..MAP_HEIGHT {
        for tx in 0..MAP_WIDTH {
            if tx < 32 && ty < 32 {
                map.set(tx, ty, TileValue::Grass);
            } else if tx >= 32 && ty >= 32 {
                map.set(tx, ty, TileValue::Water);
            } else {
                map.set(tx, ty, TileValue::Stone);
            }
        }
    }

    // 模拟两个不同的 camera 位置
    for (i, (cx, cy)) in [(0, 0), (500, 500), (1000, 1000)].iter().enumerate() {
        let mut fb = vec![0u32; (SCREEN_WIDTH * SCREEN_HEIGHT) as usize];
        render_tiles(&map, *cx, *cy, &mut fb);
        let filename = format!("frame_{}.ppm", i);
        write_ppm(&filename, &fb).expect("write ppm");
        println!("Wrote {} (camera at ({}, {}))", filename, cx, cy);
    }
}
```

跑完后,当前目录有 `frame_0.ppm`、`frame_1.ppm`、`frame_2.ppm`。在 Arch 上:

```bash
# 用 feh 打开(eog / gimp / ffmpeg 都行)
sudo pacman -S feh

# frame_0.ppm:左上 Grass(绿)
# frame_1.ppm:Grass / Stone / Water 三色块交界
# frame_2.ppm:右下 Water(蓝)
```

**每行解释**:

- `vec![TileValue::Empty; (width * height) as usize]` —— Rust 的 Vec 宏,创建长度为 `width * height` 的 Vec,每个元素初始化为 Empty。`as usize` 把 i32 转成 usize(Vec 长度必须 usize)。
- `pixel >> 16` —— 位运算,取 pixel 的高 8 位(R 通道)。Casey 的 framebuffer 格式是 `0x00RRGGBB`,R 在 bit 16-23,G 在 8-15,B 在 0-7。
- `writeln!(f, "...")` —— Rust 写文本到文件。`writeln!` 自动加换行。`!` 表示这是宏(macro),不是函数。
- `f.write_all(&bytes)` —— 写二进制数据。`write_all` 保证写完所有字节,出错返回 `Err`。

const TILE_SIZE: i32 = 32;
const SCREEN_WIDTH: i32 = 1280;
const SCREEN_HEIGHT: i32 = 720;
const MAP_WIDTH: i32 = 200;
const MAP_HEIGHT: i32 = 200;

#[derive(Copy, Clone, Debug, PartialEq)]
enum TileValue { Empty, Grass, Stone, Water }

struct TileMap {
    tiles: Vec<TileValue>,
    width: i32, height: i32,
}

impl TileMap {
    fn new(width: i32, height: i32) -> Self {
        Self {
            tiles: vec![TileValue::Empty; (width * height) as usize],
            width, height,
        }
    }
    fn get(&self, tx: i32, ty: i32) -> TileValue {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height {
            return TileValue::Empty;
        }
        self.tiles[(ty * self.width + tx) as usize]
    }
    fn set(&mut self, tx: i32, ty: i32, v: TileValue) {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height { return; }
        self.tiles[(ty * self.width + tx) as usize] = v;
    }
}

fn write_ppm(filename: &str, fb: &[u32]) -> std::io::Result<()> {
    use std::io::Write;
    let mut f = std::fs::File::create(filename)?;
    writeln!(f, "P6\n{} {}\n255", SCREEN_WIDTH, SCREEN_HEIGHT)?;
    let mut bytes = Vec::with_capacity((SCREEN_WIDTH * SCREEN_HEIGHT * 3) as usize);
    for &p in fb {
        bytes.push((p >> 16 & 0xFF) as u8);
        bytes.push((p >> 8 & 0xFF) as u8);
        bytes.push((p & 0xFF) as u8);
    }
    f.write_all(&bytes)
}

fn render_tiles(map: &TileMap, cam_x: i32, cam_y: i32, fb: &mut [u32]) {
    let cam_tx = cam_x / TILE_SIZE;
    let cam_ty = cam_y / TILE_SIZE;
    let n_tx = SCREEN_WIDTH / TILE_SIZE + 1;
    let n_ty = SCREEN_HEIGHT / TILE_SIZE + 1;

    for ty in 0..n_ty {
        for tx in 0..n_tx {
            let wtx = cam_tx + tx;
            let wty = cam_ty + ty;
            let color = match map.get(wtx, wty) {
                TileValue::Empty => 0x000000,
                TileValue::Grass => 0x44AA44,
                TileValue::Stone => 0x888888,
                TileValue::Water => 0x4444AA,
            };
            let sx = wtx * TILE_SIZE - cam_x;
            let sy = wty * TILE_SIZE - cam_y;
            for dy in 0..TILE_SIZE {
                for dx in 0..TILE_SIZE {
                    let px = sx + dx;
                    let py = sy + dy;
                    if px < 0 || py < 0 || px >= SCREEN_WIDTH || py >= SCREEN_HEIGHT {
                        continue;
                    }
                    fb[(py * SCREEN_WIDTH + px) as usize] = color;
                }
            }
        }
    }
}

fn parse_args() -> (i32, i32) {
    let args: Vec<String> = std::env::args().collect();
    let mut x = 0;
    let mut y = 0;
    let mut i = 1;
    while i < args.len() {
        match args[i].as_str() {
            "--x" => { x = args[i + 1].parse().unwrap_or(0); i += 2; }
            "--y" => { y = args[i + 1].parse().unwrap_or(0); i += 2; }
            _ => i += 1,
        }
    }
    (x, y)
}

fn main() {
    let (cam_x, cam_y) = parse_args();
    println!("Camera at ({}, {})", cam_x, cam_y);

    // 构造测试地图
    let mut map = TileMap::new(MAP_WIDTH, MAP_HEIGHT);
    for ty in 0..MAP_HEIGHT {
        for tx in 0..MAP_WIDTH {
            let cx = tx - MAP_WIDTH / 2;
            let cy = ty - MAP_HEIGHT / 2;
            let dist = (cx * cx + cy * cy).abs();
            if dist < 1000 {
                map.set(tx, ty, TileValue::Grass);     // 中心草地
            } else if dist < 3000 {
                map.set(tx, ty, TileValue::Stone);     // 中圈石头
            } else {
                map.set(tx, ty, TileValue::Water);     // 外圈水
            }
        }
    }

    // 渲染并测时间
    let mut fb = vec![0u32; (SCREEN_WIDTH * SCREEN_HEIGHT) as usize];
    let start = Instant::now();
    render_tiles(&map, cam_x, cam_y, &mut fb);
    let elapsed = start.elapsed();

    println!("Render took: {:?}", elapsed);

    // 数 framebuffer 里非空像素,大致验证渲染了东西
    let non_empty = fb.iter().filter(|&&p| p != 0).count();
    println!("Non-empty pixels: {} / {}", non_empty, fb.len());

    write_ppm("output.ppm", &fb).expect("write ppm");
    println!("Wrote output.ppm ({}x{})", SCREEN_WIDTH, SCREEN_HEIGHT);
}

**Troubleshooting**:

- `error: cannot divide i32 by i32` —— Rust 整数除法不会自动 panic,但要注意负数除法的 truncation 行为(`-1 / 32 = 0` 不是 `-1`)。如果 camera 可以是负数,用 `(cam_x - TILE_SIZE + 1) / TILE_SIZE` 或 `cam_x.div_euclid(TILE_SIZE)`(Rust 1.62+ 的 floor 除法)。
- PPM 文件打不开 —— 检查写入时是否漏了 `f.write_all(&bytes)`,只用了 `writeln!` 是文本模式。
- 性能差 —— 确认是 `cargo run --release`,debug 模式 Rust 数学运算慢 10-100 倍。
