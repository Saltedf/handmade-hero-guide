
# Day 057 · 空间划分:均匀网格

> 昨天把墙改成 entity,代价是 entity 数从 30 暴涨到 5000,碰撞 O(N²) 退化到 25,000,000 次/帧。今天 Casey 用一张"看不见的渔网"——空间网格(spatial grid)——把这件事救回来。

## 0 · 为什么要有这一天

讲一个你马上要撞到的墙:

第 56 集重构后,你的游戏有 5000 个 entity(墙占 4800 个,怪 / 玩家 / 投射物 ~200 个)。每帧碰撞检测:

```
5000 × 5000 / 2 = 12,500,000 次 Minkowski AABB 测试
每次测试 ~10 ns(f32 比较 + 分支)
=> 每帧 125 ms 仅碰撞
```

60 FPS 一帧 16.6 ms。**单碰撞就吃掉 7.5 帧**。游戏不可能跑。

这个问题的本质:**朴素的"两两测试"在 N 大时坍塌**。N=30 没事,N=5000 就死。

但仔细想想——大部分 entity 对**根本不可能相撞**。屏幕角落的墙(世界坐标 (0, 0))和另一头的墙((10000, 10000))之间的距离有 14142 像素,你不需要做任何浮点运算就知道它们不相撞。我们浪费了 99.99% 的计算在"明显不撞的 entity 对"上。

**空间划分**的核心思想:**把"距离远的 entity 对"用 O(1) 操作排除掉,只对"距离近的 entity 对"做精细检测**。

具体怎么做?在世界上铺一张看不见的渔网,把世界切成方块格子(cell)。每个 entity 根据"自己的位置"挂到对应的格子上。查询时:**只查目标所在格子 + 周围 8 个邻居**(共 9 个格子),不查其他。

代价:每个 entity 挂格子的开销 O(1)(算 `(x/cell_size, y/cell_size)` 即可);查询从 O(N) 降到 O(1)(只有 9 个格子的 entity 数,通常是 0~5 个)。

这个思想不止游戏用——Linux 内核的页面调度、数据库的索引、地理信息系统(GIS)的最近邻查询、网卡的 RSS(receive side scaling)都是同一思想的不同实现。**把"全量扫描"换成"按位置索引"是计算机科学最普遍的优化**。

读完今天,你要做到:
- 用 1 分钟在白板上画出空间网格的数据结构
- 计算 cell_size 的选择依据(等于查询半径)
- 写出 Rust 版本(注意 ownership:entity 移动时如何更新所在 cell)
- 知道 Casey 选了 uniform grid 而不是 quadtree / BVH 的理由

如果你卡在第三点(ownership),那是 Rust 特有的难题——空间网格同时持有 entity 的引用,而 entity 又要在别处被修改。今天会教你用 ID 而不是引用解决。

## 2 · 心智模型

### 2.1 类比:看不见的渔网

想象一艘渔船撒下一张方形大网,网孔是 1 米 × 1 米。这张网覆盖整个海域。

海里有鱼。每条鱼都在某个网孔里(按它的 (x, y) 坐标算)。你想找"我附近 1 米内的鱼",不用扫整个海域——只要看**我所在的网孔 + 周围 8 个网孔**,共 9 个网孔,而每个网孔里大概几条鱼。

这就是空间网格。

如果网孔太大(比如 100 米 × 100 米),每个网孔里有几千条鱼,查 9 个网孔 ≈ 扫整个海域,没意义。如果网孔太小(1 厘米 × 1 厘米),几百万个空网孔浪费内存,而且鱼会同时跨多个网孔(实现复杂)。

**最佳网孔大小 ≈ 你要查询的距离**。游戏里"碰撞查询"的距离 ≈ 玩家半径 + 怪半径,通常 ~32 像素,所以 cell_size ≈ 32 像素。

### 2.2 严谨:数据结构和算法

#### 数据结构

```rust
struct SpatialGrid {
    cells: HashMap<(i32, i32), Vec<EntityId>>,  // key: 格子坐标,value: 该格的 entity ID 列表
    cell_size: f32,                              // 每格多大
}
```

`HashMap<(i32, i32), Vec<EntityId>>` 用 (i32, i32) 作 key。`HashMap` 要求 key 实现 `Hash + Eq`,Rust 的 tuple 默认实现这两个 trait,所以直接用。

为什么不直接用 `Vec<Vec<Vec<EntityId>>>`(二维数组)?
- 世界无限大(虚拟化大世界,Day 33),用二维数组需要确定边界
- 大部分格子是空的,二维数组浪费内存
- HashMap 只存非空格子,稀疏高效

代价:HashMap 的 hash + lookup 比 array index 慢(~50 ns vs ~2 ns)。但相对"省下的几百万次碰撞检测",这点开销忽略不计。

#### Insert 算法

```rust
impl SpatialGrid {
    fn cell_coord(&self, pos: Vec2) -> (i32, i32) {
        // 用 floor:负数也要正确归类(-1.5 → -2,不是 -1)
        ((pos.x / self.cell_size).floor() as i32,
         (pos.y / self.cell_size).floor() as i32)
    }

    fn insert(&mut self, pos: Vec2, id: EntityId) {
        let c = self.cell_coord(pos);
        self.cells.entry(c).or_default().push(id);
    }
}
```

`entry(c).or_default()` 是 Rust HashMap 的惯用法:
- `entry(c)` 返回一个 Entry enum,可能是 Occupied(格子已存在)或 Vacant(不存在)
- `.or_default()` 如果是 Vacant,插入一个默认值(对 Vec 是空 vec),返回可变引用
- `.push(id)` 把 id 推进去

#### Query 算法

```rust
impl SpatialGrid {
    fn query_nearby(&self, pos: Vec2) -> Vec<EntityId> {
        let (cx, cy) = self.cell_coord(pos);
        let mut result = Vec::new();
        // 3×3 = 9 个邻居(包括自己)
        for dx in -1..=1 {
            for dy in -1..=1 {
                if let Some(ids) = self.cells.get(&(cx + dx, cy + dy)) {
                    result.extend_from_slice(ids);
                }
            }
        }
        result
    }
}
```

`extend_from_slice(ids)` 把一个 slice 的所有元素 append 到 result。比 `for id in ids { result.push(*id) }` 快(内部 memcpy)。

#### 为什么是 9 个邻居(3×3)

考虑玩家在格子 (3, 3)。它的中心可能在格子右下角,接近 (4, 4) 格子的边界。如果它要查询半径 = cell_size,可能查到 (4, 4) 格子里的 entity。所以查询必须包含 (3±1, 3±1),共 9 个格子。

如果查询半径 = 2 × cell_size,需要 5×5 = 25 个格子。所以**查询半径和 cell_size 的比例决定邻居数**。Casey 选 cell_size = 查询半径,保证 9 邻居够用。

### 2.3 重建策略:全量 vs 增量

每个 entity 移动后,它可能从一个格子跳到另一个。两种处理方式:

**全量重建**(Casey 选这个):
```rust
fn frame_update(world: &mut World) {
    world.grid.clear();
    for (id, e) in &world.entities {
        world.grid.insert(e.pos, *id);
    }
    // 后续碰撞 / AI / 渲染都用 grid
}
```
- 优点:简单,没有"忘了删除旧位置"的 bug
- 缺点:每帧 N 次 insert,即使 entity 没动也重做
- 适用:N 不太大(几千),或者 entity 大部分每帧都动

**增量更新**(复杂场景):
```rust
fn entity_moved(world: &mut World, id: EntityId, old_pos: Vec2, new_pos: Vec2) {
    let old_cell = world.grid.cell_coord(old_pos);
    let new_cell = world.grid.cell_coord(new_pos);
    if old_cell != new_cell {
        // 从旧 cell 删除
        if let Some(v) = world.grid.cells.get_mut(&old_cell) {
            v.retain(|x| *x != id);
        }
        // 加到新 cell
        world.grid.cells.entry(new_cell).or_default().push(id);
    }
}
```
- 优点:不动不付钱
- 缺点:每个移动都要做 cell 检查,代码复杂,容易出 bug(忘了 remove / double-insert)
- 适用:N 极大(几万),或大部分 entity 静止

Casey 用全量重建,理由:**sim region(Day 063)之后,active entity 只有几百个,全量重建几百个 hash 比维护增量状态简单**。这是工程权衡——选简单的,除非简单的不够用。

### 2.4 完整工作流

每帧做的事:

```
1. update 所有 entity 的位置(物理 / AI / 玩家输入)
2. grid.clear()
3. for e in entities: grid.insert(e.pos, e.id)
4. for e in entities:
       candidates = grid.query_nearby(e.pos)  // ~10 个
       for c in candidates:
           if c != e.id && minkowski_collide(e, entities[c]):
               resolve_collision(...)
5. render:
       visible_cells = compute_cells_in_screen_rect(camera, screen_size)
       for cell in visible_cells:
           for id in grid[cell]:
               draw(entities[id])
```

注意:**第 3 步全量 insert 完了才开始碰撞**。不要边 insert 边查——会导致漏掉同帧移到一起的 entity。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

空间划分是游戏引擎的**基础零件**。所有引擎都有,叫法不同:

| 引擎 | 名称 | 数据结构 |
|---|---|---|
| Unity | Broadphase | AABB tree(动态)+ Uniform grid(静态) |
| Unreal | Physics Broadphase | BVH |
| Box2D | Broadphase | Dynamic tree(动态 AABB 树) |
| PhysX | Broadphase | SAP(sweep and prune)+ BVH |
| Minecraft | Chunk | 16³ 的 voxel grid |
| HH Casey | Spatial grid | Uniform grid |

**Broadphase vs Narrowphase**:游戏 / 物理引擎把碰撞分两阶段:
- Broadphase(粗筛):空间划分排除明显不撞的对,输出候选对
- Narrowphase(精检):对候选对做精确几何检测(Minkowski / GJK / SAT)

今天的 spatial grid 就是 broadphase。Minkowski 是 narrowphase。

**为什么 Casey 选 uniform grid 而不是 quadtree / BVH**:
- uniform grid 实现极简(100 行),debug 容易
- HH 是 2D,且 entity 大小相对均匀(都在 16~64 像素),uniform grid 恰到好处
- quadtree 在 entity 大小差异大时有优势(大树占多个 leaf,小怪占一个 leaf),但 case 多了实现复杂
- BVH 在 3D raycast 时强,2D 没明显优势

**教训**:选择空间划分算法时,先问"我的 entity 分布特性是什么"。Casey 的 entity 分布均匀(墙都是 16 像素),uniform grid 最优。如果你的游戏 entity 大小差 1000×(飞船 vs 子弹),quadtree 更好。

### 3.2 · 🎨 图形学视角

图形学的"剔除(culling)"也是空间划分:

- **Frustum culling**:相机视野是一个 frustum(平截头体),只画 frustum 内的物体。用 BVH 加速——从根节点开始,如果节点的 AABB 完全在 frustum 外,跳过整棵子树。
- **Occlusion culling**:被前面的物体挡住的物体不画。Hi-Z buffer 算法用 mipmap pyramid 做空间划分。
- **Light culling**:每个光源只照亮一定半径,用空间网格找"光源半径内的物体"。
- **Tiled shading**(deferred rendering):把屏幕分成 16×16 tile,每个 tile 记录"影响这个 tile 的光源列表"。这是空间网格在 GPU 上的应用。

Phase 5(OpenGL)+ Phase 6(光照)会大量用空间划分。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核**到处**用空间划分:

- **页表(page table)**:多级页表就是空间划分。虚拟地址按 bit 分段(9+9+9+9+12),每段索引到一层页表。等价于"嵌套的网格"——粗网格定位 PDPT,细网格定位 PDE,再细定位 PTE。
- **Buddy allocator**(物理页分配器):把物理内存按 2 的幂分成块(4K, 8K, 16K, ..., 4M),用空间划分加速"找一个 N 字节的空闲块"。
- **SLAB allocator**(小块分配器):每种 size class 一个 slab 池,等价于"按大小分格子"。
- **CFQ / BFQ I/O 调度器**:按进程分 I/O 队列,等价于"按 owner 分格子"。
- **cgroup**:把进程按 group 分,资源按 group 限制——空间划分在资源管理上的应用。

**启示**:空间划分是一种**通用思想**——"先把全集合按某个维度分桶,再在桶内精细操作"。Casey 教你的不只是游戏技巧,是一种普适的工程思维。

### 3.4 · 🦀 Rust 生态视角

Rust 表达空间划分有几个 crate:

- `rstar`(R*-tree):2D / 3D,适合动态点和矩形
- `kd-tree`:静态点集的最近邻查询
- `grid`(简单 uniform grid)
- `bucketed_hash_table`(类似 spatial hash)

**用 crate vs 手写**:
- 教学阶段(Phase 1-2):手写,理解每一行
- 生产阶段(Phase 4+):用 crate,但**理解它的实现**(读源码),不要黑盒

#### Ownership 挑战:Entity 在 grid 和 entities 列表两边

最常踩的 Rust 坑:

```rust
// 错误!grid 和 entities 都持有 entity 数据,借用冲突
struct World {
    entities: HashMap<EntityId, Entity>,
    grid: SpatialGrid,  // 内部是 HashMap<(i32,i32), Vec<&Entity>>  // ← 引用!
}
```

`grid.cells` 里的 `Vec<&Entity>` 引用 `entities` 里的 Entity。如果 entities 改了(grid rebuild 时),grid 里的引用就悬空。Rust 编译器拒绝。

**解决方案:存 ID,不存引用**:

```rust
type EntityId = u32;

struct SpatialGrid {
    cells: HashMap<(i32, i32), Vec<EntityId>>,  // ID,不是 &Entity
    cell_size: f32,
}

struct World {
    entities: HashMap<EntityId, Entity>,  // Entity 数据的唯一所有者
    grid: SpatialGrid,                     // 只存 ID
}

// 查询
fn query_nearby_entities(world: &World, pos: Vec2) -> Vec<&Entity> {
    world.grid.query_nearby(pos)
        .into_iter()
        .filter_map(|id| world.entities.get(&id))
        .collect()
}
```

这就是**ID-based reference**(基于 ID 的引用)。Rust 游戏开发的标准模式。

**好处**:
- entities 是数据的唯一 owner,grid 只引用 ID
- ID 是 `u32`(4 字节),比 `&Entity`(8 字节)小
- ID 可以序列化(保存到磁盘),引用不行
- hot reload 时 ID 不变(下一集 deep-dive)

**坏处**:
- 每次访问要 `entities.get(&id)` 一次 hash 查询(~50 ns)
- 不能用引用的 `*` 操作,要写 lookup

这是 Rust 游戏开发**最重要的模式之一**,记住它。

## 5 · 对照与变奏

### Quadtree vs Uniform Grid

**Uniform Grid**:
```
+--+--+--+--+--+
|  |  |E |  |  |
+--+--+--+--+--+
|  |  |  |  |  |
+--+--+--+--+--+
|E |  |  |  |E |
+--+--+--+--+--+
```
固定大小格子,entity 按位置放进去。

**Quadtree**:
```
+-------+-------+
|       |   E   |
|   E   +---+---+
|       | E |   |
+---+---+---+---+
|   |   |       |
+---+---+       |
|       |       |
+-------+-------+
```
递归分割,密集区域分得更细。

**何时 quadtree 更好**:entity 在某些区域密集,其他区域稀疏(比如 RPG 的城市 vs 野外)。uniform grid 在野外浪费(很多空格子),在城市不够细(一格塞几百 entity)。Quadtree 自适应。

**何时 uniform grid 更好**:entity 分布均匀(比如俄罗斯方块,或者 HH 这种 tile-based 世界)。Quadtree 实现复杂,白白增加代码量。

### Hash Grid vs Array Grid

**Array Grid**:`cells: Vec<Vec<Vec<EntityId>>>`,二维数组
- 优点:O(1) 查询(array index 比 hash 快 20 倍)
- 缺点:需要确定世界大小;空格子浪费内存
- 适合:有界小世界(比如棋盘)

**Hash Grid**:`cells: HashMap<(i32, i32), Vec<EntityId>>`
- 优点:无限大;稀疏高效
- 缺点:每次查询 ~50 ns(hash)
- 适合:虚拟化大世界(HH Day 33+)

Casey 选 Hash Grid,因为他的世界是无限大的(虚拟化)。但 sim region 内(几百个格子)其实可以用 array 加速——Phase 4 性能优化阶段会讨论。

### 历史演化

- **1970s**:游戏 tile map 本身就是 uniform grid(每个 tile 是一个格子)
- **1980s**:quadtree 出现在 GIS 和图像压缩
- **1990s**:BVH 在 3D raytrace 普及,Quake 用 BSP
- **2000s**:物理引擎(Box2D, PhysX)用 SAP 和 dynamic AABB tree
- **2010s**:GPU 上 tiled shading,空间划分搬到 shader

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:case_size 设成 1 像素 vs 10000 像素,各有什么问题?

**参考解答**:
- **cell_size = 1**:每个 entity 跨几百个格子(玩家 16 像素 = 跨 16 个格子),需要把 entity 注册到每个格子。HashMap 里有几百万 entry,内存爆炸,hash 也慢。查询从 9 个格子变成"几十×几十 = 几千"个,退化。**cell_size 太小 = 网格碎裂**。
- **cell_size = 10000**:所有 entity 在同一个格子里(世界大小通常 < 10000),查询要扫所有 entity,等于没划分。**cell_size 太大 = 网格退化成"一个桶"**。
- **最优 cell_size ≈ 查询半径**:9 个邻居恰好覆盖查询范围,每个格子 entity 数适中(1-10)。Casey 选 16(tile size),因为查询半径约一个 tile。

### Lv2 · 动手实践

**参考解答**:

```rust
use std::collections::HashMap;
use std::time::Instant;

type EntityId = u32;

#[derive(Clone, Copy, PartialEq, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn add(self, o: Self) -> Self { Self { x: self.x + o.x, y: self.y + o.y } }
    fn sub(self, o: Self) -> Self { Self { x: self.x - o.x, y: self.y - o.y } }
}

#[derive(Clone, Copy, PartialEq)]
enum EntityKind { Player, Wall }

#[derive(Clone, Copy)]
struct Entity {
    pos: Vec2, half: Vec2, kind: EntityKind,
}

struct SpatialGrid {
    cells: HashMap<(i32, i32), Vec<EntityId>>,
    cell_size: f32,
}

impl SpatialGrid {
    fn new(cell_size: f32) -> Self {
        Self { cells: HashMap::new(), cell_size }
    }
    fn cell_coord(&self, pos: Vec2) -> (i32, i32) {
        ((pos.x / self.cell_size).floor() as i32,
         (pos.y / self.cell_size).floor() as i32)
    }
    fn insert(&mut self, pos: Vec2, id: EntityId) {
        let c = self.cell_coord(pos);
        self.cells.entry(c).or_default().push(id);
    }
    fn query_nearby(&self, pos: Vec2) -> Vec<EntityId> {
        let (cx, cy) = self.cell_coord(pos);
        let mut r = Vec::new();
        for dx in -1..=1 {
            for dy in -1..=1 {
                if let Some(ids) = self.cells.get(&(cx + dx, cy + dy)) {
                    r.extend_from_slice(ids);
                }
            }
        }
        r
    }
}

struct World {
    entities: Vec<Entity>,
    grid: SpatialGrid,
}

impl World {
    fn new() -> Self {
        let mut entities = vec![];
        // 玩家
        entities.push(Entity { pos: Vec2::new(50.0, 50.0), half: Vec2::new(8.0, 8.0), kind: EntityKind::Player });
        // 5000 个墙,铺 50×100
        let mut id = 1u32;
        for ty in 0..100 {
            for tx in 0..50 {
                if tx == 0 || tx == 49 || ty == 0 || ty == 99 {
                    entities.push(Entity {
                        pos: Vec2::new(tx as f32 * 16.0, ty as f32 * 16.0),
                        half: Vec2::new(8.0, 8.0),
                        kind: EntityKind::Wall,
                    });
                    id += 1;
                }
            }
        }
        Self {
            entities,
            grid: SpatialGrid::new(16.0),  // cell_size = tile size
        }
    }

    fn rebuild_grid(&mut self) {
        self.grid.cells.clear();
        for (id, e) in self.entities.iter().enumerate() {
            self.grid.insert(e.pos, id as EntityId);
        }
    }

    fn move_player(&mut self, dx: f32, dy: f32) {
        self.entities[0].pos = self.entities[0].pos.add(Vec2::new(dx, dy));
        self.resolve_player_collision();
    }

    fn resolve_player_collision(&mut self) {
        let player_id = 0u32;
        let player_pos = self.entities[0].pos;
        let player_half = self.entities[0].half;
        let mut new_pos = player_pos;

        // 用 grid 缩小候选集
        let candidates = self.grid.query_nearby(player_pos);
        for id in candidates {
            if id == player_id { continue; }
            let e = self.entities[id as usize];
            if e.kind != EntityKind::Wall { continue; }
            let dx = new_pos.x - e.pos.x;
            let dy = new_pos.y - e.pos.y;
            let ox = (player_half.x + e.half.x) - dx.abs();
            let oy = (player_half.y + e.half.y) - dy.abs();
            if ox > 0.0 && oy > 0.0 {
                if ox < oy { new_pos.x += dx.signum() * ox; }
                else { new_pos.y += dy.signum() * oy; }
            }
        }
        self.entities[0].pos = new_pos;
    }
}

fn main() {
    let mut world = World::new();
    world.rebuild_grid();

    let start = Instant::now();
    for _ in 0..60 {
        world.move_player(0.0, -2.0);
        // 每帧重建 grid(简单做法,Casey 也这么做)
        world.rebuild_grid();
    }
    let elapsed = start.elapsed();
    println!("60 frames with 5000 entities: {:?}", elapsed);
    println!("per frame: {:?}", elapsed / 60);
    println!("player final pos: {:?}", world.entities[0].pos);
    assert!(world.entities[0].pos.y >= 16.0, "player should hit bottom wall");
    println!("OK");
}
```

**关键代码点**:
- `cell_size = 16.0`:等于 tile size,case 大小合适
- 每帧 `rebuild_grid`:全量重建,简单但有 N 次 hash。N=5000,每次 ~50 ns = 250 µs,可接受
- `query_nearby`:返回 9 个格子的 entity ID 列表,通常 ~10 个
- 用 `id as EntityId` 把 Vec 下标当 ID——简单,但删除 entity 后会失效。生产代码用 HashMap<EntityId, Entity>

## 8 · Rust / Arch 落地代码

### 关键 Rust 特性

#### 1. HashMap 的 entry API

```rust
self.cells.entry(c).or_default().push(id);
```

`entry()` 返回 Entry enum,可能是:
- `Entry::Occupied(o)` —— key 存在,可以 `o.into_mut()` 拿可变引用
- `Entry::Vacant(v)` —— key 不存在,可以 `v.insert(value)` 插入

`or_default()` 等价于"如果 Occupied 就拿引用,如果 Vacant 就 insert Default::default() 然后拿引用"。对 `Vec<_>`,default 是空 vec。

替代写法:
```rust
// 啰嗦版
if !self.cells.contains_key(&c) {
    self.cells.insert(c, Vec::new());
}
self.cells.get_mut(&c).unwrap().push(id);
```

`entry()` 是 Rust 惯用,因为只查一次 hash。

#### 2. ID-based reference

```rust
type EntityId = u32;

struct World {
    entities: HashMap<EntityId, Entity>,  // 数据唯一所有者
    grid: SpatialGrid,                     // 只存 ID
}
```

Rust 游戏开发**必须掌握**的模式。避免 self-referential struct(World 同时持有 entity 数据和指向 entity 的引用,Rust 编译器拒绝)。

#### 3. floor vs as i32

```rust
(pos.x / self.cell_size).floor() as i32
```

为什么不直接 `(pos.x / cell_size) as i32`?因为 `as i32` 对负数是**截断**(`-1.5 as i32 = -1`),不是向下取整。`floor()` 才是正确的"哪个格子"——`(-1.5).floor() = -2.0`。

举例:cell_size = 16。entity 在 x = -1,应该属于格子 (-1, ?) 因为 `-1 / 16 = -0.0625,floor 后 = -1`。如果用 `as i32` 就变成 0,导致负坐标 entity 全跑到格子 0,炸掉。
