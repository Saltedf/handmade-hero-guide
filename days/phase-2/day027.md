# Day 027 · 探索式架构

> Casey 用整整一集不讲代码,讲一件事:**"不要预先设计"**。这听起来反工程师,却是他 30 年游戏开发总结出的核心方法论。Phase 2 后面 44 集每一集都在演示这套方法论——Casey 经常一集推翻上一集的设计,你看到的不是"教科书答案",而是"真实工程师如何思考"。

## 0 · 为什么要有这一天

很多新手跟做 Handmade Hero 时撞到一堵看不见的墙:他们能看懂 Casey 每一集的代码,但**自己写不出**。原因不是缺 Rust 知识或缺游戏开发经验,而是缺一种**思维模式**——Casey 怎么决定下一行写什么。

具体看看下面这几个常见困境:

- **困境 A**:你想加一个功能(比如"小人跳跃"),你**先去网上搜**"2D 平台游戏怎么实现跳跃"。看完 5 篇博客,你写了 200 行带"跳跃力曲线"、"土狼时间(coyote time)"、"缓冲输入"的代码。然后发现 Casey 在 Day 050 才简单加了一句 `if jump_pressed { vel.y = -200; }`,200 行只用了 1 行。你怀疑自己学错了。
- **困境 B**:你看 Casey 写的 `GameState`,字段少得可怜——`player_pos`、`monsters`、`world`。你心想"这怎么够用?是不是应该提前设计好 Inventory、Quest、Dialogue 这些字段?"。你预先加了 20 个字段,结果 Casey 在 Day 200 才用上 Inventory,你那 20 个字段早过期了。
- **困境 C**:你看 Casey 经常说"这个函数名字不好,改一下"。你心想"为什么不一开始就想好名字?"。你预先取了"完美"的名字,结果后面 Casey 改设计时你的名字反而成了阻碍。

这些困境的**根因都是一个**:**你想用"预先设计"对抗"未知"**。但游戏的本质是探索——你不知道玩法好不好玩,直到玩家试;你不知道代码该怎么写,直到你写完发现哪里别扭。预先设计就是在你**还不知道需求**的时候,把代码结构锁定。锁定后,你失去调整空间,新需求来了就要"推翻重写"或"硬塞进旧结构"——两条路都很痛苦。

Casey 提出"探索式架构"(Exploration-based Architecture):**先写最简单能跑的版本,玩一会儿,发现别扭的地方,针对别扭的地方重构,重复**。这看起来像"瞎写",但其实是**最高效的学习路径**——每一次重构都基于"已经踩过的坑",不是"想象的坑"。

心理锚点:看完这集,你应该能用一段话解释"为什么 Casey 反对 Big Design Up Front(BDUF,预先完整设计)",能说出 Rule of Three 和 YAGNI 这两个原则的精确含义。如果你做不到,先停在 §2 反复琢磨——这一集的方法论贯穿 HH 全剧 667 集。

## 1 · Casey 今天做了什么

Casey 这一天**没打开 IDE 写一行业务代码**,他在白板上做了一场关于"工程哲学"的演讲:

1. 抛出核心论点:**"过早设计是万恶之源"**(Premature design is the root of all evil,化用 Knuth 的"过早优化"名言)
2. 用三个反例说明 BDUF 的问题:过早抽象、过早优化、过早通用化
3. 提出"探索式架构"的四个步骤:**写最简版本 → 玩一会儿 → 找别扭 → 重构**——循环
4. 强调这和"瀑布模型 / BDUF"的关系:BDUF 适合**需求稳定**的领域(航天、医疗),游戏**需求本质上不稳定**,BDUF 不适用
5. 对比敏捷开发(Agile):敏捷是"探索式 + 团队协作",Casey 是"探索式 + 个人"——单人项目可以更激进地探索
6. 顺便教观众**怎么跟做 HH**:不要照抄 Casey(不动脑),也不要预先自己设计(失去学习 Casey 思路的机会),要**边抄边想"为什么他这么写,如果是我会怎么写"**

这集教学价值在 HH 全剧排前三。Casey 后面 600+ 集每一次重构都在演示这套方法论——你在 Day 027 立的心智锚,让你看后面的重构不会觉得"Casey 又在乱改",而是理解"他在针对踩到的坑调整"。

## 2 · 心智模型

### 类比:做菜不能预先决定一切

你做大厨的朋友做菜,他从不**预先**写完整菜谱。他会:

1. **先尝食材**:这个番茄酸不酸?这个辣椒辣不辣?
2. **试做小份**:炒一小撮,尝一下,缺什么补什么
3. **逐步调整**:觉得淡了加盐,觉得油了挤柠檬,觉得颜色不亮加点酱油
4. **形成最终菜谱**:多试几次,稳定下来,这时候才写菜谱

如果让他**预先**写完整菜谱,会发生什么?食材是新的(不像他试过的)、厨房温度不一样、客人喜好不确定——预写的菜谱一定不准,只能边做边改,菜谱反而成累赘。

软件也是这样。游戏开发尤其像做菜——**需求是不确定的**(玩家会喜欢这种玩法吗?),**实现细节是探索出来的**(这种数据结构 cache 友好吗?)。预先设计 = 还没尝食材就写菜谱 = 浪费。

### 反例 1:过早抽象(Premature Abstraction)

新手看到两个相似函数,本能想提取 trait:

```rust
// 错误的过早抽象
trait Drawable {
    fn draw(&self, buf: &mut FrameBuffer);
}

struct Player { ... }
struct Monster { ... }

impl Drawable for Player { fn draw(&self, buf: &mut FrameBuffer) { /* 略 */ } }
impl Drawable for Monster { fn draw(&self, buf: &mut FrameBuffer) { /* 略 */ } }
```

看起来不错?但你后续发现 Player 的 `draw` 还要处理**朝向**(左右翻转贴图),Monster 的 `draw` 还要处理**血量条**(低血量变红)。两个 `draw` 函数越走越远,trait 强行统一的接口反而成了累赘——你只能在 trait 里加 `fn draw(&self, buf: &mut FrameBuffer, ctx: &DrawContext)`,然后 ctx 里塞各种字段,最后 ctx 变成大杂烩。

**Rule of Three**(三次法则):**等到第三次重复再抽象**。一两次相似不抽象,留点重复。第三次出现时,你已经看清共同点和差异点,这时候提取的抽象**正好覆盖实际需求**,不会过度。

Casey 在 HH 里反复演示:Phase 2 的 Player / Monster 都是独立 struct,不抽 trait。Day 350+ 才出现"批量渲染实体"的真正需求,这时候抽象一个 trait(或 ECS system),刚好。

### 反例 2:过早优化(Premature Optimization)

Knuth 1974 年的名言:"Premature optimization is the root of all evil"(过早优化是万恶之源)。Casey 这集引用并扩展为"过早设计也是万恶之源"。

新手看到 hot loop(热路径),本能想 SIMD:

```rust
// 错误的过早优化
use std::arch::x86_64::*;
fn sum(xs: &[f32]) -> f32 {
    unsafe {
        let mut acc = _mm_setzero_ps();
        for chunk in xs.chunks(4) {
            let v = _mm_loadu_ps(chunk.as_ptr());
            acc = _mm_add_ps(acc, v);
        }
        // ... horizontal sum
    }
}
```

但你这个数组只有 **10 个元素**。SIMD 加载/存储开销(几纳秒)比加速省下的时间还多——SIMD 比 scalar 慢。

正确做法:**先写最朴素的 `xs.iter().sum()`**,用 profiler 测,如果这个函数真是瓶颈,再上 SIMD。99% 的代码不是瓶颈,预先优化 = 浪费时间 + 代码变难读。

Casey 在 HH 全剧贯彻这个原则:**Day 1-200 写最朴素的标量版本,Day 200+ 才用 profiler 找瓶颈,针对瓶颈 SIMD**。学完整个 HH 你看到的是"数据驱动优化"的标准流程。

### 反例 3:过早通用化(Premature Generalization)

新手喜欢"通用化"。比如要写一个"读 BMP 文件"的函数:

```rust
// 错误的过早通用化
fn load_image<T: PixelFormat, R: Read>(reader: R, format: T) -> Image<T> { ... }
```

支持**任意像素格式**(RGBA / RGB / BGR / 16-bit / Float)+ **任意输入流**(File / Network / Memory)。结果函数签名复杂到没人能正确调用,任何小改动都要改 trait、改 impl、改泛型约束。

**YAGNI**(You Aren't Gonna Need It,你不需要它):**先只支持现有需求**。Casey 的 load_bmp:

```rust
// 正确:只支持现有需求
fn load_bmp(path: &str) -> Bitmap { ... }
```

简单直接。等以后真有"从网络读 BMP"的需求,再重构——这时候你知道**真实**的需求是什么,不会过度抽象。

### 探索式架构的四个步骤

Casey 总结的流程:

```
┌────────────────────────────────────┐
│  1. 写最简单能跑的版本              │
│     (用最直接的方法,不考虑扩展性)  │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│  2. 玩一会儿 / 用一会儿             │
│     (发现问题,体验别扭)            │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│  3. 针对最别扭的地方重构            │
│     (哪里痛改哪里,不预先改别处)    │
└──────────────┬─────────────────────┘
               ▼
┌────────────────────────────────────┐
│  4. 重复 1-3                        │
└────────────────────────────────────┘
```

**关键约束**:第 3 步只针对**已经踩到的坑**重构,不针对**想象中未来可能踩到的坑**。这是和 BDUF 的核心区别。

### 探索式不是"瞎写"

新手听到"探索式"会误解为"乱写代码不用思考"。**完全不是**。

Casey 在 HH 里**预先设计的部分**:

- 平台 / 游戏分离(Day 011)
- 三明治分层(Day 026)
- GameState 用 Vec<Entity> 而不是 LinkedList
- Vec2 用 f32 而不是 f64
- 内存对齐到 16 字节

这些都是"核心不变量"——**一旦定下来,后续 600 集不改**。Casey 不预先设计的部分:

- 具体的 Entity 字段(加什么字段看需求)
- 具体的渲染 API(先用 framebuffer,Day 235 才换 OpenGL)
- 具体的资产格式(先用 BMP,Day 436 才上 PNG)
- 具体的算法实现(先用 O(n²),profiler 说慢才优化)

区分原则:**架构性的、改一次伤筋动骨的**(如分层、坐标系方向、数据布局)**预先设计**;**实现性的、改一次只影响局部的**(如某个函数怎么写、用什么数据结构存小东西)**探索式**。

这个区分很难,**只能靠经验**。HH 的价值就是让你看 Casey 怎么做这种区分——667 集的样本足够你建立直觉。

### 跟做 HH 的正确姿势

Casey 在这集最后给观众的建议:

| 错误姿势 | 后果 |
|---|---|
| 照抄不动脑 | 学不到"为什么",换个项目就懵 |
| 预先自己设计 | 错过 Casey 的思路,自己设计的版本可能跑偏 |
| 边抄边想"为什么" | ✅ 正确:理解 Casey 的"问题 → 决策"链路 |

具体操作:

1. 看 Casey 这集做什么(理解他的目标)
2. **暂停视频**,自己想"如果是我,会怎么实现"
3. 想个大概,**不要写代码**(否则容易陷入自己的实现细节)
4. 继续 Casey 视频,看他的实现
5. **对比**:你的方案和 Casey 的差异在哪?谁的更好?为什么?
6. 在你的 Rust 项目里实现(可能参考 Casey 的 C,也可能用你自己的方案)
7. commit,记录"这集学到了什么"

这套流程的核心是**对比思维**——你的方案和 Casey 的差异,正是你学习的机会。即使你的方案更好(偶尔会),你也能理解 Casey 的取舍。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发圈对"探索式 vs BDUF"的态度几乎是**一边倒支持探索式**。原因:

1. **游戏本质是体验设计**:玩家感受决定一切,但玩家感受**不可预测**。你设计了一个"完美"的战斗系统,玩家可能觉得"无聊"——这种反馈只能通过试玩得到。
2. **技术风险高**:图形学、物理、AI 都有未知——你的阴影算法在真实场景下可能跑不动。预先设计 100% 完美方案是不可能的。
3. **市场压力**:游戏发售日是固定的(圣诞节、暑期档),延期成本高。BDUF 假设"设计完了再实现",但游戏项目往往**永远设计不完**,直接进入"无限延期"陷阱。

但游戏开发也不能完全没设计。主流做法是 **"垂直切片"(Vertical Slice)**:

- 早期花 2-3 个月做一个**完整的小关卡**(从开始到结束),所有系统都跑通
- 通过这个小关卡验证:玩法好不好玩?技术能不能行?
- 验证通过后,扩展到完整游戏——这时候才有"BDUF"的基础

HH 是单人教学项目,**Casey 本人就是垂直切片**——他每天做一小块,逐步拼出完整游戏。你跟做的过程,本身就是探索式架构的演示。

**反例:一些失败的项目**

- **Star Citizen**(2012-):典型的 BDUF 失败案例。预先设计"宇宙级 MMO",15 年还在 alpha
- **Duke Nukem Forever**(1997-2011):每次有新技术就推翻重做,14 年才出,口碑崩盘
- 对比 **Minecraft**(2009-2011):Notch 几周做一个最简版本,玩家反馈驱动开发,2 年成现象级

### 3.2 · 🦀 Rust 生态视角

Rust 社区对"探索式 vs BDUF"的态度微妙。Rust 的类型系统**鼓励**预先设计:

- Trait 设计:Rust 的 trait 比 Java interface 更严格(associated type、generic bound),改 trait 影响大,**鼓励预先想清楚**
- Ownership 设计:Rust 的所有权让"循环引用"无法直接表达,你必须预先想清楚谁拥有谁

但 Rust 也**支持**探索式:

- `unwrap()` / `todo!()` / `unimplemented!()` —— 让你"先跑通,后补错误处理"
- `#[allow(dead_code)]` —— 临时容忍未使用代码
- Cargo 的 `examples/` 和 `tests/` —— 快速试验新 API 不污染主代码
- Rust 的重构工具(`rust-analyzer` 的 rename、extract function)很强,大幅降低重构成本

**Rust 探索式的最佳实践**:

1. **第一阶段(Phase A)**:大量用 `unwrap()` / `clone()`,先跑通逻辑
2. **第二阶段(Phase B)**:用 profiler / `cargo clippy` 找热点和坏味道
3. **第三阶段(Phase C)**:针对热点优化(去掉不必要的 `clone`、改用 `Cow<str>`、加 SIMD)

这种"先跑通再优化"和 Casey 的方法论完全一致。

**反模式:Rust 新手的"过度泛型"**

```rust
// 过度泛型(过度抽象)
fn process<T: Clone + Send + Sync + 'static, F: FnMut(&T) -> Option<T>>(
    items: impl Iterator<Item = T>,
    mut f: F,
) -> impl Iterator<Item = T> { ... }
```

Rust 让"过度抽象"变得**特别容易**(trait bound 太灵活)。新手写完发现没人(包括自己)调用得舒服,改起来 trait 一改连带所有 impl 都要改。YAGNI 在 Rust 里尤其重要。

### 3.3 · Linux 系统编程视角

Linux 内核开发的"探索式"和"BDUF"平衡:**核心 API 极度 BDUF,实现细节探索式**。

Linux 的核心 syscall 接口(open / read / write / mmap / fork / exec)从 1991 年到 2025 年**几乎没有变化**——这是 BDUF。但具体文件系统(ext4 / btrfs / xfs)、调度器(CFS / EEVDF)、内存管理的实现一直在演化——这是探索式。

Linus 的著名原则:**"Never break userspace"**(永远不破坏用户态)。这就是 BDUF 部分——一旦 syscall 接口定下来,后面几十年不能改。这迫使内核开发者**预先设计 syscall 接口时极度谨慎**。

对比游戏开发:Casey 的"平台 / 游戏分离"也是这种 BDUF——一旦定下来,Day 026-667 不改。但具体游戏逻辑是探索式。

Arch Linux 用户应该熟悉 AUR 的"探索式"——大量包是社区快速试验的,好的被收录到 official repo,差的被淘汰。这就是"演化"。

### 3.4 · 软件工程方法论视角

主流软件开发方法论的"探索程度"光谱:

```
最 BDUF ◄─────────────────────────────────────────► 最探索式

瀑布模型 ─ Spiral ─ RUP ─ Scrum ─ XP ─ Lean ─ Casey HH
         (Boehm)         (Agile)
```

| 方法论 | 探索程度 | 适合 |
|---|---|---|
| 瀑布(Waterfall) | 极低 | 需求极稳定(航天、医疗) |
| Spiral(螺旋) | 中 | 大型企业项目 |
| Scrum | 较高 | 团队敏捷开发 |
| XP(极限编程) | 高 | 小团队 + TDD |
| Lean Startup | 极高 | 创业公司 |
| Casey HH | 极高(个人版) | 单人学习项目 |

Casey 的探索式接近 Lean Startup 的"build-measure-learn"循环,但**单人版**——没有团队协调成本,可以更激进地推翻重做。

**关键差别**:Casey 的探索式适合**学习项目**(目标是最大化学习),不适合**商业项目**(目标是稳定交付)。如果你做的是商业游戏,适度 BDUF(垂直切片、设计文档)能让团队协作更顺。

## 4 · 认知地图

### 4.1 上级

- **演化式架构**(Evolutionary Architecture)—— 架构随时间演化,不是一次性设计
- **YAGNI**(You Aren't Gonna Need It)—— 极限编程核心原则之一
- **敏捷开发**(Agile)—— 拥抱变化的开发方法论
- **经验主义**(Empiricism)—— 知识来自经验,不是先验推理

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| BDUF(Big Design Up Front) | 完整设计再编码 | 需求极稳定 | HH 不用(需求不定) |
| 探索式(Exploration) | 边做边设计 | 需求不确定 | ✅ Casey 选了 |
| TDD(Test-Driven) | 先写测试再写实现 | 接口稳定但实现可换 | HH 部分用(逻辑层) |
| Spiral Model | 多轮迭代,每轮风险分析 | 大型企业项目 | HH 不用(单人不需要) |
| Lean Startup | MVP + 用户反馈驱动 | 创业产品 | HH 精神接近但不是 |

### 4.3 下级

- **Rule of Three**(三次法则)—— 第三次重复才抽象
- **YAGNI** —— 不要预先加"可能用到"的代码
- **Refactoring**(重构)—— 不改外部行为地改内部结构
- **Profiler-driven optimization** —— 用 profiler 数据决定优化哪里,不靠猜
- **KISS**(Keep It Simple, Stupid)—— 简单方案优先

## 5 · 对照与变奏

### 同一原则在不同领域的变体

**"先尝后定"的原则无处不在**:

| 领域 | "BDUF"叫法 | "探索式"叫法 |
|---|---|---|
| 软件 | BDUF / 瀑布 | 敏捷 / 探索式 |
| 建筑 | 完整图纸再施工 | 设计-建造一体 |
| 写作 | 详细大纲再写正文 | 自由写作再编辑 |
| 做菜 | 完整菜谱再开做 | 边尝边调 |
| 科学研究 | 假设驱动(先假设再验证) | 探索性数据分析 |
| 教育 | 课程大纲先定 | 蒙特梭利式探索 |

这些领域的成功者大多用**混合策略**:核心不变量 BDUF,细节探索式。Casey 在 HH 里就是这种混合——平台/游戏分离 BDUF,具体实现探索式。

### 历史演化

- **1960s-1980s**:瀑布模型主导,软件工程模仿建筑工程
- **1990s**:Winston Royce(瀑布提出者)自己说"瀑布被误解了,我本来想说迭代",但已经晚了
- **2001**:敏捷宣言(Agile Manifesto),17 位软件大师签的,核心是"响应变化胜过遵循计划"
- **2010s**:Lean Startup(Eric Ries)把敏捷扩展到创业,MVP 概念普及
- **2020s**:Casey HH(2014-2023)成为"探索式游戏开发"的样本,被游戏开发圈反复引用

Casey 的方法论不是孤例,他是 30 年软件工程演化的产物。理解这个演化,你就理解为什么 Casey 反 BDUF——他不是反对"想清楚",他反对的是"在信息不足时假装想清楚"。

### 探索式的代价

探索式不是免费午餐。它的代价:

- **重写成本**:每次重构都花时间。Casey 在 HH 里花大量时间重构,占总时长 30%+
- **认知负担**:你不知道下一集 Casey 会不会推翻这集的设计,跟做者容易"挫败感"
- **不适合团队**:多人协作时,频繁重构需要大量沟通,团队项目用 BDUF + 迭代会更顺

所以 Casey 在这集最后说:**"这种风格适合学习项目,不适合你的公司项目"**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 反对 BDUF,但 HH 跑了 667 集没崩,从结果上看有某种"秩序"在维持。Casey 怎么平衡"探索"和"秩序"?Day 011 的平台/游戏分离算不算 BDUF?

**参考解答**:**Day 011 的架构是 BDUF,但只 BDUF 了"核心不变量"**。

Casey 的策略:**核心抽象预先设计,细节探索式**。

预先设计的核心(不变的):
- 平台 / 游戏分离(Day 011)
- 三明治分层(Day 026)
- Vec2 用 f32
- y 轴向下
- framebuffer 是 `[u32]`,每个 u32 是 `0x00RRGGBB`

这些是 BDUF,因为改一次伤筋动骨,后面 600+ 集都要跟着改。

探索式的细节(可改的):
- Entity 的具体字段
- 渲染 API(先 framebuffer,后 OpenGL)
- 资产格式(先 BMP,后 PNG)
- 算法实现(先 O(n²),后优化)

这些是探索式,因为改一次只影响局部。

区分原则:**改一次的"伤口大小"**。伤口大到伤筋动骨的(架构性的)BDUF,伤口小的(实现性的)探索式。这种区分能力靠经验——HH 667 集足够你建立直觉。

### Lv2 · 动手实践

**题**:找一个你最近写的 Rust 项目(任何项目都行,小到 50 行也行)。挑一个**你预先过度设计**的部分,按"探索式"原则重构。

完成标准:

1. 列出你过度设计的部分(具体哪个 trait、哪个泛型、哪个接口)
2. 解释为什么这是"过度设计"(实际只有 1-2 个 caller,但你预先支持了 10 个)
3. 重构成"最简单能跑的版本"
4. `cargo test` 通过

**参考解答**(假设你写了过度泛型的 `process` 函数):

过度设计版:
```rust
// 过度泛型:支持任何迭代器、任何映射函数
fn process<T, I, F>(items: I, mut f: F) -> Vec<T>
where
    I: IntoIterator,
    F: FnMut(I::Item) -> T,
{
    items.into_iter().map(|x| f(x)).collect()
}

// 实际只有这两处调用
let xs: Vec<i32> = process(vec![1, 2, 3], |x| x * 2);
let ys: Vec<String> = process(vec!["a", "b"], |s| s.to_uppercase());
```

重构版(YAGNI):
```rust
// 直接用标准库 map / collect,无需自定义 process
let xs: Vec<i32> = vec![1, 2, 3].into_iter().map(|x| x * 2).collect();
let ys: Vec<String> = vec!["a", "b"].into_iter().map(|s| s.to_uppercase()).collect();
```

**为什么这么改**:`process` 函数只是 `map + collect` 的包装,而 `Iterator::map` 和 `Iterator::collect` 已经是标准库的事——再包一层没有任何额外能力,反而增加阅读成本。Rule of Three 的反例:**只有 2 个 caller,且标准库已经做了这件事**,抽象无收益。

**题**:在 GitHub 上找一个**轻量级 Rust crate**(star 100-1000 范围,容易看懂源码),看它有没有"探索式架构"留下的痕迹。

1. 用 `gh search repos --language=rust --stars=100..1000` 找候选
2. 选一个感兴趣的(比如某个 CLI 工具、某个解析库)

6. 写一段总结:这个 crate 的演化路径是否符合"探索式"?哪些是预先设计的?哪些是探索后改的?

**示例**(不要照抄):

```
repo: https://github.com/xxx/yyy
提交样本:git log --oneline | head
  a3f4c5c refactor: replace custom error type with thiserror
  8b9e012 feat: add streaming support
  5f0d331 BREAKING CHANGE: rename Config::new to Config::default
  ...

分析:
  - "replace custom error type with thiserror":作者最初自己手写 error enum,
    后来发现 thiserror crate 更标准,改用——典型"探索式"重构
  - "add streaming support":新需求驱动,不是预先设计的——YAGNI 的胜利
  - "BREAKING CHANGE: rename":发现 new 和 default 重复,选 default——
    这就是"探索式 + 重构"

总结:这个 crate 严重倾向探索式。核心 trait 接口(就是文件 parse/serialize)
稳定不变,但具体实现细节(API 命名、error 类型、内存布局)演化多次。
```

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例:探索式的"先简后优"

下面这段代码演示"探索式"的典型流程:第一版用最朴素方式,第二版针对踩到的坑重构,第三版只在确实需要时再优化。

```rust
// src/main.rs
// cargo new --bin exploration_demo && cd exploration_demo

// ========================================
// 第一阶段:最简单能跑的版本
// 目标:统计字符串里每个单词出现次数
// ========================================
fn word_count_naive(text: &str) -> std::collections::HashMap<&str, u32> {
    let mut counts = std::collections::HashMap::new();
    for word in text.split_whitespace() {
        // entry().or_insert() 是 Rust 处理"键可能存在"的标准模式
        // entry 拿到 key 的"占位",or_insert 在 key 不存在时插入
        // 然后 we get a &mut u32,可以 += 1
        *counts.entry(word).or_insert(0) += 1;
    }
    counts
}

// ========================================
// 第二阶段:玩了一会儿,发现问题——大小写不一致
// "Hello" 和 "hello" 应该算同一个词,但当前实现分开统计
// 针对这个痛点重构
// ========================================
fn word_count_case_insensitive(text: &str) -> std::collections::HashMap<String, u32> {
    let mut counts = std::collections::HashMap::new();
    for word in text.split_whitespace() {
        // 把 word 转小写作为 key——注意这里要 String(拥有所有权),
        // 因为 to_lowercase 返回的新 String,不能引用原 text
        let key = word.to_lowercase();
        *counts.entry(key).or_insert(0) += 1;
    }
    counts
}

// ========================================
// 第三阶段:再用一会儿,发现还有问题——标点贴在单词上
// "hello," 和 "hello" 也应该算同一个词
// 注意:Casey 在 HH 里也是这种"针对新痛点小步重构"的模式
// ========================================
fn word_count_stripped(text: &str) -> std::collections::HashMap<String, u32> {
    let mut counts = std::collections::HashMap::new();
    for word in text.split_whitespace() {
        // trim_end_matches 去掉末尾的标点
        // chars().filter(char::is_alphanumeric).collect() 保留字母数字
        let cleaned: String = word.chars()
            .filter(|c| c.is_alphanumeric())
            .collect();
        if cleaned.is_empty() { continue; }  // 跳过纯标点
        let key = cleaned.to_lowercase();
        *counts.entry(key).or_insert(0) += 1;
    }
    counts
}

fn main() {
    let text = "Hello world! Hello, rust. World? Rust rust rust.";

    println!("Stage 1 (naive):");
    for (w, c) in word_count_naive(text) { println!("  {} => {}", w, c); }

    println!("Stage 2 (case-insensitive):");
    for (w, c) in word_count_case_insensitive(text) { println!("  {} => {}", w, c); }

    println!("Stage 3 (stripped):");
    for (w, c) in word_count_stripped(text) { println!("  {} => {}", w, c); }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn naive_separates_case() {
        let counts = word_count_naive("Hello hello");
        assert_eq!(counts["Hello"], 1);
        assert_eq!(counts["hello"], 1);  // 大小写分开
    }

    #[test]
    fn case_insensitive_merges_case() {
        let counts = word_count_case_insensitive("Hello hello");
        assert_eq!(counts["hello"], 2);  // 合并
    }

    #[test]
    fn stripped_removes_punctuation() {
        let counts = word_count_stripped("Hello, world! Hello.");
        assert_eq!(counts["hello"], 2);
        assert_eq!(counts["world"], 1);
    }
}
```

**Rust 特性解释**:

- `entry(key).or_insert(0)` —— `HashMap` 的标准模式。`entry` 返回一个枚举 `Entry`,可能是 `Occupied`(已有)或 `Vacant`(没有)。`or_insert(0)` 在 Vacant 时插入 0,然后两种情况都返回 `&mut V`。这让"先查再插"这件事一行写完,不需要 `match` 或 `if let`。
- `*counts.entry(key).or_insert(0) += 1` —— 解引用 + 自增。`or_insert` 返回 `&mut u32`,要先 `*` 解引用才能 `+= 1`。
- `word.to_lowercase()` 返回 `String`(不是 `&str`)。因为小写化可能产生新字符(德语 ß → ss),无法引用原字符串。这就是为什么 Stage 2 的 HashMap key 是 `String` 不是 `&str`——所有权变化。
- `chars().filter(|c| c.is_alphanumeric()).collect()` —— 这是 Rust 处理 unicode 的标准模式。`.chars()` 给 UTF-8 解码后的字符迭代器,`.filter` 留下字母数字,`.collect()` 聚合成 String。

### 探索式流程的 git commit 历史

在真实项目里,探索式开发的 git 历史大概长这样:

```bash
# 看一个真实 Rust 项目的演化
gh repo clone BurntSushi/ripgrep
cd ripgrep
git log --oneline | head -30

# 你会看到大量这种提交:
# a3f4c5c refactor: simplify ignore walker
# 8b9e012 feat: add --hidden flag
# 5f0d331 fix: handle non-UTF8 paths on Windows
# 9c1a8b0 BREAKING CHANGE: rename --invert to --line-regexp
# ...

# 这就是"探索式"的痕迹——
# 重构(refactor)、新功能(feat)、修 bug(fix)、推翻重做(BREAKING CHANGE)
# 交替出现,每条 commit 都针对一个具体的"踩到的坑"
```
