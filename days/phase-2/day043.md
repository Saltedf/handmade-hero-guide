# Day 043 · 运动方程

> Day 042 你把 `(x, y)` 绑成 Vec2,但小人在屏幕上还是不动。今天 Casey 写下游戏开发里最重要的两行代码:`vel += acc * dt; pos += vel * dt;`——这两行让方块从"位置"变成"运动"。

## 0 · 为什么要有这一天

回想 Day 029 玩家移动的代码:

```rust
let new_x = player.x + speed * dt;
```

你直接把"按键 → 位移"硬编码。这种代码做不出像样的游戏:

- **没有加速度**:按下右键,玩家瞬间满速。松开右键,瞬间停下。手感僵硬,像机器人。所有商业游戏(超级马里奥、塞尔达、Hollow Knight)的玩家移动都有"加速 → 巡航 → 减速"的曲线,这是手感的核心。
- **没有重力**:玩家不会跳,所有 2D 平台游戏都做不出来。
- **没有动量**:玩家撞到怪物不会被弹开,因为速度直接被按键控制。

要解决这些,你需要把"位置"和"按键"之间引入两层间接:**速度**和**加速度**。按键改的是加速度,加速度改的是速度,速度改的才是位置。这就是**运动方程**。

```
输入(按键) → 加速度(acc)→ 速度(vel)→ 位置
```

这条链路不是 Casey 发明的,是牛顿力学的基础。物理课你学过 `F = ma`(力等于质量乘加速度),`v = v₀ + at`(匀加速运动),`s = v₀t + ½at²`(位移公式)。今天 Casey 把这些公式**离散化**(因为游戏是逐帧的,不是连续时间)应用到游戏里。

Casey 在这集选 **Euler 积分**(最简单的数值积分):每帧 `vel += acc * dt; pos += vel * dt;`。两条赋值语句,几行代码,但能模拟出加速、减速、跳跃、抛物线。这是游戏物理的"你好世界"。

心理锚点:做完今天,你应该能调三个参数(加速度、最大速度、摩擦系数)让玩家"走路感觉轻"、"跑步感觉重"、"冰面感觉滑"——这就是**游戏手感**(game feel)的数学基础。如果你只让方块按速度匀速动,你的游戏永远不会"好玩"。

## 1 · Casey 今天做了什么

Casey 在 Day 043 的视频里做了三件事:

1. **给玩家结构体加 `dPlayer` 字段**(C 原版叫 `dP`,意思是 "delta P",即位移变化率 = 速度)。Vec2 类型。再加一个 `ddP`(delta delta P = 位移变化率的变化率 = 加速度)。
2. **改造输入处理**:之前输入直接改位置,现在输入改 `ddP`(加速度)。按右键 `ddP.x = +500`,松开 `ddP.x = 0`。
3. **写主循环里的积分**:`dP += ddP * dt; P += dP * dt;`。两条赋值,完成 Euler 积分。

Casey 还加了一个细节:**速度上限**(max speed)。按住右键加速度持续作用,理论上速度无限增加。但游戏里玩家有最大速度,超过就钳制。Casey 加了一行 `if dP.x > MAX_SPEED { dP.x = MAX_SPEED; }`。

视频里 Casey 没碰到数学难点,他反复试参数(加速度多大?最大速度多大?摩擦多大?)——这是**手感调参**,本质是数学参数化的设计。每个游戏的手感差异,大部分来自这三个数字。

## 2 · 心智模型

### 费曼类比:运动方程是"汽车的油门刹车"

你开一辆车,踩油门 → 车加速 → 速度变大 → 位置变化。松开油门 → 没有加速度 → 速度不变(理想无摩擦)→ 车匀速。踩刹车 → 反向加速度 → 速度变小 → 车减速。

这里三个量:

- **位置**(Position):车现在在哪
- **速度**(Velocity):车现在开多快,朝哪个方向
- **加速度**(Acceleration):油门踩多深,每秒速度变化多少

按键控制的是**加速度**(油门),不是速度。这点新手最容易搞错——他们写 `if right_pressed { player.x += 5; }`,这是"按键直接改位置",跳过了加速度层。正确的写法是 `if right_pressed { acc.x = +500; }`,然后让积分系统自动把 acc → vel → pos。

**为什么必须经过加速度层?** 因为加速度带来**惯性**(inertia)。你松开右键,加速度变 0,但速度不变,玩家继续滑行——这就是"手感"。如果直接改位置,松开键玩家瞬停,感觉僵硬。

### 严谨定义:微积分关系

**位置 p(t)** 是时间的函数。**速度 v(t)** 是位置的导数:`v(t) = dp/dt`(位置变化率)。**加速度 a(t)** 是速度的导数:`a(t) = dv/dt`(速度变化率)。

反过来:**位置是速度的积分** `p(t) = ∫v dt`,**速度是加速度的积分** `v(t) = ∫a dt`。

**符号积分**(数学课的版本):如果 `a = const`,`v(t) = v₀ + a·t`,`p(t) = p₀ + v₀·t + ½a·t²`。这是高中物理的"匀加速运动公式"。

游戏不做符号积分(公式复杂、不通用),我们做**数值积分**(numerical integration):把时间切成小段(每帧 dt),每段用近似公式更新。

### 数值积分:Euler 法

最简单的数值积分叫 **Euler 法**(以数学家欧拉命名)。核心思想:在每一段短时间 dt 内,假设速度 / 加速度不变,用线性近似。

```
当前帧:
    vel = vel + acc * dt   // 速度 = 旧速度 + 加速度 × 时间(从 a 算 v)
    pos = pos + vel * dt   // 位置 = 旧位置 + 速度 × 时间(从 v 算 p)
```

**注意更新顺序**:先算 vel(用 acc),再算 pos(用更新后的 vel)。这叫"显式 Euler"(explicit Euler)。如果反过来(先用旧 vel 算 pos,再更新 vel),叫"隐式 Euler",稳定性不同但近似。Casey 用显式。

**几何直觉**:Euler 法把曲线运动近似成"很多小段直线"。dt 越小,近似越准。60 FPS 时 dt = 1/60 ≈ 0.0167 秒,近似误差 < 1%,肉眼无感。

### 实例:跳跃的完整轨迹

玩家在 (0, 0),按跳跃键,初始速度 `vel = (0, -300)`(y 向上,屏幕坐标 y 向下,负值 = 向上)。重力加速度 `acc = (0, +800)`(向下)。

```
帧 0:  vel = (0, -300), pos = (0, 0)
       一步积分:
         vel += acc*dt = (0, -300) + (0, 800)*(1/60) = (0, -300+13.3) = (0, -286.7)
         pos += vel*dt = (0, 0) + (0, -286.7)*(1/60) = (0, -4.78)
帧 1:  vel = (0, -286.7), pos = (0, -4.78)
       积分:vel = (0, -273.3), pos = (0, -9.34)
帧 2:  vel = (0, -273.3), pos = (0, -9.34)
       积分:vel = (0, -260), pos = (0, -13.67)
...
帧 22: vel ≈ (0, -10), pos ≈ (0, -56)  ← 接近最高点
帧 23: vel ≈ (0, +3), pos ≈ (0, -56)   ← 速度变正(开始下落)
...
帧 45: vel ≈ (0, +300), pos ≈ (0, 0)   ← 落回起点
```

轨迹是**抛物线**。最高点出现在 `vel.y = 0` 那一帧。物理课的公式 `h_max = v₀² / (2g) = 300² / (2 × 800) = 56.25` 像素,Euler 积分因为逐帧近似,可能算出 55 或 56,误差 < 2%,可接受。

### 摩擦力:让停下来感觉自然

光加速度不够。如果只有加速度,你松开右键后玩家继续匀速运动(牛顿第一定律),永远不停。游戏里要加**摩擦**(friction):

```rust
// 每帧
if !right_pressed && !left_pressed {
    // 没按方向键,施加摩擦
    let friction = 0.85;  // 每帧保留 85% 速度
    vel.x *= friction;
    if vel.x.abs() < 5.0 {
        vel.x = 0.0;  // 太小直接归零,避免抖动
    }
}
```

**摩擦 = 0.85** 意味着每帧 vel 乘 0.85。一秒(60 帧)后 `0.85^60 ≈ 7e-5`,几乎为 0——玩家 ~0.5 秒内停下。

**摩擦调参决定手感**:

- 摩擦 = 0.5(强):玩家很快停下,感觉"沉"
- 摩擦 = 0.85(中):自然停下,主流手感
- 摩擦 = 0.98(弱):玩家滑行很久,感觉"冰面"
- 摩擦 = 1.0(无):永不停止,感觉"太空"

Hollow Knight、Celeste 这种平台游戏精心调摩擦,让"小跳 vs 大跳 vs 滑行"的手感完美。

### 加速度的瞬时 vs 持续

**瞬时加速度**(impulse,脉冲):某帧一次性改速度,不改加速度。例:跳跃按一次,`vel.y = -300`(直接改速度,不改 acc)。

**持续加速度**(continuous):每帧持续作用。例:重力 `acc.y = +800`,每帧都加。

游戏里两种都用:

```rust
// 跳跃(瞬时):按下跳跃键的瞬间
if jump_pressed && on_ground {
    vel.y = -300.0;  // 直接给一个向上速度
}

// 重力(持续):每帧
acc.y = 800.0;  // 永远向下

// 移动(持续 + 限速):按方向键
if right_pressed { acc.x = 500.0; }
else if left_pressed { acc.x = -500.0; }
else { acc.x = 0.0; }

// 限速
const MAX_SPEED: f32 = 200.0;
if vel.x > MAX_SPEED { vel.x = MAX_SPEED; }
if vel.x < -MAX_SPEED { vel.x = -MAX_SPEED; }
```

这种混合模型足够大部分 2D 游戏。

### 完整代码骨架

```rust
use crate::math::Vec2;

const GRAVITY: f32 = 800.0;       // 重力(像素/秒²)
const MOVE_ACCEL: f32 = 500.0;    // 移动加速度
const MAX_SPEED: f32 = 200.0;     // 最大水平速度
const JUMP_VEL: f32 = -300.0;     // 跳跃初速度(y 向上)
const FRICTION: f32 = 0.85;       // 摩擦系数(每帧保留比例)

#[derive(Default)]
pub struct Player {
    pub pos: Vec2,  // 位置
    pub vel: Vec2,  // 速度
    pub acc: Vec2,  // 加速度(每帧重置)
    pub on_ground: bool,
}

pub struct Input {
    pub left: bool,
    pub right: bool,
    pub jump_pressed: bool,  // 这一帧按下(不是按住)
}

impl Player {
    pub fn update(&mut self, input: &Input, dt: f32) {
        // === 1. 根据输入设置水平加速度 ===
        self.acc.x = 0.0;
        if input.right { self.acc.x = MOVE_ACCEL; }
        if input.left { self.acc.x = -MOVE_ACCEL; }

        // === 2. 重力 ===
        self.acc.y = GRAVITY;

        // === 3. 跳跃(瞬时改速度,不改 acc)===
        if input.jump_pressed && self.on_ground {
            self.vel.y = JUMP_VEL;
            self.on_ground = false;
        }

        // === 4. Euler 积分 ===
        self.vel += self.acc * dt;
        self.pos += self.vel * dt;

        // === 5. 限速 ===
        if self.vel.x > MAX_SPEED { self.vel.x = MAX_SPEED; }
        if self.vel.x < -MAX_SPEED { self.vel.x = -MAX_SPEED; }

        // === 6. 摩擦(没按方向键时)===
        if !input.left && !input.right {
            self.vel.x *= FRICTION.powf(dt * 60.0);  // 帧率无关
            if self.vel.x.abs() < 1.0 { self.vel.x = 0.0; }
        }
    }
}
```

**每段解释**:

1. **设置 acc.x**:按键映射到加速度。这是"输入 → 物理"的接口。
2. **重力**:每帧加。重力是常数(在地球表面)。
3. **跳跃**:不修改 acc,直接改 vel。这是瞬时动作。
4. **Euler 积分**:核心两行。
5. **限速**:防止无限加速。
6. **摩擦**:用 `powf(dt * 60.0)` 让摩擦和帧率无关——60 FPS 时 powf(1.0) = 0.85,30 FPS 时 powf(0.5) = √0.85 ≈ 0.92,等效"半帧摩擦"。

### Euler 积分的局限

Euler 法简单但**不完美**:

- **能量泄漏**:长时间运行,系统会逐渐获得或损失能量。轨道力学(行星绕恒星)用 Euler 会看到轨道椭圆逐渐变化。
- **不稳定**:对刚性系统(弹簧,撞球)Euler 可能爆炸(数值发散)。
- **精度**:O(dt) 误差。dt 减半,误差减半,但精度不如高阶方法。

**为什么游戏用 Euler?** 因为:

1. **短时模拟**:游戏物理几秒内不会显著发散
2. **dt 小**:60 FPS 时 dt = 0.0167,误差 < 1%
3. **简单**:两条赋值,容易实现和调试
4. **足够**:玩家看不出来

**什么时候升级?**

- **Verlet**:粒子系统、布料模拟(能量更稳定)
- **RK4**:轨道力学(Kerbal Space Program 用)
- **隐式 Euler**:刚性弹簧(更稳定)

Casey 全程用 Euler,直到 Day 274 物理专题才讨论替代。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业管"调加速度 / 速度 / 摩擦参数"叫 **game feel tuning**(手感调参)。这是资深游戏设计师的核心技能。

**经典案例**:

- **超级马里奥**:玩家按下右键,加速度逐渐升到最大速度(0.3 秒),松开逐渐减速(0.2 秒)。这个曲线就是马里奥"灵活但可控"手感的来源。
- **Hollow Knight**:玩家加速更快(0.1 秒),最大速度更高,摩擦极强——冲刺般的战斗手感。
- **Celeste**:玩家加速几乎瞬时(0.05 秒),给玩家精准控制感。摩擦也强,停止快。
- **Stardew Valley**:加速度慢(0.5 秒),摩擦弱,感觉"悠闲"。

**手感调参的工具化**:商业引擎(Unity、Unreal)提供"曲线编辑器"——你画一条曲线描述"按键时间 → 当前速度"的映射,引擎自动应用。Casey 的简单 Euler + 常数 acc 是这条曲线的最简版本(线性)。

#### 多帧率一致性

游戏可能在 30 FPS / 60 FPS / 144 FPS 不同设备上跑。同一个游戏在 144 Hz 显示器上不应该跑得更快(经典 bug)。

**Euler 积分自然处理这个**:每帧 dt 不同,但 `vel * dt` 算出的位移在相同时间内一致。

```
60 FPS:60 帧 × (vel * 1/60) = vel
144 FPS:144 帧 × (vel * 1/144) = vel
```

总位移相同。前提:**用 dt 而不是固定步长**。新手常犯的错误:

```rust
// 错误:固定步长,帧率不同结果不同
player.x += 5.0;  // 60 FPS 时每秒走 300,144 FPS 时每秒走 720
```

正确写法:

```rust
// 正确:用 dt
player.x += 300.0 * dt;  // 不管帧率,每秒走 300
```

**Half-Life 2 早期 bug**:游戏在 60 FPS 和 100 FPS 跳跃距离不同,玩家发现后用来 speedrun,叫 "bunny hopping"。Valve 后来修了。

### 3.2 · 🎨 图形学视角

运动方程在图形学里很少直接用——图形学关注"渲染",物理关注"演化"。但有几个交叉点:

**粒子系统**(particle system):粒子用 Euler 积分。每个粒子是,update 函数就是 Euler 两行。GPU shader 里大量做这个(并行成千上万粒子)。

**布料模拟**:Verlet 积分更适合。布料是一组质点 + 约束,Verlet 自然处理约束(碰撞、风)。

**骨骼动画**:不是物理模拟,是关键帧插值。但插值公式 `p = p0.lerp(p1, t)` 本质是位置积分的简化版(t 是归一化时间)。

**相机跟随**:相机用 lerp 平滑跟随玩家:`camera = camera.lerp(target, 0.1)`。这是离散低通滤波器(信号处理概念),让相机不会瞬间跳。

### 3.3 · 🐧 Linux 系统编程视角

Linux 工具链对运动方程的诊断:

```bash
# 1. 用 perf 看物理 update 的 CPU 占用
$ perf record -g ./target/release/mygame
$ perf report
# 看 update_player 是不是 hot path(应该是)

# 2. 用 valgrind 看内存访问模式
$ sudo pacman -S valgrind

# 看 cache miss,优化 Vec2 数组布局

```

**Linux 内核的运动方程?** 内核不直接用,但**调度器**(scheduler)用了类似思想:进程的"nice 优先级"是"加速度"(决定调度倾向),实际 CPU 时间是"位置"(累积效果)。CFS(Completely Fair Scheduler)维护每个进程的 vruntime(虚拟运行时间),按 vruntime 排序选下一个运行的进程。这是运动方程式的"积分"。

### 3.4 · 🦀 Rust 生态视角

#### Rust 写运动方程的注意事项

**所有权**:Player 持有 pos、vel、acc 三个 Vec2(各 8 字节,共 24 字节)。Player 不是 Copy(因为以后会加 String、Vec 等堆字段),所以传递用 `&mut Player`。

```rust
// 推荐:函数接收 &mut self
impl Player {
    pub fn update(&mut self, input: &Input, dt: f32) { ... }
}

// 调用
player.update(&input, dt);
```

**借用规则**:更新顺序很重要。如果你同时遍历多个 Player 并让它们互相作用(比如碰撞推开),需要小心:

```rust
// 错误:不能同时 &mut 多个 Player
for p1 in &mut players {
    for p2 in &mut players {  // 编译报错:已借用 players
        ...
    }
}

// 正确:用索引分离借用
let n = players.len();
for i in 0..n {
    for j in (i+1)..n {
        let (p1, p2) = players.split_at_mut(j);
        // ... 处理 p1[i] 和 p2[0]
    }
}
```

`split_at_mut` 是 Rust 标准库的工具,把切片分成两段,让你同时持有两段的可变借用。这是 Rust 解决"同时修改两个元素"的官方方案。

**常量声明**:`const GRAVITY: f32 = 800.0;` 在文件顶部声明,编译期常量。Rust 常量必须用大写,带类型注释。

**f32 操作**:`0.85_f32.powf(60.0 * dt)` —— `_f32` 后缀让字面量是 f32(默认 f64)。powf 是浮点幂运算。

#### 用 Rust 写单元测试

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_gravity_pulls_down() {
        let mut p = Player::default();
        p.vel = Vec2::new(0.0, 0.0);
        let input = Input::default();
        p.update(&input, 1.0 / 60.0);
        // 一帧后,重力让 vel.y 增加 GRAVITY*dt
        assert!((p.vel.y - 800.0 * (1.0/60.0)).abs() < 1e-6);
    }

    #[test]
    fn test_jump_initial_velocity() {
        let mut p = Player::default();
        p.on_ground = true;
        let mut input = Input::default();
        input.jump_pressed = true;
        p.update(&input, 1.0 / 60.0);
        // 跳跃给 vel.y = -300
        assert!((p.vel.y - JUMP_VEL).abs() < 1e-6);
    }

    #[test]
    fn test_friction_stops_player() {
        let mut p = Player::default();
        p.vel = Vec2::new(100.0, 0.0);
```

#### 性能:SIMD 加速 Euler

如果有几千个粒子,标量 Euler 慢。SIMD 一次处理 4 个 Vec2:

```rust
#[cfg(target_arch = "x86_64")]
fn update_particles_simd(particles: &mut [Particle], dt: f32) {
    use std::arch::x86_64::*;
    unsafe {
        let dt_v = _mm_set1_ps(dt);
        let gravity_v = _mm_set1_ps(GRAVITY);
        // 假设 particles 内存布局是 SoA(各字段分开数组)
        for chunk in particles.chunks_exact(4) {
            // 一次更新 4 个粒子的 vel.y(加重力)
            let vel_y = _mm_load_ps(...);
            let new_vel_y = _mm_add_ps(vel_y, _mm_mul_ps(gravity_v, dt_v));
            _mm_store_ps(..., new_vel_y);
        }
    }
}
```

## 4 · 认知地图

### 4.1 上级

- **数值积分** —— 用离散步骤近似连续微分方程的整套方法
- **牛顿力学** —— 经典物理的运动定律(F = ma)
- **微分方程** —— 描述变量如何随时间变化的数学
- **游戏物理引擎** —— Box2D、PhysX、Bullet,本质都是大规模 Euler/Verlet 求解器

### 4.2 同级(并行方案对比)

| 方案 | 复杂度 | 稳定性 | 精度 | 何时用 | 本项目选 |
|---|---|---|---|---|---|
| 显式 Euler | O(1)/步 | 低(能量泄漏) | O(dt) | 短时游戏物理 | ✅ Casey 选 |
| 半隐式 Euler | O(1)/步 | 中 | O(dt) | 弹簧、阻尼系统 | HH 部分用 |
| Verlet | O(1)/步 | 高(能量守恒好) | O(dt²) | 布料、粒子 | Day 274+ |
| Velocity Verlet | O(1)/步 | 高 | O(dt²) | 分子动力学 | 不用 |
| RK4(Runge-Kutta 4) | O(1)/步 × 4 | 高 | O(dt⁴) | 轨道力学 | Kerbal Space |
| 隐式 Euler | O(n)/步 | 极高(刚性) | O(dt) | 刚性弹簧 | HH 不用 |

详细对比:

- **显式 Euler**(Casey 用):`vel += a*dt; pos += vel*dt;`。简单,但对刚性系统不稳定。
- **半隐式 Euler**:`vel += a*dt; pos += vel*dt;`(注意 pos 用更新后的 vel)。Casey 实际写的就是这个,比纯显式稳定。
- **Verlet**:`pos_new = 2*pos - pos_old + a*dt²`。不显式存速度,适合约束系统。
- **RK4**:每步采样 4 次,精度 O(dt⁴) 但计算量 4 倍。轨道力学精度优先时用。

### 4.3 下级

- **加速度(acc)** —— 每帧重置,从输入算出
- **速度** —— 持续累积,加速度的积分
- **位置** —— 速度的积分,渲染时读
- **dt(帧时间)** —— 积分步长,60 FPS = 0.0167s
- **摩擦系数** —— 让速度自然衰减
- **最大速度限制** —— 防止无限加速
- **重力常数** —— 持续向下的加速度

## 5 · 对照与变奏

### 离散 vs 连续时间

数学课的运动方程是**连续时间**的:`v(t) = dp/dt`。游戏是**离散时间**:每帧一个 dt 步长。

**连续 → 离散**就是数值积分(Euler、Verlet 都是离散化方案)。**离散 → 连续**:dt → 0 时,Euler 收敛到真实微分方程。

**物理引擎的固定时间步**:Box2D 等引擎用 fixed timestep(固定 dt = 1/60),即使游戏渲染 30 FPS,物理仍然 60 Hz。这保证物理行为确定性(同样输入永远同样结果)。Casey 的简单版用可变 dt,debug 时会麻烦。

### 平台跳跃 vs 俯视角

**平台跳跃**(platformer,超级马里奥、Celeste):需要重力 + 跳跃。重力是核心,Y 轴是"运动"的主轴。

**俯视角**(top-down,塞尔达、HH 的游戏):没有重力。Y 轴是另一个水平方向,和 X 对称。Casey 的 HH 是俯视角,所以没有重力,只有水平移动的加速度 + 摩擦。但 Day 043 的运动方程还是适用,只是 `acc.y = 0`(没重力)。

**FPS 第一人称**:更复杂,因为相机+移动分离。但移动本身还是 Euler。

### 物理引擎 vs 游戏代码

**游戏代码直接写 Euler**(Casey 的方式):几行,完全可控,适合简单 2D 游戏。

**用物理引擎**(Box2D、PhysX、rapier):处理刚体、碰撞、约束、关节。复杂但通用,适合 3D 游戏。Phase 5+ Casey 不引入物理引擎,因为他要保持代码完全自写。

**用 ECS + 物理组件**(Bevy + bevy_rapier):现代 Rust 游戏的标配。组件化的好处是灵活组合。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Euler 积分先更新 vel 再更新 pos(显式 Euler),而不是反过来?如果反过来(隐式 Euler),会有什么不同?

**参考解答**:

**显式 Euler**(先 vel 后 pos):

```
vel_new = vel_old + acc * dt
pos_new = pos_old + vel_new * dt
```

**隐式 / 半隐式 Euler**(反过来):

```
pos_new = pos_old + vel_old * dt
vel_new = vel_old + acc * dt
```

差别看似微小(只差一帧的速度),但稳定性不同。

- **显式**:每帧用更新后的 vel 算 pos,等价于"用未来速度推位置"。能量可能轻微增加。
- **隐式**:用旧速度推位置,等价于"用过去速度推位置"。能量可能轻微减少(更稳定)。

**Casey 的实际代码**是半隐式(用更新后的 vel 推 pos),对游戏物理足够稳定。理论上,**弹簧系统**(stiff)用显式会爆炸(振幅指数增长),用隐式稳定。但游戏很少做刚性弹簧,所以 Casey 不操心。

**直觉**:谁先更新,谁的"新鲜度"更高。位置更新得更"新"意味着响应快(显式),反之稳定(隐式)。

### Lv2 · 动手实践

**题**:在你的 HH Rust 项目里实现完整的 Player 移动系统:

1. 定义 `Player { pos, vel, acc, on_ground }` 结构体
2. 定义 `Input { left, right, up, down, jump_pressed }`(支持 4 方向移动 + 跳跃)
3. 实现 `Player::update(&mut self, input: &Input, dt: f32)`
4. **没有重力**(HH 是俯视角),但有水平移动 + 摩擦
5. 写测试:模拟按住右键 1 秒,验证玩家移动了正确距离
6. (可选)在 main 里跑 100 帧循环,打印每 10 帧的位置,看加速曲线

完成标准:`cargo run` 打印位置序列,看到加速 → 巡航 → 减速曲线。

**参考解答**:

```rust
use crate::math::Vec2;

const MOVE_ACCEL: f32 = 800.0;   // 像素/秒²
const MAX_SPEED: f32 = 250.0;    // 像素/秒
const FRICTION: f32 = 0.85;      // 每帧保留比例(60 FPS 下)
const FRICTION_EPS: f32 = 5.0;   // 小于此值直接归零

#[derive(Default)]
pub struct Player {
    pub pos: Vec2,
    pub vel: Vec2,
    pub acc: Vec2,
}

#[derive(Default, Clone, Copy)]
pub struct Input {
    pub left: bool,
    pub right: bool,
    pub up: bool,
    pub down: bool,
}

impl Player {
    pub fn update(&mut self, input: &Input, dt: f32) {
        // 1. 根据输入算加速度(俯视角,4 方向)
        let mut ax = 0.0;
        let mut ay = 0.0;
        if input.right { ax += 1.0; }
        if input.left { ax -= 1.0; }
        if input.down { ay += 1.0; }
        if input.up { ay -= 1.0; }

        // 对角线归一化(不让斜走比直走快)
        let acc_dir = Vec2::new(ax, ay);
        if acc_dir.length_sq() > 1e-6 {
            let acc_dir = acc_dir.normalize();
            self.acc = acc_dir * MOVE_ACCEL;
        } else {
            self.acc = Vec2::ZERO;
        }

        // 2. Euler 积分
        self.vel += self.acc * dt;
        self.pos += self.vel * dt;

        // 3. 限速
        let speed_sq = self.vel.length_sq();
        if speed_sq > MAX_SPEED * MAX_SPEED {
            self.vel = self.vel.normalize() * MAX_SPEED;
        }

        // 4. 摩擦(没按键时)
        if ax.abs() < 1e-6 {
            let frame_friction = FRICTION.powf(dt * 60.0);
            self.vel.x *= frame_friction;
            if self.vel.x.abs() < FRICTION_EPS { self.vel.x = 0.0; }
        }
        if ay.abs() < 1e-6 {
            let frame_friction = FRICTION.powf(dt * 60.0);
            self.vel.y *= frame_friction;
            if self.vel.y.abs() < FRICTION_EPS { self.vel.y = 0.0; }
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_acceleration_then_cruise() {
        let mut p = Player::default();
        let input = Input { right: true, ..Default::default() };
        let dt = 1.0 / 60.0;

        // 模拟 1 秒
        let mut positions = Vec::new();
        for frame in 0..60 {
            p.update(&input, dt);
            if frame % 10 == 9 {
                positions.push(p.pos.x);
            }
        }

        // 加速 → 巡航曲线:位置增量应先大后稳
        let deltas: Vec<f32> = positions.windows(2)
            .map(|w| w[1] - w[0])
            .collect();
        // 前期加速度高,后期达到 MAX_SPEED 增量稳定
        // 总位移应该接近 MAX_SPEED * 1秒 = 250(近似,因为有加速期)
        assert!(p.pos.x > 100.0 && p.pos.x < 250.0,
                "expected 100 < x < 250, got {}", p.pos.x);
    }

    #[test]
    fn test_diagonal_not_faster() {
        let mut p = Player::default();
        let input_diag = Input { right: true, down: true, ..Default::default() };
        let input_horiz = Input { right: true, ..Default::default() };
        let dt = 1.0 / 60.0;

        let mut p1 = Player::default();
        let mut p2 = Player::default();
        for _ in 0..60 {
            p1.update(&input_diag, dt);
            p2.update(&input_horiz, dt);
        }

        // 对角线方向速度不该比水平快(归一化的效果)
        let speed_diag = p1.vel.length();
        let speed_horiz = p2.vel.length();
        assert!((speed_diag - speed_horiz).abs() < 5.0,
                "diag {} should equal horiz {}", speed_diag, speed_horiz);
    }
}
```

**关键决策解释**:

- **对角线归一化**:如果不归一化,按"右+下"时 `acc = (1, 1)`,长度 √2 ≈ 1.414 倍单方向。归一化让斜走和直走一样快。这是 2D 俯视角游戏的标准做法。
- **FRICTION.powf(dt * 60.0)**:帧率无关的摩擦。60 FPS 时 dt * 60 = 1,摩擦 = 0.85^1 = 0.85。30 FPS 时 dt * 60 = 2,摩擦 = 0.85^2 = 0.7225,等效"两帧累积"。这保证不管帧率,1 秒后摩擦效果一致。
- **测试用 windows(2)** 算位置增量,优雅地获取"速度近似"。

### Troubleshooting

**问题 1**:玩家瞬间从 0 加速到 1000+,飞出屏幕

原因:你忘了限速,或 dt 太大(比如 1.0 秒)。

修复:

- 加 MAX_SPEED 限制
- 检查 dt 是否正确(应该是 1/60 = 0.0167,不是 1.0)
- 在 main 里打印 dt 确认

**问题 2**:玩家朝左走,加速度算错

原因:`if right { ax += 1 }; if left { ax -= 1 }`,但如果同时按 right 和 left,ax = 0,但视觉上玩家以为"按了右"。这是设计选择,不算 bug。

**问题 3**:对角线移动比直走快

原因:没归一化。按"右+下"时 acc = (1, 1),长度 √2。

修复:加 `acc_dir.normalize()`(参考 Lv2 解答)。

**问题 4**:帧率不同(30 FPS vs 144 FPS)玩家跑得不一样快

原因:你用了固定步长 `vel.x += 5` 而不是 `vel.x += 5 * dt`。

修复:所有运动用 `vel * dt` / `acc * dt` 形式。
