
# Day 069 · 成对碰撞规则

> 玩家撞怪扣血、火球撞怪扣血、火球撞墙消失、玩家撞墙停下、怪和怪互相穿过……五种行为,本质是同一个碰撞事件按"两个 entity 的类型"派发到不同的处理函数。今天 Casey 把这些 `if` 抽成一张**类型对 → 行为**的表,游戏从此变成数据驱动:**加新 entity 类型只改表,不改碰撞代码**。

## 0 · 为什么要有这一天

到 Day 068 为止,你的碰撞检测代码大致是这样的:

```rust
fn on_collision(a: &mut Entity, b: &mut Entity) {
    if a.kind == Player && b.kind == Wall {
        stop_player_at_wall(a, b);
    } else if a.kind == Player && b.kind == Monster {
        damage(a, 10);
    } else if a.kind == Projectile && b.kind == Monster {
        damage(b, 20);
        destroy(a);
    } else if a.kind == Projectile && b.kind == Wall {
        destroy(a);
    } else if a.kind == Monster && b.kind == Wall {
        slide_along_wall(a, b);
    }
    // ... 几十个 else if
}
```

现在加一个新 entity 类型 `Fire`(火堆,碰到玩家扣血,碰到墙消失,碰到水消失)。你要:

1. 在所有 `if a.kind == ... && b.kind == ...` 链里**找到所有相关位置**,加新的 if 分支
2. 注意 `a, b` 的顺序——`(Fire, Player)` 和 `(Player, Fire)` 是不是都要处理?
3. 写完测试,看有没有遗漏

这种**控制流驱动的**碰撞规则有几大毛病:

- **散弹枪修改**:加一个类型,要改 N 处代码,漏一处就有 bug
- **顺序依赖**:`(Player, Wall)` 还是 `(Wall, Player)` 先匹配?顺序错了行为就错
- **不可视化**:整个规则集合藏在一长串 if/else 里,看一眼全貌需要把代码读完
- **不可热加载**:规则改一行要重新编译游戏

Casey 今天做的重构,把这一坨 if/else 变成一张表:

```rust
fn collision_rule(a: EntityKind, b: EntityKind) -> CollisionRule {
    match (a, b) {
        (Player, Wall)     => CollisionRule::Block,
        (Player, Monster)  => CollisionRule::Damage(10),
        (Projectile, Monster) => CollisionRule::Damage(20),
        (Projectile, Wall) => CollisionRule::Destroy,
        _ => CollisionRule::None,
    }
}
```

`match (a, b)` 是 Rust 的**模式匹配**——`(Player, Wall) =>` 读作"当 a 是 Player 且 b 是 Wall 时返回 Block"。这张表:

- **集中**:所有规则在一个函数里,一眼看全
- **无序**:match 的臂不依赖顺序(只要模式不重叠)
- **完整**:Rust 强制 match 穷尽所有可能(有 `_ =>` 默认),漏写编译器会警告
- **可扩展**:加 Fire 类型,只需在 match 里加 `(Fire, Player) => Damage(5)`,**碰不到任何其他代码**

**心理锚点**:看完这集,你应该能解释:

- 数据驱动 vs 控制流驱动的本质区别
- 为什么 `match (a, b)` 比一长串 if/else 更安全
- 怎么把碰撞规则外置成数据(配置文件),让策划不用改代码就能调
- 业界(Box2D / Unity / Unreal)怎么做同样的事

这是 Phase 2 接近尾声时一个重要的工程化练习。Day 070 的 Phase 2 收官就是把这种"集中规则"思想推广到整个代码库。

## 1 · Casey 今天做了什么

Day 069 的视频里 Casey 干了三件事:

1. **复现问题**:他展示现有代码——一长串 if/else 处理碰撞,然后说"我要加一个新怪物类型(飞行怪,能穿过墙),我必须改 4 处代码,这太蠢了"。
2. **重构为 match 表**:把所有 if/else 抽成 `collision_rule(a_kind, b_kind) -> CollisionRule` 函数。`CollisionRule` 是个 enum,有 `Block / Damage(i32) / Destroy / Push(f32) / None` 等变体。`on_collision` 函数变成:调用 `collision_rule` 拿到规则,再根据规则分发到 `apply_rule`。
3. **统一 a/b 顺序**:Casey 注意到 `(Player, Wall)` 和 `(Wall, Player)` 在物理上是同一碰撞,代码里要统一处理。他在 `collision_rule` 函数开头加规范化:

```c
if (order(a, b) > 0) { swap(&a, &b); }
// 现在 a.kind <= b.kind(按 enum 值排序),规则只写 (小, 大)
```

这一步是**消除对称重复**——你不写 `(Player, Wall)` 和 `(Wall, Player)` 两份,只写一份。

Casey 最后留了一个**思考题**:这张表能不能完全外置成数据(比如 JSON / Lua)?能,但他不打算现在做——"等真需要策划改规则再说"。这是 HH 的工程哲学:**先把代码内的数据结构弄对,真的需要外置时再外置**。

## 2 · 心智模型

### 类比:餐厅点菜

你开了一家餐厅,服务员要记每种客人和每种菜的搭配规则:

- 老人 + 牛排 → 切小块
- 小孩 + 牛排 → 切小块
- 老人 + 辣椒 → 不放辣
- 小孩 + 辣椒 → 不放辣
- 素食者 + 肉 → 拒绝

一种记法是:**每个客人走到厨房,厨房问"你是谁、点的什么菜",然后跑一长串 if 判断**——这是控制流驱动。

另一种记法是:**贴一张表在墙上**:

| | 牛排 | 辣椒 | 肉 |
|---|---|---|---|
| 老人 | 切小块 | 不放辣 | OK |
| 小孩 | 切小块 | 不放辣 | OK |
| 素食者 | 拒绝 | OK | 拒绝 |

服务员看一眼表就知道怎么办。**这张表是数据驱动**:加一个新菜(比如"鱼"),只需要在表里加一列;加一个新客人(比如"孕妇"),加一行。表本身是死的,改表的人不需要懂厨房代码。

游戏里的碰撞规则就是这张表。**类型 a 是行,类型 b 是列,单元格是行为**。

### 严谨原理:enum + match

Rust 的 enum 是**带数据的代数数据类型**(ADT)。`CollisionRule` 定义如下:

```rust
enum CollisionRule {
    None,                       // 不响应
    Block,                      // 阻挡(玩家停下)
    Destroy,                    // 销毁 a
    DamageBoth(i32),            // a 和 b 都扣血
    DamageA(i32),               // 只 a 扣血
    DamageB(i32),               // 只 b 扣血
    Bounce(f32),                // 反弹,系数
    Push(f32),                  // 推开
}
```

每个变体可以**带数据**:`Damage(10)` 表示"扣 10 血"。`Bounce(0.8)` 表示"反弹 80% 能量"。

`match` 是 Rust 的模式匹配:

```rust
match rule {
    CollisionRule::None => {},                              // 不做事
    CollisionRule::Block => block(a, b),                    // 调 block 函数
    CollisionRule::Damage(amt) => { a.hp -= amt; },         // 把 amt 解构出来
    CollisionRule::Bounce(k) => bounce(a, b, k),            // k 是反弹系数
    // Rust 强制穷尽——所有变体都要处理(或用 _ => 兜底)
}
```

**关键 Rust 特性**:match 是穷尽的——如果你加了 `CollisionRule::Teleport` 但忘了在 match 里处理,编译器报错 `non-exhaustive patterns`。这就是为什么 enum + match 比 if/else 安全:**编译器帮你检查完整性**。

### 双重 match:类型对 → 规则

碰撞规则的本质是**二元函数**:`f(EntityKind, EntityKind) -> CollisionRule`。

```rust
fn collision_rule(a: EntityKind, b: EntityKind) -> CollisionRule {
    match (a, b) {
        // (a_kind, b_kind) => rule
        (Player, Wall)        => CollisionRule::Block,
        (Player, Monster)     => CollisionRule::DamageB(10),  // b(怪)扣血?不对...
        // 等等,让我们想清楚 a 和 b 的角色
    }
}
```

**关键设计问题**:a 是谁,b 是谁?有两种约定:

**约定 A:a 是"主动方"**(攻击者、移动者),b 是"被动方"。`DamageB(10)` 意思是"被动方 b 扣 10 血"。但主动被动有时不明确(玩家撞怪,谁是主动?)。

**约定 B:统一排序**——保证 `a.kind ≤ b.kind`(按 enum 数值)。这样所有规则只写"小在大前"的形式。Casey 选这个。

```rust
fn collision_rule(mut a: EntityKind, mut b: EntityKind) -> CollisionRule {
    // 规范化:a.kind ≤ b.kind
    if (a as u32) > (b as u32) { std::mem::swap(&mut a, &mut b); }
    // 现在 a.kind ≤ b.kind,只写一半的规则
    match (a, b) {
        (Player, Wall)       => CollisionRule::Block,
        (Player, Monster)    => CollisionRule::DamageBoth(10), // 互相伤害
        (Projectile, Monster)=> CollisionRule::DestroyAandDamageB(20),
        (Projectile, Wall)   => CollisionRule::DestroyA,
        (Monster, Monster)   => CollisionRule::None,           // 怪和怪互穿
        (Wall, Wall)         => CollisionRule::None,           // 墙不动
        _ => CollisionRule::None,
    }
}
```

**注意**:`DamageBoth`、`DestroyAandDamageB` 这种命名暗示了 a 和 b 都受影响。规范化后 a 是较小 kind 的 entity,b 是较大 kind 的。怎么知道哪个是玩家哪个是怪?**调用 collision_rule 之前,你必须保留原始的 a, b 引用**,规范化只是为了查表。Casey 实际写法:

```rust
fn on_collision(world: &mut World, e1: EntityId, e2: EntityId) {
    let k1 = world.kind(e1);
    let k2 = world.kind(e2);
    let (rule, first, second) = if k1 <= k2 {
        (collision_rule(k1, k2), e1, e2)
    } else {
        (collision_rule(k2, k1), e2, e1)
    };
    // 现在 rule 是规范化后的,(first, second) 是对应的原始 entity
    apply_rule(world, rule, first, second);
}
```

### 数据驱动 vs 控制流驱动

**数据驱动**:把规则当成"数据"——可以是 enum + match(Rust 编译期),也可以是 `Vec<((Kind, Kind), Rule)>` 数组(运行期),还可以是 JSON 文件(配置期)。代码逻辑只是"查表 + 执行"。

**控制流驱动**:把规则当成"代码"——`if kind == X && other == Y { do_x_y() }`。

两者差别:

| 维度 | 控制流驱动 | 数据驱动 |
|---|---|---|
| 加规则 | 改代码 N 处 | 改 1 处(表里加一行) |
| 完整性检查 | 人工(易漏) | 编译器(match)/ 单元测试(表) |
| 可读性 | 一长串 if/else | 一张表 |
| 性能 | 分支预测差(if/else) | 表查 O(1) |
| 可热加载 | 否(要重新编译) | 是(如果表是数据文件) |
| 类型安全 | 弱(类型用 string 或 int) | 强(用 enum) |

游戏业界公认:**核心规则用 enum + match(强类型、性能好),策划可调规则用数据文件(灵活、热加载)**。Unity 的 Physics Material、Unreal 的 Collision Profile 都是后者——本质是一张数据表。

### 规则的复合

实际游戏里规则可能更复杂。比如:

- **攻击者等级**:玩家 Lv5 火球 vs Lv10 怪 → 怪没死;玩家 Lv20 火球 vs Lv10 怪 → 怪死。规则依赖参数。
- **状态依赖**:怪睡着 vs 怪醒着,玩家偷袭 → 不同行为。
- **位置依赖**:玩家踩到怪头上 → 怪死(马里奥式);玩家从侧面撞 → 玩家死。

**怎么处理**?把 `collision_rule` 升级:

```rust
fn collision_rule(
    a_kind: EntityKind, a_state: &EntityState,
    b_kind: EntityKind, b_state: &EntityState,
    contact: &ContactInfo,  // 接触方向、力度等
) -> CollisionRule {
    match (a_kind, b_kind) {
        (Player, Monster) => {
            // 玩家从上方踩怪(马里奥式)
            if contact.from_above && b_state.vel.y > 0.0 {
                CollisionRule::DamageB(100)
            } else {
                CollisionRule::DamageA(10)
            }
        }
        // ...
    }
}
```

这种"参数化规则"是 Day 070 之后的演化方向。Casey 现在(Phase 2)只做最基本的"类型对 → 行为",Phase 4+ 才会演化出更复杂的规则系统。

## 3 · 四域深入

### 3.1 · 游戏编程视角

碰撞规则系统是游戏引擎的核心子系统之一。每个商业引擎都有一套:

| 引擎 | 系统 | 关键特性 |
|---|---|---|
| Unity | Physics Material + Collision Matrix | 矩阵配置 + 物理材质(摩擦、弹性) |
| Unreal | Collision Profile (channels) | 通道制(`TraceType1`, `ObjectType2`...) |
| Godot | Collision Layer + Mask | 32 位 mask,二进制位运算 |
| Box2D | Contact Filter | 自定义回调函数 |
| Bevy | bevy_ecs + bevy_rapier | ECS query + Rapier 物理后端 |

它们的核心抽象都一样:**类型对 → 行为**。差别只在表达方式:

- **Unity / Unreal**:可视化矩阵(策划在编辑器里点格子)
- **Box2D**:回调函数 `bool ShouldCollide(b2Fixture* a, b2Fixture* b)`
- **Bevy**:ECS query `Query<(&Player, &Transform)>, Query<(&Monster, &Transform)>`

Casey 的 enum + match 是最朴素的实现。简单、强类型、编译器保证完整性。**对学习目的足够,但商业游戏引擎需要更多灵活性**(运行时编辑、热加载、序列化),所以演化出 Unity / Unreal 那种矩阵系统。

### 3.2 · 图形学视角

碰撞规则系统严格说不是图形学话题,但有一个间接关联:**渲染层**。

游戏里"可见性"也是一种"类型对 → 行为"——透明物体(玻璃) vs 不透明物体(墙),透明物体要后渲染(painter's algorithm)。这是渲染管线的核心设计之一。

```rust
match object.material {
    Material::Opaque => render_opaque(object),    // 走 depth pre-pass
    Material::Transparent => render_alpha(object), // 走 alpha blending,后渲染
    Material::Additive => render_additive(object), // 粒子特效,最后渲染
}
```

这种 `material → 渲染策略` 的派发,和今天的 `kind → 碰撞策略` 是同一模式。**数据驱动的派发是游戏引擎的通用 pattern**——渲染、碰撞、AI、音效,每个子系统都有。

### 3.3 · Linux 系统编程视角

Linux 内核里也有大量"类型对 → 行为"的派发。最典型的是 **`file_operations`** 表:

```c
// 内核里每种文件系统(ext4 / nfs / proc / sys)都提供这张表
struct file_operations {
    int (*open)(struct inode *, struct file *);
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*release)(struct inode *, struct file *);
    // ... 几十个函数指针
};
```

每个文件系统在 `open`、`read`、`write` 字段填自己的实现,VFS 通用层 `vfs_read()` 调用 `file->f_op->read(file, ...)` 就派发到具体实现。**这是 C 语言版的数据驱动**——`file_operations` 是一张函数指针表,VFS 是查表 + 执行。

Linux 内核比游戏引擎更早用这个 pattern,因为 C 没有 enum + match 的强类型保证,只能用函数指针 + struct。

### 3.4 · Rust 生态视角

Rust 表达"类型对 → 行为"有几个流派:

**流派 1:enum + match(最简单)**

```rust
#[derive(Clone, Copy, PartialEq, PartialOrd, Ord)]
enum EntityKind { Player = 0, Monster = 1, Wall = 2, Projectile = 3 }

enum CollisionRule {
    None,
    Block,
    Damage(u32),
    Destroy,
}

fn rule(a: EntityKind, b: EntityKind) -> CollisionRule {
    let (a, b) = if a <= b { (a, b) } else { (b, a) };
    match (a, b) {
        (EntityKind::Player, EntityKind::Wall) => CollisionRule::Block,
        (EntityKind::Player, EntityKind::Monster) => CollisionRule::Damage(10),
        _ => CollisionRule::None,
    }
}
```

优点:强类型、零成本、编译器查完整性。缺点:加规则要重新编译。

**流派 2:HashMap<(Kind, Kind), Rule>**(运行期表)

```rust
use std::collections::HashMap;

let mut table: HashMap<(EntityKind, EntityKind), CollisionRule> = HashMap::new();
table.insert((Player, Wall), CollisionRule::Block);
table.insert((Player, Monster), CollisionRule::Damage(10));

fn rule(table: &HashMap<(EntityKind, EntityKind), CollisionRule>,
        a: EntityKind, b: EntityKind) -> CollisionRule {
    let key = if a <= b { (a, b) } else { (b, a) };
    *table.get(&key).unwrap_or(&CollisionRule::None)
}
```

优点:运行期可改(支持热加载)。缺点:HashMap 查询有 hashing 开销(~10ns),match 是 O(1) jump table。

**流派 3:ECS Query(bevy_ecs 风格)**

```rust
fn collision_system(
    mut players: Query<(&mut Health, &Transform), With<Player>>,
    mut monsters: Query<(&mut Health, &Transform), With<Monster>>,
) {
    for (mut player_hp, player_t) in &mut players {
        for (mut monster_hp, monster_t) in &monsters {
            if player_t.translation.distance(monster_t.translation) < 16.0 {
                **player_hp -= 10;
                **monster_hp -= 10;
            }
        }
    }
}
```

优点:类型安全、自动并行。缺点:学习曲线陡。

**Casey 选流派 1**——HH 是教学项目,简单优先。Phase 5+ 进入 bevy 风格时,你可以重写。

## 4 · 认知地图

### 4.1 上级

- **数据驱动设计** —— 把规则从代码里抽出来,变成可配置的数据
- **派发模式(Dispatch)** —— 用一个抽象派发到多个具体实现(策略模式)
- **代数数据类型(ADT)** —— enum + match 是 ADT 在 Rust 里的表达

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| enum + match | 编译期,强类型 | 类型数量少(<20) | Day 069 |
| HashMap 表 | 运行期,可热加载 | 类型多 / 策划可调 | HH 不用 |
| 函数指针表 | C 风格,VFS 用 | 跨 ABI 边界 | HH 不用 |
| ECS query | 自动并行 | 大规模 entity | Phase 5+ 考虑 |
| Script (Lua) | 完全外置 | 大型游戏(魔兽世界) | HH 不用 |

### 4.3 下级

- `EntityKind` enum —— entity 类型的"标签"
- `CollisionRule` enum —— 行为的"标签"(带数据)
- `match (a, b)` —— 二元派发
- 规范化(把 `(a, b)` 和 `(b, a)` 统一) —— 消除对称重复
- 规则应用函数 —— `apply_rule(rule, a, b)` 把抽象规则变成具体动作

## 5 · 对照与变奏

### 2D vs 3D 的碰撞规则

2D 和 3D 的规则系统**完全一样**——都是"类型对 → 行为"。差别只在碰撞检测的几何算法(2D 是矩形 vs 矩形,3D 是 OBB / 球 / 凸包)。

### 编译期 vs 运行期表

```rust
// 编译期(Rust enum + match)
match (a, b) { (Player, Wall) => Block, _ => None }
// 编译成 jump table,纳秒级

// 运行期(HashMap)
table.get(&(a, b))
// 编译成 hash + 内存访问,十纳秒级
```

对每帧调 N² 次的碰撞代码,**编编译期表快 10 倍**。Casey 选编译期。

### 历史演化

- **1980s**:游戏用 int 表示 kind,if/else 大爆炸(初版《超级马里奥》)
- **1990s**:enum 普及,switch/case 代替 if/else(Quake / Doom)
- **2000s**:数据驱动兴起,规则搬到配置文件(Unreal Ed 的 Collision Profile)
- **2010s**:ECS 普及,规则用 query 表达(Bevy / Unity DOTS)
- **2020s**:AI 辅助生成规则(GPT 给游戏写 Lua 配置)

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么要做"规范化"(把 `(a, b)` 排序成 `(小, 大)`)?如果不规范化会怎样?

**参考解答**:
1. **消除对称重复**:不规范化,你要写 `(Player, Wall) => Block` 和 `(Wall, Player) => Block` 两份——规则集合翻倍,加规则要改两处,易漏。
2. **降低维护成本**:规范化后所有规则只写"小在大前",规则集合大小是 N*(N+1)/2 而不是 N²。20 种 entity,不规范化 400 条规则,规范化 210 条。
3. **保证唯一性**:规范化后每对类型只对应一条规则,不会出现 `(Player, Wall) => Block` 但 `(Wall, Player) => Damage` 的矛盾。

代价:规范化需要 swap 操作(O(1)),以及调用 collision_rule 时要保留原始引用(因为规范化丢掉了"谁是主动方"信息)。

### Lv2 · 动手实践

**题**:实现一个最简单的碰撞规则系统。Entity 类型有 4 种:Player / Monster / Wall / Projectile。规则:

| | Player | Monster | Wall | Projectile |
|---|---|---|---|---|
| Player | - | 玩家扣 10 血 | 阻挡 | - |
| Monster | 玩家扣 10 血 | 互穿 | 阻挡 | 怪扣 20 血,投射物消失 |
| Wall | 阻挡 | 阻挡 | - | 投射物消失 |
| Projectile | - | 怪扣 20 血,投射物消失 | 投射物消失 | - |

完成标准:`cargo run` 跑测试,所有 assert 通过。

**参考解答**:

```rust
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
enum Kind { Player = 0, Monster = 1, Wall = 2, Projectile = 3 }

#[derive(Debug, PartialEq)]
enum Rule {
    None,
    Block,
    DamageA(u32),  // a 扣血
    DamageB(u32),  // b 扣血
    DestroyA,      // 销毁 a
    DestroyB,      // 销毁 b
}

fn collision_rule(mut a: Kind, mut b: Kind) -> Rule {
    // 规范化:保证 a <= b
    if a > b { std::mem::swap(&mut a, &mut b); }
    match (a, b) {
        (Kind::Player,    Kind::Wall)       => Rule::Block,
        (Kind::Player,    Kind::Monster)    => Rule::DamageA(10),  // a=Player 扣血
        (Kind::Monster,   Kind::Wall)       => Rule::Block,
        (Kind::Monster,   Kind::Monster)    => Rule::None,         // 互穿
        (Kind::Monster,   Kind::Projectile) => Rule::DamageA(20),  // a=Monster 扣血
        // (注意:这里 a 是规范化后的"较小"方。Monster(1) < Projectile(3),
        // 所以 a 是 Monster。DamageA(20) 怪扣 20。)
        (Kind::Wall,      Kind::Projectile) => Rule::DestroyB,     // b=Projectile 消失
        // (a=Wall(2) < b=Projectile(3),b 是 Projectile)
        _ => Rule::None,
    }
}

fn main() {
    // 验证对称性:rule(A, B) 和 rule(B, A) 应该一致(只是 a/b 角色换)
    let r1 = collision_rule(Kind::Player, Kind::Wall);
    let r2 = collision_rule(Kind::Wall, Kind::Player);
    println!("(Player, Wall): {:?}", r1); // Block
    println!("(Wall, Player): {:?}", r2); // Block

    let r3 = collision_rule(Kind::Monster, Kind::Projectile);
    let r4 = collision_rule(Kind::Projectile, Kind::Monster);
    println!("(Monster, Projectile): {:?}", r3);
    println!("(Projectile, Monster): {:?}", r4);

    // 注意 r3 和 r4 不一样!因为 DamageA 在 r3 是 Monster,在 r4 是 Projectile
    // 规范化后,a 始终是 Monster,所以 r3 和 r4 都是 DamageA(20)
    // 但调用方需要知道:规范化后"DamageA"对应的原始 entity 是 Monster
}
```

**关键解释**:
- `#[derive(PartialOrd, Ord)]` 让 Kind 可以比较大小,这是规范化的前提。
- `match (a, b)` 是 Rust 二元模式匹配,编译成 jump table。
- 规范化后 a 始终 ≤ b,所以表里只写 `(Player, Wall)` 不写 `(Wall, Player)`。
- 规则的 `DamageA` 表示"a 扣血",规范化后 a 是较小 kind。调用方需要保留原始引用才能正确施加伤害。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

下面是一个完整的小游戏碰撞规则演示。4 种 entity,规则表,简单的 HP 系统。

```rust
// Cargo.toml: 没有 dependency,纯 std

use std::mem::swap;

#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
enum Kind { Player = 0, Monster = 1, Wall = 2, Projectile = 3 }

#[derive(Clone, Copy, Debug, PartialEq)]
enum Rule {
    None,
    Block,
    DamageA(u32),
    DamageB(u32),
    DestroyA,
    DestroyB,
}

#[derive(Debug)]
struct Entity {
    id: u32,
    kind: Kind,
    hp: i32,
    alive: bool,
}

fn collision_rule(mut a: Kind, mut b: Kind) -> Rule {
    if a > b { swap(&mut a, &mut b); }
    match (a, b) {
        (Kind::Player,    Kind::Wall)       => Rule::Block,
        (Kind::Player,    Kind::Monster)    => Rule::DamageA(10),
        (Kind::Monster,   Kind::Wall)       => Rule::Block,
        (Kind::Monster,   Kind::Monster)    => Rule::None,
        (Kind::Monster,   Kind::Projectile) => Rule::DamageA(20),
        (Kind::Wall,      Kind::Projectile) => Rule::DestroyB,
        _ => Rule::None,
    }
}

fn on_collision(world: &mut Vec<Entity>, id_a: usize, id_b: usize) {
    let kind_a = world[id_a].kind;
    let kind_b = world[id_b].kind;
    // 规范化:记录 (原始较小索引, 原始较大索引)
    let (rule, idx_small, idx_large) = if kind_a <= kind_b {
        (collision_rule(kind_a, kind_b), id_a, id_b)
    } else {
        (collision_rule(kind_b, kind_a), id_b, id_a)
    };

    match rule {
        Rule::None => {},
        Rule::Block => {
            // 在真实游戏里这里做物理阻挡(改 pos)。本演示跳过。
            println!("  Block: {} vs {}", world[idx_small].id, world[idx_large].id);
        },
        Rule::DamageA(dmg) => {
            world[idx_small].hp -= dmg as i32;
            if world[idx_small].hp <= 0 { world[idx_small].alive = false; }
            println!("  DamageA({}): {} → hp={}", dmg, world[idx_small].id, world[idx_small].hp);
        },
        Rule::DamageB(dmg) => {
            world[idx_large].hp -= dmg as i32;
            if world[idx_large].hp <= 0 { world[idx_large].alive = false; }
            println!("  DamageB({}): {} → hp={}", dmg, world[idx_large].id, world[idx_large].hp);
        },
        Rule::DestroyA => {
            world[idx_small].alive = false;
            println!("  DestroyA: {}", world[idx_small].id);
        },
        Rule::DestroyB => {
            world[idx_large].alive = false;
            println!("  DestroyB: {}", world[idx_large].id);
        },
    }
}

fn main() {
    let mut world: Vec<Entity> = vec![
        Entity { id: 1, kind: Kind::Player,    hp: 100, alive: true },
        Entity { id: 2, kind: Kind::Monster,   hp: 30,  alive: true },
        Entity { id: 3, kind: Kind::Wall,      hp: 1,   alive: true },
        Entity { id: 4, kind: Kind::Projectile,hp: 1,   alive: true },
    ];

    println!("=== Player 撞 Monster ===");
    on_collision(&mut world, 0, 1);
    // Player(0) < Monster(1) 规范后不变,rule = DamageA(10)
    // idx_small = 0 (Player),Player hp 100→90

    println!("=== Monster 撞 Projectile ===");
    on_collision(&mut world, 1, 3);
    // Monster(1) < Projectile(3) 规范后不变,rule = DamageA(20)
    // idx_small = 1 (Monster),Monster hp 30→10

    println!("=== Projectile 撞 Wall(反过来调用) ===");
    on_collision(&mut world, 3, 2);
    // 注意调用顺序是 (Projectile, Wall),但规范化后会 swap
    // Wall(2) < Projectile(3),所以 idx_small = 2 (Wall),idx_large = 3 (Projectile)
    // rule = DestroyB,idx_large 是 Projectile,Projectile 被销毁

    println!("=== 最终状态 ===");
    for e in &world {
        println!("  id={} kind={:?} hp={} alive={}", e.id, e.kind, e.hp, e.alive);
    }
}
```

**预期输出**:

```
=== Player 撞 Monster ===
  DamageA(10): 1 → hp=90
=== Monster 撞 Projectile ===
  DamageA(20): 2 → hp=10
=== Projectile 撞 Wall(反过来调用) ===
  DestroyB: 4
=== 最终状态 ===
  id=1 kind=Player hp=90 alive=true
  id=2 kind=Monster hp=10 alive=true
  id=3 kind=Wall hp=1 alive=true
  id=4 kind=Projectile hp=1 alive=false
```

**关键 Rust 特性**:
- `#[derive(PartialOrd, Ord)]` 自动从 enum 的数值派生大小比较。
- `std::mem::swap` 原地交换两个可变引用(底层是 `memcpy`)。
- `match rule` 的穷尽性保证——所有 Rule 变体都处理,否则编译报错。
- `usize` 索引代替裸指针,Rust 的"安全指针"。

### 把规则外置成数据(JSON)

如果你想进步到"策划可热加载":

```rust
// Cargo.toml: serde = { version = "1", features = ["derive"] }, serde_json = "1"

use serde::{Deserialize, Serialize};

#[derive(Serialize, Deserialize, Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
#[serde(rename_all = "lowercase")]
enum Kind { Player, Monster, Wall, Projectile }

#[derive(Serialize, Deserialize, Debug, Clone)]
#[serde(tag = "type")]
enum Rule {
    None,
    Block,
    #[serde(rename = "damage_a")]
    DamageA { amount: u32 },
    #[serde(rename = "damage_b")]
    DamageB { amount: u32 },
}

#[derive(Serialize, Deserialize, Debug)]
struct RuleEntry { a: Kind, b: Kind, rule: Rule }

fn rule_from_json(json: &str, a: Kind, b: Kind) -> Rule {
    let entries: Vec<RuleEntry> = serde_json::from_str(json).unwrap();
    let (a, b) = if a <= b { (a, b) } else { (b, a) };
    for e in &entries {
        let (ea, eb) = if e.a <= e.b { (e.a, e.b) } else { (e.b, e.a) };
        if ea == a && eb == b { return e.rule.clone(); }
    }
    Rule::None
}

fn main() {
    let json = r#"[
        {"a": "player", "b": "wall", "rule": {"type": "block"}},
        {"a": "player", "b": "monster", "rule": {"type": "damage_a", "amount": 10}}
    ]"#;
    let r = rule_from_json(json, Kind::Player, Kind::Wall);
    println!("{:?}", r); // Block
}
```

这样规则完全在 JSON 里,策划改 JSON 不重新编译。
