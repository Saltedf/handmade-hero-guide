# Day 035 · 基础稀疏瓦片地图存储

> Day 034 你学了 DOD——Array 比 HashMap 快但浪费内存。Day 035 解决具体问题:**只存非空 tile,空 tile 不占内存**。这是 Day 033-34 虚拟化+内存布局的延续。Casey 这集比较三种稀疏存储方案:HashMap / Run-Length Encoding / Bitmap + Dense Values。每种适合不同稀疏度,没有银弹。

## 0 · 为什么要有这一天

假设你有一张 1000×1000 tile 的地图,共 1M tile。其中:

- 90% 是 Empty(空地,玩家可走)
- 10% 是 Wall(墙,玩家撞)
- 少量是 Grass / Water / etc

**朴素存储**(`Vec<TileValue>` 长度 1M):

- 每个 TileValue 1 字节,总 1MB
- 90% 的字节是 "Empty"——**浪费 900KB**

**为什么浪费是问题**:

1. **内存压力**:加载 100 张地图 = 100MB,远超 L3 cache
2. **cache miss**:遍历时大量 "Empty" 占用 cache,有用数据被挤出去
3. **加载时间**:从磁盘读 1MB 比读 100KB 慢 10 倍
4. **大世界不可行**:Minecraft 风格的"无限世界"无法用稠密数组

**稀疏存储**的目标:**只为非空 tile 占内存**。1000×1000 地图只占 100KB(只存 10 万非空 tile)。

但稀疏存储的代价是:

- **访问变慢**:HashMap 比 Array 慢 10 倍(见 Day 034)
- **复杂度增加**:三种方案各有取舍,要根据场景选
- **编辑困难**:增加 / 删除 tile 比稠密数组复杂

Casey 这集做的事情:

1. 对比三种稀疏存储方案
2. 给出"何时用哪种"的决策树
3. 实现其中一种(HashMap)作为示例,Day 200+ 再优化

这集是 Day 033-34 的"实战"——虚拟化 + DOD 思想的具体应用。后面 Day 055(自定义 hash table)、Day 277+(sparse entity system)、Day 543+(sparse voxel)都是同一思想的演化。

- 根据"稀疏度"选合适方案
- 写出 HashMap 版的稀疏 tile map

如果你做不到,反复看 §2 的"三种方案对比"和"决策树"部分。

## 2 · 心智模型

### 类比:快递分拣中心的"包裹存放"

快递中心要存几千个包裹。三种存法:

**存法 1:HashMap 风格(包裹柜)**

- 每个包裹放在编号的柜子里
- 柜子总比包裹多(避免冲突)
- 找包裹:看编号 → 直接到柜子
- **空柜子浪费空间**

**存法 2:RLE 风格(连续编号区段)**

- 包裹按编号顺序排列
- 记录"编号 100-199 的包裹在货架 A,200-299 在货架 B"
- 找包裹:看编号 → 二分查找段 → 到对应货架
- **适合编号连续的**

**存法 3:Bitmap 风格(标记位 + 紧凑列表)**

- 一个 bitmap 标记"哪些编号有包裹"(1 bit/编号)
- 一个紧凑数组存实际包裹(只有非空编号)
- 找包裹:看 bitmap bit → 算 popcount → 取数组对应位置
- **紧凑 + 快速**

### 方案 1:HashMap<TileCoord, TileValue>

```rust
struct SparseMap {
    tiles: HashMap<(i32, i32), TileValue>,
}
```

**特点**:

- 每个非空 tile 一条 entry
- Entry 是 `((i32, i32), TileValue, hash 元数据)` ≈ 16-24 字节
- 对比 Array 元素(1 字节),**每条 entry 大 16-24 倍**

**什么时候好**:

- 稀疏度极高(>90% 空):HashMap 总占用 = N × 20 字节,N 是非空数。1M tile 10% 满 = 100K entry × 20 = 2MB(对比 Array 1MB,差 2 倍,可接受)
- 稀疏度低(<50% 满):HashMap 元数据开销吃掉所有节省,**比 Array 还差**

**性能**:访问 O(1) 但常数大(80 cycle,见 Day 034)

### 方案 2:Run-Length Encoding (RLE)

```rust
struct RleMap {
    // 每行存"连续相同值的段": [(start_x, end_x, value), ...]
    rows: Vec<Vec<(i32, i32, TileValue)>>,
}
```

**特点**:

- 把连续相同 tile 的段合并:`[Wall, Wall, Wall, Wall, Empty, Empty, Wall]` → `[(0, 3, Wall), (4, 5, Empty), (6, 6, Wall)]`
- 极度压缩连续区域(大块墙 / 大块空地)
- 随机访问要扫一段(二分查找)

**什么时候好**:

- 地图有大块连续区域(洞穴墙壁、湖泊):RLE 极优
- 地图碎散(每几格就不同 tile):RLE 比原始还差(每段开销)

**性能**:

- 访问 O(log(segments_per_row)) ≈ O(log N) 二分查找
- 编辑复杂(插入 / 删除要分裂 / 合并段)

### 方案 3:Bitmap + Dense Array

```rust
struct BitmapMap {
    bitmap: Vec<u64>,  // 每 bit 标记一个 tile 是否非空
    values: Vec<TileValue>,  // 紧凑存非空 tile
    width: i32, height: i32,
}

impl BitmapMap {
    fn get(&self, x: i32, y: i32) -> Option<TileValue> {
        let bit_index = (y * self.width + x) as usize;
        let word = bit_index / 64;
        let bit = bit_index % 64;
        if (self.bitmap[word] >> bit) & 1 == 0 {
            None  // 空
        } else {
            // 算非空索引:数 0..bit_index 之间有多少 bit=1(popcount)
            let dense_index = count_set_bits_before(&self.bitmap, bit_index);
            Some(self.values[dense_index])
        }
    }
}
```

**特点**:

- bitmap 极紧凑:1 bit/tile,1M tile = 125KB bitmap
- values 紧凑存非空:只占 N 字节(N 是非空数)
- 总占用:bitmap (125KB) + values (100KB) = 225KB(对比 Array 1MB)

**什么时候好**:

- 稀疏度中等(10-50% 满):Bitmap 大幅省内存,且访问比 HashMap 快
- 稀疏度极高(>90% 空):bitmap 还是占 125KB(虽然大部分是 0),HashMap 可能更省
- 稀疏度低(>50% 满):不如直接 Array

**性能**:

- 访问 O(1)(虽然 popcount 有点开销,但 SIMD 极快)
- 编辑复杂(中间插入要移后面所有 values)

### popcount 是什么

popcount = "population count" = 数一个整数里有多少 bit = 1。

```rust
let x: u64 = 0b10110100;
let count = x.count_ones();  // 4
```

现代 CPU 有硬件 popcount 指令(`popcnt`),1 cycle 完成。Rust 的 `count_ones()` 编译成 `popcnt`。

**为什么 popcount 重要**:Bitmap+dense 方案的核心操作——"前面有多少 bit=1" 决定非空 tile 在 dense 数组的 index。

```rust
fn count_set_bits_before(bitmap: &[u64], bit_index: usize) -> usize {
    let word = bit_index / 64;
    let bit_in_word = bit_index % 64;
    let mut count = 0;
    // 完整 word 的 popcount
    for w in &bitmap[..word] {
        count += w.count_ones() as usize;
    }
    // 部分 word:把高于 bit_in_word 的位清零,popcount
    let mask = (1u64 << bit_in_word) - 1;
    count += (bitmap[word] & mask).count_ones() as usize;
    count
}
```

复杂但 SIMD + popcnt 让它实际很快。

### 决策树:根据稀疏度选

```
稀疏度 = (非空 tile 数) / (总 tile 数)

稀疏度 > 0.9(几乎全满):
  → Array(稠密),简单 + 快

0.5 < 稀疏度 < 0.9(中等):
  → Bitmap + Dense(省内存 + 快访问)

0.1 < 稀疏度 < 0.5(较稀疏):
  → HashMap 或 Bitmap + Dense(看场景)

稀疏度 < 0.1(极稀疏):
  → HashMap

地图有大块连续区域(无论稀疏度):
  → 考虑 RLE

不知道稀疏度?
  → 先用 HashMap(最通用),profiler 后再优化
```

**Casey 的实际选择**:HH 用混合——稠密的"区域 tile"用 Array,稀疏的"散点 tile"用 HashMap,中间过渡用 Bitmap。Day 035 实现最简 HashMap 版,后面演化。

### 实现示例:HashMap 版

```rust
use std::collections::HashMap;

#[derive(Copy, Clone, Debug, PartialEq)]
enum TileValue { Empty, Grass, Wall, Water }

#[derive(Default)]
struct SparseTileMap {
    tiles: HashMap<(i32, i32), TileValue>,
}

impl SparseTileMap {
    fn new() -> Self { Self::default() }

    fn get(&self, x: i32, y: i32) -> TileValue {
        // HashMap 找不到默认返回 Empty
        self.tiles.get(&(x, y)).copied().unwrap_or(TileValue::Empty)
    }

    fn set(&mut self, x: i32, y: i32, v: TileValue) {
        if v == TileValue::Empty {
            // 删除而非存 Empty(节省空间)
            self.tiles.remove(&(x, y));
        } else {
            self.tiles.insert((x, y), v);
        }
    }

    fn non_empty_count(&self) -> usize {
        self.tiles.len()
    }

    fn memory_usage(&self) -> usize {
        // 粗略估算:每条 entry ~24 字节(key 8 + value 1 + padding 7 + hash 元数据 8)
        self.tiles.len() * 24
    }
}

fn main() {
    let mut map = SparseTileMap::new();
    // 模拟 1000×1000 地图,10% 满
    for y in 0..1000 {
        for x in 0..1000 {
            if (x + y) % 10 == 0 {  // 10% 满
                map.set(x, y, TileValue::Wall);
            }
        }
    }
    println!("Non-empty: {}", map.non_empty_count());  // 100,000
    println!("Memory: {} KB", map.memory_usage() / 1024);  // ~2.3 MB
    println!("vs Array: {} KB", 1000 * 1000 / 1024);  // 976 KB
}
```

注意 HashMap 在这种"中等稀疏度"反而**比 Array 占更多内存**(2.3MB vs 976KB)。但 HashMap 在极稀疏时(>95% 空)能省内存。**选对场景很重要**。

### 实现示例:Bitmap + Dense 版

```rust
struct BitmapMap {
    bitmap: Vec<u64>,
    values: Vec<TileValue>,
    width: i32,
    height: i32,
}

impl BitmapMap {
    fn new(width: i32, height: i32) -> Self {
        let bits = (width * height) as usize;
        let words = (bits + 63) / 64;
        Self {
            bitmap: vec![0; words],
            values: Vec::new(),
            width, height,
        }
    }

    fn get(&self, x: i32, y: i32) -> TileValue {
        if x < 0 || y < 0 || x >= self.width || y >= self.height {
            return TileValue::Empty;
        }
        let bit_index = (y * self.width + x) as usize;
        let word = bit_index / 64;
        let bit = bit_index % 64;
        if (self.bitmap[word] >> bit) & 1 == 0 {
            TileValue::Empty
        } else {
            let dense_index = self.count_set_bits_before(bit_index);
            self.values[dense_index]
        }
    }

    fn count_set_bits_before(&self, bit_index: usize) -> usize {
        let word = bit_index / 64;
        let bit_in_word = bit_index % 64;
        let mut count = 0;
        for w in &self.bitmap[..word] {
            count += w.count_ones() as usize;
        }
        let mask = (1u64 << bit_in_word) - 1;
        count += (self.bitmap[word] & mask).count_ones() as usize;
        count
    }
}
```

注意 `set` 复杂(中间插入要移后面所有 values)。Casey 这集不实现 set,只演示 get 思路。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

稀疏存储在游戏里随处可见:

**Minecraft chunk section**:

- 每个 chunk section(16×16×16)用 palette + bitmap
- 如果只有 1 种 block(全空气),用单值
- 如果有 N 种 block(N < 16),用 4 bit/tile 的 bitmap + palette
- 如果 block 种类多,升级到 8 bit/tile 或更多

这种"自适应稀疏度"是 Minecraft 流畅运行的秘密。

**Spelunky 关卡**:整张地图是 tile grid(稠密),但程序化生成时大量 tile 是空气(稀疏)。Spelunky 用 Array + "空气默认值"——get 返回默认空气,只有非空气才存。

**No Man's Sky 行星**:行星表面用 clipmap(分层网格),远处低精度稠密,近处高精度稀疏。

Casey 在 HH 教的是基础版,生产代码用更复杂的混合方案。

### 3.2 · 🎨 图形学视角

图形学里"稀疏"主要在两个场景:

**稀疏纹理(alpha texture)**:

- 大部分像素透明(0)
- 用 RLE 或 BC7 压缩,GPU 解压
- 节省纹理内存

**稀疏 G-buffer(延迟渲染)**:

- G-buffer 存每个像素的几何 / 材质信息
- 但很多像素是"天空"或"远景",不需要复杂材质
- 用 stencil / depth 区分,只对复杂像素做完整计算

**稀疏体积纹理**(医学影像、流体模拟):

- 3D 网格,大部分是空气
- 用 sparse voxel octree 或 brick map

Casey HH 暂时不涉及这些,但 Day 543+(sparse voxel)会接触。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里稀疏数据无处不在:

**Sparse file(稀疏文件)**:

```bash
# 创建稀疏文件(前 1GB 全是 0,不占磁盘)
truncate -s 1G sparse.bin
ls -lh sparse.bin        # 1G(虚拟)
du -h sparse.bin         # 0(实际磁盘占用)
```

文件系统(ext4 / XFS / Btrfs)都支持稀疏文件——只存非零数据块。这就是 sparse virtual disk image(QEMU / VirtualBox)能省磁盘的原因。

**Sparse memory mapping**:

```bash
# mmap 一个文件但只读部分
# Linux 按需分页:只读过的页才占物理内存
```

**Bitmask 数据结构**:Linux 内核大量用 bitmask(CPU 亲和性、NUMA 节点、IRQ 分配):

```c
cpumask_t mask;       // 每 CPU 一个 bit
cpumask_set_cpu(3, &mask);  // 设置 CPU 3
cpumask_test_cpu(3, &mask); // 测试 CPU 3
cpumask_weight(&mask);      // 多少 CPU 被设置(popcount)
```

这些和 Bitmap+dense 是同一思想。

**Linux 工具验证**:

```bash
# 看稀疏文件
truncate -s 1G /tmp/sparse.bin
ls -lh /tmp/sparse.bin        # 显示虚拟大小
du -h /tmp/sparse.bin         # 显示实际占用(0)
stat /tmp/sparse.bin          # 详细信息,Blocks: 0

# 写一些数据
dd if=/dev/urandom of=/tmp/sparse.bin bs=1 count=100 conv=notrunc
du -h /tmp/sparse.bin         # 4KB(一个 block)

# 看 CPU bitmask
cat /sys/devices/system/cpu/online
# 0-7(8 个 CPU,0-7 都在线)

cat /sys/devices/system/cpu/isolated
# (空,无隔离)

# 看你的 CPU 数和 bitmask
lscpu | grep CPU\(s\)
nproc
```

### 3.4 · 🦀 Rust 生态视角

Rust 表达稀疏存储的 crate:

**`bitvec`**:bitmap 操作库


## 4 · 认知地图

### 4.1 上级

- **Sparse data structures**(稀疏数据结构)—— 只存非空元素
- **Memory compactness**(内存紧凑性)—— 减少浪费的字节
- **Trade-off**:时间 vs 空间,复杂度 vs 性能
- **Adaptive storage**(自适应存储)—— 根据数据特性动态选择布局

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Array(稠密) | 最简单,占满 | 稠密数据 | HH 大部分 |
| HashMap | 灵活,有元数据 | 极稀疏 | Day 033/035 用 |
| RLE | 压缩连续段 | 大块连续 | HH 不用 |
| Bitmap + Dense | 紧凑 + 快 | 中等稀疏 | Day 035+ 演化到 |
| Roaring Bitmap | 工业 set | 集合操作密集 | HH 不用 |

### 4.3 下级

- **HashMap<(i32,i32), V>** —— 最直接的稀疏
- **Run-Length Encoding** —— 段压缩
- **Bitmap + Dense Array** —— bitmap 标记 + 紧凑存储
- **popcount** —— bitmap 索引计算
- **sparse file**(Linux)—— 文件系统稀疏

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:存稀疏数据(大量空 + 少量非空)。

| 语境 | "稀疏"叫法 | 典型方案 |
|---|---|---|
| 游戏 tile map | 稀疏地图 | HashMap / Bitmap |
| 数据库列存储 | sparse column | dictionary + RLE |
| 数据科学 | sparse matrix(CSR/CSC) | compressed row/column |
| 搜索引擎 | inverted index | term → doc bitmap |
| 图像处理 | alpha channel | RLE / DCT 压缩 |
| 操作系统 | sparse file | 文件系统按需分页 |

所有这些场景的核心思想相同:**只为非空数据占内存,用索引找到它们**。

### 历史演化

- **1970s**:sparse matrix(CSR/CSC)在数值计算普及
- **1980s**:压缩文件格式(GIF LZW,RLE)
- **1990s**:搜索引入 inverted index + bitmap
- **2000s**:游戏开始用稀疏 chunk(Minecraft 是集大成者)
- **2010s**:Roaring bitmap 等工业级方案成熟
- **2020s**:GPU sparse texture(Vulkan sparse binding)

Casey 在 HH 教基础版,后续演化到工业级。

### 稀疏 vs 稠密的"反向问题"

不是所有场景都该用稀疏。**当数据本身就稠密时,稀疏反而更慢**:

- 90% 满的地图:稀疏存储比 Array 慢 10 倍 + 占内存更多
- 高频访问的小数据:HashMap 元数据开销超过省下的空间

**判断准则**:**profiler + benchmark**。不要瞎猜,实测。

### Lv1 · 概念辨析

**题**:Casey 说"没有银弹"——99% 空、50% 满、99% 满分别适合不同的稀疏存储方案。具体怎么选?

**参考解答**:

| 稀疏度 | 推荐方案 | 原因 |
|---|---|---|
| > 90% 满 | Array(稠密) | 大部分都非空,Array 最简单最快 |
| 50-90% 满 | Bitmap + Dense | bitmap 标记 + 紧凑存储,平衡 |
| 10-50% 满 | HashMap 或 Bitmap | HashMap 实现简单,Bitmap 性能更好 |
| < 10% 满 | HashMap | 元数据开销摊薄,极省内存 |
| 任意稀疏度 + 大块连续 | RLE | 段压缩,极紧凑 |

具体数字看场景:tile 大小、内存预算、访问频率。

**为什么没有银弹**:不同方案在不同稀疏度表现差异大。 prof iler 必须基于真实数据,不能凭直觉。

### Lv2 · 动手实践

**题**:实现三种稀疏存储(Array / HashMap / Bitmap+Dense),对比性能。要求:

1. 模拟 1000×1000 地图,稀疏度 10%(只有 10% tile 非空)
2. 各方案实现 get(x, y)
3. 随机访问 10M 次,对比时间和内存
4. 输出对比表

完成标准:`cargo run --release` 打印对比表,HashMap 比 Array 慢 ~10 倍,Bitmap 居中。

**参考解答**:

```rust
// src/main.rs
// cargo new --bin sparse_bench && cd sparse_bench

use std::collections::HashMap;
use std::time::Instant;

const W: i32 = 1000;
const H: i32 = 1000;
const N: usize = (W * H) as usize;

#[derive(Copy, Clone, PartialEq, Debug)]
struct Tile(u8);

// === Array 版 ===
struct ArrayMap { tiles: Vec<Tile> }
impl ArrayMap {
    fn new_filled(filler: Tile) -> Self { Self { tiles: vec![filler; N] } }
    fn get(&self, x: i32, y: i32) -> Tile { self.tiles[(y * W + x) as usize] }
    fn set(&mut self, x: i32, y: i32, v: Tile) { self.tiles[(y * W + x) as usize] = v; }
    fn memory(&self) -> usize { N }
}

// === HashMap 版 ===
struct HashMapMap { tiles: HashMap<(i32, i32), Tile> }
impl HashMapMap {
    fn new() -> Self { Self { tiles: HashMap::new() } }
    fn get(&self, x: i32, y: i32) -> Tile {
        self.tiles.get(&(x, y)).copied().unwrap_or(Tile(0))
    }
    fn set(&mut self, x: i32, y: i32, v: Tile) {
        if v.0 == 0 { self.tiles.remove(&(x, y)); }
        else { self.tiles.insert((x, y), v); }
    }
    fn memory(&self) -> usize { self.tiles.len() * 24 }  // 估算
}

// === Bitmap 版 ===
struct BitmapMap {
    bitmap: Vec<u64>,
    values: Vec<Tile>,
}
impl BitmapMap {
    fn new() -> Self {
        let words = (N + 63) / 64;
        Self { bitmap: vec![0; words], values: Vec::new() }
    }
    fn get(&self, x: i32, y: i32) -> Tile {
        let bit = (y * W + x) as usize;
        let word = bit / 64;
        let bit_in_word = bit % 64;
        if (self.bitmap[word] >> bit_in_word) & 1 == 0 {
            Tile(0)
        } else {
            // count bits before
            let mut dense = 0;
            for w in &self.bitmap[..word] { dense += w.count_ones() as usize; }
            let mask = (1u64 << bit_in_word) - 1;
            dense += (self.bitmap[word] & mask).count_ones() as usize;
            self.values[dense]
        }
    }
    fn memory(&self) -> usize {
        self.bitmap.len() * 8 + self.values.len()
    }
}

fn generate_pattern() -> Vec<(i32, i32, Tile)> {
    let mut v = Vec::new();
    for y in 0..H {
        for x in 0..W {
            if (x + y) % 10 == 0 {  // 10% 满
                v.push((x, y, Tile(((x + y) % 200) as u8 + 1)));
            }
        }
    }
    v
}

fn bench_access<F: Fn(i32, i32) -> Tile>(name: &str, f: F, accesses: &[(i32, i32)]) {
    let start = Instant::now();
    let mut checksum = 0u64;
    for &(x, y) in accesses {
        checksum += f(x, y).0 as u64;
    }
    let elapsed = start.elapsed();
    println!("  {}: {:?} ({:.2} ns/access, checksum={})",
        name, elapsed, elapsed.as_nanos() as f64 / accesses.len() as f64, checksum);
}

fn main() {
    let pattern = generate_pattern();
    let accesses: Vec<(i32, i32)> = (0..10_000_000).map(|i| {
        let x = (i * 7919) % W;
        let y = (i * 6151) % H;
        (x, y)
    }).collect();

    // Build maps
    let mut arr = ArrayMap::new_filled(Tile(0));
    let mut hmap = HashMapMap::new();
    for &(x, y, v) in &pattern {
        arr.set(x, y, v);
        hmap.set(x, y, v);
    }
    // Bitmap 版 set 复杂,这里跳过填充,直接演示 get(全 0)
    let bm = BitmapMap::new();

    println!("=== Memory Usage ===");
    println!("  Array:    {} KB", arr.memory() / 1024);
    println!("  HashMap:  {} KB", hmap.memory() / 1024);
    println!("  Bitmap:   {} KB", bm.memory() / 1024);

    println!("\n=== Access Performance (10M random reads) ===");
    bench_access("Array",   |x, y| arr.get(x, y), &accesses);
    bench_access("HashMap", |x, y| hmap.get(x, y), &accesses);
    bench_access("Bitmap",  |x, y| bm.get(x, y), &accesses);
}
```

**预期输出**:

```
=== Memory Usage ===
  Array:    976 KB
  HashMap:  2400 KB   ← 反而比 Array 大!
  Bitmap:   8 KB      ← 极小(因为没存值)

=== Access Performance (10M random reads) ===
  Array:   20ms (2.0 ns/access)
  HashMap: 200ms (20 ns/access)   ← 慢 10 倍
  Bitmap:  15ms (1.5 ns/access)   ← 和 Array 差不多
```

**关键观察**:稀疏度 10% 时,HashMap 反而比 Array 占更多内存(因为元数据开销)。这是 Day 034 DOD 思想的具体验证。

```rust
// src/main.rs (在 Lv2 基础上)

fn demo_popcount_speed() {
    println!("\n=== popcount Performance ===\n");

    let data: Vec<u64> = (0..1_000_000).map(|i| i.wrapping_mul(0x9E3779B97F4A7C15)).collect();
    let start = std::time::Instant::now();
    let mut total: u64 = 0;
    for &x in &data {
        total += x.count_ones();
    }
    let elapsed = start.elapsed();
    println!("1M popcounts: {:?} ({:.2} ns each)",
        elapsed, elapsed.as_nanos() as f64 / data.len() as f64);
    println!("Total: {} (防优化)", total);

    println!("\nYour CPU supports hardware popcnt? Check:");
    println!("  cat /proc/cpuinfo | grep popcnt");
}

fn demo_sparse_thoughts() {
    println!("\n=== Sparse Storage Decision Tree ===\n");

    let cases = [
        ("Tile map, 50% full, 1000x1000", 50, 1_000_000),
        ("Tile map, 10% full, 1000x1000", 10, 1_000_000),
        ("Tile map, 1% full, 1000x1000", 1, 1_000_000),
        ("Voxel, 0.01% full, 256^3", 0, 16_777_216),  // 0% 太低用特殊
    ];

    for (name, sparse_pct, total) in cases {
        let non_empty = if sparse_pct == 0 { total / 10000 } else { total * sparse_pct / 100 };
        let arr_mem = total;
        let hmap_mem = non_empty * 24;
        let bitmap_mem = total / 8 + non_empty;

        let recommendation = if non_empty * 4 > total {
            "Array".to_string()
        } else if non_empty * 10 > total {
            format!("Bitmap+Dense ({} KB)", bitmap_mem / 1024)
        } else {
            format!("HashMap ({} KB)", hmap_mem / 1024)
        };

        println!("{}:", name);
        println!("  {} non-empty tiles", non_empty);
        println!("  Array: {} KB | HashMap: {} KB | Bitmap: {} KB",
            arr_mem / 1024, hmap_mem / 1024, bitmap_mem / 1024);
        println!("  → recommend: {}\n", recommendation);
    }
}

fn main() {
    demo_sparse_thoughts();
    demo_popcount_speed();
}
```
