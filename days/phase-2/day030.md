
# Day 030 · 在瓦片地图之间移动

> Day 028-029 你做完一张 tile map + 碰撞,玩家能在一张地图上跑动撞墙。Day 030 加多 tile map——玩家从草地地图边缘走出去,进入森林地图。这是世界结构的开始:多张地图通过边界连接。Casey 还顺手埋下一个"游戏状态持久化"的种子——哪些状态离开地图后保留,哪些重置。

## 0 · 为什么要有这一天

你想想,经典 2D 游戏的世界是怎么组织的?

- **塞尔达(初代 NES)**:林克从 overworld(大地图)走到一个洞口,切到 dungeon(地下城)地图。每个 dungeon 是独立地图,通关后回到 overworld
- **宝可梦**:玩家走到城市边缘,切到 Route(道路)地图。Route 是城市之间的连接
- **Celeste**:玩家在关卡选择界面选一个,切到具体关卡。关卡之间相对独立
- **空洞骑士**:大世界通过"房间"组织,房间之间用通道连接,玩家从一个房间走到另一个

这些都是**多 tile map + 边界连接**的结构。游戏世界不再是"一张大地图",而是"多张小地图通过边/通道连接"。这种结构的好处:

1. **内存可控**:不需要把整个世界一次性加载到内存,只加载当前地图
2. **设计灵活**:每张地图可以有独特主题(草地、火山、雪原),用不同 tile 集
3. **节奏分明**:玩家"穿越"地图时有心理切换感(可以加过场动画、过渡效果)
4. **状态隔离**:每张地图可以独立保存状态(墙破没破、怪物在不在)

但多 tile map 引入几个**新问题**:

- **边界检测**:玩家走到地图边缘,怎么判断"该切到下一张地图了"?
- **位置衔接**:切到新地图后,玩家应该出现在新地图的哪个位置?
- **状态保留**:玩家在地图 A 杀了怪物,走到 B 再回来——怪物还在吗?
- **过渡效果**:硬切换(瞬间换地图)还是软切换(淡入淡出)?

Casey 这集解决前两个(边界检测 + 位置衔接),给出第三、四个的初步思路(状态保留用"tile 持久 / entity 重置",过渡效果后面再加)。

心理锚点:看完这集,你应该能用一张图描述"多 tile map 怎么用 `door_north / door_south / door_east / door_west` 这种字段连接",能解释"为什么 tile 数据保留而 entity 重置"。Day 031 形式化坐标系,Day 033+ 演化到虚拟化大世界(连续地图无切换),都是这集思想的延伸。

## 2 · 心智模型

### 类比:博物馆的展厅

把多 tile map 想象成**博物馆的多个展厅**:

- 每个展厅是一个独立的房间(独立的 tile map)
- 展厅之间通过门连接(door_north / door_south 等字段)
- 你站在一个展厅里,只能看到这个展厅的内容(只渲染当前地图)
- 走到展厅北门,穿过门,进入相邻展厅(切到 door_north 指向的地图)
- 进入新展厅后,你站在新展厅的南门附近(因为你是从北门"过来"的)

每个展厅(地图)有:

- 固定内容:墙、地板、展品(tile 数据)
- 临时内容:其他游客、临时展板(entity 数据)

**关键决策**:你离开一个展厅再回来,固定内容(墙、展品)不变,临时内容(游客)可能变了。游戏里就是:

- **tile 数据保留**:你打破的墙还是破的,你打开的门还是开的
- **entity 数据重置**:你杀的怪物可能刷新(可以反复刷),临时投射物消失

这是游戏设计的经典模式。后面详谈。

### 数据结构

```rust
struct World {
    maps: Vec<TileMap>,        // 所有的地图
    current_map_idx: usize,    // 当前在哪个地图
}

struct TileMap {
    tiles: Vec<TileValue>,
    width: i32, height: i32,

    // 哪条边连到哪张地图(None = 没出口,边界是封闭的)
    door_north: Option<usize>,
    door_south: Option<usize>,
    door_east: Option<usize>,
    door_west: Option<usize>,
}
```

`Option<usize>` 是 Rust 的"可能没有"类型。`Some(3)` 表示"连到第 3 张地图",`None` 表示"没有出口(地图边缘是封闭的)"。

### 边界检测 + 切换逻辑

每帧检查玩家位置:

```rust
fn check_boundary(player: &mut Player, world: &mut World) {
    let map = &world.maps[world.current_map_idx];
    let map_width_px = map.width * TILE_SIZE;
    let map_height_px = map.height * TILE_SIZE;

    // 走到西边边界(x < 0)
    if player.pos.x < 0.0 {
        if let Some(target_idx) = map.door_west {
            // 切到西边地图
            world.current_map_idx = target_idx;
            // 玩家从新地图的东边进入
            let new_map = &world.maps[target_idx];
            player.pos.x = (new_map.width * TILE_SIZE - PLAYER_SIZE) as f32;
            return;
        } else {
            // 没有西出口,把玩家推回来
            player.pos.x = 0.0;
        }
    }

    // 类似处理东、南、北
    if player.pos.x + PLAYER_SIZE as f32 > map_width_px as f32 {
        if let Some(target_idx) = map.door_east {
            world.current_map_idx = target_idx;
            player.pos.x = 0.0;  // 从新地图西边进入
            return;
        } else {
            player.pos.x = (map_width_px - PLAYER_SIZE) as f32;
        }
    }

    if player.pos.y < 0.0 {
        if let Some(target_idx) = map.door_north {
            world.current_map_idx = target_idx;
            let new_map = &world.maps[target_idx];
            player.pos.y = (new_map.height * TILE_SIZE - PLAYER_SIZE) as f32;
            return;
        } else {
            player.pos.y = 0.0;
        }
    }

    if player.pos.y + PLAYER_SIZE as f32 > map_height_px as f32 {
        if let Some(target_idx) = map.door_south {
            world.current_map_idx = target_idx;
            player.pos.y = 0.0;
            return;
        } else {
            player.pos.y = (map_height_px - PLAYER_SIZE) as f32;
        }
    }
}
```

**关键细节**:

- 切地图时,**玩家位置 adjust 到新地图的对应边**。比如从地图 A 的西边走出去,进入地图 B,玩家应该出现在 B 的东边——这样视觉上"自然延续"
- `if let Some(target_idx) = map.door_west` 是 Rust 处理 Option 的标准模式。`if let` 解构,匹配 `Some(x)` 时执行,x 绑定到内部值。`None` 时跳过
- `return` 提前退出函数,因为切地图后后面的检查没意义(地图都换了)

### 状态保留策略

Casey 这集讨论了"切地图回来,状态保留什么"的问题。三种策略:

**策略 1:全部保留**(把每张地图的所有状态都存)

- 优点:玩家觉得世界"真实",任何状态都永久保留
- 缺点:内存爆炸(每张地图存所有 entity),玩家积攒大量"未处理"事件,游戏越玩越乱

**策略 2:全部重置**(每次进入地图都重新生成)

- 优点:内存可控,游戏简单
- 缺点:玩家打破的墙又长回来,违和;玩家打开的门又关上,卡关;任务进度丢失

**策略 3:混合**(Casey 选这个)

- **tile 数据保留**:墙破了还是破的,门开了还是开的——世界状态稳定
- **entity 数据重置**:怪物会刷新(可以反复刷经验),临时投射物消失——避免内存爆炸 + 提供刷怪机会

这种"持久 vs 临时"二分是游戏设计的常见模式。**MMO 更激进**:玩家房屋永久保留,NPC 定时刷新。**Roguelike 全部重置**:每次进入一个全新地图,这是 roguelike 的核心玩法。Casey 选中间方案,适合教学。

实现层面:

```rust
struct TileMap {
    tiles: Vec<TileValue>,    // ← 持久:不随切换重置
    width: i32, height: i32,
    doors: ...,
}

struct MapEntityState {
    monsters: Vec<Monster>,   // ← 临时:进入地图时重新生成
    projectiles: Vec<Projectile>,
}

struct World {
    maps: Vec<TileMap>,                   // 持久数据
    // 临时数据按需生成,不存这里
}
```

进入一张地图时:

```rust
fn enter_map(world: &mut World, map_idx: usize) -> MapEntityState {
    let map = &world.maps[map_idx];
    let mut state = MapEntityState { monsters: vec![], projectiles: vec![] };
    // 根据 tile 数据生成怪物(比如每个 Water tile 旁有 50% 概率刷水怪)
    for ty in 0..map.height {
        for tx in 0..map.width {
            if map.get(tx, ty) == TileValue::Water && rng.gen::<f32>() < 0.5 {
                state.monsters.push(Monster::water_at(tx as f32 * 32.0, ty as f32 * 32.0));
            }
        }
    }
    state
}
```

这是 procedural generation(过程化生成)的雏形。Day 033+ Casey 把它扩展为"无限世界"。

### 过渡效果:淡入淡出

切地图瞬间,屏幕"硬切"——上一帧是地图 A,这一帧突然变地图 B。视觉上很突兀。

**淡入淡出**:切换瞬间整个屏幕渐变到黑(100ms),切完后从黑渐变到正常(100ms)。比硬切换舒服得多。

实现思路:

```rust
struct World {
    // ...
    transition_alpha: f32,        // 0 = 正常,1 = 全黑
    pending_switch: Option<usize>,  // 切换中,目标地图
}

fn update(world: &mut World, player: &mut Player, input: &GameInput, dt: f32) {
    // 正常 update
    if world.transition_alpha < 0.01 {
        // 没有 transition,正常逻辑
        player.update(&world.maps[world.current_map_idx], input, dt);
        check_boundary(player, world);  // 可能触发 transition
    } else {
        // transition 中:渐变 alpha,中间点切换地图
        if world.transition_alpha < 0.5 && world.pending_switch.is_some() {
            // 中间点:执行切换
            world.current_map_idx = world.pending_switch.unwrap();
            world.pending_switch = None;
            // adjust 玩家位置...
        }
        world.transition_alpha += dt * 4.0;  // 250ms 完成
        if world.transition_alpha > 1.0 {
            world.transition_alpha = 1.0;
            // 反向开始变亮...
        }
    }
}

fn render(world: &World, fb: &mut [u32]) {
    // 正常渲染当前地图
    render_tiles(&world.maps[world.current_map_idx], ..., fb);

    // 如果 transition 中,叠加黑色
    if world.transition_alpha > 0.01 {
        let black_amount = world.transition_alpha;
        for pixel in fb.iter_mut() {
            // 把每个像素往黑色拉
            let r = (*pixel >> 16 & 0xFF) as f32 * (1.0 - black_amount);
            let g = (*pixel >> 8 & 0xFF) as f32 * (1.0 - black_amount);
            let b = (*pixel & 0xFF) as f32 * (1.0 - black_amount);
            *pixel = ((r as u32) << 16) | ((g as u32) << 8) | (b as u32);
        }
    }
}
```

Casey 这集**不实现**过渡效果,只给思路。Day 035+ 才加完整过渡。

### 整体 update / render 流程

```rust
fn game_update(state: &mut GameState, input: &GameInput, dt: f32) {
    let map = &state.world.maps[state.world.current_map_idx];

    // 1. 玩家移动 + 碰撞
    state.player.update(map, input, dt);

    // 2. 边界检测 + 可能切地图
    check_boundary(&mut state.player, &mut state.world);

    // 3. 如果切了地图,重新生成 entity
    if state.last_map_idx != state.world.current_map_idx {
        state.entity_state = enter_map(&mut state.world, state.world.current_map_idx);
        state.last_map_idx = state.world.current_map_idx;
    }

    // 4. 更新 entity(怪物 AI、投射物)
    for m in &mut state.entity_state.monsters {
        m.update(dt, &state.player);
    }
}

fn game_render(state: &GameState, fb: &mut [u32]) {
    let map = &state.world.maps[state.world.current_map_idx];

    // 1. 渲染 tile map
    render_tiles(map, ..., fb);

    // 2. 渲染 entity
    for m in &state.entity_state.monsters {
        render_monster(m, fb);
    }

    // 3. 渲染玩家
    render_player(&state.player, fb);
}
```

注意 Day 026 的"三明治分层"在 Day 030 完整体现——`update` 改 state,`render` 读 state。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

多地图结构在游戏开发里叫 **hub world**(中心世界)或 **level-based**(关卡制)。主流变体:

**变体 1:Hub world(中心世界)**

- 一个中心地图(hub)连接多个子地图(levels)
- 玩家从 hub 选择进入哪个 level
- 例:超级马里奥 64(城堡是 hub,画作是 levels)、Crash Bandicoot

**变体 2:Linear progression(线性进度)**

- 地图按顺序排列,玩家从第 1 张到第 N 张
- 例:超级马里奥兄弟(World 1-1 → 1-2 → ...)
- Casey 这集结构上接近这种

**变体 3:Open world(开放世界)**

- 一张大地图,无切换
- 例:GTA、Skyrim、塞尔达旷野之息
- 内存压力大,但沉浸感最强

**变体 4:Metroidvania**

- 大世界互联,需要解锁能力(二段跳、变身)才能到达新区域
- 例:空洞骑士、Super Metroid
- Casey Day 033+ 接近这种(连续大世界)

**变体 5:Instance-based(副本)**

- MMO 风格,每个队伍独立地图
- 例:魔兽世界副本、命运 2 strike

Casey Day 030 做 hub world 雏形,Day 033+ 升级为虚拟化大世界(变体 4)。

### 3.2 · 🎨 图形学视角

切地图时的过渡效果是图形学的一个小话题。常见过渡:

| 过渡 | 实现 | 视觉效果 |
|---|---|---|
| 硬切 | 无 | 突兀 |
| 淡入淡出 | 全屏 alpha | 经典,常用于关卡通切换 |
| 滑动 | 偏移整个 framebuffer | 横向 / 纵向滑动,适合"相邻"地图 |
| 缩放 | framebuffer 中心缩放 | "进入"感,适合进入"小世界" |
| 模糊 | framebuffer 高斯模糊 | 梦境 / 时间流逝感 |
| 像素化 | framebuffer 马赛克化 | 复古 / 传送感 |

Casey Day 030 只讨论淡入淡出。商业引擎(Unity / Unreal)有完整 post-processing stack,一键加各种过渡。

### 3.3 · 🐧 Linux 系统编程视角

"切地图"在系统编程里对应"加载资源"。Linux 上加载新地图有几种方式:

**方式 1:同步 read**(简单,但有卡顿)

```rust
let data = std::fs::read("assets/map2.bin")?;
let map = parse_map(&data)?;
```

加载时主线程阻塞,游戏卡 N 毫秒。N 取决于文件大小和磁盘速度。

**方式 2:异步加载**(用线程)

```rust
let handle = std::thread::spawn(|| {
    let data = std::fs::read("assets/map2.bin").unwrap();
    parse_map(&data).unwrap()
});
// 主线程继续渲染过渡动画
let map = handle.join().unwrap();
```

主线程不阻塞,可以同时渲染过渡动画掩盖加载时间。这是商业游戏的标配。

**方式 3:mmap + 懒加载**

```rust
let file = std::fs::File::open("assets/map2.bin")?;
let mmap = unsafe { memmap2::Mmap::map(&file)? };
// mmap 不实际读文件,只有访问 mmap[i] 时才从磁盘读
```

适合"大文件,只访问部分"的场景。

**方式 4:预加载**(所有地图开游戏时全加载)

```rust
let maps: Vec<TileMap> = (0..N).map(|i| load_map(format!("assets/map{}.bin", i))).collect();
```

简单但内存占用大。适合小地图集。

Casey 在 Phase 2 早期用方式 4(教学清晰),Day 200+ 加资产系统后切到方式 1/2。Day 436+ PNG 解码可能用方式 2 异步加载。

**Linux 上验证加载时间**:

```bash
# 用 strace 看游戏启动时打开了哪些文件
strace -e trace=openat -f ./your_game 2>&1 | grep assets
# 输出每个 openat 系统调用,看到加载顺序

# 用 time 看启动总时间

# 输出 real(实际时间)、user(CPU 时间)、sys(系统调用时间)
# 如果 real 远大于 user + sys,说明在等 IO(磁盘)
```

### 3.4 · 🦀 Rust 生态视角

Rust 表达"多地图 + 边界连接"有几种方式:

**方式 1:`Vec<TileMap>` + index**(Casey 选这个)

```rust
struct World {
    maps: Vec<TileMap>,
    current_map_idx: usize,
}
struct TileMap {
    door_north: Option<usize>,  // 用 index 引用其他 map
    ...
}
```

优点:简单。缺点:**不能动态加 map**(后面 push 新 map 时,index 不稳定——`Vec` 扩容可能移动元素地址,但 index 不会变,所以这个其实没问题)。**不能删除 map**(删除后 index 错乱)。

**方式 2:`HashMap<MapId, TileMap>`**

```rust
struct World {
    maps: HashMap<MapId, TileMap>,
    current: MapId,
}
struct TileMap {
    door_north: Option<MapId>,
    ...
}
```

MapId 是 stable id(字符串 / u64 hash)。可以动态加 / 删 map。代价:每次访问要 hash lookup,比 Vec 慢一点。

**方式 3:图结构**

```rust
struct World {
    maps: HashMap<MapId, TileMap>,
    edges: Vec<(MapId, Direction, MapId)>,  // 边的列表
}
```

把"连接关系"独立成图。适合复杂拓扑(非 grid 的连接)。

**方式 4:SlotMap**(代际索引)

```rust
use slotmap::SlotMap;
slotmap::new_key_type! { struct MapKey; }
struct World {
    maps: SlotMap<MapKey, TileMap>,
    current: MapKey,
}
```

SlotMap 给每个 entry 一个"代",删除后再次分配时**代 +1**,旧的代访问会返回 None。这能识别"悬空引用"——你存了一个旧 MapKey,后来这个 map 被删了,你的 key 失效。

Casey 用方式 1(教学最优)。生产代码可能用方式 4(SlotMap)。

**Rust 所有权陷阱**:

```rust
// ❌ 这段代码非法
fn check_boundary(player: &mut Player, world: &mut World) {
    let map = &world.maps[world.current_map_idx];  // 借了 world
    if player.pos.x < 0.0 {
        if let Some(target_idx) = map.door_west {
            world.current_map_idx = target_idx;  // 改 world——但 world 还被借着!
        }
    }
}
```

Rust 编译器会拒绝:`world` 被 `map` 借走,不能同时改。解决方法:**先复制 door 索引,放下借用,再改 world**:

```rust
fn check_boundary(player: &mut Player, world: &mut World) {
    // 先把 door 索引 copy 出来(usize 是 Copy 类型)
    let door_west = world.maps[world.current_map_idx].door_west;
    let door_east = world.maps[world.current_map_idx].door_east;
    // ... 现在不再借 world.maps,可以改 world 了

    if player.pos.x < 0.0 {
        if let Some(target_idx) = door_west {
            world.current_map_idx = target_idx;
            // ...
        }
    }
}
```

或者用 `std::mem::replace` / `std::mem::take` 在原地操作。Casey 在 HH 里经常用这种"先 copy 出来再操作"的模式。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 让 tile 数据保留(墙破了回来还是破的),entity 重置(怪物回来又有了)。为什么不全部保留?为什么不全部重置?

**参考解答**:

**全部保留的问题**:

1. **内存爆炸**:每张地图所有 entity 都存,N 张地图 × M 个 entity / map = N×M 个 entity 永久占内存
2. **玩家积攒大量"未处理"entity**:游戏越玩越乱,玩家杀不玩的怪物堆在某地图
3. **临时 entity 保留无意义**:粒子效果、爆炸碎片、投射物——这些"几秒就该消失"的东西永久存没意义

**全部重置的问题**:

1. **玩家打破的墙又长回来**:违和(墙是物理对象,不会"复活")
2. **玩家打开的门又关上**:卡关(玩家可能用开门操作解锁了路径,门关上后路堵了)
3. **任务进度丢失**:玩家在地图 A 完成的任务,离开回来发现又没完成

**混合策略**(Casey 选这个):

- **tile 保留**:世界状态稳定,玩家的改动有持久影响
- **entity 重置**:怪物可反复刷(玩家刷经验),临时效果消失(避免内存堆积)

延伸:不同游戏选不同平衡。

| 游戏 | 策略 | 原因 |
|---|---|---|
| MMO(魔兽) | 激进持久(玩家房屋)+ 怪物定时刷新 | 多人需要一致世界 + 刷怪需求 |
| Roguelike(杀戮尖塔) | 全部重置(每次新地图) | 核心玩法是"每次重新来过" |
| 单机 RPG(塞尔达) | 关键道具持久 + 怪物重置 | 解锁感 + 刷怪需求 |
| Casey HH | tile 持久 + entity 重置 | 教学清晰 |

### Lv2 · 动手实践

**题**:基于 day028/029 的代码,加多 tile map 支持。要求:

1. 3 张地图:草地、森林、沙漠(用不同 tile 颜色)
2. 草地的东边连到森林的西边,森林的东边连到沙漠的西边
3. 玩家从草地中央出发,向东走能进入森林,再向东走能进入沙漠
4. 每次切地图,终端打印 "Entering map X"

完成标准:`cargo run` 跑出"切地图"的效果(用文字输出代替图形渲染,验证逻辑)。

**参考解答**:

```rust
// src/main.rs
// cargo new --bin multi_map && cd multi_map

const TILE_SIZE: i32 = 32;
const PLAYER_SIZE: i32 = 32;

#[derive(Copy, Clone, Debug, PartialEq)]
enum TileValue { Empty, Grass, Tree, Sand, Rock }

struct TileMap {
    tiles: Vec<TileValue>,
    width: i32, height: i32,
    name: &'static str,
    door_north: Option<usize>,
    door_south: Option<usize>,
    door_east: Option<usize>,
    door_west: Option<usize>,
}

impl TileMap {
    fn new(name: &'static str, width: i32, height: i32, fill: TileValue) -> Self {
        Self {
            tiles: vec![fill; (width * height) as usize],
            width, height, name,
            door_north: None, door_south: None,
            door_east: None, door_west: None,
        }
    }
    fn get(&self, tx: i32, ty: i32) -> TileValue {
        if tx < 0 || ty < 0 || tx >= self.width || ty >= self.height {
            return TileValue::Rock;  // 越界当墙
        }
        self.tiles[(ty * self.width + tx) as usize]
    }
}

#[derive(Default, Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

struct Player { pos: Vec2 }

struct World {
    maps: Vec<TileMap>,
    current: usize,
}

fn check_boundary(player: &mut Player, world: &mut World) -> Option<&'static str> {
    let map = &world.maps[world.current];
    let map_width_px = map.width * TILE_SIZE;
    let map_height_px = map.height * TILE_SIZE;

    // 西边
    if player.pos.x < 0.0 {
        if let Some(target) = map.door_west {
            world.current = target;
            let new_map = &world.maps[target];
            player.pos.x = (new_map.width * TILE_SIZE - PLAYER_SIZE) as f32;
            return Some(new_map.name);
        }
        player.pos.x = 0.0;
    }
    // 东边
    if player.pos.x + PLAYER_SIZE as f32 > map_width_px as f32 {
        if let Some(target) = map.door_east {
            world.current = target;
            player.pos.x = 0.0;
            return Some(world.maps[target].name);
        }
        player.pos.x = (map_width_px - PLAYER_SIZE) as f32;
    }
    // 北边
    if player.pos.y < 0.0 {
        if let Some(target) = map.door_north {
            world.current = target;
            let new_map = &world.maps[target];
            player.pos.y = (new_map.height * TILE_SIZE - PLAYER_SIZE) as f32;
            return Some(new_map.name);
        }
        player.pos.y = 0.0;
    }
    // 南边
    if player.pos.y + PLAYER_SIZE as f32 > map_height_px as f32 {
        if let Some(target) = map.door_south {
            world.current = target;
            player.pos.y = 0.0;
            return Some(world.maps[target].name);
        }
        player.pos.y = (map_height_px - PLAYER_SIZE) as f32;
    }
    None
}

fn main() {
    // 构造 3 张地图
    let mut grass = TileMap::new("Grass", 20, 15, TileValue::Grass);
    let mut forest = TileMap::new("Forest", 20, 15, TileValue::Tree);
    let mut desert = TileMap::new("Desert", 20, 15, TileValue::Sand);

    // 设置连接关系
    grass.door_east = Some(1);    // 草地东 → 森林
    forest.door_west = Some(0);   // 森林西 → 草地
    forest.door_east = Some(2);   // 森林东 → 沙漠
    desert.door_west = Some(1);   // 沙漠西 → 森林

    let mut world = World {
        maps: vec![grass, forest, desert],
        current: 0,
    };

    let mut player = Player {
        pos: Vec2 { x: 10.0 * 32.0, y: 7.0 * 32.0 }  // 草地中央
    };

    println!("Start in {}", world.maps[world.current].name);
    println!("Player at ({}, {})", player.pos.x as i32, player.pos.y as i32);

    // 模拟:玩家持续向右走 30 秒(应该穿过 3 张地图)
    let dt = 0.0167_f32;
    let speed = 200.0_f32;
    let mut sim_time = 0.0;
    let mut last_map = world.current;

    while sim_time < 30.0 {
        // 持续向右
        player.pos.x += speed * dt;
        sim_time += dt;

        // 边界检测
        if let Some(new_name) = check_boundary(&mut player, &mut world) {
            if world.current != last_map {
                println!("[t={:.1}] Entered {} (player at ({}, {}))",
                    sim_time, new_name, player.pos.x as i32, player.pos.y as i32);
                last_map = world.current;
            }
        }
    }
}
```

**预期输出**:

```
Start in Grass
Player at (320, 224)
[t=2.0] Entered Forest (player at (0, 224))
[t=4.0] Entered Desert (player at (0, 224))
```

玩家从草地(20 tile 宽 = 640 像素)中央(320 像素)出发,向右以 200 像素/秒走。约 (640-320)/200 = 1.6 秒后到东边,触发切换。但 dt 离散步进,可能 2.0 秒才触发。

**每行解释**:

- `TileMap::new(name, w, h, fill)` —— 创建一张用 `fill` tile 填满的地图。教学简化,真实游戏从文件加载
- `door_east: Some(1)` —— 草地东连到 maps[1](forest)。Some 是 Option 的有值变体
- `check_boundary` 返回 `Option<&'static str>` —— 切了地图返回新地图名(便于打印日志),没切返回 None
- `if let Some(target) = map.door_west` —— 解构 Option。Some 时执行,target 绑定内部值;None 时跳过

    fn check_boundary(&mut self, player: &mut Player) -> Option<&'static str> {
        // 先 copy 出 door 信息(避免借用冲突)
        let (door_w, door_e, door_n, door_s) = {
            let map = &self.maps[self.current];
            (map.door_west, map.door_east, map.door_north, map.door_south)
        };

        // 西边
        if player.pos.x < 0.0 {
            if let Some(target) = door_w {
                self.current = target;
                let new_w = self.maps[target].width * TILE_SIZE;
                player.pos.x = (new_w - PLAYER_SIZE) as f32;
                return Some(self.maps[target].name);
            }
            player.pos.x = 0.0;

        // 东边

            if let Some(target) = door_e {
                self.current = target;
                player.pos.x = 0.0;
                return Some(self.maps[target].name);
            }
            player.pos.x = (map_w_px - PLAYER_SIZE) as f32;
        }
        // 北边
        if player.pos.y < 0.0 {
            if let Some(target) = door_n {
                self.current = target;
                let new_h = self.maps[target].height * TILE_SIZE;
                player.pos.y = (new_h - PLAYER_SIZE) as f32;
                return Some(self.maps[target].name);
            }
            player.pos.y = 0.0;

            if let Some(target) = door_s {
                self.current = target;
                player.pos.y = 0.0;
                return Some(self.maps[target].name);
            }
            player.pos.y = (map_h_px - PLAYER_SIZE) as f32;
        }
        None
    }

    }

    #[test]
    fn walk_west_from_forest_switches_to_grass() {
        let mut world = make_test_world();
        world.current = 1;  // 从森林开始
        let mut player = Player { pos: Vec2 { x: 0.0, y: 0.0 } };
        player.pos.x -= 100.0;
        let result = world.check_boundary(&mut player);
        assert_eq!(result, Some("Grass"));
        assert_eq!(world.current, 0);
        // 玩家应该出现在草地的东边
        let expected_x = (world.maps[0].width * TILE_SIZE - PLAYER_SIZE) as f32;
        assert_eq!(player.pos.x, expected_x);
    }

    #[test]
    fn walking_north_with_no_door_blocks() {
        let mut world = make_test_world();
        let mut player = Player { pos: Vec2 { x: 100.0, y: 0.0 } };
        player.pos.y -= 50.0;
        let result = world.check_boundary(&mut player);
        assert_eq!(result, None);
        assert_eq!(player.pos.y, 0.0);
    }
}

**Troubleshooting**:

- `error: borrow checker` —— `check_boundary` 内部既读 `self.maps` 又改 `self.current`,要先 copy 出 door 信息再改 self。这是 Rust 所有权规则的常见模式。
- 切地图后玩家位置错 —— 检查 `enter from` 逻辑。从西边进入新地图,玩家应该在东边(`x = map_width_px - PLAYER_SIZE`),不是 0。
- 测试失败,actual ≠ expected —— 注意 f32 → i32 转换的截断。`19.0 * 32.0 = 608.0`,as i32 = 608,没问题。但 `19.5 * 32.0 = 624.0`,as i32 = 624。
