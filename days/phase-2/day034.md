# Day 034 · 瓦片地图内存布局

> Day 033 你实现虚拟化 tile map,但用的是 HashMap。看起来 O(1) 够快,但 Casey 这集指出:**HashMap 的 O(1) 和 Array 的 O(1) 不一样快**——常数因子差 10-25 倍。这集引入 **Data-Oriented Design**(数据导向设计)的核心思想:**数据布局比算法更影响性能**。这是从"程序员视角"切换到"硬件视角"的关键一课。

## 0 · 为什么要有这一天

你大概听过"O(1) 比 O(n) 快"——这是大 O 表示法的直觉。但**实际工程里**,O(1) 之间也可能差 10-25 倍。

具体看一个例子。渲染 1000 个 tile,每个 tile 要 `map.get(tx, ty)` 一次。两种实现:

**实现 A:HashMap**

```rust
let map: HashMap<(i32, i32), TileValue> = ...;
for tile in visible_tiles {
    let v = map.get(&(tile.x, tile.y));  // O(1),但每次 50-100 cycle
}
```

**实现 B:Array**

```rust
let map: Vec<TileValue> = vec![...; WIDTH * HEIGHT];
for tile in visible_tiles {
    let v = map[tile.y * WIDTH + tile.x];  // O(1),每次 4 cycle(L1 cache hit)
}
```

两者都是 O(1)。但 1000 次访问:

- HashMap:1000 × 80 cycle ≈ 80,000 cycle ≈ 25 微秒(3 GHz CPU)
- Array:1000 × 4 cycle ≈ 4,000 cycle ≈ 1.3 微秒

差 **20 倍**。1000 tile 不是问题,但 10000 tile(开放世界大场景)就 250 vs 13 微秒——还是差 20 倍,但绝对值 240 微秒,玩家肉眼能看到卡顿。

**根因**:HashMap 每次访问要算 hash、查表、可能 cache miss(HashMap 内部是稀疏数组,内存不连续)。Array 直接算 index × size,内存连续,L1 cache 几乎必然命中。

这就是 **Data-Oriented Design** 的核心:**数据的内存布局**(怎么放)比**算法**(怎么找)更影响性能。

Casey 这集做的事情:

1. 对比 HashMap / Array / Hybrid 三种 tile map 存储方案
2. 解释 CPU cache 层次结构(L1 / L2 / L3 / 主存)
3. 解释 **cache line**(64 字节,一次读最小单位)
4. 提出"为 cache 设计数据布局"的思想

这集不写大量代码(主要讨论),但**思想贯穿后面所有性能优化集**(Day 112+ SIMD、Day 200+ 内存布局优化)。

心理锚点:看完这集,你应该能:

## 2 · 心智模型

### 类比:仓库 vs 散乱堆放

想象两种仓库:

**仓库 A(数组式)**:货物按编号顺序放在货架上,每件货物紧贴下一件。要找第 N 件,直接走到第 N 个货架。**找得快**。

**仓库 B(HashMap 式)**:货物散乱放在仓库各处,有个"目录"告诉你"第 N 件在哪个角落"。要找第 N 件,先查目录,再走过去。**找得慢**(查目录 + 走两步)。

但仓库 B 有个优点:**可以放编号不连续的货物**(比如只有第 1, 100, 5000 件)。仓库 A 必须连续,中间空位也要占地方。

游戏里:

- **Array**:像仓库 A,适合"稠密"数据(tile 全满的地图)
- **HashMap**:像仓库 B,适合"稀疏"数据(tile 大部分空的地图)

### CPU Cache 层次结构

现代 CPU 有多级 cache:

```
              延迟        大小
   ┌──────────────────┐
   │  寄存器           │ 0 cycle      ~200 个
   └──────────────────┘
            ↑
   ┌──────────────────┐
   │  L1 cache        │ 4 cycle      32 KB / 核心
   └──────────────────┘
            ↑
   ┌──────────────────┐
   │  L2 cache        │ 12 cycle     256 KB - 1 MB / 核心
   └──────────────────┘
            ↑
   ┌──────────────────┐
   │  L3 cache        │ 40 cycle     几 MB - 几十 MB / 全 CPU 共享
   └──────────────────┘
            ↑
   ┌──────────────────┐
   │  主存(RAM)       │ 200+ cycle   GB 级
   └──────────────────┘
```

**关键**:

- L1 极快(4 cycle ≈ 1 纳秒),但极小(32KB)
- 主存极慢(200 cycle ≈ 70 纳秒),但极大
- **每差一级,慢 3-10 倍**

CPU 访问主存的延迟是 L1 的 **50 倍**。所以"避免 cache miss"是性能优化的核心。

### Cache Line:一次读 64 字节

CPU 不是按字节读内存,而是按 **cache line**(缓存行)读——一次 64 字节。

```
你访问 byte[100]:
  CPU 看 100 在哪个 cache line:100 / 64 = 1(第 1 个 cache line)
  CPU 把 byte[64..128] 全部读到 L1
  返回 byte[100]

接下来你访问 byte[101]:
  已经在 L1 里(因为 byte[100] 触发了整行读)
  直接返回,4 cycle

接下来你访问 byte[200]:
  不在 L1
  触发新 cache line 读,把 byte[192..256] 读到 L1
  200+ cycle
```

**关键**:**连续访问内存**比**跳跃访问**快得多。连续访问(数组遍历)几乎都在 L1 命中,跳跃访问(HashMap / 链表)经常 cache miss。

### Array 的内存布局

```rust
let arr: Vec<TileValue> = vec![...; 1000];
// 内存布局(假设 TileValue = 1 字节):
// [t0][t1][t2][t3]...[t63] | [t64][t65]...[t127] | ...
//  ↑___ cache line 0 ____↑   ↑___ cache line 1 ___↑
//
// 一个 cache line 装得下 64 个 TileValue
```

遍历 1000 个 tile:

- 第 1 个 tile:cache miss(读 cache line),4 cycle + 200 cycle = 204 cycle
- 第 2-64 个 tile:cache hit,4 cycle each
- 第 65 个 tile:cache miss(下一个 cache line),204 cycle
- 第 66-128:cache hit
- ...

平均:每 64 个 tile 一次 cache miss,所以 1000 / 64 ≈ 16 次 miss,16 × 204 + 1000 × 4 ≈ 7300 cycle。

**单次访问平均 7.3 cycle**。

### HashMap 的内存布局

```rust
let map: HashMap<Key, Value> = ...;
// 内部结构:
// - buckets: Vec<Option<(Key, Value)>>,稀疏数组
// - 每个 bucket 可能空,可能有值
// - hash 后 modulo bucket_count 得到 index
//
// 内存布局(假设 8 字节 Key + 1 字节 Value):
// [bucket0][bucket1][bucket2]...[bucketN]
// 每个 bucket 16 字节(对齐),装 Key+Value 或 None
```

遍历 1000 个 tile(查 map):

- 每个 get:算 hash(20 cycle)+ 找 bucket(cache miss 可能,200 cycle)
- 平均每次 80-100 cycle(假设 50% cache miss)

**单次访问平均 80 cycle**。

### 对比总结

| 方案 | 单次访问(cycle) | 1000 次访问(微秒) | 内存占用 |
|---|---|---|---|
| Array | 7.3 | 2.4 | N elements 紧凑 |
| HashMap | 80 | 27 | N elements + ~50% overhead |
| 链表 | 200+(每次 cache miss) | 67 | N elements + 每个节点指针 |

Array 比 HashMap 快 ~10 倍,比链表快 ~30 倍。这就是 **Data-Oriented Design** 的威力。

### 三种 tile map 存储方案对比

**方案 A:HashMap<(i32, i32), TileMap>**(Day 033 用)

```rust
maps: HashMap<TileCoord, TileMap>
```

- 优点:任意坐标能存,稀疏友好
- 缺点:每次访问 ~80 cycle,缓存不友好
- 适合:**地图分布稀疏**(玩家只在某些区域活动)

**方案 B:Array**(完整 2D 数组)

```rust
maps: Vec<TileMap>  // 固定大小,WORLD_W * WORLD_H
fn index(x: i32, y: i32) -> usize { (y * WORLD_W + x) as usize }
```

- 优点:O(1) 访问,极快(~7 cycle),无元数据
- 缺点:固定大小,大量空位浪费内存
- 适合:**地图分布稠密**(整个世界都有内容)

**方案 C:Hybrid(混合)**——世界分大网格(chunk),每 chunk 内用 Array

```rust
const CHUNK_SIZE: i32 = 16;
maps: HashMap<ChunkCoord, [TileMap; (CHUNK_SIZE * CHUNK_SIZE) as usize]>
```

- 优点:chunk 内 Array 快,chunk 间 HashMap 灵活
- 缺点:实现复杂
- 适合:**地图分布中等稀疏**(局部稠密,全局稀疏)

**Casey 的选择**:Day 034 不立刻重构(用 HashMap 还合理),Day 035 实现稀疏存储时再考虑 hybrid。

### Mike Acton 的 Data-Oriented Design

Mike Acton(原 Insomniac Games 引擎主管)在 GDC 2014 演讲 "Data-Oriented Design and C++":

> **"The vast majority of software engineering is about getting the data layout right."**
>
> (软件工程的绝大部分,是关于把数据布局做对。)

核心思想:

1. **先想数据布局,再想算法**。传统 OOP 是"对象 + 行为",DOD 是"数据 + 转换"。
2. **数据布局 = 内存里怎么排**。Array 紧凑 vs HashMap 稀疏 vs SoA(struct of arrays)。
3. **不同场景不同布局**。一个数据结构不是"通用最好",而是"针对场景最优"。

DOD 不是反对 OOP,是反对"无脑封装"。游戏开发里**性能是产品需求**,DOD 把性能放到第一位。

### SoA(Struct of Arrays)vs AoS(Array of Structs)

DOD 里的另一个关键概念。假设有 1000 个 entity,每个有 pos 和 vel:

**AoS**(Array of Structs):

```rust
struct Entity { pos: Vec2, vel: Vec2 }
let entities: Vec<Entity> = ...;
// 内存:[pos0,vel0,pos1,vel1,pos2,vel2,...]
```

**SoA**(Struct of Arrays):

```rust
struct Entities {
    pos: Vec<Vec2>,
    vel: Vec<Vec2>,
}
let entities: Entities = ...;
// 内存:[pos0,pos1,pos2,...] [vel0,vel1,vel2,...]
```

**性能差异**:如果只想遍历 pos 不用 vel:

- AoS:每个 entity 读 16 字节(pos + vel),但你只用 8 字节(pos)。50% 浪费。
- SoA:只读 pos 数组,完全用上。0% 浪费。

**SIMD 友好**:SoA 的 pos 数组 `[pos0, pos1, pos2, ...]` 可以直接 SIMD 加载(4 个 pos 一次),AoS 不行(pos 和 vel 交错)。

Casey 在 Day 1-200 用 AoS(简单),Day 200+ 性能优化时讨论 SoA。Bevy ECS 用 SoA 风格(每个 Component 独立 Vec)。

### 实践建议

1. **hot path 优先 Array**。碰撞检测、渲染、update 这些每帧跑的代码,优先 Array
2. **cold path 用 HashMap 没事**。初始化、加载、配置读——这些一次性或低频的,HashMap 无所谓
3. **profiler 决定**。不要瞎猜,用 perf / valgrind --tool=cachegrind 看真实热点
4. **数据布局和算法分开考虑**。"Vec<TileValue>"是布局,"get(tx, ty)"是算法。两个独立优化

### 3.1 · 🎮 游戏编程视角

游戏开发圈普遍接受 DOD。主流引擎的设计:

**Unity DOTS(Data-Oriented Technology Stack)**:Unity 2018+ 推出 DOTS,基于 ECS(Entity-Component-System),核心是 DOD。Unity 官方说 DOTS 比传统 OOP 快 10-100 倍。

**Unreal Engine Mass Entity**:UE 5+ 加入了类似 ECS 的 Mass Entity 系统,走 DOD 路线。

**Bevy**:Rust 的 ECS 引擎,从第一天就是 DOD 设计。每个 Component 类型一个 Vec,系统(system)处理批量 component。

**Casey HH**:HH 全剧贯彻 DOD 思想——Casey 总是先考虑数据布局,再考虑算法。Day 112 SIMD 优化、Day 200+ 内存优化都基于 DOD。

**反例**:传统 OOP 引擎(早期 Unity、Unreal)用 deep class hierarchy + virtual functions,性能差。这是 DOD 兴起的原因——OOP 的封装让数据布局分散,cache 不友好。

### 3.2 · 🎨 图形学视角

GPU 是 DOD 的极致——**SIMD + 大规模并行 + 紧凑数据布局**。

GPU 渲染时:

- vertex buffer 必须紧凑(SoA 或 AoS,但都要连续)
- texture 必须按特定对齐(swizzled layout)
- shader 处理 batch(warp / wavefront)——同 batch 必须数据相似

如果数据布局不对,GPU 性能崩盘。这就是为什么 Casey 在 Day 235+ 切 OpenGL 时要重新组织 vertex 数据——CPU 软渲染的布局可能不适合 GPU。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核是 DOD 的祖师爷。内核数据结构全是为 cache 优化:

**`struct list_head`**:Linux 的双向链表实现,**反向嵌入**——不是 `struct node { data; next; prev; }`,而是 `struct list_head { next; prev; }` 嵌入到任意 struct 里。这让"链表节点"和"数据"在内存里相邻,cache 友好。

**`struct hlist_head`**:Linux 的 hash bucket 链表,设计上**只存一个指针**(不是双向),节省 8 字节/bucket。

**per-CPU 变量**:`DEFINE_PER_CPU(type, name)` 定义每个 CPU 一份副本,避免 false sharing(多核 CPU 同时改同一 cache line 导致的性能崩盘)。

**Linux 工具验证**:

```bash
# 看 CPU cache 层次
lscpu
# 输出包含:
# L1d cache: 32K  (一级数据 cache)
# L1i cache: 32K  (一级指令 cache)
# L2 cache: 256K
# L3 cache: 8192K (= 8 MB)

# 或者更详细
cat /sys/devices/system/cpu/cpu0/cache/index*/size
# 40960 (= 40 KB L1 d+i)
# 98304 (= 96 KB L2,某些 CPU)

# 用 perf 测 cache miss
sudo pacman -S perf
perf stat -e cache-misses,cache-references ./your_program
# 输出类似:
# 1,234,567 cache-misses      ← 总 miss 数
# 100,000,000 cache-references  ← 总访问数
# 1.2% of all cache refs

# 用 valgrind --tool=cachegrind 详细分析
valgrind --tool=cachegrind ./your_program
# 输出每个函数的 cache miss 数,精确定位
```

### 3.4 · 🦀 Rust 生态视角

Rust 表达 DOD 有几个利器:

**1. `Vec<T>` 是天然 cache 友好**

```rust
let arr: Vec<u32> = vec![...];
// 内存连续,cache 完美
```

Rust 的 `Vec` 是 (pointer, capacity, length),分配在堆,但内容连续。遍历极快。

**2. `Box<[T]` 比 `Vec<T>` 略优**(已知大小)

```rust
let arr: Box<[u32]> = vec![...].into_boxed_slice();
// 比 Vec 少 8 字节(没有 capacity 字段),固定大小
```

**3. `SmallVec<T>` / `ArrayVec<T>`**:小型 Vec 在栈上

```rust
use smallvec::SmallVec;
let v: SmallVec<[u32; 4]> = smallvec![1, 2, 3];  // 栈上,无堆分配
```

适合"通常小,偶尔大"的场景。避免堆分配开销。

**4. `soa_derive` / `serde_repr`**:SoA 派生

```rust
#[derive(StructOfArray)]
struct Entity { pos: Vec2, vel: Vec2 }
// 自动生成 EntitySoA,有 pos: Vec<Vec2> 和 vel: Vec<Vec2>
```

手写 SoA 麻烦,crate 自动派生。

**5. SIMD 友好的 vector 类型**

```rust
use std::simd::*;
let v: f32x4 = f32x4::from_array([1.0, 2.0, 3.0, 4.0]);
// 一次处理 4 个 f32
```

Rust 的 portable-simd(实验性)让 SIMD 跨平台。

**Rust 的 zero-cost abstraction 哲学**:

```rust
// 高层抽象
for x in &vec { process(*x); }

// 编译后(优化模式)
let ptr = vec.as_ptr();
let len = vec.len();
for i in 0..len { process(*ptr.add(i)); }
// 完全没有迭代器开销
```

Rust 的 iterator 是 zero-cost——抽象不掉性能。这让 DOD 在 Rust 里写起来不痛苦。

## 4 · 认知地图

### 4.1 上级

- **Data-Oriented Design**(数据导向设计)—— 围绕数据布局设计的编程范式
- **Cache-friendly programming**(cache 友好编程)—— 为 CPU cache 优化的代码风格
- **Locality of reference**(局部性)—— 数据访问的时间和空间局部性
- **Memory hierarchy**(存储层次)—— 寄存器 / L1 / L2 / L3 / 主存的速度-容量权衡

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Array(紧凑数组) | 最快,固定大小 | 稠密数据 | Day 035+ |
| HashMap | 灵活,有元数据开销 | 稀疏数据 | Day 033 用 |
| Hybrid(chunk + Array) | 平衡 | 局部稠密,全局稀疏 | Day 035+ Casey 演化到 |
| 链表 | 极慢(cache miss) | 几乎不用 | HH 永远不用 |
| Tree(B-tree, etc) | 中速,有序 | 数据库,文件系统 | HH 不用 |

### 4.3 下级

- **L1 / L2 / L3 cache** —— CPU 多级缓存
- **Cache line**(64 字节)—— 一次读最小单位
- **AoS vs SoA** —— Array of Structs vs Struct of Arrays
- **Cache miss / hit** —— 命中 vs 不命中
- **Prefetching** —— CPU 预取(连续访问时自动)
- **False sharing** —— 多核 CPU 同 cache line 的并发问题

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:让数据访问对 cache 友好。

| 语境 | "cache 友好"叫法 | 典型做法 |
|---|---|---|
| 游戏开发 | DOD | AoS → SoA,Array 优先 |
| 数据库 | buffer pool 优化 | page size 调优,索引 cache 友好 |
| 图形学 | vertex buffer layout | 紧凑 layout,对齐 |
| 操作系统内核 | per-CPU 数据 | 避免锁竞争 + false sharing |
| 机器学习 | tensor layout | NCHW vs NHWC,GPU 友好 |
| Web 浏览器 | DOM virtual scrolling | 只渲染可见元素 |

所有这些场景的核心问题相同:**让"经常用的数据"在 cache 里**。

### 历史演化

- **1980s**:cache 出现(80386),程序员开始关心 cache
- **1990s**:CPU 频率飙升,主存跟不上,cache miss 代价暴涨
- **2000s**:多核 CPU 出现,false sharing 成问题
- **2010s**:DOD 运动兴起(Mike Acton GDC 2014 演讲)
- **2020s**:ECS 成主流,所有大引擎都 DOD

Casey HH 是这场运动的产物——他每集都在演示 DOD 思维。

### CPU cache 的演化

| 时期 | L1 | L2 | L3 | 典型延迟比 |
|---|---|---|---|---|
| 1990 | 无 | 无 | 无 | 主存够快 |
| 1995 | 8KB | 无 | 无 | L1 ~1 cycle |
| 2000 | 16-32KB | 128-256KB | 无 | L1:1, L2:10, mem:100 |
| 2010 | 32KB | 256KB | 几 MB | L1:4, L2:12, L3:40, mem:200 |
| 2025 | 48KB | 1-2MB | 几十 MB | L1:4, L2:14, L3:50, mem:300 |

主存延迟**永远跟不上 CPU**,所以 cache 越来越重要。DOD 是应对这种趋势的核心方法论。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 说"HashMap 的 O(1) 和 Array 的 O(1) 不一样快"。具体差多少倍?为什么?

**参考解答**:**差 10-25 倍**。

具体数字(现代 x86_64 CPU):

- **Array** 单次访问:平均 7-10 cycle(大部分 cache hit,偶尔 cache miss)
- **HashMap** 单次访问:平均 50-100 cycle(hash 计算 + bucket 查找 + ~50% cache miss)

差 ~10 倍。

**为什么 HashMap 慢**:

1. **每次都要算 hash**:hash 函数本身要 10-20 cycle(尽管 modern hash like xxhash 很快)
2. **bucket 数组稀疏**:HashMap 内部 Vec 是稀疏的(为减少冲突),cache 利用率低
3. **冲突时遍历**:即使 load factor 控制,偶尔还是要链表/开放寻址处理冲突
4. **元数据开销**:每个 bucket 有 Option/标记位,占空间,降低 cache 密度

**为什么 Array 快**:

1. **直接算 index**:`base + i * sizeof(T)`,几条指令
2. **紧凑内存**:无元数据,cache 100% 利用
3. **prefetching**:CPU 自动预取连续内存

**结论**:大 O 表示法忽略常数因子,但工程上常数因子很重要。**hot path 优先 Array**。

### Lv2 · 动手实践

**题**:写一个 benchmark 对比 Array vs HashMap 性能。要求:

1. 生成 1,000,000 个 tile 数据(随机值)
2. 两种存储:`Vec<TileValue>`(Array)和 `HashMap<(i32, i32), TileValue>`(HashMap)
3. 随机访问 10,000,000 次,测平均耗时
4. 输出对比

完成标准:`cargo run --release` 打印两种方案的耗时,Array 应该比 HashMap 快 5-10 倍。

**参考解答**:

```rust
// src/main.rs
// cargo new --bin cache_bench && cd cache_bench

use std::collections::HashMap;
use std::time::Instant;

const W: i32 = 1000;
const H: i32 = 1000;

#[derive(Copy, Clone)]
struct TileValue(u8);

fn main() {
    let n = (W * H) as usize;
    let accesses = 10_000_000;

    // 生成数据
    let arr: Vec<TileValue> = (0..n).map(|i| TileValue((i % 256) as u8)).collect();
    let mut map = HashMap::new();
    for y in 0..H {
        for x in 0..W {
            map.insert((x, y), TileValue(((x + y) % 256) as u8));
        }
    }

    // 生成随机访问 pattern(固定的,确保公平)
    let mut rng_state = 42u64;
    let access_pattern: Vec<(i32, i32)> = (0..accesses).map(|_| {
        rng_state = rng_state.wrapping_mul(6364136223846793005).wrapping_add(1);
        let x = (rng_state % W as u64) as i32;
        rng_state = rng_state.wrapping_mul(6364136223846793005).wrapping_add(1);
        let y = (rng_state % H as u64) as i32;
        (x, y)
    }).collect();

    // Bench Array
    let mut sum_a = 0u64;
    let start = Instant::now();
    for &(x, y) in &access_pattern {
        let v = arr[(y * W + x) as usize].0;
        sum_a += v as u64;
    }
    let arr_time = start.elapsed();

    // Bench HashMap
    let mut sum_m = 0u64;
    let start = Instant::now();
    for &(x, y) in &access_pattern {
        let v = map.get(&(x, y)).unwrap().0;
        sum_m += v as u64;
    }
    let map_time = start.elapsed();

    // 防止编译器优化掉
    println!("Array sum: {}, HashMap sum: {} (must match: {})",
        sum_a, sum_m, sum_a == sum_m);

    println!("\n=== Performance Comparison ===");
    println!("Array:    {:?} ({} ns/access)", arr_time, arr_time.as_nanos() / accesses as u128);
    println!("HashMap:  {:?} ({} ns/access)", map_time, map_time.as_nanos() / accesses as u128);
    println!("Ratio:    HashMap is {:.1}x slower", map_time.as_secs_f64() / arr_time.as_secs_f64());
}
```

**预期输出**(具体数字看 CPU):

```
Array sum: 1280000, HashMap sum: 1280000 (must match: true)

=== Performance Comparison ===
Array:    13ms (1 ns/access)
HashMap:  145ms (14 ns/access)
Ratio:    HashMap is 11.1x slower
```

Array 比 HashMap 快 11 倍。这就是 DOD 的威力。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

把 Lv2 的代码扩展,加 cachegrind 验证:

```rust
// src/main.rs (扩展 Lv2)
// 加 SoA vs AoS 对比

#[derive(Copy, Clone)]
struct EntityAoS {
    pos_x: f32, pos_y: f32,
    vel_x: f32, vel_y: f32,
}

struct EntitiesSoA {
    pos_x: Vec<f32>, pos_y: Vec<f32>,
    vel_x: Vec<f32>, vel_y: Vec<f32>,
}

fn bench_aos(entities: &[EntityAoS]) -> f32 {
    // 只用 pos,不用 vel——AoS 浪费 50% cache
    let mut sum = 0.0;
    for e in entities {
        sum += e.pos_x + e.pos_y;
    }
    sum
}

fn bench_soa(pos_x: &[f32], pos_y: &[f32]) -> f32 {
    // 只读 pos 数组——SoA 100% cache 利用
    let mut sum = 0.0;
    for i in 0..pos_x.len() {
        sum += pos_x[i] + pos_y[i];
    }
    sum
}

fn main() {
    let n = 1_000_000;
    let aos: Vec<EntityAoS> = (0..n).map(|i| EntityAoS {
        pos_x: i as f32, pos_y: i as f32 * 2.0,
        vel_x: 0.0, vel_y: 0.0,
    }).collect();
    let mut soa = EntitiesSoA {
        pos_x: Vec::with_capacity(n),
        pos_y: Vec::with_capacity(n),
        vel_x: Vec::with_capacity(n),
        vel_y: Vec::with_capacity(n),
    };
    for i in 0..n {
        soa.pos_x.push(i as f32);
        soa.pos_y.push(i as f32 * 2.0);
        soa.vel_x.push(0.0);
        soa.vel_y.push(0.0);
    }

    use std::time::Instant;

    // Bench AoS
    let start = Instant::now();
    let s1 = bench_aos(&aos);
    let aos_time = start.elapsed();

    // Bench SoA
    let start = Instant::now();
    let s2 = bench_soa(&soa.pos_x, &soa.pos_y);
    let soa_time = start.elapsed();

    println!("AoS sum: {}, SoA sum: {} (match: {})", s1, s2, (s1 - s2).abs() < 0.1);
    println!("AoS: {:?} ({:.2} ns/elem)",
        aos_time, aos_time.as_nanos() as f64 / n as f64);
    println!("SoA: {:?} ({:.2} ns/elem)",
        soa_time, soa_time.as_nanos() as f64 / n as f64);
    println!("Ratio: SoA is {:.2}x faster", aos_time.as_secs_f64() / soa_time.as_secs_f64());
}
```

### Arch Linux 工具链验证

```bash
# 1. 创建项目并跑
cd /tmp && cargo new --bin cache_bench && cd cache_bench
# 把代码粘进 src/main.rs

cargo run --release
# 输出:
# AoS sum: ..., SoA sum: ... (match: true)
# AoS: 2ms (2.0 ns/elem)
# SoA: 1ms (1.0 ns/elem)
# Ratio: SoA is 2.0x faster
# (实际数字看 CPU 和 cache 大小)

# 2. 看 CPU cache
lscpu | grep -E "L1|L2|L3"

# 3. 用 perf 测 cache miss
sudo pacman -S perf
perf stat -e cache-misses,cache-references,L1-dcache-load-misses,L1-dcache-loads ./target/release/cache_bench
# 输出:
# 1,234,567 cache-misses
# 100,000,000 cache-references  # 1.2% miss rate

# 4. 用 valgrind cachegrind 详细分析
sudo pacman -S valgrind
valgrind --tool=cachegrind ./target/release/cache_bench
# 输出类似:
# I1 refs: 1,000,000,000
# L1i miss rate: 0.5%
# L1d miss rate: 8.3%   ← 看 AoS vs SoA 的差异
# LL miss rate: 0.2%

# 5. 看 cachegrind 的详细 report
# 默认 cachegrind 生成 cachegrind.out.<pid> 文件
ls cachegrind.out.*
# 用 cg_annotate 看每个函数的 cache miss
cg_annotate cachegrind.out.* | head -50

# 6. 验证数据布局:用 gdb 看 Vec 在内存里的位置
cargo build
gdb target/debug/cache_bench
(gdb) break main
(gdb) run
(gdb) print aos
# 看每个 EntityAoS 的内存地址,确认它们紧凑排列
(gdb) x/10gx &aos[0]
# 应该看到 pos_x, pos_y, vel_x, vel_y 连续(每 4 字节一个)
```

**Troubleshooting**:

- Release 模式性能差 100 倍 —— 确认用 `--release`。debug 模式 Rust 数学运算慢 10-100 倍。
- perf 看不到 cache miss —— 需要 root 或 `kernel.perf_event_paranoid = 1`(`sudo sysctl kernel.perf_event_paranoid=1`)。
- cachegrind 输出难读 —— 用 `cg_annotate` 自动 pretty-print。
