
# T5-1 · 游戏手感:输入与时间

> 这是**游戏手感序列 part 1 / 4**。它把 phase-2 的那份 16KB 简版(`game-feel-short.md`)扩成一套完整四部曲:part 1 讲输入与时间手感(你正在读的这篇),part 2 讲相机手感(`game-feel-02-camera.md`),part 3 讲反馈与 juice(`game-feel-03-feedback-juice.md`),part 4 讲打磨与微调(`game-feel-04-polish.md`)。如果你只读过简版,简版里关于 input buffer 和 coyote time 的描述被压缩到一行;这一篇就是那一行的展开。

## 0 · 同样的跳跃,一个是神作,一个是垃圾

现在有两款平台跳跃游戏,我们都精确地拆开它们的代码看过了。它们的跳跃参数**完全一致**:起跳初速度都是 600 像素/秒,重力都是 1400 像素/秒²,最大跳跃高度都是 128 像素。两个角色能跳到的位置一模一样,落到同一个平台上的弧线分毫不差。

你拿起来玩 5 分钟,你的结论是:**A 神作,B 垃圾**。A 的角色像长在你手指上,你说跳它就跳,踩边缘永远踩得稳,你晚按半拍也能补救;B 的角色像隔着一层棉花,经常你明明按了跳它没跳,从悬崖边走过去你以为还能跳,结果就那么掉下去了,一次又一次,你摔手柄。

这是手感行业里最经典的一个谜题:**机制完全相同,体验天差地别**。差别不在"角色跳多高",差别藏在更隐蔽的层里——你的按键**什么时候**被游戏记下、你的失误**被原谅到什么程度**、从你按下到屏幕上看见反应之间**有多少毫秒**。这些参数不写在角色移动代码里,它们写在移动代码**外围**的一圈薄薄的"输入与时间手感"代码里。这一圈代码每一行都很短,但加在一起,就是 A 和 B 的全部差距。

这一篇要教你的,就是这一圈代码。它分成四个零件:**输入缓冲(input buffer)**、**郊狼时间(coyote time)**、**可变跳跃高度(variable jump height)**、以及最容易被忽略也最难搞的——**输入延迟(input latency)**。每个零件都不复杂,但它们是平台跳跃游戏从"能玩"到"想再玩一次"的全部秘密。Steve Swink 在《Game Feel》里把这四个东西称为 platformer 的"四大支柱",不是夸张。

## 1 · 先承认一件事:玩家是不准的

要理解输入缓冲和郊狼时间,你得先承认一件让工程师难受的事实:**玩家的手指是不准的**。

精确地说,玩家想表达的意图,和他真正按下按键的物理时刻,中间有一个 30 到 120 毫秒的随机偏差。这不是因为玩家菜,这是人类的生理极限。你要在角色**正好**落地的那一帧按跳,精度大约 ±50 毫秒;你要在角色**正好**离开悬崖的那一帧按跳,精度大约 ±80 毫秒。专业 speedrunner 也就这水平,普通玩家更松。

一个"诚实"的游戏——也就是把玩家的每一次按键严格按物理时刻处理的游戏——会把所有这些不准的按键,变成游戏里看得见的失败:你早按 30 毫秒,游戏判定你"在空中按了跳,无效";你晚按 50 毫秒,游戏判定你"已经离开地面,跳不了"。这种诚实在工程上漂亮,在体验上是灾难。**玩家不会觉得是自己不准,玩家只会觉得游戏不公平、操作不跟手**。

输入缓冲和郊狼时间,就是两个把这种"工程诚实"换成"体验温柔"的小机器。它们的共同原理是:游戏不把玩家的按键当成离散事件立刻处理,而是把玩家的**意图**短暂地存起来,在一个宽容的时间窗内,把意图"挪"到能让它成功的时刻去执行。这是工程师很少想、但用户体验设计师天天想的事——**对用户宽容,比要求用户精确,通常是更好的设计**。游戏手感,本质是这件事在 60 帧每秒上的体现。

## 2 · 输入缓冲:把"你刚才想跳"记 100 毫秒

输入缓冲解决的是**早按**的失误。场景是这样:你的角色正在下落,马上就要落到一块平台上。你心里清楚落地的瞬间就该跳——连跳连到下一个平台。你的大脑提前算好了时机,你的手指在大脑判断的"差不多到点了"的瞬间按下跳键。但你的视觉延迟、神经延迟加在一起,让你**早按了 40 毫秒**。

一个诚实的游戏,在那一刻的物理状态是:角色还在空中(`on_ground == false`)。游戏查一下跳键是不是这一帧"刚按下",发现是,但角色不在地面——于是丢弃这次按键。40 毫秒后,角色真落地了,但游戏已经忘了你按过跳——它只关心"这一帧刚按下"。结果就是:你想连跳,角色落地了却没跳,卡在那。你下次再玩,你会更晚一点按,结果这次**晚**了,角色起跳晚了一帧,连不上下一个平台。无论你怎么调整,总有几次失败,因为人类的精度就是这么个区间,而游戏要求的精度是一个零宽度的点。

输入缓冲的修法很简单,几行代码。游戏不再问"这一帧刚按下吗",而是问"**过去 N 毫秒内,有没有按下过**"。你按跳的那一帧,游戏把这个意图写进一个叫 buffer 的小容器,标上时间戳。每一帧,游戏检查:角色现在能跳吗(在地面)?如果能,而且 buffer 里有"想跳"的记录且没过期(比如 100 毫秒内),那就**这一帧执行跳**,并清空 buffer。如果角色不能跳,buffer 里的意图就继续等,等到过期或者等到能用为止。

这就把游戏对玩家精度的要求,从"必须在一帧内按",放宽到"在 100 毫秒窗口内按都行"。人类精度是 ±50 毫秒,100 毫秒的窗口绰绰 COVER。从此玩家早按也能跳成,体验立刻从"不跟手"变成"我手指长在角色上"。

下面是 Rust 实现。注意它**完全独立于移动逻辑**——它是移动逻辑外面的一层薄壳。

```rust
use std::time::{Duration, Instant};

/// 输入缓冲:把"玩家想干什么"短暂地存起来。
/// 任何离散动作(跳、攻击、闪避、互动)都能套同一个壳。
pub struct InputBuffer {
    /// 上一次"按下"的时刻,None 表示没有未消费的意图
    queued_at: Option<Instant>,
    /// 缓冲窗口:超过这个时长,意图作废
    window: Duration,
}

impl InputBuffer {
    pub fn new(window_ms: u64) -> Self {
        Self {
            queued_at: None,
            window: Duration::from_millis(window_ms),
        }
    }

    /// 玩家按下了对应按键(平台的 input 回调里调)
    pub fn press(&mut self, now: Instant) {
        self.queued_at = Some(now);
    }

    /// 游戏逻辑每帧调用:现在能不能消费这个意图?
    /// 返回 true 表示"刚才那个按下,这一帧生效",并清空 buffer。
    pub fn consume(&mut self, now: Instant) -> bool {
        match self.queued_at {
            Some(t) => {
                if now.duration_since(t) <= self.window {
                    self.queued_at = None;  // 消费掉,不重复触发
                    true
                } else {
                    // 过期了,丢弃。一个迟到的"想跳"不能再憋在 buffer 里
                    // 等下次落地——那是另一个意图,不是这次。
                    self.queued_at = None;
                    false
                }
            }
            None => false,
        }
    }
}
```

关于窗口设多少:业界经验值 80 到 120 毫秒。100 毫秒是个安全默认。**窗口不能太长**——超过 200 毫秒,玩家会感受到"我明明只是手抖按了一下,角色却莫名其妙跳了",缓冲变成"幽灵输入"。也不能太短——低于 50 毫秒,普通人精度的边缘还是会被吃掉。100 毫秒是个甜点,具体多少要 playtest 调,我们后面讲 CVar 调参时回来。

注意一个微妙的设计点:过期时,我把 `queued_at` 设成 `None` 而不是保留。理由是,**输入缓冲存的是"玩家某一次具体的按下意图"**,不是"玩家一直想跳"。如果玩家在 200 毫秒前按了一下没成,然后没有再按,游戏不应该假设他还想跳——也许他已经改主意了。一次按下对应一次意图,过期就作废,下一次按下重新计时。这是一条容易被忽略但对体验影响巨大的规则。

## 3 · 郊狼时间:你刚离开地面,游戏假装你还在

输入缓冲解决早按,郊狼时间解决**晚按**。场景换一个:你的角色在悬崖边奔跑,跑到尽头要跳到对面平台。你的视觉判断"该跳了"的时机,基本是角色**离开悬崖**的那一瞬间。但你的手指同样有延迟——你晚按了 60 毫秒。这 60 毫秒里,角色已经离开了悬崖,正在空中往下掉。诚实的游戏判定:角色在空中,跳不了。你眼睁睁看着角色从两块平台之间的缝隙掉下去。

这种死亡是最让人破防的。因为玩家心里清楚——**我差点就跳成了**。差那 60 毫秒,不是玩家菜,是人类。游戏却用零宽度的判定线,把所有人类精度的边缘都判死。这种死亡积累三五次,玩家就放下手柄了,而且不是觉得"我菜",是觉得"游戏赖"。

郊狼时间的修法,名字来自那个动画片段——狼跑出悬崖,在空中悬了一秒才掉下去。游戏在角色**离开地面**之后,给一个 100 毫秒左右的"宽限窗",在这个窗内,角色虽然物理上在空中,但游戏**仍然允许它跳**。这 100 毫秒里,玩家按跳,角色从空中的当前位置起跳,跳出的弧线和"假如他在悬崖边最后一帧跳"的弧线几乎一样——视觉上你根本看不出区别。但玩家心里清楚,他这次是"被救了"。

这是平台跳跃游戏最经典的一个手感技巧。Celeste、Super Meat Boy、Hollow Knight、Ori,几乎所有口碑好的平台跳跃,都有这个机制,数值略有不同,但都在 80 到 150 毫秒。它的别名也叫"宽限跳"(grace jump)或"边缘跳"(ledge jump)——同一个意思,都是承认玩家精度有限,给一点宽限。

代码非常短,关键是它和地面检测是耦合的:

```rust
/// 玩家角色的"地面感"状态,不仅跟踪是否在地面,
/// 还跟踪"离开地面后过了多久"。
pub struct GroundSense {
    on_ground: bool,
    /// 离开地面的时刻。仍在地面时为 None。
    left_ground_at: Option<Instant>,
    /// 郊狼窗口:离开地面后多久内仍可以跳。
    coyote_window: Duration,
}

impl GroundSense {
    pub fn new(coyote_ms: u64) -> Self {
        Self {
            on_ground: false,
            left_ground_at: None,
            coyote_window: Duration::from_millis(coyote_ms),
        }
    }

    /// 物理系统每帧调用,告诉它"现在到底在不在地面"
    pub fn update(&mut self, on_ground: bool, now: Instant) {
        if on_ground && !self.on_ground {
            // 刚落地:清空"离开时刻"
            self.left_ground_at = None;
        } else if !on_ground && self.on_ground {
            // 刚离开地面:记下时刻
            self.left_ground_at = Some(now);
        }
        self.on_ground = on_ground;
    }

    /// 跳跃逻辑调用:现在这个瞬间,允不允许跳?
    pub fn can_jump(&self, now: Instant) -> bool {
        if self.on_ground {
            return true;  // 在地面,当然能跳
        }
        match self.left_ground_at {
            Some(t) => now.duration_since(t) <= self.coyote_window,
            None => false,  // 在空中且从未触地(比如开局就在空中)
        }
    }
}
```

这里有个**必须强调**的设计点:郊狼时间只在"**刚离开地面**"时给宽限,**不能**在"角色从来没碰过地面"的情况下生效(比如角色一开始就在空中下落)。这就是 `left_ground_at == None` 时返回 `false` 的原因。否则你可以在任何空中按下跳直接起跳,游戏就废了——变成飞天模式。郊狼时间**奖励的是"曾经在地面上"的玩家**,不是"想跳就跳"。这个边界画错了,平台跳跃变成飞行游戏。

还有一个微妙处:从悬崖**走**下去(没有跳,自然离开地面)和从悬崖**跳**下去,在物理上是同一个状态变化(从 on_ground 到 not on_ground),所以两者都会触发郊狼窗口。这是对的——玩家走下悬崖想补救,和跳下悬崖想补救,公平起见应该一视同仁。这点很反直觉但很重要。

## 4 · 把两个机制拼起来:一次"想跳",三种被救的方式

输入缓冲和郊狼时间各自管一摊,但真正神奇的是它们**配合**起来的时候。考虑一个综合场景:你的角色在悬崖边,你想跳到对面。你按下跳键的时间稍微早了 30 毫秒(你太急了),也就是角色还没到悬崖边你就按了。游戏接下来会发生什么?

如果只有输入缓冲:游戏记住你想跳,等角色到了"可以跳"的状态(在地面),就触发跳。这里角色一直在地面上跑,所以缓冲很快被消费,角色到悬崖边正常起跳。✓

如果只有郊狼时间:你早按的 30 毫秒里,角色还在地面,跳直接成功。✓ 但如果是另一种失误——你**晚**按 60 毫秒——只有郊野时间能救你。

两个机制都用:无论你早按还是晚按,游戏都能"挪"你的意图到那个零宽度的精确时刻去执行。早按的,缓冲帮你挪到落地那一刻;晚按的,郊狼时间把"能跳"的状态延长到你按下的那一刻。

把两个机制和真实跳跃逻辑拼起来,大致是这样:

```rust
pub struct PlayerController {
    jump_buffer: InputBuffer,
    ground: GroundSense,
    // 可变跳跃高度,下一节讲
    jump_held: bool,
    vel_y: f32,
}

impl PlayerController {
    pub fn on_jump_pressed(&mut self, now: Instant) {
        // 平台输入回调:只记下意图,不直接跳
        self.jump_buffer.press(now);
        self.jump_held = true;
    }

    pub fn on_jump_released(&mut self) {
        self.jump_held = false;
    }

    /// 每个固定步长调用一次(注意:是在 step 里,不是在渲染里)
    pub fn step(&mut self, dt: f32, now: Instant, on_ground: bool) {
        self.ground.update(on_ground, now);

        // 试着消费缓冲里的"想跳"。这里同时检查郊狼时间。
        // 两个机制在同一个 if 里握手:buffer 有意图 + 当前允许跳。
        if self.jump_buffer.consume(now) && self.ground.can_jump(now) {
            self.vel_y = JUMP_INITIAL_VEL;
            // 跳完之后,如果还想做"郊狼时间已用掉就别再给"的精细控制,
            // 可以在这里把 left_ground_at 清空,防止同一次起跳被双消费。
        }

        // 可变跳跃高度:松开跳键时,如果还在上升,削减速度
        if !self.jump_held && self.vel_y < 0.0 {
            self.vel_y *= 0.5;  // 砍半,实现"小跳"
        }

        // ...重力、移动、碰撞响应...
        self.vel_y += GRAVITY * dt;
    }
}
```

注意一个关键约定:`step` 是被固定步长循环调用的(见 `09B-1`)。`now` 这个时间戳,也应该是**模拟时间**,不是墙上时钟。如果你的 buffer 窗口和 coyote 窗口用墙上时钟,会出现一种诡异现象:游戏卡顿时,真实时间继续流逝,等你卡顿恢复,所有 buffer 都"莫名其妙过期了",玩家按的跳全没了。把这两个窗口绑在模拟时间上,卡顿就不会偷走玩家的意图。这就是为什么这一篇的 prereq 是 `09B-1`——固定步长是手感的**地基**,没有它,手感本身也是飘的。

## 5 · 可变跳跃高度:按住跳键跳得高,点一下跳得低

讲完两个"救你"的机制,讲一个"让你能精确控制"的机制。场景:一连串矮平台,你需要小跳;接着一个高墙,你需要大跳。如果游戏只有一种跳跃高度(初速度固定),你只能跳一种高度——要么小跳够不到矮平台,要么大跳跳过头。**可变跳跃高度**(variable jump height)给玩家一个旋钮:按住跳键的时间长短,决定跳得多高。

经典实现:起跳时给一个**最大**初速度,角色上升;一旦玩家**松开**跳键,如果角色还在上升(速度向上),游戏立刻把上升速度**砍半**(或乘以某个系数,比如 0.5)。结果是:点一下跳键就松开,角色只跳了最大高度的 1/4 左右;按住不放,角色跳到最大高度。玩家通过按住时长,精确连续地控制跳跃高度——从最小跳到最大跳,中间任何高度都能跳到。

代码在上一节已经写过(`if !self.jump_held && self.vel_y < 0.0 { self.vel_y *= 0.5; }`),但值得单独拎出来强调一个**极易做错**的点:那个"砍半"操作,**只发生一次**,就是玩家松开跳键的那一帧。不是每帧都砍,不是按比例衰减,是松开瞬间一次性砍。如果做成每帧都砍,角色会立刻被拽下来,跳不起来;如果做成持续按住才不砍,松开就立刻停,也是一样的问题。**正确做法是:监听"松开"事件,只在那一次把速度砍掉**。剩下的交给重力自然减速。

这个机制看起来朴素,但它是平台跳跃游戏"操作深度"的源头。Super Mario Bros 1985 年就有了,所有现代平台跳跃都继承了它。没有它,跳跃是个二值操作(跳 / 不跳);有了它,跳跃是个连续操作(跳多高),玩家可以在矮跳和大跳之间精确选择,关卡设计也才能围绕"高跳够不到、矮跳过不去"这种张力展开。

数值方面:`self.vel_y *= 0.5` 的 0.5 是个常见值,意思是松开瞬间速度减半。这个系数越小,小跳越矮(更精确的控制,但矮跳也越没用);越大,小跳越接近大跳(控制力弱)。0.4 到 0.6 之间是甜点。和 buffer、coyote 一样,这个值也要 playtest 调,且应该做成 CVar。

## 6 · 输入延迟:那个看不见但能感觉到的敌人

讲到这里,前面三个机制都是"游戏对玩家意图的处理"。现在讲一个更隐蔽、也更难搞的:**输入延迟**(input latency)——从玩家物理按下按键,到屏幕上看到反应,中间经过的**所有时间**。这个时间玩家看不见,但能感觉到。它是手感行业里公认的"第一公敌",所有手感优化有一半的篇幅都在讲怎么压缩它。

把延迟拆开,它由四段组成,每一段都是可以优化的:

第一段是**输入设备到游戏进程的延迟**。键盘、手柄有自己的扫描周期(消费级键盘 1 毫秒到 10 毫秒,蓝牙手柄可能 20 毫秒),事件经过操作系统、窗口系统、再排到游戏进程的事件队列。这一段你大部分控制不了,但你可以选——比如启用 raw input 绕过窗口系统的事件队列,或用更高轮询率的设备。

第二段是**游戏从队列取事件到状态更新的延迟**。一个常见错误是:游戏在每一帧的**最后**才轮询输入。结果是这一帧的输入,要等下一帧渲染才反映出来——白白多了一帧延迟。**正确做法是在每一帧的最开始就轮询输入**,这样这一帧的渲染就能用上这次的输入。这一条改起来不难,效果立竿见影,但很多业余游戏都做错了。

第三段是**渲染到屏幕的延迟**,这一段最复杂。游戏渲染好一帧,这帧要进 swapchain 队列,等下一次 vsync 才被显示设备取走。如果你用了双缓冲 + vsync,渲染好的帧要等一个完整的刷新周期才能上屏——60 Hz 屏幕上这就是 16 毫秒。如果你还开了三缓冲,延迟更长。这一段的处理见 `09C-2-instance-device-swapchain.md` 里讲到的 present mode——`VK_PRESENT_MODE_IMMEDIATE_KHR` 最短延迟但有撕裂,`VK_PRESENT_MODE_FIFO_KHR` 是 vsync 无撕裂但有完整一帧延迟,`VK_PRESENT_MODE_MAILBOX_KHR` 是兼顾方案。竞技游戏常常牺牲撕裂保护换最低延迟,这是手感和画质的取舍。

第四段是**显示器本身的响应时间**。IPS 屏 5 毫秒,VA 屏 10 毫秒,OLED 0.1 毫秒。这一段你完全控制不了。

四段加起来,从按到看见,常见范围 30 毫秒(高刷屏 + raw input + immediate present)到 100 毫秒(60 Hz vsync + 普通键盘 + 普通屏)。**100 毫秒是手感的死亡线**——超过这条线,玩家开始觉得"钝",专业玩家甚至能感觉到 50 毫秒的差异。如果你做竞技游戏,你应该把延迟压到 30 毫秒以内;做单机平台跳跃,60 毫秒以内是可接受的目标。

延迟优化是个系统工程,本篇只能点到为止,但有一条原则要记住:**延迟不是某一个组件的锅,是所有组件累加的结果**。所以优化延迟靠的是"每一处都抠一点"——早 1 毫秒轮询、少一帧 swapchain 队列、用更快的 present mode、关掉不必要的后处理——每处省几毫秒,加起来就是手感的质变。这也是为什么专业手感团队会拿高速摄像机(1000 fps)实拍"按键到屏幕反应"的过程来测量端到端延迟——他们不靠感觉,他们测。

## 7 · 为什么手感和帧率独立是一回事

讲到这里,你应该开始感到一个矛盾:我们一直在讲"100 毫秒""50 毫秒"这种以真实时间计量的窗口,但 `09B-1` 反复强调,**游戏逻辑要按固定步长走,不能依赖真实时间**。这两件事怎么调和?

调和的办法是:**手感参数用真实时间表达(玩家友好的单位),但执行用固定步长衡量**。具体说,buffer 窗口你写 `Duration::from_millis(100)`,这是给设计者读的——"100 毫秒的缓冲"。但游戏内部,这个 100 毫秒会被换算成"固定步长下相当于多少步":固定步长 1/60 秒,100 毫秒就是 6 步。buffer 的实现内部,不是按墙上时钟计时的,而是按"已经过去的固定步长次数"计时的——`step` 被调用了几次,buffer 就走了几个步。

这样设计有两个好处。第一,无论游戏跑在 60 Hz 还是 144 Hz 屏幕,固定步长永远是 1/60 秒,buffer 永远是 6 个 step,游戏行为完全一致——手感帧率无关。第二,游戏卡顿时(`09B-1` 讲的 MAX_FRAME 机制),模拟会主动慢下来,buffer 也会跟着慢——玩家主观感受是"游戏变慢了,但操作还是对的"。如果 buffer 用墙上时钟,卡顿期间真实时间流逝但模拟不推进,buffer 会"莫名其妙过期",体验崩溃。

这就是为什么 `09B-1` 的固定步长是手感的**地基**。没有固定步长,你刚才写的所有 buffer、coyote、可变跳跃高度,在不同帧率的机器上表现都不一样——你以为调好了,换个屏幕就崩了。固定步长把"按时间定义的手感参数"和"按帧数执行的物理逻辑"解耦,让前者稳定地映射到后者。这一篇和 `09B-1` 是一对,顺序读它们你才完整。

我们把上面的 buffer 改成"按固定步长计数"的版本,你能看出区别:

```rust
/// 按固定步长计数的输入缓冲。窗口用"步数"表达,但构造时
/// 用毫秒 + 步长自动换算,设计者依然写毫秒。
pub struct StepInputBuffer {
    /// 缓冲里还剩多少个 step 才过期
    remaining_steps: i32,  // -1 表示 buffer 空
    window_steps: i32,
}

impl StepInputBuffer {
    /// window_ms: 窗口毫秒;fixed_dt_secs: 固定步长秒数(如 1/60)
    pub fn new(window_ms: i32, fixed_dt_secs: f32) -> Self {
        let steps = ((window_ms as f32 / 1000.0) / fixed_dt_secs).round() as i32;
        Self {
            remaining_steps: -1,
            window_steps: steps.max(1),
        }
    }

    pub fn press(&mut self) {
        self.remaining_steps = self.window_steps;
    }

    /// 每个 step 调用一次。返回 true 表示这一步应该触发动作。
    pub fn step_consume(&mut self) -> bool {
        if self.remaining_steps < 0 {
            return false;
        }
        let fire = self.remaining_steps > 0;  // 还有意图
        // 不在这里清空——清空交给"真正执行动作"的地方。
        // 这里只递减,这样不消费就自然过期。
        self.remaining_steps -= 1;
        if self.remaining_steps < 0 {
            // 过期了
            return false;
        }
        fire
    }

    /// 真正触发了动作(跳成功)之后调用,清空意图防止重复触发
    pub fn clear(&mut self) {
        self.remaining_steps = -1;
    }
}
```

注意这里 `step_consume` 不主动清空——清空(`clear`)留给真正"跳成功"的那一步。这样设计是为了让 buffer 可以连续多步"请求"跳,直到某一步地面检测通过、跳成功、才清空。否则角色如果在空中按了跳,buffer 立刻被消费清空,落地后就跳不成了——这正是输入缓冲要解决的事,不能在实现里自己拆自己的台。

郊狼时间同样可以改成 step 计数版,思路一样,这里不重复。

## 8 · 调参:CVar 是手感的最后一块拼图

到这里你已经把四大支柱的代码写完了。但你还没真正"调好手感",因为代码里的 `100 毫秒`、`100 毫秒`、`0.5 系数` 都是我给的默认值。这些值对不对,只有玩起来才知道——而玩起来发现不对,你得回去改代码、重新编译、再玩、再改、再编译。

这就是 `09B-4-cvars-and-dev-console.md` 里那个著名的"40 秒编译"问题的实战表现。手感调参是个**高频迭代**过程——你可能要试 buffer 是 80 还是 120、coyote 是 90 还是 150、跳跃削减系数是 0.4 还是 0.55,几十个组合,每个组合都要重新玩一遍感受。如果每次改都要编译 40 秒,你调一晚上参数,大半时间花在等编译上,效率崩溃。

CVar 把这件事彻底改变了。你把所有手感参数注册成 CVar:`g_jump_buffer_ms`(默认 100)、`g_coyote_ms`(默认 100)、`g_jump_cut_factor`(默认 0.5)、`g_jump_initial_vel`(默认 600)、`g_gravity`(默认 1400)……然后游戏运行时,你打开 dev console,改一个值,角色立刻按新值跳,不用重新编译。你可以站在游戏里,边跳边改,边改边跳,十秒钟试十组参数。这是专业手感团队的标准工作流——**所有手感参数都是 CVar,所有 CVar 都能在运行时改**。

下面是把 buffer 和 coyote 接到 CVar 上的样子(假设你已经按 `09B-4` 实现了 CVar 系统):

```rust
use crate::cvars::CVars;

pub struct PlayerController {
    jump_buffer: StepInputBuffer,
    ground: GroundSense,
    jump_held: bool,
    vel_y: f32,
}

impl PlayerController {
    /// 每帧渲染前调用,根据当前 CVar 值重建参数化的子结构。
    /// 这里我们简单地让 buffer / coyote 每次"重新校准"窗口大小。
    /// 注意:校准不影响"已经在 buffer 里的意图",只是改过期阈值。
    pub fn retune_from_cvars(&mut self, cvars: &CVars, fixed_dt: f32) {
        let buf_ms = cvars.get_int("g_jump_buffer_ms").unwrap_or(100) as i32;
        let coy_ms = cvars.get_int("g_coyote_ms").unwrap_or(100) as u64;
        self.jump_buffer = StepInputBuffer::new(buf_ms, fixed_dt);
        // GroundSense 的窗口可以直接改字段
        self.ground.coyote_window = Duration::from_millis(coy_ms);
    }

    // ...step 等方法同前
}
```

实际工程里,你不会每帧都重建 `StepInputBuffer`(那样会丢失正在排队的意图),更优雅的做法是 buffer 内部把 `window_steps` 做成可变字段,每帧从 CVar 读取覆盖。这里为了示意简化了。重点是:**让所有手感参数都受 CVar 控制**,这样调参从"改代码 + 编译"变成"开控制台 + 输数字"。

调参的流程也有讲究,不是乱来。一个好的工作流是:**先把数值推到极端,再往回拨**。比如调 buffer,先把 `g_jump_buffer_ms` 设成 0(关掉缓冲),玩一关,感受"不跟手";再设成 500(超长缓冲),玩一关,感受"幽灵输入";然后慢慢往中间收,找到那个"刚好够用、又没有副作用"的甜点。这种二分搜索式的调法,比从默认值微调更有效率,也更让你理解每个参数的边界行为。

## 9 · 在你 HH 项目里动手(做中学红线)

把这一篇的所有东西落到你的 Handmade Hero 项目里。这是检验你有没有真懂的环节,光读不练,手感这件事你学不会——手感是练出来的。

第一步,前提检查。先确认你的 HH 主循环已经按 `09B-1` 改造成了固定步长。如果还是浮动 dt,先回去改完再来——这一篇的手感机制都假设固定步长,在浮动 dt 上它们的行为不可预测。

第二步,实现输入缓冲。在你的角色控制代码里,把"按下跳键直接跳"改成"按下跳键只写 buffer"。新增一个 `StepInputBuffer` 字段。在 `step` 函数里,先 `step_consume` buffer,如果有意图且 `can_jump`,就执行跳并 `clear`。把窗口大小作为常量,先用 100 毫秒。

第三步,实现郊狼时间。在你的地面检测代码里,加一个 `GroundSense` 字段。物理系统每帧告诉它"现在在不在地面",它负责维护"离开地面多久了"。跳跃判定改成 `ground.can_jump(now)`,而不是简单看 `on_ground`。coyote 窗口先用 100 毫秒。

第四步,实现可变跳跃高度。监听跳键的"松开"事件(不是按住状态,是状态变化的瞬间)。松开瞬间,如果角色速度向上,把速度乘 0.5。

第五步,接到 CVar。如果你已经做了 `09B-4`,把上面三个参数(`g_jump_buffer_ms`、`g_coyote_ms`、`g_jump_cut_factor`)注册成 CVar。如果还没做,先记下来,等做完 `09B-4` 再回来接。

第六步,**关闭单个机制,感受回归**。这是这一篇最有价值的一步,也是新手最容易跳过的一步。把游戏跑起来,然后:**只关掉输入缓冲**(buffer 窗口设 0),玩两分钟。你应该立刻感觉到"我明明按了跳它没跳"——那些原本被缓冲救下的早按,现在全部失败。**只关掉郊狼时间**,再玩两分钟。你应该感觉到"我从悬崖边走过去就掉下去,怎么都救不回来"——那些原本被郊野时间救下的晚按,现在全部死亡。**只关掉可变跳跃高度**,玩两分钟。你应该感觉到"我只能跳一种高度,矮平台跳过头,高墙跳不上去"。每个机制单独关掉,你才能**亲身感受到它解决了什么问题**——这种感受,是读多少文字都替代不了的。

第七步,调参。把 buffer、coyote、cut factor 三个参数,按上面说的"先推极端再往回收"的方法,各自调一遍。把每组的"手感最佳值"记下来,对比一下你最终的值和我给的默认值(100 / 100 / 0.5)差多少。差得越多,说明你的游戏风格越远离"标准平台跳跃",这本身是有信息量的——它告诉你,你的游戏需要什么独特的手感参数。

做完这一篇的红线,你的 HH 角色应该已经从"能跑能跳"进化到"操作跟手、跳跃宽容、精度可调"。这是一个值得 commit 的里程碑,提交信息可以写"add input buffer, coyote time, and variable jump height to player controller"。

## 10 · 练习

**练习一(概念,Lv1)**:有人跟你说"输入缓冲不就是检测按键时长嘛,我每帧检查跳键是不是按住,按住超过 5 帧就跳"。想清楚为什么这是错的——按住和按下是两个完全不同的事件,缓冲存的是"按下的瞬间意图",不是"持续按住的状态"。如果你按住跳键不放,用我的实现,缓冲只会在你**第一次按下**的那一刻写入一次;如果你的实现是"按住就持续写 buffer",玩家按住一次,会被反复重新计时,体验完全不同。讲清楚这个区别。

**练习二(动手,Lv2)**:完成前面 §9 的全部七步,提交 commit。重点保证第六步"关闭单个机制感受回归"你真的玩过了——光写代码不玩,不算完成。

**练习三(设计,Lv3)**:除了跳跃,把输入缓冲用到另一个动作上——比如"攻击"或"闪避"。思考:哪些动作适合缓冲,哪些不适合?一般规则是,**有冷却的动作不适合缓冲**(否则玩家无意按一下,冷却好了会莫名其妙触发),**没有冷却但需要时机的动作适合缓冲**(跳跃、互动、上膛)。在你的 HH 项目里找一个适合的动作,给它加缓冲,感受差别。

**练习四(进阶,Lv4)**:测一下你 HH 角色的端到端输入延迟。方法:用手机的慢动作模式(240 fps)拍屏幕和你的手指,从你按下跳键到角色开始向上加速,数一下过了多少帧,换算成毫秒。如果你能做到 60 毫秒以内,及格;50 毫秒以内,优秀;40 毫秒以内,你已经达到竞技游戏水准。如果超过 100 毫秒,回到 §6 检查——是输入轮询时机错了(在帧末尾轮询)?还是 vsync 多了一帧?还是后处理太重?把延迟压下来,再玩一次,感受手感的质变。这一步是这一篇最难也最值得做的练习,它让你从"凭感觉调手感"升级到"用数据测手感"。

## 11 · 延伸阅读与下一篇

这一篇的理论框架主要来自 Steve Swink 的《Game Feel》(2008),这本书是手感领域的圣经,虽然例子有些过时,但底层理论至今适用。比 Swink 更早、也更经典的是 Vlambeer(Jan Willem Nijman)的 GDC 演讲 "The Art of Screenshake"(2013,YouTube),它更偏 juice 不那么偏输入,但精神是相通的。还有 Squirrel Eiserloh 的 "Juice It or Lose It"(GDC 2015),讲数学曲线的源头。Celeste 的开发者 Maddy Thorson 在博客上有几篇关于 Celeste 手感设计的文章(Celeste 的 feel 被广泛认为是平台跳跃的天花板),特别推荐 "Celeste's Feel" 和 "Celeste and TowerFall Physics" 两篇——里面详细讲了 Celeste 的 coyote time、input buffer、可变跳跃高度的具体数值,以及为什么这么选。

工程实践方面,这一篇和 phase-9 的两个模块紧密绑定:`09B-1-game-loop-and-timestep.md` 是地基(没有固定步长,手感参数不稳定);`09B-4-cvars-and-dev-console.md` 是迭代工具(没有 CVar,调参效率崩溃)。建议你把这一篇和这两篇作为一个连贯的整体来读和做。`09C-2-instance-device-swapchain.md` 里关于 present mode 的讨论,直接关系到 §6 讲的输入延迟优化——选什么 present mode,本质上是在选"撕裂 vs 延迟"的取舍。`days/phase-3/deep-dives/camera-systems.md` 会讲相机对手感的影响(相机抖动、跟随平滑、look-ahead),它是 part 2 的预热。`days/phase-2/deep-dives/input-handling-for-games.md`(我们计划中的输入处理专题)会从更底层讲事件队列、raw input、手柄死区,和这一篇互为补充。

游戏手感序列 part 2 [game-feel-02-camera](game-feel-02-camera.md) 会继续往上搭——讲相机手感。相机的平滑跟随、look-ahead(角色移动方向上提前露出一点视野)、相机抖动、相机 deadzone、动态 FOV,所有这些都会显著影响"游戏感觉多重、多稳、多跟手"。如果说这一篇讲的是"你的输入怎么被游戏接住",part 2 讲的是"游戏世界怎么跟着你动"。两者加起来,才是平台跳跃游戏手感的前半段;后半段(part 3 反馈与 juice,part 4 打磨)会把这些手感机制和视觉/音效反馈结合起来,变成完整的体验。

最后一句:这一篇讲的所有机制,代码加起来不超过 100 行。但它们是平台跳跃游戏从"能玩"到"好玩"的全部秘密。写完它们,调好参数,关掉再打开,亲身感受差别——这个流程走完一遍,你就理解了什么叫"game feel is engineered",而不是玄学。
