# Day 066 · 空间实体与非空间实体

> 玩家、怪、墙都是"在地图某位置"的 entity。但游戏里还有"游戏结束 UI"、"调试覆盖层"、"过场动画 controller"——这些东西**没有位置**,不参与碰撞 / AI / sim region。今天 Casey 把这两类分开,让每种 entity 走自己的最优路径。

## 0 · 为什么要有这一天

到目前为止(第 65 集),所有 entity 都有 `pos: Vec2` 字段。这个字段对玩家、怪、墙、投射物有意义——它们都在地图某处。

但游戏还要这些"东西":

- **UI 元素**:HP 条 / 小地图 / 物品栏 / 准星
- **Debug overlay**:FPS 显示 / 实体计数器
- **过场动画 controller**:播动画期间控制游戏
- **音频 listener**(虽然不是 spatial):全局背景音
- **存档触发器**:碰到存档点的逻辑 controller

这些"东西"和 spatial entity 一样是 entity(都有 update / state / data),但**没有世界位置**。把它们和 spatial entity 混在一起有几个问题:

**问题 1**:每帧 sim region unpack 时,要遍历**所有 entity** 找出在 sim region 内的。但 UI 不在地图上,"在 sim region 内"这个判断对它无意义。要么 UI 永远进 sim region(浪费),要么永远不进(那它怎么 update?)。

**问题 2**:spatial grid 把 entity 按位置放格子。UI 没位置,放哪个格子?随便放 = 查询命中错误,不放 = UI 不参与 grid,但 grid 是统一的啊。

**问题 3**:渲染时,spatial entity 用世界坐标 → 屏幕坐标转换。UI 用屏幕坐标直接画。混在一起,渲染逻辑要 if 分支。

**解决方案**:把 entity 分两类——**spatial**(有 pos,走 sim region / grid / 世界渲染)和 **non-spatial**(无 pos,走全局 update / 屏幕渲染)。

这就是 Casey 第 66 集做的事。听起来简单,但它是"游戏引擎分层"的关键一步——之后你能在 spatial entity 之上做物理,在 non-spatial 之上做 UI / debug / 工具。

读完今天,你要做到:
- 知道为什么 UI 不应该和地图 entity 混在一起
- 能用 Rust 的 enum 区分 spatial / non-spatial,让两种走不同 update 路径
- 理解 Unity 的 Canvas / GameObject 分离也是同样思想
- 知道 Casey 后面 Day 180+ 的 debug overlay 是 non-spatial entity

如果你卡在"为什么不直接给 UI 加个 pos = (0,0) 字段",回去看 §2.2——把无关概念硬塞进同一结构会模糊语义,导致 bug。

## 1 · Casey 今天做了什么

Casey 第 66 集做的事:

1. 给 Entity 加 `is_spatial: bool` 字段(或更 Rust 的:用 enum)
2. sim region unpack 时跳过 non-spatial:`if e.is_spatial && sim.contains(e.pos) { unpack }`
3. non-spatial entity 在另一个 update 路径——全局 update,不进 sim region
4. 渲染时:spatial 走 world-to-screen 转换,non-spatial 直接 screen 坐标

视频里 Casey 演示了一个 non-spatial entity:debug overlay。每帧画 FPS / entity 计数 / sim region 边界,这些东西不在地图上,跟着屏幕而不是相机。

## 2 · 心智模型

### 2.1 类比:剧场里的演员 vs 工作人员

剧场里有两类人:

- **演员**(spatial entity):站在舞台上某个位置,观众能看见。台词、动作都和位置有关
- **工作人员**(non-spatial):灯光师、音效师、道具管理员。他们在后台,观众看不见。他们做的事和"舞台位置"无关

如果把工作人员也塞进"舞台调度表"(spatial grid),你会发现:
- 灯光师的"位置"是什么?控制室?灯光在哪?混淆
- 工作人员不参与"演员之间的互动"(collision / AI),但要参与"剧组运转"(每帧 update)
- 他们的"渲染"是后台监视器,不是舞台灯光

所以剧场有两套调度:舞台调度(演员,spatial)+ 后台调度(工作人员,non-spatial)。两套并行,互不干扰。

### 2.2 严谨:is_spatial 字段 vs enum

#### 方案 A:bool 字段(Casey 在 C 用)

```rust
struct Entity {
    pos: Vec2,
    is_spatial: bool,
    kind: EntityKind,
    // ...
}

fn update(world: &mut World, dt: f32) {
    for e in &mut world.entities {
        if e.is_spatial {
            // 走 sim region 路径(只对 sim 内的)
        } else {
            // 全局 update(所有 non-spatial)
        }
    }
}
```

简单但**不类型安全**——spatial entity 的 pos 字段永远有意义,non-spatial 的 pos 永远没用。但都占内存。

#### 方案 B:enum with data(Rust idiomatic)

```rust
enum Entity {
    Spatial {
        pos: Vec2,
        kind: SpatialKind,
        // ...
    },
    NonSpatial {
        kind: NonSpatialKind,
        // ...
    },
}

fn update(e: &mut Entity, dt: f32) {
    match e {
        Entity::Spatial { pos, kind, .. } => {
            // spatial update
        }
        Entity::NonSpatial { kind, .. } => {
            // non-spatial update
        }
    }
}
```

类型安全——spatial 必有 pos,non-spatial 必无。但 enum 大小取最大 variant(浪费内存)。

#### 方案 C:两个独立集合

```rust
struct World {
    spatial_entities: Vec<SpatialEntity>,
    non_spatial_entities: Vec<NonSpatialEntity>,
}
```

最干净——两种完全独立的 storage / update / render 路径。Casey 在 Phase 5+ 接受这种分离。

#### 推荐方案

教学阶段:方案 A,理解概念
Rust 项目:方案 B,类型安全
生产阶段:方案 C,完全分离

Casey 第 66 集用方案 A(他在 C 里),Rust 翻译时建议方案 B。

### 2.3 sim region unpack 过滤

```rust
fn unpack(world: &World, sim: &mut SimRegion, camera_pos: Vec2) {
    sim.entities.clear();
    for (id, e) in &world.entities {
        // 只 unpack spatial 且在 region 内的
        if !e.is_spatial { continue; }
        if !sim.contains(e.pos) { continue; }
        sim.entities.push(SimEntity::from_world(*id, e));
    }
    // non-spatial 不进 sim,在另一个路径处理
}

fn update_non_spatial(world: &mut World, dt: f32) {
    for e in &mut world.entities {
        if !e.is_spatial {
            // debug overlay update / UI update / cutscene update
            update_non_spatial_entity(e, dt);
        }
    }
}
```

frame_update 现在两步:

```rust
fn frame_update(world: &mut World, dt: f32) {
    let mut sim = SimRegion::new(...);
    unpack(world, &mut sim, camera_pos);
    simulate(&mut sim, dt);  // spatial
    update_non_spatial(world, dt);  // non-spatial
    pack(world, &sim);
}
```

### 2.4 渲染分离

```rust
fn render(world: &World, sim: &SimRegion, camera: &Camera) {
    // 第一层:spatial entity(世界坐标 → 屏幕坐标)
    for e in &sim.entities {
        let screen_pos = camera.world_to_screen(e.pos);
        draw_sprite(e.sprite, screen_pos);
    }
    // 第二层:background(spawn 在 spatial 之前)
    draw_background(world.tile_map, camera);

    // 第三层:non-spatial entity(屏幕坐标)
    for e in &world.entities {
        if !e.is_spatial {
            draw_sprite(e.sprite, e.screen_pos);  // 直接屏幕坐标,无转换
        }
    }
}
```

**渲染顺序**很重要:背景 → spatial → non-spatial(UI 永远在最上层)。

### 2.5 为什么不"让 UI 也有 pos"

最直觉的"简化":

```rust
// 给 UI 也加 pos,设成 (0,0),反正不参与 collision
struct Entity { pos: Vec2, kind: EntityKind }
// UI entity: pos = (0,0)
```

听起来简化了(所有 entity 都有 pos),实际埋了几个 bug:

**bug 1**:UI 在 (0,0) 位置,如果 sim region 包含 (0,0),UI 被错误 unpack 进 sim region。然后 spatial grid 把它放在 (0,0) 格子,玩家走到 (0,0) 附近时,grid 查询返回 UI,碰撞检测尝试 minkowski_collide(player, UI),UI 没碰撞箱(或碰撞箱为 0)→ 行为未定义。

**bug 2**:UI 的 pos 没意义,但代码到处 `e.pos`。读代码的人不知道"这个 pos 有没有意义",要靠注释 / 经验。语义模糊。

**bug 3**:渲染时,UI 的 pos 是世界坐标还是屏幕坐标?如果用 (0,0),世界坐标转换到屏幕可能不在 (0,0)。语义不清。

**教训**:**结构表达语义**。如果某字段对某些 entity 无意义,要么用 Option<>,要么用 enum 分开,不要"假装有意义但实际不用"。这是数据建模的基本原则。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏引擎的"spatial / non-spatial"分离是**通用模式**:

- **Unity**:GameObject(3D 空间)vs Canvas(UI 屏幕空间)。两套完全独立的渲染管线
- **Unreal**:Actor(3D 空间)vs UMG Widget(UI)。完全分离
- **Godot**:Node2D / Node3D(spatial)vs Control(UI)。基类不同
- **Bevy**:没有内置 UI 抽象,但社区用 `bevy_ui` 单独 component

**为什么都分开**:UI 的需求(响应式布局 / 文本渲染 / 输入事件 / DPI 适配)和游戏 entity 的需求(物理 / 碰撞 / 动画)完全不同。**共用一个结构会两边都不优化**。

**Casey 的 HH 不会做完整 UI 系统**——他只做 debug overlay。但 non-spatial 的概念是基础。

### 3.2 · 🐧 Linux 系统编程视角

Linux 的窗口系统(X11 / Wayland)也分 spatial / non-spatial:

- **窗口(spatial)**:在屏幕某位置 / 大小,可移动 / 缩放。每个窗口是 spatial entity
- **Notification(non-spatial)**:屏幕角落,固定位置,不参与窗口管理
- **Cursor(non-spatial)**:鼠标光标,在所有窗口之上,不参与窗口堆叠
- **IME 候选词(non-spatial)**:跟随光标,但是是 UI 层

X11 把这些区分:
- 普通窗口:`CreateWindow` 创建,有 (x, y, w, h)
- Override-redirect 窗口:绕过窗口管理器,自己管位置(cursor / popup 用)
- Composite overlay:全屏覆盖层,永远在最上

这就是 spatial / non-spatial 的对应——不同的渲染路径 / 输入处理 / z-order。

### 3.3 · 🦀 Rust 生态视角

Rust 表达 spatial / non-spatial 的几种方式:

#### 方案 A:trait 多态

```rust
trait Entity {
    fn update(&mut self, world: &World, dt: f32);
    fn render(&self, ctx: &mut RenderCtx);
}

struct SpatialEntity { pos: Vec2, /* ... */ }
impl Entity for SpatialEntity { /* ... */ }

struct UiEntity { screen_pos: Vec2, /* ... */ }
impl Entity for UiEntity { /* ... */ }
```

灵活但 vtable 开销 + Box 堆分配,不适合 hot loop。

#### 方案 B:两个 Vec(推荐)

```rust
struct World {
    spatial: Vec<SpatialEntity>,
    non_spatial: Vec<NonSpatialEntity>,
}
```

每种类型连续内存,cache 友好。两条独立 update 路径。

#### 方案 C:enum + 标记(适合概念演示)

```rust
enum Entity {
    Spatial(SpatialData),
    NonSpatial(NonSpatialData),
}
```

简单,但 enum 大小取最大 variant。

### 3.4 数学/语义视角

更深一层:**类型表达不可能状态**。

```rust
// 错误:这个 struct 允许"无 pos 但有 collision"这种无意义组合
struct BadEntity {
    pos: Option<Vec2>,
    collision: Option<Aabb>,
}

// 好:类型保证组合有意义
enum GoodEntity {
    Spatial { pos: Vec2, collision: Aabb },
    NonSpatial { /* 无 pos 无 collision */ },
}
```

让"不可能的状态无法表达"(Parse, don't validate; Alexis King)——这是 Rust 类型系统的精髓。把"spatial 必有 pos / non-spatial 必无 pos"编进类型系统,编译器帮你检查。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么把 UI 强行加上 `pos = (0,0)` 字段是坏设计?

**参考解答**:三个理由:

1. **语义模糊**:UI 的"位置"是什么?屏幕左上角?世界原点?读代码的人不知道这个 (0,0) 是有意义的还是占位的。语义不清,bug 来源
2. **数据不一致**:spatial entity 的 pos 永远有意义(世界坐标),UI 的 pos 永远是占位。同样字段不同语义,违反"字段一致性"原则
3. **逻辑混乱**:UI 进入 spatial grid(因为 pos=(0,0) 算格子),被错误地参与碰撞查询。即使加 `if e.kind != UI` 跳过,每个 spatial 算法都要加这个分支,代码臭

正确做法:用 enum 或两个独立集合,让"UI 没有 pos"在类型系统层面表达。

### Lv2 · 动手实践

**题**:实现一个 debug overlay(non-spatial entity),显示 FPS / sim region 内 entity 数。验证:
1. spawn 一个 DebugOverlay entity,kind = NonSpatial
2. sim region unpack 时跳过它(因为 non-spatial)
3. 每帧 update 时,它读取 sim.entities.len() 并存到自己的字段
4. 渲染时,直接画在屏幕角落

**完成标准**:游戏运行后,屏幕角落显示"FPS: 60, sim entities: 7"之类的文字(可以用 println 代替真实渲染)。

**参考解答**:

```rust
use std::collections::HashMap;

type EntityId = u32;

#[derive(Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

#[derive(Clone, Copy, PartialEq, Debug)]
enum EntityKind {
    Spatial { kind: SpatialKind },
    NonSpatial { kind: NonSpatialKind },
}

#[derive(Clone, Copy, PartialEq, Debug)]
enum SpatialKind { Player, Monster, Wall }

#[derive(Clone, Copy, PartialEq, Debug)]
enum NonSpatialKind { DebugOverlay, FpsCounter }

#[derive(Clone, Debug)]
struct Entity {
    id: EntityId,
    kind: EntityKind,
    pos: Option<Vec2>,           // 仅 spatial 有
    fps: Option<f32>,            // 仅 DebugOverlay 有
    sim_count: Option<usize>,    // 仅 DebugOverlay 有
}

impl Entity {
    fn debug_overlay(id: EntityId) -> Self {
        Self {
            id, kind: EntityKind::NonSpatial { kind: NonSpatialKind::DebugOverlay },
            pos: None, fps: Some(0.0), sim_count: Some(0),
        }
    }
    fn player(id: EntityId, pos: Vec2) -> Self {
        Self {
            id, kind: EntityKind::Spatial { kind: SpatialKind::Player },
            pos: Some(pos), fps: None, sim_count: None,
        }
    }
    fn is_spatial(&self) -> bool {
        matches!(self.kind, EntityKind::Spatial { .. })
    }
}

struct World {
    entities: HashMap<EntityId, Entity>,
    next_id: EntityId,
}

impl World {
    fn new() -> Self { Self { entities: HashMap::new(), next_id: 1 } }
    fn spawn(&mut self, e: Entity) -> EntityId {
        let id = e.id;
        self.entities.insert(id, e);
        id
    }
    fn alloc_id(&mut self) -> EntityId {
        let id = self.next_id; self.next_id += 1; id
    }
}

fn unpack_sim(world: &World, sim_region: &[EntityId], sim: &mut Vec<EntityId>) {
    sim.clear();
    for id in sim_region {
        if let Some(e) = world.entities.get(id) {
            if e.is_spatial() {
                sim.push(*id);
            }
        }
    }
}

fn update_non_spatial(world: &mut World, sim_count: usize, fps: f32) {
    for e in world.entities.values_mut() {
        if !e.is_spatial() {
            if let Some(f) = e.fps.as_mut() { *f = fps; }
            if let Some(c) = e.sim_count.as_mut() { *c = sim_count; }
        }
    }
}

fn render(world: &World) {
    // 模拟渲染
    for e in world.entities.values() {
        match &e.kind {
            EntityKind::Spatial { .. } => {
                let pos = e.pos.unwrap();
                println!("  [spatial] draw at world ({}, {})", pos.x, pos.y);
            }
            EntityKind::NonSpatial { kind: NonSpatialKind::DebugOverlay } => {
                println!("  [overlay] FPS: {}, sim entities: {}",
                    e.fps.unwrap(), e.sim_count.unwrap());
            }
            _ => {}
        }
    }
}

fn main() {
    let mut world = World::new();
    let _p = world.spawn(Entity::player(world.alloc_id(), Vec2 { x: 100.0, y: 100.0 }));
    let _dbg = world.spawn(Entity::debug_overlay(world.alloc_id()));

    // 模拟一帧
    let sim_region: Vec<EntityId> = world.entities.keys().copied().collect();
    let mut sim = vec![];
    unpack_sim(&world, &sim_region, &mut sim);
    println!("sim region unpacked: {} entities (player only, overlay skipped)", sim.len());
    assert_eq!(sim.len(), 1);

    update_non_spatial(&mut world, sim.len(), 60.0);
    println!("after render:");
    render(&world);
}
```

## 8 · Rust / Arch 落地代码

### 关键 Rust 特性

#### enum with data 表达"互斥状态"

```rust
enum EntityKind {
    Spatial { kind: SpatialKind },
    NonSpatial { kind: NonSpatialKind },
}
```

variant 带数据,Rust 编译器强制 match 完整。spatial / non-spatial 互斥,不可能"既是又不是"。

#### Option<T> 表达"可能有"

```rust
pos: Option<Vec2>,
fps: Option<f32>,
```

Option 强制用户检查 None。比 null 安全。

#### matches! 宏

```rust
fn is_spatial(&self) -> bool {
    matches!(self.kind, EntityKind::Spatial { .. })
}
```

`{ .. }` 表示忽略 variant 内部字段。简洁。
