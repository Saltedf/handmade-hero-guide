
# Day 037 · 基础位图渲染

> Day 036 你能加载 BMP 到内存,但还不会画到屏幕。Day 037 实现最经典的 2D 渲染操作——**blit**(位块传送)。把一块像素从源(bitmap)复制到目标(framebuffer)。听起来简单,但 blit 是所有 2D 渲染的基础:tile 贴图、sprite 动画、UI 元素、文字渲染,本质都是 blit 的变种。

## 0 · 为什么要有这一天

你做完 BMP 加载,有一个 `BmpImage` 在内存里,但游戏画面还是纯色块。**怎么把 BMP 画到屏幕?**

最直接的想法:

```rust
for y in 0..bmp.height {
    for x in 0..bmp.width {
        framebuffer[(screen_y + y) * SCREEN_WIDTH + (screen_x + x)] =
            bmp.pixels[y * bmp.width + x];
    }
}
```

这就是 **blit**(BitBlt = BITmap Block Transfer)。看似简单,但有几个**非平凡决策**:

1. **越界处理**:bitmap 一部分在屏幕外,要不要画?怎么画?
2. **裁剪**(clipping):屏幕只有 1920×1080,bitmap 大于此,只画可见部分
3. **API 设计**:`blit(fb, x, y, bmp)` 还是 `push_command(Blit { ... })`?
4. **性能**:32×32 = 1024 像素 × 几百 sprite = 几十万次内存写。怎么保证 60 FPS?
5. **未来扩展**:blit 现在是 1:1 复制,以后要 alpha 混合(Day 038)、缩放(Day 094)、旋转(Day 092)

**Casey 的核心思路**:**抽象**。这集不直接 blit 像素,而是 **push 命令**(PushBitmap{x, y, id})。渲染器消费命令执行 blit。这是 Day 088 push buffer 的雏形——让渲染后端可换(Day 235 切 OpenGL 时游戏代码几乎不改)。

心理锚点:看完这集,你应该能:

- 写出一个最简的 `blit` 函数(1:1 复制)
- 解释为什么 Casey 用 "push command" 而不是 "直接画"
- 算出 blit 的性能预算(32×32 sprite × 100 = ?)
- 在白板上画出"屏幕外部分如何裁剪"

如果你做不到,反复看 §2 的"blit 算法"和"裁剪"部分。Day 038(透明混合)、Day 088(push buffer)、Day 235(OpenGL)都基于这集的抽象。

## 2 · 心智模型

### 类比:盖章

把 blit 想象成**盖章**:

- bitmap 是刻好的章(已经"画"好的像素)
- framebuffer 是纸
- blit = 把章按在纸上某个位置,印出图案

特点:

- **1:1 复制**:章多大,印出来就多大(这集不做缩放)
- **位置**:你可以按在任意位置(屏幕坐标)
- **不能旋转**:章的"上"始终是上(Day 092 才加旋转)
- **没透明**:章的所有部分都印(Day 038 才加 alpha 混合)

后期演化:

- **alpha 混合**(Day 038):章的部分透明
- **缩放**(Day 094):章大小可变
- **旋转**(Day 092):章可旋转
- **着色**:章的颜色可调(染色)

但**所有这些都是在基础 blit 上加变换**——基础 blit 是地基。

### 最简 blit 算法

```rust
fn blit_basic(
    fb: &mut [u32],
    fb_w: i32, fb_h: i32,
    dest_x: i32, dest_y: i32,
    src: &[u32], src_w: i32, src_h: i32,
) {
    for sy in 0..src_h {
        for sx in 0..src_w {
            let dx = dest_x + sx;
            let dy = dest_y + sy;
            // 越界检查
            if dx < 0 || dy < 0 || dx >= fb_w || dy >= fb_h {
                continue;
            }
            fb[(dy * fb_w + dx) as usize] = src[(sy * src_w + sx) as usize];
        }
    }
}
```

**问题**:每个像素都要 if 越界检查,**浪费**。优化:**先算 visible 区域,只迭代 visible**。

### 优化版:计算 visible 区域

```rust
fn blit(
    fb: &mut [u32],
    fb_w: i32, fb_h: i32,
    dest_x: i32, dest_y: i32,
    src: &[u32], src_w: i32, src_h: i32,
) {
    // 计算 visible 区域(在 src 坐标里)
    let src_x_start = if dest_x < 0 { -dest_x } else { 0 };
    let src_y_start = if dest_y < 0 { -dest_y } else { 0 };
    let src_x_end = std::cmp::min(src_w, fb_w - dest_x);
    let src_y_end = std::cmp::min(src_h, fb_h - dest_y);

    // 全部在屏幕外,什么都不画
    if src_x_start >= src_x_end || src_y_start >= src_y_end {
        return;
    }

    // 只迭代 visible
    for sy in src_y_start..src_y_end {
        for sx in src_x_start..src_x_end {
            let dx = dest_x + sx;
            let dy = dest_y + sy;
            fb[(dy * fb_w + dx) as usize] = src[(sy * src_w + sx) as usize];
        }
    }
}
```

**关键变化**:

- **if 检查移到外面**:不再每像素 if,只算一次 visible 边界
- **visible 内的循环**:dx, dy 必然在 fb 内,不用 if
- **早返回**:如果 visible 为空,直接 return

这优化让 blit 的性能**提升 1.5-2 倍**(具体看 bitmap 是否大部分在屏幕内)。

### 性能预算

假设渲染 1000 个 32×32 sprite:

- 每个 sprite 32×32 = 1024 像素
- 1000 sprite = 1,024,000 像素写入
- 每像素 1 次内存读 + 1 次内存写 ≈ 2 cycle(L1 cache hit)
- 总 cycle ≈ 2,000,000
- 60 FPS 时一帧 50,000,000 cycle(3 GHz CPU)
- 渲染占比:2M / 50M = 4%

**完全够 60 FPS**,还有 96% CPU 时间给其他事。所以 Casey 这集**不优化 blit**——直接写最清晰的版本。

如果 bitmap 大(512×512 sprite),或 sprite 多(10000),blit 可能成瓶颈。这时候用 SIMD(Day 121+)或 GPU(Day 235+)。

### API 设计:push command vs 直接画

Casey 的设计:**push command,渲染器消费**。

```rust
enum RenderCommand {
    Bitmap { x: i32, y: i32, asset_id: BitmapId },
    Rect { x: i32, y: i32, w: i32, h: i32, color: u32 },
    Text { x: i32, y: i32, text: String },
}

struct RenderBuf {
    commands: Vec<RenderCommand>,
}

impl RenderBuf {
    fn push_bitmap(&mut self, x: i32, y: i32, asset_id: BitmapId) {
        self.commands.push(RenderCommand::Bitmap { x, y, asset_id });
    }
}

// 游戏代码(逻辑层)→ push 命令
fn render(state: &GameState, render_buf: &mut RenderBuf) {
    render_buf.push_bitmap(player.pos.x, player.pos.y, player.bitmap_id);
    for monster in &state.monsters {
        render_buf.push_bitmap(monster.pos.x, monster.pos.y, monster.bitmap_id);
    }
}

// 渲染器(渲染层)→ 消费命令,画像素
fn flush_render_buf(render_buf: &RenderBuf, assets: &AssetLibrary, fb: &mut [u32]) {
    for cmd in &render_buf.commands {
        match cmd {
            RenderCommand::Bitmap { x, y, asset_id } => {
                let bmp = assets.get(*asset_id);
                blit(fb, SCREEN_W, SCREEN_H, *x, *y, &bmp.pixels, bmp.width, bmp.height);
            }
            ...
        }
    }
}
```

**为什么这样设计**:

1. **逻辑层不依赖渲染后端**:`render` 函数 push 命令,不直接画像素。换 OpenGL / Vulkan 时逻辑层不改
2. **命令可重放**:把 commands 序列化到文件,反序列化就能复现画面(调试用)
3. **批量优化**:渲染器可以重排命令(按纹理 batch),减少 GPU state 切换
4. **多线程**:逻辑层和渲染器可并行(逻辑 push,渲染消费)

**Day 026 三明治分层**再次显现:**逻辑层** push 命令,**渲染层**执行。

### 渲染顺序很重要

```rust
// 1. 画背景(tile map)
render_tiles(map, fb);

// 2. 画 entity(怪物,投射物)
for m in &state.monsters { draw_bitmap(fb, ..., &m.bitmap); }

// 3. 画玩家
draw_bitmap(fb, ..., &player.bitmap);

// 4. 画 UI(血量,得分)
draw_text(fb, ..., "HP: 100");
```

**顺序决定 z-order**(谁盖谁):

- 后画的盖先画的(画家算法 painter's algorithm)
- 背景在底,玩家在上面,UI 在最上

如果顺序错(玩家先画,然后 tile),玩家被 tile 盖住,看不见。

Casey 这集保持简单顺序:tile → entity → player → UI。Day 040+ 加 z-buffer(3D 必需,2D 可选)。

### 调试辅助:画 bitmap 边界

debug 模式下,给每个 bitmap 画一个 1 像素红框,方便检查:

```rust
fn draw_bitmap_debug(
    fb: &mut [u32],
    fb_w: i32, fb_h: i32,
    dest_x: i32, dest_y: i32,
    bmp: &BitmapAsset,
) {
    // 正常 blit
    blit(fb, fb_w, fb_h, dest_x, dest_y, &bmp.pixels, bmp.width, bmp.height);

    // 画边界(红)
    let red = 0xFF0000;
    for x in 0..bmp.width {
        // 上边
        let dy = dest_y;
        let dx = dest_x + x;
        if dx >= 0 && dy >= 0 && dx < fb_w && dy < fb_h {
            fb[(dy * fb_w + dx) as usize] = red;
        }
        // 下边
        let dy = dest_y + bmp.height - 1;
        if dx >= 0 && dy >= 0 && dx < fb_w && dy < fb_h {
            fb[(dy * fb_w + dx) as usize] = red;
        }
    }
    for y in 0..bmp.height {
        // 左边
        let dy = dest_y + y;
        let dx = dest_x;
        if dx >= 0 && dy >= 0 && dx < fb_w && dy < fb_h {
            fb[(dy * fb_w + dx) as usize] = red;
        }
        // 右边
        let dx = dest_x + bmp.width - 1;
        if dx >= 0 && dy >= 0 && dx < fb_w && dy < fb_h {
            fb[(dy * fb_w + dx) as usize] = red;
        }
    }
}
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

Blit 是 2D 游戏的**核心原语**(primitive)。所有 2D 渲染都基于 blit 变种:

| 渲染操作 | 本质 |
|---|---|
| 画 tile | blit(tile 贴图 → framebuffer) |
| 画 sprite | blit(sprite → framebuffer,带 alpha) |
| 画 UI | blit(UI 元素 → framebuffer) |
| 画文字 | blit(字符 sprite → framebuffer) |
| 滚动 | blit(整个 framebuffer 偏移) |
| 屏幕震动 | blit(framebuffer → framebuffer,偏移) |

**SDL / Win32 / GDI** 都有 blit 函数(`SDL_BlitSurface`、`BitBlt`)。Casey HH 自己写 blit,理解原理。

**SDL_BlitSurface**:SDL 的 blit 支持透明色(color key)、alpha 混合、缩放。Casey Day 037 做最简版,Day 038+ 加 alpha。

**现代 GPU 的 blit**:`vkCmdBlitImage`(Vulkan)、`glBlitFramebuffer`(OpenGL)。GPU 硬件加速,但概念一样——一块像素 → 另一块。

### 3.2 · 🎨 图形学视角

Blit 在图形学里属于 **raster operation**(光栅操作)。具体分类:

**1:1 blit**(这集):

- 不变形,直接复制
- 用于:tile、UI、固定大小 sprite

**拉伸 blit**:

- 源和目标大小不同
- 用双线性 / 三线性插值

**旋转 blit**:

- 源旋转后 blit
- 用 shear / 仿射变换

**Alpha blit**(Day 038):

- 每像素有透明度
- 混合:`out = src * alpha + dst * (1 - alpha)`

**Tinted blit**:

- blit 时染色(把白色 sprite 染成红色)
- 用于:UI 状态变化(hover 状态变亮)

**Additive blit**:

- 像素相加而非替换
- 用于:光效、火焰、激光

Casey 在 Day 037 做 1:1 blit,后面逐步加各种变种。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上 blit 由 **DRM / KMS**(Direct Rendering Manager / Kernel Mode Setting)硬件加速。

**用户态 blit 路径**:

```
你的代码:fb[i] = pixel;
   ↓
Rust std 库:内存写入
   ↓
glibc / musl:无操作(直接内存)
   ↓
CPU:写入内存,可能进 L1/L2 cache
   ↓
(framebuffer 在显存时)PCIe 写到 GPU
   ↓
GPU 显示
```

如果 framebuffer 是**主存的某段**(Linux fbdev `/dev/fb0`),CPU 直接写主存,GPU 通过 DMA 显示。

**Linux 工具**:

```bash
# 看 Linux fbdev(老式 framebuffer 接口)
ls /dev/fb*
# /dev/fb0

# 看 framebuffer 信息
cat /sys/class/graphics/fb0/virtual_size
# 1280,720
cat /sys/class/graphics/fb0/bits_per_pixel
# 32

# 直接写 framebuffer(危险!)
# 以下命令会直接画一个红点在 (100, 100):
echo -ne '\x00\x00\xff\xff' | dd of=/dev/fb0 bs=4 count=1 seek=$((100 * 1280 + 100)) 2>/dev/null
# (实际可能需要 root,且现代 Linux 用 DRM 替代 fbdev)

# 看 DRM(现代显示子系统)
ls /dev/dri/
# card0  renderD128

# 用 modetest 看 DRM 模式
sudo pacman -S libdrm
modetest -M i915  # Intel GPU
```

现代 Linux 桌面(Wayland / X11)用 DRM + GPU 加速,但**原理和 Casey 的 CPU blit 一样**——都是"一段内存表示画面"。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 blit 有几种方式:

**方式 1:`for` 循环(Casey 风格)**

```rust
for y in 0..height {
    for x in 0..width {
        fb[dst_idx] = src[src_idx];
    }
}
```

清晰,完全控制。release 模式下编译器优化得很好。

**方式 2:slice 操作**

```rust
// 一行一行复制(更快,memcpy 风格)
for y in 0..height {
    let src_row = &src[y * src_w..(y + 1) * src_w];
    let dst_row = &mut fb[dst_offset + y * fb_w..];
    dst_row[..src_w].copy_from_slice(src_row);
}
```

`copy_from_slice` 内部用 `memcpy`,极快。

**方式 3:iterator**

```rust
for (sy, dy) in (0..src_h).zip(0..dst_h) {
    let src_row = src[sy * src_w..(sy+1)*src_w].iter();
    let dst_row = fb[dy * fb_w..].iter_mut();
    for (s, d) in src_row.zip(dst_row) {
        *d = *s;
    }
}
```

函数式风格,但生成的代码和方式 1 差不多。

**方式 4:SIMD**

```rust
use std::simd::*;
// 一次 4 个 u32(16 字节)
for chunk in src.chunks(4) {
    let v = u32x4::from_slice(chunk);
    // 写到 fb ...
}
```

最快,但复杂。Day 121+ Casey 加 SIMD。

**Casey 选方式 1/2**(教学清晰)。

**Rust 所有权和 blit**:

```rust
// ✓ 借用 fb(可变)+ 借用 src(只读)
fn blit(fb: &mut [u32], src: &[u32], ...) { ... }

// 调用
blit(fb, &bmp.pixels, ...);  // OK
```

借用规则自然支持"读一个,写另一个"。如果 fb 和 src 是同一段内存(self-blit),需要小心——Rust 的借用规则不允许同时 `&mut` 和 `&`。

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:把一段像素复制到另一段。

| 语境 | "blit"叫法 | 实现 |
|---|---|---|
| 2D 游戏 | blit / draw_sprite | CPU 或 GPU |
| 操作系统 GUI | BitBlt(Win32) | 内核 + GDI |
| 命令行 TUI | 直接写 cell | termios + ANSI |
| Web | drawImage(Canvas API) | JS → 浏览器 → GPU |
| 视频播放 | display frame | 解码 → blit → 显示 |
| 远程桌面(VNC) | send rect | 压缩 → 网络传输 |

所有这些场景的核心思想相同:**一段像素 → 另一段**。

### blit 的演化

- **1970s**:Smalltalk 的 BITBLT 操作,第一个 blit
- **1980s**:Amiga 的 Blitter 芯片(硬件 blit!),游戏机标配
- **1990s**:Win32 BitBlt,带 ROP(raster operation)
- **2000s**:GPU 普及,blit 走 GPU
- **2010s**:WebGL / canvas drawImage,Web 也能 blit
- **2020s**:WebGPU,跨平台 GPU blit

Casey HH 教 CPU blit → Day 235+ 切 GPU blit。

### CPU blit vs GPU blit

| | CPU blit | GPU blit |
|---|---|---|
| 像素 / 秒 | ~100M | ~10G(100 倍) |
| 延迟 | 低(CPU 直接) | 中(命令提交 + GPU 执行) |
| 灵活 | 高(任何算法) | 低(GPU 擅长的算法) |
| 适合 | 少量 sprite / 复杂控制 | 大量 sprite / 标准渲染 |

HH Day 1-234 CPU,Day 235+ GPU。理解 CPU blit 是 GPU blit 的基础——概念一样,只是执行单元不同。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 用"push command"接口(`push_bitmap(x, y, id)`),而不是"直接画"(`fb[i] = pixel`)。两个理由是什么?

**参考解答**:

**理由 1:换渲染后端不动逻辑层**

Day 026 的三明治分层让逻辑层和渲染层解耦。push command 是这个分层的"接口"——逻辑层只描述"画什么",不关心"怎么画"。

切 OpenGL(Day 235)时,逻辑层一行不改,只改渲染器(命令消费者)。这就是 push command 接口的价值。

**理由 2:命令可重放 / 重排**

push 的命令存在 Vec 里,渲染器可以:

- **重排**:按纹理 batch,减少 GPU state 切换
- **重放**:序列化到文件,反序列化复现画面(调试)
- **过滤**:某些 debug 模式不画某些命令

如果直接画像素,这些都做不了——像素已经写到 framebuffer,无法回溯。

### Lv2 · 动手实践

**题**:实现 blit,渲染一个 BMP 到屏幕。要求:

1. 用 Day 036 的 BMP 加载代码
2. 实现 `blit(fb, fb_w, fb_h, dest_x, dest_y, src, src_w, src_h)`
3. 实现带 visible 区域计算的优化版
4. 在 PPM 文件上"blit"——把一个 BMP blit 到另一个大的纯色 framebuffer,导出 PPM

完成标准:导出的 PPM 上能看到 BMP 图案。

**参考解答**:

```rust
// src/main.rs
// cargo new --bin blit_demo && cd blit_demo

const FB_W: i32 = 320;
const FB_H: i32 = 240;

fn blit(
    fb: &mut [u32], fb_w: i32, fb_h: i32,
    dest_x: i32, dest_y: i32,
    src: &[u32], src_w: i32, src_h: i32,
) {
    // 计算 visible 区域(src 坐标系)
    let src_x_start = dest_x.max(0).min(src_w) - dest_x;
    let src_y_start = dest_y.max(0).min(src_h) - dest_y;
    let src_x_end = (fb_w - dest_x).max(0).min(src_w);
    let src_y_end = (fb_h - dest_y).max(0).min(src_h);

    if src_x_start >= src_x_end || src_y_start >= src_y_end {
        return;
    }

    for sy in src_y_start..src_y_end {
        let dy = (dest_y + sy) as usize;
        let sx_start = src_x_start as usize;
        let sx_end = src_x_end as usize;
        let src_row_start = sy as usize * src_w as usize;
        let dst_row_start = dy * fb_w as usize + dest_x as usize;

        // 用 slice 操作,一次复制一行
        fb[dst_row_start + sx_start..dst_row_start + sx_end]
            .copy_from_slice(&src[src_row_start + sx_start..src_row_start + sx_end]);
    }
}

fn write_ppm(filename: &str, fb: &[u32], w: i32, h: i32) {
    use std::io::Write;
    let mut f = std::fs::File::create(filename).unwrap();
    writeln!(f, "P6\n{} {}\n255", w, h).unwrap();
    let mut bytes = Vec::with_capacity((w * h * 3) as usize);
    for &p in fb {
        bytes.push(((p >> 16) & 0xFF) as u8);
        bytes.push(((p >> 8) & 0xFF) as u8);
        bytes.push((p & 0xFF) as u8);
    }
    f.write_all(&bytes).unwrap();
}

fn main() {
    // 创建 framebuffer(蓝色背景)
    let mut fb = vec![0x000044_u32; (FB_W * FB_H) as usize];

    // 创建"sprite"(32x32 红色方块带白色边框)
    let sprite_w = 32_i32;
    let sprite_h = 32_i32;
    let sprite: Vec<u32> = (0..sprite_h).flat_map(|y| {
        (0..sprite_w).map(move |x| {
            let is_border = x == 0 || y == 0 || x == sprite_w - 1 || y == sprite_h - 1;
            if is_border { 0xFFFFFF } else { 0xFF0000 }
        })
    }).collect();

    // blit 几个 sprite 到不同位置
    blit(&mut fb, FB_W, FB_H, 50, 50, &sprite, sprite_w, sprite_h);   // 中间
    blit(&mut fb, FB_W, FB_H, -10, -10, &sprite, sprite_w, sprite_h); // 部分在屏幕外(左上)
    blit(&mut fb, FB_W, FB_H, FB_W - 20, FB_H - 20, &sprite, sprite_w, sprite_h); // 部分在屏幕外(右下)
    blit(&mut fb, FB_W, FB_H, 200, 100, &sprite, sprite_w, sprite_h); // 中间
    blit(&mut fb, FB_W, FB_H, -50, 200, &sprite, sprite_w, sprite_h); // 完全在屏幕外(应该不画)

    write_ppm("output.ppm", &fb, FB_W, FB_H);
    println!("Wrote output.ppm ({}x{})", FB_W, FB_H);
    println!("View with: feh output.ppm");
}
```

**预期输出**(打开 output.ppm):

```
[蓝色背景]
   [红+白边 sprite]   [红+白边 sprite]   [...]
                        ...
                                   [红+白边 sprite](部分裁)
```

注意左上和右下的 sprite 应该被正确裁剪(只画可见部分)。屏幕外的 sprite(-50, 200)完全不画。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例(性能对比)

把 Lv2 扩展,加性能对比:

```rust
// src/main.rs (扩展 Lv2)
// 加:naive vs clipped blit 性能对比

fn blit_naive(
    fb: &mut [u32], fb_w: i32, fb_h: i32,
    dest_x: i32, dest_y: i32,
    src: &[u32], src_w: i32, src_h: i32,
) {
    for sy in 0..src_h {
        for sx in 0..src_w {
            let dx = dest_x + sx;
            let dy = dest_y + sy;
            if dx < 0 || dy < 0 || dx >= fb_w || dy >= fb_h {
                continue;
            }
            fb[(dy * fb_w + dx) as usize] = src[(sy * src_w + sx) as usize];
        }
    }
}

fn bench_blits() {
    let fb_w = 1280;
    let fb_h = 720;
    let sprite_w = 32;
    let sprite_h = 32;
    let sprite: Vec<u32> = vec![0xFF0000; (sprite_w * sprite_h) as usize];

    let n = 10_000;

    // Bench naive
    let mut fb1 = vec![0u32; (fb_w * fb_h) as usize];
    let start = std::time::Instant::now();
    for _ in 0..n {
        blit_naive(&mut fb1, fb_w, fb_h, 100, 100, &sprite, sprite_w, sprite_h);
    }
    let naive_time = start.elapsed();

    // Bench clipped
    let mut fb2 = vec![0u32; (fb_w * fb_h) as usize];
    let start = std::time::Instant::now();
    for _ in 0..n {
        blit(&mut fb2, fb_w, fb_h, 100, 100, &sprite, sprite_w, sprite_h);
    }
    let clipped_time = start.elapsed();

    println!("=== Blit Performance ({} iterations) ===", n);
    println!("Naive (per-pixel if):  {:?}", naive_time);
    println!("Clipped (visible area): {:?}", clipped_time);
    println!("Speedup: {:.2}x", naive_time.as_secs_f64() / clipped_time.as_secs_f64());

    // 验证结果一致
    assert_eq!(fb1, fb2);
}

fn main() {
    bench_blits();
}
```

**预期输出**:

```
=== Blit Performance (10000 iterations) ===
Naive (per-pixel if):  18ms
Clipped (visible area): 7ms
Speedup: 2.57x
```

clipped 版比 naive 快 2-3 倍。
