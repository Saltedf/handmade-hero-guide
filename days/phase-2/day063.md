# Day 063 · 模拟区域:只更新相机附近

> 世界有 100 万个 entity。每帧 update 100 万次?那游戏跑不到 5 FPS。Casey 今天做了一件 Phase 2 最聪明的事:**不管世界多大,每帧只把相机周围的 entity "unpack" 到一个紧凑 Vec 上跑模拟,完了再 "pack" 回稀疏存储**。这就是大世界游戏能跑得动的秘密。

## 0 · 为什么要有这一天

到第 62 集为止,你的游戏世界假设是"中等大小"——几千个 entity,每帧扫一遍 update + collision + AI。还能跑。

但你一旦想做**大世界**(Minecraft 那种 60000×60000 块,或 GTA 那种几平方公里的城市),立刻撞墙:

```
100 万 entity × 每帧 update(假设 1 µs/entity)
= 1,000,000 µs = 1 秒 / 帧
=> 1 FPS
```

不可玩。

但你仔细想:**玩家看不到的 entity,真的需要 update 吗?**
- 1000 像素外的怪,它巡逻 / 攻击 / 死亡,玩家完全看不到
- 即使你 update 了,对玩家体验零贡献
- **不 update 也无所谓**(只要玩家走过去时,这些怪"恢复"到合理状态)

这就是 **Simulation Region**(模拟区域)的核心思想:

> 每帧只 update 相机周围的 entity。世界存储是稀疏的(HashMap),每帧开始时把 sim region 内的 entity **拷贝到紧凑 Vec** 上,模拟完**拷回**稀疏存储。

效果:
- **O(1) 模拟成本**(不管世界多大,sim region 内 entity 数固定,通常几百个)
- **Cache-friendly**(sim region 是连续 Vec,L1 cache 命中率极高)
- **自然支持"虚拟化大世界"**(Day 033+ 的概念,今天落地)

读完今天,你要做到:
- 用 1 分钟画出 unpack → simulate → pack 的流程
- 理解为什么 unpack 到 Vec 而不是直接在 HashMap 上跑(L1 cache)
- 知道 Casey 后面 Day 121 / Day 350 都基于这个模式
- 能动手实现简化版 sim region

如果你卡在"为什么不直接在 HashMap 上跑"——回去看 §2.3 关于 cache 的讨论。这是 sim region 的真正动机,不是为了"减少 update 数"(那只是副作用)。

## 1 · Casey 今天做了什么

Casey 第 63 集做的事(架构层):

1. 定义 `SimRegion` 结构:`entities: Vec<SimEntity>` + 边界矩形 + 双向映射表
2. 每帧开始时:
   - 清空 sim region
   - 计算相机中心 + sim region 边界(玩家周围 ±300 像素)
   - 遍历世界存储(`world.entities` HashMap),把 sim region 内的 entity "unpack" 到 `sim.entities.push(SimEntity::from_world(...))`
3. 模拟阶段(整个 update / collision / AI / render)全部在 sim region 上跑
4. 帧末:遍历 sim region,把改动 "pack" 回世界存储
5. 下一帧重新 unpack(因为玩家可能移动了)

视频里 Casey 强调:"sim region 不是为了'少 update'——你 update 的 entity 数本来就只有几百。它是为了**让 hot loop 在连续内存上跑**。HashMap 是稀疏的,每次访问 cache miss,慢 10-25×。Vec 是连续的,L1 cache 命中。这就是 sim region 的真正动机。"

## 2 · 心智模型

### 2.1 类比:画家的工作台

想象一个画家,要画一幅 100 米长的画卷,上面有 10000 个角色。但他**工作台只有 1 米宽**——一次只能放 100 个角色。

朴素做法:把整个画卷摊开,画家走来走去画每个角色。
- 问题:画家花大量时间走来走去
- 问题:每次走到新位置要"重新载入"那部分画卷

聪明做法:画家**只把"当前正在画的部分"剪下来,放到工作台上**,画完,**贴回去**,再剪下一段。
- 工作台上是连续的(容易看 / 改)
- 画卷 100 米长的整体不用变

sim region 就是这个"1 米宽的工作台"。世界存储是 100 米长的画卷。每帧把当前要处理的区域"剪下来",处理完"贴回去"。

### 2.2 严谨:数据流

```
[世界存储:HashMap<EntityId, Entity>]  (稀疏,可能几百万个)
                  ↓ unpack(过滤 + 复制到 Vec)
[Sim Region:Vec<SimEntity>]            (紧凑,几百个)
                  ↓ simulate(update / collision / AI)
[Sim Region:Vec<SimEntity>](mutated)
                  ↓ pack(写回 HashMap)
[世界存储:HashMap<EntityId, Entity>]
```

每帧重复。

#### unpack:稀疏 → 紧凑

```rust
fn unpack_sim_region(world: &World, camera_pos: Vec2, region_size: f32) -> SimRegion {
    let region_aabb = Aabb::from_center(camera_pos, Vec2::new(region_size, region_size));
    let mut sim = SimRegion::new();
    for (id, e) in &world.entities {
        if region_aabb.contains(e.pos) {
            sim.entities.push(SimEntity::from_world(*id, e));
        }
    }
    sim
}
```

**关键**:这里**拷贝**了 entity 数据(`SimEntity::from_world`),不是引用。所以 sim region 是 Vec<SimEntity>(owned),后续 mutate 自由。

#### simulate:hot loop on Vec

```rust
fn simulate(sim: &mut SimRegion, input: &Input, dt: f32) {
    // update AI / 物理 / 碰撞 / 攻击
    // 全部在 sim.entities(Vec) 上跑,L1 cache 命中
    for e in &mut sim.entities {
        e.update(dt, input);
    }
    // 碰撞、AI 视线、攻击都在 sim 内
}
```

#### pack:紧凑 → 稀疏

```rust
fn pack_sim_region(world: &mut World, sim: &SimRegion) {
    for se in &sim.entities {
        if let Some(we) = world.entities.get_mut(&se.id) {
            *we = se.to_world();
        }
        // 如果 sim 期间 entity 被删了(state == Dead),这里跳过写回,
        // 顺便从 world 也删
    }
    // cleanup dead
    world.entities.retain(|_, e| e.state != EntityState::Dead);
}
```

### 2.3 为什么 unpack 到 Vec:cache 的真相

这是 sim region 设计的**真正动机**。详细解释:

CPU 缓存层级(x86_64):

| 层 | 大小 | 延迟(cycles) |
|---|---|---|
| 寄存器 | 几十字节 | 0 |
| L1 cache | 32 KB | 4 |
| L2 cache | 256 KB | 12 |
| L3 cache | 几 MB | 40 |
| 主内存(RAM) | GB | 200+ |

**关键事实**:每次访问内存,CPU 先查 L1,miss 查 L2,再 miss 查 L3,再 miss 查 RAM。每"下一层"慢 3-5×。

#### Vec<Entity> 的访问模式

```rust
for e in &sim.entities { ... }
```

Vec 在内存里是连续的。entity[0] 在地址 1000,entity[1] 在 1032,entity[2] 在 1064……

CPU 读 entity[0] 时:
- L1 cache line 是 64 字节
- 一次读 64 字节,正好覆盖 entity[0] + entity[1](假设 entity 32 字节)
- 下次读 entity[1] 时,**L1 命中**(0 cycles 额外延迟)

所以遍历 Vec<Entity>,**每 2 个 entity 才一次 RAM 访问**。剩余的 L1 命中。

#### HashMap<EntityId, Entity> 的访问模式

HashMap 内部是 bucket 数组,但**每个 bucket 的 Entity 是 Box(堆分配)**——因为 HashMap 要支持动态大小。

读 `world.entities.get(&id)` 时:
- hash(id) → bucket 索引(L1/L2,看 bucket array 大小)
- bucket 里的指针 → Entity 数据(堆地址,**几乎肯定 cache miss**)

每个 entity 都一次 cache miss。访问成本 = 200 cycles × N。

**对比**:
- Vec<Entity>:每 entity ~4 cycles(L1 命中)
- HashMap<Entity>:每 entity ~200 cycles(L1 miss)

差 50×。

#### 实测

Casey 在 Day 121(tiled marathon)展示过:遍历同样 10000 个 entity:
- Vec:0.5 ms
- HashMap:25 ms
差 50×。这就是 sim region 的核心动机——**让 hot loop 在连续内存上跑**。

### 2.4 SimRegion 的边界

```rust
struct SimRegion {
    center: Vec2,
    half_size: Vec2,  // 半边长(比如 300x300)
    entities: Vec<SimEntity>,
    // 双向映射(下一天 Day 064 详谈)
    world_to_sim: HashMap<EntityId, usize>,
}

impl SimRegion {
    fn contains(&self, pos: Vec2) -> bool {
        let d = pos.sub(self.center).abs();
        d.x < self.half_size.x && d.y < self.half_size.y
    }
}
```

`half_size` 的选择:
- **太小(比如 50x50)**:玩家很快走出 sim region,频繁 unpack/pack
- **太大(比如 5000x5000)**:sim region 内 entity 太多,失去优化意义
- **Casey 选 300x300**:玩家移动一段距离后 sim region 才扩展,平衡

如果 sim region 是相机视野的 2-3 倍,玩家移动时 sim region 不需要每帧重建——只是边界推一下,加几个新 entity 进来。

### 2.5 跨边界的 entity

entity 跨越 sim region 边界时,有一个微妙的 bug:

```
怪在 sim region 边缘,玩家在中心
怪每帧移动到 sim region 外 → 不再被 unpack
下一帧 sim 重新 unpack 时,怪又被 unpack 进来
但中间那一帧,怪没 update(速度 / AI 没算)
```

这是 sim region 的"边界抖动"问题。两种解法:

**解法 1**:sim region 比 update region 大
- update region = 200x200(只 update 这个范围的)
- sim region = 300x300(unpack 这个范围)
- 即使 entity 在 update region 边缘移出,它仍在 sim region 内,继续 update

**解法 2**:连续 unpack
- 每帧用上一帧的 sim region 作为基础
- 加上新进入 sim region 边界的 entity
- 不重新全 unpack

Casey 第 63 集用解法 1,简单稳定。

### 2.6 hot loop 在 sim region 上的具体应用

// 玩家 update
fn update_player(sim: &mut SimRegion, input: &Input, dt: f32) {

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

"只模拟附近"是大世界游戏的**通用模式**。术语:

- **Sim region**:今天讲的范围(单机游戏用)
- **Chunk**:Minecraft 的 16×16×16 体素块,玩家附近 chunk 才模拟 / 渲染 / 加载
- **Cell**:Bethesda 游戏(上古卷轴 / 辐射)的术语,世界分成 cell,玩家附近 cell active
- **Level streaming**:GTA / 赛博朋克用,根据玩家位置流式加载地图 chunk
- **LOD(level of detail)**:远处物体用低精度模型,近处用高精度

这些都是"按位置 / 距离划分模拟强度"的变体。

**Casey 的 sim region vs Minecraft chunk**:
- Casey:2D 矩形,按 entity 位置过滤
- Minecraft:3D 立方体,按 voxel 位置过滤

抽象层一致。

**多人游戏的 sim region**:每个玩家有自己的 sim region,服务器只 update 有玩家的 region。这就是 MMO 服务器架构(zone-based)。

### 3.2 · 🎨 图形学视角

渲染剔除(Day 058)和 sim region 是**互补**的:
- 渲染剔除:决定**画哪些 entity**(屏幕外的剔除)
- Sim region:决定**模拟哪些 entity**(相机外的冻结)

通常 sim region > 视锥(因为玩家可能突然转身,需要附近 entity 已经在 update)。所以:
- 在 sim region 内,但视锥外:更新但不画(怪在玩家背后巡逻)
- 在视锥内,但 sim region 外:不可能发生(视锥 ⊆ sim region)

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核**也用 sim region 类设计**:

- **Page cache**:文件内容按页(4KB)缓存。只缓存"最近访问的页",不缓存整个磁盘。访问文件 → 找 page cache → miss 则从磁盘读
- **swap space**:物理内存不够时,把不活跃的页换到磁盘。等价于"sim region 外的 entity 不在 RAM,需要时再 load"
- **working set**:操作系统理论术语,指"进程最近访问的内存集合"。OS 调度器保证 working set 在物理内存,sim region 外的可以 swap

**Casey 的 sim region 等价于进程的 working set**——只把"当前活跃的"放在快速存储(连续 Vec / L1 cache),其他放慢速存储(HashMap / L3 / RAM)。

更直接对应:**Linux SLAB allocator 的 partial slab 列表**。kernel 维护"最近用的 slab"在 partial list(快速访问),没用到的在 full / empty list。和 sim region 同构。

### 3.4 · 🦀 Rust 生态视角

Rust 实现 sim region 的几个考量:

#### 拷贝 vs 引用

```rust
// 方案 A:拷贝(Casey 选这个)
struct SimRegion {
    entities: Vec<SimEntity>,  // owned,从 world 拷贝过来
}

// 方案 B:索引(避免拷贝)
struct SimRegion {
    entity_indices: Vec<usize>,  // 指向 world.entities 的索引
}
```

**方案 A 优点**:
- 完全 owned,无借用冲突
- Vec 是连续内存(cache 友好)
- 可以 reorder(把 player 永远放 index 0)

**方案 A 缺点**:
- 每帧拷贝(几百个 entity,~16KB,~1 µs)
- 同步问题:sim 改了,world 没改,直到 pack

Casey 选 A,因为 cache 友好的收益远大于拷贝成本。Rust 的 ownership 模型让 A 容易实现(owned 数据无借用问题)。

#### 并发 sim region(Phase 4+)

```rust
struct World {
    sim_regions: Vec<SimRegion>,  // 多个 sim region 并行
}

// 用 rayon 并行 update
sim_regions.par_iter_mut().for_each(|sim| {
    simulate(sim, dt);
});
```

每个 sim region 一个 thread。Day 350+ Casey 进入多线程后用这种模式。

## 5 · 对照与变奏

### 同一思想在不同语境

| 语境 | "活跃集合" | 慢存储 |
|---|---|---|
| HH(Casey) | SimRegion(Vec) | World(HashMap) |
| CPU cache | L1 cache | RAM |
| OS | Physical memory | Swap space |
| 浏览器 | Active tab | Disk-cached tab |
| 数据库 | Buffer pool | Disk |
| 编辑器 | Open file | File system |
| 大脑 | Working memory | Long-term memory |

**普遍原则**:"活跃集合"快速访问,"非活跃"慢速存储,根据访问模式动态迁移。这是计算机科学最普遍的优化。

- **2000s**:开放世界(GTA / 上古卷轴)用 cell-based streaming
- **2010s**:Minecraft 用 chunk-based procedural world

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不直接在 World 的 HashMap 上跑模拟,而要 unpack 到 Vec?选择 unpack 的两个核心理由。

**参考解答**:
1. **Cache 友好**:HashMap 的 value 是堆分配的,遍历时每个 entity 都 cache miss(~200 cycles)。Vec 是连续内存,每 64 字节 cache line 覆盖 2 个 entity,L1 命中(~4 cycles)。差 50×。这是 hot loop 性能的根本。
2. **借用冲突**:Rust 的 borrow checker 不让你在 `for e in &world.entities` 里 mutable 操作 world(比如 spawn 新 entity)。unpack 到 owned Vec 后,sim 完全独立,可以自由 mutate,最后一次性 pack 回去。

次要理由:
3. **Reorder**:Vec 可以把 player 放在 index 0,方便快速访问
4. ** locality**:sim region 内的 entity 数稳定(几百),分支预测更稳定

### Lv2 · 动手实践

**题**:实现简化版 sim region。验证:
1. World 有 1000 个 entity 散布在 1000x1000 范围
2. Sim region 是 100x100,以 (500, 500) 为中心
3. unpack 后 sim.entities.len() 应该 ~10(1000 × (100² / 1000²) = 10)
4. 模拟 1 秒(60 帧),sim 内 entity 移动,pack 后 world 内对应 entity 也移动了

**完成标准**:模拟前后 sim.entities 和 world.entities 的对应 entity 位置一致。

**参考解答**:

```rust
use std::collections::HashMap;

type EntityId = u32;

#[derive(Clone, Copy, Debug, PartialEq)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn add(self, o: Self) -> Self { Self { x: self.x + o.x, y: self.y + o.y } }
    fn mul(self, k: f32) -> Self { Self { x: self.x * k, y: self.y * k } }
    fn sub(self, o: Self) -> Self { Self { x: self.x - o.x, y: self.y - o.y } }
}

#[derive(Clone, Debug)]
struct WorldEntity {
    id: EntityId,
    pos: Vec2,
    vel: Vec2,
}

#[derive(Clone, Debug)]
struct SimEntity {
    world_id: EntityId,
    pos: Vec2,
    vel: Vec2,
}

struct World {
    entities: HashMap<EntityId, WorldEntity>,
    next_id: EntityId,
}

impl World {
    fn new() -> Self { Self { entities: HashMap::new(), next_id: 1 } }
    fn spawn(&mut self, pos: Vec2, vel: Vec2) -> EntityId {
        let id = self.next_id;
        self.next_id += 1;
        self.entities.insert(id, WorldEntity { id, pos, vel });
        id
    }
}

struct SimRegion {
    center: Vec2,
    half: Vec2,
    entities: Vec<SimEntity>,
}

impl SimRegion {
    fn new(center: Vec2, half: Vec2) -> Self {
        Self { center, half, entities: vec![] }
    }
    fn contains(&self, pos: Vec2) -> bool {
        let d = pos.sub(self.center);
        d.x.abs() < self.half.x && d.y.abs() < self.half.y
    }
}

fn unpack(world: &World, sim: &mut SimRegion) {
    sim.entities.clear();
    for (id, e) in &world.entities {
        if sim.contains(e.pos) {
            sim.entities.push(SimEntity {
                world_id: *id,
                pos: e.pos,
                vel: e.vel,
            });
        }
    }
}

fn simulate(sim: &mut SimRegion, dt: f32) {
    for e in &mut sim.entities {
        e.pos = e.pos.add(e.vel.mul(dt));
    }
}

fn pack(world: &mut World, sim: &SimRegion) {
    for se in &sim.entities {
        if let Some(we) = world.entities.get_mut(&se.world_id) {
            we.pos = se.pos;
            we.vel = se.vel;
        }
    }
}

fn main() {
    let mut world = World::new();
    // 撒 1000 个 entity
    use std::cell::Cell;
    thread_local! { static SEED: Cell<u32> = Cell::new(12345); }
    fn rand() -> f32 {
        SEED.with(|s| {
            let mut x = s.get();
            x = x.wrapping_mul(1103515245).wrapping_add(12345);
            s.set(x);
            (x >> 8) as f32 / 0xFFFFFF as f32
        })
    }
    for _ in 0..1000 {
        let pos = Vec2::new(rand() * 1000.0, rand() * 1000.0);
        let vel = Vec2::new(rand() * 10.0 - 5.0, rand() * 10.0 - 5.0);
        world.spawn(pos, vel);
    }

    let mut sim = SimRegion::new(Vec2::new(500.0, 500.0), Vec2::new(50.0, 50.0));
    unpack(&world, &mut sim);
    println!("unpacked {} entities", sim.entities.len());
    assert!(sim.entities.len() > 0 && sim.entities.len() < 50, "expected ~10, got {}", sim.entities.len());

    // 记录 unpack 前位置
    let before: Vec<(EntityId, Vec2)> = sim.entities.iter().map(|e| (e.world_id, e.pos)).collect();

    // 模拟 1 秒
    let dt = 1.0 / 60.0;
    for _ in 0..60 {
        simulate(&mut sim, dt);
    }

    // pack 回去
    pack(&mut world, &sim);

    // 验证:world 内对应 entity 也移动了
    for (id, before_pos) in &before {
        let we = world.entities.get(id).unwrap();
        let moved = we.pos.sub(*before_pos).length();
        assert!(moved > 0.0, "entity {} should have moved", id);
    }
    println!("OK: all {} sim entities moved and packed back", before.len());
}
```

## 8 · Rust / Arch 落地代码

### 关键 Rust 特性

#### HashMap iteration

```rust
for (id, e) in &world.entities {
    // id 是 &EntityId,e 是 &WorldEntity
}
```

不可变借用,可以读但不能改。改用 `&mut world.entities` 然后 iter_mut。

#### 拷贝语义

```rust
let sim_e = SimEntity { world_id: e.id, pos: e.pos, vel: e.vel };
```

Vec2 是 `#[derive(Copy)]`,赋值时复制。SimEntity 包含 Vec2 + EntityId(也是 Copy),所以 `sim_e` 是 owned(栈分配),无堆引用。

#### Thread-local RNG(简化)

```rust
thread_local! { static SEED: Cell<u32> = Cell::new(12345); }
```

`thread_local!` 让每个线程有自己的 SEED。`Cell<u32>` 提供内部可变性(不需要 `&mut`)。

生产代码用 `rand` crate,这里简化。
