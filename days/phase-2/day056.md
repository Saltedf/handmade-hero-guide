# Day 056 · 从瓦片到实体:拆除一个特例

> 玩家撞墙的判定,在第 29 集里是 `tile.get(tx, ty) == Wall`。从今天起,墙不再是 tile,墙是 entity。一行代码的改动,却**把游戏从"瓦片世界"重定义成"实体世界"**——这是 Phase 2 架构的真正转折点。

## 0 · 为什么要有这一天

到目前为止(第 55 集),你的游戏世界是这样的:

- 一张二维数组 `tile_map[ty][tx]` 存"地形",值是 `Empty` / `Wall` / `Floor`
- 一组 `Entity`(玩家、怪物、金币)存"能动的东西",每个 entity 有 `pos: Vec2`
- 碰撞分两路:玩家 vs tile 用 Day 029 的分轴扫描;玩家 vs entity 用 Day 050 的 Minkowski AABB

听起来没问题。但你试一下加这些功能:

1. **会动的墙**(魔法墙):每隔 3 秒消失再出现。它该写在 tile map 里还是 entity 列表里?写在 tile 里就不能动;写在 entity 里就走 Minkowski——**两套碰撞逻辑都要会**。
2. **有 HP 的墙**(可破坏的箱子):它要被火球打掉,要扣血。tile map 不存 hp。
3. **开门触发**:踩压力板开一扇门。门也是空间阻挡,但状态会变。
4. **半高墙**(只能挡怪不能挡子弹):tile 的"是/否墙"二值表达不了这种语义。

这些问题共同指向一个结论:**"墙"和其他游戏对象没有本质区别,只是碰巧不会动的 entity**。把它当作 tile 是一个**过早的特例化**(premature special-casing)。

Casey 第 56 集做了一件大事:把墙从 tile map 搬进 entity 列表。从此 tile map **只画背景**(纯视觉,像一张贴图),所有"会挡路的东西"——包括静态的墙——都是 entity,统一走 Day 050 的 AABB 碰撞。

这不是小修小补,是一次**架构重构**。重构后:
- 碰撞代码只有**一套**(AABB),不再有"tile vs entity"的分叉
- 加新地形(可破坏箱、触发门、魔法墙)成本极低:加一种 EntityKind 即可
- tile map 退化成"一张纸",地位降级

但天下没有白吃的午餐。代价是:**墙的数量从几十(瓦片地图分辨率)暴涨到几千**(每块墙都是一个 entity)。N=5000 个 entity 两两碰撞检测 = 2500 万次/帧,机器扛不住。

Casey 第 56 集先做重构,把这条"性能账"留给第 57 集的空间网格解决。这就是工程节奏:**先统一抽象,再优化性能**。如果一上来就纠结"5000 个 entity 怎么办",你会一直留在"两套碰撞系统并存"的屎山里。

**心理锚点**:读完今天,你能回答三个问题——
- 为什么"墙"应该和"玩家"用同一套数据结构表达?
- 这种"取消特例"的重构,代价是什么?(增加的 entity 数量 / 失去的 tile 直觉)
- tile map 没消失,它退化成什么角色?(纯渲染层)

如果你卡在第二问,说明你还没真正接受"重构 = 用一种抽象换走另一种抽象"。每删一个特例,你都要在另一个维度付出代价。这不是"简化",是"重新分配复杂度"。

## 1 · Casey 今天做了什么

Casey 这一天坐在键盘前完成了一次安静的 refactor(refactor = 重构:不改行为,改结构)。具体动作:

1. 打开 `handmade.cpp`,找到 `tile_map` 结构(包含一个二维数组的 tile 类型),它**原本**承担两个职责:渲染(画地面 / 墙) + 碰撞(查询某格是不是 Wall)。
2. 在 `entity` 结构里新增一种 `Kind::Wall`,带 `AABB` 字段。墙从此是 entity。
3. 把世界生成函数从"按 tile 类型填 tile_map"改成"按 tile 类型 spawn entity"——遇到 `Wall` tile 就 `push_entity(Wall { pos, half_size })`。
4. 把所有"读 tile_map 判断 Wall"的代码(碰撞、AI 视线、渲染剔除)改成"扫描 entity 列表,过滤 Wall 类型,做 AABB 相交"。
5. tile_map 保留,但只剩**渲染**用途——画地板贴图。墙的贴图也搬到 entity 上(像画怪一样画墙)。
6. 编译,运行,**功能不变**。这是 refactor 的验收标准。

Casey 在视频里反复强调:"这不是优化,是清理(cleanup)。性能上其实**变差了**(N 变大),但代码更对(cohesive)。"——他下集就要把性能账讨回来。

## 2 · 心智模型

### 2.1 类比:从"两个仓库"到"一个大仓库"

想象你管理一个物流仓库,货物分两类:
- **货架商品**(tile):静物,整齐码在固定格子,有(行,列)地址
- **快递包裹**(entity):在传送带上跑的,有 (x,y) 坐标

你原本有两套系统管这两类:货架管理系统管"哪个格是空的",包裹跟踪系统管"哪个包裹在哪"。每个包裹要"判断有没有撞到货架"时,你**先查货架管理系统的格子**,简单粗暴 O(1)。

这套系统一直跑得好好的,直到有一天来了**魔法货架**(会消失)和**带电货架**(碰到会爆)。它们的属性(状态、HP、计时器)放进 tile map 里很难看;你又不想为它们单开一套系统。

于是你做了一个决定:**所有东西都打包成"包裹"**。货架也是包裹,只是"位置永远不变"。这样:
- 只需要一套系统(包裹跟踪)
- 任何"特殊货架"都是改个包裹的属性,不需要新系统
- 但现在判断"包裹 A 是否撞到包裹 B"是 O(N²)(N 个包裹两两测试),不像以前 O(N)(每个包裹查一次格子)

这就是 Day 056 的本质:用**一套抽象**(entity)取代**两套抽象**(tile + entity),代价是从 O(N) 退化到 O(N²)。Casey 接受这个退化——因为下一集会用空间网格把复杂度降回来,而届时**所有 entity 一视同仁**地受益,不再有"墙特殊处理"。

### 2.2 严谨:重构前后的代码结构对比

**Day 055 之前**——两套并存:

```rust
// 瓦片地图(第 29 集实现)
struct TileMap {
    tiles: Vec<Vec<TileKind>>,  // tiles[ty][tx]
    tile_size: f32,
}

impl TileMap {
    fn is_wall(&self, pos: Vec2) -> bool {
        let tx = (pos.x / self.tile_size) as usize;
        let ty = (pos.y / self.tile_size) as usize;
        self.tiles[ty][tx] == TileKind::Wall
    }
}

// 实体列表(第 51 集实现)
struct World {
    entities: Vec<Entity>,
}

fn update_player(player: &mut Entity, world: &World, dt: f32) {
    // 移动
    player.pos = player.pos.add(player.vel.mul(dt));

    // 碰撞分两路:
    // 1) 玩家 vs tile(分轴扫描,Day 029)
    resolve_tile_collision(player, &world.tile_map);

    // 2) 玩家 vs entity(Minkowski,Day 050)
    for e in &world.entities {
        if let Some(c) = minkowski_collide(player, e) {
            resolve_entity_collision(player, e, c);
        }
    }
}
```

**问题**:这段代码藏着两个隐式假设——
- 假设 1:墙都是 tile(所以走 `resolve_tile_collision`)。一旦有"非 tile 的墙"(魔法墙),你必须在第二步再加一段。
- 假设 2:tile 不参与 entity-entity 的碰撞响应。但其实"墙挡住玩家"和"怪挡住玩家"在物理上**是同一件事**(都是 AABB 阻挡),只是代码上分了两套算法。

**Day 056 之后**——一套吃下:

```rust
// tile map 退化成纯背景渲染数据
struct BackgroundTiles {
    floor_sprites: Vec<Vec<SpriteId>>,  // 只画地板
    tile_size: f32,
}

// 实体列表承担一切
struct World {
    entities: Vec<Entity>,
}

#[derive(Clone, Copy, PartialEq)]
enum EntityKind {
    Player,
    Monster,
    Wall,       // 新增!墙现在是 entity
    Projectile,
    Destructible,
}

fn update_player(player_idx: usize, world: &mut World, dt: f32) {
    let player_pos = world.entities[player_idx].pos;
    world.entities[player_idx].pos = player_pos.add(world.entities[player_idx].vel.mul(dt));

    // 一套碰撞:扫所有 entity,做 Minkowski
    let mut new_pos = world.entities[player_idx].pos;
    for (i, e) in world.entities.iter().enumerate() {
        if i == player_idx { continue; }
        if let Some(mtv) = minkowski_collide(new_pos, half_size_player, e.pos, e.half_size) {
            // mtv = minimum translation vector,把玩家推出墙的最短向量
            new_pos = new_pos.add(mtv);
        }
    }
    world.entities[player_idx].pos = new_pos;
}
```

**重点对比**:
- 旧代码:`resolve_tile_collision` + `resolve_entity_collision` 两套
- 新代码:只有 `minkowski_collide` 一套,墙、怪、玩家**用同一个函数**算

### 2.3 EntityKind 枚举:Rust 的代数数据类型在游戏里开花

`enum EntityKind` 是 Rust 的**代数数据类型**(algebraic data type)。它在游戏开发里有个特殊用法:**类型 tag**。

Casey 的 C 代码用一个 int 字段 `entity_kind` 标识类型,然后用 switch 分发。Rust 的 enum 让这件事更安全——编译器在 `match` 时强制你覆盖所有 variant,漏一个就编译失败。

```rust
match e.kind {
    EntityKind::Player => update_player(e, dt),
    EntityKind::Monster => update_monster(e, dt),
    EntityKind::Wall => { /* 静止,不 update */ }
    EntityKind::Projectile => update_projectile(e, dt),
    EntityKind::Destructible => update_destructible(e, dt),
}
// 如果你新加 EntityKind::Fire 但忘了写 _ => ... 或 Fire arm,编译器报错
```

这是 Rust 相对 C 的一个**工程优势**——重构时编译器帮你找漏掉的分支。Casey 在 C 里靠手工 grep。

### 2.4 重构的成本账

| 维度 | 重构前(Day 055) | 重构后(Day 056) | 谁赢 |
|---|---|---|---|
| 碰撞代码路径数 | 2(tile + entity) | 1(entity) | 重构后 |
| 加新"墙类型"成本 | 改 tile enum + 改碰撞分支 + 改渲染 | 加一个 EntityKind 变体 | 重构后 |
| 内存占用 | tile_map 是 N×M 字节;entity 几十 KB | tile_map 退化;entity 几 MB(几千个 Wall) | 重构前 |
| 碰撞复杂度(朴素) | O(N)(N=entity 数,~30) | O(N²)(N=entity 数,~5000) | 重构前 |
| 渲染剔除 | tile 直查(只画可见 tile) | 扫所有 entity,过滤可见 | 重构前 |
| 概念清晰度 | tile 和 entity 是两个东西,要解释为什么 | 只有一个概念(entity),无歧义 | 重构后 |

**核心权衡**:重构用**内存 + 性能**换**概念清晰 + 扩展性**。在 N=5000 时,性能差距 O(N) vs O(N²) 是 30 vs 25,000,000——必须救。下一集空间网格救活它。

### 2.5 为什么"概念清晰"值得用性能换

初学者会想:用 1/1000 的性能换"代码漂亮",值得吗?

答案分两层:

**第一层:工程师心智带宽**。每多一套抽象(比如"tile 和 entity"),你脑子里就多一个上下文。N 套抽象并存的代码库,工程师改一行要先想"这行属于哪套抽象",认知负担指数增长。Handmade Hero 这 667 集能做下去,关键就是 Casey 反复**砍抽象**——少而锋利,胜过多而臃肿。

**第二层:架构演化成本**。你后面想加"会动的墙""有 HP 的墙""触发式墙",每加一种都要决定"塞 tile 还是塞 entity"。这种决策反复消耗时间。统一后,**新需求一律 spawn entity**,决策成本为 0。

性能问题永远是"具体场景具体分析"(下一集就解决),但**架构债是复利**——越拖越难还。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

"从 tile 到 entity"是游戏行业普遍演化路径,不是 Casey 独创:

- **早期(1980s Pac-Man / Super Mario)**:纯 tile based,墙是 tile,角色用 tile 坐标移动。原因:硬件太弱,只跑得起 tile。
- **中期(1990s Quake / Doom)**:混合——BSP 树管静态墙(还是 tile 思路),entity 管怪物。BSP 是空间划分(类似下一集的空间网格),静态地形走 BSP,动态走 entity。
- **现代(Unity / Unreal)**:几乎全 entity。Unity 的 GameObject + Transform 模型里,**所有东西**包括地形、灯光、相机都是 GameObject。地形只是带 MeshRenderer 的 GameObject。Unreal 的 Actor 模型同样。
- **ECS 阵营(bevy / Unity DOTS)**:更激进,GameObject 都不存,只有"组件组合"(entity = 一组 component 的 ID)。墙就是有 `Position + Aabb + Sprite` 组件的 entity。

Casey 的 HH 走"中等激进"——entity 是核心抽象(像 Unity),但**不用组件**(不像 ECS),用 enum + variant 字段。这是 Casey 的取舍:enum 的好处是**所有 entity 共享布局**(cache friendly),坏处是加字段时所有 entity 都变胖(下一集会看到这个权衡)。

**对照点**:如果你以后用 Unity 做游戏,会发现 Unity 的"Tilemap"组件本质上也是"在底层生成一组带 Sprite 的 GameObject"——和你今天做的事一样,只是 Unity 把细节藏起来了。读完今天,你理解了 Unity 的实现思路。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核里有**完全一样**的"取消特例"演化,可以作类比加深理解:

**Linux 进程模型演化**:
- 早期 Unix:进程是"程序运行的实例",线程是"轻量进程"(special case)
- Linux 2.6 后(NPTL):**进程和线程统一为 task**——内核里只有 `struct task_struct`,线程就是"共享地址空间的 task"。`clone()` 系统调用通过 flags 决定共享什么(地址空间 / 文件描述符 / 信号处理……)。

这就是"取消特例"——以前线程和进程是两个东西,现在都是 task,通过参数化(共享什么)区分。和 Casey 今天把 tile 和 entity 统一为 entity,逻辑完全一致。

**Linux 文件模型**:
- "Everything is a file"——普通文件 / 设备 / socket / pipe 都用 `read/write/close` 接口
- 这是 1970s Unix 天才设计,核心就是"取消特例"——以前每种设备有专用 syscall,现在统一

**启示**:Linux 这种"一个抽象打天下"的哲学,和 Casey 的"一个 entity 抽象打天下"是同一种工程美学。**好的工程师倾向于减少抽象数量,哪怕单个抽象变复杂**。这是 Day 056 教给你的更深一课。

### 3.3 · 🦀 Rust 生态视角

Rust 表达"统一类型 + 多 variant"有几种方式,各有取舍:

#### 方案 A:enum + 共享字段(Casey 式)

```rust
struct Entity {
    pos: Vec2,
    half_size: Vec2,
    vel: Vec2,
    kind: EntityKind,
    // 每种 kind 用到的字段都堆在这里
    hp: Option<i32>,
    damage: Option<i32>,
    lifetime: Option<f32>,
    owner: Option<EntityId>,
    sprite: SpriteId,
}

enum EntityKind {
    Player, Monster, Wall, Projectile, Destructible, Familiar,
}
```

**优点**:所有 entity 同布局,Vec<Entity> 是 cache-friendly。
**缺点**:Player 不需要 `lifetime`,Wall 不需要 `vel`,但字段都占内存。

#### 方案 B:enum + 独立字段(Rust idiomatic)

```rust
enum Entity {
    Player { pos: Vec2, half: Vec2, vel: Vec2, hp: i32, facing: Dir },
    Monster { pos: Vec2, half: Vec2, vel: Vec2, hp: i32, ai_state: AiState },
    Wall { pos: Vec2, half: Vec2, sprite: SpriteId },
    Projectile { pos: Vec2, half: Vec2, vel: Vec2, dmg: i32, life: f32, owner: EntityId },
}
```

**优点**:每种 entity 只占自己需要的字段(Wall 不存 vel / hp,省内存)。
**缺点**:variant 大小不同,enum 取最大 variant 的大小——所以 Wall 实际占内存 = Projectile 的内存。**这是 Rust enum 的"隐形成本"**。

#### 方案 C:Box<dyn Trait>(OOP)

```rust
trait Entity {
    fn pos(&self) -> Vec2;
    fn update(&mut self, world: &World, dt: f32);
}

struct Player { pos: Vec2, hp: i32 }
impl Entity for Player { /* ... */ }

let entities: Vec<Box<dyn Entity>> = vec![Box::new(Player { ... })];
```

**优点**:每种类型独立大小,vtable 分发。
**缺点**:堆分配 + vtable 跳转 + cache 不友好(每个 Box 在堆上散落)。游戏 hot loop 不推荐。

#### Casey 选 A,Rust 圈选 B

Casey 用 C,所以用 A 风格(struct + tag)。Rust 项目通常用 B(enum 变体带数据),因为 Rust 编译器在 B 上能做更好的 pattern matching 分析。

**实际建议**(Phase 2 阶段):用 B,理解 enum 的内存代价。等 Phase 4 性能优化时,再考虑 A(Casey 式 flat struct)或 SoA。

### 3.4 · 内存布局补充

无论选 A 还是 B,你都需要理解**enum 的内存布局**。Rust enum 是 tag + union:

```
方案 B 的 Entity 内存(假设 Vec2 是 8 字节,i32 是 4 字节):

  tag(1 字节,标识哪个 variant) + padding(7 字节) + 最大 variant 数据

Variant Projectile(最大):
  pos: Vec2 (8) + half: Vec2 (8) + vel: Vec2 (8) + dmg: i32 (4) + life: f32 (4) + owner: EntityId (8) = 40 字节

所以 enum Entity 总大小 = 8(tag+padding) + 40 = 48 字节
Wall variant 实际只用 pos(8) + half(8) + sprite(4) = 20 字节,但占 48 字节(浪费 28)
```

这就是为什么 Casey 在 C 里用方案 A——**所有 entity 同布局**,Wall 字段空着也没事,因为外部代码不访问它们,compiler 可以把它们放在同一段连续内存。

Rust 想达到同样效果,可以用 `#[repr(C)]` + union:

```rust
#[repr(C)]
struct Entity {
    kind: EntityKind,           // tag
    data: EntityData,           // union of all variants
}

#[repr(C)]
union EntityData {
    player: PlayerData,
    wall: WallData,
    // ...
}
```

这是 unsafe 的(union 访问要 unsafe),但布局和 C 一致。Phase 4 性能优化时再考虑。

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:如何表达"会挡路的静态物体"?

| 语境 | 方案 | 优点 | 缺点 |
|---|---|---|---|
| 2D 像素游戏(早期) | tile_map 二维数组 | O(1) 查询 | 不能动 / 不能有状态 |
| 2D 像素游戏(现代) | Entity with kind=Wall | 统一抽象 | N² 碰撞,需空间划分 |
| 3D 游戏(Quake 式) | BSP tree(静态)+ entity(动态) | 大场景剔除快 | BSP 预计算复杂 |
| 3D 游戏(Unity 式) | MeshCollider + GameObject | 编辑器友好 | 性能不如 BSP |
| 物理引擎(Box2D) | Body with fixture + collision filter | 通用 | 太重,游戏用不上全部 |

### 历史演化

- **1970s**:游戏用 tile grid(Pac-Man),因为硬件只跑得起这个
- **1990s**:3D 兴起,BSP / portal culling 出现,静态 / 动态分两套
- **2000s**:Unity 出现,统一为 GameObject + Component(早期 ECS 雏形)
- **2010s**:Unity / Unreal 引入 ECS 子系统(DOTS / Mass),推向数据驱动
- **2020s**:Bevy 等纯 ECS 引擎成熟

Casey 的 HH 走在"现代但不过度激进"的位置——entity + enum,不上 ECS。这是 667 集能讲完的关键——再激进就需要更多集数解释 ECS 的边边角角。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:重构后 tile_map 还存在,它的职责发生了什么变化?为什么没有完全删除?

**参考解答**:重构后 tile_map 从"地形数据 + 碰撞数据 + 渲染数据"三合一,退化成**只有渲染数据**(画地板贴图)。
- 碰撞数据搬到了 entity(墙是 Wall entity)
- 渲染数据保留在 tile_map,因为地板这种"铺满整片"的视觉元素,用 tile 坐标 + 贴图 ID 比每个地板都 spawn 一个 entity 更紧凑(几千个 FloorEntity vs 一个二维数组)
- 完全删除 tile_map 的代价:渲染地板时要遍历所有 FloorEntity,内存浪费
- 所以 Casey 留它做"纯背景图层"

这条思路:**重构不是"删掉一切特例",而是"把特例限制在不影响主路径的角落"**。地板不影响碰撞 / AI / 物理,所以它可以继续做特例(留在 tile_map)。

### Lv2 · 动手实践

**题**:在 Rust 项目里完成 tile → entity 的迁移。具体:
1. 现有代码里有一个 `World { tile_map: TileMap, entities: Vec<Entity> }`,你把它改成 `World { background: BackgroundTiles, entities: Vec<Entity> }`
2. 世界生成时,遇到 `TileKind::Wall` 不再写 tile_map,而是 `entities.push(Entity::wall(pos))`
3. 碰撞代码统一改成扫 entity 列表过滤 `kind == Wall`,做 Minkowski
4. 运行后,玩家撞墙仍然停住(行为不变),tile_map 的 is_wall 函数再也没人调用

**完成标准**:`cargo run` 玩家撞墙正确停住,`grep -r "is_wall" src/` 没有调用方(只剩定义)。

**参考解答**:

```rust
// src/world.rs

#[derive(Clone, Copy, PartialEq, Debug)]
enum EntityKind {
    Player, Monster, Wall, Projectile, Familiar,
}

struct Entity {
    pos: Vec2,
    half: Vec2,           // AABB 半宽半高
    vel: Vec2,
    kind: EntityKind,
    // 通用字段,各种 kind 都可能用
    hp: Option<i32>,
    sprite: Option<SpriteId>,
}

impl Entity {
    fn wall(pos: Vec2, half_size: Vec2) -> Self {
        Self {
            pos, half: half_size,
            vel: Vec2::new(0.0, 0.0),
            kind: EntityKind::Wall,
            hp: None,
            sprite: Some(SpriteId::Wall),
        }
    }
}

struct World {
    background: BackgroundTiles,  // 退化后的 tile map,只画地板
    entities: Vec<Entity>,
}

fn spawn_world(world: &mut World) {
    // 假设原本 tile_map[y][x] 是 TileKind,我们遍历它生成 entity
    for ty in 0..world.background.height() {
        for tx in 0..world.background.width() {
            let pos = world.background.tile_center(tx, ty);
            match world.background.tile_at(tx, ty) {
                TileKind::Wall => {
                    world.entities.push(Entity::wall(pos, Vec2::new(16.0, 16.0)));
                    // 注意:wall 的 tile 数据可以保留在 background 里,
                    // 也可以从这里删除——只要渲染逻辑不依赖它。
                }
                TileKind::Floor => { /* 渲染用,不 spawn entity */ }
                TileKind::Empty => {}
            }
        }
    }
}

// 统一的碰撞函数:玩家 vs 任何 entity(墙、怪、其他玩家)
fn resolve_player_collision(world: &mut World, player_idx: usize) {
    let mut new_pos = world.entities[player_idx].pos;
    let player_half = world.entities[player_idx].half;

    // 扫所有 entity
    for (i, e) in world.entities.iter().enumerate() {
        if i == player_idx { continue; }
        // Minkowski AABB(Day 050):玩家中心是否在 (玩家半+entity半) 矩形内
        let dx = new_pos.x - e.pos.x;
        let dy = new_pos.y - e.pos.y;
        let overlap_x = (player_half.x + e.half.x) - dx.abs();
        let overlap_y = (player_half.y + e.half.y) - dy.abs();
        if overlap_x > 0.0 && overlap_y > 0.0 {
            // 撞了!推出去(MTV = 最小推回向量)
            if overlap_x < overlap_y {
                new_pos.x += dx.signum() * overlap_x;
            } else {
                new_pos.y += dy.signum() * overlap_y;
            }
        }
    }
    world.entities[player_idx].pos = new_pos;
}
```

**每行解释**:
- `Entity::wall` 工厂方法:让 spawn 代码可读(`Entity::wall(pos, half)` 比 `Entity { kind: Wall, pos, half, ... }` 简洁)
- `Option<i32>` / `Option<SpriteId>`:Rust 的 nullable 字段。Wall 的 hp 是 None,怪的是 Some(100)。
- Minkowski 公式:`overlap_x > 0 && overlap_y > 0` ⟺ 玩家中心在 (玩家半+entity半) 的矩形内 ⟺ 相交
- MTV(minimum translation vector):选 overlap 小的那条轴推回,玩家不会卡进墙
- `dx.signum()` 返回 -1.0 / 0.0 / 1.0,把玩家往"远离 entity 中心"的方向推

**坑**:
- 不要在 `for (i, e) in world.entities.iter()` 里 `world.entities[i].pos = ...`,会借用冲突。先收集到 `new_pos`,循环完再写回。
- `Entity` 必须实现 `Clone` 或者用索引隔离读写,否则 borrow checker 不让你"读 e 的同时写 player"。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

下面是一个最小化的"tile → entity 迁移"演示,你可以直接 cargo run 跑通:

```rust
// src/main.rs

#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn add(self, o: Self) -> Self { Self { x: self.x + o.x, y: self.y + o.y } }
    fn sub(self, o: Self) -> Self { Self { x: self.x - o.x, y: self.y - o.y } }
    fn mul(self, k: f32) -> Self { Self { x: self.x * k, y: self.y * k } }
}

#[derive(Clone, Copy, PartialEq, Debug)]
enum EntityKind { Player, Monster, Wall }

#[derive(Clone, Copy)]
struct Entity {
    pos: Vec2,
    half: Vec2,
    vel: Vec2,
    kind: EntityKind,
}

impl Entity {
    fn wall(pos: Vec2, half: Vec2) -> Self {
        Self { pos, half, vel: Vec2::new(0.0, 0.0), kind: EntityKind::Wall }
    }
    fn player(pos: Vec2) -> Self {
        Self { pos, half: Vec2::new(8.0, 8.0), vel: Vec2::new(0.0, 0.0), kind: EntityKind::Player }
    }
}

struct World {
    entities: Vec<Entity>,
}

impl World {
    fn new() -> Self {
        let mut entities = vec![];
        // 玩家在 (50, 50)
        entities.push(Entity::player(Vec2::new(50.0, 50.0)));
        // 围一圈墙
        for i in 0..10 {
            let x = i as f32 * 16.0;
            entities.push(Entity::wall(Vec2::new(x, 0.0), Vec2::new(8.0, 8.0)));
            entities.push(Entity::wall(Vec2::new(x, 160.0), Vec2::new(8.0, 8.0)));
        }
        Self { entities }
    }

    fn player_idx(&self) -> usize { 0 } // 约定:entity[0] 是玩家

    fn move_player(&mut self, dx: f32, dy: f32) {
        let i = self.player_idx();
        self.entities[i].pos = self.entities[i].pos.add(Vec2::new(dx, dy));
        self.resolve_player_collision();
    }

    fn resolve_player_collision(&mut self) {
        let i = self.player_idx();
        // 先读出玩家位置和半宽,避免借用冲突
        let player_pos = self.entities[i].pos;
        let player_half = self.entities[i].half;
        let mut new_pos = player_pos;

        for (j, e) in self.entities.iter().enumerate() {
            if j == i { continue; }
            if e.kind != EntityKind::Wall { continue; } // 只和墙碰撞
            // Minkowski AABB
            let dx = new_pos.x - e.pos.x;
            let dy = new_pos.y - e.pos.y;
            let ox = (player_half.x + e.half.x) - dx.abs();
            let oy = (player_half.y + e.half.y) - dy.abs();
            if ox > 0.0 && oy > 0.0 {
                if ox < oy {
                    new_pos.x += dx.signum() * ox;
                } else {
                    new_pos.y += dy.signum() * oy;
                }
            }
        }
        self.entities[i].pos = new_pos;
    }
}

fn main() {
    let mut world = World::new();
    println!("start: {:?}", world.entities[0].pos);
    // 试图穿过下面的墙
    for _ in 0..20 {
        world.move_player(0.0, -5.0);
    }
    println!("after move down: {:?}", world.entities[0].pos);
    // 玩家应该被墙挡在 y=8+8=16(墙中心 y=0,墙半高=8,玩家半高=8)
    // 越靠近墙被挡,实际位置应该在 y≈16 附近
    assert!(world.entities[0].pos.y >= 16.0, "player should be blocked by wall");
    println!("OK: wall blocks player");
}
```

**`cargo run` 预期输出**:

```
start: Vec2 { x: 50.0, y: 50.0 }
after move down: Vec2 { x: 50.0, y: 16.0 }
OK: wall blocks player
```

**关键 Rust 特性**:
- `Entity::wall` / `Entity::player` 工厂方法——把构造逻辑封装,而不是每次写完整 struct literal
- `for (j, e) in self.entities.iter().enumerate()` —— 借用 entities 不可变地读,然后循环完再写 `self.entities[i].pos`。这是 Rust 借用规则的典型 workaround
- `e.kind != EntityKind::Wall { continue }` —— 过滤掉非墙 entity。生产代码里会用下一集的空间网格加速
- `dx.signum()` —— signum 返回 -1/0/+1 的 f32。Rust 的 `f32::signum` 处理 NaN 安全(返回 NaN)
