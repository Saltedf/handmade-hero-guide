
# Day 068 · 精确强制最大移动距离

> 一个高速 entity(玩家冲刺、火球、子弹)在 60 FPS 下每帧能走 64 像素——一个 tile 32 像素。也就是说,**它一帧能直接穿过一面墙**。Day 045 的 temporal search 能查路径,但它假设"每帧移动量小到不会跳过 entity"。今天 Casey 给世界加一条硬规则:**任何 entity 单帧移动距离不超过 max_move_distance**,从源头杜绝穿墙。这听起来简单,实际涉及"在任意多边形路径上裁剪到 max 距离"的几何问题。

## 0 · 为什么要有这一天

回到 Day 045。Casey 当时给了一套"几何搜索 vs 时间搜索"的对照:

- 几何搜索:沿 entity 移动方向射线和场景求交,找到最近碰撞点。问题:它假定你"沿直线匀速走完整个 dt"。
- 时间搜索:在 [0, dt] 区间二分搜索,找到第一个发生碰撞的时间 t* < dt,entity 走到 t* 的位置停下。

两个方法都有一个**隐含前提**:整帧的移动距离 `|v * dt|` 在合理范围内(比如不超过一个 tile)。当这个前提被打破,问题就出来了。

**典型翻车场景**:你给玩家加了 Shift 冲刺,速度从 200 px/s 变成 2000 px/s。一帧(1/60 秒)走 ~33 px——刚好一个 tile 宽度。你写了 Minkowski 碰撞,玩家开始冲刺,然后**直接穿墙出现在墙后面**。你看代码,Minkowski 公式是对的、temporal search 也调用了,为什么还穿墙?

答案:**你查碰撞用的是"起始位置 + 速度×dt"作为终点位置**,这条线段虽然穿过了墙,但你只检查了"终点是否在墙内"。终点刚好越过墙到墙外,碰撞检测返回 false,entity 就这么穿过去了。

Casey 给的解法分两层:

1. **物理层 clamp**:在 update 一开始就强制限制 `vel` 的模长,保证 `|vel * dt| ≤ max_move_distance`。这是 cheap 的"粗筛",把"极端情况"压到"合理范围"。
2. **几何层 sub-step**:即便 clamp 了,如果 entity 真的想走很远(冲刺、传送门),把这一帧拆成多个子步,每步距离 ≤ max,每步单独做碰撞检测。这是更贵的"精筛"。

今天我们重点讲第一层(clamp),因为第二层 Casey 在 Day 121 才正式做。但你要知道:clamp 是"工程妥协",sub-stepping 是"工业级正确"。Casey 选 clamp,因为 60 FPS 下 clamp 后的剩余穿墙概率极低,不值得立刻上 sub-stepping。

**心理锚点**:看完这集,你应该能解释:

- 为什么高速 entity 会穿墙(几何上的本质)
- clamp 速度和二分搜索碰撞的关系(互补,不是替代)
- 怎么选 `max_move_distance`(和 tile size、entity 半径相关)
- 如果你的游戏里有超高速物体(光线、激光),你应该跳过 clamp 直接走 raycast,而不是 clamp

这是 Day 045 几何/时间搜索那集的"补丁",也是 Day 121 sub-stepping 的伏笔。

## 1 · Casey 今天做了什么

Day 068 在 HH 视频里是一段"清账"——Casey 把 Day 065 没解决的高速 entity 穿墙问题收尾。

1. 他先复现了 bug:把玩家速度调到 5000 px/s,然后冲向一面墙,**人穿墙而过**。然后他对着这个画面说:"这不是碰撞算法的问题,是 update 步长的问题。"

## 2 · 心智模型

### 类比:刹车,不是传送

想象你在高速上开车,前面 50 米是红灯。你有两种停车方式:

1. **刹车**:让车速从 120 km/h 慢慢降到 0,你在 50 米内匀减速停下。物理上正确,引擎没受罪。
2. **传送**:在红灯前一瞬间把车"瞬移"到停止线。物理上荒谬,但游戏里你完全可以这么做——直接把 `pos.x = stop_line`。

Casey 选的是"刹车"的近亲:**限速**。他不在终点强制停车,他在路上限速——你最大速度被强制限制到某个值,这样无论你怎么冲刺,一帧内最多走 max_move_distance。

这个限速的本质:**让物理积分的步长保持在碰撞算法能处理的范围内**。

### 严谨原理:为什么 entity 会穿墙?

我们 Day 050 写的 Minkowski 碰撞,核心逻辑是:

```
两个 AABB A 和 B 相交  ⟺  |A.center - B.center| 在 x 和 y 上都小于 (A.half + B.half)
```

这是**离散时刻**的判定——它只回答"此刻两者是否重叠"。它不回答"过去这一段时间内两者是否曾经重叠"。

游戏循环里我们这样用:

```
update(dt):
    e.pos += e.vel * dt      # 1. 先移动
    for other in entities:   # 2. 再检测
        if overlap(e, other):
            resolve_collision(e, other)
```

如果 `e.vel * dt` 很大,移动那一步可能让 e **从墙的左侧直接跳到墙的右侧**,中间没经过墙的位置——所以 step 2 的"此刻是否重叠"返回 false。这是离散碰撞检测的根本缺陷:**采样不足**。

**连续碰撞检测**(Continuous Collision Detection, CCD)就是解决这个的:它问"从 t=0 到 t=dt,entity 是否在任何时刻和墙重叠"。CCD 的标准做法有三种:

| 方法 | 思路 | 成本 |
|---|---|---|
| Sub-stepping | 把 dt 拆成 N 个小步,每步做离散检测 | N 倍检测成本 |
| Ray cast | 把 entity 当成一个点,从起点射线到终点,和所有 AABB 求交 | O(墙数 × entity数) |
| Sweep test | 计算 entity AABB 在路径上扫过的形状(Minkowski 和),和墙求交 | 几何复杂 |

Casey 现在用的 clamp 是"sub-stepping 的退化版"——保证 N=1 也够。N=1 等价于"离散检测",只要每步距离足够小,离散检测的误差就足够小。

### 公式:速度 clamp

设当前速度向量 v = (vx, vy),dt 是这一帧时间。entity 这帧的位移 = |v| * dt。

我们要求 `|v| * dt ≤ D_max`(D_max 是 max_move_distance)。

如果违反:

```
|v| * dt > D_max
=> |v| > D_max / dt
=> 缩放因子 s = (D_max / dt) / |v| = D_max / (|v| * dt)
=> v_new = v * s
```

注意 `|v_new| * dt = |v| * s * dt = D_max`——刚好等于上限。

```rust
fn clamp_velocity(v: &mut Vec2, dt: f32, d_max: f32) {
    let dist = v.length() * dt;
    if dist > d_max {
        let s = d_max / dist;
        v.x *= s;
        v.y *= s;
    }
}
```

### 关键区分:clamp vel vs clamp pos

新手常见错误:看到 entity 穿墙了,觉得"那我直接把 pos clamp 到墙边不就好了?"这是错的,原因有三:

1. **加速度丢失**:你改了 pos 但没改 vel,下一帧 vel 还是大的,entity 会在墙边抖动(每帧 clamp pos,每帧 vel 又把它推过去)。
2. **物理不一致**:游戏里物理是 `pos += vel * dt`,你直接改 pos 等于"破坏了物理方程",撞击反弹、摩擦、惯性全失真。
3. **碰撞响应失败**:Minkowski 碰撞的 resolve_collision 函数需要正确的 vel 来算反弹方向。你 vel 没动,resolve 算出来的反弹是错的。

正确的做法:clamp vel 后让物理方程自己跑。物理方程 `pos += vel * dt` 保证 pos 和 vel 一致。

### 选 D_max 的依据

`D_max` 不是随便选的。Casey 选 `TILE_SIZE * 0.5`,背后的逻辑:

1. **entity 的 AABB 半宽 = TILE_SIZE / 4 = 8 px**(总宽 16 px = 半个 tile)。墙的最小宽度 = 1 tile = 32 px。
2. 如果 entity 单帧移动 ≤ 8 px,AABB 完整的"穿过墙"几乎不可能——entity 至少有一帧和墙重叠。
3. Casey 用 `D_max = TILE_SIZE * 0.5 = 16 px`,比 8 略大,给速度一点弹性。

更严谨的算法:`D_max = min(entity_half_width, wall_min_width) - epsilon`。这保证"entity 不会一帧从墙外跳到墙外而不和墙重叠"。

### 什么时候 clamp 不够?

**激光武器**:激光速度 = 光速(在游戏里 = 一帧从一头到另一头)。clamp 会把它降速到 16 px/帧,这就毁了激光的本意。激光走 raycast 路径:起点 → 射线 → 第一个相交的墙/entity → 那里就是激光的终点。

**传送门**:传送门让玩家瞬移。瞬移不是 clamp 能管的,瞬移后要专门做"瞬移后位置合法性检查"(不能瞬移到墙里)。

**极速物体(光速粒子)**:粒子模拟里常有这种东西,clamp 会改变物理结果。需要 sub-stepping 或显式 CCD。

Casey 后面 Day 121+ 做 sub-stepping 时会回头讲这些场景。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏业界管 clamp 这件事叫 **"tunneling prevention"**(防穿墙)。tunneling 是离散物理引擎(像 Box2D 在默认配置下)的经典 bug,几乎每个游戏引擎都有一套对应的"防穿墙"机制。

业界做法对比:

| 引擎 / 库 | 做法 |
|---|---|
| Casey HH | vel clamp + (Day 121+) sub-stepping |
| Box2D (默认) | sub-stepping(叫做 CCD 选项) |
| Bullet Physics | sweep test + GJK |
| PhysX | CCD on/off 开关 + speculative contacts |
| Unity (DOTS Physics) | 子步:fixed update 频率高于 render |

**Casey 的选择是最轻量的**:vel clamp 是 O(1) 操作,几乎免费。sub-stepping 是 O(N) 操作,N 是子步数,代价随 entity 数线性增长。Casey 知道这一点,所以"先把 clamp 用足,实在不够再上 sub-stepping"——这是典型的 HH 工程哲学:**从最便宜的方案开始,只有真的不够才升级**。

游戏里还有一个常见 trick:**"墙比 tile 厚"**。tile 是 32×32,但墙 entity 的 AABB 是 32×40(略厚)。这样即使 entity 一帧走 32 px,也可能撞到墙——因为墙的"碰撞厚度"更大。这个 trick 在街机游戏里特别常见。

### 3.2 · 图形学视角

clamp 在图形学里有一个对应物:**光线步进**(ray marching)的 step size。两者本质都是"采样间隔"。

考虑你做一个体积云的渲染——光线穿过云,你沿光线方向每隔 step 采样一次密度。step 太大,云的细节被跳过,云变粗糙;step 太小,渲染慢。

游戏物理的 step size 之于碰撞,和光线 step size 之于云渲染,是同一个权衡:**采样密度 vs 计算成本**。

另一个相关概念是 **temporal aliasing**(时间走样)。空间走样是锯齿(高频信号欠采样),时间走样是动画抖动(高速运动欠采样)。vel clamp 本质是"低通滤波"——把高频运动(高速 entity)的低通部分(位移)保留,高频部分(瞬时位置突变)滤掉。这和抗锯齿(MSAA / TAA)的数学根源是同一个 Nyquist-Shannon 采样定理。

### 3.3 · Linux 系统编程视角

clamp 是纯数学,本来和 Linux 无关。但有一个相关的话题:**实时系统的时间保证**。

游戏循环假设 dt 稳定(60 FPS → dt = 16.67 ms)。但如果游戏跑在一个非实时调度系统上(普通 Linux 桌面),系统可能突然卡 100 ms(垃圾回收、磁盘 IO、内核抢占)。这时 dt = 100 ms,vel × dt = 6 倍平时的位移,entity 一帧可能走 200 px。

解法 1:**clamp dt**——dt 上限设 1/30 秒,系统卡时游戏"慢动作"但不"穿墙"。

```rust
let dt = real_dt.min(1.0 / 30.0);
```

Casey 在 Day 014+ 就做了这个。这是**时间维度的 clamp**,和今天的"速度维度 clamp"互补。

解法 2:**实时调度**——把游戏进程提升到 SCHED_FIFO / SCHED_RR,内核不抢占。Linux 提供 `sched_setscheduler(2)` 系统调用,但需要 root 或 CAP_SYS_NICE 权限。

```bash
# 看 chrt 工具
chrt -f 99 ./your_game
# -f = SCHED_FIFO,99 = 最高优先级
# 需要 sudo 或 cap_net_admin+cap_sys_nice
```

但 Casey 不建议游戏走这条路——"游戏不是实时系统,你卡了用户能接受,但你抢了系统别人受不了"。所以**clamp dt 才是游戏该走的路**。

### 3.4 · Rust 生态视角

Rust 实现 clamp 非常简洁:

```rust
fn clamp_velocity(v: &mut Vec2, dt: f32, d_max: f32) {
    let len_sq = v.x * v.x + v.y * v.y;       // 算长度平方(避免 sqrt)
    let max_v = d_max / dt;                    // 速度上限
    let max_v_sq = max_v * max_v;
    if len_sq > max_v_sq {
        let s = max_v_sq.sqrt() / len_sq.sqrt(); // = max_v / |v|
        // 等价于 s = max_v / v.length(),但少一次除法
        v.x *= s;
        v.y *= s;
    }
}
```

**关键 Rust 技巧**:

1. `len_sq > max_v_sq` 用长度平方比较,避免 `sqrt`(sqrt 在 x86 上是 4-15 cycles,看似不多但热路径上累积成本可观)。
2. 如果只是"是否需要 clamp"的判断,完全不用 sqrt。只有真的要 clamp 时才算 sqrt。

更优化的版本用 `f32::clamp`:

```rust
impl Vec2 {
    fn clamp_length(mut self, max_len: f32) -> Self {
        let len_sq = self.x * self.x + self.y * self.y;
        if len_sq > max_len * max_len {
            let s = max_len / len_sq.sqrt();
            self.x *= s;
            self.y *= s;
        }
        self
    }
}
```

`glam` crate 的 `Vec2::clamp_length_max` 就是这么实现的。

```rust
// Cargo.toml
// [dependencies]
// glam = "0.29"

use glam::Vec2;

fn main() {
    let mut v = Vec2::new(3000.0, 4000.0); // 长度 5000
    v = v.clamp_length_max(16.0);          // 限到 16
    println!("{:?}", v.length());          // 16.0
}
```

**所有权视角**:`clamp_velocity(&mut Vec2, ...)` vs `v.clamp_length_max(16.0)`(消费 self 返回新值)。前者更接近 C 风格,后者更 Rust 风格。Casey 用前者;glam 用后者。两种都可以,但如果 Vec2 是 Copy(8 字节),传值比传引用更高效(避免间接寻址)。所以**推荐 glam 风格**:

```rust
#[derive(Copy, Clone)]
struct Vec2 { x: f32, y: f32 }

impl Vec2 {
    fn clamp_length(self, max_len: f32) -> Self { ... }
}

// 用法
v = v.clamp_length(16.0);
```

注意 `v = v.clamp_length(...)`——值类型函数返回新值,赋值回 v。Rust 编译器会优化掉这个赋值(直接在 v 的栈位置 mutate)。

## 5 · 对照与变奏

### 2D vs 3D 的 clamp

2D 是 `(vx, vy)`,clamp 到 `|v| ≤ max_v`。3D 是 `(vx, vy, vz)`,公式完全一样:`|v| = sqrt(vx² + vy² + vz²)`,clamp 同理。

唯一区别:**3D 里 AABB 是 6 个面**,高速 entity 可能从墙的"边角缝"穿过——这需要 sweep test 而不是简单 clamp。Casey 在 Phase 3+ 进入 3D 后会重新讨论。

### clamp vs CCD 的业界辩论

物理引擎社区有个长期辩论:**clamp(限速)是不是"作弊"?**

反方:clamp 改变了物理,高速 entity 被人为降速,玩家感受不到"快"。如果是赛车游戏,clamp 会毁掉速度感。

正方:游戏物理本来就不是真实物理,关键是"玩家感受合理"。只要 clamp 上限设得够高(玩家平时根本到不了),就没问题。

Casey 站正方。但他承认:**赛车 / 飞行模拟类游戏不能用 clamp**,必须上 CCD。

### 历史演化

- **1980s 街机**:游戏用整数坐标,vel 是 int,穿墙是常态(玩家学会"利用 bug")
- **1990s**:浮点普及,但碰撞算法还是离散,tunneling 仍是 bug 来源
- **2000s**:Box2D / Havok 引入 CCD 选项,默认不开
- **2010s**:VR 要求高帧率 + 低延迟,CCD 成为标配
- **2020s**:机器学习物理引擎(如 Brax)开始用神经 CCD

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不直接 clamp pos(`if pos.x > wall.x: pos.x = wall.x`),而要先 clamp vel?

**参考解答**:
1. clamp pos 改了位置但没改速度。下一帧 vel 还是大,entity 会被 vel 推回墙里——出现"墙边抖动"。
2. 物理方程是 `pos += vel * dt`,直接改 pos 违反了这个方程,撞击反弹、摩擦、惯性全失真。
3. resolve_collision 函数依赖正确的 vel 来算反弹方向。vel 错了,反弹也错。
4. clamp vel 让物理方程自然产生"慢下来"的效果,保留加速度的累积(下一帧 vel 会被加速度重新增长,但不超过 max)。

### Lv2 · 动手实践

**题**:在 Rust 里实现 `Vec2::clamp_length(self, max_len: f32) -> Self`。要求:

- 用 length-squared 优化(只在必要时 sqrt)
- 测试三种情况:(a) len < max_len 不变;(b) len > max_len 被缩到 max_len;(c) len == 0 返回零向量(不要 panic)

完成标准:`cargo run` 打印:
```
v1 = Vec2 { x: 3.0, y: 4.0 } (len=5,未变,因为 5 ≤ 5)
v2 = Vec2 { x: 6.0, y: 8.0 } (len=10,clamp 到 5)
v3 = Vec2 { x: 0.0, y: 0.0 } (零向量,正常返回)
```

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec2 { x: f32, y: f32 }

impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn length_squared(self) -> f32 { self.x * self.x + self.y * self.y }
    fn length(self) -> f32 { self.length_squared().sqrt() }

    fn clamp_length(self, max_len: f32) -> Self {
        let max_sq = max_len * max_len;
        let len_sq = self.length_squared();
        if len_sq > max_sq && len_sq > 0.0 {
            // 需要缩放:factor = max_len / sqrt(len_sq)
            let factor = max_len / len_sq.sqrt();
            Self::new(self.x * factor, self.y * factor)
        } else {
            // 不需要缩放(或零向量):原样返回
            self
        }
    }
}

fn main() {
    let v1 = Vec2::new(3.0, 4.0).clamp_length(5.0);     // 长度 5,刚好等于 max,不缩放
    let v2 = Vec2::new(6.0, 8.0).clamp_length(5.0);     // 长度 10,缩放到 5
    let v3 = Vec2::new(0.0, 0.0).clamp_length(5.0);     // 零向量

    println!("v1 = {:?} (len={})", v1, v1.length());
    println!("v2 = {:?} (len={})", v2, v2.length());
    println!("v3 = {:?} (len={})", v3, v3.length());
}
```

**关键解释**:
- `length_squared` 单独算,因为热路径里我们只想知道"是否超限",不想 sqrt。
- `len_sq > 0.0` 的判断防止零向量除以零(`0.0 / 0.0 = NaN`)。
- 注意 `v1`(长度 5,max 5)走 else 分支不缩放,所以保留原方向和大小。如果你的需求是"严格小于 max",改成 `len_sq >= max_sq`。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

下面是一个完整的"小人冲刺穿墙"演示。它构造一个 32 px 厚的墙,让小人用不同速度撞,看 clamp 前后的差异。

```rust
// Cargo.toml: [dependencies] glam = "0.29"

use glam::Vec2;

const TILE_SIZE: f32 = 32.0;
const MAX_MOVE_DIST: f32 = TILE_SIZE * 0.5; // 16 px
const DT: f32 = 1.0 / 60.0;

#[derive(Debug)]
struct Entity {
    pos: Vec2,    // 中心位置
    vel: Vec2,    // 速度(像素/秒)
    half: f32,    // AABB 半宽
}

#[derive(Debug)]
struct Wall { center: Vec2, half: Vec2 } // AABB 表示

impl Wall {
    fn contains_point(&self, p: Vec2) -> bool {
        (p.x - self.center.x).abs() <= self.half.x &&
        (p.y - self.center.y).abs() <= self.half.y
    }
}

/// Minkowski AABB 重叠判定
fn aabb_overlap(a: &Entity, w: &Wall) -> bool {
    (a.pos.x - w.center.x).abs() <= a.half + w.half.x &&
    (a.pos.y - w.center.y).abs() <= a.half + w.half.y
}

/// 限速 clamp:让一帧移动 ≤ MAX_MOVE_DIST
fn clamp_velocity(v: Vec2) -> Vec2 {
    let dist = v.length() * DT;
    if dist > MAX_MOVE_DIST {
        v * (MAX_MOVE_DIST / dist)
    } else {
        v
    }
}

fn step(e: &mut Entity, walls: &[Wall], use_clamp: bool) -> bool {
    // 1. clamp
    if use_clamp { e.vel = clamp_velocity(e.vel); }
    // 2. 移动
    e.pos += e.vel * DT;
    // 3. 检测
    for w in walls {
        if aabb_overlap(e, w) {
            return true; // 撞到了
        }
    }
    false // 没撞到
}

fn main() {
    // 墙:x=64~96(32 px 厚),y=-100~100
    let walls = vec![
        Wall { center: Vec2::new(80.0, 0.0), half: Vec2::new(16.0, 100.0) }
    ];
    let wall_left = 64.0;
    let wall_right = 96.0;

    // 不 clamp:玩家高速冲刺
    let mut e1 = Entity {
        pos: Vec2::new(20.0, 0.0),  // 起点 x=20(墙左 64)
        vel: Vec2::new(5000.0, 0.0),// 5000 px/s,一帧走 ~83 px
        half: 8.0,
    };
    // 一步走完
    let hit1 = step(&mut e1, &walls, /*use_clamp=*/ false);
    println!("不 clamp:");
    println!("  起点 x=20, vel=5000, 终点 x={}", e1.pos.x);
    println!("  一帧走 {} px", e1.pos.x - 20.0);
    println!("  撞墙? {}", hit1);
    println!("  穿墙? {}", e1.pos.x > wall_right); // 终点 x > 96 就是穿墙
    println!();

    // clamp:同样速度
    let mut e2 = Entity {
        pos: Vec2::new(20.0, 0.0),
        vel: Vec2::new(5000.0, 0.0),
        half: 8.0,
    };
    let hit2 = step(&mut e2, &walls, /*use_clamp=*/ true);
    println!("clamp:");
    println!("  起点 x=20, vel=5000(clamped), 终点 x={}", e2.pos.x);
    println!("  一帧走 {} px", e2.pos.x - 20.0);
    println!("  撞墙? {}", hit2);
}
```

**预期输出**:

```
不 clamp:
  起点 x=20, vel=5000, 终点 x=103.333336
  一帧走 83.333336 px
  撞墙? false
  穿墙? true

clamp:
  起点 x=20, vel=5000(clamped), 终点 x=36
  一帧走 16 px
  撞墙? false
```

clamp 版本一帧只走 16 px(刚好等于 MAX_MOVE_DIST),下一帧再走 16 px(撞墙)。不 clamp 版本一帧走 83 px,直接越过 32 px 厚的墙,撞墙检测返回 false——**穿墙**。

**关键 Rust 特性**:
- `glam::Vec2` 实现了 `Add` / `AddAssign` / `Mul<f32>` 等 trait,可以直接写 `e.pos += e.vel * DT`。
- `Vec2::length()` 内部用 `sqrt`(底层是 `sqrtss` 硬件指令)。
- struct `Entity` / `Wall` 都是 plain data,可以 `#[derive(Debug)]` 打印。

### 时间维度 clamp(dt 上限)

除了 vel clamp,Casey 在 Day 014+ 还做了 dt clamp。这两个互补:

```rust
fn update(world: &mut World, real_dt: f32) {
    // dt clamp:防止系统卡顿时 dt 过大
    let dt = real_dt.min(1.0 / 30.0);  // 最大 1/30 秒(慢动作)

    // vel clamp:防止高速 entity 穿墙
    for e in &mut world.entities {
        e.vel = clamp_velocity(e.vel, dt, MAX_MOVE_DIST);
    }

    // 物理积分
    for e in &mut world.entities {
        e.pos += e.vel * dt;
    }

    // 碰撞检测
    detect_collisions(world);
}
```

`dt.min(1.0 / 30.0)` 是关键:**如果系统卡了 100 ms,我们假装只过了 33 ms**——游戏慢动作,但物理不出 bug。这是游戏引擎的标准做法,几乎所有商业游戏都这么干。
