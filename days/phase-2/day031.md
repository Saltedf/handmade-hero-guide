# Day 031 · 瓦片地图坐标系

> Day 028-030 你画 tile map、加碰撞、多地图切换,代码能跑了,但你心里可能还糊着——"tile 坐标和世界坐标到底怎么对应?玩家在 tile (3, 5) 对应世界坐标 (96, 160)?还是 (112, 176)?tile (3, 5) 的'中心'在哪?"。Day 031 把这件事彻底说清:Casey 给出一套明确的坐标约定,后面 600+ 集都遵守。

## 0 · 为什么要有这一天

坐标系听起来像数学课的复习,但 game dev 里**坐标系是反复踩坑的源头**。具体看几个常见的 bug:

- **Bug A**:玩家在 tile (3, 5),你想画一个"玩家头上的标记",位置算成 `tile_center + Vec2(0, -10)`。结果标记画在 tile (3, 4) 的位置——你用错了 "tile (3, 5) 的中心" 的定义
- **Bug B**:你写碰撞代码,玩家在 (95, 70),你想知道他在哪个 tile,用 `wx / TILE_SIZE` = 2,但实际他在 tile (2, 2) 还是 tile (3, 2)?——你没意识到 95 / 32 = 2.97,意思是"在 tile 2 内的 97% 位置"
- **Bug C**:你切地图,玩家从地图 A 的东边走到地图 B 的西边,但视觉上玩家"跳"了一下——因为两张地图对"tile (0, 0)"的世界坐标定义不一样
- **Bug D**:Day 235 你切到 OpenGL,屏幕上的画面上下颠倒——因为你的 game 用 y 向下,OpenGL 默认 y 向上,你没显式处理

这些 bug 的根因都是**坐标系没明确约定**。Casey 这集做的事情:

1. 明确**世界坐标**和**tile 坐标**的关系
2. 明确 **y 轴方向**(向下,不是数学课的向上)
3. 明确**玩家位置**是"AABB 左上角"还是"AABB 中心"
4. 明确**世界坐标 → 屏幕坐标**的转换公式
5. 给出几个**helper 函数**(`world_to_tile`, `tile_to_world_min`, `tile_to_world_center`),后面所有代码都用这些

心理锚点:看完这集,你应该能在 30 秒内回答:

- 玩家在世界坐标 (100.5, 70.3),他在哪个 tile?
- tile (3, 5) 的左上角世界坐标是什么?
- 玩家 32×32,AABB 左上角在 (100, 50),AABB 中心在哪?

## 2 · 心智模型

### 类比:地图上的网格坐标

你用过纸质地图吗?地图上有方格网,每个方格有坐标(A1、B2、C3 等)。地图上的"实际位置"和"方格坐标"是两套系统:

- **实际位置**:连续的(可以在方格内的任何位置)
- **方格坐标**:离散的(整个方格只有一个名字)

游戏里也是这样:

- **世界坐标**:连续(浮点),玩家可以在 tile 内的任何位置
- **tile 坐标**:离散(整数),整个 tile 共享一个名字

两套系统并存,需要**精确的转换规则**。Casey 这集把规则定下来。

### 决策 1:y 轴向下

这是最大的"反直觉"决策——**和数学课学的相反**。数学课的笛卡尔坐标系 y 向上,游戏用 y 向下。为什么?

**历史原因**:显示器硬件。CRT(阴极射线管)显像管从屏幕**左上角**开始,**从上到下**一行行扫描。framebuffer 的第 0 行对应屏幕最上面。游戏代码用 y 向下 = 渲染时不用翻转 = 代码直观。

```
数学坐标系(y 向上):            屏幕坐标系(y 向下):
        y                                
        ↑                                (0, 0) →→→ x
        │                                ↓
   ←────┼────→ x                         ↓ y
        │                                ↓
        ↓                                
   (0, 0)                                
```

**踩坑预警**:Day 235 切 OpenGL 时,OpenGL 默认 y 向上(数学传统)。Casey 在 Day 104 处理这个:**渲染层**做转换(game y 向下 → OpenGL y 向上),**逻辑层**保持 y 向下不变。这就是 Day 026 三明治分层的威力——一次架构决策让后续大改动隔离在单层。

### 决策 2:tile (0, 0) 的世界坐标范围

Casey 的约定:

```
tile (tx, ty) 占据世界坐标范围:
  x in [tx * 32, tx * 32 + 32)
  y in [ty * 32, ty * 32 + 32)

即:
  tile (0, 0):  x in [0, 32),    y in [0, 32)
  tile (1, 0):  x in [32, 64),   y in [0, 32)
  tile (3, 5):  x in [96, 128),  y in [160, 192)
```

**注意**:范围是**左闭右开** `[start, end)`。`32` 不属于 tile (0, 0),而是属于 tile (1, 0)。这避免了"边界点归谁"的歧义。

### 决策 3:tile 的"中心"

```rust
fn tile_center(tx: i32, ty: i32) -> Vec2 {
    Vec2 {
        x: (tx as f32 + 0.5) * TILE_SIZE as f32,
        y: (ty as f32 + 0.5) * TILE_SIZE as f32,
    }
}
```

tile (3, 5) 的中心 = ((3+0.5) × 32, (5+0.5) × 32) = (112, 176)。

**为什么 +0.5**:tile 占据 [tx, tx+1) 的 tile 单位空间。中心在 tx + 0.5。乘以 TILE_SIZE 转成像素。

### 决策 4:玩家位置 = AABB 左上角

```rust
struct Player {
    pos: Vec2,  // ← 这是 AABB 的左上角,不是中心
}
```

玩家 32×32,AABB 左上角在 (100, 50),则:

```
    (100, 50) ← AABB 左上角 = player.pos
       ┌────────────┐
       │            │
       │   玩家     │ height = 32
       │            │
       └────────────┘
        width = 32
   (132, 82) ← AABB 右下角(不含)
```

**为什么选左上角不选中心**:

- 碰撞代码简单:`AABB.left = pos.x, AABB.right = pos.x + size`
- 渲染代码简单:`draw_at(pos.x, pos.y)` 直接画左上角对齐
- 多数游戏开发约定俗成

**踩坑预警**:某些算法(比如"以玩家中心为圆心的圆形碰撞")用中心更方便。Casey 在 Day 050+ Minkowski 碰撞时,引入 `center = pos + Vec2(size/2, size/2)` 概念。但**位置字段始终是左上角**,center 是计算出来的派生值。

### 转换公式汇总

```rust
const TILE_SIZE: f32 = 32.0;

// 世界坐标 → tile 坐标
fn world_to_tile(wx: f32, wy: f32) -> (i32, i32) {
    // floor 对正数和负数都正确(-1.5 floor = -2,不是 -1)
    // Rust 的 i32::from_f32 是 truncate,我们要 floor
    (wx.floor() as i32 / TILE_SIZE as i32, wy.floor() as i32 / TILE_SIZE as i32)
}

// 但上面有个 bug:负数 floor 后再除,可能错(因为 Rust 整数除法 truncate)
// 比如 wx = -1.5,floor = -2,-2 / 32 = 0(truncate),但实际 tile 是 -1
// 正确写法:先除再 floor,或用 div_euclid

// 正确版本(Rust 1.62+):
fn world_to_tile_safe(wx: f32, wy: f32) -> (i32, i32) {
    let tx = (wx / TILE_SIZE).floor() as i32;
    let ty = (wy / TILE_SIZE).floor() as i32;
    (tx, ty)
}
// 注意:把 TILE_SIZE 当 f32 处理,先除后 floor。
// (wx / TILE_SIZE).floor() 等价于 floor(wx / 32.0)
// -1.5 / 32.0 = -0.046875,floor = -1。正确。

// tile → 世界(左上角)
fn tile_to_world_min(tx: i32, ty: i32) -> Vec2 {
    Vec2 {
        x: tx as f32 * TILE_SIZE,
        y: ty as f32 * TILE_SIZE,
    }
}

// tile → 世界(中心)
fn tile_to_world_center(tx: i32, ty: i32) -> Vec2 {
    Vec2 {
        x: (tx as f32 + 0.5) * TILE_SIZE,
        y: (ty as f32 + 0.5) * TILE_SIZE,
    }
}

// 世界 → 屏幕
fn world_to_screen(wx: f32, wy: f32, cam: Vec2) -> (i32, i32) {
    ((wx - cam.x) as i32, (wy - cam.y) as i32)
}
```

**关键细节**:

- **负数 floor**:Rust 的 `as i32` 对 f32 是 truncate-towards-zero(`-1.5 as i32 = -1`),不是 floor(`-1.5 floor = -2`)。所以**必须先调用 `.floor()` 再 `as i32`**。
- **整数除法的陷阱**:`-2_i32 / 32 = 0`(Rust 整数除法 truncate),但 `-2 / 32` 用 floor 应该是 `-1`。所以负数处理要小心。**最稳的做法**:始终用 `f32` 计算,最后转 `i32`。
- **`(wx / TILE_SIZE).floor()`** —— 这等价于"wx 在哪个 tile"。wx=100.5,100.5/32=3.14,floor=3。在 tile 3。wx=-1.5,-1.5/32=-0.047,floor=-1。在 tile -1(负数 tile 是允许的,只是越界)。

### 具体例子:玩家在 (100.5, 70.3)

```
玩家在 (100.5, 70.3):
  他在哪个 tile?  floor(100.5/32) = 3, floor(70.3/32) = 2 → tile (3, 2)
  tile (3, 2) 左上角:(3 × 32, 2 × 32) = (96, 64)
  tile (3, 2) 中心:((3+0.5) × 32, (2+0.5) × 32) = (112, 80)
  玩家在 tile 内的偏移:(100.5 - 96, 70.3 - 64) = (4.5, 6.3)
  玩家在 tile 内的归一化偏移:(4.5/32, 6.3/32) = (14%, 19.7%)

如果 camera 在 (200, 150):
  玩家在屏幕坐标:(100.5 - 200, 70.3 - 150) = (-99.5, -79.7)
  负数——玩家在屏幕外(左上方)。需要 camera 移到玩家附近。
```

### 坐标系可视化

```
世界坐标(浮点):
   (0, 0) ────────────────────────────────► x
     │
     │   tile (0, 0) │ tile (1, 0) │ tile (2, 0) │ ...
     │   [0, 32)×    │ [32, 64)×   │ [64, 96)×   │
     │   [0, 32)     │ [0, 32)     │ [0, 32)     │
     │ ──────────────┼─────────────┼─────────────┼────
     │   tile (0, 1) │ tile (1, 1) │ tile (2, 1) │ ...
     │   [0, 32)×    │ [32, 64)×   │ [64, 96)×   │
     │   [32, 64)    │ [32, 64)    │ [32, 64)    │
     │ ──────────────┼─────────────┼─────────────┼────
     │
   y ▼
```

每个 tile 是 32×32 的"格子",玩家位置是浮点数,可以在格子内的任何位置。

### 玩家 AABB 在多 tile 上的覆盖

玩家 32×32,AABB 左上角在 (50, 70):

```
tile 覆盖:
  tile_left = 50 / 32 = 1.5 → 1(floor)
  tile_right = (50 + 32 - 1) / 32 = 81 / 32 = 2.5 → 2
  tile_top = 70 / 32 = 2.18 → 2
  tile_bottom = (70 + 32 - 1) / 32 = 101 / 32 = 3.15 → 3

覆盖 2×2 = 4 个 tile:(1, 2), (2, 2), (1, 3), (2, 3)
```

**为什么 tile_left ≠ tile_right**(即使 width = 32 = TILE_SIZE):因为玩家**不在 tile 边界对齐**(50 不是 32 的倍数)。如果玩家正好在 tile 边界(x=32, y=32),则 tile_left=tile_right=1(单个 tile)。

这就是 Day 029 碰撞代码里 `tile_left = x / TILE_SIZE, tile_right = (x + size - 1) / TILE_SIZE` 的来源。

### 决策 5:Camera 偏移

```rust
struct Camera {
    pos: Vec2,  // camera 左上角的世界坐标
}

// 世界 → 屏幕:减去 camera 偏移
let screen_x = world_x - camera.pos.x;
let screen_y = world_y - camera.pos.y;

// 屏幕 → 世界:加上 camera 偏移
let world_x = screen_x as f32 + camera.pos.x;
let world_y = screen_y as f32 + camera.pos.y;
```

**Camera 的意义**:camera 在哪,屏幕显示的就是"camera 周围的世界"。玩家移动 = camera 跟随玩家 = 世界相对屏幕滚动。

**Camera 跟随玩家的策略**:

```rust
// 简单版:camera 中心始终对齐玩家中心
fn update_camera(camera: &mut Camera, player: &Player, dt: f32) {
    let target_x = player.pos.x + PLAYER_SIZE as f32 / 2.0 - SCREEN_WIDTH as f32 / 2.0;
    let target_y = player.pos.y + PLAYER_SIZE as f32 / 2.0 - SCREEN_HEIGHT as f32 / 2.0;
    camera.pos.x = target_x;
    camera.pos.y = target_y;
}

// 平滑版:camera 缓慢追随玩家,有"惯性"感
fn update_camera_smooth(camera: &mut Camera, player: &Player, dt: f32) {
    let target_x = player.pos.x + PLAYER_SIZE as f32 / 2.0 - SCREEN_WIDTH as f32 / 2.0;
    let target_y = player.pos.y + PLAYER_SIZE as f32 / 2.0 - SCREEN_HEIGHT as f32 / 2.0;
    // lerp:camera 当前位置 → 目标位置,每次走 10%
    camera.pos.x += (target_x - camera.pos.x) * 0.1;
    camera.pos.y += (target_y - camera.pos.y) * 0.1;
}
```

`lerp`(linear interpolation,线性插值)是游戏开发的常用技巧——"以一定比例向目标靠近"。`0.1` 意味着每帧走剩余距离的 10%,10 帧后大概到目标(指数衰减)。

Casey 这集先用简单版(直接对齐),Day 100+ 才加平滑版。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

坐标系是游戏开发的基础设施。每个游戏都要明确:

**问题 1:世界坐标的"原点"在哪?**

- 单地图游戏:世界原点 = 地图左上角
- 多地图游戏(Casey Day 030):每张地图有自己的原点(地图左上角)
- 大世界(Casey Day 032 WorldPos):世界原点 = 大世界左上角,地图只是"区域"
- 开放世界(Skyrim):世界原点 = 整个大陆的中心(便于负数坐标)

**问题 2:y 轴方向?**

- 2D 游戏:几乎都是 y 向下(屏幕传统)
- 3D 游戏:分歧——OpenGL 默认 y 向上,DirectX 默认 y 向下
- Casey HH:game 代码 y 向下,Day 104+ render target 改 y 向上(为 OpenGL)

**问题 3:单位?**

- Casey HH:1 单位 = 1 像素(2D 游戏)
- 3D 游戏:1 单位 = 1 米(物理引擎需要真实尺度)
- Minecraft:1 单位 = 1 立方体(可缩放)

**问题 4:玩家位置 = 什么?**

- AABB 左上角(Casey)
- AABB 中心(某些物理引擎)
- 脚下中心(平台游戏,便于跳跃判定)

每种约定都有道理,**关键是项目内一致**。Casey 选 AABB 左上角,后面 600+ 集一致。

### 3.2 · 🎨 图形学视角

坐标系在图形学里是**多套**并存的:

| 坐标系 | 范围 | 用途 |
|---|---|---|
| 屏幕坐标 | (0, 0) 到 (W, H),y 向下 | framebuffer 像素位置 |
| 世界坐标 | 任意浮点 | game 代码用的坐标 |
| NDC(Normalized Device Coords) | (-1, -1) 到 (1, 1) | OpenGL 投影后 |
| Clip 空间 | (-W, -W) 到 (W, W) | OpenGL 顶点 shader 输出 |
| 视口坐标 | (0, 0) 到 (1, 1) | GPU 渲染目标 |
| UV 坐标 | (0, 0) 到 (1, 1) | 纹理采样 |

每个空间都有不同目的:

- 世界坐标:游戏逻辑
- 屏幕坐标:像素绘制
- NDC:GPU 投影的统一中间表示
- UV:纹理上的位置

**坐标变换链**(2D 简化版):

```
世界坐标 (100, 50)
   │  - camera
   ▼
屏幕坐标 (10, 20)  (假设 camera 在 90, 30)
   │  / window_size * 2 - 1
   ▼
NDC (-0.99, -0.94)  (假设窗口 1280×720)
```

OpenGL 渲染时还要做 MVP 变换,但 2D 软渲染不用。Casey Day 1-234 软渲染只有"世界 ↔ 屏幕"两套坐标,Day 235+ 才用 OpenGL 的完整链路。

### 3.3 · 🐧 Linux 系统编程视角

Linux 系统编程里也有"坐标系"——文件偏移量。`lseek(fd, offset, SEEK_SET)` 把文件指针移到 offset 字节。这和游戏的"世界坐标"是同一抽象——**一个连续空间里的位置**。

**文件 offset 的"坐标系"**:

- offset 0 = 文件开始
- offset 文件大小 = 文件结束
- offset 单位 = 字节
- 负 offset 通常非法(SEEK_SET),但 SEEK_CUR/SEEK_END 可以用负

**游戏的"坐标系"**:

- 世界坐标 (0, 0) = 世界左上角
- 世界坐标 (W, H) = 世界右下角
- 单位 = 像素
- 负坐标允许(地图外)

这种类比帮你理解"为什么 mmap 之后用 pointer 算 offset 和游戏坐标转换是同一类问题"。

**Linux 工具验证**:

```bash
# 看 framebuffer 的"坐标系"
# /dev/fb0 是 Linux framebuffer 设备
ls -la /dev/fb0
# crw-rw---- 1 root video 29, 0 ... /dev/fb0

# 看 framebuffer 信息(分辨率、bpp)
cat /sys/class/graphics/fb0/virtual_size
# 1280,720  ← x,y 像素数
cat /sys/class/graphics/fb0/bits_per_pixel
# 32  ← 每像素 32 位

# framebuffer 的"tile_size"是 1(单像素),y 向下(行优先存储)
# 这就是 game dev 用 y 向下的原因——硬件就这么干
```

### 3.4 · 🦀 Rust 生态视角

Rust 表达"坐标系转换"的最佳实践:**用类型系统防止搞混**。

**坏做法**:`f32` 通杀

```rust
fn render(wx: f32, wy: f32, cam_x: f32, cam_y: f32) {
    // 这里 wx 是世界坐标还是屏幕坐标?不知道!
    let sx = wx - cam_x;
    draw_at(sx, ...);
}
```

调用者容易传错——把屏幕坐标当世界坐标传,编译器不报错,运行时画面错乱。

**好做法**:用 newtype 区分

```rust
#[derive(Copy, Clone, Debug)]
struct WorldCoord(f32);

#[derive(Copy, Clone, Debug)]
struct ScreenCoord(f32);

fn world_to_screen(wx: WorldCoord, cam: WorldCoord) -> ScreenCoord {
    ScreenCoord(wx.0 - cam.0)
}

fn draw_at(sx: ScreenCoord, ...) { ... }

// 现在:draw_at(WorldCoord(10.0), ...) 是编译错误
// Rust 强制你先转换
```

这种"newtype 模式"是 Rust 防止"传错单位"的标准技巧。零开销(编译后就是 f32),但编译时强类型。

**Casey 的做法**:Casey 在 C 里用 typedef + 匈牙利命名(`worldX`, `screenX`),不强制但约定。Rust 翻译可以用 newtype 加强。

**glam / nalgebra 的做法**:

- `glam::Vec2` 没区分坐标空间,纯 `f32` 二元组
- `nalgebra::Point2<f32>` 区分 Point(位置)和 Vector(位移),但同空间内

生产代码用 glam 就够。教学代码 Casey 用裸 `f32`,强调"用纪律不用类型"。

## 5 · 对照与变奏

### 同一抽象在不同语境下的变体

**问题**:把"连续位置"和"离散网格"对应起来。

| 语境 | 连续 | 离散 |
|---|---|---|
| 2D 游戏 | 世界坐标(浮点像素) | tile 坐标(整数) |
| 图像处理 | 像素坐标(浮点用于插值) | 像素索引(整数) |
| 数字音频 | 时间(秒,浮点) | sample 索引(整数) |
| 3D 建模 | UV 坐标(浮点 [0,1]) | 纹理像素(整数) |
| GPS | 经纬度(浮点) | 网格(0.0001 度一格) |
| 元胞自动机 | 浮点场 | 网格 cell |

所有这些场景的核心问题相同:**浮点连续位置 ↔ 整数离散网格的转换**。`floor`、`ceil`、`round` 各有用,关键是项目内一致。

### 2D vs 3D 坐标系

| | 2D | 3D |
|---|---|---|
| 维度 | (x, y) | (x, y, z) |
| y 方向 | 向下(屏幕) | 向上(数学,OpenGL)/ 向下(DirectX) |
| 旋转 | 单角度 θ | 三角度(euler)/ 四元数 |
| 单位 | 像素 | 米 |
| 投影 | 无(直接画) | 透视 / 正交 |

3D 比 2D 复杂得多,但本质还是"位置 + 方向"。Phase 3 进入 3D 后会展开。

### 历史演化

- **1970s**:整数坐标为主(硬件浮点慢),游戏用 16-bit 整数
- **1980s**:浮点普及,游戏开始用 f32
- **1990s**:3D 游戏,OpenGL y 向上 / DirectX y 向下,业界分裂
- **2000s**:WebGL 用 OpenGL 风格(y 向上),Web game 开发者经常困惑
- **2010s**:统一趋势,主流引擎让用户可选(Unity y 向上,Godot 2D y 向下)
- **2020s**:WebGPU 统一标准,但底层坐标系仍各引擎不同

Casey 在 HH 里用"y 向下"——2D 游戏传统。这是合理选择,但你以后学 3D 要适应"y 向上"。

### Lv1 · 概念辨析

**题**:Casey 选 y 向下(屏幕坐标),不选 y 向上(数学坐标)。为什么?Day 235 切 OpenGL 时会带来什么麻烦?

**参考解答**:**选 y 向下因为显示设备**。CRT/LED 从上往下扫描,framebuffer 第 0 行 = 屏幕最上面。y 向下 = 渲染时不用翻转 = 代码直观。

**Day 235 切 OpenGL 的麻烦**:OpenGL 默认 y 向上(右手系,数学传统)。game 代码用 y 向下 → OpenGL 渲染画面会**上下颠倒**。

两种解决:

1. **翻转 y**:渲染时所有 y 取反。简单但要小心文字方向(文字翻转后是颠倒的,要再翻回来)
2. **用 y 向上 render target**(Day 104 Casey 选这个):game 内部 y 向下,渲染层把 y 翻转

Day 026 的 update/render 分离再次证明价值——只改渲染层,game 代码不动。

**参考解答**:

```rust
// src/main.rs
// cargo new --bin coords && cd coords

const TILE_SIZE: f32 = 32.0;

#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec2 { x: f32, y: f32 }

impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
}

// 世界坐标 → tile 坐标
fn world_to_tile(wx: f32, wy: f32) -> (i32, i32) {
    // 注意:必须 .floor() 后再 as i32,否则负数会 truncate 不是 floor
    ((wx / TILE_SIZE).floor() as i32, (wy / TILE_SIZE).floor() as i32)
}

// tile → 世界(左上角)
fn tile_to_world_min(tx: i32, ty: i32) -> Vec2 {
    Vec2::new(tx as f32 * TILE_SIZE, ty as f32 * TILE_SIZE)
}

// tile → 世界(中心)
fn tile_to_world_center(tx: i32, ty: i32) -> Vec2 {
    Vec2::new(
        (tx as f32 + 0.5) * TILE_SIZE,
        (ty as f32 + 0.5) * TILE_SIZE,
    )
}

// 世界 → 屏幕
fn world_to_screen(wx: f32, wy: f32, cam: Vec2) -> Vec2 {
    Vec2::new(wx - cam.x, wy - cam.y)
}

// 屏幕 → 世界
fn screen_to_world(sx: f32, sy: f32, cam: Vec2) -> Vec2 {
    Vec2::new(sx + cam.x, sy + cam.y)
}

fn describe_position(name: &str, wx: f32, wy: f32, cam: Vec2) {
    println!("=== {} ===", name);
    println!("  World pos: ({}, {})", wx, wy);
    let (tx, ty) = world_to_tile(wx, wy);
    println!("  In tile: ({}, {})", tx, ty);
    let tile_min = tile_to_world_min(tx, ty);
    println!("  Tile min: ({}, {})", tile_min.x, tile_min.y);
    let tile_cen = tile_to_world_center(tx, ty);
    println!("  Tile center: ({}, {})", tile_cen.x, tile_cen.y);
    let offset = Vec2::new(wx - tile_min.x, wy - tile_min.y);
    println!("  Offset in tile: ({}, {})", offset.x, offset.y);
    let screen = world_to_screen(wx, wy, cam);
    println!("  Screen pos: ({}, {})", screen.x, screen.y);
    println!();
}

fn main() {
    let cam = Vec2::new(200.0, 150.0);
    describe_position("Aligned to tile edge", 96.0, 64.0, cam);
    describe_position("Inside tile", 100.5, 70.3, cam);
    describe_position("Negative (off-map)", -10.0, -20.0, cam);
    describe_position("At origin", 0.0, 0.0, cam);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn aligned_position_in_single_tile() {
        // (32, 32) 应该在 tile (1, 1)
        let (tx, ty) = world_to_tile(32.0, 32.0);
        assert_eq!((tx, ty), (1, 1));
    }

    #[test]
    fn inside_tile_stays_in_that_tile() {
        // (33, 33) 还在 tile (1, 1),因为是 [32, 64) 范围
        let (tx, ty) = world_to_tile(33.0, 33.0);
        assert_eq!((tx, ty), (1, 1));
        // (63, 63) 也还在 tile (1, 1)
        let (tx, ty) = world_to_tile(63.0, 63.0);
        assert_eq!((tx, ty), (1, 1));
    }

    #[test]
    fn negative_position_uses_floor_not_truncate() {
        // -1.0 / 32 = -0.03125,floor = -1,truncate = 0
        // 我们要 floor,所以 -1.0 应该在 tile (-1, ...)
        let (tx, _) = world_to_tile(-1.0, 0.0);
        assert_eq!(tx, -1);
        // -33 / 32 = -1.03,floor = -2
        let (tx, _) = world_to_tile(-33.0, 0.0);
        assert_eq!(tx, -2);
    }

    #[test]
    fn tile_min_vs_center_differ_by_half_tile() {
        let min = tile_to_world_min(3, 5);
        let cen = tile_to_world_center(3, 5);
        assert_eq!(cen.x - min.x, TILE_SIZE / 2.0);  // 16
        assert_eq!(cen.y - min.y, TILE_SIZE / 2.0);  // 16
    }

    #[test]
    fn world_screen_roundtrip() {
        // 任意世界坐标 → 屏幕 → 世界,应该回到原值
        let cam = Vec2::new(123.4, 567.8);
        let wx = 999.0;
        let wy = -42.0;
        let s = world_to_screen(wx, wy, cam);
        let w = screen_to_world(s.x, s.y, cam);
        assert!((w.x - wx).abs() < 0.001);
        assert!((w.y - wy).abs() < 0.001);
    }

    #[test]
    fn tile_at_origin_covers_0_to_32() {
        // tile (0, 0) 的左上角是 (0, 0),右下角是 (32, 32)
        let min = tile_to_world_min(0, 0);
        assert_eq!(min, Vec2::new(0.0, 0.0));
        // (0, 0) 在 tile (0, 0)
        assert_eq!(world_to_tile(0.0, 0.0), (0, 0));
        // (31.9, 31.9) 也在 tile (0, 0)
        assert_eq!(world_to_tile(31.9, 31.9), (0, 0));
        // (32, 32) 在 tile (1, 1)(左闭右开)
        assert_eq!(world_to_tile(32.0, 32.0), (1, 1));
    }
}
```

### Rust 完整可跑示例(可视化坐标转换)

把 Lv2 的代码扩展,加一个**ASCII 可视化**——把 tile map 用字符画出来,标记玩家位置。

```rust
// src/main.rs (扩展 Lv2)
// 在 Lv2 代码基础上加 visualize 函数

const MAP_W: i32 = 16;
const MAP_H: i32 = 8;

fn visualize_tile_map(player_wx: f32, player_wy: f32) {
    println!("Tile map visualization ({}x{}):", MAP_W, MAP_H);
    println!("Player world pos: ({}, {})", player_wx, player_wy);
    let (ptx, pty) = world_to_tile(player_wx, player_wy);
    println!("Player tile: ({}, {})", ptx, pty);
    println!();

    // 打印 tile map,标记玩家所在 tile
    for ty in 0..MAP_H {
        let mut row = String::new();
        for tx in 0..MAP_W {
            if tx == ptx && ty == pty {
                row.push_str("[PP]");  // 玩家所在 tile
            } else {
                row.push_str("[  ]");
            }
        }
        println!("  {}", row);
    }

    // 打印 tile 边界的世界坐标
    println!();
    println!("Tile boundaries (world coords):");
    println!("  Vertical lines (x = tx * 32):");
    for tx in 0..=MAP_W {
        print!("    x={} ", tx * 32);
    }
    println!();
}

fn main() {
    visualize_tile_map(100.5, 70.3);
    println!("\n---\n");
    visualize_tile_map(96.0, 64.0);
}
```
