# Day 036 · 加载 BMP 位图

> Day 028-035 你画的 tile 都是纯色块——绿方块、灰方块。Day 036 终于可以加载**真实图片**(BMP 格式)。但 Casey 故意选 BMP 不是 PNG/JPG——BMP **无压缩**,解析最简单。先教你 BMP,后面 Day 436+ 才手写 PNG(LZ77+Huffman)。这种递进让 PNG 解析不显得"魔法"——你已经会 BMP,只是再加几步压缩。

## 0 · 为什么要有这一天

你的游戏一直用纯色块:Grass = 绿,Stone = 灰,Water = 蓝。这是 Day 028-35 的简化,但**真实游戏需要真实贴图**——草有草叶纹路、石头有裂纹、水有波纹。这些细节必须用图片,不能用纯色。

加载图片要选**文件格式**。三大主流:

- **BMP**(Windows Bitmap):无压缩,文件大,解析最简单
- **PNG**(Portable Network Graphics):无损压缩(LZ77+Huffman),文件小,解析中等复杂
- **JPEG**:有损压缩(DCT),文件最小,解析最复杂

为什么 Casey 这集选 BMP?

1. **教学渐进**:BMP 无压缩,你只需要理解"二进制文件格式"。Day 436+ 学 PNG 时再加"压缩层"
2. **快速验证**:BMP 解析 50 行代码,你今天就能跑通。PNG 需要 1000+ 行
3. **真实使用**:Windows 系统原版大量 BMP,GDI 传统
4. **支持 alpha**:32-bit BMP 支持 RGBA(带透明),够游戏用

但 BMP 有几个**经典坑**:

1. **BGR vs RGB 顺序**:Windows GDI 历史原因,像素字节是 B-G-R 不是 R-G-B
2. **bottom-up vs top-down**:height 正数时,像素数据从最后一行开始往前存(CRT 扫描传统)
3. **row padding**:每行要 4 字节对齐,24-bit BMP 可能要 pad
4. **多种 bpp**(bits per pixel):1/4/8/16/24/32 位深,各有不同

Casey 这集做的事情:

1. 解释 BMP 文件结构(文件头 + 信息头 + 像素数据)
2. 用 `std::fs::read` 读二进制文件
3. 解析 header(验证魔数、读 width/height/bpp)
4. 处理 BGR → RGB 顺序转换
5. 处理 bottom-up → top-down 翻转
6. 处理 row padding

心理锚点:看完这集,你应该能:

- 解释 BMP 文件的三段结构
- 解释 BGR vs RGB 的历史原因
- 写出一个最简的 BMP 解析器(24-bit BMP)
- 知道 row padding 是什么、怎么处理

如果你做不到,反复看 §2 的"BMP 文件结构"和"三大坑"。Day 037(位图渲染)、Day 038(混合)、Day 436+(PNG)都基于这集。

## 2 · 心智模型

### 类比:读快递单

你拿到一个**快递包裹**,要找到里面是什么。包裹上有标签:

1. **外层标签**(物流信息):发件人、收件人、重量
2. **内层标签**(商品信息):里面是什么、几件、易碎吗
3. **商品本身**:实际内容

BMP 文件一样:

1. **文件头**(BITMAPFILEHEADER,14 字节):文件类型、大小、像素数据偏移
2. **信息头**(BITMAPINFOHEADER,40 字节):width、height、bpp、压缩方式
3. **像素数据**:实际像素

读完前两段,你知道像素数据从哪开始、怎么排列。然后读像素。

### BMP 文件结构

```
偏移    大小    字段                  说明
0       2      魔数 "BM"             验证是 BMP
2       4      文件大小              字节数
6       2      保留1                 通常 0
8       2      保留2                 通常 0
10      4      像素数据偏移          从文件开始算的字节偏移
14      40     BITMAPINFOHEADER:
  14    4      header 大小            通常 40
  18    4      width                  像素宽度(有符号 i32!)
  22    4      height                 像素高度(正=bottom-up,负=top-down)
  26    2      planes                 通常 1
  28    2      bpp                    位/像素:1/4/8/16/24/32
  30    4      压缩方式               0=不压缩,1=RLE8,2=RLE4,3=bitfield
  34    4      image size             像素数据大小(不压缩可设 0)
  38    4      水平 DPI               像素/米
  42    4      垂直 DPI               像素/米
  46    4      调色板颜色数           0=默认
  50    4      重要颜色数             0=所有
54      ...    像素数据               从这里开始
```

**关键**:

- 文件头 14 字节,信息头 40 字节(标准),总 54 字节
- 像素数据偏移 = 54(标准 BMP),但可能更多(如有调色板)
- **height 是 i32**:正数 bottom-up(默认),负数 top-down
- **bpp 决定每像素字节**:24 bpp = 3 字节(BGR),32 bpp = 4 字节(BGRA)

### 三大坑

#### 坑 1:BGR vs RGB

Windows GDI(Graphics Device Interface)历史原因,BMP 像素字节顺序是 **BGR**(蓝-绿-红),不是 R-G-B。

```
24-bit BMP 一个像素的 3 字节:
  byte[0] = Blue
  byte[1] = Green
  byte[2] = Red
```

读取时要手动 swap:

```rust
let b = bytes[i];
let g = bytes[i + 1];
let r = bytes[i + 2];
let pixel_u32 = (r << 16) | (g << 8) | b;  // 0x00RRGGBB
```

**为什么不标准化为 RGB?** 历史原因——1980 年代 OS/2 和 Windows 设计 BMP 时显示硬件用 BGR 顺序。不同格式不同顺序:

- BMP / Windows GDI:BGR(little-endian 传统)
- PNG / OpenGL:RGB(big-endian 传统)

**本质都是历史包袱**——选了某顺序就不能改(否则破坏兼容)。

#### 坑 2:bottom-up vs top-down

标准 BMP 的像素数据是 **bottom-up**——从最下面一行开始存,往上走。

```
像素数据在文件里的排列(bottom-up):

  [最后一行的像素][倒数第二行]...[第一行的像素]
       ↑ 文件偏移小          ↑ 文件偏移大
```

**为什么这样**:CRT 显像管从下往上扫描(电子枪物理特性)。早期 BMP 是给 CRT 用的,直接按硬件顺序存。

**结果**:你读完所有像素后,第一行像素是文件的最后一段,需要**翻转**:

```rust
// 读完后,数据是 bottom-up
// 翻转成 top-down
for y in 0..height / 2 {
    for x in 0..width {
        let top_idx = y * width + x;
        let bot_idx = (height - 1 - y) * width + x;
        pixels.swap(top_idx, bot_idx);
    }
}
```

或者更简单:**读的时候直接按 top-down 顺序读**:

```rust
for y in 0..height {
    let file_y = height - 1 - y;  // 文件里的行号(反过来)
    for x in 0..width {
        let byte_offset = ...;  // 算 file_y 那行的字节位置
        let pixel = read_pixel(bytes, byte_offset);
        pixels[y * width + x] = pixel;  // 直接放到 y 行
    }
}
```

#### 坑 3:row padding

BMP 规定**每行字节数必须是 4 的倍数**。但 24-bit BMP 一个像素 3 字节,一行 N 个像素 = 3N 字节,**不一定是 4 的倍数**。

例:width = 10 像素,24 bpp → 一行 30 字节。30 不是 4 的倍数,要 pad 2 字节凑 32。

```
row_stride = ((width * 3 + 3) / 4) * 4  // 上取整到 4 倍数
// width=10:row_stride = ((30+3)/4)*4 = 32
// width=20:row_stride = ((60+3)/4)*4 = 64
// width=100:row_stride = ((300+3)/4)*4 = 304
```

**padding 字节是垃圾值**,读取时跳过。

**32-bit BMP 无 padding 问题**:每像素 4 字节,一行 4N 字节,自然 4 倍数。

### 解析流程

```rust
fn load_bmp(path: &str) -> Result<BmpImage, BmpError> {
    let bytes = std::fs::read(path)?;  // 读整个文件

    // 1. 验证最小长度
    if bytes.len() < 54 {
        return Err(BmpError::TooShort);
    }

    // 2. 验证魔数
    if &bytes[0..2] != b"BM" {
        return Err(BmpError::NotBmp);
    }

    // 3. 读文件头
    let pixel_data_offset = u32::from_le_bytes(bytes[10..14].try_into().unwrap()) as usize;

    // 4. 读信息头
    let header_size = u32::from_le_bytes(bytes[14..18].try_into().unwrap());
    let width = i32::from_le_bytes(bytes[18..22].try_into().unwrap());
    let height = i32::from_le_bytes(bytes[22..26].try_into().unwrap());
    let bpp = u16::from_le_bytes(bytes[28..30].try_into().unwrap());
    let compression = u32::from_le_bytes(bytes[30..34].try_into().unwrap());

    // 5. 验证支持
    if compression != 0 {
        return Err(BmpError::CompressedNotSupported);
    }
    if bpp != 24 && bpp != 32 {
        return Err(BmpError::UnsupportedBpp(bpp));
    }

    // 6. 处理 height 符号
    let height_abs = height.abs();
    let top_down = height < 0;  // 负 height = top-down

    // 7. 读像素数据
    let bytes_per_pixel = (bpp / 8) as usize;
    let row_size_unpadded = width as usize * bytes_per_pixel;
    let row_stride = (row_size_unpadded + 3) & !3;  // 上取整到 4 倍数

    let mut pixels = vec![0u32; (width as usize) * (height_abs as usize)];

    for y in 0..height_abs as usize {
        // bottom-up:文件第 y 行(从下数)→ 我们要放到 pixels 第 y 行(从上数)
        // top-down:文件第 y 行(从上数)→ pixels 第 y 行
        let file_y = if top_down { y } else { height_abs as usize - 1 - y };
        let row_start = pixel_data_offset + file_y * row_stride;
        for x in 0..width as usize {
            let pixel_offset = row_start + x * bytes_per_pixel;
            let (r, g, b, a);
            if bpp == 24 {
                b = bytes[pixel_offset];
                g = bytes[pixel_offset + 1];
                r = bytes[pixel_offset + 2];
                a = 255;
            } else {
                b = bytes[pixel_offset];
                g = bytes[pixel_offset + 1];
                r = bytes[pixel_offset + 2];
                a = bytes[pixel_offset + 3];
            }
            pixels[y * width as usize + x] = ((a as u32) << 24)
                | ((r as u32) << 16)
                | ((g as u32) << 8)
                | (b as u32);
        }
    }

    Ok(BmpImage { width: width as u32, height: height_abs as u32, pixels })
}
```

**关键 Rust 特性**:

- `u32::from_le_bytes(bytes[10..14].try_into().unwrap())` —— Little-Endian 读取。`try_into` 把 `&[u8]` 转成 `&[u8; 4]`(固定大小数组)。`from_le_bytes` 把 4 字节合成 u32(假设 little-endian)。
- `width.abs()` / `height.abs()` —— 取绝对值。如果 height 是 -100(表示 top-down),abs = 100。
- `(value + 3) & !3` —— 上取整到 4 倍数。`& !3` 把低 2 位清零(等价于 round down to 4),`+3` 先加 3 让 up round 生效。
- `vec![0u32; W * H]` —— 预分配 + 零初始化。比逐个 push 快。

### Little-Endian vs Big-Endian

**字节序**(endianness)—— 多字节整数在内存里怎么排。

- **Little-Endian**(LE):低位字节先。`u32 = 0x12345678`,内存里 `[0x78, 0x56, 0x34, 0x12]`(低位 0x78 在前)
- **Big-Endian**(BE):高位字节先。`u32 = 0x12345678`,内存里 `[0x12, 0x34, 0x56, 0x78]`

x86 / x86_64 CPU 是 LE。ARM / PowerPC 可以是 BE 或 LE(可切换)。**BMP 文件总是 LE**(Windows x86 传统)。

**Rust 标准库**:`from_le_bytes`(明确 LE)、`from_be_bytes`(明确 BE)、`from_ne_bytes`(本机字节序,匹配 CPU)。

**踩坑预警**:如果你在 x86 上用 `from_ne_bytes` 读 BMP,正常工作(x86 是 LE)。但移植到 BE 平台(某些嵌入式)就会出错。**正确做法**:文件格式相关的读法用 `from_le_bytes` / `from_be_bytes`,不用 `from_ne_bytes`。

### 验证 BMP 文件:hex dump

```bash
# 用 Linux 的 xxd 看一个 BMP 的二进制
xxd test.bmp | head
# 输出(每行 16 字节):
# 00000000: 424d 3604 0000 0000 0000 3600 0000 2800  BM6...........6...
# 00000010: 0000 0a00 0000 0a00 0000 0100 1800 0000  ................

# 解析:
# 42 4d = "BM"(魔数)
# 36 04 00 00 = 0x436 = 1078 字节(文件大小)
# 00 00 00 00 = 保留
# 36 00 00 00 = 0x36 = 54(像素数据偏移)
# 28 00 00 00 = 0x28 = 40(信息头大小)
# 0a 00 00 00 = 0x0a = 10(width)
# 0a 00 00 00 = 0x0a = 10(height,bottom-up)
# 01 00 = 1(planes)
# 18 00 = 0x18 = 24(bpp)
# 00 00 00 00 = 0(不压缩)
```

每字段都是 little-endian 4 字节,所以 `36 04 00 00` 实际值是 `0x00000436 = 1078`。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏加载图片是**资产管线**(asset pipeline)的第一步。主流格式:

- **TGA**:游戏行业传统,简单无损,支持 alpha。Quake / Doom 用
- **PNG**:通用,无损压缩。现代游戏主流
- **DDS**:DirectX 标准的 GPU 纹理格式,支持 mipmap 和块压缩
- **KTX2**:跨平台 GPU 纹理格式(Khronos 标准)
- **BMP**:Windows 传统,简单。教学用

**Casey 选 BMP 教学的理由**:**渐进式学习**。BMP 无压缩 → PNG 加 LZ77+Huffman → DDS 加 GPU 块压缩。每一步都是上一步加新概念。

游戏运行时的资产加载流程:

1. **打包阶段**(build time):源文件(PSD / PNG)→ 压缩 / 转换 → 运行时格式
2. **加载阶段**(run time):运行时格式 → 内存 → GPU(如果用 GPU)

### 3.3 · 🐧 Linux 系统编程视角

读文件有几种方式:

**方式 1:`std::fs::read`(Casey 选这个)**

```rust
let bytes = std::fs::read("test.bmp")?;
// 一次性读完整个文件到 Vec<u8>
```

简单。对小文件(几 MB)完全够。大文件浪费内存(全读)。

**方式 2:`std::io::Read` 流式**

```rust
use std::io::Read;
let mut file = std::fs::File::open("test.bmp")?;
let mut header = [0u8; 54];
file.read_exact(&mut header)?;
// 只读 header
// 然后按需读像素数据
let mut row = vec![0u8; row_stride];
file.read_exact(&mut row)?;
```

流式,内存友好。适合超大文件。

**方式 3:`mmap`(内存映射)**

```rust
use memmap2::Mmap;
let file = std::fs::File::open("test.bmp")?;
let mmap = unsafe { Mmap::map(&file)? };
// mmap[0..54] 是 header,mmap[54..] 是像素数据
```

OS 按需读页。大文件友好。Day 436+ PNG 可能用 mmap。

### 3.4 · 🦀 Rust 生态视角

Rust 表达二进制解析有几种方式:

**方式 1:手动 `from_le_bytes`(Casey 风格)**

```rust
let width = i32::from_le_bytes(bytes[18..22].try_into().unwrap());
```

完全控制,但啰嗦。

**方式 2:`#[repr(C)] struct` + unsafe 转换**

```rust
#[repr(C)]
struct BmpFileHeader {
    magic: [u8; 2],
    file_size: u32,
    reserved: u32,
    pixel_offset: u32,
}

let header: &BmpFileHeader = unsafe {
    &*(bytes.as_ptr() as *const BmpFileHeader)
};
```

性能高(无拷贝),但 unsafe,且 padding 问题(`#[repr(C)]` 可能加 padding)。

**方式 3:`nom` crate**(parser combinator)

```rust
use nom::IResult;
use nom::bytes::complete::tag;
use nom::number::complete::le_u32;

fn parse_header(input: &[u8]) -> IResult<&[u8], BmpHeader> {
    let (input, _) = tag("BM")(input)?;
    let (input, file_size) = le_u32(input)?;
    let (input, _) = le_u32(input)?;  // reserved
    let (input, pixel_offset) = le_u32(input)?;
    Ok((input, BmpHeader { file_size, pixel_offset }))
}
```

高级,但学习曲线陡。

**方式 4:`serde + bincode`**

```rust
#[derive(Deserialize)]
struct BmpHeader {
    magic: [u8; 2],
    file_size: u32,
    ...
}
let header: BmpHeader = bincode::deserialize(&bytes)?;
```

适合"规范"格式,但 BMP 字段顺序需要手动控制。

**Casey 选方式 1**(教学清晰,完全控制)。生产代码可能选方式 3(`nom`)或专门库(`image` crate)。

**`image` crate**:Rust 主流图片库,支持 PNG/JPEG/GIF/BMP/WEBP 等:

```rust
use image::GenericImageView;
let img = image::open("test.bmp")?;
println!("{:?}", img.dimensions());
```

Casey **不用** `image` crate——他要教你**怎么解析**,不是**怎么用**。学完 HH 你完全能自己实现 `image` crate 的功能。

| TGA | 无压缩 / RLE | 游戏 / Quake | HH 不用 |
| DDS | GPU 原生(BC 压缩) | 3D 游戏 | HH 不用 |
| WebP | 有损 + 无损 | Web | HH 不用 |

### 4.3 下级

- **BITMAPFILEHEADER** —— 文件头(14 字节)
- **BITMAPINFOHEADER** —— 信息头(40 字节)
- **BGR vs RGB** —— 像素字节顺序
- **bottom-up vs top-down** —— 行存储顺序
- **Row padding** —— 4 字节对齐
- **bpp**(bits per pixel)—— 位深

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:把图片存成二进制文件,可跨平台读取。

| 语境 | "图片格式"叫法 | 核心思想 |
|---|---|---|
| 静态图片 | BMP / PNG / JPEG | header + 像素 |
| 动画 | GIF / APNG / WebP | header + 帧序列 |
| 视频 | MP4 / WebM / AV1 | header + 编码帧 |
| 3D 模型 | OBJ / glTF / FBX | header + 几何 |
| 音频 | WAV / MP3 / FLAC | header + 样本 |
| 文档 | PDF / DOCX / EPUB | header + 内容 |

所有这些场景的核心思想相同:**header(元数据)+ payload(实际内容)**。

### 字节序的历史

- **1980s**:x86 LE,PowerPC / 68000 BE,网络字节序(BE)标准化
- **1990s**:Windows 在 x86 上用 LE,BMP 也 LE
- **2000s**:ARM 双模式(可切换),手机 / 嵌入式各有
- **2010s**:网络用 BE(RFC 标准),文件格式各有
- **2020s**:WebAssembly 默认 LE

BMP 的 LE 是 Windows x86 时代的产物。PNG 的 BE 是网络 / Unix 传统的产物。

### 图像格式演化

- **1970s**:GIF(CompuServe),256 色,LZW 压缩
- **1980s**:BMP(Windows / OS2),无压缩
- **1990s**:JPEG(照片),PNG(GIF 替代品,无损)
- **2000s**:WebP(Google),AVIF(下一代)
- **2020s**:JPEG XL(新一代照片格式)

Casey HH 教 BMP → PNG 路径,跳过 JPEG(因为 JPEG 不适合游戏,有 alpha 问题)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:BMP 用 BGR 顺序,但 PNG 用 RGB 顺序。为什么不标准化?

**参考解答**:**历史原因**,选了就不能改(否则破坏兼容)。

- **BMP / Windows GDI**:1980 年代设计,显示硬件用 BGR 顺序(可能是某种硬件优化)
- **PNG**:1990 年代设计,Unix / 网络传统,用 big-endian RGB
- **OpenGL**:RGB 顺序,但 internal format 灵活(可指定 BGRA)

字节序也是类似情况:

- x86 LE / PowerPC BE / ARM 双模式
- 网络字节序(BE)标准化,但文件格式各有

**为什么没人改**:已有的 BMP 文件都是 BGR,改成 RGB 就读不了旧文件。已有的工具(Windows GDI)假设 BGR。改了破坏所有依赖。**行业成本太高**。

**程序员视角**:接受现实,知道每种格式的字节序,**用对应的 `from_le_bytes` / `from_be_bytes` 读**。不要假设。

**参考解答**:

```rust
// src/main.rs
// cargo new --bin bmp_loader && cd bmp_loader

#[derive(Debug)]
enum BmpError {
    IoError(std::io::Error),
    TooShort,
    NotBmp,
    UnsupportedBpp(u16),
    CompressedNotSupported,
    TryFromSlice,
}

impl From<std::io::Error> for BmpError {
    fn from(e: std::io::Error) -> Self { BmpError::IoError(e) }
}
impl From<std::array::TryFromSliceError> for BmpError {
    fn from(_: std::array::TryFromSliceError) -> Self { BmpError::TryFromSlice }
}

struct BmpImage {
    width: u32,
    height: u32,
    pixels: Vec<u32>,  // 0x00RRGGBB
}

fn load_bmp(path: &str) -> Result<BmpImage, BmpError> {
    let bytes = std::fs::read(path)?;

    if bytes.len() < 54 { return Err(BmpError::TooShort); }
    if &bytes[0..2] != b"BM" { return Err(BmpError::NotBmp); }

    let pixel_offset = u32::from_le_bytes(bytes[10..14].try_into()?) as usize;
    let width = i32::from_le_bytes(bytes[18..22].try_into()?);
    let height = i32::from_le_bytes(bytes[22..26].try_into()?);
    let bpp = u16::from_le_bytes(bytes[28..30].try_into()?);
    let compression = u32::from_le_bytes(bytes[30..34].try_into()?);

    if compression != 0 { return Err(BmpError::CompressedNotSupported); }
    if bpp != 24 && bpp != 32 { return Err(BmpError::UnsupportedBpp(bpp)); }

    let height_abs = height.abs() as u32;
    let top_down = height < 0;
    let bytes_per_pixel = (bpp / 8) as usize;
    let row_unpadded = width as usize * bytes_per_pixel;
    let row_stride = (row_unpadded + 3) & !3;

    let mut pixels = vec![0u32; (width as usize) * (height_abs as usize)];

    for y in 0..height_abs as usize {
        let file_y = if top_down { y } else { (height_abs as usize) - 1 - y };
        let row_start = pixel_offset + file_y * row_stride;
        for x in 0..width as usize {
            let offset = row_start + x * bytes_per_pixel;
            let b = bytes[offset] as u32;
            let g = bytes[offset + 1] as u32;
            let r = bytes[offset + 2] as u32;
            // 0x00RRGGBB
            pixels[y * width as usize + x] = (r << 16) | (g << 8) | b;
        }
    }

    Ok(BmpImage { width: width as u32, height: height_abs, pixels })
}

fn main() {
    // 如果用户传了 BMP 路径,加载它
    let args: Vec<String> = std::env::args().collect();
    if args.len() < 2 {
        println!("Usage: {} <file.bmp>", args[0]);
        println!("Generate a test BMP with: convert -size 10x10 xc:red test.bmp");
        return;
    }
    match load_bmp(&args[1]) {
        Ok(img) => {
            println!("Loaded: {}x{}", img.width, img.height);
            println!("First pixel: 0x{:06x}", img.pixels[0]);
        }
        Err(e) => println!("Error: {:?}", e),
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    fn make_24bit_bmp(width: usize, height: usize, color: (u8, u8, u8)) -> Vec<u8> {
        let (r, g, b) = color;
        let bpp = 24;
        let bytes_per_pixel = 3;
        let row_unpadded = width * bytes_per_pixel;
        let row_stride = (row_unpadded + 3) & !3;
        let pixel_data_size = row_stride * height;
        let file_size = 54 + pixel_data_size;

        let mut bytes = Vec::new();
        // File header (14 bytes)
        bytes.extend(b"BM");                      // magic
        bytes.extend(&(file_size as u32).to_le_bytes());
        bytes.extend(&0u32.to_le_bytes());         // reserved
        bytes.extend(&54u32.to_le_bytes());        // pixel offset
        // Info header (40 bytes)
        bytes.extend(&40u32.to_le_bytes());        // header size
        bytes.extend(&(width as i32).to_le_bytes());
        bytes.extend(&(height as i32).to_le_bytes());  // positive = bottom-up
        bytes.extend(&1u16.to_le_bytes());         // planes
        bytes.extend(&(bpp as u16).to_le_bytes());
        bytes.extend(&0u32.to_le_bytes());         // compression
        bytes.extend(&(pixel_data_size as u32).to_le_bytes());
        bytes.extend(&0u32.to_le_bytes());         // h dpi
        bytes.extend(&0u32.to_le_bytes());         // v dpi
        bytes.extend(&0u32.to_le_bytes());         // colors
        bytes.extend(&0u32.to_le_bytes());         // important colors

        // Pixel data (bottom-up)
        for _row in 0..height {
            for _x in 0..width {
                bytes.push(b);
                bytes.push(g);
                bytes.push(r);
            }
            // padding
            for _ in 0..(row_stride - row_unpadded) {
                bytes.push(0);
            }
        }
        bytes
    }

    #[test]
    fn rejects_non_bmp() {
        let bad = b"XXrest of file is more than 54 bytes....................";
        let path = "/tmp/test_bad.bmp";
        std::fs::write(path, bad).unwrap();
        let result = load_bmp(path);
        assert!(matches!(result, Err(BmpError::NotBmp)));
    }

    #[test]
    fn loads_24bit_red() {

    }
```

**关键代码细节**:

- `bytes[10..14].try_into()?` —— `try_into` 把 `&[u8]`(slice)转 `&[u8; 4]`(固定大小)。可能失败(长度不匹配),所以返回 Result。`?` 自动 unwrap。
- `From<std::array::TryFromSliceError> for BmpError` —— 让 `try_into` 的错误自动转成 `BmpError`。Rust 的 `?` 操作符依赖这个 trait。
- `bytes.extend(&x.to_le_bytes())` —— `extend` 把 slice 内容追加到 Vec。`to_le_bytes` 把 u32 转成 4 字节 LE 数组。
- 测试用 `make_24bit_bmp` 手动构造 BMP 字节流——避免依赖外部 ImageMagick。

```rust
// src/main.rs (扩展 Lv2)

impl BmpImage {
    fn save_as_ppm(&self, path: &str) -> std::io::Result<()> {
        use std::io::Write;
        let mut f = std::fs::File::create(path)?;
        writeln!(f, "P6\n{} {}\n255", self.width, self.height)?;
        let mut bytes = Vec::with_capacity(self.pixels.len() * 3);
        for &p in &self.pixels {
            let r = ((p >> 16) & 0xFF) as u8;
            let g = ((p >> 8) & 0xFF) as u8;
            let b = (p & 0xFF) as u8;
            bytes.push(r); bytes.push(g); bytes.push(b);
        }
        f.write_all(&bytes)
    }
}

fn main() {
    let args: Vec<String> = std::env::args().collect();
    let path = if args.len() >= 2 { &args[1] } else { "test.bmp" };
    match load_bmp(path) {
        Ok(img) => {
            println!("Loaded {}: {}x{}", path, img.width, img.height);
            println!("First pixel: 0x{:06x}", img.pixels[0]);
            println!("Last pixel: 0x{:06x}", img.pixels[img.pixels.len() - 1]);

            // 转 PPM 便于查看
            let ppm_path = "output.ppm";
            img.save_as_ppm(ppm_path).expect("save ppm");
            println!("Wrote {}", ppm_path);
            println!("View with: feh {}", ppm_path);
        }
        Err(e) => {
            eprintln!("Error: {:?}", e);
            eprintln!("\nGenerate a test BMP with ImageMagick:");
            eprintln!("  sudo pacman -S imagemagick");
            eprintln!("  convert -size 32x32 xc:red test.bmp");

        }
    }
```
