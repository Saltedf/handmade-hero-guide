# Day 026 · 游戏架构入门

> Phase 1 结束时,你的程序能开窗、显示像素、读键盘、播音频——所有代码堆在 `main.rs` 里几百行。Phase 2 第一天,Casey 暂停编码,做一件被初学者反复跳过却决定后面 600 集生死的事:**把"游戏代码"和"渲染代码"再分一层**。

## 0 · 为什么要有这一天

Phase 1 你写的代码大概长这样:平台层把输入、framebuffer、音频回调交给一段"游戏代码",游戏代码自己读输入、改状态、把像素 push 到 framebuffer。这套结构在 Day 1-25 完全够用,因为游戏内容只有"按 A 键,屏幕变绿"这种 demo 级逻辑。

但只要你想做下面任何一件事,就立刻撞墙:

- 想给游戏加**网络多人**:你发现"渲染"和"逻辑"耦合——同一份代码既改玩家位置又画玩家像素,你没法把"画"的部分隔离出去,因为网络只关心逻辑。
- 想做**回放系统**(录像):理论上是"记录每帧输入,重放"。但你的逻辑层直接画像素,重放时无法判断"现在该不该画"——状态和绘制搅在一起。
- 想做**单元测试**:测一个函数"玩家攻击怪物,怪物扣 10 血"。但这个函数最后一句是 `framebuffer.draw_text("hit!")`,你没有 framebuffer 就跑不了测试。
- 想**切到 OpenGL 渲染**:你发现逻辑代码里到处是 `framebuffer[pixel_index] = ...`,要切 GPU 渲染,几千行代码全要重写。
- 想做**热重载**(改代码不重启游戏):你的逻辑函数直接持有 framebuffer 引用,函数指针签名一变,热重载框架立刻崩。

这些问题的**根因都是一个**:你的游戏代码既"决定世界长什么样"又"决定怎么画"。两个职责搅在同一个函数里,你想换掉其中一个就动不了。

Casey 这一天提出一个**铁律**:**游戏代码内部再分两层**——一层只改世界状态(逻辑层),一层只读世界状态生成"画什么"的指令(渲染层)。这就是经典的 Model-View 分离,但 Casey 用游戏开发的视角重新讲了一遍,后面 600+ 集每一集都在遵守这个约定。

心理锚点:看完这集,你应该能用一句话回答"为什么游戏代码内部要分逻辑层和渲染层",能用一张图描述 Casey 的"三明治分层"。如果做不到,先停下来,把 §2 反复读到你能在白板上画出三层结构并解释每一层做什么为止。Phase 2 后面的 44 集,每一集都在这个骨架上长肉。

## 1 · Casey 今天做了什么

Casey 这一天**几乎不写新代码**,他在画板上做架构讨论:

1. 回顾 Day 011 已有的"平台层 vs 游戏层"两层分离,指出它**不够**:游戏层内部还需要进一步拆分
2. 提出**三明治分层**:平台层 → 游戏逻辑层 → 渲染层 → 渲染器(framebuffer),每层只能调下一层
3. 解释这个分层的**三大收益**:可测试(逻辑层不依赖渲染)、跨平台(换渲染后端不动逻辑)、可重放(记录输入能复现整局游戏)
4. 在白板上画出 `GameState` 结构体雏形,把"位置"、"血量"、"目标"等状态字段和 `update()`、`render()` 方法**严格分离**
5. 给出一个明确的禁忌:**逻辑层永远不持有 framebuffer 引用**,所有渲染必须通过 push command(虽然 push buffer 的完整实现要到 Day 88 才出现,Day 026 已经把"将来要这么做"的契约定下来)
6. 最后强调:这一集的目标不是写代码,是**立规矩**。后面 600+ 集每一集都在遵守这套规矩。

教学价值极高。Casey 自己说"如果这集你跳过了,后面 30 集你会不断回来翻"。

## 2 · 心智模型

### 类比:三明治分层

你吃过三明治吗?顶层是一片面包,中间夹肉,底层又一片面包。**每一层只跟相邻那层打交道**:肉不会跳出去跟最外面的桌子说话,顶层面包也不会伸进肉里。

游戏代码就是这样的三明治:

```
┌─────────────────────────────────┐
│  平台层(Phase 1 已分好)         │ ← 开窗、读输入、播音频
└──────────────┬──────────────────┘
               │ 传入:GameInput + GameMemory + dt
               ▼
┌─────────────────────────────────┐
│  游戏代码(handmade.rs)         │
│  ┌───────────────────────────┐  │
│  │ 游戏逻辑层                 │  │ ← 决定"世界现在长什么样"
│  │  • 实体系统                │  │
│  │  • 物理 / AI               │  │
│  │  • 战斗规则                │  │
│  │  • 地图状态                │  │
│  └─────────────┬─────────────┘  │
│                │ 只产出"画什么"指令
│                ▼                │
│  ┌───────────────────────────┐  │
│  │ 渲染层                     │  │ ← 决定"怎么画成像素"
│  │  • push bitmap             │  │
│  │  • push rect               │  │
│  │  • push text               │  │
│  └─────────────┬─────────────┘  │
└────────────────┼────────────────┘
                 │ 最终:像素写入 framebuffer
                 ▼
┌─────────────────────────────────┐
│  渲染器(renderer / framebuffer)│
└─────────────────────────────────┘
```

**关键约束**:每一层只调下一层。逻辑层**不能**直接写 framebuffer,只能往渲染层"下命令"(push 一条 bitmap 指令)。渲染层**不能**改游戏状态,只能读状态生成像素。

### 为什么必须分:三个具体例子

#### 例子 1:回放系统

假设你想"录像":把整局游戏存成文件,下次加载重放。

最朴素的做法是**每帧录 framebuffer**(像录视频)。但 1280×720×4 字节 × 60 帧/秒 × 60 秒 = **12 GB/分钟**。不可行。

正确做法是**只录输入**。每帧 8 字节的 GameInput,60 帧/秒 = 480 字节/秒,1 小时游戏 = 1.7 MB。小到可以邮件传。

但"录输入能精确复现游戏"这件事**只有在逻辑层和渲染层分离时才成立**。如果你的逻辑函数里有 `rand()`(随机数),重放时随机数序列变了,世界就乱了。Casey 在 Day 026 立规矩:**逻辑层必须是"输入 → 状态"的纯函数**(给定相同输入,产出的状态一定相同),所有随机数都来自一个**种子可控制的 RNG**(random number generator),不能依赖系统时间、线程 ID 这种"不可重放"的源。

渲染层则不需要可复现——像素怎么画不影响游戏状态,即使两次画得略有不同(浮点抖动),游戏逻辑依然正确。

#### 例子 2:换渲染后端

Day 1-234 你用 CPU 软渲染(逐像素写 framebuffer)。Day 235 切 OpenGL。如果逻辑层和渲染层耦合,这次切换要改上千行。如果分离,**逻辑层一行不改**,只改渲染层的"push bitmap 命令"如何变成 OpenGL 调用。

这就是 Day 026 立规矩的真正威力:**让代码的"骨架"和"皮肤"可以独立替换**。

#### 例子 3:单元测试

测"玩家攻击怪物,怪物扣 10 血":

```rust
#[test]
fn player_attack_reduces_monster_hp() {
    let mut state = GameState::new();
    state.spawn_monster_at(100, 100);
    state.player.pos = Vec2::new(95, 95);  // 玩家靠近怪物
    state.player.attack(&mut state);       // 攻击
    assert_eq!(state.monsters[0].hp, 90);  // 怪物扣 10 血
}
```

这个测试**不需要 framebuffer、不需要窗口、不需要 GPU**。逻辑层是纯 Rust 代码,可以 `cargo test` 在 CI(持续集成)里跑。

如果逻辑层和渲染耦合,你测试时必须先开一个 winit 窗口——CI 服务器没显示器,测试直接挂。

### Casey 的 GameState 结构

Casey 这集在白板上画的结构(Rust 翻译):

```rust
// 游戏状态:逻辑层拥有,渲染层只能读
pub struct GameState {
    pub player: Player,           // 玩家
    pub monsters: Vec<Monster>,   // 怪物列表
    pub world: World,             // 地图状态
    pub time: f32,                // 游戏内时间(秒)
    pub score: i32,               // 得分
}

pub struct Player {
    pub pos: Vec2,                // 位置(世界坐标,像素)
    pub vel: Vec2,                // 速度(像素/秒)
    pub hp: i32,                  // 血量
    pub facing: Direction,        // 朝向(用于选动画)
}

pub enum Direction { Left, Right, Up, Down }

impl GameState {
    /// 逻辑层入口:每帧调用,改状态
    pub fn update(&mut self, input: &GameInput, dt: f32) {
        // 1. 处理输入(玩家)
        self.player.update(input, dt, &mut self.world);

        // 2. 更新怪物 AI
        for m in &mut self.monsters {
            m.update(dt, &self.player);
        }

        // 3. 战斗判定、得分计算、世界事件...
        self.resolve_combat();
        self.update_score();

        self.time += dt;
    }

    /// 渲染层入口:每帧调用,读状态生成渲染指令
    /// 注意:&self,不改状态!
    pub fn render(&self, render_buf: &mut RenderBuf) {
        // 1. 画世界
        self.world.render(render_buf);

        // 2. 画怪物
        for m in &self.monsters {
            render_buf.push_bitmap(m.pos, m.bitmap_id);
        }

        // 3. 画玩家
        render_buf.push_bitmap(self.player.pos, self.player.bitmap_id());

        // 4. 画 UI(血量、得分)
        render_buf.push_text(10, 10, &format!("HP: {}", self.player.hp));
    }
}
```

**注意几个细节**:

- `update` 签名是 `&mut self`(可变借用),`render` 签名是 `&self`(只读借用)。Rust 的所有权系统**强制**执行了"渲染不改状态"的契约——你写 `render` 时如果不小心改了 `self.player.hp`,编译器立刻报错。
- `GameInput` 是一个跨层传递的"输入快照"——平台层把键盘、鼠标、手柄状态打包成这个结构,逻辑层消费。这个结构 Day 027 详谈。
- `RenderBuf` 是渲染指令的容器(后面 Day 88 实现)。Day 026 暂时直接画 framebuffer,但**接口**已经按"push 命令"的形状写了。

### "铁律"的精确定义

Casey 在这集给出**三条铁律**:

1. **逻辑层不持有 framebuffer 引用**。任何 `&mut [u32]`(framebuffer)只能出现在渲染层。
2. **渲染层不改 GameState**。`render` 函数签名只能是 `&self`,不能是 `&mut self`。
3. **逻辑层不调用 OS API**。`open()`、`read()`、`sleep()`、`rand()` 这种"和外界打交道"的函数只能在平台层或资产加载层出现。逻辑层是**纯函数**。

这三条规则从 Day 026 开始到 Day 667,**一行不改**。后面 Casey 偶尔破例(比如临时加调试代码),都会强调"这是破例,正常逻辑不该这样"。

### 一句话总结

> 游戏代码 = 纯函数式逻辑层 + 副作用式渲染层。
>
> 逻辑层决定世界**是什么**,渲染层决定世界**看起来什么样**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发社区对"逻辑/渲染分离"几乎是一边倒的支持,但在**怎么分**上有几个流派:

**流派 A:Immediate-mode(立即模式)**。Casey 早期(Phase 2)、Casey 的 hero —— Jef Bloodworth 的 Dear ImGui 都属于这种。逻辑层每帧调一次 `render(state, framebuffer)`,所有渲染命令当场执行。优点:简单,无中间状态;缺点:换 GPU 渲染要大改。

**流派 B:Retained-mode scene graph(保留模式场景图)**。Unity / Unreal / Godot 用这种。游戏对象挂在场景树(scene graph)上,引擎遍历树生成渲染指令。优点:换渲染后端只改引擎;缺点:层和层之间多了一层间接,初学者看不到全貌。

**流派 C:Push buffer / Command buffer(命令缓冲)**。这是 Casey Day 88+ 的最终选择,也是主流 AAA 引擎用的。逻辑层 push 一串"draw bitmap at X,Y"的命令到 buffer,渲染器独立消费 buffer。这就是 Day 026 铺垫的目标。

| 流派 | 代表 | 适合 |
|---|---|---|
| Immediate | HH 早期、Dear ImGui | 教学项目、调试 UI |
| Retained (scene graph) | Unity / Godot | 商业引擎 |
| Push buffer | HH 后期、AAA 引擎 | 高性能专业项目 |

Casey 从 A 演化到 C,中间过程你能学到"为什么 A 不够"——这是宝贵经验。

**陷阱**:很多新手把 `render(state)` 写成 `render(state, framebuffer, time_of_day, weather, ...)` —— 参数越来越多。这是没分清"渲染的输入"和"世界的状态"。世界状态(玩家在哪、怪物死没死)在 `state` 里;渲染输入(光照、雾效)是**渲染层自己关心的细节**,不该污染逻辑层接口。Casey 的做法:`GameState` 只放"逻辑层关心的",渲染层另外有自己的 `RenderState`(相机位置、屏幕大小、调试图层开关)。

### 3.2 · 🐧 Linux 系统编程视角

Linux 系统编程里"分层"是**核心哲学**。对比一下:

| HH 分层 | Linux 类比 |
|---|---|
| 平台层(开窗、读输入) | VFS(虚拟文件系统):统一接口,后端可换 |
| 游戏逻辑层 | syscall handler:纯逻辑,不碰硬件 |
| 渲染层 | device driver:把高层命令翻译成硬件操作 |
| 渲染器 / GPU | 实际硬件 |

Linux 内核的设计原则之一就是**机制和策略分离**(mechanism vs policy)。比如 `mmap` 是机制(怎么映射内存),映射到哪个 fd、什么权限是策略(用户态决定)。Casey 的"逻辑 / 渲染分离"本质是同一个思想:**机制(逻辑)和呈现(渲染)分离**。

Linux 用户态工具链也体现这个哲学:

- **Mesa**:OpenGL 实现,后端可换(AMD/Intel/Nouveau 驱动)
- **PipeWire**:音频服务器,后端可换(ALSA/JACK/PulseAudio)
- **winit**:窗口抽象,后端可换(Wayland/X11)

这些都是"平台层"的实例。**Linux 文化推崇"做一件事,做好"**——Unix 哲学。Casey 的"三明治"和 Unix 哲学同源。

**Arch Linux 验证**:

```bash
# 看 Mesa 怎么分层
pacman -Ql mesa | grep -E "\.so$" | head
# /usr/lib/libGLX_mesa.so.0     ← GLX 的 Mesa 实现
# /usr/lib/libEGL_mesa.so.0     ← EGL 的 Mesa 实现
# 这就是"机制(Mesa)和策略(具体硬件)分离"

# 看 PipeWire 的后端抽象
pacman -Ql pipewire | grep -E "spa" | head
# SPA = Simple Plugin API,允许不同后端(ALSA/Bluez/...)接入
```

### 3.3 · 🦀 Rust 生态视角

Rust 的所有权系统**天生适合**三明治分层,因为它能**编译时强制**"渲染层不改状态"的契约。看下面两个签名:

```rust
// ✓ 正确:render 用 &self(只读),不可能改 state
impl GameState {
    pub fn render(&self, render_buf: &mut RenderBuf) { ... }
}

// ✗ 错误:render 用 &mut self,逻辑层契约被破坏
impl GameState {
    pub fn render(&mut self, render_buf: &mut RenderBuf) { ... }
}
```

Rust 编译器会拒绝第二种写法吗?**不会直接拒绝**,但只要你在 render 里不小心写了 `self.player.hp -= 1`,逻辑层 bug 就产生了。所以 Casey 的"铁律"在 Rust 里要靠**纪律 + 编译器辅助**来执行:你的 render 函数**必须**写 `&self`,这是团队约定,违反的 PR 不通过。

更激进的 Rust 写法:**用类型系统强制铁律**。让 GameState 不能持有 framebuffer:

```rust
/// 标记 trait:实现了这个的类型,逻辑层可以持有
pub trait GameLogicData {}

/// 标记 trait:实现了这个的类型,渲染层可以持有
pub trait RenderData {}

// GameState 实现了 GameLogicData,但**没有** RenderData
impl GameLogicData for GameState {}

// FrameBuffer 实现了 RenderData,但**没有** GameLogicData
impl RenderData for FrameBuffer {}

// 渲染函数只能拿实现了 GameLogicData 的数据(读)和 RenderData 的数据(写)
pub fn render<S: GameLogicData, R: RenderData>(state: &S, render_buf: &mut R) {
    // 编译时保证:state 不能改,render_buf 不能传给逻辑层
}
```

这种"用类型系统编码架构约束"是 Rust 的强项。HH 教学版不必这么极端,**但理解为什么 Rust 比 C 更适合大型游戏代码**,这是关键。

**Rust crate 对照**:

- `bevy_ecs`(https://github.com/bevyengine/bevy)—— Bevy 引擎的 ECS 实现。ECS 本质是"逻辑和渲染分离"的极致形式:数据(Component)和行为(System)完全分开。读 `crates/bevy_ecs/src/system/system.rs` 看系统接口设计。
- `gfx-rs`(https://github.com/gfx-rs/wgpu)—— 跨平台 GPU 抽象。它的核心思路就是 Casey 的"渲染层"——上层只 push 命令,下层(具体 GPU 后端)执行。

### 3.4 · 游戏引擎视角(扩展)

主流游戏引擎的"分层"程度比 Casey 更深:

| 层 | Unity 叫法 | Unreal 叫法 | Godot 叫法 |
|---|---|---|---|
| 平台 | Platform Layer | Application | OS abstraction |
| 逻辑(玩家写的脚本) | MonoBehaviours | Actors + Components | Nodes + Scripts |
| 引擎层(物理、AI) | Subsystems | Modules | Servers |
| 渲染层 | SRP / URP | RHI | RenderingServer |
| GPU | Various backends | DX12 / Vulkan | Vulkan / GLES |

Casey 的"游戏代码内部两层"对应 Unity 的 "MonoBehaviour / Rendering"。Casey 故意只分两层(教学),实际工业引擎分 5+ 层。学完 HH 你看 Unity/Unreal 不会迷失——你知道哪层是哪层。

## 4 · 认知地图

### 4.1 上级

- **Model-View 分离** —— 三明治分层的本质就是 MVC(Model-View-Controller)的简化版,把 Controller 去掉(因为游戏里逻辑层就是 Controller)
- **Single Responsibility Principle**(单一职责原则)—— 一个模块只做一件事,SOLID 原则之一
- **Separation of Concerns**(关注点分离)—— 软件工程的基础概念,把不同"关注点"(逻辑、渲染、IO)分到不同模块
- **Pure function**(纯函数)—— 逻辑层的理想形态:输入相同 → 输出相同,无副作用

### 4.2 同级(并行架构方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 三明治分层(逻辑/渲染分) | 渲染是"读状态生成像素"的纯消费者 | 2D/3D 游戏、教学项目 | ✅ Casey 选了 |
| ECS(Entity-Component-System) | 数据(Component)和行为(System)完全正交 | 大型游戏、Bevy 用 | HH 不用(过重) |
| MVC(Model-View-Controller) | 多一个 Controller 层处理输入路由 | Web 后端、UI 重应用 | HH 不用(2D 游戏不需要) |
| Immediate-mode GUI | 每帧重画,无保留状态 | 调试 UI、Dear ImGui | HH 调试层用 |

### 4.3 下级

- **GameState 结构体** —— 逻辑层拥有的世界状态容器
- **GameInput 结构体** —— 平台层 → 逻辑层的输入快照
- **RenderBuf / Command buffer** —— 逻辑层 → 渲染层的命令容器
- **`update` / `render` 函数对** —— 三明治的核心接口
- **铁律三条** —— 编译器无法强制的契约,靠纪律执行

## 5 · 对照与变奏

### 同一抽象在不同语境下的变体

**问题**:把"逻辑"和"呈现"分开。

| 语境 | "逻辑"叫法 | "呈现"叫法 |
|---|---|---|
| 游戏 | Game logic | Renderer |
| Web 前端 | Model / Store | View / Component |
| 浏览器引擎 | DOM tree | Render tree / Layout |
| 数据库 | Query planner | Storage engine |
| 操作系统 | Syscall handler | Device driver |
| 编译器 | Semantic analysis | Code generation |

所有这些场景的本质都是同一种:**有一份"事实"(状态),有多种"看法"(渲染)**。游戏的渲染只是其中一种看法,你还可以加:日志(把状态序列化到文件)、网络同步(把状态序列化到网络)、调试 UI(把状态画成图表)。

### 历史演化

- **1970s**:游戏代码全堆在一起(pong, space invaders),没有分层概念
- **1980s**:出现"游戏引擎"概念,开始分平台/逻辑
- **1990s**:Quake 把渲染和逻辑明确分开,id Tech 引擎
- **2000s**:Unity / Unreal 普及 ECS 思想
- **2010s**:Data-Oriented Design 兴起,逻辑层数据布局被严格设计
- **2020s**:Bevy 把 ECS 推到极致,逻辑和渲染完全正交

Casey 在 HH 走的是 90 年代风格(简单分层),但教的是"演化思维"——你跟做 667 天,看着代码从一层(Phase 0)到两层(Phase 1)再到三层(Phase 2),最后演化到 ECS 风格(Phase 5+),每一步都理解**为什么**这样改。

### 工业化实现的差别

教学版(Casey):逻辑层和渲染层在同一个二进制里,函数直接调函数。
工业版(Bevy):逻辑层和渲染层可能是**不同进程**(网络同步),或**不同线程**(并行),通过消息队列通信。

教学版让你看到本质,工业版让你看到性能。**先学教学版,再上工业版**,这是 HH 的设计哲学。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 的三条铁律里有一条是"渲染层不改 GameState"。这条铁律用 Rust 类型系统能**强制**执行吗?如果能,怎么写?如果不能,为什么?

**参考解答**:**部分能,完全不能**。

**部分能**:把 `render` 函数签名写成 `fn render(&self, ...)` 而不是 `fn render(&mut self, ...)`。`&self` 是只读借用,Rust 编译器会在编译时拒绝任何修改 `self` 字段的尝试。这是**强制执行**的部分。

**完全不能**:Rust 不能阻止你在 `render` 函数里调用一个**修改全局可变状态**的函数(比如 `unsafe { GLOBAL_COUNTER += 1; }` 或修改一个 `Mutex`、`AtomicUsize`)。这些"绕过 &self 检查"的副作用 Rust 类型系统看不到。

所以 Casey 的"铁律"在 Rust 里**通过约定 + 部分编译器检查**来执行:**render 函数必须是 `&self`**(编译器强制),**render 函数体内不能改全局可变状态**(纪律强制)。在大型 Rust 项目里,这种"约定 + 编译器辅助"的模式非常常见——Rust 不替代纪律,但让违反纪律更难。

### Lv2 · 动手实践

**题**:写一个最小的"三明治分层"骨架。要求:

1. `GameState` 结构体,至少有 `player_pos: Vec2` 和 `score: i32`
2. `GameInput` 结构体,至少有 `move_left: bool`, `move_right: bool`, `score_up: bool`
3. `update(&mut self, input: &GameInput, dt: f32)` —— 逻辑层
4. `render(&self, render_buf: &mut Vec<String>)` —— 渲染层(用 String 模拟渲染指令)
5. 一个 `main` 函数模拟平台层:构造假输入、调 update、调 render、打印 render_buf

完成标准:`cargo run` 打印类似 `["bitmap at (10.0, 5.0)", "text: Score=42"]`,证明 update 改了状态、render 读到了新状态。

**参考解答**:

```rust
// 简化版 Vec2,只需要 x/y,后续 day042 才正式实现
#[derive(Copy, Clone, Debug, Default)]
struct Vec2 { x: f32, y: f32 }

// 1. 游戏状态(逻辑层拥有)
#[derive(Default)]
struct GameState {
    player_pos: Vec2,    // 玩家位置
    score: i32,          // 得分
}

// 2. 输入快照(平台层构造,逻辑层消费)
#[derive(Default, Clone, Copy)]
struct GameInput {
    move_left: bool,     // A 键
    move_right: bool,    // D 键
    score_up: bool,      // 空格键
}

// 3. 逻辑层:更新状态(可变借用 &mut self)
impl GameState {
    fn update(&mut self, input: &GameInput, dt: f32) {
        let speed = 100.0;  // 像素/秒
        if input.move_left  { self.player_pos.x -= speed * dt; }
        if input.move_right { self.player_pos.x += speed * dt; }
        if input.score_up   { self.score += 1; }
    }

    // 4. 渲染层:读状态生成"渲染指令"(只读借用 &self)
    // 注意签名是 &self——Rust 编译器强制"不改状态"
    fn render(&self, render_buf: &mut Vec<String>) {
        render_buf.push(format!("bitmap at ({}, {})",
            self.player_pos.x, self.player_pos.y));
        render_buf.push(format!("text: Score={}", self.score));
    }
}

// 5. 平台层:构造输入、调 update、调 render
fn main() {
    let mut state = GameState::default();
    let mut render_buf: Vec<String> = Vec::new();
    let dt = 0.0167;  // 假装 60 FPS

    // 假装玩家按了 D 和空格
    let input = GameInput {
        move_left: false,
        move_right: true,
        score_up: true,
    };

    // 模拟 5 帧
    for _ in 0..5 {
        state.update(&input, dt);
    }

    // 渲染
    state.render(&mut render_buf);

    // 平台层打印"渲染结果"
    for cmd in &render_buf {
        println!("{}", cmd);
    }
}
```

**每行解释**:

- `#[derive(Default)]` — Rust 自动生成"零值初始化":Vec2 默认 (0,0),i32 默认 0,bool 默认 false。省得写 `new()`。
- `&mut self` / `&self` 的差别是 Rust 所有权核心。`&mut self` 允许改字段,`&self` 只读。Rust 编译器**编译时**检查,运行时无开销。
- `dt = 0.0167` 是 60 FPS 的帧间隔(1/60 ≈ 0.0167)。后面 Day 037 详细讲为什么用 dt 不用固定步长。
- `render_buf` 用 `Vec<String>` 模拟"渲染指令容器"。真实项目里这是 `Vec<RenderCommand>` 或 push buffer。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例:三明治骨架 + 单元测试

把 Lv2 的代码扩展,加上**单元测试**——这是三明治分层最直接的红利:逻辑层可以独立测。

```rust
// src/main.rs(项目根的 src/main.rs)
// cargo new --bin sandwich_arch && cd sandwich_arch

#[derive(Copy, Clone, Debug, Default, PartialEq)]
struct Vec2 { x: f32, y: f32 }

#[derive(Default)]
struct GameState {
    player_pos: Vec2,
    score: i32,
}

#[derive(Default, Clone, Copy)]
struct GameInput {
    move_left: bool,
    move_right: bool,
    score_up: bool,
}

impl GameState {
    fn update(&mut self, input: &GameInput, dt: f32) {
        // 逻辑层:纯函数,输入相同 → 状态变化相同
        let speed = 100.0_f32;
        if input.move_left  { self.player_pos.x -= speed * dt; }
        if input.move_right { self.player_pos.x += speed * dt; }
        if input.score_up   { self.score += 1; }
    }

    fn render(&self, render_buf: &mut Vec<String>) {
        // 渲染层:只读 self,不改状态
        render_buf.push(format!("bitmap at ({:.1}, {:.1})",
            self.player_pos.x, self.player_pos.y));
        render_buf.push(format!("text: Score={}", self.score));
    }
}

fn main() {
    let mut state = GameState::default();
    let mut render_buf: Vec<String> = Vec::new();
    let dt = 0.0167;
    let input = GameInput { move_right: true, score_up: true, ..Default::default() };

    for _ in 0..5 {
        state.update(&input, dt);
    }
    state.render(&mut render_buf);
    for cmd in &render_buf { println!("{}", cmd); }
}

// 单元测试:逻辑层可以独立测,不需要 framebuffer / window / GPU
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn player_moves_right_when_d_pressed() {
        let mut state = GameState::default();
        let input = GameInput { move_right: true, ..Default::default() };
        state.update(&input, 1.0);  // dt=1s, 走 100 像素
        assert!((state.player_pos.x - 100.0).abs() < 0.01);
    }

    #[test]
    fn score_increments_when_space_pressed() {
        let mut state = GameState::default();
        let input = GameInput { score_up: true, ..Default::default() };
        state.update(&input, 0.0);  // dt 不影响 score
        assert_eq!(state.score, 1);
    }

    #[test]
    fn logic_is_deterministic_same_input_same_state() {
        // 同样的输入序列,无论何时跑,产出的状态一定相同
        // 这是"回放系统"的基础
        let mut s1 = GameState::default();
        let mut s2 = GameState::default();
        let input = GameInput { move_right: true, score_up: true, ..Default::default() };
        for _ in 0..10 {
            s1.update(&input, 0.0167);
            s2.update(&input, 0.0167);
        }
        assert_eq!(s1.player_pos.x, s2.player_pos.x);
        assert_eq!(s1.score, s2.score);
    }
}
```

**Rust 特性解释**:

- `#[cfg(test)] mod tests` —— Rust 的测试惯例。`cargo test` 时编译这段代码,`cargo build` / `cargo run` 时跳过。这让生产二进制不含测试代码。
- `..Default::default()` —— struct update 语法。"剩下字段用 Default 填"。比每次写完整字面量简洁。
- `(state.player_pos.x - 100.0).abs() < 0.01` —— 浮点比较用"差值小于阈值",不用 `==`(浮点舍入误差会让 `==` 失败)。这是 Day 041 详细讲的浮点陷阱。
- `assert_eq!(s1.score, s2.score)` —— Rust 内置的相等断言,失败时打印两个值便于调试。
