
# Day 052 · 相机空间中的实体运动

> Day 031 你学了"世界坐标 vs 屏幕坐标",屏幕 = 世界 - camera。Day 052 Casey 试图反过来:**让 entity 的存储位置直接是相对相机的**——相机移动时,所有 entity 平移跟随。这看似优雅,但 Casey 很快发现 10000 个 entity 每帧平移成本太大,最终(Day 063)放弃,改用 sim region。Day 052 是"探索式开发"的经典案例。

## 0 · 为什么要有这一天

游戏世界可能很大(10 公里 × 10 公里),但屏幕只显示 1920×1080。**视野剔除**(frustum culling)决定哪些 entity 在屏幕上,只渲染这些。

Day 031 的方案:每个 entity 存世界坐标。渲染时算 `screen = world - camera`,看 screen 是否在 [0, screen_width] × [0, screen_height]。

Day 052 的反向思路:每个 entity 存**相对相机**的位置(`rel = world - camera`)。相机移动时,所有 entity 自动平移:

```
相机右移 10 → 所有 entity 的 rel.x -= 10
entity 在相机视野内 ⟺ |rel.x| < screen_width / 2 且 |rel.y| < screen_height / 2
```

**好处**:视野剔除变成"abs 比较",简单。Sim region 概念自然出现——离相机远的 entity 的 rel 也远,可以剔除。

**坏处**:10000 个 entity 每帧平移(每个 entity 改 rel),写入 80KB/帧(10000 × 2 f32)。内存带宽成本。

Casey 在 Day 052 试了一集,Day 054-063 演化到最终方案:**保留世界坐标,但只 update 相机附近的 entity**(sim region)。这避免了平移成本,但享受"只模拟近处"的好处。

**这集的教学价值**不在"相机空间存 entity"本身(后面被推翻),而在:

1. **坐标系变换**:世界 ↔ 相机 ↔ 屏幕,理解每层
2. **取舍思维**:平移成本 vs 视野剔除简化
3. **探索式开发**:试了一个方案,发现不好,推翻

心理锚点:做完今天,你应该能解释为什么 Casey 最终不存相机空间(成本太高),以及 sim region 怎么解决同一问题(不动 entity,只选择 update)。这是工程决策的训练。

## 2 · 心智模型

### 费曼类比:鱼缸里的鱼

想象你拿着一个鱼缸,鱼缸里有 100 条鱼。你想看不同的鱼。

**方案 A**(世界坐标):鱼缸固定,你(相机)绕着鱼缸走。从不同角度看不同的鱼。

**方案 B**(相机空间):你固定,鱼缸相对你移动。每秒你换一个角度看鱼——但鱼缸移动需要把所有鱼的位置都更新。

如果鱼多(10000 条),方案 B 每秒"搬动鱼缸"成本高。方案 A 你只是"转头",便宜。

但方案 B 有一个好处:**离你远的鱼(鱼缸边缘)你能立刻剔除**——不用看 abs(相对你的位置)。方案 A 要算 `world - camera`,再做 abs。

**Casey 的最终选择**(Day 063):方案 A 存储 + sim region 选择性 update。既不搬动鱼缸(省成本),又只关注近处的鱼(省 CPU)。

### 严谨定义:三个坐标系

**世界坐标**(world space):entity 在游戏世界的绝对位置。

**相机坐标**(camera space):entity 相对相机的位置 = world - camera。

**屏幕坐标**(screen space):像素位置,通常 = camera space + screen_size / 2(相机在屏幕中央)。

变换链:

```
world → camera:  cam = world - camera_pos
camera → screen: screen = cam + Vec2::new(screen_w/2, screen_h/2)
```

渲染时:entity.pos 是世界坐标,变换到屏幕坐标,画到 framebuffer。

### 相机空间存储的代码

```rust
pub struct World {
    pub entities: Vec<Entity>,
    pub camera_world: Vec2,  // 相机在世界中的位置(用于换算)
    // entity.pos 是相对相机的!
}

impl World {
    pub fn move_camera(&mut self, delta: Vec2) {
        self.camera_world += delta;
        // 所有 entity 平移
        for e in &mut self.entities {
            e.pos -= delta;
        }
    }

    pub fn entity_in_view(&self, e: &Entity, screen_w: f32, screen_h: f32) -> bool {
        // entity 相对相机,abs 比较决定是否在屏幕
        e.pos.x.abs() < screen_w * 0.5 && e.pos.y.abs() < screen_h * 0.5
    }
}
```

### 性能成本分析

假设 10000 个 entity,每帧相机移动(玩家走),平移成本:

```
10000 entity × Vec2(8 字节) = 80 KB 写入/帧
60 FPS × 80 KB = 4.8 MB/秒
```

4.8 MB/秒看似不多,但这是**强制写入**(不是 cache-friendly 的)。CPU cache line 64 字节,80KB = 1250 个 cache line。

**对比**:世界坐标 + sim region:

```
0 平移(不动 entity)
只 update 相机附近 N 个 entity,N << 10000
```

方案 A 的成本更低,因为不写 entity 数据。

### 视野剔除的两种方案

**方案 A**(世界坐标,Day 031):

```rust
fn in_view(entity_world: Vec2, camera: Vec2, screen_w: f32, screen_h: f32) -> bool {
    let rel = entity_world - camera;
    rel.x.abs() < screen_w * 0.5 && rel.y.abs() < screen_h * 0.5
}
```

每次渲染时算减法。

**方案 B**(相机空间,Day 052):

```rust
fn in_view(entity_cam: Vec2, screen_w: f32, screen_h: f32) -> bool {
    entity_cam.x.abs() < screen_w * 0.5 && entity_cam.y.abs() < screen_h * 0.5
}
```

不需要减法(entity 已经是相对相机)。但平移成本转移到了 update 阶段。

**总成本**:

- 方案 A:每帧每个 entity 一次减法(渲染时)
- 方案 B:每帧每个 entity 一次减法(update 时,相机移动)

数学上等价。但方案 B 的减法发生在 update(必然每帧),方案 A 的减法发生在渲染(也每帧)。**总开销相同**。

**真正的优势**不在视野剔除,而在 sim region(选择哪些 entity update)——但这是 Day 063 的事。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的坐标系设计:

**1. 世界坐标存储**(主流):Unity、Unreal 都用。entity 存 transform.position(world),渲染时变换。

**2. 相对父对象**(hierarchical):Unity 的 transform 有 parent。child 的 position 是相对 parent。常用于"角色 + 武器"关系。

**3. 相机空间渲染**:GPU 渲染时,所有顶点先转 camera space(model → view 矩阵),再投影(projection)。但 entity 的存储还是世界坐标。

**4. 屏幕空间 UI**:UI 元素直接用屏幕坐标。不受相机影响。

Casey 的 Day 052 是少数尝试相机空间存储的——因为 HH 是探索式开发。商业引擎不会这么做(性能 + 工具链支持难)。

### 3.2 · 🎨 图形学视角

图形学的坐标系变换链:

```
Model space (物体本地)
  ↓ model matrix
World space (世界)
  ↓ view matrix
Camera / View space (相机)
  ↓ projection matrix
Clip space (裁剪空间,[-w, w])
  ↓ perspective divide
NDC space (Normalized Device Coordinates,[-1, 1])
  ↓ viewport transform
Screen space (屏幕像素)
```

每个变换是矩阵乘法。GPU shader 在 vertex shader 里做 model → view → projection(一次 4×4 矩阵乘)。

**Casey 的 Day 052** 是把 view 变换提前到 update 阶段(平移 entity),让渲染时已经是 camera space。但 GPU 本来就要做 view 变换,提前没省什么——徒增 update 成本。

### 3.3 · 🐧 Linux 系统编程视角

Linux 的坐标变换:

**1. 进程的虚拟地址**:每个进程看自己的虚拟地址空间(从 0 开始),内核通过页表映射到物理地址。这类似"相机空间"——每个进程有自己视角,内核做变换。

**2. 容器命名空间**(namespace):Docker 容器看自己的 PID 空间(PID 1 是容器入口),实际宿主机 PID 不同。这是"相机空间"思路的应用——容器视角 ≠ 全局视角。

**3. chroot**:改变进程的"文件系统根",进程看 `/` 实际是宿主的 `/var/jail/`。坐标系偏移。

Casey 的相机空间 = 容器的命名空间——"换视角"思想。

### 3.4 · 🦀 Rust 生态视角

#### Rust 实现

```rust
pub struct Entity {
    pub pos: Vec2,  // 相对相机(Day 052 风格)
    pub kind: EntityKind,
}

pub struct World {
    pub entities: Vec<Entity>,
    pub camera_world: Vec2,
}

impl World {
    pub fn move_camera(&mut self, delta: Vec2) {
        self.camera_world += delta;
        for e in &mut self.entities {
            e.pos -= delta;
        }
    }

    pub fn add_entity_at_world(&mut self, world_pos: Vec2, kind: EntityKind) {
        let cam_pos = world_pos - self.camera_world;
        self.entities.push(Entity { pos: cam_pos, kind });
    }

    pub fn entity_world_pos(&self, e: &Entity) -> Vec2 {
        e.pos + self.camera_world
    }
}
```

**外部 API**:get_world_pos / set_world_pos 通过 camera_world 换算。内部存储是相对相机。

**测试**:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_camera_move_shifts_entities() {
        let mut world = World {
            entities: vec![Entity {
                pos: Vec2::new(100.0, 0.0),
                kind: EntityKind::Decoration,
            }],
            camera_world: Vec2::new(0.0, 0.0),
        };

        // 相机右移 50,entity 相对相机左移 50
        world.move_camera(Vec2::new(50.0, 0.0));
        assert_eq!(world.entities[0].pos, Vec2::new(50.0, 0.0));
        assert_eq!(world.camera_world, Vec2::new(50.0, 0.0));

        // 但 entity 的世界位置不变
        let world_pos = world.entity_world_pos(&world.entities[0]);
        assert_eq!(world_pos, Vec2::new(100.0, 0.0));
    }
}
```

#### 所有权和迭代

平移所有 entity 用 `for e in &mut self.entities`——单线程顺序迭代。如果用多线程(rayon),可以并行:

```rust
self.entities.par_iter_mut().for_each(|e| {
    e.pos -= delta;
});
```

但 80KB 写入,单线程已经够快(几微秒)。多线程反而启动开销大。

## 5 · 对照与变奏

### 不同游戏类型的相机

**固定相机**(Pac-Man):相机不动,所有 entity 直接用屏幕坐标。

**跟随相机**(超级马里奥):相机随玩家移动,但 entity 存世界坐标。

**滚动相机**(银河战士):相机沿预设路径,触发剧情时移动。

**自由相机**(3D 游戏):玩家控制相机方向 + 位置。

Casey 的 HH 是跟随相机。

### 2D vs 3D 相机

2D:相机只有 position + zoom(2D + 缩放)。

3D:相机有 position + rotation + fov(3 维 + 朝向 + 视野角)。变换矩阵复杂(model → view → projection)。

Day 052 是 2D 简化版,Day 108+ 切到 3D 时复杂度上升。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 最终不用相机空间存 entity?具体成本是多少?

**参考解答**:

**主要成本**:相机移动时,所有 entity 都要平移(更新 rel = world - camera)。

**数字**:10000 entity × Vec2(8 字节)= 80KB 写入/帧。60 FPS = 4.8 MB/秒。

虽然 4.8 MB/秒看似不多,但有几个问题:

1. **Cache 不友好**:entity 数组不是连续访问(每帧都要全部写一遍)。CPU cache 反复失效。
2. **平移无意义**:entity 的世界坐标本来不变,平移只是为了"换视角"。这是浪费。
3. **视野剔除没省**:不管存什么坐标,判断"在屏幕内"都要做 abs 比较。相机空间只是省了减法(几十纳秒),但平移成本(几微秒)远超省下的。

**替代方案**(Day 063 sim region):保留世界坐标存储,只 update 相机附近的 entity。entity 不平移(零写入成本),但 update 调用减少(只对近处)。

**直觉**:与其"让数据跟着视角变",不如"让计算跟着视角变"。前者影响所有数据,后者只影响部分计算。

```rust
// src/cam_world.rs
use crate::math::Vec2;

#[derive(Clone, Copy, Debug)]
pub enum EntityKind { Player, Monster, Decoration }

pub struct Entity {
    pub pos: Vec2,  // 相对相机
    pub kind: EntityKind,
}

pub struct World {
    pub entities: Vec<Entity>,
    pub camera_world: Vec2,
}

impl Default for World {
    fn default() -> Self {
        Self {
            entities: Vec::new(),
            camera_world: Vec2::ZERO,
        }
    }
}

impl World {
    pub fn move_camera(&mut self, delta: Vec2) {
        self.camera_world += delta;
        for e in &mut self.entities {
            e.pos -= delta;
        }
    }

    pub fn add_entity_at_world(&mut self, world_pos: Vec2, kind: EntityKind) {
        let cam_pos = world_pos - self.camera_world;
        self.entities.push(Entity { pos: cam_pos, kind });
    }

    pub fn entity_world_pos(&self, e: &Entity) -> Vec2 {
        e.pos + self.camera_world
    }

    pub fn in_view(&self, e: &Entity, screen_w: f32, screen_h: f32) -> bool {
        e.pos.x.abs() < screen_w * 0.5 && e.pos.y.abs() < screen_h * 0.5
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_camera_move() {
        let mut world = World::default();
        world.add_entity_at_world(Vec2::new(100.0, 0.0), EntityKind::Monster);

        // 相机右移 50
        world.move_camera(Vec2::new(50.0, 0.0));
        assert_eq!(world.camera_world, Vec2::new(50.0, 0.0));
        assert_eq!(world.entities[0].pos, Vec2::new(50.0, 0.0));  // 相对变了

        // 世界位置不变
        let world_pos = world.entity_world_pos(&world.entities[0]);
        assert_eq!(world_pos, Vec2::new(100.0, 0.0));
    }

    #[test]
    fn test_in_view() {
        let mut world = World::default();
        world.add_entity_at_world(Vec2::new(100.0, 0.0), EntityKind::Monster);
        world.add_entity_at_world(Vec2::new(5000.0, 0.0), EntityKind::Decoration);

        // 屏幕宽 800,高 600。视野半径 400x300
        let in_view_0 = world.in_view(&world.entities[0], 800.0, 600.0);
        let in_view_1 = world.in_view(&world.entities[1], 800.0, 600.0);
        assert!(in_view_0);   // 100 在视野内
        assert!(!in_view_1);  // 5000 远超视野
    }
}
```

```rust
use math::Vec2;

fn main() {
    println!("=== 相机空间存储演示 ===\n");

        let world_pos = world.entity_world_pos(e);
        println!("  Entity {}: 相机相对={:?}, 世界={:?}, 在屏幕?{}",
                 i, e.pos, world_pos,
                 world.in_view(e, 1920.0, 1080.0));
    }

    println!("\n--- 相机右移 100 ---");
    world.move_camera(Vec2::new(100.0, 0.0));
    println!("camera_world = {:?}", world.camera_world);
    for (i, e) in world.entities.iter().enumerate() {
        let world_pos = world.entity_world_pos(e);
        println!("  Entity {}: 相机相对={:?}, 世界={:?}",
                 i, e.pos, world_pos);
    }

    // 性能测试
    println!("\n--- 性能测试(10000 entity × 1000 帧平移)---");
    let mut big_world = World::default();
    for i in 0..10000 {
        big_world.add_entity_at_world(
            Vec2::new(i as f32, 0.0),
            EntityKind::Decoration,
        );
    }
    let start = std::time::Instant::now();
    for _ in 0..1000 {
        big_world.move_camera(Vec2::new(1.0, 0.0));
    }
    let elapsed = start.elapsed();
    println!("1000 次相机平移:{}({:.2} µs/次)",
             elapsed.as_millis(),
             elapsed.as_micros() as f64 / 1000.0);
    println!("每次平移 10000 entity,理论写入 80KB");
}
```

### Troubleshooting

**问题 1**:相机移动后 entity 渲染位置错乱

原因:渲染时忘了考虑 entity 已经是相机相对,直接画到屏幕。

修复:渲染时 `screen = entity.pos + screen_center`,不要再减 camera。

**问题 2**:entity 在屏幕外但仍 update

原因:Day 052 没自动剔除视野外 entity。

修复:加 in_view 检查,update 时跳过视野外。或者改用 Day 063 的 sim region。

**问题 3**:性能比 Day 031 的世界坐标慢

原因:平移成本累加。

修复:回归 Day 031,等待 Day 063 的 sim region。
