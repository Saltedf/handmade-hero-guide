
# Day 611 · 检查 CPU 体素采样

> Day 576-610 把全局光照(GI)的算法骨架搭好了,但每帧仍然要在 CPU 上对体素网格做**数百次光线投射**。这些光线负责把每个体素接收到的辐射度传到下一帧。Casey 今天没有写新算法,而是**用 profiler 把"采样热点"扒出来**——为后面 4 集的性能优化铺路。这一天的核心动作就是"看见性能问题在哪",而不是"猜测然后乱优化"。

## 0 · 为什么要有这一天

我们站在游戏发布前 60 天的节点。Casey 已经在 Day 588 的性能测试中发现:CPU 端的体素采样占了每帧 25-40ms。换算成帧预算,意味着**单这一项就把 60FPS 的预算(16.67ms)花光了**。剩下的游戏逻辑、AI、动画、音频全部要挤进 0ms——这显然不行。

但 Casey 没有立刻"动手优化"。他做的第一件事是**把问题展开看清楚**:profiler 抓出的火焰图显示什么?哪个函数被调用最多次?哪个循环体每次都在算冗余的东西?这是工程化的"诊断优先于治疗"——你不知道病在哪,任何药都是猜测。

**今天的核心学习点**不是某个新算法,而是 **Casey 调优的方法论**:打开 profiler → 读火焰图 → 锁定热点 → 把热点拆成可量化指标 → 写下来。这听起来平淡,但**90% 的初学者优化代码时跳过这一步**,直接凭"我觉得这里慢"动手改,结果改完发现根本没改善——因为他们改的不是真正的瓶颈。

心理锚点:看完这集,你能在自己的 Rust 项目里**用 `perf record` 抓火焰图**,**从火焰图里找出最热的三层调用栈**,并写出"优化前的基线数字"。这是任何性能优化的前提条件——没有基线,就没有"优化了多少"。

## 1 · Casey 今天做了什么

Casey 这一天**不写一行新算法**,而是:

1. **打开 VTune / `perf`**,跑一帧 GI propagation,把火焰图调出来
2. **观察热点**:发现 `sample_voxel_irradiance` 一个函数就占了 35% CPU 时间
3. **进入函数体看循环**:外层是体素遍历,内层是方向采样(每个体素采 64 个方向)
4. **统计调用次数**:每帧调用 `sample_voxel_irradiance` 大约 18 万次,每次执行 200+ 条指令
5. **看 cache miss**:L2 cache miss rate 高达 45%——意味着数据布局不友好(体素在内存里跳着访问)
6. **看分支预测失败率**:8% 的分支失败,主要是"如果体素是空气就跳过"这种条件判断
7. **总结**:这一帧 40ms 里有 14ms 花在 `sample_voxel_irradiance`,其中 6ms 是 cache miss,4ms 是分支预测失败,剩下 4ms 是真正在做计算
8. **写白板**:列出"可能的优化方向"——降低采样数 / 改数据布局 / 用 SIMD / 把数据搬 GPU

这是 Day 612-617 的总规划。

## 2 · 心智模型

### 类比:修车前的诊断

你的车跑不快。你不会立刻换发动机——你会先开到 4S 店,接上 OBD 诊断仪,读故障码,看是哪个传感器异常。**修车的 80% 是诊断,20% 是换零件**。

代码性能调优完全一样。Casey 今天做的事情,就是把游戏接到"代码诊断仪"(profiler)上,读"故障码"(热点函数 + cache miss + 分支失败率),然后写"诊断报告"。后面 4 集才是"换零件"。

如果你跳过诊断直接换零件,经常出现"换了发动机,结果是轮胎花纹太浅"的尴尬。

### 严谨原理:性能分析的三层指标

profiler 给你的不是"哪个函数慢",而是**三层嵌套的指标**:

**第一层:Wall-clock time(墙上时钟时间)**——"用户感受到的时间"。这是终极指标,所有优化都为它服务。

**第二层:CPU 时间分解**——把 wall-clock 拆成:
- **计算时间**(真正在算 ALU 指令)
- **内存时间**(在等 RAM 把数据搬到 CPU)
- **分支预测失败时间**(流水线被清空)
- **指令缓存未命中**(代码本身不在 i-cache)

**第三层:微架构事件**——这是最细的:
- `L1-dcache-load-misses`——L1 数据 cache 未命中数
- `L1-icache-load-misses`——L1 指令 cache 未命中
- `branch-misses`——分支预测失败次数
- `iTLB-load-misses`——指令 TLB 未命中(虚拟地址翻译 cache 未命中)
- `cache-references` / `cache-misses`——L2/L3 cache 命中/未命中

```
Wall-clock time (40ms)
├── CPU busy (24ms)
│   ├── ALU compute (4ms)      ← 真正算数
│   ├── L1 hit (8ms)           ← cache 命中的内存访问
│   ├── L2 miss penalty (6ms)  ← 等 L2 (~10 cycles)
│   ├── L3 miss penalty (4ms)  ← 等 RAM (~100 cycles)
│   └── branch mispredict (2ms)← 流水线清空 (~20 cycles)
└── Stalled / waiting (16ms)
    ├── Memory stall (12ms)
    └── Other (4ms)
```

**关键直觉**:
- CPU 一秒能算 50 亿次 ALU 运算(5GHz),但**等一次 RAM 要 100 纳秒**——够算 500 条指令
- 所以"算得快"远没有"数据离 CPU 近"重要
- 一个 L3 cache miss 等价于 100 条 ALU 指令的代价

这就是为什么 Casey 今天的诊断报告**重点不在 ALU 而在 cache miss**——cache miss 才是 GI 慢的真凶。

### 体素采样的数据流

让我们看一下 Casey 在测的 `sample_voxel_irradiance` 究竟在做什么。先回顾体素采样的数据流:

```
对于场景中每个非空体素 V:
    对于 64 个方向 D(球面均匀分布):
        从 V 朝 D 发射一条光线,长度 L=2m
        命中另一个体素 W
        把 W 的辐射度按距离衰减后累加到 V 的入射辐射度
```

`sample_voxel_irradiance(V, D)` 做的就是**这个内循环的单次迭代**:从 V 沿 D 发射光线,找到 2 米内的命中体素,返回它的辐射度。

为什么慢?三个原因:

1. **每次都要走光线**:哪怕方向 D 几乎不变,每次都要从 V 重新出发,沿 D 一步一步走网格(DDA 算法),命中一个体素就返回。这个"走"的代价不小——每米 16 步(体素边长 6cm),2 米就是 32 步,每步都要查一次体素 ID
2. **体素在内存里跳着排**:Casey 用稀疏存储(哈希表),相邻体素的物理地址可能差很远。这意味着 DDA 每一步都触发一次 cache miss
3. **每个体素独立采 64 次**:没有跨体素的共享——比如相邻的 V1 和 V2 在同一方向 D 上看到的大致是同一面墙,但代码各自走一遍

Day 611 的诊断报告精确指出:**80% 的时间花在 DDA 步进的体素查找上,只有 20% 在算光照**。后面几天的优化全围绕"减少 DDA 步数 / 加速体素查找 / 共享相邻体素的采样结果"展开。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发里"诊断优先"的文化很重。**Real-Time Rendering**(Akenine-Möhrs)反复强调:优化前必须 profile,profile 后必须把数字写下来,否则你不知道"优化有效"还是"只是改了代码"。

游戏行业一个真实案例:**Unreal Engine 4** 的 GPU Visualizer(GPUvis)。任何 UE4 开发者做 GPU 优化前都要先按 `Ctrl+Shift+,` 弹出 GPUvis,看 pass-by-pass 的耗时。这个工具就是"诊断仪"——如果不知道哪个 pass 慢,任何 GPU 优化都是猜测。

Casey 今天做的事情本质就是"做自己的 GPUvis",只不过针对 CPU。他在 Day 588 写了一个简单的 frame profiler(每个主要子系统计时间),Day 611 用更细的 `perf` 把单一子系统内部的热点挖出来。

**初学者常犯的错**:看到代码慢就直接改算法(比如"我把 O(n) 改成 O(log n) 一定快")。但现代 CPU 上,**算法复杂度不是性能的全部**——一个 O(n) 但 cache-friendly 的算法经常比 O(log n) 但 cache-unfriendly 的快。Casey 今天的诊断就证明了:DDA 是 O(网格步数) 算法,理论上不算复杂,但 cache miss 让它实际慢得离谱。

### 3.2 · 🎨 图形学视角

图形学领域的"采样"有几个层次:

1. **像素采样**——光栅化阶段,每个像素在三角形内算颜色
2. **纹理采样**——fragment shader 读纹理图,带双线性 / 三线性 / 各向异性过滤
3. **光线采样**——ray tracing,从相机或光源发射光线
4. **方向采样**——对球面 / 半球面均匀采样(用于 Monte Carlo 路径追踪、 irradiance cache)

今天 Casey 的 `sample_voxel_irradiance` 属于**第 4 类:方向采样**。每个体素在 64 个方向上发射探针光线,收集来自这些方向的辐射度。这和 irradiance caching、light probe 等技术同源。

**为什么 64 个方向?** 这是性能 / 质量的折中。理论上半球面需要无穷多个方向才能精确积分 irradiance,但工程上 64 个均匀分布的方向已经能给出视觉上够好的结果(误差 < 5%)。Casey 在 Day 612 会讨论"能不能降到 32 个",答案是"看具体情况——如果在室内场景,墙少,16 个也够"。

**方向分布的数学**:64 个方向要怎么分布才均匀?这是球面均匀采样问题。最常用的是 Fibonacci 球面分布(基于黄金分割):

```rust
fn fibonacci_sphere(n: usize) -> Vec<Vec3> {
    (0..n).map(|i| {
        let golden = (1.0 + 5.0_f32.sqrt()) / 2.0;  // 黄金比例 φ
        let t = i as f32 / n as f32;
        let phi = (2.0 * std::f32::consts::PI * i as f32 / golden).acos() * 0.5; // 极角
        let theta = 2.0 * std::f32::consts::PI * i as f32 / golden;               // 方位角
        Vec3::new(
            phi.sin() * theta.cos(),
            phi.cos(),
            phi.sin() * theta.sin(),
        )
    }).collect()
}
```

但 Casey 用的是 octahedral 编码(Phase 8 开头 Day 576 讲过)对应的 64 个固定方向——不是球面最优分布,但和 irradiance 存储格式对齐(每个方向对应 atlas 的一个像素)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上做 CPU 性能分析的核心工具是 **`perf`**(perf_events 子系统的用户态接口)。今天 Casey 用到的命令:

```bash
# 抓 30 秒性能数据,采样频率 999Hz(避免和 1000Hz 系统时钟同步)
sudo perf record -F 999 -g --call-graph=dwarf ./target/release/handmade_hero

# 看火焰图(需要 perf report 的 TUI 界面)
sudo perf report --no-children

# 导出 perf.data 给 flamegraph 工具用
sudo perf script > out.perf
# 然后用 FlameGraph 脚本(https://github.com/brendangregg/FlameGraph)
./stackcollapse-perf.pl out.perf > out.folded
./flamegraph.pl out.folded > flame.svg
```

**`perf` 工作原理**:Linux 内核的 `perf_event_open(2)` 系统调用允许用户态进程订阅硬件性能计数器(PMU,Performance Monitoring Unit)。CPU 内部有几十个 PMU 计数器,每发生一次 cache miss、分支预测失败等事件就 +1。`perf record` 每隔 N 个事件(或每秒 N 次)就把当前指令指针(IP)和调用栈采样下来,写入 `perf.data`。

**为什么用 `-F 999`?** 999Hz 是常用采样频率——比 1000Hz 系统时钟略低,避免采样和时钟中断同步,导致采样有偏。如果你用 1000Hz,每次时钟中断都刚好触发一次采样,你看到的全是"时钟中断时刻的调用栈",这是误导。

**`--call-graph=dwarf` 的含义**:抓调用栈有两种方法:
- `--call-graph=lbr`——用 CPU 的 LBR(Last Branch Record)硬件,快但只能抓最近的 16-32 层调用
- `--call-graph=dwarf`——用 DWARF 调试信息 + 栈展开,慢但能抓任意深度

Casey 在开发阶段用 `dwarf`(更准),在 CI 性能基准用 `lbr`(更快)。

**Arch Linux 上的替代工具**:

```bash
# 1. 火焰图一键工具(基于 perf + FlameGraph)
sudo pacman -S flamegraph  # 社区包,不存在则手动 clone FlameGraph repo

# 2. Intel VTune(免费但闭源,功能最强)
yay -S intel-vtune-profiler

# 3. AMD μProf(AMD CPU 用)
yay -S amd-microprofiler

# 4. Hotspot(Qt 界面的 perf frontend,推荐!)
sudo pacman -S hotspot
hotspot ./target/release/handmade_hero
# Hotspot 提供和 perf report 类似的火焰图 + 时间线视图
```

### 3.4 · 🦀 Rust 生态视角

Rust 的几个工具能帮我们做性能分析:

```bash
# 1. cargo flamegraph(封装了 perf + FlameGraph)
cargo install flamegraph
cargo flamegraph --bin handmade_hero --release
# 自动生成 flame.svg

# 2. cargo profiler(支持 perf + callgrind)

# 3. perf 直接对 cargo 二进制(需要 sudo 因为 PMU 需要 root)

```

**注意**:Rust 默认 debug info 在 release 模式下被剥光,这会让火焰图看不到函数名(只看到地址)。修复:

```toml
# Cargo.toml
[profile.release]
debug = true  # 保留 debug info(只增加二进制大小,不影响运行速度)
# 或者更精确:
# debug = "line-tables-only"  # 只保留行号,省空间
```

**测量函数耗时的"穷 man profiler"**:

```rust
use std::time::Instant;

fn sample_voxel_irradiance(voxel: V3i, dir: Vec3) -> Rgb {
    let start = Instant::now();
    
    // ... 实际工作 ...
    
    let elapsed = start.elapsed();
    // 累加到 thread-local 计数器
    thread_local! {
        static SAMPLE_TIME: Cell<u64> = Cell::new(0);
    }
    SAMPLE_TIME.with(|t| t.set(t.get() + elapsed.as_nanos() as u64));
    
    result
}
```

这种方法比 `perf` 粗,但优势是**精确到你想要的函数**。Casey 在 Day 588 用这种方法搭了一个简单的 frame profiler。

## 4 · 认知地图

### 4.1 上级

- **性能优化方法论** —— 任何系统调优的通用流程:measure → analyze → optimize → measure again
- **微架构调优** —— 利用 CPU cache / branch predictor / SIMD 的特性,从硬件层面榨取性能
- **数据导向设计(DOD, Data-Oriented Design)** —— 把数据布局放在第一位,算法次之——因为 CPU 算得够快,数据搬得不够快

### 4.2 同级(并行方案)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| `perf`(Linux perf_events) | 系统级,采样式,免费 | Linux CPU profiling | ✅ Casey 用 |
| VTune | Intel 专属,功能最全 | Intel CPU,需要详细微架构分析 | 备选 |
| Instruments | macOS / iOS | Apple 平台 | 不适用 |
| Tracy | 跨平台,tracing-style | 实时游戏(低开销,锁帧可视化) | Day 588 用了 |
| Simple `Instant::now()` 计时 | 手写,粒度粗 | 单函数耗时,不依赖外部工具 | Day 588 基础 |

详细比较:
- **采样式 vs 追踪式**:`perf` 是采样式(每 1ms 抓一次调用栈),开销低但分辨率有限;`Tracy` 是追踪式(每次函数调用都记录),分辨率高但开销大。Casey 两者都用了——`Tracy` 看宏观(整个游戏循环),`perf` 看微观(`sample_voxel_irradiance` 内部)
- **基于硬件 vs 基于软件**:`perf` 用 CPU PMU 硬件计数器,精确到指令级别;`Instant::now()` 用 OS 系统时钟,精度受 OS 调度影响
- **离线分析 vs 实时可视化**:`perf` 把数据写到磁盘后离线分析;`Tracy` 实时流到 GUI 客户端

### 4.3 下级

- **火焰图**(Flame Graph)—— Brendan Gregg 发明的可视化,把调用栈画成"堆积的矩形"
- **PMU 计数器**(L1-miss / branch-miss / iTLB-miss)—— CPU 内部的硬件计数器
- **`perf_event_open(2)`** —— Linux 系统调用,订阅 PMU 事件
- **DWARF 调试信息** —— 二进制里的栈展开信息,用于把指令地址翻译回函数名
- **`Instant::now()` + `Duration`** —— Rust 标准库的纳秒级计时器

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:"我的代码慢,我应该改什么?"

| 语境 | 工具 | 方法 |
|---|---|---|
| 游戏 CPU 代码 | `perf` / VTune / Tracy | 火焰图找热点 |
| 游戏 GPU 代码 | RenderDoc / Nsight / GPUvis | pass-by-pass 耗时 |
| Web 应用 | Chrome DevTools / Lighthouse | Network + JS profiler |
| 数据库 | `EXPLAIN ANALYZE` / pt-query-digest | 慢查询日志 |
| 内核 | ftrace / eBPF / bpftrace | 内核函数追踪 |
| 嵌入式 | 逻辑分析仪 + GPIO 翻转 | 信号边沿计时 |

工具不同,**方法论完全一样**:measure first, optimize second。这个原则是软件工程的"第一原理"之一。

### 历史演化

- **1970s**:UNIX `prof` / `gprof` —— 用编译器插桩,采样调用计数
- **1990s**:`perf-tools` / `oprofile` —— Linux 早期 profiling
- **2005+**:Intel VTune / AMD CodeAnalyst —— 商用微架构分析
- **2010+**:Linux `perf` —— 内核内置,免费,统一接口
- **2015+**:eBPF —— 内核可编程追踪,革命性
- **2018+**:Tracy / Optick / Superluminal —— 实时游戏 profiler 黄金时代

你跟 HH 学的`perf` + `Tracy` 是 2018 年代的工业标准。

### CPU 调优 vs GPU 调优

| | CPU | GPU |
|---|---|---|
| 主要瓶颈 | Cache miss | Memory bandwidth |
| Profiler | `perf` / VTune | Nsight / RenderDoc |
| 数据布局 | SoA / Morton 编码 | Texture / SSBO |
| 并行度 | 数十核 | 数千线程 |
| 单线程性能 | 单核 ~5 GHz | 单核 ~2 GHz |

CPU 调优的核心是 **"减少 stall"**——等内存、等分支、等依赖。GPU 调优的核心是**"喂饱 SM"**——同时跑够多线程隐藏延迟。两者优化方向完全不同。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 今天发现 `sample_voxel_irradiance` 占 35% CPU 时间,但他没有立刻去优化它的算法,而是继续拆解"这 35% 内部是什么"。为什么不直接重写算法?

**参考解答**:
- 如果直接重写,你可能改了算法但**没改真正的瓶颈**
- 例如:你把算法从 O(n) 改成 O(log n),但 cache miss 才是真凶——复杂度降低没用,因为时间花在等 RAM 上
- 拆解后看到"57% 是 DDA 步进的 cache miss",这告诉你**优化方向不是降复杂度,而是改数据布局**
- 工程经验:优化前的"问题分析"占 70% 时间,优化本身占 30%。Casey 用一整集做分析,后面 6 集才是优化,正是这个比例

### Lv2 · 动手实践

**题**:在你的 Rust 项目里(任何项目都行,甚至是 `cargo new hello` 加一个慢函数),用 `cargo flamegraph` 抓火焰图。完成标准:

1. 安装 `cargo-flamegraph` 和 `perf`
2. 写一个有空转循环的 Rust 函数(让它出现在火焰图上)
3. 运行 `cargo flamegraph`,生成 `flame.svg`
4. 在浏览器里打开,找到你的慢函数

**参考解答**:

```bash
# 安装工具
sudo pacman -S perf
cargo install flamegraph

# Rust 代码
cat > src/main.rs << 'EOF'
fn slow_function() -> u64 {
    let mut sum = 0u64;
    for i in 0..100_000_000 {
        sum = sum.wrapping_add(i);
    }
    sum
}

fn main() {
    let result = slow_function();
    println!("result = {}", result);
}
EOF

# Cargo.toml 加 debug = true
cat >> Cargo.toml << 'EOF'
[profile.release]
debug = true
EOF

# 抓火焰图(需要 root 因为 perf 需要 PMU 访问)
cargo flamegraph --release
# 输出:flame.svg 已经生成在当前目录

# 用浏览器打开
xdg-open flame.svg
```

**输出解读**:火焰图的 X 轴是采样百分比(代表 wall-clock 时间),Y 轴是调用栈深度。最宽的"塔"就是热点——你应该看到 `slow_function` 占据火焰图中央 90%+ 宽度。

**Troubleshooting**:
- `error: perf not found` — 装 perf:`sudo pacman -S perf`
- `error: No permission to enable perf event` — 用 sudo:`sudo cargo flamegraph`
- 火焰图里函数名都是十六进制地址 — 检查 `Cargo.toml` 有 `debug = true`
- 火焰图上找不到你的函数 — 函数太短(不到 1% 采样),增大循环次数

## 8 · Rust / Arch 落地代码

### 完整可跑示例:简易 frame profiler

下面是一个 Rust 程序,模拟 Casey 在 Day 588 / Day 611 用的"per-frame subsystem timing":

```rust
// Cargo.toml:
// [package]
// name = "frame_profiler"
// version = "0.1.0"
// edition = "2021"
//
// [profile.release]
// debug = true  // 让火焰图能看到函数名

use std::cell::RefCell;
use std::collections::BTreeMap;
use std::time::{Duration, Instant};

// 一个 scoped timer:RAII 自动记录 enter/leave 时间
pub struct SectionTimer {
    name: &'static str,
    start: Instant,
}

impl SectionTimer {
    pub fn new(name: &'static str) -> Self {
        Self { name, start: Instant::now() }
    }
}

impl Drop for SectionTimer {
    fn drop(&mut self) {
        // Drop 在作用域结束时自动调用,记录这一段耗时
        let elapsed = self.start.elapsed();
        PROFILER.with(|p| p.borrow_mut().add(self.name, elapsed));
    }
}

// 用宏隐藏样板代码,调用者写 `let _t = profile!("name");`
macro_rules! profile {
    ($name:expr) => {
        let _t = SectionTimer::new($name);
    };
}

// Thread-local profiler:每帧把数字累加到一个 BTreeMap
thread_local! {
    static PROFILER: RefCell<Profiler> = RefCell::new(Profiler::new());
}

pub struct Profiler {
    sections: BTreeMap<&'static str, (Duration, u64)>,  // (name → (total_time, call_count))
}

impl Profiler {
    fn new() -> Self {
        Self { sections: BTreeMap::new() }
    }

    fn add(&mut self, name: &'static str, elapsed: Duration) {
        let entry = self.sections.entry(name).or_insert((Duration::ZERO, 0));
        entry.0 += elapsed;
        entry.1 += 1;
    }

    fn print_and_reset(&mut self) {
        let mut total = Duration::ZERO;
        for (_, (t, _)) in &self.sections {
            total += *t;
        }
        println!("--- Frame profile (total: {:.2}ms) ---", total.as_secs_f32() * 1000.0);
        for (name, (t, count)) in &self.sections {
            let pct = t.as_secs_f32() / total.as_secs_f32() * 100.0;
            println!(
                "  {:30} {:7.3}ms ({:5.1}%) × {:6} calls",
                name,
                t.as_secs_f32() * 1000.0,
                pct,
                count
            );
        }
        self.sections.clear();
    }
}

// 模拟 Casey 的 GI propagation
fn gi_propagation() {
    let _t = profile!("gi_propagation");

    // 子段:体素采样(占 35%)
    for _ in 0..10_000 {
        let _t = profile!("sample_voxel_irradiance");
        sample_voxel_irradiance();
    }

    // 子段:邻居传播
    for _ in 0..5_000 {
        let _t = profile!("propagate_to_neighbors");
        propagate_to_neighbors();
    }
}

fn sample_voxel_irradiance() {
    // 模拟 DDA 步进(空循环,模拟 cache miss)
    let mut acc = 0u64;
    for i in 0..200 {
        acc = acc.wrapping_add(i);
    }
    std::hint::black_box(acc);  // 防止编译器优化掉
}

fn propagate_to_neighbors() {
    let mut acc = 0u64;
    for i in 0..50 {
        acc = acc.wrapping_add(i * 7);
    }
    std::hint::black_box(acc);
}

fn main() {
    // 模拟 60 帧
    for frame in 0..3 {
        println!("=== Frame {} ===", frame);
        gi_propagation();
        PROFILER.with(|p| p.borrow_mut().print_and_reset());
    }
}
```

运行:

```bash
cargo run --release
```

预期输出(数字因 CPU 而异,但比例应该接近 2:1):

```

--- Frame profile (total: 5.234ms) ---
  gi_propagation                 0.012ms (  0.2%) ×      1 calls
  propagate_to_neighbors         1.634ms ( 31.2%) ×   5000 calls
  sample_voxel_irradiance        3.588ms ( 68.6%) ×  10000 calls
=== Frame 1 ===
...
```

### Arch Linux 上的 perf 命令

```bash
# 1. 装 perf
sudo pacman -S perf

# 2. 抓火焰图数据

# 输出:[ perf record: Woken up 1 times to write data ]

# 3. 看 TUI 报告

sudo perf stat -e L1-dcache-load-misses,LLC-load-misses,branch-misses ./target/release/frame_profiler

#   1,234,567  L1-dcache-load-misses
#      45,678  LLC-load-misses        # L3 cache miss(代价大)
#      12,345  branch-misses

# 5. 生成 SVG 火焰图(需 FlameGraph 工具)

# 6. 装 Hotspot(GUI 版)

# Hotspot 自动打开 perf.data,提供火焰图 + 时间线 + 调用树视图
```

**Troubleshooting**:

- `perf: command not found` → `sudo pacman -S perf`
- `No permission to enable task-clock event` → 用 `sudo`
- `Couldn't record kernel reference relocation symbol` → 用 `sudo` 或者 `--no-inherit`
- 火焰图全是 `unknown` → Cargo.toml 加 `debug = true`
- 火焰图太稀疏 → 增大采样频率 `-F 9999`,或让程序运行更久
