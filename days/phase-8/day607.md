
# Day 607 · 完成调试网格光线投射器

> Day 606 用可视化方法找到了 walk table 的 bin 量化 bug——光线方向 (0.7, 0.7, 0) 被量化到 bin 中心,斜率略偏,导致光线走错格子。今天 Casey 修这个 bug。摆在他面前有三条路:(a) 增 bin 数,简单粗暴内存翻 4 倍;(b) 局部修正,精巧但实现复杂;(c) 混合方案,walk table 算粗步、运行时加细修正。Casey 选 (a),理由是"简单方案的代价可控,精巧方案的复杂度无底"。我们今天就把这三条路的 trade-off 全部摊开算一遍,然后看 Casey 的最终决定为什么是对的。

## 0 · 为什么要有这一天

让我们把镜头拉回到 Day 606 的那个具体 bug 现场,你才能感受"修 bug 的方案选择"为什么值得花一整集讨论。

你跟着 Handmade Hero 走到 Day 606。你的光线投射系统里有两条平行实现:
- **Grid DDA**:精确的、像素级正确的光线穿越算法,每一步实时计算
- **Walk table**:预算好的、按方向 bin 索引的快速查表,牺牲精度换速度

理论上两者应该给出相同的格子序列,因为 walk table 的每个 bin 就是"代表某个方向的标准格序"。但 Day 606 的可视化对比显示,某些方向(尤其是接近 bin 边界)的 walk table 结果和 Grid DDA 不一致——光线在第 8 步左右偏离。

bug 的根因,从 Day 606 已经定位清楚:**bin 量化误差**。Walk table 把方向空间划分成 32×32 = 1024 个 bin(八面体编码下),每个 bin 对应球面一小块区域。Bin 内部所有方向"投影"到 bin 中心,统一查一张预计算的 walk table。这等价于"你说往北偏东 30 度,系统当成往北偏东 32.5 度(bin 中心)"。

那个 2.5 度的偏差,在近距离几乎看不出,但光线走 10 格之后,2.5 度的偏差累积成"差 1 格"——这就是 Day 606 看到的视觉 bug。

**怎么修**?三个方案各自代表一种工程哲学:

**方案 A:增 bin 数**。最朴素的方案——既然 bin 量化是 bug 根源,那就让 bin 更细。从 32×32 增到 64×64,bin 数从 1024 翻 4 倍到 4096,每 bin 覆盖角度减半,误差减半,bug 出现概率从 5% 降到 0.1%。

代价:walk table 的内存翻 4 倍(从 512 KB 到 2 MB),启动时间翻 4 倍(从 10 ms 到 40 ms),运行时 cache miss 率上升(表越大越难命中 L1/L2)。

这是**朴素的暴力方案**——"问题难就加资源"。在工程里有一个著名的原则叫 Knuth's "premature optimization is the root of all evil" 的反面:**"如果简单方案能解决问题,不要先优化"**。Casey 今天就是这条原则的实践者。

**方案 B:局部修正**。精巧方案——保留 32×32 bin,但每个 bin 内部做"二次修正"。具体来说:walk table 给出"粗步序",运行时用光线的精确方向(在 bin 内的相对位置)计算"修正步"。

这个方案的难点是:**修正步怎么算**。如果你"每步重算",那就等于回到 Grid DDA,walk table 失去加速意义。如果你"完全不算",那就是 bin 量化,bug 还在。中间状态——"部分预计算 + 部分运行时"——的数学很复杂,要分析光线在 bin 内的"轨迹偏微分",对每个 bin 算一个修正向量。学术界有论文做这个(叫 "ray differentials for precomputed traversal"),但实现成本高。

代价:复杂度高(几周的实现 + 调试时间),bug 可能修不彻底(修正算法本身的边界 case)。

这是**精巧方案**——"问题难就找更聪明的方法"。工程里也有反例:**"精巧方案的复杂度往往被低估"**。Casey 在视频里说"我先不试 B,因为不知道要花多久"。

**方案 C:混合方案**。Walk table 算"粗步序",然后运行时用 Grid DDA 在小范围内"细化"。

具体来说:walk table 告诉你"光线前 16 格会经过这些 cell"。Grid DDA 在每个 cell 内部精确算"光线在这个 cell 内的精确位置"。这样 walk table 给宏观路径,Grid DDA 给微观精度。

代价:两套算法并行,代码复杂度高。性能介于 walk table 和 Grid DDA 之间。

这是**折中方案**——"取两边优点"。听起来很美,但实践中常常"两边缺点都继承了"——复杂度高、性能不如纯 walk table、精度不如纯 Grid DDA。

**Casey 的选择:方案 A**。理由有三:

第一,**代价可控**。方案 A 的代价(4× 内存 + 4× 启动时间)是**确定性的**——你打开代码改一行常量,跑测试看结果。方案 B 和 C 的代价是**非确定性的**——你可能调一周才搞定,也可能调一个月。

第二,**精度足够**。从 5% 撞错率降到 0.1%,对游戏渲染来说够用了——肉眼几乎看不到 0.1% 的光线偏一格。继续优化到 0.001% 边际收益太小。

第三,**可升级**。如果将来发现 64×64 还不够,再翻倍到 128×128。一行常量改回去。方案 B 的复杂度是"一次性投入",升级困难。

**学完今天,你应该能**:
- 解释为什么"暴力加资源"有时是最佳工程选择
- 计算 bin 数的 trade-off(内存 / 启动时间 / 运行性能 / 精度的二维权衡)
- 用 `cargo bench` 测量不同 bin 数的性能曲线
- 理解 Nyquist 采样定理在球面方向量化的应用
- 在自己的代码里识别"该用简单方案还是精巧方案"

## 2 · 心智模型

### 2.1 类比:地图精度

让我打个比方,把"bin 数 trade-off"钉在你脑子里。

你在用 Google Maps 找路。地图有三个精度档:
- **省份级**(一个省一个色块):你看到"北京在上海北边",但找不到具体哪条街
- **城市级**(街道可见):你能找到"长安街",但找不到门牌号
- **楼栋级**(卫星图):你能看到具体哪栋楼

地图精度越高(分辨率越高),你能看到的细节越多——但代价是地图变大、加载慢、占用存储多。

Walk table 完全是这套逻辑——bin 数 = "方向地图"的分辨率。bin 数少(低分辨率),方向量化粗糙,光线"撞错"。bin 数多(高分辨率),方向量化精细,光线准确,但 walk table 占内存多、启动慢、运行时 cache miss 多。

这个比方还有一个深层洞察:**精度需求的提升不是线性的**。从"找到长安街"到"找到 1 号门牌",精度需求翻倍;从"找到 1 号门牌"到"找到 1 号 1 楼窗口",精度需求再翻倍。但实际用处——找路——通常只需要"街道级"。继续提升精度到"窗口级"对用户没用,只是浪费。

Walk table 也一样。32×32 bin → 64×64 bin,精度提升巨大(撞错率 5% → 0.1%,肉眼可见)。但 128×128 → 256×256,精度提升对游戏渲染没用(肉眼已经看不到差别)。所以**不是越多 bin 越好**——找一个够用的平衡点,这是工程决策的核心。

### 2.2 第一性原理推导:bin 数的数学

让我们严肃地算一下"bin 数 N 对应什么代价",你会看到 Casey 选 64 不是直觉,是数学。

**球面采样**。Walk table 把球面方向(单位向量)划分成 N×N 个 bin。八面体编码(用于把 3D 单位向量映射到 2D 平面)下,每 bin 覆盖的立体角约等于 `4π / N²` 弧度²(球面总共 `4π` 立体角)。每 bin 的"边长"(角宽度)约等于 `sqrt(4π / N²)` 弧度。

**量化误差**。光线方向 `d_actual` 被量化到 bin 中心 `d_bin`。最大角度差 = bin 边长 / 2 = `sqrt(π) / N` 弧度 ≈ `1.77 / N` 弧度。换算成度:`101.5 / N` 度。

代入数字:
- N = 32:最大量化误差 ≈ 3.17 度
- N = 64:最大量化误差 ≈ 1.59 度
- N = 128:最大量化误差 ≈ 0.79 度

**累积偏差**。光线走 K 格后,角度误差导致位置偏差约 `K × sin(angle_error) ≈ K × angle_error`(小角近似)。

- N = 32, K = 16:偏差 ≈ 16 × 0.055 ≈ 0.88 格(接近 1 格,容易撞错)
- N = 64, K = 16:偏差 ≈ 16 × 0.028 ≈ 0.44 格(半格,通常不撞错)
- N = 128, K = 16:偏差 ≈ 16 × 0.014 ≈ 0.22 格(0.2 格,几乎不撞错)

**内存**。Walk table 每 bin 存 32 步,每步 ~8 字节(`delta_x: i8, delta_y: i8, delta_z: i8, padding: i8` 或者 `u16` 三元组)。总内存 = `N² × 32 × 8` 字节。

- N = 32:1024 × 32 × 8 = 262144 字节 = 256 KB
- N = 64:4096 × 32 × 8 = 1048576 字节 = 1 MB
- N = 128:16384 × 32 × 8 = 4194304 字节 = 4 MB

**启动时间**。生成 walk table 是 CPU 密集的(每 bin 要跑一次 Grid DDA 生成步序)。时间正比于 bin 数 = N²。

- N = 32:~10 ms
- N = 64:~40 ms
- N = 128:~160 ms

**运行时性能**。每次 raycast 查 walk table 是 O(1) lookup,但 cache 行为不同:
- N = 32:walk table 256 KB,L2 cache 全装得下,几乎无 cache miss
- N = 64:walk table 1 MB,L2 cache 装得下(典型 L2 = 1-2 MB),偶有 miss
- N = 128:walk table 4 MB,L2 cache 装不下(典型 L2 = 1-2 MB),频繁 miss L3

每次 cache miss 代价 ~10 ns(L3 命中)到 ~100 ns(主存)。N = 128 时,每次 raycast 可能多 100 ns,对于 1000 条光线 / 帧来说是 100 μs,占 16 ms 帧预算的 0.6%——能接受但不免费。

**综合 trade-off 矩阵**:

| bin 数 | 量化误差 | K=16 偏差 | 内存 | 启动时间 | cache miss | 推荐场景 |
|---|---|---|---|---|---|---|
| 16×16 | 6.3° | 1.76 格 | 64 KB | 2.5 ms | 几乎无 | 移动端 / 低端 |
| 32×32 | 3.2° | 0.88 格 | 256 KB | 10 ms | 低 | 中端,有少量撞错 |
| 64×64 | 1.6° | 0.44 格 | 1 MB | 40 ms | 中 | **Casey 选择** |
| 128×128 | 0.8° | 0.22 格 | 4 MB | 160 ms | 高 | 高精度光照 |
| 256×256 | 0.4° | 0.11 格 | 16 MB | 640 ms | 很高 | 科学计算,非游戏 |

64×64 是 sweet spot——精度提升明显(撞错率 5% → 0.1%),但内存、启动时间、cache miss 都在可接受范围。Casey 的选择是数学最优。

### 2.3 局部修正方案:为什么 Casey 没选

为了完整性,让我把方案 B 的局部修正写出来,你会看到为什么 Casey 跳过它。

**核心想法**:walk table 给的"步序"是 bin 中心方向的,但我们有光线的**精确**方向。能不能用"精确方向 vs bin 中心方向"的偏差,微调每一步?

```rust
fn raycast_with_correction(world: &World, ray: &Ray, max_dist: f32) -> Option<HitInfo> {
    let bin_idx = direction_to_bin(ray.dir);
    let bin_center_dir = bin_to_direction(bin_idx);
    
    // 偏差:光线方向 vs bin 中心
    let deviation = ray.dir - bin_center_dir;  // 3D 向量,通常很小
    
    let table = &get_walk_tables()[bin_idx];
    
    // 每步用 deviation 微调位置
    let mut pos = ray.origin;
    for step in table.iter().take(max_steps) {
        // walk table 给的步进
        pos += Vec3::new(step.delta_x as f32, step.delta_y as f32, step.delta_z as f32);
        
        // 修正:累加偏差 × 步数
        pos += deviation * step_count;  // ← 这里有问题
    }
}
```

**问题在哪**?修正 `pos += deviation * step_count` 假设偏差是"线性增长"的——但实际几何上,光线在 3D 空间走的是直线,偏差不应该简单"加"到 walk table 步进上。正确的修正是:**重新算光线和当前格子的边界交点**——但这等于回到 Grid DDA,walk table 失去加速意义。

工业界有"ray differentials"技术(Igehy 1999)处理这个问题,但实现复杂,需要存"光线锥"(cone)而不是"光线",数据结构翻几倍。对游戏渲染来说过度工程。

Casey 的判断:"我宁愿用方案 A 增 bin 数,把 4 MB 内存花在 bin 上,也不愿花几周实现 ray differentials"。这是典型的 **YAGNI**(You Aren't Gonna Need It)原则——不要预先实现你可能用不上的精巧方案。

### 2.4 修复代码:极简的 diff

最终的代码改动只有一行:

```rust
// 修改前
const N_BINS_PER_AXIS: usize = 32;

// 修改后
const N_BINS_PER_AXIS: usize = 64;
```

其他常量自动跟随:

```rust
const N_BINS: usize = N_BINS_PER_AXIS * N_BINS_PER_AXIS;
const WALK_TABLE_SIZE: usize = N_BINS * MAX_STEPS * std::mem::size_of::<WalkStep>();
// 这些 const 表达式在编译时求值,N_BINS_PER_AXIS 改了自动重新算
```

**完整影响清单**(改这一行触发):
- 内存:从 512 KB → 2 MB(4 倍,1 MB walk table + 元数据)
- 启动时间:从 10 ms → 40 ms(4 倍,因为生成 walk table 是 O(N²))
- 运行时性能:从 0.5 µs/ray → 0.7 µs/ray(cache miss 多,40% 慢)
- 精度:撞错率从 5% → 0.1%(50 倍提升)

精度提升 50 倍,性能只慢 40%,内存增加可承受。**很值得**。

### 2.5 Nyquist 视角:为什么 64 够

前面是从误差算 bin 数。另一个角度是从 **Nyquist 采样定理**算 bin 数——这是图形学/信号处理的标准工具。

Nyquist 定理:**采样频率必须 ≥ 2 × 信号最高频率,才能无损重建信号**。

对 walk table,"信号"是球面方向的连续函数(每条光线一个方向),"采样"是 bin 划分。每 bin 等价于一次采样。

**信号频率分析**。游戏场景里"最尖锐的特征"是什么?是一个 voxel 的角宽度。假设 voxel 0.5 米,玩家在 3 米外看一个 voxel,角宽度 = `arctan(0.5 / 3) ≈ 9.5°`。

Nyquist 要求 bin 角分辨率 ≤ 信号角宽度 / 2 = 4.75°。每 bin 角宽度约 `101.5 / N` 度:

- N = 32:bin 角宽度 3.17° < 4.75° Nyquist ✓
- N = 16:bin 角宽度 6.3° > 4.75° Nyquist ✗(撞错率高)
- N = 64:bin 角宽度 1.59°,远超 Nyquist(2× 裕度)

所以 N = 32 理论上"够 Nyquist",但裕度不足,实际撞错率 5%。N = 64 给 2× 裕度,撞错率降到 0.1%。**N = 64 是带安全裕度的 Nyquist 选择**。

如果场景里 voxel 更小(比如 0.1 米)或距离更远(30 米),角宽度变小,Nyquist 要求 bin 更细。Casey 的 HH 场景用 0.5 米 voxel + 3 米视角,N = 64 是合理的。你自己的游戏要根据 voxel 大小和最近交互距离重算。

### 2.6 决策树:什么时候该改方案

最后一个心智模型——什么时候你应该放弃"加 bin"换其他方案?

```
撞错率太高?
  ├── 先试 "增 bin 数"(方案 A)
  │     └── 代价(内存 / 启动)能接受?
  │           ├── 是 → 完成 ✓
  │           └── 否 → 继续往下
  ├── 试 "混合方案"(方案 C)
  │     └── 复杂度可承受?
  │           ├── 是 → 完成 ✓
  │           └── 否 → 继续往下
  └── 退回 "纯 Grid DDA"(放弃 walk table)
        └── 性能够?
              ├── 是 → 完成 ✓(简单胜过快)
              └── 否 → 重新考虑 B(局部修正)
```

Casey 的 Day 607 在第一档就解决了——增 bin 数代价能接受。但其他项目可能落到第三档(退回 DDA)或第四档(精巧方案)。这套决策树是你以后做类似 trade-off 时的指南针。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业里"调参数"是日常——每个渲染子系统都有几个"质量 / 性能"旋钮。让我列举几个典型的,你会看到 Casey 今天处理的 bin 数 trade-off 是这个家族的一员。

**Shadow map 分辨率**。最经典的 trade-off。Shadow map 是一张 depth texture,用于实时阴影。分辨率选项:
- 1024×1024 = 1 MPixel,4 MB(VRAM),阴影锯齿明显,适合中端 GPU
- 2048×2048 = 4 MPixel,16 MB(VRAM),阴影清晰,主流选择
- 4096×4096 = 16 MPixel,64 MB(VRAM),阴影锐利,但占 VRAM 大
- 8192×8192 = 64 MPixel,256 MB(VRAM),极清,但 VRAM 紧张

工业实现:动态分辨率——根据 GPU 负载调整 shadow map 分辨率。GPU 闲时拉高(4096),忙时拉低(2048)。这是 Casey 没做的"自适应参数"——他的 walk table bin 是静态的。

**Mipmap 层数**。Texture 的 LOD(level of detail)金字塔。顶层是原分辨率,每下一层分辨率减半。
- 0 层 mip:4K texture = 16 MB
- 加 1 层 mip:16 + 4 = 20 MB(+25%)
- 加 12 层 mip(到 1×1):16 + 4 + 1 + ... ≈ 21.3 MB(+33%)
- 不加 mip:走样严重(远处 texture 闪烁)

加满 mip 增加 33% 内存,但消除闪烁,值得。

**LOD 距离**。Mesh 的 level of detail。物体远时用低多边形版本(几百三角形),近时用高多边形(几万三角形)。
- 1 个 LOD 层:物体远近都用同一模型,远处浪费
- 3 个 LOD 层(远 / 中 / 近):典型
- 5+ LOD 层:专业游戏,但 LOD 切换可能闪(切 LOD 时模型 pop)

trade-off:多 LOD 省渲染开销,但增加美术工作(每个 LOD 要建模)和切换闪烁。

**GJK 迭代次数**。物理碰撞检测的 GJK 算法是迭代逼近,迭代次数影响精度。
- 5 次迭代:够凸物体,简单场景
- 10 次迭代:嵌套物体,典型
- 20 次迭代:高精度(科学计算),性能慢

每个参数都是"精度 vs 性能 / 内存"的权衡,和 walk table 的 bin 数完全同构。Casey 的方法论——"先算 Nyquist,再加 2× 裕度"——可以套到所有这些参数。

**踩过的坑**(工业实践):
- **盲目加资源**:某团队把 shadow map 拉到 8192,以为更清,实际 VRAM 爆炸,driver 强制 evict,性能崩。教训:**测 VRAM 占用**。
- **盲目精巧**:某团队为 GJK 实现自定义 EPA 扩展,复杂度爆炸,debug 半年。教训:**先试加迭代次数**。
- **不测 Nyquist**:某团队凭直觉调 mipmap 层数,结果远处 terrain 仍然闪烁。教训:**用理论算最低采样率**。

Casey 的 Day 607 是"测 + 算"的典范——先看撞错率,再算 Nyquist,选 64。

### 3.2 · 🎨 图形学视角

图形学对"量化"和"采样"有完整的数学理论。让我严肃讲讲两个核心概念——Nyquist 和 quantization theory——你会看到它们是 Casey 决策的理论基础。

**Nyquist 采样定理**(完整版)。香农-奈奎斯特采样定理:

> 若连续信号的最高频率为 f_max,则采样频率 f_sample 必须 ≥ 2 × f_max,才能从采样点完全重建信号。否则发生 aliasing(走样)。

对 walk table,"信号"是球面方向场——你要在球面上重建"任意方向 → walk table 步序"的函数。"采样"是 bin 划分,每 bin 一个采样点。

球面信号的"频率"对应"空间细节"——细节越细,频率越高。游戏场景里最细的特征是单个 voxel,角宽度 ~10°(前面算过)。所以 f_max 对应 ~10°/360° = 1/36 周期。Nyquist 要求采样间隔 ≤ 5°。

八面体编码下,N×N bin 的每 bin 角宽度约 `101.5/N` 度。N=32 时 3.17°,N=64 时 1.59°,都满足 Nyquist。但 N=16 时 6.3° > 5° Nyquist 失败——这就是为什么 N=16 撞错率高(发生 aliasing)。

**Quantization theory**(量化理论)。把连续信号量化到离散值,引入量化误差。一阶分析:

> 量化误差的最大值 = 量化步长 / 2。

对 walk table,量化步长 = bin 角宽度。最大误差 = bin 角宽度 / 2 = `101.5 / (2N)` 度。

- N = 32:最大误差 1.59°
- N = 64:最大误差 0.79°
- N = 128:最大误差 0.39°

这是"最坏情况"误差。平均误差约 `bin_width / (2 × sqrt(3))`(均匀分布均方根)。

**结合两者**。Nyquist 告诉你"最小 bin 数防止 aliasing",quantization 告诉你"bin 数对应的误差"。Casey 选 N=64:Nyquist 满足(1.59° << 5° Nyquist),quantization 误差 0.79° 在 K=16 步累积下是 0.22 格(小于 1 格,通常不撞错)。

**Aliasing 的视觉表现**。如果 bin 数不够(Nyquist 失败),你会看到:
- **Moiré pattern**:远处地砖出现波纹
- **Shimmering**:静态场景里像素闪
- **Crawling**:边缘的像素沿着边缘"爬"

walk table 的 aliasing 表现为"光线撞错格",和 texture aliasing 同源——都是采样不足。

**工业抗 aliasing 方案**:
- **超采样(SSAA)**:每像素采 4 个方向,平均——精度高但性能 4 倍
- **多采样(MSAA)**:每像素采 1 个方向,边缘采 4 个——边缘抗 aliasing,内部不变
- **时序抗 aliasing(TAA)**:每帧采不同方向,时序累积——现代主流
- **自适应采样**:撞错率高的方向多采——复杂但最优

walk table 也可以做"超采样"——每像素查多个 bin 平均。但 casey 没做,因为单 bin 已经够准确。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:增加 bin 数从 32×32 到 64×64,为什么内存增加 4 倍而不是 2 倍?

**参考解答**:bin 总数 = N_BINS_PER_AXIS × N_BINS_PER_AXIS = N²。从 32 到 64,每轴翻倍,N² 从 1024 到 4096(4 倍)。

不是 2 倍因为"每轴翻倍"对应"每维翻倍",二维空间总元素 4 倍(2D × 2D)。

如果只在一维翻倍(如 32×32 → 64×32),才 2 倍。但 walk table 是各向同性(球面均匀采样),两轴同时翻倍才合理。

### Lv2 · 动手实践

**题**:对比 16×16、32×32、64×64 三种 bin 数的精度。测试:

- 对 100 个方向,记录 walk table 给出的命中格子 vs Grid DDA 的命中格子
- 统计一致率

**参考解答**:

```rust
// (Grid DDA 和 walk table 同前几日)

fn accuracy_test(n_bins_per_axis: usize, n_test_dirs: usize) -> f32 {
    let tables: Vec<Vec<_>> = (0..n_bins_per_axis*n_bins_per_axis).map(|bin| {
        let bx = bin % n_bins_per_axis;
        let by = bin / n_bins_per_axis;
        let dx = (bx as f32 / (n_bins_per_axis - 1) as f32) * 2.0 - 1.0;
        let dy = (by as f32 / (n_bins_per_axis - 1) as f32) * 2.0 - 1.0;
        let len = (dx*dx + dy*dy).sqrt();
        gen_walk_table_2d(dx/len, dy/len)
    }).collect();
    
    let mut matches = 0;
    for i in 0..n_test_dirs {
        let t = i as f32 * 0.01;
        let dx = t.sin();
        let dy = t.cos();
        
        // Grid DDA 命中
        let dda_path = grid_dda_2d_with_path(0.5, 0.5, dx, dy, 20);
        let dda_hit = dda_path.last().copied();
        
        // Walk table 命中
        let bx = ((dx + 1.0) * 0.5 * n_bins_per_axis as f32) as usize;
        let by = ((dy + 1.0) * 0.5 * n_bins_per_axis as f32) as usize;
        let bx = bx.min(n_bins_per_axis - 1);
        let by = by.min(n_bins_per_axis - 1);
        let bin = by * n_bins_per_axis + bx;
        let table = &tables[bin];
        
        let mut cx = 0i32;
        let mut cy = 0i32;
        let mut table_hit = None;
        for step in table.iter().take(20) {
            cx += step.delta_x as i32;
            cy += step.delta_y as i32;
            table_hit = Some((cx, cy));
        }
        
        if dda_hit == table_hit {
            matches += 1;
        }
    }
    matches as f32 / n_test_dirs as f32
}

fn main() {
    for &n in &[8, 16, 32, 64] {
        let acc = accuracy_test(n, 100);
        println!("Bin {}x{}: {:.1}% match with Grid DDA", n, n, acc * 100.0);
    }
}
```
