
# Day 619 · 资产标签的使用代码

> Day 618 搭好 asset tag 哈希基础设施。今天 Casey 把整个游戏里"硬编码的资产 ID"逐一改成"按 tag 查找"。例如代码原本写 `draw_sprite(SPRITE_WALL_STONE_ID, ...)`,改成 `draw_sprite(assets.get("wall_stone").unwrap(), ...)`。这是**重构日**,改动量大但难度低——核心是把"魔术数字"换成"语义字符串"。

## 0 · 为什么要有这一天

经过 Phase 7 + Day 618,资产系统的"查找基础设施"已经搭好。但游戏代码里仍然到处是**硬编码的资产 ID**:

```rust
// 旧代码
match tile_type {
    TileType::WallStone => draw_sprite(SPRITE_WALL_STONE_ID, x, y),
    TileType::WallWood => draw_sprite(SPRITE_WALL_WOOD_ID, x, y),
    TileType::DoorWood => draw_sprite(SPRITE_DOOR_WOOD_ID, x, y),
    // ... 几十个 match arm
}
```

这种代码有几个问题:

1. **资产 ID 是编译期常量**:换资产加载顺序、删除一个资产,代码都要重编
2. **没有语义**:`SPRITE_WALL_STONE_ID = 42` 看不出 "wall" 或 "stone"
3. **难扩展**:加新资产要改 enum + 改 ID 表 + 改所有 match
4. **难本地化**:不同语言版本的资产 ID 可能不同

**改造后的代码**:

```rust
// 新代码:按 tag 查
let sprite = match tile_type {
    TileType::WallStone => assets.get_sprite("wall_stone"),
    TileType::WallWood => assets.get_sprite("wall_wood"),
    TileType::DoorWood => assets.get_sprite("door_wood"),
    // ...
};
draw_sprite(sprite, x, y);
```

`assets.get_sprite("wall_stone")` 内部用 Day 618 的 FNV hash + HashMap,O(1) 查找。语义清晰,资产加载顺序变化不影响代码。

**今天的主题**:**代码重构的工程实践**。把"魔术数字 ID"换成"语义化 tag",不是简单查找替换——要保证:

1. **不破坏性能**:重构后帧率不变
2. **不破坏正确性**:每个 match arm 仍然渲染正确的资产
3. **代码可读**:语义清晰
4. **后续可扩展**:加新资产只改资产文件,不改源码

**心理锚点**:看完这集,你能:
- 在大型代码库里做"重构 + 性能 + 正确性"三重保证
- 把硬编码的 ID 替换成语义查找
- 用测试 + benchmark 验证重构没退化

## 2 · 心智模型

### 类比:整理仓库

你的车库堆满东西,每件东西有个编号(资产 ID)。最初编号随手写,东西放哪都没规律。时间一长:

- 你忘了"42 号是啥",要走到 42 号位置看一眼才知道
- 加新东西时,要重新决定下一个编号
- 太太说"把那个石头墙的装饰拿来",你要在脑子里映射"石头墙装饰 = 42 号"

整理方案:**给每件东西贴语义标签**("石头墙装饰"、"车库备用灯泡"、"圣诞树")。然后建一个**索引本**:标签 → 编号。查东西时先按标签查索引本,再拿东西。

- 一开始麻烦(每次查都要翻索引本)
- 但**索引本是 HashMap,O(1)**,几纳秒
- 好处:**任何人都能用语义标签查**(你太太、孩子、邻居),不用记编号

### 严谨:重构的工程模式

#### 2.1 重构前的代码

```rust
// constants.rs
pub const SPRITE_WALL_STONE_ID: u32 = 1;
pub const SPRITE_WALL_WOOD_ID: u32 = 2;
pub const SPRITE_DOOR_WOOD_ID: u32 = 3;
// ... 几十个

// renderer.rs
pub fn draw_tile(tile: TileType, x: f32, y: f32) {
    let sprite_id = match tile {
        TileType::WallStone => SPRITE_WALL_STONE_ID,
        TileType::WallWood => SPRITE_WALL_WOOD_ID,
        TileType::DoorWood => SPRITE_DOOR_WOOD_ID,
    };
    draw_sprite(sprite_id, x, y);
}
```

问题:
- `match` 退化为 `TileType` → 数字的纯映射
- 加新 `TileType` 要同时改 enum + constants + match
- `SPRITE_WALL_STONE_ID` 是"魔术数字"

#### 2.2 重构后的代码

```rust
// constants.rs:删掉所有 SPRITE_*_ID
// 新增:tag 常量(语义字符串)
pub const TAG_WALL_STONE: &str = "wall_stone";
pub const TAG_WALL_WOOD: &str = "wall_wood";
pub const TAG_DOOR_WOOD: &str = "door_wood";

// assets.rs:Day 618 的 AssetStore,加 get_sprite
impl AssetStore {
    pub fn get_sprite(&self, tag: &str) -> SpriteId {
        self.get(tag).expect("Missing sprite for tag")
    }
}

// renderer.rs
pub fn draw_tile(assets: &AssetStore, tile: TileType, x: f32, y: f32) {
    let tag = match tile {
        TileType::WallStone => TAG_WALL_STONE,
        TileType::WallWood => TAG_WALL_WOOD,
        TileType::DoorWood => TAG_DOOR_WOOD,
    };
    let sprite_id = assets.get_sprite(tag);
    draw_sprite(sprite_id, x, y);
}
```

**关键变化**:
- `match` 现在返回 `&str`(tag),而不是 `u32`(ID)
- tag 字符串是**语义化的**,读者立刻理解
- `assets.get_sprite` 内部 O(1) 查找,~10ns
- 加新 tile:加一个 `TAG_XXX` + 一个 match arm,不需要改资产 ID

#### 2.3 重构步骤(Casey 的实际流程)

```
Step 1: grep -rn "SPRITE_WALL_STONE" src/
        → 找到 20 个引用

Step 2: 在每个引用点附近加 debug assert:
        assert_eq!(assets.get_sprite("wall_stone"), SPRITE_WALL_STONE_ID);
        → 确认 hash 查找返回正确 ID

Step 3: 替换硬编码:
        -SPRITE_WALL_STONE_ID
        +assets.get_sprite(TAG_WALL_STONE)

Step 4: 跑游戏,目测无变化

Step 5: 删除 assert(只用于重构期验证)

Step 6: 删除 SPRITE_WALL_STONE_ID 常量定义

Step 7: grep 确认无残留引用
```

每个 ID 重复 5-7 步。如果有 100 个 ID,工作量 100 × 5 = 500 次操作。Casey 一天能做完(每小时 60 次)。

#### 2.4 性能验证

每次重构后跑 benchmark:

```rust
#[bench]
fn bench_draw_tile(b: &mut Bencher) {
    let assets = setup_assets();
    b.iter(|| {
        for _ in 0..1000 {
            draw_tile(&assets, TileType::WallStone, 0.0, 0.0);
        }
    });
}
```

预期:重构后 ~10ns/op 增量(每次 hash 查找),1000 tiles 渲染加 ~10us。**总帧时间应无明显变化**(< 1% 增量)。

如果增量 > 5%,说明 hash 函数选错或 inline 失败,需要排查。

### 2.5 单元测试验证

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_tag_lookup_matches_id() {
        let assets = setup_assets();
        // 重构正确性:hash 查找应该返回原来的 ID
        assert_eq!(assets.get_sprite("wall_stone").0, 1);
        assert_eq!(assets.get_sprite("wall_wood").0, 2);
        assert_eq!(assets.get_sprite("door_wood").0, 3);
    }

    #[test]
    fn test_missing_tag_panics() {
        let assets = setup_assets();
        let result = std::panic::catch_unwind(|| assets.get_sprite("nonexistent"));
        assert!(result.is_err());
    }
}
```

这些测试**永久保留**——任何后续重构都会跑这些测试,防止 tag 拼写错误或资产删除导致的回退。

### 2.6 重构的"安全网"

重构容易引入 bug。Casey 用三层安全网:

1. **编译期**:Rust 类型系统保证 `&str` 和 `u32` 不混淆
2. **运行期 assert**:重构期临时加,验证 ID 映射
3. **单元测试**:永久保留,长期保护

**这是工业级重构的标准做法**。比"凭感觉改"可靠 100 倍。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

资产 → tag 是游戏引擎的标配:

- **Unreal Engine**:`FName` 系统,所有资产引用通过 `FName`(interned string)
- **Unity**:`AssetReference` + Addressable Asset System
- **Godot**:`ResourceLoader.load("res://path/to/asset.tres")`,路径当 tag
- **Bevy**:`Handle<T>` 内部用 `AssetPath`,可序列化为字符串

**为什么要 tag/路径而非 ID**:

- 关卡设计师(非程序员)要按语义查
- modders 不能改源码,只能改资源
- 翻译/本地化时,资产 ID 不能依赖具体语言

**坑**:

- **打字错误**:`"wll_stone"` 拼写错,运行时 panic。解决:用 const 常量(`pub const TAG_WALL_STONE: &str`)而非字面量
- **资产改名**:`"wall_stone"` 改成 `"stone_wall"`,所有引用要更新。解决:加 lint 工具检查未使用的 tag
- **运行时发现缺失**:tag 不存在游戏崩溃。解决:启动时 sanity check 所有引用的 tag

### 3.2 · 🎨 图形学视角

图形 API 里也有类似机制:

- **OpenGL**:`GLuint` texture ID,运行时分配。无 tag 系统
- **Vulkan**:`VkImage` + `VkImageView`,显式管理。无 tag
- **DirectX 12**:`ID3D12Resource`,COM 接口。无 tag

**为什么低层 API 没 tag**:它们是"裸 GPU 资源"层,资产语义在上层。OpenGL 的 texture ID 类似 HH 的旧资产 ID——需要上层封装(tag)才有语义。

**Bevy 的 wgpu 抽象**:在 wgpu 之上加 `Handle<Image>` + AssetServer,实现 tag 查找。这就是 Casey 在 Day 618-619 做的事,工业引擎都做。

### 3.3 · 🐧 Linux 系统编程视角

Linux 也有"ID vs name"的二分:

- **inode number**:文件系统内的整数 ID,稳定但无语义
- **filename**:人类可读的"tag",通过 dentry cache 映射到 inode

访问文件时:

```bash
open("/home/user/file.txt", O_RDONLY)
```

内核流程:

1. 解析路径,逐级查 dentry
2. dentry cache 用 hash(filename) 加速
3. 最终拿到 inode number
4. 读 inode 数据

这和 HH 的 asset tag 完全一样:**人类用字符串(tag/filename),机器用整数(ID/inode),中间用 hash 桥接**。

#### `/proc` 文件系统的"tag"

`/proc/[pid]/` 里每个文件是一个"tag" → 进程内部数据:

```bash
ls /proc/$$/status  # 一个 tag
cat /proc/$$/status  # 内核读 tag,返回数据
```

内核内部用 `pid → task_struct` 的 hash 表,与 HH 的 `tag → AssetId` 异曲同工。

### 3.4 · 🦀 Rust 生态视角

Rust 表达"语义查找"有几种模式:

#### 模式 1:直接 &str + AssetStore

```rust
fn get_sprite(&self, tag: &str) -> SpriteId { ... }
```

简单,但 tag 拼写错误要运行时才发现。

#### 模式 2:newtype 包装 tag

```rust
#[derive(Copy, Clone)]
struct SpriteTag(&'static str);

impl SpriteTag {
    const WALL_STONE: Self = Self("wall_stone");
    const WALL_WOOD: Self = Self("wall_wood");
}

fn get_sprite(&self, tag: SpriteTag) -> SpriteId { ... }

// 使用
let id = assets.get_sprite(SpriteTag::WALL_STONE);
```

`SpriteTag` 是 newtype,编译期类型检查。`SpriteTag::WALL_STONE` 是 const,内联为字面量。**Casey 选这个**。

#### 模式 3:enum + match

```rust
enum SpriteTag { WallStone, WallWood, DoorWood }

impl SpriteTag {
    fn as_str(&self) -> &'static str {
        match self {
            Self::WallStone => "wall_stone",
            Self::WallWood => "wall_wood",
            Self::DoorWood => "door_wood",
        }
    }
}

fn get_sprite(&self, tag: SpriteTag) -> SpriteId {
    self.get(tag.as_str())
}
```

最类型安全(编译期穷尽检查),但加新 tag 要改 enum + match。

#### 模式 4:宏生成

```rust
macro_rules! sprite_tags {
    ($($name:ident => $tag:literal),* $(,)?) => {
        pub mod sprite_tags {
            $(
                pub const $name: &str = $tag;
            )*
        }
    };
}

sprite_tags! {
    WALL_STONE => "wall_stone",
    WALL_WOOD => "wall_wood",
}
```

宏自动生成 const,避免手写。最 DRY(Don't Repeat Yourself)。

**Casey 选择**:模式 2(newtype)。理由:类型安全 + 不需要宏黑魔法。

## 4 · 认知地图

### 4.1 上级

- **Refactoring**(重构)—— 改善代码结构而不改外部行为
- **Semantic indirection**(语义间接层)—— 用语义 key 代替实现细节
- **Loose coupling**(松耦合)—— 资产和代码不直接绑定 ID

### 4.2 同级

| 方案 | 类型安全 | 灵活度 | 性能 |
|---|---|---|---|
| 硬编码 ID(u32) | 无 | 无(编译期固定) | 最快 |
| &str 直接字面量 | 无(拼写错误) | 高 | O(1) ~10ns |
| newtype SpriteTag(本日) | 中(const 保证) | 高 | O(1) ~10ns |
| enum + match | 高(穷尽) | 低(加 tag 改 enum) | O(1) ~10ns |
| 路径字符串("res://...") | 无 | 极高(动态) | O(L) 路径长 |

### 4.3 下级

- **AssetStore**(Day 618)—— hash 查找基础设施
- **FNV-1a**—— hash function
- **newtype pattern**—— Rust 类型包装
- **const &str**—— 编译期字符串常量
- **单元测试**—— 重构正确性保证

## 5 · 对照与变奏

### 同一重构模式在不同语言

**问题**:把"魔术 ID"换成"语义查找"。

| 语言 | 推荐模式 |
|---|---|
| Rust | newtype + const(本日) |
| C++ | `constexpr std::string_view` |
| C | `#define TAG_WALL_STONE "wall_stone"` |
| Go | `const TagWallStone = "wall_stone"` |
| Python | class constants |
| Java | `public static final String TAG_WALL_STONE = "wall_stone";` |

核心都是"**给字符串起个语义化的常量名**"。

### 历史演化

- **1970s**:C 程序员用 `#define` 给常量起名
- **1990s**:C++ 引入 `const`、`inline`
- **2000s**:Java / C# 引入 `enum`,game engine 开始用 enum 替代裸 int
- **2010s**:data-driven 设计流行,资产和代码解耦
- **2020s**:Hot reload + asset tag 标配

### 数据驱动的极致

Casey 的 asset tag 是"半数据驱动"——tag 是字符串(数据),但 match arm 是代码。完全数据驱动:

```json
{
    "tiles": {
        "WallStone": { "sprite": "wall_stone", "collision": true },
        "WallWood": { "sprite": "wall_wood", "collision": true }
    }
}
```

加新 tile 只改 JSON,不改源码。但代价:运行时类型检查弱,改 JSON 容易出错。

**Casey 选择中间路线**:tag 是数据(字符串),match 是代码。平衡灵活和类型安全。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"用 tag 字面量 `"wall_stone"`"比"用 const `TAG_WALL_STONE = "wall_stone"`"差?给出三个理由。

**参考解答**:

1. **拼写错误风险**:字面量 `"wll_stone"` 运行时 panic;const `TAG_WLL_STONE` 编译期 error
2. **重命名困难**:字面量要 grep + 替换,容易漏;const 只改一处
3. **IDE 支持**:const 有自动补全 + 跳转,字面量没有

### Lv2 · 动手实践

**题**:实现一个 newtype `SpriteTag` 模式,要求:
- `SpriteTag::WALL_STONE`、`SpriteTag::WALL_WOOD` 等 const
- `AssetStore::get_sprite(tag: SpriteTag) -> SpriteId`
- 测试:`get_sprite(SpriteTag::WALL_STONE)` 返回正确 ID
- 验证:拼写错 `SpriteTag::WALL_STON`(少了 E)编译失败

完成标准:`cargo build` 通过 + `cargo test` 通过 + 故意拼错的版本编译失败(注释掉)。

**参考解答**:

```rust
use std::collections::HashMap;

const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

#[inline]
fn fnv1a(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    h
}

#[derive(Copy, Clone)]
struct SpriteTag(&'static str);

impl SpriteTag {
    const WALL_STONE: Self = Self("wall_stone");
    const WALL_WOOD: Self = Self("wall_wood");
    const DOOR_WOOD: Self = Self("door_wood");
}

#[derive(Copy, Clone, Debug, PartialEq)]
struct SpriteId(u32);

struct AssetStore {
    by_hash: HashMap<u64, SpriteId>,
}

impl AssetStore {
    fn new() -> Self {
        Self { by_hash: HashMap::new() }
    }
    fn register(&mut self, tag: SpriteTag, id: SpriteId) {
        let h = fnv1a(tag.0);
        self.by_hash.insert(h, id);
    }
    fn get_sprite(&self, tag: SpriteTag) -> SpriteId {
        let h = fnv1a(tag.0);
        *self.by_hash.get(&h).unwrap_or_else(|| panic!("Missing sprite for tag: {}", tag.0))
    }
}

fn main() {
    let mut store = AssetStore::new();
    store.register(SpriteTag::WALL_STONE, SpriteId(1));
    store.register(SpriteTag::WALL_WOOD, SpriteId(2));
    store.register(SpriteTag::DOOR_WOOD, SpriteId(3));

    assert_eq!(store.get_sprite(SpriteTag::WALL_STONE), SpriteId(1));
    assert_eq!(store.get_sprite(SpriteTag::DOOR_WOOD), SpriteId(3));

    println!("All assertions passed!");

    // 故意拼错的版本(取消注释应该编译失败):
    // let _ = store.get_sprite(SpriteTag::WALL_STON);
    // error: no associated item `WALL_STON` found for struct `SpriteTag`
}
```

**关键解释**:
- `SpriteTag(&'static str)` — newtype,内部是 `&'static str`(编译期字符串)
- `const WALL_STONE: Self = Self("wall_stone")` — 关联常量,内联为字面量
- `unwrap_or_else(|| panic!(...))` — 显式 panic 信息,比 `unwrap()` 更易调试
- 编译期检查:`SpriteTag::WALL_STON` 不存在 → 编译 error,而非运行时 panic

### 完整可跑的重构示例

```rust
// Cargo.toml: 空

use std::collections::HashMap;
use std::time::Instant;

const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

#[inline]
fn fnv1a(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    h
}

#[derive(Copy, Clone)]
struct SpriteTag(&'static str);

impl SpriteTag {
    const WALL_STONE: Self = Self("wall_stone");
    const WALL_WOOD: Self = Self("wall_wood");
    const DOOR_WOOD: Self = Self("door_wood");
    const TORCH: Self = Self("torch");
    const FOUNTAIN: Self = Self("fountain");
    const TREE_OAK: Self = Self("tree_oak");
    const TREE_PINE: Self = Self("tree_pine");
    const ROCK: Self = Self("rock");
    const GRASS: Self = Self("grass");
    const WATER: Self = Self("water");
}

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
struct SpriteId(u32);

struct AssetStore {
    by_hash: HashMap<u64, SpriteId>,
}

impl AssetStore {
    fn new() -> Self {
        Self { by_hash: HashMap::new() }
    }
    fn register(&mut self, tag: SpriteTag, id: u32) {
        let h = fnv1a(tag.0);
        self.by_hash.insert(h, SpriteId(id));
    }
    #[inline]
    fn get_sprite(&self, tag: SpriteTag) -> SpriteId {
        let h = fnv1a(tag.0);
        *self.by_hash.get(&h).expect("missing tag")
    }
}

// 旧式:硬编码 ID
mod legacy {
    pub const WALL_STONE: u32 = 1;
    pub const WALL_WOOD: u32 = 2;
    pub const DOOR_WOOD: u32 = 3;
    pub const TORCH: u32 = 4;
    pub const FOUNTAIN: u32 = 5;
    pub const TREE_OAK: u32 = 6;
    pub const TREE_PINE: u32 = 7;
    pub const ROCK: u32 = 8;
    pub const GRASS: u32 = 9;
    pub const WATER: u32 = 10;
}

fn setup() -> AssetStore {
    let mut s = AssetStore::new();
    s.register(SpriteTag::WALL_STONE, legacy::WALL_STONE);
    s.register(SpriteTag::WALL_WOOD, legacy::WALL_WOOD);
    s.register(SpriteTag::DOOR_WOOD, legacy::DOOR_WOOD);
    s.register(SpriteTag::TORCH, legacy::TORCH);
    s.register(SpriteTag::FOUNTAIN, legacy::FOUNTAIN);
    s.register(SpriteTag::TREE_OAK, legacy::TREE_OAK);
    s.register(SpriteTag::TREE_PINE, legacy::TREE_PINE);
    s.register(SpriteTag::ROCK, legacy::ROCK);
    s.register(SpriteTag::GRASS, legacy::GRASS);
    s.register(SpriteTag::WATER, legacy::WATER);
    s
}

fn main() {
    let assets = setup();

    // 正确性测试:每个 tag 应该返回原 ID
    assert_eq!(assets.get_sprite(SpriteTag::WALL_STONE).0, legacy::WALL_STONE);
    assert_eq!(assets.get_sprite(SpriteTag::WALL_WOOD).0, legacy::WALL_WOOD);
    assert_eq!(assets.get_sprite(SpriteTag::DOOR_WOOD).0, legacy::DOOR_WOOD);
    println!("Correctness: OK");

    // 性能测试
    let tags = [
        SpriteTag::WALL_STONE, SpriteTag::WALL_WOOD, SpriteTag::DOOR_WOOD,
        SpriteTag::TORCH, SpriteTag::FOUNTAIN, SpriteTag::TREE_OAK,
        SpriteTag::TREE_PINE, SpriteTag::ROCK, SpriteTag::GRASS, SpriteTag::WATER,
    ];

    let t0 = Instant::now();
    let mut sum = 0u64;
    for _ in 0..1_000_000 {
        for &tag in &tags {
            sum += assets.get_sprite(tag).0 as u64;
        }
    }
    let dt = t0.elapsed();
    println!("10M lookups: {:?} ({:.2} ns/op)", dt, dt.as_nanos() as f64 / 10_000_000.0);
    // 应该 ~10-20 ns/op

    // 重构前(直接用常量)的性能
    let t1 = Instant::now();
    let mut sum2 = 0u64;
    for _ in 0..1_000_000 {
        sum2 += legacy::WALL_STONE as u64;
        sum2 += legacy::WALL_WOOD as u64;
        // ... 简化,只测两个
    }
    let dt1 = t1.elapsed();
    println!("Constant access: {:?} ({:.2} ns/op)", dt1, dt1.as_nanos() as f64 / 2_000_000.0);
    // 应该 ~1 ns/op(常量比 hash 快 10 倍,但 10ns 仍可接受)

    println!("Overhead: {:.2}x", dt.as_nanos() as f64 / 10.0 / dt1.as_nanos() as f64 * 2.0);

    // 防止编译器优化掉
    println!("sum = {}, sum2 = {}", sum, sum2);
}
```

## 附录 · 重构的工程方法论

Day 619 的核心不只是"代码改造",更是**重构的工程方法论**。Casey 用的是经典的"小步快跑"重构模式,每一步都可验证、可回滚。

### 重构 vs 重写

新手常犯的错:**重构 = 重写**。其实不然:

- **重写**(rewrite):从零开始写新版本,旧版本丢掉。风险极大,经典案例 Netscape Navigator 5.0 重写导致公司倒闭
- **重构**(refactoring):**保持外部行为不变,改善内部结构**。每一步都通过测试

Casey 在 Day 619 做的是重构——游戏外观完全不变,但内部从"硬编码 ID"改成"tag 查找"。这就是马丁·福勒《Refactoring》一书的核心定义。

### 重构的安全网

| 安全网 | 何时用 | 代价 |
|---|---|---|
| 编译器类型检查 | 总是开 | 0(免费) |
| 单元测试 | 永久维护 | 写测试时间 |
| Integration tests | 关键模块 | 维护成本 |
| 运行期 assert | 重构期临时加 | 几 ns/assert |
| 手工目测 | 每次提交 | 主观,慢 |

Casey 用三层:类型检查 + 单元测试 + 重构期 assert。这是工业级标准做法。

### 重构的"两顶帽子"

马丁·福勒提出"两顶帽子"比喻:

- **重构帽子**:只改结构,不改功能
- **功能帽子**:只加功能,不改结构

**不要同时戴两顶**。Casey 在 Day 619 戴"重构帽子"——只改结构,不加新功能。如果发现 bug,先记下来,完成重构后再单独修。

### "Boy Scout Rule"

童子军规则:**离开营地时比来时更干净**。代码也是——每次改一个文件,顺手改一两处小问题(变量命名、注释、消除小重复)。

Casey 在 Day 619 替换 ID 时,顺手:
- 把变量名 `s` 改成 `assets`(语义清晰)
- 加 doc comment 解释为什么用 tag
- 把过长的函数拆开

这些"顺手清理"积累起来,代码质量持续提升。

### 重构的认知陷阱

新手重构常踩的坑:

1. **大爆炸重构**:一次改 1000 行,出 bug 找不到。**正确**:每次改 < 50 行
2. **重构 + 加功能**:同时改两层,出 bug 不知道是哪层。**正确**:两顶帽子分开戴
3. **没测试就重构**:重构完不知道有没有破坏。**正确**:先补测试,再重构
4. **重构不 benchmark**:重构完性能退化。**正确**:重构前 / 后 benchmark 对比
5. **重构完美主义**:重构没完没了。**正确**:有明确的"重构完"标准(如"所有 ID 都换 tag")

### 今天的认知收获

完成 Day 619,你应该理解:

- **重构是工程师的核心能力**:不是"重写",而是"小步快跑改善"
- **类型系统是第一道防线**:Rust newtype 让拼写错编译期暴露
- **hash 查找的代价是可接受的**:~10ns/op,对 60 FPS 游戏(16.6ms 预算)几乎免费
- **资产系统是"半数据驱动"的起点**:tag 是数据(字符串),代码是 logic(match)

带着这些认知,你后面看任何"魔术数字遍布"的老代码,都能问出**正确的问题**:
- 这些数字能改成语义查找吗?
- 有什么安全网保证重构正确?
- benchmark 能验证不退化吗?

day619 之后,你不仅会"写代码",更会"改代码"。这是从"码农"到"工程师"的关键跃迁。
