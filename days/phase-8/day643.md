# Day 643 · 猎捕碰撞 bug

> Day 642 修了 chunk 边界,但留下一些边角 bug。今天 Casey 把录制器开到最大,**系统地复现每一个 bug,定位根因,逐一修复**。这是 Phase 8 后期的典型工作:不再加新功能,而是**polish**(打磨)。

## 0 · 为什么要有这一天

游戏开发有个反直觉的现象:**最后 20% 的 polish,要花 80% 的时间**。加新功能("玩家能跳")很容易;但修边角 bug("玩家在东北角跳跃时偶尔会卡")要花几倍时间——因为 bug 触发条件诡异,根因隐藏在多层抽象下。

这条规律叫 **Pareto principle of polish**(打磨的帕累托原则):前 80% 的工作占 20% 时间,后 20% 占 80%。资深 game designer 反复强调:**不要把 polish 留到最后**——很多 polish 工作应该在功能开发时就同步做,否则会积重难返。

但完全避免 polish 阶段也不现实。一些 bug 只在功能完整后才能发现——"跳跃"和"墙角"独立测都 OK,组合起来才暴露 bug。所以工业流程是:**前期重视 polish,但接受最后还有 polish 阶段**。

今天的 bug 列表(实际 Casey 列了 5-6 个,精简):

1. **快速转身穿墙**:玩家高速转身时,某一帧球被推到墙外
2. **跳跃落地时下陷**:落地后球嵌入地面 0.05 米,玩家视觉上"陷一下"
3. **推墙时反复抖动**:玩家持续按 W 推墙,球每帧微抖
4. **斜坡滑落**:斜面上玩家"滑下去"——理论该静止,实际慢慢滑

每个 bug 的根因都不一样,但调试方法相同:**用录制器复现 → 单步 → 定位 → 修**。这就是"polish"阶段的工作模式。

**为什么 polish 阶段的 bug 这么难修?**

1. **触发条件复杂**:不是"按 A 就崩",而是"在 X 位置,以 Y 速度,做 Z 动作"才出现。手动测试覆盖率低。
2. **根因跨多个抽象层**:bug 表现是"穿墙",但根因可能是 update order + 浮点误差 + resolver 收敛慢,要逐层拆。
3. **修一个 bug 可能引起新 bug**:polish bug 之间互相依赖,改一处影响另一处。
4. **缺乏测试基础设施**:polish bug 涉及"感觉",自动化测试难。

这些困难让 polish 阶段成为项目最累的时期。资深程序员的能力主要在这里体现。

心理锚点:看完今天,你能:

- 系统化排查多个相关 bug
- 区分"逻辑 bug"和"参数 bug"
- 调参(precision、threshold、iteration count)
- 在多个修法中权衡(简单 hack vs 正确架构)
- 用"科学方法"调试任意 bug

## 1 · Casey 今天做了什么

Casey 用同一个 workflow 处理 4 个 bug:

**Bug 1:快速转身穿墙**

- 复现:固定速度旋转,在某角度穿墙
- 录制器:发现旋转时球的"瞬时速度"过大,跨过整个 voxel
- 根因:rotational velocity 没纳入 collision check
- 修法:每帧最大旋转角度 clamp,或者 rotation 也走 sweep collision
- 修复:**clamp 角速度**(简单但有效)

**Bug 2:落地陷下**

- 复现:从某高度跳下,看落地瞬间
- 录制器:落地时球的 y 从 -0.05 → 0.0,玩家视觉先陷再上来
- 根因:iterative resolver 走 4 轮才收敛,期间渲染帧已经画了"中间位置"
- 修法:**先把 resolver 跑完,再渲染**——逻辑和渲染解耦
- 修复:把 collision 放在 update 末尾,渲染之前

**Bug 3:推墙抖动**

- 复现:玩家推墙,看球的 x 坐标
- 录制器:x 在 0.5001 / 0.4999 之间振荡
- 根因:iterative resolver 不收敛——每轮推一点点,下一帧重力又拉回来
- 修法:**unembed 后立即"锁定"该轴速度**——推墙后玩家沿墙法线方向速度归零
- 修复:加 `collision_normal`,玩家速度沿法线分量清零

**Bug 4:斜坡滑落**

- 复现:玩家在斜面上静止,看 10 秒
- 录制器:y 缓慢下降
- 根因:每帧重力推球进斜面,resolver 推出,但有微小残余
- 修法:加 `ground_friction` —— 玩家在地面时,y 速度被快速衰减
- 修复:加 friction 系数

每个 bug 修完都跑一次完整 demo 确认没回归。

## 2 · 心智模型

### 类比:刷墙

刷墙分两次:**底漆**(把墙补平)和**面漆**(上色)。底漆要补裂缝、找平,这一步耗时但不显眼。游戏 polish 像刷底漆——玩家看不到你修了什么,但能感受到"游戏更顺了"。

每个 bug 单独看很小,但 100 个 bug 累积起来,就是"业余游戏"和"专业游戏"的区别。

### 速度法线分量清零

Bug 3 的修复涉及一个经典物理概念:**碰撞响应中的法线速度清零**。

球以速度 v 撞墙(墙法线 n)。撞墙后,速度 v 沿法线方向被吸收(弹性碰撞则反向 + 衰减)。数学:

```
v_normal = (v · n) * n    // 法线方向分量
v_tangent = v - v_normal  // 切线方向分量(沿墙)
v_after = v_tangent       // 法线分量清零(完全非弹性碰撞)
```

或带 restitution(弹性系数)`e`:

```
v_after = v_tangent - e * v_normal   // e=0 完全非弹性,e=1 完全弹性
```

这就是为什么 Bug 3 的修法是"沿法线清零速度"——玩家推墙时,法线方向速度被吸收,只剩切线方向(沿墙滑动),所以不再抖。

### Ground friction

Bug 4 的修法涉及 friction(摩擦力):

```
// 玩家在地面时
if on_ground {
    v.x *= 0.95;   // 每帧衰减 5%(沿地面方向)
    v.z *= 0.95;
    // y 速度由重力 + 法线响应控制,不衰减
}
```

这是简化版 Coulomb friction——每帧速度乘一个 < 1 的系数。物理上正确的 friction 是 `f = μ * N`(μ 是摩擦系数,N 是法向力),但游戏里用"每帧衰减"足够,代码简单。

### Bug 分类

游戏 bug 大致分四类:

1. **逻辑 bug**:代码做错事(穿墙 = 没检查某些 voxel)
2. **参数 bug**:代码对,参数错(epsilon 太大,iteration 太少)
3. **时序 bug**:代码对,执行顺序错(resolver 在渲染后才跑)
4. **架构 bug**:代码对,抽象不对(把 rotation 当 instant 没纳入 collision)

Casey 今天的 4 个 bug 覆盖全部 4 类:

| Bug | 类型 | 修法 |
|---|---|---|
| 快速转身穿墙 | 逻辑 | clamp 速度 |
| 落地陷下 | 时序 | 调 update / render 顺序 |
| 推墙抖动 | 参数 / 架构 | 加法线速度清零 |
| 斜坡滑落 | 参数 | 加 friction |

### 调试方法论

Casey 用统一的"科学方法":

1. **复现**:找一个 100% 触发的输入序列
2. **量化**:bug 出现时,某个数值是多少?(球的位置 / 速度)
3. **隔离**:去掉无关代码,bug 仍出现?
4. **假设**:可能是 X 导致
5. **验证**:改 X,bug 消失?
6. **回归**:bug 修了,但有没有引入新 bug?

这套方法在 Phase 0 的 [13-diagnosis-tools.md](../phase-0/13-diagnosis-tools.md) 详细讲过。今天的 4 个 bug 是这套方法的实例。

**为什么这套方法有效?**

人类大脑天生擅长"模式识别",但不擅长"逻辑推理多步"。如果直接从"看到 bug"跳到"猜测原因",大脑会用直觉,经常猜错(因为 bug 表象和根因常常无关)。

科学方法强制把"直觉猜"换成"假设 + 验证"。每一步:

- **复现**:把"偶发"变"必发",才能调试。复现脚本 = 调试的基础。
- **量化**:把"看起来抖"变成"x 在 0.4999 和 0.5001 间振荡"。量化才能比较"修前 / 修后"。
- **隔离**:确认 bug 不是别的代码引起。如果删一半代码 bug 还在,bug 在另一半。
- **假设 + 验证**:把猜测变成可证伪的命题。如果改 X 后 bug 消失,X 是根因(或相关);如果没消失,X 不是根因。
- **回归**:防止引入新 bug。工业实践用"bug 不再复现 + 完整测试套件"双重保证。

这套方法在所有工程领域通用——不仅游戏 bug,网络 bug、数据库 bug、kernel panic 都适合。它本质是**实验科学方法**在工程中的应用。

工业实践的延伸:

- **bisect**(二分调试):bug 是某次 commit 引入的?用 `git bisect` 二分查找。
- **differential debugging**:两个相似版本(一个有 bug,一个没 bug),diff 找差异。
- **statistical debugging**:bug 偶发?采集多次运行的 trace,统计"bug 时哪些代码路径执行"。
- **time-travel debugging**:UndoDB / rr / WinDbg TTT,让程序"倒回"到 bug 发生前。

这些工具都基于"科学方法"——假设、验证、迭代。资深工程师的工具箱越大,调试速度越快。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏 polish 的常见 bug 模式:

- **Camera clipping**:相机穿墙(用 camera collision,让相机也走 collision)
- **Animation desync**:动画状态机和物理状态机不同步
- **Audio latency**:音频相对画面滞后
- **Input buffering**:玩家按键没响应(按键应该 buffer 几帧)
- **Sticky cover**:玩家贴掩体后无法脱离

每个都有自己的 polish 模式。Casey 今天修的是 collision polish,其他 polish 在不同 day 处理。

**Camera clipping** 的经典 polish:玩家角色在第三人称视角,相机离角色 3 米。如果相机背后有墙,相机要么"穿墙"(看进墙里),要么"贴脸"(瞬间拉到角色头)。修法:

1. 相机做 raycast 从角色到相机理想位置,如果撞墙,移到撞墙点之前。
2. 加平滑插值,避免相机瞬移。
3. 如果距离过近,淡入第一人称或顶视角。

Unreal / Unity 都有内置的 camera collision 组件。但每个游戏还要调参——壁炉 / 楼梯 / 矮墙各有边角 case。

**Animation desync**:玩家按攻击键,动画状态机切换到"攻击中",但物理状态机仍允许移动。结果玩家"边攻击边跑步"。修法:把动画状态和物理状态联动——攻击时锁定移动。

**Input buffering**:玩家按"跳跃"时正在攻击中,不应该响应。但如果按完跳跃 0.1 秒后攻击结束,玩家的本意是"先攻击后跳",这时应该响应。修法:输入 buffer 100 ms,在合适时机重放。

**Sticky cover**:Gears of War 这种 cover-based shooter,玩家贴掩体后按方向键"脱离"有时无响应。修法:脱离方向 + 距离阈值,某些角度永远脱离,某些要双击。

这些都是 polish 阶段要解决的"手感"问题。资深游戏程序员的心得:**polish 是 90% 工程师做不好的部分**,因为需要艺术家般的细心和玩家般的直觉。Casey 在 HH 反复演示这种细心——每个 bug 都要"看到 → 理解 → 修",不能跳过。

### 3.2 · 图形学视角

法线速度清零在物理引擎里叫 **normal impulse**。Box2D / Havok 都用 sequential impulse 算法,每个约束解出一个 impulse,作用到物体上,改变其速度。Casey 简化为"直接清零",无 impulse 概念。

法线 vs 切线:**法线方向是"穿透"方向,要阻止**;切线方向是"滑动"方向,要允许但加 friction。

**Sequential impulse 算法**详解(工业级):

Box2D / Havok 解约束的方式是"迭代解 impulse"。每次迭代:

1. 对每个 contact constraint,计算"违反约束的程度"(法线方向速度负值 = 撞墙)
2. 计算"修正 impulse"= 把违反约束的速度归零需要的冲量
3. 把 impulse 作用到两个物体上,更新速度
4. 处理下一个 constraint
5. 全部处理完后,如果还有违反(因为 constraint 之间互相影响),重复 1-4

通常 8-16 次迭代就收敛。这是 Box2D `b2World::Step` 的核心算法,Erin Catto 在 GDC 演讲里详细讲过。

Casey 的简化版("直接清零")等价于"单次 impulse + 完全吸收"。这是 sequential impulse 的退化版,适合玩家这种"质量无穷大"的特殊物体。

**为什么工业用 impulse 而不是直接清零?**

因为 impulse 是物理量,可以正确处理"质量比"。重物撞轻物,轻物反弹多,重物反弹少。如果直接清零,违反物理直觉。

Casey 在 HH 没这个问题,因为玩家是"运动学物体"(kinematic),不受外力影响。但 NPC / 物品应该走 impulse 路径。

**图形学的另一个相关概念**:**Position-Based Dynamics (PBD)**。PBD 不解速度,直接解位置——把违反约束的物体移回约束内。Christoph Fedkiw 等人发明,Pixar 大量用。

PBD 和 Casey 的"unembed + 速度清零"思路类似——先修位置,再修速度。这是游戏物理和离线物理的桥梁。

最后,**friction 在物理引擎里也很微妙**。Coulomb friction(`f ≤ μN`)是个**不等式约束**,意味着"如果切向力 < μN,物体不滑;否则滑动 + 力 = μN"。这种"if-else"约束让 solver 复杂——要用 quadratic programming(QP)。Box2D 用简化版,假设 always 滑动(sliding friction)。Casey 用更简化的 per-frame decay,完全跳过"是否滑动"的判断。

### 3.3 · Linux 系统编程视角

Linux 内核也有"normal/tangent"的影子:

- **TCP 拥塞控制**:cwnd(窗口)在 bandwidth 探测(tangent)和 packet loss 恢复(normal)之间切换
- **Page reclaim**:active list(tangent)+ inactive list(normal)的 LRU
- **Scheduler CFS**:vruntime 推进(normal)+ nice 优先级(tangent)

物理和内核都用"约束 + 切线"的思路管理状态。

### 3.4 · Rust 生态视角

Rust 的所有权系统帮我们避免一类 bug:

```rust
// 错误(Rust 编译器拒绝)
fn update_player(player: &mut Player, world: &World) {
    let chunk = &world.chunks[&player.chunk]; // borrow world
    player.pos += chunk.get_velocity_at(player.pos); // borrow player (OK)
    world.update_chunk(player.chunk); // 再 borrow worldmutable —— 编译错误
}
```

borrow checker 强制"修改数据时不能有别名",避免迭代器失效 / use after free。Casey 在 C 里要手动管理(容易出 bug),Rust 编译器帮我们挡住。

Rust 在物理引擎领域的优势:

- **Send + Sync**:多线程物理(线程池并行解算多个 island)安全。C 引擎要手写锁,Rust 自动。
- **no_std 支持**:引擎能跑在嵌入式 / WASM,移植方便。
- **trait 系统的 dispatch**:碰撞 shape trait(`trait Shape { fn aabb(&self); fn collide(...); }`)让多种 shape(Sphere / Capsule / Convex)用统一接口。
- **宏的代码生成**:大量重复的物理公式(SAT、GJK、EPA)用宏生成,减少手写错误。

但 Rust 物理引擎仍有局限:

- **SIMD 表达能力弱**:Rust 的 portable SIMD API 仍在演化(`std::simd`),没有 C++ 的 `__m128` 那么直接
- **GPU compute 不成熟**:Rust 的 compute shader 生态(HAL、wgpu compute)比 CUDA / HLSL 弱
- **Real-time guarantees 弱**:Rust 默认 panic on overflow,游戏物理要 `panic = "abort"` + 自定义 allocator 才能跑 real-time

这些是 Rust 游戏生态正在解决的问题。**bevy_rapier** / **bevy_xpbd** 是当前主流 Rust 物理引擎,casey 风格的"手写物理"在 Rust 里更适合学习项目。

工业教训:**Rust 在物理引擎的 killer feature 不是性能,而是 refactoring safety**。物理引擎频繁重构(每加一个新 shape 都要改 dispatch),Rust 编译器保证改完不崩。C/C++ 物理引擎要写大量测试才能维持质量,Rust 编译器自带。

## 5 · 对照与变奏

不同碰撞响应模型:

| 模型 | 法线方向 | 切线方向 | 适用 |
|---|---|---|---|
| 完全非弹性(e=0) | 清零 | 保留 | ✅ 玩家碰撞 |
| 弹性(e=1) | 反向 | 保留 | 弹球游戏 |
| 部分弹性(0<e<1) | 反向 * e | 保留 | 真实物理 |
| 高摩擦 | 清零 | 强衰减 | 黏胶 |
| 低摩擦 | 清零 | 弱衰减 | 冰面 |

不同 friction 模型:

| 模型 | 公式 | 适用 |
|---|---|---|
| Coulomb | f = μN | 学校物理 |
| Viscous | f = -kv | 流体 |
| Per-frame decay | v *= 0.95 | ✅ 游戏 |
| Static + kinetic | 静摩擦 > 动摩擦 | 真实接触 |

Casey 用 per-frame decay,简单稳定。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"法线速度清零"能修推墙抖动 bug?

**参考解答**:玩家推墙时,速度 v 可以分解为法线方向(朝墙内)和切线方向(沿墙)。每帧 resolver 把球推回墙外(法线方向位移),但下一帧重力 / 输入又把球推向墙(法线速度不归零),所以球每帧"陷一点 + 推回一点",视觉抖动。把法线速度清零,球不再被推回墙内,稳定。

### Lv2 · 动手实践

**题**:实现"法线速度清零",模拟玩家推墙:

```rust
// 假设玩家撞墙,法线 (1, 0, 0)
let v = Vec3::new(2.0, 0.0, 1.0); // 玩家速度(朝墙 +x,沿墙 +z)
let n = Vec3::new(1.0, 0.0, 0.0); // 墙法线
let v_normal = v.dot(n) * n;
let v_after = v - v_normal;
println!("v_after: {:?}", v_after);
// 预期 (0, 0, 1) —— x 分量被清零,z 保留
```

**参考解答**:

```rust
use glam::Vec3;

fn main() {
    let v = Vec3::new(2.0, 0.0, 1.0);
    let n = Vec3::new(1.0, 0.0, 0.0);
    let v_normal = v.dot(n) * n;
    let v_after = v - v_normal;
    println!("v:       {:?}", v);
    println!("v_normal: {:?}", v_normal);
    println!("v_after: {:?}", v_after);
    // 应输出 v_after = (0, 0, 1)
}
```

### Lv3 · 迁移设计

**题**:把法线速度清零扩展成"部分弹性"——加 restitution 系数 e。撞墙后法线方向速度反向 * e。

**提示**:`v_after = v - v_normal - e * v_normal = v - (1 + e) * v_normal`

**推导**:撞墙前,速度 v 沿法线分量是 v_n = (v · n) * n。完全非弹性碰撞(e=0)后,法线速度 = 0(被吸收)。完全弹性(e=1)后,法线速度反向(反弹)。中间值 e∈(0,1)是部分弹性。

数学上,撞墙后 v_n_after = -e * v_n_before。所以:

```
v_after = v - v_n_before + v_n_after
        = v - v_n_before + (-e * v_n_before)
        = v - (1 + e) * v_n_before
```

实现:

```rust
fn collide_with_restitution(v: Vec3, n: Vec3, e: f32) -> Vec3 {
    let vn = v.dot(n) * n;       // 法线分量
    let vt = v - vn;              // 切线分量(沿墙滑动)
    // 法线分量反向 * e,切线保留
    let vn_after = -e * vn;
    vt + vn_after
}

fn main() {
    let v = Vec3::new(2.0, 0.0, 1.0);  // 朝 +x 方向走
    let n = Vec3::new(1.0, 0.0, 0.0);  // 墙法线朝 +x
    
    let v_plastic = collide_with_restitution(v, n, 0.0);
    println!("e=0 (plastic): {:?}", v_plastic);  // (0, 0, 1)
    
    let v_rubber = collide_with_restitution(v, n, 0.9);
    println!("e=0.9 (rubber): {:?}", v_rubber);  // (-1.8, 0, 1)
    
    let v_perfect = collide_with_restitution(v, n, 1.0);
    println!("e=1 (perfect): {:?}", v_perfect);  // (-2, 0, 1)
}
```

**应用场景**:

- **玩家撞墙**:e=0(完全非弹性),玩家不会反弹
- **弹球**:e=0.95,弹起 95% 高度
- **真实物理材质**:木头 e=0.5,钢 e=0.7,橡胶 e=0.9,玻璃 e=0.95
- **游戏手雷**:e=0.3,稍微弹一下就停

调试时,e 是关键调参——太大像橡胶,太小像泥潭。资深物理程序员花大量时间"调 e"。

更高级的模型:**位置依赖 restitution**——不同材质的墙有不同 e。例如,钢墙 e=0.9,木墙 e=0.4。需要材质查询系统。

工业级物理引擎(Box2D / Havok)支持 per-contact restitution,数据从物理材质表查询。Casey 简化为全局 e,够用。

## 8 · Rust / Arch 落地代码

完整碰撞响应(法线清零 + friction):

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::{Vec3, IVec3};

const GROUND_FRICTION: f32 = 0.92;
const AIR_FRICTION: f32 = 0.99;
const GRAVITY: f32 = -9.81;

struct Player {
    pos: Vec3,
    vel: Vec3,
    radius: f32,
    on_ground: bool,
    contact_normal: Vec3,
}

fn is_solid(v: IVec3) -> bool { v.y < 0 }

fn flood_collide(center: Vec3, r: f32) -> Vec<IVec3> {
    let lo = (center - Vec3::splat(r + 0.5)).floor().as_ivec3();
    let hi = (center + Vec3::splat(r + 0.5)).floor().as_ivec3();
    let mut solids = Vec::new();
    for z in lo.z..=hi.z {
        for y in lo.y..=hi.y {
            for x in lo.x..=hi.x {
                let v = IVec3::new(x, y, z);
                if is_solid(v) { solids.push(v); }
            }
        }
    }
    solids
}

fn resolve_and_get_normal(p: &mut Player) {
    p.contact_normal = Vec3::ZERO;
    p.on_ground = false;
    for _ in 0..8 {
        let voxels = flood_collide(p.pos, p.radius);
        let mut total_push = Vec3::ZERO;
        for v in voxels {
            let vmin = v.as_vec3() - Vec3::splat(0.5);
            let vmax = v.as_vec3() + Vec3::splat(0.5);
            let closest = p.pos.clamp(vmin, vmax);
            let d = p.pos - closest;
            let dist_sq = d.length_squared();
            if dist_sq < p.radius * p.radius && dist_sq > 1e-10 {
                let dist = dist_sq.sqrt();
                let push = d * (p.radius / dist - 1.0);
                total_push += push;
                // 累加法线(取每个 voxel 的法线)
                if push.y > 0.1 { p.on_ground = true; }
                p.contact_normal += d / dist; // 单位向量累加
            }
        }
        if total_push.length_squared() < 1e-8 { break; }
        let len = total_push.length();
        let step = if len > 0.05 { total_push * (0.05 / len) } else { total_push };
        p.pos += step;
    }
    if p.contact_normal.length_squared() > 1e-6 {
        p.contact_normal = p.contact_normal.normalize();
    }
}

fn update_player(p: &mut Player, dt: f32) {
    // 重力
    p.vel.y += GRAVITY * dt;

    // 移动
    p.pos += p.vel * dt;

    // 碰撞
    resolve_and_get_normal(p);

    // 法线速度清零
    if p.contact_normal.length_squared() > 1e-6 {
        let vn = p.vel.dot(p.contact_normal);
        if vn < 0.0 {
            // 速度有沿法线负方向(撞向墙)的分量
            p.vel -= vn * p.contact_normal;
        }
    }

    // friction
    let damp = if p.on_ground { GROUND_FRICTION } else { AIR_FRICTION };
    p.vel.x *= damp;
    p.vel.z *= damp;
}

fn main() {
    let mut p = Player {
        pos: Vec3::new(0.5, 5.0, 0.5),
        vel: Vec3::new(2.0, 0.0, 0.0),
        radius: 0.4,
        on_ground: false,
        contact_normal: Vec3::ZERO,
    };
    for i in 0..120 {
        update_player(&mut p, 1.0 / 60.0);
        if i % 30 == 0 {
            println!("t={:.2}: pos={:?} vel={:?} on_ground={}",
                i as f32 / 60.0, p.pos, p.vel, p.on_ground);
        }
    }
}
```

## 10 · 工程反思

Day 643 传达的核心教训:**polish 是工程的镜子,反映项目成熟度**。

具体的三条反思:

**教训一:Bug 修复要"标本兼治"**。"标"是症状(穿墙、抖动),"本"是根因(速度未清零、friction 缺失)。**只修标不修本,bug 会反复出现**。Casey 修每个 bug 都追到根因,而不是加 hack。这是资深工程师的关键能力。

例如 Bug 3(推墙抖动),简单 hack 是"加 epsilon,允许微小嵌入"。这样能"看起来修了",但根本问题(速度没清零)还在,后面会以其他形式出现。Casey 修法是加法线速度清零——治本,后续 polish 都受益。

**教训二:Polish 要有"工程纪律"**。复现、量化、隔离、假设、验证、回归——这套方法不能省。资深工程师即便"一眼看出 bug",也走完这套流程,因为:

1. 防止"看起来修了实际没修"
2. 留下文档,新人能 follow
3. 测试套件受益(回归测试)

这是"工程师思维"vs"hacker 思维"的分水岭。

**教训三:接受 polish 阶段的存在**。新人对"polish 占 80% 时间"感到沮丧,觉得"为什么不能像早期那样快速推进"。资深工程师接受这是必然,**前期能 polish 就同步做,后期接受慢节奏**。

工业教训:**很多独立游戏死于 polish 阶段**——开发者低估 polish 时间,release 日期一拖再拖,资金耗尽。资深开发者用"垂直切片"(vertical slice)方法论:**早期做一个完整的小片段(角色 + 关卡 + UI + 音效),保证 polish 流程跑通,再扩展内容**。这样 polish 时间可预估,不会拖延。

Casey 在 HH 反复演示这套节奏:**先做最小可玩版本,再 polish,再扩展**。Day 643 是 polish 阶段的高峰,接下来 Day 644-667 仍然是 polish + 简化 + 最终发布。
