> 你打开 `lighting.rs` 滚动——1500 行。滚到中间,看到三个函数 `propagate_direct_light`、`propagate_indirect_light`、`propagate_indirect_v2`,前两个还在用,第三个标了"TODO 删除"但没删。再往下,`grid_dda_raycast`、`kdtree_raycast`、`walktable_raycast` 三个光线投射实现,签名各不相同——一个返回 `Option<HitInfo>`,一个返回 `Result<Vec<HitInfo>, Error>`,一个返回原始 `Vec<(i32,i32,i32)>`。调用方写三个不同的代码块来处理。这是 Day 576-604 累积 30 天的"代码债"。今天 Casey 做第二次大清理:删冗余、统一接口、拆模块、加文档。**零新功能**,纯重构,但代码库回到"健康"状态。下一周的开发速度因此提升 50%。

## 0 · 为什么要有这一天

软件工程有一条铁律叫 **software rot**(软件腐烂):**代码不维护就会腐烂,即便它什么都不做**。听起来反直觉——代码又不会"坏掉",怎么会腐烂?让我解释为什么这件事真实存在,以及为什么"定期重构"是它的唯一解药。

代码腐烂的根源是**上下文流失**。设想你 30 天前写了一段代码:

```rust
// Day 576: 实现 propagate_direct_light
fn propagate_direct_light(scene: &Scene, light: &Light) -> LightMap {
    // ... 200 行实现 ...
}
```

写这段代码时,你脑子里有完整的 mental model——你记得 propagate 是为渲染管线准备的,你记得 LightMap 的格式约定,你记得为什么用 `&Light` 而不是 `Light`,你记得边界 case 怎么处理。

30 天后(Day 605),这个 mental model 已经**部分流失**。你做过 30 天其他工作,Day 576 的细节模糊。这时你打开 `propagate_direct_light` 想"加个参数让它支持 shadow",你怎么办?

- 你**重读代码**,试图重建 mental model。花 30 分钟。
- 重读时你**忽略了一些边界 case**(因为不显眼),可能引入 bug。
- 你**重复实现**了某些已存在的辅助函数——你以为它们不存在,或懒得找。

这还只是一个函数。30 天里你写了 2000+ 行新光照代码,里面有这样的"半遗忘"函数 50 个。每个都需要重读、可能引入 bug、可能重复实现。**累积成本巨大**。

代码腐烂的具体症状:

**症状 1:Dead code 累积**。你写了 `propagate_indirect_v2`(用新算法重做),但忘了删 `propagate_indirect_v1`。v1 现在没人调用——但因为还在编译产物里,新人读代码会问"v1 和 v2 哪个在用?",浪费认知资源。Dead code 还增加编译时间、增加 binary 体积、阻碍 IDE 跳转。

**症状 2:接口不一致**。同一概念有多套实现,签名各异。你的三个 raycast 实现签名不同,调用方要写"if 是 grid_dda 就这样调,if 是 kdtree 就那样调"。新代码沿用最近的模式,旧代码沿用旧模式——签名的"多样性"不断增长。

**症状 3:文件膨胀**。`lighting.rs` 从 Day 576 的 200 行增长到 Day 604 的 1500 行。IDE 加载慢、git diff 上下文不够、code review 时滚动疲劳。

**症状 4:文档欠债**。早期函数有 doc comment,后期函数没。新人读代码遇到没文档的函数,要么猜要么问。问浪费团队时间,猜可能错。

**症状 5:测试覆盖不均**。早期函数有完整单测,后期函数没测。重构时无测的部分容易出 bug。

这些症状**不会自己消失**。Dead code 不会"自动删",接口不会"自动统一",文档不会"自动长出来"。除非你**主动清理**。

工业界的标准做法叫**定期重构**(periodic refactoring)。Martin Fowler 在《Refactoring》里定义:重构是"在不改变代码外部行为的前提下,改变其内部结构"。重点:**不改变行为**——所有测试必须仍通过。**改变结构**——更清晰、更可维护。

重构的频率:
- **每次 PR 微重构**(持续):改一个函数时,顺手清理它的相邻代码
- **每里程碑大重构**(定期):每个 sprint / 里程碑做一次系统化清理
- **每版本架构重构**(战略):每个大版本考虑架构调整

Casey 的 Day 605 是**里程碑大重构**——30 天累积的债一次性还清。这种重构的标志:
- 0 行新功能代码
- 0 行测试改动(因为行为不变)
- 大量"删 + 移 + 改名"
- PR description 写"refactor: ..."

重构不是奢侈品,是**必需品**。如果你不重构,代码腐烂累积到某个临界点,新功能开发速度趋近于零——所有时间都花在"理解烂代码"上。工业界叫这个**legacy code trap**(遗留代码陷阱),Michael Feathers 的《Working Effectively with Legacy Code》专门讨论。

**学完今天,你应该能**:
- 识别代码腐烂的 5 个症状
- 用 `cargo +nightly udeps` 找未使用代码
- 用 `trait` 统一多套接口
- 用 Rust module 系统拆大文件
- 写出能通过 `cargo doc` 的 doc comment
- 区分"重构"(行为不变)和"重写"(行为可能变)
- 用 Rust 编译器保证重构安全(类型 / borrow / 死代码检测)

## 1 · Casey 今天做了什么

Casey 这一天的工作量按代码行数算不多(改 200 行,删 100 行),但思考量大。完整动作:

**动作 1:用工具找 dead code**。Casey 跑 `cargo +nightly udeps`(nightly 工具链的 unused dependencies 检测)和手动 `grep`:

```bash
# 找 unused dependencies(Cargo.toml 里声明但代码没 use)
rustup toolchain install nightly
cargo +nightly install cargo-udeps
cargo +nightly udeps

# 找 unused functions(定义了但没调用)
# 用 grep:如果函数名只在定义处出现一次,就是 dead
for fn in $(grep -E '^\s*fn\s+\w+' src/lighting.rs | awk '{print $2}' | cut -d'(' -f1); do

    fi
done

## 2 · 心智模型

### 2.1 类比:房间定期整理

让我打个比方把"定期重构"钉在脑子里。

你住在一个公寓。每天生活:起床、做饭、上班、回家、做饭、睡觉。每天产生一些"杂物"——衣服随手放椅子上,碗堆在水槽里,邮件随手扔桌上,充电线缠在沙发上。

第一周:房间看起来还行。杂物有一些,但你记得每样东西在哪。找袜子?在椅子左下角。找钥匙?门边鞋柜。找账单?桌上某处。

第二周:杂物累积。你开始忘记东西在哪。找袜子要翻 5 分钟,找钥匙要翻 10 分钟。生活效率降低。

第三周:房间乱到无法忍受。你下定决心,周末花 4 小时彻底整理:
- **扔掉没用的**(过期的食物、坏掉的电器)—— 等价删 dead code
- **归类放置**(衣服进衣柜、碗进橱柜、邮件归档)—— 等价拆模块
- **统一容器**(鞋盒装鞋、文件夹装文件)—— 等价定义 trait
- **标注**(标签纸写"重要账单")—— 等价加 doc comment

整理后,房间回到第一周状态。下周生活效率高。然后**又开始累积**——这是 entropy。

代码完全一样。每次开发产生"杂物"——临时变量、debug print、TODO 注释、试错代码。如果不整理,累积到无法维护。定期重构 = 周末整理房间。

这个比方的核心洞察:**整理不是奢侈品,是必需品**。即便没人要求,你也要主动整理——否则 entropy 让你越来越慢。

但这个比方还有一个深层教训:**整理是周期性的,不是一次性的**。Casey 的 Day 583 做过一次清理,30 天后(Day 605)又要清理。这是 software entropy 的本质——开发就有积累,积累就要清理。**没有"一次清理就永远干净"的代码库**。

### 2.2 第一性原理:代码腐烂的物理学

让我用更严肃的语言讨论代码腐烂。它本质是 **information entropy** 的体现。

每行代码有**信息含量**——它表达了开发者的意图。但随着时间推移,代码上下文变化,信息含量"衰减":

- 代码刚写时:信息含量 100%(开发者完全理解)
- 30 天后:开发者记忆模糊,信息含量 60%
- 90 天后:开发者基本忘记,信息含量 20%
- 1 年后:开发者完全忘记,信息含量 5%(代码看起来像别人写的)

衰减率取决于:
- **代码可读性**:好的命名 / 文档衰减慢,坏的衰减快
- **变更频率**:经常修改的代码,因每次修改更新理解,衰减慢
- **依赖复杂度**:依赖多的代码,理解它需要先理解依赖,衰减快
- **测试覆盖**:有测试的代码,可以通过测试重建理解,衰减慢

代码腐烂就是"信息含量衰减导致维护成本上升"。重构是"主动补充信息含量"——通过清理结构、加文档、加测试,让信息含量回到 100%。

**重构的成本/收益**:
- **成本**:重构本身的时间(几小时到几天)
- **收益**:未来 N 天的开发速度提升

数学上:
```
收益 = (开发速度提升) × (受益天数)
成本 = (重构时间)

if 收益 > 成本,做重构。
```

Casey 的 Day 605 重构花一天(8 小时)。如果未来 30 天开发速度提升 20%(每天省 1.6 小时),总收益 = 30 × 1.6 = 48 小时。**净收益 40 小时**。值。

但如果重构花一周(40 小时),未来 30 天只提升 5%(每天省 0.4 小时),总收益 = 12 小时。**净亏 28 小时**。不值。

这个 cost/benefit 分析是判断"何时重构"的核心。Casey 的判断是 30 天累积的债已经到"清理一天收益巨大"的临界点。

### 2.3 严谨模型:清理步骤

让我把 Casey 的清理步骤详细展开,你会看到每一步对应的工具和考量。

**步骤 1:找 dead code**

```bash
# 装 nightly 工具链
rustup toolchain install nightly

# 装 cargo-udeps
cargo +nightly install cargo-udeps

# 跑 unused deps 检测
cargo +nightly udeps
# 输出例:
# warning: Package `rayon` was specified in Cargo.toml but never used
# warning: Function `propagate_v2` was defined but never called

# 手动 grep 找 unused functions
grep -rn "propagate_v2" src/
# 如果输出只有 src/lighting.rs:42:fn propagate_v2(...)  这一行
# (就是定义本身,没有任何调用),就是 dead code
```

判断 dead code 的谨慎之处:
- **pub fn** 可能在下游 crate 用(库代码),不能删
- **#[cfg(test)] fn** 只在测试时调用,不是 dead
- **macro 生成的代码** cargo-udeps 可能误报
- **trait methods** 必须 pub(可能被外部实现),不能删

Casey 删 5 个函数前,每个都确认是"内部函数 + 没人调用"。

**步骤 2:统一 API**

定义 trait:

```rust
/// 光线投射器 trait。所有 raycast 实现都实现这个 trait。
pub trait Raycaster {
    /// 投射一条光线,返回最近的命中信息。
    ///
    /// # 参数
    /// - `ray`:光线(起点 + 方向,方向必须是单位向量)
    /// - `max_dist`:最大距离(超出返回 None)
    ///
    /// # 返回
    /// - `Some(HitInfo)`:命中
    /// - `None`:未命中(超出 max_dist 或走出场景)
    fn raycast(&self, ray: &Ray, max_dist: f32) -> Option<HitInfo>;
}

impl Raycaster for GridDda {
    fn raycast(&self, ray: &Ray, max_dist: f32) -> Option<HitInfo> {
        // Grid DDA 实现
    }
}

impl Raycaster for KdTree {
    fn raycast(&self, ray: &Ray, max_dist: f32) -> Option<HitInfo> {
        // k-d tree 实现
    }
}

// 调用方
fn render_pixel<R: Raycaster>(raycaster: &R, ray: &Ray) -> RGB32F {
    if let Some(hit) = raycaster.raycast(ray, 100.0) {
        compute_lighting(hit)
    } else {
        sky_color()
    }
}
```

trait 让调用方**不依赖具体类型**——可以传 GridDda、KdTree、或未来的新实现。这是 Rust 实现"多态"的标准方式。

为什么用 trait 不用函数指针?
- **trait 静态分发**:编译时已知类型,LLVM 内联优化,零开销
- **函数指针动态分发**:运行时查 vtable,无法内联,有 ~5ns 间接调用开销
- **trait 还能定义关联类型、默认方法**:函数指针做不到

Casey 用 trait(性能优先,游戏开发标准)。

**步骤 3:拆模块**

原来 `src/lighting/mod.rs` 是单文件:

```rust
// lighting/mod.rs - 1500 行
pub fn propagate_direct_light(...) { ... }
pub fn propagate_indirect_light(...) { ... }
fn grid_dda_raycast(...) { ... }
fn kdtree_raycast(...) { ... }
fn walktable_raycast(...) { ... }
pub struct LightAtlas { ... }
impl LightAtlas { ... }
pub struct TraceRecorder { ... }
// ... 等等 ...
```

拆成多文件:

```
src/lighting/
├── mod.rs           ← 子模块声明 + pub 重导出
├── atlas.rs         ← LightAtlas
├── raycast.rs       ← GridDda + WalkTableRaycaster
├── kdtree.rs        ← KdTree
├── propagate.rs     ← propagate 函数
└── trace.rs         ← TraceRecorder
```

`src/lighting/mod.rs` 的内容:

```rust
// 声明子模块
mod atlas;
mod raycast;
mod kdtree;
mod propagate;
mod trace;

// 重导出公共 API
pub use atlas::LightAtlas;
pub use raycast::{GridDda, WalkTableRaycaster, Ray, HitInfo};
pub use kdtree::KdTree;
pub use propagate::{propagate_direct_light, propagate_indirect_light};
pub use trace::TraceRecorder;

// pub use 让外部写 `use crate::lighting::LightAtlas` 而不是
// `use crate::lighting::atlas::LightAtlas`
// 隐藏内部模块结构
```

每个子文件职责单一,典型 < 300 行。IDE 加载快,git diff 上下文清晰,code review 友好。

Rust module 系统的关键概念:
- `mod foo;` — 声明子模块(在 `foo.rs` 或 `foo/mod.rs` 找代码)
- `pub mod foo;` — 子模块对外可见
- `pub use foo::Bar;` — 重导出 `foo::Bar` 让外部直接用
- 默认所有 mod / fn / struct 是**私有**(只有同模块可见)
- `pub` 让其公开

**步骤 4:加文档**

每个 pub 接口加 `///` doc comment:

```rust
/// 光照贴图。存每个 voxel 的光照值(RGBE 格式)。
///
/// # 字段
/// - `width`, `height`, `depth`: voxel 网格尺寸
/// - `data`: 紧凑存储的光照数据(RGBE 4 字节/voxel)
///
/// # 用法
/// ```
/// use handmade_hero::lighting::LightAtlas;
///
/// let atlas = LightAtlas::new(32, 32, 32);
/// atlas.set(0, 0, 0, [1.0, 1.0, 1.0]);
/// let color = atlas.get(0, 0, 0);
/// ```
pub struct LightAtlas {
    width: u32,
    height: u32,
    depth: u32,
    data: Vec<u8>,
}
```

doc comment 规则:
- `///` 是单行 doc(在 item 之前)
- `//!` 是 module-level doc(在文件顶部)
- 文档支持 markdown(标题、列表、代码块)
- 代码块 ``` ``` 是 doc test,`cargo test` 会跑

`cargo doc --open` 生成 HTML 文档,浏览器打开。这是 Rust 的 killer feature 之一。

**步骤 5:跑测试**

```bash
cargo test
# running 87 tests
# test lighting::atlas::tests::test_set_get ... ok
# test lighting::raycast::tests::test_grid_dda_basic ... ok
# test result: ok. 87 passed; 0 failed

cargo clippy  # lint 检查
cargo fmt     # 格式化
```

测试全过 = 行为不变 = 重构成功。如果某个测试失败,要么是重构改了行为(bug),要么是测试太依赖实现细节(test smell)。

### 2.4 清理前后对比

**清理前**(混乱):

### 3.1 · 🎮 游戏编程视角

游戏工业里"定期重构"是核心工程实践。让我严肃讨论几个游戏引擎的重构节奏和经验。

**Unreal Engine 的重构节奏**:
- **每次 PR 微重构**:每个 PR 必须 code review,reviewer 检查"代码风格、命名一致性、模块归属"。Epic 内部 CI 跑大量 lint。
- **每个 milestone 大重构**:UE 把开发分 milestone(几周到几个月)。每个 milestone 末有"polish week",专门清理。
- **每个大版本架构重构**:UE 4 → UE 5 是巨大重构(5 年开发)。Nanite / Lumen 是新架构,GPU-driven pipeline 重写。

UE 5 相对 UE 4 的清理成果:
- 删了 deprecated API(几百个类)
- 统一了 rendering API(RHI 重写)
- 模块拆分更细(`Engine/Source/Runtime/` 下 200+ 模块)

**Unity 的清理经验**:Unity 经历过几次大规模重构,伴随痛苦:
- **Unity 2018→2019**:SRP(HDRP/URP)取代 Built-in Pipeline。旧代码标记 deprecated 但保留(向后兼容),新代码走 SRP。**双轨制**导致 5 年里维护两套渲染。
- **Unity DOTS**(2019+):ECS 重构,旧 MonoBehaviour 保留。又是双轨制。
- **教训**:Unity 的"不删旧代码"政策让代码库巨大(GB 级),但避免了 break 用户。Trade-off。

**Bevy 的清理文化**:Bevy 是开源,有明确的"breaking change 节奏":
- 每个主版本(0.x → 0.(x+1))允许 breaking change
- 旧 API 在 PR 里讨论后删除(无 deprecation period)
- 每次发版前做大规模 cleanup PR

Bevy 0.10 → 0.11 → 0.12 都有几十个 cleanup PR,删了几千行 deprecated 代码。这种"激进清理"在开源世界可行(用户跟得上),在企业产品里不行(用户依赖旧 API)。

**Casey 的 HH 文化**:Handmade Hero 是教学项目,Casey 自己一人维护。他可以激进清理(没有用户依赖)。Day 583、Day 605、Day 663 都是定期 cleanup。

**踩过的坑**(工业实践):
- **过度重构**:某团队为"完美架构"重构 6 个月,功能延迟,产品死。教训:**重构不是目的,产品才是**。
- **不重构**:某团队 5 年不重构,代码腐烂到无法加新功能。教训:**不重构的代价是渐进的,但累积致命**。
- **重构期间出 bug**:某团队重构后没跑 integration test,生产环境崩。教训:**重构必须有完整测试覆盖**。
- **重构 PR 太大**:某团队 5000 行 cleanup PR,review 一周,合并冲突。教训:**拆小 PR,每个 < 500 行**。

Casey 的 Day 605 是中型 PR(几百行),review 时间适中,是工业推荐的尺度。

### 3.2 · 🎨 图形学视角

图形代码的清理有特殊性。让我讲讲图形程序员视角的 cleanup。

**Shader 代码清理**。Shader 是另一套代码(HLSL/GLSL/WGSL),清理规则不同于 Rust/C++:
- **shader 变量不能简单删**:GPU pipeline state 依赖某些 uniform 存在。删 uniform 要确保 renderer 不再 set 它,否则 GPU validation error
- **shader permutation 管理**:同一 shader 有多个变体(defines 组合)。重构 permutation 系统是大事
- **shader reflection**:shader 编译后 reflection 给出 input/output 签名。重构时 reflection 数据要更新

**Buffer 管理清理**。GPU buffer 有生命周期约束:
- buffer 在 use 期间不能 unmap(否则 GPU 读 garbage)
- buffer 的同步依赖 fence,清理时不能破坏 fence 顺序
- 大 buffer 的 realloc 慢(几 ms),清理时不能在 hot path realloc

**Texture format 统一**。多个模块可能用不同 texture format(BC1 / BC7 / R8G8B8A8 / R32F)。清理时统一 format,但要注意:
- 不同 format 占用 VRAM 不同(BC1 = 0.5 byte/pixel,R8G8B8A8 = 4 byte/pixel)
- 不同 format 采样性能不同(BC 压缩快,R32F 慢)
- 重构 format 可能改变 visual quality(BC1 有损)

**Casey 的特殊情况**:Phase 8 还在 CPU 渲染(软件光栅化),所以 cleanup 简单——没有 GPU pipeline 的约束。Phase 5+ 之后切到 GPU,cleanup 复杂度上升一个量级。

**Render pipeline 重构的典型模式**:

```rust
// 反模式:每次 draw call 单独 set state(状态切换昂贵)
for obj in &objects {
    cmd_buf.set_shader(obj.shader);
    cmd_buf.set_texture(obj.texture);
    cmd_buf.draw(obj.mesh);
}

// 重构后:按 state 排序,batch draw(state 切换少)
let mut sorted = objects.clone();
sorted.sort_by_key(|o| (o.shader.id, o.texture.id));

let mut cur_shader = None;
let mut cur_texture = None;
for obj in &sorted {
    if cur_shader != Some(obj.shader.id) {
        cmd_buf.set_shader(obj.shader);
        cur_shader = Some(obj.shader.id);
    }
    if cur_texture != Some(obj.texture.id) {
        cmd_buf.set_texture(obj.texture);
        cur_texture = Some(obj.texture.id);
    }
    cmd_buf.draw(obj.mesh);
}
```

这是"sort by state"重构,工业 GPU 渲染的标准优化。

### 3.4 · 🦀 Rust 生态视角

Rust 的特殊工具让重构**比其他语言安全**。让我详细讲几个。

**1. 编译器强约束**。Rust 编译器强制类型 / 借用规则,重构时编译错立即暴露。

C++ 重构可能引入"运行时 crash 但编译过",bug 难找。Rust 编译错 95% 的重构 bug 在编译时——你不会运行时才发现"use after free"或"double free"。

具体表现:
- 改函数签名:所有调用站点编译错
- 改 struct 字段:所有访问编译错
- 改 module 路径:所有 `use` 编译错
- 改 trait 方法:所有 `impl` 编译错

每个编译错都是"重构 bug 的现场",编译器精确告诉你修哪里。这是 Rust 的杀手锏。

**2. `cargo fix`**。自动修复 clippy warnings。

```bash
cargo clippy --fix --allow-dirty
# 自动应用所有"safe"的 lint fix
```

某些 clippy 规则有"自动修复"版本(比如 `if x > 0 { true } else { false }` → `x > 0`)。`cargo fix` 自动改。

**3. Trait 抽象**。前面讲过——trait 让接口稳定,实现可换。

```rust
trait Raycaster { ... }

// 切换实现只需改一行
let raycaster: Box<dyn Raycaster> = Box::new(WalkTableRaycaster::new());
// 改成 GridDda:
let raycaster: Box<dyn Raycaster> = Box::new(GridDda::new());
```

或者用泛型(静态分发,零开销):
```rust
fn render<R: Raycaster>(r: &R, ...) { ... }

// 调用方
render(&WalkTableRaycaster::new(), ...);  // 编译时单态化
render(&GridDda::new(), ...);  // 另一个版本
```

**4. Module 系统**。Rust 的 module 系统让"拆文件"简单。

```rust
// lighting/mod.rs
mod atlas;     // 内部 mod,外部不可见
mod raycast;   // 外部通过 pub use 间接访问

pub use atlas::LightAtlas;  // 重导出,外部用 crate::lighting::LightAtlas
```

Module 可见性规则:
- `mod foo;` — 子模块,默认私有(只有父 mod 可见)
- `pub mod foo;` — 子模块,外部可见
- `pub use foo::Bar;` — 重导出
- `pub(crate) use foo::Bar;` — 仅 crate 内可见(隐藏 API 细节)

`pub(crate)` 是工业 Rust 的常用模式——内部共享但不暴露给下游。

**5. type alias 简化签名**。

```rust
// 清理前
fn complex_fn(map: &HashMap<u32, Arc<LoadedAsset>>) -> Result<Vec<(u32, HitInfo)>, Box<dyn Error>> { ... }

// 清理后
type AssetMap = HashMap<u32, Arc<LoadedAsset>>;
type HitList = Vec<(u32, HitInfo)>;
type Result<T> = std::result::Result<T, Box<dyn Error>>;

fn complex_fn(map: &AssetMap) -> Result<HitList> { ... }
```

类型别名让长签名变短,可读性大幅提升。

**6. derive 减少样板**。

```rust
#[derive(Debug, Clone, PartialEq)]
struct HitInfo {
    distance: f32,
    position: Vec3,
    normal: Vec3,
}
// 自动生成 Debug / Clone / PartialEq 实现
```

不用手写 Debug impl,编译器自动生成。

**7. 重构工具 IDE 支持**。rust-analyzer 是 LSP,提供 IDE 重构支持:
- 重命名(symbol rename,所有引用同步更新)
- 提取函数(选代码 → refactor menu → extract function)
- 内联函数(把函数调用替换为函数体)
- 移动到模块(改 mod 路径)

VS Code + rust-analyzer 是 Rust 重构的标准工具链。

**反模式**:Rust 重构不要这样:
- ❌ 跨 module 大量 `pub use`——破坏封装,外部能看到内部细节
- ❌ 用 `unsafe` 绕过 borrow checker 来"重构"——重构应该让代码更安全,不是更危险
- ❌ 把所有 trait method 都加默认实现——增加复杂度,新人难理解
- ❌ 拆出 1-2 行的"helper 函数"——拆太碎反而难读,函数应该独立有意义

### Lv1 · 概念辨析

**题**:为什么"统一 raycast API"用 trait 比"函数指针"好?

**参考解答**:
- **trait**:编译时静态分发,内联优化,零开销。改实现只改一行(Box::new 类型)。
- **函数指针**:运行时动态分发,无法内联,有间接调用开销。改实现改函数指针。

trait 在性能上优,但要求实现类型在编译时确定。函数指针灵活(运行时可换),但慢。

游戏开发中,通常用 trait(性能优先)。Day 605 的 Casey 用 trait。

### Lv2 · 动手实践

**题**:定义 `trait Raycaster`,为两个 raycast 实现做 trait。测试:
- 通过 trait 调用,两种实现都能用
- 行为正确

完成标准:`cargo run` 测试通过。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 { fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } } }

struct Ray { origin: Vec3, dir: Vec3 }
struct HitInfo { distance: f32 }

trait Raycaster {
    fn raycast(&self, ray: &Ray, max_dist: f32) -> Option<HitInfo>;
}

// 实现 1:简单平面 raycast
struct PlaneRaycaster { z: f32 }
impl Raycaster for PlaneRaycaster {
    fn raycast(&self, ray: &Ray, max_dist: f32) -> Option<HitInfo> {
        if ray.dir.z.abs() < 1e-10 { return None; }
        let t = (self.z - ray.origin.z) / ray.dir.z;
        if t < 0.0 || t > max_dist { return None; }
        Some(HitInfo { distance: t })
    }
}

// 实现 2:始终无命中
struct NullRaycaster;
impl Raycaster for NullRaycaster {
    fn raycast(&self, _ray: &Ray, _max_dist: f32) -> Option<HitInfo> {
        None
    }
}

fn use_raycaster<R: Raycaster>(r: &R, ray: &Ray) -> Option<f32> {
    r.raycast(ray, 100.0).map(|h| h.distance)
}

fn main() {
    let plane = PlaneRaycaster { z: 5.0 };
    let null = NullRaycaster;
    
    let ray = Ray {
        origin: Vec3::new(0.0, 0.0, 0.0),
        dir: Vec3::new(0.0, 0.0, 1.0),
    };
    
    println!("Plane: {:?}", use_raycaster(&plane, &ray));  // Some(5.0)
    println!("Null: {:?}", use_raycaster(&null, &ray));    // None
    
    // 两种实现可以用同一个函数
    let raycasters: Vec<Box<dyn Raycaster>> = vec![
        Box::new(plane),
        Box::new(null),
    ];
    for r in &raycasters {
        println!("via dyn: {:?}", r.raycast(&ray, 100.0).map(|h| h.distance));
    }
}
```

// (Vec3, Ray, HitInfo, Raycaster, PlaneRaycaster, NullRaycaster 同 Lv2)

// 实现 3:命中所有
struct AlwaysHitRaycaster;
impl Raycaster for AlwaysHitRaycaster {
    fn raycast(&self, _ray: &Ray, _max_dist: f32) -> Option<HitInfo> {
        Some(HitInfo { distance: 1.0 })
    }
}

fn benchmark<R: Raycaster>(name: &str, r: &R, rays: &[Ray]) {
    let start = std::time::Instant::now();
    let mut hits = 0;
    for ray in rays {
        if r.raycast(ray, 100.0).is_some() {
            hits += 1;
        }
    }
    println!("{}: {} hits in {:?}", name, hits, start.elapsed());
}

fn main() {
    // 1000 条光线
    let rays: Vec<Ray> = (0..1000).map(|i| {
        let t = i as f32 * 0.01;
        Ray {
            origin: Vec3::new(0.0, 0.0, 0.0),
            dir: Vec3::new(0.0, 0.0, 1.0),
        }
    }).collect();
    
    let plane = PlaneRaycaster { z: 5.0 };
    let null = NullRaycaster;
    let always = AlwaysHitRaycaster;
    
    benchmark("Plane", &plane, &rays);
    benchmark("Null", &null, &rays);
    benchmark("Always", &always, &rays);
    
    // 用 trait object
    let raycasters: Vec<Box<dyn Raycaster>> = vec![
        Box::new(plane),
        Box::new(null),
        Box::new(always),
    ];
    
    println!("\nDynamic dispatch:");
    for (i, r) in raycasters.iter().enumerate() {
        let start = std::time::Instant::now();
        let hits = rays.iter().filter(|ray| r.raycast(ray, 100.0).is_some()).count();
        println!("  {}: {} hits in {:?}", i, hits, start.elapsed());
    }
}
```
