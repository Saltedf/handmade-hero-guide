# Day 625 · 修复一个真正的光照 bug

> Day 623-624 调查角落变暗(确认是 feature)。今天 Casey 处理另一个光照 bug——这个**是真的 bug**:特定角度的光源在某些 tile 上产生"过曝"(overexposure)。和 Day 623-624 的"调查 + 不修"不同,今天是"调查 + 修"。两天的对比让读者看清"真 bug"和"假 bug"的区别。

## 0 · 为什么要有这一天

测试者反馈第二个光照问题:

- 某些角度(如光从东南方向斜射)时,特定 tile 显得"过亮"
- 过亮的 tile 范围不固定,但角度固定时位置一致
- 重启游戏后 bug 出现在同一位置

Casey 应用 Day 622-624 的方法论调查:

1. **现象量化**:用 debug overlay 测量,过曝 tile 的亮度是正常 tile 的 1.8 倍
2. **理论分析**:物理正确应该是 max 1.0(因为 light_color × N·L,两者归一化),1.8 不合理
3. **反假设**:
   - 数值 bug?(N·L > 1?)
   - 多光源叠加?
   - 间接光加直接光算重?
4. **定位 bug**:`compute_direct_light` 函数返回值有时 > 1,因为 **N·L 算了两次**(normalization 前后各一次)
5. **修复**:删除冗余计算

**今天的核心概念**:**真 bug 的特征**——理论违反、量化异常、可复现。和 Day 623 的"假 bug"(理论符合)对比鲜明。

**心理锚点**:看完这集,你能:
- 识别"真 bug"的特征
- 应用科学方法定位根因
- 修复并加测试防回退

## 1 · Casey 今天做了什么

Casey 这一天的具体动作:

1. **bug 复现**:固定光源角度,bug 必现
2. **加 debug log**:打印每个 tile 的 `compute_direct_light` 输入输出
3. **观察**:过曝 tile 的 N·L 计算结果 = 1.41(应为 max 1.0)
4. **代码追踪**:发现 `compute_direct_light` 内部:

   ```rust
   let n_dot_l = normal.dot(light_dir) * 2.0;  // bug:多乘了 2
   let lambert = n_dot_l.max(0.0);
   let final = albedo * light_color * lambert;
   ```

   历史原因:某次试验中乘 2 做"亮度补偿",忘了删除
5. **修复**:删除 `* 2.0`
6. **加测试**:每个 tile 的 lambert ≤ 1.0
7. **commit**:详细说明 bug 原因 + 修复 + 防回退测试

代码改动 ~10 行(主要是修复 + 测试)。这一天的核心是**bug 修复方法论**。

## 2 · 心智模型

### 类比:做菜时盐放多了

你做菜,尝一口觉得咸。两种可能:

1. **盐就是咸的**(feature):盐的特性,不能改
2. **盐放多了**(bug):可以修

怎么判断?

- **理论**:这道菜的盐量应该是 5g,实际放了 10g
- **量化**:测量盐量,对比理论
- **决策**:超过理论 → bug,修

光照完全一样:

- **理论**:亮度 max 1.0(归一化光源 + 单位 normal)
- **实测**:亮度 1.8
- **决策**:超过 → bug,修

Day 623 的"角落变暗"理论 max 1.0,min 0.5,**实测在范围内 → feature**。Day 625 的"过曝"理论 max 1.0,**实测 1.8 超过 → bug**。

### 严谨:Bug 的特征

#### 2.1 理论违反

**真 bug 第一特征**:**测量值违反理论**。

| 场景 | 理论 | 实测 | 判断 |
|---|---|---|---|
| 角落亮度(Day 623) | 0.5-1.0 | 0.5 | feature |
| 过曝 tile(Day 625) | max 1.0 | 1.8 | bug |
| 浮点精度 | < 10^-6 误差 | < 10^-7 | feature(数值) |
| 死循环 | 应该结束 | 不结束 | bug |

#### 2.2 可复现

**真 bug 第二特征**:**条件相同 → 现象必现**。

- Day 625 的 bug:固定光源角度 → 必现。可复现,可调试
- 浮点精度问题:可能不同时复现(受其他运算影响)
- 并发 bug:难复现(时序依赖)

可复现 bug 是最容易修的。**复现 bug 是修复的第一步**。

#### 2.3 量化

**真 bug 第三特征**:**有明确量化指标**。

- "亮度 1.8"比"看起来怪"具体
- "帧率 30 FPS"比"卡"具体
- "内存 2GB"比"占太多"具体

量化让 bug 讨论有客观依据。

#### 2.4 根因可定位

**真 bug 第四特征**:**能找到具体代码行**。

Day 625 的 bug 定位到 `compute_direct_light` 的 `* 2.0`——具体、可验证。修这一行,bug 消失。

对比"看起来奇怪"的现象:没有具体行,只能"调参数"。

### 2.5 修复流程

```
1. 复现 bug(确保可触发)
2. 量化现象(具体数值)
3. 与理论对比(应是什么)
4. 定位根因(grep / 二分 / log)
5. 修复代码
6. 加测试(防回退)
7. 验证修复(bug 消失,无新 bug)
8. commit 详细说明
```

### 2.6 防回退测试

```rust
#[test]
fn test_direct_light_never_exceeds_one() {
    let world = setup_test_world();
    // 测试所有可能的方向
    for i in 0..1000 {
        let theta = std::f32::consts::FRAC_PI_2 * (i as f32 / 1000.0);
        for j in 0..1000 {
            let phi = 2.0 * std::f32::consts::PI * (j as f32 / 1000.0);
            let light_dir = Vec3::new(
                theta.sin() * phi.cos(),
                theta.cos(),
                theta.sin() * phi.sin(),
            );
            let normal = Vec3::new(0.0, 1.0, 0.0);
            let light = world.compute_direct_light(normal, light_dir);
            assert!(light <= 1.0 + 1e-6,
                "light = {} for theta={} phi={}", light, theta, phi);
        }
    }
}
```

这个测试**遍历所有方向**,保证修复后任何方向都不会过曝。永久防回退。

### 3.1 · 🎮 游戏编程视角

游戏开发常见 bug 类型:

| Bug 类型 | 难度 | 工具 |
|---|---|---|
| 数值 bug(本日) | 简单 | log + assert |
| 时序 bug(并发) | 难 | helgrind |
| 内存 bug | 中 | valgrind |
| 渲染 bug | 中 | RenderDoc |
| 物理 bug | 难 | 单步调试 |
| AI bug | 极难 | trace + 复现 |

Day 625 是简单的数值 bug,**容易修**。

### 3.2 · 🎨 图形学视角

图形学常见"亮度 bug":

1. **HDR 未 tone map**:亮度 > 1.0 直接显示,过曝。修复:加 tone mapping
2. **Gamma 错误**:在线性空间算光照,但显示用 sRGB,颜色错。修复:正确转换
3. **N·L 未 clamp**:`N·L` 可能为负,导致负亮度。修复:`.max(0.0)`
4. **多光源叠加**:每个光源 max 1.0,叠加后 > 1.0。修复:tone map 或 HDR pipeline
5. **Specular 高光过大**:Phong exponent 太低,高光扩散全表面。修复:提高 exponent

Day 625 的 bug 类似 1(HDR 未 tone map)+ 4(叠加错),本质是**亮度计算错误**。

### 3.3 · 🐧 Linux 系统编程视角

Linux 系统编程的"数值 bug":

1. **Integer overflow**:`i32::MAX + 1` wrapping 或 panic
2. **Off-by-one**:`for i in 0..=n` 多一次,`for i in 0..n-1` 少一次
3. **Signed/unsigned mixup**:`-1 as u32 = 4294967295`
4. **Null pointer dereference**:Rust 没有(安全 Rust)
5. **Race condition**:多线程共享数据未同步

每个 bug 类型有专门工具(gcc sanitizer、valgrind、helgrind 等)。

### 3.4 · 🦀 Rust 生态视角

Rust 表达"防回退测试":

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_no_over_exposure() {
        // 测试代码
    }

    // Property-based testing(更强)

```

`proptest` crate 可以自动生成大量测试输入,比手写更全面:

```toml

```

```rust
proptest! {

    fn test_light_clamp(theta in 0.0..FRAC_PI_2, phi in 0.0..2.0*PI) {
        let light_dir = Vec3::new(theta.sin()*phi.cos(), theta.cos(), theta.sin()*phi.sin());
        let normal = Vec3::new(0.0, 1.0, 0.0);
        let light = compute_direct_light(normal, light_dir);
        proptest::prop_assert!(light <= 1.0 + 1e-6);
    }
}
```

自动生成数百个 `(theta, phi)` 组合,每个都验证。**比手写更严谨**。

```rust
#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn dot(self, o: Self) -> f32 { self.x*o.x + self.y*o.y + self.z*o.z }
    fn length(self) -> f32 { self.dot(self).sqrt() }
    fn normalized(self) -> Self {
        let l = self.length();
        if l > 1e-9 { Self::new(self.x/l, self.y/l, self.z/l) } else { Self::new(0.0, 0.0, 0.0) }
    }
}

// BUGGY version(本日要修的)
fn compute_direct_light_buggy(normal: Vec3, light_dir: Vec3) -> f32 {
    let n_dot_l = normal.dot(light_dir) * 2.0;  // BUG:多乘 2
    n_dot_l.max(0.0).min(1.0)
}

// FIXED version
fn compute_direct_light_fixed(normal: Vec3, light_dir: Vec3) -> f32 {
    let n_dot_l = normal.dot(light_dir);  // 正确
    n_dot_l.max(0.0).min(1.0)
}

fn main() {
    let normal = Vec3::new(0.0, 1.0, 0.0);
    // 45 度斜射
    let light_dir = Vec3::new(1.0, 1.0, 0.0).normalized();

    let buggy = compute_direct_light_buggy(normal, light_dir);
    let fixed = compute_direct_light_fixed(normal, light_dir);

    println!("Buggy: {:.3} (bug if > 1.0)", buggy);
    println!("Fixed: {:.3}", fixed);

    assert!(buggy > 1.0, "Buggy should over-expose");
    assert!(fixed <= 1.0, "Fixed should be in range");
    println!("Bug confirmed and fixed!");
}
```

## 8 · Rust / Arch 落地代码

### 完整 bug 修复示例 + property-based test

```rust
// Cargo.toml:
// [dev-dependencies]
// proptest = "1.0"

#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn dot(self, o: Self) -> f32 { self.x*o.x + self.y*o.y + self.z*o.z }
    fn length(self) -> f32 { self.dot(self).sqrt() }
    fn normalized(self) -> Self {
        let l = self.length();
        if l > 1e-9 { Self::new(self.x/l, self.y/l, self.z/l) } else { Self::new(0.0, 0.0, 0.0) }
    }
}

fn compute_direct_light_fixed(normal: Vec3, light_dir: Vec3) -> f32 {
    let n_dot_l = normal.dot(light_dir);
    n_dot_l.max(0.0).min(1.0)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_no_over_exposure_specific() {
        // 45 度斜射(触发过曝的具体方向)
        let normal = Vec3::new(0.0, 1.0, 0.0);
        let light_dir = Vec3::new(1.0, 1.0, 0.0).normalized();
        let light = compute_direct_light_fixed(normal, light_dir);
        assert!(light <= 1.0 + 1e-6, "light = {}", light);
    }

    #[test]
    fn test_no_over_exposure_all_directions() {
        // 遍历所有方向,确保无过曝
        let normal = Vec3::new(0.0, 1.0, 0.0);
        for i in 0..100 {
            for j in 0..100 {
                let theta = std::f32::consts::FRAC_PI_2 * (i as f32 / 100.0);
                let phi = 2.0 * std::f32::consts::PI * (j as f32 / 100.0);
                let light_dir = Vec3::new(
                    theta.sin() * phi.cos(),
                    theta.cos(),
                    theta.sin() * phi.sin(),
                );
                let light = compute_direct_light_fixed(normal, light_dir);
                assert!(light <= 1.0 + 1e-6,
                    "light = {} at theta={} phi={}", light, theta, phi);
                assert!(light >= -1e-6, "light < 0");
            }
        }
    }
}

fn main() {
    // 演示
    let normal = Vec3::new(0.0, 1.0, 0.0);
    let dirs = [
        ("Directly above", Vec3::new(0.0, 1.0, 0.0)),
        ("45° angle", Vec3::new(1.0, 1.0, 0.0).normalized()),
        ("Horizon", Vec3::new(1.0, 0.0, 0.0)),
        ("Below horizon", Vec3::new(0.0, -1.0, 0.0)),
    ];

    println!("Direction\t\tLight");
    for (name, dir) in &dirs {
        let l = compute_direct_light_fixed(normal, *dir);
        println!("{}\t\t{:.3}", name, l);
    }

    // 运行测试
    println!("\nRunning tests...");
    // cargo test
}
```

## 附录 · "Bug 修复"方法论深入

Day 625 的 bug 修复看起来简单(改 1 行),但**完整的方法论值得深入**。

### Bug 修复的 7 个步骤

#### Step 1: 复现 bug

**复现 = 修复的一半**。无法复现的 bug 无法修。

- 写最小复现 case(剥离无关代码)
- 记录触发条件(输入 / 状态 / 时序)
- 自动化复现(脚本 / 测试)

```bash
# 写复现脚本
cat > repro.sh << 'EOF'
#!/bin/bash
./handmade_hero --scene=test --light-angle=45 --tile=10,5
EOF
chmod +x repro.sh
./repro.sh  # 必现 bug
```

#### Step 2: 量化现象

**用数字,不用形容词**。

- 坏:"看起来过曝"
- 好:"亮度 1.8,理论 max 1.0"

```rust
let light = compute_direct_light(normal, light_dir);
println!("light = {:.3} (max should be 1.0)", light);
```

#### Step 3: 与理论对比

**先问"理论应该是什么"**,再判断现象是否符合。

- 光照理论:lambert ≤ 1.0(归一化向量)
- 实测 1.8 → 违反理论 → bug

#### Step 4: 定位根因

工具箱:

- **`eprintln!`**(printf 调试):简单粗暴
- **gdb**:复杂状态
- **`git bisect`**:回归 bug,二分查找引入 commit
- **profiler**:性能 bug

```bash
git bisect start
git bisect bad HEAD  # 当前有 bug
git bisect good v1.0  # v1.0 没 bug
# git 自动 checkout 中间 commit,你测试 + 标 good/bad
# 几次后定位引入 bug 的具体 commit
```

#### Step 5: 修复代码

**最小改动原则**——只改必要的,不顺手"清理"。否则引入新 bug 难定位。

```rust
// 修复前
let n_dot_l = normal.dot(light_dir) * 2.0;  // bug

// 修复后(只改这一行)
let n_dot_l = normal.dot(light_dir);  // 修复
```

#### Step 6: 加测试防回退

**没有测试的 bug 修复不算完整**。同样的 bug 6 个月后会再次出现。

```rust
#[test]
fn test_no_over_exposure() {
    // 测试覆盖所有可能触发场景
}
```

#### Step 7: 文档化

**commit message 写清楚**:

```
fix: remove redundant * 2.0 in compute_direct_light

Root cause: legacy "brightness boost" never cleaned up
Symptom: light > 1.0 for n_dot_l > 0.5, causing over-exposure
Fix: removed * 2.0
Test: test_no_over_exposure_all_directions covers all (theta, phi)
```

下一个开发者看 commit,立刻知道一切。

### Bug 修复的反模式

新手常踩坑:

#### 反模式 1: 不复现就修

"我猜是这里的问题"——改了再说。结果 bug 没修,引入新 bug。

**正确**:**先复现,再修**。

#### 反模式 2: 顺手清理

修 bug 时发现"这段代码也丑",顺手改。结果新代码引入 bug。

**正确**:**两顶帽子**(重构 vs 修 bug)分开戴。

#### 反模式 3: 不加测试

修了 bug,没加测试。6 个月后回归。

**正确**:**每个 bug 加测试**。

#### 反模式 4: commit message 不写

`fix bug` —— 谁知道修了啥?

**正确**:**详细说明 root cause + fix + test**。

#### 反模式 5: 修了不验证

"代码看起来对"——提交。结果用户报告 bug 还在。

**正确**:**跑测试 + 手动复现验证**。

- **真 bug 的特征**:理论违反、可复现、可量化、根因可定位
- **Bug 修复的 7 步**:复现 → 量化 → 理论对比 → 定位 → 修复 → 测试 → 文档化
- **防回退测试**:每个 bug 必加
- **commit 文档化**:详细写 root cause + fix + test

带着这些认知,你后面遇到任何 bug,都不会慌——**有方法论,任何 bug 都能修**。这是工程师最宝贵的能力。

## 附录 II · Property-Based Testing 深度

Day 625 提到 proptest。这是测试领域的革命性方法,值得深入。

### 传统单元测试 vs Property-Based

**传统**:

```rust
#[test]
fn test_add() {
    assert_eq!(2 + 3, 5);
    assert_eq!(0 + 0, 0);
    assert_eq!(-1 + 1, 0);
}
```

每个 case 手写,覆盖有限。

**Property-based**:

```rust
proptest! {
    #[test]
    fn test_add_commutative(a in -1000..1000, b in -1000..1000) {
        // 性质:加法交换律
        prop_assert_eq!(a + b, b + a);
    }

    #[test]
    fn test_add_zero_identity(a in -1000..1000) {
        // 性质:0 是加法单位元
        prop_assert_eq!(a + 0, a);
    }
}
```

proptest 自动生成数百个 `(a, b)` 组合,每个验证性质。**比手写更全面**。

### Property-Based 的核心思想

不是测"具体值符合预期",而是测"性质对所有输入成立"。

例子:

- 排序:排序后 `a[i] <= a[i+1]`(性质)
- 序列化:`deserialize(serialize(x)) == x`(性质)
- 哈希:`hash(x) == hash(x)`(确定性性质)

### shrinking

proptest 找到失败 case 后,会**自动 shrink**——尝试找到最小失败 case。

例:

- 失败 case:`a = 847, b = -293`
- shrink 后:`a = 1, b = 0`(最小失败 case)

**最小失败 case** 让 debug 容易——不用看 847 / -293 的复杂场景。

### Hypothesis(Python 的 PBT)

Python 的 hypothesis 是 PBT 的代表。Rust 的 proptest 受其启发。Haskell 的 QuickCheck 是 PBT 的鼻祖(2000s 初)。

### Day 625 用 PBT

光照测试的 PBT 版:

```rust
proptest! {
    #[test]
    fn test_light_in_range(
        nx in -1.0f32..1.0,
        ny in -1.0f32..1.0,
        nz in -1.0f32..1.0,
        lx in -1.0f32..1.0,
        ly in -1.0f32..1.0,
        lz in -1.0f32..1.0,
    ) {
        let normal = Vec3::new(nx, ny, nz).normalized();
        let light_dir = Vec3::new(lx, ly, lz).normalized();
        let light = compute_direct_light_fixed(normal, light_dir);
        prop_assert!(light >= -1e-6 && light <= 1.0 + 1e-6);
    }
}
```

proptest 自动生成数百组 (normal, light_dir),每组验证 light 在 [0, 1]。**手写需要 10000 行测试代码**才能达到的覆盖。

### PBT 的局限

PBT 不是万能:

- **只能测可表达的 property**:某些 bug 没有简单 property
- **生成器设计难**:需要合理生成器覆盖边界 case
- **shinking 慢**:某些 case shrink 需要长时间

### PBT 在工业的应用

- **Haskell QuickCheck**:函数式编程标配
- **Python hypothesis**:数据科学、ML 测试
- **Rust proptest**:库代码测试
- **Clojure test.check**:动态语言

**核心价值**:**比手写测试更全面,自动找边界 case**。
