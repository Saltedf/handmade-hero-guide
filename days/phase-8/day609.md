# Day 609 · 减少不可访问体素的光贡献

> Day 608 可视化光照值后,Casey 发现一个奇怪现象:某些被墙完全包围的体素(玩家永远看不到),仍然贡献辐射场,影响附近可见体素。今天他要降低这些"不可访问体素"的贡献,让 GI 更准确。

## 0 · 为什么要有这一天

回顾 GI 数据流:

```
体素 A 的辐射场 ← 接收所有其他体素 B 的辐射
```

这是**全部体素都贡献**的模型。问题:如果体素 C 被 4 面墙完全包围(没有空间),它在物理上"不存在光",但代码仍让它贡献辐射场给邻居。

**结果**:某些"看不见的体素"通过辐射场"泄漏"光,导致画面看起来不对(墙后面似乎有光)。

**解决**:
1. **检测不可访问体素**:光线投射测试——从该体素能不能"逃出去"
2. **降低它们的辐射场权重**:不可访问体素的辐射场 *= 0.1(衰减)

Casey 这一天实现这两步。

心理锚点:看完这集,你能识别"数据合理性"问题(某些体素不该贡献),能用算法过滤不合理数据,能在自己写系统时主动考虑"哪些数据可能误导"。

## 1 · Casey 今天做了什么

Casey 这一天的几个动作:

1. **可视化发现问题**:用 Day 608 的可视化,Casey 看到墙后某些 atlas 有"亮斑",这些体素理论上是黑的。
2. **定义"不可访问"**:从该体素朝 6 个主方向(±x/±y/±z)射光,如果都被墙挡(短距离内),就是"不可访问"。
3. **检测算法**:对每个体素,做 6 次 raycast(短距离,如 2 米),统计挡墙数。
4. **应用权重**:不可访问体素的辐射场 *= 0.1(降低 90% 贡献)。

这一天的工程产出大约 100 行 Rust 代码,价值在于**让 GI 物理更合理**。

## 2 · 心智模型

### 类比:声音从墙后传

你站在墙前听音乐。墙后有个房间,房间里有音响。如果墙是石头(隔音好),你几乎听不到。

但如果代码模拟时,墙后房间的"声音"直接传给墙前的你,你听到的比实际大。这是因为代码没考虑"墙隔了多少"。

**修复**:测"墙后房间"和"墙前空间"的连通性,如果不连通,降低"墙后"的贡献。

GI 完全一样——被墙完全包围的体素,理论上不"看见"也不"被看见",但代码让它们互相贡献,导致"光泄漏"。

### 严谨原理:可达性检测

```rust
fn is_voxel_accessible(world: &World, voxel_util: &VoxelUtility, voxel_pos: (i32, i32, i32)) -> bool {
    let (x, y, z) = voxel_pos;
    let center = voxel_util.voxel_center(x, y, z);
    
    // 朝 6 个主方向射光,如果至少一个能走出 2 米,则可达
    let directions = [
        Vec3::new(1.0, 0.0, 0.0),
        Vec3::new(-1.0, 0.0, 0.0),
        Vec3::new(0.0, 1.0, 0.0),
        Vec3::new(0.0, -1.0, 0.0),
        Vec3::new(0.0, 0.0, 1.0),
        Vec3::new(0.0, 0.0, -1.0),
    ];
    
    for dir in &directions {
        let ray = Ray { origin: center, dir: *dir };
        let hit = raycast(&world, &ray, 2.0);  // 2 米内
        if hit.is_none() {
            return true;  // 这个方向 2 米内无墙,可达
        }
    }
    false  // 所有方向都被挡,不可达
}
```

**每行解释**:
- `voxel_center` — 体素中心世界坐标。
- 6 个主方向:±x、±y、±z。
- `raycast(..., 2.0)` — 投射光线,最大 2 米。
- 至少一个方向"逃出"2 米,可达。

**应用权重**:

```rust
fn apply_accessibility_weights(world: &mut World) {
    for (i, voxel) in world.voxels.iter_mut().enumerate() {
        let voxel_pos = world.voxel_pos(i);
        if !is_voxel_accessible(&world, &world.voxel_util, voxel_pos) {
            // 不可达,降低辐射场
            for texel in &mut voxel.atlas.texels {
                texel.r *= 0.1;
                texel.g *= 0.1;
                texel.b *= 0.1;
            }
            voxel.diffuse_color.r *= 0.1;
            voxel.diffuse_color.g *= 0.1;
            voxel.diffuse_color.b *= 0.1;
        }
    }
}
```

每帧调用 `apply_accessibility_weights`(在 propagate 之后,采样之前)。

### 边界情况

**"半可达"**:某体素朝 +x 方向逃出 2 米,但 -x 方向 0.5 米就撞墙。这体素部分可达。Casey 的简化版本(二元"可达/不可达")处理不了,工业级会用"可达性 0-1 连续值"。

```rust
fn accessibility_score(world: &World, voxel_util: &VoxelUtility, voxel_pos: (i32, i32, i32)) -> f32 {
    // 0 完全不可达,1 完全可达
    let (x, y, z) = voxel_pos;
    let center = voxel_util.voxel_center(x, y, z);
    let directions = [...];
    let mut escaped = 0;
    for dir in &directions {
        if raycast(&world, &Ray { origin: center, dir: *dir }, 2.0).is_none() {
            escaped += 1;
        }
    }
    escaped as f32 / directions.len() as f32
}

fn apply_weights(world: &mut World) {
    for (i, voxel) in world.voxels.iter_mut().enumerate() {
        let score = accessibility_score(&world, &world.voxel_util, world.voxel_pos(i));
        for texel in &mut voxel.atlas.texels {
            texel.r *= score;
            texel.g *= score;
            texel.b *= score;
        }
    }
}
```

Casey 在 Day 609 用简化版本(二元),Day 610 可能升级。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业里"数据合理性检查"是常见优化:
- **可见性检测**:玩家看不到的物体不渲染(视锥剔除、遮挡剔除)
- **重要性采样**:对玩家重要的物体多投入资源
- **LOD**:远处物体低精度

GI 系统的"可达性"是这种思路在"光照探针"上的应用——只对可达探针做精确计算,不可达的简化。

**踩过的坑**:
- **可达性误判**:墙体附近的体素被错误判为"不可达"。解决:用更长的射线(5 米而非 2 米)
- **场景变化**:墙被打洞,可达性变化。解决:每帧重算(代价大)或事件触发
- **可达性突变**:玩家走动时,某体素突然从可达变不可达,光照跳变。解决:用连续权重(0-1)

### 3.2 · 🎨 图形学视角

**Visibility**(可见性)是图形学核心概念:
- **Direct visibility**:光从光源能不能直接照到点(直接光阴影)
- **Indirect visibility**:点能不能间接接收光(间接光可达性)
- **Camera visibility**:点能不能被相机看到(渲染剔除)

Casey 的 Day 609 是 **Indirect visibility**——体素的辐射场能不能影响其他体素。

**工业级方案**:
- **Precomputed Visibility**:静态场景预算可见性矩阵(N² 大小)
- **Online Visibility**:运行时用 raycast 检测
- **Probabilistic Visibility**:蒙特卡洛采样,统计估计

Casey 用 Online(每帧 raycast),简单但慢。

### 3.3 · 🐧 Linux 系统编程视角

这一集主要是算法,Linux 系统调用面没什么。但**性能分析**值得一提。

可达性检测 = 每体素 6 次 raycast。1000 个体素 × 6 = 6000 次 raycast / 帧。如果每次 raycast 50 µs,总 300 ms / 帧——爆炸。

**优化**:
1. **离线预算**:静态场景的可达性预算,运行时只查表
2. **稀疏更新**:不是每帧重算,每 N 帧一次
3. **粗筛选**:先用简单启发式(如"该体素周围 6 个体素都是墙")判不可达

```bash
sudo perf stat -e instructions ./your_game
# 监控 apply_accessibility_weights 的开销
```

### 3.4 · 🦀 Rust 生态视角

Rust 实现"数据过滤"的模式:

**1. Map + Filter**:

```rust
let filtered: Vec<_> = voxels.iter()
    .map(|v| (v, is_accessible(v)))
    .filter(|(_, acc)| *acc)
    .collect();
```

函数式,清晰但分配多。

**2. 命令式循环**:

```rust
for voxel in &mut voxels {
    if !is_accessible(voxel) {
        voxel.atlas *= 0.1;
    }
}
```

性能好,无分配。Casey 用这个。

**3. Trait 抽象**:

```rust
trait Filter {
    fn should_filter(&self, voxel: &Voxel) -> bool;
    fn apply(&self, voxel: &mut Voxel);
}

struct AccessibilityFilter;
impl Filter for AccessibilityFilter {
    fn should_filter(&self, voxel: &Voxel) -> bool { !is_accessible(voxel) }
    fn apply(&self, voxel: &mut Voxel) { voxel.atlas *= 0.1; }
}
```

灵活,可组合。Casey 不用(简单场景过度抽象)。

### Lv1 · 概念辨析

**题**:为什么"被墙完全包围的体素"在物理上不应该贡献光?具体是哪种物理现象?

**参考解答**:光在物理上是电磁波,在物质中传播。被墙完全包围的空间(没有空间让光走),光不能"存在"——因为光需要介质或真空传播。

但代码模拟里,我们用"体素辐射场"近似光场,每个体素都有辐射场。如果某体素被完全包围,理论上它的辐射场应该 = 0(没有外部光进入)。

但代码 bug(光"泄漏"通过墙)让被围体素的辐射场非零,且通过传播影响邻居——这违反物理,需要过滤。

### Lv2 · 动手实践

**题**:实现 `is_voxel_accessible` 和 `apply_accessibility_weights`(2D 简化版)。测试:
- 16×16 网格,中间 (8, 8) 周围 3×3 是墙(完全包围 (8, 8))
- 检测 (8, 8) 应该是"不可达"
- 应用权重后,(8, 8) 的值应该减少 90%

完成标准:`cargo run` 测试通过。

**参考解答**:

```rust
struct World2D {
    dim: usize,
    cells: Vec<bool>,  // true = 墙
    light: Vec<f32>,   // 每个 cell 的光照值
}

impl World2D {
    fn new(dim: usize) -> Self {
        Self {
            dim,
            cells: vec![false; dim * dim],
            light: vec![1.0; dim * dim],
        }
    }
    fn set_wall(&mut self, x: usize, y: usize) {
        self.cells[y * self.dim + x] = true;
    }
    fn is_wall(&self, x: i32, y: i32) -> bool {
        if x < 0 || y < 0 || x >= self.dim as i32 || y >= self.dim as i32 {
            return true;  // 边界外 = 墙
        }
        self.cells[y as usize * self.dim + x as usize]
    }
}

fn is_accessible_2d(world: &World2D, x: i32, y: i32, ray_length: i32) -> bool {
    // 朝 4 方向射光
    let directions = [(1, 0), (-1, 0), (0, 1), (0, -1)];
    for (dx, dy) in &directions {
        let mut escaped = false;
        for step in 1..=ray_length {
            let nx = x + dx * step;
            let ny = y + dy * step;
            if world.is_wall(nx, ny) {
                break;  // 撞墙
            }
            if step == ray_length {
                escaped = true;
            }
        }
        if escaped {
            return true;
        }
    }
    false
}

fn apply_accessibility(world: &mut World2D, ray_length: i32) {
    let dim = world.dim as i32;
    for y in 0..dim {
        for x in 0..dim {
            if world.is_wall(x, y) { continue; }
            if !is_accessible_2d(world, x, y, ray_length) {
                let idx = (y as usize) * world.dim + x as usize;
                world.light[idx] *= 0.1;
            }
        }
    }
}

fn main() {
    let mut world = World2D::new(16);
    // (8, 8) 周围 3x3 全是墙(除了 (8, 8) 自己)
    for y in 7..=9 {
        for x in 7..=9 {
            if x == 8 && y == 8 { continue; }
            world.set_wall(x, y);
        }
    }
    
    // (8, 8) 被墙包围,不可达
    println!("(8,8) accessible: {}", is_accessible_2d(&world, 8, 8, 2));
    println!("Light before: {}", world.light[8 * 16 + 8]);
    
    apply_accessibility(&mut world, 2);
    
    println!("Light after: {}", world.light[8 * 16 + 8]);
    // 应该是 0.1(原 1.0 * 0.1)
    
    // 边界附近的可达
    println!("\n(0, 0) accessible: {}", is_accessible_2d(&world, 0, 0, 2));
}
```

```rust
fn main() {
    let mut world = World2D::new(32);
    
    // 创建场景:几个"房间"(被墙完全包围的空间)

        .count();
    let n_walls = world.cells.iter().filter(|&&c| c).count();
    println!("\nWalls: {}, Inaccessible empty voxels: {}", n_walls, n_inaccessible);
}
```

## 10 · 补充材料:Light propagation 的不可达问题

### A.1 "不可访问体素"的定义

Day 609 的核心问题:某些 voxel 从任何方向都"不可达"光线——它们被完全包围,无光进入。这些 voxel 对光照计算贡献为 0,但 propagation 算法仍在它们上浪费时间。

**示例**:

```
俯视图(2D 简化):
████████████
█        █
█  ████  █   ← 内部 4×4 区域,被外层围住
█  █  █  █
█  █  █  █
█  ████  █
█        █
████████████

内部的 4×4 voxel 永远接收不到光(从任何方向 raycast 都被外墙挡)。
```

Propagation 算法在这些 voxel 上"反复 bounce",但永远是 0(无光进入)。浪费 CPU。

### A.2 检测不可达 voxel

Casey 的方法:从所有光源方向 raycast 到 voxel,如果所有方向都挡,标记"不可达"。

```rust
fn is_reachable(world: &World, target: Vec3) -> bool {
    let directions = generate_test_directions(32);  // 32 个均匀方向
    
    for dir in directions {
        let ray = Ray::new(target, dir);
        let dist = raycast_to_sky(world, ray);
        if dist > 0.0 {
            // 这个方向能到天空
            return true;
        }
    }
    false  // 所有方向都挡
}
```

每个 voxel 检查 32 个方向,代价 O(32 × N) where N = voxel 数。一次性预计算,缓存结果。

### A.3 不可达 voxel 的处理

预计算后:
```rust
struct World {
    voxels: Vec<Voxel>,
    reachable: Vec<bool>,  // 每 voxel 一个 bool
}
```

Propagation 时跳过不可达 voxel:
```rust
fn propagate(world: &mut World) {
    for i in 0..world.voxels.len() {
        if !world.reachable[i] {
            continue;  // 跳过
        }
        // 计算 propagation
    }
}
```

加速 10-50%(取决于场景几何)。

### A.4 Light propagation 的算法谱系

工业级 propagation 算法:

**Brute force**:每个 voxel × 每方向 raycast。极慢,O(V × D × R) where D=方向数, R=平均 raycast 长度。

**Flood fill**:BFS 从光源开始,每步传播到邻居。O(V) 但只适合简单 diffuse light。

**Light Propagation Volumes**(Kaplanyan 2010):3D texture + 多次迭代,每步融合邻居 + 应用 SH。GPU 加速。

**Voxel Cone Tracing**(Crassin 2011):GPU 上用 cone 代替 ray,模拟"diffuse inter-reflection"。 Crytek SVOGI 用。

**Precomputed + delta update**:大部分预计算,变化部分增量更新(玩家挖墙时只更新受影响区域)。

Casey 的 HH 用简化 flood fill / propagation。

### A.5 Light cache 的工业实现

工业实现用 SH + 多 bounce precomputed:

```
预计算阶段(几小时):
  for each voxel:
    sample N=256 directions(Monte Carlo)
    for each direction:
      raycast,记录 visibility(0=可见,1=被挡)
    SH projection:visibility 函数转 9 SH 系数
  
  → 每 voxel 存 9 floats × 3 RGB = 27 floats 的 SH visibility

运行时:
  for each frame:
    sky_sh = compute_sky_sh(sun_dir)  // 实时算 sky 光 SH
    for each voxel:
      received = SH_dot(voxel.visibility_sh, sky_sh)  // SH 内积
      voxel.light = received
  
  → 复杂度 O(V × SH_size) = O(V × 27)
```

Halo 3(2007)是第一个商业 PRT 游戏。

### A.6 增量更新

玩家挖 / 放 voxel 时,只更新受影响区域:

```rust
fn on_voxel_change(world: &mut World, x: i32, y: i32, z: i32) {
    // 受影响范围:N voxel 半径
    let radius = 8;
    
    for dz in -radius..=radius {
        for dy in -radius..=radius {
            for dx in -radius..=radius {
                let nx = x + dx;
                let ny = y + dy;
                let nz = z + dz;
                
                // 重新计算这个 voxel 的光照
                relight_single_voxel(world, nx, ny, nz);
            }
        }
    }
}
```

挖一个 voxel,只重算 (2×8+1)^3 = 4913 voxel 的光照。比全场景重算快几个量级。

### A.8 Voxel cone tracing 详解

让我严肃讲讲 voxel cone tracing(工业级实时 GI 的核心算法)。

**核心思想**:从 camera 或 voxel 出发,沿"锥"(cone)而不是"线"(ray)。锥的半径随距离增大,等价于"看更大范围"。

```
Ray(传统):
  camera ----o---------o---------o----→
  
Cone(tracing):
  camera --<---o----o----o------o------o-->-->-->  ← 半径递增
```

锥的"覆盖率"用 voxel mipmap 算——粗 mipmap 表示远处低频 voxel。

**算法步骤**(fragment shader,每个屏幕像素):

```glsl
vec3 voxel_gi(vec3 pos, vec3 normal) {
    vec3 color = vec3(0);
    float remaining = 1.0;
    
    // 沿 normal 半球发射多个 cone
    for (int i = 0; i < NUM_CONES; i++) {
        vec3 cone_dir = cone_directions[i];  // 预计算的圆锥方向
        
        vec3 p = pos;
        float dist = 0.1;
        float tan_half_angle = tan(0.5 * cone_angles[i]);
        
        for (int step = 0; step < MAX_STEPS; step++) {
            // 在 voxel mipmap 查 cone 当前位置的"占用"
            float diameter = max(dist * tan_half_angle, MIN_DIAMETER);
            int mip = log2(diameter);
            vec4 voxel = textureLod(voxel_mipmap, p, mip);
            
            if (voxel.a > 0) {
                // 命中,累加颜色
                color += remaining * voxel.rgb * cone_weights[i];
                remaining *= (1 - voxel.a);
            }
            
            if (remaining < 0.01) break;
            
            dist += diameter;
            p = pos + cone_dir * dist;
        }
    }
    
    return color;
}
```

NUM_CONES 通常 5-9,每 cone 半径递增。8 cone × 32 step = 256 voxel 查询 / 像素,可承受。

**优势**:实时 GI,无 baking,光源任意变。

**劣势**:GPU 必须支持 texture mipmap + textureLod。需要预先生成 voxel mipmap。

### A.9 Sparse Voxel Octree(SVO)

Cone tracing 的 GPU 实现用 Sparse Voxel Octree:

```
全场景 voxel:
  level 0:每个 voxel(0.5m)
  level 1:4 voxel 合并(1m)
  level 2:8 voxel 合并(2m)
  ...
  level N:整个场景
```

不是 3D texture(浪费),而是 sparse octree(只存有 voxel 的节点)。内存省 90%+。

GPU 查询 octree:
```glsl
vec4 voxel_octree_traverse(vec3 pos, float size) {
    int node = 0;  // root
    int target_level = log2(size);
    
    for (int level = 0; level < target_level; level++) {
        vec3 frac_pos = (pos - node_bounds[node].min) / node_bounds[node].size;
        int child_idx = (frac_pos.x > 0.5 ? 1 : 0) | (frac_pos.y > 0.5 ? 2 : 0) | (frac_pos.z > 0.5 ? 4 : 0);
        node = child_pointers[node][child_idx];
        if (node == -1) return vec4(0);  // 空
    }
    return voxel_data[node];
}
```

Crytek SVOGI / Unreal VXGI 用这套。

### A.10 Light Propagation Volumes(LPV)

LPV 是另一套工业 GI:

```
1. 把场景注入 RSM(Reflective Shadow Map)的虚拟光源
2. 把 RSM 的光"注入"3D grid(SH 系数)
3. 多次迭代 propagation(grid 之间传播 SH)
4. 渲染时,每像素查 grid 的 SH,得到 GI
```

LPV 极快(GPU grid 是固定大小),但精度受 grid 分辨率限制。

Crysis 2 控制台版用 LPV,首个 console 实时 GI。

### A.11 Lumen(Unreal 5)

Lumen 综合多种 GI:
- Screen-space GI(快速近似)
- SDF tracing(software ray tracing,基于 distance field)
- Voxel tracing(中等距离)
- Mesh distance field(精确)

Lumen 自动选最适合的,提供"无 baking 实时 GI"。Unreal 5 默认。

Lumen 实现 50K+ 行代码,综合 Crytek / Kaplanyan / 多年 GI 研究。是目前最先进的实时 GI。

### A.16 性能优化的层次(L1-L5)

**L1: 算法选择**
- O(N²) → O(N log N)
- 例: bubble sort → quicksort

**L2: 数据布局**
- AoS → SoA
- 例: Vec<Voxel> → struct { Vec<u8> materials, ... }

**L3: Micro**
- inline、branchless、SIMD
- 例: SIMD 4-wide float

**L4: 并行**
- multi-thread、SIMD、GPU
- 例: rayon par_iter

**L5: 架构**
- streaming、incremental、async
- 例: chunked world

每层收益递减难度递增。Proflier 决定优化哪层。
