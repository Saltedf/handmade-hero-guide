# Day 639 · 绘制调试图表

> Day 638 Casey 录好了命令缓冲。今天把命令真正画到屏幕上——line / AABB / text 全部 immediate-mode 渲染,叠加在游戏画面上。核心挑战:**怎么把 3D 几何画到 2D 屏幕上,又怎么让 debug text 永远朝向相机(billboard)**?

## 0 · 为什么要有这一天

录制器录了一堆 `Cmd::AABB(...)`,但如果你不能把它画到屏幕上,你只是把数据从一个内存区域挪到另一个内存区域。**调试器看不见 = 不存在**。

今天 Casey 把命令缓冲接到渲染管线:

1. **line 渲染**:在 3D 世界里画线段,需要把端点投影到 2D 屏幕坐标,然后用 Bresenham 或者 GPU line list
2. **AABB 渲染**:画一个 wireframe cube(12 条边)
3. **text 渲染**:最难——3D 空间里的 text 会被透视投影拉变形,要么强行画在屏幕固定位置(hud-like),要么 billboard 让它始终朝向相机

**为什么这一步是 polish 阶段的里程碑?**

新手以为"debug 工具就是 print",资深工程师知道 debug 可视化是**完整渲染管线**。从数据(命令)到像素(屏幕),要走:

- **顶点变换**:model → world → view → clip → NDC → screen
- **图元组装**:line / triangle / point
- **光栅化**:Bresenham / DDA / scanline
- **像素着色**:颜色、深度、blend
- **输出**:framebuffer

每步都要正确,debug 几何才能正确显示。Casey 在 Day 639 演示的是这个完整管线的小版本——不含 PBR / 光照 / 阴影,只有"画线 + 画字"。

**为什么用 immediate-mode 而非 retained-mode?**

debug 几何每帧都变,retained-mode(每帧更新数据)有开销。immediate-mode(每帧重新提交)更简单:

```rust
fn render_debug_overlay(recorder: &Recorder, renderer: &mut Renderer) {
    if let Some(cmds) = recorder.playback_current() {
        for cmd in cmds {
            match cmd {
                Cmd::Line(from, to, color) => renderer.draw_line_3d(from, to, color),
                Cmd::AABB(min, max, color) => renderer.draw_aabb_wireframe(min, max, color),
                Cmd::Text(pos, text, color) => renderer.draw_text_billboard(pos, text, color),
            }
        }
    }
}
```

简单清晰。这是 Dear ImGui / egui / immediate-mode GUI 的核心思想。

心理锚点:看完今天,你能:

- 把 3D line 投影到屏幕坐标
- 实现 wireframe AABB 渲染
- 让 3D 空间里的 text billboard 朝向相机
- 理解为什么 debug draw 不能用游戏主 mesh 的 shader
- 区分 immediate-mode vs retained-mode 渲染

## 2 · 心智模型

### 类比:在地图上画线

想象你拿一张世界地图(2D),想标出从北京到纽约的飞行路线(3D 球面上的曲线)。你需要:

1. 把 3D 球面上的点投影到 2D 地图(墨卡托投影)
2. 在 2D 地图上画线

游戏里的 debug draw 完全一样:3D 世界坐标 → 2D 屏幕坐标 → 画像素。投影函数就是你的"MVP 矩阵"(model-view-projection)。

### MVP 矩阵复习

3D 点 → 2D 屏幕点的链路:

```
Model 矩阵:  局部坐标   → 世界坐标
View 矩阵:   世界坐标   → 相机坐标(相机在原点,朝 -z)
Proj 矩阵:   相机坐标   → 裁剪空间(NDC,-1 到 1 的立方体)
Viewport:    NDC        → 屏幕像素坐标
```

合并:`screen = viewport(proj * view * model * local)`

对 debug draw,几何通常已经在世界坐标里(model = identity),所以:

```
clip = proj * view * world_pos
ndc = clip.xyz / clip.w   // 透视除法
screen.x = (ndc.x + 1) * 0.5 * width
screen.y = (1 - ndc.y) * 0.5 * height  // y 翻转(屏幕 y 向下)
```

`clip.w` 是透视除法的分母——它代表"相机距离这个点的深度"。如果 `clip.w <= 0`,点在相机后面,不该画。

### Wireframe AABB:12 条边

AABB 有 8 个顶点:

```
E ──── F
/|     /|
A ──── B |
| |    | |
| H ───|─ G
|/     |/
D ──── C
```

12 条边:底面 4 条 + 顶面 4 条 + 4 条立柱。

```rust
fn draw_aabb_wireframe(r: &mut Renderer, min: Vec3, max: Vec3, color: u32) {
    let a = min;
    let b = Vec3::new(max.x, min.y, min.z);
    let c = Vec3::new(max.x, max.y, min.z);
    let d = Vec3::new(min.x, max.y, min.z);
    let e = Vec3::new(min.x, min.y, max.z);
    let f = Vec3::new(max.x, min.y, max.z);
    let g = max;
    let h = Vec3::new(min.x, max.y, max.z);
    // 底面 ABCD
    r.line(a, b, color); r.line(b, c, color);
    r.line(c, d, color); r.line(d, a, color);
    // 顶面 EFGH
    r.line(e, f, color); r.line(f, g, color);
    r.line(g, h, color); r.line(h, e, color);
    // 立柱
    r.line(a, e, color); r.line(b, f, color);
    r.line(c, g, color); r.line(d, h, color);
}
```

### Billboard text

3D 空间里的 text 有两个选择:

1. **世界空间 text**:text 几何在 3D 里,经过 MVP 投影。问题:远处的 text 缩成一点点,看不清
2. **Billboard text**:text 始终朝向相机,大小不变。问题:要让"始终朝向相机",需要每帧根据相机方向旋转 text 四元数
3. **Screen-space overlay**:text 投影到屏幕坐标,直接画 2D UI text。问题:多个远近距离的 text 可能重叠

Casey 选最简单的:**project 3D point to 2D,then draw 2D text at that pixel**。这是"hybrid billboard"——位置在 3D 里,渲染是 2D。这种方式:

- text 大小固定(不会被透视缩小)
- text 永远朝上(没有 3D 旋转)
- 容易实现(只投一个点,不投四边形)

### Backface culling for lines

线没有"面",所以严格意义上没 backface。但 Case 的 wireframe 在某些视角下会让"看不见的边"画在前面,看起来乱。修法:**深度测试**——如果 wireframe 边的深度比当前像素大,不画。

但深度测试对 wireframe 不友好——因为 wireframe 是线条,深度差一点就 missed。Casey 的折中:**关闭深度测试,让所有 wireframe 都画在前面**(always-on-top),接受视觉混乱。

更好的做法(没做):**双 pass**——先画半透明背面 wireframe,再画不透明正面 wireframe,模拟 x-ray 效果。这是 Unity / Unreal debug draw 的标配。

### 颜色系统:HSV → RGB

Casey 加了一个"按 debug 标签自动配色"的小功能。每次新建标签,从 HSV 色环上取下一个颜色,转 RGB:

```rust
fn hsv_to_rgb(h: f32, s: f32, v: f32) -> (u8, u8, u8) {
    let c = v * s;
    let x = c * (1.0 - ((h * 6.0) % 2.0 - 1.0).abs());
    let m = v - c;
    let (r, g, b) = match (h * 6.0).floor() as i32 % 6 {
        0 => (c, x, 0.0),
        1 => (x, c, 0.0),
        2 => (0.0, c, x),
        3 => (0.0, x, c),
        4 => (x, 0.0, c),
        _ => (c, 0.0, x),
    };
    ((r + m) * 255.0) as u8, ((g + m) * 255.0) as u8, ((b + m) * 255.0) as u8
}
```

HSV(hue, saturation, value)比 RGB 直观:hue 决定"色相"(0-1 转一圈),saturation 决定饱和度,value 决定亮度。要"循环色环",只要让 hue 从 0 增长到 1 再绕回 0,saturation 和 value 固定。

### 性能考虑

Debug draw 在 release build 不应该影响 frame rate。Casey 的做法:

1. debug draw 函数全部 `#[cfg(debug_assertions)]` 或自定义 feature gate
2. 在 release build 整段消失,零开销
3. debug build 里也没事——60fps 跑几十条 wireframe 完全无压力

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏里 debug draw 的标准实现:

- **Unity**: `Debug.DrawLine / Debug.DrawRay / Gizmos.DrawCube` —— 只在 scene view 和 game view(debug build)显示,build 出来不显示

Casey 自建版本和这些没本质差别——都是"几何 + 颜色 + 生命周期"的组合。差别在于**Casey 把命令缓冲做成了 first-class**,可以跨帧回放,商业引擎通常每帧画完就丢。

### 3.2 · 图形学视角

Wireframe 渲染在图形学有几个变种:

- **朴素 wireframe**:每条边一条线,容易重叠
- **Barycentric wireframe**:用 fragment shader 算重心坐标,接近边的像素画线。优点:无 geometry shader,完美 anti-aliasing
- **Hidden line removal**:背面边变虚线。需要两次 render pass

Casey 用最朴素的 12 条边,够 debug 用了。

### 3.3 · Linux 系统编程视角

Linux 上"叠加层渲染"的对应:

- **X11 composite extension**:窗口管理器画一个 overlay 窗口,合成到主桌面
- **Wayland subsurfaces**:类似 X11 composite,但更现代
- **OpenGL debug overlay**:Mesa 的 `MESA_DEBUG` 环境,driver 自己画 FPS / 帧时间 overlay

Casey 的 debug overlay 思路和 GPU vendor 的 driver overlay 同源——**都是在主渲染之上的合成层**。

### 3.4 · Rust 生态视角

Rust 里 wireframe + text 的常用 crate:

- `wgpu` + `wgpu_glyph`(text):基础 GPU 渲染
- `lyon`(几何 tessellation):复杂路径渲染
- `ab_glyph` / `rusttype`:字体解析 + 光栅化
- `epaint`(egui 的 paint 层):已经是 immediate-mode 的 paint crate

Casey 全手写,不依赖外部 crate——因为他在 HH 里要展示"从零搭起来",而不是"调用库"。

不同 wireframe 风格对比:

```
朴素 wireframe              Hidden-line            Barycentric
                                                  
   ┌─────┐                    ┌─────┐               ┌─────┐
  /│    /│                  /     /│             /│    /│
 / │   / │                ┄┄┄┄┄┄┄┄┄             / │   / │

│  │  │  │                │     │               │  │  │  │
```

历史演化:

- **1980s**:wireframe 是唯一选择(硬件弱)

- **2000s**:GLSL 出现,barycentric wireframe 流行
- **2010s**:GPU pipeline 完善,debug draw 在 CPU
- **2020s**:mesh shader 让 wireframe 更灵活

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 选"3D 点投影到 2D 屏幕坐标,再画 2D text",而不是把 text 当 3D 几何画?

**参考解答**:3D text 会被透视投影缩放——远处的 text 缩成几像素,看不清;近处的 text 占满半屏,挡视野。投影一个点再画 2D text,让 text 大小固定,始终可读,且不被深度遮挡。代价:多个远距离 text 可能屏幕重叠,但 debug 场景下可接受。

### Lv2 · 动手实践

**题**:实现 `project_to_screen(world_pos: Vec3, view: Mat4, proj: Mat4, width: f32, height: f32) -> Option<(f32, f32)>`。返回 None 表示点在相机后面。

**参考解答**:

```rust
use glam::{Vec3, Mat4, Vec4};

fn project_to_screen(world: Vec3, view: Mat4, proj: Mat4, w: f32, h: f32) -> Option<(f32, f32)> {
    let clip = proj * view * Vec4::new(world.x, world.y, world.z, 1.0);
    if clip.w <= 0.0 { return None; }
    let ndc = Vec3::from(clip.truncate() / clip.w);
    let sx = (ndc.x + 1.0) * 0.5 * w;
    let sy = (1.0 - ndc.y) * 0.5 * h; // y 翻转
    Some((sx, sy))
}
```

## 8 · Rust / Arch 落地代码

完整可跑示例(纯 std,无 GPU):

```rust
// 模拟"画 wireframe AABB 到字符 grid"
// 用 ASCII 画 2D 投影

fn project(x: f32, y: f32, z: f32, w: usize, h: usize) -> Option<(usize, usize)> {
    // 假装有个简单的投影:世界 x → 屏幕 x,世界 z → 屏幕 y,y 是深度
    if y <= 0.0 { return None; }
    let sx = ((x / y + 1.0) * 0.5 * w as f32) as usize;
    let sy = ((1.0 - z / y) * 0.5 * h as f32) as usize;
    if sx < w && sy < h { Some((sx, sy)) } else { None }
}

struct Canvas { w: usize, h: usize, buf: Vec<char> }
impl Canvas {
    fn new(w: usize, h: usize) -> Self {
        Self { w, h, buf: vec![' '; w * h] }
    }
    fn set(&mut self, x: usize, y: usize, c: char) {
        if x < self.w && y < self.h { self.buf[y * self.w + x] = c; }
    }
    fn line(&mut self, (x0, y0): (usize, usize), (x1, y1): (usize, usize)) {
        // Bresenham
        let (dx, dy) = (x1 as i32 - x0 as i32, y1 as i32 - y0 as i32);
        let steps = dx.abs().max(dy.abs()).max(1);
        for i in 0..=steps {
            let t = i as f32 / steps as f32;
            let x = (x0 as f32 + dx as f32 * t) as usize;
            let y = (y0 as f32 + dy as f32 * t) as usize;
            self.set(x, y, '#');
        }
    }
    fn render(&self) {
        for row in 0..self.h {
            let line: String = self.buf[row * self.w..(row + 1) * self.w].iter().collect();
            println!("{}", line);
        }
    }
}

fn main() {
    let mut c = Canvas::new(60, 20);
    // 画一个 3D wireframe box,8 顶点投影
    let verts = [
        (-1.0, 3.0, -1.0), ( 1.0, 3.0, -1.0),
        ( 1.0, 3.0,  1.0), (-1.0, 3.0,  1.0),
        (-1.0, 5.0, -1.0), ( 1.0, 5.0, -1.0),
        ( 1.0, 5.0,  1.0), (-1.0, 5.0,  1.0),
    ];
    let proj: Vec<_> = verts.iter()
        .map(|&(x, y, z)| project(x, y, z, 60, 20))
        .collect();
    let edges = [(0,1),(1,2),(2,3),(3,0), (4,5),(5,6),(6,7),(7,4),
                 (0,4),(1,5),(2,6),(3,7)];
    for (a, b) in edges {
        if let (Some(p1), Some(p2)) = (proj[a], proj[b]) {
            c.line(p1, p2);
        }
    }
    c.render();
}
```

## 5 · 对照与变奏(补充)

工业级 debug draw 系统对比:

每个工具都解决同一问题:**"如何快速画几何 debug"**。但每个实现都不同——有的 immediate,有的 retained;有的引擎集成,有的独立。

资深工程师的选择:**用现成**——Dear ImGui / egui / 引擎内置。**不要自己写**,除非有特殊需求。Casey 在 HH 自己写是因为教学目的,展示"内部如何工作"。生产项目应该用现成。

**为什么 Casey 不用 Dear ImGui?**

- 教学目的(让学生看内部)
- 减少依赖(HH 是单语言项目)
- 简化跨平台(Dear ImGui 跨平台 setup 复杂)

工业级项目应该用 Dear ImGui——成熟、稳定、社区大。Rust 项目用 egui。

**Billboard 详解**:

Billboard 是"广告牌"——3D 几何永远朝向相机。原理:每帧重新计算 model matrix,让 quad 的法线 = camera forward。

```rust
fn billboard_matrix(camera_pos: Vec3, billboard_pos: Vec3) -> Mat4 {
    let forward = (camera_pos - billboard_pos).normalize();
    let right = Vec3::Y.cross(forward).normalize();
    let up = forward.cross(right);
    Mat4::from_cols(
        right.extend(0.0),
        up.extend(0.0),
        forward.extend(0.0),
        billboard_pos.extend(1.0),
    )
}
```

这个矩阵让 quad "正面朝相机"。无论相机怎么转,billboard 上的 text 永远可读。

工业实例:

- **HP bar**:每个 NPC 头上 HP 条,billboard 朝相机
- **Damage number**:射击游戏的伤害数字,billboard
- **Minimap icon**:小地图标记,billboard
- **Marker**:任务标记,billboard

每个用法都需要 billboard。Casey 在 HH Day 639 演示最简 billboard,工业级是标准技术。

Day 639 传达的核心工程教训:**渲染 debug 几何是"图形学小作品"**。

绘制 line / AABB / text 这些"看似简单"的东西,实际涉及图形学基础:坐标系变换、深度测试、字体光栅化、抗锯齿。Casey 在 Day 639 演示的是"自造 immediate-mode debug renderer",这是工业级游戏引擎的标准组件。

**为什么自造,不用现成?**

- **Dear ImGui**:成熟 immediate-mode UI,但偏向"应用 UI"(按钮 / 滑块),不是"几何 overlay"
- **bgfx / ImGuizmo**:可以画几何,但依赖大
- **RenderDoc**:可视化整个 draw call,但太重

Casey 想要的"轻量 debug overlay",只能自己写。每个游戏团队最终都会写自己的,因为业务特定需求无法用现成满足。

**第二条教训**:**3D 几何的 2D 化绘制是核心技术**。

debug 几何在 3D 空间,但屏幕是 2D。如何画 3D AABB 让玩家"看懂位置"?需要:

1. **View matrix**:相机变换
2. **Projection matrix**:透视 / 正交投影
3. **Clip space → NDC → screen space**:坐标变换
4. **Line rasterization**:Bresenham / DDA
5. **Depth test**(可选):depth buffer 决定线被几何挡住还是浮在前

每个步骤都是图形学基础。Casey 在 HH Day 100+ 软渲染时讲过,Day 639 是复习+应用。

**Billboard**(广告牌)是 Day 639 的关键技术:让 text 永远朝向相机,无论相机怎么转。数学:把 text 的 quad 法线设为 camera forward,确保 text 在屏幕上始终"正面"。

工业实践:**所有 3D 游戏都有 debug billboard**——玩家头上名字、技能图标、伤害数字、迷你地图标签。Casey 在 HH 演示最简单的 billboard 实现。

**第三条教训**:**text rendering 是隐藏的复杂**。

新手以为"画字"简单,实际 text rendering 涉及:

- **Font parsing**:TTF / OTF 文件解析
- **Glyph rasterization**:把矢量字形转位图
- **Kerning**:字符间距调整
- **Ligature**:fi / fl 等组合字符
- **Subpixel rendering**:抗锯齿
- **RTL / LTR**:阿拉伯语 / 希伯来语 / 中文混合

完整 text rendering 几千行代码。Casey 在 HH 简化到"ASCII + 单色 bitmap font",够 debug 用。但工业级(Unreal / Unity)用 HarfBuzz + FreeType + Stb_truetype 全套。

**迁移到其他领域**:

"自定义 debug renderer"思路在多个领域有对应:

- **Linux kernel**:trace-cmd / ftrace,内核"自定义 debug 输出"
- **Database**:EXPLAIN ANALYZE,可视化 query plan
- **Web DevTools**:可视化 DOM tree
- **AI**:tensorboard,可视化训练曲线
- **Game engine**:scene view gizmos

每个领域都需要"业务特定的可视化"。Casey 在 HH 实现的是游戏版本。

## 12 · debug draw 的工业最佳实践

工业级 debug draw 系统的 best practices:

**1. 颜色编码一致**

整个 team 约定颜色:

- 红色 = 错误 / bug
- 绿色 = OK / 成功
- 黄色 = 警告
- 蓝色 = 信息 / 中性
- 紫色 = AI / NPC
- 青色 = 网络

新人加入 team 第一天学这套,后期看 debug overlay 一眼就知道发生了什么。

**2. 持续时间**

每个 debug 几何有 lifetime:

- `draw_line(..., lifetime=0)`:单帧(下帧消失)
- `draw_line(..., lifetime=60)`:1 秒(60 FPS)
- `draw_line(..., lifetime=Infinity)`:直到游戏退出

Unity / Unreal 都用这套。Casey 在 HH 简化为"全单帧"。

**3. 类别过滤**

每个 debug 几何有 category:

```rust
enum Category { Collision, AI, Audio, Network, Physics }
draw_line(..., category=Category::Collision);
```

overlay 可以按类别开关(`F1` 切换 collision,`F2` 切换 AI)。这避免"调试一个系统被其他系统干扰"。

**4. 命名空间**

```rust
debug_section("collision_broad_phase", || {
    draw_aabb(...);
    draw_aabb(...);
});
```

整个 section 可以开关,不用逐个调用 `category`。Unity / Unreal 类似。

**5. 性能 budget**

debug draw 也有性能 budget——不能让它拖累游戏 FPS。工业级系统限制:

- 最多 N 个 line / frame(超出丢弃)
- 最多 M 个 text / frame
- 总渲染时间 < X ms

如果超 budget,优先级低的丢弃。这是资深工程师的 polish 细节。

**6. 跨平台**

debug draw 要在 PC / 主机 / 移动都跑。Console 经常不能调试(NDA 限制),所以 PC 优先。Mobile 用简化版本(性能有限)。

## 12.5 · Casey 演示的核心思想回顾

Day 639 表面是"画 line / AABB / text",但深层是几个关键思想的实例:

**思想 1: 延迟求值**

录制器把"画几何"延迟到任意时刻。这是 functional programming 的 lazy evaluation 在 debug 工具的应用。延迟求值让代码更灵活——同一个录制可以多次 replay、不同视角、不同帧。

**思想 2: 数据驱动**

命令是数据(枚举值),不是函数调用。这让命令可以被:

- 序列化(存盘)
- 测试(assert)
- 优化(batch 渲染)
- 过滤(类别开关)

数据驱动是软件工程的基础方法论。

**思想 3: 工具与产品分离**

游戏代码不调用 debug draw(产品),而是 push 命令(数据)。debug 渲染器(工具)从命令消费。这种分离让 shipping build 可以完全删 debug,产品性能不受影响。

**思想 4: 用户体验**

debug draw 的"用户"是开发者。开发者用得舒服 = 调试快。颜色编码、类别过滤、键盘快捷键——这些都是 UX。资深工程师把 debug 工具当产品打磨。

**思想 5: 抽象层次**

debug draw 涉及多层抽象:

- 业务层:`draw_player_bbox(player)` (game-specific)
- 几何层:`draw_aabb(min, max, color)` (generic)
- 渲染层:`draw_line(p1, p2, color)` (primitive)
- GPU 层:`vkCmdDrawLines(...)` (Vulkan)

每层都有抽象边界。资深工程师的 ability:**在合适的层工作**——业务问题用业务 API,不直接调 Vulkan。

Casey 在 Day 639 演示 layer 分离。这是工业级代码组织的范式。

## 13 · 现代游戏 debug draw 的演化

2020s 的 debug draw 加了新特性:

**1. GPU-driven debug draw**:

- CPU 端 push command
- GPU 端 batch 渲染
- 单 draw call 画 10000 line

**2. Ray-traced debug**:

- 用 RT core 做 raycast
- 显示"被挡住的"几何
- debug 可视化更直观

**3. VR debug draw**:

- billboard 在 VR 头显里更复杂(stereo)
- 远近要正确(depth buffer)
- 不能让 debug 干扰玩家视野

**4. Web debug draw**:

- WebGL / WebGPU
- 浏览器内 debug 可视化
- 远程协作 debug

每个演化都让 debug 更高效。Casey 在 HH 演示最简 CPU 版本,工业级是 GPU + RT + VR + Web 全套。
