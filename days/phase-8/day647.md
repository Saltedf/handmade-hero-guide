
# Day 647 · 调试简化光照

> Day 646 把光照从 3D 切到 2D。但切换有 bug——某些场景下,光看起来"消失"或"太亮"。今天 Casey 用 Day 638 的录制器(本来是为 collision 写的)调试光照 bug,展示**调试工具的复用性**。

## 0 · 为什么要有这一天

简化重构总是伴随 bug。Day 646 的 2D 光照切换引入了几个问题:

1. **某些光源完全不亮**:输入数据里有,渲染出来 0
2. **角落特别亮**:光照漏出"灯泡效果"
3. **远距离光没衰减**:本该衰减,实际不衰减

这里要强调一个反复出现的工程教训:**"等价重构"是神话**。你以为把 3D 代码改成 2D 只是删一个分量,但每一处用到 `Vec3` 的地方都要想"删哪个分量"。一个漏改 = 一个 bug。这就是为什么工业级重构总是伴随着**回归测试套件**——每改一处,自动跑几百个对比,确认输出像素一致。Casey 在 HH 没有这个 lux,所以他只能靠录制器手工对比。

更微妙的是,**bug 的种类决定调试方法**。今天的三个 bug 各属不同类型:

- "光完全不亮"是**逻辑 bug**(坐标系弄错,atan2 用了错的轴)——典型症状是"输入数据正确,输出全黑"
- "角落特别亮"是**几何 bug**(法线没归一化、或衰减公式错)——典型症状是"特定几何位置才出现"
- "远距离光不衰减"是**数据 bug**(intensity 字段没读取、或单位错)——典型症状是"看起来符合趋势,但数值 off by constant"

每种 bug 要用不同工具:逻辑 bug 用录制器单步看变量流;几何 bug 用 RenderDoc 抓帧看 vertex attribute;数据 bug 用 printfs 或 memory inspector 看字节。Casey 今天主要演示的是逻辑 bug 那条路径。

每个 bug 都需要"先复现,再定位"。Casey 用的是同一个录制器——这验证了 Day 638 投资的价值:**调试工具是长期资产**,今天为光照复用,明天可以为音频复用。

心理锚点:看完今天,你能:

- 用同一录制器调多种 bug
- 区分"shader bug"、"数据 bug"、"逻辑 bug"
- 用 binary search 缩小 bug 范围
- 解释为什么 xz 平面 ≠ xy 平面(对 2D 渲染的意义)
- 把"等价重构"识别为风险活动,知道要配套回归测试

## 2 · 心智模型

### 类比:翻译文章漏字

把 3D 光照"翻译"到 2D,就像把英文文章翻译成中文——容易漏字、改错意思。**简化重构不是简单删除**,而是要保证语义等价。

Casey 漏掉的部分:坐标系映射。3D 时 y 是上下,2D 光照在 xz 平面(不是 xy 平面),但代码里有些地方仍按 xy 平面算——这就是 bug。

### 坐标系混淆

HH 坐标系:

- x:东西
- y:上下(垂直)
- z:南北

3D 光照在 (x, y, z) 三轴。2D 光照在 (x, z) 平面——丢掉 y。

为什么选 xz 而不是 xy?这是 HH 的视角决定的。HH 用"俯视视角"——相机从天空往下看,xz 平面就是玩家看到的"地图平面"。如果把光照降到 xy 平面,意味着光照计算在"东西 × 上下"平面进行,但玩家看不到"上下"方向的延展,所以这部分光照浪费。**降到 xz 平面 = 把光照计算精确对应到玩家能看到的方向**。

但 Vec2 的两个分量是 (x, y) by default。所以从 Vec3 转 Vec2 时,要**显式取 xz**:

```rust
let v3 = Vec3::new(1.0, 2.0, 3.0);
let v2_correct = v3.xz(); // (1, 3) ← 正确
let v2_wrong = v3.xy();   // (1, 2) ← 错误(y 是上下!)
```

Casey 漏了某处,导致 2D 光照用错误的 y 分量。这种 bug 在 review 时很难看出来——`v.xy()` 和 `v.xz()` 长得几乎一样,但语义完全不同。

更隐蔽的是,**3D 的 atan2 角度公式**也要改。3D 光照里如果用极角:`atan2(y, x)` 给出 xy 平面的角度。但 2D 在 xz 平面,角度应该用 `atan2(z, x)`。Casey 漏改这个 atan2,导致光方向计算错乱。这是典型的"重构不彻底"——表面看像改完了,但隐藏的数学公式仍按旧约定算。

### Bug 排查的 binary search

调试 bug 时,从输入到输出逐层检查:

1. **输入**:`light.pos` 数值对吗?
2. **存储**:`light_table[idx]` 写入的数值对吗?
3. **shader uniform**:`glUniform3f(...)` 传入的值对吗?
4. **vertex shader**:`varying vec2 light_dir` 输出对吗?
5. **fragment shader**:`texture(light_table, uv)` 读出来的值对吗?
6. **framebuffer**:写出来的 pixel 值对吗?

每一步**断言数值**,缩小范围。

这个方法叫 **bisect debugging**(二分调试)。它的核心洞察:**bug 总在"输入正确"和"输出错误"之间的某条数据流路径上**。如果你能把这条路径切成 N 段,在每段边界断言数值,logN 次断言就能定位 bug 在哪段。

实操时,你不需要每次都跑全部 6 步。Casey 通常的次序是:

- 先看第 6 步(framebuffer),确认 bug 真的存在(不是看错)
- 跳到第 1 步(输入),确认数据正确(否则问题在数据生成)
- 然后用 binary search 在 2-5 之间找

工业级 bisect 工具:`git bisect`(对 commit 二分)、`cargo bisect-rustc`(对 rustc 版本二分)。思想上和这里一样。

注意"输入正确"和"输出错误"的定义要严格——你不能只看"差不多对"。Casey 经常说:**"差不多对"就是"错"**。浮点比较用 epsilon(比如 `abs(a - b) < 1e-5`),整数比较用精确相等。如果你的断言写得宽松,bug 就会在断言的灰色地带躲过你。

### 录制器复用

录制器的核心是命令流。为光照调试,只需加几条命令:

```rust
enum DiagramCmd {
    // ... 老的 collision 命令
    LightPos(Vec3, u32),       // 新:光源位置
    LightDir(Vec2, u32),       // 新:光方向(2D)
    LightInfluence(Vec3, f32), // 新:光源影响半径
}
```

老的 collision 命令 + 新的 light 命令,共享同一录制器 / 同一时间轴 / 同一 UI。这就是**调试工具的复用价值**。

这个抽象的本质是 **command pattern**(命令模式)——把"画什么"抽象成数据,而不是函数调用。Day 638 设计录制器时,Casey 大概没想到它会用于光照,但 command pattern 的好处就是**未来不期而至的复用**。如果 Casey 当初把 collision debug 写成 `draw_debug_collision(...)` 直接画,光照调试就要从头写一个新的 `draw_debug_lighting(...)`。但有了 command pattern,只需加 3 个 enum 变体,renderer 端加 3 个 match arm,完事。

这是软件工程里"**开闭原则**"(open-closed principle)的具体体现:**对扩展开放,对修改关闭**。Day 638 写的代码不需要改,只加新代码。

更深一层:command pattern 还让"录制"和"回放"分离。如果你直接画函数,你只能"实时画",没法回头。但 command 是数据,可以存到磁盘、可以倒放、可以做差分对比。这就是为什么所有专业 debug tool —— RenderDoc、Tracy、PIX、Xcode Metal debugger——都用 command pattern 存帧数据。Casey 在 HH 自己实现了一个迷你版本。

## 2.5 · 真实 bug 案例:atan2 坐标轴混淆

让我们把 Casey 找到的核心 bug 拉近看,因为它是教科书级的"重构不彻底"案例。

**3D 光照代码**(简化):

```c
// 3D 版本:计算光源相对片段的方向
Vec3 light_dir = normalize(light_pos - frag_pos);
float angle = atan2(light_dir.y, light_dir.x);  // xy 平面角度
// 用 angle 查表 / 计算阴影 / ...
```

**Day 646 改成 2D**(简化):

```c
// 2D 版本:在 xz 平面算光照
Vec2 light_dir_2d = normalize((light_pos - frag_pos).xz);
float angle = atan2(light_dir.y, light_dir.x);  // ← BUG:还是用 xy!
```

注意 bug:第二行从 `Vec3 light_dir` 改成了 `Vec2 light_dir_2d`,但**第三行的 atan2 没改**。它仍然引用了已经不存在的 `light_dir.y`,但 C 的弱类型系统让这个错误被掩盖——可能 light_dir 仍然在作用域里,或者用了一个全局变量,或者用了一个默认值。

实际 bug 表现:**光源在某些角度完全不亮**。因为 atan2 用错误的分量,计算出的 angle 是错的,后续查表查到错的 entry,光照就是 0。

Casey 的修复:把所有 atan2 改成 `atan2(z, x)`(因为 HH 是 xz 平面)。这看似只是 1 个字符的修改(y → z),但要在整个 codebase 找到所有 atan2 调用,逐个判断语义,这是 polish 阶段最累人的活。

**教训**:**重构时,数学公式是最容易漏改的地方**。函数调用容易看(`fn(v3.x, v3.y)` 改成 `fn(v3.x, v3.z)`),但纯数学表达式(`atan2(a, b)`)如果不带上下文,你不知道 a 和 b 代表什么。一个解法是用 named constant:

```rust
const AXIS_HORIZONTAL: usize = 0; // x
const AXIS_VERTICAL: usize = 2;   // z (for xz plane)

let angle = light_dir[AXIS_VERTICAL].atan2(light_dir[AXIS_HORIZONTAL]);
```

虽然啰嗦,但 review 时一眼能看出"用的是 AXIS_VERTICAL,如果项目改了上下轴,只需改常量"。这就是 defensive coding。

## 3 · 四域深入

### 3.1 · 游戏编程视角

调试工具的复用案例:

- **Unity Gizmos**:既用于 collision bounds,也用于 navmesh、AI waypoints、trigger zones
- **Unreal DrawDebugLine**:同上
- **Insomniac Hubba**:索尼第一方工作室的统一 debug overlay

投资一个调试工具,长期受益。

Unity 的 Gizmos 系统是这个理念的最佳例子。`OnDrawGizmos()` 是一个回调,你在里面写 `Gizmos.color = Color.red; Gizmos.DrawWireSphere(transform.position, 5f);`,编辑器视图里就画出红色线框球。同一个 API 被 collision、AI、audio、animation 各个子系统调用——因为它们都"想画几何"。

Unreal 的 `DrawDebugLine` / `DrawDebugSphere` / `DrawDebugPoint` 系列函数也是这个思路。区别是 Unreal 用 immediate 调用(每帧调一次),Unity 用回调(自动每帧调)。

工业里这条抽象的最终形态是 **debug draw API**:一个引擎级接口,任何子系统都能"画一行 debug 几何",引擎统一收集、剔除、渲染。Casey 在 HH 实现的就是这个——只是简化版,集中在录制器里。

游戏程序员面试常问的一道题:**"你怎么设计引擎的 debug draw 系统?"** 标准答案要点:

1. **多类别**(collision / AI / audio / network),每类有开关
2. **生命周期**(单帧 / 持续 / 直到条件)
3. **颜色编码**(红色 = 错误,绿色 = OK,蓝色 = 信息)
4. **持久化**(录制帧,支持回放)
5. **零开销 in shipping**(cfg 掉)

Casey 的录制器实现了 1、3、4、5,2 留给将来。这是 80% 解决方案,实用。

### 3.2 · 图形学视角

光照 bug 的常见类型:

- **坐标轴混淆**:x/y/z 弄错(今天 Casey 的 bug)
- **单位不一致**:position 用 world space,normal 用 tangent space,直接相乘错
- **线性 vs sRGB**:颜色没做色彩空间转换
- **距离衰减公式错误**:`1/d^2` 还是 `1/(1+d^2)`?
- **shadow acne**:bias 不够

每一类都需要不同的调试方法。

### 3.3 · Linux 系统编程视角

Linux 里类似的"接口契约不一致" bug:

- **SIGPIPE vs EPIPE**:read 端和 write 端处理不匹配
- **errno 线程局部性**:多线程下 errno 是 thread-local,跨线程误读
- **byte order**:ntohl / htonl 网络 vs 主机字节序

这些 bug 都源于"接口两端约定不一致",和 Casey 今天的 bug 同构。

### 3.4 · Rust 生态视角

Rust 类型系统帮我们避免一些 bug:

```rust
// 用 newtype 模式区分不同坐标系
struct WorldCoord(Vec3);
struct LocalCoord(Vec3);
struct LightSpaceCoord(Vec3);

// 这样就不能混用
fn light(world: WorldCoord) -> LightSpaceCoord { ... }
let p: WorldCoord = ...;
let _ = light(p); // OK
let bad = light(p.0); // 类型不匹配,编译错误
```

Casey 在 C 里没法这样做,所以 bug 容易漏。Rust 的 newtype 是消除坐标混淆的利器。

再举一个 Rust 帮忙的场景:坐标轴混淆。如果你定义:

```rust
struct X(f32);
struct Y(f32);
struct Z(f32);

fn light_offset(x: X, z: Z) -> Vec2 {
    Vec2::new(x.0, z.0)
}
```

调用 `light_offset(Z(1.0), X(2.0))` 就会编译失败——X 和 Z 是不同类型。这把"axis 混淆"从 runtime bug 变成 compile error,**这是 Rust 的最大卖点之一**。

不过 newtype 也有代价——你失去了 `Vec3` 的算术运算(`+`, `-`, `*`)。要么手写 `impl Add for WorldCoord`,要么用宏自动生成(bevy / glam 生态有一些 helper crate)。在大型游戏项目里,这种代价是值得的;在小项目里可能 over-engineered。

Rust 的另一个工具是 `#[track_caller]` 和 panic message——你可以在 debug build 里加 assertion,出错时打印调用位置:

```rust
fn light_offset_xz(pos: Vec3) -> Vec2 {
    debug_assert!(pos.is_finite(), "non-finite light pos: {:?}", pos);
    debug_assert!(pos.y.abs() < 1e-3, "y component too large for 2D light: {}", pos.y);
    pos.xz()
}
```

这两个 assert 在 release build 被 cfg 掉,debug build 里帮你捕获"错误坐标系传入"。Casey 在 C 里用 `Assert(...)` 宏做同样的事。

## 5 · 对照与变奏

不同坐标系约定:

| 引擎 | 上下轴 | 前后轴 | 备注 |
|---|---|---|---|
| Unity | Y | Z | 左手系 |
| Unreal | Z | X | 左手系,Z 朝上 |
| HH | Y | Z(OpenGL 风格) | 右手系 |
| Source | Z | Y | 左手系 |
| Godot | Y | Z | 右手系(3.x 之后默认) |
| Bevy | Y | Z | 右手系 |

跨引擎协作时容易混淆。Rust newtype 能挡住类型错误,但不能挡住"上下轴是哪个"的语义错误。

跨引擎协作的真实场景:**美术在 Maya 建模,导入 Unity**。Maya 默认 Y up,Unity 也是 Y up,但前后方向相反——模型导入后转了 180 度。修法:在导入管线加 `rotation.y = 180`。这是"美术管线 bug",经常困扰中级开发者。

跨引擎协作的另一个常见 bug:**法线方向反了**。OpenGL 是右手系,D3D 是左手系,法线 z 分量要 negate。如果你的 game engine 用 OpenGL 但 import 了 D3D 资源,所有法线都反了,光照计算给出"黑暗背面"的效果。修法:在 import 时检测引擎 handedness,需要时 negate。

更深层的历史演化:**坐标系之争是图形学的"宗教战争"**。

- **1970s**:SGI OpenGL 选右手系,因为数学传统(右手系更"自然")
- **1990s**:Microsoft Direct3D 选左手系,因为屏幕坐标(左上角原点,y 向下)天然是左手
- **2000s**:OpenGL ES、Vulkan 都继承右手系
- **2010s**:Unity 用左手(因为早期 D3D),Unreal 用左手(同理),Godot 选右手(因为 OpenGL ES)
- **2020s**:WebGPU 抽象掉了 handedness,你可以在 clip space 自己选

Casey 在 HH 选右手系,跟随 OpenGL 传统。这意味着所有叉乘用右手定则,所有 normal 朝外,z 向屏幕外。如果你之前用 Unity 习惯了左手系,到 HH 要重新校准空间直觉。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 的录制器能复用到光照?录制器的核心抽象是什么?

**参考解答**:录制器核心是**声明式命令流 + 时间轴**。它不关心"画的是什么",只关心"什么时候画什么几何"。光照调试需要画"光源位置"和"光影响范围",这些都是几何(点 / 圆 / 向量),和 collision 调试画的"AABB"和"velocity vector"同构。所以同一录制器通用,只需加几条新命令变体。

### Lv2 · 动手实践

**题**:在 Day 638 的 DiagramCmd 加 `LightPos` 和 `LightInfluence` 命令,实现录制和回放。

**额外要求**(进阶):实现一个 `Bisect` 函数,给定一个帧索引和一条 assertion,自动找到第一帧违反 assertion 的位置(类似 `git bisect`)。

**参考解答**:

```rust
use std::collections::VecDeque;

#[derive(Clone, Debug)]
enum Cmd {
    Point([f32; 3], u32),
    AABB([f32; 3], [f32; 3], u32),
    LightPos([f32; 3], u32),
    LightInfluence([f32; 3], f32, u32), // pos, radius, color
}

struct Recorder {
    cmds: VecDeque<Vec<Cmd>>,
    capacity: usize,
}

impl Recorder {
    fn new(c: usize) -> Self { Self { cmds: VecDeque::with_capacity(c), capacity: c } }
    fn record_frame(&mut self, frame_cmds: Vec<Cmd>) {
        if self.cmds.len() == self.capacity { self.cmds.pop_front(); }
        self.cmds.push_back(frame_cmds);
    }
    fn playback(&self, idx: usize) -> Option<&Vec<Cmd>> {
        self.cmds.get(idx)
    }
    /// Binary search: 找第一帧 assertion 返回 false 的位置
    fn bisect<F: Fn(&[Cmd]) -> bool>(&self, assertion: F) -> Option<usize> {
        // 假设 assertion 在所有早期帧返回 true,后期帧返回 false
        // 找最早的 false 帧
        let n = self.cmds.len();
        if n == 0 { return None; }
        if assertion(&self.cmds[0]) { return None; } // 第一帧就违反
        if !assertion(&self.cmds[n - 1]) { return Some(n - 1); }
        let mut lo = 0usize;
        let mut hi = n - 1;
        while hi - lo > 1 {
            let mid = (lo + hi) / 2;
            if assertion(&self.cmds[mid]) {
                hi = mid;  // mid 仍然 ok,所以最早的 bad 在 mid 之后
            } else {
                lo = mid;  // mid 已经 bad
            }
        }
        // 此时 lo 是最后一个 ok,hi 是第一个 bad
        if assertion(&self.cmds[lo]) && !assertion(&self.cmds[hi]) {
            Some(hi)
        } else {
            None // 不满足单调假设
        }
    }
}

fn main() {
    let mut rec = Recorder::new(60);
    // 模拟 1 帧
    rec.record_frame(vec![
        Cmd::AABB([0.0; 3], [1.0; 3], 0xFF0000),
        Cmd::LightPos([5.0, 3.0, 5.0], 0xFFFF00),
        Cmd::LightInfluence([5.0, 3.0, 5.0], 10.0, 0xFFFF00),
    ]);
    let frame = rec.playback(0).unwrap();
    println!("Frame 0 has {} commands", frame.len());
    for cmd in frame {
        println!("  {:?}", cmd);
    }

    // bisect 测试:模拟一个 bug 在第 30 帧引入
    for i in 1..60 {
        let mut cmds = vec![Cmd::AABB([0.0; 3], [1.0; 3], 0xFF0000)];
        if i >= 30 {
            // bug 帧:多了一个错误的 LightInfluence
            cmds.push(Cmd::LightInfluence([0.0; 3], -1.0, 0xFF0000));
        }
        rec.record_frame(cmds);
    }
    let bug_frame = rec.bisect(|cmds| {
        // assertion: 没有 radius < 0 的 LightInfluence
        cmds.iter().all(|c| !matches!(c, Cmd::LightInfluence(_, r, _) if *r < 0.0))
    });
    println!("Bug introduced at frame: {:?}", bug_frame);
    // 应该输出 30
}
```

bisect 是工程利器。如果你的录制器录了 60 帧且 bug 在某帧出现,bisect 只需 log2(60) ≈ 6 次 assertion 调用就能定位——比线性扫描快 10 倍。在大型游戏项目里,有时录制上千帧,bisect 节省的时间非常可观。

```rust
use std::collections::VecDeque;

#[derive(Clone, Debug)]
enum Cmd {
    Point([f32; 3], u32),
    AABB([f32; 3], [f32; 3], u32),
    LightPos([f32; 3], u32),
    LightInfluence([f32; 3], f32, u32),
    Raycast([f32; 3], [f32; 3], u32),
}

struct Recorder {
    frames: VecDeque<Vec<Cmd>>,
    capacity: usize,
}

impl Recorder {
    fn new(c: usize) -> Self {
        Self { frames: VecDeque::with_capacity(c), capacity: c }
    }
    fn end_frame(&mut self, cmds: Vec<Cmd>) {
        if self.frames.len() == self.capacity { self.frames.pop_front(); }
        self.frames.push_back(cmds);
    }
    fn playback(&self, frame_idx: usize) -> Option<&Vec<Cmd>> {
        self.frames.get(frame_idx)
    }
}

// 2D 光照计算
fn compute_lighting(
    lights: &[(Vec3, [f32; 3])],  // (pos, color)
    surfaces: &[(Vec3, Vec3, [f32; 3])], // (pos, normal, albedo)
) -> Vec<([f32; 3], [f32; 3])> {  // (pos, final_color)
    surfaces.iter().map(|(pos, normal, albedo)| {
        let mut color = [0.0; 3];
        for (lpos, lcol) in lights {
            let dir = *lpos - *pos;
            let dir_2d = dir.xz();
            let normal_2d = normal.xz();
            let dist = dir_2d.length();
            if dist < 1e-6 { continue; }
            let dir_2d = dir_2d / dist;
            let n_dot_l = normal_2d.dot(dir_2d).max(0.0);
            let atten = 1.0 / (1.0 + dist * dist);
            color[0] += albedo[0] * lcol[0] * n_dot_l * atten;
            color[1] += albedo[1] * lcol[1] * n_dot_l * atten;
            color[2] += albedo[2] * lcol[2] * n_dot_l * atten;
        }
        ([pos.x, pos.y, pos.z], color)
    }).collect()
}

fn main() {
    use glam::{Vec2, Vec3};
    let lights = vec![
        (Vec3::new(5.0, 3.0, 5.0), [1.0, 1.0, 0.9]),
    ];
    let surfaces = vec![
        (Vec3::new(2.0, 0.0, 2.0), Vec3::new(1.0, 0.0, 1.0).normalize(), [0.8, 0.8, 0.8]),
        (Vec3::new(0.0, 0.0, 0.0), Vec3::new(1.0, 0.0, 0.0).normalize(), [0.5, 0.5, 0.5]),
    ];
    let results = compute_lighting(&lights, &surfaces);
    for (pos, color) in &results {
        println!("pos={:?} color={:?}", pos, color);
    }

    // 录制
    let mut rec = Recorder::new(60);
    let mut frame = vec![
        Cmd::LightPos([5.0, 3.0, 5.0], 0xFFFF00),
        Cmd::LightInfluence([5.0, 3.0, 5.0], 5.0, 0xFFFF00),
    ];
    for (pos, color) in &results {
        let c = (color[0] as u32) << 16 | (color[1] as u32) << 8 | color[2] as u32;
        frame.push(Cmd::Point(*pos, c));
    }
    rec.end_frame(frame);
    println!("Recorded frame 0 with {} cmds", rec.playback(0).unwrap().len());
}
```

## 10 · 工程反思

Day 647 表面是"修 bug",但传达了三个长期受益的工程教训:

**教训一:工具投资回报率高**。Day 638 Casey 花了一整集做录制器,看起来是"和当前 bug 无关"。但 Day 647 光照 bug、Day 644 单步控制、Day 643 角落碰撞——全部得益于这个录制器。**好的调试工具是基础设施**,今天的"浪费"是明天的"杠杆"。工业里,team lead 经常要 push 团队"花一周做 debugging 工具",因为短期看像没产出,长期看节省数月。

**教训二:重构不彻底是 bug 工厂**。把 3D 改成 2D 看似简单,但每一行涉及坐标的代码都要审查。漏改一行 = 一个 bug。**预防方案是"原子重构"**:用一次性 PR、用 sed/regex 批量替换、用类型系统(newtype)保护。Casey 在 C 里没法用类型系统,只能靠手工 review——这就是为什么 C 项目重构比 Rust 项目重构难。

**教训三:坐标系是 graphics bug 的温床**。xy vs xz、left-handed vs right-handed、world space vs view space vs clip space——任何一个混淆都能让光照算出错的值。养成习惯:**写每行坐标代码时,在心里标注"这一项在什么坐标系"**。如果代码读起来不清晰,加注释、加 newtype、加 assert——一切都值得。

这三条教训不仅适用于游戏开发,适用于任何涉及"多个抽象层"的工程。当你看到"看似简单的修改引入 bug",大概率就是这三类问题的某一个。
