
# Day 640 · 调查角落碰撞

> 有了 Day 638/639 的录制器和可视化,今天 Casey 用它们追一个具体 bug:玩家从两个 voxel 拐角穿过时,**有时**会被卡,有时不会。这是 voxel collision 的经典边角 case——**多边形拐角几何**导致的歧义。

## 0 · 为什么要有这一天

voxel collision 的最坏场景是**角落**:两个 solid voxel 形成 L 形拐角,玩家从对角方向穿过,可能:

- 玩家球同时碰到两个 voxel,各自的解嵌向量指向**相反方向** → 累加为零,玩家卡死
- 玩家球碰到拐角 voxel 的"凹角",最近点在角顶,解嵌向量沿对角线,但因为第二个 voxel 干扰,推错方向
- 玩家球碰到的 voxel 集合**每帧不同**,导致 unembed 向量**每帧方向不同**,玩家"颤抖"

这就是 Casey 今天要调查的问题。**录制器**让 Casey 能"看"到每一帧玩家碰了哪些 voxel、各自推了什么方向——以前看不见,只能猜。

工业做法叫 **iterative collision resolution**:多轮迭代,每轮 unembed 后重新检查,直到稳定。但迭代有**震荡风险**——A 把球推到 B,B 把球推回 A,无限震荡。Casey 今天研究**怎么避免震荡**。

心理锚点:看完今天,你能:

- 诊断"多 voxel 拐角卡死"的根因
- 解释为什么简单 unembed 在拐角失败
- 实现稳定的 iterative collision resolution

## 2 · 心智模型

### 类比:挤地铁

想象你在挤地铁,左右两侧都有人推你:

- 左边的人推你向右 +1 米
- 右边的人推你向左 -1 米
- 两个力加起来 = 0,你卡在中间

但现实里你不会卡——你会找一个**夹缝**:左右都没人推的方向(比如斜前方)。voxel collision 同理:当球同时在两个 voxel 的"力场"里,简单累加会导致卡死。**正确的解法是找"全局最优解嵌方向"**,而不是各方向独立计算再叠加。

### 数学:为何简单 unembed 在拐角失败

设球心 C,两个 solid voxel V1、V2 形成 L 拐角。C 同时在 V1 和 V2 的"最近点"附近。

- V1 的最近点 P1,解嵌向量 d1 = (C - P1) * (r / |C - P1| - 1)
- V2 的最近点 P2,解嵌向量 d2 = (C - P2) * (r / |C - P2| - 1)

如果 P1 和 P2 在 C 的两侧,d1 和 d2 大致反向,加起来 ~0。

**正确做法**:不要"每个 voxel 独立算",而要"所有 voxel 一起优化"。这就是 **non-linear optimization**——求一个 C',使得对所有 voxel,|C' - closest_i(C')| >= r。

工业做法有几种:

1. **Sequential impulse**(Box2D):迭代每个约束,每次只解一个,反复迭代直到收敛
2. **Projected Gauss-Seidel**:类似 sequential impulse,但数学上更严格
3. **Linear complementarity problem (LCP)**:正式的数学表述,用 Lemke 算法解
4. **IPC**(Incremental Potential Contact):最近几年的新方法,barrier function 防穿透

Casey 用的是简化版 sequential impulse——简单,稳定,够用。

### Iterative resolution 算法

```
fn resolve_collisions(pos: &mut Vec3, radius: f32, voxels: &[IVec3]) {
    let max_iters = 8;
    let max_step = 0.1; // 每次最多推 0.1 米
    
    for _ in 0..max_iters {
        let mut total_push = Vec3::ZERO;
        let mut any_collision = false;
        
        for v in voxels {
            let d = sphere_voxel_distance(*pos, *v, radius);
            if d < 0.0 {
                // 碰撞,push 方向是球心到 voxel 最近点
                let push = ...; // 见 Day 637
                total_push += push;
                any_collision = true;
            }
        }
        
        if !any_collision { break; }
        
        // clamp 防瞬移
        let len = total_push.length();
        if len > max_step {
            total_push = total_push * (max_step / len);
        }
        
        *pos += total_push;
    }
}
```

关键点:

- **多轮迭代**:每轮推一点,下一轮基于新位置再算
- **每轮 clamp**:防止单次推太大,导致 overshoot
- **early-exit**:如果某轮没碰撞,提前结束

### 震荡 vs 收敛

为什么简单迭代会震荡?考虑两个 voxel V1、V2,球 C 在中间:

- 第 1 轮:V1 把 C 推到右边(+x),C 现在更靠近 V2
- 第 2 轮:V2 把 C 推到左边(-x),C 又回到中间
- 反复

修法:**取累加后的总 push**,而不是逐个应用。Casey 的 `total_push += push` 就是这个思路。

但累加也可能问题:如果两个 push 反向大小相同,`total_push = 0`,玩家卡死。这时**只能换思路**——用 sequential impulse 的正式版,每轮每个 voxel 单独应用 + 投影,反复 N 次直到收敛。

### L 拐角的几何直觉

```
        V2 (solid)
        ████
        ████
─────C─ ██
ball   ↑
       │
       │ 这里 "凹角",V1 的右下角 + V2 的左下角
───────████───
       ████ V1 (solid)
       ████
```

球 C 想从下方进入拐角,V1 的最近点在 C 下方,V2 的最近点在 C 左方。两个解嵌向量 +y 和 +x,加起来 (+1, +1) 方向——这是合理的!球应该被推到右上方。

但**有时** V1 和 V2 都把 C 当成"在 voxel 内",最近点都是 voxel 中心,解嵌向量变得奇怪。这就是 Day 641 要用 flood fill 解决的问题——**正确识别哪些 voxel "算作"碰撞**。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏里"角落卡死"经典案例:

- **Minecraft**:玩家在 1x1 的洞里有时卡住(虽然 Notch 用 AABB,但同样问题)
- **Roblox**:早期版本有大量"墙角卡死" bug,后来用 sequential impulse
- **Source 引擎**:CS:GO 玩家有时"被墙吸住",通过 un-stuck 命令救出
- **GTA V**:玩家在墙角连续跳跃会被瞬移到附近合法位置(自动 un-stuck)

工业引擎的"un-stuck"逻辑都是 iterative resolution 的变种,加 timeout(超过 N 轮就 teleport 玩家)。

### 3.2 · 图形学视角

物理引擎的"LCP formulation":

约束 J*v >= 0(速度方向上不能穿透),求力 f >= 0 使 J*v = 0。
这是线性互补问题(Linear Complementarity Problem),用 Lemke 算法或 projected Gauss-Seidel 解。

Box2D 的 Erin Catto 系列论文(GDC 2005-2014)系统讲解这个领域。Casey 用最简版本,足够 voxel 场景。

### 3.3 · Linux 系统编程视角

Linux 内核也有"迭代收敛":

- **page reclaim**:每轮 kswapd 扫描一定页,直到空闲页达到阈值
- **OOM**:多轮回收失败,触发 OOM killer
- **scheduler load balancing**:周期性 balance CPU 队列,收敛到均衡

内核不需要严格"收敛",只要"单调趋近"。

### 3.4 · Rust 生态视角

Rust 里 iterative solver:

```rust
fn resolve_collisions(
    pos: &mut Vec3,
    radius: f32,
    is_solid: impl Fn(IVec3) -> bool,
) -> bool {
    let max_iters = 8;
    for _ in 0..max_iters {
        let push = compute_total_push(*pos, radius, &is_solid);
        if push.length_squared() < 1e-8 { return true; } // 收敛
        let len = push.length();
        let step = if len > 0.1 { push * (0.1 / len) } else { push };
        *pos += step;
    }
    false // 没收敛,可能要 teleport
}

fn compute_total_push(pos: Vec3, r: f32, is_solid: &dyn Fn(IVec3) -> bool) -> Vec3 {
    let lo = (pos - Vec3::splat(r)).floor().as_ivec3();
    let hi = (pos + Vec3::splat(r)).floor().as_ivec3();
    let mut total = Vec3::ZERO;
    for z in lo.z..=hi.z {
        for y in lo.y..=hi.y {
            for x in lo.x..=hi.x {
                let v = IVec3::new(x, y, z);
                if !is_solid(v) { continue; }
                let v_min = v.as_vec3() - Vec3::splat(0.5);
                let v_max = v.as_vec3() + Vec3::splat(0.5);
                let closest = pos.clamp(v_min, v_max);
                let d = pos - closest;
                let dist_sq = d.length_squared();
                if dist_sq < r * r && dist_sq > 1e-12 {
                    let dist = dist_sq.sqrt();
                    total += d * (r / dist - 1.0);
                }
            }
        }
    }
    total
}
```

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"每个 voxel 独立 unembed 后累加"在拐角失败,但"iterative resolution"能成功?

**参考解答**:独立 + 累加是"一次性"算法,把所有约束的"梯度"加起来走一步。但每个约束的梯度是在**当前位置**算的,新位置可能让某些约束的梯度方向反转——一次大步走错。iterative 走小步,每步重新算梯度,允许中途修正方向,所以更稳。本质上:**非线性优化必须迭代,一次解不适用**。

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::{Vec3, IVec3};

fn is_solid(v: IVec3) -> bool { v.y < 0 }

fn compute_push(pos: Vec3, r: f32) -> Vec3 {
    let lo = (pos - Vec3::splat(r)).floor().as_ivec3();
    let hi = (pos + Vec3::splat(r)).floor().as_ivec3();
    let mut total = Vec3::ZERO;
    for z in lo.z..=hi.z {
        for y in lo.y..=hi.y {
            for x in lo.x..=hi.x {
                let v = IVec3::new(x, y, z);
                if !is_solid(v) { continue; }

                let vmax = v.as_vec3() + Vec3::splat(0.5);
                let closest = pos.clamp(vmin, vmax);
                let d = pos - closest;
                let dist_sq = d.length_squared();
                if dist_sq < r * r && dist_sq > 1e-12 {
                    let dist = dist_sq.sqrt();
                    total += d * (r / dist - 1.0);
                }
            }
        }
    }
    total
}

fn resolve(pos: &mut Vec3, r: f32) -> bool {
    for iter in 0..16 {
        let push = compute_push(*pos, r);
        let len_sq = push.length_squared();
        if len_sq < 1e-8 {
            println!("Converged at iter {}", iter);
            return true;
        }
        let len = len_sq.sqrt();
        let step = if len > 0.1 { push * (0.1 / len) } else { push };
        *pos += step;
    }
    false
}

fn main() {
    // 玩家从空中落下,卡进地里
    let mut p = Vec3::new(0.5, -0.2, 0.5);
    println!("Initial: pos = {:?}", p);
    let ok = resolve(&mut p, 0.4);
    println!("After:   pos = {:?}, converged = {}", p, ok);
}
```

## 10 · 工程反思

Day 640 传达的核心工程教训:**边角 case 是真正的工程挑战**。

新手工程师实现 "AABB 碰撞" 觉得简单——单 voxel 单玩家 30 行代码搞定。但当玩家在两个 voxel 拐角时,**代码可能进入未定义行为**——某个法线算错,推回方向反了,玩家"卡死"。

工业教训:**80% 的时间花在 20% 的边角 case**。资深工程师的能力是"识别边角 case + 系统化解决"。

**Casey 的方法论**:

1. **用录制器复现 bug**——找到 100% 触发的输入序列
2. **画出几何状态**——肉眼看到错误
3. **追溯根因**——从"表现"回溯到"代码"
4. **修复**——治本(算法层面),不治标(hack)

这套方法在 Phase 0 的"系统化调试"讲过,Day 640 是实例。

**第二条教训**:**几何歧义是图形/物理的共同难题**。

"两个 voxel 形成 L 形拐角"这个几何,数学上有歧义——玩家从对角方向靠近,可以"从左推"也可以"从右推",没有"正确答案"。物理引擎处理这种歧义有几种方法:

- **Conservative**(保守):拒绝任何模糊移动,玩家卡住
- **Heuristic**(启发式):选一个方向(基于玩家速度方向)
- **Stochastic**(随机):随机选,多次平均
- **Soft constraint**(软约束):用约束求解器,无强制

Casey 选 heuristic(基于运动方向选 unembed 方向)。每种方法都有 trade-off,资深工程师选最合适当前场景的。

**第三条教训**:**视觉欺骗工程师**。

玩家撞墙角,从视觉看像"穿墙",但实际可能是"球嵌入后推出"。如果工程师不画几何状态,会被视觉误导——以为"碰撞代码错了",实际是"绘制与物理不一致"。

录制器的价值在这里:**让"看不见的物理"变成"看得见的几何"**。Casey 在 HH Day 640 反复演示这套思维。

**迁移到其他领域**:

边角 case 处理在多处通用:

- **整数溢出**:INT_MAX + 1 是边角
- **空指针**:nullptr deref 是边角
- **并发竞争**:多线程 race condition 是边角
- **网络分区**:split-brain 是边角
- **数据迁移**:旧 schema 是边角

每个领域都有"边角 case 占 80% 时间"现象。资深工程师的核心能力是系统化应对。

## 11 · 角落 collision 的算法细节

L 形拐角的 unembed 是 collision 经典问题。算法:

```rust
fn unembed_at_corner(bbox: &Bbox, voxel_a: IVec3, voxel_b: IVec3) -> Vec3 {
    // 两个 voxel 形成 L 形,玩家在拐角
    let normal_a = unembed_one_voxel(bbox, voxel_a);
    let normal_b = unembed_one_voxel(bbox, voxel_b);
    // 合并法线,但要避免相互抵消
    let combined = normal_a + normal_b;
    if combined.length_squared() > 1e-6 {
        combined.normalize() * normal_a.length().max(normal_b.length())
    } else {
        // 抵消了,选任意一个
        normal_a
    }
}
```

关键洞察:**两个 voxel 法线相加**,而不是逐个应用。逐个应用会导致"震荡"——A 推后碰到 B,B 推后碰 A,反复。

工业级物理引擎(Box2D / Havok)用 sequential impulse 算法解决类似问题——所有 constraint 同时考虑,迭代收敛。Casey 在 HH 简化为"法线相加",大多数 case 工作。

**实际 demo 案例**:

玩家在 L 形拐角,球嵌入两个 voxel。Casey 调试发现:

- 单 voxel unembed:震荡(球在两个 voxel 之间来回)
- 法线相加:平滑(球被推到拐角外)

这是 Day 640 的核心 insight。资深工程师的 ability:从"震荡"现象推出"需要联合求解"。

**工业级 corner case 处理**:

- **Concave corner**(凹角):两个 solid voxel 形成"内拐角",玩家嵌入。联合解。
- **Convex corner**(凸角):两个 solid voxel 形成"外拐角",玩家嵌入一个或两个。联合解。
- **Edge case**(边):单 voxel 边缘,玩家嵌入。单解。
- **Face case**(面):玩家嵌入 voxel 平面。单解。

每种 case 有自己的最优算法。资深工程师按 case 选算法,优化每个场景。

## 12 · 工业级 corner case 处理工具

工业级游戏处理边角 case 的工具集:

**1. Property-based testing**:

```rust
// proptest crate
proptest! {
    fn test_no_embed_after_unembed(bbox in arbitrary_bbox()) {
        let corrected = unembed(&bbox);
        prop_assert!(!is_embedded(&corrected));
    }
}
```

随机生成 bbox,确保 unembed 后不再 embedded。捕获边角 case。

**2. Fuzz testing**:

cargo-fuzz + libFuzzer,生成"奇怪"输入(极端位置、NaN、超大值),测试 unembed 不 panic。

**3. Recording regression tests**:

录制 bug 触发的输入序列,作为永久 test case。下次代码改动跑同序列,确认 bug 不复发。

**4. Visual diff testing**:

每帧截图,新版本和上一版本对比。如果像素差异 > 阈值,警告。捕获视觉回归。

每个工具都让边角 case 工程化。Casey 在 HH 用录制器做 regression,但工业级全套都用。

## 13 · 案例:Dark Souls 角落 bug

Dark Souls 1 著名的"角落 bug"——玩家在墙角后退时,被墙"吸住",速度变成"反向"。这是 collision normal 计算错误——墙角的两个 voxel 法线相互抵消,玩家被推回墙里。

修法(From Software 在 Remastered 版):用 sequential impulse 算法,所有约束同时解,避免相互抵消。这是工业级 corner case 处理的典型。

资深工程师从这种 bug 学到:**collision 算法的边角 case 是游戏口碑的关键**。玩家不会原谅"手感烂"的游戏,即使内容再好。

## N0 • 深度教学补充

### 核心概念重新梳理

Day 640 涉及的核心概念需要在多个层次上理解:

**第一层:直观理解**

新手第一次接触概念,需要建立直觉。例如 voxel collision 是"虚拟物体不能穿过虚拟墙"——这个直觉每个人都能从现实经验获得。

**第二层:数学理解**

把直觉形式化。collision = "两个几何体的体积有交集"。对于 AABB,这等价于"三轴投影都重叠"。

**第三层:工程理解**

数学正确不等于工程实现正确。要考虑:

- 浮点精度边界
- 性能(每帧 N 个查询)
- 内存(数据结构紧凑)
- 边角 case(无穷大、NaN、负数)

**第四层:工业理解**

工业级要再加:

- 多线程安全
- SIMD 优化
- 网络同步(多人游戏)
- 跨平台(Windows/Mac/Linux/Mobile)
- 可访问性(色盲友好)
- 反作弊

每层理解都让代码更鲁棒。资深工程师在所有层次同时思考。

### 实际工程的细节

工业代码 80% 是"边角 case 处理",20% 是"核心算法"。Casey 在 HH 演示核心,工业代码加大量边角处理。

**边角 case 类型**:

1. 空输入(空 Vec、null pointer)
2. 极端输入(NaN、无穷大、超大数)
3. 并发竞争(多线程同时访问)
4. 资源不足(内存满、磁盘满)
5. 网络异常(超时、断连、包丢失)
6. 版本不兼容(老配置 / 新代码)
7. 权限错误(只读文件、无网络)
8. 用户误操作(连点、撤销重做)

每个 case 都要单独处理。这是工业代码 50%+ 行数的原因。

### 优化思路

性能优化有顺序:

1. **算法**:O(N²) → O(N log N),最大提升
2. **数据结构**:Vec → HashMap / BTreeMap,常数提升
3. **Cache**:AoS → SoA,cache 命中提升
4. **SIMD**:4-16 元素并行,巨大常数提升
5. **GPU**:数千核并行,极致性能
6. **分布式**:多机器,无限扩展

每级提升都需要更复杂的代码。先优化低级,够用再升级。
