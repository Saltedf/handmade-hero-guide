
# Day 578 · 采样八面体图集

> 昨天 Casey 搭好了"光照图集"的骨架,今天他要把采样做到位。最容易忽视的细节是"贴图边界怎么处理"——八面体 UV 平面的 4 条边对应球面上的赤道一圈,采样时如果线性插值跨过边界,光强会瞬间跳变,墙角会出现"亮带"。今天这一集就是把这些细节啃下来。

## 0 · 为什么要有这一天

你昨天写了 `sample(dir: Vec3) -> RGB32F`,在单点测试里它返回了正确的结果。当你把它接到游戏里——让墙体颜色随玩家位置变,从墙上的每个 texel 反向采样光照图集——你会发现一些诡异现象:

- **墙角闪烁**:玩家走到墙角,墙面突然出现一道亮带,转身又消失。这是因为某个 texel 的采样方向刚好穿过八面体贴图的"翻折线"(对应球面赤道对面),双线性插值从一个 texel 跳到反面 texel,光强跳变。
- **接缝伪影**:同一段墙,玩家正对它看颜色正常,转头侧着看,接缝处突然变暗或变亮。
- **南北极异常**:往正北极和正南极方向采样,光强和预期差很多——因为这两个方向被映射到 UV 平面的中心点和角点,那里的 texel 在双线性插值里和邻居"对应方向"完全相反。

这些问题的根源只有一个:**双线性插值假设 texel 在 UV 空间里"挨着",但在球面方向上不挨着**。八面体 UV 平面的边界两侧,球面方向要么是"翻折"的(对应赤道对面),要么是"对极"的(北极南极)。这些都需要特殊处理。

Casey 这一天不发明新算法——他要解决一个"工程上的脏活":让八面体图集的采样在边界处也连续可微。

心理锚点:看完这集,你能用 Rust 写一个"边界感知"的双线性采样函数,知道每条边界对应的球面映射,能解释"为什么不能简单地把 UV wrap 起来"。如果不懂,墙角闪烁就会跟着你的游戏一辈子。

## 2 · 心智模型

### 类比:卷起来的报纸

想象一张报纸,左右两条边"卷起来"接在一起,变成一个圆柱。报纸平铺时,左边的字和右边的字相距整张报纸;卷起来后,左右两条边相邻,字直接挨着。

双线性插值在平铺报纸上工作得很好:`u = 0.99` 和 `u = 1.0` 之间插值,左边采到 0.99 位置的 texel,右边采到 1.0 位置的 texel,中间加权平均。但卷起来后,`u = 0.0` 和 `u = 1.0` 应该是**同一个 texel**(或者说,贴图 wrap 模式)——如果直接 wrap,`u = 0.99` 和 `u = 1.0` 之间插值,采到 texel[0.99] 和 texel[0.0],这是对的。

八面体 UV 平面比这复杂:它的边界**不是简单的 wrap**,而是"翻折"。也就是说,UV 平面右边超出 `u = 1` 时,对应的不是左边 `u = 0`,而是"翻折"到平面内某个特定位置——具体位置取决于你穿过的"哪条边 + 哪个角"。

### 严谨原理:边界拓扑

八面体 UV 平面是 `[-1, 1] × [-1, 1]` 的正方形。这个正方形的 4 条边 + 4 个角对应球面上的:

- **4 条边**:正方形上 `u = 1`(右)、`u = -1`(左)、`v = 1`(上)、`v = -1`(下)四条边。这 4 条边**共同对应球面上的赤道**(`z = 0` 的那个大圆)。这是因为八面体展开时,赤道被"剪开"贴到了正方形 4 条边上——一条赤道被分成 4 段。
- **4 个角**:正方形 4 个角对应球面的 4 个"对极"方向:`(1, 0, 0) → (-1, 0, 0)`,等等。

**翻折规则**:如果 UV 坐标超过 `u = 1`(即 `u > 1`),相当于我们穿过了右边界。在球面上,这是"跨过赤道到对面的方向"。这个对面方向对应的 UV 不在 `u = -1`(左边界),而是在**翻折后的位置**:

- `u = 1 + δ`(穿右边界)→ 翻折后 `u = 1 - δ`,但 `v` 改成 `-v`(因为赤道对面是反射的)

这是从 Day 576 八面体编码推导出的几何对应。具体公式:

```rust
// 给定一个 UV 坐标可能超出 [-1, 1],把它"修正"回界内
fn wrap_uv(u: f32, v: f32) -> (f32, f32) {
    // 假设 u, v 都在 [-1-ε, 1+ε] 范围(超出不多)
    let mut u = u;
    let mut v = v;
    if u > 1.0 { u = 2.0 - u; v = -v; }  // 翻右边界
    if u < -1.0 { u = -2.0 - u; v = -v; }  // 翻左边界
    if v > 1.0 { v = 2.0 - v; u = -u; }  // 翻上边界
    if v < -1.0 { v = -2.0 - v; u = -u; }  // 翻下边界
    (u, v)
}
```

**每行解释**:
- `u > 1.0 { u = 2.0 - u; v = -v; }` — 翻右边界。`2 - u` 把 `u = 1 + δ` 映射到 `u = 1 - δ`(反射)。`v = -v` 因为穿右边界后,球面方向在赤道对面,对应 UV 平面的"上下翻"。
- 4 条边对称处理。

### 修正后的双线性采样

把 wrap 逻辑接到双线性插值里:

```rust
impl LightAtlas {
    fn sample_with_wrap(&self, dir: Vec3) -> RGB32F {
        let (mut u, mut v) = encode_octahedral(dir.normalize());
        // UV 在 [-1, 1],变换到 [0, 1]
        let fu = (u + 1.0) * 0.5;
        let fv = (v + 1.0) * 0.5;
        // texel 浮点坐标,可能略超出 [0, dim-1]
        let tx = fu * (self.dim as f32 - 1.0);
        let ty = fv * (self.dim as f32 - 1.0);

        let x0f = tx.floor();
        let y0f = ty.floor();
        let fx = tx - x0f;
        let fy = ty - y0f;

        // 4 个邻居的 texel 索引
        // 注意:x1 = x0 + 1,可能 = dim,需要 wrap
        let fetch = |xf: f32, yf: f32| -> RGB32F {
            // 把 xf, yf 转回 [-1, 1] UV
            let u_tex = (xf / (self.dim as f32 - 1.0)) * 2.0 - 1.0;
            let v_tex = (yf / (self.dim as f32 - 1.0)) * 2.0 - 1.0;
            // 应用 wrap 规则
            let (wu, wv) = wrap_uv(u_tex, v_tex);
            // 再转回 texel 索引
            let fu = (wu + 1.0) * 0.5;
            let fv = (wv + 1.0) * 0.5;
            let xi = (fu * (self.dim as f32 - 1.0)).round() as usize;
            let yi = (fv * (self.dim as f32 - 1.0)).round() as usize;
            let xi = xi.min(self.dim - 1);
            let yi = yi.min(self.dim - 1);
            self.texels[yi * self.dim + xi]
        };

        let c00 = fetch(x0f, y0f);
        let c10 = fetch(x0f + 1.0, y0f);
        let c01 = fetch(x0f, y0f + 1.0);
        let c11 = fetch(x0f + 1.0, y0f + 1.0);

        let top = c00.scale(1.0 - fx).add(c10.scale(fx));
        let bot = c01.scale(1.0 - fx).add(c11.scale(fx));
        top.scale(1.0 - fy).add(bot.scale(fy))
    }
}
```

**关键点**:
- `fetch` 闭包 — 给定"理论上"的 texel 浮点坐标,先转回 UV、wrap、再转回 texel 索引。这样不管边界怎么穿,都能找到对应的 texel。
- `round() as usize` — 用四舍五入而不是 floor,因为 wrap 后我们已经在最近的 texel 里了,不需要再插值。
- 性能损耗:每个 texel fetch 多了 4-5 次浮点运算。1000 个体素 × 256 texel × 每帧采样 = 数百万次,需要 SIMD 化(Day 587)。

### 更高效的实现:padding

上面的 wrap 每次都重算 UV,代价高。工程上的标准做法是**预先在贴图边缘加 padding**——把边界 texel 重复在贴图外围一圈,这样采样 `u = 1 + δ` 时,直接采到 padding 区域的 texel(已经在 wrap 后的"正确"位置)。


## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业里,所有"球面参数化"的方案都要处理边界。最常见的就是"贴图 wrap"——纹理坐标超出 `[0, 1]` 时怎么处理。OpenGL 的标准 wrap 模式:

- `GL_REPEAT`:重复(像地砖)。八面体贴图不能用,会采到错误方向。
- `GL_MIRRORED_REPEAT`:镜像重复。八面体边界对应球面赤道,镜像恰好是正确的"翻折"!
- `GL_CLAMP_TO_EDGE`:超出取边缘 texel。简单,但精度差。
- `GL_CLAMP_TO_BORDER`:超出用指定颜色填充。

**关键发现**:八面体边界的"翻折"恰好等价于 `GL_MIRRORED_REPEAT`!也就是说,如果你的贴图本身存的是 16×16 数据,你只要把 wrap 模式设成 mirrored,采样器自己会处理边界。

但 Casey 在 CPU 端做采样(没有硬件 wrap),所以他必须手写 wrap 逻辑。

### 3.2 · 🎨 图形学视角

球面参数化的边界问题在图形学里叫**"接缝"(seam)**问题。所有从 2D 贴图采样球面数据的场景都有接缝:CubeMap 的 12 条边、等距矩形的 1 条经线、八面体的 4 条边 + 4 个角。

接缝处理的标准方法:
- **Padding**:在贴图边缘加重复 texel(如本节 §2 提到的)
- **Hardware wrap**:用 GPU 硬件支持的 wrap 模式(GL_MIRRORED_REPEAT 等)
- **Sphere-side resampling**:不在 UV 空间插值,而是在球面方向上找最近的几个 texel,在球面空间做插值(更准但贵)

Casey 选 padding(后面加),平衡性能和精度。

### 3.4 · 🦀 Rust 生态视角

Rust 实现边界 wrap 时,有个常被忽视的细节:**整数 vs 浮点索引**。

```rust
// 错误版本(浮点舍入误差)
let xi = (fu * self.dim as f32) as usize;
// 如果 fu * dim = 16.0(恰好),as usize = 16,越界!
// 这是因为 f32 表示 0.9999999 可能舍入成 1.0

// 正确版本
let xi = (fu * self.dim as f32) as usize;
let xi = xi.min(self.dim - 1);  // clamp
```

Casey 的代码里到处都是 `.min(dim - 1)`,这是 Rust 数组索引的标准防御。漏一个就会 panic,游戏闪退。

另一个 Rust 细节:`fetch` 闭包捕获 `&self` 时,需要 `&` 借用:

```rust
let fetch = |xf: f32, yf: f32| -> RGB32F {
    // 这里访问 self.texels,自动借用 &self
    ...
};
```

如果同时有 `&mut self` 引用(因为我们要返回 `RGB32F`,不需要写),闭包内是 `&self`,不会冲突。但如果你在 sample 函数内部又改 texels,会 borrow check 报错。

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

| 语境 | 边界 | wrap 方式 |
|---|---|---|
| 地球地图(等距矩形)| 经线 0/360 | GL_REPEAT(纬度连续) |
| 地球地图(纬度)| 极点 ±90 | clamp 或特殊处理(极点退化) |
| CubeMap | 12 条边 | 手工选相邻面 |
| 八面体贴图 | 4 边 + 4 角 | GL_MIRRORED_REPEAT 或手写 wrap |
| 体积纹理(3D)| 6 个面 | 通常 clamp(很少 wrap) |

每种方案都面对"边界连续性"问题,但具体数学不同。

### CPU vs GPU 实现

- **CPU**(Casey 在 Day 578):手写 wrap 函数,每个 fetch 多算几次浮点。可读性高,慢。
- **GPU**(shader):直接用 `sampler2D` + wrap mode,硬件免费。Casey 在 Phase 5 之后的 GPU 渲染部分用这种。

工业方案都是 GPU——CPU 端做 wrap 仅用于离线工具或烘焙。

### Lv1 · 概念辨析

**题**:为什么八面体贴图边界对应的不是简单 `GL_REPEAT`(wrap 到对面),而是 `GL_MIRRORED_REPEAT`(镜像翻折)?用一句话解释几何直觉。

**参考解答**:八面体 UV 平面的边界对应球面赤道(被剪成 4 段),赤道对面是"翻折"方向,几何上等价于 UV 平面的镜像。简单 wrap(`u = 1 + δ → u = -1 + δ`)对应球面方向 `(1, 0, 0) → (-1, 0, 0)`,这是对极方向,完全错误。镜像 wrap(`u = 1 + δ → u = 1 - δ`)对应球面方向 `(1, 0, 0) → (1, 0, 0)`(同方向),但这只对赤道外延一小段有效——再走远了又会撞到下一个边。

```rust
    let mut u = u;
    let mut v = v;
    if u > 1.0 { u = 2.0 - u; v = -v; }
```

```rust
}

impl LightAtlas {
    fn sample_with_wrap(&self, dir: Vec3) -> RGB32F {
        let (u, v) = encode_octahedral(dir.normalize());
        let fu = (u + 1.0) * 0.5;
        let fv = (v + 1.0) * 0.5;
        let tx = fu * (self.dim as f32 - 1.0);
        let ty = fv * (self.dim as f32 - 1.0);
        let x0f = tx.floor();
        let y0f = ty.floor();
        let fx = tx - x0f;
        let fy = ty - y0f;

        let fetch = |xf: f32, yf: f32| -> RGB32F {
            let u_tex = (xf / (self.dim as f32 - 1.0)) * 2.0 - 1.0;
            let v_tex = (yf / (self.dim as f32 - 1.0)) * 2.0 - 1.0;
            let (wu, wv) = wrap_uv(u_tex, v_tex);
            let fu = (wu + 1.0) * 0.5;
            let fv = (wv + 1.0) * 0.5;
            let xi = ((fu * (self.dim as f32 - 1.0)).round() as isize).max(0).min(self.dim as isize - 1) as usize;
            let yi = ((fv * (self.dim as f32 - 1.0)).round() as isize).max(0).min(self.dim as isize - 1) as usize;
            self.texels[yi * self.dim + xi]
        };

        let c00 = fetch(x0f, y0f);
        let c10 = fetch(x0f + 1.0, y0f);
        let c01 = fetch(x0f, y0f + 1.0);
        let c11 = fetch(x0f + 1.0, y0f + 1.0);

        let top = c00.scale(1.0 - fx).add(c10.scale(fx));
        let bot = c01.scale(1.0 - fx).add(c11.scale(fx));
        top.scale(1.0 - fy).add(bot.scale(fy))
    }
}

fn main() {
    let mut atlas = LightAtlas::new(16);
    // 在 u = 1 边界附近放一个亮 texel
    atlas.accumulate(Vec3 { x: 0.99, y: 0.0, z: 0.0 }.normalize(), RGB32F::new(1.0, 1.0, 1.0));
    // 采样边界附近,不应 panic
    let c = atlas.sample_with_wrap(Vec3 { x: 0.999, y: 0.01, z: 0.0 }.normalize());
    println!("Boundary sample: {:?}", c);
}
```

### A.2 Voxel lighting 的工程挑战

Voxel lighting 是计算机图形学的难点,因为:

**1. 数据量大**:
- 大场景(100m × 100m × 100m)有几百万 voxel
- 每 voxel 存光照值(RGB 或 SH)
- 总数据 GB 级

**2. 实时性要求**:
- 玩家挖 / 改 voxel,光照立即变化
- 16.67 ms 帧预算(60 FPS)
- 不能阻塞玩家操作

**3. 物理准确性**:
- 直接光(sun)
- 间接光(bounce)
- 阴影(hard / soft)
- 反射(diffuse / specular)
- 折射(glass / water)

工业方案在物理准确性和实时性之间权衡。

### A.3 工业级实现的层次

**Layer 1:Brute force**
- 每 voxel × 每方向 raycast
- 准确但极慢
- 适合离线渲染(movie)

**Layer 2:Grid DDA**
- 快速 raycast(穿格子)
- 适合简单场景
- Casey 的 HH 用这层

**Layer 3:Precomputed**
- 离线算光照 cache
- 运行时查表
- 适合静态场景(Minecraft baked)

**Layer 4:Real-time approximation**
- LPV / SVOGI / Voxel Cone Tracing
- 实时但近似
- Crytek / Unreal 用

**Layer 5:Hardware ray tracing**
- RTX / RDNA2 核心
- 真实光传播
- Minecraft RTX / Teardown

每代技术对硬件要求递增。Casey 的 HH 在 Layer 2(教学优先)。

### A.4 性能 profile 的实战

Casey 在 phase-8 多次 profile:

**Profile 工具**:
- Linux:perf、Valgrind、flamegraph
- Windows:Superluminal、VTune
- 跨平台:Tracy

**典型发现**:
- Raycast 占 50%+
- Propagation 占 20%+
- Meshing 占 10%+
- 其他占 20%

**优化顺序**:
1. 最慢函数 → 算法优化
2. Cache miss → 数据布局优化
3. 锁等待 → 并发优化

每优化一个,重新 profile 找下一个。

### A.5 Casey 的 phase-8 工程决策

Casey 在 phase-8 做的关键工程决策:

**1. CPU 渲染**:简单,跨平台,教学优先
**2. Voxel grid(非 octree)**:简单,固定大小
**3. RGBE atlas(非 SH)**:内存小,够教学
**4. Precomputed + delta update**:平衡实时性和准确性

这些决策让 HH 代码可读、可教学。生产游戏可能选 GPU + SH + realtime(更复杂)。

### A.7 Voxel lighting 算法的核心循环

让我写一个简化的 voxel lighting 主循环:

```rust
fn update_lighting(world: &mut World, sun_dir: Vec3) {
    let direct = compute_direct_lighting(world, sun_dir);
    let indirect = compute_indirect_lighting(world, &direct, 3);  // 3 bounce
    let final_light = combine(&direct, &indirect);
    world.light_atlas = final_light;
}

fn compute_direct_lighting(world: &World, sun_dir: Vec3) -> LightAtlas {
    let mut atlas = LightAtlas::new(world.dims());
    for each voxel {
        if voxel.is_solid() && !is_occluded(world, voxel_pos, sun_dir) {
            let lambert = compute_normal(world, x, y, z).dot(sun_dir).max(0.0);
            atlas.set(x, y, z, sun_color * lambert);
        }
    }
    atlas
}

fn compute_indirect_lighting(world: &World, direct: &LightAtlas, bounces: usize) -> LightAtlas {
    let mut current = direct.clone();
    for _ in 0..bounces {
        let mut next = current.clone();
        for each voxel {
            let bounce = average_neighbors(&current, x, y, z) * 0.15;
            next.set(x, y, z, current.get(x, y, z) + bounce);
        }
        current = next;
    }
    current
}
```

这是 Casey phase-8 的简化核心。工业实现更复杂(SH、GPU、并行)。

### A.8 Voxel lighting 的内存估算

```
Per voxel 数据:
  - material: 1 byte
  - color: 3 byte RGB
  - light: 4 byte RGBE
  - flags: 1 byte
  Total: 9 byte

场景尺寸:
  - 32^3(教学):36 KB
  - 100^3(小场景):9 MB
  - 256^3(中场景):150 MB
  - 1024^3(大场景):9.6 GB

大场景必须 streaming(chunked)。
```

工业 voxel 游戏(Minecraft):
- 16×16×256 chunk
- 每 chunk ~36 KB
- 同时加载 100 chunk ≈ 3.6 MB
