# Day 622 · 调试资产标签哈希

> Day 618-621 搭好 tag hash 系统,今天发现一个诡异 bug:某些 tag 查询返回错误资产。Casey 一开始怀疑 hash 碰撞,排查后发现是**注册顺序 bug** + **大小写不一致**。这集是"调试方法论"教学——当 hash 系统出 bug,如何系统化定位。

## 0 · 为什么要有这一天

Day 620 加随机变体后,Casey 测试时发现一个奇怪现象:

- 生成 "wall_stone" tile,有时显示成"墙+草"的混合精灵
- 生成 "door_wood" tile,有时显示成"门+石头"
- 重启游戏后,bug 出现的位置变化

第一反应:hash 碰撞?FNV-1a 在 2^64 空间,概率上 1000 个 tag 不应该碰撞。

排查过程:

1. **加 debug log**:打印每次 hash 计算的输入和输出
2. **观察**:发现 `"Wall_Stone"`(大写 W)和 `"wall_stone"`(小写 w)都出现在代码里
3. **FNV 是字节敏感**:大写小写算出不同 hash,导致同概念的两个 tag 被认为是不同 tag
4. **注册顺序**:有些 tile 注册时用大写,有些用小写,有的两边都注册
5. **真实 bug**:`register("Wall_Stone", id1)` 和 `register("wall_stone", id2)`,两个不同 hash 都映射到"石头墙"概念

**今天的核心概念**:**字符串归一化(normalization)**——使用前必须把字符串归一化(如全小写、去空格、统一 Unicode),否则同概念的不同字符串被认为是不同 key。

**心理锚点**:看完这集,你能:
- 系统化调试 hash 系统的 bug
- 加 debug log、二分法、单元测试三件套
- 在 hash 系统设计时考虑归一化

## 2 · 心智模型

### 类比:图书馆的书名拼写

图书馆按书名索引,如果:

- "The Lord of the Rings" 和 "the lord of the rings" 是不同条目
- "Harry Potter" 和 "Harry  Potter"(双空格)是不同条目
- "Color" 和 "Colour"(美式/英式)是不同条目

读者搜不到正确书,索引形同虚设。

**解决**:**归一化**——索引前把书名统一格式(全小写、单空格、统一拼写)。

游戏 tag 完全一样:

- `"wall_stone"` / `"Wall_Stone"` / `"WALL_STONE"` 应该是同一 tag
- `"wall__stone"`(双下划线,打字错)应该是 `"wall_stone"`
- `" wall_stone "`(前后空格)应该是 `"wall_stone"`

**解决**:hash 前归一化:`fn normalized(s: &str) -> String { s.trim().to_lowercase().replace("__", "_") }`

### 严谨:Hash 系统的常见 bug

#### 2.1 字符串大小写

```rust
let h1 = fnv1a("Wall_Stone");
let h2 = fnv1a("wall_stone");
assert_ne!(h1, h2);  // 不同 hash!
```

**修复**:`fn fnv1a_normalized(s: &str) -> u64 { fnv1a(&s.to_lowercase()) }`

#### 2.2 多余空格

```rust
let h1 = fnv1a("wall_stone");
let h2 = fnv1a(" wall_stone ");  // 前后空格
assert_ne!(h1, h2);
```

**修复**:`s.trim()`

#### 2.3 双字符

```rust
let h1 = fnv1a("wall_stone");
let h2 = fnv1a("wall__stone");  // 双下划线
assert_ne!(h1, h2);
```

**修复**:正则替换:`regex::Regex::new(r"_+").unwrap().replace_all(s, "_")`

#### 2.4 Unicode normalization

```rust
let h1 = fnv1a("café");      // NFC:é 单字符
let h2 = fnv1a("café");      // NFD:e + combining accent
// 两个看起来一样,但字节不同
assert_ne!(h1, h2);
```

**修复**:`unicode-normalization` crate 转 NFC。

#### 2.5 Hash 碰撞(罕见)

如果以上都不是,可能是真碰撞。但 64 位 hash 在 < 1M 输入时几乎不可能。**先排除其他原因**。

#### 2.6 完整归一化

```rust
fn normalize_tag(s: &str) -> String {
    s.trim()
        .to_lowercase()
        .replace("__", "_")  // 简化版
        // 真实项目可能加 unicode normalization
}

fn fnv1a_tag(s: &str) -> u64 {
    fnv1a(&normalize_tag(s))
}
```

#### 2.7 调试方法论

**第一步:加 debug log**

```rust
fn fnv1a(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    eprintln!("[hash] {:?} → {:#x}", s, h);  // 加 log
    h
}
```

运行后看 log,人工找异常。

**第二步:二分法**

注释掉一半 tag 注册,看 bug 还在不。如果在,bug 在剩下一半;如果不在,bug 在注释的一半。递归到定位。

**第三步:单元测试**

```rust
#[test]
fn test_tag_normalization() {
    assert_eq!(fnv1a_tag("Wall_Stone"), fnv1a_tag("wall_stone"));
    assert_eq!(fnv1a_tag(" wall_stone "), fnv1a_tag("wall_stone"));
    assert_eq!(fnv1a_tag("wall__stone"), fnv1a_tag("wall_stone"));
}
```

每次发现新 bug,加一个 test 防止回退。

### 2.8 调试心态

调试 hash 系统的"心态":

1. **不要假设**:不要假设"hash 一定碰撞",先看数据
2. **从数据到代码**:先 log 看实际 hash 值,再回到代码
3. **加测试**:每个 bug 加 test,防回退
4. **统一规范**:用 normalize 函数 + lint 防止人为错误

**核心**:**hash 系统的 bug 几乎都是输入不一致,不是 hash 算法本身**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏 tag 系统的常见 bug:

- **大小写**:C# / Rust 大小写敏感,容易踩坑
- **空格**:编辑器自动 trim 与代码字面量不一致
- **同义词**:`"floor"` vs `"ground"` 表达同样概念
- **拼写错误**:`"srite"` 应该是 `"sprite"`

**防御性编程**:

- CI lint 检查 tag 拼写(用字典 + Levenshtein 距离)
- 编辑器自动补全 + 高亮
- 启动时 sanity check 所有 tag

### 3.2 · 🎨 图形学视角

图形 API 的"字符串归一化":

- **GLSL shader uniforms**:`glGetUniformLocation("uColor")`,大小写敏感
- **Vulkan**:`VkPipeline` 创建参数严格 match,任何字段不一致导致 validation error
- **OpenGL extension names**:`GL_ARB_*` 严格大小写

**坑**:

- **driver-specific**:某些 GPU driver 对字符串宽松(自动 lowercase),某些严格。导致跨平台 bug
- **CI 不一致**:开发机 GPU 和 CI 机 GPU 不同,bug 难复现

**经验**:所有字符串归一化在应用层做,不依赖底层 API。

### 3.3 · 🐧 Linux 系统编程视角

Linux 文件名 case sensitivity:

```bash
# ext4 / btrfs:case sensitive
ls /tmp/Test
ls /tmp/test  # 不同文件

# macOS HFS+/APFS default:case insensitive
ls /tmp/Test
ls /tmp/test  # 同一文件
```

跨平台游戏(Steam Deck 是 Linux)常踩这个坑。HH 在 Linux 开发,默认 case sensitive,严格。

#### grep 的 case insensitive

```bash
# 默认 case sensitive
grep "wall" file.txt

# case insensitive
grep -i "wall" file.txt  # 也匹配 Wall, WALL

# 等价于先 lowercase
cat file.txt | tr A-Z a-z | grep wall
```

`-i` 是 grep 内部归一化的体现。

### 3.4 · 🦀 Rust 生态视角

Rust 的字符串处理:

```rust
"Wall".to_lowercase();       // "wall"
"Wall".to_uppercase();       // "WALL"
"  wall  ".trim();           // "wall"
"wall__stone".replace("__", "_"); // "wall_stone"
```

注意:

- **`to_lowercase` 是 Unicode aware**:`"STRASSE".to_lowercase()` = `"strasse"`(德语 ß)
- **不是所有字符 1:1 转换**:`"İ".to_lowercase()` = `"i̇"`(土耳其语 İ,2 字符)
- **如果只用 ASCII**:用 `to_ascii_lowercase()`,更快

```rust
"Wall".to_ascii_lowercase();  // "wall",~2x 快
```

**Unicode normalization**:

```toml
[dependencies]
unicode-normalization = "0.1"
```

```rust
use unicode_normalization::UnicodeNormalization;

let normalized: String = "café".nfc().collect();
```

Casey 用 ASCII tag(`to_ascii_lowercase`),足够。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 hash 系统的 bug 几乎总是输入不一致,而不是 hash 算法?给出三个理由。

**参考解答**:

1. **hash 算法经过验证**:FNV / xxHash 等经过 20+ 年工业使用,实现正确性高
2. **碰撞概率极低**:64 位 hash 在 < 1M 输入下碰撞概率 < 10^-10,工程上几乎不可能
3. **输入来源多样**:用户输入、文件读取、网络传输,每处都可能引入"大小写不一致 / 多余空格"等

### Lv2 · 动手实践

**题**:实现一个完整的 normalized hash 系统,要求:
- `fnv1a_normalized(s: &str) -> u64`:trim + lowercase + replace 双下划线
- `register(tag: &str, id)` 和 `get(tag: &str)` 内部都用 normalized
- 测试:`register("Wall_Stone", 1)` 和 `get("wall_stone")` 应该返回 1

完成标准:`cargo test` 通过,验证大小写、空格、双下划线都正确归一化。

**参考解答**:

```rust
use std::collections::HashMap;

const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

fn fnv1a_raw(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    h
}

fn normalize(s: &str) -> String {
    let trimmed = s.trim();
    let lower = trimmed.to_ascii_lowercase();
    // 简化:只处理双下划线
    let mut result = String::with_capacity(lower.len());
    let mut prev_under = false;
    for c in lower.chars() {
        if c == '_' {
            if !prev_under {
                result.push(c);
            }
            prev_under = true;
        } else {
            result.push(c);
            prev_under = false;
        }
    }
    result
}

fn fnv1a_normalized(s: &str) -> u64 {
    fnv1a_raw(&normalize(s))
}

struct AssetStore {
    by_hash: HashMap<u64, u32>,
}

impl AssetStore {
    fn new() -> Self { Self { by_hash: HashMap::new() } }
    fn register(&mut self, tag: &str, id: u32) {
        let h = fnv1a_normalized(tag);
        self.by_hash.insert(h, id);
    }
    fn get(&self, tag: &str) -> Option<u32> {
        let h = fnv1a_normalized(tag);
        self.by_hash.get(&h).copied()
    }
}

fn main() {
    let mut store = AssetStore::new();
    store.register("Wall_Stone", 1);
    store.register("Door_Wood", 2);

    // 大小写归一化
    assert_eq!(store.get("wall_stone"), Some(1));
    assert_eq!(store.get("WALL_STONE"), Some(1));
    assert_eq!(store.get(" Wall_Stone "), Some(1));  // 前后空格
    assert_eq!(store.get("Wall__Stone"), Some(1));   // 双下划线

    // 不存在的
    assert_eq!(store.get("missing"), None);

    println!("All normalization tests passed!");
}
```

## 8 · Rust / Arch 落地代码

### 完整可跑的归一化 hash + 调试

```rust
// Cargo.toml: 空

use std::collections::HashMap;
use std::time::Instant;

const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

#[inline]
fn fnv1a_raw(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    h
}

fn normalize(s: &str) -> String {
    let trimmed = s.trim();
    let lower = trimmed.to_ascii_lowercase();
    let mut result = String::with_capacity(lower.len());
    let mut prev_under = false;
    for c in lower.chars() {
        if c == '_' {
            if !prev_under { result.push(c); }
            prev_under = true;
        } else {
            result.push(c);
            prev_under = false;
        }
    }
    result
}

#[inline]
fn fnv1a_normalized(s: &str) -> u64 {
    fnv1a_raw(&normalize(s))
}

struct AssetStore {
    by_hash: HashMap<u64, u32>,
    debug: bool,
}

impl AssetStore {
    fn new() -> Self { Self { by_hash: HashMap::new(), debug: false } }
    fn debug_on(&mut self) { self.debug = true; }
    fn register(&mut self, tag: &str, id: u32) {
        let n = normalize(tag);
        let h = fnv1a_raw(&n);
        if self.debug {
            eprintln!("[register] {:?} → normalized {:?} → hash {:#x}", tag, n, h);
        }
        self.by_hash.insert(h, id);
    }
    fn get(&self, tag: &str) -> Option<u32> {
        let n = normalize(tag);
        let h = fnv1a_raw(&n);
        if self.debug {
            eprintln!("[get] {:?} → normalized {:?} → hash {:#x}", tag, n, h);
        }
        self.by_hash.get(&h).copied()
    }
}

fn main() {
    let mut store = AssetStore::new();
    store.debug_on();

    println!("=== Registering ===");
    store.register("Wall_Stone", 1);
    store.register("Door_Wood", 2);

    println!("\n=== Lookup ===");
    assert_eq!(store.get("wall_stone"), Some(1));
    assert_eq!(store.get("WALL_STONE"), Some(1));
    assert_eq!(store.get(" Wall_Stone "), Some(1));
    assert_eq!(store.get("Wall__Stone"), Some(1));
    assert_eq!(store.get("missing"), None);

    println!("\nAll normalization tests passed!");

    // 性能对比
    let t0 = Instant::now();
    for _ in 0..1_000_000 {
        let _ = fnv1a_raw("wall_stone");
    }
    let dt_raw = t0.elapsed();

    let t1 = Instant::now();
    for _ in 0..1_000_000 {
        let _ = fnv1a_normalized("wall_stone");
    }
    let dt_norm = t1.elapsed();

    println!("\nRaw FNV: {:?} ({:.2} ns/op)", dt_raw, dt_raw.as_nanos() as f64 / 1_000_000.0);
    println!("Normalized FNV: {:?} ({:.2} ns/op)", dt_norm, dt_norm.as_nanos() as f64 / 1_000_000.0);
    println!("Overhead: {:.2}x", dt_norm.as_nanos() as f64 / dt_raw.as_nanos() as f64);
}
```

5. **修正假设**:不是碰撞,是归一化缺失
6. **修复 + 测试**:加 normalize + 单元测试

### 调试的三种境界

**第一层:printf 调试**

加 `eprintln!`,跑,看输出。简单粗暴,但有效。Casey 在 Day 622 起步用这个。

```rust
eprintln!("[hash] {:?} → {:#x}", s, h);
```

**第二层:断点调试(gdb / lldb)**

设置断点,逐步执行,看变量值。

```bash
gdb ./target/release/handmade_hero
(gdb) break fnv1a
(gdb) run
(gdb) print s
(gdb) print h
(gdb) continue
```

适合"复杂状态"调试,但游戏 60 FPS 跑很慢。

**第三层:instrumented 调试**

加专用 instrumentation:

- **tracing** crate:分布式追踪,每函数 enter/exit 记录
- **DTrace / eBPF**:内核级追踪,无侵入
- **perf record**:硬件计数器,看 cache / branch miss

这是工业级调试,Casey 在 Day 622 没用到,但 Phase 4+ 大量用。

### Bug 的分类

不同 bug 用不同调试方法:

| Bug 类型 | 工具 |
|---|---|
| 字符串 / 逻辑错误(本日) | printf + 单元测试 |
| 内存错误(段错误) | gdb + valgrind |
| 性能问题 | perf + flamegraph |
| 并发 bug | ThreadSanitizer + helgrind |
| GPU bug | RenderDoc + Spector |
| 网络问题 | wireshark + tcpdump |

每种 bug 都有专门的工具,没有"万能调试器"。**好工程师知道用什么工具调什么 bug**。

### "5 Whys" 调试法

Toyoda(丰田)发明的"5 Whys"方法:

```
Bug:wall 显示成草
Why 1:wall_stone 的 hash 查找返回了 grass 资产
Why 2:wall_stone 的 hash 和 wall_grass 的 hash 相同?不对,不一样
Why 3:wall_stone 的 hash 查到 grass 资产 ID
Why 4:grass 资产注册时用了 wall_stone 这个 tag
Why 5:代码里 "Wall_Stone" 大写,注册时和查找时归一化不一致
```

5 个 why 之后,根因清晰:**归一化缺失**。修复方法:加 normalize 函数。

**核心原则**:**不要停在"为什么 1"**,继续问"为什么",直到找到根因。

### 防御性编程

调试之外的"防御":

1. **类型系统**:用 newtype(`SpriteTag(&'static str)`)避免裸字符串
2. **const 常量**:用 `const TAG_WALL_STONE: SpriteTag = SpriteTag("wall_stone")`,避免拼写错
3. **lint**:CI 检查所有 tag 字面量是否在 approved list
4. **编译期**:用 const fn 在编译期算 hash,拼写错编译失败

```rust
// 编译期 hash
const fn fnv1a_const(s: &str) -> u64 { ... }
const WALL_STONE_HASH: u64 = fnv1a_const("wall_stone");
```

如果 `"wall_stone"` 拼成 `"wll_stone"`,虽然编译能过,但运行时 hash 不一致 —— 这时候**编译期常量比较**能发现:

```rust
// 在 build.rs 或 const 上下文里 assert
const _: () = assert!(WALL_STONE_HASH == fnv1a_const("wall_stone"));
```

如果两个常量不一致,编译失败。这是 Rust 的"防御性 const 编程"。

## 附录 II · Casey 的"功能 vs Bug"原则

Day 622 调试后,Casey 提出"功能 vs Bug"原则,会在 Day 623-625 详细讨论。预告:

**任何"看起来不对"的现象,先判断是 feature 还是 bug**:

1. **能用理论解释 → feature**:理论推导说应该这样,那就是 feature
2. **理论上不应这样 → bug**:违反物理 / 逻辑,是 bug
3. **理论模糊 → 实验**:量化测量,看是否符合预期

Day 622 的"wall 显示成草"是**bug**(归一化缺失),不是 feature。Day 623 会讨论一个"看起来像 bug 但其实是 feature"的光照现象。

### 防御性归一化的副作用

Day 622 加了 normalize 函数,但**过度归一化也有 bug**:

- 强制 lowercase 可能让 `"Nike"` 和 `"nike"` 同一,但品牌名 "Nike" 应该保留大写
- 强制 trim 可能让 `" Donald "` 和 `"Donald"` 同一,但用户名前后空格可能 intentional

**原则**:**归一化的范围要明确**——只对"用作 key 的部分"归一化,显示用的字符串保留原样。

```rust
struct Tag(String);  // 原样保留
impl Tag {
    fn hash_key(&self) -> u64 {
        fnv1a(&normalize(&self.0))  // 归一化算 hash
    }
    fn display(&self) -> &str {
        &self.0  // 显示原样
    }
}
```

这样 hash 系统归一化,UI 显示原始大小写。两全其美。

## 附录 III · Hash 系统的工业级防错

工业级 hash 系统有几个高级防错技巧:

### 1. Perfect Hashing(完美哈希)

对**静态 key 集合**(所有 tag 编译期已知),用 gperf 等工具生成"完美哈希"——零碰撞、O(1) 查找、无 hash table 内存开销。

```
$ gperf tags.txt > perfect_hash.rs
```

适用于 tag 集合不变的引擎(如编译器关键字、HTTP status code)。

### 2. Two-tier hash

主 hash + 验证:

```rust
fn lookup(tag: &str) -> Option<AssetId> {
    let h = fnv1a(tag);
    let id = self.by_hash.get(&h)?;
    // 验证:从 id 反查原始 tag,确认一致
    if self.tags_by_id[id] != tag {
        return None;  // 碰撞,虽然 hash 一样但 tag 不同
    }
    Some(*id)
}
```

应对 hash 碰撞,100% 正确,代价是多一次字符串比较。

### 3. Hash prefix

用 hash 的低 16 位作"快速区分":

```rust
fn quick_compare(tag1: &str, tag2: &str) -> bool {
    let h1 = fnv1a(tag1) as u16;
    let h2 = fnv1a(tag2) as u16;
    h1 == h2  // 99.998% 准确,碰撞概率 1/65536
}
```

适合"不需要 100% 准确"的场景(如 cache key)。

### 4. Salted hash

加随机 salt 防 HashDoS:

```rust
thread_local! {
    static SALT: u64 = random();
}

fn salted_hash(s: &str) -> u64 {
    let salt = SALT.with(|s| *s);
    let mut h = salt;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    h
}
```

Rust 默认 hasher 用 SipHash + 随机 salt,就是这个思路。

### 5. Auditing

每次启动,扫描所有 tag,报告:

- 重复 tag(同一 hash 多个注册)
- 大小写不一致(`"Wall"` 和 `"wall"` 共存)
- 拼写可疑(Levenshtein 距离 < 3 的 tag 对)

```rust
fn audit_tags(store: &AssetStore) {
    let tags: Vec<&str> = store.all_tags();
    for i in 0..tags.len() {
        for j in i+1..tags.len() {
            let d = levenshtein(tags[i], tags[j]);
            if d > 0 && d < 3 {
                eprintln!("Suspicious tag pair: {:?} vs {:?} (distance {})", tags[i], tags[j], d);
            }
        }
    }
}
```

启动时跑一次,提前发现潜在 bug。

### 工业实践总结

| 防错技巧 | 何时用 |
|---|---|
| Normalize | 永远(本日) |
| Perfect hash | 静态 key 集合 |
| Two-tier hash | 严格要求无碰撞 |
| Hash prefix | 快速但不严格 |
| Salted hash | 不可信输入 |
| Auditing | CI 检查 |
