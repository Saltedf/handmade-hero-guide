# Day 648 · 重建光表

> Day 646 把光照切到 2D,但旧的 3D 光表还在硬盘上(占几 GB)。今天 Casey **重建光表**——生成全新的 2D 光表,完全删除 3D 残留。这是一个"清理"日,代表着重构的最后一步:**删旧数据,用新数据**。

## 0 · 为什么要有这一天

光表(light table)是 precomputed lighting(预计算光照)的存储结构。游戏启动时从硬盘加载,运行时直接查询——避免每帧重算光照。

光表的内容大致是:

- 每个 voxel 表面的最终光照(在所有光源、阴影、衰减后)
- 表面法线 / 方向(给 specular 用)
- 间接光 / 全局光照的近似

3D 光表每个 voxel 存,2D 光表每个 surface voxel 存。差别巨大:

- 3D:100 万 voxel × 16 字节 = 16 MB(压缩后)
- 2D:1 万 surface voxel × 16 字节 = 160 KB

**重建光表 = 重新跑光照模拟,生成 2D 版本**。Casey 用了 Day 576+ 的算法,但去掉 z 维度。

今天的工作是"工程清理"——加新代码、删旧代码、跑测试。

心理锚点:看完今天,你能:

- 设计光表的二进制格式
- 实现批量光照重算
- 验证新旧光表数据一致性(或预期差异)

## 1 · Casey 今天做了什么

1. 写一个 `build_light_table` 程序,扫所有 surface voxel,跑光照模拟
2. 输出新光表文件(2D 格式)
3. 修改游戏加载代码,读 2D 光表
4. 删除旧 3D 光表加载代码
5. 删除旧 3D 光表文件(回收磁盘)
6. 跑游戏,看光照效果,与旧版本对比(应该相似但不完全相同)
7. 调差异:某些场景 2D 光照"看起来扁",这是预期的(没有 z 方向变化)

## 2 · 心智模型

### 类比:换地图投影

地球仪是 3D 球体,世界地图是 2D 投影。从球体换到地图,**信息丢失**(南极看起来比实际大),但**方便使用**(可以挂在墙上)。

3D → 2D 光表类似——丢掉垂直方向信息,但光表小 100 倍。

### 光表的二进制格式

Casey 设计的简化格式:

```
[Header]
magic: "HH2DLIT" (7 bytes)
version: u16
world_size: (u32, u32)  // x, z in voxels
surface_count: u32

[Surface entries] (surface_count 次)
voxel_x: i32
voxel_z: i32
facing: u8    // 0=right, 1=left, 2=up, 3=down, 4=front, 5=back
color: [u8; 3]
direction_u8: u8  // 2D 方向,0-255 编码 0-2π
indirect: [u8; 3] // 间接光
```

每个 surface entry 16 字节。100 万 surface = 16 MB,可接受。

`facing` 6 个值代表 voxel 6 个面(类似 Minecraft 方向)。每个面有自己的光照。

### Surface voxel 识别

不是所有 voxel 都是 surface。**surface = 紧邻 air voxel 的 solid voxel 的那个面**。例:

- voxel (0,0,0) solid,(1,0,0) air:voxel (0,0,0) 的 +x 面是 surface
- voxel (0,0,0) solid,(-1,0,0) solid:无 surface(完全埋在墙里)

```rust
fn find_surfaces(world: &World) -> Vec<SurfaceEntry> {
    let mut surfaces = Vec::new();
    for each voxel v in world {
        if !world.is_solid(v) { continue; }
        for dir in 6_directions {
            let neighbor = v + dir.offset();
            if world.is_air(neighbor) {
                surfaces.push(SurfaceEntry {
                    voxel: v,
                    facing: dir,
                });
            }
        }
    }
    surfaces
}
```

HH 世界 1000×1000×100,大概 1% voxel 是 surface,即 100 万 surface entry。

### 光照模拟

对每个 surface entry,跑光照模拟:

```rust
fn compute_lighting(surface: &SurfaceEntry, lights: &[Light]) -> LightInfo {
    let mut total = [0.0; 3]; // RGB
    let mut direction = Vec2::ZERO;
    for light in lights {
        let lpos_2d = light.pos.xz();
        let spos_2d = surface.voxel.xz();
        let dir = lpos_2d - spos_2d;
        let dist = dir.length();
        if dist < 1e-6 { continue; }
        // 2D raycast 看是否被挡
        if raycast_blocked(spos_2d, lpos_2d) { continue; }
        let atten = light.intensity / (1.0 + dist * dist);
        let n_dot_l = surface.normal_2d().dot(dir / dist).max(0.0);
        let contribution = n_dot_l * atten;
        total[0] += light.color[0] * contribution;
        total[1] += light.color[1] * contribution;
        total[2] += light.color[2] * contribution;
        direction += dir / dist * contribution; // 加权平均方向
    }
    LightInfo {
        color: total,
        direction: direction.normalize_or_zero(),
    }
}
```

每个 surface 跑 N 光源 = N 次 raycast。100 万 surface × 10 光源 = 1000 万 raycast。每次 raycast ~100 步,共 10 亿次操作。Casey 在 SSD 上跑 ~30 秒完成光表生成。

### 增量重建

每次改关卡都要全量重算?太慢。增量重建:**只重算"可能受影响"的 surface**:

- 改一个 voxel:只重算邻居 6×6×6 范围的 surface
- 移动一个光源:只重算光源影响半径内的 surface

但增量重建复杂(要追踪依赖),Casey 暂时全量重算,够快。

### 二进制 vs JSON

二进制格式优势:

- 小 5-10 倍(JSON 多花括号、引号、空格)
- 加载快(直接 memcpy,不解析)

JSON 优势:

- 人可读,debug 方便
- 可版本化(git diff 看)

Casey 选二进制——光表是构建产物,不是源文件,人不需要读。

### 序列化用 Rust 的 serde

```rust
#[derive(Serialize, Deserialize)]
struct LightTableHeader {
    magic: [u8; 7],
    version: u16,
    world_size: (u32, u32),
    surface_count: u32,
}

#[derive(Serialize, Deserialize)]
struct SurfaceEntry {
    voxel_x: i32,
    voxel_z: i32,
    facing: u8,
    color: [u8; 3],
    direction: u8,
}

fn save(path: &str, header: &LightTableHeader, surfaces: &[SurfaceEntry]) -> io::Result<()> {
    let mut file = File::create(path)?;
    // bincode: 序列化成二进制
    bincode::serialize_into(&mut file, header)?;
    for s in surfaces {
        bincode::serialize_into(&mut file, s)?;
    }
    Ok(())
}
```

`bincode` 是 Rust 高效二进制序列化 crate,格式紧凑,反序列化快。

## 3 · 四域深入

### 3.1 · 游戏编程视角

预计算光照的工业实践:

- **Quake / Half-life lightmap**:每个表面纹素(texel)存预计算光照
- **Source 引擎**:cube map blurred lightprobe,放在关卡各点
- **Unity / Unreal baked lighting**:GI 系统预计算,运行时采样

光表大小是关键 trade-off:

- 大光表:高精度,加载慢,内存大
- 小光表:低精度,加载快,内存小

游戏通常分 chunk streaming——玩家靠近某 chunk 才加载其光表。

### 3.2 · 图形学视角

光表 vs 实时光照:

| 方案 | 适合 | 性能 | 质量 |
|---|---|---|---|
| 全实时 | 动态场景 | 慢 | 中 |
| 预计算光表 | 静态场景 | 极快 | 高(直接光照)|
| 预计算 + 实时混合 | 半动态 | 中 | 高 |
| Light Probe + GI | 复杂 | 中 | 极高 |

HH 是静态关卡 + 动态光源的混合,但 Casey 选简化版:光源位置预计算,只动态改 intensity。

### 3.3 · Linux 系统编程视角

Linux 大文件的 streaming load:

```rust
use std::io::{BufReader, Read};

fn load_light_table(path: &str) -> io::Result<LightTable> {
    let file = File::open(path)?;
    let mut reader = BufReader::new(file);
    let mut header_bytes = [0; size_of::<LightTableHeader>()];
    reader.read_exact(&mut header_bytes)?;
    let header: LightTableHeader = bincode::deserialize(&header_bytes)?;
    // ... 读 surface entries
}
```

`BufReader` 包装 File,批量读取,避免每 read 一次 syscall。8 KB 默认 buffer,对大文件性能 10 倍提升。

### 3.4 · Rust 生态视角

Rust 序列化生态:

- `serde`:序列化框架
- `bincode`:二进制后端
- `serde_json`:JSON 后端
- `rmp-serde`:MessagePack 二进制
- `postcard`:no_std 友好的二进制

Casey 用 bincode(同步 / 紧凑 / 快)。如果要网络传输,postcard 更好(no_std + 嵌入式友好)。

## 8 · Rust / Arch 落地代码

完整光表生成 + 加载:

```rust
// Cargo.toml:
// [dependencies]
// serde = { version = "1", features = ["derive"] }
// bincode = "1"

use serde::{Serialize, Deserialize};
use std::io::{BufReader, BufWriter, Result};
use std::fs::File;
use std::collections::HashMap;

#[derive(Serialize, Deserialize, Debug, Clone)]
struct SurfaceEntry {
    vx: i32,
    vz: i32,
    facing: u8,
    color: [u8; 3],
    direction: u8,
}

#[derive(Serialize, Deserialize)]
struct Header {
    magic: [u8; 7],
    version: u16,
    world_w: u32,
    world_d: u32,
    surface_count: u32,
}

struct World {
    solid: HashMap<(i32, i32), bool>, // 简化:2D 平面
}

impl World {
    fn is_solid(&self, x: i32, z: i32) -> bool {
        *self.solid.get(&(x, z)).unwrap_or(&false)
    }
    fn find_surfaces(&self) -> Vec<(i32, i32, u8)> {
        let mut out = Vec::new();
        for &(x, z) in self.solid.keys() {
            if !self.is_solid(x + 1, z) { out.push((x, z, 0)); }
            if !self.is_solid(x - 1, z) { out.push((x, z, 1)); }
            if !self.is_solid(x, z + 1) { out.push((x, z, 2)); }
            if !self.is_solid(x, z - 1) { out.push((x, z, 3)); }
        }
        out
    }
}

fn build_light_table(world: &World) -> Vec<SurfaceEntry> {
    let surfaces = world.find_surfaces();
    surfaces.iter().map(|&(vx, vz, facing)| {
        // 简化:每个 surface 给固定光照(实际有 raycast)
        let color = match facing {
            0 | 1 => [200, 180, 160],
            _ => [160, 160, 180],
        };
        SurfaceEntry { vx, vz, facing, color, direction: 128 }
    }).collect()
}

fn save_table(path: &str, world_w: u32, world_d: u32, entries: &[SurfaceEntry]) -> Result<()> {
    let file = File::create(path)?;
    let mut w = BufWriter::new(file);
    let header = Header {
        magic: *b"HH2DLIT",
        version: 1,
        world_w,
        world_d,
        surface_count: entries.len() as u32,
    };
    bincode::serialize_into(&mut w, &header).map_err(|e| std::io::Error::new(std::io::ErrorKind::Other, e))?;
    for entry in entries {
        bincode::serialize_into(&mut w, entry).map_err(|e| std::io::Error::new(std::io::ErrorKind::Other, e))?;
    }
    Ok(())
}

fn load_table(path: &str) -> Result<(Header, Vec<SurfaceEntry>)> {
    let file = File::open(path)?;
    let mut r = BufReader::new(file);
    let header: Header = bincode::deserialize_from(&mut r).map_err(|e| std::io::Error::new(std::io::ErrorKind::Other, e))?;
    let mut entries = Vec::with_capacity(header.surface_count as usize);
    for _ in 0..header.surface_count {
        let e: SurfaceEntry = bincode::deserialize_from(&mut r).map_err(|e| std::io::Error::new(std::io::ErrorKind::Other, e))?;
        entries.push(e);
    }
    Ok((header, entries))
}

fn main() {
    // 简单 5x5 关卡:外围一圈 solid
    let mut world = World { solid: HashMap::new() };
    for i in 0..5 {
        world.solid.insert((i, 0), true);
        world.solid.insert((i, 4), true);
        world.solid.insert((0, i), true);
        world.solid.insert((4, i), true);
    }
    let entries = build_light_table(&world);
    println!("Built {} surface entries", entries.len());

    save_table("/tmp/light_table.bin", 5, 5, &entries).unwrap();
    println!("Saved to /tmp/light_table.bin");

    let (header, loaded) = load_table("/tmp/light_table.bin").unwrap();
    println!("Loaded: magic={:?}, version={}, {} entries",
        std::str::from_utf8(&header.magic), header.version, loaded.len());
    println!("First entry: {:?}", loaded.first());
}
```

## 10 · 工程反思

Day 648 传达的核心工程教训:**预计算 + 缓存是图形学的基础**。

新手以为"游戏每帧实时算光照",但工业级游戏 80% 光照是**预计算 + 缓存**(lightmap、irradiance volume、photon map、SH coefficient)。原因:光照计算贵,但场景大多静态,预计算一次反复用。

**Light table**(光照表)就是这个思路的实例。Casey 把每个 voxel 的预计算光照存到表里,运行时只查表。这等价于 Quake 1 的 lightmap——1996 年技术,至今仍在用。

**为什么 lightmap 至今仍是主流?**

1. **GPU 友好**:纹理查找是 GPU 最快操作(100 GB/s 带宽)
2. **质量高**:预计算可慢(几小时),高质量 GI
3. **运行时便宜**:每像素一次纹理 lookup
4. **灵活**:可手绘 / 烘焙 / 混合

缺点:**静态**——光源移动要重新烘焙。但工业游戏大多用 hybrid(静态 lightmap + 动态 direct light)。

**第二条教训**:**数据结构选择决定算法可行性**。

Casey 的 light table 用什么数据结构?

- **3D texture**:GPU 原生,采样快,但占显存大
- **Sparse storage**:只存非空 voxel,但访问复杂
- **Compressed**:BC7 / ASTC 压缩,小但有损
- **Multi-resolution**:近处高精度,远处低精度(mipmap)

每种 trade-off 不同。Casey 在 HH 选最简单的(uniform 3D array),够教学用。工业级要更复杂。

**第三条教训**:**预计算 = 离线工作流**。

预计算 lightmap 需要"烘焙工具"——离线计算光照,存盘,运行时加载。这等于"内容管线"。Quake 1 的 `qrad` 工具,Unity 的 Lightmass,Unreal 的 Lightmass——都是这个。

烘焙工具有自己的复杂度:

- **Clustering**:把场景离散成 patches
- **Form factor**:算几何
- **Visibility**:raycast
- **Solver**:迭代解方程
- **Storage**:存到 lightmap 纹理

每个步骤都有学术研究。Casey 在 HH 演示最简版本,工业级是数十人月工程。

**迁移到其他领域**:

"预计算 + 缓存"在多处通用:

- **数据库**:materialized view(预计算 + 缓存)
- **Web**:SSR(server-side render 预计算 HTML)
- **CDN**:edge cache(预计算 + 缓存)
- **编译器**:JIT vs AOT(预编译)
- **AI**:pre-trained model(预训练)

每个领域都有"trade 计算时间换存储"的思想。Casey 在 HH 演示的是图形版本。

## 11 · 光照预计算的工业实例

工业级光照预计算的复杂度远超 HH 演示:

**Quake 1 lightmap**(1996):

- 离线 `qrad` 工具计算每个表面 texel 的光照
- Radiosity + direct light + ambient
- 输出 16x16 / 32x32 lightmap textures
- 运行时只查 lightmap(modulate diffuse texture)
- 这套技术 1996-2005 是金标准

**Half-Life 2 lightmap**(2004):

- 同 Quake 但加 radiosity normal mapping(3 个 lightmap:diffuse / normal map / specular)
- 表面响应光照方向变化(normal map lighting)
- 2004-2012 主流

**Unreal Lightmass**(2009+):

- Photon mapping + final gather
- 高质量 GI
- UV unwrapping 自动化
- 2009-2018 UE 标准

**Unreal Lumen**(2020+):

- 实时 GI(无 baking)
- 多分辨率 voxel GI + screen-space GI + ray tracing
- ML denoiser 去噪
- UE5 标准

每个时代都有自己的"主流"。Casey 在 HH 用 1990s 风格 radiosity,教学清晰,工业级是数十人月工程。

**预计算的 trade-off**:

| 方面 | 预计算(baking) | 实时 |
|---|---|---|
| 启动时间 | 几分钟-几小时 | 即时 |
| 运行时性能 | 极快(只查 texture) | 慢(每帧算) |
| 视觉质量 | 高(仔细算) | 中-高(快速算) |
| 灵活性 | 静态(光源不能动) | 动态 |
| 内存 | 大(lightmap texture) | 小 |
| 实现复杂度 | 中(baking tool) | 高(实时算法) |

工业实践:**hybrid**——静态场景烘焙 + 动态光源实时。这是 Unity / Unreal 默认配置。

## 12 · 数据驱动的光照参数

Casey 的 light table 是数据驱动设计——每个 voxel 的光照参数从表读。工业级:

**1. ScriptableObject(Unity)/ DataAsset(Unreal)**:

- 光照参数(asset)
- Inspector 编辑
- 序列化到磁盘

**2. JSON / TOML 配置**:

- 文本格式
- 人类可读
- 版本控制友好

**3. 二进制 asset**:

- 紧凑
- 加载快
- IP 保护(玩家不易修改)

每种 trade-off 不同。Casey 在 HH 用 hard-coded,工业级是 data-driven。这是从教学到工业的关键升级。

## 13 • 光照预计算的版本管理

光表是 binary asset,版本管理复杂:

**1. Format versioning**:

```rust
#[derive(Serialize, Deserialize)]
struct LightTableHeader {
    magic: [u8; 7],
    version: u32,  // 1, 2, 3 ...
    // ...
}
```

加载时检查 version,不匹配走 migration。

**2. Migration scripts**:

```rust
fn migrate_v1_to_v2(v1: LightTableV1) -> LightTableV2 {
    LightTableV2 {
        // ...
        new_field: default_value,
    }
}
```

**3. Backward compatibility**:

老版本游戏能加载新光表吗?通常不能。但**新版本能加载老光表**(向后兼容)。这要求每个 version 留 parser。

**4. Asset regeneration**:

艺术家改关卡,光表过时。自动 re-bake:

```bash
make bake_light_table
```

CI 跑 build,asset 自动 re-bake。这是工业级 content pipeline 的标准。

## 14 • 多平台 asset

PC / Mac / 主机 / 手机,每个平台 asset 不同:

- 纹理:BC7(PC)/ ASTC(mobile)/ BC5(老 PC)

- mesh:fp64 / fp32 / fp16

每个平台要 baking。Unity / Unreal 的 asset importer 自动处理。Casey 在 HH 单平台,工业级必须多平台。

## N0 • 深度教学补充

### 核心概念重新梳理

Day 648 涉及的核心概念需要在多个层次上理解:

**第一层:直观理解**

新手第一次接触概念,需要建立直觉。例如 voxel collision 是"虚拟物体不能穿过虚拟墙"——这个直觉每个人都能从现实经验获得。

**第二层:数学理解**

把直觉形式化。collision = "两个几何体的体积有交集"。对于 AABB,这等价于"三轴投影都重叠"。

**第三层:工程理解**

数学正确不等于工程实现正确。要考虑:

- 浮点精度边界
- 性能(每帧 N 个查询)
- 内存(数据结构紧凑)
- 边角 case(无穷大、NaN、负数)

**第四层:工业理解**

工业级要再加:

- 多线程安全
- SIMD 优化
- 网络同步(多人游戏)
- 跨平台(Windows/Mac/Linux/Mobile)
- 可访问性(色盲友好)
- 反作弊

每层理解都让代码更鲁棒。资深工程师在所有层次同时思考。

### 实际工程的细节

工业代码 80% 是"边角 case 处理",20% 是"核心算法"。Casey 在 HH 演示核心,工业代码加大量边角处理。

**边角 case 类型**:

1. 空输入(空 Vec、null pointer)
2. 极端输入(NaN、无穷大、超大数)
3. 并发竞争(多线程同时访问)
4. 资源不足(内存满、磁盘满)
5. 网络异常(超时、断连、包丢失)
6. 版本不兼容(老配置 / 新代码)
7. 权限错误(只读文件、无网络)
8. 用户误操作(连点、撤销重做)

每个 case 都要单独处理。这是工业代码 50%+ 行数的原因。

### 优化思路

性能优化有顺序:

1. **算法**:O(N²) → O(N log N),最大提升
2. **数据结构**:Vec → HashMap / BTreeMap,常数提升
3. **Cache**:AoS → SoA,cache 命中提升
4. **SIMD**:4-16 元素并行,巨大常数提升
5. **GPU**:数千核并行,极致性能
6. **分布式**:多机器,无限扩展

每级提升都需要更复杂的代码。先优化低级,够用再升级。
