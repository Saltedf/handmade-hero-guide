## 2 · 心智模型

### 类比:工具箱整理

你的工具箱里堆了 50 把螺丝刀——一字、十字、内六角、星形、不同尺寸。一开始你随手扔进去,后来发现要找某把螺丝刀要翻 5 分钟。你花一个下午整理:
- 按类型分组(一字区、十字区、内六角区……)
- 同类型按尺寸排
- 每把刀贴标签
- 坏的扔掉,重复的合并

整理后,你下次找螺丝刀 30 秒搞定。整理本身没"增加工具",但提升了"工具使用效率"。重构代码完全一样。

### 严谨原理:代码异味

"代码异味"(code smell)是 Martin Fowler 在《Refactoring》一书提出的术语,指**代码中可能暗藏问题的征兆**。常见异味:

| 异味 | 表现 | 重构方法 |
|---|---|---|
| 长函数 | 函数 > 100 行 | 拆分提取子函数 |
| 重复代码 | 同样的代码出现在多处 | 提取公共函数 |
| 魔数 | 代码里直接写 16, 256, 0.5 | 提取为常量 |
| 命名不一致 | 同概念用不同名字 | 统一命名 |
| 巨大类 | struct 字段 > 20 | 拆分 |
| 深嵌套 | if/for 嵌套 > 3 层 | 提取早期返回 |
| 注释解释代码 | 注释说"这里在干嘛" | 重命名让代码自解释 |

Casey 这一天主要处理前 4 种。

### 拆分长函数:示例

之前:

```rust
fn propagate_indirect(world: &mut World) {
    for i in 0..world.voxels.len() {
        // 第一段:收集入射光(80 行)
        let mut incoming = LightAtlas::new(16);
        for j in 0..world.voxels.len() {
            if i == j { continue; }
            let dir = (world.voxels[i].pos - world.voxels[j].pos).normalize();
            // ... 复杂的遮挡、距离衰减
            let color = world.voxels[j].specular_atlas.sample(-dir);
            incoming.accumulate(dir, color);
        }
        // 第二段:卷积漫反射(30 行)
        let diffuse = specular_to_diffuse(&incoming, world.voxels[i].normal);
        // 第三段:更新 atlas(80 行)
        world.voxels[i].specular_atlas = incoming;
        world.voxels[i].diffuse_color = diffuse;
        // 第四段:清理(10 行)
    }
}
```

之后:

```rust
fn propagate_indirect(world: &mut World) {
    for i in 0..world.voxels.len() {
        let incoming = gather_incoming_light(world, i);
        let diffuse = specular_to_diffuse(&incoming, world.voxels[i].normal);
        update_voxel_lighting(&mut world.voxels[i], incoming, diffuse);
    }
}

fn gather_incoming_light(world: &World, voxel_idx: usize) -> LightAtlas {
    let mut incoming = LightAtlas::new(ATLAS_DIM);
    for j in 0..world.voxels.len() {
        if voxel_idx == j { continue; }
        let (dir, attenuation) = compute_direction_and_attenuation(world, voxel_idx, j);
        let color = world.voxels[j].specular_atlas.sample(-dir).scale(attenuation);
        incoming.accumulate(dir, color);
    }
    incoming
}

fn update_voxel_lighting(voxel: &mut Voxel, incoming: LightAtlas, diffuse: RGB32F) {
    voxel.specular_atlas = incoming;
    voxel.diffuse_color = diffuse;
}
```

**关键变化**:
- `propagate_indirect` 现在只有 5 行,可一眼读懂
- 三个子函数各自 < 30 行,职责单一
- 常量 `ATLAS_DIM` 替换魔数 16

### 提取常量

之前:

```rust
let atlas = LightAtlas::new(16);  // 16 是什么?为什么 16?
let total = atlas.dim * atlas.dim;  // 256 个 texel
```

之后:

```rust
/// 八面体光照贴图的边长(texel 数)。
/// 选择 16 是工程权衡:分辨率足够高(避免颤抖),内存足够小(3KB/体素)。
const ATLAS_DIM: usize = 16;
/// 八面体光照贴图的 texel 总数。
const ATLAS_TEXELS: usize = ATLAS_DIM * ATLAS_DIM;
/// 帧率(Hz),用于计算"更新预算"(每帧跑多少体素)。
const TARGET_FPS: u32 = 60;

let atlas = LightAtlas::new(ATLAS_DIM);
let total = ATLAS_TEXELS;
```

**好处**:
- 名字传达意图(读者知道"16"是 atlas 尺寸)
- 改值只改一处(把 16 改成 32,只改 const)
- 文档注释解释"为什么是 16"

### 3.1 · 🎮 游戏编程视角

### 3.2 · 🎨 图形学视角

图形学代码特别需要重构,因为:
- **抽象密集**:贴图、shader、光照、几何、相机……多个抽象层
- **性能敏感**:重构不仅要清晰,还要保持性能
- **跨平台**:同一概念在 CPU / GPU / 不同 API 下表达不同

重构图形代码的关键模式:
- **资源管理**:贴图、buffer 等 GPU 资源用 RAII(Rust 的 Drop trait)
- **渲染 pass 抽象**:把"开始 pass / 绑定资源 / draw / 结束 pass" 封装成 trait

### 3.4 · 🦀 Rust 生态视角

Rust 的语言特性让重构比 C++ 安全得多:

**特性 1:强类型系统**。改函数签名后,所有调用方编译错,必须更新。这避免了"忘记改某处"的 bug。

```rust
// 改前
fn update(atlas: &mut LightAtlas) { ... }

// 改后(加参数)
fn update(atlas: &mut LightAtlas, normal: Vec3) { ... }

// 所有调用方立即编译错:
// error: expected 2 arguments, found 1
//    --> src/main.rs:42
//    update(&mut atlas);
```

C++ 里这种错误编译可能通过(隐式默认参数),运行时炸。Rust 编译时强制修。

**特性 2:模块系统**。Rust 的 `pub` / `use` 控制可见性,鼓励清晰的接口边界。私有函数只能在定义模块内用,强制你想清楚"什么是公共接口"。

**特性 3:Trait**。Rust 的 trait 让你"提取共同接口"。比如多个不同的"采样器"(CubeMap、八面体、SH)都实现 `trait Sampler { fn sample(&self, dir) -> RGB32F; }`,调用方代码可以泛型化,不依赖具体类型。

```rust
trait LightSampler {
    fn sample(&self, dir: Vec3) -> RGB32F;
}

impl LightSampler for CubeMap { ... }
impl LightSampler for LightAtlas { ... }

fn render_pixel<S: LightSampler>(sampler: &S, dir: Vec3) -> RGB32F {
    sampler.sample(dir)
}
```

这是 Casey 后续 SIMD 优化、多线程并行的关键——保持接口稳定,只改实现。

**Clippy**:Rust 的 linter,自动找"代码异味"。

```bash
rustup component add clippy
cargo clippy
# 输出 warning: this function has too many lines
# 输出 warning: this variable name doesn't follow convention
```

Casey 偶尔跑 clippy,但不依赖它(他有更严格的标准)。

## 5 · 对照与变奏

### 同一重构问题在不同语境下的变体

| 语境 | 重构方法 |
|---|---|
| Rust 项目 | 用 trait + module 系统重构 |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:"重构"和"改 bug"有什么本质不同?为什么应该分开做?

**参考解答**:重构(refactoring)= 不改变外部行为,只改进内部结构。改 bug = 改变外部行为(让行为符合预期)。

分开做的原因:
1. **关注点分离**:重构时如果同时改 bug,出问题时不知道是重构引入还是 bug 修复引入
2. **可回退性**:重构是"无风险"操作(行为不变),应该可以随时回退;改 bug 是"必要"操作,不能随意回退
3. **测试设计**:重构后应该所有测试通过(行为不变);改 bug 后应该有新测试覆盖(行为变了)
4. **代码审查**:重构 PR 容易 review(只是结构变化);bug fix PR 难 review(行为变化)

工业实践中,经常规定"一次 PR 只做一件事"——要么重构,要么改 bug,要么加功能,不混合。

```rust
/// 光照更新调度器,负责 round-robin 调度所有体素的辐射场更新。
pub struct LightingScheduler {
    /// 下一个要更新的体素索引。
    next_voxel_idx: usize,
    /// 每帧更新的体素数量。
    batch_size: usize,
}

/// 配置 LightingScheduler 的常量。
pub const DEFAULT_BATCH_SIZE: usize = 16;
pub const TARGET_FPS: u32 = 60;

impl LightingScheduler {
    pub fn new(batch_size: usize) -> Self {
        Self { next_voxel_idx: 0, batch_size }
    }

    /// 跑一帧的光照更新。
    pub fn tick(&mut self, world: &mut World) {
        for _ in 0..self.batch_size {
            self.update_one_voxel(world);
        }
    }

    fn update_one_voxel(&mut self, world: &mut World) {
        let n = world.voxels.len();
        if n == 0 { return; }
        let i = self.next_voxel_idx;
        propagate_indirect_for_voxel(world, i);
        self.next_voxel_idx = (i + 1) % n;
    }
}

fn propagate_indirect_for_voxel(world: &mut World, idx: usize) {
    // 实现略
}
```

**每行解释**:
- `pub struct LightingScheduler` — 调度器独立成 struct,职责清晰。
- `///` 文档注释——让 IDE / `cargo doc` 能自动生成文档。
- `pub fn tick` — 外部 API,名字简短。
- `fn update_one_voxel` — 内部细节,私有。
- `(i + 1) % n` — round-robin 推进。

```rust
                self.update_one_voxel(world);
            }
```

### A.1 该 Day 在 phase-8 的位置

Phase 8(day576-667)是 voxel lighting 系统的工业级实现。本日是其中一天。

### A.2 Voxel lighting 的工程挑战

Voxel lighting 是计算机图形学的难点,因为:

**1. 数据量大**:
- 大场景(100m × 100m × 100m)有几百万 voxel
- 每 voxel 存光照值(RGB 或 SH)
- 总数据 GB 级

**2. 实时性要求**:
- 玩家挖 / 改 voxel,光照立即变化
- 16.67 ms 帧预算(60 FPS)
- 不能阻塞玩家操作

**3. 物理准确性**:
- 直接光(sun)
- 间接光(bounce)
- 阴影(hard / soft)
- 反射(diffuse / specular)
- 折射(glass / water)

工业方案在物理准确性和实时性之间权衡。

### A.3 工业级实现的层次

**Layer 1:Brute force**
- 每 voxel × 每方向 raycast
- 准确但极慢
- 适合离线渲染(movie)

**Layer 2:Grid DDA**
- 快速 raycast(穿格子)
- 适合简单场景
- Casey 的 HH 用这层

**Layer 3:Precomputed**
- 离线算光照 cache
- 运行时查表
- 适合静态场景(Minecraft baked)

**Layer 4:Real-time approximation**
- LPV / SVOGI / Voxel Cone Tracing
- 实时但近似
- Crytek / Unreal 用

**Layer 5:Hardware ray tracing**
- RTX / RDNA2 核心
- 真实光传播
- Minecraft RTX / Teardown

每代技术对硬件要求递增。Casey 的 HH 在 Layer 2(教学优先)。

### A.4 性能 profile 的实战

Casey 在 phase-8 多次 profile:

**Profile 工具**:
- Linux:perf、Valgrind、flamegraph
- Windows:Superluminal、VTune
- 跨平台:Tracy

**典型发现**:
- Raycast 占 50%+
- Propagation 占 20%+
- Meshing 占 10%+
- 其他占 20%

**优化顺序**:
1. 最慢函数 → 算法优化
2. Cache miss → 数据布局优化
3. 锁等待 → 并发优化

每优化一个,重新 profile 找下一个。

### A.5 Casey 的 phase-8 工程决策

Casey 在 phase-8 做的关键工程决策:

**1. CPU 渲染**:简单,跨平台,教学优先
**2. Voxel grid(非 octree)**:简单,固定大小
**3. RGBE atlas(非 SH)**:内存小,够教学
**4. Precomputed + delta update**:平衡实时性和准确性

这些决策让 HH 代码可读、可教学。生产游戏可能选 GPU + SH + realtime(更复杂)。

### A.7 Voxel lighting 算法的核心循环

让我写一个简化的 voxel lighting 主循环:

```rust
fn update_lighting(world: &mut World, sun_dir: Vec3) {
    let direct = compute_direct_lighting(world, sun_dir);
    let indirect = compute_indirect_lighting(world, &direct, 3);  // 3 bounce
    let final_light = combine(&direct, &indirect);
    world.light_atlas = final_light;
}

fn compute_direct_lighting(world: &World, sun_dir: Vec3) -> LightAtlas {
    let mut atlas = LightAtlas::new(world.dims());
    for each voxel {
        if voxel.is_solid() && !is_occluded(world, voxel_pos, sun_dir) {
            let lambert = compute_normal(world, x, y, z).dot(sun_dir).max(0.0);
            atlas.set(x, y, z, sun_color * lambert);
        }
    }
    atlas
}

fn compute_indirect_lighting(world: &World, direct: &LightAtlas, bounces: usize) -> LightAtlas {
    let mut current = direct.clone();
    for _ in 0..bounces {
        let mut next = current.clone();
        for each voxel {
            let bounce = average_neighbors(&current, x, y, z) * 0.15;
            next.set(x, y, z, current.get(x, y, z) + bounce);
        }
        current = next;
    }
    current
}
```

这是 Casey phase-8 的简化核心。工业实现更复杂(SH、GPU、并行)。

### A.8 Voxel lighting 的内存估算

```
Per voxel 数据:
  - material: 1 byte
  - color: 3 byte RGB
  - light: 4 byte RGBE
  - flags: 1 byte
  Total: 9 byte

场景尺寸:
  - 32^3(教学):36 KB
  - 100^3(小场景):9 MB
  - 256^3(中场景):150 MB
  - 1024^3(大场景):9.6 GB

大场景必须 streaming(chunked)。
```

工业 voxel 游戏(Minecraft):
- 16×16×256 chunk
- 每 chunk ~36 KB
- 同时加载 100 chunk ≈ 3.6 MB

### A.9 Voxel lighting 调试
