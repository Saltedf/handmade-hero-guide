# Day 646 · 从光照移除 Z

> 体素碰撞重构(Day 636-645)完成后,Casey 把注意力转回光照系统。今天的简化很激进:**移除光照计算里的 Z 分量**——光照从 3D 变成 2D 平面版本。为什么?因为 HH 是 2D-floorplan 视角的 3D 游戏,玩家俯视 2D 网格,3D 光照的 Z 维度信息用户**根本看不到**。

## 0 · 为什么要有这一天

回顾 HH 的视角设计:

- 玩家看到的画面是**俯视 2D 平面**(类似《塞尔达:众神》)
- 玩家不能"抬头""低头",视角固定
- 所有 gameplay 发生在一个固定的 Y 平面(地板)

这种视角下,3D 光照的 Z 分量是**冗余**的——光从正上方照下来 vs 从 30° 角照下来,玩家看到的画面差别极小(主要是 specular highlight 位置),但代码复杂度天差地别。

更关键的:**光照表的存储**。HH 用 precomputed light table(预计算光照表),3D 光照表大小是 `W × H × D × 6 face × RGB` = 100 万 voxel 时几 GB。2D 光照表是 `W × D × RGB`,小 1000 倍。

**性能与认知成本的权衡**是今天要传达的核心工程教训。看一组数字:

- **3D 光照**:光照方向是单位向量 `(x, y, z)`。要做 raycast 在 3D voxel 网格里走,DDA 算法每步要比较 3 个轴的 t_max。每个 surface 存"6 面"光照(立方体六面)。
- **2D 光照**:光照方向是单位向量 `(x, z)`。raycast 在 2D 网格里走,DDA 每步比较 2 个轴。每个 surface 存"4 边"光照。

3D 比 2D 多 50% 的计算量、多 1000 倍的内存。但对 HH 玩家来说,3D 光照的"垂直分量"信息**永远不显示在屏幕上**——玩家只能看到 xz 平面的投影。

这就是"**冗余计算**"——CPU / GPU / 内存都在算玩家看不到的东西。Casey 今天的优化,本质是"**砍冗余**"。

Casey 今天的简化:**光照计算从 3D 球面光分布,变成 2D 圆盘光分布**。

心理锚点:看完今天,你能:

- 解释为什么"减少维度"是性能优化的重要手段
- 区分"3D 物理 + 2D 视觉"的混合架构
- 实现 2D 光照表
- 算出维度降低带来的内存 / CPU / 代码复杂度的多重节省
- 判断什么场景适合降维、什么场景必须保 3D

## 1 · Casey 今天做了什么

1. 删掉光照结构体的 `z_direction` 字段
2. 把光照方向的 octahedral 编码(Day 576)从 2D octahedral 改成 1D(圆环上的角度)
3. 把光照表的 z 轴去掉,从 `Vec3` 改成 `Vec2`
4. 把 raycast 算法从 3D 改成 2D
5. 跑测试:光照在 2D 平面里仍然正确(垂直照度近似)
6. 性能测试:光照表大小减半,内存压力减小

这是一个"反向重构"——把 3D 拍扁成 2D,简化代码。

## 2 · 心智模型

### 类比:照相 vs 全息照相

普通相片是 2D——记录平面上的光强,丢掉深度信息。全息照相是 3D——记录光的相位,可以重建 3D 场景。

游戏里"3D 光照"对应全息照相,"2D 光照"对应普通相片。**如果玩家只能看 2D 画面**(HH 是俯视),那 3D 光照信息在视觉上**部分丢失**——保留 3D 计算的成本,但享受不到全部好处。

Casey 的洞察:**视觉只看 2D → 光照计算也只需 2D**。

### 2D 光照的数学

3D Lambert 漫反射:`intensity = max(0, N · L)`,N 和 L 都是 Vec3。

2D Lambert:N 和 L 是 Vec2(在水平面上):

```
N = Vec2::new(nx, ny)  // 表面法线(x, z 平面)
L = Vec2::new(lx, ly)  // 光方向(x, z 平面)
intensity = max(0, N · L) = max(0, nx*lx + ny*ly)
```

注意:HH 里"y" 是垂直方向(上下),"z" 是前后。2D 平面是 x-z 平面,不是 x-y。

### Octahedral 编码的 2D 简化

Day 576 Casey 用 octahedral encoding 把 3D 单位向量压成 2D 纹理坐标。2D 单位向量本来就在圆环上,**只需要一个角度**:

```
theta = atan2(y, x)  // [-π, π]
// 压缩到 [0, 1]
encoded = (theta / (2 * π)) + 0.5
```

1 个 float 存 2D 方向,比 octahedral 的 2 个 float 省 50%。

### 光照表的尺寸对比

假设世界 1000 × 1000 × 100 voxel,3D 光照表:

- 每个 voxel 存 RGB + 1D 方向 = 4 floats = 16 字节
- 总:1000 × 1000 × 100 × 16 = 1.6 GB

2D 光照表(只存表面 voxel):

- 每个 surface voxel 存 RGB + 1D 方向 = 16 字节
- 总:1000 × 1000 × 16 = 16 MB

节省 100 倍。

### 2D raycast 简化

3D raycast 用 DDA(数字微分分析器)在 voxel 网格上走射线:

```
3D: t_max_x, t_max_y, t_max_z 三个候选时间,取最小
2D: t_max_x, t_max_z 两个候选,简化逻辑
```

代码减半,速度提高 ~30%。

**DDA 算法的核心思想**: voxel 网格是离散的,射线穿过网格时,**每次只跨过一条格线**——要么跨过 x 方向的格线,要么跨过 z 方向的(2D),要么还跨过 y 方向的(3D)。

我们维护三个"到达下一格线的时间"——t_max_x, t_max_y, t_max_z(3D)。每步选最小的一个,把对应的坐标 += 1(或 -= 1,看方向)。

举个具体例子:从原点 (0, 0) 出发,方向 (1, 0.5)。第一步射线穿过 x=1 边界(时间 1.0),到时位置 (1, 0.5)。然后射线穿过 y=1 边界(时间 2.0),位置 (2, 1)。然后又穿 x=2(时间 2.0,与 y 同时),位置 (2, 1)。等等。

DDA 在 2D 时逻辑:每步比较 t_max_x 和 t_max_z,选小的步进。3D 多一个比较——表面上是 1.5x,但因为分支预测失败(branch predictor 对 if-else 难预测),实测 3D 比 2D 慢 ~30-50%。

更深的优化:**SIMD DDA**。GPU shader 里可以同时跑 8 条或 16 条射线(SIMD lane),每条射线独立 DDA。这是 GPU voxel 渲染的核心技术。

### "3D 物理 + 2D 视觉"架构

HH 的最终架构:

- **物理**:3D(玩家有 3D AABB / sphere,重力是 -y)
- **碰撞**:3D(voxel 是 3D,玩家可以在 y 方向跳)
- **渲染**:3D 模型 + 2D 视角(俯视相机)
- **光照**:2D(只算 xz 平面)

这是一个**实用主义的混合**——哪里需要 3D 就 3D,哪里 2D 够用就 2D。Casey 不强求"全 3D"或"全 2D",而是**哪里节省最大就改哪里**。

这种"混合维度"在游戏工业里非常常见。再举几个例子:

- **DOOM(1993)**:渲染是 2D + 高度信息("2.5D"),物理是 2D(怪物不能真正"跳"),光照是 1D(sector brightness)。
- **Diablo 2**:渲染是 2D sprite,物理是 2D,光照是 0D(常量)+ 简单动画。
- **Starcraft(1998)**:全 2D,光照不存在(每个 sprite 像素固定)。
- **Final Fantasy Tactics**:3D 地形 + 2D sprite 角色,光照在 sprite 上预烘焙。
- **Animal Crossing: New Horizons**:3D 模型 + 实时阴影 + 简化 GI(球谐环境光)。

每个游戏都在"维度阶梯"上选合适的位置——不一定是最高维度。

判断"哪里能降维"的方法论:

1. **看玩家能感知什么**:玩家看不到的信息一定可以降维
2. **看内存成本**:内存爆炸的地方优先降维
3. **看 CPU hot path**:profiler 显示热点的地方优先简化
4. **看代码复杂度**:复杂代码 bug 多,降维能简化代码

HH 的光照同时满足 1、2、3、4——玩家看不到 z 分量(条件 1)、光照表 1 GB(条件 2)、raycast 是 hot path(条件 3)、3D 光照代码 1000 行(条件 4)。四个条件都满足,降维是合理选择。

对**第一人称 3D 游戏**(CS:GO、Valorant),条件 1 不满足(玩家抬头能看到天花板光照),所以光照必须 3D。维度选择是**视角决定的**。

### 简化的代价

2D 光照的代价:

- **没有"光从上方照"的概念**:光照只在水平方向变化,垂直方向一致
- **不能正确表现天花板**:天花板 voxel 的"上表面"和"下表面"亮度相同
- **specular 不真实**:3D 半角向量在 2D 退化,specular 位置可能错

但 HH 是俯视游戏,玩家**看不到天花板**,看不到 specular 位置偏移。简化合理。

**具体表现的限制**:

1. **角色阴影**:3D 光照能给角色投出"软阴影",2D 光照只能投"hard blob"。HH 用单独的 sprite-based 阴影系统弥补(角色脚下画一个椭圆)。
2. **地砖反光**:3D 光照能让 wet floor 反光"闪烁"(specular),2D 光照只能给一个 diffuse 颜色。HH 用预烘焙的 specular map 弥补。
3. **半透明物体的光照**:3D 光照能让玻璃透光 + 染色(beer-lambert),2D 光照只能给 alpha blend。HH 用 sprite mask 实现"彩色玻璃"效果。

这些"绕过限制"的 hack 是游戏开发的核心技能——**没有完美的渲染,只有"看起来够好"的渲染**。资深游戏程序员的能力不是"会用最新技术",而是"知道当前技术能用 90% 实现,然后用 hack 补剩下 10%"。

工业实践:**Legend of Zelda: Breath of the Wild** 的渲染就是个超大 hack 集合——表面看是 PBR,实际用了大量"看似 3D 实则 2D"的技巧(球谐 ambient、cubic environment probe、distance field shadow)。但玩家完全看不出来,因为任天堂的艺术家和工程师**完美匹配了 hack 和视觉**。这是游戏工业 40 年积累的智慧。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏里"减少维度"的常见做法:

- **2.5D 游戏**(Doom、Duke Nukem 3D):渲染是 2D + 高度信息,简化 collision 和渲染
- **顶视角 RPG**(塞尔达、口袋妖怪):物理是 2D,角色控制简单
- **RTS**:单位在 2D 平面,高度只是视觉装饰
- **格斗游戏**:战斗在 2D 平面,简化判定

Casey 的"3D 物理 + 2D 视觉"是 2.5D 的反向——"3D 物理 + 2D 光照"。

具体到光照降维的工业例子:

- **Diablo 3**:固定俯视角度,光照在 sprite 上预烘焙。运行时只算 character 动态光照,环境是静态 lightmap。
- **League of Legends**:俯视 MOBA,光照全 2D。但用高度图让某些区域"看起来有深度"——这是渲染 hack。
- **Stardew Valley**:2D pixel art,光照就是 sprite alpha blend,没有任何"光照计算"。
- **Hades**:iso 视角,3D 模型 + 2D 光照 + hand-painted texture。极简光照让艺术风格突出。

每个游戏都按"我需要什么视觉"反推"我要做什么计算"。HH 跟随这个传统——视角决定光照维度。

降维的副作用要注意:**调试复杂度上升**。3D 光照代码虽然复杂,但逻辑清晰(每个 voxel 都按物理算)。2D 光照代码看起来简单,但隐藏了"哪些信息被砍掉"的决策——后来者读代码不知道为什么没 z 分量,可能误以为是 bug。**修法**:在光照系统入口加大段注释,解释"为什么 2D,以及视觉上 z 被忽略了"。

工业惯例:每个"反直觉的设计决策"都加 ADR(Architecture Decision Record)文档。光照降维应该有一份 ADR,记录决策时间、理由、影响范围、未来可能回滚的条件。这样 6 个月后回看,不会困惑。

### 3.2 · 图形学视角

光照的 2D / 3D 取舍:

- **Doom(1993)**:光照完全 2D(sectors),不存 y 方向亮度
- **Quake(1996)**:真 3D 光照,lightmap 是 3D 表面参数化
- **Source 引擎**:lightmap + precomputed 3D radiosity
- **Unity / Unreal**:实时 3D PBR,full 3D lighting

光照的 2D 简化是历史包袱——早期硬件弱,2D 是必须的。后来硬件强了,但 2D 仍用在 mobile / web 游戏。

图形学里的"降维"技巧:

- **Normal mapping**(法线贴图):把高精度 3D 法线压到 2D 纹理,第 3 维用 sqrt(1 - x² - y²) 重建。是 PC 游戏标准技术。
- **Shadow map**:3D 阴影投影成 2D 深度图,运行时只查 2D。比 shadow volume 快 10 倍。
- **Baked GI**:静态 3D 光照烘焙成 2D lightmap,运行时只采样 2D 纹理。Quake 引入,至今仍在用。
- **Irradiance volume**:3D 入射光场采样成低分辨率 3D 网格,但每格只存球谐(SH)系数(2D 表达),实际查找是 3D 网格 + 2D 数据。
- **Cube map**:3D 入射光压成 6 张 2D 纹理(cubemap),采样时按 3D 方向选 1 张。

每个技术都是"用 2D 数据表达 3D 信息"。为什么?**GPU 的纹理硬件极快**(带宽 100s GB/s),但 3D 纹理(3D texture)硬件慢得多(很多时候是模拟的)。把 3D 数据"展开"成 2D,享受 GPU 优化,是图形程序员的常用思路。

Casey 在 HH 把光照表降到 2D,与这个工业思路一致:**2D 数据 = 更快的访问 = 更好的帧率**。

更深一层:**降维不是"砍掉信息",而是"找到合适的 2D 表示来保留足够信息"**。Cube map 保留所有方向信息(6 张 2D),normal map 保留所有法线信息(sqrt 重建)。Casey 的 2D 光照**砍掉**了 z 方向——这是"砍掉信息"而不是"压缩信息",所以适用于"玩家不需要 z 方向信息"的场景(HH 俯视)。如果场景需求变化(玩家能抬头),这套就要重新设计。

### 3.3 · Linux 系统编程视角

Linux 里"减少维度":

- **flat namespace**(进程 PID):1D 命名空间,简化查找
- **kernel ring buffer**:log 在 1D 循环 buffer 里
- **systemd unit dependency**:DAG(2D),不是任意图

减少维度让代码简单、查找快,代价是表达力受限。

更深的例子:

- **fd table**:每个进程的 fd 是 1D 整数(0, 1, 2, ...),不是路径。简化了 syscall 引用——`read(3, buf, n)` 比 `read("/path/to/file", buf, n)` 快得多。代价:fd 数量上限(默认 1024)。
- **page table**:虚拟地址 → 物理地址的多级映射,本质是 1D(线性地址空间),但实现是树形(4 级 page table)。
- **inode**:文件在磁盘上是 1D 索引,不是路径树。路径解析只在 VFS 层,inode 本身不存路径。这让 fsck、journal、defrag 都容易实现。
- **CPU topology**:从 NUMA 角度看是 2D(CPU × NUMA node),但用 cpuset 表达成 1D bitmask。

每个"降维"都让某个查询变得 O(1) 或 O(log N)。Casey 的 2D 光照同理——光照表查询从 3D index 变成 2D index,理论 O(1) 不变但常数更小。

工业教训:**降维不是"懒"**,而是"针对查询模式优化"。Linux inode 不是路径树,因为 99% 的 fs 操作通过 fd(数字),不需要路径。Casey 的光照不是 3D,因为 99% 的光照查询在 xz 平面,y 方向用不到。每次降维都要问:**"我的查询模式是什么?能不能针对它优化?"**

### 3.4 · Rust 生态视角

Rust 里 Vec3 → Vec2 的优雅转换:

```rust
use glam::{Vec3, Vec2};

let v3 = Vec3::new(1.0, 2.0, 3.0);
let v2 = v3.xz(); // 取 x 和 z 分量

let dir_3d = Vec3::new(0.0, 1.0, 0.0); // up
let dir_2d = dir_3d.xz(); // (0, 0),up 没有水平分量
```

glam 提供 `.xy()`, `.xz()`, `.yz()`, `.xyz()` 等 swizzle,处理维度转换很方便。

**swizzle** 的来历:GLSL(OpenGL shader 语言)原生支持 `.xy`, `.xyz`, `.xz` 等语法,叫 swizzle(取自色彩调酒 swizzle stick)。这是 GPU shader 编程的标准。glam 把这套语法带到 Rust CPU 代码,让 CPU 和 GPU 代码风格一致——这是图形程序员写 Rust 的主要原因之一。

如果你想自己写 swizzle,可以这样:

```rust
struct Vec3 { x: f32, y: f32, z: f32 }

impl Vec3 {
    fn xy(&self) -> Vec2 { Vec2 { x: self.x, y: self.y } }
    fn xz(&self) -> Vec2 { Vec2 { x: self.x, y: self.z } }
    fn yz(&self) -> Vec2 { Vec2 { x: self.y, y: self.z } }
}
```

但 glam 用 macro 自动生成所有组合(`xyz`, `xzy`, `yxz`, ...),覆盖几十种 permutation。这样你写 `v.xzy()` 都能编译。

**类型安全 swizzle**:Rust 1.x 的 const generics 让你能写"维度 N 的向量":

```rust
struct Vec<N, T> { data: [T; N] }
```

但 glam 选择用具体类型(Vec2 / Vec3 / Vec4),因为编译器优化更好,API 更直观。这是"通用 vs 专用"的经典权衡——通用更灵活,专用更高效。图形代码里专用胜出。

最后,Rust 生态对降维的支持很好:

- `bytemuck` / `cast` crate 让 Vec3 / Vec2 之间 zero-cost cast
- `mint` crate 提供"数学类型 interop",不同库(glam, cgmath, nalgebra)的 Vec3 可以互转
- `glamour` crate 提供 GPU-friendly 类型,直接映射到 shader

这些工具让 Rust 写图形代码非常顺手。

## 5 · 对照与变奏

不同游戏的"维度取舍":

| 游戏 | 物理 | 渲染 | 光照 |
|---|---|---|---|
| Doom | 2.5D | 2.5D | 2D |
| Quake | 3D | 3D | 3D(lightmap)|
| Starcraft | 2D | 2D sprite | 0D(常量) |
| HH | 3D | 2.5D(俯视) | 2D |
| Modern FPS | 3D | 3D PBR | 3D PBR + GI |

游戏维度不是越多越好,而是越合适越好。

历史上的"维度降级"案例:

**DOOM(1993)** 在 386 上跑,3D 渲染不可能。John Carmack 用了 BSP 树 + sector 的高度信息,做出了"看起来 3D"但底层 2D 的渲染。光照也是 2D——每个 sector 一个 brightness 值,玩家"靠近"亮的 sector 就亮。这套技术让 DOOM 在 1993 年的 PC 上 35 FPS 跑。

**Quake(1996)** 才做到真 3D——多边形 + lightmap。但 Quake 仍然为了性能做了"假 3D":怪物模型是 2D sprite + 不同角度的多张图,不是真 3D mesh。这是另一种"维度混合":渲染 3D,角色 2D。

**Starcraft(1998)** 全 2D,但用"sprite + palette"做出"看起来像 3D"的效果——每个单位从 32 个方向预渲染,运行时按角度选 sprite。这是"渲染时 2D,资产制作时 3D"的混合。

**Final Fantasy 7(1997)**:3D 战斗 + 2D 探索。野外地图是 2D 背景 + 3D 角色,战斗场景是全 3D。这是"场景级别"的维度混合。

每个游戏都按"哪里能省,哪里必须保"做选择。HH 在 2025 年仍然选 2D 光照,是因为**视角固定 + 性能不是瓶颈 + 教学清晰**——Casey 想让代码可读,不追求 photorealistic 渲染。

### Lv1 · 概念辨析

**题**:为什么 HH 选 2D 光照而不是 3D?用视角和性能两点解释。

**参考解答**:视角上,HH 是俯视 2D,玩家看不到垂直方向的光照变化(z 分量),所以 3D 光照的 z 信息无用。性能上,2D 光照表是 3D 的 1/100 大小,内存压力小,raycast 也快 2 倍。两者综合,2D 是 HH 这个特定游戏的合理选择。但对 FPS 游戏(玩家能看到垂直光照变化),3D 是必须的。

### Lv3 · 迁移设计

**题**:2D 光照只能表现水平方向。设计一个**hybrid 方案**——水平方向用 2D 压缩,垂直方向只存 1 bit("from above" / "from below")。光照方向 = (Vec2 horizontal, 1 bit vertical)。

**提示**:存 `Vec2 + bool` 比 Vec3 省,但比纯 2D 多 1 bit 表达力。

**参考思路**:每个 surface 存 `(theta, vertical_bit)`,theta 是水平角度。重建时,如果 vertical_bit = 1,光来自上方(y 分量 +);如果 0,光来自下方。

这种"压缩到极致"的方案在工业里常见。例如 normal mapping:切线空间法线通常是 Vec3,但只需要 2D(tangent + bitangent),第 3 维用 `z = sqrt(1 - x² - y²)` 重建(因为 normal 永远朝外,z > 0)。这就把 Vec3 从 12 字节压到 8 字节,节省 33%。

类似地,Unreal 的 GBuffer 把 base color / normal / roughness / metallic 压到一张 RGBA 浮点纹理(16 字节 per pixel),用各种 bit-packing 技巧。这是 console 游戏优化的日常。

## 8 · Rust / Arch 落地代码

2D 光照 demo:

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::{Vec2, Vec3};

#[derive(Clone, Copy, Debug)]
struct Light2D {
    pos: Vec2,
    color: [f32; 3],
    intensity: f32,
}

#[derive(Clone, Copy, Debug)]
struct Surface2D {
    pos: Vec2,
    normal: Vec2,
    albedo: [f32; 3],
}

fn lambert_2d(light: &Light2D, surface: &Surface2D) -> [f32; 3] {
    let l = (light.pos - surface.pos).normalize_or_zero();
    let n = surface.normal;
    let n_dot_l = n.dot(l).max(0.0);
    let dist_sq = (light.pos - surface.pos).length_squared();
    let attenuation = light.intensity / (1.0 + dist_sq);
    let intensity = n_dot_l * attenuation;
    [
        surface.albedo[0] * light.color[0] * intensity,
        surface.albedo[1] * light.color[1] * intensity,
        surface.albedo[2] * light.color[2] * intensity,
    ]
}

// 2D raycast:从 from 到 to,看是否被 voxel 挡
fn raycast_2d(voxels_solid: &[bool], w: usize, h: usize, from: Vec2, to: Vec2) -> bool {
    // 用 DDA 算法
    let dir = to - from;
    let len = dir.length();
    if len < 1e-6 { return false; }
    let dir = dir / len;
    let mut t = 0.0;
    let mut x = from.x.floor() as i32;
    let mut y = from.y.floor() as i32;
    let step_x = if dir.x > 0.0 { 1 } else { -1 };
    let step_y = if dir.y > 0.0 { 1 } else { -1 };
    let t_delta_x = (1.0 / dir.x.abs()).max(1e-6);
    let t_delta_y = (1.0 / dir.y.abs()).max(1e-6);
    let mut t_max_x = if dir.x > 0.0 {
        (x as f32 + 1.0 - from.x) / dir.x
    } else {
        (x as f32 - from.x) / dir.x
    };
    let mut t_max_y = if dir.y > 0.0 {
        (y as f32 + 1.0 - from.y) / dir.y
    } else {
        (y as f32 - from.y) / dir.y
    };
    while t < len {
        if x >= 0 && (x as usize) < w && y >= 0 && (y as usize) < h {
            if voxels_solid[y as usize * w + x as usize] { return true; }
        }
        if t_max_x < t_max_y {
            t = t_max_x;
            t_max_x += t_delta_x;
            x += step_x;
        } else {
            t = t_max_y;
            t_max_y += t_delta_y;
            y += step_y;
        }
    }
    false
}

fn main() {
    let light = Light2D { pos: Vec2::new(5.0, 5.0), color: [1.0, 1.0, 0.9], intensity: 10.0 };
    let surface = Surface2D {
        pos: Vec2::new(2.0, 2.0),
        normal: Vec2::new(1.0, 1.0).normalize(),
        albedo: [0.5, 0.5, 0.5],
    };
    let color = lambert_2d(&light, &surface);
    println!("Surface lit: {:?}", color);

    // raycast
    let solid = vec![false; 100]; // 10x10 全空
    let blocked = raycast_2d(&solid, 10, 10, Vec2::new(0.0, 0.0), Vec2::new(5.0, 5.0));
    println!("Raycast from (0,0) to (5,5) in empty grid: blocked={}", blocked);
}
```

## 10 · 工程反思

Day 646 传达的核心教训:**降维是终极优化**。

性能优化的层级:

1. **算法优化**(把 O(N²) 改成 O(N log N)):10 倍提升
2. **数据结构优化**(用 SIMD-friendly layout):3-5 倍提升
3. **内存层次优化**(cache friendly):3-10 倍提升
4. **降维**(从 3D 到 2D,从 2D 到 1D):100-1000 倍提升

降维的效果最大,但**条件也最严格**——你必须证明"被砍掉的维度不影响视觉"。Casey 用 HH 的俯视视角作为论证:玩家看不到 z,所以 z 是冗余。

**适用场景**:

- 俯视 / 横版游戏:光照 / 阴影可降维
- 2D 物理(平台跳跃):物理本来就是 2D
- Mobile / Web 游戏:资源紧张时降维优先

**不适用场景**:

- VR / 第一人称 3D:玩家能转视角,任何维度都可能进入视野
- 高品质 cinematic 渲染:每个像素都要精确
- 物理仿真(流体 / 布料 / 破坏):3D 是物理本质,降维失真

**第三条教训**:**简化代码是 polish 阶段的高 ROI 工作**。Day 636-645 Casey 在做 voxel 碰撞重构,Day 646 切到光照简化——这是"项目后期典型 polish 节奏"。早期拼命加功能,后期拼命简化。"加"是创造,"减"是智慧。资深程序员的 polish 能力 = 删代码 + 简化架构的能力。

Casey 在 HH 里反复演示这套节奏:**重构 → 测试 → 简化 → 测试 → 再重构**。Day 646 的 2D 光照简化是这个节奏的一环。
