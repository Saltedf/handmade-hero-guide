### 严谨:复合 tag 系统

#### 2.1 资产结构升级

```rust
enum AssetKind {
    Sprite(SpriteData),
    Sound(SoundData),
    Particle(ParticleData),
    Collision(CollisionData),
}

struct Asset {
    id: AssetId,
    kind: AssetKind,
    tags: Vec<u64>,  // FNV hash of tag strings

```

**变化**:之前 `SpriteAsset`、`SoundAsset` 是独立 struct;现在合并为 `Asset` + `AssetKind` enum。统一管理。

#### 2.2 多 tag 注册

```rust
impl AssetStore {
    fn register(&mut self, tags: &[&str], kind: AssetKind) -> AssetId {
        let id = self.next_id;
        self.next_id += 1;
        let tag_hashes: Vec<u64> = tags.iter().map(|t| fnv1a(t)).collect();
        let asset = Asset { id, kind, tags: tag_hashes.clone() };
        self.assets.insert(id, asset);

        // 维护每个 tag → 资产列表的反向索引
        for th in &tag_hashes {
            self.by_tag.entry(*th).or_default().push(id);
        }
        id
    }
}
```

#### 2.3 复合查询

```rust
impl AssetStore {
    /// 返回所有 tags 都匹配的资产
    fn get_with_tags(&self, tags: &[&str]) -> Vec<AssetId> {
        let tag_hashes: Vec<u64> = tags.iter().map(|t| fnv1a(t)).collect();
        if tag_hashes.is_empty() { return Vec::new(); }

        // 取第一个 tag 的候选,然后过滤
        let first = tag_hashes[0];
        let candidates = self.by_tag.get(&first).cloned().unwrap_or_default();

        candidates.into_iter()
            .filter(|id| {
                let asset = &self.assets[id];
                tag_hashes.iter().all(|th| asset.tags.contains(th))
            })
            .collect()
    }
}
```

**算法**:
1. 取第一个 tag 的候选集(`by_tag[first]`)
2. 对每个候选,检查它是否包含所有其他 tag
3. 复杂度:O(K × M),K 是第一个 tag 的候选数,M 是 query tag 数。两者通常 < 10,所以实际 O(1)

#### 2.4 上下文生成

```rust
enum Area { Indoor, Outdoor, Underground }
enum Weather { Sunny, Rainy, Snowy }

struct Context {
    area: Area,
    weather: Weather,
}

fn tags_for_floor(ctx: &Context) -> Vec<&'static str> {
    let mut tags = vec!["floor"];
    match ctx.area {
        Area::Indoor => tags.push("wood"),
        Area::Outdoor => tags.push("grass"),
        Area::Underground => tags.push("stone"),
    }
    if ctx.weather == Weather::Snowy && ctx.area == Area::Outdoor {
        tags.push("snowy");
    }
    tags
}

fn gen_tile(assets: &AssetStore, rng: &mut Lcg, ctx: &Context, x: i32, y: i32) -> Tile {
    let tags = tags_for_floor(ctx);
    let candidates = assets.get_with_tags(&tags);
    let asset_id = if candidates.is_empty() {
        // fallback:任意 floor
        assets.get_random_with_tag("floor", rng)
    } else {
        candidates[rng.gen_range(candidates.len())]
    };
    Tile { x, y, asset_id }
}
```

```rust
fn main() {

            // tile.asset_id 应该是 "floor + wood" 的某个变体

            let tile = gen_tile(&assets, &mut rng, &ctx_outdoor_snowy, x, y);

        }
    }
}
```

#### 2.6 性能考虑

- `by_tag` 反向索引:O(1) 查询第一个 tag
- 后续过滤:O(K × M),K/M 通常 < 10
- 总查询时间:~100-200ns,可接受

如果有 1000+ tag,可以加 bloom filter 加速,但 HH 规模不需要。

### 3.1 · 🎮 游戏编程视角

复合 tag 在游戏里常用:

- **Vulkan render pass**:`attachments + subpasses + dependencies`,本质是 tag 系统

### 3.4 · 🦀 Rust 生态视角

Rust 表达"复合查询"有几种模式:

#### 模式 1:for 循环 + filter(本日)

```rust
candidates.into_iter().filter(|id| {
    tag_hashes.iter().all(|th| self.assets[id].tags.contains(th))
}).collect()
```

简单直接,性能足够。

#### 模式 2:bloom filter

```rust
struct AssetStore {
    blooms: HashMap<u64, BloomFilter>,  // 每个 tag 一个 bloom
}

fn get_with_tags(&self, tags: &[&str]) -> Vec<AssetId> {
    // 每个 tag 的 bloom AND 起来
    let mut result = Vec::new();
    for (id, asset) in &self.assets {
        if tags.iter().all(|t| {
            let h = fnv1a(t);
            self.blooms[&h].contains(&id.0)
        }) {
            result.push(*id);
        }
    }
    result
}
```

适合大规模(百万资产),bloom 有 false positive 但不漏。

#### 模式 3:bitset

```rust
struct AssetStore {
    tag_bitsets: HashMap<u64, BitVec>,  // 每个 tag 一个 bitset
}

fn get_with_tags(&self, tags: &[&str]) -> Vec<AssetId> {
    let mut result = self.tag_bitsets[&fnv1a(tags[0])].clone();
    for t in &tags[1..] {
        result &= &self.tag_bitsets[&fnv1a(t)];
    }
    result.ones().map(|i| AssetId(i as u32)).collect()
}
```

最快(SIMD 加速 bitset AND),但内存大(N tag × M assets bit)。

**Casey 选择**:模式 1(简单)。HH 资产规模小(~100),不需要 bloom/bitset。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么复合 tag 用 AND 而不是 OR 作为默认?给出三个理由。

**参考解答**:

1. **AND 更严格,符合直觉**:用户说"我要 wall + stone"通常是想要"石头墙"(AND),不是"墙或石头"(OR)
2. **OR 容易表达**:用户想 OR 可以分多次查 + 合并,AND 一次性查
3. **AND 查询结果少,性能好**:AND 是 narrowing,结果集小;OR 是 widening,结果集大

```rust
const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

fn fnv1a(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);

        self.next_id += 1;

        self.assets.insert(id, asset);

            self.by_tag.entry(th).or_default().push(id);

            })

    let mut store = AssetStore::new();
    let _id1 = store.register(&["floor", "wood", "indoor"]);
    let _id2 = store.register(&["floor", "grass", "outdoor"]);
    let _id3 = store.register(&["floor", "stone", "underground"]);
    let _id4 = store.register(&["floor", "wood", "outdoor"]);

    // AND 查询 1: floor + wood → 2 个(id1, id4)

    assert_eq!(r2.len(), 1);
    assert_eq!(r3.len(), 0);
    println!("All assertions passed!");
```

## 8 · Rust / Arch 落地代码

### 完整可跑的复合 tag 系统

```rust
// Cargo.toml: 空

use std::collections::HashMap;

const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

#[inline]
fn fnv1a(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    h
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum AssetKind {
    Sprite(u32),  // 简化:用 u32 代表 sprite 数据句柄
    Sound(u32),
    Particle(u32),
}

#[derive(Debug)]
struct Asset {
    id: u32,
    kind: AssetKind,
    tags: Vec<u64>,
}

struct AssetStore {
    assets: HashMap<u32, Asset>,
    by_tag: HashMap<u64, Vec<u32>>,
    next_id: u32,
}

impl AssetStore {
    fn new() -> Self {
        Self { assets: HashMap::new(), by_tag: HashMap::new(), next_id: 1 }
    }
    fn register(&mut self, tags: &[&str], kind: AssetKind) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        let tag_hashes: Vec<u64> = tags.iter().map(|t| fnv1a(t)).collect();
        let asset = Asset { id, kind, tags: tag_hashes.clone() };
        self.assets.insert(id, asset);
        for th in tag_hashes {
            self.by_tag.entry(th).or_default().push(id);
        }
        id
    }
    fn get_with_tags(&self, tags: &[&str]) -> Vec<u32> {
        if tags.is_empty() { return Vec::new(); }
        let tag_hashes: Vec<u64> = tags.iter().map(|t| fnv1a(t)).collect();
        let first = tag_hashes[0];
        let candidates = self.by_tag.get(&first).cloned().unwrap_or_default();
        candidates.into_iter()
            .filter(|id| {
                let asset = &self.assets[id];
                tag_hashes.iter().all(|th| asset.tags.contains(th))
            })
            .collect()
    }
    fn get_kind(&self, id: u32) -> Option<AssetKind> {
        self.assets.get(&id).map(|a| a.kind)
    }
}

fn main() {
    let mut store = AssetStore::new();

    // 注册一组资产,每种带不同 tag 组合
    store.register(&["floor", "wood", "indoor"], AssetKind::Sprite(1));
    store.register(&["floor", "wood", "indoor"], AssetKind::Sprite(2));
    store.register(&["floor", "grass", "outdoor"], AssetKind::Sprite(3));
    store.register(&["floor", "stone", "underground"], AssetKind::Sprite(4));
    store.register(&["door", "wood", "indoor"], AssetKind::Sound(1));
    store.register(&["door", "wood", "indoor"], AssetKind::Sound(2));

    // 复合查询
    println!("floor + wood + indoor:");
    for id in store.get_with_tags(&["floor", "wood", "indoor"]) {
        println!("  id={} kind={:?}", id, store.get_kind(id).unwrap());
    }

    println!("\ndoor + wood + indoor (sounds):");
    for id in store.get_with_tags(&["door", "wood", "indoor"]) {
        println!("  id={} kind={:?}", id, store.get_kind(id).unwrap());
    }

    println!("\nfloor + outdoor:");
    for id in store.get_with_tags(&["floor", "outdoor"]) {
        println!("  id={} kind={:?}", id, store.get_kind(id).unwrap());
    }

    // 边界:空查询
    println!("\nempty query: {:?}", store.get_with_tags(&[]));

    // 边界:不存在 tag
    println!("\nnonexistent tag: {:?}", store.get_with_tags(&["spaceship"]));
}
```

## 附录 · Inverted Index 深入

Day 621 的核心数据结构是 **inverted index**(倒排索引)。这是搜索引擎的核心技术,值得深入理解。

### Inverted Index 原理

普通索引是"资产 → tag 列表"(forward index):

```
资产 1 → [floor, wood, indoor]
资产 2 → [floor, grass, outdoor]
...
```

倒排索引是"tag → 资产列表":

```
floor → [1, 2, 3, 4]
wood → [1, 5]
indoor → [1, 5]
grass → [2]
outdoor → [2]
```

**为什么叫"倒排"**:它把 forward index 的方向反过来。

### 用 Inverted Index 做 AND 查询

查询 `floor + wood`:

1. 取 `floor` 的倒排表 `[1, 2, 3, 4]`
2. 取 `wood` 的倒排表 `[1, 5]`
3. 求交集:`[1]`

**交集算法**:
- 如果倒排表是有序的:两个指针同时走,O(M + N)
- 如果用 bitset:AND 是 SIMD 加速的,O(N/64)

### Google 等搜索引擎的核心

Google 的搜索本质:

```
查询: "rust gamedev"
→ inverted index["rust"] AND inverted_index["gamedev"]
→ ~1M 个网页,按 PageRank 排序
→ 返回 top 10
```

inverted index 让"在 100 亿网页里找两个词"变成 O(M + N),几毫秒完成。

### 与 SQL 的对比

```sql
-- SQL
SELECT * FROM assets WHERE id IN (
    SELECT asset_id FROM asset_tags WHERE tag = 'floor'
)
INTERSECT
SELECT * FROM assets WHERE id IN (
    SELECT asset_id FROM asset_tags WHERE tag = 'wood'
);
```

SQL 的 INTERSECT 内部就是 inverted index 的交集。HH 的 HashMap 实现是手写版的同样思想。

### 分布式 Inverted Index

Google 等大公司的 inverted index 是**分布式**的:

- 索引分片(每个 shard 存一部分)
- 查询并行(发给所有 shard,合并结果)
- MapReduce / Spark 做批量构建

这是搜索引擎能扩展到 100 亿页的原因。HH 规模小,单机 HashMap 足够。

### Rust 生态的搜索引擎

- **`tantivy`**:Rust 的 Lucene 等价物,全文搜索引擎
- **`meilisearch`**:Rust 写的轻量搜索引擎
- **`sonic`**:Rust 写的索引服务

这些 crate 内部都是 inverted index + 复杂的查询优化(query planner、bloom filter、cache 等)。HH 的 Day 621 是它们的"教学版"。

### 今天的认知收获

完成 Day 621,你应该理解:

- **Inverted index 是搜索引擎的核心**:`tag → 资产` 的反向索引,让 AND 查询变成 O(M+N) 交集
- **复合 tag = SQL INTERSECT**:同样的思想,不同抽象层
- **设计 tag 系统的关键是节制**:30-50 个清晰独立的 tag,而不是几百个重叠的
- **Asset system 的统一性**:Sprite/Sound/Particle 用同一套 tag 系统,极大简化引擎

带着这些认知,你后面看任何"按多个属性过滤"的系统(搜索引擎、SQL、ORM),都能问出**正确的问题**:
- 有 inverted index 吗?
- 查询是 AND 还是 OR 默认?
- tag 数量是否在合理范围(30-50)?

day621 之前,你看搜索引擎觉得"魔法"。day621 之后,你能从原理上理解它们。

## 附录 II · Tag System 的工业实现对比

不同游戏引擎的 tag 系统设计:

### Unreal Engine 5

- **Asset registry tags**:`UPROPERTY meta=(AssetRegistrySearchable)` 让属性可搜索
- **Collections**:虚幻的"资产文件夹",本质是 tag 集合
- **Data table**:用 row name 作 tag

**特点**:深度集成编辑器,UI 友好,但 API 复杂。

### Unity

- **Addressables**:label 系统,资产可贴多个 label
- **Asset bundles**:按 label 打包
- **ScriptableObjects**:可自定义 tag 字段

**特点**:轻量,但需要自己搭查询系统。

### Godot

- **Groups**:Node 可加入多个 group
- **Resource classes**:用类继承代替 tag
- **Custom Resource**:自定 tag 字段

**特点**:简单,但 group 是 Node 级别,不是 Resource 级别。

### Bevy

- **AssetServer + Handle**:类型安全 Handle<T>
- **States**:用 Rust 类型系统做 tag
- **Reflect + Resource**:运行时反射

**特点**:利用 Rust 类型系统,编译期安全,但灵活性低。

### HH 的位置

Casey 的设计:

- 简单:HashMap + FNV
- 灵活:任意字符串 tag
- 编译期:`&'static str` + const
- 无依赖:不用 crate

**这是教学项目的最优选择**——学原理,不依赖。

### 何时需要升级

如果 HH 扩展到:

- 1000+ 资产 → 加 bitset 加速 AND
- 100+ tag → 加 bloom filter
- 多语言 → tag 加 locale 维度
- mod 支持 → tag 加 namespace(`"core:wall"` vs `"mymod:wall"`)

每一步升级都是工程权衡。**Day 621 的版本是"够用的最优"**——100 资产 + 30 tag + 单机,完全够用。

完成 Day 621 + 附录,你应该理解:

- **Tag system 是引擎的核心抽象之一**:决定资产如何被组织、查找、使用
- **Inverted index 是搜索引擎的基础**:从 HH 到 Google 都用同样思想
- **简单实现常常够用**:Day 621 的 HashMap 版本对 HH 完全足够,不需要 bitset/bloom
