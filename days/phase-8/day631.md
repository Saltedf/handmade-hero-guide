## 2 · 心智模型

### 类比:重新装修 vs 推倒重建

你的房子住了 10 年,有些问题:

- 电线老化(常跳闸)
- 隔音差(邻居吵)
- 布局不合理(厨房离餐厅远)

两种选择:

1. **重新装修**:换电线、加隔音、改布局。保留主体结构,工作量中等
2. **推倒重建**:全部拆掉,从地基开始。彻底解决,但工作量极大

碰撞系统完全一样:

- **重新装修**:加特殊 case 处理(门半开、斜坡),保留 Minkowski 核心。工作量小,但治标不治本
- **推倒重建**(本日决定):重写为体素化,彻底统一。工作量大,但解决根本问题

Casey 选**推倒重建**——Minkowski 已经累积太多 hack,继续 patch 不是长久之计。

### 严谨:Minkowski AABB 回顾

#### 2.1 Day 050 的算法

```rust
fn minkowski_collide(a: Aabb, b: Aabb) -> bool {
    let dx = (a.center.x - b.center.x).abs();
    let dy = (a.center.y - b.center.y).abs();
    let sum_half_w = a.half_w + b.half_w;
    let sum_half_h = a.half_h + b.half_h;
    dx < sum_half_w && dy < sum_half_h
}
```

**几何意义**:`a` 和 `b` 相交 ⟺ `a` 中心在 `b` 膨胀(`b` 加 `a` 半尺寸)的 AABB 内。

**优点**:

- O(1) 检测
- 简单
- 数值稳定(整数比较)

**缺点**:

- 只支持 AABB
- 不支持旋转
- 多对象碰撞 O(N²)

#### 2.2 Phase 8 的需求

新系统应该:

1. **支持任意几何**:斜坡、楼梯、不规则形状
2. **3D 优先**:不是 2D + 3D 扩展
3. **与 raycast 统一**:raycast 已经用 DDA,碰撞也应该
4. **空间加速**:大数据量不能 O(N²)

#### 2.3 体素化方案的提议

把所有几何**体素化**:

- 世界已经体素化(Day 588+)
- 玩家、怪物也"体素化"(简化为 1 个体素)
- 碰撞 = "玩家体素 + 移动方向 → 是否撞实体体素"

```rust
fn voxel_collide(world: &World, player_pos: Vec3, move_dir: Vec3, dt: f32) -> Vec3 {
    let new_pos = player_pos + move_dir * dt;
    let voxel = world.voxel_at(new_pos);
    if voxel.is_solid() {
        // 撞了,不移动
        player_pos
    } else {
        new_pos
    }
}
```

**优势**:

- 支持任意几何(因为已体素化)
- 3D 优先(体素是 3D)
- 与 raycast 共享基础设施(都是 voxel grid)
- 空间加速天然(O(1) 查体素)

**劣势**:

- 精度受 voxel size 限制
- 移动可能"卡"在体素边界
- 斜坡 / 楼梯体素化可能不连续

#### 2.4 Flood fill 体素化

如何把任意几何转体素?**flood fill**:

1. 找几何的边界体素(种子)
2. 标记边界为 solid
3. **flood fill** 内部为 solid
4. 外部为 empty

这是 Day 638 的核心算法。

#### 2.5 新旧系统对比

| 维度 | Minkowski AABB | 体素化 |
|---|---|---|
| 几何支持 | 仅 AABB | 任意 |
| 维度 | 2D / 3D | 3D |
| 与 raycast 统一 | 否 | 是 |
| 多对象 | O(N²) | O(1) |
| 精度 | 精确 | 体素分辨率 |
| 复杂度 | 简单 | 中等 |

#### 2.6 决策

**决策**:**重写为体素化**。理由:

1. 长期价值大(支持未来扩展)
2. 与 raycast 统一(代码精简)
3. 性能好(O(1) 查询)
4. 精度可接受(玩家 1 体素,1m 分辨率足够)

**风险**:

- 重写工作量大(Day 631-638,8 天)
- 可能有 bug(新系统未测试)
- 可能视觉不一致(移动手感不同)

**风险缓解**:

- 双系统并行(Day 632-637 同时跑新旧,Day 638 切换)
- 大量测试(每个 tile 类型测一遍)
- 玩家反馈(早期测试者体验新旧对比)

### 2.7 RFC 文档

Casey 写 RFC(Request For Comments)文档:

```markdown
# Collision Refactoring Plan

## Background
Current collision (Day 050) uses Minkowski AABB. Works for 2D AABB-only scenes,
but doesn't scale to 3D / non-AABB geometry / large entity counts.

## Goals
- Support arbitrary geometry (slopes, stairs, curves)
- 3D-first design
- Unify with voxel raycast infrastructure
- O(1) per-entity collision check

## Non-goals
- Realistic physics (joints, ragdoll)
- High precision (1m voxel resolution acceptable)

## Design
- Voxelize all geometry using flood fill (Day 638)
- Player movement = "next voxel position is solid?"
- Collision response = "cancel movement if solid"

## Migration plan
- Day 631: design (this RFC)
- Day 632-633: prototype voxel collision
- Day 634: integrate with movement system
- Day 635-637: tests + tuning
- Day 638: switch from Minkowski to voxel

## Risks
- Movement feel changes (mitigate: tune parameters)
- Edge cases at voxel boundaries (mitigate: extensive testing)
- Performance regression possible (mitigate: profile)
```

RFC 让团队 / 未来的自己理解决策。

### 3.2 · 🎨 图形学视角

碰撞算法谱:

| 算法 | 几何 | 速度 | 用途 |
|---|---|---|---|
| AABB(本日旧) | 仅 AABB | 极快 | 简单 2D |
| Sphere | 仅球 | 极快 | 简单 3D |
| OBB | 任意方向 box | 快 | 中等 |
| SAT(Separating Axis) | 凸多边形 | 中 | 通用 |
| GJK | 凸形状 | 中 | 通用 |
| BVH | 任意 + 加速结构 | 快 | 现代 |
| Voxel(本日新) | 任意(已体素化) | O(1) | HH 选 |

工业引擎(Unreal / Unity)用 BVH + SAT。HH 用 voxel,**因为已有 voxel 系统**(raycast 共享)。

### 3.3 · 🐧 Linux 系统编程视角

每次重写都引发争议(sysd 争议最大),但**长期看是进步**。

### 3.4 · 🦀 Rust 生态视角

- **Firefox → Servo → Firefox Quantum**:浏览器引擎部分重写

## 8 · Rust / Arch 落地代码

Day 631 是文档日,代码示例少。但可以准备 Day 632+ 的基础——一个简化的 voxel collision 原型:

```rust
// Cargo.toml: 空

#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn add(self, o: Self) -> Self { Self::new(self.x+o.x, self.y+o.y, self.z+o.z) }
    fn scale(self, k: f32) -> Self { Self::new(self.x*k, self.y*k, self.z*k) }
}

struct World {
    voxels: Vec<bool>,  // true = solid
    w: usize, h: usize, d: usize,
}

impl World {
    fn new(w: usize, h: usize, d: usize) -> Self {
        Self { voxels: vec![false; w*h*d], w, h, d }
    }
    fn is_solid(&self, x: i32, y: i32, z: i32) -> bool {
        if x < 0 || y < 0 || z < 0 ||
           x >= self.w as i32 || y >= self.h as i32 || z >= self.d as i32 {
            return true;  // 世界外视为 solid
        }
        self.voxels[(z as usize * self.h + y as usize) * self.w + x as usize]
    }
    fn set_solid(&mut self, x: usize, y: usize, z: usize, v: bool) {
        self.voxels[(z * self.h + y) * self.w + x] = v;
    }
}

// 旧版碰撞:Minkowski AABB(简化 2D 版)
fn minkowski_collide_2d(
    ax: f32, ay: f32, ahw: f32, ahh: f32,
    bx: f32, by: f32, bhw: f32, bhh: f32,
) -> bool {
    (ax - bx).abs() < ahw + bhw && (ay - by).abs() < ahh + bhh
}

// 新版碰撞:Voxel
fn voxel_collide(world: &World, pos: Vec3) -> bool {
    let xi = pos.x.floor() as i32;
    let yi = pos.y.floor() as i32;
    let zi = pos.z.floor() as i32;
    world.is_solid(xi, yi, zi)
}

fn move_with_voxel_collision(world: &World, pos: Vec3, dir: Vec3, dt: f32) -> Vec3 {
    let new_pos = pos.add(dir.scale(dt));
    if voxel_collide(world, new_pos) {
        pos  // 撞了,不动
    } else {
        new_pos
    }
}

fn main() {
    let mut world = World::new(10, 10, 10);
    // 围墙
    for i in 0..10 {
        world.set_solid(i, 0, 0, true);
        world.set_solid(0, i, 0, true);
    }

    let mut player = Vec3::new(5.5, 5.5, 0.5);

    // 尝试向左走
    let new_pos = move_with_voxel_collision(&world, player, Vec3::new(-1.0, 0.0, 0.0), 1.0);
    println!("After move: ({}, {}, {})", new_pos.x, new_pos.y, new_pos.z);
    // 应该正常移动到 (4.5, 5.5, 0.5)

    // 走很多步,直到撞墙
    for step in 0..10 {
        player = move_with_voxel_collision(&world, player, Vec3::new(-1.0, 0.0, 0.0), 1.0);
        println!("Step {}: pos = ({}, {}, {})", step, player.x, player.y, player.z);
        if player.x <= 1.0 {
            println!("Hit wall at x = {}", player.x);
            break;
        }
    }
}
```

## 附录 · Architecture Decision Records(ADR)深入

Day 631 写的 RFC 是 ADR 的变体。这是工业级项目管理的重要工具。

### ADR vs RFC

- **RFC**(Request for Comments):提出新功能 / 改动,征求反馈
- **ADR**(Architecture Decision Record):记录决策,通常 shorter

两者都重要,RFC 用于讨论,ADR 用于存档。

### ADR 标准结构

```markdown
# ADR-001: Switch from Minkowski to Voxel Collision

Date: 2024-XX-XX
Status: Accepted

## Context
[问题描述]

## Decision
[决策内容]

## Status
[接受 / 拒绝 / 替代]

## Consequences
[正面 + 负面后果]

## Alternatives considered
[其他方案 + 为什么没选]
```

### ADR 仓库

大型公司有专门的 ADR repo:

- **Stripe**:github.com/stripe/architecture-decision-records
- **AWS**:github.com/awslabs/aws-architecture-best-practices
- **Spring**:github.com/spring-projects/spring-framework/tree/main/architecture

每个 ADR 编号、日期、状态,便于追溯。

### ADR 的价值

1. **决策记录**:未来不知道为什么这样设计 → 看 ADR
2. **避免重复讨论**:已经决策的事不再争议
3. **新人 onboarding**:新人看 ADR 理解项目历史
4. **责任追溯**:谁、何时、为什么决策

### ADR 的反模式

#### 反模式 1:口头决策不记录

"我记得当时决定用 X"——6 个月后没人记得,争议重启。

**正确**:**重要决策必写 ADR**。

#### 反模式 2:过于详细

ADR 50 页 → 没人读。

**正确**:**1-2 页**,关键信息清楚。

#### 反模式 3:status 不更新

ADR 写"Accepted",但后来发现不可行,放弃。ADR 没更新 → 误导新人。

**正确**:**status 改为 Superseded / Deprecated**。

Decision:

Alternatives considered:

## 附录 II · 碰撞检测算法谱系

Day 631 决定用 voxel collision。完整理解碰撞算法谱系很重要。

### Broad Phase vs Narrow Phase

碰撞检测分两阶段:

- **Broad Phase**:快速找出"可能碰撞"的对(O(N log N) 或更好)
- **Narrow Phase**:精确检测每个候选对(O(1) per pair)

```
所有物体 (N=1000) → broad phase → 100 个候选对 → narrow phase → 10 个真碰撞
```

### Broad Phase 算法

#### 1. Brute Force

O(N²) 两两 check。简单但慢。

#### 2. Sweep and Prune

按某轴排序,只 check 相邻。O(N log N) + O(K) 检查,K = 候选数。

#### 3. Uniform Grid Hash

每个物体按位置 hash 到 grid cell,只 check 同 cell。O(N) 平均。

```rust
let cell = pos / cell_size;
let hash = hash_cell(cell);
grid[hash].push(entity);
// 同 cell 内两两 check
```

HH 体素化的天然就是 uniform grid,O(1) 查找。

#### 4. BVH(Bounding Volume Hierarchy)

层次包围盒树,空间加速结构。O(N log N) 构建,O(log N) 查询。

```
Root
├── BV 1
│   ├── Object A
│   └── Object B
└── BV 2
    ├── Object C
    └── Object D
```

Raycast 用 BVH 找最近命中,碰撞用 BVH 找候选对。

#### 5. Octree / KD-tree

类似 BVH,但更结构化的空间分割。

### Narrow Phase 算法

#### 1. AABB(本日旧)

轴对齐包围盒,只支持 box。O(1)。

#### 2. OBB

有向包围盒,支持旋转 box。O(1) 但稍复杂。

#### 3. SAT(Separating Axis Theorem)

凸多边形 / 多面体,找分离轴。O(M + N),M/N 是面数。

#### 4. GJK(Gilbert-Johnson-Keerthi)

凸形状的通用算法。O(N) 最坏,O(1) 平均。

#### 5. Voxel(本日新)

把所有几何体素化,check 体素是否 solid。O(1)。

### 算法选择决策树

```
你的几何是什么?
├── 仅 AABB → Minkowski / AABB
├── 仅球 → Sphere-Sphere
├── 凸多边形 → SAT / GJK
├── 任意 → 体素化 / BVH
└── 复杂(关节 / ragdoll)→ 物理引擎(Box2D, Rapier)
```

HH 的体素化路径:**任意几何 → 体素化 → O(1) 查询**。代价是精度(1m 分辨率),但游戏可接受。

### HH 的算法谱系

| 模块 | 算法 |
|---|---|
| Raycast(Day 611+) | DDA 体素网格 |
| 间接光(Day 617) | Voxel cone tracing(简化版) |
| 碰撞(本日新) | Voxel collision |
| Tile 渲染(Day 620) | Sprite tile |

**所有 3D 系统都基于 voxel grid**——这是 HH 的设计哲学。**统一的基础设施 = 更简单的代码**。

### 工业级碰撞(对比)

- **Unreal Engine**:`PhysX`(NVIDIA),BVH + SAT
- **Unity**:内置 PhysX 或 Havok
- **Godot**:自研,BVH + SAT
- **Box2D**:2D,SAP + SAT
- **HH(本日)**:Voxel,简单但够用

工业级"重型",HH"轻量"。**适合自己项目的才是最好的**。

### 今天的认知收获(终)

完成 Day 631 + 全部附录,你应该理解:

- **碰撞检测两阶段**:broad + narrow phase
- **算法谱系**:AABB / OBB / SAT / GJK / Voxel / BVH

- **适合自己项目的才是最好的**

带着这些认知,你后面设计任何碰撞系统,都能问出**正确的问题**:
- 几何是什么?

## 附录 III · "重写"的心理学

Day 631 决定重写碰撞。但"重写"在软件工程里有**坏名声**——Joel Spolsky 2000 年代写过著名文章《Things You Should Never Do》(重写是公司最大错误)。

### 重写 vs 渐进重构

**重写**(rewrite):

- 从零开始,丢老代码
- 风险极大(Netscape 5.0)
- 长期看可能收益大

**渐进重构**(incremental refactor):

- 保留老代码,逐步替换
- 低风险
- 长期看不一定能完成

**Strangler Fig 模式**(Martin Fowler):

- 新系统在老系统旁边生长
- 逐步"勒死"老系统
- 用户无感迁移

HH 用 Strangler Fig:

- Day 631-637:新系统并行运行
- Day 638:切换主路径
- 老 Minkowski 代码作为 fallback 保留几周,确认稳定后删除

### Joel Spolsky 的警告

Joel 在 2000 年代警告:重写会丢"嵌入代码的隐性知识"——老代码看起来烂,但解决了无数边角 case,重写会重新踩这些坑。

**Casey 的反驳**:

- 老代码的"隐性知识"应该提取到注释 / 文档
- 重写时**读老代码**(Day 626 的"考古学")
- 用单元测试覆盖老代码的所有 case,重写时跑同样测试

**关键**:**重写不是"不看老代码",而是"理解后重写"**。

### 何时该重写?

决策树:

```
1. 老系统是否累积大量债务?
   ├─ 否 → 不重写,patch 即可
   └─ 是 → 跳到 2

2. 老系统能否渐进重构?
   ├─ 能 → 渐进重构(Strangler Fig)
   └─ 不能(架构根本不同)→ 跳到 3

3. 新系统收益是否 > 风险?
   ├─ 是 → 重写
   └─ 否 → 接受老系统的债务
```

HH 碰撞重写:

1. Minkowski 累积了"traversable"模糊、几何限制等债务 → 是
2. 渐进重构困难(几何模型根本不同)→ 不能
3. Voxel 统一基础设施,长期收益大 → 是

**决策:重写**。

### 重写的心态

重写时要**谦卑**——老开发者可能比你想的更聪明:

- 看到老代码的"奇怪",先问"为什么这样写"
- 不要立刻"我比他聪明"
- 找原作者聊(如果可能),理解背景
- 读 git history,看演化过程

**重写不是否定原作者,而是在新需求下的演进**。

### Joel Spolsky vs Casey

Joel 视角:**重写危险,要避免**(他看 Netscape 的惨剧)。
Casey 视角:**重写有时必要**(他做单人项目,自己理解所有代码)。

**两个视角都对**,适用于不同情境:

- **大团队 / 商业产品**:Joel 对——重写风险大
- **单人项目 / 教学**:Casey 对——重写是学习机会

HH 是单人教学项目,**重写合适**。

### 重写的"机会成本"

重写 8 天(Day 631-638),这 8 天能做什么其他?

- 8 个新 tile 类型?
- 2 个新 boss?
- 网络多人模式雏形?

**重写代价**:**机会成本**——这 8 天没做的其他事。

**判断**:

- 重写收益(未来节省的开发时间)> 机会成本 → 重写
- 否则 → 不重写

HH 判断:**重写收益(后续所有功能都更快加)> 机会成本**。

完成 Day 631 + 全部附录,你应该理解:

- **重写是工程决策,不是技术决策**
- **Strangler Fig 模式**:渐进重写,降低风险
- **Joel Spolsky 警告**:重写风险大,但有时必要
- **决策树**:何时重写,何时 patch
- **谦卑心态**:理解老代码再重写

带着这些认知,你后面做任何"老系统要不要重写"的决策,都能问出**正确的问题**:
- 债务多大?

- 收益 > 风险?
- 机会成本?
- 我理解老代码吗?
