
# Day 629 · 移除实体生成器

> Day 628 引入 Brain + Apron,Monster 系统重写。今天 Casey 处理"前任"——Phase 4 引入的 EntityGenerator(随机生成怪物的代码),已经被 Brain + Apron 系统取代。今天的主题是**删除 dead code**——清理不再需要的代码,减少维护负担。

## 0 · 为什么要有这一天

HH 的 EntityGenerator 是 Phase 4 加的:

```rust
// 旧代码:EntityGenerator
struct EntityGenerator {
    templates: Vec<EntityTemplate>,
    spawn_points: Vec<Vec3>,
}

impl EntityGenerator {
    fn generate(&mut self, world: &mut World) {
        for spawn in &self.spawn_points {
            let template = self.templates.choose(&mut rng);
            let entity = template.instantiate(*spawn);
            world.spawn(entity);
        }
    }
}
```

这是"随机生成怪物"的简单实现。Phase 7-8 加了更复杂的系统:

- Day 620:WorldGenerator 用 tag + 随机
- Day 628:Brain + Apron 系统

EntityGenerator **不再被使用**——所有 spawn 走新系统。但代码还在,占内存、增加维护成本、混淆新开发者。

**今天的主题**:**删除 dead code**。把 EntityGenerator 整个模块移除。

### Dead code 的危害

新手觉得"留着不就行了?",但 dead code 有多重危害:

1. **认知负担**:新开发者读代码,看到 EntityGenerator,以为"还在用",浪费时间理解
2. **维护成本**:每次重构都要考虑"会不会影响 EntityGenerator",增加心理负担
3. **编译时间**:dead code 仍然编译,拖慢 build
4. **测试覆盖**:dead code 没测试,但可能"看起来"有(混入活代码)
5. **未来 bug 基础**:有人误以为"还活着",在新功能里调用,引入 bug

**核心**:**dead code 是技术债务**,留着就是欠利息。

**心理锚点**:看完这集,你能:
- 用 Rust 工具找 dead code
- 安全删除而不破坏功能
- 建立"无 dead code"的项目文化

## 2 · 心智模型

### 类比:搬家时扔旧物

搬家前整理:

- 留下的:还在用、有纪念意义、可能未来用
- 扔掉的:**几年没用过、坏掉、过时**

判断标准:**过去 6 个月用过吗?未来 6 个月会用吗?**

代码完全一样:

- 留下的:正在用、计划用
- 扔掉的:**dead code**

判断标准:**grep 找到引用吗?**

### 严谨:Dead Code 检测

#### 2.1 编译器自动检测

Rust 编译器自动检测 unused:

```bash
cargo build
# warning: function is never used: `generate`
# warning: struct is never constructed: `EntityGenerator`
```

但这些 warning 只在"模块内 private" 才有效。如果是 public API,编译器不警告(因为可能被外部用)。

#### 2.2 `cargo udeps` 找未使用依赖

```bash
cargo install cargo-udeps
cargo udeps
# 输出:unused dependencies: `serde` in package `hh`
```

找出 Cargo.toml 里声明但代码里没用的依赖。

#### 2.3 `cargo machete` 找未使用依赖

```bash
cargo install cargo-machete
cargo-machete
# 更快,适合大型项目
```

#### 2.4 `cargo clippy` 找 dead code

```bash
cargo clippy -- -W dead_code -W unused_imports
```

clippy 有多个 lint 找冗余代码。

#### 2.5 `rg` 手动找

```bash
# 找 EntityGenerator 所有引用
rg "EntityGenerator" src/
# 如果只有定义,没引用 → dead code

# 找 import 但没用的
rg "^use " src/ | awk '{print $2}' | sort | uniq -c | sort -n
# 出现 1 次的可能 dead
```

#### 2.6 删除前的验证

**不要立刻删**。先:

1. **grep 引用**:`rg EntityGenerator src/`,确认无引用
2. **运行测试**:`cargo test`,确认测试全过(说明真的没在用)
3. **临时注释**:注释掉定义,`cargo build`,确认编译过
4. **跑游戏**:`cargo run`,确认功能正常
5. **删除**:确实安全后,删除文件
6. **再跑测试**:确认无回退

#### 2.7 删除后的维护

**dead code 删除后,在 commit message 写清楚**:

```
chore: remove unused EntityGenerator

EntityGenerator was added in Phase 4 for random monster spawning.
Phase 7-8 replaced it with:
- Day 620: WorldGenerator (tag-based spawning)
- Day 628: Brain + Apron system (behavior)

EntityGenerator has no remaining references. All tests pass.

If you need random spawning, use the new system. See:
- src/world/generator.rs (Day 620)
- src/monster/brain.rs (Day 628)
```

下一个开发者看到这个 commit,**立刻知道为什么删除 + 替代品在哪**。

### 2.8 渐进 vs 激进删除

**渐进删除**(推荐):

1. 标记 `#[deprecated]`,等几个版本
2. 确认无人用,删除
3. 写 commit 说明

**激进删除**(本日 Casey 用):

1. 直接 grep 确认无引用
2. 删除
3. 跑测试验证

HH 是单人项目,激进删除可接受。开源项目要渐进(给用户迁移期)。

### 2.9 dead code 的特殊形式

不是所有 dead code 都明显:

- **dead branch**:`if false { ... }` 里的代码永远不执行
- **dead after refactor**:重构后老代码留在角落
- **commented out**:大段注释代码
- **test only**:生产代码没用,只有 test 用(仍可保留)
- **conditional dead**:`#[cfg(windows)]` 在 Linux 不编译(但其他平台可能用)

每种 dead code 有不同处理方式。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏项目累积 dead code 极快:

- **每个 level 一个 struct**:加新 level 不删旧 → 累积
- **每个 character 一个 class**:老 character 弃用但代码留着
- **每场 cutscene 一段逻辑**:演完不删

**典型游戏项目**:30-50% 是 dead code(保守估计)。

**工业实践**:

- **Code review 强制**:每次 PR 必须证明没引入 dead code
- **CI 检查**:`cargo clippy` 在 CI 失败 build
- **定期 audit**:每季度专门一周清理 dead code

### 3.2 · 🎨 图形学视角

图形代码的 dead code:

- **deprecated shader**:旧 shader 留着,运行时选新的
- **old render path**:Forward / Deferred / Clustered 三套都留着
- **platform-specific**:`#ifdef _XBOX` `#ifdef _PS5`,跨平台累积

**清理模式**:

- **shader 变体管理**:用 SPIR-V reflection 找实际用到的 variant
- **render graph**:动态构建,无用 pass 自动跳过
- **dead code elimination**:GPU shader compiler 自动剔除

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的 dead code 清理:

- **CONFIG_ 选项**:每个功能可选编译,不用就不编进去
- **`#ifdef`**:旧 API 标记 deprecated,新版本移除
- **`__init` / `__exit`**:初始化代码用 `__init`,加载完后内存释放

```bash
# 看内核选项
make menuconfig  # 交互式选择
make defconfig   # 默认配置
```

`CONFIG_` 让 dead code 不编译,但保留源代码(供未来用)。

### 3.4 · 🦀 Rust 生态视角

Rust 的 dead code 检测工具:

```bash
# 1. cargo clippy(基础)
cargo clippy -- -W dead_code

# 2. cargo udeps(找未使用依赖)
cargo install cargo-udeps
cargo udeps

# 3. cargo machete(更快)
cargo install cargo-machete
cargo machete

# 4. cargo modules(看模块树)
cargo install cargo-modules
cargo modules tree

# 5. miri(找未定义行为)
cargo +nightly miri test  # 找内存 bug
```

每个工具解决不同问题。组合用最全面。

#### Rust 的 `#[allow(dead_code)]`

有时 dead code 是 intentional(预 API):

```rust
#[allow(dead_code)]
pub fn future_api() {
    // 未来用,现在留接口
}
```

但谨慎用,容易掩盖真 dead code。

## 附录 · Dead Code 的深层原因

Day 629 表面是"删代码",深层是**为什么会有 dead code**。理解原因才能预防。

### 5 个常见原因

#### 1. 重构遗留

新系统上线,老系统没清理。HH 的 EntityGenerator 就是这个原因——Phase 4 写,Phase 7-8 替代,但老代码留着。

**预防**:重构完立刻清理老代码,**两顶帽子**分开戴(重构 + 清理一起做)。

#### 2. "以防万一"

开发者想"这个函数未来可能用,先留着"。结果**永远不用**。

**预防**:**YAGNI**(You Aren't Gonna Need It)原则——不要为想象中的需求写代码。

#### 3. 复制粘贴

复制一段代码改几个字,原代码留在原地。结果**两份代码,一份 dead**。

**预防**:**DRY**(Don't Repeat Yourself)原则——提取共享函数。

#### 4. 试验代码

开发时试验多种方案,A 方案留下,B/C 方案也留下(注释掉)。结果**A 工作,B/C 注释在那**。

**预防**:试验代码用 git branch,不在主分支保留。

#### 5. 平台 / 配置

`#[cfg(target_os = "windows")]` 的代码在 Linux 不编译。Linux 开发者忘了它存在。

**预防**:CI 跑多平台 build,定期 review cfg 代码。

### 心理学层面

为什么开发者倾向"留着"?

1. **失去厌恶**(loss aversion):删了感觉"失去",留着感觉"安全"
2. **未来焦虑**:"万一以后要用呢?"——但 99% 不会用
3. **工作证明**:删代码看起来"没产出",留着感觉"有工作量"
4. **责任规避**:删了出问题自己背,留着出问题原作者背

**每个心理障碍都需要克服**——好工程师**敢删**。

### 工业级 dead code 管理

开源项目的 dead code 管理:

- **GitHub issue**:用 label `dead-code` 跟踪
- **PR template**:模板问"是否清理了 dead code"
- **CI 检查**:`cargo clippy` 失败 build
- **年度 cleanup week**:每年专门一周清理

### "删 + 测"循环

安全删除的循环:

```
1. grep 找所有引用
2. 如果有引用 → 不是 dead code,停止
3. 如果无引用 → 临时注释,build
4. build 失败 → 还有引用,恢复注释,回到 1
5. build 成功 → 跑测试
6. 测试失败 → 恢复,重新分析
7. 测试通过 → 删除代码,提交
```

**关键**:**临时注释 + build** 这一步**必做**。直接删除可能漏掉 cfg / dynamic dispatch。

## 附录 II · "Boy Scout Rule" 与代码卫生

Day 629 是"代码卫生"(code hygiene)的体现。**Boy Scout Rule**:

> Leave the campground cleaner than you found it.

童子军规则:**离开时比来时更干净**。应用到代码:

每次打开一个文件,**顺手改 1-2 处小问题**:

- 重命名更清晰的变量名
- 删除一个 unused import
- 加一个文档注释
- 提取一个长函数的一段
- 删除一个 dead code

**积少成多**,代码库质量持续提升。

### Boy Scout Rule 的反模式

#### 反模式 1: 大爆炸重构

"我决定花 1 周重构整个模块"——结果引入 bug,延期。

**正确**:小步快跑,每次提交 < 50 行。

#### 反模式 2: 不动原则

"不是我的代码,不动"——代码腐烂,新功能越来越难加。

**正确**:碰到的代码顺手改。

#### 反模式 3: 强迫症

每次提交都重写整个文件——其他开发者 review 困难。

**正确**:**1-2 处小改**,主要工作还是当前任务。

### 实践 Boy Scout Rule

每天的开发流程:

```
1. 接到任务(如 fix bug)
2. 打开相关文件
3. 读代码时:
   - 看到 typo → 顺手修
   - 看到重复代码 → 顺手提取
   - 看到模糊命名 → 顺手重命名
   - 看到 dead code → 顺手删
4. fix bug
5. 提交:bug fix + 顺手清理(分两个 commit 更好)
```

**关键**:**主要任务和清理分开 commit**,方便 review。

### 工业级"代码卫生"

大型团队:

- **CI lints**:每次 PR 跑 clippy,新代码必须 clean
- **PR template**:提示"是否做了 Boy Scout 改进?"
- **dedicated cleanup PR**:每月一次专门 cleanup PR
- **Tech debt Friday**:每周五专门还债

- **每次重构都顺手清理**(Day 619 / 626 / 629 都是)
- **每周 grep 找 dead code**

### "代码卫生"的认知价值

## 附录 III · 大型代码库的 dead code 战争

工业级大型代码库(Linux kernel / Chromium / LLVM)的 dead code 战争值得深入。

### Linux Kernel 的 dead code

Linux 有 3000 万行代码,dead code 是大问题。

**策略**:

- **CONFIG_ 系统**:可选编译,不用的功能不编入
- **`__init` 宏**:初始化代码用 `__init`,加载后内存释放
- **`__exit` 宏**:卸载代码,运行时不加载
- **modular 设计**:模块化,不需要的模块不加载

```c
static int __init my_init(void) {
    // 这个函数只在加载时跑一次
    // 加载完后,内存释放
}
module_init(my_init);
```

这种"自动 dead code 清理"是 Linux 长期可维护的关键。

### Chromium 的 dead code

Chromium 几千万行,跨平台。

**策略**:

- **GN build system**:精确控制编译什么
- **mojo interface**:进程间通信接口,旧接口标记 deprecated
- **Web Platform evolution**:Web API 进化,旧 API 渐进删除

### LLVM 的 dead code

LLVM 编译器有强大的 dead code elimination:

- **`-dce` pass**:Dead Code Elimination
- **`-adce` pass**:Aggressive DCE
- **`mem2reg`**:SSA 形式,自动消除无用赋值

```bash
clang -O2 -mllvm -print-after-all test.c
# 看每个 pass 后的 IR,DCE 移除了什么
```

LLVM 的 DCE 自动消除"算出但不用的值"。这是编译器优化的基础。

### Rust 编译器的 dead code

Rust 编译器(rustc)用 LLVM,所以享受 LLVM 的 DCE。

```rust
fn main() {
    let x = 5;  // dead,从不用
    let y = 10;
    println!("{}", y);
}
```

编译后,x 不存在(编译器消除)。

### 编译期 vs 运行期 dead code

| 层级 | 工具 |
|---|---|
| 源码 | clippy, udeps |
| 编译期 | LLVM DCE |
| 链接期 | linker GC(`--gc-sections`) |
| 运行期 | JIT profile(PGO) |

每层都有 dead code 检测。

### 工程师视角

工程师看待 dead code:

1. **预防 > 清理**:写代码时遵循 YAGNI / DRY
2. **定期 audit**:每月 / 每季度专门清理
3. **工具组合**:clippy + udeps + linker GC
4. **文化倡导**:Boy Scout Rule,新代码必须 clean

**核心**:**dead code 是慢性病**,需要长期管理,不是一次性清理。

每次清理都是**还技术债务**。Phase 8 末尾,代码库回到"健康"状态。

## 附录 IV · 删除代码的勇气

Day 629 表面是技术活,深层是**心理战**——**敢不敢删代码**。

### 删除代码的心理障碍

#### 障碍 1: "这是别人的代码"

看到别人写的代码,觉得"不尊重原作者",不敢删。

**反驳**:**代码属于项目,不属于个人**。原作者也认同项目健康最重要。

#### 障碍 2: "万一以后要用"

未来焦虑。但 99% 的"以防万一"永远不会用。

**反驳**:**git 永久保留历史**。需要时 `git revert` 即可恢复。

#### 障碍 3: "删了出问题谁负责"

责任规避。删了出 bug,自己背锅。

**反驳**:**有测试 + code review**,bug 容易发现。删了反而可能修复隐藏 bug。

#### 障碍 4: "时间不够"

赶 deadline,没时间清理。

**反驳**:**长期看,清理节省的时间 > 清理花费的时间**。

### 工程师 vs 完美主义者

- **工程师**:权衡,该删就删,该留就留
- **完美主义者**:什么都不敢动,代码库变成"博物馆"

**好工程师有勇气**——敢于删、敢于重构、敢于做不流行的事。

### Linus Torvalds 的"throw it away"哲学

Linus 多次说:**"如果你重写三次,第三次最好"**。

- 第一次:学怎么做
- 第二次:发现第一次的错
- 第三次:真正理解需求

**不要害怕重写 / 删除**。Linux kernel 的 BKL 花了 10 年才删,但删了之后内核快了。

### 删除代码的"仪式感"

每次大删除,做"告别仪式":

1. **写 commit message 说明**:为什么删,删了什么,替代品在哪
2. **通知团队**:让其他人知道(避免他们困惑)
3. **更新文档**:README / CHANGELOG 反映删除
4. **观察一段时间**:删除后 1-2 周,看有没有问题

**仪式感**让删除**有意识、有记录**,不后悔。
