### 严谨:Voxel Collision 算法

#### 2.1 Naive MVP(初版)

```rust
fn move_player(world: &World, player: &mut Player, dir: Vec3, dt: f32) {
    let new_pos = player.pos + dir * player.speed * dt;
    if !world.is_solid_at(new_pos) {
        player.pos = new_pos;
    }
    // 撞了就不动
}
```

**问题**:

1. **穿墙**:速度大时,一帧从 (4.5, 0, 0) 跳到 (5.5, 0, 0),中间 voxel (5, 0, 0) 没检查
2. **卡墙**:贴墙走时,任何小 step 都触发碰撞,玩家完全卡住
3. **斜向**:同时移动 x 和 y,可能斜着穿墙

#### 2.2 分轴检测(改进)

```rust
fn move_player(world: &World, player: &mut Player, dir: Vec3, dt: f32) {
    let dx = dir.x * player.speed * dt;
    let dy = dir.y * player.speed * dt;
    let dz = dir.z * player.speed * dt;

    // X 轴
    let new_x = player.pos + Vec3::new(dx, 0, 0);
    if !world.is_solid_at(new_x) {
        player.pos = new_x;
    }
    // Y 轴
    let new_y = player.pos + Vec3::new(0, dy, 0);
    if !world.is_solid_at(new_y) {
        player.pos = new_y;
    }
    // Z 轴
    let new_z = player.pos + Vec3::new(0, 0, dz);
    if !world.is_solid_at(new_z) {
        player.pos = new_z;
    }
}
```

**改进**:

- 斜向移动分轴 check,**至少一个方向能走**
- 沿墙滑行(X 撞了 Y 还能走)

**仍有问题**:

- 速度大时,单步仍然穿墙
- 边角 case(玩家 1m 但 voxel 1m)仍可能卡

#### 2.3 步进检测(再改进)

```rust
fn move_player(world: &World, player: &mut Player, dir: Vec3, dt: f32) {
    let total = dir * player.speed * dt;
    let distance = total.length();
    let step_size = 0.5;  // 半个 voxel
    let n_steps = (distance / step_size).ceil() as usize;
    let step = total / n_steps as f32;

    for _ in 0..n_steps {
        // 分轴
        let new_x = player.pos + Vec3::new(step.x, 0, 0);
        if !world.is_solid_at(new_x) {
            player.pos = new_x;
        }
        let new_y = player.pos + Vec3::new(0, step.y, 0);
        if !world.is_solid_at(new_y) {
            player.pos = new_y;
        }
        let new_z = player.pos + Vec3::new(0, 0, step.z);
        if !world.is_solid_at(new_z) {
            player.pos = new_z;
        }
    }
}
```

**改进**:

- 长距离移动拆成小步,**不会跳过 voxel**
- 每个小步分轴,**沿墙滑行**

**问题**:

- 性能:速度大时 n_steps 大,每帧几十次检查
- 玩家高度:玩家不止 1 voxel,需要 check 头 / 中 / 脚

#### 2.4 玩家高度

```rust
fn is_player_collide(world: &World, pos: Vec3) -> bool {
    // 玩家是 1×2×1 的 box(宽 1,高 2,深 1)
    let foot = pos;
    let head = pos + Vec3::new(0, 1, 0);  // 头在脚上 1m
    world.is_solid_at(foot) || world.is_solid_at(head)
}
```

更精确:玩家是 1×2×1 box,check 8 个角。但 8 次 voxel check 仍然快。

#### 2.5 完整 MVP

```rust
struct Player {
    pos: Vec3,
    vel: Vec3,
    speed: f32,
}

fn update_player(world: &World, player: &mut Player, input: Input, dt: f32) {
    // 输入 → 速度
    let mut wish_dir = Vec3::new(0, 0, 0);
    if input.w { wish_dir.z -= 1; }
    if input.s { wish_dir.z += 1; }
    if input.a { wish_dir.x -= 1; }
    if input.d { wish_dir.x += 1; }
    wish_dir = wish_dir.normalized();

    // 重力
    player.vel.y -= 9.8 * dt;

    // 移动
    let total = wish_dir * player.speed * dt + player.vel * dt;
    let distance = total.length();
    let n_steps = ((distance / 0.3).ceil() as usize).max(1);
    let step = total / n_steps as f32;

    for _ in 0..n_steps {
        // 分轴
        let dx = Vec3::new(step.x, 0, 0);
        if !is_player_collide(world, player.pos + dx) {
            player.pos += dx;
        } else {
            player.vel.x = 0;  // 撞了,停 x 速度
        }
        // 同理 dy, dz
        let dy = Vec3::new(0, step.y, 0);
        if !is_player_collide(world, player.pos + dy) {
            player.pos += dy;
        } else {
            player.vel.y = 0;
        }
        let dz = Vec3::new(0, 0, step.z);
        if !is_player_collide(world, player.pos + dz) {
            player.pos += dz;
        } else {
            player.vel.z = 0;
        }
    }
}
```

struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn add(self, o: Self) -> Self { Self::new(self.x+o.x, self.y+o.y, self.z+o.z) }
    fn sub(self, o: Self) -> Self { Self::new(self.x-o.x, self.y-o.y, self.z-o.z) }
    fn scale(self, k: f32) -> Self { Self::new(self.x*k, self.y*k, self.z*k) }
    fn dot(self, o: Self) -> f32 { self.x*o.x + self.y*o.y + self.z*o.z }
    fn length(self) -> f32 { self.dot(self).sqrt() }
    fn normalized(self) -> Self {
        let l = self.length();
        if l > 1e-9 { self.scale(1.0/l) } else { Self::new(0.0, 0.0, 0.0) }
    }
}

struct World { voxels: Vec<bool>, w: usize, h: usize, d: usize }
impl World {
    fn new(w: usize, h: usize, d: usize) -> Self {
        Self { voxels: vec![false; w*h*d], w, h, d }
    }
    fn is_solid(&self, x: i32, y: i32, z: i32) -> bool {
        if x < 0 || y < 0 || z < 0 ||
           x >= self.w as i32 || y >= self.h as i32 || z >= self.d as i32 { return true; }
        self.voxels[(x as usize + y as usize * self.w + z as usize * self.w * self.h)]
    }
    fn set_solid(&mut self, x: usize, y: usize, z: usize, v: bool) {
        self.voxels[x + y * self.w + z * self.w * self.h] = v;
    }
}

fn is_player_collide(world: &World, pos: Vec3) -> bool {
    world.is_solid(pos.x.floor() as i32, pos.y.floor() as i32, pos.z.floor() as i32)

fn move_player(world: &World, pos: &mut Vec3, delta: Vec3) {
    let distance = delta.length();
    let n_steps = ((distance / 0.3).ceil() as usize).max(1);
    let step = delta.scale(1.0 / n_steps as f32);

    for _ in 0..n_steps {
        // 分轴
        let dx = Vec3::new(step.x, 0.0, 0.0);
        if !is_player_collide(world, pos.add(dx)) { *pos = pos.add(dx); }
        let dy = Vec3::new(0.0, step.y, 0.0);
        if !is_player_collide(world, pos.add(dy)) { *pos = pos.add(dy); }
        let dz = Vec3::new(0.0, 0.0, step.z);
        if !is_player_collide(world, pos.add(dz)) { *pos = pos.add(dz); }

## 附录 · Continuous Collision Detection(CCD)

Day 632 用"步进 + 分轴"防止穿墙。这是简化的 CCD——真正的 CCD 算法更严谨。

### CCD 原理

**问题**:物体高速移动,一帧从位置 A 到 B,中间可能穿过障碍。

**离散检测**:`if collide(B)`——只在终点 check,中间不 check。

**CCD**:**沿路径 check**——从 A 到 B 的连续轨迹,找最早碰撞时刻。

### Sweep algorithm

把物体"扫过"路径,找碰撞:

```
物体从 A 到 B,扫过的形状 = "胶囊"(A-B 之间 + 物体半径)
```

检测这个胶囊与其他物体的相交。

### Time of Impact(ToI)

CCD 算最早碰撞时刻 t:

```
collide(A + t*(B-A)) == true
```

二分搜索或解析解求 t。

### Bullet physics engine

Bullet 的 CCD 是工业级实现:

- Sub-stepping:把大步拆成小步(类似 Day 632)
- Speculative CCD:预测下一帧可能碰撞,提前响应
- Sphere sweep:简化为球扫

### HH 的"穷人版 CCD"

Day 632 用 sub-stepping,本质是简化 CCD:

- 优点:实现简单,易理解
- 缺点:仍然可能漏(步进太大)

**改进方向**:

- 用 sphere sweep(更精确)
- 用 raycast 检测路径(类似 raycast 系统)

### Raycast-based collision

最严谨的 voxel collision:

```rust
fn move_with_raycast(world: &World, pos: Vec3, dir: Vec3, dist: f32) -> Vec3 {
    // cast 一条光线,找最近 hit
    if let Some(hit) = world.raycast(pos, dir, dist) {
        // 撞了,移到 hit 点(减去 epsilon 防止卡)
        pos + dir * (hit.t - 0.01)
    } else {
        pos + dir * dist
    }
}
```

**优势**:利用已有 raycast 系统(DDA),精确无穿墙。

**劣势**:每帧多次 raycast(分轴 + 步进),性能稍差。

### HH 未来可能升级

## 附录 II · Prototyping 的"快速失败"哲学

Day 632 是 prototype——快速验证假设。这背后是"快速失败"(Fail Fast)哲学。

### Fail Fast 原则

**核心**:**假设可能是错的,快速验证比长期投入重要**。

应用:

- **写 100 行 MVP**,跑起来,验证手感
- **失败就改**,不要在错方向上花 8 天
- **成功就放大**,投入生产实现

### Fail Fast 的反面

**Waterfall(瀑布模型)**:

- 3 个月设计文档
- 3 个月开发
- 3 个月测试
- 上线发现用户不要 → 浪费 9 个月

**Fail Fast**(Agile / Lean):

- 1 周设计
- 1 周 MVP
- 1 周用户测试
- 不对 → 改方向(损失 3 周)
- 对 → 继续放大

### 游戏开发的 Fail Fast

- **Game jam**:48 小时做游戏原型
- **Vertical slice**:做完整一段(从开始到 boss),验证 fun
- **Playtest early**:早让玩家玩,收集反馈
- **Soft launch**:小范围发布,看数据

每个都是 Fail Fast 实践。

### Casey 的 Fail Fast

Day 631 决定重写 → Day 632 立刻写 MVP,验证可行 → 发现问题 → 调整。

如果 Day 631 之后直接花 8 天写生产代码,Day 639 上线发现根本不工作,就浪费 8 天。**Day 632 的 MVP 把风险降到 1 天**。

### Fail Fast 的边界

不是所有事都该 Fail Fast:

- **核心架构**:要深思熟虑,不能"快速试错"
- **安全相关**:谨慎,不能失败
- **不可逆决策**(如删数据库):不能 fail fast

**适用 Fail Fast**:

- UI 设计
- 游戏玩法
- 算法选择
- 性能优化

完成 Day 632 + 全部附录,你应该理解:

- **MVP / Prototype 是核心工具**
- **Fail Fast 比 Waterfall 更适合软件开发**

## 附录 III · Game Feel(Juice)深入

Day 632 的实验不仅是验证"能不能碰撞",也验证"手感怎么样"。**Game Feel**(游戏手感)是游戏设计的核心。

### 什么是 Game Feel

Game Feel(也叫 Juice、Polish):

- **响应**:按键立刻反应,无延迟
- **物理感**:重量、惯性、动量真实
- **反馈**:每个动作有视觉 / 听觉反馈
- **连贯**:动作之间的过渡平滑

### 碰撞与 Game Feel

碰撞系统直接决定 game feel:

- **太严**:每次撞墙都"撞死",挫败
- **太松**:穿墙,失去紧张感
- **刚好**:撞墙有反馈但不挫败,玩家理解边界

Day 632 的实验发现:

- 沿墙滑行好(不会卡死)
- 高速穿墙差(失去紧张感)
- 边界精度差(浮点抖动)

每个都影响 game feel。

### 经典游戏的 Game Feel

- **Super Mario 64**:跳跃 + 着地的"重量感",革命性
- **Celeste**:精确碰撞,1 帧响应,完美控制
- **Hades**:每个动作都有视觉反馈,juice 满满
- **Animal Crossing**:松散碰撞,容错高,轻松

每个游戏按"目标体验"调手感。

### Game Feel 的 5 个要素

Steve Swink 的《Game Feel》提出:

1. **输入**:按键、鼠标、手柄,响应时间
2. **响应**:角色怎么动,物理参数
3. **环境**:碰撞、摩擦、空间感
4. **润色**:粒子、屏幕震动、音效
5. **学习曲线**:玩家掌握节奏

碰撞属于第 3 个(环境),但影响所有其他要素。

### 调 Game Feel 的方法

1. **大量 playtest**:让玩家玩,观察反应
2. **A/B 测试**:不同参数,看哪个更好
3. **数字调试**:可视化位置 / 速度,精确调
4. **对比经典**:玩经典游戏,对比手感

### HH 的 Game Feel

Casey 调碰撞手感:

- 步进大小(0.3 → 0.1,更细)
- 玩家高度(2 voxels → 1.8,稍矮)
- 速度上限(5 m/s → 7 m/s,稍快)
- 摩擦力(高 → 低,更滑)

每个参数都影响手感,**反复测试 + 调整**。

### "Juice" 的具体技巧

- **Screen shake**:撞墙时屏幕轻微震动
- **Particles**:撞击粒子
- **Sound**:撞击音效
- **Haptic**(手柄):震动反馈
- **Animation**:角色撞击动画

这些"juice"让碰撞从"机械"变"有感"。

### 今天的认知收获(终)

完成 Day 632 + 全部附录,你应该理解:

- **Game Feel 是游戏设计的灵魂**
- **碰撞系统直接影响 Game Feel**
- **调整 Game Feel 需要反复 playtest**
- **Juice 技巧**(screen shake, particles, sound)

带着这些认知,你后面做任何游戏,都会:

## 附录 IV · 物理引擎的内部结构

Day 632 实现的"分轴 + 步进"是简化版。工业级物理引擎(Havok, PhysX, Rapier)更复杂。理解其结构有助于看 HH 的位置。

### 物理引擎的 4 个阶段

```
1. Broad Phase
   - 找出可能碰撞的对
   - 用 BVH / SAP / Grid hash

2. Narrow Phase
   - 精确检测每个对
   - 用 GJK / SAT / Voxel(本日)

3. Solver
   - 解决碰撞(分离物体)
   - Sequential Impulse / Lagrange multiplier

4. Integration
   - 应用速度到位置
   - Euler / Verlet / RK4
```

HH 简化版:

- **Broad**:Voxel grid 自然 O(1)
- **Narrow**:Voxel solid check
- **Solver**:简单"撞了就停"
- **Integration**:Explicit Euler

### 工业级的复杂

- **多体碰撞**:3+ 物体同时碰撞,需要 solver 解联立方程
- **摩擦力**:静态 / 动态摩擦,接触点法线
- **滚动 / 旋转**:Torque + 角速度
- **关节 / Constraint**:铰链、弹簧、机械
- **堆叠**:多个箱子堆,稳定计算

HH 都不做——是简化版。

### Rapier(Rust 物理引擎)

```toml
[dependencies]
rapier3d = "0.18"
```

```rust
use rapier3d::dynamics::{RigidBodyBuilder, RigidBodyType};
use rapier3d::geometry::ColliderBuilder;

let mut bodies = RigidBodySet::new();
let mut colliders = ColliderSet::new();

let body = RigidBodyBuilder::dynamic().translation(0.0, 5.0, 0.0).build();
let collider = ColliderBuilder::cuboid(0.5, 0.5, 0.5).build();
let handle = bodies.insert(body);
colliders.insert_with_parent(collider, handle, &mut bodies);
```

完整物理引擎。HH 不用,但理解工业级有助对比。

### HH vs Rapier

| 维度 | HH(本日) | Rapier |
|---|---|---|
| 几何 | 仅 voxel | 任意 convex |
| 物理 | 简单移动 + 碰撞 | 完整 rigid body |
| 摩擦 | 简单"撞了停" | 静 / 动摩擦 |
| 关节 | 无 | hinge / spring / fixed |
| 性能 | 极快(voxel O(1)) | 中等(BVH) |
| 复杂度 | 低 | 高 |

HH 选最简单方案,**因为游戏不需要复杂物理**。如果 HH 是物理游戏(如 Portal),要 Rapier。

### 决策:自己写 vs 用引擎

写不写自己的物理?

- **简单游戏**:自己写,完全控制
- **物理游戏**(Portal, Angry Birds):用引擎
- **多人游戏**:引擎 + 网络同步复杂,可能自己写

HH 单人 / 简单物理,自己写。**理解原理比用现成更重要**。
