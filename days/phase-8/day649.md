
# Day 649 · 移除光照步进表

> 旧光照系统有个"步进表"(walk table):预计算"从光源出发,每步走到哪里",用于加速 raycast。新的 2D 光照 + 中心约定下,raycast 已经够快,**步进表变成冗余**。今天 Casey 删掉它,代码简化 1000 行。

## 0 · 为什么要有这一天

光照系统的旧架构是:

- 每个光源有 walk table:从光源出发,按 N 个方向预计算每步走到哪里
- raycast 时直接查表,不用 DDA 算法
- 表的大小:N 方向 × M 步 × 3D 坐标 = 几 MB / 光源

但 2D 光照下:

- raycast 只在 2D 平面,DDA 简单(2 步而不是 3 步)
- 中心约定让 raycast 更稳定
- 光源数 N 不固定(玩家移动),预计算每个光源 walk table 太慢

Casey 决定**全删 walk table,改成实时 DDA raycast**。性能没掉(2D DDA 快),代码大幅简化。

这一集展示了一个**反直觉的工程教训**:**有时候"优化"是删代码,不是加代码**。早期光照系统加 walk table 是为了性能——那时 CPU 慢,raycast 慢,需要预计算加速。但 CPU 速度和缓存层次都在演化,walk table 反而成了负担:它占内存,cache 不友好,代码复杂。

**Cache locality(缓存局部性)**是这个决策的核心概念。现代 CPU 的 L1 cache 延迟 ~1ns,L2 ~4ns,L3 ~12ns,主内存 ~100ns。如果一个数据结构太大放不进 cache,每次访问都要走主内存,**比"实时计算"慢得多**。walk table 7 MB 远超 L1/L2(几十 KB 到几 MB),每次 lookup 都是 cache miss,实际比"实时算 1 次 sin/cos"慢。

工业实践:**"少即多"**——简单代码常常更快,因为编译器更好优化、cache 更友好、branch predictor 更准。

心理锚点:看完今天,你能:

- 区分"预计算缓存" vs "实时计算"
- 知道什么时候缓存反而拖累(简化 / 内存)
- 实施大段代码删除
- 解释 cache locality 对性能的影响
- 用工具(cargo machete、dead_code lint)找死代码

## 2 · 心智模型

### 类比:GPS 实时导航 vs 预存地图

GPS 导航两种思路:

- **预存地图**:把全国地图存到设备,导航时查询
- **实时算路**:实时计算路径(网络在线时)

预存快但更新慢(地图变了要重存),实时慢但永远最新。

walk table 是预存思路:对每个光源,预计算"光从这里朝某方向走 N 步到哪里"。但 HH 的光源在变(玩家走动),预计算赶不上变化。

### 预计算 vs 实时计算的取舍

预计算优势:

- 运行时快(查表 vs 计算)
- 结果稳定(预计算时算仔细)

预计算劣势:

- 占内存
- 不灵活(预计算条件变了要重算)
- 启动慢(预计算一次性做完)

实时计算优势:

- 内存省
- 灵活(随时改条件)
- 启动快

实时计算劣势:

- 运行时 CPU 代价
- 可能不稳定(数值精度)

**取舍原则**:**如果实时计算的速度可接受,优先实时**——简单、灵活、少缓存管理 bug。

Casey 的取舍:2D DDA raycast ~100 ns,100 万 surface × 10 光源 = 1 秒,可接受。所以删 walk table,用实时 DDA。

### Walk table 的具体结构

旧 walk table(3D 版本):

```rust
struct WalkTable {
    directions: Vec<Vec3>,           // 64 个方向(球面均匀分布)
    walks: Vec<Vec<Vec3>>,           // 64 个方向 × 100 步 = 6400 个 3D 点
}

// 查询:从光源 pos 朝方向 dir,走 t 步到哪里?
fn lookup(table: &WalkTable, pos: Vec3, dir_idx: usize, t: usize) -> Vec3 {
    pos + table.walks[dir_idx][t]
}
```

64 方向 × 100 步 × 12 字节(Vec3)= 76 KB / 光源。100 光源 = 7.6 MB。

新(实时 DDA):

```rust
fn raycast_step(pos: Vec2, dir: Vec2, t: f32) -> Vec2 {
    pos + dir * t
}
```

无存储,实时算。每次 ~10 ns。

### 删除的工程方法

大段代码删除要小心:

1. **确认无引用**:`grep -r "walk_table"` 找所有使用点
2. **逐个删除**:删一个,编译,看错误
3. **删数据结构**:struct WalkTable 删,所有 walk table 实例删
4. **删文件 IO**:load/save walk table 代码删,文件格式废弃
5. **更新文档**:相关 doc 删
6. **跑测试**:确认无回归

Casey 用了 30 分钟删完,1 小时测试。

### 删除带来的好处

- **代码少 1000 行**:维护成本下降
- **构建快**:编译时间减几秒
- **内存省 7 MB**:光表加载快
- **缓存 locality 好**:walk table 内存大,占 cache,删除后 cache 命中率上升
- **新加光源快**:不用预计算,直接实时

让我把"cache locality"展开讲,因为这是工业游戏开发的高频话题。

**CPU cache hierarchy**(典型桌面 CPU):

```
L1 data cache: 32 KB / 核,延迟 1ns,带宽 ~1 TB/s
L2 cache:      256 KB / 核,延迟 4ns,带宽 ~500 GB/s
L3 cache:      8-32 MB / CPU,延迟 12ns,带宽 ~200 GB/s
主内存 DRAM:   16-64 GB / 系统,延迟 100ns,带宽 ~50 GB/s
```

注意带宽差:L1 是 DRAM 的 20 倍,延迟差是 100 倍。所以 cache miss 是**性能杀手**。

walk table 7 MB,远超 L2(256 KB),勉强能塞 L3。每次 lookup 都是 L3 miss 到 DRAM——延迟 100ns。而实时算 sin/cos(用 SIMD intrinsic)~5ns,加上 Vec2 加法 1ns,共 ~6ns。

**结论**:walk table lookup 100 ns vs 实时计算 6 ns,**实时快 16 倍**。这就是 Casey 删 walk table 后 FPS 反而上升的原因。

更激进:**结构数组 vs 数组结构(SoA vs AoS)**。如果你的数据是 Vec3 数组,AoS 是 `[Vec3; N]`(每个 Vec3 三个 float 一起)。但 raycast 只查 x 分量,AoS 把 y/z 也载入 cache,浪费。改成 SoA `[xs: [f32; N], ys: [f32; N], zs: [f32; N]]`,只载入 xs,cache 利用率 3 倍。这是 SIMD 优化的基础。

游戏工业有一句格言:**"数据布局决定性能,算法不是"**。Casey 删 walk table 改实时 DDA,本质就是从"大块查找数据"改成"小段紧凑计算",数据布局更适合 cache。

### 反例:什么时候 walk table 该保留

如果:

- 光源位置固定(不移动)
- 方向数固定(不需要任意方向)
- 实时计算太慢(光线追踪 100 步 / 帧)

那 walk table 还是有用的。比如静态场景的 lightmap baking,可以用 walk table 加速。HH 的"动态光源"决定它必须实时。

更具体:

- **lightmap baking**(Unity / Unreal 静态光照):离线烘焙,慢几分钟,可接受。baking 时用 walk table 加速。
- **Photon mapping**(CryEngine / 离线 GI):发射 100 万光子,每光子反弹多次。walk table 在这里能加速光子追踪。
- **Precomputed radiance transfer**(Microsoft D3D 时代):预计算光传输,运行时只查表。
- **Spherical harmonics**(Irradiance volume):3D 入射光压成 SH 系数(查表),实时旋转。这里的"表"是 SH 系数,不是 walk table,但思想类似。

每个查表方案都对应"实时算太慢"的场景。Casey 的 walk table 因为实时够快,所以删。

### 3.2 · 图形学视角

图形里"查找表"的演化:

- **PAL 调色板**(老 CRT):256 颜色查找表,lookup 像素颜色
- **LUT shader**(post-process):颜色分级 LUT,2D 纹理存色调映射
- **Cube map**:环境光查找表,6 面 texture
- **SH**(球谐函数):3D 方向压成 9 个系数,实时重建

LUT 在图形里仍大量使用——但**每个 LUT 都对应"实时算太慢"的场景**。如果实时算够快,LUT 就该删。

具体到 raycast 的演化:

- **1990s 软件 raycaster**(DOOM):precompute BSP 树,运行时 O(log N) 查找
- **2000s GPU raycaster**:cube map / depth texture,实时 GPU 计算
- **2010s voxel raycaster**:3D DDA on GPU,实时算
- **2020s RTX**:硬件 RT core,实时 10+ GRay/s

每一代硬件进步,都让更多"预计算"变成"实时算"。今天用 RTX,你能实时跑 path tracing(1990s 是几小时一帧,现在 60 FPS)。

但有些 LUT 仍然主流:

- **Spherical harmonics**:9 个系数表示 3D 辐照度,实时重建。比 cube map 省内存 100 倍。
- **BRDF LUT**:preintegrate Cook-Torrance BRDF,存 2D 纹理。Unity / Unreal 默认用。
- **Color grading LUT**:电影级调色,32³ voxel 的颜色映射。
- **Ambient occlusion baked**:静态场景的 AO,烘焙到 vertex 或 texture。

每个 LUT 都对应"实时算太慢"的场景。Casey 删 walk table 因为他的"实时 DDA 够快",其他场景仍需 LUT。

更深的洞察:**LUT 的存在本身就是"性能债务"**。今天 GPU 能实时算很多年前要 LUT 的东西。如果你的项目用旧 LUT,升级硬件后应该评估"是否能改成实时算"。这是技术债务管理的一部分。

### 3.3 · Linux 系统编程视角

Linux 里"查找表"案例:

- **routing table**:路由查找,内核维护
- **ARP cache**:IP-MAC 映射缓存
- **page table**:虚拟到物理内存映射
- **dentry cache**:文件路径到 inode 缓存

这些都是"实时算太慢"(每次网络包 / 内存访问查实时),所以内核维护缓存。但如果缓存命中率低、内存压力大,内核也会动态收缩缓存(类似 Casey 删 walk table)。

**具体例子**:**ARP cache**。内核存"IP → MAC"映射,默认 cache 1 分钟。如果没 cache,每个网络包都要广播 ARP request,网络瘫痪。但 cache 太大也会有问题——内存被占、可能存过时映射。内核的策略:**LRU cache**(最近最少使用淘汰),只在 cache 命中率 > 阈值时维持。

**dentry cache**(目录项缓存)类似。文件系统调用 `open("/foo/bar/baz.txt")`,内核要解析每一级(foo, bar, baz)。每级 dentry 都缓存,下次找快。但如果文件被删,dentry 失效,内核要 invalidate。这套机制复杂,但收益巨大——典型 Linux 系统 dentry 命中率 > 99%。

**page table** 更微妙。虚拟地址 → 物理地址的映射,理论可以"实时算"(每次查 page table 4 级),但太慢。所以 CPU 有 **TLB**(Translation Lookaside Buffer),cache 最近翻译的项。TLB miss 时仍要查 page table(hardware page table walk)。

如果 page table 太大(进程用了大量分散内存),TLB 装不下,每次访问都 TLB miss,性能崩盘。Linux 的 **huge pages**(2 MB 或 1 GB page)就是解法——一个 TLB entry 覆盖 2 MB 而不是 4 KB,TLB 利用率 500 倍。这是数据库 / JVM 调优的关键。

Casey 删 walk table 的决策对应 Linux 内核的 cache 管理:**缓存不是越多越好,要看 cache hit rate 和 cache 占用内存的取舍**。如果 cache 命中率低、占用大,删了反而更快。这是工业代码优化的普适原则。

### 3.4 · Rust 生态视角

Rust 里"删除代码"的工具:

- **dead_code lint**:rustc 警告未使用代码
- **cargo udeps**(第三方):找未使用依赖
- **cargo machete**:同上,更快

```bash
# 查找未使用代码
cargo build --release 2>&1 | grep "warning:.*never used"

# 查找未使用依赖
cargo install cargo-machete
cargo machete
```

Casey 删 walk table 后跑这些工具,确认无残留。

Rust 在死代码检测上比 C/C++ 优秀很多。原因:

1. **严格的可见性规则**:pub / pub(crate) / private,编译器知道每个符号的可见范围
2. **无 macro 黑魔法**(对比 C 的 `#define`):Rust macro 仍然能被跟踪
3. **MIR-level analysis**:rustc 在 MIR 层做使用分析,精度高

Rust 工业项目常用工具链:

- **cargo machete**:找未使用依赖
- **cargo udeps**:同上,更精确(基于编译 trace)但慢
- **cargo bloat**:找 binary 体积大头
- **cargo asm**:看反汇编,确认编译器输出
- **twiggy**:binary 分析,找 dead code

每个工具解决一类问题。养成习惯:**每次大重构后跑一遍这套工具**,确保没有死代码残留。

工业实践:CI 集成

```yaml
# .github/workflows/cleanup.yml
- name: Check unused deps
  run: cargo install cargo-machete && cargo machete
- name: Check dead code
  run: cargo build --release 2>&1 | grep -E "warning:.*never used" | tee /dev/stderr | test ! -s
```

第二个 step 检查 dead_code lint,有 warning 就失败。这强制团队保持代码 clean。

Rust 生态的另一个相关工具是 **`cargo fix --edition`**——自动把代码迁移到新版 edition。这是 Rust "无破坏性演进"的支柱——你能用最新 edition 的特性,但旧代码自动迁移。

最后,**Rust 的 ownership 系统**让"代码删除"更安全。删一段代码,所有引用立即编译错误,你能逐个修。C/C++ 删代码经常产生悬挂指针 / 未定义符号,运行时崩。Rust 编译期就能定位所有引用,这是 Rust 重构风险低的根本原因。

## 5 · 对照与变奏

预计算成本的演化:

| 时代 | 算力 | 预计算 |
|---|---|---|
| 1990s | 弱 | 大量(磁盘慢但 CPU 更慢) |
| 2000s | 中 | 中等(GPU 起) |
| 2010s | 强 | 少(GPU 通用了) |
| 2020s | 极强 | 最少(实时更好) |

趋势:**硬件越强,实时越划算**。HH 1990s 风格的 walk table 在 2020s 是历史包袱。

**演化细节**:

- **1990s 游戏**(Quake、DOOM):大量预计算——BSP 树、lightmap、vis data。DOOM 的 WAD 文件几 MB 都是预计算数据。CPU 太弱(486 50 MHz),实时算什么都慢。
- **2000s 游戏**(Half-Life 2、Halo):中等预计算——lightmap 仍烘焙,但物理 / AI 实时。GPU 兴起,vertex / pixel shader 让 GPU 做重活。
- **2010s 游戏**(Crysis 3、The Last of Us):少量预计算——PBR 实时渲染、实时阴影、实时反射。lightmap 仍烘焙但小众。
- **2020s 游戏**(Cyberpunk 2077、Hogwarts Legacy):最少预计算——RTX 实时光追、实时 GI(Lumen)、实时反射(SSR + RT)。lightmap 几乎消失。

每一代硬件进步,都让"预计算"减少,"实时"增加。原因:**预计算的不灵活**——bake 几小时,改一个 light 要重新 bake。实时虽然慢,但能 dynamic。

**反例**:某些场景仍需大量预计算:

- **Mobile / Web 游戏**:硬件弱,需要预计算
- **电影级 cinematic**:每帧 30 分钟渲染,大量预计算(虽然每帧预计算)
- **MMO 大世界**:地理数据太大,需 streaming + 预计算 LOD

每个场景的"实时 / 预计算"平衡不同。HH 选实时符合"PC + 单机"的定位。

**Casey 的智慧**:Day 649 删 walk table 不是因为"新潮",而是因为**这个特定项目的特定阶段,实时更好**。Casey 反复强调"不要迷信'最新最好',要根据当前需求选"。这是资深工程师的标志。

### Lv2 · 动手实践

**题**:实现"walk table vs 实时 DDA"性能对比。

```rust
// 预计算:对 64 个方向,每个走 100 步,记录位置
struct WalkTable { walks: Vec<Vec<Vec2>> } // 64 × 100

fn lookup_walk(t: &WalkTable, dir_idx: usize, step: usize) -> Vec2 {
    t.walks[dir_idx][step]
}

// 实时 DDA
fn raycast_dda_step(pos: Vec2, dir: Vec2, t: f32) -> Vec2 {
    pos + dir * t
}
```

benchmark 两种方法,看性能差。

**参考解答**:

```rust
use glam::Vec2;
use std::time::Instant;

struct WalkTable { walks: Vec<Vec<Vec2>> }

fn build_table() -> WalkTable {
    let mut walks = Vec::with_capacity(64);
    for i in 0..64 {
        let angle = (i as f32) * std::f32::consts::TAU / 64.0;
        let dir = Vec2::new(angle.cos(), angle.sin());
        let mut path = Vec::with_capacity(100);
        for step in 1..=100 {
            path.push(dir * step as f32);
        }
        walks.push(path);
    }
    WalkTable { walks }
}

fn lookup(table: &WalkTable, dir_idx: usize, step: usize) -> Vec2 {
    table.walks[dir_idx][step]
}

fn realtime(pos: Vec2, dir_idx: usize, step: usize) -> Vec2 {
    let angle = (dir_idx as f32) * std::f32::consts::TAU / 64.0;
    let dir = Vec2::new(angle.cos(), angle.sin());
    pos + dir * step as f32
}

fn main() {
    let table = build_table();
    let pos = Vec2::new(5.0, 5.0);
    let n = 10_000_000;

    let start = Instant::now();
    let mut acc = 0.0;
    for i in 0..n {
        let v = lookup(&table, i % 64, i % 100);
        acc += v.x;
    }
    println!("Walk table lookup: {:?}, sum={}", start.elapsed(), acc);

    let start = Instant::now();
    let mut acc = 0.0;
    for i in 0..n {
        let v = realtime(pos, i % 64, i % 100);
        acc += v.x;
    }
    println!("Realtime compute: {:?}, sum={}", start.elapsed(), acc);
}
```

预期:walk table lookup 比 realtime 稍快(因为 realtime 多算 sin/cos),但差别不大。在大数据量下,walk table 占内存,cache miss 多,realtime 可能反而快。

### Lv3 · 迁移设计

**题**:把 walk table 改成"lazy memoize"——只 cache 最近用过的 (dir_idx, step),其他实时算。提示:LruCache。

**提示**:`LruCache<(usize, usize), Vec2>`,容量 1024。

**思路**:不是全预计算,而是按需计算并缓存。第一次查 (dir=5, step=10) 时实时算并存入 LRU;第二次查同 key 时直接返回 cache。

```rust
use std::collections::HashMap;

struct LazyWalkCache {
    cache: HashMap<(usize, usize), Vec2>,
    capacity: usize,
}

impl LazyWalkCache {
    fn new(capacity: usize) -> Self {
        Self { cache: HashMap::with_capacity(capacity), capacity }
    }
    fn get(&mut self, dir_idx: usize, step: usize) -> Vec2 {
        let key = (dir_idx, step);
        if let Some(&v) = self.cache.get(&key) {
            return v;
        }
        // cache miss,实时算
        let angle = dir_idx as f32 * std::f32::consts::TAU / 64.0;
        let dir = Vec2::new(angle.cos(), angle.sin());
        let v = dir * step as f32;
        if self.cache.len() >= self.capacity {
            // 简单淘汰:随便删一个(真正的 LRU 用 LinkedList)
            let first_key = *self.cache.keys().next().unwrap();
            self.cache.remove(&first_key);
        }
        self.cache.insert(key, v);
        v
    }
}
```

这是"按需缓存"模式。优点:内存占用 = 实际用到的方向/步数;缺点:HashMap 查询有 hash 开销,小规模时反而慢。

什么时候 lazy memoize 比"全缓存"或"全实时"更好?

- **访问有局部性**(某些方向/步数频繁用):memoize 命中率高
- **计算成本高于 cache 查询**:hash ~10 ns,计算 > 10 ns 时值得 memoize
- **总状态空间大但访问稀疏**:全缓存占内存,稀疏访问适合 lazy

工业例子:Web 框架的 template rendering。模板多,但每个用户只访问几个,LRU cache 渲染结果。代码风格:Redis / Memcached 服务,本质都是 lazy memoize。

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::Vec2;

// 实时 2D DDA raycast
fn raycast_2d_dda(
    solid: &dyn Fn(i32, i32) -> bool,
    from: Vec2,
    dir: Vec2,
    max_dist: f32,
) -> Option<f32> {
    let len = dir.length();
    if len < 1e-6 { return None; }
    let dir = dir / len;
    let mut t = 0.0;
    let mut x = from.x.floor() as i32;
    let mut y = from.y.floor() as i32;
    let step_x = if dir.x > 0.0 { 1 } else { -1 };
    let step_y = if dir.y > 0.0 { 1 } else { -1 };
    let t_delta_x = if dir.x.abs() > 1e-6 { 1.0 / dir.x.abs() } else { f32::INFINITY };
    let t_delta_y = if dir.y.abs() > 1e-6 { 1.0 / dir.y.abs() } else { f32::INFINITY };
    let mut t_max_x = if dir.x > 0.0 {
        (x as f32 + 1.0 - from.x) / dir.x
    } else if dir.x < 0.0 {
        (from.x - x as f32) / -dir.x
    } else { f32::INFINITY };
    let mut t_max_y = if dir.y > 0.0 {
        (y as f32 + 1.0 - from.y) / dir.y
    } else if dir.y < 0.0 {
        (from.y - y as f32) / -dir.y
    } else { f32::INFINITY };

    while t < max_dist {
        if solid(x, y) { return Some(t); }
        if t_max_x < t_max_y {
            t = t_max_x;
            t_max_x += t_delta_x;
            x += step_x;
        } else {
            t = t_max_y;
            t_max_y += t_delta_y;
            y += step_y;
        }
    }
    None
}

fn main() {
    // 简单 grid:5x5,中间一堵墙
    let solid = |x: i32, y: i32| -> bool {
        (x == 2 && y >= 0 && y <= 5) || (x == 4 && y == 4)
    };
    let from = Vec2::new(0.5, 0.5);
    let dir = Vec2::new(1.0, 0.0);
    let hit = raycast_2d_dda(&solid, from, dir, 100.0);
    println!("Raycast from {:?} dir {:?}: hit at t = {:?}", from, dir, hit);
    // 应该 hit t = 1.5(到墙边)

    // 性能测试:10 万次 raycast
    use std::time::Instant;
    let start = Instant::now();
    for _ in 0..100_000 {
        let _ = raycast_2d_dda(&solid, from, dir, 100.0);
    }
    println!("100k raycasts: {:?}", start.elapsed());
}
```

## 10 · 工程反思

Day 649 传达三个长期受益的工程教训:

**教训一:不是所有优化都是加法**。资深程序员能识别"应该删的代码"。这种判断能力来自经验——你见过太多"为了优化而加的代码"最后变成负担。删代码的勇气,是 senior 与 junior 的分水岭。

工业实践:**"Premature optimization is the root of all evil"**(Donald Knuth)。Casey 早期加 walk table 是合理的(那时 CPU 慢),但环境变化后必须敢于删。**坚持旧优化是另一种 evil**——代码越积越多,最终维护成本超过性能收益。

**教训二:cache locality 决定性能**。游戏工业 20 年的核心优化方向,从"算法"转向"数据布局"。Data-Oriented Design(DOD)是这个思想的代表——以数据为中心设计代码,而不是以对象为中心。

DOD 的核心原则:

- 数据按访问模式组织(SoA 还是 AoS,按"读什么字段"决定)
- hot/cold separation(常用字段紧凑,罕用字段分离)
- cache line alignment(64 字节对齐,避免 false sharing)
- 避免 indirection(指针追逐 → cache miss)

Casey 的 walk table 是反 DOD 的典型——大块数据、随机访问、cache 不友好。删除它符合 DOD 精神。

**教训三:工具辅助的代码删除**。Casey 用 `cargo machete`、`dead_code lint` 等工具找未使用代码。工业级项目每周跑这些工具,自动 PR 清理死代码。这是 code health 的重要指标。

Rust 在这方面比 C/C++ 强很多——编译器严格检查使用关系,死代码几乎无处藏身。但即便如此,大型项目仍要定期清理。**代码 health 像身体健康,需要持续维护**。

## 11 • Cache locality 的工业优化

工业级 cache 优化的工具箱:

**1. Profile**:

- `perf stat -e cache-misses`:CPU cache miss 统计
- `perf c2c`:false sharing 检测
- `Intel VTune`:专业 cache 分析

**2. Data layout**:

- AoS → SoA(数组结构 → 结构数组)
- Hot/cold splitting(常用字段紧凑,罕用分离)
- Cache line alignment(64 bytes 对齐)

**3. Algorithm**:

- Tiling(分块,数据局部化)
- Prefetching(预取,软件提示)
- Loop fusion / fission(循环合并 / 拆分)

每个优化让 cache miss 减少 50%+,性能提升 2-10x。Casey 在 HH 不优化(简单代码),工业级必须。

## 12 • Data-Oriented Design 的工业实践

DOD(Data-Oriented Design)是现代游戏开发的方法论:

**1. 数据先于代码**:

先想"数据是什么形状",再写代码。例:

```
// 想清楚:1000 个 entity,每个有 pos + vel + hp
// SoA:
struct World { positions: Vec<Vec3>, velocities: Vec<Vec3>, hps: Vec<f32> }
// 比 AoS:
struct World { entities: Vec<Entity> }
// 更 cache 友好
```

**2. 按 access pattern 组织**:

如果某 system 只读 position,不读 hp,把 position 和 hp 分开存,position 数组紧凑。

**3. SIMD 友好**:

数据连续 + 同质(都是 Vec3),SIMD 一次处理 4-8 个。CPU vector unit 满载。

**4. cache line aware**:

64 bytes 一行,struct 大小尽量是 64 的因数(8, 16, 32, 64),避免跨行。

工业实践:**Unity DOTS / Unreal Mass / Bevy ECS** 都是 DOD 框架。资深工程师把 DOD 当信仰。
