# Day 626 · 清理可遍历物

> Day 618-625 处理资产系统 + 光照 bug。今天 Casey 回到游戏逻辑,处理**遗留代码**:Phase 2-7 留下的 "traversable" 概念(玩家可否通过某 tile),已经和新的体素碰撞系统冲突。今天的主题是**清理**:删过时概念、统一接口、移除 dead code。

## 0 · 为什么要有这一天

HH 的代码经过 626 天演进,有大量"历史包袱":

1. **Phase 2 的 `traversable` 概念**:2D tile-based 碰撞,标记哪些 tile 可走
2. **Phase 4 的 entity collision**:实体间碰撞,基于 AABB
3. **Phase 8 准备引入 voxel collision**(Day 631+):3D 体素,完全不同模型

**冲突**:

- `traversable` 是 2D 概念,但 Phase 3+ 进入 3D
- 现在有些"3D 体素"也用 `traversable` 标记,语义混淆
- 新代码不该用旧概念,但旧代码没清理

**今天的主题**:**清理过时概念**。把 `traversable` 从代码里完全删除,改用更准确的 `walkable` / `solid` 二元组。

**清理 vs 重写**:

- **重写**:从零开始,丢旧代码。风险大
- **清理**(本日):**保留工作代码,逐步去除过时概念**。低风险

**心理锚点**:看完这集,你能:
- 识别代码里的"过时概念"
- 安全清理而不破坏功能
- 用渐进式重构管理大型代码库

### 严谨:过时概念的清理

#### 2.1 识别过时概念

`traversable` 在 HH 代码里的语义演化:

**Phase 2**:`traversable: bool`,2D tile,玩家是否可走过去。

**Phase 3**:`traversable` 用于 3D,但语义模糊——可走?可飞?可游?

**Phase 7**:`traversable` 还用于 entity,但意思变成"可推动"。

**Phase 8 准备**:3D 体素碰撞,需要明确"几何实体"vs"玩家可通过",但 `traversable` 已经语义混乱。

**清理动机**:**`traversable` 不再表示单一概念**,继续用会导致 bug。

#### 2.2 设计新概念

```rust
// 新概念:两个独立 bool
struct Tile {
    solid: bool,     // 几何实体(碰撞)
    walkable: bool,  // 玩家可走(游戏逻辑)
}
```

- `solid`:**几何**——这个 tile 有实体碰撞吗?物理判断
- `walkable`:**逻辑**——玩家可不可以走过去?游戏设计判断

两者**正交**:

- 墙:`solid = true, walkable = false`
- 地板:`solid = false, walkable = true`
- 流沙:`solid = false, walkable = false`(玩家陷进去)
- 机关门:`solid = true, walkable = false`,但开机关后变成 `solid = false, walkable = true`

#### 2.3 替换流程

```
Step 1: 加新字段
struct Tile {
    traversable: bool,  // 旧,保留
    solid: bool,        // 新
    walkable: bool,     // 新
}

Step 2: 双写,跑测试
- 初始化时同时设 traversable 和 solid/walkable
- 验证两者一致

Step 3: 改用新字段
- 渲染 / 碰撞 / 移动 都用 solid / walkable
- traversable 不再被读

Step 4: 删 traversable
- struct 只剩 solid / walkable
- 测试通过

Step 5: 提交,commit message 说明
```

**双写阶段**(Step 2)是关键——保证新旧字段一致,如果发现不一致,说明语义有问题,要重新设计。

#### 2.4 dead code 检测

```bash
# Rust 的 dead code lint
cargo build --warnings
# warning: field is never read: `traversable`

# 或用 clippy
cargo clippy -- -W dead_code
```

Rust 编译器自动找未使用字段 / 函数。Casey 用这个找出所有 `traversable` 残留。

#### 2.5 防回退测试

```rust
#[test]
fn test_wall_blocks() {
    let wall = Tile::wall();
    assert!(wall.solid);
    assert!(!wall.walkable);
}

#[test]
fn test_floor_walkable() {
    let floor = Tile::floor();
    assert!(!floor.solid);
    assert!(floor.walkable);
}
```

每个 tile 类型一个 test,确保语义清晰。

### 2.6 清理的代价

清理"看起来没产出"——用户看到的功能没变。但**长期价值巨大**:

- **减少认知负担**:新开发者更容易理解代码
- **减少 bug**:语义模糊导致 bug,清晰语义减少 bug
- **加速新功能**:干净代码加新功能更快

**经理 vs 工程师**:

- 经理看"产出":清理一天没新功能,觉得"浪费时间"
- 工程师看"债务":清理减少未来成本

Casey 是工程师,**主动清理**。

**清理模式**:

- **删 dead code**:没人调用的函数
- **合并重复**:多个相似的函数合并
- **重命名**:语义模糊的名字改清晰
- **拆分**:单一类做太多事,拆成多个

### 3.2 · 🎨 图形学视角

图形 API 也有"过时概念":

- **OpenGL `glBegin/glEnd`**:1990s 设计,2010s deprecated,2020s 删除
- **DirectX 9 fixed-function pipeline**:被 shader 替代,deprecated
- **Vulkan 1.0 的 `VkRenderPass`**:1.3 后用 dynamic rendering 替代

每次升级都是"清理"——删旧概念,加新概念。**但保持兼容**(deprecation period)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的"清理":

- **`bKL` (Big Kernel Lock)**:1990s 设计,2011 年彻底移除。花了 10+ 年
- **`a.out` 格式**:被 ELF 替代,内核 5.1 移除支持
- **`SysV IPC`**:仍然在,但现代代码用 POSIX IPC 或 D-Bus

每次清理都是**渐进的、保持兼容的**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 `solid` 和 `walkable` 应该是两个独立 bool,而不是单一 `traversable`?给出三个理由。

**参考解答**:

1. **正交语义**:`solid` 是几何属性(碰撞),`walkable` 是逻辑属性(游戏设计),两者独立
2. **未来扩展**:机关门需要 `solid=true, walkable=false` → 开门后 `solid=false, walkable=true`,单 bool 表达不了
3. **代码清晰**:看到 `tile.solid` 立刻知道是几何,`tile.walkable` 是逻辑,而 `tile.traversable` 模糊

### Lv2 · 动手实践

**题**:实现一个 Tile struct,带 solid / walkable。要求:
- 4 种 tile:Wall(solid + !walkable), Floor(!solid + walkable), Quicksand(!solid + !walkable), OpenDoor(!solid + walkable)
- 函数 `can_move_through(tile, is_player) -> bool`
- 测试覆盖

完成标准:`cargo test` 通过。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Tile {
    solid: bool,
    walkable: bool,
}

impl Tile {
    fn wall() -> Self { Self { solid: true, walkable: false } }
    fn floor() -> Self { Self { solid: false, walkable: true } }
    fn quicksand() -> Self { Self { solid: false, walkable: false } }
    fn open_door() -> Self { Self { solid: false, walkable: true } }
}

/// 判断玩家能否通过这个 tile
fn can_move_through(tile: Tile, is_player: bool) -> bool {
    if is_player {
        tile.walkable  // 玩家看 walkable
    } else {
        !tile.solid  // 物品看 solid(可推动)
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_wall() {
        let wall = Tile::wall();
        assert!(!can_move_through(wall, true));  // 玩家不能过
        assert!(!can_move_through(wall, false)); // 物品不能过
    }

    #[test]
    fn test_floor() {
        let floor = Tile::floor();
        assert!(can_move_through(floor, true));
        assert!(can_move_through(floor, false));
    }

    #[test]
    fn test_quicksand() {
        let q = Tile::quicksand();
        assert!(!can_move_through(q, true));  // 玩家不能(陷进去)
        assert!(can_move_through(q, false)); // 物品可以(掉进去)
    }
}

fn main() {
    println!("Wall (player): {}", can_move_through(Tile::wall(), true));
    println!("Floor (player): {}", can_move_through(Tile::floor(), true));
    println!("Quicksand (player): {}", can_move_through(Tile::quicksand(), true));
}
```

## 8 · Rust / Arch 落地代码

### 完整清理示例

```rust
// Cargo.toml: 空

// 旧版(将被替换)
mod legacy {
    #[derive(Copy, Clone, Debug)]
    pub struct Tile {
        pub traversable: bool,  // 模糊:可走?可推?
    }

    impl Tile {
        pub fn wall() -> Self { Self { traversable: false } }
        pub fn floor() -> Self { Self { traversable: true } }
    }

    pub fn can_move(tile: Tile) -> bool {
        tile.traversable
    }
}

// 新版(替换)
mod new_system {
    #[derive(Copy, Clone, Debug, PartialEq)]
    pub struct Tile {
        pub solid: bool,
        pub walkable: bool,
    }

    impl Tile {
        pub fn wall() -> Self { Self { solid: true, walkable: false } }
        pub fn floor() -> Self { Self { solid: false, walkable: true } }
        pub fn quicksand() -> Self { Self { solid: false, walkable: false } }
        pub fn open_door() -> Self { Self { solid: false, walkable: true } }
    }

    pub fn can_walk(tile: Tile) -> bool {
        tile.walkable
    }

    pub fn can_push(tile: Tile) -> bool {
        !tile.solid
    }
}

fn main() {
    use legacy::*;
    use new_system::*;

    println!("=== Legacy ===");
    println!("Wall traversable: {}", legacy::can_move(legacy::Tile::wall()));
    println!("Floor traversable: {}", legacy::can_move(legacy::Tile::floor()));

    println!("\n=== New system ===");
    println!("Wall walkable: {}, pushable: {}", can_walk(new_system::Tile::wall()), can_push(new_system::Tile::wall()));
    println!("Floor walkable: {}, pushable: {}", can_walk(new_system::Tile::floor()), can_push(new_system::Tile::floor()));
    println!("Quicksand walkable: {}, pushable: {}", can_walk(new_system::Tile::quicksand()), can_push(new_system::Tile::quicksand()));
    println!("Open door walkable: {}, pushable: {}", can_walk(new_system::Tile::open_door()), can_push(new_system::Tile::open_door()));
}
```

## 附录 · Technical Debt(技术债务)深入

Day 626 的清理本质是**还技术债务**。这是 Ward Cunningham(1980s)提出的概念。

### 什么是技术债务

代码就像金融债务:

- **借债**:快速写代码(不重构、不文档),完成功能快
- **利息**:未来维护成本上升(读代码慢、加功能慢、bug 多)
- **还债**:重构、清理、写文档

**借债有时是对的**(快速验证想法),但**必须还**(否则利息压垮项目)。

### 技术债务的分类

Martin Fowler 提出四象限:

| | 鲁莽 | 谨慎 |
|---|---|---|
| **故意** | "没时间设计" | "先 quick and dirty,后续重构" |
| **无意** | "什么是分层?" | "现在知道分层了,重构吧" |

- **故意 + 谨慎**:好债务,有计划还
- **故意 + 鲁莽**:坏债务,无计划
- **无意 + 谨慎**:学习后清理(本日 Casey 行为)
- **无意 + 鲁粹**:最坏,完全失控

### HH 的技术债务

HH 经过 600+ 天演进,累积的技术债务:

1. **`traversable` 模糊**(本日):无意 + 谨慎,清理
2. **Phase 2 的 2D 概念**:被 Phase 3+ 3D 覆盖,但代码残留
3. **重复实现**:Vec2 / Vec3 在多个模块有不同版本
4. **缺失文档**:核心算法没文档,靠 commit message 理解
5. **过时依赖**:某些 crate 版本旧

每个债务 Casey 都在 Phase 8 还。Day 626 是其中一步。

### 还债的策略

1. **Boy Scout Rule**(本日):每次改文件顺手清理
2. **每周还债日**:团队约定每周一天还债
3. **新功能前还债**:加新功能前,清理相关旧代码
4. **重大版本前还债**:1.0 发布前,系统性还债

### 代码考古学的工具

#### 1. git blame

```bash
# 查看每行代码是谁、何时、为什么加的
git blame src/tile.rs
# 输出:
# abc1234 (Casey 2023-05-15 12:34) pub traversable: bool,
```

```bash

# 看到当时是 Phase 2,只考虑 2D tile
```

理解为什么这样设计,**再决定怎么改**。

#### 2. git log

```bash
# 看文件历史
git log --oneline -- src/tile.rs

# 看某个函数的演化
git log -L 'fn can_move:src/tile.rs'

# 看特定时期
git log --since="2023-05-01" --until="2023-05-31" -- src/tile.rs
```

#### 3. git bisect

```bash
# 找引入 bug 的 commit
git bisect start
git bisect bad HEAD
git bisect good v0.1.0
# git 自动二分,你每次测试 + 标 good/bad
```

定位"功能什么时候坏"。

#### 4. commit message 考古

```bash
git log --grep="traversable"
# 看所有提到 traversable 的 commit
```

理解每个 commit 的动机,**避免重蹈覆辙**。

### 考古的"不要做"

新手考古常犯:

1. **不看历史就改**:不理解原设计意图,改了反而坏
2. **凭"现在看不懂"判断**:可能是当时有理由,先看 commit
3. **大规模重写**:不渐进,引入新 bug
4. **不写新 commit 说明**:未来考古者无法理解你的改动

**核心**:**代码是工程决策的沉积物,每行都有故事**。考古学家的任务就是读懂故事,然后写新故事。

## 附录 III · Semantic Versioning 与 Deprecation

Day 626 的清理在 HH 内部完成,但工业级开源项目要考虑**外部用户**——他们用旧 API,清理会影响他们。

### Semantic Versioning(SemVer)

SemVer 用三段数字:`MAJOR.MINOR.PATCH`

- **MAJOR**:不兼容变更(可能破坏调用方)
- **MINOR**:向后兼容的新功能
- **PATCH**:向后兼容的 bug fix

HH 的 `traversable` → `walkable` 是**MAJOR**变更(破坏旧调用方)。

### Deprecation 流程

工业级项目的渐进迁移:

#### Step 1: Mark deprecated

```rust
#[deprecated(since = "1.0.0", note = "use `walkable` instead, will remove in 2.0.0")]
pub fn traversable(&self) -> bool {
    self.walkable
}
```

调用方收到 warning,知道要迁移。

#### Step 2: 给迁移期

通常 1-2 个 MINOR 版本(6-12 个月)。

#### Step 3: MAJOR 版本删除

```rust
// HH 2.0.0
pub struct Tile {
    solid: bool,
    walkable: bool,
    // traversable 字段删除
}
```

#### Step 4: 写 migration guide

```markdown
# Migrating from HH 1.x to 2.0

## Breaking changes

- `Tile.traversable` removed. Use `Tile.walkable` (game logic) or
  `Tile.solid` (geometric collision) depending on use case.
```

### Rust 的 deprecation 工具

```bash
# 找所有 deprecated 调用
cargo build -- -W deprecated

# 在 CI 强制
cargo deny --deny deprecated
```

### 工业实践

- **Rust std**:每次版本都标记 deprecated,1.0 后从无 breaking change(承诺)
- **bevy**:每个 MINOR 都可能有 breaking change,但 SemVer 不严格
- **React**:大版本(17→18)有 migration guide + codemod 自动迁移
- **Python**:`warnings.warn(DeprecationWarning)` + PEP 文档

### HH 的位置

HH 是单人项目,Casey 自己用,不需要 SemVer。但**清理流程仍然借鉴工业实践**:

- 标记 deprecated(注释 + commit)
- 给迁移期(几天)
- 删除
- 写 commit 说明
