
# Day 624 · 确认光照是 feature

> Day 623 调查角落变暗,得出"是 AO(物理正确)"的结论。今天 Casey 进一步**确认**这个结论,通过对照实验:用一个"反 AO"的 test scene,验证如果代码"修了"角落变暗,反而会引入真 bug。这是 Day 623 的延续——**用更严格的实验确认 feature 判断**。

## 0 · 为什么要有这一天

Day 623 的判断是"角落变暗是 feature",但 Casey 没立刻相信自己的判断。**自我怀疑**是工程师的宝贵品质——即使你觉得对了,也要做反向验证。

今天的反向验证:

1. **假设**:角落变暗是 AO,物理正确
2. **反假设**:如果是真 bug,我们应该能"修",而且修后视觉合理
3. **实验**:
   - 选项 A:加补偿光(让角落变亮)→ 视觉变成"角落和中央一样亮",但物理不对
   - 选项 B:fix raycast(假设角落是 raycast 漏检)→ 找不到漏检 bug,证明 raycast 正确
   - 选项 C:加可视化,对比物理模拟和实测 → 完全一致
4. **结论**:**所有反向验证都支持 feature 判断**

**今天的核心概念**:**科学方法中的反向验证**。Day 623 用正向验证(实测符合理论),今天用反向验证(假设是 bug,证伪)。**两个方向都验证,结论才能稳**。

**心理锚点**:看完这集,你能:
- 用反向验证强化 feature vs bug 判断
- 设计对照实验
- 在自我怀疑中坚持科学方法

## 2 · 心智模型

### 类比:医生的"鉴别诊断"

医生看到症状,不会立刻下诊断。他会做"鉴别诊断":

1. **初步诊断**:症状 A 符合疾病 X
2. **排除其他可能**:症状 A 也可能符合 Y、Z
3. **逐一排除**:做测试,排除 Y、Z
4. **确认 X**:剩下的最可能就是 X

Day 624 完全一样:

1. **初步判断**:角落暗符合 AO
2. **排除其他可能**:也符合"raycast bug"、"tag bug"、"数值 bug"
3. **逐一排除**:
   - raycast bug?跑 raycast 可视化,无漏检 → 排除
   - tag bug?查 asset tag,无错配 → 排除
   - 数值 bug?跑 Monte Carlo reference,匹配 → 排除
4. **确认 AO**:剩下唯一可能就是物理正确的 AO

### 严谨:科学方法的可证伪性

Karl Popper 的"可证伪性"原则:**科学理论必须能被实验证伪**。

应用:

- **假设 H1**:角落暗是 AO(物理)
- **可证伪预测**:如果是 AO,与 Monte Carlo reference 应该一致
- **实验**:对比实时和 reference
- **结果**:一致 → H1 暂时成立(没被证伪)
- **继续验证**:换不同场景,继续测,看是否有反例

**反假设 H2**:角落暗是 bug
- **可证伪预测**:如果是 bug,应该能在 raycast / tag / 数值里找到错误
- **实验**:逐一排查
- **结果**:找不到 → H2 被证伪

**结论**:H1 成立,H2 不成立。

### 2.3 反向 fix 测试

如果 Casey 想要"修"角落变暗:

**选项 A:加补偿光**

```rust
fn light_at(p: Vec3) -> f32 {
    let mut light = compute_normal_light(p);
    // 角落补偿:如果 AO 低,加补偿
    let ao = compute_ao(p);
    if ao < 0.7 {
        light += (0.7 - ao) * 0.5;  // 补偿到至少 0.7
    }
    light
}
```

**结果**:角落变亮了,但**看起来扁平**——失去了深度感。玩家反馈"场景像 2D"。

**结论**:补偿光破坏 AO 的视觉效果,**不该修**。

**选项 B:假设 raycast 漏检**

```rust
fn debug_raycast(world: &World, p: Vec3, dir: Vec3) {
    let hit = world.raycast(p, dir, 5.0);
    println!("raycast from {:?} dir {:?}: {:?}", p, dir, hit);
    // 可视化光线,看是否漏检
}
```

**结果**:所有测试光线都正确命中或正确 miss,**没有漏检 bug**。

**结论**:raycast 正确,**bug 不存在**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

"自我怀疑 + 反向验证"在游戏开发的几个案例:

1. **Halo 的"shield 缓慢恢复"**:测试者觉得"卡顿",想立即恢复。开发者验证后确认"缓慢恢复是 intentional,提高战略性"
2. **Dark Souls 的"难度高"**:测试者觉得太难,要求降低。开发者验证后"难度是 intentional,系列核心"
3. **Spelunky 的"随机性"**:玩家抱怨"运气决定一切"。开发者验证"随机 + 技能 50/50 是 intentional"

**共同点**:**坚持 intentional design,不轻易"修"feature**。

### 3.2 · 🎨 图形学视角

图形学的"feature vs bug"判断常踩坑:

1. **Gamma 校正**:1980s-2000s 大部分游戏没做,场景"看起来对"但物理错。后来改了,场景看起来"更对"
2. **Tone mapping**:HDR 渲染 + tone mapping,场景"看起来更真实",但有些场景玩家觉得"颜色怪"
3. **PBR**:物理正确渲染,但有些材质(皮肤、布料)需要特殊处理才"看起来对"

**核心**:**"看起来对"和"物理对"经常矛盾**。Casey 选物理对(Day 624),某些项目选看起来对(美术驱动)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的"feature vs bug"判断:

1. **OOM killer**:Linux 在内存紧张时杀进程。测试者觉得"为什么杀我的进程?" → 内核 intentional
2. **TCP keepalive**:连接空闲一段时间,内核可能关闭。测试者觉得"为什么连接断了?" → intentional
3. **swap**:内存换到磁盘,系统变慢。测试者觉得"为什么慢?" → intentional

每个 feature 都有"看起来像 bug"的用户反馈。内核开发者坚持 intentional design,**不轻易改**。

### 3.4 · 🦀 Rust 生态视角

Rust 的"feature vs bug":

1. **borrow checker**:新手觉得"为什么编译失败?" → intentional(安全保证)
2. **zero-cost abstraction**:Rust 的迭代器和手写循环一样快。测试者觉得"应该慢" → intentional(优化)
3. **`Result<T, E>`**:Rust 强制错误处理。新手觉得"啰嗦" → intentional(安全)

每个特性都让初学者觉得"是 bug",但理解后会发现是 feature。**坚持 intentional design,不轻易改**。

## 8 · Rust / Arch 落地代码

### 完整 Monte Carlo AO 对比

```rust
// Cargo.toml: 空

// 基于 Day 623 的代码,加 multi-resolution 对比

#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn add(self, o: Self) -> Self { Self::new(self.x+o.x, self.y+o.y, self.z+o.z) }
    fn sub(self, o: Self) -> Self { Self::new(self.x-o.x, self.y-o.y, self.z-o.z) }
    fn scale(self, k: f32) -> Self { Self::new(self.x*k, self.y*k, self.z*k) }
    fn dot(self, o: Self) -> f32 { self.x*o.x + self.y*o.y + self.z*o.z }
    fn length(self) -> f32 { self.dot(self).sqrt() }
    fn normalized(self) -> Self {
        let l = self.length();
        if l > 1e-9 { self.scale(1.0/l) } else { Self::new(0.0, 0.0, 0.0) }
    }
    fn cross(self, o: Self) -> Self {
        Self::new(
            self.y*o.z - self.z*o.y,
            self.z*o.x - self.x*o.z,
            self.x*o.y - self.y*o.x,
        )
    }
}

struct World { boxes: Vec<(Vec3, Vec3)> }

impl World {
    fn ray_hits_box(&self, ro: Vec3, rd: Vec3, max_t: f32) -> bool {
        for &(min, max) in &self.boxes {
            if ray_box_intersect(ro, rd, min, max, max_t) { return true; }
        }
        false
    }
    fn ao(&self, p: Vec3, n: Vec3, samples: usize) -> f32 {
        let mut visible = 0;
        let up_t = if n.y.abs() < 0.99 { Vec3::new(0.0, 1.0, 0.0) } else { Vec3::new(1.0, 0.0, 0.0) };
        let t1 = n.cross(up_t).normalized();
        let t2 = n.cross(t1).normalized();

        for i in 0..samples {
            let u = halton(i as u32 + 1, 2);
            let v = halton(i as u32 + 1, 3);
            let r = u.sqrt();
            let phi = 2.0 * std::f32::consts::PI * v;
            let local = Vec3::new(r*phi.cos(), r*phi.sin(), (1.0 - u).sqrt());
            let dir = t1.scale(local.x).add(t2.scale(local.y)).add(n.scale(local.z)).normalized();
            if !self.ray_hits_box(p.add(n.scale(0.001)), dir, 5.0) {
                visible += 1;
            }
        }
        visible as f32 / samples as f32
    }
}

fn halton(index: u32, base: u32) -> f32 {
    let mut f = 1.0; let mut r = 0.0; let mut i = index;
    while i > 0 {
        f /= base as f32;
        r += f * (i % base) as f32;
        i /= base;
    }
    r
}

fn ray_box_intersect(ro: Vec3, rd: Vec3, min: Vec3, max: Vec3, max_t: f32) -> bool {
    let mut tmin = f32::MIN;
    let mut tmax = f32::MAX;
    for axis in 0..3 {
        let ro_a = [ro.x, ro.y, ro.z][axis];
        let rd_a = [rd.x, rd.y, rd.z][axis];
        let min_a = [min.x, min.y, min.z][axis];
        let max_a = [max.x, max.y, max.z][axis];
        if rd_a.abs() < 1e-9 {
            if ro_a < min_a || ro_a > max_a { return false; }
        } else {
            let t1 = (min_a - ro_a) / rd_a;
            let t2 = (max_a - ro_a) / rd_a;
            let (t1, t2) = if t1 < t2 { (t1, t2) } else { (t2, t1) };
            tmin = tmin.max(t1);
            tmax = tmax.min(t2);
            if tmin > tmax { return false; }
        }
    }
    tmin >= 0.0 && tmin <= max_t
}

fn main() {
    let world = World {
        boxes: vec![
            (Vec3::new(-10.0, -1.0, -10.0), Vec3::new(10.0, 0.0, 10.0)),  // 地板
            (Vec3::new(-1.0, 0.0, -10.0), Vec3::new(0.0, 10.0, 10.0)),    // 左墙
            (Vec3::new(-10.0, 0.0, -1.0), Vec3::new(10.0, 10.0, 0.0)),    // 后墙
        ]
    };

    let n_up = Vec3::new(0.0, 1.0, 0.0);

    let test_points = [
        ("Center    ", Vec3::new(5.0, 0.001, 5.0)),
        ("Corner    ", Vec3::new(0.001, 0.001, 0.001)),
        ("Wall edge ", Vec3::new(0.001, 0.001, 5.0)),
        ("Open field", Vec3::new(5.0, 5.0, 5.0)),
    ];

    println!("Point        Low(32)  High(4096)  Diff%   Verdict");
    println!("-----------------------------------------------------");
    for (name, p) in &test_points {
        let low = world.ao(*p, n_up, 32);
        let high = world.ao(*p, n_up, 4096);
        let diff = ((low - high) / high).abs() * 100.0;
        let verdict = if diff < 5.0 { "OK (feature)" } else { "INVESTIGATE" };
        println!("{}  {:.3}    {:.3}      {:>5.1}%   {}", name, low, high, diff, verdict);
    }
}
```

## 附录 · 科学方法在工程中的 5 个应用

Day 624 的方法论(科学方法 + 反向验证)在软件工程的 5 个核心应用:

### 1. 性能优化

**假设**:函数 X 是瓶颈。**反向验证**:替换 X 为 stub,看性能改善。**结论**:改善 → X 是;不改善 → 不是。

这是 profiler 工作原理之一——通过"假设 + 验证"找瓶颈。

### 2. Bug 定位

**假设**:bug 在文件 X。**反向验证**:用旧版本 X,看 bug 是否消失。**结论**:消失 → bug 在 X;不消失 → 不在。

这是 git bisect 的原理。

### 3. 安全审计

**假设**:输入 X 触发漏洞。**反向验证**:用 fuzzing 生成类似输入,看是否触发。**结论**:触发 → 找到漏洞;不触发 → 假设错误。

### 4. ML 模型评估

**假设**:模型在数据 X 上准确。**反向验证**:用 adversarial example(对抗样本)测试。**结论**:准确 → 模型好;对抗失败 → 模型有弱点。

### 5. 渲染验证(本日)

**假设**:渲染效果符合物理。**反向验证**:Monte Carlo reference 对比 + 反 fix 实验。**结论**:一致 → feature;不一致 → bug。

**核心**:**科学方法是工程的核心方法论**,不只是科学家的工具。

### 工程师的科学方法 vs 码农的"凭感觉"

| 维度 | 工程师 | 码农 |
|---|---|---|
| 看到现象 | 先问"是 feature 吗?" | 立刻"修" |
| 验证假设 | 反向排除其他可能 | 只验证自己的假设 |
| 失败处理 | 接受假设错,重新调研 | 坚持"我没错" |
| 文档化 | 写清楚验证过程 | 不写,凭记忆 |

**核心**:**工程师是怀疑论者**——甚至怀疑自己。码农是自我中心——相信自己直觉。

### 自我怀疑的边界

虽然"自我怀疑"好,但**过度怀疑也会出问题**:

- 决策瘫痪(永远在验证,不行动)
- 错失机会(feature 拖太久才上线)
- 团队士气低(反复推翻决策)

**平衡**:**关键决策严格验证,小决策快速行动**。Day 624 是关键决策(影响整个 AO 系统),值得 1-2 天验证。但"按钮颜色"这种小事不该花几天。

## 附录 II · Monte Carlo 方法的深度

Day 624 用 Monte Carlo 积分做 reference。这是数值方法的重要工具,值得深入理解。

### Monte Carlo 原理

**问题**:计算积分 `I = ∫ f(x) dx`。

**Monte Carlo 方法**:

```
1. 在积分域随机采样 N 个点 x_1, x_2, ..., x_N
2. 计算 f(x_i) 的平均:I ≈ (V / N) × Σ f(x_i)
   (V 是积分域体积)
3. 当 N → ∞,I 收敛到真值(中心极限定理)
```

**误差**:`~ 1/√N`(平方根收敛)。N=100 误差 10%,N=10000 误差 1%,N=1000000 误差 0.1%。

### 应用到 AO

AO 定义:`AO(P) = (1/π) ∫ visibility(P, ω) cos(θ) dω`

- 积分域:P 的上半球
- 被积函数:`visibility(P, ω) × cos(θ)`
- Monte Carlo:上半球随机采样 N 个方向,看多少 visible

N=32(实时):误差 ~18%。
N=1024(reference):误差 ~3%。
N=4096(高精度 reference):误差 ~1.5%。

Day 624 用 4096 作 reference,验证实时版本。

### 重要采样(Importance Sampling)

普通 Monte Carlo 在所有方向均匀采样。但 AO 中,cos(θ) 权重让接近"顶部"的方向更重要。**重要采样**:用 `cos(θ)` 分布采样,而不是均匀。

```rust
fn sample_hemisphere_cos(rng: &mut Rng) -> Vec3 {
    // cos-weighted hemisphere sample
    let u1: f32 = rng.gen();
    let u2: f32 = rng.gen();
    let r = u1.sqrt();
    let phi = 2.0 * PI * u2;
    Vec3::new(r * phi.cos(), (1.0 - u1).sqrt(), r * phi.sin())
}
```

**效果**:同样 N 下,误差减少 ~3-5 倍。

### Quasi-Monte Carlo

用低差异序列(low-discrepancy sequence)代替随机:

- **Halton sequence**:Day 624 用
- **Sobol sequence**:更均匀
- **Hammersley sequence**:适合 N 已知

**效果**:误差从 `1/√N` 改善到 `1/N`,大大加速收敛。

### 蓝噪声 vs 白噪声

普通随机是"白噪声",某些区域过密、某些过疏。

**蓝噪声**:更均匀分布,视觉上"友好"。游戏渲染常用。

### 工业实践

- **Mitsuba / pbrt**:Monte Carlo path tracer,reference 级渲染
- **RenderMan**:电影级 Monte Carlo
- **Real-time denoiser**(SVGF):用 temporal accumulation + filter,降低 Monte Carlo 噪声

## 附录 III · "Feature Not Bug" 在 HH 项目中的应用

HH 项目中有多个"以为是 bug 实际是 feature"的案例:

### 案例 1:角落变暗(Day 623-624)

- **现象**:房间角落亮度低于中央
- **理论**:AO,物理正确
- **决策**:保留,加 debug overlay 解释

### 案例 2:Diffuse 模糊(Day 617)

- **现象**:间接光阴影边缘模糊
- **理论**:半球积分必然模糊
- **决策**:保留,接受

### 案例 3:色彩 bleeding

- **现象**:红色墙边的间接光带红色
- **理论**:color bleeding 是 GI 的正确表现
- **决策**:保留(美术可能不喜欢,但物理对)

### 案例 4:TAA 残影(如有)

- **现象**:运动物体留下淡淡"残影"
- **理论**:temporal anti-aliasing 是历史帧混合
- **决策**:可调 strength,默认保留

### 案例 5:Moiré 纹理

- **现象**:远处的纹理出现奇怪条纹
- **理论**:采样不足,违反 Nyquist
- **决策**:加 mip mapping,默认保留

### 共同模式

每个 case 都遵循:**理解 → 判断 → 决策**。

1. **理解**:用理论 / 实验确认现象来源
2. **判断**:feature(物理正确)vs bug(数值 / 算法错)
3. **决策**:feature 保留,bug 修

### 何时"修 feature"

虽然原则上 feature 保留,但有时需要妥协:

1. **美术强烈反对**:美术总监说"这个不对",物理正确也得改
2. **玩家普遍反对**:玩家反馈"看起来奇怪",可能需要折中
3. **跨平台不一致**:不同硬件渲染不同,统一改

**修法**:

- 加调节参数(强度、半径)
- 加 post-process(改变视觉效果)
- 完全替换算法(如 PBR → stylized)

### 项目长期维护

"feature not bug"决策的**文档化**至关重要:

```
commit: Day 624 - confirmed corner darkening is AO

Verification:
- Monte Carlo reference matches within 1% error
- Ray cast visualization: no missed rays
- Anti-fix experiment: compensation light flattens scene

Decision: KEEP as feature. Do NOT add compensation.
If users complain, add "AO strength" slider, default 1.0.

References:
- Real-Time Rendering Ch. 11.3.4 (Ambient Occlusion)
- Crytek SSAO paper (2007)
```

下一个开发者看到这个 commit,**立刻知道为什么"角落变暗"留着**。这种文档化是**长期项目维护的关键**——避免"修 feature"的回退。
