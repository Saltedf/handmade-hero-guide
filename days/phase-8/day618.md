
# Day 618 · 资产标签哈希

> Raycast 优化段(Day 611-617)结束,Casey 回到游戏逻辑。今天的主题是**资产标签**(asset tag)——给每个资产(精灵、模型、音效)贴一组语义标签(如 `["wall", "stone", "medieval"]`),用字符串查找。直接字符串比较慢,Casey 用**哈希**(hash)把字符串压成 u64,常数时间查找。这是字符串 → 整数的经典优化。

## 0 · 为什么要有这一天

HH 的资产系统在 Phase 7 已经搭好:加载 PNG 精灵、glTF 模型、WAV 音频。但 Phase 7 用的是**整数 ID**(`asset_id: u32`)来引用资产。这在编译期很方便,但**运行时编辑器**需要按"语义"查找——例如关卡设计师点"添加一面石墙",编辑器要找所有标签为 `wall + stone` 的资产。

如果资产 ID 是硬编码的,关卡设计就要修改源码;如果用字符串查找,运行时灵活但慢。**Asset tag 是折中方案**:

1. 资产加载时,美术给每个资产贴一组字符串标签(`"wall"`, `"stone"`, `"door"`……)
2. 引擎把这些字符串预哈希成 u64,存进 HashMap
3. 运行时,关卡 designer 用字符串查 → 哈希 → HashMap 查找 → 返回资产 ID
4. 全程 O(1),不损失灵活性

**今天的核心概念**:**字符串哈希** —— 把任意长度字符串映射到固定长度(通常是 u64)的整数,用作 HashMap 的 key。一个好的哈希函数满足:

- **快速**(算哈希比比字符串快很多)
- **均匀分布**(不同字符串哈希到不同值,碰撞少)
- **确定**(同字符串每次哈希结果相同,不依赖随机种子)

**心理锚点**:看完这集,你能:
- 实现一个工业级字符串哈希函数(如 FNV-1a 或 xxHash)
- 用 HashMap 优化字符串查找,从 O(N) 降到 O(1)
- 解释为什么不能用 Rust 的默认 `Hasher`(它有随机种子,每次运行结果不同)

## 2 · 心智模型

### 类比:图书馆 ISBN 编号

图书馆里有 100 万本书。如果按书名找,需要从书架一格一格扫,O(100万)。但如果每本书有一个 ISBN(整数),按 ISBN 找只要 O(1)——因为 ISBN 直接索引到书架位置。

**ISBN 是书名的"哈希"**:把变长字符串(书名)映射到固定长度整数(ISBN)。ISBN 唯一(没有两本书 ISBN 相同),所以查找精确。

**字符串哈希完全一样**:把 `&str` → `u64`,用作 HashMap 的 key。O(N) 字符串比较变成 O(1) 哈希查找。

### 严谨推导:FNV-1a 哈希

#### 2.1 哈希函数的要求

给定字符串 `s`,哈希函数 `h(s)` 应该:

1. **确定性**:`h(s)` 永远相同(对同一 `s`)
2. **均匀分布**:不同 `s` 哈希到不同值,概率上 1/2^64 均匀
3. **快速**:几纳秒内算完
4. **雪崩效应**(avalanche):输入改变 1 bit,输出改变 ~50% 的 bit

#### 2.2 FNV-1a 算法

FNV(Fowler-Noll-Vo)是 1991 年的哈希函数,a 变种是改进版。算法极简:

```
hash = offset_basis  # 起始值,固定常数
for byte in input:
    hash = hash XOR byte
    hash = hash * FNV_prime  # 固定常数
return hash
```

**64 位 FNV-1a 常数**:
- `offset_basis = 0xcbf29ce484222325`
- `FNV_prime = 0x100000001b3`

**为什么有效**:

- **XOR**:让每个字节都影响 hash 的低位(直接混合)
- **乘法 prime**:让低位的影响"扩散"到高位(prime 保证乘法不丢失信息)
- 重复应用 → 48 轮后每个 bit 都依赖输入的每个 bit(雪崩)

#### 2.3 Rust 实现

```rust
const FNV_OFFSET_BASIS: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

fn fnv1a_hash(s: &str) -> u64 {
    let mut hash = FNV_OFFSET_BASIS;
    for byte in s.bytes() {
        hash ^= byte as u64;       // XOR 字节
        hash = hash.wrapping_mul(FNV_PRIME);  // 乘 prime(wrapping 防止溢出 panic)
    }
    hash
}
```

**注释**:
- `wrapping_mul` — Rust 的整数乘法默认 debug 模式 panic on overflow,release 模式 wrapping。显式 wrapping_mul 保证两种模式行为一致
- `byte as u64` — u8 转 u64,零扩展
- 一次循环 ~1ns,字符串 "wall" 4 字节 → 4ns;100 字节 → 100ns

#### 2.4 用作 HashMap 的 key

```rust
use std::collections::HashMap;

struct AssetStore {
    by_hash: HashMap<u64, AssetId>,
}

impl AssetStore {
    fn register(&mut self, tag: &str, id: AssetId) {
        let h = fnv1a_hash(tag);
        if self.by_hash.insert(h, id).is_some() {
            // 同哈希已存在 → 碰撞警告
            eprintln!("Hash collision or duplicate tag: {}", tag);
        }
    }
    fn get(&self, tag: &str) -> Option<AssetId> {
        let h = fnv1a_hash(tag);
        self.by_hash.get(&h).copied()
    }
}
```

**注释**:
- `HashMap<u64, AssetId>` 内部用开放寻址 + 红黑树(Java)或 Robin Hood hashing(Rust std),查找 O(1) 平均
- `insert(h, id).is_some()` — 返回旧值(如果存在)。Some 表示冲突,需要警告
- `.copied()` — `Option<&AssetId>` → `Option<AssetId>`(因为 AssetId 是 Copy)

#### 2.5 为什么不用 Rust 默认 Hasher?

```rust
use std::collections::HashMap;
let mut map: HashMap<String, i32> = HashMap::new();
map.insert("foo".to_string(), 1);
// 默认 Hasher 是 SipHash(随机种子,防 HashDoS 攻击)
```

Rust 默认 `RandomState` 用 SipHash 1-3,每次程序启动**种子随机**。这意味着:

- **同字符串不同运行结果不同**(防攻击者预先算哈希)
- **慢**:SipHash ~10ns/byte,FNV ~1ns/byte,慢 10 倍

**游戏资产不是 HashDoS 目标**(攻击者无法控制资产标签),所以可以**安全用 FNV + 固定种子**。这是性能 vs 安全的工程权衡。

```rust
use std::collections::HashMap;
use std::hash::BuildHasherDefault;

#[derive(Default)]
struct FnvHasher(u64);

impl std::hash::Hasher for FnvHasher {
    fn write(&mut self, bytes: &[u8]) {
        for &b in bytes {
            self.0 ^= b as u64;
            self.0 = self.0.wrapping_mul(FNV_PRIME);
        }
    }
    fn finish(&self) -> u64 { self.0 }
}

type FnvHashMap<K, V> = HashMap<K, V, BuildHasherDefault<FnvHasher>>;
```

这样 `FnvHashMap<String, AssetId>` 在标准库 HashMap 接口下用 FNV 哈希,无随机种子,~10 倍速。

### 2.6 哈希碰撞处理

理论上 64 位哈希空间有 2^64 ≈ 1.8×10^19 个值,碰撞概率极低。但如果发生:

1. **同哈希不同字符串**:HashMap 会用 `==` 比较 String 找正确值(O(1) 平均,O(log N) 最坏)
2. **同哈希同字符串**:不会发生,HashMap 第二次 insert 会覆盖

实际工程:**对几千到几万个资产标签,碰撞概率几乎为 0**。Casey 不担心。

### 3.1 · 🎮 游戏编程视角

**坑**:

- **打字错误**:`"wall"` vs `"Wall"` 是不同 tag。Casey 加了大小写归一化(`to_lowercase()`)
- **空间字符串**:同字符串在二进制里多次存储,内存浪费。Casey 用 `String` interning(字符串驻留)
- **热重载**:资产重新加载后 tag → ID 映射要重建

### 3.2 · 🎨 图形学视角

图形学里的"哈希"主要用于:

1. **Texture cache**:用 `hash(texture_path)` 作 key,避免重复加载
2. **Shader cache**:`hash(shader_source)` 作 key,缓存编译结果
3. **Material pipeline**:`hash(material_params)` 作 PSO(Pipeline State Object)key
4. **Mipmap chain**:`hash(texture_id, mip_level)` 作 cache key

这些都是"字符串 → 整数"的扩展,本质相同。

**GPU 端 hash**:GPU shader 不能用 HashMap,但可以用 hash 做:

- **A-Buffer 渲染**:用 hash 把 fragment 索引到 linked list
- **Hash-based稀疏体素**:hash(voxel_pos) → 数据
- **GPU-driven culling**:hash(mesh_id) → indirect draw command

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核大量用哈希:

1. **dentry cache**:`hash(filename) → dentry pointer`,加速文件查找
2. **inode cache**:`hash(inode_number) → inode`
3. **PID hash table**:`hash(pid) → task_struct`
4. **sysfs / procfs**:类似

**查看内核哈希表大小**:

```bash
# /proc/sys/kernel/file-max 等显示哈希表大小
cat /proc/sys/kernel/file-max
cat /proc/sys/kernel/inotify/max_user_watches

# dmesg 看启动时的哈希表初始化
dmesg | grep -i hash
# 输出例子:
# [    0.000000] Dentry cache hash table entries: 2097152
# [    0.000000] Inode-cache hash table entries: 1048576
```

**这些哈希表大小**根据物理内存动态调整(经验法则:每 MB 内存 4K 项)。

**Linux 文件系统里的"标签"**:

- **xattr(extended attributes)**:文件可以贴任意 key-value 标签,如 `user.wall = "stone"`
- **SELinux contexts**:安全标签,如 `system_u:object_r:httpd_sys_content_t:s0`
- 这些都用 hash 加速查找

## 4 · 认知地图

### 4.1 上级

- **Hash table**(哈希表)—— 数据结构基础,O(1) 查找的核心
- **Hash function**(哈希函数)—— 任意长度 → 固定长度的映射
- **String interning**(字符串驻留)—— 把重复字符串合并成单一实例

### 4.2 同级

| 方案 | 速度 | 防碰撞 | 何时用 |
|---|---|---|---|
| 直接字符串比较 | O(N) × 字符串长度 | 完美 | N < 100 |
| FNV-1a hash | O(1) ~10ns | 概率 | HH 选了这个 |
| xxHash | O(1) ~1ns | 概率 | 大数据流 |
| SipHash | O(1) ~100ns | 概率 + 防 DoS | 不可信输入 |
| Trie(字典树) | O(L) | 完美 | 前缀查找 |
| Perfect hashing | O(1) | 完美 | 静态数据集 |

**详细对比**:

- **字符串比较 vs hash**:字符串比较是 O(L)(L 是长度),哈希是 O(L) 算一次 + O(1) 查 N 次。当查找次数 > 1 时,hash 赢
- **Trie vs HashMap**:Trie 支持前缀查找(`"wall*"`),HashMap 不支持。但 Trie 内存大
- **Perfect hashing**:用 gperf 等工具预先算"完美哈希"(零碰撞),但只能用于静态数据集(标签集合不变)

### 4.3 下级

- **FNV offset / prime** — 哈希常数
- **XOR / 乘法** — 哈希核心操作
- **HashMap open addressing** — std::collections::HashMap 内部
- **BuildHasherDefault** — Rust 让自定义 hasher 接入 HashMap
- **wrapping_mul** — 显式整数溢出语义

## 5 · 对照与变奏

### 同一问题在不同语言的实现

**问题**:字符串作为 key 的高速查找。

| 语言 | 推荐做法 | 特点 |
|---|---|---|
| Rust | HashMap + 自定义 Hasher | 零开销抽象 |
| C++ | `std::unordered_map<string, V>` | 默认哈希慢 |

### 历史演化

- **1950s**:Hash table 概念提出(Hans Peter Luhn, IBM)
- **1960s**:各种 hash function 出现
- **1991**:FNV 提出(Fowler, Noll, Vo)
- **2010s**:xxHash、HighwayHash、AHash 等高性能哈希流行

### 哈希的应用谱

**题**:为什么 Rust 默认 `HashMap<String, V>` 不适合游戏资产查找?给出三个理由。

**参考解答**:

1. **慢**:SipHash 1-3 ~10ns/byte,比 FNV ~1ns/byte 慢 10 倍。资产查找是 hot path,慢 10 倍累积明显

### Lv2 · 动手实践

**题**:实现一个完整的 asset tag store,要求:
- `register(tag: &str, id: u32)`:注册资产
- `get(tag: &str) -> Option<u32>`:按 tag 查找
- `get_all_with_prefix(prefix: &str) -> Vec<u32>`:按前缀查找(注意:这不能用 hash 直接做,要扫描所有 tags)
- 测试:注册 3 个资产,查找 + 前缀查找都正确

完成标准:`cargo run` 输出预期查找结果。

**参考解答**:

```rust
use std::collections::HashMap;

const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

fn fnv1a(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    h
}

struct AssetStore {
    by_hash: HashMap<u64, u32>,
    // 同时维护 tags 列表,支持前缀查找
    all_tags: Vec<(String, u32)>,
}

impl AssetStore {
    fn new() -> Self {
        Self { by_hash: HashMap::new(), all_tags: Vec::new() }
    }
    fn register(&mut self, tag: &str, id: u32) {
        let h = fnv1a(tag);
        if self.by_hash.insert(h, id).is_some() {
            eprintln!("Collision or duplicate: {}", tag);
        }
        self.all_tags.push((tag.to_string(), id));
    }
    fn get(&self, tag: &str) -> Option<u32> {
        let h = fnv1a(tag);
        self.by_hash.get(&h).copied()
    }
    fn get_all_with_prefix(&self, prefix: &str) -> Vec<u32> {
        self.all_tags.iter()
            .filter(|(t, _)| t.starts_with(prefix))
            .map(|(_, id)| *id)
            .collect()
    }
}

fn main() {
    let mut store = AssetStore::new();
    store.register("wall_stone", 1);
    store.register("wall_wood", 2);
    store.register("door_wood", 3);

    println!("Exact: wall_stone = {:?}", store.get("wall_stone"));
    println!("Exact: missing = {:?}", store.get("missing"));

    let walls = store.get_all_with_prefix("wall_");
    println!("Prefix 'wall_': {:?}", walls);
    // [1, 2]

    let woods = store.get_all_with_prefix("");
    println!("All: {:?}", woods);
    // [1, 2, 3]
}
```

**关键解释**:
- `by_hash` 提供 O(1) 精确查找
- `all_tags` 提供 O(N) 前缀查找(因为 hash 不支持前缀)
- 这是 **space-time tradeoff**:多存一份 tags 列表,换取前缀查找能力
- 实际引擎用 Trie 或 Radix Tree 替代 `all_tags`,前缀查找也 O(L)

## 8 · Rust / Arch 落地代码

### 完整可跑的 FNV + AssetStore + bench

```rust
// Cargo.toml: 空,纯 std

use std::collections::HashMap;
use std::time::Instant;

const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

#[inline]
fn fnv1a(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for b in s.bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    h
}

struct AssetStore {
    by_hash: HashMap<u64, u32>,
}

impl AssetStore {
    fn new() -> Self {
        Self { by_hash: HashMap::new() }
    }
    fn register(&mut self, tag: &str, id: u32) {
        let h = fnv1a(tag);
        self.by_hash.insert(h, id);
    }
    #[inline]
    fn get(&self, tag: &str) -> Option<u32> {
        let h = fnv1a(tag);
        self.by_hash.get(&h).copied()
    }
}

fn main() {
    let mut store = AssetStore::new();
    let tags = ["wall_stone", "wall_wood", "door_wood", "torch", "fountain",
                "tree_oak", "tree_pine", "rock", "grass", "water"];
    for (i, t) in tags.iter().enumerate() {
        store.register(t, i as u32);
    }

    // 正确性测试
    assert_eq!(store.get("wall_stone"), Some(0));
    assert_eq!(store.get("torch"), Some(3));
    assert_eq!(store.get("missing"), None);
    println!("Correctness: OK");

    // 性能测试:1M 次查找
    let t0 = Instant::now();
    let mut sum = 0u64;
    for _ in 0..1_000_000 {
        sum += store.get("torch").unwrap() as u64;
    }
    let dt = t0.elapsed();
    println!("1M FNV lookups: {:?} ({:.2} ns/op)", dt, dt.as_nanos() as f64 / 1_000_000.0);
    // 应该 ~10-20 ns/op

    // 对比:直接 String HashMap(用 std default hasher)
    let mut std_map: HashMap<String, u32> = HashMap::new();
    for (i, t) in tags.iter().enumerate() {
        std_map.insert(t.to_string(), i as u32);
    }
    let t1 = Instant::now();
    let mut sum2 = 0u64;
    for _ in 0..1_000_000 {
        sum2 += *std_map.get("torch").unwrap() as u64;
    }
    let dt1 = t1.elapsed();
    println!("1M std lookups: {:?} ({:.2} ns/op)", dt1, dt1.as_nanos() as f64 / 1_000_000.0);
    // std 应该 ~30-50 ns/op

    println!("Speedup: {:.2}x", dt1.as_nanos() as f64 / dt.as_nanos() as f64);
}
```

**关键 Rust 特性**:

- `#[inline]` — `fnv1a` 和 `get` 必须 inline,避免函数调用开销
- `wrapping_mul` — 显式 overflow 语义,debug/release 一致
- `as u64` — u8/u32 转 u64,零扩展
- `.copied()` — `Option<&u32>` → `Option<u32>`,Copy 类型用

## 附录 · Hash 函数选型决策树

当你需要在项目里选 hash 函数,按这个决策树走:

```
1. 输入数据可信吗?
   ├─ 是(游戏资产、内部数据)→ 跳到 2
   └─ 否(用户输入、网络数据)→ 用 SipHash / std::DefaultHasher(防 HashDoS)

2. 数据是短字符串(<64 字节)吗?
   ├─ 是 → FNV-1a(简单、足够快)
   └─ 否 → 跳到 3

3. 数据是大数据流(MB 级)?
   ├─ 是 → xxHash 3(SIMD 加速,最快)
   └─ 否 → AHash(AES-NI 加速,通用)

4. 需要加密安全(防篡改)吗?
   └─ 是 → 这不是 hash function,是 cryptographic hash(SHA-256 / BLAKE3)
```

### 工业实践

**Bevy 引擎**:用 AHash(基于 AES-NI 的非加密 hash)。理由:游戏资产可信 + 需要 ~0.5 cycle/byte 的极速。

**Linux 内核**:多个 hash 函数。`dcache` 用 Linux 自己的 `full_name_hash`(变种 FNV);网络栈用 `jhash`(Jenkins hash);BPF map 用 `bpf_hashfn`。

**PostgreSQL**:用 `hash_any`(变种 FNV)作 internal hash。pg_catalog 用更精确的 hash 防碰撞。

**Node.js**:`V8` 的 string hash 用 32 位 FNV 变种,因为 V8 主要在 32 位平台起家。

## 附录 II · Hash 函数的数学理论

**为什么 FNV-1a 这样设计?**

FNV 的核心操作 `hash = (hash XOR byte) * prime`。这看似简单,背后的数学很深:

#### 群论角度

把 u64 看作 64 维向量空间 GF(2)^64。XOR 是这个空间的向量加法。乘 prime 是模 2^64 的标量乘法。

**好的 hash function**应该是"双射"(从输入到输出完全可逆)+ "扩散"(小输入变化导致大输出变化):

- **XOR byte**:输入字节影响 hash 的 8 个 bit(扩散)
- **乘 prime**:prime 与 2^64 互质,所以乘法是 GF(2^64) 上的双射(不丢失信息)。同时让低位的扩散"传播"到高位

经过 L 轮(输入字节数),理论上每个 hash bit 都依赖所有输入 bit(雪崩)。

#### 雪崩效应定量分析

输入 1 bit 翻转,理想 hash 输出 32 bit 翻转(50%)。FNV-1a 实测 ~48-52% 翻转率,接近理想。

#### FNV vs xxHash

为什么 xxHash 比 FNV 快 3-5 倍?

1. **SIMD**:xxHash 一次处理 16/32 字节(用 SSE/AVX),FNV 一次 1 字节
2. **多 lane 并行**:xxHash 内部 4 条 lane 并行 hash,FNV 单 lane
3. **循环展开**:xxHash 算法设计便于编译器展开

但 xxHash 实现 ~200 行,FNV ~10 行。**简单 vs 极致的 tradeoff**。

### 编译器对 hash 的优化

```rust
const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

fn fnv1a(s: &str) -> u64 { ... }
```

当 `s` 是编译期常量(如 `fnv1a("wall")`),编译器可以**完全在编译期算出**哈希值。这是 Rust 的 const fn + 编译期优化的能力。

```rust
const WALL_HASH: u64 = fnv1a_const("wall");

const fn fnv1a_const(s: &str) -> u64 {
    let bytes = s.as_bytes();
    let mut h = FNV_OFFSET;
    let mut i = 0;
    while i < bytes.len() {
        h ^= bytes[i] as u64;
        h = h.wrapping_mul(FNV_PRIME);
        i += 1;
    }
    h
}
```

这样 `WALL_HASH` 在编译期算好,运行时直接是常量,零开销。Casey 不用这招(他更喜欢运行时哈希),但工业引擎常用。

### 安全性顾虑:HashDoS

**HashDoS 攻击**:攻击者构造大量碰撞的 key,让 HashMap 退化到 O(N),CPU 跑满。

**经典案例**:
- 2003:Perl CGI script 被攻击,POST 数据全是碰撞 key
- 2011-2012:PHP, Java, Python, Ruby 都中招
- 2012:Rust 默认 hasher 改成 SipHash(带随机种子)

**游戏场景**:资产标签是开发者控制的,不是用户输入。所以**游戏 HashDoS 风险接近 0**,可以用 FNV。但如果游戏有"用户上传 mod"功能,mod 里的资产 tag 就是"半可信输入",需要更谨慎。
