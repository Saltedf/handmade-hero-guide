
# Day 650 · 调试光采样位置

> 光照系统重构后留下一个微妙 bug:**间接光"漏"到墙后**。本该被墙挡住的光,泄露到墙的另一侧。今天 Casey 调查根因——**光采样位置**(light sampling location)选错了。这是图形学的经典坑:**shadow acne**(阴影痘痕)的变种。

## 0 · 为什么要有这一天

回顾 Day 648 的光照模拟:

```rust
for surface in surfaces {
    for light in lights {
        if !raycast_blocked(surface.pos, light.pos) {
            // 光照贡献
        }
    }
}
```

`surface.pos` 是 voxel 中心,但**voxel 表面**实际占据 `voxel ± 0.5`。当 raycast 从 voxel 中心出发,经过相邻 solid voxel 时,**起点本身就在墙的"内部"**——raycast 立刻返回 "blocked",光照为 0。

这就是 shadow acne:光线从表面某点出发,因为浮点精度,起点被判断为"已经在下一个 solid 内",导致表面全部黑(自己挡自己)。

修法:**采样位置偏移**——把 raycast 起点沿表面法线偏移一小段,确保它在"外面"。

**为什么这个 bug 是图形学的"经典坑"?**

因为它有反直觉性:看起来"代码完全正确"——你从 voxel 中心射线,经过其他 voxel,逻辑无懈可击。但浮点数不是实数,有微小误差。当起点恰好在 voxel 边界上,误差让它有时落在 voxel A、有时落在 voxel B,这就是"数值不稳定"。

更深的问题是**符号错误**:raycast 应该从"外部"开始,但 voxel 中心是"内部"。如果 voxel (0,0,0) 是空气,(1,0,0) 是 solid,从 (0,0,0) 朝 +x 射线,应该立刻 hit (1,0,0) 的 -x 面。但因为浮点,起点可能算成 (0.0001, 0, 0) 或 (-0.0001, 0, 0),前者算"从 voxel 0 内",后者算"从 voxel -1 内"——如果 (-1,0,0) 也是 solid,raycast 错误地"立刻 hit"。

这类 bug 不是"代码错",是"数值方法错"。修法不在代码层,而在数学层——把"采样点从 voxel 中心移到表面 + 一点偏移",从根源避开边界。

**这个 bug 在工业图形学的普遍性**:

- **Shadow mapping**(GPU 阴影):同问题,depth buffer 精度有限,需要 bias
- **Reflection**(反射):反射光线起点要在表面外,否则自己反射自己
- **Ambient occlusion**(环境光遮蔽):采样半球方向,起点要偏移
- **Ray tracing**(光追):每个 ray hit 都要偏移,否则光线"卡"在表面

每个图形学算法都要面对这个 bug。资深图形程序员把它当"入门必修课",新手第一次遇到会调试几天。HH Day 650 把这个必修课讲透了。

心理锚点:看完今天,你能:

- 理解 shadow acne 的根因
- 应用 bias / normal offset 修复
- 用录制器可视化光采样位置
- 解释为什么浮点运算有精度边界
- 在自己的图形算法里预防类似 bug

## 1 · Casey 今天做了什么

1. 看到 bug:某些房间内表面 0 光照(完全黑)
2. 录制器画 surface.pos 和 raycast 路径——发现 raycast 起点紧贴 voxel 边界
3. 浮点误差:起点被判断为"在相邻 solid 内",raycast 立刻 hit

## 2 · 心智模型

### 类比:枪口贴墙开火

你拿枪对墙开火。如果枪口**贴在墙上**,子弹出膛瞬间"撞墙",弹道 = 0。

光线追踪同理。raycast 起点贴 voxel 边界,光线"出膛瞬间"撞下一个 voxel,看不到远处。

修法:**枪口离墙远一点**——raycast 起点沿法线偏移。

### Shadow acne 详解

考虑光照计算:

```
surface at voxel (0, 0, 0), +x 面朝外
surface.pos = (0, 0, 0)  // voxel 中心
light at (10, 5, 0)
raycast from (0,0,0) to (10,5,0)
```

理论上:光线从 voxel (0,0,0) 出发,经过 (1,0,0)、(2,0,0)... 到达光。如果中间没墙,可见。

但浮点精度下:

- 实际算 (0,0,0) 到 (10,5,0) 的射线起点
- 浮点算起点是 (0.000001, 0, 0)
- DDA 找起点 voxel:(0, 0, 0)
- 第一步:t_max_x = 1.0(到 voxel (1,0,0))
- 假设 (1,0,0) 是 air,继续
- ...

但有时候,起点被算成 (-0.000001, 0, 0),DDA 找起点 voxel:(-1, 0, 0)。如果 (-1,0,0) 是 solid(墙的另一边),raycast 立刻 hit,光照为 0。

**修法 1:沿法线偏移**

```
offset_pos = surface.pos + surface.normal * 0.01
raycast from offset_pos to light.pos
```

`surface.normal` 指向外面,+normal*0.01 让起点离 voxel 中心远一点,远离边界,浮点更稳定。

**修法 2:distance bias**

```
hit_dist = raycast(...)
if hit_dist < 0.1 { ignore }  // 太近的 hit 当作 false
```

接受"极近 hit"作为浮点误差,忽略。但容易漏真实 hit。

**修法 3:exclusion list**

raycast 时,跳过"起点 voxel 和邻居"。但代码复杂。

Casey 选修法 1——简单,稳定。

### 为什么 epsilon 不是 0.001 或 0.1

太小(0.001):浮点误差仍可能让起点超出 epsilon,acne 复发。
太大(0.1):光线起点离表面太远,可能"穿过"薄墙(厚度 < 0.1)。

工程经验:0.01 是 trade-off 平衡点。

## 3 · 四域深入

### 3.1 · 游戏编程视角

shadow acne 在游戏里的历史:

- **Quake 1**(1996):lightmap baking 时大量 shadow acne,John Carmack 写了"polygon offset" 修法
- **Doom 3**(2004):stencil shadow volume 也用 bias 防 acne
- **现代 shadow mapping**:GPU shadow pass 加 `glPolygonOffset`,标准 bias 修法

**Quake 1 的 Carmack reverse** 是个著名 trick。stencil shadow volume 算法里,通常渲染"前面"的 shadow volume;Carmack 反过来渲染"背面",绕过 depth test 的精度问题,消除 acne。这个 trick 后续被广泛采用,甚至 Doom 3 / Half-Life 2 都用。

**Doom 3 的 unified lighting**:id Software 用 stencil shadow 做动态阴影,每个光源每帧重算 shadow volume。代价高,但视觉惊艳——2004 年看到动态手电筒效果震撼全场。当然,stencil shadow 有自己的 acne 问题(精度边界),需要 bias。

**现代 shadow mapping**:几乎所有 3D 游戏都用 shadow map。硬件支持 `glPolygonOffset`,让 GPU 自动加 bias。但仍然要调参——bias 太小有 acne,太大阴影"飞离"物体(叫 peter-panning,因为物体看起来"飘"在地面)。

**Cascaded Shadow Map (CSM)**:大型开放世界用 CSM——把视锥分成 4-6 个 cascade,每个 cascade 单独 shadow map。近处 cascade 高精度,远处低精度。这是 Skyrim / Witcher 3 / Cyberpunk 2077 的标准配置。

**Ray-traced shadows**(RTX 时代):用 RT core 直接做光-三角形相交,理论上无 acne(因为连续空间,不是离散 shadow map)。但仍要 normal offset——道理和 Casey 今天的 bug 一样,数值边界永远存在。

工业教训:**shadow 是图形学的"未完之争"**——每个时代都有新技术,但都有边界 case 要处理。Casey 在 HH 用 voxel raycast,简化了"哪段 voxel 挡光",但仍要处理 raycast 起点精度。这是图形程序员永恒的修行。

### 3.2 · 图形学视角

阴影算法里的 bias 类型:

| 类型 | 公式 | 适用 |
|---|---|---|
| Constant bias | +0.001 | 简单 |
| Slope-scale bias | 0.001 * tan(theta) | 陡斜面 |
| Normal offset | +normal * epsilon | ✅ Casey 选 |
| Receiver plane bias | 沿接收平面投影 | 高质量 |

GPU shadow map 通常用 slope-scale + constant 组合。

**Shadow mapping 算法详解**(因为这是图形学最重要的算法之一):

1. **Shadow pass**:从光源视角渲染场景,只存深度(depth)到 shadow map。这是个 2D 纹理,每个像素存"光源到最近几何体的距离"。
2. **Main pass**:从相机视角渲染场景。对每个 fragment,把它从世界空间转换到光源空间,查 shadow map 比较深度。如果 fragment 深度 > shadow map 深度,说明"被遮挡",在阴影里。

**shadow acne 在 shadow mapping 里的表现**:由于 shadow map 是离散采样,某些 fragment 的深度和 shadow map 深度"差不多"——有时大于,有时小于,产生"条纹"现象。

经典图示:

```
    光源 →
     |
     v
   ┌─shadow map─┐
   │ ↓  ↓  ↓  ↓ │  ← 每个 ↓ 是 shadow map 的一个像素
   └────────────┘
   ─────────────── ← 接收表面(地板)
   |  |  |  |  |  |  |  |  ← 地板上的 fragment
   ✓  ✗  ✓  ✗  ✓  ✗  ✓  ✗  ← 因精度差异,有些被误判为"阴影"
```

这种"黑白条纹"是 shadow acne 的典型视觉。修法:加 bias,让 fragment 深度 + 0.001 再比较,确保始终"近一点"。

**slope-scale bias** 的原理:陡斜面的 fragment 在光线方向上"投影拉长",单个 shadow map 像素覆盖多个 fragment,精度更差。所以陡斜面需要更大 bias:`bias = constant + slope_factor * tan(angle)`。

Casey 在 HH 没用 shadow mapping(他用 voxel raycast),但 normal offset 是同一种思想——避开数值边界。

**Front-face culling** 是另一种修法:渲染 shadow map 时只画背面(back face),不画正面(front face)。这样 shadow map 存的是"墙的背面深度",地板 fragment 永远比这近,不会 acne。但代价:薄物体(单面)会失效。Half-Life 2 用这种技巧。

工业里最 robust 的是 **VSM(Variance Shadow Map)**:存深度平方,用切比雪夫不等式估算遮挡概率。无 acne,但内存翻倍。

### 3.3 · Linux 系统编程视角

Linux 上的"浮点精度 bug":

- **kernel timer drift**:调度器精度受 TSC 频率影响,需要 NTP 校正
- **file offset 0 vs 0.0**:fseek 接受整数,某些 libc 实现内部用 double 转换
- **TCP sequence wraparound**:32-bit 计数器溢出,要 PAWS 机制保护

这些和 shadow acne 同构——**数值精度边界**。

**Kernel timer drift 详解**:TSC(Time Stamp Counter)是 CPU 的 cycle counter,理论精确到纳秒。但 CPU 频率会变(turbo boost、节能),TSC 频率不固定。内核用 calibration 估算 TSC 频率,但估算有误差。

如果内核 timer 偏差 1 ppm(百万分之一),每天累计 86 ms。长时间跑的服务器(NFS、Kerberos)会因为时间偏差出错。NTP 协议每 64 秒校正一次,把误差控制在 0.1 ms 以内。

这和 shadow acne 同构:**精度边界问题**——理论精确,实际有误差,需要 bias / 校正机制。

**TCP sequence wraparound**:TCP 序列号 32-bit,高速网络(10 Gbps)几秒就溢出。新老 connection 的序列号可能重叠,导致数据混淆。修法:PAWS(Protect Against Wrapped Sequences),每个 packet 带 timestamp,接收方只接受更新的 timestamp。

这是"用额外信息消除精度边界"的思路——shadow acne 的 normal offset 也是"用额外偏移消除精度边界"。两者数学结构类似。

**File offset** 的微妙:`fseek(fp, 0, SEEK_SET)` 接受 long,但 glibc 内部某些路径用 fpos_t(可能是 struct)。如果你 `ftell()` 拿到位置,再 `fseek()` 回去,某些 locale 下可能错位(因为 wide character 转换)。这是数值边界导致的"看起来对实际错"。

工业教训:**所有数值边界都要 bias / safety margin**。网络协议(MTU headroom)、文件系统(block alignment)、内存(allocator guard bytes)、定时器(早 1ms 触发防漏帧),都是同一思想。Casey 在 HH 处理 shadow acne 就是这个工业思维的实例。

### 3.4 · Rust 生态视角

Rust 里浮点偏移的安全做法:

```rust
const EPSILON: f32 = 0.01;

fn raycast_with_bias(
    solid: impl Fn(Vec3) -> bool,
    surface_pos: Vec3,
    surface_normal: Vec3,
    light_pos: Vec3,
) -> bool {
    let biased = surface_pos + surface_normal * EPSILON;
    raycast(solid, biased, light_pos)
}
```

`EPSILON` 是 const,不可变,编译期内联。比 `#define EPSILON 0.01f`(C 风格)更安全。

Rust 在浮点计算上的额外工具:

```rust
// 1. checked operations(防 overflow)
let result = a.checked_add(b);  // None if overflow

// 2. saturating operations
let result = a.saturating_add(b); // clamps at MAX

// 3. NaN 检查
debug_assert!(!x.is_nan(), "NaN detected");

// 4. f64 兼容
let precise: f64 = x as f64; // 提升精度

// 5. fixed-point(完全避免浮点)
// 用 fixed crate:i32 表示 16.16 fixed-point
```

Rust 浮点有几个陷阱:

- `f32::NAN == f32::NAN` 返回 false(NaN 不等于自己)
- `f32::INFINITY - f32::INFINITY` = NaN
- `-0.0 == 0.0` 返回 true(但 bit pattern 不同)
- 整数除零 panic,浮点除零 = inf 或 NaN

工业实践:**用 `ordered_float` crate**——把 f32 包成 NotNan / Ordered 类型,编译期防 NaN。这对长期跑的服务器代码很重要(NaN 会"传染",一个 NaN 污染整个计算)。

```rust
use ordered_float::NotNan;
let x: NotNan<f32> = NotNan::new(1.0).unwrap();
let y = x + 2.0; // 不会 NaN
```

最后,**Rust 的 cargo bench** 让你方便测浮点性能:

```rust
#[bench]
fn bench_raycast(b: &mut test::Bencher) {
    b.iter(|| raycast_with_bias(/* ... */));
}
```

发现 hot spot,优化(SIMD、parallel、cache friendly)。HH Day 650 的 bias 增加了一次 Vec3 加法,看似微不足道,但每帧 1M 个 raycast 时,要确保这次加法不引入 cache miss 或 dependency stall。这种微优化是工业图形代码的日常。

## 5 · 对照与变奏

不同 epsilon 的视觉效果:

```
epsilon = 0       epsilon = 0.01    epsilon = 0.1
                                              
acne everywhere   clean shadows    light leaks
 ████████████     ████████████     ████████████
 █░░░░░░░░░░█     █              █ █          █
 █░░░░░░░░░░█     █              █ █          █
 █░░░░░░░░░░█     █              █ █          █
 ████████████     ████████████     ████████████
```

epsilon 太小:阴影里有"痘痕"(acne)。epsilon 太大:阴影从墙根"漏光"。中间值平衡。

**调参是图形程序员的日常**。每个 bias 参数都要"试值 + 跑场景 + 视觉检查"。工业实践:

- **写 debug overlay**:实时显示 bias 值,允许运行时调参(`+`/`-` 键调整)
- **多场景测试**:不同关卡 / 不同光源角度都跑一遍
- **截图对比**:同一场景不同 bias 截图,并排比较
- **commit 历史**:每个 bias 值 commit,留作 reference

工业级游戏引擎(Unreal / Unity)有"shadow bias set"——每个光源、每个材质都可设独立 bias。这是图形程序员长期调参的产物。

**bias vs accuracy 的根本权衡**:

- 加 bias → 减 acne,但牺牲精度(物体可能"飘"在地面上)
- 减 bias → 提精度,但 acne 复发

工业里"完美"的解法是**更高精度的 shadow map**(32-bit float 而不是 16-bit)。但精度翻倍 = 内存翻倍 = 性能下降。所以 bias 仍然是主流。

**Casey 在 HH 选 normal offset(0.01 米)** 的智慧:不是"最优",而是"够用且简单"。资深工程师知道"完美解法太贵",选 80% 解法。这是工程现实主义。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 epsilon 不能太小(0.0001)?为什么不能太大(1.0)?

**参考解答**:太小:浮点运算有 ~1e-6 的相对误差,0.0001 仍在误差范围内,acne 复发。太大:1 米的偏移让光线"穿过"薄墙(voxel 厚度 1 米),光"漏"到不该亮的地方。0.01 米是工程上的平衡点——比浮点误差大 1000 倍(稳定),但远小于 voxel 厚度(不穿墙)。

### Lv2 · 动手实践

**题**:实现带 bias 的 raycast,对比 bias 和不带 bias 的结果。

```rust
fn raycast_no_bias(solid, from: Vec2, to: Vec2) -> bool {
    // 直接从 from raycast
}

fn raycast_with_bias(solid, from: Vec2, normal: Vec2, to: Vec2) -> bool {
    let biased = from + normal * 0.01;
    // 从 biased raycast
}
```

构造一个边界 case:surface 在 voxel 边界,normal 指向外,验证不带 bias 时偶尔 hit(由于浮点),带 bias 时一致 miss。

**参考解答**:

```rust
use glam::Vec2;

fn raycast_dda(solid: &dyn Fn(i32, i32) -> bool, from: Vec2, dir: Vec2, max_t: f32) -> bool {
    let mut x = from.x.floor() as i32;
    let mut y = from.y.floor() as i32;
    let mut t = 0.0;
    let step_x = if dir.x > 0.0 { 1 } else { -1 };
    let step_y = if dir.y > 0.0 { 1 } else { -1 };
    let dx = (1.0 / dir.x.abs()).max(1e-6);
    let dy = (1.0 / dir.y.abs()).max(1e-6);
    let mut tx = if dir.x > 0.0 { (x as f32 + 1.0 - from.x) / dir.x }
                 else { (x as f32 - from.x) / dir.x };
    let mut ty = if dir.y > 0.0 { (y as f32 + 1.0 - from.y) / dir.y }
                 else { (y as f32 - from.y) / dir.y };
    while t < max_t {
        if solid(x, y) { return true; }
        if tx < ty { t = tx; tx += dx; x += step_x; }
        else { t = ty; ty += dy; y += step_y; }
    }
    false
}

fn main() {
    let solid = |_x: i32, _y: i32| false; // 全空 grid
    let from = Vec2::new(1.0, 1.0); // 边界上
    let dir = Vec2::new(1.0, 0.0).normalize();

    // 不带 bias:from=(1.0, 1.0) floor=(1,1),但浮点可能算成 0.9999 -> floor=(0,1)
    // 带 bias:from=(1.01, 1.0) floor=(1,1),稳定
    let normal = Vec2::new(-1.0, 0.0); // 朝外
    let from_biased = from + normal * 0.01;

    println!("No bias from={:?}: hit={}", from, raycast_dda(&solid, from, dir, 10.0));
    println!("With bias from={:?}: hit={}", from_biased, raycast_dda(&solid, from_biased, dir, 10.0));
}
```

### Lv3 · 迁移设计

**题**:实现 GPU shadow map 的 "slope-scale bias"——bias 大小根据表面法线和光源方向夹角变化:angle = acos(N · L),bias = 0.001 * tan(angle)。

**提示**:陡斜面需要更大 bias(因为像素 footprint 在光线方向上拉长)。

**推导**:shadow map 是 2D 纹理,每个像素覆盖一片世界空间。陡斜面(法线和光方向夹角大)的 fragment 在光线方向上"投影拉长",单个 shadow map 像素覆盖更多 fragment,精度变差。

数学上,光线方向 L,法线 N,夹角 θ = angle between L and N。fragment 沿 L 方向的"深度差"和像素 footprint 的关系:

```
depth_diff = pixel_size / cos(θ)
```

θ 越大,depth_diff 越大,需要的 bias 越大。

```rust
fn slope_scale_bias(n_dot_l: f32) -> f32 {
    let cos_theta = n_dot_l.max(0.01); // 防止除 0
    let theta = cos_theta.acos();
    let tan_theta = theta.tan();
    0.001 + 0.002 * tan_theta  // constant + slope-scale
}
```

工业实践:**shadow map bias 是项目后期重要调参**。艺术家会反复抱怨"这块有 acne"或"阴影飞起来",程序员调 bias 直到满意。Unreal / Unity 都有 shadow bias 暴露给美术,允许场景级别调整。

## 8 · Rust / Arch 落地代码

带 bias 的光照模拟:

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::{Vec2, Vec3};

const LIGHT_BIAS: f32 = 0.01;

#[derive(Clone, Copy)]
struct Surface {
    pos: Vec2,
    normal: Vec2,
    albedo: [f32; 3],
}

#[derive(Clone, Copy)]
struct Light {
    pos: Vec2,
    color: [f32; 3],
    intensity: f32,
}

fn raycast_dda(solid: &dyn Fn(i32, i32) -> bool, from: Vec2, to: Vec2) -> bool {
    let dir = to - from;
    let len = dir.length();
    if len < 1e-6 { return false; }
    let dir = dir / len;
    let mut x = from.x.floor() as i32;
    let mut y = from.y.floor() as i32;
    let mut t = 0.0;
    let step_x = if dir.x > 0.0 { 1 } else { -1 };
    let step_y = if dir.y > 0.0 { 1 } else { -1 };
    let dx = (1.0 / dir.x.abs()).max(1e-6);
    let dy = (1.0 / dir.y.abs()).max(1e-6);
    let mut tx = if dir.x > 0.0 { (x as f32 + 1.0 - from.x) / dir.x }
                 else if dir.x < 0.0 { (x as f32 - from.x) / dir.x }
                 else { f32::INFINITY };
    let mut ty = if dir.y > 0.0 { (y as f32 + 1.0 - from.y) / dir.y }
                 else if dir.y < 0.0 { (y as f32 - from.y) / dir.y }
                 else { f32::INFINITY };
    while t < len {
        if solid(x, y) { return true; }
        if tx < ty { t = tx; tx += dx; x += step_x; }
        else { t = ty; ty += dy; y += step_y; }
    }
    false
}

fn compute_lighting(
    solid: &dyn Fn(i32, i32) -> bool,
    surface: &Surface,
    lights: &[Light],
) -> [f32; 3] {
    let biased_pos = surface.pos + surface.normal * LIGHT_BIAS;
    let mut color = [0.0; 3];
    for light in lights {
        if raycast_dda(solid, biased_pos, light.pos) { continue; } // 被挡
        let dir = light.pos - biased_pos;
        let dist = dir.length();
        let atten = light.intensity / (1.0 + dist * dist);
        let n_dot_l = surface.normal.dot(dir / dist).max(0.0);
        color[0] += surface.albedo[0] * light.color[0] * n_dot_l * atten;
        color[1] += surface.albedo[1] * light.color[1] * n_dot_l * atten;
        color[2] += surface.albedo[2] * light.color[2] * n_dot_l * atten;
    }
    color
}

fn main() {
    let solid = |x: i32, _y: i32| -> bool { x == 5 }; // x=5 一堵墙

    let surface = Surface {
        pos: Vec2::new(2.0, 0.0),
        normal: Vec2::new(1.0, 0.0),
        albedo: [0.8, 0.8, 0.8],
    };
    let light = Light {
        pos: Vec2::new(10.0, 0.0),
        color: [1.0, 1.0, 0.9],
        intensity: 10.0,
    };

    let color = compute_lighting(&solid, &surface, &[light]);
    println!("Surface at {:?}, color: {:?}", surface.pos, color);
    // 应该非 0(光没被墙挡,墙在 x=5,光在 x=10,surface 在 x=2 < 5)
}
```

## 10 · 工程反思

Day 650 传达三个长期受益的工程教训:

**教训一:浮点不是实数**。这是数值计算最重要的认知。新手以为浮点和数学上的实数一样,实际上浮点有:

- 精度边界(7 位有效数字 for f32,15 位 for f64)
- 范围边界(overflow / underflow)
- 比较边界(`a == b` 不可靠,要用 `abs(a-b) < eps`)
- 运算不可结合(`(a+b)+c ≠ a+(b+c)` 因为舍入)

资深工程师写浮点代码时,脑子里始终有这些边界。Casey 加 0.01 的 bias,就是承认"浮点不是实数,要给安全余量"。

**教训二:边界 case 是 bug 工厂**。shadow acne 出现在 voxel 边界(恰好在两个 voxel 之间),这是典型的"边界 case"。其他例子:

- 整数溢出(INT_MAX + 1)
- 数组越界(off-by-one)
- 字符串结尾(空字符串 / 全空格)
- 时间戳边界(1970-01-01、2038-01-19、9999-12-31)
- 几何退化(面积为 0 的三角形、共线点)

工业实践:**遇到边界 case 多思考 5 分钟**。不要假设"正常 case 工作,边界也工作"。Casey 在 Day 650 演示的就是"专门处理边界"——把采样点从 voxel 中心(边界附近)移到 surface 外(安全区)。

**教训三:可视化是无价之宝**。Day 650 的 breakthrough 来自录制器画出 raycast 路径。如果不画,Casey 可能要花几小时猜"为什么这里 0 光照"。画出来,一眼看到"raycast 起点错了"。

这是 debug 的金科玉律:**让不可见的可见**。数值看不见,但画成图就看得见。Casey 在 HH 反复演示这套方法——投资可视化工具,debug 速度 10 倍提升。
