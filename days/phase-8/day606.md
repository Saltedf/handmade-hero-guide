心理锚点:看完这集,你能用 debug overlay 可视化光线轨迹,理解"可视化调试"对 raycast 的价值,能在自己写算法时主动加可视化验证。

## 1 · Casey 今天做了什么

Casey 这一天的几个动作:

## 2 · 心智模型

### 类比:跟踪 GPS 路线

GPS 给你路线,但你走错路。怎么定位?
- 看坐标:从 (lat, lon) 数字看不出哪里错
- 看地图:在地图上画路线 + 你的实际位置,立刻看到"你在第 5 个路口偏了"

光线调试完全一样——看 raycast 结果数字看不出问题,可视化光线轨迹立刻看到偏离。

### 严谨原理:光线可视化

每个 raycast 在内循环里收集"穿过的格子序列"。debug overlay 把这些格子画到屏幕上。

```rust
fn raycast_with_path(world: &World, ray: &Ray, max_dist: f32) -> (Option<HitInfo>, Vec<(i32, i32, i32)>) {
    let mut path = vec![];
    
    // ... Grid DDA 内循环
    while t < max_dist {
        path.push((cx, cy, cz));  // 记录格子
        // ... 跨格
    }
    
    (None, path)
}
```

**Debug overlay**:

```rust
fn draw_raycast_path(framebuffer: &mut Framebuffer, path: &[(i32, i32, i32)], color: RGB) {
    for (i, (x, y, z)) in path.iter().enumerate() {
        let world_pos = Vec3::new(x as f32 + 0.5, y as f32 + 0.5, z as f32 + 0.5);
        let screen_pos = world_to_screen(world_pos);
        let size = 5 - (i / 10).min(4);  // 越远越小
        framebuffer.draw_marker(screen_pos, size, color);
    }
}
```

**每行解释**:
- `path.push((cx, cy, cz))` — 记录每步格子。
- `world_to_screen(world_pos)` — 3D 世界坐标投影到 2D 屏幕。
- `size = 5 - i/10` — 步数远(光走得远)的格子画小,近的画大,区分前后。

### 双版本对比

```rust
fn debug_compare_raycasts(world: &World, ray: &Ray) {
    let (grid_hit, grid_path) = grid_dda_with_path(world, ray, 100.0);
    let (table_hit, table_path) = walktable_raycast_with_path(world, ray, 100.0);
    
    println!("Grid DDA: path {} steps, hit {:?}", grid_path.len(), grid_hit);
    println!("Walk table: path {} steps, hit {:?}", table_path.len(), table_hit);
    
    // 找不同
    for (i, (g, t)) in grid_path.iter().zip(table_path.iter()).enumerate() {
        if g != t {
            println!("  Step {}: Grid {:?} vs Table {:?}", i, g, t);
            break;
        }
    }
    
    // 可视化(假设 framebuffer 全局)
    draw_raycast_path(&mut framebuffer, &grid_path, RGB::GREEN);
    draw_raycast_path(&mut framebuffer, &table_path, RGB::RED);
}
```

Grid DDA 画绿色,walk table 画红色。两线重叠看不出差别,偏离立刻看到红色离开绿色。

### Bug 定位

Casey 跑 debug_compare,看到:
- 前 7 步:绿色和红色重合
- 第 8 步:红色偏到旁边格子(绿色继续直走,红色斜走)
- 最后:绿色命中 (5, 5, 0),红色命中 (5, 6, 0)

**原因**:walk table 用方向 bin 中心。光线方向 (0.7, 0.7, 0) 被量化到 bin 中心(可能是 (0.71, 0.71, 0))。0.71/0.71 的斜率略大于 0.7/0.7,光线略偏。

**修复**:bin 内做"局部修正"——把光线的精确方向(在 bin 内的相对位置)加到 walk table 上。复杂,Casey 暂不修(精度够用,bug 只影响极少数边缘情况)。

### 3.2 · 🎨 图形学视角

**Debug Drawing**:图形学调试的核心。所有引擎都有"draw line / draw point / draw box"接口。

**Immediate Mode**(立即可视化):

```rust
fn update(world: &World, debug: &mut DebugDraw) {
    debug.clear();  // 每帧清空
    if debug.show_rays {
        for ray in &world.active_rays {
            debug.draw_ray(ray, Color::RED);
        }
    }
    if debug.show_aabb {
        for obj in &world.objects {
            debug.draw_aabb(obj.aabb, Color::GREEN);
        }
    }
}
```

"Immediate" 指每帧重新画,不持久化。简单灵活。

**Retained Mode**(持久化可视化):存在场景里,持续显示。适合静态数据(如 nav mesh)。

### 3.4 · 🦀 Rust 生态视角

Rust 实现"可视化调试"的模式:

**1. 条件编译**:

```rust
#[cfg(feature = "debug_visuals")]

```

release 编译时不需要可视化,通过 feature flag 切换。

**2. Debug struct**:

```rust
struct DebugDraw {
    enabled: bool,
    lines: Vec<(Vec3, Vec3, Color)>,
    markers: Vec<(Vec3, Color)>,
}

impl DebugDraw {
    fn draw_ray(&mut self, ray: &Ray, color: Color) {
        if !self.enabled { return; }
        let end = ray.origin + ray.dir.scale(100.0);
        self.lines.push((ray.origin, end, color));
    }
    
    fn render(&self, framebuffer: &mut Framebuffer) {
        for (a, b, color) in &self.lines {
            framebuffer.draw_line(*a, *b, *color);
        }
    }
}
```

**3. 全局 vs 参数**:

```rust
// 全局(static)
static DEBUG: DebugDraw = ...;

// 参数(传递)
fn update(world: &World, debug: &mut DebugDraw) { ... }
```

参数更灵活(可以多实例),全局更简单。Casey 用参数。

### 可视化的精度问题

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"光线轨迹可视化"比"打印格子坐标列表"更有用?具体是哪种信息只能从可视化得到?

**参考解答**:可视化提供**空间直观**——你一眼看到"光线从左到右穿过格子,在第 8 格偏离"。打印列表给你"step 0: (0,0), step 1: (1,0), step 2: (1,1), ..."需要你**心算空间位置**才能发现偏离。

具体只能从可视化得到的信息:
- **偏离方向**(向上偏、向下偏、向左偏)
- **偏离程度**(一格、几格)
- **偏离发生的精确位置**(可视化上"红线离开绿线"的点)

打印列表给数字,可视化给图像。大脑识别图像中的"模式 / 异常"远快于识别数字序列中的异常。

### Lv2 · 动手实践

**题**:实现 2D 可视化版本——记录 Grid DDA 的格子路径,在 ASCII 图上画出来。测试:
- 光从 (0.5, 0.5) 朝 (0.6, 0.8) 射,穿 20 格
- 打印 32×32 ASCII 图,标记穿过的格子

完成标准:`cargo run` 打印 ASCII 图。

**参考解答**:

```rust
fn grid_dda_2d_with_path(ox: f32, oy: f32, dx: f32, dy: f32, max_steps: usize) -> Vec<(i32, i32)> {
    let mut cx = ox.floor() as i32;
    let mut cy = oy.floor() as i32;
    let mut path = vec![(cx, cy)];
    
    let step_x = if dx > 0.0 { 1 } else { -1 };
    let step_y = if dy > 0.0 { 1 } else { -1 };
    
    let mut t_max_x = if dx.abs() > 1e-10 { ((cx + if dx > 0 { 1 } else { 0 }) as f32 - ox) / dx } else { f32::INFINITY };
    let mut t_max_y = if dy.abs() > 1e-10 { ((cy + if dy > 0 { 1 } else { 0 }) as f32 - oy) / dy } else { f32::INFINITY };
    let t_dx = if dx.abs() > 1e-10 { 1.0 / dx.abs() } else { f32::INFINITY };
    let t_dy = if dy.abs() > 1e-10 { 1.0 / dy.abs() } else { f32::INFINITY };
    
    for _ in 0..max_steps {
        if t_max_x < t_max_y {
            cx += step_x;
            t_max_x += t_dx;
        } else {
            cy += step_y;
            t_max_y += t_dy;
        }
        path.push((cx, cy));
    }
    path
}

fn visualize_path(path: &[(i32, i32)], grid_size: usize) {
    let mut grid = vec![vec!['.'; grid_size]; grid_size];
    for (i, (x, y)) in path.iter().enumerate() {
        if *x >= 0 && *y >= 0 && (*x as usize) < grid_size && (*y as usize) < grid_size {
            let ch = if i == 0 { 'S' }  // start
                else if i == path.len() - 1 { 'E' }  // end
                else { ((i % 9) + 1) as u8 as char };  // 中间步用数字
            grid[*y as usize][*x as usize] = ch;
        }
    }
    for row in grid.iter().rev() {  // y 轴反向(顶部 y 大)
        println!("{}", row.iter().collect::<String>());
    }
}

fn main() {
    let path = grid_dda_2d_with_path(0.5, 0.5, 0.6, 0.8, 20);
    println!("Path ({} steps):", path.len());
    visualize_path(&path, 16);
}
```

## 10 · 补充材料:可视化调试的工业实践

### A.1 为什么"看到"比"读到"重要

人类大脑处理图像的速度比处理数字快几个量级。神经科学研究:

- **图像处理**:视觉皮层在 13ms 内识别图像内容
- **数字处理**:阅读和理解数字序列需要几百毫秒
- **差异识别**:看到"红线离开绿线"是直觉的,看到"path[7]=(3,4) vs path[7]=(3,5)"需要思考

这就是为什么"打印 debug"对几何 / 光线 / 物理这类空间问题效率低——大脑要把数字翻译回空间模型,慢且易错。

工业级可视化调试工具:

**游戏开发专用**:
- **RenderDoc**:GPU draw call 抓帧,可视化每个 draw
- **PIX**(Windows):DirectX 抓帧
- **Nsight**(NVIDIA):GPU profile + 抓帧
- **Tracy**:CPU/GPU profiler,实时可视化
- **optick**:类似 Tracy,开源

**通用图形**:
- **gdb image**:gdb 插件,可视化变量
- **paraview**:科学计算可视化(向量场、流场)
- **blender**:3D 模型检查(用于资产 debug)

Casey 的 Day 606 是简化版——游戏内嵌的 debug overlay,自己画线 / 点。

### A.2 实现完整 debug overlay 的工业级 API

工业级 debug overlay 通常提供"drawXXX"接口:

```rust
struct DebugDraw {
    lines: Vec<(Vec3, Vec3, Color, f32)>,  // (start, end, color, lifetime)
    points: Vec<(Vec3, Color, f32, f32)>,  // (pos, color, size, lifetime)
    boxes: Vec<(Vec3, Vec3, Color, f32)>,  // (min, max, color, lifetime)
    spheres: Vec<(Vec3, f32, Color, f32)>, // (center, radius, color, lifetime)
    text: Vec<(Vec3, String, Color, f32)>, // (pos, text, color, lifetime)
}

impl DebugDraw {
    fn draw_line(&mut self, start: Vec3, end: Vec3, color: Color, lifetime: f32) {
        self.lines.push((start, end, color, lifetime));
    }
    
    fn draw_ray(&mut self, origin: Vec3, dir: Vec3, length: f32, color: Color) {
        let end = origin + dir * length;
        self.draw_line(origin, end, color, 0.0);  // 0 = 持续到帧结束
    }
    
    fn draw_aabb(&mut self, min: Vec3, max: Vec3, color: Color) {
        // 画 AABB 的 12 条边
        // ...
    }
    
    fn draw_text_3d(&mut self, pos: Vec3, text: String, color: Color) {
        self.text.push((pos, text, color, 0.0));
    }
    
    fn update(&mut self, dt: f32) {
        // 减少 lifetime,移除过期的
        self.lines.retain(|(_, _, _, lt)| *lt > dt);
        for (_, _, _, lt) in &mut self.lines { *lt -= dt; }
        // ... 同样处理 points / boxes / 等
    }
    
    fn render(&self, framebuffer: &mut Framebuffer, view: &Mat4, proj: &Mat4) {
        // 画 lines
        for (start, end, color, _) in &self.lines {
            let screen_start = world_to_screen(start, view, proj);
            let screen_end = world_to_screen(end, view, proj);
            framebuffer.draw_line(screen_start, screen_end, color);
        }
        // ... 画其他
    }
}
```

**关键设计**:
- **lifetime**:每个 debug 元素有"存活时间"。lifetime=0 表示"只这一帧"。`update` 每帧减 dt,过期的移除。
- **3D 投影**:元素存 3D 坐标,渲染时投影到屏幕。
- **批量渲染**:所有 lines 一次性 draw(GPU 一次 draw call)。

### A.3 颜色编码的标准

工业级 debug 工具用**语义颜色**(semantic colors):

- **绿色**:正确 / 命中 / OK
- **红色**:错误 / 偏离 / 警告
- **黄色**:中间状态 / 注意
- **蓝色**:信息 / 系统数据
- **白色**:中性 / 调试数据

Casey 的 Day 606:
- Grid DDA 路径 = 绿色(参考正确)
- Walk table 路径 = 红色(怀疑有 bug)
- 重合部分:看不见(红绿重叠)
- 偏离部分:看见红色离开绿色 → 立刻定位

**颜色选择的原则**:
- 用对比色(红 vs 绿,蓝 vs 黄)
- 避免近似色(深红 vs 浅红,难分)
- 考虑色盲(8% 男性是红绿色盲,改用蓝 / 黄)

### A.4 可视化的精度问题

可视化本身是渲染,有渲染误差。要小心:

**浮点精度**:64-bit double vs 32-bit float 累积误差。可视化用 double 减少误差。

**像素离散**:可视化最终落到像素,亚像素细节看不见。放大可视化(4× supersampling)显示更多细节。

**坐标变换**:3D → 2D 投影有精度损失。透视投影远处细节小,正交投影保持尺寸但失真深度。

**解决方法**:
- 可视化用更高精度(double 而不是 float)
- 可视化用更高分辨率(4× SSAA)
- 不依赖可视化做精确判断,可视化只是"指示器"
- 可视化发现"有 bug"后,回到数字 / 单测精确验证

### A.5 debug overlay 的性能

debug overlay 不是 hot path,但仍要考虑性能:

**每帧开销**(典型):
- update(清理过期):O(N),N = 元素数
- render(画到 framebuffer):O(N × element_complexity)

如果 N = 10000 个元素,每元素 10 像素:
- 10000 × 10 = 100,000 像素操作
- 每像素 ~10 ns(blend)
- 总计 1 ms / 帧

可接受(< 16.67 ms 帧预算)。

但**debug overlay 不该在 release build 里**。用 Cargo feature 隔离(Day 201 学过):

```rust
#[cfg(feature = "debug_overlay")]
mod debug_draw;

#[cfg(feature = "debug_overlay")]
fn update_debug_overlay(state: &mut State) {
    state.debug_draw.update(state.dt);
    state.debug_draw.render(&mut state.framebuffer);
}

#[cfg(not(feature = "debug_overlay"))]
fn update_debug_overlay(_state: &mut State) {
    // no-op
}
```

Release build 编译时 debug overlay 完全消失,0 binary、0 CPU、0 攻击面。

### A.6 可视化 vs 单元测试的关系

可视化调试和单元测试不是替代关系,是互补:

**单元测试**:
- 优势:自动化,CI 跑,精确数值断言
- 劣势:只能测"想到的 case",想不到的 bug 漏掉

**可视化调试**:
- 优势:直觉发现"想不到的 bug"
- 劣势:手动,不能 CI,主观判断

工业实践:
- 单元测试覆盖已知 case
- 可视化调试发现未知 bug
- 发现后,加单元测试覆盖

Casey 的 Day 606 流程:
1. 可视化发现"walk table 在第 8 步偏离"
2. Day 607 修 bug
3. 加单元测试:每个测试方向对比 walk table 和 Grid DDA 路径
4. CI 跑测试,确保后续 refactor 不破坏

这是完整循环:**可视化 → 修 → 测试 → CI**。

### A.8 工业级工具:RenderDoc

RenderDoc 是 GPU 调试的标准工具,让我介绍它的可视化能力。

**用途**:抓 GPU 帧,看每个 draw call 的输入 / 输出。

**典型流程**:
1. 启动游戏,RenderDoc 注入
2. 按 F12 抓帧
3. 在 RenderDoc UI 浏览 draw call 序列
4. 点某个 draw,看:
   - 输入 vertex / texture / shader
   - 输出 render target
   - GPU pipeline state
5. 修改 shader / state 实时看效果

**对 debug raycast 的用处**:如果你 GPU 渲染 walk table 路径,RenderDoc 能抓帧看具体 vertex 位置。但 Casey 是 CPU 渲染,不用 RenderDoc。

类似工具:PIX(DirectX)、Nsight Graphics(NVIDIA)、Metal Debugger(Apple)。
