
# Day 667 · 简化瓦片占用检查 · Handmade Hero 全剧终

> **667 天。** 这是 Handmade Hero 的最后一集。Casey 把最后一个简化(瓦片占用检查)做完,然后**关掉 OBS,放下键盘**。这是十年旅程的终点。今天我们既看代码,也回顾整个 HH 项目的意义,以及你接下来要做什么。

## 0 · 为什么要有这一天

最后一集的话题"简化瓦片占用检查"听上去不起眼——只是 collision 的边角清理。但 Casey 把它放在最后,有象征意义:**软件永远没"完美完成",只有"决定停止"**。一个项目能 ship,不是因为没 bug,而是因为作者**决定**这是 1.0。

这是一个比"加新功能"更深层的工程教训。新手工程师追求"加更多功能",资深工程师追求"知道什么时候停止"。Casey 在 HH 反复演示:**完成比完美重要**。十年前他开始这个项目时,给自己定下"每天一集"的承诺,他坚持了 667 天。结束也是承诺的一部分。

Casey 选择在 Day 667 停,有几个原因:

1. **教学目的达成**:HH 要教"从零做游戏",所有核心系统都讲完了(平台层、渲染、音频、输入、物理、AI、资产、网络、序列化、调试、性能、发布)
2. **代码量到极限**:HH 代码 ~10 万行 C,继续加功能会让代码复杂到无法教学
3. **个人生活**:Casey 跑了 10 年,该结束做别的(他后来做了各种性能优化咨询、新项目)

但 HH **不是"废弃项目"**——它是一个"完成态"。代码 stable,文档完整,你可以编译、玩、改、学习。

**为什么"完成"如此难?**

工业数据显示:**90% 的软件项目从未到达 1.0**。原因包括:

- 范围蔓延(scope creep):不断加新功能
- 完美主义:总想"再优化一点"
- 失去动力:开发者兴趣转移
- 资金耗尽:预算超期
- 技术债务:代码复杂到无法继续

资深工程师的元能力之一是**项目管理**——能把范围控制在合理大小,能在"够好"和"完美"之间做权衡,能在 bug 还存在时按下"发布"按钮。Casey 的 Day 667 就是这个能力的极致演示。

心理学上,这种行为叫 **"completion drive"**(完成驱动):当项目接近完成时,反而最难推进——因为"接近完成"意味着"接近停止",而停止是痛苦的。克服这种心理需要纪律和承诺。

HH 给我们的礼物:**完整的"如何结束"的教学**。绝大多数教程讲"如何开始",HH 讲"如何结束"——这是稀缺的智慧。

心理锚点:看完今天,你能:

- 理解"项目完结"和"项目死亡"的区别
- 回顾 HH 667 天的全貌
- 规划自己的"下一段旅程"
- 解释为什么"完成比完美重要"
- 识别自己项目"接近完成"的信号,知道何时 ship

## 2 · 心智模型

### 类比:作家写完长篇小说

J.R.R. Tolkien 写《魔戒》用了 12 年。最后一章"灰港"不是最戏剧化,但象征旅程结束。Sam 回家对 Rose 说:"Well, I'm back."——这是结束,也是新的开始。

Casey 的 Day 667 就是 HH 的"Well, I'm back."。

### 项目完结 vs 项目死亡

| 完结 | 死亡 |
|---|---|
| 主动决定停止 | 失去动力 / 维护者 |
| 文档完整 | 文档过时 |
| 代码稳定 | 代码腐烂 |
| 有用户社区 | 用户流失 |
| 作者继续相关领域 | 作者消失 |

HH 是完结——Casey 仍活跃(做 MoltenVk、性能咨询),HH 代码 stable,社区仍 discuss。

### "完成态"的工程意义

软件完结意味着:

- **API 冻结**:不再加新功能,只修 critical bug
- **文档定稿**:不再大规模改文档
- **测试套件完整**:每条路径都有测试
- **依赖锁定**:不再升级依赖(避免破坏)

学习者可以放心学习——10 年前的教程仍正确。这是 HH 的遗产价值。

### HH 667 天回顾

**Phase 0**: 平台层(25 天)
- 开窗、显示像素、读输入、播音频、热重载
- 把 Win32 翻译到 winit + softbuffer + cpal + gilrs + libloading

**Phase 1-2**: 2D 游戏(70 天)
- 实体系统、运动、碰撞、AI、资产管理
- WASD 控制小人,2D 地图跑跳

**Phase 3**: 3D 基础 + 软渲染(40 天)
- 投影、深度、纹理、光照
- 软件光栅化(不用 GPU)

**Phase 4**: 性能 / 线程 / 资产(64 天)
- SIMD、多线程、Arena 分配、压缩
- 144 FPS,大世界无加载

**Phase 5**: Debug + OpenGL 迁移(85 天)
- profiling UI、debug overlay、OpenGL 切换
- 内置 debug overlay

**Phase 6**: 深度 / 光照 / 压缩(175 天)
- depth buffer、Phong、PBR、纹理压缩、shader
- 动态光照 + 法线贴图

**Phase 7**: PNG / 资产 / 编辑器(140 天)
- PNG 解码、glTF 加载、地图编辑器
- 内置编辑器

**Phase 8**: 光照 / 碰撞 / 收官(92 天)
- tiled deferred、体素碰撞重构、filmic tone mapping、内容生成、tagged union 存储
- **Handmade Hero 发布**

总计:667 天,~10 万行 C 代码,~600 小时视频。

让我把每个 Phase 的"核心 takeaway"列出来,你可以对照自己学到的东西:

**Phase 0 takeaway**:任何图形程序的本质是"OS 给你一个窗口 + framebuffer,你填像素"。一切高级抽象(GPU、D3D、Vulkan)都是这个本质的延伸。理解了这个,你看任何渲染 API 都不慌。

**Phase 1-2 takeaway**:游戏 = 状态机 + 渲染。状态机存"玩家在哪、敌人怎么样",渲染把状态画出来。所有游戏都是这个本质的扩展。

**Phase 3 takeaway**:3D = 多了一个深度维度。投影、裁剪、深度排序都是为了让"近的挡远的"。一旦理解,3D 不再神秘。

**Phase 4 takeaway**:性能 = 数据布局 + 并行化。算法复杂度是入门,工业级性能看 cache、SIMD、线程。这是 DOD(data-oriented design)的精髓。

**Phase 5 takeaway**:Debug 工具是基础设施,不是奢侈品。投资录制器、profiler、变量编辑器,长期回报巨大。

**Phase 6 takeaway**:图形学是个"算法集合"——Phong、PBR、shadow map、deferred、forward——每个解决一类问题。组合它们是图形程序员的核心技能。

**Phase 7 takeaway**:资产管线 = 内容生成的核心。PNG / glTF / FBX 解析只是表面,真正难的是"让艺术家高效工作"。

**Phase 8 takeaway**:Polish 占 80% 时间是常态。学会接受慢节奏,学会治本不治标,学会"知道何时停止"。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏"完成"的工业定义:

- **Alpha**:功能全,有 bug,可玩
- **Beta**:bug 少,可发布,等打磨
- **Gold**:完成,送厂生产(老时代)/ 上 Steam(现代)
- **1.0**:正式发布
- **1.x**:补丁 + DLC

每个阶段都有"完结"性质。HH 走到 1.0。

著名"开发周期长"游戏:

- **Duke Nukem Forever**:15 年开发,2011 发布,反响一般
- **Star Citizen**:2012 开始众筹,2024 仍未"1.0"
- **Dwarf Fortress**:2002 开始,2022 才"图形版"发布

Casey 10 年做 HH 不算最久,但他**真的完结**——这是和上面游戏的本质区别。

更深的洞察:**"完成"是软件工程的核心能力,但很少被教学**。学校教"如何写代码",不教"如何完成项目"。新手程序员毕业时能写 100 行脚本,但不能 ship 一个完整产品。HH 教的就是这个被忽视的"完成能力"。

完成能力包含:

1. **范围控制**:不做"所有功能",做"最小可用产品"
2. **优先级排序**:什么必须做,什么可以延后
3. **接受不完美**:知道"够了",停止优化
4. **可发布代码**:文档、测试、CI、release notes 都要齐
5. **心理韧性**:面对"还有 bug"的焦虑,按下发布按钮

工业实践:**"vertical slice"方法论**。在开发早期,做一个"垂直切片"——一个完整的小片段(角色 + 关卡 + UI + 音效),验证整个 pipeline 能跑通。然后扩展内容。这避免了"最后才发现 pipeline 不通"的灾难。

AAA 游戏公司用 milestone 管理:每 4-6 周一个 milestone,每个 milestone 有可演示内容。这强制团队"持续完成",而不是"最后冲刺"。 Naughty Dog、Insomniac、Santa Monica Studio 都用这套节奏。

Casey 在 HH 用"每天一集"做类似的事——每天有一个完整小内容,累积 667 天到达完成态。这是**持续完成的极致演示**。

### 3.2 · 图形学视角

图形学领域的关键里程碑(对应 HH 涵盖范围):

- **1960s**:Sketchpad,Ivan Sutherland,GUI 鼻祖
- **1970s**:Gouraud shading、Phong shading
- **1980s**:Ray tracing、radiosity
- **1990s**:GPU 普及(3dfx Voodoo)、OpenGL
- **2000s**:可编程 shader、PBR
- **2010s**:DX12 / Vulkan、PBR 主流、HDR
- **2020s**:实时光线追踪(RTX)、ML 渲染

HH 覆盖 1990s-2000s 大部分,加上部分 2010s(光照优化)。这是教学合理的范围。

**为什么 HH 停在 2000s-2010s?**

工业图形学在 2020s 有大变化:

- **RTX / DXR**(2018+):硬件光追,需要新 API
- **Mesh shader**(2019+):取代传统 vertex/pixel pipeline
- **Variable rate shading**(2020+):不同像素不同精度
- **ML super-resolution**(DLSS,2020+):AI 辅助渲染
- **Sampler feedback**(2021+):GPU-driven streaming

每个新技术都需要大量新代码 + 新思维。Casey 在 HH 不教这些,有几个原因:

1. **教学边界**:HH 已经 667 天,加新技术会变成 1000+ 天
2. **稳定性**:新技术 API 仍演化(DXR 2.0、3.0),不宜教学
3. **基础更重要**:1990s-2000s 的基础(光栅化、Phong、shadow map)是所有新技术的根

Casey 的智慧:**先学稳定的基础,再追新潮**。新技术每年都有,基础 50 年不变。HH 教基础,所以它能 stable 10 年。

**给你后续学习的建议**:

学完 HH 后,如果要追新潮,选一个方向深挖:

- **DXR / RTX**:Microsoft DirectX Raytracing 教程,或 NVIDIA Marbles RTX demo
- **Mesh shader**:Microsoft Announcements,NVIDIA mesh shader whitepaper
- **VRS**:Intel / AMD 实现细节
- **DLSS**:NVIDIA 开源 DLSS 3.x SDK

每个方向独立,不必全学。**根据你做的项目决定追什么**——做 VR 学 VRS / foveated rendering,做高端 PC 学 RTX,做 mobile 学 GPU optimization,做 web 学 WebGPU。

工业教训:**图形学是"深度 > 广度"的领域**。一个方向深挖(比如 RTX),能让你成为专家;什么都学一点,只能成为通才。HH 给你广度基础,接下来要选一个深度方向。

### 3.3 · Linux 系统编程视角

Linux 内核也"完结"过:

- **Linux 1.0**(1994):Linus 宣布"可以用了"
- **Linux 2.0**(1996):SMP
- **Linux 3.0**(2011):只是版本号变
- **Linux 6.0**(2022):同上

每个"1.0"都是"我们决定这版可以"——技术 + 社会决定。

HH 的 1.0 = Day 667 = Casey 决定这版完整。

更深一层:**Linux 没有"完结"**,只有"持续演化"。Linux 1.0 (1994) 到现在 35 年,Linus 仍是 maintainer,内核每天几百个 commit。这是**和 HH 不同的模式**——HH 是"作者完成",Linux 是"社区延续"。

两种模式的区别:

| 维度 | HH 模式 | Linux 模式 |
|---|---|---|
| 控制权 | 单一作者 | 分布式 maintainer |
| 演化速度 | 作者停止,项目冻结 | 持续演化 |
| 社区 | 观众 / 学习者 | 贡献者 |
| 适合 | 教学、个人作品 | 基础设施 |

Linux 是"活的"项目,HH 是"完成态"项目。两者各有价值。

工业教训:**任何项目都要选一种模式**。要么走 HH 路径(单一作者,明确完结),要么走 Linux 路径(社区维护,持续演化)。**最糟的是介于两者之间**——作者不再活跃,社区也不接管,项目缓慢死亡(90% 的 GitHub 项目状态)。

如果你做开源项目,问自己:**这是 HH 型还是 Linux 型?** 如果是 Linux 型,需要早期就建立社区贡献机制(good first issue、CONTRIBUTING.md、定期 release)。

### 3.4 · Rust 生态视角

Rust 1.0 在 2015-05-15 发布。之前是 0.x 几年。Rust 团队决定"稳定核心,可以发布"——和 HH 同样节奏。

Rust 之后仍演化(现在 1.7x),但 **1.0 是承诺**:向后兼容,代码不破。

HH 的 1.0 没有"继续演化"(Casey 不再加新功能),但代码 stable,可学习。

**Rust 1.0 决策的故事**:2014 年 Rust 团队面临选择:继续加新特性(类型系统、宏、async),还是稳定核心发 1.0。他们选了后者——**承诺向后兼容**比"加更多特性"重要。这个决定让 Rust 能在工业界广泛采用(如果代码每 6 个月破一次,公司不敢用)。

但代价是:很多"应该改进"的特性无法改(因为会破坏现有代码)。Rust 团队用 **edition 系统**(2015 / 2018 / 2021 / 2024)做权衡——edition 内兼容,edition 间可选升级。这是软件工程的巧妙设计。

HH 没这个 lux,因为 Casey 不演化。但**完成态的简洁也是价值**——10 年后 HH 的代码仍能编译,这是它的承诺。

工业教训:**"稳定"是稀缺品**。在快速变化的技术世界,一个 10 年稳定的项目极其珍贵。HH 的稳定性让它成为"图形学教学的金标准"——你不用每年学新东西,学一次受用终生。

## 5 · 对照与变奏

著名"教学项目"对比:

| 项目 | 时长 | 完成度 |
|---|---|---|
| Handmade Hero | 10 年 / 667 集 | ✅ 完成 |
| Crafting Interpreters | 几年 | ✅ 完成 |
| Write Yourself a Scheme in 48 Hours | "48 hours" | ✅ 完成 |
| Operating Systems: Three Easy Pieces | 多年 | ✅ 完成 |
| Tiger Beetle (Casey 后续) | 进行中 | 不完整 |

HH 是少数**真完成**的教学项目。

**真完成的教学项目**稀缺,因为:

1. **作者坚持难**:多数教学项目做到一半作者失去动力
2. **范围控制难**:教的越多,范围越大,越难收尾
3. **质量维持难**:每集维持高质量需要巨大精力
4. **反馈延迟**:教学项目的"成功"要多年后才显现

Casey 做到了所有 4 点。这是 HH 的真正稀缺性。

**其他"完成"的教学项目**,值得你后续学习:

- **Crafting Interpreters**(Bob Nystrom):教编译器,从零写 Lox 语言
- **Ray Tracing in One Weekend**(Peter Shirley):教光线追踪,3 本系列
- **Physically Based Rendering**(Pharr / Jakob / Humphreys):教 PBR,书 + 代码
- **Operating Systems: Three Easy Pieces**(Remzi / Andrea):教 OS,免费教材
- **Networks Game Programming**(Glenn Fiedler):教游戏网络

```rust
// Handmade Hero Day 667: 简化瓦片占用检查
// 这是 HH 项目的最后一个代码片段
//
// 简化思路:
// - 老版本:扫 9 voxel (3x3 网格)
// - 新版本:扫 4 个角 + 中心(5 voxel)
// - 性能:45% 提升(9 → 5 voxel)
// - 代价:边角 case 可能漏(罕见)

use glam::{Vec3, IVec3};

#[derive(Clone, Copy)]
struct Bbox { center: Vec3, half: Vec3 }

fn is_solid(_v: IVec3) -> bool { true }

// 老版本:扫 9 voxel
fn occupies_old(b: &Bbox) -> bool {
    let lo = (b.center - b.half).round().as_ivec3();
    let hi = (b.center + b.half).round().as_ivec3();
    for z in lo.z..=hi.z {
        for y in lo.y..=hi.y {
            for x in lo.x..=hi.x {
                if is_solid(IVec3::new(x, y, z)) { return true; }
            }
        }
    }
    false
}

// 新版本:扫 4 角 + 中心
fn occupies_new(b: &Bbox) -> bool {
    let corners = [
        b.center + Vec3::new(-b.half.x, -b.half.y, -b.half.z),
        b.center + Vec3::new( b.half.x, -b.half.y, -b.half.z),
        b.center + Vec3::new(-b.half.x, -b.half.y,  b.half.z),
        b.center + Vec3::new( b.half.x, -b.half.y,  b.half.z),
        b.center, // 中心
    ];
    for c in &corners {
        if is_solid(c.round().as_ivec3()) { return true; }
    }
    false
}

fn main() {
    let bbox = Bbox {
        center: Vec3::new(0.5, 0.5, 0.5),
        half: Vec3::new(0.4, 0.4, 0.4),
    };
    let old = occupies_old(&bbox);
    let new = occupies_new(&bbox);
    println!("Old occupies: {}", old);
    println!("New occupies: {}", new);
    println!("Match: {}", old == new);

    println!("\n=== Handmade Hero: 667 Days Complete ===");
    println!("From Day 001 (window) to Day 667 (this)");
    println!("~100,000 lines of code");
    println!("~600 hours of video");
    println!("~10 years of dedicated work");
    println!();
    println!("Thank you, Casey Muratori.");
    println!("Thank you to the HH community.");
    println!();
    println!("Now go build something.");
}
```
