
# Day 664 · 简化实体存储 第二部分

> Day 663 把 Entity struct 重构为 tagged union。今天 Casey 继续:**遍历优化**——遍历所有 Enemy 时,不用扫整个 Entity 数组,而是按变体分组。这是 ECS 的核心思想"archetype storage"的简化版。

## 0 · 为什么要有这一天

回顾 Day 663:Entity 是 enum,存一个 Vec<Entity>。AI 系统更新所有 Enemy:

```rust
for e in &mut entities {
    if let EntitySpecific::Enemy { ai_state, .. } = &mut e.specific {
        // AI 逻辑
    }
}
```

问题:**遍历所有 Entity,但只处理 Enemy**。如果场景有 1000 个 Treasure + 10 个 Enemy,AI 系统扫 1010 个,跳过 1000,效率低。

ECS 的解法:**archetype storage**。每种 Component 组合一个 archetype,Entity 按 archetype 分组。AI 系统直接遍历 `(Position, Health, AI)` archetype,跳过其他。

HH 选简化版:**按 Entity 变体分桶**。Player 在一个 Vec,Enemy 在另一个,Treasure 第三个。系统遍历自己关心的桶。

心理锚点:看完今天,你能:

- 实现 archetype-style 分桶存储
- 用 Rust enum + index 双向索引
- 优化按类型的遍历

## 1 · Casey 今天做了什么

1. 设计 `EntityStorage`:每个变体一个 Vec
2. EntityId 引用:`enum EntityRef { Player(usize), Enemy(usize), ... }`
3. 遍历:AI 系统直接 `for enemy in &storage.enemies`,无需过滤
4. 增删:加 Enemy 时 push 到 enemies Vec,记录 EntityRef
5. 测试:性能对比,大场景下分桶快 5-10 倍

## 2 · 心智模型

### 类比:图书馆

老图书馆:所有书放一排,按书号排。找"所有科幻"要扫所有书。

新图书馆:按类型分房间(科幻、历史、文学)。找"所有科幻"直接进科幻房间。

Entity 分桶同构:**按类型分桶,遍历特定类型直接看对应桶**。

### Archetype storage

ECS 的 archetype:特定 Component 组合。例:

- `(Position, Health)` 是一个 archetype
- `(Position, Health, AI)` 是另一个 archetype
- `(Position, Inventory)` 又是一个

每种 archetype 一个 Vec。系统按 archetype 查询:

```rust
for (pos, hp, ai) in storage.query::<(Position, Health, AI)>() {
    // 只遍历有这三种 Component 的 Entity
}
```

这是 ECS 的核心数据结构。

HH 简化:用 enum 变体代替 Component 组合,本质相同。

### 双向索引

```rust
struct EntityStorage {
    players: Vec<EntityCommon + PlayerData>,
    enemies: Vec<EntityCommon + EnemyData>,
    treasures: Vec<EntityCommon + TreasureData>,
    // ...
}

enum EntityRef {
    Player(usize),
    Enemy(usize),
    Treasure(usize),
}

impl EntityStorage {
    fn add_enemy(&mut self, common: EntityCommon, data: EnemyData) -> EntityRef {
        let idx = self.enemies.len();
        self.enemies.push((common, data));
        EntityRef::Enemy(idx)
    }
    fn get(&self, r: EntityRef) -> Option<&dyn HasCommon> {
        match r {
            EntityRef::Player(i) => self.players.get(i).map(|(c, _)| c as &dyn HasCommon),
            // ...
        }
    }
}
```

`HasCommon` trait 暴露 common 部分。但 dyn dispatch 有虚函数开销——HH 避开 dyn,直接 match。

### 分桶遍历

```rust
fn update_ai(storage: &mut EntityStorage, dt: f32) {
    for (common, data) in &mut storage.enemies {
        // AI 逻辑,只看 enemies
        data.ai_state = next_state(data.ai_state, common);
    }
    for (common, data) in &mut storage.bosses {
        // Boss AI
    }
    // 不扫 players / treasures,因为这些不需要 AI
}
```

遍历复杂度 O(Enemy 数),不是 O(总 Entity 数)。

### 删除的难题

分桶存储的删除比单 Vec 复杂。Vec 删除中间元素要 O(N) 移动。解法:**swap_remove**:

```rust
impl EntityStorage {
    fn remove(&mut self, r: EntityRef) {
        match r {
            EntityRef::Enemy(i) => {
                self.enemies.swap_remove(i);
                // 但 swap_remove 后,最后一个 Entity 现在在 i 位置
                // 如果有外部引用持有 EntityRef::Enemy(last_idx),它们现在指向 i
            }
            _ => {}
        }
    }
}
```

swap_remove 后 EntityRef 失效——指向 last_idx 的 ref 现在指向被删的。解法:**重定向 EntityRef**(用 EntityId 而非 index),或者**只支持尾部删除**(gameplay 难)。

工业 ECS 用 **generational index**——每个槽有"代数",删除时增加代数,旧 ref 不匹配。

```rust
struct GenerationalIndex {
    index: usize,
    generation: u32,
}

struct Slot<T> {
    generation: u32,
    data: Option<T>,
}
```

Casey 简化:用 Vec + 标记 deleted(tombstone),不实际移除。下次 compaction 时清理。

### 3.1 · 游戏编程视角

### 3.2 · 图形学视角

类似分桶:

- **GPU instancing**:同 mesh + 同 material 的实例一批画
- **Draw call batching**:同 shader 的几何合并
- **Texture atlas**:同 atlas 的纹理一次绑定

每个都是"按类型分组,批量处理"。

### 3.3 · Linux 系统编程视角

Linux 里"按类型分桶":

- **cgroup**:进程按 group 分,v2 改成 hierarchy
- **task scheduler**:CFS per-CPU runqueue
- **memory pages**:per-NUMA-node 分配

每个都是"按属性分组,提升 locality"。

### 3.4 · Rust 生态视角

Rust 里分桶存储:

```rust
struct Storage {
    players: Vec<Player>,
    enemies: Vec<Enemy>,
    treasures: Vec<Treasure>,
    // ...
}

impl Storage {
    fn iter_all(&self) -> impl Iterator<Item = EntityRef> + '_ {
        self.players.iter().enumerate().map(|(i, _)| EntityRef::Player(i))
            .chain(self.enemies.iter().enumerate().map(|(i, _)| EntityRef::Enemy(i)))
            .chain(self.treasures.iter().enumerate().map(|(i, _)| EntityRef::Treasure(i)))
    }
}
```

`chain` 把多个 iterator 串起来。Rust 零成本抽象。

## 5 · 对照与变奏

不同删除策略:

| 策略 | 复杂度 | 适用 |
|---|---|---|
| Vec::remove | O(N) | 罕见删除 |
| swap_remove | O(1) | 顺序无关 |
| Tombstone | O(1) | 周期 compaction |
| Generational | O(1) | 严格索引 |
| Linked list | O(1) | cache 不友好 |

HH 选 swap_remove + Tombstone 平衡。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 archetype storage 比单 Vec 快?

**参考解答**:单 Vec 遍历要"过滤"——每个 Entity 看一次类型,符合才处理。1000 个 Entity,只有 10 个 Enemy,AI 系统扫 1000 次但只处理 10 次,990 次浪费。archetype 分桶后,直接遍历 enemies Vec,扫 10 次处理 10 次,100% 利用率。两者复杂度 O(N) vs O(M),M = 该类型数量。

### Lv2 · 动手实践

**题**:实现 §3.4 的 Storage 分桶,加 add / remove / 遍历。

**参考解答**:

```rust
use glam::Vec3;

#[derive(Clone, Debug)]
struct Player { pos: Vec3, hp: f32 }
#[derive(Clone, Debug)]
struct Enemy { pos: Vec3, hp: f32, ai_state: u8 }
#[derive(Clone, Debug)]
struct Treasure { pos: Vec3, gold: u32 }

#[derive(Clone, Copy, Debug, PartialEq)]
enum EntityRef { Player(usize), Enemy(usize), Treasure(usize) }

struct Storage {
    players: Vec<Player>,
    enemies: Vec<Enemy>,
    treasures: Vec<Treasure>,
}

impl Storage {
    fn new() -> Self {
        Self { players: Vec::new(), enemies: Vec::new(), treasures: Vec::new() }
    }
    fn add_player(&mut self, p: Player) -> EntityRef {
        let i = self.players.len();
        self.players.push(p);
        EntityRef::Player(i)
    }
    fn add_enemy(&mut self, e: Enemy) -> EntityRef {
        let i = self.enemies.len();
        self.enemies.push(e);
        EntityRef::Enemy(i)
    }
    fn add_treasure(&mut self, t: Treasure) -> EntityRef {
        let i = self.treasures.len();
        self.treasures.push(t);
        EntityRef::Treasure(i)
    }
    fn remove(&mut self, r: EntityRef) {
        match r {
            EntityRef::Player(i) => { self.players.swap_remove(i); }
            EntityRef::Enemy(i) => { self.enemies.swap_remove(i); }
            EntityRef::Treasure(i) => { self.treasures.swap_remove(i); }
        }
    }
}

fn update_enemies_ai(storage: &mut Storage) {
    for enemy in &mut storage.enemies {
        enemy.ai_state = (enemy.ai_state + 1) % 4;
    }
}

fn main() {
    let mut s = Storage::new();
    s.add_player(Player { pos: Vec3::new(5.0, 0.0, 5.0), hp: 100.0 });
    let e1 = s.add_enemy(Enemy { pos: Vec3::new(10.0, 0.0, 10.0), hp: 30.0, ai_state: 0 });
    let _e2 = s.add_enemy(Enemy { pos: Vec3::new(15.0, 0.0, 15.0), hp: 30.0, ai_state: 0 });
    s.add_treasure(Treasure { pos: Vec3::new(20.0, 0.0, 20.0), gold: 50 });

    println!("Before AI update: enemies = {:?}", s.enemies);
    update_enemies_ai(&mut s);
    println!("After AI update:  enemies = {:?}", s.enemies);

    s.remove(e1);
    println!("After remove e1: enemies count = {}", s.enemies.len());
    println!("Enemies: {:?}", s.enemies);
    // swap_remove 后,原 e2 数据现在在 e1 索引位置
}
```

## 8 · Rust / Arch 落地代码

完整分桶存储:

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::Vec3;
use std::collections::HashMap;

#[derive(Clone, Debug)]
struct Player { pos: Vec3, hp: f32, inventory: Vec<String> }

#[derive(Clone, Debug)]
struct Enemy { pos: Vec3, hp: f32, ai_state: u8, damage: f32 }

#[derive(Clone, Debug)]
struct Treasure { pos: Vec3, gold: u32, opened: bool }

#[derive(Clone, Debug)]
struct Boss { pos: Vec3, hp: f32, phase: u8 }

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
struct EntityId(u64);

#[derive(Clone, Copy, Debug)]
enum EntityType { Player, Enemy, Treasure, Boss }

struct Slot<T> {
    generation: u32,
    data: Option<T>,
}

struct TypedStorage<T> {
    slots: Vec<Slot<T>>,
    free_list: Vec<usize>,
    id_to_index: HashMap<EntityId, (usize, u32)>, // (index, generation)
}

impl<T> TypedStorage<T> {
    fn new() -> Self {
        Self {
            slots: Vec::new(),
            free_list: Vec::new(),
            id_to_index: HashMap::new(),
        }
    }
    fn insert(&mut self, id: EntityId, data: T) {
        if let Some(&(_, gen)) = self.id_to_index.get(&id) {
            // existing id, update
            if let Some(slot) = self.slots.get_mut(gen as usize) {
                slot.data = Some(data);
            }
            return;
        }
        let (idx, gen) = if let Some(i) = self.free_list.pop() {
            let gen = self.slots[i].generation + 1;
            self.slots[i] = Slot { generation: gen, data: Some(data) };
            (i, gen)
        } else {
            let i = self.slots.len();
            self.slots.push(Slot { generation: 0, data: Some(data) });
            (i, 0)
        };
        self.id_to_index.insert(id, (idx, gen));
    }
    fn get(&self, id: EntityId) -> Option<&T> {
        let &(idx, gen) = self.id_to_index.get(&id)?;
        let slot = self.slots.get(idx)?;
        if slot.generation != gen { return None; }
        slot.data.as_ref()
    }
    fn remove(&mut self, id: EntityId) {
        if let Some(&(idx, _)) = self.id_to_index.get(&id) {
            if let Some(slot) = self.slots.get_mut(idx) {
                slot.data = None;
                self.free_list.push(idx);
            }
            self.id_to_index.remove(&id);
        }
    }
    fn iter(&self) -> impl Iterator<Item = (&EntityId, &T)> {
        self.id_to_index.iter().filter_map(|(id, &(idx, gen))| {
            let slot = self.slots.get(idx)?;
            if slot.generation != gen { return None; }
            slot.data.as_ref().map(|d| (id, d))
        })
    }
}

struct World {
    players: TypedStorage<Player>,
    enemies: TypedStorage<Enemy>,
    treasures: TypedStorage<Treasure>,
    bosses: TypedStorage<Boss>,
    next_id: u64,
}

impl World {
    fn new() -> Self {
        Self {
            players: TypedStorage::new(),
            enemies: TypedStorage::new(),
            treasures: TypedStorage::new(),
            bosses: TypedStorage::new(),
            next_id: 1,
        }
    }
    fn new_id(&mut self) -> EntityId {
        let id = EntityId(self.next_id);
        self.next_id += 1;
        id
    }
    fn spawn_player(&mut self) -> EntityId {
        let id = self.new_id();
        self.players.insert(id, Player {
            pos: Vec3::new(5.0, 0.0, 5.0), hp: 100.0, inventory: Vec::new(),
        });
        id
    }
    fn spawn_enemy(&mut self, pos: Vec3) -> EntityId {
        let id = self.new_id();
        self.enemies.insert(id, Enemy {
            pos, hp: 30.0, ai_state: 0, damage: 5.0,
        });
        id
    }
    fn update_enemies(&mut self) {
        for (_, enemy) in self.enemies.iter_mut() {
            enemy.ai_state = (enemy.ai_state + 1) % 4;
        }
    }
}

// iter_mut 需要 Mutable extension(为简洁,在 main 里用 for + get_mut)
impl World {
    fn enemies_iter_mut(&mut self) -> impl Iterator<Item = &mut Enemy> {
        self.enemies.slots.iter_mut().filter_map(|s| s.data.as_mut())
    }
}

fn main() {
    let mut world = World::new();
    let _p = world.spawn_player();
    let e1 = world.spawn_enemy(Vec3::new(10.0, 0.0, 10.0));
    let _e2 = world.spawn_enemy(Vec3::new(15.0, 0.0, 15.0));

    println!("Initial enemies: {}", world.enemies.id_to_index.len());
    for (id, enemy) in world.enemies.iter() {
        println!("  {:?}: pos={:?}, hp={}, ai={}", id, enemy.pos, enemy.hp, enemy.ai_state);
    }

    // 更新所有 Enemy AI(用 mut iter)
    for enemy in world.enemies_iter_mut() {
        enemy.ai_state = (enemy.ai_state + 1) % 4;
    }

    println!("\nAfter AI update:");
    for (id, enemy) in world.enemies.iter() {
        println!("  {:?}: ai={}", id, enemy.ai_state);
    }

    // 删除
    world.enemies.remove(e1);
    println!("\nAfter remove e1: {} enemies", world.enemies.id_to_index.len());
}
```

## 10 · 工程反思

Day 664 传达的核心工程教训:**Entity storage 设计是 ECS 性能关键**。

新手用 `Vec<Entity>`(array of struct),资深工程师用 `Struct of Arrays`(SoA)或 sparse set。差别是 cache 性能——`Vec<Entity>` 100 个 entity,只查 Position 时,把整个 Entity(可能 100+ bytes)载入 cache,浪费。SoA 只载 Position 数组,cache 效率高 10 倍。

**存储 layout 对比**:

```rust
// AoS(Array of Structs):OO 风格
struct Entity { pos: Vec3, vel: Vec3, hp: f32 }
let entities: Vec<Entity> = ...;
// 查询 Position:每个 Entity 32 bytes,cache 浪费

// SoA(Struct of Arrays):DOD 风格
struct World {
    pos: Vec<Vec3>,
    vel: Vec<Vec3>,
    hp: Vec<f32>,
}
// 查询 Position:只载 pos,cache 完美
```

SoA 是 SIMD 友好(连续 float 数组,SIMD 一次处理 4-16 个)。PS3 / Xbox 360 时代(2005-2013)SoA 成为主流。

**Sparse set ECS**:

如果 entity 没所有组件(每个 entity 只有一部分),SoA 浪费内存(空 slot)。Sparse set 解决:每个组件类型单独 sparse set,entity ID → component 查询。

bevy / Unity DOTS / Unreal Mass 都用 sparse set 变体。这是现代 ECS 标准。

**Casey 在 HH 的演化**:

- 早期:`Entity` 大 struct,所有字段
- 中期:tagged union,variant 存不同类型
- Day 664:sparse set 风格,组件独立存储

每一步都更 cache friendly。

**第二条教训**:**component 设计要"小而精"**。

新手把所有相关字段塞一个 component(`Player { pos, vel, hp, inventory, skills }`),资深工程师拆成多个(`Position / Velocity / Health / Inventory / Skills`)。原因:

- **小 component** = cache 友好
- **多 component** = 灵活组合(不是所有 player 都有 Inventory)
- **query 高效** = 只查需要的 component

bevy 的 ECS 强制这种"小而精"。每个 component 单独 struct。

**第三条教训**:**Archetype 是 ECS 优化**。

Archetype = "有相同组件集合的 entity"。ECS 把同 archetype entity 存一起,query 时跳过整个 archetype。

Unity ECS 用 archetype 主导,bevy 用 sparse set。两者各有 trade-off。学懂 archetype,你看 Unity ECS 性能优化有新视角。

**迁移到其他领域**:

"SoA / sparse set"思路在多处通用:

- **数据库**:columnar storage(PostgreSQL cstore / ClickHouse)
- **数据分析**:Apache Arrow / Parquet
- **ML**:tensor layout(NCHW vs NHWC)
- **科学计算**:NumPy ufunc
- **大数据**:Spark SQL columnar format

每个领域都有"按列存储"的优化。Casey 在 HH 演示的是 ECS 版本。

这种哲学在工业化"用引擎 + 用框架"的时代尤其珍贵。学完 HH 你不只会写游戏,你**理解游戏**。这是 HH 最大的价值。

## N0 • 深度教学补充

### 核心概念重新梳理

Day 664 涉及的核心概念需要在多个层次上理解:

**第一层:直观理解**

新手第一次接触概念,需要建立直觉。例如 voxel collision 是"虚拟物体不能穿过虚拟墙"——这个直觉每个人都能从现实经验获得。

**第二层:数学理解**

把直觉形式化。collision = "两个几何体的体积有交集"。对于 AABB,这等价于"三轴投影都重叠"。

**第三层:工程理解**

数学正确不等于工程实现正确。要考虑:

- 浮点精度边界
- 性能(每帧 N 个查询)
- 内存(数据结构紧凑)
- 边角 case(无穷大、NaN、负数)

**第四层:工业理解**

工业级要再加:

- 多线程安全
- SIMD 优化
- 网络同步(多人游戏)
- 跨平台(Windows/Mac/Linux/Mobile)
- 可访问性(色盲友好)
- 反作弊

每层理解都让代码更鲁棒。资深工程师在所有层次同时思考。

### 实际工程的细节

工业代码 80% 是"边角 case 处理",20% 是"核心算法"。Casey 在 HH 演示核心,工业代码加大量边角处理。

**边角 case 类型**:

1. 空输入(空 Vec、null pointer)
2. 极端输入(NaN、无穷大、超大数)
3. 并发竞争(多线程同时访问)
4. 资源不足(内存满、磁盘满)
5. 网络异常(超时、断连、包丢失)
6. 版本不兼容(老配置 / 新代码)
7. 权限错误(只读文件、无网络)
8. 用户误操作(连点、撤销重做)

每个 case 都要单独处理。这是工业代码 50%+ 行数的原因。

### 优化思路

性能优化有顺序:

1. **算法**:O(N²) → O(N log N),最大提升
2. **数据结构**:Vec → HashMap / BTreeMap,常数提升
3. **Cache**:AoS → SoA,cache 命中提升
4. **SIMD**:4-16 元素并行,巨大常数提升
5. **GPU**:数千核并行,极致性能
6. **分布式**:多机器,无限扩展

每级提升都需要更复杂的代码。先优化低级,够用再升级。

- **简单 > 复杂**:够用就行
- **理解 > 记忆**:概念比代码重要
- **完成 > 完美**:能跑 > 能优化
- **持续学习**:技术永远在演化

这些哲学跨技术领域通用。学完 HH,你不只会写游戏,你**理解工程**。这是 HH 最大的价值。

### Rust 视角

Day 664 用 C 写,但 Rust 版本会更安全 / 更高效:

- **所有权**:消除 use-after-free / double-free

- **match exhaustive**:case 漏写编译错
- **Result<T, E>**:错误显式处理
- **no null**:Option<T> 强制 null 检查
- **fearless concurrency**:多线程安全

每条都让代码更鲁棒。Rust 是游戏开发的新趋势(bevy / wgpu / rend3),学习 Rust 让你未来 10 年受益。
