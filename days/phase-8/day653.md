# Day 653 · 加电影级响应曲线

> 光照计算出来的颜色是**线性**的(linear RGB),但显示器的响应是**非线性**的。直接显示线性值,亮处过曝,暗处死黑。今天 Casey 加 **filmic tone mapping**(电影级色调映射)——用一条曲线把线性 HDR 颜色压回 LDR 显示范围,同时保留亮暗细节。

## 0 · 为什么要有这一天

回顾渲染管线:

```
光照计算(linear RGB,可能 > 1.0)
→ gamma 校正
→ 显示器(sRGB,0-255)
```

光照可能产生亮度 5.0(HDR,high dynamic range),但显示器只能显示 0-1(LDR)。如果直接 clamp 5.0 → 1.0,亮处全白,无细节。

**Tone mapping**(色调映射)解决:用一条"软"曲线把 HDR 压回 LDR,既不丢亮处细节,也不丢暗处细节。

**Filmic tone mapping**(电影级)是工业标杆,模仿真实胶片的响应曲线。最著名的实现是 Uncharted 2 的 **John Hable curve**(简称 "Hable curve" / "Uncharted 2 tone mapper")。

要理解为什么 tone mapping 如此重要,需要先理解**HDR vs LDR**:

- **HDR(High Dynamic Range)**:颜色值可以是任意正数(0.5、5.0、100.0)。物理光强就是任意数——太阳是 100,000 lux,室内灯是 500 lux,差 200 倍。
- **LDR(Low Dynamic Range)**:颜色值限定 [0, 1]。显示器物理只能显示这个范围(每个 channel 8 bit = 256 级)。

物理世界是 HDR,显示器是 LDR。中间需要一个 mapping。最简单的 mapping 是 **clamp**:`display = clamp(linear, 0, 1)`——但这丢失所有 >1 的信息,亮处全白。

好一点的 mapping 是 ** Reinhard**:`display = linear / (1 + linear)`——这是渐进压缩,亮度 5 → 0.83,亮度 100 → 0.99。但 Reinhard 让中间调"褪色"。

**Filmic** 曲线模仿真实胶片——胶片对中间调响应好,对极端值"软压缩"。视觉上"自然",像电影。这是 Hollywood 数十年的标准。

为什么"像电影"是好事?因为**人眼习惯了电影的视觉语言**。100 年的电影工业训练观众"看这种曲线 = 看故事"。游戏跟随这个标准,玩家潜意识"代入感"强。这是艺术 + 工程的结合。

ACES(American Cinema Editors)是更新的标准——好莱坞色彩委员会定的,跨电影 / 电视 / 流媒体统一。游戏业 2015 后大量采用,因为 ACES 处理高光更优雅(蓝天 → 浅蓝过渡自然,不"碎")。

心理锚点:看完今天,你能:

- 解释线性 vs 非线性色彩
- 应用 Hable / ACES / Reinhard tone mapping
- 理解为什么游戏画面需要 tone mapping
- 区分 gamma 校正 vs tone mapping(两件事!)
- 调参 tone mapper,达到"电影感"

## 2 · 心智模型(深度)

### Gamma 校正 vs Tone mapping:关键区分

新手常混淆两件事:

- **Gamma 校正**:linear ↔ sRGB 的转换,**只是编码**(数学:`sRGB = linear^(1/2.2)`)
- **Tone mapping**:HDR → LDR 的压缩,**改变内容**(高亮被压低)

为什么需要 gamma 校正?人眼对暗处更敏感(进化适应夜间),所以显示器给暗处更多 bit。linear 空间均匀分布 bit,暗处只有少数 bit。sRGB 空间用幂函数,**暗处 bit 多**。

数学:linear 0.5(中间灰)在 sRGB 大约是 0.735。`sRGB = linear^(1/2.2) = 0.5^0.4545 ≈ 0.735`。

工作流:

```
linear space:        linear = 5.0 (HDR light)
       ↓ tone mapping (HDR → LDR)
linear compressed:   linear = 0.8 (still linear, but in display range)
       ↓ gamma correction (linear → sRGB)
sRGB output:         sRGB = 0.8^(1/2.2) ≈ 0.906 (to monitor)
```

注意:**tone mapping 在 linear 空间,gamma 是最后一步**。顺序反了就出错。

### 色彩空间基础

每个色彩空间定义"颜色编码":

- **linear RGB**:物理光强度,值可以是任意正数
- **sRGB**:显示器标准,值 [0, 1],幂函数编码
- **Rec.709**:HDTV 标准,类似 sRGB 但略不同
- **Rec.2020**:UHD 标准,更广色域
- **ACEScg / ACEScc**:电影制作标准,广色域

不同色彩空间转换有精度损失。游戏工业通常在 linear sRGB 渲染,输出 sRGB。HDR 项目用 Rec.2020 或 ACEScg。

### Tone mapping 的数学

每个 tone mapper 是一个**单调递增函数** `f: [0, ∞) → [0, 1]`。要求:

1. `f(0) = 0`(黑 → 黑)
2. `f(∞) = 1`(无穷亮 → 白,不溢出)
3. 单调递增(亮 → 更亮)
4. 中间调对比度好(不"褪色")

**Reinhard 公式**:`f(x) = x / (1 + x)`,最简单的满足上述条件的函数。

**Hable 公式**:多项式拟合胶片响应,公式更复杂但视觉更"电影感"。

**ACES 公式**:有理函数,模仿胶片+数码混合响应。

每个公式都有参数(exposure、contrast、shoulder strength)。资深图形程序员调参到满意,可能花数天。



### 类比:手机相机的 HDR

手机相机拍逆光照片:

- 不开 HDR:人脸黑(暗处细节丢),背景白(亮处过曝)
- 开 HDR:多张曝光合成,人脸清楚(暗处保留),背景云朵也清楚(亮处保留)

tone mapping 类似——把"亮暗差很大"的光照,压缩到显示器能表达的"亮暗差有限"范围。

### 为什么需要 tone mapping

物理世界的亮度范围极大:

- 阳光直射:10^5 cd/m²
- 室内灯:10^2
- 月光:10^0
- 全黑:0

比值 10^5 = 100000 倍。

显示器能表达范围:

- 最亮:300 cd/m²(典型)
- 最暗:0.5 cd/m²

比值 600 倍。

物理世界 100000 倍 vs 显示器 600 倍——直接 1:1 映射不行,必须**压缩**(tone map)。

### Reinhard tone mapping(简单版)

最简单的 tone mapping:

```
color_tm = color / (1 + color)
```

效果:小 color 几乎不变,大 color 趋近 1.0(不到 1)。一条"软"压缩曲线。

```
color = 0   → 0 / 1 = 0       (暗处不变)
color = 0.5 → 0.5 / 1.5 = 0.33 (中亮稍压)
color = 1   → 1 / 2 = 0.5      (1.0 → 0.5)
color = 5   → 5 / 6 = 0.83     (5.0 → 0.83)
color = 10  → 10 / 11 = 0.91   (10.0 → 0.91,饱和)
```

Reinhard 简单但亮处不够"平"——大量亮值挤在 0.8-1.0 区间。

### Hable curve(Uncharted 2)

John Hable 在 GDC 2010 提出:

```
A = shoulder_strength  (0.22)
B = linear_strength    (0.30)
C = linear_angle       (0.10)
D = toe_strength       (0.20)
E = toe_numerator      (0.01)
F = toe_denominator    (0.30)
linear_white = 11.2

def hable(x):
    return ((x*(A*x+C*B)+D*E) / (x*(A*x+B)+D*F)) - E/F
```

曲线分三段:**toe(暗部)**,**linear(中段)**,**shoulder(亮部)**。toe 把暗处提亮一点(看清楚),shoulder 把亮处压平一点(不过曝),中段几乎不变(自然对比)。

```
       shoulder
       /
      /
─────/─── linear
    /
   /
  toe
```

### ACES curve(电影标准)

Academy Color Encoding System 是电影行业标准,2020+ 游戏普遍采用。简化版 Narkowicz fit:

```
def aces(x):
    a = 2.51
    b = 0.03
    c = 2.43
    d = 0.59
    e = 0.14
    return clamp((x*(a*x+b)) / (x*(c*x+d)+e), 0, 1)
```

ACES 比 Hable 颜色更"暖",电影感更强。Unreal、Unity 默认 tone mapper 都是 ACES。

### Exposure(曝光)

tone mapping 前通常先乘 exposure:

```
color_exposed = color * exposure
color_tm = tone_map(color_exposed)
```

`exposure > 1`:整体变亮(玩家拿手电筒)
`exposure < 1`:整体变暗(玩家在黑暗环境)

游戏里 exposure 可以**自动调节**(eye adaptation)——根据场景平均亮度调整,模拟人眼适应黑暗 / 光亮。

### Tone mapping 在管线的位置

```
1. 光照计算(linear,可能 HDR)
2. Bloom(可选,亮度 > 阈值的部分模糊 + 叠加)
3. Tone mapping(本次)← linear HDR → linear LDR
4. Gamma 校正 ← linear → sRGB
5. 显示器
```

tone mapping 在 bloom 之后(用 HDR 算 bloom,看起来真实)、gamma 之前(避免在 sRGB 空间算色调)。

### Linear workflow

整个渲染管线应该是"线性"的:

- 光照计算:**linear RGB**(光的物理叠加)
- 颜色混合:**linear**(alpha blending 必须在线性空间)
- Tone map:**linear HDR → linear LDR**
- Gamma 校正:最后一步,**linear → sRGB**(为显示器准备)

如果不在线性空间计算(比如直接用 sRGB 纹理做光照),光照会偏暗 / 偏色,这是新手最常犯的错。

### 3.4 · Rust 生态视角

Rust tone mapping 实现:

```rust
fn tone_map_reinhard(x: f32) -> f32 {
    x / (1.0 + x)
}

fn tone_map_aces(x: f32) -> f32 {
    let a = 2.51; let b = 0.03; let c = 2.43; let d = 0.59; let e = 0.14;
    let num = x * (a * x + b);
    let den = x * (c * x + d) + e;
    (num / den).clamp(0.0, 1.0)
}

fn tone_map_hable(x: f32) -> f32 {
    let a = 0.22; let b = 0.30; let c = 0.10; let d = 0.20; let e = 0.01; let f = 0.30;
    let num = x * (a * x + c * b) + d * e;
    let den = x * (a * x + b) + d * f;
    let linear_white = 11.2;
    let white = ((linear_white * (a * linear_white + c * b) + d * e) /
                 (linear_white * (a * linear_white + b) + d * f)) - e / f;
    ((num / den) - e / f) / white
}
```

ACES 在 GPU fragment shader 用 GLSL:

```glsl
vec3 aces(vec3 x) {
    const float a = 2.51, b = 0.03, c = 2.43, d = 0.59, e = 0.14;
    return clamp((x * (a * x + b)) / (x * (c * x + d) + e), 0.0, 1.0);
}
```

## 5 · 对照与变奏

不同 tone mapper 的曲线对比:

```
1.0 ┌─────────────────────────────────
    │                       ACES ─ ─ ─
    │                  Hable ─── ─
    │             Reinhard ────
0.5 │          ────────
    │     ─────
    │ ────
    │
0.0 └─────────────────────────────────
    0     1     2     3     4    5
                input color
```

Reinhard 上升最快(快速到饱和),Hable 中等,ACES 最平缓(保留更多亮处细节)。

**Tone mapper 的历史演化**:

- **2000s 早期**:无 tone mapping,直接 clamp。LDR 渲染,bloom 用 blur 模拟 HDR
- **2002 Reinhard**:论文 "Photographic Tone Reproduction for Digital Images"。第一个广泛使用的 tone mapper
- **2010 Hable**:Uncharted 2 团队发 GDC 演讲,"Filmic Tonemapping for Real-Time Renderers"。游戏行业标准
- **2014 ACES**:好莱坞委员会发布,跨媒体统一。游戏从 Hable → ACES
- **2020s**:Microsoft DirectX 12 / Vulkan 支持 HDR10 显示器,tone mapping 适配 HDR output

工业实践:**ACES 是现代游戏默认**。Unreal / Unity 都内置 ACES。Hable 仍用于老项目兼容。Reinhard 用于简单 demo。

**为什么 ACES 比其他好?**

ACES 是好莱坞"色彩科学家"设计的——经过严格测试,人眼主观偏好。它的曲线特点:

- 中间调对比度合适(电影感)
- 高光柔和过渡(蓝天 → 浅蓝自然)
- 阴影保留细节(不死黑)

这些特点来自胶片响应的物理建模。胶片 100 年的演化让"观众审美"和"胶片响应"互相适应——ACES 模仿胶片,所以观众喜欢。

**HDR 显示器时代**(2020s):

传统 LDR 显示器 8 bit / channel,HDR 显示器 10-12 bit。游戏渲染后,HDR 显示器能直接显示 1000+ nit 亮度(OLED)。tone mapping 不再"压缩到 LDR",而是"压缩到显示器实际亮度范围"。

但 HDR 显示器普及慢(2024 仍 5% 用户),所以多数游戏仍按 LDR tone map + HDR output 处理。这是过渡期。

**未来 tone mapping**:

- **Local tone mapping**:不同区域不同曲线(眼睛适应)
- **ML-based**:神经网络学习最优映射
- **Perceptual**:基于人眼感知模型

每个方向都有研究,但 ACES 仍是工业 baseline。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 tone mapping 必须在 gamma 校正之前?

**参考解答**:tone mapping 是**线性空间**内的操作(把 linear HDR 压到 linear LDR)。gamma 校正是 linear → sRGB 的非线性变换。如果在 gamma 之后做 tone map,tone map 在 sRGB 空间算,数学不对——sRGB 空间的"线性插值"会偏色,tone map 的曲线也会失真。线性 workflow 要求所有计算在线性空间,gamma 是最后一步。

### Lv2 · 动手实践

**题**:实现三种 tone mapper,画出值表:

```rust
fn main() {
    let test_values = [0.0, 0.1, 0.5, 1.0, 2.0, 5.0, 10.0];
    for x in test_values {
        println!("x={:5.1}: Reinhard={:.3} Hable={:.3} ACES={:.3}",
            x,
            tone_map_reinhard(x),
            tone_map_hable(x),
            tone_map_aces(x));
    }
}
```

**参考解答**:

```rust
fn tone_map_reinhard(x: f32) -> f32 { x / (1.0 + x) }

fn tone_map_aces(x: f32) -> f32 {
    let (a, b, c, d, e) = (2.51, 0.03, 2.43, 0.59, 0.14);
    let num = x * (a * x + b);
    let den = x * (c * x + d) + e;
    (num / den).clamp(0.0, 1.0)
}

fn tone_map_hable(x: f32) -> f32 {
    let (a, b, c, d, e, f) = (0.22, 0.30, 0.10, 0.20, 0.01, 0.30);
    let num = x * (a * x + c * b) + d * e;
    let den = x * (a * x + b) + d * f;
    let linear_white = 11.2;
    let white_num = linear_white * (a * linear_white + c * b) + d * e;
    let white_den = linear_white * (a * linear_white + b) + d * f;
    let white = white_num / white_den - e / f;
    (num / den - e / f) / white
}

fn main() {
    let test_values = [0.0, 0.1, 0.5, 1.0, 2.0, 5.0, 10.0];
    println!("  x  | Reinhard | Hable  | ACES");
    println!("-----|----------|--------|------");
    for x in test_values {
        println!("{:5.1} | {:8.3} | {:6.3} | {:6.3}",
            x,
            tone_map_reinhard(x),
            tone_map_hable(x),
            tone_map_aces(x));
    }
}
```

预期:Reinhard 上升最快,ACES 最慢但更"柔"。

### Lv3 · 迁移设计

**题**:加 exposure 控制:`tone_map(x * exposure)`。在游戏中按 +/- 调 exposure,看亮度变化。exposure 在 0.1 / 0.5 / 1.0 / 2.0 / 5.0 时画面差别?

**提示**:exposure 高,亮处快速 tone map 到 1.0(饱和),暗处变亮。exposure 低,暗处更暗(死黑)。

**进阶**:实现"自动曝光"(auto exposure / eye adaptation)——每帧统计画面平均亮度,exposure 平滑趋近"目标 exposure"(让平均亮度 = 0.5)。

```rust
fn compute_target_exposure(avg_luminance: f32) -> f32 {
    // 目标:让 tone map 后平均亮度 = 0.5
    // 反解:0.5 = tone_map(avg * exp) → exp = ?
    // 简化:exp = 0.5 / (avg + 1e-6)
    0.5 / (avg_luminance + 1e-6).max(0.01)
}

fn update_exposure(current: f32, target: f32, dt: f32, adaptation_speed: f32) -> f32 {
    // 平滑过渡,避免"亮度跳变"
    current + (target - current) * (1.0 - (-adaptation_speed * dt).exp())
}
```

`adaptation_speed` 控制眼睛适应速度——0.5 = 慢(模拟人眼),2.0 = 快(游戏感觉)。Crysis / Far Cry 用类似系统,玩家从亮处走到暗处,画面渐变暗,人眼"适应"。这是 immersive 关键。

**工业细节**:自动曝光计算需要"luminance histogram",不是简单平均(否则被极亮像素主导)。Unity / Unreal 提供"eye adaptation"组件,内置 histogram + auto exposure。

## 8 · Rust / Arch 落地代码

完整 tone mapping demo:

```rust
// Cargo.toml: 无依赖(纯数学)

fn tone_map_reinhard(x: f32) -> f32 {
    x / (1.0 + x)
}

fn tone_map_aces(x: f32) -> f32 {
    let (a, b, c, d, e) = (2.51_f32, 0.03, 2.43, 0.59, 0.14);
    let num = x * (a * x + b);
    let den = x * (c * x + d) + e;
    (num / den).clamp(0.0, 1.0)
}

fn tone_map_hable(x: f32) -> f32 {
    let (a, b, c, d, e, f) = (0.22_f32, 0.30, 0.10, 0.20, 0.01, 0.30);
    let num = x * (a * x + c * b) + d * e;
    let den = x * (a * x + b) + d * f;
    let lw = 11.2_f32;
    let white = (lw * (a * lw + c * b) + d * e) / (lw * (a * lw + b) + d * f) - e / f;
    (num / den - e / f) / white
}

// linear → sRGB approx(2.2 gamma)
fn linear_to_srgb(x: f32) -> f32 {
    if x <= 0.0031308 { 12.92 * x } else { 1.055 * x.powf(1.0 / 2.4) - 0.055 }
}

fn render(color: [f32; 3], exposure: f32) -> [u8; 3] {
    // 1. exposure
    let exposed = [color[0] * exposure, color[1] * exposure, color[2] * exposure];
    // 2. tone map(ACES)
    let mapped = [
        tone_map_aces(exposed[0]),
        tone_map_aces(exposed[1]),
        tone_map_aces(exposed[2]),
    ];
    // 3. gamma(linear → sRGB)
    let srgb = [
        linear_to_srgb(mapped[0]),
        linear_to_srgb(mapped[1]),
        linear_to_srgb(mapped[2]),
    ];
    // 4. to u8
    [
        (srgb[0] * 255.0) as u8,
        (srgb[1] * 255.0) as u8,
        (srgb[2] * 255.0) as u8,
    ]
}

fn main() {
    let hdr_colors = [
        ([0.1, 0.1, 0.1], "dim"),
        ([1.0, 1.0, 1.0], "white"),
        ([5.0, 5.0, 5.0], "bright"),
        ([10.0, 10.0, 10.0], "very bright"),
    ];
    for (color, label) in hdr_colors {
        let rendered = render(color, 1.0);
        println!("{}: HDR {:?} → sRGB {:?}", label, color, rendered);
    }

    // 测试不同 exposure
    println!("\nExposure test (white color):");
    for exposure in [0.5, 1.0, 2.0, 5.0] {
        let r = render([1.0, 1.0, 1.0], exposure);
        println!("  exposure={}: RGB={:?}", exposure, r);
    }
}
```

## 10 · 工程反思

Day 653 传达的核心教训:**视觉效果来自"工程 + 艺术"的结合**。

tone mapping 表面是数学曲线,实质是**审美选择**。Reinhard / Hable / ACES 数学都不复杂,但每个曲线背后的"为什么"涉及电影工业、人眼感知、色彩心理学。

**资深图形程序员的能力**不仅是写代码,还要理解"为什么这个曲线看起来好"。这需要:

1. **看电影**:理解好莱坞审美标准
2. **学色彩学**:色彩空间、感知模型、设备特性
3. **调参经验**:每个项目调 tone mapping 参数,积累直觉

**第二条教训**:**linear workflow 是图形学的基础纪律**。所有计算在 linear 空间,gamma 只在最后输出。违反这条会导致"颜色不一致"、"alpha blend 错误"、"tone mapping 偏色"。

新手常犯的错:

- 读 JPEG 直接当纹理(应该是 sRGB,要转 linear)
- 在 sRGB 空间做光照计算(颜色偏暗)
- 不写 gamma correction 输出(画面偏暗)

这些 bug 都是"linear workflow"没遵守。Casey 在 HH 反复强调这点,这是工业图形代码的纪律。

**第三条教训**:**HDR 是未来,LDR 是过渡**。物理光是 HDR,显示器物理是 LDR,但 HDR 显示器在普及。学懂 tone mapping,你打开了"HDR 渲染"的大门——未来 5-10 年游戏的主流。

工业教训:**tone mapping 看似简单,实际是图形管线的"艺术核心"**。一个项目视觉好坏,50% 取决于 tone mapping 调参。资深程序员花大量时间在这。

## 11 • Color space(色彩空间)深度

Color space 是图形学最复杂的 topic 之一:

**Linear vs sRGB**:

- Linear:物理光强度,值均匀分布
- sRGB:显示器编码,值在暗处密集(给人眼用)

linear 0.5 = sRGB 0.735(中间灰)。游戏渲染在 linear,输出转 sRGB 给显示器。

**HDR vs LDR**:

- HDR:任意正数(0.5, 5, 100),物理量
- LDR:[0, 1],显示器范围

tone mapping 是 HDR → LDR 的转换。

**Gamut(色域)**:

- sRGB:小色域,普通显示器
- Adobe RGB:中色域,专业摄影
- DCI-P3:中色域,电影
- Rec.2020:大色域,4K HDR
- ACES:极大色域,电影制作

每个 gamut 能表达的色彩不同。宽 gamut 显示器(Apple Retina Display)能显示更鲜艳的颜色。

**Color management**:

专业图形管线要管理 color space:

- 资产制作:ACEScg
- 渲染:linear sRGB
- 输出 sRGB 显示器:sRGB encode
- 输出 HDR 显示器:Rec.2020 + tone map

每个转换有精度损失。资深图形程序员管理 color pipeline,确保"所见即所得"。

## 12 • HDR 显示器的 tone mapping

HDR 显示器(2020s)能显示 1000+ nit(OLED)。tone mapping 不再"压到 LDR",而是"压到显示器实际亮度"。

**HDR10 标准**:

- 10-bit per channel(普通 8-bit)
- Rec.2020 色域
- ST.2084 PQ 曲线(perceptual quantizer)

游戏支持 HDR 要:

- 输出 10-bit / 12-bit
- Rec.2020 色域
- PQ 编码
- 用户亮度调整(每台 HDR 显示器亮度不同)

Cyberpunk 2077 / Last of Us Part 2 是 HDR 实现的典范。Casey 在 HH 用 LDR,工业级 HDR 是新挑战。

## 13 • tone mapping 的视觉感知

tone mapping 不是纯数学,涉及**视觉感知**:

**1. 人眼对中间调敏感**:

- 暗处精度低(看不清细节)
- 中间调精度高(主要看这)
- 亮处精度中(过亮就饱和)

ACES 曲线设计符合这个——中间调对比度好。

**2. 颜色恒常性**:

- 人眼"白平衡"——不同光下白色仍是白色
- 但相机 / 游戏不能自动白平衡
- tone mapping 要考虑 color constancy

**3. 局部适应**:

- 人眼适应亮度变化(从亮处到暗处,几秒适应)
- 游戏做"自动曝光"(auto exposure)模拟

**4. 高动态范围视觉**:

- HDR 显示器(1000+ nit)接近人眼真实感受
- LDR(100 nit)是简化

资深图形程序员理解人眼视觉模型,把数学应用到 tone mapping。这是艺术 + 科学的交叉。
