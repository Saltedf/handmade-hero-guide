# Day 577 · 加八面体光照图集

> 昨天把"3D 方向压成 2D 纹理"的数学工具搞定了。今天 Casey 把这个工具**接到游戏里**——为每个体素分配一张八面体贴图,把现有的 CubeMap 数据"迁移"过来。这一天的工程量不大,但能让你看到一个抽象数学概念怎么变成游戏里跑得起来的数据结构。

## 0 · 为什么要有这一天

数学公式跑通(单元测试都过)和实际用起来是两回事。昨天你写的 `encode_octahedral` 在测试里能完美还原单位向量,但只要把它接到游戏里——把它存的数据传给 GPU shader、让 shader 用它采样光照——你会发现一堆新问题:

- **数据格式**:GPU 贴图有 `RGBA32F`、`RGBA16F`、`RGBA8` 几种,选哪个?16 位浮点(半精度)够吗?8 位直接映射会失真吗?
- **贴图尺寸**:16×16、32×32 还是 64×64?大尺寸精度高但内存贵,小尺寸糊。
- **mipmap**:八面体贴图要不要建 mipmap?建了之后采样会变软(低频化),不建会有走样。
- **边界处理**:八面体 UV 空间的边缘对应球面的赤道,采样时如果线性插值跨过边缘,会"穿到反面",光照就闪烁。
- **数据迁移**:你之前存的是 CubeMap,现在要换成八面体,怎么把老数据搬过来?是不是要写一个一次性 bake 脚本?

Casey 这一天不解决所有这些问题——他只做一件事:**搭好数据结构骨架**,让后续天数的代码有地方落地。

心理锚点:看完这集,你能用 Rust 写出一个 `LightAtlas` 结构体,知道它每个字段为什么这样设计,能解释"为什么不直接用 CubeMap 简化代码"。如果不懂这些,后面 Day 584 的"无限弹射 GI"你会完全跟不上。

## 2 · 心智模型

### 类比:立方体盒子变成方砖

想象你有一个立方体盒子,六个面各贴了一张照片。你想把这个盒子"压扁"成一块方砖,但所有六个面的内容都要保留在方砖上。

最直接的做法:**六个面分别压在方砖的六个区域**。这正是 CubeMap 的 6-tile layout。问题是六个面之间有 12 条边(每两个面共享一条边),方砖上这些边对应 12 条"接缝"。采样时如果方向正好跨过接缝,会从一个面跳到另一个面,边缘像素的双线性插值就会出错。

八面体贴图换了一种压扁方式:把立方体盒子**先变成八面体**(8 个三角形),**再把这 8 个三角形拼成一个正方形**。8 个三角形在正方形上没有"接缝"——它们是连续的(上半球 4 个三角形拼成中间的菱形,下半球 4 个翻折到外围)。

**关键差别**:CubeMap 在 GPU 端是"6 张独立贴图,采样器内部选一张";八面体贴图是"1 张连续贴图,采样器用 encode(dir) 算 UV"。前者把"选面"逻辑放在 GPU 硬件里,后者把"算 UV"放在 shader 里(或 CPU 端)。

### 严谨原理:数据布局

每个 `LightAtlas` 就是一张方形贴图。 Casey 选 16×16 分辨率起步,原因:

**为什么 16×16?** 八面体 UV 平面有 16×16 = 256 个 texel,对应球面上 256 个均匀分布的方向。看起来少,但 Casey 存的是"间接漫反射"(Indirect Diffuse)——这种光照天然低频(墙反射的光不会尖锐),256 个方向足够刻画。

**数据类型**:Casey 一开始用 `RGB32F`(每个分量 32 位浮点)。原因:他在 CPU 端做计算,精度优先,内存不紧张。后面 Day 583 会切到 `RGBA16F`(每分量 16 位浮点,3 字节变 1.5 字节)省内存。

```rust
#[derive(Copy, Clone, Debug, Default, PartialEq)]
struct RGB32F { r: f32, g: f32, b: f32 }

impl RGB32F {
    const BLACK: Self = Self { r: 0.0, g: 0.0, b: 0.0 };
    fn add(self, o: Self) -> Self {
        Self { r: self.r + o.r, g: self.g + o.g, b: self.b + o.b }
    }
    fn scale(self, k: f32) -> Self {
        Self { r: self.r * k, g: self.g * k, b: self.b * k }
    }
}
```

**每行解释**:
- `#[derive(Default)]` — 让 `RGB32F::default()` 返回 `{0, 0, 0}`(f32 的 Default)。这在"批量初始化贴图为黑色"时方便:`vec![RGB32F::default(); N]`。
- `const BLACK` — 编译时常量,代码里写 `RGB32F::BLACK` 比写 `RGB32F { r: 0.0, g: 0.0, b: 0.0 }` 短。
- `add` 和 `scale` — 颜色加法和标量乘法,光照计算的标准操作。

### 采样过程

给定方向 `dir`,从 `LightAtlas` 取一个颜色:

```rust
impl LightAtlas {
    fn sample(&self, dir: Vec3) -> RGB32F {
        let (u, v) = encode_octahedral(dir.normalize());
        // UV ∈ [-1, 1],变换到 [0, 1] 用于索引
        let fu = (u + 1.0) * 0.5;
        let fv = (v + 1.0) * 0.5;
        // 算 texel 坐标
        let tx = fu * (self.dim as f32 - 1.0);
        let ty = fv * (self.dim as f32 - 1.0);
        // 双线性插值
        let x0 = tx.floor() as usize;
        let y0 = ty.floor() as usize;
        let x1 = (x0 + 1).min(self.dim - 1);
        let y1 = (y0 + 1).min(self.dim - 1);
        let fx = tx - x0 as f32;
        let fy = ty - y0 as f32;

        let c00 = self.texels[y0 * self.dim + x0];
        let c10 = self.texels[y0 * self.dim + x1];
        let c01 = self.texels[y1 * self.dim + x0];
        let c11 = self.texels[y1 * self.dim + x1];

        // 行内插值
        let top = c00.scale(1.0 - fx).add(c10.scale(fx));
        let bot = c01.scale(1.0 - fx).add(c11.scale(fx));
        // 行间插值
        top.scale(1.0 - fy).add(bot.scale(fy))
    }
}
```

**关键点**:
- **UV → texel**:`(u + 1) * 0.5` 把 `[-1, 1]` 映射到 `[0, 1]`,然后乘以 `(dim - 1)` 得到 texel 浮点索引(0 到 dim-1)。
- **双线性插值**:在 4 个邻居 texel 之间做加权平均。这是 2D 贴图采样的标准做法。注意 `.min(self.dim - 1)` 防越界。
- **为什么不用 SIMD**:Casey 在 Day 577 写朴素版本,Day 587 才 SIMD 化。"先跑对,再跑快"。

### 存储过程

存数据是采样的逆运算。Casey 在 Day 577 写了一个"accumulate"操作——给定方向和颜色,加到对应 texel:

```rust
impl LightAtlas {
    fn accumulate(&mut self, dir: Vec3, color: RGB32F) {
        let (u, v) = encode_octahedral(dir.normalize());
        let fu = (u + 1.0) * 0.5;
        let fv = (v + 1.0) * 0.5;
        let tx = (fu * self.dim as f32) as usize;
        let ty = (fv * self.dim as f32) as usize;
        let tx = tx.min(self.dim - 1);
        let ty = ty.min(self.dim - 1);
        let idx = ty * self.dim + tx;
        self.texels[idx] = self.texels[idx].add(color);
    }
}
```

**注意**:存储不做插值,只找一个最近的 texel(也叫"最近邻写入")。这是工程权衡——双线性"分配"会变复杂(需要把光按权重分给 4 个邻居),代价不值。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

在游戏工业里,"每体素一张光照贴图"是 Light Propagation Volume(LPV,Anton Kaplanyan 2009 提出)和 Irradiance Volume(Greger et al. 1998)的核心数据结构。这两套方案在 CryEngine 3 和 Unreal Engine 里都用过,后来逐渐被更先进的方案(SVOGI、Lumen)取代,但核心思想一致:**把世界切成格子,每个格子存一个全方向辐射场**。

Casey 的实现简化版:他不做"光照在格子间传播"的复杂计算(那是 LPV 的核心),他做的是"无限弹射 GI"——通过反复渲染所有格子、互相采样,迭代收敛。Day 584 会展开讲。

游戏工业踩过的坑:
- **内存带宽**:1000 个体素 × 16×16 × 12 字节 = 3 MB,听起来不多,但每帧都要写一遍,GPU 端要读,带宽吃紧。Casey 在 Day 588 把贴图对齐到相机空间减少更新频率。
- **Voxel 缝隙**:相邻体素的贴图在边界处会"打架"(一个体素看墙是亮的,邻居看是暗的)。Casey 在 Day 609 处理这个。

### 3.2 · 🎨 图形学视角

"Atlas"(图集)是图形学里常用术语,指**多张小图拼成一张大图**。例如角色精灵动画把每帧拼到一张大图上,采样时按帧索引切。光照图集八面体格式,是把"球面所有方向的光照"拼到一张方形图上。

**图集 vs 数组**:
- **Texture Atlas**:多张图拼成一张,UV 坐标区分。优势:一次 bind,采样快。劣势:相邻子图的边界 texel 会"互相影响"(mipmap 时尤其)。
- **Texture Array**:同尺寸的多张图,用 layer index 区分。优势:无边界干扰。劣势:需要 GPU 支持(OpenGL 3.0+)。

Casey 在 Day 577 用单一 atlas(每体素一张独立贴图)。Day 585 会讨论是不是把这些图集打包成一个大的(批量上传 GPU)。

**Mipmap 问题**:八面体贴图如果开 mipmap,边界(对应球面赤道)会"模糊到对面的方向",因为 mipmap 生成器不知道边界两侧方向是连续的。解决:不用硬件 mipmap,用 CPU 端"球面平均"生成 mipmap 链。Casey 在 Day 589 触及这个。

### 3.3 · 🐧 Linux 系统编程视角

这一集 Casey 主要在 Rust 内部数据结构上工作,Linux 系统调用面没什么。但有一个**内存分配**的细节值得注意。

`Box<[RGB32F]>` 在堆上分配连续内存。当 1000 个体素每个分配一个 LightAtlas,会有 1000 次堆分配。Linux 上每次堆分配通过 `malloc`(glibc)→ 底层是 `mmap` 或 `brk`。1KB 大小的分配通常走 slab(小块缓存),不真的 `mmap`——但仍然有锁竞争。

替代方案:**Arena 分配器**。一次性分配大块内存,内部按需切片。Casey 在 Phase 4 详细讲过(bumpalo crate)。对 LightAtlas 数组,Casey 在 Day 588 把所有 atlas 打包到一个 `Box<[RGB32F]>`(用 `voxel_index * atlas_size + texel_index` 寻址)。

Linux 上验证当前分配:

```bash
# 跑游戏 30 秒,看 malloc 调用数
strace -c -e trace=mmap,brk,munmap -p $(pidof your_game) 2>&1 | head -20
# 如果 mmap 调用上千次,说明堆分配过多,该用 arena
```

### 3.4 · 🦀 Rust 生态视角

Rust 表达"贴图"有几种方式,各有取舍:

**流派 1:Vec<T>**(Casey 选的):

```rust
struct LightAtlas {
    texels: Vec<RGB32F>,
    dim: usize,
}
```

简单,但 `Vec` 是"可增长"的,我们其实不需要可增长(贴图尺寸固定)。这有性能损失(Vect 存 capacity、len、ptr 三字段,内存占 24 字节而不是裸指针 8 字节)。

**流派 2:Box<[T]>**(更紧凑):

```rust
struct LightAtlas {
    texels: Box<[RGB32F]>,
    dim: usize,
}
```

`Box<[T]>` 是"固定大小堆分配",只存 ptr + len(16 字节)。但 Casey 在 Day 577 用 Vec,因为一开始他要调试,Vec 的 `push` 等方法方便。

**流派 3:数组(栈上)**(小尺寸时):

```rust
struct LightAtlas {
    texels: [RGB32F; 256],  // 16×16
    dim: usize,
}
```

256 × 12 = 3 KB,放栈上可能 OK,但放堆更稳(避免栈溢出)。Rust 默认栈 8MB,3000 个 atlas 就爆栈。

**所有权的细节**:`LightAtlas` 拥有 `texels`,谁拥有 `LightAtlas`?游戏世界(`World` struct)拥有所有 atlas。Casey 在 Day 577 用 `Vec<LightAtlas>`——每个体素一个 atlas。

```rust
struct World {
    atlases: Vec<LightAtlas>,  // 一个体素一个
    voxels: Vec<Voxel>,        // 体素几何 / 材质
    // ...
}
```

为什么不用 `HashMap<VoxelIndex, LightAtlas>`?因为体素在 3D 网格里是密集的(不是稀疏的),数组比 HashMap 快(没有 hash 计算 + 哈希碰撞)。Casey 在 Day 588 优化时仍保持 `Vec<LightAtlas>` 紧凑布局。

## 5 · 对照与变奏

### 同一存储在不同语境下的变体

| 语境 | 数据 | 采样 | 存储 |
|---|---|---|---|
| 静态光照贴图(预烘焙) | 大图(Lightmap)| UV 映射 | 离线工具 |
| 动态光照探针 | 八面体小图 | encode + bilinear | 实时更新 |
| 反射探针 | CubeMap | direction → face + UV | 烘焙或低频更新 |
| 体积雾(Volumetric Fog)| 3D 纹理 | 三线性插值 | 每帧重建 |

每种方案在"分辨率 × 内存 × 更新频率"三角上做不同权衡。Casey 选的是"低分辨率(16×16)× 中等内存(3KB)× 高频率(每帧更新)"——这适合实时 GI。

### 历史演化

- **1998**:Greger et al. 提出 Irradiance Volume(每个空间格子存辐射度)。光照图集的祖先。
- **2009**:Kaplanyan 提出 Light Propagation Volume(CryEngine 3 用)。Voxel + 八面体存储 + 迭代传播。
- **2014**: Unreal Engine 4 用 LPV 简化版作为 GI 解决方案。
- **2020+**:UE5 Lumen 用"距离场 + 卡牌渲染 + 屏幕空间 GI",但底层光照探针仍是八面体变种。

Casey 的实现是 LPV 的简化教学版——不做传播,只做迭代收敛。教学价值在"让你看到数据流",不在"复制工业方案"。

### CPU 端 vs GPU 端实现

CPU 端(我们现在):编码、采样、双线性都在 Rust 里写。慢,但好调试。每帧一次更新光照,GI 一次需要数十毫秒。

GPU 端(工业方案):整个流程在 compute shader 里。快,但调试痛苦。Casey 在 Phase 5 切到 OpenGL 后,有些光照计算搬到 GPU;Day 577 仍是 CPU 版本。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 选 16×16 而不是 32×32 或 8×8 起步?三个尺寸的代价和收益分别是什么?

**参考解答**:
- **8×8 = 64 texel**:每个方向覆盖球面 4π/64 ≈ 0.2 球面度(像一颗大弹珠的视角)。对间接漫反射,这分辨率太粗,角落的尖锐高光会被涂糊。
- **16×16 = 256 texel**:每方向 0.05 球面度(像葡萄大小)。Casey 的间接漫反射场景足够。内存 256 × 12 字节 = 3 KB / 体素,1000 个体素 = 3 MB,可接受。
- **32×32 = 1024 texel**:每方向 0.012 球面度(像沙粒大小)。精度足够存间接镜面反射(墙面的镜面倒影),但内存 12 KB / 体素,带宽吃紧。

Casey 选 16×16 是"刚好够用"的工程判断。等系统跑通再考虑升 32×32(如果视觉精度不够)或降 8×8(如果性能不够)。

**参考解答**:

```rust

struct RGB32F { r: f32, g: f32, b: f32 }

impl RGB32F {
    fn new(r: f32, g: f32, b: f32) -> Self { Self { r, g, b } }
    fn add(self, o: Self) -> Self { Self::new(self.r+o.r, self.g+o.g, self.b+o.b) }
    fn scale(self, k: f32) -> Self { Self::new(self.r*k, self.g*k, self.b*k) }
}

#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn normalize(self) -> Self {
        let len2 = self.x*self.x + self.y*self.y + self.z*self.z;
        let inv = 1.0 / len2.sqrt();
        Self { x: self.x*inv, y: self.y*inv, z: self.z*inv }
    }
}

// 八面体编码(见 day576)
fn encode_octahedral(n: Vec3) -> (f32, f32) {
    let l1 = n.x.abs() + n.y.abs() + n.z.abs();
    let inv = 1.0 / l1;
    let x = n.x * inv;
    let y = n.y * inv;
    let z = n.z * inv;
    if z >= 0.0 { (x, y) }
    else {
        let ax = x.abs();
        let ay = y.abs();
        let u = if x >= 0.0 { 1.0 - ay } else { -(1.0 - ay) };
        let v = if y >= 0.0 { 1.0 - ax } else { -(1.0 - ax) };
        (u, v)
    }
}

struct LightAtlas {
    texels: Vec<RGB32F>,
    dim: usize,
}

impl LightAtlas {
    fn new(dim: usize) -> Self {
        Self {
            texels: vec![RGB32F::default(); dim * dim],
            dim,
        }
    }

    fn accumulate(&mut self, dir: Vec3, color: RGB32F) {
        let (u, v) = encode_octahedral(dir.normalize());
        let fu = (u + 1.0) * 0.5;
        let fv = (v + 1.0) * 0.5;
        let tx = (fu * self.dim as f32) as usize;
        let ty = (fv * self.dim as f32) as usize;
        let tx = tx.min(self.dim - 1);
        let ty = ty.min(self.dim - 1);
        let idx = ty * self.dim + tx;
        self.texels[idx] = self.texels[idx].add(color);
    }

    fn sample(&self, dir: Vec3) -> RGB32F {
        let (u, v) = encode_octahedral(dir.normalize());
        let fu = (u + 1.0) * 0.5;
        let fv = (v + 1.0) * 0.5;
        let tx = fu * (self.dim as f32 - 1.0);
        let ty = fv * (self.dim as f32 - 1.0);
        let x0 = tx.floor() as usize;
        let y0 = ty.floor() as usize;
        let x1 = (x0 + 1).min(self.dim - 1);
        let y1 = (y0 + 1).min(self.dim - 1);
        let fx = tx - x0 as f32;
        let fy = ty - y0 as f32;
        let c00 = self.texels[y0 * self.dim + x0];
        let c10 = self.texels[y0 * self.dim + x1];
        let c01 = self.texels[y1 * self.dim + x0];
        let c11 = self.texels[y1 * self.dim + x1];
        let top = c00.scale(1.0 - fx).add(c10.scale(fx));
        let bot = c01.scale(1.0 - fx).add(c11.scale(fx));
        top.scale(1.0 - fy).add(bot.scale(fy))
    }
}

fn main() {
    let mut atlas = LightAtlas::new(16);
    // 在北极放红光
    atlas.accumulate(Vec3 { x: 0.0, y: 0.0, z: 1.0 }, RGB32F::new(1.0, 0.0, 0.0));
    // 采样北极附近,应该返回红
    let c1 = atlas.sample(Vec3 { x: 0.0, y: 0.0, z: 1.0 });
    println!("Sample at north pole: {:?}", c1);  // 应该接近 (1, 0, 0)
    // 采样略微偏移的方向,双线性插值应该返回部分红
    let c2 = atlas.sample(Vec3 { x: 0.1, y: 0.0, z: 0.99 }.normalize());
    println!("Sample at near-north: {:?}", c2);  // 应该部分红
}
```

**每行解释**:
- `vec![RGB32F::default(); dim * dim]` — 创建 `dim*dim` 个 `RGB32F::default()`(全黑),堆分配。
- `tx.min(self.dim - 1)` — 防越界。`fu` 在 `[0, 1]`,`fu * dim` 最大可能等于 `dim`(刚好),需要 clamp。
- 双线性插值里 `tx * (dim - 1)` 而不是 `tx * dim`:这是"以 texel 中心为采样点"的约定。`fu = 0` 对应第一个 texel 中心,`fu = 1` 对应最后一个。
- `floor() as usize` — 浮点转整数,向下取整。

    let samples = [
