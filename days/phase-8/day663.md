## 0 · 为什么要有这一天

回顾 HH 的 Entity 演化:

- Day 027:简单 struct,几个字段

每个 Entity 是 enum 变体(Player / Enemy / Treasure / Boss / Shopkeeper),变体只持有自己需要的字段。这是 Rust enum 的天然用法,内存紧凑。

心理锚点:看完今天,你能:

- 把胖 struct 拆成 enum 变体
- 理解 ECS 的替代方案
- 设计紧凑的实体存储

## 2 · 心智模型

### 类比:医院病历

老医院:所有病人用同一份病历表,50 个字段。哮喘病人填"过敏史",骨折病人填"既往病史",大多数字段空着——表格大,查阅慢。

新医院:每种病有专门病历表,哮喘病人用"哮喘表"(8 字段),骨折用"骨科表"(6 字段)。每份表小,查阅快。

Entity 存储同构。每个类型有自己的 struct,内存紧凑,cache 友好。

### Tagged union(标签联合)

Rust enum 是 sum type(和类型):

```rust
enum Entity {
    Player(PlayerData),
    Enemy(EnemyData),
    Treasure(TreasureData),
    // ...
}
```

每个 Entity 在内存里是:

- 标签(1-2 字节,标识变体)
- 变体的 payload(struct)
- padding 对齐

总大小 = max(各变体大小) + 标签 + padding。Rust 自动算最大变体。

### Data struct 设计

```rust
struct PlayerData {
    pos: Vec3,
    vel: Vec3,
    hp: f32,
    inventory: Vec<Item>, // 玩家有库存
    // 不放 AI state,玩家不需要
}

struct EnemyData {
    pos: Vec3,
    vel: Vec3,
    hp: f32,
    ai_state: AIState, // 敌人有 AI
    // 不放 inventory,敌人掉落是死亡时
}

struct TreasureData {
    pos: Vec3,
    content: Item, // 宝箱只存物品
    opened: bool,
    // 不放 vel / hp / ai_state
}

struct BossData {
    pos: Vec3,
    vel: Vec3,
    hp: f32,
    phase: u8, // Boss 阶段
    ai_state: AIState,
}
```

每个 struct 只放自己需要的字段。

### 共享字段的 trait

某些操作对所有实体都适用——比如"获取位置"。两种思路:

1. **match + match**:每次取 pos 都 match 一次
2. **trait + dyn dispatch**:运行时多态
3. **辅助 struct**:把"所有实体共有"的字段提到外面

Casey 选思路 3:

```rust
struct Entity {
    common: EntityCommon, // 所有实体共有
    specific: EntitySpecific, // 类型特定
}

struct EntityCommon {
    pos: Vec3,
    vel: Vec3,
    hp: f32,
    facing: Vec3,
    // 所有实体都有
}

enum EntitySpecific {
    Player { inventory: Vec<Item> },
    Enemy { ai_state: AIState },
    Treasure { content: Item, opened: bool },
    Boss { phase: u8 },
}
```

`EntityCommon` + `EntitySpecific` 的组合让通用操作(更新 pos、绘制)只看 Common,特定操作(玩家输入、AI 决策)看 Specific。

### ECS 对比

ECS 的核心:

- **Entity**:只是 ID(u32)
- **Component**:数据片段(Position / Health / Inventory)
- **System**:操作某类 Component 的函数

ECS 让你"按需"加 Component,Entity 1 有 Position + Health,Entity 2 有 Position + AI,没有"冗余字段"。但 ECS:

- 复杂(框架)
- 内存布局分散(Component 在不同 Vec 里,cache miss)
- 调试难(看 Entity 状态要拼多个 Component)

Casey 的 tagged union 是 ECS 的简化版——共享部分提出来,特定部分 enum,内存连续,简单。

### 内存对比

```rust
// 老:50 字段 * 平均 4 字节 = 200 字节 / Entity
struct OldEntity {
    pos: Vec3, vel: Vec3, hp: f32, mp: f32, ...
    // 50 字段
}

// 新:Common + Specific,Common 32 字节,Specific 最大 24 字节
struct NewEntity {
    common: EntityCommon, // 32
    specific: EntitySpecific, // 8 (tag) + 24 (max variant) = 32
}
// Total: 64 字节,3 倍小
```

1000 个实体:200 KB → 64 KB,cache 命中率 3 倍。

### 3.2 · 图形学视角

图形里"按类型 dispatch":

- **Render pipeline**:不同 material 走不同 shader
- **GPU command**:不同 command type 走不同硬件路径
- **Asset loader**:不同 asset 类型走不同 loader

每个都是"看类型做事"。

### 3.3 · Linux 系统编程视角

Linux 内核里类似设计:

- **inode**:不同文件系统(ext4 / btrfs / xfs)有自己的 inode struct,但共用 `struct inode` 通用部分
- **task_struct**:进程通用 + 各子系统(调度 / 内存 / 网络)的 hook 字段
- **file**:通用 + 各 fs 的 private_data

每个都是"common + specific"分层。

### 3.4 · Rust 生态视角

Rust 里 tagged union:

```rust
enum Shape {
    Circle(CircleData),
    Rect(RectData),
    Triangle(TriangleData),
}

fn area(s: &Shape) -> f32 {
    match s {
        Shape::Circle(d) => std::f32::consts::PI * d.r * d.r,
        Shape::Rect(d) => d.w * d.h,
        Shape::Triangle(d) => 0.5 * d.base * d.height,
    }
}
```

`match` 强制 exhaustive——加新变体时,所有 match 处编译器警告。这是 Rust 比 C++ 优势之一。

## 5 · 对照与变奏

Entity 存储不同方案对比:

```
胖 struct:
[player, pos, vel, hp, mp, ai, inv, ...] x 1000 = 200 KB
所有字段,大量浪费

Tagged union:
[common, specific] x 1000 = 64 KB
紧凑,但 specific 受 max variant 限制

ECS:
positions: [pos x 1000] = 12 KB
velocities: [vel x 800] = 10 KB (200 个无速度)
hps: [hp x 1000] = 4 KB
...
每个 Component 独立 Vec,按需
```

ECS 最紧凑,但 casey 选 tagged union 平衡简单 + 紧凑。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:tagged union 比胖 struct 在内存上节省多少?

**参考解答**:胖 struct 有 N 个字段,所有实体都有所有字段(很多 unused),每个 Entity 占 N * 4 字节(典型)。tagged union 的 Entity = max(变体大小)+ 标签。如果变体平均只 30% 字段,union 比 struct 小 70%。1000 个 Entity 时,可能从 200 KB 降到 60 KB,3 倍 cache 改善。

## 8 · Rust / Arch 落地代码

完整 tagged union:

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::Vec3;

#[derive(Clone, Debug, PartialEq)]
enum AIState { Idle, Chasing, Attacking, Fleeing }

#[derive(Clone, Debug)]
struct Item(String);

#[derive(Clone, Debug)]
struct EntityCommon {
    pos: Vec3,
    vel: Vec3,
    hp: f32,
    facing: Vec3,
}

#[derive(Clone, Debug)]
enum EntitySpecific {
    Player { inventory: Vec<Item>, glove_state: u8 },
    Enemy { ai_state: AIState, damage: f32 },
    Treasure { content: Item, opened: bool },
    Boss { phase: u8, ai_state: AIState, damage: f32 },
    Shopkeeper { inventory: Vec<Item> },
}

#[derive(Clone, Debug)]
struct Entity {
    id: u32,
    common: EntityCommon,
    specific: EntitySpecific,
}

impl Entity {
    fn new_player(id: u32, pos: Vec3) -> Self {
        Self {
            id,
            common: EntityCommon {
                pos, vel: Vec3::ZERO, hp: 100.0,
                facing: Vec3::new(1.0, 0.0, 0.0),
            },
            specific: EntitySpecific::Player {
                inventory: Vec::new(),
                glove_state: 0,
            },
        }
    }
    fn new_enemy(id: u32, pos: Vec3) -> Self {
        Self {
            id,
            common: EntityCommon {
                pos, vel: Vec3::ZERO, hp: 30.0,
                facing: Vec3::new(1.0, 0.0, 0.0),
            },
            specific: EntitySpecific::Enemy {
                ai_state: AIState::Idle, damage: 5.0,
            },
        }
    }
}

fn update_all(entities: &mut [Entity], dt: f32) {
    for e in entities {
        e.common.pos += e.common.vel * dt;
        match &mut e.specific {
            EntitySpecific::Enemy { ai_state, .. } => {
                if *ai_state == AIState::Idle {
                    *ai_state = AIState::Chasing; // 简化:总是切换
                }
            }
            EntitySpecific::Boss { ai_state, phase, .. } => {
                if *ai_state == AIState::Idle && e.common.hp < 50.0 {
                    *phase = 2;
                    *ai_state = AIState::Attacking;
                }
            }
            _ => {}
        }
    }
}

fn main() {
    let mut entities = vec![
        Entity::new_player(0, Vec3::new(5.0, 0.0, 5.0)),
        Entity::new_enemy(1, Vec3::new(10.0, 0.0, 10.0)),
        Entity::new_enemy(2, Vec3::new(15.0, 0.0, 15.0)),
    ];
    println!("Before update:");
    for e in &entities {
        println!("  Entity {}: pos={:?}, hp={:?}, specific={:?}",
            e.id, e.common.pos, e.common.hp, e.specific);
    }

    update_all(&mut entities, 0.1);

    println!("\nAfter update:");
    for e in &entities {
        println!("  Entity {}: pos={:?}, hp={:?}, specific={:?}",
            e.id, e.common.pos, e.common.hp, e.specific);
    }

    println!("\nMemory:");
    println!("  Per entity: {} bytes", std::mem::size_of::<Entity>());
    println!("  1000 entities: {} KB", std::mem::size_of::<Entity>() * 1000 / 1024);
}
```

## 10 · 工程反思

Day 663 传达的核心工程教训:**tagged union + storage 设计 = 性能 + 灵活**。

新手用 OO 继承(Animal → Dog / Cat),资深工程师用 tagged union(EntityType::Dog / Cat)。原因:

- **OO 继承**:vtable 开销,内存碎片,难演化
- **Tagged union**:紧凑存储,编译期检查,易演化

Rust 的 enum 是 tagged union 的语言级支持。每个 variant 是一个 case,match 强制 exhaustive。这是 Rust 的核心优势之一。

**为什么 tagged union 适合 ECS?**

ECS 的 entity 是"组件集合"。组件类型多(Position / Velocity / Health / AI / Render / ...),每个 entity 只有一部分。两种存储:

- **Map per entity**:`HashMap<ComponentType, Component>` —— 灵活但慢
- **Tagged union**:`enum Components { Position(Position), ... }` —— 快但固定
- **Sparse set**:每种组件单独存,entity 查询时合并 —— 现代 ECS 标准

每种 trade-off 不同。Casey 在 HH 用 tagged union,教学清晰。工业级 ECS(bevy / Unity DOTS)用 sparse set。

**Data-Oriented Design(DOD)**:

DOD 是工业级游戏开发的方法论:**以数据为中心设计,而非以对象为中心**。核心原则:

- 数据布局优先于算法
- 按访问模式组织数据(SoA vs AoS)
- 减少 indirection
- cache friendly

DOD 让 CPU 友好,性能 10-100x。Casey 在 HH 反复演示(arena allocator、手写 ECS)。

**第二条教训**:**序列化决定 savegame / 网络协议**。

如果 entity 是 tagged union,序列化简单——`serialize(entity)`,反序列化也简单。如果 entity 是 OO 继承树,序列化复杂(要处理多态)。

Rust 的 serde 库自动派生 Serialize / Deserialize,enum 天然支持。这是 Rust 在游戏开发的杀手锏——序列化简单。

**第三条教训**:**enum 内存占用 = max(variant size)**。

```rust
enum E {
    A(u8),         // 1 byte
    B([u8; 100]),  // 100 bytes
}
// sizeof(E) ≈ 100 + tag(1 byte)
```

如果 variant 大小差异大,enum 占内存大。优化:`Box` 包装大 variant:

```rust
enum E {
    A(u8),
    B(Box<[u8; 100]>),  // heap 分配
}
// sizeof(E) ≈ 8 (pointer) + tag
```

这是 Rust 性能优化的基础技巧。工业级 Rust 游戏代码大量用 Box 减小 enum 大小。

**迁移到其他领域**:

"tagged union + DOD"思路在多处通用:

- **数据库**:tagged row format(PostgreSQL)
- **编译器**:AST node 用 tagged union
- **网络**:protocol buffer oneof
- **Web**:TypeScript discriminated union
- **ML**:tensor 不同 dtype(tagged)

每个领域都有"tagged data"需求。Casey 在 HH 演示的是 ECS 版本。

## 11 · Tagged Union 的内存优化技巧

Rust enum 默认 sizeof = max(variant size) + tag。如果 variant 大小差异大,浪费。

**示例**:

```rust
enum Value {
    Int(i32),        // 4 bytes
    Str(String),     // 24 bytes
    Arr(Vec<Value>), // 24 bytes
}
// sizeof(Value) ≈ 24 + 8(tag) = 32 bytes
```

如果 90% 是 Int,浪费 28 bytes/value。优化:

**1. Box 大 variant**:

```rust
enum Value {
    Int(i32),
    Str(Box<String>),
    Arr(Box<Vec<Value>>),
}
// sizeof(Value) ≈ 8(pointer) + 4(Int) + 4(padding) + 8(tag) = 24 bytes
```

`Box` 让大 variant 在堆,enum 在栈只占 pointer。

**2. Small string optimization (SSO)**:

`String` 类型固定 24 bytes。短字符串(< 23 bytes)放在 inline buffer,不分配 heap。这是 C++ std::string 的优化技巧。

Rust 的 `String` 不做 SSO(标准库设计选择),但 `smartstring` crate 实现 SSO。

**3. Pointer tagging**:

利用"指针低位是 0"(aligned),把 tag 编码进 pointer:

```rust
// 假设 pointer 是 8-byte aligned,低位 3 bits 可用
// tag = pointer & 0x7
// real_pointer = pointer & !0x7
```

这是 JavaScript engine 的高性能技巧。Rust 用 `tagged-box` crate 实现。

每个优化都有 trade-off。资深 Rust 工程师按需选。

## 12 · ECS 的并行调度

现代 ECS(bevy / Unity DOTS)支持**system parallelism**:

```rust
// bevy
fn update_positions(mut query: Query<&mut Position>) {
    query.par_iter().for_each(|mut pos| {
        // 每个实体独立并行
    });
}
```

`par_iter` 让多线程并行遍历实体。前提是 system 之间无冲突(不写同一 component)。

bevy 的 scheduler 自动检测冲突,串行执行冲突 system,并行执行独立 system。这是工业级 ECS 的杀手锏——自动 parallelism。

Casey 在 HH 单线程,工业级多线程。学懂 HH,工业级是"HH + 并行"。

## N0 • 深度教学补充

### 核心概念重新梳理

Day 663 涉及的核心概念需要在多个层次上理解:

**第一层:直观理解**

新手第一次接触概念,需要建立直觉。例如 voxel collision 是"虚拟物体不能穿过虚拟墙"——这个直觉每个人都能从现实经验获得。

**第二层:数学理解**

把直觉形式化。collision = "两个几何体的体积有交集"。对于 AABB,这等价于"三轴投影都重叠"。

**第三层:工程理解**

数学正确不等于工程实现正确。要考虑:

- 浮点精度边界
- 性能(每帧 N 个查询)
- 内存(数据结构紧凑)
- 边角 case(无穷大、NaN、负数)

**第四层:工业理解**

工业级要再加:

- 多线程安全
- SIMD 优化
- 网络同步(多人游戏)
- 跨平台(Windows/Mac/Linux/Mobile)
- 可访问性(色盲友好)
- 反作弊

每层理解都让代码更鲁棒。资深工程师在所有层次同时思考。

### 实际工程的细节

工业代码 80% 是"边角 case 处理",20% 是"核心算法"。Casey 在 HH 演示核心,工业代码加大量边角处理。

**边角 case 类型**:

1. 空输入(空 Vec、null pointer)
2. 极端输入(NaN、无穷大、超大数)
3. 并发竞争(多线程同时访问)
4. 资源不足(内存满、磁盘满)
5. 网络异常(超时、断连、包丢失)
6. 版本不兼容(老配置 / 新代码)
7. 权限错误(只读文件、无网络)
8. 用户误操作(连点、撤销重做)

每个 case 都要单独处理。这是工业代码 50%+ 行数的原因。

### 优化思路

性能优化有顺序:

1. **算法**:O(N²) → O(N log N),最大提升
2. **数据结构**:Vec → HashMap / BTreeMap,常数提升
3. **Cache**:AoS → SoA,cache 命中提升
4. **SIMD**:4-16 元素并行,巨大常数提升
5. **GPU**:数千核并行,极致性能
6. **分布式**:多机器,无限扩展

每级提升都需要更复杂的代码。先优化低级,够用再升级。

Day 663 不只是技术教学,也是"工程哲学"教学:

- **简单 > 复杂**:够用就行
- **理解 > 记忆**:概念比代码重要
- **完成 > 完美**:能跑 > 能优化
- **持续学习**:技术永远在演化

这些哲学跨技术领域通用。学完 HH,你不只会写游戏,你**理解工程**。这是 HH 最大的价值。

Day 663 用 C 写,但 Rust 版本会更安全 / 更高效:

每条都让代码更鲁棒。Rust 是游戏开发的新趋势(bevy / wgpu / rend3),学习 Rust 让你未来 10 年受益。
