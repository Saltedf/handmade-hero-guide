
# Day 656 · 草拟移动队列

> Day 655 引入了"移动请求"概念。今天 Casey 把"请求"扩展成"队列"——一个实体可以同时有多条**等待执行**的移动指令。例如:玩家"向前走 5 步,然后右转,然后冲刺"——这是一条**预录路径**,逐帧执行。

## 0 · 为什么要有这一天

移动请求(Day 655)处理"当下这一帧"的移动。但游戏有"序列化移动"需求:

- **AI 路径**:NPC 从 A 到 B,中间经过 5 个 waypoint,每个 waypoint 一段移动
- **剧情脚本**:玩家进入剧情,角色按预设走路 / 转身 / 表情
- **组合招式**:玩家连招 AABB→CC,每段是独立移动请求
- **过场动画**:相机 / 角色按时间轴走

**移动队列**(move queue)就是这种"待执行"的请求列表。每帧从队列取一个执行,执行完出列,下一条接上。

心理锚点:看完今天,你能:

- 设计移动队列数据结构
- 实现队列的逐帧消费
- 处理"队列中断"(玩家输入打断当前序列)

## 1 · Casey 今天做了什么

1. 引入 `MoveQueue`:`VecDeque<MoveRequest>` 加当前正在执行的 request
2. 实体每帧从队列取一个 request,执行,完成后出列
3. 处理"完成"概念:Dash / Walk 是瞬时的(一帧完成),Force 是持续的(持续 N 帧才完成)
4. 设计"中断"机制:玩家按某键,清空队列,加新请求
5. 写一个简单 AI:巡逻 NPC,队列里有 4 个 Walk 段
6. 测试:NPC 按 4 段走路,玩家冲撞 NPC,NPC 队列被 Knockback 中断

## 2 · 心智模型

### 类比:GPS 逐段导航

GPS 给出整个路线,但你**每段一段执行**——开完一段路,GPS 才给下一段。如果路上突然变道(用户选了捷径),GPS 重新算路线,旧路线"作废"。

移动队列同构:**预录多段**,逐段执行,**用户可中断重算**。

### 持续请求 vs 瞬时请求

请求分两类:

- **瞬时**(instant):执行一次就完成。例:Teleport、Dash、Walk(只设 vel,后续由物理演化)
- **持续**(sustained):持续一段时间。例:Force(每帧加力),Walk(持续多帧,玩家一直按方向键)

瞬时请求容易出列:执行后立刻 pop。持续请求需要"完成条件":

```rust
enum MoveRequest {
    Walk { vel: Vec3, duration: f32 },  // 持续 N 秒
    Dash { dir: Vec3, distance: f32 },  // 瞬时
    Force { accel: Vec3, duration: f32 }, // 持续
    // ...
}

impl MoveRequest {
    fn update(&mut self, dt: f32) -> bool {
        // 返回 true 表示完成
        match self {
            MoveRequest::Walk { duration, .. } => {
                *duration -= dt;
                *duration <= 0.0
            }
            MoveRequest::Force { duration, .. } => {
                *duration -= dt;
                *duration <= 0.0
            }
            _ => true, // 瞬时请求立刻完成
        }
    }
}
```

### 队列消费

```rust
fn update_entity(e: &mut Entity, dt: f32) {
    while let Some(req) = e.queue.front_mut() {
        apply_request(e, req, dt);
        if req.update(dt) {
            e.queue.pop_front();
        } else {
            break; // 当前请求没完成,等下一帧
        }
    }
}
```

`while let` + `front_mut` 让我们看队列头部,执行,如果完成就 pop,不完成就停。

### 中断机制

队列可以被外部中断:

```rust
impl Entity {
    fn interrupt(&mut self, new_req: MoveRequest) {
        self.queue.clear();
        self.queue.push_back(new_req);
    }
}
```

例:玩家被 Knockback,清空当前所有移动,只处理 Knockback。

但有些请求**不能被中断**(剧情脚本),需要 `interruptible: bool` 标志:

```rust
struct MoveQueue {
    items: VecDeque<(MoveRequest, bool)>, // (request, interruptible)
}
```

### AI 巡逻队列

```rust
fn setup_patrol(e: &mut Entity, waypoints: &[Vec3]) {
    for wp in waypoints.windows(2) {
        let from = wp[0];
        let to = wp[1];
        let dir = to - from;
        let distance = dir.length();
        let vel = dir / distance * PATROL_SPEED;
        let duration = distance / PATROL_SPEED;
        e.queue.push_back(MoveRequest::Walk { vel, duration });
    }
}
```

NPC 按路径走完所有 waypoint。windows(2) 给出相邻 waypoint 对。

- **netfilter queue**:网络包逐个处理
- **IO 队列**:每个 block device 一个
- **message queue (POSIX)**:进程间通信

每个都是"待执行任务"。

### 3.4 · Rust 生态视角

Rust 的 VecDeque 实现:

```rust
use std::collections::VecDeque;

let mut q: VecDeque<i32> = VecDeque::new();
q.push_back(1);
q.push_back(2);
q.push_front(0); // 头部插入
assert_eq!(q.front(), Some(&0));
assert_eq!(q.pop_front(), Some(0)); // 头部弹出
```

VecDeque 是 ring buffer,O(1) 头尾操作。比 Vec+remove(0)(O(N))快。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:瞬时请求和持续请求在队列处理上有什么区别?

**参考解答**:瞬时请求(如 Dash)执行一次就完成,立刻 pop,下一帧处理下一条。持续请求(如 Walk 持续 5 秒)需要 N 帧才完成,这期间队列"卡"在这条上,直到 duration 计时器到 0。队列代码用 `req.update(dt) -> bool` 区分——返回 true 就 pop,false 就停。

### Lv2 · 动手实践

**题**:实现 §2 的 MoveQueue + update_entity,测试:

```rust
let mut e = Entity::new();
e.queue.push_back(MoveRequest::Walk { vel: Vec3::new(1.0, 0.0, 0.0), duration: 0.5 });
e.queue.push_back(MoveRequest::Dash { dir: Vec3::new(1.0, 0.0, 0.0), distance: 5.0 });

}
// 预期:前 30 帧 Walk,后 30 帧已经 Dash 完(Dash 瞬时),队列空
```

**参考解答**:

```rust
use glam::Vec3;
use std::collections::VecDeque;

#[derive(Clone, Debug)]
enum MoveRequest {
    Walk { vel: Vec3, duration: f32 },
    Dash { dir: Vec3, distance: f32 },
    Force { accel: Vec3, duration: f32 },
}

impl MoveRequest {
    fn update(&mut self, dt: f32) -> bool {
        match self {
            MoveRequest::Walk { duration, .. } | MoveRequest::Force { duration, .. } => {
                *duration -= dt;
                *duration <= 0.0
            }
            MoveRequest::Dash { .. } => true,
        }
    }
}

struct Entity {
    pos: Vec3,
    vel: Vec3,
    queue: VecDeque<MoveRequest>,
}

impl Entity {
    fn new() -> Self { Self { pos: Vec3::ZERO, vel: Vec3::ZERO, queue: VecDeque::new() } }
}

fn apply(e: &mut Entity, req: &MoveRequest, dt: f32) {
    match req {
        MoveRequest::Walk { vel, .. } => {
            e.vel = *vel;
        }
        MoveRequest::Dash { dir, distance } => {
            e.pos += dir.normalize_or_zero() * distance;
            e.vel = Vec3::ZERO;
        }
        MoveRequest::Force { accel, .. } => {
            e.vel += *accel * dt;
        }
    }
}

fn update_entity(e: &mut Entity, dt: f32) {
    while let Some(req) = e.queue.front_mut() {
        apply(e, req, dt);
        e.pos += e.vel * dt;
        if req.update(dt) {
            e.queue.pop_front();
        } else {
            break;
        }
    }
}

fn main() {
    let mut e = Entity::new();
    e.queue.push_back(MoveRequest::Walk { vel: Vec3::new(1.0, 0.0, 0.0), duration: 0.5 });
    e.queue.push_back(MoveRequest::Dash { dir: Vec3::new(1.0, 0.0, 0.0), distance: 5.0 });

    for frame in 0..60 {
        let queue_len_before = e.queue.len();
        update_entity(&mut e, 1.0 / 60.0);
        let queue_len_after = e.queue.len();
        if queue_len_before != queue_len_after {
            println!("Frame {}: queue {} → {}, pos={:?}",
                frame, queue_len_before, queue_len_after, e.pos);
        }
    }
    println!("Final: pos={:?}, queue empty={}", e.pos, e.queue.is_empty());
}
```

## 8 · Rust / Arch 落地代码

完整移动队列系统:

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::Vec3;
use std::collections::VecDeque;

#[derive(Clone, Debug)]
enum MoveRequest {
    Walk { vel: Vec3, duration: f32 },
    Dash { dir: Vec3, distance: f32 },
    Teleport { target: Vec3 },
    Knockback { impulse: Vec3 },
    Force { accel: Vec3, duration: f32 },
    Wait { duration: f32 },
}

impl MoveRequest {
    fn is_instant(&self) -> bool {
        matches!(self, MoveRequest::Dash { .. } | MoveRequest::Teleport { .. } | MoveRequest::Knockback { .. })
    }
    fn update(&mut self, dt: f32) -> bool {
        match self {
            MoveRequest::Walk { duration, .. }
            | MoveRequest::Force { duration, .. }
            | MoveRequest::Wait { duration } => {
                *duration -= dt;
                *duration <= 0.0
            }
            _ => true,
        }
    }
    fn apply(&self, e: &mut Entity, dt: f32) {
        match self {
            MoveRequest::Walk { vel, .. } => { e.vel = *vel; }
            MoveRequest::Dash { dir, distance } => {
                e.pos += dir.normalize_or_zero() * distance;
                e.vel = Vec3::ZERO;
            }
            MoveRequest::Teleport { target } => {
                e.pos = *target;
                e.vel = Vec3::ZERO;
            }
            MoveRequest::Knockback { impulse } => { e.vel += *impulse; }
            MoveRequest::Force { accel, .. } => { e.vel += *accel * dt; }
            MoveRequest::Wait { .. } => { /* 不动 */ }
        }
    }
}

struct Entity {
    pos: Vec3,
    vel: Vec3,
    queue: VecDeque<MoveRequest>,
}

impl Entity {
    fn new() -> Self { Self { pos: Vec3::ZERO, vel: Vec3::ZERO, queue: VecDeque::new() } }
    fn push(&mut self, r: MoveRequest) { self.queue.push_back(r); }
    fn interrupt(&mut self, r: MoveRequest) {
        self.queue.clear();
        self.queue.push_back(r);
    }
}

fn update(e: &mut Entity, dt: f32) {
    let mut iterations = 0;
    while iterations < 16 {  // 防死循环
        iterations += 1;
        let Some(req) = e.queue.front_mut() else { break; };
        req.apply(e, dt);
        e.pos += e.vel * dt;
        if req.update(dt) {
            e.queue.pop_front();
        } else {
            break;
        }
    }
}

fn main() {
    let mut e = Entity::new();
    // 巡逻:走 0.5s → 等 1s → 冲刺
    e.push(MoveRequest::Walk { vel: Vec3::new(2.0, 0.0, 0.0), duration: 0.5 });
    e.push(MoveRequest::Wait { duration: 1.0 });
    e.push(MoveRequest::Dash { dir: Vec3::new(1.0, 0.0, 0.0), distance: 5.0 });

    let mut last_state = String::new();
    for frame in 0..120 {
        let queue_front = e.queue.front().map(|r| format!("{:?}", r)).unwrap_or_default();
        update(&mut e, 1.0 / 60.0);
        let state = format!("queue_len={}", e.queue.len());
        if state != last_state {
            println!("Frame {:3}: {} pos={:?} vel={:?}", frame, state, e.pos, e.vel);
            last_state = state;
        }
    }

    println!("\n--- Interrupt test ---");
    let mut e2 = Entity::new();
    e2.push(MoveRequest::Walk { vel: Vec3::new(2.0, 0.0, 0.0), duration: 10.0 });
    e2.push(MoveRequest::Wait { duration: 10.0 });
    e2.push(MoveRequest::Dash { dir: Vec3::new(1.0, 0.0, 0.0), distance: 5.0 });
    println!("Before interrupt: {} queued", e2.queue.len());
    update(&mut e2, 1.0 / 60.0);
    println!("After 1 frame: {} queued", e2.queue.len());
    e2.interrupt(MoveRequest::Knockback { impulse: Vec3::new(0.0, 5.0, 0.0) });
    println!("After interrupt: {} queued", e2.queue.len());
    update(&mut e2, 1.0 / 60.0);
    println!("After knockback frame: {} queued, vel={:?}", e2.queue.len(), e2.vel);
}
```

## 10 · 工程反思

Day 656 传达的核心工程教训:**AI 架构是游戏品质的分水岭**。

新手以为"AI = 寻路",资深工程师知道 AI 涉及**感知 / 决策 / 执行 / 学习**多层架构。每个 NPC 都有:

- **感知**:看到 / 听到 / 闻到玩家
- **决策**:基于感知选行为(追 / 逃 / 攻击 / 闲逛)
- **执行**:执行行为(move / animate / play sound)
- **协调**:与其他 NPC 交流(群体 AI)

每层都有自己的实现。Casey 在 HH 用简化的 FSM(有限状态机),工业级用 behavior tree / GOAP / utility AI / ML。

**AI 架构演化**:

- **1990s**:FSM(Pac-Man ghost 4 状态)
- **2000s**:Behavior Tree(Halo 2 引入)
- **2010s**:GOAP / Utility AI(FEAR / Civilization)
- **2020s**:ML(Monte Carlo Tree Search,强化学习)

每种架构解决前一种的局限。FSM 简单但僵硬,BT 灵活但复杂,GOAP 智能但难调,ML 自主但不可预测。

**第二条教训**:**AI debug 是游戏开发最难的**。

AI bug 不是"崩溃"或"数值错",是"行为怪"——NPC 卡墙、攻击自己人、不会用门、重复说话。这些 bug 难复现、难定位、难修复。

工业实践:**AI 录制器 + 行为可视化**。每个 NPC 状态、决策路径、感知范围可视化,debug 时一目了然。这是 Day 638 录制器的扩展应用。

**第三条教训**:**AI 设计师 + 工程师协作**。

工业级 AI 不是工程师独立做,是设计师(写 behavior tree)+ 工程师(写 AI framework)协作。设计师调参数(优先级、阈值),工程师实现框架。

这种协作要求 AI framework **暴露参数**——设计师不用改代码就能调。这是 game designer-friendly 的核心。

**迁移到其他领域**:

"AI 架构"思路在多处通用:

- **机器人**:ROS 的 behavior tree
- **自动化测试**:selenium 的状态机
- **业务流程**:BPMN 工作流
- **智能家居**:Home Assistant 的 automation

每个领域都有"决策架构"。Casey 在 HH 演示的是游戏版本,但思路普适。

## 12 · AI 的伦理设计

AI 设计不只技术,还有伦理:

**1. 沉浸感 vs 操纵**:

- AI 太聪明:玩家觉得"被针对"
- AI 太笨:玩家无聊
- 平衡:AI 表现"刚够聪明"

**2. 难度调节**:

- 动态难度(AI 随玩家水平调整)
- 显式难度(简单 / 中等 / 困难)
- 混合

**3. 公平性**:

- AI 看到玩家不应该"作弊"(不能查玩家位置)
- 但太"公平"AI 显得笨(玩家躲墙后 AI 不知道)

资深 AI 设计师的能力:平衡技术 / 玩家体验 / 工程复杂度。

## N0 • 深度教学补充

### 核心概念重新梳理

Day 656 涉及的核心概念需要在多个层次上理解:

**第一层:直观理解**

新手第一次接触概念,需要建立直觉。例如 voxel collision 是"虚拟物体不能穿过虚拟墙"——这个直觉每个人都能从现实经验获得。

**第二层:数学理解**

把直觉形式化。collision = "两个几何体的体积有交集"。对于 AABB,这等价于"三轴投影都重叠"。

**第三层:工程理解**

数学正确不等于工程实现正确。要考虑:

- 浮点精度边界
- 性能(每帧 N 个查询)
- 内存(数据结构紧凑)
- 边角 case(无穷大、NaN、负数)

**第四层:工业理解**

工业级要再加:

- 多线程安全
- SIMD 优化
- 网络同步(多人游戏)
- 跨平台(Windows/Mac/Linux/Mobile)
- 可访问性(色盲友好)
- 反作弊

每层理解都让代码更鲁棒。资深工程师在所有层次同时思考。

### 实际工程的细节

工业代码 80% 是"边角 case 处理",20% 是"核心算法"。Casey 在 HH 演示核心,工业代码加大量边角处理。

**边角 case 类型**:

1. 空输入(空 Vec、null pointer)
2. 极端输入(NaN、无穷大、超大数)
3. 并发竞争(多线程同时访问)
4. 资源不足(内存满、磁盘满)
5. 网络异常(超时、断连、包丢失)
6. 版本不兼容(老配置 / 新代码)
7. 权限错误(只读文件、无网络)
8. 用户误操作(连点、撤销重做)

每个 case 都要单独处理。这是工业代码 50%+ 行数的原因。

### 优化思路

性能优化有顺序:

1. **算法**:O(N²) → O(N log N),最大提升
2. **数据结构**:Vec → HashMap / BTreeMap,常数提升
3. **Cache**:AoS → SoA,cache 命中提升
4. **SIMD**:4-16 元素并行,巨大常数提升
5. **GPU**:数千核并行,极致性能
6. **分布式**:多机器,无限扩展

每级提升都需要更复杂的代码。先优化低级,够用再升级。

### 教学价值

Day 656 不只是技术教学,也是"工程哲学"教学:

- **简单 > 复杂**:够用就行
- **理解 > 记忆**:概念比代码重要
- **完成 > 完美**:能跑 > 能优化
- **持续学习**:技术永远在演化

这些哲学跨技术领域通用。学完 HH,你不只会写游戏,你**理解工程**。这是 HH 最大的价值。

### Rust 视角

Day 656 用 C 写,但 Rust 版本会更安全 / 更高效:

- **所有权**:消除 use-after-free / double-free
- **borrow check**:消除 data race
- **match exhaustive**:case 漏写编译错
- **Result<T, E>**:错误显式处理
- **no null**:Option<T> 强制 null 检查
- **fearless concurrency**:多线程安全

每条都让代码更鲁棒。Rust 是游戏开发的新趋势(bevy / wgpu / rend3),学习 Rust 让你未来 10 年受益。

### Arch / Linux 视角

Arch Linux 是 HH 教学的隐含平台——一切从命令行开始,理解底层。这对学习极有价值:

- 包管理(pacman)清晰

- 内核可定制
- 工具链完整(gcc, clang, rustup, perf, valgrind)

Arch 用户天然理解 HH 的从零搭起来哲学。其他 distro(Ubuntu)用户要补这部分。
