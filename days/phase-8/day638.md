# Day 638 · 录制图表命令

> 今天是 Handmade Hero 历史上最长的几集之一,Casey 标记为 **Marathon**。问题:体素碰撞重构进入第 8 集,bug 越来越隐蔽——单步调试器看不下问题,因为问题不是"某行代码错了",而是"多帧的状态机演化路径错了"。Casey 的解法是**自建一个"图表录制器"**:把每帧的几何状态(bbox、voxel、推回向量)录成命令流,事后回放、单步、可视化。

## 0 · 为什么要有这一天

你大概用过 gdb / lldb。它们的模型是"程序停在某个断点,你查看变量"。这种模型适合"逻辑 bug",但**不适合"动态状态 bug"**:

- 玩家在拐角卡住,但不知道是哪一帧开始的
- voxel 解嵌向量"看起来对",但累加之后错位
- 物理 step 1 帧看不出问题,要连续看 30 帧

gdb 一次只能看一个时刻。如果你 set watch 一个变量,每次变化都会停,你就要按 30 次继续,而且每次都丢失"全局视图"。

**图表录制器**的核心思路:**让游戏正常跑(不被打断),同时把每帧的"几何状态"录到内存里**,跑完之后再回放。这就是商用引擎的 **timeline debugger** / **frame profiler** 的思路——Unity 有 Recorder,Unreal 有 Session Frontend,Insomniac 有 Hubba。

但 Casey 不要用别人的工具,他要**自己写一个**。为什么?

1. **教学价值**:你看到工具是怎么从零长出来的
2. **集成度**:Casey 的图表录制器和游戏共享内存、共享坐标系,不需要导出再导入
3. **定制化**:他能精确控制"录什么",只录和当前 bug 相关的几何,不录噪声

今天的 marathon 体现在:**一套完整的"录制 → 回放 → 单步 → 可视化"管线**,涉及 immediate-mode UI、命令模式(command pattern)、frame timeline、SVG-like 矢量绘图。Casey 花了大半天把它写完。

心理锚点:看完今天,你能:

- 设计自己的 immediate-mode debug draw 系统
- 理解"录制-回放"调试范式 vs "断点"调试范式
- 用"命令流"表达几何操作,而不是直接调 draw 函数

## 1 · Casey 今天做了什么

Casey 的具体动作(7+ 小时的 marathon,精简成主线):

1. 引入一个 `DebugDiagram` 结构,内部是一个**命令缓冲**(command buffer),记录用户画的几何
2. 定义命令种类:`DrawPoint / DrawLine / DrawAABB / DrawText / PushColor / PopColor` 等
3. 在 collision 代码里,不再直接调 `draw_aabb()`,而是调 `diagram.draw_aabb()`——只是 push 一个命令到 buffer
4. 每帧末尾把 buffer 的内容 render 到屏幕(debug overlay)
5. 加一个 frame buffer:不只录当前帧,还录前 N 帧
6. 加键盘控制:暂停 / 单步前进 / 单步后退 / 跳到指定帧
7. 加慢放 / 快放,frame-by-frame 看每一步碰撞演化

注意 Casey 用 **immediate mode**:每帧重画 UI,不存"控件树"。这是Dear ImGui / Casey 的 Handmade Hero UI 的核心思路。

## 2 · 心智模型

录制器的核心抽象是 **command pattern**——把"画什么"建模为数据,而不是函数调用。这是 software engineering 经典模式,在游戏开发里尤其有用。

**为什么 command pattern 适合录制?**

传统 debug 用"立即画"——`draw_line(from, to, color)`。问题是:

- 无法回放(画完就消失)
- 无法测试(画的什么无法 assert)
- 无法优化(每次都从头画)

command pattern 把画变成数据:

```rust
enum Cmd {
    Line { from: Vec3, to: Vec3, color: u32 },
    AABB { min: Vec3, max: Vec3, color: u32 },
    Text { pos: Vec3, text: String, color: u32 },
}
```

每帧收集 Vec<Cmd>,后续可以:

- 渲染(立即画)
- 录制(存到 ring buffer)
- 回放(从 buffer 读)
- 测试(assert 某帧包含特定 Cmd)
- 序列化(存盘分享)

这是"延迟执行"——把"画"和"何时画"解耦。资深工程师用 command pattern 解决一类"操作时序"问题。

### 类比:录制视频而不是看监控

调试 bug 有两种隐喻:

**断点调试(监控室)**:你坐在监控室,有 100 路监控,你切到某一路,看当下。如果错过了关键画面,你只能等下次发生。
**录制回放(拍摄视频)**:你在每个监控点架一台摄像机,一直录,事后挑某段回放、慢放、暂停。

游戏调试 90% 用第二种更有效,因为 bug 涉及多帧演化。Casey 今天的图表录制器就是摄像机。

### 命令模式(command pattern)

直接调 draw 函数的写法:

```rust
fn draw_collision_debug() {
    draw_aabb(player_bbox, RED);
    for v in colliding_voxels {
        draw_voxel(v, GREEN);
    }
    draw_arrow(correction_vector, BLUE);
}
```

问题:这只在"当下"画。如果你想"看上一帧",没办法——上一帧的几何已经丢失。

**命令模式**的写法:把 draw 调用变成"录制命令":

```rust
fn record_collision_debug(d: &mut Diagram) {
    d.push(AABB(player_bbox, RED));
    for v in colliding_voxels {
        d.push(Voxel(v, GREEN));
    }
    d.push(Arrow(correction_vector, BLUE));
}
```

`d` 内部是个 `Vec<Command>`,可以**存到任意长的时间**(只要内存够)。回放时:

```rust
fn playback(d: &Diagram, renderer: &mut Renderer) {
    for cmd in &d.commands {
        renderer.execute(cmd);
    }
}
```

这就是 Casey 的核心架构。**录制 = 把几何操作变成数据**,而不是直接执行。这是经典的 **data over behavior** 思路——Unix 的管道、vim 的宏、Photoshop 的 Action,都是这个思路。

### 命令种类设计

Casey 的命令 enum:

```rust
enum DiagramCmd {
    Point { pos: Vec3, color: u32 },
    Line { from: Vec3, to: Vec3, color: u32 },
    AABB { min: Vec3, max: Vec3, color: u32 },
    Text { pos: Vec3, text: String, color: u32 },
    Arrow { from: Vec3, to: Vec3, color: u32 },
    PushTransform { mat: Mat4 },
    PopTransform,
}
```

`PushTransform / PopTransform` 用栈管理坐标变换,可以画"局部坐标的几何"——比如玩家本地空间的 bbox,然后整体平移到玩家世界坐标。

为什么 enum?Rust 的 enum 是 sum type(和类型),每个变体可以有自己的字段。比 OOP 的"基类 + 子类"更紧凑,内存连续(`Vec<DiagramCmd>` 是连续内存,cache 友好)。

### Immediate mode UI vs Retained mode UI

**Retained mode**(传统 GUI):你创建一个 button 对象,设置 callback,GUI 框架持有这个对象。例:Qt、GTK。

**Immediate mode**(Casey / ImGui):每帧调用 `ui.button("label")` 函数,函数返回 true 表示"这一帧被点了"。**没有持久对象**,每帧从零画。

Immediate mode 的优势:

- 无状态,bug 少
- 数据流显而易见(代码顺序就是 UI 顺序)
- 天然支持录制/回放——每帧就是一个独立 function call 流

Casey 的图表录制器本质是 **deferred immediate mode**:这一帧 record,下一帧(或某帧之后)replay。这是 immediate + retained 的混合。

### Frame timeline 数据结构

```rust
struct FrameTimeline {
    frames: Vec<FrameData>,
    cursor: usize, // 当前回放位置
}

struct FrameData {
    commands: Vec<DiagramCmd>,
    dt: f32, // 这一帧耗时
    player_pos: Vec3,
    // ... 其他想录的状态
}
```

容量管理:`frames` 用 ring buffer(`VecDeque` 或固定数组 + 环形索引),避免无限增长。Casey 录最近 300 帧(5 秒 @ 60fps)。

### 单步前进/后退的实现

后退比前进难——游戏世界是"前向演化"的,你不能让物理"反向跑"。但**录制器不需要反向演化**,它只是回放命令流:

```rust
fn render_at(timeline: &FrameTimeline, frame_idx: usize, r: &mut Renderer) {
    let frame = &timeline.frames[frame_idx];
    for cmd in &frame.commands {
        r.execute(cmd);
    }
}
```

前进就是 `frame_idx += 1`,后退就是 `frame_idx -= 1`。**因为几何被存成了"声明式数据",不是"过程化调用",所以任意一帧都能直接画**——这是声明式 vs 命令式的核心差别。

### 为什么不用 rr (record and replay)

Linux 上有 `rr`(Mozilla 的 record-replay debugger),可以录整个进程然后反向单步。Casey 没用,因为:

- `rr` 在游戏场景下慢 5-10 倍,实时跑不起来
- `rr` 录的是"系统调用流",对"游戏内几何状态"无概念
- Casey 想要的是"按游戏帧"timeline,不是"按指令"timeline

`rr` 适合 "core dump 后反向追",不适合"60fps 实时跑 + 看演化"。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏里的"录制"非常常见:

- **Replay 系统**:星际争霸、CS:GO 都有 replay——把每帧的输入/状态录下来,事后回放
- **死亡回放**(killcam):CoD 的 killcam 是录最近 5 秒玩家视角,从击杀者视角重放
- **Ghost racing**:马里奥赛车的时间竞速模式,录"最佳圈"的 ghost
- **Training data 录制**:ML 训练游戏 AI 时,录玩家行为做 imitation learning

Casey 的图表录制器是**调试专用**,不存到磁盘,只录几何状态。但架构和 replay 系统是同源的——都是"声明式状态 + 时间序列"。

### 3.2 · 图形学视角

图形管线里的"录制":

- **Display list**:老式 OpenGL 的 glNewList / glCallList——把绘制命令录到一个 list 里,反复回放。现代 OpenGL 用 VBO 替代。
- **Command buffer**:Vulkan / DX12 的核心——把渲染命令录到 buffer,提交给 GPU 执行。Casey 的设计是 CPU 版本。
- **Render graph**:现代引擎(Unity HDRP、Unreal RDG)用 render graph 描述整帧渲染结构,本质是声明式 command buffer。

Casey 的"diagram command"和 Vulkan 的 command buffer 在抽象上一样——**把行为变成数据,延迟执行**。

### 3.3 · Linux 系统编程视角

Linux 上的"录制"工具:

- **strace**:录系统调用,事后回放——文本流形式的 command buffer
- **perf record**:采样 CPU 状态,事后 `perf report`
- **ftrace**:内核函数调用追踪
- **rr**:进程级 record-replay
- **rr + gdb combo**:`rr replay` 启动 gdb session,可以反向 continue

 Casey 的录制器和这些工具的差别:**粒度**。strace 是"系统调用粒度",Casey 的是"游戏帧 + 几何粒度"。后者更贴近游戏开发者关心的"游戏世界状态"。

### 3.4 · Rust 生态视角

Rust 的 enum + match 让命令模式非常优雅:

```rust
#[derive(Clone, Debug)]
enum DiagramCmd {
    Point { pos: [f32; 3], color: u32 },
    Line { from: [f32; 3], to: [f32; 3], color: u32 },
    AABB { min: [f32; 3], max: [f32; 3], color: u32 },
    Text { pos: [f32; 3], text: String, color: u32 },
    PushTransform { mat: [f32; 16] },
    PopTransform,
}

struct Diagram {
    cmds: Vec<DiagramCmd>,
    transform_stack: Vec<[f32; 16]>,
}

impl Diagram {
    fn point(&mut self, pos: [f32; 3], color: u32) {
        self.cmds.push(DiagramCmd::Point { pos, color });
    }
    fn aabb(&mut self, min: [f32; 3], max: [f32; 3], color: u32) {
        self.cmds.push(DiagramCmd::AABB { min, max, color });
    }
    fn execute(&self, r: &mut Renderer) {
        for cmd in &self.cmds {
            match cmd {
                DiagramCmd::Point { pos, color } => r.draw_point(*pos, *color),
                DiagramCmd::Line { from, to, color } => r.draw_line(*from, *to, *color),
                DiagramCmd::AABB { min, max, color } => r.draw_aabb(*min, *max, *color),
                DiagramCmd::Text { pos, text, color } => r.draw_text(pos, text, *color),
                DiagramCmd::PushTransform { mat } => r.push_transform(*mat),
                DiagramCmd::PopTransform => r.pop_transform(),
            }
        }
    }
}
```

`String` 在 enum 里要注意:它有所有权,所以 `DiagramCmd` 不是 `Copy`。`Vec<DiagramCmd>` 仍然合法,但你不能 `cmd1 = cmd2`(只能 clone)。

| 粒度 | 工具 | 适合 |
|---|---|---|
| 指令级 | rr / gdb stepi | 编译器 / 库 bug |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:录制器用 `enum DiagramCmd`,而不用 trait object `Box<dyn Draw>`。两种做法的优劣?

**参考解答**:

enum + match 的优势:
- 内存连续(整个 Vec 是一块),cache 友好
- 编译期穷尽检查(match 漏一个变体,编译器警告)
- 无虚函数调用,inline 友好
- 容易序列化(enum 可以 `#[derive(Serialize)]`)

trait object 的优势:
- 开放集合(第三方 crate 可以加新的 Draw 类型)
- 多态参数更灵活

Casey 选 enum 因为命令种类封闭(只有那几种),性能优先。如果命令集会随插件扩展,trait object 更合适。

### Lv2 · 动手实践

**题**:实现 §3.4 的 `Diagram` 结构,加上一个假 Renderer(只打印命令),写测试:

```rust
fn main() {
    let mut d = Diagram::new();
    d.point([1.0, 2.0, 3.0], 0xFF0000);
```

**参考解答**:

```rust
#[derive(Clone, Debug)]
enum DiagramCmd {
    Point { pos: [f32; 3], color: u32 },
    Line { from: [f32; 3], to: [f32; 3], color: u32 },
    AABB { min: [f32; 3], max: [f32; 3], color: u32 },
    Text { pos: [f32; 3], text: String, color: u32 },
}

struct Diagram { cmds: Vec<DiagramCmd> }

impl Diagram {
    fn new() -> Self { Self { cmds: Vec::new() } }
    fn point(&mut self, pos: [f32; 3], color: u32) {
        self.cmds.push(DiagramCmd::Point { pos, color });
    }
    fn aabb(&mut self, min: [f32; 3], max: [f32; 3], color: u32) {
        self.cmds.push(DiagramCmd::AABB { min, max, color });
    }
    fn execute(&self, r: &mut dyn Renderer) {
        for cmd in &self.cmds {
            match cmd {
                DiagramCmd::Point { pos, color } => r.draw_point(*pos, *color),
                DiagramCmd::Line { from, to, color } => r.draw_line(*from, *to, *color),
                DiagramCmd::AABB { min, max, color } => r.draw_aabb(*min, *max, *color),
                DiagramCmd::Text { pos, text, color } => r.draw_text(*pos, text, *color),
            }
        }
    }
}

trait Renderer {
    fn draw_point(&mut self, pos: [f32; 3], color: u32);
    fn draw_line(&mut self, from: [f32; 3], to: [f32; 3], color: u32);
    fn draw_aabb(&mut self, min: [f32; 3], max: [f32; 3], color: u32);
    fn draw_text(&mut self, pos: [f32; 3], text: &str, color: u32);
}

struct PrintRenderer;
impl Renderer for PrintRenderer {
    fn draw_point(&mut self, pos: [f32; 3], color: u32) {
        println!("point at {:?} color #{:06X}", pos, color);
    }
    fn draw_line(&mut self, from: [f32; 3], to: [f32; 3], color: u32) {
        println!("line {:?} -> {:?} color #{:06X}", from, to, color);
    }
    fn draw_aabb(&mut self, min: [f32; 3], max: [f32; 3], color: u32) {
        println!("aabb {:?}-{:?} color #{:06X}", min, max, color);
    }
    fn draw_text(&mut self, pos: [f32; 3], text: &str, color: u32) {
        println!("text {:?} '{}' color #{:06X}", pos, text, color);
    }
}

fn main() {
    let mut d = Diagram::new();
    d.point([1.0, 2.0, 3.0], 0xFF0000);
    d.aabb([0.0, 0.0, 0.0], [1.0, 1.0, 1.0], 0x00FF00);
    let mut r = PrintRenderer;
    d.execute(&mut r);
}
// 输出:
// point at [1.0, 2.0, 3.0] color #FF0000
// aabb [0.0, 0.0, 0.0]-[1.0, 1.0, 1.0] color #00FF00
```

### Lv3 · 迁移设计

**题**:把录制器扩展成"时间窗口"——不只录当前帧,还录最近 N 帧。设计 API:`fn frame_begin(&mut self); fn frame_end(&mut self);`,中间的命令都属于"当前帧",结束后 push 到 ring buffer。设计 `fn playback(&self, frame_offset: i32, r: &mut dyn Renderer)`,正负 offset 表示未来/过去帧。

**提示**:用 `Vec<Vec<DiagramCmd>>` 加 head index,或 `VecDeque<Vec<DiagramCmd>>`。

### Lv4 · 进阶设计

**进阶题**:录制器支持"标记帧"——开发者按键标记某一帧,事后从标记列表快速跳转。设计 API 和数据结构。

**思路**:

```rust
struct Recorder {
    frames: VecDeque<Vec<Cmd>>,
    bookmarks: Vec<(usize, String)>,  // (frame_idx, label)
    capacity: usize,
}

impl Recorder {
    fn add_bookmark(&mut self, label: String) {
        let current_idx = self.frames.len().saturating_sub(1);
        self.bookmarks.push((current_idx, label));
    }
    fn jump_to_bookmark(&self, label: &str) -> Option<usize> {
        self.bookmarks.iter()
            .find(|(_, l)| l == label)
            .map(|(idx, _)| *idx)
    }
}
```

这是 time-travel debugging 的核心——开发者标记关键事件,事后快速定位。Unity / Unreal / Visual Studio 都有"bookmark"功能。

**工业实例**:

- **RenderDoc**:每个 draw call 自动"标记",用户可跳转
- **Tracy**:profiler 标记关键 frame,分析性能
- **Chrome DevTools**:network 请求标记,debug 时序
- **rr / UndoDB**:每个系统调用标记,debug 复杂流程

每个工具都基于"标记 + 跳转"。Casey 在 HH 演示最简版本。

## 8 · Rust / Arch 落地代码

完整可跑示例:录制器 + 多帧 ring buffer + 单步控制。

```rust
// Cargo.toml: 无依赖,纯 std

use std::collections::VecDeque;

#[derive(Clone, Debug)]
enum Cmd {
    Point([f32; 3], u32),
    Line([f32; 3], [f32; 3], u32),
    AABB([f32; 3], [f32; 3], u32),
    Text([f32; 3], String, u32),
}

struct Frame {
    cmds: Vec<Cmd>,
    frame_num: u64,
}

struct Recorder {
    current: Vec<Cmd>,
    history: VecDeque<Frame>,
    capacity: usize,
    frame_num: u64,
}

impl Recorder {
    fn new(capacity: usize) -> Self {
        Self {
            current: Vec::new(),
            history: VecDeque::with_capacity(capacity),
            capacity,
            frame_num: 0,
        }
    }
    fn point(&mut self, p: [f32; 3], c: u32) { self.current.push(Cmd::Point(p, c)); }
    fn aabb(&mut self, min: [f32; 3], max: [f32; 3], c: u32) {
        self.current.push(Cmd::AABB(min, max, c));
    }
    fn text(&mut self, p: [f32; 3], s: &str, c: u32) {
        self.current.push(Cmd::Text(p, s.to_string(), c));
    }
    fn frame_end(&mut self) {
        let frame = Frame {
            cmds: std::mem::take(&mut self.current),
            frame_num: self.frame_num,
        };
        if self.history.len() == self.capacity {
            self.history.pop_front(); // 丢掉最老的
        }
        self.history.push_back(frame);
        self.frame_num += 1;
    }
    fn playback(&self, offset: i32) {
        // offset = 0 表示最新一帧,-1 表示上一帧,+1 不存在(未来未发生)
        let idx = if offset >= 0 {
            self.history.len().checked_sub(1 + offset as usize)
        } else {
            None // 暂不支持未来
        };
        match idx {
            Some(i) => {
                let frame = &self.history[i];
                println!("=== Frame {} ({} cmds) ===", frame.frame_num, frame.cmds.len());
                for cmd in &frame.cmds {
                    println!("  {:?}", cmd);
                }
            }
            None => println!("no such frame"),
        }
    }
}

fn main() {
    let mut rec = Recorder::new(300); // 录最近 300 帧

    // 模拟 3 帧游戏
    for f in 0..3 {
        rec.point([f as f32, 0.0, 0.0], 0xFF0000);
        rec.aabb([0.0, 0.0, 0.0], [f as f32 + 1.0, 1.0, 1.0], 0x00FF00);
        rec.text([0.0, 2.0, 0.0], &format!("frame {}", f), 0xFFFFFF);
        rec.frame_end();
    }

    // 回放
    rec.playback(0); // 最新
    rec.playback(1); // 上一帧
    rec.playback(2); // 上上帧
    rec.playback(3); // 不存在
}
```

## 9.5 · 录制器在工业的位置

录制器是工业级游戏 debug 基础设施的核心组件。每个 AAA 游戏工作室都有自己的实现:

- **Insomniac**:Hubba system,统一 debug overlay
- **Naughty Dog**:custom debug draw,集成到引擎
- **Epic Games**:Unreal Insight,profiling + debug overlay
- **Unity**:Frame Debugger + Profiler
- **Valve**:Source 2 的 debug overlay

每个工作室投资百万级美元到这套基础设施。原因是 ROI 极高——一次投资,十年受益。Casey 在 HH 用一集演示最简版本,工业级是几万行代码。但思路相同:**command pattern + ring buffer + 可视化**。

新手工程师不重视 debug 工具("只是工具,不是产品"),资深工程师把它视为基础设施("没有好工具,产品做不出来")。这是工业思维的差异。

## 10 · 工程反思

Day 638 传达的核心工程教训:**录制器是工业级 debug 基础设施**。

新手工程师 debug 用"print 大法"——在代码里塞 println!,看输出。但游戏 bug 涉及空间 / 时间演化,print 输出是 1D 文本,无法表达 2D/3D/4D 数据。所以工业级游戏都有"录制器"——每帧记录状态,事后回放、可视化、单步。

**录制器的本质是"把执行转成数据"**。运行时把状态序列化到 buffer,UI 时再反序列化渲染。这等于"延迟执行"——把"实时画 debug 几何"延迟到"任意时刻画任意时刻的几何"。这是延迟求值(lazy evaluation)在 debug 工具上的应用。

**录制器在工业的价值**:

- **复现 bug**:玩家报告"第 30 秒卡住",你回放第 30 秒
- **A/B 对比**:同一帧不同算法的输出对比
- **共享 debug**:把录制发同事,他能在自己机器分析
- **回归测试**:每次改代码后跑同一录制,确认结果一致
- **教学**:录制展示"什么是好 / 坏"

每个价值都让团队效率提升 10-100 倍。所以**没有录制器的团队,debug 速度慢 10 倍**。这是工业教训。

**为什么 Casey 不用现成工具**(RenderDoc / Tracy / Pix)?

因为这些工具针对"通用渲染管线",不针对"voxel 碰撞"这种特定问题。Casey 需要的录制器要画 voxel grid、bbox、raycast、velocity vector——这些是 HH 特定的。现成工具只能画 mesh / shader / draw call,不能画 voxel grid。

工业实践:**每个复杂项目都需要自定义 debug overlay**。Unity 有 Gizmos,Unreal 有 DrawDebugLine,但项目仍要写自己的"业务特定 debug"。Casey 在 HH 演示的录制器是这个"业务特定"层的最简实现。

**第二条教训**:**immediate-mode UI 适合 debug overlay**。Casey 不用 retained-mode UI(HTML / Qt),用 immediate-mode(类似 Dear ImGui)。原因:

- 状态最小化(每帧重新构造 UI)
- 灵活(任何代码可加 debug 命令)
- 无副作用(关掉 = 不存在)

retained-mode UI 适合"应用",immediate-mode UI 适合"工具"。Day 638 的录制器是后者的典型。

**迁移到其他领域**:

"录制器"思路在多个领域有对应:

- **Flight recorder**(飞机黑匣子):记录所有传感器数据,事后分析
- **Network packet capture**(Wireshark):抓网络包,事后分析
- **Database query log**:每个 query 记录,事后优化
- **Browser DevTools**:记录所有请求 / 渲染,事后 debug
- **Time-travel debugger**(UndoDB / rr):记录程序执行,事后任意点查看

每个领域都需要"记录 + 回放 + 分析"的 debug 基础设施。Casey 在 HH 实现的是游戏版本。
