
# Day 651 · 修复光反馈

> 光照系统又一个微妙 bug:**间接光反复累积,越来越亮**。某些位置的光照值每秒翻倍,最终整屏白。今天 Casey 调查——发现是**间接光反馈循环**:A 表面收到 B 表面的间接光,把光"反弹"回 B,B 又反弹回 A,无限累加。

## 0 · 为什么要有这一天

间接光(indirect lighting,或 global illumination,GI)是真实光照的核心:光照到地面,反弹到墙上,墙上的光又反弹到天花板......每次反弹衰减,但理论上无限。

要理解这个 bug,需要先理解**真实物理的光传输模型**。当一束光从光源射出,撞到一个表面,会发生三件事:

1. **吸收**(absorption):一部分光能被材质吸收,变成热能(这就是为什么深色物体在阳光下变热)
2. **漫反射**(diffuse reflection):一部分光被均匀散射到上半球——这是肉眼看到的"物体颜色"
3. **镜面反射**(specular reflection):一部分光按"入射角=反射角"反射,形成高光

材质的**反射率**(albedo)就是 (2) + (3) 占入射光的比例。剩余 (1 - albedo) 被吸收。物理上,**albedo 永远 < 1**——没有任何材质能 100% 反弹所有光(否则能量守恒被违反)。

游戏渲染器在模拟间接光时,必须把"反弹衰减"实现进去,否则光在虚拟场景里无限累加。Casey 之前的代码漏了这个,所以出现指数爆炸。

预计算光表时,Casey 之前的算法是:

```
for each surface:
    for each other surface as indirect source:
        add indirect light contribution
```

问题:如果两个 surface 互相"看"对方,它们的间接光会互相累加。第一轮 A 反弹光到 B,第二轮 B 反弹(包含 A 给的)回 A,A 现在有更多光,第三轮反弹更多......指数爆炸。

这个 bug 的根因是**物理模型缺失**——代码不对应真实物理。物理上每次反弹必然有吸收,代码里没有。修法不是"加补丁",而是"补回物理":**让每次反弹乘 albedo**(吸收率),albedo < 1 保证能量衰减。

修法:**限制反弹次数**(bounces),或**用收敛算法**(radiosity iterative solver)。

心理锚点:看完今天,你能:

- 解释间接光的反馈问题
- 实现反弹次数限制
- 理解 radiosity(辐射度)算法
- 用矩阵特征值判断迭代收敛性
- 区分物理建模和数值实现两个层次

## 2 · 心智模型

### 类比:两镜子对面

两面镜子面对面放着,你站中间——看到无数个自己的倒影。每次反射光强度衰减一点,但理论无穷。

间接光也这样:两个 surface 互相反弹光,理论无穷次。**真实物理**里,光每次反弹被材质吸收一部分(不能 100% 反弹),所以最终衰减到 0。但**游戏代码**里如果不实现这个吸收,光就会无限累加。

### Albedo(反射率)

每个表面有 albedo(反射率):

- albedo = 0:全吸收(黑体)
- albedo = 0.5:50% 反弹
- albedo = 1.0:全反弹(完美镜面或白墙)

实际游戏材质 albedo 通常 0.1-0.5。Casey 之前忘了加 albedo,默认 1.0,所以反弹无穷。

### 反弹次数限制

物理上,光反弹无限次,但**能量迅速衰减**。albedo = 0.5 时,10 次反弹后剩 0.5^10 = 0.001(几乎黑)。所以代码里反弹 3-5 次就够。

### 收敛性数学

记 N 个表面,光强向量 L = (L_1, L_2, ..., L_N)。一次反弹 = 矩阵乘法 `L_new = K * L`,K 是反弹矩阵(K_ij 表示 j 反弹到 i 的光比例)。

**收敛条件**:K 的最大特征值 < 1。

如果 albedo 全 1.0,K 特征值可能 = 1,不收敛。加 albedo < 1 后,特征值 < 1,收敛。

这是 **Power Iteration**(幂迭代)算法——反复乘 K,直到 L 不再变化。

```rust
let mut light = initial_light;
for _ in 0..3 {  // 3 次反弹
    let mut new_light = initial_light; // 直接光每轮加
    for i in 0..N {
        for j in 0..N {
            if i != j && visibility[i][j] {
                new_light[i] += light[j] * form_factor[i][j] * albedo[j];
            }
        }
    }
    light = new_light;
}
```

`form_factor[i][j]` 是几何系数(表面 j 反弹的光到表面 i 的比例),`visibility[i][j]` 是 i 能否看到 j(raycast)。

为什么"特征值 < 1 ⟹ 收敛"?让我把推导讲清楚。

设迭代式:`L_{n+1} = E + K * L_n`,其中 E 是直接光(常数),K 是反弹矩阵。我们想看 L_n 是否收敛到某个不动点。

假设 L_n 收敛到 L*,则 `L* = E + K * L*`,解出 `L* = (I - K)^{-1} * E`(如果 I - K 可逆)。

误差:`e_n = L_n - L*`,则 `e_{n+1} = L_{n+1} - L* = (E + K*L_n) - (E + K*L*) = K * (L_n - L*) = K * e_n`。

所以 `e_n = K^n * e_0`。

把 e_0 在 K 的特征基下展开:`e_0 = sum_i c_i * v_i`,v_i 是 K 的特征向量,对应特征值 λ_i。

那么 `e_n = K^n * e_0 = sum_i c_i * λ_i^n * v_i`。

如果所有 |λ_i| < 1,则 λ_i^n → 0,e_n → 0,L_n → L*,收敛。

如果某个 |λ_i| ≥ 1,则 λ_i^n 不趋于 0,e_n 不趋于 0,可能发散或震荡。

对反弹矩阵 K = form_factor ∘ albedo(逐元素乘),如果所有 albedo < 1,且 form_factor 行和 ≤ 1(能量守恒),那么 K 的最大特征值 < 1(由 Perron-Frobenius 定理 + Gershgorin circle theorem)。

这就是为什么加 albedo < 1 能修 bug——数学保证收敛。

### Radiosity(辐射度)

radiosity 算法就是间接光的标准实现:

1. 把场景离散成 patches(小面片)
2. 算 form factor 矩阵
3. 解线性方程组 `B = E + R * F * B`,其中 B 是最终辐射度,E 是直接光,R 是反射率,F 是 form factor
4. 解出 B,作为最终光照

工业实现用 **Gauss-Seidel iteration**(高斯-赛德尔迭代):每次更新一个 B_i 用最新值。收敛比朴素迭代快。

Casey 简化版:固定 3 次迭代 + albedo 衰减,不严格解方程。

Form factor 的计算公式(两个 patch i, j):

```
F_ij = (cos θ_i * cos θ_j) / (π * r^2) * visibility_ij * A_j
```

θ_i, θ_j 是表面法线和两点连线的夹角,r 是距离,A_j 是 j 的面积。这个公式来自**热辐射学**——1980s 的 Goral、Cohen、Greenberg 把它从工程引入图形学,获得了 SIGGRAPH 成就奖。

直观理解:

- `cos θ_i * cos θ_j`:两个表面"面对面"时光传输效率高,擦肩而过时低
- `1/r^2`:距离平方衰减(光的扩散)
- `visibility_ij`:几何遮挡(中间有墙就 0)
- `A_j`:发射面积,j 越大发射光越多

## 3 · 四域深入

### 3.1 · 游戏编程视角

GI(全局光照)的工业实现:

- **Quake 1**:radiosity baking 离线,lightmap 存预计算结果
- **Half-Life 2**:cube map lightprobe + radiosity
- **CryEngine**:Light Propagation Volume(LPV)实时 GI
- **Unreal**:Photon mapping + irradiance cache
- **RTX / DXR**:硬件实时光线追踪 GI

HH 的简化版是 1990s 的标准做法。

**Quake 1 的 radiosity** 是 GI 在游戏的第一次大规模工业化。id Software 用 ARGB lightmap(每像素 4 字节)存预计算的间接光,运行时只查表。Bake time 几分钟到几小时(取决于地图复杂度)。这套技术一直用到 Source 引擎(Half-Life 2)时代,2004 年左右。

**Crytek LPV**(2010,Crysis 2)是实时 GI 的突破:把场景分成 3D 网格,每格存球谐(SH)光分布,光在网格里"传播"几次得到 GI。优点是 100% 实时(可动态光源),缺点是分辨率低、有"格子 artifact"。

**Unreal Lightmass**(2009,UE3)是离线 GI,类似 Quake radiosity 但用 photon mapping + final gather,质量高。UE4 加了 LPV 类似物,UE5 用 Lumen(实时 + 离线混合 + ML denoise)。

**RTX GI**(2018+,NVIDIA)用硬件 RT core 算光线追踪,每秒 10+ GRay。配合 DLSS / Reflex / RTX Direct Illumination,单帧 30 FPS 跑几十个反弹。Crysis Remastered / Cyberpunk 2077 / Minecraft RTX 都用。

每个时代的"GI 圣杯"都不一样:1990s 求"能跑",2000s 求"好看",2010s 求"实时",2020s 求"逼真 + ML 加速"。HH 选 1990s 的方案是教学最优——简单、可解释、能完整实现。

Casey 在视频里特别强调:"我不要'看起来好看'的 hack,我要'理解每个像素为什么这么亮'的简单模型"。这是教学项目的正确取舍。

### 3.2 · 图形学视角

GI 算法分类:

| 算法 | 反弹 | 适合 |
|---|---|---|
| Direct only | 0 | 极简游戏 |
| Single bounce | 1 | 移动设备 |
| Multi-bounce radiosity | 3-5 | ✅ HH 选 |
| Path tracing | 1000+ | 离线渲染 |
| Photon mapping | 5-10 | 复杂场景 |
| ML GI(Neural) | 学习 | RTX |

反弹越多越真实,但成本指数增长。

**Path tracing**(路径追踪)是离线渲染(电影特效、动画)的金标准。它的思路:**从相机每个像素出发,反向追踪光线**——光击中表面,随机选一个新方向继续,反弹若干次后击中光源。所有路径采样的平均就是像素颜色。1000+ 反弹让结果接近物理真实,但每像素要采样几千条路径,几十小时一帧。

**Photon mapping**(光子映射)是 Jensen 1996 提出的混合方法:第一阶段从光源发射光子,追踪到 diffuse 表面,存到光子图;第二阶段从相机渲染,在 diffuse 表面查光子图估算间接光。优点是比 path tracing 快,缺点是 memory hungry。

**Light Propagation Volume (LPV)** 是 Crytek 在 CryEngine 3 引入的实时方法:把场景分成 3D 网格,每格存球谐(spherical harmonics)表示的入射光。光在网格里"传播"几次,得到近似 GI。快但精度有限。

**RTX / DXR**(2018+)硬件加速光线追踪:GPU 有专用 RT core,每秒能算几十亿次 ray-triangle intersection。让 path tracing 实时化。但单帧仍只能采样几十个反弹(对比离线的几千),要 DLSS 之类的 upscaler + denoiser 才能稳定 60 FPS。

**Neural radiance cache**(2023+):用神经网络缓存间接光,推理时直接采样。NVIDIA 在 DLSS 3.5 / Reflex / RTX Direct Illumination 都用到。这是 GI 的最新方向,但仍未完全替代传统方法。

HH 选 radiosity(3 bounces)是 1990s 的标准做法,Quake 1 / Half-Life 1 都是这套。教学价值在于:**简单到能完整实现,够展示 GI 的核心思想**。

### 3.3 · Linux 系统编程视角

Linux 里"反馈循环"案例:

- **TCP congestion control**:loss → 减速 → 减少拥塞 → 加速 → 增加拥塞——典型反馈
- **page cache balancing**:内存压力大 → 回收 → 减少 cache → IO 变慢 → 减少压力
- **CPU thermal throttle**:温度高 → 降频 → 温度低 → 升频

每个反馈循环必须有"阻尼"(damping),否则震荡或爆炸。Casey 的 albedo < 1 就是阻尼。

**TCP 拥塞控制**的细节最能类比今天的 bug。早期 TCP(Reno)用 AIMD(Additive Increase, Multiplicative Decrease):

- 每收到一个 ACK,拥塞窗口 +1(线性增长)
- 每检测到 loss,窗口 ÷ 2(乘性减少)

这是收敛的——loss 时大幅减,success 时小幅加,长期均值收敛到网络容量。如果反过来(loss 时加,success 时减),网络流量会指数爆炸,整个互联网崩。

**Page cache** 同样:Linux 内核守护进程 `kswapd` 监控内存压力,压力高时回收 page cache。这是负反馈——压力↑ → 回收↑ → 压力↓。如果实现成正反馈(压力↑ → 不回收 → 压力↑↑),系统几秒内 OOM。

**CPU 频率调节**(intel_pstate / amd-pstate)类似:温度高 → 降频 → 温度降 → 升频。如果调节系数错(过激),会震荡——频率在 max/min 之间快速切换,用户体验卡顿。这就是为什么内核 schedutil governor 用温和的步进。

Casey 的间接光爆炸 = 把反馈循环的阻尼(albedo)设成了 1.0(无衰减),等价于"TCP 每收到 ACK 就翻倍窗口",几秒内网络崩。修法就是加 albedo < 1 的阻尼。

### 3.4 · Rust 生态视角

Rust 实现收敛迭代的优雅写法:

```rust
fn iterate_radiosity(
    initial: &Vec<f32>,
    form_factor: &Vec<Vec<f32>>,
    albedo: &Vec<f32>,
    bounces: usize,
) -> Vec<f32> {
    let mut current = initial.clone();
    for _ in 0..bounces {
        let mut next = initial.clone(); // 直接光每轮加
        for i in 0..current.len() {
            for j in 0..current.len() {
                if i == j { continue; }
                next[i] += current[j] * form_factor[i][j] * albedo[j];
            }
        }
        current = next;
    }
    current
}
```

`&Vec<f32>` 借用,无 clone。`albedo[j]` < 1 是阻尼,保证收敛。

Rust 生态里 ND array 计算的最佳实践是 `ndarray` crate,提供 NumPy 风格 API:

```rust
use ndarray::Array2;

fn iterate_radiosity_nd(
    initial: &ndarray::Array1<f32>,
    form_factor: &Array2<f32>,
    albedo: &ndarray::Array1<f32>,
    bounces: usize,
) -> ndarray::Array1<f32> {
    // form_factor.outer_iter() 给每行 view
    // 矩阵向量乘用 .dot()
    let mut current = initial.clone();
    for _ in 0..bounces {
        let mut next = initial.clone();
        // 这里需要手动循环因为 form_factor[i][j] * albedo[j] 的逐元素乘
        // 如果预先把 form_factor * albedo 算成 K,就只需 K.dot(&current)
        next += &(form_factor * &albedo.insert_axis(ndarray::Axis(1))).dot(&current);
        current = next;
    }
    current
}
```

`ndarray` + `blas` feature 可以用 BLAS 加速矩阵乘,对大型 form factor 矩阵(N=10000+ 表面)速度差 10 倍。

更激进的方案:`candle`(Hugging Face Rust ML 框架)支持 GPU 矩阵运算。但对 HH 这种小规模(N=几百)CPU 已经够快。

数学库选择的经验法则:

- N < 100:朴素循环就够,代码最清晰
- N ∈ [100, 10000]:用 ndarray,享受 BLAS 加速
- N > 10000:上 GPU(CUDA / wgpu),否则跑不动

## 5 · 对照与变奏

不同反弹数的视觉:

```
0 bounces:         1 bounce:          5 bounces:
直接光,             + 第一次反弹,       + 多次反弹,
阴影里全黑          阴影里有点光         阴影里有柔光
```

反弹数越多越真实,但成本指数。

反弹数对比详解:

- **0 bounces**(只有直接光):每个表面只接收来自光源的光。阴影是死黑——没有光反弹到那里。这是 Quake 1 之前的 DOOM / Wolfenstein 3D 的做法,场景看起来"扁平"。
- **1 bounce**:加上第一次反弹。阴影里有了"间接光晕",场景看起来"立体"。Gears of War 1 用这种,跑得动 Xbox 360。
- **3 bounces**(HH 选):阴影边缘有"光渗"(light bleeding),颜色互相影响——红墙边的白地板带粉。这是 Quake 1 radiosity 的标准。
- **5+ bounces**:颜色"渗透"更深,场景看起来"温暖"。HL2 / Portal 用这种。
- **1000+ bounces**(path tracing):物理真实,但每帧几秒到几小时。Pixar / Disney 用这种做电影。

反弹越多,**颜色调和**(color bleeding)越明显。这就是为什么电影里红墙反射到白衬衫上是粉红色——你需要多次反弹让光"渗"过来。

历史上 GI 的演化:

- **1984**:Goral、Cohen、Greenberg 提出 radiosity(基于热辐射学),SIGGRAPH best paper。
- **1986**:Kajiya 提出 path tracing 和 rendering equation,统一了所有 GI 算法。
- **1996**:Jensen 提出 photon mapping,适合 caustics(焦散)。
- **2000s**:实时 GI 用 spherical harmonics(Sloan et al., precomputed radiance transfer)。
- **2010s**:Voxel GI(Crassin et al., voxel cone tracing)、LPV(Kaplanyan)、SSVO/SSDO(screen-space)。
- **2018+**:RTX 硬件,实时光线追踪普及。
- **2023+**:Neural radiance cache,把 ML 用在 GI 上。

每个时代都有自己的"GI 圣杯"。HH 选 radiosity 反映了 Casey 的"够用就行"——简单、可教、能跑。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 albedo = 1.0 时间接光不收敛?用数学解释。

**参考解答**:间接光迭代 = `L_{n+1} = E + K * L_n`,K 是反弹矩阵。如果所有 albedo = 1,K 的特征值可能 = 1,迭代不收缩。具体来说:`L_{n+1} - L_n = K * (L_n - L_{n-1})`,如果 K 有特征值 1,差分不衰减,L_n 可能持续增长。加 albedo < 1 后,K 特征值 < 1,差分指数衰减,L_n 收敛到 `E / (1 - K)`。

### Lv2 · 动手实践

**题**:实现 §3.4 的 radiosity 迭代,3 个 surface,测试收敛。

```rust
fn main() {
    let initial = vec![1.0, 0.0, 0.0]; // 只有表面 0 有直接光
    let form_factor = vec![
        vec![0.0, 0.5, 0.0],
        vec![0.5, 0.0, 0.5],
```

### Lv3 · 迁移设计

**题**:把 albedo 改成 1.0,跑同样迭代,看到不收敛(指数增长)。然后改成 0.9,看缓慢收敛。

**进阶**:实现一个"自动检测发散"的 wrapper——每轮迭代检查 max(L),如果超过 1e6,自动 panic 并报告"不收敛,可能 albedo 太大"。

**参考解答**:

```rust
fn iterate_radiosity_safe(
    initial: &[f32],
    form_factor: &[Vec<f32>],
    albedo: &[f32],
    bounces: usize,
) -> Result<Vec<f32>, &'static str> {
    let mut current = initial.to_vec();
    for bounce in 0..bounces {
        let mut next = initial.to_vec();
        for i in 0..current.len() {
            for j in 0..current.len() {
                if i == j { continue; }
                next[i] += current[j] * form_factor[i][j] * albedo[j];
            }
        }
        let max_val = next.iter().cloned().fold(0.0f32, f32::max);
        if !max_val.is_finite() {
            return Err("数值溢出 (NaN/Inf),反弹矩阵不收敛");
        }
        if max_val > 1e6 {
            return Err("光强指数增长,可能 albedo 太接近 1");
        }
        println!("Bounce {}: max = {:.4}", bounce + 1, max_val);
        current = next;
    }
    Ok(current)
}

fn main() {
    // 测试 albedo = 1.0(发散)
    let initial = vec![1.0, 0.0, 0.0];
    let form_factor = vec![
        vec![0.0, 0.5, 0.0],
        vec![0.5, 0.0, 0.5],
        vec![0.0, 0.5, 0.0],
    ];
    let bad_albedo = vec![1.0; 3];
    match iterate_radiosity_safe(&initial, &form_factor, &bad_albedo, 10) {
        Ok(r) => println!("OK: {:?}", r),
        Err(e) => println!("ERR: {}", e),
    }
    // 应该输出 "ERR: 光强指数增长..."

    // 测试 albedo = 0.5(收敛)
    let good_albedo = vec![0.5; 3];
    match iterate_radiosity_safe(&initial, &form_factor, &good_albedo, 10) {
        Ok(r) => println!("OK: {:?}", r),
        Err(e) => println!("ERR: {}", e),
    }
}
```

这种 "防御性编程"在数值算法里很重要——你不希望玩家进游戏 5 秒后看到全白屏崩溃,而希望提前检测、用安全 fallback(比如关掉 GI,只用直接光)。

工业实践:Unreal Engine 的 GI 系统(Lumen)有大量这种"数值守卫",如果检测到光强爆炸,会自动 fallback 到低质量模式。这是 shipping-grade 代码的标志。

```rust
// Cargo.toml: 无依赖

struct Surface {
    direct: f32,
    albedo: f32,
}

fn compute_indirect(
    surfaces: &mut [Surface],
    form_factor: &[Vec<f32>],
    bounces: usize,
) {
    let n = surfaces.len();
    let mut current: Vec<f32> = surfaces.iter().map(|s| s.direct).collect();
    for bounce in 0..bounces {
        let mut next: Vec<f32> = surfaces.iter().map(|s| s.direct).collect();
        for i in 0..n {
            for j in 0..n {
                if i == j { continue; }
                next[i] += current[j] * form_factor[i][j] * surfaces[j].albedo;
            }
        }
        let max_val = next.iter().cloned().fold(0.0f32, f32::max);
        println!("Bounce {}: max light = {:.4}", bounce + 1, max_val);
        current = next;
    }
    for (i, s) in surfaces.iter_mut().enumerate() {
        s.direct = current[i];
    }
}

fn main() {
    let mut surfaces = vec![
        Surface { direct: 1.0, albedo: 0.5 },
        Surface { direct: 0.0, albedo: 0.5 },
        Surface { direct: 0.0, albedo: 0.5 },
    ];
    let form_factor = vec![
        vec![0.0, 0.5, 0.0],
        vec![0.5, 0.0, 0.5],
        vec![0.0, 0.5, 0.0],
    ];
    compute_indirect(&mut surfaces, &form_factor, 10);
    println!("Final: {:?}", surfaces.iter().map(|s| s.direct).collect::<Vec<_>>());

    // 不收敛的对照:albedo = 1.0
    println!("\n--- Diverging case (albedo=1.0) ---");
    let mut bad = vec![
        Surface { direct: 1.0, albedo: 1.0 },
        Surface { direct: 0.0, albedo: 1.0 },
        Surface { direct: 0.0, albedo: 1.0 },
    ];
    compute_indirect(&mut bad, &form_factor, 10);
}
```

## 10 · 工程反思

Day 651 的核心教训:**模拟物理的代码必须忠实于物理**。

Casey 之前的 bug 看似是个"逻辑错误",但深层原因是"代码不对应真实物理"。物理上,光每次反弹必然有能量损失(吸收);代码里漏了这一步,等于违反了能量守恒定律。结果就是数值爆炸。

这条教训的推广:**任何"模拟某物理现象"的代码,都要先理解那个物理的守恒律**。能量守恒、动量守恒、质量守恒——这些不只是教科书概念,是数值稳定性的根本保证。如果你写流体模拟忘了质量守恒(体积膨胀/收缩)、写刚体模拟忘了动量守恒(碰撞后速度突变)、写热传导忘了能量守恒(温度爆炸),bug 都和今天 Casey 的间接光爆炸同构。

第二条教训:**矩阵特征值是判断迭代算法稳定性的金标准**。无论你做物理模拟、神经网络训练(GD 收敛)、PageRank 算法(M 阵谱半径)、还是金融模型(蒙特卡洛采样),都是"反复迭代直到收敛"。看一眼迭代矩阵的特征值,就能预测收敛性。这是数值分析的核心技术。

第三条教训:**有时 bug 的修复不是"加补丁",而是"补回物理"**。Casey 没有用什么巧妙的 trick,而是回到了"光反弹必须衰减"这个第一原理。工业代码里很多"诡异 bug"其实都是物理建模缺失,加 trick 解决不了,只有重新对齐物理才彻底。这要求程序员**理解物理 + 理解代码**,而不只是"会写代码"。
