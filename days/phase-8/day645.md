
# Day 645 · 碰撞切换到体素中心

> 经过 Day 636-644 的体素碰撞工作,Casey 终于决定一个根本性重构:**把碰撞检测从"voxel 边界"切换到"voxel 中心"**。这是一个看似细微、实际影响深远的决定——它消除了 Day 635 的浮点抖动、Day 643 的多个边角 bug,把数学变得更干净。

## 0 · 为什么要有这一天

回顾 Day 635-644 的体素碰撞:

- voxel 在世界坐标里是 `floor(pos)` 索引
- voxel "占据" 的空间是 `[voxel_idx, voxel_idx + 1)` 的区间
- 但实际我们做 collision 时,用的是 **voxel 中心** 还是 **voxel 边界**?

这两种坐标系下,同一个数学操作给出不同结果:

**Voxel 边界约定**(原版):voxel (0,0,0) 占据世界坐标 [0, 1) × [0, 1) × [0, 1)
**Voxel 中心约定**(新):voxel (0,0,0) 的中心在世界坐标 (0, 0, 0),占据 [-0.5, 0.5) × [-0.5, 0.5) × [-0.5, 0.5)

差别看似只是"偏移 0.5",但影响巨大:

- 浮点抖动:玩家位置在 voxel 边界(如 x = 1.0)时,floor 算法给出不稳定的索引
- AABB 计算:边界约定的 AABB 不对称(原点在角上),中心约定的 AABB 对称(原点在中心)
- 距离计算:中心约定的最近点公式更简洁

Casey 今天把整个 collision 系统切到中心约定。这是一个 8 集大重构的最后一集。

心理锚点:看完今天,你能:

- 解释 voxel 边界 vs 中心约定的差别
- 理解为什么中心约定让数学更简洁
- 完成一次大的概念重构而不留回归 bug

## 2 · 心智模型

### 类比:GPS 坐标系

GPS 经度有两种约定:

- **以本初子午线为 0**:经度 0 在格林尼治,东经正、西经负
- **以国际日期变更线为 0**:经度 0 在太平洋,东西经都是正(0-360)

两者数学等价(只是平移 180°),但**写代码时**,某些约定比其他更方便。比如以本初子午线为 0 时,东西半球经度符号不同,容易写错;以日期变更线为 0 时,所有经度都是正的,简单。

voxel 边界 vs 中心约定也是这个差别——数学等价,但**中心约定的某些公式更简洁**。

### 中心约定的数学简洁性

考虑"球到 voxel 的最近点"。

**边界约定**:voxel (0,0,0) 占据 [0, 1)^3。voxel (3, 0, 5) 占据 [3, 4) × [0, 1) × [5, 6)。要算最近点:

```rust
let v_min = Vec3::new(voxel.x as f32, voxel.y as f32, voxel.z as f32);
let v_max = v_min + Vec3::splat(1.0);
let closest = pos.clamp(v_min, v_max);
```

**中心约定**:voxel (0,0,0) 中心在 (0,0,0),占据 [-0.5, 0.5)^3。voxel (3, 0, 5) 中心在 (3, 0, 5),占据 [2.5, 3.5) × [-0.5, 0.5) × [4.5, 5.5):

```rust
let center = voxel.as_vec3();
let v_min = center - Vec3::splat(0.5);
let v_max = center + Vec3::splat(0.5);
let closest = pos.clamp(v_min, v_max);
```

看起来差不多,但**距离判定**更简洁:

```rust
// 边界约定:要算 floor 找 voxel,然后看是否 solid
let voxel_idx = pos.floor().as_ivec3();
let is_in_solid = is_solid(voxel_idx);

// 中心约定:中心点距离直接给答案
let voxel_idx = (pos + Vec3::splat(0.5)).floor().as_ivec3();
// 等价:voxel_idx = pos.round().as_ivec3()
let center = voxel_idx.as_vec3();
let dist = (pos - center).length(); // 到中心距离
let is_in_solid = is_solid(voxel_idx) && dist < 0.5; // 0.5 是 voxel 半边长
```

`pos.round()` 比地板更稳定——离中心最近的整数。这对浮点抖动免疫。

### 浮点抖动的根本解决

Day 635 的 bug:玩家位置在 voxel 边界(如 x = 1.0)时,floor 给出不同结果:

- pos.x = 0.9999999(浮点误差):floor = 0
- pos.x = 1.0000001:floor = 1
- 真实值 1.0,两种情况都可能

中心约定下,我们 round,不是 floor:

- pos.x = 0.9999999:round = 1
- pos.x = 1.0000001:round = 1
- 都给 1,稳定

round 比 floor 更鲁棒,因为浮点误差通常很小(微秒级),不会让 0.9999999 变成 0.4。

### 中心约定下的 unembed

unembed 公式不变,但最近的 voxel 找法变了:

```rust
// 中心约定找所有可能碰撞的 voxel
let center_voxel = pos.round().as_ivec3();
for offset in NEIGHBOR_OFFSETS {
    let v = center_voxel + offset;
    if !is_solid(v) { continue; }
    let vc = v.as_vec3();
    let closest = pos.clamp(vc - Vec3::splat(0.5), vc + Vec3::splat(0.5));
    let d = pos - closest;
    let dist_sq = d.length_squared();
    if dist_sq < r * r { /* 碰撞 */ }
}
```

`NEIGHBOR_OFFSETS` 是 3x3x3 立方体里的偏移(27 个 voxel),覆盖球的所有可能影响范围。

### 为什么 27 个 voxel 够

球半径 r ≤ 0.5 时,球最多覆盖 2x2x2 = 8 个 voxel。但球可能"贴近" voxel 边界,所以保险起见扫 3x3x3 = 27 个。如果球更大(r > 0.5),要扫更多 voxel,或者用 flood fill。

Casey 在 Day 641 的 flood fill 在中心约定下变得简单——起始 voxel 就是 `pos.round()`,扩散规则不变。

### 重构的工程方法

切换约定是大型重构。Casey 的方法:

1. **新写一个,老的不动**:实现 `is_solid_v2(center: IVec3)` 等新函数
2. **逐步替换**:把 collision 代码里调用的函数一个个换
3. **保持兼容**:游戏渲染、序列化等代码仍用旧约定,只是 collision 用新约定
4. **测试**:每替换一处,跑测试套件
5. **清理**:全部替换完,删除老函数

这就是 **strangler vine pattern**(绞杀者藤蔓模式)——新代码逐步"包裹"老代码,最后老代码被完全替换。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏里 voxel 约定的不同实现:

- **Minecraft**:voxel (0,0,0) 占据 [0, 1) × [0, 1) × [0, 1)(边界约定)
- **Voxel Farm**:中心约定
- **7 Days to Die**:边界约定
- **Stonehearth**:中心约定

没有"标准答案",每个项目选自己的。但**一旦选定,整个项目要一致**——混用会导致难以察觉的 bug。

### 3.2 · 图形学视角

图形里的"边界 vs 中心"约定:

- **UV 坐标**:纹理 (0,0) 在角(角约定)还是中心(中心约定)。OpenGL 角约定,DirectX 中心约定(早期版本)
- **Pixel 中心**:像素 (0,0) 的中心是 (0.5, 0.5) 还是 (0, 0)?OpenGL 0.5 中心,DirectX 0 中心
- **Sample position**:MSAA 采样点在像素中心还是边角

这些约定差别是 cross-API 渲染引擎的重大坑(OpenGL texture vs DirectX texture y 翻转问题)。

### 3.3 · Linux 系统编程视角

Linux 内核的"边界 vs 中心":

- **page size**:4 KB page 边界是 0x1000 对齐,内存分配必须对齐
- **cache line**:64 字节,数据布局考虑 cache line 中心还是边界
- **NUMA node**:节点边界 vs 节点中心(对性能分析不重要,但对迁移重要)

类似概念,但内核更看重边界(对齐要求)。

### 3.4 · Rust 生态视角

Rust 里 voxel 重构的关键工具:

- **`#[deprecated]` 标注**:把老的 `voxel_at_boundary_style` 标 deprecated,编译器警告所有调用者
- **`cfg(test)` 双轨**:同时跑边界约定和中心约定的测试,确认行为一致后再删老的
- **cargo fuzz**:模糊测试,随机生成位置,确保新约定在所有情况都收敛

```rust
#[deprecated(note = "use voxel_at_center_style instead")]
fn voxel_at_boundary_style(pos: Vec3) -> IVec3 {
    pos.floor().as_ivec3()
}

fn voxel_at_center_style(pos: Vec3) -> IVec3 {
    (pos + Vec3::splat(0.5)).floor().as_ivec3()
    // 等价: pos.round().as_ivec3()
}
```

`round()` 在 Rust f32 上是"四舍六入五成双"(banker's rounding),不是"四舍五入"。`pos.round()` 在 0.5 时给最近的偶数。但我们 voxel 通常不在 0.5 边界,所以差别不大。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 `round()` 比 `floor()` 对浮点抖动鲁棒?

**参考解答**:floor 在整数边界附近不稳定——0.9999999 给 0,1.0000001 给 1。round 在整数附近稳定——0.9999999 给 1,1.0000001 给 1。因为浮点误差通常很小(< 1e-6),round 的"最近整数"几乎总是正确的那个,而 floor 在边界附近"跳"。

### Lv2 · 动手实践

**题**:实现 `voxel_at_center_style(pos)` 和 `voxel_at_boundary_style(pos)`,测试几个边界点:

- pos = (0.5, 0.5, 0.5):两种约定都给 (0,0,0) 或 (1,1,1)?哪个?
- pos = (0.9999999, 0, 0):floor vs round 各给什么?

**参考解答**:

```rust
use glam::{Vec3, IVec3};

fn voxel_floor(pos: Vec3) -> IVec3 {
    pos.floor().as_ivec3()
}

fn voxel_round(pos: Vec3) -> IVec3 {
    // 等价于 (pos + 0.5).floor(),但更直观
    IVec3::new(pos.x.round() as i32, pos.y.round() as i32, pos.z.round() as i32)
}

fn main() {
    let p1 = Vec3::new(0.5, 0.5, 0.5);
    println!("p={:?} floor={:?} round={:?}", p1, voxel_floor(p1), voxel_round(p1));
    // floor 给 (0,0,0),round 给 (0,0,0) 或 (1,1,1) (取决于 banker's rounding)

    let p2 = Vec3::new(0.9999999, 0.0, 0.0);
    println!("p={:?} floor={:?} round={:?}", p2, voxel_floor(p2), voxel_round(p2));
    // floor 给 (0,0,0),round 给 (1,0,0)

    let p3 = Vec3::new(1.0000001, 0.0, 0.0);
    println!("p={:?} floor={:?} round={:?}", p3, voxel_floor(p3), voxel_round(p3));
    // floor 给 (1,0,0),round 给 (1,0,0)
    // 所以 round 在 p2 和 p3 都给 (1,0,0),floor 不一致
}
```

## 8 · Rust / Arch 落地代码

完整中心约定 voxel collision:

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::{Vec3, IVec3};

fn is_solid(_v: IVec3) -> bool { true } // 假设全部 solid(demo)

// 中心约定:voxel (x,y,z) 中心在 (x,y,z),占据 [x-0.5, x+0.5)
fn world_to_voxel(pos: Vec3) -> IVec3 {
    IVec3::new(pos.x.round() as i32, pos.y.round() as i32, pos.z.round() as i32)
}

fn voxel_center(v: IVec3) -> Vec3 {
    v.as_vec3()
}

fn voxel_aabb(v: IVec3) -> (Vec3, Vec3) {
    let c = voxel_center(v);
    (c - Vec3::splat(0.5), c + Vec3::splat(0.5))
}

// 扫 3x3x3 = 27 voxel 找碰撞
fn collide(pos: Vec3, r: f32) -> Vec<(IVec3, Vec3, f32)> {
    let center = world_to_voxel(pos);
    let mut hits = Vec::new();
    for dx in -1..=1 {
        for dy in -1..=1 {
            for dz in -1..=1 {
                let v = IVec3::new(center.x + dx, center.y + dy, center.z + dz);
                if !is_solid(v) { continue; }
                let (vmin, vmax) = voxel_aabb(v);
                let closest = pos.clamp(vmin, vmax);
                let d = pos - closest;
                let dist_sq = d.length_squared();
                if dist_sq < r * r {
                    let dist = dist_sq.sqrt();
                    let push_dir = if dist > 1e-6 { d / dist } else { Vec3::Y };
                    let penetration = r - dist;
                    hits.push((v, push_dir, penetration));
                }
            }
        }
    }
    hits
}

fn resolve(pos: &mut Vec3, r: f32) -> bool {
    for _ in 0..16 {
        let hits = collide(*pos, r);
        if hits.is_empty() { return true; }
        let mut total = Vec3::ZERO;
        for (_, dir, pen) in hits {
            total += dir * pen;
        }
        let len = total.length();
        if len < 1e-8 { return true; }
        let step = if len > 0.05 { total * (0.05 / len) } else { total };
        *pos += step;
    }
    false
}

fn main() {
    let mut p = Vec3::new(0.0, -0.2, 0.0); // 嵌入 voxel (0,0,0) 下方
    println!("Before: pos={:?}", p);
    resolve(&mut p, 0.4);
    println!("After:  pos={:?}", p);
    // 中心约定:球被推到 y > 0.0(在 voxel 上方)
}
```

## 10 · 工程反思

Day 645 传达的核心工程教训:**约定(convention)是 bug 工厂**。

"voxel 边界" vs "voxel 中心"是约定——两种都可以工作,但**混用就 bug**。Casey 在 Day 635-644 反复遇到这种 bug,Day 645 终于"统一约定到中心",彻底消除歧义。

这是工程经验:**不一致的约定是 bug 永远来源**。资深工程师的能力是"识别约定不一致,主动统一"。这种"约定重构"看起来不起眼(只是改 floor() → round()),但解决一类 bug。

**为什么约定这么重要?**

1. **隐式**:约定通常不写在代码里,只在工程师脑子里
2. **传染**:一个模块的约定会扩散到其他模块
3. **难发现**:bug 表象和约定无关,根因在约定
4. **难修复**:改约定要改大量代码,容易引入新 bug

工业教训:**每个项目都应该有"约定文档"**——明确"坐标系、原点、单位、方向、命名风格"。新成员 onboarding 必读。

**Casey 的 voxel 中心约定**:

- voxel 的"位置"= 中心坐标(整数 + 0.5)
- voxel 的"范围"= [center - 0.5, center + 0.5]
- 玩家进入 voxel 当玩家中心在 voxel 范围内
- raycast 与 voxel 相交 = 射线穿过 voxel 范围

这套约定清晰、一致、可推理。Casey 用它替换了之前的"voxel 边界"约定(voxel 位置 = 边界整数,voxel 范围 = [n, n+1])。两种都能工作,但前者更直觉(整数对应 voxel 本身,小数对应 voxel 内位置)。

**第二条教训**:**重构是 polish 的高级形式**。

Day 645 不是"修 bug",是"重构约定"。这比修 bug 更难,因为:

- 影响范围广(每个 voxel 操作都改)
- 临时 double-maintain(新旧约定共存)
- 风险高(引入新 bug 概率大)

但收益也大——消除整类 bug,代码更清晰。资深工程师的判断:**何时修 bug,何时重构**。

**第三条教训**:**约定应该早定,后期改成本高**。

Day 635 就发现边界 bug,但 Casey 当时用 hack 修(单个 bug)。Day 645 才彻底重构,因为 hack 累积到不可持续。如果 Day 635 就重构,成本更低。

工业教训:**遇到第二次同类 bug,就该重构**。不要等第三次、第四次。

**迁移到其他领域**:

"约定不一致"在多处通用:

- **API**:RESTful vs RPC,URL 命名约定
- **数据库**:日期格式、null 处理、外键
- **代码**:命名风格(camelCase vs snake_case)
- **网络**:字节序(big / little endian)
- **时间**:时区、夏令时
- **字符编码**:UTF-8 vs UTF-16 vs Latin-1

每个领域都有"约定战争"。资深工程师的元能力是**统一约定 + 强制执行**。Casey 在 HH Day 645 演示的是空间坐标的约定统一。

## 11 · voxel 中心 vs 边界的完整对比

 voxel 坐标约定有两种主流:

**约定 A:voxel 中心在整数坐标**

```
voxel (0, 0, 0) 中心 = world (0, 0, 0)
voxel (0, 0, 0) 范围 = world [-0.5, 0.5]^3
voxel (n, n, n) 中心 = world (n, n, n)
voxel (n, n, n) 范围 = world [n-0.5, n+0.5]^3
```

转换:`world = voxel_coord`(直接相等),`voxel = floor(world + 0.5)`(round)。

**约定 B:voxel 边界在整数坐标**

```
voxel (0, 0, 0) 范围 = world [0, 1]^3
voxel (0, 0, 0) 中心 = world (0.5, 0.5, 0.5)
voxel (n, n, n) 范围 = world [n, n+1]^3
voxel (n, n, n) 中心 = world (n+0.5, n+0.5, n+0.5)
```

转换:`voxel = floor(world)`,中心 = `voxel + 0.5`。

**对比**:

| 方面 | 约定 A(中心整数) | 约定 B(边界整数) |
|---|---|---|
| floor 调用 | 多(需 +0.5 再 floor) | 少(直接 floor) |
| 中心表达 | 直接 `Vec3::new(x, y, z)` | `Vec3::new(x+0.5, y+0.5, z+0.5)` |
| 边界表达 | `x ± 0.5` | `x, x+1` |
| 浮点抖动 | 较少(中心在整数,稳定) | 较多(中心在 0.5,边界敏感) |
| 与 Minecraft 一致 | 否(Minecraft 用 B) | 是 |

Casey 在 Day 645 切换到约定 A(中心整数),因为浮点更稳定。Minecraft 用约定 B,因为代码生成时自然。两种都能工作,关键是**一致**。

**为什么浮点抖动在约定 B 更严重?**

边界在整数坐标,玩家移动经过边界时,`floor(world)` 的结果在 0.99999 / 1.00001 之间跳变——浮点误差让 voxel 归属不确定。约定 A 的边界在小数(x ± 0.5),玩家移动到边界时 floor 仍稳定(因为整数点是中心,远离边界)。

工业教训:**坐标约定要选"远离边界"的方案**——浮点精度边界处最不稳定。Casey 在 Day 645 修这个,Day 635 的抖动 bug 彻底消除。

## 12 · 重构的技术债管理

Day 645 是大型重构——改全局约定。技术债(technical debt)管理:

**1. 识别债务**:

- 反复修同类 bug → 约定不一致
- 新人困惑 → API 不直观
- 性能瓶颈 → 数据结构过时
- 测试覆盖低 → 设计脆弱

每个症状都暗示"该重构"。

**2. 评估成本**:

- 时间:Day 645 重构 ~ 1 周
- 风险:引入新 bug 概率
- 收益:消除整类 bug + 代码简化

如果收益 > 成本,重构。

**3. 分步执行**:

- 先建新约定(并存)
- 逐模块迁移
- 旧约定 deprecate
- 最终移除

避免"大爆炸"重构(一次性改全部),因为风险太高。

**4. 测试覆盖**:

重构前必须有测试。否则"重构后行为不变"无法验证。Casey 在 HH 没有 formal test,但用"录制的 demo"做 manual regression——跑同 demo,确认输出一致。

工业教训:**重构是工程,不是艺术**——分步、有测试、可回滚。资深工程师的能力是"安全重构大型代码"。

## 13 · 重构风险评估

Day 645 的大型重构风险评估:

**Risk 1: 引入新 bug**

- 概率:中(重构改全局约定,边角多)
- 影响:高(collision 出 bug 玩家直接感受到)
- 缓解:测试覆盖 + 录制器 regression

**Risk 2: 性能 regression**

- 概率:低(round 不比 floor 慢)
- 影响:低(每帧 collision 占比小)
- 缓解:profiling

**Risk 3: 时间超支**

- 概率:中(重构经常超时)
- 影响:中(delay 其他功能)
- 缓解:限定 scope(只改 collision,渲染 / AI 不动)

**Risk 4: 代码 review 不充分**

- 概率:中(重构涉及大量代码)
- 影响:中(隐藏 bug)
- 缓解:小步提交,逐 commit review

每个 risk 都要识别 + 缓解。资深工程师的能力是"事前评估 + 事中监控"。

## 14 · 大型重构的 commit 策略

工业级重构的 commit 策略:

**1. 小步提交**:

每个独立改动一个 commit。例如:

- commit 1: 添加 voxel_at_center 函数
- commit 2: 把 collision 代码改用 voxel_at_center
- commit 3: 删除老 voxel_at_boundary
- commit 4: 更新文档

每个 commit 单独 review,bug 容易定位。

**2. 保持 buildable**:

每个 commit 后代码必须 build。不能 "中途破"。

**3. Feature flag**:

用 cfg 隔离新旧约定,生产用新,测试用旧。这样新约定验证通过前不破现有功能。

**4. Bisection friendly**:

如果某 commit 引入 bug,`git bisect` 能快速定位。每个 commit 自包含、可独立 revert。

资深工程师把重构当"科学实验"——假设、验证、迭代。Casey 在 HH 简化(单 commit),工业级是几十 commit。

## N0 • 深度教学补充

### 核心概念重新梳理

Day 645 涉及的核心概念需要在多个层次上理解:

**第一层:直观理解**

新手第一次接触概念,需要建立直觉。例如 voxel collision 是"虚拟物体不能穿过虚拟墙"——这个直觉每个人都能从现实经验获得。

**第二层:数学理解**

把直觉形式化。collision = "两个几何体的体积有交集"。对于 AABB,这等价于"三轴投影都重叠"。

**第三层:工程理解**

数学正确不等于工程实现正确。要考虑:

- 浮点精度边界
- 性能(每帧 N 个查询)
- 内存(数据结构紧凑)
- 边角 case(无穷大、NaN、负数)

**第四层:工业理解**

工业级要再加:

- 多线程安全
- SIMD 优化
- 网络同步(多人游戏)
- 跨平台(Windows/Mac/Linux/Mobile)
- 可访问性(色盲友好)
- 反作弊

每层理解都让代码更鲁棒。资深工程师在所有层次同时思考。

### 实际工程的细节

工业代码 80% 是"边角 case 处理",20% 是"核心算法"。Casey 在 HH 演示核心,工业代码加大量边角处理。

**边角 case 类型**:

1. 空输入(空 Vec、null pointer)
2. 极端输入(NaN、无穷大、超大数)
3. 并发竞争(多线程同时访问)
4. 资源不足(内存满、磁盘满)
5. 网络异常(超时、断连、包丢失)
6. 版本不兼容(老配置 / 新代码)
7. 权限错误(只读文件、无网络)
8. 用户误操作(连点、撤销重做)

每个 case 都要单独处理。这是工业代码 50%+ 行数的原因。

### 优化思路

性能优化有顺序:

1. **算法**:O(N²) → O(N log N),最大提升
2. **数据结构**:Vec → HashMap / BTreeMap,常数提升
3. **Cache**:AoS → SoA,cache 命中提升
4. **SIMD**:4-16 元素并行,巨大常数提升
5. **GPU**:数千核并行,极致性能
6. **分布式**:多机器,无限扩展

每级提升都需要更复杂的代码。先优化低级,够用再升级。
