
# Day 655 · 重新审视实体移动

> 体素碰撞 / 光照都完工后,Casey 把目光转回**实体系统**(entity system)——玩家、敌人、可拾取物品的统一抽象。今天重新审视"实体怎么移动":老代码假设每帧单一速度,但实际游戏需要**复杂的移动模式**(冲刺、击退、传送),要重新设计。

## 0 · 为什么要有这一天

回顾早期 HH 实体移动:

```rust
struct Entity {
    pos: Vec3,
    vel: Vec3,
}

fn update(e: &mut Entity, dt: f32) {
    e.vel += gravity * dt;
    e.pos += e.vel * dt;
    collide_and_resolve(e);
}
```

简单 Euler 积分 + 碰撞响应。但游戏后期出现新需求:

- **冲刺**(dash):玩家按某键,瞬间 1 米位移,不通过普通物理
- **击退**(knockback):敌人攻击玩家,玩家被推飞 3 米
- **传送**(teleport):魔法效果,玩家瞬间出现在新位置
- **AI 巡逻**(patrol):NPC 按预设路径走,不受重力
- **电梯**:垂直位移,不能被 collision 挡

每种移动模式对物理系统的要求不同。直接在 `update` 里加 if-else 会让代码乱。

今天 Casey **抽象出"移动请求"**(movement request)的概念:每帧,实体不直接改 pos / vel,而是生成"我想这样动"的请求,物理系统处理请求,生成实际位移。

心理锚点:看完今天,你能:

- 区分"直接移动"和"请求式移动"
- 设计移动请求队列
- 在物理系统里处理多种移动模式

## 1 · Casey 今天做了什么

1. 引入 `MoveRequest` enum:`Walk(velocity) / Dash(direction, distance) / Teleport(position) / Knockback(impulse)`
2. 每帧实体不直接改 pos,而是 push 一个或多个 MoveRequest 到队列
3. 物理系统按优先级处理:Teleport > Dash > Knockback > Walk
4. 每个 request 处理后更新 pos 和 vel
5. 碰撞检查在每个 request 之后
6. 测试:冲刺穿过敌人,击退把玩家推飞,传送跳关
7. 简化 AI:用 Walk 模式,但加目标位置(每帧朝目标走)

## 2 · 心智模型

### 类比:酒店前台

老式酒店:你直接走到房间,自己拿钥匙开。问题:前台不知道你在哪,出事找不到人。

新式酒店:你到前台登记,前台给你钥匙。前台知道每个客人状态,可以"加服务"(叫醒、行李搬送)。

实体移动同构。老式:实体自己改 pos。新式:实体生成请求,物理系统(前台)处理。物理系统知道每个请求的语义,可以**调度**(谁先动)、**仲裁**(冲突时谁赢)、**审计**(记录每次移动用于 replay)。

### MoveRequest enum

```rust
enum MoveRequest {
    Walk { vel: Vec3 },                   // 常规移动(玩家输入)
    Dash { dir: Vec3, distance: f32 },    // 瞬移固定距离
    Teleport { target: Vec3 },            // 瞬移到指定位置
    Knockback { impulse: Vec3 },          // 被推(加到速度)
    Force { acceleration: Vec3 },         // 持续力(电梯、引力)
}

struct Entity {
    pos: Vec3,
    vel: Vec3,
    pending_moves: Vec<MoveRequest>,
}
```

`pending_moves` 是队列——每帧可以 push 多个请求(玩家 Walk + 风的 Force + 突然被 Knockback)。

### 优先级处理

物理系统按优先级处理请求:

1. **Teleport**(最高):直接覆盖位置,不检查 collision
2. **Dash**:瞬间位移,可能做 raycast 防穿墙
3. **Knockback**:加到 vel,后续由 Walk / Force 演化
4. **Force**:加到 vel(力 = 加速度 * dt)
5. **Walk**(最低):直接设置 vel(覆盖)

```rust
fn process_moves(e: &mut Entity, dt: f32) {
    for req in e.pending_moves.drain(..) {
        match req {
            MoveRequest::Teleport { target } => {
                e.pos = target;
                e.vel = Vec3::ZERO; // 传送后速度归零
            }
            MoveRequest::Dash { dir, distance } => {
                // raycast 防穿墙
                let dest = e.pos + dir.normalize() * distance;
                if !raycast_solid(e.pos, dest) {
                    e.pos = dest;
                }
            }
            MoveRequest::Knockback { impulse } => {
                e.vel += impulse;
            }
            MoveRequest::Force { acceleration } => {
                e.vel += acceleration * dt;
            }
            MoveRequest::Walk { vel } => {
                e.vel.x = vel.x;
                e.vel.z = vel.z;
                // y 由重力 / 跳跃控制,Walk 不影响
            }
        }
        // 每个 request 后做碰撞检查
        collide_and_resolve(e);
    }
}
```

### 不同移动模式的 collision

每种请求对 collision 的要求不同:

- **Walk**:标准 collision(拒绝非法位移)
- **Dash**:raycast sweep(避免穿墙)
- **Teleport**:无 collision(用户负责选合法位置)
- **Knockback / Force**:标准 collision(基于新 vel 的位移)

请求系统让 collision 逻辑**集中**(每个请求后做一次),而不是分散在各 case 里。

### 请求队列的好处

为什么用队列而不是单值?

- **多请求 / 帧**:玩家 Walk + 风 Force + 被 Knockback,3 个请求
- **优先级**:Teleport 必须在 Walk 前处理
- **审计**:每帧记录所有请求,replay 系统可以重放
- **可扩展**:加新请求类型时,不动核心代码,只加 enum 变体

### Move queue vs state machine

移动队列 vs 状态机:

- **状态机**:实体处于 Running / Dashing / Stunned 状态之一,每个状态有自己的 update
- **移动队列**:每帧生成请求,物理统一处理

两者可以共存:状态机决定**生成什么请求**,物理系统**执行请求**。这是职责分离。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏里"移动请求"的著名实现:

- **Unreal CharacterMovementComponent**:复杂的移动状态机 + 网络同步

每个游戏的移动系统都精心调教,因为"手感"是动作游戏的生命。

### 3.2 · 图形学视角

请求 / 响应架构在图形也常见:

- **Vulkan command buffer**:录命令,GPU 异步执行
- **Render graph**:声明渲染 pass 依赖,引擎调度
- **GPU driven rendering**:CPU 生成 indirect command,GPU 自己 cull

"声明意图,系统调度"是复杂系统的好架构。

### 3.3 · Linux 系统编程视角

Linux 上的"请求队列":

- **I/O scheduler**:每个 block device 有请求队列,电梯算法合并 / 排序
- **Task scheduler**:进程就绪队列,CFS 调度
- **Network packets**:sk_buff 队列,逐层处理

每个都是"生成请求,系统调度"。

### 3.4 · Rust 生态视角

Rust 里 enum-based 请求系统:

```rust
enum Request {
    Walk { vel: Vec3 },
    Dash { dir: Vec3, dist: f32 },
    // ...
}

struct Handler {
    state: State,
}

impl Handler {
    fn process(&mut self, req: Request) -> Response {
        match req {
            Request::Walk { vel } => self.walk(vel),
            Request::Dash { dir, dist } => self.dash(dir, dist),
        }
    }
}
```

Rust enum 比 OOP 多态(基类 + 子类 + virtual method)更紧凑——单 match 处理所有变体,内存连续。

```rust
use glam::Vec3;

#[derive(Clone, Debug)]
enum MoveRequest {
    Walk { vel: Vec3 },
    Dash { dir: Vec3, distance: f32 },
    Teleport { target: Vec3 },
    Knockback { impulse: Vec3 },
    Force { acceleration: Vec3 },
}

struct Entity {
    pos: Vec3,
    vel: Vec3,
    pending: Vec<MoveRequest>,
}

impl Entity {
    fn new() -> Self { Self { pos: Vec3::ZERO, vel: Vec3::ZERO, pending: Vec::new() } }
    fn push(&mut self, r: MoveRequest) { self.pending.push(r); }
}

fn process_moves(e: &mut Entity, dt: f32) {
    let reqs: Vec<_> = e.pending.drain(..).collect();
    for req in reqs {
        match req {
            MoveRequest::Teleport { target } => {
                e.pos = target;
                e.vel = Vec3::ZERO;
            }
            MoveRequest::Dash { dir, distance } => {
                let n = dir.normalize_or_zero();
                e.pos += n * distance;
            }
            MoveRequest::Knockback { impulse } => {
                e.vel += impulse;
            }
            MoveRequest::Force { acceleration } => {
                e.vel += acceleration * dt;
            }
            MoveRequest::Walk { vel } => {
                e.vel.x = vel.x;
                e.vel.z = vel.z;
            }
        }
        // collision would go here
        e.pos += e.vel * dt;
    }
}

fn main() {
    let mut e = Entity::new();
    e.push(MoveRequest::Walk { vel: Vec3::new(1.0, 0.0, 0.0) });
    e.push(MoveRequest::Knockback { impulse: Vec3::new(0.0, 5.0, 0.0) });
    process_moves(&mut e, 1.0 / 60.0);
    println!("After: pos={:?} vel={:?}", e.pos, e.vel);
    // pos ~ (0.0166, 0.00139, 0)
    // vel = (1, 5, 0)
}
```

## 8 · Rust / Arch 落地代码

完整移动请求系统:

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::Vec3;

#[derive(Clone, Debug)]
enum MoveRequest {
    Walk { vel: Vec3 },
    Dash { dir: Vec3, distance: f32 },
    Teleport { target: Vec3 },
    Knockback { impulse: Vec3 },
    Force { acceleration: Vec3 },
}

impl MoveRequest {
    fn priority(&self) -> u8 {
        match self {
            MoveRequest::Teleport { .. } => 4,
            MoveRequest::Dash { .. } => 3,
            MoveRequest::Knockback { .. } => 2,
            MoveRequest::Force { .. } => 1,
            MoveRequest::Walk { .. } => 0,
        }
    }
}

struct Entity {
    pos: Vec3,
    vel: Vec3,
    pending: Vec<MoveRequest>,
    radius: f32,
}

impl Entity {
    fn new() -> Self {
        Self { pos: Vec3::ZERO, vel: Vec3::ZERO, pending: Vec::new(), radius: 0.4 }
    }
    fn request(&mut self, r: MoveRequest) { self.pending.push(r); }
}

fn is_solid(_v: glam::IVec3) -> bool { false }

fn collide(e: &mut Entity) {
    // 简化:无 collision(假设全空)
}

fn process(e: &mut Entity, dt: f32) {
    let mut reqs: Vec<_> = e.pending.drain(..).collect();
    reqs.sort_by(|a, b| b.priority().cmp(&a.priority())); // 高优先级先
    for req in reqs {
        match req {
            MoveRequest::Teleport { target } => {
                e.pos = target;
                e.vel = Vec3::ZERO;
                println!("  Teleport to {:?}", e.pos);
            }
            MoveRequest::Dash { dir, distance } => {
                let n = dir.normalize_or_zero();
                e.pos += n * distance;
                println!("  Dash to {:?}", e.pos);
            }
            MoveRequest::Knockback { impulse } => {
                e.vel += impulse;
                println!("  Knockback, vel now {:?}", e.vel);
            }
            MoveRequest::Force { acceleration } => {
                e.vel += acceleration * dt;
            }
            MoveRequest::Walk { vel } => {
                e.vel.x = vel.x;
                e.vel.z = vel.z;
            }
        }
        collide(e);
        e.pos += e.vel * dt;
    }
}

fn main() {
    let mut e = Entity::new();

    println!("Frame 1: Walk + Knockback");
    e.request(MoveRequest::Walk { vel: Vec3::new(2.0, 0.0, 0.0) });
    e.request(MoveRequest::Knockback { impulse: Vec3::new(0.0, 10.0, 0.0) });
    process(&mut e, 1.0 / 60.0);
    println!("  After: pos={:?} vel={:?}", e.pos, e.vel);

    println!("\nFrame 2: Teleport (overrides position)");
    e.request(MoveRequest::Teleport { target: Vec3::new(100.0, 0.0, 100.0) });
    process(&mut e, 1.0 / 60.0);
    println!("  After: pos={:?} vel={:?}", e.pos, e.vel);

    println!("\nFrame 3: Gravity force");
    for _ in 0..60 {
        e.request(MoveRequest::Force { acceleration: Vec3::new(0.0, -9.81, 0.0) });
        process(&mut e, 1.0 / 60.0);
    }
    println!("  After 1s gravity: pos={:?} vel={:?}", e.pos, e.vel);
}
```

## 10 · 工程反思

Day 655 传达的核心工程教训:**review 是 polish 阶段的金矿**。

新手以为"代码写完就完了",资深工程师知道**"写完"才是 review 的开始**。Casey 在 Day 655 重读自己几个月前写的实体移动代码,发现可以简化的地方——这些不是 bug,是"可以更好"。

**为什么 review 这么有价值?**

1. **新视角**:写代码时沉浸细节,review 时跳出来看整体
2. **知识积累**:写完后学的知识,review 时能用上
3. **遗忘效应**:自己写的代码几个月后像别人的,更容易发现缺陷
4. **简化机会**:写时追求"能工作",review 时追求"优雅"

工业实践:**每个 PR 必须 review**——GitHub / GitLab 流程强制。Google 的代码 review 文化特别严格,每个 PR 平均 5 轮 review。这是高质量代码的来源。

**第二条教训**:**重构是持续过程**。

软件不是"写完就稳定",是"持续演化"。Day 655 不是"加新功能",是"重新审视已有功能"。这是 refactoring 的核心——**代码价值随时间贬值**(技术债务),重构是"维护价值"。

Casey 在 HH 反复演示这套节奏:

- Day 636-645 重构 voxel 碰撞
- Day 646 重构光照(3D → 2D)
- Day 649 删除 walk table
- Day 655 重构实体移动

每个都是"重构"而非"加功能"。这是 polish 阶段的标志。

**第三条教训**:**实体移动是游戏手感的核心**。

玩家每帧感受的是"按 W 玩家移动",这是最直接的游戏体验。如果移动代码有 bug(抖动、卡顿、不响应),玩家直接感受到"游戏烂"。

资深游戏程序员把"角色控制器"视为最关键代码——比渲染、AI、网络都重要。Unity / Unreal 都有内置 CharacterController,但每个 AAA 游戏仍自研,因为业务特定需求高。

**迁移到其他领域**:

"持续 review + 重构"在多处通用:

- **Linux kernel**:Linus 仍每天 review PR
- **Rust std**:core team 持续 refactor
- **Web framework**:Django / Rails 每个大版本都重构
- **数据库**:PostgreSQL 持续优化

每个长寿项目都靠持续 review 维持质量。Casey 在 HH 演示的是游戏版本。

## 11 · Character Controller 的工业实现

Unity / Unreal 的 character controller:

**Unity CharacterController**:

- 内置 capsule collider
- `Move(vector)` 处理碰撞响应
- 自动滑墙、上楼梯
- `OnControllerColliderHit` 回调

**Unreal CharacterMovementComponent**:

- 完整角色移动系统
- 走 / 跑 / 跳 / 游泳 / 飞行 / 下落
- 网络同步(多人游戏)
- 工业级复杂度

**Bevy bevy_rapier**:

- 用 rapier 物理引擎
- 玩家是 kinematic body(不受物理影响但触发 collision)
- 手写移动逻辑

每个实现都有自己的哲学。Casey 在 HH 自研 character controller,这是教学最优——理解每个组件。工业级用现成,但理解内部很重要。

## 12 · 网络同步的 character controller

多人游戏的 character controller 更复杂——客户端预测 + 服务器校正:

**1. 客户端预测**:

- 玩家按 W,客户端立即移动(不等服务器)
- 视觉响应快

**2. 服务器权威**:

- 服务器收到输入,跑物理,广播位置
- 防作弊

**3. Reconciliation**:

- 客户端收到服务器位置,如果和自己预测的不一样,纠正
- 看起来"瞬移",但通常很小

这是 FPS / MMO 的核心。CSGO / Valorant / Fortnite 都用这套。Casey 在 HH 单机,但理解扩展对 multiplayer 项目重要。

## N0 • 深度教学补充

### 核心概念重新梳理

Day 655 涉及的核心概念需要在多个层次上理解:

**第一层:直观理解**

新手第一次接触概念,需要建立直觉。例如 voxel collision 是"虚拟物体不能穿过虚拟墙"——这个直觉每个人都能从现实经验获得。

**第二层:数学理解**

把直觉形式化。collision = "两个几何体的体积有交集"。对于 AABB,这等价于"三轴投影都重叠"。

**第三层:工程理解**

数学正确不等于工程实现正确。要考虑:

- 浮点精度边界
- 性能(每帧 N 个查询)
- 内存(数据结构紧凑)
- 边角 case(无穷大、NaN、负数)

**第四层:工业理解**

工业级要再加:

- 多线程安全
- SIMD 优化
- 网络同步(多人游戏)
- 跨平台(Windows/Mac/Linux/Mobile)
- 可访问性(色盲友好)
- 反作弊

每层理解都让代码更鲁棒。资深工程师在所有层次同时思考。

### 实际工程的细节

工业代码 80% 是"边角 case 处理",20% 是"核心算法"。Casey 在 HH 演示核心,工业代码加大量边角处理。

**边角 case 类型**:

1. 空输入(空 Vec、null pointer)
2. 极端输入(NaN、无穷大、超大数)
3. 并发竞争(多线程同时访问)
4. 资源不足(内存满、磁盘满)
5. 网络异常(超时、断连、包丢失)
6. 版本不兼容(老配置 / 新代码)
7. 权限错误(只读文件、无网络)
8. 用户误操作(连点、撤销重做)

每个 case 都要单独处理。这是工业代码 50%+ 行数的原因。

### 优化思路

性能优化有顺序:

1. **算法**:O(N²) → O(N log N),最大提升
2. **数据结构**:Vec → HashMap / BTreeMap,常数提升
3. **Cache**:AoS → SoA,cache 命中提升
4. **SIMD**:4-16 元素并行,巨大常数提升
5. **GPU**:数千核并行,极致性能
6. **分布式**:多机器,无限扩展

每级提升都需要更复杂的代码。先优化低级,够用再升级。

### 教学价值

Day 655 不只是技术教学,也是"工程哲学"教学:

- **简单 > 复杂**:够用就行
- **理解 > 记忆**:概念比代码重要
- **完成 > 完美**:能跑 > 能优化
- **持续学习**:技术永远在演化

这些哲学跨技术领域通用。学完 HH,你不只会写游戏,你**理解工程**。这是 HH 最大的价值。

### Rust 视角

Day 655 用 C 写,但 Rust 版本会更安全 / 更高效:

- **所有权**:消除 use-after-free / double-free
- **borrow check**:消除 data race
- **match exhaustive**:case 漏写编译错
- **Result<T, E>**:错误显式处理
- **no null**:Option<T> 强制 null 检查
- **fearless concurrency**:多线程安全

每条都让代码更鲁棒。Rust 是游戏开发的新趋势(bevy / wgpu / rend3),学习 Rust 让你未来 10 年受益。
