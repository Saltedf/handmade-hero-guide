7. **更深入**:多看几帧,发现 vel.x 是负的(向左),delta = -0.008(每帧 8mm)。位置变 3.7 → 3.692 → 3.684 → ... → 3.65,然后下一帧 3.642 → 3.634。
8. **真正根因**:`3.65 + (-0.008) = 3.642`,但浮点误差,实际算成 3.6500001,floor 还是 3。下一帧 3.642(注意:此时已经"穿过"了 3.65 的逻辑点)。**步进没触发 collide**,但 epsilon 检测 `pos.x + 0.05 = 3.692`,`(3.692).floor() = 3`。再下一帧 ...

实际上根因是**步进检测的"半步"边界**:

- 玩家位置在 3.5 voxel 中心(边界)
- 步进 0.1,有时正好"跨"voxel 边界,有时不跨
- 跨边界 → collide,不跨 → 不 collide
- 结果:每帧 50% 几率 collide,玩家"抖动"

**修复**:**epsilon 改成基于 voxel 中心**,不是 voxel 边界。

**今天的核心概念**:**浮点精度 + 步进边界**的边角 case。这是 voxel collision 的经典坑。

**心理锚点**:看完这集,你能:
- 系统化调试"抖动" bug
- 理解浮点精度对 voxel collision 的影响
- 设计"鲁棒"的 collision 检测

## 2 · 心智模型

### 类比:尺子测量的精度问题

你用 1mm 刻度的尺子量物体:

- 物体长 5mm → 直接读 5
- 物体长 5.5mm → 估计 5 或 6,精度有限
- 物体长 5.4999mm → 可能读 5 或 5.5

**测量精度有限导致结果不稳定**。

Voxel collision 完全一样:

- 玩家位置在 voxel 边界(x = 3.0)→ 明确在 voxel 3
- 玩家位置在 voxel 中心(x = 3.5)→ 明确在 voxel 3
- 玩家位置在边界附近(x = 2.99999)→ 浮点误差,可能 floor 到 2 或 3

**浮点精度 + voxel 边界 = 不稳定**。

### 严谨:浮点 + Voxel 边界

#### 2.1 IEEE 754 浮点精度

`f32` 有 24 位尾数,精度约 7 位有效数字。

- 0.5 表示精确
- 0.1 表示不精确(二进制循环小数)
- 0.7 表示不精确

具体:

- `(0.1 + 0.2) == 0.3` → **false**(因为浮点误差)
- `0.1_f32 + 0.2_f32 = 0.30000001192092896`

#### 2.2 Voxel 边界问题

Voxel 边界在整数 x = 0, 1, 2, ...

- 玩家 x = 0.5 → voxel 0(明确)
- 玩家 x = 1.0 → voxel 1(边界,可能 0 或 1)
- 玩家 x = 0.99999 → voxel 0(应该)
- 但浮点误差,`floor(0.99999)` 可能 = 0 或 1

**问题**:玩家"穿越"边界时,`floor` 可能给出不稳定结果。

#### 2.3 步进 + Epsilon 加剧问题

Day 634 的 collision 检测:

```rust
fn is_player_collide(world: &World, pos: Vec3) -> bool {
    let x = (pos.x + COLLISION_EPSILON).floor() as i32;  // 加 epsilon 后 floor
    let y = pos.y.floor() as i32;
    let z = pos.z.floor() as i32;
    world.is_solid(x, y, z)
}
```

玩家 x = 0.95,epsilon 0.05 → 检测 x = (1.0).floor() = 1 → voxel 1
玩家 x = 0.94,epsilon 0.05 → 检测 x = (0.99).floor() = 0 → voxel 0

**问题**:玩家从 0.95 → 0.94 移动,检测的 voxel 从 1 跳到 0。如果 voxel 0 是墙,voxel 1 是空,玩家会"半帧撞,半帧不撞"——抖动。

#### 2.4 修复:Snap to Grid

**方案 C**:玩家位置在 voxel 边界附近时,**snap 到 voxel 中心**。

```rust
fn snap_to_voxel_center(pos: Vec3) -> Vec3 {
    let x_voxel = pos.x.floor();
    let x_center = x_voxel + 0.5;  // voxel 中心
    // 如果玩家在 voxel 中心 ± 0.01 内,snap 到中心
    if (pos.x - x_center).abs() < 0.01 {
        Vec3 { x: x_center, y: pos.y, z: pos.z }
    } else {
        pos
    }
}
```

**效果**:玩家"贴墙"时,位置稳定在 voxel 中心 ± 0.5,不会卡边界。

#### 2.5 更优雅的方案:Box-based Collision

不用"点 + epsilon",用"box"做 collision:

```rust
struct PlayerBox {
    center: Vec3,
    half_size: Vec3,  // 玩家是 0.4 × 0.9 × 0.4 的 box
}

fn is_player_collide_box(world: &World, box_: &PlayerBox) -> bool {
    // 检查 box 占据的所有 voxel
    let min_x = (box_.center.x - box_.half_size.x).floor() as i32;
    let max_x = (box_.center.x + box_.half_size.x).floor() as i32;
    // 同理 y, z
    for x in min_x..=max_x {
        for y in min_y..=max_y {
            for z in min_z..=max_z {
                if world.is_solid(x, y, z) {
                    return true;
                }
            }
        }
    }
    false
}
```

**优势**:

- 检测玩家 box 占据的所有 voxel
- 不需要 epsilon(box 自带"宽度")
- 更鲁棒

HH 未来可能改成 box-based。Day 635 用 snap 作为快速修复。

### 2.7 防御性编程

预防浮点抖动:

- **避免精确比较**:`a == b` 用 `(a - b).abs() < epsilon`
- **Snap 到 grid**:边界附近 snap
- **用整数坐标**:游戏内部用整数,渲染时转浮点
- **避免 0 附近运算**:用 epsilon 保护除零

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

浮点精度问题在游戏很常见:

- **多人同步**:不同机器浮点结果不同,导致 desync
- **物理稳定性**:堆叠物体抖动
- **大世界坐标**:坐标 > 10000 时精度不够(用 f64 或相对坐标)

工业级引擎用**fixed-point 数学**或**相对坐标**避免浮点问题。

### 3.2 · 🎨 图形学视角

图形学的浮点:

- **GPU 浮点**:浮点精度低于 CPU(fast math)
- **Depth buffer**:24-bit float,远处精度低 → z-fighting
- **UV 坐标**:`uv > 1` 时 wrapping,可能浮点抖动

每个都需要 epsilon / 重新参数化。

### 3.3 · 🐧 Linux 系统编程视角

Linux 的"浮点":

- **Kernel 一般不用浮点**:浮点指令慢 + 上下文切换开销
- **用户态用 SSE / AVX**:SIMD 浮点
- **科学计算**:`long double`(80-bit),`__float128`(128-bit)

Kernel 用整数代替浮点(如 jiffies = 1/100 秒)。

### 3.4 · 🦀 Rust 生态视角

Rust 浮点:

- `f32` / `f64`:IEEE 754
- `ordered_float`:实现 Ord 的浮点(避免 NaN 比较问题)
- `decimal`:十进制浮点,避免 0.1 + 0.2 != 0.3


### Lv1 · 概念辨析

**题**:为什么 voxel collision 在边界附近会"抖动"?给出数学论证。

**参考解答**:

Voxel 边界在整数 x。玩家 x 接近整数(如 0.99999),`floor(x)` 可能因浮点误差给出 0 或 1。每次运算结果不同,导致 voxel index 振荡。

具体:`0.99999_f32` 的二进制表示可能略小于 1(因浮点精度),`floor` 给 0;但加上 epsilon 0.05 后,`(0.99999 + 0.05).floor() = 1.049998.floor() = 1`。所以同一位置,加 epsilon 前后 floor 不同 → collide 结果不同 → 抖动。

### 完整可跑的抖动复现 + 修复

```rust
// Cargo.toml: 空

#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
}

struct World {
    voxels: Vec<bool>,  // 简化:1D
    w: usize,
}

impl World {
    fn is_solid(&self, x: i32) -> bool {
        if x < 0 || x >= self.w as i32 { return true; }
        self.voxels[x as usize]
    }
}

const EPS: f32 = 0.05;

fn is_collide_buggy(world: &World, x: f32) -> bool {
    // Buggy:加 eps 后 floor,边界附近不稳定
    let xi = (x + EPS).floor() as i32;
    world.is_solid(xi)
}

fn is_collide_box(world: &World, x: f32, half_width: f32) -> bool {
    // 鲁棒:检测整个 box
    let min_x = (x - half_width).floor() as i32;
    let max_x = (x + half_width).floor() as i32;
    for xi in min_x..=max_x {
        if world.is_solid(xi) { return true; }
    }
    false
}

fn main() {
    // Voxel 1 是墙,其余空
    let world = World { voxels: vec![false, true, false, false], w: 4 };

    println!("=== Buggy version ===");
    let mut pos = 0.95_f32;
    let vel = -0.001_f32;
    let mut last_collide = false;
    let mut changes = 0;
    for frame in 0..200 {
        let collide = is_collide_buggy(&world, pos);
        if collide != last_collide {
            changes += 1;
            println!("frame {}: pos={:.10} collide changed: {} → {}", frame, pos, last_collide, collide);
            last_collide = collide;
        }
        pos += vel;
    }
    println!("Total collide changes (jitter count): {}", changes);

    println!("\n=== Box version (robust) ===");
    let mut pos = 0.95_f32;
    let vel = -0.001_f32;
    let mut last_collide = false;
    let mut changes = 0;
    for frame in 0..200 {
        let collide = is_collide_box(&world, pos, 0.3);  // 玩家宽 0.6
        if collide != last_collide {
            changes += 1;
            println!("frame {}: pos={:.10} collide changed: {} → {}", frame, pos, last_collide, collide);
            last_collide = collide;
        }
        pos += vel;
    }
    println!("Total collide changes (jitter count): {}", changes);
}
```

## 附录 · IEEE 754 深度

Day 635 的浮点抖动根因是 IEEE 754。深入理解很重要。

### IEEE 754 浮点格式

f32 结构(32 位):

- **Sign**:1 bit
- **Exponent**:8 bits(bias 127)
- **Mantissa**:23 bits

公式:`value = (-1)^sign × (1.mantissa)_2 × 2^(exponent - 127)`

例:0.5 = `0 01111110 00000000000000000000000`

- sign=0, exponent=126(实际 -1), mantissa=0
- value = 1.0 × 2^(-1) = 0.5

### 为什么 0.1 不能精确表示

0.1 在二进制是循环小数:

- 0.1 = 0.0001100110011001100... (循环)
- 截断到 23 bits → 误差

所以 `0.1_f32 ≠ 0.1`,是 0.10000000149011612...

### Floating-Point Errors 的累积

每次运算有微小误差。**累积**会让误差放大:

```rust
let mut sum = 0.0_f32;
for _ in 0..1000 {
    sum += 0.001;
}
println!("{}", sum);  // 0.99999998,不是 1.0
```

1000 次加 0.001 应该 = 1.0,但浮点累积误差。

### Kahan Summation Algorithm

减少累积误差的算法:

```rust
fn kahan_sum(values: &[f32]) -> f32 {
    let mut sum = 0.0;
    let mut c = 0.0;  // compensation
    for v in values {
        let y = v - c;
        let t = sum + y;
        c = (t - sum) - y;
        sum = t;
    }
    sum
}
```

**效果**:1000 次加 0.001 = 0.99999998(普通)→ 1.0(Kahan)。

### 多机同步问题

不同机器浮点结果可能不同:

- x86 vs ARM:中间精度不同
- 不同 compiler flags:`-ffast-math` 改变行为
- FMA(融合乘加):不同硬件可能用 / 不用

**多人游戏**用 lockstep 同步,浮点 desync 导致"幽灵行为"。

**修复**:

- 用 fixed-point math
- 或 determinism 模式(`#[cfg(deterministic)]`)
- 或 server-authoritative

### NaN 和 Inf

IEEE 754 特殊值:

- **NaN**(Not a Number):0/0, √-1 等
- **+Inf**:1/0
- **-Inf**:-1/0

Rust:

```rust
let nan = f32::NAN;
nan == nan  // false!NaN 不等于自己
nan.is_nan()  // true
```

**坑**:`Vec<f32>::sort()` 在 NaN 时 panic,因为 Ord 没法定义。

### Subnormal Numbers

非常小的数(< 1.1754949e-38),特殊表示。

- **慢**:某些硬件 subnormal 处理慢 10-100 倍
- **flush to zero**:某些平台把 subnormal 当 0

游戏性能问题可能源自 subnormal。

### Flush to Zero(FTZ)

```rust
// Rust 默认不开 FTZ
// C 用 _MM_SET_FLUSH_ZERO_MODE(_MM_FLUSH_ZERO_ON)
```

开启 FTZ 提速,但精度损失。游戏开发常用。

## 附录 II · Fixed-Point Math(替代浮点)

Day 635 用浮点 + epsilon 解决抖动。**根本解决**用 fixed-point。

### Fixed-Point 原理

不用 IEEE 754,用**整数**表示小数:

```rust
struct FixedPoint<i32> {
    raw: i32,
    // 假设小数点后 16 位(16.16 格式)
}

impl FixedPoint {
    fn from_int(x: i32) -> Self { Self { raw: x << 16 } }
    fn from_f32(x: f32) -> Self { Self { raw: (x * 65536.0) as i32 } }
    fn to_f32(&self) -> f32 { self.raw as f32 / 65536.0 }

    fn add(self, other: Self) -> Self { Self { raw: self.raw + other.raw } }
    fn sub(self, other: Self) -> Self { Self { raw: self.raw - other.raw } }
    fn mul(self, other: Self) -> Self {
        Self { raw: ((self.raw as i64 * other.raw as i64) >> 16) as i32 }
    }
    fn div(self, other: Self) -> Self {
        Self { raw: ((self.raw as i64 << 16) / other.raw as i64) as i32 }
    }
}
```

**优势**:

- 精确(整数运算无误差)
- 多机同步(同输入同输出)
- 快(整数运算比浮点快在某些硬件)

**劣势**:

- 范围有限(16.16 最大 ~32K)
- 复杂(每个运算要 shift)
- 库支持少

### Fixed-Point 在游戏中的应用

- **Doom**(1993):用 16.16 fixed-point,因为当时浮点慢
- **StarCraft**:网络同步用 fixed-point
- **GBA / DS 游戏**:没有 FPU,fixed-point 必须
- **多人游戏**(Lockstep):fixed-point 保证 desync-free

### Rust 的 fixed-point crate

```toml
[dependencies]
fixed = "1.20"  # 各种 bit width
fixpt = "0.2"
```

```rust
use fixed::types::I16F16;
let a = I16F16::from_num(0.1);
let b = I16F16::from_num(0.2);
let c = a + b;
assert_eq!(c, I16F16::from_num(0.3));  // 精确!
```

### 何时用 fixed-point

- **多人 lockstep 游戏**:必须 fixed(浮点 desync)
- **金融**:必须 fixed(0.1 元精确)
- **嵌入式**:可能没 FPU
- **科学计算**:用浮点(范围 + 精度)

HH 单人游戏,**浮点 + epsilon 够用**。如果未来加多人,切 fixed。

### Voxel 整数坐标

更激进:**所有 voxel 坐标用整数**:

```rust
struct PlayerPos {
    voxel: (i32, i32, i32),  // 所在 voxel
    offset: (i32, i32, i32),  // voxel 内偏移,0..65536(16-bit fixed)
}
```

完全无浮点。HH 的简化版用浮点,**因为代码简单 + 玩家不需要多机同步**。

- **float inspector**:GDB 看浮点位
- **deterministic build**:同代码同输入同输出
- **lockstep validator**:多机结果对比

每个工具解决不同问题。

## 附录 III · 调试方法论总结

Day 635 是浮点 bug 调试。这总结 Phase 8 学的调试方法论。

### 调试的 7 个步骤

#### 1. 复现

bug 必现才能修。

- 找最小复现 case
- 记录触发条件
- 自动化(脚本)

#### 2. 量化

数字而非形容词。

- "1 帧卡顿" 而非 "慢"
- "位置 3.642" 而非 "附近"

#### 3. 加 debug log

打印关键变量,观察行为。

#### 4. 二分定位

注释 / 启用部分代码,找引入 bug 的具体行。

#### 5. 提出假设

"我假设 bug 在 X,因为 Y"

#### 6. 反向验证

"如果是 X,那么 Z 应该成立。测 Z → 不成立 → 假设错"

#### 7. 修复 + 测试 + 防回退

修代码,加测试,确保不再回归。

### 调试的"反向思维"

不要问"为什么 bug 出现",问:

- **"为什么不是 bug"**——所有"非 bug"的可能性都排除后,剩下的就是 bug 根因
- 类似 Sherlock Holmes:**"排除不可能,剩下的无论多荒谬都是真相"**

### 调试的反模式

#### 反模式 1: 凭感觉改

"我觉得是这里" → 改了再说。引入新 bug。

**正确**:**复现 → 量化 → log → 定位**,不要凭感觉。

#### 反模式 2: 大改修小 bug

bug 小,改了一大堆。引入复杂度。

**正确**:**最小改动**——只改必要的。

#### 反模式 3: 不加测试

修了,没加测试。6 个月后回归。

**正确**:**每个 bug 加测试**。

#### 反模式 4: 不写 commit 说明

"fix bug"——谁知道修了啥。

**正确**:**详细说明 root cause + fix + test**。

### Casey 的调试风格

Casey 调试:

- 复现至上
- 加大量 log
- 反向排除
- 修复后必加测试
- commit 详细

**这是工业级工程师的调试风格**。

### 调试的认知层面

调试不全是技术——也考验:

- **耐心**:复现 bug 可能要几小时
- **谦虚**:不假设"我没错"
- **好奇**:"为什么这样"的好奇心
- **专注**:不被其他事打断

每个品质都需要培养。
