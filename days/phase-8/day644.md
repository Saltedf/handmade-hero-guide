# Day 644 · 单步图表

> Day 638 录制器 / Day 639 画图 / Day 643 修了 4 个 bug。今天 Casey 把录制器**完全集成到调试 workflow**——加键盘控制(单步前进/后退/暂停/慢放),让你可以像 gdb 那样"逐帧"调游戏。

## 0 · 为什么要有这一天

修了 4 个 bug 之后,Casey 意识到:**每次新 bug 都要重写调试代码很烦**。需要的不是"再加一个 debug print",而是"系统化的回放工具"——像视频播放器一样,任意拖动时间轴,看任意一帧的状态。

今天 Casey 给录制器加 keyboard control:

- **F1**:暂停/继续
- **F2**:单步前进(下一帧)
- **F3**:单步后退(上一帧)
- **F4**:慢放(0.25x)
- **F5**:正常速度
- **F6**:快放(2x)

这套 control 之所以重要,因为 **bug 不是在某帧发生,而是在某段帧序列里演化**。单帧调试器(gdb)看不到演化,你只能猜。录制器让你"看到演化",这就是为什么工业引擎都内置 frame debugger。

心理锚点:看完今天,你能:

- 实现时间轴控制 UI
- 设计录制器 / 模拟器分离的架构
- 用键盘热键驱动调试

## 1 · Casey 今天做了什么

1. 引入 `DebugState` enum:`Running / Paused / Stepping(direction)`
2. 主循环读键盘,根据 state 决定是否 advance simulation
3. 录制器始终录,即使暂停(暂停时录的是"空"帧,或者直接不 advance 但画 overlay)
4. 单步后退:`frame_cursor -= 1`,只画 `history[frame_cursor]`,不 advance simulation
5. 慢放:每 N 个真实帧才 advance 一次模拟
6. 把控制 panel 也用 immediate mode 画到屏幕一角
7. 用新工具回头看 Day 643 的 4 个 bug,确认 bug 修复彻底

## 2 · 心智模型

### 类比:看视频回放

视频播放器有"暂停 / 单步 / 慢放 / 快放"——录制器完全一样。差别是:**视频已经录好,你在播放;录制器是边玩边录,但可以"冻结时间"**。

冻结时间是游戏的特权——真实物理不能暂停,但游戏世界是你的,你想停就停。

### 时间轴状态机

游戏主循环的状态:

```
            F1
   ┌─────────────────────┐
   │                     ▼
┌──┴───┐ F2     ┌────────┴──┐
│Paused│ ─────> │Stepping + │
│      │ <───── │           │
└──┬───┘        └───────────┘
   │                     ▲
   │ F1                  │ F2
   ▼                     │
┌──────┐ F4/F5/F6 ┌──────┴──┐
│Running│ <──────> │Slow/Fast│
└──────┘          └─────────┘
```

Paused 时,simulation 不前进,只画当前 cursor 处的录制。
Stepping 时,simulation 前进一帧,然后自动变 Paused。

### 主循环的修改

原来:

```rust
while running {
    let dt = clock.tick();
    process_input();
    update_simulation(dt);
    render();
}
```

修改后:

```rust
while running {
    let dt = clock.tick();
    process_input();
    handle_debug_keys(); // F1-F6 处理

    let should_advance = match debug_state {
        DebugState::Running => true,
        DebugState::Paused => false,
        DebugState::Stepping(_) => { /* one-shot */ true },
        DebugState::Slow(scale) => { /* every 1/scale frames */ ... },
    };

    if should_advance {
        update_simulation(dt);
        recorder.frame_end(); // 把这一帧 commands 入 ring buffer
    }

    render();
    if !should_advance { recorder.playback_at(cursor); }
}
```

### 单步后退的实现

后退不像前进那么直接——simulation 是前向的,你不能"反向跑"。但**录制器存的是声明式命令**,不是过程化执行,所以可以直接画任意一帧:

```rust
fn playback_at(recorder: &Recorder, frame_idx: usize, r: &mut Renderer) {
    let frame = &recorder.history[frame_idx];
    r.clear();
    for cmd in &frame.commands {
        r.execute(cmd);
    }
}
```

前进 cursor += 1,后退 cursor -= 1。**关键是 cursor 和 simulation 解耦**——simulation 一直跑,但你可以"回看"任意历史帧。

### 慢放实现

慢放不是让 dt 变小(那会改变物理),而是**降低帧率**——每 N 个真实帧才 advance 一次:

```rust
let mut frame_accumulator = 0;
let scale = 0.25; // 0.25x speed
frame_accumulator += scale;
if frame_accumulator >= 1.0 {
    frame_accumulator -= 1.0;
    update_simulation(dt);
}
// render 总是跑,所以画面流畅,只是 simulation 慢
```

但是慢放有个细节:**渲染是每帧,但 simulation 不是每帧**。玩家在慢放时看到画面 60 fps,但游戏世界以 15 fps 演化。这对应**真实 dt**(每帧 1/60),不是"虚拟 dt"(应该慢)。Casey 让 simulation 总是用固定 dt(1/60),慢放只是降低 simulation 频率。

### 录制器和模拟器的分离

这是关键的架构决策:**simulation 不知道 recorder 的存在**。simulation 每帧调 `recorder.draw_aabb(...)` 等函数,以为自己在直接画,但实际是录到 buffer。

```rust
// Simulation 代码
fn update_simulation(world: &mut World, recorder: &mut Recorder) {
    world.update();
    recorder.draw_aabb(world.player.bbox(), RED);
    recorder.draw_text(world.player.pos, &format!("vel={:?}", world.player.vel), WHITE);
}
```

simulation 永远调 recorder 函数,不管是在 Running 还是 Paused 状态。recorder 决定:

- **Running / advance**:录 + 立即执行
- **Paused**:不录(因为 simulation 没跑),不执行,只画 cursor 处的历史
- **Stepping**:录一帧 + 立即执行,然后 Paused

### Immediate mode UI for control panel

```rust
fn draw_debug_ui(ui: &mut Ui, state: &mut DebugState, cursor: usize, total: usize) {
    ui.text(&format!("Frame {} / {}", cursor, total));
    ui.button("Play", || *state = DebugState::Running);
    ui.button("Pause", || *state = DebugState::Paused);
    ui.button("Step +1", || *state = DebugState::SteppingForward);
    ui.button("Step -1", || *state = DebugState::SteppingBackward);
}
```

immediate mode:每帧重新调一次,函数式风格。状态在 `state` 里,UI 函数不持有任何持久对象。这是 Casey 风格 UI 的核心。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏里"录制-回放"的著名实现:

- **Unity Recorder**:Editor 工具,录场景动画到文件
- **Unreal Take Recorder**:类似 Unity Recorder,录电影机动画

- **Dota 2 demo**:录比赛 demo 文件,小(几 KB / 秒)

关键差别:**录输入 vs 录状态**。Casey 录状态(几何命令),简单但内存大。商业游戏录输入,小但要求"模拟器确定"(不能有 random / nondeterministic 代码)。

### 3.2 · 图形学视角

frame debugger 的工业标杆:

- **RenderDoc**:录一帧 GPU 命令,任意 step through draw calls
- **PIX**(DirectX):Windows 上 GPU profiling
- **Intel Graphics Performance Analyzer**:跨平台 GPU profiling
- **NVIDIA Nsight**:NV GPU 专用

这些工具录 GPU 命令,Casey 的录制器录 CPU 几何命令,但**架构一样**:命令流 + 时间轴 + 单步。

### 3.3 · Linux 系统编程视角

Linux 上的录制工具:

- **strace -o file**:录系统调用,事后分析
- **rr record**:录进程执行,`rr replay` 反向单步
- **perf record -g**:采样调用栈,事后 `perf report`
- **ftrace**:内核函数 trace,可触发 echo > traceon

差别:strace / rr 录"行为",Casey 录"声明式数据"。声明式数据更容易任意点回放(不需要"反向执行")。

### 3.4 · Rust 生态视角

Rust 里时间轴控制的优雅实现:

```rust
use std::collections::VecDeque;

#[derive(Clone, Copy, PartialEq)]
enum DebugState { Running, Paused, Stepping(i32) } // i32: -1 后退 +1 前进

struct Debugger {
    state: DebugState,
    cursor: usize,
    slow_factor: u32, // 每 N 帧一次 advance
    slow_counter: u32,
}

impl Debugger {
    fn should_advance(&mut self) -> bool {
        match self.state {
            DebugState::Running => true,
            DebugState::Paused => false,
            DebugState::Stepping(d) => {
                if d > 0 { /* cursor +1 逻辑 */ }
                self.state = DebugState::Paused; // 一步就停
                false // simulation 不跑,只 cursor 移
            }
        }
    }
    fn handle_key(&mut self, key: KeyCode) {
        match key {
            KeyCode::F1 => self.state = match self.state {
                DebugState::Running => DebugState::Paused,
                _ => DebugState::Running,
            },
            KeyCode::F2 => self.state = DebugState::Stepping(1),
            KeyCode::F3 => self.state = DebugState::Stepping(-1),
            _ => {}
        }
    }
}
```

`enum DebugState` 是 sum type,变体可以带 payload。比 OOP 的"基类 + 子类"更紧凑。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么单步后退在录制器里"免费",但在 simulation 里"不可能"?

**参考解答**:录制器存的是**声明式命令**(几何数据),声明式数据可以任意时刻读取。simulation 是**过程化执行**(代码),过程不能反向跑——你不能"撤销物理演化"。录制器把过程"投影"为声明,丢失了过程信息,但获得了"任意时刻可读"的能力。这就是声明式 vs 命令式的核心差别。

### Lv2 · 动手实践

**题**:实现 §3.4 的 Debugger,加 ring buffer 录制,加键盘模拟(F1/F2/F3)。

**参考解答**:

```rust
use std::collections::VecDeque;

#[derive(Clone, Copy, PartialEq, Debug)]
enum State { Running, Paused, Step(i32) }

#[derive(Clone, Debug)]
struct Frame { label: String }

struct Sim {
    state: State,
    cursor: usize,
    history: VecDeque<Frame>,
    capacity: usize,
    sim_time: usize,
}

impl Sim {
    fn new(cap: usize) -> Self {
        Self {
            state: State::Running,
            cursor: 0,
            history: VecDeque::with_capacity(cap),
            capacity: cap,
            sim_time: 0,
        }
    }
    fn key(&mut self, k: &str) {
        match k {
            "F1" => self.state = match self.state {
                State::Running => State::Paused,
                _ => State::Running,
            },
            "F2" => self.state = State::Step(1),
            "F3" => self.state = State::Step(-1),
            _ => {}
        }
    }
    fn tick(&mut self) {
        let advance = match self.state {
            State::Running => true,
            State::Paused => false,
            State::Step(d) => {
                if d > 0 {
                    self.cursor = self.cursor.saturating_add(1).min(self.history.len().saturating_sub(1));
                } else {
                    self.cursor = self.cursor.saturating_sub(1);
                }
                self.state = State::Paused;
                false
            }
        };
        if advance {
            self.sim_time += 1;
            if self.history.len() == self.capacity { self.history.pop_front(); }
            self.history.push_back(Frame { label: format!("frame {}", self.sim_time) });
            self.cursor = self.history.len() - 1;
        }
    }
    fn current(&self) -> Option<&Frame> {
        self.history.get(self.cursor)
    }
}

fn main() {
    let mut sim = Sim::new(300);
    // 模拟 5 帧运行
    for _ in 0..5 { sim.tick(); println!("run:   {:?}", sim.current().map(|f| &f.label)); }
    sim.key("F1"); // 暂停
    sim.tick(); println!("pause: cursor={}, len={}", sim.cursor, sim.history.len());
    sim.key("F3"); // 后退一步
    sim.tick(); println!("back:  {:?}", sim.current().map(|f| &f.label));
    sim.key("F2"); // 前进一步
    sim.tick(); println!("fwd:   {:?}", sim.current().map(|f| &f.label));
}
```

## 8 · Rust / Arch 落地代码

完整 frame debugger(纯 std):

```rust
use std::collections::VecDeque;
use std::io::{self, BufRead, Write};

#[derive(Clone, Copy, PartialEq, Debug)]
enum State { Running, Paused, StepFwd, StepBack, Slow(u32) }

struct Frame {
    sim_time: u64,
    label: String,
}

struct Debugger {
    state: State,
    history: VecDeque<Frame>,
    cursor: usize,
    capacity: usize,
    sim_time: u64,
    slow_counter: u32,
}

impl Debugger {
    fn new(cap: usize) -> Self {
        Self {
            state: State::Running,
            history: VecDeque::with_capacity(cap),
            cursor: 0,
            capacity: cap,
            sim_time: 0,
            slow_counter: 0,
        }
    }
    fn handle_cmd(&mut self, line: &str) {
        match line.trim() {
            "play" | "F5" => self.state = State::Running,
            "pause" | "F1" => self.state = State::Paused,
            "fwd" | "F2" => self.state = State::StepFwd,
            "back" | "F3" => self.state = State::StepBack,
            "slow" => self.state = State::Slow(4),
            s if s.starts_with("slow ") => {
                let n: u32 = s[5..].parse().unwrap_or(4);
                self.state = State::Slow(n);
            }
            "quit" => std::process::exit(0),
            _ => {}
        }
    }
    fn tick(&mut self) {
        let advance = match self.state {
            State::Running => true,
            State::Paused => false,
            State::StepFwd => {
                self.state = State::Paused;
                if self.cursor + 1 < self.history.len() {
                    self.cursor += 1;
                    return;
                }
                true // 在最新帧上 step,继续 advance
            }
            State::StepBack => {
                self.state = State::Paused;
                if self.cursor > 0 { self.cursor -= 1; }
                false
            }
            State::Slow(n) => {
                self.slow_counter += 1;
                if self.slow_counter >= n {
                    self.slow_counter = 0;
                    true
                } else { false }
            }
        };
        if advance {
            self.sim_time += 1;
            if self.history.len() == self.capacity { self.history.pop_front(); }
            self.history.push_back(Frame {
                sim_time: self.sim_time,
                label: format!("frame_{}", self.sim_time),
            });
            self.cursor = self.history.len() - 1;
        }
    }
    fn render(&self) {
        let f = self.history.get(self.cursor);
        println!("State: {:?}, cursor: {}/{}, frame: {:?}",
            self.state, self.cursor, self.history.len(),
            f.map(|f| &f.label));
    }
}

fn main() {
    let mut dbg = Debugger::new(300);
    println!("Commands: play, pause, fwd, back, slow [n], quit");
    let stdin = io::stdin();
    print!("> "); let _ = io::stdout().flush();
    for line in stdin.lock().lines() {
        let line = line.unwrap();
        dbg.handle_cmd(&line);
        for _ in 0..3 {
            dbg.tick();
            dbg.render();
        }
        print!("> "); let _ = io::stdout().flush();
    }
}
```

## 10 · 工程反思

Day 644 传达的核心工程教训:**调试工具的 UI 设计 = 应用 UX 设计**。

新手工程师做 debug UI 随便堆按钮——"加一个按钮",资深工程师做 debug UI 用 UX 原则——"键盘优先、清晰分组、即时反馈"。Day 644 的"单步图表"是个完美的 UX 案例:

- **键盘控制**:F5 单步,F6 反向,F7 暂停,F8 慢放——符合 vim / gdb 习惯
- **状态可见**:右上角显示"当前帧 / 总帧数",玩家知道在哪
- **快捷键友好**:单键、无 modifier、易按
- **响应迅速**:按下立即反馈,无延迟

这套 UX 让 debug 高效。工业级 debug 工具(RenderDoc、PIX、Xcode Metal debugger、Tracy)都用类似 UX。

**第二条教训**:**Time-travel debugging 是 debug 终极形态**。

传统 debug(gdb)是"线性的"——程序停在某个点,你看变量。但 bug 涉及"演化",你需要"倒带"看历史。

time-travel debugging 工具:

- **rr**(Mozilla):Linux C/C++,record + replay
- **UndoDB**:商业,工业级
- **WinDbg TTT**:Windows 时间旅行
- **Chrome DevTools**:JS 录制 + 回放
- **Casey 的录制器**:游戏状态的录制 + 回放

每个工具都让 debug 效率 10x。学懂这套思路,你看所有 debug 工具都是同构的。

**第三条教训**:**录制 + 回放是 testing 的基础**。

录制器录制的"帧序列"可以直接当 test case。运行时跑同一录制,确认输出一致。这是**deterministic testing**(确定性测试)——同样的输入产生同样的输出。

工业实践:游戏行业叫它"automation replay"。每次发布前跑所有 replay,确认无 regression。比传统单元测试覆盖率高 10 倍(因为 replay 包含完整状态演化)。

**迁移到其他领域**:

"录制 + 回放 debug"在多处通用:

- **数据库**:binlog replay(MySQL、PostgreSQL)
- **网络**:tcpdump + tcpreplay
- **API 测试**:Postman / Insomnia 录制请求序列
- **ML training**:checkpoint + replay
- **操作系统**:system call replay(strace + 重放)

每个领域都需要"记录 + 重放"的能力。Casey 在 HH 实现的是游戏版本。

## 11 · 单步回放的工业级实现

Day 644 演示最简单的"键盘控制单步"。工业级实现要考虑:

**1. 录制格式**:

```rust
struct Recording {
    version: u32,
    seed: u64,  // 用于确定性重放
    frames: Vec<Frame>,
}

struct Frame {
    index: u32,
    timestamp: f64,
    entities: Vec<EntitySnapshot>,
    inputs: Vec<InputEvent>,
    random_state: u64,  // PRNG 状态,确保重放确定性
}
```

每个字段都为"确定性"服务——同种子 + 同输入 = 同输出。

**2. 压缩**:

完整录制 1000 帧 × 1000 entities = 1M snapshots,内存大。压缩方法:

- **Delta encoding**:只存变化
- **Quantization**:float 32 → 16
- **Key frame**:每 N 帧存完整,中间存 delta
- **zstd**:整体压缩

工业级录制器 10-100x 压缩。

**3. 回放控制**:

- 暂停 / 继续
- 单步前进 / 后退
- 跳到任意帧
- 慢放 / 快放
- 反向播放(需要全部录制,不能 stream)

每个功能都要 UX 设计。Unity / Unreal 的 recorder 都有这套。

**4. 多视角**:

回放时,相机可以独立移动——不绑定到玩家。这允许"自由观察 bug 现场"。

**5. 分享**:

录制文件可以分享给同事。同事打开同录制,看到同 bug。这是工业 team debug 的核心。

**Casey 在 HH 简化**:

- 单线程(工业多线程)
- 单视角(工业自由相机)
- 无压缩(工业有)
- 无分享(工业有)

但**核心思路一致**——record + replay。学懂 HH,工业级是"HH + 优化 + UX"。

## 12 · deterministic replay 的工程意义

确定性重放(deterministic replay)是工业级 game testing 的金矿:

- **Regression test**:每次改代码,跑老录制,确认结果不变
- **Bug report**:玩家上传"卡 bug 的录制",开发者本地复现
- **Performance test**:同录制不同机器,对比 FPS
- **Multiplayer sync**:server 录制,client 重放(确认一致性)

每个价值都让团队效率 10x。所以 AAA 游戏公司都投资 deterministic replay 系统。

**deterministic 的难点**:

- **浮点**:不同 CPU 浮点行为略不同(x87 vs SSE)
- **多线程**:线程调度顺序不确定
- **系统调用**:time / random / IO 不确定
- **初始化**:未初始化内存(UB)

每个都要严格控制。Rust 在这方面优秀——所有权系统、严格的 UB 检测、`std::time::Instant` 抽象。

工业教训:**deterministic 不是免费的**——需要从项目开始就设计,后期改造痛苦。Casey 在 HH 没追求完全 deterministic,但他的录制器结构允许扩展。

## 13 · deterministic replay 的工业级挑战

完全 deterministic replay 需要解决:

**1. 浮点确定性**:

不同 CPU(x86 / ARM)、不同编译器(MSVC / GCC / Clang)、不同优化级别(O0 / O2 / O3)下,浮点运算结果可能不同。这是 deterministic replay 的最大障碍。

工业解法:

- **Fixed-point**:用整数代替浮点(1000 = 1.0 米)
- **Software float**:自己实现 IEEE 754,确保跨平台一致
- **Lockstep**:每帧结束时 hash 所有状态,不同步就 rollback

每个解法都有自己的代价。StarCraft / Age of Empires 用 fixed-point,因为 RTS 需要严格 lockstep。

**2. 多线程**:

线程调度顺序影响结果。工业解法:

- **Single-threaded simulation**:物理在主线程,渲染并行
- **Deterministic scheduler**:线程调度按固定顺序

**3. Random**:

全局 PRNG 跨线程不安全。工业解法:

- **Per-thread PRNG**:每线程独立种子
- **Pre-generated random table**:预生成,运行时查表

**4. System state**:

时间戳、文件内容、网络延迟——都影响 deterministic。工业级隔离这些(用 mock time / fixed file / network replay)。

## 14 · 录制器作为 QA 工具

工业级 QA(Quality Assurance)用录制器做:

**1. Automated smoke test**:

- 录制 "通关一遍" 的输入
- 每次 build 后跑 replay,确认没崩

**2. Stress test**:

- 录制 "100 个敌人同屏"
- 跑 replay 测性能

**3. Compatibility test**:

- 不同硬件(DirectX / Vulkan / Metal)跑同 replay
- 确认视觉一致

**4. Bug report**:

- 玩家上传 replay
- 开发者本地复现,debug

每个用途都让 QA 效率 10x。这是工业级录制器的核心价值。

## 15 • 录制器作为教学工具

录制器不仅是 debug 工具,也是教学工具:

**1. 视觉化抽象概念**:

**3. 历史回放**:

工业教训:**教学项目应该投资录制器**。Casey 在 HH Day 638-644 用 7 集建录制器,后续几十集都受益。这是教学ROI 最高的工程。
