# Day 633 · 收敛到碰撞方案

> Day 632 实验发现 3 个问题(穿墙、斜坡、边界卡)。今天 Casey **收敛方案**——决定保留哪些简化、修哪些问题、放弃哪些 case。设计是 trade-off,完美不存在,**收敛 = 选择放弃什么**。

## 0 · 为什么要有这一天

Day 632 的 MVP 发现:

1. **高速穿墙**(速度 > 20 m/s 时仍可能穿):步进不够细
2. **无法上斜坡**:voxel 都是立方体,没有斜面
3. **边界卡顿**:浮点精度问题,玩家"卡"voxel 边

**完美解决**(全做):8 天都不够。

**实用解决**(选择):今天的工作。

每个问题的解决方案:

| 问题 | 完美方案 | 实用方案 | 决定 |
|---|---|---|---|
| 穿墙 | 真 CCD(sweep) | 步进 size 减小到 0.1 | 步进减小(够用) |
| 斜坡 | Voxel + metadata(斜面 voxel) | 不支持斜坡(只有台阶) | 不支持(简化) |
| 边界卡 | 容差 + sub-voxel 精度 | 加 0.05 epsilon | 加 epsilon |

**今天的核心概念**:**Trade-off analysis**(权衡分析)。每个决策都有代价,**选择放弃什么比选择做什么更重要**。

**心理锚点**:看完这集,你能:
- 做 trade-off 分析
- 决定"放弃哪些 case"
- 接受"不完美但够用"

## 2 · 心智模型

### 类比:买车时的取舍

你买车,有 30 万预算。选项:

- 跑车(快,但费油)
- SUV(空间大,但慢)
- 经济型(省油,但性能一般)
- 二手豪华(品牌好,但维修贵)

**不能全要**——必须取舍。

- 你常通勤?经济型
- 你常郊游?SUV
- 你爱速度?跑车

**选了 X,就放弃 Y**。

游戏设计完全一样:

- 完美碰撞(无穿墙 + 支持斜坡 + 高精度)→ 慢,工作量大
- 实用碰撞(允许极少数穿墙 + 不支持斜坡 + 中精度)→ 快,工作量小

**选实用 = 放弃完美**。

### 严谨:Trade-off 分析

#### 2.1 三个问题的详细分析

##### 问题 1:高速穿墙

**完美方案**:Continuous Collision Detection(CCD)

- 用 sphere sweep 或 raycast 沿路径检测
- 性能:每帧多次 raycast,~10x 慢
- 工作量:1-2 天

**实用方案**:减小步进 size

- 步进从 0.3 减到 0.1
- 性能:每帧步进数 3x,但每次 O(1),总开销小
- 工作量:改 1 个常量

**决策**:**实用**。理由:

- HH 玩家速度 5 m/s,dt 0.016s,每帧移动 0.08m
- 步进 0.1m > 0.08m,**单步足够**
- 不需要真 CCD

##### 问题 2:斜坡

**完美方案**:Voxel + metadata(每个 voxel 有"斜面"信息)

- 渲染:斜面 voxel 用特殊 sprite
- 碰撞:斜面 voxel 玩家"滑上去"
- 工作量:2-3 天

**实用方案**:不支持斜坡

- 场景只有台阶(每阶 0.5m),玩家跳上去
- 工作量:0(什么都不做)

**决策**:**实用**。理由:

- HH 的场景设计是 medieval dungeon,主要是台阶不是斜坡
- 玩家有跳跃能力,可以上台阶
- 斜坡支持太复杂,**未来需要时再加**

##### 问题 3:边界卡顿

**完美方案**:Sub-voxel precision(用 capsule + raycast 精确)

- 玩家用 capsule 表示,raycast 找精确碰撞
- 性能:稍慢,但精确
- 工作量:1-2 天

**实用方案**:加 epsilon

- 碰撞检测时,玩家位置 + epsilon 容差
- 比如 is_solid(pos - eps) 检测,撞了就不动
- 工作量:1 个常量

**决策**:**实用**。理由:

- 边界卡顿影响"贴墙走"手感
- Epsilon 0.05 足以消除抖动
- 完美方案工作量大,收益边际

#### 2.2 决策矩阵

| 问题 | 完美 | 工作量 | 实用 | 工作量 | 选 |
|---|---|---|---|---|---|
| 穿墙 | CCD | 2 天 | 减小步进 | 1 行 | 实用 |
| 斜坡 | Voxel metadata | 3 天 | 不支持 | 0 | 实用 |
| 边界 | Sub-voxel | 2 天 | Epsilon | 1 行 | 实用 |

**节省**:7 天 vs 2 行代码。**用 2 行代码获得 80% 的完美方案效果**——这是 80/20 法则。

#### 2.3 80/20 法则

帕累托法则:**80% 的效果来自 20% 的投入**。

应用到碰撞:

- 完美(100% 效果):7 天工作
- 实用(80% 效果):2 行代码

**实用方案获得 80% 效果,投入 < 5%**。

**剩下 20%**(高速穿墙、斜坡、sub-voxel 精度)**需要 95% 投入**——不划算。

**核心**:**实用方案足够好时,就别追求完美**。

#### 2.4 决策的代价

每个"放弃"都有代价:

- 穿墙:玩家速度 > 10 m/s 时偶尔穿(罕见,因为速度上限 5)
- 斜坡:场景没有斜坡(美术约束)
- 边界:极少数情况仍有 1mm 抖动(肉眼几乎看不出)

**每个代价都小**,**整体价值大**(节省 7 天)。

### 2.5 Design Doc

```markdown
# Collision Design (Final)

Date: Day 633
Status: Final

## Decisions

###穿墙
- Solution: Reduce step size to 0.1 (was 0.3)
- Trade-off: Slight perf cost (3x more steps per frame), still O(1)
- Rejected: True CCD (too much work for rare case)

### 斜坡
- Solution: NOT SUPPORTED
- Trade-off: Level designers must use stairs (0.5m steps), player jumps
- Rejected: Voxel slope metadata (2-3 days work, marginal value)

### 边界卡顿
- Solution: Add 0.05 epsilon to collision check
- Trade-off: Player position may be slightly off (1-2cm)
- Rejected: Sub-voxel precision (too complex)

## Acceptance criteria

- Player moves at 5 m/s without穿墙
- Stairs (0.5m steps) navigable
- Wall sliding smooth (no visible jitter)

## Future considerations

- If game adds vehicles (>10 m/s), revisit CCD
- If level designs need slopes, add voxel slope metadata
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发的"实用主义":

- **Minecraft**:无物理引擎,所有"碰撞"是 voxel + 简单 AABB。够用就行
- **Stardew Valley**:2D tile,简单碰撞。够用
- **Celeste**:精确 collision box + tight 控制。需要精度
- **HH(本日)**:实用 voxel collision。够用

每个游戏按需求选精度。**没有"对错",只有"合适"**。

### 3.2 · 🎨 图形学视角

图形学的 trade-off:

- **Ray tracing**(完美)vs **Rasterization**(快)
- **BRDF**(物理)vs **Blinn-Phong**(简单)
- **Path tracing**(慢但真实)vs **Real-time**(快但近似)

每个都是 trade-off,**适合场景才是关键**。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的 trade-off:

- **Throughput vs Latency**:批量 vs 响应
- **Fairness vs Performance**:公平 vs 速度
- **Memory vs CPU**:用内存缓存省 CPU

每个调度器(CFS / EEVDF / deadline)都是不同 trade-off。

### 3.4 · 🦀 Rust 生态视角

Rust 的 trade-off:

- **Safe vs Fast**(unsafe)
- **Expressive vs Compile time**(类型系统复杂度)
- **Zero-cost vs Convenience**(高级抽象)

Rust 选 safe + zero-cost,**牺牲了一些 convenience**。

## 附录 II · 工程实用主义

Day 633 的核心是"实用主义"。这是工程师 vs 学者的关键区别。

### 学者 vs 工程师

| | 学者 | 工程师 |
|---|---|---|
| 目标 | 真理 / 完美 | 解决问题 |
| 评估 | 论文质量 | 用户满意度 |
| 时间 | 长(数年) | 短(数周 / 数月) |
| 完美 | 必须 | 不必要 |

学者追求完美,工程师追求"够好"。

### 工程实用主义的 5 原则

#### 1. 80/20 法则

80% 效果来自 20% 投入。先做 20%。

#### 2. KISS(Keep It Simple, Stupid)

简单比复杂好。能用 10 行代码,别用 100 行。

#### 3. YAGNI(You Aren't Gonna Need It)

不为想象中的需求写代码。

#### 4. Done is better than perfect

完成比完美重要。先 ship,后优化。

#### 5. Worst-case thinking

考虑最坏情况,而不是最好。

### 实用主义的代表人物

- **Casey Muratori**(HH):实用主义,够用就行
- **John Carmack**:工程美学,但接受 trade-off
- **Linus Torvalds**:简洁实用,反对过度抽象
- **Bjarne Stroustrup**:C++ 必须"好用",不只是"强大"

每个都是工程师实用主义代表。

### 实用主义的反模式

#### 反模式 1: 过早优化

Knuth 说:"Premature optimization is the root of all evil"。先正确,再优化。

#### 反模式 2: 滥用 KISS

KISS 不等于"懒"。简单不等于简陋。

#### 反模式 3: 反对完美

实用不等于放弃追求。**完美是目标,实用是路径**。

### 平衡:实用 + 完美

好工程师**两者兼顾**:

- 短期:实用方案解决眼前问题
- 长期:朝着完美方向演进

HH 的碰撞:

- Day 632-637:实用 voxel collision
- 未来 Day(如有的话):加真 CCD / 支持斜坡

## 附录 III · 决策记录的"考古学"

Day 633 写的 design doc 是未来"考古"的基础。值得深入理解。

### 为什么写决策记录

新手觉得"我自己记着就行",但:

1. **6 个月后**:你不记得为什么选 X
2. **新成员加入**:不知道历史决策
3. **决策被质疑**:没有依据
4. **类似决策再现**:重复犯错

**决策记录**解决所有这些问题。

### 决策记录的层级

#### Level 1: Commit message

最小粒度。每次 commit 写清楚:

- 什么改动
- 为什么
- 影响

#### Level 2: PR description

中粒度。PR 描述:

- 背景
- 改动
- 测试
- 风险

#### Level 3: Design doc / RFC

大粒度。架构决策:

- Context
- Decision
- Alternatives
- Consequences

#### Level 4: ADR

专门仓库。所有架构决策:

- 编号
- 日期
- 状态(Accepted / Superseded)
- 内容

每层对应不同决策大小。HH 用 Level 1-3,大公司用 Level 4。

### 决策记录的"考古"

未来回顾决策时,问:

1. **当时的 Context 是什么?**(看 Context 章节)
2. **决策基于什么信息?**(看 Alternatives)
3. **现在的 Context 变了吗?**(可能需要新决策)
4. **决策还合理吗?**(可能 Superseded)

**好决策记录**让"考古"容易。**坏决策记录**(只有"决定用 X")让考古困难。

### 决策记录的反模式

#### 反模式 1: 不写

只在脑子里 → 6 个月后忘记。

#### 反模式 2: 写太短

"decided to use voxel"——为什么?alternatives?都没。

#### 反模式 3: 写太长

50 页文档 → 没人读。

#### 反模式 4: 不更新

status 一直 "Accepted",实际已经 Superseded → 误导。

### Casey 的决策记录实践

Casey 每个 Phase 8 day 都有详细 commit:

```
Day 631 - re-examine collision, plan voxel refactoring
Day 632 - experiment with voxel collision MVP
Day 633 - converge on design (epsilon, smaller steps, no slopes)
Day 634 - finalize collision design (本日之后)
```

每个 commit 几百字,讲清楚**为什么 + 怎么做 + 风险**。下一个开发者(或 1 年后的 Casey)看 commit,**立刻理解一切**。

### 工业级决策记录

- **GitHub PR template**:每个 PR 必填"背景 / 改动 / 测试 / 风险"
- **ADR repo**:github.com/.../architecture-decision-records
- **Engineering blog**:公开重要决策 Stripe / Lyft / Cloudflare
- **Internal wiki**:Confluence / Notion

每个都是决策记录的不同形式。

## 附录 IV · "放弃"的智慧

Day 633 决定不支持斜坡——这是**主动放弃**。在工程文化里,"放弃"是智慧。

### 完美主义的陷阱

新手觉得"什么都该支持",否则"不完整"。结果:

- 工作量爆炸,延期
- 复杂度高,bug 多
- 维护成本大
- 用户根本不需要(80/20)

**完美主义是工程师的敌人**。

### "放弃"的勇气

敢于说**"不支持 X"**:

- "我们不支持斜坡"
- "我们不支持 mobile"
- "我们不支持 IE 11"
- "我们不支持 32-bit"

每个"不支持"都是**专注**——把精力投入真正重要的事。

### 著名的"放弃"决策

- **Apple 放弃软驱**(1998 iMac):革命性,业界跟随
- **Slack 放弃 IRC 协议**:做成专有协议,更好体验
- **Tesla 放弃 LIDAR**:纯视觉,争议但坚持
- **HH 放弃斜坡**(本日):简化碰撞,聚焦 dungeon

每个都是"放弃换专注"的案例。

### "放弃"vs"懒惰"

放弃是**深思熟虑后选择**;懒惰是**没想就跳过**。

判断:

- **写 ADR**:trade-off 分析 → 主动放弃
- **不写直接跳过**:懒

Day 633 写 design doc 说明"不支持斜坡"的理由——**主动放弃**,不是懒。

### 用户反馈与放弃

放弃前问:

- 用户真的需要吗?(看数据,不靠猜)
- 没有这个功能用户能活吗?
- 加这个功能值多少工作量?

如果**用户少数需要 + 工作量大**,放弃。

### HH 的"放弃"清单

Casey 在 Phase 8 主动放弃:

每个"放弃"都节省时间,聚焦核心。

## 附录 V · "实用主义" 的边界

Day 633 推崇实用主义,但要警惕**过度实用**。

### 实用主义的 3 个边界

#### 边界 1: 安全

安全相关**不能**实用主义。飞机、医疗、自动驾驶——必须完美主义。

例:Boeing 737 MAX 的 MCAS 系统"实用主义"过度,导致空难。

#### 边界 2: 长期价值

短期"实用"可能牺牲长期:

- 不写测试:短期快,长期 bug 多
- 不重构:短期快,长期维护慢
- 不文档:短期快,长期 onboarding 难

**判断**:用"5 年视角"——这个决策 5 年后还合理吗?

#### 边界 3: 用户体验

"实用主义"不能牺牲核心体验:

- 游戏卡顿 30 FPS → 玩家体验差
- 网站加载 10s → 用户离开
- App 闪退率高 → 用户卸载

**核心体验必须完美主义**。

### 平衡实用 + 完美

好工程师**两者兼顾**:

- **核心**:完美主义(用户体验、安全)
- **边缘**:实用主义(内部工具、不常用功能)

HH 的平衡:

- 碰撞(核心体验):用实用方案,但**保证手感**
- 渲染(核心体验):用 PBR(物理正确)
- 内部工具(编辑器):实用主义
- 测试覆盖:核心功能必测,边缘功能 smoke test

### 实用主义失败的案例

- **Theranos**:为了"实用"省去严格医学验证,导致丑闻
- **波音 737 MAX**:为了"实用"省去飞行员培训,导致空难
- **HH 假设场景**:如果碰撞"实用主义"导致游戏不可玩,就是失败

每个失败都是"实用主义过度"。

### 实用主义的"指导问题"

每次想"实用主义",问:

1. **这是核心还是边缘?**
   - 核心:慎用实用主义
   - 边缘:放心用

2. **失败的成本多大?**
   - 小:实用主义
   - 大(钱 / 生命):完美主义

3. **能迭代修复吗?**
   - 能:实用主义(先 ship 再修)
   - 不能(已发布的硬件):完美主义

### HH 的判断

HH 碰撞是"游戏感"——重要但不是"生死"。

- 玩家可能偶尔穿墙 → 接受(实用主义)
- 玩家碰撞导致闪退 → 不可接受(完美主义)
- 玩家碰撞数据 corrupt → 不可接受(完美主义)

**核心:用户体验必须保证,内部细节可以实用**。
