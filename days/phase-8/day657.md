## 2 · 心智模型

### 类比:工厂流水线升级

老工厂:工人直接装产品(直接改 vel)。
新工厂:工人把零件放传送带,机器自动装(队列 + processor)。

升级时不能停工——边运行边换。Casey 用**渐进式迁移**:先加新系统(MoveQueue),不动老代码,逐个 case 迁移,最后删老代码。

### Entity 结构演化

```rust
// 老版本
struct Entity {
    pos: Vec3,
    vel: Vec3,
    // ...
}

// 新版本
struct Entity {
    pos: Vec3,
    vel: Vec3,  // 保留:由队列驱动

```

`vel` 字段保留,但**外部不再直接写**——只有队列处理器写。这避免"老代码绕过队列"的 bug。

### 玩家输入的迁移

老代码:

```rust
fn handle_player_input(player: &mut Entity, input: &Input) {
    if input.held(KeyW) { player.vel.z = 1.0; }
    if input.held(KeyS) { player.vel.z = -1.0; }
    if input.pressed(KeySpace) { player.vel.y = 5.0; }
}
```

新代码:

```rust
fn handle_player_input(player: &mut Entity, input: &Input) {
    let mut vel = Vec3::ZERO;
    if input.held(KeyW) { vel.z = 1.0; }
    if input.held(KeyS) { vel.z = -1.0; }
    player.move_queue.push_back(MoveRequest::Walk { vel, duration: 0.0 });
    // duration = 0 表示瞬时,update 返回 true,pop

    if input.pressed(KeySpace) {
        player.move_queue.push_back(MoveRequest::Force {
            accel: Vec3::new(0.0, 50.0, 0.0),
            duration: 0.1,  // 100ms 跳跃力
        });
    }
}
```

注意:Walk 的 duration = 0 表示"瞬时"——这一帧应用 vel,立刻 pop,下一帧 player.vel 仍是这个值(直到新请求覆盖)。这是 hack,但工作。

更干净的设计:Walk 请求**覆盖** vel 字段,pop 后 vel 不变,直到下一个 Walk 请求覆盖。

### AI 巡逻的迁移

老代码(每帧朝目标):

```rust
fn update_npc(npc: &mut Entity, target: Vec3) {
    let dir = target - npc.pos;
    npc.vel = dir.normalize() * NPC_SPEED;
}
```

问题:NPC 一直在追目标,绕圈子。

新代码(预设路径):

```rust
fn setup_patrol(npc: &mut Entity, path: &[Vec3]) {
    for window in path.windows(2) {
        let from = window[0];
        let to = window[1];
        let dir = to - from;
        let distance = dir.length();
        let vel = dir / distance * NPC_SPEED;
        let duration = distance / NPC_SPEED;
        npc.move_queue.push_back(MoveRequest::Walk { vel, duration });
    }
    // 可选:循环(在最后 push 一段从 path 最后回 path[0])
}
```

NPC 按预设路径走,不受玩家位置干扰。如果玩家攻击 NPC,interrupt 清空队列,加 Knockback。

### 队列消费顺序

每帧的 update:

1. handle_input:把玩家输入 push 到玩家队列
2. AI:根据状态 push 到 NPC 队列(如果队列空)
3. physics_step:消费所有实体的队列,更新 pos / vel
4. collide:每个实体在新位置做碰撞

队列处理在物理之前,确保物理看到的是"这一帧应该是什么 vel"。

### 队列空时

队列空时 update 啥也不做,vel 不变。玩家松开所有键,vel 仍然是上一次的值——但每帧物理摩擦力衰减,逐渐停下。

如果队列空 + 摩擦力,玩家自然停下,不需要显式"零速"请求。

## 3 · 四域深入

### 3.1 · 游戏编程视角

队列集成的常见陷阱:

- **double update**:同一帧 push 同一请求两次,vel 变 2 倍——用 set 而非 push,或每帧 clear 后 push
- **race condition**:多线程时,producer/consumer 同步
- **queue bloat**:某些代码持续 push,队列爆炸——加 max_size 或 trim
- **ordering**:玩家 push + AI push,顺序错乱——明确"玩家优先"或"AI 优先"

### 3.2 · 图形学视角

类似集成:render graph 替代 immediate draw。先把所有 draw call 录到 graph,引擎优化排序,再 submit。

### 3.3 · Linux 系统编程视角

类似集成:Linux kernel io_uring 替代 read/write syscall。先录命令到 ring buffer,内核异步消费。

io_uring 是 Casey 队列思想的系统级实现。

### 3.4 · Rust 生态视角

Rust 里 Entity 设计模式:

```rust
struct Entity {
    pos: Vec3,
    vel: Vec3,
    move_queue: MoveQueue,
}

impl Entity {
    fn update(&mut self, dt: f32) {
        self.move_queue.process(self, dt);
    }
}

impl MoveQueue {
    fn process(&mut self, entity: &mut Entity, dt: f32) {
        // 注意:entity 包含 self,需要 split
        // 用 while let + 单独 apply 函数避免 borrow 问题
        while let Some(req) = self.queue.front_mut() {
            req.apply(entity, dt);
            if req.update(dt) {
                self.queue.pop_front();
            } else {
                break;
            }
        }
    }
}
```

Rust borrow checker 在"持有 self.queue 的同时修改 entity.pos"时会报错。解法:**MoveQueue 不持有 Entity 引用**,而是被 Entity 调用,传 &mut Entity 作参数。这就是上面写法。

```rust
use glam::Vec3;
use std::collections::VecDeque;

#[derive(Clone, Debug)]
enum MoveRequest {
    Walk { vel: Vec3, duration: f32 },
    Force { accel: Vec3, duration: f32 },
}

impl MoveRequest {
    fn apply(&self, e: &mut Entity, dt: f32) {
        match self {
            MoveRequest::Walk { vel, .. } => { e.vel = *vel; }
            MoveRequest::Force { accel, .. } => { e.vel += *accel * dt; }
        }
    }
    fn update(&mut self, dt: f32) -> bool {
        match self {
            MoveRequest::Walk { duration, .. } | MoveRequest::Force { duration, .. } => {
                *duration -= dt;
                *duration <= 0.0
            }
        }
    }
}

struct MoveQueue { items: VecDeque<MoveRequest> }
impl MoveQueue {
    fn new() -> Self { Self { items: VecDeque::new() } }
    fn push(&mut self, r: MoveRequest) { self.items.push_back(r); }
    fn process(&mut self, entity: &mut Entity, dt: f32) {
        while let Some(req) = self.items.front_mut() {
            req.apply(entity, dt);
            if req.update(dt) { self.items.pop_front(); }
            else { break; }
        }
    }
}

struct Entity {
    pos: Vec3,
    vel: Vec3,
    queue: MoveQueue,
}

impl Entity {
    fn new() -> Self { Self { pos: Vec3::ZERO, vel: Vec3::ZERO, queue: MoveQueue::new() } }
    fn update(&mut self, dt: f32) {
        self.queue.process(self, dt);
        self.pos += self.vel * dt;
    }
}

struct Input { w: bool, s: bool, space: bool }

fn handle_input(e: &mut Entity, input: &Input) {
    let mut vel = Vec3::ZERO;
    if input.w { vel.z = 1.0; }
    if input.s { vel.z = -1.0; }
    e.queue.push(MoveRequest::Walk { vel, duration: 0.0 });
    if input.space {
        e.queue.push(MoveRequest::Force {
            accel: Vec3::new(0.0, 50.0, 0.0),
            duration: 0.1,
        });
    }
}

fn main() {
    let mut player = Entity::new();
    for _ in 0..60 {
        handle_input(&mut player, &Input { w: true, s: false, space: false });
        player.update(1.0 / 60.0);
    }
    println!("After 1s walk forward: pos={:?}, vel={:?}", player.pos, player.vel);

    let mut npc = Entity::new();
    npc.pos = Vec3::ZERO;
    let path = vec![
        Vec3::new(0.0, 0.0, 0.0),
        Vec3::new(0.0, 0.0, 5.0),
        Vec3::new(5.0, 0.0, 5.0),
    ];
    for w in path.windows(2) {
        let dir = w[1] - w[0];
        let dist = dir.length();
        let vel = dir / dist * 2.0; // 速度 2 m/s
        let duration = dist / 2.0;
        npc.queue.push(MoveRequest::Walk { vel, duration });
    }
    for frame in 0..300 {
        npc.update(1.0 / 60.0);
    }
    println!("NPC after patrol: pos={:?}", npc.pos);
    // 应该在 (5, 0, 5) 附近
}
```

```rust
// Cargo.toml:
// [dependencies]
// glam = "0.29"

use glam::Vec3;
use std::collections::VecDeque;

#[derive(Clone, Debug)]
enum MoveRequest {
    Walk { vel: Vec3, duration: f32 },
    Dash { dir: Vec3, distance: f32 },
    Force { accel: Vec3, duration: f32 },
    Wait { duration: f32 },
}

impl MoveRequest {
    fn apply(&self, e: &mut Entity, dt: f32) {
        match self {
            MoveRequest::Walk { vel, .. } => { e.vel = *vel; }
            MoveRequest::Dash { dir, distance } => {
                e.pos += dir.normalize_or_zero() * distance;
                e.vel = Vec3::ZERO;
            }
            MoveRequest::Force { accel, .. } => { e.vel += *accel * dt; }
            MoveRequest::Wait { .. } => {}
        }
    }
    fn tick(&mut self, dt: f32) -> bool {
        match self {
            MoveRequest::Walk { duration, .. }
            | MoveRequest::Force { duration, .. }
            | MoveRequest::Wait { duration } => {
                *duration -= dt;
                *duration <= 0.0
            }
            MoveRequest::Dash { .. } => true,
        }
    }
}

struct MoveQueue { items: VecDeque<MoveRequest> }
impl MoveQueue {
    fn new() -> Self { Self { items: VecDeque::new() } }
    fn push(&mut self, r: MoveRequest) { self.items.push_back(r); }
    fn clear(&mut self) { self.items.clear(); }
    fn process(&mut self, e: &mut Entity, dt: f32) {
        let mut iter = 0;
        while iter < 32 {
            iter += 1;
            let Some(req) = self.items.front_mut() else { break; };
            req.apply(e, dt);
            if req.tick(dt) {
                self.items.pop_front();
            } else {
                break;
            }
        }
    }
}

struct Entity {
    name: &'static str,
    pos: Vec3,
    vel: Vec3,
    queue: MoveQueue,
}

impl Entity {
    fn new(name: &'static str) -> Self {
        Self { name, pos: Vec3::ZERO, vel: Vec3::ZERO, queue: MoveQueue::new() }
    }
    fn update(&mut self, dt: f32) {
        self.queue.process(self, dt);
        self.pos += self.vel * dt;
        // 摩擦
        self.vel.x *= 0.95;
        self.vel.z *= 0.95;
    }
}

fn main() {
    let mut player = Entity::new("player");

    // 走 1 秒
    for _ in 0..60 {
        player.queue.push(MoveRequest::Walk {
            vel: Vec3::new(1.0, 0.0, 0.0),
            duration: 0.0,
        });
        player.update(1.0 / 60.0);
    }
    println!("After 1s walk: pos={:?}, vel={:?}", player.pos, player.vel);

    // Dash
    player.queue.push(MoveRequest::Dash {
        dir: Vec3::new(1.0, 0.0, 0.0),
        distance: 3.0,
    });
    player.update(1.0 / 60.0);
    println!("After dash:    pos={:?}", player.pos);

    // 跳跃
    player.queue.push(MoveRequest::Force {
        accel: Vec3::new(0.0, 50.0, 0.0),
        duration: 0.1,
    });
    for _ in 0..120 {
        // 重力(每帧)
        player.queue.push(MoveRequest::Force {
            accel: Vec3::new(0.0, -9.81, 0.0),
            duration: 1.0 / 60.0,
        });
        player.update(1.0 / 60.0);
    }
    println!("After jump:    pos={:?}, vel={:?}", player.pos, player.vel);

    // AI 巡逻 NPC
    let mut npc = Entity::new("npc");
    let path: Vec<Vec3> = vec![
        Vec3::new(0.0, 0.0, 0.0),
        Vec3::new(0.0, 0.0, 10.0),
        Vec3::new(10.0, 0.0, 10.0),
        Vec3::new(10.0, 0.0, 0.0),
    ];
    for w in path.windows(2) {
        let dir = w[1] - w[0];
        let dist = dir.length();
        let vel = dir / dist * 2.0;
        let dur = dist / 2.0;
        npc.queue.push(MoveRequest::Walk { vel, duration: dur });
    }
    let initial_pos = npc.pos;
    for _ in 0..600 { // 10 秒
        npc.update(1.0 / 60.0);
    }
    println!("NPC: initial={:?}, after patrol={:?}", initial_pos, npc.pos);
    // 应该回到起点附近(假设巡逻结束)

    // 中断
    npc.queue.clear();
    npc.queue.push(MoveRequest::Force {
        accel: Vec3::new(0.0, 0.0, 100.0),
        duration: 0.1,
    });
    npc.update(1.0 / 60.0);
    println!("NPC after knockback: vel={:?}", npc.vel);
}
```

## 10 · 工程反思

Day 657 传达的核心工程教训:**input handling 是体验的基石**。

新手以为"input = 读键盘",资深工程师知道 input 涉及**捕获 / 路由 / 缓冲 / 反馈**多个阶段。每个阶段都影响体验:

- **捕获**:键盘 / 鼠标 / 手柄 / 触屏 / 体感,各不同
- **路由**:input 发给哪个 UI / 玩家 / NPC?
- **缓冲**:玩家按键到响应,中间几帧 buffer
- **反馈**:视觉 / 听觉 / 触觉响应

每阶段都重要。比如"按下立刻响应"和"按下 100ms 后响应",玩家感受天差地别——这就是 input lag。资深游戏程序员把 input lag 视为关键性能指标。

**为什么 input 这么重要?**

因为 input 是**玩家和游戏的唯一接口**。其他系统(渲染、AI、物理)出 bug,玩家"看到怪现象";input 出 bug,玩家"无法玩"。所以工业级 input 系统格外小心。

**Input 概念**:

- **Polling**(轮询):每帧查"现在按住没"。适合连续动作(移动)
- **Event**(事件):按下 / 抬起触发回调。适合离散动作(跳跃)
- **Buffer**(缓冲):按下后 N 帧内仍生效。适合"玩家提前按"
- **Queued**(队列):多个 input 排队处理。适合格斗游戏连招

每种机制有自己的 use case。Casey 在 HH 演示最简单的 polling。

**第二条教训**:**多平台 input 是地狱**。

PC(键盘鼠标)+ 主机(手柄)+ 手机(触屏)+ VR(体感),每种平台 input 不同。Unity / Unreal 用抽象层(Input System / Enhanced Input)处理。但每个游戏仍要调参——手柄 deadzone、触屏 swipe 阈值、VR 手势识别。

资深游戏程序员的 ability:**跨平台 input 协调**。这个能力稀缺,薪资高。

**第三条教训**:**input recording 是 QA 工具**。

工业 QA(Quality Assurance)团队用 input recording 测试:

- 录制"通关一遍"的 input
- 每次发版前 replay,确认能通关
- 不同 input 录制对应不同测试场景

这是 regression testing 的游戏版本。Casey 在 HH Day 638 的录制器扩展就能做这个。

**迁移到其他领域**:

"input 处理"思路在多处通用:

- **Web**:DOM event / React synthetic event
- **Mobile**:touch event / gesture recognizer
- **CLI**:stdin / argparse
- **VR/AR**:hand tracking / eye tracking
- **Accessibility**:screen reader / voice control

每个领域都有"用户输入"处理。Casey 在 HH 演示的是游戏版本,但思路普适。

```rust
}
```

抽象不同手柄(Xbox / PS / Switch / Generic),统一 API。

**Touch input**:

- 单点触控:position + phase(began / moved / ended)
- 多点触控:多个 finger 独立追踪
- Gesture:swipe / pinch / rotate(高层抽象)

iOS / Android 各有自己的 API,Rust 用 `winit` 的 touch event 抽象。

**VR input**:

- 6DoF 手柄(position + rotation)
- 手势识别(pinch / fist / open)
- 眼动追踪(eye gaze)

每个平台都有特殊 input 模式。Casey 在 HH 只用键盘鼠标,工业级要支持全部。

## 12 · Input accessibility

游戏 input 的 accessibility:

**1. 可重映射**:

- 玩家自定义按键
- 不同能力玩家适配

**2. Hold vs Toggle**:

- 持续按 vs 按一次切换
- 行动不便玩家友好

**3. Aim assist**:

- 手柄玩家自动瞄准
- 视觉障碍玩家辅助

工业级游戏都有 accessibility 选项。这是资深工程师的 polish 细节。

## N0 • 深度教学补充

### 核心概念重新梳理

Day 657 涉及的核心概念需要在多个层次上理解:

**第一层:直观理解**

新手第一次接触概念,需要建立直觉。例如 voxel collision 是"虚拟物体不能穿过虚拟墙"——这个直觉每个人都能从现实经验获得。

**第二层:数学理解**

把直觉形式化。collision = "两个几何体的体积有交集"。对于 AABB,这等价于"三轴投影都重叠"。

**第三层:工程理解**

数学正确不等于工程实现正确。要考虑:

- 浮点精度边界
- 性能(每帧 N 个查询)
- 内存(数据结构紧凑)
- 边角 case(无穷大、NaN、负数)

**第四层:工业理解**

工业级要再加:

- 多线程安全
- SIMD 优化
- 网络同步(多人游戏)
- 跨平台(Windows/Mac/Linux/Mobile)
- 可访问性(色盲友好)
- 反作弊

每层理解都让代码更鲁棒。资深工程师在所有层次同时思考。

### 实际工程的细节

工业代码 80% 是"边角 case 处理",20% 是"核心算法"。Casey 在 HH 演示核心,工业代码加大量边角处理。

**边角 case 类型**:

1. 空输入(空 Vec、null pointer)
2. 极端输入(NaN、无穷大、超大数)
3. 并发竞争(多线程同时访问)
4. 资源不足(内存满、磁盘满)
5. 网络异常(超时、断连、包丢失)
6. 版本不兼容(老配置 / 新代码)
7. 权限错误(只读文件、无网络)
8. 用户误操作(连点、撤销重做)

每个 case 都要单独处理。这是工业代码 50%+ 行数的原因。

### 优化思路

性能优化有顺序:

1. **算法**:O(N²) → O(N log N),最大提升
2. **数据结构**:Vec → HashMap / BTreeMap,常数提升
3. **Cache**:AoS → SoA,cache 命中提升
4. **SIMD**:4-16 元素并行,巨大常数提升
5. **GPU**:数千核并行,极致性能
6. **分布式**:多机器,无限扩展

每级提升都需要更复杂的代码。先优化低级,够用再升级。
