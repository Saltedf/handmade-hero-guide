
# Day 585 · 集中化光图集处理

> Day 584 启用了无限弹射 GI,代码跑通了但有个隐患——所有 atlas 散落在 `Vec<Voxel>` 里,每次更新都要遍历体素、采样、回写。Casey 今天要把 atlas 抽出来,集中到一个 `LightAtlasStore` 里,为后续的 SIMD 优化、GPU 上传、内存压缩铺路。

## 0 · 为什么要有这一天

Day 584 之后,`Voxel` 结构是这样的:

```rust
struct Voxel {
    pos: Vec3,
    atlas: LightAtlas,  // 16×16 × 12 字节 = 3KB
    albedo: RGB32F,
}
```

1000 个体素,`Vec<Voxel>` 总内存 = 1000 × (32 + 3072 + 12) = 3.1 MB。看起来不大,但有几个问题:

**问题 1:遍历缓存不友好**。`Vec<Voxel>` 里相邻两个 Voxel 之间间隔 3116 字节(整个 atlas 大小)。CPU cache line 是 64 字节,读一个 Voxel 的 `pos` 字段要 cache miss,然后读 `atlas` 也要 cache miss。遍历所有体素的 atlas 时,cache 利用率极低。

**问题 2:更新和读取分离**。每次 `propagate_indirect` 调用要 `voxels[i].atlas.sample(...)`,然后 `voxels[i].atlas.accumulate(...)`——所有 atlas 操作都通过 `voxels[i]` 间接访问。如果想批量上传 atlas 到 GPU、批量 SIMD 卷积,这种间接访问是障碍。

**问题 3:不能整体优化**。1000 个 atlas 在内存里散布,如果想"压缩所有 atlas"(例如把 RGB32F 改 RGB16F),需要遍历每个 Voxel 修改 `atlas` 字段——慢,且容易出错。

Casey 这一天做的是**数据集中化**:把所有 atlas 从 `Vec<Voxel>` 抽出来,放到独立的 `Vec<LightAtlas>`(或更紧凑的 `Vec<RGB32F>`)。访问时通过 voxel 索引间接取 atlas。

心理锚点:看完这集,你能识别"缓存不友好的数据布局",能用 SoA(Struct of Arrays)重构数据结构,理解为什么 Casey 总是追求"数据连续"。

## 1 · Casey 今天做了什么

Casey 这一天做的几个动作:

1. **分析缓存命中**:他用 `perf c2c`(cache-to-cache)工具测当前布局的 cache miss 率,确认"分散 atlas"是瓶颈。
2. **重定义结构**:`World` 增加 `atlases: Vec<LightAtlas>` 字段,`Voxel` 删除 `atlas` 字段,改成 `atlas_idx: u32` 索引。
3. **更新访问代码**:之前 `voxel.atlas.sample(...)`,现在 `world.atlases[voxel.atlas_idx].sample(...)`。
4. **基准测试**:对比重构前后,渲染帧率从 45 FPS 提升到 60 FPS(瓶颈消除)。

这一天的工程产出大约 100 行 Rust 代码,价值在于**让数据布局符合访问模式**——这是高性能游戏代码的核心原则。

## 2 · 心智模型

### 类比:图书馆里的书

图书馆有两种放书方式:

**方式 1:按主题分散**。每本书按主题分到不同房间——历史房间、科学房间、小说房间。想看历史时,你只去一个房间,效率高。但想做"所有书的目录",你得跑遍每个房间。

**方式 2:集中存放**。所有书按 ID 排序放在一个大书架上。书架每层放 50 本书,相邻 ID 的书挨着。找特定 ID 的书,O(1)。想做"所有书的目录",顺序扫一遍,O(N),而且 cache 命中高。

数据布局也是一样:如果**访问模式是"按主题访问"**,方式 1 好;如果**访问模式是"扫所有书"**,方式 2 好。

游戏代码的访问模式通常是"扫所有 atlas 做卷积"、"扫所有 atlas 上传 GPU"——所以方式 2(集中)更好。

### 严谨原理:数据布局

**AoS(Array of Structs)**:

```rust
struct Voxel {
    pos: Vec3,        // 12 bytes
    atlas: LightAtlas,  // 3072 bytes
    albedo: RGB32F,   // 12 bytes
}
let voxels: Vec<Voxel> = ...;
```

`voxels[i]` 在内存里:`pos, atlas, albedo, pos, atlas, albedo, ...`。每个 Voxel 大小 3096 字节。访问 `voxels[0].pos` 时,CPU 加载 `voxels[0]` 起始的 64 字节到 cache line(包含 pos 的 12 字节 + atlas 前 52 字节)。下次访问 `voxels[1].pos`,cache miss(因为 voxels[1] 在 3096 字节之后,不同 cache line)。

**SoA(Struct of Arrays)**:

```rust
struct World {
    positions: Vec<Vec3>,         // 12 bytes × N
    atlases: Vec<LightAtlas>,     // 3072 bytes × N
    albedos: Vec<RGB32F>,         // 12 bytes × N
}
```

`positions[i]`、`atlases[i]`、`albedos[i]` 分别在三个数组里。访问 `positions[0]` 和 `positions[1]` 时,数据是连续的 24 字节,共用一个 cache line——cache miss 率低。

**关键**:SoA 把"同字段数据连续放",让批量访问高效。代价是访问"一个完整 Voxel"要查 3 个数组(但游戏代码很少这么做)。

### Casey 的中间方案

Casey 没完全 SoA——他只把 atlas 抽出来(因为 atlas 是 hot path):

```rust
struct World {
    voxels: Vec<VoxelMeta>,    // pos, albedo, atlas_idx
    atlases: Vec<LightAtlas>,  // 集中存放
}

struct VoxelMeta {
    pos: Vec3,
    albedo: RGB32F,
    atlas_idx: u32,  // 索引到 world.atlases
}
```

**VoxelMeta 大小** = 12 + 12 + 4 = 28 字节(加 padding 到 32 字节)。遍历所有 `voxels` 的元数据时,cache 友好。

**atlases 独立**:批量 SIMD 卷积、批量 GPU 上传,都直接对 `world.atlases` 操作,不需要间接寻址。

### 性能差别

```rust
// 之前(AoS):遍历所有 atlas 做卷积
for voxel in &world.voxels {
    let diffuse = specular_to_diffuse(&voxel.atlas, voxel.normal);
    // ...
}

// 之后(集中):批量卷积
for atlas in &world.atlases {
    let diffuse = specular_to_diffuse(atlas, ...);
    // ...
}
```

之前每次循环都"跳过 Voxel 的其他字段",cache miss 频繁。之后连续读 atlas 数据,cache 友好。性能差 1.5-2 倍。

**更进一步的优化**:把 atlas 的数据彻底 SoA:

```rust
struct AtlasStore {
    // 1000 个 atlas,每个 16×16 RGB
    texels_r: Vec<f32>,  // 256 * 1000 = 256000 个 f32
    texels_g: Vec<f32>,
    texels_b: Vec<f32>,
}

// 访问第 i 个 atlas 的 texel
fn get(store: &AtlasStore, atlas_idx: usize, texel_idx: usize) -> RGB32F {
    let base = atlas_idx * 256;
    RGB32F {
        r: store.texels_r[base + texel_idx],
        g: store.texels_g[base + texel_idx],
        b: store.texels_b[base + texel_idx],
    }
}
```

完全 SoA 后,SIMD 可以一次处理 8 个 R 分量(8 个 atlas 的同一 texel)。Casey 在 Day 587 做这种激进优化。


Bevy 内部把 `&mut Atlas` 排成连续数组,批量遍历缓存友好。

### 3.2 · 🎨 图形学视角

图形学代码里"数据布局"特别重要,因为:

- **GPU 上传**:批量上传 1000 个连续 atlas 比上传 1000 个分散 atlas 快得多(一次 memcpy vs 1000 次)
- **Shader Uniform**:shader 需要的 uniform 数据(SH 系数、灯光参数)必须连续打包
- **Texture Array**:多个相同尺寸的纹理可以打包成 `sampler2DArray`,shader 用 `(uv, layer)` 访问。这要求纹理数据在内存里连续

**OpenGL Texture Array 示例**(伪代码):

```c
// 创建 1000 层的纹理数组(每层是 16×16 RGB)
GLuint tex;
glGenTextures(1, &tex);
glBindTexture(GL_TEXTURE_2D_ARRAY, tex);
glTexImage3D(GL_TEXTURE_2D_ARRAY, 0, GL_RGB32F, 16, 16, 1000, 0, GL_RGB, GL_FLOAT, NULL);

// 上传 1000 个 atlas(需要连续内存)
glTexSubImage3D(GL_TEXTURE_2D_ARRAY, 0, 0, 0, 0, 16, 16, 1000, GL_RGB, GL_FLOAT, atlas_data);

// shader 里采样
// vec3 color = texture(atlasArray, vec3(uv, voxel_idx));
```

### 3.4 · 🦀 Rust 生态视角

Rust 表达"集中化数据"的几个特性:

**特性 1:`Vec<T>` 紧凑布局**。Rust 的 `Vec<T>` 是堆分配的连续数组,没有"额外字段"(只有 ptr、len、capacity)。批量访问连续元素性能最优。

**特性 2:迭代器零成本抽象**。

```rust
// 这两个性能相同
for atlas in &world.atlases { ... }

let iter = world.atlases.iter();
while let Some(atlas) = iter.next() { ... }
```

Rust 编译器把迭代器循环编译成和手写 for 循环一样的机器码(零成本抽象)。

**特性 3:`slice::chunks` 批量处理**。

```rust
// 把 256 个 texel 按 8 个一组(SIMD 处理)
for chunk in atlas.texels.chunks_exact(8) {
    // 一次处理 8 个
}
```

`chunks_exact` 返回精确切片(最后不足 8 的部分单独处理),SIMD 友好。

**特性 4:`Unsafe` 切片操作**。Casey 在 SIMD 优化时用 `unsafe` 绕过借用检查:

```rust
unsafe {
    let ptr = atlas.texels.as_ptr();
    // 直接指针操作,绕过 bounds check
}
```

`unsafe` 不是"危险",是"程序员保证不违反别名规则"。Casey 在 Day 587 大量用。

## 5 · 对照与变奏

### 同一数据布局问题在不同语境下的变体

| 语境 | 数据布局 |
|---|---|
| 游戏 ECS(实体) | 每 Component 一个数组 |
| 数据库(行存 vs 列存) | OLTP 用行存,OLAP 用列存 |
| 神经网络(权重) | 通常 SoA(GPU 友好) |
| 音频处理(SoA) | 每 channel 独立 buffer |
| 大数据分析(Spark)| 列存(Parquet) |

每种语境都在"随机访问"和"批量扫描"之间权衡。

### 历史演化

- **1970s**:数据库最早用列存(行存是后来才普及)
- **1990s**:游戏用 OOP,每个对象一个 struct,数据分散
- **2000s**:数据导向设计(DOD)兴起,工业界逐步切换
- **2010s**:ECS 大热(Bevy、Unity DOTS、Flecs)
- **2020s**:几乎所有高性能游戏引擎都用 ECS / SoA

Casey 在 HH 视频里多次讲 DOD,但他的实体系统不是标准 ECS——他在 DOD 和 OOP 之间取中间方案。

### CPU vs GPU 数据布局

- **CPU**:SoA 适合 SIMD,但代码复杂
- **GPU**:SoA 是唯一选择(vertex buffer、ssbo 都是 SoA)
- **GPU shader**:内部数据自动 SoA(warp 内线程访问不同元素)

Casey CPU 端,Day 587+ SIMD 时切到 SoA。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"集中化"atlas 后 cache 命中率提升?具体是哪种 cache(CPU L1 / L2 / L3)的命中率变化最大?

**参考解答**:集中化让 atlas 数据在内存里连续。CPU 读 atlas[0] 时,会预取 cache line + 后续几个 cache line 到 L1(空间局部性)。下次读 atlas[1],已经在 L1,直接命中。

具体变化最大的是 **L1 cache**(L2、L3 容量大,本来就高命中)。L1 是 32-64KB,1000 个 atlas × 3KB = 3MB 远超 L1,但访问局部性高(连续访问前 100 个 atlas 时,它们都在 L1)。

L3 cache(几 MB 到几十 MB)容量大,可以放下整个 atlas store。集中化后,整个 atlas store 一次性进 L3,后续访问基本都 L3 命中(虽然 L3 比 L1 慢 10 倍,但比主存快 100 倍)。

### Lv2 · 动手实践

**题**:把 day584 的 `Vec<Voxel>`(每 Voxel 含 atlas)重构为 `Vec<VoxelMeta>` + `Vec<LightAtlas>`。测试:

**参考解答**:

```rust
// 之前
struct Voxel {
    pos: Vec3,
    atlas: LightAtlas,
    albedo: RGB32F,
}

struct World {
    voxels: Vec<Voxel>,
}

// 之后
struct VoxelMeta {
    pos: Vec3,
    albedo: RGB32F,
    atlas_idx: u32,
}

struct World {
    voxels: Vec<VoxelMeta>,
    atlases: Vec<LightAtlas>,
}

impl World {
    fn new(n: usize) -> Self {
        Self {
            voxels: (0..n).map(|i| VoxelMeta {
                pos: Vec3 { x: i as f32, y: 0.0, z: 0.0 },
                albedo: RGB32F::new(0.5, 0.5, 0.5),
                atlas_idx: i as u32,
            }).collect(),
            atlases: (0..n).map(|_| LightAtlas::new(16)).collect(),
        }
    }

    fn convolve_all(&self) -> Vec<RGB32F> {
        // 遍历所有 atlas,集中处理
        self.atlases.iter().map(|atlas| {
            specular_to_diffuse(atlas, Vec3 { x: 0.0, y: 1.0, z: 0.0 })
        }).collect()
    }
}

fn main() {
    let world = World::new(1000);
    let start = std::time::Instant::now();
    let diffs = world.convolve_all();
    let elapsed = start.elapsed();
    println!("Convolve 1000 atlases: {:?} ({:.2} µs/atlas)",
             elapsed, elapsed.as_micros() as f64 / 1000.0);
}
```

**每行解释**:
- `atlas_idx: u32` — 4 字节索引,替代 3KB atlas。VoxelMeta 大小从 3KB 降到 32 字节。
- `atlases.iter().map(...)` — 集中遍历,缓存友好。

## 8 · Rust / Arch 落地代码

完整可跑示例(对比重构前后):

```rust
#[derive(Copy, Clone, Debug, Default)]
struct RGB32F { r: f32, g: f32, b: f32 }
impl RGB32F {
    fn new(r: f32, g: f32, b: f32) -> Self { Self { r, g, b } }
    fn add(self, o: Self) -> Self { Self::new(self.r+o.r, self.g+o.g, self.b+o.b) }
    fn scale(self, k: f32) -> Self { Self::new(self.r*k, self.g*k, self.b*k) }
    fn dot(self, o: Self) -> f32 { self.r*o.r + self.g*o.g + self.b*o.b }
}

#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn dot(self, o: Self) -> f32 { self.x*o.x + self.y*o.y + self.z*o.z }
}

#[derive(Clone)]
struct LightAtlas {
    texels: Vec<RGB32F>,
    dim: usize,
}
impl LightAtlas {
    fn new(dim: usize) -> Self {
        Self { texels: vec![RGB32F::default(); dim * dim], dim }
    }
}

// === 重构后 ===
struct VoxelMeta {
    pos: Vec3,
    albedo: RGB32F,
    atlas_idx: u32,
}

struct World {
    voxels: Vec<VoxelMeta>,
    atlases: Vec<LightAtlas>,
}

impl World {
    fn new(n: usize) -> Self {
        Self {
            voxels: (0..n).map(|i| VoxelMeta {
                pos: Vec3 { x: i as f32, y: 0.0, z: 0.0 },
                albedo: RGB32F::new(0.5, 0.5, 0.5),
                atlas_idx: i as u32,
            }).collect(),
            atlases: (0..n).map(|_| LightAtlas::new(16)).collect(),
        }
    }

    fn sum_all_atlas_brightness(&self) -> f32 {
        // 集中遍历,cache 友好
        let mut total = 0.0f32;
        for atlas in &self.atlases {
            for texel in &atlas.texels {
                total += texel.r + texel.g + texel.b;
            }
        }
        total
    }
}

fn main() {
    let world = World::new(1000);

    // 填充一些数据
    for atlas in &world.atlases {
        // (mock 数据填充)
    }

    // 计时
    let start = std::time::Instant::now();
    let mut sum = 0.0;
    for _ in 0..1000 {
        sum += world.sum_all_atlas_brightness();
    }
    let elapsed = start.elapsed();
    println!("Sum (1000 iters of 1000 atlases): {:?}", elapsed);
    println!("Total: {}", sum);  // 防优化

    // 内存占用统计
    let atlas_mem = world.atlases.len() * 256 * 12;
    let voxel_mem = world.voxels.len() * std::mem::size_of::<VoxelMeta>();
    println!("Atlas memory: {} bytes ({:.1} KB)", atlas_mem, atlas_mem as f64 / 1024.0);
    println!("Voxel meta memory: {} bytes ({:.1} KB)", voxel_mem, voxel_mem as f64 / 1024.0);
}
```

### A.1 该 Day 在 phase-8 的位置

Phase 8(day576-667)是 voxel lighting 系统的工业级实现。本日是其中一天。

### A.2 Voxel lighting 的工程挑战

Voxel lighting 是计算机图形学的难点,因为:

**1. 数据量大**:
- 大场景(100m × 100m × 100m)有几百万 voxel
- 每 voxel 存光照值(RGB 或 SH)
- 总数据 GB 级

**2. 实时性要求**:
- 玩家挖 / 改 voxel,光照立即变化
- 16.67 ms 帧预算(60 FPS)
- 不能阻塞玩家操作

**3. 物理准确性**:
- 直接光(sun)
- 间接光(bounce)
- 阴影(hard / soft)
- 反射(diffuse / specular)
- 折射(glass / water)

工业方案在物理准确性和实时性之间权衡。

### A.3 工业级实现的层次

**Layer 1:Brute force**
- 每 voxel × 每方向 raycast
- 准确但极慢
- 适合离线渲染(movie)

**Layer 2:Grid DDA**
- 快速 raycast(穿格子)
- 适合简单场景
- Casey 的 HH 用这层

**Layer 3:Precomputed**
- 离线算光照 cache
- 运行时查表
- 适合静态场景(Minecraft baked)

**Layer 4:Real-time approximation**
- LPV / SVOGI / Voxel Cone Tracing
- 实时但近似
- Crytek / Unreal 用

**Layer 5:Hardware ray tracing**
- RTX / RDNA2 核心
- 真实光传播
- Minecraft RTX / Teardown

每代技术对硬件要求递增。Casey 的 HH 在 Layer 2(教学优先)。

### A.4 性能 profile 的实战

Casey 在 phase-8 多次 profile:

**Profile 工具**:
- Linux:perf、Valgrind、flamegraph
- Windows:Superluminal、VTune
- 跨平台:Tracy

**典型发现**:
- Raycast 占 50%+
- Propagation 占 20%+
- Meshing 占 10%+
- 其他占 20%

**优化顺序**:
1. 最慢函数 → 算法优化
2. Cache miss → 数据布局优化
3. 锁等待 → 并发优化

每优化一个,重新 profile 找下一个。

### A.5 Casey 的 phase-8 工程决策

Casey 在 phase-8 做的关键工程决策:

**1. CPU 渲染**:简单,跨平台,教学优先
**2. Voxel grid(非 octree)**:简单,固定大小
**3. RGBE atlas(非 SH)**:内存小,够教学
**4. Precomputed + delta update**:平衡实时性和准确性

这些决策让 HH 代码可读、可教学。生产游戏可能选 GPU + SH + realtime(更复杂)。

### A.7 Voxel lighting 算法的核心循环

让我写一个简化的 voxel lighting 主循环:

```rust
fn update_lighting(world: &mut World, sun_dir: Vec3) {
    let direct = compute_direct_lighting(world, sun_dir);
    let indirect = compute_indirect_lighting(world, &direct, 3);  // 3 bounce
    let final_light = combine(&direct, &indirect);
    world.light_atlas = final_light;
}

fn compute_direct_lighting(world: &World, sun_dir: Vec3) -> LightAtlas {
    let mut atlas = LightAtlas::new(world.dims());
    for each voxel {
        if voxel.is_solid() && !is_occluded(world, voxel_pos, sun_dir) {
            let lambert = compute_normal(world, x, y, z).dot(sun_dir).max(0.0);
            atlas.set(x, y, z, sun_color * lambert);
        }
    }
    atlas
}

fn compute_indirect_lighting(world: &World, direct: &LightAtlas, bounces: usize) -> LightAtlas {
    let mut current = direct.clone();
    for _ in 0..bounces {
        let mut next = current.clone();
        for each voxel {
            let bounce = average_neighbors(&current, x, y, z) * 0.15;
            next.set(x, y, z, current.get(x, y, z) + bounce);
        }
        current = next;
    }
    current
}
```

这是 Casey phase-8 的简化核心。工业实现更复杂(SH、GPU、并行)。

### A.8 Voxel lighting 的内存估算

```
Per voxel 数据:
  - material: 1 byte
  - color: 3 byte RGB
  - light: 4 byte RGBE
  - flags: 1 byte
  Total: 9 byte

场景尺寸:
  - 32^3(教学):36 KB
  - 100^3(小场景):9 MB
  - 256^3(中场景):150 MB
  - 1024^3(大场景):9.6 GB

大场景必须 streaming(chunked)。
```

工业 voxel 游戏(Minecraft):
- 16×16×256 chunk
- 每 chunk ~36 KB
- 同时加载 100 chunk ≈ 3.6 MB
