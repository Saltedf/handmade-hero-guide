# Day 519 · 头脑风暴:Z 偏移

> HH 是 2D 游戏,但 Casey 想加"假 3D"——某些 sprite 比其他更"高"(Z 偏移),玩家走过时前后关系正确。Day 519 是头脑风暴日,Casey 探讨几种 Z 偏移方案,评估利弊。

## 0 · 为什么要有这一天

### 真实场景:为什么 2D 游戏需要 Z 偏移

让我们把镜头拉近。假设你正在做一个 2D 角色 RPG,类似 Zelda 或 Stardew Valley。地图上有一棵树,玩家走过树下。**问题来了:玩家应该在树前面,还是树后面?**

如果树是简单的 sprite,玩家走过去,你用 painter's algorithm(按 y 排序):
- 树根在 y=300(屏幕下方),玩家在 y=300 时,谁先画谁后画?
- 玩家在树根左边或右边时,树根应该挡玩家吗?

最简单的方案:**按 sprite 的 y 排序**——y 大的(屏幕下方)后画,挡住 y 小的(屏幕上方)。这让"近的挡远的"自动正确。

但这套机制碰到几个**反例**:

**反例一:悬挂物体**。屋顶有吊灯,吊灯 y=100(屏幕上方),玩家 y=300(屏幕下方)走过。**玩家应该挡吊灯**(玩家在前),但 y 排序会让吊灯先画(因为 y 小),玩家后画——结果玩家挡吊灯。**等等,这个对了**。

再想:吊灯 y=100,玩家 y=80(玩家在屏幕更上方,可能跳起来或上台阶)。y 排序:玩家(80)在吊灯(100)前画。结果吊灯挡玩家——但**正确的是玩家挡吊灯**(玩家在前)。**这就错了**。

**反例二:平台 / 台阶**。玩家站在台阶上,台阶 y=200,玩家 y=180(玩家在台阶上方)。y 排序:玩家(180)在台阶(200)前画,台阶挡玩家——**但玩家站在台阶上,玩家应该挡台阶顶面**。

**反例三:倾斜地面**。3D 透视效果,地面 sprite 倾斜,玩家"远" 的位置 y 小(屏幕上方),"近"的位置 y 大。y 排序正确——但天花板 sprite 也是倾斜的,顺序反了。

这些都是 2D 游戏"伪 3D"的经典难题。工业级游戏的解决方案是 **Z 偏移**——给 sprite 加 z 值,排序键变成 `y + z` 或 `(layer, y, z)` 多级排序。

### 工业级"伪 3D"游戏的实际案例

**The Legend of Zelda: Link's Awakening**(Game Boy, 1993):用 4 层 sprite 系统。地面 tile、地面物体(草)、角色、悬挂物体(树枝、屋顶)。每层内按 y 排序。这是 8-bit / 16-bit 时代的标准方案。

**Stardew Valley**(2016):树木有 z 偏移——树冠在树根前。玩家走过树,先挡树根,然后被树冠挡。这需要 z 排序。

**Hades**(2020):2.5D,角色是 3D 模型,环境是 2D 背景画。混合方案。

**Disco Elysium**(2019):角色是 3D 模型,环境是 2D 油画背景。混合方案,特殊处理角色 / 背景的 z 关系。

## 1 · Casey 今天做了什么

Casey 这一天不开电脑写代码,而是在白板(其实是直播讲)讨论方案。这是工业级开发里 **design review** 的实践——先想清楚,再动手。

Casey 提出 4 种 Z 偏移方案,逐一讨论:

**方案 A:简单 Z 排序**。每个 sprite 有离散 z 值,排序后画:

```
z = 0:地面
z = 1:玩家
z = 2:树木
z = 3:飞行物体
```

问题:不灵活。玩家上台阶,z 应该变。如果 z 是固定常量,玩家走上台阶时,z 不变,但视觉上应该"高于"地面。需要**动态 z**。

**方案 B:Y + Z**。用 `y + z * scale` 排序:

```
sort_key = pos.y + z_offset * scale
```

`z_offset` 是该 sprite 的 z 偏移(相对其 y 位置)。例如吊灯 y=100, z_offset=+100, sort_key = 100 + 100*1 = 200,排在地面(y=200, z=0, sort_key=200)前——但视觉上吊灯应在玩家下方(玩家走过吊灯下方时玩家在前)。

问题:`z_offset` 大小怎么选?太小没效果,太大排序乱。

**方案 C:多层 Z**。每个 sprite 属于一层(地面 / 物体 / 角色 / 飞行):

```
layer 0: 地面 tile
layer 1: 地面物体(草、石头)
layer 2: 角色(玩家、敌人)
layer 3: 飞行物体(吊灯、树冠、屋顶)
```

每层内按 y 排序。**层间严格按层序**——layer 3 永远在 layer 2 前。

实现简单:每层一个 Vec,各排序,各画。

**方案 D:真 3D Z-buffer**。用真正的 3D 引擎,2D sprite 当 3D quad(在 z=平面上)。GPU 的 depth buffer 自动处理遮挡。

完美但过度——2D 游戏用 3D 引擎,成本高。Bevy / Unity 可以这么干,但 Casey 在 HH 的纯 2D renderer 上不值得。

**Casey 的讨论过程**:他画图、举例、反驳、调整。例如:

- "方案 C 多层 Z 下,玩家(layer 2)走过树冠(layer 3),玩家在树冠前——但应该树冠挡玩家。冲突。"
- "解决:树冠的 layer 不固定——动态看玩家位置。如果玩家在树根旁,树冠 layer 高;玩家远离,树冠 layer 低。但这就成方案 B 了。"
- "或者:加更细的 layer(树根 layer 1, 树冠 layer 3, 玩家 layer 2)。玩家走过树,先在树根前(layer 2 > 1),后被树冠挡(layer 3 > 2)。视觉正确!"

每种方案讨论利弊,Casey 决定 Day 520 实施(具体多 layer + Y + Z 混合)。

### Brainstorming 方法的工业级价值

Casey 这一天的教学不是"学到一个算法",而是"学会怎么 design review"。工业界很多 bug 来自"想都没想就写代码"。程序员碰到一个问题,立刻打开 IDE 开始 hack。一天后,代码写得乱七八糟,发现方案根本不对,推倒重来。

**Design review** 的纪律:在开始 coding 前,先做这几步:

1. **明确问题**:你解决的具体问题是什么?用一句话描述。
2. **列出方案**:至少 3 种,不要只想到 1 种就开干。
3. **比较利弊**:每种方案的优点、缺点、副作用、复杂度。
4. **选最优**:基于"哪个最简单且解决问题",不是"哪个最炫"。
5. **写 design doc**:简短文档(1 页),记录决策。让别人 review。
6. **再开始 coding**:有了明确方向,代码自然清晰。

Google、Microsoft、Amazon 等大公司**强制** design review 流程。 Casey 在 HH 里反复演示。这不是"官僚主义",是**避免返工的核心工程纪律**。

## 2 · 心智模型

### 类比:舞台剧

演员在舞台上有"前后"关系。前排演员挡后排。

2D 游戏的 sprite 同构——靠 y 坐标决定前后(靠下 = 靠前)。

但舞台上有特殊效果:演员踩高跷(高过其他人)、悬挂道具(从天花板垂下)。这些"打破"y 排序规则。

Z 偏移就是给 sprite 加"高跷"或"悬挂"能力。

### Painter's Algorithm

最简单的 2D 排序:**按 y 坐标排序**。

```
sort sprites by y
draw back to front
```

规则:玩家在树下,树根 y 大(屏幕下方),玩家 y 中,树冠 y 小(屏幕上方)。

画顺序:树冠 → 玩家 → 树根。玩家被树根挡(正确),玩家挡树冠(正确)。

但悬挂物体:吊灯在玩家头顶,玩家走过应该玩家挡吊灯(玩家在前)。y 排序做不到——吊灯 y 小(屏幕上方),会先画,玩家后画会挡吊灯(错)。

### Z 偏移

加 z 值:`sort_key = y + z * scale`。

吊灯 y = 100(屏幕上方),z = 100(高悬):sort_key = 100 + 100*10 = 1100。玩家 y = 300,z = 0:sort_key = 300。玩家 sort_key 小,先画,吊灯后画挡玩家(对!)。

加 z 给排序更多自由度。

### 多层 Z

更结构化:

```
[Ground layer]    z=0    - 地面 tile
[Object layer]    z=1    - 草、石头
[Character layer] z=2    - 玩家、敌人
[Overhead layer]  z=3    - 吊灯、树冠
```

每层内按 y 排。层间严格按层序。

实现:每层一个 Vec,各排序,各画。

### Z-buffer

3D 引擎的 Z-buffer:每个像素存 z 值,画时比较,depth test 通过才画。

2D 用 Z-buffer 过度。但能完全解决遮挡问题,适合复杂场景。

### 层 vs Z 值

层(离散):简单,可控。
Z 值(连续):灵活,但难调。

工业级倾向层 + 层内 y 排序。

```rust
fn sort_sprites(sprites: &mut [Sprite]) {
```

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 2D 游戏通常用 y-sort 而不是 z-buffer?

**参考解答**:三个理由:

第一,**简单**。y-sort 几行代码,z-buffer 需要 GPU / 软件实现深度缓冲,内存 + 性能开销。

第二,**足够好**。绝大多数 2D 场景 y-sort 正确。z-buffer 解决的问题(复杂遮挡)2D 罕见。

第三,**艺术控制**。y-sort 给艺术家精确控制——同一 y 值的 sprite 可以指定顺序。z-buffer 自动,不可控。

代价:y-sort 对悬挂物体、平台不灵。这些用 z 偏移补充。

### Lv2 · 动手实践

**题**:实现 sprite 排序器,支持层 + y-sort + z 值。给定 N 个 sprite,排序后画。

完成标准:`cargo run` 显示排序后的画顺序。

**参考解答**:

```rust
#[derive(Debug, Clone)]
struct Vec2 { x: f32, y: f32 }

#[derive(Debug, Clone)]
struct Sprite {
    name: String,
    pos: Vec2,
    layer: i32,    // 离散层(0 = 地面, 1 = 物体, 2 = 角色, 3 = 悬挂)
    z: i32,        // 层内 z(细粒度调整)
}

fn sort_sprites(sprites: &mut Vec<Sprite>) {
    sprites.sort_by(|a, b| {
        a.layer.cmp(&b.layer)        // 层优先
            .then_with(|| a.pos.y.partial_cmp(&b.pos.y).unwrap())  // 层内 y
            .then_with(|| a.z.cmp(&b.z))    // 同 y 看 z
    });
}

fn main() {
    let mut sprites = vec![
        Sprite { name: "ground".into(), pos: Vec2 { x: 0.0, y: 0.0 }, layer: 0, z: 0 },
        Sprite { name: "grass".into(), pos: Vec2 { x: 10.0, y: 5.0 }, layer: 1, z: 0 },
        Sprite { name: "tree_root".into(), pos: Vec2 { x: 20.0, y: 30.0 }, layer: 1, z: 0 },
        Sprite { name: "player".into(), pos: Vec2 { x: 15.0, y: 25.0 }, layer: 2, z: 0 },
        Sprite { name: "tree_trunk".into(), pos: Vec2 { x: 20.0, y: 20.0 }, layer: 1, z: 1 },
        Sprite { name: "tree_crown".into(), pos: Vec2 { x: 20.0, y: 10.0 }, layer: 1, z: 2 },
        Sprite { name: "chandelier".into(), pos: Vec2 { x: 15.0, y: 5.0 }, layer: 3, z: 0 },
    ];
    
    println!("=== Before sort ===\n");
    for s in &sprites {
        println!("  {} layer={} y={} z={}", s.name, s.layer, s.pos.y, s.z);
    }
    
    sort_sprites(&mut sprites);
    
    println!("\n=== After sort (paint order) ===\n");
    for (i, s) in sprites.iter().enumerate() {
        println!("  {}. {} (layer={}, y={:.0}, z={})", i, s.name, s.layer, s.pos.y, s.z);
    }
    
    // 讨论:chandelier(layer 3)最后画,挡住玩家走过(对的)
    // 玩家(layer 2)画在树根(layer 1)之后,挡住树根(对的,玩家在前)
    // 玩家走过树干(layer 1, z=1)和树冠(layer 1, z=2)时:
    //   - 玩家在树干前(layer 2 > 1),挡树干(对)
    //   - 但树冠在玩家头顶,玩家走过应被树冠挡(不对,玩家 layer 2 > 1)
    // → 这是 z 偏移的局限,需要更复杂方案
    
    println!("\n=== 局限性分析 ===");
    println!("玩家走过树:树冠应在玩家前(覆盖玩家头顶)");
    println!("但 layer 1 < layer 2,玩家总在树前(包括树冠)");
    println!("→ 需要 layer 设计调整,或加 z");
}
```

### Lv3 · 迁移设计

**题**:把 sprite 排序迁移到**桌面窗口管理**。设计:窗口层 + 内部 Z 顺序。

窗口管理(Wayland compositor、X11、Windows 桌面)本质也是 sprite 排序问题——每个窗口是一个矩形,可能有重叠,要按 z 顺序绘制。但桌面有几类特殊需求:

**永远在顶层**的窗口(taskbar、始终置顶的 toast notification)。这些要强制最大 z。
**永远在底层**的窗口(桌面壁纸 widget)。强制最小 z。
**模态对话框**。要在父窗口之上,但不能高过其他应用。
**Tooltip**。要在所有窗口之上,但不抢焦点。
**Drag-and-drop 半透明**。要浮动但鼠标交互穿透。

设计:
```rust
enum WindowLayer {
    Desktop,        // 壁纸
    Normal,         // 普通窗口
    Dialog,         // 对话框
    AlwaysOnTop,    // 始终置顶
    Tooltip,        // tooltip
    Drag,           // 拖拽预览
}

struct Window {
    layer: WindowLayer,
    z_in_layer: i32,  // 层内 z
    rect: Rect,
}

fn render_order(windows: &mut Vec<Window>) -> Vec<usize> {
    let mut order: Vec<usize> = (0..windows.len()).collect();
    order.sort_by_key(|&i| (windows[i].layer as i32, windows[i].z_in_layer));
    order
}
```

这是 i3、sway、 Mutter、KWin 这些 Linux 桌面的核心逻辑。

### 8.1 完整 sprite 排序系统

下面是 Day 519 完整代码(同 Lv2,加测试)。

```rust
#[derive(Debug, Clone, Copy, PartialEq)]
struct Vec2 { x: f32, y: f32 }

#[derive(Debug, Clone, PartialEq)]
struct Sprite {
    name: String,
    pos: Vec2,
    layer: i32,
    z: i32,
}

impl Sprite {
    fn new(name: &str, x: f32, y: f32, layer: i32, z: i32) -> Self {
        Self { name: name.into(), pos: Vec2 { x, y }, layer, z }
    }
}

fn sort_sprites(sprites: &mut Vec<Sprite>) {
    // 稳定排序,按 (layer, y, z) 多级 key
    sprites.sort_by(|a, b| {
        a.layer.cmp(&b.layer)
            .then_with(|| a.pos.y.partial_cmp(&b.pos.y).unwrap_or(std::cmp::Ordering::Equal))
            .then_with(|| a.z.cmp(&b.z))
    });
}
```

### 8.5 Troubleshooting

**问题1**:玩家走过树,树冠在玩家前面挡视野。
原因:树冠 layer 太高 / 玩家 layer 太低。
解决:树冠 layer 设低于玩家,或树冠用单独的 "overhead" 层(仅当玩家在树下时显示)。

**问题2**:同样 sprite 在不同位置排序错乱。
原因:z 值用全局常量,不区分场景。
解决:z 值动态计算——根据 sprite 离玩家距离调整。

**问题3**:排序性能不够(10k+ sprite)。
原因:O(n log n) 全排序。
解决:空间分区——只对可见 sprite 排序(相机剔除),或用 bucket sort(O(n))。

**问题4**:透明边缘的 sprite 重叠时出现锯齿。
原因:alpha blending + 排序。
解决:用 alpha to coverage,或预乘 alpha。

**问题5**:动态 sprite(粒子)拖累排序。
原因:每帧重新排序所有 sprite,粒子占大头。
解决:粒子用单独系统,不参与主排序(粒子用 additive blending,顺序无关)。

### 附录:工业级 2D 排序的进阶技术

#### Sprite Atlas + Batch Rendering

工业级 2D 引擎不只关心"排序",还关心"批量渲染"。10k 个 sprite 如果每个都单独 draw call,CPU 提交瓶颈主导,帧率被卡在 30 FPS。

解决方案:**sprite atlas**——把所有 sprite 打包到一张大贴图(2048×2048),然后**一次 draw call 画上千个 sprite**。这要求所有 sprite **同贴图 + 同 shader**,否则要拆 batch。

排序与 batch 的冲突:
- 排序按 (layer, y, z) 多级
- batch 要求同贴图

实际做法:**先按贴图 hash 分桶,每桶内按 (layer, y, z) 排序**。每个桶一个 batch。这样 batch 数 = 贴图数,通常 < 20,draw call 极少。

#### Y-Sort 的 GPU 实现

某些引擎(Citybuilder 类游戏)有几万个 sprite,Y-sort 在 CPU 太慢。方案:**GPU driven rendering**——把所有 sprite 数据推到 GPU,vertex shader 算排序键,fragment shader 直接画。

具体技术:Compute shader 做 bitonic sort,O(n log² n) 并行。然后 indirect draw call 渲染。这是 Bevy 0.13+ 的 sprite 优化路径。

#### 透明物体排序的根本难题

无论怎么排,透明物体总有"相互贯穿"的难题——三个透明 sprite 互相遮挡,A 在 B 前,B 在 C 前,C 在 A 前,无法用单一顺序正确渲染。

工业级方案:
- **Order-Independent Transparency (OIT)**:用 per-pixel linked list 存所有覆盖该像素的 fragment,最后合成。完美但耗显存。
- **Depth Peeling**:多次渲染,每次"剥掉"最前层。慢但正确。
- **Weighted Blended OIT**:近似 OIT,快但不完美。这是 Unity HDRP 的方案。

这些都在 2D + 3D 都适用。Casey 在 HH 里没深入,但工业级引擎必备。
