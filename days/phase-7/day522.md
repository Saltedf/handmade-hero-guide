# Day 522 · 求解排序位移

> 编辑器里两个 z 值非常接近的精灵(sprite)开始"打架"——这一帧 A 盖在 B 上,下一帧 B 盖在 A 上,屏幕上看起来疯狂闪烁。Casey 这一天做的事听起来很小:**给每个精灵加一个微小的 z 偏置(sorting displacement),让它在排序时稳定下来**——但里面藏着一个数学问题:偏置应该取多少?取太小没用,取太大破坏视觉。这一集把这个"小数"的取值问题彻底讲清楚。

## 0 · 为什么要有这一天

你在编辑器里放了两个物体:一把剑和一个挂在剑柄上的宝石。它们在世界坐标里 z 值几乎一样(因为附接关系,宝石就在剑柄那个位置)。渲染时,你用 painter's algorithm(画家算法,后画的覆盖先画的)按 z 排序。问题来了:浮点数比较是危险的。

`z_sword = 1.0`,`z_gem = 1.0 + 1e-7`(附接偏移)。理论上宝石应该在前。但下一帧,因为相机移动、矩阵乘法累积误差,`z_sword` 变成 `1.0 + 2e-7`,`z_gem` 变成 `1.0 + 1e-7`——它们的相对顺序**翻了**。屏幕上看到宝石闪到剑后面,然后下一帧又闪到前面。

这不是逻辑 bug,是**数值稳定性**问题。Casey 这一天做的事:在排序键里加一个**确定性偏置**,让"应该在前"的物体稳定获得一个比浮点误差大的优势。这个偏置怎么取?取多少?这背后是一类经典问题:**在数值比较里,如何引入"工程容差"**。

类似问题在工业界无处不在:

- 物理引擎里"两个碰撞体是否接触"——不能直接 `d < 0`,要用 `d < epsilon`
- 浮点矩阵"是否相等"——不能 `==`,要 `abs(a-b) < epsilon`
- 像素深度"是否覆盖"——OpenGL 用 depth bias 解决 shadow acne(阴影痘疤)
- 网络 RTS 游戏"两个单位在同一格"——加随机偏移避免冲突

完成这一天之后,你具备:

- 看到 z-fighting / flickering 时知道是排序浮点误差,有标准解法
- 理解 epsilon(ε)在数值算法里的角色——不是"魔法常数",是有推导依据的
- 在 Rust 里写稳定的排序键(用整数排序代替浮点排序,或用 fixed-point)

## 1 · Casey 今天做了什么

Casey 这一天的动作可以拆成三步:

第一步,他**确认症状**:打开编辑器,把宝石附接到剑柄上,放大相机看,观察到屏幕上的闪烁。然后他切到 wireframe 模式,确认两个 quad 的 z 值确实只差很小一点(在像素层面)。

第二步,他**思考根因**:不是排序算法错,是浮点比较本身不稳定。如果两个排序键 `k1` 和 `k2` 满足 `|k1 - k2| < epsilon`,它们的相对顺序可能因为浮点运算的微小扰动而翻转。

第三步,他**加偏置**:在计算排序键时,显式给"应该在前"的物体加一个 `displacement`。这个值要满足两个约束:**比浮点误差大**(否则没用),**比视觉可感知阈值小**(否则物体看起来"飘"在另一个上面)。Casey 选了 `1e-3` 量级——足够大于浮点噪声,远小于一个像素的深度差。

视频里他半开玩笑地说"这个数是经验值,不是推导出来的",但其实背后有数学依据:**float32 的 epsilon 在 z=1.0 附近是 1.19e-7,在 z=1000 附近是 1.1e-4**。所以 displacement 至少要比当前 z 量级的 epsilon 大一个数量级。

让我把这个推理过程用数学写得更精确。假设当前两个精灵的 z 值都是 `z0`,它们经过矩阵变换后的 z 值变成 `z0 + δ`,这里 δ 是浮点运算的累积误差。对于 float32,δ 大约是 `z0 * 2^-23 ≈ z0 * 1.19e-7`。如果两个精灵经过**不同的运算路径**(比如 child 多了一次矩阵乘法),它们的 δ 可能不同,差值 `δ1 - δ2` 的量级仍然是 `z0 * 1.19e-7`。

要让 displacement `D` 稳定生效,需要:

```
D >> |δ1 - δ2|
D >> z0 * 1.19e-7
```

"远大于"在工程上一般取 10 倍以上,所以 `D >= 10 * z0 * 1.19e-7 = 1.19e-6 * z0`。当 `z0 = 1.0` 时,`D >= 1.19e-6`;当 `z0 = 100.0` 时,`D >= 1.19e-4`。Casey 选 `D = 1e-3` 是对所有合理的 z 范围都满足这个约束——`1e-3 / 1.19e-7 ≈ 8403`,大约是 8000 倍的浮点噪声余量。

同时 displacement 的上限是"视觉不可感知"。人眼能感知的最小深度差在 60Hz、1 米视距下,大约是 1mm。游戏单位一般 1 米 = 1.0,所以 1mm = 1e-3。Casey 选 1e-3 正好在视觉阈值的边缘——这可能"恰好可见",但对小物体(宝石、徽章)很难察觉。如果你做的是一个 10 米长的剑,1e-3 的位移完全不可见;如果做的是几毫米的精密零件,可能要选更小的 displacement。

## 2 · 心智模型

### 类比:田径比赛的"千分之一秒"

两个短跑选手过线,计时器显示 9.81 秒和 9.81 秒——肉眼觉得平手。但你必须决出冠军,怎么办?把计时精度提高到万分之一秒,就能看到 9.8124 和 9.8141 的差别。

排序位移的作用相反:**故意降低精度**,让"千分之一秒以内的差距"被忽略,但在忽略的同时,**给指定选手一个固定的"千分之五秒优势"**,这样即使两个选手时间在浮点噪声里翻转,优势方也稳定获胜。

### 严谨展开:浮点数的相对精度

float32 是 IEEE 754 单精度浮点数,32 bit 里 1 位符号、8 位指数、23 位尾数。它能表示的精度不是固定的——`1.0 + epsilon == 1.0` 的最小 epsilon 是 `2^-23 ≈ 1.19e-7`(机器 epsilon 的一半),但在 `1024.0` 附近,epsilon 是 `2^-13 ≈ 1.22e-4`。

这是因为 float32 的相对精度是固定的(约 6 位十进制有效数字),但绝对精度随数量级变化。**z 值越大,绝对噪声越大**。

### 排序键的三种取法

**直接用 world z**:最简单,但有上述浮点翻转问题。

**world z + 显式 displacement**:Casey 的方案。给"应该在前"的物体加固定偏置(比如附接在 parent 上的 child 加 `parent_z + child_offset - small_epsilon`)。优点:简单。缺点:需要工程师手动判断"谁在前"。

**整数排序键**:把 z 量化成整数。比如把世界 z 范围 `[0, 1000]` 量化成 `u32`,精度 `1000 / 2^32 ≈ 2.3e-7`。整数比较是精确的,没有浮点翻转问题。工业级引擎常用这个方案。

### z-fighting 的视觉症状

z-fighting(z 战斗)指两个面距离太近,深度缓冲(depth buffer)无法稳定决定哪个在前。表现就是闪烁——这一帧 A 像素覆盖 B,下一帧 B 覆盖 A。

OpenGL 标准对此的解法是 `glPolygonOffset`:给指定多边形加一个固定的深度偏移,常用于画贴在地面上的辅助线。Casey 用的是软件排序,所以等价的方案是在排序键里加偏置——同样的思想,不同的实现层。

### 排序位移的"分类讨论":为何 Casey 不能直接用 depth bias

你可能会问:既然 OpenGL 有 `glPolygonOffset`,Casey 为什么不直接用?答案是 **HH 用的是软件 painter's algorithm,没有 depth buffer**。Casey 的 2D 渲染器按 z 排序,然后**从后往前**画——后画的覆盖先画的。这是 alpha blending(透明度混合)的标准做法,因为半透明物体不能简单地"谁近谁赢"。

这意味着 `glPolygonOffset`(GPU 硬件级深度偏移)**根本进不来**——它只能影响 depth buffer 测试,但 HH 不用 depth buffer。Casey 必须在**软件层**做等价的事:在排序键里加偏置。

这种"GPU 硬件支持 vs 软件实现"的对比在图形学里到处都是。例子:

- **MSAA(多重采样抗锯齿)**:GPU 有硬件实现,直接 `glEnable(GL_MULTISAMPLE)`。软件实现要写 A-buffer 算法,代码量大十倍。
- **Instancing(实例化)**:GPU 硬件支持,一次 draw call 画多个相同 mesh。软件实现要循环 draw call。
- **Depth test**:GPU 硬件 `glDepthFunc`,每像素测试深度。软件实现要按 z 排序,然后 painter's algorithm。

Casey 选软件实现,是因为 HH 教学目标是"自研一切",而且 2D 不需要 GPU 的硬件加速(物体少、像素少)。3D 引擎必须用 GPU。**这就是为什么 Day 522 的"软件排序位移"看起来 primitive——它是教学选择,不是工业实践**。

### 工程容差的通用原则

排序位移背后是一个跨学科通用原则:**所有数值比较都要有容差**。这条原则在工程界有名字——"tolerance(容差)"。机械工程里零件必须留公差(否则装不上),电子工程里信号阈值要留噪声余量,软件工程里浮点比较要留 epsilon。

容差的取值有通用公式:

```
tolerance = K * (typical_magnitude * unit_precision)
```

- `K` —— 安全系数,通常 10-1000,看场景
- `typical_magnitude` —— 数据的典型量级
- `unit_precision` —— 表示精度的"机器单位",float32 是 1.19e-7

对排序位移:`tolerance = 10 * z * 1.19e-7 ≈ 1.19e-6 * z`。Casey 取 1e-3,是给 z 在 `[1, 100]` 范围留 8000-800 倍余量,远超最低要求。

这种"用公式推导容差,而不是拍脑袋"的思维方式,是数值分析这门学科的核心。Casey 不是数值分析专家,但他的工程直觉给出了一致的答案。

## 3 · 四域深入

### 3.1 · 游戏编程视角

2D 游戏里 sprite sorting 是经典问题。比如俯视角 RPG:角色 A 站在桌子前面,角色 B 站在桌子后面。两个角色的 y 坐标(等价于"深度")决定谁在前。当 A 和 B 的 y 值非常接近(都站在桌子边缘),就开始 flicker。

经典解法:**y-sort + 显式 layer offset**。每个 sprite 有一个 `sort_y` 字段,等于 `position.y + feet_offset`,feet_offset 让 sprite 的"脚"作为排序基准。然后给每个 sprite 类别加一个固定 layer offset(player=0, prop=0.001, item=0.002),保证不同类别稳定排序。

3D 游戏里用 depth buffer 替代排序,所以这个问题少得多。但**透明物体必须用排序**(因为 depth buffer 不支持半透明混合),所以粒子系统、玻璃、水这类透明物体仍然有 z-fighting 问题。

### 3.2 · 图形学视角

Depth buffer 的精度分布不均——离相机近的 z 值精度高,远的精度低。这是 perspective projection 矩阵的设计决定的:它把 near plane 附近"拉伸",把 far plane 附近"压缩"。结果就是远处物体更容易 z-fight。

让我用数学推一下为什么。透视投影矩阵的 z 分量变换是:

```
z_clip = (far + near) / (far - near) - (2 * far * near) / (z_eye * (far - near))
```

求导:

```
dz_clip / dz_eye = -(2 * far * near) / (z_eye^2 * (far - near))
```

这是一个 **z_eye 的反平方函数**。z_eye 越大(越远),导数越小,意味着 z_eye 的同样变化在 z_clip 里产生的变化越小——也就是"远处精度低"。当 `near = 0.1`, `far = 1000`,在 z_eye = 1 时,精度是 1e-7;在 z_eye = 100 时,精度掉到 1e-3。所以远处物体 z-fight 概率远高于近处。

**Reverse-Z 技巧**:把 perspective 矩阵的 z 翻转——near plane 映射到 depth=1,far plane 映射到 depth=0。这样近处精度反而更低(原本近处精度高得多,翻转后变成"够用"),远处精度变高(原本低,翻转后够用)。整体精度分布更均匀。这是现代引擎标配,几乎免费就能拿到一倍深度精度。

工业级解法:

- **reverse-Z**:把 near/far 颠倒,让远处精度反而更高。这是现代引擎标配。
- **logarithmic depth buffer**:用 log(z) 替代 z,精度分布均匀。代价是 GPU 性能略降。
- **depth bias**:OpenGL `glPolygonOffset` / Vulkan `depthBias` 的硬件支持。

Casey 在 HH 用的是软件排序(没有 depth buffer 的 2D 模式),所以靠排序键加偏置。

### 3.2.1 · shadow mapping 里的同类问题

z-fighting 在 **shadow mapping(阴影映射)**里特别严重。shadow map 是从光源视角渲染的深度图,然后从相机视角渲染时,比较像素深度和 shadow map 里的深度——如果像素"更远",说明被遮挡,渲染为阴影。

问题是:被光照射的表面,它在 shadow map 里的深度和它在相机视角下的深度,理论上应该相等。但浮点精度有限,有些像素被错误判定为"被自己遮挡"——产生 "shadow acne(阴影痘疤)",表面布满条纹状噪声。

GPU 的标准解法还是 depth bias:`glPolygonOffset(1.0, 1.0)` 给所有阴影 caster 加一个微小偏置,让它们在 shadow map 里"远一点点",避免自遮挡。**和 Casey 的排序位移是完全一样的思想,只是在不同层**(shadow map 层 vs 排序层)。学会这个原则,你看任何"浮点比较问题"都能秒答:**加 bias**。

### 3.2.2 · 浮点排序的 EBADF 经典案例

给你一个工业级例子:Chromium 浏览器的 CSS z-index 排序。CSS `z-index` 是个 32 位整数,标准规定可以是负数。但浏览器内部用 float 存储(为了支持 transform 的 z-translation),所以 `z-index: 999999999`(超过 float 精度)会被 round 成 `1000000000`,导致两个相邻 z-index 比较失败,渲染顺序错乱。

Chromium 的源码里有专门的注释解释为什么 `z-index` 要量化到整数比较,避免浮点翻转。这是工业级代码处理浮点排序的标准做法——**用整数,不用浮点**。

### 3.3 · Linux 系统编程视角

Linux 内核里类似问题是"时间戳比较"。内核用 `ktime_t`(纳秒精度)或 `struct timespec64`(秒 + 纳秒)表示时间。两个事件的时间戳在纳秒精度下可能"相等",但你必须排序。

内核的解法:**用 64 位整数**而不是浮点。`u64` 纳秒精度可以表示 584 年的范围,完全够用。整数比较是精确的,没有浮点翻转问题。这印证了上面说的"整数排序键"方案。

### 3.4 · Rust 生态视角

Rust 表达稳定排序:

```rust
// 方案 A:用 f32 排序(可能有浮点翻转)
sprites.sort_by(|a, b| a.sort_z.partial_cmp(&b.sort_z).unwrap_or(Equal));

// 方案 B:用整数排序键(稳定)
sprites.sort_by_key(|s| s.sort_key_i32);  // 把 z 量化到 i32

// 方案 C:用 OrderedFloat(无 NaN,可 Ord)
use ordered_float::OrderedFloat;
sprites.sort_by_key(|s| OrderedFloat(s.sort_z + s.displacement));
```

`ordered_float` crate 提供了 `OrderedFloat(f32)`,包装后实现 `Ord`,可以直接用作排序键。NaN 处理可配置(默认 panic 或排序到末尾)。这是 Rust 比 C++ 优雅的地方——C++ 里 f32 不支持 `<` 严格弱序(因为 NaN),所以 std::sort 是 UB;Rust 在类型层强制 `Ord`,编译期就拦下。

`sort_by_key` 比手写 closure 快——它会缓存 key 计算结果,而 `sort_by` 每次比较都重新算 key。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **数值稳定性** —— 浮点运算的误差传播与控制

## 5 · 对照与变奏

2D 游戏的经典做法是 y-sort——所有 sprite 按 y 坐标排序,后画的(屏幕下方)覆盖先画的。简单可靠,但问题是当两个 sprite 的 y 相等时,相对顺序由 sort 算法决定(稳定排序时按插入顺序),不稳定。

Stardew Valley(开源-ish 的 2D 农场游戏)用的是 y-sort + 显式 layer。每个 sprite 有 `drawOrder` 字段,默认等于 y,但可以手动覆盖。它的源码公开,可以去 GitHub 看。

3D 引擎里这种问题被 depth buffer 解决了——GPU 像素级深度测试,完全不会闪烁。所以 3D 引擎只有在透明物体(必须软件排序)上才有 z-fighting。

工业级渲染管线(Unity、Unreal)用 `Sorting Layer` + `Order in Layer` 两个值组合,前者是粗粒度分组(Background / Foreground / UI),后者是组内细粒度。开发者通过 Inspector 调,本质就是 displacement 思想的工业化。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:有人提议:"把 displacement 取得越大越好,这样排序永远不会翻转。"这个想法错在哪?

**参考解答**:displacement 太大会破坏视觉。比如 displacement = 1.0,意味着附接在剑柄上的宝石看起来"飘在剑前面 1 米"。displacement 应该满足两个相互制约的约束:**比浮点噪声大**(否则没用),**比视觉感知阈值小**(否则破坏画面)。Casey 选 `1e-3` 量级,正是这两个约束的平衡点。任何工程容差都有"上限和下限",没有"越大越好"。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:用 Rust 实现一个 sprite 排序系统,要求:(1)每个 sprite 有 `world_z: f32` 和 `layer: i32`(粗粒度,0=background, 1=mid, 2=foreground);(2)排序键 = `(layer, world_z)`,先按 layer,同 layer 按 world_z;(3)同 layer 同 world_z 的 sprite,稳定保持插入顺序。运行测试:构造 100 个随机 sprite,排序后检查稳定性。

**参考解答**:

```rust
#[derive(Clone)]
struct Sprite {
    name: String,
    world_z: f32,
    layer: i32,
}

fn stable_sort_sprites(sprites: &mut Vec<Sprite>) {
    // Rust 的 sort_by 是稳定排序(stable sort),相等元素保持原顺序
    sprites.sort_by(|a, b| {
        // 先按 layer,再按 world_z
        match a.layer.cmp(&b.layer) {
            std::cmp::Ordering::Equal => a.world_z.partial_cmp(&b.world_z).unwrap_or(std::cmp::Ordering::Equal),
            other => other,
        }
    });
}

fn main() {
    let mut sprites = vec![
        Sprite { name: "A".into(), world_z: 1.0, layer: 0 },
        Sprite { name: "B".into(), world_z: 1.0, layer: 0 },  // 同 layer 同 z
        Sprite { name: "C".into(), world_z: 0.5, layer: 0 },
        Sprite { name: "D".into(), world_z: 99.0, layer: 1 },
    ];
    stable_sort_sprites(&mut sprites);
    for s in &sprites {
        println!("{}: layer={}, z={}", s.name, s.layer, s.world_z);
    }
    // 输出:
    // C: layer=0, z=0.5
    // A: layer=0, z=1
    // B: layer=0, z=1    (A 在 B 前,因为稳定排序)
    // D: layer=1, z=99
}
```

为什么这么写:`sort_by` 是稳定排序——这是 Rust 标准库保证的(具体用 Timsort 算法)。C++ 的 `std::sort` 不是稳定的,要用 `std::stable_sort`。Rust 在这里的设计更友好。

### Lv3 · 迁移设计(换场景用同一原理)

**题**:你要做一个任务调度器,有 N 个任务,每个有 `priority: u8`(0-255)、`submit_time: f64`(提交时刻)。要求:优先级高的先执行;同优先级的,先提交的先执行(FIFO)。但提交时间用 f64 浮点比较不稳定——两个任务在同一毫秒内提交,比较结果可能翻转。设计一个排序键,让"同一毫秒内"的任务按 submit_time 顺序,但**不**用浮点比较。提示:把 submit_time 量化到纳秒整数(u64)。

**提示**:`submit_time * 1e9` 转成 u64,然后排序键是 `(priority, submit_ns)`。整数比较精确,不会翻转。

**详细参考**:

```rust
#[derive(Clone, Debug)]
struct Task {
    name: String,
    priority: u8,
    submit_ns: u64,  // 纳秒整数,不用 f64
}

impl Task {
    fn new(name: &str, priority: u8, submit_sec: f64) -> Self {
        Self {
            name: name.into(),
            priority,
            submit_ns: (submit_sec * 1e9) as u64,  // 量化到纳秒
        }
    }
    
    /// 排序键:先按 priority 降序(高的先执行),同 priority 按 submit_ns 升序
    fn sort_key(&self) -> (std::cmp::Reverse<u8>, u64) {
        (std::cmp::Reverse(self.priority), self.submit_ns)
    }
}

fn schedule(tasks: &mut Vec<Task>) {
    tasks.sort_by_key(|t| t.sort_key());
}
```

为什么用 `std::cmp::Reverse<u8>`:Rust 的 `sort_by_key` 默认升序,要把 priority 改成降序就用 `Reverse<u8>` 包一层——`Reverse<u8>` 实现了 `Ord`,比较时把 255 视为"最小"(所以排到最前)。这是 Rust 的优雅写法,等价于手写 `b.priority.cmp(&a.priority)`。

整数方案的额外好处:**整数比较是 O(1) 的硬件指令**,比浮点快一点点(浮点比较在 x86 上是 `ucomiss`,整数是 `cmp`)。在大量元素的排序场景(N > 100000),这能省 5-10% 时间。这是为什么工业级调度器(Linux CFS、Kubernetes)都用整数时间戳。

### Lv3.1 · 拓展任务:多维度排序

承接上题,现在你的任务还有 `deadline: u64`(纳秒)。要求:优先级高的先执行;同优先级,**先到 deadline 的先执行**;同 deadline,先提交的先执行。这是经典的 EDF(Earliest Deadline First)调度。

写一个 sort_key 表达三层排序:

```rust
fn sort_key(&self) -> (std::cmp::Reverse<u8>, u64, u64) {
    (std::cmp::Reverse(self.priority), self.deadline_ns, self.submit_ns)
}
```

Rust 的 tuple 自动实现 `Ord`,按 lexicographic 顺序比较。所以这个三元组天然满足"先按第一维,同第一维按第二维,同第二维按第三维"。这种"元组排序键"是函数式编程的传统技巧,Lisp/Haskell/OCaml 都这么写。Rust 把它带进了系统编程。

```rust
// 排序位移的完整实现

#[derive(Clone, Debug)]
struct Entity {
    name: String,
    world_z: f32,
    sort_displacement: f32,  // 显式偏置
}

impl Entity {
    /// 排序键 = world_z + displacement
    /// displacement 为负数,让该实体"看起来在前"(更小 = 先画)
    fn sort_key(&self) -> f32 {
        self.world_z + self.sort_displacement
    }
}

fn render_order(entities: &mut Vec<Entity>) {
    // sort_by_key 缓存 key,比 sort_by 快
    // OrderedFloat 避免 NaN 导致的 UB
    use ordered_float::OrderedFloat;
    entities.sort_by_key(|e| OrderedFloat(e.sort_key()));
}

fn main() {
    let mut entities = vec![
        Entity { name: "sword".into(),       world_z: 1.0,    sort_displacement: 0.0 },
        Entity { name: "gem_on_sword".into(), world_z: 1.0,   sort_displacement: -1e-3 },  // 比 sword 略前
        Entity { name: "ground".into(),      world_z: 0.0,    sort_displacement: 0.0 },
    ];
    render_order(&mut entities);
    for e in &entities {
        println!("{}: sort_key = {:.6}", e.name, e.sort_key());
    }
    // 输出:
    // ground: sort_key = 0.000000
    // gem_on_sword: sort_key = 0.999000   (1.0 - 0.001 = 0.999)
    // sword: sort_key = 1.000000
    // 渲染顺序:ground → gem_on_sword → sword
    // 宝石稳定地在剑前面
}

/// 浮点噪声测试:模拟相机移动导致的 z 抖动
#[test]
fn test_stability_under_noise() {
    let base_z = 1.0_f32;
    let mut flips = 0;
    for i in 0..1000 {
        // 模拟浮点噪声,±1e-7 量级
        let noise_sword = (i as f32) * 1e-7;
        let noise_gem = ((i + 1) as f32) * 1e-7;
        
        let z_sword = base_z + noise_sword;
        let z_gem = base_z + noise_gem - 1e-3;  // displacement
        
        // 如果不加 displacement,这里会比较 noise,可能翻转
        // 加了 displacement,gem 永远 < sword
        if z_gem > z_sword {
            flips += 1;
        }
    }
    assert_eq!(flips, 0, "排序不应该翻转");
}
```
