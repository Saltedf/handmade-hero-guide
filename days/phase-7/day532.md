#### "Stub-and-replace"开发法

Casey 的字体管线开发过程演示了一个工业级模式:**stub-and-replace**(桩代码 → 真实现)。

开发流程:

1. **Day 100+:写 stub**——用最简单的方式(BMP + hardcoded metric)让游戏能跑起来。这是"假"实现,只为验证上层逻辑。
2. **Day 524-531:写真实现**——逐步搭建完整管线(WAV、PNG writer、HHT、字体提取)。这是"真"实现,但要花几天。
3. **Day 532:替换**——把游戏里的 stub 调用换成真实现调用。架构统一,旧代码下线。

这种开发法的好处:**上层逻辑和底层实现解耦**。游戏开发期间,UI 设计师可以用 stub 字体继续工作,不被字体管线开发阻塞。字体管线开发好之后,一行代码替换即可。

代价:**临时存在两套代码**。如果你不替换,代码库永久带两套,认知负担变大。所以 stub-and-replace 要求**有意识地计划"替换 day"**,不能让 stub 永久驻留。

工业级项目都有这种节奏:GitHub 早期用 MongoDB stub,后来替换成 MySQL;Twitter 早期用 Ruby on Rails stub,后来替换成 Scala/JVM。每次替换都是大工程,但**stub 让项目能早启动**。

#### "特殊情况"的债务累积

让我把"消除特殊情况"讲具体。Casey 在 Day 100+ 写 stub 时,代码里大概是这样:

```rust
// 旧代码:字体是特殊情况
fn load_asset(path: &str) -> Asset {
    if path.ends_with(".bmp") && is_font_atlas(path) {
        load_font_from_bmp(path)  // 特殊路径 1
    } else if path.ends_with(".png") {
        load_image_from_png(path)  // 通用路径
    } else if path.ends_with(".wav") {
        load_sound_from_wav(path)  // 通用路径
    }
    // ...
}
```

这个 `is_font_atlas(path)` 分支就是"特殊情况"。它让代码读起来要思考"哦字体有特殊路径",增加认知负担。

Day 532 重构后:

```rust
// 新代码:字体走通用路径
fn load_asset(path: &str) -> Asset {
    if path.ends_with(".png") {
        load_image_from_png(path)
    } else if path.ends_with(".wav") {
        load_sound_from_wav(path)
    } else if path.ends_with(".hht") {
        load_font_from_hht(path)  // 走和 png/wav 同样的"通用模式"
    }
}
```

字体走"通用资产管线"——加载 → 解析 → 缓存 → 卸载,所有资产共享同一套生命周期管理。代码理解成本骤降。

这是 refactor 的核心价值:**不是减少代码量,是减少认知分支**。10 种资产加载方式 → 1 种,代码量可能差不多,但维护成本天差地别。

- 理解"统一架构"的价值——同一种模式处理多种资产类型
- 能用 Rust trait 抽象"资产加载"
- 知道"refactor for consistency"和"refactor for performance"的差别
- 学会 stub-and-replace 开发法的节奏

### "Stub-and-replace"的工程纪律

让我把 Day 532 的工程纪律总结成可操作的建议。任何 stub-and-replace 都应该:

1. **明确 stub 的范围**:写下"这是 stub,计划 Day X 替换",贴在代码注释里
2. **计划替换 day**:在开发日程里专门留一天做替换,不能"以后有空再换"
3. **替换时小步前进**:一次只换一个 stub,跑测试验证,再换下一个
4. **替换后删 stub**:不要"保留 stub 作为 fallback"——会让代码永远不干净
5. **git commit 单独提交**:替换 commit 和功能 commit 分开,方便 bisect

工业级项目用 issue tracker 跟踪 stub。GitHub issue 标 `tech-debt` 标签,每周扫一次。Casey 在 HH 单人项目用注释跟踪(`// TODO: replace with HHT-based loader`)。两种方式都行,关键是**别让 stub 永驻**。

## 2 · 心智模型

### 类比:工具箱的"螺丝刀多件套"

你有一个工具箱,里面有 5 把螺丝刀:十字、一字、六角、梅花、Torx。每把都能拧螺丝,但你每次都要选对的。

如果你能发明一种**万能螺丝刀**——一个手柄,5 种可换头——你只需要一件工具,认知负担减半。

代码统一就是这种"万能螺丝刀"。多种加载路径 = 多把螺丝刀;统一的加载接口 = 一把万能螺丝刀。

### 严谨展开:Asset trait 抽象

Rust 用 trait 抽象多种资产类型:

```rust
// 通用 trait:任何资产都能用同一接口加载
trait Asset: Sized {
    fn load_from_hha(reader: &mut HhaReader) -> Result<Self, AssetError>;
    fn asset_type() -> AssetType;
}

struct Bitmap { /* ... */ }
struct Sound { /* ... */ }
struct Font { /* ... */ }

impl Asset for Bitmap {
    fn load_from_hha(reader: &mut HhaReader) -> Result<Self, AssetError> {
        // 从 HHA 读 bitmap asset
    }
    fn asset_type() -> AssetType { AssetType::Bitmap }
}

impl Asset for Font {
    fn load_from_hha(reader: &mut HhaReader) -> Result<Self, AssetError> {
        // 从 HHA 读 font asset(PNG 像素 + glyph metrics)
    }
    fn asset_type() -> AssetType { AssetType::Font }
}

// 统一的加载入口
fn load_asset<T: Asset>(id: AssetId) -> Result<T, AssetError> {
    let mut reader = open_hha(id.hha_file)?;
    reader.seek(id.offset)?;
    T::load_from_hha(&mut reader)
}
```

调用:`let font: Font = load_asset(font_id)?;`

不管 Font 还是 Bitmap,调用方式一样。这是 trait 的力量。

#### 用 trait 抽象"资产":Rust 的优势

上面那个 `Asset` trait 是 Rust 抽象的标准模式。对比 C++:

```cpp
// C++:用基类 + virtual
class Asset {
public:
    virtual ~Asset() = default;
    virtual AssetType type() const = 0;
    virtual void load_from_hha(HhaReader& reader) = 0;
};

class Font : public Asset {
public:
    AssetType type() const override { return AssetType::Font; }
    void load_from_hha(HhaReader& reader) override { /* ... */ }
};
```

C++ 用 virtual function(虚函数),有 vtable 开销(每个对象多 8 字节指针 + 每次调用间接寻址)。Rust 的 trait 默认是静态分发(compile-time dispatch),零开销。

具体区别:

```rust
// 静态分发(默认):零开销,编译期确定
fn load_asset<T: Asset>(id: AssetId) -> Result<T, AssetError> { ... }

// 动态分发:类似 C++ virtual,有 vtable 开销
fn load_asset_dyn(id: AssetId) -> Result<Box<dyn Asset>, AssetError> { ... }
```

Rust 让你**选择**:
- 静态分发(`T: Asset`):性能好,但每种类型 monomorphize(代码膨胀)
- 动态分发(`dyn Asset`):代码小,但 vtable 开销

工业级 Rust 资产系统常用混合策略:对外接口用静态分发(性能关键路径),内部存储用动态分发(集合异质资产)。Bevy 的 `Asset` trait 就是这种设计。

Casey 在 HH C 里手动实现 vtable(struct + function pointers),代码冗长。Rust 的 trait 把这一切自动化,且编译期检查类型安全。这是 Rust 适合做游戏引擎的核心原因之一。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏引擎的"资产类型"通常用面向对象(基类 Asset)或 ECS(component)抽象。Unreal 用 `UObject` 基类,Unity 用 `UnityEngine.Object`。Casey 在 HH 用 C 风格(`enum AssetType` + tagged union),Rust 翻译用 trait + generic 更优雅。

#### 工业级资产系统的演进

让我把游戏引擎资产系统的演进讲清楚:

**第一代(1990s)**:每类资产硬编码。Final Fantasy 7 的字段、角色、音效用三套完全独立的格式和加载代码。代码混乱但能跑。

**第二代(2000s)**:面向对象抽象。Unreal Engine 2 引入 `UObject` 基类,所有资产继承。统一接口但 vtable 开销大。

**第三代(2010s)**:数据驱动 + ECS。Unity 和 Unreal 都转向"资产是数据,组件是数据,代码是 system"。资产加载变成"读数据 + 注册 component"。

**第四代(2020s)**:无引擎,直接用 ECS + 序列化。Bevy 用 `Assets<T>` 资源,任何类型自动获得资产管理。Casey 的 HH 走的是"自己造第四代"路线——他的 HHA 是序列化,ECS 是 entity system。

你的 Rust 项目应该用 Bevy 风格的资产管理。如果不用 Bevy,自己实现也很简单:

```rust
struct AssetStore {
    bitmaps: HashMap<AssetId, Bitmap>,
    sounds: HashMap<AssetId, Sound>,
    fonts: HashMap<AssetId, Font>,
}

impl AssetStore {
    fn load<T: Asset>(&mut self, id: AssetId) -> &T {
        // 根据 T 类型路由到对应 HashMap
    }
}
```

这种"中央 store + 类型路由"是工业级资产管理的基础模式。Casey 在 HH 手写,你用 Rust trait 自动化。

### 3.2 · 图形学视角

GPU 资源管理也用"统一接口":纹理、buffer、shader 都是 GPU resource,有同样的生命周期(create → use → destroy)。Vulkan、DirectX 12、Metal 都用类似的 API。

### 3.3 · Linux 系统编程视角

Linux 内核的 `file_operations` 结构是统一的"文件"接口——普通文件、设备、socket、pipe 都实现它。`open`/`read`/`write`/`close` 对所有"文件"通用。这是 Unix 哲学:"一切皆文件"。

Casey 的资产系统统一,本质是同样的设计哲学。

### 3.4 · Rust 生态视角

Rust 的 trait + generic 让"统一接口"自然且高效:

- 静态分发(monomorphization):编译期生成特化代码,零运行时开销
- 动态分发(trait object `dyn Trait`):运行时多态,有 vtable 开销

游戏开发常用静态分发——性能优先。Bevy ECS 用 trait + 复杂的类型擦除实现"任何组件都通用"。

## 4 · 认知地图

### 4.1 上级

- **统一架构** —— 同一模式处理多种类型
- **抽象** —— 隐藏细节,暴露接口
- **代码简化** —— 减少特殊情况

### 4.2 同级

| 方案 | 描述 | 何时用 |
|---|---|---|
| trait + generic | Rust 风格 | 推荐方案 |
| tagged union | C/C++ 风格 | 跨平台 |
| inheritance | OOP 风格 | C#/Java |
| type-erased `dyn` | 运行时多态 | 不推荐(性能) |

### 4.3 下级

- **Asset trait** —— 统一加载接口
- **AssetType enum** —— 资产种类标识
- **HHA reader** —— 通用二进制读取器
- **special case elimination** —— 特殊情况消除

### 4.4 单元测试策略

统一架构后,测试变得简单:所有资产类型走同样的接口,你可以写**通用测试模板**:

```rust
#[test]
fn test_asset_load_round_trip<T: Asset + PartialEq + Debug>() {
    let original = T::sample();
    let mut writer = HhaWriter::new(Vec::new());
    original.serialize(&mut writer);
    
    let bytes = writer.into_inner();
    let mut reader = HhaReader::new(&bytes);
    let loaded = T::load_from_hha(&mut reader).unwrap();
    
    assert_eq!(original, loaded);
}

// 用 macro 为每种资产类型生成测试
macro_rules! test_asset {
    ($t:ty) => {
        #[test]
        fn test_round_trip() { test_asset_load_round_trip::<$t>(); }
    };
}

test_asset!(Bitmap);
test_asset!(Sound);
test_asset!(Font);
```

这就是统一架构的"复利"——一次设计,后续所有资产类型自动受益。如果 Casey 不做 Day 532,每种资产要写一份独立测试,代码量翻 3 倍。

## 5 · 对照与变奏

不同语言/框架的"统一资产接口":

- **Rust + Bevy**:Asset trait + ECS component
- **C++ + Unreal**:UObject 基类 + smart pointer
- **C# + Unity**:UnityEngine.Object + ScriptableObject
- **C + HH**:tagged union + 函数指针

每种实现有自己的约束(ownership、GC、内存安全),但概念一致。

### "Refactor for consistency" vs "Refactor for performance"

工业级 refactor 分两类,你应该能区分:

**Refactor for consistency**(本日):目标是消除特殊情况,让代码模式统一。性能可能不变,甚至略变差(因为加了抽象层)。但可读性、可维护性提升。

**Refactor for performance**:目标是让代码更快。可能引入特殊情况(如"热路径用 specialized 代码,冷路径用通用代码"),可读性下降。但性能提升。

新手常犯的错误:**混淆两种 refactor**。比如一致性重构后,你说"为什么性能没变?"——那是因为目标本就不是性能。或者性能重构后,你说"为什么代码变难读了?"——那是因为你牺牲了可读性换性能。

正确做法:**明确 refactor 的目标,衡量对应指标**。一致性 refactor 衡量"代码行数 / 特殊情况数 / 测试覆盖率";性能 refactor 衡量"benchmark / frame time / 内存峰值"。两者各做各的,不混淆。

Casey 的 Day 532 是 refactor for consistency。后续 Day 555+(GPU 性能优化)是 refactor for performance。学会区分,你才能正确做计划。

**题**:Casey 删除了 BMP 字体加载路径。为什么不"以防万一"保留?

**参考解答**:保留死代码有四个危害。第一,**认知负担**——新开发者读到 BMP 路径会问"这还在用吗?",浪费时间。第二,**测试负担**——BMP 路径如果有 bug,修不修?测不测?第三,**编译时间**——多余的代码增加编译时间。第四,**误用风险**——某天有人误以为 BMP 还在用,调用了它,引入 bug。"以防万一"听起来稳妥,实际是技术债。删除死代码是好习惯。

### Lv2 · 动手实践

**题**:用 Rust trait 设计一个统一的 Asset 加载接口。给 Bitmap、Sound、Font 三个具体实现。写一个测试,创建一个假 HHA(包含三种资产),用统一接口加载它们。运行后:打印每个资产的元数据。

**参考解答**:

```rust
#[derive(Debug, Clone, Copy, PartialEq)]
enum AssetType { Bitmap, Sound, Font }

#[derive(Debug)]
enum AssetError {
    NotFound,
    FormatError(String),
}

trait Asset: Sized {
    fn asset_type() -> AssetType;
    fn load(bytes: &[u8]) -> Result<Self, AssetError>;
}

#[derive(Debug)]
struct Bitmap { width: u32, height: u32, pixels: Vec<u8> }
impl Asset for Bitmap {
    fn asset_type() -> AssetType { AssetType::Bitmap }
    fn load(bytes: &[u8]) -> Result<Self, AssetError> {
        // 假设 bytes = [width:4][height:4][pixels]
        if bytes.len() < 8 { return Err(AssetError::FormatError("too short".into())); }
        let width = u32::from_le_bytes(bytes[0..4].try_into().unwrap());
        let height = u32::from_le_bytes(bytes[4..8].try_into().unwrap());
        let pixels = bytes[8..].to_vec();
        Ok(Bitmap { width, height, pixels })
    }
}

#[derive(Debug)]
struct Sound { sample_rate: u32, samples: Vec<i16> }
impl Asset for Sound {
    fn asset_type() -> AssetType { AssetType::Sound }
    fn load(bytes: &[u8]) -> Result<Self, AssetError> {
        if bytes.len() < 4 { return Err(AssetError::FormatError("too short".into())); }
        let sample_rate = u32::from_le_bytes(bytes[0..4].try_into().unwrap());
        let samples: Vec<i16> = bytes[4..]
            .chunks_exact(2)
            .map(|c| i16::from_le_bytes([c[0], c[1]]))
            .collect();
        Ok(Sound { sample_rate, samples })
    }
}

#[derive(Debug)]
struct Font { size: u32, glyph_count: u32 }
impl Asset for Font {
    fn asset_type() -> AssetType { AssetType::Font }
    fn load(bytes: &[u8]) -> Result<Self, AssetError> {
        if bytes.len() < 8 { return Err(AssetError::FormatError("too short".into())); }
        let size = u32::from_le_bytes(bytes[0..4].try_into().unwrap());
        let glyph_count = u32::from_le_bytes(bytes[4..8].try_into().unwrap());
        Ok(Font { size, glyph_count })
    }
}

fn load_asset<T: Asset>(bytes: &[u8]) -> Result<T, AssetError> {
    T::load(bytes)
}

fn main() {
    // 假 HHA:三个资产的字节序列
    let bitmap_bytes = {
        let mut v = Vec::new();
        v.extend_from_slice(&8u32.to_le_bytes());   // width
        v.extend_from_slice(&8u32.to_le_bytes());   // height
        v.extend_from_slice(&[255, 0, 0].repeat(64));  // 64 pixels
        v
    };
    let sound_bytes = {
        let mut v = Vec::new();
        v.extend_from_slice(&44100u32.to_le_bytes());  // sample_rate
        for i in 0..10 {
            v.extend_from_slice(&(i * 100).to_le_bytes());
        }
        v
    };
    let font_bytes = {
        let mut v = Vec::new();
        v.extend_from_slice(&32u32.to_le_bytes());  // size
        v.extend_from_slice(&94u32.to_le_bytes());  // glyph_count (ASCII 可打印)
        v
    };
    
    // 用统一接口加载
    let bitmap: Bitmap = load_asset(&bitmap_bytes).unwrap();
    let sound: Sound = load_asset(&sound_bytes).unwrap();
    let font: Font = load_asset(&font_bytes).unwrap();
    
    println!("Bitmap: {}x{}, {} bytes", bitmap.width, bitmap.height, bitmap.pixels.len());
    println!("Sound: {} Hz, {} samples", sound.sample_rate, sound.samples.len());
    println!("Font: size={}, glyphs={}", font.size, font.glyph_count);
}
```

为什么这么写:trait + generic 是 Rust 表达多态的标准方式。`load_asset::<T>` 的 `T` 在调用时根据赋值目标推断(`let bitmap: Bitmap = load_asset(...)` 隐式指定 T=Bitmap)。`try_into().unwrap()` 把 `&[u8]` 转成 `[u8; 4]`,这是固定大小数组的转换。

```rust
// 完整的资产系统骨架(参考 Bevy 风格但极简)

use std::collections::HashMap;
use std::sync::Arc;

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct AssetId(pub u64);

#[derive(Debug)]
pub enum AssetError {
    NotFound(AssetId),
    TypeMismatch,
    IoError(String),
}

pub trait Asset: std::fmt::Debug + Send + Sync + 'static {
    fn asset_type_name() -> &'static str;
}

#[derive(Debug)]
pub struct BitmapAsset {
    pub width: u32,
    pub height: u32,
    pub pixels: Arc<[u8]>,  // 共享所有权,避免拷贝
}
impl Asset for BitmapAsset {
    fn asset_type_name() -> &'static str { "Bitmap" }
}

#[derive(Debug)]
pub struct FontAsset {
    pub size: u32,
    pub atlas: Arc<[u8]>,
    pub glyph_count: u32,
}
impl Asset for FontAsset {
    fn asset_type_name() -> &'static str { "Font" }
}

/// 资产注册表:统一存储所有已加载资产
pub struct AssetRegistry {
    assets: HashMap<AssetId, Box<dyn std::any::Any + Send + Sync>>,
}

impl AssetRegistry {
    pub fn new() -> Self {
        Self { assets: HashMap::new() }
    }
    
    pub fn insert<T: Asset + 'static>(&mut self, id: AssetId, asset: T) {
        self.assets.insert(id, Box::new(asset));
    }
    
    pub fn get<T: Asset + 'static>(&self, id: AssetId) -> Result<&T, AssetError> {
        self.assets
            .get(&id)
            .ok_or(AssetError::NotFound(id))?
            .downcast_ref::<T>()
            .ok_or(AssetError::TypeMismatch)
    }
}

fn main() {
    let mut registry = AssetRegistry::new();
    
    // 创建几个资产
    let bitmap = BitmapAsset {
        width: 8, height: 8,
        pixels: Arc::from(vec![255u8; 8*8*3].into_boxed_slice()),
    };
    let font = FontAsset {
        size: 32,
        atlas: Arc::from(vec![0u8; 512*512].into_boxed_slice()),
        glyph_count: 94,
    };
    
    // 注册
    registry.insert(AssetId(1), bitmap);
    registry.insert(AssetId(2), font);
    
    // 用统一接口取出
    let b: &BitmapAsset = registry.get(AssetId(1)).unwrap();
    let f: &FontAsset = registry.get(AssetId(2)).unwrap();
    
    println!("{}: {}x{} {} bytes", BitmapAsset::asset_type_name(), b.width, b.height, b.pixels.len());
    println!("{}: size={} glyphs={}", FontAsset::asset_type_name(), f.size, f.glyph_count);
    
    // 类型错误会失败
    let result: Result<&FontAsset, _> = registry.get(AssetId(1));  // ID 1 是 Bitmap
    match result {
        Ok(_) => println!("不应该到这里"),
        Err(AssetError::TypeMismatch) => println!("正确:类型不匹配"),
        Err(e) => println!("其他错误: {:?}", e),
    }
}
```

出错怎么办:

- **`error: trait object cannot have generic`**:`dyn Trait<T>` 不允许,要么用 generic(`fn foo<T: Trait>(x: &T)`),要么用 `Box<dyn Trait>` 不带 generic。
- **`downcast_ref returns None`**:类型不对。注册时是 `BitmapAsset`,取出时写成 `FontAsset` 就 None。
- **`Send + Sync` 报错**:资产里有非线程安全的字段(如 `Rc<RefCell<T>>`)。改用 `Arc<Mutex<T>>` 或 `Arc<[T]>`。
