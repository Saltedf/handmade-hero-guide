
# Day 471 · 完全分离渲染器(第二部分)

> Day 470 把 Render Group 的"骨架"立起来了,但还有一半的 game code 在直接调 OpenGL。Day 471 是"扫尾"——把剩下所有 draw 调用迁移到 push 模式,并写第一个真正的 renderer 后端,把 group 解释成 OpenGL 命令。

## 0 · 为什么要有这一天

重构有两条路:一是"大爆炸",一个周末把所有代码全推倒重写;二是"渐进",一次只动一个模块,每动一步都能跑。Casey 永远选第二条。

Day 470 做的事是建好了 `Render Group` 这个新家,Day 471 做的事是把家具一件件从旧家(直接 OpenGL 调用)搬到新家。**搬的过程必须保证每搬一件,游戏都能正常跑**——否则你搬完才发现"咦小人不见了",根本不知道是哪一步搞坏的。

这种工程方法论有个名字叫 **"Strangler Fig Pattern"**(绞杀者模式),Martin Fowler 提的。名字来自热带雨林里的一种树——绞杀榕种子落在另一棵树上,慢慢长出根把宿主包围,最后宿主死亡,绞杀榕自立门户。代码重构也是这样:新系统慢慢生长,旧系统逐步退场,中间始终可运行。

为什么这件事必须分两天?因为如果一天搞完,改动太大,出 bug 难定位;如果分得太细(比如十天),每天改动太小,看不出进度。两天是个甜区——Day 470 立骨架,Day 471 迁完剩余 + 接通后端。

完成这一天之后,你具备了:

- 把"立即渲染"代码渐进迁移到"命令缓冲"代码的实操经验
- 写"解释器"的能力——把抽象命令翻译成具体 API 调用
- 理解为什么"Strangler Fig"比"Big Bang Rewrite"安全

## 1 · Casey 今天做了什么

Casey 这一天的动作分四步:

第一步,他列出 game code 里所有还在直接调 OpenGL 的地方。一查发现 20+ 处:画 hero sprite、画怪物、画地面 tile、画粒子、画 UI 文字、画 debug overlay。每处都需要替换。

第二步,他为每种用途写对应的 `Push` 函数:`PushBitmap`、`PushRect`、`PushText`(后者内部循环调 PushBitmap,每个字符一个)、`PushCoordinateSystem`(用于 3D 渲染时的变换矩阵边界)。这些函数都是同样的模式:把 entry header + payload 序列化进 group buffer。

第三步,他写 `RenderGroupToOutput(group, renderer)`。这个函数遍历 group 的所有 entry,根据 type 调对应的 OpenGL 函数:`glBindTexture`、`glDrawArrays`、`glUniform4f` 等。这就是把"抽象命令"翻译成"具体 GL 调用"的**解释器**。

第四步,他逐处替换 game code 的直接 GL 调用,每替换一处就跑一遍游戏验证。最后跑一遍,确认游戏画面和重构前完全一样——这就是 **"behavior-preserving refactoring"**(保持行为不变的重构),Martin Fowler 在《Refactoring》里定义的核心原则。

## 2 · 心智模型

### 类比:从汇编到解释器

想象你写了个计算器,最初版本是直接调 CPU 指令——你输入 `2 + 3`,代码翻译成 `mov eax, 2; add eax, 3`。这能跑,但你要换 CPU 架构(从 x86 到 ARM)就得全改。

后来你设计了**字节码**:你输入 `2 + 3`,代码先翻译成字节码 `[PUSH 2, PUSH 3, ADD]`,再有个解释器读字节码执行。换 CPU 架构只改解释器,前端代码不动。

Day 470/471 做的事完全对应:**Render Group = 字节码,Renderer 后端 = 解释器**。

为什么这个类比精确?因为本质上**所有"命令缓冲 + 解释器"模式都是同构的**:

| 领域 | 命令缓冲 | 解释器 |
|---|---|---|
| CPU | 机器码 | CPU 硬件 |
| JVM | Java bytecode | JVM |
| 浏览器 | DOM 操作 | 浏览器 layout engine |
| PostScript | PS 命令 | PS 解释器 |
| Vulkan | command buffer | GPU driver |
| Casey | Render Group | OpenGL renderer |

理解了这一层,你看任何"分层架构"都能秒懂:上层产生抽象命令,下层解释命令。中间的命令格式就是两层的**契约**(contract)。

### 解释器的结构

`RenderGroupToOutput` 解释器的核心是个循环:

```
for entry in group.entries:
    match entry.type:
        Bitmap => {
            glBindTexture(GL_TEXTURE_2D, entry.bitmap_id);
            glUniform4f(color_loc, entry.color);
            setup_quad_vertices(entry.x, entry.y);
            glDrawArrays(GL_TRIANGLES, 0, 6);
        }
        Rectangle => {
            glBindTexture(GL_TEXTURE_2D, white_texture);
            glUniform4f(color_loc, entry.color);
            setup_quad_vertices(entry.x, entry.y, entry.w, entry.h);
            glDrawArrays(GL_TRIANGLES, 0, 6);
        }
        ...
```

注意一个关键点:**每个 entry 都触发一次 glDrawArrays**。这是 Day 470/471 的"过渡状态"——技术上已经分离了,但性能没改善,因为还是每个 bitmap 一个 draw call。Day 477 的单 dispatch 优化才真正解决这个问题(把所有 entry 收集成一个大 vertex buffer,一次画完)。

所以 Day 471 的价值不在性能,而在**架构清晰度**——分离这件事做完了,后面所有优化(状态排序、单 dispatch、instancing)才有空间下手。

### Entry 序列化的细节

Casey 用 C 写 entry 序列化时,做了几个值得注意的工程决策:

**第一,变长 entry,固定 header**。每条 entry 都以 `RenderEntryHeader` 开头,header 里有 `type` 和 `size`。这样遍历时知道每条多长,可以跳过。Rust 等价:

```rust
#[repr(C)]
struct RenderEntryHeader {
    entry_type: u32,
    size: u32,  // 包括 header
}
```

**第二,payload 紧跟 header**。Bitmap 的 payload 是 `BitmapPayload`,紧跟在 header 后面。解析时拿到 header 指针 +8 字节就是 payload 指针。

**第三,不存指针,只存 ID**。`bitmap_id` 是个 u32,不是 `&Bitmap`。原因:group 可能跨帧使用、跨线程使用,指针会失效。ID 看起来抽象,但 renderer 后端有 ID → 实际纹理的映射表,可以稳定解析。这是工业系统里常见的 **"handle" 模式**——用整数 ID 替代指针,避免悬挂引用。

**第四,frame 结束统一 reset group buffer**。Group 在 arena 上分配,frame 结束 arena.reset(),所有 entry 一起释放。零分配开销。

### 为什么这个抽象是对的

抽象好坏的判断标准:**它能让你在不改变调用方的情况下替换实现**。Render Group 满足这个标准,因为:

1. Game code 调 `PushBitmap(group, ...)`,完全不知道 group 怎么实现
2. Group 的实现可以变(Vec 改成 arena、改成 mmap 共享内存),game code 不动
3. Renderer 后端可以变(OpenGL → Vulkan → 软渲染),game code 不动
4. Push 函数的签名可以保持稳定,内部数据结构随便改

反面例子:**直接调 OpenGL 的代码无法替换实现**。你想换 Vulkan?得改 game code 几百处。这就是抽象失败了。

Casey 在 Day 471 反复强调这件事:他不在乎 Render Group 当前的性能(因为还没优化),他在乎的是**架构打开了未来的可能性**。一旦架构对了,优化是几天的活;架构错了,优化要先重构,代价是几周。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业游戏引擎里的"渲染层抽象"层级一般是这样:

```
Game Code (高层数据:entity、material、camera)
    ↓
Scene Graph / Render Queue (中间表示:要画什么)
    ↓
Render Hardware Interface (跨平台抽象:OpenGL/Vulkan/Metal/D3D)
    ↓
Native Graphics API (具体平台:OpenGL/Vulkan/...)
```

Casey 的 Day 470/471 把前两层做出来了:Render Group 就是 Scene Graph 的简化版(没有树结构,只有线性命令),`RenderGroupToOutput` 就是 RHI 的雏形。后面 Day 475 他会进一步把 RHI 抽象成 trait,允许 OpenGL 和软渲染并存。

商业引擎(Unreal、Unity)在这一层做得更复杂——他们要支持很多平台、很多渲染特性(forward / deferred / hybrid)、很多 shader 变体。这些复杂度对 HH 来说没必要,但**核心抽象思想是一样的**。

游戏开发里有个有趣的细节:**debug 渲染**和**正式渲染**通常用不同的 Render Group。Debug overlay(帧率、hit box、AI 路径)画在正式场景之上,不参与深度测试。Casey 在 Day 490 合并 debug UI 时会处理这种事。

### 3.2 · 🎨 图形学视角

从图形学角度,Day 471 的解释器模式有一个隐藏的优化机会:**状态缓存(state caching)**。每个 `glBindTexture`、`glUseProgram` 调用即使数据没变也有开销——driver 要检查状态机。解释器可以缓存"上一次绑定的纹理 ID",如果新 entry 的纹理和上次一样,跳过 bind 调用。

这就是 Casey 后面 Day 477 单 dispatch 优化的前置概念之一。当前 Day 471 的解释器没做这个缓存(因为还没必要),但**架构允许后面加**——这也是 Render Group 抽象的价值之一。

另一个图形学要点:**vertex 数据的组织**。Casey 当前是每个 entry 即时生成 quad 顶点(6 个顶点构成两个三角形),上传到 GPU 一次画完。这是 immediate quad rendering 的做法。Day 477 之后会改成**预生成大 vertex buffer**,把所有 entry 的 quad 拼到一起,一次性上传,一次性画。

图形学里管前者叫 "per-draw vertex submission",后者叫 "batched vertex submission"。后者在所有现代 GPU 上性能好 5-10 倍,因为 PCIe 传输是瓶颈。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的图形栈本身就是一个"双层解释器"系统:

```
App (用 OpenGL / Vulkan API)
    ↓ Mesa 把 API 调用翻译成
DRM command buffer (ioctl 提交)
    ↓ 内核 DRM 子系统排队
GPU driver command ring buffer
    ↓ GPU 硬件解释执行
```

每一层都是"命令 + 解释器"。Casey 在用户态做的 Render Group 就是 Mesa 在用户态做的事的迷你版。

Linux 上你能在两个地方观察这个过程:

第一,**Mesa 源码**。`mesa/src/gallium/` 是 Gallium3D 抽象层,定义了 pipe context 接口(`draw_vbo`、`set_constant_buffer` 等),和 Casey 的 Renderer trait 概念上一样。Mesa 把 OpenGL 调用翻译成 Gallium 调用,Gallium 后端(radeonsi、iris、nvc0)再把 Gallium 调用翻译成 DRM 命令。**三层翻译**。

第二,**ioctl trace**。用 `apitrace`(开源工具)录制一个 OpenGL 程序,你能看到所有 GL 调用序列化成 trace 文件,可以重放、diff、统计。这本质上就是 Render Group 的"序列化版本"——证明了"命令缓冲"是 OpenGL 的天然中间表示。

```bash
# Arch 上装 apitrace
pacman -S apitrace

# 录制
apitrace trace ./my_game
# 生成 my_game.trace 文件

# 查看
qapitrace my_game.trace
# GUI 里能看到每帧的 GL 调用、参数、耗时

# 统计 draw call 数
apitrace report my_game.trace | grep -c draw
```

`qapitrace` 是个超棒的工具——你不仅能看 trace,还能改 trace 后重放,看效果。这是工业调试 OpenGL 问题的标准方式。

### 3.4 · 🦀 Rust 生态视角

Rust 在写解释器时有几个特别的优势。

第一,**enum + match 是写解释器的范式**。C 里写解释器要用 tagged union:

```c
struct Entry {
    int type;
    union {
        BitmapEntry bitmap;
        RectEntry rect;
    } u;
};

switch (entry->type) {
    case ENTRY_BITMAP: draw_bitmap(&entry->u.bitmap); break;
    case ENTRY_RECT:   draw_rect(&entry->u.rect);     break;
    // 漏了 default 就 UB
}
```

Rust 用 enum:

```rust
enum Entry {
    Bitmap(BitmapEntry),
    Rect(RectEntry),
}

match entry {
    Entry::Bitmap(b) => draw_bitmap(b),
    Entry::Rect(r) => draw_rect(r),
    // 编译器强制 exhaustive
}
```

不仅类型安全,而且添加新 variant 时编译器会在所有 match 处提示你补 case。这是 C 写解释器难以企及的工程红利。

第二,**`bytemuck` / `zerocopy` crate** 做零拷贝字节转换。Casey 在 C 里直接 cast 字节到 struct 指针(`(BitmapPayload*)(bytes + offset)`),依赖 C 的宽松内存模型。Rust 不能这么干——strict aliasing rules。`bytemuck::from_bytes::<T>(slice)` 是 safe 等价,编译时检查 T 是 Pod。

第三,**`trait` 表达 renderer 接口**。Day 475 会展开讲。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Interpreter Pattern**(设计模式)—— 定义一种语言,再写解释器执行它
- **Strangler Fig Pattern** —— 渐进式替换旧系统
- **Behavior-Preserving Refactoring** —— 重构不改变可观察行为

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Big Bang Rewrite | 一次性全换 | 时间允许 + 团队小 | 否 |
| Strangler Fig(本日) | 渐进迁移,始终可跑 | 大型系统、长期演化 | 是 |
| Branch & Merge | 新代码在新分支,验证后合 | 实验性重构 | 否 |
| Parallel Run | 新旧并存运行,对比结果 | 关键系统、要求零停机 | 否 |

### 4.3 下级(内部零件)

- **Push API** —— game code 入口,产生 entry
- **Entry header** —— type + size,让遍历知道边界
- **Entry payload** —— 各类型的具体数据
- **Interpreter loop** —— 遍历 entry + match type + 调后端
- **Backend dispatch** —— OpenGL/Vulkan/软渲染的具体调用

## 5 · 对照与变奏

Casey 在 Day 470/471 走的"Render Group + 解释器"模式,在不同领域有不同的对应物:

**CPU 设计**:汇编指令就是 entry,decoder 是解释器。现代 CPU 内部把 x86 指令解码成 μops(micro-ops),μops 才是真正执行的——这是"双层解释器",和 Mesa/DRM 双层对应。

**数据库**:SQL 是声明式查询,query planner 把它翻译成执行计划(execution plan),executor 解释执行。Day 471 的 `RenderGroupToOutput` 就是数据库的 executor。

**浏览器**:HTML/CSS 是声明,浏览器 parse 成 DOM/CSSOM,layout engine 解释渲染。和 Casey 的模式完全同构。

**编译器**:AST 是中间表示,codegen 把 AST 翻译成目标机器码。Casey 的 Render Group 就是 AST 的简化版(线性而非树形)。

理解这种结构同构性的价值:**你学一个领域,等于学所有领域**。Day 471 学的不只是游戏渲染,是计算机系统里反复出现的核心模式。

另一个对照:**手写 vs 工具生成**。Casey 手写 Render Group 和解释器。工业界有工具自动生成——比如 gRPC 用 Protocol Buffers 定义消息格式,自动生成序列化代码。Casey 没用这种工具,因为他的 entry 类型只有几种,手写比代码生成简单。但理解这种取舍很重要:**复杂度上去了就该上工具**。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:扩展 Day 470 的 Render Group,加入 `PushText(text: &str, x: f32, y: f32)` 命令——内部循环字符,每个字符 push 一个 Bitmap entry(bitmap_id 用字符 ASCII 码假装)。然后写解释器 `interpret(group)`,打印每个 entry 的处理动作。

完成标准:`cargo run` 输出包含每个字符的 bitmap draw 调用,且 PushText 一行能产生多个 entry。

**参考解答**:

```rust
// RenderEntry 复用 Day 470 的定义
#[derive(Debug)]
enum RenderEntry {
    Bitmap { bitmap_id: u32, x: f32, y: f32 },
}

struct RenderGroup {
    entries: Vec<RenderEntry>,
}

impl RenderGroup {
    fn new() -> Self { Self { entries: Vec::new() } }

    fn push_bitmap(&mut self, id: u32, x: f32, y: f32) {
        self.entries.push(RenderEntry::Bitmap { bitmap_id: id, x, y });
    }

    // PushText:把字符串拆字符,每个字符 push 一个 bitmap
    // 字符 ASCII 当 bitmap_id,假装每个字符有一张预渲染纹理
    fn push_text(&mut self, text: &str, x: f32, y: f32) {
        let mut cur_x = x;
        for ch in text.chars() {
            let id = ch as u32;            // 字符编码当 ID
            self.push_bitmap(id, cur_x, y);
            cur_x += 8.0;                  // 假装每个字符宽 8 像素
        }
    }
}

// 解释器:遍历 entry,模拟 OpenGL 调用
fn interpret(group: &RenderGroup) {
    println!("Rendering {} entries:", group.entries.len());
    for (i, entry) in group.entries.iter().enumerate() {
        match entry {
            RenderEntry::Bitmap { bitmap_id, x, y } => {
                // 模拟 OpenGL 调用
                println!("  [{}] glBindTexture(GL_TEXTURE_2D, {});", i, bitmap_id);
                println!("       draw_quad at ({}, {});", x, y);
            }
        }
    }
}

fn main() {
    let mut group = RenderGroup::new();
    group.push_text("Hello", 10.0, 20.0);
    group.push_text("World", 10.0, 30.0);
    interpret(&group);
}
```

为什么这么写:`push_text` 内部不直接产生新 entry 类型,而是循环调 `push_bitmap`——这就是 **"高层 API 在低层 API 之上构建"** 的范式。你可以继续叠:`push_button` 调 `push_text` + `push_rect`,`push_window` 调多个 `push_button`。每一层都是抽象的累积。

### Lv3 · 迁移设计(换场景用同一原理)

**题**:用"Render Group + 解释器"模式做一个**网络消息系统**。设计 `NetMessageGroup` 客户端 push 命令(Send、Broadcast、Subscribe),`interpret` 函数把这些命令翻译成 TCP `send()` 调用。要求:命令先 push 到 group,frame 末统一 flush,这样能把多个小消息合并成一个大包发送(Nagle 算法的应用层版本)。

**提示**:想想"批处理"在网络上意味着什么。一个 100 字节的小消息走 TCP 单独 send,header 开销 40 字节(TCP+IP),效率 71%。如果把 100 个小消息拼成 10000 字节一次发,效率 99%。

```rust
use std::fmt;

// Entry type
#[repr(u32)]
#[derive(Debug, Clone, Copy, PartialEq)]
enum EntryType {
    Bitmap = 1,
    Rect = 2,
    Clear = 3,
    CoordSystem = 4,
}

// 所有 entry 的 enum(Rust idiom,对应 C 的 tagged union)
#[derive(Debug)]
enum Entry {
    Bitmap {
        bitmap_id: u32,
        x: f32, y: f32,
        color: [f32; 4],
    },
    Rect {
        x: f32, y: f32, w: f32, h: f32,
        color: [f32; 4],
    },
    Clear {
        color: [f32; 4],
    },
    CoordSystem {
        // 用于 3D,标记变换矩阵边界
        matrix: [[f32; 4]; 4],
    },
}

// Render Group
struct RenderGroup {
    entries: Vec<Entry>,
    // 后续 Day 473 会加 camera、clip rect 等 metadata
}

impl RenderGroup {
    fn new() -> Self { Self { entries: Vec::new() } }

    // 各种 Push 函数:game code 的入口
    fn push_bitmap(&mut self, id: u32, x: f32, y: f32, color: [f32; 4]) {
        self.entries.push(Entry::Bitmap { bitmap_id: id, x, y, color });
    }

    fn push_rect(&mut self, x: f32, y: f32, w: f32, h: f32, color: [f32; 4]) {
        self.entries.push(Entry::Rect { x, y, w, h, color });
    }

    fn push_clear(&mut self, color: [f32; 4]) {
        // clear 通常放在 entries 开头
        self.entries.insert(0, Entry::Clear { color });
    }

    fn push_text(&mut self, text: &str, x: f32, y: f32) {
        let mut cx = x;
        for ch in text.chars() {
            self.push_bitmap(ch as u32, cx, y, [1.0; 4]);
            cx += 8.0;
        }
    }
}

// Renderer trait:解释器的接口
trait Renderer {
    fn submit(&mut self, group: &RenderGroup);
}

// OpenGL 后端(假装)
struct OpenGlRenderer {
    // 状态缓存:记录上一次绑定的纹理,避免重复 bind
    last_texture: u32,
    draw_call_count: u32,        // 统计 draw call 数,debug 用
}

impl OpenGlRenderer {
    fn new() -> Self { Self { last_texture: 0, draw_call_count: 0 } }
}

impl Renderer for OpenGlRenderer {
    fn submit(&mut self, group: &RenderGroup) {
        // 解释器核心循环
        for entry in &group.entries {
            match entry {
                Entry::Clear { color } => {
                    println!("glClearColor({}, {}, {}, {})",
                             color[0], color[1], color[2], color[3]);
                    println!("glClear(GL_COLOR_BUFFER_BIT)");
                }
                Entry::Bitmap { bitmap_id, x, y, color } => {
                    // 状态缓存:只在纹理变化时 bind
                    if self.last_texture != *bitmap_id {
                        println!("glBindTexture(GL_TEXTURE_2D, {})", bitmap_id);
                        self.last_texture = *bitmap_id;
                    }
                    println!("glUniform4f(color, {:?})", color);
                    println!("glDrawArrays at ({}, {})", x, y);
                    self.draw_call_count += 1;
                }
                Entry::Rect { x, y, w, h, color } => {
                    // rect 用纯色特殊纹理
                    if self.last_texture != u32::MAX {
                        println!("glBindTexture(GL_TEXTURE_2D, white_tex)");
                        self.last_texture = u32::MAX;
                    }
                    println!("glUniform4f(color, {:?})", color);
                    println!("glDrawArrays rect at ({},{}) size {}x{}", x, y, w, h);
                    self.draw_call_count += 1;
                }
                Entry::CoordSystem { matrix } => {
                    println!("glUniformMatrix4fv(model_view_proj, {:?})", matrix);
                }
            }
        }
        println!("--- {} draw calls this frame ---", self.draw_call_count);
    }
}

fn main() {
    let mut group = RenderGroup::new();
    // game code 只调 push,完全不知道 OpenGL
    group.push_clear([0.2, 0.3, 0.4, 1.0]);
    group.push_bitmap(1, 100.0, 100.0, [1.0; 4]);
    group.push_bitmap(1, 120.0, 100.0, [1.0; 4]);  // 同纹理,应跳过 bind
    group.push_bitmap(2, 140.0, 100.0, [1.0; 4]);
    group.push_rect(10.0, 10.0, 50.0, 20.0, [1.0, 0.0, 0.0, 1.0]);
    group.push_text("HUD", 5.0, 5.0);

    let mut renderer = OpenGlRenderer::new();
    renderer.submit(&group);
}
```

出错怎么办:

- **`borrow checker: cannot borrow group as mutable`** —— 你在循环里同时持有 group 的引用又想修改。把循环改成先 collect 再修改,或者用 index。
- **`error[E0004]: non-exhaustive patterns`** —— 你的 match 漏了某个 enum variant。编译器会告诉你漏了哪个,加上即可。
- **`stack overflow`** —— 解释器递归过深。Render Group 应该用迭代而不是递归。
