# Day 467 · 游戏代码切到 HHA V1

> Day 465 写了迁移工具,Day 466 写了 dumper。今天 Casey 把游戏代码本身从 V0 切到 V1——这意味着所有 HHA 加载路径(贴图、声音、字体、tag)都要走 V1 reader。如果一切顺利,玩家看不出来;如果有 bug,资产立刻粉屏。

## 0 · 为什么要有这一天

到目前为止,Casey 的游戏代码里有两套 HHA 加载逻辑:旧的 V0 路径(读 null-terminated 字符串、字段宽度不同、没 CRC)和新的 V1 路径。Day 465-466 把迁移工具和 dumper 都做好了,但**游戏运行时还在用 V0**——因为 Casey 还不敢切。切换意味着:

第一,**所有 reader 函数要换签名**。V0 用 `read_string_nt` 读字符串,V1 用 `read_string_lp`。两个函数返回类型都是 `String`,但底层语义不同。游戏代码里凡是有 `read_string` 的地方都要审一遍。

第二,**所有 asset 字段宽度要核对**。V0 的 type_code 是 `u32`,V1 可能改成 `u16`;V0 没有 asset CRC,V1 有。这些差异直接影响 struct layout,一个错位所有 asset 读出来都是垃圾。

第三,**tag 语义要确认**。V0 的 tag 只有 name 字段,V1 可能加了其他元数据。游戏代码依赖 tag 的地方都要改。

这个"切版本"动作在工业界叫**cutover**(切换),是软件升级的高风险时刻。Casey 之所以谨慎,是因为他单人开发,没有 QA 团队兜底。如果切完玩家报告"我的角色变成一团紫色",他得一个人 debug。

**为什么不能 V0 V1 长期共存?** 因为维护双份代码成本太高。每次 V1 加新功能,V0 也要加(否则老玩家用不上),双份代码很快漂移,最终你不知道哪个是"真"代码。所以工程上**切换必须一刀切**:某天 commit 之后,所有人用 V1,V0 路径删除。

完成这一天之后,你具备了:
- 理解"代码切换"为什么是高风险动作,以及如何降低风险
- 知道如何用 `git bisect` 定位"切完之后哪个 commit 引入了 bug"
- 把 V0 reader / V1 reader 用 trait 抽象统一,以后再切 V2 不用动游戏代码

## 1 · Casey 今天做了什么

Casey 这一天的计划是"逐文件切":

第一步,他列出游戏代码里所有读 HHA 的地方(`grep` 找 `ReadHHA`、`LoadHHA`、`GetTag` 等函数调用点),形成清单。

第二步,他逐个把 V0 reader 换成 V1 reader。每次换一个文件,跑一次游戏,看是否正常。如果粉屏,立刻 `git diff` 看改了什么,fix 后继续。

第三步,他遇到一个隐藏 bug:V0 的 `asset_count` 字段在 V1 改了语义(原本是 "asset 总数",V1 改成 "asset 数组占的字节数 / sizeof(asset)")。这个改动 Casey 自己都忘了,切的时候踩了坑,花 20 分钟才想起来。

第四步,他确认游戏从启动到关闭用 V1 跑了一遍,没有异常,然后**删除 V0 reader 代码**——一刀切完成。

这集的核心教训:**切版本不是技术难题,是注意力难题**。所有字段差异你都记得,但记得不完整;一切就出错。所以工程上要靠工具(`git bisect`、dumper、自动化测试)而不是记忆。

## 2 · 心智模型

### 类比:铁路换轨

想象一条铁路从窄轨(1067mm)换成标准轨(1435mm)。你不能"逐步换"——某天某段是窄轨,某段是宽轨,火车没法跑。你必须**一夜之间**把所有铁轨换完,第二天所有火车走新轨。

HHA V0→V1 就是这种切换。**格式就是轨道,游戏代码就是火车**。火车只能跑在一种轨道上,所以轨道必须一刀切。

工业史上的真实案例:俄罗斯铁路的轨距和欧洲不同(1520mm vs 1435mm),跨国火车到边境必须换转向架。这种"双轨共存"成本极高,通常只用在**无法切换**的场景(国界、历史遗留)。软件里我们一般能切换,所以选一刀切。

### 切换的三种策略

**策略 1:Big Bang(大爆炸)** —— 某个 commit 之前所有代码用 V0,之后所有代码用 V1,中间没有过渡。Casey 今天选这个。

优点:简单,代码干净。
缺点:中间 commit 跑不通,如果出 bug 难回滚。

**策略 2:Parallel Run(并行运行)** —— 一段时间内 V0 和 V1 同时加载,游戏对比两边结果,如果不一致报警。一段时间后确认稳定,删除 V0。

优点:风险低,出 bug 立刻知道。
缺点:维护双份代码、双份加载时间。Casey 不选因为他是单人开发,双份太累。

**策略 3:Adapter(适配器)** —— 写一个 V0-to-V1 转换层,游戏只看 V1,但能加载 V0 文件(运行时转换)。

优点:文件级平滑迁移,旧文件不用动。
缺点:每次加载都要转换,性能损失。Casey 在 Day 465 写了离线迁移工具,所以不需要 adapter。

Casey 选策略 1,因为 Day 465 已经把所有 V0 文件离线转成 V1,运行时不需要兼容。

### 字段差异审计

切之前必须列清楚 V0 和 V1 的字段差异。Casey 的差异表(简化):

| 字段 | V0 | V1 | 影响 |
|---|---|---|---|
| magic | "HHA0" | "HHA1" | 改 reader 的 magic 检查 |
| version | u32 = 0 | u32 = 1 | 用于 dispatch |
| string 编码 | null-terminated | length-prefix | 改 read_string |
| type_code 宽度 | u32 | u32(没改) | 无影响 |
| asset CRC | 无 | 有(文件末尾 4 字节) | 多读 4 字节,可选校验 |
| asset_count 语义 | 总数 | 总数(没改) | 无影响 |
| tag 字段 | 只有 name | 加了 value 字段 | tag struct 加字段 |

每个差异都要对应到代码改动。审计这一步**绝不能省**——任何漏掉的字段都会变成运行时 bug。

### 用 trait 抽象统一接口

Rust 的 trait 是降低切换成本的关键。我们可以定义一个 `HhaReader` trait,V0 和 V1 各自实现:

```rust
trait HhaReader {
    fn read_magic(&mut self) -> io::Result<[u8; 4]>;
    fn read_version(&mut self) -> io::Result<u32>;
    fn read_string(&mut self) -> io::Result<String>;
    fn read_asset(&mut self) -> io::Result<Asset>;
}

struct V0Reader<R: Read> { inner: R }
struct V1Reader<R: Read> { inner: R }

impl<R: Read> HhaReader for V0Reader<R> {
    fn read_string(&mut self) -> io::Result<String> {
        // null-terminated
        read_string_nt(&mut self.inner)
    }
    // ...
}

impl<R: Read> HhaReader for V1Reader<R> {
    fn read_string(&mut self) -> io::Result<String> {
        // length-prefix
        read_string_lp(&mut self.inner)
    }
    // ...
}
```

然后游戏代码只依赖 `impl HhaReader`,不关心 V0 还是 V1:

```rust
fn load_tags<R: HhaReader>(reader: &mut R, count: u32) -> io::Result<Vec<Tag>> {
    let mut tags = Vec::with_capacity(count as usize);
    for _ in 0..count {
        let name = reader.read_string()?;
        tags.push(Tag { name });
    }
    Ok(tags)
}
```

这样以后切 V2 时,只需要写 V2Reader 实现 HhaReader,游戏代码完全不动。这是**依赖倒置**的威力——游戏代码依赖抽象,不依赖具体实现。

Casey 在 C 里没有 trait,只能用函数指针 + struct,实现起来繁琐。Rust 的 trait 让"多版本兼容"变得几乎免费。

### 切换之后:删除 V0

切完之后,V0 reader 代码就要删。**留着没用,反而增加心智负担**——下次读代码你会想"这个 V0 还在用吗?"。Casey 的原则:**死代码立刻删,Git 历史就是你的备份**。

Rust 编译器会帮你确认 V0 删干净——如果还有调用 V0 函数的地方,编译失败,你能立刻发现。这是静态类型语言的优势。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业里"格式切换"是常态:

- **Unreal** 每个大版本(UE4 → UE5)都要切资产格式,迁移工具是 `UE-AssetMigration-Tool`
- **Unity** 的资产格式在 Unity 2018 / 2019 / 2020 / 2021 各有差异,升级项目时跑 `AssetDatabase.UpgradeProjectItems`
- **id Software** 的 Quake 1 / 2 / 3 各用不同 BSP 格式,社区 dumper 兼容所有版本

游戏公司通常有专人管"资产管线",职责就是版本切换 + 工具维护。Casey 单人开发,身兼数职,但他有意识地遵守工业流程:**先迁移、再 dump 验证、最后切代码**。

游戏里常见踩坑场景:
- 切完之后,某个**冷门 asset**(比如某个 NPC 的对话音)没被加载过,bug 隐藏到玩家触发对话才暴露
- 切完之后,**save file 格式**没切,玩家旧存档加载失败
- 切完之后,**网络协议**没切,联机模式版本不一致

Casey 的 HH 没有联机(save file 在 Day 200+),所以这次切换比较干净。商业游戏切换往往要协调多团队。

### 3.2 · 🎨 图形学视角

虽然今天主题不是图形学,但 HHA 里的 texture asset 切换涉及几个图形学点:

第一,**纹理格式**(RGBA8 / BCn)的描述在 V0 和 V1 可能不同。V0 用 enum int(0=RGBA8, 1=BC1, ...),V1 用 string("RGBA8", "BC1")。游戏代码读出来要 map 到 GPU 的 internal format(`gl::RGBA8` / `gl::COMPRESSED_RGBA_S3TC_DXT3_EXT`)。切换时这个 map 表要同步改。

第二,**mip level 数**。V0 可能没存 mip,V1 加了。切换时 GPU 上传逻辑要改——V0 每个纹理只有一个 level,V1 可能多个。

第三,**color space**。V0 默认 sRGB,V1 显式标记。这影响 `glTexImage2D` 用的 internal format(`gl::SRGB8_ALPHA8` vs `gl::RGBA8`)。弄错会导致颜色看起来"太亮"或"太暗"。

这些字段虽然今天 Casey 没全切,但当你将来扩展 HHA 时,这些都是字段。

### 3.3 · 🐧 Linux 系统编程视角

Linux 系统编程里"格式切换"无处不在:

- **glibc 的 libc.so.6** 升级时,所有依赖它的程序都要"切到新版本"。glibc 用 symbol versioning(`__libc_start_main@GLIBC_2.2.5`)实现"同文件多版本共存"——新程序用新 symbol,旧程序继续用旧 symbol,两边都不破坏。这是**适配器策略**的极致实现。
- **systemd 的 journal** 格式从 v1 升到 v2 时,systemd 提供了 `journalctl --header` 检查格式版本,旧 journal 文件用 v1 reader 读,新文件用 v2 reader。**并行运行 + 渐进淘汰**策略。
- **ext4 文件系统**升级 feature 时,要求 `tune2fs -O extent /dev/sda1` 显式启用新 feature,且旧 kernel 不挂载。这是"原子升级 + 兼容标记"。

Casey 的 HHA 切换和这些系统级升级**本质相同**——都是"格式 + reader 同步升级"。区别只在规模:HHA 是单游戏,libc 是整个 Linux 发行版。

实操:Arch Linux 上看 glibc 的版本化:

```bash
# 看 libc.so.6 提供哪些版本的符号
nm -D /usr/lib/libc.so.6 | grep -E " GLIBC_" | head -10
# 输出类似:
# 00000000000a23a0 W accept4@@GLIBC_2.2.5
# ...
# 多个 @@ 表示 symbol 有多个版本

# 看 readelf 包含哪些 GLIBC 版本依赖
readelf -V /bin/ls | grep Name
# 输出包含 GLIBC_2.x 系列

# 用 strings 看二进制里嵌的版本字符串
strings /bin/ls | grep GLIBC_ | head
```

这套工具链就是工业级"格式切换观察台"。Casey 的 hhadump 在 HHA 世界里扮演类似角色。

### 3.4 · 🦀 Rust 生态视角

Rust 在格式切换方面有几个独特优势:

**优势 1:类型系统防漂移**。Rust 的 enum 是 sum type,如果你 V0 用 `enum AssetType { Texture, Sound }`,V1 加 `Font`,所有 `match asset_type { ... }` 编译器强制要求覆盖新 variant。这是**编译期防漂移**。

**优势 2:trait 优雅抽象**。前面讲的 `HhaReader` trait,V0 和 V1 各实现,游戏代码用泛型 `<R: HhaReader>`。这是工业 Rust 的标准模式。

**优势 3:serde 强大**。如果你的 struct 派生 `Serialize` / `Deserialize`,加字段时用 `#[serde(default)]` 自动处理旧文件缺失字段:

```rust
#[derive(Deserialize)]
struct AssetV1 {
    name: String,
    #[serde(default)]
    crc: u32,  // V0 没有,默认 0
    #[serde(default = "default_type")]
    type_code: u32,
}
```

Casey 不用 serde 因为他手写二进制读写,但现代 Rust 项目大多选 serde。

**优势 4:`cfg` 编译条件**。你想保留 V0 代码做 reference,但不让它进 release build:

```rust
#[cfg(feature = "legacy_v0")]
mod v0_reader { ... }
```

`Cargo.toml` 里:
```toml
[features]
legacy_v0 = []  # 默认不启用
```

这样默认 build 没有 V0,但需要时 `cargo build --features legacy_v0` 能拉回来。这是**条件编译 + 死代码隔离**。

| 策略 | 描述 | 风险 | 维护成本 | 本项目选了哪个 |

## 5 · 对照与变奏

### 同一问题:数据库 schema 升级

数据库 schema 升级和 HHA 升级本质相同——结构变了,旧数据要迁移,代码要切。

- **SQLAlchemy Alembic**:写 migration script,每个版本一个 script,顺序执行。对应 HHA 的 V0→V1 迁移工具
- **Rails Active Record Migrations**:`rails db:migrate`,同上
- **glibc symbol versioning**:runtime 同时支持多版本 symbol,渐进淘汰。对应 HHA 的 Parallel Run 策略
- **systemd journal 格式**:文件 header 嵌版本号,reader dispatch。对应 HHA 的 `match version`

注意共性:**所有升级方案都需要"版本号"**。HHA 有 version 字段,数据库有 schema_version,journal 有 header.version。**没有版本号,无法升级**。这是工程铁律。

### 切换的"心理成本"

切换表面是技术问题,实际是**心理问题**。工程师不愿意切,因为:
- 怕出 bug(安全感)
- 怕"动到不该动的"(敬畏)
- 怕"花了功夫但没人在意"(成就感缺失)

Casey 切 HHA V1 也没人鼓掌,但他知道这是工程纪律。成熟工程师**愿意做没人看见但对的事**。

工业界有个术语叫 **"cutover plan"**——切换计划,详细列出切换的每一步、回滚条件、责任人。NASA 的软件切换计划长达几百页。Casey 单人开发不需要这么正式,但思路一致:**列清楚、逐步骤、可回滚**。

### 历史演化:从手写迁移到自动迁移

早期(1990s)的迁移靠人手写 SQL,容易错。

中期(2000s-2010s)出现 migration framework(Rails、Alembic),自动生成 + 顺序执行,大幅降低出错率。

近期(2020s-)趋势是"schema-less"——用 JSON / Protobuf / Avro 等"自描述"格式,字段缺失自动 nullable。本质上把"格式迁移"变成了"字段兼容"。但代价是性能损失(JSON 比 struct 慢)和类型安全损失。

游戏资产追求性能,所以 Casey 坚持**显式 schema + 显式迁移**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 不让游戏代码同时支持 V0 和 V1(永久双版本),而是切完就删 V0?用"维护成本"和"漂移"解释。

**参考解答**:永久双版本有两个致命问题:

第一,**维护成本翻倍**。每次给 V1 加 feature(比如新 asset type),V0 也要加(否则老文件用不上)。这相当于每个 feature 写两遍。

第二,**漂移(drift)**。两份代码会逐渐不一致——V0 里某 bug 修了,V1 没修,或反之。最终你不知道哪个是"正确"版本,debug 变成考古。

工业经验:**双版本共存只能用作过渡,不能用作长期方案**。要么切完删旧版(Big Bang),要么用 adapter 让"旧版"自动转新版,不维护两份代码。Casey 选前者,因为 Day 465 已经离线转完所有文件。

### Lv2 · 动手实践

**题**:用 Rust trait 实现 V0 和 V1 reader。完成标准:
- 定义 `trait HhaReader`,包含 `read_magic`, `read_version`, `read_string`, `read_asset` 方法
- `V0Reader` 和 `V1Reader` 各实现 trait
- 写一个 `load_hha<R: HhaReader>(reader: &mut R)` 函数,接受任意 reader
- 在 main 里用 V0 读 test_v0.hha,用 V1 读 test_v1.hha,各自打印 asset 数

**参考解答**:

```rust
use std::io::{self, Read};

// trait:接口契约。任何实现这个 trait 的类型都能被 load_hha 用
trait HhaReader {
    fn read_magic(&mut self) -> io::Result<[u8; 4]>;
    fn read_version(&mut self) -> io::Result<u32>;
    fn read_string(&mut self) -> io::Result<String>;
    fn read_asset(&mut self) -> io::Result<Asset>;
}

#[derive(Debug)]
struct Asset {
    type_code: u32,
    name: String,
    offset: u32,
    size: u32,
}

// V0 reader:字符串是 null-terminated
struct V0Reader<R: Read> { inner: R }

impl<R: Read> V0Reader<R> {
    fn new(r: R) -> Self { Self { inner: r } }
}

impl<R: Read> HhaReader for V0Reader<R> {
    fn read_magic(&mut self) -> io::Result<[u8; 4]> {
        let mut buf = [0u8; 4];
        self.inner.read_exact(&mut buf)?;
        Ok(buf)
    }
    fn read_version(&mut self) -> io::Result<u32> {
        read_u32_le(&mut self.inner)
    }
    fn read_string(&mut self) -> io::Result<String> {
        // null-terminated:读到 \0 停
        let mut bytes = Vec::new();
        let mut b = [0u8; 1];
        loop {
            self.inner.read_exact(&mut b)?;
            if b[0] == 0 { break; }
            bytes.push(b[0]);
        }
        Ok(String::from_utf8_lossy(&bytes).into_owned())
    }
    fn read_asset(&mut self) -> io::Result<Asset> {
        let type_code = read_u32_le(&mut self.inner)?;
        let name = self.read_string()?;
        let offset = read_u32_le(&mut self.inner)?;
        let size = read_u32_le(&mut self.inner)?;
        Ok(Asset { type_code, name, offset, size })
    }
}

// V1 reader:字符串是 length-prefix
struct V1Reader<R: Read> { inner: R }

impl<R: Read> V1Reader<R> {
    fn new(r: R) -> Self { Self { inner: r } }
}

impl<R: Read> HhaReader for V1Reader<R> {
    fn read_magic(&mut self) -> io::Result<[u8; 4]> {
        let mut buf = [0u8; 4];
        self.inner.read_exact(&mut buf)?;
        Ok(buf)
    }
    fn read_version(&mut self) -> io::Result<u32> {
        read_u32_le(&mut self.inner)
    }
    fn read_string(&mut self) -> io::Result<String> {
        // length-prefix:先 u32 长度,再那么多字节
        let len = read_u32_le(&mut self.inner)? as usize;
        let mut bytes = vec![0u8; len];
        self.inner.read_exact(&mut bytes)?;
        Ok(String::from_utf8_lossy(&bytes).into_owned())
    }
    fn read_asset(&mut self) -> io::Result<Asset> {
        let type_code = read_u32_le(&mut self.inner)?;
        let name = self.read_string()?;
        let offset = read_u32_le(&mut self.inner)?;
        let size = read_u32_le(&mut self.inner)?;
        Ok(Asset { type_code, name, offset, size })
    }
}

fn read_u32_le<R: Read>(r: &mut R) -> io::Result<u32> {
    let mut buf = [0u8; 4];
    r.read_exact(&mut buf)?;
    Ok(u32::from_le_bytes(buf))
}

// 泛型函数:接受任何实现 HhaReader 的类型
fn load_hha<R: HhaReader>(reader: &mut R) -> io::Result<Vec<Asset>> {
    let _magic = reader.read_magic()?;
    let _version = reader.read_version()?;
    let _tag_count = read_u32_le_external(reader)?;  // 假设 trait 之外的小工具
    let asset_count = read_u32_le_external(reader)?;
    
    let mut assets = Vec::with_capacity(asset_count as usize);
    for _ in 0..asset_count {
        assets.push(reader.read_asset()?);
    }
    Ok(assets)
}

// 注:tag_count / asset_count 是文件级,不放 trait 里。
// 实际工程会放,这里为了演示从简。
fn read_u32_le_external<R: Read>(r: &mut R) -> io::Result<u32> {
    read_u32_le(r)
}

fn main() -> io::Result<()> {
    use std::fs::File;
    
    // V0 文件
    let f0 = File::open("test_v0.hha")?;
    let mut r0 = V0Reader::new(f0);
    let assets_v0 = load_hha(&mut r0)?;
    println!("V0 assets: {}", assets_v0.len());
    
    // V1 文件
    let f1 = File::open("test_v1.hha")?;
    let mut r1 = V1Reader::new(f1)?;
    let assets_v1 = load_hha(&mut r1)?;
    println!("V1 assets: {}", assets_v1.len());
    
    Ok(())
}
```

**每行解释**:
- `trait HhaReader` —— 定义接口。trait 类似 Java interface / Haskell typeclass
- `<R: Read>` —— 泛型约束,R 必须实现 std::io::Read
- `impl<R: Read> HhaReader for V0Reader<R>` —— 给 V0Reader(对任意 R: Read)实现 HhaReader
- `String::from_utf8_lossy` —— 字节转字符串,非法字节替换成 `?`,不 panic
- `fn load_hha<R: HhaReader>` —— 函数泛型,任何 HhaReader 都能用。这就是依赖倒置

### Lv3 · 迁移设计

**题**:你的 HHA 现在要切 V2,加了"CRC 字段在每个 asset 后"。设计 V2 的字段顺序 + V2Reader 实现 + 一个 V1→V2 离线转换工具。要求 V2 reader 读 V1 文件时直接报错(强制转换),而不是"默默兼容"。

**提示**:
- 字段顺序:`magic + version + tag_count + tags + asset_count + assets(每个有 crc)`
- V2Reader 在 read_magic 后检查 version 必须 == 2
- 离线工具读 V1,内存中加 crc 字段(可以用 0 或真的算 CRC),写 V2
- 思考:CRC 字段是 asset 数据的 CRC 还是 asset 元数据的 CRC?两者有什么区别?

```rust
fn load_game_assets() -> Vec<Asset> {
    let file = File::open("game.hha").unwrap();
    let mut reader = BufReader::new(file);
    
    let magic = read_magic_v0(&mut reader);  // V0 函数
    let version = read_u32_v0(&mut reader);   // 假设永远 0

        let asset = read_asset_v0(&mut reader);  // null-terminated 字符串
        assets.push(asset);
    }
    assets
}
```

切换后(用 trait 抽象):

```rust
// 新代码:依赖 trait,不关心版本
fn load_game_assets<R: HhaReader>(reader: &mut R) -> Vec<Asset> {
    let _magic = reader.read_magic().unwrap();
    let version = reader.read_version().unwrap();
    
    // 版本分发(可选:如果想 runtime dispatch)
    match version {
        0 | 1 => {
            let asset_count = read_u32_le_external(reader).unwrap();
            let mut assets = Vec::new();
            for _ in 0..asset_count {
                assets.push(reader.read_asset().unwrap());
            }
            assets
        }
        v => panic!("Unknown HHA version {}", v),
    }
}
```

差异:`read_magic_v0` 这种"V0 硬编码函数"换成了 `reader.read_magic()`,reader 是 V0Reader 或 V1Reader 实例,编译期决定。

### 用 git bisect 定位切换 bug

切完跑游戏,粉屏。怎么定位?`git bisect` 是利器:

```bash
# 1. 标记当前坏 commit
git bisect start
git bisect bad HEAD

# 2. 标记最后一个好的 commit(切换前的 commit)
git bisect good HEAD~20  # 假设切了 20 个 commit

# 3. git 自动 checkout 中间 commit,你跑游戏测试
# 假设中间 commit 也是坏的
git bisect bad

# 4. git 继续二分,直到定位到第一个 bad commit
# 5. 完成后退出 bisect 模式

```

```
    ...
```

定位到具体 commit 后,`git show abc1234 --stat` 看改了哪些文件,聚焦看那些文件。

### Troubleshooting

- **切换后所有 asset name 都是乱码** —— read_string 函数搞错版本,把 V1 文件用 null-terminated 读
- **切换后 asset_count 是天文数字** —— 字段顺序错了,V1 多了个字段你跳过了
- **切换后 CRC 校验失败** —— CRC 算法实现错(检查 polynomial 和 byte order)
- **切换后某些 asset offset 不对** —— header 总长度变了,asset 数据 offset 跟着变,但你还在用旧 offset
