## 1 · Casey 今天做了什么

Casey 这一天的工作:

第一步,他跑 Day 479 的代码,期望看到角色立绘正确显示。实际看到的是**全屏黑**或者**纹理错乱**。

第二步,他开始**二分定位**:

第三步,他发现一个典型 bug:**`tiles_per_row` 用了 float 而不是 int 传到 shader**。shader 里 `int(uv.x * tiles_per_row)` 算的是 `int(uv.x * 4.0)` 而不是 `int(uv.x) * 4`,语义不同。

第五步,他发现第二个 bug:**vertex attribute offset 错**。他加了 `tiles_per_row` 字段但忘了调整后续字段的 offset,导致 color 字段读到错位置。

第七步,他总结:**调试图形 bug 要按 pipeline 顺序排查**(CPU 数据 → 上传 → shader → 帧缓冲)。每一步都有独立工具验证。

## 2 · 心智模型

### 类比:工厂流水线故障排查

想象一条汽车装配流水线:发动机 → 车身 → 喷漆 → 内饰。如果出厂的车有问题(比如发动机没装),你不能盲目拆整辆车。你要在流水线每个工位**设检查点**——发动机工位后检查发动机有没有,喷漆工位后检查漆面颜色对不对。

图形渲染也是流水线:

```
CPU 数据准备 → 上传 GPU → Vertex Shader → Rasterizer → Fragment Shader → Framebuffer
```

每一步都可能出错。你要在每步后验证"这一步的输出对不对"。

### 科学调试法

调试不是"瞎猜 + 改一改试试",是**科学方法**:

1. **观察**:bug 现象是什么?(全黑 / 错乱 / 闪烁)
2. **假设**:可能的原因是什么?(纹理没上传 / shader 算错 / vertex 数据错)
3. **预测**:如果是这个原因,其他地方应该有什么表现?
4. **实验**:验证预测(读 GPU 数据、改一行代码看反应)
5. **结论**:假设成立 / 不成立,继续下一个假设

这套方法叫 **"Hypothesis-Driven Debugging"**(假设驱动调试)。Casey 在 Day 480 完整演示。

### 图形调试工具箱

| 工具 | 用途 | 难度 |
|---|---|---|
| `println!` / `printf` | 验证 CPU 端数据 | 简单 |
| `glGetError` | 检查 GL 错误 | 简单 |
| `glReadPixels` | 读帧缓冲/纹理像素 | 中等 |
| `apitrace` | 录制 + 重放 GL 调用 | 中等 |
| `renderdoc` | 图形化单帧调试 | 强大但复杂 |
| `GALLIUM_HUD` | 实时性能监控 | 简单 |
| `valgrind` | 内存错误 | 中等 |
| `gdb` | 通用调试器 | 中等 |

Casey 在 Day 480 主要用前四个——`printf`、`glGetError`、`apitrace`。RenderDoc 是工业级,他没在视频里用。

### 常见图形 bug 模式

Casey 在 HH 几百集里反复遇到这几类 bug:

**黑屏**:整个 framebuffer 全黑。原因:shader 编译失败、texture 没绑、depth test 把所有片段剔掉。

**纹理错乱**:有图但颜色/位置错。原因:UV 错、纹理 format 错(把 RGBA 当 RGB)、byte order 错(RGBA vs BGRA)。

**闪烁**:帧间不稳定。原因:未初始化内存、数据竞争(多线程写同一 buffer)。

**变形**:三角形看起来不对。原因:顶点顺序错(CCW vs CW)、矩阵 row-major / column-major 混淆。

**性能差**:FPS 低。原因:draw call 过多、纹理太大、shader 太复杂。

每类 bug 有标准排查思路。Casey Day 480 处理"纹理错乱"——按 pipeline 顺序逐段验证。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的图形调试早已工业化。Unity 有 Frame Debugger,Unreal 有 Render Dependency Graph 调试器,Godot 有 Frame Profiler。这些工具可视化每一帧的渲染步骤。

但工具再好,核心方法不变:**科学调试 + pipeline 排查**。

游戏开发圈有个经验:**先怀疑自己的代码,再怀疑工具/驱动**。99% 的 bug 是自己代码错,1% 是 driver bug。如果你一开始就怪 driver,大概率浪费时间。

Casey 在 Day 480 严格遵循这个原则——先彻底验证自己代码,才考虑其他。

### 3.2 · 🎨 图形学视角

图形 pipeline 的每一段都有自己的调试方法。

**Vertex Shader 调试**:用 `gl_Position` 输出 + transform feedback 把 vertex 数据写回 CPU,看实际值。

**Rasterizer 调试**:看 `gl_FragCoord`,确认 fragment 在期望位置生成。

**Fragment Shader 调试**:用 `gl_FragColor = vec4(red, 0, 0, 1)` 输出固定颜色,看 fragment 是否执行。这是 **"visualization debugging"**——把数据当颜色输出,看屏幕。

**Texture 调试**:用 `glReadPixels` 从 texture 读回像素,或者 blit texture 到屏幕直接看。

Casey 在 Day 480 主要用 texture 读回 + fragment shader 染色,两个工具足够定位大部分 bug。

### 3.3 · 🐧 Linux 系统编程视角

### 3.4 · 🦀 Rust 生态视角

Rust 写图形代码有几个调试便利。

第一,**`Debug` 派生**。所有 struct 都 `#[derive(Debug)]`,可以一行打印:

```rust
println!("entry = {:?}", entry);
// 比 C 的 printf 体验好得多
```

第二,**`assert_eq!`** 验证假设。在 shader 计算前后插 assert,早期发现 bug:

```rust
let layer = base_layer + offset;
assert!(layer < total_layers, "layer {} overflow", layer);
```

第三,**`Result` 显式错误**。OpenGL 错误用 `glGetError` 查询,容易漏。Rust 可以包一层 safe wrapper,把 GL error 转成 Result:

```rust
fn gl_check() -> Result<(), String> {
    let err = unsafe { gl::GetError() };
    match err {
        gl::NO_ERROR => Ok(()),
        gl::INVALID_ENUM => Err("GL_INVALID_ENUM".into()),
        gl::INVALID_VALUE => Err("GL_INVALID_VALUE".into()),
        // ...
        _ => Err(format!("GL error 0x{:x}", err)),
    }
}

fn upload_texture(...) -> Result<(), String> {
    unsafe { gl::TexImage2D(...); }
    gl_check()?;   // ? 自动传播错误
    Ok(())
}
```

这样每次 GL 操作后自动检查错误,不用手动插。

## 5 · 对照与变奏

Casey 在 Day 480 的调试方法在不同领域有不同对应:

**硬件调试**:示波器看信号、逻辑分析仪看总线。和图形调试的 pipeline 排查同构——按信号流逐段检查。

**网络调试**:`ping` 测网络通不通、`traceroute` 看路径、`tcpdump` 抓包。每步都是 pipeline 的一段。

**数据库调试**:`EXPLAIN ANALYZE` 看 query plan,逐 stage 看耗时。和图形调试的 pipeline 排查同构。

**分布式系统**:链路追踪(Jaeger、Zipkin)看请求经过的每个服务。同 pipeline 排查。

理解"按 pipeline 排查"是工程师的核心素养。每次遇到 bug,问自己:**这个系统的 pipeline 是什么?哪一段最可能出错?**

另一个对照:**好工程师 vs 普通工程师**。普通工程师改一改跑一跑,改不对再改。好工程师先想清楚"为什么",改之前预测结果,改之后验证预测。这个差别在复杂系统里放大——普通工程师改一周可能修不好,好工程师一天搞定。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:调试图形 bug 时,为什么先验证 CPU 端数据,再验证 GPU 端?

**参考解答**:两个理由:

第一,**因果顺序**。CPU 数据是 GPU 渲染的输入,输入错则结果必然错。如果先查 GPU,发现 texture 全黑,可能是 CPU 上传错(根因)也可能是 shader 采样错(下游)。先查 CPU 排除一半可能性。

第二,**工具便利**。CPU 数据用 `println!` 立即看,GPU 数据要用 `glReadPixels` 或 apitrace,复杂。先做容易的验证。

排查顺序通常是:**CPU 数据 → 上传 → vertex shader → fragment shader → framebuffer**。这是数据流方向,每段验证通过才查下一段。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:写一段"假设驱动"调试代码。模拟一个 bug:`uv_to_layer_offset` 函数有 off-by-one 错误(返回 layer 时多算了 1)。写一个测试,运行测试发现 bug,然后修。要求:测试包含至少 3 个边界用例(UV (0,0)、(1,1)、(0.5, 0.5))。

完成标准:`cargo test` 在修复前失败,修复后通过。

**参考解答**:

```rust
const TILES_PER_ROW: usize = 4;

// 故意有 bug 的版本(模仿 Day 480 的真实 bug)
fn uv_to_layer_offset_buggy(u: f32, v: f32) -> usize {
    let tu = u * TILES_PER_ROW as f32;
    let tv = v * TILES_PER_ROW as f32;
    let tile_x = (tu as usize) + 1;   // BUG:多 +1
    let tile_y = (tv as usize) + 1;
    tile_y * TILES_PER_ROW + tile_x
}

// 正确版本
fn uv_to_layer_offset_correct(u: f32, v: f32) -> usize {
    let tu = u * TILES_PER_ROW as f32;
    let tv = v * TILES_PER_ROW as f32;
    let tile_x = (tu as usize).min(TILES_PER_ROW - 1);  // clamp
    let tile_y = (tv as usize).min(TILES_PER_ROW - 1);
    tile_y * TILES_PER_ROW + tile_x
}

#[cfg(test)]
mod tests {
    use super::*;
    
    #[test]
    fn test_origin() {
        // UV (0, 0) 应该映射到 layer 0
        assert_eq!(uv_to_layer_offset_correct(0.0, 0.0), 0);
    }
    
    #[test]
    fn test_center() {
        // UV (0.5, 0.5) 在第 2 行第 2 列(0-indexed)
        // tile_x = 2, tile_y = 2, layer = 2*4 + 2 = 10
        assert_eq!(uv_to_layer_offset_correct(0.5, 0.5), 10);
    }
    
    #[test]
    fn test_corner() {
        // UV (1, 1) 接近右下角
        // 不 clamp:tu = 4, tile_x = 4(越界)
        // clamp:tile_x = 3, tile_y = 3, layer = 3*4 + 3 = 15
        assert_eq!(uv_to_layer_offset_correct(1.0, 1.0), 15);
    }
    
    #[test]
    fn test_buggy_version_fails() {
        // 验证 buggy 版本确实错
        assert_ne!(uv_to_layer_offset_buggy(0.0, 0.0), 0);  // 错位
    }
}

fn main() {
    // 演示调试过程
    println!("=== 假设驱动调试演示 ===");
    println!("观察:纹理显示错位");
    println!("假设 1:UV 计算错");
    println!("预测:uv_to_layer_offset(0, 0) 应返回 0");
    println!("实验:实际返回 {}", uv_to_layer_offset_buggy(0.0, 0.0));
    println!("结论:假设成立,有 off-by-one");
    println!("修复:去掉 +1");
    println!("验证:修复后返回 {}", uv_to_layer_offset_correct(0.0, 0.0));
}
```

为什么这么写:每个测试是一个"假设验证"。`test_buggy_version_fails` 显式证明 buggy 版本错。这是 TDD(test-driven debugging)的思路。

## 8 · Rust / Arch 落地代码

下面是一个完整的"调试工具箱" Rust 代码。

```rust
// ========================================
// 调试工具:GL error checker(假装)
// ========================================

mod gl {
    pub const NO_ERROR: u32 = 0;
    pub const INVALID_ENUM: u32 = 0x0500;
    pub const INVALID_VALUE: u32 = 0x0501;
    pub const INVALID_OPERATION: u32 = 0x0502;
    pub const OUT_OF_MEMORY: u32 = 0x0505;
    
    // 假装的 GetError(实际会调 OpenGL)
    thread_local! {
        static LAST_ERROR: std::cell::Cell<u32> = std::cell::Cell::new(NO_ERROR);
    }
    
    pub fn set_error(e: u32) {
        LAST_ERROR.with(|cell| cell.set(e));
    }
    
    pub fn get_error() -> u32 {
        LAST_ERROR.with(|cell| {
            let e = cell.get();
            cell.set(NO_ERROR);
            e
        })
    }
}

fn gl_check(context: &str) -> Result<(), String> {
    let err = gl::get_error();
    match err {
        gl::NO_ERROR => Ok(()),
        gl::INVALID_ENUM => Err(format!("{}: GL_INVALID_ENUM", context)),
        gl::INVALID_VALUE => Err(format!("{}: GL_INVALID_VALUE", context)),
        gl::INVALID_OPERATION => Err(format!("{}: GL_INVALID_OPERATION", context)),
        gl::OUT_OF_MEMORY => Err(format!("{}: GL_OUT_OF_MEMORY", context)),
        _ => Err(format!("{}: unknown GL error 0x{:x}", context, err)),
    }
}

// ========================================
// 调试工具:断言 + 可视化
// ========================================

#[derive(Debug)]
struct Vertex {
    pos: [f32; 3],
    uv: [f32; 2],
    color: [f32; 4],
    texture_layer: i32,
}

fn debug_vertex(label: &str, v: &Vertex) {
    println!("[DEBUG] {}: pos={:?} uv={:?} color={:?} layer={}",
             label, v.pos, v.uv, v.color, v.texture_layer);
    
    // Sanity check
    assert!(v.texture_layer >= 0, "texture_layer should be non-negative");
    assert!(v.uv[0] >= 0.0 && v.uv[0] <= 1.0, "uv.x out of range: {}", v.uv[0]);
    assert!(v.uv[1] >= 0.0 && v.uv[1] <= 1.0, "uv.y out of range: {}", v.uv[1]);
}

// ========================================
// 调试场景:模拟 Day 480 的 bug
// ========================================

fn simulate_buggy_upload() {
    println!("=== 模拟 Day 480 bug ===");
    
    // Bug 1:tiles_per_row 错位
    println!("\n--- Bug 1: tiles_per_row 传错 ---");
    let tiles_per_row_float: f32 = 4.0;     // 错:float
    let tiles_per_row_int: i32 = 4;          // 对:int
    
    let uv = 0.5_f32;
    let buggy = (uv * tiles_per_row_float) as i32;   // int(2.0) = 2
    let correct = (uv * tiles_per_row_int as f32) as i32;  // int(2.0) = 2
    println!("uv={}, float 版本 tile_x={}, int 版本 tile_x={}",
             uv, buggy, correct);
    // 在某些情况下,(uv * float) as int 因为浮点精度可能少 1
    // 如:uv = 0.4999999,tiles_per_row_float = 4.0
    // uv * 4 = 1.9999996,as int = 1(应该是 2)
    
    let tricky_uv = 0.4999999;
    let buggy2 = (tricky_uv * tiles_per_row_float) as i32;
    let correct2 = (tricky_uv * tiles_per_row_int as f32) as i32;
    println!("tricky uv={}, buggy={}, correct={}", tricky_uv, buggy2, correct2);
    
    // Bug 2:vertex attribute offset 错
    println!("\n--- Bug 2: vertex offset 错 ---");
    
    // 假装的 vertex layout(故意算错 offset)
    let pos_offset = 0;
    let uv_offset = 12;       // pos 3f = 12B
    let color_offset = 20;    // uv 2f = 8B,但忘了 uv 实际只占 8B
    
    // 正确 offset
    let correct_color_offset = 12 + 8;  // = 20,这里对
    let layer_offset = 20 + 16;          // color 4f = 16B = 36
    let correct_layer_offset = 12 + 8 + 16;  // 同
    
    println!("pos offset={}, uv offset={}, color offset={}, layer offset={}",
             pos_offset, uv_offset, color_offset, layer_offset);
    println!("Correct color offset={}, layer offset={}",
             correct_color_offset, correct_layer_offset);
    
    // 如果 layer_offset 错(写成 32 而不是 36),vertex shader 会读错位置
    let buggy_layer_offset = 32;
    if buggy_layer_offset != layer_offset {
        println!("BUG: layer_offset 应该是 {},实际传了 {}",
                 layer_offset, buggy_layer_offset);
    }
}

fn bisect_debug() {

    println!("步骤 1:验证 CPU 端 vertex 数据");
    let v = Vertex {

    gl::set_error(gl::NO_ERROR);
    gl_check("upload texture").unwrap();
    println!("→ 上传无错误");
    
    println!("\n步骤 3:验证 shader uniform");
    let base_layer = 0;
    let tiles_per_row = 4;

    println!("\n步骤 4:验证 draw call");
    gl_check("draw call").unwrap();

    println!("\n结论:GPU 端无错误,bug 可能在 shader 内部计算");
```

出错怎么办:

- **apitrace 报 "GL_NO_ERROR in glGetError"** —— 但视觉上还是错。说明 GL 调用都对,bug 在 shader 逻辑或 vertex 数据。用 RenderDoc 看 vertex input texture 内容。
- **renderdoc 不显示 texture** —— 你可能用了 attribute 而不是 uniform 传 texture。RenderDoc 显示当前绑定的 texture,attribute 形式要看 vertex input 面板。
- **MESA_DEBUG 输出大量 "performance warning"** —— 不是 bug,只是 driver 提示。filter 掉 `grep -v performance`。

## 10 · 复习要点

读完这一天你应该能用 30 秒回答以下问题:

**Q1**:为什么调试图形 bug 要按 pipeline 顺序排查?
> CPU 数据 → 上传 → vertex shader → fragment shader → framebuffer。每段验证通过才查下一段。先做容易验证的(CPU 数据),再做难的(GPU)。

**Q2**:科学调试法的五个步骤?
> 观察、假设、预测、实验、结论。每步缩小可能性范围。不是"瞎改试试",是"想清楚再改"。

**Q3**:apitrace 和 RenderDoc 的差别?
> apitrace 录制 + 重放 GL 调用,看 trace 文件。RenderDoc 是图形化单帧调试器,更强大但复杂。apitrace 适合"看调用序列",RenderDoc 适合"看具体像素"。

**Q4**:Wolf-fence 调试法是什么?
> 二分注释代码——一半一半地禁用代码,看 bug 是否消失。定位"哪段触发 bug"的快速方法。

**Q5**:为什么"先怀疑自己代码,再怀疑工具/驱动"?
> 99% 的 bug 是自己代码错。如果一开始怪 driver,大概率浪费时间。先彻底验证自己代码,才考虑其他。

如果你能流畅回答这五个问题,说明 Day 480 的核心你已经内化。下一日 Day 481 处理 cube map UV 编码。

**Q6**:`{:?}` debug 格式为什么是 Rust 调试字符串的瑞士军刀?
> 它自动转义不可见字符(`\r`、`\n`、`\t`、Unicode escapes),让字符串内容一目了然。`println!("{}", s)` 看不到末尾的 `\r`,`println!("{:?}", s)` 立即看到。

**Q7**:图形 pipeline 调试的标准顺序是什么?
> CPU 数据(println)→ 上传到 GPU(glGetError)→ vertex shader(transform feedback)→ rasterizer(gl_FragCoord)→ fragment shader(fixed color output)→ framebuffer(glReadPixels)。每段验证通过才查下一段。

**Q8**:为什么 Casey 强调"修 bug 后加 unit test"?
> 防回归——同样的 bug 可能在未来再次出现(代码重构、新功能引入)。Unit test 锁定正确行为,bug 再现时立刻被测试发现。这是工业项目的纪律。

如果你能流畅回答这八个问题,Day 480 的核心你已经吃透。

## 11 · 真实工程参考

理解 Day 480 的概念后,你可以参考这些真实代码加深:

**Casey 的 HH Day 480 视频**——这一集 Casey 真实演示调试过程,不是预先准备的剧本。看他怎么思考、怎么定位、怎么验证假设,胜过读任何调试教科书。

**RenderDoc**:`renderdoc.org`。开源图形调试器,GPU vendor 无关。下载安装,抓一帧看具体 pixel 怎么生成。

**apitrace**:`apitrace.github.io`。GL trace 工具,录制 + 重放。适合"看 GL 调用序列"。

**gdb / lldb**:通用调试器。配合 Rust 的 `rust-gdb` / `rust-lldb`(自动加载 pretty printer)。

**valgrind**:`valgrind.org`。内存错误检测工具,Linux 必备。`memcheck`(内存)、`massif`(堆)、`callgrind`(CPU)。

**perf**:`perf.wiki.kernel.org`。Linux 内置 profiler,看 cache miss、branch prediction、instructions。

**flamegraph**:`github.com/brendangregg/FlameGraph`。火焰图可视化 CPU profile。

**heaptrack**:`github.com/KDE/heaptrack`。内存分配追踪,比 massif 更精确。

**strace / ltrace**:系统调用 / 库调用追踪。看程序实际调了什么 syscall。

**Linux 系统级调试**:`/proc/<pid>/`、`/sys/`、`dmesg`、`sysrq`、`bpftrace`、`systemtap`。

阅读这些工具的文档时,关注:

1. **工具覆盖什么**(内存 / CPU / GPU / 网络 / 系统)
2. **侵入性**(全开销 vs 采样)
3. **输出格式**(文本 / 图形 / 火焰图)
4. **能定位什么 bug**(崩溃 / 性能 / 内存 / 死锁)

Day 480 之后,你遇到任何 bug 都能想到"该用什么工具"。
