# Day 535 · 小型美术更新、重启用粒子、手套修复

> Casey 这天不是讲新概念,而是修一批小 bug 和小改进:**美术资产更新**(新角色 sprite)、**重启用粒子系统**(之前禁用了,因为 Day 533 改资产管线时被破坏)、**手套(glove)附接点 bug**(玩家手套的视觉位置错位)。这种"小修小补日"是工业级开发的日常——大重构后必然有连锁修复。

## 0 · 为什么要有这一天

### 真实场景:大重构后的连锁 bug

Day 524-534 你做了完整的资产管线重构:WAV 导入、字体提取、HHT writer、PNG writer、Asset trait 抽象、bbox 计算。这种大规模重构会**破坏**之前能工作的功能——粒子系统因为加载路径变了,运行时找不到粒子资产;手套因为附接点坐标系改了,视觉位置错位。

Casey 这天做的事就是"扫尾"——把重构后的小 bug 一个个修。教学价值不在新概念,而在展示**"大重构后必须有扫尾日"**这个工程规律。

工业级开发的"扫尾日"叫**stabilization**——大重构后专门花几天修小 bug,稳定后再继续推进新功能。Linux 内核在 -rc1 到 -rc7 阶段就是 stabilization,只接受 bug fix,不接受新功能。

### 为什么 stabilization 这么重要

让我们把镜头拉近。假设你刚做完 Day 524-534 的资产管线重构(10 天大重构)。重构期间你只关注"主流程能不能跑"——load HHT、parse、build TagDatabase、查询。主流程跑通,你觉得"完成了"。

但很多边缘功能在重构期间被你**无意中破坏**:
- 粒子系统:之前用 hardcoded path 加载粒子 sprite,现在 TagId 系统不知道这个 sprite 在哪
- 手套附接:之前 alignment point 用世界坐标,现在改用相对坐标,手套位置错位
- 字体渲染:之前直接用 sprite sheet,现在字体提取到独立 asset,字体不显示
- 音频系统:类似粒子,WAV 路径硬编码,新系统找不到

每个 bug 单独看都"小"——花 10 分钟能修。但 10 个 bug 累加 = 半天。如果你**继续推进新功能**,bug 越累越多,最后 codebase 进入"半坏"状态——任何改动可能破坏别的东西,你不知道哪个功能还能用。

工业级解决方案:**stabilization phase**。每完成一个大重构,专门留 1-N 天(根据重构规模)修连锁 bug,确保 codebase **完全健康**再继续。

### 工业级 stabilization 的实践

让我把"stabilization"在工业级项目的具体实践讲清楚:

**Linux 内核**:Linus 每 8-10 周发布一个版本。前 6-7 周是 "merge window"(接受新功能),后 2-3 周是 -rc1 到 -rc7 stabilization(只接受 bug fix)。这种节奏保证每个版本质量。

**Google Chrome**:每 4 周一个稳定版。前三周开发,第四周 "beta freeze"(只修 bug)。Chrome 的稳定性声誉靠这种节奏。

**Unity/Unreal 游戏引擎**:大版本之间 6-12 个月,后期 3-6 个月 stabilization。Unreal Engine 5 的 Early Access → Preview → Release 流程就是分阶段 stabilization。

**开源项目**:Linux 内核、Rust 编译器、PostgreSQL 都有明确的 stabilization 阶段。GitHub 的 release 流程常用 `pre-release` 标签区分。

Casey 的 HH 是单人项目,没有正式 stabilization phase,但 Day 535 是事实上的 stabilization——他暂停新功能开发,把连锁 bug 修完。

**对你的项目**:做 Rust 游戏项目,每完成一个大模块(资产管理、音频、网络、AI),留 1-2 天 stabilization。修小 bug + 跑完整测试套件 + 玩一遍游戏验证每个功能正常。这种纪律让你的项目长期健康。



### stabilization 的工程纪律

具体纪律:

**纪律 1:Bug 列表**。重构时发现 bug,不立刻修(打断节奏),记到 todo list。
**纪律 2:Stabilization 日**。重构后专门一天 / 一周修 list 上的 bug。
**纪律 3:Regression test**。每个 bug 修后,加 test 防止再犯。
**纪律 4:No new feature**。Stabilization 期间不加新功能——只修 bug。
**纪律 5:健康度指标**。Stabilization 结束,跑全套测试 + 性能 benchmark,确认无 regression。

工业级实例:

**Linux kernel release cycle**:
- 2 周合并窗口(merge window):接受新功能
- 6-8 周 stabilization:rc1 → rc7,只 bug fix
- 正式发布
- 下个版本循环

**Apple iOS release**:
- 1 年开发
- 6 个月 beta
- 2 个月 final beta(stabilization)
- 正式发布

**Rust release(6 周循环)**:
- 5 周新功能
- 1 周 stabilization(beta 阶段,只接受 critical bug fix)
- 正式发布

**Google Chromium release**:
- 持续集成 + 6 周分支(stabilization 期)

所有大型项目都有这套节奏。Stabilization 不是浪费,是**保障质量的关键**。

### "技术债"和扫尾的关系

Ward Cunningham 提出 **"技术债"** (technical debt) 概念:

每次你"快速实现而不优化"或"重构但没扫尾",你**借了一笔债**。债会**累积利息**——之后每次接触这部分代码,都更难做。

Stabilization 就是**还债**。每个 bug fix = 还一点债。

如果不还:债越累越多,最终 codebase 进入"债务危机"——任何改动需要数月(因为要清理积压的 bug)。这是为什么很多大型项目(Ubuntu Unity、Apple Aperture、Mozilla Servo)最终被废弃——技术债太多,无法维护。

Casey Day 535 演示的是**主动还债**——重构后立刻扫尾,保持 codebase 健康。这是开源黑客的核心习惯。

### "Bug batch"的诊断策略

Casey 这天有 3 个独立 bug(美术、粒子、手套)。如果一次只看一个 bug,你花 30 分钟修;如果同时看 3 个 bug,容易混淆——你不知道某个改动是否影响别的 bug。

工业级 bug batch 处理:

1. **列出所有 bug**(casey 在视频开头列了清单)
2. **按独立性排序**(完全独立的 bug 先修,有依赖的后修)
3. **一次只修一个**(commit per bug,方便 bisect)
4. **每个 bug 修完跑回归测试**(确认没引入新 bug)

Casey 的顺序:美术更新(独立)→ 粒子(依赖资产系统)→ 手套(独立)。这个顺序让每步验证清晰。

#### Git commit 的"per-bug"原则

工业级 git workflow 强调:**每个 bug 一个 commit**。Casey 在视频里没显式说,但他的 HH commit 节奏遵循这个原则。

为什么 per-bug commit:

1. **bisect 友好**:如果有 bug,`git bisect` 能精确定位是哪个 commit 引入
2. **revert 友好**:某个 fix 有副作用,可以单独 revert 而不影响其他 fix
3. **review 友好**:PR 的 reviewer 一次只看一个改动,容易发现错误

反例:**"batch commit"**(一个 commit 改 10 个不相关的 bug)。这种 commit 让 bisect 失败(revert 一个 bug 要 revert 全部),review 困难(reviewer 不知道从哪开始看)。

你的 Rust 项目应该:

```bash
# 错误:批量
git add .
git commit -m "fix various bugs"

# 正确:per-bug
git add particle_fix.rs
git commit -m "fix: particle emitter position after asset refactor"

git add glove_attach.rs
git commit -m "fix: glove alignment offset_y not read correctly"

git add hero_sprite.hht
git commit -m "chore: update hero sprite to new art"
```

这种习惯让 PR 流程顺畅,也让你的 git log 看起来专业。

## 2 · 心智模型

### 类比:搬家后的"找东西日"

你搬家了,所有家具堆在新家。一开始用着没问题——但逐渐发现:

- 牙刷找不到(在某个箱子里)
- 充电器找不到(在另一个箱子)
- 剪刀找不到(在第三个箱子)

搬家日是"大重构",接下来几天是"找东西日"——把每个被搬乱的东西归位。如果不做这一步,生活永远乱糟糟。

代码重构后的扫尾日同样——重构破坏的"小东西"必须修,否则代码永远 buggy。

### 严谨展开:bug 的分类

软件 bug 按来源分:

- **逻辑 bug**:算法错(数学公式错、条件判断反)
- **集成 bug**:模块间接口错(类型不匹配、参数错位)
- **资源 bug**:资产/配置错(路径错、格式不对)
- **回归 bug**:之前能工作,改了别处后坏了

Day 535 修的三个 bug 都是**回归 bug**——大重构破坏的连锁反应。

回归 bug 的特点:**单个 bug 容易修,但发现困难**。因为它们分布在代码各处,大重构时谁也不知道改坏了什么。需要系统测试才能发现。

### Casey 的 bug 调试流程

每个 bug 走标准流程:

1. **复现**:稳定触发(打开游戏、走到 X 位置、按 Y 键、看到错误)
2. **隔离**:缩小到最小测试用例
3. **诊断**:用调试器/日志/printf 找根因
4. **修复**:改最小代码修问题
5. **验证**:再跑一遍,确认 bug 没了

例如手套修复:

1. 复现:启动游戏,装备手套,看到手套在脚边
2. 隔离:用编辑器查看手套的附接点数据
3. 诊断:打印 `attachment.world_position`,发现 y 偏移是 -1。读 alignment point 时 `offset_y` 没读
4. 修复:在 alignment point parser 里加 `offset_y` 字段解析
5. 验证:重跑游戏,手套在手部正确位置

### "扫尾日"的工程价值

为什么大重构后必须扫尾?

- **回归 bug 集中暴露**:重构破坏的小 bug,在持续使用中逐渐暴露
- **新架构磨合**:新代码需要时间找到所有边界情况
- **开发者信心恢复**:连续小修复让团队恢复"代码工作"的信心
- **防止累积**:小 bug 不修会累积成大 bug,届时定位困难

工业级项目每个大重构后,都有 1-2 周的 stabilization 期。Linux 内核、Windows、macOS 都遵循这个节奏。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发的"扫尾"现象:

- **frame analyzer**:逐帧分析渲染调用(NVIDIA Nsight、RenderDoc)
- **shader debugger**:step through shader
- **visual diff**:对比预期 vs 实际输出

Casey 在 Day 535 修手套 bug 时,可能用了 RenderDoc 抓一帧,看附接点的世界坐标。

### 3.3 · Linux 系统编程视角

### 3.4 · Rust 生态视角

Rust 让"扫尾"更容易:

- **编译器拦下集成 bug**:类型错、参数错编译就失败
- **trait 让接口清晰**:不符合 trait 的实现编译报错
- **`#[derive(Debug)]`**:打印中间状态方便调试

Rust 的代价是**编译时间长**,但收益是 runtime bug 少——这是 Rust 的核心卖点。

## 5 · 对照与变奏

**Game studios**:

### "Feature freeze"的具体实践

工业级 stabilization 的核心机制是 **feature freeze**——某个时间点之后,所有新功能 PR 拒绝合并,只接受 bug fix PR。

实施细节:

1. **声明 freeze**:在某次 release meeting 上宣布 "Day X 之后 feature freeze"
2. **CI 加检查**:任何 PR 必须打 `bug fix` 或 `new feature` 标签,后者在 freeze 期被自动 reject
3. **freeze 持续时间**:小项目 1 周,大项目 1-3 月
4. **release 后 unfreeze**:release 完成后重新开放新功能

Rust 编译器团队把这个机制做得很正式。每个 6-week cycle 有 "announcement week"、"development week"、"beta week" 三阶段。你的 Rust 项目可以简化:每个 milestone 前 1 周 feature freeze。

### "Bug bash"活动

工业级团队在 stabilization phase 经常举办 **bug bash**——一群人(开发者、QA、PM)集中 1-2 小时找 bug,谁找的多有奖。

- **Google** 每月有 bug bash,产品全员参加
- **Microsoft** 在 Windows 开发中有 "bug bash week"
- **Game studios** 在 alpha 阶段每周 bug bash

Casey 单人项目的 bug bash 就是"自己玩 30 分钟游戏,记录所有 weird behavior"。这种"自己当玩家"的视角能发现开发者视角看不到的 bug。

学会这套 stabilization 实践,你将来加入任何工业级团队都能立刻融入。



不同项目对 stabilization 的态度:

- **Linux**:严格,stable tree 只接 bug fix
- **Windows**:Service Pack / Cumulative Update
- **macOS**:point release(15.1 → 15.2)
- **Rust edition**:每 3 年一次大版本,中间 stabilization
- **HH 项目**:每 30 集大重构后,几天 stabilization

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 修的三个 bug(美术、粒子、手套),哪个最严重?哪个最容易修?

**参考解答**:严重程度排序:**手套 > 粒子 > 美术**。手套 bug 是 gameplay-critical(玩家直接看到错位,影响体验)。粒子 bug 是 visual polish(游戏可玩,只是少了特效)。美术 bug 几乎不影响(新 sprite 比旧的更好,但游戏本就能玩)。难度排序相反——美术最容易(改个文件路径),粒子中等(代码接口对接),手套最难(需要诊断附接点坐标变换)。**严重 ≠ 难**,这是工程经验。

### Lv2 · 动手实践

**题**:模拟一个"回归 bug"场景。你有一个 working 的 entity 系统,entity 有 position。重构后 position 从 `(x, y)` 变成 `(x, y, z)`。回归 bug:某个调用点没更新,只用 `(x, y)`,z 永远是 0。写一个 Rust 程序:用 Rust 编译器强制让所有调用点都提供 z(让 bug 在编译期暴露)。

**参考解答**:

```rust
// 重构前
#[derive(Debug, Default)]
struct Vec2 { x: f32, y: f32 }

impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
}

// 重构后(用新类型强制更新所有调用)
#[derive(Debug, Default)]
struct Vec3 { x: f32, y: f32, z: f32 }

impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
}

struct Entity { position: Vec3 }

fn move_entity(entity: &mut Entity, delta: Vec3) {
    entity.position.x += delta.x;
    entity.position.y += delta.y;
    entity.position.z += delta.z;
}

fn main() {
    let mut e = Entity { position: Vec3::new(0.0, 0.0, 0.0) };
    
    // 如果调用者试图用 Vec2,编译器报错(因为 move_entity 要 Vec3)
    // move_entity(&mut e, Vec2::new(1.0, 2.0));  // 编译错误!
    move_entity(&mut e, Vec3::new(1.0, 2.0, 0.0));  // OK
    
    println!("{:?}", e.position);
}
```

为什么这么写:Rust 编译器强制类型匹配,如果 `move_entity` 签名要 `Vec3`,所有调用必须提供 z。这就是"让 bug 在编译期暴露"——Rust 比 C++ 更强的原因。

### Lv3 · 迁移设计

**题**:你的 Rust crate 升级了依赖(从 v1 到 v2),v2 的 API 变了。设计一个迁移工具:扫描代码里所有调用 v1 API 的地方,自动改成 v2 API。提示:用 `syn` crate 解析 Rust AST,找到调用点,改写。

### 附录:扫尾日的"心理学"

扫尾日对程序员心理健康有特殊意义。让我们讨论。

#### "完成感"的重要

每个程序员都熟悉这种状态:大重构做完,主流程跑通,你觉得"我搞定了!"。但下一秒你打开 todo list,发现还有 10 个 bug 要修。心情立刻低落。

工业界叫这种现象 **"long tail problem"**——大重构 80% 时间做 80% 工作,剩下 20% 时间做 20% 工作。但这 20% 工作分布在数天 / 数周,感觉"永远做不完"。

应对策略:

1. **接受 long tail**。这是工程现实,不是失败。重构没"做完",只有"够好"。
2. **庆祝 milestone**。每修 5 个 bug,休息一下,记录成就。
3. **优先级排序**。10 个 bug 不一样重要——重要的先修,小 bug 留着。
4. **时间盒**。给扫尾定时间(比如 3 天),时间到,继续推进新功能,小 bug 留下次扫尾。

Casey 在 Day 535 视频里表现出这种成熟——他知道这是 long tail,接受它,系统修。

#### "Broken Windows" 理论

"破窗理论"(来自犯罪学,后被软件工程采用):

> 一栋楼有一扇破窗,如果不修,其他窗也会被破。最终整栋楼废弃。

应用到代码:**如果代码有可见 bug / 坏味道,新 contributor 觉得"这代码本来就乱",于是加更多 bug / 坏味道。最终 codebase 腐烂**。

应对:**主动修"破窗"**。看到 typo 改掉,看到死代码删掉,看到不合理命名改对。每次接触代码都顺手清理。

这是 Bob 大叔的 "Boy Scout Rule"。Day 535 演示的就是这个——重构后扫尾,清理"破窗",保持 codebase 健康。

#### "Bug 修复的多巴胺"

修复 bug 触发 dopamine——你看到"红 → 绿"(test fail → pass),立刻满足。这是程序员工作的快感来源之一。

但 dopamine 有副作用:**只修小 bug 会让你失去大方向**。你一天修 20 个 typo,觉得很 productive,但项目整体没进展。

平衡:**主动分配"大重构"和"小修复"的时间**。比如 70% 时间大重构,30% 时间扫尾。每周 review——"这周我做了什么?是只修小 bug,还是真有进展?"

工业级项目管理用 **sprint planning** 处理这个——每个 sprint(2 周)分 milestone features 和 bug fix 两条线,平衡推进。

#### 实战:为自己项目设计 stabilization phase

如果你在做自己的项目(开源 / 闭源),尝试:

1. **每周 review**。每周花 1 小时,看 todo list,排序 bug。
2. **每 sprint 留 20% stabilization**。比如 2 周 sprint,最后 2-3 天只修 bug,不加新功能。
3. **公开 changelog**。每个版本列出"修了什么 bug",给用户透明度。
4. **bug-burn-down chart**。每周画 bug 数图表,看趋势下降还是上升。

时间预算:1 小时 / 周的 review。回报:**codebase 长期健康,避免技术债危机**。
