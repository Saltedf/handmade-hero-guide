
# Day 544 · 跨帧缓存解包实体

> Day 543 闭环了 sim region → world 的回写。但每次模拟都要把 world → sim region **重新解包**——这重复劳动很费 CPU。Day 544 加一层**跨帧缓存**:上一帧已经解包的 entity,如果还在 sim region 范围内,这一帧不用重新解包,直接复用。

## 0 · 为什么要有这一天

回忆 Day 543 的流程:每帧开始,从 world 里把玩家附近的 entity **clone** 一份到 sim region,模拟完,**clone** 一份回 world。一个 entity 在一帧里被 clone 两次。

如果玩家站着不动,周围 100 个 entity 跨 60 帧都是同样那 100 个——每帧 clone 两次就是 12000 次 clone,全是浪费。**真正变的**只是其中被修改的部分。

更糟的是,clone 不仅仅是字段拷贝——unpacked entity 可能有衍生数据(比如骨骼动画状态、AI pathfinding 上下文),这些数据可能几 KB。每个 entity 4 KB,100 个就是 400 KB / 帧,60 帧就是 24 MB / 秒——纯拷贝,不是有效计算。

Casey 在视频里说,他在做编辑器时第一次发现这个浪费:"我打开编辑器,看一个 entity 的属性,改一下,然后画面上一闪——所有解包的 entity 都重新生成了一遍,因为我移动了一帧。"这迫使他加缓存。

完成这一天之后,你具备:

- 理解"帧间数据复用"模式
- 能正确处理缓存的失效(invalidation)——什么时候该丢
- 知道 ECS 框架的 archetype 缓存是怎么做的
- 体会到"缓存失效是最难的两个问题之一"(另一个是命名),学会**保守失效**的工程纪律
- 在自己的项目里设计 dirty flag / generation counter,知道何时用 dirty bit、何时用 generation、何时用 hash

### 0.1 · 这一集的真正难度:不在实现,在"什么时候失效"

很多人看 day 544 的代码会觉得"不就是加个 generation 字段吗,有什么难的"。这个想法是对的——**实现确实不复杂**,代码不到 100 行。但 day 544 真正的复杂度在**失效策略的设计**。

具体说:你必须**枚举所有可能让 unpacked entity "变旧"的事件**,给每个事件决定"要不要 +1 generation"。这个枚举永远不完整——只要你漏掉一个,游戏就出现诡异 bug。漏掉"玩家传送"事件,玩家传送到新位置后,周围 entity 显示的还是老 unpacked 状态(因为缓存 hit 了);漏掉"编辑器改属性"事件,编辑器改了玩家看不见效果。

Casey 在视频里反复强调:**"保守失效"优于"精确失效"**。宁可多 +1(白白重新解包,慢一点点),也不要漏 +1(数据错乱,bug 难查)。这是工程现实主义——精确性需要复杂的"依赖追踪",保守只要"宁可错杀不可放过"。

这种思维方式在软件工程里反复出现。CPU 的 cache coherence(MESI 协议)也是宁可过度 invalidate 也不要让两个核看到不一致数据。Linux 内核的 RCU grace period 也是宁可等长一点也不允许提前回收。Day 544 的训练让你内化这种"保守优先"的工程直觉。

## 1 · Casey 今天做了什么

Casey 的做法是给每个 unpacked entity 加一个 **generation counter**(代际计数器):

第一步,在 world 里给 entity slot 加 `unpacked_generation: u32` 字段。每次 entity 被解包,generation +1。

第二步,在 sim region 里持有 unpacked entity 时,记录它的 generation。下次需要解包时,先查 world——如果 world 里这个 entity 的 generation 没变(说明没被修改),就复用 sim region 里的旧副本,不重新解包。

第三步,显式的**失效路径**——当 entity 跨 chunk 边界、被攻击、被传送等"结构性变化"时,generation +1,强制下一帧重解包。

视频里他特别强调:缓存失效是**最危险的**——一旦漏掉某个失效点,缓存里的旧数据会让游戏出现"打了没反应""走到墙里"等诡异 bug。所以他的失效策略是 **保守失效**——宁可多失效几次,也不漏。

## 2 · 心智模型

### 类比:图书馆的借书卡

想象 world 是图书馆,**每个 entity 是一本书**。Sim region 是你的书桌。

旧的做法:每天早上你出门时把书桌上的书**全部还回图书馆**,傍晚回家时**重新借**——哪怕这本书你昨天就在读,而且没人动过。

新的做法:在书的封底盖一个**版本号戳**。每次图书馆修改这本书(比如编目员改了它的分类号),版本号 +1。你出门时只把"图书馆里版本号变了"的书还回去重借,其他保留在书桌上。

这样:如果一本书没人动,你保留它,不浪费一次"还书+借书"的动作。

但是这个机制有个陷阱:你必须**正确地**给书盖版本号戳。如果图书馆某次改了书但忘了盖戳,你书桌上还是老版本——读到的内容是错的。

### 严谨展开:Generation counter

让我们把 generation counter 的每个细节说清楚,你才能在自己的项目里复用这个模式。

```rust
// WorldEntity 是 world 里的紧凑存储。我们加一个 generation 字段。
struct WorldEntity {
    id: EntityId,
    pos: [f32; 3],
    health: i32,
    // 新增:这个 entity 自上次解包以来,被修改了几次。
    // 用 u32 而不是 u64——u64 太大,而且 wrapping_add 后 u32 也够 40 亿帧。
    unpacked_generation: u32,
}

// 缓存条目:每个被解包过的 entity 在这里存一份
struct CachedUnpacked {
    // 缓存的副本本身
    entity: UnpackedEntity,
    // 解包时记下的 generation —— 用于和 world 当前的 generation 对比
    generation: u32,
}

// 帧开始:试图复用缓存。
// 返回值是这一帧要用的 unpacked entity 列表,顺带 hit/miss 统计供调试
fn try_reuse_cache(
    world: &World,
    cache: &mut HashMap<EntityId, CachedUnpacked>,
    needed_ids: &[EntityId],
) -> Vec<UnpackedEntity> {
    let mut result = Vec::with_capacity(needed_ids.len());  // 预分配,避免多次 realloc
    for id in needed_ids {
        let world_ent = world.entities.get(id).unwrap();
        if let Some(cached) = cache.get(id) {
            // 缓存里有,且 generation 相同 → 复用
            if cached.generation == world_ent.unpacked_generation {
                // 重要:clone 是必要的,因为 result 是 owned,cache 里也要保留
                // 如果 UnpackedEntity 大,可以用 Rc<UnpackedEntity> 共享所有权
                result.push(cached.entity.clone());
                continue;
            }
            // generation 变了,缓存里的版本过期,要重解包(fall-through 到下面)
        }
        // 缓存 miss 或 generation 变了 → 重新解包
        let unpacked = unpack(world_ent);
        // 同时更新缓存(下次同样 generation 还能 hit)
        cache.insert(id.clone(), CachedUnpacked {
            entity: unpacked.clone(),
            generation: world_ent.unpacked_generation,
        });
        result.push(unpacked);
    }
    result
}
```

这段代码的关键设计:

**第一,generation 用 u32 不是 u64**。40 亿帧 = 60FPS 跑 778 天,实际游戏跑不到。如果真超了,`wrapping_add` 让它环绕——只要对比的是 `==` 而不是 `>`,环绕也没问题。

**第二,缓存的"写入"和"读取"在同一函数里**。这避免了"先批量 miss,再批量更新"的两阶段,简化代码。代价是 cache 在循环中频繁 borrow,但 HashMap 的 borrow 开销很小。

**第三,clone 是必要的**。如果你不想 clone,可以用 `Rc<UnpackedEntity>` 共享所有权,但 Rc 有 atomic refcount 开销。教学版用 clone,工程版可能用 Arena + handle。

**第四,没有"主动失效"路径**。失效是**隐式**的——world 那边 `unpacked_generation += 1`,下次 cache lookup 时自然 miss。这种设计避免了"两个独立路径都要管缓存"的复杂度。

### 失效的"哪些事件要 +1"

这是个枚举式的苦力活——必须列出所有"会让 entity 状态变化"的事件:

| 事件 | 是否 +1 | 原因 |
|---|---|---|
| 玩家移动 | 否(只动自己) | 自己的解包状态自动跟 |
| 受伤(health 变) | 否 | 解包实体的 health 字段在 sim 内改,world 同步 |
| 跨 chunk 边界 | 是 | entity 现在属于另一个 chunk,sim region 范围变了 |
| 传送 | 是 | 位置突变,旧的"附近"列表失效 |
| 死亡 | 是 | entity 不再存在,sim region 缓存里的副本作废 |
| 出生 | 是(新 entity) | 新 entity 没有 generation,必须首次解包 |
| 编辑器改属性 | 是 | 强制刷新,确保编辑器看到最新 |

注意:**"受伤"不加 generation**——因为 health 是 mutable 字段,sim region 内部直接改 sim 副本,然后 patch 回 world,world 的 health 也变了,但 generation 没必要 +1(缓存里 health 是被同步更新的)。

### 缓存的内存代价

100 个 entity,每个解包副本 4 KB,缓存占 400 KB——一直驻留。如果你担心,可以加 LRU(least recently used)淘汰:超过 N 个就把最久没用的踢掉。

Handmade Hero 没加 LRU,因为 unpacked entity 数据量可控(几百 KB),不值得为这点内存加复杂度。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发里这个模式叫 **dirty flag**(脏标记)或 **coherency tracking**(一致性追踪)。

典型用例:

- **光照烘焙**:静态物体(墙、地板)的光照预算一次烘焙,缓存;物体移动才重算
- **动画系统**:骨骼 Pose 缓存,只在动画状态变时重算
- **物理 broadphase**:AABB 树缓存,只在物体移动时更新对应节点
- **UI layout**:计算一次,父 widget 尺寸变化才重算

Unreal 的 `UPrimitiveComponent` 有 `MarkRenderStateDirty()`,Unity 有 `SetDirty()`——都是这个模式。

让我把 Unreal 的 dirty flag 系统展开讲。Unreal 里每个 `UObject` 都有 `Modified()` 方法,被调用时触发一系列 dirty 通知。比如 `UPrimitiveComponent::SetWorldLocation()` 内部会调用 `MarkRenderStateDirty()`,标记"渲染数据过期",下一帧 render thread 会重新同步。这和 day 544 的"generation +1 → 下次解包 miss"完全对偶。

Unreal 还有一个更精细的系统叫 `FCoreUObjectDelegates::OnObjectModified`,这是一个广播委托——任何订阅者都能在对象修改时收到通知。这让"多个系统关心同一对象的修改"变得可扩展。比如同时有渲染系统、物理系统、AI 系统关心 entity 修改,它们各自订阅,互不干扰。

Unity 的 `Undo.RecordObject` + `SetDirty` 组合类似。Unity 还有个 `EditorUtility.SetDirty`,专门用于编辑器扩展——告诉 Unity "这个对象变了,需要保存到场景文件"。这是 dirty flag 在持久化层面的应用。

Godot 用不同的方案——节点有 `notification` 系统,父节点修改会向子节点广播。本质上还是 dirty flag,只是用消息传递表达。

### 3.2 · Rust 生态视角

Rust 用 ownership + borrow 强制约束共享数据,但缓存这种"读取时 lazily 构造"的模式用以下工具:

- **`once_cell::Lazy`**:第一次访问时初始化,之后返回缓存值。适合"全局只算一次"的场景。
- **`memoize` crate**:把函数调用结果按参数缓存。适合纯函数。
- **`cached` crate**:更通用的 memoize,支持 LRU/TTL。适合 Web 服务的热点查询缓存。
- **`dashmap`**:线程安全的缓存 map。多线程读多线程写时的首选。
- **`moka`**:工业级 cache,支持 LRU、LFU、TTL、size-based eviction。Tokio 生态常用。

如果 generation 用 atomic,可以做到 lock-free 多读:

```rust
use std::sync::atomic::{AtomicU32, Ordering};

struct WorldEntity {
    unpacked_generation: AtomicU32,
}

impl WorldEntity {
    fn touch(&self) {
        // Release:确保 touch 之前的所有写操作对后续 Acquire 可见
        self.unpacked_generation.fetch_add(1, Ordering::Release);
    }
    fn current_gen(&self) -> u32 {
        // Acquire:看到 touch 的 Release,确保看到最新的 entity 状态
        self.unpacked_generation.load(Ordering::Acquire)
    }
}
```

这里 Release / Acquire 的语义解释:当线程 A 调用 `touch()`(Release),它会先把 entity 的字段写好,再 fetch_add generation。线程 B 调用 `current_gen()`(Acquire),如果读到的 generation ≥ A 写入的值,那 A 之前写的所有字段都对 B 可见。这就是 lock-free 一致性。

但要注意:**AtomicU32 的 fetch_add 不保证 "如果两个线程同时 touch,generation 一定加 2"**。两个线程并发 touch,generation 至少加 1(可能加 2),但缓存逻辑只关心"generation 变了吗",所以这种语义足够。

Bevy 的 `Ticks` 字段是工业级实现——它记录"上次添加 component"和"上次修改 component"的 tick。`Changed<T>` filter 通过对比 tick 决定是否触发。这套机制比 day 544 的 generation 更精细,因为区分了"Added"(首次)和"Changed"(后续)两种语义。

### 3.3 · Linux 系统编程视角

Linux 内核大量用 dirty flag:

- **Page cache**:`PG_dirty` 标志,page 被写时设置,定期 writeback。Linux 的 `write()` 默认只进 page cache,后台 pdflush 线程定期扫描 dirty page,writeback 到磁盘。这就是"延迟失效 + 批量回写"。
- **Inode**:inode 的 `i_state` 有 `I_DIRTY`,inode 变化时设置。`fsync()` 强制把 dirty inode 写回磁盘。
- **MMU page table**:页表项的 dirty bit,CPU 写时硬件自动设。操作系统用这个 bit 实现 copy-on-write(COW)——fork 时页表都标 read-only,写时 trap,OS 看 dirty bit 决定是否复制页。
- **VFS dentry**:目录项缓存,有 refcount 和 LRU。

generation counter 是 dirty flag 的"加强版"——不仅知道"脏了",还知道"脏了几次",可以做更精细的失效决策。

让我用一个具体的 Linux 例子说明。假设你写一个文件系统监控工具:

```c
// 监控 /etc 目录变化
int fd = inotify_init1(IN_NONBLOCK);
int wd = inotify_add_watch(fd, "/etc", IN_MODIFY | IN_CREATE | IN_DELETE);

// 读取事件
char buf[4096] __attribute__((aligned(4)));
ssize_t len = read(fd, buf, sizeof(buf));
// 处理 buf 里的 inotify_event 结构
```

`inotify` 就是 Linux 的"generation counter"——内核维护一个 watch 列表,文件变化时往 fd 写事件。用户态读取事件做对应处理。这和 HH 的"world 那边 touch → sim region 那边 miss cache"是同样的模式,只是事件传递通过 fd 而不是字段对比。

### 3.4 · 图形学视角

GPU 也有类似机制。Vulkan 的 `VkAccessFlagBits` 标注资源在不同阶段的访问,driver 据此做 cache invalidation。

`glInvalidateFramebuffer`(OpenGL)/`vkCmdInvalidateAttachment`(非标准)告诉 driver "这个 framebuffer 后面不用了,可以扔"——也是显式的缓存失效。

让我深入讲 Vulkan 的资源 transition。GPU 资源(texture、buffer)在不同 pipeline 阶段(vertex shader、fragment shader、transfer)有不同的"理想 layout"。比如 texture 在 shader 读时是 `SHADER_READ_ONLY_OPTIMAL`,在 transfer 写时是 `TRANSFER_DST_OPTIMAL`。切换 layout 需要 **pipeline barrier**:

```cpp
vkCmdPipelineBarrier(
    cmd,
    SRC_STAGE_MASK,
    DST_STAGE_MASK,
    0,
    0, nullptr,
    0, nullptr,
    1, &image_memory_barrier  // 这里指定 layout 转换
);
```

pipeline barrier 本质就是"告诉 driver:之前对这块内存的所有写,后续读必须看到"。这就是 GPU 端的"缓存一致性维护"。现代 GPU 有 L1/L2 cache、TLB、texture cache,driver 要协调所有这些 cache 的 invalidate / flush。barrier 是程序员给 driver 的提示。

`glInvalidateFramebuffer` 是反向操作——告诉 driver "这个 framebuffer 的内容我后面不需要了,你可以扔掉它的 cache 内容,不要 writeback 到主存"。这是显式的 cache 丢弃,节省带宽。在移动 GPU 上(带宽紧张)用得特别多。

## 4 · 认知地图

### 4.1 上级

- **Memoization** —— 把函数结果按参数缓存
- **Dirty flag pattern** —— 标记变化,延迟重算
- **Coherency tracking** —— 多份数据间维护一致

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Generation counter | 精确,但每字段都得维护 | 复杂数据 | **是** |
| Dirty bit | 简单,只能问"脏不脏" | 二值语义 | 否(粒度粗) |
| Hash 比较 | hash 值变了就失效 | 难枚举变化源 | 否(开销) |
| 全量重算 | 不缓存 | 数据小 | 否 |

### 4.3 下级

- **Generation counter** —— 自上次解包的修改次数
- **Invalidation points** —— 触发 +1 的事件列表
- **Cache miss path** —— 找不到/失效时的 fallback 逻辑

## 5 · 对照与变奏

游戏行业对此有不同做法:

- **ECS archetype caching**:Bevy 等用 archetype(组件组合)做缓存键。同 archetype 的 entity 共享布局,query 时一次取出
- **Snapshot + diff**:每帧做 world snapshot,下一帧 diff 出变化。开销大但实现简单
- **Event sourcing**:所有变化作为 event 存储,订阅者按需更新

工业级 vs 教学版的差别:工业级缓存通常多级(L1/L2/L3),每级容量和失效策略不同;教学版单级够用。

历史:早期游戏因为内存小,普遍**不缓存**——重新算反而省内存。到 2000 年代大世界出现,缓存成为标配。Quake 3 的 BSP PVS(potentially visible set)就是经典缓存案例。

### 5.1 把"缓存 + 失效"放到更广的工程语境

让我把"缓存 + 失效"这个模式在不同领域的对应写出来,你会看到 day 544 不是孤例:

**CPU 硬件层**:CPU 的 L1/L2/L3 cache 就是"用 dirty bit 维护一致性"。MESI 协议(Modified / Exclusive / Shared / Invalid)用 2 bit 状态机维护 cache line 的一致性。当一个核修改某个 cache line,其他核里同一 line 的副本被标 Invalid(失效)。这就是 generation counter 的硬件版——只是状态简化到 2 bit 而不是 u32。

**操作系统层**:Linux 的 dentry cache 缓存"路径 → inode"映射,inode 变化时通过 dentry invalidate 通知。page cache 的 PG_dirty 标记"内存和磁盘不一致",writeback 时清除。这些都是 dirty flag 的不同实现。

**数据库层**:PostgreSQL 的 MVCC(多版本并发控制)用 xmin/xmax 事务 ID 做"版本"——和 generation counter 同构。每个 row 有创建事务 ID 和删除事务 ID,查询时根据当前事务的可见性判断版本是否可见。这就是带版本控制的缓存。

**Web 缓存层**:HTTP 的 `ETag` 和 `If-None-Match` 是 generation counter 的 HTTP 版本。服务器给资源一个 ETag(版本 hash),客户端缓存时记下 ETag。下次请求带 `If-None-Match: <etag>`,服务器对比,相同则返回 304(用缓存),不同返回 200(新内容)。

**Git 版本控制**:Git 的 commit hash 就是"整个仓库的 generation"。`git status` 对比工作区和 HEAD,告诉你哪些文件"脏了"。`git stash` 是把脏修改暂存。Git 的整个模型就是"内容寻址的 generation counter"。

**React 前端**:React 的 `useMemo` / `useCallback` 是 day 544 模式的直接对应——deps 数组变化时缓存失效,否则复用。React 的 reconciler 用 virtual DOM diff 决定哪些组件需要 re-render,本质上也是 generation 对比。

理解这一层后,day 544 的"generation counter + cache"就不再是一个具体的 Rust 代码技巧,而是软件工程最基础的 pattern 之一。**任何"重复计算 + 偶尔变化"的场景都适用**。

### 5.2 历史:从"全部重算"到"精细缓存"

让我把缓存策略在游戏开发里的历史演化画成一条线:

- **1980s**:全部重算。世界小,CPU 慢,内存贵——重新算反而省内存。
- **1990s**:静态烘焙。光照、路径、LOD 等离线计算,运行时直接用。Quake 的 lightmap 是经典案例。
- **2000s**:运行时 dirty flag。大世界出现,运行时计算预算紧。Unreal 3 的 `MarkRenderStateDirty` 是这个时代的标志。
- **2010s**:细粒度 ECS cache。Bevy、Unity DOTS 用 archetype + tick 做精确缓存。粒度从"整个 entity"细到"单个 component"。
- **2020s**:预测性缓存。机器学习预测哪些 entity 可能变化,提前预热缓存。这种模式在大型 MMO 里开始出现。

HH 走的是 2000s 这条路——粗粒度 dirty flag。Casey 故意不用细粒度 ECS cache,因为 HH 的目标是教底层,而不是教框架。但你看 Bevy 的源码,会发现 day 544 的 generation 是 Bevy `Ticks` 的简化版——同样的思想,不同的实现细节。

### 5.3 类比表:不同"缓存 + 失效"系统

让我们把这个模式抽象到最一般的形式:

| 系统 | 缓存内容 | 失效机制 | 失效粒度 |
|---|---|---|---|
| HH sim cache | unpacked entity | generation counter | per-entity |
| CPU L1 cache | cache line | MESI protocol | per-cache-line |
| Linux page cache | 文件页 | PG_dirty + writeback | per-page |
| Browser HTTP cache | 资源 | ETag + If-None-Match | per-resource |
| Redis | key-value | TTL / LRU / explicit | per-key |
| React useMemo | 函数结果 | deps array diff | per-call |
| Bevy Changed<T> | component | Ticks | per-component |
| Git index | 文件状态 | content hash | per-file |

每一行都是"缓存 + 失效"模式的实例。理解 day 544 后,你看所有这些系统都会觉得"哦,本质都一样"——缓存是优化,失效是正确性,两者必须配套。**漏失效就是 bug,过失效就是浪费**。这是软件工程永恒的张力。

### Lv1 · 概念辨析

**题**:如果某个 unpacked entity 一直没人改,但玩家在它附近来回走,缓存里有它。某天有人在编辑器里改了它的 health 字段。如果**忘了** generation +1,会发生什么?

**参考解答**:缓存里的副本还是老 health。下次解包时检查 generation——没变,复用缓存。结果游戏里看到的是**旧 health**(编辑前的值),而 world 里已经是新值——两个数据不一致。玩家会感觉"编辑器改了没生效"。这就是为什么"失效策略必须保守"——宁可多 +1 也别漏。

### Lv2 · 动手实践

**题**:基于 Day 543 的代码,加跨帧缓存。要求:

- World entity 加 `unpacked_generation: u32` 字段
- Sim region 持有一个 `HashMap<EntityId, CachedUnpacked>`,跨帧存活
- 模拟 3 帧,第 1 帧和第 3 帧有 entity 被攻击(generation +1)
- 打印每帧的 cache hit / miss 数

**参考解答**:

```rust
use std::collections::HashMap;

#[derive(Clone, Debug, PartialEq, Hash, Eq)]
struct EntityId(u64);

#[derive(Clone, Debug)]
struct WorldEntity {
    id: EntityId,
    health: i32,
    unpacked_generation: u32,
}

impl WorldEntity {
    fn touch(&mut self) {
        self.unpacked_generation += 1;
    }
}

#[derive(Clone, Debug)]
struct UnpackedEntity {
    id: EntityId,
    health: i32,
}

#[derive(Clone)]
struct CachedUnpacked {
    entity: UnpackedEntity,
    generation: u32,
}

struct World {
    entities: HashMap<EntityId, WorldEntity>,
}

impl World {
    fn pack_sim(
        &self,
        needed_ids: &[EntityId],
        cache: &mut HashMap<EntityId, CachedUnpacked>,
    ) -> (Vec<UnpackedEntity>, usize, usize) {
        let mut result = Vec::new();
        let mut hits = 0;
        let mut misses = 0;

        for id in needed_ids {
            let world_ent = self.entities.get(id).unwrap();
            if let Some(cached) = cache.get(id) {
                if cached.generation == world_ent.unpacked_generation {
                    result.push(cached.entity.clone());
                    hits += 1;
                    continue;
                }
            }
            let unpacked = UnpackedEntity {
                id: id.clone(),
                health: world_ent.health,
            };
            cache.insert(id.clone(), CachedUnpacked {
                entity: unpacked.clone(),
                generation: world_ent.unpacked_generation,
            });
            result.push(unpacked);
            misses += 1;
        }
        (result, hits, misses)
    }
}

fn main() {
    let mut world = World { entities: HashMap::new() };
    world.entities.insert(EntityId(1), WorldEntity {
        id: EntityId(1), health: 100, unpacked_generation: 0,
    });
    world.entities.insert(EntityId(2), WorldEntity {
        id: EntityId(2), health: 100, unpacked_generation: 0,
    });

    let mut cache: HashMap<EntityId, CachedUnpacked> = HashMap::new();
    let ids = vec![EntityId(1), EntityId(2)];

    // 第 1 帧
    let (ents, h, m) = world.pack_sim(&ids, &mut cache);
    println!("Frame 1: hits={} misses={}", h, m);  // 0, 2

    // 第 2 帧:没人改,全 hit
    let (ents, h, m) = world.pack_sim(&ids, &mut cache);
    println!("Frame 2: hits={} misses={}", h, m);  // 2, 0

    // 第 3 帧:entity 1 被攻击,touch()
    world.entities.get_mut(&EntityId(1)).unwrap().touch();
    let (ents, h, m) = world.pack_sim(&ids, &mut cache);
    println!("Frame 3: hits={} misses={}", h, m);  // 1, 1
}
```

## 8 · Rust / Arch 落地代码

完整 generation + cache 的最小实现:

```rust
use std::collections::HashMap;

#[derive(Clone, Debug, PartialEq, Eq, Hash)]
struct EntityId(u64);

#[derive(Clone, Debug)]
struct WorldEntity {
    id: EntityId,
    pos: [f32; 3],
    health: i32,
    gen: u32,  // generation
}

impl WorldEntity {
    fn invalidate(&mut self) {
        self.gen = self.gen.wrapping_add(1);
    }
}

struct World {
    entities: HashMap<EntityId, WorldEntity>,
}

impl World {
    fn new() -> Self {
        World { entities: HashMap::new() }
    }

    fn insert(&mut self, e: WorldEntity) {
        // 新 entity 默认 gen=0
        self.entities.insert(e.id.clone(), e);
    }

    fn get_mut(&mut self, id: &EntityId) -> Option<&mut WorldEntity> {
        self.entities.get_mut(id)
    }
}

#[derive(Clone, Debug)]
struct UnpackedEntity {
    id: EntityId,
    pos: [f32; 3],
    health: i32,
}

struct CachedUnpacked {
    entity: UnpackedEntity,
    gen: u32,
}

struct SimCache {
    entries: HashMap<EntityId, CachedUnpacked>,
}

impl SimCache {
    fn new() -> Self {
        SimCache { entries: HashMap::new() }
    }

    // 解包一个 entity,优先复用缓存
    fn get_or_unpack(&mut self, world: &World, id: &EntityId) -> UnpackedEntity {
        let world_ent = world.entities.get(id).unwrap();
        if let Some(cached) = self.entries.get(id) {
            if cached.gen == world_ent.gen {
                // 复用缓存
                return cached.entity.clone();
            }
        }
        // 缓存 miss 或失效,重新解包
        let unpacked = UnpackedEntity {
            id: world_ent.id.clone(),
            pos: world_ent.pos,
            health: world_ent.health,
        };
        self.entries.insert(id.clone(), CachedUnpacked {
            entity: unpacked.clone(),
            gen: world_ent.gen,
        });
        unpacked
    }
}

fn main() {
    let mut world = World::new();
    world.insert(WorldEntity {
        id: EntityId(1), pos: [0.0; 3], health: 100, gen: 0,
    });
    world.insert(WorldEntity {
        id: EntityId(2), pos: [1.0, 0.0, 0.0], health: 80, gen: 0,
    });

    let mut cache = SimCache::new();
    let ids = vec![EntityId(1), EntityId(2)];

    // 模拟 5 帧
    for frame in 1..=5 {
        let mut unpacked_ents: Vec<UnpackedEntity> = Vec::new();
        for id in &ids {
            unpacked_ents.push(cache.get_or_unpack(&world, id));
        }

        // 帧 3:entity 1 被攻击,血量变化 + 失效
        if frame == 3 {
            let e = world.get_mut(&EntityId(1)).unwrap();
            e.health -= 30;
            e.invalidate();
        }

        // 帧 5:entity 2 跨 chunk 边界,失效
        if frame == 5 {
            let e = world.get_mut(&EntityId(2)).unwrap();
            e.pos = [2.0, 0.0, 0.0];
            e.invalidate();
        }

        println!(
            "Frame {}: ent1.health={} ent2.health={}",
            frame,
            unpacked_ents[0].health,
            unpacked_ents[1].health,
        );
    }
}
```

预期输出:

```
Frame 1: ent1.health=100 ent2.health=80    // 缓存初始化
Frame 2: ent1.health=100 ent2.health=80    // 全 cache hit
Frame 3: ent1.health=70  ent2.health=80    // ent1 失效重解包
Frame 4: ent1.health=70  ent2.health=80    // 全 hit
Frame 5: ent1.health=70  ent2.health=80    // ent2 pos 变但 health 没变
```

注意 Frame 5:ent2 的 `pos` 已经在 world 里变了,但因为缓存复用了旧的 unpacked,所以 unpacked 里的 `pos` 还是旧值。这就是为什么 unpacked 里只放**mutable 字段**——pos 不在 sim 内修改,而是直接 invalidate 重解包。
