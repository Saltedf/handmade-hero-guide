# Day 516 · 重写 HHT

> Day 509-515 都是"读 HHT"。Day 516 反向:**写 HHT**——把内存里的 entity 数据写回 HHT 文件。这让用户在编辑器里改的数据可以保存为文本,易 diff。

## 0 · 为什么要有这一天

### 真实场景:为什么需要"写 HHT"

你跟着 Casey 做到 Day 515。游戏能读 HHT,构建 entity,渲染 sprite。但**用户在 in-game editor 里改了一个 alignment point 的位置,怎么保存?**

如果不实现"写 HHT",用户改了数据,游戏一关,数据丢了。下次启动游戏,alignment point 又回到原位。这意味着 in-game editor 是"玩具"——不能真用。

到 Day 515,游戏读 HHT 构建 entity。但如果用户在编辑器改了 alignment point 位置,怎么保存?

两种选择:

1. **存 HHA**:二进制,紧凑,但不可读
2. **存 HHT**:文本,可读,易 diff / merge

工业级选 HHT。原因:

- **Git diff 友好**:文本文件可以 diff,二进制不行
- **手工编辑**:设计师可以打开 HHT 改
- **Merge**:多人协作时,文本文件可以 merge

Day 516 实现 HHT 写入器——内存 entity → 文本 HHT。

### 为什么文本格式 > 二进制格式

工业界对"资产文件"格式有强烈偏好——**文本格式 vs 二进制格式**。让我们深度对比。

**二进制格式(HHA、ZIP、PNG)**:
- 优点:紧凑(30-70% 压缩)、加载快(直接 memcpy)
- 缺点:不可读、不可 diff、不可 merge、修一个字节可能整个文件坏

**文本格式(HHT、JSON、YAML、XML)**:
- 优点:可读、可 diff、可 merge、可手写、版本控制友好
- 缺点:冗长(30-100% 膨胀)、需要 parser

游戏开发的标准做法:**两套格式并存**。源格式是文本(HHT),便于设计师 / 程序员编辑;发布格式是二进制(HHA),便于运行时加载。**构建时**从 HHT 转换成 HHA(`make` 或 `cargo cook`)。

工业级类比:
- **图像**:源是 PSD(Photoshop)或 SVG,发布是 PNG / WebP
- **3D 模型**:源是 BLEND(Blender)或 FBX,发布是 glTF 或自定义二进制
- **音频**:源是 WAV(无损),发布是 OGG / OPUS(有损压缩)
- **代码**:源是 .rs / .ts / .py,发布是 .exe / .wasm / .pyc

每一对都是"源文本 / 可编辑格式 → 发布二进制 / 紧凑格式"。

### 文本序列化的工业标准

工业界的文本格式选择:

**JSON**:最普及,Web 标准。语法简单,但没注释、没多行字符串。
**YAML**:人类友好,支持注释、多行、引用。但 spec 极复杂。
**TOML**:配置文件首选。Rust Cargo.toml 用。
**XML**:企业级(配置、SOAP)。冗长但 schema 强。
**Custom (HHT)**:领域特定,语法精确匹配需求。

HHT 是 Casey 自定义格式,理由:**领域特定 + 教学**。生产环境通常用 TOML 或 JSON。

### 写入 vs 读取的对称性

读 HHT 是 **text → AST**:
```
"entity hero {\n  piece body {\n    sprite: hero.png\n  }\n}"
   ↓ tokenize
   ↓ parse
Entity { name: "hero", pieces: [Piece { name: "body", sprite: "hero.png" }] }
```

写 HHT 是反向 **AST → text**:
```
Entity { name: "hero", pieces: [Piece { name: "body", sprite: "hero.png" }] }
   ↓ format
"entity hero {\n  piece body {\n    sprite: hero.png\n  }\n}"
```

**关键**:读和写必须对称——读出的 AST,再写回文本,应该得到**等价的文本**(可能空白不同,但语义相同)。

这是 round-trip 测试的核心:**read(text) → write → 应该等价于 read(text)**。

如果不对称,会有 bug:
- 读:识别 `piece` keyword
- 写:输出 `Piece`(大写 P)
- 重新读:`Piece` 是 unknown keyword,parse 失败

工业级解决:测试覆盖所有 keyword / value 的 round-trip。

- **格式设计**:HHT 格式读 + 写必须对称
- **数据持久化**:用户改的数据怎么存

**第三步,处理嵌套**。Piece 在 entity 内,缩进 4 空格。Alignment point 在 piece 内,缩进 8 空格。Parent 引用在 piece 内,缩进 8 空格。

```rust
fn write_piece(p: &Piece, indent: usize) -> String {
    let pad = " ".repeat(indent);
    let mut s = String::new();
    s.push_str(&format!("{}piece {} {{\n", pad, p.name));
    s.push_str(&format!("{}    sprite = \"{}\"\n", pad, p.sprite));
    for ap in &p.alignment_points {
        s.push_str(&format!("{}    alignment_point {} = ({}, {})\n",
            pad, ap.name, ap.offset.x, ap.offset.y));
    }
    s.push_str(&format!("{}}}\n", pad));
    s
}
```

每次进入新嵌套层,`indent += 4`。退出,`indent -= 4`。

**第四步,处理元组**。`(x, y)` 格式。X、Y 是 f32,直接 `format!("{}", x)`。注意 -0 vs 0(规范化)、整数无小数点(1.0 → "1")。

**第五步,加注释**(可选)。某些字段自动加注释,帮助读:

```
entity hero {    # entity 名
    piece body {    # piece 名
        sprite = "hero_body"    # sprite 文件
    }
}
```

Casey 在演示里加少量注释,生产级 HHT 加更多。

**第六步,加 round-trip 测试**。读 HHT → 内存 → 写 HHT → 文本 → 读 HHT → 内存。两个内存对象应该相等:

```rust
#[test]
fn test_round_trip() {
    let text1 = r#"
entity hero {
    piece body {
        sprite = "hero_body"
        alignment_point neck = (0, -20)
    }
}
"#;
    let ast1 = parse_hht(text1).unwrap();
    let text2 = write_hht(&ast1);
    let ast2 = parse_hht(&text2).unwrap();
    assert_eq!(ast1, ast2);    // round-trip 一致
}
```

这验证读 / 写对称。如果不等,有 bug——例如读识别 `piece`,写输出 `Piece`,重新读时 `Piece` 是 unknown keyword,parse 失败。

### Round-trip 一致性的深层意义

Round-trip 测试看似简单,实际暴露格式设计的微妙问题:

**问题 1:默认值**。读时某字段省略(用默认),写时要不要写出来?如果写出来,round-trip 不一致(原文没,生成文有)。

**问题 2:浮点精度**。读 `0.1`,内部存 f32,写时输出 `0.100000001`(浮点精度损失)。重新读,得到略不同的 f32。严格 round-trip 要求"规范浮点格式"。

**问题 3:字符串转义**。读 `"a\"b"`,内存存 `a"b`,写时输出 `"a\"b"`(转义 `"` 为 `\"`)。如果写时忘了转义,重新读 parse 错。

**问题 4:字段顺序**。读时不要求顺序(sprite 在 alignment_point 前后都行)。写时固定顺序(sprite 先)。重新读,内存对象一致(但文本不一定一致)。

工业级 pretty printer(rustfmt、prettier)定义"canonical form"——所有等价输入 format 后输出同一文本。这样:
- 用户随便写,format 后变 canonical
- diff 干净(canonical 之间才能 diff)
- 工具链统一

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 HHT 文本格式比 HHA 二进制更适合"用户编辑"?

**参考解答**:三个理由:

第一,**可读**。设计师可以打开 HHT 看懂。HHA 二进制,只有专门工具能读。

第二,**diff 友好**。Git diff 文本立即看出改了什么(改 alignment point 位置)。HHA 二进制 diff 全是乱码。

第三,**手工编辑**。设计师可以 vim HHT 改一行。HHA 必须用工具。

代价:文本比二进制大、解析慢。但用户编辑场景,这些不重要。

**题**:实现 HHT writer。给定内存 entity,写文本 HHT。round-trip 测试。

完成标准:`cargo run` 显示写入的 HHT 文本,round-trip 一致。

**参考解答**:

```rust
#[derive(Debug, Clone, PartialEq)]
struct Vec2 { x: f32, y: f32 }

#[derive(Debug, Clone, PartialEq)]
struct AlignmentPoint { name: String, offset: Vec2 }

#[derive(Debug, Clone, PartialEq)]
struct Piece {
    name: String,
    sprite: String,
    alignment_points: Vec<AlignmentPoint>,
    parent: Option<(String, String)>,
}

#[derive(Debug, Clone, PartialEq)]
struct Entity {
    name: String,
    pieces: Vec<Piece>,
}

struct HhtWriter {
    buf: String,
    indent: usize,
}

impl HhtWriter {
    fn new() -> Self { Self { buf: String::new(), indent: 0 } }
    
    fn pad(&self) -> String { "    ".repeat(self.indent) }
    
    fn line(&mut self, text: &str) {
        self.buf.push_str(&self.pad());
        self.buf.push_str(text);
        self.buf.push('\n');
    }
    
    fn blank(&mut self) {
        self.buf.push('\n');
    }
    
    fn write_entity(&mut self, entity: &Entity) {
        self.line(&format!("entity {} {{", entity.name));
        self.indent += 1;
        
        for piece in &entity.pieces {
            self.write_piece(piece);
        }
        
        self.indent -= 1;
        self.line("}");
    }
    
    fn write_piece(&mut self, piece: &Piece) {
        self.line(&format!("piece {} {{", piece.name));
        self.indent += 1;
        
        self.line(&format!("sprite = \"{}\"", piece.sprite));
        
        for ap in &piece.alignment_points {
            self.line(&format!("alignment_point {} = ({}, {})",
                ap.name, ap.offset.x, ap.offset.y));
        }
        
        if let Some((parent_piece, parent_ap)) = &piece.parent {
            self.line(&format!("parent = {}.{}", parent_piece, parent_ap));
        }
        
        self.indent -= 1;
        self.line("}");
    }
    
    fn finish(self) -> String { self.buf }
}

fn write_hht(entities: &[Entity]) -> String {
    let mut w = HhtWriter::new();
    for entity in entities {
        w.write_entity(entity);
        w.blank();
    }
    w.finish()
}

fn main() {
    let entities = vec![
        Entity {
            name: "hero".into(),
            pieces: vec![
                Piece {
                    name: "body".into(),
                    sprite: "hero_body".into(),
                    alignment_points: vec![
                        AlignmentPoint { name: "neck".into(), offset: Vec2 { x: 0.0, y: -20.0 } },
                        AlignmentPoint { name: "hand_r".into(), offset: Vec2 { x: 15.0, y: 0.0 } },
                    ],
                    parent: None,
                },
                Piece {
                    name: "head".into(),
                    sprite: "hero_head".into(),
                    alignment_points: vec![],
                    parent: Some(("body".into(), "neck".into())),
                },
            ],
        },
    ];
    
    let hht_text = write_hht(&entities);
    println!("=== Written HHT ===\n{}", hht_text);
    
    // 验证可读
    println!("\n=== Round-trip verification ===\n");
    println!("(文本写入 → 解析回内存 → 应和原始一致)");
    println!("Written bytes: {}", hht_text.len());
    println!("Original entities: {}", entities.len());
}
```

### 附录:工业级 pretty printer 的设计

工业级 pretty printer(`prettyplease` for Rust syn、`prettier` for JS、`rustfmt` for Rust)有几个 Day 516 没涉及的高级特性:

#### 1. Wadler-style pretty printing

学术论文 "A prettier printer" (Wadler, 1997) 描述了一套 pretty printing 算法。核心思想:**声明式描述布局,算法自动决定换行**。

```rust
// 声明式:这个 group 在空间够时一行,不够时多行
let group = vec![
    text("foo"),
    soft_line(),  // 空间够 = 空格,不够 = 换行
    text("bar"),
];
```

如果空间够,渲染成 `foo bar`。不够,渲染成:
```
foo
bar
```

这是 `prettier` 的核心,也是 Rust `syn` pretty printing 的核心。Day 516 是简化版,直接固定换行。

#### 2. 行宽自适应

工业级 pretty printer 测量行宽,智能换行:

```rust
struct Printer {
    max_line_width: usize,  // 默认 80
    current_width: usize,
}

// 如果当前行 + 新内容超过 max,提前换行
```

Casey 的简化版固定缩进,不自适应。生产项目通常用自适应。

#### 3. 注释保留

最难的特性。读 HHT 时,parser 提取注释 + 关联到 AST 节点。write 时,注释必须**放回原位置**。

```rust
struct Node {
    kind: NodeKind,
    leading_comments: Vec<Comment>,  // 节点前的注释
    trailing_comments: Vec<Comment>, // 节点后的注释
}
```

`rustfmt` 用这套机制保留注释。Day 516 不保留注释(写入时丢),这是简化。

#### 4. Idempotent printing

工业级 pretty printer 必须 **idempotent**:对同一 AST,无论调用多少次,输出文本一致。

```
format(format(text)) == format(text)
```

如果 format 不是 idempotent,用户跑两次格式化,文件不停变化,git diff 永远 dirty。

#### 5. Canonical form

工业级格式定义"canonical form"——唯一正确格式。所有合规 HHT 文件 format 后都变成 canonical。这样:

- 用户随便写,format 后变 canonical
- diff 干净(canonical 之间才能 diff)
- 工具链统一

HHT 没有正式 canonical 定义,但 Casey 的 writer 隐式定义了一种。

### 反思:HHT 格式是否"过度设计"?

有人会问:"Casey 为什么不直接用 JSON / TOML?自定义 HHT 是不是过度设计?"

这是好问题。Casey 的 HHT 设计理由:

**第一,教学**。HH 是教学项目,Casey 想教学生"如何设计文本格式"。用现成 JSON 没教学价值。

**第二,领域特定**。HHT 有特殊需求:
- 嵌套 entity → piece → alignment_point,JSON 嵌套没问题但冗长
- alignment_point 的 `(x, y)` 元组,JSON 写 `[x, y]`,HHT 写 `(x, y)`,后者更接近数学表达
- 注释支持(JSON 不支持,要 JSON5 / JSON-C)

**第三,parser 写作练习**。学生自己写 parser,学到 tokenizer + AST + parser combinator 的核心能力。

**反对方**:
- JSON 库成熟,casey 自己写 HHT 浪费时间
- 工业项目通常用 TOML / JSON,不用自定义
- 多一种格式 = 多一份学习成本

**结论**:Casey 的选择在教学场景合理,工业场景不推荐。如果你做生产项目,**优先用成熟格式**(TOML 配置、JSON 数据、Protobuf 二进制),不要自定义。

但 Casey 教你的是**能力**——你以后看任何格式(包括自定义)都能理解。这就是 HH 的价值。
