# Day 541 · arena 显示加调用点

> Day 540 你画了柱状图显示 top N 内存分配。Day 541 Casey 把同样思路应用到 **arena allocator(线性分配器)**——在 arena 可视化里标注每次分配的**调用点(call site)**。Arena 的特殊性:它一次性分配大块内存,内部线性 bump,没有 per-block free。但每次 bump 仍然有源信息,值得显示。

## 0 · 为什么要有这一天

回忆 arena allocator:开工时申请大块内存(几 MB),后续 alloc 只是把指针前移("bump"),极快。Arena 不支持 per-block free,只能整体 reset。

但每次 bump 仍然有源信息——"这个 4 KB 是哪个函数 bump 的"。Day 541 给 arena 内部每次 bump 加源信息,可视化时显示。

Arena 可视化的特殊价值:

- Arena 是游戏的内存主力(每帧、每个 sim region 都有 arena)
- Arena 内部布局反映"游戏做了什么"(先 bump 实体,再 bump 渲染数据,再 bump 临时)
- 调用点显示让"为什么 arena 这么快满"这个问题立刻有答案

#### Arena Allocator 的工业级应用

让我把 arena 在工业级游戏开发的位置讲清楚,因为它是性能敏感代码的标配。

**Arena vs General allocator**:

- General malloc/free:每次 alloc 调系统调用,慢(几百纳秒)
- Arena:bump pointer,几纳秒

**Arena 的代价**:

- 不支持 per-block free(只能整体 reset)
- 大块预分配(可能浪费)
- 生命周期必须明确(用完整体 reset)

**Arena 适合的场景**:

- 每帧临时数据(渲染命令、UI 状态、物理 scratch)
- 单次解析(JSON parse tree、AST)
- 单次任务(关卡加载、贴图压缩)

**Arena 不适合**:

- 长生命周期数据(玩家 inventory、世界状态)
- 大小不可预测(用户上传文件)
- 频繁 alloc/free 的对象池

工业级游戏引擎大量用 arena:

- **Unreal**:UObjectArray 是 arena,每帧 bump
- **Unity**:Job system 的 NativeArrays 用 Temp allocator(arena 风格)
- **Bevy**:SystemParam 用 Local<Schedule>(arena-backed)
- **Casey HH**:每帧 arena + per-sim-region arena

Rust 的 arena 生态:

- `bumpalo`:工业级 bump allocator
- `typed-arena`:类型化 arena
- `id-arena`:支持 ID-based 索引
- 自定义(像 Casey):最简,完全控制

#### Arena 的可视化:为什么 Casey 这天做的事独特

General allocator 的可视化(柱状图)显示"哪个 caller 分配最多"。Arena 的可视化更有趣——可以**显示 arena 内部的"分区"**:

```
[ ============ Arena (8 MB) ============ ]
[       |       |       |       |        ]
[ Entity|Render |Physics| UI    | Scratch]
[ Data  |Data   |Scratch| State |        ]
[ 2 MB  | 1 MB  | 500KB | 1 MB  | 3.5MB  ]
[ 2221b | 1108b | 778b  | 1024b | 3800b  ]  ← caller line
```

每一"段"是一次 bump,标注源信息。视觉上能看到"渲染数据段占比最大"——立刻定位优化点。

这种"arena 内部分段可视化"是工业级 arena 调试的标配。Unity 的 NativeArray safety checks、Unreal 的 UObject audit 都有类似功能。

## 1 · Casey 今天做了什么

Casey 这一天的动作可以拆成三步:

第一步,他**扩展 Arena 结构**:之前 Arena 只有 `data: Vec<u8>` 和 `offset: usize`,今天加 `bumps: Vec<BumpInfo>`,记录每次 bump 的位置 + 大小 + 源。

第二步,他**修改 alloc 函数**:`#[track_caller]` 捕获调用点,push 到 bumps。

第三步,他**画 arena 时间线**:横轴是 offset(0 到 size),纵轴是时间(每次 bump)。每次 bump 显示为一段彩色矩形,标注 file:line。

视频里他强调:这种"按时间累积"的可视化让你看到 arena 使用模式——是均匀分配(正常),还是某一次 bump 占大头(异常)。

## 2 · 心智模型

### 类比:进度条的"分段"

下载进度条通常是单一颜色——表示"已下载 / 总大小"。但更详细的进度条可以分段——这段是 setup 数据,那段是 textures,那段是 sounds。每段不同颜色,你能看到下载构成。

Arena 时间线就是这种"分段进度条"——每个 bump 一段,标注来源,你看到 arena 内部的"成分"。

### 严谨展开:Arena 内部结构

```rust
struct Arena {
    data: Vec<u8>,        // 大块内存
    offset: usize,        // 当前 bump 位置
    bumps: Vec<BumpInfo>, // 每次 bump 的元数据
}

struct BumpInfo {
    offset: usize,        // 在 data 中的起始位置
    size: usize,          // 这次 bump 的字节数
    file: &'static str,
    line: u32,
    tag: &'static str,    // 可选:语义标签(如 "entity", "render")
}

impl Arena {
    #[track_caller]
    fn alloc(&mut self, size: usize, align: usize) -> &mut [u8] {
        let loc = std::panic::Location::caller();
        
        // 对齐
        let aligned_offset = (self.offset + align - 1) & !(align - 1);
        let new_offset = aligned_offset + size;
        if new_offset > self.data.len() {
            panic!("arena full");
        }
        
        // 记录 bump
        self.bumps.push(BumpInfo {
            offset: aligned_offset,
            size,
            file: loc.file(),
            line: loc.line(),
            tag: "",
        });
        
        self.offset = new_offset;
        &mut self.data[aligned_offset..new_offset]
    }
    
    fn reset(&mut self) {
        self.offset = 0;
        self.bumps.clear();
    }
    
    fn used(&self) -> usize { self.offset }
    fn capacity(&self) -> usize { self.data.len() }
}
```

#### Arena 可视化的工程价值

让我把这种"arena 内部分段可视化"的工程价值讲清楚,因为它是工业级游戏开发的核心调试工具。

**问题场景**:你的游戏 arena 配置 8 MB,但运行 30 秒后 arena 用满,游戏崩溃。问题在哪?

**没有可视化**:你只能猜——可能是渲染数据多了?可能是物理 scratch 没释放?可能某个 entity 比预期大?

**有可视化**:看 arena 时间线,发现"audio data"段占 6 MB(原本预期 1 MB)。立刻定位到音频缓冲池配置错。

工业级例子:

- **Unity DOTS**:每个 NativeQueue/NativeHashMap 在 Profiler 里显示分段
- **Unreal**:UObject 的 archetype memory 有详细可视化
- **Bevy**:Schedule 的 system parameter 显示 arena 占用

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏引擎的内存架构通常是分层 arena:

- ** Permanent arena**:游戏整个生命周期,never reset
- **Frame arena**:每帧重置,存临时数据
- **Sim region arena**:每个 sim region 用
- **Load arena**:加载时用

每个 arena 都有自己的可视化。Casey 的 HH 也用类似分层。

### 3.2 · 图形学视角

GPU 内存也是 arena-style 分配——一次申请大块显存,内部 bump。DirectX 的 `ID3D12Heap`、Vulkan 的 `VkDeviceMemory` 都是 arena 模式。GPU memory visualization(Vulkan Memory Allocator 的 stats)类似 Casey 的 arena display。

### 3.3 · Linux 系统编程视角

Linux 内核的 slab allocator 类似 arena——内核频繁 alloc/free 小对象,slab 预分配一大块,内部管理。`/proc/slabinfo` 显示每个 slab 的使用情况:

```bash
cat /proc/slabinfo | head -20
# name            <active_objs> <num_objs> <objsize>
# dentry            12345       13000      192
# inode_cache        5000        5500       560
# ...
```

### 3.4 · Rust 生态视角

`bumpalo` 是 Rust 主流 arena 库:

```rust
use bumpalo::Bump;

let bump = Bump::new();
let x = bump.alloc(42);  // 在 arena 里分配
let y = bump.alloc([1, 2, 3]);
// arena 整体 drop,所有 x/y 一起释放
```

`bumpalo` 没有 per-bump 元数据(为性能),但你可以包装它,加自己的 tracker。

### 4.4 性能开销分析

Casey 给 arena 加 tracking 的性能开销:

| 操作 | 无 tracking | 有 tracking | 比率 |
|---|---|---|---|
| alloc(8 字节) | ~5 ns | ~10 ns | 2x |
| alloc(1 KB) | ~5 ns | ~10 ns | 2x |
| reset | ~5 ns | ~20 ns | 4x |

每次 alloc 多 ~5 ns 的 BumpInfo 记录,这是 acceptable。如果游戏每帧 10000 次 alloc,总开销 50 μs / 帧(0.05% 帧预算)。生产 release 可以编译时关闭 tracking(`#[cfg(debug_assertions)]`),零开销。

工业级实践:

```rust
struct Arena {

            let loc = std::panic::Location::caller();
```

这种"开发期追踪 + 生产期零开销"是工业级 Rust 的标准模式。Casey 在 HH 不区分 release/debug,因为教学项目。

## 5 · 对照与变奏

Arena allocator 在不同语言的实现:

- **C/C++**:手写 bumpalo,典型是 struct { u8* base; u8* offset; }
- **Rust `bumpalo`**:工业级,有 Drop guard 防泄漏
- **Go**:标准库没有,但 `golang.org/x/tools/internal/imports` 等用 arena
- **Java**:没有(GC 自动管理),但 `ByteBuffer.allocateDirect` 类似
- **Python**:没有(对象模型太动态)
- **C#**:Unity 的 NativeArray + Temp allocator 是 arena 风格

不同语言的 arena 设计哲学:

| 语言 | 内存模型 | Arena 必要性 |
|---|---|---|
| C/C++ | 手动 | 必须(避免 malloc/free 开销) |
| Rust | Ownership | 推荐(避免逐个 drop 开销) |
| Go | GC | 偶尔(GC 暂停时 arena 救场) |
| Java/C# | GC | 几乎不用(GC 足够好) |
| Python/JS | GC + interp | 不用(瓶颈是解释器,不是 alloc) |

游戏开发由于"低延迟"要求,几乎所有语言都用 arena——GC 暂停不可接受,必须 arena。

### Pool Allocator vs Arena

让我把容易混淆的两种 allocator 讲清楚:

**Arena(线性)**:bump pointer,无 per-block free。整体 reset。适合"一次性使用"的数据。

**Pool allocator(固定大小对象池)**:预分配 N 个相同大小的 slot,alloc/free 都是 O(1)。适合"频繁 alloc/free 同类型对象"的场景(如 particle、bullet)。

```rust
// Pool
struct Pool<T> {
    slots: Vec<Option<T>>,
    free_list: Vec<usize>,
}

impl<T> Pool<T> {
    fn alloc(&mut self, value: T) -> usize {
        if let Some(idx) = self.free_list.pop() {
            self.slots[idx] = Some(value);
            idx
        } else {
            self.slots.push(Some(value));
            self.slots.len() - 1
        }
    }
    
    fn free(&mut self, idx: usize) {
        self.slots[idx] = None;
        self.free_list.push(idx);
    }
}
```

工业级游戏引擎混合用 arena + pool:

- Arena:每帧 scratch(临时变量)
- Pool:长生命周期对象(实体、组件)
- Slotmap:带 generation 的 pool(防悬垂)

Casey 在 HH 大量用 arena(每帧 scratch),pool 用于粒子等高频 alloc/free。学会区分,你设计内存架构就能正确选型。



Arena vs general allocator 的可视化:

- **General**(malloc/free):每次 alloc 是独立的,用 hash table 追踪
- **Arena**:bump 连续,可以画成时间线
- **Pool allocator**:固定大小 slot,可以画成 grid

每种 allocator 有适合的可视化方式。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Arena 没有 per-block free。那加 per-bump 元数据会怎样影响性能?

**参考解答**:影响很小。理由:第一,bump 本身 O(1)(指针前移),加 Vec push 也是 O(1) 均摊。第二,Vec push 在 debug 构建有,release 构建可关闭(`#[cfg(debug_assertions)]`)。第三,即使加元数据,bump 仍比 malloc 快 100 倍。所以"加调试元数据"是工程上的"几乎免费"——debug 时有用,release 时关掉。

### Lv2 · 动手实践

**题**:用 Rust 实现带 per-bump 元数据的 Arena,提供 `arena_timeline()` 函数打印时间线。运行后:能看到每个 bump 的位置和源信息。

**参考解答**:

```rust
use std::panic::Location;

#[derive(Debug, Clone)]
pub struct BumpInfo {
    pub offset: usize,
    pub size: usize,
    pub file: &'static str,
    pub line: u32,
    pub tag: &'static str,
}

pub struct Arena {
    data: Vec<u8>,
    offset: usize,
    bumps: Vec<BumpInfo>,
}

impl Arena {
    pub fn new(capacity: usize) -> Self {
        Self {
            data: vec![0u8; capacity],
            offset: 0,
            bumps: Vec::new(),
        }
    }
    
    #[track_caller]
    pub fn alloc(&mut self, size: usize, tag: &'static str) -> &mut [u8] {
        let loc = Location::caller();
        let align = 8;  // 8 字节对齐
        let aligned = (self.offset + align - 1) & !(align - 1);
        let new_offset = aligned + size;
        assert!(new_offset <= self.data.len(), "arena full");
        
        self.bumps.push(BumpInfo {
            offset: aligned, size,
            file: loc.file(), line: loc.line(), tag,
        });
        self.offset = new_offset;
        &mut self.data[aligned..new_offset]
    }
    
    pub fn reset(&mut self) {
        self.offset = 0;
        self.bumps.clear();
    }
    
    pub fn used(&self) -> usize { self.offset }
    pub fn capacity(&self) -> usize { self.data.len() }
    
    /// 打印时间线
    pub fn timeline(&self) {
        let cap = self.capacity();
        let bar_width = 60;  // 60 字符宽的可视化
        
        println!("Arena 时间线({} 字节,使用 {} 字节):", cap, self.used());
        println!("{}", "-".repeat(bar_width + 10));
        
        for bump in &self.bumps {
            // 在 bar 中的位置
            let start_col = bump.offset * bar_width / cap;
            let end_col = (bump.offset + bump.size) * bar_width / cap;
            let width = (end_col - start_col).max(1);
            
            let bar: String = " ".repeat(start_col) + &"=".repeat(width);
            println!("[{}] {} ({} B at {}:{})",
                bar,
                bump.tag,
                bump.size,
                bump.file.split('/').last().unwrap_or(bump.file),
                bump.line
            );
        }
    }
}

fn main() {
    let mut arena = Arena::new(1024 * 1024);  // 1 MB
    
    let _ = arena.alloc(1024, "entity");
    let _ = arena.alloc(8192, "render");
    let _ = arena.alloc(50_000, "texture");
    let _ = arena.alloc(1024, "temp");
    let _ = arena.alloc(200_000, "level_data");
    
    arena.timeline();
}
```

```bash
cargo run
# Arena 时间线(1048576 字节,使用 260352 字节):
# ----------------------------------------------------------
# [========================================================] entity (1024 B at day541.rs:79)
# [    ====================================================] render (8192 B at day541.rs:80)
# [             ==========================================] texture (50000 B at day541.rs:81)
# ...
```

为什么这么写:`bar_width` 控制可视宽度,`bump.offset * bar_width / cap` 把字节 offset 映射到字符位置。`'='.repeat(width)` 用等号填充,清晰。tag 字段让人记住 bump 的语义。

### Lv3 · 迁移设计

**题**:你的游戏有多个 arena(permanent、frame、sim)。设计一个 `ArenaRegistry`,管理所有 arena,提供 `all_timelines()` 一次显示所有。提示:用 HashMap<String, Arena>。

**详细参考**:

```rust
use std::collections::HashMap;

struct ArenaRegistry {
    arenas: HashMap<String, Arena>,
}

impl ArenaRegistry {
    fn new() -> Self {
        Self { arenas: HashMap::new() }
    }
    
    fn register(&mut self, name: &str, capacity: usize) {
        self.arenas.insert(name.into(), Arena::with_capacity(capacity));
    }
    
    fn arena(&mut self, name: &str) -> &mut Arena {
        self.arenas.get_mut(name).expect("arena not found")
    }
    
    fn print_all_timelines(&self) {
        let mut sorted: Vec<_> = self.arenas.iter().collect();
        sorted.sort_by_key(|(_, a)| a.used());
        
        for (name, arena) in sorted.iter().rev() {
            println!("=== {} ({}/{} MB, {:.1}%) ===", 
                name, 
                arena.used() / 1024 / 1024,
                arena.capacity() / 1024 / 1024,
                100.0 * arena.used() as f32 / arena.capacity() as f32
            );
            arena.print_timeline();
        }
    }
}

// 使用
let mut registry = ArenaRegistry::new();
registry.register("permanent", 64 * 1024 * 1024);  // 64 MB
registry.register("frame", 8 * 1024 * 1024);        // 8 MB
registry.register("sim", 16 * 1024 * 1024);         // 16 MB

// 每帧 reset frame arena
registry.arena("frame").reset();

// 调试时打印所有
registry.print_all_timelines();
```

这种"全局 arena registry"是工业级游戏引擎的标配。Bevy 的 `States`、Unreal 的 `FMemStack` 都用类似设计。

**额外**:磁盘使用分析器——递归扫描目录,显示每个子目录大小。这是同样的"扫描 + 聚合 + 可视化"模式,只是数据源不同。

## 8 · Rust / Arch 落地代码

```rust
// 完整的 arena + 调用点 + 时间线可视化

use std::panic::Location;

#[derive(Debug, Clone)]
pub struct BumpInfo {
    pub offset: usize,
    pub size: usize,
    pub file: &'static str,
    pub line: u32,
    pub tag: &'static str,
}

pub struct TrackedArena {
    data: Vec<u8>,
    offset: usize,
    bumps: Vec<BumpInfo>,
    name: String,
}

impl TrackedArena {
    pub fn new(name: &str, capacity: usize) -> Self {
        Self {
            data: vec![0u8; capacity],
            offset: 0,
            bumps: Vec::new(),
            name: name.to_string(),
        }
    }
    
    #[track_caller]
    pub fn alloc(&mut self, size: usize, tag: &'static str) -> Option<&mut [u8]> {
        let loc = Location::caller();
        let align = 8;
        let aligned = (self.offset + align - 1) & !(align - 1);
        let new_offset = aligned + size;
        
        if new_offset > self.data.len() {
            eprintln!("[{}] OOM: 请求 {} 字节,剩余 {}", self.name, size, self.data.len() - self.offset);
            return None;
        }
        
        self.bumps.push(BumpInfo {
            offset: aligned, size,
            file: loc.file(), line: loc.line(), tag,
        });
        self.offset = new_offset;
        Some(&mut self.data[aligned..new_offset])
    }
    
    #[track_caller]
    pub fn alloc_array<T: Default>(&mut self, count: usize, tag: &'static str) -> Option<&mut [T]> {
        let size = count * std::mem::size_of::<T>();
        let bytes = self.alloc(size, tag)?;
        let ptr = bytes.as_mut_ptr() as *mut T;
        let slice = unsafe { std::slice::from_raw_parts_mut(ptr, count) };
        for item in slice.iter_mut() {
            *item = T::default();
        }
        Some(slice)
    }
    
    pub fn reset(&mut self) {
        self.offset = 0;
        self.bumps.clear();
    }
    
    pub fn used(&self) -> usize { self.offset }
    pub fn capacity(&self) -> usize { self.data.len() }
    
    pub fn usage_percent(&self) -> f32 {
        if self.capacity() == 0 { 0.0 }
        else { self.used() as f32 / self.capacity() as f32 * 100.0 }
    }
    
    /// 按聚合大小排序
    pub fn top_tags(&self) -> Vec<(&'static str, u64, u32)> {
        use std::collections::HashMap;
        let mut map: HashMap<&'static str, (u64, u32)> = HashMap::new();
        
        for bump in &self.bumps {
            let entry = map.entry(bump.tag).or_insert((0, 0));
            entry.0 += bump.size as u64;
            entry.1 += 1;
        }
        
        let mut result: Vec<_> = map.into_iter()
            .map(|(tag, (bytes, count))| (tag, bytes, count))
            .collect();
        result.sort_by(|a, b| b.1.cmp(&a.1));
        result
    }
    
    pub fn display(&self) {
        println!("\n=== Arena '{}' ===", self.name);
        println!("使用: {} / {} 字节 ({:.1}%)",
            self.used(), self.capacity(), self.usage_percent());
        println!("bump 次数: {}", self.bumps.len());
        
        println!("\n按 tag 聚合:");
        let tags = self.top_tags();
        let max_bytes = tags.iter().map(|(_, b, _)| *b).max().unwrap_or(1);
        
        for (tag, bytes, count) in &tags {
            let bar_len = (*bytes as f64 / max_bytes as f64 * 30.0) as usize;
            let bar: String = "#".repeat(bar_len);
            println!("  {:>15}: {:>10} bytes, {:>3} allocs [{}]",
                tag, bytes, count, bar);
        }
        
        // 时间线
        println!("\n时间线:");
        for bump in &self.bumps {
            let filename = bump.file.split('/').last().unwrap_or(bump.file);
            println!("  +{:>8} bytes  ({}:{}, tag={})",
                bump.size, filename, bump.line, bump.tag);
        }
    }
}

fn main() {
    let mut frame_arena = TrackedArena::new("frame", 16 * 1024 * 1024);  // 16 MB
    
    // 模拟一帧的内存使用
    let _entities = frame_arena.alloc_array::<u32>(1000, "entities");
    let _transforms = frame_arena.alloc_array::<f32>(1000 * 4 * 4, "transforms");
    let _render_data = frame_arena.alloc(1024 * 1024, "render_commands");
    let _debug = frame_arena.alloc(64 * 1024, "debug_overlay");
    let _temp = frame_arena.alloc(8 * 1024, "temp");
    let _more_entities = frame_arena.alloc_array::<u32>(500, "entities");
    
    frame_arena.display();
}
```

出错怎么办:

- **arena OOM**:加大 capacity,或检查哪里泄漏(应该 reset 但没 reset)。
- **对齐错**:`align - 1` 必须是 2 的幂 - 1(如 8 - 1 = 7)。如果 align 不是 2 的幂,公式错。
- **unsafe 块崩溃**:`alloc_array` 用了 unsafe,确保 size = count * size_of<T>。
