# Day 445 · 清理实体创建

> 在开始填实世界生成器之前,Casey 决定先清理实体创建——把零散的 "AddEntity / AddPlayer / AddRoom" 函数合并成一个统一的工厂(factory)模式。这一步看起来是清理,实则为后面"自动生成 N 个房间"做准备。

## 0 · 为什么要有这一天

经过 Phase 2-6 的代码积累,HH 项目里有十几个"创建实体"的函数:`AddPlayer`, `AddMonster`, `AddSword`, `AddRoom`, `AddWall`……它们各自有微妙差异:有的从内存池分配,有的从 stack,有的接收 `EntityId` 输入,有的自动生成。这种"各自为政"在功能少时还能管,但 Day 446+ Casey 要写"自动生成几十个房间实体",旧代码就开始碍事。

清理的目标:统一所有"创建实体"的接口。无论是玩家、怪物、房间,都走同一条路径:`create_entity(world, EntitySpec)`,根据 spec 字段决定要哪种实体、初始位置、特殊属性。

这种重构叫**工厂模式(factory pattern)**。它把"怎么造实体"集中到一处,让上层调用简洁、类型安全、易扩展。

要理解为什么这次重构是必要的,让我们看一个具体的痛点场景。

假设 Casey 直接在 day446 用旧代码生成 20 个房间。每个房间调用 `AddRoom(world, position, size)`。每个房间里有 4 个墙(`AddWall`),1 个门(`AddDoor`),1 个灯(`AddLight`)。20 个房间 = 20 × 7 = 140 次 `AddXXX` 调用,每次参数列表不同,每次内存分配路径不同,每次返回的 `EntityId` 处理方式不同。

这种代码会有什么 bug?

第一,**参数列表混乱**。`AddWall` 接收 `(world, position, height, material_id)`,而 `AddDoor` 接收 `(world, position, width, is_open)`——位置参数都叫"position"但语义不同。Casey 自己写的代码,半年后回来读也要查文档。

第二,**内存管理不统一**。`AddPlayer` 用内存池,`AddWall` 用临时 stack 分配,`AddDoor` 用 heap。当你想统一改用内存池(为了减少 fragmentation),要改 5 个函数。

第三,**新功能扩展痛点**。假设你想给所有实体加"创建时间戳"用于动画过渡。在旧代码里要改 5 个 `AddXXX` 函数签名 + 所有调用点。在工厂模式里只改 1 个 `EntitySpec` 结构。

第四,**测试困难**。`AddPlayer` 测试要 mock 整个 world;`AddWall` 测试也要 mock 整个 world。没有统一接口,每个测试独立维护,逐渐腐烂。

工厂模式解决所有这些问题——把"创建实体"的所有复杂性集中到一处,对外暴露简洁的统一接口。

完成这一天后,你能做到:把分散的 `AddXXX` 函数合并成统一的 `create_entity`,用 enum + struct 表达"实体规格"(spec),并能解释为什么这种重构是后面"程序化生成"的必要前置。

## 1 · Casey 今天做了什么

Casey 这一天的动作分四步:

第一,他列出当前所有"创建实体"的函数和它们的签名,发现至少 4 种风格不一致。

第二,他设计统一的 `EntitySpec` 结构:

```rust
enum EntityKind {
    Player, Monster, Sword, Room, Wall, Door,
}

struct EntitySpec {
    kind: EntityKind,
    position: Vec3,
    size: Vec3,
    flags: EntityFlags,  // 可选标志位
    // ...
}
```

第三,他把所有 `AddXXX` 函数体复制到 `create_entity` 的 match 分支里,然后让旧函数变成简单 wrapper(调用 `create_entity`),最后逐步删除 wrapper。

第四,他跑游戏验证玩家、怪物、房间都还能正常出现,行为没变。

## 2 · 心智模型

### 类比:工厂的"产品目录"

旧代码像一个杂乱的车间——你想要一把剑,要找"打铁工"(AddSword);想要怪物,要找"训兽师"(AddMonster);每个工种都用自己的工具、自己的流程、自己的记录系统。

新代码像一个标准化的工厂——所有产品都从一个"产品目录"(EntitySpec)开始,然后由统一的"生产线"(create_entity)按目录制造。生产线内部分不同子流程(玩家线、怪物线),但**对外的接口统一**。

### 严谨原理:工厂模式

工厂模式的核心:**调用者不直接构造对象,而是通过一个工厂**。

旧风格:
```rust
let player = Player::new(position, health);
let monster = Monster::new(position, speed);
let sword = Sword::new(position, damage);
```

每种实体有自己的构造函数,参数各异。增加新实体类型 = 加新构造函数 + 改所有调用者。

工厂风格:
```rust
let player = create_entity(EntitySpec::player(position));
let monster = create_entity(EntitySpec::monster(position));
let sword = create_entity(EntitySpec::sword(position));
```

所有调用走 `create_entity`,spec 是入口。增加新实体 = 在 EntitySpec 里加一个 variant + 在 `create_entity` 里加分支。

**为什么工厂更好?**
- **集中**:所有"创建"逻辑在一处,方便修改
- **可扩展**:新类型不破坏旧代码
- **类型安全**:Rust 的 enum 是 closed(不能在外扩展),编译器检查穷尽性
- **测试**:一个工厂好测,十几个分散函数难测

让我把"工厂模式"在面向对象 vs Rust 的表达差异讲透,这是 Casey 这次重构背后的设计哲学。

**经典 OOP 工厂**。GoF 设计模式里的"工厂方法"和"抽象工厂"是这样的:

```java
// Java 风格
interface EntityFactory {
    Entity create(EntitySpec spec);
}

class PlayerFactory implements EntityFactory {
    public Entity create(EntitySpec spec) {
        return new Player(spec.position, spec.health);
    }
}

class MonsterFactory implements EntityFactory {
    public Entity create(EntitySpec spec) {
        return new Monster(spec.position, spec.speed);
    }
}

// 使用:
EntityFactory factory = get_factory(kind);
Entity e = factory.create(spec);
```

这种模式依赖**继承**和**动态分派**——每个具体工厂是一个子类,运行时通过虚函数表(vtable)调用。优点是"开放扩展"(加新实体 = 加新工厂类),缺点是"运行时开销 + 接口冗长"。

**Rust 的工厂:enum + match**。Rust 没有"经典 OOP 继承",但它的 enum 是 closed(所有 variant 在 enum 定义里列出),配合 `match` 表达式,编译器强制**穷尽性检查**——你必须处理所有 variant。

```rust
fn create_entity(spec: EntitySpec) -> Entity {
    match spec.kind {
        EntityKind::Player { health } => Entity::player(spec.position, health),
        EntityKind::Monster { speed, damage } => Entity::monster(spec.position, speed, damage),
        // 加新 variant 时编译器报错"non-exhaustive match",强迫你处理
    }
}
```

这种工厂的优点:

1. **零成本**:match 是 jump table,编译后和 switch 一样快,无 vtable
2. **穷尽性**:加新 variant 时所有 match 自动报错,强制更新
3. **数据导向**:EntityKind 直接携带数据(health、speed),不需要额外 setter
4. **可序列化**:enum 派生 `Serialize` 后可以序列化为 JSON / 二进制,工厂调用即"从存档恢复"

**对比开放扩展 vs 封闭扩展**。OOP 的 interface 是**开放**——任何人都可以 `implements EntityFactory` 加新类型,无需修改原文件。Rust 的 enum 是**封闭**——所有 variant 在 enum 定义里。

开放的好处:库的用户可以扩展。开放坏处:原作者无法预见所有扩展,代码可能依赖"封闭"假设(如"我知道所有实体类型")被破坏。

封闭的好处:编译器强制穷尽性,重构安全。封闭坏处:加新类型必须改 enum 定义。

**Casey 的选择**:封闭 enum。HH 是单游戏项目,所有实体类型在源代码里可见,无需运行时扩展。封闭 enum 给编译期保证,比开放接口安全得多。

**何时用开放(trait object)?** 当你想做"插件式"扩展——比如 mod 系统让玩家定义新实体类型,或者你的库要让下游扩展。那时用 trait + Box<dyn Entity>。

## 2 · 心智模型(续)

### Rust 的 enum + match 是天生的工厂

```rust
enum EntityKind {
    Player { health: i32 },
    Monster { speed: f32, damage: i32 },
    Sword { damage: i32 },
    Room { volume: AABB },
}

struct Entity {
    position: Vec3,
    kind: EntityKind,
}

fn create_entity(spec: EntityKind, position: Vec3) -> Entity {
    Entity { position, kind: spec }
}

// 使用
let player = create_entity(EntityKind::Player { health: 100 }, pos);
let goblin = create_entity(EntityKind::Monster { speed: 5.0, damage: 10 }, pos);
```

每行解释:
- `enum EntityKind` — Rust 的"标签联合"(tagged union)。每个 variant 可以带不同数据。
- `EntityKind::Player { health }` — 用 struct-like variant,带字段名,可读。
- `create_entity` 函数本身简单——复杂在 enum 的设计。

**对比 C 风格**:C 要用 union + tag 手写:
```c
typedef enum { PLAYER, MONSTER, SWORD } EntityKind;
typedef struct {
    EntityKind kind;
    union {
        struct { int health; } player;
        struct { float speed; int damage; } monster;
    };
} EntityKind;
```

C 没编译器检查穷尽性,容易漏 case。Rust 的 `match` 强制覆盖所有 variant。

### 工厂的进阶:trait object

如果实体行为差别很大(玩家有 AI、剑没有),可以用 trait object:

```rust
trait Behavior {
    fn update(&mut self, world: &World, dt: f32);
    fn render(&self, renderer: &mut Renderer);
}

struct Entity {
    position: Vec3,
    behavior: Box<dyn Behavior>,  // 动态分发
}

fn create_player(position: Vec3) -> Entity {
    Entity {
        position,
        behavior: Box::new(PlayerBehavior::new()),
    }
}
```

但 Casey HH 不用 trait object——他的实体都是 POD(plain old data),数据和行为分离。这是 data-oriented design 的精神。所以 Day 445 用 enum 而不是 trait。

### 内存分配:Casey 的 Arena

Casey HH 的实体都从一块大 arena 分配,不用堆:

```rust
struct World {
    entities: Vec<Entity>,  // 实际是预分配的 arena
    entity_count: usize,
}

fn create_entity(world: &mut World, spec: EntityKind, position: Vec3) -> EntityId {
    let id = world.entity_count;
    world.entities.push(Entity { position, kind: spec });
    world.entity_count += 1;
    EntityId(id)
}
```

`EntityId(usize)` 是"代际索引"(generational index)的简化版——只是个下标。生产代码要加 generation 字段防止 dangling id(被删 entity 的 id 复用导致问题)。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏引擎的实体创建:

| 引擎 | 模式 |
|---|---|
| Casey HH | 手写 arena + enum |
| Unreal | UClass 反射 + Factory |
| Unity | GameObject + AddComponent |
| Bevy | ECS + Bundle |

**ECS(Entity-Component-System)** 是现代主流:实体只是一个 ID,组件是数据片段,系统是行为。新建实体 = "spawn 一个 ID + 加一组组件"。

```rust
// Bevy 风格
commands.spawn((
    Transform::from_translation(pos),
    Player::new(),
    Health(100),
    Mesh::from(shape::Cube::default()),
));
```

但 ECS 的复杂度对 Casey 教学不利——他强调"理解每一行"。所以 HH 用简化 enum + 手写 arena,概念清晰。

让我把 ECS vs 工厂模式 vs 继承的演化讲清楚,这样你能看清工业游戏引擎的设计选择。

**1990s:继承体系(OOP)**。Quake/Source 早期用 C++ 继承:

```cpp
class Entity { virtual void update(); };
class Player : public Entity { ... };
class Monster : public Entity { ... };
class Sword : public Entity { ... };
```

问题:**多重继承噩梦**(玩家既是 Entity 又是 Damageable 又是 Visible),**深继承树**(改基类影响所有派生),**vtable 开销**(每个虚函数调用一次间接跳转)。

**2000s:组件化(Component-based)**。Unreal/Unity 转向"Entity + Components"组合:

```csharp
// Unity
GameObject player = new GameObject();
player.AddComponent<Transform>();
player.AddComponent<PlayerController>();
player.AddComponent<Health>();
player.AddComponent<MeshRenderer>();
```

Entity 是个空容器,组件是数据 + 行为。这是**组合优于继承(composition over inheritance)**的实践。优势:加新功能 = 加新组件,不修改现有代码。劣势:组件间通信仍然麻烦(互相 `GetComponent`),内存布局碎片化(每个组件独立分配)。

**2010s:ECS(Data-Oriented)**。Bevy、Unity DOTS、Flecs 把组合推到极致:

```rust
// ECS:实体只是 ID,组件是 plain data,系统是处理组件 batch 的函数
fn movement_system(mut query: Query<(&mut Position, &Velocity)>) {
    for (mut pos, vel) in &mut query {
        pos.0 += vel.0;
    }
}
```

ECS 的核心洞察:**数据布局决定性能**。把所有 Position 组件连续存储(SoA,structure of arrays),迭代时缓存命中率高,GPU/SIMD 友好。

**Casey HH 的位置**。HH 是 90s 风格的"手写 arena + enum kind",这是教学友好的简化版本。Casey 反复强调"工业 ECS 太复杂,先理解基础"。如果你将来用 Bevy / hecs / Unity DOTS,你需要理解**今天讲的工厂模式是 ECS 的演化前身**——ECS 仍然有"创建实体的统一接口"(spawn),只是把"实体规格"扩展成"组件 tuple"。

**工厂在游戏运行时**:
- **关卡加载**:每秒可能创建上千个实体(整个关卡),工厂要快
- **子弹生成**:每秒几十个,工厂要支持"prefab"(预制体)
- **存档/读档**:序列化所有实体,工厂要可逆(创建 → 数据 → 创建)

### 3.2 · 图形学视角

渲染端的"工厂"——材质工厂、shader 工厂:

```rust
fn create_material(spec: MaterialSpec) -> MaterialId {
    match spec {
        MaterialSpec::Unlit { color } => ...,
        MaterialSpec::PBR { albedo, roughness, metallic } => ...,
        MaterialSpec::Custom { shader_id } => ...,
    }
}
```

这和实体工厂同构。每个工厂负责"根据规格创建资源"。

### 3.3 · Linux 系统编程视角

Linux 内核也有"工厂"思想:
- `struct file` 的创建由 `alloc_file()` 统一处理
- `struct task_struct`(进程)由 `copy_process()` 创建
- `struct socket` 由 `sock_create()` 创建

这些函数接收参数(struct),返回 initialized struct,内部处理所有细节。这就是工厂模式。

### 3.4 · Rust 生态视角

Rust 的工厂常用 trait:

```rust
trait Factory {
    type Output;
    fn create(&self, spec: Spec) -> Self::Output;
}

struct EntityFactory;
impl Factory for EntityFactory {
    type Output = Entity;
    fn create(&self, spec: Spec) -> Entity { ... }
}
```

但日常代码用普通函数就够了,不需要 trait 抽象。Trait 适合"测试时换 mock factory"。

**真实 crate**:`slotmap` 是 Rust 标准的"代际索引"容器,完美适合实体系统。`hecs` / `bevy_ecs` 是 ECS 实现。

让我把"代际索引(generational index)"讲深一点——这是工业 ECS 的核心数据结构,Casey HH 简化版没讲透。

**问题**:你有 entity arena,每个 entity 有个 ID(就是 arena index)。entity 被删除后,index 被 reuse 给新 entity。**问题来了**:旧代码可能持有旧 ID(指向已删 entity),它会读到新 entity 的数据——这是 dangling reference 类的游戏崩溃源。

**朴素方案**:用 `Option<Entity>`——但每个 ID 引用都要 unwrap,啰嗦。

**代际索引方案**:ID 不是简单 `usize`,而是 `(index, generation)`。arena 维护每个槽位的 generation:

```rust
struct Arena<T> {
    slots: Vec<Slot<T>>,
    free_list: Vec<usize>,
}

struct Slot<T> {
    generation: u32,
    data: Option<T>,  // None = 已删除
}

struct EntityId {
    index: usize,
    generation: u32,  // 创建时记录
}

impl<T> Arena<T> {
    fn insert(&mut self, data: T) -> EntityId {
        let index = self.free_list.pop().unwrap_or_else(|| {
            self.slots.push(Slot { generation: 0, data: None });
            self.slots.len() - 1
        });
        let slot = &mut self.slots[index];
        slot.generation += 1;  // 新一代
        slot.data = Some(data);
        EntityId { index, generation: slot.generation }
    }
    
    fn get(&self, id: EntityId) -> Option<&T> {
        let slot = self.slots.get(id.index)?;
        if slot.generation == id.generation {
            slot.data.as_ref()
        } else {
            None  // 这一代已死,ID 过期
        }
    }
    
    fn remove(&mut self, id: EntityId) -> Option<T> {
        let slot = self.slots.get_mut(id.index)?;
        if slot.generation == id.generation {
            let data = slot.data.take();
            // generation 在下次 insert 时增加
            self.free_list.push(id.index);
            data
        } else {
            None
        }
    }
}
```

**关键点**:每次 `insert` 复用槽位时,`generation += 1`。旧 ID 持有的 generation 不匹配,`get` 返回 `None`,安全失败而不是读错误数据。

`slotmap` crate 实现这个,API:

```rust
use slotmap::SlotMap;
slotmap::new_key_type! { struct EntityKey; }

let mut entities: SlotMap<EntityKey, Entity> = SlotMap::with_key();
let key = entities.insert(Entity::player());
// 后续
if let Some(entity) = entities.get(key) {
    // ...
}
entities.remove(key);
entities.get(key);  // None,即使 key 被复用给新 entity
```

Casey HH 简化用 `EntityId(usize)` 不带 generation——这是教学简化,生产代码必须用代际索引。今天讲工厂模式时提一下,真正的"安全实体系统"需要这种数据结构。

## 4 · 认知地图

### 4.1 上级

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:工厂模式和直接构造的区别是什么?工厂在什么时候反而更糟?

**参考解答**:工厂把"构造"集中到一处,调用者通过 spec 描述需求。**工厂在以下情况更糟**:
- 类型少(2-3 个),直接 new 更清晰
- 参数简单,无 shared logic
- 性能关键(工厂多一层间接调用)

例:两个 Vec2 加法不需要工厂,直接 `Vec2::new(x, y)`。但创建不同类型的实体,工厂能消除重复代码。

### Lv2 · 动手实践

**题**:把下面三个函数合并成工厂。

旧代码:
```rust
fn add_player(world: &mut World, pos: Vec3, health: i32) -> EntityId;

fn add_sword(world: &mut World, pos: Vec3, damage: i32) -> EntityId;
```

**参考解答**:

```rust
enum EntitySpec {
    Player { health: i32 },
    Monster { speed: f32 },
    Sword { damage: i32 },
}

impl EntitySpec {
    // 便捷构造器
    fn player(health: i32) -> Self { Self::Player { health } }
    fn monster(speed: f32) -> Self { Self::Monster { speed } }
    fn sword(damage: i32) -> Self { Self::Sword { damage } }
}

fn create_entity(world: &mut World, spec: EntitySpec, pos: Vec3) -> EntityId {
    let entity = Entity { position: pos, kind: spec };
    let id = world.entities.len();
    world.entities.push(entity);
    EntityId(id)
}

// 使用
fn add_player(world: &mut World, pos: Vec3, health: i32) -> EntityId {
    create_entity(world, EntitySpec::player(health), pos)
}
// (类似的 wrapper,可以保留也可以删除)
```

每行解释:
- `EntitySpec::player(health)` — 简化构造器,避免重复 `EntitySpec::Player { health }`。
- `Entity { position, kind: spec }` — 把 spec 嵌入 Entity。
- 保留旧函数作为 wrapper,让上层代码不破坏,逐步迁移。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

完整工厂模式 + benchmark:

```rust
use std::time::Instant;

#[derive(Debug, Clone, Copy)]
struct Vec3 { x: f32, y: f32, z: f32 }

#[derive(Debug, Clone, Copy)]
struct EntityId(usize);

#[derive(Debug, Clone, Copy)]
enum EntitySpec {
    Player { health: i32 },
    Monster { speed: f32, damage: i32 },
    Sword { damage: i32 },
    Room { width: f32, height: f32, depth: f32 },
}

#[derive(Debug, Clone, Copy)]
struct Entity {
    position: Vec3,
    kind: EntitySpec,
}

struct World {
    entities: Vec<Entity>,
}

impl World {
    fn new() -> Self { Self { entities: Vec::with_capacity(1024) } }
    fn create_entity(&mut self, spec: EntitySpec, pos: Vec3) -> EntityId {
        let id = self.entities.len();
        self.entities.push(Entity { position: pos, kind: spec });
        EntityId(id)
    }
    fn get(&self, id: EntityId) -> Option<&Entity> {
        self.entities.get(id.0)
    }
}

fn main() {
    let mut world = World::new();

    // 创建各种实体
    let player_id = world.create_entity(
        EntitySpec::Player { health: 100 },
        Vec3 { x: 0.0, y: 0.0, z: 0.0 },
    );
    let goblin_id = world.create_entity(
        EntitySpec::Monster { speed: 5.0, damage: 10 },
        Vec3 { x: 5.0, y: 0.0, z: 0.0 },
    );
    let sword_id = world.create_entity(
        EntitySpec::Sword { damage: 25 },
        Vec3 { x: 1.0, y: 0.0, z: 0.0 },
    );

    println!("Player: {:?}", world.get(player_id));
    println!("Goblin: {:?}", world.get(goblin_id));
    println!("Sword:  {:?}", world.get(sword_id));

    // Benchmark: 创建 10000 个实体
    let start = Instant::now();
    for i in 0..10_000 {
        world.create_entity(
            EntitySpec::Room { width: 10.0, height: 4.0, depth: 10.0 },
            Vec3 { x: i as f32, y: 0.0, z: 0.0 },
        );
    }
    println!("Created 10000 rooms in {:?}", start.elapsed());
    println!("Total entities: {}", world.entities.len());
}
```

每行解释:
- `Vec::with_capacity(1024)` — 预分配,避免后续 push 触发 reallocate。
- `entities.get(id.0)` — 通过下标取,Option 返回处理越界。
- benchmark 创建 10000 个实体,在普通机器上 < 1ms。

```bash
cd entity_factory
cargo run --release
# 输出:Created 10000 rooms in ~200μs
```
