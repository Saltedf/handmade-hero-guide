## 0 · 为什么要有这一天

DEFLATE 的核心是 **Huffman 编码**——一种"高频符号用短码、低频符号用长码"的变长编码。Huffman 1952 年提出,至今 70 年仍是压缩算法的基础。

为什么 Huffman 这么重要?**因为它达到"给定符号频率下的最优前缀编码"**。前缀编码的意思是:没有任何符号的编码是另一个符号的前缀。这让解码器可以一边读 bit 一边判断"我读完一个符号了"。

DEFLATE 用两套 Huffman 表:
- **Literal/length 表**:解码"字面字节"或"匹配长度"
- **Distance 表**:解码"匹配距离"

每个 DEFLATE 块的开头可以**动态定义**自己的 Huffman 表(code lengths 编码),也可以引用**固定表**(fixed Huffman)。

Casey Day 455 解析动态 Huffman 表。这是 PNG 解码器最难的一集,涉及位读取、code lengths 序列、Huffman 树构造、查找算法。今天讲透,Day 456 用它解码真正的数据。

让我从 Huffman 编码的**理论根基**讲起,你才能理解为什么 DEFLATE 这么设计。

**信息熵(entropy)**。Shannon 1948 年提出:一个符号源(随机变量 X,概率分布 p),其信息熵 `H(X) = -Σ p(x) log2 p(x)`。熵是"编码这个源每个符号平均最少需要的 bit 数"。

举例:抛硬币(50/50)熵 = 1 bit。掷骰子(1/6 each)熵 = log2(6) ≈ 2.58 bit。英语文本熵 ≈ 1-1.5 bit/字符(预测后),远少于 8 bit/字符(ASCII)。

**Huffman 编码定理**。Huffman 1952 年证明:对任何符号源,存在一个**前缀码(prefix code)**,其平均编码长度 `L` 满足 `H(X) ≤ L < H(X) + 1`。即 Huffman 编码**最多比理论最优差 1 bit**。

**Huffman 算法构造**。给定符号频率,构造 Huffman 树:

1. 把每个符号看作一个"叶子节点",权重 = 频率
2. 选权重最小的两个节点,合并成一个父节点,父权重 = 两子之和
3. 把父节点放回集合,重复
4. 最后剩一个节点(根),树构造完

叶子到根的路径 = 编码(左 0,右 1)。

**举例**:符号 {A: 5, B: 2, C: 1, D: 1} 频率。

```
Step 1: 选 C(1) 和 D(1),合并成 N1(2)
        集合: {A:5, B:2, N1:2}
Step 2: 选 B(2) 和 N1(2),合并成 N2(4)
        集合: {A:5, N2:4}
Step 3: 选 A 和 N2,合并成 root(9)
```

树:

```
            root
           /     \
          A       N2
                 /  \
                B    N1
                    /  \
                   C    D
```

编码:A = 0(1 bit),B = 10(2 bit),C = 110(3 bit),D = 111(3 bit)。

平均长度:`5/9 * 1 + 2/9 * 2 + 1/9 * 3 + 1/9 * 3 = 5/9 + 4/9 + 3/9 + 3/9 = 15/9 ≈ 1.67 bit`。

熵:`-(5/9 log2 5/9 + 2/9 log2 2/9 + 1/9 log2 1/9 + 1/9 log2 1/9) ≈ 1.55 bit`。

Huffman 编码 1.67 bit,熵 1.55 bit,差 0.12 bit——比理论上限 1 bit 小很多。

**前缀码的性质**。看编码 {0, 10, 110, 111}——没有任何一个是另一个的前缀。这意味着解码器可以**一边读 bit 一边判断**:读"0"立刻知道是 A;读"1"再看下一位,如果是"0"就是 B;以此类推。

这种性质让 Huffman 解码是**流式**的——不需要预先知道编码长度。

**DEFLATE 用 canonical Huffman**。标准 Huffman 有个问题:同样频率分布,不同的"合并选择"产生不同树(同样最优)。DEFLATE 规定**canonical form**——给定 code lengths(每符号的编码长度),编码值唯一确定:

1. 按 code length 升序排符号
2. 同 length 按符号值升序
3. 第一个符号编码 = 0(全部 0)
4. 后续符号:编码 = 前一个 + 1
5. 跨 length:编码 = (前一个 + 1) << 1

例:符号 [A, B, C, D],lengths [1, 2, 3, 3]:

```
A (length 1): 0
B (length 2): 10
C (length 3): 110 = (10 + 1) << 1 = 110
D (length 3): 111 = 110 + 1
```

**canonical 的好处**:DEFLATE 只需传输 code lengths(每个符号 1 字节),不必传输整个树。压缩后省空间。

**DEFLATE 动态 Huffman 块**。Block 开头编码自己的 code lengths,用"超 Huffman"(对 code lengths 序列再 Huffman)。这是双层 Huffman——第一层压缩"码长序列",第二层压缩"实际数据"。

## 补充:Huffman 解码的工业实现

让我讲讲 Huffman 解码的几种实现方式,以及 DEFLATE 用的"lookup table"。

**方法 1:树遍历**。读一位 bit,走左/右子树,到叶子输出符号。简单但慢——每个 bit 一次内存访问(树节点散在内存)。

```rust
enum Node {
    Leaf(u16),
    Internal(Box<Node>, Box<Node>),
}

fn decode(reader: &mut BitReader, root: &Node) -> u16 {
    let mut node = root;
    loop {
        let bit = reader.read_bits(1);
        node = match (node, bit) {
            (Node::Internal(left, right), 0) => left,
            (Node::Internal(left, right), 1) => right,
            (Node::Leaf(v), _) => return *v,
        };
    }
}
```

**方法 2:lookup table**。DEFLATE 的 code length ≤ 15。预计算一个 `2^15 = 32768` 项的表,索引是"读 15 bit",值是 `(symbol, actual_code_length)`。

```rust
struct HuffmanTable {
    // 索引 = 读取的 15 位 bit(LSB first)
    // 值 = (symbol, 实际 code length)
    table: [(u16, u8); 32768],
}

fn decode(reader: &mut BitReader, table: &HuffmanTable) -> u16 {
    // peek 15 位(不消费)
    let bits = reader.peek_bits(15);
    let (symbol, len) = table.table[bits as usize];
    // 消费 len 位
    reader.consume(len);
    symbol
}
```

每次解码 1 次表查找(O(1))——比树遍历快 5-10 倍。代价:表大(128 KB),但只算一次,后续解码都查表。

**方法 3:多级表**。如果完整 15 位表太大,用 2 级——第一级 9 位表(512 项),命中直接返回;不命中(代码 > 9 位)查第二级表。工业 zlib 用这种。

DEFLATE 实际用方法 2 或 3。Casey HH 教学可能用方法 1,然后提到方法 2 优化。

## 补充:DEFLATE 的 LZ77 sliding window

让我把 LZ77 sliding window 算法讲清楚,这是 Day 456 的核心。

**LZ77 思想**。数据中很多重复子串。例如 `abcabcabc` 可以编码为 `abc` + `(back 3, length 6)`——用 (distance, length) 引用代替重复部分。

**滑动窗口**。LZ77 维护一个"已编码数据"的滑动窗口(典型 32 KB)。当前要编码的位置,可以引用窗口内任何 32 KB 范围内的子串。

```
[已编码数据(最多 32 KB)][当前编码位置 ...]
     ↑ 滑动窗口
```

**编码过程**。在每个位置:

1. 在滑动窗口内找最长匹配(hash table 或 suffix tree 加速)
2. 如果匹配长度 ≥ 3,输出 `(distance, length)`
3. 否则输出 literal byte
4. 窗口滑动

**DEFLATE 的具体编码**:

- **literal**:0-255,直接的字节值
- **length 256**:end of block
- **length 257-285**:匹配长度,长度 3-258
  - 257 → length 3
  - 258 → length 258(最长)
- **distance**:1-32768,匹配距离

length 和 distance 都用 Huffman 编码,且各有"extra bits"扩展——比如 code 265 表示"length 11-12",再读 1 个 extra bit 决定具体 11 还是 12。

**解码**。DEFLATE 解码器从 Huffman 码读出 token:

- 0-255:输出这个字节
- 256:end of block
- 257-285:读 extra bits 得 length,再读 distance Huffman + extra bits 得 distance,从输出 buffer 的 `pos - distance` 复制 length 字节到 `pos`

```rust
fn inflate_block(reader: &mut BitReader, output: &mut Vec<u8>, lit_huff: &Huffman, dist_huff: &Huffman) {
    loop {
        let token = decode(reader, lit_huff);
        if token < 256 {
            output.push(token as u8);
        } else if token == 256 {
            break;  // end of block
        } else {
            // length + distance
            let length = LENGTH_BASE[(token - 257) as usize] + reader.read_bits(LENGTH_EXTRA[token - 257]) as usize;
            let dist_code = decode(reader, dist_huff);
            let distance = DIST_BASE[dist_code as usize] + reader.read_bits(DIST_EXTRA[dist_code as usize]) as usize;
            // 复制
            let start = output.len() - distance;
            for i in 0..length {
                output.push(output[start + i]);
            }
        }
    }
}
```

注意复制循环——`output.push(output[start + i])`。如果 distance < length(比如 distance=1, length=5),复制会"重叠"——这是 RLE(run-length encoding)的形式,正确处理需要按字节复制(不是按块)。

## 2 · 心智模型

### 类比:莫尔斯电码

莫尔斯电码是早期的"变长编码"——常用字母 E 是一个点(.),罕用字母 Q 是 --.-。E 频率高,码短;Q 频率低,码长。Huffman 是这个思想的数学最优版。

但 Huffman 比 Morse 更严格:**前缀性**。任何符号的编码不是另一个的前缀。这让解码无歧义——读到一个完整编码就知道是哪个符号,不用等下一个 bit。

### Huffman 树的严谨定义

Huffman 树是一棵二叉树,叶子节点是符号。从根到叶子的路径决定编码:左分支 0,右分支 1。

例:符号 A、B、C、D 频率 5、3、2、1。

构造过程:
1. 频率最低的两个(C=2, D=1)合并成新节点(频率 3)
2. 现在有 B=3、(CD)=3、A=5。再合并 B 和 CD(频率 6)
3. 现在有 A=5、(BCD)=6。合并,得根

```
            root
           /    \
          A      ◯
                / \
               B   ◯
                  / \
                 C   D
```

编码:
- A: 0
- B: 10
- C: 110
- D: 111

A 频率高,1 bit;D 频率低,3 bit。这就是 Huffman 的精神。

### Canonical Huffman

Huffman 树有多种可能的"形状"(同样频率分布,不同合并顺序可能得到不同树)。DEFLATE 用 **canonical Huffman**:不传输整个树结构,只传输每个符号的 **code length**(编码长度,如 A=1, B=2, C=3, D=3)。接收方按规则重建唯一的"规范"Huffman 码。

规范规则:
1. 同长度的码按符号值升序排列
2. 长度 N 的第一个码 = 长度 N-1 的最后一个码 + 1,然后左移 1
3. 长度 1 的第一个码是 0

例:code lengths [1, 2, 3, 3] 给符号 [A, B, C, D]:
- 长度 1:A = 0
- 长度 2:B = 10(0 + 1,左移 1)
- 长度 3:C = 110,B = 11 → C 是 B+1=11,左移 1 = 110
- 长度 3:D = 111(C+1)

Rust 实现:

```rust
fn build_canonical_huffman(code_lengths: &[u8]) -> Vec<(u32, u32)> {
    // 返回每个符号的 (code, length)
    let n = code_lengths.len();
    let mut result = vec![(0u32, 0u32); n];
    
    // 按长度升序排序符号
    let mut symbols_by_length: Vec<Vec<usize>> = vec![Vec::new(); 16];
    for (sym, &len) in code_lengths.iter().enumerate() {
        if len > 0 {
            symbols_by_length[len as usize].push(sym);
        }
    }
    
    let mut code: u32 = 0;
    let mut prev_len: u32 = 0;
    for len in 1..=15 {
        for &sym in &symbols_by_length[len] {
            if prev_len != len as u32 {
                code <<= 1;
                prev_len = len as u32;
            }
            // 实际上,正确做法是:每个长度切换时 code = (code + 1) << 1
            // 这里用简化版,实际见下文
        }
    }
    result
}
```

正确的 canonical 算法(RFC 1951 §3.2.2):

```rust
fn build_canonical_codes(code_lengths: &[u8]) -> Vec<u32> {
    // 第一步:数每个长度的符号数
    let mut bl_count = [0u32; 16];
    for &cl in code_lengths {
        if cl > 0 {
            bl_count[cl as usize] += 1;
        }
    }
    // 第二步:算 first_code 每个长度
    let mut next_code = [0u32; 16];
    let mut code: u32 = 0;
    bl_count[0] = 0;
    for bits in 1..=15 {
        code = (code + bl_count[bits - 1]) << 1;
        next_code[bits] = code;
    }
    // 第三步:给每个符号赋码
    let mut codes = vec![0u32; code_lengths.len()];
    for (sym, &cl) in code_lengths.iter().enumerate() {
        if cl > 0 {
            codes[sym] = next_code[cl as usize];
            next_code[cl as usize] += 1;
        }
    }
    codes
}
```

每行解释:
- `bl_count[bits]` = 长度为 bits 的符号数。
- `next_code[bits]` = 长度 bits 的下一个可用码。
- `(code + bl_count[bits-1]) << 1` — 长度 bits 的起始码 = 上一长度起始码 + 上一长度符号数,然后左移 1(增加位长度)。
- 最后给每个非零 code length 的符号按"符号升序"赋码。

### BitReader(LSB-first)

DEFLATE 用 LSB-first 位顺序:从字节的低位读起。

```rust
struct BitReader<'a> {
    data: &'a [u8],
    byte_pos: usize,
    bit_pos: u8,  // 0-7
}

impl<'a> BitReader<'a> {
    fn new(data: &'a [u8]) -> Self {
        Self { data, byte_pos: 0, bit_pos: 0 }
    }
    fn read_bits(&mut self, n: u8) -> Result<u32, String> {
        let mut result: u32 = 0;
        for i in 0..n {
            if self.byte_pos >= self.data.len() {
                return Err("EOF".into());
            }
            let bit = (self.data[self.byte_pos] >> self.bit_pos) & 1;
            result |= (bit as u32) << i;  // LSB first
            self.bit_pos += 1;
            if self.bit_pos == 8 {
                self.bit_pos = 0;
                self.byte_pos += 1;
            }
        }
        Ok(result)
    }
}
```

每行解释:
- `bit_pos` 0-7,0 是字节最低位。
- 读 1 bit:`(byte >> bit_pos) & 1`,放到 result 的第 i 位(LSB first)。
- 满 8 bit 进下一字节。
- 这是性能最简版。生产代码用 `u64 buffer` 一次读 8 字节再分。

### DEFLATE 块头

```
BFINAL: 1 bit(1 = 最后块,0 = 还有更多)
BTYPE:  2 bit
  00 = 无压缩(存原始字节)
  01 = 固定 Huffman
  10 = 动态 Huffman
  11 = 保留(错误)
```

PNG 用动态 Huffman(BTYPE=2)。

### 动态 Huffman 头部

```
HLIT:  5 bit(字面/长度表符号数 = HLIT + 257)
HDIST: 5 bit(距离表符号数 = HDIST + 1)
HCLEN: 4 bit(code length 表符号数 = HCLEN + 4)

接下来 HCLEN+4 个 3-bit 值,按特殊顺序给 code length 表
```

**code length 表的特殊顺序**:DEFLATE 不按 0, 1, 2, ... 顺序,而按 `16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1, 15`(RFC 1951 §3.2.7)。这个顺序是按 code length 出现频率排的——频率高的(16=重复 3-10 次、17=重复 11-138 次)放前面,减少传输长度。

```rust
const CL_ORDER: [usize; 19] = [
    16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1, 15
];
```

### 解析 code lengths

code length 表的值有特殊含义:
- 0-15:直接的 code length
- 16:重复上一个 code length 3-10 次(接下来 2 bit + 3)
- 17:重复 0 共 3-10 次(接下来 3 bit + 3)
- 18:重复 0 共 11-138 次(接下来 7 bit + 11)

这让 code length 序列本身也被压缩(运行长度编码 + Huffman)。

### 3.1 · 游戏编程视角

Huffman 编码在游戏里:

- **PNG / OGG / Theora 解码**(本日)
- **网络协议**:HTTP/2 HPACK 用 Huffman 压头部
- **存档压缩**:游戏存档常 Huffman + LZ77
- **资源打包**:ZIP / PAK 用 DEFLATE

**坑**:Huffman 解码是分支密集型(每个符号一棵树查找),GPU 不擅长。所以 PNG 在 CPU 解,GPU 用 BCn。游戏启动期预解压所有 PNG 到 GPU,运行时不碰。

### 3.2 · 图形学视角

PNG 的 Huffman 表对像素艺术特别有效——像素艺术颜色少,频率分布不均,Huffman 压缩比极高。

进阶:**算术编码(arithmetic coding)** 比 Huffman 更优(可以打破"整数 bit"限制),但慢且专利问题。**Range coding** 是常见替代。JPEG 2000、H.264 用算术编码,但 PNG 用 Huffman 保简洁。

### 3.4 · Rust 生态视角

Rust 实现 Huffman:

```rust
struct HuffmanTree {
    // 紧凑表示:用 (code, length) 排序后二分查找
    entries: Vec<(u32, u8, u16)>,  // (code, length, symbol)
}

impl HuffmanTree {
    fn from_code_lengths(code_lengths: &[u8]) -> Self {
        let codes = build_canonical_codes(code_lengths);
        let mut entries: Vec<(u32, u8, u16)> = code_lengths.iter().enumerate()
            .filter(|(_, &cl)| cl > 0)
            .map(|(sym, &cl)| (codes[sym], cl, sym as u16))
            .collect();
        entries.sort_by_key(|&(c, l, _)| (l, c));  // 按长度+码排序
        Self { entries }
    }
    fn decode(&self, reader: &mut BitReader) -> Result<u16, String> {
        let mut code: u32 = 0;
        for len in 1..=15 {
            code = (code << 1) | reader.read_bits(1)?;
            // 查找 (code, len) 是否匹配
            for &(c, l, sym) in &self.entries {
                if l == len as u8 && c == code {
                    return Ok(sym);
                }
            }
        }
        Err("invalid Huffman code".into())
    }
}
```

每行解释:
- 树用 `(code, length, symbol)` 元组列表,简单。
- `decode` 逐 bit 读取并拼接 code,每个长度检查匹配。
- 这是教学简化版,生产用快速查表。

**真实 crate**:`miniz_oxide`、`flate2`、`libpng` 都有完整 Huffman 解码。

- **前缀编码(prefix code)** — 无歧义解码的必要条件

### 4.2 同级

|---|---|

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 DEFLATE 用 canonical Huffman 而不是传输完整 Huffman 树?

**参考解答**:完整树结构开销大(每个内部节点 2 字节),而 code lengths 序列开销小(每符号 1 字节,且能用 RLE 压缩)。canonical 规则保证接收方从 code lengths 重建**唯一的码**,跨实现一致。这是"用计算换带宽"的典型设计。

### Lv2 · 动手实践

**题**:实现 BitReader 和 `build_canonical_codes`,验证给定 code lengths `[1, 2, 3, 3]` 得到 codes `[0, 10, 110, 111]`(二进制表示)。

**参考解答**:见 §2 代码。完成标准:
- BitReader LSB-first 正确
- canonical codes 符合 RFC 1951 算法
- 测试用例 [1, 2, 3, 3] 输出 [0, 2, 6, 7](十进制,= 0, 10, 110, 111 二进制)

```rust
fn build_canonical_codes(code_lengths: &[u8]) -> Vec<u32> {
    let mut bl_count = [0u32; 16];
    for &cl in code_lengths {
        if cl > 0 { bl_count[cl as usize] += 1; }
    }
    let mut next_code = [0u32; 16];
    let mut code: u32 = 0;
    for bits in 1..=15usize {
        code = (code + bl_count[bits - 1]) << 1;
        next_code[bits] = code;
    }
    let mut codes = vec![0u32; code_lengths.len()];
    for (sym, &cl) in code_lengths.iter().enumerate() {
        if cl > 0 {
            codes[sym] = next_code[cl as usize];
            next_code[cl as usize] += 1;
        }
    }
    codes
}

fn main() {
    let lengths = [1u8, 2, 3, 3];  // A=1, B=2, C=3, D=3
    let codes = build_canonical_codes(&lengths);
    for (i, &c) in codes.iter().enumerate() {
        println!("Symbol {}: code = {:b} (len {})", i, c, lengths[i]);
    }
    // 应输出:
    // Symbol 0: code = 0 (len 1)
    // Symbol 1: code = 10 (len 2)
    // Symbol 2: code = 110 (len 3)
    // Symbol 3: code = 111 (len 3)
}
```

每行解释:
- 算法直接对应 RFC 1951 §3.2.2。
- 输出 codes 二进制符合预期。

## 8 · Rust / Arch 落地代码

完整 Huffman 表构造:

```rust
struct BitReader<'a> {
    data: &'a [u8],
    byte_pos: usize,
    bit_pos: u8,
}

impl<'a> BitReader<'a> {
    fn new(data: &'a [u8]) -> Self {
        Self { data, byte_pos: 0, bit_pos: 0 }
    }
    fn read_bits(&mut self, n: u8) -> Result<u32, String> {
        let mut result: u32 = 0;
        for i in 0..n {
            if self.byte_pos >= self.data.len() {
                return Err("EOF".into());
            }
            let bit = (self.data[self.byte_pos] >> self.bit_pos) & 1;
            result |= (bit as u32) << i;
            self.bit_pos += 1;
            if self.bit_pos == 8 {
                self.bit_pos = 0;
                self.byte_pos += 1;
            }
        }
        Ok(result)
    }
}

fn build_canonical_codes(code_lengths: &[u8]) -> Vec<u32> {
    let mut bl_count = [0u32; 16];
    for &cl in code_lengths {
        if cl > 0 { bl_count[cl as usize] += 1; }
    }
    let mut next_code = [0u32; 16];
    let mut code: u32 = 0;
    for bits in 1..=15usize {
        code = (code + bl_count[bits - 1]) << 1;
        next_code[bits] = code;
    }
    let mut codes = vec![0u32; code_lengths.len()];
    for (sym, &cl) in code_lengths.iter().enumerate() {
        if cl > 0 {
            codes[sym] = next_code[cl as usize];
            next_code[cl as usize] += 1;
        }
    }
    codes
}

const CL_ORDER: [usize; 19] = [
    16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1, 15
];

fn read_dynamic_huffman(reader: &mut BitReader) -> Result<(), String> {
    let _bfinal = reader.read_bits(1)?;
    let btype = reader.read_bits(2)?;
    if btype != 2 {
        return Err(format!("Only dynamic Huffman supported, got BTYPE={}", btype));
    }

    let hlit = reader.read_bits(5)? as usize + 257;
    let hdist = reader.read_bits(5)? as usize + 1;
    let hclen = reader.read_bits(4)? as usize + 4;

    println!("HLIT={} (lit/len symbols), HDIST={} (dist symbols), HCLEN={} (cl entries)",
        hlit, hdist, hclen);

    // 读 code length 表
    let mut cl_lengths = [0u8; 19];
    for i in 0..hclen {
        cl_lengths[CL_ORDER[i]] = reader.read_bits(3)? as u8;
    }
    print!("Code-length code lengths: ");
    for (i, &cl) in cl_lengths.iter().enumerate() {
        if cl > 0 { print!("{}:{} ", i, cl); }
    }
    println!();

    // 接下来用 cl_lengths 表解码 hlit + hdist 个 code lengths(此处略,Day 456 实现)
    println!("(接下来 {} 个字面/长度 + {} 个距离 code lengths 待解码)", hlit, hdist);
    
    Ok(())
}

fn main() -> Result<(), String> {
    let args: Vec<_> = std::env::args().collect();
    let data = std::fs::read(args.get(1).ok_or("usage")?).map_err(|e| e.to_string())?;
    
    // 跳过 PNG magic + IHDR chunk
    let mut cursor = 8usize;
    // IHDR
    cursor += 4 + 4 + 13 + 4;  // length + type + data + CRC
    
    // 找 IDAT
    loop {
        let length = u32::from_be_bytes([
            data[cursor], data[cursor+1], data[cursor+2], data[cursor+3]
        ]) as usize;
        let ctype = &data[cursor+4..cursor+8];
        cursor += 8;
        if ctype == b"IDAT" {
            // 跳过 zlib 头 2 字节,然后是 DEFLATE 流
            let mut reader = BitReader::new(&data[cursor + 2..cursor + length]);
            read_dynamic_huffman(&mut reader)?;
            break;
        }
        cursor += length + 4;
        if ctype == b"IEND" { break; }
    }
    Ok(())
}
```

每行解释:
- 跳过 IHDR chunk(固定 13 字节数据 + 12 字节头尾)。
- 找 IDAT 后跳 zlib 头 2 字节,余下是 DEFLATE 流。
- DEFLATE 流第一 bit 是 BFINAL,接下来 2 bit 是 BTYPE。
- `hlit + 257` 等 — DEFLATE 表大小有最小值(lit/len 至少 257,因为 256 是 end-of-block 标记)。
