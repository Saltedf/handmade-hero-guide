# Day 563 · 使用光探针空间索引

> Sparse voxel grid(554 天做的)用 HashMap 存 chunk,但 query 时 `HashMap::get` 慢(每帧几百万次查)。Day 563 Casey 加**空间索引(spatial index)**——给定世界坐标,O(1) 找到所属 chunk + voxel。

## 0 · 为什么要有这一天

让我们从一个真实的性能 profile 说起。

你跟 Day 554 做完 sparse voxel grid,跑游戏看 FPS。fragment shader 一帧要 sample 几百万次 voxel 光照——每个像素一次,1280×720 屏幕 ≈ 100 万像素,每个像素查 1-8 个 voxel 做 trilinear 插值,总共几百万查询。

`perf record` 看,**80% 时间在 `HashMap::get`**——hash 计算 + bucket 找 = 50-200ns/查询。几百万 × 100ns = 几百毫秒。**帧时间 16ms 完全超**。

为什么 HashMap 慢?有几个原因:

**第一,cache miss**。HashMap 内部是 array of buckets,bucket 内是 linked list 或 open addressing。访问时 hash → bucket index → bucket → key compare → value。每步可能 cache miss。CPU L1 cache 命中 1ns,L2 命中 10ns,L3 命中 30ns,DRAM 命中 100ns。HashMap 的"随机访问"模式让大部分访问是 L2/L3/DRAM——慢。

**第二,hash 计算**。SipHash(Rust std 默认)每次 hash 几十纳秒。即便用 ahash 更快,仍有 5-10ns 开销。

**第三,key 比较**。Hash 碰撞时逐字节比较 key,ChunkCoord 是 24 字节,比较也要时间。

总加起来 50-200ns/查询。在 fragment shader 跑几百万次 = 灾难。

**Spatial index**(空间索引)的目标:**让"找某坐标的 chunk"更快**。核心思路:**利用 spatial locality(空间局部性)**——玩家附近的 chunk 经常一起访问。如果 chunk 按空间顺序排列(而不是 HashMap 的 hash 顺序),邻近访问的 cache 命中率高。

工业界的 spatial index 有几个家族:

**Hash grid**(本项目)。最简单——chunk coord 做 hash,放 HashMap。优点简单,缺点慢。

**3D array**(稠密数组)。世界坐标 → 数组 index,O(1) 极快。但只能装小世界(大世界内存爆)。

**Chunk cache + HashMap**(Casey 今天用)。固定 N 个最近用的 chunk 放连续 Vec(数组),其他在 HashMap。命中率高时极快,miss 时 fallback 到 HashMap。**这是 L1 cache 思想**——快速小缓存 + 慢速大后端。

**Morton code + sorted array**。3D 坐标编码到 1D 整数(Z-order curve),邻近 3D 在 1D 也邻近。Chunk 按 Morton 排序,binary search O(log N)。Cache 友好。

**Octree**(八叉树)。把空间递归切 8 份。稀疏场景(99% 空)友好——空区域不展开。Unreal Lumen 用 sparse voxel octree。

**BVH(Bounding Volume Hierarchy)**。Ray tracing 主流,三角形按 AABB 树组织。每光线上 O(log N) 找交点。NV RTX 硬件加速 BVH。

每种适合不同场景。GI(全局光照)通常用 hash grid + chunk cache,ray tracing 用 BVH。Casey 这天用 **chunk cache**——N 个固定 slot,类似 Day 558 的 slot pool。

完成这一天之后,你具备:

- **理解空间索引的几种实现**:HashMap、3D array、Octree、BVH、Morton code,各自取舍
- **能用 Morton code 加速 3D 坐标查询**:把 3D 空间邻近变成 1D 邻近
- **设计 chunk cache**:小快速缓存 + 大慢速后端,L1 cache 思想
- **看懂工业引擎的 spatial index 选型**:Unreal Lumen、Frostbite GI、Unity HDRP 的不同选择

## 1 · Casey 今天做了什么

Casey 这天加一层 **chunk cache**——介于 fragment shader 和 sparse HashMap 之间。让我把他的步骤拆开。

**第一步,维护活跃 chunk 列表**。一个连续 Vec<Option<Chunk>>,长度 N=64。每个 slot 存"最近用过的 chunk"。Vec 连续内存,fragment shader 通过 index 访问——cache 友好,5-10ns/访问。

**第二步,每帧玩家移动,更新活跃列表**。玩家进入新区域,新 chunk 加入 cache。LRU(最久未用)的 chunk 淘汰,给新 chunk 腾位置。

**第三步,查询时两级 fallback**:
- 先在 chunk cache 数组里 linear search,找到返回(O(N),但 N=64 仍快)
- 找不到,fallback 到 sparse HashMap(O(1) per query 但常数大)

实测命中率 80-95%(玩家附近的 chunk 持续热),所以平均速度接近 cache 数组的 O(N)/64 = 几纳秒。

视频里他展示:fragment shader 查询时间从 200ns 减到 30ns——**6 倍加速**。这是个朴素但有效的优化——CPU 设计的 L1/L2 cache 思想在应用层重新实现。

**为什么不用 3D array?**如果世界小(几百 chunk),3D array 最快——O(1) index 计算,cache 友好。但大世界(几万 chunk)3D array 稀疏,大部分 slot 是空,内存浪费。Chunk cache 兼顾两者——小数组(快)+ HashMap 后端(省内存)。

**为什么不用 Morton code?**Morton 能让 HashMap 更快(邻近 chunk 的 hash 邻近,cache 友好)。但 Casey 这天的瓶颈是 HashMap 本身,不是 hash 计算。他先用 chunk cache 把热数据移出 HashMap,Hash 计算就不再 hot path。Morton 是后续优化。

## 2 · 心智模型

### 2.1 类比:图书馆的"畅销书架"

我打个比方。图书馆有几百万本书(HashMap),不可能全部摆在前面。但**最近热门的 100 本放"畅销书架"**(cache 数组)——读者大部分时候要的就是这 100 本,直接拿(O(1) 数组访问)。

只有要"非畅销书"时才去大库房查 HashMap(慢)。但因为大部分查询是热门(O(80%+) 命中),平均速度快。

这就是 **CPU cache 层次思想**(L1/L2/L3/RAM)的应用——加一层"快速小缓存"。CPU 设计师 50 年前发明的概念,在软件层重新实现。

类比的关键洞察:**两级存储的命中率决定速度**。如果命中率 90%,平均时间 = 0.9 × fast + 0.1 × slow = 0.9 × 5ns + 0.1 × 200ns = 25ns——接近 fast。如果命中率 50%,平均 = 0.5 × 5ns + 0.5 × 200ns = 103ns——几乎和 slow 一样。**命中率是 cache 设计的核心指标**。

如何提升命中率?**LRU 替换策略 + 足够大的 cache**。LRU 利用"时间局部性"——刚用过的更可能再用(玩家附近 chunk 持续访问)。Cache 大小要够容纳"工作集"(working set)——玩家附近所有 chunk。

### 2.2 Morton code:Z-order curve 的奥秘

让我深入讲讲 Morton code,你会看到 3D → 1D 映射的数学之美。

**问题**:3D 空间的坐标(x, y, z),怎么映射到 1D 整数,让"邻近 3D 坐标"在 1D 也邻近?

朴素方案:`idx = x + width * (y + height * z)`(row-major)。但**邻近 3D 不一定 1D 邻近**——(0,0,0) → 0,(1,0,0) → 1(邻近),但(0,1,0) → width(可能很大),不邻近 0。

Morton code 用 **bit interleaving**(位交错):

```
x = 0b101    (5)
y = 0b011    (3)
z = 0b110    (6)

Morton = 0b z y x z y x z y x
       = 0b 1 0 1 1 0 1 1 0 0
       = 0b101101100
```

每个轴的 bit 交错放——bit 0 给 x,bit 1 给 y,bit 2 给 z,bit 3 给 x,...

**为什么 Morton 让 3D 邻近 1D 邻近**?考虑 (0,0,0) Morton = 0。(1,0,0) Morton = 0b001 = 1。(0,1,0) Morton = 0b010 = 2。(0,0,1) Morton = 0b100 = 4。**3D 邻居的 Morton 差值小**——1, 2, 4 vs row-major 的 1, width, width²。

更精确:Morton 的 Z-order curve 是 **space-filling curve**(空间填充曲线)——一条线穿过 3D 空间每个点,且**邻近点在线上也邻近**(大约)。这让 cache 友好——访问 Morton 排序的 chunk,cache line 一次取多个邻近 chunk。

**Morton 编码实现**:

```rust
// Morton encode:3D 坐标 → 1D u64
fn spread(mut v: u64) -> u64 {
    // 把 v 的每 bit 之间塞 2 个 0 bit,变成每 3 bit 一个有效位
    v = (v | (v << 32)) & 0x1F00000000FFFF;
    v = (v | (v << 16)) & 0x1F0000FF0000FF;
    v = (v | (v << 8))  & 0x100F00F00F00F00F;
    v = (v | (v << 4))  & 0x10C30C30C30C30C3;
    v = (v | (v << 2))  & 0x1249249249249249;
    v
}

fn morton3(x: u32, y: u32, z: u32) -> u64 {
    spread(x as u64) | (spread(y as u64) << 1) | (spread(z as u64) << 2)
}
```

`spread` 函数把"连续 bit"变成"每隔 3 bit 一个有效位"——magic number 是精心设计的 bitmask。这种 bit trick 是高性能计算的经典。

**Morton 用途**:
- 排序 chunk,cache 友好遍历
- Hash function(替代 ChunkCoord 的 hash)
- BVH / octree 的节点编码

### 2.3 Octree:稀疏空间索引

Octree(八叉树)是另一种 spatial index,适合**极稀疏**场景。让我深入讲讲。

**核心思想**:把空间递归切成 8 份(2×2×2)。每份再切 8 份,直到叶子节点(单 voxel 或空区域)。

```
Root:整个 1km³
  Level 1:8 份(每份 500m³)
    Level 2:64 份(每份 250m³)
      ...
        Leaf:1m³ voxel(深度 log2(1000) ≈ 10 层)
```

**稀疏友好**:空区域(没几何体的开放空间)不展开——一个 Level-N 节点直接标记"空",不递归。99% 空的场景,octree 节点数远少于 voxel 数。

**查询**:从 root 开始,根据坐标选 8 个孩子之一,递归下行。每层 O(1),总 O(log N)。N=10^9 时 log N = 30,极快。

**对比 HashMap**:HashMap O(1) per query,但常数大(hash 计算 + cache miss)。Octree O(log N),但常数小(每层几次比较,cache 友好)。**稀疏度高时 octree 胜出**,稠密时 HashMap 胜出。

Unreal Lumen 用 sparse voxel octree。GTA 5 GI 用 baked lightmap(不是动态 voxel),Cyberpunk 用 SDFGI(signed distance field GI,类似 voxel 但用 SDF 表达几何)。

Octree 的实现挑战:**指针 chase**——每个内部节点指向 8 个孩子(指针或索引),访问孩子可能 cache miss。工业实现经常用 **linear octree**——所有节点放在一个 Vec,用 index 代替指针,cache 更友好。或者 **hashed octree**——每个节点用 Morton code 索引,HashMap 查找。

Casey 这天用 chunk cache(简单),octree 是后续工作。但理解 octree 让你看懂 Unreal Lumen。

### 2.4 BVH 与 ray tracing

虽然 Casey 这天用 chunk cache 不是 BVH,但讲 spatial index 不能不提 BVH——它是 ray tracing 的标准。

**Ray tracing 的核心操作**:给定一条射线(起点 + 方向),找场景中第一个相交的三角形。朴素遍历所有三角形 = O(N),N=百万三角形 = 太慢。

**BVH(Bounding Volume Hierarchy)**:把三角形按 AABB(axis-aligned bounding box)组织成树。内部节点存自己的 AABB,叶子节点存三角形。射线遍历时:
1. 从 root 开始
2. 测试射线 vs root AABB——相交则递归孩子,不相交则剪枝
3. 递归到叶子,测试射线 vs 叶子内三角形

**剪枝效果**:大部分分支因 AABB 不交而被剪掉,实际访问的三角形数 << N。复杂度 O(log N) 平均。

**SAH(Surface Area Heuristic)**:BVH 构建的优化策略——让"射线更可能命中"的子树更平衡。具体:子树的"被命中概率"正比于其 AABB 表面积。SAH 让总访问代价最小。这是工业 BVH 构建的标准。

NV RTX / AMD RDNA2 / Intel Arc 都有 **hardware BVH traversal**——GPU 硅片直接遍历 BVH,不占 shader 时间。Unreal Lumen 的 ray tracing 用 hardware BVH,几纳秒/射线。

Casey 的 HH 在 OpenGL,没 hardware ray tracing。但他用的 voxel GI 思路——sample voxel texture——和 ray tracing 解决同样问题(找某点的光照),但用 sampling 而非 ray。两种 trade-off:voxel GI 快但精度低,ray tracing 精度高但慢。

### 2.5 Cache hit ratio:数据决定一切

chunk cache 的核心指标是 **hit ratio**(命中率)。让我分析什么影响命中率。

**Working set(工作集)大小**。玩家附近的 chunk 数 = working set。玩家在开阔地形,working set ~30 chunk(玩家周围 5×5×2 区域)。Cache size ≥ working set 才能命中。

**Spatial locality(空间局部性)**。玩家移动慢时,附近 chunk 持续访问——locality 强,命中率高。玩家瞬移(传送)时,locality 中断——命中率暂时降。

**Temporal locality(时间局部性)**。同一 chunk 反复访问——locality 强。Casey 的 voxel GI 每帧访问所有附近 chunk,局部性极强。

实测工业场景:
- 静态玩家:hit ratio 95%+
- 玩家步行:hit ratio 85-90%
- 玩家开车:hit ratio 70-80%
- 玩家瞬移:hit ratio 0%(瞬间 miss,慢慢回升)

提升 hit ratio 的策略:
1. **增大 cache**——但内存代价线性增长
2. **Prefetch**——预测玩家下一步位置,提前加载
3. **Hysteresis**——chunk 离开视野后保留几秒,防"回马枪"
4. **Priority**——视野中心 chunk 优先 cache

Casey 这天选最简单的 LRU + 固定 N=64。N=64 在 16³ chunk、玩家步行场景下,工作集 ~32 chunk,有 32 chunk 余量——命中率 90%+。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 chunk cache 用 LRU?用 FIFO 或 random 不行吗?

**参考解答**:LRU 假设"时间局部性"——最近访问的更可能再访问(玩家附近 chunk 反复查)。FIFO 假设"先来先用完"——但玩家附近的 chunk 可能早进 cache 仍然热,不该被淘汰。Random 完全乱——命中率不稳。LRU 在玩家场景下命中率 80-95%,因为玩家移动慢,附近 chunk 持续热。代价:LRU 要记每 chunk 的 last-access time,稍微多内存。

### Lv2 · 动手实践

**题**:实现 chunk cache,测命中率。

要求:
- Sparse grid 模拟,1000 个 chunk
- Cache 大小 64
- 玩家访问模式:90% 时间在 5 个 chunk 内,10% 随机
- 测 LRU vs FIFO vs Random 命中率

**参考解答**:

```rust
use std::collections::{HashMap, VecDeque};

struct ChunkCache {
    capacity: usize,
    chunks: HashMap<u64, ()>,  // chunk_id → in cache
    access_order: VecDeque<u64>,  // LRU 顺序
    hits: u64,
    misses: u64,
    mode: CacheMode,
}

#[derive(Clone, Copy)]
enum CacheMode { LRU, FIFO, Random }

impl ChunkCache {
    fn new(capacity: usize, mode: CacheMode) -> Self {
        ChunkCache {
            capacity,
            chunks: HashMap::new(),
            access_order: VecDeque::new(),
            hits: 0, misses: 0,
            mode,
        }
    }

    fn access(&mut self, chunk_id: u64) {
        if self.chunks.contains_key(&chunk_id) {
            self.hits += 1;
            if let CacheMode::LRU = self.mode {
                // 移到末尾
                if let Some(pos) = self.access_order.iter().position(|&c| c == chunk_id) {
                    self.access_order.remove(pos);
                }
                self.access_order.push_back(chunk_id);
            }
            return;
        }
        self.misses += 1;

        // 淘汰
        if self.chunks.len() >= self.capacity {
            let evict = match self.mode {
                CacheMode::LRU | CacheMode::FIFO => self.access_order.pop_front(),
                CacheMode::Random => {
                    use std::collections::hash_map::DefaultHasher;
                    use std::hash::{Hash, Hasher};
                    let mut h = DefaultHasher::new();
                    chunk_id.hash(&mut h);
                    let idx = (h.finish() as usize) % self.access_order.len();
                    self.access_order.remove(idx)
                }
            };
            if let Some(e) = evict {
                self.chunks.remove(&e);
            }
        }
        self.chunks.insert(chunk_id, ());
        self.access_order.push_back(chunk_id);
    }
}

fn main() {
    use std::time::SystemTime;
    let mut rng_seed = SystemTime::now().duration_since(SystemTime::UNIX_EPOCH).unwrap().subsec_nanos();

    for mode in [CacheMode::LRU, CacheMode::FIFO, CacheMode::Random] {
        let mut cache = ChunkCache::new(64, mode);

        // 模拟 10000 次访问
        for _ in 0..10000 {
            rng_seed = rng_seed.wrapping_mul(1103515245).wrapping_add(12345);
            let r = (rng_seed >> 16) % 100;

            let chunk_id = if r < 90 {
                // 90% 时间在 5 个热 chunk
                (rng_seed >> 16) as u64 % 5
            } else {
                // 10% 随机全 chunk
                (rng_seed >> 16) as u64 % 1000
            };
            cache.access(chunk_id);
        }

        let total = cache.hits + cache.misses;
        println!("{:?}: hit rate = {:.1}%", mode, cache.hits as f64 * 100.0 / total as f64);
    }
}
```

## 8 · Rust / Arch 落地代码

完整 chunk cache + morton:

```rust
use std::collections::HashMap;

#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
struct ChunkCoord { x: i64, y: i64, z: i64 }

// Morton encode:3D 坐标 → 1D u64
fn spread(mut v: u64) -> u64 {
    v = (v | (v << 32)) & 0x1F00000000FFFF;
    v = (v | (v << 16)) & 0x1F0000FF0000FF;
    v = (v | (v << 8))  & 0x100F00F00F00F00F;
    v = (v | (v << 4))  & 0x10C30C30C30C30C3;
    v = (v | (v << 2))  & 0x1249249249249249;
    v
}

fn morton3(x: u32, y: u32, z: u32) -> u64 {
    spread(x as u64) | (spread(y as u64) << 1) | (spread(z as u64) << 2)
}

#[derive(Clone)]
struct Chunk {
    voxels: Vec<[f32; 3]>,  // 16³ = 4096 voxel
    dim: usize,
}

impl Chunk {
    fn new(dim: usize) -> Self {
        Chunk { voxels: vec![[0.0; 3]; dim*dim*dim], dim }
    }
    fn get(&self, lx: usize, ly: usize, lz: usize) -> [f32; 3] {
        self.voxels[(lz * self.dim + ly) * self.dim + lx]
    }
}

const CHUNK_DIM: usize = 16;

struct SparseGrid {
    chunks: HashMap<ChunkCoord, Chunk>,
}

impl SparseGrid {
    fn new() -> Self { SparseGrid { chunks: HashMap::new() } }

    fn add_chunk(&mut self, coord: ChunkCoord) {
        self.chunks.insert(coord, Chunk::new(CHUNK_DIM));
    }
}

struct ChunkCache {
    capacity: usize,
    slots: Vec<Option<(u64, ChunkCoord)>>,  // (morton, coord)
    chunks: Vec<Option<Chunk>>,
    hits: u64,
    misses: u64,
}

impl ChunkCache {
    fn new(capacity: usize) -> Self {
        ChunkCache {
            capacity,
            slots: vec![None; capacity],
            chunks: vec![None; capacity],
            hits: 0,
            misses: 0,
        }
    }

    // 线性查找(morton 排序的话可以 binary search)
    fn find(&self, morton: u64) -> Option<usize> {
        self.slots.iter().position(|s| s.map_or(false, |(m, _)| *m == morton))
    }

    fn get_or_fetch(
        &mut self,
        coord: ChunkCoord,
        backing: &SparseGrid,
    ) -> Option<usize> {
        let m = morton3(
            (coord.x + 10000) as u32,
            (coord.y + 10000) as u32,
            (coord.z + 10000) as u32,
        );

        if let Some(idx) = self.find(m) {
            self.hits += 1;
            return Some(idx);
        }

        self.misses += 1;

        // 从 backing 取
        if let Some(chunk) = backing.chunks.get(&coord) {
            // 找空 slot,或淘汰 LRU(简化:淘汰第一个)
            let target = self.slots.iter().position(|s| s.is_none())
                .unwrap_or(0);
            self.slots[target] = Some((m, coord));
            self.chunks[target] = Some(chunk.clone());
            Some(target)
        } else {
            None
        }
    }

    fn hit_rate(&self) -> f64 {
        let total = self.hits + self.misses;
        if total == 0 { 0.0 } else {
            self.hits as f64 / total as f64
        }
    }
}

fn main() {
    let mut grid = SparseGrid::new();
    // 加 100 个 chunk
    for cx in 0..5 {
        for cy in 0..5 {
            for cz in 0..4 {
                grid.add_chunk(ChunkCoord { x: cx, y: cy, z: cz });
            }
        }
    }

    let mut cache = ChunkCache::new(8);

    // 模拟 1000 次查询,大部分集中在 (1,1,1) 附近
    let queries = vec![
        ChunkCoord { x: 1, y: 1, z: 1 },
        ChunkCoord { x: 1, y: 1, z: 2 },
        ChunkCoord { x: 2, y: 1, z: 1 },
        ChunkCoord { x: 1, y: 2, z: 1 },
        ChunkCoord { x: 1, y: 1, z: 1 },  // 重复,应该 hit
    ];

    for q in &queries {
        cache.get_or_fetch(*q, &grid);
    }

    println!("Cache: capacity={}, hits={}, misses={}, hit_rate={:.1}%",
        cache.capacity, cache.hits, cache.misses, cache.hit_rate() * 100.0);

    // Morton code 测试
    println!("Morton(1,2,3) = {}", morton3(1, 2, 3));
    println!("Morton(0,0,0) = {}", morton3(0, 0, 0));
    println!("Morton(7,7,7) = {}", morton3(7, 7, 7));
}
```

如果命中率低,常见原因:

- Cache 太小 → 增大 capacity
- 玩家快速移动 → 加 prefetch(预测下一帧访问)
- Chunk coord hash 不均匀 → 改用 Morton code 索引
