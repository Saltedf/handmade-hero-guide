# Day 531 · 解析与更新字体元数据

> 字体管线接近收尾。Day 528 你写了 HHT 的字体段,Day 529-530 写了 PNG atlas。Day 531 Casey 把整套整合:**解析已有 HHT,修改某些字段(如字号、advance),再写回 HHT**。这是 Day 510 HHT parser + Day 528 HHT writer 的组合实战。本质上是"读 → 改 → 写"循环——所有配置文件工具的核心模式。

## 0 · 为什么要有这一天

游戏开发中,资产经常需要"批处理修改"。比如你做了 100 个字体的 HHT,现在想:

- 把所有字体的 size 从 32 改为 36(玩家反馈"字太小")
- 给所有字体的 advance 字段乘 1.1(字间距太挤)
- 删除某些不再使用的 glyph

如果手工编辑 100 个文件,你能改到吐。**自动化是工程师的本能**——写一个工具,读 HHT,改字段,写回 HHT。这就是 Day 531 的本质。

这种"读 → 改 → 写"模式不止 HHT,几乎所有文本格式都用:

- `sed -i 's/old/new/g'` —— 流编辑器,批量替换
- `jq '.field = new_value'` —— JSON 编辑
- `xq` (yq) —— YAML 编辑
- `toml-edit` —— TOML 编辑

Casey 选择手写工具(而不是用 sed),因为 HHT 是自定义格式,sed 无法理解它的结构。你需要**结构化编辑**:读成 AST → 改 AST → 序列化回文本。

#### 结构化编辑 vs 文本替换:精度对比

让我把这两种编辑方式的差别讲清楚,因为这是工具开发的核心选择。

**文本替换**(sed/awk 风格):
- 优点:简单快,一行命令搞定
- 缺点:不理解语义,容易误改

**结构化编辑**(AST + 序列化):
- 优点:精确,只改你想改的
- 缺点:需要 parser + writer,代码量大

具体例子:你想把 HHT 文件里 `font_size = 32` 改成 `font_size = 36`。

文本替换 `sed 's/size = 32/size = 36/g'` 会改:
- `font_size = 32` → `font_size = 36` ✓
- `glyph_size = 32` → `glyph_size = 36` ✓(可能也想改)
- `default_size = 32` → `default_size = 36` ✗(可能不想改)
- `texture_size = 32` → `texture_size = 36` ✗(肯定不想改,这是纹理像素数)

结构化编辑只在 `Font.size` 字段改,其他不动。精度差异巨大。

工业级 JSON 工具 `jq` 走的是结构化路线:`jq '.font.size = 36'` 只改 font.size,不动其他字段。这是为什么 `jq` 比 `sed` 在 JSON 编辑上更可靠。

**通用规则**:对结构化格式(JSON、YAML、TOML、XML、自有 HHT),**永远用结构化编辑**。对纯文本(log、CSV、Markdown),文本替换够用。

#### CLI 工具的设计哲学

Casey 这一天做的工具是个 CLI 命令:`modify_hht --size 36 --advance-scale 1.1 file.hht`。让我把这个 CLI 的设计哲学讲清楚。

工业级 CLI 工具遵循 POSIX 风格:

1. **参数命名一致**:`--size`、`--advance-scale`,所有参数都用 `--` 前缀
2. **支持 `--help`**:列出所有参数和用法
3. **支持 `--version`**:打印版本号
4. **退出码语义**:0 = 成功,1 = 参数错,2 = 文件错
5. **stdin/stdout 流**:默认从 stdin 读,写 stdout;`-i` 修改原文件
6. **错误信息友好**:`Error: file 'x.hht' not found` 而不是 panic

Casey 的 HH 工具不全遵循这些(他是单人项目,够用就行),但你的开源工具应该。Rust 用 `clap` crate 自动生成符合这些惯例的 CLI。

## 2 · 心智模型

### 类比:文本编辑器的"查找替换"

文本编辑器的"查找替换"功能:输入"找什么"和"替换为什么",编辑器扫描全文,把所有匹配项替换。但**编辑器不理解文本的含义**——它只是字节匹配。如果你的代码里有个变量叫 `font_size`,你替换 `size` 也会改这个变量名——bug。

结构化编辑相反:**先理解文本是什么**(parse 成 AST),**再改 AST 的特定节点**,**最后序列化**。改 `font.size` 字段不会误伤变量名 `font_size`。

Casey 这天就是结构化编辑——HHT 是结构化的,字段名明确,改字段不影响其他部分。

### 严谨展开:读-改-写循环

```rust
fn main() {
    // 1. 读
    let text = std::fs::read_to_string("input.hht").unwrap();
    let mut font = parse_hht_font(&text).unwrap();
    
    // 2. 改
    font.size = 36;
    for glyph in &mut font.glyphs {
        glyph.advance *= 1.1;  // 字间距加 10%
    }
    
    // 3. 写
    let new_text = write_hht_font(&font);
    std::fs::write("input.hht", new_text).unwrap();
}
```

三个步骤:

- **读**:文件 → 字节 → 字符串 → AST → 结构体
- **改**:操作结构体(Rust 的所有权让这步安全)
- **写**:结构体 → AST → 字符串 → 字节 → 文件

每一步都可独立测试。

#### 处理多文件:glob 模式

实际场景中你要改的不止一个 HHT,可能是 100 个。Rust 用 `glob` crate 匹配多个文件:

```rust
use glob::glob;

for entry in glob("assets/**/*.hht").expect("bad pattern") {
    let path = entry.unwrap();
    println!("Processing: {:?}", path);
    
    // 读-改-写
    let text = std::fs::read_to_string(&path).unwrap();
    let mut font = parse_hht_font(&text).unwrap();
    font.size = 36;
    let new_text = write_hht_font(&font);
    std::fs::write(&path, new_text).unwrap();
}
```

`**` 是 glob 的递归通配符,匹配任意层级子目录。`assets/**/*.hht` 匹配 `assets/font1.hht`、`assets/sub/font2.hht`、`assets/sub/subsub/font3.hht` 等。

工业级 CLI 工具都支持 glob。GNU `find` + `xargs` 是这种模式的 POSIX 经典组合:

```bash
find assets -name '*.hht' -exec modify_hht --size 36 {} \;
```

Rust 的 `glob` crate 让你在程序内做同样的事。

#### 备份和 dry-run:工业级 CLI 的安全网

批量修改文件很危险——一次错误操作可能毁掉 100 个文件。工业级 CLI 有两个安全网:

1. **`--dry-run` 模式**:打印"会改什么",但不实际写
2. **`--backup` 模式**:修改前把原文件备份到 `.bak`

```rust
use clap::Parser;

#[derive(Parser)]
struct Args {
    #[arg(long)]
    size: Option<u32>,
    
    #[arg(long)]
    advance_scale: Option<f32>,
    
    /// 不实际修改,只打印将要做的改变
    #[arg(long)]
    dry_run: bool,
    
    /// 修改前备份原文件
    #[arg(long)]
    backup: bool,
    
    /// 要处理的 HHT 文件(glob 模式)
    files: Vec<String>,
}

fn main() {
    let args = Args::parse();
    for pattern in &args.files {
        for entry in glob(pattern).unwrap() {
            let path = entry.unwrap();
            process_one(&path, &args);
        }
    }
}

fn process_one(path: &Path, args: &Args) {
    let original = std::fs::read_to_string(path).unwrap();
    let mut font = parse_hht_font(&original).unwrap();
    
    if let Some(s) = args.size { font.size = s; }
    if let Some(scale) = args.advance_scale {
        for g in &mut font.glyphs { g.advance *= scale; }
    }
    
    let new_text = write_hht_font(&font);
    
    if args.dry_run {
        println!("Would modify {:?}: size={}", path, font.size);
        return;
    }
    
    if args.backup {
        let backup = path.with_extension("hht.bak");
        std::fs::write(&backup, &original).unwrap();
    }
    
    std::fs::write(path, new_text).unwrap();
}
```

这两个 flag 是工业级 CLI 的标配。你的开源工具应该都有。Casey 在 HH 没做这些(单人项目),但你做生产工具必须有。

### 结构化编辑 vs 文本替换

**文本替换**(sed 风格):

```bash
sed -i 's/size = 32/size = 36/g' input.hht
```

简单但脆弱。如果 HHT 里其他地方有 "size = 32"(比如某个 glyph 的 width = 32),也会被改。

**结构化编辑**(parse + modify + write):

```rust
let mut font = parse(&text);
font.size = 36;  // 只改 font 级 size 字段
std::fs::write(path, write(&font));
```

精确,只改你想改的字段。代价是必须先写 parser 和 writer。

Casey 选结构化,因为 HHT 字段语义复杂,文本替换会误伤。

### 增量更新 vs 全量重写

Casey 的方案是**全量重写**:读所有 → 改 → 写所有。这丢失了原始文件里的注释、空行、字段顺序——格式化的 writer 可能改变字段顺序,删掉用户加的注释。

工业级方案:**保留原文件的"格式信息"**(空格、注释、字段顺序),只改特定字段。这叫**增量编辑**。JSON 的 `jq` 工具支持 `--indent` 等选项控制输出格式,但完全保留原格式仍是研究课题。

Casey 不在乎这些(他的 HHT 是工具产出,没有手工编辑),所以全量重写够用。

## 5 · 对照与变奏

不同语言的"读-改-写"工具:

**Python + PyYAML**:
```python
import yaml
with open('config.yaml') as f:
    config = yaml.safe_load(f)
config['font']['size'] = 36
with open('config.yaml', 'w') as f:
    yaml.dump(config, f)
```
Python 因为类型松散,适合快速原型。但 production 用 Rust/Go 更安全。

**Go + gopkg.in/yaml.v3**:
```go
data, _ := os.ReadFile("config.yaml")
var config Config
yaml.Unmarshal(data, &config)
config.Font.Size = 36
out, _ := yaml.Marshal(&config)
os.WriteFile("config.yaml", out, 0644)
```
Go 比 Rust 简单,适合 DevOps 工具。

**Rust + serde_yaml**:
```rust
let config: Config = serde_yaml::from_reader(File::open("config.yaml")?)?;
let mut config = config;
config.font.size = 36;
serde_yaml::to_writer(File::create("config.yaml")?, &config)?;
```
Rust 编译期检查类型,最安全。Casey 风格的工业级实现。

**Casey 的 HH**:手写 parser/writer,因为 HHT 是自定义格式。如果你的项目用标准格式(JSON/YAML/TOML),用 serde 一行解决。

### "Round-trip"测试:验证读-改-写不破坏数据

工业级 parser/writer 必须通过的测试:**parse(string) → write(parsed) == string**。这叫 round-trip property(往返不变性)。如果 parse + write 后的字符串和原文不同,说明 parser 或 writer 有 bug。

```rust
#[test]
fn test_round_trip() {
    let original = std::fs::read_to_string("test.hht").unwrap();
    let parsed = parse_hht_font(&original).unwrap();
    let written = write_hht_font(&parsed);
    assert_eq!(original, written, "round-trip failed");
}
```

如果 round-trip 失败,常见原因:
- Parser 容忍了非标准格式(如多余空格),writer 不写空格
- Writer 加了默认字段,parser 不读
- 字段顺序不稳定(HashMap 遍历顺序随机)

修复:**用 BTreeMap 替代 HashMap**(保证顺序),**保留原 raw 文本** (parser 记录每个字段的原始字符串),**显式处理默认值**。

这种"round-trip property"是 property-based testing 的核心思想——你不写具体测试用例,而是写一个对任意输入都成立的"性质",用随机输入测试 1000 次。Rust 的 `proptest` crate 是这个领域的标准工具。

### 序列化格式的演进

Casey 的 HHT 格式是 v1,以后可能演进到 v2(加新字段)、v3(改字段含义)。如何兼容旧文件?

工业级方案:

1. **版本号字段**:文件开头写 `version = 1`,parser 根据版本走不同分支
2. **默认值**:新字段加 default,旧文件解析时填 default
3. **可选字段**:`Option<T>` 表示可能不存在的字段
4. **migration 函数**:旧版本 → 新版本的转换函数,自动跑

Rust 的 `serde` 配合 `#[serde(default)]` 和 `#[serde(alias = "old_name")]` 自动处理大部分情况。Casey 手动处理这些(因为没有 serde),代码更冗长但完全可控。

这种"格式演进"是工业级数据格式的核心难题。Protocol Buffers、Avro、Cap'n Proto 都是为解决这个问题设计的。学会这些思想,你看 Google/Netflix 的内部数据格式都豁然开朗。



不同领域的"读-改-写"工具:

- **文本**:`sed`、`awk`、`perl -i`
- **JSON**:`jq`、`dasel`
- **YAML**:`yq`、`yq-go`

### Lv2 · 动手实践

**题**:写一个 `hhfont_edit` 工具,命令行参数:`hhfont_edit <input.hht> --size N --scale-advance F`。功能:读 HHT,把 font.size 改为 N,把所有 glyph.advance 乘 F,写回原文件。运行后:HHT 的 size 字段变化,glyph 的 advance 数值按 F 缩放。

**参考解答**:

```rust
use std::env;

// 假设已有 parse_hht_font 和 write_hht_font(来自 day528)

struct Args {
    input: String,
    new_size: Option<u32>,
    advance_scale: Option<f32>,
}

fn parse_args() -> Args {
    let args: Vec<String> = env::args().collect();
    let mut input = String::new();
    let mut new_size = None;
    let mut advance_scale = None;
    
    let mut i = 1;
    while i < args.len() {
        match args[i].as_str() {
            "--size" => {
                i += 1;
                new_size = args[i].parse().ok();
            }
            "--scale-advance" => {
                i += 1;
                advance_scale = args[i].parse().ok();
            }
            _ => input = args[i].clone(),
        }
        i += 1;
    }
    Args { input, new_size, advance_scale }
}

fn main() {
    let args = parse_args();
    if args.input.is_empty() {
        eprintln!("用法: hhfont_edit <input.hht> [--size N] [--scale-advance F]");
        std::process::exit(1);
    }
    
    // 读
    let text = std::fs::read_to_string(&args.input)
        .expect("read input");
    let mut font = parse_hht_font(&text).expect("parse");
    println!("原: size={}, glyphs={}", font.size, font.glyphs.len());
    
    // 改
    if let Some(s) = args.new_size {
        font.size = s;
    }
    if let Some(scale) = args.advance_scale {
        for g in &mut font.glyphs {
            g.advance *= scale;
        }
    }
    println!("新: size={}, glyphs={}", font.size, font.glyphs.len());
    
    // 写回(全量重写)
    let new_text = write_hht_font(&font);
    std::fs::write(&args.input, new_text).expect("write");
    println!("已写回 {}", args.input);
}
```

为什么这么写:`env::args()` 是 Rust 标准的 CLI 参数读取(简单场景够用,复杂场景用 `clap` crate)。读 → 改 → 写三步清晰分离。`Option<T>` 表示"可能不改"——None 时不操作。

// 完整的 HHT 字体元数据编辑器

use std::env;
use std::fmt::Write as _;

#[derive(Debug, Clone, PartialEq)]
pub struct HhtFont {
    pub name: String,
    pub size: u32,
    pub png_path: String,
    pub ascent: i32,
    pub descent: i32,
    pub line_gap: i32,
    pub glyphs: Vec<HhtGlyph>,
}

#[derive(Debug, Clone, PartialEq)]
pub struct HhtGlyph {
    pub char_code: char,
    pub atlas_x: u32,
    pub atlas_y: u32,
    pub width: u32,
    pub height: u32,
    pub advance: f32,
}

// 极简 parser(参考 day528)
pub fn parse_hht_font(text: &str) -> Result<HhtFont, String> {
    let mut name = String::new();
    let mut size = 0u32;
    let mut png_path = String::new();
    let mut ascent = 0i32;
    let mut descent = 0i32;
    let mut line_gap = 0i32;
    let mut glyphs = Vec::new();
    
    let mut lines = text.lines().peekable();
    while let Some(line) = lines.next() {
        let line = line.trim();
        if line.starts_with("name") {
            name = line.split('=').nth(1).unwrap().trim().trim_matches('"').into();
        } else if line.starts_with("size") && !line.contains("atlas") {
            size = line.split('=').nth(1).unwrap().trim().parse().map_err(|e: std::num::ParseIntError| e.to_string())?;
        } else if line.starts_with("png") {
            png_path = line.split('=').nth(1).unwrap().trim().trim_matches('"').into();
        } else if line.starts_with("ascent") {
            ascent = line.split('=').nth(1).unwrap().trim().parse().map_err(|e: std::num::ParseIntError| e.to_string())?;
        } else if line.starts_with("descent") {
            descent = line.split('=').nth(1).unwrap().trim().parse().map_err(|e: std::num::ParseIntError| e.to_string())?;
        } else if line.starts_with("line_gap") {
            line_gap = line.split('=').nth(1).unwrap().trim().parse().map_err(|e: std::num::ParseIntError| e.to_string())?;
        } else if line.starts_with("glyph") {
            let char_part = line.split('\'').nth(1).unwrap_or(" ");
            let char_code = char_part.chars().next().unwrap_or(' ');
            // 收集 glyph body
            let mut atlas_x = 0u32;
            let mut atlas_y = 0u32;
            let mut width = 0u32;
            let mut height = 0u32;
            let mut advance = 0.0f32;
            for body_line in lines.by_ref() {
                let bl = body_line.trim();
                if bl.starts_with('}') { break; }
                if let Some(eq_pos) = bl.find('=') {
                    let key = bl[..eq_pos].trim();
                    let val = bl[eq_pos+1..].trim();
                    match key {
                        "atlas_x" => atlas_x = val.parse().unwrap_or(0),
                        "atlas_y" => atlas_y = val.parse().unwrap_or(0),
                        "width" => width = val.parse().unwrap_or(0),
                        "height" => height = val.parse().unwrap_or(0),
                        "advance" => advance = val.parse().unwrap_or(0.0),
                        _ => {}
                    }
                }
            }
            glyphs.push(HhtGlyph {
                char_code, atlas_x, atlas_y, width, height, advance
            });
        }
    }
    
    Ok(HhtFont { name, size, png_path, ascent, descent, line_gap, glyphs })
}

pub fn write_hht_font(f: &HhtFont) -> String {
    let mut s = String::new();
    writeln!(s, "font {{").unwrap();
    writeln!(s, "    name = \"{}\"", f.name).unwrap();
    writeln!(s, "    size = {}", f.size).unwrap();
    writeln!(s, "    png = \"{}\"", f.png_path).unwrap();
    writeln!(s, "    ascent = {}", f.ascent).unwrap();
    writeln!(s, "    descent = {}", f.descent).unwrap();
    writeln!(s, "    line_gap = {}", f.line_gap).unwrap();
    writeln!(s).unwrap();
    for g in &f.glyphs {
        writeln!(s, "    glyph '{}' {{", g.char_code).unwrap();
        writeln!(s, "        atlas_x = {}", g.atlas_x).unwrap();
        writeln!(s, "        atlas_y = {}", g.atlas_y).unwrap();
        writeln!(s, "        width = {}", g.width).unwrap();
        writeln!(s, "        height = {}", g.height).unwrap();
        writeln!(s, "        advance = {:.2}", g.advance).unwrap();
        writeln!(s, "    }}").unwrap();
    }
    writeln!(s, "}}").unwrap();
    s
}

fn main() {
    let args: Vec<String> = env::args().collect();
    if args.len() < 2 {
        eprintln!("用法: {} <input.hht> [--size N] [--scale-advance F] [--rename NEW_NAME]", args[0]);
        std::process::exit(1);
    }
    
    let input = &args[1];
    let mut new_size: Option<u32> = None;
    let mut advance_scale: Option<f32> = None;
    let mut rename: Option<String> = None;
    
    let mut i = 2;
    while i < args.len() {
        match args[i].as_str() {
            "--size" => { i += 1; new_size = args[i].parse().ok(); }
            "--scale-advance" => { i += 1; advance_scale = args[i].parse().ok(); }
            "--rename" => { i += 1; rename = Some(args[i].clone()); }
            _ => {}
        }
        i += 1;
    }
    
    // 读
    let text = std::fs::read_to_string(input).expect("read");
    let mut font = parse_hht_font(&text).expect("parse");
    println!("原: name={} size={} glyphs={}", font.name, font.size, font.glyphs.len());
    
    // 改
    if let Some(s) = new_size { font.size = s; }
    if let Some(scale) = advance_scale {
        for g in &mut font.glyphs {
            g.advance *= scale;
        }
    }
    if let Some(ref name) = rename {
        font.name = name.clone();
    }
    println!("新: name={} size={} glyphs={}", font.name, font.size, font.glyphs.len());
    
    // 写回
    let new_text = write_hht_font(&font);
    std::fs::write(input, new_text).expect("write");
    println!("已写回 {}", input);
}

出错怎么办:

- **`parse error`**:HHT 格式不对。先用 `cat input.hht` 检查。
- **`glyph 解析为空`:body 行被当成 glyph 处理。检查 `peekable` 和 `by_ref` 用法。
- **数值没改变**:Option 没传,或 parser 没解析到该字段。
