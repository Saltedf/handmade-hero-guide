# Day 469 · 对导入资产下采样

> 你导入了一张 4096×4096 的英雄贴图,但游戏相机永远离角色 5 米远,4096 完全用不到——它在显存里占 64MB,而 1024 就够清晰只占 4MB。Casey 这一天做的事:**在导入时下采样(downsample)**,把超大贴图缩小到合理尺寸。这听起来"只是缩小图像",但它涉及**信号处理理论**(采样定理、抗锯齿)和**GPU 显存管理**(mipmap、texture streaming)。

## 0 · 为什么要有这一天

游戏开发最常见的资源浪费之一:**贴图分辨率过高**。美术习惯性画 4096×4096,因为"细节多,以后能裁剪"。但游戏里:

- UI 图标永远显示 64×64,4096 完全是浪费
- 远景的天空盒在屏幕上只占 200 像素,8K 贴图毫无意义
- NPC 在玩家 10 米外,1K 贴图就够,4K 多余

过大的贴图不仅浪费显存,还导致:
- **加载时间变长**(从磁盘读 64MB vs 4MB)
- **GPU 带宽浪费**(采样 4096² 纹理 cache miss 频繁)
- **构建包体变大**(分发文件膨胀)

**解决方案**:**在导入时下采样**——美术提供高分辨率原图,导入器根据 annotation 或类型自动缩小到合适尺寸。Casey 这一天加这个功能。

但下采样不能简单"丢像素"。考虑下采样的核心问题:

**问题**:一张 4×4 的图(16 像素),缩到 2×2(4 像素)。如果直接丢像素(取左上、左下、右上、右下的某一个),结果取决于选哪个——选不同像素得到完全不同的小图。这种"挑一个扔"叫**最近邻下采样(nearest neighbor downsampling)**,在像素艺术里能用,在真实贴图里会导致**摩尔纹(moiré)**和**锯齿(aliasing)**。

**正确做法**:把多个源像素**加权平均**成一个目标像素。4×4 缩 2×2 时,每个目标像素是 4 个源像素的平均。这叫**盒式滤波(box filter)**,简单但有效。

更高级的下采样用**双线性(bilinear)**、**双三次(bicubic)**、**Lanczos** 等滤波器,核(filter kernel)不同,效果和计算成本不同。Casey 这一天选最简单的盒式,够用。

完成这一天之后,你具备了:
- 理解采样定理(Nyquist)为什么决定下采样必须有低通滤波
- 在 Rust 里写高性能像素循环
- 知道何时选哪种下采样算法(pixel art vs photo)

## 1 · Casey 今天做了什么

Casey 这一天的工作分四步:

第一步,他在导入器里加了一个 `downsample_if_needed(asset, target_width, target_height)` 函数。如果 asset 的 annotation 有 `max_width` / `max_height`,且原图大于这个尺寸,触发下采样。

第二步,他实现了盒式滤波下采样。对于 2x downsample(目标尺寸是源一半),每个目标像素是 2×2 个源像素的平均。对于非整数倍(比如源 100×100,目标 30×30),他用了"近似"做法——不做精确重采样,只支持 2x / 4x / 8x 整数倍。

第三步,他遇到一个 bug:下采样后 alpha 通道(透明度)被错误地"和 RGB 一起平均"。这导致半透明边缘变成"半透明的灰色",看起来像有黑色 fringe。Casey 意识到:**premultiplied alpha** 应该在平均前应用,不是后应用。

第四步,他在 annotation 里加了 `downsample_to = 1024` 字段,美术可以在 sidecar 里指定目标尺寸。

这集的核心教训:**图像处理看似简单,实际处处是坑**。任何"像素数学"都有色彩空间、alpha、gamma 的微妙问题。

## 2 · 心智模型

### 类比:缩略图生成

你拍了一张 4000×3000 的照片,要在画廊里显示成 200×150 缩略图。怎么做?

最简单粗暴的方法:**最近邻**——从原图每 20 个像素挑一个。结果会非常难看,因为挑中的像素可能恰好是黑色(阴影)或白色(高光),整体看起来斑驳。

正确做法:**平均**——把每 20×20 个像素的颜色平均,得到一个缩略图像素。这样保留了"这块区域的平均颜色",视觉上接近原图缩小后的样子。

下采样的本质就是缩略图生成。但游戏贴图比照片更挑剔,因为贴图会被 GPU 反复采样、放缩、滤波,任何下采样瑕疵都会被放大。

### 采样定理(Nyquist-Shannon)

下采样不是随便丢像素,背后有严格数学。**采样定理**说:

> 一个信号如果最高频率是 f,采样率必须 ≥ 2f 才能无损重建。反过来说,采样率是 f_s 时,信号最高频率不能超过 f_s / 2(叫 Nyquist 频率)。

图像是 2D 信号,贴图 4096×4096 的"频率"是每 4096 像素有多少个周期。下采样到 1024×1024 时,Nyquist 频率降低 4 倍——超过这个频率的内容必须**滤掉**(低通滤波),否则产生**锯齿(aliasing)**。

锯齿的表现:
- 高频细节(细线、点阵)变成低频伪影(摩尔纹)
- 边缘出现"阶梯"
- 颜色失真

下采样前**必须**先低通滤波(平均就是最简单的低通)。这就是为什么"丢像素"不行,"平均像素"可以。

### 盒式滤波(Box Filter)详解

最简单的低通滤波是**盒式滤波**:目标像素 = 对应源区域所有像素的算术平均。

2x 下采样的数学:

```
target(x, y) = average of source pixels in [2x..2x+1, 2y..2y+1]
            = (source(2x, 2y) + source(2x+1, 2y) + 
               source(2x, 2y+1) + source(2x+1, 2y+1)) / 4
```

推广到 4x 下采样:目标 1 像素 = 源 16 像素平均。Nx 下采样:目标 1 像素 = 源 N² 像素平均。

盒式滤波的优点:
- 计算简单(N² 次加法 + 1 次除法)
- 实现直观(双重循环)
- 对大多数贴图足够好

缺点:
- 频域响应不平坦(高频残留多)
- 对极端高对比度边缘(黑白像素相邻)有"振铃"伪影

更高级的滤波器(高斯、Lanczos)频域响应更好,但计算复杂。Casey 选盒式,够用。

### RGBA 通道的微妙问题

下采样时,RGB 和 A(alpha)通道的处理方式有讲究。考虑半透明像素 `(R=255, G=0, B=0, A=128)`(半透明红色)。

**错误做法**:直接对 RGBA 各通道独立平均。

```
source:
  (255, 0, 0, 128)  (0, 0, 0, 0)
  (255, 0, 0, 128)  (0, 0, 0, 0)
box filter naive:
  ((255+0+255+0)/4, (0+0+0+0)/4, (0+0+0+0)/4, (128+0+128+0)/4)
= (128, 0, 0, 64)
```

结果是"半透明的暗红色"。但视觉上,两个半透明红像素 + 两个透明像素,应该看起来像"很淡的红色"。半透明暗红错误——它会把背景和半透明红"混"在一起。

**正确做法**:premultiplied alpha。

先把每个像素 RGB 乘以 alpha(归一化到 0-1):

```
(255, 0, 0, 128) -> premul: (128, 0, 0, 128)  // R 乘以 alpha/255
(0, 0, 0, 0)     -> premul: (0, 0, 0, 0)
```

然后对 premultiplied RGB 和 alpha 各自平均:

```
premul RGB avg: ((128+0+128+0)/4, 0, 0) = (64, 0, 0)
alpha avg: (128+0+128+0)/4 = 64
result premul: (64, 0, 0, 64)
result straight: (64/64*255, 0, 0, 64) = (255, 0, 0, 64)
```

结果是"很淡的红色,Alpha=64"。这就是视觉上正确的结果——颜色还是红,只是更透明了。

Casey 在第三步踩了这个坑,意识到下采样必须用 premultiplied alpha。

### Mipmap:GPU 上的下采样

GPU 自己也会下采样,但它的下采样是 **mipmap** 链——预先计算好的多级纹理:

```
level 0: 1024×1024(原图)
level 1: 512×512(box filter 下采样)
level 2: 256×256
level 3: 128×128
...
level 10: 1×1
```

GPU 渲染时根据贴图在屏幕上的大小,自动选合适的 level——离得远用 level 5(32×32),离得近用 level 0(1024×1024)。这避免了"远距离反复采样高分辨率纹理"的浪费。

Casey 现在的导入器下采样是**一次性**的(把 4096 缩到 1024),不生成完整 mipmap 链。Day 500+ 他会加 mipmap 自动生成。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业里下采样是资产管线的标准步骤:

- **Unity**:导入贴图时设置 Max Size(32 / 64 / 128 / ... / 8192),导入器自动下采样。Compression 选项也在此设置(BCn / ASTC / ETC)
- **Unreal**:Texture Setting 里的 Maximum Texture Size,同上
- **Godot**:Import dialog 里的 Size Limit,同上
- **glTF pipeline**:用 `gltf-transform` 等工具后处理,可下采样

商业引擎还提供"多版本"——同一张贴图存多个分辨率,运行时根据硬件(手机 / 高配 PC)选合适的。这叫 **texture LOD bias** 或 **texture streaming**。

### 3.2 · 🎨 图形学视角

下采样涉及的图形学概念:

- **采样定理**:决定最小滤波要求
- **抗锯齿(anti-aliasing)**:消除边缘锯齿,MSAA / FXAA / TAA 都是某种意义上的"超采样"
- **mipmap**:GPU 端的预下采样
- **各向异性滤波(anisotropic filtering)**:斜视角下用多个 mipmap level 混合,避免远距离纹理模糊
- **gamma 校正**:在 sRGB 空间做平均 vs 在 Linear 空间做平均,结果不同(应该在 Linear 空间下采样,但 PNG 是 sRGB)

gamma 校正的下采样问题:

PNG 存 sRGB(非线性编码)。直接在 sRGB 数值上平均是错的——应该先转 Linear 再平均再转回 sRGB。

```
错误:sRGB_avg = (sRGB_a + sRGB_b) / 2
正确:lin_avg = (sRGB_to_linear(a) + sRGB_to_linear(b)) / 2
      sRGB_avg = linear_to_sRGB(lin_avg)
```

Casey 这一天没做 sRGB 校正(简化),后期 Day 500+ 会处理。商业引擎(Unity / Unreal)默认做。

### 3.4 · 🦀 Rust 生态视角

Rust 处理图像的标准 crate 是 `image`(https://github.com/image-rs/image):

```toml
[dependencies]
image = "0.25"
```

```rust
use image::{ImageBuffer, Rgba, imageops};

let img = image::open("hero.png")?.to_rgba8();
// image::imageops 提供 FilterType 列表
use image::imageops::FilterType;
let small = imageops::resize(&img, 1024, 1024, FilterType::Lanczos3);
small.save("hero_small.png")?;
```

`FilterType` 支持:
- `Nearest`:最近邻,像素艺术用
- `Triangle`:双线性
- `CatmullRom`:双三次,中等质量
- `Gaussian`:高斯
- `Lanczos3`:Lanczos,最高质量但最慢

Casey 手写盒式滤波,等价于 `Triangle`(近似)。Rust 实现可以选:

```rust
// 自己手写盒式(教学价值)
fn box_downsample_2x(img: &ImageBuffer<Rgba<u8>, Vec<u8>>) 
    -> ImageBuffer<Rgba<u8>, Vec<u8>> 
{
    let (w, h) = img.dimensions();
    let new_w = w / 2;
    let new_h = h / 2;
    let mut out = ImageBuffer::new(new_w, new_h);
    
    for y in 0..new_h {
        for x in 0..new_w {
            // 取 2x2 的 4 个像素
            let p00 = img.get_pixel(2*x, 2*y);
            let p10 = img.get_pixel(2*x+1, 2*y);
            let p01 = img.get_pixel(2*x, 2*y+1);
            let p11 = img.get_pixel(2*x+1, 2*y+1);
            
            // Premultiplied alpha
            let premul = |p: &Rgba<u8>| -> [u32; 4] {
                let a = p[3] as u32;
                [p[0] as u32 * a / 255, p[1] as u32 * a / 255, 
                 p[2] as u32 * a / 255, a]
            };
            
            let s = [premul(p00), premul(p10), premul(p01), premul(p11)];
            let avg: [u32; 4] = [
                s.iter().map(|p| p[0]).sum::<u32>() / 4,
                s.iter().map(|p| p[1]).sum::<u32>() / 4,
                s.iter().map(|p| p[2]).sum::<u32>() / 4,
                s.iter().map(|p| p[3]).sum::<u32>() / 4,
            ];
            
            // Un-premultiply
            let pixel = if avg[3] > 0 {
                Rgba([
                    (avg[0] * 255 / avg[3]) as u8,
                    (avg[1] * 255 / avg[3]) as u8,
                    (avg[2] * 255 / avg[3]) as u8,
                    avg[3] as u8,
                ])
            } else {
                Rgba([0, 0, 0, 0])
            };
            
            out.put_pixel(x, y, pixel);
        }
    }
    
    out
}
```

性能:Rust 的 image crate 用 SIMD 优化,4 通道 RGBA 1024×1024 下采样到 512×512 在 release 模式 < 5ms。Casey 手写的 C 版本类似性能。

## 5 · 对照与变奏

### 同一下采样,不同算法

考虑把 4×4 RGB 图下采样到 2×2。源数据:

```
255 0 0   0 255 0   |  0 0 255   255 255 0
0 255 0   255 0 0   |  255 0 255  0 255 255
---------+----------
0 0 255   255 255 0 |  255 0 0   0 255 0
255 0 255 0 255 255 |  0 255 0   255 0 0
```

**最近邻**(取左上像素):

```
255 0 0   |  0 0 255
0 0 255   |  255 0 0
```

结果失真严重——每个 2×2 块只取一个像素,其他三个被忽略。

**盒式**(平均 4 像素):

```
(255+0+0+255)/4, ... = 128, 128, 0
```

每个目标像素是 4 源的平均,看起来"模糊但保留整体色"。

**双线性**:对盒式的扩展,核是三角形权重(中心权重大,边缘小)。结果和盒式相似但边缘更平滑。

**Lanczos**:用 sinc 函数做核,理论上最优。但每目标像素要 36 个源像素参与(6×6 核),计算贵。

工业经验:99% 场景 Box / Bilinear 够用,Lanczos 留给"贴图最终发布前的最后处理"。

### CPU 下采样 vs GPU 下采样

| | CPU 下采样 | GPU 下采样 |
|---|---|---|
| 时机 | 导入时(offline) | 运行时(runtime) |
| 实现 | Rust / C 代码 | glGenerateMipmap |
| 性能 | 一次,慢无所谓 | 每帧,要快 |
| 控制力 | 完全自定义 | 固定算法(盒式) |

Casey 用 CPU 下采样(导入时一次性),GPU 后续做 mipmap 自动生成。两个不是互斥,而是分工。

### 历史演化

- **1990s**:游戏贴图普遍 64×64 / 128×128,下采样没必要
- **2000s**:GPU 显存增长,贴图到 1024×1024,开始需要下采样
- **2010s**:移动游戏兴起,手机显存小,激进下采样(1024 → 512)
- **2020s**:ASTC / BC7 压缩 + mipmap 链,下采样变成"压缩 pipeline 的一环"

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"直接丢像素"(最近邻下采样)在照片贴图上会出现摩尔纹,但在 pixel art 上不会?用 Nyquist 定理解释。

**参考解答**:Nyquist 定理说,采样率 ≥ 2倍信号最高频率才能无损重建。反过来说,采样率降低时,信号最高频率必须相应降低(低通滤波),否则高频"折叠"成低频伪影,即摩尔纹。

**照片贴图**:含丰富高频细节(细密的纹理、毛发、点阵)。下采样时如果不滤掉这些高频,它们会"折叠"成低频,表现为摩尔纹(同心圆、波纹)。所以必须先低通滤波。

**pixel art**:本身就是离散设计,没有"信号频率"概念——每个像素是"设计意图",不是连续信号的采样。下采样时不需要低通,因为不存在"高频"。最近邻反而最忠实地保留"哪个像素是哪个颜色"。

类比:照片是"连续绘画的数字化采样",pixel art 是"原生数字设计"。两者下采样逻辑根本不同。

### Lv2 · 动手实践

**题**:在 Rust 里实现盒式下采样(2x),处理 RGBA 数据,要求正确处理 premultiplied alpha。完成标准:
- 输入是 `Vec<u8>`(RGBA packed,4 字节一像素)+ width + height
- 输出是 2x 下采样后的 `Vec<u8>` + 新 width / height
- 测试:输入 4 个像素 `(255,0,0,128), (0,0,0,0), (255,0,0,128), (0,0,0,0)`,输出应该是 `(255,0,0,64)`(颜色保留,半透明)

**参考解答**:

```rust
// 简化版:不处理奇数尺寸(假设 width / height 都是偶数)

pub struct RgbaImage {
    pub data: Vec<u8>,
    pub width: u32,
    pub height: u32,
}

impl RgbaImage {
    pub fn pixel(&self, x: u32, y: u32) -> [u8; 4] {
        let i = ((y * self.width + x) * 4) as usize;
        [self.data[i], self.data[i+1], self.data[i+2], self.data[i+3]]
    }
    
    pub fn box_downsample_2x(&self) -> RgbaImage {
        assert!(self.width % 2 == 0 && self.height % 2 == 0);
        
        let new_w = self.width / 2;
        let new_h = self.height / 2;
        let mut out = vec![0u8; (new_w * new_h * 4) as usize];
        
        for y in 0..new_h {
            for x in 0..new_w {
                // 取 2x2 的 4 个源像素
                let p00 = self.pixel(2*x, 2*y);
                let p10 = self.pixel(2*x+1, 2*y);
                let p01 = self.pixel(2*x, 2*y+1);
                let p11 = self.pixel(2*x+1, 2*y+1);
                
                // Premultiplied alpha 转换
                let premul = |p: [u8; 4]| -> [u32; 4] {
                    let a = p[3] as u32;
                    // R, G, B 各乘以 alpha/255
                    [p[0] as u32 * a / 255,
                     p[1] as u32 * a / 255,
                     p[2] as u32 * a / 255,
                     a]
                };
                
                let ps = [premul(p00), premul(p10), premul(p01), premul(p11)];
                
                // 平均(注意 alpha 也平均)
                let sum_a: u32 = ps.iter().map(|p| p[3]).sum();
                let avg_a = sum_a / 4;
                
                let avg_premul: [u32; 3] = [
                    ps.iter().map(|p| p[0]).sum::<u32>() / 4,
                    ps.iter().map(|p| p[1]).sum::<u32>() / 4,
                    ps.iter().map(|p| p[2]).sum::<u32>() / 4,
                ];
                
                // Un-premultiply(从 premultiplied RGB 还原 straight RGB)
                let straight_rgb: [u8; 3] = if avg_a > 0 {
                    [
                        (avg_premul[0] * 255 / avg_a) as u8,
                        (avg_premul[1] * 255 / avg_a) as u8,
                        (avg_premul[2] * 255 / avg_a) as u8,
                    ]
                } else {
                    [0, 0, 0]
                };
                
                let i = ((y * new_w + x) * 4) as usize;
                out[i]   = straight_rgb[0];
                out[i+1] = straight_rgb[1];
                out[i+2] = straight_rgb[2];
                out[i+3] = avg_a as u8;
            }
        }
        
        RgbaImage { data: out, width: new_w, height: new_h }
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    
    #[test]
    fn test_semitransparent_red() {
        // 2x2:两个半透明红,两个完全透明
        let data = vec![
            255, 0, 0, 128,  0, 0, 0, 0,
            255, 0, 0, 128,  0, 0, 0, 0,
        ];
        let img = RgbaImage { data, width: 2, height: 2 };
        let small = img.box_downsample_2x();
        
        let p = small.pixel(0, 0);
        assert_eq!(p[0], 255); // 红色保留
        assert_eq!(p[3], 64);  // alpha = (128+0+128+0)/4 = 64
    }
    
    #[test]
    fn test_solid() {
        // 2x2 全是不透明红
        let data = vec![
            255, 0, 0, 255,  255, 0, 0, 255,
            255, 0, 0, 255,  255, 0, 0, 255,
        ];
        let img = RgbaImage { data, width: 2, height: 2 };
        let small = img.box_downsample_2x();
        
        let p = small.pixel(0, 0);
        assert_eq!(p, [255, 0, 0, 255]); // 完全不变
    }
}
```

**每行解释**:
- `pixel()` —— 把 (x, y) 转成线性索引 `i = (y * width + x) * 4`,返回 4 字节
- `premul` 闭包 —— 接受 [u8; 4] 返回 [u32; 4],把 RGB 乘以 alpha(避免溢出用 u32)
- `ps.iter().map(|p| p[3]).sum()` —— 函数式求和,Rust 风格
- `un-premultiply` —— `premul_rgb * 255 / alpha` 还原。alpha=0 时除零,用 if 保护

### Lv3 · 迁移设计

**题**:你的 2x 下采样只支持偶数尺寸。设计一个**任意倍数**下采样函数 `downsample(img, target_w, target_h)`,能处理 100×100 → 30×30 这种非整数倍。要求用"面积平均"算法——每个目标像素的值等于覆盖它的所有源像素的加权平均(权重 = 重叠面积)。

**提示**:
- 对每个目标像素 (tx, ty),计算它在源图的覆盖区域 `[(tx * src_w / target_w, ty * src_h / target_h), ((tx+1) * src_w / target_w, (ty+1) * src_h / target_h)]`
- 遍历覆盖区域内的所有源像素,部分覆盖的按面积加权
- 浮点运算,精度 f32 或 f64
- 思考:如何避免内层循环(否则 1024×1024 下采样到 33×33 要遍历 33*33*1024*1024 像素)

use image::{GenericImageView, imageops::FilterType};

fn downsample_image(input: &str, output: &str, target_w: u32, target_h: u32) 
    -> Result<(), Box<dyn std::error::Error>> 
{
    let img = image::open(input)?;
    let (w, h) = img.dimensions();
    println!("Original: {}x{}", w, h);
    
    let dimensions = if w > target_w || h > target_h {
        println!("Downsampling to {}x{}", target_w, target_h);
        (target_w, target_h)
    } else {
        println!("No downsampling needed");
        (w, h)
    };
    
    let small = img.resize_exact(dimensions.0, dimensions.1, FilterType::Lanczos3);
    small.save(output)?;
    println!("Saved: {}", output);
    Ok(())
}

### Troubleshooting

- **下采样后边缘出现黑色 fringe** —— 没用 premultiplied alpha。重写,premul 后平均再 unpremul
- **pixel art 下采样后变模糊** —— 用 Nearest 而不是 Box / Lanczos
- **性能慢** —— 检查 release build(`cargo build --release`),debug 模式慢 50 倍
- **半透明像素颜色偏暗** —— un-premultiply 时 alpha 误差累积。考虑用 f32 计算而非 u32
