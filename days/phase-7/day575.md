## 2 · 心智模型

### 2.1 类比:网页开发的 "live reload"

前端开发有 "live reload"——你改 .css / .js,浏览器自动刷新。这把"改代码 → 切到浏览器 → 刷新"循环从几秒变成"眨眼"。Webpack Dev Server、Vite、Parcel 都内置这个——文件保存的瞬间,浏览器自动刷新或 hot module replacement(HMR)只替换改动的模块,保留状态。

游戏开发的 hot reload 类似——改游戏代码或 asset,游戏立刻反映。开发节奏 10 倍快。**但比 web 更难**:游戏有 GPU state(pipeline、texture、buffer),替换 GPU state 需要"等待 GPU 用完老资源"——GPU 命令是异步的,你不能在 CPU 端立刻销毁老 texture,GPU 可能还在渲染它。需要 frame fencing 和延迟销毁(deferred destruction)。

Casey 这天把"只热重载代码"扩展到"热重载一切",实现完整 hot reload 体验。这是工业游戏开发标配——Unreal、Unity、Godot 都有,但实现细节不同。Casey 的实现简洁,直接用 inotify + state machine,适合学习。

### 2.2 严谨展开:Linux inotify 的工作原理

Linux 用 inotify(inode notify)监控文件变化。让我把这个机制彻底展开,你会看到它是"零开销、实时"的精妙设计。

**传统轮询(inefficient)**:每秒 `stat()` 所有文件,比较 mtime。代价:O(N) stat 调用,CPU 浪费。10 万文件每秒轮询 = 10 万次 syscall。

**inotify(event-driven)**:进程注册"我想监控这个目录"到内核。内核在 inode 操作(VFS write/close)时检查"这个 inode 有 watch 吗",如果有就把事件放入内核 queue。进程 `read()` 这个 queue——和 socket recv 一样,**阻塞直到事件来**。代价:O(1) per event,空闲时 0 CPU。

```rust
use inotify::{Inotify, EventMask, WatchMask};

let mut inotify = Inotify::init()?;  // 创建 inotify fd
let watch_handle = inotify.watches().add(
    "assets/textures/",
    WatchMask::MODIFY | WatchMask::CLOSE_WRITE | WatchMask::CREATE,
)?;

let mut buffer = [0u8; 4096];
loop {
    let events = inotify.read_events_blocking(&mut buffer)?;
    for event in events {
        if event.mask.contains(EventMask::CLOSE_WRITE) {
            println!("File changed: {:?}", event.name);
            // 触发 reload
            reload_asset(&event.name.unwrap());
        }
    }
}
```

关键 WatchMask 选项:
- `MODIFY`:文件被写入(write syscall 触发)。**但很多编辑器先写临时文件再 rename**,所以单看 MODIFY 不够
- `CLOSE_WRITE`:文件以写模式打开后**关闭**——这才是"保存完成"的信号
- `CREATE`:新文件创建。**但 rename 到目标路径也是 CREATE**(覆盖)
- `MOVE`:重命名(包括 atomic save 的临时文件 rename)

**编辑器的 atomic save 陷阱**:Vim、Emacs、VS Code 默认做 atomic save——写 `.file.txt.swap`,然后 `rename` 替换原文件。这种情况下 `MODIFY` 永远不触发(原文件没被写),只触发 `MOVE_SELF` 或 `CREATE`(新文件)。**正确做法**是监控目录而非文件,处理所有事件类型。

inotify 限制:每个 watch 占内核内存(约 1 KB),默认 8192 个 watch(8 MB 内存)。大项目要 `cat /proc/sys/fs/inotify/max_user_watches` 调高。Docker、JetBrains IDE 都会撞到这个限制。

### 2.3 Asset reload 状态机

每个 asset 有状态。**为什么用状态机**?因为文件变化是异步的——reload 不能立即在 inotify callback 里做(callback 在 inotify 线程,不能访问游戏 state)。状态机让游戏主循环每帧检查"哪些 asset 需要重新加载",在自己的线程上下文里做。

```rust
enum AssetState {
    Unloaded,
    Loaded(AssetData),
    Outdated,  // 文件变了,需要 reload
    Reloading, // 正在重新加载(异步)
}

struct Asset {
    path: PathBuf,
    state: AssetState,
    last_mtime: SystemTime,
}

impl Asset {
    fn check_reload(&mut self) {
        let mtime = std::fs::metadata(&self.path).unwrap().modified().unwrap();
        if mtime != self.last_mtime {
            self.state = AssetState::Outdated;
            self.last_mtime = mtime;
        }
    }

    fn reload(&mut self) {
        if let AssetState::Outdated = self.state {
            let data = load_asset(&self.path);
            self.state = AssetState::Loaded(data);
        }
    }
}
```

每帧 `check_reload` 所有 asset,如果 outdated,异步 reload(可能用 `rayon` 并行加载)。**异步的原因**:PNG 解码、JSON parse 可能耗时几十 ms,如果同步做会卡帧。用 `tokio::spawn` 或 `rayon::spawn` 后台加载,加载完后通知主线程替换 `AssetState::Loaded(new_data)`。

### 2.4 Shader reload:GPU pipeline 的微妙之处

Shader reload 比较麻烦——**GPU pipeline state 不能直接替换**。GPU pipeline 包含 shader module + vertex layout + blend state + depth state,这是个 immutable 对象,创建后不能改。必须**创建新 pipeline,然后替换指针**。

```rust
struct Shader {
    source_path: PathBuf,
    pipeline: Option<wgpu::RenderPipeline>,
    pending_pipeline: Option<wgpu::RenderPipeline>,  // 新 pipeline,等下帧用
}

impl Shader {
    fn reload(&mut self, device: &wgpu::Device) {
        // 读新源码
        let source = std::fs::read_to_string(&self.source_path).unwrap();
        let module = device.create_shader_module(wgpu::ShaderModuleDescriptor {
            source: wgpu::ShaderSource::Wgsl(source.into()),
            label: None,
        });
        // 重建 pipeline
        let new_pipeline = device.create_render_pipeline(&wgpu::RenderPipelineDescriptor {
            vertex: wgpu::VertexState {
                module: &module,
                entry_point: "vs_main",
                buffers: &[],
            },
            // ...
            label: None,
        });
        // 不立即替换 self.pipeline——可能 GPU 正在用它
        self.pending_pipeline = Some(new_pipeline);
    }

    fn swap(&mut self) {
        // 每帧调用,GPU 空闲后才 swap
        if let Some(p) = self.pending_pipeline.take() {
            self.pipeline = Some(p);
        }
    }
}
```

**延迟销毁(deferred destruction)**:老 pipeline 不能立即 drop,GPU 可能在用它渲染上一帧。wgpu 的设计是"GC when GPU done"——`wgpu::RenderPipeline` 内部是 Arc,只要没引用就 drop。但你必须**确保自己没有 stale 引用**——如果有变量持有老 pipeline 的 Arc,它不会销毁。

更精细:用 `wgpu::Device::poll(Maintain::Wait)` 强制 GPU flush,然后销毁。但 poll 是阻塞的,不利于 hot reload 的"立刻反映"。**最佳实践**:用 frame counter,等 2-3 帧后再销毁老 pipeline——确保 GPU 已经把所有用老 pipeline 的帧渲染完。

**Shader 编译错误处理**:如果新 shader 编译失败(wgsl 语法错误),wgpu 的 `create_shader_module` 会 panic 或返回 Error。**正确做法**是 catch error,保持老 pipeline 不变,打印错误到日志。开发者修语法错误保存,再次触发 reload。**这就是为什么 shader hot reload 比代码 hot reload 难**——代码错误链接器报错,shader 错误 GPU 编译器报错,而且 GPU 状态难回滚。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

Hot reload 在游戏开发必备,各大引擎都做了大量工作:

- **Unreal Engine**:Hot reload(通过 DLL)+ Live coding。UE 的 Live Coding 是 C++ hot reload——你改 .cpp 文件,UE 自动编译这个文件,链接到 .dll,然后用 Windows DLL reload 机制替换。**问题**:UE class 的反射系统(UClass)需要更新——新增 UPROPERTY / UFUNCTION 不能简单 reload,因为 UClass 内存布局变了。所以 UE Live Coding 只支持"函数体修改",不支持"加新成员"。
- **Unity**:Hot reload 用 Mono C# 的 JIT——任何 C# 改动立刻生效,因为 C# 是托管代码。但 Unity 的"序列化字段"(public 字段或 [SerializeField])改变会破坏 Inspector 状态——Unity 用"字段 ID"维持状态,改名/改类型会丢失引用。
- **Godot**:GDScript 是解释执行,任何 .gd 改动立刻 reload。但 C# binding 需要重新编译。
- **Bevy**:Rust + ECS,Bevy 提供 `bevy_ecs_dynamic` 和第三方 `bevy_hotreload`——但 Rust 没原生 hot reload,必须用 cdylib + libloading,复杂。

**Game engine asset hot reload 的挑战**:
- **依赖追踪**:一个 material 用了 texture A、B、C。texture A 改了,要 reload material 吗?如果 material 缓存了 texture handle,需要 invalidate 缓存
- **GPU resource 生命周期**:GPU texture 不能立即销毁,可能 GPU 在用。延迟销毁(deferred destruction)
- **状态保留**:reload shader 后,游戏状态(玩家位置、当前关卡)要保留——不能 reload 就重新开始关卡
- **类型安全**:Rust 项目里,asset 类型(JSON 转 struct)改变后,老 asset 文件可能不兼容。需要版本号 + migration

### 3.2 · 🎨 图形学视角

Shader hot reload 的 GPU 工程复杂度:

- **Pipeline state**:GPU state 不能原子替换,要等当前帧完成
- **Bind group**:变了 shader,binding 可能不兼容——老 binding 用了 uniform buffer 0,新 shader 改成了 texture,bind group 类型变了
- **Specialization constants**:WGSL 的 const 改变要重 compile
- **Pipeline layout**:如果新 shader 改了 uniform 结构,pipeline layout 变了,**所有依赖的 bind group 都要重建**
- **Root signature**(DX12)/ **Pipeline layout**(Vulkan):低层 GPU API 把 layout 抽象成显式对象,改 layout 是大手术

解决:用 double-buffering shader——老 pipeline 用到完,新 pipeline 替换。**更深入的工业实践**:

**Pipeline cache**:GPU driver 缓存 shader 编译结果到磁盘(`.pso` 文件)。第二次启动时,从缓存加载 shader,跳过编译。NVIDIA 的 `GL_SHADER_BINARY`、Vulkan 的 `VK_PIPELINE_CACHE`、wgpu 的 `wgpu::PipelineCache` 都是这套。

**Shader permutation**:大游戏一个 shader 有几百个变体(不同材质、不同光照模式)。预编译所有变体时间长,工业做法是**按需编译 + 缓存**——第一次遇到某变体编译,后续从缓存加载。Cyberpunk 2077 有 5 万 shader 变体,首次启动编译 30 分钟(预编译),后续从磁盘缓存秒加载。

**Async shader compilation**:shader 编译异步进行,GPU 先用"fallback pipeline"(简单 shader),编译完后 swap。这样不会卡帧。DirectX 12 的 `ID3D12Device::CreatePipelineState` 异步版本支持这个。

### 3.3 · 🐧 Linux 系统编程视角

inotify 是 Linux 标准,但跨平台要小心。让我对比四大 OS 的文件监控 API:

- **Linux**:`inotify_init1` + `inotify_add_watch` + `read`(从 `/proc/sys/fs/inotify/max_user_watches` 看默认 8192 个 watch,大项目要调到 524288)
- **macOS**:FSEvents——比 inotify 更宽松(监控整个 volume),但事件粒度粗。在 Apple Silicon 上性能好
- **Windows**:`ReadDirectoryChangesW`——回调式,需要 IOCP 或 overlapped I/O 处理高并发
- **BSD/kqueue**:`kqueue` + `EVFILT_VNODE`——BSD 原生,但 Linux 没有

**`notify` crate** 包装所有平台,API 统一:

```rust
use notify::{Watcher, RecursiveMode, watcher};

let (tx, rx) = std::sync::mpsc::channel();
let mut watcher = watcher(tx, std::time::Duration::from_secs(1)).unwrap();
watcher.watch("assets/", RecursiveMode::Recursive).unwrap();

for event in rx {
    println!("{:?}", event);
}
```

跨平台 hot reload 用 notify 简单。**但 notify 5.x 用 ` RecommendedWatcher`(基于 inotify/FSEvents),需要不同 backend 时切换——比 4.x 的 polling-watcher 兼容性好但 API 复杂**。

**`inotify` 在容器里的特殊问题**:Docker bind-mount 文件,某些 inotify 事件不触发(因为 overlayfs 的 copy-up 机制)。**解决**:在 host 上 inotify,把变化通过 IPC 通知容器。Kubernetes + Skaffold 用这套做容器 hot reload。

**Linux 系统调用细节**:`inotify_init1(IN_NONBLOCK)` 创建非阻塞 inotify fd,可以 `poll()`/`epoll` 等多路复用。Rust 的 `mio` crate(Mio,I/O 事件循环)支持 inotify——Tokio 异步运行时基于 mio。**所以 Tokio 项目可以直接 await inotify 事件**:

```rust
use tokio::stream::StreamExt;
use inotify::Inotify;

let mut inotify = Inotify::init()?;
inotify.watches().add("assets/", WatchMask::MODIFY)?;
let mut stream = inotify.event_stream([0u8; 4096]);
while let Some(event) = stream.next().await {
    println!("Changed: {:?}", event);
}
```

### 3.4 · 🦀 Rust 生态视角

Rust 的 hot reload 工具生态:

- **cargo-watch**:监控 src/ 变化,自动 cargo build / test。**最常用**,每个 Rust 开发者必备
- **hot-lib-reloader**:Rust crate,运行时 reload cdylib。**原理**:把游戏代码编译成 `.so`(cdylib),主程序用 `libloading` 加载,文件变了就 unload + reload。**限制**:不能 reload 全局状态(static 变量会重置),不能 reload 改了 struct layout 的代码
- **rust-script**:脚本式跑 Rust——`#!/usr/bin/env rust-script` shebang。每次改代码重新编译,适合小工具
- **bacon**:Rust 的 `cargo-watch` 升级版,有 TUI 显示编译错误。比 cargo-watch 体验好

`cargo-watch` 开发必备:

```bash
cargo install cargo-watch
cargo watch -x run  # src/ 变,自动 cargo run
cargo watch -x "test -- --nocapture"  # 自动跑测试
cargo watch -w src/ -x run  # 只监控 src/,忽略 tests/
```

**Rust hot reload 的根本挑战**:Rust 是 AOT 编译语言,不像 Python/JS 可以 JIT。Rust 的 cdylib 方案需要把代码分成"主程序"(不 reload)+ "动态库"(reload)两部分,代码组织受限。而且 Rust 的 trait / generic 在 cdylib 边界处受限——dyn trait 是 OK 的,泛型不行(monomorphization 在编译时展开)。

**Bevy 项目的 hot reload**:`bevy_mod_debugdump` 显示 ECS 系统 DAG,`bevy_editor_pls` 提供编辑器 UI。Hot reload 用 `bevy_dynamic_bundle` 实验性 crate——可以 reload resource 和 component,但 system 函数仍需手动 reload。

**Rust 的 `linkme` crate**:编译时收集分布式数据(用 ELF section),不需要 runtime registration。和 hot reload 冲突——relink 后 section 内容变了,但已加载的代码不知道。**避免在 hot reload 项目用 linkme**。
- **Unity**:domain reload + script recompile
- **Godot**:editor script reload
- **Dear ImGui**:UI live edit

工业游戏都把 hot reload 当 first-class citizen。开发体验直接决定生产力。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 shader hot reload 比 code hot reload 复杂?

**参考解答**:Code hot reload 是替换函数指针——简单。Shader hot reload 要重建 GPU pipeline state——pipeline 是不可变的(创建后不能改),要创建新 pipeline 替换旧。但旧 pipeline 可能正在被当前帧用,不能立刻 drop——要等帧结束。所以 shader hot reload 用 double-buffer:新 pipeline 准备好,等帧结束 swap。代码 hot reload 没这问题(代码可以原子替换)。

### Lv2 · 动手实践

**题**:用 notify crate 监控目录,实现 asset reload。

要求:
- 创建 /tmp/test_assets/ 目录
- 写一个文件 foo.txt
- 用 notify 监控
- 改 foo.txt 内容
- 验证 watcher 收到事件

**参考解答**:

```rust
// Cargo.toml: notify = "6"

use notify::{Watcher, RecursiveMode, EventKind, Config};
use std::sync::mpsc::channel;
use std::time::Duration;

fn main() {
    std::fs::create_dir_all("/tmp/test_assets").ok();
    std::fs::write("/tmp/test_assets/foo.txt", "initial content").unwrap();

    let (tx, rx) = channel();
    let mut watcher = notify::recommended_watcher(|res: Result<notify::Event, _>| {
        if let Ok(event) = res {
            tx.send(event).unwrap();
        }
    }).unwrap();

    watcher.watch(std::path::Path::new("/tmp/test_assets"), RecursiveMode::Recursive).unwrap();

    println!("Watching /tmp/test_assets/. Modify foo.txt to test.");
    println!("Press Ctrl+C to stop.\n");

    // 子线程:5 秒后修改文件
    std::thread::spawn(|| {
        std::thread::sleep(Duration::from_secs(2));
        std::fs::write("/tmp/test_assets/foo.txt", "modified content").unwrap();
        println!("[thread] Modified foo.txt");
    });

    for event in rx {
        match event.kind {
            EventKind::Modify(_) | EventKind::Create(_) | EventKind::Access(_) => {
                println!("Event: {:?} paths={:?}", event.kind, event.paths);
            }
            _ => {}
        }
    }
}
```

## 8 · Rust / Arch 落地代码

完整 hot reload 系统:

```rust
use std::collections::HashMap;
use std::path::{Path, PathBuf};
use std::time::SystemTime;

// Asset 类型
#[derive(Clone, Copy, PartialEq)]
enum AssetKind {
    Texture,
    Shader,
    Json,
    Mesh,
}

struct Asset {
    path: PathBuf,
    kind: AssetKind,
    last_mtime: SystemTime,
    // 实际还有 data / GPU handle,简化
}

struct AssetManager {
    assets: HashMap<PathBuf, Asset>,
    watch_dir: PathBuf,
}

impl AssetManager {
    fn new(watch_dir: &Path) -> Self {
        AssetManager {
            assets: HashMap::new(),
            watch_dir: watch_dir.to_path_buf(),
        }
    }

    fn register(&mut self, path: &Path, kind: AssetKind) {
        let mtime = std::fs::metadata(path)
            .and_then(|m| m.modified())
            .unwrap_or(SystemTime::UNIX_EPOCH);
        self.assets.insert(path.to_path_buf(), Asset {
            path: path.to_path_buf(),
            kind,
            last_mtime: mtime,
        });
    }

    fn check_reloads(&mut self) -> Vec<PathBuf> {
        let mut reloaded = Vec::new();
        for asset in self.assets.values_mut() {
            let current_mtime = std::fs::metadata(&asset.path)
                .and_then(|m| m.modified())
                .unwrap_or(SystemTime::UNIX_EPOCH);
            if current_mtime != asset.last_mtime {
                println!("[reload] {:?} (kind={:?})", asset.path, asset.kind);
                asset.last_mtime = current_mtime;
                reloaded.push(asset.path.clone());
                // 实际:根据 kind 调不同 reload 函数
                //   Texture → 重新 decode + update GPU texture
                //   Shader → 重新 compile + 重建 pipeline
                //   Json → 重新 parse + 更新 entity data
            }
        }
        reloaded
    }
}

// 简化版 inotify polling(实际用 notify crate 异步)
fn poll_files(manager: &mut AssetManager) {
    loop {
        let reloaded = manager.check_reloads();
        if !reloaded.is_empty() {
            println!("Reloaded {} assets", reloaded.len());
        }
        std::thread::sleep(std::time::Duration::from_millis(100));
    }
}

fn main() {
    // 演示用:创建临时 asset 目录
    let dir = std::env::temp_dir().join("handmade_hero_assets");
    std::fs::create_dir_all(&dir).unwrap();
    let tex_path = dir.join("texture.png");
    let shader_path = dir.join("shader.wgsl");
    let json_path = dir.join("level.json");

    std::fs::write(&tex_path, b"fake png").unwrap();
    std::fs::write(&shader_path, b"fake shader").unwrap();
    std::fs::write(&json_path, b"{}").unwrap();

    let mut manager = AssetManager::new(&dir);
    manager.register(&tex_path, AssetKind::Texture);
    manager.register(&shader_path, AssetKind::Shader);
    manager.register(&json_path, AssetKind::Json);

    println!("Asset manager watching {} files", manager.assets.len());

    // 模拟"另一线程"修改文件
    let tex_path_clone = tex_path.clone();
    let shader_path_clone = shader_path.clone();
    std::thread::spawn(move || {
        std::thread::sleep(std::time::Duration::from_millis(300));
        std::fs::write(&tex_path_clone, b"modified png content").ok();
        println!("[other thread] Modified texture");

        std::thread::sleep(std::time::Duration::from_millis(300));
        std::fs::write(&shader_path_clone, b"new shader code").ok();
        println!("[other thread] Modified shader");
    });

    // Poll 1 秒(模拟游戏主循环的 reload 检查)
    for _ in 0..10 {
        let reloaded = manager.check_reloads();
        if !reloaded.is_empty() {
            println!("Reloaded: {:?}", reloaded);
        }
        std::thread::sleep(std::time::Duration::from_millis(100));
    }

    // 清理
    let _ = std::fs::remove_dir_all(&dir);

    // === M8 总结 ===
    println!("\n=== M8 Milestone Summary ===");
    println!("Phase 7 (Day 436-575) - 140 days - complete:");
    println!();
    println!("  Day 436-440: Asset pipeline foundation (PNG, sampling)");
    println!("  Day 441-452: World generator (rooms, connections)");
    println!("  Day 453-462: Hand-written PNG decoder");
    println!("  Day 463-470: HHA asset format");
    println!("  Day 471-510: Asset loading & bitmap ops");
    println!("  Day 511-540: Editor UI (immediate mode, undo/redo)");
    println!("  Day 541-546: Memory viz & mipmap");
    println!("  Day 547-575: Light probe / Voxel GI (28 days)");
    println!();
    println!("  Final: light probes + editor + world generator");
    println!("  Hot reload generalized to all assets");
}
```
