# Day 474 · 移除暂态概念

> 重构像剥洋葱,Day 473 剥掉"屏幕坐标",Day 474 剥掉"transient state"——一个 Casey 早期为了图省事引入的中间概念。每次剥离都让代码更清晰,但也暴露下一个抽象债。

## 0 · 为什么要有这一天

你在前几百天写代码时,经常遇到一个场景:这一帧需要一块"临时内存",用完就扔。比如:

- 拼一个字符串(打印 debug 信息),拼完用一下就丢
- 临时存储一组 entity ID(碰撞检测结果),用完不需要
- 渲染时构造一个临时的 vertex buffer,渲染完丢

这些"临时"的内存,Casey 早期统一用一块叫 **transient memory** 的内存池管理。这块内存每帧开始时 reset 到 0,每帧结束自动释放——本质是个 arena。

听起来很合理,但用着用着 Casey 发现了问题:**transient 这个概念让代码"隐式"依赖内存生命周期**。一个函数拿 `transient_state` 引用,你不知道它 push 进去的内存活多久——可能活到帧末,可能活到下帧,取决于这个函数被谁调。代码读起来要看上下文才能确定。

Day 474 的目标:**移除 transient 概念,让所有内存生命周期显式**。

这件事的核心思想是 **"explicit over implicit"**——显式优于隐式。Rust 借用检查器就是这个思想的极致实现:每个引用的 lifetime 显式标注(或编译器推导),不能"隐式"假设引用活多久。Casey 用 C 没有 Rust 的工具,但他用结构设计达到了类似效果。

完成这一天之后,你具备了:

- 识别"隐式生命周期依赖"这种代码味道(code smell)
- 用显式参数替代隐式全局状态的能力
- 理解 Rust 所有权系统为什么这么设计——它就是强制你显式化

## 1 · Casey 今天做了什么

Casey 这一天的工作:

第一步,他列出所有 transient state 的使用点:大概 30 处。每处都是 `MemoryPool* trans = state->transient; ... push_something(trans, ...)`,依赖 `trans` 这块内存在帧末释放。

第二步,他识别出 transient 的两类用法:

- **真·临时**:这帧用完就丢(render group、临时字符串)
- **伪·临时**:其实需要跨帧(debug overlay 缓存、UI 状态)

第三步,他对每类做不同处理。真临时的改成"显式 arena 参数",caller 明确知道这块内存活到 arena 释放。伪临时的移到"持久状态"里,显式标注它跨帧。

第四步,他删除 `transient_state` 这个全局结构。所有原来的 caller 现在要么接受 arena 参数(显式),要么操作持久状态。

第五步,他验证游戏照常运行,但代码可读性大幅提升——每个内存生命周期都明确。

## 2 · 心智模型

### 类比:工具箱 vs 桌面

想象两种工作方式:

**方式 A(隐式 transient)**:你有一个"桌面",所有东西都往桌面扔。书、笔、文件、零食用同一个空间。你不知道这本书放多久——可能你今天看完收走,可能放一周。每件东西的生命周期没明说。

**方式 B(显式)**:你定义不同的空间——书架(长期)、笔筒(永久)、文件柜(按项目)、垃圾桶(短期)。每件东西放进对应空间,生命周期明确。

方式 B 看起来麻烦(你要思考"这放哪"),但实际更高效——你找东西时知道去哪找,不会在桌面翻遍所有杂物。

代码里的"transient memory"就是方式 A。它图省事,但实际让代码难懂、易出 bug。

### 为什么"显式优于隐式"

这个原则在编程里到处都是:

- **Python 之禅**:"Explicit is better than implicit"
- **Rust ownership**:每个值的所有者显式,生命周期显式
- **C++ RAII**:资源获取就是初始化,资源释放显式绑定到对象生命周期
- **函数参数 vs 全局变量**:函数参数显式,全局变量隐式(没人知道谁改了它)

为什么显式更好?

第一,**可读性**。读代码时不需要"跟踪上下文"就能知道数据从哪来、活多久。

第二,**可测试性**。函数参数可以 mock、可以传不同值测试。全局状态难 mock。

第三,**可重入性**。显式参数的函数可以多次调用,每次独立。全局状态的函数不可重入(多线程炸)。

第四,**可推理性**。编译器能帮你检查显式参数的正确性(类型、lifetime),但管不了全局状态。

Casey 的 transient state 是个"半全局"——它通过参数传递,但语义是"隐式临时"。Day 474 把它彻底显式化。

### Arena vs Pool:两种"批量分配"

Casey 的 transient 本质是个 **arena**(连续内存,frame 末整体 reset)。Arena 有几个特点:

- 分配超快(O(1),只移动指针)
- 释放超快(O(1),指针归零)
- **不能单个释放**(没有 free 单个对象)

这跟 **pool**(对象池)不同——pool 可以单个释放(放回池里),但分配慢一点(查 free list)。

Arena 适合"frame 级"的批量分配,pool 适合"对象级"的反复使用。Casey 用 arena 给 Render Group 分配 entry,用 pool 给 entity 分配。

Day 474 的改动不是改 arena 本身(它还是 arena),而是改"使用 arena 的代码风格"。之前是"隐式使用全局 transient arena",之后是"显式接受 arena 参数"。

### "作用域"的显式表达

显式化内存生命周期的一个常见模式是 **"作用域对象"**。Rust 的 `drop`、C++ 的 RAII、Python 的 `with` 都是这种模式——一个对象代表一个作用域,作用域结束自动清理。

```rust
// Rust 的 arena + 作用域
let bump = Bump::new();        // 创建 arena
let group = RenderGroup::new_in(&bump);   // group 借用 bump
group.push_bitmap(...);        // push 到 group
render(&group);                // 用 group
// 离开作用域,bump drop,group 自动失效
```

`group` 借用 `bump`,编译器保证 `group` 不会比 `bump` 活得久。这是 Rust 的"显式作用域"——通过类型系统强制。

Casey 用 C 没这个能力,但他通过 API 设计模拟——`RenderGroup` 创建时接受 arena 引用,arena 释放时 group 自动失效(语义上)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏引擎里的"frame memory"是标配。Unity 有 `ObjectPool<T>`,Unreal 有 `TArray` 的 arena 模式,Godot 有 `OS::get_singleton()->get_scratch_buffer()`。这些都是 transient memory 的工业化版本。

但工业引擎都把它们做成**显式 API**——你调 `ObjectPool<T>::acquire()` 拿一个对象,显式 `release()`。不存在"全局 transient"这种东西。

为什么工业代码严格?因为工业项目大,几十万行代码,隐式依赖会指数级放大复杂度。Casey 的 HH 是单人项目,几百行代码,他能 hold 住隐式依赖。但他的"重构到显式"反映了好习惯——即使小项目也用最佳实践。

游戏开发里另一个相关概念:**data-oriented design**(DOD)。DOD 强调"数据布局决定代码结构",反对"面向对象封装"。Casey 的 Render Group 是 DOD 的典范——entry 是数据,push 是数据生成,render 是数据消费。没有"对象"概念,只有数据流。

### 3.2 · 🎨 图形学视角

图形学里"transient resource"是个 GPU 概念。Vulkan 有 `VK_IMAGE_USAGE_TRANSIENT_ATTACHMENT_BIT`——一个 image 标记为 transient,意味着它只在 render pass 内有效,pass 结束 GPU 可以回收。

CPU 上的 transient memory 和 GPU 上的 transient image 是同一思想:**资源生命周期绑定到作用域,作用域结束自动回收**。Vulkan 把这个思想刻进 API,因为 GPU 资源昂贵(显存有限),必须严格管理。

Casey 在 Day 474 的 CPU 端做的是类似的事——把"资源生命周期"从隐式变成显式,方便未来加 GPU transient 资源。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里有大量"transient memory"的例子:

- **slab allocator**:为内核对象池设计,分配/释放超快
- **per-CPU buffer**:每个 CPU 一块 scratch 内存,内核代码临时用
- **scratch page**:DMA 操作的临时页

这些都用显式 API:`kmalloc(size, GFP_KERNEL)`、`free_pages(addr, order)`,没有"隐式 transient"。

Linux 内核的代码纪律比用户态严得多——任何"隐式全局"都被视为 bug。因为内核 bug 会 panic 整个系统,代价巨大。Casey 在 HH 里走内核风格,反映他对工程严谨的追求。

Linux 用户态有个工具叫 `scratchpad`(`mmap(MAP_ANONYMOUS | MAPScratchpad)`),专门给"frame memory"用。但这不是标准 API,实际工程用 `jemalloc` 或 `tcmalloc` 的小对象缓存替代。

### 3.4 · 🦀 Rust 生态视角

Rust 里"transient memory"的最佳实现是 `bumpalo` crate。它是个 arena allocator,API 显式:

```rust
use bumpalo::Bump;
use bumpalo::collections::Vec;

let bump = Bump::new();
let mut v: Vec<i32> = Vec::new_in(&bump);   // v 借用 bump
v.push(1);
v.push(2);
// v 离开作用域,但 bump 还活着
// 除非显式 v.into_iter() 或 bump.reset(),v 的内存不释放
```

`v` 的生命周期绑定到 `bump`,这是显式的——你看代码就知道 v 活多久。

Rust 的所有权系统强制你思考生命周期。Casey 用 C 没有 Rust 工具,但他通过 discipline 达到同样效果。这就是为什么 Rust 学习曲线陡——它强制你"显式思考",不让你"图省事"。

工业 Rust 项目几乎不用"全局 transient",而是显式传 arena 参数。`bevy_ecs`、`rend3`、`wgpu` 都是这种风格。

## 5 · 对照与变奏

Casey 在 Day 474 的"移除 transient"思想在不同领域有不同对应:

**编译器**:GCC 早期用 GTY(垃圾回收标记)管理 AST 节点,后来改成显式 arena(ggc-alloc)。原因一样——显式 > 隐式。

**数据库**:PostgreSQL 用 memory context——每个 query 有独立的 memory context,query 结束整个 context 释放。这是显式 arena,不是全局 transient。

**Java**:JVM 的 GC 是隐式内存管理,反过来——Java 程序员不需要思考生命周期。但代价是 GC 暂停、内存压力。现代 Java 引入了 `Arena` API(JEP 442),让程序员可选地用显式 arena——是向 Rust/C++ 学习的体现。

**Web 浏览器**:Chrome 的 V8 用 handle scope——一段代码内的所有 handle 自动释放。这是个"作用域 transient"的合理使用,因为 API 设计良好(进入/退出作用域显式)。

理解"显式 vs 隐式"的取舍是工程师的核心素养。原则:**默认显式,只在 API 设计良好且性能关键时用隐式**。

另一个对照:**Rust 的 unsafe**。Rust 允许 unsafe 块跳过检查,这是"显式的隐式"——你明确说"这块我知道在干啥,别管"。这比 C 的"全隐式"安全得多。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:Casey 为什么不直接用 C 的 `malloc`/`free`,而是要折腾 arena?

**参考解答**:三个理由:

第一,**性能**。malloc/free 每次调用走 libc,有锁、有内部碎片、有 size class 查找。每帧几千次分配,malloc 直接拖垮帧率。Arena 是 O(1) 指针移动,快几十倍。

第二,**碎片**。malloc/free 反复用会内存碎片化——大块申请失败,即使空闲内存总和够。Arena 是连续内存,无碎片。

第三,**生命周期管理**。malloc 的对象必须显式 free,漏 free 就泄漏。Arena 的对象整体 reset,不会泄漏——所有 frame 内的临时对象一次性释放。

Casey 还是有 malloc 用法,但只用在"启动时一次性分配,程序结束释放"的长期对象(纹理、模型)。frame 级临时对象全走 arena。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:写一段"显式 arena"的 Rust 代码。模拟一个游戏帧:`frame_render(state: &GameState, arena: &Bump)`,在 arena 上分配 Render Group,push 一些 entry,渲染,函数返回后 arena 由 caller 决定何时 reset。展示:即使函数返回,group 也不会被"自动"释放,因为 arena 还活着。

完成标准:`cargo run`,输出能看到 group 创建后内容、渲染调用、然后 group 仍可访问(因为 arena 没释放)。

**参考解答**:

```rust
use bumpalo::Bump;
use bumpalo::collections::String as BumpString;

// 假装的 GameState
struct GameState {
    frame_count: u32,
}

// Entry 类型
#[derive(Debug)]
enum Entry {
    Bitmap { id: u32, x: f32, y: f32 },
    DebugText { text: BumpString<'_> },   // 注意 lifetime
}

// Render Group 借用 arena
struct RenderGroup<'a> {
    entries: Vec<&'a Entry>,     // entry 也存在 arena 上
}

impl<'a> RenderGroup<'a> {
    fn new_in(arena: &'a Bump) -> Self {
        Self { entries: Vec::new_in(arena) }   // 假装有 new_in
    }
}

// 简化版:不用 bumpalo 的 Vec,直接 Vec<&Entry>
fn frame_render<'a>(state: &GameState, arena: &'a Bump) -> Vec<&'a Entry> {
    let mut entries: Vec<&'a Entry> = Vec::new();
    
    // 在 arena 上分配 entry
    let bitmap = arena.alloc(Entry::Bitmap { id: 1, x: 0.0, y: 0.0 });
    entries.push(bitmap);
    
    // 调试文本
    let mut text = BumpString::new_in(arena);
    text.push_str("Frame ");
    text.push_str(&state.frame_count.to_string());
    let text_entry = arena.alloc(Entry::DebugText { text });
    entries.push(text_entry);
    
    // 渲染
    for e in &entries {
        println!("render: {:?}", e);
    }
    
    entries   // 返回,caller 持有引用
}

fn main() {
    let state = GameState { frame_count: 42 };
    let arena = Bump::new();
    
    // 帧 1
    let entries = frame_render(&state, &arena);
    
    // arena 还活着,entries 还能访问
    println!("After frame, {} entries still accessible:", entries.len());
    for e in &entries {
        println!("  {:?}", e);
    }
    
    // 显式 reset
    arena.reset();
    // 现在 entries 引用悬空,但 Rust 编译器不让我们用——
    // entries 还活着但 arena 已 reset,理论上 UB
    // 实际 bumpalo 的 reset 要求 arena 没有借用,所以编译器阻止
    
    println!("Arena reset");
}
```

为什么这么写:`arena.alloc(...)` 返回 `&'a T`,lifetime 绑定 arena。这是 Rust 表达"显式生命周期"的方式。编译器保证借用规则:`entries` 不能比 `arena` 活得久。

注意一个细节:`bumpalo` 的 `Bump::reset()` 要求 `&mut self`,所以如果你有 `&arena` 借用,无法 reset。这就是 Rust 的"显式安全"——你不能在借用期间释放底层内存。

## 8 · Rust / Arch 落地代码

下面是一段完整的"显式 arena" Rust 代码,展示 Day 474 的核心改动。

```rust
use bumpalo::{Bump, alloc::Alloc};
use bumpalo::collections::Vec as BumpVec;

// ========================================
// 旧设计(隐式 transient,Day 474 之前)
// ========================================
mod old_design {
    // 一个全局 transient state,所有"临时"内存都从这里分配
    // 问题:用户不知道这块内存活多久
    pub struct TransientState {
        buffer: Vec<u8>,
        offset: usize,
    }
    
    impl TransientState {
        pub fn alloc(&mut self, size: usize) -> &mut [u8] {
            let start = self.offset;
            self.offset += size;
            &mut self.buffer[start..self.offset]
        }
    }
    
    // 函数签名只说"用 transient",不说活多久
    pub fn do_something(transient: &mut TransientState) -> &mut [u8] {
        transient.alloc(64)
    }
}

// ========================================
// 新设计(显式 arena,Day 474)
// ========================================
mod new_design {
    use bumpalo::Bump;
    
    // GameState 持有持久的 arena(整个游戏期间)
    pub struct GameState {
        pub frame_arena: Bump,           // 每帧重置
        pub persistent_arena: Bump,      // 长期持有
    }
    
    impl GameState {
        pub fn new() -> Self {
            Self {
                frame_arena: Bump::new(),
                persistent_arena: Bump::new(),
            }
        }
        
        pub fn end_frame(&mut self) {
            self.frame_arena.reset();    // 显式 reset
        }
    }
    
    // 函数签名明确借用哪个 arena
    // 'a 是 Rust 的 lifetime 参数,编译器推导
    pub fn render_frame<'a>(
        state: &GameState,
        frame_arena: &'a Bump,           // 显式传 arena
    ) -> &'a [u8] {
        // 在 frame_arena 上分配,生命周期明确到帧末
        let buf: &mut [u8] = frame_arena.alloc_slice_fill_default(64);
        // ... 渲染逻辑
        buf
    }
    
    // 持久数据用 persistent_arena
    pub fn cache_data<'a>(
        state: &GameState,
        persistent_arena: &'a Bump,
    ) -> &'a [u8] {
        persistent_arena.alloc_slice_fill_default(1024)
    }
}

// ========================================
// 演示
// ========================================
use new_design::GameState;

fn main() {
    let mut state = GameState::new();
    
    // 帧 1
    {
        let frame_data = new_design::render_frame(&state, &state.frame_arena);
        println!("Frame 1: got {} bytes", frame_data.len());
        // frame_data 借用 frame_arena
    }
    // frame_data 离开作用域,借用归还
    
    state.end_frame();   // 现在 frame_arena 可以 reset
    
    // 帧 2
    {
        let frame_data = new_design::render_frame(&state, &state.frame_arena);
        println!("Frame 2: got {} bytes", frame_data.len());
    }
    state.end_frame();
    
    // 持久数据
    let cached = new_design::cache_data(&state, &state.persistent_arena);
    println!("Cached: {} bytes (persists across frames)", cached.len());
    // 注意:不调 end_frame,cached 跨帧有效
}

// ========================================
// 性能对比
// ========================================
mod bench {
    use std::time::Instant;
    
    pub fn bench_malloc_vs_arena() {
        let n = 100_000;
        
        // malloc 路径
        let start = Instant::now();
        let mut vec: Vec<Vec<u8>> = Vec::with_capacity(n);
        for _ in 0..n {
            vec.push(vec![0u8; 64]);
        }
        drop(vec);
        let malloc_time = start.elapsed();
        
        // arena 路径
        let bump = bumpalo::Bump::new();
        let start = Instant::now();
        for _ in 0..n {
            bump.alloc_slice_fill_default::<u8>(64);
        }
        bump.reset();
        let arena_time = start.elapsed();
        
        println!("malloc: {:?}", malloc_time);
        println!("arena:  {:?}", arena_time);
        println!("speedup: {:.1}x", 
                 malloc_time.as_secs_f64() / arena_time.as_secs_f64());
    }
}
```

出错怎么办:

- **`error: cannot borrow state.frame_arena as mutable`** —— 你在同一作用域里既借用 frame_arena 又想调 `state.end_frame()`(后者要 `&mut state`)。解决:让借用先离开作用域(`drop(frame_data)` 或者用 block scope)。
- **`alloc_slice_fill_default not found`** —— bumpalo 版本不对。检查 `Cargo.lock`,升级到 3.13+。
- **arena 内存增长** —— 你忘了 reset。检查每个帧函数末尾是否调 end_frame。

## 10 · 复习要点

读完这一天你应该能用 30 秒回答以下问题:

**Q1**:为什么"显式优于隐式"是工程原则?
> 显式代码可读、可测试、可重入、可推理性都更强。隐式依赖让代码难懂、难调试、难并发。

**Q2**:Arena allocator 和 pool 有什么区别?
> Arena 分配 O(1)、释放 O(1) 整体 reset,不能单个释放。Pool 可以单个释放,但分配慢。Arena 适合 frame 级批量,pool 适合对象级反复使用。

**Q3**:transient state 的本质问题是什么?
> 它让内存生命周期"隐式"——一个函数拿 transient 引用,你不知道它 push 的内存活多久。Day 474 把它显式化(arena 参数)。

**Q4**:Rust 怎么用类型系统强制显式生命周期?
> 通过 lifetime parameter (`'a`) 和借用检查器。`fn foo<'a>(x: &'a T) -> &'a U` 明确返回值的生命周期绑定输入。

**Q5**:为什么工业 Rust 项目几乎不用"全局 transient"?
> 显式传 arena 参数让代码可读、可测试、可并发。bevy_ecs、rend3、wgpu 都用显式 arena。

如果你能流畅回答这五个问题,说明 Day 474 的核心你已经内化。下一日 Day 475 抽象渲染器接口。

**Q6**:为什么 Rust 强制 lifetime 标注,而 C 不强制?
> Rust 用类型系统在编译期保证内存安全。Lifetime 是类型系统的一部分,让编译器验证引用不悬空。C 没有这种类型系统,程序员手动管理,bug 多。

**Q7**:Drop trait 怎么实现"显式作用域"?
> Drop trait 在对象离开作用域时自动调用。Rust 的 `let x = ...;` 当 x 离开作用域时 drop 自动执行,释放资源。这是 RAII 模式——资源获取即初始化,资源释放即析构。

**Q8**:工业级 Rust 项目用什么 arena?
> `bumpalo`(最流行)、`typed-arena`(类型化 arena)、`id-arena`(带 ID 引用)、`generational_arena`(代际 arena,允许重用 slot)。每个有不同的语义取舍。

如果你能流畅回答这八个问题,Day 474 的核心你已经吃透。

**Rust 的 std::arena**(`std::arena` 实验性):Rust 标准库曾尝试加 arena,但后来移除。现在用第三方 crate。
