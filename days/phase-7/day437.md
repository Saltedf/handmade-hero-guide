# Day 437 · 切换到预计算半球分布

> 昨天 Casey 写了一段漂亮的螺旋分布生成代码;今天他把它"打碎"——不再每帧算,而是开机算一次,从此当作常量使用。这一步看似微小,却埋下了"GPU 数据上传"和"const 数组生命周期"两个工业级问题的伏笔。

## 0 · 为什么要有这一天

你在 Day 436 写出的 `spiral_point` 函数,如果每帧调用 64 次来生成采样方向,在 60 FPS 下就是每秒 3840 次 `acos/sin/cos` 调用——听起来不多,但你要明白:**这些数字每帧完全一样**。每一帧 N=64 个螺旋方向,因为 N 不变,输出不变。这意味着你在做无用功。

更糟的是,你后面要把这些方向传到 GPU 做 shader 计算。如果每帧重新算、重新上传到 GPU,你就在 60 次/秒地往 PCIe 总线灌完全相同的 768 字节。GPU 内存带宽再大,这种事也是浪费,而且**会和真正的动态数据(模型变换、相机参数)抢带宽**。

工程上有一个简单原则:**不变的数据,计算一次,缓存起来**。今天 Casey 把这个原则应用到球面采样:开机时一次性算好 N 个方向,塞进一个静态数组,从此当作只读常量。这听起来很无聊——它确实无聊——但它引出三个非平凡的话题:

第一,**半球 vs 球面**。Casey 不再算完整球面,只算上半球(N 朝向),因为光照计算是在表面法线周围的半球做积分。
第二,**GPU 上传策略**:预计算数组怎么从 CPU 内存进到 GPU uniform buffer?
第三,**const fn vs 静态初始化**:Rust 表达"编译期常量数组"的几种写法及它们的代价。

完成这一天后,你的代码会有一个 `static HEMISPHERE_SAMPLES: [(f32,f32,f32); 64]`,无论谁调用都不会重新计算。你还能解释"为什么把它放在 GPU uniform buffer 里比放在 SSBO 里更合适"。

## 1 · Casey 今天做了什么

Casey 这一天的动作分四步:

第一,他把 Day 436 的 `spiral_point` 函数从一个独立 utility 改成"开机调用一次"的初始化代码。他新增一个 `BuildHemisphereDistribution(&MemoryArena, u32 SampleCount)` 函数,在游戏启动时分配一块内存,把 N=64 个方向写进去。

第二,他把球面螺旋改成**半球螺旋**——只取 z >= 0 的部分。这相当于在 Day 436 公式里把 `t` 从 [0, 1] 改成 [0, 0.5],或者等价地 `theta` 从 [0, π] 改成 [0, π/2]。

第三,他更新所有光照 shader:从原来"运行时调 spiral 函数"改成"从预计算 buffer 取第 i 个方向"。shader 代码因此变得简洁。

第四,他做了性能验证——`perf stat` 显示 CPU 端光照计算时间下降了百分之几,GPU 端"buffer 上传"开销几乎归零(只在启动时上传一次)。

## 2 · 心智模型

### 类比:把电话簿印成书

你查电话号码有两种方式:每次需要时翻原始档案(慢但实时),或者把常用号码预先抄到一个小本子上(快但需要先抄一次)。**预计算**就是后者。

球面螺旋的 64 个方向,在这个意义上就是你"每天都要查"的号码。第一次开机时你抄一遍,以后 60 帧/秒都查这个小本子,从不重抄。

### 半球螺旋的严谨公式

半球的定义是 `z >= 0` 的那半个球面。在 Day 436 的球面螺旋里,这意味着 `theta ∈ [0, π/2]`(从北极到赤道)。要让 N 个点在这个范围内面积均匀:

```
对 i = 0, 1, ..., N-1:
    z_i = 1.0 - (i + 0.5)/N       // z 从 1(北极)线性到 0(赤道)
    r_i = sqrt(1 - z_i²)           // 纬度圈半径
    phi_i = π * (1+√5) * i         // 黄金角累加
    方向 = (r_i cos(phi_i), r_i sin(phi_i), z_i)
```

**关键改动**:`z = 1 - (i+0.5)/N` 而不是 `z = 1 - 2(i+0.5)/N`。前者 z 从 1 到 0(上半球),后者 z 从 1 到 -1(整个球)。**直觉**:半球的 z 范围是 [0,1] 而不是 [-1,1],所以系数是 1 不是 2。

### Rust 的预计算三件套

Rust 表达"全局只算一次的常量数组"有三种写法。理解它们的差别很重要,这是从"会写 Rust"到"会工程化 Rust"的分水岭。

**写法 A: const 数组(编译期常量)**

```rust
const N: usize = 64;
const HEMISPHERE: [(f32, f32, f32); N] = build_hemisphere();

const fn build_hemisphere() -> [(f32, f32, f32); 64] {
    let mut arr = [(0.0, 0.0, 0.0); 64];
    let mut i = 0;
    while i < 64 {
        let z = 1.0 - (i as f32 + 0.5) / 64.0;
        let r = (1.0 - z * z).sqrt();
        let phi = std::f32::consts::PI * (1.0 + 5.0_f32.sqrt()) * i as f32;
        let (sp, cp) = phi.sin_cos();
        arr[i] = (r * cp, r * sp, z);
        i += 1;
    }
    arr
}
```

- `const fn` 是 Rust 的"编译期函数"。`HEMISPHERE` 不会出现在运行时代码里——它在编译时就被算成 64 个具体的 float,直接写进二进制 `.rodata` 段。
- **优点**:零运行时开销,程序启动即可用,而且不需要可执行文件之外的数据。
- **缺点**:`const fn` 限制多——不能 `for` 循环、不能 `format!`、不能 heap 分配。Rust 1.65+ 才稳定 `acos`/`sqrt` 在 const 上下文。
- **case 选不选?** Casey 在 HH C 代码里用 `static const` 等价物,因为他不在乎 const fn 限制。Rust 工程化项目里这是首选。

**写法 B: lazy_static / once_cell(运行时一次性初始化)**

```rust
use once_cell::sync::Lazy;

static HEMISPHERE: Lazy<Vec<(f32,f32,f32)>> = Lazy::new(|| {
    (0..64).map(|i| spiral_point(i, 64)).collect()
});
```

- 第一次访问 `HEMISPHERE` 时才执行 closure,以后所有访问都拿到同一个 `Vec`。
- **优点**:不受 `const fn` 限制——closure 里可以做任何事(分配、I/O、调 libm)。
- **缺点**:每次访问有一次原子读(Lazy 内部用 `Once`)。微优化场景下可感知。
- 现代写法用 `std::sync::LazyLock`(Rust 1.80+),不用第三方依赖。

**写法 C: 启动时显式初始化(Casey 的 HH 风格)**

```rust
struct GameState {
    hemisphere_samples: Box<[(f32,f32,f32); 64]>,
    // ... 其他游戏状态
}

fn init_game(arena: &mut MemoryArena) -> GameState {
    let mut samples = Box::new([(0.0,0.0,0.0); 64]);
    for i in 0..64 {
        samples[i] = spiral_point(i, 64);
    }
    GameState { hemisphere_samples: samples, ... }
}
```

- 数据放在 GameState 里,和游戏其他状态平等。**好处**:不依赖任何全局变量(全局变量在多线程、热重载、测试里都是坑)。
- **Casey 的 HH C 代码用这种**,因为他的 GameMemory 模型就是"一个大 arena 装一切"。Rust 翻译也走这条路最自然。
- **缺点**:访问时要传 `&state.hemisphere_samples`,代码冗余些。

**怎么选?**
- 编译期可计算 + 数据小 + 无 libm 依赖 → 写法 A
- 需要运行时计算 + 想要全局访问 → 写法 B
- Casey 风格 + 测试友好 + 热重载友好 → 写法 C

Day 437 Casey 选 C。你跟 Casey 学,推荐 C。这是"全状态显式传参"的工程纪律,从长远看能避免很多坑。

### GPU 上传策略

预计算好的数组最终要进 GPU。两种方式:

**Uniform Buffer(UBO)**:小数据(通常 ≤ 16KB)、只读、shader 里直接索引。N=64 个 float3 = 768 字节,完美适合 UBO。

**Shader Storage Buffer(SSBO)**:大数据(MB 级)、可读写、shader 里可变长索引。适合粒子系统、骨骼动画。

GLSL 端声明:
```glsl
layout(std140) uniform HemisphereSamples {
    vec4 samples[64];  // 用 vec4 对齐(std140 要求)
};
```

**为什么用 vec4 而不是 vec3?** `std140` 内存布局规则要求 vec3 占 16 字节(对齐到 vec4)。如果硬用 vec3,GPU 会自动 padding,反而更乱。所以工业代码统一用 vec4,第 4 个分量要么不用、要么塞 weight。

**上传时机**:`glBufferData` 一次性上传,然后永不更新。这是 Day 437 的"零带宽浪费"做法。

## 3 · 四域深入

### 3.1 · 游戏编程视角

预计算是游戏工程的**核心纪律**之一。游戏 60 FPS,意味着每帧 16.6ms 预算。CPU 在这 16ms 里要做:输入、AI、物理、动画、可见性、提交渲染。任何"不变的数据"重新计算,都是从这 16ms 里偷工。

预计算应用场景:
- **光照采样方向**(本日):N 个螺旋方向
- **球谐函数系数**:预计算 9 个或 16 个 SH 系数,代替原始环境贴图
- **BRDF LUT**:Schlick Fresnel 近似的查找表,GPU 一次查找代替几次 pow
- **粒子初始化**:开火时 100 个粒子的初速度、生命周期、颜色,预生成随机模板,复制粘贴
- **动画曲线**:美术做的 bezier 路径,烘焙成 N 个采样点

工业级工具:**烘焙(baking)**。所有静态光照、反射、GI 都可以在编辑器里预计算,打包成 lightmap。游戏运行时只查表,不算。

工程坑:**热重载时预计算要不要重算?** 如果螺旋公式不变,不需要重算。但如果你改了 N(64→128),就要重算。Casey 的 GameState 模式天然支持——热重载时整个 GameState 重建,所有预计算重做。这就是写法 C 的隐性优势。

### 3.2 · 图形学视角

半球分布是**所有基于物理的光照**的基础。回顾 Lambert 漫反射积分:

```
L_out = ∫∫_hemisphere (albedo/π) * L_in(ω) * cos(θ) dω
```

这个二重积分没有闭式解(L_in 是任意环境贴图),只能用 Monte Carlo 近似:

```
L_out ≈ (albedo * 2π / N) * Σ L_in(ω_i) * cos(θ_i)
```

`ω_i` 就是 64 个螺旋方向。`(2π)` 来自半球的"采样 PDF 归一化"——半球上均匀采样的 PDF 是 `1/(2π)`。

**余弦加权**:更高级的版本不是均匀半球采样,而是"余弦加权"——`ω_i` 的密度 ∝ `cos(θ)`。这把 `cos(θ)` 因子吸收进 PDF,降低方差。Casey Day 438 会切到这个版本(Poisson sampling)。

进阶术语:
- **重要性采样(importance sampling)**:PDF ∝ 被积函数的形状,降低方差
- **多重重要性采样(MIS)**:组合多个分布,各取所长
- **next event estimation**:在 path tracing 里直接采样光源方向

### 3.3 · Linux 系统编程视角

预计算数组的内存布局在 Linux 上有几个细节值得说:

**`.rodata` 段**:写法 A 的 const 数组,编译后落到 ELF 文件的 `.rodata`(read-only data)段。CPU 第一次访问时,内核做一次 page fault,把这一页从 ELF map 到内存,以后所有访问都是直接读 cache。`readelf -S binary | grep rodata` 可以看。

**`.bss` 段**:写法 C 的 `Box::new([(0,0,0); 64])` 在堆上分配,但 `[(0,0,0); 64]` 字面量是 `.bss`(零初始化数据)——内核不给它分配物理内存,直到第一次写。

**mmap 和大数据**:如果预计算数组是 16MB 的查找表(例如 BRDF LUT),`Box` 就不合适了——堆碎片化、分配慢。改用 `memmap2` crate 把文件直接 mmap 进内存,Linux 内核按需分页。

```bash
# 看你的程序 .rodata 段有多大
readelf -S target/release/mygame | grep -E "rodata|bss"
# 输出:.rodata 大小、地址、对齐

# 看运行时内存映射
cat /proc/$(pidof mygame)/maps | grep -E "rodata|heap"
```

**Cache friendliness**:N=64 个 float3 = 768 字节,正好 12 个 cache line(64 字节/line)。GPU 上传时 DMA 一次性搬完。这就是为什么"小数据"是最快的——它完全装进 L1 cache,后续访问零等待。

### 3.4 · Rust 生态视角

预计算数组的 Rust 写法有几个进阶技巧:

**A. `const` 表达式 vs `const fn`**

```rust
// 简单常量(数值字面量)
const N: usize = 64;

// const fn(编译期函数)
const fn build() -> [(f32,f32,f32); 64] { ... }
const ARR: [(f32,f32,f32); 64] = build();
```

Rust 1.65 起,`const fn` 支持绝大多数 `f32` 操作,包括 `sin`、`cos`、`sqrt`、`acos`。今天的代码可以完全 `const` 化。

**B. 数组初始化语法**

```rust
// 全部填零
let a = [(0.0, 0.0, 0.0); 64];

// 用 const fn 填
let b: [Vec3; 64] = core::array::from_fn(|i| spiral_point(i, 64));
```

`core::array::from_fn` 是 Rust 1.63+ 的标准库函数,适合运行时数组初始化。

**C. 全局状态的替代方案**

不要写:
```rust
static mut HEMISPHERE: [(f32,f32,f32); 64] = [(0.0,0.0,0.0); 64];

unsafe {
    for i in 0..64 { HEMISPHERE[i] = spiral_point(i, 64); }
}
```

`static mut` 是 Rust 的反模式——它在多线程下是数据竞争的温床。改用 `Lazy`/`LazyLock`(写法 B)或显式传参(写法 C)。

**D. SIMD 友好布局**

如果后面要做"批量变换 64 个方向到 tangent space",SoA 布局更好:

```rust
struct HemisphereSoA {
    xs: [f32; 64],
    ys: [f32; 64],
    zs: [f32; 64],
}
```

这样 SIMD 指令 `_mm256_mul_ps` 可以一次处理 8 个 f32,而不是一个 Vec3。

**真实 crate**:
- `bevy_render::renderer::RenderDevice`:封装 Vulkan/Metal/DX12,提供 buffer 上传 API
- `wgpu::BufferUsage::UNIFORM` / `STORAGE`:声明 buffer 用途,驱动决定放显存还是系统内存
- `glam::Vec3A`:16 字节对齐的 Vec3,适合 UBO 的 std140 布局

## 5 · 对照与变奏

**同一原则在不同场景的体现**:

| 场景 | 预计算内容 | 节省的运行时开销 |
|---|---|---|
| 光照采样方向 | 64 个 vec3 | 3840 次 sin/cos/秒 |
| 球谐函数 | 9 或 16 个系数 | 环境贴图压缩到几十字节 |
| BRDF LUT | 128×128 RG32 贴图 | 替代实时 Fresnel/Roughness 计算 |
| 动画曲线 | N 个采样点 | 替代 bezier 递归 |
| 字体字形 | SDF atlas | 替代每帧 curve tessellation |
| 路径规划 | 邻接矩阵 + Dijkstra 表 | 替代每次寻路 |

**工业级预计算工具**:
- **Delight / Houdini Mantra**:电影级光照烘焙
- **Simplygon**:网格减面、LOD 生成
- **Basis Universal**:纹理超压缩(打包时压,运行时解压)

**预计算的代价**:
不是免费午餐。预计算 = **构建时间**。游戏打包可能几小时,就是预计算多。Indie 游戏常用"渐进式预计算"——开发时不预计算(快速迭代),发布前才预计算(画质优先)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 为什么把球面螺旋改成半球螺旋,而不是直接用球面螺旋然后丢弃 z<0 的点?

**参考解答**:丢弃 z<0 的点意味着"原 N 个点只有一半在半球",N 减半。如果想保持 64 个有效方向,要生成 128 个再丢弃一半——浪费 CPU。直接在公式里把 z 范围限制到 [0,1](即 `z = 1 - (i+0.5)/N` 而不是 `1 - 2(i+0.5)/N`),让 N 个点全部落在半球内,且面积均匀。这是数学上的等价改写,没有任何代价。

### Lv2 · 动手实践

**题**:在 Rust 项目里实现"启动时初始化"的预计算模式(GameState 持有数组),并写一个测试验证数组在多次调用间不变(没有意外重新计算)。

**参考解答**:

```rust
// 模拟 Casey 的 GameState 模式
struct GameState {
    hemisphere: [(f32, f32, f32); 64],
    init_count: u32,  // 记录初始化次数,用于测试
}

impl GameState {
    fn new() -> Self {
        let mut hemisphere = [(0.0, 0.0, 0.0); 64];
        for i in 0..64 {
            let z = 1.0 - (i as f32 + 0.5) / 64.0;
            let r = (1.0 - z * z).sqrt();
            let phi = std::f32::consts::PI * (1.0 + 5.0_f32.sqrt()) * i as f32;
            let (sp, cp) = phi.sin_cos();
            hemisphere[i] = (r * cp, r * sp, z);
        }
        Self { hemisphere, init_count: 1 }
    }
    fn sample(&self, i: usize) -> (f32, f32, f32) {
        self.hemisphere[i]
    }
}

fn main() {
    let state = GameState::new();

    // 验证:取若干次,结果都一样
    let s0 = state.sample(0);
    let s0_again = state.sample(0);
    assert_eq!(s0, s0_again);

    // 验证:所有点都在半球(z >= 0)
    for i in 0..64 {
        let (_, _, z) = state.sample(i);
        assert!(z >= 0.0, "point {} has z={}, should be >= 0", i, z);
    }

    // 验证:所有点都在单位球上(|v| ≈ 1)
    for i in 0..64 {
        let (x, y, z) = state.sample(i);
        let len2 = x*x + y*y + z*z;
        assert!((len2 - 1.0).abs() < 1e-5, "point {} |v|²={}, should be 1", i, len2);
    }

    println!("All hemisphere samples valid. init_count = {}", state.init_count);
}
```

每行解释:
- `init_count` 是测试用的"探针",在工程代码里没有,但能验证"初始化只发生一次"。
- `assert_eq!(s0, s0_again)` — 因为 `(f32,f32,f32)` 实现了 `PartialEq`,可以直接比。这里 f32 是确定的常量,没有舍入误差。
- `len2 ≈ 1` 检查单位向量,允许 1e-5 浮点误差。
- 整个测试不需要任何依赖,`cargo run` 直接跑。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

把 Lv2 扩展,加上"三种写法对比"和"性能测量":

```rust
use std::time::Instant;

// 写法 A: const fn
const N: usize = 64;
const HEMISPHERE_CONST: [(f32, f32, f32); N] = {
    let mut arr = [(0.0, 0.0, 0.0); N];
    let mut i = 0;
    while i < N {
        let z = 1.0 - (i as f32 + 0.5) / N as f32;
        let r = (1.0 - z * z).sqrt();
        let phi = std::f32::consts::PI * (1.0 + 5.0_f32.sqrt()) * i as f32;
        let (sp, cp) = phi.sin_cos();
        arr[i] = (r * cp, r * sp, z);
        i += 1;
    }
    arr
};

// 写法 C: 显式 GameState
struct GameState {
    hemisphere: [(f32, f32, f32); N],
}

impl GameState {
    fn new() -> Self {
        let mut h = [(0.0, 0.0, 0.0); N];
        for i in 0..N {
            h[i] = HEMISPHERE_CONST[i];  // 直接复制 const 版本
        }
        Self { hemisphere: h }
    }
}

fn main() {
    // 写法 A 直接可用(编译期已经算好)
    println!("const[0] = {:?}", HEMISPHERE_CONST[0]);

    // 测量写法 C 的初始化时间
    let start = Instant::now();
    let state = GameState::new();
    let elapsed = start.elapsed();
    println!("GameState init: {:?}", elapsed);

    // 测量写法 C 的访问时间(基准)
    let start = Instant::now();
    let mut acc = 0.0f32;
    for _ in 0..1_000_000 {
        for i in 0..N {
            let (_, _, z) = state.hemisphere[i];
            acc += z;
        }
    }
    let elapsed = start.elapsed();
    println!("1M iterations of 64-sample lookup: {:?}", elapsed);
    println!("(dummy acc = {} to prevent DCE)", acc);
}
```

每行解释:
- `const { while i < N { ... i += 1; } }` — const fn 里不能用 `for ... in`,只能 `while`。这是 Rust 当前限制。
- `Instant::now()` — 测量单调时间,适合性能基准。注意不是 bench(没统计学精度)。
- `acc += z` + 最后打印 — 防止 LLVM 把整个循环 DCE(死代码消除)。如果不用 acc,优化器会发现循环没有副作用,直接删掉。
- `{:?}` 格式化元组 — `Debug` trait 已经为元组实现。

### Arch Linux 工具链

```bash
# 看 const 数组在 ELF 的位置
cargo build --release
readelf -S target/release/precompute | grep -E "\.rodata|\.bss"
# 应该看到 .rodata 段包含 HEMISPHERE_CONST(64 个 vec3 = 768 字节)

# 看汇编,确认 const fn 在编译期已算好(运行时无 sin/cos)
cargo rustc --release -- --emit asm
grep -E "call.*sin|call.*cos|call.*acos" target/release/deps/precompute-*.s | head
# 如果是 const fn 版本,这里应该看不到 sin/cos 调用(都被求值了)
# 只有写法 C 的 init 才会有(但写法 C 这里也用了 const 数组,所以也看不到)

# 用 perf 做更精确的 profile
sudo pacman -S perf
perf stat -e cycles,instructions,cache-misses ./target/release/precompute
# cache-misses 应该接近 0(数组完全装进 L1)

# 用 valgrind 的 cachegrind 看缓存详细
sudo pacman -S valgrind
valgrind --tool=cachegrind ./target/release/precompute
# 输出会显示 L1 cache miss 数
```

**Troubleshooting**:
- `error[E0658]: const fn unstable` → 升级 Rust 到 1.65+,或不用 const fn
- `error: unsupported operation in const fn` → const fn 里用了不支持的 API(如 `format!`),改用普通 fn
- 性能测试结果抖动大 → 关掉 CPU 频率缩放:`sudo cpupower frequency-set -g performance`
