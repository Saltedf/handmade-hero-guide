让我把 PNG 文件格式彻底讲清楚,这是 Day 453-459 的整体地图。

**PNG 文件结构**。一个 PNG 文件是固定签名 + 一串 chunk:

```
[8 字节签名] [chunk 1] [chunk 2] ... [chunk N] [IEND chunk]
```

签名(magic number)是固定的 8 字节:`89 50 4E 47 0D 0A 1A 0A`。这用来识别"这是个 PNG 文件"。

每个 chunk 结构:

```
[4 字节 length] [4 字节 type] [length 字节 data] [4 字节 CRC32]
```

length 是 data 的字节数。type 是 ASCII 4 字符(如 "IHDR"、"IDAT"、"IEND")。CRC32 是 type + data 的校验和。

**关键 chunk 类型**:

- **IHDR**:Image Header,文件必备,**第一个 chunk**。包含宽度(4 字节)、高度(4 字节)、位深度(1 字节)、颜色类型(1 字节)、压缩方法(1 字节)、过滤方法(1 字节)、交错方法(1 字节)——共 13 字节 data。
- **PLTE**:Palette,可选。索引颜色模式用。
- **IDAT**:Image Data,可能多个(连续)。压缩的图像数据。
- **IEND**:Image End,**最后一个 chunk**。标志文件结束。data 长度 0。
- **其他**:tEXt(文本元数据)、tIME(修改时间)、gAMA(gamma 校正)等。

**为什么用 chunk 而不是顺序结构?** chunk 化的格式有几个工程优势:

1. **可扩展**:加新 chunk 类型不破坏老解析器(老解析器跳过未知 chunk)
2. **可校验**:每个 chunk 独立 CRC,损坏只影响一个 chunk
3. **可流式**:解析器可以边读边处理,不用整个文件加载
4. **可选数据**:元数据 chunk(文本、时间)是可选的,符合"最小化必须"原则

这是 PNG 设计于 1995 年的现代化决策——比 BMP(纯顺序结构)、GIF(简单结构)更灵活。后来 WebP、AVIF 都沿用 chunk 化。

**PNG 头部签名的设计巧思**。8 字节签名 `89 50 4E 47 0D 0A 1A 0A` 不是随便选的:

- `89`:非 ASCII 字符。如果文件被错误地以 ASCII 文本传输(比如 FTP 的 text mode),`\r\n` 转换会破坏二进制,签名变。`89` 不在 ASCII 范围,容易检测。
- `50 4E 47`:ASCII "PNG"。人类可读的标记。
- `0D 0A`:CR LF(DOS 换行)。检测换行转换。
- `1A`:Ctrl-Z(ASCII 文件结束符)。FTP text mode 截断的标记。
- `0A`:LF(Unix 换行)。检测换行转换。

**这个签名能在 7 种最常见的传输错误下被发现**——是 90 年代网络传输的工程教训的结晶。

## 补充:CRC-32 多项式的推导

CRC32 是 PNG 每个 chunk 的校验码。让我把这个核心算法讲清楚。

**CRC(Cyclic Redundancy Check)** 是基于多项式除法的校验码。把数据看作一个巨大的二进制数,除以一个固定的"生成多项式",余数就是 CRC。

**为什么用多项式?** 二进制除法在硬件上极快(XOR + 移位),而且对突发错误(burst error,连续位翻转)敏感——比简单 checksum 强。

**标准 CRC-32 多项式**(IEEE 802.3):

```
G(x) = x^32 + x^26 + x^23 + x^22 + x^16 + x^12 + x^11 + x^10
       + x^8 + x^7 + x^5 + x^4 + x^2 + x + 1
```

写成二进制(从高位到低位):`1 00000100 11000001 00011101 10110111`

十六进制:`0x04C11DB7`(高位的 1 是隐含的,实际只用低 32 位)。

**CRC 计算**。把数据看作一个 N-bit 二进制数,在末尾追加 32 个 0(给余数留位),然后对 G(x) 做 XOR 除法(无进位)。余数就是 CRC32。

```rust
fn crc32(data: &[u8]) -> u32 {
    let mut crc: u32 = 0xFFFFFFFF;  // 初始值
    for &byte in data {
        crc ^= byte as u32;
        for _ in 0..8 {
            if crc & 1 != 0 {
                crc = (crc >> 1) ^ 0xEDB88320;  // 反射多项式
            } else {
                crc >>= 1;
            }
        }
    }
    crc ^ 0xFFFFFFFF  // 最终 XOR
}
```

**几个工程细节**:

1. **初始值 `0xFFFFFFFF`**:避免数据前的零字节不影响 CRC(全零输入应给非零 CRC)
2. **反射多项式 `0xEDB88320`**:CRC-32 标准用"反射输入输出"——位的顺序反转,所以多项式也要反射
3. **最终 XOR `0xFFFFFFFF`**:类似初始值的目的

**CRC vs checksum**。简单 checksum 是"所有字节加起来 mod 256"。问题:重排字节 checksum 不变——不能检测顺序错。CRC 因为多项式除法,**对顺序敏感**——重排字节 CRC 变。

**CRC 的局限**:CRC 检测"意外损坏",不防"恶意篡改"。攻击者可以同时改数据和 CRC——CRC 算法公开,他能算正确 CRC。要防篡改用 HMAC 或数字签名。

**用 CRC 工具验证**:

```bash
# 计算文件的 CRC32
cksum /path/to/file  # POSIX 标准(用不同多项式)
crc32 /path/to/file  # zlib 工具
python3 -c "import binascii; print(hex(binascii.crc32(open('foo.png','rb').read())))"
```

PNG 文件每个 chunk 的 CRC 可以独立验证——损坏的 chunk 不影响其他。这是 chunk 化的另一个好处。

## 补充:IHDR 各字段详解

IHDR chunk 的 13 字节 data 拆解:

```
偏移  字段                字节数  说明
0     Width              4       图像宽度(像素),big-endian
4     Height             4       图像高度(像素),big-endian
8     Bit depth          1       每通道位数:1, 2, 4, 8, 16
9     Color type         1       0=灰度, 2=RGB, 3=索引, 4=灰度+α, 6=RGBA
10    Compression method 1       必须 0(DEFLATE)
11    Filter method      1       必须 0(标准过滤)
12    Interlace method   1       0=无, 1=Adam7 交错
```

**位深度**(bit depth):

- 1-bit:每像素 1 位,黑白图像(如线条画)
- 8-bit:每通道 8 位,RGB 总共 24 位/像素——最常用
- 16-bit:每通道 16 位,RGB 总共 48 位/像素——高色彩精度(摄影)

**颜色类型**(color type):

- 0:Grayscale(灰度,1 通道)
- 2:RGB(3 通道)
- 3:Indexed(索引颜色,用 PLTE chunk 查表)
- 4:Grayscale + Alpha(灰度 + α,2 通道)
- 6:RGB + Alpha(RGBA,4 通道)——游戏常用,带透明

**交错方法**(interlace):

- 0:无交错,按行扫描
- 1:Adam7 交错——7 个 pass,先传稀疏像素,后逐渐填密

Adam7 让浏览器在 PNG 没下完时显示"模糊预览",逐渐清晰。代价:文件略大(每 pass 各自过滤),编码复杂。游戏不用,网页常用。

**Endianness**。PNG 所有 16/32 位字段是 **big-endian**(网络字节序)。Rust 默认 little-endian,解析时要 swap:

```rust
fn read_u32_be(bytes: &[u8], offset: usize) -> u32 {
    u32::from_be_bytes([bytes[offset], bytes[offset+1], bytes[offset+2], bytes[offset+3]])
}
```

`from_be_bytes` 是 Rust 标准库的 big-endian 解码——明确指定字节序,代码跨平台一致。

## 2 · 心智模型

### 类比:打开包裹

PNG 文件像一个快递包裹。外面包裹上有快递单(magic number + 标签)。拆开第一层是 IHDR(包裹规格:多大、什么类型)。后面是 IDAT(实际内容,但被压缩了)。最后是 IEND(结束标记)。

每层(chunk)都有自己的"小标签"(类型名)和"封口"(CRC32 校验)。如果哪一层校验失败,说明损坏,拒绝整个文件。

### PNG 文件的整体结构

```
┌──────────────────────┐
│ 8 字节魔数(magic)    │  89 50 4E 47 0D 0A 1A 0A
├──────────────────────┤
│ Chunk: IHDR          │  13 字节数据,固定第一个
├──────────────────────┤
│ Chunk: IDAT          │  压缩的图像数据,可能多个
├──────────────────────┤
│ Chunk: IDAT ...      │
├──────────────────────┤
│ Chunk: IEND          │  结束标记
└──────────────────────┘
```

### 严谨原理:PNG chunk 结构

每个 chunk 由 4 部分组成:

```
+----------------+----------------+----------------+----------------+
| Length (4 字节) | Type (4 字节)   | Data (N 字节)   | CRC (4 字节)   |
+----------------+----------------+----------------+----------------+
```

- **Length**:数据字节数(big-endian u32),不含 Type 和 CRC。
- **Type**:4 字节 ASCII(如 `IHDR`, `IDAT`, `IEND`)。第一字节大写表示"关键 chunk",小写表示"辅助 chunk"。
- **Data**:Length 字节的数据。
- **CRC32**:覆盖 Type + Data 的 CRC 校验。读者必须验证 CRC,损坏则拒绝。

### Magic number(魔数)

PNG 文件头 8 字节:`89 50 4E 47 0D 0A 1A 0A`

为什么不是简单的 "PNG"?**两个原因**:

第一,**避免误识别**。如果 PNG 用 "PNG" 三字节开头,文本文件里出现 "PNG" 字样会被误识别。`89` 是非 ASCII,排除纯文本。`50 4E 47` = "PNG" 的 ASCII,`0D 0A` = CRLF(Windows 换行),`1A` = EOF 字符(让文本工具提前停),`0A` = LF(Unix 换行)。这套设计让 PNG 通过文本工具 / 串口 / 不同换行系统时,文件头不被改坏。

第二,**端到端测试**。这 8 字节同时检测:文件被当文本处理(CRLF 转换)、被截断(EOF)、被二进制损坏。

### IHDR 字段

IHDR 的 13 字节数据:

| 偏移 | 长度 | 字段 | 含义 |
|---|---|---|---|
| 0 | 4 | Width | 图像宽度(像素,big-endian u32) |
| 4 | 4 | Height | 图像高度 |
| 8 | 1 | Bit depth | 每通道位深(1, 2, 4, 8, 16) |
| 9 | 1 | Color type | 颜色类型(0=灰度, 2=RGB, 3=索引, 4=灰度+α, 6=RGBA) |
| 10 | 1 | Compression | 压缩方法(永远 0=DEFLATE) |
| 11 | 1 | Filter | 过滤方法(永远 0=adaptive) |
| 12 | 1 | Interlace | 交错方法(0=none, 1=Adam7) |

Rust 解析:

```rust
struct Ihdr {
    width: u32,
    height: u32,
    bit_depth: u8,
    color_type: u8,
    compression: u8,
    filter: u8,
    interlace: u8,
}

fn parse_ihdr(data: &[u8]) -> Result<Ihdr, String> {
    if data.len() < 13 {
        return Err("IHDR too short".into());
    }
    Ok(Ihdr {
        width: u32::from_be_bytes([data[0], data[1], data[2], data[3]]),
        height: u32::from_be_bytes([data[4], data[5], data[6], data[7]]),
        bit_depth: data[8],
        color_type: data[9],
        compression: data[10],
        filter: data[11],
        interlace: data[12],
    })
}
```

每行解释:
- `u32::from_be_bytes` — big-endian 字节转 u32。PNG 全部用 BE(网络字节序)。
- `[data[0], data[1], data[2], data[3]]` — 数组字面量,4 字节。
- 验证 `data.len() < 13` 防御损坏的 chunk。

### Chunk 读取循环

```rust
struct PngReader<'a> {
    data: &'a [u8],
    cursor: usize,
}

impl<'a> PngReader<'a> {
    fn new(data: &'a [u8]) -> Self { Self { data, cursor: 0 } }
    
    fn read_bytes(&mut self, n: usize) -> Result<&'a [u8], String> {
        if self.cursor + n > self.data.len() {
            return Err(format!("Unexpected EOF at cursor {}", self.cursor));
        }
        let result = &self.data[self.cursor..self.cursor+n];
        self.cursor += n;
        Ok(result)
    }
    
    fn read_u32_be(&mut self) -> Result<u32, String> {
        let b = self.read_bytes(4)?;
        Ok(u32::from_be_bytes([b[0], b[1], b[2], b[3]]))
    }
    
    fn read_chunk(&mut self) -> Result<Chunk, String> {
        let length = self.read_u32_be()? as usize;
        let chunk_type = self.read_bytes(4)?;
        let data = self.read_bytes(length)?;
        let crc = self.read_u32_be()?;
        // 验证 CRC(下面实现)
        let computed_crc = crc32(chunk_type, data);
        if computed_crc != crc {
            return Err(format!("CRC mismatch: expected {:08x}, got {:08x}", crc, computed_crc));
        }
        let chunk_type_str = std::str::from_utf8(chunk_type)
            .map_err(|_| "Invalid chunk type")?;
        Ok(Chunk {
            chunk_type: chunk_type_str.to_string(),
            data: data.to_vec(),
        })
    }
}

struct Chunk {
    chunk_type: String,
    data: Vec<u8>,
}
```

每行解释:
- `'a` 生命周期 — `data` 引用外部 buffer,不拷贝。
- `read_bytes` — 推进游标,返回切片。EOF 时 Err。
- `crc32` — Day 460+ 详细实现,本日先用占位。
- `chunk_type_str` — 4 字节 ASCII,转字符串可读。

### CRC32 校验

CRC32(Cyclic Redundancy Check)是数据校验的经典算法。**直觉**:把数据当成一个巨大的多项式,除以一个固定的"生成多项式",余数就是 CRC。读的时候重算 CRC,如果和存的 CRC 不一致 → 数据损坏。

完整 CRC32 算法:
```rust
fn crc32_table() -> [u32; 256] {
    let mut table = [0u32; 256];
    for i in 0..256u32 {
        let mut c = i;
        for _ in 0..8 {
            if c & 1 != 0 {
                c = 0xEDB88320 ^ (c >> 1);
            } else {
                c >>= 1;
            }
        }
        table[i as usize] = c;
    }
    table
}

fn crc32(type_bytes: &[u8], data: &[u8]) -> u32 {
    let table = crc32_table();
    let mut crc: u32 = 0xFFFFFFFF;
    for &b in type_bytes.iter().chain(data.iter()) {
        let idx = ((crc ^ b as u32) & 0xFF) as usize;
        crc = (crc >> 8) ^ table[idx];
    }
    crc ^ 0xFFFFFFFF
}
```

每行解释:
- `0xEDB88320` — CRC-32 标准生成多项式(反向位序)。
- 表 256 项 — 预计算每字节对应的 CRC 贡献。
- `crc ^ 0xFFFFFFFF` — 标准 CRC 用反向初始和最终翻转。
- `chain` — 迭代器拼接,CRC 覆盖 type + data。

## 3 · 四域深入

### 3.1 · 游戏编程视角

PNG 在游戏里:
- **UI / 图标**:PNG 是 UI 资产主流格式(无损 + α 通道)
- **纹理**:工业上更多用 DDS / KTX(GPU 直接格式),但 PNG 适合"开发期"(看得到内容)
- **截图**:游戏截图存 PNG(无损)
- **配置 / 元数据**:PNG 的辅助 chunk 可以塞自定义数据(如关卡布局)

工业坑:**PNG 解码慢**。每帧从 PNG 解纹理不现实,所以游戏启动时**一次性解码所有 PNG**,缓存到 GPU。

### 3.2 · 图形学视角

PNG 的图形学特性:

- **无损**:不丢精度,适合像素艺术、UI
- **α 通道**:RGBA 支持,适合叠加图层
- **压缩**:DEFLATE 平均压缩 2:1(自然图像)、10:1(像素艺术)
- **交错**:Adam7 让浏览器逐步显示 PNG(先 1/64,再 1/32...)

**Adam7 交错**:7 个 pass,每个 pass 处理不同像素。第一个 pass 是每 8 像素取 1,让人看到模糊轮廓;最后一个 pass 补全所有细节。这是渐进式 JPEG 的替代。

### 3.3 · Linux 系统编程视角

Linux 上处理 PNG 的工具:

### 3.4 · Rust 生态视角

Rust 解析二进制的几种风格:

**A. 手写字节游标(本日)** — `PngReader` 风格,直观但啰嗦。

**B. `nom` crate** — parser combinator:
```rust
use nom::{bytes::complete::take, number::complete::be_u32};
fn chunk(input: &[u8]) -> IResult<&[u8], Chunk> {
    let (input, length) = be_u32(input)?;
    let (input, ctype) = take(4u8)(input)?;
    let (input, data) = take(length)(input)?;
    let (input, crc) = be_u32(input)?;
    Ok((input, Chunk { ctype, data, crc }))
}
```
声明式,适合复杂格式。

**C. `binrw` crate** — derive 宏:
```rust
use binrw::binrw;
#[binrw]
#[br(big)]
struct Ihdr {
    width: u32,
    height: u32,
    bit_depth: u8,
    color_type: u8,
    compression: u8,
    filter: u8,
    interlace: u8,
}
```

## 5 · 对照与变奏

**不同文件格式的 magic**:

| 格式 | Magic(十六进制) |
|---|---|
| PNG | 89 50 4E 47 0D 0A 1A 0A |
| JPEG | FF D8 FF |
| GIF | 47 49 46 38 (GIF8) |
| PDF | 25 50 44 46 (%PDF) |
| ZIP | 50 4B 03 04 (PK) |
| ELF | 7F 45 4C 46 (\x7FELF) |
| WASM | 00 61 73 6D (\0asm) |

每个 magic 都经过精心设计,避免误识别。

**chunk 化 vs 顺序**:
- chunk 化:PNG、RIFF(AVI/WAV)、MPEG
- 顺序:JPEG(标记 + 数据)、BMP(头部 + 像素)

chunk 化优点:可扩展(新 chunk 不破坏旧解析器),可校验(每 chunk CRC)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 PNG 用 chunk 而不是顺序结构?给两个具体好处。

**参考解答**:
1. **可扩展**:新版本可以加新 chunk(如 iCCP 颜色配置、tEXt 元数据),旧解析器跳过未知 chunk,不破坏。
2. **可校验**:每 chunk 独立 CRC,损坏可以定位到具体 chunk,不丢整个文件。
3. **流式友好**:chunk 序列可以流式读写,不需要预先知道总长。

**题**:在 Rust 里实现 `PngReader` 的 magic 验证 + IHDR 解析。读一张测试 PNG,打印宽高、颜色类型。

**参考解答**:

```rust
struct PngReader<'a> {
    data: &'a [u8],
    cursor: usize,
}

impl<'a> PngReader<'a> {
    fn new(data: &'a [u8]) -> Self { Self { data, cursor: 0 } }
    fn read(&mut self, n: usize) -> Result<&'a [u8], String> {
        if self.cursor + n > self.data.len() {
            return Err(format!("EOF at {}", self.cursor));
        }
        let s = &self.data[self.cursor..self.cursor + n];
        self.cursor += n;
        Ok(s)
    }
    fn read_u32(&mut self) -> Result<u32, String> {
        let b = self.read(4)?;
        Ok(u32::from_be_bytes([b[0], b[1], b[2], b[3]]))
    }
}

const PNG_MAGIC: [u8; 8] = [0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A];

fn main() -> Result<(), String> {
    // 用 std::fs::read 读 PNG 文件
    let args: Vec<_> = std::env::args().collect();
    if args.len() < 2 {
        return Err("Usage: png_header <file.png>".into());
    }
    let data = std::fs::read(&args[1]).map_err(|e| e.to_string())?;
    let mut reader = PngReader::new(&data);

    // 1. 验证 magic
    let magic = reader.read(8)?;
    if magic != PNG_MAGIC {
        return Err(format!("Not a PNG, got magic: {:02x?}", magic));
    }
    println!("PNG magic OK");

    // 2. 第一个 chunk 必须是 IHDR
    let length = reader.read_u32()? as usize;
    let ctype = reader.read(4)?;
    if ctype != b"IHDR" {
        return Err(format!("First chunk must be IHDR, got {:?}", ctype));
    }
    if length != 13 {
        return Err(format!("IHDR length must be 13, got {}", length));
    }
    let ihdr_data = reader.read(13)?;
    let _crc = reader.read_u32()?;  // 跳过 CRC(本日不验证)

    let width = u32::from_be_bytes([ihdr_data[0], ihdr_data[1], ihdr_data[2], ihdr_data[3]]);
    let height = u32::from_be_bytes([ihdr_data[4], ihdr_data[5], ihdr_data[6], ihdr_data[7]]);
    let bit_depth = ihdr_data[8];
    let color_type = ihdr_data[9];

    println!("Width: {}", width);
    println!("Height: {}", height);
    println!("Bit depth: {}", bit_depth);
    println!("Color type: {} ({})", color_type, match color_type {
        0 => "Grayscale",
        2 => "RGB",
        3 => "Indexed",
        4 => "Grayscale + Alpha",
        6 => "RGBA",
        _ => "Unknown",
    });

    Ok(())
}
```

- `std::env::args` — 读命令行参数。
- `std::fs::read` — 一次性读整个文件。
- magic 比较用字节数组直接 `!=`。
- IHDR length 必须 13,否则损坏。
- color_type 用 match 映射到可读字符串。

完整 PNG header 解析器(在 §7 Lv2 基础上加 CRC32 验证):

```rust
// CRC32 表(预计算)
fn crc32_table() -> [u32; 256] {
    let mut t = [0u32; 256];
    for i in 0..256u32 {
        let mut c = i;
        for _ in 0..8 {
            c = if c & 1 != 0 { 0xEDB88320 ^ (c >> 1) } else { c >> 1 };
        }
        t[i as usize] = c;
    }
    t
}

fn crc32(parts: &[&[u8]]) -> u32 {
    let table = crc32_table();
    let mut crc: u32 = 0xFFFFFFFF;
    for part in parts {
        for &b in *part {
            let idx = ((crc ^ b as u32) & 0xFF) as usize;
            crc = (crc >> 8) ^ table[idx];
        }
    }
    crc ^ 0xFFFFFFFF
}

struct PngReader<'a> { data: &'a [u8], cursor: usize }

impl<'a> PngReader<'a> {
    fn new(data: &'a [u8]) -> Self { Self { data, cursor: 0 } }
    fn read(&mut self, n: usize) -> Result<&'a [u8], String> {
        if self.cursor + n > self.data.len() {
            return Err(format!("EOF at {}", self.cursor));
        }
        let s = &self.data[self.cursor..self.cursor + n];
        self.cursor += n;
        Ok(s)
    }
    fn read_u32(&mut self) -> Result<u32, String> {
        let b = self.read(4)?;
        Ok(u32::from_be_bytes([b[0], b[1], b[2], b[3]]))
    }
}

const PNG_MAGIC: [u8; 8] = [0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A];

fn main() -> Result<(), String> {
    let args: Vec<_> = std::env::args().collect();
    let path = args.get(1).ok_or("Usage: png_header <file>")?;
    let data = std::fs::read(path).map_err(|e| e.to_string())?;
    let mut reader = PngReader::new(&data);

    let magic = reader.read(8)?;
    if magic != PNG_MAGIC {
        return Err(format!("Not PNG: {:02x?}", magic));
    }
    println!("Magic OK");

    // IHDR
    let length = reader.read_u32()? as usize;
    let ctype = reader.read(4)?.to_vec();
    if &ctype != b"IHDR" || length != 13 {
        return Err("Invalid IHDR".into());
    }
    let ihdr = reader.read(13)?;
    let crc = reader.read_u32()?;
    let computed = crc32(&[&ctype, ihdr]);
    if crc != computed {
        return Err(format!("IHDR CRC mismatch: file {:08x}, computed {:08x}", crc, computed));
    }
    println!("IHDR CRC OK");

    let w = u32::from_be_bytes([ihdr[0], ihdr[1], ihdr[2], ihdr[3]]);
    let h = u32::from_be_bytes([ihdr[4], ihdr[5], ihdr[6], ihdr[7]]);
    let bd = ihdr[8];
    let ct = ihdr[9];
    let cm = ihdr[10];
    let fm = ihdr[11];
    let il = ihdr[12];

    println!("  Width:       {}", w);
    println!("  Height:      {}", h);
    println!("  Bit depth:   {}", bd);
    println!("  Color type:  {} ({})", ct, match ct {
        0 => "Gray", 2 => "RGB", 3 => "Indexed", 4 => "Gray+Alpha", 6 => "RGBA", _ => "?"
    });
    println!("  Compression: {} (must be 0)", cm);
    println!("  Filter:      {} (must be 0)", fm);
    println!("  Interlace:   {} ({})", il, if il == 0 { "none" } else { "Adam7" });

    Ok(())
}
```
