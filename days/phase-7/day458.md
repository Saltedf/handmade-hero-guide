# Day 458 · 调试 PNG 读取器

> Day 453-457 写了完整 PNG 解码器,但跑起来全是错——像素花屏、CRC 失败、Huffman 死循环。今天 Casey 用调试工具找出每个 bug,演示"造轮子时怎么定位问题"。

## 0 · 为什么要有这一天

写代码 20% 时间,调 bug 80% 时间。这句话对 PNG 解码器特别准确——Day 453-457 5 集内容,Day 458 整整一集调试。这不是 Casey 写得不好,而是**二进制解析的特殊性**:每个 bit 都要精确,错一个位整个解码就乱。

PNG 调试难点:
- **位级错误**:BitReader 一个 bit 错,后面全乱
- **Huffman 死循环**:树构造错,decoder 永远找不到匹配
- **LZ77 引用越界**:distance > output.len(),panic 或垃圾数据
- **滤镜 bpp 错**:bpp 算错,反过滤像素错位
- **CRC 不匹配**:数据损坏或 CRC 实现错

今天 Casey 演示**系统化调试**:
1. **找最小复现**:用最简单的 PNG(单色 1x1 像素)
2. **分阶段验证**:每个阶段(magic / IHDR / zlib / DEFLATE / 滤镜)单独验证
3. **对比已知正确实现**:用 `image` crate / Python PIL 解同一张图,逐字节对比
4. **二分定位**:在不同阶段插入 `assert`,找第一个不一致点

完成这一天后,你能掌握二进制解析的系统化调试方法论,并能用 Rust 工具链(`dbg!`、`RR`、`valgrind`)高效定位类似 bug。

## 补充:PNG 解码的常见 bug 模式

让我把 PNG 解码的常见 bug 整理出来,这是 Day 458 的实战知识。

**Bug 模式 1:bit ordering 错**。DEFLATE 是 LSB-first,但 Huffman codes 在被读出后**按 MSB-first 解释**(因为 Huffman 是"前缀码",bit order 影响)。这种"读时 LSB,用前翻转"的转换错,导致 Huffman 解码全错。

```rust
// 错的:直接用 LSB 顺序解释
let code = reader.read_bits(5);
// 这给出 LSB-first 排列,但 Huffman code 是 MSB-first

// 对的:翻转位
let code_raw = reader.read_bits(5);
let code = reverse_bits(code_raw, 5);
```

或者用"逐位解码"——读 1 位,走树节点,不用 reverse。但 lookup table 方法要 reverse。

**Bug 模式 2:Huffman 表构造错**。Canonical Huffman 的位分配规则微妙:

```
1. count = 符号数
2. 对每个 length bl_count[i] = "code length 为 i 的符号数"
3. next_code[1] = 0
   next_code[i] = (next_code[i-1] + bl_count[i-1]) << 1
4. 对每个符号(按 length 升序,同 length 按值升序):
   symbol.code = next_code[symbol.length]++
```

任何一个 `<<` 或 `++` 错位,整个表错。Casey Day 458 调试时通常这个最多坑。

**Bug 模式 3:dynamic Huffman 块的"超 Huffman"**。DEFLATE 动态块先读 HCLEN(4 位) + HCLEN+4 个 3-bit code lengths,构造"用于解码 code length 序列"的 Huffman 表。然后再用这个表解码 literal/distance 的 code length 序列。**两层 Huffman**——容易混淆。

**Bug 模式 4:LZ77 复制的边界**。复制 `length` 字节,从 `pos - distance`:

```rust
// 错的:可能越界或 overlap 错
output.extend_from_within(pos - distance..pos - distance + length);

// 对的:逐字节,自动处理 overlap
let start = pos - distance;
for i in 0..length {
    output.push(output[start + i]);
}
```

**Bug 模式 5:滤镜 bpp 错**。bpp = bytes per pixel。RGB = 3,RGBA = 4。Sub/Average/Paeth 滤镜的"左邻"是 `bpp` 字节前的像素(不是 1 字节前)。算错 bpp 导致过滤预测错,反推像素错位。

**Bug 模式 6:CRC32 实现错**。CRC32 有多种变体(CRC-32, CRC-32/BZIP2, CRC-32/POSIX 等)。PNG 用 "CRC-32/ISO-HDLC"(反射、初始 0xFFFFFFFF、最终 XOR)。用错变体导致 CRC 永远不匹配。

## 补充:二进制调试的工业工具

**1. Hex viewer**。直接看字节:`xxd image.png | head -20` 或 `hexdump -C image.png`。Rust 工具:`hexyl`(更漂亮的输出)。

**2. Python 参考实现**。Python 的 `zlib` / `struct` 模块交互式好用:

```python
import zlib, struct
with open('image.png', 'rb') as f:
    data = f.read()
# 解析 IHDR
sig = data[:8]
chunk_len = struct.unpack('>I', data[8:12])[0]
chunk_type = data[12:16]
width = struct.unpack('>I', data[16:20])[0]
height = struct.unpack('>I', data[20:24])[0]
print(f'Sig: {sig.hex()}, Type: {chunk_type}, {width}x{height}')
```

**3. cargo expand**。看 macro 展开后的代码:

```bash
cargo install cargo-expand
cargo expand --bin your_program
```

**4. RR (Record and Replay)**。Linux 特有,录制程序执行,然后**反向调试**——可以"倒回"到 panic 之前。

```bash
sudo pacman -S rr
rr record ./target/debug/your_program
rr replay
# 在 gdb 里:reverse-step, reverse-continue
```

这是定位"数据损坏"类 bug 的神器——你可以倒回到写入错误数据的那个时刻。

**5. Valgrind**。检测内存错误(虽然 Rust 较少需要):

```bash
valgrind --tool=memcheck ./target/debug/your_program
valgrind --tool=callgrind ./target/debug/your_program  # 性能剖析
```

**6. Differential testing**。对相同输入,你的解码器和 libpng 应该输出一致。Rust 的 `proptest` 自动 fuzz:

```rust
proptest! {
    #[test]
    fn decodes_same_as_libpng(ref input in any::<Vec<u8>>()) {
        let mine = my_png_decoder(input);
        let reference = libpng_decode(input);
        prop_assert_eq!(mine, reference);
    }
}
```

proptest 会自动生成大量随机输入,暴露隐藏 bug。这是工业库(matzruby、image)的标准测试方式。

## 补充:Rust 的 debugging 工具链

**`dbg!` macro**。比 `println!` 更简洁——打印表达式值 + 位置:

```rust
let x = 5;
let y = dbg!(x * 2) + 1;
// 输出:[src/main.rs:2] x * 2 = 10
```

`dbg!` 在 debug build 用,release build 自动消除。Casey HH 在 C 里用 `printf` 调试,Rust 等价是 `dbg!`。

**`#[track_caller]`**。让 panic 信息定位到调用者,而不是 panic 函数:

```rust
#[track_caller]
fn must_succeed(result: Result<T, E>) -> T {
    match result {
        Ok(v) => v,
        Err(_) => panic!("must_succeed failed"),
    }
}

// 调用 must_succeed 失败时,panic 指向调用点,不是 must_succeed 内部
```

**Custom panic hooks**。重写 panic 行为,记录到日志:

```rust
std::panic::set_hook(Box::new(|info| {
    let location = info.location().unwrap();
    eprintln!("[PANIC] {}:{}: {}",
        location.file(), location.line(), info);
    // 也可以写日志、发邮件等
}));
```

游戏发行版常用——把 panic 转成"友好的错误弹窗"。

**Backtrace**。设置 `RUST_BACKTRACE=1`:

```bash
RUST_BACKTRACE=1 ./target/debug/your_program
RUST_BACKTRACE=full ./target/debug/your_program  # 更详细
```

panic 时打印完整调用栈,定位 panic 的源头。

**`cargo flamegraph`**。性能剖析可视化:

```bash
cargo install flamegraph
cargo flamegraph --bin your_program
# 生成 flamegraph.svg,在浏览器看
```

每帧"火焰"宽度 = CPU 时间占比,宽的就是热点。

这些工具是 Rust 程序员调试的标准武器。Casey HH 在 C 用 gdb + printf,Rust 工具链更丰富。

## 补充:case study - "图像花屏" 的调试路径

让我用一个具体例子展示系统化调试。假设你的 PNG 解码器输出花屏——颜色错乱、有水平条纹。怎么定位?

**第一步:测试输入**。用最简单的 1x1 像素纯红色 PNG。预期输出:`[(255, 0, 0, 255)]`(一个 RGBA 红像素)。实际输出:`[(255, 0, 0, 0)]`——α 错了。

**第二步:对比**。Python PIL 解相同文件:`list(Image.open('test.png').getdata()) = [(255, 0, 0, 255)]`。PIL 正确,你的错。

**第三步:定位阶段**。在每阶段插入 assert:

```rust
let magic = parse_magic(&data);
assert_eq!(magic, [0x89, b'P', b'N', b'G', 0x0D, 0x0A, 0x1A, 0x0A]);

let ihdr = parse_ihdr(&data[12..]);
assert_eq!(ihdr.width, 1);
assert_eq!(ihdr.height, 1);
assert_eq!(ihdr.color_type, 6);  // RGBA

let idat = parse_idat(&data);
let decompressed = inflate(&idat);
// 预期:5 字节(1 字节 filter + 4 字节 RGBA)
assert_eq!(decompressed, vec![0, 255, 0, 0, 255]);  // filter 0 = None

let pixels = reconstruct(&decompressed, 1, 1, 4);
assert_eq!(pixels, vec![255, 0, 0, 255]);  // 期望
```

**第四步:二分**。哪个 assert 失败?假设 decompressed assert 失败——inflate 有问题。具体:decompressed = `vec![0, 255, 0, 0, 0]`,最后字节是 0 而不是 255。

**第五步:深挖 inflate**。decompressed 的前 4 字节对,最后 1 字节错。可能是:

- BitReader 提前结束(少读 8 位)
- LZ77 复制错(用了错 distance)
- Huffman 解码漏了最后 token

加详细日志:

```rust
eprintln!("Final decompressed length: {}", decompressed.len());
eprintln!("Last 8 bytes: {:?}", &decompressed[decompressed.len().saturating_sub(8)..]);
eprintln!("Bit reader at: byte={}, bit={}", reader.byte_pos, reader.bit_pos);
```

发现 bit reader 在某个位置提前 EOF——可能是 zlib 头解析多了 1 字节,或 IDAT chunk 边界算错。

**第六步:修复**。具体问题具体修。Casey Day 458 演示的就是这个流程——分阶段、对比、二分。

**核心原则**:**永远从最简单 input 开始**。1x1 像素、纯色、filter 0(None)的 PNG,让你看到每个字节应该是啥。复杂 input 出错,你根本不知道哪个字节错。

## 2 · 心智模型

### 类比:解剖标本

调 PNG 像解剖标本。你不能"看整体",因为整体太复杂。要**分层剥离**:
- 第一层:文件结构(chunk 解析)
- 第二层:压缩(zlib/DEFLATE)
- 第三层:数据(过滤反推)
- 第四层:像素(布局解释)

每层都要验证。哪层出错,问题就在哪层。**关键工具**:每层都和"已知正确实现"对比。

### 系统化调试的 4 个步骤

**步骤 1:最小复现**
不要用复杂 PNG。从最小开始:
- 1x1 像素,单色,8-bit grayscale(无 α,无交错)
- 然后 1x1 RGB
- 然后 2x2 RGB
- 然后 4x4 RGB(验证 LZ77 引用)

每一步都通过后再放大。

**步骤 2:阶段验证**
在每个阶段加输出:
```rust
println!("magic: {:02x?}", magic_bytes);
println!("IHDR: {}x{}, ct={}, bd={}", width, height, color_type, bit_depth);
println!("IDAT collected: {} bytes", idat.len());
println!("zlib CMF={:02x} FLG={:02x}", cmf, flg);
println!("DEFLATE output: {} bytes", decompressed.len());
println!("First 16 filtered bytes: {:02x?}", &decompressed[..16.min(decompressed.len())]);
println!("Reconstructed first pixel: {:?}", &output[..bpp]);
```

每行解释:
- 每个阶段都打印关键信息,让你看到"进度"。
- 第一个不一致阶段就是 bug 所在。

**步骤 3:对比已知正确实现**

```bash
# 用 Python 创建测试 PNG
python3 -c "
from PIL import Image
img = Image.new('L', (1, 1), 128)  # 1x1 灰度,值 128
img.save('/tmp/min.png')
"

# 用 PIL 读取,打印每个像素
python3 -c "
from PIL import Image
img = Image.open('/tmp/min.png')
print('Size:', img.size)
print('Mode:', img.mode)
print('Pixels:', list(img.getdata()))
"

# 用 zlib dump 中间数据
python3 -c "
import zlib
with open('/tmp/min.png', 'rb') as f:
    data = f.read()
# 找 IDAT(简化)
idat_start = data.find(b'IDAT') + 4
idat_end = data.find(b'IEND') - 4
idat = data[idat_start:idat_end]
print(f'IDAT size: {len(idat)}')
decompressed = zlib.decompress(idat)
print(f'Decompressed: {len(decompressed)} bytes')
print(f'Hex: {decompressed.hex()}')
# 对 1x1 灰度:1 字节 filter type + 1 字节像素 = 2 字节
# 通常 [0, 128] (filter None + pixel 128)
"
```

**步骤 4:二分定位**

如果第一阶段都对、最后像素错,bug 在中间。在中间插 assert:
```rust
let stage1 = parse_magic(...);
let stage2 = parse_ihdr(...);
// 在这里加 assert,如果通过说明 1+2 对
let stage3 = deflate_decode(...);
// 再加 assert
let stage4 = reconstruct(...);
```

第一个失败的 assert 告诉你 bug 在哪个阶段。

### 常见 bug 和修复

**Bug 1:BitReader 顺序错**

```rust
// 错:MSB first
result |= (bit as u32) << (n - 1 - i);

// 对:LSB first(DEFLATE)
result |= (bit as u32) << i;
```

DEFLATE 用 LSB first,不是 MSB first(直觉相反)。这是 Day 455 容易写错的地方。

**Bug 2:Canonical Huffman 算法错**

RFC 1951 §3.2.2 算法:
```
1) bl_count[bits] = number of codes of that length
2) next_code[bits] = (next_code[bits-1] + bl_count[bits-1]) << 1
3) for each symbol in order: assign next_code[cl[sym]]++
```

错版本(忽略 bl_count[bits-1] 累加):
```rust
// 错
code = code << 1;
next_code[bits] = code;
```

对版本:
```rust
code = (code + bl_count[bits - 1]) << 1;
next_code[bits] = code;
```

**Bug 3:LZ77 引用展开顺序**

```rust
// 错(用 extend_from_within,不支持重叠)
output.extend_from_within(start..start+length);

// 对(逐字节,支持重叠)
for i in 0..length {
    let byte = output[start + i];
    output.push(byte);
}
```

**Bug 4:Paeth 边界**

```rust
// 错(忽略 i < bpp 时 a = 0)
let a = current[i - bpp] as i32;

// 对(行首 a = 0)
let a = if i >= bpp { current[i - bpp] as i32 } else { 0 };
```

**Bug 5:bpp 计算**

```rust
// 错(RGBA 算 5)
let bpp = match color_type {
    2 => 3, 6 => 5, _ => ...
};

// 对(RGBA = 4)
let bpp = match color_type {
    0 => 1,  // Gray 8-bit
    2 => 3,  // RGB
    4 => 2,  // Gray+Alpha
    6 => 4,  // RGBA
    _ => panic!(),
} * (bit_depth / 8) as usize;
```

注意 bit_depth 也影响 bpp:16-bit RGB bpp = 6,不是 3。

## 3 · 四域深入

### 3.1 · 游戏编程视角

调试是游戏开发的核心技能。游戏 bug 特点:

- **状态复杂**:游戏状态有几千字段,bug 复现难
- **时序敏感**:每帧 16ms,bug 可能在某帧特定输入触发
- **跨平台**:Windows / Linux / 主机行为不同

工业调试工具:
- **printf 大法**:简单,慢
- **Debugger**(gdb / lldb):断点,变量查看
- **Reverse debugging**(rr / WinDbg Time Travel):倒退执行,找根因
- **Replay**:确定性回放,重现 bug
- **Sanitizer**(ASAN/UBSAN/MSAN):内存错误检测

### 3.2 · 图形学视角

图形 bug 特点:
- **视觉症状明显**:花屏、白屏、闪烁
- **定位难**:看不出哪个 shader 错
- **数据量大**:百万像素,只看几行没用

图形调试工具:
- **RenderDoc**:截帧、像素归因(已在 Day 442 讲)
- **Shader printf**(GL_KHR_debug):shader 内输出
- **Visual shader debugger**:断点在 shader 中
- **Frame analysis**:对比帧差

PNG 解码的"花屏"在图形学里很常见——一个 bit 错可能让整张图错。

### 3.3 · Linux 系统编程视角

Linux 调试工具链:

```bash
# 1. gdb
gdb --args ./target/debug/png_decoder test.png
(gdb) b png_decoder::bit_reader::read_bits
(gdb) run
(gdb) bt  # backtrace

# 2. rr(record and replay)
sudo pacman -S rr

# 在 rr 里可以反向单步

# 3. valgrind(内存错误)

# 4. ASAN(address sanitizer)
RUSTFLAGS="-Zsanitizer=address" cargo +nightly build --target x86_64-unknown-linux-gnu
# ASAN 找内存越界、UAF

# 5. strace(系统调用)
strace -e read,open ./target/debug/png_decoder test.png

# 6. perf
perf record ./target/debug/png_decoder test.png
perf report
```

## 5 · 对照与变奏

**调试不同类型 bug**:

| Bug 类型 | 工具 |
|---|---|
| 内存越界 | valgrind / ASAN |
| 数据竞争 | ThreadSanitizer |
| 死锁 | helgrind |
| 浮点精度 | godbolt / 人工验证 |
| 二进制解析 | printf + 对比 |
| shader 花屏 | RenderDoc |

**调试心态**:
- 不要"猜 bug",要"找 bug"
- 先复现,再定位
- 假设代码有 bug,不是工具/编译器有 bug

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"对比已知正确实现"是二进制解析调试的关键?

**参考解答**:二进制解析的中间结果(位流、Huffman 码、LZ77 引用)人脑无法直接验证。但已知正确的实现(如 Python PIL、`image` crate)产生同样的中间结果。如果你的中间结果和它一致,说明你这一阶段对;不一致,bug 就在这一阶段。这把"理解二进制"问题转化为"二分查找"问题——线性降为对数。

## 8 · Rust / Arch 落地代码

### Rust 完整调试设置

```rust
// 在 PNG 解码器每个阶段加 debug 输出

fn debug_decode(path: &str) -> Result<(), String> {
    let data = std::fs::read(path).map_err(|e| e.to_string())?;
    println!("[debug] File size: {} bytes", data.len());

    // 阶段 1: magic
    if data.len() < 8 || data[..8] != [0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A] {
        return Err("Magic check failed".into());
    }
    println!("[debug] Magic OK");

    // 阶段 2: IHDR
    let length = u32::from_be_bytes([data[8], data[9], data[10], data[11]]) as usize;
    let ctype = &data[12..16];
    if ctype != b"IHDR" || length != 13 {
        return Err(format!("IHDR invalid: type={:?} length={}", ctype, length));
    }
    let width = u32::from_be_bytes([data[16], data[17], data[18], data[19]]);
    let height = u32::from_be_bytes([data[20], data[21], data[22], data[23]]);
    let bit_depth = data[24];
    let color_type = data[25];
    println!("[debug] IHDR: {}x{} bit_depth={} color_type={}", width, height, bit_depth, color_type);

    // 验证:对比 PIL 输出
    // $ python3 -c "from PIL import Image; img = Image.open(path); print(img.size, img.mode)"

    let bpp = match color_type {
        0 => 1, 2 => 3, 4 => 2, 6 => 4,
        _ => return Err(format!("Unsupported color_type {}", color_type)),
    } * (bit_depth / 8) as usize;
    println!("[debug] bpp = {}", bpp);

    // 阶段 3: 收集 IDAT
    let mut cursor = 8 + 4 + 4 + 13 + 4;  // magic + IHDR length + type + data + CRC
    let mut idat = Vec::new();
    loop {
        if cursor + 8 > data.len() { return Err("EOF before IEND".into()); }
        let len = u32::from_be_bytes([data[cursor], data[cursor+1], data[cursor+2], data[cursor+3]]) as usize;
        let t = &data[cursor+4..cursor+8];
        cursor += 8;
        if t == b"IDAT" {
            idat.extend_from_slice(&data[cursor..cursor+len]);
        } else if t == b"IEND" {
            break;
        }
        cursor += len + 4;
    }
    println!("[debug] IDAT collected: {} bytes", idat.len());

    // 阶段 4: zlib 头
    if idat.len() < 2 { return Err("IDAT too short".into()); }
    let cmf = idat[0];
    let flg = idat[1];
    let combined = ((cmf as u16) << 8) | (flg as u16);
    if combined % 31 != 0 {
        return Err(format!("zlib check: {} % 31 = {}", combined, combined % 31));
    }
    println!("[debug] zlib: CMF=0x{:02x} FLG=0x{:02x}", cmf, flg);

    // 阶段 5: DEFLATE 解压(简化:假设函数 deflate_decode 就位)
    // 这里用 flate2 作为参考
    let decompressed = {
        use std::io::Read;
        let mut d = flate2::read::ZlibDecoder::new(&idat[..]);
        let mut out = Vec::new();
        d.read_to_end(&mut out).map_err(|e| e.to_string())?;
        out
    };
    println!("[debug] Decompressed: {} bytes", decompressed.len());
    let expected = (width as usize + 1) * height as usize * bpp;  // 每行 +1 字节 filter
    println!("[debug] Expected: {} bytes (height={}, row_stride={}, bpp={})",
        expected, height, width as usize + 1, bpp);
    if decompressed.len() != expected {
        return Err(format!("Size mismatch: got {}, expected {}", decompressed.len(), expected));
    }
    println!("[debug] First 16 bytes: {:02x?}", &decompressed[..16.min(decompressed.len())]);

    // 阶段 6: 反滤镜(reconstruct_image,见 day457)
    // let pixels = reconstruct_image(&decompressed, width as usize, height as usize, bpp)?;
    // println!("[debug] First pixel: {:02x?}", &pixels[..bpp]);

    println!("[debug] Decoding succeeded");
    Ok(())
}

fn main() {
    let args: Vec<_> = std::env::args().collect();
    if let Err(e) = debug_decode(args.get(1).unwrap_or(&"/tmp/min.png".to_string())) {
        println!("[ERROR] {}", e);
        std::process::exit(1);
    }
}
```

每行解释:
- 每阶段加 `println!("[debug] ...")`,带前缀,容易扫描。
- 每阶段失败立即返回,不停继续。
- 用 `flate2` 作为 DEFLATE 参考实现,跳过自己手写 DEFLATE 的潜在 bug。
- 预期大小 = `(width + 1) * height * bpp`(每行 +1 字节 filter type)。

### Arch Linux 工具链

```bash
# 1. 准备测试 PNG
python3 -c "
from PIL import Image
img = Image.new('L', (1, 1), 128)
img.save('/tmp/min.png')
"

# 2. 用 Python 看所有中间步骤
python3 << 'EOF'
import zlib
import struct
with open('/tmp/min.png', 'rb') as f:
    data = f.read()
print(f'File size: {len(data)}')
print(f'Magic: {data[:8].hex()}')
print(f'IHDR len: {struct.unpack(">I", data[8:12])[0]}')
print(f'IHDR type: {data[12:16]}')
print(f'Width: {struct.unpack(">I", data[16:20])[0]}')
print(f'Height: {struct.unpack(">I", data[20:24])[0]}')
print(f'Bit depth: {data[24]}')
print(f'Color type: {data[25]}')

# IDAT
cursor = 8 + 4 + 4 + 13 + 4
idat = b''
while True:
    length = struct.unpack('>I', data[cursor:cursor+4])[0]
    ctype = data[cursor+4:cursor+8]
    cursor += 8
    if ctype == b'IDAT':
        idat += data[cursor:cursor+length]
    elif ctype == b'IEND':
        break
    cursor += length + 4

print(f'IDAT: {len(idat)} bytes')
print(f'zlib CMF: 0x{idat[0]:02x}')
print(f'zlib FLG: 0x{idat[1]:02x}')

decompressed = zlib.decompress(idat)
print(f'Decompressed: {len(decompressed)} bytes')
print(f'Hex: {decompressed.hex()}')
EOF

# 3. 用 gdb 调试你的解码器
gdb --args ./target/debug/png_decoder /tmp/min.png
(gdb) break debug_decode
(gdb) run
(gdb) next  # 单步
(gdb) print data.len()
(gdb) continue

# 4. 用 rr 反向调试(找难 bug)
sudo pacman -S rr
rr record ./target/debug/png_decoder /tmp/min.png
rr replay
(rr) break png_decoder::reconstruct_row
(rr) continue
(rr) reverse-step  # 反向!

# 5. 用 valgrind 找内存问题
valgrind --tool=memcheck ./target/debug/png_decoder /tmp/min.png
```

**Troubleshooting**:
- Decompressed 大小不对 → 检查 row_stride 公式
- zlib 校验失败 → 检查 IDAT 收集是否漏字节
- 像素花屏 → 滤镜 bpp 错或 Paeth 边界错
