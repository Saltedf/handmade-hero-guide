# Day 559 · 实验片段光采样

> 之前光探针查询在 vertex shader(每顶点一次,3 个顶点插值到整个三角形)。Day 559 Casey 把查询**移到 fragment shader**——每像素独立查 voxel grid,光照细节更准。这是 day553 cosine-weighted sampling 的具体应用。

## 0 · 为什么要有这一天

让我们把镜头贴近画面,看到这两种渲染路径的实际差别。你跟着 Handmade Hero 走到 Day 558——Casey 的 voxel 光探针在 vertex shader 里查询,每个 mesh 的每个顶点采一次。你跑游戏,看一面**大墙**——这面墙可能只有 2 个三角形(四边形),所以只在 4 个顶点(角落)采了 voxel 光照,GPU 把这 4 个顶点的颜色**线性插值**到整面墙。结果:**墙中央的"亮斑"看不到**。如果光源打在墙的正中央,顶点(角落)采到的是暗的,插值后整面墙是均匀暗色——光斑消失了。

这就是 **per-vertex lighting(Gouraud shading)** 的根本限制——它在三角形内部做线性插值,**捕捉不到比三角形小的光照细节**。三角形越大,丢失细节越多。Gouraud shading 适合低多边形(low-poly)美学——Quake 1、PS1 时代游戏的"塑料感"就是这个原因。

**Per-pixel lighting(Phong shading)** 把查询移到 fragment shader——每个像素独立查 voxel,每个像素独立计算光照。墙中央的像素采到墙中央的 voxel,看见亮斑。1080p 屏幕有 200 万像素,每像素独立算——光照细节精确到 1 像素,高光清晰,阴影边界锐利。

**为什么之前用 per-vertex?**性能。每顶点 1 次查询 vs 每像素 1 次查询,像素是顶点的 1000 倍数量(典型 mesh 1 万顶点,1080p 屏 200 万像素,200 倍)。但现代 GPU 算力够,per-pixel 是标配,只有 LOD 远景用 per-vertex。

为什么这一天叫"实验"?因为它不是确定的迁移,Casey 在试:per-pixel 在 voxel probe 系统上效果如何,值不值得性能代价。如果太慢,可能保留 per-vertex,或者只在某些 mesh 上用 per-pixel。

完成这一天之后,你具备:

- 理解 per-vertex(Gouraud)vs per-pixel(Phong)shading 的根本区别——为什么 Gouraud 是"低通"而 Phong 不是
- 能在 fragment shader 实现 voxel probe 查询,理解每像素一次 texture fetch 的 GPU cache 影响
- 知道 query frequency(查询频率)对视觉细节的影响——三角形大小决定 Gouraud 的有效分辨率
- 在 WGSL/GLSL 里手写 per-pixel voxel 查询和 BRDF 组合,理解 normal mapping 为什么必须 per-pixel

## 2 · 心智模型

### 2.1 类比:油画 vs 喷漆

**Per-vertex shading** 像油画——画家在画布几个关键点(顶点)调色,其他地方用刷子抹开(线性插值)。抹出的渐变平滑但缺细节,大块面感觉"模糊"。**关键限制**:细节只能出现在"调色点"附近——如果你想在画布中央加一个亮点,中央没有调色点,亮点的颜色是从周围调色点插值来的,会被稀释。

**Per-pixel shading** 像喷漆——每个像素独立喷色,细节精确到 1 像素。可以画出尖锐的高光、清晰的阴影边界。**没有"调色点"概念**——每个像素都是独立的颜色源。代价:喷得慢。

游戏史上的对比很直观:**Quake 3**(1999,per-vertex)的角色模型光照"塑料感"重,因为顶点少(500-1000 个),高光只能出现在顶点附近。**Doom 3**(2004,per-pixel)的角色光照"真实",因为每像素独立算 normal map——角色表面有几千像素的细节,normal map 让每像素的"朝向"不同,光照计算用每像素的 normal。

为什么 Doom 3 转 per-pixel?**因为 normal mapping**。normal map 是一张"每像素的法线方向"贴图,如果光照是 per-vertex,normal map 没用(顶点光照不读 normal map)。normal mapping 必须 per-pixel。这是 GPU 时代(2002+)per-pixel shading 普及的根本驱动力。

### 2.2 严谨展开:per-vertex vs per-pixel in shader

让我把两种 shader 写出来对比,你会看到 GPU 管线在哪里不同。

**Per-vertex**(Gouraud):

```glsl
// vertex shader
in vec3 world_pos;
out vec3 v_light_color;  // 输出到 fragment

void main() {
    vec3 voxel = texture(voxel_grid, world_pos / voxel_size).rgb;
    v_light_color = surface_color * voxel;
    gl_Position = ...;
}

// fragment shader
in vec3 v_light_color;
out vec4 frag_color;

void main() {
    frag_color = vec4(v_light_color, 1.0);  // 直接用插值结果
}
```

注意 `v_light_color` 是 vertex shader 算的,GPU 在 fragment shader 之前对它做**重心坐标插值**(barycentric interpolation)——三角形内部每个像素的颜色 = 三个顶点颜色的加权和。**这就是"细节丢失"的根源**——插值是线性操作,无法重建出顶点之间的高频变化。

**Per-pixel**(Phong):

```glsl
// vertex shader
out vec3 v_world_pos;
out vec3 v_normal;

void main() {
    v_world_pos = world_pos;
    v_normal = normal;
    gl_Position = ...;
}

// fragment shader
in vec3 v_world_pos;
in vec3 v_normal;
out vec4 frag_color;

void main() {
    vec3 voxel = texture(voxel_grid, v_world_pos / voxel_size).rgb;
    vec3 normal = normalize(v_normal);
    vec3 final_color = surface_color * voxel * dot(normal, light_dir);
    frag_color = vec4(final_color, 1.0);
}
```

关键差别:**fragment shader 里**调用 `texture(voxel_grid, ...)`——每像素一次 voxel texture fetch。三角形内部的每个像素根据自己的 `v_world_pos`(插值得到的世界坐标)独立采样 voxel grid。

### 2.3 Voxel fetch 的 cache 命中:为什么 per-pixel 不是慢 1000 倍

理论上 per-pixel 比 per-vertex 多 1000 倍 voxel 查询,实际只慢 3-10 倍。**为什么?GPU cache 友好**。

GPU 的 L1 texture cache 是 2D/3D 空间分块——一个 cache line 覆盖 voxel grid 的一小块(如 8x8x8 voxel)。fragment shader 处理像素是**空间连续**的——相邻像素的 world_pos 接近,它们采的 voxel 接近,大概率在同一个 cache line。所以第一个像素 miss cache(从显存加载 8x8x8 voxel 块),后续 63 个像素命中 cache。

具体数学:1080p 屏 200 万像素,voxel texture fetch 每像素 trilinear 8 voxel,总 fetch 1600 万次。但 cache 命中率 90%+,实际显存访问 160 万次。**vs per-vertex 1 万顶点 * 8 fetch = 8 万次**,差距 20 倍而非 200 倍。

实测:per-pixel voxel fetch 比 per-vertex 慢 3-10 倍,不是 1000 倍。这就是为什么工业 GI 都用 per-pixel——视觉质量是质变,性能代价可承受。

**进一步优化**:per-pixel voxel fetch 可以用 `textureGather`(一次取 4 邻居)减少调用次数,或者用 bindless texture 减少 binding 开销。GPU 还有 texture L2 cache(更大,8-32 MB),热数据共享更好。

### 2.4 Cosine-weighted sampling 应用

Day 553 学的 cosine-weighted sampling 在 per-pixel voxel 查询里发挥重要作用。**单点采样不够**——一个像素的世界坐标对应一个 voxel,但这个像素**朝某方向**接收的光来自整个半球。要做"半球积分"——从该像素沿 normal 半球射 N 条 ray,每条 ray 查 voxel 累加光。

```glsl
// fragment shader
uniform sampler3D voxel_grid;
uniform vec3 sample_dirs[64];  // cosine-weighted 采样方向

vec3 compute_irradiance(vec3 world_pos, vec3 normal) {
    vec3 sum = vec3(0);
    mat3 tbn = build_tangent_space(normal);
    for (int i = 0; i < 64; i++) {
        vec3 dir = tbn * sample_dirs[i];  // 转到世界坐标
        // ray march:沿 dir 走,累加 voxel 光照(被墙衰减)
        vec3 hit = ray_march(world_pos, dir);
        sum += hit;
    }
    return sum / 64.0;
}
```

`ray_march` 沿方向走,每步查 voxel,如果 voxel occupied 就停(墙挡光),否则累加 voxel 光照。**cosine-weighted** 让靠近 normal 的方向采样更多(对光照贡献大),偏离 normal 的方向采样少(贡献小)——这比均匀采样收敛快 3-5 倍(同样 64 个样本,误差更小)。

这就是 Day 553 cosine-weighted + Day 559 per-pixel 的组合威力——每像素 64 个 ray,每个 ray 走 voxel grid,累加得到该像素的精确 irradiance。代价是 fragment shader 复杂度上升 64 倍,但 GPU 并行能掩盖这个代价。

### 2.5 性能 vs 质量的工程权衡

Casey 在视频里承认 per-pixel 让 GPU 时间增加 30%,但视觉效果是"质变"。**这是工业图形程序员每天都面对的权衡**。

具体数字:1080p 60 FPS 的 frame budget 是 16.6 ms。如果 fragment shader 每像素 100 ns,200 万像素 = 200 ms 总 GPU 时间(单 SM)—— 实际 GPU 有几千 SM 并行,降到几 ms。per-pixel voxel fetch 让 fragment shader 慢 30% 意味着 GPU 时间从 4 ms 涨到 5.2 ms,frame budget 还剩 11 ms,绰绰有余。

但如果场景复杂(pixel overdraw 高,多个透明 mesh 叠加),per-pixel 可能撑爆 frame budget。优化方向:
- **降低 voxel 查询频率**:某些 mesh(小、远)仍用 per-vertex,大 mesh 用 per-pixel
- **降低 ray 数**:从 64 ray 降到 32 ray,空间时间滤波器(spatial filter)平滑噪声
- **Voxel LOD**:远处用低分辨率 voxel grid,query 更便宜
- **Asynchronous compute**:voxel ray march 在 async compute queue,不阻塞 graphics queue

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

per-pixel shading 在现代游戏里的工业应用远不止 voxel GI:

**Normal mapping(法线贴图)**:每像素从 normal map 读"微细节法线"——一张 1024x1024 的法线贴图能让低多边形模型(1000 三角形)看起来像高多边形(100 万三角形)。这是 PS3/Xbox 360 时代 per-pixel shading 普及的根本原因——给美术"假细节"的能力。Doom 3、Half-Life 2、Gears of War 都重度使用。

**Parallax mapping(视差贴图)**:每像素从 height map 算"虚拟位移"——表面看起来有凹凸感,但实际几何没变。比 normal mapping 更强,但贵——每像素多次 texture fetch(沿 view ray 步进)。**Steep parallax mapping** 和 **parallax occlusion mapping(POM)** 是变体,质量更高。

**Screen-space reflections(SSR)**:每像素 raycast 屏幕空间——反射看到的是当前帧的 color buffer,不是真实环境。Cyberpunk 2077、Control 的"湿润地板反光"是 SSR。每像素一次 raycast,ray step 数 16-64,贵但效果好。SSR 的限制是"屏幕外的东西反射不到"——所以和 planar reflection(渲染两次)组合。

**Voxel GI(本仓库主题)**:每像素从 voxel probe 采——比 SSR 多一层抽象(voxel grid 是世界的 3D 表示,不是屏幕 2D)。光线追踪能力更强(可看屏幕外),但 voxel 分辨率有限。Casey 在做这一类。

**Ray-traced shading(DXR / RTX)**:每像素 trace 真实光线,撞场景几何(mesh)。Minecraft RTX、Cyberpunk 2077 RT Overdrive 用这个。质量最高(物理正确反射、折射、阴影),但每像素多帧光线 trace,需要 RT core 硬件加速。**未来方向**——RTX 4090 上 60 FPS 全 RT 是可能的。

现代游戏几乎所有光照都是 per-pixel(per-vertex 只在 LOD 远景用——远处模型顶点少,per-vertex 节省 GPU 时间给近处 mesh)。

### 3.2 · 🎨 图形学视角

per-pixel shading 是 **Phong interpolation**(Phong Bui Tuong 1975)提出。在那之前 Gouraud shading(Henri Gouraud 1971)是 per-vertex,因为便宜。**两者的核心差别**:

- **Gouraud**:在顶点算 `color = brdf(normal, light)`,三角形内部**线性插值 color**。这是**信号处理的低通滤波**——三角形大小是 filter size,大三角形丢高频。
- **Phong**:在顶点传递 `normal`,三角形内部**线性插值 normal**(再 normalize),fragment shader 算 `color = brdf(normal, light)`。**插值 normal 而非 color**——normal 是低频信号(表面平滑变化),插值 normal 不丢信息;`brdf(normal, light)` 可能产生高频(specular 高光),保留高频。这就是 Phong 比 Gouraud 质量高的数学根源。

GPU 早期(2000-2005)per-pixel 贵,Pixel Shader 1.0-2.0 限制多。**2003 年 Shader Model 3.0** 后 fragment shader 强大,per-pixel 成为标配。

Voxel GI 的 per-pixel 查询有几种 filter:

- **Trilinear**:8 邻居线性插值,基础。Casey 当前用这个。
- **Tricubic**(Day 564 学过):64 邻居三次插值,质量高但贵 8 倍
- **Cone tracing**(Crassin 2011):沿圆锥方向采样,模拟 soft shadow——圆锥半径随距离扩大,采多个 voxel 平均
- **Ray march**:沿射线步进,精确——撞墙算 shadow,不撞算 light

Casey 用 trilinear,后面 day572+ 加 ray march。

### 3.3 · 🐧 Linux 系统编程视角

"per-element vs per-batch"是系统设计的通用权衡模式,深入理解它有助于你看穿很多架构:

**CPU SIMD**:标量代码每指令处理 1 个元素(per-element),AVX2 SIMD 一次处理 8 个 float(per-batch 的反向——batch 是 SIMD lane)。SIMD 让 per-element 变快,但仍保持 per-element 的精度。**类比 Gouraud**:SIMD 把多个 element 打包,但仍独立处理。

**Network packet processing**:Linux 内核协议栈每包独立处理(每包一次 netfilter、路由查找),XDP / DPDK 让每包 bypass 内核直接用户态处理。**性能 trade-off**:XDP 快但失去 netfilter 灵活性。**类比 per-vertex vs per-pixel**:per-vertex 灵活度低(顶点光照),per-pixel 灵活度高(每像素独立)。

**GPU compute**:GPU 每线程独立算(per-element 视角),但 warp/wavefront 让 32/64 线程同步执行(per-batch 视角)。shader 编程是 per-element 写法,SIMT 硬件做 per-batch 执行——程序员抽象 vs 硬件实现的鸿沟。

**文件系统 block size**:4KB block(默认)适合小文件(per-element 颗粒),1MB huge block 适合大视频(per-batch 颗粒)。trade-off:小 block 灵活但 metadata 多,大 block 节省 metadata 但浪费空间(internal fragmentation)。**类比 Gouraud**:大三角形(大 block)省 metadata 但丢细节;小三角形(小 block)细节好但 metadata 多。

**Database row vs column store**:row store 每行连续(per-entity),column store 每列连续(per-attribute batch)。OLTP(每行事务)用 row,OLAP(每列聚合)用 column。**类比**:per-pixel vs per-vertex——取决于查询模式。

性能 trade-off 一致:**per-element 准确但贵,per-batch 快但失细节**。Casey 的 per-pixel 是选了 per-element 的准确性,接受 30% 性能代价。

### 3.4 · 🦀 Rust 生态视角

Rust + WGSL fragment shader 是工业 wgpu 项目的标配。让我把 Rust 端和 shader 端代码完整展示:

Rust 端准备 uniform 和 bind group:

```rust
// Rust 端准备 uniform
let voxel_bind_group = device.create_bind_group(&wgpu::BindGroupDescriptor {
    layout: &voxel_layout,
    entries: &[
        wgpu::BindGroupEntry {
            binding: 0,
            resource: wgpu::BindingResource::TextureView(&voxel_texture_view),
        },
        wgpu::BindGroupEntry {
            binding: 1,
            resource: wgpu::BindingResource::Sampler(&linear_sampler),
        },
    ],
    label: None,
});
```

WGSL fragment shader 端:

```wgsl
// fragment shader
@group(0) @binding(0) var voxel_tex: texture_3d<f32>;
@group(0) @binding(1) var voxel_sampler: sampler;

@fragment
fn fs_main(
    @location(0) world_pos: vec3<f32>,
    @location(1) normal: vec3<f32>,
) -> @location(0) vec4<f32> {
    let voxel_coord = world_pos / voxel_size;
    let voxel_color = textureSample(voxel_tex, voxel_sampler, voxel_coord);
    let n = normalize(normal);
    let ndl = max(dot(n, vec3(0.0, 1.0, 0.0)), 0.0);  // 假设光源向上
    return vec4(surface_color * voxel_color.rgb * ndl, 1.0);
}
```

**Rust + wgpu 的 voxel probe 系统架构**:
- `wgpu::Texture3D` 存 voxel grid(R32G32B32A32Float 格式,RGB 存光照,alpha 存 flags)
- fragment shader `textureSample` 采 trilinear,wgpu 自动配 LINEAR_MIPMAP_LINEAR
- `compute_pass` 每帧更新 voxel grid(光源移动后)

**Rust 图形生态的 per-pixel voxel GI 实现**:
- `bevy_voxel_world`:Bevy 的 voxel world plugin,per-pixel lighting
- `rend3`:wgpu 上的渲染库,支持 voxel GI
- `wgpu::trace` feature:GPU trace,可以 profile per-pixel shader

**Rust 性能分析**:用 `wgpu::util::DeviceExt` 和 `RenderPass::insert_debug_marker` 给 GPU 命令打标签,然后用 RenderDoc 或 PIX 查看每段 GPU 时间。per-pixel voxel fetch 通常占 5-15% GPU frame——可控。

### Lv1 · 概念辨析

**题**:per-pixel 比 per-vertex 慢多少?为什么 GPU cache 能缓解?

**参考解答**:朴素估算:per-vertex 每三角形 3 次查询,per-pixel 每像素 1 次。1080p 每帧 2M 像素,三角形 5M(覆盖屏幕,平均 0.4 像素/三角形),所以 per-vertex 5M * 3 = 15M 查询 vs per-pixel 2M 查询——其实 per-pixel 可能更少(三角形多但每三角形少像素)?不对,per-vertex 是每三角形 3 顶点(共享),unique 顶点数约 1M;per-pixel 是每像素,2M。所以 per-pixel 多 2 倍。但 cache 命中让 per-pixel 实际只多 3-10 倍 cache miss,而非 1000 倍——因为相邻像素查的 voxel 邻近,共享 cache line。

### Lv2 · 动手实践

**题**:CPU 模拟 per-vertex vs per-pixel voxel sampling 的差异。

要求:
- 一个 4x4 voxel grid,内容 `[i+j+k] mod 4 / 4.0` 的浮点值
- 一个 100x100 像素的 quad,4 个顶点
- Per-vertex:4 顶点查 voxel,像素线性插值
- Per-pixel:每个像素独立查 voxel
- 对比两种结果,找出 per-vertex 漏掉的细节

**参考解答**:

```rust
fn voxel_value(grid: &[[[f32; 4]; 4]; 4], x: f32, y: f32, z: f32) -> f32 {
    let i = x.floor() as usize;
    let j = y.floor() as usize;
    let k = z.floor() as usize;
    let i = i.min(3); let j = j.min(3); let k = k.min(3);
    grid[k][j][i]
}

fn lerp(a: f32, b: f32, t: f32) -> f32 { a + (b - a) * t }

fn bilinear(a: f32, b: f32, c: f32, d: f32, tx: f32, ty: f32) -> f32 {
    lerp(lerp(a, b, tx), lerp(c, d, tx), ty)
}

fn main() {
    // 创建 voxel grid
    let mut grid = [[[0.0f32; 4]; 4]; 4];
    for k in 0..4 { for j in 0..4 { for i in 0..4 {
        grid[k][j][i] = ((i + j + k) % 4) as f32 / 4.0;
    }}}

    let quad_corners = [(0.5, 0.5), (3.5, 0.5), (3.5, 3.5), (0.5, 3.5)];
    let y_layer = 1;  // 看 y=1 这层

    // Per-vertex: 4 个角各查一次
    let corners_v = quad_corners.map(|(x, _)| {
        voxel_value(&grid, x as f32, y_layer as f32, 0.0)
    });

    // Per-pixel:每个像素查
    let mut per_pixel_image = vec![0.0; 100 * 100];
    for py in 0..100 {
        for px in 0..100 {
            let x = 0.5 + 3.0 * (px as f32 / 100.0);
            let z = 0.5 + 3.0 * (py as f32 / 100.0);
            per_pixel_image[py * 100 + px] = voxel_value(&grid, x, y_layer as f32, z);
        }
    }

    // Per-vertex 插值
    let mut per_vertex_image = vec![0.0; 100 * 100];
    for py in 0..100 {
        for px in 0..100 {
            let u = px as f32 / 100.0;
            let v = py as f32 / 100.0;
            let c = bilinear(corners_v[0], corners_v[1], corners_v[3], corners_v[2], u, v);
            per_vertex_image[py * 100 + px] = c;
        }
    }

    // 对比 4 个像素
    for (px, py) in [(10, 10), (50, 50), (90, 90), (50, 10)] {
        println!("({},{}): per-pixel={:.3}, per-vertex={:.3}",
            px, py,
            per_pixel_image[py * 100 + px],
            per_vertex_image[py * 100 + px]);
    }
}
```

per-vertex 全是同色(因为 4 个角查询值相同),per-pixel 有细节差异——这就是 Gouraud 失真的来源。

### Lv3 · 迁移设计

**题**:音频也有"per-sample vs per-block"处理。EQ 滤波器可以:

- Per-sample:每样本独立算 `y[n] = b0*x[n] + b1*x[n-1] - a1*y[n-1]`(IIR)
- Per-block(FFT):N 个样本一起 FFT,频域滤波,IFFT

请对比两种的性能和精度,什么场景用哪种?

**提示**:FFT per-block O(N log N) 但常数大,N > 1024 才划算。Per-sample O(N) 但每样本独立。

// 一个简化 voxel probe grid
struct VoxelGrid {
    data: Vec<[f32; 3]>,  // RGB 光照
    dim: [usize; 3],
}

impl VoxelGrid {
    fn new(dim: [usize; 3]) -> Self {
        let mut g = VoxelGrid {
            data: vec![[0.0; 3]; dim[0]*dim[1]*dim[2]],
            dim,
        };
        // 放一个虚拟光源
        g.set(8, 8, 8, [1.0, 0.8, 0.6]);
        g
    }
    fn idx(&self, i: usize, j: usize, k: usize) -> usize {
        (k * self.dim[1] + j) * self.dim[0] + i
    }
    fn set(&mut self, i: usize, j: usize, k: usize, c: [f32; 3]) {
        if i < self.dim[0] && j < self.dim[1] && k < self.dim[2] {
            self.data[self.idx(i, j, k)] = c;
        }
    }
    fn sample_trilinear(&self, x: f32, y: f32, z: f32) -> [f32; 3] {
        let i = x.floor() as usize;
        let j = y.floor() as usize;
        let k = z.floor() as usize;
        let fx = x - i as f32;
        let fy = y - j as f32;
        let fz = z - k as f32;
        let corners: [[f32; 3]; 8] = [
            *self.data.get(self.idx(i, j, k)).unwrap_or(&[0.0; 3]),
            *self.data.get(self.idx(i+1, j, k)).unwrap_or(&[0.0; 3]),
            *self.data.get(self.idx(i, j+1, k)).unwrap_or(&[0.0; 3]),
            *self.data.get(self.idx(i+1, j+1, k)).unwrap_or(&[0.0; 3]),
            *self.data.get(self.idx(i, j, k+1)).unwrap_or(&[0.0; 3]),
            *self.data.get(self.idx(i+1, j, k+1)).unwrap_or(&[0.0; 3]),
            *self.data.get(self.idx(i, j+1, k+1)).unwrap_or(&[0.0; 3]),
            *self.data.get(self.idx(i+1, j+1, k+1)).unwrap_or(&[0.0; 3]),
        ];
        let lerp3 = |a: [f32; 3], b: [f32; 3], t: f32| -> [f32; 3] {
            [a[0]+(b[0]-a[0])*t, a[1]+(b[1]-a[1])*t, a[2]+(b[2]-a[2])*t]
        };

        let c00 = lerp3(corners[0], corners[1], fx);
        let c10 = lerp3(corners[2], corners[3], fx);
        let c01 = lerp3(corners[4], corners[5], fx);
        let c11 = lerp3(corners[6], corners[7], fx);

        let c0 = lerp3(c00, c10, fy);
        let c1 = lerp3(c01, c11, fy);
        lerp3(c0, c1, fz)
    }
}

// 一个"像素"片段
struct Fragment {
    world_pos: [f32; 3],
    normal: [f32; 3],
}

// Per-pixel fragment light
fn per_pixel_light(grid: &VoxelGrid, frag: &Fragment, surface_color: [f32; 3]) -> [f32; 3] {
    let voxel_color = grid.sample_trilinear(
        frag.world_pos[0],
        frag.world_pos[1],
        frag.world_pos[2],
    );
    // Lambertian: dot(normal, up)
    let ndl = frag.normal[1].max(0.0);  // 假设光来自上方
    [
        surface_color[0] * voxel_color[0] * ndl,
        surface_color[1] * voxel_color[1] * ndl,
        surface_color[2] * voxel_color[2] * ndl,
    ]
}

fn main() {
    let grid = VoxelGrid::new([16, 16, 16]);

    // 一组像素(模拟一个三角形的 fragments)
    let fragments: Vec<Fragment> = (0..100).map(|i| {
        let t = i as f32 / 100.0;
        Fragment {
            world_pos: [7.0 + t * 2.0, 8.0, 8.0],
            normal: [0.0, 1.0, 0.0],
        }
    }).collect();

    let surface = [0.8, 0.8, 0.8];

    for (i, f) in fragments.iter().enumerate() {
        if i % 25 == 0 {
            let c = per_pixel_light(&grid, f, surface);
            println!("Pixel {}: pos={:?} color=({:.3}, {:.3}, {:.3})",
                i, f.world_pos, c[0], c[1], c[2]);
        }
    }
}
