# Day 542 · 精确绘制内存占用

> Day 541 你画了 arena 时间线,但显示的是"每个 bump 的连续 offset"。实际内存使用更复杂:某些 bump 有 alignment padding(对齐填充),某些被 free 产生 hole(arena 一般不 free,但 sub-arena 可能)。Day 542 修复这些细节,**精确**画内存占用。

## 0 · 为什么要有这一天

之前的可视化假设内存是连续 bump,但实际有:

- **Alignment padding**:每次 alloc 需要 8/16 字节对齐,如果上次 bump 不在 8 字节边界,中间有"空白"
- **Sub-arena**(嵌套 arena):大 arena 内部开小 arena,小 arena 的 offset 不一定和大 arena 对齐
- **Free**(部分 arena 支持):某些 arena 支持 per-block free,产生 hole

#### Alignment:为什么内存需要"对齐"

让我把"内存对齐"讲清楚,因为它是 Day 542 的核心概念,也是系统编程的基础知识。

CPU 读内存不是按字节的,而是按"字"(word)读——32 位 CPU 一次读 4 字节,64 位一次读 8 字节。如果一个 4 字节 int 跨越字边界(比如从 byte 2 开始,占 byte 2-5),CPU 要读两次再拼接,慢一倍。所以编译器把数据"对齐"到边界——int 放在 4 的倍数地址。

对齐规则:

- `u8` / `i8`:1 字节对齐(任意地址)
- `u16` / `i16`:2 字节对齐(偶数地址)
- `u32` / `i32` / `f32`:4 字节对齐
- `u64` / `i64` / `f64` / 指针(64 位):8 字节对齐
- SIMD(`__m128`、`__m256`):16/32 字节对齐

Rust 的 `std::mem::align_of::<T>()` 返回类型的对齐要求。

Arena 在 alloc 时必须考虑对齐。Casey 的代码:

```rust
let aligned_offset = (self.offset + align - 1) & !(align - 1);
```

这是经典的"向上对齐"公式。例:`offset = 5`, `align = 4`:
- `(5 + 4 - 1) & !(4 - 1)` = `8 & !3` = `8 & 0xFFFFFFFC` = `8`
- aligned to 8 ✓

如果 offset 已经对齐(如 8),公式给出 8,无 padding。如果 offset 是 5,padding 是 3 字节。

工业级 arena 都用这个公式。Casey 在 Day 541 简化忽略了对齐,Day 542 修复——精确显示 padding 部分。

#### 对齐 padding 的可视化

精确绘制时,每个 bump 段显示:

```
arena layout:
[entity 100B][padding 4B][render 5KB][padding 12B][texture 200KB]...
```

每个 padding 段用不同颜色(灰色),让你看到"对齐浪费多少"。

工业级实践:

- 小数据频繁 alloc,padding 累积可能占 5-10% 内存
- 大数据 alloc,padding 比例小
- 优化:把同类型小对象打包(`SoA` 布局),减少 padding

#### Sub-arena:嵌套 arena

工业级游戏引擎经常"嵌套 arena":

```rust
// 大 arena 用于整帧
let frame_arena = Arena::new(64 * MB);

// 帧内某个子系统开 sub-arena
{
    let physics_arena = frame_arena.sub_arena(8 * MB);
    // physics_arena 在 frame_arena 内部占用 8 MB
    // physics_arena 内部又有自己的 offset
}
// sub-arena 离开作用域,frame_arena "释放"那 8 MB?不,frame_arena 不知道
```

问题:sub-arena 怎么"释放"内存?答案:**frame_arena 不释放**,但 sub-arena 离开作用域后,frame_arena 可以"截断"到 sub_arena 之前的位置。

这种"嵌套生命周期"的可视化:在 arena 时间线上画嵌套区域,标注 sub-arena 范围。

工业级例子:Unity 的 NativeUnsafeList 内部用 frame allocator 的 sub-arena。

#### Free 的复杂度

部分 arena(如 `bumpalo`)支持 `free`,但实现复杂。最简单:`Arena::free(ptr)` 标记"这块内存可复用",下次 alloc 同大小时优先填回 free 出来的 hole。

这种"free list"在可视化上产生 hole——内存图变得"瑞士奶酪",不再连续。Casey 在 Day 542 处理这种复杂情况。

完成这一天之后,你具备:

- 理解内存对齐的原理
- 能画精确的内存布局(含 padding)
- 知道 sub-arena 和 free list 的可视化挑战
- 能优化 arena 使用(减少 padding)

如果可视化忽略这些,会误导——你以为 arena 用了 100%,实际有 20% 是 padding。

精确绘制的目标:每个字节的状态明确——**已用**、**padding**(对齐填充)、**hole**(释放)、**free**(未分配)。

工业级内存分析工具(Vulkan Memory Allocator、 Tracy、mimalloc)都精确显示这些状态,让优化有依据。

## 2 · 心智模型

### 类比:停车场的设计

停车场每个车位 5 米长。如果车有 4 米,剩 1 米是"padding"。如果车有 3 米,剩 2 米 padding。如果车刚好 5 米,没 padding。

如果停车场全停 4 米车(1 米 padding),实际利用 80%。改车位 4 米长,padding 消失,利用 100%。这就是对齐优化的本质——**让容器尺寸匹配内容**。

### 严谨展开:对齐 padding

alloc 时,如果 offset 不在 align 边界,需要前推到下一个 align 边界。前推的字节数是 padding。

```rust
fn aligned_offset(offset: usize, align: usize) -> (usize, usize) {
    let mask = align - 1;
    let aligned = (offset + mask) & !mask;
    let padding = aligned - offset;
    (aligned, padding)
}

fn test() {
    let (off, pad) = aligned_offset(5, 8);   // 5 → 8, padding 3
    let (off, pad) = aligned_offset(8, 8);   // 8 → 8, padding 0
    let (off, pad) = aligned_offset(9, 16);  // 9 → 16, padding 7
}
```

#### 这个对齐公式的"位运算魔法"

让我把 `(offset + align - 1) & !(align - 1)` 的位运算原理讲清楚,因为它是系统编程的经典 idiom。

`align` 必须是 2 的幂(2, 4, 8, 16, ...)。这保证 align - 1 是"全 1 低 n 位",如 align=8: `0b1000`, align-1 = `0b0111`。

`!(align - 1)` 是"清掉低 n 位的 mask"。如 !0b0111 = `0b...11111000`。

`& !(align - 1)` 把 offset 的低 n 位清零,**向下**取整到 align 边界。

`+ (align - 1)` 先加 align-1,如果 offset 不是 align 倍数,加上 align-1 后必然进位到下一个 align 倍数。

合起来:`(offset + align - 1) & !(align - 1)` 是**向上**取整到 align 倍数。

为什么用位运算不用除法?**位运算快 5-10 倍**(CPU 单 cycle vs division 多 cycle)。系统编程的"快路径"全用位运算。

#### Sub-arena 的实现

```rust
impl Arena {
    fn sub_arena(&mut self, size: usize) -> SubArena {
        let (start, _padding) = aligned_offset(self.offset, 8);
        let end = start + size;
        assert!(end <= self.data.len(), "sub-arena overflows parent");
        self.offset = end;  // parent 的 offset 推进
        SubArena {
            parent_offset_before: start,
            data: &mut self.data[start..end],
        }
    }
}

struct SubArena<'a> {
    parent_offset_before: usize,
    data: &'a mut [u8],
}

impl<'a> Drop for SubArena<'a> {
    fn drop(&mut self) {
        // sub-arena 析构时,理论上可以让 parent 回退到 parent_offset_before
        // 但 Rust 的 borrow 规则让这复杂——通常 sub-arena 不能"还回"内存
        // 实践中:sub-arena 只是"逻辑分区",parent 仍占全部
    }
}
```

padding 字节"消耗"内存但不存有用数据。

### padding 的常见来源

- **自然对齐**:alloc u32 需要 4 字节 align,alloc u64 需要 8 字节
- **SIMD 对齐**:SSE 16 字节,AVX 32 字节
- **GPU 对齐**:统一 buffer 通常 256 字节对齐
- **缓存行对齐**:64 字节对齐避免 false sharing

如果 alloc 顺序杂乱(交替 alloc 1 字节和 16 字节),padding 累积。

### 减小 padding 的策略

1. **大对齐在前**:先 alloc 大对齐需求(SIMD),后 alloc 小
2. **打包数据**:把多个 u8 打包成 u64,一次 alloc
3. **SoA 布局**:struct of arrays,不是 array of structs,减少 padding
4. **使用 align(1) 类型**:能避免对齐就避免(如用 u8 数组代替 struct)

### 内存可视化布局

```
arena (100 字节,offset 0..100):
[USED: 0-30] [PAD: 30-32] [USED: 32-40] [PAD: 40-48] [USED: 48-90] [FREE: 90-100]

颜色:
绿:USED(有效数据)
灰:PAD(对齐填充)
白:FREE(未分配)
红:HOLE(释放后产生的洞,复杂 arena 才有)
```

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发常见的 padding 问题:

- **ECS 内存布局**:每个 component 数组的 padding 影响缓存命中
- **GPU vertex buffer**:每个顶点的 padding 影响带宽
- **网络包**:对齐影响带宽
- **存档**:对齐影响文件大小

Data-Oriented Design(DOD)就是研究如何最小化 padding。

### 3.2 · 图形学视角

GPU 缓冲的对齐要求严格:

- **Uniform buffer**(OpenGL):通常 256 字节对齐
- **Storage buffer**(Vulkan):16 字节对齐
- **Vertex attribute**:每个属性的 align 取决于格式

不遵守对齐 = GPU 拒绝或慢。

### 3.3 · Linux 系统编程视角

Linux 内核对齐:

- **page**:4096 字节(大多数架构)
- **huge page**:2 MB / 1 GB
- **cache line**:64 字节

malloc 返回的指针默认 max_align_t 对齐(16 字节 on x86_64)。`posix_memalign` 可以指定 align。

### 3.4 · Rust 生态视角

Rust 的对齐:

- `std::mem::align_of::<T>()` 返回类型对齐
- `#[repr(align(N))]` 自定义类型对齐
- `Vec<u8>` 对齐 1,`Vec<u64>` 对齐 8

```rust
println!("{}", std::mem::align_of::<u8>());   // 1
println!("{}", std::mem::align_of::<u32>());  // 4
println!("{}", std::mem::align_of::<u64>());  // 8

#[repr(C)]
struct Mixed {
    a: u8,    // offset 0
              // padding 1-3
    b: u32,   // offset 4
    c: u8,    // offset 8
              // padding 9-15 (整个 struct align 8)
}  // 总大小 16
```

`#[repr(packed)]` 取消对齐(节省空间,但访问慢,有些平台崩)。

## 5 · 对照与变奏

不同语言的 alignment 控制:

- **C/C++**:`alignas(16) int x;` 显式对齐
- **Rust**:`#[repr(align(16))] struct X;` 显式对齐
- **Go**:runtime 自动对齐,无法手动控制
- **Java**:JVM 自动对齐,无法手动控制
- **Python**:无对齐概念(对象模型不同)

Rust 比 C 严格——编译期检查 alignment,不允许"把 u8 数组 reinterpret 成 u32"(可能未对齐)。这是 Rust 内存安全的核心。

#### SIMD 要求的特殊对齐

SIMD(Single Instruction Multiple Data)指令对对齐要求更严格:

- SSE `__m128`:16 字节对齐
- AVX `__m256`:32 字节对齐
- AVX-512 `__m512`:64 字节对齐

不对齐的 SIMD 访问在某些 CPU 上是**未定义行为**(crash),在另一些 CPU 上是慢(性能减半)。所以 SIMD 代码必须显式对齐数据。

Rust 的 `std::simd`(nightly)和 `wide` crate(stable)的 SIMD 类型自动 16/32 字节对齐。Arena 给 SIMD 数据 alloc 时必须 align >= 16:

```rust
arena.alloc(size, 16);  // 16 字节对齐
```

工业级游戏引擎的 arena 配置:

- 普通数据 arena:8 字节对齐(默认)
- SIMD data arena:16 字节对齐
- GPU upload arena:256 字节对齐(Vulkan constant buffer 要求)

学会这种"按场景选对齐",你的内存管理性能最优。

不同 allocator 的碎片模式:

- **Arena**:无碎片(连续 bump),除非 reset
- **Pool allocator**:固定 slot,无碎片

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:对齐 padding 看起来是浪费,为什么不直接 align(1)?

**参考解答**:硬件要求对齐。CPU 访问 unaligned 数据可能:(1)慢(两次内存访问拼接);(2)崩(SPARC 等架构对 unaligned access 触发 SIGBUS);(3)非原子(unaligned 的 atomic 无效)。SIMD 指令(SSE/AVX)严格要求对齐,unaligned 直接 segfault。GPU 同样。所以对齐不是"可选优化",是"硬件契约"。Padding 是为了遵守契约付出的代价。

### Lv2 · 动手实践

**题**:用 Rust 计算并显示 struct 的 padding。给定 struct:
```rust
struct S { a: u8, b: u32, c: u8, d: u64 }
```
画出每个字段的 offset 和 padding。

**参考解答**:

```rust
use std::mem::{size_of, align_of};

#[repr(C)]
struct S {
    a: u8,    // offset 0, padding 1-3
    b: u32,   // offset 4
    c: u8,    // offset 8, padding 9-15
    d: u64,   // offset 16
}

fn main() {
    println!("=== struct S 的内存布局 ===");
    println!("总大小: {} 字节", size_of::<S>());
    println!("对齐:   {} 字节", align_of::<S>());
    println!();
    
    println!("字段布局:");
    println!("  a (u8):  offset 0, size 1");
    println!("  [padding 3 字节]");
    println!("  b (u32): offset 4, size 4");
    println!("  c (u8):  offset 8, size 1");
    println!("  [padding 7 字节, 因为 d 需要 8 字节对齐]");
    println!("  d (u64): offset 16, size 8");
    println!();
    
    let useful = 1 + 4 + 1 + 8;  // 14 字节有用数据
    let total = size_of::<S>();
    let padding = total - useful;
    println!("有用数据: {} 字节", useful);
    println!("Padding:  {} 字节 ({:.1}%)", padding, padding as f32 / total as f32 * 100.0);
    
    // 优化建议
    println!("\n优化建议:");
    println!("  把 a 和 c 放一起,大对齐字段在后:");
    println!("  struct SOptimized {{ a: u8, c: u8, [pad 2], b: u32, d: u64 }} = 16 字节");
}
```

```rust
// 精确的 arena 内存可视化(区分 used / padding / free)

use std::panic::Location;

#[derive(Debug, Clone)]
pub struct PreciseBump {
    pub used_offset: usize,    // 有效数据开始
    pub used_size: usize,      // 有效数据大小
    pub padding_before: usize, // 对齐填充(在 used_offset 前)
    pub file: &'static str,
    pub line: u32,
    pub tag: &'static str,
}

pub struct PreciseArena {
    data: Vec<u8>,
    offset: usize,
    bumps: Vec<PreciseBump>,
    name: String,
}

impl PreciseArena {
    pub fn new(name: &str, capacity: usize) -> Self {
        Self {
            data: vec![0u8; capacity],
            offset: 0,
            bumps: Vec::new(),
            name: name.to_string(),
        }
    }
    
    #[track_caller]
    pub fn alloc(&mut self, size: usize, align: usize, tag: &'static str) -> Option<&mut [u8]> {
        let loc = Location::caller();
        let mask = align - 1;
        let aligned = (self.offset + mask) & !mask;
        let padding = aligned - self.offset;
        let new_offset = aligned + size;
        
        if new_offset > self.data.len() {
            return None;
        }
        
        self.bumps.push(PreciseBump {
            used_offset: aligned,
            used_size: size,
            padding_before: padding,
            file: loc.file(), line: loc.line(), tag,
        });
        self.offset = new_offset;
        Some(&mut self.data[aligned..new_offset])
    }
    
    pub fn total_used(&self) -> usize {
        self.bumps.iter().map(|b| b.used_size).sum()
    }
    
    pub fn total_padding(&self) -> usize {
        self.bumps.iter().map(|b| b.padding_before).sum()
    }
    
    pub fn total_free(&self) -> usize {
        self.data.len() - self.offset
    }
    
    pub fn display(&self) {
        println!("\n=== Arena '{}' ===", self.name);
        let cap = self.data.len();
        let used = self.total_used();
        let padding = self.total_padding();
        let free = self.total_free();
        
        println!("容量:    {} 字节", cap);
        println!("已用:    {} 字节 ({:.1}%)", used, used as f32 / cap as f32 * 100.0);
        println!("Padding: {} 字节 ({:.1}%)", padding, padding as f32 / cap as f32 * 100.0);
        println!("空闲:    {} 字节 ({:.1}%)", free, free as f32 / cap as f32 * 100.0);
        
        // 文本时间线:每个字符代表 capacity/80 字节
        let bar_width = 80;
        let mut bar = vec![' '; bar_width];
        
        for bump in &self.bumps {
            // padding 部分(灰色)
            let pad_start = bump.used_offset - bump.padding_before;
            let pad_end = bump.used_offset;
            for byte in pad_start..pad_end {
                let col = byte * bar_width / cap;
                if col < bar_width { bar[col] = '.'; }  // padding
            }
            // used 部分(实心)
            for byte in bump.used_offset..bump.used_offset + bump.used_size {
                let col = byte * bar_width / cap;
                if col < bar_width { bar[col] = '#'; }
            }
        }
        
        // 剩余部分留空(' ')
        println!("\n内存布局({} 字节):", cap);
        println!("[{}]", bar.iter().collect::<String>());
        println!("图例: # = used, . = padding, (space) = free");
        
        // 每个 bump 详情
        println!("\n详细分配:");
        for bump in &self.bumps {
            let filename = bump.file.split('/').last().unwrap_or(bump.file);
            let mut detail = format!("  +{} ({}:{} tag={})",
                bump.used_size, filename, bump.line, bump.tag);
            if bump.padding_before > 0 {
                detail.push_str(&format!(" [pad {}]", bump.padding_before));
            }
            println!("{}", detail);
        }
        
        // 优化建议
        if padding > used / 10 {
            println!("\n⚠ Padding 占用 {:.1}% of used,考虑重排或减小 align",
                padding as f32 / used as f32 * 100.0);
        }
    }
}

fn main() {
    let mut arena = PreciseArena::new("frame", 1024 * 1024);
    
    // 模拟一帧分配
    let _ = arena.alloc(3, 1, "byte_data");      // 3 字节,无 align
    let _ = arena.alloc(8, 8, "u64_data");        // 8 字节,align 8(需要 5 字节 padding)
    let _ = arena.alloc(1, 1, "flag");            // 1 字节
    let _ = arena.alloc(16, 16, "simd");          // 16 字节 SIMD
    let _ = arena.alloc(1, 1, "byte");            // 1 字节
    let _ = arena.alloc(1024, 4, "array_u32");    // 1 KB u32 数组
    
    arena.display();
}
```

出错怎么办:

- **bar 渲染乱**:bar 数组用 char,确认每列只被一个 byte 覆盖。
- **padding 计算负数**:`aligned - self.offset` 应该总是 ≥ 0。如果 negative,公式错。
