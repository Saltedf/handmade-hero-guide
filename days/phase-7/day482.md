# Day 482 · 为 PNG 关联标签

> 美术给你 100 张 PNG,你怎么知道哪张是"hero",哪张是"敌人",哪张是"地形"?Casey 这一天给资产管线加 **tag**——每个 PNG 在导入时关联若干标签,游戏运行时按 tag 查询资产。

## 0 · 为什么要有这一天

PNG 文件本身只有像素数据。文件名 `hero_idle_01.png` 暗示这是 hero 的 idle 动画第 1 帧,但游戏运行时怎么用这个信息?

最直接的方式:写代码 `if filename.starts_with("hero_idle")`。但这种方式有问题:

- 文件名规则容易忘(三个月后你记得 `hero_idle` 还是 `hero.idle` 还是 `hero-idle`?)
- 重命名要改代码
- 同一张图可能有多个语义(它既是 hero,又是 humanoid,也是 character)

工业界用 **tag 系统** 解决:每个资产关联一组 tag(标签),游戏按 tag 查询。

```
asset: hero_idle_01.png
tags: [hero, idle, character, humanoid, frame_01]
```

查询时:`assets.find(tags=["hero", "idle"])` 返回所有匹配的资产。Tag 之间是"且"关系——所有 tag 都匹配才算。

这种 tag 系统在工业界到处都是:

- 博客系统:文章有 tags
- 文件系统:macOS 的 Finder tags、Linux 的 `tmsu`
- docker:镜像有 tags
- git:标签标记 release
- YouTube/Bilibili:视频有 tags

Tag 系统的核心是 **"自由的元数据"**——不限制结构,允许任意标记,运行时灵活查询。代价是查询性能(没有结构索引),但灵活性收益大。

Casey Day 482 做的就是给 HH 资产加 tag 系统。

完成这一天之后,你具备了:

- Tag 系统的设计和实现
- 资产管线的元数据扩展
- 理解"自由元数据 vs 严格 schema"的取舍

## 1 · Casey 今天做了什么

Casey 这一天的工作:

第一步,他改 HHA 格式,加 tag 表。每个 asset 关联若干 tag(用 tag index 引用,避免重复字符串)。

第二步,他改资产导入器(`asset_packer`)——读 PNG 文件时,同时读一个 sidecar `.tags` 文件,里面是该资产的 tag 列表。

第三步,他写 game code 的 tag 查询 API:`get_asset_by_tag(state, "hero")` 返回匹配的 asset。

Casey 在这一天的关键决策:**tag 是 import 时关联的,不是 runtime 计算的**。这样 runtime 只查询,不解析——快。Casey 把 tag 表存到 HHA 文件里,game 加载 HHA 时一次性拿到所有 tag 映射。

## 2 · 心智模型

### 类比:图书馆主题分类

想象图书馆有两种找书方式:

**方式 A(按文件名)**:书按"书名"分类。《Handmade Hero Day 041》在 H 区,《Handmade Hero Day 042》在 H 区……但如果你要找"所有讲向量数学的书",你得遍历整个图书馆,因为书名不一定包含"向量"。

**方式 B(按主题标签)**:每本书贴多个标签:"向量数学"、"游戏开发"、"Day 041"。要找"向量数学"的所有书,只要查"向量数学"标签,不用遍历。

Tag 系统的优势:**多维度查询**。一本书可以同时属于多个主题,文件名只能表达一个维度。

HH 的资产也是多维度。`hero_idle_01.png` 既是:

- 角色 = hero
- 状态 = idle
- 类型 = character
- 帧号 = 01

Tag 让你按任何维度查询。

### Tag 的实现:HHA 的 tag 表

HHA 文件结构(简化):

```
+--------------------+
| Header             |
| - magic            |
| - version          |
| - tag_count        |
| - asset_count      |
+--------------------+
| Tag Table          |
| [0] string = "hero" |
| [1] string = "idle"|
| ...                |
+--------------------+
| Asset Table        |
| [0]                |
|   first_tag_index  |
|   one_past_last_tag_index  → 引用 tag table 的范围
|   type = bitmap     |
|   data_offset       |
| ...                |
+--------------------+
| Tag Indices        |  (asset 用 tag index 数组)
| 0: 0, 1            |  (asset 0 的 tag 是 [hero, idle])
| 2: 2, 3            |  (asset 1 的 tag 是 [character, humanoid])
| ...                |
+--------------------+
| Data Blob          |
| (PNG 像素数据)     |
+--------------------+
```

关键设计:**tag 字符串去重**。如果 100 个 asset 都用 "hero" tag,"hero" 字符串只存一次,asset 引用 tag index 而不是字符串。这叫 **string interning**(字符串驻留)。

### Tag 查询的算法

Game code 查询"所有匹配 tag 'hero' 的 asset":

```rust
fn find_assets_by_tag(state: &GameState, query_tag: &str) -> Vec<AssetId> {
    // 1. 把 query_tag 转成 tag index(string interning)
    let query_tag_idx = state.tag_string_to_index.get(query_tag)?;
    
    // 2. 遍历所有 asset,检查每个 asset 的 tag 是否包含 query_tag_idx
    let mut result = Vec::new();
    for (asset_idx, asset) in state.assets.iter().enumerate() {
        let asset_tags = &state.tag_indices[asset.first_tag_idx..asset.one_past_last_tag_idx];
        if asset_tags.contains(query_tag_idx) {
            result.push(AssetId(asset_idx as u32));
        }
    }
    result
}
```

时间复杂度 O(N×K),N 是 asset 数,K 是每 asset 平均 tag 数。对 HH(几百 asset)足够快。

工业级(几万 asset)用 **inverted index**——每个 tag 维护一个"哪些 asset 有这个 tag"的列表,查询是 O(1) lookup + O(M) iteration,M 是结果数。

### 多 tag 查询(AND / OR)

Casey 的 tag 系统支持多 tag:

```rust
// AND:asset 必须包含所有 query tags
fn find_assets_all_tags(state: &GameState, query_tags: &[&str]) -> Vec<AssetId> {
    let query_indices: Vec<u32> = query_tags.iter()
        .filter_map(|t| state.tag_string_to_index.get(t).copied())
        .collect();
    
    state.assets.iter().enumerate()
        .filter(|(_, asset)| {
            let asset_tags = &state.tag_indices[asset.first_tag_idx..asset.one_past_last_tag_idx];
            query_indices.iter().all(|q| asset_tags.contains(q))
        })
        .map(|(i, _)| AssetId(i as u32))
        .collect()
}
```

OR 查询类似,把 `.all()` 换成 `.any()`。

### Sidecar 文件:tag 存哪

Tag 怎么从美术那边传到游戏?Casey 选 **sidecar 文件**:

```
hero_idle_01.png       # 像素数据
hero_idle_01.png.tags  # tag 列表(纯文本)
```

`.tags` 文件内容:

```
hero
idle
character
humanoid
frame_01
```

资产导入器读 `.png` 时同时读 `.tags`,把 tag 关联到 asset。

为什么用 sidecar 而不是把 tag 存到 PNG 元数据(PNG 的 tEXt chunk 可以存 key-value)?两个理由:

第一,**简单**。Sidecar 是纯文本,美术可以用任何编辑器改。PNG tEXt 需要工具。

第二,**解耦**。美术可以批量改 tag(改 sidecar)不需要重新编码 PNG。

工业级资产管线通常用更结构化的 sidecar(JSON、YAML):

```json
{
  "name": "hero_idle_01",
  "tags": ["hero", "idle", "character"],
  "fps": 12,
  "loop": true
}
```

Casey 简化用纯文本每行一个 tag,够用。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

Tag 系统在游戏引擎里几乎是标配。Unity 的 AssetDatabase 用 GUID + label,Unreal 的 Object 用 tag,Godot 的 Resource 用 meta。

工业级 tag 系统通常更复杂:

- **Tag hierarchy**:`enemy.boss.dragon` 这种层级 tag,匹配时可以通配
- **Tag query language**:`(hero AND idle) OR (enemy AND attack)`,布尔表达式
- **Tag inheritance**:asset 继承父 asset 的 tag
- **Tag namespace**:`render:hero` vs `audio:hero`,避免冲突

Casey 的简单 tag 系统(纯文本 + AND 查询)覆盖 HH 需求。但他后面如果加复杂动画系统,可能需要 tag hierarchy。

游戏开发里还有一个相关概念:**addressable assets**。Unity 的 Addressable Assets 系统让 asset 用字符串地址引用(类似 tag),而不是文件路径。这是 tag 思想的极致——asset 不再有"路径",只有"地址"。

### 3.2 · 🎨 图形学视角

图形学里 tag 用于**资产类型分类**:

- texture:diffuse、normal、roughness、metalness、emissive
- mesh:static、skeletal、collision
- shader:opaque、transparent、alpha-test、post-process
- material:PBR、unlit、toon

PBR 渲染管线特别依赖 tag——一个 material 的渲染方式由 tag 决定(opaque/transparent),shader 选择也由 tag 决定。

Casey 的 tag 系统目前只用在 bitmap 资产上,后面 Day 540+ 加 PBR 时会扩展到 material / mesh。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上 tag 系统的几个对应:

**SELinux label**:每个文件有 security label,类似 tag。SELinux policy 按 label 控制访问。

**systemd unit 的 After=/Wants=**:服务依赖关系,类似 tag。

**udev rules**:设备属性匹配,类似 tag query。例如 `ATTR{idVendor}=="1234"` 匹配特定 USB 设备。

**Linux extended attributes(xattr)**:文件附加 key-value 元数据。`getfattr -d filename` 查看。和 PNG tEXt chunk 同构。

```bash
# 给文件加 tag(用 user namespace xattr)
setfattr -n user.tag.hero -v 1 hero.png
getfattr -d hero.png
# user.tag.hero="1"

# 找所有有特定 tag 的文件
find . -exec sh -c 'getfattr -n user.tag.hero "$1" 2>/dev/null | grep -q 1 && echo "$1"' _ {} \;
```

这些是 Linux 系统级的 tag 实现。Casey 在 HH 里做的是游戏资产级的 tag,但思想完全一致。

### 3.4 · 🦀 Rust 生态视角

Rust 里实现 tag 系统有几个 idiomatic 选择。

第一,**`HashMap<String, Vec<TagId>>`** 做反向索引:

```rust
struct TagIndex {
    tag_to_assets: HashMap<String, Vec<AssetId>>,   // tag → 资产列表
    asset_to_tags: HashMap<AssetId, Vec<String>>,   // 资产 → tag 列表
}
```

双向索引,正反查询都快。代价是内存(两份索引)。

第二,**`String::from` interning 用 `unicase::AsciiCaseInsensitive`** 让 tag 不区分大小写:

```rust
use unicase::Ascii;

let tag_map: HashMap<Ascii<String>, TagId> = HashMap::new();
// "Hero" 和 "hero" 是同一个 tag
```

第三,**`enum Tag` 表达固定 tag 集**。如果 tag 种类有限(比如就那十几种),用 enum 编译时检查:

```rust
enum AssetTag {
    Hero,
    Enemy,
    Idle,
    Attack,
    // ...
}
```

但 Casey 想让 tag 灵活(美术能加任意 tag),所以用 String 不是 enum。

## 5 · 对照与变奏

Casey 在 Day 482 的 tag 思想在不同领域有不同对应:

**博客系统**:WordPress tags、Hexo categories。文章按 tag 聚合。

**文件系统**:macOS Finder tags(用户给文件打颜色/文字标签)。Linux 的 `tmsu` 命令行 tag 工具。

**数据库**:PostgreSQL 的 `array`、`jsonb` 字段类型。可以存 tag 数组,用 GIN 索引加速查询。

**搜索引擎**:Elasticsearch 的 `tags` 字段 + filter。每个文档多个 tag,查询时按 tag filter。

**Git**:轻量级 tag(`git tag v1.0`)和注释 tag。标记 release 点。

**Docker**:image tag。`nginx:1.21` 表示 nginx image 的 1.21 版本。

理解"自由元数据 + 查询"是工程师的核心素养。每次你处理"如何快速找到符合某条件的对象",问自己:**能不能用 tag 系统?**

另一个对照:**Tag vs Category**。Category 互斥(一本书只能在一个分类),Tag 不互斥(一本书可以有多个 tag)。Category 适合严格分类,Tag 适合灵活标记。Casey 用 tag 是因为 asset 多语义。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:为什么 Casey 用 sidecar `.tags` 文件而不是把 tag 存到 PNG 的 tEXt chunk?

**参考解答**:三个理由:

第一,**简单**。Sidecar 是纯文本,美术用记事本就能改。PNG tEXt 需要工具(命令行 exiftool 或 GUI 图像编辑器)。

第二,**解耦**。Sidecar 改了不需要重编码 PNG(像素数据没变)。PNG tEXt 改了要重存整张 PNG(消耗 CPU、可能损坏数据)。

第三,**工具友好**。命令行工具(cat、grep、awk)能直接处理 sidecar。PNG tEXt 需要专门工具。

PNG tEXt 的优点是"自包含"——一个 PNG 文件包含所有信息。Casey 权衡后选 sidecar,因为他注重可读性和工具友好。工业项目(必须传单个文件)可能选 tEXt。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:实现一个简化的 tag 系统。给定 5 个 asset(每个有名字和一组 tag),实现 `find_by_tag(tag: &str) -> Vec<&Asset>` 和 `find_by_all_tags(tags: &[&str]) -> Vec<&Asset>`。验证:能找到正确的 asset。

完成标准:跑测试用例,find_by_tag("hero") 返回 2 个 asset,find_by_all_tags(["hero", "idle"]) 返回 1 个 asset。

**参考解答**:

```rust
#[derive(Debug)]
struct Asset {
    name: String,
    tags: Vec<String>,
}

struct AssetDatabase {
    assets: Vec<Asset>,
    // 反向索引:tag → 哪些 asset 有这个 tag
    tag_index: std::collections::HashMap<String, Vec<usize>>,
}

impl AssetDatabase {
    fn new() -> Self {
        Self {
            assets: Vec::new(),
            tag_index: std::collections::HashMap::new(),
        }
    }
    
    fn add(&mut self, asset: Asset) {
        let idx = self.assets.len();
        for tag in &asset.tags {
            self.tag_index
                .entry(tag.clone())
                .or_default()
                .push(idx);
        }
        self.assets.push(asset);
    }
    
    fn find_by_tag(&self, tag: &str) -> Vec<&Asset> {
        // 用反向索引,O(1) lookup
        match self.tag_index.get(tag) {
            Some(indices) => indices.iter().map(|&i| &self.assets[i]).collect(),
            None => Vec::new(),
        }
    }
    
    fn find_by_all_tags(&self, tags: &[&str]) -> Vec<&Asset> {
        if tags.is_empty() {
            return self.assets.iter().collect();
        }
        
        // 找出每个 tag 的 asset 集合,求交集
        // 启发式:从 tag 对应 asset 最少的开始,减少计算量
        let mut tag_assets: Vec<&Vec<usize>> = tags.iter()
            .filter_map(|t| self.tag_index.get(*t))
            .collect();
        tag_assets.sort_by_key(|v| v.len());
        
        if tag_assets.is_empty() {
            return Vec::new();
        }
        
        // 第一个 tag 的 asset 作为候选,逐个 filter
        let candidates: Vec<usize> = tag_assets[0].iter().cloned().collect();
        let other_sets: Vec<&std::collections::HashSet<usize>> = tag_assets[1..].iter()
            .map(|v| v.iter().cloned().collect::<std::collections::HashSet<_>>())
            .collect::<Vec<_>>();
        let other_sets_refs: Vec<&std::collections::HashSet<usize>> = other_sets.iter().collect::<Vec<_>>();
        
        candidates.iter()
            .filter(|&&idx| {
                other_sets_refs.iter().all(|s| s.contains(&idx))
            })
            .map(|&idx| &self.assets[idx])
            .collect()
    }
}

fn main() {
    let mut db = AssetDatabase::new();
    
    db.add(Asset {
        name: "hero_idle_01".to_string(),
        tags: vec!["hero".into(), "idle".into(), "character".into()],
    });
    db.add(Asset {
        name: "hero_walk_01".to_string(),
        tags: vec!["hero".into(), "walk".into(), "character".into()],
    });
    db.add(Asset {
        name: "goblin_idle_01".to_string(),
        tags: vec!["goblin".into(), "idle".into(), "enemy".into()],
    });
    db.add(Asset {
        name: "sword".to_string(),
        tags: vec!["weapon".into(), "sword".into()],
    });
    db.add(Asset {
        name: "tree_01".to_string(),
        tags: vec!["environment".into(), "tree".into()],
    });
    
    println!("=== find_by_tag ===");
    println!("'hero': {:?}", db.find_by_tag("hero").iter().map(|a| &a.name).collect::<Vec<_>>());
    println!("'idle': {:?}", db.find_by_tag("idle").iter().map(|a| &a.name).collect::<Vec<_>>());
    
    println!("\n=== find_by_all_tags ===");
    println!("[hero, idle]: {:?}", 
             db.find_by_all_tags(&["hero", "idle"]).iter().map(|a| &a.name).collect::<Vec<_>>());
    println!("[idle]: {:?}", 
             db.find_by_all_tags(&["idle"]).iter().map(|a| &a.name).collect::<Vec<_>>());
    println!("[character]: {:?}", 
             db.find_by_all_tags(&["character"]).iter().map(|a| &a.name).collect::<Vec<_>>());
    println!("[sword, weapon]: {:?}", 
             db.find_by_all_tags(&["sword", "weapon"]).iter().map(|a| &a.name).collect::<Vec<_>>());
    println!("[hero, walk, character]: {:?}",
             db.find_by_all_tags(&["hero", "walk", "character"]).iter().map(|a| &a.name).collect::<Vec<_>>());
}
```

为什么这么写:`tag_index` 是反向索引,`find_by_tag` O(1)。`find_by_all_tags` 用启发式——从最小的 tag 集合开始,减少 filter 次数。这是工业级 tag 查询的标准优化。

## 8 · Rust / Arch 落地代码

下面是 Day 482 完整的 tag 系统 Rust 实现,集成到 HHA 加载流程。

```rust
use std::collections::HashMap;
use std::fs;
use std::path::Path;

// ========================================
// HHA 数据结构(简化)
// ========================================

#[derive(Debug)]
struct HhaTag {
    string: String,
}

#[derive(Debug)]
struct HhaAsset {
    name: String,
    first_tag_index: u32,
    one_past_last_tag_index: u32,
    data_offset: u64,
}

#[derive(Debug)]
struct HhaFile {
    tags: Vec<HhaTag>,
    assets: Vec<HhaAsset>,
    tag_indices: Vec<u32>,          // 每个 asset 的 tag index 平铺
}

// ========================================
// Tag 查询接口
// ========================================

struct AssetLibrary {
    hha: HhaFile,
    tag_to_index: HashMap<String, u32>,
    // 反向索引:tag index → 哪些 asset
    tag_to_assets: HashMap<u32, Vec<u32>>,
}

impl AssetLibrary {
    fn load(hha: HhaFile) -> Self {
        // 建字符串 → tag index 映射
        let mut tag_to_index = HashMap::new();
        for (i, t) in hha.tags.iter().enumerate() {
            tag_to_index.insert(t.string.clone(), i as u32);
        }
        
        // 建反向索引
        let mut tag_to_assets: HashMap<u32, Vec<u32>> = HashMap::new();
        for (asset_idx, asset) in hha.assets.iter().enumerate() {
            for ti in asset.first_tag_index..asset.one_past_last_tag_index {
                let tag_idx = hha.tag_indices[ti as usize];
                tag_to_assets.entry(tag_idx).or_default().push(asset_idx as u32);
            }
        }
        
        Self { hha, tag_to_index, tag_to_assets }
    }
    
    fn find_by_tag(&self, tag: &str) -> Vec<&HhaAsset> {
        match self.tag_to_index.get(tag) {
            Some(&tag_idx) => {
                self.tag_to_assets.get(&tag_idx)
                    .map(|indices| indices.iter()
                         .map(|&i| &self.hha.assets[i as usize])
                         .collect())
                    .unwrap_or_default()
            }
            None => Vec::new(),
        }
    }
    
    fn find_by_all_tags(&self, tags: &[&str]) -> Vec<&HhaAsset> {
        let tag_indices: Vec<u32> = tags.iter()
            .filter_map(|t| self.tag_to_index.get(*t).copied())
            .collect();
        
        if tag_indices.is_empty() {
            return Vec::new();
        }
        
        // 找每个 tag 的 asset 集合,求交集
        let mut sets: Vec<Vec<u32>> = tag_indices.iter()
            .map(|&ti| self.tag_to_assets.get(&ti).cloned().unwrap_or_default())
            .collect();
        sets.sort_by_key(|v| v.len());
        
        let first: Vec<u32> = sets[0].clone();
        let other_sets: Vec<std::collections::HashSet<u32>> = sets[1..].iter()
            .map(|v| v.iter().cloned().collect())
            .collect();
        
        first.into_iter()
            .filter(|idx| other_sets.iter().all(|s| s.contains(idx)))
            .map(|i| &self.hha.assets[i as usize])
            .collect()
    }
}

// ========================================
// 资产导入器(从文件系统读 PNG + sidecar)
// ========================================

struct PngImporter {
    base_dir: String,
}

impl PngImporter {
    fn new(base_dir: &str) -> Self {
        Self { base_dir: base_dir.to_string() }
    }
    
    fn import(&self, name: &str) -> Option<ImportedAsset> {
        let png_path = Path::new(&self.base_dir).join(format!("{}.png", name));
        let tags_path = Path::new(&self.base_dir).join(format!("{}.png.tags", name));
        
        if !png_path.exists() {
            return None;
        }
        
        // 读 sidecar tags(如果有)
        let tags: Vec<String> = if tags_path.exists() {
            let content = fs::read_to_string(&tags_path).ok()?;
            content.lines()
                .map(|l| l.trim().to_string())
                .filter(|l| !l.is_empty())
                .collect()
        } else {
            Vec::new()
        };
        
        // 假装读 PNG 文件
        let png_data = fs::read(&png_path).ok()?;
        
        Some(ImportedAsset {
            name: name.to_string(),
            tags,
            png_data,
        })
    }
}

struct ImportedAsset {
    name: String,
    tags: Vec<String>,
    png_data: Vec<u8>,
}
```

出错怎么办:

- **`HashMap` 找不到 tag** —— tag 字符串 trim 不彻底。`.trim()` 后还有 `\r`(Windows 换行)的话,`"hero\r" != "hero"`。用 `.trim_end_matches(|c| c == '\r' || c == '\n')`。
- **反向索引重复** —— 同一个 asset 被加多次。导入时检查是否已存在,或用 HashSet 而不是 Vec。
- **大量 tag 时内存爆炸** —— 字符串 intern 应该用 `Rc<str>` 或 `Arc<str>` 共享,而不是每个 entry 都 `String::from`。
