
# Day 546 · GPU MIP 映射

## 0 · 为什么要有这一天

让我们把镜头贴近画面,真实地看到这个问题。假设你跟着 Handmade Hero 走到 Day 545——你刚把一张 512x512 的草地纹理贴到大地上。相机拉近看脚下的草,每根草叶清晰可辨,你拍了一张截图,觉得"这引擎做得不错"。然后你抬起头,远处的草地在地平线上展开——**奇怪的事情发生了**:远处的草**像电视雪花一样闪**。相机一动,某个像素前一帧是绿,这一帧变白,下一帧变黑,**整片远处的草地像坏掉的电视**在颤动。这是每一个 3D 引擎开发者都遇到过的问题,这个现象有专门的名字:**flickering(闪烁)**,更技术地说叫 **texture aliasing(纹理走样)**。

为什么远处的草会闪?让我把这件事拆开。纹理是 512x512 的高分辨率图,你贴在 100 米 x 100 米的大地上。当相机**近处**看时,屏幕上一个像素覆盖纹理上大约一个 texel(纹理像素)的区域——GPU 采一个 texel,结果稳定。但是当相机**远处**看,屏幕上一个像素覆盖了纹理上 32x32 的 texel 区域——这就是说,屏幕一个像素"代表"了 1024 个 texel。GPU 默认用 **point sampling(点采样)**——它只取这 1024 个 texel 中的**一个**(通常是左上角的那个)。相机一动,屏幕像素覆盖的那 1024 个 texel 重新算,采样到的那个 texel 跳到另一个位置,颜色就可能**突变**——前一帧采到一个浅色草叶,这一帧采到深色泥土,颜色就从浅绿跳到暗褐。整个远处画面像这样乱跳,就是 flickering。

这件事的根源是**信号处理的奈奎斯特定理**(我们在 §3.2 会展开):如果一个高频信号(密集的草叶纹理)被低于它频率 2 倍的速率采样(远处屏幕像素稀疏),就会产生 **aliasing(走样)**——高频信号"伪装"成低频,看起来就是闪烁。Mipmap 的发明就是为了解决这个问题。

正确的做法是 **downsampling(降采样)**:不要让 GPU 在远处强行用 512x512 原图采一个像素,而是预先准备好一系列缩小版本——256x256、128x128、64x64...一直到 1x1。远处屏幕像素覆盖 32x32 texel 时,GPU 自动切换到 32x32 那一级 mipmap,这样屏幕一个像素正好对应这一级里的一个 texel,**采样稳定**,不再闪。这"一系列缩小版本"就叫 **mipmap**(多级渐远纹理),来自拉丁语 *multum in parvo* "much in little"——一个 mipmap chain 里塞了好几个分辨率的图,每一级都"包含"原图的一个低频版本。

Casey 之前手贴纹理时一直没开 mipmap——因为前几天的 BMP 测试场景里相机离物体太近,屏幕像素和 texel 差不多一对一,不闪。Day 545 加了大地和草地,远处的地平线突然出现明显闪烁,Day 546 必须修。

**学完今天,你应该能**:
- 解释奈奎斯特定理和 aliasing 的关系,理解 mipmap 是如何从信号处理角度解决这个问题的
- 用 OpenGL/Vulkan/wgpu API 在 GPU 上生成 mipmap chain 并配置 trilinear 采样
- 知道 box filter、Gaussian filter、Lanczos filter 各自做 downsample 的差别,以及为什么 sRGB-aware mipmap 是必须的
- 理解 anisotropic filtering(各向异性过滤)在斜视角场景(地板、铁轨)的关键作用
- 用 RenderDoc 或 `glGetTexLevelParameteriv` debug GPU 实际选了哪一级 mipmap

## 2 · 心智模型

### 2.1 类比:看远处的风景照

想象你有一张 8K(7680x4320)分辨率的城市航拍图,你能看到每辆车的颜色。现在你做三个实验:

**实验一**:把它打印成 A4 大,贴在你眼前 30 厘米。你能数出停车场里的车——因为一个车在视网膜上覆盖几十个感光细胞,信息量充足。

**实验二**:你把这张 A4 拿到 30 米外。现在一张车在视网膜上只覆盖一个感光细胞——你的眼睛做了"自然的 downsample",车变成模糊的色块。你**不会觉得这图坏了**,因为大脑预期"远处的东西就该模糊"。

**实验三**:你**不**缩小图,而是强行用原图上的**一个像素**代表那辆车——每秒眼睛随机扫到原图上一个像素位置,你看到的"那辆车"颜色每秒都在变。你**会**觉得这图坏了——因为它在闪。

**关键洞察**:大脑接受"远处的图变模糊"(信号的低频表示),但**不接受**"远处的图在随机跳变"(高频 aliasing)。Mipmap 就是让 GPU 做实验二(用低频版本),避免实验三(强行用高频原图采一点)。

### 2.2 严谨展开:mip chain 的构造

mip chain(链)是纹理的多个分辨率版本。每个 level 边长减半:

```
Level 0: 512 x 512   (原图,占用 1 MB)
Level 1: 256 x 256   (1/4 MB)
Level 2: 128 x 128   (1/16 MB)
Level 3:  64 x 64    (1/64 MB)
...
Level 9:   1 x 1     (4 bytes)
```

总内存是等比级数和:`sum = 1 + 1/4 + 1/16 + ... ≈ 4/3 * 原图`。**开启 mipmap 多占 33% 内存**,但视觉质量大幅提升。这个 4/3 的系数无论纹理多大都成立——级数收敛到 4/3。

每级 level 由上一级**降采样**得到。最简单的算法是 2x2 像素 box filter(取平均):

```rust
fn downsample_2x2(src: &[u8], src_w: usize) -> Vec<u8> {
    let dst_w = src_w / 2;
    let dst_h = src_w / 2;  // 假设正方形
    let mut dst = vec![0u8; dst_w * dst_h * 4];
    for y in 0..dst_h {
        for x in 0..dst_w {
            for c in 0..4 {
                // 4 个源像素平均(box filter)
                let s = src[(y*2 * src_w + x*2) * 4 + c] as u32
                      + src[(y*2 * src_w + x*2 + 1) * 4 + c] as u32
                      + src[((y*2+1) * src_w + x*2) * 4 + c] as u32
                      + src[((y*2+1) * src_w + x*2 + 1) * 4 + c] as u32;
                dst[(y * dst_w + x) * 4 + c] = (s / 4) as u8;
            }
        }
    }
    dst
}
```

box filter 的频域特性是 sinc 函数——它**不完全**消除高频,会有少量"泄漏"。工业级 GPU 用更高级的 filter 来减少这个问题:**高斯 filter**(中心加权 4,邻接加权 2,角点加权 1)或 **Kaiser filter**(带通带 ripple 控制)。Casey 在视频里用 box filter 演示原理——OpenGL 的 `glGenerateMipmap` 默认也是 box-like,但具体实现由 driver 决定,质量参差。

### 2.3 GPU 怎么自动选 level

GPU 在 fragment shader 里能用两个特殊函数算"像素间的 UV 变化率":

- `dFdx(uv)`:UV 在屏幕 x 方向的偏导(右邻居像素 UV 减我像素 UV)
- `dFdy(uv)`:UV 在屏幕 y 方向的偏导

变化率大(屏幕动一点,UV 跳很多)说明纹理被压缩了(远处),用高 level。变化率小说明近处,用 level 0。具体公式:

```
ρ_x = ||dFdx(uv) * textureSize||
ρ_y = ||dFdy(uv) * textureSize||
λ = log2(max(ρ_x, ρ_y))
level = floor(λ + 0.5)  // 或在两个 level 间线性插值(trilinear)
```

这个计算是 GPU 内部硬件做的,你不用写。但理解它的**几何含义**很重要:`ρ_x` 和 `ρ_y` 描述了"屏幕一个像素在纹理空间是一个多大的区域"。如果 ρ=1,屏幕像素等于 1 个 texel,用 level 0;如果 ρ=4,屏幕像素等于 4x4 texel(16 个),用 level 2(因为 log2(4)=2)。

### 2.4 Trilinear vs Bilinear vs Anisotropic

| 过滤方式 | 怎么采 | 何时用 |
|---|---|---|
| Nearest | 1 个像素 | 像素艺术 |
| Bilinear | 同 level 4 像素线性 | 2D 游戏 |
| Trilinear | 两 level 各 4 像素 + level 间线性 | 3D 近距离 |
| Anisotropic | 椭圆形采多个像素 | 3D 斜视角(地板) |

**Anisotropic(各向异性)** 值得单独讲。考虑斜着看地板的场景:屏幕一个像素在纹理空间不是正方形,而是**长椭圆**——沿屏幕 x 方向覆盖很多 texel,沿 y 方向覆盖少。各向同性(mipmap)的方案用一个圆形 mip level,会**过度模糊** y 方向(把不该模糊的细节也模糊了)。各向异性沿椭圆主轴采样多个点,既抗锯齿又保留细节。地板、铁轨、墙根这些"掠射角"场景,anisotropic 是必须的。

OpenGL API:

```c
// trilinear filtering
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MIN_FILTER, GL_LINEAR_MIPMAP_LINEAR);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAG_FILTER, GL_LINEAR);  // mag 永远线性,不需 mipmap

// 各向异性 8x(NVIDIA/AMD 推荐最大 16x,但 8x 性能/质量比最好)
glTexParameterf(GL_TEXTURE_2D, GL_TEXTURE_MAX_ANISOTROPY_EXT, 8.0f);
```

`GL_TEXTURE_MAG_FILTER` 没设 mipmap 选项,因为 magnification(放大)发生在屏幕像素比 texel 多时——此时直接用 level 0 双线性插值即可,**不存在 aliasing**。

### 2.5 mipmap 的代价与一个反直觉的坑

mipmap 不是免费的午餐:
- **内存 +33%**:多存各级 mipmap
- **加载时间**:首次生成(或预生成)
- **bandwidth**:GPU 采样时根据 level 采不同缓存,可能 cache miss 多

但相比"远处闪烁"的视觉缺陷,这些代价完全值得。

**反直觉坑:sRGB texture 的 mipmap 必须在 linear 空间做平均**。如果你直接在 sRGB 编码的字节上做 box filter(取 4 个 sRGB 值的平均),结果是**过暗**的。原因是 sRGB 是非线性的(gamma ≈ 2.2),平均非线性值会偏向暗色(因为暗色在 sRGB 里数值小,平均后被"放大")。正确做法是:每像素 sRGB → linear → 平均 → linear → sRGB。Casey 这天用 linear workflow 没遇到这个问题,但实际项目里所有贴图都是 sRGB,这个坑必须填。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业级游戏加 mipmap 是默认操作,几乎没例外。但游戏开发里 mipmap 还有几个**进阶坑**需要小心:

**Alpha cutout 的 mipmap 问题**:树叶贴图常常用 alpha channel 做"剪影"——alpha=1 的像素显示,alpha=0 的像素丢弃(alpha test)。如果你把这种贴图 mipmap,小 level 里 alpha 被平均:原来 4 个像素里 1 个 alpha=1、3 个 alpha=0,mipmap 后 alpha=0.25——alpha test 失败(threshold=0.5),整个像素丢弃,**树叶从远处消失**。解决方法有三种:(1) mipmap 时对 alpha 取特殊处理(如取 max 而非 avg);(2) 用 alpha-to-coverage 把 alpha test 转成 MSAA coverage;(3) 用 mipmap alpha scale——在材质里指定一个比例,小 level 的 alpha 全局放大。Unreal Engine 用第三种,默认 0.5。

**Texture streaming(纹理流送)**:3A 游戏一个场景可能用 8GB 贴图,显存只有 8-12GB,装不下。解决方案是**虚拟纹理**(SVT,Software Virtual Texture),把贴图切成 128x128 的小块(tile),按需加载。每个 tile 自带 mipmap——近处的 tile 加载 level 0(高分辨率),远处的 tile 只加载 level 5(低分辨率)。玩家走动时,新的近处 tile 流入,远处的低分辨率 tile 留在显存里。FarCry 5、Call of Duty 都用这套。实现复杂但显存收益巨大。

**Compressed mipmap(BCn/DXT)**:GPU 纹理压缩格式 BC1-7(也叫 DXT、S3TC)每个 block 压 4x4 像素到 8-16 字节,整体压缩比 4:1 或 8:1。mipmap chain 每级都压缩,内存收益叠加。但 BCn 是**有损**压缩,某些高频纹理(草、铁丝网)压缩后有明显 artifact,需要美术手动调压缩参数。

**Mipmap bias(偏置)**:游戏开发者可以通过 `GL_TEXTURE_LOD_BIAS` 让 GPU 选比"理论正确"高一级或低一级的 mipmap。负 bias 让结果更锐利但更易闪(选更低 level),正 bias 让结果更模糊但稳定(选更高 level)。某些风格化游戏(如《原神》的远景)用正 bias 让远处更"卡通化"模糊。

### 3.2 · 🎨 图形学视角

mipmap 的数学本质是 **signal processing(信号处理)** 的 **奈奎斯特-香农采样定理**:要无失真重建一个最高频率为 f 的信号,采样频率必须 ≥ 2f。低于这个频率,信号里的高频成分会"伪装"成低频——**aliasing(走样)**。

把纹理看作一个 2D 信号 f(x,y)。它的最高频率由"细节程度"决定——一张 512x512 草地纹理,最高频率大约是 256 cycles/单位(因为 512 像素、Nyquist 频率是分辨率的一半)。屏幕一个像素覆盖纹理上 ρ x ρ 个 texel 时,屏幕采样频率是 1/ρ cycles/像素。要满足奈奎斯特,需要 `1/ρ ≥ 2 * 256`,即 ρ ≤ 1/512——只要 ρ > 1/512,就走样。

mipmap 的解决方案是**预先 low-pass filter**:在每一级 mipmap,纹理经过 2x downsample,等效于低通滤波(去掉一半高频)。这样每级 mipmap 的最高频率是上一级的一半——Level 0 是 256 cycles,Level 1 是 128,Level 2 是 64... 远处屏幕像素覆盖大区域时,GPU 切换到对应 level,这个 level 的最高频率匹配屏幕采样频率,**奈奎斯特条件满足,无 aliasing**。

这就是为什么 `GL_LINEAR_MIPMAP_LINEAR` 也叫 **trilinear filtering**——UV 空间双线性(2 个轴) + level 空间线性 = 3 个线性。"tri"指的是三个线性维度,不是三个 level。

**频域 vs 空域**:从频域看 mipmap 是低通滤波器;从空域看是 box/gaussian 平均。这两个视角等价(傅里叶变换),但**频域视角更深刻**——它告诉你"为什么"必须低通(为了满足奈奎斯特),"为什么" box filter 不完美(box 的频域响应是 sinc,有 sidelobe,会泄漏高频),"为什么"高斯更好(高斯的频域也是高斯,无 sidelobe)。理解频域让你能选对 filter。

### 3.3 · 🐧 Linux 系统编程视角

mipmap 的"多级预生成,按需选"思想在系统层无处不在。我列举几个关键例子:

**Linux page cache**:你读一个文件,Linux 内核不会只把读到的字节放进内存,而是把**整个 4KB page**(或更大 huge page)放进去。这是"多级粒度"——粒度大,加载次数少但浪费内存;粒度小,加载精确但 I/O 多。Linux 用 4KB 默认 page、2MB/1GB huge page 选项,本质上是"按访问模式选合适粒度",和 GPU 选 mipmap level 异曲同工。

**x86_64 page table**:x86_64 用 4 级页表(PML4 → PDPT → PD → PT),每级粒度从粗到细。CPU 查 TLB miss 时从粗到细查找——如果高层级指向"未映射",直接失败,不需查低层级。这就像 GPU 选 mipmap——先看"整体是否覆盖",再决定采样哪一级。

**JPEG thumbnail**:`xdg` 在 `~/.cache/thumbnails/` 缓存缩略图,文件管理器显示大图时用原图、显示缩略图时用缓存。这就是 mipmap 思想——预生成多个分辨率版本,按需选。Linux 桌面环境的 `gdk-pixbuf` 和 `qimage` 都内置 thumbnail 缓存。

**apt/pacman package cache**:`/var/cache/pacman/pkg/` 保留旧版本包,你可以"按需选"合适的版本。同样是"预存多版本,按需取"。

**SQLite WAL**:Write-Ahead Log 的 page 大小可以选 512-65536 字节。小 page 适合频繁小写入,大 page 适合批量读写。这是"按访问模式选粒度"的另一种体现。

理解 mipmap 后,你看这些系统设计的"分级粒度"思想会豁然开朗——它们都是**同一抽象的实例**:准备多个分辨率版本,根据使用场景按需选。

### 3.4 · 🦀 Rust 生态视角

Rust 图形生态对 mipmap 的支持分两层:**CPU 端生成**(image crate、fast_image_resize)和 **GPU 端管理**(wgpu、glow、vulkano)。

`image` crate 提供基础的 mipmap 生成 API:

```rust
use image::{imageops, GenericImageView, ImageBuffer, Rgba};

fn generate_mipmaps(
    img: &ImageBuffer<Rgba<u8>, Vec<u8>>,
) -> Vec<ImageBuffer<Rgba<u8>, Vec<u8>>> {
    let mut chain = vec![img.clone()];
    let (mut w, mut h) = img.dimensions();
    while w > 1 || h > 1 {
        w = (w / 2).max(1);
        h = (h / 2).max(1);
        let smaller = imageops::resize(
            chain.last().unwrap(),
            w, h,
            imageops::FilterType::Lanczos3,  // 高质量,慢
        );
        chain.push(smaller);
    }
    chain
}
```

`FilterType` 的选项值得记住:
- `Nearest`:最近邻,最快但锯齿
- `Triangle`:双线性,中等质量
- `CatmullRom`:双三次,锐利
- `Gaussian`:模糊,适合 downsample 抗 aliasing
- `Lanczos3`:窗口 sinc,最高质量但最慢(3 倍 CatmullRom 时间)

`fast_image_resize` 是 Rust 生态里**最快的 CPU 重采样库**,SIMD 加速,比 `image::imageops::resize` 快 5-10 倍。生产环境用它做 mipmap 生成。

GPU 端用 `wgpu` 的代码:

```rust
let texture = device.create_texture(&wgpu::TextureDescriptor {
    label: Some("grass texture"),
    size: wgpu::Extent3d { width: 512, height: 512, depth_or_array_layers: 1 },
    mip_level_count: 10,  // log2(512)+1 = 10 级
    sample_count: 1,
    dimension: wgpu::TextureDimension::D2,
    format: wgpu::TextureFormat::Rgba8UnormSrgb,  // 注意 Srgb 后缀
    usage: wgpu::TextureUsages::COPY_DST | wgpu::TextureUsages::SAMPLED
                | wgpu::TextureUsages::RENDER_ATTACHMENT,  // RENDER_ATTACHMENT 用于 GPU 端生成 mipmap
    view_formats: &[],
});

// wgpu 没内置 generate_mipmaps,要自己写 downsample shader
// wgpu examples 里有完整例子:wgpu/examples/mipmap
```

wgpu 的一个微妙点:**`mip_level_count` 必须满足 `texture dimensions >> mip_level_count >= 1`**。512x512 最多 10 级(512 = 2^9),如果你想给 500x500 的非 2 的幂纹理做 mipmap,最大 level 数是 floor(log2(500)) + 1 = 9。非 2 的幂纹理(NPOT)在早期 OpenGL 上不支持 mipmap,但 OpenGL 2.0+ 和所有现代 API(Vulkan、Metal、DX12、WebGPU)都支持。

## 4 · 认知地图

### 4.1 上级

- **Anti-aliasing** —— 消除走样(锯齿、闪烁)

## 5 · 对照与变奏

mipmap 的历史:

- **1983**:Williams 首次提出 pyramidal parametric discrete(原始论文)
- **1996**:Consumer GPU(Voodoo)开始支持 bilinear
- **1998**:Trilinear 成为标配
- **2000s**:Anisotropic filtering 进入主流
- **2010s**:Texture compression + mipmap 自动生成是 GPU 标准

工业化方向:从"手动指定各级 mipmap"到"GPU 自动生成",从"box filter"到"sRGB-aware filter"(避免暗化)。

一个有意思的细节:**sRGB texture 的 mipmap 必须在 sRGB 空间采 gamma-correct 平均**,否则远处变暗。Casey 这天没遇到这个问题(他用 linear),实际项目要注意。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 mipmap 用"取平均"做 downsample,而不是"取最近邻"?

**参考解答**:取平均是 box filter,在频域是低通滤波——去掉高频细节(就是远处看不见的细节),保留低频(整体颜色)。取最近邻是抽样,频域是抽样 + 复制频谱——会产生 aliasing(混叠),结果远处仍有闪烁。mipmap 的本质是"用低分辨率表示低频",而低通滤波器(取平均)恰好能取出低频。

### Lv2 · 动手实践

**题**:写一个 Rust 函数,生成 512x512 RGBA 纹理的完整 mipmap chain,返回所有 level。要求:

- 用 box filter(2x2 平均)
- 共 10 级(512 → 1)
- 打印每级的尺寸和字节数
- 验证总内存 < 原图的 4/3

**参考解答**:

```rust
fn downsample_2x2(
    src: &[u8], src_w: usize, src_h: usize,
) -> (Vec<u8>, usize, usize) {
    let dst_w = (src_w / 2).max(1);
    let dst_h = (src_h / 2).max(1);
    let mut dst = vec![0u8; dst_w * dst_h * 4];
    for y in 0..dst_h {
        for x in 0..dst_w {
            for c in 0..4 {
                let mut sum = 0u32;
                let mut count = 0u32;
                for sy in 0..2 {
                    for sx in 0..2 {
                        let px = x * 2 + sx;
                        let py = y * 2 + sy;
                        if px < src_w && py < src_h {
                            sum += src[(py * src_w + px) * 4 + c] as u32;
                            count += 1;
                        }
                    }
                }
                dst[(y * dst_w + x) * 4 + c] = (sum / count) as u8;
            }
        }
    }
    (dst, dst_w, dst_h)
}

fn generate_mipchain(
    mut src: Vec<u8>, mut w: usize, mut h: usize,
) -> Vec<(Vec<u8>, usize, usize)> {
    let mut chain = vec![(src.clone(), w, h)];
    while w > 1 || h > 1 {
        let (new_data, new_w, new_h) = downsample_2x2(&src, w, h);
        chain.push((new_data.clone(), new_w, new_h));
        src = new_data;
        w = new_w;
        h = new_h;
    }
    chain
}

fn main() {
    // 创建 512x512 RGBA 纹理(每像素随机色)
    let w = 512; let h = 512;
    let mut src = vec![0u8; w * h * 4];
    let mut s: u32 = 42;
    for byte in src.iter_mut() {
        s ^= s << 13; s ^= s >> 17; s ^= s << 5;
        *byte = (s & 0xff) as u8;
    }

    let chain = generate_mipchain(src, w, h);
    let mut total_bytes = 0;
    for (i, (data, lw, lh)) in chain.iter().enumerate() {
        println!("Level {}: {}x{} ({} bytes)", i, lw, lh, data.len());
        total_bytes += data.len();
    }
    println!("Total: {} bytes", total_bytes);
    println!("Original: {} bytes", w * h * 4);
    let ratio = total_bytes as f32 / (w * h * 4) as f32;
    println!("Ratio: {:.3} (should be < 1.333)", ratio);
    assert!(ratio < 4.0 / 3.0 + 0.01);
}
```

## 8 · Rust / Arch 落地代码

完整的 mipmap 生成 + 视觉验证:

```rust
// 生成 mipmap chain,带 gamma-correct(sRGB-aware)选项
fn downsample_srgb_aware(
    src: &[u8], src_w: usize, src_h: usize,
) -> (Vec<u8>, usize, usize) {
    let dst_w = (src_w / 2).max(1);
    let dst_h = (src_h / 2).max(1);
    let mut dst = vec![0u8; dst_w * dst_h * 4];

    fn srgb_to_linear(c: u8) -> f32 {
        let c = c as f32 / 255.0;
        if c <= 0.04045 { c / 12.92 } else { ((c + 0.055) / 1.055).powf(2.4) }
    }
    fn linear_to_srgb(c: f32) -> u8 {
        let c = if c <= 0.0031308 { c * 12.92 } else { 1.055 * c.powf(1.0 / 2.4) - 0.055 };
        (c.max(0.0).min(1.0) * 255.0) as u8
    }

    for y in 0..dst_h {
        for x in 0..dst_w {
            let mut linear_sum = [0.0f32; 3];
            let mut alpha_sum = 0u32;
            let mut count = 0u32;
            for sy in 0..2 {
                for sx in 0..2 {
                    let px = x * 2 + sx;
                    let py = y * 2 + sy;
                    if px < src_w && py < src_h {
                        for c in 0..3 {
                            linear_sum[c] += srgb_to_linear(src[(py * src_w + px) * 4 + c]);
                        }
                        alpha_sum += src[(py * src_w + px) * 4 + 3] as u32;
                        count += 1;
                    }
                }
            }
            for c in 0..3 {
                dst[(y * dst_w + x) * 4 + c] = linear_to_srgb(linear_sum[c] / count as f32);
            }
            dst[(y * dst_w + x) * 4 + 3] = (alpha_sum / count) as u8;
        }
    }
    (dst, dst_w, dst_h)
}

fn main() {
    // 简单测试:512x512 全红 + 一个黑点
    let w = 512; let h = 512;
    let mut src = vec![0u8; w * h * 4];
    for px in src.chunks_mut(4) {
        px[0] = 255; px[1] = 0; px[2] = 0; px[3] = 255;
    }
    // 中间一个白点
    let cx = w / 2; let cy = h / 2;
    src[(cy * w + cx) * 4 + 1] = 255;
    src[(cy * w + cx) * 4 + 2] = 255;

    println!("Original: {}x{} first pixel: {:?}", w, h, &src[0..4]);

    let (level1, w1, h1) = downsample_srgb_aware(&src, w, h);
    println!("Level 1: {}x{} first pixel: {:?}", w1, h1, &level1[0..4]);

    // 验证:原图全红 + 一个白点,downsample 后大部分像素还是红
    // (白点被平均到 1/4 像素,实际很难看出来,演示用)
}
```
