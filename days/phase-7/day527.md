
# Day 527 · 制作独立字体提取器

> 游戏需要字体来画 UI 文字(生命值、对话框、得分)。Casey 之前用过程序化字体(在 Day 100+ 自己画每个字符),但最终决定走更工业的路线——**从 TrueType/OpenType 字体文件提取字符 glyph(字形),转成位图,打包成游戏可用的位图字体**。Day 527 他做一个独立的工具:**Font Extractor(字体提取器)**,读 TTF/OTF,输出 PNG + 元数据。这是一个"工具"而不是"游戏代码"——它跑一次,产出资产,游戏运行时只用产出物。

## 0 · 为什么要有这一天

游戏的 UI 文字需要字体。两种方案:

**方案 A:运行时矢量字体**——在游戏运行时加载 TTF 文件,用 FreeType 库实时栅格化(把矢量 glyph 转像素)。优点:字体可任意大小、可任意缩放。缺点:每个字符每次画都要栅格化,性能差;依赖 FreeType,增加二进制大小。

**方案 B:预栅格化位图字体**——离线把 TTF 的每个字符栅格化一次,存成 PNG 图集(atlas),游戏运行时只查表 + blit。优点:运行时极快(只是图像拷贝)。缺点:字体大小固定(要 24px 就得预栅格化 24px)。

Casey 在 HH 选 B——因为 HH 是固定分辨率游戏(1280x720),字体大小固定,预栅格化最简单。Casey 在 Day 527 做的工具叫 `font_extractor`:`font_extractor input.ttf output.png output.hhf`,跑一次,产出游戏用的资产。

这个工具**独立于游戏**——不是 `game.exe` 的一部分,而是一个单独的可执行文件。这是工业级"资产管线(asset pipeline)"的标准模式:**离线工具** 跑一次,产出**运行时资产**。

为什么独立?三个原因:

第一,**职责清晰**。游戏的代码只关心运行时,字体提取只关心离线,两者分开。
第二,**语言自由**。字体提取可以用 Python、Rust、Go——只要产出格式约定好。游戏代码可以保持 C++ 不变。
第三,**性能隔离**。字体提取可能慢(几秒),不影响游戏启动速度。

#### 字体格式的两个家族:TTF vs OTF

让我把字体格式的"两大阵营"讲清楚,因为这是字体编程的基础知识。

**TrueType(TTF)**,Apple 1991 年设计。glyph 用 ** quadratic Bezier curves(二次贝塞尔曲线)**描述。每个 glyph 是一组闭合曲线,曲线围成的区域就是字符的形状。Apple 当年设计 TTF 是为了和 Adobe 的 Type 1 字体竞争,关键是 TTF 包含 **hinting(提示信息)**——一组指令告诉栅格化器在小字号时如何对齐像素,避免字符模糊。这是 TTF 的核心优势。

**OpenType(OTF)**,Microsoft + Adobe 1996 年设计,作为 TTF 的继任者。OTF 可以用两种 glyph 格式:**TrueType outlines**(同 TTF)或 **CFF outlines**(基于 PostScript,用 cubic Bezier 三次贝塞尔)。CFF outlines 在大字号时更精确,但栅格化稍慢。

实际选择:大部分现代字体两种格式都支持。Inter、Roboto、Fira Code 等流行字体都同时发布 TTF 和 OTF 版本。Casey 用 FreeType,它自动识别两种格式。

工业级游戏引擎都同时支持 TTF 和 OTF。Unity 的 TextMeshPro、Unreal 的 Slate 用 FreeType(开源)。Godot 用 stb_truetype 或自家 ETML。Rust 生态用 `ab_glyph`、`rusttype` 或 FreeType binding。

#### 位图字体的优势场景

虽然矢量字体是主流(动态缩放、可访问性),但**位图字体在游戏里有不可替代的优势**:

1. **像素艺术游戏**(Stardew Valley、Celeste):位图字体保证像素级精确,矢量字体在小字号模糊
2. **特效字体**(发光、描边、阴影):位图可以预先绘制特效,矢量要实时计算
3. **复古风格**:8-bit / 16-bit 游戏故意用位图字体模拟 NES/SNES 时代的字体
4. **嵌入式平台**:GPS、智能手表没有 FreeType 的算力,只能用位图

Casey 的 HH 接近"复古像素艺术",所以位图字体是合理选择。你的项目如果是 3D 高保真游戏,选矢量字体;2D 像素艺术选位图字体。

完成这一天之后,你具备:

- 理解 TTF/OTF 字体格式的基础(TrueType outlines, glyph IDs)
- 能用 `rusttype` 或 `ab_glyph` crate 栅格化字体
- 能设计"离线工具 + 运行时资产"的资产管线架构
- 知道在什么场景选位图字体、什么场景选矢量字体

## 1 · Casey 今天做了什么

Casey 这一天的动作可以拆成四步:

第一步,他**新建独立项目**:`font_extractor`,有自己的 `main()` 和 build script。和游戏 exe 平级,不是 DLL 也不是子目录。

第二步,他**集成 FreeType**(C 库,用 stb_truetype 替代也可以)——FreeType 是工业级字体栅格化库,几乎所有游戏(Unity、Unreal)和图形软件(Photoshop、GIMP)都用它。Casey 在 Day 100+ 已经手写过 stb_truetype 集成,这里他重用之前的工作。

第三步,他**写提取逻辑**:遍历 ASCII 32-126(可打印字符),对每个字符:
- 用 FreeType 加载 glyph(`FT_Load_Char`)
- 栅格化到灰度位图(`FT_Render_Glyph`)
- 把位图打包到一个 PNG atlas(每个字符占一个矩形区域)
- 记录每个字符在 atlas 中的位置(offset_x, offset_y, width, height)

第四步,他**输出两个文件**:PNG atlas(图像)+ HHFont 元数据(每个字符的位置和 metrics:advance width、bearing X/Y)。这两个文件一起被游戏加载,组合成位图字体。

## 2 · 心智模型

### 类比:出版社的"字体雕刻工"

想象你在做一本印刷书,需要用某种字体印。你拿到一个矢量字体文件(TTF),但印刷机不懂矢量——它需要"铅字字模",每个字符一个。

**字体提取器**就是"铅字雕刻工":它读矢量字体(TTF),把每个字符"雕刻"成铅字字模(栅格化位图),然后存到一个盒子里(PNG atlas)。游戏运行时从这个盒子里取字模,印到屏幕上。

出版业历史上真的就是这样:每个出版社有自己的雕刻工,生产字模,排版工从字模盒取字模排版。软件完全沿用了这个分工。

### 严谨展开:字体格式

**TrueType(TTF)** —— Apple 1991 年设计,用二次贝塞尔曲线描述 glyph 轮廓。每个 glyph 是一组点 + 控制点,栅格化时用扫描线填充。

**OpenType(OTF)** —— Microsoft + Adobe 1996 年设计,TrueType 的扩展,支持三次贝塞尔曲线(CFF/PostScript outlines)+ 高级排版特性(ligatures、kerning、small caps)。

**WOFF / WOOF2** —— Web 字体格式,本质是 TTF/OTF 的压缩包装。

这些格式都是矢量——存储 glyph 的数学描述,而不是像素。优点:任意大小不变形。缺点:栅格化需要计算,实时画 1000 个字符就要做 1000 次栅格化。

字体文件结构:

```
- header (offset table)
- table directory (表目录,如 cmap/glyf/head/hhea/hmtx/maxx/name/post...)
- 各 table 数据
```

关键表:

- `cmap` —— character code → glyph ID 的映射
- `glyf` —— glyph 轮廓数据(矢量点)
- `hmtx` —— horizontal metrics(advance width 等)
- `head` —— 字体元数据(units per em 等)

栅格化时:输入 character code → cmap 查 glyph ID → glyf 拿轮廓 → 扫描线填充得到像素位图。

### 位图字体 atlas

PNG atlas 是一张大图(比如 512×512),所有字符的小位图拼在里面。游戏运行时根据字符查表,得到该字符在 atlas 中的矩形区域,blit 到屏幕。

```
[ atlas 512x512 ]
+----+----+----+----+----+----+
| A  | B  | C  | D  | E  | F  |  <- 每个格子是一个字符
+----+----+----+----+----+----+
| G  | H  | I  | J  | K  | L  |
+----+----+----+----+----+----+
| M  | N  | O  | P  | Q  | R  |
+----+----+----+----+----+----+
| ...
```

Atlas 的好处:**一次纹理绑定**画所有字符。如果每个字符独立纹理,UI 文字画 100 个字符就是 100 次纹理切换,慢。

每个字符的元数据:

```rust
struct GlyphInfo {
    char_code: u32,         // 字符的 Unicode(如 'A' = 65)
    atlas_x: u32,           // 在 atlas 中的左上 x
    atlas_y: u32,           // 在 atlas 中的左上 y
    width: u32,             // 字符宽度
    height: u32,            // 字符高度
    bearing_x: i32,         // 字符左边距(可能负)
    bearing_y: i32,         // 字符顶边距(可能负)
    advance: f32,           // 字符占用的水平推进
}
```

`bearing_x`/`bearing_y` 描述字符相对光标位置的偏移(有些字符像 'j' 有下沉笔画,会延伸到 baseline 下方)。`advance` 是画完这个字符后光标右移多少。

### 离线工具 vs 运行时库

字体提取器是一个**离线工具**——开发期跑一次,产出 PNG + 元数据,游戏运行时直接用。对比**运行时库**(如 FreeType 在游戏里实时栅格化):

| 维度 | 离线工具 | 运行时库 |
|---|---|---|
| 启动速度 | 快(只加载 PNG) | 慢(每次栅格化) |
| 字体大小灵活 | 差(固定大小) | 好(任意大小) |
| 内存占用 | 小(已栅格化) | 中(字体文件 + 缓存) |
| 依赖 | 无(游戏只需 PNG) | FreeType/stb_truetype |

游戏行业两种方案都常见:console 游戏(固定分辨率)用离线,PC 游戏(玩家可调字体大小)用运行时。Casey 选离线,因为 HH 是教学项目,且 console-style。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏字体的工业方案:

- **bmfont**(AngelCode 出品,免费):经典工具,生成 PNG + .fnt 元数据
- **Distance Field Fonts**(Valve 2007 论文):把位图字体存成"距离场",运行时可任意缩放不失真。是现代 UI 的标配
- **MSDFG**(Multi-channel Signed Distance Field Generator):距离场的开源实现
- **Slug**:商业库,运行时高效栅格化矢量字体

 Casey 的位图字体方案是最低端的,但对 HH 足够。

游戏里字体的特殊需求:

- **国际化**:中文有 5000+ 常用字,atlss 不能装下所有。要么按需栅格化,要么限制字符集
- **emoji**:彩色字体(OpenType-SVG),需要特殊栅格化
- **变体**:粗体、斜体、light、bold 等多个变体,每个独立 atlas

### 3.2 · 图形学视角

字体的核心数学:**贝塞尔曲线**和**扫描线填充**。

二次贝塞尔曲线:`B(t) = (1-t)²P0 + 2(1-t)t·P1 + t²P2`,t ∈ [0,1]。
三次贝塞尔曲线:`B(t) = (1-t)³P0 + 3(1-t)²t·P1 + 3(1-t)t²·P2 + t³P3`。

TrueType 用二次,OpenType CFF 用三次。栅格化算法:对每条扫描线(y 固定),求所有曲线在该 y 的交点,排序,配对填充。这是经典计算机图形学算法,Graphics Gems 里有详细实现。

Distance field 字体的核心:**每个像素不存颜色,存到 glyph 边界的距离**。正距离=内部,负=外部。运行时根据阈值(0)= 边界,生成任意大小的字符。Valve 论文是这一领域的奠基。

### 3.3 · Linux 系统编程视角

### 3.4 · Rust 生态视角

Rust 字体库:

- **`rusttype`** —— 老牌,纯 Rust,栅格化矢量字体
- **`ab_glyph`** —— `rusttype` 作者的新版本,API 更简洁,性能更好
- **`fontdue`** —— 极致性能,适合游戏
- **`swash`** —— 复杂 shaping 支持

用 `ab_glyph` 栅格化:

```rust
// Cargo.toml:
// [dependencies]
// ab_glyph = "0.2"

use ab_glyph::{Font, FontRef, Glyph, PxScaleFont, ScaleFont};

fn extract_glyphs(font_path: &str, font_size: f32) -> Vec<(char, Vec<u8>, u32, u32)> {
    let font_data = std::fs::read(font_path).unwrap();
    let font = FontRef::try_from_slice(&font_data).unwrap();
    let scaled = PxScaleFont::from(font.as_scaled(font_size));
    
    let mut glyphs = Vec::new();
    for c in '!'..'~' {  // ASCII 可打印
        let glyph_id = font.glyph_id(c);
        let glyph: Glyph = glyph_id.with_scale_and_position(font_size, ab_glyph::point(0.0, 0.0));
        if let Some(outline) = font.outline_glyph(glyph.clone()) {
            let bounds = outline.px_bounds();
            let width = bounds.width().max(1.0) as u32;
            let height = bounds.height().max(1.0) as u32;
            let mut pixels = vec![0u8; (width * height) as usize];
            outline.draw(|x, y, coverage| {
                pixels[(y as u32 * width + x as u32) as usize] = (coverage * 255.0) as u8;
            });
            glyphs.push((c, pixels, width, height));
        }
    }
    glyphs
}
```

`ab_glyph::FontRef::try_from_slice` 零拷贝地解析字体——只读 offset table,实际 glyph 数据延迟加载。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:为什么字体提取器是独立工具,而不是游戏运行时代码的一部分?

**参考解答**:三个原因。第一,**职责分离**——离线工具关注"产出资产",游戏关注"用资产"。两者变化节奏不同(工具可能因为字体库升级要改,游戏不改)。第二,**语言自由**——工具可以用 Rust/Python/Go,只要产出格式约定。游戏代码不必依赖工具的依赖(FreeType 几 MB)。第三,**性能隔离**——工具跑一次产出资产,可能慢几秒;游戏运行时不重复跑。这是软件工程里"关注点分离(Separation of Concerns)"原则的应用。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:用 `ab_glyph` 提取一个系统字体的 ASCII 字符,把每个字符存成单独的小 PNG 文件(`char_65.png` 等)。运行后:`ls /tmp/font_out/` 看到 90+ 个 PNG 文件。

**参考解答**:

```rust
// Cargo.toml:
// [dependencies]
// ab_glyph = "0.2"
// image = "0.25"

use ab_glyph::{Font, FontRef, PxScaleFont, ScaleFont, Glyph};
use std::path::Path;

fn main() {
    // 用系统字体
    let font_path = "/usr/share/fonts/TTF/DejaVuSans.ttf";
    let font_data = std::fs::read(font_path).expect("read font");
    let font = FontRef::try_from_slice(&font_data).expect("parse font");
    
    let font_size = 32.0;
    let scaled = PxScaleFont::from(font.as_scaled(font_size));
    
    let out_dir = Path::new("/tmp/font_out");
    std::fs::create_dir_all(out_dir).unwrap();
    
    let mut count = 0;
    for c in '!'..'~' {  // ASCII 33-126
        let glyph_id = font.glyph_id(c);
        let glyph: Glyph = glyph_id.with_scale_and_position(
            font_size, 
            ab_glyph::point(0.0, scaled.ascent())
        );
        
        if let Some(outline) = font.outline_glyph(glyph.clone()) {
            let bounds = outline.px_bounds();
            let width = bounds.width().max(1.0) as u32;
            let height = bounds.height().max(1.0) as u32;
            
            // 灰度 → RGBA
            let mut pixels = vec![0u8; (width * height * 4) as usize];
            outline.draw(|x, y, coverage| {
                let idx = ((y * width + x) * 4) as usize;
                let alpha = (coverage * 255.0) as u8;
                pixels[idx..idx+4].copy_from_slice(&[255, 255, 255, alpha]);
            });
            
            let path = out_dir.join(format!("char_{}.png", c as u32));
            image::save_buffer(&path, &pixels, width, height, image::ColorType::Rgba8).unwrap();
            count += 1;
        }
    }
    println!("提取了 {} 个字符到 {}", count, out_dir.display());
}
```

为什么这么写:`ab_glyph::FontRef::try_from_slice` 零拷贝解析,适合大字体文件。`outline.draw` 是 callback 风格,对每个像素调一次,coverage ∈ [0,1]。把 coverage 转 alpha(0=透明,255=不透明),白色 RGBA,就是经典位图字体格式。

```rust
// 完整的字体提取器(独立工具)

use ab_glyph::{Font, FontRef, FontVec, Glyph, PxScale, PxScaleFont, ScaleFont};
use std::path::Path;

#[derive(Debug, Clone)]
struct GlyphMetadata {
    char_code: u32,
    atlas_x: u32,
    atlas_y: u32,
    width: u32,
    height: u32,
    bearing_x: i32,
    bearing_y: i32,
    advance: f32,
}

struct AtlasPacker {
    width: u32,
    height: u32,
    cursor_x: u32,
    cursor_y: u32,
    row_height: u32,
}

impl AtlasPacker {
    fn new(width: u32, height: u32) -> Self {
        Self { width, height, cursor_x: 0, cursor_y: 0, row_height: 0 }
    }
    
    /// 尝试把 w×h 的矩形装进 atlas,返回位置;失败返回 None
    fn pack(&mut self, w: u32, h: u32) -> Option<(u32, u32)> {
        if self.cursor_x + w > self.width {
            // 当前行装不下,换行
            self.cursor_y += self.row_height;
            self.cursor_x = 0;
            self.row_height = 0;
        }
        if self.cursor_y + h > self.height {
            return None;  // atlas 装不下了
        }
        let pos = (self.cursor_x, self.cursor_y);
        self.cursor_x += w;
        self.row_height = self.row_height.max(h);
        Some(pos)
    }
}

fn main() {
    let args: Vec<String> = std::env::args().collect();
    if args.len() != 4 {
        eprintln!("用法: {} input.ttf output.png output.hhf", args[0]);
        std::process::exit(1);
    }
    
    let (input_path, png_path, meta_path) = (&args[1], &args[2], &args[3]);
    
    // 1. 加载字体
    let font_data = std::fs::read(input_path).expect("read font");
    let font = FontRef::try_from_slice(&font_data).expect("parse font");
    let font_size = 32.0;
    let scaled = PxScaleFont::from(font.as_scaled(font_size));
    
    // 2. 提取所有字符
    let mut packer = AtlasPacker::new(512, 512);
    let mut atlas_pixels = vec![0u8; (512 * 512 * 4) as usize];  // RGBA
    let mut metadata: Vec<GlyphMetadata> = Vec::new();
    
    for c in '!'..'~' {
        let glyph_id = font.glyph_id(c);
        if glyph_id.0 == 0 { continue; }  // 字体不含此字符
        
        let glyph: Glyph = glyph_id.with_scale_and_position(
            PxScale::from(font_size),
            ab_glyph::point(0.0, scaled.ascent())
        );
        
        if let Some(outlined) = font.outline_glyph(glyph.clone()) {
            let bounds = outlined.px_bounds();
            let w = bounds.width().max(1.0) as u32;
            let h = bounds.height().max(1.0) as u32;
            
            if let Some((x, y)) = packer.pack(w, h) {
                outlined.draw(|px, py, coverage| {
                    if (px as u32) < w && (py as u32) < h {
                        let idx = (((y + py as u32) * 512 + (x + px as u32)) * 4) as usize;
                        let alpha = (coverage * 255.0) as u8;
                        atlas_pixels[idx..idx+4].copy_from_slice(&[255, 255, 255, alpha]);
                    }
                });
                
                metadata.push(GlyphMetadata {
                    char_code: c as u32,
                    atlas_x: x,
                    atlas_y: y,
                    width: w,
                    height: h,
                    bearing_x: bounds.min.x as i32,
                    bearing_y: bounds.min.y as i32,
                    advance: scaled.h_advance(glyph_id),
                });
            }
        }
    }
    
    // 3. 写 PNG atlas
    image::save_buffer(
        png_path,
        &atlas_pixels,
        512, 512,
        image::ColorType::Rgba8
    ).expect("write png");
    
    // 4. 写元数据(简化版,实际 Casey 用二进制)
    let meta_text = metadata.iter().map(|m| {
        format!("{}: pos=({},{}) size={}x{} advance={:.1}",
            char::from_u32(m.char_code).unwrap_or('?'),
            m.atlas_x, m.atlas_y, m.width, m.height, m.advance)
    }).collect::<Vec<_>>().join("\n");
    std::fs::write(meta_path, meta_text).expect("write meta");
    
    println!("提取 {} 个字符 → {} + {}", metadata.len(), png_path, meta_path);
}
```

出错怎么办:

- **`error: missing field in offset table`**:字体文件损坏或不支持。试另一个字体。
- **glyph 是空(0x0)**:字符不被字体支持(比如 emoji 在普通字体里)。检查 `glyph_id.0 == 0`。
- **atlas 装不下**:增大 atlas 尺寸(512×512 → 1024×1024),或减小字号。
- **PNG 文件超大**:字体大小越大,glyph 像素越多。试着减小字号。
