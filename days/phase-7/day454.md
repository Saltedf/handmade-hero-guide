# Day 454 · 解析 ZLIB 头部

> PNG 的 IHDR 之后是 IDAT,里面装的是 zlib 包装的 DEFLATE 压缩数据。今天 Casey 解析 zlib 头部 2 字节(CMF + FLG),为 Day 455+ 的 DEFLATE 解压做准备。

## 0 · 为什么要有这一天

PNG 用 zlib 作为压缩外层,zlib 内部用 DEFLATE 算法。两者关系:

```
PNG IDAT chunk data
  ↓
zlib wrapper(2 字节头 + DEFLATE 数据 + 4 字节 Adler-32 校验)
  ↓
DEFLATE stream(Huffman 编码的位流)
```

为什么要两层?**zlib 提供完整性校验和元数据**(压缩级别、滑动窗口大小),**DEFLATE 只关心压缩比**。这种"分层"是协议设计的常见模式——核心算法做一件事,wrapper 加元信息。

让我把"协议分层"的工程哲学讲深一些,这是 Day 454 的设计背景。

**为什么分层?** 工程上的"关注点分离(separation of concerns)"原则。每层只关心一件事:

- **DEFLATE 层**:压缩字节流。输入任意字节,输出压缩后的位流。不关心数据是 PNG 还是 zip。
- **zlib 层**:包装 DEFLATE,加完整性校验(Adler-32)、压缩参数(CMF/FLG)。
- **PNG 层**:把 zlib 包装进 IDAT chunk,加 PNG 自己的 CRC32 校验。

每层独立设计、独立测试、独立复用。gzip 也是 DEFLATE + 头尾,zip 内部也是 DEFLATE——同一个压缩核心,不同的 wrapper。这种分层让 DEFLATE 库(zlib, miniz)被无数项目复用,工程效率极高。

**类比:TCP/IP 协议栈**。互联网也是这样分层的——以太网层管物理传输,IP 层管路由,TCP 层管可靠传输,HTTP 层管应用。每层只看下一层提供的"服务",不关心下面怎么实现。

**zlib 头部 2 字节**。CMF(Compression Method and Flags)1 字节 + FLG(Flags)1 字节。

**CMF 字节解码**:

```
低 4 位:CM (Compression Method) — 必须 8 (DEFLATE)
高 4 位:CINFO (Compression Info) — 窗口大小的 log2 - 8
```

例:`0x78`(0111 1000)→ CM=8(低 4 位),CINFO=7(高 4 位)。CINFO=7 表示窗口大小 `2^(7+8) = 2^15 = 32 KB`——DEFLATE 最大窗口。

**FLG 字节解码**:

```
bit 5:  FDICT (是否用预设字典,通常 0)
bit 6-7: FLEVEL (压缩级别:0=最快, 1=快速, 2=默认, 3=最大压缩)
bit 0-4: FCHECK (CMF*256 + FLG 必须是 31 的倍数)
```

例:`0x9C`(1001 1100)→ FDICT=0,FLEVEL=2(默认),FCHECK=28。验证:`0x78 * 256 + 0x9C = 30876 = 31 * 996`。对!

**FCHECK 的妙处**。这个"必须 31 的倍数"用 5 位简单的数学约束,**保证头部本身有 1 字节错误也能被发现**——比 CRC 简单但够用。

**Adler-32 校验**。zlib 末尾的 4 字节 Adler-32 是 DEFLATE 解压后数据的校验。比 CRC32 简单(快但弱):

```rust
fn adler32(data: &[u8]) -> u32 {
    let mut a: u32 = 1;
    let mut b: u32 = 0;
    for &byte in data {
        a = (a + byte as u32) % 65521;
        b = (b + a) % 65521;
    }
    (b << 16) | a
}
```

`65521` 是小于 2^16 的最大素数。Adler-32 比 CRC32 快约 2 倍,但检测错误能力略弱。zlib 选它是性能优先。

## 补充:位流读取器(Bit Reader)

DEFLATE 是位级编码,不是字节级。Day 454 末尾或 Day 455 开头通常实现位流读取器——这是 PNG 解码的关键基础设施。

DEFLATE 的位排列规则是 **LSB first**(最低有效位优先)。一个字节 `0xAB = 1010 1011`(二进制,MSB 在左),DEFLATE 读它的顺序是 `1, 1, 0, 1, 0, 1, 0, 1`(从 LSB 到 MSB)。

**位读取器实现**:

```rust
struct BitReader<'a> {
    data: &'a [u8],
    byte_pos: usize,
    bit_pos: u8,  // 0..8,当前字节的当前位
}

impl<'a> BitReader<'a> {
    fn new(data: &'a [u8]) -> Self {
        Self { data, byte_pos: 0, bit_pos: 0 }
    }
    
    fn read_bits(&mut self, n: u8) -> u32 {
        let mut result: u32 = 0;
        for i in 0..n {
            if self.byte_pos >= self.data.len() {
                panic!("bit stream exhausted");
            }
            let bit = (self.data[self.byte_pos] >> self.bit_pos) & 1;
            result |= (bit as u32) << i;
            self.bit_pos += 1;
            if self.bit_pos == 8 {
                self.bit_pos = 0;
                self.byte_pos += 1;
            }
        }
        result
    }
    
    fn align_to_byte(&mut self) {
        if self.bit_pos != 0 {
            self.bit_pos = 0;
            self.byte_pos += 1;
        }
    }
}
```

每行解释:
- `byte_pos` 是当前字节,`bit_pos` 是当前位。
- `read_bits(n)` 读 n 位,从小到大填到 result 的低位。
- `align_to_byte` 把读取位置对齐到字节边界——DEFLATE 的某些段(Huffman 表)之后需要字节对齐。

**性能优化**。简单实现是 O(N) for N bits,慢。工业实现用**位缓冲区**——一次读 64 位到 u64,然后用位运算快速提取:

```rust
struct FastBitReader<'a> {
    data: &'a [u8],
    pos: usize,
    buffer: u64,
    bits_in_buffer: u8,
}

impl<'a> FastBitReader<'a> {
    fn read_bits(&mut self, n: u8) -> u32 {
        while self.bits_in_buffer < n {
            // 填充 buffer
            self.buffer |= (self.data[self.pos] as u64) << self.bits_in_buffer;
            self.pos += 1;
            self.bits_in_buffer += 8;
        }
        let result = (self.buffer & ((1 << n) - 1)) as u32;
        self.buffer >>= n;
        self.bits_in_buffer -= n;
        result
    }
}
```

每次填充一个字节到 64 位 buffer,然后用位运算一次取出 n 位。性能是简单版的 5-10 倍。工业 zlib / miniz 用这个模式。

## 补充:DEFLATE 算法的高层结构

让我给你 Day 455-457 的地图——DEFLATE 是 PNG 解码最复杂的部分。

**DEFLATE 的组成**。一个 DEFLATE stream 是一系列 block。每个 block:

1. **BFINAL**(1 位):是否最后一个 block
2. **BTYPE**(2 位):block 类型
   - 00:uncompressed(无压缩,数据原样)
   - 01:fixed Huffman(固定 Huffman 码)
   - 10:dynamic Huffman(动态 Huffman 码,块内带码表)
   - 11:reserved(错误)

3. **block 内容**:根据 BTYPE 不同。

**uncompressed block**(BTYPE=00)。最简单——字节对齐,然后是 LEN(2 字节)+ NLEN(2 字节,LEN 的位反码)+ LEN 字节数据。无压缩,用于"压缩效果差不如不压缩"的场景(已经是随机的数据)。

**fixed Huffman block**(BTYPE=01)。用预定义的 Huffman 码——DEFLATE 规范里有固定表。block 内容是 Huffman 编码的 literal/length 序列,中间穿插 LZ77 back-reference。

**dynamic Huffman block**(BTYPE=10)。最常用——block 开头编码自己的 Huffman 码表,然后用这个表编码数据。码表针对当前 block 优化,压缩率最好。

**LZ77 sliding window**。DEFLATE 用 LZ77 算法——发现数据中重复的子串,用 `(distance, length)` 引用代替。例如 "abcabc" 可以编码为 "abc" + reference(3 bytes back, length 3)。

LZ77 的"滑动窗口"是 32 KB——引用最多回看 32 KB。这是 zlib 头 CINFO 字段的含义。

**Huffman 编码**。LZ77 输出的 token(literal 字节、length、distance)用 Huffman 编码进一步压缩。Huffman 给频繁 token 短编码,稀有 token 长编码——信息论的最优前缀码。

Day 455 实现 Huffman 解码,Day 456 实现 LZ77 解码,Day 457 整合成完整 DEFLATE。理解这个结构,你就能跟 Casey 的代码节奏。

### zlib vs gzip vs zip 的家族关系

让我把 zlib、gzip、zip 三者的关系讲清楚,因为它们都用 DEFLATE 但 wrapper 不同。

**zlib**。最基础的 wrapper——2 字节头 + DEFLATE 数据 + 4 字节 Adler-32。用于嵌入式的压缩通道(HTTP Content-Encoding: deflate、PNG IDAT)。

**gzip**。zlib + 文件元数据——文件名、修改时间、OS 类型。**单一文件**压缩格式。`.gz` 后缀,`gzip / gunzip` 命令。HTTP `Content-Encoding: gzip`。

```
gzip 头:
  10 字节固定头(魔数 0x1F 0x8B + 版本 + flags)
  可选字段(原文件名、注释)
  DEFLATE 数据
  4 字节 CRC32(原数据校验)
  4 字节 ISIZE(原数据大小 mod 2^32)
```

gzip 比 zlib 多了文件元数据,但仍只压缩**一个文件**。

**zip**。多文件归档 + 每个文件独立压缩:

```
zip 结构:
  Local File Header 1 + Compressed Data 1
  Local File Header 2 + Compressed Data 2
  ...
  Central Directory(所有文件的元数据)
  End of Central Directory Record
```

每个 Local File Header 包含文件名、压缩方法(通常是 DEFLATE)、压缩前后大小、CRC32。Central Directory 在文件末尾,列出所有文件——这让 zip 文件可以从中间开始读(不用扫整个文件)。

**对比**:

| 格式 | 用途 | 文件数 | 元数据 | 压缩 |
|---|---|---|---|---|
| zlib | 通道压缩 | 1 | 最少 | DEFLATE |
| gzip | 单文件 | 1 | 多 | DEFLATE |
| zip | 多文件归档 | N | 丰富 | DEFLATE / 其他 |

**为什么 PNG 用 zlib 而非 gzip?** PNG 的 IDAT chunk 内部需要"纯压缩数据 + 校验",不需要文件元数据(文件名等已经在 PNG chunk 系统里)。zlib 提供最薄的 wrapper,最合适。

**工业工具**:

```bash
# zlib 解压(用 Python)
python3 -c "import zlib; data = open('idat.bin', 'rb').read(); print(zlib.decompress(data))"

# gzip 解压
gunzip file.gz

# zip 解压
unzip file.zip
```

所有这些工具底下都是 DEFLATE——这就是为什么"理解 DEFLATE"在工业里如此重要。一通百通。

## 2 · 心智模型

### 类比:快递包裹的运输标签

zlib 头部 2 字节像快递公司贴在包裹外的运输标签:标明用了什么快递(DEFLATE)、最大包装尺寸(窗口大小)、是否易碎(预设字典标志)。运输标签本身不参与"装什么",但告诉接收方怎么处理包裹。

### zlib 头部 2 字节

```
字节 0: CMF(Compression Method and Flags)
  bit 0-3: CM(Compression Method, 必须 8 = DEFLATE)
  bit 4-7: CINFO(Compression Info, 窗口大小 = 2^(CINFO + 8) 字节)
           CINFO=7 → 窗口 32KB(最大)
           CINFO=0 → 窗口 256B(最小)

字节 1: FLG(Flags)
  bit 0-4: FCHECK(5 位校验和)
  bit 5:   FDICT(是否使用预设字典,通常 0)
  bit 6-7: FLEVEL(压缩级别 0-3,信息性)
```

**校验和规则**:`(CMF * 256 + FLG) % 31 == 0`。这是设计简单的 31 进制校验,确保头部字节没被损坏。31 选质数,Mod 31 用位运算可以快速算。

### CMF 和 FLG 的常见值

PNG 几乎永远用:
- `CMF = 0x78`(CM=8, CINFO=7)
- `FLG = 0x9C`(FCHECK=28, FDICT=0, FLEVEL=2)

`0x78 = 0111 1000`,低 4 位 `1000` = 8 (DEFLATE),高 4 位 `0111` = 7 (32KB 窗口)。
`0x9C = 1001 1100`,低 5 位 `11100` = 28 (FCHECK),bit 5 `0` (无 FDICT),高 2 位 `10` = 2 (默认级别)。

`(0x78 * 256 + 0x9C) = 30876`,`30876 / 31 = 996` 整除。校验通过。

### Rust 实现

```rust
struct ZlibHeader {
    cm: u8,
    cinfo: u8,
    fdict: bool,
    flevel: u8,
}

fn parse_zlib_header(data: &[u8]) -> Result<ZlibHeader, String> {
    if data.len() < 2 {
        return Err("zlib header too short".into());
    }
    let cmf = data[0];
    let flg = data[1];
    
    // 校验:(CMF * 256 + FLG) % 31 == 0
    let check = ((cmf as u16) << 8 | flg as u16) % 31;
    if check != 0 {
        return Err(format!("zlib header check failed: {} mod 31 = {}", 
            (cmf as u16) << 8 | flg as u16, check));
    }
    
    let cm = cmf & 0x0F;
    let cinfo = (cmf >> 4) & 0x0F;
    let fdict = (flg & 0x20) != 0;
    let flevel = (flg >> 6) & 0x03;
    
    if cm != 8 {
        return Err(format!("Compression method {} not supported (only 8/DEFLATE)", cm));
    }
    if cinfo > 7 {
        return Err(format!("CINFO {} invalid (> 7)", cinfo));
    }
    
    Ok(ZlibHeader { cm, cinfo, fdict, flevel })
}
```

每行解释:
- `(cmf as u16) << 8 | flg as u16` — 把 CMF 和 FLG 拼成 16 位,模拟 `CMF * 256 + FLG`。
- `% 31` — zlib 校验,31 是 RFC 1950 指定。
- `& 0x0F` — 取低 4 位。
- `& 0x20` — 检查 bit 5(FDICT)。
- `>> 6 & 0x03` — 取高 2 位(FLEVEL)。
- cm 必须 8(DEFLATE 是 zlib 唯一支持的压缩方法)。

### 窗口大小的意义

CINFO 决定 DEFLATE 解压时的滑动窗口大小:

```
window_size = 2^(CINFO + 8) 字节
```

CINFO=7 → 32768 字节(32KB)。窗口大小决定 DEFLATE 能"回看多远"找重复数据。窗口越大压缩率越高,但内存占用越多。

PNG 永远用 CINFO=7(32KB),因为现代机器不在乎这点内存。但 zlib 协议允许更小窗口,适应嵌入式设备。

### 接下来:DEFLATE

zlib 头部之后的所有字节(除最后 4 字节 Adler-32 校验)都是 DEFLATE stream。Day 455 开始解析。

DEFLATE stream 是**位流**(bit stream),不是字节流——数据按 bit 切分,可能 1 bit、3 bit、5 bit、9 bit 等。这是为了压缩比。Day 455 实现 bit reader。

## 3 · 四域深入

### 3.1 · 游戏编程视角

zlib / DEFLATE 在游戏里:

- **PNG 纹理**(本日)
- **ZIP 包**:游戏打包多个资产成 .zip
- **网络协议**:HTTP gzip、WebSocket permessage-deflate

工业坑:**zlib 解压慢**。100MB ZIP 解压要几百毫秒,不适合实时。游戏启动时预解压到 GPU,运行时不碰 zlib。

### 3.2 · 图形学视角

PNG 压缩对图形学:
- **像素艺术**:**压缩比极高**(10:1+),因为像素重复多
- **照片**:**压缩比一般**(2:1),因为高频细节多
- **UI / 截图**:中等(3:1)

纹理压缩格式(BCn / ETC / ASTC)和 DEFLATE 是**不同概念**:
- DEFLATE:CPU 解压,适合存盘和传输
- BCn:GPU 直接采样,适合运行时纹理

游戏流水线:PNG(DEFLATE)→ BCn(GPU 格式)打包,运行时只用 BCn。

### 3.3 · Linux 系统编程视角

Linux 上 zlib / gzip / zip 的关系:

```
DEFLATE:核心压缩算法(RFC 1951)
zlib:DEFLATE + 头部 + Adler-32(RFC 1950)
gzip:DEFLATE + 头部 + CRC32(RFC 1952)
zip:多个文件 + 各自 DEFLATE,跨平台归档
```

都基于 DEFLATE,但 wrapper 不同。命令行工具:

```bash
# zlib(少见,但 PNG 内部用)
echo "hello" | openssl zlib | hexdump -C

# gzip(网页 / 文件压缩)
echo "hello" | gzip | hexdump -C
# 输出:1f 8b 08 00 ...(magic 1f 8b,然后 CM=8)

# 真正的 PNG 文件用 zlib wrapper
xxd test.png | grep "49 44 41 54"  # IDAT chunk

# 用 zcat 直接读 gzip 文件
echo "hello" | gzip > /tmp/hello.gz
zcat /tmp/hello.gz  # 输出 hello

# 用 zlib-flate 解压 zlib 流(需要安装)
sudo pacman -S zlib
```

Linux 内核也用 zlib:内核镜像(vmlinuz)是 gzip,initramfs 是 cpio+gzip,某些文件系统(Btrfs)有 zlib 压缩选项。

### 4.1 上级

- **协议分层(layering)** — 核心算法 + wrapper 元数据
- **校验和(checksum)** — 检测数据损坏

| 格式 | Wrapper |
|---|---|

## 5 · 对照与变奏

**不同压缩算法的对比**:

| 算法 | 压缩比 | 速度 | 用途 |
|---|---|---|---|
| DEFLATE | 中 | 中 | PNG/ZIP/HTTP |
| LZ4 | 低 | 极快 | 实时 |
| Zstd | 高 | 快 | 现代 |
| Brotli | 高 | 中 | HTTP |
| LZMA | 高 | 慢 | 归档 |
| Bzip2 | 高 | 慢 | 归档 |

**为什么 DEFLATE 流行?** 1990s Phil Katz 设计,简洁、专利免费、压缩比够好。即使今天 Zstd 更优,DEFLATE 仍是兼容性最好的格式。

**历史**:
- 1977:LZ77(Lempel-Ziv)算法
- 1990s:Phil Katz 改进为 DEFLATE,PKZIP 使用
- 1996:PNG 标准化,选 zlib
- 2010s:LZ4、Zstd 出现,但 DEFLATE 仍是 baseline

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 zlib 用 `% 31` 校验,而不是 CRC32?

**参考解答**:31 是质数,Mod 31 可以快速用加减算(无需乘除)。32 - 1 = 31,这种"2^n - 1"校验和叫 **Fletcher checksum** 的变体。

CRC32 强得多(检测所有 ≤3 位错误),但慢。zlib 头部只有 2 字节,5 位校验和(FCHECK)够防大多数损坏。Adler-32(末尾)更强但仍弱于 CRC32。zlib 的设计哲学:**头部轻量,数据校验用更强的 Adler-32**。

### Lv2 · 动手实践

**题**:实现 `parse_zlib_header`,读一张真实 PNG 的 IDAT 数据前 2 字节,验证它们是合法 zlib 头部。

**参考解答**:

```rust
// (PngReader 见 day453)

struct ZlibHeader {
    cm: u8,
    cinfo: u8,
    fdict: bool,
    flevel: u8,
}

fn parse_zlib_header(data: &[u8]) -> Result<ZlibHeader, String> {
    if data.len() < 2 {
        return Err("zlib header too short".into());
    }
    let cmf = data[0];
    let flg = data[1];
    let combined = ((cmf as u16) << 8) | (flg as u16);
    if combined % 31 != 0 {
        return Err(format!("zlib check failed: {} % 31 = {}", combined, combined % 31));
    }
    let cm = cmf & 0x0F;
    let cinfo = (cmf >> 4) & 0x0F;
    let fdict = (flg & 0x20) != 0;
    let flevel = (flg >> 6) & 0x03;
    if cm != 8 {
        return Err(format!("CM={} (must be 8)", cm));
    }
    if cinfo > 7 {
        return Err(format!("CINFO={} (must be <= 7)", cinfo));
    }
    Ok(ZlibHeader { cm, cinfo, fdict, flevel })
}

fn main() -> Result<(), String> {
    let args: Vec<_> = std::env::args().collect();
    let data = std::fs::read(args.get(1).ok_or("usage")?).map_err(|e| e.to_string())?;
    
    // PNG magic
    if data[..8] != [0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A] {
        return Err("Not PNG".into());
    }
    
    // 找第一个 IDAT
    let mut cursor = 8usize;
    loop {
        let length = u32::from_be_bytes([data[cursor], data[cursor+1], data[cursor+2], data[cursor+3]]) as usize;
        let ctype = &data[cursor+4..cursor+8];
        cursor += 8;
        if ctype == b"IDAT" {
            // 解析 zlib 头部
            let header = parse_zlib_header(&data[cursor..cursor+2])?;
            println!("IDAT found at {}, zlib header:", cursor - 8);
            println!("  CM:    {} (DEFLATE)", header.cm);
            println!("  CINFO: {} (window = 2^({}+8) = {} bytes)",
                header.cinfo, header.cinfo, 1 << (header.cinfo + 8));
            println!("  FDICT: {}", header.fdict);
            println!("  FLEVEL: {} ({})", header.flevel, match header.flevel {
                0 => "fastest", 1 => "fast", 2 => "default", 3 => "max", _ => "?"
            });
            break;
        }
        cursor += length + 4;  // data + CRC
    }
    Ok(())
}
```

每行解释:
- 找到 IDAT chunk 后,前 2 字节是 zlib 头部。
- `1 << (header.cinfo + 8)` — 计算窗口大小。
- FLEVEL 是信息性的,解压器可以忽略。

完成标准:跑 `cargo run -- /tmp/test.png`,输出 zlib 头部字段,所有合法 PNG 都应该 CM=8、CINFO≤7、校验通过。

## 8 · Rust / Arch 落地代码

完整 zlib 头部解析器 + 多 IDAT 拼接:

```rust
// (PngReader 见 day453)

struct ZlibHeader {
    cm: u8,
    cinfo: u8,
    fdict: bool,
    flevel: u8,
}

fn parse_zlib_header(data: &[u8]) -> Result<ZlibHeader, String> {
    if data.len() < 2 {
        return Err("zlib header too short".into());
    }
    let cmf = data[0];
    let flg = data[1];
    let combined = ((cmf as u16) << 8) | (flg as u16);
    if combined % 31 != 0 {
        return Err(format!("zlib check: {} % 31 = {}", combined, combined % 31));
    }
    let cm = cmf & 0x0F;
    let cinfo = (cmf >> 4) & 0x0F;
    let fdict = (flg & 0x20) != 0;
    let flevel = (flg >> 6) & 0x03;
    if cm != 8 {
        return Err(format!("CM={} not supported", cm));
    }
    if cinfo > 7 {
        return Err(format!("CINFO={} invalid", cinfo));
    }
    Ok(ZlibHeader { cm, cinfo, fdict, flevel })
}

fn collect_idat(data: &[u8]) -> Result<Vec<u8>, String> {
    // PNG magic
    const MAGIC: [u8; 8] = [0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A];
    if data.len() < 8 || data[..8] != MAGIC {
        return Err("Not PNG".into());
    }
    
    let mut cursor = 8usize;
    let mut idat_data = Vec::new();
    
    loop {
        if cursor + 8 > data.len() {
            return Err("Truncated".into());
        }
        let length = u32::from_be_bytes([
            data[cursor], data[cursor+1], data[cursor+2], data[cursor+3]
        ]) as usize;
        let ctype = &data[cursor+4..cursor+8];
        cursor += 8;
        
        if ctype == b"IDAT" {
            idat_data.extend_from_slice(&data[cursor..cursor+length]);
        } else if ctype == b"IEND" {
            break;
        }
        
        cursor += length + 4;  // data + CRC
    }
    
    Ok(idat_data)
}

fn main() -> Result<(), String> {
    let args: Vec<_> = std::env::args().collect();
    let data = std::fs::read(args.get(1).ok_or("usage")?).map_err(|e| e.to_string())?;
    
    let idat = collect_idat(&data)?;
    println!("Total IDAT size: {} bytes", idat.len());
    
    let header = parse_zlib_header(&idat)?;
    println!("zlib header:");
    println!("  CM={}(DEFLATE), CINFO={}(window {}KB)",
        header.cm, header.cinfo, (1 << (header.cinfo + 8)) / 1024);
    println!("  FDICT={}, FLEVEL={}", header.fdict, header.flevel);
    
    // 末尾 4 字节是 Adler-32
    if idat.len() >= 6 {
        let adler = u32::from_be_bytes([
            idat[idat.len()-4], idat[idat.len()-3],
            idat[idat.len()-2], idat[idat.len()-1]
        ]);
        println!("Adler-32 checksum: {:08x}", adler);
        println!("(中间 {} 字节是 DEFLATE stream)", idat.len() - 6);
    }
    
    Ok(())
}
```

每行解释:
- `collect_idat` 把所有 IDAT chunk 的数据拼接(PNG 允许 IDAT 分多个 chunk)。
- 拼接后第一字节是 zlib CMF,第二是 FLG,中间是 DEFLATE,最后 4 字节 Adler-32。
- `1 << (header.cinfo + 8)` — 窗口字节数,除以 1024 得 KB。
