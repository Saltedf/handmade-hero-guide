
# Day 497 · 开始清理资产系统

> Day 496 调试完附接点 bug,Casey 留下一堆"刚才为了赶进度没整理"的代码。今天起连续两天他做"清道夫"——把临时变量、重复结构、耦合的 API 拆开。这是商业项目里最高频的动作:**重构(refactor)**,不加功能、不改行为,只让代码更可读、更易改。

## 0 · 为什么要有这一天

你大概经历过这种事:

- 为了赶一个 deadline,你写了一个函数 `load_asset`——它接受文件路径、读字节、解压、解析、生成 GPU 纹理、塞进缓存,300 行,中间 7 层 if-else
- deadline 过后,你想加一个新功能("支持 KTX2 格式"),打开 `load_asset` 看了 5 分钟,决定关掉——它太复杂,改一个地方会牵连 10 个地方
- 这就是"**技术债**(technical debt)":你为了短期速度牺牲了长期可维护性,欠下的债每天都在生利息

Casey 在 Day 436-496 跑了 60 天,为了演示各种特性(热重载、附接点、tag 系统),代码里塞了:

- 3 种不同的"asset id"类型(数字、字符串、hash)
- 4 个独立的"加载"函数(load_bitmap, load_png, load_hha_image, load_hha_sound)
- 2 套缓存系统(LRU + 永久)
- 散落在 5 个文件里的死代码

今天 Casey 决定**停下来还债**。这不是因为代码"丑",而是因为**下一个功能(编辑器保存)需要在这堆代码上加东西**,如果不先清理,加东西时 80% 时间会花在"理解旧代码"上,而不是"写新代码"。

更深层的原因:**重构是软件工程师和"会写代码的人"的分水岭**。会写代码的人能堆功能;软件工程师能在堆功能的同时保持代码可维护。Casey 这两天就是在示范"怎么把'能跑'升级成'能改'"。

心理锚点:看完今天,你能做到:**拿一段你自己写的、3 个月前的代码,用 30 分钟把它的"重复结构"列出来,设计一个统一的抽象消除重复**。你还能解释什么是"提取函数"、"提升类型"、"合并参数"这三种最常见的重构手法,以及为什么"重构前先保证有测试"。

## 1 · Casey 今天做了什么

Casey 今天的工作流是经典的"红绿黄"重构循环:

第一步,**列出所有"资产"类型**:bitmap、sound、font、model。他发现每种类型都有自己的 `XxxId` 结构(`BitmapId`、`SoundId`……),内部都是 `u32` 索引。这是明显的重复。

第二步,**统一 ID 类型**。他定义一个通用 `AssetId { type_tag: AssetType, index: u32 }`,`AssetType` 是 enum。所有原来的 `BitmapId` 都变成 `AssetId { type_tag: Bitmap, ... }`。

第三步,**统一加载入口**。他把 4 个 `load_xxx` 函数合成一个 `load_asset(id: AssetId) -> AssetSlot`,内部根据 `type_tag` 分发。

第四步,**移除死代码**。他用 `git grep` 找到 5 处定义但未调用的函数,删掉。

今天没写新功能,但代码减少了 ~400 行,API 表面减少了 30%。Casey 在视频里反复强调一句:"**重构不需要理由,不重构才需要理由**"——意思是默认就该重构,除非有明确的"现在不能动"的理由(发布前夕、未知风险)。

## 2 · 心智模型

### 类比:重构是"整理衣柜"

你的衣柜一开始所有衣服都挂得好好的。一年后,T 恤、外套、内裤混在一起,你每次找一件都得翻 5 分钟。整理衣柜不是买新衣服,而是**分类、归位、扔掉破的**。

重构 = 给代码整理衣柜:

- **提取函数(extract function)**:把一段 100 行的代码拆成 5 个 20 行的小函数,每个函数名说明它干嘛。等于把一摞衣服分成"外套/T 恤/裤子"三摞。
- **提升类型(lift type)**:发现 5 个结构体都长得一样,合成一个带 tag 的 union。等于发现 5 个抽屉都装袜子,合并成一个袜子抽屉。
- **合并参数(parameter object)**:一个函数原本接受 8 个参数,把相关的 4 个组成一个 struct 传进去。等于把零散的钥匙、钱包、手机装进一个包。

### 严谨原理:重构的三条铁律

Martin Fowler(《Refactoring》作者)给的三条:

1. **不改行为**:重构前后,程序对外可见的行为完全一样。测试用例一个不改,全过。
2. **小步快走**:每次只改一点(一个函数、一个变量),改完立刻编译 + 跑测试。绝不"一次重构 1000 行"。
3. **自动化**:用工具(rustfmt、clippy、IDE 重构功能)做机械改动,人脑只做"想清楚怎么拆"。

第三条尤其重要。Fowler 的书 1999 年第一版是 Java 版,所有重构手法都配对应的"自动化工具操作"。今天 Rust 生态有 rust-analyzer,90% 的重构可以一键完成——右键 → Refactor → Rename,所有引用自动更新。

### 重构 vs 重写

新手常把"重构"和"重写"搞混:

- **重构**:在原代码上小步修改,行为不变,逐步改善内部结构。风险低,可回滚。
- **重写**:丢掉旧代码,从零写新代码。风险高,容易引入新 bug,业界名言:"重写是软件项目失败的头号原因"(Joel Spolsky 的经典文章 "Things You Should Never Do")。

Casey 永远是重构,不是重写。哪怕 HHA V0 → V1(Day 465)也是"加新读路径,旧读路径并存",而不是"删掉旧代码重写"。这就是所谓的"**双轨过渡**":新代码和旧代码并存,逐步把流量从旧的迁到新的,最后删掉旧的。比一次性重写安全得多。

### 重构的"嗅觉":什么时候该重构

Fowler 总结了 22 种"代码臭味(code smell)"提示你该重构。今天 Casey 触到 3 个:

- **重复代码(duplicated code)**:4 个 `load_xxx` 函数 80% 相同——这是最有力的重构信号
- **过长函数(long function)**:`load_asset` 300 行——拆成多个小函数
- **散弹式修改(shotgun surgery)**:加一种新资产要改 5 个文件——说明抽象边界划错了

臭味不是 bug,是"未来很可能出 bug"的信号。闻到臭味就该重构——不是因为它现在错,而是因为它将来易错。

### Casey 的具体动作:统一 AssetId

Day 496 之前的代码:

```rust
struct BitmapId(u32);
struct SoundId(u32);
struct FontId(u32);
struct ModelId(u32);

fn load_bitmap(id: BitmapId) -> Bitmap { ... }
fn load_sound(id: SoundId) -> Sound { ... }
// ... 重复 4 次
```

每个 `XxxId` 都是一个 `u32` newtype(新类型模式),功能完全一样。Casey 把它们合成:

```rust
enum AssetType { Bitmap, Sound, Font, Model }

struct AssetId {
    type_tag: AssetType,
    index: u32,
}

fn load_asset(id: AssetId) -> AssetSlot {
    match id.type_tag {
        AssetType::Bitmap => load_bitmap_inner(id.index),
        AssetType::Sound  => load_sound_inner(id.index),
        // ...
    }
}
```

好处:任何"对资产"的 API(缓存、卸载、热重载)现在只写一遍。代价:每次调用多了一个 match 分发(几乎零成本)。

### newtype 模式回顾

`struct BitmapId(u32);` 是 Rust 的 **newtype 模式**:包一层新类型,既阻止了"不小心把 SoundId 当 BitmapId 用",又零运行时成本(编译期就退化为 u32)。

Casey 现在的"反 newtype"做法看似倒退,其实是更高层的抽象:不再有 4 种 ID 类型,而是一种带 tag 的 ID。这是抽象层级的提升——`AssetId` 是更宽的概念。

但 newtype 仍有价值——它阻止了"两个不同语义的 u32 被混用"。统一后,Casey 必须在 AssetId 里加 `type_tag` 来恢复这种区分。这是抽象的"代价":用 type_tag 字段换 API 统一性。

### 测试是重构的前提

Fowler 的另一条铁律:**没有测试不要重构**。因为重构后你怎么知道行为没变?测试。

Casey 在 Day 200+ 加了基础单元测试(`#[test]` 函数),覆盖了资产加载的核心路径。今天的重构每改一步,跑一次 `cargo test`,全绿才继续。这是"红绿黄"循环的来源:

- **红**:写测试(可能失败)
- **绿**:改代码让测试通过
- **黄**:重构(测试仍然绿)

如果你跳过测试重构,等于闭眼开车——你以为路直,可能已经开到沟里。

---

**总结**:重构是商业项目的高频动作,核心是"不改行为、小步快走、消除重复"。今天的 AssetId 统一是经典的"提升类型"手法。下一节看四个领域里怎么用。

### 重构的商业价值

让我们把镜头拉远,看重构的工业级意义。

软件项目失败的常见原因不是"功能不够",而是"代码烂到无法继续"。具体表现:
- 加一个简单功能要改 10 处代码(散弹式修改)
- 改一处代码引发 3 个不相关 bug(耦合)
- 新员工 3 周才能改第一个 bug(可读性差)
- 一个 bug 修了 5 次,每次在不同地方(重复代码)

这些都是"技术债"的症状。Martin Fowler 的《Refactoring》一书的核心论点:**重构是日常开发的一部分,不是"特殊活动"**。每次加功能前 / 后,花 10-30% 时间重构附近代码,长期项目健康。

工业级重构的 KPI(关键绩效指标):
- **Cyclomatic complexity**(圈复杂度):每函数分支数。理想 < 10。
- **Coupling**(耦合度):模块 A 改动影响多少模块。理想 < 3。
- **Cohesion**(内聚度):模块内代码相关性。理想高(单一职责)。
- **Test coverage**(测试覆盖):重构安全网。理想 > 80%。

工具:`cargo clippy`、`cargo audit`、`cargo bloat`、SonarQube。Rust 生态的 clippy 是金标——它会指出"这段代码可以重构得更地道",并给出建议。

### 重构 vs 优化的区别

新手常把"重构"和"优化"搞混:

**重构(refactor)**:不改行为,改内部结构,提升可读性 / 可维护性。例:把 300 行函数拆成 5 个 20 行小函数。**测试不变,全过**。

**优化(optimize)**:不改语义(对外行为),改性能(更快 / 更省内存)。例:用 SIMD 替代 scalar 循环。**测试不变,全过**,但 profile 显示更快。

两者常一起做——重构让代码清晰后,优化更易。但**先重构,后优化**,不要为了优化牺牲可读性("Premature optimization is the root of all evil"——Donald Knuth)。

Casey Day 497 是纯重构——代码行为不变,但 AssetId 统一后,未来加新资产类型只改 1 处(优化加新功能的速度)。

### 3.1 · 🎮 游戏编程视角

游戏开发里"资产系统"是基础设施层——所有美术资源(贴图、模型、音频、动画)都流经它。它做得好,加新内容是几分钟的事;做得差,加一张贴图要改 5 处代码。

业界主流的资产系统设计:

- **Unreal Engine**:用 UObject 系统,所有资产继承一个基类,有反射(运行时知道自己的字段)。强项:编辑器深度集成。弱项:启动慢、内存大。
- **Unity**:用 ScriptableObject,数据资产是序列化对象。强项:编辑器友好。弱项:类型耦合到 Unity 引擎。
- **Bevy**(Rust):用 ECS + Resource,资产是 `Asset<T>` 类型,通过 handle 引用。强项:类型安全 + ECS 一体。弱项:生态年轻。
- **Casey 的 HH**:手写,极简,AssetId + slot table,够用就好。强项:完全可控、易理解。弱项:功能少。

Casey 的设计哲学和工业引擎不同:工业引擎追求"通用",Casey 追求"刚好"。Day 497 的重构不是为了像 Bevy,而是为了让"加新资产类型"这一件事的成本降到最低。

游戏开发圈对资产系统的另一条经验:**资产 ID 必须是稳定的**。如果你给一个贴图分配了 ID = 5,然后某次重构后变成 ID = 7,所有引用这个贴图的代码都断了。Casey 用"hash 文件名"作为 ID 的算法,保证同名文件永远同 ID,这就是稳定性的来源。

### 3.2 · 🎨 图形学视角

资产系统对图形学的影响体现在"纹理上传"。同一个 bitmap 资产,可能被引用多次(同一个贴图用在 10 个 entity 上)。资产系统负责:

- **去重**:只上传一次到 GPU
- **LRU 卸载**:显存满了,卸载最近最久没用的
- **热重载**:磁盘文件改了,重新上传
- **异步加载**:大资产在后台线程加载,不卡主线程

Casey 在 Day 507(LRU 纹理句柄复用)会专门讲这个。今天的重构打基础——统一 ID 让 LRU 算法只用写一遍。

另一个图形学视角:不同资产类型有不同的"加载特征":

| 类型 | 大小 | 解码时间 | GPU 占用 |
|---|---|---|---|
| Bitmap | 中(几 MB) | 快(<10ms) | 大(显存) |
| Sound | 小(<1MB) | 极快(<1ms) | 小(音频缓冲) |
| Font | 极小(<100KB) | 慢(光栅化) | 中(纹理图集) |
| Model | 大(几十 MB) | 中(几十 ms) | 大(VBO) |

资产系统要识别这些差异——比如 Model 加载必须异步,Sound 可以同步。统一 ID 后,这些差异封装在 `load_xxx_inner` 里,对外的 `load_asset` 接口不变。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上"资产"对应"文件 + 内存映射"。重构资产系统时涉及几个 Linux 概念:

- **mmap**:把文件直接映射到内存,不需要 read 系统调用。Casey 的 HHA 加载可以用 mmap 提速,但他选择 `read` 因为简单。
- **inotify**:监控文件变化,实现热重载。Casey 的热重载目前是定时检查 mtime,inotify 更高效(事件驱动)。
- **/proc/<pid>/maps**:查看进程映射了哪些文件,调试内存泄漏时有用
- **/proc/<pid>/fd**:查看进程打开了哪些文件描述符,调试"文件泄漏"(打开从不关)

重构时如果想验证"新代码读的字节和旧代码一样",用 `strace -e read ./game`:

```bash
$ strace -e read -f ./target/release/game 2>&1 | grep -v "^read(.*= 0" | head -20
```

`-e read` 只显示 read 系统调用,过滤掉返回 0 的(EOF),head -20 只看前 20 个。对比重构前后输出,字节级别应该完全一样。

如果重构涉及内存布局变化(比如从 Vec<Box<T>> 改成 Vec<T>),用 `/usr/bin/time -v` 看内存峰值:

```bash
$ /usr/bin/time -v ./target/release/game
...
    Maximum resident set size (kbytes): 245760
```

`Maximum resident set size` 是进程峰值内存。重构后这个数应该不变或更小。

### 3.4 · 🦀 Rust 生态视角

Rust 的 enum + match 是表达"统一类型 + 分发"的最佳工具:

```rust
enum AssetType { Bitmap, Sound, Font, Model }

fn load(id: AssetId) -> AssetSlot {
    match id.type_tag {
        AssetType::Bitmap => load_bitmap(id.index),
        // 编译器强制穷尽所有分支——加新类型时编译器会报错提醒你
    }
}
```

Rust enum 的"穷尽性检查(exhaustiveness)"是重构大杀器:加一个 `Video` 类型,编译器会列出所有需要更新的 match 表达式。这是 C/C++ 没有的安全网。

Rust 工具链对重构的支持:

- **rustfmt**:格式化,保证团队风格统一
- **clippy**:lint,提醒"这段代码有更地道的写法"
- **cargo fix --edition**:自动迁移到新版本
- **rust-analyzer**:IDE 后端,提供"重命名"、"提取函数"等重构操作

今天的 AssetId 重构,rust-analyzer 的"重命名类型"功能可以一键改所有引用,从 `BitmapId` 改成 `AssetId`,比手动 sed 安全得多。

Rust 还有一个常被忽视的特性:**`#[non_exhaustive]`**。给 enum 或 struct 加上这个 attribute,意味着"未来可能加新变体",强制外部代码处理 default 分支。这对库作者很有用——你重构 enum 时不会破坏下游代码。

```rust
#[non_exhaustive]
pub enum AssetType { Bitmap, Sound, Font, Model }
```

外部代码 match 时必须加 `_ => ...`,这样你加 `Video` 变体时下游不会编译失败。

## 4 · 认知地图

### 4.1 上级

- **资产管线(asset pipeline)** — 从原始文件(PNG/WAV)到运行时数据的全链路
- **基础设施层** — 游戏代码下方的"看不见的"系统
- **技术债管理** — 软件工程的长期视角
- **抽象边界** — 模块间契约的设计

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 多个 XxxId + 多个 load | 类型隔离好 | 类型差异大 | 否 |
| 统一 AssetId + 分发 | 通用,代码少 | 类型相似,API 统一 | ✓ |
| 类型擦除(trait object) | 动态分发 | 运行时才知道类型 | 否 |
| 泛型 AssetId<T> | 编译期分发 | T 类型固定 | 否 |

详细:trait object 是 `Box<dyn Asset>` 这种,运行时分发(虚函数调用),灵活但有性能开销。泛型是 `AssetId<T: Asset>`,编译期单态化,零成本但每种 T 是不同类型,无法装进同一个 Vec。

### 4.3 下级

- **newtype 模式** — `struct Foo(u32)` 的零成本包装
- **enum + match** — Rust 的代数数据类型(ADT)
- **slot table** — 用 u32 索引的稀疏数组
- **死代码删除** — `cargo +nightly udeps` 或 `cargo machete`

## 5 · 对照与变奏

重构在不同语言生态有不同的工具支持:

- **Java**:IntelliJ 的重构功能最强大,因为 Java 有反射 + 完整 AST
- **Go**:`gofmt` + `gopls`,但 Go 没有 enum,重构时类型安全网较弱
- **Rust**:rust-analyzer + clippy,加上 enum 穷尽性,重构体验最安全
- **C++**:最难重构,头文件 + 模板 + 宏让 IDE 难以分析

Casey 用 C(他原版 HH 是 C),重构更依赖手动。Rust 版本(本教程)享受了类型系统红利。

历史上"重构"这个词是 1992 年 Opdyke 在博士论文里正式定义的。Fowler 1999 年的《Refactoring》把它推向主流。今天每个软件工程师都要会——它是"职业"和"业余"的分水岭。

历史上著名的重构失败案例:Netscape 4.0 重写(1998),导致 Netscape 浏览器市场被 IE 吃掉;Mozilla Firefox 因此诞生,前 5 年都在弥补重写的代价。Casey 反复提醒观众:不要重写,要重构。

### Lv1 · 概念辨析

**题**:下面哪几个是"重构",哪几个不是?说明理由。

a) 把一个 200 行函数拆成 5 个小函数
b) 修一个崩溃 bug
c) 加一个新文件格式支持
d) 把 `Vec<String>` 改成 `Vec<&str>`(参数都加 `&`)
e) 把 4 个重复的 `load_xxx` 合成一个 `load`

**参考解答**:a, d, e 是重构(不改对外行为);b, c 不是(b 是 bug 修复,c 是新功能)。
- a:典型 extract function,行为不变
- d:_lifetime_ 改变,但调用方调整后行为不变(虽然这是接口改动,严格来说算 breaking change,通常归类重构)
- e:今天的主题,合并重复

为什么这么想:重构的判据是"对外行为不变"。bug 修复改变了行为(原来崩,现在不崩);新功能加了行为。重构是把"行为等价的代码"换个写法。

### Lv2 · 动手实践

**题**:下面这段 Rust 代码有重复。重构它,让 `sum_xxx` 不再重复。

```rust
struct Point { x: i32, y: i32 }
struct Rect { x: i32, y: i32, w: i32, h: i32 }

fn sum_x_points(ps: &[Point]) -> i32 { ps.iter().map(|p| p.x).sum() }
fn sum_x_rects(rs: &[Rect]) -> i32 { rs.iter().map(|r| r.x).sum() }
```

**参考解答**:

```rust
// 方案 A:闭包参数化
fn sum_x<T, F>(items: &[T], getter: F) -> i32
where F: Fn(&T) -> i32
{
    items.iter().map(getter).sum()
}
// 调用:sum_x(points, |p| p.x), sum_x(rects, |r| r.x)

// 方案 B:定义 trait
trait HasX { fn x(&self) -> i32; }
impl HasX for Point { fn x(&self) -> i32 { self.x } }
impl HasX for Rect  { fn x(&self) -> i32 { self.x } }
fn sum_x_generic<T: HasX>(items: &[T]) -> i32 {
    items.iter().map(|i| i.x()).sum()
}
```

为什么选 A 还是 B:如果只有 2 种类型用闭包(A)更简洁;如果类型会增长到 5+ 且每个都有 x(),用 trait(B) 更扩展。Casey 偏好简单方案,会用 A。

### Lv3 · 迁移设计

**题**:你的网络代码里有 `send_tcp`、`send_udp`、`send_unix_socket` 三个函数,结构 80% 相同(都做"序列化 + 发送 + 重试")。设计一个统一抽象,让加 `send_websocket` 时只需写 50 行而不是 200 行。

**提示**:抽出 `Transport` trait,有 `send_bytes(&mut self, &[u8]) -> Result<()>` 方法。三个具体实现 TCP/UDP/Unix。`send_xxx` 的共同逻辑(序列化、重试)放在 trait 之上的 generic 函数 `send_with_retry<T: Transport>(t: &mut T, msg: &Msg) -> Result<()>`。这是经典的"模板方法模式"。

## 8 · Rust / Arch 落地代码

下面演示今天的核心重构:把 4 个 `XxxId` 合并成一个 `AssetId`,并保证编译通过。

```rust
// src/asset/mod.rs

use std::collections::HashMap;

/// 资产类型枚举
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum AssetType {
    Bitmap,
    Sound,
    Font,
    Model,
}

/// 统一的资产 ID
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct AssetId {
    pub type_tag: AssetType,
    pub index: u32,
}

impl AssetId {
    // 构造 helper——保留原来的 BitmapId(123) 风格
    pub fn bitmap(index: u32) -> Self {
        Self { type_tag: AssetType::Bitmap, index }
    }
    pub fn sound(index: u32) -> Self {
        Self { type_tag: AssetType::Sound, index }
    }
    // ...
}

/// 资产数据(持有具体资产)
pub enum AssetData {
    Bitmap(Bitmap),
    Sound(Sound),
    Font(Font),
    Model(Model),
}

/// 资产槽——slot table 的一项,带 LRU 元数据
pub struct AssetSlot {
    pub data: AssetData,
    pub last_used_frame: u64,
    pub state: AssetState,
}

pub enum AssetState {
    Loaded,
    Loading,
    Failed(String),
}

pub struct AssetStore {
    slots: HashMap<AssetId, AssetSlot>,
    current_frame: u64,
}

impl AssetStore {
    pub fn load(&mut self, id: AssetId) -> Result<&AssetSlot, String> {
        // 检查缓存
        if !self.slots.contains_key(&id) {
            // 分发到具体加载
            let data = match id.type_tag {
                AssetType::Bitmap => AssetData::Bitmap(self.load_bitmap(id.index)?),
                AssetType::Sound  => AssetData::Sound(self.load_sound(id.index)?),
                // ... 加新类型时这里加一行
            };
            self.slots.insert(id, AssetSlot {
                data,
                last_used_frame: self.current_frame,
                state: AssetState::Loaded,
            });
        }
        // 更新 LRU
        if let Some(slot) = self.slots.get_mut(&id) {
            slot.last_used_frame = self.current_frame;
        }
        Ok(self.slots.get(&id).unwrap())
    }

    fn load_bitmap(&self, index: u32) -> Result<Bitmap, String> {
        // 占位实现
        Ok(Bitmap { width: index, height: 0 })
    }
    fn load_sound(&self, index: u32) -> Result<Sound, String> {
        Ok(Sound { samples: index as usize })
    }
}

// 占位类型
pub struct Bitmap { pub width: u32, pub height: u32 }
pub struct Sound { pub samples: usize }
pub struct Font;
pub struct Model;
```

注释要点:

- `enum` + `match` 的穷尽性是重构安全网:加新 `AssetType` 变体,编译器会指出所有需要更新的 match
- `HashMap<AssetId, AssetSlot>` 的 key 必须实现 `Hash + Eq`,所以 AssetId 派生了这两个 trait
- `load` 函数同时做缓存和分发,这就是"合并重复"的成果——以前是 4 个独立的 `load_xxx`,各自维护自己的 HashMap
- 错误处理用 `Result<T, String>`(简单版);生产代码用 `thiserror::Error` 或 `anyhow::Error`
- LRU 信息(`last_used_frame`)放在 slot 里,因为它是"资产级"的元数据

跑通预期:

```bash
$ cargo check
    Finished dev [unoptimized + debuginfo] target(s) in 0.42s

$ cargo clippy -- -W clippy::pedantic
    Finished in 1.20s
# 没有 warning 说明重构干净
```

`cargo check` 比 `cargo build` 快,只做类型检查不生成代码——重构时反复 check 最快。`clippy -- -W pedantic` 打开所有 lint,任何"代码臭味"都会暴露。

### Arch 命令

如果想找出仓库里的死代码:

```bash
$ cargo install cargo-machete    # 装 cargo-machete
$ cargo machete
Reading Cargo.toml
Unused dependencies:
  some-crate  # ← 找出未使用的依赖
```

`cargo-machete` 比 `cargo udeps`(nightly-only)快很多,而且不需要 nightly toolchain。

如果想找出从未调用的函数:

```bash
$ cargo install cargo-udeps      # 装 udeps
$ cargo +nightly udeps
```

`udeps` 用 nightly 编译器的特殊功能找出"定义但未使用"的项。今天 Casey 手动 git grep 找死代码,你用 udeps 自动化。

如果想看重构前后的代码量差异:

```bash
$ git diff --stat HEAD~1
 src/asset/mod.rs | 240 ++++++++-------------------------------------
 1 file changed, 40 insertions(+), 200 deletions(-)
```

`--stat` 显示每个文件的增删行数。今天的重构应该呈现"大量删除、少量新增"。

如果你想生成一张可视化"代码热度图",看哪些函数被改得最频繁:

```bash
$ git log --oneline --pretty=format: --name-only | sort | uniq -c | sort -rn | head -10
   42 src/asset/mod.rs       # 改了 42 次,最热
   28 src/editor.rs
   ...
```

热文件往往是技术债最重的地方——它"什么都往里塞"。下一轮重构就该把这种文件拆开。
