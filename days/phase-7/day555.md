
# Day 555 · 寻找 GPU 性能问题

> 内存降了 10 倍,但帧率还是不高。Day 555 Casey 用 GPU profiler **找瓶颈**——是 vertex shader 慢?fragment shader 慢?带宽?还是 draw call 太多?

## 0 · 为什么要有这一天

GPU 性能调优和 CPU 完全不同。CPU 看一行代码慢,能直接看到。GPU 看一行代码慢,可能是:

- **Shader 计算慢**(ALU bound)
- **纹理采样慢**(texture fetch)
- **带宽限制**(memory bandwidth bound)
- **Vertex 处理慢**(geometry bound)
- **Rasterization 慢**(pixel fill rate)
- **Draw call 太多**(CPU overhead)
- **Pipeline stall**(等之前 draw call 完成)

每种瓶颈的优化方法完全不同——带宽瓶颈你优化 ALU 没用。

诊断 GPU 性能要用 **GPU profiler**——能区分上述瓶颈的工具。Day 555 Casey 用 NVIDIA Nsight(Windows),Linux 等价物是 `vkCmdTraceRays` 时序 + `RenderDoc` + `Radeon GPU Profiler`。

### 真实场景:为什么这一天这么重要

让我们把镜头拉近,体验一下 GPU 性能调试的痛。

你跟着 Handmade Hero 做到 Day 555。游戏终于能跑了:60 FPS,内存合理,资产管线顺畅。你打开 Nsight 截一帧,看 frame analyzer,发现 **voxel light probe 的 trilinear 采样占整帧时间的 40%**。40% 是什么概念?60 FPS 意味着每帧 16.67 ms,40% 就是 6.7 ms——**这一项就吃了将近一半帧预算**。

你不知道这正常还是异常。你也不知道为什么。你只能猜:
- 是采样次数太多?
- 是 texture cache miss?
- 是 texture format 选错(用了 RGBA32 而非 BCn)?
- 还是 shader 算错了?

每一个猜测都可能对,也都可能错。**GPU 是大规模并行 + 多级缓存 + 异步执行**的黑盒,你的 CPU 直觉全部失效。你猜"是 texture fetch 慢",改了 shader 减少 fetch 次数,帧率不变——说明猜错了。改回去,再猜别的。一周过去了,瓶颈还在。

这就是为什么 GPU profiler 这么重要。它**让你看见 GPU 内部**——哪个 shader 慢、哪段代码热、哪个 cache miss、哪段 memory bandwidth 满载。**没有 GPU profiler,GPU 调优就是闭眼开车**。

### CPU 调优 vs GPU 调优的本质差别

CPU 调优,你打开 `perf record` / `gprof` / `pprof`,运行程序,看到一份 flamegraph。flamegraph 直接告诉你**哪个函数慢**——一目了然。

GPU 调优不行,原因有三:

**第一,GPU 是异步的**。你提交一个 draw call,CPU 立刻返回,GPU 异步执行。等 CPU 看到"draw call 完成",GPU 已经处理了几千个 draw call。你**没法把 CPU 时间和 GPU 时间对应起来**。

**第二,GPU 并行度极高**。现代 GPU 几千个核心同时跑。某个 shader "慢" 不是单核慢,是**整体吞吐量低**。原因可能是 cache miss、bank conflict、wave 占用率低、branch divergence。这些**没法用 CPU profiler 看到**。

**第三,GPU 内部状态不公开**。NVIDIA 和 AMD 不公开 microarchitecture 细节——cache 层级、scheduler 算法、wave formation 规则。你只能用厂商提供的 profiler(Nsight / Radeon Profiler),这些工具给你**厂商愿意给你看的视图**。

所以 GPU 调优要专门的工具链。Casey 这一天演示的就是这个工具链。

### 工业级的 GPU 调优纪律

商业游戏团队(Ubisoft、Naughty Dog、Epic)的 GPU 调优有一套标准纪律:

**第一步,定 baseline**。每帧预算多少?60 FPS = 16.67 ms。30 FPS = 33.33 ms。把每帧实际时间记下来。

**第二步,分阶段测时**。GPU timestamp query 在每个 pass 开始 / 结束写时间戳,算出每个 pass 耗时。Shadow pass 几 ms?G-buffer pass 几 ms?Lighting pass 几 ms?Transparent pass 几 ms?

**第三步,定位 hotspot**。最耗时的 pass 是什么?进那个 pass 看——是 vertex 慢、fragment 慢、还是 texture 慢?

**第四步,验证假设**。你假设"fragment 慢"。改 fragment shader(简化算法 / 减少纹理采样 / 改用更便宜的近似),测帧时间。如果下降 → 假设对。如果不变 → 假设错,重新诊断。

**第五步,记录结果**。每帧各 pass 的耗时做成表格 / 图表。每周对比,看回归。

这套纪律和 CPU 调优类似,但**工具完全不同**。CPU 用 perf / valgrind / gdb;GPU 用 Nsight / Radeon Profiler / RenderDoc / MangoHud。

## 2 · 心智模型

### 2.1 类比:工厂生产线

想象工厂有 4 个工序:原材料(input assembler)→ 零件加工(vertex shader)→ 组装(rasterizer)→ 喷漆(fragment shader)→ 出货(output merger)。

如果总效率低,可能某个工序是瓶颈:

- 喷漆慢 → 雇更多喷漆工(优化 fragment shader)
- 零件加工慢 → 升级机器(优化 vertex shader)
- 原材料供应慢 → 改物流(优化 input assembler)
- 出货堆积 → 加仓库(优化 ROP)

不知道哪个工序慢,瞎升级机器没用——可能喷漆才是瓶颈。

GPU pipeline 也是这样:**5 个阶段都可能瓶颈**。先诊断瓶颈位置,再针对性优化。

让我们把工厂类比再推进一层。GPU 不是简单 4 工序流水线——它是**多车道并行流水线**。喷漆车间有 100 个喷漆工(fragment shaders),同时处理 100 个零件。但若**喷漆料(fragment 数据)从仓库(texture memory)运过来慢**,100 个喷漆工有 80 个在等料——这就是 bandwidth bound。即便你雇更多喷漆工,也没用,因为瓶颈在物流。

或者:喷漆工各自按不同工序处理(some parts need 3 coats, some need 1)——慢的零件拖累整组,这叫 **wave divergence**。GPU 的 warp / wavefront 是 32 或 64 个 thread 一组,必须同步执行。组里有快有慢,慢的拖累整组。

这些细节用 CPU profiler 看不到,要用 GPU profiler。

### 2.2 严谨展开:GPU pipeline 阶段

```
1. Input Assembler (IA) —— 读 vertex/index buffer
2. Vertex Shader (VS) —— 处理每个顶点(变换、变形)
3. Tessellation (可选) —— 细分曲面
4. Geometry Shader (可选) —— 增删图元
5. Rasterizer (RS) —— 三角形 → 像素,生成 fragment
6. Fragment/Pixel Shader (FS) —— 处理每个像素(纹理、光照)
7. Output Merger (OM) —— depth test、blend、写 framebuffer
```

每个阶段并行处理大量数据(GPU 是大规模并行),但**前一阶段的输出是后一阶段的输入**——前一阶段慢,后一阶段饿着。

每个阶段的瓶颈特征:

**IA bottleneck**:顶点数据布局不好。例如 position 用 RGBA32F(16 字节/顶点),改成 RGBA16F(8 字节)能减半带宽。或者用 indexed drawing 减少重复顶点。

**VS bottleneck**:vertex shader 算得太多。常见原因——skin动画(每个顶点 4 个 bone matrix 乘法)、复杂的 displacement mapping。优化:预计算、用 compute shader 做 skinning。

**RS bottleneck**:三角形太小。1 个像素的三角形也走完整光栅化流程,效率极低。优化:用 LOD(level of detail),远距离用低 mesh。

**FS bottleneck**:这是最常见的。fragment shader 算得太多 / 采样太多纹理 / 循环太深。优化:简化算法、用 mipmap、合并纹理。

**OM bottleneck**:blend 开启 + overdraw 高。优化:用 Z-prepass 提前剔除被遮挡的 fragment。

### 2.3 瓶颈诊断的简单方法

**改分辨率测试**:渲染分辨率减半,如果帧率不变 → fragment shader 不是瓶颈(因为 fragment 数减半但帧率没变)。如果帧率翻倍 → fragment 是瓶颈。

具体怎么做:把 swapchain 从 1920×1080 改成 960×540(渲染到小 texture,然后 upscale 到屏幕)。fragment 数减 75%,顶点数不变。

- 帧率从 30 FPS 升到 60 FPS → fragment 是瓶颈,你被 fill rate 限制。
- 帧率不变 → fragment 不是瓶颈,问题在 vertex / IA / draw call。

**改顶点数测试**:顶点数减半,帧率不变 → vertex shader 不是瓶颈。

具体怎么做:用 LOD,把高 mesh 换成低 mesh。比如 100 万顶点换成 10 万。

- 帧率提升 → vertex shader 或 IA 是瓶颈。
- 帧率不变 → 问题在 fragment 或其他。

**改贴图大小**:贴图 1024² 改 16²,帧率不变 → 纹理不是瓶颈。

具体怎么做:用一张 16×16 的纯色贴图替换。如果帧率提升 → 纹理带宽是瓶颈。

这些"反向推理"是定位瓶颈的标准操作。

### 2.4 工业级 GPU profiler

**RenderDoc**:开源,免费,所有 GPU 都支持。能截帧看每 draw call 的输入/输出。但**不是性能分析工具**——它看正确性,不看耗时。它是"调试器",不是"profiler"。

**NVIDIA Nsight Graphics**:NVIDIA 官方,Windows/Linux,免费。看每 shader 指令的耗时,看 SM utilization。这是"profiler"——告诉你性能数据。

**Radeon GPU Profiler**:AMD 宨方,Linux/Windows,免费。看 GCN/RDNA 架构的细节。

**Intel Graphics Performance Analyzer**:Intel 集成显卡。

**MangoHud**:Linux 开源 overlay,实时显示帧率 / 帧时间 / CPU 占用 / GPU 占用。轻量,适合长期监测。

### 2.5 GPU timestamp query 的原理

GPU profiler 怎么"测时间"?不是 CPU 端 `clock()`——GPU 异步,CPU 时间无意义。GPU 端用 **timestamp query**。

工作原理:GPU 命令流里插入 "vkCmdWriteTimestamp" 命令。GPU 执行到这条命令时,把当前 GPU 时钟写到一个 query pool 的 slot 里。CPU 后续读这个 slot,得到 GPU 时钟值。两个 timestamp 相减,得到中间那段 GPU 命令的耗时。

```rust
// Vulkan 伪代码
let query_pool = create_query_pool(2);  // 2 个 slot

cmd.begin();
cmd.write_timestamp(query_pool, 0, PIPELINE_TOP);  // 起点
cmd.draw(...);  // 你要测的 draw call
cmd.write_timestamp(query_pool, 1, PIPELINE_TOP);  // 终点
cmd.end();

queue.submit(cmd);
queue.wait_idle();

let mut timestamps = [0u64; 2];
device.get_query_pool_results(query_pool, 0, 2, &mut timestamps, ...);

let elapsed_ns = (timestamps[1] - timestamps[0]) as f32 * timestamp_period;
```

`timestamp_period` 是 GPU 报告的"每个 tick 等于多少纳秒",在物理设备 properties 里 query。

timestamp 的精度通常是 1 ns 级别,足够精细分析单个 draw call。但 timestamp query 有数量限制——某些 GPU 只允许每帧 4096 个 timestamp,所以你不能给每个 draw call 都加,要分组。

### 2.6 工业级 GPU profiler 的工作流程

不是截一帧就完事。Casey 在视频里展示的标准流程:

**第一步:Live profiling**。用 MangoHud 看长期帧时间。如果某帧 spike,记录这一帧。

**第二步:Frame capture**。用 Nsight 抓那一帧。Nsight 记录 GPU 命令流的所有细节。

**第三步:Range-based replay**。Nsight 重新提交这一帧的命令到 GPU,可以**反复重放**。改 shader / 改 texture / 改 buffer,看新结果,不用重跑游戏。

**第四步:Rule-based analysis**。Nsight 跑一组"启发式规则",自动指出可疑模式——例如"这个 fragment shader 采样纹理但没用 mipmap,可能有 cache miss"。

**第五步:Experimentation**。Nsight 提供 "experiments"——临时改 GPU 状态看效果。例如"All texture fetches are 1×1 pixel"(测试理论上的 ALU bound)——如果帧率没变,说明纹理确实不是瓶颈。

这套流程在工业级 GPU 调优里是标准。RenderDoc 偏调试,Nsight 偏分析,两者互补。

## 8 · Rust / Arch 落地代码

### 8.1 完整的 GPU timestamp 测量系统

让我们从零做一个完整的 GPU 测时项目,使用 `ash` (Vulkan binding)。

```bash
# 创建项目
cargo new --bin gpu-perf-demo
cd gpu-perf-demo

# 加 Vulkan binding
cargo add ash
cargo add winit  # 窗口
```

`src/main.rs` 关键代码:

```rust
use ash::vk;

struct GpuTimer {
    query_pool: vk::QueryPool,
    device: ash::Device,
    timestamps: Vec<u64>,
    timestamp_period: f32,  // 1 tick = N ns
}

impl GpuTimer {
    fn new(device: ash::Device, physical_device: vk::PhysicalDevice, slot_count: u32) -> Self {
        // 1. 查询 timestamp_period(N ns per tick)
        let props = unsafe {
            device
                .get_physical_device_properties(physical_device)
                .limits
                .timestamp_period
        };

        // 2. 创建 query pool
        let create_info = vk::QueryPoolCreateInfo::builder()
            .query_type(vk::QueryType::TIMESTAMP)
            .query_count(slot_count);

        let query_pool = unsafe {
            device
                .create_query_pool(&create_info, None)
                .expect("Failed to create query pool")
        };

        Self {
            query_pool,
            device,
            timestamps: vec![0u64; slot_count as usize],
            timestamp_period: props,
        }
    }

    fn record(&self, command_buffer: vk::CommandBuffer, slot: u32) {
        // 在 command buffer 里写 timestamp
        unsafe {
            self.device.cmd_write_timestamp(
                command_buffer,
                vk::PipelineStageFlags::BOTTOM_OF_PIPE,  // 等 GPU 跑到这里才写
                self.query_pool,
                slot,
            );
        }
    }

    fn read(&mut self) -> Vec<f32> {
        // 把 GPU 端 timestamp 拷到 CPU
        unsafe {
            self.device
                .get_query_pool_results(
                    self.query_pool,
                    0,
                    self.timestamps.len() as u32,
                    &mut self.timestamps,
                    vk::QueryResultFlags::TYPE_64 | vk::QueryResultFlags::WAIT,
                )
                .expect("Failed to get query results");
        }

        // 转 ns
        self.timestamps
            .iter()
            .map(|t| *t as f32 * self.timestamp_period)
            .collect()
    }

    fn elapsed_ns(&mut self, start: u32, end: u32) -> f32 {
        let timestamps_ns = self.read();
        timestamps_ns[end as usize] - timestamps_ns[start as usize]
    }
}

fn main() {
    // 简化:实际要初始化 Vulkan instance、device 等
    println!("GpuTimer 演示 - 见 ash 文档完整初始化");
    println!("用法:");
    println!("  timer.record(cmd, 0);  // pass 开始");
    println!("  // ... draw calls ...");
    println!("  timer.record(cmd, 1);  // pass 结束");
    println!("  let elapsed_ns = timer.elapsed_ns(0, 1);");
    println!("  println!(\"Pass took {:.2} ms\", elapsed_ns / 1e6);");
}
```

### 8.2 启发式瓶颈诊断

不用 GPU profiler,先用启发式判断:

```rust
#[derive(Debug, Clone, Copy)]
struct FrameStats {
    frame_time_ms: f32,
    fragment_count: usize,    // 像素数
    triangle_count: usize,
    draw_call_count: usize,
    texture_fetch_count: usize,
}

#[derive(Debug)]
enum Bottleneck {
    Fragment,         // fragment 处理慢
    Vertex,           // vertex 处理慢
    TextureBandwidth, // 纹理带宽
    DrawCallCpu,      // CPU 提交慢
    Unknown,
}

fn diagnose(stats: &FrameStats) -> Bottleneck {
    // 60 FPS = 16.67ms 预算
    let frame_budget_ms = 16.67;
    let over_budget = stats.frame_time_ms > frame_budget_ms;
    if !over_budget {
        return Bottleneck::Unknown;  // 没问题
    }

    // 1. CPU 端 draw call 太多?CPU overhead 每 draw call 大概 5-50μs
    let cpu_overhead_ms = stats.draw_call_count as f32 * 0.02;  // 假设 20μs/call
    if cpu_overhead_ms > frame_budget_ms * 0.5 {
        return Bottleneck::DrawCallCpu;
    }

    // 2. Triangle 数太多?(>3M 通常 vertex bound)
    if stats.triangle_count > 3_000_000 {
        return Bottleneck::Vertex;
    }

    // 3. Fragment 数太多?1080p = 2M,4K = 8M
    if stats.fragment_count > 5_000_000 {
        return Bottleneck::Fragment;
    }

    // 4. Texture bandwidth?每个 fetch 大概 4-16 bytes
    let bandwidth_bytes = stats.texture_fetch_count * 8;
    let bandwidth_gb_s = 500.0;  // 假设 500 GB/s
    let bandwidth_ms = (bandwidth_bytes as f32 / (bandwidth_gb_s * 1e9)) * 1000.0;
    if bandwidth_ms > frame_budget_ms * 0.5 {
        return Bottleneck::TextureBandwidth;
    }

    Bottleneck::Unknown
}

fn main() {
    let test_cases = vec![
        ("Standard 1080p", FrameStats {
            frame_time_ms: 16.0,
            fragment_count: 2_000_000,
            triangle_count: 500_000,
            draw_call_count: 500,
            texture_fetch_count: 4_000_000,
        }),
        ("Fragment heavy", FrameStats {
            frame_time_ms: 25.0,
            fragment_count: 8_000_000,  // 4K
            triangle_count: 500_000,
            draw_call_count: 500,
            texture_fetch_count: 16_000_000,
        }),
        ("Draw call storm", FrameStats {
            frame_time_ms: 25.0,
            fragment_count: 1_000_000,
            triangle_count: 1_000_000,
            draw_call_count: 5000,  // 太多
            texture_fetch_count: 5_000_000,
        }),
        ("Triangle heavy", FrameStats {
            frame_time_ms: 22.0,
            fragment_count: 2_000_000,
            triangle_count: 5_000_000,  // 多
            draw_call_count: 500,
            texture_fetch_count: 5_000_000,
        }),
    ];

    for (name, stats) in test_cases {
        let diag = diagnose(&stats);
        println!("{:20} → frame_time={:.1}ms, diagnosis={:?}", name, stats.frame_time_ms, diag);
    }
}
```

预期输出:
```
Standard 1080p      → frame_time=16.0ms, diagnosis=Unknown
Fragment heavy      → frame_time=25.0ms, diagnosis=Fragment
Draw call storm     → frame_time=25.0ms, diagnosis=DrawCallCpu
Triangle heavy      → frame_time=22.0ms, diagnosis=Vertex
```

### 8.4 实际场景:测 voxel light probe 的 trilinear 采样

回到 Casey Day 555 的真实场景。他发现 voxel light probe 的 trilinear 采样占 40% 帧时间。让我们重现这个分析:

```rust
// 假设你的 voxel light probe 是 64x64x64 RGBA16F texture
// 每次 fragment shader 采样 1 次 trilinear
// 假设 1920x1080 = 2M fragment,每 fragment 采 1 次 = 2M samples

let fragment_count = 2_000_000;
let samples_per_fragment = 1;  // trilinear 1 次
let bytes_per_sample = 8;       // RGBA16F = 8 字节
let total_bytes = fragment_count * samples_per_fragment * bytes_per_sample;
// = 16 MB

let gpu_bandwidth_gbps = 500.0;  // 假设 500 GB/s
let time_ms = (total_bytes as f32 / (gpu_bandwidth_gbps * 1e9)) * 1000.0;
// = 16e6 / 5e11 * 1000 = 0.032 ms

println!("Trilinear 采样理论耗时: {:.3f} ms", time_ms);
// 0.032 ms 远小于 16.67 ms 预算
```

理论 0.032 ms,但实测 6.7 ms(40% 帧)。差 200 倍——说明**不是 bandwidth 而是 cache miss**。

为什么 cache miss? voxel texture 64×64×64 = 256K texel × 8 byte = 2 MB。GPU L2 cache 通常 4-8 MB,理论上能装下。但 trilinear 采样 pattern 是 3D,空间局部性差,cache line 利用率低。

解决:Casey 改用更紧凑的存储(例如 RGBA8 而不是 RGBA16F),texture 缩小到 1 MB,L1 cache 装下,sample 不再 miss,帧率回升。

这个分析过程**完全依赖 GPU profiler**——光看代码看不出 cache miss。

### 8.7 Troubleshooting

**问题1**:Nsight 显示 "GPU hang detected"。
原因:你的 shader 有死循环或越界访问。
诊断:用 Vulkan validation layer 跑 `VK_INSTANCE_LAYERS=VK_LAYER_LUNARG_standard_validation ./game`。

**问题2**:MangoHud 不显示。
原因:游戏不是 Vulkan / OpenGL(可能是 CPU 渲染)。
诊断:`vulkaninfo | grep deviceName` 确认 Vulkan 装好。

**问题3**:Nsight 截不到帧。
原因:游戏用了 swapchain 模式 Nsight 不识别。
诊断:用 `nsys profile --trace=vulkan --delay=5` 跳过启动期。

**问题4**:帧时间不稳,spike 偶发。
原因:可能是 CPU 端 GC / 内存分配,不是 GPU。
诊断:`mangohud` 看 CPU 占用,或用 `perf record` 看 CPU flamegraph。

**问题5**:Nsight 跑得很慢,游戏卡住。
原因:Nsight instrumentation 有开销。
诊断:用 "frame range" 限制只测第 N 帧,不全程跟踪。
