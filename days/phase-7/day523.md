# Day 523 · Git 入门

> Casey 在 Day 441 警告过"永远不要更新开发工具,永远",但他没说不准学新工具。Day 523 Casey 做了一件让 HH 老观众惊讶的事:**他从 Day 1 到现在 500 多集没用过版本控制**,所有改动靠手动备份文件夹。今天他终于介绍 Git——不是因为编程上需要,而是因为他的开发机要换/重装/迁移,Git 终于从"奢侈品"变成"必需品"。这一集对自学读者意义特殊:你前面 500 天可能一直在用 Git,现在终于能看到 Casey 亲自解释为什么 Git 必不可少。

## 0 · 为什么要有这一天

如果你已经跟着本教程做到 Day 523,你应该在 Day 12(article 12-opensource-pr-flow)学过 Git 基础。但 Casey 在 HH 里不用 Git——他用最原始的方式:**复制整个项目文件夹**作为"备份"。这种做法在 HH 项目里凑合能用,因为 Casey 一个人开发、版本节奏明确(一集对应一次改动)、不需要回退到任意历史。

但 Casey 终于在 Day 523 引入 Git,为什么?三个原因:

第一,**硬盘迁移**。Casey 要把整个项目从一台机器搬到另一台,复制文件夹能搬代码,但搬不动"开发环境配置"。Git 仓库 + 一个 README 列依赖 = 完整可重现的开发环境。

第二,**远程备份**。复制文件夹到 USB 是本地备份,硬盘坏了就完蛋。Git push 到 GitHub 是异地备份,即使整栋房子烧了代码也在。

第三,**协作**。HH Q&A 论坛上观众经常贴代码改动给 Casey 看,Casey 复制粘贴很麻烦。Git 的 fork/PR 模型让协作顺畅。

但 Casey 强调:他**不打算用 Git 的分支/合并/rebase 这类复杂功能**,他只把 Git 当"时间机器"——`git commit` 把当前状态存档,`git checkout` 切换到任意历史存档。这是 Git 最朴素也最稳的用法。

这一天的价值对你,**不是**学 Git 命令(你应该已经会),而是**理解为什么有人不用 Git,以及什么时候 Git 是 overkill**。Casey 的"500 天不用 Git"是反直觉但有道理的——他在挑战"必须用版本控制"这个软件工程教条。完成这一天之后,你能:

- 理解 Git 的核心数据模型(对象图,不是"快照列表")
- 知道什么场景适合 Git、什么场景 Git 是负担
- 在 Rust 项目里正确设置 `.gitignore`,避免提交编译产物

## 1 · Casey 今天做了什么

Casey 这一天没有写代码,而是花一整集讲 Git 的概念。他的动作可以拆成四步:

第一步,他**承认自己之前没用 Git**。说自己的"备份"方式是复制整个文件夹到外部硬盘,每次大改动前手动 backup。这种方式的好处:简单、不依赖工具、不怕 Git 命令出错。坏处:无法回到任意历史,无法异地备份,无法协作。

第二步,他**介绍 Git 的核心概念**:repository(仓库)、commit(提交)、working directory(工作目录)、staging area(暂存区)。他画图解释:Git 仓库不是"一串快照",而是一个**有向无环图(DAG)**,每个 commit 指向它的父 commit(s)。

第三步,他**演示最基础的工作流**:`git init`(初始化仓库)、`git add .`(把改动放进暂存区)、`git commit -m "..."`(把暂存区作为新 commit 永久保存)、`git log`(看历史)、`git checkout <hash>`(回到历史状态)。

第四步,他**强调他不打算用 Git 的高级功能**:不用 branch(分支)、不用 merge(合并)、不用 rebase(变基)、不用 pull request。他把 Git 当"高级的复制文件夹工具"——只用 `commit` 和 `checkout` 两个命令。这是 Git 的"最低可用"形态。

## 2 · 心智模型

### 类比:Git 是"存档系统"

你玩游戏,每过一关就存一次档。下次打开游戏,可以选 "Continue"(最新存档)或 "Load"(选历史存档)。Git 就是这种"代码存档系统",只是更精细——你每改完一个功能就存一次,任何时候都能回到任意历史存档。

但 Git 比游戏存档强一点:**它的存档是 diff(差异)链**。每次存档不是完整复制,而是记录"从上次存档到现在改了什么"。这让存档本身很小,几 KB 的 commit 能记录 10000 行的改动。

### 严谨展开:Git 的对象模型

Git 的核心数据结构是**对象图**,不是"提交列表"。每个对象用一个 SHA-1 哈希标识:

- **blob** —— 文件内容(二进制大对象)
- **tree** —— 目录(包含文件名 → blob 的映射)
- **commit** —— 一次提交(指向一个 tree,记录作者、时间、消息,指向父 commit)
- **tag** —— 命名引用(可选)

一个 commit 长这样(伪代码):

```
commit 7a3f2e1...
  tree: 9b8d4c2...
  parent: 4e1a7b3...
  author: Casey <casey@example.com> 1700000000 +0000
  message: "Day 523: Fixed parent pointer bug"
```

这个 commit 指向一个 tree(当时的文件结构),指向一个 parent(上一个 commit)。整条历史是 parent 链组成的链表(或 DAG,如果有合并)。

**关键洞察**:Git 不是存"当前状态 + 历史 diff",而是存**每次 commit 的完整 tree**(通过 blob 共享实现去重)。这意味着 checkout 任意历史都是 O(1)——直接读那个 commit 的 tree 即可,不用回放 diff。

### working directory / staging / repository 的三层模型

这三层是 Git 最容易让新手混淆的:

| 层 | 在哪 | 内容 |
|---|---|---|
| **Working directory** | 你的硬盘上的项目文件夹 | 你正在编辑的文件 |
| **Staging area (index)** | `.git/index` 二进制文件 | 准备提交的快照 |
| **Repository (.git)** | `.git/` 隐藏文件夹 | 所有 commit 历史 |

工作流:

```
编辑文件  →  git add  →  git commit
   ↓             ↓           ↓
工作目录       暂存区       仓库历史
```

为什么有暂存区?因为有时你只想提交部分改动(比如修了 3 个文件,只想提交其中 1 个)。`git add file1.txt` 只把 file1 加入暂存区,其他文件保持 unstaged。然后 `git commit` 只提交暂存区内容。

Casey 的简化用法:`git add .`(全加)+ `git commit -m`(全提)。这是最朴素也最安全的流程,适合一个人开发。

### Casey 的"不用 Git 高级功能"哲学

Casey 在视频里明确说:"我不打算学 branch、merge、rebase 这些。"他的工作流就是线性的 main 分支,每个 commit 都是 main 的延续。这种方式有得有失:

**得**:不会遇到 merge conflict(合并冲突),不会 rebase 错乱历史,工作流极简。
**失**:无法做实验性改动(必须 commit 才能切换上下文),无法协作(PR 需要 branch)。

对 Casey 这种"一个人 + 直线推进"的模式,这是合理的。对你(将来要贡献开源),branch/merge 是必备技能——但今天不必学,后面专门有一天讲 PR。

### SHA-1 哈希:Git 的"防伪印章"

Git 的每个对象都用 SHA-1 哈希标识(40 字符十六进制)。这听起来像"加密",但 Git 用 SHA-1 的目的不是加密,是**完整性校验**——任何字节改了,哈希就变。

举例:一个 commit 的 hash 是 `7a3f2e1...`,这个 hash 是这样算出来的:

```
hash = SHA-1("commit <length>\0" + 
             "tree 9b8d4c2...\n" + 
             "parent 4e1a7b3...\n" + 
             "author Casey <c@x.com> 1700000000 +0000\n" + 
             "committer Casey <c@x.com> 1700000000 +0000\n" + 
             "\n" + 
             "Day 523: Fixed parent pointer bug\n")
```

任何字段改一个字符,hash 完全变化。这就是为什么 Git 不能"伪造历史"——如果你改了一个 commit 的内容,它的 hash 变了,后续所有 commit(它的子 commit)的 hash 也跟着变(因为它们记录了 parent hash)。一改全改,改完不是同一个仓库了。

这种"内容寻址(content-addressable)"的存储模式是 Git 设计的核心:**对象的 ID 就是它的内容的哈希**。这种模式在密码学货币(Bitcoin)、IPFS(分布式文件系统)、Nix(声明式包管理)里都是基础。学会 Git 的对象模型,你看这些系统就豁然开朗。

SHA-1 在 2017 年被 Google 公开碰撞攻击(SHA-1 shattered:两个不同 PDF 拥有相同 SHA-1)。但 Git 仍然用 SHA-1,因为:(1)Git 的"防伪"主要靠 commit hash 链,不是单纯 SHA-1;(2)Git 已经在迁移到 SHA-256(`git config core.hashAlgorithm sha256`)。这个迁移在大型项目(Linux 内核)上仍然在缓慢进行——存储格式变更涉及所有对象。

### Git 内部存储:其实是一堆文件

Git 仓库的 `.git` 目录里到底是什么?让我打开看:

```bash
ls -la .git/
# HEAD          <- 当前 checkout 的分支引用
# config        <- 仓库级配置
# description   <- 仓库描述(默认为 "Unnamed repository")
# hooks/        <- 钩子脚本(commit 前自动跑的脚本)
# info/         <- 全局 exclude(类似 .gitignore)
# objects/      <- 所有 Git 对象(blob/tree/commit/tag)
# refs/         <- 所有引用(branch/tag)
# index         <- 暂存区(二进制)
```

`objects/` 里每个对象是一个文件,文件名是 SHA-1 哈希,内容是 zlib 压缩的对象数据。所以 Git 仓库本质是"一个文件系统,文件按 hash 命名"——非常简单的设计。这种简单性让 Git 高度可移植(任何文件系统都能存)、可读写(不需要数据库)、可脚本化(任何语言都能读)。

### git status 和 git diff 的工作原理

这两个命令背后是同样的"对象比较"逻辑:

- `git status`:对比 working directory、staging area、HEAD commit 三棵 tree,找出差异
- `git diff`:对比两棵 tree 的 blob 内容,逐行显示差异

具体:HEAD commit 指向一棵 tree,这棵 tree 是上次 commit 时的快照。staging area 是另一棵 tree,是"将要 commit 的快照"。working directory 是文件系统上的实际文件。Git 把这三棵 tree 两两比较,告诉你差异。

- `git diff`(无参数):working dir vs staging area
- `git diff --staged`:staging area vs HEAD
- `git diff HEAD`:working dir vs HEAD

理解这三层模型后,你能精确预测 `git status` 会显示什么——不再"恐惧 Git"。这是 Casey 这一天最想让观众理解的事:**Git 不是黑魔法,它的每个命令背后都是简单的对象比较**。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发里 Git 的典型用法:

- 主分支 main 永远可编译可运行
- 新功能开 feature branch,开发完合并回 main
- 发布版本打 tag(如 `v1.0.0`)
- 美术资产用 Git LFS(Large File Storage)避免仓库膨胀

游戏开发的 Git 坑:

- 二进制资产(psd、fbx、png)无法 diff,Git 只能存全量,仓库很快变大
- 大文件频繁修改会让 `git clone` 极慢(因为要下载全历史)
- 解决方案:Git LFS(只存指针,真实资产在 LFS 服务器),或者把美术资产完全分离(不在 Git 里)

Unreal Engine 项目通常用 Perforce(Helix Core)而非 Git,因为 Perforce 对大文件和二进制资产支持更好。Unity 项目用 Git + LFS。

### 3.2 · 图形学视角

shader 文件、纹理、模型这些**应该**进 Git,但要注意 `.gitignore`:

- `.gitignore` 列出"不要提交"的文件(编译产物、临时文件、二进制资产)
- Rust 项目 `.gitignore` 典型内容:`/target`、`Cargo.lock`(库项目时可选)
- 游戏 `.gitignore` 加 `*.log`、`/build`、`*.tmp`

shader 文件(`.glsl`、`.hlsl`、`.wgsl`)是纯文本,**强烈推荐**进 Git——你能看到每次 shader 改动的 diff,这对调试渲染 bug 极有帮助。

### 3.3 · Linux 系统编程视角

Linux 内核本身就是 Git 的"杀手项目"。Linus Torvalds 2005 年因为 BitKeeper 闭源,自己花 10 天写了 Git。Git 的设计受 Linux 内核开发的影响:

- 分布式(每个克隆都是完整仓库,没有"中央服务器"必需)
- 高性能(对象用 SHA-1 哈希索引,O(1) 查找)
- 数据完整性(所有内容 SHA-1 校验,损坏自动检测)

Linux 内核的 Git 工作流极其复杂:mainline、stable、linux-next、子系统维护树、子系统 → mainline 的 pull request……Casey 在视频里说"我不用 branch",但 Linux 内核没 branch 完全没法运转。这是 Git 在不同规模下的不同用法。

Arch Linux 上 Git 的几个常用工具:

- `git` —— 基础
- `git-lfs` —— 大文件支持
- `tig` —— 终端里的 Git 浏览器
- `lazygit` —— 终端 Git TUI
- `gh` —— GitHub CLI(发起 PR、看 issue)

### 3.4 · Rust 生态视角

Rust 项目用 Git 是事实标准。`cargo new` 自动 `git init` 你的项目。`Cargo.toml` 可以指定 Git 依赖:

```toml
[dependencies]
my_crate = { git = "https://github.com/user/my_crate", branch = "dev" }
```

这意味着 cargo 会 `git clone` 那个仓库,用指定分支的代码。这就是为什么 Git 对 Rust 生态必不可少——大量 crate 只在 GitHub 上,没有 crates.io 发布。

crates.io 本身的发布流程:`cargo publish` 把 crate 上传到 crates.io 服务器。但**crate 源码通常先在 GitHub**(开发用),`publish` 时镜像一份到 crates.io。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **版本控制(Version Control)** —— 跟踪文件随时间的变化
- **内容寻址存储(Content-addressable storage)** —— Git 用哈希作为 key 的存储模型
- **分布式系统** —— 没有中心节点,每个克隆对等
- **不可变数据结构(Immutable data structures)** —— Git 对象一旦创建不可改,改了就是新对象

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Git | 分布式,内容寻址 | 几乎所有现代项目 | Casey 选这个 |
| Mercurial (hg) | 分布式,Python 实现 | Python 项目历史选择 | 已弃用 |
| Subversion (SVN) | 集中式,中心服务器 | 老旧企业项目 | 不推荐 |
| Perforce (Helix Core) | 集中式,大文件友好 | 游戏公司美术资产 | Unreal 用这个 |
| Fossil | 单文件仓库,SQLite 内核 | SQLite 自用 | 极小众 |
| 手动复制文件夹 | 无工具 | 极简单人项目 | Casey 前 522 集 |

### 4.3 下级(内部零件)

- **blob/tree/commit/tag** —— Git 的四种对象类型
- **SHA-1 哈希** —— 40 字符十六进制,唯一标识对象
- **DAG(有向无环图)** —— commit 历史的结构
- **ref(reference)** —— 命名引用(branch、tag、HEAD)
- **packfile** —— 压缩存储,把多个对象打包

### 4.4 Git 对象的内部格式(给你一把"X 光")

Git 对象在磁盘上是 zlib 压缩的二进制。但解压后,内容很可读:

```bash
# 看 HEAD 指向的 commit 内部
git cat-file -p HEAD
# tree 9b8d4c2...
# parent 4e1a7b3...
# author Your Name <you@x.com> 1700000000 +0800
# committer Your Name <you@x.com> 1700000000 +0800
# 
# Initial commit: HH Rust project setup

# 看 tree 内部(目录列表)
git cat-file -p HEAD^{tree}
# 100644 blob abc123...    .gitignore
# 100644 blob def456...    Cargo.toml
# 040000 tree ghi789...    src

# 看 blob 内容(文件)
git cat-file -p abc123
# (文件原始内容)

# 看对象类型
git cat-file -t HEAD
# commit

git cat-file -t abc123
# blob
```

这些 `git cat-file` 命令是 Git 的"调试入口",让你看对象的内部结构。理解后,Git 不再是黑盒。**Casey 没在视频里演示这些,但他对 Git 内部结构了如指掌**——他能正确解释每条命令的行为,因为他理解对象模型。这是 Casey 的"我不学高级功能"的真实含义:他用 80% 的时间做 20% 的核心功能,但那 20% 他理解到骨子里。

## 5 · 对照与变奏

Git 之前的版本控制:CVS(80 年代)、SVN(2000 年)。它们都是集中式——中心服务器持有完整历史,客户端只 checkout 当前快照。这种模型的问题是中心服务器是单点故障,网络断了就没法 commit。

Git 是分布式的——每个克隆都是完整仓库,断网也能 commit/push 到本地。这种模型在开源协作里几乎成了默认。

Git 的"对头"主要是 Mercurial(Python 社区早期用)和 Perforce(游戏公司用)。Mercurial 因为 GitHub 的崛起基本被淘汰。Perforce 在游戏行业(大文件)继续占主导。

现代新版本控制系统:Fossil(SQLite 作者写,集 wiki + bug tracking 一体)、Pijul(基于 patch theory,理论更优雅)、Jujutsu(用 Rust 写,兼容 Git 后端)。这些都没撼动 Git 的统治地位——网络效应太强。

### Git 的设计哲学:UNIX 管道精神

Linus 在 2007 年的 Google Tech Talk 里讲 Git 设计时,反复强调一个原则:**Git 是工具集,不是单体应用**。Git 的每个命令(`git add`、`git commit`、`git log`...)是独立的小工具,通过管道组合。这和 UNIX 哲学一致——do one thing well。

例子:你想统计本周 commit 数,不需要 Git 内置这个功能,直接管道:

```bash
git log --since="1 week ago" --pretty=format:"%h" | wc -l
# --pretty=format:"%h" 只输出 hash,每行一个
# wc -l 数行数
```

这种"组合性"是 Git 比 SVN/CVS 优雅的地方——后者是单体软件,功能由开发者决定,用户无法扩展。Git 把所有数据通过 `git log`、`git show`、`git cat-file` 这些"原语"暴露出来,用户用 shell 组合。

Casey 在视频里其实没充分展示这种"组合性",因为他只用 `commit` 和 `checkout`。但**理解 Git 的设计精神,你后面学任何 CLI 工具(docker、kubectl、systemctl)都会快**——它们都遵循 UNIX 管道精神。

### "复制文件夹"为什么不专业?

Casey 之前的"复制文件夹"做法听起来原始,但他在视频里给出理由:他要保证每个版本"完全独立",不依赖外部工具。如果 Git 仓库被误删,500 集 history 全没。但复制文件夹到独立硬盘,每个备份是 self-contained 的。

这种"不依赖工具"的哲学在嵌入式开发、安全关键系统(医疗、航空)里也常见。但开源协作的代价太高——没有 Git 就没法 PR、没法 review、没法自动化测试。Casey 现在引入 Git,是因为 HH 项目要发布到 GitHub,他需要协作流程。

**对自学者**:你跟本教程,从 Day 1 就该用 Git。理由:(1)你将来要贡献开源,Git 是必备技能;(2)你回看本教程,能 git log 看自己每天的进步,极有成就感;(3)如果你改坏代码,git checkout 一键回到上一个 working 版本。Casey 的"500 天不用 Git"是教学效果,不是实践建议。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:Casey 说"Git 是 DAG(有向无环图),不是链表"。如果不用 branch/merge,Git 历史就是链表。所以 Casey 的"链式 commit"用法是不是 Git 的滥用?

**参考解答**:不是滥用。DAG 是 Git 的**模型**,链表是 DAG 的**特例**——每个节点只有一个父节点时,DAG 退化为链表。Casey 的"线性历史"完全合法,只是 Git 表达力的一个子集。Git 不强制你用合并,你可以一辈子只用线性 commit。这是 Git 的"渐进复杂度"设计:简单需求简单用,复杂需求复杂用,工具不强迫你学全部。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:给你的 HH Rust 项目设置一个完整的 Git 工作流:(1)`git init`(如果还没初始化);(2)写 `.gitignore` 忽略 `/target`、`*.lock-bak`、`/.vscode`(可选);(3)配置 `user.name` 和 `user.email`;(4)首次 `git commit -m "Initial commit"`;(5)看 `git log` 确认。运行后:`git log` 显示你的初始 commit。

**参考解答**:

```bash
# 1. 初始化(在项目根目录)
git init
# Initialized empty Git repository in /home/sun/src/handmade-hero-guide/.git/

# 2. 配置用户信息(只需一次,会写入 ~/.gitconfig)
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# 3. 写 .gitignore
cat > .gitignore << 'EOF'
# Rust 编译产物
/target
**/target

# 编辑器临时文件
*.swp
*~
.vscode/
.idea/

# 系统垃圾文件
.DS_Store
Thumbs.db

# 日志
*.log

# 不进版本控制的资产(按需)
# /assets/raw_psd
EOF

# 4. 查看将要提交的内容
git status
# On branch main
# No commits yet
# Untracked files:
#   (use "git add <file>..." to include in what will be committed)
#         .gitignore
#         Cargo.toml
#         src/
#
# nothing added to commit but untracked files present

# 5. 把所有文件加入暂存区
git add .
# (无输出,但 .git/index 已更新)

# 6. 提交
git commit -m "Initial commit: HH Rust project setup"
# [main (root-commit) 7a3f2e1] Initial commit: HH Rust project setup
#  12 files changed, 345 insertions(+)
#  create mode 100644 .gitignore
#  create mode 100644 Cargo.toml
#  ...

# 7. 查看历史
git log
# commit 7a3f2e1... (HEAD -> main)
# Author: Your Name <you@example.com>
# Date:   Mon Jun 23 12:00:00 2026 +0800
# 
#     Initial commit: HH Rust project setup

# 8. 查看更紧凑的历史
git log --oneline
# 7a3f2e1 Initial commit: HH Rust project setup
```

为什么这么写:`.gitignore` 必须在第一次 commit 前写好,否则编译产物会被 Git 追踪,后面再 ignore 也没用。`--global` 配置一次,所有项目共享。`git status` 是你最常用的命令——它告诉你现在工作目录的状态,而 `git log` 看历史。

### Lv3 · 迁移设计(换场景用同一原理)

**题**:你有一个 Rust 项目,已经 commit 了 10 次。最近一次 commit 引入了一个崩溃 bug,你想用 Git 找出"哪一次 commit 引入了 bug"。你不想手动测试每一次 commit——Git 有什么命令能帮你做这件事?

**提示**:`git bisect` 命令。它做二分搜索:你告诉它"这个 commit 是好的(老版本)"、"这个 commit 是坏的(最新)",Git 自动 checkout 中间 commit,你测试后告诉 Git 好坏,几次后定位到引入 bug 的具体 commit。

### Lv4 · 开源贡献

**题**:找一个你在用的 Rust crate(比如 `serde` / `anyhow` / `tokio`)。在 GitHub 上 fork 它,克隆你的 fork 到本地。看它的 commit 历史有多长?最近 10 个 commit 在做什么?找一个看起来简单的小 issue(标了 `good first issue` 标签),fork → 改 → push → 发 PR。即使你的改动只是修一个 typo 或加一个 doc comment,这是真实的开源贡献。

```rust
// 在 Rust 代码里调用 Git 命令(可选高级用法)
// 用 git2 crate(libgit2 的 Rust 绑定)

// Cargo.toml:
// [dependencies]
// git2 = "0.18"

use git2::Repository;

fn main() {
    // 打开当前目录的 Git 仓库
    let repo = Repository::open(".").expect("not a git repository");
    
    // 拿到 HEAD
    let head = repo.head().expect("no HEAD");
    let commit = head.peel_to_commit().expect("HEAD not a commit");
    
    println!("current commit: {}", commit.id());
    println!("message: {}", commit.message().unwrap_or("(no message)"));
    println!("author:  {}", commit.author().name().unwrap_or("(unknown)"));
    println!("time:    {}", commit.time().seconds());
}
```

出错怎么办:

- **`fatal: not a git repository`**:你不在 Git 仓库里。`cd` 到项目目录,或 `git init`。
- **`error: pathspec '...' did not match any files`**:你 `git add` 的路径不对,用 `git status` 看实际文件路径。
- **`nothing to commit, working tree clean`**:你没有改动,或所有改动已被 `.gitignore` 忽略。`git status --ignored` 看被忽略的文件。
- **`git config` 配置丢失**:检查 `~/.gitconfig` 是否存在。`git config --list --show-origin` 显示每个配置的来源文件。
