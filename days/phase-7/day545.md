
# Day 545 · 加地表覆盖

> 游戏地板上一直空空荡荡——只有大块的地面 mesh,没有"小草、小石头、落叶"这种细节。Day 545 Casey 加 **ground cover(地表覆盖)**:在每个地砖上撒一批小 mesh,让世界有"密度感"。

## 0 · 为什么要有这一天

回想你玩过的开放世界游戏:《塞尔达:旷野之息》的草地、《艾尔登法环》的乱石堆、《巫师 3》的落叶。这些"小东西"看似无关紧要,但少了它们整个世界会感觉"塑料"——空旷、假、不真实。

为什么?因为现实世界**从来不是干净的几何体**——草地永远有杂草,路面永远有碎石,墙边永远有落叶。这些细节给眼睛"密度信息":让大脑判断"这是真的"还是"这是模型"。

技术层面,ground cover 是个**渲染工程问题**:

- **数量巨大**:一块地 1000 棵草,渲染开销大
- **不能 1 个 mesh 1 个 draw call**:draw call 是 GPU 调用,每次几十微秒,1000 次 = 几十毫秒,卡
- **要做 LOD**:远处的草画成一个三角形,近处画十根
- **要随风摆动**:草不动很死,但要动又得算动画

Casey 这一天只做第一件:**撒大量小 mesh**。后续的 LOD / 风动留到后面。

完成这一天之后,你具备:

- 理解 instanced rendering(实例化渲染)的动机
- 能用 Rust 在 CPU 端生成大量随机分布的点
- 知道 GPU instancing 的接口设计

### 0.1 · 为什么"撒草"是一整集的内容

很多人看到 day 545 标题"加地表覆盖",第一反应:"这不就是 for 循环里放几棵草吗?"。这种想法忽略了渲染工程的现实约束——**真实开放世界游戏的草地上有几十万到几百万棵草**,你怎么把它们画出来不卡?

让我把问题分解。假设你的游戏世界是 1km × 1km,草的密度是每平方米 10 棵(现实草地的密度)。总草数 = 1000 × 1000 × 10 = 1000 万棵。哪怕每帧只渲染玩家视野内的 100m × 100m = 1 万平方米,那就是 10 万棵草。

每棵草画一个 draw call?10 万次 draw call × 5 微秒/次 = 500 毫秒,你跑 2 FPS。**这条路走不通**。

合并成一个大 mesh?10 万棵草 × 每棵 100 个三角形 = 1000 万三角形。这不是不行,但每帧都重新合并太慢,而且草的 LOD/风动都做不到。

正确答案是 **instanced rendering**:CPU 准备"一棵草的 mesh + 10 万个 transform 矩阵",GPU 一次 draw call 内部循环画 10 万次。每次 instance 只用不同的 transform,vertex shader 跑同样的代码。

但 instancing 还有"位置怎么生成"的问题——CPU 端生成?GPU 端用 compute shader 生成?Casey 这天选 CPU 端生成,因为教学版要可调试。生产级会选 GPU 端生成(快 10 倍以上),代价是调试困难。

Day 545 的核心训练是:**理解 GPU 的"批处理"特性,学会用 CPU 端的"准备阶段"+ GPU 端的"批量执行"来对抗 per-call overhead**。这种"批处理"思路贯穿了 GPU 编程的方方面面——instanced draw、indirect draw、compute shader dispatch,甚至 Vulkan 的 command buffer 录制都是同一思想的不同应用。

### 0.2 · 确定性生成:为什么"同 seed 同输出"很重要

Casey 在视频里特别强调:"草每次都长在同一个地方,玩家走开再回来还在。"这是**确定性生成**(deterministic generation)的核心价值,值得展开讲。

假设你的 chunk 系统是这样工作的:玩家走到 (100, 0, 100),加载附近的 chunk(110, 110);玩家走开到 (200, 0, 200),chunk(110, 110)卸载;玩家走回 (100, 0, 100),chunk(110, 110)重新加载。**重新加载时,这块地上的草应该和之前一模一样**——否则玩家会觉得"草在动",世界感觉不稳定。

要做到这点,草的位置不能用 `rand::thread_rng()`(每次跑结果不同),必须用**确定性伪随机数生成器**(deterministic PRNG):给定 seed,生成的随机数序列固定。chunk (110, 110) 用 seed = hash(110, 110),每次加载这个 chunk 都用同样的 seed,生成的草位置就一样。

这种"确定性"在游戏开发里反复出现: Minecraft 的世界生成(同样 world seed 同样地形)、No Man's Sky 的星球生成(同样坐标同样星球)、Spelunky 的关卡布局(同样 seed 同样关卡)。核心思想是:**用算法代替存储**——不存 100 万棵草的位置,只存 1 个 seed,需要时按 seed 算出来。这是 procedural generation 的灵魂。

确定性还有个意外的好处:**多人游戏里玩家之间不需要同步草的位置**。每个玩家客户端各自算,因为 seed 一样,大家看到的草位置一样。这大幅减少网络带宽。

## 1 · Casey 今天做了什么

Casey 的做法是 CPU 端**预生成位置**,然后用 instanced rendering:

第一步,他定义一个 `ground_cover` 字段在每个 chunk 里,类型是 `Vec<GroundCoverPlacement>`,每个 placement 包含 position(位置)、rotation(旋转)、scale(缩放)、mesh_id(用哪个 mesh)。

第二步,他写一个**生成函数**,在 chunk 加载时调用:基于一个 seed(种子)用伪随机数撒 N 个 placement。N 由 chunk 大小和密度参数决定。

第三步,渲染时,**不是**遍历 placement 一个个画——而是把所有 placement 的 transform 矩阵打包成一个 buffer,一次 draw call 画完所有。

视频里他强调:"为什么不用 GPU 端随机生成位置?因为我想让草每次都长在同一个地方(玩家走开再回来还在)。伪随机 seed 决定位置,确定性 = 一致性。"

## 2 · 心智模型

### 类比:在沙滩上撒贝壳

想象你要在 100 平方米的沙滩上撒 1000 个贝壳,让它们看起来"自然分布"。

**朴素做法**:每次走到沙滩,扔一个贝壳,看哪儿落。但 1000 次扔太慢,且每次位置不一样。

**工程做法**:先在地图上画 1000 个点(基于种子随机生成),记下坐标。每次到沙滩,**按这个清单撒**——又快又一致。

**渲染优化**:不用 1000 个 "捡起贝壳→放下" 动作(1000 次 draw call),而是把 1000 个贝壳一起打包,"哗"地一下撒完(1 次 instanced draw call)。

### 严谨展开:伪随机 + 种子

要让"同一 chunk 每次生成同样的草",用**确定性伪随机**——给定 seed,生成的随机数序列固定。

```rust
// 简单的 xorshift32 伪随机数生成器。
// 选 xorshift 而不是更复杂的算法,因为:
//   1. 代码极短(3 个 XOR + 3 个 shift),容易记、容易写
//   2. 速度快:每个 next_u32 只要 3-5 纳秒,比 cha ChaCha20 快 10 倍
//   3. 统计性质对游戏内容生成足够(不是密码学用途)
// 缺点:低 bit 不够随机(看 Marsaglia 的论文),但游戏里用 high bit 就好
struct Rng {
    state: u32,
}

impl Rng {
    fn new(seed: u32) -> Self {
        // state == 0 会让 xorshift 永远输出 0(fixed point),要避免
        Rng { state: if seed == 0 { 0xDEADBEEF } else { seed } }
    }

    fn next_u32(&mut self) -> u32 {
        let mut x = self.state;
        // 这三个常数 (13, 17, 5) 是 George Marsaglia 2003 年论文推荐的
        // 不要乱改 —— 不同 shift 量的统计性质差别很大
        x ^= x << 13;
        x ^= x >> 17;
        x ^= x << 5;
        self.state = x;
        x
    }

    fn next_f32(&mut self) -> f32 {
        // 取 high 24 bit,转 [0, 1) 浮点。
        // 为什么 24?因为 f32 的 mantissa 是 23 bit + 1 implicit = 24 bit,
        // 用 24 bit 整数 / 2^24 得到最精确的 [0, 1) 浮点
        (self.next_u32() >> 8) as f32 / (1u32 << 24) as f32
    }
}

// 用法:chunk 的 seed 由 chunk_x, chunk_z 决定
fn chunk_seed(chunk_x: i32, chunk_z: i32) -> u32 {
    // Knuth 推荐的 multiplicative hash 乘数,保证不同 chunk_x/z 得到不同 seed
    (chunk_x as u32).wrapping_mul(2654435761)
        .wrapping_add(chunk_z as u32)
}

let mut rng = Rng::new(chunk_seed(110, 110));
for _ in 0..1000 {
    let x = rng.next_f32() * chunk_size;
    let z = rng.next_f32() * chunk_size;
    // 在 (x, 0, z) 放一个草
}
```

为什么用 xorshift 而不是 `rand::thread_rng()`?因为 `thread_rng` 每次跑结果不同(用系统熵做种子),不利于"同样输入 → 同样输出"。Xorshift 是确定性的,适合做内容生成。

确定性 PRNG 的另一个关键性质:**stream quality**——给定 seed 生成的序列要看起来"够随机"。Xorshift32 通过了大部分统计测试(DieHarder、TestU01 的 Crush),对游戏内容生成完全够用。如果你做科学计算需要更高质量,用 PCG 或 xoshiro256。但 xorshift32 的代码长度(6 行)和速度(每秒 10 亿次)是它的杀手锏。

### 0.x · 几种 PRNG 的对比

让我把游戏开发里常见的 PRNG 列出来,你会看到选型的权衡:

| PRNG | 周期 | 速度 | 状态大小 | 统计质量 | 适用场景 |
|---|---|---|---|---|---|
| LCG(线性同余) | 2^32 | 极快 | 4 字节 | 差 | 嵌入式 / 老 C `rand()` |
| xorshift32 | 2^32 - 1 | 极快 | 4 字节 | 中 | 游戏内容生成(本日选) |
| xoroshiro128+ | 2^128 - 1 | 快 | 16 字节 | 良 | 通用游戏 PRNG |
| PCG32 | 2^64 | 快 | 8 字节 | 优 | 高质量内容生成 |
| xoshiro256++ | 2^256 - 1 | 快 | 32 字节 | 优 | 现代游戏首选 |
| ChaCha20 | 2^256 | 慢 | 64 字节 | 极优 | 密码学、赌博游戏 |

密码学 PRNG(ChaCha20)慢但不可预测——黑客无法从输出反推 seed。游戏内容生成不需要这个性质,选 xorshift 即可。但如果你的游戏涉及真钱赌博(在线赌博机),法律要求用密码学 PRNG,玩家不能反推 next card。

### Instanced rendering 的原理

普通 draw call:

```
CPU: 渲染一个 mesh,位置 P1
GPU: 画一个 mesh 在 P1
CPU: 渲染一个 mesh,位置 P2
GPU: 画一个 mesh 在 P2
... (重复 1000 次)
```

每次 CPU→GPU 通信有固定开销(~10 微秒),1000 次 = 10 毫秒,卡。

Instanced draw call:

```
CPU: 渲染 1000 个 instance,这是 mesh,这是 1000 个 transform 矩阵
GPU: 内部循环,画 1000 个,每个用对应 transform
```

一次 CPU→GPU 通信,1 次开销。GPU 内部并行处理 1000 个 instance。

**OpenGL 接口**(参考,Handmade Hero 用 D3D,概念相同):

```glsl
// vertex shader
in vec3 base_position;    // mesh 顶点
in mat4 instance_transform; // 每个 instance 的 transform(instanced attribute)

void main() {
    vec4 world = instance_transform * vec4(base_position, 1.0);
    gl_Position = proj * view * world;
}
```

```c
// CPU 端
glVertexAttribDivisor(0, 0);  // base_position: 每顶点前进
glVertexAttribDivisor(2, 1);  // instance_transform: 每 instance 前进

glDrawArraysInstanced(GL_TRIANGLES, 0, vertex_count, instance_count);
// 一次画 instance_count 个 instance
```

### 草的特殊性:Billboard vs Mesh

Casey 这天用小 mesh(3D 模型)。但实际游戏中草通常用 **billboard**(广告牌)——一个面朝相机的 quad(四边形),贴一张草的图。原因:

- 真 mesh 一个草几 KB,1000 棵几 MB,内存大
- billboard 一棵几十字节(位置 + 朝向),内存省
- billboard 永远正面朝你,看起来"立体"(因为图本身是立体的)

但 billboard 的缺点:从上往下看就扁了(因为 quad 平躺)。游戏里用 cross-billboard(几个十字交叉的 quad)缓解。

## 3 · 四域深入

### 3.1 · 游戏编程视角

工业级 ground cover 系统:

- **Density map**:一张灰度图,亮的地方草密,暗的地方稀
- **Height-based**:海拔太高的地方不撒(雪山顶没草)
- **Slope-based**:陡坡上少撒(物理上草不容易长在悬崖)
- **Wind simulation**:用 noise 函数让草随风摆动
- **LOD**:近处 mesh,中距离 billboard,远处不画

Unreal 的 `Foliage` 系统、Unity 的 `Terrain Details` 都是 ground cover 的工业实现。Casey 这一天是教学版,后面会迭代。

### 3.2 · 图形学视角

GPU instancing 的硬件层原理:GPU 是 **SIMT**(single instruction multiple threads)架构,一个 draw call 内部,成千上万核心并行执行同样的 vertex shader 代码,只是数据不同。instancing 把"重复 draw call"变成"一次 draw call 内的循环",完美匹配 SIMT。

性能数字:NV RTX 3080 上,普通 draw call ~5 微秒,instanced draw call 不论 instance 数,~10 微秒。1000 个 mesh:

- 1000 个普通 draw call:5 ms
- 1 个 instanced draw call:0.01 ms

差 500 倍。这就是 instancing 的威力。

### 3.3 · Linux 系统编程视角

这个"批量请求"模式在系统编程里也常见:

- **io_uring**(Linux 5.1+):一次系统调用提交多个 I/O 请求,避免 per-syscall 开销
- **sendmmsg/recvmmsg**:一次发送/接收多个网络包
- **Vulkan command buffer**:录制一组命令一次提交

核心理念:**减少 per-call overhead**,把多次小请求合并成一次大请求。

### 3.4 · Rust 生态视角

Rust 的 `glam` crate 提供 `Mat4` 矩阵,`bytemuck` 提供"零拷贝"地把 Rust struct 转 GPU buffer。

```rust
use glam::Mat4;
use bytemuck::{Pod, Zeroable};

#[repr(C)]
#[derive(Clone, Copy, Pod, Zeroable)]
struct InstanceRaw {
    transform: [[f32; 4]; 4],  // Mat4
}

fn build_instances(placements: &[Placement]) -> Vec<InstanceRaw> {
    placements.iter().map(|p| {
        let t = Mat4::from_translation(p.position.into());
        let r = Mat4::from_rotation_y(p.rotation);
        let s = Mat4::from_scale(p.scale.into());
        InstanceRaw { transform: (t * r * s).to_cols_array_2d() }
    }).collect()
}

// 这个 Vec 可以直接送 GPU:
// let instance_buffer = device.create_buffer_with_data(&instances);
```

如果想生成确定性伪随机,用 `rand_xoshiro`(快速、确定性):

```rust
use rand_xoshiro::Xoshiro256PlusPlus;
use rand::{SeedableRng, Rng};

let mut rng = Xoshiro256PlusPlus::seed_from_u64(chunk_seed);
let x: f32 = rng.gen_range(0.0..chunk_size);
```

## 5 · 对照与变奏

游戏行业 ground cover 演化:

- **1990s**:几乎没 ground cover,纯纹理。Super Mario 64 的"草"就是绿色地面贴图

工业化方向:从"贴图假装"到"真几何",从 CPU 生成到 GPU 生成。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 ground cover 用"伪随机"而不是"真随机"?如果用真随机,玩家走开再回来,草还在原位吗?

**参考解答**:伪随机给定 seed 输出固定,真随机每次跑结果不同。如果用真随机,玩家走开再回来,chunk 重新加载,草重新撒——位置全变了,玩家会觉得"草在动"。伪随机保证 chunk 每次生成的草位置一致,世界感觉稳定。这就是"确定性生成"的核心价值——同样输入永远同样输出。

### Lv2 · 动手实践

**题**:写一个程序,在 10x10 的 chunk 里撒 200 棵草。要求:

- 用 xorshift PRNG,seed = chunk_x * 31 + chunk_z
- 每个草的位置 (x, 0, z) 都在 [0, 10) 范围
- 每个草有 0..2π 的随机旋转,0.8..1.2 的随机缩放
- 打印前 5 棵的位置

**参考解答**:

```rust
struct Rng { state: u32 }
impl Rng {
    fn new(seed: u32) -> Self {
        Rng { state: if seed == 0 { 1 } else { seed } }
    }
    fn next_u32(&mut self) -> u32 {
        let mut x = self.state;
        x ^= x << 13; x ^= x >> 17; x ^= x << 5;
        self.state = x;
        x
    }
    fn next_f32(&mut self) -> f32 {
        (self.next_u32() >> 8) as f32 / (1u32 << 24) as f32
    }
}

#[derive(Debug)]
struct Placement {
    pos: [f32; 3],
    rot: f32,
    scale: f32,
}

fn generate(chunk_x: i32, chunk_z: i32, count: usize) -> Vec<Placement> {
    let seed = (chunk_x as u32).wrapping_mul(31).wrapping_add(chunk_z as u32);
    let mut rng = Rng::new(seed);
    let mut result = Vec::new();
    for _ in 0..count {
        let x = rng.next_f32() * 10.0;
        let z = rng.next_f32() * 10.0;
        let rot = rng.next_f32() * std::f32::consts::TAU;
        let scale = 0.8 + rng.next_f32() * 0.4;
        result.push(Placement { pos: [x, 0.0, z], rot, scale });
    }
    result
}

fn main() {
    let grasses = generate(3, 7, 200);
    for (i, g) in grasses.iter().take(5).enumerate() {
        println!("{}: pos={:?} rot={:.2} scale={:.2}", i, g.pos, g.rot, g.scale);
    }
    // 再生成一次验证确定性
    let grasses2 = generate(3, 7, 200);
    assert_eq!(grasses[0].pos, grasses2[0].pos);
    println!("确定性验证通过");
}
```

```rust
use glam::{Mat4, Quat, Vec3};

// 确定性 PRNG
struct Rng { state: u32 }
impl Rng {
    fn new(seed: u32) -> Self {
        Rng { state: if seed == 0 { 0xCAFEBABE } else { seed } }
    }
    fn next_u32(&mut self) -> u32 {
        let mut x = self.state;
        x ^= x << 13; x ^= x >> 17; x ^= x << 5;
        self.state = x;
        x
    }
    fn range(&mut self, lo: f32, hi: f32) -> f32 {
        let t = (self.next_u32() >> 8) as f32 / (1u32 << 24) as f32;
        lo + t * (hi - lo)
    }
}

// 一个 chunk 的地表覆盖
struct ChunkCover {
    placements: Vec<Placement>,
}

#[derive(Clone, Debug)]
struct Placement {
    pos: Vec3,
    rot_y: f32,   // Y 轴旋转
    scale: f32,
    mesh_id: u32, // 用哪个 mesh
}

impl ChunkCover {
    fn generate(chunk_x: i32, chunk_z: i32, chunk_size: f32) -> Self {
        let seed = (chunk_x as u32)
            .wrapping_mul(2654435761)  // Knuth 推荐的乘数
            .wrapping_add(chunk_z as u32);
        let mut rng = Rng::new(seed);

        // 密度:每平方米 5 棵草
        let count = (chunk_size * chunk_size * 5.0) as usize;
        let mut placements = Vec::with_capacity(count);

        for _ in 0..count {
            let x = rng.range(0.0, chunk_size);
            let z = rng.range(0.0, chunk_size);
            let rot_y = rng.range(0.0, std::f32::consts::TAU);
            let scale = rng.range(0.8, 1.2);
            placements.push(Placement {
                pos: Vec3::new(x, 0.0, z),
                rot_y,
                scale,
                mesh_id: 0,
            });
        }

        // 也撒几个石头
        let stone_count = (chunk_size * chunk_size * 0.1) as usize;
        for _ in 0..stone_count {
            let x = rng.range(0.0, chunk_size);
            let z = rng.range(0.0, chunk_size);
            placements.push(Placement {
                pos: Vec3::new(x, 0.0, z),
                rot_y: rng.range(0.0, std::f32::consts::TAU),
                scale: rng.range(0.3, 1.0),
                mesh_id: 1,  // 石头
            });
        }

        ChunkCover { placements }
    }

    // 构造 instance 矩阵数组,送给 GPU
    fn instance_matrices_by_mesh(&self) -> Vec<Vec<Mat4>> {
        let mut result: Vec<Vec<Mat4>> = Vec::new();
        for p in &self.placements {
            while result.len() <= p.mesh_id as usize {
                result.push(Vec::new());
            }
            let t = Mat4::from_translation(p.pos);
            let r = Mat4::from_quat(Quat::from_rotation_y(p.rot_y));
            let s = Mat4::from_scale(Vec3::splat(p.scale));
            result[p.mesh_id as usize].push(t * r * s);
        }
        result
    }
}

fn main() {
    let cover = ChunkCover::generate(5, 3, 16.0);
    println!("Generated {} placements", cover.placements.len());

    let matrices = cover.instance_matrices_by_mesh();
    for (mesh_id, ms) in matrices.iter().enumerate() {
        println!("mesh_id={}: {} instances", mesh_id, ms.len());
    }

    // 验证确定性:同 chunk_x/z 生成两次
    let cover2 = ChunkCover::generate(5, 3, 16.0);
    assert_eq!(cover.placements.len(), cover2.placements.len());
    assert_eq!(cover.placements[0].pos, cover2.placements[0].pos);
    println!("Determinism OK");
}
```
