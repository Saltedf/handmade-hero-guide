# Day 460 · 向游戏提供平台文件信息

> PNG 解码器集成后,接下来 5 集是"热重载资产"系列。今天第一步:让游戏查询"资产文件的修改时间",实现"文件变了就重新加载"。

## 0 · 为什么要有这一天

游戏开发的一大痛点:**改资产(改贴图、调参数)要重启游戏**。每次小调整重启 30 秒,一上午改 100 次,1 小时没了。

**热重载(hot reload)** 解决这个问题:游戏运行时监听资产文件,文件变了自动重新加载。开发者保存 PS 里的贴图,游戏立刻看到新贴图,不用重启。

实现热重载的第一步:**让游戏知道资产文件的元数据**——尤其是"最后修改时间"(modification time)。游戏每帧查询这个时间,如果变了,触发重新加载。

Casey HH 的平台层(Phase 1)此前已经封装了文件读取,但没暴露"文件元数据"。Day 460 给平台层加这个能力,为 Day 461+ 的热重载铺路。

让我把"文件元数据"在 OS 层的实现讲清楚,这是 Day 460 的核心。

**Linux:stat 系统调用**。Linux 提供 `stat` / `fstat` / `lstat` 三个 syscall 查询文件元数据:

```c
struct stat {
    dev_t     st_dev;     // 设备 ID
    ino_t     st_ino;     // inode 号
    mode_t    st_mode;    // 文件类型 + 权限
    nlink_t   st_nlink;   // 硬链接数
    uid_t     st_uid;     // 所有者 UID
    gid_t     st_gid;     // 所有者 GID
    off_t     st_size;    // 字节数
    struct timespec st_atim;  // 访问时间
    struct timespec st_mtim;  // 修改时间  ← 热重载用这个
    struct timespec st_ctim;  // 状态改变时间
    blksize_t st_blksize; // 块大小
    blkcnt_t  st_blocks;  // 分配的块数
};
```

Rust 标准库封装:

```rust
use std::fs;
use std::time::SystemTime;

let metadata = fs::metadata("asset.png")?;
let mtime: SystemTime = metadata.modified()?;
let size: u64 = metadata.len();
```

**Linux 的 mtime vs ctime**。Linux 文件有 3 个时间:

- **atime**(access time):文件被读的时间。可能更新慢(默认 `relatime` mount 选项,只在过去 24 小时或 mtime 之后才更新)。
- **mtime**(modification time):文件内容被修改的时间。**热重载用这个**。
- **ctime**(change time):文件 inode 被改变的时间——权限、所有者、链接数变化等。**不是内容修改**。

很多人混淆 mtime 和 ctime。Casey HH 用 mtime,因为"内容变了"是热重载关心的。

**Windows:GetFileAttributesEx**。Windows API 不同:

```c
WIN32_FILE_ATTRIBUTE_DATA attrs;
GetFileAttributesEx(L"asset.png", GetFileExInfoStandard, &attrs);
// attrs.ftCreationTime, ftLastAccessTime, ftLastWriteTime
```

`ftLastWriteTime` 是 Windows 上的 mtime 等价。

**跨平台抽象**。`std::fs::metadata` 在 Linux/Windows/macOS 都返回 `SystemTime`,统一接口。Casey HH 自己写平台层(教学目的),手写每个 OS 的封装;Rust 项目用标准库就够了。

**mtime 的精度**。Linux 默认 mtime 是纳秒精度(timespec),但 FAT32 文件系统只到 2 秒精度,NTFS 是 100 ns,SMB 可能是 1 秒。**热重载要看精度**——如果保存两次差 100 ms 但 mtime 精度只到秒,第二次不会被检测。

工业方案:**对比 mtime + size**——mtime 变 OR size 变都触发重载。或用文件 inode/Content hash 做更可靠的检测。

**文件监听 vs 轮询**。Day 460 的"每帧查 mtime"是**轮询**。Linux 有更高效的 **inotify**(事件驱动):

```rust
use notify::{Watcher, RecursiveMode, Event};
let mut watcher = notify::recommended_watcher(|res: Result<Event, _>| {
    if let Ok(event) = res {
        println!("File changed: {:?}", event.paths);
    }
})?;
watcher.watch("assets/", RecursiveMode::Recursive)?;
// watcher 在后台线程接收内核事件
```

inotify 让内核推送"文件变化"事件到用户态,而不是用户态每帧轮询。**游戏开发用 inotify 或 polling 都常见**——inotify 省电(不轮询),polling 简单(无后台线程)。

Casey HH 用 polling——简单、跨平台一致。工业大型引擎(Unreal)用 inotify / ReadDirectoryChangesW (Windows)。

## 补充:文件系统的"事件"模型

让我把"事件驱动"vs"轮询"的对比讲深一点,这是 Day 460 的核心架构决策。

**轮询(polling)**。每帧/每秒问 OS:"这个文件变了吗?" Casey HH 用。

```rust
loop {
    let mtime = fs::metadata(path)?.modified()?;
    if mtime != last_mtime {
        reload(path);
        last_mtime = mtime;
    }
    sleep(Duration::from_millis(100));
}
```

**优点**:简单、跨平台、无需特殊权限。**缺点**:CPU 浪费(每秒查 10 个文件 = 10 syscall/s)、延迟(100ms polling = 100ms 最大延迟)。

**事件驱动(events)**。OS 推送"文件变了"事件给应用。

**Linux: inotify**。Linux 内核提供的文件事件机制:

```c
int fd = inotify_init();
int wd = inotify_add_watch(fd, "asset.png", IN_MODIFY);
char buf[4096];
read(fd, buf, sizeof(buf));  // 阻塞,直到事件
// buf 里有 IN_MODIFY 事件结构
```

inotify 让内核在文件变化时唤醒你的进程,而不是你主动问。零 CPU 开销,毫秒级延迟。

**Rust 封装**:`notify` crate 跨平台:

```rust
use notify::{Watcher, RecursiveMode, EventKind};

let (tx, rx) = std::sync::mpsc::channel();
let mut watcher = notify::recommended_watcher(tx)?;
watcher.watch("assets/", RecursiveMode::Recursive)?;

for event in rx {
    if let Ok(e) = event {
        match e.kind {
            EventKind::Modify(_) => {
                for path in &e.paths {
                    reload(path);
                }
            }
            _ => {}
        }
    }
}
```

notify 在 Linux 用 inotify,macOS 用 FSEvents,Windows 用 ReadDirectoryChangesW——统一 API。

**事件驱动的挑战**:

1. **事件洪流**:大量文件同时变(比如 git checkout),事件队列爆。
2. **事件去重**:文本编辑器经常 "save to .tmp + rename",触发多个事件。
3. **事件丢失**:进程没读队列,事件被丢。

工业方案:**debounce**——把短时间内多个事件合并:

```rust
struct Debouncer {
    pending: HashMap<PathBuf, Instant>,
    debounce_ms: u64,
}

impl Debouncer {
    fn on_event(&mut self, path: PathBuf) {
        self.pending.insert(path, Instant::now());
    }
    fn poll_ready(&mut self) -> Vec<PathBuf> {
        let now = Instant::now();
        let debounce = Duration::from_millis(self.debounce_ms);
        let ready: Vec<_> = self.pending.iter()
            .filter(|_, t| now.duration_since(**t) > debounce)
            .map(|p, _| p.clone())
            .collect();
        for p in &ready { self.pending.remove(p); }
        ready
    }
}
```

500ms debounce 让"快速保存多次"只触发一次重载。

**Casey HH 选 polling 的理由**:

- 教学简化(不引入后台线程)
- 跨平台一致(inotify 是 Linux only)
- 资产少时 polling 开销可接受(每帧 stat 几个文件)

工业级引擎用 events + debounce——更快、更省。但你能在 Casey HH 基础上扩展。

## 补充:Linux 文件系统的 inode 模型

让我把 Linux 文件系统的"inode"概念讲清楚,这是 Day 460 stat syscall 背后的核心抽象。

**inode(index node)**。Linux 文件系统的核心数据结构——每个文件有一个 inode,存:

- 文件大小、权限、所有者、时间戳(mtime、ctime、atime)
- **数据块的指针**(文件内容存在 disk 的哪些 block)
- inode 编号(唯一标识文件)

**目录**。目录是个特殊文件,内容是"文件名 → inode 编号"的映射表。所以 Linux 文件系统是:

```
目录树(文件名) → inode 表 → 数据块
```

**硬链接(hard link)**。多个文件名指向同一 inode:

```bash
$ echo "hello" > a.txt
$ ln a.txt b.txt  # 硬链接
$ ls -li a.txt b.txt
12345 -rw-r--r-- 2 user a.txt    # inode 12345, link count 2
12345 -rw-r--r-- 2 user b.txt    # 同 inode

$ rm a.txt  # 只删 link count 减 1
$ ls -li b.txt
12345 -rw-r--r-- 1 user b.txt    # inode 还在,数据可访问
```

`rm` 删的是"文件名 → inode"映射,inode 等所有 link 删才释放。

**这对 mtime 的影响**:mtime 是 inode 的属性,不是文件名的。同一 inode 的所有 hard link 看到同一 mtime。

**符号链接(symbolic link / soft link)**。文件内容是"另一个文件的路径":

```bash
$ ln -s a.txt c.txt  # 软链接
$ ls -li c.txt
67890 lrwxrwxrwx 1 user c.txt -> a.txt
```

c.txt 是独立 inode,内容是字符串 "a.txt"。读 c.txt 时 OS 解析路径,实际读 a.txt。

**热重载考虑**:

- 监听 hard link 任一个,看到的是同一 inode 的 mtime。
- 监听 symlink,看的是 symlink 自己的 mtime(symlink 改了);如果 symlink 指向的目标改了,你不直接看到(要 follow symlink 看 target)。

工业 asset pipeline 通常 `canonicalize` 路径——把所有 symlink 解析成最终路径,确保监听的是真实文件:

```rust
use std::fs;
let canonical = fs::canonicalize("assets/sprite.png")?;
// canonical 现在是 /home/user/game/assets/sprite.png(无 symlink)
```

**mtime 的稳定性**。Linux mtime 用 `struct timespec`,纳秒精度。同一文件在 1ms 内改两次,mtime 应该能区分。但有些文件系统(FAT32、网络挂载)精度低。**对策**:对比 mtime + size + inode,任一变化都触发。

```rust
fn file_signature(path: &Path) -> (SystemTime, u64, u64) {
    let meta = fs::metadata(path).unwrap();
    (
        meta.modified().unwrap(),
        meta.len(),
        // inode 在 Linux 用 std::os::unix::fs::MetadataExt::ino()
        #[cfg(unix)] { use std::os::unix::fs::MetadataExt; meta.ino() },
        #[cfg(not(unix))] { 0 },
    )
}
```

比较 `(mtime, size, inode)` 三元组,比单 mtime 稳健。

## 2 · 心智模型

### 类比:文件柜的标签

文件柜里的文件贴"修改日期"标签。你不用打开文件就知道它什么时候改过——只要看标签。

OS 给每个文件维护类似的"元数据标签":大小、修改时间、创建时间、权限等。这些元数据和文件内容分开存储(inode),查询快——不用读文件内容。

### 严谨原理:Linux 文件元数据

Linux 用 inode(index node)存储文件元数据。`stat(2)` 系统调用查询:

```c
struct stat {
    dev_t     st_dev;     // 设备 ID
    ino_t     st_ino;     // inode 号
    mode_t    st_mode;    // 文件类型 + 权限
    nlink_t   st_nlink;   // 硬链接数
    uid_t     st_uid;     // 所有者用户 ID
    gid_t     st_gid;     // 所有者组 ID
    off_t     st_size;    // 字节大小
    time_t    st_atime;   // 最后访问时间
    time_t    st_mtime;   // 最后修改时间(本日核心)
    time_t    st_ctime;   // 最后状态变化时间
    blksize_t st_blksize; // 块大小
    blkcnt_t  st_blocks;  // 块数
};
```

**`st_mtime`** 是热重载关心的字段——内容最后修改的时间。

### Rust 跨平台 API

```rust
use std::fs;
use std::time::SystemTime;

fn get_file_mtime(path: &str) -> std::io::Result<SystemTime> {
    let metadata = fs::metadata(path)?;
    metadata.modified()
}
```

每行解释:
- `fs::metadata` 跨平台:Linux 调 `stat`,Windows 调 `GetFileAttributesExW`。
- `metadata.modified()` 返回 `SystemTime`,跨平台抽象。
- 不读文件内容,只查元数据——快速。

### 比较时间

```rust
use std::time::SystemTime;

struct AssetWatcher {
    last_mtime: Option<SystemTime>,
    path: String,
}

impl AssetWatcher {
    fn new(path: &str) -> Self {
        Self { last_mtime: None, path: path.to_string() }
    }
    fn check_and_reload(&mut self) -> bool {
        let current = match std::fs::metadata(&self.path)
            .and_then(|m| m.modified()) {
            Ok(t) => t,
            Err(_) => return false,
        };
        if Some(current) != self.last_mtime {
            self.last_mtime = Some(current);
            true  // 变了
        } else {
            false
        }
    }
}
```

每行解释:
- `last_mtime` 初始 None,第一次总是返回 true(触发初始加载)。
- `metadata.and_then(m.modified)` 链式处理 IO 错误。
- `Some(current) != self.last_mtime` — Option 比较,简单清晰。

### 轮询频率

每帧查询 N 个资产,IO 开销可能不小。优化:

```rust
const CHECK_INTERVAL_FRAMES: u32 = 60;  // 每秒检查一次(60 FPS)

struct AssetManager {
    watchers: Vec<AssetWatcher>,
    frame_counter: u32,
}

impl AssetManager {
    fn update(&mut self) -> Vec<usize> {
        self.frame_counter += 1;
        if self.frame_counter < CHECK_INTERVAL_FRAMES {
            return Vec::new();
        }
        self.frame_counter = 0;
        
        let mut changed = Vec::new();
        for (i, w) in self.watchers.iter_mut().enumerate() {
            if w.check_and_reload() {
                changed.push(i);
            }
        }
        changed
    }
}
```

每行解释:
- 每 60 帧检查一次(60 FPS = 每秒)。
- 返回变化的资产索引,让游戏层决定怎么处理。

更高效方案:**inotify**(Linux)/ **ReadDirectoryChangesW**(Windows)——内核通知变化,不用轮询。但跨平台复杂,Rust 的 `notify` crate 提供。

### Casey HH 的"平台/游戏分离"

回顾 Phase 1 的架构:平台层负责所有 OS 相关操作(开窗、IO、时间),游戏层纯逻辑。这种分离让游戏代码跨平台。

平台层的接口扩展:
```rust
// 平台层 API
pub trait Platform {
    fn read_file(&mut self, path: &str) -> Option<Vec<u8>>;
    fn get_file_mtime(&mut self, path: &str) -> Option<SystemTime>;
    // ... 其他 OS 操作
}

// 游戏层调用
fn check_asset(platform: &mut impl Platform, watcher: &mut AssetWatcher) -> bool {
    let mtime = match platform.get_file_mtime(&watcher.path) {
        Some(t) => t,
        None => return false,
    };
    if Some(mtime) != watcher.last_mtime {
        watcher.last_mtime = Some(mtime);
        true
    } else {
        false
    }
}
```

每行解释:
- `Platform` trait 抽象所有 OS 操作。
- 游戏层通过 trait object 或泛型调平台,不依赖具体 OS。
- 测试时可以 mock `Platform`,不需真实文件。

## 3 · 四域深入

### 3.1 · 游戏编程视角

热重载是工业游戏引擎的标配:

- **Unreal Engine**:编辑器内改资产实时反映到游戏视口

### 3.2 · 图形学视角

GPU 资源热重载的技术细节:

- **纹理**:`glTexImage2D` 重新上传,旧 texture ID 复用
- **shader**:`glShaderSource` + `glCompileShader`,如果失败保留旧 shader
- **mesh**:类似纹理,VBO 重新上传

**关键**:**资源 ID 不变**。游戏代码用 `TextureId(42)` 引用,重载后 42 仍指向新纹理。这要求资源管理器把 ID 和数据分离。

### 3.3 · Linux 系统编程视角

Linux 文件元数据:

```bash
# stat 命令看完整元数据
stat /tmp/test.png
# 输出:Size, Blocks, IO Block, Device, Inode, Links, Access, Modify, Change, Birth

# 用 ls -l --time=mtime
ls -l --full-time /tmp/test.png

# Rust 调底层 syscall(不用 std)
use std::ffi::CString;
use std::os::raw::{c_char, c_int};
extern "C" {
    fn stat(path: *const c_char, buf: *mut libc_stat) -> c_int;
}

# inotify:内核通知文件变化
sudo pacman -S inotify-tools

# 文件被修改时,内核通知

# 用 Rust inotify
# crate: notify(跨平台)/ inotify(Linux 原生)
```

**mtime vs ctime**:
- `mtime`:文件**内容**最后修改时间
- `ctime`:文件**inode** 最后修改时间(权限、所有权等)
- 热重载关心 mtime(内容变)

### 3.4 · Rust 生态视角

Rust 的文件元数据:

```rust
use std::fs;
use std::time::SystemTime;

let meta = fs::metadata("file")?;
println!("Size: {}", meta.len());
println!("Modified: {:?}", meta.modified()?);
println!("Created: {:?}", meta.created()?);  // 某些 OS 不支持

```

跨平台细节:
- `meta.created()` Linux 上返回 inode change time(不是真创建时间),Windows 才有真"创建时间"
- `meta.modified()` 全平台支持

**真实 crate**:
- `notify`:跨平台文件监听(inotify + ReadDirectoryChangesW + FSEvents)
- `notify-debouncer-full`:防抖(避免编辑器多次保存触发多次重载)

## 5 · 对照与变奏

**不同 OS 的文件元数据**:

| OS | 元数据 API | 创建时间 |
|---|---|---|
| Linux | stat / statx | 不存(用 ctime 近似) |
| macOS | stat / getattrlist | 存(BirthTime) |
| Windows | GetFileAttributesEx | 存(CreationTime) |

**为什么 Linux 没创建时间?** Unix 传统"内容为王",元数据尽量少。ext4 实际上支持 crtime,但 stat 不暴露。需要 `debugfs -R "stat <inode>"` 才能看。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么轮询 stat 比监听 inotify 简单?各自适合什么场景?

**参考解答**:轮询 stat 实现简单(几行代码),每秒检查 N 个文件,适合 N < 1000 的中小项目。inotify 高效(内核推送通知,无需轮询),适合大规模(>10000 文件)或实时性要求高。但 inotify 跨平台复杂——Linux 有 inotify,Windows 有 ReadDirectoryChangesW,macOS 有 FSEvents。`notify` crate 抽象三者,但 API 仍比 stat 复杂。

游戏开发常用轮询,因为资产数量小(几十到几百)、网络盘 inotify 不可靠。

### Lv2 · 动手实践

**题**:实现 `AssetWatcher`,监听一个文件,你手动改文件后程序检测到变化并打印"文件变了"。

**参考解答**:

```rust
use std::fs;
use std::time::SystemTime;

struct AssetWatcher {
    path: String,
    last_mtime: Option<SystemTime>,
}

impl AssetWatcher {
    fn new(path: &str) -> Self {
        Self { path: path.to_string(), last_mtime: None }
    }
    fn check(&mut self) -> bool {
        let mtime = match fs::metadata(&self.path).and_then(|m| m.modified()) {
            Ok(t) => t,
            Err(e) => {
                eprintln!("stat failed: {}", e);
                return false;
            }
        };
        if Some(mtime) != self.last_mtime {
            self.last_mtime = Some(mtime);
            true
        } else {
            false
        }
    }
}

fn main() {
    let args: Vec<_> = std::env::args().collect();
    let path = args.get(1).expect("Usage: watch <file>");
    let mut watcher = AssetWatcher::new(path);
    
    // 第一次 check,记录初始 mtime
    watcher.check();
    println!("Watching {}. Press Ctrl+C to stop.", path);
    
    loop {
        std::thread::sleep(std::time::Duration::from_millis(500));
        if watcher.check() {
            println!("[{}] File changed!", chrono::Local::now().format("%H:%M:%S"));
            // (这里实际游戏会触发资产重新加载)
        }
    }
}
```

每行解释:
- 用 0.5 秒轮询,平衡响应性和 CPU 占用。
- 第一次 check 不算"变化",只记录初始。
- 文件变化时打印时间戳。

完成标准:程序运行时你 `echo "x" >> /tmp/file` 触发变化,程序打印。

### Lv3 · 迁移设计

提示:

```rust
use notify::{Watcher, RecursiveMode, watcher, DebouncedEvent};
use std::sync::mpsc;
use std::time::Duration;

let (tx, rx) = mpsc::channel();
let mut watcher = watcher(tx, Duration::from_secs(1)).unwrap();
watcher.watch("file", RecursiveMode::NonRecursive).unwrap();

for event in rx {
    match event {
        DebouncedEvent::Write(_) => println!("changed!"),
        _ => {}
    }
}
```

## 8 · Rust / Arch 落地代码

完整 AssetManager,集成到游戏:

```rust
use std::fs;
use std::path::PathBuf;
use std::time::SystemTime;

#[derive(Debug, Clone)]
pub struct AssetInfo {
    pub path: PathBuf,
    pub last_mtime: Option<SystemTime>,
}

pub struct AssetManager {
    assets: Vec<AssetInfo>,
    check_interval_frames: u32,
    frame_counter: u32,
}

impl AssetManager {
    pub fn new() -> Self {
        Self {
            assets: Vec::new(),
            check_interval_frames: 60,
            frame_counter: 0,
        }
    }
    
    /// 注册一个资产,返回 ID
    pub fn register(&mut self, path: &str) -> usize {
        let path = PathBuf::from(path);
        let mtime = fs::metadata(&path).and_then(|m| m.modified()).ok();
        let id = self.assets.len();
        self.assets.push(AssetInfo { path, last_mtime: mtime });
        id
    }
    
    /// 每帧调用,返回变化的资产 ID 列表
    pub fn update(&mut self) -> Vec<usize> {
        self.frame_counter += 1;
        if self.frame_counter < self.check_interval_frames {
            return Vec::new();
        }
        self.frame_counter = 0;
        
        let mut changed = Vec::new();
        for (i, asset) in self.assets.iter_mut().enumerate() {
            let current = fs::metadata(&asset.path).and_then(|m| m.modified()).ok();
            if current != asset.last_mtime {
                asset.last_mtime = current;
                changed.push(i);
            }
        }
        changed
    }
    
    pub fn get_path(&self, id: usize) -> &PathBuf {
        &self.assets[id].path
    }
}

fn main() {
    let args: Vec<_> = std::env::args().collect();
    let files: Vec<_> = args.iter().skip(1).collect();
    
    let mut manager = AssetManager::new();
    for f in &files {
        let id = manager.register(f);
        println!("Registered asset {}: {}", id, f);
    }
    
    if files.is_empty() {
        eprintln!("Usage: asset_manager <file1> [file2 ...]");
        return;
    }
    
    println!("Watching {} files. Press Ctrl+C to stop.", files.len());
    
    loop {
        std::thread::sleep(std::time::Duration::from_millis(100));
        manager.frame_counter = 60;  // 强制每 100ms 检查(简化演示)
        let changed = manager.update();
        for id in changed {
            println!("[{}] Asset {} changed: {:?}",
                humantime::format_rfc3339(std::time::SystemTime::now()),
                id, manager.get_path(id));
        }
    }
}
```

每行解释:
- `AssetManager` 管理多个资产,每帧 update。
- `register` 在游戏启动时调,记录初始 mtime。
- 实际游戏 60 FPS 调用 update,每 60 帧(1 秒)检查一次。
- 本 demo 简化:每 100ms 检查(便于演示)。

### Arch Linux 工具链

```bash
# 看 stat 的所有字段
stat /tmp/test.png

# 看 inode 信息
ls -li /tmp/test.png

# 用 inotifywait 监听(命令行版)
sudo pacman -S inotify-tools
inotifywait -m /tmp/test.png

# 用 strace 看 stat 系统调用
strace -e stat,statx,fstat ./target/release/asset_manager /tmp/test.png

# 看 systemd 的"文件触发器"概念(类似思路)
systemctl list-timers
# systemd path units 也是基于 inotify

# NFS 场景(NFS 不支持 inotify,只能轮询)
mount | grep nfs  # 看你有没有 NFS 挂载
```

**Troubleshooting**:
- 程序检测不到变化 → 检查轮询间隔
- 误报(每次都变)→ 比较逻辑可能错(SystemTime 精度)
- NFS 慢 → 网络延迟,NFS mtime 可能不一致
