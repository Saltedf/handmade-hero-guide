# Day 512 · 通过 HHT 文件更新资产

> Day 511 把 HHT 集成进资产系统。Day 512 加"更新"——HHT 文件改动后,游戏自动检测并加载新资产。这是热重载(系统核心特性)的实现。

## 0 · 为什么要有这一天

让我们把镜头拉近,真实地体验这个场景。

你跟着 Casey 做到 Day 511。游戏启动时,代码读 `assets.hht`,构建 entity 数据库,加载所有 sprite 到 GPU。游戏跑起来——画面、音效、entity 全部正常工作。

然后你的美术师说:"我画了一张新怪 goblin_archer 的 sprite,加进游戏吧。" 工业级流程是这样的:

1. 美术师把 `goblin_archer.png` 放到 `assets/bitmaps/` 目录
2. 美术师编辑 `assets.hht`,在 `[bitmaps]` 段加一行 `goblin_archer`
3. 美术师(或程序员)**重启游戏**
4. 游戏读 HHT,看到 `goblin_archer`,加载 PNG,出现在 entity 编辑器里

第 3 步——**重启游戏**——是瓶颈。重启可能花 5-30 秒(取决于游戏复杂度)。如果你一天加 50 个新资产,这是 50 × 10 = 500 秒 ≈ 8 分钟,纯白等。更糟的是,重启破坏你的"测试场景"——你正在调试 player 跳跃,加了新 sprite 后,游戏重启,玩家位置回到起点,你要重新走一遍到调试点。

**热重载(Hot Reload)** 解决这个问题。美术师编辑 HHT,**保存**,**不重启**,游戏自动检测文件变化,自动重新加载新资产,**立即生效**。这就是 Day 512 的目标。

工业级游戏编辑器全部有这个特性:
- **Unity**:Edit > Preferences > Auto-Refresh,改 .asset 自动 reimport
- **Unreal**:Live Coding + Asset Hot Reload
- **Godot**:改 scene / script 立即重载
- **Bevy**:`bevy-hot-reload` crate,改 Rust 代码也能热重载

热重载不是奢侈品——它是**现代游戏开发的核心生产力工具**。Casey 在 HH Day 512 把它带给 HH 的资产系统。

### 热重载的三大挑战

实现热重载不只是"检测文件变,重新加载"这么简单。三个工程挑战:

**挑战一:文件变化检测**。你怎么知道文件变了?最简单的——每秒查文件 mtime(modification time,修改时间),对比上次记录的 mtime,如果不同就 reload。这种叫 **polling(轮询)**。优点是简单跨平台(`std::fs::metadata` 全平台),缺点是有延迟(最多 1 秒)和 CPU 开销(每秒一次系统调用)。

第二种叫 **event-based**——Linux 的 `inotify(7)`、macOS 的 `FSEvents`、Windows 的 `ReadDirectoryChangesW`。操作系统在文件变化时**主动通知**应用程序。零延迟,无 polling 开销。但每个平台 API 不同,实现复杂。

工业级用跨平台封装库(Rust 的 `notify` crate,Node.js 的 `chokidar`)——内部用各平台原生 event API,对外统一接口。

**挑战二:状态一致性(diff)**。文件变化后,你不能"全量重载"——把所有 entity 销毁再重建。这会丢失游戏状态(玩家位置、AI 状态、UI 状态)。你必须**增量更新**:

- 新加的 tag → 加载对应资产
- 删除的 tag → 卸载对应资产
- 修改的 tag → 卸载旧的 + 加载新的

这要求"diff" 算法——对比 old database 和 new database,找出 added / removed / modified 集合。和 `git diff` 同构。

**挑战三:正在使用的资产不能立即卸载**。如果玩家正拿着 sword(纹理在 GPU),你 HHT 里删除 sword,你不能立即卸载纹理——不然玩家手上的剑消失了。你需要 **引用计数(reference counting)**——只有 ref_count == 0 时才真正卸载。或者用 **延迟卸载**——标记为"pending unload",下一帧 / 几秒后真正卸载。

这三个挑战决定了 Day 512 的实现复杂度。Casey 用 polling + diff + 立即卸载(简化版),工业级加 inotify + 增量 + 引用计数。

### 为什么花一整天做这件事

有人会问:"热重载不就是 `if mtime 变了 { reload() }` 吗?为啥花一天?"

答案是:**热重载的复杂度在"边缘情况"**。具体:

- **race condition**——文件正在写一半时被读到(读到部分内容)
- **batch write**——美术师一次保存多个文件,如何处理?
- **circular dependency**——entity A 引用 entity B,B 引用 A
- **partial reload failure**——5 个新资产,3 个加载成功,2 个失败,如何 rollback?
- **reload 时的渲染**——reload 期间(可能 100ms),游戏继续渲染,但 entity 数据可能不一致

工业级热重载系统(Unity、Unreal)有几千行代码处理这些边缘情况。Casey 在 Day 512 演示最简版,但讨论了所有边缘情况——这是教学价值。

### 完成这一天,你能:

- 用 mtime / inotify 检测文件变化
- 设计增量更新算法(diff old / new,应用变化)
- 处理热重载时的状态一致性(引用计数、延迟卸载)
- 理解热重载的边界(哪些资产能热,哪些不能)
- 评估 polling vs event-based 的工程权衡

## 1 · Casey 今天做了什么

Casey 这一天做了 6 步,演示一个完整的热重载系统。

**第一步,记录 HHT 文件的 mtime**。游戏启动时,读 HHT 文件,同时用 `std::fs::metadata` 读它的修改时间,存到 `last_mtime` 字段。这是后续比较的"基线"。

**第二步,每帧 check mtime**。游戏主循环里(或每 60 帧一次),重新读文件 mtime,和 `last_mtime` 比较:

```rust
// 每帧调用一次(或每秒)
let mtime = fs::metadata("assets.hht")?.modified()?;
if mtime != self.last_mtime {
    // 文件变了!需要 reload
    self.reload();
    self.last_mtime = mtime;
}
```

`fs::metadata` 返回 `Metadata`,`.modified()` 返回 `SystemTime`。`SystemTime` 实现 `PartialEq`,可以直接 `!=` 比。如果不同,说明文件被修改过,触发 reload。

**第三步,reload 实现**。Reload 不是"清空一切再加载"——而是**增量**:

```rust
fn reload(&mut self) {
    // 1. 读文件
    let text = fs::read_to_string("assets.hht")?;
    
    // 2. 解析(新文件可能 parse 失败,要 handle)
    let new_hht = match parse_hht(&text) {
        Ok(h) => h,
        Err(e) => {
            eprintln!("HHT reload failed: {}", e);
            return;    // 解析失败,保持当前状态
        }
    };
    
    // 3. 构建 new database
    let new_db = TagDatabase::from_hht(&new_hht);
    
    // 4. Diff:找出新加 / 删除 / 修改的 tag
    let diff = diff_databases(&self.db, &new_db);
    
    // 5. 应用 diff
    for added in &diff.added {
        self.load_asset(added);    // 加载新资产
    }
    for removed in &diff.removed {
        self.unload_asset(removed);    // 卸载
    }
    
    // 6. 替换 db
    self.db = new_db;
}
```

每一步都有教学点:解析失败的优雅降级(不 panic)、diff 算法、应用 diff 的顺序(先加后删,避免中间状态空数据库)。

**第四步,加 debug 输出**。Reload 时打印新增 / 删除的 tag,让程序员看到 reload 是否生效:

```
[RELOAD] Detected file change
  + added: [bitmaps]goblin_archer
  + added: [bitmaps]tree_pine
  - removed: [bitmaps]old_test_sprite
  (2 added, 1 removed, total now 47)
```

这看似简单,实际关键——热重载 bug 常常"看不见"(文件改了但游戏没反应),log 让调试可行。

**第五步,跑游戏验证**。Casey 打开游戏,然后开另一个 terminal `vim assets.hht`,加一行 `goblin_archer`,保存,切回游戏——看到 log 输出 `[RELOAD] + added: goblin_archer`,entity 编辑器里出现 goblin_archer。**没重启**。

**第六步,讨论边界**。Casey 提到几个"不能热重载"的情况:
- 改了 entity 的 piece 结构(代码引用方式变了)
- 改了 sprite atlas 布局(整个 atlas 要重建)
- 改了 shader 代码(需要 GL 重新 link program)

这些"半热重载"边界,是真实游戏开发的工程现实。

## 2 · 心智模型

### 类比:浏览器自动刷新(livereload)

你做 Web 开发时,有没有用过 livereload?流程是这样的:

1. 你在 VSCode 写 HTML / CSS,保存
2. 浏览器(开着一个 watcher 插件)自动检测到文件变化
3. 浏览器自动刷新页面(或局部重载 CSS)
4. 你立刻看到改动效果——**不用手动 Ctrl+R**

这套工作流让你 1 秒内看到改动,迭代速度极快。Web 开发体验"丝滑",livereload 是关键之一。

Day 512 的 HHT reload 同构。你改 HHT 文件 → 游戏自动检测 → 自动重新加载 → 立即看到效果。完全一样的"save-and-see"工作流。

但游戏比 Web 复杂——浏览器刷新是"全量"(整个页面重画),游戏是"增量"(只重载变化的资产)。增量比全量难得多——你需要 diff、状态保留、引用计数。

### 文件变化检测的两种方法

**Polling(轮询)**。最简单——程序每隔 N 毫秒(`stat`/`fs::metadata`)查文件 mtime:

```rust
loop {
    let mtime = fs::metadata("assets.hht")?.modified()?;
    if mtime != last_mtime {
        reload();
        last_mtime = mtime;
    }
    sleep(Duration::from_millis(1000));    // 1 秒 polling
}
```

优点:**简单**(10 行代码)、**跨平台**(POSIX stat 全平台)、**无需特殊权限**(普通进程能 stat 任何文件)。

缺点:**有延迟**(polling 周期决定,通常 1 秒)、**有 CPU 开销**(每秒一次 syscall,虽然小,但累积)、**能耗**(笔记本 / 手机上 polling 阻止 CPU 睡眠)。

**Event-based(inotify / FSEvents / ReadDirectoryChangesW)**。操作系统维护"被监视的文件列表",文件变化时内核主动通知应用程序:

```c
// Linux inotify
int fd = inotify_init();    // 创建 inotify 实例
int wd = inotify_add_watch(fd, "/path", IN_MODIFY);    // 添加监视

char buf[4096];
read(fd, buf, sizeof(buf));    // 阻塞直到事件
// buf 里是 inotify_event 结构
```

优点:**零延迟**(文件变化的微秒级,内核立刻通知)、**零 CPU 开销**(没事不消耗)。

缺点:**平台相关**(每个 OS API 不同)、**资源限制**(inotify 默认只能 watch 8192 个文件,大型项目要调 `fs.inotify.max_user_watches`)、**实现复杂**(要 event loop、要 decode event 结构)。

工业级解决方案:`notify` crate(Rust)、`chokidar`(Node.js)、`watchdog`(Python)——内部封装各平台原生 API,对外统一接口。Casey 在 Day 512 用 polling(教学简化),工业级用 `notify` crate。

### 用 inotify-tools 实地试一下

让我们在 Arch Linux 上用 `inotifywait` 命令实地体验 inotify:

```bash
# 装 inotify-tools
sudo pacman -S inotify-tools

# 在 terminal 1:监控一个文件
touch /tmp/test.txt
inotifywait -m /tmp/test.txt

# 在 terminal 2:修改文件
echo "hello" > /tmp/test.txt
# terminal 1 立刻输出:
# /tmp/test.txt MODIFY
# /tmp/test.txt OPEN
# /tmp/test.txt MODIFY
# ...

# 监控目录递归
inotifywait -m -r /tmp/my_dir/

# 只监控特定事件
inotifywait -m -e modify,create,delete /tmp/
```

`inotifywait -m` 的 `-m` 是 monitor(持续监控,不退出)。默认是一次性(event 触发后退出)。`-r` 是 recursive(递归子目录)。`-e` 指定 event 类型(modify、create、delete、access、close_write 等)。

这是工业级 file watcher 的核心。VSCode 的文件 watcher、nodemon、cargo-watch 都基于 inotify。

### Diff 算法:set 操作

文件变了,你需要知道**具体什么变了**——哪个 tag 加了,哪个删了,哪个改了。这是 **diff 算法** 的问题。

幸运的是,我们的数据是 **set(集合)**——一组 (section, tag_name) 对。Set diff 算法实现起来不复杂:

```rust
struct DatabaseDiff {
    added: Vec<(String, String)>,    // 新 db 有,旧 db 没有
    removed: Vec<(String, String)>,    // 旧 db 有,新 db 没有
    modified: Vec<(String, String)>,    // 都有但内容变(本例简化,不算 modified)
}

fn diff_databases(old: &TagDatabase, new: &TagDatabase) -> DatabaseDiff {
    let old_keys: HashSet<_> = old.name_to_id.keys().cloned().collect();
    let new_keys: HashSet<_> = new.name_to_id.keys().cloned().collect();
    
    DatabaseDiff {
        added: new_keys.difference(&old_keys).cloned().collect(),
        removed: old_keys.difference(&new_keys).cloned().collect(),
        modified: vec![],
    }
}
```

关键操作:`set.difference(&other_set)`,返回 `set` 有但 `other_set` 没有的元素。

- `new_keys.difference(&old_keys)` → added(新加的)
- `old_keys.difference(&new_keys)` → removed(删除的)

这是 O(n) 操作(线性扫描 set)。对 1000 个 tag,几微秒。

复杂 diff(树结构、嵌套 entity)用 **Myers diff algorithm**(git 用的)或 **Patience diff**。Day 512 用 set diff 够用。

### 增量加载

Diff 给出 added / removed,然后:

- **Added** → 加载对应资产。例如新增 `[bitmaps]goblin_archer` → `load_bitmap("goblin_archer")` → PNG 解码 → 上传 GPU → 在 GPU 上有新纹理。
- **Removed** → 卸载对应资产。例如删除 `[bitmaps]old_sprite` → `unload_bitmap(old_sprite)` → GPU 纹理释放 → 显存回收。
- **Modified** → 卸载旧的 + 加载新的。

挑战:**正在使用的资产不能立即卸载**。如果玩家手持 sword(纹理在 GPU 上 bind),HHT 里删 sword,你不能立即卸载纹理——否则玩家手上剑瞬间消失。

两种解决方案:

**Reference counting(引用计数)**:每个资产有 ref_count。代码用资产时 `acquire()`(ref_count++),不用时 `release()`(ref_count--)。Ref_count == 0 才真正卸载。Rust 的 `Arc<T>`(Atomic Reference Counted)就是这个模式。

```rust
fn unload_asset(&mut self, tag: &TagId) {
    let rc = self.ref_count.get(tag).copied().unwrap_or(0);
    if rc == 0 {
        // 没人用,立即卸载
        self.gpu_textures.remove(tag);
    } else {
        // 还有人在用,标记为 pending unload
        self.pending_unloads.push(*tag);
    }
}
```

**Pending unload queue(延迟卸载)**:不立即卸载,放到队列,几秒后再尝试。如果那时 ref_count 降到 0,真卸载。

工业级用引用计数。Casey Day 512 简化版用立即卸载(假设 reload 时游戏暂停)。

### 热重载的边界:哪些资产能热,哪些不能

**能热重载**:
- **纹理 / sprite**:`glTexSubImage2D` 替换纹理内容,texture ID 不变。所有引用者自动看到新纹理。
- **音频**:类似,buffer 替换。
- **Shader**:可以,但要重新 link program。所有引用者用 program ID 不变。
- **配置数据**(HHT、JSON):解析后内存替换,代码引用新数据。
- **关卡数据**:可以,但要考虑"当前正在跑的关卡"——保留玩家位置。

**不能热重载**(或难):
- **Entity 类型的 Rust 代码**:玩家 entity 用 `Player` struct,你改 `Player` 加字段,代码要重编译。Rust 难以热重载代码本身(虽然有 `hot-lib-reloading` crate)。
- **GPU buffer 布局**:你改了 mesh vertex 格式(加 tangent),整个 mesh 要重建。引用者也要重写 vertex shader。
- **资源 ID 重新分配**:如果你重 reload 后,sword 的 TagId 从 42 变成 7,所有 `TagId(42)` 引用都失效。需要"稳定 ID"(每个 tag 一个 hash,不随 reload 变)。
- **存档兼容**:玩家存档里有 `equipped_sword: TagId(42)`。Reload 后 TagId(42) 是另一个东西。需要版本号 + 迁移。

Casey Day 512 限纹理 / 音频 / 配置热重载——这是工业级的"安全区"。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

热重载在游戏开发圈是**核心生产力工具**,不是奢侈品。每个商业引擎都做了大量投资。

**Unity**:Edit > Preferences > General > Auto-Refresh(默认开)。改 .asset / .prefab / .scene 文件,Unity 自动 reimport。Domain Reload(脚本域重载)更激进——C# 代码改了,Unity 重新编译 .dll,重新加载到 game domain。但 Domain Reload 会丢失所有 static 状态,Unity 用 `[SerializeField]` + `[FormerlySerializedAs]` 帮助保持状态。

**Unreal Engine**:两个系统:
- **Live Coding**:C++ 代码改了,增量编译 .so / .dll,运行时 swap 函数指针。**不重启游戏**就能用新代码。Epic 内部用这个迭代 AAA 游戏。
- **Asset Hot Reload**:编辑器里改 texture / mesh / material,立即反映到 game window。

**Godot**:scene / script / resource 文件保存,Godot 的 ResourceFormatLoader 自动重载。Godot 4 加了 "Reload Current Project" 命令,完全重载所有资源。

**Bevy**(Rust):`bevy-hot-reload` crate(社区),用 Rust 的 `hot-lib-reloading` crate 实现。改 Rust 代码,bevy 重载 `bevy_main` 函数,保留 ECS world 状态。这是 Rust 游戏生态的"黑科技"。

**Handmade Hero**:Day 512 的 polling mtime + diff。简单,但 Casey 自己用——他在直播里改 HHT,HH 立刻看到改动。

游戏开发圈术语:
- **Hot Reload** —— 热重载(改资源 / 配置)
- **Live Coding** —— 实时编码(改代码)
- **Livereload** —— 浏览器自动刷新(Web 术语)
- **File Watcher** —— 文件监控器
- **Asset Pipeline Refresh** —— 资产管线刷新
- **Domain Reload** —— 域重载(Unity 术语,重新加载 C# 域)
- **Reimport** —— 重新导入(改 .meta 后强制重导入)

### 3.2 · 🎨 图形学视角

纹理热重载的图形学细节。

**Texture replacement**:OpenGL 提供 `glTexSubImage2D`,**替换纹理内容**,**texture ID 不变**。所有引用 texture ID 的代码自动看到新内容——不用重新 bind、不用改 shader uniform。

```c
// 热重载纹理
GLuint tex_id = ...;    // 已有的 texture ID
glBindTexture(GL_TEXTURE_2D, tex_id);
glTexSubImage2D(GL_TEXTURE_2D, 0,    // level
                0, 0, width, height,
                GL_RGBA, GL_UNSIGNED_BYTE, new_pixels);
// 完成,所有用 tex_id 的代码自动看新纹理
```

挑战:GPU 操作是**异步的**——CPU 提交 `glTexSubImage2D`,立即返回,但 GPU 可能还没执行。如果你立即画 sprite,可能用旧纹理。需要 sync——`glFinish` 或 `glFenceSync` 等待 GPU 完成。

**Shader replacement**:类似,但要重新编译 shader,attach 到 program,link。Link 可能失败(语法错误),要 handle。

```c
GLuint new_shader = glCreateShader(GL_FRAGMENT_SHADER);
glShaderSource(new_shader, 1, &new_source, NULL);
glCompileShader(new_shader);
// 检查 compile 错误
glAttachShader(program, new_shader);
glLinkProgram(program);
// 检查 link 错误
glDetachShader(program, new_shader);
glDeleteShader(new_shader);
```

**Mesh replacement**:VBO 重新上传数据(`glBufferData` 或 `glBufferSubData`)。

**Material**:material 引用 texture,改 material 后,所有用 material 的 mesh 自动更新。

**Asset bundle / texture atlas**:大型 atlas 改了,所有引用 atlas 子区域的 sprite 都受影响。这是为什么工业级引擎把 atlas 当"特殊资产"——热重载复杂。

### 3.3 · 🐧 Linux 系统编程视角

Linux 文件监控的两个 API:**inotify(7)** 和 **fanotify(7)**。

**inotify(7)** 是经典的文件事件 API。每个 watch 是一个文件 / 目录,有 IN_MODIFY、IN_CREATE、IN_DELETE 等事件。

```c
#include <sys/inotify.h>

int fd = inotify_init();    // 创建 inotify 实例
int wd = inotify_add_watch(fd, "/path", IN_MODIFY | IN_CREATE | IN_DELETE);

char buf[4096] __attribute__((aligned(8)));
ssize_t len = read(fd, buf, sizeof(buf));    // 阻塞直到事件

// 解析 buf 里的 inotify_event 结构
ssize_t i = 0;
while (i < len) {
    struct inotify_event *event = (struct inotify_event *)&buf[i];
    printf("wd=%d mask=%u name=%s\n", event->wd, event->mask, event->name);
    i += sizeof(struct inotify_event) + event->len;
}
```

inotify 限制:`/proc/sys/fs/inotify/max_user_watches`(默认 8192)。大型项目(VS Code 监控 node_modules)会撞到这个限制,要 `echo 999999 | sudo tee /proc/sys/fs/inotify/max_user_watches` 调大。

**fanotify(7)** 是 inotify 升级版,可监控**整个文件系统**(不限于 watch 列表),但需要 root 权限。Linux 5.0+ 加了 fanotify permission events。Antivirus 软件用 fanotify。

```bash
# 装 inotify-tools,提供 inotifywait 命令
sudo pacman -S inotify-tools

# 监控单个文件
inotifywait -m /etc/hostname

# 监控目录递归
inotifywait -m -r /tmp/

# 监控特定事件
inotifywait -m -e modify,create,delete /home/user/

# 看当前 inotify watches 数
cat /proc/sys/fs/inotify/max_user_watches
# 看你的进程占了多少 inotify watch
cat /proc/*/fd/* 2>/dev/null | grep inotify | wc -l

# 看文件 mtime(access, modify, change, birth)
stat /etc/hostname
# Access: 最后访问时间
# Modify: 最后修改时间(内容)
# Change: 最后改变时间(元数据,如权限)
# Birth: 创建时间(ext4 支持)

# 用 find 找最近 1 分钟修改的文件
find / -mmin -1 -type f 2>/dev/null | head

# Linux 内核的 page cache 也是基于 LRU + 文件大小 + mtime
free -h
cat /proc/meminfo | grep -E "Cached|SwapCached"
```

`stat` 显示三种时间——`atime`(access,读时更新)、`mtime`(modify,写时更新)、`ctime`(change,inode 元数据改变时更新,如 chmod)。热重载用 mtime,因为我们要检测"内容变化"。

### 3.4 · 🦀 Rust 生态视角

Rust 文件监控生态。

**`notify` crate**:跨平台 inotify / FSEvents / ReadDirectoryChangesW。Rust 生态的事实标准。

```rust
use notify::{Watcher, RecursiveMode, RecommendedWatcher, Event};
use std::sync::mpsc::channel;
use std::time::Duration;

// 创建 channel,异步接收事件
let (tx, rx) = channel();

// 创建 watcher(用 RecommendedWatcher,自动选最佳 backend)
let mut watcher: RecommendedWatcher = notify::recommended_watcher(move |res: Result<Event, _>| {
    if let Ok(event) = res {
        tx.send(event).unwrap();
    }
}).unwrap();

// 监控文件
watcher.watch(std::path::Path::new("assets.hht"), RecursiveMode::NonRecursive).unwrap();

// 在主循环里 check events
loop {
    if let Ok(event) = rx.try_recv() {
        println!("File changed: {:?}", event);
        reload();
    }
    // 渲染游戏
    render();
}
```

`RecommendedWatcher` 自动选 backend——Linux 用 inotify,macOS 用 FSEvents,Windows 用 ReadDirectoryChangesW。一套代码三平台跑。

**`notify-debouncer`**:防抖库。文件保存时常常多次触发(WRITE、CLOSE_WRITE、ATTRIB 等),debouncer 把多个事件合并成一个。避免 reload 触发 N 次。

**`cargo-watch`**:cargo 命令的 watcher。`cargo watch -x run` 监控 Rust 源码,改了就 `cargo run` 重启。Rust 开发者日常工具。

**`watchexec`**:通用命令 watcher。`watchexec -e hht -r 'cargo run'` 监控 .hht 文件,改了重启 cargo run。和 cargo-watch 类似但不限于 cargo。

Rust 编译器考验:reload 时借 `&mut self`,但同时读文件——分两步:

```rust
// 错误:同时 &mut self 和借用文件
fn reload(&mut self) {
    let text = std::fs::read_to_string("assets.hht")?;
    self.parse_and_apply(text)?;    // 借用冲突
}

// 正确:分两步
fn reload(&mut self) {
    // 第一步:读文件,无 self 借用
    let text = match std::fs::read_to_string("assets.hht") {
        Ok(t) => t,
        Err(e) => {
            eprintln!("Reload failed: {}", e);
            return;
        }
    };
    
    // 第二步:用 self 解析
    if let Err(e) = self.parse_and_apply(&text) {
        eprintln!("Parse failed: {}", e);
    }
}
```

这是 Rust borrow checker 强制的"分阶段思考"——读文件是 I/O,parse 是状态修改,Rust 强制你把它们分开。其实是好事——清晰、可测试。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 polling mtime 比 inotify 慢,但 Casey 仍选它?

**参考解答**:三个理由:

第一,**简单**。Polling 几行代码,inotify 需要系统调用 + event loop。

第二,**跨平台**。`std::fs::metadata` 全平台,inotify 是 Linux-only。

第三,**足够快**。1 秒延迟对游戏开发可接受。inotify 的零延迟对实时系统重要,但 HH 不是。

工业级用 `notify` crate(跨平台抽象),既简单又零延迟。

### Lv2 · 动手实践

**题**:实现 HHT 热重载。模拟文件改动(改 String),检测变化,增量更新。

完成标准:`cargo run` 显示多次"reload"和每次的 diff。

**参考解答**:

```rust
use std::collections::{HashMap, HashSet};
use std::time::SystemTime;

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
struct TagId(u32);

#[derive(Debug, Default, Clone)]
struct HhtFile {
    sections: HashMap<String, Vec<String>>,
}

fn parse_hht(text: &str) -> HhtFile {
    let mut file = HhtFile::default();
    let mut section = String::new();
    for line in text.lines() {
        let line = line.trim();
        if line.is_empty() || line.starts_with('#') { continue; }
        if line.starts_with('[') && line.ends_with(']') {
            section = line[1..line.len()-1].to_string();
        } else if !section.is_empty() {
            file.sections.entry(section.clone()).or_default().push(line.into());
        }
    }
    file
}

struct TagDatabase {
    name_to_id: HashMap<(String, String), TagId>,
    next_id: u32,
}

impl TagDatabase {
    fn from_hht(hht: &HhtFile) -> Self {
        let mut db = Self { name_to_id: HashMap::new(), next_id: 0 };
        for (section, tags) in &hht.sections {
            for tag in tags {
                let id = TagId(db.next_id);
                db.next_id += 1;
                db.name_to_id.insert((section.clone(), tag.clone()), id);
            }
        }
        db
    }
    
    fn keys(&self) -> HashSet<(String, String)> {
        self.name_to_id.keys().cloned().collect()
    }
}

#[derive(Debug, Default)]
struct Diff {
    added: Vec<(String, String)>,
    removed: Vec<(String, String)>,
}

fn diff_databases(old: &TagDatabase, new: &TagDatabase) -> Diff {
    let old_keys = old.keys();
    let new_keys = new.keys();
    Diff {
        added: new_keys.difference(&old_keys).cloned().collect(),
        removed: old_keys.difference(&new_keys).cloned().collect(),
    }
}

struct AssetSystem {
    db: TagDatabase,
    last_mtime: Option<SystemTime>,
    loaded_count: usize,
}

impl AssetSystem {
    fn new() -> Self {
        Self {
            db: TagDatabase { name_to_id: HashMap::new(), next_id: 0 },
            last_mtime: None,
            loaded_count: 0,
        }
    }
    
    fn check_and_reload(&mut self, hht_text: &str, simulated_mtime: SystemTime) {
        let needs_reload = match self.last_mtime {
            None => true,
            Some(last) => simulated_mtime != last,
        };
        
        if !needs_reload { return; }
        
        println!("[RELOAD] Detected file change");
        
        let hht = parse_hht(hht_text);
        let new_db = TagDatabase::from_hht(&hht);
        let diff = diff_databases(&self.db, &new_db);
        
        for added in &diff.added {
            println!("  + added: [{}]{}", added.0, added.1);
            self.loaded_count += 1;
        }
        for removed in &diff.removed {
            println!("  - removed: [{}]{}", removed.0, removed.1);
            self.loaded_count = self.loaded_count.saturating_sub(1);
        }
        
        if diff.added.is_empty() && diff.removed.is_empty() {
            println!("  (no changes)");
        }
        
        self.db = new_db;
        self.last_mtime = Some(simulated_mtime);
    }
}

fn main() {
    let mut sys = AssetSystem::new();
    
    let t0 = SystemTime::UNIX_EPOCH;
    let t1 = t0 + std::time::Duration::from_secs(10);
    let t2 = t0 + std::time::Duration::from_secs(20);
    
    // V1
    let v1 = "[bitmaps]\nplayer\nsword\n";
    println!("=== V1 (initial) ===");
    sys.check_and_reload(v1, t0);
    println!("  loaded: {}", sys.loaded_count);
    
    // V2:加 goblin
    println!("\n=== V2 (added goblin) ===");
    let v2 = "[bitmaps]\nplayer\nsword\ngoblin\n";
    sys.check_and_reload(v2, t1);
    println!("  loaded: {}", sys.loaded_count);
    
    // V3:删 sword,加 tree
    println!("\n=== V3 (removed sword, added tree) ===");
    let v3 = "[bitmaps]\nplayer\ngoblin\ntree\n";
    sys.check_and_reload(v3, t2);
    println!("  loaded: {}", sys.loaded_count);
    
    // 没变
    println!("\n=== V4 (no change) ===");
    sys.check_and_reload(v3, t2);
    println!("  loaded: {}", sys.loaded_count);
}
```

```rust
#[cfg(test)]
mod tests {
    use super::*;
    
    #[test]
    fn test_diff_added() {
        let h1 = parse_hht("[s]\na\n");
        let h2 = parse_hht("[s]\na\nb\n");
        let d1 = TagDatabase::from_hht(&h1);
        let d2 = TagDatabase::from_hht(&h2);
        let diff = diff_databases(&d1, &d2);
        assert_eq!(diff.added.len(), 1);
        assert_eq!(diff.removed.len(), 0);
    }
    
    #[test]
    fn test_diff_removed() {
        let h1 = parse_hht("[s]\na\nb\n");
        let h2 = parse_hht("[s]\na\n");
        let d1 = TagDatabase::from_hht(&h1);
        let d2 = TagDatabase::from_hht(&h2);
        let diff = diff_databases(&d1, &d2);
        assert_eq!(diff.added.len(), 0);
        assert_eq!(diff.removed.len(), 1);
    }
    
    #[test]
    fn test_diff_no_change() {
        let h = parse_hht("[s]\na\n");
        let d1 = TagDatabase::from_hht(&h);
        let d2 = TagDatabase::from_hht(&h);
        let diff = diff_databases(&d1, &d2);
        assert_eq!(diff.added.len(), 0);
        assert_eq!(diff.removed.len(), 0);
    }
    
    #[test]
    fn test_reload_increments_count() {
        let mut sys = AssetSystem::new();
        let t = SystemTime::UNIX_EPOCH;
        sys.check_and_reload("[s]\na\nb\n", t);
        assert_eq!(sys.loaded_count, 2);
    }
    
    #[test]
    fn test_no_reload_same_mtime() {
        let mut sys = AssetSystem::new();
        let t = SystemTime::UNIX_EPOCH;
        sys.check_and_reload("[s]\na\n", t);
        let count_before = sys.loaded_count;
        sys.check_and_reload("[s]\na\nb\n", t);    // 同 mtime,不 reload
        assert_eq!(sys.loaded_count, count_before);
    }
}

fn main() {
    println!("Day 512 demo - 见 Lv2");
}
```
