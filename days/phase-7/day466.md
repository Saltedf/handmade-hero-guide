# Day 466 · 以文本形式加载显示 HHA 文件

> 你刚把 HHA 格式从 V0 升级到 V1,现在 Casey 加了一个"反工具":用文本方式把 `.hha` 二进制结构导出成人能读的清单。这听起来像在做"调试工具",但本质是工程里被严重低估的**自省(introspection)**能力——任何二进制格式,如果开发者不能反推它里面到底装了什么,后面所有问题都是黑盒。

## 0 · 为什么要有这一天

你刚做完 Day 465 的 V0→V1 迁移,看着那个 `.hha` 文件你能猜到里面有 magic、tags、assets,但你**没法眼见为实**。打开 `xxd test.hha | head` 看到一堆二进制,你能猜哪几个字节是 tag 数量?哪几个字节是 asset offset?不能。

这件事在工业界太常见了。任何一个**自定义二进制格式**(ELF、PE、PNG、BSP、glb……)的开发者,都会配一个"dumper"——把二进制按字段打印成文本,这样调试时不用 hex 编辑器一个个抠字节。Linux 上 `readelf -a a.out` 就是 ELF 的 dumper;`objdump -x` 是 PE/ELF 的 dumper;`pngcheck -v` 是 PNG 的 dumper。

Casey 这一天做的事完全对应:**给 HHA 写一个 `hhadump test.hha`**。输入文件路径,输出结构化的字段列表。这一天的真正价值不在工具本身,而在逼你回答两个问题:

第一,**你的二进制格式是不是真的"自我描述"**?如果你设计的格式只在你脑子里清楚,别人(包括三个月后的你)打开文件一脸懵,那这个格式有设计缺陷。一个好的二进制格式应该让你写 dumper 时**毫无障碍**——每个字段都能从文件里读出来,语义清楚。

第二,**你的解析器和格式 spec 是不是一致**?如果你写 dumper 时发现"咦,这个字段我以为 4 字节,实际是 2 字节",说明你的 spec 和实现已经漂移了。Day 466 的 dumper 就是把这个不一致**提前暴露**——在出 bug 之前。

完成这一天之后,你具备了:
- 给任何二进制格式快速写 dumper 的能力
- 理解为什么"可自省"是工业格式设计的硬指标
- 用 Rust 写结构化文本输出的常见模式(`writeln!` 到 `BufWriter`,`Display` trait)

## 1 · Casey 今天做了什么

Casey 这一天的动作可以拆成四步:

第一步,他在 game code 旁边加了一个独立的小工具 `hhadump`(在 Casey 的工程里通常是 `build.bat` 编译出来的另一个 exe)。命令行参数就一个:文件路径。

第二步,他写了一个 `print_hha(reader)` 函数,接受已经打开的 HHA 文件(用之前 Day 463 写的 reader API),逐字段读出来,用 `printf` 打印到 stdout。打印的格式是缩进的树状:`HHA file` / `  magic: HHA1` / `  version: 1` / `  tags: [N]` / `    [0] name=hero` ……

第三步,他遇到了一个典型的"工程小坑":V0 的字符串是 null-terminated,V1 的字符串是 length-prefix。dump 旧文件时要走 V0 路径,dump 新文件时要走 V1 路径。他在 dumper 里加了**版本分发**:`match version { 0 => dump_v0(...), 1 => dump_v1(...) }`。这就是为什么"格式升级"必须**同时**升级工具——dumper 不升级,旧文件读不了,新工具变废铁。

第四步,他跑了一遍 dumper,把输出贴到 chat 里(给观众看),然后说:"看,这就叫自省,以后调试 HHA 不用 hex 编辑器了。"

## 2 · 心智模型

### 类比:图书馆的"图书索引卡"

想象你是一座图书馆的管理员。每本书背后贴了一张索引卡,上面有:书名、作者、ISBN、馆藏位置、借阅状态。这张卡就是**元数据(metadata)**——它描述书本身的信息,不是书的内容。

`.hha` 文件就是一座小图书馆。文件里有两部分:
- **元数据区**(header + tag 表 + asset 表):告诉你"这个文件里有几个 asset、每个 asset 叫什么名字、数据存在文件哪个 offset、有多长"
- **数据区**(data blob):实际的字节流(PNG 像素、字体 glyph、音频 PCM……)

dumper 干的事,就是**把元数据区"翻译"成人话打印出来**。它不读数据区(那是 asset loader 的事),只读元数据区,然后告诉你"图书馆里有 47 本书,第 12 本叫 `hero.png`,在书架 D-3,有 2048 页"。

### 为什么 dumper 是"自省"

"自省(introspection)"这个词来自面向对象——一个对象能"问自己有什么字段、什么方法"。在二进制格式的语境里,自省意味着:**给定一个文件,你能不能不带源码、不靠记忆,光看文件就知道里面装了什么**。

设计良好的格式都会主动支持自省:

| 格式 | 自省工具 | 怎么用 |
|---|---|---|
| ELF | `readelf`, `objdump` | `readelf -a /bin/ls` |
| PE | `dumpbin`(MSVC)/ `objdump` | `dumpbin /headers notepad.exe` |
| Mach-O | `otool` | `otool -L /bin/ls` |
| PNG | `pngcheck`, `file` | `pngcheck -v photo.png` |
| glTF | `gltf-validator` | `gltf-validator scene.gltf` |
| WAV | `soxi`, `ffprobe` | `soxi beep.wav` |
| ZIP | `unzip -l`, `zipinfo` | `zipinfo archive.zip` |
| HHA | `hhadump`(本日) | `hhadump test.hha` |

注意一个共性:这些工具都**不依赖源码**。你不需要 .c 或 .rs 文件就能 dump 任何 .png——dumper 自己内嵌了格式知识。这是工程上的关键决策:**格式 spec 应该被工具完全编码,而不是依赖"读源码"**。

### Rust 怎么写 dumper

一个 dumper 的核心循环是:

```
读 magic -> 打印 "magic: HHA1"
读 version -> 打印 "version: 1"
读 tag_count -> 打印 "tags: [N]"
for i in 0..tag_count {
    读 tag[i] -> 打印 "  [i] name=..."
}
读 asset_count -> 打印 "assets: [M]"
for i in 0..asset_count {
    读 asset[i] -> 打印 "  [i] type=... name=... offset=... size=..."
}
```

这要求你的 reader API 暴露**逐字段的读取方法**(read_u32, read_string, read_bytes)。Casey 在 Day 463 已经搭好了 reader(本质是一个 cursor + 一堆 read_xxx 方法),今天 dumper 直接复用。

### 缩进和文本格式的设计

一个常被忽视的细节:dumper 的输出格式怎么设计?有三个流派:

**流派 1:树状缩进**(Casey 选这个)
```
HHA File
  magic: 'HHA1'
  version: 1
  tags (3):
    [0] name='hero'
    [1] name='enemy'
    [2] name='background'
  assets (2):
    [0] type=texture name='hero.png' offset=128 size=4096
    [1] type=sound  name='beep.wav' offset=4224 size=1024
```
优点:层次清晰,人眼易扫。缺点:难机器解析。

**流派 2:JSON 输出**
```json
{"magic": "HHA1", "version": 1, "tags": ["hero", "enemy", "background"], ...}
```
优点:既能人读也能机器解析。缺点:嵌套深时难看。Rust 用 `serde_json::to_string_pretty`。

**流派 3:S-表达式**
```
(hha (magic "HHA1") (version 1) (tags "hero" "enemy" "background") ...)
```
优点:Lisp 传统,极简。缺点:现代工程师不熟。

Casey 选流派 1,因为他**主要用途是 debug 时人眼看**,机器解析不需要。

### 版本分发:V0 vs V1

dumper 必须能同时处理 V0 和 V1 文件,因为 Day 465 之后还有 V0 文件没迁移。Casey 在 dumper 开头读 magic + version,然后:

```c
switch (version) {
    case 0: dump_v0(reader); break;
    case 1: dump_v1(reader); break;
    default: fprintf(stderr, "unknown HHA version %u\n", version); exit(1);
}
```

Rust 等价物是 `match`。**为什么必须分发**?因为 V0 和 V1 的字段顺序、字段宽度、字符串编码都不同——V0 的 string 是 null-terminated(读到一个 `\0` 停),V1 的 string 是 length-prefix(先读 u32 长度,再读那么多字节)。一个读法不能兼容两种格式。

这就是为什么格式设计里**版本号是必需的**——没有版本号,你无法分发。Casey 在 Day 463 设计 V1 时就把 version 字段写进 header,今天派上用场。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业里 dumper 是基础设施。商业引擎都有自己格式的 dumper:

- **Unreal Engine** 的 `.uasset` / `.umap` 是自定义二进制,UE 编辑器内置 dump 工具
- **Unity** 的 `.asset`(YAML 文本)和 `.assets`(二进制)有 `AssetBundle Browser`
- **id Software** 的 Quake / Doom 用 `.bsp` / `.wad`,社区写了无数 dumper(`qbsp`, `bspinfo`)

Casey 写 HHA dumper 的根本动机和这些商业引擎一样:**资产系统复杂到一定程度,你必须有内省工具,否则 debug 资产加载 bug 是噩梦**。

游戏开发常见场景:玩家报告"我的角色贴图是粉色的"(意味着贴图没加载),你打开 dumper,跑一遍:
```
$ hhadump game.hha
...
  assets (124):
    [47] type=texture name='hero.png' offset=... size=0   ← size 是 0!
```
立刻定位到"hero.png 的 size 字段为 0,导入器出 bug 了"。没有 dumper,这种 bug 你可能要花半天 hex dump。

### 3.2 · 🎨 图形学视角

虽然今天主题不是图形学,但 HHA 的 asset type 里包含 `texture`,dumper 打印 texture 时会暴露图形学相关的元数据:

- **像素格式**(RGBA8 / R8 / BC7……):dumper 应该打印,因为这决定 GPU 上传时用什么 internal format
- **尺寸**(width × height):dumper 应该打印,因为尺寸错(比如 0×0)是经典的 GPU 上传 crash 原因
- **mip level**:dumper 应该打印,因为压缩纹理(BCn)的 mip 计算有微妙规则
- **color space**(sRGB / Linear):dumper 应该打印,因为 sRGB texture 上传到 non-sRGB internal format 会导致"颜色看起来不对"

Casey 在 Day 482 之后会加 PNG tag 来标记这些信息,今天 dumper 还很简单,但这些字段以后会越加越多。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上"dumper 文化"特别浓厚。这有几个历史原因:

第一,**Unix 哲学**鼓励"小工具 + 文本流"。每个二进制格式都配一个 dump 工具,可以管道串起来:`readelf -a a.out | grep NEED | awk '{print $2}'` 拿到所有动态依赖。Casey 的 hhadump 也应该支持这种管道用法——**输出到 stdout,日志和错误输出到 stderr**,这样 `hhadump game.hha | grep hero` 就能快速过滤。

第二,**/proc 和 /sys 是内核的 dumper**。Linux 把内核状态做成文本文件暴露给用户空间——`/proc/cpuinfo` 就是 CPU 的"dump 工具"。这种"内核也用文本"的设计渗透到整个 Linux 生态。

第三,**CLI 工具链**。Linux 上你有 `jq`(JSON dumper / filter)、`xmlstarlet`(XML dumper)、`yaml-cli`、`toml-cli`……每一种结构化格式都有 dump 工具。Casey 的 hhadump 在 Linux 上是个标准操作:`hhadump game.hha | less` 翻页看。

实操:Arch Linux 上类似工具的安装:
```bash
# binutils 提供 readelf / objdump
sudo pacman -S binutils

# file 命令识别文件格式
sudo pacman -S file

# pngcheck 是 PNG dumper(在 AUR)
yay -S pngcheck

# jq 是 JSON dumper / filter
sudo pacman -S jq
```

跑几个看看输出风格:
```bash
$ readelf -h /bin/ls | head -5
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
  Class:                             ELF64
  Data:                              2's complement, little endian
  Type:                              DYN (Position-Independent Executable file)
```

注意缩进风格——**和 Casey 的 HHA dumper 一模一样**。这不是巧合,是工程界共识。

### 3.4 · 🦀 Rust 生态视角

Rust 写 dumper 有几个常见模式。

**模式 1:`Display` trait**

如果你的 HHA struct 实现了 `Display`,可以直接 `println!("{}", hha)`。但 Display 适合"短"输出,dumper 通常要长树状,Display 不够用。

**模式 2:`Debug` trait 派生**

```rust
#[derive(Debug)]
struct HhaFile { ... }
println!("{:#?}", hha);  // # 表示 pretty-print
```

这是最快的做法,Rust 自动递归打印所有字段。缺点:格式是 Rust 自己的语法(`Struct { field: value }`),不可控。

**模式 3:手写 `pretty` 函数**

```rust
impl HhaFile {
    fn dump(&self, w: &mut impl std::io::Write, indent: usize) -> std::io::Result<()> {
        writeln!(w, "{:indent$}HHA File", "", indent = indent)?;
        writeln!(w, "{:indent$}magic: {:?}", "", indent = indent + 2)?;
        // ...
        Ok(())
    }
}
```

这是 Casey 风格的对应物——完全控制输出格式,适合复杂场景。`{:indent$}` 是 Rust 的格式化 trick:用命名参数 `indent` 控制字段宽度,前面填空格。`indent + 2` 实现"递归时多缩进两层"。

**模式 4:`serde` + `serde_json`**

如果你的 HHA struct 派生了 `Serialize`,可以直接转 JSON:

```rust
use serde::Serialize;
#[derive(Serialize)]
struct HhaFile { ... }

let json = serde_json::to_string_pretty(&hha)?;
println!("{}", json);
```

这是工业 Rust 的标准做法——格式工具用 `serde` 抽象,一行代码切换 JSON / YAML / TOML / RON 输出。缺点:你的 struct 必须完全 `Serialize`,如果某些字段是 raw bytes(`Vec<u8>`),JSON 会把它编码成数字数组,很难看。

**Casey 不用 serde**,因为他要手写 reader / writer 来精确控制二进制布局(`#[repr(C)]` + 显式 offset),serde 的派生对二进制布局没帮助。他选择"手写 dumper",对应模式 3。

**BufWriter 性能**

dumper 写大量文本到 stdout 时,记得用 BufWriter 包一层:

```rust
let stdout = std::io::stdout();
let mut out = std::io::BufWriter::new(stdout.lock());
hha.dump(&mut out, 0)?;
out.flush()?;
```

`BufWriter` 把多次小 write 累积成一次大 write,减少系统调用。stdout 是 line-buffered(每次 `\n` flush),大量输出时不包 BufWriter 会慢 10 倍以上。

## 4 · 认知地图

### 4.1 上级

- **自省(Introspection)** —— 程序能"问自己有什么"
- **可观测性(Observability)** —— 系统状态能被外部观察,这是 SRE / DevOps 的核心概念
- **调试基础设施(Debug Infra)** —— 不直接产生游戏功能,但让 debug 速度快 10 倍

### 4.2 同级(并行方案)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 手写 dumper | 完全控制格式 | 调试时人眼看 | ✅ Casey 选了 |
| `Debug` 派生 | 一行代码,格式 Rust 风 | 快速验证字段值 | 备用 |
| serde JSON | 机器可读 + 人读 | 需要 pipe 给 jq / 程序 | Day 500+ 可能切 |
| hex editor | 看原始字节 | 字段对齐出 bug 时 | 偶尔辅助 |

详细说明:Casey 选手写 dumper 因为输出格式需要"缩进 + 中英混合 + 树状",这些 Rust derive 的 Debug 做不到。serde JSON 是工业 Rust 主流,但它要求所有字段都 Serialize,raw bytes 字段丑。hex editor 是最后手段——字段对齐错了(`offset` 多读 2 字节)时,hex editor 是定位 bug 的唯一办法。

### 4.3 下级

- **`Write` trait** —— Rust 标准库的输出抽象, BufWriter / File / stdout 都实现它
- **`writeln!` 宏** —— 带换行的格式化输出,返回 `io::Result<()>`
- **`{:indent$}` 格式化** —— 用命名参数控制字段宽度,实现缩进
- **cursor-based reader** —— 内部维护 offset,提供 read_u32 / read_string 等方法
- **版本分发** —— match version { 0 => ..., 1 => ... } 处理多版本格式

## 5 · 对照与变奏

### 同一格式,不同 dumper 风格

HHA 这种小格式只会有一个 dumper,但大格式(ELF、PE)有多个 dumper,风格差异显著:

- **`readelf`**:GCC / binutils 出品,输出详细冗长,机器解析友好(每行字段对齐)
- **`objdump -x`**:风格紧凑,把多个字段挤在一行
- **`llvm-readelf`**:LLVM 出品,兼容 GNU readelf 但有额外字段
- **`dwarfdump`**:专门 dump DWARF 调试信息(ELF 里的 .debug_* 段)

这种"同一格式多个 dumper"的现象说明:**dumper 不只是格式 spec 的翻译,它服务于具体调试场景**。readelf 关注链接器视角,dwarfdump 关注调试器视角,各有侧重。

### 历史演化:从 hex dump 到结构化 dump

早期(1970s)的 Unix 工具主要是 hex dump(`od`、`hexdump`、`xxd`)——逐字节打印。那时的工程师看 hex 比 ASCII 还熟。

中期(1980s-1990s)开始出现"结构化 dump":`readelf`、`objdump`、`nm`。这些工具知道格式的语义,把字节流翻译成字段。

近期(2010s-)趋势是"自描述格式 + 通用 dump 工具"。JSON / XML / YAML 这种文本格式 + `jq` / `xmlstarlet` 这种通用工具,你不用给每个新格式写专门 dumper。但二进制格式(为了紧凑、为了速度)依然存在,dumper 文化延续。

Casey 选 HHA 是二进制(为了快速加载,文件小),所以必须配 dumper。

### 文本 vs 二进制:工业权衡

| 维度 | 文本(JSON/XML) | 二进制(HHA) |
|---|---|---|
| 文件大小 | 大 2-10 倍 | 紧凑 |
| 加载速度 | 慢(解析) | 快(memcpy) |
| 调试 | `cat`, `jq` 直接看 | 需要 dumper |
| Diff 友好 | 是 | 否 |
| 人工编辑 | 是 | 否 |

游戏资产一般是**二进制为主**(PNG 像素、BC7 压缩纹理、PCM 音频),因为这些数据巨大且不需要人编辑。配置文件一般**文本**(JSON / TOML),因为需要人编辑、Git diff 友好。

HHA 是"游戏资产打包格式",选二进制合理。但 Casey 也承认,如果重来,某些元数据部分可能用 JSON,数据 blob 还是二进制——这是混合策略,glTF 2.0 就是这么做的(`.gltf` 是 JSON,`.bin` 是二进制)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 不直接用 `xxd` 这种 hex dump 工具看 HHA 文件,要专门写一个 `hhadump`?用"自省"这个概念解释。

**参考解答**:`xxd` 把字节当**无结构**的十六进制打印,你看到 `48 48 41 31 01 00 00 00`,要靠人脑识别"前 4 字节是 magic 'HHA1',后 4 字节是 version 1"。这要求你**记住格式 spec**,且**眼力精确**。任何错位(比如数错了 2 字节)后面的解读全错。

`hhadump` 把字节当**结构化字段**打印,`magic: 'HHA1'`, `version: 1`,你不用记 spec,工具替你认。这就是"自省"——格式知识编码在工具里,而不是依赖人脑。

工业类比:你能用 `cat /bin/ls` 看 ELF 吗?能,但屏幕一片乱码。`readelf -a /bin/ls` 才能看懂。readelf 就是 ELF 的"hhadump"。

### Lv2 · 动手实践

**题**:写一个 `hhadump` 工具,Rust 实现,接受文件路径参数,把 HHA 文件按树状缩进格式打印。完成标准:
- `cargo run -- test.hha` 打印出 magic / version / tags / assets 字段
- 用 Day 465 生成的 V1 文件测试
- 输出到 stdout,错误输出到 stderr,可以 `hhadump test.hha | less` 翻页

**参考解答**:

```rust
// src/bin/hhadump.rs
use std::env;
use std::fs::File;
use std::io::{self, BufWriter, Read, Write};

// 从 stdin/文件读 u32(little-endian)
fn read_u32(r: &mut impl Read) -> io::Result<u32> {
    let mut buf = [0u8; 4];
    r.read_exact(&mut buf)?;
    Ok(u32::from_le_bytes(buf))
}

// 读 length-prefix 字符串(V1):先 u32 长度,再那么多字节
fn read_string_lp(r: &mut impl Read) -> io::Result<String> {
    let len = read_u32(r)? as usize;
    let mut buf = vec![0u8; len];
    r.read_exact(&mut buf)?;
    Ok(String::from_utf8_lossy(&buf).into_owned())
}

// 读 null-terminated 字符串(V0):读到 \0 停
fn read_string_nt(r: &mut impl Read) -> io::Result<String> {
    let mut buf = Vec::new();
    let mut byte = [0u8; 1];
    loop {
        r.read_exact(&mut byte)?;
        if byte[0] == 0 { break; }
        buf.push(byte[0]);
    }
    Ok(String::from_utf8_lossy(&buf).into_owned())
}

fn dump_v1(r: &mut impl Read, w: &mut impl Write) -> io::Result<()> {
    let tag_count = read_u32(r)?;
    let asset_count = read_u32(r)?;
    
    writeln!(w, "  tags ({}):", tag_count)?;
    for i in 0..tag_count {
        let name = read_string_lp(r)?;
        writeln!(w, "    [{}] name='{}'", i, name)?;
    }
    
    writeln!(w, "  assets ({}):", asset_count)?;
    for i in 0..asset_count {
        let type_code = read_u32(r)?;
        let name = read_string_lp(r)?;
        let offset = read_u32(r)?;
        let size = read_u32(r)?;
        writeln!(w, "    [{}] type={} name='{}' offset={} size={}",
                 i, type_code, name, offset, size)?;
    }
    Ok(())
}

fn main() -> io::Result<()> {
    let args: Vec<String> = env::args().collect();
    if args.len() != 2 {
        eprintln!("Usage: {} <file.hha>", args[0]);
        std::process::exit(1);
    }
    
    let mut file = File::open(&args[1])?;
    
    // 读 magic(4 字节)
    let mut magic = [0u8; 4];
    file.read_exact(&mut magic)?;
    let magic_str = std::str::from_utf8(&magic).unwrap_or("<binary>");
    
    // 读 version
    let version = read_u32(&mut file)?;
    
    let stdout = io::stdout();
    let mut out = BufWriter::new(stdout.lock());
    
    writeln!(out, "HHA File")?;
    writeln!(out, "  magic: '{}'", magic_str)?;
    writeln!(out, "  version: {}", version)?;
    
    match version {
        1 => dump_v1(&mut file, &mut out)?,
        0 => {
            // V0 用 null-terminated 字符串,代码类似但调 read_string_nt
            writeln!(out, "  (V0 dump not implemented in this demo)")?;
        }
        v => {
            eprintln!("Error: unknown HHA version {}", v);
            std::process::exit(1);
        }
    }
    
    out.flush()?;
    Ok(())
}
```

**每行解释**:
- `from_le_bytes` —— 把 4 字节小端序组合成 u32。Intel CPU 是小端,所以 HHA 用小端
- `String::from_utf8_lossy` —— 把字节转字符串,遇到非 UTF-8 字节用 `?` 替代而不报错。这是稳健做法(文件可能含非 UTF-8)
- `BufWriter::new(stdout.lock())` —— 锁住 stdout(避免多线程时锁开销),包 BufWriter 减少系统调用
- `match version` —— Rust 的模式匹配,等价于 C 的 switch 但更安全(exhaustive)
- 错误处理用 `?` —— `Result<T, io::Error>` 自动传播,主函数返回 `Result<(), io::Error>` 让 `main` 处理

### 构造一个测试 HHA

为了测试 dumper,我们写一个简单的 HHA writer 生成测试文件:

```rust
// src/bin/hhawrite.rs(辅助工具,不是 main)
use std::fs::File;
use std::io::{self, BufWriter, Write};

fn write_u32(w: &mut impl Write, v: u32) -> io::Result<()> {
    w.write_all(&v.to_le_bytes())
}

fn write_string_lp(w: &mut impl Write, s: &str) -> io::Result<()> {
    write_u32(w, s.len() as u32)?;
    w.write_all(s.as_bytes())
}

fn main() -> io::Result<()> {
    let file = File::create("test.hha")?;
    let mut w = BufWriter::new(file);
    
    // magic
    w.write_all(b"HHA1")?;
    // version
    write_u32(&mut w, 1)?;
    // tag count + tags
    write_u32(&mut w, 3)?;
    write_string_lp(&mut w, "hero")?;
    write_string_lp(&mut w, "enemy")?;
    write_string_lp(&mut w, "background")?;
    // asset count + assets
    write_u32(&mut w, 2)?;
    // asset 0: texture hero.png
    write_u32(&mut w, 1)?;  // type_code = 1 (texture)
    write_string_lp(&mut w, "hero.png")?;
    write_u32(&mut w, 128)?;  // offset
    write_u32(&mut w, 4096)?;  // size
    // asset 1: sound beep.wav
    write_u32(&mut w, 2)?;  // type_code = 2 (sound)
    write_string_lp(&mut w, "beep.wav")?;
    write_u32(&mut w, 4224)?;
    write_u32(&mut w, 1024)?;
    
    w.flush()?;
    println!("Created test.hha");
    Ok(())
}
```

### Troubleshooting

- **`Error: Custom { kind: UnexpectedEof, error: "failed to fill whole buffer" }`** —— 文件没读完。检查 writer 和 reader 的字段顺序是否一致,某处少读了字段。
- **`magic: 'HHA\x01'` 而不是 `'HHA1'`** —— version 字段读成 magic 的一部分了。检查 offset,reader 必须严格按 writer 的顺序读。
- **dumper 输出截断** —— 没有 `out.flush()`。BufWriter 在 drop 时会 flush,但显式 flush 更安全。
- **panic on non-UTF-8 字符串** —— 用了 `String::from_utf8` 而不是 `from_utf8_lossy`。前者遇到非法字节 panic,后者替换成 `?`。
