## 1 · Casey 今天做了什么

Casey 这一天的工作:

第一步,他准备测试用例——5 个 PNG 各写 sidecar `.tags` 文件。运行游戏,tag 查询返回空。

第二步,他开始二分:

- 内容对吗?(println 打印读取到的 tag 列表)

第六步,他顺手加 unit test,确保以后不再回归:

```rust

    let raw = "hero\r\nidle\r\nwalk\r\n";
    let tags: Vec<&str> = raw.lines().map(|l| l.trim_end_matches('\r')).collect();
    assert_eq!(tags, vec!["hero", "idle", "walk"]);
}
```

## 2 · 心智模型

### 类比:翻译的"标点符号错位"

想象你让翻译把一段中文翻成英文。翻译完后你说"读不通"。怎么定位?

逐字检查翻译对不对?太慢。
比较段落结构对不对?也对,但慢。
**最快**:看标点符号——可能翻译把中文的句号"。"当成英文的"."放在错误位置,导致整段被理解成一句话。

跨平台字符串 bug 就是这种"标点错位"——`\r` 看不见,但破坏了字符串相等。

### 数据流调试的科学方法

数据流 bug 的调试遵循 Day 480 的科学法,但"观察"更难——你看不到 HHA 文件内部。需要用 dumper 把内部数据打印出来观察。

```
观察:find_by_tag("hero") 返回空,应该非空
假设 1:sidecar 文件没读
预测:println 应该输出"opening hero.png.tags"
实验:加 println,运行
结论:文件被读,假设 1 否定

假设 2:tag 字符串读错
预测:println 打印 tag 应该看到 "hero"
实验:println tag 字符串
结论:看到 "hero\r"(注意末尾 \r),假设 2 成立
```

每一步缩小可能性范围。这是 Day 480 的方法在数据流场景的应用。

### 不可见字符的诊断技巧

`\r`、`\t`、零宽空格(U+200B)、BOM(U+FEFF)——这些不可见字符是 bug 富矿。诊断技巧:

第一,**`{:?}` debug 格式**。Rust 的 `{:?}` 会转义不可见字符:

```rust
let s = "hero\r";
println!("{}", s);   // 输出:hero(看不出问题)
println!("{:?}", s); // 输出:"hero\r"(立刻看到)
```

C 的 `printf` 没这种功能,Casey 用 C 调试时只能 `printf("[%s]\n", tag)`——加方括号让末尾不可见字符的位置暴露。Rust 的 `{:?}` 自动做这事。

第二,**hexdump**。最确定的诊断——直接看字节:

```bash
echo "hero" | xxd
# 00000000: 6865 726f 0a                        hero.
# 0a 是 \n

echo "hero" | od -c
# 0000000   h   e   r   o  \n
```

如果输出有 `0d 0a`(`\r\n`),立刻知道是 Windows 换行。

第三,**`cat -A`** 显示所有不可见字符:

```bash
cat -A hero.tags
# hero^M$    ← ^M 是 \r,$ 是行尾
# idle$
# walk$
```

`^M` 就是 `\r`。一眼看出问题行。

### 跨平台字符串处理

工业代码必须考虑跨平台。规则:

第一,**永远 trim `\r\n`,不只是 `\n`**。Rust 的 `.trim()` 处理 Unicode whitespace,包括 `\r`、`\n`、`\t`、空格。但 `.lines()` 按 `\n` 分割,留下 `\r`。

```rust
let s = "hero\r\nidle\r\n";
let lines: Vec<&str> = s.lines().collect();
// lines[0] = "hero\r"  ← 注意末尾 \r!
```

正确做法:

```rust
let lines: Vec<&str> = s.lines().map(|l| l.trim_end_matches('\r')).collect();
```

第二,**注意 BOM**。UTF-8 BOM 是 EF BB BF 三个字节,有些 Windows 工具会加。读文件时检查并跳过:

```rust
fn read_without_bom(path: &str) -> io::Result<String> {
    let bytes = fs::read(path)?;
    let bytes = if bytes.starts_with(&[0xEF, 0xBB, 0xBF]) {
        &bytes[3..]
    } else {
        &bytes[..]
    };
    Ok(String::from_utf8_lossy(bytes).to_string())
}
```

第三,**注意编码**。Latin-1 vs UTF-8 vs UTF-16。Linux 文件默认 UTF-8,Windows 文本可能是 UTF-16 LE。Rust 默认 UTF-8,读 UTF-16 要用专门库(`encoding_rs`)。

Casey 在 Day 483 主要处理 `\r\n` 问题,BOM 和编码问题他暂时没遇到(因为 sidecar 是他自己生成的)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发的跨平台 bug 极多:

- 路径分隔符:`/` vs `\`
- 换行符:`\n` vs `\r\n`
- 编码:UTF-8 vs UTF-16 vs Shift-JIS
- 浮点精度:x86 vs ARM
- endianness:little vs big(老平台如 PS3 Cell)

工业引擎都有"跨平台工具库"。Unity 的 `System.IO.Path`,Unreal 的 `FPaths`,Godot 的 `OS::get_singleton()`。这些库自动处理路径、换行、编码。

Casey 在 HH 上是单人项目,Linux 开发,跨平台 bug 少。但 sidecar 文件可能是美术在 Windows 上写的,所以 `\r\n` bug 出现。

游戏开发里跨平台 bug 的最经典例子:**Konami 的《Silent Hill 2》HD Remaster**。原作 PS2,移植到 PS3/Xbox 360 时源码丢了,只能从可执行文件反编译。结果 bug 一堆——浮点精度差异导致物理异常,编码差异导致部分文本乱码。这个项目最后被玩家称为"HD 残骸版"。

理解跨平台 bug 的根源,你能避免类似悲剧。

### 3.2 · 🎨 图形学视角

图形学的跨平台 bug 主要在 shader:

- **GLSL vs HLSL vs MSL**:不同 shader 语言,语法相近但语义有微妙差异
- **row-major vs column-major matrix**:OpenGL vs DirectX 默认不同
- **clip space z 范围**:`[-1, 1]`(OpenGL)vs `[0, 1]`(DirectX)
- **UV 原点**:左下角(OpenGL)vs 左上角(DirectX)

这些差异工业引擎用 RHI 抽象层隐藏。但你写跨 API 代码时必须知道。

Casey 用 OpenGL,不用担心这些。但他在 Day 483 处理 `\r\n` 反映了"跨上下文"调试的普遍性——图形 API 差异、字符串差异,本质都是"两个上下文对同一数据的解释不同"。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的换行符约定:

- C 源码:LF(`\n`),POSIX 标准
- Shell 脚本:LF
- 配置文件(.conf, .ini):LF
- 网络协议(HTTP, SMTP):CRLF(`\r\n`),RFC 标准
- 文本文件:LF(Linux)/ CRLF(Windows)/ CR(老 Mac)

Linux 工具有几个处理换行:

```bash
# 转换 CRLF 到 LF(dos2unix)
pacman -S dos2unix
dos2unix hero.tags

# 反向(unix2dos)
unix2dos hero.tags

# 不装 dos2unix 用 sed
sed -i 's/\r$//' hero.tags   # 删除行末 \r

# 用 tr
tr -d '\r' < hero.tags > hero.tags.new

# 检测文件类型
file hero.tags
# 输出:ASCII text, with CRLF line terminators
```

Linux 内核代码严格审查换行符——任何 CRLF 提交会被拒。这是 Linux 项目维护跨发行版兼容的方式。

### 3.4 · 🦀 Rust 生态视角

Rust 标准库对换行的处理:

- `read_to_string` 不转换(原样返回)
- `.lines()` 按 Universal Line Separator 分割(Unicode line ending,包括 LF、CRLF、CR),但保留 `\r`(若原始是 CRLF)
- `.trim()` / `.trim_end()` 删除所有 Unicode whitespace

最佳实践:**读文件后立即 `.trim_end_matches(|c| c == '\r' || c == '\n')`**:

```rust
let raw = fs::read_to_string(path)?;
for line in raw.lines() {
    let line = line.trim_end_matches(|c| c == '\r' || c == '\n');
    // 处理 line
}
```

或者用 `bytes()` 而不是 `lines()`,自己控制:

```rust
let bytes = fs::read(path)?;
let s = String::from_utf8_lossy(&bytes);
for line in s.split(|c| c == '\n') {
    let line = line.trim_end_matches('\r').trim();
    // 处理
}
```

Rust crate `dunce`、`path-slash` 处理路径跨平台。`encoding_rs` 处理编码。这些是工业 Rust 跨平台工具箱。

## 5 · 对照与变奏

Casey 在 Day 483 的"不可见字符"调试,在不同领域有不同对应:

**协议**:`\r\n` 在 HTTP、SMTP、IMAP。早期 web server bug 多源自 `:` 后空格、`HTTP/1.1` 大小写。

**编码**:UTF-8 BOM 引发的 bug。Python 2 读带 BOM 的文件,第一行有 `EF BB BF` 三个字节,被解释成奇怪字符。

**二进制**:endianness。PowerPC(老 Mac、PS3)是 big-endian,x86 是 little-endian。读二进制文件不考虑 endianness 会读出乱数。

**Unicode 规范化**:NFC vs NFD。`é` 可以是 U+00E9(单个字符)或 U+0065 U+0301(e + combining acute)。两个看起来一样但字节不同。文件名比较如果不规范化,会判不相等。

理解"看似相同实则不同"是工程师的核心素养。每次你做字符串比较、文件读写、网络协议,问自己:**两端对数据的解释一致吗?**

另一个对照:**测试驱动调试**。Casey 在修 bug 后加单元测试。这是 **TDD(test-driven development)** 的反向应用——bug 先,test 后。每个 bug 都要变成 test,锁住正确行为。这是工业项目的纪律。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:为什么 Casey 不直接用 `.trim()` 而是手动 `trim_end_matches('\r')`?

**参考解答**:两个理由:

第一,**精确控制**。`.trim()` 删除所有 Unicode whitespace(包括 tab、零宽空格等),可能误删你不想删的字符。`trim_end_matches('\r')` 只删 `\r`,精确。

第二,**意图清晰**。代码读起来一眼知道在处理"Windows 换行留下的 `\r`"。`.trim()` 含义模糊,三个月后看到不知道为什么 trim。

但是,如果 sidecar 数据可能有多余空白(美术手抖打了 tab、空格),用 `.trim()` 更宽容。Casey 的选择(`trim_end_matches`)适合严格场景。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:写一个"诊断工具"。给定一个字符串切片,返回它的诊断信息:长度、首尾字符(用 `{:?}` 显示)、hex dump、是否含 `\r` 或 BOM。然后用它诊断 3 个测试字符串:`"hero"`、`"hero\r"`、`"\u{FEFF}hero"`。

完成标准:`cargo run` 输出三个字符串的诊断,清晰显示它们的差异。

**参考解答**:

```rust
fn diagnose(name: &str, s: &str) {
    println!("=== {} ===", name);
    println!("Display: [{}]", s);
    println!("Debug:   {:?}", s);
    println!("Length:  {} chars, {} bytes", s.chars().count(), s.len());
    
    if let Some(first) = s.chars().next() {
        println!("First char: {:?} (U+{:04X})", first, first as u32);
    }
    if let Some(last) = s.chars().last() {
        println!("Last char: {:?} (U+{:04X})", last, last as u32);
    }
    
    if s.contains('\r') {
        println!("⚠ Contains \\r (carriage return)");
    }
    if s.starts_with('\u{FEFF}') {
        println!("⚠ Starts with BOM (U+FEFF)");
    }
    if s.contains('\t') {
        println!("⚠ Contains \\t (tab)");
    }
    if s.contains(' ') {
        println!("⚠ Contains space");
    }
    
    // Hex dump
    print!("Hex: ");
    for b in s.as_bytes() {
        print!("{:02x} ", b);
    }
    println!();
    
    // od -c 风格
    print!("od: ");
    for b in s.as_bytes() {
        if *b >= 0x20 && *b < 0x7f {
            print!("  {} ", *b as char);
        } else {
            match *b {
                0x0a => print!(" \\n "),
                0x0d => print!(" \\r "),
                0x09 => print!(" \\t "),
                _ => print!("\\{:02x}", b),
            }
        }
    }
    println!();
    println!();
}

fn main() {
    diagnose("clean string", "hero");
    diagnose("Windows CRLF leftover", "hero\r");
    diagnose("With BOM", "\u{FEFF}hero");
    diagnose("With tab + space", "hero\tidle ");
    diagnose("Unicode combining", "café");   // é 是 U+00E9
    diagnose("Unicode decomposed", "cafe\u{0301}");  // e + combining acute
}
```

为什么这么写:`{:?}` debug 格式是 Rust 调试字符串的瑞士军刀。`hex dump` 和 `od` 风格补充诊断——当 `{:?}` 不够时(比如你想看字节级)。这套工具放进你的工具箱,以后遇到任何字符串 bug 都能秒定位。

## 8 · Rust / Arch 落地代码

下面是 Day 483 完整的 tag 系统 + 调试工具。

```rust
use std::collections::HashMap;
use std::fs;

// ========================================
// 带调试工具的 tag 系统
// ========================================

struct AssetDatabase {
    tags: Vec<String>,                          // tag 字典
    assets: Vec<Asset>,
    tag_index: HashMap<u32, Vec<u32>>,          // tag index → asset indices
}

struct Asset {
    name: String,
    first_tag_index: u32,
    one_past_last_tag_index: u32,
    // ...
}

impl AssetDatabase {
    fn new() -> Self {
        Self {
            tags: Vec::new(),
            assets: Vec::new(),
            tag_index: HashMap::new(),
        }
    }
    
    fn intern_tag(&mut self, tag: &str) -> u32 {
        // 严格 trim:删除 \r、\n、空白
        let cleaned = tag.trim_matches(|c: char| 
            c.is_whitespace() || c == '\r' || c == '\n');
        
        if let Some(i) = self.tags.iter().position(|t| t == cleaned) {
            return i as u32;
        }
        let i = self.tags.len() as u32;
        self.tags.push(cleaned.to_string());
        i
    }
    
    fn add_asset(&mut self, name: &str, tags: &[&str]) -> u32 {
        let first = self.tags.len() as u32;
        // 实际 tag index 存哪?这里我们用每 asset 一个 Vec
        // 简化:不放 tag_indices 全局表
        let tag_ids: Vec<u32> = tags.iter().map(|&t| self.intern_tag(t)).collect();
        let last = first + tag_ids.len() as u32;
        
        let asset_idx = self.assets.len() as u32;
        for &tag_idx in &tag_ids {
            self.tag_index.entry(tag_idx).or_default().push(asset_idx);
        }
        
        self.assets.push(Asset {
            name: name.to_string(),
            first_tag_index: first,
            one_past_last_tag_index: last,
        });
        
        asset_idx
    }
    
    fn find_by_tag(&self, tag: &str) -> Vec<&Asset> {
        // 注意:查询的 tag 也要 intern(同样的 trim)
        let cleaned = tag.trim_matches(|c: char| 
            c.is_whitespace() || c == '\r' || c == '\n');
        
        let tag_idx = match self.tags.iter().position(|t| t == cleaned) {
            Some(i) => i as u32,
            None => return Vec::new(),
        };
        
        match self.tag_index.get(&tag_idx) {
            Some(indices) => indices.iter()
                .map(|&i| &self.assets[i as usize])
                .collect(),
            None => Vec::new(),
        }
    }
    
    // ========================================
    // 调试工具:dump 内部状态
    // ========================================
    
    fn dump_tags(&self) {
        println!("=== Tag table ({} tags) ===", self.tags.len());
        for (i, t) in self.tags.iter().enumerate() {
            println!("  [{}] {:?}", i, t);
        }
    }
    
    fn dump_assets(&self) {
        println!("=== Asset table ({} assets) ===", self.assets.len());
        for (i, a) in self.assets.iter().enumerate() {
            println!("  [{}] name={:?} tag_range=[{}..{})",
                     i, a.name, a.first_tag_index, a.one_past_last_tag_index);
        }
    }
    
    fn dump_inverted_index(&self) {
        println!("=== Inverted index ===");
        for (tag_idx, asset_indices) in &self.tag_index {
            let tag = &self.tags[*tag_idx as usize];
            let asset_names: Vec<&str> = asset_indices.iter()
                .map(|&i| self.assets[i as usize].name.as_str())
                .collect();
            println!("  tag [{}] {:?} → {:?}", tag_idx, tag, asset_names);
        }
    }
}
```

出错怎么办:

- **`test_crlf_parsing FAILED`** —— 你的 parser 没处理 `\r`。改用 `.trim()` 或 `.trim_end_matches('\r')`。
- **`find_by_tag` 返回不一致结果** —— intern 时和 query 时用的 normalize 不一致。封装一个 `normalize_tag` 函数,两处都用。
- **大量字符串 intern 内存爆炸** —— 改用 `Rc<str>` 或 `Arc<str>` 共享。或者 `String::leak` 转 `&'static str`(程序结束时回收)。
