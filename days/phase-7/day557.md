# Day 557 · 基础动态四边形输出优化

> 游戏里的 UI、文字、debug overlay 都是 **dynamic quad**(动态四边形)——每帧重新生成、上 GPU、画。Day 555-556 优化了 3D 场景,Day 557 转向 2D/UI 路径,优化四边形渲染。

## 0 · 为什么要有这一天

让我们从一个真实性能问题说起。

你的 voxel light probe 系统在 3D 场景跑得不错,但 UI 渲染还有问题。你打开 debug overlay——一个边长 400 像素的半透明面板,里面有 100 行性能图表,每行 60 个柱状(每秒 60 帧)。一行图表 = 60 个 quad(矩形),100 行 = 6000 个 quad。加上按钮、文字、滑块、滚动条,debug overlay 一帧要画 8000+ 个 quad。

你 F5 跑游戏,看 FPS:只有 35(本该 144)。`perf record` 看热点,发现 80% CPU 时间在 `update_and_render_ui` 函数。打开 RenderDoc 抓帧,**8000 个 draw call**——每个 quad 一个 draw call。

每个 draw call 的开销:
- **CPU 端**:driver 验证 state、写 command buffer、可能锁上下文。10-50μs/draw call。
- **GPU 端**:固定开销——vertex fetcher 初始化、rasterizer 配置、ROP flush。5-20μs/draw call。
- **8000 个 draw call × 30μs 平均 = 240ms 单纯 overhead**。这远超 16.6ms 帧时间。

这就是为什么 UI 渲染需要**深度优化**。Day 557 Casey 把朴素实现改造成工业级——通过 batching、ring buffer、vertex format 压缩,把 8000 个 draw call 压到 1 个,把每帧 8MB GPU 传输降到 2MB。

但这里有个反直觉的事实:**UI 渲染的瓶颈不在 GPU,在 CPU**。GPU 画 8000 个简单 quad 毫无压力(几百万顶点 / 秒),但 CPU 端"准备 8000 个 draw call"的 overhead 极大。优化方向**不是让 GPU 更快,而是减少 CPU 工作**。

这反映了现代 GPU 编程的核心思想:**GPU 算力远超 CPU 端的"喂"能力**。CPU 一帧能"喂"给 GPU 几百到几千个 draw call(状态切换、command buffer 生成、validation 都吃 CPU),GPU 一帧能跑几百万顶点。**优化 GPU 性能,首要目标是减少 CPU 端的 draw call / state change / upload**。

UI 渲染的特点 vs 3D 渲染,你需要清晰对比:

| 维度 | 3D 渲染 | UI 渲染 |
|---|---|---|
| 顶点数 | 高(几 M) | 中(几 K-M) |
| 顶点大小 | 大(几十字节) | 中(16-32 字节) |
| Draw call 数 | 中(几百) | 应该低(几十) |
| Texture 切换 | 低 | 高(每 UI panel 不同) |
| Overdraw | 中 | 高(叠加层) |
| 是否每帧变化 | 中(mostly static) | 高(全 immediate-mode) |

UI 是 **immediate-mode**(立即模式):每帧从头重新生成所有 widget,然后丢弃。下一帧再生成。这和 3D 场景的 **retained mode**(保留模式)相反——3D 场景的 mesh 大多静态,只在物体移动时更新。

UI 的 immediate-mode 优点是**编程模型简单**(widget 函数直接画,不需要 cache / invalidation),缺点是**每帧重新生成所有顶点 + 上传 GPU**,CPU 开销大。

完成这一天之后,你具备:

- **理解 immediate-mode UI 渲染管线**:从 widget 函数到 GPU draw call 的全链路
- **能用 ring buffer 避免 GPU 内存碎片**:预分配 + 轮换,避免每帧 alloc/free
- **实现 draw call batching**:把 N 个 quad 打包成 1 个 draw call
- **用顶点格式压缩**:u16 替 f32 存 uv,u8 存 color,带宽减半
- **看懂 Dear ImGui / egui 的实现**:它们都遵循 Casey 这天的模式

## 1 · Casey 今天做了什么

Casey 这天没加新功能,而是**重写 UI 渲染管线**。让我把他的步骤拆开,你会看到每步对应一个具体瓶颈。

**第一步,vertex batching(顶点批处理)**。之前每个 quad 单独 alloc GPU buffer、单独 draw。现在他把所有 UI quad 的顶点**打包到一个连续 Vec**,一次 `vkCmdUpdateBuffer` 或 `glBufferSubData` 上传整个 Vec,一次 draw call 画完。**这一步把 8000 draw call 压到 1 个,性能直接提升 10-50 倍**。

为什么 batching 这么有效?因为 draw call 的 overhead 主要在 CPU 端——driver 验证、command buffer 写入、context switch。把这些固定开销摊到 8000 个 quad 上,每个 quad 平均分摊到几纳秒,而不是每个独占 30μs。

**第二步,ring buffer(环形缓冲区)**。朴素方案:每帧 alloc 一个 GPU buffer 用完就 free。问题是 alloc/free GPU 内存**慢且碎片化**。Casey 改成预分配 N 个 GPU buffer(通常 N=3,对应 triple buffering),每帧轮流用一个。buffer 0 给 frame 0,buffer 1 给 frame 1,buffer 2 给 frame 2,frame 3 又回到 buffer 0。**永远不 alloc/free GPU buffer**。

为什么需要 N 个而不是 1 个?**GPU 异步执行**——你提交 draw call 后立刻返回,GPU 在后台跑。如果只有 1 个 buffer,你下一帧想写新数据,但 GPU 还在读旧数据——读写冲突,数据撕裂(看到一半新一半旧)。N=3 给 GPU "等的时间":frame N 用 buffer A,frame N+1 用 buffer B,frame N+2 用 buffer C,frame N+3 用 buffer A——此时 GPU 早处理完 frame A(3 帧 = 50ms,远超单帧 GPU 时间)。

**第三步,vertex format 压缩**。之前每个顶点 32 字节:`pos: [f32; 2]` (8 字节) + `uv: [f32; 2]` (8 字节) + `color: [f32; 4]` (16 字节)。Casey 注意到:**UI 的 uv 坐标永远在 [0, 1] 区间**——用 u16 (unorm,0..65535 映射到 0..1) 完全够精度,**省 4 字节**。**UI 的 color 是 RGBA,每个分量 0..255 够**——用 u8 (RGBA8 格式),省 12 字节。压缩后 16 字节/顶点,**节省 50%**。

每帧 8000 quad × 6 顶点 × 16 字节 = 768 KB,而不是之前的 1.5 MB。PCIe 带宽节省,frame time 降低。

视频里他强调一个关键洞察:"**UI 渲染的瓶颈不在 GPU,在 CPU 端准备数据的开销**。优化 CPU 端的内存布局,UI 帧率能涨 3-5 倍。"——这是 industrial UI 引擎(Dear ImGui、egui)的核心优化理念。

## 2 · 心智模型

### 2.1 类比:餐厅厨房处理订单

我打个比方。你经营一家餐厅,每秒来几个订单,厨房要做菜。

**朴素做法**(每订单单独处理):每订单一来,雇一个厨师(alloc),做完,解雇(free)。慢且累——**雇人/解雇比做菜还慢**。在 GPU 编程里,这对应"每 quad 一个 vertex buffer,draw 完就释放 GPU buffer"。GPU alloc/free 是 ms 级,慢得离谱。

**Batching**(批量处理):收集 100 个订单,**一个厨师一次做完**。雇人开销摊平到 100 单。在 GPU 编程里,这对应"把 1000 个 quad 的顶点打包到一个 buffer,一次 draw call 画完"。alloc 开销摊到 1000 quad,平均每个 quad 几纳秒。

**Ring buffer**(固定厨师轮班):**雇 3 个厨师固定轮班**,每厨师做一单。不用雇/解雇,每单立马上手。在 GPU 编程里,这对应"预分配 N 个 buffer,轮流用"。无 alloc 开销,且 N=3 给 GPU 异步执行留时间。

对应到 UI 渲染:

| 策略 | 朴素 | Batching | Ring buffer |
|---|---|---|---|
| GPU buffer 数 | 8000/帧 | 1/帧 | 3 永久 |
| Draw call 数 | 8000 | 1 | 1 |
| Alloc/free 开销 | 巨大 | 中(每帧 1 次) | 零 |
| Race condition 风险 | 低 | 高(单 buffer 改写) | 低(N buffer 隔离) |

最优解:**batching + ring buffer**——预分配 N 个 buffer,每帧把所有 quad 打包到 1 个 buffer,一次 draw call,下一帧用另一个 buffer。

### 2.2 Draw call batching:第一性原理

让我深入 batching 的原理。一个 draw call 是 CPU 给 GPU 的一条命令:"用这个 vertex buffer、这个 shader、这个纹理,画 N 个三角形"。CPU 端的开销来自:

1. **State validation**:driver 检查所有 state(pipeline、blend、depth、stencil)合法,~5μs。
2. **Command buffer write**:driver 把命令编码进 command buffer,~5μs。
3. **Cache flush**:某些 state 改变要 flush CPU cache,~5μs。
4. **Kernel transition**:用户态到内核态(syscall 提交 command buffer),~10μs。

加起来一个 draw call ~25μs CPU 时间。8000 个 draw call = 200ms。**帧时间 16ms 完全用完还有余**。

batching 的核心:**把多个 draw call 合并成 1 个**。条件是它们用同一个 shader、同一个 texture set、同一个 pipeline state。**UI quad 满足条件**——同 shader、同 atlas、同 blend mode。所以 8000 quad 可以合并成 1 个 draw call,画 8000×6=48000 个顶点。

未 batch:
```rust
for quad in ui_quads {
    let mut buf = alloc_vertex_buffer(...);  // 慢:GPU buffer alloc ~1ms
    fill(&mut buf, &quad.vertices);
    let _ = device.draw(&buf);  // draw call: 25μs
}
// 1000 次 alloc(1ms) + 1000 次 draw call(25μs) = 1ms + 25ms = 26ms
```

Batched:
```rust
let mut all_vertices = Vec::with_capacity(ui_quads.len() * 6);
for quad in &ui_quads {
    all_vertices.extend(&quad.vertices);  // 内存拷贝,~1ns/顶点
}
let buf = upload_to_gpu(&all_vertices);  // 一次 upload
device.draw(&buf);  // 一次 draw call
// 6000 顶点拷贝(6μs) + 1 次 upload(50μs) + 1 次 draw call(25μs) = 81μs
```

**单帧从 26ms 降到 81μs,提升 320 倍**。这就是 batching 的威力。

注意 batching 不是免费的。合并 vertex buffer 要拷贝数据(几纳秒/顶点,但累积起来不可忽略)。如果 quad 用不同 shader / texture,batching 失效——需要 draw call 之间切 state。**UI 用 texture atlas**(所有 UI 贴图拼到一张大纹理),避免 texture 切换,这是 batching 能 work 的前提。

### 2.3 Ring buffer:GPU 异步执行的必然产物

让我从 GPU 异步执行讲起,你会看到 ring buffer 是它的必然解。

GPU 编程的核心事实:**`vkCmdDraw` / `glDrawArrays` 是异步的**。CPU 调用立刻返回,GPU 在后台执行。CPU 继续跑下一行代码,GPU 在自己的 timeline 上排队 draw command。

异步的好处:**CPU 和 GPU 并行**。CPU 准备 frame N+1,GPU 画 frame N,100% 并行。理论帧时间 = max(CPU 时间, GPU 时间),不是和。

异步的坏处:**race condition**。CPU 写 buffer,GPU 同时读 buffer,看到一半新一半旧。

具体场景:
```rust
// Frame N
let verts_n = generate_ui_vertices();
write_to_gpu_buffer(&buffer, &verts_n);  // CPU 写
issue_draw_call(&buffer);                 // CPU 提交,GPU 异步开始

// CPU 立刻到 Frame N+1
let verts_n1 = generate_ui_vertices();
write_to_gpu_buffer(&buffer, &verts_n1);  // CPU 又写
// 但 GPU 还没开始读 verts_n!GPU 启动时读到的是 verts_n1,前面提交的 draw 看到错误数据
```

这是 **write-after-write hazard**。解决:**N 个 buffer,轮流用**。

```rust
let buffers = [buf0, buf1, buf2];  // N=3
let mut current = 0;

fn frame(&mut buffers, &mut current) {
    let buf = &buffers[*current];
    write_to_gpu_buffer(buf, &vertices);
    issue_draw_call(buf);
    *current = (*current + 1) % 3;  // 环形
}
```

为什么 N=3 而不是 2?考虑最坏情况:**某帧 GPU 卡顿,延迟 2 帧才执行**。如果 N=2,frame N+2 用 buffer 0——但 buffer 0 还在被 GPU 用(frame N 卡了)。N=3 给一帧 buffer,frame N+3 才回到 buffer 0,3 帧 = 50ms 足够 GPU 处理完。

NVIDIA 文档推荐 N=3 "绝对安全"。N=2 "大多数场景够用"。Casey 用 N=3。

注意:**ring buffer 不是 slot pool 的替代,而是补充**。slot pool 解决"shader 看见多少资源",ring buffer 解决"GPU 异步执行下 buffer 安全复用"。今天 Casey 在 UI 渲染用 ring buffer,在 light probe slot pool 用 `in_flight` 标记,本质都是同一个原理。

### 2.4 顶点格式压缩:从 f32 到 packed integer

UI 渲染顶点格式有大量冗余,可以压缩。让我详细分析。

**朴素 vertex(32 字节/顶点)**:

```rust
#[repr(C)]
struct Vertex {
    pos: [f32; 2],   // 8 字节——屏幕坐标,0..1920 / 0..1080
    uv: [f32; 2],    // 8 字节——纹理坐标,永远 0..1
    color: [f32; 4], // 16 字节——RGBA,每分量 0..1
}
// 总 32 字节
```

**冗余分析**:

- **uv 在 [0, 1] 区间**:f32 的精度(7 位有效数字)远超需求。u16 unorm(0..65535 映射 0..1)精度 = 1/65535 ≈ 1.5e-5,人眼分辨不出。**省 4 字节**。
- **color 每分量 0..1**:人眼对颜色精度不敏感,8 bit (0..255) 完全够。**省 12 字节**。
- **pos 是屏幕坐标**:f32 必要(支持 4K / 8K 分辨率)。**保持 8 字节**。

**压缩后 vertex(16 字节/顶点)**:

```rust
#[repr(C)]
struct VertexPacked {
    pos: [f32; 2],       // 8 字节
    uv: [u16; 2],        // 4 字节(unorm 0..1)
    color: [u8; 4],      // 4 字节(RGBA8)
}
// 总 16 字节/顶点,节省 50%
```

**shader 端解码**:GPU 硬件支持 vertex attribute 格式自动转换。声明 `VK_FORMAT_R16G16_UNORM` 或 `GL_UNSIGNED_SHORT` 配合 `GL_TRUE` normalized,GPU 在 vertex fetch 阶段自动转 f32,shader 不用做。

```glsl
// GLSL vertex shader
layout(location = 0) in vec2 pos;        // 自动从 f32 读
layout(location = 1) in vec2 uv;          // 自动从 u16 unorm 转 f32
layout(location = 2) in vec4 color;       // 自动从 u8 RGBA 转 f32

void main() {
    gl_Position = vec4(pos, 0.0, 1.0);
    v_uv = uv;       // 已是 f32
    v_color = color; // 已是 f32
}
```

**带宽对比**:

| 顶点格式 | 字节/顶点 | 8000 quad × 6 顶点 | PCIe 传输(每帧) |
|---|---|---|---|
| 朴素 f32 | 32 | 1.5 MB | 1.5 MB |
| Packed | 16 | 0.75 MB | 0.75 MB |

每帧省 0.75 MB。PCIe 3.0 带宽 ~12 GB/s,1 MB = 80μs。每帧省 60μs CPU→GPU 传输时间。看似小,但累积到 60 fps,每秒省 3.6ms——**够让某些场景从 60 FPS 到 75 FPS**。

**更激进的压缩**:`pos` 也能压缩——UI quad 通常用整数像素坐标,u16 (0..65535) 覆盖到 64K 像素(远超 8K),精度 1 像素够。这样 12 字节/顶点,再省 25%。但 Casey 这天保守地只压 uv 和 color,pos 保持 f32。

### 2.5 把所有概念整合:完整 UI 渲染管线

让我把 batching、ring buffer、顶点压缩合在一起,给出完整管线。

```
每帧 UI 渲染:
  1. Immediate-mode widget 函数调用
     ├── button("OK", x, y) → push_quad(...)
     ├── text("Hello", x, y) → push_quad(...) × N glyphs
     └── ...
     累积所有 quad 到 Vec<UiQuad>
  2. 分配 ring buffer slot(预分配 N 个,轮流用)
  3. 把 Vec<UiQuad> 转成 Vec<UiVertex>(紧凑格式)
     └── 每个 quad → 6 个顶点(2 三角形)
  4. upload_to_gpu(ring_buf[current], &vertices)
     └── PCIe 传输,~50μs
  5. issue draw call
     └── shader 读取 ring_buf[current],画所有顶点
  6. current = (current + 1) % N  // 下一帧用另一个 buffer
```

整个流程 CPU 端几百微秒,GPU 端几毫秒,完全在 16ms 帧预算内。

## 3 · 四域深入

### 3.1 · 游戏编程视角

UI 渲染的工业做法:

- **Dear ImGui**:C++,immediate-mode,默认 1 个 draw call 跑完所有 UI
- **Nuklear**:Rust 移植,同样 immediate-mode
- **egui**:Rust 原生 immediate-mode,batching 好

文字渲染的特殊处理:**SDF(Signed Distance Field)字体**——把 glyph 存成 SDF texture,放大不糊。Valve 在 Team Fortress 2 推广。

### 3.2 · 图形学视角

UI 渲染的特点 vs 3D 渲染:

| 维度 | 3D 渲染 | UI 渲染 |
|---|---|---|
| 顶点数 | 高(几 M) | 中(几 K-M) |
| 顶点大小 | 大(几十字节) | 中(16-32 字节) |

| Texture 切换 | 低 | 高(每 UI panel 不同) |

UI 高 overdraw 是性能杀手——透明背景的 panel 上再叠 panel,fragment shader 跑 N 次。优化:把同层的 panel 合并成一个 quad。

### 3.3 · Linux 系统编程视角

"Ring buffer" 模式在系统编程常见:

- **Linux kernel ring buffer**:`dmesg` 看的就是
- **TCP socket buffer**:环形队列
- **Lock-free MPMC queue**:生产者-消费者,常 ring buffer
- **GPU command queue**:驱动提交给 GPU 的命令是 ring

`crossbeam-queue` 提供工业级 ring buffer:

```rust
use crossbeam_queue::ArrayQueue;
let q = ArrayQueue::new(100);
q.push(1).unwrap();
let v = q.pop().unwrap();
```

### 3.4 · Rust 生态视角

Rust 写 UI 渲染:

```rust
use wgpu::util::DeviceExt;

let vertex_buffer = device.create_buffer_init(&wgpu::util::BufferInitDescriptor {
    label: Some("UI Vertices"),
    contents: bytemuck::cast_slice(&vertices),
    usage: wgpu::BufferUsage::VERTEX | wgpu::BufferUsage::COPY_DST,
});
```

`bytemuck` 是零拷贝 cast——把 Rust struct 当字节送 GPU。

Ring buffer 简单实现:

```rust
struct UiRingBuffer {
    vertex_buffers: Vec<wgpu::Buffer>,
    current: usize,
}

impl UiRingBuffer {
    fn next_buffer(&mut self) -> &wgpu::Buffer {
        let buf = &self.vertex_buffers[self.current];
        self.current = (self.current + 1) % self.vertex_buffers.len();
        buf
    }
}
```

### Lv1 · 概念辨析

**题**:Ring buffer 为什么需要 N(N >= 2)个 buffer?用 1 个不行吗?

**参考解答**:GPU 异步执行——你提交 draw call 后立刻返回,GPU 后台跑。如果只有 1 个 buffer,你下一帧想写新数据,但 GPU 还在读旧数据——读写冲突,数据撕裂(看到一半新一半旧)。N=2 时:frame 0 用 buffer A,GPU 处理;frame 1 用 buffer B,GPU 处理 A;frame 2 又用 buffer A——此时 GPU 应该处理完 A 了(2 帧 = 33ms,GPU 一帧 16ms,够)。所以 N >= 2 给 GPU 处理时间。NV 推荐 3 更安全(避免极端 slow frame)。

### Lv2 · 动手实践

**题**:实现 batched UI quad 顶点生成,验证 draw call 数减少。

要求:
- 模拟 1000 个 quad,每个 6 个顶点
- 朴素版:每 quad 一个 vertex buffer,一次 draw
- Batched 版:所有 quad 一个 vertex buffer,一次 draw
- 打印两种的 vertex buffer 数和 draw call 数

**参考解答**:

```rust
#[derive(Clone, Copy, Debug)]
struct Vertex {
    pos: [f32; 2],
    uv: [u16; 2],
    color: [u8; 4],
}

fn naive_render(quads: &[[Vertex; 6]]) -> (usize, usize) {
    let mut buf_count = 0;
    let mut draw_count = 0;
    for _quad in quads {
        let _buf = vec![0u8; 6 * 16];  // 假装 alloc GPU buffer
        buf_count += 1;
        draw_count += 1;
    }
    (buf_count, draw_count)
}

fn batched_render(quads: &[[Vertex; 6]]) -> (usize, usize) {
    let mut all = Vec::with_capacity(quads.len() * 6);
    for quad in quads {
        all.extend(quad.iter());
    }
    let _buf = bytemuck::cast_slice(&all).to_vec();  // 假装 upload
    (1, 1)  // 1 buffer, 1 draw call
}

fn main() {
    let mut quads = Vec::new();
    for _ in 0..1000 {
        let v = Vertex { pos: [0.0; 2], uv: [0; 2], color: [255; 4] };
        quads.push([v; 6]);
    }

    let (n_buf, n_draw) = naive_render(&quads);
    println!("Naive: {} buffers, {} draws", n_buf, n_draw);

    let (n_buf, n_draw) = batched_render(&quads);
    println!("Batched: {} buffers, {} draws", n_buf, n_draw);
}
```

完整 ring buffer + batching:

```rust
// 紧凑顶点格式
#[repr(C)]
#[derive(Clone, Copy, Debug, bytemuck::Pod, bytemuck::Zeroable)]
struct UiVertex {
    pos: [f32; 2],       // 8 字节
    uv: [u16; 2],        // 4 字节(unorm)
    color: [u8; 4],      // 4 字节(RGBA8)
}  // 16 字节/顶点

// 模拟 GPU buffer(实际是 wgpu::Buffer)
struct GpuBuffer {
    size: usize,
    in_use: bool,
}

impl GpuBuffer {
    fn new(size: usize) -> Self { GpuBuffer { size, in_use: false } }
}

// Ring buffer:N 个 GPU buffer 轮流用
struct UiRingBuffer {
    buffers: Vec<GpuBuffer>,
    current: usize,
}

impl UiRingBuffer {
    fn new(frame_latency: usize, buffer_size: usize) -> Self {
        let buffers = (0..frame_latency)
            .map(|_| GpuBuffer::new(buffer_size))
            .collect();
        UiRingBuffer { buffers, current: 0 }
    }

    fn next_buffer(&mut self) -> &mut GpuBuffer {
        let buf = &mut self.buffers[self.current];
        self.current = (self.current + 1) % self.buffers.len();
        buf.in_use = true;
        buf
    }
}

// 一个 UI quad:4 个顶点(或 6,如果有重复)
#[derive(Clone, Copy)]
struct UiQuad {
    x: f32, y: f32, w: f32, h: f32,  // 屏幕坐标
    color: [u8; 4],
}

fn quad_to_vertices(q: UiQuad) -> [UiVertex; 6] {
    let x = q.x; let y = q.y;
    let x2 = q.x + q.w; let y2 = q.y + q.h;
    [
        UiVertex { pos: [x, y],  uv: [0, 0], color: q.color },
        UiVertex { pos: [x2, y], uv: [65535, 0], color: q.color },
        UiVertex { pos: [x2, y2], uv: [65535, 65535], color: q.color },
        UiVertex { pos: [x, y],  uv: [0, 0], color: q.color },
        UiVertex { pos: [x2, y2], uv: [65535, 65535], color: q.color },
        UiVertex { pos: [x, y2], uv: [0, 65535], color: q.color },
    ]
}

// 一帧 UI 渲染
fn render_frame(ring: &mut UiRingBuffer, quads: &[UiQuad]) {
    let mut all_vertices = Vec::with_capacity(quads.len() * 6);
    for q in quads {
        all_vertices.extend(&quad_to_vertices(*q));
    }

    // 拿一个 ring buffer slot
    let buf = ring.next_buffer();

    // 假装 upload(bytemuck::cast_slice 转 bytes,然后 map buffer 写入)
    let _bytes = bytemuck::cast_slice(&all_vertices);
    // 实际 wgpu: queue.write_buffer(buf, 0, &_bytes);

    println!(
        "Rendered {} quads ({} vertices) into buffer slot, size {} bytes",
        quads.len(),
        all_vertices.len(),
        _bytes.len(),
    );

    // 假装一次 draw call
    // render_pass.draw(0..all_vertices.len() as u32, 0..1);
}

fn main() {
    // 3 个 ring buffer slot,每个 1 MB
    let mut ring = UiRingBuffer::new(3, 1024 * 1024);

    // 模拟 5 帧,每帧 500 个 quad
    for frame in 0..5 {
        let quads: Vec<UiQuad> = (0..500).map(|i| UiQuad {
            x: i as f32, y: i as f32, w: 50.0, h: 50.0,
            color: [255, 255, 255, 255],
        }).collect();
        print!("Frame {}: ", frame);
        render_frame(&mut ring, &quads);
    }
}
```
