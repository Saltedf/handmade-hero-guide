
# Day 526 · 单缓冲音频流

> Day 524 你把 WAV 加载到内存然后播放——一个小音效(几百 KB)这样没问题,但一段 BGM(50 MB)加载到内存就太奢侈。Day 526 Casey 引入"流式播放":**只有一个音频缓冲区,一边播放一边从磁盘续杯**。这是音频编程的核心难点——你必须避免"缓冲区欠载(underrun)"(读盘太慢导致播放卡顿),又要避免"缓冲区溢出"(读太多撑爆内存)。Casey 用最简单的设计:单缓冲 + 环形写入,这是一个非常聪明的折衷。

## 0 · 为什么要有这一天

把 5 分钟的 CD 音质音乐加载到内存:

- 44100 Hz × 2 声道 × 2 字节(i16)× 300 秒 = **52 MB**

50 MB 不算大,但游戏可能有 10 首音乐,那就是 500 MB——占了玩家内存的一大块。手机游戏更敏感,内存只有 1-2 GB,500 MB 给音乐不可接受。

解决方案:**流式播放**。音频数据留在磁盘上,只在需要时读一小段到内存。播放指针在缓冲区里循环走,每当快到缓冲区末尾,后台线程从磁盘读下一段,填充缓冲区头部。这样不管音乐多长,内存里始终只有 1-2 秒的数据(几百 KB)。

但流式播放有挑战:**读盘速度必须快于播放速度**。CD 音质每秒消耗 176 KB,如果你的硬盘或解码器慢于一秒 176 KB,就 underrun——播放器找不到下一段数据,发出刺耳的杂音或卡顿。

Casey 这一天的设计是**单缓冲 + 环形写入**。单缓冲意味着只有一块内存区域(比如 1 秒钟的数据 = 176 KB),后台线程在这个区域里循环写入,播放器循环读出。这种设计的优点是**实现简单**(只有一个指针要管理),缺点是**容错差**(任何一次读盘超时都会立刻听到杂音)。

工业级方案是**双缓冲(double buffering)**或**多缓冲**:两块或更多缓冲区轮流用,一块在播放,另一块在后台预读,即使读盘偶尔慢也有备份。Casey 选单缓冲是为了教学清晰——单缓冲已经够用,且更适合理解本质。

让我把 underrun 这个核心问题讲清楚。音频硬件的工作方式:它有一个内部的 DAC(Digital-to-Analog Converter,数模转换器),每秒 44100 次从硬件缓冲读一个采样,转成模拟电压送扬声器。硬件缓冲通常很小(几毫秒数据 = 几 KB)。如果硬件缓冲空了,DAC 找不到下一个采样,就会**输出上一次的值或 0**,造成"嗡嗡声"或"咔哒声"。

所以你的软件必须**总是让硬件缓冲有数据**。这要求:(1)读盘速度 > 播放速度(够快补得上);(2)调度延迟 < 缓冲时长(够及时被调度)。两者任何一个不满足就 underrun。

举具体数字。假设缓冲 100 ms(17600 字节)。如果读盘速度是 100 MB/s(NVMe SSD),100 ms 数据只需 1.76 ms 读——余量 98 ms。但如果调度延迟偶尔达到 50 ms(系统繁忙),100 ms 缓冲还撑得住。如果缓冲只有 10 ms,50 ms 调度延迟就 underrun。**缓冲大小是"延迟 vs 容错"的权衡**:大缓冲延迟高(听到声音滞后于触发),小缓冲容错差(易 underrun)。游戏 SFX(枪声)需要低延迟(50 ms 内),BGM 容忍高延迟(几百 ms 无感)。

完成这一天之后,你具备:

- 理解音频流的核心矛盾:内存小 vs 读盘速度
- 能用 Rust 实现环形缓冲(ring buffer)
- 理解为什么音频线程必须是实时线程(real-time thread)
- 知道如何调试 underrun 问题(用 latency 日志、PPM meter)

## 1 · Casey 今天做了什么

Casey 这一天的动作可以拆成四步:

第一步,他**问题诊断**:把 50 MB WAV 一次性加载,内存占用暴增,启动延迟变长(读盘要几秒)。这是不可接受的。

第二步,他**设计单缓冲**:`SoundBuffer` 结构持有 1-2 秒的 PCM 数据,以及一个"读取位置"(read cursor,播放器读到哪了)和"写入位置"(write cursor,后台线程写到哪了)。

第三步,他**实现后台线程**:这个线程循环检查"写入位置 - 读取位置 < 缓冲大小",如果是,从磁盘读一段 PCM 数据填充到 write cursor 位置,write cursor 推进。这是经典的生产者-消费者模式。

第四步,他**接入音频输出回调**:Win32 DirectSound 用一个 callback(回调函数)来要 PCM 数据。Casey 在 callback 里从 read cursor 拷贝 N 个采样到 DirectSound 的内部缓冲,read cursor 推进。如果 read cursor 追上了 write cursor(没有新数据),就播放静音——这就是 underrun。

视频里他强调:音频线程必须是**实时线程**(priority = THREAD_PRIORITY_TIME_CRITICAL),否则 OS 调度可能让线程睡眠几十毫秒,直接 underrun。

## 2 · 心智模型

### 类比:DJ 的黑胶唱片

想象一个 DJ 在用黑胶唱片播放音乐。唱片是磁盘,唱针是播放指针。DJ 一边播一边从架子上换唱片——这就是流式播放的本质。

但 DJ 的难点是:**换唱片时音乐不能停**。如果 DJ 慢了,音乐断了一拍,听众立刻察觉。所以 DJ 要预判——音乐还剩 30 秒结束时,就要去拿下一张唱片。

单缓冲相当于"唱针只在一个固定大小的环上转,DJ 必须在唱针转一圈的时间内换上新数据"。如果 DJ 慢了,唱针读到的就是旧数据(杂音)。

### 严谨展开:环形缓冲(ring buffer)

环形缓冲是一块固定大小的内存,读写指针在 [0, size) 区间循环。两个指针:

- `write_pos`(写入位置):后台线程写到这里
- `read_pos`(读取位置):播放器从这里读

不变量(invariant):**write_pos 永远领先 read_pos**(在环形意义下),即"已写但未读"的数据量 ≥ 0。

环形布局:

```
buffer[N]:
[已读 | 待读 | 未写 | 已读]
       ^          ^
       read_pos   write_pos
```

写入:`buffer[write_pos] = sample; write_pos = (write_pos + 1) % N`
读取:`sample = buffer[read_pos]; read_pos = (read_pos + 1) % N`

**关键问题**:write_pos 不能"绕一圈追上"read_pos。如果 write_pos + 1 == read_pos(环形),说明缓冲满了,必须停。同理 read_pos 不能追上 write_pos——缓冲空。

更严格的表达:在环形缓冲里,可写空间 = N - (write_pos - read_pos) mod N - 1。这个 "-1" 是因为如果不留一个空位,无法区分"满"和"空"——两者都满足 write_pos == read_pos。

### 单缓冲 vs 双缓冲

**单缓冲**:一块环形缓冲区。

```
[ buffer A ]
   ↑↑
   读写都在这里
```

读和写在同一块内存上交替,需要锁(或原子操作)同步。优点:简单。缺点:对读盘延迟敏感——读盘变慢,write_pos 不前进,read_pos 立刻追上,underrun。

**双缓冲**:两块缓冲区,轮流用。

```
[ buffer 1 (前台,正在播放) ] [ buffer 2 (后台,正在预读) ]
```

后台线程在 buffer 2 里预读,等 buffer 1 播放完,交换——buffer 2 变前台继续播,buffer 1 变后台继续预读。这种"swap"交换是 O(1)。

双缓冲的优点:读盘延迟隐藏——即使某次读盘慢了一倍,只要前一个 buffer 还在播,听众听不出来。缺点:实现复杂(状态机管理交换)。

Casey 选单缓冲,因为 HH 的音频流是简单场景,且教学上单缓冲更容易理解。

### 为什么音频线程是实时的

CPU 调度器分时给所有线程。普通线程时间片是 10-20 ms(取决于 OS)。如果音频线程被换出 20 ms,缓冲区里的数据(假设 30 ms 的 PCM)在 30 ms 内耗尽——20 ms 后切换回来,但 read_pos 已经追上 write_pos,underrun。

实时线程(priority 高)几乎不被换出。但代价是占用 CPU 多(不让别人用)。

Linux 上设置实时优先级:`pthread_setschedparam` 用 `SCHED_FIFO`。Rust 里用 `libc` crate 或专门的 `realtime` crate。

但 Casey 在 Windows 上用 `SetThreadPriority(THREAD_PRIORITY_TIME_CRITICAL)`,这是 Windows 特有 API。

### 实时编程的"禁忌清单"

实时音频线程有严格的禁忌——下面这些操作**绝对不能在音频回调里做**:

1. **不能分配内存**(`malloc`、`new`)——分配器可能加锁,锁可能阻塞几十毫秒
2. **不能 I/O**(文件、网络、控制台)——I/O 是阻塞操作
3. **不能锁互斥量**(`Mutex::lock`)——其他线程持有锁时你要等
4. **不能系统调用**(`println!`、`gettimeofday`)——大部分系统调用会切换到内核态
5. **不能复杂算法**(FFT、压缩)——计算时间不可预测
6. **不能 log**——log 库通常有锁

音频回调里只能做:**纯计算 + 访问预分配内存**。Casey 在视频里反复强调这一点——他的 DirectSound 回调只做"从环形缓冲拷贝 PCM 到硬件缓冲"这一件事,没有任何 I/O 或锁。

工业级音频中间件(Wwise、FMOD)的"音频线程"和"渲染线程"、"IO 线程"严格分离:

```
IO 线程       →  从磁盘读 PCM,放进环形缓冲(可以慢,可以阻塞)
音频线程      →  从环形缓冲读 PCM,送 DAC(必须实时,不能阻塞)
渲染线程      →  画 visualizer、Spectrum 等(可以丢帧)
主线程        →  处理用户输入、游戏逻辑(可以慢)
```

线程间通过**无锁队列**(lock-free queue)通信。Rust 生态有 `crossbeam-queue`、`rtrb`(real-time ring buffer)专门为这种场景设计。

Rust 的所有权系统在这里特别有用——`Send + Sync` 标记让你知道哪些数据能跨线程传递,编译器拦截数据竞争。这是 Rust 比传统 C/C++ 音频代码安全的核心原因。

### 3.1 · 游戏编程视角

游戏音频流的工业级方案:

- **Wwise / FMOD**:商业中间件,内置流管理
- **Unity**:AudioSource 组件 + streaming clip
- **Unreal**:USoundWave with Streaming flag

这些方案的共同点:开发者不直接管理缓冲,而是给音频资产打"streaming"标签,引擎自动处理。Casey 选择手写,是为了让你看到内部机制。

游戏音频的另一个考虑:**多语言支持**。同样一段过场动画,英文和中文的语音时长不同。流式播放可以让"开始播放时"不阻塞(不需要全部加载),适合本地化。

### 3.1.1 · " Banking":音频资产打包

工业级游戏不用单文件 WAV,而是把多个音频打包成 **bank**(声音库)。一个 bank 可能包含:
- 一个区域的全部音效(脚步、枪声、对话)
- 一个角色的全部语音
- 一段过场动画的全部音轨

游戏加载 bank 时,所有这些音频同时进内存。bank 切换(玩家进入新区域)时,卸载旧 bank,加载新 bank。这种粒度比"每文件流式"更高效,因为:

1. **批量加载比单文件快**:一次 I/O 读 50 MB 比读 500 个 100KB 文件快
2. **内存复用**:同一 bank 的音频共享缓冲,避免重复加载
3. **依赖管理**:角色对话依赖角色模型,放同一 bank 保证原子加载

Wwise/FMOD 的 bank 系统是这个领域的工业标准。Casey 的 HHA 格式其实就是简化版的 bank——一个 .hha 文件包含多个资产。

### 3.1.2 · " Voice Limiting":同时播放上限

如果你的游戏里 100 个 NPC 同时中枪,每个 NPC 触发"惨叫"音效,你想听见几个?显然不是 100 个——会变成噪音,且混音器过载。

工业级引擎有 **voice limit(声道限制)**:同时最多 N 个声音(N 通常 32-64)。超出时优先级低的(远的、不重要的)被静音。这种"voice stealing(声道偷取)"是音频引擎的核心算法。

Casey 在 HH 简化了——他不限制 voice,直接全播放。生产游戏必须做 voice limiting,否则大规模战斗场景会爆。Rust 实现示例:

```rust
struct VoiceManager {
    active_voices: Vec<Option<Voice>>,
    max_voices: usize,
}

impl VoiceManager {
    fn play(&mut self, new_voice: Voice) {
        if self.active_voices.iter().filter(|v| v.is_some()).count() >= self.max_voices {
            // 找最低优先级的 voice 偷取
            let victim_idx = self.active_voices.iter()
                .enumerate()
                .filter_map(|(i, v)| v.as_ref().map(|v| (i, v.priority)))
                .min_by_key(|&(_, p)| p)
                .map(|(i, _)| i);
            if let Some(idx) = victim_idx {
                self.active_voices[idx] = None;  // 杀掉低优先级的
            } else {
                return;  // 所有 voice 都是高优先级,放弃新声音
            }
        }
        // 找空槽插入
        let slot = self.active_voices.iter().position(|v| v.is_none());
        if let Some(idx) = slot {
            self.active_voices[idx] = Some(new_voice);
        }
    }
}
```

### 3.2 · 图形学视角

GPU 也有类似的概念:**纹理流(texture streaming)**。一个 4K 纹理是 16 MB,GPU 显存可能装不下所有纹理。引擎只加载玩家附近物体的纹理,远处的纹理低分辨率版(mipmap),需要时才加载高分辨率。

虚幻引擎 5 的 Nanite 系统把这个做到极致——几何体也是流式,几百亿三角形不需要全装内存。

纹理流和音频流的数学结构完全一样:环形缓冲 + 优先级队列(哪个对象先用,先加载)。

### 3.3 · Linux 系统编程视角

Linux 上音频流的标准栈:

- **ALSA**:`snd_pcm_hw_params` 设置缓冲大小,`snd_pcm_writei` 提交 PCM
- **PulseAudio**:异步 API,客户端发 PCM 给服务器,服务器混音
- **JACK**:专业音频,周期性回调(callback),每个周期提供固定帧数
- **PipeWire**:统一 PulseAudio + JACK

JACK 模式和 Casey 的 DirectSound 模式最像——都是 callback 风格。Linux 上典型的 JACK 周期是 64-256 帧,buffer 大小 = 周期 × 帧数 × channels × bytes_per_sample。

```bash
# 查看 ALSA 缓冲配置
cat /proc/asound/card0/pcm0p/sub0/hw_params
# access: MMAP_INTERLEAVED
# format: S16_LE
# subformat: STANDARD
# channels: 2
# rate: 44100 (44100/1)
# period_size: 1024
# buffer_size: 4096

# 这里 buffer_size = 4096 帧 = 4096/44100 = 93 ms 缓冲
```

### 3.4 · Rust 生态视角

Rust 的音频流库 `cpal`:

```rust
use cpal::traits::{DeviceTrait, HostTrait, StreamTrait};
use cpal::{Data, Sample, SampleFormat};

let host = cpal::default_host();
let device = host.default_output_device().unwrap();
let config = device.default_output_config().unwrap();

let stream = match config.sample_format() {
    SampleFormat::F32 => device.build_output_stream(
        &config.into(),
        |data: &mut [f32], _: &cpal::OutputCallbackInfo| {
            // 在 callback 里:从环形缓冲读 PCM,写入 data
            write_samples(data);
        },
        |err| eprintln!("audio error: {}", err),
        None,
    ),
    // 其他格式...
};
stream.play().unwrap();
```

`cpal` 的 callback 风格和 Casey 的 DirectSound 一样——音频驱动要数据时调你的函数,你必须在 callback 返回前填满 data。

环形缓冲的 Rust crate:`heapless::spsc::Queue`(无 heap 分配,适合嵌入式)、`ringbuf`(通用)、`crossbeam-queue`(多生产者多消费者)。

注意:**音频 callback 里绝对不能做阻塞操作**(锁、磁盘 IO、内存分配)。否则 callback 超时,underrun。Casey 强调这一点——Rust 翻译版要严格遵守。

## 5 · 对照与变奏

音频流和视频流的对比:

- 视频:每帧 1/60 秒,数据量比音频小(可能),但解码复杂(H.264 解码)
- 音频:每帧 1/44100 秒,但播放连续(无"帧"概念),解码简单(PCM)或中等(Ogg)
- 视频流缓冲:几十到几百毫秒,音频流缓冲:几百毫秒到几秒

工业级视频流(YouTube、Netflix)的延迟目标是几秒(可以缓冲几秒)。游戏音频流的延迟目标必须 < 100 ms,否则玩家感觉到操作和声音不同步。

游戏里的混合方案:小音效(枪声、UI 点击)一次性加载到内存,大音频(BGM、过场配音)流式播放。Casey 在 HH 里也是这样混用——只是 Day 526 专门讲流式那部分。

### Lv1 · 概念辨析(读懂)

**题**:Casey 用单缓冲,但有人说"双缓冲更优"。Casey 为什么不直接用双缓冲?

**参考解答**:Casey 选单缓冲有两个原因。第一,**教学清晰**——单缓冲暴露所有细节(读写指针、同步、underrun 检测),双缓冲把这些藏起来,初学者看不到核心。第二,**HH 场景简单**——Casey 的音频流是 BGM,本地文件,读盘延迟稳定(几十毫秒),单缓冲够用。双缓冲在工业级才有明显优势——网络流(YouTube)、压缩格式(Ogg 需要异步解码)、多语言切换。教学项目选单缓冲是合理的取舍。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:用 Rust 实现一个简单的环形缓冲区,要求:(1)固定大小 `N`;(2)`push(item)` 写入;(3)`pop() -> Option<item>` 读出;(4)满了 push 返回 Err,空了 pop 返回 None。注意用 `AtomicUsize` 让读写可以多线程并发。

**参考解答**:

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::cell::UnsafeCell;

const N: usize = 1024;

struct RingBuffer<T> {
    buffer: UnsafeCell<[T; N]>,  // UnsafeCell 让原子操作可变
    write_pos: AtomicUsize,
    read_pos: AtomicUsize,
}

unsafe impl<T: Send> Sync for RingBuffer<T> {}  // 标记线程安全(我们保证原子访问)

impl<T: Default + Copy> RingBuffer<T> {
    fn new() -> Self {
        Self {
            buffer: UnsafeCell::new([T::default(); N]),
            write_pos: AtomicUsize::new(0),
            read_pos: AtomicUsize::new(0),
        }
    }
    
    fn push(&self, item: T) -> Result<(), T> {
        let write = self.write_pos.load(Ordering::Relaxed);
        let read = self.read_pos.load(Ordering::Acquire);
        
        // 计算可写空间:N - (write - read) - 1
        // (mod N,因为环形)
        let available = (N + read - write) % N;
        // 留 1 个空位避免满空混淆
        if available <= 1 {
            return Err(item);  // 缓冲满了
        }
        
        unsafe {
            (*self.buffer.get())[write] = item;
        }
        // Acquire-Release 配对,确保写入对其他线程可见
        self.write_pos.store((write + 1) % N, Ordering::Release);
        Ok(())
    }
    
    fn pop(&self) -> Option<T> {
        let read = self.read_pos.load(Ordering::Relaxed);
        let write = self.write_pos.load(Ordering::Acquire);
        
        if read == write {
            return None;  // 空
        }
        
        let item = unsafe { (*self.buffer.get())[read] };
        self.read_pos.store((read + 1) % N, Ordering::Release);
        Some(item)
    }
}

fn main() {
    let rb = RingBuffer::<i32>::new();
    for i in 0..5 {
        rb.push(i).unwrap();
    }
    for _ in 0..5 {
        println!("{:?}", rb.pop());
    }
    println!("{:?}", rb.pop());  // None
}
```

为什么这么写:`UnsafeCell` + `unsafe impl Sync` 是 Rust 表达"我自己保证原子访问"的方式——绕过编译器的 aliasing 检查,自己负责线程安全。这是写 lock-free 数据结构的标准模式。`Ordering::Acquire/Release` 保证内存可见性——没有它,写线程的写入可能永远读不到。

## 8 · Rust / Arch 落地代码

```rust
// 完整的单缓冲音频流实现(简化版,不接 cpal,只演示逻辑)

use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;
use std::time::Duration;

const BUFFER_FRAMES: usize = 44100;  // 1 秒缓冲(44100 Hz)
const CHANNELS: usize = 2;

struct AudioStream {
    buffer: Vec<std::sync::atomic::AtomicI16>,  // 每个 sample 一个原子 i16
    write_frame: AtomicUsize,  // 写到第几帧
    read_frame: AtomicUsize,   // 读到第几帧
    total_frames: usize,       // 总帧数(从文件)
    loaded_frames: AtomicUsize,  // 已加载帧数
}

impl AudioStream {
    fn new(total_frames: usize) -> Arc<Self> {
        let mut buffer = Vec::with_capacity(BUFFER_FRAMES * CHANNELS);
        for _ in 0..(BUFFER_FRAMES * CHANNELS) {
            buffer.push(std::sync::atomic::AtomicI16::new(0));
        }
        Arc::new(Self {
            buffer,
            write_frame: AtomicUsize::new(0),
            read_frame: AtomicUsize::new(0),
            total_frames,
            loaded_frames: AtomicUsize::new(0),
        })
    }
    
    /// 后台线程:从磁盘读 PCM,填充缓冲
    fn producer(self: Arc<Self>) {
        let mut next_frame_to_load = 0;
        loop {
            let write = self.write_frame.load(Ordering::Relaxed);
            let read = self.read_frame.load(Ordering::Relaxed);
            
            // 计算可写空间(留 1 个 frame 余量)
            let available = (BUFFER_FRAMES + read - write) % BUFFER_FRAMES;
            if available <= 1 || next_frame_to_load >= self.total_frames {
                // 缓冲满,或全部加载完
                if next_frame_to_load >= self.total_frames {
                    break;  // 完成
                }
                thread::sleep(Duration::from_millis(5));
                continue;
            }
            
            // 从"磁盘"读一帧(这里用合成数据模拟)
            let left = (next_frame_to_load as f32 * 0.1).sin() * 1000.0;
            let right = (next_frame_to_load as f32 * 0.1).sin() * 1000.0;
            self.buffer[write * CHANNELS].store(left as i16, Ordering::Relaxed);
            self.buffer[write * CHANNELS + 1].store(right as i16, Ordering::Relaxed);
            
            self.write_frame.store((write + 1) % BUFFER_FRAMES, Ordering::Release);
            next_frame_to_load += 1;
            self.loaded_frames.fetch_add(1, Ordering::Relaxed);
        }
    }
    
    /// 播放器:从缓冲读一帧
    fn read_frame(&self) -> Option<(i16, i16)> {
        let read = self.read_frame.load(Ordering::Relaxed);
        let write = self.write_frame.load(Ordering::Acquire);
        
        if read == write {
            return None;  // underrun!
        }
        
        let left = self.buffer[read * CHANNELS].load(Ordering::Relaxed);
        let right = self.buffer[read * CHANNELS + 1].load(Ordering::Relaxed);
        self.read_frame.store((read + 1) % BUFFER_FRAMES, Ordering::Release);
        Some((left, right))
    }
}

fn main() {
    let total = 5 * 44100;  // 5 秒音频
    let stream = AudioStream::new(total);
    
    // 启动 producer 线程
    let producer_stream = stream.clone();
    let producer = thread::spawn(move || {
        producer_stream.producer();
    });
    
    // 主线程扮演 consumer(模拟播放)
    let mut played = 0;
    let mut underruns = 0;
    while played < total {
        match stream.read_frame() {
            Some((_l, _r)) => played += 1,
            None => {
                underruns += 1;
                thread::sleep(Duration::from_millis(1));
            }
        }
    }
    
    producer.join().unwrap();
    println!("播放 {} 帧, {} 次 underrun", played, underruns);
}
```

出错怎么办:

- **underrun 频繁**:缓冲太小,增大 BUFFER_FRAMES。或 producer 太慢,优化读盘。
- **`panic: index out of bounds`**:环形指针 mod 错了。检查 `(pos + 1) % N`。
- **数据竞争**:确保所有共享数据用原子操作或锁。Rust 编译器抓数据竞争,但 `unsafe` 块绕过。
- **`thread panicked while panicking`**:panic 在 lock 持有期间,后续操作再 panic。never panic in callbacks!
