# Day 498 · 完成资产系统清理

> Day 497 Casey 把 ID 类型统一了,但留了"加载入口"还是分发的尾巴。今天他收尾——把 4 种资产的"加载过程"也彻底抽象化,让"加新资产类型"变成只改一个 enum + 一个 match 分支。这是把"重构"做到底的样子。

## 0 · 为什么要有这一天

昨天的统一 ID 解决了"参数",但还有一个更深的问题:**加载流程本身仍然重复**。每种资产(bitmap、sound、font、model)的加载都包含 5 个步骤:

1. 算出文件路径
2. 读字节
3. 解压(如果有压缩)
4. 解析格式
5. 转 GPU/CPU 资源

这 5 步在 4 种资产里 80% 相同,但每个 `load_xxx_inner` 都把这 5 步重新写一遍。Casey 今天把"5 步流程"抽象成 trait,**每种资产类型只填自己的"差异点"**,公共部分写一次。

这种抽象叫"**模板方法模式(template method)**":父类/通用函数定义流程骨架,子类/具体实现填空。Rust 里用 trait + 默认方法实现。

为什么这事重要?因为你做编辑器时(接下来的 Day 499+),会反复"加一种新资产"——加 sprite、加 tilemap、加音频片段。如果加载流程不抽象,每加一种你要写 200 行;抽象后只需 50 行。**抽象的回报是"加新东西的成本"**——这就是为什么商业代码必须定期重构。

更深层 Casey 的考量:他正在为"开源化"做准备。HH 项目在 GitHub 上,观众 fork 后可能加自己想要的资产类型。如果加载流程清晰,观众贡献代码的成本低,PR 数量自然多。重构是开源项目的"基础设施投资"。

心理锚点:看完今天,你能做到:**设计一个 trait,把"5 步加载流程"抽象化,新加一种资产只需实现 trait 的 2-3 个方法**。你还能解释 Rust trait 的"默认方法"、"关联类型"、"supertrait"三个特性,以及它们在重构里的角色。

## 1 · Casey 今天做了什么

Casey 今天延续昨天的清理,核心动作:

第一步,定义 `AssetLoader` trait:

```rust
trait AssetLoader {
    type Output;
    fn file_extension(&self) -> &str;
    fn parse(&self, bytes: &[u8]) -> Result<Self::Output, LoadError>;
}
```

第二步,为每种资产实现 trait:`BitmapLoader`、`SoundLoader` 等。每个实现只填"自己的差异点"(文件后缀、解析逻辑),通用步骤(读字节、解压)由 trait 默认方法处理。

第三步,把 `load_asset` 改成泛型:

```rust
fn load<L: AssetLoader>(loader: &L, id: AssetId) -> Result<L::Output, LoadError> {
    let path = format!("assets/{}.{}", id.index, loader.file_extension());
    let bytes = std::fs::read(&path)?;
    loader.parse(&bytes)
}
```

第四步,跑全量测试,确认行为不变。Casey 删除了所有 `load_xxx_inner`,代码减少了 800 行。

这集的工程产出是一个**架构改动**,而不是新功能。Casey 用了"小步快走"——每改一步编译一次,每改一步跑一次测试。整集没有"大爆炸式"的修改。

## 2 · 心智模型

### 类比:trait 是"工作合同"

想象你雇员工。你给每个员工一份**工作合同**:合同规定"你要做这几件事(parse、validate、format),我给你这些资源(bytes、context)"。具体怎么做由员工决定,但合同规定的步骤必须执行。

Rust trait 就是工作合同。`AssetLoader` trait 规定:"任何想当 AssetLoader 的类型,必须能告诉我文件后缀、能解析字节流、能返回特定类型"。具体类型(BitmapLoader、SoundLoader)是员工,合同是 trait。

### 严谨原理:trait 的三种核心特性

**1. 关联类型(associated type)**:

```rust
trait AssetLoader {
    type Output;       // 关联类型:每种 Loader 的 Output 不同
    fn parse(&self, bytes: &[u8]) -> Result<Self::Output, LoadError>;
}

struct BitmapLoader;
impl AssetLoader for BitmapLoader {
    type Output = Bitmap;     // BitmapLoader 输出 Bitmap
    fn parse(&self, b: &[u8]) -> Result<Bitmap, LoadError> { ... }
}

struct SoundLoader;
impl AssetLoader for SoundLoader {
    type Output = Sound;      // SoundLoader 输出 Sound
    fn parse(&self, b: &[u8]) -> Result<Sound, LoadError> { ... }
}
```

关联类型让"Loader 输出的类型"和 Loader 本身绑定。`BitmapLoader::Output` 永远是 `Bitmap`,编译期固定。

**为什么不用泛型?** `trait Loader<T>` vs `trait Loader { type Output; }` 的区别:泛型让"同一个类型可以实现多个 Loader<T>"(BitmapLoader 可以既是 Loader<Bitmap> 又是 Loader<Image>);关联类型则强制"一个 Loader 类型只有一种 Output"。Casey 用关联类型,因为一个 BitmapLoader 永远只输出 Bitmap,这种"一一对应"用关联类型表达更精确。

**2. 默认方法(default method)**:

```rust
trait AssetLoader {
    type Output;
    fn file_extension(&self) -> &str;
    fn parse(&self, bytes: &[u8]) -> Result<Self::Output, LoadError>;

    // 默认方法:子类可以 override,也可以不写直接用默认
    fn load_from_disk(&self, id: AssetId) -> Result<Self::Output, LoadError> {
        let path = format!("assets/{}.{}", id.index, self.file_extension());
        let bytes = std::fs::read(&path).map_err(|e| LoadError::Io(e.to_string()))?;
        self.parse(&bytes)
    }
}
```

`load_from_disk` 有默认实现,任何 `AssetLoader` 自动获得这个方法。如果想 override(比如 Model 需要异步加载),自己写一遍即可。

**3. supertrait(超位 trait)**:

```rust
trait SendLoader: AssetLoader + Send + Sync {
    // SendLoader 要求实现它的类型同时也是 AssetLoader + Send + Sync
    fn load_async(&self, id: AssetId) -> BoxFuture<'_, Result<Self::Output, LoadError>>;
}
```

`SendLoader` 要求 `Self` 同时满足 `AssetLoader + Send + Sync`——这是"supertrait 约束",让 SendLoader 自动继承 AssetLoader 的所有方法。Casey 用这个表达"这种 Loader 可以跨线程使用"。

### 模板方法模式在 Rust 里的表达

模板方法是 OO 设计模式里的经典——父类定义流程骨架,子类填空。Rust 用 trait + 默认方法表达:

```rust
trait AssetLoader {
    type Output;
    fn read_bytes(&self, id: AssetId) -> Result<Vec<u8>, LoadError> { /* 默认 */ }
    fn decompress(&self, bytes: Vec<u8>) -> Result<Vec<u8>, LoadError> { /* 默认 */ }
    fn parse(&self, bytes: &[u8]) -> Result<Self::Output, LoadError>;

    // 模板方法:固定流程,子类不重写
    fn load(&self, id: AssetId) -> Result<Self::Output, LoadError> {
        let raw = self.read_bytes(id)?;
        let dec = self.decompress(raw)?;
        self.parse(&dec)
    }
}
```

`load` 是模板方法——它定义了"读 → 解压 → 解析"的固定顺序,任何 Loader 都走这条路。Loader 类型只需实现 `parse`(必填),其余有默认。

### 为什么这样比重构前好

重构前的代码:

```rust
fn load_bitmap(id) {
    let bytes = read(...);  // 重复 1
    let dec = decompress(...);  // 重复 2
    parse_bitmap(...);
}

fn load_sound(id) {
    let bytes = read(...);  // 重复 1
    let dec = decompress(...);  // 重复 2
    parse_sound(...);
}
```

加一种 `load_video` 你要复制 80% 的代码。重构后:

```rust
struct VideoLoader;
impl AssetLoader for VideoLoader {
    type Output = Video;
    fn parse(&self, b: &[u8]) -> Result<Video, LoadError> { /* 唯一需要写的 */ }
}
```

加新类型 = 1 个 struct + 1 个 impl = 30 行。这就是抽象的力量。

### 抽象的代价:何时不要抽象

但抽象不是免费的。**过度抽象(over-abstraction)**比不抽象更糟——因为它把简单问题复杂化。

判定标准:

- **有 3+ 个具体例子**才考虑抽象(2 个可能是巧合)
- **未来真的会加新类型**才抽象(只有 bitmap + sound 且永不加,就别抽)
- **流程的"共同部分"真的相同**(80% 相同不算)

Casey 今天满足:4 种资产 + 未来要加 sprite/tilemap/video + 5 步流程 95% 相同。所以抽象合理。如果你只有 2 种且不打算加,直接重复 200 行更清晰。

### 重构的"停损点"

Casey 今天还有意留了一些"没动"的代码:

- 字体加载用了不同的解压库(miniz 而非 deflate),逻辑差异大,不强行统一
- Model 加载涉及异步,逻辑差异大,放到独立 trait

这是**"重构的智慧"**:不是把所有重复都消灭,而是消灭"消灭了有价值"的重复。剩下的差异是真实的差异,抽象反而模糊它。

---

**总结**:trait + 默认方法 = 模板方法模式,把"加载流程"骨架抽出来,具体类型只填差异。这是 Rust 表达抽象的核心工具。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏引擎里"asset pipeline"是工业级设计。Unreal Engine 5 的 asset pipeline 有 5 个阶段(import → reimport → cook → package → load),每阶段都是一个抽象层。Casey 今天的 trait 抽象相当于 Unreal 的"import + load"两阶段。

游戏开发圈的另一条经验:**asset pipeline 越抽象越好,因为内容会膨胀**。一个商业游戏有 10 万个资产文件,加载逻辑必须是数据驱动的(配置文件描述"怎么加载"),不能硬编码。

Casey 还没到"数据驱动",今天的 trait 是"代码驱动"的——加新资产要改源码。但 trait 让改动局部化(只加 impl,不改 load 函数),这是向"数据驱动"过渡的中间形态。

### 3.2 · 🎨 图形学视角

图形学视角看资产加载,关键是"**何时上传 GPU**"。Casey 的 trait 抽象后,这一步必须在 `parse` 里做:

```rust
impl AssetLoader for BitmapLoader {
    type Output = GpuTexture;
    fn parse(&self, bytes: &[u8]) -> Result<GpuTexture, LoadError> {
        let img = png::decode(bytes)?;
        let tex = upload_to_gpu(&img)?;  // 这里上传
        Ok(tex)
    }
}
```

但 GPU 上传必须在主线程(OpenGL 上下文绑定线程)。这导致 `parse` 不能异步。Casey 在 Day 540+ 加光探针时,会把"CPU 解码"和"GPU 上传"分开成两个 trait 方法——这是抽象演化。

另一个图形学考虑:**贴图压缩格式**。Bitmap 加载后是 RGBA8888(每像素 32 位),但 GPU 上传时应该转成 BC1/BC3/BC7(每像素 4-8 位),节省显存。这个"压缩"应该放在 trait 的哪个方法里?Casey 今天没处理,但他的抽象支持以后加一个 `compress_for_gpu` 方法。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上"读字节 + 解压"对应:

- **`read(2)`**:同步读文件
- **`mmap(2)`**:把文件映射到内存,延迟读取(只在实际访问时触发 page fault)
- **`aio_read(3)`**:异步 IO(Linux 原生 aio 用起来复杂)
- **`io_uring(2)`**:Linux 5.1+ 的现代异步 IO,性能极强

Casey 用同步 `read`,因为简单。如果你想优化到异步,trait 抽象让改动局部化——只改 `read_bytes` 默认方法,所有 Loader 自动用新实现。

解压(LZ4、zstd、deflate)在 Linux 上有 `libzstd`、`libdeflate` 等库,Rust 通过 `zstd-rs`、`miniz_oxide` 等 crate 调用。这些库都是 CPU 密集型,适合放后台线程。

Linux 上还可以用 `pread(2)`(位置读)避免 lseek 系统调用,适合"从大文件读一小段"。Casey 的 HHA 文件是单文件 pread 友好的——但 Casey 没用 pread,因为他不需要那么多优化。

### 3.4 · 🦀 Rust 生态视角

Rust trait 系统是表达抽象的核心工具。今天用到的三个特性(关联类型、默认方法、supertrait)是 trait 最强大的部分。

Rust 生态里类似的 asset loader 设计:

- **Bevy 的 `AssetLoader` trait**:`bevy::asset::AssetLoader`,有关联类型 `Asset`,有异步加载方法 `load(...)`. Casey 的设计是它的简化版。
- **`assets_manager` crate**:提供类似抽象,支持多种格式 + 缓存。
- **`ggez` 的 `Context`**:把 asset 加载揉进 Context 对象,简单但耦合。

Casey 不用这些库,因为他要"手把手教学"——让观众看到抽象怎么形成。但生产代码可以直接用 Bevy 的 AssetLoader。

Rust 的 trait 有一个常被忽视的特性:**`dyn Trait` vs `impl Trait`**。

- `impl Trait`(静态分发):编译期单态化,零成本,但每种实现是不同类型
- `dyn Trait`(动态分发):运行时虚函数调用,有少量开销,但所有实现装进同一个 `Box<dyn Trait>`

今天 Casey 用 `impl Trait`(在泛型 `<L: AssetLoader>` 里)。如果他想把所有 Loader 装进一个 Vec(`Vec<Box<dyn AssetLoader>>`),就必须用 `dyn`——但 `dyn` 要求 trait 是 **object safe**(不能有关联类型,除非用 `Box<dyn Trait<Output=X>>` 这种)。

这是 Rust trait 系统的核心权衡:**单态化 = 性能 + 类型扩散,trait object = 灵活 + 运行时开销**。

## 4 · 认知地图

### 4.1 上级

- **资产管线(asset pipeline)** — 从原始文件到运行时数据的全链路
- **trait 抽象** — Rust 表达"共用接口"的核心机制
- **模板方法模式** — OO 设计模式,在 Rust 里用 trait + 默认方法实现
- **类型驱动设计(type-driven design)** — 先设计类型,再写代码

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| trait + 默认方法 | 模板方法,代码骨架固定 | 流程相同,差异点少 | ✓ |
| trait object (`dyn`) | 运行时分发,异构集合 | 同一集合装多种实现 | 否 |
| 函数指针 `fn(&[u8]) -> T` | 极简,无状态 | 单一函数 | 否 |
| 数据驱动(配置文件描述加载) | 最灵活,运行时可改 | 商业引擎 | 否(将来) |

### 4.3 下级

- **关联类型** — trait 里的 `type Output`,绑定到 impl
- **默认方法** — trait 里有默认实现的方法
- **supertrait** — `trait B: A` 要求 B 同时是 A
- **object safety** — trait 能否做成 `dyn Trait`

## 5 · 对照与变奏

模板方法模式在不同语言:

- **C++**:虚函数 + 抽象基类,运行时分发
- **Java**:抽象类 + interface default method(Java 8+)
- **Python**:duck typing,无显式 trait
- **Go**:interface + 隐式实现,无默认方法(只能用嵌入 struct 模拟)
- **Rust**:trait + 默认方法,编译期分发(单态化)

Rust 的优势是"零成本抽象"——trait 的默认方法在编译期被单态化,运行时和手写代码一样快。

抽象的演化:Casey 在 Day 1-400 没有 trait,直接 4 个 load 函数;Day 497 统一 ID;Day 498 抽象 loader;Day 540+ 会进一步分 CPU 解码和 GPU 上传。**抽象是逐步加的,不是一开始就完美的**。这叫"**rule of three**":第一次写直接写,第二次重复忍一下,第三次重复就抽象。Casey 严格遵循这个规则。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:下面这个 trait 有几个方法?有几个是必须实现的?几个有默认?

```rust
trait Serializer {
    type Output;
    fn serialize(&self, v: &Self::Output) -> Vec<u8>;
    fn extension(&self) -> &str { "bin" }
    fn version(&self) -> u32 { 1 }
}
```

**参考解答**:3 个方法。1 个必须实现(`serialize`,无默认)。2 个有默认(`extension`、`version`)。`type Output` 不是方法,是关联类型。

为什么这么想:trait 方法的"必须 vs 可选"看有没有方法体。`serialize` 只有签名(分号),必须由 impl 提供;`extension`、`version` 有方法体(花括号),有默认实现,impl 可以不写。

### Lv2 · 动手实践

**题**:定义一个 `Logger` trait,有关联类型 `Output`,有方法 `log(&mut self, msg: &str) -> Self::Output`。给两个实现:`CountLogger`(数消息条数,Output = u32)和 `CollectLogger`(收集消息到 Vec,Output = Vec<String>)。写一段测试代码,两个 Logger 都用同一个 generic 函数处理。

**参考解答**:

```rust
trait Logger {
    type Output;
    fn log(&mut self, msg: &str) -> Self::Output;
    fn finalize(&mut self) -> Self::Output;  // 返回累积结果
}

struct CountLogger { count: u32 }
impl Logger for CountLogger {
    type Output = ();
    fn log(&mut self, _msg: &str) { self.count += 1; }
    fn finalize(&mut self) -> u32 { self.count }
}

struct CollectLogger { msgs: Vec<String> }
impl Logger for CollectLogger {
    type Output = ();
    fn log(&mut self, msg: &str) { self.msgs.push(msg.to_string()); }
    fn finalize(&mut self) -> Vec<String> {
        std::mem::take(&mut self.msgs)
    }
}

fn run_test<L: Logger>(logger: &mut L) -> L::Output {
    logger.log("hello");
    logger.log("world");
    logger.finalize()
}

fn main() {
    let mut c = CountLogger { count: 0 };
    assert_eq!(run_test(&mut c), 2);

    let mut col = CollectLogger { msgs: vec![] };
    let result = run_test(&mut col);
    assert_eq!(result, vec!["hello".to_string(), "world".to_string()]);
}
```

为什么这么写:`run_test` 是泛型函数,对任何 `Logger` 都能工作。`finalize` 的 Output 不同——这就是关联类型的用武之地。如果用泛型 `Logger<T>`,你需要明确说 `run_test::<u32>(&mut c)`,而关联类型让 Rust 自动推断。

## 8 · Rust / Arch 落地代码

下面是完整的 trait 抽象实现,可独立运行,演示今天的核心重构。

```rust
// src/asset/loader.rs

use std::fmt;
use std::fs;
use std::path::PathBuf;

/// 加载错误
#[derive(Debug)]
pub enum LoadError {
    Io(String),
    Parse(String),
    InvalidFormat(String),
}

impl fmt::Display for LoadError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            LoadError::Io(s) => write!(f, "io error: {s}"),
            LoadError::Parse(s) => write!(f, "parse error: {s}"),
            LoadError::InvalidFormat(s) => write!(f, "invalid: {s}"),
        }
    }
}

impl std::error::Error for LoadError {}

/// 资产加载器 trait —— 模板方法模式
pub trait AssetLoader {
    /// 输出类型(关联类型)
    type Output;

    /// 文件后缀(必须实现)
    fn file_extension(&self) -> &str;

    /// 解析字节流为具体资产(必须实现)
    fn parse(&self, bytes: &[u8]) -> Result<Self::Output, LoadError>;

    /// 解压(默认:不解压)
    fn decompress(&self, bytes: Vec<u8>) -> Result<Vec<u8>, LoadError> {
        Ok(bytes)  // 默认直通
    }

    /// 读字节(默认:从文件系统读)
    fn read_bytes(&self, base_dir: &str, index: u32) -> Result<Vec<u8>, LoadError> {
        let path = PathBuf::from(base_dir)
            .join(format!("{}.{}", index, self.file_extension()));
        fs::read(&path).map_err(|e| LoadError::Io(format!("{e}: {}", path.display())))
    }

    /// 模板方法:固定流程,具体 Loader 不应 override
    fn load(&self, base_dir: &str, index: u32) -> Result<Self::Output, LoadError> {
        let raw = self.read_bytes(base_dir, index)?;
        let dec = self.decompress(raw)?;
        self.parse(&dec)
    }
}

/// Bitmap 加载器(伪实现:把字节当成 width × height 的 RGBA)
pub struct BitmapLoader;

pub struct Bitmap {
    pub width: u32,
    pub height: u32,
    pub pixels: Vec<[u8; 4]>,
}

impl AssetLoader for BitmapLoader {
    type Output = Bitmap;

    fn file_extension(&self) -> &str { "bmp" }

    fn parse(&self, bytes: &[u8]) -> Result<Bitmap, LoadError> {
        if bytes.len() < 8 {
            return Err(LoadError::InvalidFormat("too short".into()));
        }
        let width = u32::from_le_bytes([bytes[0], bytes[1], bytes[2], bytes[3]]);
        let height = u32::from_le_bytes([bytes[4], bytes[5], bytes[6], bytes[7]]);
        let pixel_bytes = &bytes[8..];
        if pixel_bytes.len() < (width * height * 4) as usize {
            return Err(LoadError::InvalidFormat("pixel data short".into()));
        }
        let pixels = pixel_bytes
            .chunks_exact(4)
            .map(|c| [c[0], c[1], c[2], c[3]])
            .collect();
        Ok(Bitmap { width, height, pixels })
    }
}

/// Sound 加载器(伪实现:把字节当成 16-bit PCM samples)
pub struct SoundLoader;

pub struct Sound {
    pub sample_rate: u32,
    pub samples: Vec<i16>,
}

impl AssetLoader for SoundLoader {
    type Output = Sound;

    fn file_extension(&self) -> &str { "wav" }

    fn parse(&self, bytes: &[u8]) -> Result<Sound, LoadError> {
        if bytes.len() < 4 {
            return Err(LoadError::InvalidFormat("too short".into()));
        }
        let sample_rate = u32::from_le_bytes([bytes[0], bytes[1], bytes[2], bytes[3]]);
        let samples = bytes[4..]
            .chunks_exact(2)
            .map(|c| i16::from_le_bytes([c[0], c[1]]))
            .collect();
        Ok(Sound { sample_rate, samples })
    }
}

/// 通用加载入口(泛型 + 自动推断)
pub fn load_asset<L: AssetLoader>(
    loader: &L,
    base_dir: &str,
    index: u32,
) -> Result<L::Output, LoadError> {
    loader.load(base_dir, index)
}

fn main() {
    // 演示:加载 Bitmap 和 Sound 用同一个泛型入口
    let bmp = load_asset(&BitmapLoader, "assets", 0);
    match bmp {
        Ok(b) => println!("loaded bitmap: {}x{}", b.width, b.height),
        Err(e) => eprintln!("bitmap load failed: {e}"),
    }

    let snd = load_asset(&SoundLoader, "assets", 0);
    match snd {
        Ok(s) => println!("loaded sound: {} samples @ {}Hz", s.samples.len(), s.sample_rate),
        Err(e) => eprintln!("sound load failed: {e}"),
    }
}
```

注释要点:

- `AssetLoader` 是核心 trait,定义了"读 → 解压 → 解析"的模板方法
- `decompress` 和 `read_bytes` 有默认实现——非压缩资产不用 override
- `parse` 是每个具体 Loader 的差异点——它决定输出类型
- `load_asset` 函数是泛型的——它对任何 `AssetLoader` 都工作,编译期单态化(零成本)
- 错误用 `LoadError` enum 表达,实现 `std::error::Error` trait 让它符合 Rust 错误处理惯例

### Arch 命令

生成测试用的假资产文件:

```bash
$ mkdir -p test_assets
$ dd if=/dev/urandom of=test_assets/0.bmp bs=1024 count=4
4+0 records in
4+0 records out
4096 bytes (4.1 kB, 4.0 KiB) copied, 0.00012 s, 33.9 MB/s
```

`dd` 是 Linux 的"字节复制器",`if`=input file,`of`=output file,`bs`=block size,`count`=块数。这里从 `/dev/urandom`(随机字节源)读 4KB 写到 `0.bmp`。

如果想看 trait 在内存里的布局:

```bash
$ rust-gdb target/release/game
(gdb) print sizeof BitmapLoader
$1 = 0
(gdb) print sizeof SoundLoader
$2 = 0
```

BitmapLoader 和 SoundLoader 都是**零大小类型(ZST)**——它们没有数据,只有行为(impl AssetLoader)。这是 Rust 表达"无状态策略"的优雅方式。

如果想分析 trait 方法的开销:

```bash
$ cargo asm --release asset::loader::load_asset<BitmapLoader>
# 输出汇编代码,能看到 load_asset 已被单态化,没有虚函数调用
```

`cargo asm` 是 cargo 子命令(`cargo install cargo-asm`),输出函数的汇编。如果你看到 `call vtable` 或 `jmp [rax+8]`,说明是动态分发;如果看到 `call BitmapLoader::parse@PLT`,说明是静态分发(单态化)。
