# Day 524 · 集成 WAV 导入

> 前 500 多集 Casey 用现成的 .hha 文件装声音资产,Day 462 起他从 PNG 提取图像资产。今天他把同样的"导入管线"扩展到声音——读 WAV 文件,转换成 HHA 内部格式,嵌入到 .hha 资产包里。声音导入和图像导入有相似之处(都是"读外部格式 → 转内部格式 → 写 HHA chunk"),也有独特之处(WAV 比 PNG 简单,但**采样率/位深/声道**的处理是图像没有的)。

## 0 · 为什么要有这一天

游戏里的声音资产,跟图像资产一样必须从外部格式转换成引擎内部格式。Casey 在 Day 462-465 已经建立了 PNG → HHA 的图像导入管线。今天他把同一套管线扩展到 WAV(声音)。

**WAV 是什么?**Waveform Audio File Format,微软和 IBM 1991 年设计的非压缩声音格式。结构上和 PNG 几乎一模一样:也是分 chunk(块),也是 little-endian(小端序),也是 [length-prefix, data] 模式。所以你 Day 453 学的 PNG chunk 解析能直接复用。

**WAV 的独特处**是声音数据本身:它有**采样率**(sample rate,比如 44100 Hz,每秒采样 44100 次)、**位深**(bit depth,每个采样用 8/16/24/32 bit)、**声道数**(channels,1=mono, 2=stereo)。这些参数图像没有,但游戏引擎必须知道——因为播放时混音器要按这些参数处理。

工业级引擎(Unity、Unreal)的音频导入器还要处理更复杂的事:Ogg Vorbis 解码、MP3 解码、3D 空间化、循环点标记。Casey 用最简单的 WAV(非压缩 PCM),因为他要保留"完全自研"的精神——压缩格式(Day 453 PNG 解码)已经演示过,WAV 就用最直接的 PCM。

完成这一天之后,你具备:

- 能解析 RIFF 容器格式(WAV 的父格式,AVI 也是 RIFF)
- 理解 PCM 音频的基础参数(采样率、位深、声道)
- 在 Rust 里用 `hound` crate 读 WAV,或手写解析器

## 1 · Casey 今天做了什么

Casey 这一天的动作可以拆成四步:

第一步,他在资产系统里加了一个新的 asset type:`AssetType_Sound`,和原来的 `AssetType_Bitmap`、`AssetType_Font` 并列。

第二步,他写了一个 `LoadWAV` 函数,读 WAV 文件头(RIFF chunk + fmt chunk + data chunk),把 PCM 数据拷贝到 HHA 的 sound asset slot。这和 `LoadPNG` 是镜像函数,模式完全一样。

第三步,他修改了 HHA 格式,加了一个 `HHAAssetSound` 结构:`sample_count`、`channel_count`、`samples[]`(PCM 数据)。这是一个 chunk 嵌入到 .hha 文件里。

第四步,他跑了一遍导入器,看 .hha 文件大小变大(因为多了 PCM 数据),然后用游戏里的 `PlaySound` API 触发,听到声音——确认整条管线贯通。

视频里他强调:这一天的本质是**把图像导入的架构抽象出来,复用到声音**。HHA 设计的 chunk-based 结构让它天然支持多种资产类型,加一种类型不需要重写整个管线。

让我把"抽象复用"这件事讲清楚,因为这是工程能力的核心。Casey 在 Day 462-465 写 PNG 导入器时,代码大致是:

```
1. 读文件头,验证魔数(magic number)
2. 循环读 chunk:解析 chunk 类型,按类型分发处理
3. 把解析结果填进 HHA 内部结构
4. 写入 .hha 文件
```

这套结构对 WAV 是**直接适用**的,因为 WAV 也是 chunk-based。Casey 在 Day 524 重新写 `LoadWAV`,代码模式几乎一样——区别只在 chunk 类型名(PNG 是 IHDR/IDAT,WAV 是 fmt /data)和 endianness(PNG big-endian,WAV little-endian)。

这就是"软件架构"的价值:**好的抽象让你新增功能时,改动局限在一个函数**。如果 Casey 当初把 PNG 解析硬编码到 asset pipeline 里,加 WAV 就要拷一份 800 行代码,以后改一处要改两处。Casey 在 Day 463 设计 HHA 格式时已经预见到这一点——他把 chunk-based 解析做成独立的 utility,而不是埋在 PNG 代码里。这就是为什么他在 Day 524 只需要 30 分钟就接入了 WAV。

对你的启发:**写代码时永远问"未来还会不会有同类需求?"**。如果有,把"模式"做成抽象,把"差异"做成参数。今天加 WAV,明天可能要加 TTF(字体)、OGG(压缩音频)、FBX(3D 模型)。每加一种都从头写,代码会爆炸;复用 chunk-based 模式,加一种的成本是几十行,不是几千行。

## 2 · 心智模型

### 类比:集装箱的多功能舱

想象一个货轮,装货的集装箱都是标准化的(20 英尺、40 英尺)。集装箱里装什么都行——衣服、电子产品、食品。货轮不关心里面装什么,只关心集装箱外形。

HHA 就是这个货轮,asset 就是集装箱。集装箱的"标签"标明里面是图像还是声音还是字体。货轮(HHA 文件)按标签把集装箱存到对应的槽位,游戏运行时按标签取用。今天 Casey 加的 WAV 导入,就是"给货轮新增一类标准集装箱——音频集装箱"。

### 严谨展开:RIFF 容器格式

WAV 文件实际是 RIFF(Resource Interchange File Format)容器的实例。RIFF 是微软 1991 年设计的元格式,所有 RIFF 文件由 chunk 组成:

```
[4B FourCC] [4B length] [length bytes data]
```

- **FourCC** —— 4 字符 ASCII 标识,如 `RIFF`、`fmt `、`data`、`LIST`
- **length** —— 4 字节小端无符号整数,数据长度
- **data** —— 任意二进制数据

WAV 文件结构:

```
RIFF chunk
  ├─ FourCC: "RIFF"
  ├─ length: (文件大小 - 8)
  ├─ FourCC: "WAVE"  (子类型)
  │
  ├─ fmt chunk
  │   ├─ FourCC: "fmt "
  │   ├─ length: 16 (PCM) 或 18/40 (扩展)
  │   ├─ AudioFormat: u16 (1 = PCM)
  │   ├─ NumChannels: u16 (1=mono, 2=stereo)
  │   ├─ SampleRate: u32 (44100 等)
  │   ├─ ByteRate: u32 (= SampleRate * NumChannels * BitsPerSample/8)
  │   ├─ BlockAlign: u16 (= NumChannels * BitsPerSample/8)
  │   └─ BitsPerSample: u16 (8/16/24/32)
  │
  └─ data chunk
      ├─ FourCC: "data"
      ├─ length: PCM 数据长度
      └─ PCM samples
```

对比 PNG chunk:

- PNG chunk 是 `[4B type] [4B length big-endian] [data] [4B CRC]`,CRC 是 PNG 独有的(数据完整性)
- RIFF chunk 没有 CRC
- PNG length 是大端(big-endian),RIFF length 是小端(little-endian)

这两个格式设计哲学一样(chunk-based),实现细节不同。Casey 在 Day 453 写 PNG 解析时建立的"chunk reader"抽象,这里改一下 endianness 和 length 字节序,就能复用。

### PCM 数据的本质

PCM(Pulse Code Modulation,脉冲编码调制)是最原始的数字音频表示:每个采样点是声音波形在该时刻的振幅,直接编码为整数。

对 16-bit PCM(最常见),每个采样是 `i16`,范围 `[-32768, 32767]`。0 表示静音,32767 表示最大正振幅,-32768 表示最大负振幅。

**采样率**决定频率范围。Nyquist 定理:能表示的最高频率 = 采样率 / 2。CD 音质 44100 Hz 能表示到 22050 Hz,人耳上限是 20000 Hz,够用。

**声道**是同时播放的独立流。立体声(stereo)有 2 个声道——左右,模拟两只耳朵。多声道(5.1、7.1)用于影院。

PCM 数据布局:交错(interleaved)。立体声 16-bit PCM 数据是 `[L0, R0, L1, R1, L2, R2, ...]`,每个 u16 是一个采样。

### Nyquist 定理:为什么 CD 是 44100 Hz

人耳听觉范围是 20 Hz - 20000 Hz。Nyquist-Shannon 采样定理说:**要完美重建一个最高频率 f 的信号,采样率必须 >= 2f**。所以 20000 Hz 需要 40000 Hz 采样率。CD 选 44100 Hz 是因为多出的 4100 Hz 给低通滤波器留"过渡带"——理想滤波器是物理不可实现的,实际滤波器在截止频率附近有衰减斜坡,需要留余量。

44100 这个数字本身有历史原因:它是 Sony 1979 年选的,因为兼容 NTSC/PAL 视频设备的采样频率(每行 3 采样 × 245 行 × 60 Hz = 44100 Hz)。这个数字一直延续到今天,即便我们不再用视频设备做音频。

工业级音频采样率阶梯:

- **8000 Hz** —— 电话(够语音,不够音乐)
- **22050 Hz** —— 游戏 SFX(短促音效,空间小)
- **44100 Hz** —— CD 音质(标准)
- **48000 Hz** —— DVD / 专业音频
- **96000 Hz** —— 高解析音频(母带处理)
- **192000 Hz** —— 母带级(后期制作)

游戏用 44100 或 48000。Casey 用 44100(CD 标准)。**别盲目用 192000**,文件大小翻 4 倍,人耳听不出差别。

### 位深的物理意义

位深决定**动态范围**(最弱到最强声音的比值)。公式:

```
dynamic_range_db ≈ 6.02 * bits
```

- 8-bit PCM:48 dB(电话音质,信噪比低)
- 16-bit PCM:96 dB(CD 标准,人耳动态范围 ~90 dB,够用)
- 24-bit PCM:144 dB(工作室母带,留大量 headroom)
- 32-bit float:1528 dB(理论值,实际不必要)

人耳的动态范围是大约 90-100 dB(从耳语到痛阈)。16-bit 的 96 dB 已经够,但工作室录音用 24-bit,因为录音时不知道最终 mix 的动态,留余量。游戏运行时混音用 16-bit 或 32-bit float(浮点避免 clipping)。

### Casey 为什么选非压缩 PCM

Casey 在视频里说:他用 PCM 不用 Ogg/MP3,因为**这一集讲的是导入,不是压缩**。Ogg 解码是另一个主题(Day 527 之后会涉及)。教学上,先讲最简单的格式,再讲压缩。

工业级游戏发布版用压缩(Ogg/Opus)的理由:
- 1 分钟立体声 16-bit 44.1k PCM = 10 MB
- 同样时长 Ogg Vorbis q5 = 1 MB(10 倍压缩比)
- 一款游戏可能有 100 首背景音乐 = 1 GB PCM vs 100 MB Ogg

差距巨大。但**开发阶段用 PCM**——因为加载快(无需解码),改起来方便。Casey 用 PCM 是合理的教学选择,生产环境会再加一层压缩。

### Casey 的 WAV 解析步骤

```
1. 读 12 字节 RIFF header
   - 验证 FourCC == "RIFF"
   - 验证 WAVE == "WAVE"
2. 循环读 chunk:
   - 读 8 字节 chunk header (FourCC + length)
   - 如果 FourCC == "fmt ":解析格式信息
   - 如果 FourCC == "data":存 PCM 数据
   - 跳过其他 chunk
3. 验证:必须有 fmt + data
4. 转换到内部 SoundAsset 结构
```

这和 PNG 解析几乎一模一样——PNG 是 `[IHDR] [IDAT] [IEND]`,WAV 是 `[fmt ] [data]`,都是"关键 chunk + 跳过其他"的模式。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏音频导入要考虑的事比 Casey 演示的多得多:

- **压缩**:Ogg Vorbis、MP3、Opus 是常见的压缩格式。文件大小比 WAV 小 5-10 倍。但解码需要 CPU——权衡。
- **流式播放**:大音频(BGM,5 分钟 50 MB)不能一次性加载到内存,要流式读盘。Casey 在 Day 526 处理这个。
- **3D 空间化**:声音根据声源和玩家距离衰减、低通滤波。需要空间化插件(OpenAL、Wwise、FMOD)。
- **混音**:多个声音同时播放,混音器负责合成。需要避免削波(clipping)。

工业级游戏音频中间件:FMOD(商业)、Wwise(商业)、OpenAL(开源)、Csound(开源)。Casey 不用中间件,直接 Win32 DirectSound,Rust 翻译用 `cpal` crate。

#### 游戏音频管线的完整结构

工业级音频管线比 Casey 演示的多这些组件:

1. **AssetDB**:管理所有音频文件,每个有 metadata(类型、循环点、音量、空间化参数)
2. **构建期压缩**:构建时把 WAV 转成 Ogg/Opus,减小包体
3. **加载期解码**:游戏运行时,小音频一次性解码到 PCM;大音频流式解码(每秒解一部分)
4. **混音器**:多个声音源混合,加效果(DSP:reverb、EQ、compressor)
5. **空间化**:3D 声音根据玩家位置/朝向调整左右声道平衡、距离衰减、遮挡
6. **输出**:发送到 OS 音频 API( ALSA、CoreAudio、WASAPI)

Casey 在 HH 实现了 1 和 3 的一部分(简单 PCM),其他留给后续天。这是教学项目的合理简化——先有能跑的最小管线,再加复杂功能。

#### 音频中间件 vs 自研

商业游戏用 FMOD/Wwise,理由:
- 跨平台支持(PS5、Xbox、Switch、PC、Mobile 全覆盖)
- 工业级编辑器(可视化事件编辑、混音路由)
- 内存/性能优化(流式加载、动态压缩)
- 授权费(~$3 万 / 平台)

自研(像 Casey)适合:
- 学习目的(理解每个细节)
- 小型游戏(< 10MB 音频,不需要复杂管线)
- 平台唯一(只发 PC)

你的 Rust 项目应该:
- 学习阶段:用 `cpal` + `hound`,自己实现简单管线
- 真正发游戏:用 `kira` crate(Rust 生态最成熟的游戏音频库),或绑定 FMOD/Wwise

### 3.2 · 图形学视角

音频不是图形学主题,但音频的 **DSP(数字信号处理)** 和图像处理共享很多数学:卷积、FFT、滤波器。学音频对图形学的人有帮助:

- **卷积**:图像模糊(Gaussian kernel)= 音频低通滤波(平滑相邻采样)
- **FFT**:图像频率域分析 = 音频频谱分析
- **重采样**:图像缩放 = 音频采样率转换

工业级音频插件开发(VST、AU)用 C++,Rust 生态有 `vst-rs`。

### 3.3 · Linux 系统编程视角

Linux 音频栈:

- **ALSA**(Advanced Linux Sound Architecture)—— 内核级,最底层
- **PulseAudio** —— 桌面级,常见于 GNOME/KDE
- **JACK** —— 专业音频,低延迟
- **PipeWire** —— 新一代,取代 PulseAudio + JACK

`cpal` crate 抽象这些差异,跨 Linux/macOS/Windows。用法:

```rust
use cpal::traits::{DeviceTrait, HostTrait, StreamTrait};
let host = cpal::default_host();
let device = host.default_output_device().unwrap();
let config = device.default_output_config().unwrap();
// 创建 stream,提交 PCM 样本
```

Linux 上 WAV 命令行工具:

```bash
# 看 WAV 文件信息
ffprobe sound.wav
#   Stream #0:0: Audio: pcm_s16le, 44100 Hz, stereo, s16, 1411 kb/s

# 播放 WAV
aplay sound.wav          # ALSA
paplay sound.wav         # PulseAudio
ffplay -nodisp sound.wav # ffmpeg

# 转换采样率
ffmpeg -i sound.wav -ar 22050 sound_22k.wav

# 转 Ogg Vorbis
ffmpeg -i sound.wav -c:a libvorbis -q:a 4 sound.ogg
```

### 3.4 · Rust 生态视角

读 WAV 的两个选择:

**手写解析器**(教学):100 行 Rust,理解 RIFF 格式细节。
**`hound` crate**(工业级):成熟稳定,处理边界情况。

```rust
// Cargo.toml:
// [dependencies]
// hound = "0.5"

use hound::WavReader;

fn load_wav(path: &str) -> (u32, u16, Vec<i16>) {
    let mut reader = WavReader::open(path).expect("open failed");
    let spec = reader.spec();
    let samples: Vec<i16> = reader.samples::<i16>().filter_map(|s| s.ok()).collect();
    (spec.sample_rate, spec.channels, samples)
}
```

`hound` 还能写 WAV(`WavWriter`),用于 Casey Day 529 的 PNG 写入器之后的"音频导出器"。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **资产管线(Asset Pipeline)** —— 外部格式 → 引擎内部格式的转换系统
- **RIFF 容器格式** —— WAV、AVI 共享的元格式

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| WAV (PCM) | 非压缩,文件大 | 教学、原始音频 | Casey 选这个 |
| Ogg Vorbis | 压缩,开源 | 游戏发布 | 推荐发布版用 |

- **RIFF chunk** —— WAV 的存储单元
- **fmt chunk** —— 音频格式元数据
- **data chunk** —— PCM 原始采样
- **PCM sample** —— 单个采样点(i16 等)
- **frame** —— 所有声道的一组采样(立体声一帧 = 1 L + 1 R)

## 5 · 对照与变奏

WAV 的设计思路和 PNG 几乎一致——chunk-based、简单结构、易于解析。这是 90 年代多媒体格式的共识:用容器格式装不同类型的数据。

RIFF(WAV 的父格式)是微软的设计。AIFF(Audio IFF)是苹果对应的格式,大端字节序,结构类似。Apple/SGI 的 MOV/MP4 容器格式延续了这种思路,但更复杂(支持视频、字幕、章节)。

现代游戏发布版用压缩格式(Ogg、Opus)减小包体大小。但**开发阶段用 WAV**——因为不需要解码,加载快,改起来方便。Casey 用 WAV 是合理的(教学项目,不在意包大小)。

音频中间件(FMOD、Wwise)有自己的资产格式,通常包含:压缩音频 + 元数据(循环点、音量、空间化参数)+ 编辑器状态。比 HHA 复杂,但解决工业级问题。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:WAV 的 `ByteRate` 字段定义为 `SampleRate × NumChannels × BitsPerSample/8`。这是冗余的(可从其他字段计算)。为什么格式要存这个"冗余"字段?

**参考解答**:冗余字段是**优化读取速度**。播放器读 WAV 时,想知道"每秒要消费多少字节"来设置缓冲区大小。如果只有原始三个字段,每次都要做乘法。预计算后存起来,读取时直接拿。这种"用空间换时间"的冗余在二进制格式里很常见——也是为什么 PNG 的 IHDR 里既存 width 又存 height(可从其他 chunk 推算),WAV 既存 NumChannels 又存 BlockAlign(可计算)。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:用 `hound` crate 加载一个 WAV 文件,打印它的格式信息(采样率、声道、位深),然后打印前 10 个采样值。找一个测试 WAV(自己用 `ffmpeg -f lavfi -i "sine=frequency=440:duration=1" test.wav` 生成 1 秒 440Hz 正弦波)。

**参考解答**:

```rust
// Cargo.toml:
// [dependencies]
// hound = "0.5"

use hound::{WavReader, SampleFormat};

fn main() {
    let mut reader = WavReader::open("test.wav").expect("open failed");
    let spec = reader.spec();
    
    println!("=== WAV 格式信息 ===");
    println!("采样率:    {} Hz", spec.sample_rate);
    println!("声道数:    {}", spec.channels);
    println!("位深:      {} bits", spec.bits_per_sample);
    println!("采样格式:  {:?}", spec.sample_format);  // Int 或 Float
    println!("总帧数:    {}", reader.duration());  // duration() 返回帧数,不是秒
    
    // 计算时长
    let duration_sec = reader.duration() as f32 / spec.sample_rate as f32;
    println!("时长:      {:.2} 秒", duration_sec);
    
    println!("\n=== 前 10 个采样 ===");
    let samples: Vec<i16> = reader.samples::<i16>().take(10).filter_map(|s| s.ok()).collect();
    for (i, s) in samples.iter().enumerate() {
        println!("[{}] = {}", i, s);
    }
}
```

## 8 · Rust / Arch 落地代码

```rust
// 完整的 WAV 解析器,手写(教学版)

#[derive(Debug)]
struct WavFormat {
    audio_format: u16,      // 1 = PCM
    num_channels: u16,      // 1=mono, 2=stereo
    sample_rate: u32,       // 如 44100
    byte_rate: u32,         // 每秒字节数
    block_align: u16,       // 一个 frame 的字节数
    bits_per_sample: u16,   // 8/16/24/32
}

#[derive(Debug)]
struct WavFile {
    format: WavFormat,
    samples: Vec<u8>,  // 原始 PCM 字节
}

fn parse_wav(data: &[u8]) -> Result<WavFile, &'static str> {
    if data.len() < 12 {
        return Err("file too short");
    }
    
    // 1. 验证 RIFF header
    if &data[0..4] != b"RIFF" {
        return Err("not a RIFF file");
    }
    // data[4..8] 是文件大小,通常忽略(可能不准)
    if &data[8..12] != b"WAVE" {
        return Err("not a WAV file");
    }
    
    // 2. 循环读 chunk
    let mut format: Option<WavFormat> = None;
    let mut samples: Vec<u8> = Vec::new();
    
    let mut offset = 12;
    while offset + 8 <= data.len() {
        let fourcc = &data[offset..offset+4];
        let length = u32::from_le_bytes([
            data[offset+4], data[offset+5], data[offset+6], data[offset+7]
        ]) as usize;
        offset += 8;
        
        if offset + length > data.len() {
            return Err("chunk length out of bounds");
        }
        
        match fourcc {
            b"fmt " => {
                // 解析格式
                let audio_format = u16::from_le_bytes([data[offset], data[offset+1]]);
                let num_channels = u16::from_le_bytes([data[offset+2], data[offset+3]]);
                let sample_rate = u32::from_le_bytes([
                    data[offset+4], data[offset+5], data[offset+6], data[offset+7]
                ]);
                let byte_rate = u32::from_le_bytes([
                    data[offset+8], data[offset+9], data[offset+10], data[offset+11]
                ]);
                let block_align = u16::from_le_bytes([data[offset+12], data[offset+13]]);
                let bits_per_sample = u16::from_le_bytes([data[offset+14], data[offset+15]]);
                
                format = Some(WavFile { 
                    format: WavFormat {
                        audio_format, num_channels, sample_rate, byte_rate, block_align, bits_per_sample
                    },
                    samples: Vec::new(),
                }.format);
            }
            b"data" => {
                samples = data[offset..offset+length].to_vec();
            }
            _ => {
                // 跳过未知 chunk(如 LIST、fact)
            }
        }
        
        // chunk length 偶数对齐(奇数长度 + 1 padding)
        offset += length + (length % 2);
    }
    
    let format = format.ok_or("missing fmt chunk")?;
    if samples.is_empty() {
        return Err("missing data chunk");
    }
    
    Ok(WavFile { format, samples })
}

fn main() {
    let data = std::fs::read("test.wav").expect("read failed");
    match parse_wav(&data) {
        Ok(wav) => {
            println!("格式: {:?}", wav.format);
            println!("PCM 字节数: {}", wav.samples.len());
            println!("时长: {:.2} 秒", 
                wav.samples.len() as f32 / wav.format.byte_rate as f32);
        }
        Err(e) => eprintln!("解析失败: {}", e),
    }
}
```

出错怎么办:

- **`EOF` / panic on array index**:文件被截断。检查 `data.len() < 12` 边界。
- **`not a RIFF file`**:你读的不是 WAV。可能是 MP3 等其他格式,需要其他解码器。
- **采样值全 0**:文件可能是 24-bit 或 32-bit float,你的代码假设了 16-bit。检查 `bits_per_sample`。
- **chunk 顺序不对**:有些 WAV 把 data 放在 fmt 之前(非标),代码要支持任意顺序——上面的代码用 `Option<WavFormat>` 累积,顺序无关。
