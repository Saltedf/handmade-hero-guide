
# Day 514 · 分离图像与元数据导入

> 到 Day 513,资产导入是混在一起的——一个 .png 文件附带元数据。Day 514 重构:分离图像数据(.png)和元数据(.hht),让元数据可独立修改不影响图像。

## 0 · 为什么要有这一天

### 真实场景:资产管线性能问题

让我们把镜头拉近,真实地体验这个场景。

你跟着 Casey 做到 Day 513。你的游戏有 200 个 sprite、50 个 entity 类型、20 个 alignment point。每次启动游戏,你需要:

1. 读 `assets.hht`(几 KB 文本)
2. 读 200 个 PNG 文件(每个几百 KB,总共几十 MB)
3. 解码 PNG → RGBA 像素
4. 解析 HHT 元数据(alignment point、piece 结构)
5. 上传到 GPU
6. 构建 entity 数据库

启动时间:3 秒。

现在你的美术师说:"我把 sword.png 改了,剑刃加个发光效果。" 你重启游戏——又要 3 秒,因为整个流程都要重跑,即便只改了一张图。这浪费。

更糟的场景:你的策划说:"我把 hero 的 alignment_point 'neck' 位置从 (0, -20) 改成 (0, -25)。" 这只是 HHT 里一行的小改,但你的 import 流程**重新读所有 PNG、重新解码、重新上传**。一个 1ms 的改动触发 3 秒的全流程。

### 问题根源:职责混淆

到 Day 513,资产 import 是**一个函数做全部事**:

```rust
fn import_asset(path: &Path) -> Asset {
    let png_data = read_png(path);        // 读 PNG
    let pixels = decode_png(png_data);    // 解码 PNG
    let metadata = parse_metadata(...);    // 解析元数据
    Asset { pixels, metadata }
}
```

这个函数做了**两件不相关的事**:
- 读 + 解码 PNG(二进制 → 像素,慢,几百毫秒)
- 解析 HHT 元数据(文本 → 结构,快,几毫秒)

它们什么时候变化?
- PNG 变化:美术师重新画图(每天几次)
- 元数据变化:策划调位置(每分钟几次)

它们改动的**频率完全不同**。但因为代码耦合,任何一方的改动都触发**整个流程**重新跑。这就是 **职责混淆**——单一模块承担多个变化方向。

### Single Responsibility Principle(SRP,单一职责原则)

SOLID 五大设计原则的 S:每个模块**只应有一个变化的理由**。

判断方法:列出"什么会让这个模块改"——如果有多个不相关的原因,违反 SRP。

旧 import 函数会被这些改动触发:
- PNG 格式变了(如改用 WebP)
- 元数据格式变了(如 HHT 改成 JSON)
- 解码库变了(如换 lodepng 到 png crate)
- 元数据 schema 变了(如加新字段)

四个原因。违反 SRP。

### Day 514 的解决方案:职责分离

Casey 把 import 拆成两个独立函数:

```rust
// 图像 importer:只关心 PNG → 像素
fn import_image(path: &Path) -> ImageBlob {
    let png_data = read_png(path);
    decode_png(png_data)
}

// 元数据 importer:只关心 HHT → 结构
fn import_metadata(text: &str) -> MetadataStructure {
    parse_hht(text)
}
```

各自独立。改 PNG?只调 `import_image`。改 HHT?只调 `import_metadata`。互不影响。

加 HHA packer 把两者合并:

```rust
fn build_hha(images: &[ImageBlob], metadata: &[MetadataStructure]) -> Vec<u8> {
    // 把 images + metadata 序列化成二进制 HHA
}
```

这是 Day 514 的核心重构。

### 为什么这件事重要?

这看似"只是 refactor",但它教你**软件工程的核心抽象——SRP**。SRP 不是理论空话——它直接影响:

- **性能**:职责分离后,可以独立缓存、独立并行、独立 invalidate
- **可维护性**:改图像不影响元数据(反之亦然),bug 局部化
- **可测试**:图像 importer 单独测,元数据 importer 单独测,各自简单
- **可复用**:图像 importer 可以用于非 HHT 项目(纯 PNG 工具)
- **团队协作**:图像团队管 `import_image`,策划团队管 `import_metadata`,代码所有权清晰

工业级资产管线(Unity、Unreal、Bevy)都按 SRP 设计。Day 514 是 HH 里第一次系统化讲 SRP,后续 day 反复用。

完成这一天,你能:

- 应用 SRP 重构现有耦合代码
- 设计模块化的 import pipeline(分阶段、可独立热重载)
- 处理依赖关系(metadata 引用 image,反向不依赖)
- 理解打包 / 序列化的分层(binary 与 metadata 分层)
- 看懂 Unity `.meta` 文件、Unreal `.uasset` 的内部结构

## 1 · Casey 今天做了什么

Casey 这一天做了一次"职责分离重构"。他没加新功能,而是**重新组织现有代码**,让职责清晰。

**第一步,审计现有 import**。他打开 `import_asset(path)` 函数,逐行看:这行读 PNG、这行解码、这行解析 HHT、这行构建结构。每个操作分属不同职责,但混在一个函数里。

```rust
// 旧代码(混合)
fn import_asset(path: &Path, hht: &str) -> Asset {
    let png_data = read_file(path);    // 1. I/O
    let pixels = decode_png(&png_data);    // 2. 解码
    let metadata = parse_hht(hht);    // 3. 解析
    Asset { pixels, metadata }    // 4. 合并
}
```

**第二步,拆成两个函数**。图像和元数据各自独立:

```rust
fn import_image(path: &Path) -> ImageBlob {
    let png_data = read_file(path);
    decode_png(&png_data)
}

fn import_metadata(hht: &str) -> MetadataStructure {
    parse_hht(hht)
}
```

**第三步,定义中间结构**。`ImageBlob`(纯像素 + 元信息:width、height、format),`MetadataStructure`(引用 image 的 ID + alignment point 等结构)。

```rust
struct ImageBlob {
    id: u32,           // 唯一 ID
    width: u32,
    height: u32,
    pixels: Vec<u8>,   // RGBA
}

struct MetadataStructure {
    name: String,
    image_id: u32,     // 引用 ImageBlob.id
    alignment_points: Vec<AlignmentPoint>,
}
```

**第四步,改 HHA serialize**。先写所有 image blobs,再写 metadata。Metadata 用 image ID 引用 image,不直接嵌套像素。

```rust
fn pack_hha(images: &[ImageBlob], metadata: &[MetadataStructure]) -> Vec<u8> {
    let mut buf = Vec::new();
    // Header
    buf.extend_from_slice(b"HHA3");
    // Image section
    buf.extend_from_slice(&(images.len() as u32).to_le_bytes());
    for img in images {
        // id, width, height, pixels_len, pixels
    }
    // Metadata section
    buf.extend_from_slice(&(metadata.len() as u32).to_le_bytes());
    for m in metadata {
        // name, image_id, alignment_points
    }
    buf
}
```

**第五步,加热重载**。Day 512 的热重载以前是"任何文件变 → 全 reload"。Day 514 升级为:

- PNG 改 → 只重 import image,metadata 不动
- HHT 改 → 只重 import metadata,image 不动

两个独立的 watcher 监控不同文件,触发不同 reload 路径。

**第六步,跑性能测试**。对比"全 import" vs "分离 import"的耗时:

```
全 import(改一行 HHT):3.2 秒
分离 import(改一行 HHT):5 毫秒(metadata only)
分离 import(改一张 PNG):2.8 秒(image only)
```

改 HHT 从 3.2s 降到 5ms——**600 倍加速**。这就是 SRP 的实际价值。

## 2 · 心智模型

### 类比:餐厅菜单 vs 食材

想象一家餐厅。旧模式:菜单写在食材袋子上——你想改菜单("鱼香肉丝"改名为"川香肉丝"),必须**重新打包所有食材**。改菜单成本 = 改食材成本。

新模式:菜单归菜单,食材归食材。菜单印在小卡片上,食材放在冷库里。改菜单:重印卡片,1 分钟。改食材:重新采购,几小时。两者完全独立。

Day 514 的 import 重构同构:
- **HHT = 菜单**:文本,结构化,改起来快(几毫秒)
- **PNG = 食材**:二进制,大块,改起来慢(几秒)
- **HHA = 完整套餐**:菜单 + 食材打包成最终产品

职责分离后,改菜单不影响食材,改食材不影响菜单。**两种改动独立计费**。

### Single Responsibility Principle(SRP)

SRP 是 SOLID 五原则的第一个字母 (S)。SOLID 是 Robert C. Martin("Uncle Bob")总结的面向对象设计五大原则:

- **S** — Single Responsibility(单一职责)
- **O** — Open/Closed(开闭原则:对扩展开放,对修改关闭)
- **L** — Liskov Substitution(里氏替换)
- **I** — Interface Segregation(接口隔离)
- **D** — Dependency Inversion(依赖倒置)

SRP 的精确定义:**每个模块只应有一个变化的理由**。"变化的原因"通常是"某一类用户"(actor)。如果一个模块被多个不相关 actor 影响,违反 SRP。

旧 import 函数被以下"actor"影响:
- 美术师(改 PNG 内容)
- 策划(改 HHT 元数据)
- 程序员(改 import 实现细节,如换 PNG 解码库)

三个不相关 actor → 违反 SRP。

Day 514 拆成两个函数:
- `import_image`:只被美术师和程序员(图像处理)影响
- `import_metadata`:只被策划和程序员(文本解析)影响

各自只一个"主 actor" + 共享的程序员 actor。

SRP 的好处:

- **修改局部化**:改图像不碰元数据代码,反之亦然
- **测试简化**:图像 importer 单元测试不依赖 HHT 数据,反之亦然
- **复用性**:图像 importer 可以单独用(其他项目可能只需要 PNG → 像素,不需要 HHT)
- **并行开发**:图像团队和策划团队可以同时改各自的 importer,不冲突

SRP 不是教条。如果一个模块多个职责**都稳定不变**,可以不拆。SRP 是降低耦合的**工具**,不是规则。

### 依赖关系:DAG

分离后的依赖关系是 **DAG(Directed Acyclic Graph,有向无环图)**:

```
PNG file ──→ ImageBlob ──→ HHA packer
                                ↑
HHT file ──→ MetadataStructure ─┘
```

- Image 是叶子(不依赖其他)
- Metadata 依赖 Image(metadata 引用 image ID)
- HHA packer 依赖两者

关键性质:**没有循环依赖**。如果有循环(A 依赖 B,B 依赖 A),编译 / 运行时复杂度爆炸。

打包顺序由 DAG 决定:先 image(产生 ID),再 metadata(用 ID 引用)。

读取顺序反过来:metadata 找 ID,查 image。

### 分离的 import pipeline

完整的 pipeline 是这样:

```
┌─────────────┐
│  PNG file   │ (二进制,几百 KB)
└──────┬──────┘
       │ import_image()  ← 只关心 PNG 格式
       ▼
┌─────────────┐
│  ImageBlob  │ { id, width, height, pixels }
└──────┬──────┘
       │
       ├──────────────────────┐
       │                      │
       ▼                      ▼
┌─────────────┐         ┌─────────────┐
│  HHT file   │         │             │
└──────┬──────┘         │             │
       │ import_metadata() ← 只关心 HHT 格式
       ▼                │             │
┌─────────────────┐    │             │
│MetadataStructure│────┘             │
│ (用 image_id)   │                  │
└──────┬──────────┘                  │
       │                             │
       ▼                             ▼
   ┌─────────────────────────────────┐
   │           HHA packer            │
   └─────────────────┬───────────────┘
                     ▼
              ┌─────────────┐
              │  HHA file   │ (二进制,几十 MB)
              └─────────────┘
```

每步独立:
- **可并行**——多核机器上,`import_image` 可以并行处理多个 PNG
- **可缓存**——PNG 文件没变,`import_image` 结果可以缓存到磁盘
- **可独立重跑**——只 PNG 变了,只重跑 image 部分
- **可独立测试**——每个 stage 有清晰的输入 / 输出契约

这是工业级 asset pipeline 的核心结构。Unity、Unreal、Bevy 都按这个模式。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

商业游戏引擎的资产 import 全部按 SRP 设计。

**Unity**:`.meta` 文件和资产物理分离。`sword.png` 旁边有 `sword.png.meta`,元数据(GUID、import settings、texture type、compression)独立存。改 PNG 内容不影响 .meta。改 .meta(比如调整压缩格式)不重新读 PNG。Unity 的 `AssetPostprocessor` 在 PNG 变化时只重 import 图像,不动 .meta。

```yaml
# sword.png.meta(简化)
guid: 1234567890abcdef
TextureImporter:
  textureType: Sprite
  spriteMode: 1
  compression: BC7
```

**Unreal Engine**:`.uasset` 内部分 metadata 和 binary,但物理在同一文件。Unreal 的 `Reimport` 命令只重新读 binary 部分(如重新解码 PNG),不动 metadata。这是为了性能——AAA 项目有 100k+ 资产,全量重 import 要几小时。

**Godot**:`.import` 文件保存 import 设置(类似 Unity .meta),资产 cache 在 `.godot/imported/`(二进制 cache)。改 PNG → 只重 import 那一个 → 更新 cache。改 .import 设置 → 重新应用设置到现有 PNG cache。

游戏开发圈术语:

- **Asset metadata** —— 资产元数据
- **Reimport** —— 重新导入(强制重跑 import pipeline)
- **Import cache** —— 导入缓存(避免重复劳动)
- **Source asset** —— 源资产(用户编辑的,如 PNG、PSD)
- **Imported asset** —— 导入后资产(import pipeline 输出,运行时用的)
- **Asset dependency** —— 资产依赖(一个资产引用另一个)
- **Asset bundle** —— 资产打包(把多个资产合成一个文件,用于分发)

### 3.2 · 🎨 图形学视角

图形领域的数据天然分层,SRP 自动适用。

**Texture**(纹理):GPU 二进制数据,leaf。`import_image` 输出。
**Material**(材质):引用 texture,结构化数据。`import_material` 输出,引用 texture ID。
**Material Instance**:材质的实例,引用 material + 覆盖参数。
**Mesh**:顶点数据,binary,leaf。`import_mesh` 输出。
**Model**:引用 mesh + material。结构化。
**Scene**:引用 model + transform。结构化。

每层职责清晰:
- 改 texture(画贴图)→ 只重 import texture
- 改 material(换 shader / 调参数)→ 只重 import material
- 改 mesh(建模)→ 只重 import mesh
- 改 model(组合关系)→ 只重 import model

工业级引擎的 import 是这样的分层 DAG:

```
PNG/PSD → Texture
                ↓
              Material → MaterialInstance
                            ↓
                          Model ──→ Mesh ←─── OBJ/FBX
                            ↓
                          Scene
                            ↓
                          Level
```

每层独立 import、独立 cache、独立热重载。这是 Unity / Unreal 的核心架构。

### 3.3 · 🐧 Linux 系统编程视角

Linux 系统里到处是 metadata vs data 分离的例子。

**inode vs block**(文件系统):文件系统分离 inode(元数据:权限、size、time)和 data block(实际内容)。`stat` 读 inode,`read` 读 data。两者在磁盘上分开存储,读 inode 不读 data。

```bash
# 看 inode(元数据)
stat /etc/hostname
# 输出:Size, Blocks, IO Block, Device, Inode, Links, Access, Uid, Gid, Access time, Modify time, Change time, Birth time

# 看文件系统的 inode 信息
sudo dumpe2fs /dev/sda1 | head -50
# 显示 inode count, block count, free inodes, free blocks 等

# ext4 的 inode 大小(默认 256 字节)
sudo tune2fs -l /dev/sda1 | grep "Inode size"
```

**apt / dpkg**:`.deb` 包内部就是 metadata + data 分离:

```bash
# 下载 .deb
mkdir /tmp/deb_test && cd /tmp/deb_test
apt-get download bash

# 看 .deb 结构
ar x bash_*.deb
ls
# debian-binary  ← 元数据(版本)
# control.tar.gz ← 元数据(包名、依赖、描述)
# data.tar.gz    ← 实际数据(二进制、配置文件)

# 解压 control
tar xzf control.tar.gz
cat control
# Package: bash
# Version: 5.1.16-1
# Depends: ...
# Description: ...

# 解压 data
tar xzf data.tar.gz
ls usr/bin/
# bash ...
```

**ELF**(二进制文件):`/bin/ls` 等可执行文件,内部分 metadata(ELF header、section header、symbol table)和 data(code、rodata)。

```bash
# 看 ELF header(元数据)
readelf -h /bin/ls
# Magic, Class, Data, Version, OS/ABI, Type, Machine, Entry point, ...

# 看 sections(包括 metadata sections 和 data sections)
readelf -S /bin/ls
# .text (code), .rodata (read-only data), .data (data), .symtab (symbol table), ...

# 看 dynamic linking 元数据
readelf -d /bin/ls
```

**Docker image**:Docker 镜像分 layer(数据)和 config(元数据)。`docker inspect` 看 metadata,layer 在 `/var/lib/docker/overlay2/`。

Linux 哲学:**数据 + 元数据物理分离**,工具链独立操作。和 Day 514 的 SRP 完全同构。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 SRP 的几个模式。

**模式 1:`enum` 表达 either**。如果一个流程有两种 variant,用 enum:

```rust
enum Asset {
    Image(ImageBlob),
    Metadata(Metadata),
}

impl Asset {
    fn import(source: &Source) -> Result<Self> {
        match source.kind {
            SourceKind::Png => Ok(Asset::Image(import_image(source)?)),
            SourceKind::Hht => Ok(Asset::Metadata(import_metadata(source)?)),
        }
    }
}
```

但 Casey 不用 enum——他要的是**分离**,不是**统一**。enum 反而耦合。Casey 用两个独立函数。

**模式 2:`trait` 表达共性**。多个 importer 共享 trait,各自实现:

```rust
trait Importer {
    type Output;
    fn import(&self, source: &Source) -> Result<Self::Output>;
    fn cache_key(&self, source: &Source) -> String;
}

struct ImageImporter;
impl Importer for ImageImporter {
    type Output = ImageBlob;
    fn import(&self, source: &Source) -> Result<ImageBlob> {
        let png_data = source.read()?;
        decode_png(&png_data)
    }
    fn cache_key(&self, source: &Source) -> String {
        format!("image:{}", source.path)
    }
}

struct MetadataImporter;
impl Importer for MetadataImporter {
    type Output = MetadataStructure;
    fn import(&self, source: &Source) -> Result<MetadataStructure> {
        let hht_text = source.read()?;
        parse_hht(&hht_text)
    }
    fn cache_key(&self, source: &Source) -> String {
        format!("metadata:{}", source.path)
    }
}
```

trait 让你能写 generic pipeline:

```rust
fn run_pipeline<I: Importer>(importer: &I, source: &Source, cache: &mut Cache) -> Result<I::Output> {
    let key = importer.cache_key(source);
    if let Some(cached) = cache.get(&key) {
        return Ok(cached);
    }
    let result = importer.import(source)?;
    cache.insert(key, result.clone());
    Ok(result)
}
```

这是 Bevy 的 `bevy_asset` 的设计。

**模式 3:Builder pattern**。如果要传很多参数给 importer:

```rust
struct ImageImporterBuilder {
    width: Option<u32>,
    height: Option<u32>,
    format: PixelFormat,
    premultiply_alpha: bool,
}

impl ImageImporterBuilder {
    fn new() -> Self { /* defaults */ }
    fn with_width(mut self, w: u32) -> Self { self.width = Some(w); self }
    fn build(self) -> ImageImporter { /* ... */ }
}

let importer = ImageImporterBuilder::new()
    .with_width(64)
    .build();
```

Rust 编译器考验:借 `&mut importer`,同时读 source——分开:

```rust
// 错误:同时借
fn import(&mut self, source: &mut Source) -> Result<()> {
    let data = source.read()?;    // 借 source
    self.process(&data)?;          // 借 self
}

// 正确:分两步
fn import(&mut self, source: &mut Source) -> Result<()> {
    let data = source.read()?;    // 先读完,source 释放
    self.process(&data)?;          // 再处理
    Ok(())
}
```

Rust 强制"分阶段"思考,这和 SRP 的"职责分离"哲学吻合。

## 5 · 对照与变奏

分离在不同领域。

**HTML / CSS / JS**:三分离,各管一种。
**Database**:schema(元数据)vs data(实际行)。
**Source code**:code vs comments(虽然混在文件,但工具分开处理)。
**Email**:headers(元数据)vs body(数据),MIME 分离。

跨领域对照:

- **电影**:画面 vs 字幕(可独立改)。
- **音乐**:audio vs lyrics。
- **法律**:法条 vs 解释。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:SRP 重构的核心是什么?

**参考解答**:SRP 要求**每个模块只有一个变化的理由**。

判断方法:"这个模块因为 X 改动,因为 Y 改动,因为 Z 改动?"——如果有多个,违反 SRP。

旧 import 因为"图像格式改"和"元数据格式改"都会变,违反 SRP。拆成两个,各自只有一个变化理由。

SRP 不是教条,是**降低耦合**的工具。如果一个模块多个职责但都稳定,可以不拆。

### Lv2 · 动手实践

**题**:实现分离的 import。`import_image(path) -> ImageBlob`,`import_metadata(text) -> Metadata`。两者用 ID 关联。

完成标准:`cargo run` 显示分开 import 和合并的 HHA。

**参考解答**:

```rust
use std::collections::HashMap;

#[derive(Debug, Clone)]
struct ImageBlob {
    id: u32,
    width: u32,
    height: u32,
    pixels: Vec<u8>,
}

#[derive(Debug, Clone)]
struct AlignmentPoint {
    name: String,
    x: f32, y: f32,
}

#[derive(Debug, Clone)]
struct PieceMetadata {
    name: String,
    image_id: u32,    // 引用 ImageBlob
    alignment_points: Vec<AlignmentPoint>,
}

#[derive(Debug, Clone)]
struct EntityMetadata {
    name: String,
    pieces: Vec<PieceMetadata>,
}

// ============ Image importer ============
struct ImageImporter {
    next_id: u32,
}

impl ImageImporter {
    fn new() -> Self { Self { next_id: 1 } }
    
    fn import(&mut self, _path: &str, width: u32, height: u32) -> ImageBlob {
        let id = self.next_id;
        self.next_id += 1;
        // 模拟从 PNG 解码
        let pixels = vec![0u8; (width * height * 4) as usize];
        ImageBlob { id, width, height, pixels }
    }
}

// ============ Metadata importer ============
struct MetadataImporter;

impl MetadataImporter {
    fn new() -> Self { Self }
    
    fn import(&self, text: &str, image_lookup: &HashMap<String, u32>) -> Vec<EntityMetadata> {
        // 简化:不实际解析 HHT,直接 mock
        let _ = text;
        vec![
            EntityMetadata {
                name: "hero".into(),
                pieces: vec![
                    PieceMetadata {
                        name: "body".into(),
                        image_id: *image_lookup.get("hero_body").unwrap_or(&0),
                        alignment_points: vec![
                            AlignmentPoint { name: "neck".into(), x: 0.0, y: -20.0 },
                            AlignmentPoint { name: "hand_r".into(), x: 15.0, y: 0.0 },
                        ],
                    },
                    PieceMetadata {
                        name: "head".into(),
                        image_id: *image_lookup.get("hero_head").unwrap_or(&0),
                        alignment_points: vec![],
                    },
                ],
            },
        ]
    }
}

// ============ HHA Packer ============
struct HhaPacker;

impl HhaPacker {
    fn pack(images: &[ImageBlob], metadata: &[EntityMetadata]) -> Vec<u8> {
        let mut buf = Vec::new();
        
        // Header
        buf.extend_from_slice(b"HHA3");
        buf.extend_from_slice(&(images.len() as u32).to_le_bytes());
        buf.extend_from_slice(&(metadata.len() as u32).to_le_bytes());
        
        // Images
        for img in images {
            buf.extend_from_slice(&img.id.to_le_bytes());
            buf.extend_from_slice(&img.width.to_le_bytes());
            buf.extend_from_slice(&img.height.to_le_bytes());
            buf.extend_from_slice(&(img.pixels.len() as u32).to_le_bytes());
            buf.extend_from_slice(&img.pixels);
        }
        
        // Metadata
        for entity in metadata {
            buf.extend_from_slice(&(entity.name.len() as u32).to_le_bytes());
            buf.extend_from_slice(entity.name.as_bytes());
            buf.extend_from_slice(&(entity.pieces.len() as u32).to_le_bytes());
            for piece in &entity.pieces {
                buf.extend_from_slice(&(piece.name.len() as u32).to_le_bytes());
                buf.extend_from_slice(piece.name.as_bytes());
                buf.extend_from_slice(&piece.image_id.to_le_bytes());
                buf.extend_from_slice(&(piece.alignment_points.len() as u32).to_le_bytes());
                for ap in &piece.alignment_points {
                    buf.extend_from_slice(&(ap.name.len() as u32).to_le_bytes());
                    buf.extend_from_slice(ap.name.as_bytes());
                    buf.extend_from_slice(&ap.x.to_le_bytes());
                    buf.extend_from_slice(&ap.y.to_le_bytes());
                }
            }
        }
        
        buf
    }
}

fn main() {
    println!("=============================================\n");
    println!(" Day 514 · 分离图像与元数据导入\n");
    println!("=============================================\n");
    
    let mut image_importer = ImageImporter::new();
    let metadata_importer = MetadataImporter::new();
    
    // === 1. Import images ===
    println!("=== Step 1: Import Images ===\n");
    let images = vec![
        image_importer.import("hero_body.png", 64, 64),
        image_importer.import("hero_head.png", 32, 32),
        image_importer.import("goblin_body.png", 64, 64),
    ];
    
    let mut image_lookup = HashMap::new();
    image_lookup.insert("hero_body".to_string(), images[0].id);
    image_lookup.insert("hero_head".to_string(), images[1].id);
    image_lookup.insert("goblin_body".to_string(), images[2].id);
    
    for img in &images {
        println!("  image id={} ({}x{}, {} bytes)",
                 img.id, img.width, img.height, img.pixels.len());
    }
    
    // === 2. Import metadata ===
    println!("\n=== Step 2: Import Metadata ===\n");
    let hht_text = "[entities]\nhero { piece body { sprite = hero_body } }\n";
    let metadata = metadata_importer.import(hht_text, &image_lookup);
    
    for entity in &metadata {
        println!("  entity '{}':", entity.name);
        for piece in &entity.pieces {
            println!("    piece '{}' image_id={}", piece.name, piece.image_id);
            for ap in &piece.alignment_points {
                println!("      ap '{}': ({}, {})", ap.name, ap.x, ap.y);
            }
        }
    }
    
    // === 3. Pack HHA ===
    println!("\n=== Step 3: Pack HHA ===\n");
    let hha = HhaPacker::pack(&images, &metadata);
    println!("  HHA total: {} bytes", hha.len());
    println!("  images section: {} bytes", images.iter().map(|i| 16 + i.pixels.len()).sum::<usize>());
    println!("  metadata section: {} bytes", hha.len() - images.iter().map(|i| 16 + i.pixels.len()).sum::<usize>());
    
    // === 独立 reload 演示 ===
    println!("\n=== 独立 reload 演示 ===\n");
    
    println!("场景 A: 美术改了 hero_body.png");
    println!("  → 只重 import image,metadata 不变");
    let new_hero_body = image_importer.import("hero_body.png", 64, 64);
    println!("  新 image id={}", new_hero_body.id);
    println!("  metadata 仍引用 image_id=1(需要更新引用或用稳定 ID)");
    
    println!("\n场景 B: 策划改了 hero 的 alignment point");
    println!("  → 只重 import metadata,image 不变");
    let new_hht = "[entities]\nhero { piece body { alignment_point neck = (0, -25) } }\n";
    let new_metadata = metadata_importer.import(new_hht, &image_lookup);
    println!("  新 metadata: neck y = {}", new_metadata[0].pieces[0].alignment_points[0].y);
    println!("  images 不变,节省时间");
}
```

```rust
#[cfg(test)]
mod tests {
    use super::*;
    
    #[test]
    fn test_image_importer_assigns_ids() {
        let mut imp = ImageImporter::new();
        let i1 = imp.import("a", 1, 1);
        let i2 = imp.import("b", 1, 1);
        assert_eq!(i1.id, 1);
        assert_eq!(i2.id, 2);
    }
    
    #[test]
    fn test_image_pixels_size() {
        let mut imp = ImageImporter::new();
        let img = imp.import("a", 2, 3);
        assert_eq!(img.pixels.len(), 24);    // 2*3*4
    }
    
    #[test]
    fn test_metadata_importer_uses_lookup() {
        let imp = MetadataImporter::new();
        let mut lookup = HashMap::new();
        lookup.insert("hero_body".into(), 42u32);
        
        let md = imp.import("any", &lookup);
        assert_eq!(md[0].pieces[0].image_id, 42);
    }
    
    #[test]
    fn test_hha_pack_header() {
        let hha = HhaPacker::pack(&[], &[]);
        assert_eq!(&hha[0..4], b"HHA3");
        assert_eq!(hha.len(), 12);    // magic + 0 + 0
    }
    
    #[test]
    fn test_hha_pack_with_data() {
        let mut imp = ImageImporter::new();
        let img = imp.import("test", 1, 1);
        let hha = HhaPacker::pack(&[img], &[]);
        assert!(hha.len() > 12);
    }
    
    #[test]
    fn test_separation_of_concerns() {
        // 改 image 不影响 metadata,反之亦然
        let mut imp = ImageImporter::new();
        let md_imp = MetadataImporter::new();
        
        let img1 = imp.import("a", 1, 1);
        let mut lookup = HashMap::new();
        lookup.insert("a".into(), img1.id);
        let md1 = md_imp.import("", &lookup);
        
        // 只改 image,metadata 应保持
        let img2 = imp.import("a", 1, 1);
        let md2 = md_imp.import("", &lookup);    // 用相同 lookup
        
        // metadata 应一致(除非 lookup 改)
        assert_eq!(md1[0].pieces[0].image_id, md2[0].pieces[0].image_id);
    }
}
```
