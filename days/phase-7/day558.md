# Day 558 · 分配光探针槽位

> Voxel light probe 数量巨大,但 GPU 的 shader binding 槽位有限(OpenGL 32 个 uniform bindings,Vulkan 也有限制)。Day 558 Casey 把"哪些 voxel chunk 当前活跃"分配到**有限的槽位**——一种 GPU 资源调度。

## 0 · 为什么要有这一天

让我们从一个真实的卡顿场景说起。

你的 voxel light probe 系统已经跑起来——8×8×8 的体素网格,每个 chunk 在场景中摆一个 3D 纹理存 irradiance。Day 547 把框架搭好,Day 554 把内存占用压下来。现在你打开游戏,玩家站在大地图中央,周围 64 个 chunk 都活跃——按你的设计,这些 chunk 的 voxel texture 全要绑到 GPU shader 上,sample 出光照。

你按 F5 启动,**画面一片黑**,console 里 OpenGL 报错:

```
GL_INVALID_OPERATION: Program uniform "probe_textures[32]" exceeds GL_MAX_TEXTURE_IMAGE_UNITS (32)
```

你愣了一下,打开 `glGetIntegerv(GL_MAX_TEXTURE_IMAGE_UNITS, &n)`,n = 32。这是 OpenGL 4.x 的硬限制——一个 shader 同时只能"看见" 32 个 texture。可你有 64 个 chunk,加上角色贴图、天空盒、shadow map……加起来上百个 texture 要绑。**GPU 的"窗口"装不下。**

这是工业级渲染的常见困境:**你拥有的资源量 >> GPU 能同时访问的资源量**。CPU 端你可以分配几万个对象,GPU shader 在一帧里只能"指针"地访问几十个。问题不是"GPU 内存够不够",而是"shader 在一帧里能看见多少个独立的 binding"。

工业界的解决方案有两条路。**路径一**,沿用传统 OpenGL 设计:**固定数量的 binding 槽位 + 动态调度**——shader 声明 32 个槽位,每帧 CPU 决定"这 32 个槽位绑哪 32 个资源",其余的资源这一帧被忽略(或降级用别的方式访问)。**路径二**,升级到 Vulkan / D3D12 / bindless:**几乎无限的槽位**——shader 声明 `sampler2D textures[]` 数组,大小几万,CPU 把所有资源写进一个 descriptor array,shader 通过 index 访问。

Casey 这一天走第一条路。理由是 Handmade Hero 还在 OpenGL 上,bindless 是 Vulkan 后续工作。但**调度**这件事是核心概念——无论用 OpenGL 还是 Vulkan,你迟早要面对"按重要性管理有限资源"。

这条概念在计算机科学里极其普适。CPU 的 L1 cache 装不下所有内存,要 LRU 调度;OS 的物理内存装不下所有进程的虚拟页,要 page replacement;数据库的 buffer pool 装不下整个表,要淘汰策略。**资源调度是计算的元命题**。今天我们用 GPU binding 做案例,但你在任何领域都会再遇到。

完成这一天之后,你具备:

- **理解 GPU 资源调度的约束**:OpenGL 32 个 texture unit、Vulkan descriptor set 上限、D3D12 root signature 约束
- **能用 LRU / priority 算法管理 GPU 槽位**:把"重要性"概念量化、决策、实施
- **看懂工业引擎的资源调度层**:Unreal 的 texture streaming、Frostbite 的 mesh streaming 都遵循同一套
- **理解现代 bindless 设计的动机**:为什么 Vulkan 1.2 推 `VK_EXT_descriptor_indexing`,bindless 解决了什么
- **熟悉 GPU 异步执行对调度的影响**:为什么不能在 GPU 用 buffer 时改它,double/triple buffering 的来源

## 1 · Casey 今天做了什么

Casey 的实现:

第一步,他维护一个 **slot pool**——8 个固定槽位(0..7),每个槽位绑一个 chunk 的 voxel texture。

第二步,每帧**重评估**:遍历玩家可见 chunk,按"距离玩家"排序,选最近 8 个 chunk 占据槽位。

第三步,**LRU** 数据:每个槽位记上次访问时间,如果某槽位长时间没用,被新 chunk 替换。

第四步,shader 通过 binding index 访问对应 chunk——`textures[slot_index]`。

视频里他演示:玩家从一个房间走到另一个,槽位逐渐"换人"——旧房间 chunk 让位给新房间。

### 类比:电影院座位

我打个比方。想象你经营一家只有 8 个 VIP 座位的电影院。今天有 100 部电影想放映,但只能同时放 8 部。**所有 100 部电影都有观众**,而电影院只能让 8 部进入 VIP 厅——剩下 92 部只能在普通厅(低 LOD,模糊的近似光照)放映。

你怎么决定哪 8 部进 VIP?最直觉的策略是**"当前观众最多"的 8 部占座**——这对应游戏里"距离玩家最近的 8 个 chunk 占据 slot"。当一部电影的观众走了(玩家走远了,chunk 不再活跃),新电影可以换上来(新 chunk 进 slot)。

但这里有个微妙问题:**电影不能瞬间换**。VIP 厅里在放一部 2 小时电影,你 30 分钟后想换新电影,得等当前观众看完。**GPU 也是**——你给 GPU 提交一个 draw call,GPU 在后台执行需要时间(异步)。如果你提交 draw call 后立刻改 texture binding,可能 GPU 看到一半新一半旧——破图。这就是为什么需要 **double buffering**(双缓冲)或 **ring buffer**(环形缓冲):N 个槽位轮换,等 GPU 处理完旧帧再用新帧的数据。

LRU(Least Recently Used,最久未用)是另一层策略。**不只是"当前是否活跃",还要看"上次被用是什么时候"**。这处理一种情况:某 chunk 上次活跃是 100 帧前,现在某新 chunk 要进来——淘汰那个"100 帧前用过、之后没用过"的,而不是淘汰"刚用过但暂时空闲"的。LRU 假设**时间局部性**:刚用过的更可能再用。

更精细的策略是 **priority**(优先级)。不只是时间,还结合"距离玩家"、"是否在视野内"、"是否在 frustum 里"。远的 chunk 即便刚被 sample 过(时间局部性强),重要性也不如视野中心的新 chunk。Unreal 用这种 priority 调度 texture streaming。

类比的关键洞察:**调度是 trade-off**。你不可能"完美"调度(那需要预知未来),只能用启发式。每种启发式有自己的偏差:LRU 偏向"过去",priority 偏向"重要性",FIFO 偏向"公平"。工业系统经常**混合多种**——例如 priority 优先,相同 priority 时 LRU。

### 2.2 GPU binding 模型:从 OpenGL 到 Vulkan

理解 slot pool,要先理解 GPU 怎么"看见"资源。让我把 OpenGL、Vulkan、D3D12 的 binding 模型并排对比。

**OpenGL(1992 设计)**:固定数量的 binding point。`glActiveTexture(GL_TEXTURE0); glBindTexture(GL_TEXTURE_2D, tex_id);` 把一个 texture 绑到 unit 0。Shader 里 `uniform sampler2D my_tex` 通过 `glUniform1i(loc, 0)` 知道"my_tex 在 unit 0"。Unit 数量是 `GL_MAX_TEXTURE_IMAGE_UNITS`,OpenGL 4.x 至少 32,实际硬件 80-192。但**32 是 cross-platform 的安全上限**,超过这个数字可能在某些显卡失败。

**Vulkan(2016)**:descriptor set + binding。一个 descriptor set 是一组 binding,shader 通过 `layout(set=0, binding=0)` 引用。每个 binding 可以是单个资源、数组(uncapped,但有 `maxPerStageDescriptorSampledImages` 限制,通常几百万)。Vulkan 1.2 的 `VK_EXT_descriptor_indexing` 把这个限制推得很大,基本可以认为无限。

**D3D12(2015)**:root signature。root signature 是 shader 访问资源的"目录",最多 64 DWORD。一个 descriptor table 占 1 DWORD,指向 descriptor heap 的一段。Descriptor heap 大小可以很大(几百万 descriptors)。设计上和 Vulkan 类似,允许大数组 binding。

**为什么早期 GPU 限制大**?因为 binding 不只是"指针",还涉及 GPU 内部资源——texture descriptor 在 GPU 上是几字节的小结构(format、size、filter mode、addressing mode)。Shader 流式访问 texture 时,GPU 预取 descriptor 到 register file。Register file 有限,所以 binding 数量有限。现代 GPU 把 descriptor heap 放到 main memory,通过 cache 访问,允许 descriptor 数量爆炸(几百万),代价是 cache miss 时延迟。

### 2.3 LRU 算法的第一性原理

LRU 这个算法为什么 work?让我从 CPU cache 说起,你会发现 GPU slot pool 是同一个原理。

CPU cache(L1 / L2 / L3)装不下所有内存。Cache miss 比命中慢 100-1000 倍。**怎么决定哪些数据在 cache 里**?1970 年 Mattson 在 IBM 发明 LRU:每次访问一个地址,记下当前时间。当要淘汰一个时,选"最久没访问"的那个。

LRU 的理论基础是**时间局部性**(temporal locality):**刚被访问的数据,大概率很快会被再次访问**。为什么这条经验法则成立?

考虑程序的行为模式。一个 `for i in 0..N` 的循环里,`array[i]` 是顺序访问——刚刚访问的元素马上还会被再次访问(下一轮循环)。一个哈希表的查询,通常多次查同一 key。一个函数的局部变量,函数返回前一直被访问。

反例:大数组的 random walk——每次访问完全随机,LRU 失效。但实际程序极少纯随机,大多有局部性。所以 LRU 在实践中表现好。

**LRU 的实现挑战**:精确 LRU 需要每次访问都更新时间戳,代价大。工业实现经常用 **clock algorithm**(时钟算法)或 **2-bit LRU**(每条 cache line 2 bit,用概率近似 LRU)。Linux page cache 用 active/inactive 双 LRU 列表,把"热门"和"冷"分开。

回到 GPU slot pool:slot 数量小(8-32),精确 LRU 完全可行。每个 slot 记 `last_used: Instant`,淘汰时 linear search 找最小。这是 O(N) 但 N 很小,不是瓶颈。

### 2.4 Ring buffer 和 GPU 异步执行

为什么 slot pool 配 ring buffer?这个话题比 LRU 还核心,因为它解释了 GPU 编程的**异步**本质。

CPU 编程是**同步**的——你调 `printf("hello")`,函数返回时,"hello" 已经写到 stdout(可能 buffered,但函数返回意味着 I/O 操作完成或排队)。但 GPU 编程是**异步**的——你调 `vkCmdDraw(cmd_buf, ...)`,函数立刻返回,但 GPU 还没开始画!这个 draw command 进了 GPU command queue,GPU 自己的调度器决定何时执行。

异步的好处:**CPU 和 GPU 并行工作**。CPU 准备下一帧的数据,GPU 画当前帧。理论上 100% 并行,帧时间 = max(CPU 时间, GPU 时间),不是和。

但异步的坏处:**你不能立刻修改 GPU 正在用的资源**。例如:

```rust
// CPU 端
let verts = generate_ui_vertices();
write_to_gpu_buffer(&buffer, &verts);   // 写 buffer
issue_draw_call(&buffer);                // 提交 draw,GPU 异步开始
// CPU 立刻到下一行,但 GPU 还没开始 draw

let verts2 = generate_next_vertices();
write_to_gpu_buffer(&buffer, &verts2);   // 写同一个 buffer
// 这时 GPU 可能才刚开始上一次的 draw,看到的是 verts2!
```

这个 race condition 叫 **hazard**。解决方案:**多个 buffer,轮流用**。

```rust
let buffers = [buffer0, buffer1, buffer2];  // ring buffer,3 个 slot
let mut current = 0;

fn frame() {
    let buf = &buffers[current];
    write_to_gpu_buffer(buf, &vertices);
    issue_draw_call(buf);
    current = (current + 1) % 3;  // 下一帧用下一个 buffer
}
```

为什么 3 个?**frame latency** = 3 意味着 GPU 最多滞后 CPU 3 帧。frame N 用 buffer 0,GPU 开始处理 frame N;frame N+1 用 buffer 1,GPU 还在处理 frame N(buffer 0),互不干扰;frame N+2 用 buffer 2;frame N+3 又用 buffer 0——此时 GPU 早处理完 frame N(3 帧前 = 50ms,远超单帧 GPU 时间)。所以 buffer 0 可以安全复用。

NVIDIA 推荐 N=3 给"绝对安全",N=2 在大多数场景够用(2 帧 = 33ms)。Handmade Hero Casey 用 N=3。

**Slot pool 和 ring buffer 的关系**:slot pool 解决的是"shader 同时能看见多少资源",ring buffer 解决的是"GPU 异步执行下 buffer 怎么安全复用"。两者是**正交问题**。今天 Casey 在 slot pool 里加上 `in_flight` 标记,把"GPU 还在用这个 slot"考虑进去——这是 ring buffer 思想在 slot pool 上的应用。

### 2.5 Bindless:让"slot 调度"这件事消失

现代 GPU 的 bindless 模型彻底消除"slot 调度"问题。让我深入讲讲,你会理解为什么 Vulkan 1.2 把它作为 flagship 特性。

**Bindless 的核心思想**:shader 不绑定单个 texture,而是访问一个 **texture array**——一个数组,大小几万到几百万。CPU 把所有 texture 注册到 descriptor heap,shader 通过 `textures[index]` 访问,index 是运行时变量。

```glsl
// Bindless GLSL(VK_EXT_descriptor_indexing)
#extension GL_EXT_nonuniform_qualifier : enable

layout(set = 0, binding = 0) uniform sampler2D textures[];  // 几百万个

vec4 sample_at(uint idx, vec2 uv) {
    return texture(textures[nonuniformEXT(idx)], uv);
}
```

`nonuniformEXT(idx)` 告诉 GPU "idx 在 warp 内可能不同"——这是 bindless 的微妙之处。Warp(或 wave,32 个线程一组)内的线程如果都访问同一个 texture,GPU 可以 batch fetch;如果访问不同 texture,需要逐线程 fetch。Bindless 允许 divergence,代价是性能可能下降。

**Bindless 的优势**:
- 不需要 slot 调度,任何资源随时可访问
- CPU 端 descriptor heap 可以一次性建好,不用每帧 rebuild bind group
- 减少 driver overhead

**Bindless 的约束**:
- GPU 必须支持(Vulkan 1.2+ 或 VK_EXT_descriptor_indexing 扩展)
- Descriptor heap 大小仍有限(几百万,但够大)
- 性能可能略低(divergent access)
- Debug 难(数组越界不会立即崩,可能 sample 到垃圾数据)

工业实践:Unreal Engine 5 的 Nanite 和 Lumen 用 bindless 处理海量几何和光照。Steam Deck / Switch 2 等现代主机全支持。Casey 这天用 slot pool 是 OpenGL 兼容性考虑,后续切到 Vulkan 后可以改 bindless。

### 2.6 把这些概念落成代码

让我把所有概念整合——priority 选择、LRU 淘汰、ring buffer 防止 race condition。先看最朴素的版本,再逐层加细节。

**朴素 LRU slot pool**:

```rust
// ChunkId 是 chunk 的唯一标识(通常是 hash 或整数坐标)
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
struct ChunkId(u64);

struct ProbeSlotPool {
    slots: [Option<ChunkId>; NUM_SLOTS],
    last_used: [std::time::Instant; NUM_SLOTS],
}

const NUM_SLOTS: usize = 8;  // OpenGL 安全上限内

impl ProbeSlotPool {
    // 给一个 chunk 分配 slot,返回 slot index
    fn allocate(&mut self, chunk: ChunkId) -> usize {
        // 策略 1:有空 slot?直接用(避免淘汰)
        if let Some(i) = self.slots.iter().position(|s| s.is_none()) {
            self.slots[i] = Some(chunk);
            self.last_used[i] = std::time::Instant::now();
            return i;
        }

        // 策略 2:没空 slot,LRU 淘汰——找"最久没用"的 slot
        let lru_idx = (0..NUM_SLOTS)
            .min_by_key(|&i| self.last_used[i])  // 最小 = 最旧
            .unwrap();
        self.slots[lru_idx] = Some(chunk);
        self.last_used[lru_idx] = std::time::Instant::now();
        lru_idx
    }

    // 高层 API:找已有 slot,或分配新 slot
    fn find_or_allocate(&mut self, chunk: ChunkId) -> usize {
        // 先看 chunk 是否已经在某 slot——避免重复分配
        if let Some(i) = self.slots.iter().position(|s| *s == Some(chunk)) {
            self.last_used[i] = std::time::Instant::now();  // 更新时间,防 LRU 淘汰
            return i;
        }
        self.allocate(chunk)
    }
}
```

**每帧使用**:

```rust
fn frame(player_pos: Vec3, pool: &mut ProbeSlotPool) {
    // 1. 找玩家附近的 chunks(用 spatial hash)
    let nearby_chunks = find_chunks_near(player_pos, RADIUS);
    // nearby_chunks 大概 10-30 个,NUM_SLOTS=8,可能装不下

    // 2. 排序——按距离玩家近到远(让近的优先占 slot)
    let mut sorted: Vec<_> = nearby_chunks.into_iter()
        .map(|c| (c, distance(player_pos, c.center())))
        .collect();
    sorted.sort_by_key(|&(_, d)| d);

    // 3. 分配 slots——前 NUM_SLOTS 个进入 slot pool
    let mut slot_mapping = vec![];
    for (chunk_id, _dist) in sorted.into_iter().take(NUM_SLOTS) {
        let slot = pool.find_or_allocate(chunk_id);
        slot_mapping.push((chunk_id, slot));
    }

    // 4. GPU 端:把 chunk textures 绑到 slots
    for (chunk_id, slot) in &slot_mapping {
        bind_texture_to_slot(chunk_id, *slot);
        // OpenGL: glActiveTexture(GL_TEXTURE0 + slot); glBindTexture(GL_TEXTURE_3D, chunk_tex);
    }

    // 5. 没进入 slot 的 chunks,这一帧 shader 看不见——退化用 fallback(比如最近的 slot chunk)
}
```

这里关键的工程权衡:**slots 装"近的"还是"刚用的"**?Casey 选择"近的"——因为玩家视野中心最需要高精度光照。LRU 在这里只是**当多个等距时**做选择。这是 priority + LRU 的混合。

## 3 · 四域深入

### 3.1 · 游戏编程视角

资源调度的工业做法:

- **Texture streaming**:Unreal 的 VT,按需加载 texture 到有限 GPU slot
- **Mesh streaming**:FarCry 的 GeoCache,只加载可见 mesh
- **Audio streaming**:游戏音效不全加载,按距离/可见性加载
- **Animation streaming**:动作多的角色,按需加载 animation clip

槽位管理是游戏引擎的核心系统。Unreal 用 LRU + priority,Frostbite 用 hierarchical(LOD + slot)。

### 3.2 · 图形学视角

GPU 资源 binding 演化:

- **OpenGL 1.x(1992)**:无 binding 概念,glTexImage2D 直接画
- **OpenGL 2.x**:texture unit,固定 4 个
- **OpenGL 3.x+**:arbiter textures,32+ units
- **OpenGL 4.x(2010)**:bindless textures(扩展)
- **Vulkan(2016)**:descriptor set + dynamic indexing
- **Vulkan 1.2(2020)**:`VK_EXT_descriptor_indexing`,工业级 bindless

bindless 是未来。Casey 的 slot pool 是兼容性考虑。

### 3.3 · Linux 系统编程视角

资源调度是 OS 核心:

- **Page replacement**:LRU / Clock / ARC
- **File system cache**:Linux page cache,LRU
- **Network socket buffer**:有限,需要 flow control
- **CPU register allocation**:编译器把 hot 变量放 register,cold 放 memory

LRU 算法的核心是"时间局部性"——刚用过的数据更可能再用。这是 von Neumann 架构的普遍假设。

### 3.4 · Rust 生态视角

Rust 表达 slot pool:

```rust
struct SlotPool<T> {
    slots: Vec<Option<T>>,
    last_used: Vec<std::time::Instant>,
}

impl<T> SlotPool<T> {
    fn new(size: usize) -> Self {
        SlotPool {
            slots: vec![None; size],
            last_used: vec![std::time::Instant::now(); size],
        }
    }
}
```

如果要用 GPU,`wgpu::BindGroup` 可以模拟槽位:

```rust
let bind_group = device.create_bind_group(&wgpu::BindGroupDescriptor {

        wgpu::BindGroupEntry { binding: 0, resource: BindingResource::TextureView(&chunk_textures[0]) },

```

但每帧重建 bind group 慢。更好用 `wgpu::BindGroupLayout` with `dynamic_offset`,运行时改 offset。

### Lv1 · 概念辨析

**题**:为什么不用 1000 个固定槽位,省得做调度?

**参考解答**:(1) GPU binding 数量限制(OpenGL 32,Vulkan descriptor set 也有限);(2) 即使支持 1000,每帧 rebuild bind group 1000 entries 慢;(3) 大部分 slot 可能没活跃 chunk,浪费 GPU register / cache。LRU 调度让"当前最相关"的资源用 slot,冷数据走 fallback(如降低 LOD 或直接黑)。这和 CPU cache 一样——固定大小,LRU 替换。

### Lv2 · 动手实践

**题**:实现 LRU slot pool,测试淘汰行为。

要求:
- 4 个 slot
- 访问 10 个 chunk(A B C D E A B C D E)
- 打印每次访问后 slot 状态
- 验证 LRU 正确淘汰

**参考解答**:

```rust
use std::time::{Duration, Instant};

struct SlotPool {
    slots: Vec<Option<char>>,
    last_used: Vec<Instant>,
    size: usize,
}

impl SlotPool {
    fn new(size: usize) -> Self {
        SlotPool {
            slots: vec![None; size],
            last_used: vec![Instant::now(); size],
            size,
        }
    }

    fn access(&mut self, chunk: char) -> usize {
        let now = Instant::now() + Duration::from_millis(10);  // 模拟时间流逝

        // 已存在?
        if let Some(i) = self.slots.iter().position(|s| *s == Some(chunk)) {
            self.last_used[i] = now;
            return i;
        }

        // 空 slot?
        if let Some(i) = self.slots.iter().position(|s| s.is_none()) {
            self.slots[i] = Some(chunk);
            self.last_used[i] = now;
            return i;
        }

        // LRU 淘汰
        let lru_idx = (0..self.size)
            .min_by_key(|&i| self.last_used[i])
            .unwrap();
        println!("  Evict {} from slot {}", self.slots[lru_idx].unwrap(), lru_idx);
        self.slots[lru_idx] = Some(chunk);
        self.last_used[lru_idx] = now;
        lru_idx
    }

    fn dump(&self) {
        println!("Slots: {:?}", self.slots);
    }
}

fn main() {
    let mut pool = SlotPool::new(4);
    for c in "ABCDEABCDE".chars() {
        print!("Access {}: ", c);
        pool.access(c);
        pool.dump();
    }
}
```

## 8 · Rust / Arch 落地代码

完整 slot pool + GPU binding 模拟:

```rust
use std::time::{Duration, Instant};

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
struct ChunkId(u64);

struct SlotPool {
    slots: Vec<Option<ChunkId>>,
    last_used: Vec<Instant>,
    in_flight: Vec<bool>,  // GPU 是否在用这个 slot
}

impl SlotPool {
    fn new(size: usize) -> Self {
        SlotPool {
            slots: vec![None; size],
            last_used: vec![Instant::now() - Duration::from_secs(60); size],
            in_flight: vec![false; size],
        }
    }

    fn access(&mut self, chunk: ChunkId, now: Instant) -> usize {
        // 已分配?
        if let Some(i) = self.slots.iter().position(|s| *s == Some(chunk)) {
            self.last_used[i] = now;
            return i;
        }

        // 找没 in_flight 的 LRU slot
        let mut candidates: Vec<usize> = (0..self.slots.len())
            .filter(|&i| !self.in_flight[i])
            .collect();
        candidates.sort_by_key(|&i| self.last_used[i]);

        let target = candidates[0];

        // 模拟 GPU unbind 旧 chunk
        if let Some(old) = self.slots[target] {
            println!("  Slot {}: unbind {} (was unused for {:?})",
                target, old.0, now.duration_since(self.last_used[target]));
        }

        // 绑新 chunk
        self.slots[target] = Some(chunk);
        self.last_used[target] = now;
        println!("  Slot {}: bind {}", target, chunk.0);

        target
    }

    fn mark_in_flight(&mut self, slot: usize) {
        self.in_flight[slot] = true;
    }

    fn mark_done(&mut self, slot: usize) {
        self.in_flight[slot] = false;
    }
}

fn main() {
    let mut pool = SlotPool::new(8);
    let mut simulated_time = Instant::now();

    // 模拟 5 帧,玩家移动,附近 chunk 变化
    let frames: Vec<Vec<ChunkId>> = vec![
        vec![ChunkId(1), ChunkId(2), ChunkId(3)],
        vec![ChunkId(1), ChunkId(2), ChunkId(3), ChunkId(4)],
        vec![ChunkId(2), ChunkId(3), ChunkId(4), ChunkId(5)],
        vec![ChunkId(3), ChunkId(4), ChunkId(5), ChunkId(6)],
        vec![ChunkId(20), ChunkId(21), ChunkId(22)],  // 远跳
    ];

    for (frame, chunks) in frames.iter().enumerate() {
        println!("\n=== Frame {} ===", frame);
        simulated_time += Duration::from_millis(16);

        // 前一帧的 slot 标记 done(GPU 完成)
        for i in 0..8 {
            pool.mark_done(i);
        }

        // 为这帧的 chunk 分配 slot
        for chunk in chunks {
            let _slot = pool.access(*chunk, simulated_time);
        }

        // 标记 in_flight(这帧 GPU 在用)
        for slot in 0..8 {
            if pool.slots[slot].is_some() {
                pool.mark_in_flight(slot);
            }
        }
    }
}
```
