# Day 530 · 写大 PNG 与字体超采样

> Day 529 你写了 PNG 写入器,跑通了小图。Day 530 Casey 把它推到极限——**写一张非常大的 PNG**(几千乘几千像素),并且**字体超采样**(在 4x 分辨率栅格化后降采样,得到更平滑的边缘)。这两件事各自挑战一个工程难点:大 PNG 暴露内存和 IDAT 分块问题,超采样暴露抗锯齿数学。

## 0 · 为什么要有这一天

写一张 4096×4096 的 RGB PNG,raw 数据是 4096×4096×3 = 50 MB。如果用 Day 529 的写入器,**一次性把所有数据放到一个 IDAT chunk**——理论上 PNG 规范允许,但实践中很多解码器对单 chunk 大小有限制(常见 8 MB 到 2 GB)。Casey 这天要支持**多 IDAT 分块**,每块不超过几 MB。

字体超采样(supersampling)是另一回事。栅格化矢量字体时,每个像素要么填要么不填,边缘锯齿明显。解决方案:在 4x 分辨率栅格化(每个原像素 = 4×4 = 16 个子像素),然后降采样(取 16 个子像素的平均),得到带 alpha 的边缘像素。这是抗锯齿(anti-aliasing)的最朴素形式。

这两件事放在一起,因为它们都属于"质量提升"——大 PNG 是为了支持高分辨率字体 atlas,字体超采样是为了让字体边缘平滑。Casey 把它们一起做,因为新增的字体 atlas 因为超采样变成大 PNG,需要 IDAT 分块支持。

#### 工业级抗锯齿:除了 supersampling 还有什么

让我把抗锯齿(anti-aliasing,AA)的全家桶列出来,Casey 用的 supersampling 是其中一种:

| 方法 | 原理 | 优点 | 缺点 | 用在哪 |
|---|---|---|---|---|
| **SSAA**(Supersampling AA) | 在 N×N 分辨率渲染,降采样 | 质量最高,简单 | 慢(N² 倍计算) | 离线渲染、字体 |
| **MSAA**(Multisample AA) | 每像素 N 个 coverage sample,只对几何边缘 AA | 比 SSAA 快,质量好 | 不抗锯齿 shader 内部 | 3D 游戏(GPU 硬件) |
| **FXAA**(Fast Approximate AA) | 后处理:检测边缘,blur | 极快,任何场景可用 | 模糊细节 | 控制台游戏 |
| **TAA**(Temporal AA) | 多帧累积,运动补偿 | 质量好,无边缘检测 | 移动有鬼影 | 现代 3D 引擎标配 |
| **SMAA**(Enhanced Subpixel AA) | 后处理 + 子像素信息 | 比 FXAA 锐利 | 复杂 | 高质量 PC 游戏 |
| **DLSS / FSR**(AI 超分) | AI 重建 | 同时 AA + 超分 | 依赖特定 GPU | 现代 AAA 游戏 |

Casey 用 SSAA(超采样),因为字体是离线渲染,不在乎速度。**3D 游戏运行时用 MSAA 或 TAA**,因为 SSAA 太慢。学会区分这些,你才能正确选择。

#### 大文件分块:流式处理的通用模式

IDAT 分块背后是一个跨学科通用模式:**处理大文件时,永远要流式处理,不要一次性加载**。这条原则适用于:

- **PNG 写入**(本日):数据切片成多个 IDAT
- **PNG 读取**(Day 453):流式解码,不要一次性加载所有 IDAT
- **视频流**(YouTube、Netflix):chunked transfer encoding,边下边播
- **数据库 dump**(mysqldump):分批读,避免 OOM
- **机器学习训练数据**:stream dataset,不要 load 全部到内存
- **Git push 大仓库**:Git 的 packfile 协议分块传输

工业级代码必须掌握这种"流式思维"。Casey 在 HH 反复演示——他的 PNG decoder/encoder 都是流式的,his WAV loader 也是流式的。这种习惯让代码能 scale 到任何大小的输入。

完成这一天之后,你具备:

- 能处理"大文件分块写入"的工程模式
- 理解超采样的数学:子像素平均 = box filter
- 知道多种抗锯齿算法及其权衡
- 学会流式思维:不一次性加载大文件

## 2 · 心智模型

### 类比:用更多颗粒度的沙子堆字

想象你在沙盘上写字,沙粒很粗(每颗 5 毫米),字的边缘看起来锯齿明显——一颗沙子要么在字里要么不在。换成细沙(每颗 1 毫米),边缘锯齿变细。但你不想用细沙堆——太慢。

超采样的折衷:**用粗沙堆,但每颗粗沙由 16 颗细沙组成**。计算每颗粗沙"在字里"的程度 = 16 颗细沙里有几颗在字里 / 16。一颗粗沙可能有 12/16 = 75% 在字里,边缘像素就是 75% alpha,看起来平滑。

### 严谨展开:IDAT 分块

PNG 规范允许多 IDAT chunk。raw 图像数据被切成连续段,每段 zlib 压缩后放进一个 IDAT。**注意**:多 IDAT 的 zlib 流是**连续的**,不是每 chunk 重新初始化 zlib——raw 数据被作为一个整体 zlib 压缩,压缩后的字节流被切成多段放进多 IDAT。

实现:

```rust
// 1. 把 raw 数据 zlib 压缩
let mut encoder = ZlibEncoder::new(Vec::new(), Compression::default());
encoder.write_all(&raw_data)?;
let compressed = encoder.finish()?;

// 2. 把 compressed 切成 1MB 段,每段一个 IDAT
const CHUNK_SIZE: usize = 1024 * 1024;  // 1 MB
for chunk in compressed.chunks(CHUNK_SIZE) {
    write_chunk(&mut png, b"IDAT", chunk);
}

// 3. IEND 必须在所有 IDAT 之后
write_chunk(&mut png, b"IEND", &[]);
```

decoder 端:循环读 IDAT chunk,把它们的 data 拼起来,得到完整 zlib 流,然后解压。

### 超采样的数学

box filter 降采样:

```
原像素 (x, y) 的颜色 = average(子像素 (4x, 4y), (4x+1, 4y), ..., (4x+3, 4y+3))
                    = (1/16) * sum(sub_pixels)
```

每个原像素对应 4×4 = 16 个子像素,平均值是 box filter。这是最简单的低通滤波,效果是把高频锯齿"模糊掉"。

更高级的降采样滤波:Gaussian、Lanczos、Mitchell。它们给子像素不同权重(中心权重高),边缘更平滑但计算更复杂。Casey 用 box filter,够用且快。

#### 为什么 box filter 是"低通滤波"

让我把"box filter = 低通滤波"这件事讲清楚,因为它是一切抗锯齿、抗噪、抗混叠理论的基石。

信号处理理论(Nyquist-Shannon):一个数字信号能表示的最高频率 = 采样率 / 2。原像素网格的"采样率"是每像素 1 次,所以能表示的最高频率 = 0.5 cycle/像素。如果原信号里有高于 0.5 cycle/像素的频率,会发生**混叠(aliasing)**——高频"伪装"成低频,视觉上就是锯齿/摩尔纹。

字体矢量曲线包含无限高频率(边缘是阶跃,数学上频率无穷)。直接在原分辨率栅格化,超过 Nyquist 的部分变成锯齿。

解决:**先低通滤波,滤掉高频,再降采样**。box filter 就是简单的低通——它把 16 个子像素平均,等价于"在原信号上用一个 4×4 的方框卷积",频域上等价于 sinc 函数(主瓣宽,衰减高频)。所以 box filter 滤掉了大部分高于 Nyquist 的频率,锯齿大幅减少。

工业级降采样用 Gaussian / Lanczos / Mitchell 是因为它们的频率响应更"干净"——box filter 在频域有 sinc 副瓣,会留下一些 ringing(振铃)伪影。但这些滤波器计算更复杂,Casey 用 box filter 是工程权衡。

#### Box filter 的实现

实现:

```rust
fn supersample_downsample(
    high_res: &[u8],  // 4W × 4H
    w4: u32, h4: u32,
) -> Vec<u8> {  // W × H
    let w = w4 / 4;
    let h = h4 / 4;
    let mut result = vec![0u8; (w * h) as usize];
    
    for y in 0..h {
        for x in 0..w {
            let mut sum: u32 = 0;
            for sy in 0..4 {
                for sx in 0..4 {
                    let hi_x = x * 4 + sx;
                    let hi_y = y * 4 + sy;
                    sum += high_res[(hi_y * w4 + hi_x) as usize] as u32;
                }
            }
            result[(y * w + x) as usize] = (sum / 16) as u8;
        }
    }
    result
}
```

### 抗锯齿算法对比

| 算法 | 描述 | 质量 | 性能 |
|---|---|---|---|
| 无 AA | 0 或 1 | 锯齿明显 | 最快 |
| SSAA 4x(超采样) | 4x4 子像素平均 | 好 | 慢(16x) |
| MSAA | 仅几何边缘超采样 | 中 | 中(2-4x 开销) |
| FXAA | 后处理 filter | 中 | 快 |
| TAA | 时间累积 | 好 | 中 |

Casey 用 SSAA 4x——最朴素也最好理解。

### 3.1 · 游戏编程视角

游戏渲染的抗锯齿:MSAA(几何级)、FXAA(后处理)、TAA(时间累积)、DLSS(AI 超分)。每种都有权衡。

### 3.2 · 图形学视角

GPU 上的抗锯齿:MSAA 在 fragment shader 之前对几何边缘超采样,纹理内部不超采样。这是为什么 MSAA 比 SSAA 快——大部分像素不用 4x 计算。

Subpixel rendering(LCD 屏幕特有):利用 RGB 子像素排列,提高水平分辨率。Apple 和 Microsoft 都做过,但有专利问题。

#### MSAA 的具体原理

让我把 MSAA(Multisample Anti-Aliasing)讲清楚,因为它是 GPU 抗锯齿的核心技术,Day 552-553 会用到。

MSAA 的核心想法:**几何边缘 AA,shader 只算一次**。具体:

- 每个像素有 N 个**子采样点**(subsample),如 4x MSAA 有 4 个子采样点
- fragment shader 对每像素只跑**一次**(关键省时)
- 但 stencil/depth test 对每个子采样点单独做
- 几何覆盖(coverage)也是每子采样点判断:子采样点在三角形内 → 该子采样点的颜色 = shader 输出;否则 = 背景
- 最后 resolve:像素颜色 = (covered subsamples 数量 / 总 subsamples) × foreground + (其余) × background

对比 SSAA(SSAA 是 shader 跑 N 次,每个子像素一次),MSAA 省了 shader 计算。SSAA 抗锯齿所有锯齿(包括 shader 内部,如高分辨率纹理),MSAA 只抗锯齿几何边缘。

GPU 硬件支持:OpenGL `glEnable(GL_MULTISAMPLE)`,Vulkan `VkSampleCountFlagBits::VK_SAMPLE_COUNT_4_BIT`。wgpu 的 `MSAASampleCount` 在 surface 配置里设。

工业级 3D 引擎(Unity、Unreal、bevy)默认开 MSAA。Casey 在 HH 不用 GPU,所以也不需要 MSAA——他的 2D 软件渲染里字体超采样是软件 SSAA 等价。

#### Depth peel MSAA:Phase 7 后续的预告

Phase 7 后半部分(Day 552+)会涉及 depth peel MSAA——这是 MSAA 的一个高级变种,用于顺序无关的透明渲染(OIT, Order-Independent Transparency)。标准 MSAA 不能正确处理透明物体(因为透明需要按深度排序混合)。Depth peel 算法通过多次渲染,每次"剥掉"最前一层,得到正确排序的透明层。

你今天学的 box filter 和子采样概念是 depth peel 的基础——子采样点、覆盖率、深度比较都是同一套数学。所以这一天不仅是字体抗锯齿,也是后续 GPU 高级渲染的预科。

#### FreeType 的 hinting 和 AA

让我解释 Linux 字体渲染的两个核心参数:

**Hinting**:矢量字体在小字号(8-16px)时,如果不调整,笔画会模糊或缺损。Hinting 是 TTF 字体内嵌的指令,告诉栅格化器"在小字号时把这条线对齐到像素网格"。结果:小字号字体清晰,但失去部分字形细节。

FreeType 的 hinting 模式:
- `FT_LOAD_TARGET_NORMAL` —— 默认 hinting
- `FT_LOAD_TARGET_LIGHT` —— 轻量 hinting(只 hint 垂直方向)
- `FT_LOAD_TARGET_MONO` —— 黑白(无 AA)
- `FT_LOAD_NO_HINTING` —— 不 hinting(精确但模糊)

**Subpixel rendering**:LCD 屏幕每个像素是 RGB 三色 stripe。标准 AA 把像素当作整体,subpixel 把 RGB 当独立"子像素"——水平分辨率提高 3 倍。代价是颜色边缘有彩色 fringes(红/蓝条纹)。

Linux 字体渲染栈历史变迁:
- 1990s:X11 + FreeType(默认 hinting)
- 2000s:Fontconfig + Xft(可配置)
- 2010s:Cairo + FreeType + HarfBuzz(默认 subpixel)
- 2020s:Same + variable fonts 支持动态调整

Casey 用 FreeType 默认设置,够用。你的 Rust 项目用 `ab_glyph` 或 `rusttype`,这些库内部都封装了 FreeType 风格的栅格化。

## 5 · 对照与变奏

图像缩放和图像抗锯齿共享数学。Lanczos、Mitchell、Bicubic 都是采样理论的滤波器。它们的共同点:把高频信息(锯齿)从信号里去掉,留下低频(平滑)。

游戏里的 LOD(level of detail)也是同一原理——远处的物体用低频版本(低多边形、低纹理分辨率),近处用高频。这是采样理论在 3D 渲染中的应用。

### Lv1 · 概念辨析

**题**:超采样 4x 把字体栅格化的计算量乘以 16。这值得吗?为什么不用更快的方法?

**参考解答**:对于字体这种**静态资产**(开发期一次栅格化,运行时不再算),16x 计算量不是问题——你跑一次工具等几秒,产出资产永久使用。运行时性能不变。如果运行时栅格化(矢量字体),16x 开销就成问题,得用更聪明的算法(如 hinting + subpixel rendering)。Casey 选超采样是因为 HH 是离线工具,计算时间不重要,质量最重要。

### Lv2 · 动手实践

**题**:用 Rust 实现一个 4x 超采样的字体栅格化函数:输入字体大小 32,在 128x128 内栅格化,然后 box filter 降到 32x32,输出带 alpha 的位图。运行后:边缘像素的 alpha 是 0-255 的中间值(不是非 0 即 255)。

**参考解答**:

```rust
// 4x 超采样:32x32 字体 → 128x128 栅格化 → 32x32 降采样
fn rasterize_supersampled(
    font: &ab_glyph::FontRef,
    char_code: char,
    size: u32,
) -> Vec<u8> {
    let ss_factor = 4;
    let hi_size = size * ss_factor;
    
    let glyph_id = font.glyph_id(char_code);
    let glyph = glyph_id.with_scale(hi_size as f32);
    
    if let Some(outlined) = font.outline_glyph(glyph) {
        let bounds = outlined.px_bounds();
        let hi_w = bounds.width().max(1.0) as u32;
        let hi_h = bounds.height().max(1.0) as u32;
        
        // 高分辨率栅格化
        let mut hi_pixels = vec![0u8; (hi_w * hi_h) as usize];
        outlined.draw(|x, y, coverage| {
            hi_pixels[(y * hi_w + x) as usize] = (coverage * 255.0) as u8;
        });
        
        // box filter 降采样
        let lo_w = hi_w / ss_factor;
        let lo_h = hi_h / ss_factor;
        let mut lo_pixels = vec![0u8; (lo_w * lo_h) as usize];
        
        for ly in 0..lo_h {
            for lx in 0..lo_w {
                let mut sum: u32 = 0;
                for sy in 0..ss_factor {
                    for sx in 0..ss_factor {
                        let hx = lx * ss_factor + sx;
                        let hy = ly * ss_factor + sy;
                        if hx < hi_w && hy < hi_h {
                            sum += hi_pixels[(hy * hi_w + hx) as usize] as u32;
                        }
                    }
                }
                lo_pixels[(ly * lo_w + lx) as usize] = 
                    (sum / (ss_factor * ss_factor)) as u8;
            }
        }
        lo_pixels
    } else {
        Vec::new()
    }
}
```

为什么这么写:高分辨率栅格化用 `ab_glyph::FontRef` 的 scale 参数,通过 `with_scale` 直接控制。降采样是 16 个子像素求平均。box filter 是最简单的低通滤波,效果足够字体用。

**额外思考**:为什么 `ab_glyph` 内部已经做了 AA,我们还要超采样?因为 ab_glyph 的内部 AA 是 fixed-quality(每个像素 4 子采样),如果你要更高质量(16 子采样),就得手动超采样。这是工业级库的常见取舍——提供"够用"的默认行为,留给用户进阶控制。

**测试建议**:写一个测试用例,对比"无超采样"和"4x 超采样"两种模式下,字符 'A' 在 16px 时的边缘像素 alpha 分布。无超采样版本 alpha 是 0/255 二值,4x 超采样版本 alpha 是 0/64/128/192/255 等阶梯值。视觉上,4x 超采样的字符边缘平滑,无超采样的字符边缘锯齿明显。

### Lv3 · 迁移设计

**题**:你要给一段录音做"超采样降噪":用 4 倍频率采样(假设原始 44100 Hz → 176400 Hz),然后降采样回 44100 Hz。设计这个管线,要求:输入低质量 WAV,输出高质量 WAV。提示:音频降采样 = box filter on PCM samples,2D 降采样的 1D 版本。

**详细参考**:

1D box filter 比 2D 简单——每 4 个连续样本取平均:

```rust
fn downsample_audio_4x(samples: &[i16]) -> Vec<i16> {
    samples.chunks(4)
        .map(|chunk| {
            let sum: i32 = chunk.iter().map(|&s| s as i32).sum();
            (sum / 4) as i16
        })
        .collect()
}
```

这个简单实现有问题:**锯齿频率信号经过 4x 降采样会混叠**。专业做法是先做低通滤波(截止频率 = 新 Nyquist = 22050 Hz),然后降采样。这就是为什么专业音频重采样器(SoX、libsoxr)有几十个参数——核心都是"用什么低通滤波器"。

工业级音频重采样是 called **sample rate conversion**(SRC)。libsamplerate / libsoxr 是开源实现,质量比 box filter 高一个数量级。但 box filter 的思想(低通 + 降采样)是不变的。

## 8 · Rust / Arch 落地代码

```rust
// 大 PNG 写入器,支持多 IDAT 分块

use std::io::Write;
use byteorder::{BigEndian, WriteBytesExt};
use crc32fast::Hasher;
use flate2::write::ZlibEncoder;
use flate2::Compression;

const PNG_MAGIC: [u8; 8] = [0x89, b'P', b'N', b'G', 0x0D, 0x0A, 0x1A, 0x0A];
const IDAT_CHUNK_SIZE: usize = 1024 * 1024;  // 1 MB per IDAT

fn write_chunk(out: &mut Vec<u8>, chunk_type: &[u8; 4], data: &[u8]) {
    out.write_u32::<BigEndian>(data.len() as u32).unwrap();
    out.extend_from_slice(chunk_type);
    out.extend_from_slice(data);
    let mut h = Hasher::new();
    h.update(chunk_type);
    h.update(data);
    out.write_u32::<BigEndian>(h.finalize()).unwrap();
}

pub fn write_large_png(
    path: &str,
    width: u32,
    height: u32,
    pixels: &[u8],
) -> std::io::Result<()> {
    let mut png = Vec::new();
    png.extend_from_slice(&PNG_MAGIC);
    
    // IHDR
    let mut ihdr = Vec::with_capacity(13);
    ihdr.write_u32::<BigEndian>(width).unwrap();
    ihdr.write_u32::<BigEndian>(height).unwrap();
    ihdr.push(8); ihdr.push(2); ihdr.push(0); ihdr.push(0); ihdr.push(0);
    write_chunk(&mut png, b"IHDR", &ihdr);
    
    // raw 数据:每行加 filter byte
    let mut raw = Vec::with_capacity((height * (1 + width * 3)) as usize);
    for y in 0..height {
        raw.push(0);  // filter = None
        let start = (y * width * 3) as usize;
        let end = ((y + 1) * width * 3) as usize;
        raw.extend_from_slice(&pixels[start..end]);
    }
    
    // 整体 zlib 压缩
    let mut encoder = ZlibEncoder::new(Vec::new(), Compression::default());
    encoder.write_all(&raw)?;
    let compressed = encoder.finish()?;
    
    // 切成多个 IDAT(注意:不是每段单独 zlib,是同一段 zlib 流切片)
    for chunk in compressed.chunks(IDAT_CHUNK_SIZE) {
        write_chunk(&mut png, b"IDAT", chunk);
    }
    
    // IEND
    write_chunk(&mut png, b"IEND", &[]);
    
    std::fs::write(path, &png)
}

fn main() {
    // 生成 4096x4096 测试图(渐变)
    let width = 4096u32;
    let height = 4096u32;
    let pixels: Vec<u8> = (0..(width * height))
        .flat_map(|i| {
            let v = (i % 256) as u8;
            [v, v, v]  // 灰度
        })
        .collect();
    
    write_large_png("large.png", width, height, &pixels).unwrap();
    
    // 验证
    let output = std::process::Command::new("pngcheck")
        .arg("-v").arg("large.png")
        .output().unwrap();
    println!("{}", String::from_utf8_lossy(&output.stdout));
    
    let meta = std::fs::metadata("large.png").unwrap();
    println!("文件大小: {} MB", meta.len() / 1024 / 1024);
}
```

出错怎么办:

- **`pngcheck` 报 IDAT count mismatch**:你把多 IDAT 当独立 zlib 编码了。它们必须是同一段 zlib 流切片。
- **生成的图全黑**:filter byte 写错,或 raw data 索引错。
- **超采样图边缘仍是锯齿**:子像素的 coverage 没乘 255,直接取整数。
