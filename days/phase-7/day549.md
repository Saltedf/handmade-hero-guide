# Day 549 · 移除旧光照查询

> Day 547-548 搭了 voxel light probe 框架,但游戏代码里**还在用旧 mesh-based 光照查询**——新旧两套并存,既慢又难维护。Day 549 Casey 把所有旧光照查询删掉,**强制走新系统**,这是大重构的"破釜沉舟"时刻。

## 0 · 为什么要有这一天

### 真实场景:"新旧并存陷阱"的痛

你跟着 Casey 做到 Day 548。新系统(voxel light probe)搭好了——它能查询任意 world position 的光照,功能比旧的 mesh-based lighting 完整。但你**没删旧系统**——还让游戏代码继续调 `lighting_for_mesh` 旧函数。

接下来发生的事:

**第一周**:游戏跑得好,新旧两套都没 bug。你觉得"挺好"。

**第二周**:你想加新光照特性——动态阴影。你打开 shader 代码,发现有两个 path:mesh-based path 和 voxel-based path。你心想:"两个 path 都要加阴影吗?太麻烦了。先只在 mesh-based 加吧,反正 voxel-based 还没用上。"

**第三周**:玩家报 bug——某些场景光照颜色不对。你 debug,发现问题——mesh-based path 和 voxel-based path 给出不同结果,因为某处你只改了一个。游戏一会儿用 mesh-based(场景 A),一会儿用 voxel-based(场景 B),结果不一致。

**第四周**:你想"算了,把所有 mesh-based 删了,统一用 voxel-based"。但**你忘了哪些地方还在调 mesh-based**——codebase 太大,grep 也不全。你删了一处,游戏崩溃——别的地方还在调。回滚。

**第六周**:你被新旧并存拖死了。每次改光照,要么改两处(累),要么改一处(出错)。codebase 越来越乱。

这就是"新旧并存陷阱"。**Day 549 是 Casey 强制打破这个陷阱**——删除所有旧光照查询,新系统变成唯一路径。

### 为什么"破釜沉舟"在工程上是必要的

"破釜沉舟"出自项羽——把船砸了,把锅打破,士兵只能往前冲,不能后退。在工程上,这对应"主动断掉 fallback,强制走新路径"。

听起来危险,但实际**比保留 fallback 更安全**:

- **fallback 隐藏 bug**:新旧并存时,bug 可能只在某条路径出现,你测不到。强制走新路径,bug 立刻暴露。
- **fallback 制造惰性**:有 fallback 你就不会认真测试新系统。没 fallback 你必须测好。
- **fallback 阻碍架构演化**:新系统的优势可能依赖"旧系统不存在"——比如 voxel-based 想用稀疏数据结构,但 mesh-based 假设 dense,新旧并存让稀疏优化无法落地。

工业级的"破釜沉舟":
- **Python 2 → Python 3**:Python 团队宣布 2020 年停止维护 Python 2,强制用户迁移。期间痛苦,但最终 Python 3 普及。
- **Apple 从 PowerPC 转 Intel(2006),又从 Intel 转 ARM(2020)**:Apple 强制开发者重新编译所有 app,痛苦但必要。
- **Google 内部从 Perforce 转 Piper(Git-like)**:Google 一次性切换所有团队到新 VCS。
- **Microsoft Windows 弃用 IE,推 Edge**:Edge 早期不兼容 IE activeX,但强制用户切换。

这些都是大公司的"破釜沉舟"。Casey Day 549 是这个模式的教学版。

### 删除代码的心理障碍

很多程序员害怕删除代码。心理原因:

1. **"这是我辛辛苦苦写的"**:删了不甘心。**反驳**:code 不是资产,是负债——每行代码要测试、维护、读懂。删除是减债,不是损失。
2. **"万一以后还用呢"**:留着没害处。**反驳**:git history 永远保留,真要用再 cherry-pick。留在 main 是真害处。
3. **"删了我以后忘了怎么做"**:反驳:如果重要,文档化(不是死代码)。如果不重要,忘了正好。
4. **"删了破坏其他代码"**:反驳:这正是 Rust 编译器要解决的——删了立刻编译报错,你能找到所有受影响的地方。

工业界有个口号:**"好的程序员写代码,优秀的程序员删代码"**(attributed to Bill Gates)。这不是夸张——能用 1000 行解决的问题,不要用 10000 行。

## 2 · 心智模型

### 类比:搬家时的扔东西

你搬家时,把所有东西打包(新系统),然后**扔掉旧房子里的旧家具**(删旧代码)。如果你不扔,你既要维护新家具(新系统)又要管旧家具(旧代码),生活混乱。

但扔之前要确认:

- 新家具齐全(新系统功能完整)
- 没遗漏(所有调用点都迁到新系统)
- 试住过(测试过)

如果新家缺椅子(新系统有 bug),就别扔旧椅子(别删旧代码)。

### 严谨展开:用编译器辅助重构

Rust 编译器是重构的最好朋友。删除函数定义:

```rust
// 旧函数
fn old_lighting_lookup(mesh: &Mesh, light: &Light) -> Color {
    // ...
}
```

删除后,所有调用点报错:

```
error[E0425]: cannot find function `old_lighting_lookup` in this scope
  --> src/render.rs:42:18
   |
42 |     let c = old_lighting_lookup(&mesh, &light);
   |             ^^^^^^^^^^^^^^^^^^^^ not found in this scope
```

每个错误是一个**待迁移的调用点**。改完一个,编译器报错少一个。直到所有错误消失,迁移完成。

这是为什么静态类型语言(尤其 Rust/Haskell)适合大重构——编译器是免费的代码审计。

### 临时切换:feature flag

如果是生产环境大重构,直接删旧代码风险高。常用 **feature flag**:

```rust
fn lighting_lookup(...) -> Color {
    if cfg!(feature = "use_voxel_lighting") {
        voxel_lighting_lookup(...)
    } else {
        old_lighting_lookup(...)
    }
}
```

`Cargo.toml`:

```toml
[features]
use_voxel_lighting = []
```

测试期可以两种模式都跑,验证视觉一致。完全确信后,删除 `old_lighting_lookup` 和 feature flag。

Casey 因为是单人项目,直接删了,不用 feature flag。但工业项目这是必备。

### 删除的"安全顺序"

不是一次删所有东西。安全顺序:

1. **新代码完整可用**(编译通过、功能测试过)
2. **逐个调用点迁移**(每改一个,跑一次)
3. **旧函数标记 `#[deprecated]`**(警告,但不报错)
4. **运行一段时间确认无警告**(几天到几周)
5. **删除旧函数定义**
6. **删除 deprecated 标记**

跳步的风险:第 5 步太早,新代码有 bug 你没发现,得回滚。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发里"破釜沉舟"式重构:

- **Half-Life 2**:开发中期,Valve 把整个渲染器从 mesh-based 改成 brush-based,删了半年代码
- **Doom 3**:id Software 把 BSP 渲染改成Stencil shadow volumes,完全删掉旧光照
- **Unreal 5 Lumen**:删了 Unreal 4 的 Lightmass(静态光照烘焙),用 Lumen 替代

Casey 这次重构虽然在教学场景,但纪律和工业级一致。

### 3.2 · Rust 生态视角

Rust 提供几个工具辅助重构:

- **`#[deprecated]`**:警告使用旧 API
- **`rustfix`**:自动迁移(Cargo 会自动跑)
- **`cargo clippy`**:lint 提示冗余代码

```rust
#[deprecated(since = "0.2.0", note = "use voxel_lighting_lookup instead")]
fn old_lighting_lookup(...) -> Color { ... }
```

调用时:

```
warning: use of deprecated function `old_lighting_lookup`: use voxel_lighting_lookup instead
```

### 3.3 · Linux 系统编程视角

Linux 内核也大量"删旧"——`gettimeofday` 被 `clock_gettime` 替代,`select` 被 `poll`/`epoll` 替代。但内核不能真删(用户程序会坏),所以保留接口,内部转发到新实现。

这种"接口稳定 + 内部重构"叫 ABI stability,操作系统必须遵守。游戏没这个约束,可以直接删。

### 3.4 · 图形学视角

图形学的历史是一连串"删旧":

- **Fixed-function pipeline** → **programmable shaders**(2001+):删了 glLight/glMaterial
- **OpenGL 1.x** → **Vulkan/D3D12**(2014+):删了状态机,显式 API
- **Forward rendering** → **Deferred rendering**(2008+):删了 per-vertex 光照
- **Baked GI** → **Real-time GI**(2020+):删了离线烘焙管线

每次"删旧"是巨大重构,但带来性能/灵活性的飞跃。

## 4 · 认知地图

### 4.1 上级

- **Code refactoring discipline** —— 代码重构纪律
- **Migration patterns** —— 迁移模式
- **Single source of truth** —— 单一数据源(同一逻辑只一处实现)

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 直接删旧 | 简单,但有风险 | 单人项目 / 短期 | **是** |
| Feature flag 切换 | 安全,可回滚 | 团队 / 长期 | 否 |
| Strangler pattern | 新代码逐步包围旧 | 大型遗留系统 | 否 |
| Adapter pattern | 包装旧 API 为新 | 接口兼容性要求 | 否 |

### 4.3 下级

- **Compile-driven migration** —— 用编译器找调用点
- **`#[deprecated]`** —— 警告使用旧 API
- **Visual regression test** —— 视觉对比验证

## 5 · 对照与变奏

工业级"删旧"模式:

- **Strangler Pattern**(Martin Fowler):新代码逐步包围旧代码,最后旧代码像枯萎的植物,自然消失。适合改造巨型遗留系统
- **Parallel change**:同时存在新旧,内部用新,外部接口保留旧。HTTP API 的版本化常用
- **Big bang rewrite**:全部推倒重写。风险最高,但有时是唯一选项(代码太乱)

Casey 这次接近 "big bang"——Day 547 加新,Day 548 测试,Day 549 删旧。3 天完成完整切换。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不直接保留旧代码"以防万一"?保留旧代码的代价是什么?

**参考解答**:保留旧代码的代价:(1) 维护成本——每次改相关逻辑,要改两处;(2) 测试覆盖分叉——测试只测一种路径,生产可能走另一种;(3) 性能开销——两套都跑;(4) 认知负担——读代码者不知道哪条路在生产;(5) 阻碍演化——新架构的假设被旧代码破坏,新代码无法充分发挥。"以防万一"是合理担心,但应该用 git history(回滚)+ 备份,而不是把死代码留在 main 分支。

## 8 · Rust / Arch 落地代码

### 8.1 完整重构演示:旧光照系统迁移到新系统

让我们模拟整个重构流程。这个项目展示新旧并存 → feature flag → 删旧的完整路径。

```bash
cargo new --bin lighting-refactor-demo
cd lighting-refactor-demo
```

`src/main.rs`:

```rust
// 演示:旧 mesh-based 光照 → 新 voxel-based 光照的完整迁移

// ============================================================
// 旧系统(模拟)
// ============================================================
mod old_lighting {
    #[derive(Clone, Copy, Debug, PartialEq)]
    pub struct Color(pub [f32; 3]);

    /// 旧光照查询:基于 mesh ID + 顶点法线
    /// 问题:每个 mesh 都要预先 bake 光照,动态场景失效
    pub fn lighting_for_mesh(
        _mesh_id: u32,
        normal: [f32; 3],
    ) -> Color {
        // 模拟旧计算:简单的 Lambert + 环境光
        let light_dir = [0.5, 1.0, 0.3];
        let dot = normal[0] * light_dir[0]
                + normal[1] * light_dir[1]
                + normal[2] * light_dir[2];
        let lambert = dot.max(0.0);
        let ambient = 0.2;
        let intensity = (lambert + ambient).min(1.0);
        Color([intensity, intensity, intensity])
    }
}

// ============================================================
// 新系统(voxel-based)
// ============================================================
mod new_lighting {
    use super::old_lighting::Color;

    /// Voxel 光照网格 - 存储每个 voxel 的光照信息
    pub struct VoxelGrid {
        pub resolution: u32,
        pub data: Vec<[f32; 3]>,  // RGB per voxel
    }

    impl VoxelGrid {
        pub fn new(resolution: u32) -> Self {
            let total = (resolution * resolution * resolution) as usize;
            Self {
                resolution,
                data: vec![[1.0, 1.0, 1.0]; total],
            }
        }

        fn index(&self, x: u32, y: u32, z: u32) -> usize {
            ((x * self.resolution + y) * self.resolution + z) as usize
        }

        /// Trilinear 采样
        pub fn sample(&self, pos: [f32; 3]) -> [f32; 3] {
            let x = (pos[0] * self.resolution as f32) as u32 % self.resolution;
            let y = (pos[1] * self.resolution as f32) as u32 % self.resolution;
            let z = (pos[2] * self.resolution as f32) as u32 % self.resolution;
            self.data[self.index(x, y, z)]
        }
    }

    /// 新光照查询:基于 world position + 法线
    /// 优势:任意位置都能查,支持动态光照
    pub fn lighting_from_voxel(
        grid: &VoxelGrid,
        world_pos: [f32; 3],
        _normal: [f32; 3],
    ) -> Color {
        let sampled = grid.sample(world_pos);
        Color(sampled)
    }
}

// ============================================================
// 演示主程序
// ============================================================
fn main() {
    println!("=== Day 549: 删除旧光照查询 ===\n");

    let grid = new_lighting::VoxelGrid::new(16);

    // --------------------------------------------------------
    // 阶段 1:旧调用(待迁移)
    // --------------------------------------------------------
    // 旧代码,在 main 里多次调用:
    // let c1 = old_lighting::lighting_for_mesh(42, [0.0, 1.0, 0.0]);
    // let c2 = old_lighting::lighting_for_mesh(100, [1.0, 0.0, 0.0]);
    // let c3 = old_lighting::lighting_for_mesh(200, [0.0, 0.0, 1.0]);

    // --------------------------------------------------------
    // 阶段 2:逐个迁移到新系统
    // --------------------------------------------------------
    let c1 = new_lighting::lighting_from_voxel(&grid, [10.0, 5.0, 10.0], [0.0, 1.0, 0.0]);
    let c2 = new_lighting::lighting_from_voxel(&grid, [5.0, 8.0, 12.0], [1.0, 0.0, 0.0]);
    let c3 = new_lighting::lighting_from_voxel(&grid, [3.0, 15.0, 7.0], [0.0, 0.0, 1.0]);

    println!("Light at (10, 5, 10): {:?}", c1);
    println!("Light at (5, 8, 12): {:?}", c2);
    println!("Light at (3, 15, 7): {:?}", c3);

    // --------------------------------------------------------
    // 阶段 3:删除旧模块
    // --------------------------------------------------------
    // 现在可以删除 old_lighting 模块了。
    // 注释掉 mod old_lighting; 上面那行,
    // 然后 cargo build 会报错指出任何遗漏的旧调用。

    println!("\n=== 完成重构 ===");
    println!("旧 lighting_for_mesh 已删除,所有调用迁移到 lighting_from_voxel");
}
```

### 8.2 用 `#[deprecated]` 做软迁移

如果是工业项目(多人协作),不能一次性删,用 `#[deprecated]` 渐进迁移。

```rust
mod lighting {
    use super::new_lighting::{Color, VoxelGrid};

    // 全局 voxel grid(简化,实际用 OnceLock)
    use std::sync::OnceLock;
    static GRID: OnceLock<VoxelGrid> = OnceLock::new();

    pub fn init_grid(grid: VoxelGrid) {
        GRID.set(grid).ok();
    }

    /// 新 API - 推荐
    pub fn lighting_from_voxel(world_pos: [f32; 3], normal: [f32; 3]) -> Color {
        let grid = GRID.get().expect("Grid not initialized");
        new_lighting::lighting_from_voxel(grid, world_pos, normal)
    }

    /// 旧 API - 已弃用
    /// 内部转发到新 API,功能等价
    #[deprecated(since = "0.3.0", note = "use `lighting_from_voxel` instead. Will be removed in 0.4.0")]
    pub fn lighting_for_mesh(_mesh_id: u32, _normal: [f32; 3]) -> Color {
        // 警告 + 转发到新实现
        lighting_from_voxel([0.0, 0.0, 0.0], _normal)
    }
}

fn main() {
    lighting::init_grid(new_lighting::VoxelGrid::new(16));

    // 这行会产生 deprecation warning
    let c = lighting::lighting_for_mesh(42, [0.0, 1.0, 0.0]);
    println!("Color: {:?}", c);

    // 用新 API,无警告
    let c2 = lighting::lighting_from_voxel([1.0, 2.0, 3.0], [0.0, 1.0, 0.0]);
    println!("Color: {:?}", c2);
}
```

### 8.5 Troubleshooting

**问题1**:删了旧函数,编译报 100 个错误,看着吓人。
解决:用 `cargo build 2>&1 | head -50` 看前 50 个错误,一个一个改。每改一个,cargo 报错少一个。最后清零。

**问题2**:迁移完后游戏画面全黑。
诊断:新系统的某些边界 case 没覆盖。比如 voxel grid 在某些位置没初始化(默认值 0)。补:`VoxelGrid::new` 用 1.0 初始化,不是 0.0。

**问题3**:迁移完后性能下降。
诊断:新系统比旧的慢。先 commit 当前状态(`perf baseline`),profile,优化。不要回滚到旧系统——新系统的优势还没发挥。

**问题4**:同事的 PR 仍然调旧函数(基于旧代码分支)。
解决:在 merge 他的 PR 之前,先用最新 main rebase 他的分支,冲突会让他看到旧函数已删,自然迁移。

**问题5**:某个第三方的 mod 依赖旧 API。
解决:工业项目通常提供"兼容 shim"——一个空壳函数,转发到新实现。保持几个版本,让 mod 社区迁移。

### 附录:删除代码的"心理治疗"

很多程序员对删除代码有心理障碍。让我们正式讨论这个。

#### "Code as Liability, Not Asset"

Jeff Atwood(Stack Overflow 创始人)有句名言:**"Code is our enemy."** 不是夸张——每一行代码:

- 要被读懂(读代码时间 >> 写代码时间)
- 要被测试(每个函数要有测试)
- 要被维护(API 演化、bug 修复、性能优化)
- 要被编译(增加 build 时间)
- 要被部署(增加 binary 体积)
- 要被 review(增加 PR review 时间)

Net 效应:**每行代码是负债**。能用 0 行解决的问题,不要用 100 行;能用 100 行的,不要用 1000 行。

工业界度量:
- **Source Lines of Code (SLOC)**:简单的"代码量"度量。SLOC 越高,bug 越多(经验值:每 1000 行 1-25 个 bug)。
- **Cyclomatic Complexity**:分支复杂度。每个 if/for/while 加 1。> 10 的函数难维护。
- **Halstead Complexity**:操作符 / 操作数统计。

好的程序员:**降低这些指标,而不是升高**。

#### 删除代码的常见借口和反驳

**借口 1**:"这是历史代码,可能有人在用"。
**反驳**:用 `git log -p path/to/code.rs | grep -E "^\+.*func_name" --` 看最后修改时间。如果 3 年没动,99% 没人在用。

**借口 2**:"删除前要 100% 确认无用"。
**反驳**:你永远无法 100% 确认。Rust 编译器能确认 90%,运行时测试确认 9%,剩下 1% 用 git history 兜底。

**借口 3**:"删了影响别人"。
**反驳**:这正是 deprecation 警告的意义——告诉别人"我要删了,你迁移"。给个时间窗口(比如 1 个版本),然后删。

**借口 4**:"这部分代码未来可能扩展用"。
**反驳**:YAGNI(You Aren't Gonna Need It)。95% 的"未来扩展"永远不会来。删了,真要用再 cherry-pick。

**借口 5**:"删了破坏单元测试"。
**反驳**:那是因为你的测试在测实现细节,不是行为。删实现 + 删对应测试。保留行为测试。

#### "Boy Scout Rule"

Robert Martin(Bob 大叔)提出:**"离开时,让营地比你到达时更干净"**。

应用到代码:每次 PR,顺手清理一些死代码、改一些命名、删一些过时注释。每次小清理,代码库长期保持健康。

不需要专门"重构周"——每次接触代码都顺手清理 1-2 处。一年下来,代码库质量大幅提升。

#### "Chesterton's Fence"

但删除也有反例。**Chesterton's Fence** 原则:

> 在你拆掉一道栅栏之前,先搞清楚它为什么在那。

某些代码看着多余,其实是为了解决某个隐藏问题。比如:
- 某个 `sleep(10ms)` 看着像 bug,其实是为了等待硬件 handshake
- 某个 `if (x > 1000) return;` 看着像死代码,其实是为了防御某次崩溃
- 某个奇怪的类型转换,其实是为了跨平台兼容

删除前用 `git blame` 看历史,理解"为什么"——再决定删不删。

平衡:**Boy Scout Rule 让你勇于清理,Chesterton's Fence 让你谨慎清理**。两者结合,既不保守也不鲁莽。

#### 删除代码的快乐

最后, Casey 在 Day 549 视频里说:**"删除代码的感觉很好——就像清理房间,扔掉不再穿的衣服。"**

这不是夸张。删除代码触发 dopamine——你看着 LOC 数字下降,binary 体积下降,build 时间下降,是一种**纯粹的成就感**。

培养这种"删除快感"——它会让你成为更好的程序员。
