
# Day 441 · 永远不要更新开发工具,永远

> Casey 用整一集讲一件所有程序员迟早被坑的事:你的工具链(编译器、库、IDE、驱动)突然更新,代码就不编译/不运行/行为变了。Casey 的忠告:开发中**永远不要**自动更新工具,除非你已经完成当前阶段或准备好半天时间排查回归。

## 0 · 为什么要有这一天

每个程序员都会经历这个时刻:你昨晚写得正欢,关机前没动任何东西。今天早上起来 `cargo build`,突然报 100 个错误。昨晚到今早之间你没改一行代码——但你的 Arch Linux 自动 `pacman -Syu` 升级了 gcc,你的 Rust 自动 `rustup update` 升级了 rustc,你的 NVIDIA 驱动滚动升级了。

工具链升级带来的回归(regression)是工程师的隐形杀手。它们不会让你写错代码,但会让**正确的代码不工作**。Casey 这一集的核心论点:**在项目开发过程中,工具链应该是冻结的**。

为什么?

第一,**回归不可预测**。新版编译器可能优化更激进,触发你代码里某个 undefined behavior,把原本"碰巧能跑"的代码搞坏。新版库可能修复一个 bug,而你的代码恰好依赖那个 bug。

第二,**回归难排查**。代码没变,行为变了。git bisect 救不了你(因为代码 commit 是同一个)。你必须把"工具链"也纳入版本控制。

第三,**心理代价**。你正在思考游戏物理引擎,突然要花三天查为什么 shader 编译失败。这破坏心流(flow),是创作最大的敌人。

但反过来,**永远不更新也不对**。新工具带来新优化、新安全补丁、新语言特性。Casey 自己偶尔也会"主动升级窗口",花一两天验证全部回归。

让我把这件事的代价量化。商业游戏项目通常有 5-50 个开发者,持续 2-5 年。这段时间里,Rust 大约出 17-42 个 stable 版本(每 6 周一个)。每次升级,如果有 1% 概率引入一个需要 4 小时排查的回归,期望时间是 0.04 × 42 ≈ 1.7 小时/版本 × 42 版本 ≈ 70 小时工程时间——差不多两个工作周。这就是不冻结工具链的代价。

更糟的是**回归的隐蔽性**。代码"能编译"不代表"行为正确"。某个 trait 解析规则变了,代码编译过,但 trait bound 解析路径不同,导致 monomorphization 多生成了一个变体,binary 大小增加 100KB,启动慢 50ms。**这类回归在功能测试里看不出来,只在生产环境被玩家发现**。

完成这一天后,你能做到:用 `rust-toolchain.toml` 锁定项目工具链版本,用 Docker 锁定系统库,用 `cargo vendor` 缓存所有依赖。你还能解释为什么 Arch Linux 滚动发布对游戏开发有特殊风险,以及如何用 `pacman -D --asexplicit` 隔离关键包。

一个常被忽略的细节:**冻结工具链不只是冻结"自己用的工具",还包括冻结"构建产物的输出"**。这就是"可复现构建(reproducible build)"的概念——同一份源码,无论谁构建、什么时候构建,产出**字节相同**的二进制。Debian 项目为这个目标努力了十年,Rust 也在持续改进。Casey 的冻结策略是这条路上的第一步。

## 2 · 心智模型

### 类比:赛车队的零件采购

赛车队从不在比赛前一晚换零件——即使供应商说"新零件更好"。原因不是新零件差,而是**不熟悉**。比赛前你只用你训练时用过的零件,因为你的工程师熟悉它们的所有特性、bug、边界。

工具链也一样。`rustc 1.81` 你用了三个月,你知道它对哪个 generic 会过度优化,知道哪个 inline 是稳定的,知道 debug 模式哪个 panic 信息最有用。`rustc 1.82` 升级了某个 pass,你的心智模型就要重学。

这不是说 1.82 不好——它可能有重要 bug 修复。但**开发中**的稳定性比"修复一个你从没遇到的 bug"更重要。**发布前**才反过来。

### 严谨原理:工具链的依赖关系

一个游戏项目依赖的工具栈:

```
你的代码
  ↓
Rust crate(几百个,各自有版本)
  ↓
rustc(每 6 周一个 stable)
  ↓
LLVM(rustc 内部,每次 rustc 升级可能换 LLVM 版本)
  ↓
glibc / musl(Linux C 库)
  ↓
Linux 内核(syscall ABI)
  ↓
驱动(GPU、音频、输入)
  ↓
硬件(CPU、GPU)
```

每一层都可能因为上层或下层升级而出问题。

**实际案例**:
- **glibc 升级**:你的二进制是用新版 glibc 编译的,部署到旧系统上不运行。这是著名的 "GLIBC_2.XX not found" 错误。
- **rustc 升级**:某个 trait resolution 改了,你的代码不再编译。
- **驱动升级**:GPU shader 编译器更新,原本 60 FPS 变 30 FPS(罕见但有)。
- **crate 升级**:`Cargo.lock` 没锁,你 `cargo build` 拉到新版本,API 变了。

让我把"glibc 升级"这个最常见的坑讲深一点,因为它揭示了**为什么符号版本(symbol versioning)是 ABI 的核心**。

glibc 用一个叫**符号版本(symbol versioning)**的机制管理 ABI 兼容性。每个公开函数(如 `printf`、`memcpy`)有多个版本标签:`GLIBC_2.0`、`GLIBC_2.1`、`GLIBC_2.14` 等。新版本 glibc 加入优化过的 `memcpy` 实现时,会把它标 `GLIBC_2.14`,但旧版 `memcpy@GLIBC_2.0` 仍然存在。

编译时,链接器把"我调用哪个版本"写进二进制的 `.symver` 段。运行时,动态链接器检查系统能否提供这个版本——找不到就报 `GLIBC_2.14 not found`。

**这意味着**:在一台 Arch Linux(glibc 总是最新)上编译的二进制,部署到 Ubuntu 16.04(glibc 2.23)上,可能因为 `GLIBC_2.28 not found` 启动失败。**这是工业上交叉编译和容器化的根本动机**——把"构建环境"和"运行环境"严格分离。

诊断命令:

```bash
# 看二进制需要的 glibc 版本
objdump -T target/release/my_game | grep GLIBC | sort -u
# 输出类似:
# 0000000000000000      DF  UND  0000000000000000  GLIBC_2.2.5 memcpy
# 0000000000000000      DF  UND  0000000000000000  GLIBC_2.14  memcpy
# ...

# 看运行系统能提供的最高 glibc 版本
ldd --version | head -1
# 输出:ldd (Ubuntu GLIBC 2.31-0ubuntu9.9) 2.31

# 找出二进制需要的"最高版本"
objdump -T target/release/my_game | grep -oP 'GLIBC_\d+\.\d+' | sort -V | tail
```

如果二进制需要的最高版本 > 系统提供的版本,启动就失败。**对策**:用旧发行版(如 Debian Stable 或 AlmaLinux)做构建,或者用 musl libc 静态链接(`x86_64-unknown-linux-musl` target)。

### Casey 的"工具链冻结"实践

具体到 HH 的 Windows 开发:

```
- Windows 10 特定版本(可能不是最新)
- Visual Studio 2017/2019 特定 update(不是最新)
- Windows SDK 10.0.XXXXX.0 特定版本
- 第三方库特定 commit
- 显卡驱动版本特定
- 不开 Windows Update 自动
```

迁移到 Linux/Rust 后,对应:

```
- Arch 特定 snapshot(每次 pacman -Syu 后做镜像)
- rustc 特定版本(rust-toolchain.toml 锁定)
- 关键 crate 用 Cargo.lock
- 驱动(linux kernel + nvidia)用特定 pacman 缓存
```

### Rust 的工具链管理

Rust 有几个工具帮你冻结:

**`rust-toolchain.toml`**(项目级锁定):

```toml
[toolchain]
channel = "1.81.0"
components = ["rustfmt", "clippy"]
targets = ["x86_64-unknown-linux-gnu"]
profile = "minimal"
```

放在项目根目录。任何人 `cd` 进项目,`cargo` 自动用 1.81.0 而不是默认 stable。

**`Cargo.lock`**(依赖版本锁定):

```toml
# This file is automatically @generated by Cargo.
version = 3
[[package]]
name = "bevy"
version = "0.12.1"
source = "registry+https://github.com/rust-lang/crates.io-index"
...
```

`Cargo.lock` 锁定所有依赖的精确版本。`cargo build` 用 lock 文件,不会拉新版。**只有 `cargo update` 才更新 lock**。

**`cargo vendor`**(完全离线):

```bash
cargo vendor vendor-dir
# 在 .cargo/config.toml 加:
[source.crates-io]
replace-with = "vendored-sources"
[source.vendored-sources]
directory = "vendor-dir"
```

之后 `cargo build` 完全从 `vendor-dir` 取依赖,不联网。

### Arch Linux 的特殊挑战

Arch 滚动发布,工具链频繁更新。这带来挑战:

**挑战 1:`pacman -Syu` 全系统升级**
所有包一起升,无法回退单包(除非有 `/var/cache/pacman/pkg/` 缓存)。

**对策**:`/etc/pacman.conf` 里开启缓存:
```
[options]
HoldPkg = pacman glibc
# 不升级特定包
IgnorePkg = linux nvidia
```

**挑战 2:rustup 自动更新**
默认 rustup 每天检查 stable 更新并安装。

**对策**:在项目里放 `rust-toolchain.toml`,强制用项目版本。或全局 `rustup toolchain install 1.81.0-x86_64-unknown-linux-gnu` 后 `rustup default 1.81.0`。

**挑战 3:linux + nvidia 升级导致驱动不匹配**
新内核可能不兼容旧 NVIDIA 驱动模块。

**对策**:用 `pacman -Syu` 时**同时升级 linux 和 nvidia**(不能只升一个)。或用 `dkms` 让驱动随内核重编译。

让我把 Arch 的"滚动发布风险"讲透彻,这是 Linux 开发者最容易踩的坑。

**Arch 的滚动模型**。传统发行版(Debian / Ubuntu / RHEL)每 6-36 个月发布一个"快照",用户在快照间保持稳定。Arch 没有快照——`pacman -Syu` 永远把系统升级到"当前最新"。优势是你总能用上新软件;代价是**任何时候都可能出新 bug**。

**Arch 用户开发严肃项目必须做的事**:

第一,**快照系统**。在每次大升级前用 `timeshift` 或 `btrfs snapshot` 给文件系统打快照。出问题立刻回滚,不用排查。

```bash
# 装 timeshift
sudo pacman -S timeshift
# 配置成每次 pacman -Syu 前自动快照
# 或手动:
sudo timeshift --create --comments "before upgrade"
```

第二,**pacman 缓存清理要保守**。默认 `/var/cache/pacman/pkg/` 累积所有历史包,占空间。但回退时这个缓存是救命稻草。

```bash
# 看 cache 大小
du -sh /var/cache/pacman/pkg/

# 保守清理:只保留最近 3 个版本
sudo paccache -k 3
# 激进清理:只保留当前装的版本
sudo paccache -u -k 0
# 不要这样!会丢回退能力:
# sudo pacman -Sc   # 删除所有未安装的版本
```

第三,**用 pacman hook 在升级前后自动备份关键文件**。`/etc/pacman.d/hooks/` 下放个 hook:

```ini
# /etc/pacman.d/hooks/backup-toolchain.hook
[Trigger]
Operation = Upgrade
Type = Package
Target = rust
Target = gcc

[Action]
Description = Backing up toolchain versions...
When = PreTransaction
Exec = /usr/local/bin/backup-toolchain.sh
```

`backup-toolchain.sh` 内容:`rustc --version > /var/log/toolchain-snapshots/rustc-$(date +%s).txt`。

第四,**AUR 包尤其要小心**。AUR 没有签名验证,PKGBUILD 可能任意变。对开发依赖的 AUR 包,自己 fork 一份,锁定 commit hash。

```bash
# 克隆 AUR 包而不是用 helper
git clone https://aur.archlinux.org/some-package.git
cd some-package
git checkout <known-good-commit>
makepkg -si
```

第五,**docker 镜像隔离**。最彻底——把构建环境塞 docker 里,本地 Arch 怎么滚动都不影响构建产物:

```dockerfile
FROM rust:1.81-slim
WORKDIR /app
COPY . .
RUN cargo build --release
```

CI 跑这个镜像,产物 ABI 一致。

### Rust 的工具链管理(已展开)

#### Reproducible build 的进阶

可复现构建不只是"工具链版本固定"。还有几个隐藏变量:

1. **`SOURCE_DATE_EPOCH` 环境变量**:Rust 默认在 binary 里嵌入构建时间戳(`built at: 2024-01-15`)。设置 `SOURCE_DATE_EPOCH=1700000000` 让所有人构建出的时间戳一致。
2. **debuginfo 路径**:默认 debuginfo 包含绝对路径(如 `/home/alice/project/src/main.rs`),不同机器不同。用 `--remap-path-prefix` 重写:

```bash
RUSTFLAGS="--remap-path-prefix $PWD=/app" cargo build --release
```

3. **build script 的副作用**:有些 build script 调 `git describe` 把 commit hash 写进 binary——这在不同 commit 间当然不同,但同一 commit 内应该稳定。
4. **profile 设置**:`Cargo.toml` 的 `[profile.release]` 段,不同设置产出不同 binary。把 `lto`、`codegen-units`、`opt-level` 都明确写出来,而不是依赖默认值。

工业 CI 流程:每周构建一次"reference binary",存储 hash。后续构建产出 hash 应该和 reference 一致(如果代码没变)。Rust 1.x 系列在 reproducible build 上逐年改进,1.75+ 几乎完全可复现。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发对工具链稳定性的要求比一般软件更严:

- **shader 跨平台一致**:NVIDIA 驱动更新可能改变 GLSL 编译器行为,导致"原本对的 shader 在新驱动崩溃"
- **asset pipeline 一致**:构建工具(Python 脚本、ImageMagick)升级,可能改变纹理压缩输出,导致同一份源图打包出不同 .dds
- **console SDK 一致**(PS5/Xbox): Sony/Microsoft 不定期推送 SDK 更新,你必须按发行商要求升级

工业实践:**CI/CD 跑 Docker 镜像固定版本**。本地开发用最新工具,但 CI 用 freeze 镜像,保证产物可复现。

**坑**:LLVM 升级带来 LTO 优化变化。你的 release build 从 100MB 变 90MB,可能某段 SIMD 代码内联失败,性能掉 5%。LTO bug 极难排查。

### 3.2 · 图形学视角

图形程序员的"工具链灾难"故事:

- **GPU 驱动 bug**:每家厂商(NVIDIA/AMD/Intel)都有 shader 编译器 bug。游戏发行时常见"在 NVIDIA 上跑得好好的,在 AMD 上崩"——经常是 AMD shader 编译器的 bug。
- **Vulkan validation layer 更新**:旧的"非法用法"被新 layer 抓到,原本能跑的代码 crash。
- **OpenGL context 行为**:不同驱动版本对 core profile 的解释不同。
- **GLSL 标准变化**:新版 GLSL 标准加入或废弃特性,你的 shader 可能不再编译。

工业对策:
- 用 Vulkan / DX12 显式 API,把"驱动假设"减到最小
- 用 SPIR-V 直接编译 shader(绕过 GLSL 编译器的驱动差异)
- **Vsync / present mode 行为**跨驱动版本一致:用 `VK_PRESENT_MODE_MAILBOX_KHR` 显式指定

### 3.3 · Linux 系统编程视角

Linux 工具链:

| 组件 | 升级频率 | 典型回归 |
|---|---|---|
| Linux kernel | 8 周 | syscall 行为微调,perf 接口变 |
| glibc | 6 个月 | 符号版本变,二进制兼容性 |
| gcc | 1 年 | 优化更激进,UB 行为暴露 |
| binutils | 1 年 | 链接器行为变,符号解析 |
| LLVM | 6 个月 | rustc 跟随,rustc 行为变 |
| rustc | 6 周 | trait 解析,MIR 优化 |
| Wayland / X11 | 滚动 | 协议扩展,客户端库 API |

**Arch 特殊性**:`pacman -Syu` 一次性升级所有。所以 Arch 开发者必须**总是准备好处理回归**。Casey 在 Windows 上有"冻结"的奢侈,Arch 上要主动构造。

```bash
# 关键包不升级
sudo pacman -D --asexplicit linux linux-headers nvidia nvidia-utils
# 在 /etc/pacman.conf 设 IgnorePkg
sudo vim /etc/pacman.conf
# 添加:IgnorePkg = linux nvidia
```

**回退**:如果升级出问题,从 `/var/cache/pacman/pkg/` 装回旧版:
```bash
sudo pacman -U /var/cache/pacman/pkg/linux-6.6.10-1-x86_64.pkg.tar.zst
```

### 3.4 · Rust 生态视角

Rust 工具链管理工具:

**rustup**:管理多个 Rust toolchain 共存
```bash
rustup toolchain list
rustup toolchain install 1.81.0
rustup override set 1.81.0  # 当前目录用 1.81.0
```

**rust-toolchain.toml**:项目级锁定(已讲)

**cargo-fix**:升级时自动修复 deprecation 警告

**cargo outdated**:检查依赖有没有新版本
```bash
cargo install cargo-outdated
cargo outdated
# 列出所有可升级的依赖
```

**cargo-edit / cargo-update**:管理 Cargo.toml

**eddyb / miri**:运行时检查 UB,验证代码在新 rustc 下是否"碰巧能跑"

**坑**:Rust edition 升级(2015/2018/2021/2024)是更大的回归源。`edition = "2021"` 和 `edition = "2018"` 的代码行为可能不同。`cargo fix --edition` 帮你迁移,但仍需手动检查。

让我深入讲 edition 的演化,这是 Rust 程序员必须理解的"语言演化模型"。

**Rust edition 是什么**。edition 是"语言兼容性断点"。Rust 承诺"每个版本的编译器永远能编译 edition 2015 的代码",但 edition 2018/2021/2024 各自允许语言引入**不向后兼容**的变化——只要你显式 `edition = "2021"` 切换过去。

具体每个 edition 改了什么:

**Edition 2018**(2018 里程碑):
- 模块系统改革:`mod foo;` 不再需要 `mod.rs`,直接用 `foo.rs`
- `async/await` 关键字稳定化
- 非 lexical lifetime(NLL):借用检查更宽松,大量代码不再需要不必要的 clone
- `dyn Trait` 显式标注 trait object(2015 允许 `&Trait`,2018 要求 `&dyn Trait`)

**Edition 2021**:
- prelude 加入 `TryInto` / `TryFrom` / `FromIterator`
- 数组 `IntoIterator`(以前 `for x in &[1,2,3]` 借用,2021 直接消耗)
- panic macro 的格式化规则对齐 `println!`
- Cargo 默认解析器 v2(更严格的 feature 解析)

**Edition 2024**:
- `unsafe` 在 `extern` block 必须显式
- `gen` / `try` 成为关键字(为未来 gen 块和 try 块准备)
- panic 行为微调
- 一些 lifetime 推断规则变化

**坑点**:edition 切换后,**语义可能微妙变化**。比如 edition 2018 → 2021,你的 `for x in &some_array` 从"产生引用"变成"消耗数组"。如果代码原本期望引用,升级后行为变了。

诊断:`cargo +stable build` 在不同 edition 下编译,看 warning。Rust 编译器对 edition 迁移给出**详细的 lint 解释**,这是 Rust 团队的工程化优势。

```bash
# 看当前 edition
grep edition Cargo.toml

# 检查迁移到下一 edition 需要改什么
cargo fix --edition
# 这个命令会自动改大部分机械改动(如 `extern crate`),并报告需要手动的
```

工业实践:**新项目直接用最新 edition**,旧项目每 2-3 年评估一次升级窗口。

## 4 · 认知地图

### 4.1 上级

- **软件供应链管理** — 整个依赖树的版本治理
- **可复现构建(reproducible build)** — 同一输入产出同一二进制
- **依赖地狱(dependency hell)** — 上游变化对下游的连锁影响

### 4.2 同级

| 策略 | 关键差别 | 何时用 |
|---|---|---|
| 滚动更新(Arch) | 总是最新,回归风险高 | 桌面 / 个人开发 |
| 固定版本(Debian Stable) | 旧但稳 | 服务器 |
| LTS(Ubuntu LTS) | 每 2 年一个长支持版 | 企业生产 |
| 容器化(Docker) | 锁定整个文件系统 | CI/CD |
| Nix / Guix | 函数式包管理,完全可复现 | 极致可复现 |

### 4.3 下级

- **rustup** — 多 toolchain 管理
- **rust-toolchain.toml** — 项目级锁定
- **Cargo.lock** — 依赖版本锁定
- **cargo vendor** — 离线依赖缓存
- **pacman IgnorePkg** — 系统包冻结

## 5 · 对照与变奏

**不同语言的工具链管理**:

| 语言 | 工具 | 锁定粒度 |
|---|---|---|
| Rust | rustup + Cargo.lock + rust-toolchain.toml | 编译器+依赖,精细 |
| Go | go.mod + go.sum | 依赖,编译器要单独管 |
| Python | pip + requirements.txt + pyenv + poetry | 工具混乱,常用 Docker |
| C++ | CMake + vcpkg/conan + 编译器 | 编译器要手动管,依赖工具多 |
| Node.js | package-lock.json + nvm | 依赖锁定,Node 版本用 nvm |

**历史**:
- 1990s:版本控制刚起步,所有依赖手动管理
- 2000s:bundler / npm 出现,锁定依赖
- 2010s:rustup / pyenv / nvm,工具链切换器
- 2020s:Nix / Docker 普及,完全可复现

**Why Casey 这么严格?** HH 是教学项目,他要保证观众跟着代码"逐行复现"。任何工具变化都可能让"我的代码 Casey 看过"的承诺失效。商业游戏开发反而没这么严格——他们的 CI 系统会用容器化保证产物一致。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:`Cargo.lock` 和 `Cargo.toml` 有什么区别?如果团队成员的 `Cargo.lock` 不一致会怎样?

**参考解答**:
- `Cargo.toml`:你写的"我需要什么",声明依赖名和版本范围(如 `bevy = "0.12"`,意指 0.12.x)。
- `Cargo.lock`:cargo 自动维护的"实际用了什么",记录每个依赖精确版本和 hash(如 `bevy = 0.12.1`)。
- 区别:TOML 是声明,LOCK 是事实。

如果成员 lock 不一致:
- Alice 的 lock 有 `bevy 0.12.1`,Bob 的有 `bevy 0.12.2`
- 两人编译出的二进制可能行为不同(0.12.2 可能修了某个 bug)
- 这是著名的"在我电脑上能跑"问题

**对策**:`Cargo.lock` 应该提交 git(对于 binary 项目),所有成员共享。Library 项目可以不提交 lock,让下游决定。

### Lv2 · 动手实践

**题**:在你的 Rust 项目里加 `rust-toolchain.toml` 锁定到当前 rustc 版本,加 `cargo vendor` 离线化依赖。验证离线构建成功。

**参考解答**:

```bash
# 1. 看当前 rustc 版本
rustc --version
# 输出:rustc 1.81.0

# 2. 在项目根创建 rust-toolchain.toml
cat > rust-toolchain.toml << 'EOF'
[toolchain]
channel = "1.81.0"
components = ["rustfmt", "clippy"]
profile = "minimal"
EOF

# 3. 验证:进入项目后 rustc 版本被锁定
cd /path/to/project
rustc --version  # 应该输出 1.81.0,即使系统默认更新了

# 4. 离线化依赖
cargo vendor vendor
# 输出"To use vendored sources",会给你一段配置

# 5. 创建 .cargo/config.toml
mkdir -p .cargo
cat > .cargo/config.toml << 'EOF'
[source.crates-io]
replace-with = "vendored-sources"

[source.vendored-sources]
directory = "vendor"
EOF

# 6. 验证离线构建
cargo build --offline
# 应该成功
```

完成标准:`cargo build --offline` 在断网情况下成功。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

完整工具链冻结:

```bash
# 项目结构
mkdir /tmp/frozen_project && cd /tmp/frozen_project
cargo init .

# 创建 rust-toolchain.toml
cat > rust-toolchain.toml << 'EOF'
[toolchain]
channel = "1.81.0"
components = ["rustfmt", "clippy", "rust-src"]
profile = "minimal"
targets = ["x86_64-unknown-linux-gnu"]
EOF

# 加几个依赖演示 Cargo.lock
cat >> Cargo.toml << 'EOF'

[dependencies]
serde = { version = "1.0", features = ["derive"] }
serde_json = "1.0"
EOF

# 第一次 build 生成 Cargo.lock
cargo build
cat Cargo.lock | head -20

# 看 lock 里精确版本
grep -A 1 "^name = \"serde\"" Cargo.lock

# 离线化
cargo vendor vendor 2>&1 | tail -10

mkdir -p .cargo
cat > .cargo/config.toml << 'EOF'
[source.crates-io]
replace-with = "vendored-sources"

[source.vendored-sources]
directory = "vendor"
EOF

# 验证离线构建
cargo clean
cargo build --offline
echo "Offline build succeeded!"
```

### Arch Linux 工具链

```bash
# 看 pacman 缓存
ls /var/cache/pacman/pkg/ | head
# 看你的系统能不能回退到旧包

# 锁定关键包(防止升级)
sudo pacman -D --asexplicit linux linux-headers nvidia
grep -E "^IgnorePkg" /etc/pacman.conf
# 如果没有,加一行:
# IgnorePkg = linux linux-headers nvidia

# 看 rustup 已安装的 toolchain
rustup toolchain list
# 输出:stable-x86_64-unknown-linux-gnu (default)
#       1.81.0-x86_64-unknown-linux-gnu

# 安装特定版本
rustup toolchain install 1.80.0
rustup toolchain install 1.75.0

# 在某目录强制用某版本
cd /tmp/old_project
rustup override set 1.75.0
# 现在 /tmp/old_project 里所有 cargo 命令用 1.75.0

# 升级前的备份(关键包)
sudo cp -r /var/cache/pacman/pkg /tmp/pacman_backup_$(date +%Y%m%d)

# 看哪个包最近升级了(回归排查)
grep -i "upgraded" /var/log/pacman.log | tail -20
```

**Troubleshooting**:
- `rust-toolchain.toml` 不生效 → 检查文件名拼写,必须在项目根
- `cargo build --offline` 失败 → 确认 vendor 目录有所有依赖,`.cargo/config.toml` 路径对
- 升级后驱动不工作 → `sudo pacman -U /var/cache/pacman/pkg/nvidia-OLDVERSION.pkg.tar.zst` 回退
