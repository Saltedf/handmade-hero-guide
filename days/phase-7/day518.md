# Day 518 · 显示导入错误

> HHT 解析器解析失败时,要给用户友好错误信息——不是 panic,而是显示具体哪一行错。Day 518 实现"错误显示"系统。

## 0 · 为什么要有这一天

### 真实场景:糟糕错误信息的痛苦

到 Day 517,HHT 解析器有错误处理,但错误信息粗糙:

```
panic: unexpected token at line 5
```

不够好。用户不知道:

- 错在第几列
- 期望什么 token
- 实际拿到什么
- 周围上下文

工业级错误显示:

```
Error: expected '=' but found '}' at line 5, column 12

  3 | entity hero {
  4 |     piece body
  5 |         sprite "hero_body" }
  |                    ^
  6 |     }
  7 | }
```

有上下文、有指针、有修复建议。

Day 518 实现这种错误显示。Rust 编译器、TypeScript、 Elm compiler 都是这种风格。

### 为什么"错误显示"这件事这么重要

让我们把镜头拉近。假设你是 Casey,刚做完 Day 517 的 HHT AST editor。你打开自己写的 HHT 文件做测试:

```
entity hero {
    piece body {
        sprite: hero_body.png
        alignment_point neck (0, -20)
        alignment_point hand_r (15, 0)
    }
}
```

你故意打错一个字符——把 "alignment_point" 写成 "alignment_pont"。你跑游戏,游戏崩:

```
thread 'main' panicked at 'unexpected token', src/hht/parser.rs:42:18
```

你的反应:
- "哪一行?"——错误信息没说
- "什么 token?"——错误信息没说
- "我的 HHT 文件哪错了?"——你看 parser.rs:42,但那是 parser 内部,不是你的 HHT 文件
- 你打开 HHT 文件,**一行一行重读**,找 typo。10 分钟才找到 "alignment_pont"

工业级编辑器(VSCode、IntelliJ)的错误显示完全不同:

```
Error: unknown keyword 'alignment_pont', did you mean 'alignment_point'?
  --> assets/hero.hht:5:9
   |
 5 |         alignment_pont neck (0, -20)
   |         ^^^^^^^^^^^^^^^ unknown keyword
   |
help: replace with 'alignment_point'
```

一眼看出:**第 5 行第 9 列**,unknown keyword,有修复建议。10 秒搞定。

这种错误显示不是奢侈品——它是**生产力的核心**。程序员每天遇到 100 次错误,每次省 9 分 50 秒,一天省 16 小时(夸张,但你懂意思)。

### 工业级错误显示的 5 个要素

成熟编译器 / parser 的错误显示遵循 5 个要素:

**1. 精确位置(file, line, column)**。不只说"line 5",说"hero.hht:5:9"。file 让用户跳转,line+column 让光标定位。

**2. 上下文(前后几行)**。显示前后 2-3 行,让用户看到错的位置。光看错误行不够,常常上下文暴露问题。

**3. 视觉指针(箭头 / 高亮)**。在错误位置下方画 `^^^^^^^`,人眼立刻锁定。

**4. 错误描述(期望 vs 实际)**。说"expected '=' but found '}'",不只是"unexpected token"。

**5. 修复建议(可选)**。如果可能,建议修复方案。"did you mean X?" 是 Rust 编译器经典。

Casey 在 Day 518 演示前 4 个要素。修复建议是高级特性,后续可能加。

### Rust 编译器的"诊断工程"

Rust 编译器在"错误显示"上是工业金标。具体细节:

- **错误等级**:Error(必须修)、Warning(可忽略)、Note(辅助说明)、Help(修复建议)、Suggestion(自动修复 diff)
- **错误码**:`#[error_code]` 给每个错误唯一码(E0308 等),用户可查文档
- **多错误**:parser 一次报告多个错误(不 stop on first),用户一次修多个
- **错误恢复**:遇到错,parser 试图恢复(跳过坏 token),继续报告后续错误
- **诊断 derive**:`#[derive(thiserror::Error)]` 让自定义错误类型自动生成消息

TypeScript、Elm、Swift 编译器都借鉴了 Rust 的设计。这是工业级语言编译器的标准。

## 1 · Casey 今天做了什么

Casey 这一天做的是"用户体验工程"——给 parser 加工业级错误显示。具体 6 步。

**第一步,扩展错误类型**。Day 510 的 ParseError 简单,只 message。Day 518 加位置 + 上下文:

```rust
struct ParseError {
    message: String,         // "expected '=' but found '}'"
    line: u32,                // 1-based 行号
    col: u32,                 // 1-based 列号
    source_line: String,      // 错误行的原文
    span_start: u32,          // 高亮开始列
    span_end: u32,            // 高亮结束列
}
```

每个字段都有用:line / col 让用户跳转,source_line 显示上下文,span_start/end 决定 `^^^^` 长度。

**第二步,parser 失败时填充字段**。Parser 遇到错时,从当前 token 取位置,生成 ParseError:

```rust
fn expect_equals(tokens: &[Token], pos: usize) -> Result<(), ParseError> {
    if matches!(tokens[pos].kind, TokenKind::Equals) {
        Ok(())
    } else {
        Err(ParseError {
            message: format!("expected '=' but found {:?}", tokens[pos].kind),
            line: tokens[pos].line,
            col: tokens[pos].col,
            source_line: get_source_line(source, tokens[pos].line),
            span_start: tokens[pos].col,
            span_end: tokens[pos].col + tokens[pos].length,
        })
    }
}
```

每个 expect / parse 函数都返回 `Result<T, ParseError>`。

**第三步,写 format_error 函数**。生成 rustc 风格的多行错误:

```rust
fn format_error(error: &ParseError, source: &str) -> String {
    let lines: Vec<&str> = source.lines().collect();
    let line_idx = (error.line as usize).saturating_sub(1);
    let mut out = String::new();
    
    // 错误描述
    out.push_str(&format!("Error: {}\n", error.message));
    out.push_str(&format!("  --> line {}, col {}\n", error.line, error.col));
    out.push('\n');
    
    // 前一行(如果有)
    if line_idx > 0 {
        out.push_str(&format!(" {:>3} | {}\n", error.line - 1, lines[line_idx - 1]));
    }
    
    // 错误行
    out.push_str(&format!(" {:>3} | {}\n", error.line, lines[line_idx]));
    
    // 指针行(`^^^^`)
    let padding = " ".repeat(error.col as usize - 1);
    let pointer = "^".repeat((error.span_end - error.span_start).max(1) as usize);
    out.push_str(&format!("     | {}{}\n", padding, pointer));
    
    // 后一行(如果有)
    if line_idx + 1 < lines.len() {
        out.push_str(&format!(" {:>3} | {}\n", error.line + 1, lines[line_idx + 1]));
    }
    
    out
}
```

输出像:
```
Error: expected '=' but found '}'
  --> line 5, col 12

 4 |     piece body
 5 |         sprite "hero_body" }
   |                    ^
 6 |     }
```

**第四步,加多错误收集**。Day 518 的核心创新——**error recovery**。Parser 遇到错不立即返回,记录错误继续(跳过坏 token),最后报告所有:

```rust
struct ErrorReporter {
    errors: Vec<ParseError>,
    source: String,
}

impl ErrorReporter {
    fn report(&mut self, error: ParseError) {
        self.errors.push(error);
    }
    
    fn has_errors(&self) -> bool { !self.errors.is_empty() }
    
    fn format_all(&self) -> String {
        self.errors.iter()
            .map(|e| format_one(e, &self.source))
            .collect::<Vec<_>>()
            .join("\n\n")
    }
}
```

Parser 接受 `&mut ErrorReporter`,遇到错 `reporter.report(error)`,**继续解析**(不是 return Err)。

**第五步,在编辑器 UI 显示错误列表**。Parser 完成后,把 ErrorReporter 的所有错误显示在 editor 的"问题面板"。用户按 F8 跳到下一个错误,光标定位。

**第六步,测试各种错误场景**。Casey 写测试覆盖:
- 缺 `=`(语法错)
- 未闭合 `{`(EOF 错)
- 未知 keyword(语义错)
- 重复 section
- 引号不闭合

每个测试验证错误信息正确、位置准确、上下文清晰。

### Error recovery 的核心算法

Error recovery 的关键是"找恢复点"。常见策略:

**策略 1:跳到下一行**。看到错,跳到下一个 `\n`。适合 statement-based 语法(HHT、INI)。

**策略 2:跳到 matching brace**。看到错,找到 matching `}`,跳过整个 block。适合 nested 语法(JSON、Lisp)。

**策略 3:同步 token(sync token)**。某些 token 是"语句边界"——`;`、`}`、`{`、`newline`。看到错,跳到下一个 sync token。

**策略 4:prediction**。Parser 预测"下一个应该是什么",如果实际不符,跳过实际,继续预测。

每种策略都有 trade-off——简单策略可能误报"级联错误"(一个真错导致后面 10 个假错),复杂策略实现难。Casey 用策略 1(跳到下一行),够用。

### 1.1 重新审视:错误恢复的"白皮书"

错误恢复(error recovery)是 Day 518 的隐藏难点。让我们深入讨论。

Parser 遇到错误,有两种策略:

**策略 A:Fail fast**。立即返回 Err,停止 parse。简单,但用户每次只看一个错。

**策略 B:Error recovery**。跳过坏 token,试图恢复,继续 parse。可能误报(因为 parser 状态已乱),但用户一次看多个错。

工业级编译器(rustc、TypeScript、Python)用 B。但要小心实现,避免"级联错误"——一个真错导致后面 10 个假错。

具体恢复算法(以 HHT 为例):

```
ParseError 内部:
  - 看到 unknown keyword,跳到下一个 '\n'(行尾)
  - 看到不期望的 '{',跳过这个 token,假设后续可能合理
  - 看到不期望的 '}',记录错误,继续(因为可能 '}' 应该忽略)
  - 看到不期望的 EOF,记录错误,终止 parse
```

每个错误后,parser "复位"到一个**合理状态**——通常是 statement 边界。

这是 Parser combinator(如 nom)和 Parser generator(如 yacc / bison)的核心区别。Parser combinator 默认 fail fast,要手写 recovery 逻辑。Parser generator 内置 recovery(用 `error` 规则)。

### 上下文显示

```

 5 |         sprite "hero_body" }
```

### 错误恢复

简单 parser:第一个错就停。用户体验差——改一个错,再跑,发现下一个,迭代慢。

错误恢复:遇到错,跳过一些 token,继续解析。一次报多个错。

工业级 compiler(rustc、clang)都用错误恢复。

恢复策略:

- 跳到下一行
- 跳到 `;` 或 `}`
- 同步 token(语言特定)

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么错误恢复(继续解析)比立即停止好?

**参考解答**:三个理由:

第一,**用户效率**。一次报多个错,用户一次修多个。立即停止,用户修一个,跑,发现下一个,迭代慢。

第二,**反馈完整性**。用户看到所有错,知道代码整体健康度。立即停止只看一个,可能下面还有 10 个同类错。

第三,**机器分析**。CI 工具收集所有错,做趋势分析。立即停止 CI 永远只看第一个。

代价:错误恢复复杂(可能误报)。但工业级值得。

### Lv2 · 动手实践

**题**:实现 HHT 错误显示。给定错误 token 和 source,生成多行错误信息(含上下文 + 指针)。

完成标准:`cargo run` 显示像 rustc 的错误信息。

**参考解答**:

```rust
#[derive(Debug, Clone)]
struct SourceLoc {
    line: u32,      // 1-based
    col: u32,       // 1-based
    length: u32,    // token 长度
}

#[derive(Debug, Clone)]
struct ParseError {
    message: String,
    loc: SourceLoc,
}

struct ErrorReporter {
    source: String,
    errors: Vec<ParseError>,
}

impl ErrorReporter {
    fn new(source: String) -> Self {
        Self { source, errors: Vec::new() }
    }
    
    fn report(&mut self, message: &str, loc: SourceLoc) {
        self.errors.push(ParseError {
            message: message.into(), loc,
        });
    }
    
    fn has_errors(&self) -> bool { !self.errors.is_empty() }
    
    fn format_all(&self) -> String {
        self.errors.iter()
            .map(|e| self.format_one(e))
            .collect::<Vec<_>>()
            .join("\n\n")
    }
    
    fn format_one(&self, error: &ParseError) -> String {
        let lines: Vec<&str> = self.source.lines().collect();
        let line_idx = (error.loc.line as usize).saturating_sub(1);
        
        let mut out = String::new();
        out.push_str(&format!("Error: {}\n", error.message));
        out.push_str(&format!("  --> line {}, col {}\n", error.loc.line, error.loc.col));
        out.push('\n');
        
        // 显示前一行(如果有)
        if line_idx > 0 {
            out.push_str(&format!(" {:>3} | {}\n", error.loc.line - 1, lines[line_idx - 1]));
        }
        
        // 错误行
        let error_line = lines.get(line_idx).unwrap_or(&"<EOF>");
        out.push_str(&format!(" {:>3} | {}\n", error.loc.line, error_line));
        
        // 指针行
        let padding = " ".repeat(error.loc.col as usize - 1);
        let pointer = "^".repeat(error.loc.length.max(1) as usize);
        out.push_str(&format!("     | {}{}\n", padding, pointer));
        
        // 后一行(如果有)
        if line_idx + 1 < lines.len() {
            out.push_str(&format!(" {:>3} | {}\n", error.loc.line + 1, lines[line_idx + 1]));
        }
        
        out
    }
}

fn main() {
    let source = r#"# HHT example
[bitmaps]
player
sword = "path/to/sword.png"
goblin = "enemies/goblin.png""#;
    
    let mut reporter = ErrorReporter::new(source.into());
    
    // 模拟错误:第 4 行第 8 列
    reporter.report("expected '=' but found '\"'", SourceLoc {
        line: 4, col: 8, length: 6,
    });
    
    // 模拟另一个错误
    reporter.report("undefined sprite 'missing_sprite'", SourceLoc {
        line: 5, col: 1, length: 6,
    });
    
    println!("=== Single Error ===\n");
    println!("{}", reporter.format_one(&reporter.errors[0]));
    
    println!("\n=== All Errors ===\n");
    println!("{}", reporter.format_all());
    
    println!("\nTotal errors: {}", reporter.errors.len());
}
```

### 附录:工业级错误显示的进化史

#### 1970s-1980s: 错误一行流

C 编译器早期:
```
test.c:5: error: syntax error
```

只有文件名、行号、消息。没有列、没有上下文、没有指针。

#### 1990s: GCC 添加列号

```
test.c:5:12: error: 'x' undeclared
```

加列号,但还是单行,没上下文。

#### 2000s: Rust 引入"诊断工程"

Rust 1.0(2015)的错误显示是工业革命:

```
error[E0308]: mismatched types
 --> src/main.rs:3:17
  |
3 |   let x: i32 = "string";
  |                 ^^^^^^^ expected i32, found &str
  |
help: consider using `parse`
  |
3 |   let x: i32 = "string".parse()?;
  |                          ++++++
```

要素齐全:错误码、位置、上下文、指针、错误描述、修复建议、自动 diff。

#### 2010s: IDE 集成

VSCode、IntelliJ、rust-analyzer 把错误显示**实时化**——你打字,red squiggle(波浪线)立刻出现。hover 显示完整诊断。Cmd+. 跳到错误。

#### 2020s: AI 辅助诊断

GitHub Copilot Chat、Cursor 等工具:错误发生时,AI 直接解释"为什么错"和"怎么改"。从被动错误显示 → 主动错误修复。

#### 跨语言对照

不同语言的错误显示风格:

- **C/C++ (GCC)**:简洁,可解析,适合 CI
- **Java**:stack trace 长,适合 debug
- **Python**:traceback + source,可读性好
- **JavaScript (V8)**:简洁 + highlight,Web 友好
- **Rust**:工业金标,所有要素齐全
- **TypeScript**:类似 Rust,IDE 集成好
- **Elm**:用户体验最好,新手友好

错误显示是**语言设计的核心部分**——它决定了用户体验,直接关系语言是否流行。Rust 比 C++ 流行(部分原因)就是错误显示更好。

#### 实战:为你的项目设计错误显示

如果你做一个 DSL(领域特定语言)、parser、或任何接受用户文本的工具,这套错误显示纪律都适用:

1. **每个 token 记录位置**(file, line, col, length)
2. **错误时取位置,生成 ParseError**
3. **收集多个错误**,不立即 fail
4. **format_error 显示上下文 + 指针**
5. **可选:错误恢复 + 修复建议**

时间预算:实现完整错误显示大概 1-2 天。回报:**用户体验提升 10 倍**。

这是 Day 518 的真正教学——不只是"实现 HHT 错误显示",而是"学会为任何工具实现工业级错误显示"。

### 附录:错误消息的"心理学"

错误消息不只要技术正确,还要心理学友好。一个**让用户自责**的错误消息("你写错了,傻逼")会毁掉产品体验。

**好错误消息的心理学特征**:

1. **不指责用户**。说"'x' undeclared"而不是"you forgot to declare 'x'"。前者描述事实,后者指责。
2. **具体**。说"expected ';' after expression at line 5"而不是"syntax error"。具体让用户立刻知道怎么改。
3. **可行动**。给修复建议,不只说"错"。Rust 编译器在这方面做得最好。
4. **可定位**。提供 file:line:col,用户能立刻跳到位置。
5. **不打断流程**。错误不该让用户重新启动整个 build——只修那一行,rebuild。

工业级评估错误消息的质量,看三个指标:
- **首次修复时间**(time to first fix):用户看到错误后,多久能修好
- **错误正确率**:用户是否真的修对了(不是 hack 绕过)
- **重复错误率**:同一错误多久出现第二次(说明消息没说清楚)

Rust 编译器的指标都极好——这是 Rust 流行的核心原因之一。

### 实战练习:为自己的项目添加错误显示

如果你在做任何工具(CLI、parser、parser-based DSL),尝试:

1. 找到所有 `panic!` 和 `unwrap`,改成返回 `Result<T, E>`
2. 为 E 实现详细的 Display,包括 source location
3. 用 `miette` 或 `codespan-reporting` 自动生成 rustc 风格输出
4. 加 error recovery(跳过坏 token 继续)
5. 加 "did you mean" 建议(基于编辑距离)

时间预算:1-2 天。但回报终身——任何用户接触你的工具,第一印象就是错误消息质量。
