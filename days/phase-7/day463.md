# Day 463 · 准备 HHA 以便重写

> Casey 自己的资产打包格式叫 HHA(Handmade Hero Asset)。今天他为 HHA 格式的"重写"做准备——下一集会把 PNG 导入 HHA,Day 465 升级 HHA 版本。今天先理解 HHA 现状。

## 0 · 为什么要有这一天

Casey HH 此前的资产管线用预制的 .hha 文件,Casey 在视频里给观众下载。但本项目现在你有了自己写的 PNG 解码器(Day 453-459),可以从源 PNG 直接生成 HHA。这让资产管线"开源"——观众能自己构建,不依赖预制文件。

但要先理解 HHA 格式现状。Casey 在早期(Phase 4)定义了 HHA V0,现在要重写为 V1(Day 465)。Day 463 是过渡集——回顾 V0,设计 V1,准备迁移代码。

HHA 包含:
- **Bitmap assets**:纹理(从 PNG 转换)
- **Sound assets**:音频(从 WAV 转换)
- **Font / truetype**:字体
- **Metadata**:asset ID、tag、type

每个 HHA 文件有版本号、tag table、asset table。

让我把"游戏资产打包格式"的设计原则讲清楚,这是 Day 463-465 的核心。

**为什么要自定义格式?** PNG、WAV、GLTF 这些源格式各有优缺点。但游戏运行时,**加载速度**最重要——加载快 = 玩家少等。

PNG 加载慢的原因:
1. **DEFLATE 解压**:几 MB PNG 解压要几十 ms
2. **滤镜重建**:每个像素 5 个滤镜计算
3. **颜色转换**:8-bit → GPU 格式(BCn 压缩)转换

如果游戏运行时反复做这些,加载慢。**解决方案**:打包时一次性做完所有处理,运行时直接加载"准备好的"数据。这就是 HHA 这类格式的目的。

**HHA 的本质**。把 PNG 解码后的原始像素直接存,加上元数据(asset ID、宽高、格式)。运行时**不需要解码**,直接上传到 GPU。加载速度从 PNG 的几十 ms 降到几 ms。

```rust
// HHA bitmap 段
struct HhaBitmap {
    width: u32,
    height: u32,
    format: PixelFormat,  // RGBA8 / BC1 / BC3 / ...
    pixel_data_offset: u32,
    pixel_data_size: u32,
}

// 加载时
fn load_bitmap(hha: &HhaFile, bitmap: &HhaBitmap) -> GpuTexture {
    let pixels = &hha.data[bitmap.pixel_data_offset..][..bitmap.pixel_data_size];
    gpu.upload(bitmap.width, bitmap.height, bitmap.format, pixels)
}
```

**对比 PNG 加载**:

```rust
// PNG 加载(慢)
fn load_png(path: &Path) -> GpuTexture {
    let compressed = fs::read(path)?;          // IO
    let decompressed = png_decode(&compressed)?; // DEFLATE 解压 + 滤镜
    gpu.upload(decompressed)                    // GPU 上传
}
```

PNG 加载 = IO + 解压 + 滤镜 + GPU 上传。HHA 加载 = IO + GPU 上传。少两个慢步骤。

**HHA 的工程权衡**:

- **打包慢**:把 PNG 转换成 HHA 是离线步骤,慢可以接受
- **加载快**:运行时省时间,玩家体验好
- **格式需要版本化**:升级格式时要支持老存档——这就是 Day 463 的核心

**版本化的重要性**。游戏发布后,资产格式可能升级(加新字段、改压缩格式)。老玩家有旧 .hha 文件,新游戏读不了——除非版本号区分。

```rust
const HHA_VERSION_V0: u32 = 0;
const HHA_VERSION_V1: u32 = 1;

fn load_hha(data: &[u8]) -> Result<HhaFile> {
    let version = read_u32(data, 0)?;
    match version {
        HHA_VERSION_V0 => load_v0(data),
        HHA_VERSION_V1 => load_v1(data),
        _ => Err(format!("unsupported HHA version: {}", version)),
    }
}
```

**Casey HH 的版本策略**:V0 → V1 是"破坏性升级",V0 文件不再支持(Day 465)。商业游戏(Unturned、Mount & Blade)经常这样——大版本发布时换资产格式,玩家重新下载资产。

**为什么不直接用源格式(PNG)?** 有些现代游戏直接加载 PNG(快速 SSD 时代,DEFLATE 解压在 CPU 上比 IO 还快)。Casey HH 选 HHA 是 2014-2016 年的设计——那时 HDD 主流,IO 慢。今天 NVMe SSD 让 HHA 的优势变小,但仍存在(GPU 上传还是大块连续内存比 PNG 重新解码快)。

**工业标准格式**:

- **KTX**(Khronos Texture):跨平台 GPU 纹理格式,OpenGL/Vulkan 官方
- **DDS**(DirectDraw Surface):Microsoft 的,DirectX 用
- **ASTC**(Adaptive Scalable Texture Compression):移动端标准
- **CRN / KTX2**:压缩纹理 + 元数据

HHA 是 Casey 的简化教学版——商业游戏直接用 KTX2 / ASTC。

## 补充:二进制格式的设计原则

让我把 HHA 这种二进制格式的设计原则总结一下,这是 Day 463 的工程哲学。

**原则 1:Magic Number + Version**。每个二进制格式头部应该有:

- **Magic number**(4-8 字节):识别"这是个 X 格式文件"
- **Version**(1-4 字节):版本号

```rust
const HHA_MAGIC: [u8; 4] = *b"HHAH";  // 反过来是 "HHAH" = Handmade H Asset Header
const HHA_VERSION: u32 = 1;
```

加载时先验证 magic,再读 version,根据 version 选加载逻辑。

**原则 2:Fixed Layout Header**。头部字段固定(顺序、大小、对齐)。这让解析简单:

```rust
struct HhaHeader {
    magic: [u8; 4],      // offset 0
    version: u32,        // offset 4
    tag_count: u32,      // offset 8
    asset_count: u32,    // offset 12
    tag_table_offset: u32, // offset 16
    asset_table_offset: u32, // offset 20
}
// 总 24 字节
```

加载时一次性 read 24 字节,然后用 `from_bytes` 解析。简单快。

**原则 3:Offset Tables**。主表存"指向各 asset 数据的 offset",而非嵌套存储。这让任意 asset 可以快速定位,不用解析整个文件:

```rust
fn load_bitmap(hha: &HhaFile, idx: u32) -> Bitmap {
    let entry = &hha.asset_table[idx as usize];
    let data_offset = entry.data_offset as usize;
    let data_size = entry.data_size as usize;
    let data = &hha.raw[data_offset..data_offset + data_size];
    Bitmap {
        width: entry.width,
        height: entry.height,
        pixels: data,
    }
}
```

**原则 4:Alignment**。GPU 上传要求数据 16 字节对齐(SSE)或 256 字节对齐(AVX)。HHA 设计时把 asset 数据放在 16 字节对齐的 offset。

**原则 5:Endianness**。明确选择 little-endian(x86 原生)或 big-endian(网络)。HHA 用 little-endian(因为是 x86 主导)。跨平台库(KTX)用 little-endian。

**原则 6:不要过早优化**。先做 V0(简单),用着发现需求再升 V1。Casey HH V0 → V1 的演化就是这——V0 没有"sound asset"的某些字段,V1 加。

## 补充:HHA V0 → V1 的迁移

Day 465 实际重写时,Casey 改:

1. **加新字段**:某些 asset 类型加 metadata
2. **改字段大小**:u16 → u32(支持更多 asset)
3. **重组 layout**:某些数据移到不同 offset

迁移工具:`hha_upgrade_v0_to_v1`:

```rust
fn upgrade_v0_to_v1(v0_data: &[u8]) -> Vec<u8> {
    let v0 = parse_v0(v0_data);
    let mut v1 = Vec::new();
    // 写 V1 magic + version
    v1.extend_from_slice(b"HHAH");
    v1.extend_from_slice(&1u32.to_le_bytes());
    // 转换 tag table
    for tag in &v0.tags {
        // ... 加新字段或重组
    }
    // 转换 asset table
    // 转换 pixel data
    v1
}
```

迁移工具的存在让"格式升级"非破坏——老 .hha 文件可以批量转新格式。但 Casey HH 选择直接弃 V0(教学简化)。商业游戏必须支持迁移(老玩家不能强制重下载几十 GB 资产)。

## 补充:V0 → V1 的具体差异

让我猜测 Casey HH V0 vs V1 的具体差异(基于 HH 视频系列):

**V0 的局限**:

1. **Asset ID 是 u32**:V0 用 32 位 ID,够小项目,但大型 MMO 不够。V1 可能升 u64。
2. **Tag 系统简单**:V0 可能有 tag 数组,V1 加"tag 反向索引"(tag → assets)。
3. **无 CRC**:V0 文件损坏检测不到,V1 加 CRC。
4. **字符串内联**:V0 的 asset name 内联在 entry,V1 用 string table(offset + length),省空间。
5. **Asset 类型有限**:V0 只有 Bitmap/Sound,V1 加 Font/Material/Shader。

**V1 的字段示例**:

```rust
struct HhaHeaderV1 {
    magic: [u8; 4],         // "HHAH"
    version: u32,            // 1
    tag_count: u32,
    asset_count: u32,
    string_table_offset: u32,  // V1 新增
    string_table_size: u32,    // V1 新增
    tag_table_offset: u32,
    asset_table_offset: u32,
    crc32: u32,                 // V1 新增(整个文件的 CRC)
}

struct AssetEntryV1 {
    id: u64,                    // V1: u32 → u64
    kind: AssetKindV1,          // V1: 加 Font / Material / Shader
    name_offset: u32,           // V1: 用 string table,而非内联
    name_length: u32,
    data_offset: u64,           // V1: u32 → u64(支持大资产)
    data_size: u64,
    tag_count: u32,
    first_tag_index: u32,       // V1: 反向索引
}
```

V1 的优势:

- 支持更多 asset(64-bit ID + offset)
- 支持更多类型(Font、Shader、Material)
- 字符串共享(string table)
- 数据完整性(CRC32)
- 快速 tag 查询(反向索引)

V0 → V1 的字段映射:

| V0 字段 | V1 字段 | 转换 |
|---|---|---|
| `id: u32` | `id: u64` | 扩展(直接 cast) |
| `kind: u8` (Bitmap/Sound) | `kind: u8` (+Font/Shader/Material) | 直接 cast,新类型 default |
| `name: [u8; 32]` | `(name_offset, name_length)` | 拷到 string table,记 offset |
| `data_offset: u32` | `data_offset: u64` | cast |
| `data_size: u32` | `data_size: u64` | cast |
| `tags: [u32; 8]` | `tag_count + first_tag_index` | 拷到独立 tag index 表 |

每个字段单独处理,迁移工具完成对应转换。Day 465 的代码就是实现这些映射。

## 补充:数据完整性的多个层次

HHA V1 加 CRC32 是个升级,但 CRC 只检测"意外损坏"。工业级资产管线有多个层次的完整性:

**层 1:CRC32**(V1 加)。检测 99.9999% 意外损坏。**不防恶意篡改**。

**层 2:HMAC**。带密钥的 hash。攻击者不知道密钥,无法伪造匹配的 HMAC。用于"反作弊"——玩家修改资产=被 ban。

**层 3:数字签名**。私钥签名,公钥验证。最强——非对称加密,玩家无法伪造。游戏厂商用于"DLC 验证"——只允许官方 DLC 加载。

**层 4:加密整个文件**。资产文件加密,运行时解密。彻底防读但增加加载时间(解密 CPU 开销)。

Casey HH V1 选 CRC32——基础完整性,够教学项目。商业游戏选 HMAC 或签名(防 mod、防作弊)。理解层次让你能选合适的方案。

## 2 · 心智模型

### 类比:图书馆的图书目录

HHA 像图书馆的图书目录。每本书(资产)有:
- ID(书架位置)
- 标题(资产名)
- 类型(书 / 杂志 / DVD)
- 元数据(作者、年份)

V0 是简化版目录,V1 加上 ISBN(校验)、关联书籍(依赖)等。读者(V0 解析器)看不懂 V1 目录——要升级。

### HHA V0 布局(简化)

```
+-------------------------+
| Magic: "HHA0" (4 字节)  |  标识文件类型 + 版本
+-------------------------+
| TagCount: u32           |  tag 数量
+-------------------------+
| TagTable: Tag[]         |  TagCount 个 tag
|   每个含 name(string)  |
+-------------------------+
| AssetCount: u32         |  资产数量
+-------------------------+
| AssetTable: Asset[]     |  AssetCount 个资产描述
+-------------------------+
| AssetData: ...          |  实际数据(纹理像素、音频样本)
+-------------------------+
```

### Rust 表示

```rust
struct HhaHeader {
    magic: [u8; 4],          // "HHA0"
    version: u32,
}

struct HhaTag {
    name: String,            // UTF-8 字符串
    // (V0 用 null-terminated,V1 用长度前缀)
}

enum HhaAssetType {
    Bitmap,
    Sound,
    Font,
}

struct HhaBitmapAsset {
    width: u32,
    height: u32,
    pixels_offset: u32,  // 在文件中的偏移
    pixels_size: u32,
}

struct HhaAsset {
    asset_type: HhaAssetType,
    name: String,
    data: HhaAssetData,  // enum (Bitmap / Sound / Font)
}
```

### V1 改进点

```rust
struct HhaHeaderV1 {
    magic: [u8; 4],          // "HHA1"
    version: u32,
    crc32: u32,              // 整个文件的 CRC
    tag_count: u32,
    asset_count: u32,
    // ...
}

struct HhaTagV1 {
    name_len: u32,           // 长度前缀(替代 null-terminated)
    name: Vec<u8>,           // UTF-8 字节
}

struct HhaAssetV1 {
    asset_type: u16,         // 2 字节(替代 4)
    name: String,
    crc32: u32,              // 单 asset CRC
    deps_count: u32,         // 依赖数
    deps: Vec<u32>,          // 依赖的 asset ID
    // ...
}
```

每行解释:
- V1 加文件级 CRC,损坏立刻检测。
- 字符串长度前缀,避免 null-terminated 的安全问题(类似 Pascal 字符串 vs C 字符串)。
- type 用 2 字节,够表达 65536 种,省 2 字节/资产。
- 加 dependency table,表达"贴图 A 是模型 B 的漫反射"。

### 迁移工具的设计

```rust
fn migrate_v0_to_v1(v0_data: &[u8]) -> Result<Vec<u8>, String> {
    let v0 = parse_hha_v0(v0_data)?;
    let v1 = HhaV1 {
        magic: *b"HHA1",
        version: 1,
        crc32: 0,  // 占位,最后算
        tags: v0.tags.iter().map(|t| HhaTagV1::from_v0(t)).collect(),
        assets: v0.assets.iter().map(|a| HhaAssetV1::from_v0(a)).collect(),
        data: v0.data.clone(),
    };
    let mut bytes = serialize_hha_v1(&v1)?;
    // 最后算 CRC 并填回去
    let crc = crc32(&bytes);
    bytes[8..12].copy_from_slice(&crc.to_be_bytes());
    Ok(bytes)
}
```

每行解释:
- 读 V0 内存表示。
- 转 V1 内存表示。
- 序列化 V1 到字节流。
- 算 CRC 填回(CRC 不能包含自己,所以最后填)。

## 3 · 四域深入

### 3.1 · 游戏编程视角

工业资产格式:

- **Unreal .uasset**:复杂,支持版本化、依赖
- **Unity .asset**:类似 Unreal,YAML 或 binary
- **glTF**:开源 3D 模型格式,Khronos 标准
- **USD**:Pixar 的场景格式,工业级

每个格式都解决"资产打包 + 版本 + 依赖"问题。Casey HH 简化版 HHA 是教学用,概念相同。

**版本化策略**:
- **breaking change**:版本号 +1,V1 不能读 V0(必须迁移)
- **compatible change**:版本号不变,新字段可选
- **casey 选**:大改 = V1,完全 breaking,迁移工具必须运行

### 3.2 · 图形学视角

HHA 之外的资产格式:

- **KTX2**:Khronos 纹理容器,支持 BCn / ETC / ASTC
- **DDS**:DirectDraw Surface,Windows 传统
- **BASIS Universal**:超压缩,跨平台
- **glTF binary**:模型 + 贴图打包

游戏工业趋势:**单一容器,多种压缩**。运行时选合适的解压路径(GPU 友好 / CPU 兼容)。

### 3.3 · Linux 系统编程视角

Linux 文件格式版本化:

- **ELF**:有版本号 + ABI 标记
- **ext4**:superblock 有版本
- **Btrfs**:格式版本 + 兼容位
- **systemd unit**:有版本字段

每个长期演化的格式都要"版本号 + 迁移路径"。HHA V0→V1 是这个原则的小规模演练。

```bash
# 看 ELF 版本
readelf -h /bin/ls | grep -i version

# 看 ext4 版本
dumpe2fs /dev/sda1 | head -10
```

### 3.4 · Rust 生态视角

Rust 的版本化资产序列化:

- **`serde`**:通用序列化框架
- **`bincode`**:二进制序列化,紧凑
- **`rmp-serde`**:MessagePack
- **`postcard`**:嵌入式友好

```rust
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize)]
struct HhaHeader {
    magic: [u8; 4],
    version: u32,
    // ...
}

let bytes = bincode::serialize(&header)?;
let header: HhaHeader = bincode::deserialize(&bytes)?;
```

bincode 自动处理"哪些字段、什么顺序、字节序",减化代码。但 Casey HH 手写,控制每一字节。

## 5 · 对照与变奏

**不同资产格式的演化**:

| 格式 | 起源 | 演化 |
|---|---|---|
| BMP | 1980s | 几乎不变 |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"长度前缀字符串"比"null-terminated"更安全?

**参考解答**:null-terminated 字符串依赖读到 \0 才结束。如果恶意构造的字符串没有 \0,解析器读到 buffer 边界 → buffer overflow。

长度前缀字符串显式声明长度,解析器读 N 字节就停。即使数据损坏,最多读 N 字节(已知),不会越界。

C 语言 strcpy / strcat 的众多 CVE 都来自 null-terminated 的设计缺陷。Rust 的 String 用长度前缀(usize + UTF-8),从根本上避免。

### Lv2 · 动手实践

**题**:定义 HHA V0 和 V1 的 Rust struct,写 V0 解析器(读 magic、version、tag count)。

**参考解答**:

```rust
#[derive(Debug)]
struct HhaHeaderV0 {
    magic: [u8; 4],
    version: u32,
}

#[derive(Debug)]
struct HhaTagV0 {
    name: String,  // null-terminated in V0
}

#[derive(Debug)]
struct HhaFileV0 {
    header: HhaHeaderV0,
    tags: Vec<HhaTagV0>,
}

fn parse_v0(data: &[u8]) -> Result<HhaFileV0, String> {
    if data.len() < 8 { return Err("too short".into()); }
    let magic = data[..4].try_into().unwrap();
    if &magic != b"HHA0" { return Err("bad magic".into()); }
    let version = u32::from_le_bytes([data[4], data[5], data[6], data[7]]);
    
    let mut cursor = 8;
    let tag_count = u32::from_le_bytes([data[cursor], data[cursor+1], data[cursor+2], data[cursor+3]]) as usize;
    cursor += 4;
    
    let mut tags = Vec::with_capacity(tag_count);
    for _ in 0..tag_count {
        // V0: null-terminated
        let start = cursor;
        while cursor < data.len() && data[cursor] != 0 {
            cursor += 1;
        }
        let name = String::from_utf8(data[start..cursor].to_vec())
            .map_err(|_| "bad utf8")?;
        cursor += 1;  // skip null
        tags.push(HhaTagV0 { name });
    }
    
    Ok(HhaFileV0 {
        header: HhaHeaderV0 { magic, version },
        tags,
    })
}

fn main() {
    // 构造一个最小 V0 文件
    let mut v0 = Vec::new();
    v0.extend_from_slice(b"HHA0");
    v0.extend_from_slice(&0u32.to_le_bytes());  // version
    v0.extend_from_slice(&2u32.to_le_bytes());  // tag count
    v0.extend_from_slice(b"hero\0");            // tag 0
    v0.extend_from_slice(b"enemy\0");           // tag 1
    
    let parsed = parse_v0(&v0).unwrap();
    println!("Version: {}", parsed.header.version);
    println!("Tags: {:?}", parsed.tags);
}
```

每行解释:
- 用 little-endian(HHA 用 LE,与 PNG 的 BE 不同)。
- V0 用 null-terminated 字符串(简单但脆弱)。
- 验证 magic 防止误识别。

## 8 · Rust / Arch 落地代码

完整 V0 + V1 + 迁移工具骨架:

```rust
use std::io::{Read, Write};

#[derive(Debug, Clone)]
struct HhaHeaderV0 {
    magic: [u8; 4],
    version: u32,
}

#[derive(Debug, Clone)]
struct HhaTagV0 {
    name: String,
}

#[derive(Debug, Clone)]
struct HhaFileV0 {
    header: HhaHeaderV0,
    tags: Vec<HhaTagV0>,
}

#[derive(Debug, Clone)]
struct HhaHeaderV1 {
    magic: [u8; 4],
    version: u32,
    crc32: u32,
}

#[derive(Debug, Clone)]
struct HhaTagV1 {
    name_len: u32,
    name: String,
}

#[derive(Debug, Clone)]
struct HhaFileV1 {
    header: HhaHeaderV1,
    tags: Vec<HhaTagV1>,
}

fn parse_v0(data: &[u8]) -> Result<HhaFileV0, String> {
    if data.len() < 12 { return Err("too short".into()); }
    let mut magic = [0u8; 4];
    magic.copy_from_slice(&data[..4]);
    if &magic != b"HHA0" { return Err(format!("bad magic: {:?}", magic)); }
    let version = u32::from_le_bytes([data[4], data[5], data[6], data[7]]);
    
    let mut cursor = 8;
    let tag_count = u32::from_le_bytes([data[cursor], data[cursor+1], data[cursor+2], data[cursor+3]]) as usize;
    cursor += 4;
    
    let mut tags = Vec::with_capacity(tag_count);
    for _ in 0..tag_count {
        let start = cursor;
        while cursor < data.len() && data[cursor] != 0 {
            cursor += 1;
        }
        let name = String::from_utf8(data[start..cursor].to_vec()).map_err(|_| "bad utf8")?;
        cursor += 1;
        tags.push(HhaTagV0 { name });
    }
    
    Ok(HhaFileV0 {
        header: HhaHeaderV0 { magic, version },
        tags,
    })
}

fn crc32_simple(data: &[u8]) -> u32 {
    let mut crc: u32 = 0xFFFFFFFF;
    for &b in data {
        crc ^= b as u32;
        for _ in 0..8 {
            crc = if crc & 1 != 0 { 0xEDB88320 ^ (crc >> 1) } else { crc >> 1 };
        }
    }
    crc ^ 0xFFFFFFFF
}

fn serialize_v1(v1: &HhaFileV1) -> Vec<u8> {
    let mut out = Vec::new();
    out.extend_from_slice(&v1.header.magic);
    out.extend_from_slice(&v1.header.version.to_le_bytes());
    out.extend_from_slice(&0u32.to_le_bytes());  // CRC placeholder
    out.extend_from_slice(&(v1.tags.len() as u32).to_le_bytes());
    for tag in &v1.tags {
        out.extend_from_slice(&tag.name_len.to_le_bytes());
        out.extend_from_slice(tag.name.as_bytes());
    }
    // 填回 CRC
    let crc = crc32_simple(&out);
    out[8..12].copy_from_slice(&crc.to_le_bytes());
    out
}

fn migrate_v0_to_v1(v0: &HhaFileV0) -> HhaFileV1 {
    let tags = v0.tags.iter().map(|t| HhaTagV1 {
        name_len: t.name.len() as u32,
        name: t.name.clone(),
    }).collect();
    
    HhaFileV1 {
        header: HhaHeaderV1 {
            magic: *b"HHA1",
            version: 1,
            crc32: 0,  // 占位
        },
        tags,
    }
}

fn main() {
    // 构造一个 V0 测试文件
    let mut v0_bytes = Vec::new();
    v0_bytes.extend_from_slice(b"HHA0");
    v0_bytes.extend_from_slice(&0u32.to_le_bytes());
    v0_bytes.extend_from_slice(&2u32.to_le_bytes());
    v0_bytes.extend_from_slice(b"hero\0");
    v0_bytes.extend_from_slice(b"enemy\0");
    
    println!("V0 bytes: {} bytes", v0_bytes.len());
    let v0 = parse_v0(&v0_bytes).expect("parse V0");
    println!("V0: version={}, {} tags", v0.header.version, v0.tags.len());
    for (i, t) in v0.tags.iter().enumerate() {
        println!("  Tag {}: '{}'", i, t.name);
    }
    
    // 迁移到 V1
    let v1 = migrate_v0_to_v1(&v0);
    let v1_bytes = serialize_v1(&v1);
    println!("\nV1 bytes: {} bytes", v1_bytes.len());
    println!("V1 magic: {:?}, version={}, crc=0x{:08x}",
        std::str::from_utf8(&v1_bytes[..4]).unwrap(),
        u32::from_le_bytes(v1_bytes[4..8].try_into().unwrap()),
        u32::from_le_bytes(v1_bytes[8..12].try_into().unwrap()));
    
    // 验证 CRC
    let crc_stripped = {
        let mut b = v1_bytes.clone();
        b[8..12].copy_from_slice(&0u32.to_le_bytes());
        b
    };
    let computed = crc32_simple(&crc_stripped);
    println!("Re-computed CRC: 0x{:08x}", computed);
    
    // 模拟"损坏" - 改一个字节
    let mut corrupted = v1_bytes.clone();
    corrupted[16] ^= 0xFF;
    let crc_stripped2 = {
        let mut b = corrupted.clone();
        b[8..12].copy_from_slice(&0u32.to_le_bytes());
        b
    };
    let crc_corrupted = crc32_simple(&crc_stripped2);
    println!("Corrupted CRC: 0x{:08x} (should differ)", crc_corrupted);
}
```

每行解释:
- `parse_v0` 读 V0 文件。
- `migrate_v0_to_v1` 在内存表示层转换。
- `serialize_v1` 输出 V1 字节流,最后填 CRC。
- `crc32_simple` 表驱动版本的简化(直接按位计算,慢但简单)。
- 测试"损坏"场景:改 1 字节后 CRC 变化,检测到。
