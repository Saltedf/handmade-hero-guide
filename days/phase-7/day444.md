# Day 444 · 为世界生成器写桩函数

> Casey 即将开始一个 8 集(day444-450)的子项目:程序化生成 3D 房间迷宫。今天他做的不是写迷宫,而是**先搭出代码骨架**——每个函数先返回"假"数据(stub),让上层能编译、能跑,然后逐个填实。这是大型功能开发的标准节奏。

## 0 · 为什么要有这一天

想象你要写一个 1000 行的功能。**两种做法**:

做法 A:从顶到底一气写完。结果:写到 800 行发现一个早期设计错误,大段返工。

做法 B:先搭骨架。每个函数先写签名 + 注释 + 返回假数据(stub),让整体跑通。然后逐个填充。结果:每个函数独立测试,早期设计错误很快暴露。

Casey 这一天用做法 B。他规划了世界生成器的所有子函数:`GenerateRoom`, `PlaceRoom`, `ConnectRooms`, `CheckOverlap` 等等,**先全部写成 stub**,让上层 `GenerateWorld` 调用链能编译能跑。然后他跑一次"空跑",看调用顺序、参数传递、内存布局是否合理。确认骨架对之后,Day 445+ 再逐个填实。

这种做法在工程上叫**自顶向下(top-down)**开发,配合**桩函数(stub function)** 技术。它的精神:**先把骨架搭对,再填肉**。

为什么 stub 这么重要?让我从工程经济学角度算一下。

假设你要写 10 个函数的功能。如果一口气写完再集成,假设每个函数有 30% 概率需要返工(参数不对、返回类型错、调用顺序错),平均返工成本 = 重写 × 函数依赖数。在依赖链长的情况下,返工成本可能指数增长——前面的错误让你后面 5 个函数都白写。

stub 的成本:每个函数 +5 行骨架代码,5 分钟。10 个函数 = 50 分钟。

stub 的收益:集成时发现架构错误,改的只是 50 行骨架,不是 1000 行实现。如果 30% 概率发生这种事,期望节省 = 30% × 1000 行 × 重写成本 = 几天工程时间。

**stub 是廉价的保险**。

另一个常被忽略的价值:**stub 帮助思考**。当你坐下来写一个 stub 时,你被迫思考:"这个函数的输入是什么?输出是什么?它在上层流程中的位置是什么?"——这些问题在设计阶段就该回答,但很多人写到一半才意识到。stub 强制你提前面对这些设计决策。

完成这一天后,你能做到:为一个想象中的 10 函数功能写出完整 stub 骨架,编译通过,运行能跑(即使输出全是假数据),并能解释这种做法相比"一气呵成"的优势。

## 2 · 心智模型

### 类比:盖楼先搭脚手架

盖大楼不会一上来就砌砖——先搭脚手架,这是临时的金属框架,让工人有立足之地。脚手架本身不是楼,但**让楼的建造成为可能**。

软件的"脚手架"就是 stub 函数。它们本身不做有用的事,但让整个调用链能跑通,让你**尽早发现架构问题**——比如某个函数应该返回什么类型、某两个函数的调用顺序对不对、内存谁分配谁释放。

### 严谨原理:自顶向下 + stub 函数

**自顶向下**:从最高层(`GenerateWorld`)开始,逐层下钻。每一层先把签名定下来,内部调用下一层(还是 stub)。

**Stub 函数的特征**:
- 函数签名完整(参数、返回类型)
- 内部返回"假数据"或 `todo!()` panic
- 有 doc comment 说明"这个函数最终要做什么"
- 编译通过(类型正确)

让我把"自顶向下"和"自底向上"的对比讲透,这是软件工程最经典的方法论辩论。

**自顶向下(Top-Down)**:从最抽象开始,逐步细化。`GenerateWorld` 先写,但只是个空壳调用 `GenerateRoom`。`GenerateRoom` 也是空壳,调用 `PlaceRoom`。一直下钻到能用语言原语表达的层次。然后从下往上逐层填实。

**优势**:
- 每一层的设计意图明确(因为它服务上层)
- 集成风险低(骨架一开始就跑通)
- 早期能发现架构错误

**劣势**:
- 下层函数的实际可行性不确定(`GenerateRoom` 写完后才发现下层 `PlaceRoom` 实现不出来)
- 设计阶段需要"前瞻性",决定下层接口

**自底向上(Bottom-Up)**:从最具体开始,组合成更大的单元。先写工具函数(Vec3、Room、AABB),再写组合函数(rooms_overlap、room_volume),最后写主流程(GenerateWorld)。

**优势**:
- 每个下层单元独立测试,质量高
- 复用性强(底层工具可以独立用)
- 不依赖"前瞻设计",可以边做边发现

**劣势**:
- 集成阶段才发现架构问题(写了 5 个工具函数,发现主流程用不上)
- 难以并行(底层没好之前上层不能写)

**Casey 的混合实践**。Casey HH 一直是自顶向下为主:

- Day 1:写 `WinMain` 调用 `GameUpdateAndRender`,后者是空壳
- Day 2:填 GameUpdateAndRender,调 sound、input、render 子 stub
- Day 3+:逐层填实

但 Casey 也会**自底向上**地处理基础数据结构。比如知道后面要用 Vec3、Mat4,他会先实现这些(底层),再往上搭应用层。这种"基础数据结构自底向上 + 业务流程自顶向下"的混合,是工业最常见的实践。

**接口先行(Interface First)**。工业大型团队的做法:在写实现之前,所有相关人**先约定接口**(函数签名、数据结构、错误码)。然后大家按接口 stub,并行实现。

```rust
// 一开始所有人同意这个 trait:
trait RoomGenerator {
    fn generate(&mut self, params: &GenParams) -> Result<Room, GenError>;
    fn validate(&self, room: &Room) -> bool;
}

// 团队 A 写一种 generator:
struct GridRoomGenerator { ... }
impl RoomGenerator for GridRoomGenerator { ... }

// 团队 B 同时写另一种:
struct OrganicRoomGenerator { ... }
impl RoomGenerator for OrganicRoomGenerator { ... }
```

只要 trait 定义稳定,两个团队可以并行工作,集成时零冲突。这就是 Rust trait / Go interface / Java interface / C++ 抽象基类的工程价值——它们让"接口"成为一等公民。

**Rust 的 stub 模式**:

```rust
/// 在 (origin, size) 范围内生成一个房间。
/// TODO(day445): 实现真正的房间生成逻辑。
fn generate_room(rng: &mut Rng, origin: Vec3, size: Vec3) -> Room {
    let _ = (rng, origin, size);  // 暂时忽略参数,避免 warning
    Room {
        origin: Vec3::ZERO,
        size: Vec3::new(10.0, 4.0, 10.0),
        // 假数据
    }
}

/// 检查两个房间是否重叠。
/// TODO(day449): 实现 AABB 重叠检测。
fn rooms_overlap(a: &Room, b: &Room) -> bool {
    let _ = (a, b);
    false  // 假装不重叠,让上层能继续跑
}
```

每行解释:
- `let _ = (rng, origin, size);` — 故意忽略参数,避免 Rust 的"unused variable"警告。`_` 是 Rust 的"显式忽略"模式。
- `Room { ... }` 返回字面量值。上层用这个返回值能继续跑。
- `todo!()` 是 Rust 的 macro,在 stub 阶段可以代替函数体——只要没人调用,程序不会 panic。一旦被调用,panic 提示"这个 stub 没实现"。

### Stub 的三种风格

**风格 1:返回常量**(最简单):

```rust
fn room_volume(room: &Room) -> f32 {
    100.0  // 假装 100 立方米
}
```

**风格 2:返回合理猜测**(中等):

```rust
fn room_volume(room: &Room) -> f32 {
    room.size.x * room.size.y * room.size.z  // 实际公式但没考虑墙厚度
}
```

**风格 3:`todo!()`**(最严格):

```rust
fn room_volume(room: &Room) -> f32 {
    todo!("compute volume from {:?}", room.size)
}
```

- 编译通过
- 运行时调用即 panic,提示"还没实现"
- 适合"骨架阶段不希望被误调用"

**Casey 偏好**:风格 2(返回合理猜测),让上层调用链能跑通、输出有意义的 debug 信息。风格 3 适合"我绝对不想让上层先用假数据跑"的场景。

### 骨架验证

骨架写完,运行应该看到:

[World Gen] Starting world generation

### Rust 的 todo! / unimplemented! / panic! 三者

```rust
todo!()        // 还没实现,打算以后做
unimplemented!()  // 不打算实现(历史上等价 todo,现在很少用)
panic!("msg")  // 不该到这里,出现了说明 bug
unreachable!() // 编译器保证不会执行到这里
```

Rust 1.40+ 起 `todo!()` 和 `unimplemented!()` 几乎等价,但语义上 `todo!()` 表达"打算做",`unimplemented!()` 表达"不做"。

让我把这四个 panic macro 彻底区分清楚,因为初学者经常混淆。

**`panic!("msg")`**:通用的"程序错误退出"。它表示"运行到这就是 bug",你预期这里**不应该被执行到**。比如解析失败、不变式违反:

```rust
fn get_player(state: &State) -> &Player {
    state.player.as_ref().expect("player must be initialized")
    // 或更直接:
    // state.player.as_ref().unwrap_or_else(|| panic!("player not init at frame {}", state.frame))
}
```

`panic!` 触发 unwind(默认)或 abort(`panic = "abort"` 配置)。生产代码慎用——它会导致整个进程退出。

**`unreachable!()`**:专门表达"编译器/类型系统保证不会执行到这里"。和 `panic!` 类似,但语义更强——读者一看就知道"这里在数学上不可能":

```rust
match direction {
    Direction::Left => move_left(),
    Direction::Right => move_right(),
    Direction::Up => move_up(),
    Direction::Down => move_down(),
    // 编译器要求穷尽,但实际上没有其他方向
}
// 如果用 if-else chain 写,可能加 unreachable!()
```

debug build 检查;release build 可能 optimize 掉(假设真不可达)。如果 release 跑到 `unreachable!()`,是 UB(undefined behavior),后果严重。

**`todo!()` 和 `unimplemented!()`**:专门为 stub 阶段。它们都展开成 `panic!("not yet implemented: ...")`,但表达意图不同:

- `todo!("implement by Friday")` — 我打算做,只是还没
- `unimplemented!()` — 不打算实现(常见于"这个 trait method 对我这个类型无意义")

实战:stub 阶段用 `todo!()`,trait method 不适用用 `unimplemented!()`。

**`unreachable!()` 和 `todo!()` 的微妙差别**:很多程序员把 `unreachable!()` 当 stub 用——这是**错的**。`unreachable!()` 在 release 模式可能被优化掉,变成真正未定义行为,导致程序行为不可预测。stub 应该用 `todo!()`,它永远 panic。

```rust
// 错:用 unreachable! 做 stub,release 模式可能崩
fn future_function() -> i32 {
    unreachable!()  // 编译器可能假设这里真的不执行
}

// 对:用 todo! 做 stub
fn future_function() -> i32 {
    todo!()
}
```

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发的"自顶向下 + stub"是 Casey 风格核心。Casey 在 HH 反复强调这种节奏:

- 先写高层控制流,再写细节
- 先写"我想做什么",再写"具体怎么做"
- 先保证整体能跑,再优化局部

工业大型游戏(100+ 程序员)更严格:**接口先行(API first)**。在写实现之前,先定义好模块接口(头文件 / trait),所有人按接口 stub,然后并行填实。这是现代软件工程的基础。

**对应反面教材**:许多初学者"细节优先"——一上来写 `room_volume` 的精确公式,然后发现 room 数据结构里没 `wall_thickness` 字段,要返工。

工程坑:
- **stub 太多拖延**:架构正确但永远不填实,功能烂尾
- **stub 误导**:stub 返回值"碰巧对",让人以为实现了;真实现改变行为

对策:**Day 445+ 必须填实**。stub 只是过渡,不是终点。

### 3.2 · 图形学视角

图形程序里 stub 用于:

- **占位资源**:加载贴图前先返回纯色纹理,让渲染管线能跑
- **占位 shader**:用简单 unlit shader,等美术 / 程序员写最终版本
- **占位模型**:用立方体代替最终模型

游戏开发节奏:**先粗后细**。粗版本(stub)让你看到整体,细版本(实现)让你看到细节。两者都要。

### 3.3 · Linux 系统编程视角

Linux 内核开发也用 stub。一个新 syscall 的引入路径:

1. **API 头文件**:定义 `SYS_new_thing` 编号和签名
2. **stub 实现**:`SYSCALL_DEFINE1(new_thing, ...) { return -ENOSYS; }` —— 返回"未实现"
3. **glibc 包装**:用户态库提供 `new_thing()` 函数
4. **真实实现**:几个版本后才填,有人需要
5. **稳定化**:几年后才进 LTS

`-ENOSYS` 就是 Linux 的 `todo!()`。

**类似地**,Rust 标准库有些 API 是 nightly-only,本质上 stub——稳定化之前允许变动。

### 3.4 · Rust 生态视角

Rust 对 stub 的支持特别好:

**A. `todo!()` 和 `unimplemented!()`**

```rust
fn future_feature(x: i32) -> i32 {
    todo!("implement X+Y logic for {}", x)
}
```

panic 信息包含 `todo!` 字面量,帮你定位未实现的代码。

**B. Trait 的默认实现**

```rust
trait RoomGenerator {
    fn generate(&mut self, params: Params) -> Room {
        // 默认实现:返回空白房间
        Room::default()
    }
    fn validate(&self, room: &Room) -> bool {
        true  // 默认总是有效
    }
}
```

Trait 的"默认方法"是 stub 的优雅版本——实现者可以选择覆盖或用默认。

**C. `cfg(feature = " stub ")` 条件编译**

```rust
#[cfg(not(feature = "real_generator"))]
fn generate_room(...) -> Room { Room::default() }  // stub

#[cfg(feature = "real_generator")]
fn generate_room(...) -> Room { /* 真实现 */ }
```

通过 Cargo feature flag 切换 stub / 真实现。这种模式在测试和渐进开发里很有用。

**D. `mockall` crate(测试 stub)**

```rust
use mockall::*;
#[automock]
trait RoomValidator {
    fn validate(&self, room: &Room) -> bool;
}

let mut mock = MockRoomValidator::new();
mock.expect_validate().returning(|_| true);  // 测试时总返回 true
```

测试中"模拟"依赖,让单测不依赖真实实现。

## 5 · 对照与变奏

**不同语言的 stub 风格**:

| 语言 | stub 模式 |
|---|---|
| Rust | `todo!()` panic |
| C/C++ | `assert(false); return 0;` |
| Python | `raise NotImplementedError` |
| Go | `panic("not implemented")` |
| Java | `throw new UnsupportedOperationException();` |
| TypeScript | `throw new Error("todo");` |

**自顶向下 vs 自底向上的历史**:
- 1970s:Niklaus Wirth 推广自顶向下("Algorithms + Data Structures = Programs")
- 1980s:面向对象鼓励"职责分配",自顶向下弱化
- 2000s:测试驱动回归自顶向下(从用户场景开始)
- 2010s:微服务接口先行,自顶向下复兴

**Casey 的选择**:自顶向下,因为他强调"理解整体"。但他偶尔也用自底向上(比如手写数学库是自底向上,从 Vec2 开始)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:stub 函数和 mock 函数有什么区别?分别在什么场景用?

**参考解答**:
- **stub**:开发阶段,临时占位,等真实现来填。意图是"让骨架能跑"。
- **mock**:测试阶段,模拟依赖,意图是"测试时不依赖真实实现"。Mock 通常有"期望调用次数 / 参数"等行为验证。

例:
- stub:`fn generate_room() -> Room { Room::default() }` — 开发时占位
- mock:`mock.expect_generate().times(2).returning(|_| Room::new())` — 测试时期望被调 2 次

**何时用 stub**:开发一个还没实现的功能。**何时用 mock**:单元测试一个函数,但它依赖数据库/网络/其他复杂模块。

### Lv2 · 动手实践

**题**:为一个假想的"程序化迷宫生成器"写 5 个 stub 函数,串成一个完整的调用链。运行后看到调用顺序的 debug 输出。

**参考解答**:

```rust
#[derive(Debug, Default)]
struct Room {
    id: usize,
    origin: (f32, f32, f32),
    size: (f32, f32, f32),
}

#[derive(Debug, Default)]
struct Maze {
    rooms: Vec<Room>,
    connections: Vec<(usize, usize)>,
}

fn generate_world(num_rooms: usize) -> Maze {
    println!("[World] Generating {} rooms...", num_rooms);
    let mut maze = Maze::default();
    for i in 0..num_rooms {
        let room = generate_room(i);
        let placed = place_room(&mut maze, room);
        if !placed {
            println!("[World] Failed to place room {}", i);
            continue;
        }
    }
    println!("[World] Connecting rooms...");
    connect_rooms(&mut maze);
    println!("[World] Done. {} rooms, {} connections",
             maze.rooms.len(), maze.connections.len());
    maze
}

fn generate_room(id: usize) -> Room {
    println!("  [Gen] Room {} (stub)", id);
    Room {
        id,
        origin: (0.0, 0.0, 0.0),
        size: (10.0, 4.0, 10.0),
    }
}

fn place_room(maze: &mut Maze, room: Room) -> bool {
    println!("  [Place] Checking room {} against existing {} rooms",
             room.id, maze.rooms.len());
    for existing in &maze.rooms {
        if rooms_overlap(&room, existing) {
            // stub 总返回 false,所以这里不会触发
            return false;
        }
    }
    maze.rooms.push(room);
    true
}

fn rooms_overlap(a: &Room, b: &Room) -> bool {
    let _ = (a, b);
    false  // STUB
}

fn connect_rooms(maze: &mut Maze) {
    // STUB: 把所有房间两两连接
    for i in 0..maze.rooms.len() {
        for j in (i+1)..maze.rooms.len() {
            maze.connections.push((i, j));
        }
    }
}

fn main() {
    let _maze = generate_world(5);
}
```

每行解释:
- `#[derive(Default)]` — Rust 自动生成 `Room { id: 0, origin: (0,0,0), size: (0,0,0) }`,方便 stub 用 `Room::default()`。
- `let _ = (a, b);` — stub 忽略参数,显式 suppress 警告。
- `println!` 用 `[World]`、`[Gen]`、`[Place]` 前缀,方便看调用链。
- `for i in 0..num_rooms` — Rust 范围迭代。
- `connect_rooms` 完全连接(O(N²)),实际会用最小生成树。

### Rust 完整可跑示例

把 Lv2 扩展,加上 Cargo feature flag 切换 stub / 真实现:

```rust
// src/lib.rs 或 src/main.rs

#[derive(Debug, Clone)]
pub struct Room {
    pub id: usize,
    pub origin: (f32, f32, f32),
    pub size: (f32, f32, f32),
}

#[derive(Debug, Default)]
pub struct Maze {
    pub rooms: Vec<Room>,
    pub connections: Vec<(usize, usize)>,
}

// Stub vs Real 实现切换
#[cfg(not(feature = "real_generator"))]
pub fn generate_room(id: usize) -> Room {
    println!("  [stub] generate_room({})", id);
    Room {
        id,
        origin: (0.0, 0.0, 0.0),
        size: (10.0, 4.0, 10.0),
    }
}

#[cfg(feature = "real_generator")]
pub fn generate_room(id: usize) -> Room {
    // 真:每个房间随机大小
    let seed = id as u32 * 2654435761;  // Knuth multiplicative
    let size_x = 5.0 + (seed & 0xF) as f32;
    let size_z = 5.0 + ((seed >> 4) & 0xF) as f32;
    Room {
        id,
        origin: (id as f32 * 15.0, 0.0, 0.0),
        size: (size_x, 4.0, size_z),
    }
}

pub fn rooms_overlap(a: &Room, b: &Room) -> bool {
    // AABB 重叠检测(真实现,不依赖 feature)
    let (ax0, ay0, az0) = a.origin;
    let (ax1, ay1, az1) = (ax0 + a.size.0, ay0 + a.size.1, az0 + a.size.2);
    let (bx0, by0, bz0) = b.origin;
    let (bx1, by1, bz1) = (bx0 + b.size.0, by0 + b.size.1, bz0 + b.size.2);

    ax0 < bx1 && ax1 > bx0 &&
    ay0 < by1 && ay1 > by0 &&
    az0 < bz1 && az1 > bz0
}

pub fn generate_world(n: usize) -> Maze {
    let mut maze = Maze::default();
    for i in 0..n {
        let room = generate_room(i);
        let mut ok = true;
        for existing in &maze.rooms {
            if rooms_overlap(&room, existing) {
                println!("  Room {} overlaps!", i);
                ok = false;
                break;
            }
        }
        if ok { maze.rooms.push(room); }
    }
    maze
}

fn main() {
    let maze = generate_world(5);
    println!("Final maze: {} rooms", maze.rooms.len());
    for r in &maze.rooms {
        println!("  Room {}: origin={:?} size={:?}", r.id, r.origin, r.size);
    }
}
```

在 `Cargo.toml` 加:
```toml
[features]
default = []
real_generator = []
```

跑通:
```bash
# 默认(stub)
cargo run
# 输出:Room 0/1/.../4 origin=(0,0,0) size=(10,4,10),都重叠所以只放进去第一个

# 真实现
cargo run --features real_generator
# 输出:Room 0 at x=0, Room 1 at x=15, Room 2 at x=30,...
# 每个 size 不同
```

每行解释:
- `#[cfg(not(feature = "..."))]` — 条件编译,根据 Cargo feature 切换实现。
- AABB 重叠公式:两个盒子在每个轴上"投影区间"都相交 ⟺ 盒子相交。
- `seed & 0xF` — 取低 4 位作为随机数(0-15)。
- `(seed >> 4) & 0xF` — 取下一个 4 位。
