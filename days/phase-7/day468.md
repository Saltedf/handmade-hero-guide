# Day 468 · 导入时处理注解数据

> 你的 HHA V1 现在能存所有 asset,但有些 asset 需要"额外说明"——一张贴图可能附带"它的对齐点是底部中心",一个声音可能附带"它的循环模式是 loop_forever"。这些**元数据(metadata)**怎么塞进 HHA?Casey 这一天做的事:给 asset 加 annotation,在导入时从外部文件读进来,打包到 HHA 里。

## 0 · 为什么要有这一天

到目前为止,HHA 里每个 asset 只有四个核心字段:`type_code`, `name`, `offset`, `size`。够加载,但不够"正确使用"。考虑下面三个真实场景:

**场景 1**:你的角色贴图是 100×150 像素,但角色的"脚"在底部中心(不是图片中心)。当 NPC 站在 (100, 200) 时,贴图左下角应该放在哪?如果是中心对齐,左下角在 (50, 275);如果是底中心对齐,左下角在 (50, 200)。**对齐点(alignment point)**不写进 asset,游戏代码就要硬编码——每张贴图都查一个 if/else 表,噩梦。

**场景 2**:你的音效有的是"一次性"(被击中播一次),有的是"循环"(背景音乐)。**播放模式**不写进 asset,游戏代码就要靠名字硬猜(`if name.ends_with("_loop") ...`),脆弱易错。

**场景 3**:你的字体有的支持英文,有的支持中文。**字符集**不写进 asset,渲染时不知道哪些字符能画,字面给玩家显示成豆腐块。

这些信息都需要**和 asset 一起存储**——这就是 annotation。它本质上是"asset 的元数据 / 附属说明",不是 asset 数据本身,但描述 asset 怎么被使用。

**为什么不直接编码到 name 里?** 比如 `hero_align_bottom.png`。第一,name 是给开发者看的,塞业务字段污染可读性。第二,name 是 string,字段提取靠字符串解析,类型不安全(`align_bottom` vs `bottom_align` 哪个对?)。第三,新增字段(name 里的 tag 越来越长)不可扩展。所以工程上 annotation 必须是**结构化字段**,不是 name 字符串。

**为什么导入时处理而不是运行时?** 因为导入是一次,运行时是 N 次。把"读外部文件、解析、合并"这种重活放在导入期,运行时只读已经合并好的 HHA,加载快。这是经典的**预计算(precompute)**思维——把工作前移,降低热路径负担。

完成这一天之后,你具备了:
- 设计可扩展的 metadata 模式(key-value pair)
- 把"外部文本描述 + 二进制 asset"合并打包的工程模式
- 理解为什么"导入期处理"是资产管线优化的关键

## 1 · Casey 今天做了什么

Casey 这一天的工作分四步:

第一步,他在 PNG 旁边加了一个**sidecar 文件**——`hero.png` 配 `hero.txt`(或 `hero.png.meta`,Unity 风格)。这个文本文件描述这个 asset 的 annotation:`align=bottom_center`, `loop=forever` 等。

第二步,他改写 PNG 导入器:导入 `hero.png` 时,先读 `hero.txt`,把里面的 key=value 解析成内存中的 `HashMap<String, String>`,再把这个 map 序列化到 HHA 文件里(作为 asset 的 annotation 字段)。

第三步,他改了游戏代码:加载 asset 时,annotation 从 HHA 读出来,作为 asset 的字段。游戏代码用 `asset.annotation.get("align")` 拿对齐点,不再硬编码。

第四步,他扩展了 dumper:Day 466 的 dumper 现在能打印每个 asset 的 annotation:`[47] type=texture name='hero.png' align='bottom_center' loop='none'`。

这集的关键洞察:**annotation 是"asset 数据"和"游戏代码"之间的协议层**。游戏代码不再"知道"asset 的具体细节,而是从 annotation 查询。这让游戏代码和 asset 解耦——加新 asset 类型不用改游戏代码,只改 annotation。

## 2 · 心智模型

### 类比:博物馆的展品标签

博物馆里每件展品都贴一张标签:展品名、年代、材质、捐赠者。这张标签就是**注解(annotation)**——它不是展品本身,但它告诉你**展品怎么被理解**。

没有标签,参观者只看到"一个陶罐"。有标签,参观者知道"这是公元前 500 年希腊的安佛拉罐,由 Smith 先生 1980 年捐赠"。同样的展品,有 annotation 和没 annotation,**可被理解的程度完全不同**。

HHA 里的 annotation 就是这个标签。一个 asset 没有 annotation,游戏只知道"一个 PNG,100×150,4096 字节"。有 annotation,游戏知道"这是 hero 的角色贴图,对齐点是底中心,会发光特效"。

### Key-Value Pair 的工程哲学

Casey 的 annotation 用最朴素的 key-value 模式:

```
align = bottom_center
loop = forever
charset = ascii
```

每行 `key = value`,等号两边允许空格。看似简陋,但具备工业级格式的一切优点:

第一,**可扩展**。明天加 `priority = high`,无需改格式,直接多一行。key-value 本质是"无限字段"格式。

第二,**类型灵活**。value 是 string,但游戏代码可以按需 parse:`u32::from_str(value)`、`bool::from_str(value)`。不强求 schema,适合快速演化。

第三,**省空间**。空白分隔,无 JSON 的引号 / 大括号开销。10 个 annotation 占 100 字节,JSON 要 300。

第四,**人友好**。开发者在文本编辑器里写 `hero.txt` 一目了然,不像 JSON 还要管逗号 / 引号语法。

代价是**类型不安全**——`align = 123` 这种"应该 string 但写了数字"的错不会编译期报错,要运行时校验。Casey 接受这个代价,因为 annotation 量小,运行时校验足够。

### 三种 annotation 储存方式

**方式 1:Sidecar 文件(Unity 风格)** —— 每个 `.png` 配一个 `.png.meta` 文件,独立文本。

优点:开发者手动编辑方便,git diff 友好。
缺点:文件数量翻倍,容易"主文件改了 meta 没改"。

**方式 2:目录级 metadata(glTF 风格)** —— 一个目录一个 `_meta.json`,列所有 asset 的 annotation。

优点:集中管理,文件数量少。
缺点:大目录的 metadata 文件臃肿。

**方式 3:嵌入文件本身(EXIF 风格)** —— annotation 直接塞进 PNG 的 tEXt chunk。

优点:单文件自包含。
缺点:需要 PNG 解码器支持读 tEXt chunk,工具链复杂。

Casey 选方式 1,因为它最简单,而且和现有的"PNG 文件 + 字节流"导入流程契合。

### 导入时的处理流程

```
1. 输入:hero.png(二进制)+ hero.txt(annotation 文本)
2. 读 hero.txt,parse 成 HashMap<String, String>
3. 读 hero.png,解出 RGBA 像素数据
4. 把像素数据写到 HHA 的 data 区,记下 offset / size
5. 把 annotation HashMap 序列化到 asset 元数据区
6. HHA 写入完成
```

注意步骤 2 和 3 是**独立**的——annotation 解析失败不应该阻止 PNG 导入(可以警告)。这种"局部失败"的设计让管线更健壮:一张图的 annotation 写错了,其他图还能正常导入。

### Annotation 在 HHA 里的二进制布局

V1 的 asset 元数据现在变成:

```
struct Asset {
    type_code: u32,
    name_offset: u32,       // 字符串存在 string table
    name_len: u32,
    data_offset: u32,       // 像素 / 音频数据
    data_size: u32,
    annotation_count: u32,  // 新增
    annotations_offset: u32, // 新增:指向 annotation 数组
}
```

每个 annotation 是:
```
struct Annotation {
    key_offset: u32,
    key_len: u32,
    value_offset: u32,
    value_len: u32,
}
```

字符串都集中存在 string table,避免每个 annotation 重复存 key(`align` 这种 key 高频出现)。这是**字符串去重(string interning)** 的简化版,Day 500+ Casey 会做更完整的 interning。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业里 annotation 是基础设施:

- **Unity** 的 `.meta` 文件:每个 asset 配一个,存 GUID、import settings、reference 列表。Unity 工作流强依赖 `.meta`,丢了 `.meta` 就丢失所有引用关系
- **Unreal** 的 `.uasset` 内嵌 metadata:asset 本身就是二进制 + metadata 一体,不存在 sidecar
- **Godot** 的 `.import` 文件:类似 Unity 的 `.meta`,sidecar 风格
- **glTF** 的 `extras` 字段:JSON 里允许任意 application-specific 数据,自由格式

Casey 选 Unity / Godot 风格(sidecar 文本),因为它最直观,初学者立刻能上手。

游戏里 annotation 常见用途:
- **对齐点**(align):贴图相对实体中心的偏移
- **碰撞盒**(hitbox):哪些区域算"被击中"
- **动画帧率**(fps):精灵表的播放速度
- **音量**(volume):声音默认音量
- **混音组**(mixer_group):路由到 BGM / SFX / Voice
- **依赖**(depends_on):这个 asset 加载前要先加载哪些(比如材质引用贴图)
- **LOD 距离**(lod_distances):不同距离用不同模型

注意:annotation 不是任意的——好的 annotation 应该**有明确语义**,而不是"想啥写啥"。Casey 这一天加的 annotation 都是"游戏代码会查的字段",不是凭空想象。

### 3.2 · 🎨 图形学视角

annotation 在图形学语境里有几个特殊用法:

**贴图 atlas 信息**:`atlas_size = 4x4`, `tile_width = 64`。游戏代码读出后才能从 atlas 里切出单独 tile。

**色彩空间**:`color_space = sRGB` 或 `Linear`。这影响 GPU 上传时的 internal format(`SRGB8_ALPHA8` vs `RGBA8`)。弄错会导致最终画面"过亮"或"过暗"。

**premultiplied alpha**:`premul_alpha = true`。如果贴图已经在 alpha 通道预乘了 RGB,GPU 混合方程要从 `src * src.a + dst * (1 - src.a)` 改成 `src + dst * (1 - src.a)`。错的话半透明边缘会出现黑色 fringe。

**filter mode**:`filter = bilinear` 或 `nearest`。pixel-art 游戏强制 nearest,避免放大模糊。这影响 `glTexParameteri(GL_TEXTURE_MIN_FILTER, ...)`。

这些字段都是 annotation——不属于像素数据本身,但决定 GPU 怎么用像素数据。Casey 后面(Day 500+)会扩展 annotation 覆盖这些图形学字段。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上"sidecar metadata"模式无处不在:

- **`.desktop` 文件**:GUI 应用的元数据。`/usr/share/applications/firefox.desktop` 描述 Firefox 的图标、命令行、category。这是 annotation 的工业典范
- **package metadata**:`/var/lib/pacman/local/firefox-120/desc` 是 pacman 的 package annotation(版本、依赖、安装时间)
- **MIME 类型**:`~/.config/mimeapps.list` 是"用什么程序打开什么文件"的 annotation
- **ffmpeg 元数据**:`ffprobe video.mp4` 显示 codec、resolution、bitrate,这些都是内嵌在 mp4 容器里的 annotation

实操:看一个 .desktop 文件长什么样:

```bash
cat /usr/share/applications/firefox.desktop | head -20
# 输出:
# [Desktop Entry]
# Version=1.0
# Name=Firefox
# Comment=A web browser.
# Exec=/usr/lib/firefox/firefox %u
# Icon=firefox
# Terminal=false
# Type=Application
# Categories=Network;WebBrowser;
# MimeType=text/html;text/xml;...
```

这就是 Casey 的 `hero.txt` 的工业版本——key=value 形式,描述应用的"如何被使用"。

### 3.4 · 🦀 Rust 生态视角

Rust 处理 key-value metadata 有几种风格:

**风格 1:HashMap** —— 最直接

```rust
use std::collections::HashMap;
type Annotations = HashMap<String, String>;

// 读
let align = annotations.get("align").map(String::as_str).unwrap_or("center");

// 写
annotations.insert("align".to_string(), "bottom_center".to_string());
```

优点:简单,灵活。缺点:每次 get 都是 string 比较,慢;key 拼写错误运行时才发现。

**风格 2:Strongly-typed struct** —— Casey 后面会演化到这

```rust
struct AssetAnnotation {
    align: Align,        // enum
    loop_mode: LoopMode, // enum
    volume: f32,
}

enum Align { Center, BottomCenter, TopLeft }
enum LoopMode { None, Forever, PingPong }
```

优点:类型安全,编译期检查。缺点:加字段要改 struct + 改 parser,不够灵活。

**风格 3:serde + JSON / TOML** —— 现代 Rust 工业标准

```rust
#[derive(Deserialize)]
struct AssetAnnotation {
    #[serde(default)]
    align: Option<Align>,
    #[serde(default)]
    loop_mode: Option<LoopMode>,
}
let ann: AssetAnnotation = serde_json::from_str(&text)?;
```

优点:类型安全 + 灵活(Option 处理缺失字段)。缺点:依赖 serde / serde_json,编译时间增加。

Casey 在 C 里手写 key-value parser,等价于风格 1。Rust 实现可以直接用 HashMap,后期演化到 serde。

**Sidecar 文件名约定**

```rust
fn sidecar_path(asset_path: &Path) -> PathBuf {
    // 三种约定:
    // 1. 加 .meta 后缀:hero.png → hero.png.meta
    // 2. 改后缀为 .txt:hero.png → hero.txt
    // 3. 改后缀为 .meta:hero.png → hero.meta
    
    let mut p = asset_path.to_path_buf();
    p.set_extension("meta");  // Unity 风格
    p
}
```

`Path::set_extension` 是 Rust 标准库的方法,智能处理路径。

## 4 · 认知地图

### 4.1 上级

- **Metadata** —— 关于数据的数据,软件工程无处不在
- **Asset Pipeline** —— 从原始文件到运行时数据流的完整管线
- **Inversion of Control** —— 游戏"查询" annotation 而不是"硬编码",控制权反转

### 4.2 同级

| 方案 | 描述 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Sidecar 文件 | `.png.meta` 独立文本 | 开发者手动编辑 | ✅ Casey 选了 |
| 嵌入容器 | PNG tEXt chunk | 单文件分发 | glTF extras |

详细:Casey 选 sidecar 因为最简单。商业引擎选嵌入容器或数据库因为资产数量大(百万级),sidecar 文件爆炸。

## 5 · 对照与变奏

### 同一问题:程序配置

annotation 本质是"asset 的配置"。程序配置文件领域有很多类似设计:

- **TOML** —— Cargo.toml 用的格式,key=value + section,人友好
- **INI** —— Windows 传统,section + key=value
- **YAML** —— 缩进结构,强大但易错
- **JSON** —— 严格语法,机器友好
- **XML** —— 标签结构,冗长但可 schema 验证
- **Custom KV**(本日)—— 最简,适合小规模

每种格式各有取舍,但**本质都是 metadata**。Casey 选最简 KV 因为 annotation 字段少,不需要 TOML 的 section。如果 annotation 变复杂,可以演化到 TOML。

### 配置的层次

工业上 annotation / config 通常分层:

1. **Default**(代码硬编码)—— 所有 asset 默认对齐 `center`
2. **Type default**(类型级覆盖)—— 所有 texture 默认 `premul_alpha=true`
3. **Asset specific**(sidecar)—— 这个 asset 特殊,`align=bottom_center`
4. **Runtime override**(代码)—— 临时改成 `align=top_left`

每层覆盖下层。这是 **CSS specificity** 的思路——同样适用于 asset annotation。Casey 现在只做第 3 层(sidecar),后期可能加第 2 层(type default)。

### 历史演化:从硬编码到 metadata driven

- **1970s-1980s**:游戏所有参数硬编码在源码里(汇编 / C)。改一个角色速度要重新编译
- **1990s**:开始用 INI / config 文件分离"可调参数"
- **2000s**:数据驱动设计(data-driven),游戏逻辑读 metadata 行为
- **2010s**:商业引擎完全 metadata 化,游戏代码只写"通用引擎",所有内容靠 metadata
- **2020s**:甚至 metadata 也可以热重载(Unity Editor 实时改)

Casey 现在在第 3 阶段,逐步把"硬编码"搬到"metadata 驱动"。Day 488 之后(游戏内编辑器)会更进一步——开发者直接在游戏里改 annotation,不用手编辑 sidecar。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 annotation 应该是 key-value pair,而不是直接扩展 asset struct(给 struct 加 `align: Align`, `loop_mode: LoopMode` 字段)?

**参考解答**:扩展 struct 有三个问题:

第一,**改字段要改格式版本**。每加一个字段(V1 → V2),所有 HHA 文件要迁移,所有 reader 要改。annotation 加字段不动格式,只需在游戏代码 `get("new_field")`。

第二,**字段适用范围不同**。`align` 只对贴图有意义,`loop_mode` 只对声音有意义。struct 把所有字段塞一起,要么用 Option(浪费空间),要么用 enum(复杂)。annotation 是"按需存在",贴图有 align 没有loop_mode。

第三,**第三方扩展**。mod 作者想加 `custom_glow_color` 字段,struct 不允许(他不改源码),annotation 允许(直接 sidecar 加 key=value)。

annotation 的代价:类型不安全。但工程上 trade-off 划算——少量运行时校验 < 大量格式迁移。

### Lv2 · 动手实践

**题**:实现一个 sidecar annotation 解析器,Rust 写,接受 `hero.txt` 文件,返回 `HashMap<String, String>`。完成标准:
- 解析 `key = value` 格式,允许等号两边空格
- 跳过空行和 `#` 开头的注释行
- 报错时给出文件名 + 行号(`hero.txt:3: missing '='`)
- 单元测试至少 3 个 case:正常、空行、缺等号

**参考解答**:

```rust
use std::collections::HashMap;
use std::fs::File;
use std::io::{self, BufRead, BufReader};
use std::path::Path;

#[derive(Debug)]
pub enum AnnotationError {
    Io(io::Error),
    Parse { line_num: usize, msg: String },
}

impl From<io::Error> for AnnotationError {
    fn from(e: io::Error) -> Self { AnnotationError::Io(e) }
}

pub fn parse_sidecar<P: AsRef<Path>>(path: P) -> Result<HashMap<String, String>, AnnotationError> {
    let path_ref = path.as_ref();
    let file = File::open(path_ref)?;
    let reader = BufReader::new(file);
    let mut map = HashMap::new();
    
    for (i, line_result) in reader.lines().enumerate() {
        let line_num = i + 1;  // 行号从 1 开始
        let line = line_result?;
        let trimmed = line.trim();
        
        // 跳过空行
        if trimmed.is_empty() { continue; }
        // 跳过注释
        if trimmed.starts_with('#') { continue; }
        
        // 找等号
        let eq_pos = trimmed.find('=').ok_or_else(|| AnnotationError::Parse {
            line_num,
            msg: format!("missing '=' in line: {}", trimmed),
        })?;
        
        let key = trimmed[..eq_pos].trim().to_string();
        let value = trimmed[eq_pos + 1..].trim().to_string();
        
        if key.is_empty() {
            return Err(AnnotationError::Parse {
                line_num,
                msg: "empty key".to_string(),
            });
        }
        
        map.insert(key, value);
    }
    
    Ok(map)
}

        let f = write_temp("align = bottom_center\nloop = forever\n");
        let map = parse_sidecar(f.path()).unwrap();
        assert_eq!(map.get("align"), Some(&"bottom_center".to_string()));
        assert_eq!(map.get("loop"), Some(&"forever".to_string()));
    }
    
    #[test]
    fn test_blank_and_comment() {
        let f = write_temp("\n# this is a comment\nalign = center\n");
        let map = parse_sidecar(f.path()).unwrap();
        assert_eq!(map.len(), 1);
        assert_eq!(map.get("align"), Some(&"center".to_string()));
    }
    
    #[test]
    fn test_missing_equals() {
        let f = write_temp("this line has no equals\n");
        let result = parse_sidecar(f.path());
        match result {
            Err(AnnotationError::Parse { line_num, .. }) => assert_eq!(line_num, 1),
            _ => panic!("expected Parse error"),
        }
    }
}
```

**每行解释**:
- `impl From<io::Error> for AnnotationError` —— 让 `?` 自动把 io::Error 转成 AnnotationError。这是 Rust 错误处理的标准模式
- `reader.lines().enumerate()` —— 把每行带行号遍历。`enumerate()` 返回 `(index, item)`,index 从 0 开始,所以 `+1` 得到 1-based 行号
- `trimmed.find('=')` —— 返回 `Option<usize>`,找不到返回 None。`ok_or_else` 把 None 转成 Err
- `tempfile::NamedTempFile` —— 测试用临时文件,drop 时自动删除。Cargo.toml 加 `tempfile = "3"` dev-dependency
- `&"bottom_center".to_string()` —— `Option<&String>` 比较 `Some(&String)`,需要把字面量转 String 再取引用

### 完整 sidecar + HHA 写入流程

```rust
use std::collections::HashMap;
use std::fs::File;
use std::io::{self, BufWriter, Read, Write};
use std::path::Path;

// annotation 类型
type Annotations = HashMap<String, String>;

// asset struct(内存表示)
struct AssetWithAnn {
    type_code: u32,
    name: String,
    data: Vec<u8>,  // 简化:实际从 PNG 解出来
    annotations: Annotations,
}

// 从 PNG + sidecar 构造 asset
fn import_png_with_annotation<P: AsRef<Path>>(
    png_path: P,
) -> io::Result<AssetWithAnn> {
    let png_path = png_path.as_ref();
    
    // 1. 读 PNG(简化:直接读字节,不解码)
    let mut png_data = Vec::new();
    File::open(png_path)?.read_to_end(&mut png_data)?;
    
    // 2. 找 sidecar(hero.png → hero.meta)
    let mut sidecar_path = png_path.to_path_buf();
    sidecar_path.set_extension("meta");
    
    // 3. 读 sidecar,如果不存在就用空 map
    let annotations = if sidecar_path.exists() {
        parse_sidecar_simple(&sidecar_path).unwrap_or_default()
    } else {
        HashMap::new()
    };
    
    // 4. 构造 asset
    let name = png_path.file_name().unwrap().to_string_lossy().into_owned();
    Ok(AssetWithAnn {
        type_code: 1,  // texture
        name,
        data: png_data,
        annotations,
    })
}

fn parse_sidecar_simple(path: &Path) -> io::Result<Annotations> {
    let file = File::open(path)?;
    let reader = io::BufReader::new(file);
    let mut map = HashMap::new();
    use io::BufRead;
    for line in reader.lines() {
        let line = line?;
        let trimmed = line.trim();
        if trimmed.is_empty() || trimmed.starts_with('#') { continue; }
        if let Some(eq) = trimmed.find('=') {
            let k = trimmed[..eq].trim().to_string();
            let v = trimmed[eq + 1..].trim().to_string();
            map.insert(k, v);
        }
    }
    Ok(map)
}

// 写到 HHA
fn write_hha(assets: &[AssetWithAnn], out_path: &Path) -> io::Result<()> {
    let file = File::create(out_path)?;
    let mut w = BufWriter::new(file);
    
    // magic + version
    w.write_all(b"HHA1")?;
    w.write_all(&1u32.to_le_bytes())?;
    
    // tag count(简化:0 个)
    w.write_all(&0u32.to_le_bytes())?;
    
    // asset count
    w.write_all(&(assets.len() as u32).to_le_bytes())?;
    
    // asset 元数据
    for asset in assets {
        w.write_all(&asset.type_code.to_le_bytes())?;
        let name_bytes = asset.name.as_bytes();
        w.write_all(&(name_bytes.len() as u32).to_le_bytes())?;
        w.write_all(name_bytes)?;
        w.write_all(&asset.data.len().to_le_bytes())?;
        // 简化:省略 offset / 实际数据,这里演示 annotation 部分
        w.write_all(&(asset.annotations.len() as u32).to_le_bytes())?;
        for (k, v) in &asset.annotations {
            let kb = k.as_bytes();
            let vb = v.as_bytes();
            w.write_all(&(kb.len() as u32).to_le_bytes())?;
            w.write_all(kb)?;
            w.write_all(&(vb.len() as u32).to_le_bytes())?;
            w.write_all(vb)?;
        }
    }
    
    // 写 asset 数据(简化)
    for asset in assets {
        w.write_all(&asset.data)?;
    }
    
    w.flush()?;
    Ok(())
}

fn main() -> io::Result<()> {
    let asset = import_png_with_annotation("hero.png")?;
    println!("Imported: {} ({} annotations)", asset.name, asset.annotations.len());
    for (k, v) in &asset.annotations {
        println!("  {} = {}", k, v);
    }
    
    write_hha(&[asset], "out.hha")?;
    println!("Wrote out.hha");
    Ok(())
}
```

### Troubleshooting

- **sidecar 找不到** —— 检查文件后缀约定。`.png.meta` vs `.meta`,要一致
- **annotation 解析卡住** —— 检查 sidecar 是否 UTF-8 编码,Windows 默认 GBK 会导致 io::Error
- **annotation 在 HHA 里丢失** —— writer 的循环顺序错了,annotation 字段必须在 asset 元数据后、asset 数据前
- **dumper 显示乱码** —— string offset 计算错,string table 累积长度有偏差
