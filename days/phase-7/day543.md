
# Day 543 · 把解包实体从模拟区域移到世界

> Day 538 引入"解包实体(unpacked entity)"——把存档里的紧凑实体在游戏里展开成可编辑、可修改的运行时形式。但当时它们活在 sim region(模拟区域,一个帧级的临时世界切片)里,模拟完就丢。Day 543 把它们**持久化到 world**:模拟完后把"还活着"的解包实体回写到 world,跨帧保留它们的修改。

## 0 · 为什么要有这一天

我们先把上一段提到的两个概念说清楚,再回到今天。

**World(世界)** 是整个游戏的实体存储中心,横跨所有 chunk,持续整个游戏生命周期。每个 entity 有稳定 ID,跨帧存活。

**Sim region(模拟区域)** 是某一帧"我现在要算物理/AI"时圈出来的小范围,只包含玩家附近的几个 chunk,模拟完丢掉。这是 Handmade Hero 的核心性能优化——不模拟看不见的东西。

为什么把 entity 在两个区域之间来回搬?因为:

- 存储在 world(便宜,不动的世界)
- 计算在 sim region(只复制玩家周围一小块,够算就行)
- 计算结果(比如"怪物被打死了")要回写 world,否则下一帧忘了

之前的实现:解包实体从存档**进** sim region,但**没有回写**——它们在 sim region 内被编辑器修改,但 sim region 一结束修改就丢。Day 543 修这个 bug:**让解包实体的修改持久化**。

为什么这事重要?Day 538 引入解包实体是为了**编辑器**(编辑器要能改存档里的实体)。如果改完不回写,编辑器就是废的——改了等于没改,玩家走两步存档里还是老样子。Casey 在视频里说这是"绕了大圈才回的家"——之前以为 sim region 是终点,实际是中转站。

完成这一天之后,你具备:

- 理解 world ↔ sim region 双向数据流
- 能正确处理 entity 的"生命周期"——出生(world)、模拟(sim region)、死亡或存活(world)
- 知道为什么 "outgoing entity list" 这种数据结构存在
- 体会到"持久化 vs 暂存"这一对工程张力在游戏内的具体体现
- 能在自己的项目里设计类似的"工作集 ↔ 主存"双向数据流,并避免常见的"字段丢失""覆盖错误"陷阱

### 0.1 · 为什么这个看似简单的"回写"是 Phase 7 的真正起点

读者看到这一天的标题,第一反应大概是:"不就是 sim region 算完把数据 copy 回 world 吗?这也值得一整集?"

答案是:**值得**,而且这是 Phase 7 整个故事的"地基"。后续的 Phase 7 会引入光探针(light probe)、体素光照(voxel lighting)、编辑器持久化、M8 里程碑。所有这些高级功能都依赖一个共同前提——**游戏运行时修改过的状态能可靠地流回持久存储**。如果连"怪物血量减了 10,world 里也减了 10"这件事都做不到,后面所有"编辑器改存档""玩家在世界里建造,重启游戏后保留"的功能都是空中楼阁。

Casey 在视频里花了大段时间讨论这个看起来"显而易见"的事,核心原因是:**真正的复杂度不在"做出来",而在"做得对"**。任何程序员都能写一个 90% 正确的回写——把 entity 字段一个一个 copy。但剩下 10% 包括:entity 在 sim region 内死亡、entity 在 sim region 内被生出来、entity 在 sim region 内被替换(变异)、entity 跨 chunk 边界、多个 sim region 同时存在(分屏)。每一种边界情况都要被显式处理,任何一个没处理就是"物品捡了又出现"的 bug。

所以这一集的核心训练不是"学新语法",而是"学一种工程纪律"——**显式枚举所有边界情况,逐个验证**。这种纪律到 Phase 7 后面(光探针的 voxel sampling、多重光源重建)会反复用到。

## 1 · Casey 今天做了什么

Casey 这一天的核心动作是给 sim region 加一个**输出队列**(outgoing list):

第一步,他在 sim region 结构里加一个字段 `OutgoingEntities`,类型是 array,放"模拟结束仍然存活的解包实体"。

第二步,他在 sim region 的"end frame"里,把所有还活着的解包实体从内部存储 `Entities` 转移到 `OutgoingEntities`(标记为"等待回写")。

第三步,他在 world 的"接受 sim region 结果"逻辑里,遍历 `OutgoingEntities`,把每个实体的修改 patch 回 world 里对应的 entity slot。

Casey 在视频里强调:这是个看似简单但**容易出错**的事——一旦在转移过程中漏掉某个字段,游戏就会出现"怪物死了又复活""物品捡了又出现"的怪 bug。所以他把转移做成一个**显式的 struct-to-struct 拷贝**,每字段一行,方便审查。

## 2 · 心智模型

### 类比:酒店的入住和退房

想象 world 是一座大城市的人口登记册,每个 entity 是一个市民,有身份证(ID)和家庭住址(chunk 里的 slot)。

Sim region 是市中心的一家**酒店**。每天早上(每帧开始),酒店去登记册里"邀请"附近的市民来住一天——但只邀请离酒店 500 米内的(玩家周围的 entity)。市民住进酒店就是"被解包、进入 sim region"。

在酒店里(模拟),市民可能做很多事:吃饭、打架、被杀、生孩子。这些事只有**在酒店里发生**才算。

晚上(模拟结束),酒店要**办理退房**:

- 被杀的市民——从登记册删除
- 新生的婴儿——加进登记册
- 活着的市民——把他们在酒店里发生的变化(受伤了?发财了?)**回写到**登记册
- 住得太远的市民(走出了 500 米)——不再被邀请,但仍活在登记册里

之前的 bug:酒店退房时只把"住客名册"扔了,没回写变化。结果登记册里这些人永远停在"早上出门时的状态"——他们虽然在酒店里被打了一顿,登记册里还显示"健康"。

Day 543 = 给酒店加退房流程,正确回写登记册。

### 严谨展开:Sim Region 的数据结构

让我们先用最朴素的 Rust 描述把这件事落到具体内存布局上,然后再讨论每一个字段为何这样设计。请逐行读这段代码,每一行都有"为什么这么写"的理由:

```rust
// 一个 sim region 是一帧的"工作台"。
// 注意:整个结构只在一帧内 alive,帧结束就被销毁。
// 不要把它设计成"持久对象"——持久对象的代码会变复杂(需要 Drop、生命周期标注等)。
struct SimRegion {
    // 输入:从 world 解包进来的实体
    // 用 Vec 而不是 HashMap——因为模拟时是顺序遍历,Vec cache 性能更好
    // Vec 的内存是连续的,CPU prefetcher 能高效预取
    entities: Vec<UnpackedEntity>,

    // 输出:模拟结束仍存活的实体(等回写)
    // 为什么单独开一个 Vec,不直接复用 entities?
    //   1. 语义清晰:entities 是"输入",outgoing 是"输出",不同语义用不同变量
    //   2. 便于调试:出 bug 时能分别 dump 两个 vec,看哪个环节出错
    //   3. 避免误删:模拟过程中可能多次遍历 entities,如果边遍历边删除会出 bug
    outgoing: Vec<UnpackedEntity>,

    // 元数据:这一帧模拟的范围
    // center 是玩家世界坐标,radius 是模拟半径(米)
    // 这两个字段决定了"哪些 entity 会被解包进来"
    world_center: Vec3,
    world_radius: f32,

    // 隐含的"衍生字段"——不在 struct 里,在文档里说清楚:
    //   - 这个 SimRegion 不持有 world 的引用(避免借用冲突)
    //   - sim 结束时,outgoing 必须被消费,否则数据丢失
    //   - 不要在 sim region 里持有任何持久资源的 owned pointer
}

// UnpackedEntity 是"展开的实体",所有字段都明摆着,方便编辑器修改。
// 与之相对的是 WorldEntity(world 里的紧凑形式),后者可能用 bit packing、enum tag 等压缩。
// 为什么需要 unpack?因为编辑器要"看每个字段",压缩形式不好直接编辑。
struct UnpackedEntity {
    // id 是 entity 的"身份证号",全局唯一,跨帧稳定。
    // 所有 world ↔ sim region 的匹配都靠它。
    // 注意:不能简单用 array index 作为 id——entity 可能被删除,删除后 index 会"塌缩",
    // 用 stable u64 id 能避免这种问题。
    id: u64,

    // position 是世界坐标(米),mutable。
    // 模拟时 entity 会移动,移动后的 position 要回写 world。
    position: Vec3,

    // kind 是 entity 类型,immutable(本帧内不变)。
    // 标 immutable 是为了提醒回写时不要 copy 它——world 里的 kind 是真理。
    kind: EntityKind,

    // health 是血量,mutable。受击、回血都改这个。
    health: f32,

    // 一个常被遗漏的字段:spawn_this_frame。
    // 如果这个 entity 是本帧 sim region 内新生的(比如怪物产卵),
    // 回写时不能"找 world 里现有的 slot 更新",而要"在 world 里新增 slot"。
    // 漏处理这个 → 新生的怪物下一帧消失(因为 world 里没有它)。
    spawn_this_frame: bool,

    // 另一个常被遗漏的字段:dead。
    // 模拟时标记 dead 的 entity,回写时要从 world 删除。
    // 漏处理 → 死亡怪物在 world 里"诈尸"。
    dead: bool,

    // ... 其他游戏字段
}
```

这两个 struct 字段加起来不到 10 个,但每一个都对应一个"边界情况"。**casey 在视频里强调:每加一个字段都要问自己——这个字段在 sim region 里改了,要不要回写 world?如果是,新加的 entity 怎么处理?删除的 entity 怎么处理?**

### 帧的生命周期(逐阶段拆解)

下面这个"帧的生命周期"看起来像个流水账,但每个阶段都有"陷阱"。我把它们写在注释里:

```
帧开始:
  1. 创建 SimRegion — 用 Box::new 或 stack 都行,但别在 hot loop 里 alloc
     陷阱:如果每帧 alloc SimRegion, allocator 压力大;解决:复用 buffer
  2. 遍历 world 中玩家附近的 chunk
     陷阱:chunk 边界附近的 entity 可能"漏掉";解决:radius 多覆盖一个 chunk
  3. 把每个 chunk 里"靠近玩家"的 entity 解包到 sim.entities
     陷阱:clone 带指针字段(heap string、box)会深拷贝,慢;解决:用 Cow 或 arena

模拟(物理、AI、战斗):
  4. 遍历 sim.entities,跑游戏逻辑
     陷阱:遍历中修改 vec 长度(添加新生的、删除死亡的)会出问题;
     解决:用 swap_remove 或维护两个 list(新增 list、删除 list)
  5. 死的标记 dead,新的 push 进 sim.entities
     陷阱:如果在 iter() 里 push,会 borrow 冲突;解决:先收集 to_add,循环结束统一 push

帧结束:
  6. 遍历 sim.entities
     - 死的:world 里删除对应 slot
       陷阱:world.entities.remove(id) 可能 O(n);解决:用 HashMap
     - 活的:push 进 sim.outgoing
       陷阱:push 顺序可能影响回写;解决:对顺序无敏感设计
  7. 遍历 sim.outgoing,把变化 patch 回 world
     陷阱:spawn_this_frame 的 entity 要 insert,不能 update;
     解决:match on spawn_this_frame 分两条路径
  8. 销毁 SimRegion(下一帧重建)
     陷阱:如果 SimRegion 持有 world 引用,Drop 时 borrow 没释放;
     解决:SimRegion 不持有任何引用,数据全 owned
```

这 8 步看起来烦,但**这就是真游戏的代码长什么样**。教科书例子永远是"3 步:load、update、save",真游戏永远有 8-20 步,因为有边界情况要处理。

### 为什么不直接在 world 里改?

你可能会问:为啥这么麻烦,直接在 world 里改不就行了?

性能。World 可能包含 100 万个 entity(超大世界),但你一帧只模拟玩家周围 100 个。如果直接遍历 world 找这 100 个,cache miss 海了去——每次跳到新 chunk 都是几十纳秒的内存延迟。

解包到 sim region,把 100 个 entity 拷贝到一段连续内存,模拟时它们都在 L1 cache 里,跑得飞快。模拟完回写,只动 100 个 slot,不动剩下 999900 个。

这是经典的"**structure of arrays + 工作集隔离**"模式。数据库也用类似思路——把热数据复制到内存里改,定期批量写回磁盘。

### 回写时的"字段级 patch"

最微妙的细节:回写不是整个 entity 覆盖,而是**字段级 patch**。原因:

world 里 entity 可能存了"原始 + 派生"两类字段。比如 `position`(原始,会变)和 `chunk_index`(派生,从 position 算)。如果整个 entity 覆盖,派生字段也覆盖,万一 sim region 里没正确维护 `chunk_index`,world 就坏了。

正确做法:回写时只 patch **mutable 字段**(血量、位置、状态),不动 **派生字段**(在 world 里重算)。

让我们把这件事讲透。游戏里字段大概可以分三类:

1. **Immutable**(出生后永远不变):如 `entity_kind`、`creation_timestamp`、`prototype_id`。这些字段从存档读出来是什么,就一直是什么。回写时跳过——既不需要 patch,也**绝不能**让 sim region 改它。
2. **Mutable persistent**(会变且要持久化):如 `health`、`position`、`inventory`。这些是回写的目标。
3. **Derived / Cached**(从其他字段算出来,world 内部用):如 `chunk_index`(从 position 算)、`aabb_bounds`(从 position+size 算)。这些**不要从 sim region 回写**——sim region 里这个字段可能过期了(比如 position 改了但 chunk_index 没同步更新),回写会污染 world。

```rust
// 字段级 patch 的精确实现
fn write_back(world: &mut World, sim: &SimRegion) {
    for sim_ent in &sim.outgoing {
        // 分支一:本帧新生的 entity —— world 里还没有,要 insert
        if sim_ent.spawn_this_frame {
            world.insert(WorldEntity::from_unpacked(sim_ent));
            continue;
        }

        // 分支二:已存在的 entity —— 按 id 查找,字段级更新
        if let Some(we) = world.entity_mut(sim_ent.id) {
            // 只 patch mutable persistent 字段
            we.position = sim_ent.position;
            we.health = sim_ent.health;
            we.state = sim_ent.state;
            we.inventory = sim_ent.inventory.clone();  // 必要时深拷贝

            // 派生字段在 world 里重算(不要从 sim region 拷)
            we.chunk_index = world.chunk_index_for(we.position);
            we.aabb = we.compute_aabb();
            // 注意:不要写 we.kind = sim_ent.kind —— immutable 字段不能被改
        } else {
            // 异常情况:entity 不在 world 里,也没 spawn_this_frame
            // 这通常是 bug —— sim region 里有个不存在的 id。
            // 正确做法:log warning,不要 panic(panic 会让游戏崩,体验差)
            log::warn!("sim entity {} not found in world", sim_ent.id);
        }
    }
}
```

这段代码里有四个细节值得反复咀嚼:

第一,`continue` 跳过 spawn 分支——避免 fall-through 到 else 里去找 world slot(找不到会 panic)。
第二,`world.entity_mut(id)` 返回 `Option<&mut WorldEntity>`,None 表示 world 里没这个 id。
第三,派生字段(`chunk_index`、`aabb`)**在 world 这边重算**,不从 sim region 拷。
第四,异常分支用 `log::warn` 而不是 panic——生产游戏要"健壮"优先于"严格"。

这种"逐字段 patch"看起来啰嗦,但**它就是你未来给每个新字段加回写时的检查清单**。Casey 在视频里反复强调:"加新字段时,问自己:这是 immutable、mutable、还是 derived?据此决定回写策略。"这种纪律把"忘了回写"这种 bug 从"随机发生"降到"加字段时强制思考"。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发里这个模式叫 **region-based simulation** 或 **ticking partition**。Minecraft 用它决定哪些 chunk 做 mob spawning,Factorio 用它决定哪些段电网做能量结算。

关键设计点:

- **Region 大小**:太大 = 慢;太小 = 边界效应(entity 在两个 region 间反复横跳)
- **Region 边界**:entity 跨边界时不能"分裂"——必须在某一帧"完整"属于一个 region
- **跨 region 交互**:如果 entity A 在 region X,entity B 在 region Y,但 A 攻击 B 的子弹跨边界,怎么办?通常:跨边界的交互**推到下一帧**(子弹在边界等一帧)

Handmade Hero 用"sim region 半径 > 玩家可见半径"来缓解边界效应——边界外的 entity 不参与交互,但仍模拟。

让我们把这个模式放到游戏行业的历史脉络里看。早期(8-bit 时代)的整个世界就 1 屏,所有 entity 同等模拟——没有 region 概念。原因简单:屏幕上最多 8-16 个 sprite,模拟全部几乎零成本。但到了 16-bit 时代(SNES、Genesis),游戏世界扩大到几百个 entity,工程师开始意识到"远处的 enemy 不应该和近处一样吃 CPU"。

最早的解法是 **distance-based ticking**:每个 entity 算一下离玩家的距离,远的就降级(比如从 60Hz 模拟降到 15Hz)。这方法简单但有个大问题——离玩家远的 entity 在被降级模拟期间,如果有玩家触发的远程事件(比如狙击枪打远处),反应会延迟。

更精细的方案是 **region-based simulation**——把世界切成规则的格子(cell),每帧只完整模拟玩家附近的几个 cell,其他 cell 完全冻结(状态保存但不计算)。这就是 HH 用的方案。它的优点:CPU 预算精确控制(模拟规模 = 常数,和世界大小无关);缺点:跨 cell 的交互(子弹、远距攻击、声音传播)要特殊处理。

现代大型开放世界游戏(GTA、Cyberpunk、Witcher 3)都用更复杂的版本——结合 region-based ticking 和 LOD(level of detail):近处的 NPC 全功能 AI、远处的简化 AI、最远的只渲染不思考。这种分级让《Cyberpunk 2077》能在夜之城放几万个 NPC 而不卡。

### 3.2 · Linux 系统编程视角

这个"工作集隔离"模式在 Linux 内核里到处都是:

- **Page cache**:磁盘数据拷贝到内存(page cache)改,定期写回磁盘。Linux 的 `write()` 系统调用默认只把数据放进 page cache,真正的磁盘 I/O 由内核后台线程(pdflush/writethread)异步完成。这就是 sim region ↔ world 模式的"操作系统版"。
- **Per-CPU 数据**:每个 CPU 一份变量副本,定期 flush 到全局。Linux 的 `percpu` 模块让每个 CPU 独立累加计数器,避免 cache line 上的锁竞争,定期 sum 到全局。这就是"每帧 sim region 算,帧结束汇总回 world"。
- **RCU(Read-Copy-Update)**:读者看老副本,写者改新副本,合适时机 swap。RCU 的 grace period 类似于"等待 sim region 销毁"——必须等所有"持用旧数据的读者"退出后才能回收。

让我们用一个具体的 Linux 例子来类比。假设你在写一个统计每秒网络包数的工具。最朴素的实现:

```c
// 全局共享计数器
static atomic_t packet_count;
void on_packet() { atomic_inc(&packet_count); }
```

问题:多核机器上,每个核都在 atomic_inc 同一个 cache line,**cache line 在核之间反复弹跳(false sharing)**,性能极差。Linux 的解法是 per-CPU 计数器:

```c
// 每个 CPU 独立计数器
static DEFINE_PER_CPU(int, packet_count);
void on_packet() {
    // this_cpu_inc 不需要锁,因为这个变量只有当前 CPU 会写
    this_cpu_inc(packet_count);
}
// 周期性读取总和
int total() {
    int sum = 0;
    for_each_possible_cpu(cpu) {
        sum += per_cpu(packet_count, cpu);
    }
    return sum;
}
```

这正是 HH sim region 的思想:**热路径上各自运算(每 CPU / 每 sim region 帧),冷路径上汇总写回(周期性 sum / 帧结束回写 world)**。优化收益来源相同——避免共享数据的锁/cache 竞争。

Rust 生态的 `crossbeam` 提供类似的 "epoch-based reclamation",思想和 sim region 类似——不要立刻回收,等所有"读者"都离开当前 epoch 再回收。这种模式在无锁数据结构里是标配。

### 3.3 · Rust 生态视角

Rust 表达这个模式很自然——ownership 模型天然适合"转移":

```rust
// 把 entity 从 sim.entities 转移到 sim.outgoing
// 用 drain_filter 或 retain 把活的留下、死的删除
let survivors: Vec<_> = std::mem::take(&mut sim.entities)
    .into_iter()
    .filter(|e| !e.dead)
    .collect();
sim.outgoing = survivors;
```

`std::mem::take` 把 vec 内容拿走,留下空 vec——零拷贝转移 ownership。

如果想更高效(避免 Vec 重新分配),用 `swap_remove` 或 `retain_mut`:

```rust
// 原地过滤,保留活的
let mut i = 0;
while i < sim.entities.len() {
    if sim.entities[i].dead {
        sim.entities.swap_remove(i);  // O(1) 删除
    } else {
        i += 1;
    }
}
// 现在 sim.entities 里全是活的,直接当 outgoing 用
sim.outgoing = std::mem::take(&mut sim.entities);
```

Rust 的 borrow checker 在 sim region 这种"复杂状态机"里其实是**帮忙而不是阻碍**。一个常见场景:

```rust
// 错误版本(编译失败):
for sim_ent in &sim.entities {
    if sim_ent.dead {
        // 想从 vec 里 remove 这个 entity
        sim.entities.remove(...);  // 编译失败:borrow sim.entities 时不能再 mut 它
    }
}
```

这种写法在 C++ 里能编过,但运行时是 UB(iterator invalidation)。Rust 的 borrow checker 在编译期就拒绝了。正确的写法是 collect 死亡 id 后批量删除,或者用 `swap_remove` + 索引循环(我们上面的例子)。这种纪律让 Rust 游戏代码在 sim region 这种容易出 bug 的地方**编译器强制正确**。

### 3.4 · 图形学视角

虽然这天主要不是图形学,但 sim region 和渲染的 **frustum culling**(视锥剔除)思想一致——只算看得见的。Casey 在更早的天数里把渲染也分成了"可见 chunk"和"不可见 chunk",sim region 是这个思路在逻辑层的对应。

让我把这个类比展开。GPU 渲染流水线里,frustum culling 是最基础的一种"区域筛选":

1. **CPU 端 frustum cull**:遍历所有可见物体,检查 bounding sphere 是否在相机视锥内,不在的跳过 draw call。
2. **GPU 端 z-pre-pass / occlusion culling**:更精细的可见性,根据已渲染物体的深度判断被遮挡的物体。
3. **LOD selection**:远的物体用低精度 mesh,近的用高精度。也是一种"按距离分级处理"。

Sim region 是这种"按距离筛选"在逻辑层的对应:

| 阶段 | 渲染层 | 模拟层 |
|---|---|---|
| 全集 | 所有 mesh | world 里所有 entity |
| 工作集 | frustum 内的 mesh | sim region 内的 entity |
| 跳过 | frustum 外不画 | 离玩家远的 entity 不模拟 |
| 缓存 | 已算过的 visibility 不重算 | 跨帧缓存解包(day 544) |

两边思路完全对偶。**只算热区**是图形和游戏逻辑的共通智慧。

## 5 · 对照与变奏

游戏行业对此有不同做法:

- **Unity**:用 `GameObject.Find()` 直接查世界,没 sim region 概念。结果大世界性能差,要靠 DOTS/ECS 补救
- **Unreal**:用 `WorldPartition` 把大世界按 cell 切,运行时只加载附近 cell(数据流式,而非 sim region)
- **Bevy(Rust ECS)**:用 query 加 archetype,cache 表现接近 sim region

HH 选 sim region 是因为 Casey 想完整演示"为什么需要这个抽象"——他先写了没 sim region 的版本,卡了,再重构出 sim region。这是教学价值最高的路径。

### 5.1 把同一问题在不同范式里并排放

为了让这个对比更扎实,让我们把"world ↔ sim region 双向数据流"这一模式在四种工程范式里的对应写出来:

**OOP / 游戏对象模型**(Unity 早期、Unreal):没有显式的 sim region 概念。每个 GameObject 自带 Update 方法,引擎每帧遍历所有 GameObject 调用 Update。问题:大世界时全部 entity 都 Update,性能崩。后期 Unity 推出 DOTS(Data-Oriented Technology Stack),本质就是引入 ECS + sim region 思想。

**ECS / Data-Oriented**(Bevy、Unity DOTS、Flecs):用 archetype + query。每帧只 query"满足条件的 component 组合"。比如 query 所有 `(&Transform, &Health)` 在玩家附近的位置——本质上就是 sim region。但 ECS 把"哪些 entity 进 sim region"这个决策推迟到 query 阶段,更灵活。

**Functional / Immutable Data**(Clojure、Haskell 游戏如 ABE):world 是不可变数据。每帧生成新的 world 数据。回写不是"修改 slot",而是"返回新 world"。优点:无锁,可并行;缺点:GC 压力大,大型游戏用得少。

**Actor Model**(Erlang-style):每个 entity 是一个 actor(进程),消息传递。没有"共享 world"概念,entity 之间发消息。优点:天然分布式;缺点:消息开销大,不适合实时游戏。

HH 的选择(sim region + explicit patch back)是经典的 **data-oriented imperative** 范式,和 ECS 接近但更"手工"。Casey 故意不用 ECS 框架,因为 HH 的目标是"教底层",不是"教框架"。但你能在 ECS 框架里看到 sim region 思想的影子。

### 5.2 历史演化:从"全部 tick"到"分区 tick"

历史演化:早期游戏(8-bit 时代)整个世界就 1 屏,所有 entity 同等模拟。世界大了之后才有 region 概念,最早是 Zelda 系列的"screen-based simulation"——离开屏幕的 enemy "冻结"。

把这个演化画成一条时间线:

- **1980s(8-bit era)**:全部 tick。世界小,CPU 闲,不需要 region 概念。
- **1990s(16-bit era)**:distance-based ticking。远的 NPC 降级模拟(比如《Final Fantasy VI》地图上的 NPC 半速移动)。
- **2000s(3D 开放世界)**:cell-based streaming。GTA III 引入"加载附近 cell,卸载远处 cell"。但卸载的 cell 状态丢失,NPC "重生"——很出戏。
- **2010s(开放世界成熟期)**:persistent + dormant。Skyrim 让远离玩家的 NPC 进入"冬眠"状态——状态保存,不模拟,但下次回来仍是上次离开的样子。这就是 HH sim region 的思想。
- **2020s(大型 MMO)**:分布式 ticking。多个服务器各负责世界的一部分,跨服交互走消息。EVE Online 的"时间膨胀"(time dilation)是这种模式的极端例子。

HH 走的是 2010s 这条路。Casey 在视频里讨论 Skyrim 和 Oblivion 的对比——Oblivion 的 NPC 会"重置"(离开 cell 一段时间后状态丢失),Skyrim 修复了这点。这就是"day 543 思想"在商业游戏里的真实应用。

### 5.3 类比表:不同"工作集 ↔ 主存"系统

让我们把这个模式抽象到最一般的形式:

| 系统 | 主存(world) | 工作集(sim region) | 回写时机 | 一致性策略 |
|---|---|---|---|---|
| HH 游戏 | world (HashMap) | sim_region | 每帧结束 | 字段级 patch |
| Linux page cache | 磁盘 | page cache (RAM) | dirty writeback | write-through 或 write-back |
| Git | remote repo | local working tree | commit + push | 乐观并发(merge/rebase) |
| SQL DB | 数据表 | session buffer | commit | ACID transaction |
| Web 前端 | server DB | client state | save action | REST/GraphQL 写回 |
| 浏览器 cache | 远端服务器 | HTTP cache | 条件性 GET | ETag / Last-Modified |
| CPU cache | RAM | L1/L2/L3 cache | write-back on eviction | MESI 协议 |

每一行都是"工作集 ↔ 主存"模式的实例。**理解 HH sim region 后,你看所有这些系统都会觉得"哦,本质都一样"**——隔离热数据,异步同步,处理边界条件。这是软件工程最通用的一种 pattern。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Sim region 和 world 是两份"完整实体数据"吗?为什么需要两份?

**参考解答**:不是完整两份。World 是**完整的、持久的**,所有 entity 都在。Sim region 是**部分的、临时的**,只有玩家附近的 entity,且只持续一帧。两份的原因是性能——大世界不能每帧遍历全部 entity,只把热区复制到一段连续内存里高速模拟。这就像 CPU cache vs 内存:cache 不是内存的完整副本,只是热数据的副本。

### Lv2 · 动手实践

**题**:写一个最小可跑的 Rust 程序,模拟"world → sim region → world"的循环。要求:

- world 有 1000 个 entity,只有 ID 在 100..200 的进入 sim region
- 在 sim region 里,把 ID 偶数的 entity 血量减 10
- 模拟结束后,把 sim region 的修改回写 world
- 最后打印 world 中 ID 100..200 的血量,验证已被修改

**参考解答**:

```rust
#[derive(Clone, Debug)]
struct Entity {
    id: u64,
    health: i32,
}

struct World {
    entities: Vec<Entity>,
}

struct SimRegion {
    // 只持有引用或 clone 都行,这里 clone 简单
    entities: Vec<Entity>,
}

impl World {
    fn new() -> Self {
        let entities = (0..1000).map(|i| Entity { id: i, health: 100 }).collect();
        World { entities }
    }

    // 把 ID 在 [lo, hi) 的 entity 解包到 sim region
    fn pack_into_sim(&self, lo: u64, hi: u64) -> SimRegion {
        let entities = self.entities.iter()
            .filter(|e| e.id >= lo && e.id < hi)
            .cloned()
            .collect();
        SimRegion { entities }
    }

    // 把 sim region 的修改 patch 回 world(按 ID 匹配)
    fn unpack_from_sim(&mut self, sim: &SimRegion) {
        for sim_ent in &sim.entities {
            // 找 world 里 ID 相同的 entity
            if let Some(we) = self.entities.iter_mut().find(|e| e.id == sim_ent.id) {
                we.health = sim_ent.health;  // 只 patch mutable 字段
            }
        }
    }
}

fn main() {
    let mut world = World::new();

    // 一帧模拟
    let mut sim = world.pack_into_sim(100, 200);

    // 在 sim region 内,偶数 ID 的血量减 10
    for e in sim.entities.iter_mut() {
        if e.id % 2 == 0 {
            e.health -= 10;
        }
    }

    // 回写 world
    world.unpack_from_sim(&sim);

    // 验证:打印 ID 98, 100, 101, 102, 103 的血量
    for target in [98u64, 100, 101, 102, 103, 200] {
        let e = world.entities.iter().find(|e| e.id == target).unwrap();
        println!("id={} health={}", e.id, e.health);
    }
}
```

预期输出:

```
id=98 health=100    // 不在 sim region,没改
id=100 health=90    // 偶数,被改
id=101 health=100   // 奇数,没改
id=102 health=90
id=103 health=100
id=200 health=100   // 边界,不在 sim region
```

## 8 · Rust / Arch 落地代码

完整可跑的简化版 sim region 实现。我们在 §2 的基础上扩展,加入"spawn_this_frame"和"dead"的完整处理。这段代码可以直接 `cargo new` + `cargo run` 跑起来,你可以亲手改 entity 数量、模拟半径,看不同参数下的行为。

```rust
use std::collections::HashMap;

// 一个 entity 由 ID 唯一标识。Newtype 模式避免 id 和其他 u64 混淆。
#[derive(Clone, Debug, PartialEq, Eq, Hash)]
struct EntityId(u64);

// World 里的紧凑存储:大 hash map。
// 为什么不用 Vec?因为 entity 会动态增删,Vec 的 swap_remove 会改变 index,
// 而我们用 EntityId 作为外部引用,index 不能变。HashMap 解决这个问题。
#[derive(Clone, Debug)]
struct WorldEntity {
    id: EntityId,
    pos: [f32; 3],     // 世界坐标(米)
    health: i32,       // mutable persistent
    kind: &'static str, // immutable(派生)
}

struct World {
    entities: HashMap<EntityId, WorldEntity>,
}

impl World {
    fn new() -> Self {
        World { entities: HashMap::new() }
    }

    fn insert(&mut self, e: WorldEntity) {
        self.entities.insert(e.id.clone(), e);
    }

    // 把玩家附近(radius 内)的 entity 解包到 sim region。
    // 注意:这里用 clone,简化教学。真实代码会用 arena 或 Cow 减少拷贝。
    fn pack_sim(&self, center: [f32; 3], radius: f32) -> SimRegion {
        let r2 = radius * radius;
        let mut entities = Vec::new();
        for e in self.entities.values() {
            let dx = e.pos[0] - center[0];
            let dy = e.pos[1] - center[1];
            let dz = e.pos[2] - center[2];
            if dx*dx + dy*dy + dz*dz <= r2 {
                entities.push(UnpackedEntity {
                    id: e.id.clone(),
                    pos: e.pos,
                    health: e.health,
                    kind: e.kind,
                    spawn_this_frame: false,  // 从 world 解包的不算 spawn
                    dead: false,
                });
            }
        }
        SimRegion {
            entities,
            outgoing: Vec::new(),
            center,
            radius,
        }
    }

    // 接受 sim region 的回写。这一段是最容易出 bug 的,要重点 review。
    fn unpack_sim(&mut self, sim: &SimRegion) {
        for sim_ent in &sim.outgoing {
            // 分支 1:本帧新生的 —— insert,不是 update
            if sim_ent.spawn_this_frame {
                self.entities.insert(sim_ent.id.clone(), WorldEntity {
                    id: sim_ent.id.clone(),
                    pos: sim_ent.pos,
                    health: sim_ent.health,
                    kind: sim_ent.kind,
                });
                continue;
            }

            // 分支 2:已存在的 —— 字段级 patch
            if let Some(we) = self.entities.get_mut(&sim_ent.id) {
                we.pos = sim_ent.pos;
                we.health = sim_ent.health;
                // 派生字段(kind 等)不动
            } else {
                // 异常:既不是 spawn 又找不到对应 world slot
                eprintln!("[warn] sim entity {:?} not found in world", sim_ent.id);
            }
        }
    }

    // 处理"在 sim region 内死亡"的 entity —— 从 world 删除
    fn delete_dead(&mut self, dead_ids: &[EntityId]) {
        for id in dead_ids {
            self.entities.remove(id);
        }
    }
}

// UnpackedEntity 是 sim region 内部的形式。比 WorldEntity 多了 dead / spawn_this_frame
#[derive(Clone, Debug)]
struct UnpackedEntity {
    id: EntityId,
    pos: [f32; 3],
    health: i32,
    kind: &'static str,
    dead: bool,
    spawn_this_frame: bool,
}

struct SimRegion {
    entities: Vec<UnpackedEntity>,
    outgoing: Vec<UnpackedEntity>,
    center: [f32; 3],
    radius: f32,
}

impl SimRegion {
    fn simulate(&mut self) {
        // 这里跑"游戏逻辑"。教学版只检查 health <= 0 标记 dead。
        for e in self.entities.iter_mut() {
            if e.health <= 0 {
                e.dead = true;
            }
        }

        // 把活的转移到 outgoing,死的记录到 dead_ids 供 world 删除
        let mut i = 0;
        let mut dead_ids = Vec::new();
        while i < self.entities.len() {
            if self.entities[i].dead {
                dead_ids.push(self.entities[i].id.clone());
                self.entities.swap_remove(i);
            } else {
                i += 1;
            }
        }
        self.outgoing = std::mem::take(&mut self.entities);
        // dead_ids 通过外部 API 暴露给 world.delete_dead
        self.dead_ids = dead_ids;
    }
}

// main 函数演示完整流程
fn main() {
    let mut world = World::new();
    world.insert(WorldEntity {
        id: EntityId(1), pos: [0.0, 0.0, 0.0], health: 100, kind: "player",
    });
    world.insert(WorldEntity {
        id: EntityId(2), pos: [1.0, 0.0, 0.0], health: 50, kind: "enemy",
    });
    world.insert(WorldEntity {
        id: EntityId(3), pos: [100.0, 0.0, 0.0], health: 50, kind: "far_enemy",
    });

    // 玩家在 (0,0,0),模拟半径 10 米
    let mut sim = world.pack_sim([0.0, 0.0, 0.0], 10.0);
    println!("sim region 有 {} 个 entity", sim.entities.len());  // 输出 2

    // 攻击:把 enemy 血量减 100
    for e in sim.entities.iter_mut() {
        if e.kind == "enemy" {
            e.health -= 100;
        }
    }

    sim.simulate();

    // 回写 world(包括 spawn / update / delete 三类处理)
    world.unpack_sim(&sim);
    if let Some(sim_ref) = Some(&sim) {
        world.delete_dead(&sim_ref.dead_ids);
    }

    // 验证
    for (id, e) in &world.entities {
        println!("id={:?} health={} kind={}", id, e.health, e.kind);
    }
    // 输出:
    //   id=EntityId(1) health=100 kind=player   ← 玩家未变
    //   id=EntityId(3) health=50 kind=far_enemy ← 远处的未进 sim,未变
    //   (enemy 已删除)
}
```

注意 `SimRegion` 还需要加一个 `dead_ids: Vec<EntityId>` 字段,这里没在 struct 定义里展示但 main 里用到了,你可以补全。完整的工程代码还会:

- 处理"两个 entity 在同一帧内合并"(比如玩家捡物品)
- 处理"entity 跨 chunk 边界"(sim region 半径覆盖多个 chunk 时)
- 处理"分屏游戏的多个 sim region"
- 跨线程模拟时给 SimRegion 加 Send/Sync 标记

```bash
# 装 perf(如果没有)。Arch 的 perf 在 linux 包里
sudo pacman -S perf              # 可能需要重新启动到对应内核版本

# 编译 release 版
cargo build --release

# 跑 perf stat 看 cache-misses
perf stat -e cache-misses,cache-references ./target/release/sim_region_demo

# 输出示例:
# 1,234,567  cache-misses      # 12% miss rate
# 9,876,543  cache-references
```

如果想看更细的 cache 分析,用 `perf record` + `perf report`:

```bash
sudo perf record -g ./target/release/sim_region_demo
sudo perf report
# 在 TUI 里按 cache-misses 排序,看哪个函数 cache miss 多
```

如果遇 "Permission denied" 的 perf 错误:

```bash
# 临时调整 perf_event_paranoid
sudo sysctl -w kernel.perf_event_paranoid=1

# 永久调整:写入 /etc/sysctl.d/99-perf.conf
echo 'kernel.perf_event_paranoid = 1' | sudo tee /etc/sysctl.d/99-perf.conf
sudo sysctl --system
```

更现代的工具是 `hotspot`(GUI 的 perf 前端):

```bash
sudo pacman -S hotspot
perf record -g ./target/release/sim_region_demo
hotspot perf.data
# GUI 看火焰图,鼠标 hover 看每个函数的 cache miss / cycle 占比
```

### 8.y · 用 cargo flamegraph 看 sim region 在 CPU 上的占比

如果你想看"sim region 占了帧时间的多少",用 `cargo flamegraph`:

```bash
# 装
cargo install flamegraph
sudo pacman -S flamegraph   # 前端工具

# 跑(会自动 perf record 并生成 SVG)
cargo flamegraph --release
# 在浏览器打开 flamegraph.svg,看每个函数的占比
```

典型结果:如果你看到 `pack_sim` 和 `unpack_sim` 各占帧时间的 5%,`simulate` 占 30%,说明大部分时间在游戏逻辑本身,正确——回写不是瓶颈。如果反过来,回写占大头,说明 clone 太多或者 HashMap 操作太多,需要优化。
