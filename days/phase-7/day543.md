# Day 543 · 把解包实体从模拟区域移到世界

> Day 538 引入"解包实体(unpacked entity)"——把存档里的紧凑实体在游戏里展开成可编辑、可修改的运行时形式。但当时它们活在 sim region(模拟区域,一个帧级的临时世界切片)里,模拟完就丢。Day 543 把它们**持久化到 world**:模拟完后把"还活着"的解包实体回写到 world,跨帧保留它们的修改。

## 0 · 为什么要有这一天

我们先把上一段提到的两个概念说清楚,再回到今天。

**World(世界)** 是整个游戏的实体存储中心,横跨所有 chunk,持续整个游戏生命周期。每个 entity 有稳定 ID,跨帧存活。

**Sim region(模拟区域)** 是某一帧"我现在要算物理/AI"时圈出来的小范围,只包含玩家附近的几个 chunk,模拟完丢掉。这是 Handmade Hero 的核心性能优化——不模拟看不见的东西。

为什么把 entity 在两个区域之间来回搬?因为:

- 存储在 world(便宜,不动的世界)
- 计算在 sim region(只复制玩家周围一小块,够算就行)
- 计算结果(比如"怪物被打死了")要回写 world,否则下一帧忘了

之前的实现:解包实体从存档**进** sim region,但**没有回写**——它们在 sim region 内被编辑器修改,但 sim region 一结束修改就丢。Day 543 修这个 bug:**让解包实体的修改持久化**。

为什么这事重要?Day 538 引入解包实体是为了**编辑器**(编辑器要能改存档里的实体)。如果改完不回写,编辑器就是废的——改了等于没改,玩家走两步存档里还是老样子。Casey 在视频里说这是"绕了大圈才回的家"——之前以为 sim region 是终点,实际是中转站。

完成这一天之后,你具备:

- 理解 world ↔ sim region 双向数据流
- 能正确处理 entity 的"生命周期"——出生(world)、模拟(sim region)、死亡或存活(world)
- 知道为什么 "outgoing entity list" 这种数据结构存在

## 1 · Casey 今天做了什么

Casey 这一天的核心动作是给 sim region 加一个**输出队列**(outgoing list):

第一步,他在 sim region 结构里加一个字段 `OutgoingEntities`,类型是 array,放"模拟结束仍然存活的解包实体"。

第二步,他在 sim region 的"end frame"里,把所有还活着的解包实体从内部存储 `Entities` 转移到 `OutgoingEntities`(标记为"等待回写")。

第三步,他在 world 的"接受 sim region 结果"逻辑里,遍历 `OutgoingEntities`,把每个实体的修改 patch 回 world 里对应的 entity slot。

Casey 在视频里强调:这是个看似简单但**容易出错**的事——一旦在转移过程中漏掉某个字段,游戏就会出现"怪物死了又复活""物品捡了又出现"的怪 bug。所以他把转移做成一个**显式的 struct-to-struct 拷贝**,每字段一行,方便审查。

## 2 · 心智模型

### 类比:酒店的入住和退房

想象 world 是一座大城市的人口登记册,每个 entity 是一个市民,有身份证(ID)和家庭住址(chunk 里的 slot)。

Sim region 是市中心的一家**酒店**。每天早上(每帧开始),酒店去登记册里"邀请"附近的市民来住一天——但只邀请离酒店 500 米内的(玩家周围的 entity)。市民住进酒店就是"被解包、进入 sim region"。

在酒店里(模拟),市民可能做很多事:吃饭、打架、被杀、生孩子。这些事只有**在酒店里发生**才算。

晚上(模拟结束),酒店要**办理退房**:

- 被杀的市民——从登记册删除
- 新生的婴儿——加进登记册
- 活着的市民——把他们在酒店里发生的变化(受伤了?发财了?)**回写到**登记册
- 住得太远的市民(走出了 500 米)——不再被邀请,但仍活在登记册里

之前的 bug:酒店退房时只把"住客名册"扔了,没回写变化。结果登记册里这些人永远停在"早上出门时的状态"——他们虽然在酒店里被打了一顿,登记册里还显示"健康"。

### 严谨展开:Sim Region 的数据结构

```rust
// 一个 sim region 是一帧的"工作台"
struct SimRegion {
    // 输入:从 world 解包进来的实体
    entities: Vec<UnpackedEntity>,

    // 输出:模拟结束仍存活的实体(等回写)
    outgoing: Vec<UnpackedEntity>,

    // 元数据:这一帧模拟的范围
    world_center: Vec3,
    world_radius: f32,
}

// UnpackedEntity 是"展开的实体",所有字段都明摆着,方便编辑器修改
struct UnpackedEntity {
    id: u64,           // 全局唯一 ID
    position: Vec3,    // 世界坐标
    kind: EntityKind,  // 玩家/怪物/物品/...
    health: f32,       // 当前血量
    // ... 其他游戏字段
}
```

帧的生命周期:

```
帧开始:
  1. 创建 SimRegion
  2. 遍历 world 中玩家附近的 chunk
  3. 把每个 chunk 里"靠近玩家"的 entity 解包到 sim.entities

模拟(物理、AI、战斗):
  4. 遍历 sim.entities,跑游戏逻辑
  5. 死的标记 dead,新的 push 进 sim.entities

帧结束:
  6. 遍历 sim.entities
     - 死的:world 里删除对应 slot
     - 活的:push 进 sim.outgoing
  7. 遍历 sim.outgoing,把变化 patch 回 world
  8. 销毁 SimRegion(下一帧重建)
```

### 为什么不直接在 world 里改?

你可能会问:为啥这么麻烦,直接在 world 里改不就行了?

性能。World 可能包含 100 万个 entity(超大世界),但你一帧只模拟玩家周围 100 个。如果直接遍历 world 找这 100 个,cache miss 海了去——每次跳到新 chunk 都是几十纳秒的内存延迟。

解包到 sim region,把 100 个 entity 拷贝到一段连续内存,模拟时它们都在 L1 cache 里,跑得飞快。模拟完回写,只动 100 个 slot,不动剩下 999900 个。

这是经典的"**structure of arrays + 工作集隔离**"模式。数据库也用类似思路——把热数据复制到内存里改,定期批量写回磁盘。

### 回写时的"字段级 patch"

最微妙的细节:回写不是整个 entity 覆盖,而是**字段级 patch**。原因:

world 里 entity 可能存了"原始 + 派生"两类字段。比如 `position`(原始,会变)和 `chunk_index`(派生,从 position 算)。如果整个 entity 覆盖,派生字段也覆盖,万一 sim region 里没正确维护 `chunk_index`,world 就坏了。

正确做法:回写时只 patch **mutable 字段**(血量、位置、状态),不动 **派生字段**(在 world 里重算)。

```rust
fn write_back(world: &mut World, sim: &SimRegion) {
    for sim_ent in &sim.outgoing {
        // 找 world 里对应 slot
        let world_ent = world.entity_mut(sim_ent.id);
        if let Some(we) = world_ent {
            // 只 patch mutable 字段
            we.position = sim_ent.position;
            we.health = sim_ent.health;
            we.state = sim_ent.state;
            // 派生字段(chunk_index 等)不写,在 world 里重算
        }
    }
}
```

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发里这个模式叫 **region-based simulation** 或 **ticking partition**。Minecraft 用它决定哪些 chunk 做 mob spawning,Factorio 用它决定哪些段电网做能量结算。

关键设计点:

- **Region 大小**:太大 = 慢;太小 = 边界效应(entity 在两个 region 间反复横跳)
- **Region 边界**:entity 跨边界时不能"分裂"——必须在某一帧"完整"属于一个 region
- **跨 region 交互**:如果 entity A 在 region X,entity B 在 region Y,但 A 攻击 B 的子弹跨边界,怎么办?通常:跨边界的交互**推到下一帧**(子弹在边界等一帧)

Handmade Hero 用"sim region 半径 > 玩家可见半径"来缓解边界效应——边界外的 entity 不参与交互,但仍模拟。

### 3.2 · Linux 系统编程视角

这个"工作集隔离"模式在 Linux 内核里到处都是:

- **Page cache**:磁盘数据拷贝到内存(page cache)改,定期写回磁盘
- **Per-CPU 数据**:每个 CPU 一份变量副本,定期 flush 到全局
- **RCU(Read-Copy-Update)**:读者看老副本,写者改新副本,合适时机 swap

Rust 生态的 `crossbeam` 提供类似的 "epoch-based reclamation",思想和 sim region 类似——不要立刻回收,等所有"读者"都离开当前 epoch 再回收。

### 3.3 · Rust 生态视角

Rust 表达这个模式很自然——ownership 模型天然适合"转移":

```rust
// 把 entity 从 sim.entities 转移到 sim.outgoing
// 用 drain_filter 或 retain 把活的留下、死的删除
let survivors: Vec<_> = std::mem::take(&mut sim.entities)
    .into_iter()
    .filter(|e| !e.dead)
    .collect();
sim.outgoing = survivors;
```

`std::mem::take` 把 vec 内容拿走,留下空 vec——零拷贝转移 ownership。

如果想更高效(避免 Vec 重新分配),用 `swap_remove` 或 `retain_mut`:

```rust
// 原地过滤,保留活的
let mut i = 0;
while i < sim.entities.len() {
    if sim.entities[i].dead {
        sim.entities.swap_remove(i);  // O(1) 删除
    } else {
        i += 1;
    }
}
// 现在 sim.entities 里全是活的,直接当 outgoing 用
sim.outgoing = std::mem::take(&mut sim.entities);
```

## 5 · 对照与变奏

游戏行业对此有不同做法:

- **Unity**:用 `GameObject.Find()` 直接查世界,没 sim region 概念。结果大世界性能差,要靠 DOTS/ECS 补救
- **Unreal**:用 `WorldPartition` 把大世界按 cell 切,运行时只加载附近 cell(数据流式,而非 sim region)
- **Bevy(Rust ECS)**:用 query 加 archetype,cache 表现接近 sim region

HH 选 sim region 是因为 Casey 想完整演示"为什么需要这个抽象"——他先写了没 sim region 的版本,卡了,再重构出 sim region。这是教学价值最高的路径。

历史演化:早期游戏(8-bit 时代)整个世界就 1 屏,所有 entity 同等模拟。世界大了之后才有 region 概念,最早是 Zelda 系列的"screen-based simulation"——离开屏幕的 enemy "冻结"。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Sim region 和 world 是两份"完整实体数据"吗?为什么需要两份?

**参考解答**:不是完整两份。World 是**完整的、持久的**,所有 entity 都在。Sim region 是**部分的、临时的**,只有玩家附近的 entity,且只持续一帧。两份的原因是性能——大世界不能每帧遍历全部 entity,只把热区复制到一段连续内存里高速模拟。这就像 CPU cache vs 内存:cache 不是内存的完整副本,只是热数据的副本。

### Lv2 · 动手实践

**题**:写一个最小可跑的 Rust 程序,模拟"world → sim region → world"的循环。要求:

- world 有 1000 个 entity,只有 ID 在 100..200 的进入 sim region
- 在 sim region 里,把 ID 偶数的 entity 血量减 10
- 模拟结束后,把 sim region 的修改回写 world
- 最后打印 world 中 ID 100..200 的血量,验证已被修改

**参考解答**:

```rust
#[derive(Clone, Debug)]
struct Entity {
    id: u64,
    health: i32,
}

struct World {
    entities: Vec<Entity>,
}

struct SimRegion {
    // 只持有引用或 clone 都行,这里 clone 简单
    entities: Vec<Entity>,
}

impl World {
    fn new() -> Self {
        let entities = (0..1000).map(|i| Entity { id: i, health: 100 }).collect();
        World { entities }
    }

    // 把 ID 在 [lo, hi) 的 entity 解包到 sim region
    fn pack_into_sim(&self, lo: u64, hi: u64) -> SimRegion {
        let entities = self.entities.iter()
            .filter(|e| e.id >= lo && e.id < hi)
            .cloned()
            .collect();
        SimRegion { entities }
    }

    // 把 sim region 的修改 patch 回 world(按 ID 匹配)
    fn unpack_from_sim(&mut self, sim: &SimRegion) {
        for sim_ent in &sim.entities {
            // 找 world 里 ID 相同的 entity
            if let Some(we) = self.entities.iter_mut().find(|e| e.id == sim_ent.id) {
                we.health = sim_ent.health;  // 只 patch mutable 字段
            }
        }
    }
}

fn main() {
    let mut world = World::new();

    // 一帧模拟
    let mut sim = world.pack_into_sim(100, 200);

    // 在 sim region 内,偶数 ID 的血量减 10
    for e in sim.entities.iter_mut() {
        if e.id % 2 == 0 {
            e.health -= 10;
        }
    }

    // 回写 world
    world.unpack_from_sim(&sim);

    // 验证:打印 ID 98, 100, 101, 102, 103 的血量
    for target in [98u64, 100, 101, 102, 103, 200] {
        let e = world.entities.iter().find(|e| e.id == target).unwrap();
        println!("id={} health={}", e.id, e.health);
    }
}
```

预期输出:

```
id=98 health=100    // 不在 sim region,没改
id=100 health=90    // 偶数,被改
id=101 health=100   // 奇数,没改
id=102 health=90
id=103 health=100
id=200 health=100   // 边界,不在 sim region
```

## 8 · Rust / Arch 落地代码

完整可跑的简化版 sim region 实现:

```rust
// 一个 entity 由 ID 唯一标识
#[derive(Clone, Debug, PartialEq)]
struct EntityId(u64);

// World 里的紧凑存储:大 hash map
use std::collections::HashMap;

#[derive(Clone, Debug)]
struct WorldEntity {
    id: EntityId,
    pos: [f32; 3],     // 世界坐标
    health: i32,       // mutable
    kind: &'static str, // 不可变(派生)
}

struct World {
    entities: HashMap<EntityId, WorldEntity>,
}

impl World {
    fn new() -> Self {
        World { entities: HashMap::new() }
    }

    fn insert(&mut self, e: WorldEntity) {
        self.entities.insert(e.id.clone(), e);
    }

    // 把玩家附近(radius 内)的 entity 解包到 sim region
    fn pack_sim(&self, center: [f32; 3], radius: f32) -> SimRegion {
        let r2 = radius * radius;
        let mut entities = Vec::new();
        for e in self.entities.values() {
            let dx = e.pos[0] - center[0];
            let dy = e.pos[1] - center[1];
            let dz = e.pos[2] - center[2];
            if dx*dx + dy*dy + dz*dz <= r2 {
                entities.push(e.clone());  // 解包 = clone
            }
        }
        SimRegion {
            entities,
            outgoing: Vec::new(),
        }
    }

    // 接受 sim region 的回写
    fn unpack_sim(&mut self, sim: &SimRegion) {
        for sim_ent in &sim.outgoing {
            if let Some(we) = self.entities.get_mut(&sim_ent.id) {
                // 字段级 patch:只改 mutable
                we.pos = sim_ent.pos;
                we.health = sim_ent.health;
                // 不动 kind(派生)
            }
        }
    }
}

// SimRegion 内部用 UnpackedEntity(可能有更多字段)
#[derive(Clone, Debug)]
struct UnpackedEntity {
    id: EntityId,
    pos: [f32; 3],
    health: i32,
    kind: &'static str,
    dead: bool,  // sim region 特有:是否被杀
}

struct SimRegion {
    entities: Vec<UnpackedEntity>,
    outgoing: Vec<UnpackedEntity>,
}

impl SimRegion {
    // 模拟一帧
    fn simulate(&mut self) {
        for e in self.entities.iter_mut() {
            // 简单逻辑:血量 <= 0 标记 dead
            if e.health <= 0 {
                e.dead = true;
            }
        }

        // 帧结束:把活的转移到 outgoing
        let mut i = 0;
        while i < self.entities.len() {
            if self.entities[i].dead {
                self.entities.swap_remove(i);
                // dead 的不进 outgoing,world 里下一步要删除
            } else {
                i += 1;
            }
        }
        self.outgoing = std::mem::take(&mut self.entities);
    }
}

fn main() {
    let mut world = World::new();
    world.insert(WorldEntity {
        id: EntityId(1), pos: [0.0, 0.0, 0.0], health: 100, kind: "player",
    });
    world.insert(WorldEntity {
        id: EntityId(2), pos: [1.0, 0.0, 0.0], health: 50, kind: "enemy",
    });
    world.insert(WorldEntity {
        id: EntityId(3), pos: [100.0, 0.0, 0.0], health: 50, kind: "far_enemy",
    });

    // 玩家在 (0,0,0),模拟半径 10
    let mut sim = world.pack_sim([0.0, 0.0, 0.0], 10.0);
    println!("sim region 有 {} 个 entity", sim.entities.len());  // 2

    // 攻击:敌人血量减 100,死
    for e in sim.entities.iter_mut() {
        if e.kind == "enemy" {
            e.health -= 100;
        }
    }

    sim.simulate();

    // 回写 world
    world.unpack_sim(&sim);

    // 验证
    for (id, e) in &world.entities {
        println!("id={:?} health={} kind={}", id, e.health, e.kind);
    }
}
```
