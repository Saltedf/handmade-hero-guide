### Camera 参数的相互依赖

HH 的 debug camera 有几个参数:

- `focal_length`(焦距)
- `camera_distance`(相机距离)
- `viewport_height`(视口高度)
- `world_scale`(世界尺度)

这些参数相互关联——改一个,画面效果变。具体关系:

**透视投影公式**(简化):
```
screen_height = world_height × focal_length / camera_distance
```

意思是:物体在屏幕上的高度 = (世界高度 × 焦距) / 相机距离。改焦距、改距离、改世界高度,都影响屏幕高度。

**例**:50 米城堡,焦距 1.0,距离 100 米,屏幕高度 = 50 × 1.0 / 100 = 0.5(单位归一化)。如果 viewport 是 1.0,城堡占 50%。

但 Casey 想城堡占 30%——怎么调?
- 改距离:0.3 = 50 × 1.0 / x → x = 50 / 0.3 ≈ 167 米
- 改焦距:0.3 = 50 × f / 100 → f = 0.6
- 改世界尺度:0.3 = w × 1.0 / 100 → w = 30

每个解都对,但**改哪个参数**有副作用:
- 改距离 → 视野角度变(远看,广角)
- 改焦距 → 透视畸变变(短焦距,广角畸变)
- 改世界尺度 → 其他物体相对位置变

工业级选择:**固定焦距(35mm 等效),改距离**。这是摄影的"标准焦距",画面自然。

### 反向求解:代数 vs 数值

Day 520 解这道题有两种方法:

**代数法(解析)**:列方程,符号运算,得闭式解。例:已知 focal_length=1.0、world_height=50、要 screen_height=0.3,直接算 camera_distance = 50×1.0/0.3 = 167。

代数法**快**(O(1))、**精确**(无数值误差),但**要求方程可解**。复杂模型(非线性、约束)可能无解析解。

**数值法(迭代)**:猜一个值,算结果,与目标比,调整猜值,迭代。例如 Newton-Raphson、二分搜索。

数值法**通用**(对任意函数可用),但**慢**(O(N) 迭代)、**有数值误差**(收敛精度限制)。

工业级选择:**优先代数,不能则数值**。Casey Day 520 主要用代数,因为 camera 参数关系简单(线性)。

## 1 · Casey 今天做了什么

Casey 这一天做了 7 步,核心是"用数学方法解决参数 bug"。

**第一步,定义问题**。Casey 打开游戏,debug camera 画面"不对"——物体大小、位置、视野都偏离预期。他怀疑是 `focal_length` 参数错。但他不知道正确值应该是多少,只能"试"。Day 520 他决定**用代数求**——给定"想要什么效果",求"参数应该是什么"。

变量定义:
- `S`:屏幕高度(像素)
- `H`:物体在世界的高度(世界单位)
- `D`:物体到相机的距离(世界单位)
- `f`:焦距(待求)

**第二步,推导公式**。Casey 在白板(其实是直播讲)上推:

```
透视投影公式:物体在屏幕上的大小 = f * H / D
   即:projected_size = f * world_size / distance

期望:projected_size = R * S   (R 是物体占屏比例)

联立:f * H / D = R * S
求解 f:f = R * S * D / H
```

如果已知 R = 0.3(物体占屏 30%)、S = 1080、D = 10、H = 5:
```
f = 0.3 * 1080 * 10 / 5 = 648
```

Casey 验证:代入 f = 648 算 projected_size = 648 * 5 / 10 = 324。324 / 1080 = 0.3 = R。**等式成立**。

**第三步,他验证公式**。他在 Rust 里实现:

```rust
fn solve_focal_length(target_ratio: f32, screen_height: f32,
                      distance: f32, world_size: f32) -> f32 {
    target_ratio * screen_height * distance / world_size
}
```

跑测试,结果符合手算。

**第四步,发现 bug**。他改游戏代码用新公式,跑游戏——画面仍不对!他 println 出参数,发现 **`focal_length` 单位混乱**。Casey 之前的代码里,focal_length 有时是"像素"单位,有时是"世界单位",混淆。代数推导假设单位一致,实际代码里不一致,公式失效。

**第五步,统一单位**。Casey 把所有变量统一为**世界单位**(world unit)。像素在 viewport 边界转换:

```rust
// 统一单位:全部世界单位
let screen_height_world: f32 = screen_height_pixels / pixels_per_world_unit;
// pixels_per_world_unit 取决于 viewport 设置
```

这看似简单,实际**单位一致是图形学最常犯的错误**。CPU / GPU / 物理引擎各自有"单位约定",混用导致各种 bug。

**第六步,重新调参**。统一单位后,代入公式算的参数实际工作。Casey 跑游戏,物体大小、位置都正确。**代数解救了调试**。

**第七步,加 UI 滑块**。Casey 在 debug UI 加滑块,实时调 focal_length / distance / FOV。视觉反馈即时,调参极快。这是"工具链投资"——前期花时间建调参工具,后期省 100 倍时间。

Day 520 教学核心:**遇到参数 bug,不要"试",要"算"**。代数方法 5 分钟解,试错方法 5 小时不一定解。这是工业级图形程序员的思维方式。

## 2 · 心智模型

### 类比:摄影曝光三角

摄影:光圈 / 快门 / ISO 三个参数,影响曝光。改一个,其他要补偿。

相机参数同构——焦距 / 距离 / 视口相互关联。改一个,画面变。

### 透视投影公式

```
screen_size = f * world_size / distance
```

`f` 焦距(world unit),`world_size` 物体大小(world unit),`distance` 物体到相机距离(world unit)。

公式来源:相似三角形。

```
                camera
                 /|
              f / |
             /   | screen_size
            /    |
           /-----|
          / world_size
         /
        /--- distance ---/
```

相机看物体,物体投影到屏幕。`f / distance = screen_size / world_size`(相似三角形)。

所以 `screen_size = f * world_size / distance`。

### 反推参数

已知 screen_size、world_size、distance,求 f:

```
f = screen_size * distance / world_size
```

已知 f、world_size、distance,求 screen_size:

```
screen_size = f * world_size / distance
```

这是代数基本功。Casey Day 520 用这些公式调参。

### 视场角 FOV

FOV(弧度)和焦距关系:

```
tan(fov / 2) = (screen_height / 2) / f
```

或:

```
f = (screen_height / 2) / tan(fov / 2)
```

常见 FOV:60°-90°。

### Newton-Raphson 迭代:工业级数值解

Casey Day 520 的公式可解析解,直接算。但工业级图形学常遇到**不可解析**的方程。这时用 **Newton-Raphson 迭代**。

Newton-Raphson 的核心思想:**用切线近似曲线**。给定函数 f(x) 和初始猜测 x0,迭代:

```
x_{n+1} = x_n - f(x_n) / f'(x_n)
```

`f'(x)` 是导数。每步沿切线方向"滑向"零点。

例子:求 √2。等价于解 `x^2 - 2 = 0`。f(x) = x^2 - 2,f'(x) = 2x。从 x0 = 1 开始:

```
x1 = 1 - (1 - 2) / 2 = 1 + 0.5 = 1.5
x2 = 1.5 - (2.25 - 2) / 3 = 1.5 - 0.0833 = 1.4167
x3 = 1.4167 - (2.0069 - 2) / 2.8333 = 1.4142
x4 = ... = 1.41421356 (10 位精度)
```

**4 步收敛到 10 位精度**。Newton-Raphson 是**二次收敛**(quadratic convergence)——每步精度翻倍。

Rust 实现:

```rust
fn newton_solve(
    f: impl Fn(f32) -> f32,        // 函数
    df: impl Fn(f32) -> f32,        // 导数
    mut x: f32,                     // 初始猜测
    iterations: usize,
) -> f32 {
    for _ in 0..iterations {
        let fx = f(x);
        let dfx = df(x);
        if dfx.abs() < 1e-10 {
            break;    // 导数为零,无法迭代
        }
        let delta = fx / dfx;
        x -= delta;
        if delta.abs() < 1e-6 {
            break;    // 收敛
        }
    }
    x
}

// 求 √2
let sqrt2 = newton_solve(|x| x * x - 2.0, |x| 2.0 * x, 1.0, 20);
// sqrt2 ≈ 1.4142135
```

工业级应用:
- **物理引擎**:解碰撞约束(sequential impulse)
- **优化**:梯度下降找最小
- **方程求解**:任何非线性方程

### Bisection(二分搜索):简单稳定的备选

如果函数**不连续**或导数难算,Newton-Raphson 不灵。用 **bisection(二分搜索)**:

```rust
fn bisection(f: impl Fn(f32) -> f32, mut lo: f32, mut hi: f32, iterations: usize) -> f32 {
    let mut flo = f(lo);
    for _ in 0..iterations {
        let mid = (lo + hi) / 2.0;
        let fmid = f(mid);
        if flo * fmid < 0.0 {
            // 零点在 [lo, mid]
            hi = mid;
        } else {
            // 零点在 [mid, hi]
            lo = mid;
            flo = fmid;
        }
    }
    (lo + hi) / 2.0
}
```

Bisection 不如 Newton 快(线性收敛 vs 二次收敛),但**保证收敛**——只要初始 [lo, hi] 区间内有零点(f(lo) 和 f(hi) 异号)。Newton 可能不收敛(初始猜测差时)。

工业级实现常**混合**:先用 bisection 接近,然后 Newton 加速。

### 工业级相机系统的数学

Unreal、Unity 的 camera 设置背后是同一套数学:

- **Focal Length**(Unreal):直接对应 `f`
- **Field of View**(Unity / Unreal):`fov = 2 * atan(sensor_height / (2 * f))`
- **Aspect Ratio**:width / height,影响水平 FOV
- **Near / Far Plane**:裁剪面,影响 depth buffer 精度
- **Sensor Size**:模拟真实相机(35mm、 medium format)

`fov` 和 `focal_length` 是同一概念的两个表示:
- 摄影师偏好 `focal_length`(35mm、50mm、85mm lens)
- 图形程序员偏好 `fov`(60°、 90°、 110°)

转换公式:`fov_rad = 2 * atan(sensor_height / (2 * f))`,或反过来 `f = sensor_height / (2 * tan(fov_rad / 2))`。

35mm 全画幅相机,sensor_height = 24mm:
- 50mm lens → fov = 2 * atan(24 / 100) ≈ 27°
- 24mm lens → fov = 2 * atan(24 / 48) ≈ 53°
- 14mm lens → fov = 2 * atan(24 / 28) ≈ 81°

游戏里常说的"60° FOV"对应约 35mm 的"标准镜头"(类似人眼视角)。

### Lens 的视觉特性

不同 focal_length / FOV 的视觉效果:

**Wide angle(短 focal_length,大 FOV)**:
- FOV > 90°,focal_length < 24mm(35mm 等效)
- 视觉:**透视畸变**,近的物体大,远的小,边缘物体弯曲
- 用途:风景、动作、混乱场景
- 例子:《毁灭战士》(FPS,FOV 110°,临场感)

**Normal(中等 focal_length)**:
- FOV 50-70°,focal_length 35-50mm
- 视觉:**自然**,接近人眼视角
- 用途:RPG、生活模拟
- 例子:《塞尔达:旷野之息》

**Telephoto(长 focal_length,小 FOV)**:
- FOV < 30°,focal_length > 85mm
- 视觉:**压缩感**,远近物体看起来大小相似
- 用途:远观、紧张感、boss 战
- 例子:《黑暗之魂》boss 战镜头

游戏导演用这些视觉语言讲故事。Day 520 的数学是基础,镜头的"美感"是应用。

### Lv1 · 概念辨析

**题**:为什么用解析公式比经验调参好?

**参考解答**:三个理由:

第一,**可预测**。给定目标(R=30%),公式直接给参数。试错要试 N 次。

第二,**可移植**。换屏幕分辨率,公式自动算新参数。试错要重头调。

第三,**可理解**。公式让你知道参数怎么影响画面。试错只是"动一下看效果"。

代价:推导公式耗时。但一次推好,终生受益。

### Lv2 · 动手实践

**题**:实现焦距求解。给定目标(物体占屏幕比例 R),算焦距 f。

完成标准:`cargo run` 输入目标,输出参数。

**参考解答**:

```rust
struct CameraParams {
    focal_length: f32,
    distance: f32,
    world_scale: f32,
    screen_height: f32,
}

impl CameraParams {
    /// 推导:focal = R * screen_height * distance / world_size
    fn solve_focal_length(target_ratio: f32, world_size: f32) -> Self {
        let screen_height = 1080.0;
        let distance = 10.0;
        let focal_length = target_ratio * screen_height * distance / world_size;
        let world_scale = 1.0;
        
        Self { focal_length, distance, world_scale, screen_height }
    }
    
    /// 反算:给定参数,物体在屏幕占多少像素
    fn projected_size(&self, world_size: f32) -> f32 {
        self.focal_length * world_size / self.distance
    }
    
    /// 反算:占屏比例
    fn screen_ratio(&self, world_size: f32) -> f32 {
        self.projected_size(world_size) / self.screen_height
    }
}

fn main() {
    println!("=============================================\n");
    println!(" Day 520 · 求解调试相机参数\n");
    println!("=============================================\n");
    
    // 目标:5 米高的物体占屏幕 30%
    let world_size = 5.0_f32;
    let target_ratio = 0.3_f32;
    
    let cam = CameraParams::solve_focal_length(target_ratio, world_size);
    
    println!("=== 求解参数 ===");
    println!("目标:物体 {:.1}m 占屏 {:.0}%", world_size, target_ratio * 100.0);
    println!("结果:");
    println!("  focal_length: {:.2}", cam.focal_length);
    println!("  distance: {}", cam.distance);
    println!("  screen_height: {}", cam.screen_height);
    
    println!("\n=== 验证 ===");
    let projected = cam.projected_size(world_size);
    let actual_ratio = cam.screen_ratio(world_size);
    println!("projected_size = {:.1} px", projected);
    println!("screen_ratio = {:.2} (目标 {:.2})", actual_ratio, target_ratio);
    assert!((actual_ratio - target_ratio).abs() < 0.001, "公式验证失败");
    println!("✓ 公式正确");
    
    // 不同 FOV
    println!("\n=== FOV 推导 ===");
    let fov = 2.0 * (cam.screen_height / 2.0 / cam.focal_length).atan();
    println!("对应 FOV: {:.1}°", fov.to_degrees());
    
    // 不同 distance 的影响
    println!("\n=== 距离对画面影响 ===");
    for distance in [5.0, 10.0, 20.0, 50.0] {
        let mut c = cam.clone();
        c.distance = distance;
        let size = c.projected_size(world_size);
        let ratio = c.screen_ratio(world_size);
        println!("  distance={:5.1}: projected={:6.1}px, ratio={:.2}", distance, size, ratio);
    }
    
    // 不同 world_size 的影响
    println!("\n=== 物体大小对画面影响 ===");
    for world_size in [1.0, 5.0, 10.0, 50.0] {
        let size = cam.projected_size(world_size);
        let ratio = cam.screen_ratio(world_size);
        println!("  world_size={:5.1}: projected={:6.1}px, ratio={:.2}", world_size, size, ratio);
    }
    
    // Newton's method 示例
    println!("\n=== Newton's method 示例(解 √2)===");
    fn newton_sqrt(target: f32, guess: f32, iterations: usize) -> f32 {
        let mut x = guess;
        for _ in 0..iterations {
            // f(x) = x^2 - target, df = 2x
            let fx = x * x - target;
            let dfx = 2.0 * x;
            x = x - fx / dfx;
        }
        x
    }
    
    let result = newton_sqrt(2.0, 1.0, 10);
    println!("√2 ≈ {:.10} (实际 {:.10})", result, 2.0_f32.sqrt());
}
```

#### 第三人称相机的 collision

HH 的 camera 简单——固定距离。但工业级第三人称相机(Unreal、Unity)有 collision:camera 不能穿墙。如果玩家背靠墙,camera 应该自动拉近,避免穿到墙外。

实现:从玩家发射射线(camera 位置),如果射线撞墙,camera 移到撞墙点。

```rust
fn update_camera_collision(
    camera_pos: Vec3,
    target_pos: Vec3,
    world: &World,
) -> Vec3 {
    let direction = camera_pos - target_pos;
    let distance = direction.length();

    if let Some(hit) = world.raycast(target_pos, direction.normalize(), distance) {
        // 撞墙,camera 移到撞墙点
        target_pos + direction.normalize() * (hit.distance - 0.1)
    } else {
        camera_pos  // 不撞,原位置
    }
}
```

这是《Mario 64》《Zelda: OOT》以来的工业标准。

#### Camera shake(震动)

爆炸 / 受击 / 地震等场景,camera 抖动增加临场感。

实现:camera 位置加 noise offset:
```rust
let shake = Vec3::new(
    rng.gen_range(-1.0..1.0),
    rng.gen_range(-1.0..1.0),
    0.0,
) * shake_intensity;

camera.position += shake;
```

工业级用 Perlin noise(平滑),不是 random(抖动)。

#### Camera script / cinematic

游戏过场动画用 camera script——预定 camera 路径、焦点、FOV 变化。

实现:
- Camera 位置:动画曲线(Bezier)
- Camera 焦点:动画曲线
- FOV:插值

Unreal 的 Matinee、Unity的Timeline 都是这套。

#### 多 camera 系统

复杂游戏有多个 camera:第一人称、第三人称、俯视、车载、电影。切换需要平滑过渡。

实现:每个 camera 是独立 component,游戏状态决定 active camera。切换时用插值(slerp / smoothstep)。

#### Camera 后处理

工业级 camera 还有后处理:运动模糊、镜头畸变、景深、色调映射、SSAO。这些是 fragment shader 工作,但和 camera 参数(FOV、focal length)耦合。

Day 520 只涉及透视投影数学。完整工业 camera 系统是 Day 520 + 上面所有特性的组合。
