
# Day 442 · 让 NSight 跑起来

> NSight 是 NVIDIA 的 GPU profiler,告诉你"每个 draw call 在 GPU 上花了多久、瓶颈在哪里"。Casey 这一天折腾怎么把它和 HH 项目接通。Linux 用户没有 NSight,但有几个对等工具——这一集我们就讲这些。

## 0 · 为什么要有这一天

你写了一段 OpenGL 代码,帧率 30 FPS。**为什么慢?** 在 CPU 上你已经测过——`perf` 显示渲染线程 5ms,物理 1ms,IO 1ms,GPU 提交 1ms——加起来 8ms,远低于 16ms。**那 GPU 呢?** 你的 vertex shader 是不是写得太复杂?fragment shader 是不是采样太多?某个 draw call 是不是触发了深度回读?

CPU 上的 `perf` 看不到这些——它看不到 GPU 内部。GPU profiler 才能看到。

NVIDIA NSight(原名 Nsight Graphics)是 NVIDIA 官方 GPU profiler,功能强大但只支持 NVIDIA GPU + Windows/Linux。Casey 这一天的工作:把 NSight 跑起来,profile HH 的渲染管线,看每个 draw call 的耗时和瓶颈。

Linux 用户没有 NSight(有,但是 NSight Graphics Linux Edition 比 Windows 版本功能少)。但 Linux 有替代品:**Radeon GPU Profiler(AMD)**、**Intel Graphics Performance Analyzer**、**RenderDoc**(厂商中立,开源)、**vkProf** / **apitrace**(GL/Vulkan trace 工具)。

完成这一天后,你能做到:用 RenderDoc 截获你的 OpenGL/Vulkan 程序的一帧,看每个 draw call 的输入输出纹理、shader 源码、状态机。你还能用 `vk.profile` 或 `glxinfo` 看 GPU 利用率,定位瓶颈是 vertex 还是 fragment。

要理解 GPU profiler 为什么必要,你需要先理解 CPU 和 GPU 工作方式的本质差异——这两者之间的"异步鸿沟"是大多数初学者性能 bug 的根源。

CPU 是"指令驱动"的:你写一行代码,它执行一行,你能用 `perf` / `gprof` 直接对应到源码行。但 GPU 是"数据驱动"的:CPU 把命令写到 command buffer,GPU 从中异步取出执行。**你 CPU 上测的时间,基本上和 GPU 实际工作时间无关**。

举例:你 `glDrawArrays` 调用花了 0.001ms。你以为 GPU 也只花了 0.001ms——错。CPU 只是塞了个"画这个 vertex buffer"的命令到队列,GPU 可能要花 5ms 真正执行这个 draw call(取决于 vertex shader 复杂度、纹理采样、像素数)。**这就是为什么必须有 GPU 端 profiler**。

## 2 · 心智模型

### 类比:看工厂流水线

CPU 优化像看工厂的"调度员"——他什么时候发出指令、什么时候空闲。`perf` 这种工具看的就是这个。

GPU 优化像看工厂的"流水线机器"——每台机器处理一件产品要多久,哪台机器是瓶颈,传送带是不是堆积了产品。GPU profiler 看的是这个。

CPU 和 GPU 是异步的——CPU 提交命令到 command buffer,GPU 异步执行。CPU 看到"5ms 提交完",但 GPU 可能还在跑 1 秒前提交的命令。所以"CPU 测的快"不代表"GPU 跑得快"。

### 严谨原理:CPU-GPU 同步与 pipelining

```
时间轴 ─────────────────────────────►
CPU: [frame N]    [frame N+1]   [frame N+2]
GPU:        [frame N]    [frame N+1]   [frame N+2]
```

CPU 始终领先 GPU 一到两帧。这是双缓冲/三缓冲的本质——CPU 写下一帧的 command buffer 时,GPU 还在跑当前帧。

**问题**:CPU 测 "frame N 提交耗时 5ms",但 GPU 跑 frame N 可能 12ms。所以你测 CPU 看到的"快"是错觉。

**测量 GPU 的正确做法**:
- 用 GPU timestamp query(`glQueryCounter` in OpenGL, `vkCmdWriteTimestamp` in Vulkan)记录 GPU 端时间戳
- 在 frame 结束后回读这些 timestamp,得到 GPU 端真实耗时
- 或者用 GPU profiler(NSight / RenderDoc)自动做这些

### RenderDoc 工作原理

RenderDoc 是开源 GPU debugger,功能强大:

1. **截帧**:在程序运行中按 hotkey,RenderDoc 截获一帧的所有 GL/Vulkan/D3D 调用
2. **状态快照**:每个 draw call 的输入纹理、vertex buffer、shader source、uniform 值
3. **回放**:在 RenderDoc UI 里重新跑这一帧,逐步看每个 draw call 的输出
4. **像素归因**:点屏幕上任意像素,看它是哪个 draw call 渲染的,shader 怎么算的

RenderDoc 不直接给"耗时"——它给"状态"。耗时要用 NSight/RGP/vProf。

**RenderDoc 怎么截获 GL/Vulkan 调用?** 这是 Linux 系统编程的好例子。

对 OpenGL,RenderDoc 用 `LD_PRELOAD` 注入自己的库,这个库覆盖了所有 GL 函数(`glDraw*`、`glTexSubImage2D` 等)。每次程序调 GL,实际调的是 RenderDoc 的代理,它记录参数然后转发给真正的 GL driver。

```bash
# RenderDoc 启动程序时,本质是这个:
LD_PRELOAD=/usr/lib/librenderdoc.so ./your_game
```

对 Vulkan,机制更优雅。Vulkan 设计时就考虑了 **layer**——你可以注册一个"中间层",所有 Vulkan 调用先过 layer,再到底层 driver。RenderDoc 自己就是个 Vulkan layer。

```bash
# 看 Vulkan layer
ls /usr/share/vulkan/implicit_layer.d/
# 输出:renderdoc_capture.json 等
```

layer 配置 JSON 告诉 Vulkan loader:"遇到应用程序时,自动加载这个 layer 共享库"。layer 拦截 `vkCmdDraw` 等命令,记录状态。

**Vulkan 的 layer 架构是它相对 OpenGL 的重大工程优势**。OpenGL 的拦截靠 `LD_PRELOAD`(hacky、易碎),Vulkan 的拦截是 API 设计原生支持的——这就是为什么 Vulkan 的工具生态比 OpenGL 健康得多。

### GPU 性能瓶颈分类

GPU 渲染一个 draw call 涉及多个 stage:

```
1. Vertex Fetch      — 顶点数据从显存读
2. Vertex Shader     — 每顶点计算
3. Primitive Assembly — 三角形组装
4. Rasterization     — 三角形转像素
5. Fragment Shader   — 每像素计算
6. Color Blend       — 颜色混合
7. Depth Test        — 深度测试
8. Raster Output     — 写回 framebuffer
```

瓶颈可能在任一 stage:

- **Vertex bound**:模型太复杂,vertex shader 太重
- **Fragment bound**:屏幕分辨率高,fragment shader 太重
- **Memory bandwidth bound**:纹理采样太多,显存带宽打满
- **Compute bound**(compute shader):算法本身计算密集
- **Pipeline stall**:CPU/GPU 不同步,管线空泡

GPU profiler 的核心价值:**告诉你瓶颈在哪一层**。否则你只能猜。

让我把"瓶颈定位"的方法论展开,这是 GPU 性能工程的核心技能。

**第一步:测出"理论 frame budget"**。60 FPS = 16.67ms/帧。144 FPS = 6.94ms/帧。**你的所有 GPU 工作必须在这个时间内完成**。

**第二步:用 GPU timestamp 把帧分段**。在主渲染循环里,每个 pass 前/后插入 timestamp:

```
[shadow map pass]  [geometry pass]  [lighting pass]  [post-process]
2.5ms              4.0ms            6.0ms            2.0ms
                                                              总: 14.5ms
```

立刻看出 lighting pass 占了 41%——优先优化它。

**第三步:对最慢的 pass,定位它内部瓶颈**。每个 pass 内部可能瓶颈在:

- **Vertex processing**:模型顶点数 × vertex shader 复杂度。诊断:把 vertex shader 替换成空函数,如果 pass 时间减半,说明 vertex bound。
- **Rasterization**:三角形面积 × overdraw。诊断:减小 render target 一半,如果时间减半,说明 raster bound。
- **Fragment shading**:像素数 × fragment shader 复杂度。诊断:把 fragment shader 替换成 `outcolor = vec4(1)`,如果时间大幅降,说明 fragment bound。
- **Texture sampling**:纹理采样数 × 各向异性过滤代价。诊断:把所有 `texture()` 调用替换成常量,看时间变化。
- **Memory bandwidth**:总字节读写量 ÷ GPU 带宽。诊断:计算理论字节数对比实测。

**第四步:优化策略匹配瓶颈**。

- Vertex bound → 用 LOD 减少顶点 / 优化 vertex shader 算法
- Fragment bound → 用 early-z 剔除(z-prepass)/ 简化 shader / 降分辨率
- Bandwidth bound → 压缩纹理(BCn/ASTC)/ 减少 render target 数 / 用更小像素格式
- Compute bound → 优化算法(常量时间 vs 线性)

**这套方法论叫"瓶颈归类(bottleneck isolation)"**。核心思想:**不要猜,要 A/B 测**。改一处,测量变化,推出瓶颈层。

GPU profiler(NSight、RGP)的"auto-bottleneck"功能本质就是这套——它内部做这些 A/B 测量,自动报告"这个 pass 是 fragment bound"。但理解原理让你能自己手工诊断,不依赖工具。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏 GPU 优化的工业流程:

1. **基线测量**:先 profile,知道哪个 pass 最慢
2. **80/20 法则**:最慢的 20% 代码占 80% 时间,集中优化它们
3. **A/B 对比**:改一处,重新 profile,确认提升
4. **回归测试**:优化后画质不能掉(自动化截图对比)

常见 GPU 优化:

- **LOD**(细节层次):远处物体用低面数模型
- **Occlusion culling**:被遮挡的不渲染
- **Instancing**:同模型多次渲染用一个 draw call
- **Texture atlas**:多个小纹理合并,减少切换
- **GPU driven rendering**:用 compute shader 在 GPU 端做剔除/排序,CPU 几乎不参与

**坑**:GPU 优化"反向"——CPU 优化追求"少做事",GPU 优化追求"并行做更多事"(warp occupancy)。

### 3.2 · 图形学视角

GPU 架构基础:

**SIMT(Single Instruction, Multiple Threads)**:GPU 一次执行同一指令,32 个线程一组(NVIDIA 叫 warp,AMD 叫 wavefront)。如果同一 warp 内的线程走不同分支(if-else),GPU 要串行执行两路,效率减半。这就是 shader 里 `if` 重的代价。

**寄存器压力**:每个线程用 N 个寄存器。SM(streaming multiprocessor)总寄存器数固定(如 65536)。如果每线程用 64 寄存器,SM 同时跑 1024 线程;如果每线程用 128,只能跑 512。寄存器用多了 occupancy 降,可能变慢(也可能变快,因为寄存器多于 cache 命中)。

让我把 SIMT 的代价讲得更具体些。假设你写 fragment shader:

```glsl
if (uv.x > 0.5) {
    color = expensive_brdf(uv, normal);
} else {
    color = vec3(0.5);
}
```

直觉上"一半像素走 cheap 分支,应该省时间"——错。GPU SIMT 模型下,**同一 warp 的 32 个线程必须同步执行**。如果 32 个像素有的走 then 分支,有的走 else,GPU 先执行 then 分支(else 分支的线程"休眠"),再执行 else 分支(then 分支的线程"休眠")。**总时间是两个分支之和,不是较短的分支**。

例外:**统一分支(uniform branch)**——如果整个 warp 都走同一分支,GPU 优化掉另一分支。这种情况下 `if` 是免费的。常见于:用 uniform 决定材质类型(`if (material_type == METAL) ...`)。

**实战**:shader 里**避免数据相关的分支**,改用 `mix` / `step` / `lerp` 等数学等价:

```glsl
// 差:有分支
vec3 col;
if (uv.x > 0.5) col = a; else col = b;

// 好:无分支
vec3 col = mix(b, a, step(0.5, uv.x));
// step(0.5, uv.x) 返回 0 或 1,mix 在 a/b 间线性插值
```

`mix + step` 在 SIMT 下完全并行,没有 warp 分歧。这是 GPU 编程的关键 idioms。

GPU profiler(NSight、RGP)直接报告 **warp 分歧率(divergence rate)**。如果发现热点 shader 分歧率高,重写消除分支通常立刻提升 30-50%。

**Memory hierarchy**:
- 寄存器(每线程,~1 cycle)
- Shared memory / L1(每 SM,~30 cycles)
- L2 cache(全 GPU,~200 cycles)
- VRAM(全 GPU,~500 cycles)
- PCIe 主存(CPU 那边,~1000 cycles)

shader 优化核心是让数据留在 hierarchy 高层。

**GPU profiler 给的指标**:
- SM 占用率(occupancy)
- 寄存器使用
- 内存带宽利用率
- cache hit rate
- 每阶段 cycle 数

**Linux 上的 GPU 驱动模型**。理解 Linux GPU 工具链,先要理解驱动分层:

```
用户程序 (OpenGL/Vulkan 应用)
       ↓
Mesa / NVIDIA proprietary userspace
       ↓
DRM (Direct Rendering Manager) — Linux 内核子系统
       ↓
KMS (Kernel Mode Setting) — 显示输出
       ↓
GPU 硬件
```

**Mesa** 是开源图形栈,提供 OpenGL / Vulkan 实现,适配 AMD / Intel / 部分 NVIDIA。NVIDIA 也有私有驱动(`nvidia` 模块),不基于 Mesa。

```bash
# 看你的图形栈

# Mesa Intel: "OpenGL renderer string: Mesa Intel(R) ..."
# Mesa AMD:   "OpenGL renderer string: AMD Radeon ..."
# NVIDIA:     "OpenGL renderer string: NVIDIA GeForce ..."

# 看内核驱动
lspci -k | grep -A 3 VGA
# 输出 "Kernel driver in use: i915" / "amdgpu" / "nvidia" / "nouveau"
```

**调试模式**。Mesa 支持很多环境变量帮助调试:

```bash
# 启用 Mesa debug 输出
MESA_DEBUG=1 ./your_app

# 强制软件渲染(排除 GPU 驱动问题)
LIBGL_ALWAYS_SOFTWARE=1 ./your_app

# 看 shader 编译错误
MESA_SHADER_SOURCE=1 ./your_app

# 启用 Vulkan validation layer(开发时强烈推荐)
VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation ./your_app
```

**Vulkan validation layer** 是开发必备——它检查所有 Vulkan 误用(违反 spec 的代码),不开启的话很多 bug 默默出错。生产构建关掉,开发必开。

**apitrace**:

### 3.4 · Rust 生态视角

Rust GPU 编程生态:

**A. OpenGL(Rust binding)**:
- `gl`:glGen* 等函数绑定
- `glow`:跨平台 GL wrapper
- `glium`:高层抽象(已停止维护,教学仍好)

**B. Vulkan(Rust binding)**:
- `vulkano`:安全封装
- `ash`:底层 unsafe 绑定(类似 Vulkan SDK C API)
- `wgpu`:跨平台抽象(Vulkan/Metal/DX12/WebGPU)

**C. GPU timestamp query in Rust(用 glow)**:

```rust
use glow::*;

let gl = unsafe { Context::from_loader_function(|s| window.get_proc_address(s) as *const _) };

// 创建 query
let query = unsafe { gl.create_query() }.unwrap();

// 在 frame 开始记录
unsafe { gl.query_counter(query, TIME_ELAPSED); }

// 渲染...

// 在 frame 结束记录
unsafe { gl.query_counter(query, TIME_ELAPSED); }

// 下一帧开始时读上一帧结果(异步)
let time_ns = unsafe { gl.get_query_parameter_u64(query, QUERY_RESULT) };
println!("GPU frame time: {} ms", time_ns as f32 / 1e6);
```

每行解释:
- `Context::from_loader_function` — glow 用一个函数指针获取 GL 函数(平台相关,在 Linux 是 glXGetProcAddress)。
- `create_query` — 生成 GL query object,用于 GPU 端测量。
- `query_counter(query, TIME_ELAPSED)` — 在 GPU 命令流里插入一个时间戳记录。
- 下一帧再读结果 — GPU 是异步的,结果要等几帧后才可用。

**D. wgpu 的 GPU timing**:

```rust
use wgpu::*;

let mut encoder = device.create_command_encoder(&CommandEncoderDescriptor::default());
encoder.write_timestamp(&timestamp_writer, 0);  // pass 开始
// ... render passes ...
encoder.write_timestamp(&timestamp_writer, 1);  // pass 结束

// 在下一帧解析时间戳
timestamp_resolve_pass.copy_timestamp_results(&buffer);
```

**真实 crate**:
- `renderdoc-sys`:RenderDoc API 的 Rust 绑定,可以在代码里控制截帧
- `profiling`:通用 profiler 抽象,封装 GPU/CPU timing

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 CPU 测量 `glDrawArrays` 调用耗时是错的?正确做法是什么?

**参考解答**:`glDrawArrays` 在 CPU 端几乎瞬间返回——它只是把"画这个 vertex buffer"命令塞到 command buffer,GPU 异步执行。CPU 测的是"塞命令"时间,不是 GPU 真实执行时间。

**正确做法**:
1. 用 GPU timestamp query 在 `glDrawArrays` 前后插入 timestamp
2. 等几帧(GPU 异步)
3. 用 `glGetQueryObjectui64v` 读 timestamp 差,这才是 GPU 真实耗时
4. 或用 NSight / RenderDoc 自动测

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

一个最小的 OpenGL + GPU timestamp query 程序(用 glow + sdl2):

```rust
// Cargo.toml
// [dependencies]
// glow = "0.13"
// sdl2 = "0.36"
// 
// (此代码不直接跑,只展示结构)

use glow::*;

fn main() {
    let sdl = sdl2::init().unwrap();
    let video = sdl.video().unwrap();
    let window = video.window("GPU Profile Demo", 800, 600)
        .opengl()
        .build()
        .unwrap();
    let gl_ctx = window.gl_create_context().unwrap();

    let gl = unsafe {
        Context::from_loader_function(|s| video.gl_get_proc_address(s) as *const _)
    };

    // 创建 timestamp queries
    let start_query = unsafe { gl.create_query() }.unwrap();
    let end_query = unsafe { gl.create_query() }.unwrap();

    let mut frame = 0;
    let mut event_pump = sdl.event_pump().unwrap();
    'running: loop {
        for event in event_pump.poll_iter() {
            match event {
                sdl2::event::Event::Quit {..} => break 'running,
                _ => {}
            }
        }

        unsafe {
            // 插入 GPU 端时间戳
            gl.query_counter(start_query, TIME_ELAPSED);
            // ... 渲染 ...
            gl.clear_color(0.1, 0.2, 0.3, 1.0);
            gl.clear(COLOR_BUFFER_BIT);
            gl.query_counter(end_query, TIME_ELAPSED);
        }

        window.gl_swap_window();

        // 读上一帧的结果(GPU 异步,要等几帧才有)
        if frame > 3 {
            unsafe {
                let start_ns = gl.get_query_parameter_u64(start_query, QUERY_RESULT);
                let end_ns = gl.get_query_parameter_u64(end_query, QUERY_RESULT);
                let elapsed_ms = (end_ns - start_ns) as f32 / 1e6;
                if frame % 60 == 0 {
                    println!("Frame {}: GPU time = {:.3} ms", frame, elapsed_ms);
                }
            }
        }
        frame += 1;
    }
}
```

每行解释:
- `Context::from_loader_function` — glow 用 SDL2 的 `gl_get_proc_address` 加载 GL 函数指针。
- `create_query` — 生成 GPU 端 query 对象。
- `query_counter(query, TIME_ELAPSED)` — 在 GPU 命令流插入时间戳。
- `frame > 3` — 等几帧才读结果,因为 GPU 异步。第一帧的 query 还没执行完。
- `get_query_parameter_u64` — 读 query 的 64 位结果。
- 输出 GPU 端真实耗时,这是 NSight 给你的同样信息。

### Arch Linux 工具链

```bash
# 装图形栈工具
sudo pacman -S renderdoc apitrace mesa-utils

# 看 GPU
lspci -k | grep -A 3 VGA
# 应该看到 GPU + 正在使用的内核驱动

# 看 OpenGL
glxinfo | grep -E "OpenGL (vendor|renderer|version)"
# NVIDIA: "OpenGL renderer string: NVIDIA GeForce..."
# AMD: "OpenGL renderer string: AMD Radeon..."
# Intel: "OpenGL renderer string: Mesa Intel(R)..."

# 实时监控(NVIDIA)
nvidia-smi -l 1
# 每 1 秒刷新

# 用 apitrace 截获 GL 程序
apitrace trace /tmp/mygl
# 生成 mygl.trace 文件
qapitrace mygl.trace
# 在 GUI 里看每个 GL 调用

# RenderDoc 启动
renderdoccmd
# GUI 启动,配置可执行文件路径

# 看 Vulkan layers( RenderDoc 注入靠 layer)
ls /usr/share/vulkan/implicit_layer.d/
vulkaninfo --summary
```

**Troubleshooting**:
- RenderDoc 看不到你的程序 → 用 `LD_PRELOAD=librenderdoc.so ./your_program` 强制注入
- NSight Linux 装不上 → 装最新的 NVIDIA 驱动 + 关 Secure Boot
- GPU timestamp 不工作 → 检查 `glGetQueryiv(TIMESTAMP)` 是否返回 nonzero
