# Day 554 · 减少 GPU 内存占用

> Voxel light probe 占内存——每个 voxel 存 RGBA + occupied = 5 字节,1km³ × 1m voxel = 5 GB。Day 554 Casey 用几个技巧**砍掉一半** GPU 内存:稀疏存储、低精度、布局优化。

## 0 · 为什么要有这一天

让我们从一个真实的内存爆炸说起。

你把 voxel light probe 系统搭起来——每个 voxel 存 RGBA + occupied flag,大世界 1km³ × 1m voxel 精度。一算:1 km³ = 10^9 m³,每个 m³ 一个 voxel,10^9 voxel。每个 voxel RGBA32F = 16 字节,occupied u8 = 1 字节,共 17 字节。10^9 × 17 = **17 GB GPU 显存**。

NV RTX 3060 只有 12 GB 显存,GTX 1060 只有 6 GB,Steam Deck 共享内存 4 GB。你的游戏**根本跑不起来**——`vkAllocateMemory` 直接返回 `VK_ERROR_OUT_OF_DEVICE_MEMORY`,游戏黑屏 crash。

这是 industrial voxel GI(全局光照)的典型困境:**理论上的物理精度远超硬件能力**。1m voxel 看起来粗,但 1km³ 的世界就这么大。要想 voxel GI 实用,必须从**几个 GB** 压到**几百 MB**——10-100 倍压缩。

工业界的内存优化有四个层次,从粗到细:

**第一层,数据稀疏性(sparse storage)**。场景大部分是空的——开放空间没几何体,光照值低(接近黑色)。这些 voxel 不需要存储,用一个**默认值**(黑色)代替。Sparse 存储只存非空区域。在大世界游戏(GTA、Cyberpunk)里,玩家周围 1 km² 有内容,但 100 km² 的世界大部分是空——sparse 存储**省 100 倍**。

**第二层,精度量化(quantization)**。光照值范围 0..1,人眼对亮度对数敏感(分辨率随亮度递减)。用 u8 (0..255) 存完全够,精度损失视觉不可见。RGBA32F (16 字节) → RGBA8 (4 字节),**省 4 倍**。

**第三层,bit-packed 标志位**。occupied 标志只有 true/false,不需要 u8。用 bit array(1 bit/voxel),**省 8 倍**。

**第四层,运行时分块(streaming)**。整个 voxel grid 不全加载,只加载玩家附近的 chunk。远处的 chunk 临时从磁盘 stream 进来。**省 N 倍**(N = 玩家可视距离 vs 世界大小)。Day 572 会做这个。

四层叠加:**sparse × RGBA8 × bit array × streaming = 10 × 4 × 8 × N = 巨大压缩**。Casey 这一天主要做前三层,把 17 GB 砍到 ~500 MB。

完成这一天之后,你具备:

- **理解内存优化的四个层次**:sparse、quantization、bit-pack、streaming
- **能用 sparse storage 大幅减少内存**:hash map + chunk 分块,只存非空
- **用 bit array 压缩 bool 标志**:8 倍节省,cache 友好
- **量化精度损失**:知道什么时候 u8 够、什么时候需要 f16 / RGBE
- **看懂 GPU 内存的真实代价**:分配 / 访问 / 拷贝,VRAM vs PCIe vs RAM 带宽层级

## 1 · Casey 今天做了什么

Casey 这天的优化没有单一的"惊艳"技巧,而是几个朴素但累积的改进。让我把每个步骤拆开,你会看到每步对应一个具体浪费。

**第一步,改光照存储精度**。之前的代码用 RGBA32F(16 字节/voxel)——每 channel 32 位浮点。这对应"理论上最高精度",但光照值范围 0..1(归一化),256 级精度(0..255)完全够——人眼对亮度对数敏感,256 级在屏幕上看不出量化误差。Casey 改成 RGBA8(4 字节/voxel),**省 4 倍内存**。

这一步的工程难点不是改格式,而是**确认精度损失视觉不可见**。Casey 在视频里跑两个 build——RGBA32F 和 RGBA8——并排截图对比,**肉眼找不出差异**。这是"量化可行"的实证。

**第二步,分离 occupied 标志和光照值**。之前的代码把"是否占据"(occupied)塞进 RGBA 的 alpha channel——a=255 占据,a=0 空。这样 alpha 不能用来存真正的光照 transparency。Casey 把 occupied 单独抽出,用 bit array(1 bit/voxel),光照 alpha 自由。

这一步的设计动机是**正交性**(orthogonality)——一个数据字段应该只表达一个含义。alpha 既是 transparency 又是 occupied,是反模式——改一个含义会无意影响另一个。Casey 把它们分离,这是软件工程的基本纪律。

**第三步,实现 sparse storage**。之前的代码用 dense Vec<Voxel>——所有 voxel 都分配,即便大部分是空。Casey 改成 HashMap<ChunkCoord, Chunk>,只存非空 chunk。开放空间(没几何体的地方)的 chunk 直接不存,访问时返回默认值。

这一步的工程挑战是**chunk 边界处理**——访问 voxel 时要先找它的 chunk,再在 chunk 内找局部坐标。代码用 `div_euclid` 算 chunk 坐标,`rem_euclid` 算局部坐标。`euclid` 后缀确保负数行为正确(否则 -1 / 16 在 Rust 里 truncate toward zero,行为可能错)。

视频里他展示内存从 5 GB 砍到 500 MB——**10 倍优化**。这 10 倍来自:sparse(假设 50% 空)= 2 倍,RGBA8 vs RGBA32F = 4 倍,bit array vs u8 = 1.25 倍(因为 occupied 只占 voxel 一小部分),叠加 ~10 倍。

## 2 · 心智模型

### 2.1 类比:行李打包

我打个比方。你要去旅行 1 周,行李箱只有 30L。怎么打包?

**朴素打包**(高精度 + 稠密):每件衣服用纸盒装(过度包装),每双袜子单独袋(冗余),不带不穿的衣服也带上(稀疏性浪费)。30L 装 5 件衣服。

**优化打包**(稀疏 + 低精度):
- 衣服**卷起来**(量化:用紧凑格式代替松散格式)
- 袜子**塞鞋里**(空间复用:bit-packed 标志)
- **不带不穿的**(稀疏:只装非空)
- 30L 装 20 件

Voxel grid 的优化完全对应:

| 打包策略 | Voxel grid 对应 | 节省倍数 |
|---|---|---|
| 纸盒装 → 卷起来 | RGBA32F → RGBA8 | 4x |
| 袜子塞鞋里 | u8 occupied → 1 bit occupied | 8x |
| 不带不穿的 | Dense Vec → Sparse HashMap | Nx(N = 空间稀疏度) |

类比的关键洞察:**优化是分层叠加的**。每一层单独看省 4-10 倍,多层叠加可达几十倍。这是 industrial voxel GI 能跑的基础——不是单个技巧,而是 stack of optimizations。

### 2.2 量化精度分析:从 f32 到 u8

RGBA32F(16 字节/voxel) vs RGBA8(4 字节/voxel),精度损失多少?让我严格分析。

**RGBA32F**:每 channel 32 位 IEEE 754 浮点。1 sign bit + 8 exponent bit + 23 mantissa bit。归一化范围 0..1 时,精度 ~7 位有效数字(2^-23 ≈ 1.2e-7)。

**RGBA8**:每 channel 8 位无符号整数。范围 0..255,精度 1/255 ≈ 0.004。

精度损失:0.004 vs 1.2e-7,**损失 3 万倍精度**。听起来很糟,但实际不可见。为什么?

**人眼亮度感知是对数的**(Weber-Fechner law)。人眼能分辨的亮度差不是绝对值,而是比例——10% 的差异可见,1% 的差异不可见。256 级 (RGBA8) 在亮度 0.5 处的精度是 0.5/256 ≈ 0.002,即 0.4%——**人眼分辨不出**。

更深一层,**显示设备的物理限制**。普通 sRGB 显示器对比度 1000:1,色域 8 bit/channel——显示器本身只能显示 RGBA8 精度。RGBA32F 的"额外精度"在显示器上看不到。

所以 RGBA8 是"够用"的精度,RGBA32F 是"过度"。两者视觉相同,内存差 4 倍。

**HDR 场景的特例**:如果光照值可以 > 1(HDR,high dynamic range),RGBA8 不够——阳光直接照射的 voxel 光照可能 100,普通 RGBA8 溢出。这种情况用:
- **RGBE(共享指数)**:RGB 各 8 bit,E(exponent)8 bit,实际数值 = RGB × 2^E。HDR 但紧凑,8 字节。
- **R11G11B10F**:R 11 bit float,G 11 bit,B 10 bit,no alpha。4 字节,HDR 但精度低于 RGBA32F。
- **RGBA16F**:每 channel 16 bit half float。8 字节,HDR 中等精度。

Casey 这天的 voxel 光照用 LDR(低动态范围,值 0..1),RGBA8 够。

```rust
// 内存对比(1km³ × 1m voxel = 10^9 voxel)
struct VoxelRGBA32F { r: f32, g: f32, b: f32, a: f32 }  // 16 字节 → 16 GB
struct VoxelRGBA8 { r: u8, g: u8, b: u8, a: u8 }        // 4 字节 → 4 GB
// Sparse(假设 50% 空)→ 2 GB
```

### 2.3 Sparse storage:大世界的基础

为什么 sparse storage 这么重要?让我从大世界游戏的需求说起。

**Dense storage 的瓶颈**:游戏世界 100km × 100km × 100m = 10^6 × 10^6 × 10^3 m³ = 10^15 m³。1m voxel,10^15 voxel × 4 字节 = **4 PB**。即便用最高压缩,装不下任何 GPU。

**Sparse storage 的洞察**:**实际有内容的区域 << 世界大小**。开放世界游戏里,玩家附近 1 km² 有详细 voxel GI,远处的山就是远景天空盒,没 voxel 数据。100 km × 100 km 世界,只有玩家附近 1 km × 1 km 有内容——sparse 系数 10^4。10^15 / 10^4 = 10^11 voxel × 4 字节 = 400 GB——仍多,但配合 streaming(只加载玩家附近 chunk)→ 几百 MB。

工业实现:**chunk-based sparse storage**。把世界切成 chunk(16×16×16 voxel),每个 chunk 是基本单位。HashMap<ChunkCoord, Chunk> 只存非空 chunk。访问 voxel 时:
1. 算 voxel 属于哪个 chunk:`chunk_coord = voxel_coord.div_euclid(16)`
2. 在 chunk 内的局部坐标:`local = voxel_coord.rem_euclid(16)`
3. 查 HashMap——找到则返回 voxel 数据,没找到返回默认值(空 voxel)

```rust
struct SparseVoxelGrid {
    chunks: HashMap<ChunkCoord, Chunk>,
}

#[derive(PartialEq, Eq, Hash)]
struct ChunkCoord { x: i64, y: i64, z: i64 }

struct Chunk {
    data: Box<[VoxelRGBA8; 16*16*16]>,  // 16 KB
    occupied: Box<[u64; 16*16*16/64]>,   // 512 bytes(每 voxel 1 bit)
}

impl SparseVoxelGrid {
    fn get(&self, x: i64, y: i64, z: i64) -> VoxelRGBA8 {
        let cx = x.div_euclid(16);  // div_euclid 正确处理负数
        let cy = y.div_euclid(16);
        let cz = z.div_euclid(16);
        if let Some(chunk) = self.chunks.get(&ChunkCoord { x: cx, y: cy, z: cz }) {
            let lx = x.rem_euclid(16) as usize;  // rem_euclid 同理
            let ly = y.rem_euclid(16) as usize;
            let lz = z.rem_euclid(16) as usize;
            chunk.data[lz * 16 * 16 + ly * 16 + lx]
        } else {
            VoxelRGBA8::default()  // 默认空 voxel
        }
    }
}
```

为什么用 `div_euclid` 而不是 `/`?Rust 的 `/` 对负数 truncate toward zero——`-1 / 16 = 0`(不是 -1),`-1 % 16 = -1`(不是 15)。这会让 chunk 边界处理错乱。`div_euclid` / `rem_euclid` 用 floor division——`-1.div_euclid(16) = -1`,`-1.rem_euclid(16) = 15`。正确。

### 2.4 Occupied bit array:8 倍压缩 + cache 友好

之前 occupied 用 u8 array(每 voxel 1 字节),改成 bit array(每 voxel 1 bit),省 8 倍。但 bit array 还有另一个隐含优势:**cache 友好**。

CPU cache line 64 字节。u8 array 一次 cache line 取 64 voxel,bit array 一次取 512 voxel(64 byte × 8 bit/byte)。遍历 occupied 时,**cache miss 率减少 8 倍**——这比内存节省更重要。

实现:

```rust
struct OccupiedBits {
    bits: Vec<u64>,  // 每 u64 存 64 voxel 的 occupied
}

impl OccupiedBits {
    fn get(&self, idx: usize) -> bool {
        let word = idx / 64;       // 哪个 u64
        let bit = idx % 64;        // u64 内哪一位
        (self.bits[word] >> bit) & 1 == 1
    }
    fn set(&mut self, idx: usize, val: bool) {
        let word = idx / 64;
        let bit = idx % 64;
        if val {
            self.bits[word] |= 1u64 << bit;   // 置 1
        } else {
            self.bits[word] &= !(1u64 << bit); // 清 0
        }
    }
}
```

bit 操作的核心是 `1u64 << bit`——把 1 移到正确位置,然后用 `|=` 置位或 `&=` 清位。`!` 是按位取反,把目标 bit 变 0 其他变 1,再 `&=` 就清零目标 bit。

16³ chunk = 4096 voxel = 64 个 u64 = 512 字节。如果用 u8 array = 4 KB。**8 倍节省**。

bit array 的另一个优势:**SIMD 友好**。GPU shader 可以一条指令 mask 64 个 voxel,极大加速"找所有 occupied voxel"类操作。

### 2.5 GPU 内存层级:为什么省内存也省时间

GPU 内存不是单一存储——有层级。理解这个层级,你会看到"省内存"也意味着"省时间"。

```
GPU register file      (per-SM, ~256 KB)    带宽 ~10 TB/s
GPU L1 cache           (per-SM, ~64 KB)     带宽 ~5 TB/s
GPU L2 cache           (shared, ~6 MB)      带宽 ~2 TB/s
VRAM(显存)            (3-24 GB)            带宽 ~700 GB/s
PCIe(系统 RAM ↔ GPU)  (~32 GB/s)           带宽 ~32 GB/s
```

层级从上到下:**容量递增,带宽递减,延迟递增**。

Voxel 数据存在 VRAM,shader 通过 L2 / L1 cache 访问。如果 voxel grid 大,L2 cache 容不下,shader 访问 voxel 要从 VRAM 取——**慢**。如果 voxel grid 小到 L2 cache 容下,shader 全 L2 命中——**快**。

L2 cache ~6 MB,Casey 砍到 500 MB voxel 数据后,**仍远超 L2**,但**省下来的内存可以放其他热数据**(mesh、texture、material)。整体 cache 命中率提升,帧率提升。

这就是为什么"省内存"在 GPU 编程里有双重价值——**既扩大 GPU 能容纳的场景,又提升 cache 命中**。

## 3 · 四域深入

### 3.1 · 游戏编程视角

工业游戏的内存优化散布在所有子系统。让我把每个子系统的典型优化列出来,你会看到 sparse + quantization 是普遍模式。

**Texture compression(纹理压缩)**。BCn / DXT / ASTC 格式,4-6 倍压缩,几乎不可见质量损失。每张 4K texture 从 64 MB 压到 11 MB。所有现代 GPU 硬件解压——shader 采样时硬件 block decode。Unreal 和 Unity 默认所有 texture 用 BCn。

**Mesh compression(网格压缩)**。顶点位置量化到 i16(每分量 16 bit 有符号整数,精度 mm 级),UV 量化到 u16 unorm,normal 量化到 octahedral encoding(2 个 f16 编码 3D 向量)。mesh 顶点从 32 字节压到 16 字节。Id Software 在 Quake 时代就 pioneered 这类技术。

**Animation compression(动画压缩)**。每骨骼压缩 quaternion——quantize 到 quaternion 3 个分量(第 4 个用 quaternion identity 重建),每分量 16 bit。60 fps 动画 × 几百骨骼 × 几百帧,压缩后能装下。Unreal 用这种,称为 "Anim Quantization"。

**Sparse storage for virtual texturing(虚拟纹理的稀疏存储)**。Id Tech 5 的 Megatexture——每个像素独立 texture,但只有玩家附近的高分辨率 page 实际加载。远处的 page 用低 LOD 版本。这是 sparse + streaming 的结合,让"理论上无限大 texture"成为可能。

**Voxel GI 的 sparse octree**。Unreal Lumen 用 sparse voxel octree——大块空区域用一个 octree 节点表示(不存细 voxel),有内容的区域才展开 octree。Card capture(在场景中放虚拟相机)在 sparse voxel 上 capture 光照,内存 < 1 GB(GTA 5 的 lightmap 是几 GB baked texture)。

Casey 这天的优化是这条 lineage 的一部分——sparse + low precision,基本工具组合。

### 3.2 · 图形学视角

GPU 内存层级和带宽是 GPU 编程的核心约束。让我把层级详细列出来,你会理解为什么"省内存"也"省时间"。

```
GPU register file       (per-SM, ~256 KB)    带宽 ~10 TB/s    延迟 1 cycle
GPU L1 cache / shared   (per-SM, ~64 KB)     带宽 ~5 TB/s     延迟 30 cycle
GPU L2 cache            (shared, ~6 MB)      带宽 ~2 TB/s     延迟 200 cycle
VRAM(显存)             (3-24 GB)            带宽 ~700 GB/s   延迟 400 cycle
PCIe(系统 RAM ↔ GPU)   (~32 GB/s)           带宽 ~32 GB/s    延迟 1000+ cycle
```

**关键洞察**:从 register 到 VRAM,带宽递减、延迟递增。**数据越大,越可能从慢层级取**。Voxel grid 500 MB 远超 L2 cache(6 MB),shader 每次 sample 都要 VRAM 访问——延迟 400 cycle。如果 voxel grid 5 MB(通过 sparse + low precision),全在 L2 cache,sample 延迟 200 cycle——**两倍快**。

这就是为什么"省内存"有双重价值——既扩大场景,又提升 cache 命中。

GPU 内存优化的工业标准:
- **Bindless + sparse descriptor heap**:几百万 texture descriptor,GPU 通过 index 访问。无需每帧 bind。
- **Sparse texture(`VK_KHR_sparse_memory`)**:大 texture 部分加载,虚拟内存式管理。DirectX 等价是 **Tiled Resources**。
- **Memory budget API(`VK_EXT_memory_budget`)**:GPU 报告自己有多少 free memory,应用根据 budget 调整 LOD。
- **Re-bar / Above 4G decoding**:让 CPU 看到 GPU 全部 VRAM(否则只能看 256 MB),加速 PCIe 传输。

Casey 这天的优化是 software-level sparse——OS / driver 不参与,纯 Rust 数据结构。后续切到 Vulkan 可以用 GPU-level sparse texture,进一步优化。

### 3.3 · Linux 系统编程视角

稀疏存储和量化是 OS 层的核心技术。Linux kernel 大量用,概念可以迁移。

**Sparse files(稀疏文件)**:`truncate -s 1T bigfile` 创建 1TB 文件,但只占实际写的扇区。中间没写的部分,ext4 / XFS / Btrfs 都支持 sparse——访问时返回零。文件系统内部用 extent tree(类似 sparse voxel octree),只存有数据的 extent。

```bash
truncate -s 1T bigfile
ls -lh bigfile       # 显示 1T
du -h bigfile        # 显示 0(实际占用)
```

**Page table(页表)**:Linux 用 4 级页表(PML4 → PDPT → PD → PT),只映射用到的 page。一个进程虚拟地址空间 128 TB,但物理内存只占实际写的 page——sparse。Huge pages(2 MB)进一步压缩 page table——同 1 GB 内存,4 KB page 要 256 K 个 PTE,2 MB page 只要 512 个。

**Memory-mapped files**:`mmap` 让大文件"虚拟"加载——只有访问的 page 实际从磁盘读。读取 100 GB 文件的 1 KB,只占 4 KB 物理 RAM(1 page)。

```c
void* addr = mmap(NULL, file_size, PROT_READ, MAP_SHARED, fd, 0);
// 访问 addr[0..1024] 触发 1 page fault,只读 4 KB
```

**`madvise` / `fallocate`** 是显式稀疏控制的接口:
- `madvise(MADV_DONTNEED)`:告诉内核"这段内存我不用了,可以丢弃 page"(后续访问触发 page fault 重读)
- `fallocate(FALLOC_FL_PUNCH_HOLE)`:在文件里挖洞,释放对应 block

Casey 的 sparse voxel grid 是 software-level sparse——Rust HashMap 控制。在 GPU / OS 层,sparse 是 native concept。

### 3.4 · Rust 生态视角

Rust 表达 sparse storage 和 bit array 有几个生态 crate。

**`bitvec`**:工业级 bit array 实现。安全 + 高效,有 `BitVec` / `BitSlice` / `BitArray` 几个类型。

```rust
use bitvec::prelude::*;

let mut bits: BitVec = BitVec::new();
bits.resize(4096, false);
bits.set(100, true);
println!("{}", bits.get(100).unwrap());  // true

// 批量操作:count_ones
let n_ones = bits.count_ones();
```

`bitvec` 还支持 `BitBox`(owned)、`BitSlice`(borrowed)、各种 bit order(LSB first vs MSB first)、各种 address bit storage(u8 / u16 / u32 / u64)。

**`hashbrown`**:Rust std HashMap 的底层 crate(从 1.36 开始 std 用 hashbrown)。比旧 SipHash 实现快 2-3 倍。直接用 `hashbrown::HashMap` 比 std 略快。

```rust
use hashbrown::HashMap;
let mut m: HashMap<i32, String> = HashMap::new();
m.insert(1, "hello".into());
```

**`ahash`**:更快的 hash function,专门为 in-memory HashMap 优化(不防 HashDoS 攻击)。比 SipHash 快 10 倍。

```rust
use ahash::AHasher;
use std::collections::HashMap;
let mut m: HashMap<i32, String, AHasher> = HashMap::default();
```

**`smallvec`**:小型 Vec,inline 存 N 个元素(类似 SmallVector<LLVM>)。chunk 内 voxel 列表可能空,用 SmallVec<[Voxel; 16]> 避免 heap alloc。

**`rkyv` / `capnp`**:zero-copy 序列化。Voxel 数据存盘 / 读盘时,zero-copy 比 serde 快几个数量级。

这些 crate 都是 industrial voxel engine 的基础。Casey 的 HH 用手写实现是为了教学,production 用 crate 更快更安全。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 occupied 用 1 bit/voxel 而不是 u8/voxel?节省的 8 倍有意义吗?

**参考解答**:每 voxel 节省 7 bit,看起来小,但 10^9 voxel 时:7 bit * 10^9 = 875 MB。8 倍节省 = 省 875 MB GPU 内存,可以多放几张纹理。Bit array 还有一个隐含优势:cache 友好——遍历 occupied 时,64 voxel/word,cache line 一次取 512 voxel,u8 array 一次只取 64 voxel。8 倍 cache 效率。

### Lv2 · 动手实践

**题**:实现一个 sparse voxel grid,测试内存占用。

要求:
- Dense 版:Vec<Voxel>,每个 voxel 4 字节
- Sparse 版:HashMap<ChunkCoord, Chunk>
- 创建 16³ chunk,内容只有 1 个 voxel 非空
- 对比内存占用

**参考解答**:

```rust
use std::collections::HashMap;
use std::mem::size_of_val;

#[derive(Clone, Copy, Default)]
struct Voxel { r: u8, g: u8, b: u8, a: u8 }

// Dense
struct DenseGrid {
    data: Vec<Voxel>,
    dim: usize,
}

// Sparse
#[derive(PartialEq, Eq, Hash, Clone, Copy)]
struct ChunkCoord { x: i64, y: i64, z: i64 }

struct Chunk {
    voxels: Vec<Voxel>,  // 16³ = 4096 voxel
}

struct SparseGrid {
    chunks: HashMap<ChunkCoord, Chunk>,
    chunk_size: usize,
}

fn main() {
    // Dense:64³ = 262144 voxel
    let dim = 64;
    let dense = DenseGrid {
        data: vec![Voxel::default(); dim*dim*dim],
        dim,
    };
    let dense_bytes = dense.data.len() * 4;
    println!("Dense 64³: {} bytes ({:.2} MB)", dense_bytes, dense_bytes as f64 / 1_048_576.0);

    // Sparse:1 个 16³ chunk
    let mut sparse = SparseGrid {
        chunks: HashMap::new(),
        chunk_size: 16,
    };
    sparse.chunks.insert(
        ChunkCoord { x: 0, y: 0, z: 0 },
        Chunk { voxels: vec![Voxel::default(); 16*16*16] },
    );
    let chunk_bytes = 16*16*16 * 4;
    println!("Sparse (1 chunk): {} bytes ({:.2} MB)", chunk_bytes, chunk_bytes as f64 / 1_048_576.0);

    println!("Ratio: {:.1}x savings", dense_bytes as f64 / chunk_bytes as f64);
}
```

## 8 · Rust / Arch 落地代码

完整 sparse voxel grid:

```rust
use std::collections::HashMap;

#[derive(Clone, Copy, Default, Debug, PartialEq)]
pub struct Voxel { pub r: u8, pub g: u8, pub b: u8, pub a: u8 }

#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub struct ChunkCoord { pub x: i64, pub y: i64, pub z: i64 }

pub const CHUNK_SIZE: usize = 16;

pub struct Chunk {
    pub voxels: Vec<Voxel>,
    pub occupied: Vec<u64>,  // 16³ / 64 = 64 个 u64
}

impl Chunk {
    fn new() -> Self {
        Chunk {
            voxels: vec![Voxel::default(); CHUNK_SIZE*CHUNK_SIZE*CHUNK_SIZE],
            occupied: vec![0u64; CHUNK_SIZE*CHUNK_SIZE*CHUNK_SIZE / 64],
        }
    }

    fn idx(lx: usize, ly: usize, lz: usize) -> usize {
        (lz * CHUNK_SIZE + ly) * CHUNK_SIZE + lx
    }

    fn get(&self, lx: usize, ly: usize, lz: usize) -> Voxel {
        self.voxels[Self::idx(lx, ly, lz)]
    }

    fn set(&mut self, lx: usize, ly: usize, lz: usize, v: Voxel) {
        let i = Self::idx(lx, ly, lz);
        self.voxels[i] = v;
        // 更新 occupied bit
        let word = i / 64;
        let bit = i % 64;
        let is_occupied = v.r > 0 || v.g > 0 || v.b > 0 || v.a > 0;
        if is_occupied {
            self.occupied[word] |= 1u64 << bit;
        } else {
            self.occupied[word] &= !(1u64 << bit);
        }
    }

    fn is_occupied(&self, lx: usize, ly: usize, lz: usize) -> bool {
        let i = Self::idx(lx, ly, lz);
        let word = i / 64;
        let bit = i % 64;
        (self.occupied[word] >> bit) & 1 == 1
    }
}

pub struct SparseVoxelGrid {
    pub chunks: HashMap<ChunkCoord, Chunk>,
}

impl SparseVoxelGrid {
    pub fn new() -> Self {
        SparseVoxelGrid { chunks: HashMap::new() }
    }

    pub fn get(&self, x: i64, y: i64, z: i64) -> Voxel {
        let cx = x.div_euclid(CHUNK_SIZE as i64);
        let cy = y.div_euclid(CHUNK_SIZE as i64);
        let cz = z.div_euclid(CHUNK_SIZE as i64);
        if let Some(chunk) = self.chunks.get(&ChunkCoord { x: cx, y: cy, z: cz }) {
            let lx = x.rem_euclid(CHUNK_SIZE as i64) as usize;
            let ly = y.rem_euclid(CHUNK_SIZE as i64) as usize;
            let lz = z.rem_euclid(CHUNK_SIZE as i64) as usize;
            chunk.get(lx, ly, lz)
        } else {
            Voxel::default()
        }
    }

    pub fn set(&mut self, x: i64, y: i64, z: i64, v: Voxel) {
        let cx = x.div_euclid(CHUNK_SIZE as i64);
        let cy = y.div_euclid(CHUNK_SIZE as i64);
        let cz = z.div_euclid(CHUNK_SIZE as i64);
        let chunk = self.chunks.entry(ChunkCoord { x: cx, y: cy, z: cz })
            .or_insert_with(Chunk::new);
        let lx = x.rem_euclid(CHUNK_SIZE as i64) as usize;
        let ly = y.rem_euclid(CHUNK_SIZE as i64) as usize;
        let lz = z.rem_euclid(CHUNK_SIZE as i64) as usize;
        chunk.set(lx, ly, lz, v);
    }

    pub fn memory_bytes(&self) -> usize {
        self.chunks.len() * (
            CHUNK_SIZE*CHUNK_SIZE*CHUNK_SIZE * 4 +  // voxels RGBA8
            CHUNK_SIZE*CHUNK_SIZE*CHUNK_SIZE / 8    // occupied bit array
        )
    }
}

fn main() {
    let mut grid = SparseVoxelGrid::new();

    // 在 (5, 5, 5) 放一个亮红 voxel
    grid.set(5, 5, 5, Voxel { r: 255, g: 0, b: 0, a: 255 });
    // 在 (20, 5, 5) 放(在另一个 chunk)
    grid.set(20, 5, 5, Voxel { r: 0, g: 255, b: 0, a: 255 });

    println!("Chunks: {}", grid.chunks.len());
    println!("Memory: {} bytes", grid.memory_bytes());

    let v1 = grid.get(5, 5, 5);
    let v2 = grid.get(20, 5, 5);
    let v3 = grid.get(1000, 1000, 1000);  // 远处,默认值
    println!("(5,5,5): {:?}", v1);
    println!("(20,5,5): {:?}", v2);
    println!("(1000,1000,1000): {:?} (default)", v3);
}
```
