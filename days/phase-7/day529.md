
# Day 529 · 调试 PNG 写入器

> Day 453-459 你写了 PNG **解码器**(读 PNG)。今天 Day 529 Casey 写 PNG **写入器**(写 PNG)——把内存中的位图存成 PNG 文件。功能跑起来了,但生成的 PNG 在某些图像浏览器里打不开。Casey 花一整集 debug:这个 bug 不在编码逻辑,而在 CRC32 校验——他算 CRC 时混淆了 chunk data 和 chunk header。这是经典的"二进制格式 bug":逻辑正确,字节序列错误。

## 0 · 为什么要有这一天

字体提取器(Day 527)产出 PNG,但你跑出来的 PNG 在 macOS Preview 里"无法打开",在 Linux `feh` 里能开,在 Chrome 里又不能开。**不同图像浏览器对 PNG 规范的容忍度不同**——严格遵守规范的能开,不严格的就拒绝。

PNG 是 W3C 严格规范化的格式(W3C PNG Specification)。每个 chunk 有 4 字节 CRC32 校验,任何字节错都让 CRC 失败。规范严格性是 PNG 设计的安全特性(防止传输损坏),但对开发者是地狱——一个字节写错就"打不开"。

Casey 这一天的 bug 类型很典型:**CRC32 算法对了,但喂给它的数据错了**。PNG CRC 是对 chunk type + chunk data 拼接后算 CRC,Casey 误以为只对 data 算。算法相同,输入不同,结果错误。

这种 bug 在二进制格式开发中无处不在:

- ELF 写入器:section offset 算错,程序加载就崩
- PE 写入器:RVA(relative virtual address)算错,Windows 拒绝执行
- WAV 写入器:byte rate 写错,某些播放器拒绝
- BSON/MongoDB:长度字段写错,服务器拒绝
- SQL 二进制协议:length prefix 写错,连接断

为什么这种 bug 这么难修?因为**没有运行时错误信息**。你的代码跑得好好的,只是输出的字节序列不符合规范。你需要**对照规范文档,逐字节验证**。

#### 各浏览器容忍度的真实差异

让我把"不同浏览器容忍度"这件事讲具体。Casey 用的几个工具:

| 工具 | 行为 | Casey 适合用吗 |
|---|---|---|
| `pngcheck -v` | 严格,任何 CRC 错都报 | 必备调试工具 |
| `pngcrush -fix` | 自动修一些"软"错误 | 修复用 |
| macOS Preview | 严格,坏 CRC 直接拒绝打开 | 测试基线 |
| Linux `feh` | 宽松,跳过坏 CRC 强行显示 | 不能用来验证正确性 |
| Chrome | 严格,坏 CRC 显示 broken image | 测试基线 |
| Firefox | 中等,有时显示警告图标 | 辅助测试 |
| GIMP | 严格,坏 CRC 拒绝打开 | 测试基线 |

教训:**永远用最严格的工具验证**。如果你的 PNG 在 pngcheck 和 macOS Preview 都能开,基本能保证在所有浏览器都能开。反之,在 Linux `feh` 里能开**不代表**正确——它可能只是友好地忽略错误。

这是工业级开发的核心原则:**测试用最严格的客户端,部署时考虑宽松客户端**。前者保证质量,后者保证兼容性。

#### 二进制格式 bug 的 4 步定位法

Casey 在视频里用了一套标准的二进制 bug 调试流程:

1. **找一个已知正确的 reference 文件**:Casey 用 ImageMagick 生成一个相同尺寸的 PNG(`convert -size 8x8 xc:red good.png`),作为"正确字节序列"对照
2. **用 hex dump 工具看字节**:`xxd test.png > test.hex`、`xxd good.png > good.hex`,然后 `diff test.hex good.hex`
3. **定位第一个差异字节**:diff 输出告诉你哪些字节不同。这里就是 bug 位置
4. **对照规范查这个字节应该是什么**:规范文档 + diff 输出,你能精确知道"我写错了什么"

这套流程对**任何二进制格式**都适用——ELF、PE、WAV、MP4、BSON……学会它,你以后写任何二进制解析/生成器都不怕。

完成这一天之后,你具备:

- 看到"二进制文件打不开"时,知道用 hex dump 工具对照规范
- 理解 CRC32 的标准用法(在 PNG 这种格式里)
- 能用 Rust 实现 PNG 写入器(并知道 CRC 是哪里容易出错)
- 学会用 reference diff 法调试二进制 bug

## 2 · 心智模型

### 类比:写信封的邮编

邮编是 6 位数字,前 2 位是省,后 4 位是投递局。如果你写邮编时**漏了前 2 位**(只写后 4 位),信也能寄——邮局工作人能猜出来。但如果邮编规则**严格要求 6 位**,少了 2 位机器分拣就拒绝。

CRC 校验就是这种"严格要求"。少一字节、多一字节、顺序错,机器立刻拒绝。你写信的人感觉"我写的就是数据啊,应该接受",但规则是规则。

### 严谨展开:CRC32 算法

CRC32(Cyclic Redundancy Check,循环冗余校验)是经典的错误检测码。原理:把数据看作一个超大的二进制数,除以一个固定的"生成多项式",余数就是 CRC。

PNG chunk 结构(原规范第 5.3 节):

```
偏移    字段        长度    含义
0       Length      4       数据长度(big-endian)
4       Type        4       chunk 类型(ASCII 4 字符,如 "IHDR")
8       Data        Length  实际数据
8+L     CRC         4       CRC32 校验(big-endian)
```

注意 CRC 覆盖 Type + Data,**不**覆盖 Length 字段。Casey 的 bug 是把 Type 漏掉了。

CRC32 具体步骤(简化):

1. 把数据每个字节看作 8-bit
2. 维护一个 32-bit 寄存器 `crc`,初始值 = 0xFFFFFFFF
3. 对每个字节 b:`crc = crc ^ (b << 24)`,然后做 8 次:如果最高位是 1,左移 + XOR 多项式;否则只左移
4. 最后 `crc = crc ^ 0xFFFFFFFF`,这就是最终 CRC

多项式(PNG 用的标准 CRC32-IEEE):`0x04C11DB7`。

工业实现用**查表法**——预先计算 256 个 entry 的表,运行时每个字节查一次。代码:

```rust
const CRC_TABLE: [u32; 256] = [
    // 预计算 256 个值(略)
];

fn crc32(data: &[u8]) -> u32 {
    let mut crc: u32 = 0xFFFFFFFF;
    for &b in data {
        let idx = ((crc ^ (b as u32)) & 0xFF) as usize;
        crc = (crc >> 8) ^ CRC_TABLE[idx];
    }
    crc ^ 0xFFFFFFFF
}
```

查表法比 bit-by-bit 快 8 倍(每字节 1 次表查询 + 1 次 XOR,而不是 8 次条件移位)。Rust 标准库的 `std::hash::Hasher` 不是 CRC32(是 SipHash),所以你需要 `crc32fast` crate 或自己实现。

#### Casey 的具体 bug:漏了 type 字节

PNG 规范第 5.5 节说:`CRC = crc32(type_bytes + data_bytes)`。Casey 的 bug 是他只算了 `crc32(data_bytes)`,漏了 4 字节 type。

正确代码:

```rust
fn write_chunk(out: &mut Vec<u8>, chunk_type: &[u8; 4], data: &[u8]) {
    // length
    out.extend_from_slice(&(data.len() as u32).to_be_bytes());
    // type
    out.extend_from_slice(chunk_type);
    // data
    out.extend_from_slice(data);
    // CRC over type + data
    let mut crc_input = Vec::with_capacity(4 + data.len());
    crc_input.extend_from_slice(chunk_type);
    crc_input.extend_from_slice(data);
    let crc = crc32(&crc_input);
    out.extend_from_slice(&crc.to_be_bytes());
}
```

Casey 的错误版本:CRC 只对 `data`,没把 `chunk_type` 加进去。结果:CRC 值和正确值不同(因为输入少 4 字节),严格浏览器拒绝。

这个 bug 在测试时容易漏,因为如果你**只测试同一个 chunk type**,错误 CRC 和正确 CRC 的差值是固定的——某些"友好"浏览器可能忽略。但只要 chunk type 变了(从 IHDR 到 IDAT),差值也变,bug 暴露。

教训:**测试二进制格式时,要测多种 chunk / section / 类型**,不能只测一种。Casey 在视频里承认这个 bug 潜伏了几天,直到他用 ImageMagick 验证才发现。

**CRC32 算法的输入范围**:`Type + Data`(共 `4 + Length` 字节)。**不包括 Length 字段本身**。

这个规则是 PNG 规范的明确要求(W3C PNG 5.5 节):

> The CRC is calculated over the chunk type and chunk data, but not the length field.

Casey 的 bug:他对 Data 算 CRC,没有把 Type 字节拼上。所以 CRC 错了。

### CRC32 算法

CRC32(Cyclic Redundancy Check,32-bit)是经典的错误检测码。原理:把数据看作大整数,模一个 33 位生成多项式,得到 32 位余数。

IEEE 802.3 标准 CRC32 多项式:`0xEDB88320`(反射形式)。预计算 256 项表,逐字节查表 XOR。

```rust
// 标准 CRC32 实现
fn crc32(data: &[u8]) -> u32 {
    let mut crc: u32 = 0xFFFFFFFF;
    for &b in data {
        let i = ((crc ^ b as u32) & 0xFF) as usize;
        crc = (crc >> 8) ^ CRC_TABLE[i];
    }
    crc ^ 0xFFFFFFFF
}

// CRC32 查表(IEEE 802.3 多项式)
static CRC_TABLE: [u32; 256] = [
    // 预计算的 256 个值
    0x00000000, 0x77073096, 0xEE0E612C, 0x990951BA,
    // ... 完整 256 项
];
```

CRC32 的几个特性:

- **可逆性**:对相同输入,输出相同(确定性)
- **错误检测**:能检测 1-3 位错误,>99.99% 检测率
- **不防恶意篡改**:攻击者可重算 CRC,CRC 不是签名

PNG 用 CRC 是为了**检测传输损坏**,不是为了安全。

### Casey 的 bug 复现

正确的 CRC 计算:

```rust
fn write_chunk(out: &mut Vec<u8>, type_: &[u8; 4], data: &[u8]) {
    // 1. Length
    out.extend_from_slice(&(data.len() as u32).to_be_bytes());
    // 2. Type
    out.extend_from_slice(type_);
    // 3. Data
    out.extend_from_slice(data);
    // 4. CRC = crc32(Type + Data)
    let mut crc_input = Vec::with_capacity(4 + data.len());
    crc_input.extend_from_slice(type_);

}
```

### 3.4 · Rust 生态视角

Rust 写二进制格式的工具:

- **`byteorder`** —— 大端/小端整数读写
- **`bytes`**(tokio 出品)—— 缓冲区抽象,网络协议用
- **`bincode`** —— Rust 结构体自动序列化(小端)
- **`crc32fast`** —— 极速 CRC32

```rust
// Cargo.toml:
// [dependencies]
// crc32fast = "1.4"
// byteorder = "1.5"

use byteorder::{BigEndian, WriteBytesExt};
use crc32fast::Hasher;

fn write_chunk(out: &mut Vec<u8>, type_: &[u8; 4], data: &[u8]) {
    out.write_u32::<BigEndian>(data.len() as u32).unwrap();  // Length
    out.extend_from_slice(type_);                              // Type
    out.extend_from_slice(data);                               // Data
    
    // CRC over type + data
    let mut hasher = Hasher::new();
    hasher.update(type_);
    hasher.update(data);
    let crc = hasher.finalize();
    out.write_u32::<BigEndian>(crc).unwrap();                  // CRC
}
```

`crc32fast` 比手写循环快 5-10 倍(SIMD 优化)。`byteorder` 让大小端显式,避免平台相关 bug。

### 4.1 上级(它属于哪个更大抽象?)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |

## 5 · 对照与变奏

PNG vs JPEG vs WebP 的写入难度对比:

- **BMP** —— 最简单,无压缩无校验,直接 raw pixels
- **JPEG** —— 复杂(DCT 量化),无校验
- **PNG** —— 中等(DEFLATE 压缩 + CRC32 校验)
- **WebP** —— 复杂(VP8/VP8L),基于 RIFF(同 WAV)

Casey 在 Day 453-459 写了 PNG 解码,这是 Day 529 写入器的镜像。解码和编码的算法(Deflate、Huffman、CRC)是对称的——你解码器跑通了,编码器就是反向操作。

历史上 CRC 的故事:CRC 是 1961 年 W. Wesley Peterson 发明,IEEE 802.3(以太网)1983 年采用。PNG(1996)选 CRC32 是因为它是网络时代的"事实标准",所有平台都有实现。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:Casey 的 bug 是 CRC 漏算 type 字节。为什么不直接去掉 CRC,让格式更简单?

**参考解答**:CRC 是 W3C 规范的一部分,所有 PNG 解码器都期待它。如果你写不带 CRC 的 PNG,标准解码器拒绝(因为它们要校验)。即使你能修改解码器跳过 CRC,生成的 PNG 不能用标准工具(浏览器、Photoshop)打开,失去了 PNG"通用格式"的价值。规范是契约,双方都要遵守。Casey 的 PNG 解码器必须能读标准 PNG,他的写入器也必须产生标准 PNG,这样两端才互通。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:用 Rust 写一个最小的 PNG 写入器,生成 1×1 像素的红色 PNG。要求:(1)8 个字节 magic;(2)IHDR chunk(13 字节 data:width=1, height=1, bit_depth=8, color_type=2=RGB, ...);(3)IDAT chunk(DEFLATE 压缩的图像数据,用 `flate2` 库);(4)IEND chunk。每个 chunk 有 CRC。运行后用 `pngcheck -v` 验证。

**参考解答**:

```rust
// Cargo.toml:
// [dependencies]
// crc32fast = "1.4"
// flate2 = "1.0"
// byteorder = "1.5"

use crc32fast::Hasher;
use byteorder::{BigEndian, WriteBytesExt};
use flate2::write::ZlibEncoder;
use flate2::Compression;
use std::io::Write;

fn write_chunk(out: &mut Vec<u8>, type_: &[u8; 4], data: &[u8]) {
    out.write_u32::<BigEndian>(data.len() as u32).unwrap();
    out.extend_from_slice(type_);
    out.extend_from_slice(data);
    
    let mut h = Hasher::new();
    h.update(type_);
    h.update(data);
    let crc = h.finalize();
    out.write_u32::<BigEndian>(crc).unwrap();
}

fn main() {
    let mut png = Vec::new();
    
    // 1. PNG magic(8 字节)
    png.extend_from_slice(&[0x89, b'P', b'N', b'G', 0x0D, 0x0A, 0x1A, 0x0A]);
    
    // 2. IHDR: width=1, height=1, bit_depth=8, color_type=2 (RGB), ...
    let mut ihdr = Vec::new();
    ihdr.write_u32::<BigEndian>(1).unwrap();   // width
    ihdr.write_u32::<BigEndian>(1).unwrap();   // height
    ihdr.push(8);                                // bit_depth
    ihdr.push(2);                                // color_type (RGB)
    ihdr.push(0);                                // compression (deflate)
    ihdr.push(0);                                // filter (adaptive)
    ihdr.push(0);                                // interlace (none)
    write_chunk(&mut png, b"IHDR", &ihdr);
    
    // 3. IDAT: filter byte (0) + RGB pixel (255, 0, 0)
    let raw_data = vec![0, 255, 0, 0];  // filter=none, R=255, G=0, B=0
    
    // zlib 包装(deflate + zlib header)
    let mut encoder = ZlibEncoder::new(Vec::new(), Compression::default());
    encoder.write_all(&raw_data).unwrap();
    let compressed = encoder.finish().unwrap();
    
    write_chunk(&mut png, b"IDAT", &compressed);
    
    // 4. IEND(空 data)
    write_chunk(&mut png, b"IEND", &[]);
    
    std::fs::write("red.png", &png).unwrap();
    println!("写出 {} 字节到 red.png", png.len());
}
```

为什么这么写:`write_chunk` 是核心——所有 chunk 用同一逻辑写,避免重复 bug。`ZlibEncoder` 自动加 zlib header(0x78 9C)和 Adler32 checksum。CRC 必须在 type_ + data 一起算,这是 Casey 这天发现的 bug。`pngcheck -v` 是验证 PNG 正确性的金标准工具。

```rust
// 完整 PNG writer,带详细注释

use std::io::Write;
use byteorder::{BigEndian, WriteBytesExt};
use crc32fast::Hasher;
use flate2::write::ZlibEncoder;
use flate2::Compression;

const PNG_MAGIC: [u8; 8] = [0x89, b'P', b'N', b'G', 0x0D, 0x0A, 0x1A, 0x0A];

/// 写一个 PNG chunk: [length BE][type][data][crc BE]
/// CRC 计算范围是 type + data(不含 length 字段)
fn write_chunk(out: &mut Vec<u8>, chunk_type: &[u8; 4], data: &[u8]) {
    // 1. Length: 4 字节 BE(大端)
    out.write_u32::<BigEndian>(data.len() as u32)
        .expect("write length");
    
    // 2. Type: 4 字节 ASCII(如 b"IHDR")
    out.extend_from_slice(chunk_type);
    
    // 3. Data: 任意字节
    out.extend_from_slice(data);
    
    // 4. CRC: 4 字节 BE,计算范围 = Type + Data
    //    这是 Casey 这天发现的 bug 关键!
    let mut hasher = Hasher::new();
    hasher.update(chunk_type);  // ← 这一行原来漏了
    hasher.update(data);
    let crc = hasher.finalize();
    out.write_u32::<BigEndian>(crc)
        .expect("write crc");
}

/// 写一个 RGB PNG 文件
/// pixels 长度 = width * height * 3
pub fn write_rgb_png(
    path: &str,
    width: u32,
    height: u32,
    pixels: &[u8],
) -> std::io::Result<()> {
    assert_eq!(pixels.len(), (width * height * 3) as usize);
    
    let mut png = Vec::new();
    
    // 1. Magic
    png.extend_from_slice(&PNG_MAGIC);
    
    // 2. IHDR chunk
    let mut ihdr = Vec::with_capacity(13);
    ihdr.write_u32::<BigEndian>(width).unwrap();
    ihdr.write_u32::<BigEndian>(height).unwrap();
    ihdr.push(8);    // bit_depth
    ihdr.push(2);    // color_type = RGB
    ihdr.push(0);    // compression = deflate
    ihdr.push(0);    // filter = adaptive
    ihdr.push(0);    // interlace = none
    write_chunk(&mut png, b"IHDR", &ihdr);
    
    // 3. IDAT chunk:每行前加 filter byte (0 = None)
    let mut raw = Vec::with_capacity((width * height * 3 + height) as usize);
    for y in 0..height {
        raw.push(0);  // filter byte for this row
        let row_start = (y * width * 3) as usize;
        let row_end = ((y + 1) * width * 3) as usize;
        raw.extend_from_slice(&pixels[row_start..row_end]);
    }
    
    // zlib 包装的 deflate
    let mut encoder = ZlibEncoder::new(Vec::new(), Compression::default());
    encoder.write_all(&raw)?;
    let compressed = encoder.finish()?;
    write_chunk(&mut png, b"IDAT", &compressed);
    
    // 4. IEND chunk
    write_chunk(&mut png, b"IEND", &[]);
    
    std::fs::write(path, &png)
}

fn main() {
    // 生成 8x8 的红色 PNG
    let width = 8;
    let height = 8;
    let pixels: Vec<u8> = (0..(width * height * 3))
        .map(|i| if i % 3 == 0 { 255 } else { 0 })  // RGB = (255, 0, 0)
        .collect();
    
    write_rgb_png("red8x8.png", width, height, &pixels).unwrap();
    println!("写出 red8x8.png");
    
    // 用 std::process::Command 调用 pngcheck 验证
    let output = std::process::Command::new("pngcheck")
        .arg("-v")
        .arg("red8x8.png")
        .output()
        .expect("pngcheck not installed");
    
    println!("pngcheck 输出:");
    println!("{}", String::from_utf8_lossy(&output.stdout));
    if !output.status.success() {
        println!("stderr: {}", String::from_utf8_lossy(&output.stderr));
    }
}
```

出错怎么办:

- **`pngcheck` 报 CRC error**:检查 CRC 计算范围(type + data,不含 length)。这是最常见的 bug。
- **`pngcheck` 报 unexpected end of file**:某个 chunk 的 length 比实际 data 长。检查 length 写入。
- **图像浏览器提示"解码失败"**:可能是 IDAT 的 zlib 包装错——必须用 `ZlibEncoder` 而不是裸 `DeflateEncoder`。zlib 包装 = deflate + 2 字节 header(0x78 9C)+ 4 字节 Adler32。
- **生成的图像是黑色**:filter byte 错了。每行 raw 数据前必须有 1 字节 filter type(0 = None)。
