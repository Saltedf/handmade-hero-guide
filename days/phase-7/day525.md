
# Day 525 · 清理导入标签网格

> Day 482 给 PNG 关联标签(tag)时,Casey 用了一种最朴素的方案:在 PNG 图像里画一个**标签网格(tag grid)**——一张图像的最后一行(或某一行)像素颜色编码了"这个瓦片属于哪个标签"。这是一种"视觉元数据"——把元数据嵌入到图像本身。Day 525 是清理工作:这个网格的实现有重复代码、边界条件没处理干净、特殊 case 散落各处。Casey 把它重构干净。

## 0 · 为什么要有这一天

Day 482 Casey 设计了一种聪明的方案:不用单独的 metadata 文件,直接在 PNG 像素里编码元数据。具体做法是:PNG 的最后几行作为"标签行(tag row)",每个像素的颜色编码一个标签 ID。比如绿色 = "可碰撞",红色 = "危险",蓝色 = "背景"。

这种方案的好处:**资产和元数据永远在一起**。复制 PNG 文件,标签跟着走;发给别人,他打开图就能看到所有标签。Casey 在 Day 482 实现它时,代码是工作的,但粗糙——几个地方有重复、几个边界情况没处理、网格的 size 假设硬编码。

Day 525 是 cleanup day(清理日)。Casey 没加新功能,而是把现有代码**整理一遍**:提取重复逻辑、命名统一、加文档、补测试。这种"不增加功能但提升代码质量"的实践,在工业界叫**重构(refactor)**——Martin Fowler 1999 年的同名书是这一领域的经典。

为什么清理很重要?**代码读 10 次才写 1 次**。如果代码乱,你后面 10 次读它都要付代价。所以花 1 次时间清理,后面省 9 次的痛。

**重构的更深一层意义**:它把"理解"显式化。当 Casey 写 Day 482 时,他对 tag grid 的理解是隐式的——他知道哪些行是主图、哪些是标签行,但这种"知道"分散在代码的多个 if/else 里。重构时,他必须把这种隐式理解**翻译成清晰的函数名和结构**——`is_tag_row()`、`tag_from_pixel()`、`split_image()`。这些函数名就是知识的载体,以后任何人读代码,看函数名就知道"哦,这里是处理标签行的"。

这就是为什么**有经验的程序员 30% 时间写新代码,70% 时间重构**。新代码只是表达当下的理解;重构是不断把"昨天写的隐式理解"显式化,让明天读起来快。Google 的代码文化里有一条:**"如果你加一个新函数,先看看现有代码能不能稍微重构一下让你不用加"**。这种习惯让代码库长期保持健康。

完成这一天之后,你具备:

- 理解 refactor 和 feature 的差别(feature 增加行为,refactor 改善结构但不改行为)
- 知道什么代码味道(code smell)是重构的信号
- 在 Rust 里用 `extract function` / `inline function` / `rename` 三种基础重构手法
- 学会用单元测试做"安全网":重构前先写测试,验证行为不变

## 1 · Casey 今天做了什么

Casey 这一天的动作可以拆成三步:

第一步,**盘点重复**。他 grep 了 tag grid 相关代码,发现读和写两个方向各有"判断像素是否是标签行"的逻辑,但实现略有不同(一个用 row == height - 1,另一个用 row > height - 1 - tag_row_count)。Casey 提取成一个 `IsTagRow(row)` 函数,两边都用。

第二步,**命名统一**。原来代码里混用了 "metadata grid"、"tag row"、"annotation row" 三个词表达同一概念。Casey 全部统一为 "tag grid",因为这是 Casey 在视频里始终用的术语。命名一致性是可读性的基础。

第三步,**边界处理**。原来代码假设 PNG 高度 >= 1 + tag_row_count(主图至少 1 行,标签行至少 1 行),但实际可能是空图。Casey 加了 assert,并在导入时检查图像尺寸是否符合预期。

视频里他强调:重构不是"让代码更短",而是"让代码更清晰"。提取函数可能让代码行数增加(因为多了函数定义),但可读性提升(每个函数名就是注释)。

## 2 · 心智模型

### 类比:工具箱整理

你的工具箱里有螺丝刀、扳手、锤子,但乱七八糟堆在一起。每次找螺丝刀都要翻三分钟。整理工具箱:每个工具放固定位置,贴标签。整理后,工具数量没变(没有"新功能"),但找东西快了(refactor 价值)。

代码重构一样:函数数量可能没变,但函数名清晰、位置合理,读起来快了。

### 严谨展开:三种基础重构

Martin Fowler 的《Refactoring》书里列了 60+ 种重构手法,但最基础的就三个:

**提取函数(Extract Function)**:把一段代码变成一个独立函数。

```rust
// Before
fn process_image(img: &Image) {
    let tag_row_count = 2;
    let img_height = img.height;
    let main_height = img_height - tag_row_count;
    for y in 0..main_height {
        for x in 0..img.width {
            // ... 处理主图
        }
    }
    for y in main_height..img_height {
        for x in 0..img.width {
            // ... 处理标签行
        }
    }
}

// After
fn process_image(img: &Image) {
    let (main, tags) = split_image(img);
    process_main_region(main);
    process_tag_grid(tags);
}

fn split_image(img: &Image) -> (&Image, &Image) { ... }
fn process_main_region(img: &Image) { ... }
fn process_tag_grid(img: &Image) { ... }
```

**重命名(Rename)**:变量、函数、类型换更好的名字。看起来简单,但效果巨大——好的名字本身就是文档。

**内联函数(Inline Function)**:和 Extract 相反,把只有一个调用的函数体替换回调用处。有时 Extract 后发现函数只被调用一次,内联回去更清晰。

### 重构的安全网:测试

重构的危险是"我以为只改结构,实际改了行为"。防御方法是**测试**:

```
1. 跑一遍所有测试,确认通过(基线)
2. 做一个小重构(提取一个函数)
3. 跑所有测试,确认仍通过
4. 如果失败,撤销重构,重新思考
5. 如果通过,提交,继续下一个重构
```

这个循环叫 "red-green-refactor"(TDD 节奏)。Casey 没有正式的单元测试,但他有"运行游戏 → 用编辑器操作 → 视觉验证"的流程,效果类似——只要视觉一致,行为没变。

### 代码味道(Code Smells)

Martin Fowler 列了 22 种代码味道,最常见:

- **重复代码(Duplicated Code)**:同样的逻辑出现 2+ 次。提取函数。
- **过长函数(Long Method)**:一个函数 100+ 行。拆分成几个小函数。
- **过长参数列表(Long Parameter List)**:函数有 5+ 参数。打包成 struct。
- **不一致命名(Inconsistent Naming)**:同一概念用不同词。统一。
- **魔法数字(Magic Numbers)**:代码里 `2`、`3` 等无解释的常量。提取成命名常量。
- **散弹枪修改(Shotgun Surgery)**:一个改动需要改多处。重构让相关代码集中。

Casey 这一天主要处理的是"重复代码"和"不一致命名"。

#### 代码味道的"嗅觉训练"

代码味道不是教科书概念,而是**经验提炼的模式**。Fowler 用的"smell(味道)"这个词很精准——经验丰富的程序员"嗅"出代码坏味道,就像厨师尝一口就知道菜咸了。这种嗅觉只能通过读大量代码培养。

训练方法:每天读 100 行开源代码(bevy、tokio、serde),问自己"这段代码有什么味道?"。开始你只看到"乱",半年后你能精确命名"这是 divergent change(发散式修改)"。这是工程师的核心能力之一。

#### tag grid 这个具体例子的味道清单

让我对 Casey Day 482 的原始代码做一次"味道诊断":

```c
// Casey Day 482 的伪 C 代码(简化)
internal void ProcessPNGForImport(png_image* Image) {
    // 主图区:rows [0, Height-2)
    for (int y = 0; y < Image->Height - 2; y++) {  // 味道:魔法数字 2
        for (int x = 0; x < Image->Width; x++) {
            // ... 处理像素
        }
    }
    // 标签区:rows [Height-2, Height)
    for (int y = Image->Height - 2; y < Image->Height; y++) {  // 味道:重复 2
        for (int x = 0; x < Image->Width; x++) {
            // ... 读标签
        }
    }
}
```

诊断清单:
- **魔法数字 2**:这个 2 是什么?注释说"标签行数"。提取成 `#define TAG_ROW_COUNT 2`
- **重复 2**:`Height - 2` 在两个地方都出现。提取成 `MainHeight = Height - TAG_ROW_COUNT`
- **边界条件隐式**:如果 Height < 2 怎么办?现在 underflow。加 assert
- **行号语义混淆**:`y < Height - 2` 是"主图行",`y >= Height - 2` 是"标签行"。提取 `IsTagRow(y)` 让语义显式

Day 525 Casey 把这 4 个味道全修了。重构后的代码读起来"清爽"——每个函数名就是注释,没有魔法数字,边界显式检查。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏代码的特点是**节奏快**——快速迭代导致代码乱。重构在游戏开发里比企业软件更难,因为:

- 性能敏感,小函数可能阻碍内联(inlining)
- 测试难写(渲染输出是视觉,不是布尔值)
- 工期紧,重构看起来"浪费时间"

工业级游戏团队通常有"重构日"——每周或每两周一天专门整理代码。Unity 的 DOTS 重构(从 GameObject 到 ECS)就是历时多年的大规模重构。

### 3.2 · 图形学视角

渲染代码的常见重构:

- **shader 内联**:GPU shader 不支持函数调用开销,把小函数 inline 进 main
- **材质系统抽象**:把 `if material_type == X` 分发改成 trait/object 接口
- **资源生命周期**:把"手动 init/free"改成 RAII guard

这些重构不改渲染结果,但让代码维护性大幅提升。

### 3.3 · Linux 系统编程视角

Linux 内核是大型重构的宝库。每次大版本都有数百个"cleanup patch",例如:

- `scripts/checkpatch.pl` —— 自动检查代码风格
- `scripts/coccinelle/` —— 用语义补丁做大规模重构
- Linus 在邮件列表里经常说"this code is a mess, refactor it"

内核的反例:`goto cleanup` 模式看起来"丑陋",但它是内核处理资源释放的标准模式——因为它避免深层嵌套。这种"看似丑但实际好"的模式,需要工程经验才能识别。

### 3.4 · Rust 生态视角

Rust 的工具链让重构特别安全:

- **`cargo check`** —— 秒级反馈,改一行立刻知道是否编译
- **`cargo clippy`** —— 自动检测 200+ 种代码味道
- **`cargo fmt`** —— 自动格式化,消除"风格不一致"的味道
- **rust-analyzer** —— IDE 级支持,提取函数、内联变量等重构自动化
- **强类型系统** —— 重命名函数 / 改类型签名后,编译器告诉你所有受影响的调用点

对比 C++:重构一个 header 文件可能要 rebuild 整个项目(几分钟)。Rust 的增量编译让"试一下,改回来"成本极低。

#### Rust 特有的重构手法

**从 `String` 改成 `&str`**:很多新手过度使用 `String`(堆分配),重构时改成 `&str`(借用)能省一次分配。

```rust
// Before(每次调用都 clone)
fn process(name: String) -> String { name.to_uppercase() }

// After(零分配)
fn process(name: &str) -> String { name.to_uppercase() }
```

**从 `Vec<T>` 改成 `&[T]`**:函数参数优先用 slice,让调用者决定是 Vec 还是 array。

**提取 trait**:多个类型有相同方法,提取成 trait。

```rust
// Before
struct Png { ... }
struct Wav { ... }
impl Png { fn load(path: &str) -> Self { ... } }
impl Wav { fn load(path: &str) -> Self { ... } }

// After
trait Asset {
    fn load(path: &str) -> Self;
}
impl Asset for Png { fn load(...) { ... } }
impl Asset for Wav { fn load(...) { ... } }
```

这种"看到重复就提取 trait"是 Rust 重构的核心模式,Casey 在 C 里用函数指针 + struct vtable 手动实现,代码丑陋得多。Rust 的 trait 是工业级抽象的工具。


Rust 的编译器是最强的"重构安全网"。Rust 的类型系统让很多重构变得安全:

- **提取函数**:Rust 编译器会自动推断参数类型,你不需要手动声明
- **改字段类型**:编译器会标记所有用到该字段的地方
- **改 trait**:编译器强制实现所有 trait 方法

Rust 特有的重构:

- **Option<T> 替换 nullable pointer**:把 `*T` 改成 `Option<&T>` 或 `Option<Box<T>>`
- **Result<T, E> 替换 error code**:把 `i32` 返回值改成 `Result<(), Error>`
- **trait object 替换 enum dispatch**:有时让代码更扩展(可加新类型)

`clippy` 是 Rust 的 lint 工具,自动检测代码味道:

```bash
cargo clippy -- -W clippy::all
```

它会建议:`this function is too long`、`this could be a method`、`this pattern match could be simplified`。这是 Rust 比 C/C++ 优势之一——内建代码质量工具。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **重构(Refactoring)** —— 改善代码结构但不改行为
- **代码质量(Code Quality)** —— 可读性、可维护性、可扩展性
- **技术债务(Technical Debt)** —— 暂时性代码缺陷,未来要还的"利息"

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 重构(Refactor) | 不改行为,改善结构 | 代码乱但工作 | Casey 选这个 |
| 重写(Rewrite) | 从头再来 | 代码烂到救不回 | 极端情况 |
| 封装(Wrap) | 旧代码不动,加新接口 | 旧代码稳定但难用 | 中间方案 |
| 留下(Leave it) | 不动 | 改了风险大于收益 | 一次性脚本 |

### 4.3 下级(内部零件)

- **Extract Function** —— 提取函数
- **Rename** —— 重命名
- **Inline Function** —— 内联函数
- **Move Function** —— 移动到合适的模块
- **code smell** —— 重构的信号

## 5 · 对照与变奏

不同语言生态对重构的态度:

- **C++**:重构难,因为头文件依赖、宏、隐式转换。Clang 的 `clang-tidy` 提供工具支持。
- **Java**:重构文化最成熟,IDE(IntelliJ、Eclipse)自动化程度最高。
- **Python**:动态类型让重构危险,用 `mypy` + 测试弥补。
- **Rust**:编译器是最强安全网,重构相对安全。
- **JavaScript**:TypeScript 让重构可行,纯 JS 几乎不可能安全重构。

历史上著名的大型重构:

- **Mozilla Firefox Quantum**(2017):用 Rust 重写部分组件
- **Microsoft Windows NT → 2000**:内核大幅重构
- **Python 2 → 3**:历时 10 年的语言级迁移

### Casey 的"重构节奏":三天法则

Casey 在 HH 里有一个不成文的节奏:**每写 3 天新功能,就花 1 天清理**。Day 482-484 写 tag grid(3 天),Day 525 清理(1 天)。这种 3:1 的比例是工业经验——写新功能时为了赶进度会偷工减料,3 天后这些"债"积累到必须还的程度,还不还就成"技术债"。

技术债(technical debt)是 Ward Cunningham 1992 年提出的隐喻:**代码里偷工减料就像借钱,以后要还本金 + 利息**。利息就是"每次读这段代码多花的时间"。如果一直不还,利息滚利息,代码库最终会"破产"——任何改动都极度困难。

Casey 的 3:1 节奏相当于"还信用卡账单的最低还款额",保持债务稳定。如果累积到 100 天才清理(像某些大公司),就是"破产前重组",代价巨大。

### "Boy Scout Rule":比 Casey 更激进的清理

工业界有一条比 Casey 的 3:1 更激进的规则,叫 **Boy Scout Rule(童子军法则)**:"离开营地时,比来时更干净"。翻译成代码:**每次你读/改一段代码,顺手把它清理一点点**——重命名一个变量、提取一个小函数、修一个 typo。

这条规则的好处:技术债**永不积累**,因为每个接触代码的人都在还债。坏处:每次 commit 都带一些"无关清理",diff 看起来杂乱,review 时要分辨"这是改动还是清理"。

很多开源项目(Linux 内核、Rust 编译器)采用这条规则。Casey 不采用,因为他的 commit 必须和 HH 视频一一对应(每个 commit 对应一集),不能有"顺手清理"。但你的项目可以采用。

### 重构 vs 重写:什么时候不要重构

有时候"重构"不如"重写"。判断标准:

| 场景 | 选择 | 理由 |
|---|---|---|
| 现有代码逻辑清晰,只是结构差 | 重构 | 逻辑保留,只改结构 |
| 现有代码逻辑错(算法错) | 重写 | 重构保留 bug,没意义 |
| 现有代码依赖过时库 | 重写 | 重构要兼容旧 API,得不偿失 |
| 现有代码 < 1000 行 | 都行 | 重写成本可控 |
| 现有代码 > 10000 行,有测试 | 重构 | 重写风险大,测试是安全网 |
| 现有代码 > 10000 行,无测试 | 危险区 | 先补测试,再决定 |

Joel Spolsky 2000 年的著名文章《Things You Should Never Do》警告:**永远不要从头重写**。Netscape 4 → Mozilla 的从头重写几乎毁了公司。Casey 在 HH 里也遵循这条:即使有重大架构问题,他也"逐步重构"而不是推倒重来。这是工业共识。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:Casey 提取了 `IsTagRow(row)` 函数,然后发现两个调用点的实现略有不同(一个 `==`,一个 `>`)。提取后,他选了哪个实现?为什么不是"两个都能用"就不管?

**参考解答**:他选了语义更清晰的 `row > height - 1 - tag_row_count`。原因:即使两个实现对当前数据"都能用",它们在**边界条件**上的行为可能不同。比如 PNG 高度为 1(只有一行,既是主图也是标签行),两个公式给出不同结果。重构的目标不只是"消除重复",还有"消除语义模糊"——选择一个清晰的实现,让边界行为明确。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:下面的代码有 3 处代码味道。识别并重构。要求:重构后行为不变,提供单元测试验证。

```rust
fn process_png_for_import(png: &Png) -> Vec<Tile> {
    let mut tiles = Vec::new();
    let tile_size = 32;
    let metadata_rows = 2;
    let main_height = png.height - metadata_rows;
    for y in 0..main_height {
        for x in 0..png.width {
            let pixel = png.get_pixel(x, y);
            // 主图像素
            tiles.push(Tile::from_pixel(pixel));
        }
    }
    for y in main_height..png.height {
        for x in 0..png.width {
            let pixel = png.get_pixel(x, y);
```

```rust
const METADATA_ROWS: u32 = 2;
const TILE_SIZE: u32 = 32;

#[derive(Clone, Debug, PartialEq)]
enum Tag { None, Grass, Danger, Water }

fn tag_from_pixel(pixel: &Pixel) -> Tag {
    match (pixel.r, pixel.g, pixel.b) {
        (0, 255, 0)   => Tag::Grass,
        (255, 0, 0)   => Tag::Danger,
        (0, 0, 255)   => Tag::Water,
        _             => Tag::None,
    }
}

fn is_tag_row(row: u32, height: u32) -> bool {
    // 主图占 [0, height - METADATA_ROWS),标签行占 [.., height)
    row >= height.saturating_sub(METADATA_ROWS)
}

fn process_png_for_import(png: &Png) -> Vec<Tile> {
    let mut tiles = Vec::new();
    
    // 主图:每行像素 → Tile
    for y in 0..png.height {
        if is_tag_row(y, png.height) { continue; }
        for x in 0..png.width {
            let pixel = png.get_pixel(x, y);
            tiles.push(Tile::from_pixel(pixel));
        }
    }
    
    // 标签行:像素颜色 → Tag
    for y in 0..png.height {
        if !is_tag_row(y, png.height) { continue; }
        for x in 0..png.width {
            let pixel = png.get_pixel(x, y);
            let tag = tag_from_pixel(pixel);
            tiles[x].tag = tag;
        }
    }
    
    tiles
}

#[test]
fn test_tag_from_pixel() {
    assert_eq!(tag_from_pixel(&Pixel::new(0, 255, 0)), Tag::Grass);
    assert_eq!(tag_from_pixel(&Pixel::new(255, 0, 0)), Tag::Danger);
    assert_eq!(tag_from_pixel(&Pixel::new(128, 128, 128)), Tag::None);
}

#[test]
fn test_is_tag_row() {
    assert_eq!(is_tag_row(0, 10), false);  // 主图
    assert_eq!(is_tag_row(7, 10), false);  // 主图(7 < 8)
    assert_eq!(is_tag_row(8, 10), true);   // 标签行
    assert_eq!(is_tag_row(9, 10), true);   // 标签行
}
```

重构改动:

1. **魔法数字 → 命名常量**:`METADATA_ROWS`、`TILE_SIZE`
2. **裸数字 tag → enum**:`Tag::Grass` 比 `1` 清晰
3. **提取函数**:`tag_from_pixel`、`is_tag_row`
4. **加测试**:验证关键函数

```rust
// Rust 重构的核心工具:用 trait + impl 拆分大块逻辑

mod tag_grid {
    /// 标签类型(用 enum,不用裸数字)
    #[derive(Clone, Copy, Debug, PartialEq, Eq)]
    pub enum Tag {
        None,
        Grass,
        Danger,
        Water,
        Custom(u8),
    }
    
    /// 像素 → 标签的映射(纯函数,易测试)
    pub fn tag_from_pixel(r: u8, g: u8, b: u8) -> Tag {
        match (r, g, b) {
            (0, 255, 0)   => Tag::Grass,
            (255, 0, 0)   => Tag::Danger,
            (0, 0, 255)   => Tag::Water,
            _             => Tag::None,  // 默认
        }
    }
    
    /// 行号是否是标签行(纯函数,易测试)
    pub fn is_tag_row(row: u32, height: u32) -> bool {
        // height < METADATA_ROWS 时返回 false(避免 underflow)
        const METADATA_ROWS: u32 = 2;
        row >= height.saturating_sub(METADATA_ROWS)
    }
    
    /// 标签 → 像素颜色(用于写回 PNG)
    pub fn pixel_from_tag(tag: Tag) -> (u8, u8, u8) {
        match tag {
            Tag::None    => (0, 0, 0),
            Tag::Grass   => (0, 255, 0),
            Tag::Danger  => (255, 0, 0),
            Tag::Water   => (0, 0, 255),
            Tag::Custom(n) => (n, n, n),
        }
    }
}

#[cfg(test)]
mod tests {
    use super::tag_grid::*;
    
    #[test]
    fn round_trip_tag_pixel() {
        // 验证 tag → pixel → tag 的往返
        for tag in [Tag::None, Tag::Grass, Tag::Danger, Tag::Water] {
            let (r, g, b) = pixel_from_tag(tag);
            let tag_back = tag_from_pixel(r, g, b);
            assert_eq!(tag, tag_back, "round trip failed for {:?}", tag);
        }
    }
    
    #[test]
    fn tag_row_boundary() {
        // 边界:height=2 时,所有行都是标签行
        assert!(is_tag_row(0, 2));
        assert!(is_tag_row(1, 2));
        // 边界:height=3 时,row=0 是主图,row=1,2 是标签行
        assert!(!is_tag_row(0, 3));
        assert!(is_tag_row(1, 3));
        assert!(is_tag_row(2, 3));
        // 边界:height=1 时,主图为空,row=0 是标签行(理论上)
        // 但因为 METADATA_ROWS=2 > 1,saturating_sub 给 0,所以所有行都是标签行
        assert!(is_tag_row(0, 1));
    }
}

fn main() {
    println!("Tag::Grass -> {:?}", tag_grid::pixel_from_tag(tag_grid::Tag::Grass));
    println!("(0, 255, 0) -> {:?}", tag_grid::tag_from_pixel(0, 255, 0));
}
```
