
# Day 477 · 改为每 pass 单次 dispatch(第一部分)

> Day 470-476 把架构铺好了,现在吃架构的红利——Day 477 把"每个 entry 一次 draw call"改成"一帧一次大 draw call",性能提升 5-10 倍。这是 Render Group 抽象的真正回报。

## 0 · 为什么要有这一天

你之前 Render Group 的解释器是这样的:

```
for entry in group.entries:
    if entry is Bitmap:
        glBindTexture(entry.bitmap_id)
        setup_quad_vertices(entry.x, entry.y)
        glDrawArrays(GL_TRIANGLES, 0, 6)   # 每条 entry 一次 draw call
```

如果一帧有 500 个 bitmap entry,你打了 500 次 glDrawArrays。每次 draw call 都有 CPU-GPU 通信开销(~5-10μs),500 次就是 2.5-5ms——光 draw call 就吃掉 60FPS 预算的 15-30%。

优化思路:**把所有 entry 的顶点收集成一个大 buffer,一次 glDrawArrays 画完**。500 次 → 1 次,CPU 通信从 2.5ms 降到 5μs。

这就是 **"batching"**(批处理),是 GPU 渲染优化的第一原则。Vulkan/D3D12/Metal 都强制这种模式,OpenGL 也强烈推荐。

Day 477 做的就是这件事——把 per-entry draw call 改成 per-pass single draw call。

但实现起来不简单。你遇到了三个挑战:

第一,**顶点合并**。500 个 entry 各自有 6 个顶点(两个三角形构成 quad),你要把它们拼成一个 3000 顶点的大 buffer。

第二,**纹理数组**。500 个 entry 用不同纹理,你不能一次 glBindTexture。需要 **"纹理数组"**(texture array)——一个 GL_TEXTURE_2D_ARRAY,把所有纹理叠起来,shader 里用 layer 索引选纹理。

第三,**clip space 变换**。原来每个 entry 在屏幕空间,你 push 时已经是 clip space 坐标。现在 batch 后所有顶点在一个 buffer,要么 push 时就算好 clip space,要么 shader 里算。

Day 477 只做第一部分(顶点合并 + 重新设计 shader)。Day 478 完成纹理数组和细节。

完成这一天之后,你具备了:

- 真实 GPU 性能优化(batching)的实操经验
- 理解为什么 Vulkan 强制 command buffer 模式
- 设计顶点布局(vertex layout)的能力

## 2 · 心智模型

### 类比:邮件批量发送 vs 一封一封发

想象你要发 500 封邮件。两种方式:

**方式 A(per-entry)**:打开邮件客户端 → 写一封 → 发送 → 关闭。重复 500 次。每次"打开/关闭"客户端要 5 秒,500 次 = 42 分钟。

**方式 B(batched)**:打开客户端 → 写 500 封(都放在 outbox)→ 一次性点"发送全部"。一次"打开"5 秒,500 封一起发,总共 1 分钟。

方式 B 快 42 倍。

GPU 渲染完全一样。每次 glDrawArrays 是一次"客户端打开",CPU 要准备命令、提交给驱动、驱动再排队到 GPU。500 次开销惊人。

Batched 模式下,CPU 准备一次大命令,提交一次,驱动排一次队,GPU 一次性处理。开销小几个数量级。

### 为什么 draw call 贵

深入看为什么 draw call 贵。每次 `glDrawArrays` 调用,CPU 做这些事:

1. **API 调用开销**:`glDrawArrays` 是函数调用,通过 GL dispatch table 跳转(~100ns)
2. **参数验证**:GL 检查 vertex array 状态、shader 绑定、framebuffer 状态(~1μs)
3. **命令编码**:把 draw 命令编码到 command buffer(~1μs)
4. **命令提交**:把 command buffer 提交到 driver 队列,可能触发 ioctl(~5μs)
5. **driver → GPU**:driver 把命令送到 GPU ring buffer(~5μs)
6. **GPU 处理**:GPU 真正画(~10μs for 6 vertices)

加起来每次 draw call ~22μs。500 次 = 11ms。60FPS 帧预算才 16.6ms,光 draw call 就吃 66%。

Batched:1 次 command 提交,500 个 quad 在一个大 draw call 里。GPU 处理 3000 顶点 ~50μs(并行度高)。总开销 ~50μs + 命令编码 ~5μs = ~55μs。提升 200 倍。

这就是为什么所有现代 GPU 编程都强调 batching。

### 顶点布局(Vertex Layout)

Batched 模式下,所有顶点在一个 buffer 里连续存储。每个顶点的数据结构叫 **vertex layout**:

```
+--------+---------+-------+
| pos(3f)| uv(2f) | col(4f)|
+--------+---------+-------+
   12B      8B      16B = 36 字节/顶点
```

OpenGL 用 `glVertexAttribPointer` 描述这个布局:

```rust
glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 36, 0);       // pos at offset 0
glVertexAttribPointer(1, 2, GL_FLOAT, GL_FALSE, 36, 12);      // uv at offset 12
glVertexAttribPointer(2, 4, GL_FLOAT, GL_FALSE, 36, 20);      // col at offset 20
```

`stride=36` 是顶点总大小,`offset` 是该属性在顶点内的偏移。

为什么这么布局?**内存对齐 + cache 友好**。每个顶点 36 字节,虽然不是 16/32 对齐,但相邻顶点的同属性隔 36 字节,GPU 访问时 prefetch 友好。

工业级布局会考虑 SIMD 对齐:

```
struct Vertex {
    pos: [f32; 4],        // 16B,把 w 也存上,16 字节对齐
    uv: [f32; 2],         // 8B
    _pad: [f32; 2],       // 8B padding
    color: [f32; 4],      // 16B
}
// 总 48 字节,16 字节对齐
```

Casey 的简单 36 字节布局够用。工业级才需要这种精细优化。

### Shader 改造

之前 per-entry draw call,shader 接受 clip space 坐标(因为 game code 已经算好):

```glsl
in vec3 clip_pos;
void main() {
    gl_Position = vec4(clip_pos, 1.0);
}
```

现在 batched,所有顶点共享一个 view_proj。Shader 接受世界坐标,自己乘矩阵:

```glsl
in vec3 world_pos;
uniform mat4 view_proj;
void main() {
    gl_Position = view_proj * vec4(world_pos, 1.0);
}
```

这样所有顶点用同一个 view_proj(一个 uniform),不用每个 entry 单独算。

Casey 在 Day 477 改这个 shader。原来 game code 里 push 时算 clip space,现在 push world space,shader 里乘 view_proj。

### Texture Array 的预热

Day 477 没完全解决纹理问题——不同 entry 还是用不同 glBindTexture。Casey 在 Day 477 的方案是:**按纹理分组**。把用同一个纹理的 entry 收集到一起,一次 draw call 画完,然后切纹理再画下一组。

```
Group 1 (texture A): 100 entries → 1 draw call
Group 2 (texture B): 200 entries → 1 draw call
Group 3 (texture A): 50 entries → 1 draw call(回头处理)
```

总共 3 次 draw call,比 500 次少很多。这是 **"state sort"**(状态排序)的基本做法。

Day 478 进一步用 texture array 实现真正的 single draw call(所有纹理放一个数组,shader 用 layer index 选)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

Batching 是游戏引擎的标配。Unity 的 SRP Batcher、Unreal 的 Mesh Draw Pipeline、Godot 的 batching 都做这件事。

Unity 的 SRP Batcher 在 2019 年引入,典型场景提升 2-3 倍 FPS。原理和 Casey 一样——把相同 material 的物体 batch 到一起,一次 draw call。

更高级的 batching 包括:

- **GPU instancing**:同一 mesh 画多次(如森林里的树),用 instance ID 区分。
- **Draw indirect**:GPU 自己发起 draw call,完全绕开 CPU(CUDA/Metal Indirect Command Buffer)。
- **Multi-draw indirect(MDI)**:一次 API 调用画多个 mesh,Vulkan 标准。

Casey 在 Day 477 做的是最基础的 vertex batching。后面 HH 不会做 GPU instancing(场景太小用不上),但理解 batching 原理让你看 Unity/Unreal 的优化文档能秒懂。

游戏开发圈有个经验法则:**draw call 数量比顶点数更重要**。1000 个 quad 一个 draw call,比 10 个 quad 100 次 draw call 快。所以 batching 优先于几何细节优化。

### 3.2 · 🎨 图形学视角

图形学里 batching 涉及几个概念。

**Vertex Buffer Object(VBO)**:GPU 内存里的顶点数据。`glBufferData` 上传。

**Index Buffer Object(IBO)**:索引列表,告诉 GPU 用顶点的哪几个。Quad 用索引 `[0,1,2, 2,3,0]` 画两个三角形,只需要 4 个顶点(不用 6 个)。这是 **indexed drawing**,省 33% 顶点。

**Vertex Array Object(VAO)**:封装 VBO + IBO + 顶点布局。一个 VAO 一个 draw call。

**Uniform Buffer Object(UBO)**:shader 全局变量(camera、light)。batched 模式下,所有 entry 共享一个 UBO。

Casey 在 Day 477 用 VBO + IBO,UBO 用旧的 `glUniform`(每帧 set 一次)。VAO 他用了(避免每次 setup 顶点布局)。

图形学还有个相关概念:**vertex fetch bottleneck**。如果 vertex 数据大,GPU 读 vertex 比处理 vertex 慢,变成 memory-bound。解决:精简 vertex layout(用 half/ubyte 替代 float)、用 indexed drawing、压缩顶点数据(NormalAsTwoInt、QTangent)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的 GPU 驱动栈本身用了 batching 思想。Mesa 把 GL 调用攒到 command buffer,buffer 满或显式 flush 时一次性 ioctl 提交。这就是为什么 GL 调用本身相对快——开销在 flush 时。

你可以观察这个过程:

```bash
# 用 GALLIUM 内部工具看 command buffer
GALLIUM_TRACE=1 ./my_game
# 生成 trace 文件,看 batch 怎么攒的

# 用 Mesa 的 GL benchmark
pacman -S mesa-demos
glxgears -info
# 看 FPS,默认就是 batched

# ioctl 计数
strace -e ioctl -c ./my_game
# 输出每秒 ioctl 数。Batched 模式应该明显少于 per-call
```

更底层,DRM 的 `drmCommand` 系列 API 就是 batched 提交。内核 driver 把多个命令排队到 ring buffer,GPU 顺序执行。

Linux I/O 也有 batching 思想——`writev`、`readv` 系统调用允许一次提交多个 buffer,比多次 `write` 快。`io_uring` 进一步,允许异步批量提交 I/O。这都是同一思想:减少"提交次数"开销。

### 3.4 · 🦀 Rust 生态视角

Rust 里写 batched renderer 有几个 idiomatic 选择。

第一,**`Vec<Vertex>` 收集顶点**。简单直接:

```rust
let mut vertices: Vec<Vertex> = Vec::with_capacity(entries.len() * 6);
for entry in &group.entries {
    push_quad_vertices(&mut vertices, entry);
}
gl.BufferData(..., vertices.as_slice() as *const _ as *const _, ...);
```

第二,**`bytemuck::cast_slice` 零拷贝上传**:

```rust
let bytes: &[u8] = bytemuck::cast_slice(&vertices);
gl.BufferData(..., bytes.as_ptr() as *const _, ...);
```

这是 Rust 表达"把 Vec<Vertex> 当字节看"的安全方式。

第三,**`wgpu::Queue::write_buffer`** 替代 GL 的 BufferData:

```rust
queue.write_buffer(&vertex_buffer, 0, bytemuck::cast_slice(&vertices));
```

更现代,跨平台。

第四,**`rend3` 的 `MeshHandle`** 抽象。Mesh 在创建时上传一次 GPU,每帧只引用 handle。这是 retained 模式,比 Casey 的 immediate 模式更工业。

### 4.1 上级(它属于哪个更大抽象?)

- **Batching** —— 把多个小操作合并成一个大操作
- **Amdahl's Law** —— 优化最耗时的部分(draw call)收益最大
- **Pipeline Optimization** —— 减少 CPU 端瓶颈,让 GPU 喂饱

## 5 · 对照与变奏

Casey 在 Day 477 的 batching 思想在不同领域有不同对应:

**网络**:Nagle 算法把多个小 TCP 包攒成大包。HTTP/2 的 multiplexing 把多个请求复用一个 TCP 连接。都是 batching。

**数据库**:批量 INSERT 一万行 vs 单行 INSERT 一万次。前者快 100x。这是 SQL 性能优化第一原则。

**磁盘**:写 1MB 一次 vs 写 1KB 一千次。前者快 10-100x(顺序写 vs 随机写)。SSD 的 page write 也是 batching。

**编译器**:编译 100 个 .c 文件一次性 vs 一个一个。gcc 的 `make -j` 是 batching 的并行版本。

**Web**:HTTP/1.1 keep-alive 复用 TCP 连接。HTTP/2 Server Push 批量推送资源。

理解 batching 是工程师的核心素养。每次你做性能优化,问自己:**有没有多次小操作能合并成一次大操作?** 这通常是最大收益点。

另一个对照:**Vulkan 的设计哲学**。OpenGL 是 immediate(API 调用直接生效),Vulkan 是 retained(命令缓冲,显式提交)。Vulkan 强制 batching 是因为它面向高性能场景——immediate 模式做不到 batching 优化。

Casey 在 HH 里走 OpenGL + 自己 batching,这是用户态模拟 Vulkan 思想。理解了 Casey 的设计,你看 Vulkan API 会觉得"就是 Casey 那套的官方化"。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:为什么 batching 后 shader 要改成"接受世界坐标,内部乘 view_proj",而不是继续接受 clip space 坐标?

**参考解答**:两个理由:

第一,**统一矩阵**。Batched 模式下所有顶点共享一个 view_proj(uniform)。如果每个顶点自己带 clip space,那 view_proj 在 game code 里就要算 500 次(每顶点一次),失去 batching 意义。把矩阵乘法移到 shader 里,GPU 并行算,极快。

第二,**uniform 灵活性**。Camera 在帧内可能变化(比如分两个 pass,一个 3D 一个 UI,各自 view_proj)。如果 shader 接受 clip space,每次切 view_proj 都要重新 push 所有 entry。Batched + shader 算的话,只需要 set uniform,顶点不变。

这就是"延迟计算"思想——把昂贵的变换推迟到最后一刻(shader),前面的 push 只产生数据。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:实现一个 batched vertex collector。给定一个 `Vec<QuadEntry>`(每个 entry 有 x, y, size, color),收集成 `Vec<Vertex>`(每 quad 6 顶点)。Vertex 布局 `[pos(2f), color(4f)]`,共 24 字节。验证:5 个 entry 收集成 30 顶点,buffer 总 720 字节。

完成标准:`cargo run` 输出 buffer 大小,且第一顶点的 pos 和 color 正确。

**参考解答**:

```rust
#[repr(C)]
#[derive(Copy, Clone, Debug, bytemuck::Pod, bytemuck::Zeroable)]
struct Vertex {
    pos: [f32; 2],
    color: [f32; 4],
}

#[derive(Debug)]
struct QuadEntry {
    x: f32, y: f32, size: f32,
    color: [f32; 4],
}

fn collect_vertices(entries: &[QuadEntry]) -> Vec<Vertex> {
    // 预分配:每 entry 6 顶点
    let mut verts = Vec::with_capacity(entries.len() * 6);
    
    for e in entries {
        let x = e.x;
        let y = e.y;
        let s = e.size;
        let c = e.color;
        
        // quad 4 个角(左下、右下、右上、左上)
        let p00 = [x, y];
        let p10 = [x + s, y];
        let p11 = [x + s, y + s];
        let p01 = [x, y + s];
        
        // 两个三角形,共 6 顶点
        // 三角形 1: 左下、右下、右上
        verts.push(Vertex { pos: p00, color: c });
        verts.push(Vertex { pos: p10, color: c });
        verts.push(Vertex { pos: p11, color: c });
        // 三角形 2: 左下、右上、左上
        verts.push(Vertex { pos: p00, color: c });
        verts.push(Vertex { pos: p11, color: c });
        verts.push(Vertex { pos: p01, color: c });
    }
    
    verts
}

fn main() {
    let entries = vec![
        QuadEntry { x: 0.0,  y: 0.0,  size: 10.0, color: [1.0, 0.0, 0.0, 1.0] },
        QuadEntry { x: 20.0, y: 0.0,  size: 10.0, color: [0.0, 1.0, 0.0, 1.0] },
        QuadEntry { x: 40.0, y: 0.0,  size: 10.0, color: [0.0, 0.0, 1.0, 1.0] },
        QuadEntry { x: 60.0, y: 0.0,  size: 10.0, color: [1.0, 1.0, 0.0, 1.0] },
        QuadEntry { x: 80.0, y: 0.0,  size: 10.0, color: [1.0, 0.0, 1.0, 1.0] },
    ];
    
    let verts = collect_vertices(&entries);
    println!("Collected {} vertices", verts.len());
    println!("Buffer size: {} bytes", verts.len() * std::mem::size_of::<Vertex>());
    println!("First vertex: {:?}", verts[0]);
    println!("Last vertex: {:?}", verts[verts.len()-1]);
    
    // 用 bytemuck 转 bytes(模拟上传 GPU)
    let bytes: &[u8] = bytemuck::cast_slice(&verts);
    println!("Bytes len: {}", bytes.len());
    
    // 假装的"一次 draw call"
    println!("glDrawArrays(GL_TRIANGLES, 0, {})", verts.len());
}
```

为什么这么写:`bytemuck::Pod` 和 `Zeroable` 是 marker trait,告诉编译器 Vertex 是 plain old data(无 padding、无指针),可以安全 cast。这是 Rust 表达"序列化"的安全方式。

## 8 · Rust / Arch 落地代码

下面是 Day 477 完整的 batched renderer Rust 实现。

```rust
// ========================================
// Vertex 布局
// ========================================

#[repr(C)]
#[derive(Copy, Clone, Debug, bytemuck::Pod, bytemuck::Zeroable)]
struct Vertex {
    pos: [f32; 3],       // 世界坐标
    uv: [f32; 2],        // 纹理坐标
    color: [f32; 4],     // 顶点色调制
}

impl Vertex {
    const LAYOUT: &'static [(&'static str, u32, u32)] = &[
        // (name, components, offset)
        ("pos",   3, 0),
        ("uv",    2, 12),
        ("color", 4, 20),
    ];
    
    const STRIDE: u32 = 36;
}

// ========================================
// Quad 顶点生成
// ========================================

#[derive(Debug)]
struct BitmapEntry {
    bitmap_id: u32,
    x: f32, y: f32, z: f32,
    w: f32, h: f32,
    color: [f32; 4],
}

fn push_quad_vertices(verts: &mut Vec<Vertex>, e: &BitmapEntry) {
    // quad 4 角(世界坐标)
    let x = e.x;
    let y = e.y;
    let z = e.z;
    let w = e.w;
    let h = e.h;
    
    let p00 = [x,     y,     z];   // 左下前
    let p10 = [x + w, y,     z];   // 右下前
    let p11 = [x + w, y + h, z];   // 右上前
    let p01 = [x,     y + h, z];   // 左上前
    
    // UV:纹理坐标 (0,0) 左下到 (1,1) 右上
    let uv00 = [0.0, 0.0];
    let uv10 = [1.0, 0.0];
    let uv11 = [1.0, 1.0];
    let uv01 = [0.0, 1.0];
    
    // 两个三角形,6 顶点
    let c = e.color;
    // 三角形 1: 左下、右下、右上
    verts.push(Vertex { pos: p00, uv: uv00, color: c });
    verts.push(Vertex { pos: p10, uv: uv10, color: c });
    verts.push(Vertex { pos: p11, uv: uv11, color: c });
    // 三角形 2: 左下、右上、左上
    verts.push(Vertex { pos: p00, uv: uv00, color: c });
    verts.push(Vertex { pos: p11, uv: uv11, color: c });
    verts.push(Vertex { pos: p01, uv: uv01, color: c });
}

// ========================================
// Batched renderer
// ========================================

struct BatchedRenderer {
    vertex_buffer: Vec<Vertex>,
    draw_call_count: u32,
}

impl BatchedRenderer {
    fn new() -> Self {
        Self {
            vertex_buffer: Vec::new(),
            draw_call_count: 0,
        }
    }
    
    fn submit(&mut self, entries: &[BitmapEntry]) {
        // 清空 buffer
        self.vertex_buffer.clear();
        
        // 收集所有顶点
        self.vertex_buffer.reserve(entries.len() * 6);
        for e in entries {
            push_quad_vertices(&mut self.vertex_buffer, e);
        }
        
        // 上传到 GPU(假装)
        let bytes: &[u8] = bytemuck::cast_slice(&self.vertex_buffer);
        println!("Upload {} bytes ({} vertices) to GPU",
                 bytes.len(), self.vertex_buffer.len());
        
        // 单次 draw call
        println!("glDrawArrays(GL_TRIANGLES, 0, {})", self.vertex_buffer.len());
        self.draw_call_count += 1;
    }
    
    fn stats(&self) -> (u32, usize) {
        (self.draw_call_count, self.vertex_buffer.len())
    }
}

// ========================================
// 性能对比
// ========================================

fn bench_per_entry(entries: &[BitmapEntry]) -> u32 {
    let mut draws = 0;
    for _ in entries {
        // 模拟 per-entry draw call
        draws += 1;
    }
    draws
}

fn bench_batched(entries: &[BitmapEntry]) -> u32 {
    let mut r = BatchedRenderer::new();
    r.submit(entries);
    r.stats().0
}

fn main() {
    let entries: Vec<BitmapEntry> = (0..500).map(|i| BitmapEntry {
        bitmap_id: i % 5,
        x: (i % 50) as f32 * 10.0,
        y: (i / 50) as f32 * 10.0,
        z: 0.0,
        w: 8.0,
        h: 8.0,
        color: [1.0; 4],
    }).collect();
    
    println!("=== {} entries ===", entries.len());
    
    let per_entry_draws = bench_per_entry(&entries);
    let batched_draws = bench_batched(&entries);
    
    println!("Per-entry: {} draw calls", per_entry_draws);
    println!("Batched:   {} draw call", batched_draws);
    println!("Reduction: {:.0}x fewer draws", 
             per_entry_draws as f64 / batched_draws as f64);
    
    // 假装:每个 draw call 5μs 开销
    let per_entry_us = per_entry_draws * 5;
    let batched_us = batched_draws * 5 + 50; // +50μs 顶点收集
    println!("\nEstimated CPU time:");
    println!("Per-entry: {} μs ({:.2} ms)", per_entry_us, per_entry_us as f64 / 1000.0);
    println!("Batched:   {} μs ({:.2} ms)", batched_us, batched_us as f64 / 1000.0);
    println!("Speedup:   {:.1}x", per_entry_us as f64 / batched_us as f64);
}
```

出错怎么办:

- **`bytemuck::Pod must be implemented`** —— 你的 Vertex 有 padding 或非 Pod 字段。`#[repr(C)]` + 所有字段是 f32/u32 才能是 Pod。
- **顶点顺序错导致三角形"反面"** —— OpenGL 默认 back-face culling(CW 是正面)。如果你的三角形显示不出来,检查顶点顺序是否是 CCW(逆时针)。
- **顶点数不对** —— 6 顶点 quad vs 4 顶点 + 索引。如果用索引,顶点 4 个、索引 6 个。
