
# Day 499 · 统一调试与编辑器模式

> Casey 在 Day 200+ 加了"debug overlay"(FPS、entity 计数、内存图),在 Day 440+ 加了"editor"(放置 entity、调参、保存)。本来这两个是分开的——按 F1 进 debug,F2 进 editor。今天 Casey 意识到它们其实是**同一个东西的两个面**,合在一起代码量减半、用户体验翻倍。

## 0 · 为什么要有这一天

你已经做了几个月的"游戏内编辑器"和"游戏内调试器"。它们的代码大概长这样:

```rust
// 一份独立的代码路径
fn update_debug_overlay(...) { ... }
fn render_debug_overlay(...) { ... }

// 另一份独立的代码路径
fn update_editor(...) { ... }
fn render_editor(...) { ... }

// 主循环
match mode {
    Mode::Play => { update_play(...); render_play(...); }
    Mode::Debug => { update_play(...); update_debug_overlay(...); render_play(...); render_debug_overlay(...); }
    Mode::Editor => { update_play(...); update_editor(...); render_play(...); render_editor(...); }
}
```

一开始这看起来很自然。但几个月后你发现:

- **两套 UI 系统**:debug overlay 有一套 immediate-mode UI,editor 又有一套,有 30% 代码重复
- **两套输入处理**:debug 用 F1-F12,editor 用 WASD + 鼠标,但都靠同一个 `InputState`
- **两套 entity 选择**:debug 点击 entity 看变量,editor 点击 entity 编辑位置——核心逻辑都是"屏幕坐标→entity"
- **状态切换 bug**:从 editor 切回 play,某些状态没清,entity 卡住;从 debug 切到 editor,editor 残留了 debug 高亮

Casey 今天意识到:**debug 和 editor 共享 80% 的代码**。它们都是"在运行中的游戏上,叠加一层交互",区别只是"叠加层做什么"。把它们合并成一个"**dev mode**",用一个 `enum DevAction` 描述具体动作(查看、编辑、选择),代码量减半,bug 减少,UX 更一致。

心理锚点:看完今天,你能做到:**识别"两个看起来不同但本质相同的模式",合并它们**。你还能解释什么是"状态机(state machine)"、"immediate-mode UI 的优势"、"模态(modal)vs 非模态交互"。

## 1 · Casey 今天做了什么

Casey 的合并过程分四步:

第一步,他列出 debug 和 editor 共有的功能:immediate-mode UI、entity 选择、键盘/鼠标输入、overlay 渲染。这些是"公共底座"。

第二步,他定义一个统一的 `DevMode` 枚举:

```rust
enum DevMode {
    Off,           // 玩游戏,无开发覆盖
    Inspect,       // 原 debug:看变量、性能图
    Edit,          // 原 editor:改 entity、保存
}
```

第三步,把所有 update/render 函数合并:

```rust
fn update_dev_mode(mode: DevMode, ...) {
    // 公共输入处理
    handle_dev_input(...);
    match mode {
        DevMode::Inspect => update_inspect_only(...),
        DevMode::Edit => update_edit_specifics(...),
        _ => {}
    }
}
```

第四步,统一 UI 系统——所有 dev UI 都用同一套 immediate-mode API:`ui_button(...)`, `ui_slider(...)`, `ui_text(...)`。

整集 Casey 一直在删代码——总共删了 ~600 行重复实现,加了 ~200 行统一逻辑,净减 400 行。

## 2 · 心智模型

### 类比:debug 和 editor 是"医生的听诊器和手术刀"

医生看病人,有两种模式:

- **诊断(听诊器)**:只看不动,测心跳、血压、体温
- **治疗(手术刀)**:直接干预,开刀、给药、植入

它们都是"对人体的交互",区别只是"动不动"。本质上**诊断是治疗的子集**——你不能在没诊断的情况下治疗,治疗时也同时在诊断。

游戏里:

- **debug overlay** = 诊断,只读
- **editor** = 治疗,可写
- **play** = 病人不在医院(无交互)

合并后,"dev mode"是个连续光谱——Inspect 是只读的 Edit,Edit 是可写的 Inspect。

### 严谨原理:Immediate-Mode UI(IMM)

Casey 在 Day 200+ 引入了 **immediate-mode UI**(立刻模式 UI,简称 IM UI)。这是和"retained-mode UI"(保留模式)相对的概念。

**Retained-mode UI**(传统,如 Qt、Win32):
- UI 是一棵对象树(`Button`、`TextBox` 等)
- 你创建一次,框架保留它,你通过 setter 修改
- 渲染时框架遍历树画

**Immediate-mode UI**(现代,如 Dear ImGui):
- UI 是**每帧重新声明**的函数调用
- 你写 `if ui_button("Save") { save(); }`,框架立刻画按钮、立刻处理点击、立刻返回布尔值
- 没有"对象树"——UI 状态全部在你的代码里

为什么 IM UI 适合游戏:

1. **零状态同步 bug**:retained mode 最痛的是"我的数据和 UI 显示的数据不同步",IM UI 每帧重建,无此问题
2. **代码和 UI 一一对应**:看一眼代码就知道屏幕长啥样
3. **天然支持"模态"**:你只在某个 mode 下调用 `if mode == Edit { ui_button(...); }`,不需要"隐藏控件"这种操作

Casey 的合并就是利用 IM UI 的这个特性:

```rust
fn render_dev_ui(mode: DevMode) {
    ui_text(&format!("FPS: {}", fps));  // 总是显示

    match mode {
        DevMode::Inspect => {
            ui_text(&format!("Entity count: {}", entity_count));
        }
        DevMode::Edit => {
            ui_text(&format!("Entity count: {}", entity_count));
            if ui_button("Save") { save_world(); }
            if ui_button("Add Entity") { add_entity(); }
        }
        _ => {}
    }
}
```

Inspect 的所有 UI 在 Edit 里也显示——因为 Edit 是 Inspect 的超集。这就是"统一"的本质。

### 状态机视角

debug/editor 合并背后是一个**有限状态机(finite state machine, FSM)**:

```
       F1
   +--------+
   |        v
[Play]   [Inspect]
   ^        |
   |   F2   |
   +--------+
            |
       F2   |
            v
         [Edit]
```

三个状态:Play、Inspect、Edit。按键转换。FSM 是表达"模式"的最清晰方式——Casey 用一个 enum + match 表达,bug 几乎为零。

如果不合并,debug 和 editor 各自是独立 FSM,它们之间转换有 6 种路径(2x3),每条路径都可能漏掉某种状态清理。合并后只有 1 个 FSM,3 个状态,3 条转换,极简。

### 输入处理的关键挑战

合并时最大的坑是**输入路由**。在 Play 模式:

- WASD 移动玩家
- 鼠标点击攻击

在 Inspect 模式:

- WASD 移动相机(覆盖 Play 的 WASD)
- 鼠标点击选中 entity(覆盖攻击)

在 Edit 模式:

- WASD 移动相机
- 鼠标点击放置 entity

如果 WASD 同时被 Play 和 DevMode 消费,玩家会在"编辑时同时移动"——bug。Casey 的解决方法是**"输入消耗"模式**:

```rust
fn handle_input(input: &mut InputState, mode: DevMode) {
    // DevMode 优先消费输入
    if mode != DevMode::Off {
        if input.consume_key(Key::W) {
            move_camera_forward();
            return;  // ← Play 不会看到 W
        }
    }
    // Play 才看到剩余输入
    if input.is_key_down(Key::W) {
        move_player_forward();
    }
}
```

`consume_key` 把按键标记为"已消费",后续 `is_key_down` 不会再看到。这是事件系统的经典设计——游戏引擎里叫"**input focus stack**"。

### 模态 vs 非模态

UI 设计里有两种交互哲学:

- **模态(modal)**:你必须先"退出当前模式"才能做别的(如对话框,关掉才能点别的)
- **非模态(modeless)**:多个交互可以同时进行(如 IDE,代码、终端、文件树同时可用)

Casey 的 dev mode 是**轻度模态**——按 F2 进 Edit,WASD 不能同时移动玩家(被相机抢走)。这种"按键切换模式"对开发者友好(明确),但对玩家不友好(要切回去)。

商业游戏如《Minecraft》的创造模式是**非模态**——飞行、放置方块、攻击同时可用,无需切换。这种设计更复杂但更流畅。Casey 选择模态,因为 dev mode 不是给最终用户用的。

---

**总结**:debug 和 editor 是同一个抽象的两个面,合并成 dev mode 用一个 enum + match 表达,代码减半。IM UI 让合并自然——每帧重建,不需要"隐藏控件"。输入用"消耗模式"避免冲突。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏内调试 UI 是商业游戏引擎的标配。Unreal 有 `drawDebugString`、`drawDebugLine`,Unity 有 `OnDrawGizmos`,Godot 有 `draw_gizmo`。这些都在游戏运行时画辅助线/文字/形状——本质上都是 dev mode。

游戏开发圈对 dev mode 的设计经验:

- **总是可访问**:任何 build(包括 release)都应该能用某种快捷键打开 dev mode,方便现场调试
- **零性能开销**:dev mode 关闭时,所有 dev 代码应该被 `#[cfg]` 编译掉,运行时不存在
- **崩溃隔离**:dev mode 里的 bug 不应该让游戏崩溃——dev 是辅助,不是关键路径

Casey 的实现满足这三条。Rust 的 `cfg!(debug_assertions)` 让 dev 代码在 release 不存在,这是 Rust 表达"dev only"的惯用法:

```rust
if cfg!(debug_assertions) && mode != DevMode::Off {
    render_dev_ui(mode);
}
```

### 3.2 · 🎨 图形学视角

dev mode 的渲染涉及几个图形学概念:

- **overlay 渲染**:在游戏画面上叠加 UI,通常用正交投影(orthographic projection,无透视)
- **depth test 禁用**:UI 应该永远在画面之上,关闭深度测试
- **alpha blending**:UI 元素半透明,需要混合
- **字体光栅化**:UI 文字需要字体加载和实时绘制

Casey 在 Day 200+ 已经实现了 overlay 渲染管线。今天的合并不涉及图形学细节,只是把"两套调用 overlay 的代码"合成"一套调用,带 mode 参数"。

### 3.3 · 🐧 Linux 系统编程视角

dev mode 的输入处理和 Linux 的 input subsystem 有关。Linux 上读取键盘鼠标的方式:

- **evdev**:`/dev/input/event*`,原始事件,需要解析 scancode
- **libinput**:封装 evdev,提供高级 API
- **winit**(Rust):跨平台窗口库,封装 libinput/X11/Wayland

Casey 用 winit 处理输入(在 Rust 版本里)。dev mode 的"按键消耗"逻辑在 winit 之上,不影响系统层。

如果 dev mode 涉及文件操作(保存编辑),Linux 的 `inotify` 可以监控资产目录,实现"editor 保存→游戏自动热重载"。Casey 的 Day 460+ 热重载就是这么做的。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 dev mode 的 enum + match 是最自然的:

```rust
#[derive(Clone, Copy, PartialEq)]
pub enum DevMode {
    Off,
    Inspect,
    Edit,
}

fn update(mode: DevMode) {
    match mode {
        DevMode::Off => {},        // Play 走另一条路径
        DevMode::Inspect => update_inspect(),
        DevMode::Edit => update_edit(),
    }
}
```

Rust 的 `match` 强制穷尽——加新变体时编译器报错,这是 C/C++ 的 switch case 没有的安全网。

Rust 生态里 immediate-mode UI 库:

- **`egui`**(Dear ImGui 的 Rust 版):最流行,bevy 和 macroquad 都集成了
- **`iced`**:Elm 架构,retained + 响应式
- **`druid`**(已废弃):数据驱动,曾流行
- **`gpui`**(Zed 编辑器用):高性能,GPU 加速

Casey 不用任何库,自己手写最小 IM UI(只有 button、slider、text 三个原语)。这是教学考虑——让观众理解原理。

Rust 表达"按键消耗"模式:

```rust
pub struct InputState {
    keys_pressed: HashSet<KeyCode>,
    keys_consumed: HashSet<KeyCode>,
}

impl InputState {
    pub fn consume_key(&mut self, key: KeyCode) -> bool {
        if self.keys_pressed.contains(&key) && !self.keys_consumed.contains(&key) {
            self.keys_consumed.insert(key);
            true
        } else {
            false
        }
    }

    pub fn is_key_down(&self, key: KeyCode) -> bool {
        self.keys_pressed.contains(&key) && !self.keys_consumed.contains(&key)
    }
}
```

每帧开始时清空 `keys_consumed`,这样按键在下一帧又可用。

### Lv1 · 概念辨析

**题**:下面哪几条是 immediate-mode UI 的特征?哪几条是 retained-mode UI 的?

a) UI 元素是对象,持久存在
b) 每帧重建 UI 树
c) setter 修改属性
d) 渲染时遍历对象树
e) UI 代码和屏幕布局一一对应

**参考解答**:b, e 是 IM UI;a, c, d 是 retained UI。
- IM UI 没有"对象树",每帧调用 `if ui_button(...) {...}` 直接画+处理
- retained UI 有对象树,你创建一次后续 set/modify

为什么这么想:核心判据是"UI 是否持久存在"。如果 UI 元素是 struct 字段,就是 retained;如果 UI 是函数调用,就是 immediate。

### Lv2 · 动手实践

**题**:用 Rust 实现一个最小 immediate-mode UI,有一个 button 函数和 text 函数。button 返回 bool(是否点击),text 显示字符串。再写一个 demo,3 个按钮计数器(每个按钮有自己的计数),一个文字显示"点击总数"。

**参考解答**:

```rust
// 假设我们有一个 ImContext 处理鼠标点击命中
struct ImContext {
    mouse_pos: (i32, i32),
    mouse_clicked: bool,
    next_y: i32,  // 自动布局:每个 UI 元素往下堆叠
}

impl ImContext {
    fn button(&mut self, label: &str, x: i32, w: i32, h: i32) -> bool {
        let y = self.next_y;
        self.next_y += h + 4;  // 下一个元素往下
        // 命中检测
        let hit = self.mouse_pos.0 >= x && self.mouse_pos.0 < x + w
               && self.mouse_pos.1 >= y && self.mouse_pos.1 < y + h;
        // 实际渲染(伪)
        println!("  [draw button '{}' at ({},{},{},{})]", label, x, y, w, h);
        hit && self.mouse_clicked
    }

    fn text(&mut self, msg: &str) {
        let y = self.next_y;
        self.next_y += 20;
        println!("  [draw text '{}' at ({},{}))]", msg, 0, y);
    }
}

fn main() {
    let mut counts = [0u32; 3];
    let mut total = 0;

    // 模拟 3 帧
    for frame in 0..3 {
        println!("--- Frame {frame} ---");
        let mut ctx = ImContext {
            mouse_pos: (10, 10 + 24 * (frame % 3)),  // 鼠标在不同位置
            mouse_clicked: true,
            next_y: 0,
        };

        for i in 0..3 {
            if ctx.button(&format!("Btn {i} +1"), 0, 100, 20) {
                counts[i] += 1;
                total += 1;
            }
        }
        ctx.text(&format!("Total clicks: {total}"));
    }

    println!("final counts: {:?}", counts);
    println!("final total: {total}");
}
```

为什么这么写:每帧重建 ctx,counts 和 total 在 frame 之外(持久状态)。IM UI 的核心是"渲染 + 输入合并",`button` 函数同时画按钮和检测点击。

## 8 · Rust / Arch 落地代码

下面是 dev mode 的完整最小实现,演示今天的合并思路。

```rust
// src/dev_mode.rs

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum DevMode {
    Off,        // 玩游戏,无 dev
    Inspect,    // 只读 dev:看变量
    Edit,       // 可写 dev:改 entity
}

/// 输入状态——支持 consume 模式
#[derive(Default)]
pub struct InputState {
    keys_pressed: std::collections::HashSet<u32>,
    keys_consumed: std::collections::HashSet<u32>,
    mouse_pos: (i32, i32),
    mouse_clicked: bool,
}

impl InputState {
    /// 消费按键——如果按下且未被消费,标记为消费并返回 true
    pub fn consume_key(&mut self, key: u32) -> bool {
        if self.keys_pressed.contains(&key) && !self.keys_consumed.contains(&key) {
            self.keys_consumed.insert(key);
            true
        } else {
            false
        }
    }

    /// 检查按键是否仍可用(被消费后返回 false)
    pub fn is_key_down(&self, key: u32) -> bool {
        self.keys_pressed.contains(&key) && !self.keys_consumed.contains(&key)
    }

    /// 每帧开始时调用,清空消费记录
    pub fn end_frame(&mut self) {
        self.keys_consumed.clear();
        self.mouse_clicked = false;
    }
}

/// 游戏世界(简化)
pub struct World {
    pub player_pos: (f32, f32),
    pub camera_pos: (f32, f32),
    pub entities: Vec<(f32, f32)>,  // entity 位置
}

/// 公共 dev 输入处理
fn handle_dev_input(mode: DevMode, input: &mut InputState, world: &mut World) {
    if mode == DevMode::Off {
        return;  // Play 模式不处理 dev 输入
    }

    // Inspect 和 Edit 都让 WASD 移动相机
    const KEY_W: u32 = 17;
    const KEY_A: u32 = 30;
    const KEY_S: u32 = 31;
    const KEY_D: u32 = 32;

    if input.consume_key(KEY_W) { world.camera_pos.1 -= 1.0; }
    if input.consume_key(KEY_S) { world.camera_pos.1 += 1.0; }
    if input.consume_key(KEY_A) { world.camera_pos.0 -= 1.0; }
    if input.consume_key(KEY_D) { world.camera_pos.0 += 1.0; }

    // 鼠标点击——选中或放置 entity
    if input.mouse_clicked {
        match mode {
            DevMode::Inspect => {
                println!("[Inspect] clicked at {:?}", input.mouse_pos);
            }
            DevMode::Edit => {
                // 把屏幕坐标转世界坐标(简化:直接用)
                world.entities.push((
                    input.mouse_pos.0 as f32,
                    input.mouse_pos.1 as f32,
                ));
                println!("[Edit] placed entity at {:?}", input.mouse_pos);
            }
            _ => {}
        }
    }
}

/// Play 输入处理(只在 Play 模式生效)
fn handle_play_input(input: &mut InputState, world: &mut World) {
    const KEY_W: u32 = 17;
    const KEY_A: u32 = 30;
    const KEY_S: u32 = 31;
    const KEY_D: u32 = 32;
    if input.is_key_down(KEY_W) { world.player_pos.1 -= 1.0; }
    if input.is_key_down(KEY_S) { world.player_pos.1 += 1.0; }
    if input.is_key_down(KEY_A) { world.player_pos.0 -= 1.0; }
    if input.is_key_down(KEY_D) { world.player_pos.0 += 1.0; }
}

/// 主更新函数——根据 mode 分发
pub fn update(mode: DevMode, input: &mut InputState, world: &mut World) {
    // dev 模式优先消费输入
    handle_dev_input(mode, input, world);

    // Play 模式处理剩余输入
    if mode == DevMode::Off {
        handle_play_input(input, world);
    }
}

/// IM UI 渲染——根据 mode 显示不同内容
pub fn render_ui(mode: DevMode, world: &World) {
    println!("--- UI ---");
    println!("Camera: ({:.1}, {:.1})", world.camera_pos.0, world.camera_pos.1);

    match mode {
        DevMode::Off => println!("[Play mode]"),
        DevMode::Inspect => {
            println!("[Inspect]");
            println!("  Player pos: ({:.1}, {:.1})", world.player_pos.0, world.player_pos.1);
            println!("  Entity count: {}", world.entities.len());
        }
        DevMode::Edit => {
            println!("[Edit]");
            println!("  Player pos: ({:.1}, {:.1})", world.player_pos.0, world.player_pos.1);
            println!("  Entity count: {}", world.entities.len());
            println!("  [Button] Save");
            println!("  [Button] Clear All");
        }
    }
}

fn main() {
    let mut mode = DevMode::Off;
    let mut input = InputState::default();
    let mut world = World {
        player_pos: (0.0, 0.0),
        camera_pos: (0.0, 0.0),
        entities: vec![],
    };

    // 模拟 3 帧:Play, Inspect, Edit
    let frames = [
        (DevMode::Off,      vec![17u32]),          // Play,W
        (DevMode::Inspect,  vec![30u32]),          // Inspect,A
        (DevMode::Edit,     vec![]),               // Edit,鼠标点击
    ];

    for (i, (m, keys)) in frames.iter().enumerate() {
        mode = *m;
        input.keys_pressed.clear();
        for k in keys { input.keys_pressed.insert(*k); }
        if i == 2 { input.mouse_clicked = true; input.mouse_pos = (100, 200); }

        println!("=== Frame {i} (mode = {:?}) ===", mode);
        update(mode, &mut input, &mut world);
        render_ui(mode, &world);
        input.end_frame();
    }

    println!("Final player pos: {:?}", world.player_pos);   // 应该是 (0, -1)
    println!("Final camera pos: {:?}", world.camera_pos);   // 应该是 (-1, 0)
    println!("Final entities: {:?}", world.entities);       // 应该有 1 个
}
```

注释要点:

- `DevMode` 用 enum,3 个状态清晰
- `InputState::consume_key` 实现"输入消耗",防止 dev 和 play 同时消费同一个按键
- `handle_dev_input` 和 `handle_play_input` 分别处理——前者优先
- `render_ui` 用 match mode 显示不同 UI,Edit 显示 Inspect 的所有内容 + 额外按钮(超集)
- `end_frame` 每帧清空,准备下一帧

### Arch 命令

如果你想看 dev mode 在不同 build 下的行为:

```bash
$ cargo build --features dev_tools  # dev 工具打开
$ cargo build                       # 默认 dev 关闭(用 cfg 控制)
```

`Cargo.toml`:

```toml
[features]
dev_tools = []
```

代码里:

```rust
#[cfg(feature = "dev_tools")]
mod dev_mode;
```

`#[cfg(feature = "dev_tools")]` 让 dev_mode 模块只在 dev_tools feature 打开时编译。Release build 不带这个 feature,dev 代码完全不存在,既小又快。

如果想看 release build 的 binary 大小:

```bash
$ cargo build --release --features dev_tools
$ ls -lh target/release/game
-rwxr-xr-x 2.3M ... target/release/game

$ cargo build --release
$ ls -lh target/release/game
-rwxr-xr-x 1.8M ... target/release/game  # 小 500KB,因为 dev 代码没了
```

差异 500KB 就是 dev mode 的"重量"。商业游戏发布时这个差异可以更小(精简 dev UI)或为 0(dev 完全剥离)。
