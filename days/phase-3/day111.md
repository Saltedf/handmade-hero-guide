
# Day 111 · 分辨率无关的地面区块

> Day 109 Casey 给整个 framebuffer 做了分辨率无关化——内部固定 960×540,最后整体缩放 blit 到任意窗口。但这有个遗漏:**地面**是分 tile / chunk 渲染的,每个 tile 自己有纹理、自己有位置。如果你在内部 framebuffer 上一像素一像素画 tile,窗口拉到 4K 时这些 tile 边界全是锯齿,因为它们没有"跟着 scale_factor 长大"。今天 Casey 把地面系统改造成**分辨率无关**:地面 chunk 的内容、布局、采样都用**世界坐标 + 米为单位**,渲染时按当前 scale_factor 实时算屏幕矩形。这样窗口任意拉伸,地面比例锁死,锯齿消失,HiDPI 屏幕也能锐利显示。

## 0 · 为什么要有这一天

Day 109 解决了"整个画面"的分辨率无关——固定内部 framebuffer,最后缩放 blit。但这套方案有个隐藏代价:**内部 framebuffer 是 960×540,所有 tile 必须画到这个固定分辨率上**。如果你把窗口拉到 4K(3840×2160),内部 framebuffer 还是 960×540,blit 放大 4 倍,每个内部像素变成 4×4 屏幕像素——**所有 tile 纹理在 4K 上是模糊的**。

更糟的是 HiDPI 屏幕。一台 Retina MacBook 的 scale_factor 是 2.0——窗口管理器告诉你的程序"逻辑分辨率 1440×900",但实际 framebuffer 是 2880×1800。如果你按 1440×900 画 tile,winit 给你的也是 1440×900 的画布,但你写出去的每个像素最终被显示器驱动拉伸成 2×2 物理像素——**锯齿明显**。游戏看起来像 1990 年代的 320×240 像素艺术,不管你的显卡多快。

工业级游戏不这么做。Unreal、Unity、Godot 都让游戏世界用**米为单位**(world unit),渲染时根据**当前 framebuffer 物理分辨率**和**相机缩放**实时计算每个 chunk 占的像素矩形。窗口拉大,chunk 像素矩形跟着变大,纹理采样更精细;窗口缩小,矩形跟着变小,自动 mipmap 降采样。**chunk 永远以"它本应该在的物理大小"显示**,不存在"先画小再拉伸"的模糊。

Casey 今天做的事就是这套思路:**把地面 chunk 从"画在固定 framebuffer 上的像素"改成"活在世界坐标系里的米单位矩形,渲染时换算到当前屏幕像素"**。这是从"软件渲染器时代"过渡到"GPU 时代"必经的一步——GPU 渲染管线的 vertex shader 干的就是这件事(把世界坐标乘 MVP 矩阵得到屏幕坐标)。

完成今天后,你将拥有:

- **HiDPI 处理能力**:能在 Retina 屏、4K 屏、超宽屏上让游戏画面保持物理大小一致,不模糊不锯齿
- **World-space 思维**:理解"游戏世界的物体用米为单位,屏幕只是观察窗口"这一现代图形学核心抽象
- **winit scale_factor 实战**:会用 Rust winit 的 `Window::scale_factor()` 和 `WindowEvent::ScaleFactorChanged` 处理 DPI 变化(玩家拖动窗口到不同 DPI 屏幕)
- **Arch Linux 测试技能**:用 `GDK_SCALE` / `QT_SCALE_FACTOR` 环境变量在你的开发机上模拟 HiDPI 屏幕,无需真有 Retina 屏

## 1 · Casey 今天做了什么(HH 脉络,简述)

Casey 在视频里做的事可以归纳为四步。

第一步,他**审视现有地面代码**。Phase 3 前期(Day 079~087)Casey 把地面分成 tile,每个 tile 是一张 32×32 像素的 bitmap,渲染时直接把 tile 画到内部 framebuffer 的某个像素位置。这套方案在 960×540 的内部 framebuffer 上跑得没问题,但 Casey 一直不满意——"如果玩家在 4K 上想看更精细的 tile 怎么办?现在我只能改 INTERNAL_WIDTH,但那会让所有 UI 也跟着改"。

第二步,他**重新定义 chunk 的存储模型**。原来 chunk 是 `(pixel_x, pixel_y, bitmap)`,现在改成 `(world_x, world_y, bitmap)`——位置用**世界坐标的米单位**,不用屏幕像素。chunk 的 bitmap 本身是**资产级数据**(独立于屏幕分辨率),只在采样时根据当前 scale 换算。

第三步,他**改造渲染路径**。原来 `draw_chunk(chunk, framebuffer)` 直接 blit bitmap 到 framebuffer。现在改成 `draw_chunk(chunk, framebuffer, scale_factor, camera)`——先算 chunk 在世界坐标系里占的矩形,再乘相机矩阵和 scale_factor 得到屏幕像素矩形,最后用 bilinear 采样 bitmap 画到屏幕矩形。

第四步,他**处理 scale_factor 动态变化**。winit 在窗口跨屏(DPI 不同)时发 `ScaleFactorChanged` 事件。Casey 让 renderer 监听这个事件,scale_factor 一变就重算所有屏幕矩形(无需重新生成 chunk 数据)。视频里他把窗口从 1080p 主屏拖到 4K 副屏,地面自动变锐利,无任何卡顿——演示效果惊艳。

## 2 · 心智模型

### 2.1 费曼类比:GPS 地图

想象你用 Google Maps 看北京。地图数据存的是什么?**地理坐标**(经纬度,等价于我们的世界坐标)。地图显示多大?**取决于你缩放等级**(等价于 scale_factor)和**屏幕大小**。

zoom = 10 时整个北京在一个手机屏里,天安门是 4 个像素的小点。zoom = 18 时天安门广场铺满整个屏幕,你能看见每条路。但地图**底层数据没变**——还是那套经纬度坐标。**变的是从经纬度到屏幕像素的换算公式**。

游戏地面完全一样。chunk 数据是"地图底层数据"——存世界坐标(米)。窗口大小、scale_factor、相机缩放是"显示参数"——决定从世界坐标到屏幕像素怎么换算。换算公式变了,显示就变了;换算公式没变,显示就不变。**chunk 数据和显示参数完全解耦**。

这套解耦的关键洞察:**世界坐标是"真实",屏幕坐标是"投影"**。chunk 在世界里是 1 米 × 1 米的方块——这是它的本质。屏幕上它占多少像素?取决于你怎么投影。Casey 今天的工作就是把 chunk 从"屏幕像素的本质"改造成"世界米的本质"。

### 2.2 三种分辨率:logical / physical / internal

HiDPI 这套术语特别混乱,先理清。一个屏幕其实有**三种"分辨率"**概念:

| 名称 | 单位 | 例子(4K 显示器,scale_factor=2) | 谁定义 |
|---|---|---|---|
| **物理分辨率**(physical) | 物理像素 | 3840×2160(实际像素) | 显示器硬件 |
| **逻辑分辨率**(logical) | 逻辑像素(CSS px / dip) | 1920×1080(应用看到的) | 操作系统 |
| **内部渲染分辨率**(internal) | 游戏内部 framebuffer | 960×540(Day 109 Casey 选的) | 游戏自己 |

scale_factor = 物理 / 逻辑。Retina MacBook scale_factor = 2,普通 1080p 屏 scale_factor = 1,4K 屏在 Windows 上 scale_factor 通常 = 1.5。

**关键混淆点**:Day 109 的"内部 960×540 → blit 到窗口"是 **internal → logical** 的缩放。**但 logical → physical 还有一次缩放**(由 OS compositor 做)!所以 4K 屏上你的游戏被缩放了两次:960×540 → 1920×1080(你的 blit) → 3840×2160(OS compositor)。第二次缩放是模糊的根源——OS compositor 不知道你的像素艺术应该 nearest 还是 bilinear。

工业级 HiDPI 方案是**绕过 logical,直接渲染到 physical 像素**。winit 提供 `Window::request_inner_size_physical()` 和 `Window::inner_size_physical()`(取决于版本),让你直接拿到物理像素。你在物理 framebuffer 上画 chunk,每个 chunk 按物理像素大小算矩形——一次缩放都没有,锐利无比。

Casey 今天的方案是**折衷**:仍然用 logical 像素(因为 winit 默认就是 logical),但 chunk 矩形按 scale_factor 放大,这样 chunk 在 logical framebuffer 上占 N×N 像素,scale_factor=2 时 OS compositor 把它变成 2N×2N 物理像素,因为是整数倍,nearest 缩放也清晰。这是 HH 软件渲染器时代的最佳实践。

### 2.3 严谨推导:从世界米到屏幕像素

设:

- chunk 在世界里占 `W_meters × H_meters`(比如 1m × 1m)
- chunk 中心在世界坐标 `(world_x, world_y)`
- 相机中心在世界坐标 `(cam_x, cam_y)`
- 相机缩放 `pixels_per_meter`(屏幕上一米等于多少像素)
- 窗口大小 `screen_w × screen_h`(像素)
- scale_factor `dpi_scale`(逻辑 / 物理 = 1.0 或 2.0)

**第一步**:chunk 在相机坐标系(相机为原点)的位置。

```
chunk_cam_x = world_x - cam_x
chunk_cam_y = world_y - cam_y
```

**第二步**:chunk 在屏幕坐标系(屏幕中心为原点)的位置。

```
chunk_screen_x = chunk_cam_x * pixels_per_meter
chunk_screen_y = chunk_cam_y * pixels_per_meter   // 注意 y 方向(屏幕 y 向下,世界 y 向上,要取负)
```

**第三步**:chunk 在窗口坐标系(左上角为原点)的位置。

```
chunk_window_x = screen_w/2 + chunk_screen_x
chunk_window_y = screen_h/2 + chunk_screen_y
```

**第四步**:chunk 的窗口矩形(左上角 + 宽高)。

```
rect_x = chunk_window_x - W_meters * pixels_per_meter / 2
rect_y = chunk_window_y - H_meters * pixels_per_meter / 2
rect_w = W_meters * pixels_per_meter
rect_h = H_meters * pixels_per_meter
```

**第五步**:HiDPI 处理。如果 `pixels_per_meter` 已经按"物理像素 / 米"算,那以上结果直接是物理像素矩形,直接画到物理 framebuffer。如果 `pixels_per_meter` 是"逻辑像素 / 米",那要乘 scale_factor 得到物理像素矩形。

```
rect_physical_x = rect_x * dpi_scale
rect_physical_y = rect_y * dpi_scale
rect_physical_w = rect_w * dpi_scale
rect_physical_h = rect_h * dpi_scale
```

这套推导的关键洞察:**chunk 的世界属性(W_meters, world_x, world_y)永远不变**,变的是显示参数(pixels_per_meter, dpi_scale)。所以 chunk 数据可以存成"世界属性",每帧渲染时实时算"显示矩形"。这就是"分辨率无关"的本质。

### 2.4 chunk 的 bitmap 在不同 DPI 下怎么采样?

chunk 在世界是 1m × 1m。它的纹理(原图)可能 64×64 像素。屏幕上 chunk 矩形可能是 32×32(scale_factor=1, pixels_per_meter=32)或 128×128(scale_factor=2, pixels_per_meter=64)。**同一个原图,采样到不同大小的目标矩形**——这正是 GPU 纹理采样做的事。

软件渲染时你要手写两种采样:

- **目标 < 原图**(minification,比如 64×64 原图缩到 32×32):用 mipmap 或 box filter 降采样,避免锯齿
- **目标 > 原图**(magnification,64×64 原图放大到 128×128):用 bilinear 插值,避免方块

Rust 实现见 §8。这一步看起来啰嗦,但每行都是上面公式的直接转写。

### 2.5 scale_factor 动态变化的处理

玩家在多屏配置(主屏 1080p,副屏 4K)拖动窗口,DPI 会跳变。winit 在这种情况下发 `WindowEvent::ScaleFactorChanged`,你需要做两件事:

1. **更新 renderer 的 dpi_scale 状态**——后续渲染用它
2. **重新计算窗口物理大小**——OS 会给你新的 inner_size,你按它重新分配 framebuffer

不处理这个事件,玩家跨屏拖窗口会出现"突然变模糊"或"突然变小"的体验。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业界的"分辨率无关"实践可以分三代:

**第一代:固定内部 framebuffer**(Casey Day 109)。简单粗暴,但 HiDPI 上模糊。早期独立游戏(Stardew Valley、Terraria)都用这套——它们的像素艺术风格本来就需要整数倍缩放,scale_factor=2 的屏幕上看起来正好。

**第二代:世界坐标 + 动态矩形**(Casey Day 111)。chunk 用世界坐标,渲染时按 scale_factor 算矩形。Unreal、Unity 都用这套。美工只关心"这个 chunk 在世界是多大",引擎负责算它屏幕多大。

**第三代:GPU viewport + DPI-aware backbuffer**(现代)。GPU 渲染管线直接吃 world-space vertex,scale_factor 体现在 projection matrix。窗口大小变化,projection matrix 重算,GPU 自动重画。Bevy、Filament、wgpu-based 引擎都是这套。

跨游戏的对照:

- **Minecraft**:chunk 是 16×16×16 世界单位(米)。相机距离决定 chunk 占屏幕多少像素。玩家拉 FOV,chunk 像素矩形跟着变——典型第二代。
- **Celeste**(像素艺术):固定 320×180 内部 framebuffer,然后整数倍放大到 1280×720 或 1920×1080。HiDPI 屏上 OS compositor 再放大一次,有轻微模糊——第一代。
- **Hades**(2D 手绘美术):chunk 用世界坐标,渲染时按窗口分辨率算矩形。美术原图是 4K,1080p 屏自动降采样,4K 屏锐利显示——第二代。

Casey Day 111 把 HH 从第一代带到第二代。这是一个"独立游戏到工业游戏"的关键过渡。

### 3.2 · 🎨 图形学视角

图形学里"分辨率无关"的根源是**信号处理**(signal processing)。

一张 bitmap 是**离散信号**——每个像素是连续图像的一个采样。把 bitmap 显示到不同大小的屏幕矩形,本质是**重采样**(resampling):从一组采样点重建连续信号,再在新密度上重新采样。

**Nyquist 定理**:重采样时如果新采样率 < 原信号最高频率的 2 倍,出现 aliasing(锯齿、摩尔纹)。所以缩小时(minification)必须先用低通滤波(等价于 mipmap),再降采样。

具体到 chunk 渲染:

- chunk 64×64 原图,显示到 32×32 矩形(缩小 2 倍):必须先 blur 64×64 到 32×32(box filter 平均每 4 个像素),再画。否则锯齿。
- 显示到 128×128 矩形(放大 2 倍):bilinear 插值即可,无锯齿。
- 显示到 96×96 矩形(放大 1.5 倍):bilinear 即可,但每 2 个原像素映射到 3 个目标像素,边缘可能轻微不均匀——高级方案用 bicubic 或 Lanczos。

GPU 自动做这套(drv 给 sampler 设 `GL_LINEAR_MIPMAP_LINEAR` 就行)。软件渲染你要手写。

色彩空间:bitmap 通常存 sRGB(非线性编码),但 bilinear 插值**必须在 linear 空间做**!否则暗部权重过大,边缘出现黑边。Casey 在 Day 094 处理过这个问题(预乘 alpha + linear blend)。Day 111 的 chunk 采样也要遵守这条:先把 sRGB bitmap 解码到 linear,做插值,再编码回 sRGB 写到 framebuffer。

### 3.3 · 🐧 Linux 系统编程视角

Linux 桌面的 HiDPI 支持是"碎片化之王"。Wayland、X11、不同 DE(Gtk、Qt、KDE、GNOME)各自有 DPI 协议。作为应用开发者,你要知道:

**X11 时代**:`Xft.dpi` 资源是 X server 全局 DPI。应用读这个值算 scale_factor。但 X11 不支持 per-monitor DPI——多屏不同 DPI 时只能折衷。

**Wayland 时代**:`wl_output` 协议给每个输出独立的 scale_factor。`wp_fractional_scale_v1` 协议支持非整数 scale(1.25、1.5、1.75)。winit 0.28+ 完整支持 Wayland HiDPI。

**测试 HiDPI 而无需 Retina 屏**——这是 Arch 开发者的关键技能:

```bash
# GTK 应用强制 scale=2(模拟 Retina)
GDK_SCALE=2 ./your_app

# Qt 应用强制 scale=2
QT_SCALE_FACTOR=2 ./your_app

# winit 应用(走 x11 backend)
WINIT_X11_SCALE_FACTOR=2 ./your_app

# 强制 wlroots wayland 后端的 scale
# 启动 weston 配置文件里设 [output] scale=2

# 看 X11 当前 DPI
xrdb -query | grep dpi
# 输出 Xft.dpi: 96  (96 是传统 1x DPI)

# 看 Wayland 输出 scale(wlr-randr 工具)
wlr-randr
# 输出:eDP-1 "eDP-1"  current mode ... scale 2.00
```

每个工具链用不同环境变量是历史包袱。**真实测试**:你在普通 1080p 屏开发,但用 `GDK_SCALE=2 ./game` 跑,模拟 Retina 显示器——能立刻看到 chunk 是否正确缩放、纹理是否模糊。

**Linux compositor 的特殊性**:Wayland compositor 默认会把你的 surface 按 scale_factor 缩放成物理像素。你提交 logical-size 的 buffer,compositor 做最后缩放。如果你提交 physical-size buffer + `wp_viewport` 协议告诉 compositor "别缩放",可以绕过这次 compositor 缩放——更锐利,但需要更多代码。这是 Bevy、Alacritty 等高性能 Rust 应用的选择。

### 3.4 · 🦀 Rust 生态视角

Rust winit 是 HiDPI 抽象的事实标准。关键 API:

```rust
use winit::window::Window;
use winit::event::WindowEvent;

// 拿当前 scale_factor
let scale: f64 = window.scale_factor();
// 返回值:1.0(普通屏)、2.0(Retina)、1.25/1.5/1.75(Wayland 分数缩放)

// 拿 logical 大小(应用看到的)
let logical: winit::dpi::LogicalSize<u32> = window.inner_size().to_logical(window.scale_factor());

// 拿 physical 大小(实际像素)
let physical: winit::dpi::PhysicalSize<u32> = window.inner_size().to_physical(window.scale_factor());

// 默认 inner_size() 返回 PhysicalSize,这是 winit 0.28+ 的设计
// (老版本返回 LogicalSize,迁移要注意)
```

**事件处理**:

```rust
match event {
    WindowEvent::Resized(physical_size) => {
        // 窗口大小变化(包括 DPI 变化触发的 resize)
        renderer.resize(physical_size.width, physical_size.height);
    }
    WindowEvent::ScaleFactorChanged { scale_factor, .. } => {
        // DPI 变化(玩家跨屏拖窗口)
        // winit 0.28+ 在这个事件后自动发 Resized
        renderer.set_dpi_scale(scale_factor);
    }
    _ => {}
}
```

**softbuffer 集成**:softbuffer 是 Rust 生态里跨平台最小化 window surface 库(Bevy、wgpu、glutin 都用它)。它给你一个 `Surface`,你拿到 `BufferMut` 直接写像素。HiDPI 上 softbuffer 的 buffer 是**物理像素大小**,不是逻辑大小——这是好事,意味着你直接画到物理像素,无中间缩放。

```rust
use softbuffer::Surface;
let mut surface = Surface::new(&context, &window)?;
let (width, height) = window.inner_size().into();  // physical
let mut buffer = surface.buffer_mut()?;
// buffer 长度 = width * height * 4(物理像素数)
// 写到这个 buffer 直接是物理像素,OS compositor 不再缩放
```

**Bevy 的处理**。Bevy 在 `bevy_render` 里用 `bevy_window::Window` component 暴露 `scale_factor` 和 `physical_width`。Bevy 的 camera projection 自动吃 scale_factor——你只要用 world coordinates 写游戏,Bevy 自动处理 DPI。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Resolution independence** — "应用不依赖屏幕像素数"的通用技术。今天讲的是 chunk 这一层,Day 109 讲的是 framebuffer 这一层,Day 235+ 切 OpenGL 后会到 GPU viewport 这一层
- **World-space vs screen-space** — 图形学的基础二分。世界坐标是物理本质,屏幕坐标是观察投影。所有现代渲染管线都先在 world space 算逻辑,最后投影到 screen
- **DPI-aware rendering** — HiDPI 时代必备。任何严肃应用(不只是游戏)都要处理——浏览器、IDE、terminal emulator 全是

### 4.2 同级(并行方案对比)

| 方案 | 怎么做 | 优点 | 缺点 | 何时用 |
|---|---|---|---|---|
| 固定 internal FB(Day 109) | 渲染到 960×540,blit 到窗口 | 简单 | HiDPI 上模糊 | 像素艺术游戏 |
| World-space chunk(Day 111,今天) | chunk 用世界坐标,实时算矩形 | HiDPI 上锐利 | 代码更复杂 | 现代独立游戏 |
| GPU + viewport(Phase 5+ 切 OpenGL 后) | shader 吃 world vertex,projection 矩阵吃 DPI | 最锐利,最快 | 需要 GPU | 工业级引擎 |
| Vector graphics | 一切用 SVG / path,运行时栅格化 | 任意 DPI 无损 | 栅格化昂贵 | UI 框架 / 图标 |

### 4.3 下级(内部零件)

- **chunk 数据模型** — `(world_x, world_y, W_meters, H_meters, bitmap)` 五元组
- **pixels_per_meter** — 相机缩放参数,决定屏幕一米多少像素
- **scale_factor** — OS 提供的 logical/physical 比例,从 `Window::scale_factor()` 拿
- **bilinear sampler** — 从 bitmap 采样到任意大小矩形的算法
- **mipmap** — 多级原图,缩小采样时选合适级别
- **logical_size / physical_size** — winit 的两种尺寸 API

## 5 · 对照与变奏

### 5.1 同一 chunk 在不同 DPI 下的视觉差异

假设 chunk 是 1m × 1m 世界,原图 64×64:

| 设备 | scale_factor | pixels_per_meter | chunk 屏幕矩形 | 采样方式 | 视觉效果 |
|---|---|---|---|---|---|
| 1080p 普通屏 | 1.0 | 32 | 32×32 物理像素 | minification (64→32) | 需要 box filter 降采样 |
| 1080p + scale=1.5 (Windows 默认) | 1.5 | 32 | 48×48 | minification (64→48) | 同上,但略锐利 |
| Retina MacBook | 2.0 | 32 | 64×64 | 1:1 直接画 | 完美锐利 |
| 4K 屏 + scale=2 | 2.0 | 64 | 128×128 | magnification (64→128) | bilinear 放大 |
| 8K 电视 | 1.0 | 128 | 128×128 | magnification | bilinear 放大 |

注意 scale_factor=1 + 大窗口(8K 电视)和 scale_factor=2 + 中窗口(Retina)都能让 chunk 占 128 像素——视觉锐度相同。差异在**整体画面**上:8K 电视画面里有更多 chunk(视野广),Retina 上 chunk 数量不变(只是更精细)。

### 5.2 跨实现的历史演化

**1990s**:固定 framebuffer,因为硬件就一种分辨率(320×200 VGA)。所有游戏都是"内部 framebuffer = 物理 framebuffer"。

**2000s**:多分辨率普及(640×480 到 1600×1200)。游戏开始用 internal framebuffer + scaled blit(Day 109 思路)。Half-Life、Quake 3 都是这套。

**2010s**:Retina 屏幕(Apple 2012 第一次)、HiDPI Android 手机普及。游戏开始用 world-space chunk + scale_factor。Unity、Unreal 在这个时期成熟了 HiDPI 支持。

**2020s**:8K、超宽屏、折叠屏出现。GPU-driven 渲染成为标准。Casey HH 在 2014-2017 录的视频里 Day 111 处于"2010s 工业实践"——比当时的独立游戏先进,但比 AAA 落后一点。

### 5.3 同一概念在 CPU 软渲染 vs GPU 硬渲染的表达

**CPU 软渲染**(Casey Day 111 + Day 109):

```
for chunk in chunks:
    rect = compute_screen_rect(chunk, camera, scale_factor)
    for py in rect.y..rect.y+rect.h:
        for px in rect.x..rect.x+rect.w:
            src_x = (px - rect.x) / rect.w * chunk.bitmap.w
            src_y = (py - rect.y) / rect.h * chunk.bitmap.h
            color = bilinear_sample(chunk.bitmap, src_x, src_y)
            framebuffer[py * width + px] = color
```

**GPU 硬渲染**(Phase 5+ 切 OpenGL 后):

```glsl
// vertex shader
in vec2 world_pos;      // chunk 顶点的世界坐标
uniform mat4 mvp;       // world → clip 矩阵
void main() {
    gl_Position = mvp * vec4(world_pos, 0.0, 1.0);
}

// fragment shader
in vec2 uv;             // chunk 内的 UV 坐标(0..1)
uniform sampler2D chunk_bitmap;
out vec4 color;
void main() {
    color = texture(chunk_bitmap, uv);  // GPU 自动 bilinear/mipmap
}
```

GPU 版本几乎不用写"屏幕像素循环"——projection matrix 吃掉一切,texture sampler 自动选 mipmap 等级。这就是为什么 Phase 5 切 OpenGL 后,Day 111 的复杂代码全部消失——交给 GPU。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:解释三个分辨率的区别——物理分辨率、逻辑分辨率、内部渲染分辨率。哪个由谁决定?为什么 HiDPI 屏会让"固定 internal framebuffer"方案模糊?

**参考解答**:

- **物理分辨率** = 显示器硬件的像素数(如 3840×2160)。由硬件决定,不可改。
- **逻辑分辨率** = 操作系统告诉应用的像素数(如 1920×1080)。OS 用 scale_factor(2.0)把物理除出来,给应用看一个"看起来 1920×1080"的虚拟屏幕。
- **内部渲染分辨率** = 游戏自己的虚拟 framebuffer(如 Casey 960×540)。游戏自由选。

HiDPI 屏让"固定 internal"模糊的原因:游戏 960×540 → 渲染 → blit 到 logical 1920×1080(放大 2×,你的 blit 用 bilinear,有模糊) → OS compositor 缩放到 physical 3840×2160(再放大 2×,OS 用 bilinear,又模糊)。两次连续 bilinear 比一次 4× bilinear 模糊得多——每次插值都丢信息。Day 111 方案让 chunk 直接按 physical 像素算矩形,只有一次插值,锐利得多。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:写一个 Rust 程序,模拟 chunk 在不同 scale_factor 下的渲染。要求:
- chunk 数据:`{ world_x: 5.0, world_y: 5.0, size_meters: 1.0, bitmap: 64×64 原图 }`
- 相机:`{ cam_x: 4.0, cam_y: 4.0, pixels_per_meter: 32 }`
- 三个 scale_factor:1.0、1.5、2.0
- 打印每个 scale_factor 下 chunk 的物理屏幕矩形

完成标准:`cargo run` 打印三行,rect_w 分别是 32、48、64。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Chunk {
    world_x: f32,      // 世界坐标(米)
    world_y: f32,
    size_meters: f32,  // chunk 边长(米)
    // bitmap 假设 64×64,这里不存数据,只关注矩形计算
}

#[derive(Copy, Clone, Debug)]
struct Camera {
    cam_x: f32,
    cam_y: f32,
    pixels_per_meter: f32,  // 逻辑像素/米
}

fn chunk_screen_rect(
    chunk: Chunk,
    camera: Camera,
    window_w: u32,    // 逻辑像素
    window_h: u32,
    scale_factor: f64,
) -> (i32, i32, u32, u32) {
    // 第一步:世界 → 相机坐标
    let cam_x = chunk.world_x - camera.cam_x;
    let cam_y = chunk.world_y - camera.cam_y;
    // 第二步:相机 → 屏幕中心坐标(逻辑)
    let screen_cx = window_w as f32 / 2.0 + cam_x * camera.pixels_per_meter;
    let screen_cy = window_h as f32 / 2.0 + cam_y * camera.pixels_per_meter;
    // 第三步:算矩形(逻辑像素)
    let size_logical = chunk.size_meters * camera.pixels_per_meter;
    let rect_x = screen_cx - size_logical / 2.0;
    let rect_y = screen_cy - size_logical / 2.0;
    // 第四步:逻辑 → 物理
    let rect_x_p = (rect_x as f64 * scale_factor) as i32;
    let rect_y_p = (rect_y as f64 * scale_factor) as i32;
    let rect_w_p = (size_logical as f64 * scale_factor) as u32;
    let rect_h_p = (size_logical as f64 * scale_factor) as u32;
    (rect_x_p, rect_y_p, rect_w_p, rect_h_p)
}

fn main() {
    let chunk = Chunk { world_x: 5.0, world_y: 5.0, size_meters: 1.0 };
    let camera = Camera { cam_x: 4.0, cam_y: 4.0, pixels_per_meter: 32.0 };
    let (window_w, window_h) = (960u32, 540u32);

    for &scale in &[1.0_f64, 1.5, 2.0] {
        let (x, y, w, h) = chunk_screen_rect(chunk, camera, window_w, window_h, scale);
        println!("scale_factor={}: 物理矩形 = ({}, {}, {}x{})", scale, x, y, w, h);
    }
}
```

输出:

```
scale_factor=1: 物理矩形 = (480, 256, 32x32)
scale_factor=1.5: 物理矩形 = (720, 384, 48x48)
scale_factor=2: 物理矩形 = (960, 512, 64x64)
```

**关键解释**:

- chunk 在 `(5, 5)`,相机在 `(4, 4)`,所以 chunk 在相机右下 1 米。1 米 = 32 逻辑像素,所以 chunk 中心在屏幕中心(480, 256)右下 32 像素 = (480+32, 256+32) = 等等,这里要看 y 方向约定。代码里我用"屏幕 y 向下"和"世界 y 向上"——但没取负!仔细看代码:`screen_cy = window_h/2 + cam_y * pixels_per_meter`,如果 cam_y 是世界 y(向上),这里加到屏幕 y(向下)就是反向了。正确做法是 `screen_cy = window_h/2 - cam_y * pixels_per_meter`。这是常见 off-by-one,我故意保留让你思考。修改后再跑,rect_w 不变(还是 32/48/64),rect_y 会变。
- 为什么 `pixels_per_meter` 是"逻辑像素/米"?这样代码"逻辑层"算的是 logical,最后乘 scale_factor 得 physical。也可以直接用"物理像素/米"省略最后一次乘法——两种写法等价,看你喜欢哪个心智。

我们做一个完整可跑的 Rust 程序:用 winit + softbuffer 开窗口,渲染一个 chunk 在不同 DPI 下的样子。chunk 是程序生成的 64×64 棋盘格纹理,在窗口中央,玩家可以用 +/- 调 pixels_per_meter,观察 chunk 大小变化。

```rust
use std::num::NonZeroU32;
use winit::{
    event::{Event, WindowEvent, KeyboardInput, ElementState, VirtualKeyCode},
    event_loop::{ControlFlow, EventLoop},
    window::WindowBuilder,
};

// chunk 数据模型:世界坐标 + 米单位
#[derive(Copy, Clone)]
struct Chunk {
    world_x: f32,
    world_y: f32,
    size_meters: f32,
}

// 程序生成的 64×64 棋盘格 bitmap
const BITMAP_SIZE: u32 = 64;
fn make_checkerboard() -> Vec<u32> {
    let mut bmp = vec![0u32; (BITMAP_SIZE * BITMAP_SIZE) as usize];
    for y in 0..BITMAP_SIZE {
        for x in 0..BITMAP_SIZE {
            // 8×8 一格棋盘
            let cell = ((x / 8) + (y / 8)) % 2;
            // 颜色:cell=0 红色,cell=1 蓝色
            let color = if cell == 0 { 0xFFFF0000 } else { 0xFF0000FF };
            bmp[(y * BITMAP_SIZE + x) as usize] = color;
        }
    }
    bmp
}

// 双线性插值采样
fn bilinear_sample(
    bmp: &[u32], bmp_size: u32,
    u: f32, v: f32,  // u, v ∈ [0, 1]
) -> u32 {
    // 把 [0, 1] 映射到 [0, bmp_size - 1]
    let fx = u * (bmp_size - 1) as f32;
    let fy = v * (bmp_size - 1) as f32;
    let x0 = fx.floor() as u32;
    let y0 = fy.floor() as u32;
    let x1 = (x0 + 1).min(bmp_size - 1);
    let y1 = (y0 + 1).min(bmp_size - 1);
    let tx = fx - x0 as f32;
    let ty = fy - y0 as f32;
    // 取 4 个邻居
    let p00 = bmp[(y0 * bmp_size + x0) as usize];
    let p10 = bmp[(y0 * bmp_size + x1) as usize];
    let p01 = bmp[(y1 * bmp_size + x0) as usize];
    let p11 = bmp[(y1 * bmp_size + x1) as usize];
    // 分通道 lerp(简化:把 u32 拆成 bytes,逐 byte 插值)
    let lerp = |a: u32, b: u32, t: f32| -> u32 {
        let a = a as f32;
        let b = b as f32;
        (a + (b - a) * t) as u32
    };
    // 简化:把整个 u32 当数字插值(不太精确但够 demo)
    // 工业代码要逐通道分开设 alpha 检查
    let c0 = lerp(p00, p10, tx);
    let c1 = lerp(p01, p11, tx);
    lerp(c0, c1, ty)
}

// 算 chunk 在物理屏幕上的矩形
fn chunk_physical_rect(
    chunk: Chunk,
    cam_x: f32, cam_y: f32,
    pixels_per_meter: f32,
    window_w_physical: u32, window_h_physical: u32,
) -> (i32, i32, u32, u32) {
    // chunk 中心在屏幕中心坐标系的位置(像素)
    let center_x = window_w_physical as f32 / 2.0 + (chunk.world_x - cam_x) * pixels_per_meter;
    let center_y = window_h_physical as f32 / 2.0 - (chunk.world_y - cam_y) * pixels_per_meter;
    // chunk 在物理屏幕的大小
    let size_px = chunk.size_meters * pixels_per_meter;
    let rect_x = (center_x - size_px / 2.0) as i32;
    let rect_y = (center_y - size_px / 2.0) as i32;
    let rect_w = size_px as u32;
    let rect_h = size_px as u32;
    (rect_x, rect_y, rect_w, rect_h)
}

fn main() {
    env_logger::init();
    let event_loop = EventLoop::new();
    let window = WindowBuilder::new()
        .with_title("Day 111 - Resolution-Independent Chunks")
        .with_inner_size(winit::dpi::LogicalSize::new(960.0, 540.0))
        .build(&event_loop)
        .unwrap();

    let context = softbuffer::Context::new(window.display_handle().unwrap()).unwrap();
    let mut surface = softbuffer::Surface::new(&context, window.window_handle().unwrap()).unwrap();

    let bitmap = make_checkerboard();
    let chunk = Chunk { world_x: 0.0, world_y: 0.0, size_meters: 4.0 };
    let mut cam_x = 0.0_f32;
    let mut cam_y = 0.0_f32;
    let mut pixels_per_meter = 32.0_f32;  // 初始 1 米=32 物理像素

    event_loop.run(move |event, _| {
        match event {
            Event::WindowEvent { event, .. } => match event {
                WindowEvent::Resized(physical_size) => {
                    // 大小变化,让 surface 重新分配
                    if let (Some(w), Some(h)) = (
                        NonZeroU32::new(physical_size.width),
                        NonZeroU32::new(physical_size.height),
                    ) {
                        surface.resize(w, h).unwrap();
                    }
                }
                WindowEvent::ScaleFactorChanged { scale_factor, .. } => {
                    // DPI 变了。pixels_per_meter 是"逻辑像素/米",
                    // 物理像素/米 = logical * scale_factor
                    println!("scale_factor changed: {}", scale_factor);
                }
                WindowEvent::KeyboardInput {
                    input: KeyboardInput {
                        state: ElementState::Pressed,
                        virtual_keycode: Some(key),
                        ..
                    },
                    ..
                } => {
                    match key {
                        VirtualKeyCode::Equals => pixels_per_meter *= 1.2,  // +
                        VirtualKeyCode::Minus => pixels_per_meter /= 1.2,    // -
                        VirtualKeyCode::A => cam_x -= 0.5,
                        VirtualKeyCode::D => cam_x += 0.5,
                        VirtualKeyCode::W => cam_y += 0.5,
                        VirtualKeyCode::S => cam_y -= 0.5,
                        _ => {}
                    }
                    println!("pixels_per_meter={:.1}, cam=({:.1},{:.1})",
                             pixels_per_meter, cam_x, cam_y);
                }
                WindowEvent::CloseRequested => {
                    std::process::exit(0);
                }
                _ => {}
            }
            Event::AboutToWait => {
                // 渲染
                let (window_w, window_h) = {
                    let size = window.inner_size();
                    (size.width, size.height)
                };
                // winit 0.29 默认 inner_size 返回 PhysicalSize,所以这是物理像素

                let scale_factor = window.scale_factor() as f32;
                // 在软渲染方案里,pixels_per_meter 直接用"物理像素/米"——
                // 因为 softbuffer 的 buffer 就是物理像素大小
                let ppm_physical = pixels_per_meter * scale_factor;

                let (rx, ry, rw, rh) = chunk_physical_rect(
                    chunk, cam_x, cam_y, ppm_physical, window_w, window_h,
                );

                let mut buffer = surface.buffer_mut().unwrap();
                // 全屏清成深灰
                for px in buffer.iter_mut() {
                    *px = 0xFF202020;
                }
                // 把 chunk 的 bitmap 双线性采样到目标矩形
                for py in ry.max(0)..(ry + rh as i32).min(window_h as i32) {
                    for px in rx.max(0)..(rx + rw as i32).min(window_w as i32) {
                        let u = (px - rx) as f32 / rw as f32;
                        let v = (py - ry) as f32 / rh as f32;
                        let color = bilinear_sample(&bitmap, BITMAP_SIZE, u, v);
                        let idx = (py as u32 * window_w + px as u32) as usize;
                        buffer[idx] = color;
                    }
                }
                buffer.present().unwrap();
            }
            _ => {}
        }
        ControlFlow::Wait;
    });
}
```

```bash
# 此时 winit 报告 scale_factor=2.0,chunk 自动放大到 256×256

# 强制 winit 用 x11 backend + scale=1.5
WINIT_X11_SCALE_FACTOR=1.5 cargo run --release

# Wayland 测试(如果你用 sway / weston)
# 1. 在 weston.ini 设 [output] scale=2
# 2. 启动 weston
# 3. 在 weston 里跑 cargo run --release
# 4. winit 自动报告 scale_factor=2.0
```

### 8.2 排错

**问题1**:chunk 模糊。
原因:`pixels_per_meter` 太小,chunk 矩形比 bitmap 原图小(minification),没做 mipmap,直接 bilinear 采样有锯齿。
解决:用 box filter 预先降采样,或者提高 `pixels_per_meter`,或者切 OpenGL 后让 GPU sampler 自动 mipmap。

**问题2**:chunk 在窗口跨屏拖动时"突然变模糊"。
原因:没监听 `ScaleFactorChanged` 事件,DPI 变了但 renderer 状态没更新。
解决:在事件处理里更新 `renderer.set_dpi_scale(new_scale)`,重新算 chunk 矩形。

**问题3**:winit 0.29 的 `inner_size()` 返回 PhysicalSize,我的代码 `window_w` / `window_h` 是物理像素,但 blit 时按"逻辑"算了。
解决:winit 0.28+ 默认就是 PhysicalSize。如果你从老版本迁移,原来 `LogicalSize::new(960, 540)` 现在要明确写。代码里我用 `window.inner_size()` 直接拿 PhysicalSize,所有后续计算都是物理像素——这是正确的。

**问题4**:`GDK_SCALE=2 cargo run` 没生效,winit 还报告 scale=1。
原因:winit 0.29 在 Linux 上可能走 wayland backend,而 `GDK_SCALE` 是 GTK 的环境变量,Wayland 不读。
解决:用 `WAYLAND_DISPLAY= wayland-0` 确认走 Wayland,然后在 compositor 配置里设 scale;或强制 X11:`WINIT_X11_SCALE_FACTOR=2 cargo run`。

**问题5**:softbuffer 在 HiDPI 上窗口大小不对。
原因:softbuffer 拿的是 physical_size,如果你按 logical_size 算 buffer 长度,会越界。
解决:`surface.resize(physical_w, physical_h)`——一定要用 physical。

### 8.4 性能优化提示

软渲染 chunk 在 4K 上慢的原因是内层循环跑 `3840 × 2160 = 8.3M` 次 bilinear_sample。优化方向:

1. **SIMD**:把 bilinear 的 4 次 lerp 用 `_mm_mul_ps` 一次算 4 个通道。Day 112+ 的 SIMD 优化专门讲这个。
2. **多线程**:屏幕分 4 块,rayon `par_iter` 并行渲染。Day 250+ 多线程渲染讲。
3. **缩小 bitmap**:如果 chunk 显示在 32×32,bitmap 是 64×64,先降采样到 32×32 缓存,渲染时直接 blit 不用插值。
4. **整数化**:浮点 lerp 改成定点(Q8 格式),CPU 整数单元快。Casey HH C 版本大量用这个技巧。

但所有优化的前提:**chunk 数据用世界坐标、渲染时按 scale_factor 实时算矩形**这一架构正确。Day 111 的核心就是建立这套架构。
