
# Day 081 · 用重叠位图创建地面

> 你的草地用什么画?一张大位图?那美术要画 N 个不同的草地——太贵。Casey 今天教你**程序化合成**:底层大块草地,上层随机散布花朵、石头、裂缝。每张图很小,组合后产生无限变化。这是程序化生成的入门——用最简单的 alpha blending,把 5 张图变成 1000 种草地。

## 0 · 为什么要有这一天

你的游戏要 1000 块草地 tile。每种美术要画一张 64×64 的位图。如果 5 种草地(普通、花朵、石头、湿润、干枯),5 张图就够了——看起来重复,因为每块 tile 都一样。

但如果想要**每块 tile 都不一样**?1000 张图?美术会杀你。

Casey 的解法:**程序化合成**。底层 1 张大草地,上层随机散布 5-10 个小花/石头小图。每次合成结果不同。1000 块 tile 用同样的素材,但每块长不一样。

这是程序化生成(procedural generation)的核心思想——**用规则 + 随机性 + 小素材,产生无限变化**。Minecraft、Noita、Spelunky 都用这个思路。

今天的实现技术是 **alpha blending**——Day 038 学过的。把上层图按 alpha 半透明叠加到下层。Casey 今天把它用在地面合成上。

心理锚点:看完今天,你能用 5 张小图生成 1000 种草地。你能解释「程序化生成」的核心思想。你能用 Rust 写一个最简单的 tile 合成器。

## 1 · Casey 今天做了什么

Casey 今天做的事情:

1. **定义地面合成规则**:每个 ground tile 由多层 bitmap 叠加——底层草地 + 0-5 个装饰(花、石头、蘑菇)。
2. **加载小图素材**:5 张 8×8 / 16×16 小图(花、石头、蘑菇、草丛、裂缝)。
3. **随机种子**:每块 tile 用 (x, y) 作为种子,产生确定性随机(同 tile 永远生成相同装饰)。
4. **alpha blend 合成**:按 z-order 从下到上叠加。

Casey 强调「**确定性随机**」——同一个 tile 在不同帧生成相同结果(否则 tile 闪烁)。用 tile 坐标做种子,确保一致性。

## 2 · 心智模型

### 费曼类比:画家铺色 + 装饰

想象画家画一片草地:

1. 先用大刷子铺一层底色(深绿)。
2. 再用小刷子撒一些点(浅绿草尖)。
3. 再画一些花朵(红、黄)。
4. 再画一些石头(灰)。
5. 再画一些蘑菇(白)。

每一层都是**叠加**——下面的层透过上面的层露出来(alpha < 100% 时)。

游戏里,这个「画家」是程序,「刷子」是小 bitmap。程序按规则撒 bitmap,产生画家手工的效果。

### 严谨原理

#### 2.1 Alpha blending 回顾

Day 038 的 alpha blending 公式:

```
out.rgb = src.rgb * src.a + dst.rgb * (1 - src.a)
out.a   = src.a + dst.a * (1 - src.a)
```

src 是上层(要画上去的),dst 是下层(已存在的)。alpha 范围 [0, 1]。

每像素 4 个 f32(rgba)运算,4 次乘 + 3 次加。Rust 实现:

```rust
fn blend_pixel(dst: &mut [u8; 4], src: &[u8; 4]) {
    let sa = src[3] as f32 / 255.0;
    let da = dst[3] as f32 / 255.0;
    for i in 0..3 {
        let s = src[i] as f32 / 255.0;
        let d = dst[i] as f32 / 255.0;
        let out = s * sa + d * (1.0 - sa);
        dst[i] = (out * 255.0) as u8;
    }
    dst[3] = ((sa + da * (1.0 - sa)) * 255.0) as u8;
}
```

每像素 ~10 次浮点运算。一张 64×64 bitmap = 4096 像素 = 40960 次运算。1000 tile × 5 层 = 2 亿次运算/帧——CPU 能跑,但不快。Day 082 加缓存解决。

#### 2.2 确定性随机

```rust
fn hash_tile(x: i32, y: i32) -> u32 {
    // 简单 hash:把 (x, y) 映射到伪随机 u32
    let h = (x.wrapping_mul(374761393))
        .wrapping_add(y.wrapping_mul(668265263));
    h ^ (h >> 13)
}
```

这个 hash 让每个 (x, y) 产生不同的伪随机数,但同样的 (x, y) 永远产生同样的数——**确定性**。

```rust
fn decorate_tile(tile_x: i32, tile_y: i32) -> Vec<Decoration> {
    let seed = hash_tile(tile_x, tile_y);
    let mut rng = SeededRng::new(seed);
    let mut decos = Vec::new();

    // 决定装饰数量(0-5)
    let count = rng.next_u32() % 6;
    for _ in 0..count {
        // 随机选装饰类型
        let deco_type = match rng.next_u32() % 5 {
            0 => DecoType::Flower,
            1 => DecoType::Stone,
            2 => DecoType::Mushroom,
            3 => DecoType::GrassTuft,
            _ => DecoType::Crack,
        };
        // 随机位置
        let dx = (rng.next_u32() % 64) as f32;
        let dy = (rng.next_u32() % 64) as f32;
        decos.push(Decoration { kind: deco_type, pos: Vec2::new(dx, dy) });
    }
    decos
}
```

同样的 (tile_x, tile_y) 永远产生同样的装饰列表——确定性。

#### 2.3 SeededRng:简单 LCG

```rust
struct SeededRng { state: u32 }

impl SeededRng {
    fn new(seed: u32) -> Self { Self { state: seed } }

    fn next_u32(&mut self) -> u32 {
        // LCG (Linear Congruential Generator)
        // 简单的伪随机算法
        self.state = self.state.wrapping_mul(1664525).wrapping_add(1013904223);
        self.state
    }
}
```

LCG 是最简单的伪随机算法——一个公式,产生看似随机的数列。游戏开发用 LCG 因为快、确定性、足够随机。工业加密不用(可预测)。

#### 2.4 合成的完整流程

```rust
fn composite_tile(tile_x: i32, tile_y: i32, assets: &Assets) -> Bitmap {
    // 1. 底层:大草地(64×64)
    let mut result = assets.grass_base.clone();

    // 2. 装饰层
    let decos = decorate_tile(tile_x, tile_y);
    for deco in decos {
        let deco_bmp = assets.get_decoration(deco.kind);
        // alpha blend deco 到 result 的 (deco.pos.x, deco.pos.y)
        blend_bitmap(&mut result, deco_bmp, deco.pos);
    }

    result
}
```

每次合成产生一个新 64×64 bitmap。

#### 2.5 性能问题

每帧 1000 tile × 5 层 × 4096 像素 × 10 运算 = 2 亿次运算/帧。60 FPS 时每秒 120 亿次——CPU 紧张。

**Day 082 的解法**:缓存。第一次合成后存起来,后续帧直接用缓存。

但 Day 081 先把合成做对,Day 082 再优化。

### 3.2 · 🎨 图形学视角

Alpha blending 在图形学里**无处不在**:

- **UI 渲染**:按钮、文本、半透明面板都 alpha blend。
- **粒子效果**:每个粒子 alpha blend 到屏幕。
- **后处理**:blur、bloom 等用 alpha blend 累积。
- **离屏渲染**:先渲染到 offscreen buffer,再 alpha blend 到屏幕。

#### Alpha 的几种含义

| 类型 | 含义 |
|---|---|
| Per-pixel alpha | 每像素有 a 值(PNG)|
| Bitmap alpha | 整张图一个 a(tint)|
| Coverage | 子像素覆盖率(MSAA)|

Casey HH 用 per-pixel alpha,跟 PNG 一样。

#### Premultiplied alpha(Day 083 的伏笔)

合成大量 alpha bitmap 时,**premultiplied alpha**(预乘 alpha)更快——少一次乘法/像素。Day 083 Casey 会切到 premultiplied。

### 3.4 · 🦀 Rust 生态视角

#### Rust 写 alpha blending

```rust
#[derive(Clone)]
struct Bitmap {
    width: usize,
    height: usize,
    pixels: Vec<[u8; 4]>,  // RGBA
}

impl Bitmap {
    fn new(width: usize, height: usize) -> Self {
        Self {
            width,
            height,
            pixels: vec![[0, 0, 0, 0]; width * height],
        }
    }

    fn blend_at(&mut self, dst_x: usize, dst_y: usize, src: &Bitmap) {
        for y in 0..src.height {
            for x in 0..src.width {
                let dx = dst_x + x;
                let dy = dst_y + y;
                if dx >= self.width || dy >= self.height { continue; }
                let dst = &mut self.pixels[dy * self.width + dx];
                let s = src.pixels[y * src.width + x];
                blend_pixel(dst, &s);
            }
        }
    }
}

fn blend_pixel(dst: &mut [u8; 4], src: &[u8; 4]) {
    let sa = src[3] as f32 / 255.0;
    if sa == 0.0 { return; }  // 完全透明,跳过(优化)
    for i in 0..3 {
        let s = src[i] as f32;
        let d = dst[i] as f32;
        dst[i] = (s * sa + d * (1.0 - sa)).min(255.0) as u8;
    }
    // dst alpha 不变(假设 dst 已经不透明)
}
```

### 3.5 · 🐧 Linux 系统编程视角(内核空间 / 硬件加速)

Linux 系统里"碰撞 / 相交检测"的核心思想在多处出现,理解这些能让你看 Casey 的 2D / 3D collision 算法在更广的语境里。

**内核的 page fault 处理**。虚拟内存到物理内存的映射,本质是"地址空间相交检测"。CPU 访问虚拟地址,MMU 查 page table,如果地址不在已映射范围内 → page fault。内核接 fault,检查(1)地址合法吗(进程的 VMA 区间)、(2)权限对吗(read / write / exec)、(3)page 在物理内存还是 swap。这套检查就是"区间相交 + 属性匹配",和 Casey 在 day 050 的 Minkowski collision 在抽象上一致——"用几何空间判断两个东西是否接触"。

```bash
# 看你进程的 VMA(虚拟内存区域)
cat /proc/$$/maps
# 输出形如:
# 56001234-56005678 r-xp ...  /usr/bin/bash
# 7f1234560000-7f1234780000 r--p ... /usr/lib/libc.so.6

# 触发 page fault(故意访问非法地址)
python3 -c "import ctypes; ctypes.cast(0xdeadbeef, ctypes.POINTER(ctypes.c_int))[0] = 0"
# 输出:Segmentation fault (core dumped)
```

**epoll / poll / select** 是 IO 多路复用,本质是"时间区间相交"。你给内核 N 个 fd,内核检查"哪个 fd 当前可读 / 可写"。这是 N 路并行等待,内核用红黑树 + ready list 高效管理。和 collision detection 的 broad phase 类似——快速排除不可能相交的对,只在 narrow phase 详细检查。

**文件锁(flock / fcntl)**。Linux 文件锁检测"两个进程是否同时持有冲突锁"——这是"锁区间相交"。flock 用 inode-level 锁,fcntl 用 byte-range 锁(`fcntl(F_SETLK, F_WRLCK, {100..200})` 锁字节 100-200)。内核维护锁列表,新锁请求时遍历检查冲突——这就是 interval intersection 检测。

**网络栈的 TCP / IP header 校验**。每个 TCP/IP 包带 checksum,内核收到包校验——本质是"数据完整性检测"。和 collision detection 不直接相关,但**思想相同**——"用一个数学函数快速判断数据是否合法"。

**cgroup 的资源限制**。`cpu.max = 50000 100000` 表示 cgroup 在每 100ms 周期内最多用 50ms CPU。内核定期检查"当前周期已用多少 CPU",超了 throttle。这是"时间区间累积 + 阈值检测",和 Casey 的"span duration + frame budget"逻辑相同。

**netfilter / iptables** 用 BPF 风格的规则匹配,检查每个网络包。"规则匹配"本质是"包属性 vs 规则区间"——"src IP in 192.168.0.0/16 && dst port == 22"是区间检测。BPF (Berkeley Packet Filter) 让用户写过滤器,内核执行——这种"用户定义函数 + 内核执行"模式是 eBPF 的基础。

**kernel scheduling**。Linux CFS(Completely Fair Scheduler)维护红黑树 of runnable tasks,按 vruntime 排序。每个 tick(1ms / 4ms),CFS 检查当前 task 是否该让出 CPU——"时间片用完了吗"。这是"时间累积 + 阈值切换",和游戏 update 循环的 frame budget 检查同构。

### 3.6 · 🦀 Rust 生态视角

Rust 在游戏物理 / 碰撞领域有几个值得关注的 crate 和模式。

**`rapier`** 是 Rust 的 2D / 3D 物理引擎,由 Dimforge 开发。Rapier 提供 rigid body dynamics、collision detection、joints、rays、sensors——是 Bevy 生态的物理默认选项。Rapier 用 ECS 风格 API,内部用 SOA(struct of arrays)布局,cache 友好。

```rust
use rapier3d::prelude::*;

let mut rigid_body_set = RigidBodySet::new();
let mut collider_set = ColliderSet::new();

let rigid_body = RigidBodyBuilder::dynamic().translation(vector![0.0, 5.0, 0.0]).build();
let handle = rigid_body_set.insert(rigid_body);
let collider = ColliderBuilder::ball(0.5).build();
collider_set.insert_with_parent(collider, handle, &mut rigid_body_set);
```

Rapier 内部用 **broad phase(AABB tree)+ narrow phase(GJK / SAT)**,和工业 C++ 引擎(Box2D、Bullet、PhysX)思路一致。Casey HH 手写简化版,Rapier 是 production-grade。

**`parry`** 是 Rapier 抽出来的纯 collision detection 库。parry 提供 shape(ball、cuboid、convex hull、triangle mesh)、ray cast、point projection、pair collision——不涉及 dynamics。如果你只想要碰撞不想物理,parry 是答案。

**`nalgebra`** 是 Rust 的线性代数库,Dimforge 出品(同 Rapier / parry)。`Vector3`、`Matrix4`、`Quaternion`、`Isometry3`——3D 游戏需要的所有数学类型。比 `cgmath` 现代、比 `euclid` 全面。

**Rust ECS 的 collision pattern**。Bevy + Rapier 的典型代码:

```rust
use bevy::prelude::*;
use bevy_rapier3d::prelude::*;

fn setup(mut commands: Commands) {
    commands.spawn((
        RigidBody::Dynamic,
        Collider::ball(1.0),
        Transform::from_translation(Vec3::new(0.0, 5.0, 0.0)),
    ));
}

fn on_collision(
    mut events: EventReader<CollisionEvent>,
    query: Query<&Name>,
) {
    for event in events.read() {
        if let CollisionEvent::Started(e1, e2, _) = event {
            println!("{:?} collided with {:?}", query.get(*e1), query.get(*e2));
        }
    }
}
```

ECS 风格——entity 加 Collider component,系统处理 CollisionEvent。这是 Rust 风格的 collision 设计——数据导向、零成本、类型安全。Casey HH 用 OOP 风格(`struct Player { collider: Collider }`),简单但不够通用。

**Rust 的 zero-cost abstraction** 让 collision detection 可以既高级又快:

```rust
// 高级 API
let hits = colliders.iter()
    .filter(|c| c.aabb_intersects(&target_aabb))
    .filter(|c| c.shape_intersects(&target_shape))
    .collect::<Vec<_>>();

// LLVM 把这优化成手写 C 的等价代码
```

Rust 的 iterator chain + 闭包,被 LLVM inline + vectorize,生成和手写循环一样快的代码。这是 Rust 在性能敏感领域的杀手锏。

**Rust 的 SIMD** 对 collision 特别有用。AABB 测试 8 个浮点比较,用 SIMD 一次处理 4-8 个 AABB。Rust 的 `std::simd`(unstable)或 `wide` crate(stable)提供 SIMD API。Rapier 内部用 SIMD 加速 broad phase。

**Rust 的多线程 collision**。collision detection 是 embarrassingly parallel——N 个 object pair 互相独立。Rust 的 `rayon` 提供 parallel iterator,`colliders.par_iter().filter(...)` 自动并行。Bevy 用 ECS 的 `query.par_iter()` 同样效果。

**Rust 的 `Send + Sync`**。collision data 跨线程共享,要 `Send + Sync`。Rust 编译时检查——如果你的 Collider 包含 `Rc<...>`,编译失败,因为 Rc 不是 Send。这种类型系统保证的多线程安全,是 Rust 比 C++ 优势的地方。

**Rust 的 `smallvec`** 在 collision 里有用。pair list 经常是空的或只有 1-2 个 pair,用 `SmallVec<[Pair; 4]>` 避免堆分配,大部分情况栈上。

**Rust 的 `ahash`** 在 spatial hash 里替代 `DefaultHasher`——3-5 倍速度。Casey HH 的 hash chunk storage(Phase 2)用 `DefaultHasher`,Rust 版应该用 `ahash` 或 `fxhash`。

### Lv1 · 概念辨析

**题**:为什么用 (tile_x, tile_y) 作为随机种子,而不是用系统时间?

**参考解答**:**确定性**。

如果用系统时间做种子,同一 tile 每帧生成不同装饰——画面闪烁,玩家晕。

用 tile 坐标做种子,同一 tile 永远生成相同装饰——稳定。玩家走开再回来,tile 还是同样的花和石头。

**确定性**是程序化生成的核心——同样的输入永远产生同样的输出,但不同输入产生看似随机的不同输出。

### Lv2 · 动手实践

**题**:实现 SeededRng 和 decorate_tile。生成 tile (3, 5) 和 (3, 5)(同坐标)的装饰列表,验证相同。生成 (3, 5) 和 (4, 5),验证不同。

完成标准:同坐标产生相同装饰,不同坐标产生不同装饰。

**参考解答**:

```rust
struct SeededRng { state: u32 }

impl SeededRng {
    fn new(seed: u32) -> Self { Self { state: seed } }
    fn next_u32(&mut self) -> u32 {
        self.state = self.state.wrapping_mul(1664525).wrapping_add(1013904223);
        self.state
    }
}

fn hash_tile(x: i32, y: i32) -> u32 {
    let h = (x as u32).wrapping_mul(374761393)
        .wrapping_add((y as u32).wrapping_mul(668265263));
    h ^ (h >> 13)
}

#[derive(Debug, PartialEq)]
enum Deco { Flower, Stone, Mushroom, Grass, Crack }

fn decorate_tile(tx: i32, ty: i32) -> Vec<(Deco, u32, u32)> {
    let mut rng = SeededRng::new(hash_tile(tx, ty));
    let count = rng.next_u32() % 4;  // 0-3 装饰
    (0..count).map(|_| {
        let kind = match rng.next_u32() % 5 {
            0 => Deco::Flower, 1 => Deco::Stone, 2 => Deco::Mushroom,
            3 => Deco::Grass, _ => Deco::Crack,
        };
        let x = rng.next_u32() % 64;
        let y = rng.next_u32() % 64;
        (kind, x, y)
    }).collect()
}

fn main() {
    let t1 = decorate_tile(3, 5);
    let t2 = decorate_tile(3, 5);
    let t3 = decorate_tile(4, 5);
    println!("tile (3,5) #1: {:?}", t1);
    println!("tile (3,5) #2: {:?}", t2);
    println!("tile (4,5):    {:?}", t3);
    assert_eq!(t1, t2, "同坐标应相同");
    assert_ne!(t1, t3, "不同坐标应不同");
    println!("OK");
}
```

## 8 · Rust / Arch 落地代码

```rust
#[derive(Clone)]
struct Bitmap {
    width: usize,
    height: usize,
    pixels: Vec<[u8; 4]>,
}

impl Bitmap {
    fn new(width: usize, height: usize, fill: [u8; 4]) -> Self {
        Self { width, height, pixels: vec![fill; width * height] }
    }

    fn blend_at(&mut self, dst_x: usize, dst_y: usize, src: &Bitmap) {
        for y in 0..src.height {
            for x in 0..src.width {
                let dx = dst_x + x;
                let dy = dst_y + y;
                if dx >= self.width || dy >= self.height { continue; }
                let dst = &mut self.pixels[dy * self.width + dx];
                let s = src.pixels[y * src.width + x];
                let sa = s[3] as f32 / 255.0;
                if sa == 0.0 { continue; }
                for i in 0..3 {
                    dst[i] = ((s[i] as f32 * sa + dst[i] as f32 * (1.0 - sa))
                        .min(255.0)) as u8;
                }
            }
        }
    }

    fn average_rgb(&self) -> (f32, f32, f32) {
        let (mut r, mut g, mut b) = (0u32, 0u32, 0u32);
        for p in &self.pixels {
            r += p[0] as u32;
            g += p[1] as u32;
            b += p[2] as u32;
        }
        let n = self.pixels.len() as u32;
        (r as f32 / n as f32, g as f32 / n as f32, b as f32 / n as f32)
    }
}

struct SeededRng { state: u32 }
impl SeededRng {
    fn new(seed: u32) -> Self { Self { state: seed } }
    fn next_u32(&mut self) -> u32 {
        self.state = self.state.wrapping_mul(1664525).wrapping_add(1013904223);
        self.state
    }
}

fn hash_tile(x: i32, y: i32) -> u32 {
    let h = (x as u32).wrapping_mul(374761393)
        .wrapping_add((y as u32).wrapping_mul(668265263));
    h ^ (h >> 13)
}

fn make_decoration(kind: u32) -> Bitmap {
    // 简化:用颜色代替真图
    let color = match kind % 5 {
        0 => [255, 100, 100, 200],  // Flower(红)
        1 => [120, 120, 120, 200],  // Stone(灰)
        2 => [200, 200, 200, 200],  // Mushroom(白)
        3 => [50, 150, 50, 200],    // Grass(深绿)
        _ => [80, 60, 40, 200],     // Crack(棕)
    };
    Bitmap::new(8, 8, color)
}

fn composite_tile(tile_x: i32, tile_y: i32) -> Bitmap {
    // 底层:草地(深绿)
    let mut result = Bitmap::new(64, 64, [50, 120, 40, 255]);

    let mut rng = SeededRng::new(hash_tile(tile_x, tile_y));
    let count = rng.next_u32() % 5;  // 0-4 装饰
    for _ in 0..count {
        let kind = rng.next_u32() % 5;
        let x = (rng.next_u32() % 56) as usize;  // 留 8 像素边距
        let y = (rng.next_u32() % 56) as usize;
        let deco = make_decoration(kind);
        result.blend_at(x, y, &deco);
    }
    result
}

fn main() {
    let tile_a = composite_tile(3, 5);
    let tile_b = composite_tile(3, 5);
    let tile_c = composite_tile(4, 5);

    println!("tile (3,5) avg RGB: {:?}", tile_a.average_rgb());
    println!("tile (3,5) again:   {:?}", tile_b.average_rgb());  // 同
    println!("tile (4,5):         {:?}", tile_c.average_rgb());  // 不同

    assert_eq!(tile_a.average_rgb(), tile_b.average_rgb());
    assert_ne!(tile_a.average_rgb(), tile_c.average_rgb());
    println!("OK - 同 tile 一致,不同 tile 不同");
}
```
