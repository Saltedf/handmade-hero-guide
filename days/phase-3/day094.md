# Day 094 · sRGB 转光线性空间

> 你画了 sprite,光照对不上?光照在「暗」区域看起来奇怪?混合两个颜色得到的结果比预期暗?99% 的可能:**你在 sRGB 空间里做光照计算,而光照必须在 linear 空间**。今天 Casey 花一整集讲这个被无数初学者跳过的概念。这是图形学里**最容易踩坑、踩了之后最难发现、修了之后画面立刻不一样**的一个知识点。

## 0 · 为什么要有这一天

你的纹理图是 PNG。PNG 存的是 RGB 三通道,每个通道 0-255。直觉上,`(128, 128, 128)` 是 50% 灰度。**但物理上,这像素发出的光强不是「最大亮度的一半」**——它发出的是约 21.4% 的光强。

为什么?因为 PNG(以及 JPEG、BMP、几乎所有图片格式)存的是 **sRGB 编码**——一种**非线性**编码,设计来匹配人眼对暗色更敏感的特性。

人眼感知亮度的曲线**不是直线**。从全黑到 50% 灰,人眼感觉亮度已经跳了一大半;从 50% 灰到全白,感觉只跳了一小点。所以图片格式把**更多的码点**分给暗色区域——存 50% 灰时,实际光强是 21.4%,但人眼觉得是 50%。

**这有什么问题?** 当你在游戏里做光照(比如「光强 0.5 × 表面颜色 0.5」),你期望结果是 0.25(数学上 0.5×0.5)。但你**没察觉自己在用 sRGB 编码的数做线性数学**——你在 0.5(实际光强 21.4%)× 0.5(实际 21.4%)= 4.6% 实际光强,而你以为得到了 25%。

**这就是为什么你的游戏画面比 Casey 的暗、暗部一团黑、混合色不自然**。修复方法:**所有光照计算必须在 linear 空间**,而不是 sRGB 空间。具体流程:

```
1. 从纹理读 sRGB 颜色 (0.5, 0.5, 0.5)
2. 转 linear: 0.5^2.2 ≈ 0.218(实际光强)
3. 在 linear 空间做光照: light_intensity × linear_color
4. 把结果转回 sRGB: linear^(1/2.2)
5. 写到 framebuffer
```

听起来只是 2 次幂运算,但这两个幂运算是**图形学最重要的两步**。Casey 今天花一整集讲透。

心理锚点:看完今天,你能向队友解释「为什么 PNG 颜色不能直接做光照」。你能用 Rust 写 sRGB ↔ linear 转换。你能用 30 秒说清「gamma 2.2 是什么」。

## 1 · Casey 今天做了什么

Casey 今天做的事情:

1. 在白板上画出 sRGB 曲线 vs linear 直线,展示它们的差异
2. 推导 sRGB → linear 的转换公式(标准 sRGB 是分段函数,简化版用 `x^2.2`)
3. 推导 linear → sRGB 的反转换(`x^(1/2.2)`)
4. 介绍 sRGB 查表(LUT, lookup table)——预算 256 项的查找表,运行时 O(1) 查询,避免每像素调用 `powf`

Casey 强调一个工程细节:**framebuffer 也是 sRGB 的**(因为屏幕直接显示)。所以最后写 framebuffer 时也要转回 sRGB。或者用「sRGB framebuffer」让硬件自动转。

## 2 · 心智模型

### 费曼类比:耳机音量条 vs 实际声压

想象你的耳机音量条是 0 到 100。但你的耳朵对**小声**更敏感——音量从 0 到 50 听起来已经「半响了」,从 50 到 100 听起来「再加一倍」。所以耳机制造商把音量条做成**非线性**:数字 50 对应实际 21% 的声压,数字 100 对应 100%。

图片格式就是这样的「数字条」:
- 数字 0(全黑)= 实际光强 0%
- 数字 128(中灰)= 实际光强 21.4%(不是 50%!)
- 数字 255(全白)= 实际光强 100%

**sRGB 编码就是「按人眼感知非线性的数字条」**。`128 / 255 = 0.5` 是**编码值**(也叫 sRGB 空间),不是实际光强(也叫 linear 空间)。

光照计算要在 **实际光强空间** 里做——因为光的物理叠加是**线性的**(两束光加在一起,光强直接相加)。如果在 sRGB 空间做加法,你做的是「数字条加法」,不是「物理光强加法」,结果就错。

### 严谨原理

#### 2.1 sRGB 标准的定义

sRGB 是 HP 和 Microsoft 1996 年制定的标准,模拟 CRT 显示器的非线性响应。**严格定义**是分段函数:

```
// sRGB encoded (0..1) → linear (0..1)
fn srgb_to_linear(c: f32) -> f32 {
    if c <= 0.04045 {
        c / 12.92
    } else {
        ((c + 0.055) / 1.055).powf(2.4)
    }
}

// linear → sRGB encoded
fn linear_to_srgb(c: f32) -> f32 {
    if c <= 0.0031308 {
        c * 12.92
    } else {
        1.055 * c.powf(1.0 / 2.4) - 0.055
    }
}
```

**两段函数**:
- 暗部(< 0.04045):线性段(避免 log(0) 问题)
- 亮部:幂函数 `^2.4`

**简化版**:很多人用近似 `c^2.2` 而不是严格的 `^2.4 + 分段`。差异小(< 1%),但计算简单。Casey HH 一开始用 `^2.2`,后面可以换成精确版。

#### 2.2 为什么是 2.2?

CRT 显示器(阴极射线管)的物理特性:输入电压 V,输出亮度 ≈ V^2.2(因为电子枪的非线性响应)。这个「^2.2」就是 **gamma**。

后来 LCD/OLED 沿用了 sRGB(为了向后兼容)。所以今天所有显示器都「假装自己是 gamma 2.2 的 CRT」。

人眼的感知曲线恰好是「^1/2.2 反过来」——人眼对暗色更敏感。两个非线性叠加在一起,反而让 sRGB 编码很**经济**:8-bit 数据(256 级)在 sRGB 编码下,覆盖人眼可分辨的所有亮度等级。如果用 linear 编码,需要 12-bit 才能避免暗部 banding。

#### 2.3 灾难演示:在 sRGB 空间做混合

考虑一个红色像素 `(255, 0, 0)` 和一个绿色像素 `(0, 255, 0)`。50/50 混合应该是什么颜色?

**直觉(错误)**:`(128, 128, 0)` 暗黄。

**正确**:在 linear 空间混合。
- sRGB (1, 0, 0) → linear (1, 0, 0)(全白和全黑不受 gamma 影响)
- sRGB (0, 1, 0) → linear (0, 1, 0)
- linear 平均 = (0.5, 0.5, 0)
- linear (0.5, 0.5, 0) → sRGB (0.735, 0.735, 0)
- 写回 8-bit:(188, 188, 0)——比直觉的 (128, 128, 0) 亮很多!

为什么?因为 linear 0.5 是「实际半光强」,在 sRGB 编码下显示为 0.735(因为人眼觉得 0.735 是半亮)。

**如果你直接在 sRGB 空间做 `(128, 128, 0)`,实际光强只有 (0.218, 0.218, 0) = 实际暗了一半**。这就是为什么不做 gamma 校正的游戏,暗部一团黑。

#### 2.4 完整正确流程

```
1. 加载纹理:读 sRGB 字节,转 linear f32 存(预算一次)
   linear_tex[x] = srgb_to_linear(srgb_tex[x] / 255.0)

2. 渲染时:在 linear 空间做所有计算
   final_linear = lighting(material=linear_tex, ...)
   final_linear = alpha_blend(bg_linear, fg_linear, alpha)

3. 写 framebuffer:转回 sRGB
   fb_srgb = linear_to_srgb(final_linear)
   write_byte(fb_srgb * 255.0)
```

#### 2.5 优化:LUT (lookup table)

`powf` 慢(每次几十 ns)。但 sRGB 输入只有 256 种(8-bit),所以**预算 256 项查找表**:

```rust
// 程序启动时算一次
let srgb_to_linear_lut: [f32; 256] = {
    let mut t = [0.0; 256];
    for i in 0..256 {
        let s = i as f32 / 255.0;
        t[i] = srgb_to_linear(s);
    }
    t
};

// 渲染时:O(1) 查表
let linear = srgb_to_linear_lut[srgb_byte as usize];
```

256 个 f32 = 1KB,L1 cache 完全装得下,查询快得跟数组索引一样。Casey HH 用这个优化。

### Rust 完整实现

```rust
fn srgb_to_linear(c: f32) -> f32 {
    if c <= 0.04045 { c / 12.92 } else { ((c + 0.055) / 1.055).powf(2.4) }
}
fn linear_to_srgb(c: f32) -> f32 {
    if c <= 0.0031308 { c * 12.92 } else { 1.055 * c.powf(1.0 / 2.4) - 0.055 }
}

// LUT
struct SrgbLut {
    s2l: [f32; 256],  // sRGB byte → linear f32
}
impl SrgbLut {
    fn new() -> Self {
        let mut s2l = [0.0; 256];
        for i in 0..256 {
            let s = i as f32 / 255.0;
            s2l[i] = srgb_to_linear(s);
        }
        Self { s2l }
    }
    fn s2l_byte(&self, b: u8) -> f32 {
        self.s2l[b as usize]
    }
}

fn main() {
    let lut = SrgbLut::new();
    // 测试:中灰(128)的实际光强
    let mid_gray = lut.s2l_byte(128);
    println!("sRGB 128 = linear {:.4}", mid_gray);
    // 预期:0.2158,不是 0.5
    assert!((mid_gray - 0.2158).abs() < 0.01);

    // 混合测试:sRGB (255,0,0) 和 (0,255,0) 在 linear 空间混合
    let red_l = lut.s2l_byte(255);    // 1.0
    let green_l = lut.s2l_byte(255);  // 1.0(注意,我搞错了,这里应该是另一通道)
    // 修正:混合的是红色和绿色,实际应该是:
    let r_linear = [lut.s2l_byte(255), lut.s2l_byte(0), lut.s2l_byte(0)];   // 红
    let g_linear = [lut.s2l_byte(0), lut.s2l_byte(255), lut.s2l_byte(0)];   // 绿
    // 50/50 混合(linear 空间)
    let mixed = [
        (r_linear[0] + g_linear[0]) * 0.5,
        (r_linear[1] + g_linear[1]) * 0.5,
        (r_linear[2] + g_linear[2]) * 0.5,
    ];
    // 转回 sRGB
    let mixed_srgb = [
        (linear_to_srgb(mixed[0]) * 255.0).round() as u8,
        (linear_to_srgb(mixed[1]) * 255.0).round() as u8,
        (linear_to_srgb(mixed[2]) * 255.0).round() as u8,
    ];
    println!("mixed sRGB: {:?}", mixed_srgb);
    // 预期:大约 (188, 188, 0),不是 (128, 128, 0)
    assert!(mixed_srgb[0] > 150);  // 比 128 亮
}
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

sRGB 在游戏开发里处处都是:

1. **纹理加载**:PNG/JPEG 都是 sRGB。读取后立即转 linear(或让 GPU 标记为 sRGB texture,GPU 采样时自动转)
2. **shader 颜色输入**:`vec3(0.5, 0.5, 0.5)` 在 GLSL 里是**用户输入的 sRGB 值**(因为代码里写的就是这个数),要手动转 linear 再用
3. **framebuffer**:屏幕是 sRGB 的。OpenGL 有 `GL_SRGB8_ALPHA8` 格式,写入时自动 linear → sRGB
4. **HUD/UI**:UI 元素的颜色也要做 gamma 校正,否则和 3D 场景色调不一致

**坑:光照衰减**。距离光 `1/d²`(物理上)。如果你在 sRGB 空间算,光照衰减感觉不对。linear 空间算才对。

**坑:alpha 混合**。Day 095 详细讲。alpha 混合是「按权重加」,**必须在 linear 空间做**,否则暗部混合错。

**Casey 后续哪天会用到**:
- Day 095 — 预乘 alpha 在 linear 空间
- Day 096 — 光照计算在 linear 空间
- Day 097 — 法线贴图(法线本身在 linear 空间)
- Day 200+ — PBR(物理正确反射必须在 linear)

### 3.2 · 🎨 图形学视角

**色彩空间家族**:
- **sRGB**:标准显示器色彩空间(gamma ≈ 2.2)
- **Rec.709**:HDTV 标准,几乎等于 sRGB
- **Display P3**:苹果广色域,比 sRGB 多 35% 色域
- **Rec.2020**:4K/8K UHD,广色域
- **ACES**:电影工业色彩管线

**HDR (High Dynamic Range)**:不再用 0-1 范围,允许 > 1 的光强(代表比白色更亮)。HDR 显示器直接接受 linear 输入,不需要 gamma。Casey HH 用 LDR(低动态范围),全程 sRGB。

**色彩管理**:操作系统层做的「确保 PNG 在 sRGB 显示器上看起来正确,在 P3 显示器上也看起来正确」。Linux 上是 colord,macOS 上是 ColorSync。游戏开发通常绕过这些,直接管理自己的色彩管线。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的色彩管理:

```bash
# 查看当前显示器的色彩配置文件
colormgr get-devices
# 或
ls /usr/share/color/icc/

# 改变显示器的 gamma(硬件 LUT)
xgamma -gamma 1.0   # X11
# 或 wayland 上:
wlr-randr --output eDP-1 --gamma 1.0:1.0:1.0
```

但游戏开发里**不应该依赖这些**——玩家显示器各种各样。游戏应该在内部做完整色彩管线,把 sRGB framebuffer 给 OS,OS 再做最后的硬件适配。

### 3.4 · 🦀 Rust 生态视角

Rust 里 sRGB 转换的几个 crate:

1. **`palette`** — 完整色彩科学库,支持 sRGB/Linear/P3/Rec2020/CIELAB 等
   ```rust
   use palette::{Srgb, LinSrgb};
   let s = Srgb::new(0.5, 0.5, 0.5);
   let l: LinSrgb = s.into_linear();
   ```
2. **`gamma`** — 极简,只有 sRGB ↔ linear 转换
3. **`image` crate** 的 `image::ColorType::Rgba8` 默认假设 sRGB,但不会自动转——你负责

**SIMD 优化**:`powf` 不能 SIMD 化(它是分段函数 + 表查找)。但 LUT 可以——`vpgatherdps`(AVX2)指令一次查 8 个 f32。Casey Day 200+ 用这个。

**`const fn` 预算 LUT**:Rust 1.31+ 支持 const fn,可以在编译期算 LUT:

```rust
const SRGB_TO_LINEAR: [f32; 256] = {
    let mut t = [0.0; 256];
    let mut i = 0;
    while i < 256 {
        let s = i as f32 / 255.0;
        t[i] = if s <= 0.04045 { s / 12.92 } else { ((s + 0.055) / 1.055).powf(2.4) };
        i += 1;
    }
    t
};
```

可惜 `powf` 还不是 const fn(浮点特殊函数受限),所以现在用 `lazy_static` 或 `OnceLock`。

## 4 · 认知地图

### 4.1 上级

- **色彩科学 (color science)** — 研究颜色感知和编码的学科
- **色彩管线 (color pipeline)** — 从美术创建内容到玩家屏幕显示的完整色彩管理链路
- **信号编码 (signal encoding)** — 把连续信号编码成离散数字的方式

### 4.2 同级

| 编码 | 用途 | gamma |
|---|---|---|
| Linear | 物理计算、光照 | 1.0(无变换) |
| sRGB | 图片格式、显示器 | ≈ 2.2(分段) |
| Rec.709 | HDTV | ≈ 2.4(不同分段) |
| ProPhoto RGB | 专业摄影 | 1.8 |
| HDR10 (PQ) | HDR 显示器 | 不同的感知曲线 |

### 4.3 下级

- **gamma 函数** — `c^γ` 形式的幂函数
- **LUT (lookup table)** — 预算 + 查表加速的技术
- **bit depth** — 每通道位数,8/10/12/16
- **banding** — 颜色梯度不平滑,出现条纹(精度不够导致)

## 5 · 对照与变奏

### CPU vs GPU sRGB 转换

| | CPU | GPU |
|---|---|---|
| 转换实现 | LUT 数组 | 硬件 sRGB 采样器 |
| 速度 | ~5ns/像素 | 0(免费) |
| 控制精度 | 完全 | 受驱动控制 |

OpenGL ES 3.0+ 支持 `GL_SRGB8_ALPHA8` 纹理格式,GPU 硬件采样时自动 sRGB → linear。Framebuffer 用 `GL_FRAMEBUFFER_SRGB` 开启自动 linear → sRGB 写出。**这就是 GPU 时代开发者基本不用关心 sRGB 的原因**——硬件全做了。

### LDR vs HDR

- **LDR (Low Dynamic Range)**:8-bit 通道,sRGB 编码。Casey HH 用这个。
- **HDR**:10/12/16-bit 通道,Linear 或 PQ 编码。允许光强 > 1.0(代表比白色更亮)。HDR 显示器需要。

### 历史:sRGB 之前

1990s 之前游戏直接写 VGA 寄存器的 8-bit 索引,没有色彩管理概念。sRGB 1996 年标准化。2000s 中期 GPU 开始支持硬件 sRGB。2010s HDR 兴起。今天 sRGB 仍是默认,但 HDR 逐渐普及。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:你看到一段 shader 代码 `vec3 color = texture(tex, uv).rgb * 0.5;`,假设 tex 是 sRGB 纹理(没有 sRGB 标记)。这段代码错在哪?应该怎么改?

**参考解答**:在 sRGB 空间做乘法 0.5,得到的是「编码值减半」而不是「光强减半」。实际光强变成 `(srgb/2)^2.2`,而不是 `srgb^2.2 * 0.5`。

**正确做法**:
1. 把 tex 标记为 sRGB(`glTexImage2D(... GL_SRGB8_ALPHA8 ...)`),GPU 自动 sRGB → linear
2. 在 linear 空间 `× 0.5`(`texture()` 返回的就是 linear)
3. 输出 framebuffer 时,framebuffer 标记为 sRGB(`glEnable(GL_FRAMEBUFFER_SRGB)`),GPU 自动 linear → sRGB

如果不用 GPU 硬件支持,就手写:读 sRGB → 转 linear → 算 → 转 sRGB → 写。

### Lv2 · 动手实践

**题**:写一个程序,生成一张 256×256 PNG,从左到右是「在 sRGB 空间线性插值」的灰度(0 → 255),从上到下是「在 linear 空间线性插值」的灰度(0 → 1,然后转 sRGB 写)。对比两个渐变的视觉效果。

完成标准:生成的 PNG 里能看到上下两个渐变——上面的(sRGB 插值)暗部变化快、亮部变化慢;下面的(linear 插值)变化均匀。这是诊断 sRGB 问题的经典图。

**参考解答**:

```rust
// Cargo.toml
// [dependencies]
// image = "0.25"

fn srgb_to_linear(c: f32) -> f32 {
    if c <= 0.04045 { c / 12.92 } else { ((c + 0.055) / 1.055).powf(2.4) }
}
fn linear_to_srgb(c: f32) -> f32 {
    if c <= 0.0031308 { c * 12.92 } else { 1.055 * c.powf(1.0 / 2.4) - 0.055 }
}

fn main() {
    let w = 256;
    let h = 256;
    let mut pixels = Vec::with_capacity((w * h * 4) as usize);
    for y in 0..h {
        for x in 0..w {
            let top_half = y < h / 2;
            let v = if top_half {
                // 上半:sRGB 空间线性插值
                x as f32 / (w - 1) as f32
            } else {
                // 下半:linear 空间线性插值,然后转 sRGB
                let t = x as f32 / (w - 1) as f32;
                linear_to_srgb(t)
            };
            let byte = (v * 255.0).round() as u8;
            pixels.push(byte);  // R
            pixels.push(byte);  // G
            pixels.push(byte);  // B
            pixels.push(255);   // A
        }
    }
    image::save_buffer("/tmp/gamma_test.png", &pixels, w, h, image::ColorType::Rgba8).unwrap();
    println!("saved to /tmp/gamma_test.png");
}
```

观察:上半部分(sRGB 插值)在中部偏左就有「明显变亮」(因为 sRGB 编码对暗色放大感知);下半部分(linear 插值)变化更均匀,中部看起来「真正一半亮」。

### Lv3 · 迁移设计

**题**:游戏里你有两种光:**环境光**(0.2 强度)和**方向光**(0.8 强度)。你想要表面材质(纹理采样的颜色)在两种光下分别被照亮。如果纹理是 sRGB(没有标记),你应该:
1. 直接在 sRGB 空间做 `tex * 0.2` 和 `tex * 0.8`?
2. 还是先 sRGB → linear,乘,再 linear → sRGB?

**计算具体数值**:假设纹理是 sRGB (200, 100, 50),环境光 0.2 后,两种做法结果各是多少?对比差异。

**提示**:
- 法 1:`(200, 100, 50) * 0.2 = (40, 20, 10)`——直接字节乘
- 法 2:200/255 = 0.784 → srgb_to_linear(0.784) ≈ 0.583 → × 0.2 = 0.117 → linear_to_srgb(0.117) ≈ 0.385 → × 255 ≈ 98

差异:法 1 是 40,法 2 是 98。后者亮得多——因为 sRGB (200) 在 linear 空间是 0.583(实际光强 58%),0.2 倍后是 11.7%,转回 sRGB 编码后看起来比 sRGB 直接乘 0.2 亮得多。

法 2 是物理正确的。法 1 在视觉上会让暗光下的物体「过暗」。

## 8 · Rust / Arch 落地代码

### 完整可跑示例(在渲染器里集成 sRGB)

把 §2 的转换函数加到 sprite 渲染器:

```rust
// 纹理加载时预算 linear 版本
struct LinearBitmap {
    width: u32,
    height: u32,
    pixels: Vec<[f32; 4]>,  // 直接存 linear RGBA,每通道 0..1
}

impl LinearBitmap {
    fn from_srgb_bytes(width: u32, height: u32, srgb: &[u8]) -> Self {
        let lut = build_srgb_lut();
        let pixels = srgb.chunks(4).map(|c| [
            lut[c[0] as usize],
            lut[c[1] as usize],
            lut[c[2] as usize],
            c[3] as f32 / 255.0,  // alpha 不参与 gamma
        ]).collect();
        Self { width, height, pixels }
    }
}

fn build_srgb_lut() -> [f32; 256] {
    let mut t = [0.0; 256];
    for i in 0..256 {
        let s = i as f32 / 255.0;
        t[i] = if s <= 0.04045 { s / 12.92 } else { ((s + 0.055) / 1.055).powf(2.4) };
    }
    t
}

// 渲染时直接用 linear,无需转换
// 写 framebuffer 时转回 sRGB
fn write_pixel_srgb(fb: &mut Vec<u8>, idx: usize, linear: [f32; 3]) {
    let s = |c: f32| -> u8 {
        let l = if c <= 0.0031308 { c * 12.92 } else { 1.055 * c.powf(1.0 / 2.4) - 0.055 };
        (l * 255.0).round().clamp(0.0, 255.0) as u8
    };
    fb[idx * 4]     = s(linear[0]);
    fb[idx * 4 + 1] = s(linear[1]);
    fb[idx * 4 + 2] = s(linear[2]);
    fb[idx * 4 + 3] = 255;
}

fn main() {
    let srgb_bytes = [200, 100, 50, 255];  // 单像素测试
    let tex = LinearBitmap::from_srgb_bytes(1, 1, &srgb_bytes);
    println!("linear pixel: {:?}", tex.pixels[0]);
    // 预期:[0.583, 0.127, 0.031, 1.0]——比 sRGB 编码值小得多
}
```

**关键 Rust 特性**:
- `chunks(4)` — 把 `&[u8]` 按 4 字节切片迭代,适合 RGBA 数据
- `clamp(0.0, 255.0)` — 防止 round 后超出 u8 范围
- `lazy_static!` 或 `OnceLock` 启动时算 LUT——Rust 没有静态全局可变状态,需要这些封装

### Troubleshooting

- **画面变得太暗** — 你可能 linear → sRGB 转了两次(一次在 shader,一次在 framebuffer)。检查是不是 GL_FRAMEBUFFER_SRGB 已开启但你又手写了
- **画面变得太亮** — 反过来,该转的没转
- **LUT 性能没提升** — LUT 没装进 cache(数据布局不对)。试 `#[repr(align(64))]` 让 LUT 对齐 cache line
- **powf 在 const fn 里报错** — Rust 还不支持 `powf` 作为 const fn。用 `OnceLock` 或启动时初始化
