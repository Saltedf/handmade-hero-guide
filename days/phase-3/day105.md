
# Day 105 · 清理渲染器 API

> 从 Day 088 引入 push buffer、Day 093 加纹理四边形、Day 097 加法线贴图、Day 100 加反射,到 Day 104 翻 Y 轴,渲染代码已经积累了一大堆零散的入口。今天 Casey 把它们统一打包成一个 **`Renderer` struct**——持 push buffer + back buffer + camera,对外暴露 `push_bitmap / push_rect / push_text / submit` 等稳定接口。这是 HH 经典的「**重构日**」(Day 24 / 39 / 65 / 105 / 134 / 199 / 269 ……),目的是**让接下来的 Day 108 透视投影和 Day 235 切 OpenGL 不会因为入口混乱而崩盘**。

## 0 · 为什么要有这一天

如果你做过几个真实项目,你一定碰到过这种代码:**功能越加越多,但每个功能都从零写一遍胶水**。一开始只是 `blit_bitmap(buf, x, y, w, h)`;后来要旋转,加了 `blit_bitmap_rotated(buf, x, y, angle)`;再后来要纹理,加了 `blit_textured_quad(buf, ...)`,需要法线又加了 `blit_with_normal(...)`,要光照了再加 `blit_lit(...)`。

等到第 10 个变体出现时,游戏代码已经不知道该用哪个 API。每个 API 签名略有不同,每个 API 内部状态略有不同,**调用者必须读源码才知道「这个变体有没有应用 camera,有没有应用 gamma」**。这是典型的「**接口膨胀失控**」,工程灾难的开始。

Casey 在今天做的事很经典:**先把所有渲染相关状态收到一个 `Renderer` struct 里**( framebuffer、camera、gamma 表、push buffer 头指针……),**再把所有渲染入口收到这个 struct 的方法上**(`renderer.push_bitmap(...)` / `renderer.push_clear(...)` / `renderer.submit()`)。游戏代码从此只看到 `Renderer`,再也不直接碰 framebuffer 像素。

这个重构带来三个直接收益。第一,**游戏层和渲染层彻底解耦**——游戏代码不再知道帧缓冲在哪、是什么格式、Y 朝哪边。第二,**未来切到 OpenGL 时游戏代码零改动**——只要 `Renderer` 内部把 `push_bitmap` 翻译成 `glDrawArrays`,游戏代码完全感觉不到差异。第三,**测试和调试变简单**——你可以构造一个 `Renderer` 接受 dummy buffer,跑游戏代码,断言「这一天推了多少个 push command」而不真画像素。

完成今天的重构后,你将拥有一套**稳定的渲染入口**,后面 Day 106 的世界缩放、Day 108 的透视投影、Day 235 的 OpenGL 切换都建立在这套入口之上。这是软件工程里「**用接口隔离变化**」最直接的实战。

## 1 · Casey 今天做了什么(HH 脉络,简述)

Casey 在视频里做的事可以归纳为四步。

第一步,他列出过去十几天积累的所有渲染相关入口函数:`DrawBitmap`、`DrawRectangle`、`DrawText`、`PushBitmap`、`PushRect`、`PushClear`……并标记每个函数依赖哪些状态(camera、framebuffer、gamma table、sRGB→linear 查表)。这一步是在**画依赖图**,识别「哪些状态应该打包到一起」。

第二步,他新建一个 `game_renderer` 或 `game_offscreen_buffer + game_render_commands` 这样的聚合 struct,把上述状态都搬进去。`game_render_commands` 就是从 Day 088 起就存在的 push buffer,今天它正式成为「渲染器的核心数据结构」。

第三步,他把入口函数变成「**接受 `Renderer *`**」的方法:`PushBitmap(Renderer *, ...) → void`。函数体不变,只是签名统一了。游戏代码改成 `renderer.push_bitmap(...)`。

第四步,他清理了一遍「**全局变量**」——之前可能有 `global_framebuffer`、`global_camera` 之类,现在都进 `Renderer`。这是「**消除全局可变状态**」的经典动作,对 Rust 学习者尤其重要(Rust 的所有权模型天然反对全局可变状态)。

## 2 · 心智模型

**费曼类比**。把 Renderer 想象成一个**戏剧舞台管理员**。游戏代码是导演,负责「这一幕要发生什么」(玩家走到哪里、怪物开火)。舞台管理员手里有:舞台(framebuffer)、灯光(camera、光照)、剧本册(push buffer)、道具仓库(textures)。

导演不直接搬道具到舞台上,而是写小纸条:「第 3 秒,在舞台中央放一把椅子」。纸条丢进管理员手里的纸条盒(push buffer)。等这一幕要开演了(`submit`),管理员按纸条顺序把道具摆好、灯光打好、舞台亮起。

如果有一天剧院决定换舞台(从软渲染 framebuffer 换到 OpenGL 上下文),**导演写的纸条一字不改**——只是管理员内部「摆道具」的方式变了。这就是「**接口隔离变化**」的实物版。

**严谨原理**。接口隔离背后的核心概念是「**抽象数据类型(ADT)**」:把一组数据和一组操作打包,对外只暴露操作,不暴露内部布局。Rust 的 `struct` + `impl` + `pub` 关键字三件套就是 ADT 的语言级支持。

我们来把这个抽象做实。先看一段「**坏味道**」的代码,这是重构前的样子:

```rust
// === 重构前:全局状态散落 ===
static mut FRAMEBUFFER: *mut u32 = std::ptr::null_mut();   // 帧缓冲裸指针
static mut FB_WIDTH: i32 = 0;                                // 帧缓冲宽度
static mut FB_HEIGHT: i32 = 0;                               // 帧缓冲高度
static mut CAMERA_POS: (f32, f32) = (0.0, 0.0);              // 相机位置
static GAMMA_TABLE: [u8; 256] = build_gamma_table();         // sRGB 查表

unsafe fn draw_bitmap(id: BitmapId, x: f32, y: f32) {
    // ... 直接写 FRAMEBUFFER[i] = ...
}

fn draw_rect(x: f32, y: f32, w: f32, h: f32, color: u32) {
    // ... 又一次直接写 FRAMEBUFFER[i] = ...
}
```

这段代码的病灶有三处:第一,所有渲染入口共用一份全局状态,任何线程碰一下就乱;第二,加新入口时(`draw_textured_quad_lit`)必须重新读一遍全局才知道「相机变换应用了吗」;第三,要测试某个函数,你必须真的分配 framebuffer、设置全局,完全不能 mock。

重构后的形态是这样的(下面先看签名,代码体我们逐块展开):

```rust
pub struct Renderer {
    framebuffer: Framebuffer,        // 替代全局 FRAMEBUFFER / FB_WIDTH / FB_HEIGHT
    camera: Camera,                  // 替代全局 CAMERA_POS
    gamma_table: [u8; 256],          // 替代全局 GAMMA_TABLE
    push_buffer: PushBuffer,         // Day 088 引入的命令队列
    textures: TextureArena,          // 纹理仓库
}

impl Renderer {
    pub fn push_clear(&mut self, color: [f32; 4]) { /* ... */ }
    pub fn push_bitmap(&mut self, dst: Rect, id: BitmapId, tint: [f32; 4]) { /* ... */ }
    pub fn push_rect(&mut self, dst: Rect, color: [f32; 4]) { /* ... */ }
    pub fn push_text(&mut self, pos: Vec2, text: &str, color: [f32; 4]) { /* ... */ }
    pub fn submit(&mut self) { /* 消费 push_buffer,画到 framebuffer */ }
}
```

注意几个 Rust 风格关键点:`&mut self` 表示「这个方法独占修改 Renderer」——`submit` 在写 framebuffer 时持有 `&mut`,编译器保证没有别处同时读。`push_*` 方法返回 `()`(空),错误处理走内部统计或后续 verify。颜色统一用 `[f32; 4]`(linear 空间 RGBA,见 Day 094),不再是 `u32`——这避免每个调用点都自己 pack/unpack。

**Frame、Arena、Buffer 三种内存布局**。Renderer 内部有三种「装东西」的数据结构,初学者容易混。我们一次性区分清楚:

- **Framebuffer**:一块连续的 `u32` 数组(每像素 ARGB),代表「**当前帧画面**」。`submit` 写它,平台层(softbuffer)把它 blit 到窗口。
- **PushBuffer**:一段字节缓冲,游戏代码往里 push 变长命令(每条命令有 header + payload)。`submit` 从头读到尾,逐条执行。这是 Day 088 的核心数据结构。
- **TextureArena**:一个 `HashMap<BitmapId, Bitmap>` 或 `Vec<Bitmap>`,存所有已加载纹理。游戏代码 push 命令时只给 `BitmapId`,`submit` 才真正从 arena 取纹理数据。

理解这三者的关系后,Renderer 的工作流程就是一条直线:**游戏代码 → push 到 PushBuffer → submit 从 PushBuffer 读、查 TextureArena、写 Framebuffer → 平台层显示 Framebuffer**。

**重构的安全网**。重构最大风险是「**改完行为变了但没发现**」。Casey 用的是「**视觉对照**」:重构前截一张图,重构后截一张图,人眼对比。这够用但费眼。Rust 学习者可以用更系统的方法:写一个「**录制 push 命令到文件**」的测试模式,重构前录一份 baseline,重构后跑测试对比命令序列是否完全一致。这就是「**黄金文件(golden file)测试**」,在 Rust 生态用 `insta` crate 一行命令就能上。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏引擎界对 Renderer 抽象有几种主流做法,了解这些做法能让你读别的引擎源码不慌。

**Unreal Engine 的 FRendererModule**。Unreal 把渲染分成「high-level draw policy」和「low-level RHI(Render Hardware Interface)」。游戏代码 push `FMeshBatch` 这种高层命令,RHI 把它翻译成 D3D12 / Vulkan / Metal 的 draw call。和 Casey 的 push buffer 是同一种思路,只是规模大几个数量级。

**Unity 的 SRP(Scriptable Render Pipeline)**。Unity 把渲染管线暴露成 C# 脚本——游戏代码可以「**写一个 RenderPipelineAsset**」描述「先画不透明、再画透明、最后画 UI」,引擎负责调度。这是「**配置驱动渲染**」,比 Casey 的 push buffer 更高一层抽象。

**Bevy(wgpu 生态)**。Rust 的 Bevy 引擎用 `RenderApp` 子 schedule + `RenderPhase` 收集 draw command,本质也是 push buffer 的现代版。你今天学完 Casey 的 push buffer,读 Bevy 的 `bevy_render` crate 就能看懂主线。

每种实现都解决同一个问题:**让游戏逻辑不直接碰 GPU 状态**。Casey 的极简版用 200 行 C 就讲清楚了核心,这是教学价值——商业引擎的几千行代码是同一个内核的扩展。

### 3.2 · 🎨 图形学视角

Renderer 抽象对应到 GPU 概念是什么?GPU 把 Renderer 这层叫做「**render pass**」——一个 render pass 描述「绑定哪些 framebuffer、用哪些 shader、画哪些 vertex buffer、按什么 blend 模式混合」。Vulkan 里这叫 `VkRenderPass`,D3D12 里叫 `PSO(Pipeline State Object)` + `CommandList`,OpenGL 里隐式在 `glDraw*` 调用前后隐含。

`submit()` 对应 GPU 的「**flush command buffer**」——把收集到的命令一次性丢给 GPU,GPU 异步执行。Casey 的 CPU 软渲染是同步的(`submit` 完像素已经在 framebuffer 里),但 push buffer 这个抽象天生适配 GPU 异步模型——这就是为什么 Day 235 切 OpenGL 时架构几乎不变。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上和「Renderer 抽象」最像的设施是 **Wayland 的 `wl_surface` + `wl_buffer` 协议**。客户端 app 把渲染好的像素封进 `wl_buffer`,commit 给 compositor。app 不需要知道 compositor 用什么后端(KMS / DRM / NVIDIA EGL)——这是 Wayland 设计的「**接口隔离**」,和 Renderer 同构。

另一个相关概念是 **`dma-buf`**:Linux 内核提供的「跨进程/跨设备的显存共享」机制。Renderer 的 framebuffer 在 Wayland 路径下会被包成 dma-buf,直接 zero-copy 传给 compositor。理解 Renderer 抽象后,你看 `weston-simple-dmabuf` 这种 demo 源码就不会被吓到。

### 3.4 · 🦀 Rust 生态视角

Rust 的所有权系统天然适配「**Renderer 持有所有资源**」的模式。重构前那种「全局 `static mut FRAMEBUFFER`」在 Rust 里是 `unsafe` 的——这正是 Rust 想要的:**强制你把可变状态封装到 struct 里,通过 `&mut` 显式传递**。

Rust 生态里和 Renderer 同构的几个 crate:

- **`wgpu`**:WebGPU 的 Rust 实现,核心抽象 `RenderPass` 就是我们今天写的 `Renderer::submit` 的 GPU 版。
- **`softbuffer`**:提供最简单的「一块 `&mut [u32]` 当 framebuffer」抽象,Casey HH 的 Linux 翻译版用这个。
- **`winit`**:窗口抽象,提供 `Window` 给 softbuffer 用。

Rust 现代特性里几个对 Renderer 重构很有用的点。`#[non_exhaustive]` attribute 让 `RenderCommand` enum 未来加变体不算 breaking change(对库作者友好)。`Box<dyn Trait>` 给 push buffer 做「**异质命令列表**」,但 Casey 的实现更高效——直接用字节流 + tag,没有虚函数开销。`core::arch::x86_64::__m128` 在 Renderer 内部做 SIMD 化的像素 blend,我们会在 Day 121 详细讲。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **抽象数据类型(ADT)** —— Renderer 是 ADT 的实战版:数据私有,操作公开。
- **接口隔离原则(ISP,Interface Segregation Principle)** —— SOLID 中的 I,「不要让调用者依赖它不需要的方法」。Renderer 的不同调用者(游戏层/平台层)看到不同子接口。
- **数据导向设计(DOD,Data-Oriented Design)** —— push buffer 是「数据流过代码」的范式,和 OOP「代码操作数据」相反。

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| **Push Buffer(Casey)** | 高层语义命令(Bitmap/Rect/Text),后端不透明 | 教学/软渲染/未来要换后端 | ✅ |
| **直接 framebuffer 写** | 游戏代码直接 `buf[i] = pixel` | 极简项目,像素量小 | Day 037 之前用 |
| **Immediate Mode(IM)** | 每帧调用 `draw_quad()` 立刻画 | Dear ImGui 这种 UI 库 | 不用(性能差) |
| **Retained Mode Scene Graph** | 维护一棵「场景树」,渲染遍历树 | Qt / 老式 Flash / DOM | 不用(状态难追踪) |
| **ECS 渲染(Bevy)** | 渲染是 ECS 的一个 schedule,数据是 component | 大型 3D 引擎 | Day 600+ 会涉及 |

这张表回答一个常见疑问:**「为什么不直接画」**。当你的渲染目标从「画一个绿色方块」变成「画一个带光照、带法线、带透明、带文字、支持多后端的场景」时,直接画会让游戏代码变成五千行的意大利面。Push buffer 把「**画什么**」和「**怎么画**」彻底分开,这是工业级渲染的最低门槛。

### 4.3 下级(内部零件)

- **PushBuffer** —— 字节流 + 命令 header,Day 088 引入。
- **Framebuffer** —— `Vec<u32>` 或 `&mut [u32]`,像素线性存储。
- **Camera** —— 位置 + 朝向 + zoom,Day 052 引入。
- **TextureArena** —— `HashMap<BitmapId, Bitmap>` 或 slot map。
- **SortKey** —— u64 排序键,Day 089 引入,在 `submit` 前排序命令。
- **sRGB↔Linear 查表** —— `gamma_table: [u8; 256]`,Day 094 引入。

## 5 · 对照与变奏

**2D vs 3D 的 Renderer**。Casey 现在写的是 2D(其实是 2.5D)Renderer,但接口形态和 3D Renderer 几乎一样:都收集高层命令、都按某种顺序提交、都最后写像素。差别在「命令的复杂度」——2D Renderer 的命令是 `Bitmap(dst, id, tint)`,3D Renderer 的命令是 `Mesh(vertex_buffer, index_buffer, material, transform)`。但抽象层一致。这就是为什么 Casey 能在 Day 235 几乎无痛切到 OpenGL。

**CPU vs GPU Renderer**。CPU 软渲染的 `submit` 同步写像素;GPU 渲染的 `submit` 把命令丢到 command queue 异步执行。push buffer 抽象对两者完全等价——这是 Day 088 设计的红利。Casey 在 Day 235 之后的 OpenGL Renderer 内部依然维护 push buffer,只是 `submit` 改成 `glBufferData + glDrawArrays`。

**同步 vs 异步**。Rust 生态里 `wgpu` 是异步的(`queue.submit()` 返回 `()`,但 GPU 还在画),Casey 是同步的。异步带来的好处是 CPU 和 GPU 并行,坏处是「帧延迟」——你看到的画面是 1-2 帧前的命令。Day 235 切 OpenGL 后会讨论这个问题。

**历史演化**。1990 年代游戏直接写 VGA 寄存器(`outpw(0x3C4, ...)`)——没有抽象层。1995 年 DirectX 出来,把「写像素」抽象成 `IDirect3DDevice::DrawPrimitive`。2000 年代 OpenGL VBO 把 vertex 数据从 CPU 搬到 GPU。2010 年代 Vulkan/D3D12 显式 command buffer——这就是 push buffer 在 GPU 时代的官方实现。Casey 的设计是「**用 GPU 时代的抽象跑 CPU 软渲染**」,这种「跨时代兼容」的视角是 HH 教学最有价值的部分之一。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:Casey 把全局的 `framebuffer` 搬进 `Renderer` struct 后,游戏代码调用 `renderer.push_bitmap(...)` 时,这个 `push_bitmap` 方法**不会**立刻写 framebuffer。为什么?如果立刻写会发生什么问题?

**参考解答**:push buffer 的核心是「**先收集命令,后统一执行**」。如果 `push_bitmap` 立刻写 framebuffer,会出现三个问题:(1) **顺序错乱**——游戏代码 push A 后 push B,如果 A 是半透明,B 是不透明,本应先画 B 再画 A 才正确;立刻写按调用顺序画,可能产生错误的透明叠加。(2) **无法排序优化**——Day 089 的 sort key 想把同纹理的命令排一起减少状态切换,立刻写就丧失这个优化。(3) **无法换后端**——立刻写假设只有 framebuffer 一种后端,Day 235 切 OpenGL 时全部要重写。`submit()` 这一步统一消费是 push buffer 模式的关键。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:在你的 Rust 项目里定义一个最小 `Renderer` struct,持有一个 `Vec<u32>` 假装是 framebuffer(256×256)。实现 `push_clear(color: u32)` 和 `push_rect(x, y, w, h, color: u32)` 和 `submit(&mut self)`。`push_*` 只往 push buffer 里 append 一条命令;`submit` 一次性把所有命令执行到 framebuffer。main 函数 push 两条命令然后 submit,用 `image` crate 存 PNG,运行后产物是「一个红色背景上画了一个绿色矩形」。

**参考解答**:

```rust
// Renderer 持有 framebuffer + 命令队列
pub struct Renderer {
    width: u32,                          // framebuffer 宽
    height: u32,                         // framebuffer 高
    framebuffer: Vec<u32>,               // 像素数组(每像素 ARGB)
    commands: Vec<Command>,              // push buffer 命令队列
}

// 高层渲染命令(下一步 submit 才执行)
enum Command {
    Clear { color: u32 },                // 全屏填色
    Rect { x: u32, y: u32, w: u32, h: u32, color: u32 },  // 实心矩形
}

impl Renderer {
    fn new(w: u32, h: u32) -> Self {
        Self {
            width: w, height: h,
            framebuffer: vec![0; (w * h) as usize],   // 初始全黑
            commands: Vec::new(),
        }
    }

    // push_* 方法只入队,不写像素
    fn push_clear(&mut self, color: u32) {
        self.commands.push(Command::Clear { color });
    }
    fn push_rect(&mut self, x: u32, y: u32, w: u32, h: u32, color: u32) {
        self.commands.push(Command::Rect { x, y, w, h, color });
    }

    // submit 一次性消费所有命令,按 push 顺序写入 framebuffer
    fn submit(&mut self) {
        // take 出命令队列,腾空供下一帧用
        let cmds: Vec<_> = std::mem::take(&mut self.commands);
        for cmd in cmds {
            match cmd {
                Command::Clear { color } => {
                    for px in &mut self.framebuffer { *px = color; }
                }
                Command::Rect { x, y, w, h, color } => {
                    for ry in y..(y + h).min(self.height) {
                        for rx in x..(x + w).min(self.width) {
                            let i = (ry * self.width + rx) as usize;
                            self.framebuffer[i] = color;
                        }
                    }
                }
            }
        }
    }
}

fn main() {
    let mut r = Renderer::new(256, 256);
    r.push_clear(0xFFFF0000);                 // 红
    r.push_rect(64, 64, 128, 128, 0xFF00FF00); // 中央绿矩形
    r.submit();                                // 真正写像素

    // 用 image crate 存成 PNG 验证
    let img: image::ImageBuffer<image::Rgba<u8>, _> =
        image::ImageBuffer::from_raw(r.width, r.height, bytemuck::cast_vec(r.framebuffer)).unwrap();
    img.save("day105.png").unwrap();
}
```

把 push 和 submit 分开的好处:你可以 push 一堆命令、做别的、再 submit——这种「**延迟执行**」让排序、批处理、并行渲染成为可能。

### Lv3 · 迁移设计(换场景用同一原理)

**题**:你的公司有「日志系统」——多个模块(`auth`, `db`, `cache`)各自调用 `log::info(...)`,目前是同步立刻写文件。问题是:某天日志文件被锁,所有模块卡住。请用 push buffer 模式重构:**每个模块调用 `logger.push(level, msg)`,后台线程 `logger.submit()` 把队列批量写到文件**。给出 `Logger` struct 定义、`push` / `submit` 方法签名、跨线程通信方式(`std::sync::mpsc` vs `crossbeam::channel` vs `Mutex<Vec>`),并说明每种选择的开销。

**提示**:考虑「多生产者单消费者(MPSC)」模式。`push` 端高频、`submit` 端低频但批量。`mpsc::channel` 天然适合但每次 `send` 有 syscall 开销;`Arc<Mutex<VecDeque>>` 自旋锁适合小负载但 contention 大;`crossbeam::deque` 是工作窃取队列,适合 worker pool。

## 8 · Rust / Arch 落地代码

完整可跑的最小 Renderer 项目,带 cargo 命令和调试命令。

```rust
// Cargo.toml 至少要有:
// [dependencies]
// image = "0.25"
// bytemuck = { version = "1", features = ["extern_crate_alloc"] }

use std::num::NonZeroU32;

// === BitmapId:用 NonZeroU32 当 ID,0 留给「无效」 ===
#[derive(Copy, Clone, Debug, PartialEq, Eq)]
pub struct BitmapId(NonZeroU32);

// === 高层渲染命令 ===
pub enum Command {
    Clear { color: [f32; 4] },               // linear RGBA, 0..1
    Rect { x: f32, y: f32, w: f32, h: f32, color: [f32; 4] },
    Bitmap { x: f32, y: f32, id: BitmapId, tint: [f32; 4] },
    Text { x: f32, y: f32, text: String, color: [f32; 4] },
}

// === Renderer struct,持所有渲染状态 ===
pub struct Renderer {
    pub width: u32,
    pub height: u32,
    pub framebuffer: Vec<u32>,            // ARGB8888
    pub commands: Vec<Command>,           // push buffer
    pub world_scale: f32,                 // Day 106 会用
    pub camera_x: f32,                    // 简化:只有平移
    pub camera_y: f32,
}

impl Renderer {
    pub fn new(w: u32, h: u32) -> Self {
        Self {
            width: w, height: h,
            framebuffer: vec![0xFF000000; (w * h) as usize],  // 默认黑
            commands: Vec::with_capacity(1024),                // 预分配
            world_scale: 1.0,
            camera_x: 0.0,
            camera_y: 0.0,
        }
    }

    // linear→sRGB 转换,Day 094 已实现过
    fn linear_to_srgb_u8(c: f32) -> u8 {
        let s = c.max(0.0).min(1.0);
        let s = if s <= 0.0031308 { s * 12.92 } else { 1.055 * s.powf(1.0 / 2.4) - 0.055 };
        (s * 255.0) as u8
    }

    pub fn push_clear(&mut self, color: [f32; 4]) {
        self.commands.push(Command::Clear { color });
    }
    pub fn push_rect(&mut self, x: f32, y: f32, w: f32, h: f32, color: [f32; 4]) {
        self.commands.push(Command::Rect { x, y, w, h, color });
    }

    pub fn submit(&mut self) {
        // 把所有权移到局部变量,腾空 self.commands 给下一帧
        let cmds: Vec<_> = std::mem::take(&mut self.commands);
        for cmd in cmds {
            match cmd {
                Command::Clear { color } => {
                    let argb = pack_argb(color);
                    for px in &mut self.framebuffer { *px = argb; }
                }
                Command::Rect { x, y, w, h, color } => {
                    let argb = pack_argb(color);
                    // 应用 camera + world_scale
                    let sx = ((x - self.camera_x) * self.world_scale) as i32;
                    let sy = ((y - self.camera_y) * self.world_scale) as i32;
                    let sw = (w * self.world_scale) as i32;
                    let sh = (h * self.world_scale) as i32;
                    for ry in sy..(sy + sh).max(0) {
                        if ry < 0 || ry as u32 >= self.height { continue; }
                        for rx in sx..(sx + sw).max(0) {
                            if rx < 0 || rx as u32 >= self.width { continue; }
                            self.framebuffer[(ry as u32 * self.width + rx as u32) as usize] = argb;
                        }
                    }
                }
                _ => {} // 其他变体留给后续 Day 实现
            }
        }
    }
}

fn pack_argb(c: [f32; 4]) -> u32 {
    let r = Renderer::linear_to_srgb_u8(c[0]) as u32;
    let g = Renderer::linear_to_srgb_u8(c[1]) as u32;
    let b = Renderer::linear_to_srgb_u8(c[2]) as u32;
    let a = Renderer::linear_to_srgb_u8(c[3]) as u32;
    (a << 24) | (r << 16) | (g << 8) | b
}

fn main() {
    let mut r = Renderer::new(256, 256);
    r.push_clear([0.6, 0.1, 0.1, 1.0]);            // 暗红背景(linear)
    r.push_rect(64.0, 64.0, 128.0, 128.0, [0.1, 0.6, 0.1, 1.0]); // 绿矩形
    r.submit();

    let bytes: Vec<u8> = r.framebuffer.iter()
        .flat_map(|p| p.to_le_bytes())            // ARGB → bytes
        .collect();
    let img: image::ImageBuffer<image::Rgba<u8>, _> =
        image::ImageBuffer::from_raw(r.width, r.height, bytes).unwrap();
    img.save("day105.png").expect("save png");
    println!("saved day105.png, framebuffer size = {} bytes", r.framebuffer.len() * 4);
}
```

**出错怎么办(troubleshooting)**:

- **`bytemuck::cast_vec` 找不到** —— 确认 `Cargo.toml` 里 `bytemuck` 加了 `features = ["extern_crate_alloc"]`。
- **`image::ImageBuffer::from_raw` 返回 `None`** —— 字节数不够。`Vec<u32>` 转 `Vec<u8>` 要 `flat_map(|p| p.to_le_bytes())` 而不是 `as_bytes()`(对齐可能不对)。
- **PNG 看起来全黑** —— ARGB 顺序错。试试 `(r << 16) | (g << 8) | b | (a << 24)` 和 `(a << 24) | (r << 16) | (g << 8) | b` 两种,看你目标库的预期。`image` crate 的 Rgba 是 R,G,B,A 顺序,所以应该 `bytemuck` 直接 cast `Vec<u32>` 时要小心字节序。
