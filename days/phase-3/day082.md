
# Day 082 · 缓存合成位图

> 你昨天写的程序化合成很美——每块 tile 独一无二。但每帧 2 亿次像素运算,CPU 在哀嚎。Casey 今天给合成的结果加缓存:**第一次算,后续帧直接用**。这是 game dev 经典优化——「cache the rendered result」,缓存一切可以缓存的。掌握缓存思想,你就能把任何「热路径」从瓶颈变成快进。

## 0 · 为什么要有这一天

让我们从一个真实的性能瓶颈说起。

你昨天写了程序化合成——每块 tile 根据位置、噪声、装饰参数,动态合成出独一无二的纹理。看起来很美,草地、岩石、土壤无缝过渡,每块 tile 都不同。

但 F5 跑游戏,FPS 只有 1。你 `perf record` 看热点,发现 80% 时间在 `composite_tile` 函数。具体:每帧调用 1000 次,每次几毫秒(64x64 tile、5 层装饰、alpha blend),合计 1-3 秒/帧——**完全跑不动**。

你困惑——"我没做错什么啊?合成函数已经优化了"。**根因不是合成函数慢,而是重复劳动**。

仔细想想:tile (3, 5) 的合成结果,在玩家没修改这个 tile 时,**永远是同一张图**。为什么要每帧重新算?玩家的视野每帧可能不变,tile 内容也没变,但你的代码每帧都重新合成——99% 的计算是浪费。

**Casey 的解法**:**第一次算,存起来**。后续帧查缓存。这叫 **memoization**(记忆化),是计算机科学里最古老也最有效的优化。原理:**纯函数(给定输入永远产生同一输出)的结果可以无限期缓存**。tile 合成是纯函数(给定 (x, y) 永远同一图),所以可以缓存。

游戏开发里到处是缓存:

- **贴图缓存**:加载一次,反复使用。Unreal / Unity 都有 TextureCache。
- **离屏渲染**:复杂 UI 先渲染到 offscreen texture,需要时贴出来。egui / Dear ImGui 的内部缓存。
- **光照贴图**(lightmap):静态光照预计算,运行时只采样。Quake 1 发明,所有 3D 游戏至今在用。
- **路径缓存**:AI 寻路结果缓存,下次直接用。StarCraft 的 A* 寻路缓存。
- **字体缓存**:glyph 第一次光栅化,缓存,后续直接 blit。FreeType + HarfBuzz 的标准模式。

这是 industrial game dev 的"**缓存一切**"哲学——只要数据不变,就缓存。Casey 这天把这套哲学应用到 tile 合成。

完成这一天之后,你应该能:

- **解释 memoization 的本质**——纯函数 + 哈希表,把 O(N) 重复计算变成 O(1) 查询
- **写 LRU 缓存**——限制大小,淘汰最久未用的
- **理解 cache invalidation 的难点**——为什么是"计算机科学两大难题之一"
- **设计 cache-friendly 数据结构**——HashMap vs Array 的 trade-off
- **看懂 Linux kernel 的 page cache / dentry cache**——OS 层的缓存思想

## 1 · Casey 今天做了什么

Casey 这天是优化工作,不是新功能。让我把步骤拆开。

**第一步,加 tile_cache 字段**:`HashMap<(i32, i32), Bitmap>`。key 是 tile 坐标,value 是合成好的位图。空 HashMap 占用极小内存,所以可以一开始就分配。

**第二步,合成函数升级**:**先查缓存,没找到才真合成**。用 Rust HashMap 的 `entry().or_insert_with()` API——原子性地"检查 + 计算 + 插入",避免 race condition。

**第三步,缓存失效**:tile 变化(挖洞、放建筑)时,删除对应 entry。Casey 用"显式失效"——任何修改 tile 的地方手动调 invalidate。这要求程序员纪律好(忘了就 bug)。

**第四步,测试**:跑 1000 tile × 60 帧,看缓存后的性能。性能提升巨大——第一次合成 1 秒,后续帧 < 1 毫秒。60 FPS 稳定。

视频里 Casey 强调一个**反直觉的事实**:**优化不是让合成更快,而是让合成不发生**。原合成 0.5ms × 1000 tile = 500ms,优化后 0.0001ms × 1000 tile = 0.1ms——5000 倍加速。但合成函数本身没变,只是大部分时间没调它。

**缓存大小的取舍**:无限制缓存内存爆炸(大世界有几十万 tile),LRU 限制大小但可能 miss。Casey HH 中等世界,无限制够用。Day 86+ 大世界用 chunked 缓存。

## 2 · 心智模型

### 2.1 费曼类比:厨师备菜

我打个比方。厨师做菜,有些菜要现做(炒菜、烤肉),有些可以提前备(切菜、调料、汤底)。「**备菜**」就是缓存——一次准备,反复使用。

专业厨房的"备菜"叫 **mise en place**(法语"各就各位")——开始营业前把所有食材切好、量好、摆好。营业时直接用,不必每单重新切。这是专业厨房能 5 分钟出 20 道菜的秘密。

游戏里:
- **每帧变的(动态)**:玩家、怪、特效、粒子——必须每帧重画。
- **不变的(静态)**:tile、墙、地面、静态光照——一次算好,反复用。

Casey 的 tile 缓存就是「备菜」——第一次合成就好,后续直接端出去。

类比的关键洞察:**缓存的价值来自"重复访问"**。如果某 tile 只访问一次,缓存无意义(还多一次插入开销)。如果访问 1000 次,缓存省 999 次计算。游戏世界里的 tile 被玩家反复看到(视野内每帧都看),所以缓存价值巨大。

更深一层:**缓存的代价是内存**。每个缓存 entry 占用内存(Bitmap 64×64×4 = 16KB)。1000 tile 缓存 = 16MB,100000 tile = 1.6GB。大世界要 LRU 限制——只缓存"热"的 tile。

### 2.2 Memoization:计算机科学的基础优化

Memoization 是 Donald Michie 1968 年提出的概念——**把纯函数的调用结果存起来,下次同输入直接返回**。

```rust
struct TileCache {
    cache: std::collections::HashMap<(i32, i32), Bitmap>,
}

impl TileCache {
    fn get_or_compose(&mut self, x: i32, y: i32) -> &Bitmap {
        self.cache.entry((x, y))
            .or_insert_with(|| composite_tile(x, y))
    }
}
```

`entry().or_insert_with()` 是 Rust HashMap 的惯用法:
- 如果 key 已存在,返回值的引用。
- 如果 key 不存在,调用闭包计算 value,插入,返回引用。

这就是 memoization——**第一次算,后续查**。

**纯函数的要求**:memoization 要求函数对同一输入永远返回同一输出(无副作用)。`composite_tile(x, y)` 是纯函数——给定 (x, y) 永远同一图。但如果函数依赖全局变量(如时间),memoization 失效。

**Memoization 的工业应用**:
- **React 的 useMemo**——React 组件的纯函数计算缓存
- **Python 的 functools.lru_cache**——任意函数的自动 memoization
- **C++ 的 constexpr**——编译时 memoization
- **Excel 的公式缓存**——cell value 缓存,依赖未变时不重算

### 2.3 缓存失效:计算机科学两大难题之一

> There are only two hard things in Computer Science: cache invalidation and naming things.
> —— Phil Karlton(Netscape 首席架构师)

为什么 cache invalidation 难?因为缓存数据和源数据可能**不同步**:

- 文件被外部进程改了,page cache 还是旧数据。
- 玩家挖地,但缓存没失效,显示旧图。
- 数据库更新了,应用缓存还是旧值。

```rust
impl TileCache {
    fn invalidate(&mut self, x: i32, y: i32) {
        self.cache.remove(&(x, y));
    }

    fn clear(&mut self) {
        self.cache.clear();
    }
}

// 当玩家挖地(修改 tile):
fn dig_tile(cache: &mut TileCache, world: &mut World, x: i32, y: i32) {
    world.set_tile(x, y, Tile::Hole);
    cache.invalidate(x, y);  // 下次访问时重新合成
}
```

Casey HH 用「**显式失效**」——程序员手动调 invalidate。这要求纪律:任何修改 tile 的代码都要记得调 invalidate。如果忘了,玩家挖地后看到的还是旧 tile——**bug**。

更高级方案:**dirty flag**——tile 加 `dirty: bool` 字段,修改时设 true,缓存检查 dirty 决定是否重算。这是 React 的 reconciliation 思想。

```rust
struct Tile {
    kind: TileKind,
    dirty: bool,  // 是否需要重新合成
}

impl TileCache {
    fn get_or_compose(&mut self, world: &World, x: i32, y: i32) -> &Bitmap {
        let tile = world.get_tile(x, y);
        if tile.dirty || !self.cache.contains_key(&(x, y)) {
            let bmp = composite_tile(x, y);
            self.cache.insert((x, y), bmp);
            tile.dirty = false;
        }
        &self.cache[&(x, y)]
    }
}
```

dirty flag 自动失效——任何修改 tile 的地方设 dirty,缓存检查 dirty 自动重算。更安全,但代码稍复杂。

工业级方案:
- **TTL**(Time To Live):缓存有寿命,过期自动失效。Web cache 常用。
- **Versioning**:每个数据有版本号,缓存存版本号,源数据版本号变了就失效。Git / 数据库 MVCC。
- **Write-through**:写时同时更新缓存和源,保持一致。CPU cache 用。
- **Write-back**:写时只更新缓存,异步刷到源。性能高但一致性弱。

### 2.4 LRU 缓存:限制大小的核心算法

无限制缓存内存爆炸——大世界 100000 tile × 16KB = 1.6GB。需要限制大小。最常用算法是 LRU(Least Recently Used,最久未用淘汰)。

```rust
struct LRUTileCache {
    cache: HashMap<(i32, i32), (Bitmap, u64)>,  // (bitmap, last_access_time)
    time: u64,
    max_size: usize,
}

impl LRUTileCache {
    fn get(&mut self, x: i32, y: i32) -> &Bitmap {
        self.time += 1;
        let entry = self.cache.entry((x, y))
            .or_insert_with(|| (composite_tile(x, y), 0));
        entry.1 = self.time;  // 更新访问时间

        // 如果太大,删最久没用的
        if self.cache.len() > self.max_size {
            let oldest = self.cache.iter()
                .min_by_key(|(_, v)| v.1)
                .map(|(k, _)| *k);
            if let Some(k) = oldest {
                self.cache.remove(&k);
            }
        }

        &self.cache.get(&(x, y)).unwrap().0
    }
}
```

LRU 的核心:**每次访问更新 last_access_time,容量超限时删 time 最小的**。这利用"时间局部性"——刚访问的更可能再用。LRU 假设玩家附近的 tile 会被反复访问(玩家停留在某区域),远的 tile 不会(玩家走开后不再回来)。

**LRU 的实现优化**:上述实现用 `min_by_key` 找最旧,O(N)。工业级实现用 `LinkedHashMap`(Java)或 `LinkedList + HashMap`(Rust lru crate)——O(1) 查找最旧。

**其他淘汰策略**:
- **LFU**(Least Frequently Used):淘汰访问次数最少的。比 LRU 稳定,但容易"老 entry 永远占着"(高频率历史 entry 不被淘汰)。
- **FIFO**(First In First Out):按插入顺序淘汰。简单但不利用局部性。
- **ARC**(Adaptive Replacement Cache):IBM 发明,自适应 LRU + LFU。Linux ZFS 用。
- **W-TinyLFU**:Caffeine(Java)和 moka(Rust)用,工业级 SOTA。

### 2.5 缓存友好性:数据局部性

CPU 缓存(L1/L2/L3)按 cache line(64 字节)预取。如果访问模式局部性好(相邻内存连续访问),CPU 缓存命中率高。HashMap 是 cache-unfriendly——key 散布在堆上,跳跃访问。

**HashMap vs Array 的 cache 性能**:
- HashMap:每次访问 hash → bucket → key compare → value,O(1) 但常数大,cache miss 频繁。
- 2D Array:`tiles[y * W + x]` 直接 index,O(1) 且 cache 友好(连续内存)。

```rust
struct GridCache {
    tiles: Vec<Bitmap>,         // 二维数组,大小 W * H
    width: usize,
    height: usize,
}

impl GridCache {
    fn get(&self, x: i32, y: i32) -> &Bitmap {
        &self.tiles[(y as usize) * self.width + (x as usize)]
    }
}
```

但 2D 数组**大小固定**,不能动态扩展。Casey HH 用 HashMap(灵活但慢),Day 86+ 的 chunk 系统用 chunked 2D 数组(平衡)——大世界切成 chunk,每个 chunk 是固定大小 2D 数组,chunk 之间用 HashMap 索引。

**Morton code 优化**:把 2D 坐标编码到 1D(Z-order curve),邻近 2D 在 1D 也邻近。chunk 按 Morton 排序,cache 命中率高。Day 86+ 用。

### 2.6 性能基准:缓存的实际收益

合成一个 64×64 tile:

| 操作 | 时间(60 FPS 帧的预算是 16.67ms)|
|---|---|
| 完整合成(5 装饰)| 0.5-1ms |
| 缓存命中(HashMap 查)| 0.001ms |
| 缓存命中(数组查)| 0.0001ms |

1000 tile 全合成 = 500-1000ms(慢 30-60 倍)。
1000 tile 缓存命中 = 1ms(快 500-1000 倍)。

缓存的价值就在这——**1 次算 vs N 次算**。

实际游戏场景:玩家停留某区域 60 秒(3600 帧)。第一帧 cache miss(合成),后续 3599 帧 cache hit。**总开销 = 1 × 500ms + 3599 × 1ms = 4 秒**。无缓存 = 3600 × 500ms = 30 分钟。**450 倍加速**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏里到处是缓存:

#### 贴图缓存(Texture Cache)

```rust
struct TextureCache {
    cache: HashMap<String, Texture>,
}

impl TextureCache {
    fn load(&mut self, path: &str) -> &Texture {
        self.cache.entry(path.to_string())
            .or_insert_with(|| load_texture_from_disk(path))
    }
}
```

第一次从磁盘加载(慢),后续命中缓存(快)。**所有游戏引擎都有这个**。

#### 字体缓存(Font Cache / Glyph Cache)

字体渲染:第一次渲染字符 'A',光栅化 + 缓存。后续直接 blit。

```rust
struct GlyphCache {
    cache: HashMap<(char, u32), Bitmap>,  // (char, font_size) -> bitmap
}
```

如果不缓存,每帧重新光栅化文字,CPU 烧。

#### 路径缓存(Path Cache)

AI 寻路:A* 算法慢(可能 ms 级)。如果场景静态,寻路结果缓存。

```rust
struct PathCache {
    cache: HashMap<(Vec2i, Vec2i), Vec<Vec2i>>,  // (from, to) -> path
}
```

玩家走出某区域,缓存失效。

#### 光照贴图(Lightmap)

静态场景的光照预计算,烘焙到 lightmap texture。运行时采样 lightmap 而不是实时算光照。这是 Quake 1 的发明,所有 3D 游戏至今在用。

### 3.2 · 🎨 图形学视角

GPU 也有缓存:

- **贴图缓存**:GPU 显存(VRAM),采样时 O(1)。
- **顶点缓存**(Vertex Buffer / VBO):静态 mesh 上传到 GPU 一次,反复绘制。
- **Shader 缓存**:编译后的 shader 二进制缓存,避免每次启动重编译。

GPU 缓存和 CPU 缓存原理一样,但硬件不同。

#### Mipmap

为远处的小物体准备多个分辨率版本(64×64、32×32、16×16),采样时选合适的——避免 aliasing 也加速。这是一种「**预计算 + 缓存**」。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里到处是缓存:

- **page cache**:文件 IO 自动缓存,read() 第二次快。
- **dentry cache**:目录项缓存,加速路径查找。
- **inode cache**:inode 缓存。
- **buffer cache**:块设备 IO 缓存。

这些缓存让 Linux 文件 IO 飞快。`free -h` 看的「cached」就是 page cache。

工业级方案:

### 3.4 · 🦀 Rust 生态视角

#### Rust 的 HashMap

```rust
use std::collections::HashMap;

let mut map: HashMap<(i32, i32), Bitmap> = HashMap::new();
map.insert((3, 5), tile);

// 查
if let Some(bmp) = map.get(&(3, 5)) { /* ... */ }

map.entry((3, 5)).or_insert_with(|| expensive_compute());
```

Rust 的 HashMap 用 SipHash(防 hash flooding 攻击),但慢。游戏开发用 `fnv::FnvHashMap` 或 `ahash::AHashMap` 更快。

#### Rust 的 LRU crate

```toml
[dependencies]
lru = "0.12"
```

```rust
use lru::LruCache;

let mut cache: LruCache<(i32, i32), Bitmap> = LruCache::new(1000);
cache.put((3, 5), tile);  // 插入

```

`lru` crate 提供工业级 LRU 实现。

#### Rust 的缓存生命周期

```rust
struct Game {
    tile_cache: HashMap<(i32, i32), Bitmap>,
}

impl Game {
    fn render_tile(&mut self, x: i32, y: i32) {
        let bmp = self.tile_cache.entry((x, y))
            .or_insert_with(|| composite_tile(x, y));
        render_bitmap(bmp);
    }
}
```

缓存的生命周期跟 `Game` 一样长。退出游戏时自动释放。

#### Rust 的 lazy / once_cell

```rust
use once_cell::sync::Lazy;

static GLOBAL_TILE_CACHE: Lazy<RwLock<HashMap<(i32, i32), Bitmap>>> = Lazy::new(|| {
    RwLock::new(HashMap::new())

```

全局缓存,首次访问时初始化。

## 5 · 对照与变奏

### 不同游戏的缓存策略

| 游戏 | 缓存什么 |
|---|---|

### 缓存层次

| 层级 | 大小 | 速度 |
|---|---|---|
| CPU register | 几十字节 | 0 cycle |
| L1 cache | 32KB | 4 cycle |
| L2 cache | 256KB | 10 cycle |
| L3 cache | 8MB | 40 cycle |
| RAM | GB | 100 cycle |
| SSD | 100s GB | 1000 cycle |
| HDD | TB | 100000 cycle |
| Network | PB | 1000000 cycle |

游戏开发要意识到这些层级——把热数据放在 L1/L2(紧凑、连续),冷数据放 RAM(大但不连续)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:什么情况下 tile cache 应该失效?

**参考解答**:**tile 的内容变化时**。具体:

1. **玩家修改**:挖地、放建筑、烧草地。任何改变 tile 视觉的操作。
2. **游戏事件**:季节变化(草地变黄)、爆炸(地面变焦)。
3. **关卡切换**:玩家进入新关卡,所有 tile 失效。

不应该失效的情况:玩家只是走过 tile(tile 内容没变)。

失效的两种策略:
- **显式失效**:程序员在修改 tile 处手动调 invalidate。
- **自动失效**:tile 加 version 字段,缓存存 version,版本不一致就失效。

### Lv2 · 动手实践

**题**:实现 TileCache,合成 100 次 tile (3, 5),验证第二次开始命中缓存(瞬时返回)。

完成标准:第一次合成 X 毫秒,第二次开始 < 1 微秒。

**参考解答**:

```rust
use std::collections::HashMap;
use std::time::Instant;

#[derive(Clone)]
struct Bitmap { width: usize, height: usize, pixels: Vec<[u8; 4]> }

fn composite_tile(x: i32, y: i32) -> Bitmap {
    // 模拟慢合成
    std::thread::sleep(std::time::Duration::from_millis(10));
    Bitmap {
        width: 64, height: 64,
        pixels: vec![[50, 120, 40, 255]; 64 * 64],
    }
}

struct TileCache {
    cache: HashMap<(i32, i32), Bitmap>,
    hits: u32,
    misses: u32,
}

impl TileCache {
    fn new() -> Self { Self { cache: HashMap::new(), hits: 0, misses: 0 } }

    fn get_or_composite(&mut self, x: i32, y: i32) -> &Bitmap {
        if self.cache.contains_key(&(x, y)) {
            self.hits += 1;
        } else {
            self.misses += 1;
        }
        self.cache.entry((x, y))
            .or_insert_with(|| composite_tile(x, y))
    }
}

fn main() {
    let mut cache = TileCache::new();
    for i in 0..5 {
        let start = Instant::now();
        let _bmp = cache.get_or_composite(3, 5);
        println!("调用 {}: {:?} (hits={}, misses={})",
            i, start.elapsed(), cache.hits, cache.misses);
    }
}
```

**预期输出**:
```
调用 0: 10.1ms (hits=0, misses=1)   ← 真合成
调用 1: 1.2µs  (hits=1, misses=1)   ← 缓存命中
调用 2: 1.1µs  (hits=2, misses=1)
调用 3: 1.0µs  (hits=3, misses=1)
调用 4: 1.1µs  (hits=4, misses=1)
```

### Lv3 · 迁移设计

**题**:实现「**LFU**」(Least Frequently Used)缓存——淘汰访问**次数最少**的 entry,而不是最久没访问的。算法是什么?

**提示**:
- 每个 entry 加 `access_count: u32`
- 容量超限时,删 access_count 最小的
- 跟 LRU 比,LFU 更稳定(不会因偶尔访问被淘汰),但容易「老 entry 永远占着」

## 8 · Rust / Arch 落地代码

```rust
use std::collections::HashMap;

#[derive(Clone, Debug)]
struct Bitmap {
    width: usize,
    height: usize,
    pixels: Vec<[u8; 4]>,
}

fn composite_tile(x: i32, y: i32) -> Bitmap {
    // 模拟合成(实际项目里是真 alpha blend)
    let mut pixels = vec![[50, 120, 40, 255]; 64 * 64];  // 草地底色
    // 简单"装饰":在 (x%32, y%32) 加个红点
    let px = ((x.rem_euclid(64)) as usize) % 64;
    let py = ((y.rem_euclid(64)) as usize) % 64;
    pixels[py * 64 + px] = [200, 50, 50, 255];
    Bitmap { width: 64, height: 64, pixels }
}

struct TileCache {
    cache: HashMap<(i32, i32), Bitmap>,
    hits: u64,
    misses: u64,
}

impl TileCache {
    fn new() -> Self {
        Self { cache: HashMap::new(), hits: 0, misses: 0 }
    }

    fn get_or_composite(&mut self, x: i32, y: i32) -> &Bitmap {
        let exists = self.cache.contains_key(&(x, y));
        if exists { self.hits += 1; } else { self.misses += 1; }
        self.cache.entry((x, y))
            .or_insert_with(|| composite_tile(x, y))
    }

    fn invalidate(&mut self, x: i32, y: i32) {
        self.cache.remove(&(x, y));
    }

    fn stats(&self) -> (u64, u64, f32) {
        let total = self.hits + self.misses;
        let rate = if total > 0 { self.hits as f32 / total as f32 } else { 0.0 };
        (self.hits, self.misses, rate)
    }
}

fn main() {
    let mut cache = TileCache::new();

    println!("=== 模拟渲染 10 帧,每帧渲染 (3,5) 和 (4,5) 两个 tile ===\n");

    for frame in 0..10 {
        for &(x, y) in &[(3, 5), (4, 5)] {
            let _ = cache.get_or_composite(x, y);
        }
        let (h, m, r) = cache.stats();
        println!("帧 {:2}: hits={}, misses={}, 命中率={:.1}%",
            frame, h, m, r * 100.0);
    }

    println!("\n=== 模拟 tile (3,5) 被修改(挖地) ===\n");
    cache.invalidate(3, 5);

    for &(x, y) in &[(3, 5), (4, 5)] {
        let _ = cache.get_or_composite(x, y);
    }
    let (h, m, r) = cache.stats();
    println!("修改后:hits={}, misses={}, 命中率={:.1}%", h, m, r * 100.0);
}
```

**预期输出**:
```
=== 模拟渲染 10 帧,每帧渲染 (3,5) 和 (4,5) 两个 tile ===

帧  0: hits=0, misses=2, 命中率=0.0%
帧  1: hits=2, misses=2, 命中率=50.0%
帧  2: hits=4, misses=2, 命中率=66.7%
...
帧  9: hits=18, misses=2, 命中率=90.0%

=== 模拟 tile (3,5) 被修改(挖地) ===

修改后:hits=19, misses=3, 命中率=86.4%
```

命中率随时间上升——缓存效果显著。

**Troubleshooting**:
- 内存爆炸 — 加 LRU,限制缓存大小
- 缓存失效后没重算 — invalidate 后下次访问会重算,正常
- 缓存命中率低 — 检查 key 一致性(同样 tile 应该同 key)
