# Day 095 · Gamma 校正的预乘 alpha

> 昨天(Day 094)讲了 sRGB ↔ linear——你必须在做光照/混合前转 linear。今天 Casey 用这个理论修一个 Day 093 留下的坑:alpha 透明混合。具体来说,他引入**预乘 alpha**(premultiplied alpha)——一种存储纹理的方式,让 alpha 混合既**正确**(linear 空间)又**高效**(混合公式更简单)。预乘 alpha 是工业标准——PNG 不用,但 Photoshop、渲染管线、所有 GPU API 都默认它。理解它,你的渲染器就上一个台阶。

## 0 · 为什么要有这一天

回到 Day 093。我们的 sprite 渲染器有个简化处理:

```rust
if texel[3] > 0 {  // alpha > 0
    fb[px, py] = texel.rgb;  // 直接覆盖
}
```

这个 `if` 只做了「全画 or 全不画」。但很多 sprite 有**半透明像素**——比如玻璃、烟雾、毛发边缘的羽化。直接覆盖会让边缘锯齿严重(因为没考虑 alpha 的中间值)。

**朴素的修复** —— **alpha 混合**(alpha blending):

```
final = tex.rgb * tex.a + bg.rgb * (1 - tex.a)
```

读作:「按 alpha 比例混合前景和背景」。alpha=1 时全用前景,alpha=0 时全用背景,alpha=0.5 时各半。

这看起来对。但放在昨天(Day 094)学过的 sRGB 理论下,**完全错**:

1. `tex.rgb` 是 sRGB 编码,在 sRGB 空间做线性混合——错的,得到比预期暗的暗部
2. `bg.rgb` 也是 sRGB 编码——同样错

正确做法:**先把前景和背景都转 linear,然后在 linear 空间按 alpha 混合,最后转回 sRGB**。但每像素 2 次 sRGB→linear + 1 次 linear→sRGB 的开销,加上 alpha 混合本身,慢得吓人。

**预乘 alpha 的妙处**:它在**纹理加载时**就把 RGB 乘上 alpha(`rgb_premul = rgb * alpha`),并且**直接用 linear 空间存储**。这样渲染时:

```
final = tex.rgb_premul + bg.rgb * (1 - tex.a)
```

注意——前景不再乘 alpha(已经在加载时乘过了),只算 `+ bg * (1-a)`。这个简化的好处是:
- 公式更短,渲染快
- 多次叠加正确(像素 P1 上画 P2 上画 P3,结果与顺序无关的某些情况下更稳定)
- 抗锯齿边缘自然正确

预乘 alpha 的代价:RGB 通道不能超过 alpha(否则信息丢失)。但这是合理的——一个透明像素本来就不应该有「亮 RGB」。

心理锚点:看完今天,你的渲染器能正确处理半透明 sprite。你能向队友解释「为什么预乘 alpha 比 straight alpha 好」。你能用 Rust 实现完整的 linear 空间预乘 alpha 混合。

## 2 · 心智模型

### 费曼类比:半透明彩色玻璃

想象一块半透明红色玻璃,alpha=0.7。它能让 70% 的红光透过,30% 的背景光透过。

**朴素 alpha 混合**(straight alpha):
- 玻璃本身发 0.7 红光(`rgb * alpha`)
- 背景光透过 30%(1-0.7)
- 最终:`glass_red * 0.7 + bg * 0.3`

**预乘 alpha**:玻璃的「红光强度」已经被乘过 alpha——你只需要「玻璃的红光」+「背景的 30%」。
- 玻璃本身发 0.7 红光(已经预算)
- 背景光透过 30%
- 最终:`glass_red_premul + bg * 0.3`

结果数学上等价,但**玻璃的红光已经预算**,渲染时只算 `+ bg * 0.3`,少一次乘法。

**linear 空间的必要性**:
- 红光强度 0.7 是物理光强(0.7 = 70% 物理光强)
- sRGB 0.7 的物理光强是 0.7^2.2 ≈ 0.46(只有 46%!)
- 如果在 sRGB 空间做混合,你用的是 0.46 的光强,不是 0.7——物理上错

### 严谨原理

#### 2.1 Straight alpha vs Premultiplied alpha

**Straight alpha**(也叫 unassociated / non-premultiplied):
- 存储:`(r, g, b, a)`,RGB 是「不透明时应有的颜色」
- PNG 默认是 straight alpha

**Premultiplied alpha**(也叫 associated):
- 存储:`(r*a, g*a, b*a, a)`,RGB 已经被 alpha 乘过
- PSD/TIFF/DirectX 默认 premultiplied

**举例**:
- Straight:`(255, 0, 0, 128)` = 「完全不透明的红色,但只有 50% 可见」
- Premultiplied:`(128, 0, 0, 128)` = 「红色已经被半透明了,直接叠加」

注意 premultiplied 后 RGB ≤ alpha(因为 a ≤ 1,所以 r*a ≤ r)。这给出一个优化:如果 a=0,RGB 一定是 0,无需存——可以用 RGB 通道存别的信息(比如法线贴图里常见的「法线 z 分量」,因为 z=1 时其他分量必为 0)。

#### 2.2 混合公式对比

**Straight alpha 混合**(每帧):
```
final.rgb = tex.rgb * tex.a + bg.rgb * (1 - tex.a)
```
2 次乘法 + 1 次加法。

**Premultiplied alpha 混合**:
```
final.rgb = tex.rgb_premul + bg.rgb * (1 - tex.a)
```
1 次乘法 + 1 次加法。**少一次乘法**——在每像素百万次循环里,这是巨大优化。

#### 2.3 多次叠加:associativity

考虑在背景 B 上依次画 P1、P2、P3 三个半透明 sprite。

**Straight alpha**:
- 画 P1:`final1 = P1.rgb*P1.a + B.rgb*(1-P1.a)`
- 画 P2:`final2 = P2.rgb*P2.a + final1.rgb*(1-P2.a)`
- 画 P3:`final3 = P3.rgb*P3.a + final2.rgb*(1-P3.a)`

每步要 2 次乘法,且**结果依赖顺序**(画 P1 再画 P2 vs 画 P2 再画 P1,结果可能不同)。

**Premultiplied alpha**:
- 画 P1:`final1 = P1.rgb_premul + B.rgb*(1-P1.a)`
- 画 P2:`final2 = P2.rgb_premul + final1.rgb*(1-P2.a)`
- 画 P3:`final3 = P3.rgb_premul + final2.rgb*(1-P2.a)`

数学上仍然依赖顺序,但**每一步更高效**,且某些复合运算(像区域合成 compositing)有 closed-form 解。这就是为什么电影工业、Photoshop 都用 premultiplied。

#### 2.4 Linear 空间是必须的

回到 Day 094 的根本:**所有线性组合**(包括 alpha 混合)必须在 linear 空间做,否则暗部错。

完整正确流程:

```
1. 加载纹理:straight sRGB → premultiplied linear
   linear_rgb = srgb_to_linear(rgb) * alpha
   linear_a = alpha

2. 渲染:在 linear 空间混合
   fb_linear = tex.linear_rgb + fb_linear * (1 - tex.a)

3. 写 framebuffer:linear → sRGB
   fb_srgb_byte = linear_to_srgb(fb_linear) * 255
```

#### 2.5 framebuffer 的存储选择

你的 framebuffer 是 sRGB 字节(屏幕直接显示)。但渲染中间过程是 linear 浮点。两种方案:

**方案 A:framebuffer 存 linear f32**
- 渲染时直接混合,无转换
- 写屏幕时统一转 sRGB
- 内存:f32×4 = 16 字节/像素(8K 屏 = 130MB!)

**方案 B:framebuffer 存 sRGB u8**
- 渲染时每像素 sRGB → linear → 混合 → linear → sRGB
- 内存:u8×4 = 4 字节/像素(便宜)
- 但每像素 2 次 powf(慢)

**方案 C:Hybrid**
- 多个 framebuffer 中间结果存 linear f32
- 最终显示 framebuffer 存 sRGB u8
- Casey HH 用类似方案

Casey HH Day 095 用方案 B + LUT 优化(powf 换成 256 项 LUT,快很多)。

### Rust 完整实现

```rust
// LUT(同 Day 094)
fn build_srgb_lut() -> [f32; 256] {
    let mut t = [0.0; 256];
    for i in 0..256 {
        let s = i as f32 / 255.0;
        t[i] = if s <= 0.04045 { s / 12.92 } else { ((s + 0.055) / 1.055).powf(2.4) };
    }
    t
}
fn linear_to_srgb_byte(c: f32) -> u8 {
    let l = if c <= 0.0031308 { c * 12.92 } else { 1.055 * c.powf(1.0 / 2.4) - 0.055 };
    (l * 255.0).round().clamp(0.0, 255.0) as u8
}

// 纹理:premultiplied linear
struct LinearBitmap {
    width: u32,
    height: u32,
    pixels: Vec<[f32; 4]>,  // (r*a, g*a, b*a, a),全部 linear,全部 0..1
}

impl LinearBitmap {
    fn from_srgb_straight_pnm(width: u32, height: u32, srgb: &[u8; 4*256]) -> Self {
        // 简化:假设只有 256 像素
        let lut = build_srgb_lut();
        // ...
        unimplemented!()
    }
    fn from_srgba_straight(width: u32, height: u32, srgba_bytes: &[u8]) -> Self {
        let lut = build_srgb_lut();
        let pixels = srgba_bytes.chunks(4).map(|c| {
            let r = lut[c[0] as usize];
            let g = lut[c[1] as usize];
            let b = lut[c[2] as usize];
            let a = c[3] as f32 / 255.0;
            [r * a, g * a, b * a, a]  // premultiply
        }).collect();
        Self { width, height, pixels }
    }
}

// Framebuffer 也用 linear f32(为了演示,实际可以用方案 B)
struct LinearFramebuffer {
    width: usize,
    height: usize,
    pixels: Vec<[f32; 4]>,  // linear RGBA
}
impl LinearFramebuffer {
    fn new(w: usize, h: usize) -> Self {
        Self { width: w, height: h, pixels: vec![[0.0, 0.0, 0.0, 1.0]; w * h] }
    }
    fn to_srgba_bytes(&self) -> Vec<u8> {
        self.pixels.iter().flat_map(|p| {
            [
                linear_to_srgb_byte(p[0]),
                linear_to_srgb_byte(p[1]),
                linear_to_srgb_byte(p[2]),
                (p[3].clamp(0.0, 1.0) * 255.0).round() as u8,
            ]
        }).collect()
    }
}

// 预乘 alpha 混合
fn blend_premul(bg: [f32; 4], fg: [f32; 4]) -> [f32; 4] {
    let inv_a = 1.0 - fg[3];
    [
        fg[0] + bg[0] * inv_a,
        fg[1] + bg[1] * inv_a,
        fg[2] + bg[2] * inv_a,
        fg[3] + bg[3] * inv_a,  // alpha 也叠加
    ]
}

// 完整 draw_textured_quad:省略 AABB / 逆矩阵,只展示混合
fn draw_textured_quad_lin(fb: &mut LinearFramebuffer, tex: &LinearBitmap, px: usize, py: usize) {
    if px < fb.width && py < fb.height {
        let bg = fb.pixels[py * fb.width + px];
        let fg = tex.pixels[0];  // 简化:单像素纹理
        fb.pixels[py * fb.width + px] = blend_premul(bg, fg);
    }
}

fn main() {
    let mut fb = LinearFramebuffer::new(1, 1);
    fb.pixels[0] = [0.5, 0.5, 0.5, 1.0];  // 灰色背景(linear)
    // 一个半透明红色 sprite
    let tex_bytes = [255, 0, 0, 128];  // straight sRGB:不透明红,alpha=0.5
    let tex = LinearBitmap::from_srgba_straight(1, 1, &tex_bytes);
    draw_textured_quad_lin(&mut fb, &tex, 0, 0);
    let result = fb.pixels[0];
    println!("final linear: {:?}", result);
    // 转 sRGB 看看
    let bytes = fb.to_srgba_bytes();
    println!("final sRGB bytes: {:?}", bytes);
    // 预期:背景灰(0.5) + 红色半透(0.5*0.5=0.25 红) = (0.5, 0.25, 0.25)
}
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

预乘 alpha 在游戏开发里的实际影响:

1. **粒子效果**:大量半透明 sprite 叠加(烟雾、火焰)。预乘 alpha 让性能 ×2
2. **UI 渲染**:按钮边缘、阴影、毛玻璃效果都靠半透明混合
3. **抗锯齿**:Day 092 的 MSAA 边缘混合,在 linear 空间做才对
4. **post-processing**:模糊、bloom、tonemapping 都涉及混合,linear 是前提

**坑:GIF / PNG 是 straight alpha**。加载时必须**手动转 premultiplied**。如果忘了转,画面会变亮(因为 RGB 没乘 alpha,渲染时被当成 premultiplied 用,实际 RGB 太大)。

**坑:Photoshop 导出选项**。Photoshop 可以选 straight 或 premultiplied alpha 导出 PNG/PSD。游戏美术通常不知道这个区别,直接默认导出——必须美术和程序约定一个。

### 3.2 · 🎨 图形学视角

预乘 alpha 的几个深入话题:

**1. Compositing operators**(合成操作子):Porter-Duff 1984 年论文定义了 12 种合成方式(over、in、out、atop、xor...)。预乘 alpha 让所有 operator 公式简化。比如「over」(P1 画在 P2 上):
- Straight:`over.rgb = P1.rgb*P1.a + P2.rgb*P2.a*(1-P1.a)`、`over.a = P1.a + P2.a*(1-P1.a)`
- Premultiplied:`over.rgb = P1.rgb + P2.rgb*(1-P1.a)`、`over.a = P1.a + P2.a*(1-P1.a)`

**2. Alpha-to-coverage**:MSAA 把 alpha 转换成 coverage mask(子像素覆盖率),用硬件做抗锯齿。GPU API 直接支持。

**3. 干净的边**:Day 092 提到的 sprite 锯齿,预乘 alpha 自动解决——边缘像素 alpha=0.5 就是「50% 覆盖」,预乘后 RGB 减半,混合时和背景 50%/50%,自然平滑。

**4. JPEG 不支持 alpha**——所以游戏用 PNG(有 alpha)或 BC3/BC7 压缩纹理(GPU 用)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的合成器(compositor)——Wayland / X11 composite / Mutter / KWin——都涉及大量 alpha 混合。

```bash
# 看你系统的合成器
ps aux | grep -i "comp\|mutter\|kwin"
# 输出类似:/usr/lib/mutter 或 kwin_x11

# Wayland 上,每个窗口的 RGBA buffer 通过 wl_surface 提交给合成器
# 合成器在 GPU 上做预乘 alpha 混合(免费)
```

游戏自己跑在窗口里,**不要假设合成器会做 sRGB 转换**——你必须输出正确的 sRGB framebuffer。

### 3.4 · 🦀 Rust 生态视角

Rust 里 alpha 混合的 crate:

1. **`blend`** — 专门做 alpha 混合,支持多种 operator
2. **`image` crate 的 imageproc::pixelops** — 提供 blend 函数
3. **`tiny-skia`** — 内置完整 alpha 混合,工业级

**SIMD 加速混合**:`blend_premul` 是 4 个 f32 独立运算,SSE `_mm_sub_ps` + `_mm_mul_ps` + `_mm_add_ps` 一次算 4 个像素。Casey Day 112+ 大量用。

**`unsafe` 边界**:把 `Vec<u8>` 重新解释为 `Vec<[f32; 4]>`(或反过来)需要 `unsafe`。`bytemuck` crate 提供安全封装。

## 5 · 对照与变奏

### PNG vs PSD vs EXR

- **PNG**:straight alpha,sRGB。游戏加载时转 premultiplied linear。
- **PSD**:可选 straight 或 premultiplied,通常 RGB。
- **EXR**(电影用):linear half-float,premultiplied。直接用。

 Casey HH 用 PNG,自己转。Phase 7+ 会支持 EXR。

### straight → premul 转换的不可逆性?

Straight `(r, g, b, a)` 转 premul `(r*a, g*a, b*a, a)`,**反操作需要除以 a**。如果 a=0,RGB 信息丢失(任何除 0 都无穷)。所以 straight → premul 是「有损」的——零 alpha 像素的 RGB 不能恢复。

但 premul → straight 是「无损」的:只需 `rgb/a`。**为什么 PNG 不直接用 premul?** 因为 straight 让 alpha=0 像素可以存任意 RGB(比如标记颜色、editor metadata)。这是图像编辑软件需要的。

- 1984 Porter-Duff 论文《Compositing Digital Images》奠定 alpha 理论

- 2000s GPU 全面支持 premultiplied(硬件混合更快)
- 2010s PBR 兴起,linear + premul 成为标配

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 straight alpha 在 GPU 上不流行?给 2 个具体理由。

**参考解答**:
1. **混合公式多一次乘法**。Premultiplied 是 `rgb + bg*(1-a)`(1 次乘 + 1 次加),straight 是 `rgb*a + bg*(1-a)`(2 次乘 + 1 次加)。GPU 每秒做几亿次这个操作,少一次乘法 = 性能 ×2。
2. **预乘后 RGB ≤ alpha** 是一个不变式,GPU 硬件可以用来优化(比如 alpha=0 的像素直接跳过 RGB 通道处理)。

### Lv2 · 动手实践

**题**:实现完整的 `draw_textured_quad_premul`——给定 straight sRGB 纹理和 linear f32 framebuffer,正确地:
1. 在纹理加载时转 premultiplied linear
2. 渲染时在 linear 空间做预乘 alpha 混合
3. 输出 framebuffer 时转 sRGB

测试:背景是 sRGB (200, 200, 200),sprite 是 sRGB (255, 0, 0) alpha=128。最终 sRGB framebuffer 应该是什么颜色?

**参考解答**:见 §2 完整代码。预期结果:
- 背景 linear = srgb_to_linear(200/255) ≈ 0.578
- 前景 linear = srgb_to_linear(1.0) = 1.0,premul 后 = 0.5(因为 alpha=0.5)
- 混合:`fg + bg * (1-0.5) = 0.5 + 0.578 * 0.5 = 0.789`(红通道)
- 绿/蓝通道:`0 + 0.578 * 0.5 = 0.289`
- linear → sRGB:0.789 → 225,0.289 → 132
- 最终 sRGB 大约 (225, 132, 132)

### Lv3 · 迁移设计

**题**:你想做一个**渐隐效果**——sprite 从完全可见(alpha=1)渐隐到完全不可见(alpha=0),持续 1 秒。如果在 linear 空间插值 alpha vs 在 sRGB 空间插值 alpha,视觉差别是什么?

**提示**:
- linear:alpha = 1.0 - t(t 是 0..1 时间)
- sRGB:alpha 在线性 t 空间插值
- 视觉感受:人眼对暗色更敏感。渐隐时,linear 插值看起来「先慢后快」(暗部跳变更明显);sRGB 插值看起来「先快后慢」

## 8 · Rust / Arch 落地代码

### 完整 sprite 渲染器(线性 + 预乘 alpha)

```rust
// Cargo.toml: image = "0.25"
use image::GenericImageView;

// [LUT / linear_to_srgb_byte / LinearBitmap / LinearFramebuffer / blend_premul 同 §2]

fn main() {
    let img = image::open("assets/sprite.png").unwrap();
    let (w, h) = img.dimensions();
    let rgba = img.to_rgba8();
    let tex = LinearBitmap::from_srgba_straight(w, h, &rgba);

    let mut fb = LinearFramebuffer::new(800, 600);
    // 渲染一些 sprite(简化:不旋转,直接在 (100, 100) 画)
    for y in 0..h as usize {
        for x in 0..w as usize {
            let fg = tex.pixels[y * w as usize + x];
            let bg = fb.pixels[(100 + y) * 800 + (100 + x)];
            fb.pixels[(100 + y) * 800 + (100 + x)] = blend_premul(bg, fg);
        }
    }

    // 输出 sRGB PNG
    let bytes = fb.to_srgba_bytes();
    image::save_buffer("/tmp/output.png", &bytes, 800, 600, image::ColorType::Rgba8).unwrap();
}
```

### Troubleshooting

- **画面太亮** — straight alpha 没转 premultiplied。检查加载代码
- **画面太暗** — linear → sRGB 转了两次
- **半透明边缘有黑边** — 美术在 alpha 边缘外画了黑色 RGB(应该在 alpha=0 区域 RGB 也清零)
- **性能差** — 每像素 powf。改用 LUT
