# Day 097 · 管线中加入法线贴图

> 昨天 Day 096 你写了 Phong 光照——但每个 sprite 只有一个法线(整个面朝相机 (0, 0, 1))。结果光照是「整体变亮或变暗」,看不出表面**细节**。**法线贴图**(normal map)是图形学的另一招魔法——它让你在每像素**查表**得到不同的法线,从而伪造出表面有凹凸细节的效果。一面平墙看起来有砖缝、一把塑料剑看起来有刻痕、一个 200 三角形的低模看起来像 200 万三角形的高模——全是法线贴图的功劳。

## 0 · 为什么要有这一天

考虑一面砖墙的纹理。美术画的时候,他画了:
1. **diffuse map**(漫反射图):墙的砖块颜色——红棕色、灰缝
2. **normal map**(法线贴图):每像素的「表面朝向」——大部分是 (0, 0, 1)(朝相机),但砖缝处是 (0.3, 0, 0.95)(略微侧向)

渲染时,**每像素独立查法线**,Phong 光照用这个像素的法线计算亮度。结果:光从右上来时,砖缝左侧(法线偏左)看起来亮,右侧(法线偏右)看起来暗——出现**立体的砖缝效果**,虽然表面几何其实是平的!

这就是法线贴图的核心思想:**用纹理图存储法线信息,在 shader 里查表代替真实几何**。

**关键概念:tangent space**(切线空间)。法线贴图存的法线是「**相对表面**」的——(0, 0, 1) 意味着「垂直于表面」,不是「垂直于屏幕」。如果你的表面在 3D 空间里斜着摆放,法线贴图里的 (0.3, 0, 0.95) 要变换到世界空间才能用于光照。这个变换叫 **TBN 变换**(Tangent-Bitangent-Normal)。

Casey HH 因为是 2.5D(所有 sprite 都朝相机),不需要完整 TBN——法线贴图直接用,无需变换。但 Casey 会介绍 TBN 概念,因为 Day 102+ 真正的 3D 法线贴图要用。

心理锚点:看完今天,你的渲染器能伪造出**有表面细节**的 sprite——砖墙有立体感,衣物有褶皱,金属有刮痕。你能向队友解释「为什么法线贴图让低模看起来像高模」。

## 1 · Casey 今天做了什么

Casey 今天做的事情:

1. 引入法线贴图文件——一张 RGB 图,每像素存一个 3D 法线向量
2. 解码:`normal = (texel.rgb * 2.0) - 1.0`(把 [0, 1] 范围映射到 [-1, 1],因为法线分量可以是负)
3. 把 Day 096 的 Phong 光照里的法线从「固定 (0, 0, 1)」改成「从法线贴图采样」
4. 演示:用同一张 brick 纹理(有/无法线贴图)对比,法线贴图版有立体感

Casey 强调一个**色彩空间坑**:法线贴图**不是 sRGB**,是 linear 数据。加载时**不能用 sRGB→linear LUT**!否则法线被错误转换,光照结果错。法线贴图必须**直接当 linear 加载**(原始字节 / 255)。

## 2 · 心智模型

### 费曼类比:地图上的等高线

地形图用**等高线**表示高度——线越密,坡越陡。但地图本身是平的纸。

法线贴图类似——它是一张图,但**不存颜色**,而是存「**这个像素位置的表面朝哪**」。读图时,你能想象出表面形状(凹凸),但实际几何是平的。

**关键差别**:等高线存「高度」,法线贴图存「**朝向**」。朝向比高度更直接——光照只关心朝向(N·L),不关心绝对高度。所以法线贴图直接给你光照需要的信息,无需算梯度。

### 严谨原理

#### 2.1 法线贴图的存储格式

法线是 3D 单位向量 `(x, y, z)`,每个分量在 [-1, 1]。但图片格式存 [0, 255] 字节。映射:

```
// 存(写图时)
byte = (normal_component + 1.0) * 0.5 * 255
// 读(读图时)
normal_component = byte / 255.0 * 2.0 - 1.0
```

例如:
- 法线 (0, 0, 1)(朝相机):字节 (127, 127, 255)(中性紫蓝)
- 法线 (1, 0, 0)(朝右):字节 (255, 127, 255)
- 法线 (-1, 0, 0)(朝左):字节 (0, 127, 255)

**视觉判别**:打开一张法线贴图,你会看到大量「紫蓝色」——这是「朝相机」的法线。任何偏离紫蓝色的颜色代表局部表面朝向变化。

#### 2.2 为什么蓝色主导?

3D 单位法线 `N = (x, y, z)`,x² + y² + z² = 1。如果表面大致朝相机,z ≈ 1,x 和 y 很小。所以 z 通道接近 1(字节接近 255 = 蓝),xy 通道接近 0(字节接近 127 = 中性)。**RGB (127, 127, 255) 就是紫蓝**——法线贴图的标志色。

#### 2.3 tangent space vs world space

**Tangent space 法线贴图**(最常见):存的法线是「相对当前表面」的。(0, 0, 1) 意味着「朝当前表面外」。变换到世界空间需要 TBN 矩阵。

**World/object space 法线贴图**:存的法线直接是世界坐标。简单但只能用于**静态物体**(动起来法线就不对了)。

Casey HH 用 tangent space(因为 sprite 会动)。

#### 2.4 TBN 矩阵

对每个三角形,定义三个向量:
- **T**(tangent):沿纹理 u 方向的世界向量
- **B**(bitangent):沿纹理 v 方向的世界向量
- **N**(normal):垂直于表面

TBN 矩阵把 tangent space 法线变换到世界空间:

```
world_normal = TBN · tangent_space_normal
```

TBN 的列向量就是 T、B、N。对 2.5D(sprite 平铺在 xy 平面):T = (1,0,0)、B = (0,1,0)、N = (0,0,1),所以 TBN = 单位矩阵——法线贴图直接用。

对真 3D(三角形任意朝向):TBN 三角形几何计算,Day 102 Casey 详细讲。

#### 2.5 完整光照流程

```
1. 采样 diffuse map → linear surface_color(已 sRGB→linear,Day 094)
2. 采样 normal map → 解码 normal(直接 linear,NOT sRGB)
3. (3D 时)把 normal 从 tangent space 变到 world space
4. Phong/Blinn-Phong 光照
5. 输出 linear final_color
6. framebuffer: linear → sRGB
```

### Rust 实现

```rust
#[derive(Copy, Clone)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn dot(self, o: Self) -> f32 { self.x*o.x + self.y*o.y + self.z*o.z }
    fn add(self, o: Self) -> Self { Self::new(self.x+o.x, self.y+o.y, self.z+o.z) }
    fn scale(self, k: f32) -> Self { Self::new(self.x*k, self.y*k, self.z*k) }
    fn length(self) -> f32 { self.dot(self).sqrt() }
    fn normalized(self) -> Self {
        let l = self.length();
        if l > 1e-6 { self.scale(1.0 / l) } else { Self::new(0.0, 0.0, 1.0) }
    }
}

// 法线贴图:linear 直接(不经过 sRGB)
struct NormalMap {
    width: u32,
    height: u32,
    pixels: Vec<[f32; 3]>,  // tangent space normal,xyz 在 [-1, 1]
}

impl NormalMap {
    fn from_bytes(width: u32, height: u32, rgb_bytes: &[u8]) -> Self {
        let pixels = rgb_bytes.chunks(3).map(|c| {
            let x = c[0] as f32 / 255.0 * 2.0 - 1.0;
            let y = c[1] as f32 / 255.0 * 2.0 - 1.0;
            let z = c[2] as f32 / 255.0 * 2.0 - 1.0;
            Vec3::new(x, y, z).normalized()  // 保险归一化
        }).map(|v| [v.x, v.y, v.z]).collect();
        Self { width, height, pixels }
    }
    fn sample_nearest(&self, u: f32, v: f32) -> Vec3 {
        let tx = (u.clamp(0.0, 1.0) * (self.width - 1) as f32) as u32;
        let ty = (v.clamp(0.0, 1.0) * (self.height - 1) as f32) as u32;
        let p = self.pixels[(ty * self.width + tx) as usize];
        Vec3::new(p[0], p[1], p[2])
    }
}

// [LUT / Color / Light / reflect / phong_lighting 同 Day 096]

fn render_pixel_with_normal(
    diffuse_color: Color,
    normal: Vec3,           // 已归一化
    view_dir: Vec3,
    light: Light,
    ambient: Color,
    shininess: f32,
) -> Color {
    phong_lighting(diffuse_color, normal, view_dir, light, ambient, shininess)
}

fn main() {
    // 一张 4x4 法线贴图(测试用):大部分朝相机,有一个像素朝右
    let normal_bytes = vec![
        127,127,255,  127,127,255,  127,127,255,  127,127,255,
        127,127,255,  255,127,255,  127,127,255,  127,127,255,  // (1,1) 朝右
        127,127,255,  127,127,255,  127,127,255,  127,127,255,
        127,127,255,  127,127,255,  127,127,255,  127,127,255,
    ];
    let normal_map = NormalMap::from_bytes(4, 4, &normal_bytes);

    let light = Light {
        direction: Vec3::new(0.7, 0.0, 0.7).normalized(),
        color: Color { r: 1.0, g: 1.0, b: 1.0 },
        intensity: 1.0,
    };
    let ambient = Color { r: 0.1, g: 0.1, b: 0.1 };
    let view = Vec3::new(0.0, 0.0, 1.0);
    let surface = Color { r: 0.7, g: 0.7, b: 0.7 };

    // 测试两个像素的亮度差别
    let n_flat = normal_map.sample_nearest(0.0, 0.0);     // (0,0): 朝相机
    let n_right = normal_map.sample_nearest(0.4, 0.4);    // (1,1): 朝右

    let lit_flat = render_pixel_with_normal(surface, n_flat, view, light, ambient, 50.0);
    let lit_right = render_pixel_with_normal(surface, n_right, view, light, ambient, 50.0);

    println!("flat normal lighting: r={:.3}", lit_flat.r);
    println!("right normal lighting: r={:.3}", lit_right.r);
    // 朝右的法线和光向(右上方)对齐更好,应该更亮
    assert!(lit_right.r > lit_flat.r);
}
```

**关键点**:
- 法线贴图加载用 `byte/255 * 2 - 1`,**不**用 sRGB→linear LUT
- `normalized()` 保险——纹理存的可能不严格单位(美术误差)
- 同一张 diffuse map,不同法线产生不同亮度——立体感的来源

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

法线贴图在游戏开发的应用:

1. **角色装备**:剑、盾牌上的纹理细节
2. **环境**:砖墙、地砖、木材纹理
3. **角色脸**:皮肤褶皱、眉毛、伤疤
4. **科幻表面**:金属刮痕、机甲铆钉

**生成法线贴图的方法**:
- **美术手绘**(Photoshop 插件如 nDo):成本高,质量最好
- **从高模烘焙**(baking):高模(几百万三角形)渲染法线 → 写入低模(几百三角形)的 uv 空间。这是工业主流(Substance Painter、Blender bake)
- **照片生成**:`AwesomeBump`、`ShaderMap` 从照片自动推断

**坑:镜像 UV**。如果 sprite 用了镜像(对称贴图),法线也要镜像——但 xy 通道要取反。否则光照反了。

**坑:动态光照下的法线贴图**。法线贴图本身是静态的(纹理固定),但光照变化让它「活」起来。手电筒扫过墙时,砖缝的高光跟着移动——这是法线贴图最神奇的视觉效果。

### 3.2 · 🎨 图形学视角

**法线贴图的兄弟技术**:

1. **bump map**:存「高度」而不是法线。渲染时算梯度(差分)得法线。老技术(1980s),已被 normal map 取代。
2. **parallax map / parallax occlusion map**:除了法线,还存高度,渲染时做视线偏移。模拟「立体凹凸」更逼真,但有 artifact。
3. **displacement map**:真正移动几何顶点。最逼真,但需要高模(顶点 shader 改几何)。Casey HH 不用。
4. **height map**:地形高度图,定义地形几何本身。

**法线贴图的物理正确性**:法线贴图是「视觉骗术」,不改变几何。从侧面看,假砖缝仍然是平的。所以法线贴图适合「**远距离看**」——离太近会穿帮。

**与 PBR 配合**:现代 PBR 用 normal map + roughness map + metallic map + AO map 组合,完整描述表面属性。Casey HH Day 200+ 走向 PBR。

### 3.5 · 🐧 Linux 系统编程视角(内核空间 / 硬件加速)

Linux 系统里"碰撞 / 相交检测"的核心思想在多处出现,理解这些能让你看 Casey 的 2D / 3D collision 算法在更广的语境里。

**内核的 page fault 处理**。虚拟内存到物理内存的映射,本质是"地址空间相交检测"。CPU 访问虚拟地址,MMU 查 page table,如果地址不在已映射范围内 → page fault。内核接 fault,检查(1)地址合法吗(进程的 VMA 区间)、(2)权限对吗(read / write / exec)、(3)page 在物理内存还是 swap。这套检查就是"区间相交 + 属性匹配",和 Casey 在 day 050 的 Minkowski collision 在抽象上一致——"用几何空间判断两个东西是否接触"。

```bash
# 看你进程的 VMA(虚拟内存区域)
cat /proc/$$/maps
# 输出形如:
# 56001234-56005678 r-xp ...  /usr/bin/bash
# 7f1234560000-7f1234780000 r--p ... /usr/lib/libc.so.6

# 触发 page fault(故意访问非法地址)
python3 -c "import ctypes; ctypes.cast(0xdeadbeef, ctypes.POINTER(ctypes.c_int))[0] = 0"
# 输出:Segmentation fault (core dumped)
```

**epoll / poll / select** 是 IO 多路复用,本质是"时间区间相交"。你给内核 N 个 fd,内核检查"哪个 fd 当前可读 / 可写"。这是 N 路并行等待,内核用红黑树 + ready list 高效管理。和 collision detection 的 broad phase 类似——快速排除不可能相交的对,只在 narrow phase 详细检查。

**文件锁(flock / fcntl)**。Linux 文件锁检测"两个进程是否同时持有冲突锁"——这是"锁区间相交"。flock 用 inode-level 锁,fcntl 用 byte-range 锁(`fcntl(F_SETLK, F_WRLCK, {100..200})` 锁字节 100-200)。内核维护锁列表,新锁请求时遍历检查冲突——这就是 interval intersection 检测。

**网络栈的 TCP / IP header 校验**。每个 TCP/IP 包带 checksum,内核收到包校验——本质是"数据完整性检测"。和 collision detection 不直接相关,但**思想相同**——"用一个数学函数快速判断数据是否合法"。

**cgroup 的资源限制**。`cpu.max = 50000 100000` 表示 cgroup 在每 100ms 周期内最多用 50ms CPU。内核定期检查"当前周期已用多少 CPU",超了 throttle。这是"时间区间累积 + 阈值检测",和 Casey 的"span duration + frame budget"逻辑相同。

**netfilter / iptables** 用 BPF 风格的规则匹配,检查每个网络包。"规则匹配"本质是"包属性 vs 规则区间"——"src IP in 192.168.0.0/16 && dst port == 22"是区间检测。BPF (Berkeley Packet Filter) 让用户写过滤器,内核执行——这种"用户定义函数 + 内核执行"模式是 eBPF 的基础。

**kernel scheduling**。Linux CFS(Completely Fair Scheduler)维护红黑树 of runnable tasks,按 vruntime 排序。每个 tick(1ms / 4ms),CFS 检查当前 task 是否该让出 CPU——"时间片用完了吗"。这是"时间累积 + 阈值切换",和游戏 update 循环的 frame budget 检查同构。

### 3.6 · 🦀 Rust 生态视角

Rust 在游戏物理 / 碰撞领域有几个值得关注的 crate 和模式。

**`rapier`** 是 Rust 的 2D / 3D 物理引擎,由 Dimforge 开发。Rapier 提供 rigid body dynamics、collision detection、joints、rays、sensors——是 Bevy 生态的物理默认选项。Rapier 用 ECS 风格 API,内部用 SOA(struct of arrays)布局,cache 友好。

```rust
use rapier3d::prelude::*;

let mut rigid_body_set = RigidBodySet::new();
let mut collider_set = ColliderSet::new();

let rigid_body = RigidBodyBuilder::dynamic().translation(vector![0.0, 5.0, 0.0]).build();
let handle = rigid_body_set.insert(rigid_body);
let collider = ColliderBuilder::ball(0.5).build();
collider_set.insert_with_parent(collider, handle, &mut rigid_body_set);
```

Rapier 内部用 **broad phase(AABB tree)+ narrow phase(GJK / SAT)**,和工业 C++ 引擎(Box2D、Bullet、PhysX)思路一致。Casey HH 手写简化版,Rapier 是 production-grade。

**`parry`** 是 Rapier 抽出来的纯 collision detection 库。parry 提供 shape(ball、cuboid、convex hull、triangle mesh)、ray cast、point projection、pair collision——不涉及 dynamics。如果你只想要碰撞不想物理,parry 是答案。

**`nalgebra`** 是 Rust 的线性代数库,Dimforge 出品(同 Rapier / parry)。`Vector3`、`Matrix4`、`Quaternion`、`Isometry3`——3D 游戏需要的所有数学类型。比 `cgmath` 现代、比 `euclid` 全面。

**Rust ECS 的 collision pattern**。Bevy + Rapier 的典型代码:

```rust
use bevy::prelude::*;
use bevy_rapier3d::prelude::*;

fn setup(mut commands: Commands) {
    commands.spawn((
        RigidBody::Dynamic,
        Collider::ball(1.0),
        Transform::from_translation(Vec3::new(0.0, 5.0, 0.0)),
    ));
}

fn on_collision(
    mut events: EventReader<CollisionEvent>,
    query: Query<&Name>,
) {
    for event in events.read() {
        if let CollisionEvent::Started(e1, e2, _) = event {
            println!("{:?} collided with {:?}", query.get(*e1), query.get(*e2));
        }
    }
}
```

ECS 风格——entity 加 Collider component,系统处理 CollisionEvent。这是 Rust 风格的 collision 设计——数据导向、零成本、类型安全。Casey HH 用 OOP 风格(`struct Player { collider: Collider }`),简单但不够通用。

**Rust 的 zero-cost abstraction** 让 collision detection 可以既高级又快:

```rust
// 高级 API
let hits = colliders.iter()
    .filter(|c| c.aabb_intersects(&target_aabb))
    .filter(|c| c.shape_intersects(&target_shape))
    .collect::<Vec<_>>();

// LLVM 把这优化成手写 C 的等价代码
```

Rust 的 iterator chain + 闭包,被 LLVM inline + vectorize,生成和手写循环一样快的代码。这是 Rust 在性能敏感领域的杀手锏。

**Rust 的 SIMD** 对 collision 特别有用。AABB 测试 8 个浮点比较,用 SIMD 一次处理 4-8 个 AABB。Rust 的 `std::simd`(unstable)或 `wide` crate(stable)提供 SIMD API。Rapier 内部用 SIMD 加速 broad phase。

**Rust 的多线程 collision**。collision detection 是 embarrassingly parallel——N 个 object pair 互相独立。Rust 的 `rayon` 提供 parallel iterator,`colliders.par_iter().filter(...)` 自动并行。Bevy 用 ECS 的 `query.par_iter()` 同样效果。

**Rust 的 `Send + Sync`**。collision data 跨线程共享,要 `Send + Sync`。Rust 编译时检查——如果你的 Collider 包含 `Rc<...>`,编译失败,因为 Rc 不是 Send。这种类型系统保证的多线程安全,是 Rust 比 C++ 优势的地方。

**Rust 的 `smallvec`** 在 collision 里有用。pair list 经常是空的或只有 1-2 个 pair,用 `SmallVec<[Pair; 4]>` 避免堆分配,大部分情况栈上。

**Rust 的 `ahash`** 在 spatial hash 里替代 `DefaultHasher`——3-5 倍速度。Casey HH 的 hash chunk storage(Phase 2)用 `DefaultHasher`,Rust 版应该用 `ahash` 或 `fxhash`。

## 4 · 认知地图

### 4.1 上级

- **纹理映射扩展** — 法线贴图是「纹理图存非颜色数据」思想的体现
- **伪造几何 (fake geometry)** — 不改顶点但伪造表面细节的所有技术
- **BRDF 输入** — 法线是 Phong/Blinn-Phong/PBR BRDF 的核心输入

### 4.2 同级

| 技术 | 存什么 | 改变 | 复杂度 | 效果 |
|---|---|---|---|---|
| Bump map | 高度 | 法线 | 低 | 老旧 |
| Normal map | 法线 | 法线 | 中 | 主流 |
| Parallax map | 法线 + 高度 | 法线 + uv 偏移 | 高 | 更立体 |
| Displacement map | 高度 | 顶点位置 | 最高 | 真立体 |

### 4.3 下级

- **tangent space** — 法线的「相对表面」坐标系
- **TBN 矩阵** — tangent space → world space 的变换
- **解码公式** — `(byte / 255) * 2 - 1`
- **法线归一化** — 保证光照正确
- **烘焙 (baking)** — 从高模生成法线贴图的流程

## 5 · 对照与变奏

### 法线贴图 vs 顶点法线

- **顶点法线**:每个顶点一个法线,三角形内部线性插值。适合平滑表面(球、角色),但无法表达细节。
- **法线贴图**:每像素一个法线,可表达任意细节。但只能伪造(不改几何)。

工业做法:**两者都用**——顶点法线定义整体形状,法线贴图加上细节。

### Tangent space vs World space 法线贴图

| | Tangent | World |
|---|---|---|
| 法线相对 | 表面 | 世界 |
| 用于静态 | ✅ | ✅ |
| 用于动态 | ✅ | ❌(动起来法线就不对) |
| 模型变形 | ✅ | ❌ |
| 文件大小 | 同 | 同 |
| 复杂度 | 需要 TBN | 直接用 |

**主流是 tangent space**,因为灵活。Casey HH 因为 2.5D 简化,实际是 tangent space 但 TBN = 单位矩阵。

### 2D 游戏的「假法线」

很多 2D 游戏用预渲染的 3D 模型(美术在 Blender 渲染成 sprite),**同时输出 diffuse 和 normal**。这样 2D 游戏也能加动态光照——美术不动,只是法线数据来自原始 3D 渲染。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:你看到一张法线贴图,大部分是 (128, 128, 255) 的紫蓝色。这说明什么?

**参考解答**:这说明大部分像素的表面朝相机(`z ≈ 1`)。因为 z 接近 1,字节值接近 255(蓝);xy 接近 0,字节值接近 128(中性灰)——所以 RGB = (128, 128, 255) 是紫蓝色。法线贴图主要紫蓝是「表面大部分朝外」的标志,任何偏离紫蓝的颜色代表局部表面朝向变化(法线被「扰动」)。

```rust
// 生成测试法线贴图:64x64,大部分朝相机,横向中线处朝下
fn gen_test_normal() -> Vec<u8> {
    let mut bytes = vec![0u8; 64 * 64 * 3];
    for y in 0..64 {
        for x in 0..64 {
            let idx = (y * 64 + x) * 3;
            // 中线 (y == 32) 附近:法线略朝下 (y = -0.3)
            let ny = if y == 32 { -0.5 } else { 0.0 };
            let nx = 0.0;
            let nz = (1.0 - nx*nx - ny*ny).max(0.0).sqrt();
            bytes[idx]     = ((nx + 1.0) * 0.5 * 255.0) as u8;
            bytes[idx + 1] = ((ny + 1.0) * 0.5 * 255.0) as u8;
            bytes[idx + 2] = ((nz + 1.0) * 0.5 * 255.0) as u8;
        }
    }
    bytes
}
```

## 8 · Rust / Arch 落地代码

### 完整 sprite 渲染器(diffuse + normal + Phong)

```rust
// [Vec3 / Color / Light / NormalMap / phong_lighting 同 §2 + Day 096]

struct Sprite {
    diffuse: LinearBitmap,   // 已 sRGB→linear(Day 095)
    normal: NormalMap,       // 直接 linear,不参与 sRGB
}

fn render_sprite(
    fb: &mut LinearFramebuffer,
    sprite: &Sprite,
    light: Light,
    view: Vec3,
    origin: Vec2,
    m: Mat2,
) {
    let inv = m.inverse();
    // AABB 略
    for py in min_y..=max_y {
        for px in min_x..=max_x {
            let wx = px as f32 + 0.5;
            let wy = py as f32 + 0.5;
            let (u, v) = inv.mul_vec(wx - origin.x, wy - origin.y);
            if u >= 0.0 && u <= 1.0 && v >= 0.0 && v <= 1.0 {
                let diffuse = sprite.diffuse.sample(u, v);
                if diffuse[3] < 0.01 { continue; }  // 完全透明
                let normal = sprite.normal.sample_nearest(u, v);
                let surface_color = Color { r: diffuse[0], g: diffuse[1], b: diffuse[2] };
                let lit = phong_lighting(surface_color, normal, view, light,
                                         Color { r: 0.1, g: 0.1, b: 0.1 }, 50.0);
                // 预乘 alpha 混合(在 linear 空间)
                let bg = fb.pixels[py * fb.width + px];
                let inv_a = 1.0 - diffuse[3];
                fb.pixels[py * fb.width + px] = [
                    diffuse[3] * lit.r + bg[0] * inv_a,
                    diffuse[3] * lit.g + bg[1] * inv_a,
                    diffuse[3] * lit.b + bg[2] * inv_a,
                    diffuse[3] + bg[3] * inv_a,
                ];
            }
        }
    }
}
```

### Troubleshooting

- **sprite 看起来「平」,没立体感** — 法线贴图没生效。检查 `sample_nearest` 是不是返回 (0, 0, 1) 朝相机
- **光照方向反了** — 法线 xy 通道可能需要翻转。约定:法线 x 朝纹理 u 增大方向,y 朝 v 增大方向。检查 sprite 翻转 / 镜像时法线是否也要翻转
- **sprite 颜色变暗** — diffuse 已 sRGB→linear,但 framebuffer 输出时没 linear→sRGB
- **法线贴图看起来颜色不对(绿/红主导)** — 美术用了 object space 法线(不是 tangent space),需要转
