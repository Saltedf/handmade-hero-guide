# Day 106 · 世界缩放

> 今天 Casey 给 Renderer 加一个看似平淡无奇的字段:`world_scale: f32`。它的作用是「**1 个世界单位 = 多少屏幕像素**」。这个数字本身只有一行代码,但它背后的设计问题——「**游戏世界的坐标和屏幕像素如何解耦**」——是任何正经游戏引擎都必须回答的。今天我们借此机会把「**世界空间 vs 屏幕空间**」这条鸿沟讲透,顺便看到 Rust 中「**单一 f32 字段传播到全渲染管线**」是什么样子。

## 0 · 为什么要有这一天

假设你刚做完 Phase 2 的 2D 游戏。玩家精灵在世界坐标 `(100, 200)`,你在屏幕上 `(100, 200)` 像素位置画它。简单直接。问题来了——你想做以下任何一件事:

- **窗口大小可变**:从 800×600 调到 1920×1080,玩家应该看起来一样大,不是被压扁在左上角。
- **放大缩小**:鼠标滚轮拉近看细节,或拉远看全图。
- **不同 DPI 显示器**:在 1× 显示器上玩家是 64 像素,在 2× Retina 上还应该是 64「逻辑像素」(=128 物理像素),不然在高 DPI 屏上小得像蚂蚁。
- **切换分辨率无关渲染**(Day 109):内部固定渲染 960×540,然后缩放到任意窗口大小。

这四个需求都指向同一件事:**「世界里的距离」和「屏幕上的像素」必须解耦**。世界坐标用任意单位(比如「米」),渲染时乘一个 `world_scale` 转成屏幕像素。`world_scale` 是这两个空间的唯一桥梁,改它不影响游戏逻辑,只影响视觉比例。

这种解耦带来的能力是真实的。第一,**关卡设计师**用「米」思考(玩家身高 1.8 米,跳跃高度 0.8 米),不必关心屏幕像素。第二,**美术资源**用「米」建模,跨关卡复用。第三,**UI 设计师**用「屏幕像素」思考(按钮 80×24 像素),不被世界 scale 干扰。第四,**测试**容易——你可以跑一段游戏代码,把 `world_scale` 设成 1,记录玩家轨迹是世界米数,完全脱离渲染。

完成今天后,你将理解为什么所有商业引擎(Unreal 的 `unit` = 1cm、Unity 的 `unit` = 1m、Godot 的 `unit` = 1 pixel)都内置「**世界单位**」概念,以及 Rust 里这种「单一 scale 因子传播」的代码该怎么写得干净。

## 1 · Casey 今天做了什么(HH 脉络,简述)

Casey 在视频里做的事可以归纳为三步。

第一步,他注意到 Day 105 重构后,`Renderer` 里所有 push 命令都用世界坐标。比如 `push_bitmap(dst: Rect, ...)`,这个 `Rect` 的 `(x, y, w, h)` 是世界单位,但内部写 framebuffer 时直接当像素用——这就意味着如果窗口大小变了,世界里的物体比例就乱了。

第二步,他给 `Renderer` 加一个字段 `meters_to_pixels: f32`(Casey 用这个词,我们用 `world_scale` 同义)。在 `submit` 里,每条命令写 framebuffer 前先把世界坐标乘以 `world_scale` 得到屏幕像素坐标。

第三步,他在游戏层加一些示例调用——比如玩家身高定义成 `2.0`(米),怪物高度 `1.5`(米),`world_scale = 32.0`,所以玩家在屏幕上是 64 像素、怪物是 48 像素。Casey 然后边调 `world_scale` 边看视觉效果,找到他觉得舒服的数字。

整个过程不超过一集视频,但 Casey 在视频里讲了一个重要概念:**「**所有游戏代码都应该用世界单位思考**」**。像素只是渲染细节,不应该污染游戏逻辑。

## 2 · 心智模型

**费曼类比**。想象你在画一张地图。地图上的「**1 厘米**」代表真实世界的「**1 公里**」——这个比例尺就是 `world_scale`(1 cm = 1 km,所以 `world_scale = 0.00001` 公里/厘米,反过来就是 100000 厘米/公里)。

地图绘制员工作时只关心「北京到上海直线 1000 公里,在地图上应该是 1000 × 0.00001 = 0.01 厘米 = 0.1 毫米」——他不需要知道地图将来印在什么纸上。如果改用 A0 大纸(放大 4 倍),只需把 scale 改成 0.00004,所有距离自动按比例放大。北京还是离上海 1000 公里(世界),但地图上变成 0.4 毫米。

游戏世界就是这张地图。世界坐标是「公里」,屏幕坐标是「厘米」。

**严谨原理**。世界空间(world space)和屏幕空间(screen space)是两个独立的坐标系,`world_scale` 是它们之间的线性变换:

```
screen_pixel = world_unit × world_scale + camera_offset_pixel
```

这个公式有几个变体需要区分清楚:

- **`world_scale`**:标量(单个 f32),只放大不旋转。Casey 今天用的就是这种。
- **`world_to_screen_matrix`**:2×2 或 4×4 矩阵,可以表达「放大 + 旋转 + 剪切」。Day 105 完整版会用矩阵,Day 108 透视投影会扩展成 4×4。
- **`camera`**:另一个变换(平移 + 旋转 + 缩放),描述「相机在世界哪里、看哪个方向」。`world_to_screen = projection × view` 是图形学最经典的 MVP 链。

今天的 Casey 极简版只有 `world_scale`(标量)+ `camera_offset`(平移),已经够教学用。但你要知道这只是完整 MVP 链的一个特例。

我们看一下 Rust 代码怎么把这件事做实。先看「**坏味道**」:

```rust
// === 重构前:游戏代码直接用像素 ===
fn draw_player(r: &mut Renderer) {
    r.push_rect(100.0, 200.0, 64.0, 64.0, GREEN);  // 100 像素、200 像素、64×64 像素
}

fn main() {
    let mut r = Renderer::new(800, 600);
    draw_player(&mut r);
    r.submit();
}
// 问题:换 1920×1080 窗口,玩家还在 (100,200) 的 64×64,比例不对了
```

游戏逻辑层(玩家位置、碰撞体积)和渲染层(像素)混在一起。改窗口大小就要改游戏逻辑,这是反模式。重构后:

```rust
// === 重构后:游戏用世界单位,渲染乘 scale ===
const PLAYER_HEIGHT_M: f32 = 2.0;       // 玩家身高 2 米

fn draw_player(r: &mut Renderer, player: &Player) {
    let h = PLAYER_HEIGHT_M;
    let w = h * 0.5;                     // 宽高比 1:2
    r.push_rect(player.x, player.y, w, h, GREEN);   // 世界单位(米)
}

fn main() {
    let mut r = Renderer::new(1920, 1080);
    r.world_scale = 54.0;                // 1 米 = 54 像素(1080 像素 / 20 米视野)
    let player = Player { x: 5.0, y: 5.0 };
    draw_player(&mut r, &player);
    r.submit();
}
// 改窗口:只需调 world_scale,游戏逻辑完全不动
```

注意几点关键设计:**常量大写 + 后缀 `_M`** 表示「米」,文档化单位。**`Renderer` 持有 `world_scale`**,所有 push 命令的坐标都是世界单位——`submit` 时统一乘 scale。**游戏函数签名不出现 `pixel` 字眼**,杜绝误用。

**为什么世界单位用浮点**。世界单位的距离可以是 1.7 米、0.05 米、2000 米——人类直觉的小数。用 `f32` 表达自然。`i32` 像素必须整数,世界单位用浮点才能平滑插值(玩家移动 0.017 米/帧)。这也意味着提交时要做浮点到整数的转换,会有「**亚像素抖动**」问题——后面 Day 109 会用双线性插值解决。

**scale 传播的两种方式**。一种是在 `submit` 时统一乘——Casey 今天用的,代码集中。另一种是 push 时就乘好,把 scale「**烧**」到每条命令里——这是 Day 109 分辨率无关渲染的预计算方式,可以省 submit 时的乘法。两种都对,看 trade-off:统一乘好维护、烧进命令好性能。Casey 选了统一乘因为 Day 106 还没到性能瓶颈。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏业界对「世界单位」有几种主流约定,你看到别人项目时不会陌生。

- **Unity**:`1 unit = 1 meter`。所有 transform.position 用 Vector3,单位是米。物理引擎(Gravity = -9.8 m/s²)默认假设米。
- **Unreal Engine**:`1 unit = 1 centimeter`。100 uu = 1 m。Unreal 的物理参数都是 cm/s²。
- **Godot**:`1 unit = 1 pixel`(2D 默认)/ 任意(3D)。灵活但容易踩坑。
- **Casey HH**:`1 unit ≈ 任意`,Casey 这集定义 1 米 = 几像素,但「米」和「世界单位」是同义词。

约定不一致是跨引擎迁移最痛的事。把 Unreal 模型导入 Unity,数字大小差 100 倍——必须知道来源引擎的约定。

游戏设计中 `world_scale` 的常见应用还有:**相机缩放(zoom)**——鼠标滚轮改 scale 实现战略游戏拉远/拉近;**屏幕震动(screen shake)**——攻击时短暂把 scale 放大 1.05 倍再恢复;**UI 不参与 scale**——按钮永远 24 像素高,不跟 world_scale 变。

### 3.2 · 🎨 图形学视角

图形学把 `world_scale` 这个变换称为「**投影矩阵的 m00/m11 元素**」。完整 2D 投影矩阵:

```
P = | scale_x   0      0   |
    |   0     scale_y  0   |
    |   0       0      1   |
```

如果 `scale_x = scale_y = world_scale`,就是均匀缩放;不均匀(`scale_x ≠ scale_y`)就会产生「**拉伸畸变**」——4:3 的世界画到 16:9 屏幕上,圆形变椭圆。Casey HH 今天用均匀缩放避免这个问题。Day 108 的 3D 透视投影矩阵是非均匀的(因为透视本身就是非均匀变换),但今天还不到那一步。

`world_scale` 的倒数是「**视野(field of view)**」相关概念。`world_scale = 54` 像素/米意味着「屏幕 1080 像素能显示 1080/54 = 20 米宽」——这 20 米就是相机的水平视野(以世界单位计)。玩家看到的世界范围 = `screen_pixels / world_scale`。

### 3.3 · 🐧 Linux 系统编程视角

Linux 桌面环境的 HiDPI 处理是「世界缩放」最直接的对应。Wayland 协议里有 `wl_output.scale` 这个整数(1 或 2 或 3),compositor 把它告诉 client;client 渲染时用 logical pixel × scale 得到 physical pixel。`world_scale` = 2 的 Retina 屏本质和 Casey 的 `world_scale = 54` 像素/米是同一种抽象——「**逻辑单位到物理单位的转换因子**」。

Linux 工具链里有几个相关命令你要熟悉:

- `xrandr --dpi 96` 设置逻辑 DPI。
- `gsettings set org.gnome.desktop.interface scaling-factor 2` 设置 GNOME scale。
- 环境变量 `GDK_SCALE=2` 让 GTK 应用整体放大 2 倍(影响所有 widget 大小)。

这些都是「**全局 world_scale**」的实例。Casey 在游戏里把 scale 放进 Renderer,而 Linux 桌面把 scale 放进 compositor——抽象层级不同,本质一样。

### 3.4 · 🦀 Rust 生态视角

Rust 里写「**带单位的浮点数**」有几种 idiomatic 做法。最简单的是 `typealias` + 文档:

```rust
/// 世界单位(米)
type Meters = f32;

/// 屏幕像素
type Pixels = f32;

fn world_to_screen(d: Meters, scale: f32) -> Pixels {
    d * scale
}
```

更严谨的是用 ` uom ` crate(单位制检查),编译期保证不会把 Meters 当 Pixels 用:

```rust
use uom::si::f32::Length;
use uom::si::length::meter;

let player_height: Length = Length::new::<meter>(2.0);  // 编译器知道这是米
// player_height * 2.0  // 还是 Length
// player_height + 5.0  // 编译错!Length + f32 不允许
```

`uom` 在科学计算里很有用,游戏开发里**很少用**——overhead 太重(运行时也带类型 tag)。Casey HH 选择「注释 + 约定」的轻量做法,是务实派。

另一个 Rust 现代特性是 `f32::mul_add`:

```rust
// 普通:
let screen = world * scale + offset;
// mul_add(FMA 指令):
let screen = world.mul_add(scale, offset);
```

`mul_add` 编译成单条 CPU 指令(Fused Multiply-Add),只在支持 FMA 的 CPU(x86 with AVX2、ARM NEON)上更快,精度也更高(只舍入一次)。游戏渲染 hot loop 里这种细节会累积成可观性能差。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Coordinate Spaces(坐标空间)** —— 世界空间 / 屏幕空间 / 局部空间是图形学三大坐标空间,`world_scale` 是它们之间的变换。
- **Separation of Concerns(关注点分离)** —— 游戏逻辑(世界单位)和渲染(屏幕像素)是两个关注点,scale 把它们分开。
- **MVP Transform** —— Model-View-Projection 变换链,scale 是 Projection 矩阵的一部分。

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| **标量 `world_scale`** | 单 f32,均匀缩放 | 2D 游戏,无旋转 | ✅ Day 106 |
| **2×2 scale matrix** | 可非均匀缩放(x/y 不同) | 2D 各向异性渲染 | 不用 |
| **完整 4×4 MVP** | 含旋转/平移/透视 | 3D 游戏 | Day 108+ |
| **每物体独立 scale** | entity 自带 scale 字段 | 怪物变大变小特效 | Day 105 已有 entity.scale |

表中关键 takeaway:**抽象层级的复杂度应该匹配需求**。Day 106 还在 2D,用标量 scale 就够;硬上 4×4 矩阵是过度设计,徒增复杂度。Day 108 进入 3D 时再升级到矩阵,这是「**让抽象跟着需求走**」的工程智慧。

### 4.3 下级(内部零件)

- **`Renderer.world_scale: f32`** —— 标量字段,submit 时乘。
- **`Camera.x / y: f32`** —— 相机平移(世界单位),先减 camera 再乘 scale。
- **`entity.scale: f32`** —— 物体独立缩放,先乘 entity scale 再乘 world scale。
- **`meters_to_pixels`** —— Casey 用的同义词,意义完全一样。

## 5 · 对照与变奏

**统一 scale vs 每物体独立 scale**。Casey 给 Renderer 加一个 `world_scale`,但每个 entity 还有自己的 `scale` 字段(用于「怪物被变大魔法影响时整体放大」)。两者关系是乘积:`final_scale = world_scale × entity.scale`。如果只有 `world_scale`,做不出「**单个怪物变大**」效果;如果只有 `entity.scale`,改窗口大小时所有 entity 都要重设。两者分工不同,缺一不可。

**整数 scale vs 浮点 scale**。复古像素游戏偏爱整数 scale(1×, 2×, 3×)——避免像素被插值糊掉。现代高清游戏用任意浮点 scale,搭配双线性/三线性插值。Casey HH 是混合派:整数 scale 主导,需要时(旋转 sprite)用浮点 + 双线性。

**HiDPI scale vs world_scale**。HiDPI scale 是「物理像素 / 逻辑像素」,world_scale 是「物理像素 / 世界米」。两个 scale 是相乘关系:`物理像素 = 世界米 × world_scale × hidpi_scale`。Rust winit + softbuffer 路径会自动应用 hidpi_scale,所以 Casey 在游戏里只关心 world_scale。

**历史演化**。1980 年代家用电脑(Spectrum、C64)没有 scale 概念——「世界单位 = 像素」,因为屏幕分辨率固定。1990 年代 VGA 出现多分辨率,scale 概念开始流行。2000 年代 3D 加速,scale 进入投影矩阵。2010 年代 Retina/HiDPI,scale 多了一层。每次分辨率革命都让 scale 抽象更复杂,但核心公式 `物理像素 = 世界单位 × scale` 没变。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:Casey 在 Renderer 里把 `world_scale` 设为 `54.0`,游戏里玩家身高定义为 `2.0`。请回答:(a) 玩家在 1080p 屏幕上是多少像素高?(b) 如果换成 4K(2160p)显示器,玩家应该看起来多大?是否需要改 `world_scale`?(c) 如果设计师觉得玩家太小,想让玩家看起来大 1.5 倍,有两种做法——改 `PLAYER_HEIGHT_M` 或改 `world_scale`,哪种更好?为什么?

**参考解答**:(a) `2.0 × 54 = 108` 像素高。(b) 4K 显示器**应该让玩家看起来一样大**(相同物理尺寸),但屏幕像素更多,所以应该把 `world_scale` 调大(2160/1080 × 54 = 108)。或者保持 `world_scale` 不变,让玩家在屏幕上占更小比例(108/2160 = 5% 而不是 108/1080 = 10%)——这取决于设计师是想「**视野更广**」还是「**物体更大**」。Casey 一般选视野更广(看清周围更多),所以会调大 scale。(c) **改 `world_scale` 更好**——一个变量控制「整体视觉比例」,所有物体(玩家、怪物、墙)一起放大。如果改 `PLAYER_HEIGHT_M`,只有玩家变大,怪物不变,看起来比例失调(玩家比门还高)。这就是为什么「视觉全局调整」要放在 Renderer,「游戏逻辑调整」才动 entity 数据。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:基于 Day 105 的 Renderer 代码,加 `world_scale: f32` 字段。在 `submit` 里,`Rect` 命令的 `(x, y, w, h)` 都乘以 `world_scale`。再加一个滚轮回调函数 `on_wheel(delta: f32)`,滚轮上滑把 `world_scale *= 1.1`,下滑 `world_scale /= 1.1`(clamp 在 10..500)。画一个网格:每米一条线,网格大小 50×50 米。运行后滚轮可以放大缩小网格。

**参考解答**:

```rust
pub struct Renderer {
    // ... 其他字段
    pub world_scale: f32,
    pub camera_x: f32,
    pub camera_y: f32,
}

impl Renderer {
    pub fn on_wheel(&mut self, delta: f32) {
        // 滚轮上滑 delta > 0,放大
        let factor = 1.1_f32.powf(delta.signum());
        self.world_scale = (self.world_scale * factor).clamp(10.0, 500.0);
    }

    pub fn push_grid(&mut self, world_w: usize, world_h: usize) {
        // 横线
        for y in 0..=world_h {
            self.push_rect(0.0, y as f32, world_w as f32, 0.02,
                           [0.3, 0.3, 0.3, 1.0]);
        }
        // 竖线
        for x in 0..=world_w {
            self.push_rect(x as f32, 0.0, 0.02, world_h as f32,
                           [0.3, 0.3, 0.3, 1.0]);
        }
    }

    pub fn submit(&mut self) {
        let cmds: Vec<_> = std::mem::take(&mut self.commands);
        let s = self.world_scale;
        for cmd in cmds {
            match cmd {
                Command::Rect { x, y, w, h, color } => {
                    let argb = pack_argb(color);
                    // 关键变换:世界 → 屏幕
                    let sx = ((x - self.camera_x) * s) as i32;
                    let sy = ((y - self.camera_y) * s) as i32;
                    let sw = (w * s).max(1.0) as i32;
                    let sh = (h * s).max(1.0) as i32;
                    // ... 写 framebuffer,边界检查省略
                    for ry in sy..sy + sh {
                        if ry < 0 || ry as u32 >= self.height { continue; }
                        for rx in sx..sx + sw {
                            if rx < 0 || rx as u32 >= self.width { continue; }
                            self.framebuffer[(ry as u32 * self.width + rx as u32) as usize] = argb;
                        }
                    }
                }
                _ => {}
            }
        }
    }
}

fn main() {
    let mut r = Renderer::new(800, 600);
    r.world_scale = 20.0;            // 1 米 = 20 像素,40 米铺满 800 像素宽
    r.push_clear([0.1, 0.1, 0.15, 1.0]);
    r.push_grid(40, 30);             // 40×30 米网格
    r.submit();
    // 存 PNG 看效果……
}
```

注意 `sw = (w * s).max(1.0) as i32`——网格线宽 0.02 米 × scale 20 = 0.4 像素,小于 1 会被舍入成 0,看不见。`.max(1.0)` 保证最小 1 像素,这是「**亚像素几何**」的标准处理。

### Lv3 · 迁移设计(换场景用同一原理)

**提示**:PDF 的单位系统更复杂(有 user space、device space、CTM 变换),你只需做「点 → 像素」的最简版。考虑「**缩放中心**」——用户在 (400, 300) 像素位置滚轮,该位置的世界坐标在缩放后应该仍在 (400, 300),否则会跳。这需要 `camera_x/y` 配合 `scale` 一起调整,公式:`new_camera = world_pos_at_cursor - cursor_pos / new_scale`。

## 8 · Rust / Arch 落地代码

完整可跑的 world_scale 演示。在前一天 Day 105 的 Renderer 基础上加 scale。

```rust
// Cargo.toml:
// [dependencies]
// image = "0.25"
// bytemuck = { version = "1", features = ["extern_crate_alloc"] }

#[derive(Debug, Clone, Copy)]
pub struct Rect { pub x: f32, pub y: f32, pub w: f32, pub h: f32 }

pub enum Command {
    Clear { color: [f32; 4] },
    Rect { dst: Rect, color: [f32; 4] },
}

pub struct Renderer {
    pub width: u32,
    pub height: u32,
    pub framebuffer: Vec<u32>,
    pub commands: Vec<Command>,
    pub world_scale: f32,           // 新增:1 世界单位 = 多少屏幕像素
    pub camera_x: f32,              // 相机位置(世界单位)
    pub camera_y: f32,
}

impl Renderer {
    pub fn new(w: u32, h: u32) -> Self {
        Self {
            width: w, height: h,
            framebuffer: vec![0xFF101018; (w * h) as usize],
            commands: Vec::with_capacity(2048),
            world_scale: 32.0,        // 默认 1 米 = 32 像素
            camera_x: 0.0,
            camera_y: 0.0,
        }
    }

    pub fn push_clear(&mut self, c: [f32; 4]) {
        self.commands.push(Command::Clear { color: c });
    }
    pub fn push_rect(&mut self, dst: Rect, c: [f32; 4]) {
        self.commands.push(Command::Rect { dst, color: c });
    }

    // 关键:把世界矩形转成屏幕矩形
    fn world_to_screen(&self, r: Rect) -> (i32, i32, i32, i32) {
        let s = self.world_scale;
        let sx = ((r.x - self.camera_x) * s) as i32;
        let sy = ((r.y - self.camera_y) * s) as i32;
        let sw = (r.w * s).max(1.0) as i32;
        let sh = (r.h * s).max(1.0) as i32;
        (sx, sy, sw, sh)
    }

    pub fn submit(&mut self) {
        let cmds: Vec<_> = std::mem::take(&mut self.commands);
        for cmd in cmds {
            match cmd {
                Command::Clear { color } => {
                    let argb = pack_argb(color);
                    for px in &mut self.framebuffer { *px = argb; }
                }
                Command::Rect { dst, color } => {
                    let argb = pack_argb(color);
                    let (sx, sy, sw, sh) = self.world_to_screen(dst);
                    for ry in sy.max(0)..(sy + sh).min(self.height as i32) {
                        for rx in sx.max(0)..(sx + sw).min(self.width as i32) {
                            self.framebuffer[(ry as u32 * self.width + rx as u32) as usize] = argb;
                        }
                    }
                }
            }
        }
    }
}

fn pack_argb(c: [f32; 4]) -> u32 {
    let to_u = |v: f32| (v.clamp(0.0, 1.0) * 255.0) as u32;
    (to_u(c[3]) << 24) | (to_u(c[0]) << 16) | (to_u(c[1]) << 8) | to_u(c[2])
}

fn main() {
    let mut r = Renderer::new(800, 600);

    // 画 4 个不同尺寸的方块,验证 scale 传播
    r.push_clear([0.05, 0.05, 0.08, 1.0]);           // 暗背景
    r.push_rect(Rect { x: 1.0, y: 1.0, w: 2.0, h: 2.0 }, [0.8, 0.2, 0.2, 1.0]); // 2 米方块
    r.push_rect(Rect { x: 5.0, y: 1.0, w: 4.0, h: 2.0 }, [0.2, 0.8, 0.2, 1.0]); // 4×2 米
    r.push_rect(Rect { x: 1.0, y: 5.0, w: 1.0, h: 1.0 }, [0.2, 0.2, 0.8, 1.0]); // 1×1 米
    r.submit();

    let bytes: Vec<u8> = r.framebuffer.iter().flat_map(|p| p.to_le_bytes()).collect();
    let img: image::ImageBuffer<image::Rgba<u8>, _> =
        image::ImageBuffer::from_raw(r.width, r.height, bytes).unwrap();
    img.save("day106_scale32.png").unwrap();

    // 把 scale 改成 64,验证缩放效果
    r.world_scale = 64.0;
    r.push_clear([0.05, 0.05, 0.08, 1.0]);
    r.push_rect(Rect { x: 1.0, y: 1.0, w: 2.0, h: 2.0 }, [0.8, 0.2, 0.2, 1.0]);
    r.push_rect(Rect { x: 5.0, y: 1.0, w: 4.0, h: 2.0 }, [0.2, 0.8, 0.2, 1.0]);
    r.push_rect(Rect { x: 1.0, y: 5.0, w: 1.0, h: 1.0 }, [0.2, 0.2, 0.8, 1.0]);
    r.submit();
    let bytes: Vec<u8> = r.framebuffer.iter().flat_map(|p| p.to_le_bytes()).collect();
    let img: image::ImageBuffer<image::Rgba<u8>, _> =
        image::ImageBuffer::from_raw(r.width, r.height, bytes).unwrap();
    img.save("day106_scale64.png").unwrap();

    println!("对比两张图:scale=32 时方块小,scale=64 时方块大 2 倍");
}
```

预期:运行后生成 `day106_scale32.png` 和 `day106_scale64.png`。两张图里方块位置不变(世界坐标一样),但 scale=64 的方块大小是 scale=32 的 2 倍。

```bash
ls -lh day106_scale*.png

compare day106_scale32.png day106_scale64.png day106_diff.png
# diff 图里白色部分是差异(方块边界)

# 用 ffprobe / imagemagick 查 PNG 元数据
identify day106_scale32.png
# 输出: day106_scale32.png PNG 800x600 800x600+0+0 8-bit sRGB ...
```

**出错怎么办(troubleshooting)**:

- **方块超出屏幕** —— `world_to_screen` 的边界检查没做对。`ry.max(0)..(sy + sh).min(height as i32)` 保证不越界。
- **scale=0 时除零崩溃** —— 检查 `world_scale > 0.0` 或 `.clamp(0.01, ...)`。Casey 这集默认不为 0,但你做滚轮交互时要 clamp。
- **像素抖动** —— 浮点 → 整数转换时,小数部分被舍掉。比如 `2.5 像素` 变 2,看起来抖。解决:Day 109 的双线性插值,或 round 而非 trunc。
- **camera 中心不在屏幕中央** —— Casey 默认 camera 是「屏幕左下角对应世界 (camera_x, camera_y)」。如果你想 camera 是「屏幕中心看世界 (camera_x, camera_y)」,公式改为 `sx = (x - camera_x) * s + width/2`。
