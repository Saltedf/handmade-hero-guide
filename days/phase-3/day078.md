
# Day 078 · 每个实体多个碰撞体

> 你 Phase 2 写的玩家是一个 AABB——一个矩形碰撞体。但游戏里的 Boss 不是矩形——它有头、身、尾、翅膀,每部分都不一样。头被攻击伤害 ×2(弱点),尾被攻击减伤(护甲),身体正常。Casey 今天给你的 entity 加上**多个碰撞体积**,每个 part 独立判定。这让 Boss 战、复杂角色、精细碰撞成为可能。

## 0 · 为什么要有这一天

让我们把镜头拉到一个具体的开发场景里,你会立刻感受到「单一 AABB」的天花板。

你 Phase 2 的玩家是一个 AABB——一个矩形碰撞体。玩家撞墙、撞怪、撞道具,都用这个矩形。简单优雅,跑 60 帧毫无压力。但你的游戏现在长大了——你想加一只 **Boss 巨龙**。这只龙的形象是这样的:它有**头部**(玩家攻击头部 ×2 伤害,这是它的弱点)、**长颈**(攻击正常)、**宽阔的胸膛**(攻击正常)、**两只展开的翅膀**(翅膀有骨甲,攻击伤害减半)、**甩动的尾巴**(被尾巴打中,玩家被击退 5 米)。

你坐下来开始写代码。第一行:
```rust
struct Dragon { pos: Vec3, half: Vec3 }
```
**写完你愣住了**。龙的 `half` 是多少?头部小、胸膛大、尾巴细长——**一个矩形包不住这只龙**。如果你硬给龙一个巨大的 AABB(包住所有部位),玩家攻击翅膀也按弱点算(因为撞到了整个 AABB)。如果你给龙一个小 AABB(只包头部),玩家从尾巴侧接近根本撞不上。

**问题的本质是**:**单一形状表达不出「部位」**。Boss 战、关节攻击、爆头击杀——这些游戏体验都依赖于「同一个角色的不同部位有不同行为」。一个 AABB 是数学上的简化,无法承载这种丰富性。

工业界的标准答案叫 **multi-volume collision**(多体积碰撞):**一个 entity 配一组碰撞体积**,每个体积独立判定 + 带类型标签。头部体积标 `WeakPoint`、翅膀体积标 `Armor`、尾巴体积标 `Knockback`。攻击系统撞到哪个 volume,按那个 volume 的标签决定伤害和效果。

这个抽象一旦建好,你立刻能做:
- **FPS 爆头**:玩家 character 有头、身、腿三个 volume,头部中弹伤害 ×5(CS、Valorant、Apex 的标配)
- **Monster Hunter 斩尾**:龙的尾巴是一个独立 volume,被砍到一定伤害后断尾(尾巴 volume 从列表里移除)
- **Dark Souls 弹反**:敌人的盾是一个 volume,玩家在精确时机攻击盾,触发弹反动画
- **塞尔达 Boss 弱点**:Boss 的发光眼睛是 `WeakPoint` volume,被攻击 ×5 伤害 + 眩晕 3 秒
- **克苏鲁触手怪**:多臂怪每只触手一个 volume,各自独立攻击玩家
- **载具系统**:坦克有车身(volume)、炮塔(volume)、履带(volume),履带受伤后移动速度减半

**心理锚点**:学完今天,你应该能:
- 用 Rust 写一个有 N 个独立 volume 的 entity,每个 volume 有自己的位置、尺寸、类型
- 在攻击系统里,根据撞到的 volume 类型计算不同伤害(weakpoint ×2、armor ×0.5)
- 解释「单一 AABB vs 多 AABB」的性能取舍,知道何时该用哪种
- 用「broad phase + narrow phase」两阶段策略,在大规模 entity 场景下保持性能
- 看懂 Monster Hunter、Dark Souls、CS 等游戏的部位伤害系统是怎么实现的

这是从「能写撞墙的小游戏」到「能做严肃 Boss 战」的关键一步。

## 1 · Casey 今天做了什么

Casey 今天做的事情:

1. **Entity 加 volumes 字段**:`Vec<Volume>` 而不是单个 `half: Vec3`。
2. **Volume 结构**:`{ offset: Vec3, half: Vec3, type: VolumeType }`——每个 part 有偏移、尺寸、类型。
3. **VolumeType enum**:`Body`(正常)、`WeakPoint`(弱点,被攻击 ×2)、`Armor`(护甲,被攻击 ×0.5)等。
4. **碰撞测试升级**:两层循环——entity 之间遍历,内部 volume 之间遍历。
5. **简化决策**:大多数 entity 仍用单个 volume(性能),只有 Boss 等复杂 entity 用多 volume。

Casey 强调「按需复杂化」——不要一开始就给所有 entity 多 volume,90% 的 entity 一个 volume 就够,只在需要时升级。

## 2 · 心智模型

### 2.1 费曼类比:人体解剖

人不是「一个矩形」——人有头、脖子、躯干、四肢。每部分功能不同:头被攻击致命,躯干中等,手脚轻伤。医生看病、武术家攻击、运动锻炼——都基于「人的不同部位有不同特性」。

游戏里的 Boss 也是这样。一个 AABB 表达「整体范围」,但具体判定要看部位。多 volume 就是给 Boss 加上「解剖学」——每个部位有自己的体积和属性。

让我们把类比推得更远。**武术里的「穴位」**就是 multi-volume 的极端版本——人体有上百个穴位,每个穴位被点中产生不同效果(麻木、晕厥、剧痛)。医生 / 武术家在脑海中有一个「人体部位表」,每个部位对应不同动作。Boss 战里玩家做的事一样:看到 Boss 头上闪红光(weakpoint 信号),立刻知道「攻击头部 ×2」。这就是 multi-volume 的体验本质——**让玩家学会读 Boss 的「身体地图」,把攻击打到正确的部位**。

### 2.2 严谨原理:从单 AABB 到多 volume

先回顾单 AABB 怎么做碰撞。Phase 2 你写的玩家是:
```rust
struct Player { pos: Vec3, half: Vec3 }
// 碰撞测试:两个 AABB 是否重叠
fn aabb_overlap(a: &Player, b: &Player) -> bool {
    let d = a.pos.sub(b.pos).abs();
    d.x < a.half.x + b.half.x &&
    d.y < a.half.y + b.half.y &&
    d.z < a.half.z + b.half.z
}
```
这里 `pos` 是 AABB 的**中心**,`half` 是**半尺寸**(half-extent)。两个 AABB 重叠的充要条件是:在 x、y、z **每个轴**上,中心距离都小于半尺寸之和。这是分离轴定理(SAT)在 AABB-AABB 情况下的特例。

**从单到多:多 volume 的第一步**。我们要让一个 entity 拥有多个 AABB。最直接的扩展是给 entity 加一个 `Vec<AABB>`:
```rust
struct Entity {
    pos: Vec3,
    volumes: Vec<AABB>,  // 多个 part
}
struct AABB {
    offset: Vec3,  // 相对 entity.pos 的偏移
    half: Vec3,
}
```

**关键设计决策:offset 是相对的**。为什么不用绝对坐标?因为 entity 会移动。如果龙的头部 AABB 是绝对坐标 (100, 50, 240),龙移动到 (200, 50, 0),头部 AABB 还在 (100, 50, 240)——头部「漂」在原地。用相对 offset,头部 offset = (0, 0, 240),龙移动到 (200, 50, 0),头部世界坐标 = pos + offset = (200, 50, 240)——头部跟着身体走。

这是**「刚体变换」**的简化——刚体内每个点都按同一变换移动。游戏里所有 skeletal entity(骨骼角色)都是这种模型:骨骼定义相对偏移,角色移动时整体平移。

### 2.3 数据结构:Volume + VolumeType

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
enum VolumeType {
    Body,         // 普通,正常伤害
    WeakPoint,    // 弱点,伤害 ×2
    Armor,        // 护甲,被攻击 ×0.5
    Invulnerable, // 无敌(部分时候)
}

#[derive(Copy, Clone, Debug)]
struct Volume {
    offset: Vec3,  // 相对 entity pos 的偏移
    half: Vec3,    // 半尺寸
    vtype: VolumeType,
}

#[derive(Clone, Debug)]
struct Entity {
    pos: Vec3,
    height: f32,
    volumes: Vec<Volume>,  // 多个 part
}
```

每个 volume 的**实际中心** = `entity.pos + offset`。比如龙的头在 pos 上方 200,offset = (0, 0, 200)。

为什么 `VolumeType` 是 enum 而不是 int?因为 enum 让编译器帮你检查**穷尽性**——你 match 它的时候,漏掉一个 variant 编译器报错。如果用 int (0=body, 1=weak, 2=armor),你写 match 漏了 case 2,编译器没意见,运行时玩家撞到护甲不响应,你 debug 半天。

### 2.4 多 volume 的碰撞测试

```rust
fn entities_collide_volumes(a: &Entity, b: &Entity) -> Option<(usize, usize)> {
    for (i, va) in a.volumes.iter().enumerate() {
        let a_center = a.pos.add(va.offset);
        for (j, vb) in b.volumes.iter().enumerate() {
            let b_center = b.pos.add(vb.offset);
            if aabb3_overlap_at(a_center, va.half, b_center, vb.half) {
                return Some((i, j));  // 返回哪些 part 撞了
            }
        }
    }
    None
}
```

**返回值**:撞了哪两个 part 的索引(对调用者重要,因为不同 part 有不同伤害)。`Option<(usize, usize)>` 是 Rust 的表达——`Some((i, j))` 表示撞了 a 的第 i 个 volume 和 b 的第 j 个 volume,`None` 表示没撞。

注意这里**没有提前返回所有碰撞对**——只返回第一个。如果想处理多个 volume 同时撞(比如玩家同时撞到龙的头和颈),需要返回 `Vec<(usize, usize)>`。Casey HH 简化用单次返回,工业游戏引擎用 vector。

### 2.5 简化:大多数 entity 一个 volume

按需复杂化是 Casey 一贯的哲学。我们给 Entity 提供「简单构造」和「复杂构造」两个工厂方法:
```rust
impl Entity {
    fn new_simple(pos: Vec3, half: Vec3, height: f32) -> Self {
        Self {
            pos,
            height,
            volumes: vec![Volume {
                offset: Vec3::new(0., 0., height / 2.0),
                half,
                vtype: VolumeType::Body,
            }],
        }
    }

    fn new_dragon(pos: Vec3) -> Self {
        Self {
            pos,
            height: 256.,
            volumes: vec![
                Volume { offset: Vec3::new(0., 0., 240.), half: Vec3::new(32., 32., 16.),
                         vtype: VolumeType::WeakPoint },  // 头
                Volume { offset: Vec3::new(0., 0., 180.), half: Vec3::new(24., 24., 32.),
                         vtype: VolumeType::Body },         // 颈
                Volume { offset: Vec3::new(0., 0., 120.), half: Vec3::new(64., 32., 64.),
                         vtype: VolumeType::Body },         // 身
                Volume { offset: Vec3::new(80., 0., 140.), half: Vec3::new(48., 16., 32.),
                         vtype: VolumeType::Armor },        // 右翼
                Volume { offset: Vec3::new(-80., 0., 140.), half: Vec3::new(48., 16., 32.),
                         vtype: VolumeType::Armor },        // 左翼
                Volume { offset: Vec3::new(0., 80., 80.), half: Vec3::new(16., 48., 16.),
                         vtype: VolumeType::Body },         // 尾
            ],
        }
    }
}
```
普通怪用 `new_simple`,内部还是 `Vec<Volume>`(长度 1)。Boss 用 `new_dragon`,Vec 长度 6。**统一的存储格式**让碰撞代码只有一套——不用 if 分支判断「这是单 volume 还是多 volume」。

### 2.6 攻击伤害计算

```rust
fn apply_attack(
    attacker: &Entity,
    target: &Entity,
    target_volume_idx: usize,
    base_damage: f32,
) -> f32 {
    let vol = &target.volumes[target_volume_idx];
    let damage = match vol.vtype {
        VolumeType::Body => base_damage,
        VolumeType::WeakPoint => base_damage * 2.0,
        VolumeType::Armor => base_damage * 0.5,
        VolumeType::Invulnerable => 0.0,
    };
    damage
}
```

玩家攻击时,先做碰撞测试,得到撞了哪个 part,再根据 part type 算伤害。

注意这个 `match` 是**穷尽**的——你将来加一个新 variant(比如 `VolumeType::Reflective` 反弹伤害给攻击者),编译器会在所有 match 站点报错,提醒你补上处理。这是 enum 的工程价值。

### 2.7 性能考量:broad phase + narrow phase

N 个 entity,每个有 M 个 volume,复杂度是 O((NM)²)——平方爆炸。一个 entity 5 个 volume,4 个 entity 互相判定就是 4² × 5² = 400 次 AABB 测试。100 个 Boss 互撞就是 100² × 5² = 250000 次——单帧就要 25 万次 AABB 测试,虽然每次很快但累加起来影响 frame budget。

Casey 的优化:**先用 entity 级 AABB 粗筛**——如果两个 entity 的整体 AABB 不重叠,跳过 volume 级测试。

```rust
fn entities_collide(a: &Entity, b: &Entity) -> Option<(usize, usize)> {
    // 1. 粗筛:entity 整体 AABB
    let a_bounds = entity_overall_aabb(a);
    let b_bounds = entity_overall_aabb(b);
    if !aabb3_overlap(a_bounds, b_bounds) {
        return None;
    }
    // 2. 精筛:volume 级
    entities_collide_volumes(a, b)
}

fn entity_overall_aabb(e: &Entity) -> AABB3 {
    // 包围所有 volume 的最小 AABB
    let mut min = Vec3::new(f32::INFINITY, f32::INFINITY, f32::INFINITY);
    let mut max = Vec3::new(f32::NEG_INFINITY, f32::NEG_INFINITY, f32::NEG_INFINITY);
    for v in &e.volumes {
        let c = e.pos.add(v.offset);
        min.x = min.x.min(c.x - v.half.x);
        // ... 类似
    }
    AABB3 {
        center: min.add(max).mul(0.5),
        half: max.sub(min).mul(0.5),
    }
}
```

这种「粗筛 + 精筛」是工业碰撞检测的标配——**Broad Phase**(粗)+ **Narrow Phase**(精)。

Broad Phase 的核心思想:**绝大多数 entity 对根本不会碰**。1000 个 entity 中,玩家周围 5 米内可能只有 3 个 entity。其他 997 个 entity 根本不需要做 volume 级测试。Broad Phase 用便宜的算法(网格、四叉树、BVH、Sweep and Prune)快速排除 99% 的对,剩下的对才进入 Narrow Phase。

游戏引擎里常见 Broad Phase 算法:
- **Uniform Grid**(均匀网格):把世界切成 grid,每个 entity 注册到自己的 cell。只检查同 cell 和邻居 cell 的 entity。Minecraft、Terraria 用这种。
- **Quadtree / Octree**:层次网格,稀疏世界高效。但增删 entity 开销大。
- **BVH**(Bounding Volume Hierarchy):树形包围盒,射线追踪和物理引擎标配。Bullet Physics、PhysX 都用 BVH。
- **Sweep and Prune**:把所有 AABB 投影到 3 个轴,排序后只检查重叠区间。Box2D 用这种。

Casey HH 用最简单的「entity 整体 AABB 粗筛」——单 entity 只有一个 AABB,虽然比 grid / BVH 简单,但对小规模游戏够用。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

多 volume 在游戏里到处都是,而且每个游戏都有自己的术语和约定。让我把工业界常见的几种用法拆开讲。

**FPS 爆头系统**:CS / Valorant / Apex 的角色有 3 个 hurtbox——头、身、腿。子弹击中头部时,伤害乘数 4×(CS)或 2×(Apex)。这要求角色模型有 3 个独立的 hitbox,且 hitbox 跟随动画移动。比如玩家蹲下时,头部 hitbox 降低;玩家侧身时,身体 hitbox 倾斜。这种动态 hitbox 是格斗 / FPS 游戏的难点——动画和碰撞必须严格同步。

**Monster Hunter 部位破坏**:每只大型怪物有 10+ 部位。尾巴是一个部位,有独立 HP。玩家用斩击武器(太刀、大剑)攻击尾巴,累计伤害超过阈值后尾巴**物理断开**——尾巴 hitbox 从怪物的 hitbox 列表里移除,同时播放断尾动画,玩家可以捡起断尾获得素材。头部也是部位,被打击武器(锤)累计伤害后,头部肉质变软(更易受伤)。这是 multi-volume + 累计伤害 + 状态变更的综合应用。

**Dark Souls 弹反**:敌人的盾是一个 hurtbox(受玩家攻击判定)。玩家在精确时机(敌人攻击动画的特定帧)攻击盾,触发弹反——敌人失衡,玩家可处决。这要求盾 hitbox 在动画的某些帧是「可弹反」状态,其他帧不是。Multi-volume 的 vtype 字段可以扩展为「按动画帧变化」。

**塞尔达 Boss 弱点**:Boss 的眼睛通常是 WeakPoint volume,被弓箭击中 ×3 伤害 + Boss 眩晕 3 秒。眩晕期间 Boss 头部体积变化(低下头),玩家可以近战攻击。

#### Hitbox / Hurtbox 抽象

格斗游戏社区发展出更精细的术语:
- **Hurtbox**:entity 的身体,被攻击会受伤。每帧动画可能有不同的 hurtbox 布局(站立、跳、蹲)。
- **Hitbox**:攻击的范围,主动伤害别人。每个攻击动画帧有特定 hitbox。比如拳头的 hitbox 只在挥拳动画的 3 帧出现。
- **Clank box**:两个 hitbox 相撞,互相抵消(格斗游戏)。双方都进入「攻击失效」状态,可以重新出招。
- **Pushbox / Throwbox**:角色之间的物理推开范围(不让两个角色重叠)。

每个 animation frame,这些 box 都可能变化。Casey HH 简化用 volume_type,但工业格斗游戏更复杂——每个 volume 关联到骨骼节点,跟随骨骼动画。

#### 工业实现:Havok / PhysX / Box2D

商业物理引擎(Havok、PhysX、Box2D)的 collision shape 系统:
- 单 shape:球、胶囊、AABB、OBB、凸包、三角形 mesh、heightfield
- **Compound shape**:多个 shape 组合,带 transform(相对父节点)。这正是 multi-volume。
- Shape 带 material(friction、restitution)、filter mask(只跟特定 group 碰撞)

Compound shape 是 Havok / PhysX 标准功能,支持任意数量的 sub-shape,每个 sub-shape 独立碰撞 + material。Casey HH 自己手写这套,概念一致。

### 3.2 · 🎨 图形学视角

多 volume 在图形学里的应用远不止碰撞。

**Skinning / 骨骼动画**:3D 角色的 mesh 由骨骼驱动。每个 bone 关联一部分 mesh(称为「skin」)。骨骼动画 = bone 变换,自动驱动 mesh 变形。每个 bone 可以视作一个「volume」——骨骼的 transform 决定挂在它上面的 mesh 部分的位置。Multi-volume 碰撞是这套的简化版:每个 volume 关联一个「offset」,跟着 entity.pos 走;骨骼动画更进一步,每个 volume 还跟着骨骼旋转。

**碰撞 mesh**:3D mesh 本身就是碰撞体积,精确但慢。工业引擎用简化版——**凸包**(convex hull)是最常见的:把 mesh 简化为最小包围凸包,碰撞测试快很多但精度低。Boss 模型有 1 万三角形,凸包后只有 100 个面,碰撞测试快 100 倍。

**物理仿真**:布料、绳索、流体用「particle + spring」模型,每个 particle 是一个碰撞点。一条绳子可能有 50 个 particle,各自独立碰撞。这是 multi-volume 的极致——每个 particle 是一个 0 维 volume。

**射线追踪**:GPU 光追里,multi-volume 对应 BLAS(Bottom-Level Acceleration Structure)的几何体组。一个角色有多个 mesh(头、身、手),每个 mesh 在 BLAS 里独立追踪,但整体作为一个对象变换。

#### 法线贴图 vs 多 volume

法线贴图(Day 097)让一个平面**看起来**凹凸不平,但**碰撞仍然是平面**(单 volume)。多 volume 是真的不同碰撞体,法线贴图是视觉欺骗。两者结合:大多数 entity 用法线贴图(便宜),Boss 用多 volume(贵但精确)。这是性能与精度的权衡——美术想要「视觉 = 碰撞」,工程师要平衡预算。

### 3.3 · 🐧 Linux 系统编程视角

跟 Linux 没直接关系。但「**树形层次包围**」是 Linux 文件系统的核心:

- **目录树**:每个目录包含文件和子目录。找文件时,先从根目录开始,逐层深入。本质是层次包围——`/usr/include/` 这个目录的「volume」是 `/usr/` 的子集。
- **/proc 文件系统**:每个进程一个目录,目录里有 fd/、maps、status 等子项。`/proc/1234/` 包含 PID 1234 的所有信息。
- **cgroup hierarchy**:进程组层次结构,每个组有资源限制。`/sys/fs/cgroup/cpu/myapp/` 包含 myapp 子组。

碰撞检测的「Broad Phase + Narrow Phase」类似——**先粗定位,再精细查**。

#### Linux 工具:空间索引

```bash
# locate 命令用 mlocate 数据库,先粗筛(文件名包含 X)再精筛
locate "*.rs" | grep handmade
# 等价 broad phase(locate 数据库)+ narrow phase(grep)

# find 是暴力,但支持多种过滤(粗筛 + 精筛)
find / -name "*.rs" -size +1k -newer /tmp/marker
# 等价 broad phase(name 过滤)+ narrow phase(size + newer)

# mlocate 数据库
ls -la /var/lib/mlocate/mlocate.db
# 这个数据库是文件系统的「索引」,类似 broad phase 的 grid

# updatedb 重建索引(类似 broad phase 重建)
sudo updatedb
```

Linux 文件系统的「inode + dentry + page cache」三层架构也是类似——dentry 是路径缓存(broad),inode 是文件元数据(narrow),page cache 是文件内容(精确)。每层缩小搜索范围。

### 3.4 · 🦀 Rust 生态视角

#### Rust 写多 volume 系统

```rust
#[derive(Copy, Clone, Debug)]
struct Volume {
    offset: Vec3,
    half: Vec3,
    vtype: VolumeType,
}

#[derive(Clone, Debug)]
struct Entity {
    pos: Vec3,
    height: f32,
    volumes: Vec<Volume>,
}

impl Entity {
    // 返回所有 volume 的世界 AABB
    fn volume_aabbs(&self) -> impl Iterator<Item = (usize, AABB3)> + '_ {
        self.volumes.iter().enumerate().map(move |(i, v)| {
            let center = self.pos.add(v.offset);
            (i, AABB3 { center, half: v.half })
        })
    }
}

// 暴力两两测试
fn collide_all(entities: &[Entity]) -> Vec<(usize, usize, usize, usize)> {
    let mut result = Vec::new();
    for i in 0..entities.len() {
        for j in (i+1)..entities.len() {
            for (vi, va) in entities[i].volume_aabbs() {
                for (vj, vb) in entities[j].volume_aabbs() {
                    if aabb3_overlap(va, vb) {
                        result.push((i, vi, j, vj));
                    }
                }
            }
        }
    }
    result
}
```

`impl Iterator + '_` 是 Rust 的**迭代器组合**——返回一个迭代器,生命周期绑定到 &self。`'_` 是匿名生命周期,表示「跟某个借用绑定」,具体由编译器推断。这是 Rust 表达「返回引用迭代器」的标准模式。

#### Rust 的 smallvec:避免堆分配

如果大多数 entity 只有 1-3 个 volume,用 `Vec<Volume>` 浪费(每次堆分配)。`Vec` 是堆分配的——堆分配要走 allocator(慢)、可能产生碎片、影响 cache locality。游戏主循环里零分配是工业原则。

用 `smallvec::SmallVec<[Volume; 4]>`——栈上 4 个,超出才堆:

```rust
use smallvec::SmallVec;
type VolumeList = SmallVec<[Volume; 4]>;

struct Entity {
    pos: Vec3,
    height: f32,
    volumes: VolumeList,  // 通常栈上,极少堆
}
```

SmallVec 在栈上预留 4 个 `Volume` 的空间(每个 36 字节,共 144 字节)。volumes.len() ≤ 4 时零堆分配,> 4 时 spill 到堆(行为同 Vec)。游戏里 90% 的 entity 只用栈上部分——零分配,cache 友好。

类似 crate:`arrayvec::ArrayVec`(完全不允许 spill)、`tinyvec::TinyVec`(no_std 友好)。

#### Rust 的 enum dispatch

如果想避免虚函数调用,用 enum dispatch:

```rust
enum Shape {
    Aabb(AABB3),
    Sphere(Sphere),
    // 加新形状只需加 variant
}

fn collide(a: &Shape, b: &Shape) -> bool {
    match (a, b) {
        (Shape::Aabb(a), Shape::Aabb(b)) => aabb3_overlap(*a, *b),
        (Shape::Sphere(a), Shape::Sphere(b)) => sphere_overlap(*a, *b),
        (Shape::Aabb(a), Shape::Sphere(s)) => aabb_sphere_overlap(*a, *s),
        (Shape::Sphere(s), Shape::Aabb(a)) => aabb_sphere_overlap(*a, *s),
    }
}
```

C++ 用虚函数 + dynamic_cast,Rust 用 enum + match。Rust 编译器保证穷尽性——你将来加 `Shape::Capsule`,所有 match 站点编译报错,提醒你补上 Capsule 的处理。这是 Rust 在工程化上比 C++ 强的地方之一。

工业物理引擎 `rapier3d`(Rust)就是 enum dispatch 重度用户。它的 `ColliderShape` 是 enum,variant 有 Ball、Cuboid、Capsule、ConvexHull、TriMesh、Heightfield 等,所有 collision 函数都是 match 穷尽。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 90% 的 entity 应该用单 volume,而不是统一用多 volume?

**参考解答**:性能 + 简洁 + 心智模型。

**性能**:多 volume 需要 Vec(堆分配),每个 entity 一个 Vec 是大开销。1000 个 entity × 平均 1 volume,单 volume 方案零额外开销,多 volume 方案 1000 次堆分配。每次堆分配约 50ns(malloc + bookkeeping),1000 次 = 50μs,60 FPS 帧预算 16.6ms,占用 0.3%。看起来不多,但累加其他系统后开始吃紧。如果用 SmallVec 栈上 4 个,90% 的 entity 零分配。

**简洁**:单 volume 代码简单——直接 aabb3_overlap,不用迭代。逻辑清晰,新人 5 秒读懂。多 volume 代码涉及两层循环 + 索引管理,新人需要 30 秒理解。

**心智模型**:单 volume 强制你把 entity 想成一个整体——玩家撞墙,等价于玩家整体撞墙。这跟「玩家是一个角色」的直觉一致。多 volume 让 entity 看起来像「一堆零件」,这对普通怪(就是个小球)过度抽象——你不需要把小怪拆成头身尾。

**Casey 的策略**:**默认单 volume,需要时升级**。一个 entity 一开始单 volume,后期发现需要多 part(比如 Boss 战),才改成多 volume。**按需复杂化**是工程的核心思想。类似 Casey 不一开始就 ECS,而是从 hardcoded struct 起步,后期才抽象。

这个策略的工业版叫 **YAGNI**(You Aren't Gonna Need It)——不要过早抽象。早期代码简单,后期需求变化时再抽象。如果一开始就上 multi-volume,你会为「单一怪」过度付出性能 + 复杂度代价。

#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn add(self, o: Self) -> Self { Self::new(self.x+o.x, self.y+o.y, self.z+o.z) }
}

#[derive(Copy, Clone, Debug)]
enum VT { Body, WeakPoint, Armor }

#[derive(Copy, Clone, Debug)]
struct Volume { offset: Vec3, half: Vec3, vtype: VT }

fn dragon() -> Vec<Volume> {
    vec![
        Volume { offset: Vec3::new(0., 0., 240.), half: Vec3::new(32., 32., 16.), vtype: VT::WeakPoint },
        Volume { offset: Vec3::new(0., 0., 180.), half: Vec3::new(24., 24., 32.), vtype: VT::Body },
        Volume { offset: Vec3::new(0., 0., 120.), half: Vec3::new(64., 32., 64.), vtype: VT::Body },
        Volume { offset: Vec3::new(80., 0., 140.), half: Vec3::new(48., 16., 32.), vtype: VT::Armor },
        Volume { offset: Vec3::new(-80., 0., 140.), half: Vec3::new(48., 16., 32.), vtype: VT::Armor },
        Volume { offset: Vec3::new(0., 80., 80.), half: Vec3::new(16., 48., 16.), vtype: VT::Body },
    ]
}

fn aabb_overlap_at(ac: Vec3, ah: Vec3, bc: Vec3, bh: Vec3) -> bool {
    let d = ac.add(Vec3::new(-bc.x, -bc.y, -bc.z));
    d.x.abs() < ah.x + bh.x && d.y.abs() < ah.y + bh.y && d.z.abs() < ah.z + bh.z
}

fn main() {
    let dragon_pos = Vec3::new(0., 0., 0.);
    let dragon_volumes = dragon();

    // 玩家攻击位置
    let attack_pos = Vec3::new(0., 0., 250.);
    let attack_half = Vec3::new(8., 8., 8.);

    let base_damage = 10.0;

    for (i, v) in dragon_volumes.iter().enumerate() {
        let vol_center = dragon_pos.add(v.offset);
        if aabb_overlap_at(attack_pos, attack_half, vol_center, v.half) {
            let dmg = match v.vtype {
                VT::Body => base_damage,
                VT::WeakPoint => base_damage * 2.0,
                VT::Armor => base_damage * 0.5,
            };
            println!("击中 part {}: {:?},伤害 = {:.1}", i, v.vtype, dmg);
        }
    }
}

## 8 · Rust / Arch 落地代码

```rust
#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn add(self, o: Self) -> Self { Self::new(self.x+o.x, self.y+o.y, self.z+o.z) }
    fn sub(self, o: Self) -> Self { Self::new(self.x-o.x, self.y-o.y, self.z-o.z) }
    fn abs(self) -> Self { Self::new(self.x.abs(), self.y.abs(), self.z.abs()) }
}

#[derive(Copy, Clone, Debug, PartialEq)]
enum VT { Body, WeakPoint, Armor, Invuln }

#[derive(Copy, Clone, Debug)]
struct Volume { offset: Vec3, half: Vec3, vtype: VT }

#[derive(Clone, Debug)]
struct Entity {
    pos: Vec3,
    height: f32,
    volumes: Vec<Volume>,
}

impl Entity {
    fn player(pos: Vec3) -> Self {
        Self {
            pos,
            height: 64.0,
            volumes: vec![Volume {
                offset: Vec3::new(0., 0., 32.),
                half: Vec3::new(16., 16., 32.),
                vtype: VT::Body,
            }],
        }
    }

    fn dragon(pos: Vec3) -> Self {
        Self {
            pos,
            height: 256.0,
            volumes: vec![
                Volume { offset: Vec3::new(0., 0., 240.), half: Vec3::new(32., 32., 16.), vtype: VT::WeakPoint },
                Volume { offset: Vec3::new(0., 0., 180.), half: Vec3::new(24., 24., 32.), vtype: VT::Body },
                Volume { offset: Vec3::new(0., 0., 120.), half: Vec3::new(64., 32., 64.), vtype: VT::Body },
                Volume { offset: Vec3::new(80., 0., 140.), half: Vec3::new(48., 16., 32.), vtype: VT::Armor },
                Volume { offset: Vec3::new(-80., 0., 140.), half: Vec3::new(48., 16., 32.), vtype: VT::Armor },
            ],
        }
    }
}

fn aabb_overlap(ac: Vec3, ah: Vec3, bc: Vec3, bh: Vec3) -> bool {
    let d = ac.sub(bc).abs();
    d.x < ah.x + bh.x && d.y < ah.y + bh.y && d.z < ah.z + bh.z
}

fn entities_collide_volumes(a: &Entity, b: &Entity) -> Option<(usize, usize)> {
    for (i, va) in a.volumes.iter().enumerate() {
        let ac = a.pos.add(va.offset);
        for (j, vb) in b.volumes.iter().enumerate() {
            let bc = b.pos.add(vb.offset);
            if aabb_overlap(ac, va.half, bc, vb.half) {
                return Some((i, j));
            }
        }
    }
    None
}

fn damage_for(vtype: VT, base: f32) -> f32 {
    match vtype {
        VT::Body => base,
        VT::WeakPoint => base * 2.0,
        VT::Armor => base * 0.5,
        VT::Invuln => 0.0,
    }
}

fn main() {
    let player = Entity::player(Vec3::new(0., 0., 256.));  // 玩家在龙头上方
    let dragon = Entity::dragon(Vec3::new(0., 0., 0.));

    let base_dmg = 10.0;
    if let Some((i, j)) = entities_collide_volumes(&player, &dragon) {
        let vt = dragon.volumes[j].vtype;
        let dmg = damage_for(vt, base_dmg);
        println!("玩家 vol {} 撞到 龙 vol {}({:?}),伤害 = {:.1}", i, j, vt, dmg);
    } else {
        println!("没撞");
    }
}
```

**预期输出**:
```
玩家 vol 0 撞到 龙 vol 0(WeakPoint),伤害 = 20.0
```
