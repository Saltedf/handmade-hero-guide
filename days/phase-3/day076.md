
# Day 076 · 实体高度与碰撞检测

> 你的玩家现在有 (x, y, z),但**他有多高?** 你前面 Day 071 给玩家加了 `half_z = 32`,凭直觉。今天 Casey 把这个「凭直觉」的字段正式化——每个 entity 都有 **height(高度)** 字段,碰撞体积从 2D 矩形升级为 3D 长方体。这一步看似只是改字段名,但它把「玩家身高 64、怪身高 32」这种游戏数据**正式编码**进数据结构,后续的所有游戏机制(攻击范围、视野、台阶)都依赖这个数字。

## 0 · 为什么要有这一天

Phase 2 你的 entity 长这样:

```rust
struct Entity {
    pos: Vec2,
    half: Vec2,  // 碰撞矩形的半宽 / 半高
    // ...
}
```

Day 071 你加了 z 字段:

```rust
struct Entity {
    pos: Vec3,
    half: Vec3,  // half.x, half.y, half.z
    // ...
}
```

但**没有「height」这个明确字段**——你只是用 `half.z * 2` 当身高。这有两个问题:

**问题 1:语义不清**。`half.z` 是「半身高」还是「碰撞体积的半厚」?对玩家来说,「身高 64」和「碰撞体积 z 厚 64」可能不一样——比如玩家 sprite 是 64 高,但碰撞体积只用 48(为了方便穿过窄缝)。

**问题 2:多楼层语义混乱**。玩家在二楼(z 范围 [64, 128]),脚踩在 z=64 的二地板上,头在 z=128。但**他「站在」哪一层**?是 z=64(脚)还是 z=96(中)还是 z=128(头)?Day 077 的「接地点」会回答这个问题,但首先要有一个明确的「身高」字段。

Casey 今天做的:**给 entity 加 height 字段**,正式区分:
- `pos.z`:entity 的「参考点 z」(通常是脚 z,即站在哪)
- `height`:entity 的身高
- `half.z`:碰撞体积的半厚(通常 = height / 2,但可以独立调)

**这个区分让多楼层建筑的碰撞正确**。楼上玩家(height=64,站在 z=64,头顶 z=128)和楼下怪(height=32,站在 z=0,头顶 z=32)——他们的 z 范围完全不重叠,所以不碰。Phase 2 没法做这个,因为只有 2D AABB。

心理锚点:看完今天,你能写出**正式的 3D 碰撞系统**。你能解释为什么 Casey 不直接用 `pos.z` 当中心,而是当「参考点」。你能用 Rust 表达「身高 vs 半厚」两个独立概念。

## 1 · Casey 今天做了什么

Casey 今天的代码改动:

1. **Entity struct 加 height 字段**:`Entity { pos: Vec3, half: Vec3, height: f32, ... }`。
2. **half.z 改成派生量**:`half.z = height / 2`(默认)。某些特殊 entity 可以覆盖(比如矮的怪,身高 64 但碰撞只用 32)。
3. **碰撞判定改用 height**:`center_z = pos.z + height / 2`(pos.z 是脚)。
4. **测试**:多楼层场景,楼上玩家和楼下怪完全不碰。

Casey 强调:**`pos.z` 是「接地点 z」(脚在哪),不是「中心 z」**。这是关键约定。原因:玩家「站在地面」的概念比「中心在哪」更基础——多个 traversable 比较时,我们比的是脚的高度。

但碰撞数学用「中心 + half」更对称,所以碰撞时临时算 `center_z = pos.z + height / 2`。

## 2 · 心智模型

### 费曼类比:墙上的便条

你给同事留便条:**「我在 5 楼」**。你不需要说「我的脚在 5 楼地板上,头在 5 楼天花板下」——大家都知道「在 5 楼」=「我的脚踩在 5 楼地板上」。

这就是 Casey 用 `pos.z` 表达「接地点」的原因——**直觉上更接近人的描述**。

但物理引擎需要「中心 + 半尺寸」来表达 AABB。所以代码内部要转换:

```
玩家说:「我在 5 楼」(pos.z = 5楼地面 z)
代码转换为:「我的中心在 5 楼地面 + 身高/2,我的半厚是身高/2」
```

#### 2.1 数据结构

```rust
struct Entity {
    pos: Vec3,       // pos.z = 脚 z(接地点 z)
    half: Vec2,      // x/y 方向半宽(碰撞矩形)
    height: f32,     // 身高
    // ...
}

impl Entity {
    // 碰撞用的 3D AABB
    fn aabb3(&self) -> AABB3 {
        AABB3 {
            center: Vec3::new(self.pos.x, self.pos.y, self.pos.z + self.height / 2.0),
            half: Vec3::new(self.half.x, self.half.y, self.height / 2.0),
        }
    }
}
```

每次需要碰撞检测时,临时构造 AABB3。这个构造开销很小(几次乘加),不需要存。

#### 2.2 为什么 pos.z 是脚,不是中心

**理由 1:多楼层语义直观**。两个 entity 比较「谁高」时,比的是「脚踩的地面」。一个站在 5 楼(z=64),一个站在 4 楼(z=0),5 楼的高。

**理由 2:重力 / 跳跃直观**。玩家跳跃时,加 z 速度,`pos.z += vel.z * dt`。z 越大,玩家脚越离开地面。如果 pos.z 是中心,跳跃时还要算「中心 = 脚 + height/2」,多此一举。

**理由 3:跨 entity 一致**。所有 entity(玩家、怪、平台)的 pos.z 都是「脚」。比较好坏对错时,统一标准。

**反例:某些物理引擎用中心**。Box2D 的 body 是中心 + half_extents,因为 2D 物理(旋转)用中心更对称。Casey 不用旋转,用脚更直观。

#### 2.3 不同 entity 的 height 值

```rust
const PLAYER_HEIGHT: f32 = 64.0;
const MONSTER_SOLDIER_HEIGHT: f32 = 64.0;
const MONSTER_GOBLIN_HEIGHT: f32 = 32.0;
const MONSTER_DRAGON_HEIGHT: f32 = 256.0;
const WALL_HEIGHT: f32 = 128.0;
const STAIR_HEIGHT: f32 = 16.0;
```

height 不是「真实身高」,而是「碰撞体积的高度」。矮墙(墙身高 64)可能 height=96(加 collision padding),让玩家撞墙时不会「头露在墙上方」。

#### 2.4 多楼层碰撞的最终算法

```rust
fn entities_collide(a: &Entity, b: &Entity) -> bool {
    // x/y 比较(和 Phase 2 一样)
    let dx = (a.pos.x - b.pos.x).abs();
    let dy = (a.pos.y - b.pos.y).abs();
    let sx = a.half.x + b.half.x;
    let sy = a.half.y + b.half.y;
    if dx >= sx || dy >= sy { return false; }

    // z 比较(用脚 + height 算 z 范围)
    let a_bot = a.pos.z;
    let a_top = a.pos.z + a.height;
    let b_bot = b.pos.z;
    let b_top = b.pos.z + b.height;

    // z 范围重叠 ⟺ max(a_bot, b_bot) < min(a_top, b_top)
    let z_overlap_min = a_bot.max(b_bot);
    let z_overlap_max = a_top.min(b_top);
    z_overlap_min < z_overlap_max
}
```

**为什么用 `<` 而不是 `<=`?** 跟 Day 072 一样,边界相切不算碰。

**用 max/min 而不是 abs?** 因为 z 范围不是对称的(脚 ≠ 头),不能用「中心差」。用 max/min 直接表达「重叠区域」。

#### 2.5 多楼层示例

```
玩家:pos.z=64, height=64 → z 范围 [64, 128]  (站在二楼地板上)
怪:  pos.z=0,  height=64 → z 范围 [0, 64]    (站在一楼地板上)

z_overlap_min = max(64, 0) = 64
z_overlap_max = min(128, 64) = 64
64 < 64 ? false
不碰!
```

```
玩家:pos.z=64, height=64 → z 范围 [64, 128]
怪:  pos.z=32, height=64 → z 范围 [32, 96]   (站在一楼天花板下,身高穿过二楼地板?)

z_overlap_min = max(64, 32) = 64
z_overlap_max = min(128, 96) = 96
64 < 96 ? true
碰!
```

第二种情况是「怪穿过了地板」——不应该发生,但代码层判定是「碰」。这是合理的——游戏代码负责让怪不穿过地板,碰撞函数只负责报告事实。

#### 2.6 half_z vs height 的关系

Casey 默认 `half_z = height / 2`,但允许独立调:

```rust
impl Entity {
    fn new(pos: Vec3, half: Vec2, height: f32) -> Self {
        Self { pos, half, height }
    }

    // 默认:碰撞 z 半厚 = height / 2
    fn aabb3_default(&self) -> AABB3 {
        AABB3 {
            center: Vec3::new(self.pos.x, self.pos.y, self.pos.z + self.height / 2.0),
            half: Vec3::new(self.half.x, self.half.y, self.height / 2.0),
        }
    }

    // 自定义:碰撞 z 半厚可以小于 height / 2
    // 比如玩家身高 64,但碰撞 z 半厚只用 24(从脚到膝盖)
    // 这样玩家可以走过 16 高的窄缝
    fn aabb3_with_half_z(&self, half_z: f32) -> AABB3 {
        AABB3 {
            center: Vec3::new(self.pos.x, self.pos.y, self.pos.z + half_z),
            half: Vec3::new(self.half.x, self.half.y, half_z),
        }
    }
}
```

Casey HH 大多数 entity 用 default,特殊场景才自定义。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

**height 字段的设计哲学**:把「游戏感数据」(身高)和「碰撞数据」(half)分开。这有几点好处:

**1. 调参方便**。设计师改 height(角色变高),不用动 half。
**2. 视觉一致**。sprite 渲染用 height,sprite 高度严格等于 height。
**3. 碰撞灵活**。某些场景需要「碰撞比视觉小」(玩家穿过窄缝),只调 half。

#### 不同 entity 的 height 设计

| Entity | height | 设计理由 |
|---|---|---|
| 玩家 | 64 | 标准身高(1 米) |
| 哥布林 | 32 | 矮,能藏在草丛 |
| 龙 | 256 | Boss 尺寸 |
| 树 | 128 | 高,挡视线 |
| 墙 | 64 | 同玩家身高 |
| 平台 | 16 | 薄,可以踩 |
| 弹药 | 4 | 小,适合子弹 |

height 不是「真实尺寸」,是「碰撞 / 视觉尺寸」。设计师根据游戏感调。

#### 经典游戏的碰撞设计

**Zelda BOTW**:Link 身高约 1.7 米,碰撞体积约 1 米(头脚留空),让 Link 能钻小洞。

**Dark Souls**:角色身高约 1.8 米,碰撞约 1.5 米。某些「跨过尸体」的场景靠这个 margin。

**Celeste**:Madeline 身高 24 像素,碰撞 24 像素(几乎无 margin)。这是精确平台游戏的选择——任何小 margin 都可能让玩家卡住。

### 3.2 · 🎨 图形学视角

height 在渲染里有几个用途:

**Sprite 渲染**:sprite 高度严格 = height。`sprite.draw_at(pos, height)`,sprite 的脚在 pos,sprite 的顶在 pos + height。

**阴影投射**:阴影位置 = pos,大小 = half.x * 2 × half.y * 2(用 x/y 半宽,不用 z)。

**Billboard**(公告板):3D 中 sprite 永远朝向相机,billboard 高度 = entity 的 height。

**LOD**(level of detail):远处 entity 用低精度 sprite。sprite 的 height 决定 LOD——远处的 entity 可能 height 缩小到 8 像素,此时 sprite 用 8 像素版本。

#### 多楼层渲染的 Z 层渐隐

Day 107 Casey 会加「Z 层渐隐」——高 z 的楼层半透明渲染。基础数据就是 height + pos.z。比如玩家在二楼(z=64..128),三楼的 entity(z=128..192)半透明 60% 渲染,玩家能看到三楼但不被挡。

这个机制完全基于「每个 entity 有 height」,今天的数据结构。

### 3.3 · 🐧 Linux 系统编程视角

跟 Linux 没直接关系。但有一个**通用工程思想**:把「数据」和「派生量」分开。

Linux 内核里有很多类似设计:

- **task_struct 的 pid 和 tgid**:pid 是线程 ID,tgid 是进程 ID(线程组 ID)。用户看到的「进程 ID」是 tgid,内部调度用 pid。两个不同的字段,但有派生关系。
- **inode 的 i_size 和 i_blocks**:i_size 是文件字节数,i_blocks 是分配的 512 字节块数。两者相关但不严格相等(块对齐 padding)。

Casey 的 height 和 half_z 类似:height 是「真实身高」(用户看到),half_z 是「碰撞用的半厚」(内部用)。两者通常相等,但允许独立。

### 3.4 · 🦀 Rust 生态视角

#### Rust 写 entity 数据结构

```rust
#[derive(Copy, Clone, Debug)]
pub struct Entity {
    pub pos: Vec3,      // pos.z 是脚
    pub half: Vec2,     // x/y 碰撞半宽
    pub height: f32,
}

impl Entity {
    pub fn new(pos: Vec3, half: Vec2, height: f32) -> Self {
        Self { pos, half, height }
    }

    #[inline]
    pub fn aabb3(&self) -> AABB3 {
        let half_z = self.height * 0.5;
        AABB3 {
            center: Vec3::new(self.pos.x, self.pos.y, self.pos.z + half_z),
            half: Vec3::new(self.half.x, self.half.y, half_z),
        }
    }

    #[inline]
    pub fn feet_z(&self) -> f32 { self.pos.z }

    #[inline]
    pub fn head_z(&self) -> f32 { self.pos.z + self.height }
}
```

**关键设计**:`aabb3()` 是方法,不存字段。每次需要时算——避免存「派生字段」导致数据不一致。

**Rust 的派生字段陷阱**:

```rust
// 错误:存派生字段,容易不一致
struct EntityBad {
    pos: Vec3,
    half: Vec2,
    height: f32,
    center_z: f32,  // 应该是 pos.z + height/2,但如果改了 pos 或 height 忘了改 center_z 就 bug
}

// 正确:不存,需要时算
struct EntityGood { pos: Vec3, half: Vec2, height: f32 }
impl EntityGood {
    fn center_z(&self) -> f32 { self.pos.z + self.height / 2.0 }
}
```

**这是 Rust 类型系统帮我们抓 bug 的典型方式**——不存派生量,消除「数据不一致」的可能。

#### Rust 的 builder pattern

```rust
impl Entity {
    pub fn builder() -> EntityBuilder { EntityBuilder::default() }
}

#[derive(Default)]
pub struct EntityBuilder {
    pos: Option<Vec3>,
    half: Option<Vec2>,
    height: Option<f32>,
}

impl EntityBuilder {
    pub fn pos(mut self, pos: Vec3) -> Self { self.pos = Some(pos); self }
    pub fn half(mut self, half: Vec2) -> Self { self.half = Some(half); self }
    pub fn height(mut self, h: f32) -> Self { self.height = Some(h); self }
    pub fn build(self) -> Entity {
        Entity {
            pos: self.pos.unwrap_or(Vec3::new(0., 0., 0.)),
            half: self.half.unwrap_or(Vec2::new(8., 8.)),
            height: self.height.unwrap_or(64.),
        }
    }
}

// 使用
let player = Entity::builder()
    .pos(Vec3::new(100., 100., 0.))
    .half(Vec2::new(16., 16.))
    .height(64.)
    .build();
```

Builder pattern 让 entity 创建可读、可缺省值。

## 5 · 对照与变奏

### 不同游戏引擎的 entity 数据结构

| 引擎 | 碰撞体积表达 |
|---|---|
| Casey HH | pos + half + height |
| Unity | transform.position(中心)+ collider size |
| Unreal | Actor Location + collision box extents |
| Box2D | body position(中心)+ fixture shape |
| Godot | Node2D position + collision shape |

 Casey 用「脚」而非「中心」,这是个**反传统选择**——大多数引擎用中心。Casey 选择脚是因为他不做旋转(2.5D),脚更直观。

### height vs half_z 的设计空间

| 方案 | height | half_z | 用例 |
|---|---|---|---|
| 默认 | 64 | 32 | 大多数 entity |
| 头部碰撞小 | 64 | 16 | 玩家能钻小洞 |
| 腿部碰撞小 | 64 | 16,但 center 偏低 | 跨低墙 |
| 攻击范围扩大 | 64 | 64(整身) | 攻击范围 = 碰撞 |

这些组合让一个 entity 表达复杂行为,代码层很简洁。

### 历史:从「2D sprite + 高度」到「3D mesh」

- **1980s 末**:Zelda ALTTP 用「2D sprite + height 字段」做 2.5D。
- **1990s**:Diablo 改进这一思路。
- **2000s**:3D mesh 主流,但 2.5D 游戏仍用 sprite + height。
- **2010s+**:Hades 等用「2.5D + 法线贴图」精致化。

Casey HH 走 Zelda ALTTP 路线,因为简单且有效。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 用 `pos.z` 表达「脚 z」而不是「中心 z」?给两个理由。

**参考解答**:

理由 1:**多楼层语义直观**。两个 entity 比较「谁站得高」时,比的是脚踩的地面。玩家在二楼(z=64)说比一楼(z=0)高,这是脚的高度比较。如果用中心,玩家中心 z=96,一楼怪中心 z=32,差 64,但仍要算出「站在不同楼」。

理由 2:**重力 / 跳跃代码简单**。玩家跳跃时 `pos.z += vel.z * dt`——直接操作脚的位置,不需要考虑「中心 = 脚 + height/2」。同样,「站在地面」=`pos.z == ground_z`,简洁。如果用中心,「站在地面」=`center_z == ground_z + height/2`,啰嗦。

```rust

impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

}

impl Entity {
    fn new(x: f32, y: f32, z: f32, half_x: f32, half_y: f32, height: f32) -> Self {
        Self {
            pos: Vec3::new(x, y, z),
            half: Vec2::new(half_x, half_y),
            height,
        }
    }
}

fn entities_collide(a: &Entity, b: &Entity) -> bool {
    let dx = (a.pos.x - b.pos.x).abs();
    let dy = (a.pos.y - b.pos.y).abs();
    if dx >= a.half.x + b.half.x || dy >= a.half.y + b.half.y { return false; }

    let a_top = a.pos.z + a.height;
    let b_top = b.pos.z + b.height;
    a.pos.z.max(b.pos.z) < a_top.min(b_top)
}
```

```rust
#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 { fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } } }

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec3,      // pos.z 是脚
    half: Vec2,     // x/y 碰撞半宽
    height: f32,
}

impl Entity {
    fn new(x: f32, y: f32, z: f32, hx: f32, hy: f32, h: f32) -> Self {
        Self { pos: Vec3::new(x, y, z), half: Vec2::new(hx, hy), height: h }
    }

    #[inline]
    fn head_z(&self) -> f32 { self.pos.z + self.height }

    #[inline]
    fn center_z(&self) -> f32 { self.pos.z + self.height * 0.5 }
}

#[inline]
fn entities_collide(a: &Entity, b: &Entity) -> bool {
    let dx = (a.pos.x - b.pos.x).abs();
    let dy = (a.pos.y - b.pos.y).abs();
    if dx >= a.half.x + b.half.x || dy >= a.half.y + b.half.y { return false; }
    a.pos.z.max(b.pos.z) < a.head_z().min(b.head_z())
}

fn main() {
    // 多楼层示例
    let player_2f = Entity::new(100., 100., 64., 16., 16., 64.);  // 2F: z=64..128
    let monster_1f = Entity::new(100., 100., 0., 16., 16., 64.);  // 1F: z=0..64

    println!("=== 多楼层碰撞测试 ===");
    println!("玩家(2F,z=64..128)vs 怪(1F,z=0..64)");
    println!("  碰: {}", entities_collide(&player_2f, &monster_1f));  // false

    // 玩家跳起来,部分穿过二楼地板
    let player_jumping = Entity::new(100., 100., 32., 16., 16., 64.);  // z=32..96
    println!("\n玩家(z=32..96)vs 怪(1F,z=0..64)");
    println!("  碰: {}", entities_collide(&player_jumping, &monster_1f));  // true

    // 矮怪
    let goblin = Entity::new(100., 100., 0., 8., 8., 32.);  // z=0..32
    println!("\n玩家(1F,z=0..64)vs 哥布林(z=0..32)");
    println!("  碰: {}", entities_collide(&monster_1f, &goblin));  // true

    // 龙穿过两层楼
    let dragon = Entity::new(100., 100., 0., 32., 32., 256.);  // z=0..256
    println!("\n龙(z=0..256,跨两层楼)vs 玩家(2F,z=64..128)");
    println!("  碰: {}", entities_collide(&dragon, &player_2f));  // true
}
```
