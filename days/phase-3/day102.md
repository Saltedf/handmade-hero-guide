# Day 102 · 正确变换法线

> 昨天 Day 101 你学了矩阵的逆和转置,以及为什么变换法线要用 `(M⁻¹)ᵀ`。今天 Casey 把这个理论**应用**到法线贴图——3D 模型的法线贴图在模型被非均匀缩放时,如果用错误矩阵变换,光照完全错。今天修这个 bug,让法线在任意变换下都正确。

## 0 · 为什么要有这一天

让我们从一个真实的渲染 bug 说起。

你做了 64×64 像素的金属面板 sprite,带法线贴图——模拟铆钉、刮痕、凸起的细节。在 64×64 时,光照完美——金属铆钉朝上的高光、刮痕的阴影都对。

但你的游戏关卡需要 128×256 的金属面板。你把 sprite 缩放:`x * 2, y * 4`(非均匀缩放,横向 ×2,纵向 ×4)。**光照完全错**——铆钉的高光位置错了,刮痕的阴影方向反了,整块面板看起来"塑料感",不像金属。

你困惑——同样的 sprite,只是缩放,为什么光照会变?

**根因**:你的代码**直接用 Model 矩阵变换法线**,这在非均匀缩放时是错的。让我把数学展开。

Model = `diag(2, 4, 1)`(对角矩阵,x 方向 ×2,y 方向 ×4,z 方向不变)。法线 `(0.3, 0.4, 0.86)`(朝右上方倾斜)。

**错误做法**(直接乘 Model):
- 法线乘 Model = `(0.6, 1.6, 0.86)`
- 归一化 = `(0.31, 0.81, 0.43)`

这个法线**不正确**!为什么?因为 sprite 被非均匀拉伸后,表面在某点的斜率改变了——但法线是垂直于表面的向量,**垂直性不通过简单乘 Model 保持**。乘 Model 后的"法线"不再垂直于拉伸后的表面。

**正确做法**(用 `(M⁻¹)ᵀ`):
- `M⁻¹ = diag(0.5, 0.25, 1)`(逆矩阵)
- `(M⁻¹)ᵀ` = `diag(0.5, 0.25, 1)`(对角矩阵转置不变)
- 法线乘 `(M⁻¹)ᵀ` = `(0.15, 0.1, 0.86)`
- 归一化 = `(0.17, 0.11, 0.96)`

这两个结果——`(0.31, 0.81, 0.43)` vs `(0.17, 0.11, 0.96)`——**完全不同方向**。光照计算用 `dot(normal, light_dir)`,法线方向错几个角度,光照值差几倍。结果就是 bug——金属面板光照错。

`(M⁻¹)ᵀ` 的本质是数学保证:**对任意 Model 矩阵(包括非均匀缩放),变换后的法线保持垂直性**。这是 1970 年代图形学推导的结论(Foley & van Dam 的经典教科书),但今天仍被很多教程跳过——导致大量游戏在非均匀缩放时光照错。

今天 Casey 把这个理论**应用**到法线贴图——3D 模型的法线贴图在模型被非均匀缩放时,如果用错误矩阵变换,光照完全错。今天修这个 bug,让法线在任意变换下都正确。

**学完今天,你应该能**:

- **解释为什么直接乘 Model 不行**——法线垂直性不保持
- **推导 `(M⁻¹)ᵀ` 的数学**——从"法线垂直于切线"的几何约束推出
- **在 shader / 像素循环里正确变换法线**——预算 `normal_matrix` 一次性,传 GPU
- **优化正交矩阵的特殊路径**——只有旋转的 Model 不需要算逆
- **看懂 industrial shader 的 `u_normal_matrix` uniform**——它就是这个公式

## 1 · Casey 今天做了什么

Casey 今天的工作拆开:

**第一步,定位 bug**。他在 sprite 渲染里发现,法线贴图采样后的法线,直接用 sprite 的 Model 矩阵变换。非均匀缩放时,法线方向错,光照结果错。具体表现为铆钉高光偏移、刮痕阴影反向。

**第二步,应用理论**。Day 101 学的 `(M⁻¹)ᵀ`,今天用上。他在 sprite 渲染前预算 `normal_matrix = (Model⁻¹)ᵀ`,每个 sprite 算一次。然后每个像素用 normal_matrix 变换法线。

**第三步,测试验证**。他用 `(0, 0, 1)` 法线 + 非均匀缩放,变换后应该还是 `(0, 0, 1)`(因为 z 方向没缩放,垂直性自然保持)。再用斜的法线验证——正确版的法线方向应该和数学预期一致。

**第四步,性能权衡**。`(M⁻¹)ᵀ` 预算一次,每个 sprite 用一次,不是每像素算。这是性能关键——如果每像素都算 `(M⁻¹)ᵀ`,帧时间爆。

**Casey 提到的优化**:如果 Model 矩阵只有旋转和平移(无缩放),`(M⁻¹)ᵀ = M`(因为旋转矩阵的逆 = 转置)。所以 normal_matrix 直接用 Model 的旋转部分——不用算逆,节省几纳秒。但 Casey HH 通常不优化,直接用 `normal_matrix`——开销小,代码简单。

## 2 · 心智模型

### 2.1 费曼类比:拉橡皮筋

我打个比方。想象一根橡皮筋,上面画一个箭头(法线),垂直于橡皮筋。当你**拉长橡皮筋**(非均匀缩放,只拉一个方向),箭头跟着变化——但它**不再垂直**了。如果你想让箭头始终垂直于拉伸后的橡皮筋,你需要重新计算箭头方向。

数学上,「重新计算箭头方向」就是 `(M⁻¹)ᵀ · n`。直觉:
- `M⁻¹` **反拉伸**——把拉伸后的橡皮筋还原回原状态(像把橡皮筋从拉伸状态恢复)
- `ᵀ`(转置)**调整方向**——使法线垂直于新的拉伸后表面(像旋转箭头使它垂直于新方向)

为什么是这两个操作的组合?这是几何推导的结果,不是凭空发明。Eric Lengyel 在《Mathematics for 3D Game Programming and Computer Graphics》第 3 章有完整推导,核心步骤:**法线 n 垂直于切线 t**(`n · t = 0`)。变换后,切线 t' = M·t。要保持垂直性 n' · t' = 0,可以推出 n' = `(M⁻¹)ᵀ · n`。

### 2.2 严谨原理:从几何约束推导

让我把推导展开,你会看到 `(M⁻¹)ᵀ` 不是魔法,是几何必然。

**前提**:法线 n 垂直于切线 t。即 `n · t = 0`(点积为零)。

**变换**:
- 切线 t 是表面的方向向量,变换用 Model:t' = M·t
- 法线 n 是垂直于表面的向量,变换用 ??? :n' = X·n(我们要找 X)

**约束**:变换后,法线仍垂直于切线。`n' · t' = 0`。代入:
```
(X·n) · (M·t) = 0
```

**用矩阵的标量积恒等式**:`(A·u) · (B·v) = u · (Aᵀ·B·v)`。应用:
```
n · (Xᵀ·M·t) = 0
```

**这要对所有 t 成立**(任意切线),必须 `Xᵀ·M = λI`(λ 是任意标量,通常取 1)。所以:
```
Xᵀ·M = I
Xᵀ = M⁻¹
X = (M⁻¹)ᵀ
```

**结论**:法线变换矩阵 `X = (M⁻¹)ᵀ`。这是**几何必然**,不是发明。

**简化**:如果 M 是正交矩阵(只旋转),`M⁻¹ = Mᵀ`,所以 `(M⁻¹)ᵀ = (Mᵀ)ᵀ = M`。正交矩阵的法线变换 = 直接用 M。这就是 Casey 提到的优化——只有旋转时,跳过 inverse + transpose。

**完整流程**:

```
1. 从法线贴图采样 tangent_space_normal
2. 如果 sprite 是 2D(切线空间 = 视图空间),直接用
3. 否则,用 TBN 变换到 world space(见 Day 097)
4. 用 normal_matrix = (Model⁻¹)ᵀ 变换 world normal
5. 归一化((M⁻¹)ᵀ 不保长,必须归一化)
6. 用于 Phong 光照
```

对 Casey HH 的 2.5D,sprite 都朝相机,TBN 是单位矩阵,所以步骤 2-3 简化为「直接用」。但如果 sprite 被缩放(尤其是非均匀),步骤 4 必须用 `(M⁻¹)ᵀ`。

### 2.3 Rust 代码实现

```rust
// 在 Sprite 渲染时,预算 normal_matrix 一次性
let model = sprite.model_matrix();  // 包含位置、旋转、缩放
let model_rot_scale = model.upper_left_3x3();  // 提取 3x3(不含平移)
let normal_matrix = model_rot_scale.inverse().expect("Model must be invertible").transpose();

// 每像素用 normal_matrix 变换法线
for py in min_y..=max_y {
    for px in min_x..=max_x {
        // ... 采样纹理 ...
        let tangent_normal = sprite.normal.sample_nearest(u, v);
        // 关键:法线变换用 normal_matrix,不是 model
        let world_normal = normal_matrix.mul_vec(tangent_normal).normalized();
        // 用于光照
        let lit = phong_lighting(surface_color, world_normal, view, light, ...);
    }
}
```

注意几个细节:

- **预算一次**:`normal_matrix` 在 sprite 渲染前算一次,不是每像素算。每像素只做 `normal_matrix.mul_vec(normal)`(3x3 * vec3 = 9 次乘法)。
- **提取 3x3**:Model 是 4x4(含平移),法线变换不需要平移,只用 3x3 旋转+缩放部分。
- **归一化必须**:`(M⁻¹)ᵀ` 不保长,变换后法线长度可能 ≠ 1。Phong 光照要求单位向量,所以归一化。
- **逆矩阵必须存在**:如果 Model 有 0 缩放(某个方向 ×0),M 不可逆,`inverse()` 失败。生产代码用 `inverse().unwrap_or(Mat3::identity())`。

### 2.4 正交矩阵的优化

如果 Model 只旋转(正交矩阵),`(M⁻¹)ᵀ = M`,直接用 M 就行。这省了 inverse + transpose 两个矩阵运算。

```rust
fn get_normal_matrix(model: Mat3) -> Mat3 {
    let is_orthogonal = is_rotation_only(&model);  // 检查 model 是否正交
    if is_orthogonal {
        model  // 直接返回
    } else {
        model.inverse().unwrap_or(Mat3::identity()).transpose()
    }
}

fn is_rotation_only(m: &Mat3) -> bool {
    // 检查所有列向量长度 = 1(正交矩阵性质)
    let col0 = Vec3::new(m.m[0][0], m.m[1][0], m.m[2][0]);
    let col1 = Vec3::new(m.m[0][1], m.m[1][1], m.m[2][1]);
    let col2 = Vec3::new(m.m[0][2], m.m[1][2], m.m[2][2]);
    (col0.length() - 1.0).abs() < 0.001 &&
    (col1.length() - 1.0).abs() < 0.001 &&
    (col2.length() - 1.0).abs() < 0.001
}
```

但 Casey HH 通常不优化,直接用 `normal_matrix`——开销小,代码简单。**优化的本质是 trade-off**:加一行 if 节省几个乘法,但代码复杂度增加。在性能不是瓶颈的地方,简单优先。

### 2.5 错误 vs 正确的对比

让我用具体数值展示差异,你会直观理解为什么 `(M⁻¹)ᵀ` 重要。

**Model = diag(2, 4, 1),原法线 (0.6, 0.8, 0)**

- **错误**(直接乘 M):`(1.2, 3.2, 0)`,归一化 `(0.35, 0.94, 0)`
- **正确**(`(M⁻¹)ᵀ = diag(0.5, 0.25, 1)`):`(0.3, 0.2, 0)`,归一化 `(0.83, 0.55, 0)`

完全不同方向。错误法线 y 分量 0.94(几乎朝上),正确法线 y 分量 0.55(45° 倾斜)。光照计算用 `dot(normal, light)`,假设光从上方来 `(0, 1, 0)`:
- 错误:`dot((0.35, 0.94, 0), (0, 1, 0)) = 0.94`——很亮
- 正确:`dot((0.83, 0.55, 0), (0, 1, 0)) = 0.55`——中等亮度

光照差 1.7 倍。视觉上,错误版的 sprite 看起来"过亮",像打了高光;正确版的 sprite 光照自然。

**Model = 旋转矩阵 R(30°)**

旋转矩阵是正交的,`R⁻¹ = Rᵀ`。所以 `(R⁻¹)ᵀ = (Rᵀ)ᵀ = R`。直接乘 R 和 `(R⁻¹)ᵀ` 完全一样——**旋转不需要 `(M⁻¹)ᵀ`**。

但只要加了任何非均匀缩放,就必须重新算 `(M⁻¹)ᵀ`。这也是为什么很多开发者困惑——"我之前没加 normal_matrix 也对啊",因为他们只用旋转。一旦加缩放(尤其非均匀),bug 出现。

## 3 · 四域深入

### 3.1 · 游戏编程视角

法线变换在游戏的应用极其广泛。让我列几个工业场景。

**非均匀缩放 sprite**(Casey HH 场景)。角色装备大小不同——同一件衣服 sprite 给小孩穿是 ×0.7 缩放,给巨人穿是 ×1.5 缩放。如果衣服有法线贴图(模拟布料褶皱),缩放时光照必须正确。这是 Casey HH 的直接需求。

**3D 模型缩放**。玩家角色变胖/变瘦——通过 scale 修改 model matrix。如果模型有法线贴图(皱纹、肌肉细节),缩放时光照靠 `(M⁻¹)ᵀ` 保持正确。

**粒子系统**。每个粒子有自己的旋转 + 缩放——例如爆炸碎片,每片旋转 + 不同大小。粒子有法线时,`(M⁻¹)ᵀ` 必用。

**物理变形**。可变形物体(布料、毛发)的法线动态变化。每帧根据 mesh 形变重新算法线,然后用 `(M⁻¹)ᵀ` 变换。布料模拟(Woven / Position Based Dynamics)和毛发模拟(TressFX)都涉及。

**坑:TBN 矩阵也要正确变换**。如果切线 (T)、副切线 (B)、法线 (N) 三者都在 tangent space,变换到 world space 时:
- T 和 B 用 Model 矩阵变换(它们是切线,直接用 Model)
- N 用 `(Model⁻¹)ᵀ`(它垂直于表面)

否则 TBN 不再正交,法线贴图错误。这是 3D 模型法线贴图的常见 bug——TBN 一个用 Model 一个用 `(M⁻¹)ᵀ`,新手容易混。

### 3.2 · 图形学视角

法线变换是经典图形学话题,99% 的教程都讲——但 99% 的人**跳过**。结果大量游戏在非均匀缩放时光照错。这是 graphics programming 的"肮脏秘密"——很多 bug 来自"教程跳过的小细节"。

**PBR(物理基础渲染)视角**:PBR 要求所有法线在 world space 计算,normal_matrix 是必备 uniform。Unity / Unreal 的 standard shader 都自动提供 `unity_WorldToObject`(Unity)或 `WorldToObject`(Unreal),本质就是 `(M⁻¹)ᵀ`。

**Shader 实现**(GLSL):

```glsl
// vertex shader
out vec3 v_world_normal;
uniform mat4 u_model;
uniform mat3 u_normal_matrix;  // CPU 预算 (model⁻¹)ᵀ

void main() {
    v_world_normal = normalize(u_normal_matrix * a_normal);
    gl_Position = u_proj * u_view * u_model * vec4(a_pos, 1.0);
}
```

CPU 端预算 `u_normal_matrix`:

```rust
let model: Mat4 = sprite.model_matrix();
let normal_matrix: Mat3 = model.inverse().transpose().truncate();  // 提取 3x3
// 上传到 GPU
shader.set_uniform_mat3("u_normal_matrix", &normal_matrix);
```

**Unity 的标准做法**(C#):

```csharp
Matrix4x4 m = transform.localToWorldMatrix;
Matrix4x4 normalMatrix = m.inverse.transpose;
Shader.SetGlobalMatrix("_NormalMatrix", normalMatrix);
```

Unity 内置 `WorldToObject` 等价于 `localToWorldMatrix.inverse`,shader 里再 `.transpose` 即可。

**Unreal 的标准做法**:USkeletalMeshComponent 自动算 inverse transpose,作为 uniform 上传。

### 3.4 · Rust 生态视角

`glam` 提供:

```rust
use glam::{Mat3, Mat4};
let model: Mat4 = ...;
let normal_mat: Mat3 = model.inverse().transpose();  // 注意先 inverse 再 transpose
// 或 glam 的专用方法:
// (glam 没有,需要手动)
```

注意:`Mat4.inverse().transpose()` 得到 Mat4,但法线只需要 Mat3——提取左上 3×3 部分(假设 model 没有透视投影)。

`glam::Mat4::truncate()` 返回 Mat3(左上 3x3)。完整流程:

```rust
let model: Mat4 = sprite.model_matrix();
let model_3x3: Mat3 = model.truncate();  // 提取旋转+缩放部分(丢平移)
let normal_mat: Mat3 = model_3x3.inverse().transpose();
```

为什么先 inverse 再 transpose?数学上 `(M⁻¹)ᵀ = (Mᵀ)⁻¹`,两种顺序都可以。但 glam 的 `Mat4.inverse()` 比 `transpose()` 慢得多(逆矩阵涉及行列式计算),所以先 inverse 再 transpose 更高效(顺序无所谓但 inverse 是瓶颈)。同时,在数值精度上,某些库的 inverse 实现对转置输入更稳定——通常先 inverse。

**bevy 的实现**:

```rust
// bevy_render/src/mesh/mesh/mod.rs (简化)
impl Mesh {
    pub fn inverse_transpose_model_matrix(&self) -> Mat3 {
        let model = self.model_matrix();
        model.inverse().transpose()
    }
}
```

Bevy 自动算 inverse transpose 并作为 uniform 上传,用户不用手动管。

- **归一化** — 法线必须是单位向量

## 5 · 对照与变奏

### 5.1 直接 M vs (M⁻¹)ᵀ 的差异(具体数值)

考虑 Model = diag(2, 4, 1),原法线 (0.6, 0.8, 0):

- 直接 M:(1.2, 3.2, 0),归一化 (0.35, 0.94, 0)
- (M⁻¹)ᵀ = diag(0.5, 0.25, 1):(0.3, 0.2, 0),归一化 (0.83, 0.55, 0)

完全不同方向!光照结果天差地别。

### 5.2 旋转的特殊性

Model = 旋转矩阵 R(θ),原法线 (0.6, 0.8, 0):

- 直接 R(θ):法线旋转 θ
- (R(θ)⁻¹)ᵀ = (R(θ)ᵀ)ᵀ = R(θ):也是旋转 θ

两者一样!所以**旋转不需要 (M⁻¹)ᵀ**——直接用 R 就行。

但只要加了任何非均匀缩放,就必须重新算 (M⁻¹)ᵀ。

### 5.3 均匀缩放的边界情况

Model = uniform_scale(s) = diag(s, s, s)。`(M⁻¹)ᵀ = diag(1/s, 1/s, 1/s)`。法线乘这个 = `n / s`,归一化后 = `n`。**均匀缩放不影响法线方向**(只影响长度,归一化恢复)。

所以均匀缩放时光照正确,即便不用 `(M⁻¹)ᵀ`。这是为什么有些 sprite 引擎"看起来没 bug"——他们只用均匀缩放。一旦加非均匀缩放(不同的 x/y 缩放),bug 出现。

### 5.4 历史背景

`(M⁻¹)ᵀ` 公式由 Eric Haines 和 James Arvo 在 1990 年的 Graphics Gems 系列明确推导。但在那之前,Foley & van Dam 1982 年的《Fundamentals of Interactive Computer Graphics》已经隐含讨论。这个公式 40 年不变——但今天仍被教程跳过。

工业引擎的演进:
- **OpenGL 1.x(1992)**:固定管线,glNormal 用 modelview 变换——但 OpenGL 内部自动用 inverse transpose,用户不用操心。
- **OpenGL 2.0+(2004)**:可编程 shader,用户必须自己传 normal_matrix。
- **Direct3D 9(2002)**:固定管线,类似 OpenGL 1.x。
- **Direct3D 10+(2006)**:可编程 shader,用户自己管 normal_matrix。

Casey HH 是 software renderer(纯 CPU),所以 normal_matrix 完全手算。学完 HH 后切 GPU,概念相同,只是把矩阵乘法移到 shader。

### 5.5 镜面反射的特殊性

Phong shading 的镜面反射需要 `reflect(light_dir, normal)`。如果 normal 错(没用 `(M⁻¹)ᵀ`),reflect 也错——但镜面反射对法线方向更敏感(高光 spot 很小),所以视觉上更明显。Casey HH 的 sprite 如果有强高光(金属表面),bug 会非常明显。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 sprite 没缩放时,法线变换可以省略 `(M⁻¹)ᵀ`?

**参考解答**:无缩放时,Model 矩阵的左上 3×3 部分是旋转(正交)。正交矩阵的逆 = 转置,所以 `(M⁻¹)ᵀ = ((M)ᵀ)ᵀ = M`。直接用 M 等价于用 `(M⁻¹)ᵀ`,可以省略。

**参考解答**:见 §2 完整代码。

### Lv3 · 迁移设计

**题**:3D 模型的法线贴图,TBN 变换也要考虑。具体来说:
- 切线 T 沿纹理 u 方向,直接乘 Model
- 副切线 B 沿纹理 v 方向,直接乘 Model
- 法线 N 必须乘 `(Model⁻¹)ᵀ`

TBN 三向量构成的矩阵,如果只对 N 用 `(Model⁻¹)ᵀ`,T 和 B 用 Model,TBN 不再正交。怎么修复?

提示:正确做法是用 `TBN_world = [T_world | B_world | N_world]`,其中 T_world、B_world 是 model · T、model · B(归一化),N_world 是 (model⁻¹)ᵀ · N(归一化)。然后用 TBN_world 把 tangent_space_normal 变到 world space。

fn render_sprite_correct(
    fb: &mut LinearFramebuffer,
    sprite: &Sprite,
    model_rot_scale: Mat3,  // sprite 的旋转 + 缩放(不含平移)
    origin: Vec2,
    light: Light,
    view: Vec3,
    config: RenderConfig,
) {
    let inv_model = model_rot_scale.inverse().expect("Model must be invertible");
    let normal_matrix = inv_model.transpose();
    // AABB 计算
    let (min_x, max_x, min_y, max_y) = compute_aabb(&origin, &model_rot_scale, fb.width, fb.height);

    for py in min_y..=max_y {
        for px in min_x..=max_x {
            let (u, v) = match pixel_to_uv(PixelCoord { px, py }, origin, model_rot_scale.inverse().unwrap()) {
                Some(uv) => uv,
                None => continue,
            };
            let sample = sprite.sample_surface(u, v);
            if sample.alpha < config.alpha_threshold { continue; }

            // 关键:法线变换用 (M⁻¹)ᵀ
            let world_normal = normal_matrix.mul_vec(sample.normal).normalized();

            let lit = phong_lighting(
                sample.color, world_normal, view, light,
                config.ambient, config.shininess,
            );
            let bg = fb.pixels[py * fb.width + px];
            fb.pixels[py * fb.width + px] = blend_premul_linear(bg, lit, sample.alpha);
        }
    }
}

### Troubleshooting

- **光照在缩放方向反** — 确认法线变换用 `(M⁻¹)ᵀ`,不是 `M`
- **法线变换后长度不等于 1** — 正常,因为 `(M⁻¹)ᵀ` 不保长。归一化即可

### 8.3 数学验证:精确数值

测试 Model = diag(2, 4, 1),原法线 (0.6, 0.8, 0):

```rust
fn main() {
    let scale = Mat3::from_scale(2.0, 4.0, 1.0);
    let n = Vec3::new(0.6, 0.8, 0.0);

    // 错误:直接乘 Model
    let wrong = scale.mul_vec(n);
    println!("wrong: {:?}, length={}", wrong, wrong.length());
    // 输出:wrong: (1.2, 3.2, 0.0), length=3.42
    // 归一化:(0.35, 0.94, 0.0) - 几乎朝上

    // 正确:用 (M⁻¹)ᵀ
    let normal_mat = scale.inverse().unwrap().transpose();
    let right = normal_mat.mul_vec(n).normalized();
    println!("right: {:?}", right);
    // 输出:right: (0.83, 0.55, 0.0) - 45° 倾斜
    // 完全不同的方向!光照结果天差地别
}
```

差异在光照上是直接的:假设光从上方来 `(0, 1, 0)`:
- 错误:`dot((0.35, 0.94, 0), (0, 1, 0)) = 0.94` - 很亮
- 正确:`dot((0.83, 0.55, 0), (0, 1, 0)) = 0.55` - 中等

光照差 1.7 倍。视觉上,错误版"过亮",正确版"自然"。
