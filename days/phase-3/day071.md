
# Day 071 · 转换为完整 3D 定位

> 你的小人在屏幕上能跑能跳,但他被困在一张「平面纸」上。今天 Casey 把这张纸抬起来——加上第三根轴,小人从此能上楼下楼、能跳过头顶、能让楼上的怪和楼下的玩家互不干扰。这一根额外的轴,就是从 2D 到 2.5D 的全部魔法。

## 0 · 为什么要有这一天

你跟了 Phase 2 的 45 天。你的小人现在能跑、能跳、能撞墙、能攻击。地图上摆了一堆怪,玩家走到攻击范围,扣血。得分在右上角跳。一切看起来都好。

但你想加一个新功能:**两层楼的副本**。一楼有怪,二楼有宝箱,玩家要走楼梯上去。

你坐下来开始写。第一行代码:`if player.x == 100 && player.y == 200 { /* 到楼梯口了,上楼 */ }`。然后呢?你要把玩家「传送」到二楼的某个坐标?那玩家的视觉跳跃感怎么来?一楼的怪会不会继续追上来?如果玩家正在二楼,一楼的怪还能不能打他?

你立刻意识到:**之前的二维坐标 `(x, y)` 根本无法表达「高度」这件事**。两个 entity 在屏幕上同一个位置,可能是「玩家站在地板上,头上有只鸟」,也可能是「玩家在二楼,楼下有只怪」。这两种情况在 2D 看完全一样,在游戏规则里却天差地别。

Casey 给出的解法很直接也很硬核:**给每个 entity 加一根 z 轴,代表「它所在的高度」**。z=0 是一楼地板,z=64 是二楼地板。两个 entity 在 (x, y) 上重叠,只要 z 差够大,就互不碰撞。

这种「俯视角度保留,但允许 z 维度」的玩法,业界叫 **2.5D**(读作「two-and-a-half D」)。它和真 3D 的差别是:摄像机始终俯视,你看到的画面仍然是 2D 的,但游戏规则是 3D 的——上下楼梯、跳跃、楼层、跳过头顶这些 3D 玩法都成立。**Zelda: A Link to the Past**、**Dark Souls 的部分室内场景**、**Diablo**、**Hades** 都是 2.5D。

心理锚点:看完今天,你能在自己的 Rust 项目里实现「两个 entity 屏幕位置相同但不碰撞」(因为 z 不同)。你能向队友解释为什么 `Vec3` 比 `(x, y, z)` 三个变量好。你能用 30 秒说清「2.5D 和 3D 的差别在哪」。

## 1 · Casey 今天做了什么

Casey 今天做了一个**类型层面的迁移**:把游戏里所有 entity 的位置从 2D 向量 `Vec2 { x, y }` 升级为 3D 向量 `Vec3 { x, y, z }`。这看似只是加一个字段,但牵一发动全身:

1. **位置字段改类型**:`Entity.p: Vec2` → `Entity.p: Vec3`。所有读写位置的地方都要适配。
2. **碰撞函数签名**:Day 050 的 `minkowski_aabb(a: &Entity, b: &Entity)` 内部假设 2D。今天加 z 维度比较:`dz.abs() < a.hz + b.hz`。一行代码,但意义重大——不同 z 的 entity 直接判 false。
3. **`z` 的语义**:Casey 反复强调 z 是**高度**(height),不是远近(depth)。在 2.5D 游戏里,远近是用屏幕 y 表达的(俯视角下,y 大的远),所以 z 只表示「楼层 / 跳跃高度」。这一区分很关键,因为后面 Day 108 的真 3D 透视投影里 z 才表示深度。
4. **跳跃初版**:小人的 z 现在可以随时间变化。Phase 2 的「跳跃」其实是改 y(屏幕坐标)。今天起,跳跃就是改 z(物理高度),y 不动。
5. **保留 2D 渲染**:渲染层**完全不动**,仍然把所有 entity 按 (x, y) 画到屏幕上。z 只影响**碰撞和游戏逻辑**。这是 2.5D 的核心:游戏是 3D 的,画面是 2D 的。

Casey 没有立即加楼梯、加多楼层建筑。他先把这个**类型基座**铺好,后面 Day 072-080 一点点把功能堆上来。

## 2 · 心智模型

### 费曼类比:把 2D 游戏想成一张平面地图,2.5D 是给这张地图加了「透明塑料片」

想象你有一张城市地图(2D):街道、建筑、广场,都画在一张纸上。两个 token(代表玩家、怪物)放在同一格上,他们就重叠,必须碰撞。

现在你把这张纸变成**一摞透明塑料片**:第一层是「地板高度 0」,第二层是「地板高度 64」(单位是像素)。每个 token 不再只放在 (x, y) 上,而是放在 (x, y, **层**)。两个 token 在 (100, 200) 重叠时,**先比较层**:同一层才碰撞,不同层各管各。

**这就是 z 轴的全部直觉**。它就是「透明塑料片的层数」。

### 严谨原理:从 Vec2 到 Vec3

#### 2.1 Vec2 的回顾

Phase 2 你写的 Vec2 长这样:

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec2 {
    x: f32,  // 屏幕/世界水平方向
    y: f32,  // 屏幕/世界垂直方向(俯视角度下,y 大 = 远)
}
```

所有运算:加(add)、减(sub)、乘标量(mul)、点积(dot)、长度(length)。这套你 Phase 2 应该写过至少一遍。

#### 2.2 Vec3 的定义

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec3 {
    x: f32,  // 世界水平(东)
    y: f32,  // 世界垂直,俯视角度下也是屏幕的垂直(北 = 远)
    z: f32,  // 高度(垂直于地面)
}
```

**注意 x/y/z 的语义约定**:不同的游戏有不同的轴约定。Casey 的 HH 用的是**「y 是水平方向(北),z 是高度」**。另一些约定(比如 OpenGL)是**「y 是高度,x/z 是地面」**。约定本身不重要,**重要的是整个项目一致**。我们跟 Casey 的约定。

#### 2.3 Vec3 的基本运算

```rust
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self {
        Self { x, y, z }
    }

    // 加:位移合成,和 Vec2 一样,只是多一个分量
    fn add(self, o: Self) -> Self {
        Self::new(self.x + o.x, self.y + o.y, self.z + o.z)
    }

    fn sub(self, o: Self) -> Self {
        Self::new(self.x - o.x, self.y - o.y, self.z - o.z)
    }

    fn mul(self, k: f32) -> Self {
        Self::new(self.x * k, self.y * k, self.z * k)
    }

    // 长度:三维勾股定理 √(x²+y²+z²)
    fn length(self) -> f32 {
        (self.x * self.x + self.y * self.y + self.z * self.z).sqrt()
    }

    // 归一化:除以长度,得到单位向量
    fn normalized(self) -> Self {
        let len = self.length();
        if len > 1e-6 { self.mul(1.0 / len) } else { Self::new(0.0, 0.0, 0.0) }
    }

    // 点积:对应分量相乘再相加
    fn dot(self, o: Self) -> f32 {
        self.x * o.x + self.y * o.y + self.z * o.z
    }

    // 叉积:三维专属运算,结果垂直于 self 和 o
    fn cross(self, o: Self) -> Self {
        Self::new(
            self.y * o.z - self.z * o.y,
            self.z * o.x - self.x * o.z,
            self.x * o.y - self.y * o.x,
        )
    }
}
```

**每行解释**:
- `length` 用三维勾股定理。`Vec2` 是 `√(x²+y²)`,`Vec3` 是 `√(x²+y²+z²)`。这就是从原点到 (x,y,z) 的直线距离——三维空间里勾股定理的推广。
- `dot` 在 Vec3 里就是再加一项 `z*o.z`。点积的几何意义不变:`a·b = |a||b|cos(θ)`,θ 是 a 和 b 的夹角。
- `cross` 是**三维专属**的运算。结果是个新向量,**垂直于** self 和 o 张成的平面。右手定则:右手食指指向 self,中指弯向 o,大拇指就是 cross 的方向。**游戏里干嘛用?** 算三角形的法线、判定 3D 里两条线段是否相交、计算力矩。Phase 3 暂时用得少,Phase 6 光照里大量用。

#### 2.4 为什么用 Vec3 而不是 `(f32, f32, f32)`

这是一个**重要**的工程问题,值得多花一段话。

如果你用裸 tuple `(f32, f32, f32)`,你的代码会变成:

```rust
let p1 = (10.0, 20.0, 0.0);
let p2 = (15.0, 22.0, 0.0);
// 算 p1 + p2
let p3 = (p1.0 + p2.0, p1.1 + p2.1, p1.2 + p2.2);
```

每次写运算你都要拆开重组。三个分量还能忍,六个分量(速度+加速度)就乱了。Vec3 把「三个相关分量」绑成一个**类型**,然后给类型加方法——这就是 Rust 的**类型驱动**思维。

更重要的:类型让你写**有意义的代码**。`p1.add(p2)` 比 `(p1.0+p2.0, ...)` 更接近问题的本质——「两个位移相加」。代码读起来更像数学,bug 也少。

Casey 在 C 里也手写 Vec3 struct,正是这个原因。Rust 的优势是 trait(`Add`、`Sub`、`Mul`)让你写 `p1 + p2` 这种**自然**的语法,编译器自动找你实现的 `Add` trait。

#### 2.5 碰撞检测的 3D 化:从矩形到长方体

回顾 Day 050 的 2D AABB 碰撞(Minkowski 差的几何意义):

```
两个 2D AABB 重叠 ⟺ |a.cx - b.cx| < a.hx + b.hx
                  且 |a.cy - b.cy| < a.hy + b.hy
```

`cx` 是中心 x,`hx` 是 half-x(矩形宽度的一半)。

3D AABB 只要多加一个 z 的判断:

```
两个 3D AABB 重叠 ⟺ |a.cx - b.cx| < a.hx + b.hx
                  且 |a.cy - b.cy| < a.hy + b.hy
                  且 |a.cz - b.cz| < a.hz + b.hz
```

这就是「长方体相交」的判定。直觉:两个长方体相交 ⟺ 它们在 x、y、z **三个轴上各自**的投影都重叠。

代码:

```rust
#[derive(Copy, Clone, Debug)]
struct AABB3 {
    center: Vec3,  // 长方体的中心
    half: Vec3,    // 长方体的「半尺寸」(half_x, half_y, half_z)
}

fn aabb3_overlap(a: AABB3, b: AABB3) -> bool {
    let d = a.center.sub(b.center);
    let sum_half = a.half.add(b.half);
    d.x.abs() < sum_half.x
        && d.y.abs() < sum_half.y
        && d.z.abs() < sum_half.z
}
```

**为什么用 `<` 而不是 `<=`?** 边界相切不算碰撞——这是工程约定。如果想算「贴在一起」也算碰,改 `<=`。

#### 2.6 多楼层的关键:z 分层让两个 entity 不碰

假设玩家在 `(100, 200, 32)`,height=64(即 half_z=32,从 z=0 到 z=64)。一只怪在 `(100, 200, 128)`,height=64(z 从 96 到 160)。两个 entity 在屏幕 (100, 200) 完全重叠。

```rust
let player = AABB3 {
    center: Vec3::new(100.0, 200.0, 32.0),
    half: Vec3::new(16.0, 16.0, 32.0),  // 32x32 底面,64 高
};
let monster = AABB3 {
    center: Vec3::new(100.0, 200.0, 128.0),
    half: Vec3::new(16.0, 16.0, 32.0),
};
// dz = |32 - 128| = 96; sum_half.z = 32 + 32 = 64
// 96 < 64? 否 → 不碰撞
```

**这就是多楼层游戏的核心机制**。Phase 2 里两个 entity 在屏幕同一位置必须碰,因此「楼上楼下」根本没法实现。今天你用 z 维度把它们隔开了。

#### 2.7 为什么 2.5D 不需要透视投影

真 3D 游戏里,远的物体看起来小——这需要**透视投影**(Day 108 的主题)。但 2.5D 不需要:摄像机俯视,所有 entity 都投影到屏幕的 (x, y),z 不影响屏幕位置。

这就是为什么 Casey 现在能很快加 z 轴:他**没有动渲染层**。游戏逻辑用 Vec3,渲染层用 Vec2(投影时丢弃 z)。Day 107 加 Z 层渐隐时,z 才开始影响渲染(高 z 的层半透明),但仍然是 2D 渲染。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

2.5D 是游戏开发里一个**独立的设计选择**,不是「不完整的 3D」。它有自己的优势:

**优势 1:关卡设计直观**。俯视角度让玩家一眼看全局,关卡设计师不用考虑摄像机遮挡,楼梯、平台、坑洞用 2D tile 思路就能搭。

**优势 2:美术便宜**。每个 entity 只要画一张 sprite(2D 图),不用建 3D 模型。Casey 的 HH 整个 Phase 3 都是 sprite + 法线贴图模拟立体感。

**优势 3:碰撞简单**。2.5D 的碰撞仍是 AABB3(轴对齐长方体),不用旋转的 OBB(方向包围盒)。Day 078 加多碰撞体积后,即使 Boss 的复杂形状也能用一组 AABB3 近似。

**劣势:深度表达有限**。玩家很难直观感受「这个台阶多高」。Casey 用阴影投射、Z 层渐隐(Day 107)等技巧弥补。

经典 2.5D 游戏:
- **Zelda: A Link to the Past**(SFC,1991):上下两层,从悬崖跳下。
- **Diablo 系列**:俯视角度,有楼梯和高度差。
- **Hades**(2020):2.5D,有立体感的法线贴图。
- **Stardew Valley**:基本 2D,但矿洞里有「层」概念。

Casey HH 的目标是 2.5D——保留俯视玩法,加 z 轴让世界立体。这跟 Zelda 一脉相承。

### 3.2 · 🎨 图形学视角

Vec3 在图形学里有几个**完全不同**的用途,初学者常混淆。今天必须分清:

| Vec3 的语义 | 在 HH 里出现在哪 | 备注 |
|---|---|---|
| **位置**(position) | Day 071+ entity 位置 | 指向世界空间某点 |
| **方向**(direction) | Day 096 光源方向、Day 097 法线 | 单位向量,无位置 |
| **位移**(displacement) | 速度 × dt | 两个位置的差 |
| **颜色 RGB** | Day 094 颜色运算 | 三通道,可以视作 Vec3 |
| **法线贴图采样** | Day 097 | XYZ 编码法线方向 |

**容易混淆的陷阱**:同样的 `Vec3`,在物理代码里表示位置,在颜色代码里表示 RGB——它们数学上一样,但**语义不同**。一些 Rust 库(如 `glam`)直接共用一个 Vec3 类型;更严谨的做法(如 `cgmath`、`nalgebra`)用**类型标记**:`Point3<f32>` vs `Vector3<f32>` vs `Color3<f32>`。Casey HH 用最朴素的统一 Vec3,但在变量命名上区分:`p` 表示 position,`v` 表示 velocity,`n` 表示 normal。

图形学里 Vec3 的另一个重要用途是 **3D 旋转**——但不是直接旋转,而是用**四元数(quaternion)**。Day 361+ 才会进入这个话题。现在你只需要知道:Vec3 加一个角度足够表达 2.5D 的所有朝向(绕 z 轴转)。

### 3.3 · 🐧 Linux 系统编程视角

Vec3 是个**纯 CPU 内存结构**,跟 Linux 没直接关系。但有两个 Linux 相关的边角:

**1. Vec3 的内存布局对齐**

```rust
#[repr(C)]
struct Vec3 { x: f32, y: f32, z: f32 }
// 大小 12 字节,但 Rust 默认对齐到 4 字节
```

如果你想 SIMD 加速(Day 112+),Vec3 的 12 字节是个尴尬尺寸——SSE 寄存器是 16 字节,加载 12 字节 vec3 要么 padding 到 16 字节(`Vec4`),要么用 `_mm_loadu_ps` 加载多余 4 字节(可能 segfault)。Casey 后期会换成**Vec4 + padding**,即使 w 字段不用。这是性能 vs 内存占用的权衡。

**2. Linux 上测 Vec3 性能**

```bash
# 写一个加法循环 1 亿次,看耗时
cat > /tmp/vec3_bench.rs << 'EOF'
#[derive(Copy, Clone)]
struct Vec3 { x: f32, y: f32, z: f32 }

fn main() {
    let mut v = Vec3 { x: 1.0, y: 2.0, z: 3.0 };
    let d = Vec3 { x: 0.001, y: 0.002, z: 0.003 };
    for _ in 0..100_000_000 {
        v.x += d.x;
        v.y += d.y;
        v.z += d.z;
    }
    println!("{}", v.x);
}
EOF
rustc -O /tmp/vec3_bench.rs -o /tmp/vec3_bench
time /tmp/vec3_bench
# 应该在 50-100ms 之间
```

`perf stat` 看每条加法的指令数:

```bash
perf stat -e instructions,cycles /tmp/vec3_bench
```

这种「从 Rust 源码到 cycle 数」的追踪能力,Linux 是得天独厚的。Phase 4 性能优化阶段会大量用。

### 3.4 · 🦀 Rust 生态视角

#### Rust 表达 Vec3 的几种风格

**风格 A:Casey 风格(手写,plain struct)**

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
pub struct Vec3 {
    pub x: f32,
    pub y: f32,
    pub z: f32,
}

impl std::ops::Add for Vec3 {
    type Output = Vec3;
    fn add(self, rhs: Self) -> Self {
        Self { x: self.x + rhs.x, y: self.y + rhs.y, z: self.z + rhs.z }
    }
}

impl std::ops::AddAssign for Vec3 {
    fn add_assign(&mut self, rhs: Self) {
        self.x += rhs.x;
        self.y += rhs.y;
        self.z += rhs.z;
    }
}

impl std::ops::Sub for Vec3 {
    type Output = Vec3;
    fn sub(self, rhs: Self) -> Self {
        Self { x: self.x - rhs.x, y: self.y - rhs.y, z: self.z - rhs.z }
    }
}

impl std::ops::Mul<f32> for Vec3 {
    type Output = Vec3;
    fn mul(self, k: f32) -> Self {
        Self { x: self.x * k, y: self.y * k, z: self.z * k }
    }
}

// 你还需要:Neg, Mul<Vec3> (component-wise), Div<f32>, Index, IndexMut
```

**优点**:完全控制内存布局,可加 `#[repr(C)]`、`#[repr(align(16))]`,可手写 SIMD,无依赖。**缺点**:几十行 trait 实现,容易漏。

**风格 B:用 `glam` crate**(工业级)

```toml
[dependencies]
glam = "0.29"
```

```rust
use glam::Vec3;
let v = Vec3::new(1.0, 2.0, 3.0);
let w = v + Vec3::new(0.1, 0.2, 0.3);
```

`glam` 是 Bevy 引擎的默认数学库。SIMD 优化好,WASM/SSE/NEON 全覆盖。**缺点**:黑盒,看不到内部布局。Phase 5 之后可以切。

**风格 C:用 `cgmath` / `nalgebra`**(科学计算风格)

`nalgebra` 区分 `Point3` 和 `Vector3`(语义不同),编译器帮你抓 bug。但泛型带来编译时间和性能开销,游戏不推荐。

#### 推荐路径(和 Phase 2 一致)

- **Phase 1-3**(学原理):手写,理解每一行
- **Phase 4-5**(性能 / 工程化):手写 + 局部 SIMD
- **Phase 6+**(实际项目):手写核心 + glam 做周边

#### ownership 和 lifetime

Vec3 是 `Copy`(12 字节),函数传递用值,不用 `&Vec3`:

```rust
// 推荐
fn add(a: Vec3, b: Vec3) -> Vec3 { a + b }

// 反模式(Copy 类型用引用)
fn add(a: &Vec3, b: &Vec3) -> Vec3 { **a + **b }
```

#### Rust 的 const generics(可选高阶知识)

如果你想要一个泛型向量(支持 2D/3D/4D):

```rust
struct VecN<const N: usize>([f32; N]);

impl<const N: usize> VecN<N> {
    fn dot(self, other: Self) -> f32 {
        self.0.iter().zip(other.0.iter()).map(|(a, b)| a * b).sum()
    }
}
```

这叫 **const generics**(常量泛型)。学习用可以,生产代码一般直接写 `Vec2`/`Vec3`/`Vec4`(不泛型)更清晰、更易 SIMD 化。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **向量空间 / 线性空间** —— Vec3 是三维实数空间 ℝ³ 的元素
- **坐标变换** —— Vec3 是被 4×4 矩阵变换的对象(Day 101+ 详讲)
- **碰撞检测** —— Vec3 是 entity 的「位置」数据,碰撞算法基于位置比较
- **刚体动力学** —— 位置 / 速度 / 加速度三个 Vec3,共同描述运动

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Vec2 + height 字段 | 把高度作为附加字段,不融入向量运算 | z 几乎不参与运算(纯条件判断) | ❌ |
| Vec3 统一 | 三轴一体,所有向量运算一致 | z 经常参与(跳跃、楼梯、3D 碰撞) | ✅ |
| Vec4 + w=1 | 齐次坐标(homogeneous),为矩阵变换准备 | 即将上矩阵变换 | Day 101+ 切换 |

### 4.3 下级(内部零件)

- **三个 f32 分量** —— Vec3 的物理存储,12 字节
- **加减乘除运算** —— Vec3 上的算术
- **length / normalize / dot / cross** —— 几何派生运算
- **AABB3(轴对齐长方体)** —— 用 Vec3 表达的碰撞体积
- **位置 vs 方向 vs 位移** —— 同样的 Vec3,不同语义

## 5 · 对照与变奏

### 2D vs 2.5D vs 3D

| 维度 | 2D | 2.5D | 3D |
|---|---|---|---|
| entity 位置 | Vec2 | Vec3(z 表示高度) | Vec3(z 表示深度) |
| 渲染 | 直接 (x,y) → 屏幕 | 直接 (x,y) → 屏幕,z 只影响透明度 | 透视投影 |
| 碰撞 | 矩形 | 长方体(轴对齐) | 长方体 / OBB / mesh |
| 摄像机 | 固定俯视 | 固定俯视 | 自由旋转 |
| 代表作 | Mario 1 | Zelda ALTTP | Mario 64 |

### 多轴约定的混乱

业界至少有 4 种主流坐标轴约定,初学者经常混淆:

| 约定 | 上 | 前 | 右 | 用谁 |
|---|---|---|---|---|
| Casey HH / Unreal | +Z | +X | +Y | 游戏开发(左系) |
| OpenGL / Blender | +Y | -Z | +X | 图形学 |
| Unity | +Y | +Z | +X | Unity 引擎 |
| DirectX / Vulkan 的 NDC | +Y | +Z(0 到 1) | +X | GPU |

**Casey HH 选「z 向上」**,因为游戏开发的直觉——玩家在地面走路,「上」就是天。我们跟 Casey。

### Vec2 → Vec3 → Vec4 的演化

数学上,从 n 维到 n+1 维不是「凑一个字段」,而是为某个具体目的服务的:

- Vec2 → Vec3:加 z 为了表达高度 / 深度
- Vec3 → Vec4:加 w(齐次坐标)为了把**平移**也用矩阵乘法表达(矩阵乘法是线性的,平移是仿射的,加 w=1 才能统一)

Day 101 的 4×4 变换矩阵会用到。现在不展开。

**参考解答**:渲染层做的是把世界坐标 (x, y) 投影到屏幕坐标,Phase 2 用的是正交投影(orthographic),即 x→screen_x、y→screen_y 直接对应,没有「远的物体变小」。所以渲染层**只关心 (x, y)**,z 是「多余的」。今天 z 只用于游戏逻辑(碰撞、跳跃),不影响屏幕位置,渲染层一行不用改。这就是「游戏层 / 渲染层分离」(Day 026)的红利——一次架构决策,后期省下大量改动。

### Lv2 · 动手实践

**题**:在 Rust 项目里实现 `Vec3` 和 `AABB3`,写一个 `main`,做以下断言:
- `Vec3::new(1.0, 2.0, 2.0).length()` ≈ 3.0(勾股数 1-2-√5? 不是,这里就是 1+4+4=9,√9=3,对)
- `Vec3::new(1.0, 0.0, 0.0).cross(Vec3::new(0.0, 1.0, 0.0))` 应该 ≈ `Vec3::new(0.0, 0.0, 1.0)`(x 轴叉乘 y 轴 = z 轴,右手定则)
- 两个 3D AABB,z 差很大,不重叠;移近 z 后重叠

完成标准:`cargo run` 打印所有断言通过。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec3 { x: f32, y: f32, z: f32 }

impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y, self.z + o.z) }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y, self.z - o.z) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k, self.z * k) }
    fn dot(self, o: Self) -> f32 { self.x * o.x + self.y * o.y + self.z * o.z }
    fn cross(self, o: Self) -> Self {
        Self::new(
            self.y * o.z - self.z * o.y,
            self.z * o.x - self.x * o.z,
            self.x * o.y - self.y * o.x,
        )
    }
    fn length(self) -> f32 { self.dot(self).sqrt() }
    fn approx_eq(self, o: Self, eps: f32) -> bool {
        (self.x - o.x).abs() < eps && (self.y - o.y).abs() < eps && (self.z - o.z).abs() < eps
    }
}

#[derive(Copy, Clone, Debug)]
struct AABB3 { center: Vec3, half: Vec3 }

fn aabb3_overlap(a: AABB3, b: AABB3) -> bool {
    let d = a.center.sub(b.center);
    let s = a.half.add(b.half);
    d.x.abs() < s.x && d.y.abs() < s.y && d.z.abs() < s.z
}

fn main() {
    // 长度:1² + 2² + 2² = 9,sqrt = 3
    let v = Vec3::new(1.0, 2.0, 2.0);
    assert!((v.length() - 3.0).abs() < 1e-6, "length wrong");

    // 叉积:x × y = z(右手坐标系)
    let x = Vec3::new(1.0, 0.0, 0.0);
    let y = Vec3::new(0.0, 1.0, 0.0);
    let z = Vec3::new(0.0, 0.0, 1.0);
    assert!(x.cross(y).approx_eq(z, 1e-6), "cross wrong");

    // 3D AABB:z 差大不重叠
    let a = AABB3 {
        center: Vec3::new(0.0, 0.0, 0.0),
        half: Vec3::new(10.0, 10.0, 10.0),
    };
    let b_far = AABB3 {
        center: Vec3::new(0.0, 0.0, 50.0),
        half: Vec3::new(10.0, 10.0, 10.0),
    };
    assert!(!aabb3_overlap(a, b_far), "far should not overlap");

    let b_near = AABB3 {
        center: Vec3::new(0.0, 0.0, 15.0),
        half: Vec3::new(10.0, 10.0, 10.0),
    };
    assert!(aabb3_overlap(a, b_near), "near should overlap");

    println!("All assertions passed!");
}
```

**关键点**:
- `length` 用 `self.dot(self).sqrt()`,等价于 `(x²+y²+z²).sqrt()`,少写一次乘法
- `approx_eq` 自定义,因为浮点 `==` 不可靠
- AABB 测试:b_far 中心 z=50,a 半 z=10 + b 半 z=10 = 20,z 差 50 > 20,不重叠;b_near 中心 z=15,z 差 15 < 20,重叠

## 8 · Rust / Arch 落地代码

### 完整可跑的 Rust 代码

把 Lv2 的代码扩展,加上 sim region 内的多楼层碰撞示例。

```rust
// Cargo.toml: 空(纯 std)

#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec3 { x: f32, y: f32, z: f32 }

impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y, self.z + o.z) }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y, self.z - o.z) }
    fn dot(self, o: Self) -> f32 { self.x.mul_add(o.x, self.y.mul_add(o.y, self.z * o.z)) }
    // mul_add: 融合乘加,比 a*b+c 更快也更准(一次舍入)
}

// 一个最小的「多楼层」示例
#[derive(Clone, Debug)]
struct Entity {
    pos: Vec3,       // 世界位置
    half: Vec3,      // 碰撞体积的半尺寸
    name: &'static str,
}

fn entities_collide(a: &Entity, b: &Entity) -> bool {
    let d = a.pos.sub(b.pos);
    let s = a.half.add(b.half);
    d.x.abs() < s.x && d.y.abs() < s.y && d.z.abs() < s.z
}

fn main() {
    // 玩家在一楼地板上(z 中心 = 32,身高 64 → z 范围 0..64)
    let player = Entity {
        pos: Vec3::new(100.0, 100.0, 32.0),
        half: Vec3::new(16.0, 16.0, 32.0),
        name: "player",
    };

    // 一只怪在二楼(z 中心 = 96,身高 64 → z 范围 64..128)
    let monster_floor2 = Entity {
        pos: Vec3::new(100.0, 100.0, 96.0),
        half: Vec3::new(16.0, 16.0, 32.0),
        name: "monster_2f",
    };

    // 另一只怪在一楼(z 中心 = 32)
    let monster_floor1 = Entity {
        pos: Vec3::new(100.0, 100.0, 32.0),
        half: Vec3::new(16.0, 16.0, 32.0),
        name: "monster_1f",
    };

    println!("玩家 vs 2F 怪(屏幕重叠,z 差大):{}",
        entities_collide(&player, &monster_floor2));  // false
    println!("玩家 vs 1F 怪(同 z):{}",
        entities_collide(&player, &monster_floor1));  // true
}
```

**预期输出**:
```
玩家 vs 2F 怪(屏幕重叠,z 差大):false
玩家 vs 1F 怪(同 z):true
```
