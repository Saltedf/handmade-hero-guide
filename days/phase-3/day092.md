# Day 092 · 填充旋转与缩放的矩形

> 昨天你写了 2×2 旋转矩阵。今天 Casey 用它干一件真正有用的事:**画一个能旋转、能缩放、能任意摆放的矩形**——不是只能水平摆放的 AABB(axis-aligned bounding box)。听起来只是「在矩形上加个旋转角度」?不,这里有个 2D 光栅化的核心算法决定一切:**怎么遍历像素,判定哪些像素在旋转矩形里**。这个算法的思想明天(Day 093)会扩展到任意纹理四边形,Day 108+ 还会扩展到 3D 三角形光栅化。

## 0 · 为什么要有这一天

你的渲染器现在能做什么?画水平摆放的矩形——左上角 `(x, y)`、宽 `w`、高 `h`,你写一个双重循环遍历 `y in y..y+h, x in x..x+w`,把像素填上颜色。简单暴力。

可现在你想做这些事:
- 让一个**精灵**(sprite,游戏里的角色图片)面朝不同方向。最简单的实现就是**旋转 sprite**。
- 让 sprite 在不同距离**看起来有大有小**——缩放。
- 让 sprite 沿**任意方向**(不只是 x/y 轴)摆放——比如一面斜墙。

这时你立刻撞墙:**双重循环的边界 `(x..x+w, y..y+h)` 假设了矩形水平摆放**。一旦矩形旋转 30°,「水平遍历」会把不该填的像素也填上。

**两种解决方案**:

**方案 A:正向遍历**(for each pixel, test if inside rotated rect)
遍历屏幕上所有像素,对每个像素测试「是否在旋转矩形里」。这种叫 **inside test**(包含测试)。优点是简单直接,缺点是效率低——遍历整个屏幕,大部分像素不在矩形里,白白浪费 CPU。

**方案 B:逆向变换**(for each pixel in AABB of rotated rect, invert transform, test if in unit square)
旋转矩形的 bounding box(水平包围盒)很容易算。只遍历这个包围盒里的像素。对每个像素,**逆向应用 base 变换**(用矩阵的逆)把它变换回「未旋转、未缩放、未平移」的**单位矩形坐标** `[0, 1] × [0, 1]`。如果变换后的坐标在这个单位矩形里,就填颜色。这就是 Day 092 Casey 的核心思想,也是 Day 093 纹理采样的基础。

这个「**逆向变换 + 单位矩形测试**」是 2D 光栅化最强大的思想之一。它把「任意四边形」转化为「单位正方形」——所有形状的渲染都可以归约为「单位正方形渲染 + 变换」。GPU 的纹理采样本质上也是这个。

心理锚点:看完今天,你能用 Rust 画一个旋转任意角度的实心矩形。你能解释「为什么用矩阵逆而不是直接判断点在四边形里」。你能用 30 秒说清「AABB 遍历 + 逆变换」对比「全屏遍历 + 内嵌判断」的速度差别。

## 1 · Casey 今天做了什么

Casey 今天做的事情:

1. 把昨天的 `Base2D` 升级——`x_axis` 和 `y_axis` 允许是**任意长度**(不只是单位向量),代表缩放因子。
2. 算出旋转矩形的 **AABB**(轴对齐包围盒)——遍历像素时只遍历这个包围盒,而不是全屏。
3. 对包围盒内每个像素:
   - 减去 base origin,得到相对位移
   - 用 base 的**逆矩阵**变换回单位矩形坐标 `(u, v)`
   - 如果 `0 <= u <= 1` 且 `0 <= v <= 1`,填颜色
4. 实现细节:用昨天写的 `Mat2::inverse()` 做逆变换,正交矩阵的逆 = 转置(免费)。

Casey 强调这个算法是「**软件光栅化器的精髓**」——后面 Day 093 加纹理、Day 108 加透视投影、Day 200+ 改成 3D,核心循环都是「**遍历 AABB + 逆变换 + 单位坐标判断**」。

## 2 · 心智模型

### 费曼类比:在透明纸上画画再贴到墙上

想象你在一张透明的方格纸上画了一个矩形——坐标从 `(0, 0)` 到 `(1, 1)`(单位矩形)。然后你:
1. **缩放**这张纸(把它拉大成 2 倍)
2. **旋转**这张纸(转 30°)
3. **平移**这张纸(挪到墙上的 `(100, 50)`)

现在你想在墙上**填充这个变形后的矩形**。墙是像素网格。你怎么知道墙上的某个像素 `(x, y)` 是不是落在这个矩形里?

**反向思考**:把墙上的像素 `(x, y)` 「逆向」还原回透明纸上的原始坐标 `(u, v)`:
1. 减去平移:`(x, y) - (100, 50)` = 拿到墙上的相对位置
2. 逆向旋转:用旋转矩阵的逆(对正交矩阵就是转置)还原旋转
3. 逆向缩放:除以缩放因子

得到 `(u, v)` 后,看它是不是在 `[0, 1] × [0, 1]` 里。在 → 填颜色;不在 → 跳过。

这就是**逆向变换**的核心:正向变换把单位矩形扭曲成任意四边形,逆向变换把任意位置还原回单位矩形。

### 严谨原理

#### 2.1 Base 变换的代数表达

设 base = `{ origin: O, x_axis: X, y_axis: Y }`(X 和 Y 是任意长度的 2D 向量)。局部坐标 `(u, v) ∈ [0,1]²` 变换到世界坐标:

```
world = O + u * X + v * Y
```

写成矩阵:`world = M · (u, v, 1)`(用齐次坐标),其中:

```
M = | X.x  Y.x  O.x |
    | X.y  Y.y  O.y |
    | 0    0    1   |
```

#### 2.2 逆变换

要把 `world` 还原成 `(u, v)`,我们需要 `M⁻¹`:

```
(u, v, 1) = M⁻¹ · (world.x, world.y, 1)
```

**好消息**:如果 X 和 Y 都是单位向量(无缩放)且互相垂直(无错切),M 是**正交矩阵**加上平移分量。旋转部分的逆就是它的转置,**免费**。但 Day 092 我们允许 X 和 Y 是任意长度,所以需要一般 2×2 矩阵的逆——`det = X.x*Y.y - X.y*Y.x`,`inv = (1/det) · [[Y.y, -Y.x], [-X.y, X.x]]`(伴随矩阵除以行列式)。

**优化**:Casey 直接预先算好 `M⁻¹`,渲染时不需要每像素都算逆,只做矩阵乘法。这是关键优化——逆矩阵只算一次,渲染时只做乘法。

#### 2.3 AABB 计算

旋转矩形的 AABB 是「能包含它的最小水平矩形」。怎么算?

矩形 4 个角的世界坐标:

```
P0 = O + 0*X + 0*Y = O
P1 = O + 1*X + 0*Y = O + X
P2 = O + 1*X + 1*Y = O + X + Y
P3 = O + 0*X + 1*Y = O + Y
```

AABB:

```
min_x = min(P0.x, P1.x, P2.x, P3.x)
max_x = max(P0.x, P1.x, P2.x, P3.x)
min_y = min(P0.y, P1.y, P2.y, P3.y)
max_y = max(P0.y, P1.y, P2.y, P3.y)
```

遍历范围:`y in min_y..max_y, x in min_x..max_x`(像素整数坐标)。

#### 2.4 像素循环核心算法

```rust
// 预计算:base 的逆矩阵
let inv = base.rot.inverse().unwrap();
let inv_origin_offset = inv.mul_vec(base.origin.scale(-1.0));
// 等价:inv_origin_offset = inv · (-origin),这样 (u,v) = inv · world + inv_origin_offset
// 实际上更直接的做法是 (u,v) = inv · (world - origin),所以循环里减 origin 即可

for py in min_y..=max_y {
    for px in min_x..=max_x {
        // 当前像素的世界坐标(像素中心 +0.5)
        let wx = px as f32 + 0.5;
        let wy = py as f32 + 0.5;
        // 减 origin,然后乘逆矩阵,得到局部坐标
        let dx = wx - base.origin.x;
        let dy = wy - base.origin.y;
        let u = inv.m00 * dx + inv.m01 * dy;
        let v = inv.m10 * dx + inv.m11 * dy;
        // 测试是否在单位矩形 [0,1]²
        if u >= 0.0 && u <= 1.0 && v >= 0.0 && v <= 1.0 {
            framebuffer[py * width + px] = color;
        }
    }
}
```

**关键点 1:像素中心 `+0.5`**。像素 `(px, py)` 的「真实坐标」不是 `(px, py)`(那是像素左上角),而是 `(px + 0.5, py + 0.5)`(像素中心)。这避免了「直线在像素边界时一半像素半透明」的奇怪现象。

**关键点 2:`u, v` 范围 `[0, 1]`**。因为局部坐标定义在单位矩形 `[0,1]²` 里。如果你想让矩形是 `w × h`,就改成 `[0, w] × [0, h]`,或让 X 长度 = w、Y 长度 = h。

**关键点 3:整型 `px, py` vs 浮点 `wx, wy`**。`px, py` 是像素索引(整数,用于数组下标),`wx, wy` 是浮点坐标(用于矩阵运算)。这两套坐标系必须区分清楚。

#### 2.5 性能:为什么这个算法高效

对比两种遍历方式:

```
全屏遍历 + 内嵌判断:
for py in 0..height:
    for px in 0..width:
        if point_in_rotated_rect(px, py, ...):  # 每像素 4 次叉积
            framebuffer[..] = color
```

AABB 遍历 + 逆变换:
```
for py in min_y..max_y:
    for px in min_x..max_x:
        u, v = inverse(px, py)
        if 0 <= u <= 1 and 0 <= v <= 1:  # 4 次比较
            framebuffer[..] = color
```

如果屏幕是 1920×1080(2M 像素),矩形是 100×100(1 万像素):
- 全屏遍历:2M 次 point-in-rect 测试 = 8M 次叉积 ≈ 30ms
- AABB 遍历:AABB 大约 141×141(100*sqrt(2))≈ 2万次逆变换 ≈ 0.3ms

差 100 倍。这就是为什么光栅化器必须用 AABB 遍历,不能全屏遍历。

### Rust 完整实现

```rust
struct Framebuffer {
    width: usize,
    height: usize,
    pixels: Vec<u32>,   // 0xRRGGBB
}

impl Framebuffer {
    fn new(w: usize, h: usize) -> Self {
        Self { width: w, height: h, pixels: vec![0; w * h] }
    }
    fn put(&mut self, x: usize, y: usize, color: u32) {
        if x < self.width && y < self.height {
            self.pixels[y * self.width + x] = color;
        }
    }
}

#[derive(Copy, Clone)]
struct Mat2 { m00: f32, m10: f32, m01: f32, m11: f32 }
impl Mat2 {
    fn from_angle(t: f32) -> Self {
        let (s, c) = t.sin_cos();
        Self { m00: c, m10: s, m01: -s, m11: c }
    }
    fn from_scale_rot(sx: f32, sy: f32, theta: f32) -> Self {
        // 缩放后再旋转:R · S
        let r = Self::from_angle(theta);
        Self { m00: r.m00 * sx, m10: r.m10 * sx, m01: r.m01 * sy, m11: r.m11 * sy }
    }
    fn determinant(self) -> f32 { self.m00 * self.m11 - self.m01 * self.m10 }
    fn inverse(self) -> Self {
        let det = self.determinant();
        let inv_det = 1.0 / det;
        Self {
            m00: self.m11 * inv_det, m10: -self.m10 * inv_det,
            m01: -self.m01 * inv_det, m11: self.m00 * inv_det,
        }
    }
    fn mul_vec(self, x: f32, y: f32) -> (f32, f32) {
        (self.m00 * x + self.m01 * y, self.m10 * x + self.m11 * y)
    }
}

#[derive(Copy, Clone)]
struct Vec2 { x: f32, y: f32 }

fn fill_rotated_rect(fb: &mut Framebuffer, origin: Vec2, scale: (f32, f32), angle: f32, color: u32) {
    // 1. 构造 base 矩阵(旋转 + 缩放)
    let m = Mat2::from_scale_rot(scale.0, scale.1, angle);
    // 2. 算 4 个角的世界坐标
    let corners_local = [(0.0, 0.0), (1.0, 0.0), (1.0, 1.0), (0.0, 1.0)];
    let corners_world: Vec<(f32, f32)> = corners_local.iter().map(|(u, v)| {
        let (dx, dy) = m.mul_vec(*u, *v);
        (origin.x + dx, origin.y + dy)
    }).collect();
    // 3. AABB
    let min_x = corners_world.iter().map(|p| p.0).fold(f32::INFINITY, f32::min).floor() as i32;
    let max_x = corners_world.iter().map(|p| p.0).fold(f32::NEG_INFINITY, f32::max).ceil() as i32;
    let min_y = corners_world.iter().map(|p| p.1).fold(f32::INFINITY, f32::min).floor() as i32;
    let max_y = corners_world.iter().map(|p| p.1).fold(f32::NEG_INFINITY, f32::max).ceil() as i32;
    // 4. 预算逆矩阵
    let inv = m.inverse();
    // 5. 遍历 AABB 内像素
    let min_x = min_x.max(0) as usize;
    let max_x = (max_x as usize).min(fb.width - 1);
    let min_y = min_y.max(0) as usize;
    let max_y = (max_y as usize).min(fb.height - 1);
    for py in min_y..=max_y {
        for px in min_x..=max_x {
            let wx = px as f32 + 0.5;  // 像素中心
            let wy = py as f32 + 0.5;
            let dx = wx - origin.x;
            let dy = wy - origin.y;
            let (u, v) = inv.mul_vec(dx, dy);
            if u >= 0.0 && u <= 1.0 && v >= 0.0 && v <= 1.0 {
                fb.put(px, py, color);
            }
        }
    }
}

fn main() {
    let mut fb = Framebuffer::new(200, 200);
    // 在 (100, 100) 画一个 80x40、旋转 30° 的红色矩形
    fill_rotated_rect(&mut fb, Vec2 { x: 100.0, y: 100.0 }, (80.0, 40.0), 30.0_f32.to_radians(), 0xFF0000);
    // 统计填充像素数
    let count = fb.pixels.iter().filter(|&&p| p == 0xFF0000).count();
    println!("filled {} pixels", count);
    // 预期:80 * 40 = 3200 像素(旋转不改变面积)
    assert!((count as i32 - 3200).abs() < 100);
}
```

**逐段解释**:
- `from_scale_rot` — 缩放 + 旋转的复合矩阵。先缩放(把单位向量变长),再旋转(把向量转个角度)。数学上 `R · S`(先 S 后 R)。注意列主序存储。
- `inverse` — 2×2 矩阵逆。行列式 `det = ad - bc`,逆 = `(1/det) · adjugate`,adjugate 是「主对角互换、副对角取反」。
- 像素循环最里层只有 2 次乘加 + 4 次比较——非常快,可以 SIMD 化。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

旋转矩形渲染在 2D 游戏里几乎无处不在:

1. **角色 sprite**:角色面朝不同方向时,sprite 旋转(虽然 2D 游戏常通过「预先画好 8 方向 sprite」避免实时旋转,但实时旋转更灵活)
2. **粒子效果**:旋转的火花、烟雾、能量球
3. **UI 元素**:雷达扫描线、加载进度环、技能 CD 动画
4. **物理刚体**:箱子、球的运动轨迹

**坑:半透明边缘**。今天我们用「u,v 在 [0,1] 内」做硬判断(全填或全不填),边缘锯齿严重。Day 095 会引入**预乘 alpha**(premultiplied alpha)做抗锯齿。

**坑:超采样**。如果 sprite 缩小到小于 1 像素,直接采样会产生 moire(摩尔纹)。需要 **mipmap**(Day 093+ 会接触)。

### 3.2 · 🎨 图形学视角

今天的算法本质上是 **2D 光栅化**——把连续几何(旋转矩形)转换成离散像素。光栅化是 GPU 渲染管线的核心阶段之一(另一个是 fragment shading)。

GPU 的光栅化算法更高效——它不遍历 AABB 所有像素,而是用**扫描线算法**或**三角形分块(tile-based)**算法。但思想是相同的:「给定几何,确定哪些像素被它覆盖」。

**抗锯齿** 也可以加在今天算法上:把每个像素细分为 2×2 子像素,分别测试,取覆盖率作为 alpha 值。这就是 **MSAA**(multi-sample anti-aliasing)的 2D 版本。

**透视正确的纹理映射**:Day 093 我们会加纹理采样——给定 `(u, v)`,从纹理图查颜色。Day 108 加透视投影后,uv 不能直接插值,要除以 `w`(深度),叫「**透视正确插值**」。

### 3.3 · 🐧 Linux 系统编程视角

性能视角:

1. **CPU cache 友好**:像素循环按行遍历(`for y { for x }`),内存连续,cache 命中率高。如果你写 `for x { for y }`,每次跳一大段,cache miss 频繁,慢 5-10 倍。
2. **SIMD 友好**:`inv.mul_vec(dx, dy)` 是 2 个 f32 乘加,可以用 SSE `_mm_mul_ps` + `_mm_add_ps` 一次算 4 个像素(每个像素独立)。Casey Day 112+ 大量用。
3. **`perf` 分析**:

```bash
# 找到热点函数
perf record -g ./target/release/mat2_demo
perf report
# 如果 inverse 不在循环里,但 mul_vec 在,优化重点在 mul_vec
```

4. **多线程**:不同行可以并行渲染(行之间无依赖)。Day 200+ Casey 会用线程池渲染。

### 3.4 · 🦀 Rust 生态视角

Rust 写光栅化器有几个考虑:

**选择 1:帧缓冲数据结构**

```rust
// 简单版:Vec<u32>
struct Framebuffer { pixels: Vec<u32>, width: usize, height: usize }

// 高级版:typed pixel + 多缓冲
struct Framebuffer { pixels: Vec<Rgba8>, width: usize, height: usize }
```

`Rgba8` 是 `[u8; 4]`,显式表示 RGBA。游戏里常用 `Vec<u32>`(打包成 `0xRRGGBBAA`),因为 CPU 处理 u32 比 4 个 u8 快。

**选择 2:`unsafe` 边界**

```rust
fn put(&mut self, x: usize, y: usize, color: u32) {
    if x < self.width && y < self.height {
        self.pixels[y * self.width + x] = color;
    }
}
```

这里 `if` 边界检查每像素都做,占循环 ~10% 时间。可以预先 clamp 循环范围,把 `if` 移出:

```rust
let x_max = self.width.min(max_x + 1);
let y_max = self.height.min(max_y + 1);
for y in (min_y as usize).max(0)..y_max {
    for x in (min_x as usize).max(0)..x_max {
        // 不需要 if,保证 x/y 在范围内
        self.pixels[y * self.width + x] = color;
    }
}
```

Rust 编译器在 release 模式可能自动做这个优化(bounded loop optimization),但不保证。手写更稳。

**选择 3:`rayon` 并行化**

```rust
use rayon::prelude::*;
fb.pixels.par_chunks_mut(width).enumerate().for_each(|(y, row)| {
    for x in 0..width {
        // 渲染像素 (x, y)
    }
});
```

`rayon` 提供「数据并行」——把行分给不同 CPU 核。Day 200+ Casey 自己手写线程池,效果一样。

|---|---|---|---|
| AABB + 逆变换 | 任意四边形,逆矩阵一次预算 | 旋转/缩放矩形 | ✅ 今天选了 |
| 扫描线填充 | 按行算交点,效率高 | 多边形 / 复杂形状 | Day 200+ 用 |
| Edge function | GPU 用,三角形 barycentric | 三角形光栅化 | Day 230+ |
| SDF (signed distance field) | 字体渲染 / 形状并集 | UI 字体 / 矢量图 | 不用 |

### 4.3 下级

- **AABB 计算** — 包围盒,缩小遍历范围
- **逆矩阵 (inverse matrix)** — 逆向变换的代数基础
- **像素中心约定** — `+0.5` 偏移,避免边缘像素问题
- **范围 clamp** — 防止像素索引越界
- **SIMD 友好布局** — 一次处理多个像素

## 5 · 对照与变奏

### CPU 光栅化 vs GPU 光栅化

| | CPU 软渲染 | GPU 硬渲染 |
|---|---|---|
| 算法 | AABB + 逆变换 | Edge function + barycentric |
| 并行度 | 几个核(SIMD 4-16 路) | 几千个着色单元 |
| 适合 | 教学调试、UI、低分辨率 | 高分辨率 3D 场景 |
| 编程 | Rust / C++ | GLSL / HLSL / WGSL |

Casey HH 全程软渲染(Day 1-234),目的是教学——让你**完全理解每个像素怎么来**。Day 235+ 切 OpenGL 把光栅化搬 GPU。两条路相通——你今天写的算法,GPU 内部也在做,只是更高效。

### 旋转 vs 镜像

旋转 90° 不等于镜像。旋转是「绕中心转」,镜像是「沿轴翻」。旋转矩阵 `det = +1`,镜像矩阵 `det = -1`。**bug 来源**:有些 sprite 图片本身是镜像存储(比如角色面向左的图),你直接画就是反的;要在 base 里加镜像变换(让 x_axis = (-1, 0))。

### 整型像素 vs 子像素精度

游戏渲染时,如果精灵位置是整数像素,看起来「卡顿」(因为只能在像素网格上)。子像素精度让精灵位置是浮点,渲染时插值——更平滑。代价是每帧都要做插值。今天算法天然支持子像素精度——`origin` 是浮点。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:有人说「我直接遍历整个屏幕,对每个像素判断 `point_in_rotated_rect(px, py, ...)` 不就行了?」请用 2 个具体数字说明为什么这不是好主意。

**参考解答**:
1. **遍历范围太大**。1920×1080 屏幕 = 207 万像素。即使每个测试只要 10ns,总耗时 20ms。但你的帧预算只有 16ms(60 FPS)。直接超时。
2. **大部分像素不在矩形里**。100×100 矩形 = 1万像素。207 万次遍历里,99.5% 是浪费。AABB 遍历把范围缩到 ~140×140(AABB)≈ 2万次,效率提高 100 倍。

### Lv2 · 动手实践

**题**:扩展 `fill_rotated_rect`,加一个 `fill_rotated_rect_aa` 版本——每像素细分为 2×2 子像素,分别做包含测试,把覆盖率作为灰度(alpha)值。当像素部分在矩形里时,按覆盖率混色。

完成标准:画一个旋转 30° 的小矩形(比如 30×10 像素),边缘看起来比硬判断版本平滑(没有锯齿)。

**参考解答关键片段**:

```rust
fn fill_rotated_rect_aa(fb: &mut Framebuffer, origin: Vec2, scale: (f32, f32), angle: f32, color: u32) {
    let m = Mat2::from_scale_rot(scale.0, scale.1, angle);
    let inv = m.inverse();
    // AABB 略(同上)
    // ...
    let samples = [(0.25, 0.25), (0.75, 0.25), (0.25, 0.75), (0.75, 0.75)];
    for py in min_y..=max_y {
        for px in min_x..=max_x {
            let mut hits = 0;
            for (sx, sy) in samples.iter() {
                let wx = px as f32 + sx;
                let wy = py as f32 + sy;
                let (u, v) = inv.mul_vec(wx - origin.x, wy - origin.y);
                if u >= 0.0 && u <= 1.0 && v >= 0.0 && v <= 1.0 {
                    hits += 1;
                }
            }
            if hits > 0 {
                let alpha = hits as f32 / 4.0;
                // 取原像素 + 按比例混 color
                let old = fb.pixels[py * fb.width + px];
                let blended = blend_color(old, color, alpha);
                fb.put(px, py, blended);
            }
        }
    }
}

fn blend_color(bg: u32, fg: u32, alpha: f32) -> u32 {
    let br = ((bg >> 16) & 0xFF) as f32;
    let bg2 = ((bg >> 8) & 0xFF) as f32;
    let bb = (bg & 0xFF) as f32;
    let fr = ((fg >> 16) & 0xFF) as f32;
    let fg2 = ((fg >> 8) & 0xFF) as f32;
    let fb_ = (fg & 0xFF) as f32;
    let r = br * (1.0 - alpha) + fr * alpha;
    let g = bg2 * (1.0 - alpha) + fg2 * alpha;
    let b = bb * (1.0 - alpha) + fb_ * alpha;
    ((r as u32) << 16) | ((g as u32) << 8) | (b as u32)
}
```

**关键点**:
- `samples` 是 2×2 子像素的中心点——把像素分成 4 个小格,每格中心采样
- `hits` 记录有多少个子格在矩形里,除以 4 得覆盖率(0、0.25、0.5、0.75、1.0)
- 这是 **MSAA 2x2** 的最简版本。GPU 的 4x MSAA 就是这个,只是硬件实现

## 8 · Rust / Arch 落地代码

### 完整可跑示例

把 §2 的代码扩展成一个最小可看的演示——生成一个 PPM 图像(简单无依赖图像格式):

```rust
// src/main.rs
// 在 fb 上画几个旋转矩形,导出为 PPM

struct Framebuffer {
    width: usize,
    height: usize,
    pixels: Vec<u32>,
}
impl Framebuffer {
    fn new(w: usize, h: usize) -> Self {
        Self { width: w, height: h, pixels: vec![0x000000; w * h] }
    }
    fn save_ppm(&self, path: &str) -> std::io::Result<()> {
        use std::io::Write;
        let mut f = std::fs::File::create(path)?;
        writeln!(f, "P3")?;                          // PPM magic (ASCII)
        writeln!(f, "{} {}", self.width, self.height)?;
        writeln!(f, "255")?;                          // max color value
        for p in &self.pixels {
            let r = (p >> 16) & 0xFF;
            let g = (p >> 8) & 0xFF;
            let b = p & 0xFF;
            write!(f, "{} {} {} ", r, g, b)?;
        }
        Ok(())
    }
}

// [Mat2 / Vec2 / fill_rotated_rect 同 §2]

fn main() {
    let mut fb = Framebuffer::new(400, 400);
    // 3 个不同角度、不同颜色、不同大小的矩形
    fill_rotated_rect(&mut fb, Vec2 { x: 100.0, y: 100.0 }, (80.0, 40.0), 0.0_f32.to_radians(), 0xFF0000);
    fill_rotated_rect(&mut fb, Vec2 { x: 200.0, y: 200.0 }, (100.0, 30.0), 30.0_f32.to_radians(), 0x00FF00);
    fill_rotated_rect(&mut fb, Vec2 { x: 300.0, y: 300.0 }, (60.0, 60.0), 45.0_f32.to_radians(), 0x0000FF);
    fb.save_ppm("/tmp/rotated_rects.ppm").unwrap();
    println!("saved to /tmp/rotated_rects.ppm");
}
```

### Troubleshooting

- **矩形看起来位置不对** — 检查 origin 是不是矩形左下角(Convention: HH 用左下角,屏幕坐标 y 朝上),不是中心
- **矩形面积变化** — 旋转后像素数应该不变(无锯齿时);变化大说明 AABB 算错或逆矩阵算错
- **AABB 超出屏幕** — 检查 clamp 范围,确保 `min_x >= 0` 且 `max_x < width`
