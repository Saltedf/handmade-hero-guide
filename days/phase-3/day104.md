# Day 104 · 切换到 Y 轴向上渲染目标

> 今天 Casey 做一件「**纯工程化**」的事——把渲染目标的 Y 轴方向翻转。听起来无聊,但这是个**重要的视觉约定**:游戏世界 Y 朝上(重力向下),而图片格式 Y 朝下(BMP/PNG 第 0 行是顶部)。今天 Casey 把渲染管线**统一**到「Y 朝上」,为 Day 108 透视投影(3D 数学天然 Y 朝上)做准备。

## 0 · 为什么要有这一天

让我们从一个真实的"符号 bug"说起。

你跟 Casey 走到 Day 103,渲染器功能完整——Phong 光照、法线贴图、环境反射、Fresnel 都集成。但你的坐标系是 **Y 朝下**(继承 BMP 加载约定)——`(0,0)` 在左上角,Y 增大向下。

现在你想加 Day 108 的**透视投影**。3D 数学有个标准公式:

```
y_screen = y_world / z * focal_length
```

这是齐次坐标投影。问题是:**3D 数学天然 Y 朝上**(数学家规定的)——`y = sin(angle)` 在 0 到 π 之间是正的(向上)。如果你的世界 Y 朝下,`sin(angle)` 算出来要取反,否则视角反向。

具体 bug:你写 `player_pos.y = sin(time) * 5`(模拟跳跃),期望玩家跳起来(y 增加)。但在 Y 朝下的系统,y 增加是"向下",所以玩家**沉入地面**。

你困惑——"公式没错啊"。**根因**:坐标系约定和数学约定不一致。

**坐标系约定的混乱**是图形学经典 bug 源。常见三种约定:

1. **屏幕坐标 / 图片坐标**:Y 朝下——`(0, 0)` 在左上角,Y 增大向下。BMP、PNG、JPEG、HTML5 Canvas、SDL、Win32 GDI 都用这个。
2. **数学坐标 / OpenGL**:Y 朝上——`(0, 0)` 在左下角,Y 增大向上。线性代数、3D 数学、OpenGL viewport、OpenGL NDC 都用这个。
3. **3D 游戏世界**:Y 朝上(或 Z 朝上,看引擎)——Unreal 用 Z 朝上,Unity 用 Y 朝上。

Casey HH 之前用 Y 朝下(跟随 BMP),但在做 3D 数学(透视投影、向量运算)时,**Y 朝下会引入无数符号错误**——`y = sin(angle)` 算出来要取反,因为数学上 Y 朝上。

今天 Casey 切换到「**渲染目标 Y 朝上**」:
- framebuffer 的 `(0, 0)` 改成左下角
- 渲染时把所有 Y 坐标翻转:`y_screen = height - 1 - y_image`
- 纹理加载时翻转 Y(把 BMP 的行 0 当作「最底行」)

这是「**一个 bug 修一天**」的典型——一个简单的 Y 翻转,但要改十几个地方,且每个地方错了画面就镜像。

**学完今天,你应该能**:

- **解释 Y-up 和 Y-down 的历史和约定**——为什么图片格式 Y 朝下,数学 Y 朝上
- **实现 framebuffer Y 翻转**——内部 Y-up,导出 Y-down
- **处理纹理加载翻转**——BMP/PNG 行 0 是顶行,加载时翻成底行
- **理解 OpenGL / Vulkan / D3D 的 Y 方向差异**——为什么 GLSL shader bug 来自坐标方向
- **设计坐标系统一的策略**——内部 Y-up,边界处显式转换

## 1 · Casey 今天做了什么

Casey 这天是纯工程化工作,没新功能。让我把步骤拆开。

**第一步,决定坐标系约定**:渲染目标 Y 朝上(`(0, 0)` 在左下角)。这是和数学坐标系一致的约定。

**第二步,修改 framebuffer 写出**:`fb[(height - 1 - y) * width + x] = color`(行翻转)。让内部存储保持 Y-down(因为 OS framebuffer 是 Y-down),但 API 接受 Y-up 坐标。

**第三步,修改 BMP 加载**:把行 0 当作最底行(原 BMP 行 0 是顶行)。这样加载的图像在 Y-up 系统中显示正确。

**第四步,修改所有渲染函数**(AABB、像素循环、sprite 位置)的 Y 坐标语义。`min_y` 是"下"(Y 小),`max_y` 是"上"(Y 大)。原来相反。

**第五步,测试**:sprite 应该正常显示(不镜像,不颠倒)。Casey 在视频里强调这是"破坏性变更"——大量代码要改,改错一处画面就破。

**Casey 强调**:**Y 方向是约定,不是真理**。选哪个都行,但**统一**最重要——一个项目里不要混用两种约定,否则 bug 无穷。

## 2 · 心智模型

### 2.1 费曼类比:看地图

我打个比方。地理地图约定:**北朝上**。所以「北京在上海北边」=「北京在地图上方」。

但你看卫星图(从太空看地球)——「北朝上」只是约定。如果你倒过来看卫星图(南朝上),地图仍然正确,只是看起来奇怪。地理学家可能觉得南朝上"反了",但实际上**地球没有上下**——上下是人类视角的发明。

坐标系就是这种「**约定**」。数学家和物理学家偏好 Y 朝上(重力向下,自然——苹果从树上掉到地面,Y 减少);程序员历史继承 Y 朝下(电视扫描线从上到下,CRT 显像管电子枪从顶部开始扫描)。

今天 Casey 从「程序员约定」切换到「数学家约定」——Y 朝上,让 3D 数学更自然。这是"为了未来工作(3D 数学)而付一次性的迁移成本"。

### 2.2 坐标系约定的三种文化

让我把三种坐标系约定的来源讲清楚,你会看到混乱的历史。

**Y 朝下(屏幕/图片)**:
```
(0, 0) ─────────── (W, 0)
  │                    │
  │     y 增大向下     │
  │                    │
(0, H) ─────────── (W, H)
```

来源:**电视扫描线**——CRT 显像管的电子枪从屏幕左上角开始,从左到右、从上到下扫描。第一行扫描完移到第二行。这种"从上到下"的物理顺序,奠定了所有屏幕图像格式的 Y-down 约定。BMP、PNG、JPEG、GIF 全部 Y-down。HTML5 Canvas、SDL、Win32 GDI、X11、Wayland 全部 Y-down。

**Y 朝上(数学/OpenGL)**:
```
(0, H) ─────────── (W, H)
  │                    │
  │     y 增大向上     │
  │                    │
(0, 0) ─────────── (W, 0)
```

来源:**笛卡尔坐标系**——René Descartes 1637 年发明,数学家使用至今。Y 朝上是物理直觉——重力向下(Y 减少),物体上抛 Y 增加。线性代数、微积分、物理学全部 Y-up。OpenGL 1992 年由 SGI(硅图公司)设计,一群数学家做,选 Y-up。OpenGL 的 NDC(normalized device coordinates)Y-up,viewport Y-up。

**3D 游戏世界**:Y 朝上(Unity)或 Z 朝上(Unreal)。Unity 选 Y-up(因为 Unity 创始人是 OpenGL 背景)。Unreal 选 Z-up(因为 Unreal 创始人是 mod 社区背景,继承了 UnrealEd 的 Z-up 约定)。两种都合理,关键是引擎内统一。

**转换**:`y_up = H - 1 - y_down`(像素索引,从 0 开始)。浮点坐标:`y_up = H - y_down`。

### 2.3 影响的代码位置

Y 翻转影响所有「画到屏幕」的代码,让我详细列。

**1. framebuffer 索引**:`pixels[(H-1-y) * W + x]`——把 Y-up 坐标转 Y-down 索引。这是核心。

**2. AABB 计算**:`min_y` 是"下"(Y 小),`max_y` 是"上"(Y 大)。原来相反——Y-down 时 `min_y` 是"上"。

**3. 像素循环**:`for py in min_y..=max_y`(还是从小到大,但 min_y 是「下」)。循环方向不变,只是语义变。

**4. sprite 位置**:`origin.y` 是"底边"(Y 小)还是"中心"?需要重新定义。Casey HH 让 `origin.y` 是 sprite 的底边——玩家站在地面时,ground_level 和 origin.y 一致。

**5. BMP/PNG 加载**:行 0 = 顶行,加载时翻转。

**纹理坐标的 v**:这是最容易混淆的地方。
- Y 朝下时,v=0 在纹理顶行(屏幕上方),v=1 在纹理底行(屏幕下方)
- Y 朝上后,v=0 应该在"屏幕下方"(因为 v 增大向上),所以纹理 v=0 对应屏幕下方
- 但纹理图本身的 v=0 是图像顶行(物理存储)

**解决方案**:加载纹理时把图像翻转(行 0 → 行 max),让纹理内存的 v=0 是"图像底行"。这样纹理 v 直接和屏幕 Y 方向一致。这是 OpenGL 的 `GL_UNPACK_FLIP_Y` 标志的作用——加载纹理时自动翻转。

### 2.4 完整翻转:行交换算法

让我把翻转算法展开:

```rust
// 翻转图像(行翻转)
fn flip_vertically(width: u32, height: u32, pixels: &mut Vec<u8>) {
    let row_size = width as usize * 4;  // RGBA
    let mut top = 0;
    let mut bot = (height as usize - 1) * row_size;
    while top < bot {
        // 交换两行
        for i in 0..row_size {
            pixels.swap(top + i, bot + i);
        }
        top += row_size;
        bot -= row_size;
    }
}
```

算法:**双指针**——top 从 0 下移,bot 从底上移,相遇时停止。每次交换两行的所有像素。

复杂度:O(W*H)——每个像素访问一次。1000×1000 RGBA 图像 = 4MB,翻转 ~1ms。

**更高效的实现**:`u8::swap` 是字节交换,可以用 `slice::copy_within` 或 memmap 避免拷贝。但对教学目的,简单版本足够。

### 2.5 framebuffer Y-up 的实现策略

有两种实现策略,我对比。

**策略 A:内部 Y-down,API 翻转**

```rust
impl LinearFramebuffer {
    fn put_y_up(&mut self, x: usize, y: usize, color: [f32; 4]) {
        // y 是 Y-up 坐标(0 在底),转 Y-down 索引
        let y_index = self.height - 1 - y;
        self.pixels[y_index * self.width + x] = color;
    }
}
```

内部存储保持 Y-down(兼容 OS),API 接受 Y-up。每次 put 时翻转一次。优点:**输出 framebuffer 不需要再翻**(已经是 OS 格式)。缺点:**每次 put 多一次减法**(几乎免费,但概念上不纯)。

**策略 B:内部 Y-up,输出翻转**

```rust
struct Framebuffer {
    width: usize,
    height: usize,
    pixels: Vec<[f32; 4]>,  // 内部 Y-up
}

impl Framebuffer {
    fn put(&mut self, x: usize, y: usize, color: [f32; 4]) {
        if x < self.width && y < self.height {
            self.pixels[y * self.width + x] = color;  // 直接索引
        }
    }
    /// 翻转到 Y-down(导出图片时)
    fn flip_y_to_bytes(&self) -> Vec<u8> {
        let mut bytes = Vec::with_capacity(self.width * self.height * 4);
        for y in (0..self.height).rev() {  // 从顶到底
            for x in 0..self.width {
                let p = self.pixels[y * self.width + x];
                bytes.push(linear_to_srgb_byte(p[0]));
                bytes.push(linear_to_srgb_byte(p[1]));
                bytes.push(linear_to_srgb_byte(p[2]));
                bytes.push((p[3] * 255.0) as u8);
            }
        }
        bytes
    }
}
```

内部 Y-up,输出时翻转。优点:**API 纯粹**(内部和数学一致)。缺点:**输出时多一次翻转**(但只在最终输出,不在每像素)。

Casey HH 用策略 B——更干净,3D 数学计算时不会有"我应该用 Y-up 还是 Y-down"的困惑。

### 2.6 Sprite 渲染的 Y 处理

考虑 sprite 在世界坐标 `(100, 50)`(Y 朝上,所以离地 50 像素)。它的 AABB:
- 顶点 (100, 50) 是 sprite 的**底边**(局部 (0, 0))
- 顶点 (100 + w, 50 + h) 是 sprite 的**顶边**(局部 (1, 1))

渲染时遍历:
```rust
for py_world in 50..(50 + h) {  // Y 朝上,从底到顶
    for px_world in 100..(100 + w) {
        // framebuffer.put 内部用 Y-up 索引
        fb.put(px_world, py_world, color);
    }
}
```

如果用策略 A(framebuffer 内部 Y-down),要显式翻转:
```rust
for py_world in 50..(50 + h) {
    let py_screen = fb.height - 1 - py_world;  // 翻转到屏幕坐标
    for px_world in 100..(100 + w) {
        fb.pixels[py_screen * fb.width + px_world] = color;
    }
}
```

策略 B 更清晰——游戏代码不用知道"翻转",只调 fb.put。翻转隐藏在 fb 内部。

## 3 · 四域深入

### 3.1 · 游戏编程视角

坐标系在游戏开发里极其重要。让我对比几个引擎。

**2D 游戏**:常 Y 朝下(继承 HTML/Flash),简单。但物理(重力)是 -y,反直觉——`gravity = (0, 9.8)`(向下),但 y=9.8 在 Y-down 系是"向下",所以物理引擎要正确处理。

**3D 游戏**:Y 朝上(Unity)或 Z 朝上(Unreal)。
- **Unity**:Y 朝上,gravity = (0, -9.8, 0)。
- **Unreal**:Z 朝上,gravity = (0, 0, -9.8)。
- **Godot**:Y 朝上(2D 和 3D 都 Y-up)。

**2.5D**(Casey HH):Y 朝上,实体有 z(楼层)。地面是 y=0,玩家走动 y 不变,跳起来 y 增加。

**坑:mixed coords**。游戏内部用 Y 朝上,但 UI 库(ImGui)用 Y 朝下。转换处必须显式翻转,bug 高发区。Bevy 用 Transform(3D,Y-up)和 UI(UI,Y-down),需要小心。

**坑:动画系统**。骨骼动画导出(Maya / Blender)默认 Y 朝上。如果你的引擎 Y 朝下,导入时需要旋转 180°。Maya 的 FBX 导出有 "Up Axis" 选项,Blender 也有。Common bug:模型导入后颠倒或侧躺。

**坑:鼠标坐标**。鼠标事件来自 OS(Y-down),要翻转才能和游戏世界(Y-up)对齐。Casey HH 在 Day 110 屏幕反投影时处理这个。

### 3.2 · 图形学视角

坐标系在图形学是最混乱的话题之一。让我把 GPU pipeline 的 Y 方向列出来。

**1. 屏幕坐标**:Y 朝下(Vulkan / D3D / OpenGL 默认 framebuffer)。这是和 OS framebuffer 兼容的约定。

**2. NDC(Normalized Device Coordinates)**:OpenGL Y 朝上((-1, -1) 左下,(1, 1) 右上)。Vulkan Y 朝下((-1, -1) 左上,(1, 1) 右下)。**这是 OpenGL 和 Vulkan 的核心区别之一**——很多 port bug 来自这里。D3D NDC Y 朝下,跟 Vulkan 一致。

**3. 窗口坐标**(glViewport 后):OpenGL 默认 Y 朝上(从下到上)。Vulkan / D3D Y 朝下(从上到下)。

**4. 纹理坐标**:OpenGL 默认 v=0 底部,Y 朝上;D3D v=0 顶部,Y 朝下。这是另一对不一致——同一个 texture 在 OpenGL 和 D3D 看起来上下颠倒。

这个混乱是历史原因——OpenGL 想跟数学一致,Y 朝上;D3D 想跟 Win32 GDI 一致,Y 朝下。**坑无数**,大部分 GLSL/HLSL shader port bug 来自坐标方向。

Casey HH 选 Y 朝上(跟数学一致)。Day 200+ 切到 OpenGL 时,这个选择让 port 容易。

**修复 GLSL/D3D port**:Vulkan 1.1 加了 `VK_KHR_maintenance1` 扩展,允许 negative viewport height——把 Y-down viewport 翻转成 Y-up。这样 OpenGL 和 Vulkan 行为一致。

### 3.3 · Linux 系统编程视角

Linux 显示协议的 Y 方向:

**1. X11**:窗口坐标 Y 朝下(继承 X 协议 1984 年)。`XCreateWindow` 的 (x, y) 是左上角。

**2. Wayland**:表面坐标 Y 朝下(继承 X11)。Wayland 设计于 2010 年代,但保留 X-down 是为了兼容。

**3. fbdev**(framebuffer):Y 朝下。`/dev/fb0` 的内存布局是 top-to-bottom。

**4. DRM/KMS**(Direct Rendering Manager / Kernel Mode Setting):Y 朝下。Linux 内核显示子系统。

Linux 程序员的世界里 Y 几乎都朝下。Casey HH 切到 Y 朝上是**对图形学数学的妥协**,不是对 Linux 的。在 OS 边界(显示窗口)处显式翻转。

```bash
# 看你屏幕的坐标(用 xrandr)
xrandr | grep "current"
# 输出类似:1920x1080 current ... (X 轴朝右,Y 轴朝下)

# 用 xev 看鼠标事件的坐标
xev -event mouse
# 移动鼠标,看 (x, y) 输出——左上角是 (0, 0),右下角是 (W-1, H-1)
```

**Linux 游戏开发**:`glibc`、`X11`、`Wayland`、`DRM` 全部 Y-down。游戏内部 Y-up,边界翻转。SDL2 提供 `SDL_Renderer` 抽象,默认 Y-down,但可以设 `SDL_RenderSetLogicalSize` 改。GLFW(Y-up)和 SDL(Y-down)的 Y 方向不一致,跨平台开发要小心。

### 3.4 · Rust 生态视角

Rust 图形库的坐标:

**1. `image` crate**:Y 朝下(图片格式约定)。`ImageBuffer::get_pixel(x, y)` 的 y=0 是顶行。

**2. `softbuffer`**:Y 朝下(直接对应 framebuffer)。`Buffer::pixels_mut()` 给的字节流是 top-to-bottom。

**3. `winit`**:窗口坐标 Y 朝下(跟随 OS)。鼠标事件 `CursorMoved` 的 (x, y) 是窗口左上角为原点。

**4. `wgpu`**:clip space Y 朝上(跟随 Vulkan/D3D12 NDC)。但 framebuffer 输出 Y 朝下(屏幕坐标)。

**坑**:混合多个 crate 时,坐标方向可能不一致。**约定**:统一在游戏内部用 Y 朝上,边界处(显示窗口、加载图片)显式转换。

Bevy 的 Transform 用 Y-up(3D 数学),但 Bevy UI 用 Y-down(跟随 winit)。Bevy 在 UI 渲染时翻转——一个 `scale.y = -1` 的 matrix component 处理这个。

## 5 · 对照与变奏

### Y-up vs Y-down 的取舍

| | Y-up | Y-down |
|---|---|---|
| 数学直觉 | 好(向量、积分自然) | 差(符号补偿) |
| 物理直觉 | 好(重力 -y) | 差(重力 +y) |
| 图片兼容 | 差(需翻转) | 好(直接) |
| UI 库兼容 | 差(需翻转) | 好(直接) |
| 3D 数学 | 好(矩阵、相机) | 差(无数坑) |

3D 游戏开发强烈推荐 Y-up,即使初期有兼容成本。

### 历史

- 1960s Sutherland Sketchpad:Y-up(数学家做的)
- 1980s Win32 GDI:Y-down(继承 IBM 主机)

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 OpenGL NDC 的 Y 朝上,但 framebuffer 的 Y 朝下?

**参考解答**:这是 OpenGL 设计的历史妥协。NDC 是「**数学化的中间表示**」——Y 朝上和数学一致,方便顶点变换。Framebuffer 是「**物理化的最终结果**」——Y 朝下和显示器扫描线一致(从上到下)。

OpenGL 在 glViewport 之后做一次 Y 翻转,把 NDC 的 Y-up 变成 framebuffer 的 Y-down。这个翻转隐藏在 OpenGL 实现(驱动)里,用户通常不察觉。但如果你绕过 OpenGL 直接操作 framebuffer(比如用 PBO),就要自己处理 Y 翻转。

### Lv2 · 动手实践

**题**:在你的渲染器里把所有 framebuffer 操作切换到 Y-up。具体:
1. 修改 `put(x, y, color)` 让 y=0 是底
2. 修改 `flip_y_to_bytes` 输出 PNG(Y-down)
3. 修改 sprite 渲染:origin.y 是 sprite 的「底」而不是「顶」
4. 测试:在 (50, 50) 画一个 10x10 sprite,它应该出现在屏幕中央偏下

完成标准:渲染结果和 Y-down 时一致(看起来不变),但内部坐标系是 Y-up。

**参考解答**:见 §2 Rust 实现。

### Lv3 · 迁移设计

**题**:你的项目之前所有坐标系是 Y-down。现在要切换到 Y-up,但你想**最小改动**。哪种策略:
1. 全局重写所有 Y 操作(改动多,但彻底)
2. 在 framebuffer 层加一个翻转层(改动少,但有性能开销)
3. 在游戏层 Y-up,显示层 Y-down,中间转换(改动中,推荐)

提示:策略 3 最平衡——游戏代码用 Y-up(数学自然),显示层 framebuffer 保持 Y-down(兼容 OS),转换在 framebuffer.put 时做一次。

## 9 · 工业级坐标系处理补充

### 9.1 多坐标系项目的标准做法

工业项目通常有多个坐标系共存——游戏世界(Y-up)、UI(Y-down)、屏幕(Y-down)、GPU clip space(Y-up)。处理这种多坐标系的标准做法:

**约定 1**:游戏内部统一 Y-up。所有游戏逻辑(player physics、AI 寻路)在 Y-up 系统下,3D 数学自然。

**约定 2**:边界处显式翻转。从 OS 接收鼠标事件(Y-down)时翻转:`game_y = window_height - mouse_y`。向 OS 输出 framebuffer(Y-down)时翻转:`fb_y = window_height - 1 - game_y`。

**约定 3**:文档化每个 API 的坐标系。函数签名加注释:`fn get_player_pos() -> Vec2 /* Y-up */`。这样调用方知道是 Y-up 还是 Y-down。

### 9.2 跨引擎 port 案例

Casey HH 的 Y-up 选择让 port 到 OpenGL 容易——OpenGL NDC 也是 Y-up。如果 Casey HH 用 Y-down,port 时要在 vertex shader 加 `gl_Position.y = -gl_Position.y`,容易出错。

**反例**:Unity 到 Unreal port。Unity Y-up,Unreal Z-up。port 时要旋转所有 Transform(把 Y 转到 Z)。这个 port 是 industrial 难题,大量第三方工具(FBX exporter)专门处理。

### 9.3 Linux framebuffer 和 Y 方向

Linux 的 `/dev/fb0` 是 Y-down——内核 mmap 给用户的内存,top-to-bottom。Casey HH 内部 Y-up,输出到 `/dev/fb0` 时翻转。性能上,翻转是 O(W*H),~1ms,可接受。

更高效:用 `DRM` (Direct Rendering Manager) 的 page flip,直接 framebuffer swap。Linux 的 `drmModeAtomicCommit` 让你提交 framebuffer,flip 在硬件层。

```bash
# 看你 GPU 的 DRM 支持
ls /dev/dri/
# card0 renderD128 两个 device

# 看 DRM 模式
modetest -M <driver_name>
```

### 9.4 完整测试代码

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_yup_coordinate_basic() {
        let mut fb = Framebuffer::new(10, 10);
        // Y-up 的 (0, 0) = 底左
        fb.put(0, 0, [1.0, 0.0, 0.0, 1.0]);  // 红色
        // Y-up 的 (0, 9) = 顶左
        fb.put(0, 9, [0.0, 1.0, 0.0, 1.0]);  // 绿色

        // 翻转后(Y-down 输出):
        // - 顶左(Y-down (0, 0))应该是绿色
        // - 底左(Y-down (0, 9))应该是红色
        let bytes = fb.flip_y_to_bytes();
        // bytes[0] 是 Y-down (0, 0) 的 R 分量 = 0(绿色 R=0)
        assert_eq!(bytes[0], 0);
        // bytes[1] 是 Y-down (0, 0) 的 G 分量 = 255(绿色)
        assert_eq!(bytes[1], linear_to_srgb_byte(1.0));
    }

    #[test]
    fn test_yup_to_ydown_inversion() {
        // 两次翻转应该回到原状
        let mut fb = Framebuffer::new(5, 5);
        for y in 0..5 {
            for x in 0..5 {
                fb.put(x, y, [x as f32 / 5.0, y as f32 / 5.0, 0.0, 1.0]);
            }
        }
        // 翻转一次
        let bytes1 = fb.flip_y_to_bytes();
        // 把 bytes1 重建为 Y-up framebuffer(再次翻转)
        let mut fb2 = Framebuffer::new(5, 5);
        for y in 0..5 {
            for x in 0..5 {
                let i = ((4 - y) * 5 + x) * 4;  // 反向读
                let r = bytes1[i] as f32 / 255.0;
                fb2.put(x, y, [r, 0.0, 0.0, 1.0]);
            }
        }
        // fb 和 fb2 的 R 通道应该一致
        for y in 0..5 {
            for x in 0..5 {
                let original = fb.pixels[y * 5 + x][0];
                let rebuilt = fb2.pixels[y * 5 + x][0];
                assert!((original - rebuilt).abs() < 0.01);
            }
        }
    }
}
```
