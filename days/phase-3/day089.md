# Day 089 · 渲染器推送缓冲条目类型

> 你昨天搭好了 push buffer 框架,但只有 3 种命令。今天 Casey 扩展——更多 entry types(PushLine、PushQuad、PushText)+ **sort key**(排序键)。每条命令有 u64 sort key,渲染前按 key 排序。这让「同层命令在一起、同纹理命令在一起(减少 GPU 状态切换)、深度正确排序」自动实现。sort key 是工业渲染器的灵魂——理解它你就理解了 draw call batching。

## 0 · 为什么要有这一天

你的 push buffer 顺序就是 push 顺序:

```rust
push_buf.push_clear();
push_buf.push_bitmap(background);
push_buf.push_bitmap(player);
push_buf.push_bitmap(monster1);
push_buf.push_bitmap(monster2);
push_buf.push_text(score);
```

这看起来没问题,但**有几个隐藏问题**:

**问题 1:层(层序)**。你想让 UI 永远在最上面,即使后 push 的实体挡住 UI。怎么办?push 顺序硬保证?那怪物的碰撞特效如果后 push,会盖在 UI 上——错。

**问题 2:深度(2.5D 的 z)**。多个 sprite 在不同 z,要按 z 排序(高 z 后画)。但游戏代码 push 顺序不一定符合 z——后 push 的可能 z 低。

**问题 3:批处理(batching)**。GPU 渲染时,同纹理的 sprite 连续画能减少 texture binding 切换。但 push 顺序可能交错不同纹理——每次切换浪费。

**Casey 的解法**:**sort key**。

每个命令加一个 u64 sort key。渲染前按 key 排序,然后渲染。

```rust
struct RenderCommand {
    sort_key: u64,
    payload: CommandPayload,
}
```

sort key 的**位编码**多个维度:

```
bit 56-63: layer (UI / world / background)
bit 40-55: z 深度
bit 24-39: texture id (同纹理 batch)
bit 0-23: 子排序
```

按 sort_key 排序后,自然实现「先画背景,再画世界(按 z),最后画 UI」。同纹理的命令聚在一起,GPU 切换少。

心理锚点:看完今天,你能向队友解释「为什么我们的渲染器每帧只有 10 次 GPU draw call」。你能用 Rust 实现位编码 sort key。你能用 30 秒说清「draw call batching」的原理。

## 2 · 心智模型

### 费曼类比:图书馆排书

图书馆的书按 Dewey Decimal 系统分类——每本书有个数字 ID:

- 000-099:计算机
- 100-199:哲学
- ...
- 900-999:历史

每类里再按作者字母排。借书时按 ID 找,书天然按主题聚在一起。

sort key 类似——**多位数字编码多维信息**。高位是「最重要」的(类),低位是「次要」的(子序)。按数字大小排,自然得到正确顺序。

### 严谨原理

#### 2.1 sort key 的位编码

```rust
// 64 bit sort key
// bits 56-63 (8 bits): layer (0=background, 1=world, 2=foreground, 3=UI)
// bits 40-55 (16 bits): z 深度(深度越大越远,排序时画在前面——所以反转)
// bits 24-39 (16 bits): texture id (同纹理聚集)
// bits 0-23  (24 bits): 子排序(同纹理内的顺序)

const LAYER_SHIFT: u32 = 56;
const Z_SHIFT: u32 = 40;
const TEXTURE_SHIFT: u32 = 24;
const SUB_SHIFT: u32 = 0;

fn make_sort_key(layer: u8, z: u16, texture_id: u16, sub_order: u32) -> u64 {
    let layer_bits = (layer as u64) << LAYER_SHIFT;
    // z 越大越远,排序时 z 大的在前(先画),所以反转
    let z_bits = ((!z as u64) & 0xFFFF) << Z_SHIFT;
    let tex_bits = (texture_id as u64) << TEXTURE_SHIFT;
    let sub_bits = (sub_order as u64) & 0xFFFFFF;
    layer_bits | z_bits | tex_bits | sub_bits
}
```

**为什么 z 反转?** 渲染顺序是「远 → 近」(远的先画,近的覆盖)。z 越大越远,但 sort_key 升序排时小数字在前。所以**反转 z**(z 大 → sort_key 小 → 排前面 → 先画)。

#### 2.2 排序

```rust
fn sort_commands(commands: &mut [RenderCommand]) {
    commands.sort_by_key(|c| c.sort_key);
}
```

`sort_by_key` 是 Rust Vec 的方法,按 key 升序排。O(n log n),够快。

#### 2.3 排序后的好处

```
排序前(push 顺序):
  background (layer=0)
  player (layer=1, z=0)
  monster1 (layer=1, z=0, tex=1)
  ui_health (layer=3)
  monster2 (layer=1, z=0, tex=1)
  score (layer=3)

排序后(按 sort_key):
  background
  player
  monster1, monster2 (同 tex,聚集)
  ui_health
  score
```

monster1 和 monster2 因 sort_key 相同(同 layer / z / tex),聚在一起——GPU 切换 texture 的次数减少。

#### 2.4 不同层的渲染顺序

```
layer 0 (background):    最先画
layer 1 (world):         然后
layer 2 (foreground):    然后
layer 3 (UI):            最后
```

按 layer 排序后,background 永远先画,UI 永远最后——游戏代码 push 顺序不影响。

#### 2.5 Z 排序的微妙

考虑 2.5D 中两个 entity 在 (x, y) 重叠,但 z 不同:

- 玩家 (x=100, y=100, z=64)  ← 在二楼
- 怪 (x=100, y=100, z=0)     ← 在一楼

屏幕上,玩家看起来在怪的「上方」(俯视角度)。但 z 大表示「高度高」,应该看起来在「屏幕上方」?

**Casey HH 约定**:z 大的 entity 在屏幕上方,所以**渲染时 z 大的先画**(被 z 小的盖住)。

```
玩家 z=64:sort_key z 部分 = !64 = 65471
怪   z=0 :sort_key z 部分 = !0  = 65535

排序:65471 < 65535,所以 player 的 sort_key 小,先画。

玩家先画(底层),怪后画(顶层)——怪的 sprite 在玩家 sprite 上面。
```

但等等,这不对——玩家在二楼,应该看起来在怪「上面」(高度高)。让我重新想。

实际上,2.5D 中:
- 玩家在二楼,屏幕上看不到(被一楼屋顶挡)
- 或者:二楼地板半透明,玩家透过看到

Casey 在 Day 107 加 Z 层渐隐处理这个。Day 089 的 sort_key 只保证「按 z 排序」,具体怎么画看 Day 107+。

#### 2.6 子排序(sub-order)

同 layer / z / texture 的命令,需要稳定的子排序(比如多个 UI 元素按 push 顺序)。

```rust
struct Renderer {
    next_sub_order: u32,
}

impl Renderer {
    fn next_sub_order(&mut self) -> u32 {
        let s = self.next_sub_order;
        self.next_sub_order = self.next_sub_order.wrapping_add(1);
        s
    }
}
```

每次 push 时分配 sub_order,保证 push 顺序在 sort_key 同的情况下保留。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

Sort key 是工业渲染器的标配:

- **Unreal**:FMeshSortKey
- **Unity**:render queue + sorting layer
- **WebGL**:z-index(简化版 sort key)
- **Casey HH**:u64 sort key

#### Draw call batching

GPU 渲染慢的不是 draw call 本身,是**状态切换**——bind texture、bind shader、set blend mode。每次切换几十微秒。

如果连续 1000 个 sprite 都用同一纹理,**一次 bind + 1000 次 draw**(实际是 instanced draw,一次画 1000 个)——极快。

sort key 把同纹理的命令聚集,让 batching 自动发生。这是 GPU 性能的核心。

#### Instanced rendering

```rust
// 不 batching:1000 次 draw call
for s in sprites {
    bind_texture(s.tex);
    draw_quad(s.x, s.y);
}

// Batching:1 次 draw call(instanced)
let same_tex_sprites: Vec<&Sprite> = sprites.iter().filter(|s| s.tex == current).collect();
bind_texture(current);
draw_instanced(same_tex_sprites.len());
```

sort key 让 batching 简单——同 key 命令聚在一起,scan 时连续 bind 同一纹理。

### 3.2 · 🎨 图形学视角

Sort key 在图形学里延伸:

#### Transparency sorting

透明物体要按深度排序(从后向前画)。Sort key 的 z 部分就是这个。

#### Z-buffer vs sort key

Z-buffer(Day 108+)是 GPU 硬件做的「逐像素深度测试」。Sort key 是 CPU 做的「逐命令深度排序」。两者互补:

- Sort key:命令级,粗粒度
- Z-buffer:像素级,细粒度

透明物体只能用 sort key(z-buffer 不支持透明)。不透明物体可以用 z-buffer(sort key 简化为 layer)。

#### Render pass

复杂渲染(光照、阴影、后处理)分多个 pass:

- Shadow pass
- G-buffer pass
- Lighting pass
- Transparent pass
- Post-process pass

每个 pass 是一组 sort_key 相近的命令。

### 3.3 · 🐧 Linux 系统编程视角

「**多维度排序**」在 Linux 里到处是:

- **进程优先级 + niceness + cgroup**:调度器按多个维度排序进程。
- **TCP 流的 TOS** (Type of Service):路由器按 TOS 决定包顺序。
- **EXT4 文件的 hash 排序**:目录里的文件按 hash 排,加速查找。

sort key 是把多维信息压成一个数字——**lexicographic ordering** 的位编码实现。

```bash
# sort 命令多列
```

### 3.4 · 🦀 Rust 生态视角

#### Rust 写 sort key

```rust
#[derive(Copy, Clone)]
struct SortKey(u64);

impl SortKey {
    const LAYER_SHIFT: u32 = 56;
    const Z_SHIFT: u32 = 40;
    const TEX_SHIFT: u32 = 24;

    fn new(layer: u8, z: u16, tex: u16, sub: u32) -> Self {
        let l = (layer as u64) << Self::LAYER_SHIFT;
        let z = ((!z as u64) & 0xFFFF) << Self::Z_SHIFT;
        let t = (tex as u64) << Self::TEX_SHIFT;
        let s = (sub as u64) & 0xFFFFFF;
        Self(l | z | t | s)
    }
}

impl Ord for SortKey {
    fn cmp(&self, other: &Self) -> std::cmp::Ordering {
        self.0.cmp(&other.0)
    }
}

impl PartialOrd for SortKey {
    fn partial_cmp(&self, other: &Self) -> Option<std::cmp::Ordering> {
        Some(self.cmp(other))
    }
}

impl Eq for SortKey {}
impl PartialEq for SortKey {
    fn eq(&self, other: &Self) -> bool { self.0 == other.0 }
}
```

实现 `Ord` 让 SortKey 可以用 `sort()`、`binary_search` 等所有 Rust 标准库方法。

#### Rust 的 sort_unstable

```rust
let mut cmds: Vec<RenderCommand> = ...;
cmds.sort_unstable_by_key(|c| c.sort_key);
```

`sort_unstable` 比 `sort` 快——不保证相等元素的相对顺序(但我们用 sub_order 区分,所以 unstable 也行)。

#### Rust 的 bit packing

```rust
// 用 repr(packed) 节省空间
#[repr(packed)]
struct PackedKey {
    layer: u8,
    z: u16,
    tex: u16,
    sub: u16,
}
// 总共 6 字节,但访问需要 unaligned(unsafe)
```

不推荐用 packed——有 alignment 陷阱。直接用 u64 更安全。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 sort_key 把 z 反转(`!z & 0xFFFF`)?

**参考解答**:**让 z 大的命令 sort_key 小**(排前面先画)。

需求:z 大(entity 高 / 远)的 entity 先画,这样后画的 z 小(entity 低 / 近)覆盖 z 大的。

sort_key 升序排时,小数字在前 → 先画。所以「先画的」=「sort_key 小」。

要让 z 大的先画,z 大时 sort_key 应该小。`!z & 0xFFFF` 是「z 的位反转」——z 大 → 反转后小。

例如 z=0:`!0 = 0xFFFF = 65535`(大)
z=64:`!64 = 0xFFBF = 65471`(小)
z=65535:`!65535 = 0 = 0`(最小)

排序后:z=65535 的 sort_key 最小(0),先画;z=0 的 sort_key 最大(65535),最后画。完美。

## 8 · Rust / Arch 落地代码

```rust
#[derive(Copy, Clone, Debug, PartialEq, Eq, PartialOrd, Ord)]
pub struct SortKey(u64);

impl SortKey {
    pub fn new(layer: u8, z: u16, texture: u16, sub_order: u32) -> Self {
        let l = (layer as u64) << 56;
        let z = ((!z as u64) & 0xFFFF) << 40;
        let t = (texture as u64) << 24;
        let s = (sub_order as u64) & 0xFFFFFF;
        Self(l | z | t | s)
    }

    pub fn layer(self) -> u8 { (self.0 >> 56) as u8 }
    pub fn z(self) -> u16 { !((self.0 >> 40) as u16) }
    pub fn texture(self) -> u16 { ((self.0 >> 24) & 0xFFFF) as u16 }
    pub fn sub(self) -> u32 { (self.0 & 0xFFFFFF) as u32 }
}

#[derive(Clone, Debug)]
pub enum Payload {
    Clear(u32),
    Bitmap { x: f32, y: f32, id: u32, tint: u32 },
    Rect { x: f32, y: f32, w: f32, h: f32, color: u32 },
    Line { x1: f32, y1: f32, x2: f32, y2: f32, color: u32 },
    Quad { verts: [(f32, f32); 4], color: u32 },
    Text { x: f32, y: f32, text: String, color: u32 },
}

#[derive(Clone, Debug)]
pub struct Command {
    pub key: SortKey,
    pub payload: Payload,
}

#[derive(Default)]
pub struct PushBuffer {
    pub commands: Vec<Command>,
    next_sub: u32,
}

impl PushBuffer {
    pub fn clear(&mut self) {
        self.commands.clear();
        self.next_sub = 0;
    }

    fn next_sub(&mut self) -> u32 {
        let s = self.next_sub;
        self.next_sub = self.next_sub.wrapping_add(1);
        s
    }

    pub fn push_clear(&mut self, color: u32) {
        // Clear 在 layer 0 之前(最优先)
        self.commands.push(Command {
            key: SortKey::new(0, 0, 0, 0),
            payload: Payload::Clear(color),
        });
    }

    pub fn push_background(&mut self, bmp_id: u32) {
        self.commands.push(Command {
            key: SortKey::new(0, 0, bmp_id as u16, self.next_sub()),
            payload: Payload::Bitmap { x: 0., y: 0., id: bmp_id, tint: 0xFFFFFFFF },
        });
    }

    pub fn push_world_sprite(&mut self, x: f32, y: f32, z: u16, bmp_id: u32) {
        self.commands.push(Command {
            key: SortKey::new(1, z, bmp_id as u16, self.next_sub()),
            payload: Payload::Bitmap { x, y, id: bmp_id, tint: 0xFFFFFFFF },
        });
    }

    pub fn push_ui_rect(&mut self, x: f32, y: f32, w: f32, h: f32, color: u32) {
        self.commands.push(Command {
            key: SortKey::new(3, 0, 0, self.next_sub()),
            payload: Payload::Rect { x, y, w, h, color },
        });
    }

    pub fn push_ui_text(&mut self, x: f32, y: f32, text: String) {
        self.commands.push(Command {
            key: SortKey::new(3, 0, 0, self.next_sub()),
            payload: Payload::Text { x, y, text, color: 0xFFFFFFFF },
        });
    }

    pub fn sort(&mut self) {
        self.commands.sort_unstable_by_key(|c| c.key);
    }
}

fn render_demo_game(push: &mut PushBuffer) {
    push.push_clear(0xFF000000);
    push.push_background(1);

    // 几个世界 sprite(同纹理聚集)
    push.push_world_sprite(100., 100., 0, 5);  // monster1
    push.push_world_sprite(150., 100., 0, 5);  // monster2
    push.push_world_sprite(200., 100., 0, 5);  // monster3
    push.push_world_sprite(120., 100., 64, 3); // player(高 z)
    push.push_world_sprite(180., 100., 0, 7);  // wolf(不同纹理)

    // UI(最后画)
    push.push_ui_rect(10., 10., 100., 20., 0xFFFF0000);
    push.push_ui_text(15., 15., "Score: 100".to_string());
}

fn main() {
    let mut push_buf = PushBuffer::default();
    render_demo_game(&mut push_buf);

    println!("排序前(push 顺序):");
    for (i, c) in push_buf.commands.iter().enumerate() {
        println!("  [{}] layer={} z={} tex={} — {:?}",
            i, c.key.layer(), c.key.z(), c.key.texture(),
            match &c.payload {
                Payload::Clear(_) => "Clear",
                Payload::Bitmap { id, .. } => format!("Bitmap(id={})", id).leak(),
                Payload::Rect { .. } => "Rect",
                Payload::Text { text, .. } => format!("Text({})", text).leak(),
                _ => "Other",
            });
    }

    push_buf.sort();

    println!("\n排序后(渲染顺序):");
    for (i, c) in push_buf.commands.iter().enumerate() {
        println!("  [{}] layer={} z={} tex={} — {:?}",
            i, c.key.layer(), c.key.z(), c.key.texture(),
            match &c.payload {
                Payload::Clear(_) => "Clear",
                Payload::Bitmap { id, .. } => format!("Bitmap(id={})", id).leak(),
                Payload::Rect { .. } => "Rect",
                Payload::Text { text, .. } => format!("Text({})", text).leak(),
                _ => "Other",
            });
    }
}
```

**Troubleshooting**:
- 排序错 — 检查位编码,layer/z/tex 的 shift 是否正确
- z 排序反向 — z 反转公式 `(!z as u64) & 0xFFFF`,别忘 `& 0xFFFF`(否则高位溢出)
