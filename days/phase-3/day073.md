# Day 073 · 临时重叠的实体

> 你昨天写了「正确的 3D 包含测试」,看起来无懈可击。但 Casey 今天抛出一个新问题:玩家**跳过**一只怪的头顶——中途,玩家和怪的 3D AABB 是真的重叠的。如果你的碰撞函数立刻返回「碰了」,玩家会被天花板弹下来,永远跳不过去。Casey 的解法揭示了一类**所有物理引擎**都要解决的问题:**连续碰撞检测(continuous collision detection)**。

## 0 · 为什么要有这一天

想象你的 2.5D 游戏里有这样一幕:玩家在 (100, 100, 0),一只怪在 (100, 100, 0),两个 entity 中心相同(但因为它们高度不同所以本来不该碰)。玩家按跳跃键,z 速度变成 +500 px/s。一帧后,玩家 z = 500 * (1/60) ≈ 8.3。还在一楼范围内,和怪碰。

继续跳。z = 50。还在一楼怪范围内,还碰。

z = 70。玩家的 z 范围是 [70-32, 70+32] = [38, 102]。怪的 z 范围是 [0-32, 0+32] = [-32, 32]。不重叠!玩家终于跳过怪了。

但是——在 z = 0 → 70 的过程中,**有几帧 z 是 32 左右,玩家的 AABB 顶刚好碰到怪的 AABB 底**。如果碰撞函数返回 `true`,游戏代码可能立刻把玩家速度反向(撞墙响应),玩家就被弹回来,永远跳不过。

这就是 **临时重叠(temporal overlap)** 问题:两 entity 的 AABB 在某几帧**真的重叠**,但**整体趋势是分开的**(高速相对运动)。如果碰撞系统机械地返回「碰」,游戏体验就崩了。

业界的术语叫 **continuous collision detection**(CCD),也叫 **time of impact**(TOI)求解。它的核心思想:**别只看当前帧的位置,要看运动趋势**。

Casey HH 在 Day 073 用一个简单的启发式解决:看相对速度。如果两 entity 相对速度很大(说明高速飞过),即使当前 AABB 重叠,也不算碰。如果相对速度很小(慢慢挤过去),才算碰。

心理锚点:看完今天,你能向队友解释「为什么我们的碰撞系统偶尔让玩家卡住」。你能区分**离散碰撞检测**(每帧一次)和**连续碰撞检测**(看运动轨迹)的差别。你知道 Box2D / PhysX 等工业物理引擎在这个问题上的核心思路。

## 1 · Casey 今天做了什么

Casey 的 Day 073 主要做三件事:

1. **复现 bug**:他把玩家放在怪的头顶,设置跳跃速度,跑游戏。玩家被卡住,跳不过去。这是个真 bug,可复现。
2. **分析**:他画了几帧的 entity 位置,发现 AABB 在几帧里真的重叠,但**整体上玩家在向上飞,怪在原地**——相对速度大,趋势是分离。
3. **加启发式判定**:在 `entities_collide` 函数里多加一个条件——`relative_speed < threshold`。即「相对速度小于某阈值才算碰」。

这是典型的「工程启发式」(heuristic):不追求完美,先解决最常见的 bug。Casey 在视频里说,后期(Day 380+ 的物理)会换成更精确的 CCD 算法,但现在先用启发式把游戏跑通。

这集还顺带讨论了**碰撞响应策略**——碰撞后是「停止」「反弹」还是「滑动」?Casey 选择「滑动」(把速度沿墙方向投影),这样玩家撞墙不会卡死,而是顺墙滑动。

## 2 · 心智模型

### 费曼类比:两条高速公路上的车

想象两条垂直交叉的高速公路。一条是 x 轴方向,一条是 y 轴方向。两辆车各自在自己的公路上跑。

第一辆车从 (-100, 0) 向 (100, 0) 跑,速度 (10, 0)。
第二辆车从 (0, -100) 向 (0, 100) 跑,速度 (0, 10)。

某一帧两辆车都在原点附近——它们的 2D AABB **真的重叠**(各 ±5 像素)。但**两辆车各走各的路**,谁也没碰到谁。

这就是「临时重叠」的本质——**离散采样**(每帧一次位置)让我们看到了某一帧的重叠,但**真实物理**(连续运动)上两辆车应该擦肩而过。

CCD 的任务:**还原连续运动,看真实的碰撞时刻**。

### 严谨原理:离散碰撞 vs 连续碰撞

#### 2.1 离散碰撞检测(DCCD)

这是 Day 071-072 写的:

```
每帧:
  for each entity_pair (a, b):
    if aabb3_overlap(a, b):
      resolve_collision(a, b)
```

每帧只检查**当前位置**。简单,但有两个根本问题:

**问题 1:tunneling(穿透)**。高速运动的子弹,一帧前在墙左,一帧后在墙右,**从来没有一帧**子弹和墙重叠。DCCD 漏检。

**问题 2:临时重叠(今天主题)**。高速运动的玩家跳过怪的头顶,中途几帧真的重叠。DCCD 误报。

#### 2.2 连续碰撞检测(CCD)

CCD 不只看当前位置,**看运动轨迹**。具体来说,把 entity 的运动看成「时间 t 上的射线 / 线段」:

```
entity a 的轨迹:a(t) = a.t0_pos + a.velocity * t   (t ∈ [0, dt])
entity b 的轨迹:b(t) = b.t0_pos + b.velocity * t

求最小的 t* ∈ [0, dt] 使得 a(t*) 和 b(t*) 重叠
```

如果 t* 存在,那就是**真实的碰撞时刻**;在 t < t* 时,两 entity 还没碰;t > t* 后,两 entity 已经分离。

**TOI = Time Of Impact**。CCD 的核心就是求 TOI。

#### 2.3 Casey 的启发式:相对速度阈值

精确 CCD 复杂(尤其对旋转物体),Casey 在 Day 073 用一个**简单启发式**:

```rust
fn entities_collide_with_temporal_check(a: &Entity, b: &Entity) -> bool {
    // 1. 先做 3D AABB 重叠测试
    if !aabb3_overlap(a.aabb, b.aabb) {
        return false;
    }
    // 2. 算相对速度
    let rel_vel = a.vel.sub(b.vel);
    // 3. 如果相对速度的模大于阈值,认为是「高速掠过」,不算碰
    if rel_vel.length() > SPEED_THRESHOLD {
        return false;
    }
    true
}
```

**SPEED_THRESHOLD** 怎么定?Casey 试出来的——比如 1000 px/s。高于这个速度就认为「是跳过,不是真碰」。

这种启发式有**两个明显问题**:

1. **慢速跳过会误判**:玩家慢慢跳,速度只有 200 px/s,但跳过怪头顶。相对速度 < 阈值,被判「碰」。玩家被卡。
2. **高速相撞会漏判**:两架高速飞机相撞,速度 > 阈值,被判「不碰」。飞机互相穿过。

但 Casey 接受这个折中:游戏里大多数情况都是**走、跑、跳**——跳过怪的速度通常 > 阈值,慢慢撞墙的速度通常 < 阈值。启发式覆盖率 90%+,足够了。

#### 2.4 工业 CCD:更精确的算法

工业物理引擎(Box2D、PhysX、Bullet)用更精确的算法:

**算法 A:射线扫描(ray cast)**

把 entity A 看成**静止**,B 看成沿相对速度方向运动的射线。求射线第一次进入 A 的时间 t*。

```
射线起点:B.pos
方向:B.rel_vel / |B.rel_vel|   (单位向量)
长度:|B.rel_vel * dt|

求 t* ∈ [0, dt] 使得 B.pos + B.vel * t* 进入 A 的 AABB
```

对 AABB,这等价于经典的 **slab method**:在 x、y、z 三个轴上分别算「射线进入 slab 的时间」和「射线离开 slab 的时间」,然后求交集。

**算法 B:swept AABB**

AABB 在一帧内「扫过」一个区域,这个扫过区域是个更大的形状(可能是 OBB 或更复杂)。求两个 swept AABB 的重叠。

**算法 C:substep(子步进)**

最简单的「假 CCD」——把一帧拆成 N 个子步,每个子步做 DCCD。如果 N 足够大,穿透和临时重叠都不容易发生。

```rust
const SUBSTEPS: usize = 4;
let sub_dt = dt / SUBSTEPS as f32;
for _ in 0..SUBSTEPS {
    for e in entities.iter_mut() {
        e.pos += e.vel * sub_dt;
    }
    for pair in entity_pairs() {
        if aabb3_overlap(...) {
            resolve_collision(...);
        }
    }
}
```

Casey HH 在简单场景里用 DCCD + 启发式,复杂场景(Day 380+)才升级到 substep。这是「先用简单方案跑通,复杂再升级」的工程思路。

#### 2.5 碰撞响应:停 / 弹 / 滑

碰撞发生后,游戏代码怎么响应?三种常见策略:

**停止(stop)**:把 entity 的速度在碰撞法线方向上归零。

```rust
// 玩家撞墙:墙法线 n,玩家速度 v
let v_along_n = v.dot(n);  // 速度在法线方向的分量
v = v.sub(n.mul(v_along_n));  // 减去法线分量,只留切线分量
```

**反弹(bounce)**:法线分量反向(乘以恢复系数 e,通常 0-1)。

```rust
let v_along_n = v.dot(n);
v = v.sub(n.mul(v_along_n * (1.0 + e)));  // e=1 完全弹,e=0 同停止
```

**滑动(slide)**:停止的特例,但保留切线分量。Casey HH 用这个——玩家撞墙后沿墙滑动。

Casey 在 Day 073 选「滑动」,因为这种响应**手感最好**——玩家撞墙不会被卡住,可以沿墙继续移动。超级马里奥、Zelda 等经典游戏都用这个策略。

#### 2.6 临时重叠的视觉化

```
帧 0: 玩家 (0, 0, 0)   怪 (0, 0, 0)     碰!z 完全相同
帧 1: 玩家 (0, 0, 8)   怪 (0, 0, 0)     碰!z 范围重叠
帧 2: 玩家 (0, 0, 17)  怪 (0, 0, 0)     碰!z 范围重叠
帧 3: 玩家 (0, 0, 25)  怪 (0, 0, 0)     碰!z 范围重叠
帧 4: 玩家 (0, 0, 33)  怪 (0, 0, 0)     不碰!玩家 z 范围 [1, 65] vs 怪 [-32, 32],差 1
```

如果「碰」就触发响应(反弹),帧 1 时玩家 z 速度变 -500,玩家下落。永远跳不过。

**Casey 的启发式**:帧 1-3 时玩家相对怪的速度 = +500 px/s,> 阈值,不算碰。玩家继续上升,到帧 4 自然跳过。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

**临时重叠**几乎是所有 3D 动作游戏的常见 bug:

- **Dark Souls**:跳过小怪的攻击,中途偶尔会被卡。开发者用 CCD 缓解。
- **Celeste**:精确平台跳跃,玩家以高速跳过刺,绝不能误判。Celeste 用 substep + 精确 swept AABB。
- **DOOM Eternal**:高速移动的恶魔冲过玩家,如果碰撞检测有 bug,会卡游戏。DOOM 用预测 + CCD。

业界共识:**碰撞检测不能机械**,要考虑**物理意图**。

**实际开发的取舍**:

| 方案 | 性能 | 准确度 | 用在哪 |
|---|---|---|---|
| DCCD(每帧一次)| 极快 | 一般 | 大多数普通物体 |
| 启发式(速度阈值)| 快 | 较好 | 玩家角色、敌人 |
| Substep(4-8 倍)| 中 | 好 | 高速物体 |
| 完整 CCD(射线扫描)| 慢 | 极好 | 子弹、关键碰撞 |

Casey HH 的策略:**DCCD 为主,启发式为辅,substep 用于特殊场景**。这是 2.5D 游戏的典型组合。

### 3.2 · 🎨 图形学视角

CCD 不只是物理问题,**渲染管线**也有类似思想:

**Motion blur(运动模糊)**:高速运动的物体,渲染时画成「拖影」。本质上是把物体的运动轨迹渲染出来——这就是 CCD 的「视觉版」。

**Temporal anti-aliasing(TAA)**:抗锯齿算法,跨帧采样。如果物体在两帧间位置变化大,TAA 知道「这个像素上一帧在那」,做插值——这又依赖类似 CCD 的运动信息。

**视锥剔除的 temporal coherence**:上一帧可见的 entity,这一帧大概率还可见。游戏引擎维护「潜在可见集」(PVS),每帧只更新边缘——这跟 CCD 的「时间一致性」是同一思想。

### 3.3 · 🐧 Linux 系统编程视角

跟 Linux 没直接关系。但有一个**通用思想**值得提:

**Linux 调度器**也解决类似问题。每个进程都想要 CPU 时间,调度器要保证**响应性**(交互进程不卡)和**吞吐量**(批处理快)。Linux 的 CFS(完全公平调度器)用「vruntime」概念——**给每个进程一个虚拟运行时间,慢速进程慢慢攒,快速进程慢慢消耗**。

CCD 的「相对速度阈值」也是类似思路:**让高速运动的 entity 享受「豁免」**(临时重叠不算碰),慢速 entity 严格判。

**Linux 性能分析**(perf):

```bash
# 你的碰撞函数每秒被调用多少次?
perf stat -e cache-misses,cache-references,branch-misses ./your_game
# 如果 cache-misses 高,说明 entity 数组布局不友好(Day 071 提的 AoS vs SoA)
```

### 3.4 · 🦀 Rust 生态视角

#### Rust 写碰撞循环的几个要点

**1. 借用规则限制**

```rust
// 错误:同时借用 entities 可变和不可变
for a in entities.iter_mut() {
    for b in entities.iter() {  // 错!iter() 和 iter_mut() 冲突
        ...
    }
}
```

Rust 借用规则禁止这种「同时迭代两次」的模式。三种解法:

**解法 A:索引**

```rust
for i in 0..entities.len() {
    for j in (i+1)..entities.len() {
        let (a, b) = if i < j {
            // 用 split_at_mut 把数组拆两半
            let (left, right) = entities.split_at_mut(j);
            (&mut left[i], &mut right[0])
        } else {
            // 不会到这里,因为我们假设 i < j
            unreachable!()
        };
        // ... 处理 a 和 b
    }
}
```

笨重。

**解法 B:先收集碰撞对,再处理**

```rust
// 第一遍:收集所有碰撞对(不可变借用)
let mut collisions = Vec::new();
for i in 0..entities.len() {
    for j in (i+1)..entities.len() {
        if entities_collide(&entities[i], &entities[j]) {
            collisions.push((i, j));
        }
    }
}
// 第二遍:处理碰撞(可变借用)
for (i, j) in collisions {
    resolve_collision(&mut entities[i], &mut entities[j]);
}
```

清晰。

**解法 C:用索引而非引用**

把 entity 用 `Vec<entity>` 存储,所有访问用 `usize` 索引。这是 Casey HH 的核心模式,Phase 2 你应该见过。

**2. 内层循环 SIMD 化**

碰撞检测的瓶颈是内层 `entity_pair` 循环。Rust 编译器能自动向量化(autovectorize),但你要写「友好」的代码:

```rust
// 不友好:branch 太多,编译器不敢向量化
for i in 0..n {
    for j in (i+1)..n {
        if entities[i].pos.x - entities[j].pos.x > threshold {
            // ...
        }
    }
}

// 友好:先把所有 entity 的 x 排列到一个数组,然后批处理
let xs: Vec<f32> = entities.iter().map(|e| e.pos.x).collect();
for i in 0..n {
    for j in (i+1)..n {
        if (xs[i] - xs[j]).abs() > threshold {
            // ...
        }
    }
}
```

Phase 4 性能优化详讲。

**3. 用 `smallvec` / `arrayvec` 避免堆分配**

```rust
// 用 [T; N] 在栈上分配,避免堆分配
use arrayvec::ArrayVec;
let mut nearby: ArrayVec<usize, 16> = ArrayVec::new();
for (i, e) in entities.iter().enumerate() {
    if is_nearby(e, player) {
        nearby.push(i);
    }
}
```

游戏循环里绝对不能有堆分配——每帧分配会触发 GC-like 行为。`arrayvec` 是栈上分配的 Vec,固定容量,无堆。

## 5 · 对照与变奏

### 不同碰撞响应策略的对比

| 策略 | 数学 | 手感 | 用在 |
|---|---|---|---|
| 停止 | v -= n*(v·n) | 卡顿 | 推箱子 |
| 滑动 | 同停止,但保留切线 | 顺滑 | 玩家撞墙 |
| 弹性碰撞 | v -= n*(1+e)*(v·n),e∈[0,1] | 弹球 | 弹球、台球 |
| 完全弹性 | e=1,能量守恒 | 乒乓 | 物理玩具 |
| 完全非弹性 | e=0,粘在一起 | 黏液 | 史莱姆 |

### 时间步进策略

| 策略 | 描述 | 用谁 |
|---|---|---|
| Fixed timestep | dt 恒定(1/60) | 大多数游戏(稳定性优先) |
| Variable timestep | dt = 实际帧时间 | 简单游戏 |
| Semi-fixed | dt 限制在 [min, max] | Casey HH 的选择 |
| Substep | 把大 dt 拆成小步 | 高精度物理 |

Casey HH 用 semi-fixed——dt 实际测,但限制在 [1/240, 1/30] 之间。太小说明帧率太高(240+),归一化到 1/240;太大说明卡顿,归一化到 1/30(避免一帧走太远导致穿透)。

### 历史:为什么 Box2D 火了

Box2D 是 Erin Catto 写的开源 2D 物理引擎,2007 年发布。它解决的核心问题之一就是 CCD——高速物体不会穿透。Angry Birds 用 Box2D,大火,Box2D 跟着火。后来的 LiquidFun、Farseer、Chipmunk 都借鉴 Box2D。

3D 物理引擎里,PhysX(NVIDIA)、Bullet(开源)、Havok(商业)是三大主流。它们都解决 CCD。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 的启发式「相对速度 > 阈值不算碰」有什么**根本缺陷**?给一个具体的反例(应该碰但启发式判不碰)。

**参考解答**:

根本缺陷:**启发式只看速度大小,不看速度方向**。

反例:玩家用冲刺技能,以 2000 px/s 速度**冲向**一只怪。冲刺过程中,玩家和怪的 AABB 重叠,但相对速度 = 2000 > 阈值,启发式判「不碰」。玩家直接穿过怪,攻击没生效。

正确判定应该看**速度方向 vs 碰撞法线**:如果相对速度方向是「沿碰撞法线接近」(说明真的在撞),算碰;如果方向是「沿碰撞法线远离」(说明在分离),不算碰。这才是真正的「连续碰撞检测」思想。

Casey 的启发式之所以能跑,是因为游戏里高速场景大多是「跳过」(速度方向垂直于碰撞法线),而撞怪的速度通常小。但冲刺技能打破了这个假设。

### Lv2 · 动手实践

**题**:在 Rust 项目里实现「相对速度阈值」的碰撞判定。写 main:
- 玩家在 (0, 0, 0),速度 (0, 0, 600)。
- 怪在 (0, 0, 0),速度 (0, 0, 0)。
- 阈值 1000 px/s。
- 模拟 5 帧(dt = 1/60),每帧打印位置和是否碰撞。

完成标准:看到前几帧被启发式判「不碰」,玩家成功跳过。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y, self.z - o.z) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y, self.z + o.z) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k, self.z * k) }
    fn dot(self, o: Self) -> f32 { self.x * o.x + self.y * o.y + self.z * o.z }
    fn length(self) -> f32 { self.dot(self).sqrt() }
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec3,
    vel: Vec3,
    half: Vec3,
}

const SPEED_THRESHOLD: f32 = 1000.0;

fn aabb_overlap(a: &Entity, b: &Entity) -> bool {
    let d = a.pos.sub(b.pos);
    let s = a.half.add(b.half);
    d.x.abs() < s.x && d.y.abs() < s.y && d.z.abs() < s.z
}

fn collide_temporal(a: &Entity, b: &Entity) -> bool {
    if !aabb_overlap(a, b) {
        return false;
    }
    let rel_vel = a.vel.sub(b.vel);
    if rel_vel.length() > SPEED_THRESHOLD {
        return false;  // 高速掠过
    }
    true
}

fn main() {
    let mut player = Entity {
        pos: Vec3::new(0., 0., 0.),
        vel: Vec3::new(0., 0., 600.),  // 跳起
        half: Vec3::new(16., 16., 32.),
    };
    let monster = Entity {
        pos: Vec3::new(0., 0., 0.),
        vel: Vec3::new(0., 0., 0.),
        half: Vec3::new(16., 16., 32.),
    };

    let dt = 1.0 / 60.0;
    for frame in 0..5 {
        player.pos = player.pos.add(player.vel.mul(dt));
        let collide = collide_temporal(&player, &monster);
        println!("帧 {}: 玩家 z = {:.2},碰撞 = {}", frame, player.pos.z, collide);
    }
}
```

**预期输出**(大概):
```
帧 0: 玩家 z = 10.00,碰撞 = false   (相对速度 600 < 1000... 等等,应该 true?)
帧 1: 玩家 z = 20.00,碰撞 = true
...
```

**等等**:600 < 1000,所以启发式不会触发,会判碰。这跟我们的目标不符。**要让启发式生效,需要把玩家速度设大(比如 1500)**,或把阈值降低(比如 500)。改一下:

```rust
// 把 SPEED_THRESHOLD 改成 500
const SPEED_THRESHOLD: f32 = 500.0;
// 玩家速度保持 600,> 500,触发启发式
```

或者:

```rust
// 把玩家速度改成 1500
vel: Vec3::new(0., 0., 1500.),
```

然后跑,就能看到「不碰」的效果。这就是测试驱动发现 bug 的一个例子。

## 8 · Rust / Arch 落地代码

### 完整可跑代码

把 Lv2 扩展,加上 substep 版本对比:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }

impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y, self.z - o.z) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y, self.z + o.z) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k, self.z * k) }
    fn dot(self, o: Self) -> f32 { self.x * o.x + self.y * o.y + self.z * o.z }
    fn length(self) -> f32 { self.dot(self).sqrt() }
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec3,
    vel: Vec3,
    half: Vec3,
}

const SPEED_THRESHOLD: f32 = 500.0;

#[inline]
fn aabb_overlap(a: &Entity, b: &Entity) -> bool {
    let d = a.pos.sub(b.pos);
    let s = a.half.add(b.half);
    d.x.abs() < s.x && d.y.abs() < s.y && d.z.abs() < s.z
}

#[inline]
fn collide_dccd(a: &Entity, b: &Entity) -> bool {
    aabb_overlap(a, b)
}

#[inline]
fn collide_with_heuristic(a: &Entity, b: &Entity) -> bool {
    if !aabb_overlap(a, b) { return false; }
    let rel_vel = a.vel.sub(b.vel);
    rel_vel.length() <= SPEED_THRESHOLD
}

fn main() {
    let mut player = Entity {
        pos: Vec3::new(0., 0., 0.),
        vel: Vec3::new(0., 0., 1500.),  // 高速跳
        half: Vec3::new(16., 16., 32.),
    };
    let monster = Entity {
        pos: Vec3::new(0., 0., 0.),
        vel: Vec3::new(0., 0., 0.),
        half: Vec3::new(16., 16., 32.),
    };

    let dt = 1.0 / 60.0;
    println!("帧  | z     | DCCD | 启发式");
    println!("----+-------+------+------");
    for frame in 0..6 {
        player.pos = player.pos.add(player.vel.mul(dt));
        println!("{:3} | {:5.1} | {}    | {}",
            frame, player.pos.z,
            collide_dccd(&player, &monster),
            collide_with_heuristic(&player, &monster));
    }
}
```

**预期输出**:
```
帧  | z     | DCCD | 启发式
----+-------+------+------
  0 |  25.0 | true | false
  1 |  50.0 | true | false
  2 |  75.0 | true | false
  3 | 100.0 | false| false
  4 | 125.0 | false| false
  5 | 150.0 | false| false
```

可以看到:启发式让前 3 帧的「假碰撞」被过滤,玩家成功跳过。
