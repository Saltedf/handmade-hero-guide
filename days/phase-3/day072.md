
# Day 072 · 正确的 3D 包含测试

> 昨天(071)你把 entity 位置改成 Vec3,顺手把 2D AABB 碰撞加了 z 维度。但「写出来」和「写对」是两件事。今天 Casey 把 3D 包含测试的**边界条件、不等号方向、半开区间**一件件钉死——这些细节你只要错一个,后面就有「楼上玩家莫名其妙被楼下怪打死」的诡异 bug。

## 0 · 为什么要有这一天

你昨天写的 3D AABB 函数大概长这样:

```rust
fn aabb3_overlap(a: AABB3, b: AABB3) -> bool {
    let d = a.center.sub(b.center);
    let s = a.half.add(b.half);
    d.x.abs() < s.x && d.y.abs() < s.y && d.z.abs() < s.z
}
```

它「看起来对」,但你跑了几次发现诡异 bug:

- 两个 entity **完全贴在一起**(差为 0),应该碰还是不碰?
- 两个 entity **刚好边对边相切**(差等于 half 之和),应该碰还是不碰?
- 一个 entity 的 z 范围 `[0, 64]`,另一个是 `[64, 128]`,共享 z=64 这一个值,算碰还是不算?

每个决定都不复杂,但你**必须在写代码前选定**。否则代码行为飘忽,bug 没法复现。

更深层的问题:**包含测试**(inclusion test)和**重叠测试**(overlap test)是同一件事吗?「entity A 是否完全在 B 内部」和「A 是否和 B 有交集」,答案可能相反。Casey 今天会精确区分这两个概念。

心理锚点:看完今天,你能在 5 秒内回答「`<` 还是 `<=`」在你的项目里意味着什么。你能向同事解释「半开区间为什么避免双计数」。你写的 3D 碰撞代码不会再有「奇奇怪怪的边界 bug」。

## 2 · 心智模型

### 费曼类比:两个人撑伞

两个人撑伞。每把伞有个圆形伞面,半径 r。两把伞「相碰」当且仅当两个伞柄的距离 ≤ 2r(两个半径之和)。如果是 `<`,伞面贴在一起不算碰;如果是 `<=`,贴在一起算碰。

伞 ↔ AABB 的类比:把伞的「半径」换成 AABB 的「half_x / half_y / half_z」,把伞的「距离」换成两 AABB 中心的「欧几里得距离」沿某轴的分量。AABB 测试就是在 x、y、z **三个轴上分别**做伞的判定——只要任一轴上「没碰」,整体就没碰。

### 严谨原理:3D 包含测试

#### 2.1 2D 回顾(Minkowski)

Day 050 你写过的 2D AABB 碰撞,本质是这样的「投影」:

```
A 在 x 轴上的投影:[a.cx - a.hx, a.cx + a.hx]
B 在 x 轴上的投影:[b.cx - b.hx, b.cx + b.hx]

A 和 B 的 x 投影重叠 ⟺
    max(a 左边, b 左边) < min(a 右边, b 右边)
    ⟺ |a.cx - b.cx| < a.hx + b.hx
```

为什么 `|a.cx - b.cx|` 等价于「中心距」?因为绝对值就是「不考虑正负的距离」。把 a 看成原点,b 就在 -d 到 +d 之间;两边都加上一个 half,得到的就是重叠条件。

3D 只要把这个判定**在三个轴上分别做**:

```
3D AABB A 和 B 重叠 ⟺
    x 投影重叠  且
    y 投影重叠  且
    z 投影重叠
```

#### 2.2 不等号方向:`<` vs `<=`

这是今天最重要的问题。

**Casey 的选择:`<`(严格小于)**。即「相切不算碰」。

理由:
1. **物理直觉**:两个物体「正好贴在一起」,它们没真正接触,不算碰。
2. **避免重复触发**:如果 `<=`,两个 entity 刚相切的那一帧算碰,下一帧它们因碰撞响应被推开,但下一帧仍可能因同样相切再碰——一次接触被算成两次。
3. **跟 Minkowski 数学一致**:Minkowski 差给出「重叠体积」,相切时体积为 0,不算正重叠。

但**`<=` 也有合理场景**:比如「地面检测」——玩家踩在地面上,脚底和地面顶面相切,这时**必须**算碰(否则玩家悬空)。所以同一个项目里,不同情况下你可能会选不同符号。

#### 2.3 半开区间 vs 闭区间

更精确的工程做法:**半开区间**。即一个 entity 的 z 范围定义为 `[bottom, top)`——左闭右开。

```
一楼地板的 z 范围:[0, 64)
二楼地板的 z 范围:[64, 128)
```

这样,一楼的顶 = 二楼的底 = 64,但**一楼不包含 64,二楼才包含 64**。两个 entity 在 z=64 时,只有一个属于「这一层」,避免双计数。

半开区间是程序员的常识(数组下标就是 `[0, n)`),但游戏开发里常被忽略。Casey 在 Day 072 没明说,但他在后续 Day 074(楼梯)和 Day 079(地面)里大量用了这种思路。

#### 2.4 浮点的陷阱

`d.x.abs() < s.x` 在 d.x ≈ s.x 时可能误判。原因:**浮点舍入误差**。

```rust
// 假设两个 entity 的中心 x 计算时引入了浮点误差
let a_cx = 100.00001;  // 应该是 100,但有 1e-5 误差
let b_cx = 90.0;
let a_hx = 5.0;
let b_hx = 5.0;
// 真实差 = 10.00001,应该不碰(10.00001 > 10)
// 但浮点计算 90.0 + 5.0 + 5.0 = 100.0,然后 100.00001 - 100.0 = 1e-5
// d.x.abs() < s.x ⟺ 1e-5 < 10.0 ⟺ true
// 错了!
```

**Casey 的解法**:加一个 epsilon(微小容忍值):

```rust
fn aabb3_overlap(a: AABB3, b: AABB3) -> bool {
    const EPS: f32 = 1e-6;
    let d = a.center.sub(b.center);
    let s = a.half.add(b.half);
    d.x.abs() < s.x + EPS
        && d.y.abs() < s.y + EPS
        && d.z.abs() < s.z + EPS
}
```

**等等,这逻辑是反的**。如果加 `+EPS`,就**更容易判碰**(容忍接近边界的判定为碰)。这是为什么?因为浮点误差可能让「应该碰」的判定变成「不碰」(误差让 d 略大于 s)。加 `+EPS` 就是容忍这种「应该碰但浮点算成不碰」的情况。

反过来,如果项目要求「严格不碰才不算」,可以减 `EPS`。**怎么选取决于你的游戏**——Casey 倾向于「宁可多碰一点,不要漏碰」。

#### 2.5 绝对值 vs 区间测试

有两种写法,数学等价但数值稳定性不同。

**写法 A:绝对值(差值)**

```rust
let d = a.center.sub(b.center);
let s = a.half.add(b.half);
d.x.abs() < s.x && ...
```

**写法 B:区间测试**

```rust
let a_min = a.center.x - a.half.x;
let a_max = a.center.x + a.half.x;
let b_min = b.center.x - b.half.x;
let b_max = b.center.x + b.half.x;
a_max > b_min && b_max > a_min && ...
```

数学上完全等价。但**写法 A 数值更稳定**:两次减法 + 一次加法 vs 四次减法 + 四次加法 + 多次比较。当 a 和 b 都很大(比如 1e8)时,写法 B 的 `a_max - b_min` 可能丢精度(大数相减),写法 A 的 `a - b` 因为两数接近而精确。

Casey 用写法 A,推荐你也用。

#### 2.6 包含 vs 重叠

这是两个不同的概念,常被混淆:

- **重叠(overlap)**:两个体积有交集(任何点同时属于两个)。
- **包含(contains / inclusion)**:A 完全在 B 内部(A 的每一点都属于 B)。

AABB 重叠测试就是上面那个。包含测试:

```rust
fn aabb3_contains(outer: AABB3, inner: AABB3) -> bool {
    let d = outer.center.sub(inner.center);
    // |d.x| + inner.half.x ≤ outer.half.x  ⟺  inner 完全在 outer 内
    d.x.abs() + inner.half.x <= outer.half.x
        && d.y.abs() + inner.half.y <= outer.half.y
        && d.z.abs() + inner.half.z <= outer.half.z
}
```

**用 `<` 还是 `<=`?** 包含测试里通常用 `<=`(贴边算包含),因为「inner 的边界等于 outer 的边界」时仍然算「完全在内」。

**何时用包含测试?**
- **视野裁剪**:判断 entity 是否完全在屏幕矩形内,完全在内才不裁。
- **房间判定**:entity 是否完全在房间 B 内。
- **烘焙 / 缓存**:判断一个 chunk 是否完全被另一个 chunk 覆盖。

Casey 今天主要讲重叠测试,包含测试是同思路。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

碰撞测试是游戏开发的「基础设施」。今天学到的几个**工程经验**,业界几乎人人踩过坑:

**坑 1:同一帧多次碰撞**。玩家在楼梯边缘,可能这一帧 z 是 63.9(碰一楼),下一帧是 64.1(碰二楼),再下一帧又 63.9——楼梯踏空的 bug。Casey 用「max_step」(Day 075)解决。

**坑 2:浮点精度退化**。entity 跑得离原点太远(比如世界坐标 1e6),浮点精度只有 1e-3,这时碰撞判定会闪烁。解法:**浮点相对原点**(relative-to-origin),或用双精度 f64 存位置,或用 chunk 坐标 + 局部坐标(后面 Day 86+)。

**坑 3:穿透(tunneling)**。高速运动的 entity 一帧移动距离 > 自身厚度,可能跳过另一个 entity。物理引擎叫这「tunneling」。解法:continuous collision detection(CCD),即把运动看成一条线段,测线段-体积相交。Casey 在 Day 073 临时解决这个问题。

**坑 4:碰撞顺序**。如果 A 碰 B,先处理 A 还是先处理 B?处理顺序不同,结果不同。Casey 在 Day 080 详细讨论。

### 3.2 · 🎨 图形学视角

「包含测试」在图形学里有几个**不同的应用**:

- **视锥剔除(frustum culling)**:entity 是否完全在视锥内?是 → 渲染,否 → 剔除。视锥是个 6 面凸体,AABB 是否在视锥内的测试比较复杂,通常用「AABB 的 8 个顶点是否都在视锥内」简化。
- **深度测试(depth test)**:光栅化时,像素的 z 是否比 z-buffer 里的 z 小?小 → 覆盖。这是 Day 108 透视投影后的核心。
- **遮挡剔除(occlusion culling)**:entity 是否被另一个完全挡住?被挡 → 不渲染。这是高端优化。
- **拾取(picking)**:鼠标点在哪个 entity 上?鼠标位置是否在 entity 的屏幕矩形内?

每一个都是「包含测试」的变体。理解 AABB 包含的本质,你能轻松理解这些图形学概念。

### 3.3 · 🐧 Linux 系统编程视角

跟 Day 071 一样,AABB3 测试是纯 CPU 运算,跟 Linux 没直接关系。但有一个**Linux 性能分析**的边角:

**分支预测(branch prediction)**。`d.x.abs() < s.x && d.y.abs() < s.y && d.z.abs() < s.z` 这个表达式里,如果**大多数情况都不碰**(比如做空间网格剔除,99% 的 entity 对不碰),CPU 分支预测器会预期 `&&` 短路,长期不执行后续比较。这种代码 pattern 在 `perf stat` 里会显示 `branch-misses` 很低。

反过来,如果**大多数都碰**(比如玩家挤满一房间),`&&` 不会短路,所有比较都执行,branch-misses 会上升。性能可能差 20%。

Casey 在 Day 112+ 性能优化时会讨论这种「数据导向设计」(DOD)——根据**实际数据分布**决定代码结构。现在你只需要知道这个事。

### 3.4 · 🦀 Rust 生态视角

#### Rust 写包含测试的几个建议

**1. 用 `assert!` 加测试**

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_overlap_separated() {
        let a = AABB3 { center: Vec3::new(0., 0., 0.), half: Vec3::new(1., 1., 1.) };
        let b = AABB3 { center: Vec3::new(5., 0., 0.), half: Vec3::new(1., 1., 1.) };
        assert!(!aabb3_overlap(a, b));
    }

    #[test]
    fn test_overlap_touching() {
        // 相切:差 = 2,half 和 = 2。用 < 时不算碰。
        let a = AABB3 { center: Vec3::new(0., 0., 0.), half: Vec3::new(1., 1., 1.) };
        let b = AABB3 { center: Vec3::new(2., 0., 0.), half: Vec3::new(1., 1., 1.) };
        assert!(!aabb3_overlap(a, b));
    }

    #[test]
    fn test_overlap_just_inside() {
        // 略微重叠:差 = 1.99,half 和 = 2。
        let a = AABB3 { center: Vec3::new(0., 0., 0.), half: Vec3::new(1., 1., 1.) };
        let b = AABB3 { center: Vec3::new(1.99, 0., 0.), half: Vec3::new(1., 1., 1.) };
        assert!(aabb3_overlap(a, b));
    }

    #[test]
    fn test_overlap_z_separation() {
        // 多楼层:z 差大不碰
        let a = AABB3 { center: Vec3::new(0., 0., 0.), half: Vec3::new(1., 1., 1.) };
        let b = AABB3 { center: Vec3::new(0., 0., 100.), half: Vec3::new(1., 1., 1.) };
        assert!(!aabb3_overlap(a, b));
    }
}
```

`cargo test` 跑所有测试。每个边界条件一个测试——这就是**测试驱动**开发(TDD)的雏形。

**2. 用 `#[inline]` 提示编译器内联**

```rust
#[inline]
fn aabb3_overlap(a: AABB3, b: AABB3) -> bool { ... }
```

碰撞测试每帧调用几千次,内联避免函数调用开销。Rust 编译器通常自己会内联,但 `#[inline]` 提示更强。

**3. 用 `bool::then_some` 简化**

```rust
// 不推荐
if aabb3_overlap(a, b) {
    return Some(resolve_collision(a, b));
} else {
    return None;
}

// 推荐
aabb3_overlap(a, b).then_some(resolve_collision(a, b))
```

这只是语法糖,不影响性能。

**4. SIMD 友好的数据布局**

如果你的 entity 数组是 `[Entity; N]`,每个 Entity 内有 `pos: Vec3`,内存布局是 AoS(array of structs)。SIMD 优化时,SoA(struct of arrays)更友好:

```rust
// SoA 版本
struct EntityPositions {
    xs: Vec<f32>,
    ys: Vec<f32>,
    zs: Vec<f32>,
}
```

碰撞测试时一次 SIMD 比较 4-8 个 entity,速度大幅提升。Phase 4 详细讲。

## 5 · 对照与变奏

### 不同语言的「相等 / 不等」陷阱

| 语言 | 整数相等 | 浮点相等 | 推荐 |
|---|---|---|---|
| Rust | `a == b` 完全可靠 | `a == b` 不可靠,用 `(a-b).abs() < eps` | f32 / f64 都用 epsilon |
| C / C++ | 同 Rust | 同 Rust | 同 Rust |
| Python | `a == b` 可靠 | 同样不可靠 | 同样 |
| JavaScript | `===` 严格 | 永远不要 `==`,精度更糟 | 同样 |

**所有语言的浮点相等都不可靠**。这是 IEEE 754 浮点标准的本质问题——`0.1 + 0.2 == 0.3` 在所有 IEEE 754 浮点语言里都是 `false`(因为 0.1 在二进制里无限循环)。

### 浮点精度的历史

- **1985**:IEEE 754 标准化 f32 / f64,统一了所有语言的浮点行为
- **1990s**:游戏开发仍大量用定点数(fixed-point,整数模拟小数),因为浮点硬件慢
- **2000s**:浮点硬件普及,SIMD(SSE)出现
- **2010s**:GPU 浮点成为主流,深度学习推动 f16 / bf16
- **2020s**:AI 推动 f8 / e4m3 等更低精度格式

Casey HH 用 f32,因为游戏精度够。 научное计算用 f64,因为要避免累积误差。

### 不同碰撞算法的复杂度

| 算法 | 时间复杂度 | 适用 |
|---|---|---|
| 暴力两两比较 | O(n²) | n < 100 |
| 空间网格(Day 055+)| O(n + k) | n < 10000,k 是碰撞对数 |
| BVH(层次包围盒)| O(n log n + k) | 静态场景 |
| GJK + EPA | O(n + k log n) | 凸多边形 |

Casey HH 用「sim region + 空间网格」,后面 Day 86+ 的 chunk 系统也是空间分块的变体。

### Lv1 · 概念辨析

**题**:下面三种情况,aabb3_overlap 用 `<` 时,各自的返回值是什么?用 `<=` 时呢?

A. 两 AABB 中心相同(zero overlap edge)
B. 两 AABB 在某轴上「相切」(差 = half 和)
C. 两 AABB 在某轴上「刚好重叠」(差 = half 和 - epsilon)

**参考解答**:
- A:`|d| = 0 < half 和`,无论 `<` 还是 `<=`,都返回 true(碰)。
- B:`|d| = half 和`。用 `<` 时:`half 和 < half 和` 为 false,不碰。用 `<=` 时:`half 和 <= half 和` 为 true,碰。
- C:`|d| = half 和 - eps < half 和`,无论 `<` 还是 `<=`,都 true(碰)。

关键:**只有 B(相切)**的判定依赖 `<` 还是 `<=`。其他情况符号无关。Casey 选 `<` 是因为「相切不算碰」更符合物理直觉。

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec3 { x: f32, y: f32, z: f32 }

impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y, self.z - o.z) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y, self.z + o.z) }
}

#[derive(Copy, Clone, Debug)]
struct AABB3 { center: Vec3, half: Vec3 }

#[inline]
fn aabb3_overlap(a: AABB3, b: AABB3) -> bool {
    let d = a.center.sub(b.center);
    let s = a.half.add(b.half);
    d.x.abs() < s.x && d.y.abs() < s.y && d.z.abs() < s.z
}

#[inline]
fn aabb3_contains(outer: AABB3, inner: AABB3) -> bool {
    let d = outer.center.sub(inner.center);
    d.x.abs() + inner.half.x <= outer.half.x
        && d.y.abs() + inner.half.y <= outer.half.y
        && d.z.abs() + inner.half.z <= outer.half.z
}

#[cfg(test)]
mod tests {
    use super::*;

    fn a(cx: f32, hx: f32) -> AABB3 {
        AABB3 {
            center: Vec3::new(cx, 0., 0.),
            half: Vec3::new(hx, 1., 1.),
        }
    }

    #[test]
    fn separated() {
        // 差 = 5,half 和 = 2,不碰
        assert!(!aabb3_overlap(a(0., 1.), a(5., 1.)));
    }

    #[test]
    fn touching_strict_lt() {
        // 差 = 2,half 和 = 2,严格 < 时不算碰
        assert!(!aabb3_overlap(a(0., 1.), a(2., 1.)));
    }

    #[test]
    fn just_inside() {
        // 差 = 1.99,half 和 = 2,碰
        assert!(aabb3_overlap(a(0., 1.), a(1.99, 1.)));
    }

    #[test]
    fn same_position() {
        assert!(aabb3_overlap(a(0., 1.), a(0., 1.)));
    }

    #[test]
    fn contains_exact_fit() {
        // outer half = 2,inner half = 1,中心相同,刚好包含
        let outer = AABB3 { center: Vec3::new(0.,0.,0.), half: Vec3::new(2.,2.,2.) };
        let inner = AABB3 { center: Vec3::new(0.,0.,0.), half: Vec3::new(1.,1.,1.) };
        assert!(aabb3_contains(outer, inner));
    }

    #[test]
    fn contains_offcenter_still_inside() {
        let outer = AABB3 { center: Vec3::new(0.,0.,0.), half: Vec3::new(2.,2.,2.) };
        let inner = AABB3 { center: Vec3::new(1.,0.,0.), half: Vec3::new(1.,1.,1.) };
        // |d.x| + inner.half.x = 1 + 1 = 2 = outer.half.x,用 <= 算包含
        assert!(aabb3_contains(outer, inner));
    }

    #[test]
    fn contains_too_big() {
        let outer = AABB3 { center: Vec3::new(0.,0.,0.), half: Vec3::new(2.,2.,2.) };
        let inner = AABB3 { center: Vec3::new(0.,0.,0.), half: Vec3::new(3.,1.,1.) };
        assert!(!aabb3_contains(outer, inner));
    }
}
```

### Rust 完整可跑示例

把 Lv2 的代码补全,加 main 演示。

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec3 { x: f32, y: f32, z: f32 }

impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y, self.z - o.z) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y, self.z + o.z) }
}

#[derive(Copy, Clone, Debug)]
struct AABB3 { center: Vec3, half: Vec3 }

#[inline]
fn aabb3_overlap(a: AABB3, b: AABB3) -> bool {
    let d = a.center.sub(b.center);
    let s = a.half.add(b.half);
    d.x.abs() < s.x && d.y.abs() < s.y && d.z.abs() < s.z
}

#[inline]
fn aabb3_contains(outer: AABB3, inner: AABB3) -> bool {
    let d = outer.center.sub(inner.center);
    d.x.abs() + inner.half.x <= outer.half.x
        && d.y.abs() + inner.half.y <= outer.half.y
        && d.z.abs() + inner.half.z <= outer.half.z
}

fn main() {
    // 多楼层示例
    let player = AABB3 {
        center: Vec3::new(100., 100., 32.),  // 一楼,z=0..64
        half: Vec3::new(16., 16., 32.),
    };

    let scenarios = [
        ("二楼怪(屏幕重叠,z 远)", AABB3 {
            center: Vec3::new(100., 100., 96.),
            half: Vec3::new(16., 16., 32.),
        }),
        ("一楼怪(同 z)", AABB3 {
            center: Vec3::new(100., 100., 32.),
            half: Vec3::new(16., 16., 32.),
        }),
        ("楼上沿与楼下沿相切(z=64)", AABB3 {
            center: Vec3::new(100., 100., 96.0),
            half: Vec3::new(16., 16., 31.999),  // 让它和 player 顶边相切
        }),
    ];

    for (name, b) in scenarios.iter() {
        println!("{}: overlap={}", name, aabb3_overlap(player, *b));
    }
}
```

**预期输出**:
```
二楼怪(屏幕重叠,z 远): overlap=false
一楼怪(同 z): overlap=true
楼上沿与楼下沿相切(z=64): overlap=true   (因 31.999 让差 < 和)
```
