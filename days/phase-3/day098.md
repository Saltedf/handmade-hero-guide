
# Day 098 · 法线贴图代码清理

> 昨天 Day 097 你把法线贴图塞进管线,光照效果出来了。但代码现在很乱——散落的 sample 调用、重复的 sRGB 转换、魔法数字 50.0 (shininess)、`Color` 和 `[f32; 4]` 混用。今天 Casey 不加新功能,**只重构**——把代码整理干净,为后面 Day 099-110 的环境贴图、反射、透视投影做准备。重构是工程能力的核心——很多程序员只会「加功能」,不会「清理」,结果项目越加越乱,最后无法维护。

## 0 · 为什么要有这一天

你的渲染器代码现在大概长这样(伪代码):

```rust
fn render_sprite(...) {
    let inv = m.inverse();
    for py in min_y..=max_y {
        for px in min_x..=max_x {
            let (u, v) = inv.mul_vec(...);
            let diffuse = sprite.diffuse.sample(u, v);
            if diffuse[3] < 0.01 { continue; }
            let normal = sprite.normal.sample_nearest(u, v);
            let surface_color = Color { r: diffuse[0], g: diffuse[1], b: diffuse[2] };
            let lit = phong_lighting(surface_color, normal, view, light,
                                     Color { r: 0.1, g: 0.1, b: 0.1 }, 50.0);  // 魔法数字
            // alpha 混合 6 行
            // ...
        }
    }
}
```

问题:
1. **魔法数字**:`50.0` shininess、`0.1` ambient、`0.01` alpha 阈值散落代码里,改一个忘改其他
2. **类型不统一**:`Color { r, g, b }` 和 `[f32; 4]` 互转,容易出错
3. **重复代码**:`inv.mul_vec` 套路在多个函数里重复
4. **抽象缺失**:`Sprite` 是裸字段集合,没有「概念」
5. **错误处理弱**:`sample` 假设 uv 在 [0,1],不验证
6. **测试缺失**:加新功能时不知道有没有破坏旧功能

重构后:
1. 魔法数字 → `const SHININESS: f32 = 50.0;` 或 config struct
2. 类型统一 → 全部用 `Color` 类型
3. 提取 `pixel_to_uv` 函数,消除重复
4. `Sprite` 抽象化,有 `sample_surface(u, v) -> SurfaceSample` 方法返回完整信息
5. `sample` 内部 clamp uv,文档清楚说明
6. 加单元测试,每个核心函数 5+ 测试

这是「**先让它工作,再让它正确,最后让它快**」原则——今天做「让它正确」。

心理锚点:看完今天,你的渲染器代码可读性 ×3,加新功能(Day 099 环境贴图)速度 ×2。你能解释「为什么重构和加功能是两种独立能力」。

## 1 · Casey 今天做了什么

Casey 今天做的事情(纯重构,无新功能):

1. **统一色彩类型**:把所有 `[f32; 4]` 改成命名 `Color` / `LinearColor` 类型
2. **提取魔法数字**:把 shininess、ambient、alpha 阈值移到 `RenderConfig` struct
3. **抽象 Sprite**:加 `sample_surface(u, v) -> SurfaceSample { color, normal, alpha }` 方法
4. **分解 render_sprite**:外层做 AABB + 像素遍历,内层 `shade_pixel` 做光照
5. **加文档**:每个函数加 `///` doc comment,说明参数和返回值
6. **加测试**:每个核心函数加 unit test

Casey 强调一个原则:**重构不改行为**。重构前后渲染输出必须**像素级一致**——任何变化都是 bug。

## 2 · 心智模型

### 费曼类比:整理厨房

想象你的厨房乱糟糟——锅碗瓢盆堆在水池里,调料瓶散落各处。每次做饭你都要花 5 分钟找东西。

**整理**:
- 锅碗归橱柜,按大小排
- 调料瓶归架子,标签朝外
- 刀具归刀架,锋利的一律朝下
- 每次用完归位

整理后:做饭时所有东西「**伸手就到**」,效率 ×2,出错率(用错调料)↓。

代码同理——重构就是「整理代码橱柜」。没有新功能,但代码「**容易找到位置加新功能**」。

### 严谨原理

#### 2.1 重构的定义

Martin Fowler 在 1999 年《重构:改善既有代码的设计》定义:**重构是「在不改变代码外部行为的前提下,改善其内部结构」**。

关键约束:
- **行为不变**:重构前后,程序对相同输入产生相同输出
- **小步进行**:每次只做一个小改动(提取函数、改名、移动字段)
- **测试保障**:每步重构后跑测试,确认没破坏

#### 2.2 重构的类型

常见的代码坏味道(bad smell)和对应重构手法:

| 坏味道 | 重构 |
|---|---|
| 重复代码 | 提取函数 |
| 长函数 | 分解函数 |
| 大类 | 提取类 / 移动字段 |
| 长参数列 | 引入参数对象 |
| 魔法数字 | 用常量替换 |
| 散弹式修改 | 移动函数 / 字段 |
| 数据泥团 | 提取类 |
| 基本类型偏执 | 引入类型 |
| switch 语句 | 多态替换 |

Casey 今天主要用「提取函数 + 引入类型 + 用常量替换」。

#### 2.3 Rust 特有的重构考虑

Rust 的 ownership 系统让某些重构在 C++/Java 里很常见但在 Rust 里复杂:

1. **共享所有权**:`Rc<Bitmap>` vs `Arc<Bitmap>` vs `&'a Bitmap`(生命周期)
2. **可变借用**:多个 sprite 共享一个 framebuffer,需要 `&mut` 分割借用
3. **Trait object vs 泛型**:`dyn Renderer` vs `impl Renderer`,性能 / 灵活性权衡
4. **生命周期标注**:重构可能引入或消除生命周期参数

Casey HH 用 C 没有 ownership 概念,但 Rust 翻译时要处理。

#### 2.4 重构的测试保障

**没有测试,不要重构**。重构前后跑同样的测试,如果输出像素级一致,说明重构成功。

```rust
#[test]
fn render_sprite_output_matches_canonical() {
    let framebuffer = render_test_scene();
    let canonical = include_bytes!("test_data/canonical_output.bin");
    assert_eq!(framebuffer.pixels, canonical);
}
```

`include_bytes!` 把测试数据嵌入二进制。Casey HH Day 200+ 加这种「**黄金测试**」(golden test)。

### Rust 完整重构示例

**重构前**(简化):

```rust
// 散落的代码
fn render_sprite(fb: &mut FB, sprite: &Sprite, ...) {
    let inv = m.inverse();
    for py in min_y..=max_y {
        for px in min_x..=max_x {
            let wx = px as f32 + 0.5;
            let wy = py as f32 + 0.5;
            let (u, v) = inv.mul_vec(wx - origin.x, wy - origin.y);
            if u >= 0.0 && u <= 1.0 && v >= 0.0 && v <= 1.0 {
                let diffuse = sprite.diffuse.sample(u, v);
                if diffuse[3] < 0.01 { continue; }
                let normal = sprite.normal.sample_nearest(u, v);
                let surface_color = Color { r: diffuse[0], g: diffuse[1], b: diffuse[2] };
                let lit = phong_lighting(surface_color, normal, view, light,
                                         Color { r: 0.1, g: 0.1, b: 0.1 }, 50.0);
                let bg = fb.pixels[py * fb.width + px];
                let inv_a = 1.0 - diffuse[3];
                fb.pixels[py * fb.width + px] = [
                    diffuse[3] * lit.r + bg[0] * inv_a,
                    diffuse[3] * lit.g + bg[1] * inv_a,
                    diffuse[3] * lit.b + bg[2] * inv_a,
                    diffuse[3] + bg[3] * inv_a,
                ];
            }
        }
    }
}
```

**重构后**:

```rust
// 配置常量
const ALPHA_DISCARD_THRESHOLD: f32 = 0.01;
const DEFAULT_AMBIENT: Color = Color { r: 0.1, g: 0.1, b: 0.1 };
const DEFAULT_SHININESS: f32 = 50.0;

#[derive(Copy, Clone)]
struct Color { r: f32, g: f32, b: f32 }

#[derive(Copy, Clone)]
struct RenderConfig {
    ambient: Color,
    shininess: f32,
    alpha_threshold: f32,
}

impl Default for RenderConfig {
    fn default() -> Self {
        Self {
            ambient: DEFAULT_AMBIENT,
            shininess: DEFAULT_SHININESS,
            alpha_threshold: ALPHA_DISCARD_THRESHOLD,
        }
    }
}

#[derive(Copy, Clone)]
struct SurfaceSample {
    color: Color,
    alpha: f32,
    normal: Vec3,
}

impl Sprite {
    /// 采样 sprite 在 (u, v) 处的完整表面信息
    /// uv 必须在 [0, 1],否则 clamp
    fn sample_surface(&self, u: f32, v: f32) -> SurfaceSample {
        let diffuse = self.diffuse.sample(u.clamp(0.0, 1.0), v.clamp(0.0, 1.0));
        let normal = self.normal.sample_nearest(u, v);
        SurfaceSample {
            color: Color { r: diffuse[0], g: diffuse[1], b: diffuse[2] },
            alpha: diffuse[3],
            normal,
        }
    }
}

#[derive(Copy, Clone)]
struct PixelCoord { px: usize, py: usize }

/// 把屏幕像素坐标变换到 sprite 局部 (u, v) 坐标
/// 如果返回 None,像素不在 sprite 内
fn pixel_to_uv(pixel: PixelCoord, origin: Vec2, inv: Mat2) -> Option<(f32, f32)> {
    let wx = pixel.px as f32 + 0.5;
    let wy = pixel.py as f32 + 0.5;
    let (u, v) = inv.mul_vec(wx - origin.x, wy - origin.y);
    if u >= 0.0 && u <= 1.0 && v >= 0.0 && v <= 1.0 {
        Some((u, v))
    } else {
        None
    }
}

/// 应用 Phong 光照
fn shade_pixel(
    sample: SurfaceSample,
    view: Vec3,
    light: Light,
    config: RenderConfig,
) -> Color {
    phong_lighting(sample.color, sample.normal, view, light, config.ambient, config.shininess)
}

/// 在 linear 空间做预乘 alpha 混合
fn blend_premul_linear(bg: [f32; 4], fg_color: Color, fg_alpha: f32) -> [f32; 4] {
    let inv_a = 1.0 - fg_alpha;
    [
        fg_alpha * fg_color.r + bg[0] * inv_a,
        fg_alpha * fg_color.g + bg[1] * inv_a,
        fg_alpha * fg_color.b + bg[2] * inv_a,
        fg_alpha + bg[3] * inv_a,
    ]
}

fn render_sprite(
    fb: &mut LinearFramebuffer,
    sprite: &Sprite,
    origin: Vec2,
    m: Mat2,
    light: Light,
    view: Vec3,
    config: RenderConfig,
) {
    let inv = m.inverse();
    let (min_x, max_x, min_y, max_y) = compute_aabb(&origin, &m, fb.width, fb.height);

    for py in min_y..=max_y {
        for px in min_x..=max_x {
            let pixel = PixelCoord { px, py };
            let (u, v) = match pixel_to_uv(pixel, origin, inv) {
                Some(uv) => uv,
                None => continue,
            };
            let sample = sprite.sample_surface(u, v);
            if sample.alpha < config.alpha_threshold { continue; }

            let bg = fb.pixels[py * fb.width + px];
            let lit = shade_pixel(sample, view, light, config);
            fb.pixels[py * fb.width + px] = blend_premul_linear(bg, lit, sample.alpha);
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_pixel_to_uv_inside() {
        let inv = Mat2 { m00: 1.0, m10: 0.0, m01: 0.0, m11: 1.0 };
        let origin = Vec2::new(10.0, 10.0);
        let pixel = PixelCoord { px: 50, py: 50 };
        let uv = pixel_to_uv(pixel, origin, inv);
        // (50.5 - 10, 50.5 - 10) = (40.5, 40.5),在 [0, 1] 外
        assert_eq!(uv, None);
    }

    #[test]
    fn test_blend_premul_full_opacity() {
        let bg = [0.5, 0.5, 0.5, 1.0];
        let fg = Color { r: 1.0, g: 0.0, b: 0.0 };
        let result = blend_premul_linear(bg, fg, 1.0);
        // alpha = 1,完全覆盖背景
        assert!((result[0] - 1.0).abs() < 1e-6);
    }

    #[test]
    fn test_sample_surface_clamps_uv() {
        // 假设已构造 sprite...
        // let sample = sprite.sample_surface(-0.5, 1.5);
        // 应该不 panic,uv 被 clamp
    }
}

fn main() {
    let config = RenderConfig::default();
    println!("shininess: {}", config.shininess);
    // 用 config 渲染
}
```

**重构总结**:
1. 魔法数字 → `const` + `RenderConfig` struct
2. `[f32; 4]` → `Color`(语义清晰)
3. 重复代码 → `pixel_to_uv`、`shade_pixel`、`blend_premul_linear` 三个小函数
4. 字段集合 → `SurfaceSample` 抽象
5. 内嵌 if → 提前 `continue`(扁平化)
6. 加 `#[cfg(test)]` 测试

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏代码重构的特殊考虑:

1. **性能敏感**:重构不能引入运行时开销。Rust 编译器通常能内联小函数(零开销),但要避免无意义的堆分配。
2. **热重载兼容**:如果项目用 cdylib 热重载(Day 30+),重构不能改变 ABI(接口签名)。
3. **数据布局**:游戏数据大量是 Vec<T>,重构时要保持 cache 友好(不要把 AoS 改成 SoA 临时,那需要重新评估性能)。

Casey HH 经常重构——每隔 20-30 天就会做一次大重构。这是项目能持续 667 天的关键。

### 3.2 · 🎨 图形学视角

图形代码重构的特殊模式:

1. **shader 重构**:GLSL/HLSL 代码同样要重构,但工具链不如 Rust 成熟(无 cargo、无 IDE 重构)
2. **pipeline state 抽象**:把「绑定纹理 → 设置混合模式 → draw」流程封装成 Pipeline 对象
3. **资源管理**:重构出 `ResourceManager`,统一加载/释放纹理、模型、shader

### 3.3 · 🐧 Linux 系统编程视角

Linux 工具链支持重构:

```bash
# 1. cargo fmt 自动格式化(让代码风格统一)
cargo fmt

# 2. cargo clippy 静态检查(找代码坏味道)
cargo clippy -- -W clippy::all
# 输出可能:
# warning: this expression has a high complexity score
# warning: using `clone` on a Copy type

# 3. cargo fix 自动修复简单问题
cargo fix --allow-dirty --allow-no-vcs

# 4. 用 rust-analyzer 在 IDE 里做「提取函数」「改名」等
sudo pacman -S rust-analyzer
# vim / emacs / vscode 都有 rust-analyzer 集成

# 5. 性能对比,确认重构没变慢
git stash  # 保存重构
cargo build --release && cp target/release/app /tmp/old
git stash pop
cargo build --release && cp target/release/app /tmp/new
perf stat /tmp/old
perf stat /tmp/new
```

### 3.4 · 🦀 Rust 生态视角

Rust 重构的几个利器:

1. **rust-analyzer**:VS Code / vim 的 LSP(语言服务器),提供「提取函数」「改名」「内联变量」等安全重构
2. **cargo fix**:自动应用 clippy/rustc 的 lint 建议
3. **cargo mutation**:变异测试,确认你的测试真的能捕获 bug
4. **`trait` 抽象**:把多个相似 struct 的共同行为提取成 trait
5. **`#[non_exhaustive]`**:防止下游过度匹配 enum,允许以后加变体

**Rust 重构比 C++ 容易**——ownership 系统让你不会意外引入悬垂引用,trait 系统让你不会意外破坏接口。

## 4 · 认知地图

### 4.1 上级

- **软件工程** — 代码可维护性的科学
- **代码坏味道 (code smells)** — Kent Beck / Martin Fowler 提出的反模式
- **持续重构 (continuous refactoring)** — 「每次加功能时顺手清理」的工作流

### 4.2 同级

| 工作 | 目的 | 时机 |
|---|---|---|
| 重构 (refactor) | 改善结构,行为不变 | 代码乱但功能正确 |
| 优化 (optimize) | 改善性能,行为可能微变 | 性能不够 |
| 修复 (bug fix) | 改正行为 | 测试失败 / 用户报告 bug |
| 加功能 (feature) | 新行为 | 需求变化 |

### 4.3 下级

- **提取函数 (extract function)** — 把内联代码块变成命名函数
- **引入类型 (introduce type)** — 用语义类型代替基本类型
- **移动字段 (move field)** — 把字段移到合适的 struct
- **重命名 (rename)** — 改善命名
- **测试覆盖 (test coverage)** — 重构的安全网

## 5 · 对照与变奏

### 重构 vs 重写

很多人面对乱代码,第一反应是「推倒重写」。这是错的——重写丢掉了原有代码的所有隐含知识(bug fix、边界处理、用户期望)。

**重构 vs 重写**:
- 重构:小步前进,行为不变,可回滚
- 重写:大爆炸,从零开始,不可回滚

Joel Spolsky 经典文章《Things You Should Never Do》痛骂 Netscape 6 重写灾难——重写让 Netscape 失去 3 年时间,被 IE 超越。Casey HH 自己也是「**永远重构,永不重写**」原则。

### 命令式重构 vs 函数式重构

命令式语言(Java/Python)的重构聚焦于对象、方法、字段。函数式语言(Haskell/OCaml/Rust 部分)重构聚焦于函数组合、类型代数。Rust 混合两种,工具链(尤其 trait + ownership)给重构独特挑战。

### 自动化重构工具的历史

- **Smalltalk 1990s**:第一个有完整重构工具的语言
- **Java IntelliJ/IDEA 2001**:把重构工具带给大众
- **Rust rust-analyzer 2018+**:rust-analyzer 实现大部分经典重构
- **未来**:AI 辅助重构(GitHub Copilot 等)正在出现

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:有人说「重构是浪费,直接加新功能更重要」。用 2 个具体例子反驳。

**参考解答**:
1. **加新功能慢**。乱代码里加功能要先理解旧代码,如果命名不清、结构乱,可能花 1 天才找到该加在哪。重构后(命名清晰、函数小、单一职责),加同样功能可能只要 1 小时。
2. **bug 增多**。乱代码里改一行可能破坏 3 处不相关的(因为隐藏依赖)。重构后(清晰接口、有测试),改动隔离,bug 率 ↓。

具体例子:Casey HH Day 200+ 加多线程,如果代码没重构过,几乎不可能;Day 105+ 切 OpenGL,代码必须先重构出清晰抽象。

### Lv2 · 动手实践

**题**:对你 Phase 2 / Phase 3 至今的代码做一次重构。具体:
1. 找一个最长的函数(超过 50 行)
2. 用「提取函数」拆成 3-5 个小函数
3. 把魔法数字提取成 const
4. 加 3+ 个单元测试
5. 跑测试,确认重构前后行为一致

完成标准:重构后代码行数可能不变(甚至增加,因为函数签名),但每个函数 < 20 行,有清晰单一职责。

**参考解答**:见 §2 重构示例。关键是「小步前进」——每次提取一个函数,跑测试,确认无破坏。

### Lv3 · 迁移设计

**题**:你的项目现在用 `[f32; 4]` 表示 RGBA。如果想换成 `Color { r, g, b, a }` 结构体,需要:
1. 改多少处代码?
2. 怎么保证不漏?
3. 性能影响(内存布局变化)?

提示:
- Rust 的类型系统:改 struct 定义,编译器自动找出所有使用点
- 内存布局:`[f32; 4]` 和 `Color { r, g, b, a }`(无 `#[repr(C)]`)布局可能不同,但通常 Rust 会优化成一样
- 用 `cargo check` 反复迭代,直到编译通过

### Troubleshooting

- **重构后编译失败** — 通常是类型不匹配。跟着 rustc 报错逐个修
- **重构后测试失败** — 行为变了,有 bug。git diff 找出哪个改动破坏了
- **rust-analyzer 重构出错** — LSP 工具不完美,大型重构可能失败。改用 cargo fix + 手动
- **clippy 太啰嗦** — 调级别:`-W clippy::all`(默认)vs `-W clippy::pedantic`(严格)vs `-A clippy::style`(忽略风格)
