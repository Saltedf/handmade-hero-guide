# Day 180 · 加调试图表

> Day 179 把历史存下来了,但只是数字。今天 Casey 在游戏画面上画曲线图——X 轴帧号,Y 轴 cycle 数。后面所有 debug 可视化的基础。

## 0 · 为什么要有这一天

数字会骗你。

```
avg=8ms  min=5ms  max=42ms
```

你看这串数字,可能以为"基本 5-8ms,偶尔 42ms"。但实际上"42ms"是过去 5 分钟唯一的一次,还是 60 次中的一帧?数字看不出。曲线图一眼看出:

```
cycle
  ^
  |     *                       *    <- spike
  |  * * * *   * * * * *   * * * * *
  |  * * * * * * * * * * * * * * * *
  +----------------------------------> frame
```

人类大脑**视觉皮层**(50% 的大脑皮层处理视觉)看图比看数字快 100 倍。工业级 profiler(Unreal Insights、Chrome DevTools)第一屏都是曲线图。

今天 Casey 做的:
1. 在游戏画面上叠加(overlay)一张曲线图
2. X 轴是最近 300 帧
3. Y 轴是 cycle 数(自适应 scale)
4. 红线标注超过某阈值的"坏帧"

心理锚点:看完今天,你能写出"画一条由 N 个点连成的折线"的最朴素代码,并理解"立即模式渲染(immediate-mode rendering)"和 retained-mode 渲染的差别。

### 2.1 framebuffer 上画线段

回顾 Phase 1 的 framebuffer:

```rust
pub struct Framebuffer {
    pub width: u32,
    pub height: u32,
    pub pixels: Vec<u32>,  // 0xAABBGGRR (ARGB)
}
```

画一个点:

```rust
fn set_pixel(fb: &mut Framebuffer, x: i32, y: i32, color: u32) {
    if x >= 0 && y >= 0 && (x as u32) < fb.width && (y as u32) < fb.height {
        fb.pixels[(y as u32 * fb.width + x as u32) as usize] = color;
    }
}
```

画一条线段最简单的算法是 **Bresenham 算法**(1962 年发明,至今还在用)。原理:沿主轴(x 或 y)步进,次轴用累积误差决定何时+1。整条线只用整数运算,极快。

```rust
fn draw_line(fb: &mut Framebuffer, x0: i32, y0: i32, x1: i32, y1: i32, color: u32) {
    let (mut x, mut y) = (x0, y0);
    let dx = (x1 - x0).abs();
    let sx = if x0 < x1 { 1 } else { -1 };
    let dy = -(y1 - y0).abs();
    let sy = if y0 < y1 { 1 } else { -1 };
    let mut err = dx + dy;

    loop {
        set_pixel(fb, x, y, color);
        if x == x1 && y == y1 { break; }
        let e2 = 2 * err;
        if e2 >= dy { err += dy; x += sx; }
        if e2 <= dx { err += dx; y += sy; }
    }
}
```

**算法解释**:
- `dx`, `dy` — x 和 y 方向的距离(dy 取负便于统一公式)
- `sx`, `sy` — 步进方向(+1 或 -1)
- `err` — 误差累积,决定次轴何时步进
- `2 * err >= dy` 时 x 步进,`2 * err <= dx` 时 y 步进
- 循环到 (x1, y1) 停止

这是 casey 在 Phase 1 day 22 就讲过的算法。今天复用它画曲线。

### 2.2 画矩形(图表外框)

```rust
fn draw_rect_outline(fb: &mut Framebuffer, x: i32, y: i32, w: i32, h: i32, color: u32) {
    draw_line(fb, x, y, x + w, y, color);           // top
    draw_line(fb, x, y + h, x + w, y + h, color);   // bottom
    draw_line(fb, x, y, x, y + h, color);           // left
    draw_line(fb, x + w, y, x + w, y + h, color);   // right
}
```

矩形 = 4 条线段。

### 2.3 画曲线图

```rust
pub fn draw_cycle_graph(
    fb: &mut Framebuffer,
    history: &RingBuffer<u64, 300>,
    x: i32, y: i32, w: i32, h: i32,
) {
    let bg = 0xFF101010;  // 半透明黑
    let border = 0xFF00FF00;  // 绿
    let line = 0xFFFFFF00;  // 黄
    let spike = 0xFFFF0000;  // 红

    // 背景
    draw_rect_filled(fb, x, y, w, h, bg);
    draw_rect_outline(fb, x, y, w, h, border);

    // 找最大值用于自适应 scale
    let max_cycles = history.iter_recent().copied().max().unwrap_or(1).max(1);

    // 画曲线
    let frames: Vec<u64> = history.iter_recent().collect();
    for i in 1..frames.len() {
        let x0 = x + ((i - 1) as i32 * w / frames.len() as i32).max(1);
        let x1 = x + (i as i32 * w / frames.len() as i32).max(1);
        let y0 = y + h - (frames[i - 1] as i32 * h / max_cycles as i32);
        let y1 = y + h - (frames[i] as i32 * h / max_cycles as i32);
        let c = if frames[i] > max_cycles * 4 / 5 { spike } else { line };
        draw_line(fb, x0, y0, x1, y1, c);
    }
}
```

**逐段**:
- `max_cycles` 自适应 scale,曲线占满图表高度。`max(1)` 防止除 0
- `x as i32 * w / frames.len() as i32` — 把"第 i 帧"映射到像素 x 坐标
- `y + h - (cycles * h / max_cycles)` — 把"cycle 数"映射到像素 y 坐标。注意 y 轴翻转(屏幕坐标 y 向下增长)
- 阈值检查:超过 80% 的画红,其他画黄

### 2.4 即时模式渲染 vs 保留模式

Casey 的画图函数每帧调用一次,**没有持久的"Chart 对象"**。这叫 immediate-mode 渲染:

```rust
// 每帧调用
fn draw_debug_overlay(fb: &mut Framebuffer, history: &History) {
    draw_cycle_graph(fb, &history.frames, 10, 10, 600, 200);
    draw_text(fb, "Frame time", 10, 5);
}
```

游戏循环每帧调一次。下一帧如果数据变了,图自动变。**没有显式刷新**。

对比 retained-mode(传统 GUI):你要创建一个 `Chart` 对象,`chart.set_data(...)`,等"重绘事件"才更新。

| | immediate-mode | retained-mode |
|---|---|---|
| API 风格 | 每帧调函数 | 创建对象 + 改属性 |
| 状态 | 数据驱动 | 控件自己存 |
| 同步 | 自动(每帧重算) | 手动(事件触发) |
| 适合 | 游戏、调试 UI | 桌面应用 |

Casey 后面 day 196 的整个 debug UI 都用 immediate-mode。

### 2.5 Bresenham 算法的直觉推导

为什么 Bresenham 全用整数就能画直线?来手推一遍。假设我们要画 (0,0) 到 (5,2) 的直线。

**理想线段**:`y = (2/5) x`,即每 x 加 1,y 加 0.4。x=1 时 y=0.4,x=2 时 y=0.8,x=3 时 y=1.2……

**问题**:像素是整数坐标,不能画 (1, 0.4)。我们要"四舍五入"决定 y 取 0 还是 1。朴素做法 `y = round((2/5) * x)`——但浮点 round 慢。

**Bresenham 的洞察**:跟踪一个**累积误差** e,代表"理想 y 和实际 y 的差"。e 初始为 0。每次 x 加 1,e 加上斜率(2/5,即 dy/dx)。

```
x=0  e=0     y=0     (e < 0.5,不+1)
x=1  e=0.4   y=0
x=2  e=0.8   y=1     (e ≥ 0.5,+1,e -= 1 = -0.2)
x=3  e=0.2   y=1
x=4  e=0.6   y=2     (e ≥ 0.5,+1,e -= 1 = -0.4)
x=5  e=0.0   y=2     终点
```

**全整数化**:为了避免浮点,把所有数乘 2*dx。e 初始 = 2*dy - dx,递推:e += 2*dy,如果 e ≥ 0 则 y += sy,e -= 2*dx。

这就是 §2.1 里 `err = dx + dy`(等价于把 dy 取负后的 2*dy - dx)的来历。**只用加减和比较,无乘除**——所以适合 1960 年代的硬件,也适合今天 SIMD 并行。

### 2.6 数据归一化的两种策略

把"cycle 数 1000-50000"映射到"像素 y 0-200"叫**归一化**(normalization)。两种主流策略:

**线性归一化**:`y = (cycles / max) * height`。优点:看绝对值。缺点:一个 outlier spike 把其他全压扁。

**对数归一化**:`y = log(cycles + 1) / log(max + 1) * height`。优点:压缩动态范围,outlier 不压扁细节。缺点:看着不直观(对数刻度)。

```
线性归一化:对 [100, 200, 300, 5000]
   100 → 4%
   200 → 8%
   300 → 12%
   5000 → 100%(其他都看不见)

对数归一化:
   log(101)  ≈ 4.6 → 28%
   log(201)  ≈ 5.3 → 32%
   log(301)  ≈ 5.7 → 35%
   log(5001) ≈ 8.5 → 100%(其他都清晰可见)
```

Casey 选线性(简单),但如果你的 profiler 数据有大动态范围,改对数只需一行:

```rust
let normalized = ((cycles.max(1) as f64).ln() / (max_cycles.max(1) as f64).ln() * h as f64) as i32;
```

### 2.7 颜色编码

为什么 cycle 数高用红色、低用绿色?这是**红绿灯直觉**:

```
cycles < max * 50%   → 绿(0xFF00FF00)
cycles < max * 80%   → 黄(0xFFFFFF00)
cycles >= max * 80%  → 红(0xFFFF0000)
```

人类对颜色的反应比数字快。**颜色梯度**(color gradient)在数据可视化里是一门学科:Viridis / Inferno / Plasma 是 matplotlib 默认的"色盲友好"梯度。Casey 用最朴素的红黄绿,因为:

- 红 / 黄 / 绿在 LCD 屏幕都鲜艳
- 即使色盲(红绿色盲占男性 8%)也能区分亮度
- 不需要调色板配置

工业级 profiler(VTune / Superluminal)有更复杂的颜色映射,但 debug UI 上简单比好看重要。

### 2.8 hover 与交互(immediate-mode)

profiler UI 不只是被动显示——你要能 hover 看精确值,点击展开。这些交互在 immediate-mode 里怎么写?

**hover 检测**:每帧检查鼠标坐标是否在图区域内:

```rust
let mouse_x = input.mouse_x;
let mouse_y = input.mouse_y;
let hovered = mouse_x >= graph_x && mouse_x < graph_x + graph_w
           && mouse_y >= graph_y && mouse_y < graph_y + graph_h;

if hovered {
    // 算鼠标对应哪一帧
    let frame_idx = (mouse_x - graph_x) * frames.len() / graph_w;
    let cycles = frames[frame_idx];
    // 在鼠标旁画 tooltip
    draw_text(fb, &format!("frame {}: {} cycles", frame_idx, cycles), mouse_x + 10, mouse_y);
}
```

每帧重新算 hovered,没有"hover state"对象。鼠标移动时下一帧自动反映——这就是 immediate-mode 的简洁。

**点击处理**:每帧检查鼠标按键状态(按下/松开边沿):

```rust
let clicked = hovered && input.mouse_left_just_pressed;
if clicked {
    // 选中这一帧,可能在别处展开详情
    selected_frame = Some(frame_idx);
}
```

`mouse_left_just_pressed` 是边沿检测——只在按下瞬间为 true,持续按住为 false。 Casey day 196 详细讲 immediate-mode 的输入处理。

### 2.9 文字渲染的难点

画数字(如 "42ms")在 framebuffer 上比想象复杂:

1. **字体**:需要一个 font 文件(如 DejaVu Sans)或内嵌位图字体
2. **glyph** (字符形状):每个字符对应一个 glyph(黑白像素图)
3. **布局**:字符间距、行高、对齐
4. **抗锯齿**:位图 glyph 锯齿严重,矢量字体要贝塞尔曲线渲染

工业级方案:**stb_truetype**(C 库,加载 TTF)+ **rusttype** / **ab_glyph**(Rust 等价)。但**初学版**可以用最朴素的**5x7 位图字体**:每个字符 5×7 像素,硬编码数组:

```rust
const FONT_5X7: &[(u8, [u8; 7])] = &[
    (b'0', [0b01110, 0b10001, 0b10011, 0b10101, 0b11001, 0b10001, 0b01110]),
    (b'1', [0b00100, 0b01100, 0b00100, 0b00100, 0b00100, 0b00100, 0b01110]),
    // ... A-Z, a-z, symbols
];
```

每 bit 一个像素,1=亮,0=暗。5×7 像素够小但可读。Casey day 196 之前用这种最朴素的字体。

### 3.2 · 🎨 图形学视角

画曲线时,如果是连续的线(不是离散点),要考虑**反走样(anti-aliasing)**。简单 Bresenham 是"硬边",曲线有锯齿:

```
* * * *
* *
    * *
       * *
```

工业级渲染用 **MSAA**(多重采样抗锯齿)或 **FXAA**(后处理抗锯齿)。Casey 在 day 180 不做 AA——debug UI 要的就是看得清,锯齿不影响判断。

但**颜色空间**要注意。在 OpenGL 后期(Day 235+),framebuffer 默认 sRGB,颜色要转线性空间才能正确混合。Casey day 256 详细讲。

### 3.5 · 🐧 Linux 系统编程视角(共享内存 framebuffer)

## 5 · 对照与变奏

**线段算法的历史**:

- 1962:Bresenham 在 IBM 发明,初版用 integer 运算
- 1965:Pitteway 改进,统一直线 / 圆 / 椭圆
- 1986:Wu 加反走样(加权平均)
- 1990s:GPU 普及,线段硬件化
- 2000s:shader 可编程,程序化线段

**GPU 画线**:

OpenGL 用 `glDrawArrays(GL_LINES, 0, 2)`。线宽是 1 像素(粗线需要 geometry shader)。GL 4.0+ 有 `GL_LINE_WIDTH` 但 driver 支持不一。

Day 235 切到 OpenGL 后,debug UI 仍然可以用 CPU 画到 framebuffer,然后上传给 OpenGL 当纹理。或者完全切到 GL drawing。

### 与 Unreal Insights / Chrome DevTools 的可视化对比

**Unreal Insights**:多 tab 视图,Timing Insights 显示帧级别 Gantt 图,可缩放到 ns。颜色用"asset 类型"编码(actor / component / system)。基于 trace 服务,支持远程分析。

**Chrome DevTools / Firefox Profiler**:Web 性能 profiler,Timeline 显示 60 fps 目标线,可看到 main / GPU / network 多轨道。用 flame chart 展示调用栈。

**Casey day 180**:折线图 + 简单颜色梯度。够诊断问题,不适合"高级用户"。

共同点:**都是 immediate-mode**(每帧重画),都基于 ring buffer 历史。差异在**复杂度**——商业产品的 UI 几万行,Casey 的 100 行。

### 与 Bevy / egui 的对比

Bevy 推荐用 `bevy_egui` 做 debug UI——egui 是成熟的 immediate-mode GUI 库。但 Bevy 引擎本身**不强依赖 egui**,你也能用其他 UI 或自己写。

egui 的 plot 模块比 Casey day 180 复杂得多——支持:
- 多轴(左右 Y 轴独立)
- 缩放 / 平移(滚轮 / 拖拽)
- 鼠标 hover 显示精确值
- 自动 legend
- 数据点动画

代价是 egui 自己 ~50000 行,编译时间几秒。Casey 的 100 行手写 demo **够用且可读**,这是教学和工程的差别。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:immediate-mode 渲染比 retained-mode "快"还是"慢"?为什么?

**参考解答**:
- **慢**:immediate-mode 每帧重画所有元素,即便没变
- **快**:没有"控件状态同步"开销,数据直接到 GPU
- 实际**差不多**——对游戏(60fps 重画本来就够)无差别
- immediate-mode 的真正优势不是速度,是**简单**和**自动同步**——程序员不用维护控件树

### Lv2 · 动手实践

**题**:写一个完整的最小曲线图 demo,要求:
- 自己写 framebuffer(`Vec<u32>` 模拟)
- 实现 Bresenham 画线
- 画 300 点的曲线
- 输出成 PPM 文件(可以用 `eog` 看)

**参考解答**:

```rust
use std::fs::File;
use std::io::Write;

const W: usize = 800;
const H: usize = 400;

struct Framebuffer {
    pixels: Vec<u32>,
}
impl Framebuffer {
    fn new() -> Self { Self { pixels: vec![0xFF000000; W * H] } }
    fn set(&mut self, x: i32, y: i32, c: u32) {
        if x >= 0 && y >= 0 && (x as usize) < W && (y as usize) < H {
            self.pixels[(y as usize) * W + (x as usize)] = c;
        }
    }
    fn save_ppm(&self, path: &str) {
        let mut f = File::create(path).unwrap();
        writeln!(f, "P3\n{} {}\n255", W, H).unwrap();
        for p in &self.pixels {
            let r = (p >> 16) & 0xFF;
            let g = (p >> 8) & 0xFF;
            let b = p & 0xFF;
            write!(f, "{} {} {}\n", r, g, b).unwrap();
        }
    }
}

fn draw_line(fb: &mut Framebuffer, x0: i32, y0: i32, x1: i32, y1: i32, c: u32) {
    let (mut x, mut y) = (x0, y0);
    let dx = (x1 - x0).abs();
    let sx = if x0 < x1 { 1 } else { -1 };
    let dy = -(y1 - y0).abs();
    let sy = if y0 < y1 { 1 } else { -1 };
    let mut err = dx + dy;
    loop {
        fb.set(x, y, c);
        if x == x1 && y == y1 { break; }
        let e2 = 2 * err;
        if e2 >= dy { err += dy; x += sx; }
        if e2 <= dx { err += dx; y += sy; }
    }
}

fn main() {
    let mut fb = Framebuffer::new();

    // 假数据:300 帧 cycle 数,模拟有 spike
    let data: Vec<u32> = (0..300).map(|i| {
        let base = 5000u32;
        let noise = ((i * 17) % 100) as u32;
        let spike = if i == 50 || i == 180 { 15000 } else { 0 };
        base + noise + spike
    }).collect();

    let max = *data.iter().max().unwrap() as i32;
    let left = 50;
    let right = W as i32 - 50;
    let top = 30;
    let bottom = H as i32 - 30;

    // 外框
    draw_line(&mut fb, left, top, right, top, 0xFFFFFFFF);
    draw_line(&mut fb, left, bottom, right, bottom, 0xFFFFFFFF);
    draw_line(&mut fb, left, top, left, bottom, 0xFFFFFFFF);
    draw_line(&mut fb, right, top, right, bottom, 0xFFFFFFFF);

    // 曲线
    for i in 1..data.len() {
        let x0 = left + (i as i32 - 1) * (right - left) / data.len() as i32;
        let x1 = left + i as i32 * (right - left) / data.len() as i32;
        let y0 = bottom - data[i - 1] as i32 * (bottom - top) / max;
        let y1 = bottom - data[i] as i32 * (bottom - top) / max;
        let color = if data[i] > max * 4 / 5 { 0xFFFF0000 } else { 0xFFFFFF00 };
        draw_line(&mut fb, x0, y0, x1, y1, color);
    }

    fb.save_ppm("/tmp/debug_graph.ppm");
    println!("saved to /tmp/debug_graph.ppm (view with: eog /tmp/debug_graph.ppm)");
}
```

**完成标准**:运行后 `/tmp/debug_graph.ppm` 存在,打开能看到黄线曲线 + 两个红 spike。

**Troubleshooting**:

- PPM 文件巨大 — P3 是文本格式,改 P6(二进制)小 4 倍
- 颜色错 — PPM 的 ARGB 排列和 framebuffer 不同,检查 channel 顺序
- Bresenham 漏点 — 检查 sx/sy 符号(差一就漏一行)
- **曲线断开** — 端点重合时 Bresenham 可能画一个像素,检查 (x0, y0) == (x1, y1) 时的行为
- **PPM 显示倒置** — PPM 从上到下,framebuffer 也从上到下,但 y 坐标增长方向相同。如果你画时 y 减小(向上),记得 PPM 渲染时 y 增长向下
