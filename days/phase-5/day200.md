
# Day 200 · 调试元素布局

> Day 199 你写了 20 个 debug widget——button、slider、checkbox、tooltip、color picker——它们全都用绝对坐标硬编码到屏幕上。第一周你觉得挺好,跑到第二周你打开 debug overlay 一看:右上角的性能图表盖住了下面的变量列表;你刚加的一个内存分析 widget,跟原本的 sprite viewer 重叠了;你想给主菜单底下塞一排快捷按钮,发现要么自己手算十几个 `(x, y)`,要么把所有 widget 推倒重来。今天 Casey 给这套 immediate-mode UI 装上**layout 引擎**——`vertical` / `horizontal` / `grid`,widget 一加入就自动定位,你写 UI 像堆 Lego。

## 0 · 为什么要有这一天

让我把镜头拉近,真实地体验一下手写坐标的痛苦。

你跟着 Day 199 写了一个 `DebugUi`,加 button 的 API 是 `ui.button(x, y, w, h, label)`。第一天的代码:

```rust
ui.button(10.0, 10.0, 80.0, 24.0, "Save");
ui.button(10.0, 38.0, 80.0, 24.0, "Load");  // 紧跟下面,留 4px 间距
ui.button(10.0, 66.0, 80.0, 24.0, "Quit");
```

看起来还行。但第三天你想"把 Save 改成 100px 宽,因为要加图标",你就要重新算 Load 和 Quit 的 x。第七天你说"加个 Apply 按钮,放在 Save 后面",你又要算 Save 100 + 间距 4 + Apply 80 = 184。第二十天的某次重构,你想把这一组按钮整体右移 50px——`x = 10.0` 改成 `x = 60.0`,但你**漏改了一个**,某个 button 飘到屏幕外。

这就是手写坐标的**根本病因**:**坐标是绝对值,改一处影响多处,人脑是差劲的算坐标机器**。工业级 UI 框架——从 1980 年代的 Motif,到 1990 年代的 Java Swing,到 2010 年代的 CSS flexbox——全都用**layout 系统**:你声明"我想把这组 widget 垂直排""我想把这组 widget 三列排",框架**自动算坐标**。改一处不会影响别处,因为坐标不是你算的。

layout 系统的核心抽象叫 **cursor**(游标)。想象打字机:字头从纸的左上角开始,每打一个字向右走一格,打完一行按回车纸往上一格、字头回左边。layout 系统就是这个打字机字头——你 `ui.button("Save")`,框架"打字"在 cursor 当前位置,cursor 自动推进;你 `ui.newline()` 或换 layout,cursor 换行。整个屏幕的 widget **跟着代码顺序自然排布**,你永远不用算坐标。

但 layout 系统不只是 cursor 推进。工业级 layout 要处理:widget 大小**自适应**(文字长的 button 自动宽)、**嵌套**(vertical 里嵌 horizontal 里再嵌 vertical)、**间距**(item spacing / window padding)、**对齐**(左对齐 / 右对齐 / 居中)、**wrap**(超出宽度自动换行)、**滚动**(内容超视口可滚)。每一项都是一个独立的工程问题。

今天 Casey 做的是 layout 的**最小可用子集**——`Layout::Vertical` 和 `Layout::Horizontal` 两种模式 + 一个 cursor 推进 + 一个 layout 栈支持嵌套。这个子集**足以让 debug overlay 看起来整齐**,又**不超过 immediate-mode 风格的简洁边界**。Casey 在视频里特别强调:debug UI **不需要 CSS flexbox 那种强大**,只要 button 别重叠就行。简单、够用、可扩展——这是 Handmade Hero 整体哲学在 UI 层的投影。

**学完今天,你应该能**:
- 解释 immediate-mode layout 为什么用 cursor 而 retained-mode 用 layout manager
- 实现 `ui.vertical()` / `ui.horizontal()`,支持任意层嵌套
- 理解 layout 栈的工作原理(push 保存状态、pop 恢复 + 推进 cursor)
- 解释 CSS flexbox 比 Casey 的 cursor 复杂在哪(自适应大小、wrap、align、justify)
- 看 `egui` / `taffy` / `iced` 的 layout 源码,能识别"这是 cursor 推进"和"这是 flex 算法"

## 1 · Casey 今天做了什么

Casey 这一天的工作量不大,但建立了一个**关键抽象**。让我把过程拆开:

1. **`Ui` struct 加 layout 字段**。原来的 `Ui` 只有 `cursor_x` / `cursor_y`,Casey 加 `layout: Layout`(当前模式)、`max_in_perpendicular: f32`(记录交叉轴最大尺寸,用于父 layout 推进 cursor)、`layout_stack: Vec<...>`(嵌套保存)。

2. **定义 `Layout` enum**。两种模式:`Vertical` 和 `Horizontal`。每个模式可以带 `spacing: f32`(widget 间距)。

3. **实现 `ui.vertical(|ui| { ... })`**。这是一个高阶函数——接受一个闭包,闭包里调 `ui.button()`。`vertical` 在闭包前 push 旧状态、设置 `Layout::Vertical`、清零 `max_in_perpendicular`,闭包后 pop 恢复 + 推进 cursor。

4. **修改 widget 函数**。`ui.button(label)` 不再接受 `x, y` 参数,而是从 `cursor_x / cursor_y` 读位置,然后**根据当前 layout 自动推进 cursor**——vertical 推进 `cursor_y`,horizontal 推进 `cursor_x`,同时更新 `max_in_perpendicular`。

5. **加 spacing**。`button()` 后,如果当前 layout 是 vertical,cursor_y 加 `item_spacing`;如果是 horizontal,cursor_x 加 `item_spacing`。这一行让 widget 之间有 4px 间隙而不是挤在一起。

6. **演示嵌套**。Casey 在视频里写了一段:`ui.vertical(|| { ui.horizontal(|| { ui.button("A"); ui.button("B"); }); ui.button("C"); })`,展示嵌套 layout 的 cursor 自动跳回父级。

这集产出大约 100 行 layout 代码,但**改变了 debug UI 的整个使用方式**——从此你写 debug overlay 像写 HTML,不用算坐标。

## 2 · 心智模型

### 2.0 类比:打字机的回车换行

我打个比方。你坐在一台 1960 年的机械打字机前。纸上有个字头当前停留的位置——这就是 cursor。你按一个字母键,**字头在那个位置打字,然后字头自动右移一格**。你打了一行字,字头走到纸的最右边——你按"回车"键,**字头跳回最左边,纸往上卷一格**。

这套机械逻辑就是 layout 的根本:**字头自动跟踪位置,你只管"打什么字",不用管"打在哪"**。

现在映射到 UI:

- **打字机的字头** = layout 系统的 cursor `(x, y)`
- **按字母键** = `ui.button(label)` ——在 cursor 位置画 widget,cursor 推进
- **回车换行** = vertical layout ——每打完一个 widget,cursor y 加一档
- **横向打字不打换行** = horizontal layout ——cursor x 推进,y 不动
- **缩进段落** = 嵌套 layout ——`ui.vertical(|| { ui.horizontal(|| { ... }); })`,horizontal 里的 widget 先在缩进位置横排,完后回到外层 vertical 继续

这个比方的关键洞察:**layout 系统是"打字机的字头"软件化**。你打字时**绝对不会**先想"这个字打在 (124, 87)"——你只管按字母,字头自己走。Casey 的 layout 系统,让你写 UI 时也不算坐标——`ui.button("Save")`、`ui.button("Load")`,框架自己推 cursor,button 自动从上到下排。

### 2.0.1 Box / Flex / Grid:三种 layout 抽象

历史上 layout 系统有三大流派,每一种都用不同的"打字机"。

**Box model**(传统,1980s-)。每个 widget 是一个矩形盒子,有 margin / border / padding / content 四层。Layout 就是把盒子按某种顺序堆——vertical box 把盒子上下堆,horizontal box 把盒子左右排。**这是 Casey 今天的方案**:简单的 stack + spacing,无自适应大小。

**Flexbox**(CSS3,2009-)。一维 layout,但**自适应**——容器宽 800px,内部 3 个 widget 各自声明"我想要 100px"或"我可以缩到 50px"或"我可以扩到 1/3 容器宽",flexbox 算法分配空间。这就是 web 网页为什么能在不同分辨率下自动适应——你声明"主侧栏占 1/4,内容区占 3/4",浏览器算具体像素。

**Grid**(CSS3,2017-)。二维 layout——你声明一个 N×M 网格,widget 放在 `(row, col)`,可以 span 跨多个格子。Grid 比 flexbox 强大,适合**数据表格、仪表盘**这种规则结构。

Casey day 200 选 box model 的原因:**immediate-mode UI 不需要复杂 layout**。Immediate-mode 的优势是简单——每帧重新声明 widget,顺序固定,所以 cursor 推进就够了。如果你需要 flexbox 那种自适应,意味着 widget 大小会变,immediate-mode 的"上一帧状态"就难维护了。**Simple is beautiful**——Casey 的 box model 100 行代码,够 debug overlay 用 5 年;flexbox 引擎(taffy)几千行代码,做 debug UI overkill。

### 2.0.2 immediate-mode 的 layout 是控制流驱动

这是 immediate-mode UI 区别于 retained-mode 的**根本特征**。看两段代码做同一个 UI(垂直三个 button):

**immediate-mode(Rust + Casey 风格)**:
```rust
ui.vertical(|ui| {
    ui.button("Save");
    ui.button("Load");
    ui.button("Quit");
});
```

**retained-mode(C++ + Qt 风格)**:
```cpp
auto* layout = new QVBoxLayout;
auto* saveBtn = new QPushButton("Save");
auto* loadBtn = new QPushButton("Load");
auto* quitBtn = new QPushButton("Quit");
layout->addWidget(saveBtn);
layout->addWidget(loadBtn);
layout->addWidget(quitBtn);
window->setLayout(layout);
```

两种代码**做的事一样**,但思维方式完全不同:

- **immediate-mode**:代码顺序 = 视觉顺序。`ui.vertical` 是闭包,闭包里的 `ui.button` 顺序执行,cursor 顺序推进。你**沿着代码读**就能想象出 UI 长什么样。每帧执行一次。
- **retained-mode**:代码创建一堆对象,塞进 layout,框架**一次性算位置**。对象创建后位置不变。后续运行时 framework 直接用缓存的位置画。

immediate-mode 的优势是**简单**——没有 widget 对象,没有 layout 对象,只有 cursor。劣势是**每帧重算**(虽然 fast,但本质是重复)。retained-mode 优势是**解耦**(layout 与 widget 分离,可动态调整),劣势是**复杂**(对象生命周期、内存管理)。

Casey 的 day 200 layout 系统是 immediate-mode 风格的极简实现——**cursor 推进是同步的、即时的、单次的**。你写 `ui.button("Save")`,这一行执行完,cursor 已经推进到下一个位置。下一行 `ui.button("Load")` 直接用新 cursor。

### 2.0.3 layout 栈:嵌套的"保存/恢复"

光有 cursor 推进不够。设想这个 UI:

```rust
ui.vertical(|ui| {            // 外层 vertical:cursor_y 推进
    ui.button("Top");          // y=10
    ui.horizontal(|ui| {       // 内层 horizontal:cursor_x 推进
        ui.button("A");        // x=10, y=35
        ui.button("B");        // x=90, y=35
    });                        // ← horizontal 结束,要做点什么
    ui.button("Bottom");       // 应该在 y=35+24=59(在 horizontal 下面)
});
```

问题是:**`horizontal` 闭包结束时,你怎么知道父 `vertical` 的 cursor 应该推进多少**?horizontal 里两个 button 各 80px 宽,但 y 不变。所以 horizontal 结束后,外层 vertical 的 cursor_y 应该推进一个 button 高(24px),cursor_x 应该恢复到外层 vertical 的初始 x(因为 horizontal 已经"消费"了这段 x 范围)。

这就是 **layout 栈**——每次 `begin_X` 时 push 当前状态到栈,`end_X` 时 pop。栈保存的内容包括:`cursor_x`、`cursor_y`、`layout`(父级 layout 模式)、`max_in_perpendicular`(交叉轴最大尺寸,用于父级推进)。

```
ui.vertical(...) 时栈的变化:
  push (cursor_x=10, cursor_y=10, layout=Outer, max_w=0)
  → 内层 horizontal:
      push (cursor_x=10, cursor_y=35, layout=Vertical, max_w=0)
      → button("A"):cursor_x 推进到 90,horizontal 模式 max_h 更新为 24
      → button("B"):cursor_x 推进到 170,max_h 还是 24
      pop:外层 cursor_y += max_h(24)→ cursor_y=59,外层 cursor_x 保持 10
  → button("Bottom"):在 (10, 59)
  pop
```

栈的关键作用是**让 nested layout 的 cursor 推进"自洽"**——内层 layout 消费了多少交叉轴空间,外层就推进多少。这是 layout 嵌套的物理本质。

### 2.0.4 size negotiation:widget 怎么知道自己多大

layout 系统要工作,widget 必须知道自己有多大——button 多宽?text 多高?slider 多宽?工业级 UI 框架有三种 size 策略:

**固定 size**:`button(label, Vec2::new(80.0, 24.0))`。你传 w/h,框架用。简单但不灵活——不同语言的 label 长度不一样,"Save" 是 4 个字符,"Speichern"(德语)是 8 个字符,固定 80px 装不下。

**自适应 size**:框架根据 widget 内容算大小。`button_auto(label)`:测文字宽度 + 8px padding × 2 = button 宽度;高度 = 字号 + padding。复杂但灵活。Casey 在 day 200 用半自适应——文字宽度测,高度固定。

**flex size**:widget 声明 `flex-grow: 1`,容器剩余空间按比例分。这是 CSS flexbox 的核心,**Casey 不实现**。

```rust
fn button_auto(&mut self, label: &str) -> bool {
    // 测文字宽度:把 label 每个字符的 advance width 累加
    let text_w = self.font.measure_width(label, FONT_SIZE);
    let padding = 8.0;
    let size = Vec2::new(text_w + padding * 2.0, 24.0);
    let rect = self.alloc_rect(size);
    self.draw_button(rect, label)
}
```

`measure_width` 的实现依赖字体——TrueType 字体每个字符有 advance width 表,直接查表。Casey 在 HH 里手写了 bitmap 字体,每个字符 8×12 像素,所以 measure_width 直接是 `chars.len() * 8`。工业字体的 measure 更复杂(kerning、ligature、emoji)。

### 2.0.5 scroll view:layout 的边界

UI 内容超出视口怎么办?list view 1000 行、console 输出 10000 条、tree view 深度无上限。**scroll view** 解决这个。

```rust
ui.begin_scroll_view("main_scroll", Vec2::new(800.0, 600.0));
    // 这个 viewport 800×600
    for i in 0..1000 {
        ui.button(&format!("Button {}", i));
    }
ui.end_scroll_view();
```

内部维护 `scroll_offset: Vec2`。渲染时,**clip 到 viewport 矩形**——viewport 外的 widget 不画(或被裁剪)。鼠标 wheel 改 `scroll_offset.y`,layout 系统"应用"这个 offset——所有 widget 的 y 减去 scroll_offset.y,所以滚下去 button 100 时,button 0~99 在 viewport 上方被裁掉。

scroll view 的难点是**虚拟化**——1000 个 button 你不能真的全 layout 一遍(慢),要只 layout 可见的几十个。但 immediate-mode 风格难以虚拟化,因为 widget 是声明式的——你不知道下一个 widget 是哪个直到你声明。Casey 在 HH 里不做虚拟化,1000 个 button 实测能跑(每个 button 渲染 50μs,1000 个 50ms 卡顿——但 debug UI 不在乎)。商业 UI(immediate-mode 风格的 imgui / egui)用 hybrid:布局完整算,渲染只画可见的,叫 **"layout only, draw culled"**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏 UI 的 layout 系统,每个引擎都有自己的实现。让我把四大主流引擎的方案对比,你会看到 immediate-mode cursor 是众多合理方案之一。

**Unreal Engine 5 (UMG)** 用 retained-mode 的 widget tree + layout panel。你拖一个 Vertical Box 进 UMG editor,把 Button 拖进 Vertical Box,editor 自动算位置。UMG 的 layout 是**真正的对象树**——每个 widget 是 UMG object,layout panel (VerticalBox / HorizontalBox / GridPanel / CanvasPanel) 持有 children 数组,引擎在 Tick 时遍历算位置。优势是**编辑器可视化**(你在 editor 里拖拽就能布局),劣势是**对象生命周期复杂**(每个 widget 是 UCLASS,有 GC、Blueprint 通信、序列化)。UMG 的 layout 是 Qt 风格的 box layout——比 Casey 强大,但比 CSS flex 弱。

**Unity (UI Toolkit)** 用 CSS-like 的 UXML + USS。你写 UXML(类似 HTML)声明 widget 树,写 USS(类似 CSS)声明 layout。底层是 **Yoga 引擎**——Facebook 出的 flexbox 实现。这意味着 Unity UI Toolkit **支持完整 flexbox**——`flex-direction`、`flex-grow`、`align-items`、`justify-content`,web 开发者上手 Unity UI 几乎无学习成本。但代价是 UI Toolkit 比 Unity 旧 UI 系统(Canvas + Image + Text)复杂得多——光 layout 引擎就几十 MB。

**Godot 4** 用 Control 节点树 + layout property。每个 Control 有 `layout_mode`、`anchors_preset`、`grow_horizontal` 等 property。Godot 的方案介于 Unreal(对象树)和 Web(声明式)之间——节点是对象,但 layout 通过 property 声明。Godot 还有 `Container` 节点(VBoxContainer / HBoxContainer / GridContainer),类似 Qt 的 layout panel。

**Bevy UI**(Rust 生态)用 ECS + taffy layout。每个 UI 节点是 Entity,有 `Node` component(size、flex_direction 等),系统遍历 Component 树,调用 `taffy` crate 算 layout。Rust 风格——零成本、类型安全、并行友好。taffy 是 Rust 生态最成熟的 layout 引擎,支持 flexbox + grid,被 Bevy / iced / Dioxus 共用。

Casey 的方案和上面四个都不一样。Casey 用 immediate-mode + cursor + layout stack——**最朴素、最快、最适合 debug UI**。对比:

| 引擎 | 模式 | 灵活度 | 代码量 | 适用场景 |
|---|---|---|---|---|
| Casey | immediate + cursor | 低(stack only) | ~100 行 | debug overlay |
| Unreal UMG | retained + box panel | 中 | 几万行 | 商业游戏 UI |
| Unity UI Toolkit | Yoga + flexbox | 高 | 几十万行 | 复杂 UI(类似 web) |
| Godot | 节点 + property | 中 | 几万行 | 跨平台游戏 UI |
| Bevy UI | ECS + taffy | 高 | 几千行(Rust)+ taffy | Rust 游戏 UI |

你能学到的迁移:**你的 Rust 游戏项目,早期用 Casey 风格的 immediate-mode UI**——100 行 layout 代码够用。等项目成熟,要发正式 UI(主菜单、设置、背包),换成 `egui` 或 `iced`——它们实现了完整 flexbox,你声明式写 UI 代码,不用算坐标。

### 3.2 · 🎨 图形学视角

layout 系统在图形学里是个**横跨几何、文字渲染、用户输入**的交叉点。让我深入几个图形学相关的细节。

**测量文字宽度** 是 layout 的核心依赖。一个 button "Save" 的宽度,等于 S、a、v、e 四个字符的 advance width 之和。字符的 advance width 来自字体文件——TrueType (.ttf) 字体有 `hmtx` (horizontal metrics) table,每字符一个 advance width。OpenType (.otf) 类似。

```rust
// Rust 测文字宽度的伪代码
fn measure_text_width(font: &Font, text: &str, size: f32) -> f32 {
    let mut total = 0.0;
    for c in text.chars() {
        let glyph_id = font.glyph_id(c);            // cmap table
        let advance = font.advance_width(glyph_id); // hmtx table
        total += advance * (size / font.units_per_em() as f32);
    }
    total
}
```

复杂字体还要考虑 **kerning**(相邻字符的间距调整——"AV" 比 "A" + "V" 紧)、**ligature**(多个字符合成一个字形——"fi" 合成一个 glyph)、**emoji**(变长字节、组合字符)。工业字体库(rusttype、ab_glyph、swash)几千行代码。Casey 的 bitmap 字体没这些复杂度——每个字符固定 8×12,measure 就是 `chars.len() * 8.0`。

**clip / scissor rect** 是 scroll view 的基础。OpenGL / Vulkan / DirectX 都有 scissor test——你设置一个矩形,后续 draw call 只在这个矩形内可见。scroll view 渲染前 `glScissor(viewport.x, viewport.y, viewport.w, viewport.h)`,viewport 外的 widget 被裁剪。这是 GPU 级别的优化,免费。

**多分辨率支持** 是 layout 在图形学中的另一应用。屏幕分辨率从 720p 到 4K,差 9 倍像素。如果 UI 用绝对坐标,4K 屏上 UI 看起来很小。如果 UI 用 layout + 相对单位(百分比、em),框架在不同分辨率自动适应。这是 flexbox 设计的核心动机之一——web 网页要适应手机到桌面无数种分辨率。

**HiDPI / Retina** 让 layout 更复杂。屏幕物理像素 2x 逻辑像素,但 UI 要按逻辑像素 layout、按物理像素渲染。Casey 在 HH day 8 处理过这个问题(window resize / HiDPI),day 200 的 layout 在逻辑像素空间,渲染时 framework 自动乘 DPI scale。

**字体 rasterization** 是 layout 之后的图形学步骤。layout 算出 "button 'Save' 在 (10, 10), 宽 80px",渲染时要把 "Save" 字符的 glyph rasterize 到屏幕。这需要字体引擎(rusttype / ab_glyph)、glyph cache(缓存 rasterized glyph)、subpixel rendering(亚像素抗锯齿)。Casey HH 用手画 bitmap 字体,rasterization 是直接 `memcpy` glyph bitmap 到 framebuffer。

### 3.3 · 🐧 Linux 系统编程视角

Linux 桌面环境(GNOME / KDE / XFCE)用 GTK 或 Qt 做 UI。这些 framework 的 layout 系统,是 Linux 用户每天看到的。

**GTK** 用 GtkWidget 树 + GTK container。`GtkBox`(类似 Casey 的 vertical/horizontal)、`GtkGrid`、`GtkFlowBox`(wrap 流式布局)。GTK 4 引入 **GtkConstraintLayout**——iOS Auto Layout 风格的约束系统,声明 widget 之间的约束("button.left = container.left + 10"),solver 算坐标。这是 layout 系统的最复杂形态。

```bash
# 在 Arch 上装 GTK demo
sudo pacman -S gtk3 gtk3-demo
gtk3-demo
# 在 "Layout" 章节看 box / grid / flow 演示
```

**Qt** 用 QObject 树 + QLayout。`QVBoxLayout`、`QHBoxLayout`、`QGridLayout`、`QFormLayout`。Qt 的 layout 比 GTK 更面向对象——每个 layout 是 QObject,持有 children。Qt 还有 `QGraphicsView` + `QGraphicsGridLayout`,用于 scene graph 风格的 UI。

**终端 TUI**(ncurses、notcurses)也用 layout。`notcurses` 有 `ncplane` 概念——二维字符平面,可以在 plane 内 layout widget。TUI layout 比图形 UI 简单,因为字符是固定 cell(每个 cell 一个字符 + 颜色),没有 subpixel、没有 kerning。

**Wayland / X11 window manager** 本质也是 layout 系统。tiling WM(i3、sway、bspwm)把屏幕分成若干区,每个区一个 window——这是 layout 的窗口级应用。i3 用 tree 结构,每个 split 是 horizontal 或 vertical,window 自动 tile。你看 i3 配置:

```
# i3 splits
bindsym $mod+h split h      # 水平分屏
bindsym $mod+v split v      # 垂直分屏
bindsym $mod+e layout toggle split
```

这就是 layout 系统—— Casey 的 vertical / horizontal,放到窗口管理器层级。

**XKB / 输入事件** 是 layout 的下游。layout 算出 widget 位置后,鼠标点击 (x, y),框架要做 **hit testing**——哪个 widget 在 (x, y)?immediate-mode UI 每帧重算 widget 位置,hit testing 直接遍历当前帧的 widget 矩形即可。retained-mode UI 维护 widget tree,hit testing 走树查找。

Linux 的输入栈:内核 evdev → libinput → Wayland compositor / X server → toolkit(GTK / Qt)→ 应用。每一层都可能 transform 坐标(DPI scale、rotation),所以 hit testing 的 (x, y) 要在 widget layout 同一坐标系。

### 3.4 · 🦀 Rust 生态视角

Rust UI 库的 layout 实现,反映 Rust 语言特性如何影响设计。

**`egui`** 是 Rust 最流行的 immediate-mode UI 库。它的 layout 和 Casey 思路一致——cursor 推进 + layout stack。但 egui 比 Casey 强很多:支持自适应 size、`with_layout(Layout::top_down(Align::LEFT))`、自动 wrap、`Separator`、`Spacing` 配置。egui 的核心结构 `Ui`:

```rust
pub struct Ui {
    pub id: Id,
    pub layout: Layout,
    pub(crate) max_rect: Rect,    // 容器 rect
    pub(crate) min_rect: Rect,    // 内容 rect
    pub(crate) pl: Painter,
    pub(crate) spacing: Spacing,
    // ...
}
```

egui 的 layout 算法在 `egui::layout` 模块,几百行 Rust 代码。它支持 `top_down`、`bottom_up`、`left_to_right`、`right_to_left` 四个方向——比 Casey 的 vertical/horizontal 表达力更强。

**`iced`** 是 Rust 的 Elm 风格 UI 库。它的 layout 完全靠 **taffy** crate——Rust 实现的 flexbox / grid。iced widget 不直接画,而是 emit `Element` 树,layout engine 算位置,renderer 画。这是 retained-mode 的 Rust 风格——零成本抽象、类型安全。

**`taffy`** 本身是 layout 引擎,被 Bevy / iced / Dioxus / floem 共用。taffy 支持:
- Flexbox(完整 CSS spec)
- CSS Grid(完整 CSS spec)
- Block layout(web 的 default flow)
- 树形结构

taffy 用 **Rust-style 数据结构**——`Node` 是 index(不是指针)、`TaffyTree` 用 `Vec<NodeData>` 存储、cache layout 结果。这让 taffy 性能极高(每帧 layout 10000 节点 < 1ms)。

**`druid`**(已停止维护,但理念先进)用 **morphorm** layout 引擎。morphorm 是 Rust 的另一个 layout 引擎,灵感来自 CSS Flexbox 但更简单。druid 的设计哲学是"layout 是纯函数"——给定 widget 树 + 容器 size,输出每个 widget 的 rect。这种纯函数式 layout 容易测试和推理。

**`slint`** 是 Rust 的商业 UI 框架。它有自己的 DSL(.slint 文件),编译成 Rust 代码。slint layout 类似 QML——声明式、有 layout property。

**自己实现 layout 的取舍**:如果你的项目小(debug UI、工具 UI),用 egui 或自己写 Casey 风格 cursor layout,100 行代码搞定。如果你的项目大(完整游戏 UI、商业应用),用 iced / slint / druid + taffy,享受完整 flexbox 但代码复杂度上升。

**Rust 特有的 layout 优化**:
- **Arena allocation**:layout 树节点存 Vec 而非 Box,缓存友好
- **SmallVec**:浅层 widget 树用 SmallVec<[_; 4]>,避免堆分配
- **Interning**:widget id 用 Symbol 类型(基于 u32),比 String 快
- **SoA (Struct of Arrays)**:layout 数据按列存,cache line 利用率高

这些优化让 Rust UI 库比 C++ 对应物(GUI Qt、ImGui)性能高 2-5 倍,内存占用少 30%。这是 Rust 在 UI 领域的杀手锏。

## 5 · 对照与变奏

**Layout 系统的演化**:

| 时代 | 系统 | 特点 |
|---|---|---|
| 1990s | absolute / table | 手算坐标或 HTML table |
| 2000s | anchor / grid bag(Java Swing) | 相对父 / 兄弟定位 |

| 2015+ | constraint-based(Compose / SwiftUI) | 声明式约束 |

每代解决前代的痛点。Casey day 200 用最古老的 absolute + stack,够用但远不如现代方案。

### Flexbox 算法

Flexbox 看似简单,实现复杂——SpaceX 工程师写"flexbox is hard"博客详细讲。核心算法:

1. 算每个 child 的 preferred size(content-based)
2. 如果总和 > container,按 flex-shrink 比例缩
3. 如果总和 < container,按 flex-grow 比例扩
4. 按 align-items 对齐次轴
5. 按 justify-content 对齐主轴

5 步,每步都有 edge case。Rust 的 `taffy` crate 是 Rust 版 flexbox 实现,几千行代码。

### TUI / Web / Native 的 layout 比较

| 平台 | 默认 layout |
|---|---|
| Web | CSS flow + flex + grid |
| iOS | Auto Layout(constraint) |
| Android | LinearLayout / ConstraintLayout |
| Flutter | Flex / Row / Column |
| Qt | QVBoxLayout / QGridLayout |
| Win32 | absolute(老)/ XAML(新) |

每个平台都重写一遍 layout 系统。**Web 的 CSS layout 最灵活但最复杂**(浏览器实现几十万行)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 immediate-mode layout 用 cursor,retained-mode 用 layout manager?

**参考解答**:
- immediate-mode 每帧重新声明 widget,顺序固定 → cursor 自然推进
- retained-mode 创建 widget 后位置不变,layout manager 一次性算
- cursor 模式简单(无 layout 算法),但功能弱
- layout manager 复杂(flex / grid / constraint),但灵活
- 两者哲学不同:immediate 简单优先,retained 灵活优先

### Lv2 · 动手实践

**题**:实现 vertical layout,3 个 button 自动堆叠。

**参考解答**:

```rust
struct Ui {
    cursor_x: f32,
    cursor_y: f32,
    layout_stack: Vec<(f32, f32, f32)>,  // x, y, max_w
}

impl Ui {
    fn new() -> Self { Self { cursor_x: 0.0, cursor_y: 0.0, layout_stack: Vec::new() } }

    fn vertical<F: FnOnce(&mut Ui)>(&mut self, f: F) {
        self.layout_stack.push((self.cursor_x, self.cursor_y, 0.0));
        let start_y = self.cursor_y;
        f(self);
        let (_, _, max_w) = self.layout_stack.pop().unwrap();
        let (_, _, _) = (start_y, max_w, ());
    }

    fn button(&mut self, label: &str) -> (f32, f32) {
        let (x, y) = (self.cursor_x, self.cursor_y);
        println!("button '{}' at ({}, {})", label, x, y);
        self.cursor_y += 25.0;
        (x, y)
    }
}

fn main() {
    let mut ui = Ui::new();
    ui.cursor_x = 10.0;
    ui.cursor_y = 10.0;
    ui.vertical(|ui| {
        ui.button("Save");
        ui.button("Load");
        ui.button("Quit");
    });
}
```

**预期输出**:

```
button 'Save' at (10, 10)
button 'Load' at (10, 35)
button 'Quit' at (10, 60)
```
