
# Day 228 · 元游戏模式切换时等待依赖任务

> Loading mode 加载资源时,资源之间有依赖(A 的纹理引用 B 的 atlas)。今天 casey 加依赖管理:每个加载任务声明依赖,等所有依赖就位才完成。

## 0 · 为什么要有这一天

资源依赖:

- `level3.map` 依赖 `tileset.png` 和 `music.ogg`
- `player.sprite` 依赖 `player.atlas` 和 `player_anim.json`
- `boss.model` 依赖 `boss.mesh` 和 `boss.texture`

如果并行加载,可能 `level3.map` 加载完但 `tileset.png` 没好,引用是空指针。

**casey 的方案**:加 DAG (有向无环图) 依赖管理:

```rust
struct LoadJob {
    resource: ResourceId,
    dependencies: Vec<ResourceId>,
    state: JobState,
}

enum JobState { Waiting, Loading, Loaded, Failed }
```

调度器:

1. 找出所有 dependencies 都已 Loaded 的 Waiting 任务
2. 启动这些任务(并行)
3. 任务完成后,触发依赖它的下游任务

这是 **topological scheduling**:按 DAG 拓扑顺序调度。

心理锚点:看完今天,你能解释"为什么 Makefile 必须无环"(否则编译顺序无解),并自己实现依赖调度器。

## 1 · Casey 今天做了什么

1. **加 ResourceDAG**:依赖图
2. **加 topological scheduler**:按依赖顺序启动 job
3. **加错误传播**:依赖失败 → 下游也失败
4. **加优先级**:大文件早开始

## 2 · 心智模型

### 类比:做菜的工序

做一道菜:煮饭(20min)+ 切菜(5min)+ 炒菜(10min,要等切菜完)+ 上桌(等所有)。

工序图:

```
煮饭 ──┐
       ├──→ 上桌
切菜 ──┴──→ 炒菜 ──┘
```

煮饭和切菜可并行,炒菜要等切菜,上桌等所有。这是 DAG。

casey 的资源加载就是做菜工序:并行启动无依赖的,等待依赖的,最后完成。

### 2.1 DAG 数据结构

```rust
struct DependencyGraph {
    nodes: HashMap<ResourceId, Node>,
}

struct Node {
    job: LoadJob,
    dependencies: HashSet<ResourceId>,
    dependents: HashSet<ResourceId>,  // 反向:谁依赖我
    state: JobState,
}
```

每个节点知道:

- 自己依赖谁(forward edges)
- 谁依赖自己(reverse edges,便于通知)
- 当前状态

### 2.2 拓扑调度

```rust
impl DependencyGraph {
    /// 找出当前可启动的 job(所有依赖 Loaded)
    fn ready_jobs(&self) -> Vec<ResourceId> {
        self.nodes.iter()
            .filter(|(_, n)| n.state == JobState::Waiting
                && n.dependencies.iter()
                    .all(|dep| self.nodes.get(dep)
                        .map(|n| n.state == JobState::Loaded)
                        .unwrap_or(false)))
            .map(|(id, _)| *id)
            .collect()
    }

    fn mark_loaded(&mut self, id: ResourceId) {
        if let Some(node) = self.nodes.get_mut(&id) {
            node.state = JobState::Loaded;
        }
        // 通知 dependents 检查能否启动
    }

    fn all_done(&self) -> bool {
        self.nodes.values().all(|n|
            n.state == JobState::Loaded || n.state == JobState::Failed)
    }
}
```

主循环:

```rust
fn update_loading(state: &mut GameState) {
    let ready = state.dag.ready_jobs();
    for id in ready {
        state.dag.nodes.get_mut(&id).unwrap().state = JobState::Loading;
        state.loader.load_async(id);
    }
    state.loader.poll();
    for id in state.loader.drain_loaded() {
        state.dag.mark_loaded(id);
    }
    if state.dag.all_done() {
        transition_to(state, state.loading.target);
    }
}
```

### 2.3 错误传播

如果 `boss.mesh` 加载失败,`boss.model` 也无法加载:

```rust
fn mark_failed(&mut self, id: ResourceId) {
    fn fail_recursive(graph: &mut DependencyGraph, id: ResourceId) {
        if let Some(node) = graph.nodes.get_mut(&id) {
            node.state = JobState::Failed;
            let dependents: Vec<_> = node.dependents.iter().copied().collect();
            for dep_id in dependents {
                fail_recursive(graph, dep_id);
            }
        }
    }
    fail_recursive(self, id);
}
```

错误沿着 dependents 反向边传播,所有下游任务都标记 Failed。

### 2.4 优先级

不是所有 ready job 都立刻启动(磁盘带宽有限)。casey 加优先级:

```rust
struct Node {
    ...
    priority: Priority,
}

fn next_to_start(&self, max_concurrent: usize, current: usize) -> Option<ResourceId> {
    if current >= max_concurrent { return None; }
    let mut ready: Vec<_> = self.ready_jobs().into_iter()
        .map(|id| (self.nodes[&id].priority, id))
        .collect();
    ready.sort_by(|a, b| b.0.cmp(&a.0));  // 高优先先
    ready.first().map(|(_, id)| *id)
}
```

大文件优先(启动早,完成可能晚但并行度高)。

### Lv2 · 动手实践

**题**:实现 DependencyGraph + 拓扑调度。

**参考解答**:

```rust
use std::collections::{HashMap, HashSet};

#[derive(Copy, Clone, Debug, PartialEq, Eq, Hash)]
struct ResId(u32);

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
enum State { Waiting, Loading, Loaded, Failed }

struct Node {
    id: ResId,
    state: State,
    dependencies: HashSet<ResId>,
    dependents: HashSet<ResId>,
}

struct DependencyGraph {
    nodes: HashMap<ResId, Node>,
}

impl DependencyGraph {
    fn new() -> Self { Self { nodes: HashMap::new() } }

    fn add(&mut self, id: ResId, deps: &[ResId]) {
        for &dep in deps {
            self.nodes.entry(dep).or_insert(Node {
                id: dep, state: State::Waiting,
                dependencies: HashSet::new(), dependents: HashSet::new(),
            });
        }
        let node = self.nodes.entry(id).or_insert(Node {
            id, state: State::Waiting,
            dependencies: HashSet::new(), dependents: HashSet::new(),
        });
        for &dep in deps {
            node.dependencies.insert(dep);
            self.nodes.get_mut(&dep).unwrap().dependents.insert(id);
        }
    }

    fn ready(&self) -> Vec<ResId> {
        self.nodes.values()
            .filter(|n| n.state == State::Waiting
                && n.dependencies.iter()
                    .all(|d| self.nodes.get(d)
                        .map(|n| n.state == State::Loaded).unwrap_or(false)))
            .map(|n| n.id).collect()
    }

    fn mark_loaded(&mut self, id: ResId) {
        if let Some(n) = self.nodes.get_mut(&id) {
            n.state = State::Loaded;
        }
    }

    fn all_done(&self) -> bool {
        self.nodes.values().all(|n| n.state == State::Loaded || n.state == State::Failed)
    }

    fn load_order(&self) -> Vec<ResId> {
        // 简单拓扑排序(Kahn's algorithm)
        let mut in_degree: HashMap<ResId, usize> = HashMap::new();
        for n in self.nodes.values() {
            in_degree.insert(n.id, n.dependencies.len());
        }
        let mut queue: Vec<ResId> = in_degree.iter()
            .filter(|(_, &d)| d == 0).map(|(&id, _)| id).collect();
        let mut order = vec![];
        while let Some(id) = queue.pop() {
            order.push(id);
            if let Some(n) = self.nodes.get(&id) {
                for &dep in &n.dependents {
                    if let Some(d) = in_degree.get_mut(&dep) {
                        *d -= 1;
                        if *d == 0 { queue.push(dep); }
                    }
                }
            }
        }
        order
    }
}

fn main() {
    let mut dag = DependencyGraph::new();
    // level3 依赖 tileset 和 music,tileset 依赖 texture
    dag.add(ResId(1), &[ResId(2), ResId(3)]);  // level3
    dag.add(ResId(2), &[ResId(4)]);             // tileset -> texture
    dag.add(ResId(3), &[]);                      // music
    dag.add(ResId(4), &[]);                      // texture

    println!("Load order: {:?}", dag.load_order());

    // 模拟加载
    while !dag.all_done() {
        let ready = dag.ready();
        if ready.is_empty() { break; }
        for id in ready {
            println!("Loading {:?}", id);
            dag.mark_loaded(id);
        }
    }
    println!("All done!");
}
```

## 10 · 深入:任务依赖图的工业级实现

casey 在 day228 处理"mode 切换时,新 mode 依赖的异步任务可能没完成"——这是工程上的 dependency tracking 问题。让我们把它彻底讲透。

### 10.1 依赖图的概念

多个异步任务之间可能互相依赖:

```
Task A (load player data)  ─┐
                            ├─→ Task C (init game state)
Task B (load level)         ─┘
```

C 必须等 A 和 B 都完成。这就是**有向无环图(DAG)**的依赖关系。

实现:

```rust
use std::collections::HashMap;

struct TaskGraph<T> {
    tasks: HashMap<TaskId, Task<T>>,
    dependencies: HashMap<TaskId, Vec<TaskId>>,  // task -> 它依赖的 tasks
}

struct Task<T> {
    id: TaskId,
    state: TaskState<T>,
}

enum TaskState<T> {
    Pending,
    Running,
    Completed(T),
    Failed(String),
}

impl<T> TaskGraph<T> {
    fn is_ready(&self, id: TaskId) -> bool {
        // 所有依赖都完成?
        self.dependencies[&id].iter()
            .all(|dep| matches!(self.tasks[dep].state, TaskState::Completed(_)))
    }
    
    fn run_ready(&mut self) {
        for (id, task) in &mut self.tasks {
            if matches!(task.state, TaskState::Pending) && self.is_ready(*id) {
                task.state = TaskState::Running;
                // 启动任务...
            }
        }
    }
}
```

casey 的简化版用单一 "transition state" 跟踪,但概念上是 DAG。

### 10.2 拓扑排序

```
2. 标记为完成,减少其后继节点入度
3. 重复
```

### 10.3 异步等待模式

mode 切换时,等所有 dependency 完成:

```rust
async fn transition(state: &mut State, new_mode: Mode) {
    let tasks = compute_tasks_for(new_mode);
    let task_ids: Vec<_> = state.task_graph.add_tasks(tasks);
    
    // 启动所有任务(已满足依赖的会运行)
    state.task_graph.run_ready();
    
    // 等所有任务完成
    while !state.task_graph.all_completed() {
        // 显示 loading screen
        let progress = state.task_graph.progress();
        state.ui.show_loading(progress);
        tokio::time::sleep(Duration::from_millis(16)).await;
        // 推进已就绪的任务
        state.task_graph.run_ready();
    }
    
    state.mode = new_mode;
}
```

casey 用 polling 风格(每帧检查),不用 async runtime。两者等价。

### 10.4 任务取消

如果用户在 loading 中按 Cancel,要取消未完成的任务:

```rust
fn cancel_transition(state: &mut State) {
    state.task_graph.cancel_all();
    state.transition = None;
}
```

任务取消的语义:

- **未启动**:直接标记 Cancelled
- **运行中**:通常不能强制中断,要 task 内部检查 cancel flag
- **已完成**:不能取消(已经做了)

Rust 的 `tokio::task::JoinHandle::abort()` 提供强制取消,但要小心——任务可能在 unsafe state 中。

### 10.5 任务优先级

某些任务比其他重要。priority queue 控制:

```rust
use std::collections::BinaryHeap;

struct PrioritizedTask {
    priority: i32,    // 数字越大越优先
    task: Task,
}

impl Ord for PrioritizedTask {
    fn cmp(&self, other: &Self) -> std::cmp::Ordering {
        self.priority.cmp(&other.priority)
    }
}
```

### 10.7 错误处理

dependency 失败的传播:

```rust
async fn transition(state: &mut State, new_mode: Mode) -> Result<(), ModeSwitchError> {
    state.task_graph.run_ready();
    while !state.task_graph.all_settled() {
        if state.task_graph.any_failed() {
            return Err(ModeSwitchError::DependencyFailed);
        }
        tokio::time::sleep(Duration::from_millis(16)).await;
        state.task_graph.run_ready();
    }
    state.mode = new_mode;
    Ok(())
}
```

`all_settled` = 所有任务都 completed 或 failed。任何一个失败就报错。

### 10.8 progress 估算

loading screen 显示进度:

```rust
fn progress(&self) -> f32 {
    let total = self.tasks.len();
    let done = self.tasks.values()
        .filter(|t| matches!(t.state, TaskState::Completed(_)))
        .count();
    done as f32 / total as f32
}
```

### 10.9 测试 dependency system

```rust
async fn load_player(state: &State) -> PlayerData { /* ... */ }
```

### 11.6 casey 的 polling 风格 vs async

```rust
fn update(state: &mut State, dt: f32) {
    if state.transition.is_some() {
        if state.task_graph.all_settled() {
            state.mode = state.transition.take().unwrap();
        }
        // 显示 loading
```

优点:无 async runtime 开销,游戏循环稳定。缺点:代码比 async 啰嗦。

### 11.8 工业级 task system 设计

设计生产级 task system:

1. **任务抽象**:Task trait,有 run / cancel / progress
2. **依赖图**:DAG,拓扑排序启动
3. **优先级**:priority queue
4. **资源约束**:限制并发数(避免 OOM)
5. **错误恢复**:failed task 自动 retry 或降级
6. **可观察性**:每个 task 有 ID、name、status,UI 可见

### 11.10 真实世界案例:Unreal 的 StreamableManager

Unreal Engine 的 asset streaming 系统:

```cpp
// 请求加载多个 asset
TArray<FName> asset_names = { TEXT("Player"), TEXT("Level"), TEXT("Audio") };
FStreamableHandle handle = StreamableManager.RequestAsyncLoad(asset_names);

// 等所有完成
handle.WaitUntilComplete();  // 阻塞
// 或
handle.BindCompleteDelegate([]() {
    // 完成回调
});
// 或
if (handle.HasLoadCompleted()) {
    // 已经完成
}
```

设计要点:
1. **批量请求**:一次 request 多个 asset
2. **多种等待方式**:阻塞、回调、polling
3. **handle 管理**:handle 持有 asset reference,release 后 unload
4. **dependency**:asset 可以引用其他 asset,自动级联加载

casey 的 HH 简化版概念上类似。学完 day228,你看 Unreal 的 StreamableManager 不再陌生。
