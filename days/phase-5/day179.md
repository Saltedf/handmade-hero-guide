# Day 179 · 随时间跟踪调试信息

> 单帧的 cycle 数告诉你"现在有多慢",但你真正想知道的是"过去 60 帧的趋势"。今天 Casey 加上时间维度:ring buffer 存最近 300 帧,UI 能看到曲线变化。这下你才能发现"偶发卡顿"——平均 5ms,但每 100 帧会突然 50ms。

## 0 · 为什么要有这一天

你打开游戏,profiler 显示这一帧 7ms。OK,7ms 是好是坏?你不知道——你没基准。再看一帧,8ms。再一帧 6ms。这种"看着当前一帧"的调试方式有两个根本问题:

1. **看不到偶发**:平均 7ms 的游戏可能每 5 秒卡一次 50ms。如果你只看"当前帧",大概率刚好看到的是 7ms 的好帧,错过那个 50ms 的灾难
2. **看不到趋势**:你改了渲染代码,从 8ms 变 7ms——好还是坏?要看 100 帧平均才能排除噪声

工业级的解决方案:**存历史 N 帧**,画成曲线图。一眼能看到:
- 偶发的尖刺(spike)
- 长期的趋势
- 平均和最坏值的对比

存历史的数据结构是 **ring buffer**(环形缓冲)。它的精妙之处:**永远只占 N 帧的内存**,不管游戏跑多久。新数据覆盖最老的,循环利用。

心理锚点:看完今天,你能实现一个固定容量、永远只占栈内存的 ring buffer,并能解释为什么不用 `Vec::push` 而 wrap around。

## 1 · Casey 今天做了什么

Casey 把 profiler 改成"每帧记录一个 FrameData struct,存到固定大小的环形数组":

1. 定义 `DebugFrameData` struct,包含 cycle 数 + 各种 debug 状态
2. 全局一个 `DebugFrameData frames[MAX_FRAMES]`,MAX_FRAMES = 240(4 秒 @ 60fps)
3. 一个 `frame_index` 指针,每帧 `frame_index = (frame_index + 1) % MAX_FRAMES`
4. UI 渲染时,按 `frame_index` 倒序遍历

他强调:**ring buffer 不是一个新概念**,但 game dev 圈里很少用对。常见错误:
- 用 `Vec::push`,跑久了内存爆
- 用 `VecDeque`,每次 push 都堆分配
- 用 `Vec` 但每 N 帧 `drain`,有 GC-like 抖动

正确的 ring buffer 是**预分配固定大小数组 + wrap around 指针**,零堆分配。

## 2 · 心智模型

### 类比:超市的存货清单

超市有个白板写"最近 30 天的销售"。每天晚上擦掉 30 天前的数字,写今天的。30 天前的就丢了——但你不关心 30 天前,你只看最近趋势。

白板大小固定(30 格),永远只占一面墙。这就是 ring buffer:**容量固定,新数据覆盖最老,无限循环**。

物理上的"擦格子"是 O(1)——你不用移动其他 29 个格子,只擦一个。同样 ring buffer 的写入是 O(1),不管容量多大。

### 2.1 数据结构

```rust
pub struct RingBuffer<T, const N: usize> {
    data: [T; N],     // 固定大小数组,栈或静态分配
    head: usize,      // 下一个写入位置(0..N)
    len: usize,       // 已写入多少(0..N,封顶 N)
}
```

**关键 Rust 概念**:
- `const N: usize` — **const generics**,Rust 1.51+ 稳定。数组大小编译时定,不允许变
- `[T; N]` — 固定大小数组。stack 分配(N 小时)或 `.bss` 段(N 大时 static)
- `data: [T; N]` 要求 `T: Default` 或 `T: Copy`,否则无法初始化(`[T; N]::new()` 不存在)

如何初始化 `[T; N]`?三种方法:

```rust
// 方法 1:T: Copy + Default(最简单)
let data = [0u64; 300];  // [u64; 300],全 0

// 方法 2:T: Default(用 const generics 的 array helper)
let data: [String; 300] = std::array::from_fn(|_| String::new());

// 方法 3:MaybeUninit(unsafe,但能完全自定义)
let mut data: [MaybeUninit<T>; N] = unsafe { MaybeUninit::uninit().assume_init() };
for slot in &mut data { slot.write(T::new()); }
```

profiler 用 `u64`(cycle 数),用方法 1 最简单。

### 2.2 push 操作

```rust
impl<T: Copy + Default, const N: usize> RingBuffer<T, N> {
    pub fn new() -> Self {
        Self { data: [T::default(); N], head: 0, len: 0 }
    }

    pub fn push(&mut self, v: T) {
        self.data[self.head] = v;
        self.head = (self.head + 1) % N;
        if self.len < N { self.len += 1; }
    }
}
```

**逐行**:
- `data[head] = v` — 写入 head 指向的位置。O(1)
- `head = (head + 1) % N` — head 推进一格,绕回(N - 1 → 0)。**取模保证 head 始终在 0..N**
- `if len < N` — 未满时 len 增加;满后 len 停在 N

`%` 取模在 x86_64 是 1 条指令(`div`),但 div 慢(~20 cycle)。优化:`N` 选 2 的幂,`% N` 变成 `& (N - 1)`,1 个 cycle。Casey 在 Day 175+ 的所有 ring buffer 都用 2 的幂大小。

### 2.3 遍历(按时间顺序)

```rust
impl<T: Copy, const N: usize> RingBuffer<T, N> {
    pub fn iter_recent(&self) -> impl Iterator<Item = T> + '_ {
        let start = if self.len < N { 0 } else { self.head };
        // 满了:从 head 开始(head 是最老的)
        // 没满:从 0 开始(0 是最老的)
        (0..self.len).map(move |i| self.data[(start + i) % N])
    }
}
```

**注意**:`start` 在 `&self` 借用期间不变,所以可以 `move` 进闭包。每个 item 是 `T`(Copy),不需要 `&T`。

但如果你要返回引用(避免 Copy),要小心 lifetime:

```rust
impl<T, const N: usize> RingBuffer<T, N> {
    pub fn iter_recent_ref(&self) -> impl Iterator<Item = &T> {
        let start = if self.len < N { 0 } else { self.head };
        (0..self.len).map(move |i| &self.data[(start + i) % N])
    }
}
```

闭包返回 `&T`,lifetime 由 `&self` 决定,Rust 自动推断。

### 2.4 FrameData 设计

每帧不只是 cycle 数,还有更多东西:

```rust
#[derive(Clone, Default)]
pub struct FrameData {
    pub frame_index: u64,           // 全局帧号(不 wrap)
    pub total_cycles: u64,          // 本帧总 cycle
    pub update_cycles: u64,         // update 函数耗时
    pub render_cycles: u64,         // render 函数耗时
    pub entity_count: u32,          // 当前实体数(诊断内存增长)
    pub draw_call_count: u32,       // GPU draw call 次数
    pub bytes_allocated: u64,       // 本帧堆分配字节
}
```

每帧的 record 收集完后,聚合成一个 FrameData,推到 ring buffer。

### 2.5 历史数据的查询

```rust
pub struct ProfilerHistory {
    frames: RingBuffer<FrameData, 300>,
}

impl ProfilerHistory {
    pub fn last_n(&self, n: usize) -> Vec<u64> {
        self.frames.iter_recent().rev().take(n).map(|f| f.total_cycles).collect()
    }

    pub fn average_last_n(&self, n: usize) -> f64 {
        let cycles: Vec<u64> = self.last_n(n);
        if cycles.is_empty() { 0.0 }
        else { cycles.iter().sum::<u64>() as f64 / cycles.len() as f64 }
    }

    pub fn max_last_n(&self, n: usize) -> u64 {
        self.last_n(n).into_iter().max().unwrap_or(0)
    }
}
```

**为什么有这些查询?**
- `average_last_n(60)` — 过去 1 秒平均(60帧)
- `max_last_n(60)` — 过去 1 秒最坏帧(找 spike)
- `last_n(300)` — 画曲线图的数据

### 2.6 数学推导:百分位数 vs 平均

游戏里常见的统计数字:**95th percentile frame time**(P95),即"95% 的帧比这个值快"。比"平均"更能反映用户体验,因为平均会被偶尔的低值拉低,掩盖偶发 spike。

```
帧时间样本(ms):[5, 5, 5, 6, 5, 5, 5, 50, 5, 5]
总和 = 100,平均 = 10ms(看着还行)
排序 = [5, 5, 5, 5, 5, 5, 5, 5, 6, 50]
P50(中位) = 5
P95 = 50ms(第 95% 的值,即倒着数 5%,10 × 0.05 = 0.5,取第 10 个 = 50)
P99 ≈ 50ms
```

用户感受到的"流畅度"和 P95 / P99 强相关。Steam 的 SteamVR Performance profiler 用 P99。Casey 后续的 UI 也展示 P95。

实现:对 ring buffer 排序后取 percentile。每帧排序 300 个数 < 1 μs,可接受。代码:

```rust
pub fn percentile(&self, p: f64) -> u64 {
    let mut sorted: Vec<u64> = self.frames.iter_recent().map(|f| f.total_cycles).collect();
    sorted.sort_unstable();
    let idx = ((sorted.len() as f64 - 1.0) * p / 100.0).round() as usize;
    sorted[idx]
}
```

`sort_unstable` 比 `sort` 快(不保持相等元素的相对顺序),用于纯数值排序最优。

### 2.8 内存布局:对齐与 false sharing

FrameData 大约 40 字节。如果它放在 mutex 后面、被多线程频繁写,要避免和其他热数据挤在同一 cache line。用 `#[repr(align(64))]` 强制对齐:

```rust
#[repr(align(64))]
#[derive(Clone, Copy, Default)]
pub struct FrameData { /* ... */ }
```

这会让 FrameData 起始地址总是 64 的倍数,占独立 cache line(假设 struct ≤ 64 字节)。Profiler 是 hot path,值得这样做。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏里典型 spike 的来源:
- **GC**(Java / C#):每 10 秒一次,几十毫秒停顿
- **资产加载**:大纹理加载完成的那帧
- **物理 broadphase**:实体多了 brute force 卡
- **OS 抢占**:其他进程突然占 CPU

ring buffer 历史 + spike 检测能立刻发现这些。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上做"历史时间序列"的其他工具:

| 工具 | 用途 | 实现 |
|---|---|---|
| `sar` | 系统指标历史 | ring buffer in `/var/log/sa/saXX` |
| `dmesg` | 内核日志 | kernel ring buffer(`/dev/kmsg`) |
| `journalctl` | systemd 日志 | structured journal,有 vacuum |
| `perf record` | 性能采样 | ring buffer in `/proc/sys/kernel/perf_event_*` |

Linux 内核自己的 printk 就是一个巨大的 ring buffer(默认 64KB)。Casey 的设计本质上是把这套搬到用户态。

```bash
# 看内核 ring buffer 大小
cat /proc/sys/kernel/printk
# 输出:4 4 1 7(不是大小,是 log level。大小在 .config)
grep CONFIG_LOG_BUF_SHIFT /boot/config-$(uname -r)
# 输出:CONFIG_LOG_BUF_SHIFT=18 (即 2^18 = 256KB)
```

### 3.3 · 🦀 Rust 生态视角

Rust crate 里的 ring buffer:

| crate | 特点 |
|---|---|
| `heapless` | `heapless::Vec<T, N>` 等,纯栈,no_std |
| `arrayvec` | 类似 heapless,但 heap 可选 |
| `ringbuf` | heap-allocated ring,生产用 |
| 手写 | 最简单,Casey 选这个 |

手写的好处:**控制布局,控制对齐,知道每行做什么**。

```rust
// heapless 版本
use heapless::Vec as HVec;
let mut buf: HVec<u64, 300> = HVec::new();
buf.push(42).unwrap();  // 满了会 Err
```

heapless 在满了**不覆盖**,而是返回 Err。和 Casey 的 wrap-around 不同。Casey 要的就是覆盖。

**Rust 特性**:const generics 让 `[T; N]` 可以参数化大小,这是 Rust 1.51+ 的新能力。C++ 的等价(`template<size_t N>`)一直有,Java 没有(必须用 ArrayList)。

### 3.4 · 🎨 图形学视角(渲染曲线图的难点)

把 cycle 数据画成曲线在屏幕上,要解决"30 帧/秒写入 + 60 帧/秒读取"的并发。Casey 在 Day 180 才正式画曲线,这里先看技术难点:

1. **数据采样**:300 个采样画 1920 像素宽,每个采样占 6.4 像素。需要降采样或插值
2. **颜色映射**:cycle 数 1000 和 100000 都画黑线看不出差异。常用**对数刻度**或**梯度颜色**
3. **滚动视图**:数据随时间向左滚,要 smooth,不能跳

降采样的标准算法:**Min-Max 降采样**。把每 N 个采样压缩成 [min, max] 一对,保留 spike 信息(普通平均会平滑掉 spike)。这是 GPU profiler 报告里常见的可视化技巧。

```rust
fn downsample_minmax(data: &[u64], target_count: usize) -> Vec<(u64, u64)> {
    let chunk = data.len().div_ceil(target_count);
    data.chunks(chunk).map(|c| {
        let min = *c.iter().min().unwrap_or(&0);
        let max = *c.iter().max().unwrap_or(&0);
        (min, max)
    }).collect()
}
```

### 3.5 · 🐧 Linux 系统编程视角(JIT tracing)

Linux 内核的 ftrace 子系统也是 ring buffer 实现的,设计要点:

- **per-CPU buffer**(避免跨核锁)
- **_nested context**(中断里也能写,不递归)
- **overwrite / no-overwrite 模式可选**(profiler 用 overwrite,事件 log 用 no-overwrite)

Casey 的设计选 overwrite(老的被新的覆盖),因为 profiler 关心**最新**而不是**完整**。

```bash
# 看 ftrace ring buffer 大小

# 默认 1408 KB(per-CPU)

# 用 ftrace 跟踪 syscall

```

`/dev/kmsg` 也是一个 ring buffer 接口,内核 printk 写入,dmesg 读出。

## 4 · 认知地图

### 4.1 上级

- **时间序列存储**(time-series storage)— 时序数据库的核心数据结构
- **有限历史窗口**(bounded history window)— 流式系统通用模式
- **采样 vs 全量**— ring buffer 是"全量但有限"的折衷

### 4.2 同级

| 数据结构 | 何时用 |
|---|---|
| `Vec<T>` | 无限增长,无覆盖 |
| `VecDeque<T>` | 双端,heap 分配 |
| Ring buffer(`[T; N]` + head) | 固定容量,覆盖老的 |
| linked list | 不连续,慢 |
| LRU cache | ring + hash,带淘汰策略 |

### 4.3 下级

- `[T; N]` 固定数组 — 容器
- `head: usize` — 写指针
- `len: usize` — 当前有效长度
- `iter_recent()` — 顺序遍历(老的在前)
- `(start + i) % N` — 取模定位

## 5 · 对照与变奏

**Ring buffer 在不同场景**:

| 场景 | 容量 | 覆盖策略 |
|---|---|---|
| profiler 历史 | 300 帧 | wrap-around |
| 音频缓冲 | 几百毫秒 | wrap-around |
| 网络 socket buffer | 几 MB | wrap-around |
| 内核 printk | 256KB | wrap-around |
| event log(银行业) | 永久 | 不覆盖(append-only) |

**只有"必须永远可查"的日志不能 ring buffer**(比如金融交易)。游戏 / 系统 / 音频 / 网络都行。

**单生产者单消费者(SPSC)ring buffer**:

高性能场景(音频 / 网络),ring buffer 还要做"无锁"。一个线程写,一个线程读,用 atomic head/tail 保证无竞争。这是 Day 178 的 atomic 知识的延伸。

```rust
use std::sync::atomic::{AtomicUsize, Ordering};

pub struct SpscRing<T, const N: usize> {
    data: UnsafeCell<[T; N]>,
    head: AtomicUsize,  // 写指针(生产者更新)
    tail: AtomicUsize,  // 读指针(消费者更新)
}

unsafe impl<T: Send, const N: usize> Send for SpscRing<T, N> {}
unsafe impl<T: Send, const N: usize> Sync for SpscRing<T, N> {}
```

`UnsafeCell` + 手动 `unsafe impl Send/Sync`——这是 unsafe Rust 的核心工具。游戏音频常用这种模式。

### Ring buffer 的工业实现对比

不同语言 / 项目对 ring buffer 的实现:

| 项目 | 实现 | 特点 |
|---|---|---|
| Linux kernel printk | `log_buf[]` + atomic head/tail | 全局共享,多 CPU 安全 |
| Linux ALSA 音频 | per-stream ring buffer | 用户态 mmap,内核 DMA 直接写 |
| Boost lockfree queue | SPSC 用 atomic,MPMC 用更复杂结构 | C++ 模板 |
| Rust `crossbeam-queue` | SegmentedQueue / ArrayQueue | MPMC lock-free |
| Casey HH | 简单 `[T; N]` + usize head | 教学优先,够用 |

工业实现的核心难点是**多生产者**(MPMC),需要 CAS 操作防止两个写者写同一 slot。Casey 的游戏暂时不需要 MPMC ring buffer(per-thread 足够),所以保持了简单设计。

### 与 Unreal Insights 的对比

Unreal Insights(UE5 的 profiler)的数据存储更复杂:

- **Trace ring buffer**:每线程独立 + 共享 transport
- **session 文件**:磁盘持久化,可离线分析
- **remote viewer**:可在另一台机器实时分析
- **event hierarchy**:嵌套 span 通过字符串 ID 而非指针关联

Casey 的设计**没有持久化**,数据只在内存里。如果你想"今晚跑游戏,明天分析昨晚某个 spike",要自己加 binary 序列化到磁盘——这是 Day 207+ introspection 才会涉及的话题。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 ring buffer 用 `(head + 1) % N` 而不是用 `Vec::push` + 每 N 帧 `drain(0..1)`?

**参考解答**:
- **`Vec::push` + drain**:`drain(0..1)` 要把后面的 N-1 个元素前移,O(N)
- **`% N` wrap**:不动其他元素,只改 head 指针,O(1)
- ring buffer 每帧 push,如果用 drain 每帧 O(N),60fps × 300 元素 = 18000 移动/秒,白白浪费 CPU
- ring buffer 还有一个优势:**内存地址稳定**,data 数组永远在同一个位置,CPU cache 友好

### Lv2 · 动手实践

**题**:实现 RingBuffer,要求:
- 用 const generics,容量编译时定
- push / iter_recent / last_n / max
- main 里跑 1000 次 push(模拟 1000 帧),验证只保留最近 300 个

**参考解答**:

```rust
#[derive(Clone)]
pub struct RingBuffer<T: Copy + Default, const N: usize> {
    data: [T; N],
    head: usize,
    len: usize,
}

impl<T: Copy + Default, const N: usize> RingBuffer<T, N> {
    pub fn new() -> Self {
        Self { data: [T::default(); N], head: 0, len: 0 }
    }

    pub fn push(&mut self, v: T) {
        self.data[self.head] = v;
        self.head = (self.head + 1) % N;
        if self.len < N { self.len += 1; }
    }

    pub fn len(&self) -> usize { self.len }

    pub fn iter_recent(&self) -> impl Iterator<Item = T> + '_ {
        let start = if self.len < N { 0 } else { self.head };
        (0..self.len).map(move |i| self.data[(start + i) % N])
    }

    pub fn last_n(&self, n: usize) -> Vec<T> {
        self.iter_recent().rev().take(n).collect()
    }
}

fn main() {
    let mut buf: RingBuffer<u64, 300> = RingBuffer::new();
    for i in 0..1000u64 {
        buf.push(i);
    }
    println!("len after 1000 pushes: {}", buf.len());  // 300
    let last_5: Vec<u64> = buf.last_n(5);
    println!("last 5: {:?}", last_5);
    // 应该输出 [999, 998, 997, 996, 995]
    // 因为 iter_recent 是从老到新,last_n 取最近的 5 个,rev 后倒序
}
```

**注意**:`iter_recent().rev()` 要求 `DoubleEndedIterator`,需要 `ExactSizeIterator`。上面写法用 `Vec` 中转简化,但效率不如直接双指针实现。

### Lv3 · 迁移设计

**题**:实现一个 SPSC(单生产者单消费者)ring buffer 用于线程间通信,要求 lock-free。用 atomic head 和 tail。**提示**:写者只动 head,读者只动 tail,两边互不竞争。

**提示**:
- 容量 N 必须是 2 的幂(`% N` 变 `& N-1`)
- head == tail 时是空,head == tail + 1 时是满(浪费一个 slot)
- 写之前判断 `(head + 1) % N != tail`
- 读之前判断 `head != tail`
- **关键点**:head/tail 用 `AtomicUsize`,但 `Ordering` 选择影响正确性。写 head 用 `Release`(让读者看到 data),读 tail 用 `Acquire`
- **ABA 问题**:索引 wrap 后可能 head == tail 但实际"满了又空了"。解决:用 `usize` 永远递增,实际位置 = value % N(浪费一位但消除 ABA)
- **参考 crossbeam-queue ArrayQueue 的实现**

完整可跑(基于 Lv2 加 FrameData):

```rust
// Cargo.toml 空,纯 std
#[derive(Clone, Copy, Default)]
pub struct FrameData {
    pub frame_index: u64,
    pub total_cycles: u64,
    pub update_cycles: u64,
    pub render_cycles: u64,
    pub entity_count: u32,
}

pub struct RingBuffer<T: Copy + Default, const N: usize> {
    data: [T; N],
    head: usize,
    len: usize,
}

impl<T: Copy + Default, const N: usize> RingBuffer<T, N> {
    pub fn new() -> Self { Self { data: [T::default(); N], head: 0, len: 0 } }

    pub fn push(&mut self, v: T) {
        self.data[self.head] = v;
        self.head = (self.head + 1) % N;
        if self.len < N { self.len += 1; }
    }

    pub fn iter_recent(&self) -> impl Iterator<Item = T> + '_ {
        let start = if self.len < N { 0 } else { self.head };
        (0..self.len).map(move |i| self.data[(start + i) % N])
    }

    pub fn len(&self) -> usize { self.len }
}

fn main() {
    let mut history: RingBuffer<FrameData, 300> = RingBuffer::new();

    for frame in 0..500u64 {
        let mut data = FrameData::default();
        data.frame_index = frame;
        data.total_cycles = 1_000_000 + frame * 100;  // 假数据,稳定增长
        data.update_cycles = 600_000;
        data.render_cycles = 400_000;
        data.entity_count = 50 + (frame / 10) as u32;
        history.push(data);
    }

    println!("history len: {}", history.len());

    let mut max_total = 0;
    let mut min_total = u64::MAX;
    let mut sum = 0u64;
    for f in history.iter_recent() {
        sum += f.total_cycles;
        if f.total_cycles > max_total { max_total = f.total_cycles; }
        if f.total_cycles < min_total { min_total = f.total_cycles; }
    }
    let count = history.len() as u64;
    println!("min: {}  max: {}  avg: {}", min_total, max_total, sum / count);

    // 画 ASCII 直方图
    println!("--- histogram (last 60 frames) ---");
    let recent: Vec<FrameData> = history.iter_recent().rev().take(60).collect();
    for f in recent.iter().rev() {
        let bar_len = (f.total_cycles / 50_000) as usize;
        println!("frame {:3}: {}|", f.frame_index % 1000, "█".repeat(bar_len));
    }
}
```

**Troubleshooting**:

- `error[E0277]: the trait bound T: Default is not satisfied` — T 必须 Default。FrameData 用 `#[derive(Default)]`
- 数组初始化错 — 用 `[T::default(); N]`,不能用 `Vec::new()`
- 编译时间慢 — const generics 大 N (10000+) 编译慢,用关联类型或 macro 替代
- **`iter_recent().rev()` 报错** — `rev()` 要 `DoubleEndedIterator`,简单 map 不满足。改为先 collect 到 Vec 再 rev,或实现自定义迭代器
- **percentile 函数 idx 越界** — `idx` 可能 ≥ len,加 `min(sorted.len() - 1)`
