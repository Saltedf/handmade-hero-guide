工业级 debug 工具的解决方案叫 **runtime hierarchy editing**——UI 上拖动节点改变父节点,路径立即重写,变量值不变。这是把"层级"从编译时常量变成运行时数据。Casey 今天加 drag-and-drop 到 tree view,实现这件事。

实现 runtime hierarchy editing 涉及三个技术要点:

**第一,drag-and-drop 交互**。鼠标按住节点、移动、松开到目标——这是 GUI 经典交互,但 immediate-mode UI 实现有微妙之处(区分 click 和 drag、ghost preview 渲染、drop target 命中)。Casey 在 Day 197 已经做过 window 拖拽,今天扩展到 tree 节点。

**第二,路径重写**。把 `Player/Movement/Speed` 移到 `Player/Combat/` 下,新路径是 `Player/Combat/Speed`。算法:取最后一段(`Speed`)作变量名,拼到目标父路径(`Player/Combat`)后面。**变量值不变**,只是路径变。

**第三,可撤销操作**(undo)。拖错了节点?Ctrl+Z 恢复。这是工业 editor 的标配,用 Command pattern 实现——每个操作封装成 `MoveNode { from, to }` 对象,execute / undo 成对。Casey HH day 198 不实现 undo(简化),但工业 editor(Unity / Unreal / Photoshop)必须有。

层级编辑的另一关键问题是 **stable identity**——节点用什么作为唯一标识?有两种选择:

**path-based identity**:用路径字符串作 ID(`Player/Movement/Speed`)。优点:简单、可读、自动。缺点:**移动节点后 ID 变了**,所有持有旧 ID 的 state(expanded / hover / selection)失效。你拖一个节点,它的 expanded 状态丢失——用户体验差。

**UUID-based identity**:每个节点有 uuid(u64 或真正的 UUID),path 是 display 属性。改 path 不影响 ID,state 保留。优点:state 稳定。缺点:复杂,要维护 uuid ↔ path 双向映射。

工业 UI(Unity / Unreal)用 UUID-based——选中一个 actor,移动它到另一个 folder,selection 保留。Casey HH day 198 用 path-based(简化),所以拖动会丢 expanded state——debug UI 可以接受,商业 UI 不行。

## 2 · 心智模型

### 2.0 拖拽算法的实现

拖拽是 immediate-mode 的复杂交互。算法:

1. **drag start**:鼠标按下在节点上 → 记录 drag_source = path
2. **drag move**:鼠标移动 → 显示 drag preview(跟随鼠标)
3. **drag drop**:鼠标松开 → 命中测试找 drop target,执行 move

```rust
struct DragState {
    source_path: Option<String>,
    preview_pos: Option<(i32, i32)>,
}

fn draw_tree_with_drag(ui: &mut Ui, state: &mut DragState, tree: &mut Tree) {
    for (path, node) in tree.iter_mut() {
        let rect = node.rect;
        let hovered = ui.is_hovered(rect);

        // drag start
        if hovered && ui.mouse_pressed(MouseButton::Left) {
            state.source_path = Some(path.clone());
        }

        // drag move
        if state.source_path.is_some() {
            state.preview_pos = Some((ui.mouse_x, ui.mouse_y));
        }

        // drag drop
        if hovered && ui.mouse_released(MouseButton::Left) {
            if let Some(src) = &state.source_path.take() {
                if src != path {
                    tree.move_node(src, path);
                }
            }
        }

        // draw node + preview
        draw_node(ui, node);
        if let Some(p) = state.preview_pos {
            draw_drag_preview(ui, p);
        }
    }
}
```

### 2.0.2 路径重写的语义

把节点 `Player/Movement/Speed` 移到 `Player/Combat/`,新路径 `Player/Combat/Speed`。

```rust
fn move_node(&mut self, src: &str, dst_parent: &str) {
    let node_name = src.split('/').last().unwrap();
    let new_path = format!("{}/{}", dst_parent, node_name);

    // 从原位置删除
    let value = self.remove(src);
    // 插入新位置
    self.insert(&new_path, value);
}
```

**关键**:用 path 字符串作为 ID,改路径就是改 ID。所有持有旧 ID 的 state(expanded / hover)失效——这是 path-based ID 的弱点。

替代方案:**stable unique ID**(uuid)。每个节点有 uuid,path 是 display 属性。改 path 不影响 ID,state 保留。但 UI 显示 path,搜索 / 命令用 path。

### 2.0.3 undo / redo

拖拽改了层级,用户可能误操作。需要 undo:

```rust
struct History {
    undo_stack: Vec<Action>,
    redo_stack: Vec<Action>,
}

enum Action {
    MoveNode { from: String, to: String },
    // ...
}

fn move_node(&mut self, src: &str, dst: &str, history: &mut History) {
    self.do_move(src, dst);
    history.undo_stack.push(Action::MoveNode {
        from: src.to_string(),
        to: dst.to_string(),
    });
    history.redo_stack.clear();  // 新操作清 redo
}

fn undo(&mut self, history: &mut History) {
    if let Some(action) = history.undo_stack.pop() {
        match action {
            Action::MoveNode { from, to } => {
                let tmp = to.clone();
                self.do_move(&tmp, &from);  // 反向
                history.redo_stack.push(Action::MoveNode { from, to });
            }
        }
    }
}
```

Casey day 198 不做 undo(简化),工业 editor 必须有。Unity / Unreal 都有完整的 undo stack。

### 2.1 drag state

```rust
pub struct DragState {
    pub dragging: Option<(String /* source path */, DebugValue)>,
    pub ghost_pos: (f32, f32),
}

impl DragState {
    pub fn start(&mut self, path: &str, value: DebugValue, x: f32, y: f32) {
        self.dragging = Some((path.to_string(), value));
        self.ghost_pos = (x, y);
    }

    pub fn update(&mut self, mouse_x: f32, mouse_y: f32) {
        if self.dragging.is_some() {
            self.ghost_pos = (mouse_x, mouse_y);
        }
    }

    pub fn drop_on(&mut self, target_path: Option<&str>) -> Option<(String, String)> {
        // 返回 (source, new_path)
        if let Some((src, value)) = self.dragging.take() {
            let var_name = src.rsplit('/').next().unwrap_or(&src).to_string();
            let new_path = match target_path {
                Some(t) => format!("{}/{}", t, var_name),
                None => var_name.clone(),
            };
            return Some((src, new_path));
        }
        None
    }
}
```

### 2.2 tree 节点 drop 命中

```rust
fn draw_node_with_drop(
    ui: &mut Ui, drag: &mut DragState, mouse: &MouseState,
    node: &mut DebugNode, path: &str, x: f32, y: f32,
) {
    let in_node = is_in_rect(mouse.x, mouse.y, x, y, 200, 16);

    // 检测 drag 开始(左键 down 在节点上)
    if mouse.left_just_pressed && in_node && drag.dragging.is_none() {
        // 假设这是变量节点
        if let Some(value) = node.get_value() {
            drag.start(path, value.clone(), mouse.x, mouse.y);
        }
    }

    // 检测 drop(左键 up 时)
    if !mouse.left_pressed && drag.dragging.is_some() && in_node {
        if let Some((src, new_path)) = drag.drop_on(Some(path)) {
            ui.move_variable(&src, &new_path);
        }
    }

    // 渲染节点
    draw_rect(x, y, 200, 16, 0xFF222222);
    draw_text(node.name, x + 4, y + 4);

    // 渲染 ghost(如果正在 drag)
    if let Some((_, _)) = &drag.dragging {
        draw_rect(drag.ghost_pos.0, drag.ghost_pos.1, 200, 16, 0x80FFFFFF);
    }
}
```

### 2.3 路径变更

impl DebugTree {
    pub fn move_variable(&mut self, src_path: &str, new_path: &str) {
        // 1. 从 src_path 找到 value
        let value = self.remove(src_path);

### 3.4 · 🐧 Linux 系统编程视角

Linux 桌面的 drag-and-drop 是个跨进程的复杂系统,理解它你能看清"拖拽"在工业级实现里到底多深。

**X11 / Wayland 的 DnD 协议**。Linux 桌面的 drag-and-drop 不是 UI 库自己实现的——是 display server(X11 / Wayland)和 toolkit(GTK / Qt)协作的协议。你从 Nautilus(GNOME 文件管理器)拖一个文件到 GIMP,GIMP 接收这个文件——两个不同进程,通过 X server 中转。协议的核心是 **Xdnd(X Drag and Drop)**,X11 标准。Wayland 用 `wl_data_device` 协议,概念类似。

Xdnd 的工作流:
1. **drag source**(Nautilus)向 X server 注册 "我提供一个 drag",包含 supported types(text/uri-list、image/png、...)
2. X server 把鼠标事件路由给 drag source,同时给鼠标下的窗口发 `XdndPosition` 事件
3. **drop target**(GIMP)收到 `XdndPosition`,决定是否接受(检查 type 支持),回 `XdndStatus`
4. 用户松开鼠标,X server 发 `XdndDrop`,target 拿数据(通过 `XdndSelection` 的 property)
5. 数据用 **X selection mechanism** 传输(类似 clipboard)

整个协议在 ICCCM(International Cooperation for Better X Comm)和 freedesktop.org 规范里有详细定义。Rust 的 `winit` crate 在 Linux 上对接这套——你的应用收到 drag-drop event,实际是 winit 把 X11 协议事件翻译成 Rust API。

**GTK 的 DnD API** 是这套协议的高层封装。`gtk_drag_source_register`、`gtk_drag_dest_register`、signal `"drag-data-get"`、`"drag-data-received"`。你注册 widget 支持 drag-source / drop-target,设置 supported MIME types,GTK 自动处理协议细节。Casey HH 不接 GTK——他直接在 SDL/winit 的 raw mouse event 上写 drag 逻辑,没有跨进程拖拽。这是合理的取舍——debug UI 只在游戏窗口内拖,不需要跨进程。

**Qt 的 DnD API** 类似——`QDrag`、`QMimeData`、`dragEnterEvent` / `dropEvent`。Qt 比 GTK 更面向对象,把 drag 封装成 QObject。

**X11 selection mechanism** 是 clipboard 和 DnD 的底层。X server 维护若干 "selection"(PRIMARY、CLIPBOARD、XdndSelection),每个 selection 当前 owner 是某个窗口。当你"复制",你的窗口成为 CLIPBOARD 的 owner;粘贴时,target 窗口向 owner 请求数据。drag-and-drop 用同样的机制,只是 selection 名字不同。

**file manager 的拖拽语义** 是工业 drag-and-drop 的经典案例。Nautilus / Dolphin / Thunar 都支持:
- **拖到同盘文件夹**:move(原位置删,新位置加)
- **拖到不同盘**:copy(原位置保留)
- **Ctrl + 拖**:强制 copy
- **Shift + 拖**:强制 move
- **Alt + 拖**:弹菜单问"move / copy / link"

这些修饰键语义是 freedesktop.org 标准,Linux 桌面共享。Casey 的 debug hierarchy 拖拽只支持 move(简单),但工业 DnD 要支持多种操作 + 修饰键,API 复杂得多。

**touchscreen 的长按拖拽** 是另一变体。手机/平板没有右键和修饰键,drag 用 **long press** 触发——按住 500ms,然后开始 drag。GTK 4 / Qt 6 都支持。这是 touchscreen HIG(human interface guideline)的内容。

### 3.5 · 🦀 Rust 生态视角

Rust 生态的 drag-and-drop 有几个层次,从底到高:

**底层 raw event**(`winit` / `sdl2`)。winit 提供 `WindowEvent::CursorMoved`、`MouseInput`——只有鼠标位置和按键状态,drag 逻辑你自己写。Casey HH 用这一层,~100 行 Rust 写完整 drag 系统。

**Toolkit 层**(`egui` / `iced` / `tauri`)。egui 在 `Response` 上提供 `dnd_drag_source` / `dnd_release_target`:

```rust
// egui 的 DnD API(简化)
egui::dnd::DragDropItem::new(ui, id, |ui| {
    ui.label("Drag me!");
}).on_drop(|dropped_on| {
    println!("Dropped on {:?}", dropped_on);
});

let response = ui.button("Drop here");
if let Some(dropped) = response.dnd_release_target() {
    move_to(dropped);
}
```

egui 的 DnD 用 closure + ID,immediate-mode 风格——每帧声明 drag source / drop target,框架跟踪状态。

**跨进程 DnD**(`tauri` / `gtk-rs` / `Slint`)。Tauri 应用支持把文件从文件管理器拖到 app 窗口——这是接 OS 的 DnD 协议。`tauri::window::on_file_drop_event` 回调。gtk-rs 直接暴露 GTK 的 DnD API。

**Command pattern + undo** 是工业级 drag 系统的标配。Rust 实现示例:

```rust
trait Command: Send + Sync {
    fn execute(&mut self, state: &mut State);
    fn undo(&mut self, state: &mut State);
    fn description(&self) -> &str;
}

struct MoveNodeCommand {
    source_path: String,
    target_parent: String,
    original_value: Option<DebugValue>,
}

impl Command for MoveNodeCommand {
    fn execute(&mut self, state: &mut State) {
        self.original_value = state.debug_tree.remove(&self.source_path);
        if let Some(v) = &self.original_value {
            let name = self.source_path.rsplit('/').next().unwrap();
            let new_path = format!("{}/{}", self.target_parent, name);
            state.debug_tree.insert(&new_path, v.clone());
        }
    }

    fn undo(&mut self, state: &mut State) {
        // 移回去
        let name = self.source_path.rsplit('/').next().unwrap();
        let current_path = format!("{}/{}", self.target_parent, name);
        if let Some(v) = state.debug_tree.remove(&current_path) {
            state.debug_tree.insert(&self.source_path, v);
        }
    }

    fn description(&self) -> &str { "Move debug node" }
}

struct History {
    undo_stack: Vec<Box<dyn Command>>,
    redo_stack: Vec<Box<dyn Command>>,
}

impl History {
    fn execute(&mut self, mut cmd: Box<dyn Command>, state: &mut State) {
        cmd.execute(state);
        self.undo_stack.push(cmd);
        self.redo_stack.clear();  // 新操作清 redo
    }

    fn undo(&mut self, state: &mut State) {
        if let Some(mut cmd) = self.undo_stack.pop() {
            cmd.undo(state);
            self.redo_stack.push(cmd);
        }
    }

    fn redo(&mut self, state: &mut State) {
        if let Some(mut cmd) = self.redo_stack.pop() {
            cmd.execute(state);
            self.undo_stack.push(cmd);
        }
    }
}
```

这是经典 Command pattern ——每个操作封装成对象,execute / undo 成对。Unity / Unreal / Photoshop / GIMP 全都用这套。Casey HH day 198 不实现 undo(简化),但工业 editor 必须有。

**immediate-mode drag 的 ID 系统** 和 tree view 一样——drag source 用 path 字符串作 ID,drop target 也用 path。这样每帧重新声明 drag 交互,框架用 ID 关联状态。

**Rust async drag** 是个新方向。`tauri` 用 async 接收 OS DnD event,你的 handler 是 async fn。Rust 的 async/await 让 DnD 处理不阻塞 UI thread——文件大、MIME 解析慢时尤其重要。

**hit-testing 性能**:debug tree 节点数大时(1000+),每帧遍历找 drop target 慢。Rust 优化:用 **spatial index**(`rstar` / `kdtree`),鼠标位置 O(log N) 查最近节点。工业 UI 内部用 BVH(bounding volume hierarchy)做 hit testing,支持百万节点。

### 3.6 · 🐧 Linux 系统编程视角(X11/Wayland DnD 协议)

Linux 桌面环境的 UI 工具栈,从底到顶是这套:内核 evdev(输入事件)→ libinput(输入归一化)→ Wayland compositor / X server(display server)→ toolkit(GTK / Qt / egui)→ 应用。每一层都为 UI 加抽象。

**evdev** 是内核的输入事件接口。键盘、鼠标、触摸屏的硬件事件,通过 `/dev/input/event*` 字符设备暴露。每个事件是 `struct input_event`——时间戳、类型(EV_KEY / EV_ABS / EV_REL)、code(BTN_LEFT / ABS_X)、value(0/1/2)。用户态进程读这个字符设备流,拿到原始硬件事件。

```bash
# 看 evdev 设备
sudo pacman -S evtest
sudo evtest /dev/input/event0   # 看你鼠标的事件流
# 移动鼠标、点击,看 event 输出
```

**libinput** 抽象 evdev——它处理多个设备、做去抖动、合成 tap-to-click、trackpad gesture、acceleration profile。toolkit 不直接读 evdev,而是用 libinput,这样跨设备统一。Casey HH 不用 libinput,直接用 SDL 的抽象,SDL 内部在 Linux 用 libinput。

**Wayland** 是现代 Linux display server 协议(替代 X11)。Wayland 用 `wl_seat` 协议传递输入事件给应用。应用注册 listener,Wayland server 把 pointer/keyboard event 推过来。Casey HH 用 SDL/winit,SDL/winit 内部在 Wayland 上对接 wl_seat。

**X11** 是 1980 年代的 display server,至今仍广泛用。X11 协议复杂(XCreateWindow、XMapWindow、XSelectInput、XNextEvent...),但它有 30+ 年的稳定 ABI。Wayland 替代 X11 的进程已 10+ 年,但仍未完成。

**GTK / Qt** 是 Linux 桌面两大 UI toolkit。GTK 用 C 写但支持多语言绑定;Qt 用 C++ 写也有多语言绑定。它们的 widget 系统、layout 系统、事件分发,是工业级 UI 实现的范本。Rust 的 gtk-rs 给 GTK Rust 绑定,qt-rs 给 Qt 绑定。

**systemd / D-Bus / XDG** 是 Linux 桌面的服务/IPC/规范层。systemd 管理服务,D-Bus 跨进程通信,XDG 规范桌面环境目录(`/usr/share/applications`、`~/.config`)。这些都和 UI 间接相关——你的应用通过 D-Bus 通知桌面,通过 XDG 找到图标资源。

**clipboards(X11 selection)** 是 Linux 跨进程 UI 的经典案例。Linux 有三个 selection:PRIMARY(选中即复制,中键粘贴)、CLIPBOARD(Ctrl+C / Ctrl+V)、SECONDARY(几乎没人用)。每个 selection 当前 owner 是某个窗口,数据存在 owner 进程。复制时数据**不立刻传给 server**,而是 owner 记录"我有这个 selection",target 窗口粘贴时向 owner 请求数据——这种延迟传输(称为 "selection transfer protocol")避免大数据复制两次。

```bash
# X11 看剪贴板 owner
xclip -o -selection clipboard
xclip -o -selection primary

# Wayland
wl-paste --primary

# 看 X11 clients
xlsclients
```

**fontconfig / freetype / harfbuzz / pango / cairo / pixman** 是 Linux 字体和渲染栈。fontconfig 找字体文件(/usr/share/fonts、~/.fonts),freetype 解析 TTF/OTF,harfbuzz 做 text shaping(组合字符、连字、复杂脚本如阿拉伯文),pango 把文字组织成 layout,cairo/pixman 把 layout 渲染成像素。这套栈在 1990-2010 年代由 Red Hat 主导开发,是 Linux 桌面的基础设施。Rust 的 piet、cosmic-text、swash 是新一代实现,但要追平这套栈还要多年。

**XKB / evdev** 处理键盘布局。XKB(X Keyboard Extension)是 X11 的键盘映射系统——你按物理键 KeyA,XKB 根据 layout(US / Dvorak / 中文)把它映射到 keysym(XK_a),toolkit 把 keysym 映射到字符 "a"。Wayland 用 `xkbcommon` 库,逻辑相同。

### 3.7 · 🦀 Rust 生态视角(Rust DnD 库)

Rust UI 生态在 2024 年是个活跃领域,有几十个库,各有取舍。

**`egui`** 是 immediate-mode UI 的事实标准。每帧重新声明 widget,API 简洁:

```rust
egui::CentralPanel::default().show(&ctx, |ui| {
    ui.heading("Debug");
    ui.separator();
    ui.horizontal(|ui| {
        ui.label("Speed:");
        ui.add(egui::Slider::new(&mut speed, 0.0..=10.0));
    });
    if ui.button("Reset").clicked() {
        speed = 5.0;
    }
});
```

egui 适合 debug UI、工具 UI、原型 UI——上手快、代码短。劣势是不适合发布 UI(无 accessibility、不够精美)。

**`iced`** 是 Elm 风格 UI——你写 model + update + view 三件套,框架处理 message 流。Iced 用 taffy layout 引擎,支持完整 flexbox。Iced 适合应用 UI(类浏览器、编辑器),代码结构清晰但比 egui 啰嗦。

**`tauri`** 是 web UI + Rust 后端。前端用 React/Vue/Svelte,后端用 Rust,通过 IPC 通信。Tauri 适合桌面应用——你享受 web 生态(NPM、CSS、HTML),但 binary 小、性能好(不嵌 Chromium,用系统 webview)。

**`slint`** 是商业 UI 框架,有自己的 DSL。Slint DSL 类似 QML:

```slint
export component MainWindow inherits Window {
    property <float> speed;
    Text { text: "Speed: " + speed; }
    Slider { value <=> speed; }
}
```

Slint DSL 编译成 Rust 代码,运行时零开销。Slint 适合嵌入式 UI(汽车仪表盘、家电面板)——binary 小、启动快、内存可控。

**`bevy_ui`** 是 Bevy ECS 的 UI 子系统。每个 widget 是 Entity,有 Component,系统遍历 Component 树渲染。这是 Rust 风格的 ECS UI——数据导向、cache 友好。Bevy UI 适合游戏内 UI(HUD、菜单)。

**`druid`** 已停止维护,但它的理念——data + lens + widget——影响了后来的库。Lens 是函数式编程的概念,让"嵌套数据的访问"变成可组合的 first-class value。

**`taffy`** 是 layout 引擎,被多个 UI 库共用。taffy 实现 CSS flexbox + grid spec,纯 Rust,性能极高(每帧 layout 10000 节点 < 1ms)。这是 Rust 在 UI 底层的杀手锏——同样功能 C++ 实现(Chrome Blink layout)慢 2-3 倍。

**`cosmic-text`** 是 Rust 的 text shaping + 布局引擎,由 System76 开发(用于 Pop!_OS COSMIC 桌面)。它整合了 Rust 的字体库(rustybuzz、swash、ab_glyph),提供完整文字渲染流水线。这是 Rust 替代 pango/freetype/harfbuzz 的尝试,目前可用。

**Rust 的 trait object vs monomorphization**。UI 库要支持任意 widget 类型,有两种方式:`Box<dyn Widget>`(trait object,动态分发)或 `impl Widget`(泛型,单态化)。egui 用 trait object(灵活)、iced 用泛型(性能)、bevy 用 ECS Component(数据导向)。每种方案的取舍反映在 API 设计上。

**Rust UI 的 accessibility**。Linux 的 AT-SPI(Assistive Technology Service Provider Interface)是 accessibility 标准——screen reader(Orca)通过 AT-SPI 朗读 UI 元素。Rust 的 `accesskit` crate 提供 UI accessibility 抽象,让 UI 库一次实现、跨平台(Linux AT-SPI / Windows UIA / macOS AXUIElement)。egui / iced / druid 都接 accesskit,这是 Rust UI 生态对 accessibility 的认真承诺。

**Rust 的 async UI**。iced 用 async,handler 是 async fn,处理事件可 await。Rust 的 async/await 让 UI 不阻塞——长时间任务(网络请求、文件 IO)async,UI thread 继续响应。这是 Rust UI 比 JS UI 优势的地方——零成本异步,不是单线程事件循环。

### Command pattern 与 undo

工业 undo 系统用 **Command pattern**(GoF 设计模式之一):

```rust
trait Command {
    fn execute(&mut self, state: &mut State);
    fn undo(&mut self, state: &mut State);
}

struct MoveNode { from: String, to: String }

impl Command for MoveNode {
    fn execute(&mut self, state: &mut State) {
        state.move_node(&self.from, &self.to);
    }
    fn undo(&mut self, state: &mut State) {
        state.move_node(&self.to, &self.from);
    }
}

struct History {
    undo: Vec<Box<dyn Command>>,
    redo: Vec<Box<dyn Command>>,
}
```

每个用户操作封装成 Command,execute / undo 成对。Unity / Unreal / Photoshop 都用 Command pattern。

### ImGui 的 drag-drop API

Dear ImGui 内置 drag-drop API:

```cpp
ImGui::BeginDragDropSource();
ImGui::SetDragDropPayload("DND_NODE", &node_id, sizeof(node_id));
ImGui::EndDragDropSource();

if (ImGui::BeginDragDropTarget()) {
    if (const ImGuiPayload* payload = ImGui::AcceptDragDropPayload("DND_NODE")) {
        // 处理 drop
    }
    ImGui::EndDragDropTarget();
}
```

类型化的 payload("DND_NODE")避免不同 drag-drop 系统混淆(图片拖拽 vs 节点拖拽)。Casey 的简化版没有类型 payload,但概念相同。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不能直接用"鼠标 down + 移动 = drag"?要区分 click 和 drag?

**参考解答**:
- click:down + up 在同一位置(或小范围内)
- drag:down + 移动超过阈值 + up
- 区别:**意图**——click 是选,darg 是搬
- 实现:down 后,移动距离 > 5 像素才认定 drag
- 阈值小:容易误触发 drag;阈值大:click 响应慢
- 通常 4-8 像素

### Lv2 · 动手实践

**题**:实现 drag threshold:鼠标 down 后,移动超过 5 像素才触发 drag callback。

**参考解答**:

```rust
struct ClickTracker {
    down_pos: Option<(f32, f32)>,
    is_dragging: bool,
}

impl ClickTracker {
    fn new() -> Self { Self { down_pos: None, is_dragging: false } }

    fn on_down(&mut self, x: f32, y: f32) {
        self.down_pos = Some((x, y));
        self.is_dragging = false;
    }

    fn on_move(&mut self, x: f32, y: f32) -> bool {
        // 返回 true 如果刚开始 drag
        if let Some((dx, dy)) = self.down_pos {
            let dist = ((x - dx).powi(2) + (y - dy).powi(2)).sqrt();
            if dist > 5.0 && !self.is_dragging {
                self.is_dragging = true;
                return true;
            }
        }
        false
    }

    fn on_up(&mut self) -> ClickResult {
        let result = if self.is_dragging {
            ClickResult::Drag
        } else if self.down_pos.is_some() {
            ClickResult::Click
        } else {
            ClickResult::None
        };
        self.down_pos = None;
        self.is_dragging = false;
        result
    }
}

#[derive(PartialEq, Debug)]
enum ClickResult { None, Click, Drag }

fn main() {
    let mut tracker = ClickTracker::new();
    tracker.on_down(10.0, 10.0);
    assert_eq!(tracker.on_move(11.0, 11.0), false);  // 移动小,不 drag
    assert_eq!(tracker.on_up(), ClickResult::Click);

    tracker.on_down(10.0, 10.0);
    assert_eq!(tracker.on_move(20.0, 20.0), true);  // 移动大,开始 drag
    assert_eq!(tracker.on_up(), ClickResult::Drag);
    println!("OK");
}
```
