# Day 249 · 清理调试宏

> Day 177 你写了 `TIMED_BLOCK()` 宏自动包裹函数做性能计数。Day 178 加线程安全,Day 181 改 log-based,Day 213 转成 events。回头看,你有 5 个调试宏,其中 3 个已经没用了——Rust 的 attribute / cfg 系统 + 日志库替代。今天 Casey 删冗余宏。

## 0 · 为什么要有这一天

宏(macro)是 C / Rust 的"代码生成器"——一段代码生成另一段。Day 177-213 Casey 加了:

```c
TIMED_BLOCK()       // 计时函数
TIMED_FUNCTION()    // 同上但更宽
DEBUG_DATA_BLOCK()  // 数据块
DEBUG_HIERARCHY()   // 层级
DEBUG_RECORD()      // 录制
```

5 个宏,经过 30 集演化,其中 3 个已经功能重叠:

- `TIMED_BLOCK` 和 `TIMED_FUNCTION` 实际一样
- `DEBUG_RECORD` 被 Day 213 events 取代
- `DEBUG_HIERARCHY` 被 Day 219 auto hierarchy 取代

留着的只有历史代码里的调用。Day 249 Casey 把 dead macros 删掉:

```rust
// 之前
macro_rules! timed_block { ... }
macro_rules! timed_function { ... }
macro_rules! debug_data_block { ... }
macro_rules! debug_hierarchy { ... }
macro_rules! debug_record { ... }

// 之后
macro_rules! timed_block { ... }
macro_rules! debug_data_block { ... }
```

5 个 → 2 个,代码量从 500 行降到 150 行。

**为什么这件事重要**:宏是强力工具但易被滥用。学会审视宏,删冗余,是 Rust 高级技能。

**心理锚点**:看完今天,你能审视自己写的所有宏,删冗余,留必要的。

## 1 · Casey 今天做了什么

## 2 · 心智模型

### 类比:工具箱清理

工具箱塞太多:

- 5 把一字螺丝刀(不同长度)
- 实际只用 2 把
- 3 把可以收起来

清理:**留 2 把常用的,3 把收起来**(或送人)。下次找工具更快。

宏一样:**保留你每天用的**,其他删掉或合并。

### 2.1 Rust 宏 vs C 宏

Rust 宏(`macro_rules!`)和 C 宏(`#define`)不同:

| | C 宏 | Rust 宏 |
|---|---|---|
| 文本替换 | 是 | 否(语法树操作) |
| 调试 | 难(展开后乱) | 易(rustc 显示展开) |
| 类型安全 | 无 | 有(展开后类型检查) |
| 复杂度 | 低 | 中 |

Rust 宏更安全,但仍然容易过度使用。

### 2.2 Rust 宏的合理用例

Rust 宏适合:

- **减少重复**(`println!` / `vec!`)
- **DSL**(领域特定语言,如 sqlx::query!)
- **attribute 派生**(`#[derive(Debug)]`)
- **早绑定的字符串**(`file!()`, `line!()`)

不适合:

- 替代函数(用 generic 函数更好)
- 控制流(用 trait / enum)
- 类型 dispatch(用 trait object / enum)

### 2.3 TIMED_BLOCK 宏分析

```rust
macro_rules! timed_block {
    ($name:literal, $body:block) => {
        let _guard = $crate::profiler::TimerGuard::new($name);
        $body
        // _guard drop 时记录时间
    };
}

// 调用
timed_block!("game_update", {
    // ... 游戏代码 ...
});
```

合理:利用 Rust 的 RAII(`TimerGuard::drop` 自动),宏包裹代码块。函数做不到这种语法。

但 Day 177 还有 `timed_function`:

```rust
macro_rules! timed_function {
    ($name:literal) => {
        let _guard = $crate::profiler::TimerGuard::new($name);
    };
}

// 调用
fn game_update() {
    timed_function!("game_update");
    // ... 函数体 ...
}
```

两个宏**做同样的事**(都是创建 TimerGuard),只是语法不同。Day 249 合并成 1 个。

### 2.4 检查宏使用频率

```bash
# 找所有 timed_block 调用
grep -rn "timed_block!" src/
# 输出:50 处调用

# 找 timed_function 调用
grep -rn "timed_function!" src/
# 输出:3 处调用

# 找 debug_record 调用
grep -rn "debug_record!" src/
# 输出:0 处(没用)
```

策略:

- `timed_block`:留(高频用)
- `timed_function`:删(只 3 处,直接 inline)
- `debug_record`:删(0 调用)
- `debug_hierarchy`:删(被 Day 219 取代)
- `debug_data_block`:留(独特功能)

### 2.5 重构调用点

删 `timed_function`:

```rust
// 之前
fn game_update() {
    timed_function!("game_update");
    // ...
}

// 之后
fn game_update() {
    let _guard = profiler::TimerGuard::new("game_update");
    // ...
}
```

或者用 `timed_block`:

```rust
fn game_update() {
    timed_block!("game_update", {
        // ...
    });
}
```

后者语法更清晰。

### 2.6 Rust 宏的替代品

很多时候**函数 + attribute** 比宏好:

```rust
// 宏
macro_rules! debug_assert_eq {
    ($a:expr, $b:expr) => {
        if cfg!(debug_assertions) {
            assert_eq!($a, $b);
        }
    };
}

// Rust 内置
debug_assert_eq!(a, b);  // 已经有这个 macro
```

或者 attribute:

```rust
#[cfg(debug_assertions)]
fn debug_only() { /* ... */ }
```

跟 HH 学的宏替换为 attribute / cfg,通常更清晰。

### 3.1 · 🎮 游戏编程视角

**游戏代码常见宏**:

- `LOG(level, msg)` —— 日志
- `ASSERT(expr)` —— 断言

### 3.2 · 🎨 图形学视角

shader 宏(GLSL `#define`):

```glsl
#define PI 3.14159
#define MAX_LIGHTS 8
#define SAMPLE_COUNT 4
```

合理用:`#define` 是编译时常量。但如果 GLSL 里有:

```glsl
#define COMPUTE_LIGHT(l) compute_light_##l(...)
```

复杂宏通常可读性差。GLSL 4.0+ 支持函数,用函数替代。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核宏大杂烩:

```c
#define container_of(ptr, type, member) ({ \
    const typeof( ((type *)0)->member ) *__mptr = (ptr); \
    (type *)( (char *)__mptr - offsetof(type,member) );})
```

这种宏在 Rust 里直接用 trait / associated type 表达,清晰得多。

`#define min(a, b) ((a) < (b) ? (a) : (b))` 这种著名 bug(参数被 evaluate 两次)在 Rust 用 generic 函数避免:

```rust
fn min<T: Ord>(a: T, b: T) -> T {
    if a < b { a } else { b }
}
```

### 3.4 · 🦀 Rust 生态视角

**Rust decl_macro**(RFC 1583):

```rust
macro_rules! vec_of_strings {
    ($($x:expr),*) => {
        vec![$($x.to_string()),*]
    };
}

let v = vec_of_strings![1, 2, 3];
// 等价 vec!["1".to_string(), "2".to_string(), "3".to_string()]
```

**proc_macro**(过程宏):

- `#[derive(Debug)]` —— 派生 trait
- `#[derive(Serialize)]` —— serde
- 自定义:`#[my_macro] fn foo() {}`

proc_macro 比 macro_rules 更强,但写起来更复杂。

**何时用 macro vs 函数**:

| | 函数 | 宏 |
|---|---|---|
| 类型 | generic | 任意 |
| 调用开销 | 0(inline) | 0(展开) |
| 调试 | 好 | 中(展开后看) |
| 灵活度 | 中 | 高 |
| 推荐 | 默认 | 必要时 |

跟 HH 学:优先函数,宏做"函数做不到"的事(语法扩展 / 早绑定字符串)。

## 5 · 对照与变奏

### 同一功能:用宏 vs 用 trait

```rust
// 宏:计时
macro_rules! timed {
    ($name:expr, $body:block) => {{
        let _g = Timer::start($name);
        $body
    }};
}

// trait + RAII:计时
struct TimerGuard { name: &'static str, start: Instant }
impl Drop for TimerGuard {
    fn drop(&mut self) { record(self.name, self.start.elapsed()); }
}
fn timed<F: FnOnce() -> R, R>(name: &'static str, f: F) -> R {
    let _g = TimerGuard { name, start: Instant::now() };
    f()
}
```

宏的语法糖(`timed!("name", { ... })`),函数做不到。但函数更易调试、可测。

跟 HH 用宏,因为 Casey 在 C 里也用宏(C 没有 RAII)。

### Rust 宏的安全保证

- **hygiene** —— 宏内变量不污染外部
- **类型检查** —— 展开后类型检查
- **编译错误** —— 宏 misuse 报清晰错误

C 宏没这些。Rust 宏可以放心用。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Rust 的 `macro_rules!` 和函数的核心差别?为什么 `println!` 必须是宏?

**参考解答**:函数的参数在调用前全部 evaluate,类型固定。宏的参数是"语法片段",可以在调用点反复使用或选择性 evaluate。

`println!("Hello, {}!", name)` 必须是宏,因为:

1. **格式字符串是编译时验证** —— 函数做不到(运行时才能解析)
2. **可变参数** —— Rust 函数不支持真正可变参数(只有 macro / variadic generic nightly)
3. **不 evaluate 没用到的参数** —— `println!("{} {}", a, b)` 如果格式串不引用 b,b 不会被 evaluate(其实会,但 macro 让它灵活)

### Lv2 · 动手实践

### Rust 宏清理示例

```rust
// === 之前(Day 213 风格,5 个宏) ===
mod old {
    #[macro_export]
    macro_rules! timed_block {
        ($name:literal, $body:block) => {{
            let _guard = $crate::TimerGuard::new($name);
            $body
        }};
    }

    #[macro_export]
    macro_rules! timed_function {
        ($name:literal) => {
            let _guard = $crate::TimerGuard::new($name);
        };
    }

    #[macro_export]
    macro_rules! debug_data_block {
        ($name:literal, $data:expr) => {{
            $crate::DebugEvent::DataBlock {
                name: $name,
                data: $data,
            }.emit();
        }};
    }

    #[macro_export]
    macro_rules! debug_record {
        // 0 调用
        ($name:literal) => { /* ... */ };
    }

    #[macro_export]
    macro_rules! debug_hierarchy {
        // 0 调用(Day 219 取代)
        ($name:literal) => { /* ... */ };
    }
}

// === 之后(Day 249,2 个宏) ===
mod new {
    use std::time::Instant;

    pub struct TimerGuard {
        name: &'static str,
        start: Instant,
    }

    impl TimerGuard {
        pub fn new(name: &'static str) -> Self {
            Self { name, start: Instant::now() }
        }
    }

    impl Drop for TimerGuard {
        fn drop(&mut self) {
            let elapsed = self.start.elapsed();
            eprintln!("[profiler] {} {:?}", self.name, elapsed);
        }
    }

    #[macro_export]
    macro_rules! timed_block {
        ($name:literal, $body:block) => {{
            let _guard = $crate::new::TimerGuard::new($name);
            $body
        }};
    }

    #[macro_export]
    macro_rules! debug_data {
        ($name:literal, $data:expr) => {{
            eprintln!("[debug] {} = {:?}", $name, $data);
        }};
    }
}

// === 调用点重写 ===
fn game_update() {
    // 之前:timed_function!("game_update");
    // 之后:
    let _guard = new::TimerGuard::new("game_update");
    // 函数体...
}

fn render() {
    timed_block!("render", {
        // 渲染代码
    });
}

fn main() {
    game_update();
    render();
    debug_data!("frame_time", 16.7);
}
```

## 10 · 深入:Rust 宏的工程实践

casey 在 day249 清理 debug 宏——这是 Rust 宏工程的实战教学。

### 10.1 Rust 宏的种类

- **declarative macros**(`macro_rules!`):模式匹配,简单
- **procedural macros**:派生 / 属性 / 函数,复杂
- **macro 2.0**(未稳定):未来声明式宏

casey HH 用 declarative macros。

### 10.2 debug 宏的典型设计

```rust
#[macro_export]
macro_rules! debug_var {
    ($name:literal, $value:expr) => {
        $crate::debug::register_var($name, $crate::debug::Variant::from($value));
    };
}

// 使用
debug_var!("player_health", state.player.health);
```

宏展开成函数调用,自动注册 debug 变量。

### 10.3 casey 的简化

day249 之前,debug 宏可能有多个变体:

```rust
debug_var!("name", value);
debug_var_int!("name", value);
debug_var_float!("name", value);
debug_var_bool!("name", value);
debug_var_vec3!("name", value);
// 5 个宏
```

简化为 1 个:

```rust
debug_var!("name", value);  // 自动推断类型
```

通过 `From<T> for Variant`,宏内部统一调用。代码量减少 80%。

### 10.4 Rust macro 的 hygiene

Rust macro 是 **hygienic**——宏内定义的标识符不污染调用方:

```rust
macro_rules! foo {
    () => {
        let x = 42;  // 这个 x 不污染调用方
        println!("{}", x);
    };
}

fn main() {
    foo!();  // OK
    let x = "hello";  // OK,不冲突
}
```

casey 在 day249 反复讨论 hygiene——宏内 `_guard` 不污染调用方。

### 10.5 procedural macro

declarative 不够时,用 procedural macro:

```rust
use proc_macro::TokenStream;

#[proc_macro_attribute]
pub fn timed(_attr: TokenStream, item: TokenStream) -> TokenStream {
    // 解析 AST,生成代码
}
```

procedural macro 强大但复杂,需要单独 crate。casey HH 不用,但生产项目常见。

### 10.6 教学总结

day249 的核心要点:

1. **declarative macro**:简单场景用
2. **hygiene**:宏不污染调用方
3. **简化多个变体**:类型推断统一
4. **procedural macro**:复杂场景,casey 不用
5. **Rust macro 比 C 强**:类型安全、hygiene

### 10.7 宏的工业级应用

Rust 生态的宏应用:

- **serde `#[derive(Serialize)]`**:procedural macro 自动生成序列化代码
- **tokio `#[tokio::main]`**:procedural macro 包装 async main
- **clap `#[derive(Parser)]`**:procedural macro 生成 CLI parser
- **thiserror `#[derive(Error)]`**:procedural macro 生成错误类型
- **log `info!() / debug!()`**:declarative macro 日志

casey HH 的 debug 宏是 declarative,简单实用。学完后,你看 Rust 生态的宏都能秒懂。

### 10.8 宏的优缺点

- DSL 风格,可读
- 编译时生成,零运行时开销

**缺点**:
- IDE 支持差(rust-analyzer 仍在改进)
- 错误信息不友好
- 调试困难
