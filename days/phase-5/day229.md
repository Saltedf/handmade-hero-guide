
# Day 229 · 排序渲染元素 + sort key

> 渲染一帧画面有上千个 element(精灵、粒子、UI)。它们必须按特定顺序画(背景先、UI 后),否则视觉错乱。今天 casey 引入 sort key:把"画什么、什么层、是否透明"打包成一个整数,排序一次决定所有渲染顺序。

## 0 · 为什么要有这一天

游戏每帧要画几百到几万个 element:

- 背景瓦片(tile map)
- 静态装饰(树、石头)
- 动态实体(玩家、敌人、子弹)
- 粒子特效
- UI(HUD、菜单)
- Debug overlay

直接画会出现问题:

- **透明错误**:半透明精灵如果先画,被后画的背景覆盖,半透明效果丢失
- **z-order 错误**:远处的山应该被近处的树挡住,但顺序错则反过来
- **状态切换**:GPU 切换纹理 / shader 开销大,如果连续画用不同纹理的精灵,反复切换慢

**casey 今天的方案**:**sort key**——一个 u64 整数,编码所有排序维度:

```
sort_key = (layer << 32) | (depth << 16) | (texture_id << 8) | sub_index
```

按 sort_key 升序排,得到正确的渲染顺序。同时:

- 同 layer 按深度排(深度小的先画)
- 同深度按纹理排(同纹理的连续画,减少切换)

这是 GPU 渲染优化的核心模式。所有工业引擎都做类似的 sort key batching。

心理锚点:看完今天,你能解释"为什么 AAA 游戏几千个精灵能稳定 60 FPS"——一半功劳在 sort key batching。

## 1 · Casey 今天做了什么

1. **加 SortKey struct**:u64 + bit field

## 2 · 心智模型

### 类比:邮编系统

邮编把"国家、省、市、区"打包成一个数字:

```
100010 = 北京市东城区
200120 = 上海市浦东新区
```

排序邮编时,国家先排、省内再排市、市内再排区。**多维度打包成单维**。

sort key 就是游戏元素的"邮编":把多维排序需求(layer / depth / texture)打包成一个 u64。

### 2.1 SortKey 位布局

64 位可以拆分:

```
bits  63-56 (8 bits = 256):   layer       (background / world / ui / overlay / ...)
bits  55-48 (8 bits = 256):   sub_layer   (layer 内细分)
bits  47-32 (16 bits = 65536): depth       (Z 排序)
bits  31-16 (16 bits):        texture_id  (减少切换)
bits  15-0  (16 bits):        sub_index   (同纹理内顺序)
```

构造:

```rust
fn make_sort_key(layer: u8, sub_layer: u8, depth: u16, texture_id: u16, sub: u16) -> u64 {
    ((layer as u64) << 56)
    | ((sub_layer as u64) << 48)
    | ((depth as u64) << 32)
    | ((texture_id as u64) << 16)
    | (sub as u64)
}
```

升序排后:

- layer 小的先(背景 layer=0 先画)
- 同 layer sub_layer 小的先
- 同 sub_layer depth 小的先(远的先画)
- 同 depth texture_id 小的先(同纹理连续)
- 同 texture sub 小的先

### 2.2 Transparency 排序

半透明和不透明排序规则不同:

- **不透明 (opaque)**:depth 小的先画(启用深度测试,后面的被遮挡自动丢弃)
- **半透明 (transparent)**:depth 大的先画(painter's algorithm,远的先画近的后画,半透明正确合成)

casey 的方案:把 transparency 编码进 layer bit:

```
Layer 0: opaque background
Layer 1: opaque world
Layer 2: opaque entities
Layer 3: transparent world
Layer 4: transparent entities
Layer 5: UI
```

opaque 在前(layer 小),transparent 在后(layer 大)。同 layer 内 depth 升序——但 transparent 想要 depth 降序。casey 解决:transparent 把 depth 取反(`!depth`)再排,等效降序。

```rust
fn make_sort_key(...): u64 {
    let depth_bits = if is_transparent {
        (!depth) as u16 as u64  // 取反
    } else {
        depth as u64
    };
    ...
}
```

### 2.3 Batching 收益

GPU 绘制一个 sprite 需要:

- Bind texture(`glBindTexture`)
- Bind shader(`glUseProgram`)
- Set uniforms(matrix、color)
- Draw arrays

切换纹理 / shader 都是几十到几百 ns。1000 个 sprite 用 100 个不同纹理,naive 顺序:1000 次切换。按 texture_id 排序后:100 次切换(每个纹理一次性画所有用它的 sprite)。

收益:10 倍速度。

### 2.4 排序算法选择

1000 个 element 排序:

- **Comparison sort (quick / merge)**:O(n log n),~10000 操作
- **Radix sort**:O(n),~8000 操作(每 byte 一次 pass,8 byte = 8 pass)

Radix 略快但复杂。Casey Day 234 用 radix sort 实现 sort key。今天先用 `sort_by_key`,Day 234 优化。

## 3 · 四域深入

### 3.1 · 游戏编程视角

sort key 是渲染优化的核心。工业实现:

- **Unreal**:mesh draw calls sort by "draw key"(depth + material + transpose)
- **Unity**:SRP Batcher 按 shader 类型排序
- **WebGL / OpenGL**:z-prepass + opaque + transparent 三段

casey 的 sort key 是简化版,Day 234 radix sort + Day 235+ OpenGL 完整化。

### 3.2 · 图形学视角

GPU 渲染管线的排序需求:

```
1. Shadow pass:按光源排序
2. Opaque pass:按 depth + material 排序(depth 小先,reduce overdraw)
3. Transparent pass:按 depth 排序(depth 大先,painter's algorithm)
4. UI pass:按 layer 排序
5. Post-process:按 effect 排序
```

每段用不同 sort key。casey 在 day 235+ OpenGL 会拆分 pass。

### 3.3 · Linux 系统编程视角

Linux 内核也大量用 sort key 风格:

- **Page reclaim**:按 LRU 年龄排序
- **IO scheduler**:按 sector 排序(deadline / cfq 调度器)
- **Network packet scheduler**:按 QoS 字段排序

所有这些都是"多维排序需求打包成单 key"。

### 3.4 · Rust 生态视角

Rust 排序:

```rust
// sort_by_key
elements.sort_by_key(|e| e.sort_key);

// sort_unstable_by_key(更快,不保持相等元素顺序)

// radix sort(Day 234)
// 自己实现或用 crate
```

`sort_unstable` 比 `sort` 快 1.5-2 倍,因为不需要保持相等元素的原始顺序。casey 的渲染排序不关心相等元素顺序(同 key 不在乎哪个先),用 unstable。

参考 crate:`radixsort`、`voracious_radix_sort`(高性能 radix)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 opaque 和 transparent 的 depth 排序方向相反?

**参考解答**:opaque 用 depth buffer 写入,远的先画近的后画——近的覆盖远的(depth test 通过),正确。transparent 不写 depth(否则半透明部分会遮挡后面的),只能 painter's algorithm——远的先画,近的后画在上面,合成正确。所以 transparent depth 降序(远先),opaque depth 升序(也是远先,但 depth buffer 让近的覆盖)。

注意:opaque 升序 = 远先(depth 值大表示远时,要降序才远先;depth 值小表示远时,升序就是远先)。要看 depth 定义。Casey 用"近的 depth 小"约定,所以 opaque 升序、transparent 取反。

### Lv2 · 动手实践

**题**:实现 SortKey + 排序 + 模拟渲染(打印顺序)。

**参考解答**:

```rust
#[derive(Clone, Debug)]
struct RenderElement {
    name: &'static str,
    layer: u8,
    depth: u16,
    texture_id: u16,
    is_transparent: bool,
}

impl RenderElement {
    fn sort_key(&self) -> u64 {
        let layer_bits = self.layer as u64;
        // transparent 在 layer 后追加(晚画)
        let layer_with_transparency = if self.is_transparent {
            layer_bits | (1 << 4)  // 假设 layer 用低 4 bit
        } else {
            layer_bits
        };
        let depth_bits = if self.is_transparent {
            (!(self.depth as u64)) & 0xFFFF  // 取反
        } else {
            self.depth as u64
        };
        (layer_with_transparency << 48)
        | (depth_bits << 16)
        | (self.texture_id as u64)
    }
}

fn render(elements: &mut Vec<RenderElement>) {
    elements.sort_by_key(|e| e.sort_key());
    println!("Render order:");
    for e in elements {
        println!("  {} (layer={}, depth={}, tex={}, key={:#x})",
                 e.name, e.layer, e.depth, e.texture_id, e.sort_key());
    }
}

fn main() {
    let mut elements = vec![
        RenderElement { name: "bg_tile",     layer: 0, depth: 1000, texture_id: 1, is_transparent: false },
        RenderElement { name: "tree",        layer: 1, depth: 500,  texture_id: 2, is_transparent: false },
        RenderElement { name: "player",      layer: 1, depth: 400,  texture_id: 3, is_transparent: false },
        RenderElement { name: "smoke",       layer: 2, depth: 300,  texture_id: 4, is_transparent: true },
        RenderElement { name: "fire",        layer: 2, depth: 350,  texture_id: 4, is_transparent: true },
        RenderElement { name: "ui_button",   layer: 3, depth: 0,    texture_id: 5, is_transparent: false },
    ];
    render(&mut elements);
}
```

## 10 · 深入:渲染排序的工业级实现

casey 今天引入"sort key"——给每个渲染元素分配 u64,排序后决定绘制顺序。这是 GPU 渲染的核心优化技术。让我们把它彻底讲透。

### 10.1 sort key 的位编码

casey 把多个维度编码到单个 u64:

```
63                47                31                15               0
┌─────────────────┬─────────────────┬─────────────────┬───────────────┐
│ layer (8 bit)   │ texture (16 bit)│ depth (24 bit)  │ flags (16 bit)│
└─────────────────┴─────────────────┴─────────────────┴───────────────┘
```

每个字段占据连续 bits,排序时按整体 u64 大小排,自动按"layer > texture > depth > flags"优先级。

为什么这么编码?

**1. 一次比较决定所有维度**。`a.key < b.key` 一次 u64 比较,等价于比较 4 个字段。

**2. 高位优先**。高位是 layer(最粗粒度),中位是 texture(批量绘制),低位是 depth(精细排序)。排序后,同一 layer + texture 的元素连续,depth 顺序正确。

**3. 性能极致**。u64 排序用 radix sort,8 个 byte pass,极快。

### 10.2 各字段的语义

**Layer**(8 bit):UI / World / Background / Debug。不同 layer 物理上不重叠,绘制顺序固定。

**Texture**(16 bit):材质 ID。同 texture 的元素 batch 绘制,减少 GPU state switch。

**Depth**(24 bit):深度。同 layer 内,远的先画(painter's algorithm)。

**Flags**(16 bit):透明 / 不透明、blend mode、shader ID。

### 10.3 casey 在 day230 的精化

day229 是初步设计,day230 casey 精化字段位数和顺序:

- layer 从 8 bit 改为 4 bit(够用)
- texture 改为 24 bit(更多材质)
- depth 改为 32 bit(更精确)

精化动机:**真实游戏场景的数据规模**。casey 在 day230 实测发现 8 bit texture 不够(超过 256 个材质),需要扩到 24 bit。

### 10.4 排序算法的选择

sort key 是 u64,N 个元素排序:

- **std sort (pdqsort)**:O(n log n),通用,但常数大
- **radix sort**:O(8n) = O(n),整数 key 最快
- **counting sort**:O(n+k),k 是 key 范围,小 k 时最快

casey 在 day234 实现自己的 radix sort,排序 10000 个元素比 std sort 快 5-10 倍。

### 10.5 GPU 渲染管线的对应

sort key 编码对应 GPU 渲染的 batching:

- 同 texture 的元素,连续 draw call,GPU 用同一个 shader + 同一个 texture binding
- 一次 texture binding ~1μs,批量 100 个元素节省 100μs
- 10000 个元素,如果不 batch,texture switch 浪费 10ms

casey 的 sort key 是 GPU 渲染优化的 CPU 侧基础。GPU 不知道哪些元素应该 batch,需要 CPU 先排好序。

### 10.6 排序的稳定性

sort key 排序后,同 key 的元素相对顺序保留?这取决于排序算法的**稳定性**(stability)。

- 稳定排序(radix LSD、merge sort、pdqsort with stable):保留同 key 的原始顺序
- 不稳定排序(quick sort、heap sort):同 key 的顺序可能变

casey 在 day233 讨论"merge sort 能不能原地稳定"。结论:可以,但代码复杂。

游戏渲染里,稳定性重要吗?

**对透明物体**:重要!透明物体必须按 depth 精确排序,同 depth 的相对顺序影响视觉。

**对不透明物体**:不重要。GPU 用 depth buffer,谁先画都行(z-test 决定)。

casey 设计:**不透明 batch + 透明物体精确排序**。这是工业级渲染的标准做法。

### 10.7 sort key 的演化

casey 在 day229-234 逐步精化:

- **day229**:首次引入,粗略设计
- **day230**:精化位数,适应实际数据规模
- **day231**:理论铺垫(大 O)
- **day232**:具体排序算法示例
- **day233**:merge sort 能否原地
- **day234**:实现 radix sort,O(n) 排序

这是 casey 教学的"渐进式深化"——一个概念花 6 集讲完,从设计到实现到优化。

### 10.8 工业级渲染排序:Unreal 的 mesh draw command

Unreal Engine 5 的渲染管线:

```
1. 收集所有可见 mesh
2. 计算 sort key(layer + material + depth + flags)
3. 排序(stable sort)
4. 同 material 的 mesh batch 成 mesh draw command
5. GPU 执行 draw command
```

casey 的 HH 简化版本,概念上完全一样。学完 day229-234,你看 Unreal 的 `FMeshDrawCommand` 系统不再陌生。

## 11 · sort key 在不同引擎的对照

sort key 思想在所有渲染引擎都存在,只是叫法不同。

### 11.1 Unity 的 SRP Batcher

Unity 的 Scriptable Render Pipeline(SRP)有 SRP Batcher:

```
1. 收集所有 renderer
2. 按 material 分组
3. 同 material 的 renderer batch,共享 shader uniform
4. GPU 渲染 batch
```

本质就是 sort key 的 "texture/material" 字段。Unity 不暴露完整 sort key API,但内部逻辑一致。

### 11.2 Unreal 的 Drawing Policy

Unreal 用 "Drawing Policy" 概念,每个 policy 是一组(layer + material + shader):

```cpp
class FDrawingPolicy {
    FMaterial* Material;
    FShaderPipeline* Pipeline;
    ERenderPass Pass;
};

// 排序时按 policy hash
```

类似 casey 的 sort key,policy 是更高层抽象。

### 11.3 Bevy 的 render phase

Bevy 的 render phase 把 entity 按 phase 排序:

```rust
struct RenderPhase<I: PhaseItem> {
    items: Vec<I>,
}

trait PhaseItem: Ord {  // 排序
    fn sort_key(&self) -> u64;
}
```

casey 的 sort key 思想在 Bevy 是 `PhaseItem::sort_key()` 方法。完全对应。

### 11.4 GPU driven rendering

现代 GPU 渲染完全在 GPU 上排序(compute shader)。CPU 不再排序,只提供原始数据:

```
1. CPU 上传所有 entity data 到 GPU
2. GPU compute shader:计算 sort key + radix sort
3. GPU compute shader:间接 draw call
4. GPU 直接渲染
```

CPU 侧 0 工作,所有排序在 GPU 上。casey 在 day229 用 CPU 排序,后续如果要 GPU driven,概念完全相同。

### 11.5 工业教训

day229 的工程教训:

1. **排序是 GPU 渲染核心**:CPU 必须把数据排好,GPU 才能高效 batch
2. **sort key 编码多维**:单 u64 容纳所有排序字段
3. **算法选择重要**:radix sort 比 std sort 快 5-10x
4. **稳定性**:透明物体必需
5. **演化路径**:CPU sort → GPU indirect → GPU driven

casey 的 day229 是这条演化路径的起点。学完后,你能看懂任何现代渲染引擎的排序系统。

### 11.6 casey 风格的简洁

casey 设计 sort key 时,只用一个 u64,不引入复杂结构:

```rust
struct SortKey(u64);

impl SortKey {
    fn new(layer: u8, texture: u16, depth: u32, flags: u16) -> Self {
        let mut k: u64 = 0;
        k |= (layer as u64) << 56;
        k |= (texture as u64) << 40;
        k |= (depth as u64) << 8;
        k |= flags as u64;
        SortKey(k)
    }
}
```

简洁、明确、易理解。casey 不引入 SortKeyBuilder、SortKeySpec 等抽象,直接 bit 操作。

这种简洁是 casey 教学的核心——**让学生看到本质**。Unity / Unreal 隐藏在多层抽象下,casey 直接给本质代码。

学完 day229-234,你拥有从零写 GPU 渲染排序系统的能力。这是 casey HH 教学最有价值的部分之一。

### 11.7 实战:用 Rust 实现 casey 的 sort key

完整的 Rust sort key 实现:

```rust
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
struct SortKey(u64);

impl SortKey {
    const LAYER_SHIFT: u32 = 56;
    const TEXTURE_SHIFT: u32 = 40;
    const DEPTH_SHIFT: u32 = 8;
    const FLAGS_SHIFT: u32 = 0;
    
    const LAYER_MASK: u64 = 0xFF;
    const TEXTURE_MASK: u64 = 0xFFFF;
    const DEPTH_MASK: u64 = 0xFFFFFF;
    const FLAGS_MASK: u64 = 0xFFFF;
    
    fn new(layer: u8, texture: u16, depth: u32, flags: u16) -> Self {
        let k = ((layer as u64) << Self::LAYER_SHIFT)
              | ((texture as u64) << Self::TEXTURE_SHIFT)
              | ((depth as u64) << Self::DEPTH_SHIFT)
              | ((flags as u64) << Self::FLAGS_SHIFT);
        SortKey(k)
    }
    
    fn layer(&self) -> u8 {
        ((self.0 >> Self::LAYER_SHIFT) & Self::LAYER_MASK) as u8
    }
    
    fn texture(&self) -> u16 {
        ((self.0 >> Self::TEXTURE_SHIFT) & Self::TEXTURE_MASK) as u16
    }
    
    fn depth(&self) -> u32 {
        ((self.0 >> Self::DEPTH_SHIFT) & Self::DEPTH_MASK) as u32
    }
}

fn sort_renderables(items: &mut [(SortKey, RenderableId)]) {
    // 用 std sort 或 radix sort(day234)
    items.sort_by_key(|(k, _)| *k);
}
```

位编码 + derive Ord,sort 时直接比较 u64,极快。

### 11.8 sort key 的 trade-off

casey 的 sort key 不是银弹:

**优点**:
- 单 u64 比较极快
- radix sort 适用,O(n)
- 编码灵活

**缺点**:
- 位数有限(64 bit),复杂场景可能不够
- 字段顺序固定,改字段要重新设计
- debug 不直观(u64 数值难读)

**改进方向**:
- 多 u64(128 bit key),支持更多字段
- 运行时配置字段顺序(灵活性 vs 性能 trade-off)
- Debug 工具:format sort key 为字段元组(casey 在 debug UI 加这个)

casey 的 HH 用 64 bit,够用。商业引擎可能用 128 bit 或多字段 struct。

### 11.9 性能 profile

sort 10000 个 renderable 的实测:

```
算法                    时间           倍数
bubble sort            200ms         1000x(烂)
insertion sort         5ms           25x
quick sort             800μs         4x
merge sort             900μs         4.5x
pdqsort (std sort)     400μs         2x
radix sort (day234)    200μs         1x (最快)
```

radix sort 比 pdqsort 快 2 倍,比 bubble 快 1000 倍。casey 在 day234 实现 radix 后,渲染排序几乎免费。

### 11.12 排序的副作用:稳定性

casey 在 day229 提到"排序后渲染顺序",但没展开稳定性。让我们补上。

**问题**:两个透明物体 depth 完全相同,谁先画?

- 稳定排序:输入顺序保留。先添加的先画。
- 不稳定排序:可能交换。视觉上偶尔闪烁。

casey 的选择:**用稳定排序**(merge sort 或 radix LSD)。或者用次级 sort key(depth 相同时,加 entity ID 做次级 key,保证全序)。

```rust
// 全序 sort key:加 entity ID 作为 tie-breaker
fn make_key(layer, texture, depth, entity_id) -> u128 {
    let primary: u64 = encode(layer, texture, depth, flags);
    let secondary: u64 = entity_id;
    ((primary as u128) << 64) | (secondary as u128)
}
```

u128 sort key,完全消除"相同 primary key"的情况。casey 不展开,但工业级实现要考虑。

### 11.13 sort key 的 debug 可读性

u64 sort key 不直观。casey 在 debug UI 加 formatter:

```rust
impl std::fmt::Debug for SortKey {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        write!(f, "SortKey(layer={}, tex={}, depth={}, flags={})",
            self.layer(), self.texture(), self.depth(), self.flags())
    }
}
```

debug print 显示字段名,不是 raw u64。这是工程化的小细节,但极大提升 debug 效率。

### 11.14 工业教训

1. **bit 编码威力大**:多字段压成单 u64,排序变成单次比较

3. **算法选择影响性能**:radix 比 std 快 5-10x

5. **debug 可读性不能忽略**:u64 数字难读,加 formatter
