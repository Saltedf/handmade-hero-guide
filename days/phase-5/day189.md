# Day 189 · 增量调试帧处理

> 之前每帧结束都"全部 collate"——把整帧 event 排序、配对、聚合。但 event 流是连续的,其实可以**增量**处理:每来一条 event 立即更新统计,不等帧结束。今天 Casey 把 collation 改成增量算法。

## 0 · 为什么要有这一天

Day 184-185 的 collation 是**批处理**:每帧结束扫一遍所有 event,O(N) 一次。10 万 event / 帧 = 10 万次扫描。

实际上每条 event 来时就能做大部分工作:
- begin event 入栈
- end event 出栈,算 duration,**立即**累加到 SpanStats

这种"事件驱动"的增量算法**摊销到每条 event**,O(1)/event,O(N)/帧 没变但常数小。更重要的是:**可以在 frame_end 之前就显示部分统计**(live profiler)。

今天 Casey 改成增量:

1. event push 时,直接更新当前帧的 FrameSummary(不用等帧结束)
2. frame_end 只做收尾(flush pending stack、推 ring buffer)
3. UI 渲染时,看的是"当前累积 + 上 N 帧历史"

心理锚点:看完今天,你能区分"批处理"和"增量处理"两种数据流模式。

## 1 · Casey 今天做了什么

Casey 重构 collation:

1. push_event 时,直接调 collator.on_event(e)
2. on_event 做:begin 入栈 / end 弹栈 + 累加 stats
3. frame_end 调 collator.finalize(),把当前 FrameSummary 推 ring buffer,重置

代码量减少(没单独 collation pass),性能提升(常数小)。

## 2 · 心智模型

### 类比:餐厅结账

**批处理**:客人吃完,服务员拿全部订单去算账,一次性算总价。
**增量**:客人每点一道菜,服务员立刻加到总价。结账时总价已经在,不用重算。

增量算法的好处:**实时反馈**——客人随便什么时候问"现在多少钱",服务员立刻答。

profiler 一样:**实时统计**——UI 在帧中任何时刻都能看到当前累积。

### 2.1 增量 collation 算法

```rust
pub struct IncrementalCollator {
    current_frame: FrameSummary,
    open_stack: Vec<(u64, u64)>,  // (guid, begin_cycle)
}

impl IncrementalCollator {
    pub fn new() -> Self {
        Self {
            current_frame: FrameSummary::default(),
            open_stack: Vec::new(),
        }
    }

    pub fn on_event(&mut self, e: &Event) {
        match e.kind {
            Kind::Begin => {
                if e.guid == MARKER_FRAME_BEGIN {
                    self.current_frame = FrameSummary::default();
                    self.current_frame.frame_index = e.payload;
                    return;
                }
                self.open_stack.push((e.guid, e.cycle));
            }
            Kind::End => {
                if e.guid == MARKER_FRAME_END {
                    return;  // finalize 会处理
                }
                if let Some((guid, begin)) = self.open_stack.pop() {
                    if guid == e.guid {
                        let dur = e.cycle - begin;
                        let s = self.current_frame.stats.entry(guid).or_default();
                        s.count += 1;
                        s.total_cycles += dur;
                        s.max_cycles = s.max_cycles.max(dur);
                    }
                }
            }
        }
    }

    pub fn finalize(&mut self, end_cycle: u64) -> FrameSummary {
        let mut summary = std::mem::take(&mut self.current_frame);
        summary.end_cycle = end_cycle;
        summary.total_cycles = summary.stats.values().map(|s| s.total_cycles).sum();
        summary
    }
}
```

**Rust 注释**:
- `std::mem::take(&mut self.current_frame)` — 把字段移出来,原字段变 Default。O(1),不 clone
- `entry(guid).or_default()` — HashMap entry API,不存在时插默认值

### 2.2 集成到 profiler

```rust
pub struct Profiler {
    collator: IncrementalCollator,
    history: RingBuffer<FrameSummary, 300>,
    current_frame_index: u64,
}

impl Profiler {
    pub fn push(&mut self, e: Event) {
        self.collator.on_event(&e);
    }

    pub fn end_frame(&mut self) {
        let summary = self.collator.finalize(rdtsc());
        self.history.push(summary);
        self.current_frame_index += 1;
    }
}
```

每条 event 来了立刻处理,frame_end 只做 finalize + push。

### 2.4 增量算法的内存优势

批处理需要 buffer 整帧 event:

```
event 1, 2, 3, ..., 10000 → Vec<Event> (160 KB)
                              ↓
                          collate O(N)
                              ↓
                          FrameSummary
```

增量算法**不 buffer event**,直接累加:

```
event 1 → update stats
event 2 → update stats
...
event 10000 → update stats
            ↓
        FrameSummary
```

**内存对比**:
- 批处理:每帧 160 KB event buffer + FrameSummary
- 增量:只 FrameSummary(~10 KB),不需要 event buffer

对内存敏感的设备(嵌入式、移动)增量算法意义重大。Casey 在 PC 上跑,差异不大,但**设计哲学值得学**。

### 2.5 增量算法的失效场景

不是所有问题都能增量。**中位数**(median)是经典反例:

- 批处理:`sort(xs); median = xs[n/2]` 简单
- 增量:必须维护 "全部数据" 才能算中位数,不可能真增量

近似算法:**Two-Heaps**(max-heap + min-heap)维护中位数,但仍要存全部数据。**t-digest** 是流式近似分位数,牺牲精度换内存。

profiler 的 max / avg / count 都能真增量。如果加 P99 分位数,要 t-digest 或类似算法。

### 2.6 streaming 系统的设计模式

profiler 的增量 collation 是 streaming 系统的微缩版。工业 streaming(Kafka / Flink / Spark Streaming)的核心模式:

1. **event-at-a-time**:每条 event 立即处理
2. **stateful**:维护跨 event 状态(FrameSummary)
3. **windowing**:按时间 / 数量切分窗口(frame marker)
4. **watermark**:处理乱序 event(我们假设 TSC 同步)
5. **exactly-once**:保证不丢不重(我们的 event push 可能丢,但接受)

Casey 的设计包含 1-3,不含 4-5(简化)。学习时,把 profiler 看成"流处理系统"的入门例子,后面看 Kafka 等会豁然开朗。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏里增量算法的例子:
- 物理引擎:每帧增量更新位置(不是每帧重算整个轨迹)
- 网络:delta compression(只发变化)
- 渲染:dirty rectangle(只画变化区域)
- profiler:增量 collation

### 3.2 · Rust 生态视角

Rust 流处理 crate:
- `futures::stream` — async 流
- `rxRust` — Rx 风格
- 自己手写 iterator chain — 最简单

profiler 不需要 async,手写 on_event 函数够。

### 3.3 · 🐧 Linux 系统编程视角(Kafka / Flink 的设计)

工业 streaming 系统(Kafka / Flink)处理 TB/秒数据,设计原则:

- **partition**:数据按 key 分区,每区独立 collator
- **checkpoint**:定期持久化 state,故障恢复
- **exactly-once**:用两阶段提交保证不重不丢
- **watermark**:处理乱序 event(网络延迟)

profiler 是单机版流处理,event 数据量小(G/s vs TB/s),但**模式相同**。学完 profiler,理解 Kafka 的 consumer group / partition 就更容易——都是"分布式版的 on_event"。

### 3.4 · 🎮 游戏编程视角(ECS 的 archetype change)

Bevy ECS 的 archetype 变化是增量算法的另一例:

- 传统:每帧扫所有 entity 查询
- Bevy:entity 加 / 删组件时,**增量更新** archetype 内部存储

Bevy 的 query 是 O(N_components),不是 O(N_entities)。这是 ECS 比 traditional OOP 快的核心。Casey 的 profiler 不用 ECS(简化),但**思路同源**——把 O(N) 操作摊销到事件,降低常数。

### 3.5 · 🎨 图形学视角(dirty rectangle)

游戏渲染的 dirty rectangle 是增量算法:

- 传统:每帧重画整个屏幕,O(屏幕像素)
- dirty rect:只画变化的矩形,O(变化像素)

老游戏(2D 横版)用 dirty rect 优化——只画角色移动的几块,其他保持。3D 游戏因为相机每帧转,整个屏幕都变,不用 dirty rect。但 UI 用 dirty rect(Wayland 的 damage tracking)。

profiler 增量 collation 也是"只更新变化的部分",避免全扫。

## 5 · 对照与变奏

**Online algorithm 的经典例子**:

- **均值**:增量 = `avg = avg + (x - avg) / n`,批处理 = `sum(xs) / n`
- **方差**:增量 = Welford's algorithm
- **中位数**:难(要存全部数据),Two-Heaps 算法
- **分位数**:t-digest(近似)

profiler 的 SpanStats 都能用 online 算法。

### Welford 方差的增量算法

方差(variance)的传统算法:`var = sum((x_i - mean)^2) / n`。两遍扫描:第一遍算 mean,第二遍算 sum of squares。**数值不稳定**(大数据集时 sum of squares 巨大,精度丢)。

Welford 1962 年发明一遍扫描的稳定算法:

```
n = 0, mean = 0, M2 = 0
for x in stream:
    n += 1
    delta = x - mean
    mean += delta / n
    delta2 = x - mean
    M2 += delta * delta2
variance = M2 / n
```

**核心洞察**:不存 sum of squares,存 M2(每步的"累积平方差")。每步用 mean 增量更新,数值稳定。

profiler 算"cycle 的标准差"用 Welford。这能告诉你"这个函数耗时波动多大"——比 max - min 更精确。Casey 后期 day 200+ 加这个统计。

### Online 算法的工业应用

- **ClickHouse**:列式数据库,online aggregation
- **Flink**:流式 SQL,处理 Kafka 流
- **Redis**:HyperLogLog 算 cardinality(online)
- **t-digest**:流式 P99 等分位数
- **Bloom filter**:流式 membership 测试

每个都是"小内存处理大数据"的范例。profiler 的 FrameSummary 也是这种思路——固定内存,无限 event。

### Lv1 · 概念辨析

**题**:增量算法的优势是"快"吗?

**参考解答**:

- 常数略小(少一次完整扫描)

### Lv2 · 动手实践

**题**:实现 IncrementalCollator,要求:
- on_event 处理 begin/end
- finalize 返回 FrameSummary
- main 模拟 3 帧,每帧 5 个 span,验证 stats 正确

**参考解答**:

```rust
use std::collections::HashMap;

#[derive(Clone, Copy, Debug)]
enum Kind { Begin, End }

#[derive(Clone, Copy, Debug)]
struct Event { cycle: u64, guid: u64, kind: Kind, payload: u64 }

const MARKER_BEGIN: u64 = u64::MAX - 1;
const MARKER_END: u64 = u64::MAX - 2;

#[derive(Clone, Debug, Default)]
struct SpanStats { count: u32, total_cycles: u64, max_cycles: u64 }

#[derive(Clone, Debug, Default)]
struct FrameSummary {
    frame_index: u64,
    total_cycles: u64,
    stats: HashMap<u64, SpanStats>,
}

struct IncrementalCollator {
    current_frame: FrameSummary,
    open_stack: Vec<(u64, u64)>,
}

impl IncrementalCollator {
    fn new() -> Self { Self { current_frame: FrameSummary::default(), open_stack: Vec::new() } }

    fn on_event(&mut self, e: &Event) {
        match e.kind {
            Kind::Begin => {
                if e.guid == MARKER_BEGIN {
                    self.current_frame = FrameSummary::default();
                    self.current_frame.frame_index = e.payload;
                    return;
                }
                self.open_stack.push((e.guid, e.cycle));
            }
            Kind::End => {
                if e.guid == MARKER_END { return; }
                if let Some((guid, begin)) = self.open_stack.pop() {
                    if guid == e.guid {
                        let dur = e.cycle - begin;
                        let s = self.current_frame.stats.entry(guid).or_default();
                        s.count += 1;
                        s.total_cycles += dur;
                        s.max_cycles = s.max_cycles.max(dur);
                    }
                }
            }
        }
    }

    fn finalize(&mut self) -> FrameSummary {
        std::mem::take(&mut self.current_frame)
    }
}

fn main() {
    let mut collator = IncrementalCollator::new();
    let mut cycle = 0u64;

    for frame in 0..3u64 {
        collator.on_event(&Event { cycle, guid: MARKER_BEGIN, kind: Kind::Begin, payload: frame });
        cycle += 10;

        for guid in 1..=3u64 {
            collator.on_event(&Event { cycle, guid, kind: Kind::Begin, payload: 0 });
            cycle += 50 + guid * 10;
            collator.on_event(&Event { cycle, guid, kind: Kind::End, payload: 0 });
            cycle += 5;
        }

        collator.on_event(&Event { cycle, guid: MARKER_END, kind: Kind::End, payload: frame });
        let summary = collator.finalize();
        println!("Frame {}: {} spans", summary.frame_index, summary.stats.len());
        for (g, s) in &summary.stats {
            println!("  guid={}: count={} total={} max={}", g, s.count, s.total_cycles, s.max_cycles);
        }
    }
}
```

### Lv3 · 迁移设计

**题**:增量算法实时更新,但**max_cycles 不对**——只有 frame_end 才知道完整 max。怎么处理?**提示**:看 `current_frame.stats` 里的 max 是否正确(应该是,每次 end 都更新)。

**额外提示**:
- 实际上 max 在每次 end event 时就更新了,所以 max_cycles 在 frame 中部就准
- 但**平均**(avg = total / count)随着 count 增加变化,frame 中部的 avg 不代表最终 avg
- **更难的问题**:跨帧的 P99 怎么算?如果每帧只记 max / avg,P99 信息丢失
- 解决:保留最近 N 帧的全部 max / avg,从中算 P99
- **进阶**:t-digest 流式 P99 算法,固定内存近似

**Troubleshooting**:

- finalize 后 current_frame 没 reset — `std::mem::take` 自动 reset 成 Default
- 同 guid 多次 begin — 检查代码,可能漏 push stack
- **stats 在帧中没更新** — 检查 `on_event` 是否真的被 push_event 调用,可能 buffer 在某处
- **HashMap 突然变大** — 多线程同时 push,要加锁或用 thread_local
- **finalize 返回的 stats.count = 0** — on_event 没处理这条 event,检查 MARKER 过滤逻辑
