
# Day 189 · 增量调试帧处理

> 之前 profiler 的 collation 是"批处理"——每帧结束,你扫一遍整帧所有 event(begin / end 配对、算 duration、累加到统计)。10 万 event 一帧,你扫 10 万次。看起来 O(N) 没毛病——但 Casey 发现一个尴尬的事:渲染 debug overlay 时,**你想看"当前这帧"的统计**,可这帧还没结束、collation 还没跑,UI 显示的是上一帧的旧数据。今天 Casey 把 collation 改成**增量**——每条 event 来时立即更新统计,不等帧结束。代码量减少、常数变小,而且 UI 能实时显示"这帧已累积"的部分统计。这是把"批处理思维"转成"流处理思维"——计算机科学里的经典话题。

## 0 · 为什么要有这一天

让我把镜头拉近,真实地体验"批处理 vs 增量"的取舍。

你跟着 Day 184-188 做了 profiler 后端。每帧的 event 流是这样:

```
[FRAME_START]
  [UPDATE_BEGIN]
    [PHYSICS_BEGIN] ... [PHYSICS_END]    (200μs)
    [AI_BEGIN] ... [AI_END]               (150μs)
    [ANIM_BEGIN] ... [ANIM_END]           (50μs)
  [UPDATE_END]                            (500μs)
  [RENDER_BEGIN]
    [SHADOW_BEGIN] ... [SHADOW_END]       (300μs)
    [GEOMETRY_BEGIN] ... [GEOMETRY_END]   (4000μs)
    [UI_BEGIN] ... [UI_END]               (200μs)
  [RENDER_END]                            (4600μs)
[FRAME_END]                               (5200μs)
```

10 万条 event 一帧(大游戏真实数字)。每帧结束,你的 collation pass 做这些:

1. **遍历 event 列表**,按 GUID 分组(begin 配 end)
2. **算每个 span 的 duration**(end_timestamp - begin_timestamp)
3. **累加到 `SpanStats`**:`stats[guid].total_cycles += duration`
4. **维护调用计数**:`stats[guid].call_count += 1`
5. **算 min / max / 平均**

这个 collation pass 跑 10 万次 / 帧的循环,每次几十纳秒,总共几毫秒。看起来不大,但每帧都跑——144 FPS 下,1 秒里 144 × 几毫秒 = 几百毫秒花在 collation 上。这是 **10-20% 的 frame budget 被 collation 吃掉**。

更糟糕的是**实时性问题**。UI 想显示"当前这帧的更新进度",但 collation 在 frame_end 后才跑——UI 看到的是**上一帧**的统计。你 frame 100 看到的数据,实际是 frame 99 的。低帧率时(掉到 30 FPS),延迟 33ms——你能感觉到 UI 数据"慢半拍"。

工业 profiler(Tracy、OPTICK、Superluminal)用**增量 collation** 解决这个问题。每条 event push 时,collator 立即处理——begin 入栈、end 弹栈 + 算 duration + 累加 stats。**不等到 frame_end**。这样:

1. **CPU 开销摊薄**——每条 event 几纳秒,分散到 event 产生的时刻,frame_end 没有突发工作
2. **实时性好**——UI 随时可读 `current_frame_summary`,看到"这帧已累积 5ms"
3. **代码简化**——不再有单独 collation pass,push_event 直接调 on_event

增量 vs 批处理是计算机科学的经典话题。两个例子:

**数据库**。SQLite 批处理:你 `BEGIN TRANSACTION; INSERT × 10000; COMMIT;`,所有写一次性 flush 到磁盘,快。增量:你每条 INSERT 立即 flush,慢 100 倍——但**实时可见**(其他连接能立即读到)。SQLite 实际用 WAL(write-ahead log)做混合——增量写 log,定期 checkpoint 批处理。

**编译器**。批处理编译:`rustc main.rs`,一次性编译完。增量编译:`cargo check`,只编译改动部分。Rust 的 incremental compilation 让重复 build 从 30 秒降到 3 秒,这是 Rust 开发体验的关键。

**profiler 的增量 collation**。Casey HH day 189 把 collation 改成增量,event push 时直接更新 FrameSummary。这带来三个具体好处:

第一,**frame_end 不再是性能瓶颈**。frame_end 只做"finalize"——把累积的 FrameSummary push 进 ring buffer、重置 counters。这个 finalize 是 O(span count) 不是 O(event count),通常快 10-100 倍(span 数 << event 数)。

第二,**UI 实时显示**。UI 在 frame 任意时刻可读 current_frame_summary,看到"这帧已经累积 5000μs in UPDATE,1500μs in RENDER"。这对调试卡顿特别有用——你能在卡顿发生时立即看到"哪个 span 慢",不用等下一帧。

第三,**代码简化**。原来的代码有两套逻辑——event 收集(push_event 写 ring buffer)+ collation(读 ring buffer 算 stats)。改成增量后,合并成一套——push_event 直接更新 stats。**少 200 行代码,功能不变**。

但增量也有代价:**无法做"跨 event 的全局优化"**。批处理可以预先看所有 event 再决策(比如排序后处理,缓存友好);增量只能顺序处理,每条 event 单独决策。如果事件之间有强关联(比如"按 timestamp 排序后才能配对"),增量算法不适用。Casey HH 的 event 流是按时间顺序产生的,天然有序,所以增量可行。

**学完今天,你应该能**:
- 解释"批处理"和"增量处理"两种数据流模式的取舍
- 把"批处理 collation"重构成"增量 collation",保持等价语义
- 理解数据库 WAL、增量编译、流处理(Kafka)都是同一思想的工业应用
- 看自己的 profiler 代码,识别哪些 pass 可以增量、哪些必须批处理
- 解释为什么 immediate-mode UI 和增量 profiler 天生契合(都是"事件驱动")

## 1 · Casey 今天做了什么

Casey 这一天重构了 collation。让我把工作拆开:

1. **去掉 collation pass**。原来 frame_end 跑 collation,遍历 event 列表算 stats。Casey 删掉这个 pass。

2. **加 on_event handler**。在 event push 时直接调 `collator.on_event(&event)`,立即处理。

3. **on_event 的逻辑**:
   - `Event::Begin { guid, timestamp }`:push 到 `pending_stack`(`Vec<(guid, start_ts)>`)
   - `Event::End { guid, timestamp }`:pop `pending_stack`(检查 guid 匹配),算 duration,累加到 `current_frame_summary.stats[guid]`
   - `Event::FrameEnd`:调 `finalize()`,把 `current_frame_summary` 推 `ring_buffer`,重置 `current_frame_summary`

4. **UI 读 current_frame_summary**。原来的 UI 只能读 ring buffer(已完成帧),现在可以读 `current_frame_summary`——"当前这帧已累积"。

5. **验证性能**。Casey 在视频里展示 profiler overhead 从 ~3ms / 帧降到 ~0.5ms / 帧。**节省 2.5ms / 帧,30 FPS 游戏就是 7.5% frame budget**——这是程序员的时间红利。

6. **验证实时性**。Casey 在 UI 加了个"current frame progress"bar,实时显示当前帧已累积的 cycle 数。观众看见 bar 从 0 增长到 frame budget 上限,直观感受 frame 进度。

这集产出代码大约 -200 行(删除多于新增),但**架构更干净**——event 收集和 collation 合二为一。

## 2 · 心智模型

### 类比:餐厅结账

**批处理**:客人吃完,服务员拿全部订单去算账,一次性算总价。
**增量**:客人每点一道菜,服务员立刻加到总价。结账时总价已经在,不用重算。

增量算法的好处:**实时反馈**——客人随便什么时候问"现在多少钱",服务员立刻答。

profiler 一样:**实时统计**——UI 在帧中任何时刻都能看到当前累积。

### 2.1 增量 collation 算法

```rust
pub struct IncrementalCollator {
    current_frame: FrameSummary,
    open_stack: Vec<(u64, u64)>,  // (guid, begin_cycle)
}

impl IncrementalCollator {
    pub fn new() -> Self {
        Self {
            current_frame: FrameSummary::default(),
            open_stack: Vec::new(),
        }
    }

    pub fn on_event(&mut self, e: &Event) {
        match e.kind {
            Kind::Begin => {
                if e.guid == MARKER_FRAME_BEGIN {
                    self.current_frame = FrameSummary::default();
                    self.current_frame.frame_index = e.payload;
                    return;
                }
                self.open_stack.push((e.guid, e.cycle));
            }
            Kind::End => {
                if e.guid == MARKER_FRAME_END {
                    return;  // finalize 会处理
                }
                if let Some((guid, begin)) = self.open_stack.pop() {
                    if guid == e.guid {
                        let dur = e.cycle - begin;
                        let s = self.current_frame.stats.entry(guid).or_default();
                        s.count += 1;
                        s.total_cycles += dur;
                        s.max_cycles = s.max_cycles.max(dur);
                    }
                }
            }
        }
    }

    pub fn finalize(&mut self, end_cycle: u64) -> FrameSummary {
        let mut summary = std::mem::take(&mut self.current_frame);
        summary.end_cycle = end_cycle;
        summary.total_cycles = summary.stats.values().map(|s| s.total_cycles).sum();
        summary
    }
}
```

**Rust 注释**:
- `std::mem::take(&mut self.current_frame)` — 把字段移出来,原字段变 Default。O(1),不 clone
- `entry(guid).or_default()` — HashMap entry API,不存在时插默认值

### 2.2 集成到 profiler

```rust
pub struct Profiler {
    collator: IncrementalCollator,
    history: RingBuffer<FrameSummary, 300>,
    current_frame_index: u64,
}

impl Profiler {
    pub fn push(&mut self, e: Event) {
        self.collator.on_event(&e);
    }

    pub fn end_frame(&mut self) {
        let summary = self.collator.finalize(rdtsc());
        self.history.push(summary);
        self.current_frame_index += 1;
    }
}
```

每条 event 来了立刻处理,frame_end 只做 finalize + push。

### 2.4 增量算法的内存优势

批处理需要 buffer 整帧 event:

```
event 1, 2, 3, ..., 10000 → Vec<Event> (160 KB)
                              ↓
                          collate O(N)
                              ↓
                          FrameSummary
```

增量算法**不 buffer event**,直接累加:

```
event 1 → update stats
event 2 → update stats
...
event 10000 → update stats
            ↓
        FrameSummary
```

**内存对比**:
- 批处理:每帧 160 KB event buffer + FrameSummary
- 增量:只 FrameSummary(~10 KB),不需要 event buffer

对内存敏感的设备(嵌入式、移动)增量算法意义重大。Casey 在 PC 上跑,差异不大,但**设计哲学值得学**。

### 2.5 增量算法的失效场景

不是所有问题都能增量。**中位数**(median)是经典反例:

- 批处理:`sort(xs); median = xs[n/2]` 简单
- 增量:必须维护 "全部数据" 才能算中位数,不可能真增量

近似算法:**Two-Heaps**(max-heap + min-heap)维护中位数,但仍要存全部数据。**t-digest** 是流式近似分位数,牺牲精度换内存。

profiler 的 max / avg / count 都能真增量。如果加 P99 分位数,要 t-digest 或类似算法。

### 2.6 streaming 系统的设计模式

profiler 的增量 collation 是 streaming 系统的微缩版。工业 streaming(Kafka / Flink / Spark Streaming)的核心模式:

1. **event-at-a-time**:每条 event 立即处理
2. **stateful**:维护跨 event 状态(FrameSummary)
3. **windowing**:按时间 / 数量切分窗口(frame marker)
4. **watermark**:处理乱序 event(我们假设 TSC 同步)
5. **exactly-once**:保证不丢不重(我们的 event push 可能丢,但接受)

Casey 的设计包含 1-3,不含 4-5(简化)。学习时,把 profiler 看成"流处理系统"的入门例子,后面看 Kafka 等会豁然开朗。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏里增量算法的例子:
- 物理引擎:每帧增量更新位置(不是每帧重算整个轨迹)
- 网络:delta compression(只发变化)
- 渲染:dirty rectangle(只画变化区域)
- profiler:增量 collation

### 3.2 · Rust 生态视角

Rust 流处理 crate:
- `futures::stream` — async 流
- `rxRust` — Rx 风格
- 自己手写 iterator chain — 最简单

profiler 不需要 async,手写 on_event 函数够。

### 3.3 · 🐧 Linux 系统编程视角(Kafka / Flink 的设计)

工业 streaming 系统(Kafka / Flink)处理 TB/秒数据,设计原则:

- **partition**:数据按 key 分区,每区独立 collator
- **checkpoint**:定期持久化 state,故障恢复
- **exactly-once**:用两阶段提交保证不重不丢
- **watermark**:处理乱序 event(网络延迟)

profiler 是单机版流处理,event 数据量小(G/s vs TB/s),但**模式相同**。学完 profiler,理解 Kafka 的 consumer group / partition 就更容易——都是"分布式版的 on_event"。

### 3.4 · 🎮 游戏编程视角(ECS 的 archetype change)

Bevy ECS 的 archetype 变化是增量算法的另一例:

- 传统:每帧扫所有 entity 查询
- Bevy:entity 加 / 删组件时,**增量更新** archetype 内部存储

Bevy 的 query 是 O(N_components),不是 O(N_entities)。这是 ECS 比 traditional OOP 快的核心。Casey 的 profiler 不用 ECS(简化),但**思路同源**——把 O(N) 操作摊销到事件,降低常数。

### 3.5 · 🎨 图形学视角(dirty rectangle)

游戏渲染的 dirty rectangle 是增量算法:

- 传统:每帧重画整个屏幕,O(屏幕像素)
- dirty rect:只画变化的矩形,O(变化像素)

老游戏(2D 横版)用 dirty rect 优化——只画角色移动的几块,其他保持。3D 游戏因为相机每帧转,整个屏幕都变,不用 dirty rect。但 UI 用 dirty rect(Wayland 的 damage tracking)。

profiler 增量 collation 也是"只更新变化的部分",避免全扫。


### 3.6 · 🐧 Linux 系统编程视角(perf / ftrace / eBPF)

Linux 内核自带一整套 profiling 基础设施,工业 Linux 性能分析的所有工具都基于它。理解这套设施能让你看 Casey 的 profiler 处于什么位置。

**perf** 是 Linux 内核的标准 profiling 接口。`perf record ./my_game` 跑游戏,perf 通过 `perf_event_open(2)` 系统调用,让内核每隔 N 个 CPU cycle 采样一次指令指针(IP)。采到 N 万个样本后,`perf report` 显示每个函数被采到多少次——按比例还原 CPU 时间分布。这是**统计 sampling**——不记录每次调用,而是按概率采样。

```bash
# 在 Arch 上跑 perf(需要内核 CONFIG_PERF_EVENTS=y,默认开)
sudo pacman -S perf
sudo perf record ./target/release/my_game
sudo perf report --stdio | head -30
# 输出形如:
#   35.00%  my_game  my_game         [.] update_physics
#   18.00%  my_game  my_game         [.] render_geometry
#    8.00%  my_game  libc-2.31.so    [.] memcpy
```

**perf 的两种模式**:
- **Sample-based**:每 N cycle 采样,适合找 hot spot。优点开销小(1% CPU),缺点错过短函数。
- **Trace-based**:每次事件都记录,精确。Casey HH 的 profiler 是 trace-based——每条 begin/end event 都记,精确度高但开销大(~5% CPU)。

**ftrace** 是内核函数级 trace。`/sys/kernel/debug/tracing/` 暴露 trace 点:

```bash
# 启用 sched_switch trace
echo sched_switch > /sys/kernel/debug/tracing/set_event
echo 1 > /sys/kernel/debug/tracing/tracing_on
# 等几秒
cat /sys/kernel/debug/tracing/trace | head
# 看每个 context switch
```

ftrace 是内核 hook——你 enable `sched_switch`,内核每次 context switch 都写一条记录到 ring buffer。这就是 Casey HH profiler 的"内核版"——同样的 ring buffer 数据结构,同样的"事件流"思维。

**eBPF** 是 Linux 内核的革命性技术。eBPF 让你在内核运行安全的 bytecode,自定义 profiling / monitoring 逻辑。eBPF 程序用 C 子集写,编译成 BPF bytecode,加载到内核 hook 点(系统调用、网络包、trace point)。这是内核版"插件"——比 ftrace 灵活,比内核模块安全。

```bash
# 用 bpftrace 做 profiling
sudo pacman -S bpftrace
sudo bpftrace -e 'profile:hz:99 @[stack] = count();'
# 每秒采样 99 次,记录 call stack
```

**bpftrace** 一个脚本 = 一个 profiler。你可以一分钟内写"统计 malloc 调用"、"看哪个进程 IO 最多"、"找 page fault 来源"——这是 Linux 性能分析的现代化武器。

**/proc/[pid]/stat / status / maps** 暴露进程运行时状态:

```bash
# 看你当前进程的 stat(进程的运行时统计)
cat /proc/$$/stat
# 第 14 字段:utime(user CPU time)
# 第 15 字段:stime(kernel CPU time)

# 看 memory mapping
cat /proc/$$/maps
# 输出:地址范围 权限 偏移 设备 inode 文件名
```

工业 profiler 读这些文件得到 cross-process 信息。Casey HH 的 profiler 是 in-process 的(只看自己),不读 /proc——这简化了实现,但看不到 OS 视角。

**Tracy / OPTICK / Superluminal** 是工业 C++ profiler,都用类似架构:ring buffer + thread-local + sample/trace 混合。Tracy 是开源,有 WebSocket UI 跨机器查看;Superluminal 是商业,以"超低 overhead + 时间线视图"著名。Casey HH 的 profiler 简化,但**架构相同**——理解 Casey 的,你就懂了 Tracy 的核心。

### 3.7 · 🦀 Rust 生态视角

Rust 的 profiling 生态有几条主线。

**`tracing` crate** 是 Rust 应用的事实标准 logging / tracing 框架。它结合了 log(级别)和 OpenTracing(span):

```rust
use tracing::{span, info, instrument};

#[instrument]
fn update_physics(dt: f32) {
    // tracing 自动在函数 entry/exit 创建 span
    info!(dt, "physics step");
}

let _span = span!(tracing::Level::INFO, "frame").entered();
update_physics(0.016);
```

`#[instrument]` 是 derive macro——编译时生成 span 创建/退出代码。`tracing` 的 subscriber 决定如何处理 span——log 到文件、发到 tracing UI、profile 等。

**`tracing-tracy`** crate 把 tracing span 转成 Tracy 协议事件。你的 Rust 应用加 tracing + tracing-tracy,就能用 Tracy UI 看 profile。这是 Rust 生态接工业 profiler 的标准方式。

**`puffin`** 是 Rust-native profiler,immediate-mode UI 风格,专为游戏设计:

```rust
puffin::profile_scope!("physics");
update_physics(dt);
// 自动 entry/exit

// 在 egui UI 里
puffin_egui::profiler_window(egui_ctx);
```

puffin 的设计哲学和 Casey HH profiler 几乎一致——in-process、ring buffer、immediate-mode UI。Puffin 是开源,代码可读,是看"Rust 风格 profiler"的范本。

**`measureme`** 是 rustc 用的 profiler,分析 rustc 自己的编译性能。measureme 的设计原则是"低 overhead + 可序列化 + 跨工具分析"——Rust 团队用它优化 rustc。

**Rust 的 `Instant`** 是 std 提供的高精度计时器:

```rust
let start = std::time::Instant::now();
expensive_op();
let elapsed = start.elapsed();
// elapsed 是 Duration,纳秒精度
```

底层在 Linux 是 `clock_gettime(CLOCK_MONOTONIC)`,Windows 是 `QueryPerformanceCounter`,macOS 是 `mach_absolute_time`。这是跨平台高精度时间的标准答案。Casey HH 在不同平台用不同 API(Linux rdtsc、Windows QPC、macOS mach),用 Rust 应该用 `Instant` 抽象。

**Rust 的 atomic 计数**。profiler 多线程时,event push 可能从多个线程同时来。用 `Arc<Mutex<Profiler>`> 是简单方案,但有锁开销。Rust 的 `crossbeam-queue` 提供 lock-free queue,适合高并发 event push。或者用 thread-local buffer + 定期 flush,完全无锁。Tracy 用 thread-local buffer,每线程独立,profiler thread 用 lock-free merge 合并。

**Rust SIMD** 可以加速 collation。如果有 100 万 event 要 collate,用 SIMD(`std::simd` 或 `wide` crate)一次处理 4-8 条 event,duration 计算用 SIMD 减法 + 累加。Tracy 在 collation hot loop 用 AVX2 优化。Rust 的 SIMD 还在稳定化中(unstable `std::simd`),但 `wide` crate 提供稳定的 wrapper。

**Rust 的 `Bytes` / `Arc<[u8]>`** 让 event buffer 零拷贝共享。如果 event buffer 要被 UI thread 读取(同时被游戏 thread 写),用 `Bytes` 引用计数——读 thread 拷贝 Arc,写 thread 替换 Arc 指向新 buffer。这是 lock-free 数据交换的标准模式。

**Rust profiler 的内存安全优势**。C/C++ profiler 大量 ring buffer + 原子操作,容易写错(数据竞争、use-after-free)。Rust 的 borrow checker + Send/Sync + atomic API 让这些错误编译时被捕获。Puffin / measureme 的代码,你可以放心读——Rust 保证内存安全。

## 5 · 对照与变奏

**Online algorithm 的经典例子**:

- **均值**:增量 = `avg = avg + (x - avg) / n`,批处理 = `sum(xs) / n`
- **方差**:增量 = Welford's algorithm
- **中位数**:难(要存全部数据),Two-Heaps 算法
- **分位数**:t-digest(近似)

profiler 的 SpanStats 都能用 online 算法。

### Welford 方差的增量算法

方差(variance)的传统算法:`var = sum((x_i - mean)^2) / n`。两遍扫描:第一遍算 mean,第二遍算 sum of squares。**数值不稳定**(大数据集时 sum of squares 巨大,精度丢)。

Welford 1962 年发明一遍扫描的稳定算法:

```
n = 0, mean = 0, M2 = 0
for x in stream:
    n += 1
    delta = x - mean
    mean += delta / n
    delta2 = x - mean
    M2 += delta * delta2
variance = M2 / n
```

**核心洞察**:不存 sum of squares,存 M2(每步的"累积平方差")。每步用 mean 增量更新,数值稳定。

profiler 算"cycle 的标准差"用 Welford。这能告诉你"这个函数耗时波动多大"——比 max - min 更精确。Casey 后期 day 200+ 加这个统计。

### Online 算法的工业应用

- **ClickHouse**:列式数据库,online aggregation
- **Flink**:流式 SQL,处理 Kafka 流
- **Redis**:HyperLogLog 算 cardinality(online)
- **t-digest**:流式 P99 等分位数
- **Bloom filter**:流式 membership 测试

每个都是"小内存处理大数据"的范例。profiler 的 FrameSummary 也是这种思路——固定内存,无限 event。

### Lv2 · 动手实践

**题**:实现 IncrementalCollator,要求:
- on_event 处理 begin/end
- finalize 返回 FrameSummary
- main 模拟 3 帧,每帧 5 个 span,验证 stats 正确

**参考解答**:

```rust
use std::collections::HashMap;

#[derive(Clone, Copy, Debug)]
enum Kind { Begin, End }

#[derive(Clone, Copy, Debug)]
struct Event { cycle: u64, guid: u64, kind: Kind, payload: u64 }

const MARKER_BEGIN: u64 = u64::MAX - 1;
const MARKER_END: u64 = u64::MAX - 2;

#[derive(Clone, Debug, Default)]
struct SpanStats { count: u32, total_cycles: u64, max_cycles: u64 }

#[derive(Clone, Debug, Default)]
struct FrameSummary {
    frame_index: u64,
    total_cycles: u64,
    stats: HashMap<u64, SpanStats>,
}

struct IncrementalCollator {
    current_frame: FrameSummary,
    open_stack: Vec<(u64, u64)>,
}

impl IncrementalCollator {
    fn new() -> Self { Self { current_frame: FrameSummary::default(), open_stack: Vec::new() } }

    fn on_event(&mut self, e: &Event) {
        match e.kind {
            Kind::Begin => {
                if e.guid == MARKER_BEGIN {
                    self.current_frame = FrameSummary::default();
                    self.current_frame.frame_index = e.payload;
                    return;
                }
                self.open_stack.push((e.guid, e.cycle));
            }
            Kind::End => {
                if e.guid == MARKER_END { return; }
                if let Some((guid, begin)) = self.open_stack.pop() {
                    if guid == e.guid {
                        let dur = e.cycle - begin;
                        let s = self.current_frame.stats.entry(guid).or_default();
                        s.count += 1;
                        s.total_cycles += dur;
                        s.max_cycles = s.max_cycles.max(dur);
                    }
                }
            }
        }
    }

    fn finalize(&mut self) -> FrameSummary {
        std::mem::take(&mut self.current_frame)
    }
}

fn main() {
    let mut collator = IncrementalCollator::new();
    let mut cycle = 0u64;

    for frame in 0..3u64 {
        collator.on_event(&Event { cycle, guid: MARKER_BEGIN, kind: Kind::Begin, payload: frame });
        cycle += 10;

        for guid in 1..=3u64 {
            collator.on_event(&Event { cycle, guid, kind: Kind::Begin, payload: 0 });
            cycle += 50 + guid * 10;
            collator.on_event(&Event { cycle, guid, kind: Kind::End, payload: 0 });
            cycle += 5;
        }

        collator.on_event(&Event { cycle, guid: MARKER_END, kind: Kind::End, payload: frame });
        let summary = collator.finalize();
        println!("Frame {}: {} spans", summary.frame_index, summary.stats.len());
        for (g, s) in &summary.stats {
            println!("  guid={}: count={} total={} max={}", g, s.count, s.total_cycles, s.max_cycles);
        }
    }
}
```

### Lv3 · 迁移设计

**题**:增量算法实时更新,但**max_cycles 不对**——只有 frame_end 才知道完整 max。怎么处理?**提示**:看 `current_frame.stats` 里的 max 是否正确(应该是,每次 end 都更新)。

**额外提示**:
- 实际上 max 在每次 end event 时就更新了,所以 max_cycles 在 frame 中部就准
- 但**平均**(avg = total / count)随着 count 增加变化,frame 中部的 avg 不代表最终 avg
- **更难的问题**:跨帧的 P99 怎么算?如果每帧只记 max / avg,P99 信息丢失
- 解决:保留最近 N 帧的全部 max / avg,从中算 P99
- **进阶**:t-digest 流式 P99 算法,固定内存近似

**Troubleshooting**:

- finalize 后 current_frame 没 reset — `std::mem::take` 自动 reset 成 Default
- 同 guid 多次 begin — 检查代码,可能漏 push stack
- **stats 在帧中没更新** — 检查 `on_event` 是否真的被 push_event 调用,可能 buffer 在某处
- **HashMap 突然变大** — 多线程同时 push,要加锁或用 thread_local
- **finalize 返回的 stats.count = 0** — on_event 没处理这条 event,检查 MARKER 过滤逻辑
