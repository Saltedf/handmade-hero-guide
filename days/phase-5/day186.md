# Day 186 · 开始调试事件录制

> Day 185 后 profiler 后端定型,但 event 数据是"挥发性"的——程序关掉就没了。今天 Casey 给 profiler 加"录制"功能:按一个键开始录制,所有 event 写到磁盘文件,事后回放分析。

## 0 · 为什么要有这一天

让我们具体地体验"挥发性 profiler 数据"的痛。Day 185 后,你的 profiler 后端定型了——按 F1 调出实时 overlay,你能看到当前帧的 span 列表。但实际场景里,你 99% 的时间不是"看当前帧",而是"看刚才那一帧的卡顿":

你跑游戏,跑到第 1024 帧突然卡了一下。你的眼睛刚扫到屏幕,F2 帧(下一帧)的 overlay 已经覆盖了 F1 帧。你慌忙暂停,但 profiler 没暂停功能,数据流走了。你按 F1 重启,但卡顿是偶发的,接下来 5 分钟都不再出现。

这就是**挥发性数据**的痛。profiler 后端只保留最近 N 帧(ring buffer),一旦数据被覆盖,就**永远丢失**。要解决这种"事后分析"需求,你需要**持久化录制**。

录制是软件工程的标准模式:**可重现(reproducible)**。在 debug、QA、用户支持、性能优化里,这都是黄金准则。你录下"出问题的那一段",任何时候都能拿出来重看。Linux 的 tcpdump、Windows 的 ETW、Chrome 的 trace 录制、Unreal Insights 的 utrace 文件——所有工业级 profiling 工具都有这个功能。

录制的设计要点:
1. **何时开始**:用户按键,或自动(比如检测到 spike)。
2. **何时结束**:用户按键,或定时(录 N 秒),或环形(永远录,出事时按一下"抓")。
3. **格式**:二进制(紧凑)还是 JSON(可读)?工业实践倾向二进制,体积优先。
4. **数据完整性**:崩溃了还能读出来吗?要不要 CRC?
5. **与实时模式共存**:录制时不能影响实时 overlay。

今天 Casey 实现"录制到磁盘":
- 录制开始:打开文件,清空 ring buffer 计数
- 录制中:event push 时同时 append 到文件
- 录制结束:close 文件,带 metadata(开始时间、帧数、player position 等)
- 回放工具:读文件,渲染 timeline(后面 Day 211+ 实现)

**学完今天,你应该能**:
- 设计一个最小但可演进的二进制文件格式(magic + version + payload)
- 用 BufWriter 把高频小写入合并成低频大 syscall,性能提升 1000x
- 解释为什么"边录边写"和"一次性写"在不同场景各有优势
- 解释 page cache 的工作原理,理解 profiler 为什么不需要 fsync
- 用 mmap 做零拷贝读取,处理大录制文件时不在内存里全部加载
- 用 zstd / lz4 给录制文件加压缩,体积减 50-70% 性能损失可忽略

## 1 · Casey 今天做了什么

Casey 加录制功能。这一天他做的是**最小可用版本**(MVP),不追求性能极致或功能完整。

1. **文件格式设计**:简单二进制——magic bytes "HHPF" + version + frame_count + events 数组。他强调"不要造一个新格式",借鉴 PNG / pcap 等经典设计:fixed magic + version + payload。
2. **写入用 `Write` trait**,append 模式。具体用 `BufWriter<File>` 包装,把高频小写合并成低频大写。
3. **metadata 在文件头**:player position、frame count、start time。这些字段帮助回放工具定位上下文("这是哪个场景?哪个玩家位置?")。
4. **用 hash 校验文件完整性**(可选):写完文件后算 CRC32,append 到末尾。读时校验。Casey 没强求,但留了 hook。

文件格式简单,他强调:"**不要造一个新格式**"。用 magic bytes + version,够用。复杂格式(比如 BTF、PCAPng)是当你有大量兼容性需求时的演进产物,不是起步阶段该搞的。

## 2 · 心智模型

### 类比:飞机黑匣子的循环录制

飞机黑匣子不停录制最近 2 小时,出事后留 2 小时数据。游戏 profiler 类似:

- **实时模式**:ring buffer 滚动(最近 N 帧)
- **录制模式**:开始时把 ring buffer 内容刷盘,然后边跑边追加
- **崩溃模式**:崩溃前最后的 ring buffer 数据可抢救

录制 = 把易失数据持久化。

### 2.1 文件格式设计

设计一个二进制文件格式,核心问题:**怎么让文件能被未来版本的 reader 读懂,或者至少安全拒绝**?Casey 借鉴了几十年前的经典格式(ELF、PNG、pcap),得出一套最小可用模板:

```
[ magic: 4 bytes ] "HHPF" (Handmade Hero ProFile)
[ version: u16 ]   1
[ flags: u16 ]     reserved(留给未来:bit 0 = 有 checksum,bit 1 = 压缩)
[ frame_count: u32 ]
[ start_cycle: u64 ]
[ end_cycle: u64 ]
[ events: DebugEvent × N ]
```

**为什么是 magic bytes**?这是文件类型的"暗号"。Linux 的 `file` 命令靠它识别文件:`ELF` 是 Linux 二进制,`\x89PNG` 是 PNG 图像,`RIFF` 是 WAV/AVI,`%PDF` 是 PDF。你的 viewer 读文件第一步就是 check magic,错了立刻拒绝。这样防止误把别的文件喂给 profiler viewer 导致崩溃。

**为什么是 version**?未来你想加字段(比如每条 event 加 thread_id)。新文件存 version=2,旧 reader 看到 version 不匹配,要么报错要么尝试兼容。**没有 version 字段,加字段就是 breaking change**——所有旧文件没法读。这是软件设计里最贵的错误之一,所以**永远加 version**。

**为什么是 little-endian(小端)**?x86_64 和现代 ARM 都是小端,文件里直接存小端,大部分平台读写都不用 swap。如果某天你跑在 PowerPC 大端机上,reader 用 `from_le_bytes` 显式转换,没问题。**显式比隐式好**——`to_le_bytes` 不会被编译器优化成 native endian 的 bug。

**Rust 写入**:

```rust
use std::fs::File;
use std::io::{Write, BufWriter};

pub fn write_recording(path: &str, events: &[Event]) -> std::io::Result<()> {
    // BufWriter 包装 File,默认 8KB 缓冲
    // 每次 write_all 写入 buffer,满了才调 syscall
    let mut f = BufWriter::new(File::create(path)?);

    // 写 magic:4 个 ASCII 字符
    f.write_all(b"HHPF")?;

    // 写 version u16,Little-Endian
    // to_le_bytes() 把 u16 转成 [u8; 2],小端字节序
    f.write_all(&1u16.to_le_bytes())?;

    // flags u16,目前全 0
    f.write_all(&0u16.to_le_bytes())?;

    // event 数量 u32
    f.write_all(&(events.len() as u32).to_le_bytes())?;

    // 起止 cycle(用于 sanity check)
    f.write_all(&events.first().map(|e| e.cycle).unwrap_or(0).to_le_bytes())?;
    f.write_all(&events.last().map(|e| e.cycle).unwrap_or(0).to_le_bytes())?;

    // 每条 event 17 字节:8 (cycle) + 8 (guid) + 1 (kind)
    for e in events {
        f.write_all(&e.cycle.to_le_bytes())?;
        f.write_all(&e.guid.to_le_bytes())?;
        f.write_all(&[e.kind as u8])?;  // enum 强转 u8
    }

    // flush 把 buffer 剩余内容写到 File
    // 注意:flush 不调 fsync,数据在 page cache,不在磁盘
    f.flush()?;
    Ok(())
}
```

**关键点详解**:
- `BufWriter::new(File)` — 包装 File,加 8KB 缓冲。10 万次 write 不会触发 10 万 syscall,只触发约 200 次(buffer 满了的时候)。
- `b"HHPF"` — byte string literal,类型 `&[u8; 4]`,直接是 ASCII 码。
- `1u16.to_le_bytes()` — `1u16` 是字面量,类型 u16。`.to_le_bytes()` 返回 `[u8; 2]`。`&[u8; 2]` 通过 deref coercion 转成 `&[u8]`,`write_all` 接收。
- `e.kind as u8` — Rust 的 enum 默认占 1 字节(如果只有 2 个 variant),`as u8` 是 zero-cost 转换。
- `f.flush()?` — 把 BufWriter 内部 buffer 推到底层 File。不调的话 BufWriter drop 时也会调,但显式调能让你更早看到错误。

### 2.2 读取与回放

```rust
use std::io::Read;

pub fn read_recording(path: &str) -> std::io::Result<Vec<Event>> {
    let mut f = File::open(path)?;
    let mut magic = [0u8; 4];
    f.read_exact(&mut magic)?;
    if &magic != b"HHPF" { return Err(std::io::Error::new(
        std::io::ErrorKind::InvalidData, "bad magic")); }
    let mut version_bytes = [0u8; 2];
    f.read_exact(&mut version_bytes)?;
    let version = u16::from_le_bytes(version_bytes);
    if version != 1 { return Err(/* ... */); }
    // ... 读完所有 events
    let mut events = Vec::new();
    // ...
    Ok(events)
}
```

### 2.3 录制 API

```rust
pub struct Profiler {
    recording: Option<BufWriter<File>>,
    events: Vec<Event>,
}

impl Profiler {
    pub fn start_recording(&mut self, path: &str) -> std::io::Result<()> {
        let f = File::create(path)?;
        self.recording = Some(BufWriter::new(f));
        Ok(())
    }

    pub fn stop_recording(&mut self) -> std::io::Result<()> {
        if let Some(mut f) = self.recording.take() {
            // 写文件头
            // 写所有 events
            f.flush()?;
        }
        Ok(())
    }

    pub fn push(&mut self, e: Event) {
        self.events.push(e);
        // 边录边写(可选,见 §2.4)
    }
}
```

### 2.4 边录边写 vs 一次性写

两种模式:

- **一次性**:所有 event 存内存,stop 时一次写盘。**简单**,但录制长时(几分钟)内存压力大
- **边录边写**:每次 push 都 append。**实时**,但每 push 增加磁盘 IO 开销

casey 的选择:**缓冲边录边写**。`BufWriter` 缓冲 8KB,满了再 flush 一次 syscall。比纯内存慢不了多少,比每次 syscall 快很多。

```rust
pub fn push(&mut self, e: Event) {
    self.events.push(e);
    if let Some(f) = &mut self.recording {
        f.write_all(&e.cycle.to_le_bytes()).unwrap();
        f.write_all(&e.guid.to_le_bytes()).unwrap();
        f.write_all(&[e.kind as u8]).unwrap();
        // BufWriter 自动缓冲,不每次 syscall
    }
}
```

但**注意**:边录边写就**没有"文件头"**——你不知道 frame_count 直到 stop。解决:stop 时回退(seek)到文件开头,改写头部。或者用 placeholder(0),UI 读时再算。

### 2.5 二进制文件格式的设计原则

设计一个二进制格式,有几个不变原则:

1. **magic bytes**(4-8 字节):文件类型识别,前几个字节就够区分。`HHPF` / `\x89PNG` / `RIFF` 都是这个
2. **version field**:兼容性。读到 v2 文件,v1 reader 拒绝(而不是 silently 误解)
3. **fixed-size header**:固定大小,容易 seek
4. **alignment**:大数据按 4/8 字节对齐,SIMD 友好
5. **optional checksum**:CRC32 / xxHash 检测损坏,可选

```rust
// 完整的 header 设计
#[repr(C)]
struct FileHeader {
    magic: [u8; 4],         // "HHPF"
    version: u16,           // 1
    flags: u16,             // bit 0: has_checksum, bit 1: compressed
    frame_count: u32,
    event_count: u32,
    start_cycle: u64,
    end_cycle: u64,
    player_pos: [f32; 3],   // 元数据
    reserved: [u8; 32],     // 预留扩展
}
// 总 80 字节,对齐 8
```

`reserved` 字段是关键——未来加新字段时,旧 reader 跳过 reserved 读后面,兼容。

### 2.6 page cache 与 flush

Linux 文件写不直接落盘——先进 **page cache**(内核 RAM),异步由 pdflush/flush 线程刷盘。`write()` 返回后,数据在 page cache,**断电会丢**。

```bash
# 看 page cache 占用
free -h
#               total        used        free      shared  buff/cache   available
# Mem:           16Gi       4.0Gi       8.0Gi       0.5Gi       4.0Gi        11Gi
#                                                       ↑ buff/cache = page cache
```

强制刷盘用 `fsync(fd)`——但慢(磁盘瓶颈,几 ms 到几百 ms)。profiler **不调 fsync**——丢最近几秒数据可接受,性能优先。

```bash
# 手动 sync 整个系统
sync

# 看正在等待刷盘的脏页
cat /proc/meminfo | grep -E "Dirty|Writeback"
```

崩溃恢复:如果游戏崩溃,pdflush 之前的数据没刷盘——这部分丢。要 100% 保证,只能 fsync,但 profiler 不值得。

### 2.7 io_uring 与异步 IO

Linux 5.1+ 的 **io_uring** 是新一代异步 IO 接口——比 `aio_*` 快,比 epoll 更通用。profiler 用 io_uring 可以"录制完全不阻塞游戏":

```rust
// 概念性,io-uring crate 提供
let mut ring = io_uring::IoUring::new(32)?;
// 提交 N 个 write,继续跑游戏
ring.submit_write(fd, buf)?;
// 后台内核完成,游戏不被阻塞
```

Casey 不用 io_uring(太复杂,Phase 5 不需要),但**生产级 profiler**(Tracy / Superluminal)用类似机制实现"零阻塞录制"。

### 2.8 录制数据的压缩

10000 events × 17 bytes = 170 KB/帧。60 fps × 60 秒 = 61 MB。10 分钟录制 = 600 MB。

压缩方案:
- **zstd**:工业标准,压缩比 3:1,速度 1 GB/s
- **lz4**:更快,压缩比 2:1,速度 4 GB/s
- **不压缩**:简单,但磁盘贵

```rust
// 用 zstd 压缩
use zstd::stream::write::Encoder;
let f = File::create(path)?;
let mut enc = Encoder::new(f, 3)?;  // level 3,平衡速度比
// 写到 enc,自动压缩
enc.write_all(b"HHPF")?;
// ...
enc.finish()?;
```

Casey 不做压缩(Phase 5 不需要),Day 211+ 加。

## 3 · 四域深入

### 3.1 · Linux 系统编程视角

Linux 文件 IO 的延迟:

- `write` syscall:~1-5 μs(小 buffer)
- `pwrite`(定位写):同
- `fsync`(强制刷盘):~100 μs - 10 ms(磁盘瓶颈)
- `mmap` + 写:同 write,但有大块时更高效

profiler 录制不调 fsync(性能优先),系统 page cache 会异步刷盘。如果程序崩溃,**最近几秒数据可能丢**——对 profiler 可以接受。

### 3.2 · Rust 生态视角

Rust 的序列化 crate:

| crate | 用途 |
|---|---|
| `serde` + `bincode` | 二进制序列化 |
| `serde` + `serde_json` | JSON |
| `rmp-serde` | MessagePack |
| 手写 | 最快,profiler 用这个 |

profiler 数据量不大,手写就够。如果用 serde,profiler 自己依赖一个通用库,**编译时间增加 5-10 秒**——这是 Casey 不喜欢的。

### 3.3 · 游戏编程视角

商业 profiler 的录制:

- Unreal Insights: `.utracybing` 文件
- Unity Profiler: `.raw` 文件
- RenderDoc: `.cap` 文件
- Superluminal: `.sup` 文件

每个都有自己的二进制格式。 Casey 的极简格式("HHPF" magic + struct array)能扩展,但起步够用。

### 3.4 · 🐧 Linux 系统编程视角(inotify 触发回放)

录制完成后,你想自动启动回放工具。Linux 的 **inotify** 监听文件创建:

```bash
# 命令行工具 inotifywait
sudo pacman -S inotify-tools
inotifywait -m -e create /tmp/ | while read path event file; do
    if [[ "$file" == *.prof ]]; then
        profiler-viewer "$path$file"
    fi
done
```

每次 profiler 写新文件,自动弹 viewer。这是 Casey 后期 day 211+ 想做的"无缝工作流"——但 Phase 5 还没做。

### 3.5 · 🦀 Rust 生态视角(memmap 零拷贝读)

读大录制文件,最快的方法是 **mmap**——把文件直接映射到内存,读 = 内存访问,不经过 read syscall:

```rust
use memmap2::Mmap;
let f = File::open(path)?;
let mmap = unsafe { Mmap::map(&f)? };
// mmap[0..4] 是 magic,直接读字节
let magic = &mmap[0..4];
assert_eq!(magic, b"HHPF");
// 整个文件按需加载(page fault 时)
```

mmap 的优势:**虚拟内存**机制让"大文件"看起来像数组,OS 自动管理 page cache。profiler viewer 用 mmap 加载大文件最自然。

## 5 · 对照与变奏

**字节序(endianness)**:

| 字节序 | CPU | 选择 |
|---|---|---|
| Little-Endian(LE) | x86_64, ARM(默认) | Casey 用这个 |
| Big-Endian(BE) | 老式 PPC, SPARC | 网络字节序(网络协议默认) |
| Native | 不显式,跟 CPU | 不跨平台 |

文件格式必须**显式指定**,否则跨 CPU 平台读出来数据错。

Rust 的 `to_le_bytes` / `from_le_bytes` 是显式的,跨平台一致。

### Chrome Trace Event Format 的对比

Chrome DevTools 的 trace JSON 格式是事实标准:

```json
[{"name": "update", "cat": "game", "ph": "X", "ts": 1234567, "dur": 50, "pid": 1, "tid": 1},
 {"name": "render", "cat": "game", "ph": "X", "ts": 1234617, "dur": 30, "pid": 1, "tid": 1}]
```

- `ph: "X"` = Complete event(begin + end 合一,带 dur)
- 文本 JSON,可读但大
- Chrome / Firefox / Pandas / Android Studio 都能读

Casey 的 HHPF 二进制比 JSON 小 5-10x,但**只能自己的 viewer 读**。trade-off:**自包含 vs 通用**。

实际工程:**支持导出** Chrome Trace Format,让你用 chrome://tracing 这个强大工具看自己的数据。这是工业级 profiler 的标配。

### 与 pcap / BTF 的对比

**pcap**(packet capture)是网络抓包的标准格式,tcpdump / Wireshark 用:

```
[magic: 4 bytes] [version: 2 + 2] [thiszone: 4] [sigfigs: 4] [snaplen: 4] [linktype: 4]
[packet 1: ts_sec + ts_usec + caplen + len + payload]
...
```

设计原则完全一样:magic + version + per-record。Casey 的 HHPF 借鉴这种经典设计。

**BTF**(BPF Type Format)是 Linux 内核的 debug info 格式,更复杂(描述类型)。profiler 不需要那么复杂,但设计哲学同源。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么用 `BufWriter` 而不是直接 `File::write_all`?

**参考解答**:
- `File::write_all` 每次都 syscall,10 万 event × 100 字节 = 1000 万次 syscall,~10 秒
- `BufWriter` 默认 8KB 缓冲,满了才 syscall,1000 万字节 / 8KB = 1250 次 syscall,~5 ms
- 2000 倍差距
- BufWriter 还有 read side(`BufReader`),对大文件读也快

### Lv2 · 动手实践

**题**:写一个最小录制 / 回放 demo:
- 生成 10000 个 Event
- 写到 `/tmp/prof.bin`
- 读回来,验证 roundtrip 一致

**参考解答**:

```rust
use std::fs::File;
use std::io::{BufWriter, BufReader, Read, Write};

#[derive(Clone, Copy, Debug, PartialEq)]
enum Kind { Begin, End }
impl Kind {
    fn to_byte(self) -> u8 { if matches!(self, Kind::Begin) { 0 } else { 1 } }
    fn from_byte(b: u8) -> Self { if b == 0 { Kind::Begin } else { Kind::End } }
}

#[derive(Clone, Copy, Debug, PartialEq)]
struct Event { cycle: u64, guid: u64, kind: Kind }

fn write_recording(path: &str, events: &[Event]) -> std::io::Result<()> {
    let mut f = BufWriter::new(File::create(path)?);
    f.write_all(b"HHPF")?;
    f.write_all(&1u16.to_le_bytes())?;
    f.write_all(&(events.len() as u32).to_le_bytes())?;
    for e in events {
        f.write_all(&e.cycle.to_le_bytes())?;
        f.write_all(&e.guid.to_le_bytes())?;
        f.write_all(&[e.kind.to_byte()])?;
    }
    f.flush()?;
    Ok(())
}

fn read_recording(path: &str) -> std::io::Result<Vec<Event>> {
    let mut f = BufReader::new(File::open(path)?);
    let mut magic = [0u8; 4]; f.read_exact(&mut magic)?;
    assert_eq!(&magic, b"HHPF");
    let mut v = [0u8; 2]; f.read_exact(&mut v)?;
    let _version = u16::from_le_bytes(v);
    let mut n = [0u8; 4]; f.read_exact(&mut n)?;
    let count = u32::from_le_bytes(n) as usize;

    let mut events = Vec::with_capacity(count);
    for _ in 0..count {
        let mut buf = [0u8; 17];  // 8 + 8 + 1
        f.read_exact(&mut buf)?;
        let cycle = u64::from_le_bytes(buf[0..8].try_into().unwrap());
        let guid = u64::from_le_bytes(buf[8..16].try_into().unwrap());
        let kind = Kind::from_byte(buf[16]);
        events.push(Event { cycle, guid, kind });
    }
    Ok(events)
}

fn main() {
    let original: Vec<Event> = (0..10000).map(|i| Event {
        cycle: i * 100,
        guid: i % 5,
        kind: if i % 2 == 0 { Kind::Begin } else { Kind::End },
    }).collect();

    write_recording("/tmp/prof.bin", &original).unwrap();
    let read_back = read_recording("/tmp/prof.bin").unwrap();
    assert_eq!(original, read_back);
    println!("roundtrip OK, {} events", read_back.len());
}
```

### Lv3 · 迁移设计

**题**:录制文件可能很大(几百 MB)。设计"流式回放"——边读边显示,不一次全部加载。

**为什么这是个真问题**?一个 10 分钟录制大约 600 MB。你的 viewer 把它 `read_to_end` 全部读到 `Vec<Event>`,内存爆。更糟的是,UI 只显示当前屏幕上的几百帧,大部分读进来的数据根本用不到。

**设计思路**:
1. **实现 `Iterator<Item = Event>` 而非返回 `Vec<Event>`**。Iterator 是 lazy 的——`next()` 才读一条。
2. **内部维护 `BufReader<File>` + 当前位置**。每次 `next()` 调 `read_exact` 一次。
3. **UI 用 `iter.take(N).collect()`**——一次只看 N 条。
4. **进阶:支持 `seek(frame_index)`**——直接跳到第 N 帧。需要在文件里加 frame offset 索引。
5. **进阶 2:用 mmap 替代 read**——OS 自动管理缓存,读 = 内存访问。

**参考骨架**:

```rust
pub struct EventIterator {
    reader: BufReader<File>,
    remaining: usize,
}

impl EventIterator {
    pub fn open(path: &str) -> std::io::Result<Self> {
        let mut reader = BufReader::new(File::open(path)?);
        // 读 header
        let mut magic = [0u8; 4];
        reader.read_exact(&mut magic)?;
        assert_eq!(&magic, b"HHPF");
        let mut buf = [0u8; 2]; reader.read_exact(&mut buf)?;
        let _ver = u16::from_le_bytes(buf);
        reader.read_exact(&mut buf)?;
        let _flags = u16::from_le_bytes(buf);
        let mut buf4 = [0u8; 4]; reader.read_exact(&mut buf4)?;
        let count = u32::from_le_bytes(buf4) as usize;
        // skip start_cycle + end_cycle (16 bytes)
        let mut skip = [0u8; 16]; reader.read_exact(&mut skip)?;
        Ok(Self { reader, remaining: count })
    }
}

impl Iterator for EventIterator {
    type Item = Event;
    fn next(&mut self) -> Option<Event> {
        if self.remaining == 0 { return None; }
        self.remaining -= 1;
        let mut buf = [0u8; 17];
        self.reader.read_exact(&mut buf).ok()?;
        Some(Event {
            cycle: u64::from_le_bytes(buf[0..8].try_into().unwrap()),
            guid: u64::from_le_bytes(buf[8..16].try_into().unwrap()),
            kind: Kind::from_byte(buf[16]),
        })
    }
}

// 用法:UI 只取当前可见的 N 条
let iter = EventIterator::open("/tmp/prof.bin")?;
let visible: Vec<Event> = iter.skip(scroll_offset).take(page_size).collect();
```

**为什么 Iterator 比 Vec 好**:
- 内存恒定(只持有当前页)。
- 可以 lazy(用户不滚动就不读)。
- 可以组合(`iter.filter(...).map(...).take(...)`)。
- Rust 的零成本抽象保证 Iterator 链没有运行时开销。

### 8.1 字节序与二进制查看工具

`xxd` 是最常用的二进制查看器。Arch 默认装了(vim 包带)。

```bash
# xxd 输出:左是地址(十六进制),中是字节,右是 ASCII
xxd /tmp/prof.bin | head -3
# 00000000: 4848 5046 0100 0000 1027 0000 0000 6400  HHPF.......'...d.
# 00000010: 0000 0000 ...

# hexdump 是替代,默认输出格式不同
hexdump -C /tmp/prof.bin | head -3

# od (octal dump)是最老的工具,POSIX 标准
od -A x -t x1z /tmp/prof.bin | head -3

# 想分析 ELF(任何文件)的结构
readelf -h /usr/bin/ls
# 输出 ELF header 各字段(magic、entry、program header offset 等)
# 你会发现 Casey 的 HHPF header 跟 ELF header 思路完全一致
```

**怎么读 xxd 输出**:
- 地址列(`00000000:`)— 文件偏移(字节序号)
- 字节列(`4848 5046 0100`)— 每两个字符是一个字节,十六进制。`48` = ASCII 'H'。
- ASCII 列(`HHPF`)— 字节转 ASCII,不可打印用 `.`

对照解读:
- `48 48 50 46` = "HHPF" magic ✓
- `01 00` = version=1(Little-Endian:低字节先存)
- `00 00` = flags=0
- `10 27 00 00` = count=10000(LE:0x00002710 = 10000)
- 然后开始 event 数据

### 8.3 Troubleshooting

- **读 magic 错** — 字节序搞反(`from_be` vs `from_le`)。用 xxd 看实际字节,看 `01 00` 还是 `00 01`。
- **读出来的 events 数不对** — header 的 count 字段写错了。检查 `(events.len() as u32).to_le_bytes()`。
- **panic on read_exact** — 文件被截断,可能录制时崩溃。在录制循环里加 `Result` 处理,而不是 unwrap。
- **录制 1 分钟文件几百 MB** — 加 zstd 压缩。10000 events × 17 bytes = 170KB/帧,60 fps × 60s = 61MB。压缩到 ~20MB。
- **崩溃后文件不完整** — 没有 fsync,page cache 数据丢。可以接受,或者定时 fsync(每 N 帧)。
- **BufWriter 写满后卡顿** — flush 时 syscall 阻塞。可以用 io_uring 异步,或后台线程。
- **roundtrip 数据不一致** — bytes 反序列化时 offset 算错。注意 `buf[0..8]` vs `buf[8..16]` 的边界。
- **多线程录制时数据交错** — 多线程 push event 没加锁。要么用 `Arc<Mutex<Vec<Event>>>`,要么每线程独立 buffer,frame_end 时合并。

### 8.5 期望输出与字节解读

```
roundtrip OK, 10000 events
```

文件 `/tmp/prof.bin` 约 170 KB(28 字节 header + 10000 × 17 字节 event)。`xxd` 看头部:

```
00000000: 4848 5046 0100 0000 1027 0000 0000 6400  HHPF.......'...d.
00000010: 0000 0000 ...
```

字节解读:
- `48 48 50 46` = "HHPF" magic ✓
- `01 00` = version=1(Little-Endian)
- `00 00` = flags=0
- `10 27 00 00` = count=10000(LE:0x00002710 = 10000)
- 接下来 16 字节是 start_cycle + end_cycle
- 然后开始第一条 event 的 17 字节

**怎么验证文件正确**?写一个独立的 Python 脚本读出来对照:

```python
# verify.py
import struct
with open("/tmp/prof.bin", "rb") as f:
    magic = f.read(4)
    assert magic == b"HHPF", f"bad magic: {magic}"
    version, = struct.unpack("<H", f.read(2))
    flags, = struct.unpack("<H", f.read(2))
    count, = struct.unpack("<I", f.read(4))
    start, = struct.unpack("<Q", f.read(8))
    end, = struct.unpack("<Q", f.read(8))
    print(f"magic={magic}, version={version}, count={count}, start={start}, end={end}")
    # 读第一条 event
    cycle, guid, kind = struct.unpack("<QQB", f.read(17))
    print(f"first event: cycle={cycle}, guid={guid}, kind={kind}")
```

跑 `python3 verify.py`,看到 `count=10000` 和第一条 event 数据,证明文件格式正确。这种**跨语言验证**是检查二进制格式的金标准——如果 Python 都能读出来,你的格式是真标准。
