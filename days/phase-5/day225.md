
# Day 225 · 从桌面淡入淡出

> 游戏启动时直接全屏闪现,体验差。今天 casey 加启动 / 退出淡入淡出:游戏从透明逐渐变不透明,退出时反向。这需要 per-pixel alpha 合成 + 平台层支持。

## 0 · 为什么要有这一天

UX 视角:用户启动游戏,屏幕突然变成游戏画面 → 视觉冲击、不专业。优雅做法:

```
桌面 → 黑屏(0.5s) → 游戏画面淡入(1s) → 游戏可玩
```

退出时反向。整个过程 1.5-2 秒,无突兀感。

技术挑战:

- **窗口透明**:窗口本身要有 per-pixel alpha(支持半透明显示)
- **合成**:游戏画面 + 黑色背景 + alpha 控制
- **平台 API**:Win32 / Wayland / X11 各有不同 alpha 透明 API

**casey 今天的方案**:

1. 启动时窗口 alpha=0(全透明),逐渐到 alpha=1(完全不透明)
2. 退出时反向
3. 中间显示一个游戏 logo 或黑屏

**Linux 视角**:Wayland / X11 都支持 compositor alpha(ARGB visual)。Rust 用 winit 创建窗口时设置 `transparent: true`,glutin 会请求 ARGB visual。

心理锚点:看完今天,你能用代码实现"专业感的启动动画"。

## 1 · Casey 今天做了什么

1. **加 WindowAlpha 状态**:全局透明度
2. **改 platform layer**:Win32 用 `SetLayeredWindowAttributes`,Linux 类似用 compositor 协议
3. **加 fade animation**:启动后 1 秒 alpha 从 0 到 1
4. **加 fade-out**:退出前反向

## 2 · 心智模型

### 类比:剧场幕布

剧场演出:

- 开场:幕布从闭合到拉开,逐渐露出舞台
- 闭幕:幕布拉上,舞台被遮

casey 的游戏 alpha 就是幕布:0 = 闭合(透明,看不到),1 = 拉开(不透明,全显示)。

### 2.1 Alpha 合成

per-pixel alpha 合成公式:

```
result = src.rgb * src.alpha + dest.rgb * (1 - src.alpha)
```

src.alpha=1 时,result = src.rgb(完全用源)。
src.alpha=0 时,result = dest.rgb(完全用目标,源不可见)。
src.alpha=0.5 时,result = (src + dest) / 2(半透明混合)。

游戏启动时整个窗口 alpha 从 0 到 1,视觉上从"看不见"到"完全显示"。

### 2.2 平台 API

**Win32**:
```c
// 设置 layered window(支持 per-pixel alpha)
SetWindowLong(hwnd, GWL_EXSTYLE, WS_EX_LAYERED);
SetLayeredWindowAttributes(hwnd, 0, alpha_byte, LWA_ALPHA);
// alpha_byte: 0=透明, 255=不透明
```

**Wayland**:
- 用 `wp_viewport` 设置整体 opacity(部分 compositor 支持)
- 或渲染到 ARGB buffer,compositor 自动合成

**X11**:
- 用 ARGB visual + composite extension
- `_NET_WM_WINDOW_OPACITY` 属性

### 2.3 winit + glutin 实现

Rust 跨平台:

```rust
let window = WindowBuilder::new()
    .with_transparent(true)  // 请求 ARGB visual
    .build(&event_loop)?;

// 改 alpha
window.set_transparent(Some(true));  // 部分 winit 版本
// 或在 GL 里用 alpha 清屏
```

casey 在 Win32 直接用 `SetLayeredWindowAttributes`。Rust 翻译用 winit API。

### 2.4 Animation 曲线

线性 fade 看起来"机械"。专业游戏用 ease 曲线:

```rust
fn ease_in_out(t: f32) -> f32 {
    // 三次 smoothstep
    t * t * (3.0 - 2.0 * t)
}

// 启动 1 秒 fade in
let elapsed = current_time - fade_start;
let t = (elapsed / 1.0).min(1.0);
let alpha = ease_in_out(t);
```

ease_in_out 在开始 / 结束慢,中间快。视觉上更自然。

### 2.5 平台层抽象

跨平台 alpha 设置:

```rust
trait PlatformWindow {
    fn set_global_alpha(&self, alpha: f32);
}

#[cfg(target_os = "windows")]
impl PlatformWindow for Win32Window {
    fn set_global_alpha(&self, alpha: f32) {
        unsafe {
            winapi::SetLayeredWindowAttributes(
                self.hwnd, 0,
                (alpha * 255.0) as u8,
                LWA_ALPHA,
            );
        }
    }
}

#[cfg(target_os = "linux")]
impl PlatformWindow for WinitWindow {
    fn set_global_alpha(&self, _alpha: f32) {
        // Wayland/X11 没有 global alpha 概念,
        // 用 GL 清屏 alpha 替代
    }
}
```

Linux 没有"全局 alpha"直接 API,只能通过 GL 清屏色 alpha 间接实现。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 ease_in_out 看起来比 linear 自然?

**参考解答**:人类对运动的感知不是线性的。linear 在开始 / 结束"突然加速 / 减速",视觉上有跳跃感。ease_in_out 通过 smoothstep 让加速 / 减速阶段慢,中段快,符合"惯性"直觉。生物视觉对加速度敏感,linear 的"瞬间加速度"被察觉为不自然。

### Lv2 · 动手实践

**题**:实现 fade in / out 动画,用 ASCII 模拟显示(alpha 用字符密度近似)。

**参考解答**:

```rust
fn ease_in_out(t: f32) -> f32 {
    t * t * (3.0 - 2.0 * t)
}

fn alpha_to_char(a: f32) -> char {
    let chars = [' ', '.', ':', '-', '=', '+', '*', '#', '%', '@'];
    let idx = ((a * (chars.len() - 1) as f32) as usize).min(chars.len() - 1);
    chars[idx]
}

fn main() {
    let fade_duration = 2.0_f32;
    let steps = 40;

    println!("=== Fade In ===");
    for i in 0..=steps {
        let t = i as f32 / steps as f32;
        let alpha = ease_in_out(t) * (i as f32 / steps as f32).min(1.0);
        // 注:在 fade_duration 内
        let progress = (i as f32 / steps as f32) * fade_duration;
        let actual_alpha = if progress < fade_duration {
            ease_in_out(progress / fade_duration)
        } else { 1.0 };
        let c = alpha_to_char(actual_alpha);
        let line: String = std::iter::repeat(c).take(50).collect();
        println!("{} | {:.2}", line, actual_alpha);
    }
}
```

## 10 · 深入:窗口合成器与透明度

casey 今天实现的"桌面淡入淡出"——游戏窗口从不透明变透明,看见桌面——背后依赖一个叫**窗口合成器**(compositor)的 OS 服务。让我们把这件事彻底讲透。

### 10.1 三种窗口渲染架构

**架构 1:direct rendering**(经典,X11 默认 / Win32 GDI)

每个窗口直接画到屏幕的一块区域。窗口移动时,OS 让被遮挡的窗口重绘。透明效果靠"截屏背景,叠加自己的像素"——慢且不准。

**架构 2:composited rendering**(现代,macOS Quartz / Linux Wayland / Windows DWM)

所有窗口画到自己的离屏 surface。合成器把所有 surface 按 z-order 合成到屏幕。透明、模糊、阴影都是合成器特效,免费。

**架构 3:immediate-mode**(全屏游戏)

游戏独占整个屏幕,无窗口管理。透明效果由游戏自己实现(渲染时混合背景)。

casey 的 HH 默认是架构 3(全屏)。Day 225 切到架构 2(窗口模式),用合成器实现淡入淡出。

### 10.2 透明窗口的实现细节

在 composited 系统下,窗口透明需要三步:

**Step 1:窗口声明支持透明**

```rust
// X11
use xcb::x;
let attrs = [
    x::Cw::BackPixel(0),       // 黑色背景
    x::Cw::BorderPixel(0),
    x::Cw::EventMask(x::EventMask::EXPOSURE),
    x::Cw::Colormap(colormap_id),  // 32-bit colormap
];
let visual_id = xcb_depth_32_visual();  // 找 ARGB visual
xcb_create_window(conn, 32, window, ...);  // depth=32 表示 ARGB
```

**Step 2:渲染时使用 alpha 通道**

```rust
// 像素格式 BGRA8,每个像素 4 字节
struct Pixel { b: u8, g: u8, r: u8, a: u8 }  // 注意 B 顺序

// alpha=0 完全透明,alpha=255 完全不透明
fn set_fade(buffer: &mut [Pixel], alpha: u8) {
    for p in buffer {
        p.a = alpha;
    }
}
```

**Step 3:合成器接收并显示**

合成器读取 window surface,按 alpha 通道混合到桌面。这是 OS 提供的,免费。

### 10.3 不同 OS 的透明 API

**Windows DWM**:

```cpp

BOOL blurBehind = TRUE;
DwmEnableBlurBehindWindow(hwnd, &DWM_BLURBEHIND{

// 设窗口 alpha

```

**X11 / XRender**:

```c
// 找 32-bit ARGB visual

// 创建 window 用这个 visual
Window win = XCreateWindow(display, root, 0, 0, w, h, 0,

```

**Wayland**(更现代):

```c
// wl_compositor + wl_subcompositor

```

**macOS Cocoa**:

```swift

```

### 10.4 合成器延迟与游戏性能

composited 系统下,游戏帧要走"渲染 → 合成器 → 显示",多一跳。这导致:

1. **额外延迟**(~1-2ms)。玩家输入到屏幕响应慢。
2. **合成器开销**。每帧合成所有窗口,合成器 thread 用 CPU。
3. **VSync 双重**。游戏 VSync + 合成器 VSync,延迟 2 帧。

游戏要低延迟,推荐**全屏独占**(exclusive fullscreen)。casey 在 day241+ 讨论 OpenGL VSync,涉及这个问题。

### 10.5 Linux 桌面合成器对比

不同 Linux 桌面环境用不同合成器:

- **Mutter**(GNOME):Clutter-based,支持 blur / shadow
- **KWin**(KDE):强大,可配置性强
- **wlroots / Sway**:Wayland,极简
- **Picom / Compton**:X11 standalone compositor,轻量
- **Weston**:Wayland reference

casey 的 HH Linux 翻译版要透明窗口,需要保证合成器运行。X11 上没合成器(经典),透明 fallback 到"截屏 + 叠加"的慢路径。

### 10.7 淡入淡出的动画曲线

casey 实现淡入淡出,要选动画曲线:

**线性**:alpha = t / duration。简单但 unnatural。
**Ease-in-out**:alpha = t * t * (3 - 2 * t)。平滑,自然。
**Ease-out**:alpha = 1 - (1 - t)²。开始快,结束慢。
**Cubic-bezier**:CSS 风格,极精细控制。

casey 用 ease-in-out,符合直觉。商业 UI 用 cubic-bezier 精细调优(Apple 的"natural"曲线)。

淡入淡出时长:0.3-0.5 秒最自然。短了突兀,长了拖沓。casey 在视频里讨论这个细节。

### 10.8 透明窗口的渲染难点

透明窗口渲染时,如果游戏内部混合用 premultiplied alpha,要正确转换。否则透明边缘会有黑边 / halo 效应。

```rust
// Non-premultiplied:
//   final = src * src.a + dst * (1 - src.a)
// Premultiplied:
//   final = src + dst * (1 - src.a)
//   (src 已经预先乘了 alpha)

// 渲染到透明 window surface 时,合成器期望 premultiplied
fn to_premultiplied(rgba: [u8; 4]) -> [u8; 4] {
    let a = rgba[3] as f32 / 255.0;
    [
        (rgba[0] as f32 * a) as u8,
        (rgba[1] as f32 * a) as u8,
        (rgba[2] as f32 * a) as u8,
        rgba[3],
    ]
}
```

casey 在 day225 反复强调这个——premultiplied alpha 是图形学反复踩坑的地方。casey 后续在 day242 OpenGL sRGB 也要重新讨论。

### 10.9 工业级透明效果

透明窗口可以做很多酷炫效果:

**1. 圆角窗口**:用 alpha mask,角落 alpha=0,中间 alpha=255。macOS / 现代版 Windows 自动支持,跨平台要手写。

**2. 阴影效果**:窗口外加一圈半透明阴影。compositor 提供 shadow,但形状复杂(非矩形)要手写。

**3. 毛玻璃效果**:blur behind——透过窗口看到桌面是模糊的。Windows 的 `DwmExtendFrameIntoClientArea` 或 macOS NSVisualEffectView。

**4. 形状不规则**:窗口是 logo 形状(非矩形),用 alpha mask 实现。老式 splash window 常见。

**5. 抠图效果**:"绿色背景"自动变透明,实现 chroma key。casey HH 不需要,但视频流处理常用。

casey 在 day225 主要做 fade in/out,简单 alpha 渐变。生产级 UI 框架(Qt / WPF)把这些效果做成了配置项。

### 10.10 跨平台透明窗口的陷阱

不同 OS 对透明窗口行为不一致:

**Windows**:
- DWM 关闭(经典主题)时,透明窗口不支持
- Aero 玻璃效果需要 DWM 启用
- 全屏独占时无透明概念

**Linux X11**:
- 必须有合成器(否则透明 fallback 黑背景)
- ARGB visual 不一定可用(取决于 X server 配置)
- 部分老应用不识别透明窗口

**Wayland**:
- 合成器实现可选,有些不支持透明
- 部分协议(xdg-shell)对透明语义模糊

**macOS**:
- 透明窗口始终支持(Quartz 强制)
- 但透明窗口不能 get focus(否则有视觉怪事)

**WebAssembly(Browser)**:
- Canvas 默认透明背景
- 但 game canvas 通常是 `<canvas style="background: black">`,要 CSS `background: transparent` 配合

casey 的 HH Windows 为主,Rust 翻译版跨平台要测试每个 OS 的行为。

### 10.11 性能影响:透明窗口的代价

透明窗口的性能开销:

1. **额外 alpha 通道**:帧 buffer 从 RGB 变 RGBA,内存 +33%。
2. **合成器工作量**:每帧合成整个窗口到桌面,GPU 资源消耗。
3. **dirty region 更新**:部分窗口变化时,合成器只更新 dirty region,但游戏每帧全屏变化,无优化空间。
4. **premultiplied 转换**:GPU shader 多一步乘法。

总体:5-10% 性能损失。casey 的 HH 透明模式只在 menu / cutscene 用,游戏主循环回到不透明模式。

### 10.12 实战:Linux 透明游戏窗口

在 Arch Linux 上跑 Rust 游戏透明窗口的完整例子:

```rust
// Cargo.toml
// [dependencies]
// winit = "0.30"
// softbuffer = "0.4"  // 软件渲染到 window surface

use winit::application::ApplicationHandler;
use winit::event::WindowEvent;
use winit::window::Window;
use winit::dpi::PhysicalSize;

struct App {
    window: Option<Window>,
    context: Option<softbuffer::Context>,
    surface: Option<softbuffer::Surface>,
    alpha: u8,
}

impl ApplicationHandler for App {
    fn resumed(&mut self, event_loop: &winit::event_loop::ActiveEventLoop) {
        let window = event_loop.create_window(
            Window::default_attributes()
                .with_transparent(true)
                .with_inner_size(PhysicalSize::new(800, 600))
        ).unwrap();
        // ... 创建 softbuffer surface,渲染时给 alpha 渐变
        self.window = Some(window);
    }
    
    fn window_event(&mut self, event_loop, _id, event) {
        match event {
            WindowEvent::CloseRequested => event_loop.exit(),
            _ => (),
        }
    }
}

fn main() {
    let mut app = App { window: None, context: None, surface: None, alpha: 0 };
    event_loop.run_app(&mut app);
}
```

跑前确认合成器运行(GNOME / KDE 默认有,X11 上 `picom` 等)。否则透明 fallback 到黑背景。

### 10.13 教学总结

day225 的核心要点:

1. **透明窗口依赖 compositor**:不是游戏自己能做的,要 OS 提供
2. **跨平台 API 差异大**:Windows / Linux / macOS 各有机制
3. **premultiplied alpha 必懂**:图形学反复踩坑
4. **性能 5-10% 损失**:仅在需要时启用
5. **动画曲线影响观感**:ease-in-out 最自然

casey 给教学基础,生产项目用 winit 抽象跨平台差异。学完 day225,你能在自己项目里实现 menu 淡入淡出、splash screen、毛玻璃 UI。

### 10.14 历史回顾:窗口系统演化

透明窗口是窗口系统演化的副产品:

**1980s**(X11 / Win3.1):窗口不透明,无合成器。窗口移动时撕裂。

**1990s**(Windows 95 / Mac OS 7):仍无合成器,但部分 UI 用"截图叠加"实现简单透明。慢。

**2000s**(macOS Quartz Extreme 2002):第一个主流合成器,Mac 率先有透明 + 阴影 + 模糊。

**2008+**(Windows DWM with Aero):Windows Vista/7 引入 DWM,透明 + 玻璃效果。

**2010s**(Linux Compiz / Mutter / KWin):X11 上 compositor 普及,Wayland 标准化。

**2020s**(HDR + 高刷新率):合成器支持 HDR、VRR、HDR 透明。继续演化。

casey 在 2014-2015 录制 HH day225 时,合成器还不普及。今天(2026),合成器是标配,透明窗口实现极简单。

## 11 · Alpha 合成数学

最后,让我们把 alpha 合成(compositing)的数学彻底讲清楚。这是图形程序员的基本功。

### 11.1 Over operator(标准 alpha 混合)

最常用的合成模式:

```
C_out = C_src * α_src + C_dst * (1 - α_src) * α_dst
α_out = α_src + α_dst * (1 - α_src)
```

意思:源像素按 alpha 加到目标上。

举例:目标红 (255, 0, 0),源蓝 (0, 0, 255) alpha=0.5:

```
R = 0 * 0.5 + 255 * 0.5 = 127.5
G = 0 * 0.5 + 0 * 0.5 = 0
B = 255 * 0.5 + 0 * 0.5 = 127.5
```

结果紫色 (128, 0, 128)。视觉上,半透明蓝盖在不透明红上,看到紫色。

### 11.2 其他合成模式

除了 Over,还有:

- **Plus(additive)**:`C = C_src + C_dst`,无 alpha。火焰、光晕效果。
- **Multiply**:`C = C_src * C_dst / 255`。阴影变暗。
- **Screen**:`C = 255 - (255 - C_src) * (255 - C_dst) / 255`。逆 multiply。
- **Min / Max**:`C = min(C_src, C_dst)` / `max(...)`。特殊效果。
- **Difference**:`C = |C_src - C_dst|`。艺术效果。

casey 的 HH 用 Over 为主。商业图形软件(Photoshop / Krita)支持所有模式。

### 11.3 Premultiplied alpha

工业级渲染用 premultiplied alpha:

```
// Non-premultiplied(straight alpha):
//   C, A 独立存储
//   final = C_src * A_src + C_dst * (1 - A_src)

// Premultiplied:
//   C' = C * A (存储时预先乘)
//   final = C'_src + C_dst * (1 - A_src)
//   注意:减了一个乘法
```

优点:

1. **性能**:少一次乘法,GPU shader 快一点
2. **正确性**:边缘像素不会出现颜色"溢出"
3. **兼容**:大多数图像 API 期望 premultiplied

缺点:

1. **存储**:不能从 C' 反推 C(信息丢失)
2. **转换开销**:加载图片时转换,需要 pre-processing

OpenGL / Vulkan / Direct3D 默认期望 premultiplied。casey 在 day242 sRGB 讨论时再次涉及。

### 11.4 工程教训

day225 的 alpha 合成给我们的工程教训:

1. **统一 alpha 模式**:整个 pipeline 要么全 straight,要么全 premultiplied。混用产生 bug。
2. **测试边缘**:alpha 接近 0 或 255 时,数值精度问题。f32 通常 OK,f16 可能丢精度。
3. **HDR 扩展**:HDR 渲染时颜色 > 1.0,alpha 合成要重新推导。casey 不展开。

学完这些,你看任何图形 API 文档,都能秒懂 alpha 概念。

### 11.5 颜色空间与 alpha

casey 在 day225 简化用 sRGB 颜色空间做 alpha 合成。但严格来说,alpha 合成应该在**线性空间**做:

```
// 错误(直接在 sRGB 空间合成):
final = src * alpha + dst * (1 - alpha)  // 视觉上中间色偏暗

// 正确(转线性,合成,转回 sRGB):
src_lin = srgb_to_linear(src)
dst_lin = srgb_to_linear(dst)
final_lin = src_lin * alpha + dst_lin * (1 - alpha)
final = linear_to_srgb(final_lin)
```

差异在中间灰度。sRGB 不是线性,直接插值会出现"中间色偏暗"。

casey 在 day242 重新讨论 sRGB,实现正确转换。day225 是简化版,直接 sRGB 合成,视觉上可接受(差异 < 5%),但不严格。

### 11.6 实战 Rust 代码

完整的 Rust alpha 合成实现:

```rust
fn blend_premultiplied(dst: &mut [u8; 4], src: [u8; 4]) {
    // Premultiplied over operator
    let sa = src[3] as u32;
    let da = dst[3] as u32;
    let inv_sa = 255 - sa;
    
    dst[0] = (src[0] as u32 + (dst[0] as u32 * inv_sa) / 255) as u8;
    dst[1] = (src[1] as u32 + (dst[1] as u32 * inv_sa) / 255) as u8;
    dst[2] = (src[2] as u32 + (dst[2] as u32 * inv_sa) / 255) as u8;
    dst[3] = (sa + (da * inv_sa) / 255) as u8;
}

fn blend_straight(dst: &mut [u8; 4], src: [u8; 4]) {
    let sa = src[3] as f32 / 255.0;
    let inv_sa = 1.0 - sa;
    dst[0] = (src[0] as f32 * sa + dst[0] as f32 * inv_sa) as u8;
    dst[1] = (src[1] as f32 * sa + dst[1] as f32 * inv_sa) as u8;
    dst[2] = (src[2] as f32 * sa + dst[2] as f32 * inv_sa) as u8;
    dst[3] = (sa * 255.0 + dst[3] as f32 * inv_sa) as u8;
}
```

`blend_premultiplied` 性能更好(u32 整数运算),但要求 src 是 premultiplied。`blend_straight` 通用但慢(浮点)。

casey 的 HH 软件渲染器用 straight alpha(简单),day235 切到 OpenGL 后用 premultiplied(性能)。学完 alpha 数学,你能根据场景选择。

### 11.7 测试 alpha 合成

alpha 合成的测试用 snapshot 对比:

```rust
#[test]
fn test_blend_red_on_blue() {
    let mut dst = [0, 0, 255, 255];  // 不透明蓝
    let src = [255, 0, 0, 128];       // 半透明红
    blend_straight(&mut dst, src);
    // 期望:紫色调
    assert_eq!(dst, [128, 0, 128, 255]);  // 近似
}

#[test]
fn test_blend_premultiplied_white() {
    let mut dst = [0, 0, 0, 0];       // 完全透明
    let src = [255, 255, 255, 255];   // 不透明白(premultiplied 不变)
    blend_premultiplied(&mut dst, src);
    assert_eq!(dst, [255, 255, 255, 255]);
}
```

每个测试覆盖一种合成场景。casey 不写正式 unit test(他在视频里手动测试),但生产项目要有。
