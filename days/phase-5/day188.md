## 2 · 心智模型

### 类比:Excel 图表的 hover

Excel 折线图,鼠标移到点上,显示"Series 1, Point 5: Value 42"。背后:

1. 鼠标坐标
2. 反算:点 5 的屏幕坐标,鼠标离它最近
3. 弹 tooltip

profiler 曲线一样:鼠标 X 坐标 → 帧号(线性映射)。

### 2.1 命中测试(hit-test)

```rust
pub fn graph_frame_at_pos(
    mouse_x: i32, mouse_y: i32,
    graph_x: i32, graph_y: i32, graph_w: i32, graph_h: i32,
    frame_count: usize,
) -> Option<usize> {
    // 1. 鼠标在矩形内吗
    if mouse_x < graph_x || mouse_x >= graph_x + graph_w { return None; }
    if mouse_y < graph_y || mouse_y >= graph_y + graph_h { return None; }

    // 2. 算 X 坐标对应的帧号
    let rel_x = mouse_x - graph_x;
    let frame = (rel_x as usize * frame_count) / graph_w as usize;
    Some(frame.min(frame_count - 1))
}
```

**Rust 注释**:
- 整数除法 `a * n / w` — 避免浮点误差
- `.min(frame_count - 1)` — 边界 clamp

### 2.2 tooltip 渲染

```rust
pub fn draw_tooltip(
    fb: &mut Framebuffer,
    mouse_x: i32, mouse_y: i32,
    frame: &FrameSummary,
) {
    let lines = [
        format!("Frame {}", frame.frame_index),
        format!("Cycles: {}", frame.total_cycles),
        format!("Spans: {}", frame.stats.len()),
    ];

    let text_h = 16;
    let padding = 4;
    let w = 200;
    let h = lines.len() as i32 * text_h + padding * 2;
    let x = mouse_x + 16;
    let y = mouse_y + 16;

    // 背景
    draw_rect_filled(fb, x, y, w, h, 0xFF000000);
    draw_rect_outline(fb, x, y, w, h, 0xFFFFFFFF);

    // 文字
    for (i, line) in lines.iter().enumerate() {
        draw_text(fb, line, x + padding, y + padding + i as i32 * text_h, 0xFFFFFFFF);
    }
}
```

**注意**:这里 `format!` 每帧都分配内存。优化:用 `itoa` crate 或自己写数字到字符串。但对 tooltip 这种 1 帧一次的代码,format! 可接受。

### 2.3 immediate-mode 状态

immediate-mode UI 的状态怎么存?**用 ID 哈希**。每个 UI 元素(按钮、曲线图、tooltip)有一个唯一 ID,状态按 ID 索引:

```rust
pub struct UiState {
    hover: HashMap<u64, bool>,  // element_id -> is_hover
    active: HashMap<u64, bool>,
}

impl UiState {
    pub fn is_hover(&self, id: u64) -> bool {
        *self.hover.get(&id).unwrap_or(&false)
    }

    pub fn set_hover(&mut self, id: u64, h: bool) {
        self.hover.insert(id, h);
    }
}
```

每帧重新计算 hover(命中测试),更新 UiState。下一帧用上一帧的 hover 状态画 tooltip。

```rust
// 每帧
fn frame(ui: &mut UiState, mouse: MouseState) {
    let graph_id = hash("frame_time_graph");
    let hover_frame = graph_frame_at_pos(mouse.x, mouse.y, ...);
    ui.set_hover(graph_id, hover_frame.is_some());

    draw_graph(...);
    if let Some(frame_idx) = hover_frame {
        let summary = &history[frame_idx];
        draw_tooltip(...);
    }
}
```

### 2.5 immediate-mode 的状态保留

immediate-mode UI 的"无状态"指**控件对象无状态**(不像 Qt 的 QWidget 持续存在)。但**输入状态**(鼠标位置、按键状态、滚动量)是必要的。

Casey 的做法:在 main loop 维护 `MouseState` struct,每帧传入 UI 函数:

```rust
pub struct MouseState {
    pub x: i32,
    pub y: i32,
    pub left_down: bool,
    pub left_pressed: bool,   // 这一帧按下(边沿检测)
    pub left_released: bool,  // 这一帧松开
    pub wheel_delta: f32,
}

fn update_mouse_state(state: &mut MouseState, events: &[Event]) {
    let prev_down = state.left_down;
    state.left_pressed = false;
    state.left_released = false;
    for e in events {
        match e {
            Event::CursorMoved { x, y, .. } => { state.x = *x as i32; state.y = *y as i32; }
            Event::MouseInput { state: bs, button: MouseButton::Left, .. } => {
                match bs {
                    ElementState::Pressed => { state.left_down = true; state.left_pressed = true; }
                    ElementState::Released => { state.left_down = false; state.left_released = true; }
                }
            }
            _ => {}
        }
    }
}
```

`left_pressed` / `left_released` 是**边沿检测**(edge detection)——只在状态变化的帧为 true。这是 immediate-mode 检测"点击"的标准方法。

### 2.6 ID 哈希的稳定性

immediate-mode UI 的 ID 必须跨帧**稳定**——同一元素每帧 ID 相同。Casey 用位置 + 字符串 hash:

```rust
fn ui_id(label: &str, index: u32) -> u64 {
    let mut h = FnvHasher::new();
    h.write(label.as_bytes());
    h.write_u32(index);
    h.finish()
}
```

每个 UI 元素调用 `button("save")` 时,ID = hash("save", 0)。下一帧再调 `button("save")`,ID 相同,state 取出。

**坑**:如果两个 button 都叫 "save"(在不同窗口),ID 冲突,hover 状态错乱。解决:加父 ID 前缀——`hash("window1") ^ hash("save")`。Dear ImGui 用 stack-based ID(进入 window push ID,退出 pop),自动避免冲突。

### 2.7 tooltip 的延迟显示

实际产品里,tooltip 不是立即显示——鼠标停留 500ms 才弹。否则鼠标扫过 UI 时 tooltip 闪烁。

```rust
struct TooltipState {
    hover_start: Option<Instant>,
}

impl TooltipState {
    fn update(&mut self, hovering: bool, now: Instant) -> bool {
        if hovering {
            if self.hover_start.is_none() {
                self.hover_start = Some(now);
            }
            now.duration_since(self.hover_start.unwrap()) > Duration::from_millis(500)
        } else {
            self.hover_start = None;
            false
        }
    }
}
```

Casey day 188 不做延迟(立即显示),但工业 UI 都有。这是"细节决定体验"的例子。

### 2.8 边沿检测与状态机

UI 交互本质是个状态机:每个 button / hover 区域有 idle / hover / pressed / released 状态。

```
       mouse_enter            mouse_down
IDLE ─────────────→ HOVER ──────────────→ PRESSED
 ↑                                          │
 │       mouse_leave            mouse_up    │
 └────────────────── < ─────────────────────┘
                       (click 触发)
```

实现:`MouseState` 每帧更新,UI 函数读它。Casey 不显式建状态机——immediate-mode 每帧重算,自然反映状态。

```rust
// immediate-mode 状态"逻辑"
fn button(ui: &Ui, label: &str, id: u64) -> bool {
    let hovered = point_in_rect(ui.mouse, id_rect(id));
    let pressed = hovered && ui.mouse.left_down;
    let clicked = hovered && ui.mouse.left_released;  // 边沿
    let color = if pressed { COLOR_PRESSED }
                else if hovered { COLOR_HOVER }
                else { COLOR_NORMAL };
    draw_rect(id_rect(id), color);
    draw_text(label, ...);
    clicked  // 返回"这一帧是否被点击"
}
```

返回 `clicked` 而不是 `pressed` —— 区分"按住"和"完成点击"。游戏 UI 通常用 clicked(松开才触发,允许 cancel——按住鼠标移开 button 再松开,不触发)。

### 2.9 hit-test 的批量化

如果有 100 个 button,hit-test 每帧扫 100 次。优化:把所有 button rect 收集到 vec,鼠标位置二分查找 / BVH 加速。但 UI 元素通常 < 100,linear scan 够快,不值当优化。

```
button A (10, 10, 100, 30)
button B (10, 50, 100, 30)
button C (10, 90, 100, 30)
...

鼠标 (45, 65):
扫 A: not in (65 不在 10..40)
扫 B: in (65 在 50..80) → hit
```

简单 linear scan,只要鼠标命中一个就 break。游戏 UI < 100 个元素,< 1 μs 全扫一遍。

### 3.3.1 字体渲染的三种方案

tooltip 要显示文字,字体方案:

**位图字体**(bitmap font):每个字符硬编码像素图,5x7 或 8x16。优点:零依赖,简单。缺点:固定大小,缩放锯齿。Casey day 188 之前用这个。

**矢量字体**(TTF / OTF):贝塞尔曲线描述字形。`stb_truetype` / `rusttype` / `ab_glyph` 解析。运行时按需栅格化。优点:任意大小,平滑。缺点:复杂,~10000 行代码。

**SDF 字体**(Signed Distance Field):Valve 2007 论文,把字形存为距离场,运行时 shader 渲染。优点:任意缩放,边缘平滑,GPU 友好。缺点:预生成 SDF 复杂。

Casey 在 day 200+ 用矢量字体(ab_glyph),day 188 还在位图。教学优先。

### 3.3.2 多 monitor 与 DPI

鼠标位置在多 monitor / HiDPI 下复杂:

- 多 monitor:鼠标 X 坐标可能跨越 1920+1920 = 3840,但单窗口只看相对自己

winit 提供 `scale_factor()` 报告 DPI:


### 3.5 · 🐧 Linux 系统编程视角(Wayland 的 hover 限制)

Wayland 协议**默认不让应用读全局鼠标位置**——只能收到"鼠标在窗口里"的事件。鼠标离开窗口,事件停。

这影响 profiler UI:**鼠标离开游戏窗口,hover 状态怎么清?** winit 在 Wayland 上会发 `CursorLeft` 事件,你要处理。

```rust
Event::CursorLeft { .. } => {
    mouse_x = -1;  // 标记"鼠标不在窗口"
    mouse_y = -1;
}
```

X11 没这个限制(应用可以订阅 root window 的鼠标事件),但 Wayland 优先安全。这是 Wayland 设计哲学——隔离应用,防间谍行为。


### 3.6 · 🐧 Linux 系统编程视角(perf / ftrace / eBPF)

Linux 内核自带一整套 profiling 基础设施,工业 Linux 性能分析的所有工具都基于它。理解这套设施能让你看 Casey 的 profiler 处于什么位置。

**perf** 是 Linux 内核的标准 profiling 接口。`perf record ./my_game` 跑游戏,perf 通过 `perf_event_open(2)` 系统调用,让内核每隔 N 个 CPU cycle 采样一次指令指针(IP)。采到 N 万个样本后,`perf report` 显示每个函数被采到多少次——按比例还原 CPU 时间分布。这是**统计 sampling**——不记录每次调用,而是按概率采样。

```bash
# 在 Arch 上跑 perf(需要内核 CONFIG_PERF_EVENTS=y,默认开)
sudo pacman -S perf
sudo perf record ./target/release/my_game
sudo perf report --stdio | head -30
# 输出形如:
#   35.00%  my_game  my_game         [.] update_physics
#   18.00%  my_game  my_game         [.] render_geometry
#    8.00%  my_game  libc-2.31.so    [.] memcpy
```

**perf 的两种模式**:
- **Sample-based**:每 N cycle 采样,适合找 hot spot。优点开销小(1% CPU),缺点错过短函数。
- **Trace-based**:每次事件都记录,精确。Casey HH 的 profiler 是 trace-based——每条 begin/end event 都记,精确度高但开销大(~5% CPU)。

**ftrace** 是内核函数级 trace。`/sys/kernel/debug/tracing/` 暴露 trace 点:

```bash
# 启用 sched_switch trace
echo sched_switch > /sys/kernel/debug/tracing/set_event
echo 1 > /sys/kernel/debug/tracing/tracing_on
# 等几秒
cat /sys/kernel/debug/tracing/trace | head
# 看每个 context switch
```

ftrace 是内核 hook——你 enable `sched_switch`,内核每次 context switch 都写一条记录到 ring buffer。这就是 Casey HH profiler 的"内核版"——同样的 ring buffer 数据结构,同样的"事件流"思维。

**eBPF** 是 Linux 内核的革命性技术。eBPF 让你在内核运行安全的 bytecode,自定义 profiling / monitoring 逻辑。eBPF 程序用 C 子集写,编译成 BPF bytecode,加载到内核 hook 点(系统调用、网络包、trace point)。这是内核版"插件"——比 ftrace 灵活,比内核模块安全。

```bash
# 用 bpftrace 做 profiling
sudo pacman -S bpftrace
sudo bpftrace -e 'profile:hz:99 @[stack] = count();'
# 每秒采样 99 次,记录 call stack
```

**bpftrace** 一个脚本 = 一个 profiler。你可以一分钟内写"统计 malloc 调用"、"看哪个进程 IO 最多"、"找 page fault 来源"——这是 Linux 性能分析的现代化武器。

**/proc/[pid]/stat / status / maps** 暴露进程运行时状态:

```bash
# 看你当前进程的 stat(进程的运行时统计)
cat /proc/$$/stat
# 第 14 字段:utime(user CPU time)
# 第 15 字段:stime(kernel CPU time)

# 看 memory mapping
cat /proc/$$/maps
# 输出:地址范围 权限 偏移 设备 inode 文件名
```

工业 profiler 读这些文件得到 cross-process 信息。Casey HH 的 profiler 是 in-process 的(只看自己),不读 /proc——这简化了实现,但看不到 OS 视角。

**Tracy / OPTICK / Superluminal** 是工业 C++ profiler,都用类似架构:ring buffer + thread-local + sample/trace 混合。Tracy 是开源,有 WebSocket UI 跨机器查看;Superluminal 是商业,以"超低 overhead + 时间线视图"著名。Casey HH 的 profiler 简化,但**架构相同**——理解 Casey 的,你就懂了 Tracy 的核心。

### 3.7 · 🦀 Rust 生态视角

Rust 的 profiling 生态有几条主线。

**`tracing` crate** 是 Rust 应用的事实标准 logging / tracing 框架。它结合了 log(级别)和 OpenTracing(span):

```rust
use tracing::{span, info, instrument};

#[instrument]
fn update_physics(dt: f32) {
    // tracing 自动在函数 entry/exit 创建 span
    info!(dt, "physics step");
}

let _span = span!(tracing::Level::INFO, "frame").entered();
update_physics(0.016);
```

`#[instrument]` 是 derive macro——编译时生成 span 创建/退出代码。`tracing` 的 subscriber 决定如何处理 span——log 到文件、发到 tracing UI、profile 等。

**`tracing-tracy`** crate 把 tracing span 转成 Tracy 协议事件。你的 Rust 应用加 tracing + tracing-tracy,就能用 Tracy UI 看 profile。这是 Rust 生态接工业 profiler 的标准方式。

**`puffin`** 是 Rust-native profiler,immediate-mode UI 风格,专为游戏设计:

```rust
puffin::profile_scope!("physics");
update_physics(dt);
// 自动 entry/exit

// 在 egui UI 里
puffin_egui::profiler_window(egui_ctx);
```

puffin 的设计哲学和 Casey HH profiler 几乎一致——in-process、ring buffer、immediate-mode UI。Puffin 是开源,代码可读,是看"Rust 风格 profiler"的范本。

**`measureme`** 是 rustc 用的 profiler,分析 rustc 自己的编译性能。measureme 的设计原则是"低 overhead + 可序列化 + 跨工具分析"——Rust 团队用它优化 rustc。

**Rust 的 `Instant`** 是 std 提供的高精度计时器:

```rust
let start = std::time::Instant::now();
expensive_op();
let elapsed = start.elapsed();
// elapsed 是 Duration,纳秒精度
```

底层在 Linux 是 `clock_gettime(CLOCK_MONOTONIC)`,Windows 是 `QueryPerformanceCounter`,macOS 是 `mach_absolute_time`。这是跨平台高精度时间的标准答案。Casey HH 在不同平台用不同 API(Linux rdtsc、Windows QPC、macOS mach),用 Rust 应该用 `Instant` 抽象。

**Rust 的 atomic 计数**。profiler 多线程时,event push 可能从多个线程同时来。用 `Arc<Mutex<Profiler>`> 是简单方案,但有锁开销。Rust 的 `crossbeam-queue` 提供 lock-free queue,适合高并发 event push。或者用 thread-local buffer + 定期 flush,完全无锁。Tracy 用 thread-local buffer,每线程独立,profiler thread 用 lock-free merge 合并。

**Rust SIMD** 可以加速 collation。如果有 100 万 event 要 collate,用 SIMD(`std::simd` 或 `wide` crate)一次处理 4-8 条 event,duration 计算用 SIMD 减法 + 累加。Tracy 在 collation hot loop 用 AVX2 优化。Rust 的 SIMD 还在稳定化中(unstable `std::simd`),但 `wide` crate 提供稳定的 wrapper。

**Rust 的 `Bytes` / `Arc<[u8]>`** 让 event buffer 零拷贝共享。如果 event buffer 要被 UI thread 读取(同时被游戏 thread 写),用 `Bytes` 引用计数——读 thread 拷贝 Arc,写 thread 替换 Arc 指向新 buffer。这是 lock-free 数据交换的标准模式。

**Rust profiler 的内存安全优势**。C/C++ profiler 大量 ring buffer + 原子操作,容易写错(数据竞争、use-after-free)。Rust 的 borrow checker + Send/Sync + atomic API 让这些错误编译时被捕获。Puffin / measureme 的代码,你可以放心读——Rust 保证内存安全。

## 5 · 对照与变奏

**鼠标在多平台**:

| 平台 | 事件源 |
|---|---|
| Linux X11 | XEvent |
| Linux Wayland | wl_pointer |
| Windows | WM_MOUSEMOVE |
| macOS | NSEvent mouseMoved |

winit 抽象这些,统一成 winit::event::CursorMoved。

### 与 Qt / WPF 的对比

**Qt**(retained-mode C++):

```cpp
// 创建 button,挂事件
QPushButton* btn = new QPushButton("Save");
btn->setToolTip("Save file");  // tooltip 是 widget 属性
QObject::connect(btn, &QPushButton::clicked, []() { /* ... */ });
```

button 对象持续存在,Qt 在每帧 dispatch QEvent 给它。tooltip 由 Qt 自动管理(延迟显示、位置 clamp)。

**WPF**(XAML + C#):

```xml
<Button Content="Save" ToolTip="Save file" Click="OnClick"/>
```

声明式,XAML 编译成对象树。

**Dear ImGui / egui**(immediate-mode):

```rust
ui.button("Save").on_hover_text("Save file");
```

每帧调一次,无持久对象。**casey 的 day 188 是手写版**,API 类似但更精简。

immediate-mode 的优势在 profiler / 游戏开发:数据驱动 UI,无状态同步问题。retained-mode 在传统桌面应用更好(控件多、事件复杂)。

### 与 web 的 hit-testing 对比

Web 浏览器的 hit-testing 极复杂——HTML/CSS 有几百个属性影响 hit region(border-radius、transform、clip-path、overflow、z-index)。浏览器维护 **layer tree** + **hit-test tree**。

游戏 UI 简单——所有元素都是矩形,hit-test 就是 `x >= rx && x < rx + rw && y >= ry && y < ry + rh`。复杂度差几个数量级。这是为什么游戏 UI 不用 HTML/CSS——太重。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:tooltip 显示是"hover 状态触发"还是"每帧检测"?哪种更好?

**参考解答**:
- **每帧检测**:鼠标移动 → 算命中 → 显示
- **hover 事件触发**:进入 → 显示,离开 → 隐藏
- immediate-mode UI 用每帧检测,因为:
  - 简单(无事件队列)
  - 自动同步(数据变了 UI 自动变)
  - 状态少(只一个 mouse pos)
- retained-mode 用事件触发(控件对象有 hover flag)
- immediate-mode 更适合游戏 dev

### Lv2 · 动手实践

**题**:写一个最小 hover demo:
- 模拟鼠标位置(从 stdin 读)
- 在 100x100 的字符 grid 里画一个矩形
- 鼠标在矩形内 → 显示 "hover!"

**参考解答**:

```rust
use std::io::{self, BufRead};

fn main() {
    let grid_w = 100;
    let grid_h = 30;
    let rect_x = 20;
    let rect_y = 5;
    let rect_w = 40;
    let rect_h = 10;

    let stdin = io::stdin();
    for line in stdin.lock().lines() {
        let line = line.unwrap();
        let parts: Vec<&str> = line.split_whitespace().collect();
        if parts.len() != 2 { continue; }
        let mx: i32 = parts[0].parse().unwrap_or(0);
        let my: i32 = parts[1].parse().unwrap_or(0);

        let inside = mx >= rect_x && mx < rect_x + rect_w
                  && my >= rect_y && my < rect_y + rect_h;

        // 画 grid
        for y in 0..grid_h {
            let mut row = String::new();
            for x in 0..grid_w {
                let on_edge = (x == rect_x || x == rect_x + rect_w - 1)
                            && (y >= rect_y && y < rect_y + rect_h)
                           || (y == rect_y || y == rect_y + rect_h - 1)
                            && (x >= rect_x && x < rect_x + rect_w);
                let is_mouse = x == mx && y == my;
                if is_mouse { row.push('@'); }
                else if on_edge { row.push('#'); }
                else { row.push(' '); }
            }
            println!("{}", row);
        }

        if inside {
            println!(">>> HOVER! <<<");
        } else {
            println!("(mouse at {}, {})", mx, my);
        }
        println!("---");
    }
}
```

测试:`echo "30 10\n22 6\n0 0" | cargo run`
