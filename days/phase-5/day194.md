> 上周你在 debug overlay 里加了 30 个 slider——玩家速度、跳跃力、重力、AI 视野角、阴影强度、相机 FOV、BGM 音量。一开始你觉得挺好,每个变量都能调。但第三天你打开 overlay 一看:**30 个 slider 平铺在屏幕上**,找一个特定变量要滚 5 秒。你想"调一下玩家的速度",但在 Combat/Speed、Movement/Speed、Camera/Speed 三个同名 slider 之间反复犹豫。今天 Casey 给 debug 变量装上**层级路径**——每个变量有"完整路径" `Player/Movement/Speed`,UI 自动构建成 tree view,折叠展开按需浏览。这一招看似简单,却是工业级调试工具(inspector、property editor、registry editor)的核心数据结构。

总共 30 个变量。你 day 193 给它们每个一个编译时 GUID(`const SPEED_GUID: u64 = hash("speed")`),然后 UI 用 GUID 查表显示 slider。第一周觉得够用——30 个 slider 平铺在屏幕右侧,你滚一滚总能找到。

第二周,你加了 audio reverb 系统,又要 5 个变量(reverb decay、room size、wet/dry mix 等)。第三周,你给敌人加了三种 AI 行为,每种又有 4 个参数。变量数到 50。第四周,你说"我们做一个 boss 战,boss 有 10 个 phase,每个 phase 独立参数"——变量数到 150。

到第 150 个变量时,debug overlay **没法用了**。你想找 boss_phase_3 的攻击间隔,要在 150 个 slider 里翻 30 秒。你按 Ctrl+F 搜"interval",跳出 8 个匹配——"player_attack_interval"、"enemy_chase_interval"、"boss_phase_1_interval"...名字相似,你不知道哪个是你想要的。

工业级 debug 工具的解决方案叫 **hierarchical naming**(层级命名)。你不叫变量 `boss_phase_3_attack_interval`,你叫它 `Boss/Phase3/Attack/Interval`。这一串斜杠分隔的路径,本质上是个**树形结构**——`Boss` 是根,`Phase3` 是 Boss 的子,`Attack` 是 Phase3 的子,`Interval` 是 leaf。UI 把它渲染成 **tree view**(折叠展开):你先点 `Boss` 展开,再点 `Phase3` 展开,再点 `Attack` 展开,看到 `Interval` slider。

层级命名的好处有四条:

**第一,可导航**。150 个变量平铺,找不到;组织成 4 层深的树,每层只有 5-10 个节点,你从根开始一步步深入,几秒定位。这是大脑处理结构化信息的本能——目录树比扁平列表好用,文件夹比桌面好用。

**第二,可折叠**。你今天调 boss,其他子树(Player / AI / Physics)折叠掉,屏幕清爽。明天调 player,反过来。immediate-mode UI 每帧重画,折叠状态用 path 字符串作 ID 持久化,改了变量自动反映。

**第三,命名去歧义**。`Combat/Speed` 和 `Movement/Speed` 不冲突——它们在不同子树里,完整路径不同。这避免了"`speed` 到底是哪个 speed"的歧义。

**第四,自动分组**。新加变量 `Boss/Phase4/Health` 时,UI 自动放到 `Boss/Phase4/` 节点下——你不用手写"放到 boss 组"的代码。路径字符串自带分组语义。

实现层级命名的核心算法叫 **trie**(也叫 prefix tree / radix tree)。trie 把多个**共享前缀**的字符串存成一棵树——`Player/Movement/Speed`、`Player/Movement/Jump`、`Player/Combat/HP` 共享前缀 `Player/`,所以它们是 `Player` 节点的子。这个数据结构在 1960 年代发明,今天用在 DNS 服务器、路由表、auto-complete、IP routing、文件系统——**任何需要"按字符串前缀组织"的场景**。Casey 今天在 debug 变量上用它,是 trie 的经典应用。

层级命名的另一关键技术是 **运行时反射**(runtime reflection)——程序在运行时"知道自己的字段"。C# / Java / Python 内置反射;C++ 没有但 Unreal 用 UHT(Unreal Header Tool)生成;Rust 也没有但 `bevy_reflect` 提供 derive macro。Casey 在 HH 里手写了一个简化版——用 macro 自动生成 `debug_vars()` 方法,返回 `Vec<(path, value)>`。这是把 Rust struct 转成"运行时可枚举字段"的最小可行方案。

**学完今天,你应该能**:
- 解释为什么"扁平变量 + 全名搜索"不如"层级路径 + tree view"
- 实现 trie insert / lookup / delete 算法,从 `A/B/C` 字符串构建树
- 解释 immediate-mode tree view 的渲染原理(递归 + ID-based expand state)
- 看 Unreal UPROPERTY / Unity Inspector / bevy_reflect 的设计,识别"反射"在不同语言的实现
- 给自己的 Rust 游戏设计一套 debug variable 系统,支持任意层级的路径命名

## 2 · 心智模型

### 类比:操作系统的文件系统

文件系统是经典的层级组织:`/home/user/docs/file.txt`。每段是目录,最后是文件。debug 变量一样:`Player/Movement/Speed` 是"目录 Player → 子目录 Movement → 变量 Speed"。

文件系统用 **inode + dentry** 实现:每级目录有 inode(元数据),dentry 链接父目录和子文件。debug 变量树可以借鉴——用 HashMap<String, Node> 表示目录,Node 是 leaf 变量或子目录。

### 2.0 Trie / Radix tree 的核心思想

把多个字符串**共享前缀**地存:

```
"Player/Movement/Speed"  ┐
"Player/Movement/Jump"   ├─ 共享前缀 "Player/Movement/"
"Player/Combat/HP"       ┘
```

树形:

```
root
└── Player
    ├── Movement
    │   ├── Speed (leaf)
    │   └── Jump (leaf)
    └── Combat
        └── HP (leaf)
```

每个内部节点 = 共享前缀,叶子 = 完整路径。**空间效率**:N 个长度 L 的字符串,共享前缀让总节点数 < N×L。

应用:
- **DNS 服务器**:域名树
- **路由表**:URL 路径
- **auto-complete**:单词前缀
- **debug 变量**:Casey 这里

### 2.0.1 构建 Trie 的算法

```rust
#[derive(Default)]
struct TrieNode {
    children: HashMap<String, TrieNode>,
    value: Option<f32>,  // leaf 才有
}

impl TrieNode {
    fn insert(&mut self, path: &str, value: f32) {
        let mut node = self;
        for part in path.split('/') {
            node = node.children.entry(part.to_string()).or_default();
        }
        node.value = Some(value);
    }
}
```

每个变量调用 `insert("Player/Movement/Speed", 5.0)`。N 个变量 = N 次插入,每次 O(path 长度)。

### 2.0.2 tree view 的渲染

immediate-mode tree view:

```rust
fn draw_tree(ui: &mut Ui, node: &TrieNode, path: &str, expanded: &mut HashSet<String>) {
    for (name, child) in &node.children {
        let full_path = format!("{}/{}", path, name);
        let is_leaf = child.value.is_some();

        if is_leaf {
            if let Some(v) = &child.value {
                ui.slider(name, v);  // 调整值
            }
        } else {
            let is_expanded = expanded.contains(&full_path);
            if ui.tree_node(name, is_expanded) {
                if !is_expanded { expanded.insert(full_path.clone()); }
                draw_tree(ui, child, &full_path, expanded);  // 递归
            } else {
                expanded.remove(&full_path);
            }
        }
    }
}
```

每帧重画,expanded 状态用 ID(路径字符串)持久化。这就是 immediate-mode 的精髓——UI 结构跟着数据走,改了变量自动反映在树上。

### 2.1 反射式变量注册

Casey 用 macro 自动注册变量:

```rust
#[derive(Debug)]
struct PlayerVars {
    speed: f32,
    jump: f32,
    hp: i32,
}

// macro 自动生成
impl PlayerVars {
    fn debug_vars(&self) -> Vec<(String, DebugValue)> {
        vec![
            ("Player/Speed".to_string(), DebugValue::F32(self.speed)),
            ("Player/Jump".to_string(), DebugValue::F32(self.jump)),
            ("Player/HP".to_string(), DebugValue::I32(self.hp)),
        ]
    }
}
```

macro 自动生成 `debug_vars`,UI 自动遍历。这就是**反射**(reflection)的简化版——程序运行时知道自己的字段。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏 editor 的 **inspector / property tree** 是 debug 变量层级的工业级实现。让我对比四大引擎,你会看到 Casey 的方案和它们异曲同工。

**Unreal Engine 5** 的 Details Panel 是层级 inspector 的标杆。选中一个 Actor,右侧 Details Panel 自动列出所有 UPROPERTY 字段,按 `Category` metadata 分组,每组可折叠。Unreal 用 **UHT(Unreal Header Tool)** 预处理头文件——你写 `UPROPERTY(EditAnywhere, Category="Movement|Speed") float MaxSpeed = 600.0f;`,UHT 看到 `UPROPERTY` macro,生成 reflection 代码,记录字段名、类型、Category、editor widget。Editor 运行时调 `TFieldIterator<UProperty>` 遍历,自动渲染合适 widget(float → slider、FColor → color picker、TArray → list)。这套系统的核心是 **UClass**——每个 C++ 类对应的 reflection metadata,运行时可枚举字段。代码量巨大(UE5 整个 reflection 系统 5+ 万行),但用起来"零摩擦"——你加个字段,editor 自动认识。

**Unity** 的 Inspector 类似但用 C# 反射。C# 内置 `System.Reflection`,Unity 不需要 codegen——选中 GameObject,Inspector 调 `type.GetFields()`,对每个 `[SerializeField] private` 字段渲染 editor。Unity 的优势是**语言原生**(C# 反射比 C++ codegen 简单),劣势是**反射慢**(运行时 type lookup,比直接字段访问慢 100 倍——但 editor 不是 hot loop,不在乎)。Unity 还有 `PropertyDrawer` ——你给某个 type 写自定义 editor,完全控制渲染。Unity 的层级组织用 `[Header("Movement")]` attribute,给字段加"小标题",本质上是一层分组(不是树)。

**Godot 4** 用 `@export` annotation + ` @_export_group` ,语法接近 Unity 但 Godot 节点系统让 inspector 更"自然"——节点树本身是层级,每个节点的 inspector 显示其字段,父节点的 inspector 可"穿透"看子节点。

**Bevy (Rust)** 用 `bevy_reflect` crate,实现 Rust 风格的反射:

```rust
use bevy_reflect::Reflect;

#[derive(Reflect)]
struct Player {
    #[reflect(category = "Movement")]
    speed: f32,
    #[reflect(category = "Movement")]
    jump_force: f32,
    #[reflect(category = "Combat")]
    hp: i32,
}

// 运行时遍历字段
let player = Player { speed: 5.0, jump_force: 7.0, hp: 100 };
let reflect = &player as &dyn Reflect;
for field in reflect.iter_fields() {
    println!("field: {:?}", field);
}
```

`bevy_reflect` 用 derive macro 在编译时生成 Reflect trait 实现——这是 Rust 没有"语言原生反射"的工程补偿。优点是类型安全(编译时检查)、性能好(不靠 vtable);缺点是要 derive(忘加 `#[derive(Reflect)]` 字段就不能枚举)。

Casey 的方案最朴素——手写 macro 生成 `debug_vars()` 方法。比 Unreal UHT 简单(没有 codegen 工具链),比 bevy_reflect 简单(没有 trait 体系),适合 debug UI 这个"非 critical path"的场景。**取舍**:Casey 牺牲了"自动"——你加字段要手写 macro 调用;换来了"可控"——你完全决定哪些字段暴露给 UI。

**你能学到的迁移**:你的 Rust 游戏项目,debug UI 用 Casey 风格的手写注册——加 100 行代码,够用。等项目成熟,要发正式 editor(让 modder 改字段),换成 `bevy_reflect`——享受自动反射但代码依赖增加。

### 3.2 · 🎨 图形学视角

tree view 在图形学里有些不太显眼但关键的细节。让我深入几个。

**缩进渲染** 是 tree view 的视觉基础。每层深度缩进 N 像素,典型 N=16 或 20。Casey HH 用 `"  ".repeat(depth)`(两个空格 × depth)生成缩进——简单但只在 monospace 字体下好看。工业 UI 用 `padding-left = depth * indent_size`,支持任意字体。

**展开 / 折叠图标** 是 tree view 的交互基础。Casey 用 ASCII 字符:`▶`(折叠)、`▼`(展开)。工业 UI 用 vector icon——SVG path 画三角形,可缩放、可着色。egui / iced 都内置 tree icon。

**绘制三角形 vs 字符**:
```rust
// Casey 风格:用 Unicode 字符
ui.label(if expanded { "▼" } else { "▶" });

// egui 风格:画三角形
let triangle = if expanded {
    Triangle::down(rot_rect)
} else {
    Triangle::right(rot_rect)
};
painter.add(Shape::triangle(triangle, color::WHITE));
```

三角形画法更快(不依赖字体)、更可控(可旋转、可动画),但要自己写几何。Unicode 字符省事但依赖字体渲染。

**virtualized tree** 是大型树的性能优化。如果你的 debug 变量树有 10000 个节点(大型游戏的真实场景),全部渲染一遍——每帧 50ms——卡顿。virtualization 只渲染可见节点(视口内的 ~50 个),通过 `scroll_offset` 和 `node_height` 算出可见范围。这是 list view 的标配技术。Casey HH 不做 virtualization,因为 debug UI 节点数 < 1000,全渲染 5ms,够快。

**tree animation**(展开动画)是现代 UI 的 polish。点击展开按钮,子节点不是瞬间出现,而是从 height=0 缓动到 height=full。这是 user experience 的重要细节——动画让 UI 感觉"有响应"而不是"突兀"。egui 的 `CollapsingHeader` 支持 `animate` 选项,内部用 `lerp` 在 0..1 之间插值 height。

**hit testing 树节点** 是 layout 之后的步骤。鼠标点击 (x, y),哪个节点被点?immediate-mode UI 每帧记录所有节点的 rect,点击时遍历找包含 (x, y) 的。tree 节点的 rect 是 `(indent_x + icon_width, current_y, label_width, row_height)`。Casey 在 HH 里手写这个 hit testing,~20 行代码。

**键盘导航**(上下方向键、左右展开折叠)是 accessibility 的要求。tree view 应该支持纯键盘操作——上下移焦点、左折叠、右展开、Enter 编辑。这是 web `role="tree"` ARIA 标准的内容。Casey HH 不做键盘导航,但商业 UI 必须做——否则残疾人无法用你的工具。

### 3.3 · 🐧 Linux 系统编程视角

Linux 系统里**树形数据结构无处不在**。理解这些,你会看到 day 194 的 trie 不是孤立技术,而是 Unix 哲学的体现。

**文件系统** 是最经典的层级——`/home/user/docs/file.txt`。Linux 内核用 **dentry cache**(目录项缓存)实现:`struct dentry` 是路径段,链成树;每个 dentry 指向 `struct inode`(实际文件元数据)。当你 `open("/home/user/foo")`,内核 walk dentry 树:`/` → `home` → `user` → `foo`,每步查 dentry cache。这就是 trie 的内核实现——共享前缀(`/home/user/`)只 walk 一次。

```bash
# 看你当前进程的文件描述符(一个 procfs 树)
ls -la /proc/self/fd/
# 输出 0 -> /dev/pts/0 (stdin)
#     1 -> /dev/pts/0 (stdout)
#     2 -> /dev/pts/0 (stderr)
#     ...

# 看进程树(系统所有进程的 trie)
pstree -p | head -20
# init(1)──systemd-journal(430)──...
#         ──systemd-udevd(458)
#         ──dbus-daemon(510)
```

**procfs** (`/proc`) 是用户态的 trie。内核把所有运行时信息组织成 `/proc` 下的文件——`/proc/cpuinfo` 是 CPU 信息,`/proc/[pid]/status` 是进程状态,`/proc/[pid]/fd/` 是文件描述符。这是 "everything is a file" 哲学的体现——树形结构让信息有组织,工具(cat / grep / awk)统一处理。

**sysfs** (`/sys`) 类似但用于设备模型。`/sys/class/net/eth0/statistics/rx_bytes` 是 eth0 网卡接收字节数——一个 7 层深的路径,每层是 kernel 内部数据结构的对应。读这个文件,kernel walk 内部树,把对应字段暴露出来。这就是**层级命名的力量**——给 kernel 内部状态一个稳定的字符串路径,用户态工具就能访问。

**cgroup v2** 也是树形。`/sys/fs/cgroup/myapp/cpu.max` 限制 myapp 这个 cgroup 的 CPU。cgroup 树允许嵌套——`myapp/children/` 子组继承父组限制。这是 tree 数据结构的典型应用。

**D-Bus** 是 Linux 桌面的 IPC 系统,服务名是层级路径:`org.freedesktop.DBus.Properties`、`org.gnome.Shell.Introspect`。D-Bus 内部用 trie 组织服务名,匹配调用时高效查找。

**XML / HTML DOM** 是 web 的树。HTML parser 把 `<html><body><div><p>` 解析成 DOM 树,CSS selector 在树上查找。Chrome 的 DOM 树用类似 trie 的优化——按 tag name、class、id 分组,selector 匹配 O(1) 而非 O(N)。

**JSON** 是嵌套对象——`{"a": {"b": {"c": 1}}}`。Rust 的 `serde_json::Value` 是 enum(Object/Array/String/...),递归结构。访问 `obj["a"]["b"]["c"]` 是 walk 路径。如果用 trie 优化,共享前缀的 JSON 路径访问 O(1)。

Casey 的 debug 变量 trie,本质是把这些 Unix/web 经典模式用到游戏 debug UI 上——**给运行时状态一个稳定的字符串路径,UI 自动渲染成 tree**。这种思想一旦内化,你看任何系统都能识别"这是树"。

### 3.4 · 🦀 Rust 生态视角

Rust 的 tree 数据结构有几种实现,每种反映 Rust ownership 系统的取舍。让我深入对比。

**Box<Node>** 是最直接的——每个节点 own children:

```rust
struct Node {
    name: String,
    children: Vec<Box<Node>>,
    value: Option<f32>,
}
```

优点:内存自动管理(节点 drop 时 children 一起 drop);cache 友好(连续 Vec);简单。缺点:**不能从子节点回溯父节点**(parent reference 是循环引用,Rust 不允许)。如果你只需要从根到叶的访问,Box<Node> 是最好选择。

**Rc<RefCell<Node>>** 是共享 ownership:

```rust
struct Node {
    parent: Option<Weak<RefCell<Node>>>,  // 弱引用避免循环
    children: Vec<Rc<RefCell<Node>>>,
    value: Option<f32>,
}
```

Rc(reference count)允许多 owner;RefCell 允许运行时 borrow 检查(避开编译时检查)。优点:双向遍历(子→父→子)。缺点:**运行时 panic 风险**(RefCell borrow 冲突时 panic)、性能开销(Rc 原子计数、RefCell 运行时检查)、内存泄漏风险(Weak 用错就成 Rc 循环)。Rust 社区一般避免 Rc<RefCell>,除非真的需要双向。

**Arena + NodeId** 是 ECS 风格——所有节点存在一个大 Vec,节点之间用 index 引用:

```rust
struct Arena<T> {
    nodes: Vec<T>,
}

struct Node {
    parent: Option<NodeId>,
    children: Vec<NodeId>,
    name: String,
    value: Option<f32>,
}

type NodeId = usize;  // index into Arena<Node>
```

优点:**零循环引用问题**(NodeId 是数字,不参与 borrow 检查)、cache 极友好(连续内存)、可序列化(NodeId 是数字,JSON 直接存)、可删除(从 Vec 删,其他 NodeId 还有效,只要用 generational index)。缺点:**手动管理生命周期**(删除节点要手动从 parent.children 移除)。Bevy ECS、egui 内部、rnix(JSON editor)都用 arena + id 模式。

**HashMap<String, Node>** 是 Casey 在 HH 用的:

```rust
struct TrieNode {
    children: HashMap<String, TrieNode>,
    value: Option<f32>,
}
```

每个节点的 children 用 HashMap,key 是子节点名字符串。优点:**API 简洁**(`children["Player"]`)、动态增删容易、无 ownership 复杂度。缺点:**HashMap 开销**(hash 计算 + bucket lookup)、内存碎片(每个 HashMap 独立 allocation)、无序(用 BTreeMap 才有序)。适合 tree 浅、性能不敏感的场景——debug UI 完美符合。

**Rust tree 库**:
- `id-tree`:arena + id 风格
- `indextree`:基于 arena 的 tree
- `ego-tree`:带游标的 tree
- `bevy_ecs` 的 hierarchy:Parent/Children component,纯 ECS 风格

**Rust 反射库**:
- `bevy_reflect`:derive-driven,Bevy 生态主流
- `serde::Serialize`:不是反射但能"遍历字段"
- `frunk`:HList 风格,类型级编程
- 手写 macro:Casey 风格,最简也最可控

**immediate-mode tree view 的 ID 系统**:
immediate-mode UI 没有持久 widget 对象,但 tree 的 expand state 要跨帧持久化。egui / imgui 用 **ID-based state**——每帧给 tree node 一个唯一 ID(通常是路径字符串的 hash),expand state 存在 `HashMap<Id, bool>`。这样:
- 第一帧 `ui.tree_node("Player/Movement")` 创建 ID=hash("Player/Movement"),默认 collapsed
- 用户点击展开,框架记 `expanded.insert(id, true)`
- 下一帧 `ui.tree_node("Player/Movement")` 同样 ID,框架查 expanded,知道是 expanded,渲染 children

这种 ID 系统是 immediate-mode 的精髓——**无对象、有状态、按 ID 关联**。Casey HH day 194 第一次引入这套机制,后续 day 195+ 全部基于它。

**Rust 的字符串 interning**:tree 的节点名字符串可能重复出现(`Player/Movement/Speed` 和 `Player/Movement/Jump` 共享 `Movement`)。Rust 的 `string_interner` / `lasso` crate 提供 string interning——所有字符串存进一个池,返回 Symbol(u32),后续比较 u32 比较字符串快 10 倍。工业 debug UI 大量用 interning。

所有这些都是**树形结构的不同表示**。

### Unreal 的 Reflection 系统

Unreal 用 UHT(Unreal Header Tool)预处理头文件,生成 reflection 代码:

```cpp
// .h
UCLASS()
class APlayer : public AActor {
    GENERATED_BODY()
public:
    UPROPERTY(EditAnywhere, Category = "Movement")
    float Speed = 5.0f;
};
```

UHT 看到 `UPROPERTY`,生成 `Player::StaticClass()`、`PropertyIterator` 等。Editor 用这些 API 列字段、序列化、修改。

Rust 没有 UHT 等价物。`#[derive(Debug)]` 是简版,但没有"枚举所有字段"的 API。Casey 用 macro 自己生成,工程量大但灵活。

### Bevy Reflect crate

`bevy_reflect` 提供 Rust 的运行时反射:

```rust
use bevy_reflect::Reflect;

#[derive(Reflect)]
struct Player { speed: f32, hp: i32 }

let p = Player { speed: 5.0, hp: 100 };
// 运行时遍历字段
for (name, value) in p.iter_fields() {
    println!("{}: {:?}", name, value);
}
```

`#[derive(Reflect)]` 自动生成 `Reflect` trait 实现。但**有 overhead**(vtable 调用),hot loop 不用。

### Inspector / Toolbar / Property Tree

游戏 editor 的标准 UI 组件:
- **Inspector**:选中对象,显示所有字段(Unity / Unreal / Godot)
- **Toolbar**:顶栏按钮
- **Property Tree**:左侧树(Outliner)
- **Viewport**:中间 3D 视图

Casey 的 debug UI 是 inspector 的简化版——选中"调试分类",看里面所有变量。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么用路径字符串("Player/Movement/Speed")而不是 struct(`Player.Movement.Speed`)?字符串有什么好处?

**参考解答**:
- 字符串可以 hash 成 GUID(编译时 / 运行时一致)
- 字符串可以 split 成段,自动构建树
- 字符串容易序列化(JSON / toml)
- 字符串可拼接(`format!("{}/{}", parent, child)`)
- 缺点:运行时分配,弱类型

struct 的优缺点反过来:强类型,但加新节点要改代码。

### Lv2 · 动手实践

**题**:写一个 DebugNode 树,插入几个路径,然后 print 树。

**参考解答**:

```rust
use std::collections::HashMap;

#[derive(Default, Debug)]
struct DebugNode {
    name: String,
    children: HashMap<String, DebugNode>,
    variables: Vec<String>,
}

impl DebugNode {
    fn insert(&mut self, path: &str) {
        let parts: Vec<&str> = path.split('/').collect();
        let mut current = self;
        for part in &parts[..parts.len() - 1] {
            current = current.children.entry(part.to_string()).or_insert_with(|| DebugNode {
                name: part.to_string(),
                ..Default::default()
            });
        }
        if let Some(leaf) = parts.last() {
            current.variables.push(leaf.to_string());
        }
    }

    fn print(&self, depth: usize) {
        let indent = "  ".repeat(depth);
        for (_, child) in &self.children {
            println!("{}{}/", indent, child.name);
            child.print(depth + 1);
        }
        for var in &self.variables {
            println!("{}{}", indent, var);
        }
    }
}

fn main() {
    let mut root = DebugNode::default();
    root.insert("Player/Movement/Speed");
    root.insert("Player/Movement/Jump");
    root.insert("Player/Combat/HP");
    root.insert("AI/Vision/Fov");
    root.insert("AI/Vision/Range");

    root.print(0);
}
```

**预期输出**:

```
Player/
  Movement/
    Speed
    Jump
  Combat/
    HP
AI/
  Vision/
    Fov
    Range
```
