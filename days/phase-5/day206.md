# Day 206 · 实现内省

> 鼠标选中实体后,UI 要显示所有字段。手写"显示 Player 字段"代码很烦,因为 Player 有 20 个字段。今天 Casey 实现内省(introspection):程序运行时**枚举自己的结构体字段**,自动渲染。

## 0 · 为什么要有这一天

让我们把镜头拉到一个具体的开发场景。

你的游戏 entity 有 30 个字段:id、pos.x、pos.y、vel.x、vel.y、hp、max_hp、mp、attack、defense、speed、kind、faction、level、xp、inventory_size、is_alive、ai_state、ai_target_id、animation_frame、animation_time、sprite_id、tint_color、scale、rotation、collision_radius、movement_state、last_damage_time、last_attacker_id、status_effects。

每个字段都要在 debug inspector 显示。Day 205 的 `draw_entity_inspector` 写出来长这样:

```rust
fn draw_entity_inspector(ui: &mut Ui, e: &Entity) {
    ui.label(&format!("id: {}", e.id));
    ui.label(&format!("pos.x: {}", e.pos.x));
    ui.label(&format!("pos.y: {}", e.pos.y));
    ui.label(&format!("hp: {}", e.hp));
    ui.label(&format!("max_hp: {}", e.max_hp));
    ui.label(&format!("mp: {}", e.mp));
    // ... 30 行
}
```

这 30 行**复制粘贴的样板代码**,看起来无害,但埋了三颗地雷:

**第一,加字段要改两处**。你给 Entity 加一个新字段 `stamina`,要改:(1) struct 定义,(2) inspector 函数。容易忘第二处——stamina 字段加进去了,但 inspector 不显示。开发两周后你想调 stamina,打开 inspector 找不到,才发现没登记。

**第二,改字段类型两处不同步**。原本 hp 是 i32,你改成 f32(支持小数伤害)。改 struct 但忘了改 inspector,inspector 里 `format!("{}", e.hp)` 还在 format f32 成 i32 格式——可能显示截断,可能编译错。

**第三,30 个 entity 类型,每个都要写 inspector**。Player、Enemy、NPC、Projectile、Item——每个 struct 30 个字段,5 个类型就是 150 行 inspector 样板。维护噩梦。

**工业界的解法叫 introspection(内省)**:让程序**运行时枚举自己的字段**——自动列出字段名、类型、值。inspector 函数变成"通用":给任何 struct,自动渲染所有字段。加字段时只改 struct,inspector 自动跟上。

这是 Unity Inspector、Unreal Details Panel、Blender Properties 的核心技术——它们之所以能"选中任意对象,自动显示所有字段",全靠 introspection。

**为什么这件事不平凡?**

不同语言对 introspection 的支持天差地别。Java / C# / Python 有**完整的运行时反射**——`Class.getDeclaredFields()` 直接列出字段。但这些反射慢(method invocation 通过反射 ~100ns vs 直接 ~5ns),不适合游戏 hot path。

C/C++ 没有 introspection——RTTI 只能查类型(`typeid`),不能枚举字段。Casey 在 HH 用**宏生成元数据表**模拟:`MEMBER(u32, id)` 宏展开成 struct 字段 + 元数据表(`{"id", TYPE_U32, offsetof(...)}`)。元数据表是静态数据,运行时 O(1) 查。

Rust 用**过程宏(derive macro)**:`#[derive(Reflect)]` 让编译器在编译期生成 introspection 代码。这是 Rust 比 C++ 工程化的重要优势——无需外部工具,语言原生支持。

今天 Casey 在 C 里手写 introspection(宏 + offset table)。我们 Rust 版用 trait + 手写 inspect(教学),最后展示 bevy_reflect 的工业版(proc macro)。

**学完今天,你应该能**:
- 解释 introspection 解决的根本问题("加字段要改两处")
- 写出 `Inspectable` trait + 手动实现,给任意 struct 加 introspection
- 理解 `offsetof` 在 C/C++ 和 Rust 中的实现差异
- 看懂 bevy_reflect / serde 的 `#[derive(...)]` 宏在做什么
- 评估 introspection 的性能代价(运行时反射 vs 编译期生成)
- 知道为什么 Java/C# 反射慢,Rust derive 快(编译期 vs 运行时)
- 理解 Qt MOC / Unreal UHT / Rust proc macro 这三种"反射代码生成器"在抽象上是同一个东西

## 1 · Casey 今天做了什么

Casey 这一天设计 introspection 系统:

1. **定义 DebugValueView**。这是一个 enum,描述"一个字段如何显示"——Float / Int / Vec2 / String / Color 各一个 variant,带 name + value + 可选 min/max(用于 slider)。

2. **定义 Inspectable trait**。任何类型实现 `fn inspect(&self) -> Vec<DebugValueView>`,返回所有字段的视图列表。这是 introspection 的核心抽象。

3. **为每个游戏类型实现 Inspectable**。Player、Enemy、Item——每个 struct 写一个 inspect 方法,逐字段登记。C 里 Casey 用宏(CASEY_MEMBER)生成这个表,Rust 翻译版可手写(教学简化)或用 bevy_reflect(工业)。

4. **通用 inspector UI**。`draw_inspector(item: &dyn Inspectable)` 接收任何可内省对象,自动渲染所有字段。这是 introspection 的红利——一个函数服务所有 struct。

5. **加 Editable trait(可选)**。inspect 返回只读视图,Editable trait 允许"按字段名改值"。UI 编辑时调 `entity.edit("speed", Float(7.5))`。Day 207 会深入。

6. **反思边界**。Casey 提到 introspection 不应用于 hot path——vtable 调用慢,字段访问通过指针解引用慢。Debug UI 不在 hot path,可用。物理 update 在 hot path,不能用 reflection 取字段——直接 `entity.pos.x` 比 `entity.get_field::<f32>("pos.x")` 快 10 倍。

这集产出 introspection 基础设施,Day 207 用它做完整的 entity editor。

## 2 · 心智模型

### 2.1 费曼类比:医院的体检报告

想象一个医院。病人走进来,医生要给一张体检报告。报告内容是什么?身高、体重、血压、心率、血糖、血脂——这些都是**人体的"字段"**。

**朴素的做法**:每个病人类型(成人、儿童、老人)写一份专门的"报告生成函数"。函数硬编码"打印身高、打印体重、打印血压"。但人体是统一的——所有病人都有身高,所有都有体重。如果医院加一个新检查项(比如血氧),要改所有报告函数。

**introspection 的做法**:让"病人类"自己描述"我有哪些字段"——`patient.fields()` 返回 `[(name: "height", value: 175), (name: "weight", value: 70), ...]`。报告函数变成通用——给任何病人,自动遍历所有字段并打印。加新检查项只需改"病人类"的字段列表,报告函数自动跟上。

这是医院系统的核心抽象:**自描述数据(self-describing data)**——每个对象知道自己有什么字段。

程序的 introspection 一模一样:**struct 自己描述"我有哪些字段"**。inspector UI 通用化,加字段只改 struct,UI 自动跟上。

这个类比的关键洞察:introspection 不是"高级魔法",是**把"字段信息"从代码注释提升到运行时数据**。原来字段信息只存在于编译期(struct 定义),运行时丢失。introspection 把它保留下来,让程序"运行时还能看到自己"。

### 2.2 反射 vs 内省:概念辨析

这两个词经常混用,但严格区分:

**反射(reflection)**:程序运行时访问自己的**全部**类型信息——字段名、类型、方法、属性,还能**调用方法**。Java/C#/Python 有完整反射。

```java
// Java reflection
Class<?> clazz = player.getClass();
Method m = clazz.getMethod("setSpeed", float.class);
m.invoke(player, 7.0f);  // 反射调用方法
```

**内省(introspection)**:只**读**访问——看字段名、类型,不调用方法。Rust 用 trait + macro 实现简化版。Casey Day 206 的"内省"严格说是只读 introspection。

```rust
// Rust introspection(只读)
for (name, value) in player.inspect() {
    println!("{}: {:?}", name, value);
}
```

实务中两个词经常互换,但工程实现差异大——reflection 慢(支持运行时调用方法),introspection 快(只读元数据)。

### 2.3 从零推导:C 的 offsetof trick

让我们看 C 程序员怎么做 introspection,这是 Casey 在 HH 里用的方法。理解 C 的 trick 能让你看清 introspection 的本质。

**问题**:C 的 struct 在运行时是"裸字节"——没有字段名,只有偏移量。`Player { float x; float y; int hp; }` 在内存里是 `[4 bytes][4 bytes][4 bytes]` 共 12 字节,没有"x"、"y"、"hp"这些名字。

**解法**:**预生成元数据表**——`{"x", offsetof(Player, x), TYPE_F32}`。元数据表是静态数据,运行时 O(1) 查。

```c
typedef struct {
    const char* name;
    size_t offset;
    MemberType type;
} MemberDef;

MemberDef player_members[] = {
    {"x",  offsetof(Player, x),  MEMBER_F32},
    {"y",  offsetof(Player, y),  MEMBER_F32},
    {"hp", offsetof(Player, hp), MEMBER_I32},
    {NULL, 0, 0}  // 哨兵
};
```

`offsetof(Player, x)` 是 C 标准库宏,编译期算出 x 在 Player 中的字节偏移(=0)。y 偏移 4(前面 4 字节 float)。hp 偏移 8。

**通过 offset 访问字段**:

```c
void* player_ptr = &some_player;
MemberDef* m = &player_members[0];  // x 字段
float x_value = *((float*)((char*)player_ptr + m->offset));
// = *(float*)(player_ptr + 0) = player.x
```

通过 `pointer + offset` 算字段地址,cast 成正确类型,读值。这是 C 的"reflection"——纯算术,无运行时类型查询。

**遍历所有字段**:

```c
for (MemberDef* m = player_members; m->name != NULL; m++) {
    printf("%s: ", m->name);
    switch (m->type) {
        case MEMBER_F32:
            printf("%f", *((float*)((char*)player_ptr + m->offset)));
            break;
        case MEMBER_I32:
            printf("%d", *((int*)((char*)player_ptr + m->offset)));
            break;
    }
    printf("\n");
}
```

通用遍历——给任何带元数据表的 struct,自动 dump 所有字段。这就是 Casey 在 HH 用的方法。

**为什么这有效?** 因为 C struct 的**内存布局**是确定的(`#[repr(C)]` in Rust)。struct 等价于"按声明顺序排列的字节数组"。offsetof 是编译期常量。`pointer + offset` 直接定位字段。

**陷阱**:Rust 默认布局不保证(编译器可能重排字段优化),所以 `offsetof` 默认 unsafe。`#[repr(C)]` 强制 C 兼容布局,offsetof 才安全。

### 2.4 Rust 的 introspection 方案谱

Rust 提供多种 introspection 实现,各有取舍。

**方案 1:手写 trait(Casey HH 翻译版)**:

```rust
trait Inspectable {
    fn inspect(&self) -> Vec<DebugValueView>;
}

impl Inspectable for Player {
    fn inspect(&self) -> Vec<DebugValueView> {
        vec![
            DebugValueView::Float { name: "x", value: self.x, min: 0.0, max: 100.0 },
            DebugValueView::Float { name: "y", value: self.y, min: 0.0, max: 100.0 },
            DebugValueView::Int { name: "hp", value: self.hp as i64 },
        ]
    }
}
```

简单,直接,无 unsafe。缺点:**加字段要手改 inspect**(就是 Casey 想避免的)。

**方案 2:bevy_reflect(proc macro)**:

```rust
#[derive(Reflect)]
struct Player { x: f32, y: f32, hp: i32 }

// 自动生成
let p = Player { x: 1.0, y: 2.0, hp: 100 };
for field in p.iter_fields() {
    println!("{}: {:?}", field.name(), field.value());
}
```

`#[derive(Reflect)]` 编译期生成 Reflect trait 实现。加字段只需改 struct,derive 自动跟上。**这是 Rust 的工业级 introspection**。

**方案 3:serde(Serialize/Deserialize)**:

```rust
#[derive(Serialize)]
struct Player { x: f32, y: f32, hp: i32 }

let json = serde_json::to_string(&player)?;
// {"x":1.0,"y":2.0,"hp":100}
```

serde 生成序列化代码,等价于"遍历所有字段写 JSON"。可以借这套机制做 introspection——`serde_json::to_value(&player)` 返回 `Value::Object`,可以 iterate fields。

但 serde 侧重**序列化**(把数据写到外部格式),不侧重"读单个字段"或"按字段名改值"。Debug inspector 两者都要。

**方案 4:offset_of! + unsafe 指针访问**(C 风格):

```rust
#[repr(C)]
struct Player { x: f32, y: f32, hp: i32 }

let offset_x = std::mem::offset_of!(Player, x);  // 0
let offset_y = std::mem::offset_of!(Player, y);  // 4
let offset_hp = std::mem::offset_of!(Player, hp); // 8

let ptr = &player as *const Player as *const u8;
let x = unsafe { *((ptr.add(offset_x)) as *const f32) };
```

性能最高(直接指针解引用),但 unsafe + 容易写错。Casey HH 用这个(C 程序员的 default)。Rust 一般避免,用方案 1-3。

### 2.5 `offsetof` 的 Rust 实现

Rust 1.77+ 标准库内置 `mem::offset_of!`:

```rust
let offset = std::mem::offset_of!(Player, x);  // 0
let offset = std::mem::offset_of!(Player, y);  // 4
```

老版本用 unsafe pointer 算:

```rust
macro_rules! offset_of {
    ($t:ty, $f:ident) => {{
        let dummy = core::mem::MaybeUninit::<$t>::uninit();
        let base = dummy.as_ptr();
        let field = unsafe { &(*base).$f as *const _ };
        (field as usize) - (base as usize)
    }};
}
```

通过 `MaybeUninit` 创建未初始化实例(不调构造函数),算字段地址与 base 的差,即 offset。**unsafe** 但 well-defined——地址计算本身不读未初始化内存。

### 2.6 反射的性能代价

introspection 不是免费的。每种方案的性能开销:

| 方案 | 字段访问时间 | 编译开销 | 二进制 bloat |
|---|---|---|---|
| 直接 `entity.x` | 1 ns | 无 | 无 |
| 手写 inspect trait | 5 ns(trait dispatch) | 无 | 小 |
| bevy_reflect | 10 ns(vtable + type erasure) | 大(proc macro) | 大 |
| Java reflection | 100 ns(JIT 不优化反射调用) | 无 | 大 |
| offset + unsafe ptr | 2 ns(pointer + offset) | 无 | 小 |

游戏 hot path(物理 update、渲染)用**直接访问**——每帧几百万次,反射开销不可接受。

游戏 debug UI 用**反射**——每帧几千次,反射开销可忽略(< 1ms)。

Casey 在 HH 里特别强调"反射隔离在 debug 代码里"。Day 201 的 cfg 隔离 + Day 206 的 introspection 是配套的——debug 代码用反射,release build cfg 掉,反射代码不进 binary。

### 2.7 introspection 的应用场景

introspection 不只 debug UI。它支撑许多工业工具:

1. **Debug Inspector**(Casey Day 206-207):自动显示 struct 所有字段
2. **序列化**:JSON / Binary / Network(serde 全靠 introspection)
3. **Diff / Merge**:对比两 struct,自动算变化(版本控制、协同编辑)
4. **RPC**:远程调 struct 当参数,自动 marshal(gRPC、Cap'n Proto)
5. **ORM**:struct ↔ database table 映射(Diesel、SQLx)
6. **Migration**:struct 变化时自动迁移数据(Liquibase、Alembic)
7. **Editor integration**:任意 struct 都能在编辑器里编辑(Unity、Unreal)
8. **Hot reload**:改 struct,运行时自动重新加载(crash-driven dev)

每个场景都需要"运行时知道字段"。introspection 是这些工具的基础设施。Casey Day 206 是基础设施层——为后面的 debug editor、序列化、网络同步铺路。

### 2.0 反射 / 内省的定义

**反射**(reflection):程序运行时访问自己的类型信息(字段名、类型、方法)。Java / C# / Python 有完整反射。

**内省**(introspection):只读访问(看类型,不调用方法)。Rust 用 trait + macro 实现简化版。

C 没有(运行时类型信息完全 stripped)。Casey 在 C 里手写"member list"实现简化内省:

```c
typedef struct {
    const char* name;
    size_t offset;
    MemberType type;
} MemberDef;

MemberDef player_members[] = {
    {"x", offsetof(Player, x), MEMBER_F32},
    {"y", offsetof(Player, y), MEMBER_F32},
    {"hp", offsetof(Player, hp), MEMBER_I32},
    {NULL, 0, 0}
};
```

`offsetof` 是 C 标准库宏,算字段在 struct 中的字节偏移。Rust 没有等价宏,要手写或用 macro。

### 2.0.1 Rust 的内省方案

**方案 1:bevy_reflect**(运行时反射):

```rust
#[derive(Reflect)]
struct Player { x: f32, y: f32, hp: i32 }

// 运行时
let p = Player { x: 5.0, y: 3.0, hp: 100 };
for (name, value) in p.iter_fields() {
    println!("{}: {:?}", name, value);
}
```

`#[derive(Reflect)]` 自动生成 trait 实现。overhead:vtable 调用,~10 ns/access。

**方案 2:serde::Serialize**(序列化):

```rust
#[derive(Serialize)]
struct Player { x: f32, y: f32, hp: i32 }

let json = serde_json::to_string(&player)?;
// 自动枚举所有字段
```

serialize 一次扫所有字段,适合"dump 整 struct",不适合"读单个字段"。

**方案 3:手写 macro**(Casey 风格):

```rust
macro_rules! reflect {
    ($name:ident { $($field:ident : $ty:ty),* $(,)? }) => {
        struct $name { $($field: $ty),* }

        impl $name {
            fn members() -> &'static [Member<'static>] {
                &[
                    $(Member { name: stringify!($field), offset: offset_of!(Self, $field), ty: TypeId::of::<$ty>() }),*
                ]
            }
        }
    }
}

reflect!(Player { x: f32, y: f32, hp: i32 });
```

macro 生成 struct + members 列表。无 runtime overhead(都是静态数据)。

### 2.0.2 offset_of! 宏的实现

`offset_of!(Struct, field)` 算字段偏移。Rust 1.77+ 标准库内置:

```rust
let offset = std::mem::offset_of!(Player, x);  // = 0
let offset = std::mem::offset_of!(Player, y);  // = 4
let offset = std::mem::offset_of!(Player, hp); // = 8
```

老版本用 unsafe pointer 算:

```rust
macro_rules! offset_of {
    ($t:ty, $f:ident) => {{
        let dummy = core::mem::MaybeUninit::<$t>::uninit();
        let base = dummy.as_ptr();
        let field = unsafe { &(*base).$f as *const _ };
        (field as usize) - (base as usize)
    }};
}
```

通过 `MaybeUninit` 创建未初始化实例(不调构造),算字段地址。

### 2.0.3 通过 offset 访问字段

```rust
fn get_f32(ptr: *const u8, offset: usize) -> f32 {
    unsafe { *((ptr.add(offset)) as *const f32) }
}

let player: Player = ...;
let ptr = &player as *const Player as *const u8;
let x = get_f32(ptr, 0);
let y = get_f32(ptr, 4);
let hp = get_f32(ptr, 8) as i32;
```

通过 `member offset table` 遍历所有字段。**unsafe**,但 well-defined(`#[repr(C)]` 保证字段布局)。

### 2.0.4 内省的应用场景

1. **Debug Inspector**:自动显示 struct 所有字段(Casey day 206-207)
2. **序列化**:JSON / Binary / Network(serde)
3. **Diff / Merge**:对比两 struct,自动算变化
4. **RPC**:远程调 struct 当参数,自动 marshal
5. **ORM**:struct ↔ database table 映射
6. **Migration**:struct 变化时自动迁移数据

每个场景都需要"运行时知道字段"。反射是这些工具的基础设施。

### 2.0.5 反射的性能代价

- 编译时间长(derive macro 生成代码)
- 二进制大(类型元数据)
- 运行时 vtable 调用(慢 ~10x)
- 优化障碍(编译器看不清 vtable 后面的代码)

游戏 hot path 不用反射。Debug UI / 序列化用。Casey 把反射严格隔离在 debug 代码里。

## 3 · 四域深入

### 类比:体检报告

医院体检,医生扫描你身体各种指标(身高、体重、血压...),填一张报告。**不需要病人自己说"我有身高 175"——医生"看到"了**。

introspection 是程序"看到自己":像医生扫描病人,自动列出所有字段。

### 2.1 手写 introspection

```rust
pub enum DebugValueView {
    Float { name: &'static str, value: f32, min: f32, max: f32 },
    Int { name: &'static str, value: i64 },
    Vec2 { name: &'static str, x: f32, y: f32 },
    String { name: &'static str, value: String },
    Color { name: &'static str, value: u32 },
}

pub trait Inspectable {
    fn inspect(&self) -> Vec<DebugValueView>;
}

// Entity 实现
impl Inspectable for Entity {
    fn inspect(&self) -> Vec<DebugValueView> {
        vec![
            DebugValueView::Int { name: "id", value: self.id as i64 },
            DebugValueView::Vec2 { name: "pos", x: self.pos.x, y: self.pos.y },
            DebugValueView::Float { name: "radius", value: self.radius, min: 0.0, max: 100.0 },
            DebugValueView::Int { name: "hp", value: self.hp as i64 },
        ]
    }
}
```

**Rust 注释**:
- `trait Inspectable` — 任何可内省类型实现
- `&'static str` — 字段名,字面量
- `Vec<DebugValueView>` — 字段视图列表
- 手写每个字段(可读,但加字段要改 inspect)

### 2.2 UI 自动渲染

```rust
fn draw_inspector(ui: &mut Ui, item: &dyn Inspectable) {
    for view in item.inspect() {
        match view {
            DebugValueView::Float { name, value, min, max } => {

        }
    }
}
```

### 2.3 proc-macro 版本(工业)

`bevy_reflect` 用 proc macro 自动生成 inspect:

```rust
use bevy_reflect::Reflect;

#[derive(Reflect)]
struct Entity {
    id: u32,
    pos: Vec2,
    hp: i32,
}

// bevy_reflect 自动生成 Reflect trait impl
// 可以查字段:`entity.get_field::<u32>("id")`
```

proc macro 在编译期生成代码,把 `id` `pos` `hp` 字段名和类型登记。

### 2.4 编辑(双向)

inspect 返回的是**只读视图**。要编辑:

```rust
pub trait Editable {
    fn edit(&mut self, name: &str, new_value: DebugValueView);
}

impl Editable for Entity {
    fn edit(&mut self, name: &str, new_value: DebugValueView) {
        match name {
            "id" => if let DebugValueView::Int { value, .. } = new_value { self.id = value as u32 },
            "pos.x" => if let DebugValueView::Float { value, .. } = new_value { self.pos.x = value },
            "pos.y" => if let DebugValueView::Float { value, .. } = new_value { self.pos.y = value },
            "hp" => if let DebugValueView::Int { value, .. } = new_value { self.hp = value as i32 },
            _ => {}
        }
    }
}
```

UI 编辑时调 `entity.edit(name, new_value)`。

### 2.5 proc-macro 工业化的好处

手写 introspection 缺点:

- 加字段要改 inspect 函数(易漏)
- 字段类型错(inspect 写 Float,实际是 Int)
- 维护负担

proc-macro 自动化:`#[derive(Reflect)]` 后,所有字段自动登记,加字段不用改其他地方。

代价:编译时间、依赖。casey 起步手写,后期可换 bevy_reflect。

## 5 · 对照与变奏

**反射的跨语言对比**:

| 语言 | 反射机制 | 性能 |
|---|---|---|
| Java | java.lang.reflect | 慢(vtable + JIT) |
| C# | System.Reflection | 中(jit 优化) |
| Python | dir() / getattr | 慢(动态) |
| Go | reflect package | 中 |
| Swift | Mirror | 中 |
| C++ | RTTI(typeid) | 极弱(只能查类型,不能枚举字段) |
| Rust | bevy_reflect / serde | 中(macro 生成) |
| C | 无 | N/A |

C/C++ 没有完整反射是 long-standing limitation。C++23 提案加 reflection,但还没落地。

### Qt 的 MOC(Meta-Object Compiler)

Qt 用 **MOC** 预处理头文件,生成 reflection 代码:

```cpp
// .h
class MyClass : public QObject {
    Q_OBJECT  // MOC 标记
    Q_PROPERTY(int speed READ speed WRITE setSpeed NOTIFY speedChanged)
public:
    int speed() const;
    void setSpeed(int);
signals:
    void speedChanged();
};
```

MOC 扫描 `Q_PROPERTY` 等宏,生成 moc_xxx.cpp,提供 `MyClass::metaObject()`。Qt 的 signal/slot / property system 全靠 MOC。

Rust 用 `#[derive]` 等价,无需外部工具——这是 Rust 比 C++ 工程化的优势。

### Unreal 的 UHT(Unreal Header Tool)

Unreal 类似 Qt,用 UHT 处理 `UCLASS` / `UPROPERTY` / `UFUNCTION` 宏,生成 reflection 数据。编辑器、序列化、网络复制、Blueprint 都依赖 UHT 生成的代码。

### Reflection 的未来:C++26 reflection proposal

C++26 可能加入静态 reflection:

```cpp
struct Player { float x, y; int hp; };

for (auto member : std::meta::members_of(^^Player)) {
    std::cout << member.name() << "\n";
}
```

编译期 reflection,无 runtime overhead。Rust 的 const reflection 也在 proposal 阶段,未来可能加入。

### Lv3 · 迁移设计(Editable trait)

**题**:加 Editable trait,允许"按字段名改值"。UI 滑块改 `speed` 时,调 `player.edit("speed", Float(7.5))`。

**参考实现**:

```rust
trait Editable {
    fn edit(&mut self, name: &str, new_value: DebugValueView);
}

impl Editable for Player {
    fn edit(&mut self, name: &str, new_value: DebugValueView) {
        match name {
            "id" => if let DebugValueView::Int { value, .. } = new_value {
                self.id = value as u32;
            },
            "pos.x" => if let DebugValueView::Float { value, .. } = new_value {
                self.pos.x = value;
            },
            "pos.y" => if let DebugValueView::Float { value, .. } = new_value {
                self.pos.y = value;
            },
            "hp" => if let DebugValueView::Int { value, .. } = new_value {
                self.hp = value as i32;
            },
            "name" => if let DebugValueView::String { value, .. } = new_value {
                self.name = value;
            },
            "speed" => if let DebugValueView::Float { value, .. } = new_value {
                self.speed = value;
            },
            _ => {}  // 未知字段,忽略
        }
    }
}
```

**关键点**:
- `match name` 分发——按字段名字符串路由到对应赋值。
- `if let DebugValueView::Float { .. }` 类型检查——如果 UI 发错类型(比如 Int),静默忽略。也可 panic(debug 模式)。
- 加新字段要改两处——struct + edit 方法。这是手写 introspection 的代价。proc macro 自动化能消除这个。

**测试**:

```rust
fn main() {
    let mut p = Player { id: 1, pos: Vec2 { x: 0.0, y: 0.0 }, hp: 100, name: "P".into(), speed: 5.0 };
    p.edit("speed", DebugValueView::Float { name: "speed", value: 7.5 });
    assert_eq!(p.speed, 7.5);
    p.edit("hp", DebugValueView::Int { name: "hp", value: 50 });
    assert_eq!(p.hp, 50);
    println!("Editable test passed");
}
```

### 8.2 用 bevy_reflect 的工业版

```toml
[dependencies]
bevy_reflect = "0.13"
```

```rust
use bevy_reflect::{Reflect, ReflectRef};

#[derive(Reflect, Debug)]
struct Player {
    id: u32,
    pos: (f32, f32),
    hp: i32,
    name: String,
}

fn main() {
    let p = Player { id: 42, pos: (100.0, 200.0), hp: 75, name: "Hero".into() };

    // bevy_reflect 自动 introspection
    println!("Type: {}", p.reflect_type_info().type_name());

    // 按 path 访问字段
    if let Some(field) = p.get_field::<u32>("id") {
        println!("id via reflect: {}", field);
    }
    if let Some(field) = p.get_field::<i32>("hp") {
        println!("hp via reflect: {}", field);
    }

    // 遍历所有字段(struct 走 ReflectRef::Struct)
    let reflect: &dyn Reflect = &p;
    if let ReflectRef::Struct(s) = reflect.reflect_ref() {
        for field in s.iter_fields() {
            println!("field: {:?} = {:?}", field.name(), field.value());
        }
    }
}
```

**bevy_reflect vs 手写**:
- 加字段:bevy_reflect 自动跟上;手写要改 inspect/edit。
- 性能:bevy_reflect ~10 ns/access;手写 ~5 ns。
- 灵活:bevy_reflect 支持 path("pos.x")、type query、downcast;手写要自己实现。

### 8.4 Troubleshooting

**问题1**:`#[derive(Reflect)]` 编译错误。
原因:Cargo.toml 没加 bevy_reflect 依赖,或版本不匹配。
修复:`cargo add bevy_reflect`。

**问题2**:inspect 返回的字段名和实际不匹配。
原因:手写时打错字段名。
诊断:加 unit test,inspect 后 verify 每个字段值。
修复:统一字符串字面量(`const HP_FIELD: &str = "hp";`)。

**问题3**:`offset_of!` 编译错误。
原因:Rust < 1.77,或字段访问受 private 限制。
修复:升级 Rust;或字段访问受限时把 `offset_of!` 放在和字段同 module。

**问题4**:`bevy_reflect::Reflect` derive 不支持 generic struct。
原因:bevy_reflect 的 derive 对 generic struct 需要额外标注。
修复:看 bevy_reflect 文档的 "generic types" 章节。

**问题5**:introspection 在 hot path 太慢。
诊断:profiler 显示 trait dispatch + vtable 占 5%+。
修复:把 hot path 改回直接字段访问(`entity.x`),只 debug UI 用 introspection。

### 8.5 性能基线

| 操作 | 时间 |
|---|---|
| 直接 `entity.x` | 1 ns |
| 手写 inspect trait | 5 ns(trait dispatch + return Vec) |
| bevy_reflect get_field | 10 ns(vtable + HashMap lookup) |
| Java reflection get | 100 ns |
| serde Serialize (whole struct) | O(N) × 5ns |

游戏 hot path(物理 update、渲染):每帧几百万次字段访问,**用直接访问**。

游戏 debug UI:每帧几千次,**用 introspection 没问题**(< 1ms)。
