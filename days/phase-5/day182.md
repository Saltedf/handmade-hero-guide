
# Day 182 · 快速线程 ID 获取

> Day 181 的 event log 每条要记 thread_id,Casey 发现 `gettid()` 每次要 50 纳秒 syscall——每帧 10000 条 event,光 syscall 就 0.5 毫秒,影响 profiler 自己的精度。今天他优化:**用 thread_local 缓存 thread_id,只调一次 syscall**。

## 0 · 为什么要有这一天

profiler 测的东西,自己不能太慢。否则"测量行为"影响"被测系统"——这就是**观察者效应**(量子力学的概念,在 profiler 里也成立)。

Day 181 后,Casey 发现 profiler 自身开销:

- `rdtsc`:~10 ns
- thread_local 访问:~5 ns
- `push` 到 ring buffer:~20 ns
- **`gettid()`:~50 ns!**

每条 event 总开销大约 100 ns,其中 gettid 占一半。如果游戏里每帧 10000 个 span,光 thread_id 查询就 1 毫秒——影响游戏跑到 60fps。

解决方案很直接:**thread_local 缓存**。每线程第一次调用 `gettid()`,之后从 TLS 读,~5 ns。

心理锚点:看完今天,你能理解"系统调用(syscall)很慢",并能写出 TLS 缓存模式。

## 1 · Casey 今天做了什么

Casey 把 profiler 改成缓存 thread_id:

1. 加一个 thread_local: `static THREAD_ID: u32`
2. 第一次访问时调用 OS 的 `GetCurrentThreadId` / `gettid`,缓存
3. 之后直接读 TLS

代码改动 5 行,性能提升 10 倍。

他强调:**这是"测量开销"的典型例子**。profiler 自身每行代码都要被审视——你是测别人,不是被别人测。

## 2 · 心智模型

### 类比:门卫查身份证

公司门卫每次见员工进门都查身份证。员工每天进出 100 次,门卫每天查 100 次同样的身份证。聪明的门卫在门口挂个牌子"已认证员工: 张三/李四/王五",下次这些人进门直接放行,不再查。

这就是缓存:**第一次慢,后续快**。

thread_local 缓存是这个模式的极致——数据存在 TLS 段,CPU 直接 `%fs:offset` 寻址,没有函数调用,没有锁,没有原子操作。

### 2.1 Linux syscall 的代价

`gettid()` 在 Linux 上是 syscall:

```c
pid_t gettid(void) {
    return syscall(SYS_gettid);  // 不直接走 libc(gettid 直到 glibc 2.30 才有 wrapper)
}
```

syscall 的代价:

1. **用户态 → 内核态切换**(`syscall` 指令):~50-100 ns
2. 内核处理(查 task_struct):~20 ns
3. **内核态 → 用户态切换**(`sysret` 指令):~30 ns
4. **TLB / cache 影响**:每次切换可能 flush 部分 cache

总计 100-200 ns,是普通函数调用(2-5 ns)的 50 倍。

### 2.2 TLS 段

ELF 二进制有个 TLS(Thread Local Storage)段,内核创建线程时为每个线程分配一份。访问 TLS 在 x86_64 上是:

```
mov %fs:offset, %eax   # 1 cycle
```

`%fs` 是 segment register,Linux 用它指向当前线程的 TLS 区域。`offset` 是变量在 TLS 内的位置。

Rust 的 `thread_local!` 宏生成的代码就是这个:

```rust
thread_local! {
    static THREAD_ID: u32 = unsafe { libc::syscall(libc::SYS_gettid) as u32 };
}

// 用法
let tid = THREAD_ID.with(|t| *t);  // 第一次调 syscall,之后读 TLS
```

`THREAD_ID.with(|t| ...)` 展开后:

```rust
// 伪代码
static THREAD_ID_KEY: LocalKey<u32> = ...;
match THREAD_ID_KEY.try_initialize(|t| {
    let inner = unsafe { libc::syscall(libc::SYS_gettid) as u32 };
    *t = inner;
}) {
    Some(t) => /* 第一次初始化 */,
    None => /* 已存在,直接访问 */,
}
// 任何情况都能拿到 &T,无 syscall
```

### 2.3 测量对比

```rust
use std::time::Instant;

const N: usize = 1_000_000;

fn bench_syscall() {
    let start = Instant::now();
    for _ in 0..N {
        let _tid = unsafe { libc::syscall(libc::SYS_gettid) };
        std::hint::black_box(_tid);
    }
    let elapsed = start.elapsed();
    println!("syscall gettid x{}: {:?}", N, elapsed);
    // 约 50 ms(每次 50 ns)
}

thread_local! { static TLS_TID: u32 = unsafe { libc::syscall(libc::SYS_gettid) as u32 }; }

fn bench_tls() {
    let start = Instant::now();
    for _ in 0..N {
        let _tid = TLS_TID.with(|t| *t);
        std::hint::black_box(_tid);
    }
    let elapsed = start.elapsed();
    println!("TLS access x{}: {:?}", N, elapsed);
    // 约 5 ms(每次 5 ns)
}

fn main() {
    bench_syscall();
    bench_tls();
}
```

**预期输出**:

```
syscall gettid x1000000: 50.2ms   (50 ns/次)
TLS access x1000000: 5.3ms        (5 ns/次)
```

10 倍提升。

### 2.4 TLS 的两种实现

Rust 标准库的 `thread_local!` 用 `LocalKey<T>`,惰性初始化。第一次 `.with()` 时调 init function,后续直接读。

更轻量的版本:**`#[thread_local]` attribute**(nightly)+ 静态初始化:

```rust
// 仅 nightly
#![feature(thread_local)]
#[thread_local]
static THREAD_ID: std::cell::UnsafeCell<u32> = std::cell::UnsafeCell::new(0);

// 自己手动 init
unsafe {
    if *THREAD_ID.get() == 0 {
        *THREAD_ID.get() = libc::syscall(libc::SYS_gettid) as u32;
    }
    let tid = *THREAD_ID.get();
}
```

生产代码不用 nightly,用 std 的 `thread_local!` 即可。

### 2.4.1 LocalKey::with 的开销分解

`thread_local!` 展开成 `LocalKey<T>`,`with(|t| ...)` 内部做的事:

1. 读 `%fs:0x10` 拿到当前线程的 TLS block 地址(1 cycle)
2. 读 TLS block 里的 LocalKey state(指针 + bool)(1 cycle)
3. 如果 state 是"未初始化",调 init function(慢路径)
4. 把 `&T` 传给闭包

**快路径(已初始化)**:5-7 cycle,即 1-2 ns。
**慢路径(首次)**:几十 ns(init function + atomics)。

Rust 1.59+ 引入 `const { ... }` init 语法,允许在编译时初始化 TLS,跳过慢路径:

```rust
thread_local! {
    static FRAME_INDEX: std::cell::Cell<u32> = const { std::cell::Cell::new(0) };
}
// 永远走快路径,因为 init 在编译期完成
```

这是 Casey 用 const init 的场景之一。

### 2.4.2 std::cell vs std::sync::atomic

TLS 内部用 `Cell<T>` 还是 `AtomicU64`?

- **`Cell<T>`**:单线程借用检查(运行时),无需 atomic,T 是 Copy
- **`AtomicU64`**:无锁跨线程,适合"主线程写 + 工作线程读"

thread_local 永远是单线程(自己线程),所以 `Cell<T>` 是最自然的选择。如果用 `AtomicU64` 在 thread_local 里,**多余的 atomic 开销**(每次 ~5 cycle),没必要。

```rust
// 对的:thread_local 用 Cell
thread_local! {
    static COUNTER: Cell<u32> = Cell::new(0);
}

// 错的:thread_local 不需要 atomic
thread_local! {
    static COUNTER: AtomicU32 = AtomicU32::new(0);  // 浪费
}
```

### 2.5 macOS / Windows 等价

```rust
#[cfg(target_os = "linux")]
fn gettid_slow() -> u32 { unsafe { libc::syscall(libc::SYS_gettid) as u32 } }

#[cfg(target_os = "macos")]
fn gettid_slow() -> u32 {
    // macOS 没有 gettid,用 pthread_self 的指针
    let p = unsafe { libc::pthread_self() };
    p as u32
}

#[cfg(windows)]
fn gettid_slow() -> u32 {
    unsafe { windows::Win32::System::Threading::GetCurrentThreadId() }
}
```

Windows 的 `GetCurrentThreadId()` **不是 syscall,而是 user-mode 读 TLS**(kernel32 维护的 user-mode cache),已经很快(~10 ns),所以 Windows 版的优化空间小。

### 2.6 vDSO 与 vsyscall 的内部

有些 Linux syscall 不需要进内核就能完成,因为内核把代码映射到每个进程的用户态地址空间——这就是 **vDSO**(virtual Dynamic Shared Object)。

```bash
# 看你的进程的 vDSO 映射
cat /proc/self/maps | grep -E "vdso|vsyscall"
# 输出:
# 7ffd22776000-7ffd22778000 r-xp 00000000 00:00 0  [vdso]
# ffffffffff600000-ffffffffffe00000 --xp 00000000 00:00 0  [vsyscall]
```

`[vdso]` 是现代版本,提供 `clock_gettime` / `gettimeofday` / `time` / `getcpu`。
`[vsyscall]` 是古老版本(已废弃但仍存在),固定地址 `0xffffffffff600000`,只有 3 个函数。

`clock_gettime(CLOCK_MONOTONIC)` 走 vDSO 时,实际跑的是用户态代码,读内核维护的 vvar(virtual variable)页面——内核周期性更新 vvar,用户态直接读,不进内核,所以只要 ~20 ns。

**但 gettid 不在 vDSO 里**——Linux 内核认为 gettid 太简单不值得 vDSO 化,所以必须 syscall。这就是 Casey 为什么要 TLS 缓存。

### 2.7 TLS 的内存模型

ELF 的 TLS 实现有 4 种模型,由编译器根据变量属性和链接方式选:

1. **Local-Exec (LE)**:可执行文件里的 `#[thread_local]` static,直接 `%fs:offset`,最快(1 cycle)
2. **Initial-Exec (IE)**:shared library 在程序启动时加载的 TLS,通过 GOT 读 `%fs:offset`,2-3 cycle
3. **Local-Exec Dynamic (LD)**:dlopen 加载的 library,需要 `__tls_get_addr`,慢(~30 cycle)
4. **General Dynamic (GD)**:最通用,也走 `__tls_get_addr`

Rust 的 `thread_local!` 用 IE 或 LD 模型(看链接情况)。**主程序里的 thread_local 最快**,dlopen 加载的 plugin 里的 thread_local 慢——Casey 在 Phase 1 的热重载要小心这个。

```bash
# 看你的二进制用哪种 TLS 模型
readelf -r target/release/my_game | grep tls
# 输出可能有:
# Relocation section '.rela.dyn' at offset 0x... contains:
# 0000... R_X86_64_DTPMOD64 ...  (General Dynamic)
# 0000... R_X86_64_DTPOFF32  ... (Local Dynamic)
# 0000... R_X86_64_TPOFF32   ... (Local-Exec,最快)
```

### 2.8 测量微小时间的方法论

bench 测 5 ns vs 50 ns 这种小时间,**测量本身就有噪声**:

- `Instant::now()` 自己 ~20 ns,不能用来测 < 50 ns 的事
- CPU 频率漂移(睿频、节能)让 wall-clock 不稳定
- 编译器可能把循环优化掉(`black_box` 防)
- cache 状态影响(冷启动 vs 热启动)

**正确方法**:循环 N 次后取平均,N 选到总时间 > 1 ms(避免 Instant 噪声):

```rust
let n = 1_000_000;  // 1M 次,每次 5 ns → 总 5 ms,远超 Instant 精度
let start = Instant::now();
for _ in 0..n {
    black_box(gettid_cached());
}
let total = start.elapsed();
let per_call = total.as_nanos() / n as u128;
```

**进阶**:用 `criterion` 或 `divan` 这些专业 bench 库,自动处理 warmup、统计、outlier。

### 2.9 工业级 profiler 的优化清单

TLS 缓存 thread_id 只是冰山一角。完整 profiler 优化清单:

| 优化 | 效果 |
|---|---|
| TLS 缓存 thread_id | 50 ns → 5 ns(10x) |
| `&'static str` 替代 String | 100 ns → 0 ns |
| 固定大小数组替代 Vec | ~30 ns → ~5 ns |
| ring buffer 2 的幂 | 20 cycle → 1 cycle |
| `#[inline(always)]` | 函数调用 ~5 ns → 0 |
| per-thread 累加替代全局 atomic | 10-50 cycle → 1 cycle |
| 预分配 + 内存池 | malloc ~100 ns → ~5 ns |

每个都看似微小,但累加起来 profiler 总开销能从 10% 帧时间降到 0.5%。Casey day 200+ 反复做这种优化。

### 3.4 · 测量 profiler 自身开销的方法

元测量:用 profiler 测 profiler:

```rust
fn push_event(...) {
    let _self_measure = ProfileSpan::enter("push_event");
    // ...
}
```

但这会**递归**——push_event 调用 push_event 又调用...。Casey 用一个 flag 防止递归:

```rust
thread_local! { static IN_PROFILER: Cell<bool> = Cell::new(false); }

fn push_event(...) {
    if IN_PROFILER.with(|f| f.get()) { return; }  // 防递归
    IN_PROFILER.with(|f| f.set(true));
    // ... 真正的 push
    IN_PROFILER.with(|f| f.set(false));
}
```

### 3.6 · 🐧 Linux 系统编程视角(strace 看自己的 syscall)

`strace` 是看程序调了哪些 syscall 的工具。你可以用它验证 thread_id 缓存真的减少了 syscall:

```bash
# 不带缓存版
strace -c -e trace=gettid ./target/release/tid-bench-no-cache
# 输出:
# % time     seconds  usecs/call     calls    errors syscall
# ------ ----------- ----------- --------- --------- ----------------
#  100.00    0.050050          50   1000000           gettid
# ------ ----------- ----------- --------- --------- ----------------
# 1000000 次 gettid,每次 50 μs

# 缓存版
strace -c -e trace=gettid ./target/release/tid-bench
# 输出:
```

### 3.7 · 🦀 Rust 生态视角(跨平台 thread id crate)

`libc` 直接调 syscall 太底层,工业代码常用 `thread-id` crate:


## 5 · 对照与变奏

**TLS 在不同平台**:

| 平台 | 实现机制 |
|---|---|
| Linux x86_64 | `%fs` segment |
| Linux aarch64 | `tpidr_el0` register |
| Windows x86_64 | `%gs` segment |
| macOS x86_64 | `%gs` segment |
| WASM | `__tls_*` 自定义 section |

不同 ABI 但概念一样:**每线程一份存储,CPU 寄存器指向**。

**Rust 中"测量开销"的实战例子**:

- `Arc<T>` 的原子引用计数开销
- `Box<T>` 的堆分配开销
- `String` / `Vec` 的增长拷贝
- `format!` 的格式化开销

每个都有 TLS 缓存或对象池优化版本。

### TLS 缓存的历史

1980 年代单线程程序,所有"全局状态"放在 static 变量。多线程出现后,这种全局状态成了数据竞争源头。1995 年 pthread 引入 `pthread_key_create` / `pthread_getspecific`,提供软件级 TLS——慢(走函数调用)。

2003 年 **Intel 在 x86_64 引入 segment register TLS**(`%fs`),硬件级 TLS,1 cycle 访问。Linux/glibc 跟进,**ELF TLS ABI** 形成。2000 年代末所有 OS 都支持硬件 TLS。

Rust 2015 发布,`thread_local!` 宏基于 ELF TLS ABI,跨平台抽象。今天我们享受的就是 30 年工程积累的结果。

### 与现代 C++ 的对比

C++11 引入 `thread_local` 关键字,语义和 Rust 的 `thread_local!` 类似:

```cpp
// C++
thread_local int tid = syscall(SYS_gettid);
// 第一次访问时初始化,后续读 TLS
```

C++ 的 `thread_local` 是语言级关键字,编译器直接生成 `%fs:offset`。Rust 的 `thread_local!` 是宏,展开成 `LocalKey<T>`,有薄薄一层 wrapper——这是 Rust 1.x 还没稳定 `#[thread_local]` 的代价。

性能差距:C++ 直接 1 cycle,Rust `LocalKey` 3-5 cycle。**对游戏这种 hot path 差异可见**,所以 Rust 游戏引擎(Bevy / Fyrox)有时用 nightly 的 `#[thread_local]` 或 unsafe 绕过。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不直接 `#[repr(C)] static mut TID: u32 = 0;` 然后每线程写它?为什么必须 thread_local?

**参考解答**:
- `static mut TID: u32` 是**全局共享变量**,所有线程写同一个内存位置
- 线程 A 写 TID = 1,线程 B 写 TID = 2,线程 A 读到 2(错的)
- 这就是**数据竞争**(data race),Rust 编译期拒绝 `static mut TID` 的写
- thread_local 是"每线程一份独立 TID",写自己的,不影响别人
- `#[thread_local]` 在底层就是给每个线程一份独立内存

### Lv2 · 动手实践

**题**:写一个 benchmark 对比 syscall vs TLS:

```rust
// 实现
// 1. bench_syscall:循环 100万次 syscall(gettid)
// 2. bench_tls:循环 100万次 TLS 读取
// 3. 输出每次平均耗时
```

**参考解答**:

```rust
use std::cell::Cell;
use std::hint::black_box;
use std::time::Instant;

#[cfg(target_os = "linux")]
fn gettid_syscall() -> u32 {
    unsafe { libc::syscall(libc::SYS_gettid) as u32 }
}

thread_local! {
    static TLS_TID: Cell<Option<u32>> = Cell::new(None);
}

fn gettid_cached() -> u32 {
    TLS_TID.with(|c| {
        if let Some(t) = c.get() { t }
        else {
            let t = gettid_syscall();
            c.set(Some(t));
            t
        }
    })
}

const N: usize = 1_000_000;

fn main() {
    // warmup
    for _ in 0..1000 { black_box(gettid_syscall()); }
    for _ in 0..1000 { black_box(gettid_cached()); }

    let start = Instant::now();
    for _ in 0..N { black_box(gettid_syscall()); }
    println!("syscall: {:?} ({} ns/each)", start.elapsed(),
        start.elapsed().as_nanos() / N as u128);

    let start = Instant::now();
    for _ in 0..N { black_box(gettid_cached()); }
    println!("cached: {:?} ({} ns/each)", start.elapsed(),
        start.elapsed().as_nanos() / N as u128);
}
```

**Cargo.toml**:

```toml
[target.'cfg(target_os = "linux")'.dependencies]
libc = "0.2"
```

**预期输出**:syscall ~50 ns,cached ~5 ns。

### Lv3 · 迁移设计

**题**:profiler 不只缓存 thread_id,还要缓存"frame_index"(当前是第几帧)。设计 API,让 profiler 在 frame 边界时自动更新这个 cache,代码里直接读 TLS 而不调函数。**提示**:把"更新 cache"这件事也放进 frame_begin 的 hook。

**额外提示**:
- frame_index 是个 u64,主线程每帧 +1,所有线程读到的是"最近一次同步值"
- 主线程在 frame_begin 时通过 atomic 写到全局变量
- 工作线程在 hot path 直接读 TLS(由 frame_begin hook 同步到 TLS)
- **关键设计点**:工作线程不会每帧都触发 hook(它可能在跑长任务),所以 frame_index 是"上次同步时的值"——profiler event 里要记"读到的 frame_index",而不是"实际 frame"
- **进阶**:能否做到 lock-free?用 `AtomicU64::load(Relaxed)` 每次读也只要 1 cycle,不一定要 TLS。TLS 优势是**绝对无 atomic 写竞争**——主线程写 atomic 不和工作线程读竞争

**Troubleshooting**:

- 编译错:libc 找不到 — 在 Linux 上才加 libc 依赖
- bench 数字太接近 — warmup 不够,加更多 warmup
- 浮点 ns 精度不够 — 用 `as_nanos() / N` 整数除
- **TLS 变量初始化 panic** — 如果 init function panic,thread_local 永久损坏,后续访问都 panic。init function 必须不能 fail
- **bench 数字不稳** — CPU 频率漂移,跑前 `sudo cpupower frequency-set -g performance` 锁频
- **跨平台编译错** — `libc::SYS_gettid` 在 macOS / Windows 不存在,必须 `#[cfg(target_os = "linux")]`
