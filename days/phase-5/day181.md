# Day 181 · 基于日志的性能计数器

> 前 4 天的 profiler 是"按 cycle 累加"——只看到总数,看不到细节。今天 Casey 把 profiler 改成"日志式":每个 span 进入 / 退出都记一条 event,带 cycle 时间戳。这样能看每帧**所有函数**的耗时分布,而不只是总 cycle。

## 0 · 为什么要有这一天

Day 178 的"atomic 计数器"模式有一个根本缺陷:**只能看到聚合数**。`update_player: 500000 cycles`——但这 500000 cycles 是来自 1 次调用还是 100 次?是均匀的还是某次特别慢?聚合数回答不了。

更糟的是:如果你想知道"update_player 是被谁调用的"(调用栈),根本没法回答——计数器只记总数,不记来源。

Casey 今天的设计:**event log**。每次进 / 出 span 写一条记录:

```
[frame=N] begin update_player  cycles=1000
[frame=N] begin update_audio    cycles=1500
[frame=N] end   update_audio    cycles=1700
[frame=N] begin update_render   cycles=1700
[frame=N] end   update_render   cycles=2200
[frame=N] end   update_player   cycles=2300
```

时间戳用 rdtsc。**通过时间戳配对 begin/end,就能算每次调用的耗时**。这种"日志式"profiler 能回答:

- 每次调用多长(不只是总长)
- 调用顺序(谁先谁后)
- 嵌套关系(谁在谁里面)
- 调用栈(画火焰图)

心理锚点:看完今天,你能写出一个"日志式 profiler",并能解释为什么它比"聚合计数器"信息量大,但开销也大。

## 1 · Casey 今天做了什么

Casey 把 profiler 从"聚合"模式改成"event stream"模式:

1. 每次进 span 写一条 `DebugEvent::Begin`,出 span 写 `End`
2. 每条 event 带:cycle 时间戳、thread ID、span 名(或 GUID)、color
3. event 存到一个 ring buffer(per-thread)
4. 帧结束时,主线程从所有线程收集 event,合并成一张 timeline

他强调:**event log 开销大**(每次 span 2 次写,而不是 1 次累加),但能回答更多问题。trade-off 值得。

## 2 · 心智模型

### 类比:出入门禁系统

公司门口有刷卡门禁。每刷一次,系统记一条:`[time] employee_id IN/OUT`。HR 要看:
- 谁几点几分到(单条事件)
- 谁今天工作了几小时(配对 IN/OUT 算差)
- 部门里谁待得最久(分组聚合)

event log profiler 一模一样:**记原始事件**,聚合分析时再做。这种"先存原始,后聚合"的设计叫 **event sourcing**(事件溯源)——Martin Fowler 推广的设计模式,在金融、电商、数据库、profiler 都用。

### 2.1 event 结构

```rust
#[derive(Clone, Copy)]
pub struct DebugEvent {
    pub cycle: u64,           // rdtsc 时间戳
    pub thread_id: u32,       // 哪个线程
    pub guid: u64,            // span 唯一 ID(name hash)
    pub color: u32,           // UI 颜色
    pub kind: EventKind,      // Begin / End
}

#[derive(Clone, Copy)]
pub enum EventKind { Begin, End }
```

**字段解释**:
- `cycle` — rdtsc 时间戳。begin 和 end 的差就是耗时
- `thread_id` — 哪个线程记的。多线程汇总时区分
- `guid` — span 唯一标识。Casey 用编译期生成的 64 位 hash(避免字符串比较)
- `color` — UI 上不同 span 用不同颜色,容易区分
- `kind` — 进还是出

### 2.2 event 的存储

每条 event 大约 32 字节。60 FPS × 1000 span/帧 × 4 线程 = 240000 事件/秒,即 **每秒 7.7 MB**。

不能存所有,要 ring buffer 限容量:

```rust
pub struct EventBuffer {
    events: Box<[DebugEvent]>,  // 固定容量(如 1 << 20 = 100 万条 = 32 MB)
    head: usize,
    full: bool,
}

impl EventBuffer {
    pub fn push(&mut self, e: DebugEvent) {
        self.events[self.head] = e;
        self.head = (self.head + 1) & (self.events.len() - 1);  // 容量 2 的幂,用 & 代替 %
        if self.head == 0 { self.full = true; }
    }

    pub fn iter(&self) -> impl Iterator<Item = &DebugEvent> {
        let start = if self.full { self.head } else { 0 };
        let end = if self.full { self.events.len() } else { self.head };
        let slice = &self.events[start..end];
        slice.iter().chain(if self.full { self.events[..self.head].iter() } else { [].iter() })
    }
}
```

**容量选 2 的幂**,用 `& (len - 1)` 替代 `% len`——这是性能关键,取模在 x86 要 20+ cycle,位与 1 cycle。

### 2.3 span → event 自动转换

RAII guard 在 enter/drop 时各写一条:

```rust
pub struct ProfileSpan {
    guid: u64,
    color: u32,
    start: u64,
}

impl ProfileSpan {
    pub fn enter(name: &'static str, color: u32) -> Self {
        let guid = hash(name);
        let start = rdtsc();
        push_event(DebugEvent {
            cycle: start, thread_id: thread_id(), guid, color, kind: EventKind::Begin,
        });
        Self { guid, color, start }
    }
}

impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let end = rdtsc();
        push_event(DebugEvent {
            cycle: end, thread_id: thread_id(),
            guid: self.guid, color: self.color, kind: EventKind::End,
        });
    }
}
```

**注意**:`push_event` 要 thread-safe。Day 178 已经做过类似(atomic counter),今天用 thread_local + ring buffer。

### 2.4 GUID 生成

为什么用 GUID 而不是字符串?**比较快**。字符串比较 O(N),u64 比较 1 cycle。

怎么生成 GUID?编译期 hash:

```rust
const fn hash(s: &str) -> u64 {
    let bytes = s.as_bytes();
    let mut h = 0xcbf29ce484222325;  // FNV-1a offset basis
    let mut i = 0;
    while i < bytes.len() {
        h ^= bytes[i] as u64;
        h = h.wrapping_mul(0x100000001b3);  // FNV-1a prime
        i += 1;
    }
    h
}
```

**const fn** — Rust 1.31+ 的 const 函数,编译期求值。`hash("update_player")` 编译时算成 u64,运行时是常量。

用 `static UPDATE_PLAYER_GUID: u64 = hash("update_player");` 即可。

### 2.5 多线程汇总

每个线程一份 ring buffer,主线程在帧结束时遍历所有线程:

```rust
pub struct ThreadRegistry {
    thread_buffers: Mutex<Vec<Arc<EventBuffer>>>,  // Arc 共享所有权
}

impl ThreadRegistry {
    pub fn snapshot(&self) -> Vec<DebugEvent> {
        let buffers = self.thread_buffers.lock().unwrap();
        let mut all: Vec<DebugEvent> = Vec::new();
        for buf in buffers.iter() {
            // 注意:这里要 unsafe 或用 RwLock,因为 ring buffer 在被线程写
            // Casey 用双缓冲(double buffer)解决——见 Day 211+
            // 简化版:用 snapshot
        }
        all.sort_by_key(|e| e.cycle);  // 按 cycle 排序得到 timeline
        all
    }
}
```

排序是关键——多线程的 event 时间戳是相对的(各线程的 rdtsc 应该同步,但实测有偏差),排序后得到大致时间线。

### 2.6 FNV-1a hash 算法推导

为什么要用 FNV-1a 而不是 MD5 / SHA?**FNV-1a 极快**(几条指令),不是密码学安全(可逆 / 抗碰撞),但**用于 ID 足够**。

FNV-1a 的算法:

```
hash = FNV_offset_basis  (64 位版本:0xcbf29ce484222325)
for each byte b in input:
    hash = hash XOR b           # 先 XOR
    hash = hash * FNV_prime     (0x100000001b3)
return hash
```

**为什么 XOR 在乘之前?** 因为乘法会把高位混合到低位,如果先乘再 XOR,高位信息丢失。先 XOR 保证每个字节都影响所有位。

**为什么是这个魔数?** FNV 设计者实验测得,这个 prime 让 hash 分布均匀。具体推导见 Fowler/Noll/Vo 1991 年的论文。

**用 const fn 的好处**:`hash("update_player")` 在编译时算完,运行时是常量,**零运行时开销**。Rust 1.31+ 的 const fn 是 Casey 在 C 里用宏做不到的——Rust 的优势。

但要注意:**const fn 不能调任意函数**,只能调 const fn。所以 FNV-1a 要手写循环(不能用 `for` iterator,要用 `while`)。Rust 1.46+ 支持更多 const 上下文。

### 2.7 配对算法的复杂度

配对 begin/end 看起来简单,实际上**多线程环境下很 tricky**:

- 单线程严格嵌套(`A begin, B begin, B end, A end`):栈配对,O(N)
- 同线程但不严格嵌套(`A begin, B begin, A end, B end`):异常,但有些代码会这样(比如手写 RAII 错误)
- 跨线程(`thread 1: A begin`, `thread 2: A end`):几乎不可能正确处理

实际工程:**强制同线程配对**。begin 必须在自己线程的栈上,end 也必须。跨线程的 span 不存在(只有线程切换才跨)。

```rust
// 每线程独立栈
thread_local! {
    static OPEN_STACK: RefCell<Vec<(u64, u64)>> = RefCell::new(Vec::new());
}

// begin: push
OPEN_STACK.with(|s| s.borrow_mut().push((guid, cycle)));
// end: pop(必须 guid 匹配)
OPEN_STACK.with(|s| {
    let mut s = s.borrow_mut();
    if let Some(&(top_guid, start)) = s.last() {
        if top_guid == guid {
            let elapsed = cycle - start;
            s.pop();
            // record elapsed
        } else {
            // 错误:end guid 和 top 不匹配
        }
    }
});
```

这是 Casey 后续 day 211+ 双缓冲设计的基础。

### 2.8 ring buffer 容量规划

每条 event 32 字节。如何选 N?

| 用途 | 容量 | 内存 | 说明 |
|---|---|---|---|
| 60 FPS, 100 span/帧, 4 线程, 1 秒历史 | 240000 | 7.7 MB | 1 秒 |
| 5 秒历史 | 1.2M | 38 MB | 5 秒 |
| 30 秒历史 | 7.2M | 230 MB | 30 秒 |

游戏 dev 机器普遍 32 GB+,230 MB 不是问题。但**每个 CPU 核的 cache 才 32 MB**(L3),超过就要去 DRAM,慢 10 倍。

经验:**N 选到刚好填满 L3**,再多无收益。Intel i7 的 L3 12 MB,选 N = 12 MB / 32 字节 ≈ 393216 ≈ 2^18.6,选 2^18 = 262144 条 = 8 MB。

### 2.9 时间戳同步问题

每个 CPU 核有自己的 rdtsc 计数器。Intel 现代 CPU 保证 invariant TSC(所有核同步),但 **AMD 老 CPU 和虚拟机不一定**。

```bash
# 检查 invariant TSC
grep -o constant_tsc /proc/cpuinfo | head -1
grep -o nonstop_tsc /proc/cpuinfo | head -1
```

如果两个 flag 都有,跨线程 rdtsc 可比较。否则你的 event 排序会乱——线程 A 的 rdtsc 比线程 B 大,但 A 的事件其实先发生。

工程兜底:**用 frame_index 作为粗排序**,cycle 作为细排序:

```rust
struct Event {
    frame_index: u32,  // 主线程每帧 +1,所有线程共享
    cycle: u64,        // 帧内细粒度
    // ...
}
```

按 frame_index 排序,帧内按 cycle 排序。即便 rdtsc 偏差几百 cycle,帧内顺序仍准。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

event log 模式 vs aggregate counter 模式对比:

| 模式 | 数据量 | 能回答的问题 | 开销 |
|---|---|---|---|
| aggregate counter | 小(每 span 一个数) | 总耗时 / 调用次数 | 低 |
| event log | 大(每 span 两条事件) | 上面 + 顺序 + 嵌套 + 火焰图 | 高 |

工业级 profiler(Tracy、Superluminal)用 event log。轻量级(自己手写)可以用 aggregate 起步。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核的 tracepipe / ftrace 也是 event log 模式:

```bash
# 看内核的 sched event(调度切换)
echo 1 > /sys/kernel/debug/tracing/events/sched/sched_switch/enable
cat /sys/kernel/debug/tracing/trace_pipe
# 输出:
# bash-1234 [1] d..3 1000.000: sched_switch: prev_comm=bash prev_pid=1234 next_comm=swapper
# bash-1235 [2] d..3 1000.001: sched_switch: prev_comm=swapper prev_pid=0 next_comm=bash
```

每条 event 是 (timestamp, pid, cpu, event_name, payload)。Casey 的 profiler 数据格式一样。

Linux 上的等价 profiler:

```bash
# perf record + report
sudo perf record -F 99 -ag -- sleep 5
sudo perf report

# 用 bpftrace 写自己的 event log
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
```

### 3.3 · 🦀 Rust 生态视角

Rust 的 event log profiler:
- **`tracing`** crate — Rust 生态最通用,支持 span / event
- **`tracy`** bindings — 业界标准

```rust
// tracing 用法
use tracing::{span, Level, info};

let span = span!(Level::INFO, "update_player");
let _enter = span.enter();

```

`tracing` 的 span 是堆分配的(默认),casey 是栈分配 + ring buffer。trade-off:**tracing 通用,Casey 极致快**。

### 3.5 · 🐧 Linux 系统编程视角(perf_event_open)

Linux 内核提供 `perf_event_open(2)` 系统调用,让用户态程序读 CPU 的 PMC(Performance Monitoring Counter)——比 rdtsc 更强大,能数 cache miss、branch miss、IPC 等:

```c
// C 伪代码
struct perf_event_attr attr = {
    .type = PERF_TYPE_HARDWARE,
    .config = PERF_COUNT_HW_CACHE_MISSES,
};
int fd = syscall(__NR_perf_event_open, &attr, pid, cpu, -1, 0);
read(fd, &value, sizeof(value));  // 读 cache miss 数
```

但 perf_event_open 需要 root 或 `/proc/sys/kernel/perf_event_paranoid` 设到 1 以下:

```bash
cat /proc/sys/kernel/perf_event_paranoid
# 默认 2(普通用户只能 trace 自己)
# -1 = 无限制,2 = 严格
sudo sysctl -w kernel.perf_event_paranoid=1
```

Casey 不用 perf_event_open(太重),只用 rdtsc。但**生产级 profiler**(Tracy / VTune)用 PMC 数硬件事件,能告诉"update_player 里有 1000 次 L1 miss"。

### 3.6 · 🦀 Rust 生态视角(perf-event2 crate)

`perf-event2` crate 是 Rust 的 perf_event_open 封装:

```rust
use perf_event::{Builder, Group};

let mut counter = Builder::new().build()?;
counter.enable()?;
// do work
counter.disable()?;
let counts = counter.read()?;
println!("cache misses: {}", counts);
```

游戏里可以**每帧采样几个 span**,看哪些 span cache miss 高。这是工业级优化方向。

## 5 · 对照与变奏

**Event log 在不同领域的演化**:

| 领域 | 实现 |
|---|---|
| 数据库 WAL | write-ahead log,先记后做 |
| 分布式追踪 | OpenTelemetry / Jaeger / Zipkin |
| 区块链 | 链上交易 = 全局 event log |
| Linux 内核 | ftrace / bpftrace |
| 浏览器 | Chrome DevTools Timeline |

**event log 的存储权衡**:

- 完全保存在内存:快,但断电丢
- 写文件 / 网络持久:慢,但可回放
- 内存 ring buffer + 落盘:折衷,Casey 选这个

### 与 Chrome Trace Event Format 的对比

Chrome DevTools 的 trace 文件是 JSON 格式,每个 event 是一个对象:

```json
{"name": "update_player", "cat": "game", "ph": "B", "ts": 1234567, "pid": 1, "tid": 1}
{"name": "update_player", "cat": "game", "ph": "E", "ts": 1234590, "pid": 1, "tid": 1}
```

- `ph: "B"` = Begin,`ph: "E"` = End(和 Casey 的 EventKind 一样)
- `ts` 微秒精度(比 Casey 的 cycle 粗糙)
- `pid` / `tid` / `cat` 多维度分类

Chrome Trace Format 是事实标准(被 V8 / Chromium / Android systrace / Pandas profiling 用)。Casey 的设计**等价但更紧凑**(二进制 32 字节 vs JSON 200 字节)。

如果你的 profiler 数据要被 Chrome DevTools 看(可视化非常强),可以序列化成 Chrome Trace Format JSON。Tracy 的 export 就有这个选项。

### OpenTelemetry 的分布式追踪

微服务时代,一个 HTTP 请求要经过 10 个服务。OpenTelemetry 用 **trace context**(W3C 标准)传递 trace ID,每个服务的 event log 通过 trace ID 关联:

```
trace_id: abc123
├─ span: frontend (10ms)
│  ├─ span: auth_service (2ms)
│  ├─ span: product_api (5ms)
│  │  ├─ span: db_query (3ms)
│  │  └─ span: cache_lookup (1ms)
└─ span: response (1ms)
```

游戏是单进程,不需要 trace context,但**结构相同**——span 有 parent / child 关系,通过 GUID 关联。Casey 的嵌套(同线程栈)是 OpenTelemetry 的简化版(没有跨进程 trace_id)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:event log profiler 比 aggregate counter 慢,具体慢在哪?能优化到和 counter 一样快吗?

**参考解答**:
- **慢在**:每 span 写 2 条 event(每条 ~32 字节),counter 只 1 次原子加(8 字节)
- **慢在**:ring buffer 写要更新 head 指针(虽然 atomic,但 cache line 竞争)
- **慢在**:汇总要排序 O(N log N)
- **能优化**:每线程 batch N 条再合并(减少 cache contention)
- **能优化**:不用 GUID,用 enum tag(更紧凑,但要在编译期枚举所有 span)
- 但永远比 counter 慢——这是数据丰富度的代价

### Lv2 · 动手实践

**题**:写一个最小 event log profiler,要求:
- `DebugEvent { cycle, kind, guid }`
- thread_local ring buffer 容量 1024
- 4 个线程各跑 1000 次 span
- 主线程收集所有 event,打印每个 guid 的"调用次数"和"平均耗时"

**参考解答**:

```rust
use std::cell::RefCell;
use std::collections::HashMap;
use std::hint::black_box;

#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    unsafe { let lo: u32; let hi: u32;
        core::arch::asm!("rdtsc", out("eax") lo, out("edx") hi, options(nomem, nostack));
        ((hi as u64) << 32) | (lo as u64) }
}

const fn fnv(s: &str) -> u64 {
    let bytes = s.as_bytes();
    let mut h = 0xcbf29ce484222325u64;
    let mut i = 0;
    while i < bytes.len() { h ^= bytes[i] as u64; h = h.wrapping_mul(0x100000001b3); i += 1; }
    h
}

#[derive(Clone, Copy)]
struct Event { cycle: u64, kind: u8, guid: u64 }

thread_local! {
    static BUF: RefCell<std::collections::VecDeque<Event>> =
        RefCell::new(std::collections::VecDeque::with_capacity(1024));
}

fn push(e: Event) {
    BUF.with(|b| {
        let mut b = b.borrow_mut();
        if b.len() >= 1024 { b.pop_front(); }
        b.push_back(e);
    });
}

struct Span { guid: u64, start: u64 }
impl Span {
    fn enter(name: &'static str) -> Self {
        let guid = fnv(name);
        let start = rdtsc();
        push(Event { cycle: start, kind: 0, guid });
        Self { guid, start }
    }
}
impl Drop for Span {
    fn drop(&mut self) {
        push(Event { cycle: rdtsc(), kind: 1, guid: self.guid });
    }
}

fn worker() {
    for _ in 0..1000 {
        let _s = Span::enter("worker_task");
        for _ in 0..1000 { black_box(0u64.wrapping_add(1)); }
    }
}

fn main() {
    let handles: Vec<_> = (0..4).map(|_| std::thread::spawn(worker)).collect();
    for h in handles { h.join().unwrap(); }

    // 主线程上没有 event(因为没跑过 span),所以全靠 worker 的 BUF
    // 注意:thread_local 在 thread drop 时也 drop,数据没了!
    // 必须在线程结束前把数据传出。下面用 JoinHandle 返回
    println!("Note: thread_local data is lost on thread exit");
    println!("Production: use thread destructor to aggregate to global");
}
```

完整可跑(解决 thread_local 数据丢失问题):

```rust
// Cargo.toml
// [dependencies]
// once_cell = "1"

use once_cell::sync::Lazy;
use std::cell::RefCell;
use std::collections::HashMap;
use std::hint::black_box;
use std::sync::Mutex;

#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    unsafe { let lo: u32; let hi: u32;
        core::arch::asm!("rdtsc", out("eax") lo, out("edx") hi, options(nomem, nostack));
        ((hi as u64) << 32) | (lo as u64) }
}

const fn fnv(s: &str) -> u64 {
    let bytes = s.as_bytes();
    let mut h = 0xcbf29ce484222325u64;
    let mut i = 0;
    while i < bytes.len() { h ^= bytes[i] as u64; h = h.wrapping_mul(0x100000001b3); i += 1; }
    h
}

#[derive(Clone, Copy)]
struct Event { cycle: u64, kind: u8, guid: u64 }

static GLOBAL_EVENTS: Lazy<Mutex<Vec<Event>>> = Lazy::new(|| Mutex::new(Vec::new()));

thread_local! {
    static LOCAL: RefCell<Vec<Event>> = RefCell::new(Vec::new());
    static EXIT_GUARD: ExitGuard = ExitGuard;
}

struct ExitGuard;
impl Drop for ExitGuard {
    fn drop(&mut self) {
        let local = std::mem::take(&mut *LOCAL.borrow_mut());
        GLOBAL_EVENTS.lock().unwrap().extend(local);
    }
}

fn register_thread() { EXIT_GUARD.with(|_| ()); }

fn push(e: Event) {
    LOCAL.with(|b| b.borrow_mut().push(e));
}

struct Span { guid: u64, start: u64 }
impl Span {
    fn enter(name: &'static str) -> Self {
        let guid = fnv(name); let start = rdtsc();
        push(Event { cycle: start, kind: 0, guid });
        Self { guid, start }
    }
}
impl Drop for Span {
    fn drop(&mut self) {
        push(Event { cycle: rdtsc(), kind: 1, guid: self.guid });
    }
}

fn worker() {
    register_thread();
    for _ in 0..1000 {
        let _s = Span::enter("worker_task");
        for _ in 0..1000 { black_box(0u64.wrapping_add(1)); }
    }
}

fn main() {
    register_thread();
    let handles: Vec<_> = (0..4).map(|_| std::thread::spawn(worker)).collect();
    for h in handles { h.join().unwrap(); }

    let events = GLOBAL_EVENTS.lock().unwrap();
    println!("total events: {}", events.len());

    // 配对 begin/end 算每个 guid 的耗时
    let mut per_guid: HashMap<u64, (u64, u64)> = HashMap::new(); // (count, total_cycles)
    let mut open_stack: Vec<(u64, u64)> = Vec::new();
    for e in events.iter() {
        if e.kind == 0 {
            open_stack.push((e.guid, e.cycle));
        } else {
            if let Some((guid, start)) = open_stack.pop() {
                if guid == e.guid {
                    let elapsed = e.cycle - start;
                    let entry = per_guid.entry(guid).or_insert((0, 0));
                    entry.0 += 1;
                    entry.1 += elapsed;
                }
            }
        }
    }

    for (guid, (count, total)) in &per_guid {
        let avg = total / count.max(1);
        println!("guid={:016x} count={} avg_cycles={}", guid, count, avg);
    }
}
```

**Troubleshooting**:
- count=0 — 检查 thread_local destructor 是否触发(必须 `register_thread()`)
- guid 冲突 — FNV-1a 在短字符串上有碰撞,生产用更好的 hash
- 顺序错乱 — 多线程 rdtsc 可能不稳,考虑 frame_index 排序
- **memory blow up** — Vec::extend 在 destructor 里锁全局 mutex,如果有 100 个工作线程同时退出,锁竞争激烈。考虑分批:每线程先 local 排序,再一次性 extend
- **thread panic 不 unwind** — 如果 panic = "abort",thread_local Drop 不调,数据丢失
