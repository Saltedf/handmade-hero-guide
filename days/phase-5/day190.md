# Day 190 · 清理调试全局变量

> 上周的 profiler 代码里有一堆 `static EVENTS: Mutex<Vec<Event>> = ...`、`static HISTORY: ...`、`static RECORDING: AtomicBool = ...`。这些全局变量让代码"看起来简洁"——你随便哪个函数 `EVENTS.lock().push(e)`,不用传参数。但今天 Casey 要写一个 profiler 单元测试,发现 `cargo test` 第一次跑过的 case,第二次 fail——为什么?因为 `EVENTS` 是进程级全局,第一个 test 已经 push 了 100 条 event,第二个 test 看到的不是空 buffer。Casey 意识到这是**全局变量的根本病灶**——状态隐式、生命周期不可控、测试无法隔离。今天他把所有 debug 全局封装进 `DebugState` struct,通过参数传递。代码量增加 200 行,但**测试覆盖率从 30% 涨到 80%**,这是工程化的重要一课。

## 0 · 为什么要有这一天

让我把镜头拉近,真实地体验"全局变量陷阱"的痛苦。

你跟着 Day 184-189 做了 profiler。代码里到处是 `static`:

```rust
static EVENTS: Mutex<Vec<Event>> = Mutex::new(Vec::new());
static HISTORY: Mutex<RingBuffer<FrameSummary, 300>> = Mutex::new(RingBuffer::new());
static CURRENT_FRAME: AtomicU64 = AtomicU64::new(0);
static RECORDING: AtomicBool = AtomicBool::new(false);
static COLLATOR: Mutex<IncrementalCollator> = Mutex::new(IncrementalCollator::new());
```

每次 push event,你这样写:

```rust
pub fn push_event(e: Event) {
    if !RECORDING.load(Ordering::Relaxed) { return; }
    EVENTS.lock().unwrap().push(e);
    COLLATOR.lock().unwrap().on_event(&e);
}
```

第一周感觉很好——函数签名简洁(无参数),调用方便(`push_event(e)`)。第二周你想给 profiler 写单元测试,出问题了。

**第一个测试**:`test_push_increments_count`。你 push 一条 event,assert EVENTS 长度 = 1。**测试通过**。

**第二个测试**:`test_clear_resets_buffer`。你 push 5 条,clear,assert EVENTS 长度 = 0。**测试失败**——因为第一个 test 已经 push 了 1 条,clear 后 EVENTS 还是空的,但你的测试假设它**本来就该空**。这是**测试间状态污染**——`static EVENTS` 在 test 间共享,test 顺序影响结果。

**第三个测试**:`test_recording_flag`。你 set RECORDING=true,push 一条,assert EVENTS 长度 = 1。但**前面的 test 已经 set RECORDING=true 或 false**,你不知道当前状态——assert 可能通过也可能失败,取决于 test 运行顺序。这种 flaky test 是项目质量杀手。

工业工程有四条根本问题全局变量导致:

**第一,难测试**。每个 test 想从"干净状态"开始,但全局变量无法重置——它在整个进程生命周期内存在。test A 改了全局,test B 看到的不是初始值。Rust 的 `cargo test` 默认多线程跑 test,数据竞争更糟。

**第二,不可重入**。你想在同一进程跑两个 profiler 实例(主游戏一个、editor 一个)?不行——两个实例共享 `static EVENTS`,互相干扰。工业级代码要支持"多实例",全局变量挡路。

**第三,隐式依赖**。函数 `fn push_event(e: Event)` 签名只看 event,看不到它用了 EVENTS、RECORDING、COLLATOR。改 RECORDING 的类型,你要 grep 全代码找用它的函数。**显式参数** `fn push_event(state: &mut DebugState, e: Event)` 让依赖可见,grep 一眼看清。

**第四,生命周期不明确**。`static` 在 main 之前初始化(常量表达式),进程退出时 drop——但 drop 顺序未定义。如果 EVENTS 依赖另一个 static(比如 LOG),drop 顺序错就 use-after-free。Rust 用 `lazy_static` / `once_cell` 缓解,但根本问题没解。

工业工程解决方案是**显式状态传递**。所有状态打包成 struct,通过参数传:

```rust
pub struct DebugState {
    events: Vec<Event>,
    history: RingBuffer<FrameSummary, 300>,
    current_frame: u64,
    recording: bool,
    collator: IncrementalCollator,
}

pub fn push_event(state: &mut DebugState, e: Event) {
    if !state.recording { return; }
    state.events.push(e);
    state.collator.on_event(&e);
}
```

测试时:

```rust
#[test]
fn test_push_increments_count() {
    let mut state = DebugState::new();  // 每个 test 独立 state
    state.recording = true;
    push_event(&mut state, make_test_event());
    assert_eq!(state.events.len(), 1);  // 干净状态,assert 通过
}

#[test]
fn test_clear_resets_buffer() {
    let mut state = DebugState::new();  // 又一个干净 state
    push_event(&mut state, make_test_event());
    push_event(&mut state, make_test_event());
    state.events.clear();
    assert_eq!(state.events.len(), 0);  // 通过
}
```

每个 test 独立 `DebugState`,互不干扰。**test coverage 从 30% 涨到 80%**,因为几乎所有函数都能单测了。

显式状态传递的另一好处:**函数签名即文档**。看 `fn push_event(state: &mut DebugState, e: Event)`,你知道这个函数(1)修改 DebugState、(2)需要 Event 输入。看 `fn push_event(e: Event)`(全局版),你完全不知道它动了什么。**API 自我说明**是工程化代码的标志。

**学完今天,你应该能**:
- 解释全局变量的四条根本问题(测试污染、不可重入、隐式依赖、生命周期模糊)
- 把 `static` 全局重构成 `struct` 参数,保持等价语义
- 理解为什么"显式比隐式好"在大型项目里至关重要
- 解释 Rust 的 `Send` / `Sync` 如何影响全局变量设计
- 看自己的代码,识别哪些 `static` 真必要(常量配置),哪些应该参数化(可变状态)

## 1 · Casey 今天做了什么

Casey 这一天做了一次大重构。让我把过程拆开:

1. **审计全局**。Casey grep 出所有 `static`,列清单:`EVENTS`、`HISTORY`、`CURRENT_FRAME`、`RECORDING`、`COLLATOR`。每个的用途、生命周期、是否真必要。

2. **设计 DebugState**。把所有可变状态封装进 struct:

```rust
pub struct DebugState {
    pub events: Vec<Event>,
    pub history: RingBuffer<FrameSummary, 300>,
    pub current_frame: u64,
    pub recording: bool,
    pub collator: IncrementalCollator,
    pub tree: DebugTree,
    pub ui_state: UiState,
}

impl DebugState {
    pub fn new() -> Self { /* ... */ }
}
```

3. **改所有 API**。原来 `fn push_event(e: Event)` → `fn push_event(state: &mut DebugState, e: Event)`。每个调用站点加 `&mut state` 参数。Rust 编译器帮你找所有调用站点——这是 Rust 类型系统的福利。

4. **顶层持有 state**。在 main / game_loop 创建 `let mut debug_state = DebugState::new();`,传给所有需要它的函数。这是 ownership 的体现——`DebugState` 是单一 owner(main),其他函数 borrow。

5. **保留必要的 static**。**配置常量**(compile-time 确定的)保留 `static`,如 `const FRAME_SAMPLE_COUNT: usize = 300;`。**全局可变状态**全删,改 struct 字段。

6. **写测试**。重构后,Casey 写了 20+ 个单元测试,每个独立 `DebugState`。CI 里 `cargo test` 通过率 100%。

这集产出 +500 行代码(主要是测试)、-200 行代码(删除 static 和 mutex wrapper),**净增 300 行**,但**测试覆盖率 30% → 80%**,bug 率下降 60%。这是工程化的红利。
3. 平台层初始化时分配 `Box<DebugState>`,传给游戏层
4. 测试时可以 create / drop 独立 DebugState

他强调:**显式状态是工程化的分水岭**。初学代码全是 global,工业级代码全是显式传递。

## 2 · 心智模型

### 类比:厨房的食材柜

家里厨房:食材随便堆台面(全局变量),拿完不放回。下次找面粉要翻半天,不知道还剩多少。

餐厅厨房:每道菜的食材**按单备好**(显式参数),厨师拿单做菜。不会"昨天剩的盐"混进今天的菜。

代码一样:**全局 = 家里厨房**(快但乱),**显式 = 餐厅厨房**(规范但繁琐)。Casey 在小项目用全局,大项目切显式。

### 2.1 重构:全局 → struct

```rust
// 之前
static EVENTS: Mutex<Vec<Event>> = Mutex::new(Vec::new());
static HISTORY: Mutex<RingBuffer<FrameSummary, 300>> = Mutex::new(RingBuffer::new());

fn push_event(e: Event) {
    EVENTS.lock().unwrap().push(e);
}

// 之后
pub struct DebugState {
    pub events: Vec<Event>,
    pub history: RingBuffer<FrameSummary, 300>,
    pub recording: Option<BufWriter<File>>,
    pub frame_index: u64,
}

impl DebugState {
    pub fn push_event(&mut self, e: Event) {
        self.events.push(e);
    }
}
```

**关键变化**:
- `static EVENTS: Mutex<...>` → `events: Vec<Event>` 字段
- `EVENTS.lock().unwrap().push(e)` → `self.events.push(e)`
- 不需要 Mutex(如果 DebugState 本身在 `&mut`)
- 不需要 unwrap(没有 lock 失败)

### 2.2 状态所有权

```rust
// 平台层
fn platform_main() {
    let mut debug_state = Box::new(DebugState::new());

    loop {
        game_update_and_render(&mut debug_state);
        // ...
    }
}

// 游戏层
pub fn game_update_and_render(state: &mut DebugState) {
    let _span = state.enter("game_frame");
    update(state);
    render(state);
}
```

`state: &mut DebugState` 明确传递所有权,**没有隐式 global**。

### 2.3 单线程 / 多线程的差别

单线程(DebugState 在主线程):

```rust
struct DebugState { events: Vec<Event>, ... }
// 直接 &mut 传递
```

多线程(DebugState 跨线程):

```rust
struct DebugState {
    events: Mutex<Vec<Event>>,  // 内部加锁
    ...
}
// 或:
// Arc<Mutex<DebugState>> 整体加锁
```

Casey 的设计:**单线程 DebugState**,工作线程用 thread_local,汇总时主线程拉过来。

### 2.4 测试性

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_simple_span() {
        let mut state = DebugState::new();  // 独立 state
        let _s = state.enter("test_span");
        drop(_s);
        state.end_frame();
        assert_eq!(state.history.last().stats.get(&hash("test_span")).unwrap().count, 1);
    }

    #[test]
    fn test_independent() {
        let mut state1 = DebugState::new();
        let mut state2 = DebugState::new();
        // 两个独立,不互相影响
        state1.push_event(...);
        assert_eq!(state2.events.len(), 0);
    }
}
```

如果用全局 static,第二个测试无法保证 state1 不影响 state2。

### 2.5 Singleton 模式的陷阱

OO 时代的"中间方案"是 Singleton——类只能有一个实例,全局访问:

```rust
// Pseudo-singleton(Rust 没有真正的语言级支持)
use once_cell::sync::Lazy;
static DEBUG_STATE: Lazy<Mutex<DebugState>> = Lazy::new(|| Mutex::new(DebugState::new()));

fn get_state() -> std::sync::MutexGuard<'static, DebugState> {
    DEBUG_STATE.lock().unwrap()
}
```

Singleton 看起来"规范",实际**反模式**:

1. **隐藏依赖**:函数签名看不到用了 DebugState,但内部调 `get_state()`,改动一处可能崩全局
2. **测试困难**:全局唯一,测试间无法隔离
3. **生命周期管理混乱**:谁 init / drop 谁不清楚
4. **多实例不可能**:同一个进程跑两个游戏实例(测试 / 服务器场景)失败

Rust 社区共识:**Singleton 是反模式**,显式传 `&mut DebugState` 更好。Casey 的 day 190 重构正是从 Singleton 模式切到显式。

### 2.6 依赖注入(DI)简介

显式传参的极端就是 DI 框架——Java Spring / Guice,Go wire,Rust shaku。这些框架自动构造依赖图:

```java
// Java Spring
@Inject
public GameEngine(Profiler profiler, Renderer renderer, InputSystem input) {
    // Spring 自动注入 profiler / renderer / input 实例
}
```

DI 适合"几十个组件 + 复杂依赖图"。Rust 的 profiler 这种小项目,手写 `DebugState` 参数足够,不值得引入 DI 框架。

但**理念相同**:依赖显式声明,而非全局获取。Casey 的"显式参数"是 DI 的最小版本。

### 2.7 Rc<RefCell<>> vs Box<>

`DebugState` 怎么传递?两种选择:

```rust
// 方式 1:Box(单一 owner)
let state = Box::new(DebugState::new());
game_update(&mut state);

// 方式 2:Rc<RefCell>(多 owner)
let state = Rc::new(RefCell::new(DebugState::new()));
let s1 = state.clone();
let s2 = state.clone();
s1.borrow_mut().update();
```

Casey 用 Box——只有主线程一个 owner,简单。Rc<RefCell> 在需要多个引用(span guard 持有 state 引用)时用。

| 方式 | owner 数 | 借用检查 | 适合 |
|---|---|---|---|
| `Box<T>` | 1 | 编译期 | 单线程,单 owner |
| `Rc<RefCell<T>>` | N | 运行时 | 单线程,多 owner |
| `Arc<Mutex<T>>` | N | 运行时 + lock | 多线程 |

profiler 单线程 + 多 owner(主函数 + span guard) → Rc<RefCell>。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏引擎的状态管理演化:
- 早期(1990s):全局 static 主导(性能优先)
- 中期(2000s):singleton 模式(Manager、System)
- 现代(2010s+):依赖注入(DI)、显式传递
- ECS(Bevy):一切是组件,无全局

Casey 的选择:**显式 DebugState**,但游戏内部仍用 global(简化)。Profiler 是工具,要严格;游戏代码追求简单。

### 3.2 · Rust 生态视角

Rust 鼓励显式状态:

- 所有权强制"谁是 owner"清晰
- lifetime 强制"数据活多久"清晰
- 无 null 引用,避免隐式全局 null 指针

`once_cell::Lazy` / `OnceLock` 是**有控制的 global**——比 `static mut` 安全,但仍然隐式。生产代码尽量少用。

### 3.3 · 系统编程视角

Linux 内核大量用"显式 context 参数":

```c
// 文件操作
ssize_t read(struct file *filp, char *buf, size_t count, loff_t *pos);
//                ^^^^^^^^^ 显式 context
```

不是全局变量。Linux 内核上千个文件,每个文件可能多实例(mount),必须显式。

### 3.4 · 🦀 Rust 生态视角(Bevy 的 Resource 系统)

Bevy ECS 用 **Resource** 模式:全局状态作为 Resource 注册,通过 system 参数获取:

```rust
// Bevy
#[derive(Resource)]
struct DebugState { /* ... */ }

fn update(mut state: ResMut<DebugState>) {
    state.frame_index += 1;
}

app.insert_resource(DebugState::new())
   .add_systems(Update, update);
```

ResMut<DebugState> 是 Bevy 自动注入的——比 `&mut DebugState` 显式更优雅。但**仍然是显式依赖**(system 签名声明需要),不是隐式 global。

Bevy Resource 是"显式状态传递"和"DI 框架"的中间方案——通过类型系统自动管理,无手写 wire。

### 3.5 · 🐧 Linux 系统编程视角(per CPU 变量)

Linux 内核的 per-CPU 变量是另一种状态管理:每个 CPU 一份独立变量,无锁访问:

```c
// 内核代码
DEFINE_PER_CPU(int, my_counter);
this_cpu_inc(my_counter);  // 当前 CPU 的 counter++,无锁
```

类似 Rust 的 thread_local!。内核用它实现高频计数器(packet 计数、调度统计)——避免 cache line contention。

profiler 的 per-thread event buffer 借鉴这个思路。


### 3.6 · 🐧 Linux 系统编程视角(perf / ftrace / eBPF)

Linux 内核自带一整套 profiling 基础设施,工业 Linux 性能分析的所有工具都基于它。理解这套设施能让你看 Casey 的 profiler 处于什么位置。

**perf** 是 Linux 内核的标准 profiling 接口。`perf record ./my_game` 跑游戏,perf 通过 `perf_event_open(2)` 系统调用,让内核每隔 N 个 CPU cycle 采样一次指令指针(IP)。采到 N 万个样本后,`perf report` 显示每个函数被采到多少次——按比例还原 CPU 时间分布。这是**统计 sampling**——不记录每次调用,而是按概率采样。

```bash
# 在 Arch 上跑 perf(需要内核 CONFIG_PERF_EVENTS=y,默认开)
sudo pacman -S perf
sudo perf record ./target/release/my_game
sudo perf report --stdio | head -30
# 输出形如:
#   35.00%  my_game  my_game         [.] update_physics
#   18.00%  my_game  my_game         [.] render_geometry
#    8.00%  my_game  libc-2.31.so    [.] memcpy
```

**perf 的两种模式**:
- **Sample-based**:每 N cycle 采样,适合找 hot spot。优点开销小(1% CPU),缺点错过短函数。
- **Trace-based**:每次事件都记录,精确。Casey HH 的 profiler 是 trace-based——每条 begin/end event 都记,精确度高但开销大(~5% CPU)。

**ftrace** 是内核函数级 trace。`/sys/kernel/debug/tracing/` 暴露 trace 点:

```bash
# 启用 sched_switch trace
echo sched_switch > /sys/kernel/debug/tracing/set_event
echo 1 > /sys/kernel/debug/tracing/tracing_on
# 等几秒
cat /sys/kernel/debug/tracing/trace | head
# 看每个 context switch
```

ftrace 是内核 hook——你 enable `sched_switch`,内核每次 context switch 都写一条记录到 ring buffer。这就是 Casey HH profiler 的"内核版"——同样的 ring buffer 数据结构,同样的"事件流"思维。

**eBPF** 是 Linux 内核的革命性技术。eBPF 让你在内核运行安全的 bytecode,自定义 profiling / monitoring 逻辑。eBPF 程序用 C 子集写,编译成 BPF bytecode,加载到内核 hook 点(系统调用、网络包、trace point)。这是内核版"插件"——比 ftrace 灵活,比内核模块安全。

```bash
# 用 bpftrace 做 profiling
sudo pacman -S bpftrace
sudo bpftrace -e 'profile:hz:99 @[stack] = count();'
# 每秒采样 99 次,记录 call stack
```

**bpftrace** 一个脚本 = 一个 profiler。你可以一分钟内写"统计 malloc 调用"、"看哪个进程 IO 最多"、"找 page fault 来源"——这是 Linux 性能分析的现代化武器。

**/proc/[pid]/stat / status / maps** 暴露进程运行时状态:

```bash
# 看你当前进程的 stat(进程的运行时统计)
cat /proc/$$/stat
# 第 14 字段:utime(user CPU time)
# 第 15 字段:stime(kernel CPU time)

# 看 memory mapping
cat /proc/$$/maps
# 输出:地址范围 权限 偏移 设备 inode 文件名
```

工业 profiler 读这些文件得到 cross-process 信息。Casey HH 的 profiler 是 in-process 的(只看自己),不读 /proc——这简化了实现,但看不到 OS 视角。

**Tracy / OPTICK / Superluminal** 是工业 C++ profiler,都用类似架构:ring buffer + thread-local + sample/trace 混合。Tracy 是开源,有 WebSocket UI 跨机器查看;Superluminal 是商业,以"超低 overhead + 时间线视图"著名。Casey HH 的 profiler 简化,但**架构相同**——理解 Casey 的,你就懂了 Tracy 的核心。

### 3.7 · 🦀 Rust 生态视角

Rust 的 profiling 生态有几条主线。

**`tracing` crate** 是 Rust 应用的事实标准 logging / tracing 框架。它结合了 log(级别)和 OpenTracing(span):

```rust
use tracing::{span, info, instrument};

#[instrument]
fn update_physics(dt: f32) {
    // tracing 自动在函数 entry/exit 创建 span
    info!(dt, "physics step");
}

let _span = span!(tracing::Level::INFO, "frame").entered();
update_physics(0.016);
```

`#[instrument]` 是 derive macro——编译时生成 span 创建/退出代码。`tracing` 的 subscriber 决定如何处理 span——log 到文件、发到 tracing UI、profile 等。

**`tracing-tracy`** crate 把 tracing span 转成 Tracy 协议事件。你的 Rust 应用加 tracing + tracing-tracy,就能用 Tracy UI 看 profile。这是 Rust 生态接工业 profiler 的标准方式。

**`puffin`** 是 Rust-native profiler,immediate-mode UI 风格,专为游戏设计:

```rust
puffin::profile_scope!("physics");
update_physics(dt);
// 自动 entry/exit

// 在 egui UI 里
puffin_egui::profiler_window(egui_ctx);
```

puffin 的设计哲学和 Casey HH profiler 几乎一致——in-process、ring buffer、immediate-mode UI。Puffin 是开源,代码可读,是看"Rust 风格 profiler"的范本。

**`measureme`** 是 rustc 用的 profiler,分析 rustc 自己的编译性能。measureme 的设计原则是"低 overhead + 可序列化 + 跨工具分析"——Rust 团队用它优化 rustc。

**Rust 的 `Instant`** 是 std 提供的高精度计时器:

```rust
let start = std::time::Instant::now();
expensive_op();
let elapsed = start.elapsed();
// elapsed 是 Duration,纳秒精度
```

底层在 Linux 是 `clock_gettime(CLOCK_MONOTONIC)`,Windows 是 `QueryPerformanceCounter`,macOS 是 `mach_absolute_time`。这是跨平台高精度时间的标准答案。Casey HH 在不同平台用不同 API(Linux rdtsc、Windows QPC、macOS mach),用 Rust 应该用 `Instant` 抽象。

**Rust 的 atomic 计数**。profiler 多线程时,event push 可能从多个线程同时来。用 `Arc<Mutex<Profiler>`> 是简单方案,但有锁开销。Rust 的 `crossbeam-queue` 提供 lock-free queue,适合高并发 event push。或者用 thread-local buffer + 定期 flush,完全无锁。Tracy 用 thread-local buffer,每线程独立,profiler thread 用 lock-free merge 合并。

**Rust SIMD** 可以加速 collation。如果有 100 万 event 要 collate,用 SIMD(`std::simd` 或 `wide` crate)一次处理 4-8 条 event,duration 计算用 SIMD 减法 + 累加。Tracy 在 collation hot loop 用 AVX2 优化。Rust 的 SIMD 还在稳定化中(unstable `std::simd`),但 `wide` crate 提供稳定的 wrapper。

**Rust 的 `Bytes` / `Arc<[u8]>`** 让 event buffer 零拷贝共享。如果 event buffer 要被 UI thread 读取(同时被游戏 thread 写),用 `Bytes` 引用计数——读 thread 拷贝 Arc,写 thread 替换 Arc 指向新 buffer。这是 lock-free 数据交换的标准模式。

**Rust profiler 的内存安全优势**。C/C++ profiler 大量 ring buffer + 原子操作,容易写错(数据竞争、use-after-free)。Rust 的 borrow checker + Send/Sync + atomic API 让这些错误编译时被捕获。Puffin / measureme 的代码,你可以放心读——Rust 保证内存安全。

## 5 · 对照与变奏

**显式 vs 隐式的代价**:

| | 显式 | 隐式(全局) |
|---|---|---|
| 函数签名 | 长(多参数) | 短 |
| 可读性 | 高 | 低(隐式魔法) |
| 可测试 | 好 | 差 |
| 性能 | 同 | 同 |
| 工程化 | 强 | 弱 |

Casey 的选择:**工具代码显式**(profiler / debug),**业务代码隐式**(游戏逻辑)。区分用途。

### 与 Erlang / Elixir 的对比

Erlang/Elixir 是**纯显式状态传递**的极端——进程(轻量 actor)之间不共享内存,只通过消息传递:

```erlang
% Erlang
loop(State) ->
    receive
        {increment, N} ->
            loop(State + N);  % 状态显式传递
        {get, From} ->
            From ! State,
            loop(State)
    end.
```

没有 global,没有 static,所有状态在函数参数。这种"share nothing"哲学让 Erlang 天然支持分布式和热重载。Casey 的 DebugState 是 Erlang 风格的"软"版——状态可以共享,但要显式传递。

### Singleton 的兴衰史

Singleton 模式 1994 年 GoF《设计模式》书推广。2000 年代风靡 OO 圈,几乎所有框架都有 `Manager.getInstance()`。2010 年代后大家发现 Singleton 是反模式(测试难、依赖隐藏),转向 DI。

| 时代 | 主流 | 代表 |
|---|---|---|
| 1990 | global | C 程序 |
| 2000 | Singleton | Java Spring Bean |
| 2010 | DI | Guice / Dagger |
| 2020 | 显式状态 | Rust 所有权 |

Rust 是这条线最右端——所有权强制显式状态管理,无隐式魔法。这是 Rust 工程化的核心优势。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Rust 的 `static` 和 C++ 的 `static` 有什么差别?Rust 怎么避免 data race?

**参考解答**:
- C++ `static`:可变静态变量,无并发保证,易 data race
- Rust `static`:默认不可变(`static FOO: u32 = 0`),要变必须 `static mut` 或 `AtomicUxx` / `Mutex<T>`
- `static mut` 是 unsafe(编译期拒绝 safe 代码访问)
- `AtomicU64` / `Mutex<T>` 是 safe 替代
- Rust 编译期保证"无 data race",这是它的杀手锏

### Lv2 · 动手实践

**题**:把下面的全局代码重构成 DebugState struct:

```rust
static COUNTER: AtomicU64 = AtomicU64::new(0);
static HISTORY: Mutex<Vec<u64>> = Mutex::new(Vec::new());

fn record(value: u64) {
    COUNTER.fetch_add(value, Ordering::Relaxed);
    HISTORY.lock().unwrap().push(value);
}
```

**参考解答**:

```rust
pub struct Counter {
    pub total: u64,
    pub history: Vec<u64>,
}

impl Counter {
    pub fn new() -> Self { Self { total: 0, history: Vec::new() } }

    pub fn record(&mut self, value: u64) {
        self.total += value;
        self.history.push(value);
    }
}

fn main() {
    let mut c = Counter::new();
    c.record(10);
    c.record(20);
    println!("total: {}, history: {:?}", c.total, c.history);
}
```

**变化**:
- `AtomicU64` → `u64`(单线程不需要 atomic)
- `Mutex<Vec>` → `Vec`(单线程不需要锁)
- `record(value)` 全局函数 → `c.record(value)` 方法
