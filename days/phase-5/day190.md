# Day 190 · 清理调试全局变量

> Day 189 之前的代码用了大量全局变量(global state),Day 190 Casey 把它们封装成 struct,把状态显式化。这是工程化的关键一步:测试性、可重入性。

## 0 · 为什么要有这一天

之前几天的代码长这样:

```rust
// 各种全局
static EVENTS: Mutex<Vec<Event>> = ...;
static HISTORY: Mutex<RingBuffer<FrameSummary, 300>> = ...;
static CURRENT_FRAME: AtomicU64 = ...;
static RECORDING: AtomicBool = ...;
```

这种全局变量代码有几个根本问题:

1. **难测试**:全局状态无法重置,测试间互相污染
2. **不可重入**:同时跑两个 profiler 实例不行
3. **隐式依赖**:函数签名看不到用了什么状态,改一处可能崩全局
4. **生命周期不明确**:全局变量生命周期 = 进程,什么时候 init / drop 不清楚

今天 Casey 把所有全局封装进 `DebugState` struct,通过参数传递。改完后:

- profiler 测试可以 spawn 一个独立 DebugState
- 同一进程可以跑两个 profiler(虽然罕见)
- 函数签名明确

心理锚点:看完今天,你能区分"全局变量"和"显式状态传递",并知道为什么显式更好。

## 1 · Casey 今天做了什么

Casey 把所有 debug 相关全局封装:

1. 创建 `DebugState { events, history, recording, ... }`
2. 所有 profiler API 改成 `&mut DebugState` 参数
3. 平台层初始化时分配 `Box<DebugState>`,传给游戏层
4. 测试时可以 create / drop 独立 DebugState

他强调:**显式状态是工程化的分水岭**。初学代码全是 global,工业级代码全是显式传递。

## 2 · 心智模型

### 类比:厨房的食材柜

家里厨房:食材随便堆台面(全局变量),拿完不放回。下次找面粉要翻半天,不知道还剩多少。

餐厅厨房:每道菜的食材**按单备好**(显式参数),厨师拿单做菜。不会"昨天剩的盐"混进今天的菜。

代码一样:**全局 = 家里厨房**(快但乱),**显式 = 餐厅厨房**(规范但繁琐)。Casey 在小项目用全局,大项目切显式。

### 2.1 重构:全局 → struct

```rust
// 之前
static EVENTS: Mutex<Vec<Event>> = Mutex::new(Vec::new());
static HISTORY: Mutex<RingBuffer<FrameSummary, 300>> = Mutex::new(RingBuffer::new());

fn push_event(e: Event) {
    EVENTS.lock().unwrap().push(e);
}

// 之后
pub struct DebugState {
    pub events: Vec<Event>,
    pub history: RingBuffer<FrameSummary, 300>,
    pub recording: Option<BufWriter<File>>,
    pub frame_index: u64,
}

impl DebugState {
    pub fn push_event(&mut self, e: Event) {
        self.events.push(e);
    }
}
```

**关键变化**:
- `static EVENTS: Mutex<...>` → `events: Vec<Event>` 字段
- `EVENTS.lock().unwrap().push(e)` → `self.events.push(e)`
- 不需要 Mutex(如果 DebugState 本身在 `&mut`)
- 不需要 unwrap(没有 lock 失败)

### 2.2 状态所有权

```rust
// 平台层
fn platform_main() {
    let mut debug_state = Box::new(DebugState::new());

    loop {
        game_update_and_render(&mut debug_state);
        // ...
    }
}

// 游戏层
pub fn game_update_and_render(state: &mut DebugState) {
    let _span = state.enter("game_frame");
    update(state);
    render(state);
}
```

`state: &mut DebugState` 明确传递所有权,**没有隐式 global**。

### 2.3 单线程 / 多线程的差别

单线程(DebugState 在主线程):

```rust
struct DebugState { events: Vec<Event>, ... }
// 直接 &mut 传递
```

多线程(DebugState 跨线程):

```rust
struct DebugState {
    events: Mutex<Vec<Event>>,  // 内部加锁
    ...
}
// 或:
// Arc<Mutex<DebugState>> 整体加锁
```

Casey 的设计:**单线程 DebugState**,工作线程用 thread_local,汇总时主线程拉过来。

### 2.4 测试性

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_simple_span() {
        let mut state = DebugState::new();  // 独立 state
        let _s = state.enter("test_span");
        drop(_s);
        state.end_frame();
        assert_eq!(state.history.last().stats.get(&hash("test_span")).unwrap().count, 1);
    }

    #[test]
    fn test_independent() {
        let mut state1 = DebugState::new();
        let mut state2 = DebugState::new();
        // 两个独立,不互相影响
        state1.push_event(...);
        assert_eq!(state2.events.len(), 0);
    }
}
```

如果用全局 static,第二个测试无法保证 state1 不影响 state2。

### 2.5 Singleton 模式的陷阱

OO 时代的"中间方案"是 Singleton——类只能有一个实例,全局访问:

```rust
// Pseudo-singleton(Rust 没有真正的语言级支持)
use once_cell::sync::Lazy;
static DEBUG_STATE: Lazy<Mutex<DebugState>> = Lazy::new(|| Mutex::new(DebugState::new()));

fn get_state() -> std::sync::MutexGuard<'static, DebugState> {
    DEBUG_STATE.lock().unwrap()
}
```

Singleton 看起来"规范",实际**反模式**:

1. **隐藏依赖**:函数签名看不到用了 DebugState,但内部调 `get_state()`,改动一处可能崩全局
2. **测试困难**:全局唯一,测试间无法隔离
3. **生命周期管理混乱**:谁 init / drop 谁不清楚
4. **多实例不可能**:同一个进程跑两个游戏实例(测试 / 服务器场景)失败

Rust 社区共识:**Singleton 是反模式**,显式传 `&mut DebugState` 更好。Casey 的 day 190 重构正是从 Singleton 模式切到显式。

### 2.6 依赖注入(DI)简介

显式传参的极端就是 DI 框架——Java Spring / Guice,Go wire,Rust shaku。这些框架自动构造依赖图:

```java
// Java Spring
@Inject
public GameEngine(Profiler profiler, Renderer renderer, InputSystem input) {
    // Spring 自动注入 profiler / renderer / input 实例
}
```

DI 适合"几十个组件 + 复杂依赖图"。Rust 的 profiler 这种小项目,手写 `DebugState` 参数足够,不值得引入 DI 框架。

但**理念相同**:依赖显式声明,而非全局获取。Casey 的"显式参数"是 DI 的最小版本。

### 2.7 Rc<RefCell<>> vs Box<>

`DebugState` 怎么传递?两种选择:

```rust
// 方式 1:Box(单一 owner)
let state = Box::new(DebugState::new());
game_update(&mut state);

// 方式 2:Rc<RefCell>(多 owner)
let state = Rc::new(RefCell::new(DebugState::new()));
let s1 = state.clone();
let s2 = state.clone();
s1.borrow_mut().update();
```

Casey 用 Box——只有主线程一个 owner,简单。Rc<RefCell> 在需要多个引用(span guard 持有 state 引用)时用。

| 方式 | owner 数 | 借用检查 | 适合 |
|---|---|---|---|
| `Box<T>` | 1 | 编译期 | 单线程,单 owner |
| `Rc<RefCell<T>>` | N | 运行时 | 单线程,多 owner |
| `Arc<Mutex<T>>` | N | 运行时 + lock | 多线程 |

profiler 单线程 + 多 owner(主函数 + span guard) → Rc<RefCell>。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏引擎的状态管理演化:
- 早期(1990s):全局 static 主导(性能优先)
- 中期(2000s):singleton 模式(Manager、System)
- 现代(2010s+):依赖注入(DI)、显式传递
- ECS(Bevy):一切是组件,无全局

Casey 的选择:**显式 DebugState**,但游戏内部仍用 global(简化)。Profiler 是工具,要严格;游戏代码追求简单。

### 3.2 · Rust 生态视角

Rust 鼓励显式状态:

- 所有权强制"谁是 owner"清晰
- lifetime 强制"数据活多久"清晰
- 无 null 引用,避免隐式全局 null 指针

`once_cell::Lazy` / `OnceLock` 是**有控制的 global**——比 `static mut` 安全,但仍然隐式。生产代码尽量少用。

### 3.3 · 系统编程视角

Linux 内核大量用"显式 context 参数":

```c
// 文件操作
ssize_t read(struct file *filp, char *buf, size_t count, loff_t *pos);
//                ^^^^^^^^^ 显式 context
```

不是全局变量。Linux 内核上千个文件,每个文件可能多实例(mount),必须显式。

### 3.4 · 🦀 Rust 生态视角(Bevy 的 Resource 系统)

Bevy ECS 用 **Resource** 模式:全局状态作为 Resource 注册,通过 system 参数获取:

```rust
// Bevy
#[derive(Resource)]
struct DebugState { /* ... */ }

fn update(mut state: ResMut<DebugState>) {
    state.frame_index += 1;
}

app.insert_resource(DebugState::new())
   .add_systems(Update, update);
```

ResMut<DebugState> 是 Bevy 自动注入的——比 `&mut DebugState` 显式更优雅。但**仍然是显式依赖**(system 签名声明需要),不是隐式 global。

Bevy Resource 是"显式状态传递"和"DI 框架"的中间方案——通过类型系统自动管理,无手写 wire。

### 3.5 · 🐧 Linux 系统编程视角(per CPU 变量)

Linux 内核的 per-CPU 变量是另一种状态管理:每个 CPU 一份独立变量,无锁访问:

```c
// 内核代码
DEFINE_PER_CPU(int, my_counter);
this_cpu_inc(my_counter);  // 当前 CPU 的 counter++,无锁
```

类似 Rust 的 thread_local!。内核用它实现高频计数器(packet 计数、调度统计)——避免 cache line contention。

profiler 的 per-thread event buffer 借鉴这个思路。

## 5 · 对照与变奏

**显式 vs 隐式的代价**:

| | 显式 | 隐式(全局) |
|---|---|---|
| 函数签名 | 长(多参数) | 短 |
| 可读性 | 高 | 低(隐式魔法) |
| 可测试 | 好 | 差 |
| 性能 | 同 | 同 |
| 工程化 | 强 | 弱 |

Casey 的选择:**工具代码显式**(profiler / debug),**业务代码隐式**(游戏逻辑)。区分用途。

### 与 Erlang / Elixir 的对比

Erlang/Elixir 是**纯显式状态传递**的极端——进程(轻量 actor)之间不共享内存,只通过消息传递:

```erlang
% Erlang
loop(State) ->
    receive
        {increment, N} ->
            loop(State + N);  % 状态显式传递
        {get, From} ->
            From ! State,
            loop(State)
    end.
```

没有 global,没有 static,所有状态在函数参数。这种"share nothing"哲学让 Erlang 天然支持分布式和热重载。Casey 的 DebugState 是 Erlang 风格的"软"版——状态可以共享,但要显式传递。

### Singleton 的兴衰史

Singleton 模式 1994 年 GoF《设计模式》书推广。2000 年代风靡 OO 圈,几乎所有框架都有 `Manager.getInstance()`。2010 年代后大家发现 Singleton 是反模式(测试难、依赖隐藏),转向 DI。

| 时代 | 主流 | 代表 |
|---|---|---|
| 1990 | global | C 程序 |
| 2000 | Singleton | Java Spring Bean |
| 2010 | DI | Guice / Dagger |
| 2020 | 显式状态 | Rust 所有权 |

Rust 是这条线最右端——所有权强制显式状态管理,无隐式魔法。这是 Rust 工程化的核心优势。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Rust 的 `static` 和 C++ 的 `static` 有什么差别?Rust 怎么避免 data race?

**参考解答**:
- C++ `static`:可变静态变量,无并发保证,易 data race
- Rust `static`:默认不可变(`static FOO: u32 = 0`),要变必须 `static mut` 或 `AtomicUxx` / `Mutex<T>`
- `static mut` 是 unsafe(编译期拒绝 safe 代码访问)
- `AtomicU64` / `Mutex<T>` 是 safe 替代
- Rust 编译期保证"无 data race",这是它的杀手锏

### Lv2 · 动手实践

**题**:把下面的全局代码重构成 DebugState struct:

```rust
static COUNTER: AtomicU64 = AtomicU64::new(0);
static HISTORY: Mutex<Vec<u64>> = Mutex::new(Vec::new());

fn record(value: u64) {
    COUNTER.fetch_add(value, Ordering::Relaxed);
    HISTORY.lock().unwrap().push(value);
}
```

**参考解答**:

```rust
pub struct Counter {
    pub total: u64,
    pub history: Vec<u64>,
}

impl Counter {
    pub fn new() -> Self { Self { total: 0, history: Vec::new() } }

    pub fn record(&mut self, value: u64) {
        self.total += value;
        self.history.push(value);
    }
}

fn main() {
    let mut c = Counter::new();
    c.record(10);
    c.record(20);
    println!("total: {}, history: {:?}", c.total, c.history);
}
```

**变化**:
- `AtomicU64` → `u64`(单线程不需要 atomic)
- `Mutex<Vec>` → `Vec`(单线程不需要锁)
- `record(value)` 全局函数 → `c.record(value)` 方法

### Lv3 · 迁移设计

**题**:把 Counter 改成线程安全(多线程同时调 record),怎么改?**提示**:`Arc<Mutex<Counter>>` 或把字段改 `AtomicU64` + `Mutex<Vec>`。

**Troubleshooting**:

- **测试间状态污染** — 确认每个 #[test] 用独立 DebugState::new(),不共享 global
- **Rc 跨线程错** — 改 Arc,或用 thread_local
