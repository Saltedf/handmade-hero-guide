# Day 231 · 阶数表示(大 O)

> Day 232+ 要写排序算法,先必须理解"如何描述算法快慢"。今天 casey 讲大 O 表示法 (Big O notation):用函数渐进行为描述复杂度。这是后面 radix sort 是 O(n) 不是 O(n log n) 的理论基础。

## 0 · 为什么要有这一天

设想你刚入职一家游戏公司,前辈给你两段排序代码让你 review。

- 算法 A:1 万元素花 10ms
- 算法 B:1 万元素花 8ms

哪个快?直觉是 B。但如果:

- 算法 A 是 O(n):2 万元素花 20ms,4 万元素 40ms
- 算法 B 是 O(n²):2 万元素 32ms,4 万元素 128ms

10 万元素时:A = 100ms,B = 800ms。100 万元素:A = 1s,B = 80s。

**渐进行为决定大输入下的胜负**,不是常数因子。大 O 就是描述渐进行为的工具。

casey 今天讲大 O,为 Day 232-234 排序算法打基础。理解了 O(n) vs O(n log n) vs O(n²),你才能:

- 判断"用 quicksort 还是 radix sort"
- 估算"1M 元素排序要多久"
- 看懂任何算法论文 / 教材

心理锚点:看完今天,你能用大 O 描述自己写的每个函数的复杂度。

## 1 · Casey 今天做了什么

casey 不写代码,做了一节"算法复杂度入门"的纯讲解:

1. **大 O 定义**:O(f(n)) 表示"存在常数 c, n0,使得 n > n0 时 T(n) <= c × f(n)"
2. **常见阶数**:O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2^n)
3. **比较排序下界**:基于比较的排序最坏 O(n log n),不可改进
4. **非比较排序**:radix / counting 可达 O(n),前提是 key 是整数

这集对应 Day 232 的"具体排序算法示例"和 Day 234 的"radix sort 实现"。

## 2 · 心智模型

### 类比:工厂产能

工厂 A 每天 100 件产品,工厂 B 每天 90 件。直觉 B 弱。但:

- A 用工人数量 × 工人产能(n 个工人 n 件,O(n))
- B 用自动化机器:固定时间生产 90 件,不随工人增加(O(1))

1000 件需求时:A 雇 1000 人,B 还是 1 机器。10000 件:A 10000 人(贵),B 还是 1 机器(便宜)。

大 O 描述"输入 → 资源"的渐近关系,不是绝对值。

### 2.1 大 O 形式化定义

函数 T(n) 是 O(f(n)) 如果:

```
∃ c > 0, n0 ≥ 1, ∀ n > n0: |T(n)| ≤ c × |f(n)|
```

翻译:存在常数 c 和 n0,使得所有 n > n0 时,T(n) 不超过 c × f(n)。

直观:**忽略常数和低阶项**,只看主导项。

例子:

- T(n) = 3n + 5 → O(n)
- T(n) = 2n² + 100n + 7 → O(n²)
- T(n) = n log n + n → O(n log n)

### 2.2 常见阶数比较

```
输入大小 n:    1      10      100     1000     10000
O(1):         1       1        1        1         1
O(log n):     0      3        7       10        13
O(n):         1      10      100     1000     10000
O(n log n):   0     33      664    10000    133000
O(n²):        1     100    10000  1000000  100000000
O(2^n):       2    1024    10^30    (崩溃)    (崩溃)
```

注意 O(2^n) 在 n=100 时已经超过宇宙原子数。**指数算法不可扩展**。

### 2.3 比较排序的下界

基于比较的排序(quick / merge / heap / insertion):

- 每次比较得到 1 bit 信息(两个数谁大)
- N 个数有 N! 种排列,需要 log2(N!) bits 信息
- Stirling 近似:log2(N!) ≈ N log N - N
- 所以最少 N log N 次比较

**这是信息论下界,不可突破**。所有比较排序最快 O(n log n)。

### 2.4 非比较排序突破下界

如果 key 是整数(不是任意对象),用 key 的 bit 模式直接定位,不用比较:

- **Counting sort**:O(n + k),k 是 key 取值范围
- **Radix sort**:O(d × (n + b)),d 是位数,b 是基数(常用 256,即 byte)

radix 64-bit 整数:d = 8 byte,所以 O(8n) = O(n)。**比 O(n log n) 快**,但只对整数 key 适用。

casey Day 234 用 radix 排 sort key(u64),完美适用。

### 2.5 均摊复杂度

某些操作偶尔慢、通常快。均摊 (amortized) 把代价平均:

- `Vec::push` 通常 O(1),偶尔 O(n)(扩容)
- 均摊 O(1):N 次 push 总 O(N),每次均摊 O(1)

类似保险:大事件分摊到日常,每次小成本。

#### 均摊的精确推演:Vec::push 为什么是均摊 O(1)

让我们把这件事彻底讲透。`Vec::push` 内部分配策略是**几何增长**(geometric growth):容量从 1 开始,每次满了就翻倍(2×)。

假设你 push n 个元素,n 恰好是 2 的幂(比如 1024)。容量演化:

- cap 1 → push 1 个(满了) → realloc 到 cap 2,搬 1 个
- cap 2 → push 2 个(满了) → realloc 到 cap 4,搬 2 个
- cap 4 → push 4 个(满了) → realloc 到 cap 8,搬 4 个
- ...
- cap n/2 → push n/2 个 → realloc 到 cap n,搬 n/2 个

总搬迁代价:1 + 2 + 4 + ... + n/2 = n - 1。这是**所有扩容的搬迁总和**。加上 n 次 push 本身的 O(1) 写入,总代价 2n - 1,也就是 O(n)。

n 次 push 总 O(n),每次 push **均摊** O(1)。这是经典的"geometric growth 保证均摊常数"证明。

**反例:linear growth 不行**。如果每次扩容只 +1(从 cap k 扩到 cap k+1),那么 push n 次的扩容搬迁是 1+2+3+...+(n-1) = O(n²)。每次均摊 O(n),灾难。这就是为什么所有合理的动态数组都几何增长。

**均摊的两种形态**:
- **aggregate method**:总代价除以操作数(上面用的)
- **accounting / potential method**:每次操作预付"代价硬币",大事件用积攒的硬币付。Rust 标准库文档说"amortized O(1)"就是 aggregate 含义。

#### 均摊 vs worst case:实战权衡

`Vec::push` 均摊 O(1),但单次最坏 O(n)(扩容那一刻)。这在大多数场景没问题——整体吞吐好就行。但**实时游戏**不能接受最坏 O(n) 的卡顿。

实时场景的方案:
- **`Vec::reserve(n)`** 提前分配,避免 push 时扩容
- **slab allocator / arena**:预分配大块,push 在 arena 内 O(1) worst case
- **slot map**:固定容量,索引删除 O(1) worst case(casey 在 day216 用的)

游戏主循环里,所有 hot path 操作必须 worst case O(1) 或 O(log n),不能有"偶尔 100ms"的均摊操作。这是 casey 反复强调的"frame budget"——144 FPS 下每帧 6.9ms,**任何单帧超时都会被玩家感知为卡顿**。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发的大 O 实例:

- **Sprite rendering**:O(n) n 是 sprite 数
- **Collision detection**:naive O(n²),spatial hash O(n)
- **Pathfinding**:A* 最坏 O(b^d),b 是分支因子,d 是深度
- **Sorting**:O(n log n) 或 O(n)(radix)

理解大 O 让你预判"加 100 倍敌人会卡吗?"

#### 游戏循环每个阶段的复杂度

casey 的 Handmade Hero 游戏循环,每帧执行这些操作。让我把每个的复杂度标注出来:

```
UpdateAndRender():
  ProcessInput:         O(1)       # 固定几个键
  Simulate:
    For each entity:    O(n)       # n = entity 数
      Update position
      Collision check:  O(n²) naive / O(n) spatial hash
      AI decision:      O(1) per entity
    Update camera:      O(1)
  Render:
    For each entity:    O(n)
      Draw sprite
  Debug overlay:        O(debug_state)
```

如果 n = 1000 个 entity,naive collision 是 10^6 次比较,每次 ~10ns,总 10ms——已经吃掉一帧。换成 spatial hash,O(n) ~10000 次,~100μs。这就是为什么"collision 算法选择"直接决定游戏能否运行。

casey 在 HH 中期(Phase 4)遇到过这种问题——敌人数量从 50 涨到 500 时,frame rate 从 144 掉到 30。原因就是 collision 用 naive O(n²)。换成 spatial grid 后回到 144 FPS。**这就是大 O 的实战意义**。

#### Pathfinding 的复杂度真相

A* 算法的复杂度说"O(b^d)",b 是分支因子(网格游戏的相邻格子,通常 4 或 8),d 是搜索深度(路径长度)。

但实际 A* 用优先队列 + 启发函数,平均复杂度接近 O(d log d),远好于 O(b^d)。最坏情况(启发函数失效,退化成 Dijkstra)才是 O(b^d)。

游戏实战:地图 100×100 格,A* 一次寻路典型 1000 个 node expanded,优先队列操作 O(log 1000) = 10。总 10000 次比较,~100μs。100 个敌人同时寻路,10ms 总——刚好顶一帧。所以**复杂度分析告诉你"能不能这么做",真实数据告诉你"这样做够不够"**。

#### 实时游戏的"硬约束"

144 FPS 下每帧 6.9ms。任何 single operation 不能超 1ms(否则 1 个 operation 就吃 15% 帧时间)。约束:

- 单次 lookup:O(1),目标 < 100ns
- 单次插入:O(log n) 可接受,n < 10^6 时 < 1μs
- 全帧排序:O(n log n) 可接受,n = 10000 时 ~100μs
- 全帧渲染:O(n),n = sprite 数

casey 的 debug 系统(per_guid 查询)必须 O(1),否则 debug UI 渲染就吃光 frame budget。这就是为什么 casey 在 day217 加 HashMap index——把 O(n) 全扫变成 O(1) 直接查,符合 frame budget。

### 3.2 · 图形学视角

GPU 渲染的复杂度:

- **Forward rendering**:O(N × L),N 是 pixel,L 是光源
- **Deferred rendering**:O(N + L × screen_pixels)
- **Ray tracing**:O(R × log N),R 是 rays,N 是几何

不同算法渐近性能不同,场景选择不同。

### 3.3 · Linux 系统编程视角

Linux 内核复杂度:

- **Scheduler**:CFS 红黑树,O(log n) 选 next
- **Memory allocation**:slab O(1),buddy O(log n)
- **File system lookup**:ext4 hash O(1),B+ tree O(log n)

设计内核算法时大 O 是核心考虑。

### 3.4 · Rust 生态视角

Rust 标准库文档每个 API 都标复杂度:

```rust
// Vec::push 文档
// Complexity: amortized O(1)

// HashMap::get 文档
// Complexity: O(1) average, O(n) worst

// BTreeMap::get 文档
// Complexity: O(log n)
```

读 std doc 时关注这些标注。

#### 为什么 HashMap 标 "average O(1), worst O(n)"

Rust 文档诚实标出 worst case,因为 hash table 在**所有 key 都 hash 到同一个 bucket** 时退化成 O(n) 链表扫描。这种情况出现在:

1. **Hash 碰撞攻击**:恶意用户构造大量 hash 冲突的 key,把服务器拖慢(2011 年的 PHP / Java / Tomcat DoS 攻击)。Rust 用 SipHash 作为默认哈希,带随机 seed,对抗这种攻击。
2. **Hash 函数太弱**:用 identity hash `|x| x`,对连续整数,某些 bucket 被堆积。

理解 worst case 让你知道"99.9% 时 O(1),0.1% 时 O(n)"的真实含义。在游戏实时场景,0.1% 的卡顿已经不可接受,所以游戏里常用 FxHash(非加密但快且分布好)代替 SipHash——换取稳定 O(1)。

```toml
# Cargo.toml
[dependencies]
rustc-hash = "2"
```

```rust
use rustc_hash::FxHashMap;
// FxHashMap 用 FxHash,无 SipHash 的 random seed 启动开销
// 短 key(int、小 string)快 2-3 倍,游戏 debug 系统首选
let mut m: FxHashMap<u64, f32> = FxHashMap::default();
```

#### Rust 标准库的复杂度约定

Rust std 对每个公开 API 的复杂度承诺是一种契约。如果你写公开 crate,也要标。约定:

- `O(1)` — 常数时间,和输入大小无关
- `O(log n)` — 对数
- `O(n)` — 线性
- `amortized O(1)` — 均摊,大多数 O(1) 偶尔 O(n)
- `O(n) expected, O(n²) worst` — 期望和最坏都标

学完这一节,你看到任何 Rust crate 的 doc,都能秒懂作者想告诉你的性能特性。Casey 在 HH 视频里展示排序算法时,也是这套大 O 语言——"radix sort 是 O(n)"一句话,信息量等同三段叙述。

## 5 · 对照与变奏

不同算法的渐近比较:

- **Quicksort**:平均 O(n log n),最坏 O(n²)(pivot 选不好)
- **Merge sort**:稳定 O(n log n),需要 O(n) 额外空间
- **Heapsort**:原地 O(n log n),不稳定
- **Radix sort**:O(n) 但只对整数

每种有 tradeoff,选最适合场景的。

### 5.1 排序算法 trade-off 矩阵

工业界实际选择时,要考虑的远不止大 O。让我把决策因素拆开:

| 算法 | 平均时间 | 最坏时间 | 空间 | 稳定性 | 缓存友好 | 适合 |
|---|---|---|---|---|---|---|
| Insertion | O(n²) | O(n²) | O(1) | 稳定 | 极好 | n < 32 |
| Quicksort | O(n log n) | O(n²) | O(log n) | 不稳定 | 极好 | 通用,小 n |
| Merge | O(n log n) | O(n log n) | O(n) | 稳定 | 一般 | 大数据,外部排序 |
| Heap | O(n log n) | O(n log n) | O(1) | 不稳定 | 差(随机访存) | 优先队列 |
| Timsort | O(n log n) | O(n log n) | O(n) | 稳定 | 好 | 已部分有序 |
| Counting | O(n+k) | O(n+k) | O(n+k) | 稳定 | 好 | 小范围整数 |
| Radix (LSD) | O(d·n) | O(d·n) | O(n+k) | 稳定 | 好 | 整数/字符串 |

观察几个关键点:

**Insertion sort 在小 n 反而最快**。虽然 O(n²),但常数小,cache 完美,n=16 时它比 quicksort 快 3-5 倍。Rust 标准库 `sort` 在 n < 20 时切到 insertion sort 就是这个原因。

**Heapsort 听起来 O(n log n) 和 quicksort 同阶,实际慢一倍**。原因:heap 反复访问 `arr[parent(i)]` 和 `arr[child(i)]`,这些位置随机散布,cache miss 严重。Quicksort 顺序扫描 partition,cache 完美。这就是为什么"渐近复杂度相同,实际性能不同"——**常数因子和缓存行为也重要**。

**Radix sort 是"作弊"**。它假设 key 是整数,用 bit 操作直接定位。如果 key 是浮点 / 字符串 / 任意对象,必须先比较,radix 不适用。但游戏里 sort key 经常是 u64(位置、entity ID),radix 完美。

### 5.2 工业实现的 hybrid 算法

实际生产级排序都是 hybrid —— 在不同 n 切换不同算法:

**pdqsort (Rust `sort_unstable`)**:pattern-defeating quicksort。n < 24 用 insertion sort,有大量相同元素时切 counting sort,pivot 选不好时切 heapsort(避免 O(n²))。这是 Rust 1.40+ 的默认排序。

**Timsort (Python / Java)**:merge sort + insertion sort。识别已经部分有序的"run",减少工作量。对真实世界数据(部分有序)极快。

**Glidesort (Rust 提案)**:融合 pdqsort 和 Timsort 思路,适应性更强。

casey Day 234 实现的 radix sort 不是 hybrid,是"radix only"。因为 debug 系统的 sort key 类型固定(u64),数据量大(n > 10000),radix 单一最优。但通用排序库做不到这种"假设 narrow key type",所以必须 hybrid。

### 5.3 大 O 的隐藏陷阱:常数因子

理论 O(n log n) 在 n=100 万时应该比 O(n²) 快很多。但实战中,**常数因子可能让小 n 的 O(n²) 更快**。

例子:`std::sort` (O(n log n)) vs 手写 insertion sort (O(n²)) 在 n=10:

```
std::sort:         500ns  (常数 ~50)
insertion sort:    80ns   (常数 ~8)
```

理论 O(n log n) = 10 × log(10) ≈ 33;O(n²) = 100。std::sort 应该快 3 倍,但实际慢 6 倍。原因:std::sort 的常数大(分区、递归、pivot 选择开销),insertion sort 常数极小(就是 for 循环 + 比较)。

工程教训:**小 n (n < 20-50) 永远用简单算法**。这是性能优化里的常识——casey 在 HH 视频里反复强调"don't optimize the cold path",小 n 就是 cold path。

### 5.4 大 O 的隐藏陷阱:缓存行为

CPU cache 是性能的隐形维度。两个 O(n) 的算法,缓存友好的可以快 10 倍。

**例子:matrix multiply 的 cache 优化**。朴素三重循环 O(n³),优化后的 cache-blocked 也是 O(n³),但实际快 5-10 倍。

```rust
// 朴素:cache 不友好,A[i][k] 和 B[k][j] 跳跃访问
for i in 0..n {
    for j in 0..n {
        for k in 0..n {
            c[i][j] += a[i][k] * b[k][j];
        }
    }
}

// Blocked:把矩阵分块,L1 cache 命中率高
for ii in (0..n).step_by(BLOCK) {
    for jj in (0..n).step_by(BLOCK) {
        for kk in (0..n).step_by(BLOCK) {
            // 处理 BLOCK × BLOCK 的小块,全在 cache
        }
    }
}
```

大 O 完全一样,但缓存行为天差地别。**这就是为什么不能只看大 O,还要看 memory access pattern**。GPU 编程更极端——同一个算法,coalesced memory access 和 random access 性能差 100 倍。

### 6.2 学完大 O 后的下一步

大 O 只是性能分析的入门。后续要学的:

- **Master Theorem**:递归式的复杂度计算(T(n) = aT(n/b) + f(n))
- **Cache-aware / cache-oblivious 算法**:考虑 memory hierarchy
- **Parallel complexity**:work-span model,T_∞ = critical path
- **Amortized analysis 三方法**:aggregate、accounting、potential
- **Probabilistic analysis**:期望复杂度 vs 高概率复杂度

CLRS 的第 1-3 章覆盖基础大 O,第 4 章讲 Master Theorem。Casey 的 HH 视频不深入这些(他不是算法课),但需要你**懂**这些才能跟上他的优化 reasoning。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 O(n log n) 是比较排序下界,而 radix sort 能 O(n)?radix 突破了什么?

**参考解答**:比较排序每次比较只得到 1 bit 信息(谁大),要区分 N! 排列需要 log(N!) ≈ N log N 次比较。**信息论下界**。

radix 不比较,直接用 key 的 bit。每个 byte(8 bit)做一次 bucket pass,得到 8 bit 信息。u64 有 64 bit,8 pass 就区分所有可能 key。**用更多 bit per step 突破 1 bit 限制**。

但 radix 要求 key 是整数(可分解 bit)。任意对象(无天然 bit)只能比较,O(n log n) 不可破。

### Lv2 · 动手实践

**题**:写一个函数,计算"线性查找 vs 二分查找"在数组大小 1, 10, 100, ..., 1000000 时的操作次数。打印表格。

**参考解答**:

```rust
fn linear_search(n: usize) -> usize { n / 2 }  // 平均
fn binary_search(n: usize) -> usize {
    if n <= 1 { return 0; }
    (n as f64).log2().ceil() as usize
}

fn main() {
    println!("{:>10} {:>15} {:>15}", "n", "linear O(n)", "binary O(log n)");
    for &n in &[1, 10, 100, 1000, 10000, 100000, 1000000] {
        println!("{:>10} {:>15} {:>15}",
                 n, linear_search(n), binary_search(n));
    }
}
```

**预期输出**(每行解释):
```
         n    linear O(n)  binary O(log n)
         1              0                0
        10              5                4
       100             50                7
      1000            500               10
     10000           5000               14
    100000          50000               17
   1000000         500000               20
```

观察:linear 增长 10 倍 n,操作增 10 倍(线性,斜率 1);binary 增长 10 倍 n,操作只增 ~3(log10≈3.3,这是 log n 的本质)。100 万元素时,linear 要做 50 万次比较,binary 只要 20 次——**25000 倍差距**。

这就是大 O 在实战中的威力。一个简单的算法选择,25 个数量级的性能差异。

### Lv2.5 · 实测验证(进阶)

**题**:用 criterion 实测 Rust std `slice::contains`(线性查找 O(n))vs `BTreeSet::contains`(对数查找 O(log n))。验证操作次数符合大 O 预测。

**完整 setup**:

```toml
# Cargo.toml
[dependencies]
criterion = { version = "0.5", features = ["html_reports"] }

[[bench]]
name = "lookup_scaling"
harness = false
```

```rust
// benches/lookup_scaling.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion};
use std::collections::BTreeSet;

fn bench(c: &mut Criterion) {
    let mut group = c.benchmark_group("lookup");
    for n in [100, 1000, 10000, 100000] {
        let data: Vec<u64> = (0..n as u64).collect();
        let set: BTreeSet<u64> = data.iter().copied().collect();
        let target = n as u64 / 2;  // 平均位置

        group.bench_function(format!("vec_contains_n={}", n), |b| {
            b.iter(|| data.contains(&black_box(target)));
        });
        group.bench_function(format!("btree_contains_n={}", n), |b| {
            b.iter(|| set.contains(&black_box(target)));
        });
    }
    group.finish();
}

criterion_group!(benches, bench);
criterion_main!(benches);
```

```bash
cargo bench
# 看 target/criterion/lookup/report/index.html
# 验证:vec_contains 时间随 n 线性增长
# 验证:btree_contains 时间随 n 对数增长(log-log 图斜率几乎为 0)
```

**典型结果**:
```
vec_contains_n=100:        50 ns
vec_contains_n=1000:       500 ns       (10×: O(n) 验证)
vec_contains_n=10000:      5000 ns      (10×)
vec_contains_n=100000:     50000 ns     (10×)

btree_contains_n=100:      30 ns
btree_contains_n=1000:     40 ns        (1.3×: O(log n) 验证)
btree_contains_n=10000:    50 ns        (1.25×)
btree_contains_n=100000:   60 ns        (1.2×)
```

btree 在 n=100 时已经超过 vec(常数大),但 n=100000 时快 1000 倍。这是 O(1) 常数 vs O(n) 增长率的真实代价。

### 8.1 用 benchmark 验证大 O

光看理论不够,让我们用 `criterion` 实测不同 n 下排序耗时,画 log-log 图,斜率就是大 O 的指数。

```toml
# Cargo.toml
[dependencies]
criterion = { version = "0.5", features = ["html_reports"] }

[[bench]]
name = "sort_scaling"
harness = false
```

```rust
// benches/sort_scaling.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn bench_sort(c: &mut Criterion) {
    let mut group = c.benchmark_group("sort_scaling");
    for n in [100usize, 1000, 10000, 100000] {
        let data: Vec<u64> = (0..n as u64).rev().collect();  // 倒序,最坏情况
        group.bench_function(format!("n={}", n), |b| {
            b.iter_batched(
                || data.clone(),
                |mut v| { v.sort(); black_box(v); },
                criterion::BatchSize::SmallInput,
            );
        });
    }
    group.finish();
}

criterion_group!(benches, bench_sort);
criterion_main!(benches);
```

```bash
cargo bench
# 看 target/criterion/sort_scaling/report/index.html
# 对数图上 n=100,1000,10000,100000 的耗时
# 如果斜率 ≈ 1,说明 O(n);斜率 ≈ 1.1,说明 O(n log n)
```

### 8.2 用 hyperfine 实测 wall-clock 时间

`hyperfine` 是 Arch 仓库里的命令行 benchmark 工具,适合对比不同 n 的 wall-clock。
