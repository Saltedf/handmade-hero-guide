# Day 236 · GPU 概念概览

> Day 235 你刚把 OpenGL 上下文跑起来,屏幕清成绿色就算胜利。今天 Casey 不写一行渲染代码——他要先在白板上把 GPU 是什么讲清楚。这一集没代码,但比后面任何一集都重要:你脑子里如果没有 GPU 的"形状",Day 237 写的每一个 GL 调用都是黑魔法。

## 0 · 为什么要有这一天

你过去 235 集里写的所有渲染代码,本质都是同一件事:**CPU 一行一行地往 framebuffer 写像素**。Day 037 你写了 `inline_draw_rectangle`,Day 080+ 你做了纹理采样,Day 110+ 你写了 SIMD 优化的 blit。每一行 Rust 都跑在 CPU 的 4-16 个核心上,一帧 1920×1080 = 200 万像素,你能挤进 60 FPS,因为像素的运算简单(几个加法和乘法)。

但你想做下面任何一件事,CPU 就开始吃力:

- 一个有 5000 三角形的角色网格,每帧光照重算
- 全屏后处理:模糊 / 色调映射 / 景深
- 实时阴影(每个像素要查 shadow map)
- 4K 分辨率 + 144 FPS

CPU 8 核,每核 ~10 亿操作/秒,理论上限 80 亿操作/秒。一帧 16ms 给你 1.28 亿操作。200 万像素 × 几十个操作,还行;但要算 200 万次三角函数(光照)、200 万次纹理过滤(各向异性),就吃紧了。

GPU 解决这件事:**它有几千个核心**。一个 RTX 4090 有 16384 个 CUDA core,每秒能算几十万亿次浮点运算。代价是:每个核都很"笨"——只能跑简单的程序,不能跳来跳去,不能访问任意内存,必须按"大军压上"的方式批量算。

今天的核心问题:**CPU 和 GPU 的思维方式根本不同**。CPU 是个聪明的将军,擅长复杂的战术决策;GPU 是一支纪律严明的军队,擅长同一个动作做几百万次。你不能用 CPU 的思维给 GPU 写代码,所以 Casey 用整整一集来重置你的脑回路。

心理锚点:看完今天,你应该能用 30 秒回答"为什么 GPU 不能像 CPU 那样 `if (x > 0) { ... } else { ... }`",能用 1 分钟画出"顶点数据 → 顶点着色器 → 光栅化 → 片段着色器 → framebuffer"的管线图。如果画不出来,先停在 §2。

## 2 · 心智模型

### 类比:GPU 是一支工厂流水线大军

CPU 像一个**顶级大厨**:他能同时照看 8-16 口锅,每口锅里做不同的菜(乱序执行、分支预测、大 cache)。但他贵——一颗 CPU 几千块,核数有限。

GPU 像一支**5000 个学徒的流水线**:每个学徒只会做几样简单活(切菜、拌料、烤 30 秒)。但你让他们同时对 5000 个土豆削皮,5000 个学徒并行削,2 秒搞定。一个学徒削一个土豆要 10 秒,但他不需要聪明。

**关键**:GPU 不能"思考",只能"批量执行"。你不能让 GPU 写游戏逻辑(里面有无数 if/while/状态机),但你能让它对每个像素跑同一段光照代码——5000 个像素同时算,3ms 完成。

### 2.1 CPU vs GPU 的硬件差别

```
                  CPU                         GPU
+--------------------------+      +------------------------------+
| 4-16 cores               |      | 几千个 cores(分组为 warp)   |
| 每核:L1/L2/L3 cache      |      | 每组共享 L1,无 L3            |
| 乱序执行 / 分支预测       |      | 顺序执行 / 锁步              |
| 主频:3-5 GHz            |      | 主频:1.5-2.5 GHz           |
| 擅长:复杂控制流         |      | 擅长:批量同质运算           |
| 内存:DDR5(~50 GB/s)    |      | 显存:GDDR6X(~1 TB/s)     |
+--------------------------+      +------------------------------+
        |                                  |
        +------- PCIe 5.0 (~64 GB/s) -----+
```

**关键术语解释**:

- **Core(核)**:CPU 和 GPU 都叫"core",但 GPU 的 core 简单得多——没有分支预测、没有乱序、cache 小
- **Warp / Wavefront(线程束)**:GPU 把 32 个(NVIDIA)或 64 个(AMD)core 编成一组,叫 warp。warp 内所有 core 在**同一时钟周期执行同一条指令**(SIMT,Single Instruction Multiple Threads)。这是 GPU 高吞吐的根本
- **锁步(lock-step)**:warp 里 32 个 core 必须走同一条路。如果你写 `if (x > 0) { A } else { B }`,32 个 core 里 20 个走 A、12 个走 B,那 32 个 core 先全部走 A(12 个被 mask 掉),再全部走 B(20 个被 mask 掉)——两边都要算,分歧代价大

### 2.2 CPU 怎么和 GPU 通信

CPU 和 GPU 是**两台独立的电脑**,通过 PCIe 总线连接。CPU 不能直接读写 GPU 显存,必须通过命令:

```
CPU 程序                           PCIe 总线                GPU
========                           =========                ===
1. 分配显存
   glBufferData(...)  ----------> (DMA 传输) ---------->  VRAM 分配 N 字节
2. 上传顶点数据
   glBufferSubData(...) --------> (DMA 传输) ---------->  VRAM 写入顶点
3. 上传纹理
   glTexImage2D(...)  ----------> (DMA 传输) ---------->  VRAM 写入纹素
4. 编译 shader
   glCompileShader(...) --------> (命令) ------------->  GPU 上编译 GLSL → 二进制
5. 触发绘制
   glDrawArrays(...)  ----------> (命令) ------------->  GPU 开始跑管线
                                                          ↓
                                                       [顶点着色器]
                                                       [光栅化]
                                                       [片段着色器]
                                                          ↓
                                                       framebuffer
6. (可选)回读
   glReadPixels(...) <----------- (DMA 传输) <---------  从 framebuffer 拷出
```

**关键点**:每次跨 PCIe 都是慢的(微秒级延迟,GB/s 级带宽)。游戏优化的核心原则之一是**少跨 PCIe**:把数据一次性上传到 GPU,然后反复用,不要每帧来回搬。

### 2.3 渲染管线(Rendering Pipeline)

GPU 收到 `glDrawArrays` 后,跑一条固定的"流水线",每个像素流经若干阶段:

```
顶点数据 (CPU 上传)            ← 输入
     ↓
[1] 顶点着色器(Vertex Shader)  ← 对每个顶点跑一次(可编程)
     ↓
[2] 图元装配(Primitive Assembly) ← 把顶点组成三角形 / 线段(固定)
     ↓
[3] 裁剪 + 视口变换(固定)
     ↓
[4] 光栅化(Rasterization)      ← 三角形 → 像素,固定
     ↓
[5] 片段着色器(Fragment Shader) ← 对每个像素跑一次(可编程)
     ↓
[6] 深度测试 / 混合(Per-fragment ops) ← 固定
     ↓
   framebuffer                   ← 输出
```

**阶段术语**:

- **顶点着色器(Vertex Shader)**:你写的 GPU 程序,输入一个顶点(位置 + 属性),输出变换后的位置。主要用于"模型空间 → 屏幕空间"的矩阵变换。Day 237 你会写一个最简单的:把 2D 屏幕坐标直接输出。
- **图元装配(Primitive Assembly)**:GPU 把 3 个顶点组成一个三角形。这是**固定**的,你不能改。
- **光栅化(Rasterization)**:GPU 算出"这个三角形覆盖了哪些像素"。也是固定的。每个被覆盖的像素产生一个**片段(fragment)**。
- **片段着色器(Fragment Shader)**:你写的 GPU 程序,输入一个片段(插值后的属性 + 像素坐标),输出一个颜色。Day 237 你写:从纹理采样一个颜色。

**为什么分两段可编程?** 因为顶点数 << 像素数。一个三角形 3 个顶点,但可能覆盖 10000 个像素。把"重活"放片段着色器,GPU 必须对几百万像素跑它,但每次只是采样纹理 + 几次乘加,够快。

### 2.4 shader 是什么

**shader(着色器)** = GPU 上跑的小程序。最早 shader 只能算颜色(shade = 上色),所以叫这个名字。现在 shader 干很多事:几何变换、光照、阴影、后处理。但名字沿用。

shader 用专门的**着色语言**写:

- **GLSL**(OpenGL Shading Language)—— OpenGL / WebGL 用,C-like 语法
- **HLSL**(High-Level Shading Language)—— Direct3D 用
- **MSL**(Metal Shading Language)—— Apple Metal 用,C++ 子集
- **WGSL**(WebGPU Shading Language)—— WebGPU 用,Rust-like 语法

你跟 Casey 学 OpenGL,所以用 **GLSL**。一段最简单的 GLSL 顶点着色器:

```glsl
#version 330 core
// 上面的 #version 指定 GLSL 版本(对应 OpenGL 3.3)

// 输入:每个顶点的位置(从 VBO 读)
in vec2 a_pos;     // in = 顶点属性输入;vec2 = 两个 float

// 输出:变换后的位置(GL 内置变量 gl_Position)
void main() {
    gl_Position = vec4(a_pos, 0.0, 1.0);   // vec4 = 4 个 float;x,y,z,w
}
```

**GLSL 语法对照**:

| GLSL | Rust 类比 | 含义 |
|---|---|---|
| `float` | `f32` | 单精度浮点 |
| `vec2 / vec3 / vec4` | `glam::Vec2/Vec3/Vec4` | 2/3/4 维向量 |
| `mat4` | `glam::Mat4` | 4×4 矩阵 |
| `in` | 函数参数 | 顶点属性输入 |
| `out` | 返回值(隐式) | 传给下一阶段的变量 |
| `uniform` | 全局常量 | 整个 draw call 不变的值(矩阵、纹理) |
| `sampler2D` | 无对应 | 纹理采样器 |

**uniform 是关键概念**:uniform 是 CPU 在 draw call 前设置的全局变量,整个 draw 里所有顶点/片段都读同一个值。例:你画 1000 个三角形,它们都用同一个 MVP 矩阵 → MVP 是 uniform。

### 2.5 分支分歧(Warp Divergence)的代价

回到第 2.1 节末尾的"锁步"问题。考虑片段着色器里这段:

```glsl
if (uv.x > 0.5) {
    color = texture(tex1, uv);   // 走这条路
} else {
    color = texture(tex2, uv);   // 走那条路
}
```

如果 warp 里 32 个像素,18 个 `uv.x > 0.5`,14 个不是:

1. GPU 先让 32 个 core 都进 if 分支,但只 18 个真正执行(另 14 个被 mask 阻塞,空转)
2. 然后让 32 个 core 都进 else 分支,但只 14 个执行(另 18 个空转)

**代价**:你写的"二选一",实际两边都算了。GPU 不能真的分支。

这不是说不能写 if,而是要**尽量让 warp 内的像素走同一条路**。比如不要 per-pixel 决定"画不画"——用 early-z(depth test)在 fixed function 阶段丢弃像素,比在 shader 里 if 干掉快得多。

### 2.6 CPU-GPU 异步模型

CPU 发 `glDrawArrays` 是**异步**的——这个调用立刻返回,CPU 可以继续干别的事。GPU 在后台跑这条 draw。这就是为什么 OpenGL 调用快(不阻塞),但也带来两个陷阱:

1. **状态查询会强制同步**。如果你 draw 之后立刻调 `glReadPixels`(读 framebuffer),GPU 必须先把这条 draw 跑完才能给数据,CPU 卡住等。所以 readback 是性能杀手,Day 243 讲怎么用 PBO 异步读。
2. **错误检查延迟**。shader 编译错误不会在 `glCompileShader` 立刻报,你要主动调 `glGetShaderiv` 查状态。Day 237 会写一个错误检查 helper。

**同步原语**:OpenGL 提供 `glFenceSync`——一个 fence,CPU 可以问"fence 跑到了吗?"。Day 243 用它做异步纹理下载。

---

**总结**:GPU 是一台几千核的并行电脑,通过 PCIe 和 CPU 通信。CPU 上传顶点/纹理 + shader,GPU 跑顶点着色器 → 光栅化 → 片段着色器,把结果写 framebuffer。shader 是 GPU 上的小程序,用 GLSL 写。理解这条管线是后面 25 集的基础。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏引擎的渲染器架构都围绕"CPU 喂 GPU"这件事:

- **draw call 是昂贵的**。每次 `glDrawArrays` 都有固定开销(driver 验证、命令打包、PCIe 传输)。游戏优化第一原则:**batching**——把多个物体的顶点合到一个大 buffer 里,一次 draw 画完。
- **状态切换更贵**。换 shader、换纹理、换 blend mode,都触发 driver 重配 GPU。第二原则:**sort by state**——把相同 shader 的 draw 排在一起。Day 230 的 sort key 就是干这个。
- **CPU-bound vs GPU-bound**:游戏要么卡在 CPU(算游戏逻辑、准备 draw call)、要么卡在 GPU(光栅化/片段着色器太慢)。profiler 必须分清是哪种,才知道优化哪边。
- **现代引擎用更高级 API**:Vulkan / D3D12 / Metal 显式暴露 CPU-GPU 同步,OpenGL 太自动化反而隐藏了性能陷阱。但 OpenGL 学起来快,适合教学。

Casey 后面 Day 237+ 的 OpenGL 代码是"立即模式"风格(每帧上传顶点 + draw),简单但慢。Day 240 把渲染器分层,后面会提到 persistent mapped buffer 优化。

### 3.2 · 🎨 图形学视角

GPU 管线背后的数学:

- **顶点变换**:每个顶点用 4×4 矩阵变换。模型 → 世界 → 相机 → 投影 → NDC。Day 238 你写正交投影矩阵,把屏幕坐标变到 [-1, 1] NDC。
- **重心坐标(Barycentric)**:光栅化阶段,GPU 算每个像素在三角形内的 (α, β, γ) 重心坐标。顶点属性(uv, color)按重心坐标插值到像素。
- **透视正确插值**:3D 投影后,直接线性插值 uv 会变形(近处像素稀疏、远处密集)。GPU 用 `1/w` 加权做"透视正确"插值。这是 fixed function,你不用管,但要懂为什么 3D 渲染不能 2D 直接插。
- **深度测试**:每像素有 z(深度),GPU 比较新像素和 framebuffer 里旧像素的 z,新的小才画。这是 Day 261+ 深度缓冲的基础。

色彩空间也关键:GPU 默认假设 framebuffer 是线性的,但你显示器的 sRGB 是非线性的。Day 241 Casey 启用 `GL_FRAMEBUFFER_SRGB`,让 GPU 自动 sRGB ↔ linear 转换,避免之前 Day 094 的 gamma 双重校正 bug。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上 OpenGL 的栈:

```
你的 Rust 程序
     ↓ (glow = 跨后端薄封装)
glow crate
     ↓ (libGL.so = 用户态驱动)
Mesa / NVIDIA proprietary driver
     ↓ (ioctl / DRM)
Linux DRM / KMS 内核子系统
     ↓
GPU 硬件
```

**重要术语**:

- **Mesa**:Linux 上的开源 OpenGL 实现。Intel / AMD 用户都用 Mesa。NVIDIA 用户大多用 NVIDIA 自家闭源驱动
- **DRM**(Direct Rendering Manager):Linux 内核里管 GPU 的子系统。`/dev/dri/card0` 就是 DRM 设备节点
- **DRI**(Direct Rendering Infrastructure):让用户态程序绕过 X server 直接和 GPU 说话。OpenGL 直接渲染靠它
- **GBM**(Generic Buffer Management):Mesa 提供的 API,分配 GPU 能用的 buffer。Wayland 合成器靠它

**Arch Linux 工具链验证**:

```bash
# 看你装了哪个 OpenGL 实现
pacman -Qs mesa
# 输出类似:local/mesa 24.2.7-1

# 看 OpenGL 版本
glxinfo | grep "OpenGL version"
# 输出:OpenGL version string: 4.6 (Compatibility Profile) Mesa 24.2.7

# 看你的 GPU
lspci | grep -i vga
# 输出:VGA compatible controller: Intel ...或 NVIDIA ...

# 跑一个 GPU 测试
glxgears
# 三个旋转的齿轮窗口,终端打印 FPS
```

如果 `glxinfo` 没装:`sudo pacman -S mesa-utils`。

**Wayland vs X11**:Arch 现在默认 Wayland。glutin 在两个协议下都能创建 OpenGL 上下文,但 Wayland 的 EGL 实现,X11 的 GLX 实现略有不同。glutin 帮你封装,你不用直接管。

### 3.4 · 🦀 Rust 生态视角

Rust 怎么访问 OpenGL:

#### 流派 1:`glow` crate(Casey 风格,薄封装)

```toml
[dependencies]
glow = "0.14"
```

`glow` 提供跨后端的 OpenGL API(同时支持 OpenGL / OpenGL ES / WebGL)。每个 GL 调用都是 `Context` 的方法:

```rust
use glow::HasContext;

let gl = glow::Context::from_loader_function(|ptr| {
    // 通过 glutin 或别的方式拿到函数指针
    get_proc_address(ptr) as *const _
});

unsafe {
    gl.clear_color(0.0, 1.0, 0.0, 1.0);  // 清成绿色
    gl.clear(glow::COLOR_BUFFER_BIT);
}
```

**为什么 unsafe?** OpenGL 调用有"上下文当前性"约束——你必须在一个线程上"持有"当前 context 才能调 GL。Rust 编译器无法验证这点,所以 glow 全部 unsafe。

#### 流派 2:`glium` crate(高层封装,已废弃)

曾流行过,作者停维。不推荐新项目用。

#### 流派 3:`wgpu`(基于 WebGPU,现代推荐)

```toml
[dependencies]
wgpu = "22"
```

`wgpu` 不是 OpenGL,是 WebGPU 的 Rust 实现,跨后端(Vulkan / Metal / D3D12 / OpenGL)。比 OpenGL 现代,显式同步、显式资源转换。但学习曲线陡。

跟 HH 学的话,**先 glow/OpenGL**——直接对照 Casey 的代码。后面想升级到 wgpu,Phase 7+ 可以做。

#### 流派 4: Vulkan raw(`ash` crate)

最底层,显式一切。学习用过高,生产用合适。Day 235 之后你不走这条。

**HH Phase 5 推荐路径**:`winit` + `glutin` + `glow`,因为 glutin 帮你处理 X11/Wayland/EGL 的复杂性,glow 直接对应 OpenGL C API,Casey 的 C 代码可以一行一行翻译。

**Rust FFI 给 GL**:glow 底层用 `extern "C"` 调用 `libGL.so` 提供的函数。这些函数签名来自 Khronos 的 `gl.xml` 规范,glow 在 build 时生成绑定。

```bash
# 看你的 libGL
nm -D /usr/lib/libGL.so.1 | grep -E " T glClear$"
# 输出:00000000000abcde T glClear
```

`T` 表示这个符号在 .text 段(已定义的可执行代码)。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **异构计算(Heterogeneous Computing)** —— CPU + GPU + 其他加速器(TPU / NPU)协同
- **图形管线(Graphics Pipeline)** —— 从 3D 场景描述到 2D 像素的标准流程
- **SIMD/SIMT 计算模型** —— 单指令多数据 / 单指令多线程

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 软件渲染(CPU) | CPU 一行行写 framebuffer | 学习原理、调试 | Day 037-234 |

### 4.3 下级(内部零件)

- **顶点着色器(Vertex Shader)** —— 每顶点跑一次,做变换
- **片段着色器(Fragment Shader)** —— 每像素跑一次,算颜色
- **VBO / VAO(Vertex Buffer / Array Object)** —— 顶点数据 + 顶点结构描述
- **Texture** —— GPU 端的位图,shader 通过 sampler 读
- **Uniform** —— draw call 内常量(MVP 矩阵、纹理绑定)
- **Draw call** —— 一次 `glDrawArrays` 调用,触发管线
- **Warp / Wavefront** —— GPU 并行单位,32 / 64 个核锁步

## 5 · 对照与变奏

### 同一渲染问题的 CPU vs GPU 实现

**问题**:把一张 256×256 纹理 blit 到屏幕 (100, 100) 位置。

| | CPU 软渲染 | GPU OpenGL |
|---|---|---|
| 代码 | 两层 for 循环,逐像素拷贝 | 一个 draw call,画一个 quad |
| 速度 | ~1ms(1080p 单 blit) | ~0.01ms(几乎免费) |
| 内存 | 直接访问 framebuffer | 必须上传到 VRAM |
| 灵活性 | 任意像素操作 | shader 限制内 |
| 调试 | printf 即可 | 难(需要 RenderDoc) |

但 GPU 的 0.01ms 只在你已经准备好 VBO/texture 时成立。如果**每帧**重新上传纹理,CPU-GPU 带宽瓶颈反而比 CPU 软渲染慢。Day 237 你会感受到这个差异。

### 现代图形 API 的演化

- **1992**:OpenGL 1.0 —— 固定管线,没有 shader,只有 glVertex/glColor
- **2004**:OpenGL 2.0 —— GLSL 引入,可编程着色
- **2009**:Direct3D 11 —— 上一代"自动同步"API 高峰
- **2015**:Vulkan / D3D12 —— 显式同步,显式内存,陡峭学习曲线换性能
- **2023**:WebGPU —— 安全、跨平台、现代 API 的"友好子集"

OpenGL 是这条演化线的中间产物——够现代(有 shader),又够自动化(driver 帮你做同步)。教学价值最高。

### 历史:GPU 怎么演化出 shader

- **1990s**:GPU 是**固定功能**——只能算 Gouraud 着色 + 仿射纹理。开发者用 `glVertex`、`glColor` 描述场景,GPU 内部硬算
- **2001**:NVIDIA GeForce 3 —— 首次支持可编程,但用的是汇编般的"register combiner"
- **2004**:OpenGL 2.0 —— GLSL 标准化,shader 写起来像 C
- **2010+**:通用计算(GPGPU),shader 能做物理 / AI / 加密
- **2020+**:mesh shader / ray tracing shader,管线本身都可编程

你跟 HH 学的 OpenGL 3.3+,处于"成熟 shader"阶段——固定管线 + 可编程 shader 的混合。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 GPU 不能像 CPU 那样高效处理深度递归?从硬件角度解释。

**参考解答**:GPU 的并行模型是 SIMT(单指令多线程),warp 内 32 个核必须锁步执行同一条指令。递归有两个问题:(1) 栈深度不确定,而 GPU 的栈空间(stack buffer)极小;(2) 不同像素走不同深度,意味着 warp 分歧——32 个核里 5 个递归 10 层、20 个递归 5 层,所有核必须等最深的那个跑完。GPU 没有 CPU 的硬件栈/分支预测/返回地址预测器。所以 GPU 程序几乎都是迭代 + 限定的循环深度。

### Lv3 · 迁移设计

**题**:你不是在做游戏,而是在做**音频效果器**(real-time DSP)。你要对一段 1024 样本的音频跑 FFT(快速傅里叶变换),延迟要 < 5ms。CPU 单核需要 3ms。考虑用 GPU 加速:你打算怎么设计?(提示:GPU 启动开销 vs FFT 本身的并行性。)

**提示**:
- GPU 启动一个 shader 调用,driver overhead ≈ 10-50 微秒
- FFT 是 O(N log N) 操作,1024 样本 log N = 10 stage
- 一段音频 FFT 单次 GPU 启动可能比 CPU 慢(driver overhead > 实际算力节省)
- 真要做的话,要 **batch**(一次提交多段音频)、**persistent**(shader 驻留,避免每帧编译)
- 现实:专业音频效果器基本不用 GPU,因为延迟敏感的实时音频反而 CPU 更可控

## 8 · Rust / Arch 落地代码

### Rust:用 glow 创建一个最简单的清屏程序

```rust
// Cargo.toml:
// [dependencies]
// glow = "0.14"
// glutin = "0.32"
// winit = "0.30"

use glow::HasContext;
use std::num::NonZeroU32;

fn main() {
    // 1. 创建 winit 事件循环(窗口消息泵)
    let event_loop = winit::event_loop::EventLoop::new()
        .expect("事件循环创建失败");

    // 2. 创建窗口
    let window_builder = winit::window::WindowBuilder::new()
        .with_title("Day 236 GPU 概览")
        .with_inner_size(winit::dpi::PhysicalSize::new(800, 600));

    // 3. 用 glutin 创建 OpenGL 上下文(把 winit 窗口和 OpenGL 绑定)
    let (window, gl_config, window_context) = {
        let glutin_window = glutin::GlutinWindowBuilder::new(window_builder)
            .with_gl_api(glutin::config::GlApi::OpenGl)  // 指定 OpenGL(不是 GLES)
            .with_gl_profile(glutin::context::GlProfile::Core)  // Core profile(无废弃固定管线)
            .with_gl_version(glutin::context::Version::new(3, 3))  // OpenGL 3.3
            .build(&event_loop)
            .expect("窗口创建失败");
        glutin_window.split()
    };

    // 4. 让 context 成为"当前"(OpenGL 调用前必须做)
    let not_current = unsafe {
        window_context.make_current()
    }.expect("make_current 失败");

    // 5. 用 glow 包裹 context,得到类型安全的 GL 调用入口
    let gl = unsafe {
        glow::Context::from_loader_function_cstr(|s| {
            window.get_proc_address(s) as *const _
        })
    };

    // 6. 主循环
    event_loop.run(move |event, window_target| {
        match event {
            winit::event::Event::AboutToWait => {
                // 每帧清屏成深蓝色
                unsafe {
                    gl.clear_color(0.05, 0.05, 0.15, 1.0);  // RGBA,范围 [0, 1]
                    gl.clear(glow::COLOR_BUFFER_BIT);
                }
                window.swap_buffers().expect("swap_buffers 失败");
            }
            winit::event::Event::WindowEvent { event, .. } => {
                if let winit::event::WindowEvent::CloseRequested = event {
                    window_target.exit();
                }
            }
            _ => {}
        }
    }).expect("主循环异常");
}
```

**每段解释**:

- `HasContext` trait —— glow 把所有 GL 方法定义在这个 trait 上,必须 `use` 才能调 `gl.clear_color`
- `make_current` —— OpenGL 是"线程局部"的,每个线程最多一个 current context。`make_current` 把 context 绑定到当前线程。漏了这步,后续 GL 调用全崩溃
- `from_loader_function` —— 不同平台用不同方式获取 GL 函数指针(X11 用 glXGetProcAddress,Wayland 用 eglGetProcAddress)。glutin 提供 `get_proc_address` 统一接口
- `clear_color(r, g, b, a)` —— 设置清屏颜色,RGBA 浮点,范围 [0, 1] 不是 [0, 255]
- `clear(COLOR_BUFFER_BIT)` —— 用上面设的颜色填满 framebuffer
- `swap_buffers` —— 双缓冲:GPU 画到后缓冲,display 显示前缓冲。swap 把两个交换,避免撕裂

**Troubleshooting**:

- **`glutin` 报"no available pixel format"** —— 你的 OpenGL 版本不够。`glxinfo | grep "OpenGL version"` 看,需要 ≥ 3.3
- **窗口出来但是黑屏** —— 检查 `swap_buffers` 调没调,或 vsync 配错
- **FPS 很低(几帧)** —— 可能跑到 llvmpipe 软件渲染了。`glxinfo | grep renderer`,如果是 `llvmpipe`,装硬件驱动
- **panic 在 `make_current`** —— 多线程调了 GL?OpenGL 调用必须在创建 context 的那个线程
