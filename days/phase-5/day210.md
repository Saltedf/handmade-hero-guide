# Day 210 · 合并调试数据存储

> 之前有几套独立数据:profiler ring buffer、debug variable store、watch window history。它们数据重叠但存储分散。今天 Casey 合并:**一个统一的 debug data store**,所有功能从同一份读。

## 0 · 为什么要有这一天

让我们把镜头拉到一个具体的开发场景。

跟着 HH 走到 Day 209,你的 debug 系统已经成熟——data block、watch window、plot、inspector、introspection。每件工具都独立工作得很好。但你现在打开代码,数一下"维护数据的代码":

- `ProfilerState.events: Vec<DebugEvent>` — event 流,Day 178 加
- `DebugVariables.variables: HashMap<u64, DebugValue>` — 全局变量,Day 202 加
- `WatchWindow.history: HashMap<u64, RingBuffer<f32, 300>>` — watch 历史,Day 209 加
- `FrameSummary.data_blocks: Vec<(cycle, name, value)>` — 帧内数据,Day 208 加

**4 套独立的数据结构**。每个都自己管内存、自己管生命周期、自己的 read/write API。

然后你发现一个**重复模式**:

玩家的位置 `player.pos`——同一个值——在 4 套数据里**都有一份**:
1. 游戏代码 `debug_data("player_pos", pos)` 把它写入 `events`(Day 208)
2. collate 时,这个 data block 进入 `FrameSummary.data_blocks`(Day 208)
3. WatchWindow.update 从 data_blocks 拉到 `history`(Day 209)
4. inspector 读 entity 时,introspect **又算一次** `pos.x` 和 `pos.y`(Day 206)

**同一数据,4 份存储**。每份都可能不同步——你 push 进 events 但忘了 collate,或 collate 进 data_blocks 但忘了 watch update。Bug 出现时你不知道哪份是"真相"。

这是软件工程的经典反模式——**数据冗余 + 同步 bug**。Martin Fowler 在《Refactoring》里专门讨论过。

工业界的解法叫 **single source of truth(单一数据源)**——一个数据只存一份,所有 consumer 从同一份读。Day 202 已经讲过 SOT(用于 debug variables),今天把它扩展到**整个 debug 数据系统**:events、variables、history、frame summaries 全合并到一个 `DebugStore`。

这是工程化的"**架构清理**"——前面为了快速实现,数据分散各处。现在功能稳定,为了可维护,合并。

**为什么这件事不平凡?**

技术上,合并看起来是"加个 struct 包起来"。但有几个挑战:

**第一,API 迁移**。4 套数据各自的 read/write API 不同。要统一成一个 API,所有 caller 改代码。这是个**大重构**——可能几百处调用点。

**第二,key 命名空间**。variables 用 `hash("player_pos")`,events 用 event guid,watch 用 watch name。合并后要统一 key,加 namespace 区分(0x0000_ 是 profiler,0x1000_ 是 variable,等)。

**第三,生命周期不同**。events 只活一帧,data_blocks 进 frame summaries(最近 300 帧),variables 永久(直到手动删),history 是 ring buffer。合并后要各自 eviction 策略。

**第四,并发**。多线程 push event 怎么合并?per-thread buffer + frame end merge(Day 178)。

**第五,测试**。合并前后行为必须一致。要有完整的回归测试。

今天 Casey 完成这个重构。Day 211+ 用统一 store 做更复杂的功能。

**学完今天,你应该能**:
- 识别"数据冗余"反模式(同一概念在多处存储)
- 设计统一 store,多个 consumer 共享单一源
- 用 namespace key(u64 高位区分)避免冲突
- 给不同数据类型设计不同生命周期 / eviction 策略
- 看懂 Bevy Resource、Unreal Blackboard、Redux store 在结构上和 Casey 的 DebugStore 是同一个东西
- 理解"data lake" / "data warehouse" 概念在游戏 debug 里的微缩版

## 1 · Casey 今天做了什么

Casey 这一天做**架构重构**——把分散的 4 套数据合并:

1. **审计现有数据**。列出所有数据结构:`events`、`current_values`(variables)、`history`(watch)、`frame_summaries`。识别哪些字段重叠(同一变量在多处)。

2. **设计 DebugStore**。一个 struct 包含所有:`events: Vec<DebugEvent>` + `current_values: HashMap<u64, DebugValue>` + `history: HashMap<u64, RingBuffer<f32, 300>>` + `frame_summaries: RingBuffer<FrameSummary, 300>`。

3. **统一 push API**。`push_event(event)` 内部 dispatch——Begin/End 进 events 流,Data 同时更新 current_values + history。**一次 push,多处同步**。

4. **统一 read API**。`current(name)` 查 current_values、`history(name)` 查 history、`frames()` 迭代 frame_summaries。consumer 不直接访问字段,通过 method。

5. **移除旧的分散结构**。ProfilerState.events 改成 `store.events`,DebugVariables 改成 `store.current_values`,等。所有 caller 改用 `store.xxx()`。

6. **回归测试**。重构后跑所有 debug 功能(inspector、watch、profiler、recording),验证行为不变。

7. **反思边界**。Casey 提到这次重构让代码更简单,但**短期是负担**——几百处 caller 改写,容易引入 bug。重构必须有测试覆盖,否则"改了不知道哪里破"。

这集产出 0 行新功能,但代码可维护性大幅提升。后面 Day 211+ 在统一 store 上做更多功能。

## 2 · 心智模型

### 2.1 费曼类比:公司的中央数据湖

想象一个公司。早期创业时,公司只有几个人。每个人电脑上有自己的 Excel 表格——销售记客户、财务记账单、客服记支持工单。每个部门独立,效率高。

公司大了,问题出现:
- 销售答应客户"价格 8 折",但财务账单还是 10 折——**两份数据不一致**。
- 客服想看"这个客户去年买了什么",要找销售要 Excel,要找财务要账单,人工合并。
- CEO 想看"上季度各地区营收",没人有这个数据——三个部门各自有碎片。

工业界的解法叫 **data lake / data warehouse**——把所有部门的数据汇到一个中央仓库。销售、财务、客服都从仓库读写,不再各自维护 Excel。仓库统一 schema,统一查询,统一备份。

公司从"分散 Excel"迁到"中央数据湖"是个**大重构**——但长远看,数据一致性、查询效率、维护成本都大幅改善。

游戏 debug 系统一样。Day 178-209 你"快速实现"——每个工具(profiler、inspector、watch)自己有数据结构。Day 210 把它们合并成**一个 DebugStore**,所有工具从同一份读写。

这个类比的关键洞察:**数据冗余是 bug 的温床,数据合并是长期投资**。短期看合并是负担(几百处 caller 改写),长期看合并让代码可维护、可测试、可扩展。

### 2.2 重构的步骤:Martin Fowler 的方法

Martin Fowler 在《Refactoring》里给出重构的标准流程。Casey Day 210 遵循这套流程:

**Step 1:识别代码异味(code smell)**。

Casey 注意到:`player.pos` 这个值在 4 处存储(events、data_blocks、watch history、entity inspector)。每次修改一处,要手动同步其他三处。这是 **"Shotgun Surgery"(霰弹式修改)** 异味——一个改动要散到多处。

**Step 2:写测试**。

重构前必须有测试。Casey 在 HH 里反复运行 debug 系统,记录行为——inspector 显示什么、watch 显示什么、profiler 显示什么。重构后跑同样输入,行为必须一致。

**Step 3:小步重构**。

不是一次性大改。Fowler 推荐**小步前进,每步测试**。Casey 可能这样:
- 第 1 步:创建 `DebugStore` struct,但 caller 还用旧 API。
- 第 2 步:push_event 内部同时写新 store 和旧结构。
- 第 3 步:caller 一个一个改用 store API,每改一个测试。
- 第 4 步:删掉旧结构。

**Step 4:验证**。

跑完整 debug session,确认行为不变。profiler 时间不变、inspector 显示不变、watch plot 不变。

这套流程是工业级重构的标准。Casey HH 教学简化,但概念相同。

### 2.3 从零推导:DebugStore 的设计

**Step 0:分散存储**。

```rust
struct ProfilerState { events: Vec<DebugEvent> }
struct DebugVariables { variables: HashMap<u64, DebugValue> }
struct WatchWindow { history: HashMap<u64, RingBuffer<f32, 300>> }
struct FrameSummaries { frames: RingBuffer<FrameSummary, 300> }
```

4 个独立 struct,4 套 API。

**Step 1:放进同一个 struct**。

```rust
struct DebugStore {
    events: Vec<DebugEvent>,
    current_values: HashMap<u64, DebugValue>,
    history: HashMap<u64, RingBuffer<f32, 300>>,
    frame_summaries: RingBuffer<FrameSummary, 300>,
}
```

物理合并,API 还分散。caller 还各自访问字段。

**Step 2:统一 push**。

```rust
impl DebugStore {
    fn push_event(&mut self, e: DebugEvent) {
        // 1. events 流
        self.events.push(e.clone());

        // 2. 如果是 data,同步更新 current + history
        if let Kind::Data { name, value } = &e.kind {
            let guid = hash(name);
            self.current_values.insert(guid, value.clone());
            let scalar = match value {
                Value::Float(f) => *f,
                Value::Int(i) => *i as f32,
                _ => return,
            };
            self.history.entry(guid).or_insert_with(RingBuffer::new).push(scalar);
        }
    }
}
```

**一次 push,多处同步**。caller 不再手动写多处——push 一次,store 内部 fan-out 到所有存储。

**Step 3:统一 read**。

```rust
impl DebugStore {
    fn current(&self, name: &str) -> Option<&DebugValue> {
        self.current_values.get(&hash(name))
    }

    fn history(&self, name: &str) -> Option<&RingBuffer<f32, 300>> {
        self.history.get(&hash(name))
    }

    fn frames(&self) -> impl Iterator<Item = &FrameSummary> {
        self.frame_summaries.iter_recent()
    }
}
```

caller 通过 method 访问,不直接 touch 字段。store 可以重构内部,API 不变。

**Step 4:迁移 caller**。

旧代码:
```rust
debug_variables.set("speed", 5.0);
watch_window.add("speed");
inspector.show(&debug_variables);
```

新代码:
```rust
store.push_event(Event::data("speed", Value::Float(5.0)));
// store 内部自动更新 current + history
inspector.show(&store);
```

每个 caller 改写。Casey HH 有几十处 caller,每处几行改动,总共几百行。每改一处测试。

**Step 5:删旧结构**。

迁移完所有 caller,删掉旧的 `ProfilerState` / `DebugVariables` / `WatchWindow` / `FrameSummaries`。代码量减少。

### 2.4 key 命名空间

key 是 u64。不同 namespace 用高位前缀区分,避免冲突:

```rust
const NS_PROFILER: u64  = 0x0000_0000_0000_0000;
const NS_VARIABLE: u64  = 0x1000_0000_0000_0000;
const NS_WATCH:    u64  = 0x2000_0000_0000_0000;
const NS_DATA:     u64  = 0x3000_0000_0000_0000;

fn variable_key(name: &str) -> u64 {
    NS_VARIABLE | hash(name)  // 高位是 namespace,低位是 hash
}
```

`hash(name)` 在低位(60 bits,够用),高位 4 bits 是 namespace。**两个不同 namespace 的相同 name 不冲突**——`NS_VARIABLE | hash("pos")` ≠ `NS_WATCH | hash("pos")`。

这是 bitfield 技巧,内核 / 网络协议常用。Rust `NonZeroU64` + high bits 让 0 仍是 invalid sentinel。

### 2.5 不同的生命周期

数据有不同生命周期,统一 store 内部各自管理:

| 数据 | 生命周期 | eviction |
|---|---|---|
| events | 一帧(到 frame end) | frame end 清空 |
| current_values | 全程(变量一直存在) | 变量不再被 push 时手动删 |
| history | 最近 N 帧 | ring buffer 自动覆盖 |
| frame_summaries | 最近 N 帧 | ring buffer 自动覆盖 |

实现:

```rust
impl DebugStore {
    fn end_frame(&mut self) {
        self.events.clear();  // events 只活一帧
        // current_values 不清(持续存在)
        // history 自动 ring buffer 覆盖
        // frame_summaries 自动 ring buffer 覆盖
    }
}
```

不同生命周期反映不同用途。events 是 raw event 流(下一帧重写),current_values 是状态(持续),history 是趋势(最近 N 帧)。

### 2.6 GC / 内存预算

合并后,所有数据在 store 里。要监控内存:

```rust
impl DebugStore {
    fn memory_usage(&self) -> usize {
        self.events.len() * std::mem::size_of::<DebugEvent>()
        + self.current_values.len() * (std::mem::size_of::<u64>() + std::mem::size_of::<DebugValue>())
        + self.history.len() * (std::mem::size_of::<u64>() + 300 * 4)
        + self.frame_summaries.len() * std::mem::size_of::<FrameSummary>()
    }
}
```

1000 个 variable × 300 frame history × 4 byte = 1.2 MB。可接受。

如果数据大(每帧几 MB),要压缩(zstd)或落盘(SQLite)。但 debug UI 一般不存大量数据——录制文件落盘,内存只存最近 N 帧。

### 2.7 并发安全的 push

多线程 push event 怎么做?

**方案 1:Mutex<HashMap>**——简单,慢。每 push 一次锁,~1 μs/push。100 push/frame = 100 μs/frame。

**方案 2:DashMap**——lock-free 并发 HashMap。push 不阻塞,~50 ns/push。但要外部 crate。

**方案 3:per-thread buffer + frame end merge**(Casey 用)。

```rust
thread_local! {
    static LOCAL_EVENTS: RefCell<Vec<DebugEvent>> = RefCell::new(Vec::with_capacity(256));
}

fn push_event(e: DebugEvent) {
    LOCAL_EVENTS.with(|buf| buf.borrow_mut().push(e));
}

// 主线程 frame end 时 merge
fn merge_thread_locals(store: &mut DebugStore) {
    LOCAL_EVENTS.with(|buf| {
        for e in buf.borrow_mut().drain(..) {
            store.push_event(e);  // 内部分发到 events + current + history
        }
    });
}
```

每线程独立 buffer,push 零锁。frame end 主线程合并一次。Casey Day 178 已经实现,Day 210 复用。

### 2.0 统一数据存储的设计

之前散落多份:

- profiler ring buffer(per-frame cycle 数据)
- debug variables HashMap(per-variable 当前值)
- watch window history(per-watch 时间序列)
- data block buffer(per-event 任意数据)

**冗余**:`Player/Speed` 既在 variables 里(当前值),也在 data blocks 里(历史值),还在 watch 里(显示值)。改一处其他不同步。

**统一**:一个 `DebugDataStore` 包含所有:

```rust
struct DebugDataStore {
    // (key, frame_index) → value
    samples: HashMap<(u64 /* key */, u64 /* frame */), Value>,
    // 索引:按 key 找历史
    by_key: HashMap<u64, Vec<u64 /* frame */>>,
    // 当前帧
    current_frame: u64,
}

impl DebugDataStore {
    fn record(&mut self, key: u64, value: Value) {
        let frame = self.current_frame;
        self.samples.insert((key, frame), value);
        self.by_key.entry(key).or_default().push(frame);
    }

    fn latest(&self, key: u64) -> Option<&Value> {
        let frames = self.by_key.get(&key)?;
        let last = *frames.last()?;
        self.samples.get(&(key, last))
    }

    fn history(&self, key: u64) -> Vec<&Value> {
        let frames = self.by_key.get(&key).map(|v| v.as_slice()).unwrap_or(&[]);
        frames.iter().filter_map(|f| self.samples.get(&(key, *f))).collect()
    }
}
```

所有功能(profiler / variables / watch / data blocks)都通过 `record(key, value)` + `latest(key)` / `history(key)` 访问。

### 2.0.1 key 的命名空间

key 是 u64,但有命名空间:

- `0x0000_0000_0000_0000` 到 `0x0FFF_FFFF_FFFF_FFFF`:profiler cycle(每帧)
- `0x1000_0000_0000_0000` 到 `0x1FFF_FFFF_FFFF_FFFF`:variable value
- `0x2000_0000_0000_0000` 到 `0x2FFF_FFFF_FFFF_FFFF`:watch entry
- `0x3000_0000_0000_0000` 到 `0x3FFF_FFFF_FFFF_FFFF`:data block

按 namespace 分配 key,避免冲突。Hash function 自动加 namespace 前缀。

### 2.0.2 GC / eviction

数据持续增长,要清理:

- profiler cycle:保留最近 N 帧(ring buffer)
- variable value:保留当前(覆盖旧的)
- watch history:保留最近 N 帧
- data block:保留最近 N 个

不同 namespace 不同策略。统一 store 实现各自 eviction。

### 2.0.3 查询的统一 API

```rust
trait DataSource {
    fn keys(&self) -> Vec<u64>;
    fn latest(&self, key: u64) -> Option<&Value>;
    fn history(&self, key: u64) -> Vec<&Value>;
    fn record(&mut self, key: u64, value: Value);
}
```

不同存储(profiler / variable / watch)实现 DataSource。UI 通过 trait object 读,无需知道具体存储。

### 2.0.4 内存预算

1000 个 key × 300 帧历史 × 16 字节(value)= 4.8 MB。可接受。如果数据大(每帧几 MB),要压缩(zstd)或落盘(SQLite)。

### 2.0.5 多线程读写

多线程 record 怎么做?

- **Mutex<HashMap>**:简单,慢
- **DashMap**:lock-free 并发 HashMap
- **per-thread buffer**:每线程独立,frame end 时汇总

Casey 用 per-thread(已 day 178 实现)。统一 store 在主线程 frame end 时 pull 所有线程数据。

### 类比:中央数据湖

公司有多个部门(销售 / 财务 / 客服),每个有自己的数据库。数据冗余、不一致。**数据湖**(data lake)把所有数据汇到一处,各部门都从湖里取。

### 2.1 unified store 设计

```rust
pub struct DebugStore {
    // 事件流(原始数据)
    pub events: Vec<DebugEvent>,

    // 当前变量值(inspector 用)
    pub current_values: HashMap<u64, DebugValue>,

    // 历史值(watch / plot 用)
    pub history: HashMap<u64, RingBuffer<f32, 300>>,

    // 帧聚合
    pub frame_summaries: RingBuffer<FrameSummary, 300>,
}
```

### 2.2 统一 push API

```rust
impl DebugStore {
    pub fn push_event(&mut self, e: DebugEvent) {
        // 1. 写入 event 流
        self.events.push(e.clone());

        // 2. 如果是 data block,更新 current_values 和 history
        if let DebugEventKind::Data { name, value } = &e.kind {
            let guid = hash(name);
            self.current_values.insert(guid, value.clone());

            let scalar = match value {
                DebugValue::Float(f) => *f,
                DebugValue::Int(i) => *i as f32,
                _ => return,
            };
            self.history.entry(guid).or_insert_with(RingBuffer::new).push(scalar);
        }
    }
}
```

**一次 push,多个数据源同步**。

### 2.3 UI 统一查询

```rust
impl DebugStore {
    // inspector 用
    pub fn current(&self, name: &str) -> Option<&DebugValue> {
        self.current_values.get(&hash(name))
    }

    // watch / plot 用
    pub fn history(&self, name: &str) -> Option<&RingBuffer<f32, 300>> {
        self.history.get(&hash(name))
    }

    // profiler 用
    pub fn frame_summaries(&self) -> impl Iterator<Item = &FrameSummary> {
```

### 2.4 内存优化

合并前:同一变量 3 份内存(event + current + history)。
合并后:**仍然 3 份**,但 push 时一起更新,不会 inconsistent。

进一步优化:**event 流不再存 data block**(只存 begin/end),data block 进 current + history:

```rust
pub fn push_event(&mut self, e: DebugEvent) {
    match &e.kind {
        DebugEventKind::Begin | DebugEventKind::End => self.events.push(e),
        DebugEventKind::Data { name, value } => {
            // 不进 events 流,只进 current + history
            let guid = hash(name);
            self.current_values.insert(guid, value.clone());
            // ...
        }
    }
}
```

省一份内存。但**录制文件**仍然要 data block,所以录制时另外存一份。

### 2.5 数据生命周期

| 数据 | 生命周期 | 清理策略 |
|---|---|---|
| events | 短(当前帧) | 帧结束清 |
| current_values | 长(全程) | 变量不用时手动删 |
| history | 中(最近 N 帧) | ring buffer 自动 |
| frame_summaries | 中(最近 N 帧) | ring buffer 自动 |

合理设计 lifetime 防止内存爆。

### 3.2 · Rust 生态视角

Rust 的"统一 store"模式:

- `bevy::Resource` — ECS 全局资源
- `taffy::cache` — layout 缓存
- `lazy_static` / `OnceLock` — 进程级

```rust
// bevy 风格
#[derive(Resource)]
struct DebugStore { ... }

// 任何 system 通过 Res<DebugStore> 访问
fn inspector_system(store: Res<DebugStore>) { ... }
```

### 3.3 · 架构重构原则

合并多份数据的原则:

1. **识别重复**——同一概念在多处存储
2. **找单一源**——以哪个为准
3. **统一写入**——一次写入,多处更新
4. **保留多视图**——同一数据,多个 read API
5. **测试不退化**——合并后行为不变

casey 在 day 210 完成这五步。

## 5 · 对照与变奏

**统一存储 vs 分散存储**:

| 方式 | 优点 | 缺点 |
|---|---|---|
| 统一 store | 数据一致、查询简单 | 重构工作大 |
| 分散 store | 模块化、各管各 | 冗余、同步复杂 |

工业实践:**新项目用统一**(开始就规划好),**老项目渐进合并**(逐步迁)。

### time-series database 模式

Casey 的统一 store 是 TSDB 的微缩版:

- InfluxDB / TimescaleDB:云 TSDB,几亿数据点
- Prometheus:metrics TSDB,server 端聚合
- LevelDB / RocksDB:嵌入式 KV,可作 TSDB 后端

每个都是 (key, timestamp) → value 模式。Casey 用 HashMap<(key, frame), value>,简单但概念相同。

### OLAP vs OLTP

- **OLTP**(online transaction processing):高吞吐小查询,user-facing
- **OLAP**(online analytical processing):大数据分析,aggregation-heavy

profiler 是 OLAP——分析历史趋势,不是 OLTP(不每秒几万写入)。

### Data warehouse 的 ETL

工业 ETL(Extract Transform Load):

1. **Extract**:从多个 source(game state, profiler)拉数据
2. **Transform**:清洗、聚合、转换格式
3. **Load**:写到统一 store(warehouse)

Casey 的 day 210 是简版 ETL——直接 merge,无 transform。生产 ETL 更复杂(数据清洗、schema migration)。

## 6 · 关联 Day

**数据一致性的不同保证**:

| 模式 | 一致性 | 性能 |
|---|---|---|
| 强一致(单一 store) | 高 | 中 |
| 最终一致(eventual) | 中 | 高 |
| 弱一致(best effort) | 低 | 极高 |

游戏 debug UI 用强一致(单一 store),游戏逻辑用最终一致(网络同步)。

### Lv2 · 动手实践

**题**:实现 DebugStore,push_event 时同时更新 events + current + history。

**参考解答**:

```rust
use std::collections::HashMap;

#[derive(Clone, Debug)]
enum Value { Float(f32), Int(i64) }

#[derive(Clone, Debug)]
enum Kind { Begin, End, Data { name: &'static str, value: Value } }

#[derive(Clone, Debug)]
struct Event { cycle: u64, kind: Kind }

const fn fnv(s: &str) -> u64 {
    let bytes = s.as_bytes();
    let mut h = 0xcbf29ce484222325u64;
    let mut i = 0;
    while i < bytes.len() { h ^= bytes[i] as u64; h = h.wrapping_mul(0x100000001b3); i += 1; }
    h
}

struct Ring<T: Copy + Default, const N: usize> {
    data: [T; N], head: usize, len: usize,
}
impl<T: Copy + Default, const N: usize> Ring<T, N> {
    fn new() -> Self { Self { data: [T::default(); N], head: 0, len: 0 } }
    fn push(&mut self, v: T) {
        self.data[self.head] = v;
        self.head = (self.head + 1) % N;
        if self.len < N { self.len += 1; }
    }
    fn iter(&self) -> impl Iterator<Item = T> + '_ {
        let start = if self.len < N { 0 } else { self.head };
        (0..self.len).map(move |i| self.data[(start + i) % N])
    }
}

struct DebugStore {
    events: Vec<Event>,
    current: HashMap<u64, Value>,
    history: HashMap<u64, Ring<f32, 100>>,
}

impl DebugStore {
    fn new() -> Self { Self { events: Vec::new(), current: HashMap::new(), history: HashMap::new() } }

    fn push(&mut self, e: Event) {
        if let Kind::Data { name, value } = &e.kind {
            let guid = fnv(name);
            self.current.insert(guid, value.clone());
            let scalar = match value { Value::Float(f) => *f, Value::Int(i) => *i as f32 };
            self.history.entry(guid).or_insert_with(Ring::new).push(scalar);
        }
        self.events.push(e);
    }

    fn current_value(&self, name: &str) -> Option<&Value> {
        self.current.get(&fnv(name))
    }

    fn history_of(&self, name: &str) -> Option<Vec<f32>> {
        self.history.get(&fnv(name)).map(|r| r.iter().collect())
    }
}

fn main() {
    let mut store = DebugStore::new();
    for frame in 0..5 {
        store.push(Event { cycle: frame * 100, kind: Kind::Begin });
        store.push(Event {
            cycle: frame * 100 + 50,
            kind: Kind::Data { name: "hp", value: Value::Int((100 - frame * 5) as i64) },
        });
        store.push(Event {
            cycle: frame * 100 + 60,
            kind: Kind::Data { name: "speed", value: Value::Float(5.0 + frame as f32 * 0.5) },
        });
        store.push(Event { cycle: frame * 100 + 100, kind: Kind::End });
    }

    println!("current hp: {:?}", store.current_value("hp"));
    println!("current speed: {:?}", store.current_value("speed"));
    println!("hp history: {:?}", store.history_of("hp"));
    println!("speed history: {:?}", store.history_of("speed"));
}
```
