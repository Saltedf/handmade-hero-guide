# Day 246 · 工作上下文创建移到主线程

> Day 113 引入多线程后,任务系统有"工作线程"(worker thread)。Casey 在 Day 245 之后想把 OpenGL context 用于 asset 加载(在工作线程跑),但发现某些 driver 工作不正常——context 在 worker 线程创建,渲染在主线程,跨线程后丢失。今天他把 context 创建强制放主线程,worker 用"共享 context"模式。

## 0 · 为什么要有这一天

OpenGL context 是**线程局部**(thread-local)的——每个线程最多一个 current context。如果 worker 线程要加载纹理,它需要:

1. 自己的 context(`wglCreateContext` 在 worker 线程调)
2. 或者共享 context(主线程的 context 共享给 worker)
3. 或者主线程帮它干

Day 245 之前 Casey 让 worker 自己创建 context,但发现:

- **NVIDIA 驱动** —— 工作正常,跨线程共享 OK
- **Intel 集显** —— 工作正常
- **某些 AMD 驱动** —— worker context 创建后,GL 函数静默失败

这是典型的 driver 兼容性问题。Casey 不打赌,Day 246 把所有 context 操作**强制在主线程**,worker 只用 CPU 干活(读 PNG / 解码),上传 GPU 在主线程。

**为什么这件事重要**:跨线程 GL 是图形开发大坑。理解为什么"GL 单线程"是常态,你能避开这个坑。

**心理锚点**:看完今天,你能解释为什么 Casey 把 asset 加载拆成两阶段:CPU 解码(worker 线程) + GPU 上传(主线程)。

## 1 · Casey 今天做了什么

Casey 重构 asset 加载:

1. Worker 线程只做 CPU 工作:PNG 解码、数据转换
2. 把解码后的 RGBA pixels 推回主线程队列
3. 主线程每帧从队列取数据,`glTexImage2D` 上传到 GPU
4. Worker 不再创建 / 操作 context

**关键决策**:GL 上传延迟 1-2 帧可接受(asset 加载不是关键路径)。但游戏主循环不阻塞,流畅性保持。

## 2 · 心智模型

### 类比:工厂流水线分工

工厂有两条线:

- **原料处理线**(worker 线程)—— 切菜、和面,不需要烤箱
- **烘焙线**(主线程)—— 用烤箱(context),烤面包

Day 245 之前 worker 想自己用烤箱,但烤箱是"专人操作"(线程局部),工人 A 和工人 B 不能同时用。Day 246 把所有烘焙集中在主线程,worker 只准备原料,通过传送带(消息队列)送到主线程。

### 2.1 OpenGL 线程局部性

```rust
// 线程 A
let ctx = create_context();
ctx.make_current();  // 在线程 A 上 current
gl.something();  // OK

// 线程 B
gl.something();  // FAIL —— 线程 B 没 current context
```

要让线程 B 用 ctx:

```rust
// 线程 A
ctx.make_not_current();  // 释放

// 线程 B
ctx.make_current();  // 现在 B 上 current
gl.something();  // OK
```

但**同一时间一个 context 只能在一个线程 current**,所以这种"挪 context"不能并发。

### 2.2 共享 context

OpenGL 允许两个 context 共享资源(texture / buffer / shader):

```c
// 主线程
HGLRC main_ctx = wglCreateContext(hdc);

// worker 线程
HGLRC worker_ctx = wglCreateContext(hdc);
wglShareLists(main_ctx, worker_ctx);  // 共享!

// worker_ctx 现在 main_ctx 共享 texture/buffer
// 可以独立 make_current 在 worker 线程
```

但**不同 driver 对共享的支持不一致**:

- NVIDIA:完美
- AMD:基本支持,但某些资源类型不行
- Intel 集显:支持,但慢
- Mesa 软件 (llvmpipe):不支持

Casey 不信任 driver,Day 246 走"无共享"路线——worker 只 CPU,所有 GL 操作在主线程。

### 2.3 主线程上传队列

```rust
pub struct AssetLoader {
    queue: Mutex<Vec<UploadTask>>,
}

struct UploadTask {
    path: PathBuf,
    pixels: Vec<u8>,  // 已解码
    width: u32,
    height: u32,
    texture_id_out: Arc<Mutex<Option<TextureId>>>,
}

impl AssetLoader {
    pub fn load_async(&self, path: PathBuf) -> Arc<Mutex<Option<TextureId>>> {
        let result = Arc::new(Mutex::new(None));
        let task = UploadTask {
            path, pixels: vec![], width: 0, height: 0,
            texture_id_out: result.clone(),
        };

        // 把解码任务推给 worker 线程池
        self.workers.submit(move || {
            // worker:CPU 解码 PNG
            let (pixels, w, h) = decode_png(&task.path);
            // 把解码结果推回主线程队列
            let task = UploadTask {
                pixels, width: w, height: h,
                texture_id_out: task.texture_id_out.clone(),
                ..task
            };
            self.queue.lock().push(task);
        });

        result
    }

    /// 主线程每帧调用,处理上传队列
    pub fn process_uploads(&mut self, gl: &Context) {
        let tasks: Vec<_> = self.queue.lock().drain(..).collect();
        for task in tasks {
            let tex_id = upload_texture(gl, task.width, task.height, &task.pixels);
            *task.texture_id_out.lock() = Some(tex_id);
        }
    }
}
```

游戏代码:

```rust
// 启动时
let tex_handle = asset_loader.load_async("player.png".into());

// 每帧
asset_loader.process_uploads(&gl);

// 用 texture 时检查
if let Some(tex_id) = tex_handle.lock().as_ref() {
    draw_textured_quad(*tex_id, ...);
}
```

### 2.4 双阶段加载的好处

| | 同步加载 | 异步加载(Day 246) |
|---|---|---|
| 主线程阻塞 | 是(几十 ms) | 否 |
| 加载延迟 | 0 | 1-2 帧 |
| GPU 利用率 | 不连续(爆) | 平稳(每帧上传 N 个) |
| 复杂度 | 低 | 中 |

游戏启动时同步加载"必需"资源(主菜单背景),进游戏时异步加载"可选"资源(关卡贴图)。这是游戏开发的标配。

### 2.5 Vulkan 的对比

Vulkan 完全显式,没有"线程局部 context"概念:

```rust
// 任何线程都能录 command buffer
let cmd_buf = device.allocate_command_buffers(&alloc_info)?;
cmd_buf.begin_recording()?;
cmd_buf.copy_buffer_to_image(...)?;
cmd_buf.end_recording()?;

// 提交到 queue(可以是任何 queue)
queue.submit(cmd_buf, ...);
```

Vulkan 设计就是多线程友好。OpenGL 因为历史包袱(1992 设计),线程模型不友好。Day 246 是 OpenGL 的妥协,Vulkan 不需要。

---

**总结**:Day 246 把 GL context 操作集中到主线程,worker 只做 CPU 解码。这是 OpenGL 多线程的标准模式,Vulkan 不需要这种妥协。

- 显存占用 1/4 到 1/8

```rust
// 上传 BC7 压缩纹理
gl.compressed_tex_image_2d(

);
```

### 3.4 · 🦀 Rust 生态视角

Rust 的 thread + GL 模式:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let asset_loader = Arc::new(Mutex::new(AssetLoader::new()));

// spawn worker 线程池
for _ in 0..4 {
    let loader = asset_loader.clone();
    thread::spawn(move || {
        loop {
            let task = loader.lock().pop_task();
            if task.is_none() { break; }
            let task = task.unwrap();
            let pixels = decode_png(&task.path);  // CPU 工作
            loader.lock().submit_upload(task, pixels);  // 推回主线程
        }
    });
}

// 主线程
loop {
    asset_loader.lock().process_uploads(&gl);
    // ... game update + render ...
}
```

**Rust 所有权**:

- `Arc<Mutex<...>>` —— 多线程共享
- `Context` 不能跨线程(glow::Context 不是 Send/Sync)
- 把 GL 调用隔离在主线程,Rust 类型系统帮你检查

`unsafe impl Send for Context {}` 可以"强制"让 Context Send,但运行时 driver 可能崩。**不要这样做**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 OpenGL context 是 thread-local 的?这样设计有什么历史原因?

**参考解答**:OpenGL 1.0(1992)设计时,单核 CPU 为主,多线程是新兴概念。Context 是一个大状态机(几百个状态变量:当前纹理 / blend mode / depth test / ...),如果多线程共享,每次 GL 调用都要锁,极慢。把它做成 thread-local,各线程独立状态,无锁。

代价是多线程难做(必须共享 context 或主线程集中)。Vulkan(2016)重新设计,显式 command buffer + 显式同步,真正多线程友好。

**题**:写一个 AssetLoader,worker 线程解码 PNG,主线程上传。完成标准:启动时 spawn 4 个 worker,异步加载 10 张 PNG,主线程每帧检查上传队列,加载完后画出来。

**参考解答**:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

struct UploadTask {
    name: String,
    pixels: Vec<u8>,
    width: u32,
    height: u32,
}

struct AssetLoader {
    pending: Arc<Mutex<Vec<PathBuf>>>,
    upload_queue: Arc<Mutex<Vec<UploadTask>>>,
    loaded: Arc<Mutex<HashMap<String, TextureId>>>,
}

impl AssetLoader {
    fn new(paths: Vec<PathBuf>) -> Self {
        Self {
            pending: Arc::new(Mutex::new(paths)),
            upload_queue: Arc::new(Mutex::new(vec![])),
            loaded: Arc::new(Mutex::new(HashMap::new())),
        }
    }

    fn spawn_workers(&self, n: usize, image_decoder: fn(&Path) -> (Vec<u8>, u32, u32)) {
        for _ in 0..n {
            let pending = self.pending.clone();
            let upload_queue = self.upload_queue.clone();

            thread::spawn(move || {
                while let Some(path) = pending.lock().unwrap().pop() {
                    let (pixels, w, h) = image_decoder(&path);
                    let name = path.file_stem().unwrap().to_string_lossy().to_string();
                    upload_queue.lock().unwrap().push(UploadTask {
                        name, pixels, width: w, height: h,
                    });
                }
            });
        }
    }

    fn process_uploads(&self, gl: &glow::Context) {
        let tasks: Vec<_> = self.upload_queue.lock().unwrap().drain(..).collect();
        for task in tasks {
            let tex_id = unsafe {
                let t = gl.create_texture().unwrap();
                gl.bind_texture(glow::TEXTURE_2D, Some(t));
                gl.tex_image_2d(
                    glow::TEXTURE_2D, 0, glow::SRGB8_ALPHA8 as i32,
                    task.width as i32, task.height as i32, 0,
                    glow::RGBA, glow::UNSIGNED_BYTE, Some(&task.pixels),
                );
                // ... set params ...
                t
            };
            self.loaded.lock().unwrap().insert(task.name, TextureId(tex_id));
        }
    }
}
```

## 8 · Rust / Arch 落地代码

### Rust 完整 asset loader

```rust
use std::sync::{Arc, Mutex};
use std::thread;
use std::collections::HashMap;
use std::path::{Path, PathBuf};

pub struct TextureId(pub u32);

struct UploadTask {
    name: String,
    pixels: Vec<u8>,
    width: u32,
    height: u32,
}

pub struct AssetLoader {
    pending: Arc<Mutex<Vec<PathBuf>>>,
    upload_queue: Arc<Mutex<Vec<UploadTask>>>,
    pub loaded: Arc<Mutex<HashMap<String, TextureId>>>,
}

impl AssetLoader {
    pub fn new(paths: Vec<PathBuf>) -> Self {
        Self {
            pending: Arc::new(Mutex::new(paths)),
            upload_queue: Arc::new(Mutex::new(vec![])),
            loaded: Arc::new(Mutex::new(HashMap::new())),
        }
    }

    pub fn spawn_workers(&self, n: usize) {
        for _ in 0..n {
            let pending = self.pending.clone();
            let upload_queue = self.upload_queue.clone();

            thread::spawn(move || {
                while let Some(path) = pending.lock().unwrap().pop() {
                    // 简化:生成程序化 checker,实际解码 PNG 用 image crate
                    let size = 64u32;
                    let mut pixels = Vec::with_capacity((size * size * 4) as usize);
                    for y in 0..size {
                        for x in 0..size {
                            let c = if ((x / 8) + (y / 8)) % 2 == 0 { 255 } else { 32 };
                            pixels.extend_from_slice(&[c, c, c, 255]);
                        }
                    }
                    let name = path.file_stem().unwrap().to_string_lossy().to_string();
                    upload_queue.lock().unwrap().push(UploadTask {
                        name, pixels, width: size, height: size,
                    });
                    thread::sleep(std::time::Duration::from_millis(50));  // 模拟解码慢
                }
            });
        }
    }

    pub fn process_uploads(&self, gl: &glow::Context) {
        let tasks: Vec<_> = self.upload_queue.lock().unwrap().drain(..).collect();
        for task in tasks {
            let tex_id = unsafe {
                let t = gl.create_texture().expect("create_texture");
                gl.bind_texture(glow::TEXTURE_2D, Some(t));
                gl.tex_image_2d(
                    glow::TEXTURE_2D, 0, glow::SRGB8_ALPHA8 as i32,
                    task.width as i32, task.height as i32, 0,
                    glow::RGBA, glow::UNSIGNED_BYTE, Some(&task.pixels),
                );
                gl.tex_parameter_i32(glow::TEXTURE_2D, glow::TEXTURE_MIN_FILTER, glow::LINEAR as i32);
                gl.tex_parameter_i32(glow::TEXTURE_2D, glow::TEXTURE_MAG_FILTER, glow::LINEAR as i32);
                t
            };
            self.loaded.lock().unwrap().insert(task.name, TextureId(tex_id));
        }
    }

    pub fn pending_count(&self) -> usize {
        self.pending.lock().unwrap().len() + self.upload_queue.lock().unwrap().len()
    }
}

fn main() {
    let paths: Vec<_> = (0..10).map(|i| {
        PathBuf::from(format!("texture_{}.png", i))
    }).collect();

    let loader = AssetLoader::new(paths);
    loader.spawn_workers(4);

    println!("启动加载,等待 worker...");
    loop {
        let pending = loader.pending_count();
        let loaded = loader.loaded.lock().unwrap().len();
        println!("pending={}, loaded={}", pending, loaded);
        if pending == 0 { break; }
        thread::sleep(std::time::Duration::from_millis(100));
    }
    println!("加载完成");
}
```

## 10 · 深入:多线程 OpenGL context 的工程

casey 在 day246 把 context 创建移到主线程——这是 OpenGL 多线程的正确架构。

### 10.1 OpenGL context 的线程亲和性

OpenGL context 是 **thread-local**——绑定到创建它的线程。一个 context 同一时间只能在一个线程 active。

```
错误:Worker thread 创建 context → 用 context → switch 到 main thread 用
      GL 调用失败,context 不在 main thread

正确:Main thread 创建 context → make current → main thread 调用 GL
      Worker thread 只做 CPU 计算(asset decode),不调 GL
```

casey 在 day246 修复这个——把所有 GL call 移到主线程,worker 只做 CPU 工作。

### 10.2 worker thread 的职责

```
Main thread:
  - 创建 / 销毁 GL context
  - 所有 GL call
  - 游戏逻辑、渲染
  
Worker thread:
  - 纹理解码(JPEG / PNG → RGBA)
  - 模型加载(OBJ / GLTF → mesh)
  - 文件 IO
  
跨线程通信:
  - main → worker:任务请求
  - worker → main:完成回调 + 数据
```

casey HH 用类似架构。

### 10.3 cross-thread 数据传输

```rust
use std::sync::mpsc;

// main thread 创建 channel
let (tx, rx) = mpsc::channel();

// worker thread 接收请求,解码
std::thread::spawn(move || {
    while let Ok(request) = rx_requests.recv() {
        let decoded = decode_image(&request.data);  // CPU only
        tx.send(decoded).unwrap();  // 跨线程发回
    }
});

// main thread 接收结果
while let Ok(decoded) = rx.try_recv() {
    // main thread 上传到 GPU(GL call 安全)
    upload_texture_to_gpu(decoded);
}
```

GL call 只在 main thread,worker 只做 CPU。

### 10.4 shared context(可选优化)

OpenGL 支持 **shared context**——多个 context 共享资源:

```rust
let ctx1 = create_context(hdc, None);  // 主 context
let ctx2 = create_context(hdc, Some(ctx1));  // 共享 ctx1 的资源

// ctx1 和 ctx2 都能访问 texture、buffer
```

允许 worker thread 用 ctx2 上传纹理,main thread 用 ctx1 渲染。但实现复杂,driver 兼容性差。

casey HH 不用 shared context,简单架构足够。生产项目可以根据需求选。

### 10.5 现代 GPU API 的多线程

Vulkan / D3D12 / Metal 设计上支持多线程:

- **Command buffer** 在任意线程录制
- **Submit** 到 GPU queue(主线程或专用 thread)
- **Resource creation** 线程安全

OpenGL 是单线程 legacy API,多线程难用。Vulkan 修正这点。casey HH 用 OpenGL 简化,但生产项目可以考虑 wgpu(Vulkan-style 但 Rust safe)。

### 10.6 casey 的最终架构

casey 在 day246 后的架构:

```
Main thread:
  - 所有 GL call
  - 游戏主循环
  
Asset loading worker thread:
  - 解码图像 / 模型(纯 CPU)
  - 通过 channel 发送结果给 main
  
Main thread 收到结果:
  - 上传到 GPU
  - 通知游戏 asset ready
```

这是工业级游戏的标准架构。casey 在 day246 把 HH 升级到这个水平。

### 10.7 教学总结

day246 的核心要点:

1. **GL context 线程亲和**:一个 context 一个线程
2. **worker 只做 CPU**:不调 GL
3. **channel 通信**:线程安全数据传输
4. **shared context 可选**:复杂优化,driver 不稳定
5. **现代 API 改进**:Vulkan / D3D12 多线程友好

day246 修正 casey HH 的多线程架构,为后续 day247+ 的 debug 系统清理做准备。

### 10.8 完整的 Rust 多线程架构

```rust
use std::sync::{Arc, Mutex, mpsc};
use std::thread;

pub struct AssetLoader {
    sender: mpsc::Sender<AssetRequest>,
    results: Arc<Mutex<mpsc::Receiver<DecodedAsset>>>,
}

impl AssetLoader {
    pub fn new() -> Self {
        let (req_tx, req_rx) = mpsc::channel::<AssetRequest>();
        let (res_tx, res_rx) = mpsc::channel::<DecodedAsset>();
        let results = Arc::new(Mutex::new(res_rx));
        
        thread::spawn(move || {
            while let Ok(req) = req_rx.recv() {
                let decoded = match req.kind {
                    AssetKind::Image => decode_image(&req.data),
                    AssetKind::Model => decode_model(&req.data),
                };
                if res_tx.send(decoded).is_err() {
                    break;  // main thread disconnected
                }
            }
        });
        
        Self { sender: req_tx, results }
    }
    
    pub fn request(&self, kind: AssetKind, data: Vec<u8>) {
        self.sender.send(AssetRequest { kind, data }).unwrap();
    }
    
    pub fn poll(&self) -> Vec<DecodedAsset> {
        let rx = self.results.lock().unwrap();
        let mut results = vec![];
        while let Ok(asset) = rx.try_recv() {
            results.push(asset);
        }
        results
    }
}

// Main thread
let loader = AssetLoader::new();
loader.request(AssetKind::Image, std::fs::read("player.png").unwrap());

// Game loop
loop {
    let ready_assets = loader.poll();
    for asset in ready_assets {
        // main thread: upload to GPU
        upload_to_gpu(&gl, &asset);
    }
    // render...
}
```

完整的多线程 asset 加载架构。casey HH 的工业级实现。
