# Day 193 · 运行时设置编译时变量

> 有些 debug 选项是"编译时"的(用 `#[cfg(feature = "...")]` 控制),改了要重编译。今天 Casey 让运行时也能改这些:游戏内 UI 修改 build flags,触发自重编译。

## 0 · 为什么要有这一天

让我们从一个真实的开发循环说起。

你在调试游戏的 slow-motion 模式——一个用 `#[cfg(feature = "slow_mo")]` 包起来的代码路径。你按 F5 跑游戏,发现 slow_mo 没启用,因为 Cargo.toml 的 `[features]` 没默认加。你要:
1. 打开 Cargo.toml,改 `default = ["slow_mo"]`
2. 终端跑 `cargo build --features slow_mo`(等几秒)
3. 重启游戏,看效果
4. 发现不对,再改代码
5. 退出游戏,改 Cargo.toml 去掉 slow_mo
6. `cargo build`(再等几秒)
7. 重启游戏,验证 slow_mo 已关

这个循环每次 10-30 秒。一天调试几十次,**浪费半小时在 build flag 切换上**。这是工业级开发体验的反模式——开发者应该把时间花在思考,而不是等编译。

Casey 这天优化的目标:**让游戏内 UI 改 build flag,自动触发重编译 + 热重载**。开发者按几下 checkbox,游戏自己改 Cargo feature,spawn cargo build,完成后 hot-reload——**全程不离开游戏窗口**。

这本质上是 Day 192 自重编译的扩展:不只是"build",还能"build with options"。它代表了 industrial dev tooling 的方向——**把工具链 UI 化**,把命令行操作变成游戏内按钮。

为什么这件事难?因为 Cargo feature 是**编译时**概念——编译器在 build 时根据 feature 裁剪代码。运行时改 feature,必须重新触发 build。Cargo feature 不是运行时变量,改不了"当前进程的 feature"。

但 Casey 的洞察:**Cargo feature 是 CLI flag(`--features foo`)**。如果游戏 UI 能 spawn cargo build 带不同 flag,就**等效于改 feature**——虽然当前进程的 feature 不变,但下一个 reload 的进程的 feature 变了。配合 Day 192 的 cdylib hot-reload,游戏代码以动态库形式重新加载,新 feature 的代码进 game。

这个思路跨语言通用。Web 开发的 HMR(hot module replacement)、Unreal Engine 的 Live Coding、Unity 的 recompile——都是"开发时改代码,自动重 build"。Casey 这天把 Rust 这套基础设施搭起来。

完成这一天之后,你应该能:

- **理解 Cargo feature 的编译时本质**:`#[cfg(feature)]` 是 AST-level 裁剪,不是 runtime if
- **从游戏 UI 构造 cargo 命令行**:`Command::new("cargo")` 加参数,spawn 子进程
- **看懂 feature union 语义**:Cargo 的"feature unification"如何让 feature 在依赖图里传播
- **设计开发期 build flag 切换 UX**:用 UI checkbox 替代编辑 Cargo.toml 的循环
- **优化 Rust 编译时间**:用 sccache / mold / cranelift 等工具

## 1 · Casey 今天做了什么

Casey 的实现拆开看,几个步骤对应几个工程决策。

**第一步,定义全局 build options 数据结构**:

```rust
pub struct BuildOptions {
    pub features: Vec<String>,  // 启用的 feature 名
    pub release: bool,           // release vs debug
}
```

这个 struct 是 game state 的一部分,UI 直接读写它。

**第二步,UI 显示 checkbox 控制 features**。Immediate-mode UI(类似 Dear ImGui)的 checkbox API:`ui.checkbox("slow_mo", &mut is_enabled)`,每次调用立即处理输入 + 绘制。Checkbox 状态变化时,更新 `BuildOptions.features`。

**第三步,"Rebuild" 按钮触发 build**。按下时调 `options.to_command().spawn()`,spawn 一个 cargo 子进程。子进程独立运行,主游戏继续。子进程完成后(用 channel 或文件锁检测),主游戏触发 cdylib reload。

**第四步,cargo 子进程的参数动态构造**:

```rust
cmd.arg("build");
if options.release { cmd.arg("--release"); }
if !options.features.is_empty() {
    cmd.arg("--features").arg(options.features.join(","));
}
```

这把 `BuildOptions` 转成正确的 CLI flag。`--features foo,bar` 是 cargo 接受的语法。

视频里 Casey 强调:**这件事最巧妙的地方是 game UI 把 cargo 当作"后端服务"**。Game 是前端,cargo 是 build server,两者通过 CLI 参数 + 文件系统通信。这是 dev tooling 的一种通用架构。

## 2 · 心智模型

### 2.1 类比:厨房的可调菜单

我打个比方。餐厅有**固定菜单**(发行版),但厨师有"试菜"模式:今天加香菜,明天加辣。试菜时改配料单(类似 build flag),不重写整本菜单。

profiler UI 一样:发行版固定 features(发行版客户不能改),debug UI 临时改(厨师试菜)。这种"开发期可变,发行期固定"的分离是工业级 build 系统的标准。

更精确的类比:**乐队调音**。演出(发行版)时乐器定音固定,但排练(开发期)时乐手不断试不同音准。每次调音,乐队要"重 build"——所有乐器重新对齐。

Casey 的"runtime + rebuild"是"演奏时调音"——乐手演出中也能临时调音(改 feature),但要暂停一下(rebuild 时间)。完美但不可能。Casey 折衷:暂停时间尽量短(用 incremental build + sccache)。

### 2.2 Rust feature 的本质:从源码到二进制的"消失"

Rust 的 `#[cfg(feature = "...")]` 是编译时开关。让我把整个机制拆开。

```toml
# Cargo.toml
[features]
default = ["profiling"]
profiling = []
slow_mo = []
debug_render = []
```

```rust
#[cfg(feature = "slow_mo")]
fn update_slow() {
    dt *= 0.2;  // 慢动作 0.2x
}

#[cfg(not(feature = "slow_mo"))]
fn update_slow() {
    // 正常速度
}
```

编译时:

```bash
cargo build --features "slow_mo,debug_render"
```

Cargo 把 `--features` 解析出来,通过环境变量 `CARGO_FEATURE_SLOW_MO=1` 和 `CARGO_FEATURE_DEBUG_RENDER=1` 告诉 rustc。rustc 看到这些 env var,把对应的 `#[cfg(feature = "...")]` 标记为 true,删除 false 的 AST 节点。

**关键事实**:`#[cfg]` 不是 runtime if——它是 AST-level 裁剪。`#[cfg(feature = "slow_mo")]` 的代码,关 slow_mo 时**二进制里根本不存在**。所以"运行时改 feature"必须重 build——当前进程的 binary 已经是某 feature 配置,改不了。

这是为什么 Casey 的"runtime + rebuild"思路成立——它不真正"运行时改 feature",而是"运行时触发新 build",新 binary 用新 feature 配置。配合 cdylib hot-reload,主进程不重启,只重载 game library。

### 2.3 feature union 的语义:依赖图里的传播

Cargo feature 有一个**反直觉**的特性叫"feature unification"。让我详细讲。

```toml
# Cargo.toml
[features]
default = ["profiling"]
profiling = []
slow_mo = []
```

```bash
# 用户跑:cargo build
# → 实际 features = {profiling}(从 default)

# 用户跑:cargo build --no-default-features --features "slow_mo"
# → 实际 features = {slow_mo}(default 关掉,加 slow_mo)

# 用户跑:cargo build --features "slow_mo,debug_render"
# → 实际 features = {profiling, slow_mo, debug_render}
```

**unification**(统一)的微妙:**依赖图里某处启用 feature,所有用到该 crate 的地方都"看见"这个 feature 启用**。

```toml
# 你的 crate A 的 Cargo.toml
[dependencies]
serde = { version = "1", features = ["derive"] }

# 你的 crate A 依赖 crate B,B 也依赖 serde
# B 的 Cargo.toml:
[dependencies]
serde = { version = "1" }  # B 不开 derive
```

最终 build 时,**serde 是 `derive` 启用状态**——A 启用,B 没启用,但 Cargo 取**并集**。这是因为 Cargo 把所有依赖版本统一,只编译一份 serde(性能考虑)。所以 A 的 feature "污染"了 B 的视角。

这导致一个常见陷阱:**你禁用了 serde 的 `derive`,但下游用户启用了 `derive`,你的代码也"看见" `derive` 启用**。这会让你的代码在用户那里行为不同(你本地测和 CI 测可能不一致)。

工业实践:**feature 应该正交,避免不必要的 feature 间依赖**。Bevy 的 feature tree 几百个,这是工业级 complexity。

### 2.4 Cargo features vs C #ifdef:类型安全的演进

C 用 `#ifdef SLOW_MO` 做条件编译,通过 `-DSLOW_MO` 编译标志控制。Rust 的 feature 等价但**类型安全**。

```c
// C
#ifdef SLOW_MO
void update_slow() { dt *= 0.2; }
#else
void update_slow() { /* normal */ }
#endif
```

```rust
// Rust
#[cfg(feature = "slow_mo")]
fn update_slow() { dt *= 0.2; }
#[cfg(not(feature = "slow_mo"))]
fn update_slow() { /* normal */ }
```

差别:

- **C 的 `#ifdef` 是预处理器**——文本替换,在 parser 之前。容易出 bug:漏 `#endif`、嵌套 `#ifdef` 混乱、`#define` 名字打错不报错。预处理器不"理解"代码,只是 sed-like 替换。

- **Rust 的 `#[cfg]` 是编译器内置**——在 AST 阶段处理。编译器理解 token 级别,IDE / tooling 支持。`#[cfg]` 错配会立即报错,rust-analyzer 显示 cfg 不匹配的代码。

C 的 `#ifdef` 是 bug 温床。Linux 内核几百万行 `#ifdef`,维护痛苦——很多 bug 来自 `#ifdef` 漏写或嵌套错乱。Rust 改进了这点,但 trade-off 是 Rust 的 feature 必须在 Cargo.toml 声明(不能像 C 那样自由 `-D`),灵活性略低。

### 2.5 动态构造命令:从 struct 到 CLI

让我把 `BuildOptions` 转成 cargo 命令的过程详细讲。这是"game UI → cargo CLI"的关键桥梁。

```rust
use std::process::Command;

pub struct BuildOptions {
    pub features: Vec<String>,
    pub release: bool,
}

impl BuildOptions {
    pub fn to_command(&self) -> Command {
        let mut cmd = Command::new("cargo");
        cmd.arg("build");

        if self.release {
            cmd.arg("--release");
        }

        if !self.features.is_empty() {
            // --features foo,bar (逗号分隔)
            cmd.arg("--features").arg(self.features.join(","));
        }

        cmd
    }

    pub fn run_blocking(&self) -> std::io::Result<std::process::ExitStatus> {
        self.to_command().status()
    }

    pub fn run_async(&self) -> std::io::Result<std::process::Child> {
        self.to_command().spawn()
    }
}
```

`Command::new("cargo")` 创建一个 builder。`.arg()` 加参数。`.status()` 阻塞运行,等子进程结束。`.spawn()` 异步运行,返回 Child handle,主进程继续。

Casey 用 `.spawn()`——游戏不阻塞,cargo 在后台跑。子进程完成后(通过 channel 或文件锁通知),主游戏 reload cdylib。

**UI checkbox 改 features**:

```rust
fn draw_build_options_ui(
    ui: &mut Ui,
    options: &mut BuildOptions,
    all_features: &[&str],
) {
    ui.label("Build options");

    for feature in all_features {
        let mut on = options.features.iter().any(|f| f == *feature);
        if ui.checkbox(feature, &mut on) {
            if on {
                options.features.push(feature.to_string());
            } else {
                options.features.retain(|f| f != *feature);
            }
        }
    }

    if ui.button("Rebuild") {
        let _child = options.run_async().unwrap();
        println!("Spawned cargo build with features: {:?}", options.features);
    }
}
```

(假设 immediate-mode UI API,Day 196 详讲。)

每个 feature 一个 checkbox。用户勾选时,`options.features` 增删。Rebuild 按钮触发 `run_async()`。cargo 在后台跑,完成后 reload。

### 2.6 cargo feature 的限制

cargo feature 有几个约束你需要知道:

- **只能开启 Cargo.toml 声明过的 feature**。UI 里加"my_new_feature",cargo 报错"unknown feature"。新 feature 必须先改 Cargo.toml(开发者工作)。
- **同一 feature 只有 on/off,没中间值**。不能 `slow_mo = 0.5`(中间速度)。中间值用 runtime variable,不是 feature。
- **feature unification 让 feature 在依赖图里传播**。你 `default-features = false`,但下游用户启用,你的代码也看见 feature 启用。

这些限制来自 feature 的"编译时"本质——编译时必须确定所有 feature 状态,运行时不能动态变。

Casey 的方案是"运行时触发新 build"——绕过限制,但每次切换要等几秒。这是 trade-off:**编译时极快(0 开销),运行时极慢(几秒 rebuild)**。

## 3 · 四域深入

### 3.1 · Rust 生态视角

Rust 的 cfg / feature 系统有几层,我列出来你会看清层次:

- `#[cfg(target_os = "linux")]` — 平台条件(built-in)
- `#[cfg(feature = "serde")]` — feature gate(用户定义)
- `#[cfg(debug_assertions)]` — debug build 标志(built-in,Rust 自动给 debug profile)
- `#[cfg(test)]` — 测试 build
- `cfg!()` 宏 — 运行时查询(返回 bool,但实际编译时计算)

```rust
if cfg!(feature = "slow_mo") {
    // 编译时如果 slow_mo 开,这里编译,运行时进入
    // 编译时如果 slow_mo 关,这里不编译,runtime 不会到达
}
```

但 `cfg!()` 是**编译时**计算,运行时不变——它返回一个编译时常量。Casey 要的是"编译时但运行时可改",所以必须 rebuild。

**Cargo features 的依赖图传播**。一个 feature 可以拉依赖:

```toml
[features]
vulkan_backend = ["dep:wgpu", "wgpu?/vulkan"]
```

`vulkan_backend` 启用时,自动拉 `wgpu` 依赖,并启用 wgpu 的 `vulkan` feature。这是 Cargo 1.60+ 的 `dep:` 和 `?` 语法。

**Rust edition 的 cfg**:`#[cfg(edition = "2021")]`。edition 是大版本断点,影响语言语义(不是单纯 feature)。

**Architecture cfg**:`#[cfg(target_arch = "x86_64")]`、`#[cfg(target_arch = "aarch64")]`。SIMD 代码经常用,根据 CPU 架构编译不同版本。

### 3.2 · 编译时间优化:工业级 Rust 工程的核心问题

cargo build 全量:数十秒到几分钟(大项目)。增量:几秒。Casey 的自重编译用增量,**几秒内完成**。但即便增量,大项目仍可能 10+ 秒。优化技巧:

**sccache** — 编译缓存。Mozilla 开发,缓存编译结果,重复 build 用缓存命中。装:

```bash
sudo pacman -S sccache
export RUSTC_WRAPPER=sccache
cargo build  # 第一次慢,第二次极快
```

`RUSTC_WRAPPER=sccache` 让 cargo 用 sccache 包装 rustc。sccache 检查每个 crate 的 hash,命中则直接用缓存 .rlib,跳过 rustc 调用。CI 场景下加速 10-100 倍。

**mold linker** — 比 ld 快 10x 的链接器。Rust 项目 link 阶段常占 30-50% build 时间,mold 把这部分砍掉。装:

```bash
sudo pacman -S mold
# ~/.cargo/config.toml
[target.x86_64-unknown-linux-gnu]
linker = "clang"
rustflags = ["-C", "link-arg=-fuse-ld=mold"]
```

mold 由 Rui Ueyama 开发(他也是 lld 的作者),用多线程 + 现代算法,链接时间从 5 秒降到 0.5 秒。

**cranelift backend** — 替代 LLVM 的 codegen,debug build 快 2-3 倍。Rust 的 `rustc-codegen-cranelift` 项目,实验性但可用。Cargo + cranelift 在开发期极快。

**Incremental compilation** — Rust 1.24+ 内置。Cargo 跟踪文件修改时间,只重编变化的 crate + 其下游。`cargo build` 第二次开始极快。Cargo 默认开,debug profile 自动启用。

**Splitting crates** — 大单 crate 重 build 慢(整个 crate 重编)。拆成多个小 crate,只重编变的部分 + 下游。Bevy 把功能拆成 bevy_render / bevy_ecs / bevy_audio 等几百个 crate,就是为这个。

**分散 build** — 用 `cargo check`(只类型检查,不 codegen)替代 `cargo build`。IDE 经常用,rust-analyzer 默认用这个,几秒内反馈类型错误。

Casey 的 HH 是中等项目,默认 cargo + mold 足够。工业级大项目用全套工具。

### 3.3 · 游戏编程视角

商业引擎的 build flag 系统都有"运行时切换"概念:

**Unreal Engine** 用 **UBT(Unreal Build Tool)** + **Live Coding**。Project Settings 里勾选 build flag(如 `WITH_EDITOR`、`WITH_GPU_DETECTION`),UBT 重 build 整个项目(几十秒到几分钟)。Live Coding 让 C++ 改动后部分热重载——只重编变化的 .cpp,加载新 .so 到运行中的游戏。

**Unity** 用 **IL2CPP** 或 **Mono**。Player Settings 改 scripting define symbols(类似 Cargo feature),触发 IL2CPP recompile。Mono 后端 JIT,几秒;IL2CPP 后端 AOT,几十秒。Unity 的 hot reload 主要在 C# 层——改 C# 脚本立即重载,C++ 层(engine)要重启。

**Godot** 用 SCons build system,自定义 build flag。Godot 4 加了 GDExtension——类似 Casey 的 cdylib hot-reload,C++ 写扩展模块,改了重 build + 重载。

**Casey HH** 用 Rust + cdylib,game code 编成 .so,main loop 在 loader 进程。改 game code → cargo build → loader 检测 .so 文件变化 → reload。这个架构和 Unreal Live Coding / Unity cdylib 相同——**main loop + hot-reloadable game library**。

**工业 dev tooling 的核心方向**:**让开发者从命令行循环中解放,把工具链 UI 化**。Casey 这天做的"游戏 UI 改 build flag"是这个方向的一部分。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Feature flag** — 软件工程的开关模式。Compile-time feature(今天讨论)和 runtime feature(LaunchDarkly / Unleash)是两种变体。
- **Compile-time vs runtime** — 编程语言的核心二元。Compile-time 优化极致,但灵活度低;runtime 灵活,但有 overhead。
- **Incremental build** — 只重编变化部分。Make / Ninja / Cargo 都实现这套。

### 4.2 同级(并列方案对比)

| 切换方式 | 切换速度 | 性能开销 | 灵活度 |
|---|---|---|---|
| Runtime variable | 即时(纳秒) | 1 个 if 分支 | 高(可任意值) |
| env var | 重启进程 | 0 | 中(只能 string) |
| Cargo feature | 重 build(秒级) | 0(代码消失) | 中(on/off only) |
| Compile flag(rustc -C) | 全重 build(分钟级) | 0 | 低 |
| Build script (build.rs) | 重 build | 0 | 中(可生成代码) |

Casey 这天选 Cargo feature,因为它是"零 runtime overhead"+"秒级切换"的最佳平衡。

### 4.3 下级(内部零件)

- Cargo.toml `[features]` — feature 声明
- `--features` / `--no-default-features` CLI — 命令行选择
- `#[cfg(feature = "...")]` — 代码里用
- `cfg!()` 宏 — 编译时查询(返回 bool)
- UI checkbox — 用户接口
- `Command::new("cargo")` — spawn cargo 进程
- `RUSTC_WRAPPER=sccache` — 编译缓存

## 5 · 对照与变奏

### 5.1 Feature flag 的工业模式

| 系统 | 类型 | 切换粒度 | 何时用 |
|---|---|---|---|
| LaunchDarkly / Unleash | runtime | per-user / per-request | A/B 测试、灰度发布 |
| Cargo features | compile-time | per-build | 性能关键、发行版固定 |
| C `#ifdef` | preprocessor | per-build | 历史最悠久 |
| Python importlib | runtime | per-import | 动态加载 |
| Bevy Plugin | runtime | per-app | ECS 插拔 |

Rust 选 compile-time 是性能优先。Casey 的"runtime + rebuild"是工程折衷——发行版编译时极致性能,开发期运行时切换便利。

### 5.2 Feature flag 的反模式

工业实践里 feature flag 有几个常见反模式:

1. **过度使用**:每个 if 都用 feature,代码成蜘蛛网。读代码的人不知道哪个 feature 开了影响什么。
2. **未文档化**:feature 存在但没 doc,新开发者困惑。Cargo features 应该在 lib.rs 顶部 doc comment 列出。
3. **互相依赖**:`slow_mo` 依赖 `debug_render`,组合错乱。Feature 应该正交。
4. **长期短命 feature**:experimental feature 几年没合并到 main。每个 feature 是 maintenance burden,要么合并要么删除。
5. **隐式 default**:`default = ["everything"]` 让用户必须 `--no-default-features` 才能瘦身,反人类。default 应该是最小集合。

工业实践:**feature 数量严格控制**(单 crate < 20),每个有明确文档,experimental feature 限期合并或删除。

### 5.3 Cargo features vs Bevy plugins

Bevy 用 **Plugin** 系统(运行时)替代部分 feature:

```rust
// Bevy 风格
app.add_plugins(DefaultPlugins)
   .add_plugins(DebugPlugin::new());  // 运行时加 debug plugin
```

Plugin 是运行时插拔,不像 feature 编译时固定。代价:Plugin 有 vtable overhead(每次 plugin 方法调用通过 trait object)。优势:更灵活,不需要 rebuild。

Bevy 实际上**同时用 feature 和 plugin**——feature 控制编译时(如 `bevy_audio` 决定是否编译 audio 模块),plugin 控制运行时(如 `AudioPlugin::new()` 决定 app 是否启用 audio)。

Casey 的 HH 不用 plugin 系统(简化),但游戏代码用 cdylib hot reload 模拟"plugin"。两种思路本质相同——**运行时可变的功能子集**。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:为什么 Rust feature 只能开启,不能创建?为什么不能在 UI 里加一个"新 feature"叫 "my_test"?

**参考解答**:

feature 是 Cargo.toml 声明的编译时单元。编译时 rustc 要知道所有 feature 列表(从 Cargo.toml 读)。UI 里加 "my_test" → Cargo.toml 没声明 → cargo 报错 "unknown feature 'my_test'"。

用户能改"哪些已知 feature 开",但不能"加新 feature"。加新 feature 必须先改 Cargo.toml(开发者工作),然后 UI 能开关。这是 cargo feature 的"白名单"模型——只接受预先声明的 feature。

### Lv2 · 动手实践

**题**:写程序读 Cargo.toml 的 [features] 段,列出所有可用 feature。然后构造 cargo build 命令带指定 feature,并实际跑。

要求:
1. 用 `toml` crate 解析 Cargo.toml
2. 列出 features 列表
3. 让用户输入选哪些(简化:用 argv 传)
4. 构造 Command,spawn,等结果

**参考解答**:

```rust
use std::process::Command;
use toml::Value;

fn parse_features(cargo_toml: &str) -> Vec<String> {
    let v: Value = toml::from_str(cargo_toml).unwrap();
    let features = v.get("features").and_then(|f| f.as_table());
    match features {
        Some(t) => t.keys().map(|k| k.to_string()).collect(),
        None => vec![],
    }
}

fn main() {
    let cargo_toml = std::fs::read_to_string("Cargo.toml").unwrap();
    let all_features = parse_features(&cargo_toml);

    println!("Available features:");
    for f in &all_features {
        println!("  - {}", f);
    }

    // argv 选 feature
    let selected: Vec<&str> = std::env::args().skip(1).collect();
    println!("\nSelected: {:?}", selected);

    let mut cmd = Command::new("cargo");
    cmd.arg("build");
    if !selected.is_empty() {
        cmd.arg("--features").arg(selected.join(","));
    }
    println!("Running: {:?}", cmd);

    let output = cmd.status().unwrap();
    std::process::exit(output.code().unwrap_or(1));
}
```

完整项目:游戏 UI checkbox 改 build flag,触发 cargo build。

```bash

cd feature-toggle

```

`Cargo.toml`:

```toml
[package]
name = "feature-toggle"
version = "0.1.0"
edition = "2021"

[features]
default = []
slow_mo = []
debug_render = []
profiling = []

[dependencies]
toml = "0.8"
```

`src/main.rs`:

```rust
use std::process::Command;
use toml::Value;

#[derive(Debug, Clone)]
pub struct BuildOptions {
    pub features: Vec<String>,
    pub release: bool,
}

impl Default for BuildOptions {
    fn default() -> Self {
        BuildOptions { features: vec![], release: false }
    }
}

impl BuildOptions {
    pub fn to_command(&self) -> Command {
        let mut cmd = Command::new("cargo");
        cmd.arg("build");
        if self.release {
            cmd.arg("--release");
        }
        if !self.features.is_empty() {
            cmd.arg("--features").arg(self.features.join(","));
        }
        cmd
    }

    pub fn rebuild_async(&self) -> std::io::Result<()> {
        let _child = self.to_command().spawn()?;
        println!("Rebuilding with features: {:?}", self.features);
        Ok(())
    }
}

fn parse_features_from_cargo_toml() -> Vec<String> {
    let cargo_toml = std::fs::read_to_string("Cargo.toml")
        .expect("Cargo.toml not found");
    let v: Value = toml::from_str(&cargo_toml)
        .expect("invalid Cargo.toml");
    v.get("features")
        .and_then(|f| f.as_table())
        .map(|t| {
            t.keys()
                .filter(|k| k.as_str() != "default")  // 不显示 default
                .map(|k| k.to_string())
                .collect()
        })
        .unwrap_or_default()
}

fn main() {
    let all_features = parse_features_from_cargo_toml();
    println!("Available features: {:?}", all_features);

    // 模拟 UI:命令行选择
    let args: Vec<String> = std::env::args().skip(1).collect();
    let mut options = BuildOptions::default();

    for arg in &args {
        if arg == "--release" {
            options.release = true;
        } else if all_features.contains(arg) {
            options.features.push(arg.clone());
        } else {
            eprintln!("Unknown feature: {}", arg);
        }
    }

    println!("Options: {:?}", options);
    options.rebuild_async().expect("rebuild failed");
}
```

```bash
# 装 mold linker

[target.x86_64-unknown-linux-gnu]
linker = "clang"
rustflags = ["-C", "link-arg=-fuse-ld=mold"]

sudo pacman -S sccache
export RUSTC_WRAPPER=sccache

# 验证
time cargo build
# 用了 mold + sccache 应该比默认快 5-10x
```

**Troubleshooting**:

- `error: unknown feature` — Cargo.toml 没声明。加 `[features] my_feature = []`。
- spawn 失败 — cargo 不在 PATH,用 `/usr/bin/cargo`。
- 编译慢 — 用 mold + sccache,或拆 crate。
- Live reload 失败 — cdylib 输出路径错。在 Cargo.toml 加 `[lib] crate-type = ["cdylib"]`。
