
# Day 219 · 自动构造的调试层级

> 之前调试层级(`physics/gravity`、`player/max_hp`)是手动维护的树。今天 casey 让系统**从字符串自动构造**——"a/b/c" 自动展开成嵌套节点。零配置,加 guid 就自动归类。

## 0 · 为什么要有这一天

之前的 debug hierarchy:

```rust
let root = DebugNode::new("root");
let physics = root.add_child("physics");
physics.add_var("gravity");
```

每加一个变量都要手动维护树。1000 个变量 = 1000 行树构造代码。改一个变量名要改两处(字符串 + 树节点)。

**casey 今天的方案**:让字符串本身编码层级。

```rust
debug_value("physics/gravity", 9.8);
debug_value("physics/friction", 0.5);
debug_value("player/max_hp", 100.0);
debug_value("player/walk_speed", 5.0);
```

系统扫描所有 guid 字符串,按 `/` 分割,自动构造树:

```
root
├── physics
│   ├── gravity = 9.8
│   └── friction = 0.5
└── player
    ├── max_hp = 100.0
    └── walk_speed = 5.0
```

**收益**:

- 零配置:加一个 guid 自动归类
- 自文档化:字符串名 = 路径
- 容易重构:改字符串,树自动更新

**代价**:

- 字符串路径要稳定(改名 = 路径变)
- 树深度由字符串决定(可能很深)

心理锚点:看完今天,你能用"字符串即路径"的设计思想简化配置系统。

## 1 · Casey 今天做了什么

1. **加 path parser**:字符串按 `/` 分割
2. **加 auto-build tree**:扫描所有 guid,构造嵌套 HashMap
3. **改 UI 渲染**:递归画树
4. **加缓存**:树只在 guid 集合变化时重建,不每帧扫

## 2 · 心智模型

### 类比:文件系统路径

文件系统 `/home/sun/file.txt` 的路径本身就是树:`/` → `home` → `sun` → `file.txt`。OS 不需要你手动建树,路径字符串自动定义结构。

casey 的 debug hierarchy 就是用文件系统路径风格组织调试变量。每条 guid 是一个"路径",自动归到树。

这个类比可以更深:**文件系统不需要"建树"的真正原因**是路径字符串**编码了完整的祖先链**。`/home/sun/file.txt` 这一个字符串同时表达了"sun 是 file.txt 的父节点"、"home 是 sun 的父节点"。OS 不需要额外的 metadata 描述这个层级——字符串本身就是 metadata。

软件里这个模式叫**自描述数据(self-describing data)**——数据的标识符同时描述了它和其他数据的关系。和"独立 ID + 外部关系表"对比,自描述极大简化系统。

类比还能再深:**Linux 的 `/proc/sys/` 不仅是路径,还是真实配置**。`cat /proc/sys/kernel/shmmax` 既显示路径,也读取了"kernel 子系统下 shmmax 配置"。配置的路径 = 配置的逻辑归类。这是 Unix 哲学的核心:**一切皆文件,文件即路径,路径即语义**。casey 把这个哲学带到游戏 debug 系统,效果好得惊人。

### 2.1 路径解析

```rust
fn parse_path(s: &str) -> Vec<&str> {
    s.split('/').filter(|p| !p.is_empty()).collect()
}

// "physics/gravity" → ["physics", "gravity"]
// "a/b/c/d" → ["a", "b", "c", "d"]
```

Rust 的 `split` 返回迭代器,`filter` 去掉空段(处理 `//`),`collect` 转 Vec。

### 2.2 树构造

```rust
use std::collections::BTreeMap;  // 有序遍历

enum TreeNode {
    Leaf { value: DebugValue },
    Branch { children: BTreeMap<String, TreeNode> },
}

fn build_tree(guids: &[(String, DebugValue)]) -> TreeNode {
    let mut root = TreeNode::Branch { children: BTreeMap::new() };
    for (path, value) in guids {
        let parts: Vec<&str> = path.split('/').collect();
        insert_path(&mut root, &parts, value.clone());
    }
    root
}

fn insert_path(node: &mut TreeNode, parts: &[&str], value: DebugValue) {
    if parts.is_empty() {
        return;
    }
    if parts.len() == 1 {
        // leaf
        if let TreeNode::Branch { children } = node {
            children.insert(parts[0].to_string(), TreeNode::Leaf { value });
        }
    } else {
        // recurse
        if let TreeNode::Branch { children } = node {
            let child = children.entry(parts[0].to_string())
                .or_insert_with(|| TreeNode::Branch { children: BTreeMap::new() });
            insert_path(child, &parts[1..], value);
        }
    }
}
```

`BTreeMap` 而不是 `HashMap`,因为遍历时按 key 排序("physics" 在 "player" 前),UI 渲染有序。

### 2.3 缓存:不每帧重建

每帧扫 1000 guid + 构造树 = 几毫秒。144 FPS 下浪费。casey 加 dirty flag:

```rust
struct DebugHierarchy {
    tree: TreeNode,
    dirty: bool,
    last_guid_count: usize,
}

impl DebugHierarchy {
    fn update(&mut self, guids: &[(String, DebugValue)]) {
        if !self.dirty && guids.len() == self.last_guid_count {
            return;  // 没变化,跳过重建
        }
        self.tree = build_tree(guids);
        self.last_guid_count = guids.len();
        self.dirty = false;
    }
}
```

更精细:用 hash of guid set 检测内容变化(数量同但内容变)。但通常数量变化就够了。

### 2.4 UI 渲染

递归画树:

```rust
fn draw_node(ui: &mut Ui, node: &TreeNode, depth: usize) {
    match node {
        TreeNode::Leaf { value } => {
            ui.text(&format!("{}", value));  // 简化
        }
        TreeNode::Branch { children } => {
            for (name, child) in children {
                ui.indent(depth);
                if ui.collapsing_header(name) {
                    draw_node(ui, child, depth + 1);
                }
            }
        }
    }
}
```

每个 branch 用 collapsing header(可折叠),用户点击展开。

### 2.5 第一性原理推导:为什么"自描述数据"简化系统

软件设计里有两条截然不同的路线:**显式 metadata** 和**自描述数据**。

**显式 metadata**:
```rust
// 数据 + metadata 分离
let var = DebugVar { id: 1, value: 9.8 };
let path = vec!["physics", "gravity"];  // 单独维护路径
register(var, path);  // 注册到树
```

每次加 var,要写两处(var 本身 + path)。改 path 要改两处。漏改一处,path 不一致。

**自描述数据**:
```rust
// 数据自带路径
let var = DebugVar { name: "physics/gravity", value: 9.8 };
register(var);  // 路径从 name 解析
```

数据自己说明它在树里的位置。零冗余。

**为什么自描述更好?** 用信息论推导:

- 显式 metadata 系统:数据 + 关系表是**两个独立信息源**。一致性靠人维护。
- 自描述系统:数据本身**包含**关系信息。一致性自动保证。

工程上,自描述系统消除了"两个信息源不同步"这一整类 bug。casey 选这条,debug 系统的"加新 var 不需要建树"是直接收益。

**自描述的代价**:
- 数据格式更严格("name 必须是合法路径")
- 改结构要改所有数据(改路径分隔符要重写所有 name)
- 数据冗余(每个数据都重复存祖先路径)

但对 debug 系统来说,这些代价都很小,收益巨大。

**Unix 文件系统就是自描述的胜利**——50 年来文件系统核心设计没变,因为路径字符串已经足够表达层级。casey 把这个洞察带到游戏开发。

### 2.6 树的内存表示

casey 的树用 enum + BTreeMap,这是个折衷选择。看几个替代方案:

**方案 1:enum + BTreeMap(casey 选的)**
```rust
enum TreeNode {
    Leaf { value: DebugValue },
    Branch { children: BTreeMap<String, TreeNode> },
}
```
优点:简洁、自动有序。
缺点:每个节点一个 BTreeMap 分配,deep tree 浪费内存。

**方案 2:索引树(arena + index)**
```rust
struct Tree { nodes: Vec<NodeData> }
struct NodeData {
    name: String,
    first_child: Option<usize>,
    next_sibling: Option<usize>,
    value: Option<DebugValue>,
}
```
优点:无 Box 分配,所有节点连续内存,cache 友好。
缺点:复杂,删除节点要 GC。

**方案 3:flat map with dotted key**
```rust
struct Tree { vars: BTreeMap<String, DebugValue> }  // key = "physics/gravity"
```
优点:极简,一个 map 完事。
缺点:UI 渲染要每次 split key 计算层级,效率低。

**方案 4:Trie**
```rust
struct Trie { root: TrieNode }
struct TrieNode { children: HashMap<String, TrieNode>, value: Option<DebugValue> }
```
和 casey 的方案 1 类似,但用 HashMap 而不是 BTreeMap(无序)。

casey 选方案 1,平衡简洁和功能。生产代码可能选方案 2(性能)或方案 3(极简)。HH 项目是教学,清晰度优先。

**BTreeMap vs HashMap 决策**:
- BTreeMap:O(log N) lookup,有序遍历,内存 ~2x(节点结构)
- HashMap:O(1) lookup,无序遍历,内存 ~1x

casey 选 BTreeMap 因为 UI 渲染要按字母序。如果只 lookup,HashMap 更快。这是"按需求选数据结构"。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发里"路径即结构"的例子:

- Unity Inspector:组件路径 `Transform/Position/X`
- Unreal Engine:Blueprint 变量路径 `Character/Health/Max`
- Blender:object data path

所有这些都是"用字符串编码层级",UI 自动展开。

### 3.2 · Linux 系统编程视角

Linux 文件系统就是这个思想:

- `/proc/sys/net/ipv4/tcp_keepalive_time` 自动归类到 `net/ipv4/`
- `/sys/class/tty/tty0/...` 同样

sysctl 也是 `kernel.shmmax` 这种 dot-path 风格。

### 3.3 · Rust 生态视角

Rust 表达树形数据:

```rust
// Pattern 1:enum(本文用的)
enum TreeNode { Leaf(..), Branch(..) }

// Pattern 2:Box 指针
struct Node { children: Vec<Box<Node>> }

// Pattern 3:索引树(arena + index)
struct Tree { nodes: Vec<NodeData> }
struct NodeData { first_child: Option<usize>, next_sibling: Option<usize> }

// Pattern 4:indextree crate
```

casey 用 Pattern 1。Rust 的 enum + Box 是简单场景的最佳选择;arena + index 是高性能场景(避免 Box 分配)。

### 3.4 · 字符串设计视角

路径字符串设计原则:

- 用 `/` 或 `.` 作分隔符(直觉清晰)
- 段名稳定(改 = 路径变)
- 段名唯一(同层不重名)
- 大小写一致(避免 `Player` 和 `player` 并存)

casey 选 `/`,因为它和文件系统一致,IDE / 工具(模糊搜索)友好。

### 3.5 · 🐧 Linux 系统编程视角(扩展)

Linux 把"路径即结构"发挥到极致。具体例子:

**1. sysctl 的 dotted notation**:`kernel.shmmax`、`net.ipv4.tcp_keepalive_time`。点分路径,sysctl 命令解析后路由到 `/proc/sys/kernel/shmmax`、`/proc/sys/net/ipv4/tcp_keepalive_time`。两种表示(点和路径)等价。

**2. /proc 文件系统的"伪文件"**:`/proc/[pid]/status` 不是真文件,是内核动态生成。但路径名决定了语义——`[pid]/status` 表示进程状态,`[pid]/maps` 表示内存映射。casey 的 debug path 完全对应这种"路径即语义"。

**3. /sys 的 device tree**:`/sys/devices/pci0000:00/0000:00:01.0/...` 自动从硬件拓扑构造。每加一个设备,自动出现在对应路径。零配置。casey 的"加 guid 自动归类"完全对应。

**4. dbus 的 object path**:`/org/freedesktop/DBus` 是 dbus 服务里的对象路径,完全文件系统风格。一个 dbus 服务可能有几十个对象,路径自动组织层级。

**5. systemd unit name**:`dev-sda1.device`、`multi-user.target`、`ssh.service`。unit 类型(service、device、target)做"扩展名",name 是路径主体。变体但同思想。

**6. XML / YAML / JSON path**:`/foo/bar/baz` 是 XML XPath,`$.foo.bar.baz` 是 JSONPath,`foo.bar.baz` 是 YAML dot notation。这些工业标准都用了 casey 的"字符串即路径"思想。

casey 的 debug path 是 Unix 哲学的直接应用——"路径即语义"在工程上反复胜利。

### 3.6 · 🎮 游戏工业对照

游戏引擎里的路径风格:

**Unreal Engine 的 `FName`**:UE 把字符串 intern 到全局表,FName 是 (id, number) 对。但 path 风格的引用 `/Game/MyAsset/MyTexture` 也是 UE 标准。Content Browser 里的目录结构用 path 表达。

**Unity 的 `Resources.Load("path/To/Asset")`**:Unity 的 Resources 文件夹下用 path 寻址。`Resources.Load("Weapons/Sword")` 加载 `Assets/Resources/Weapons/Sword.prefab`。casey 的 debug path 完全对应。

**Godot 的 NodePath**:`"Player/Body/Sprite"` 这种路径访问 scene tree 的节点。Godot 的 scene 本身就是树,path 是它的引用语法。

**Bevy 的 reflect path**:Bevy 的 reflection 系统支持 `"player.health.max"` 这种路径访问 entity 的字段。完全 casey 风格。

**对比结论**:**整个游戏工业都用 path 编码层级**。casey 不是发明了什么新东西,他是把行业最佳实践搬到了教学项目里。学懂这个,你看任何引擎代码都能直接理解。

### 3.7 · 🎨 图形学视角

图形学的 path 编码:

**1. Render pass 的 attachment path**:`forward.color_hdr`、`gbuffer.normal`、`shadow.depth`。渲染管线的 attachment 用 path 命名,调试工具(RenderDoc)按 path 显示。

**2. Shader 的 uniform path**:`material.base_color`、`light[0].position`、`camera.view_matrix`。GLSL uniform 的命名层级用 `.` 表示,reflection API 查询时按 path 找。

**3. Scene graph**:节点的命名路径 `"root/player/weapon/sword"`。scene graph 是树,每个节点有唯一路径。

**4. Material graph (node-based shader editors)**:Blender Shader Editor、Unreal Material Editor、Substance Designer 都用节点图,节点之间的连接通过"socket path"`noise_texture.color_out` 表达。

casey 的 debug path 在渲染调试里也有用——比如把 render pass 按路径组织 `render/opaque/static`、`render/opaque/skeletal`、`render/transparent/particles`,UI 自动展开成树,调试渲染管线极方便。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么用 BTreeMap 而不是 HashMap 存 children?

**参考解答**:BTreeMap 按 key 排序,UI 渲染时 "physics" 在 "player" 前(字典序),用户预期这样。HashMap 顺序随机,每次启动顺序不同,UX 差。

### Lv2 · 动手实践

**题**:实现 path parser + build_tree + draw_node(简化为打印)。测试:

- 输入一组路径,验证树结构
- 嵌套深路径正确处理

**算法详解**:

`build_tree` 的核心是 `insert_path` 递归。对路径 `["physics", "gravity"]`:
1. 看 root 的 children,如果没有 "physics",插入一个空 branch
2. 递归进入 "physics" branch,看它的 children
3. 路径只剩 1 段 `["gravity"]`,插入一个 leaf

**为什么 `or_insert_with` 而不是 `or_insert`?** `or_insert(value)` 总是构造 value(即使 key 已存在,白白浪费)。`or_insert_with(closure)` 只在需要时调用 closure。对 `TreeNode::Branch { children: BTreeMap::new() }` 这种有分配的值,差别明显。

**为什么 `BTreeMap` 而不是 `HashMap`?** UI 渲染时希望按字母序显示("physics" 在 "player" 前),`BTreeMap` 自动有序,`HashMap` 随机顺序。代价是 lookup 从 O(1) 变 O(log N),但 N(同层节点数)通常 < 100,差异微小。

**`split('/').filter(|s| !s.is_empty())` 的作用**:
- `split('/')` 把 "a//b" 切成 ["a", "", "b"]
- `filter(|s| !s.is_empty())` 去掉空段
- 结果 ["a", "b"]
这处理了路径里有多余 `/` 的边界情况。

**TreeNode enum 的 Rust 优势**:`enum` 加 `match` 让编译器检查你处理了所有 case(Leaf 和 Branch)。如果以后加新 case(比如 "Reference" 节点,引用其他路径),所有 match 处都会编译错误,强制你处理。C 的 tagged union 没这个保证。

**测试设计**:
- 测试 `a/b` 和 `a/c` 在 `a` 下有 2 个 children
- 测试嵌套 `a/b/c/d` 深度正确
- 测试空路径(过滤后 parts = [])不 crash
- 测试重复路径(同 guid 多次 set)的行为

**参考解答**:

```rust
use std::collections::BTreeMap;

#[derive(Debug)]
enum TreeNode {
    Leaf(String),
    Branch { children: BTreeMap<String, TreeNode> },
}

fn build_tree(paths: &[(&str, String)]) -> TreeNode {
    let mut root = TreeNode::Branch { children: BTreeMap::new() };
    for (path, val) in paths {
        let parts: Vec<&str> = path.split('/').filter(|s| !s.is_empty()).collect();
        insert(&mut root, &parts, val.clone());
    }
    root
}

fn insert(node: &mut TreeNode, parts: &[&str], val: String) {
    if parts.is_empty() {
        return;
    }
    if let TreeNode::Branch { children } = node {
        if parts.len() == 1 {
            children.insert(parts[0].to_string(), TreeNode::Leaf(val));
        } else {
            let child = children.entry(parts[0].to_string())
                .or_insert_with(|| TreeNode::Branch { children: BTreeMap::new() });
            insert(child, &parts[1..], val);
        }
    }
}

fn draw(node: &TreeNode, depth: usize) {
    let indent = "  ".repeat(depth);
    match node {
        TreeNode::Leaf(v) => println!("{}= {}", indent, v),
        TreeNode::Branch { children } => {
            for (name, child) in children {
                println!("{}{}/", indent, name);
                draw(child, depth + 1);
            }
        }
    }
}

fn main() {
    let paths = vec![
        ("physics/gravity", "9.8".to_string()),
        ("physics/friction", "0.5".to_string()),
        ("player/max_hp", "100".to_string()),
        ("player/walk_speed", "5".to_string()),
        ("render/fps", "60".to_string()),
    ];
    let tree = build_tree(&paths);
    draw(&tree, 0);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn build_simple_tree() {
        let paths = vec![
            ("a/b", "1".to_string()),
            ("a/c", "2".to_string()),
        ];
        let tree = build_tree(&paths);
        if let TreeNode::Branch { children } = tree {
            assert!(children.contains_key("a"));
            if let TreeNode::Branch { children: a_children } = &children["a"] {
                assert_eq!(a_children.len(), 2);
                assert!(a_children.contains_key("b"));
                assert!(a_children.contains_key("c"));
            } else { panic!("a should be branch"); }
        } else { panic!("root should be branch"); }
    }
}
```

### Lv3 · 迁移设计

**题**:设计一个 JSON 编辑器,自动从 JSON Pointer 路径(`$['foo']['bar']` 或 `/foo/bar`)构造可编辑的树视图。

**详细提示**:
- JSON Pointer (RFC 6901):`/foo/bar` 表示 `obj["foo"]["bar"]`
- 数据结构:`enum JsonNode { Null, Bool(bool), Num(f64), Str(String), Array(Vec<JsonNode>), Object(BTreeMap<String, JsonNode>) }`
- Tree 构造:递归把 Object 的 children 显示为 branch,scalar 显示为 leaf
- 编辑:每个 leaf 有 inline editor(text input for Str/Num, checkbox for Bool)
- 验证:编辑后类型检查,Str 不能输成 Num

边界情况:
- 大数组(1000+ 元素):virtual scrolling,只渲染可见部分
- 大对象:同样 virtual scrolling
- 嵌套深:折叠展开,默认展开前 3 层
- 数组下标 vs object key 混合:JSON Pointer `/0/foo` 表示 `arr[0]["foo"]`
- 引用循环:JSON 标准不允许,但要检测输入是否恶意构造

参考实现:VSCode 的 JSON editor、`jsoneditor` 库、`egui` 的 JSON demo。casey 的 build_tree 算法是这些工具的核心。

### 实战补充:大规模 debug path 的挑战

casey 的 path parser 在 ~1000 个 guid 下完美工作。如果项目规模到 ~10000 guid,会出现几个新问题:

**1. 树深爆炸**:`"player/weapons/primary/fire_rate modifiers/aiming/bonus"` 这种深路径让 UI 显示成 6 层缩进,屏幕宽度不够。casey 的解决方案:UI 自动折叠到 3 层,深层点击展开。

**2. 路径名冲突**:两个不同 module 都有 "player/health",但语义不同(player 的 max hp vs boss 的 hp)。casey 用 module 前缀:`"gameplay/player/health"` vs `"enemy/boss/health"`。

**3. 字符串性能**:10000 guid × 30 字节平均 = 300KB 字符串。每次启动 build_tree 扫 300KB,~10μs。casey 加 dirty flag,只在 guid 集合变化时重建。

**4. 内存碎片**:TreeNode 是 enum + BTreeMap,每个节点独立分配。10000 节点 × 100 字节 = 1MB 碎片。casey 后期(Day 250+)改成 arena + index 树,所有节点连续内存。

**5. UI 渲染成本**:递归画 10000 节点 = 10000 个 UI element。egui 这种 immediate-mode UI 每帧重建 widget,~5ms。casey 加 virtual scrolling,只画展开可见的节点,降到 ~100 nodes/帧。

**6. 路径稳定性**:重构代码改字符串(比如 "player" → "avatar"),path 变化,用户保存的"展开状态"丢失。casey 用 GUID(数字)+ path 双索引,即使 path 改,GUID 不变,展开状态保留。

这些挑战在 production game engine 里都需要解决。casey 的 HH 教学版本简化处理,但理解这些边界情况对你做真实项目很重要。

### 路径风格的取舍:slash vs dot

casey 选 `/` 分隔符,但 `.` 也有优势。对比:

| 维度 | `/` (slash) | `.` (dot) |
|---|---|---|
| 文件系统一致 | 是 | 否 |
| URL 一致 | 是 | 否 |
| 编程语言成员访问 | 否 | 是(C/Java/Rust 的 `obj.field`) |
| 显示宽度 | 窄 | 极窄 |
| 输入难度(键盘) | 中(需 shift) | 易 |
| 与 Rust path 冲突 | 否 | 是(`std::vec::Vec`) |

Unix 工具(sysctl、dbus)混用——`kernel.shmmax` 用点,`/sys/devices/...` 用斜杠。casey 选 `/` 因为 debug UI 显示时更像文件路径,用户直觉清晰。

如果你做自己的项目,选哪个都行,关键是一致。混用最坑(Unity 的 `Resources.Load` 用斜杠,C# 反射用点,初学者混乱)。

## 10 · 深入:层级数据结构的实现模式

casey 今天实现的"调试层级"——debug 状态按 namespace 组织成树,UI 递归展开。这是工程里反复出现的模式。让我把所有相关实现做一遍对比。

### 10.1 五种层级数据结构

**模式 1:Path-based key**(casey 的选择)

```rust
let guid = hash("game/player/health");  // 扁平 hash
// UI 通过 split('/') 自动构造层级显示
```

- 优点:简单,无数据结构变化。UI 端解析 path。
- 缺点:每次显示都要解析 path,O(string length)。

**模式 2:嵌套树**

```rust
struct DebugTree {
    children: HashMap<String, DebugTree>,
    value: Option<DebugValue>,
}
// 查询 "game/player/health": 走 game → player → health 三层
```

- 优点:层级是结构的一部分,不需要解析 path。
- 缺点:数据结构复杂,需要管理 children HashMap。

**模式 3:Implicit tree via sort**

```rust
// 所有 debug 变量按字母排序
debug_vars: Vec<(String, DebugValue)>  // sorted
// 排序后,相同 prefix 自然相邻,UI 可以识别 prefix boundary
```

- 优点:无 HashMap 开销,缓存友好。
- 缺点:每次插入要保序,排序 O(n log n)。

**模式 4:Trie(前缀树)**

```rust
struct Trie {
    children: BTreeMap<char, Box<Trie>>,
    value: Option<DebugValue>,
}
// "game/player/health" 走 g→a→m→e→/→...
```

- 优点:相同 prefix 共享内存,长 path 节省空间。支持 prefix scan。
- 缺点:节点开销大(每 char 一个 node),短 path 反而费内存。

**模式 5:Radix tree(压缩 Trie)**

```rust
struct RadixNode {
    children: Vec<(String, Box<RadixNode>)>,  // 共享 prefix 作为一个 String
    value: Option<DebugValue>,
}
// "game/player/health" 和 "game/player/mana" 共享 "game/player/" prefix
```

- 优点:Trie 的优点但更紧凑。路由库(如 Spring、Gin)用这个。
- 缺点:实现复杂,split/merge 节点逻辑繁琐。

### 10.2 casey 的选择:模式 1 + 解析时构造

casey 选模式 1(path-based flat hash),因为:

1. **存储简单**:还是 HashMap<u64, DebugValue>,不变
2. **hash 一次**:guid 还是单 u64,所有之前的索引机制保留
3. **UI 端做层级**:渲染时 parse path,临时构造 tree

这是"延迟结构化"——数据扁平存储,需要结构时即时构造。优点:存储开销最小;缺点:UI 渲染时每次解析。

但 UI 渲染不是 hot path(每帧一次),解析几百个 path < 1ms,可接受。casey 的 trade-off 合理。

### 10.3 工业级实现:ImGui 的 namespace

Dear ImGui 的内部 debug 浏览器(implements 模式 2 嵌套树):

```cpp
struct ImGuiDebugTree {
    std::map<std::string, ImGuiDebugTree> children;
    void* value;
};
```

每次注册变量,递归 split path 找到正确节点。查询也递归走。

casey 选模式 1 而不是模式 2 的关键:**casey 的 debug 变量是 compile-time 注册的**(用 `debug_var!("game/player/health")` 宏),hash 在编译期算。模式 2 需要运行时递归插入,慢。

### 10.5 工程教训

casey 今天的设计给我们三条迁移经验:

1. **优先 flat 存储,nested 显示**。存储格式简单,显示复杂度由 UI 承担。
2. **path 分隔符选 `/` 而不是 `.`**。避免和 module / namespace 命名冲突。
3. **hash + path 分割 vs 嵌套 HashMap**。前者 O(1) hash + O(L) 显示;后者 O(L) 查询。casey 选前者因为查询频率高于显示。

如果未来 HH 的 debug UI 频率上升到"每帧渲染",casey 可能会换到嵌套 HashMap(模式 2)。但目前每秒 60 帧的显示频率,模式 1 完全够。
