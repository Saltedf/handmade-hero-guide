# Day 197 · 集成多个调试视图

> Day 196 的 immediate-mode UI 框架有了。今天 Casey 用它把之前的几个 debug 视图集成:profiler 曲线图、debug 变量 tree、entity inspector。一个 UI 里切换。

## 0 · 为什么要有这一天

让我们从一个真实的开发体验说起。

你跟 Day 196 把 immediate-mode UI 框架搭起来,然后开始用它做各种 debug 视图——Day 176 的 profiler 曲线图、Day 180 的 debug 变量 tree、Day 184 的 entity inspector。每个都是独立的"全屏覆盖"窗口。

问题:**它们没法同时显示**。你按 F1 调出 profiler,F2 调出变量,F3 调出 entity——三个互相覆盖,最后只能看一个。你想"profile 曲线和 entity inspector 并排看"——不行,系统不支持。

更糟的是,**键盘快捷键记不住**。F1-F12 一打,F5 是 reload game、F11 是 fullscreen、F2 是变量、F7 是 profiler……你抄在便利贴上贴在屏幕边,但还会按错。

工业级 IDE 的解决方案是 **multi-view + tab bar**——一个统一窗口,内部有 tabs。VS Code 的 sidebar 是 tab,VS 的 Solution Explorer + Properties + Output 是 tab,Unreal 的 Outliner / Details / Content Browser 是 dockable panel。开发者**所见即所得地切换 view**,不需要记键盘。

Casey 这天把 Day 196 的 immediate-mode 框架扩展,**实现 multi-view 架构**:

```
[profiler] [variables] [entity] [memory]
─────────────────────────────────────────
(active view content)
```

tab bar 切换不同 view,active view 全屏。每个 view 有自己 state(expanded tree、scroll position),切换不丢。

这件事的核心难点不在"画 tab bar"——画几个 button 容易。难点在**架构**:**怎么把"独立的几个 view"抽象成"可注册、可切换、state 隔离"的统一系统**。这要求你设计 trait + 泛型 + 状态管理,是 industrial software design 的训练。

完成这一天之后,你应该能:

- **用 trait object 设计 plugin-style 架构**:`Box<dyn DebugView>` 让 view 类型不固定
- **实现 immediate-mode UI 的 ID namespace 隔离**:多 view 共存时 ID 不冲突
- **设计 tab bar + view switcher**:horizontal button + active state
- **管理 view 的可见性和 state preservation**:hide/show 时 state 不丢
- **看懂 Dear ImGui / egui 的 Window / Tab API**:它们都遵循 Casey 这天的模式

## 1 · Casey 今天做了什么

Casey 这天是架构工作,不是新功能。让我把步骤拆开,你会看到每步对应一个工程决策。

**第一步,抽象 DebugView trait**。每个 view 有统一接口:`fn name() -> &str` + `fn draw(ui, game)`。这让 view 类型不固定——任何实现 DebugView 的类型都能注册。

**第二步,设计 DebugUi 容器**。一个 struct 持有 `Vec<Box<dyn DebugView>>` 和 `active_view: usize`。每帧调 `draw` 方法,先画 tab bar,再画 active view。

**第三步,把 Day 176 / 180 / 184 的 view 重构成 DebugView 实现**。每个独立 view 包成 struct,impl DebugView trait。这是**接口提取**——把分散代码统一到接口下。

**第四步,实现 ID namespace 隔离**。Immediate-mode UI 的 ID 全局唯一,两个 view 都有 "Save" button 会冲突。Casey 用 `push_id` / `pop_id` 给每个 view 一个 namespace 前缀。

**第五步,可选:动态注册**。Plugin 可以通过 `register(Box::new(MyView))` 加新 view。这让 debug UI 可扩展——开发者加新 view 不动主代码。

视频里 Casey 强调 immediate-mode 的一个优势:**state preservation 自动发生**。retained-mode UI 要手动管理每个 widget 的 state(展开 / 折叠 / 缓冲),immediate-mode 通过 widget ID 自动 hash 存 state。切走 view 再回来,所有 state 都还在。

## 2 · 心智模型

### 2.1 类比:浏览器 tab

我打个比方。浏览器有多个 tab(网页),同时只看一个。tab bar 切换。每个 tab 是独立的网页——有自己 URL、自己 history、自己 DOM。切换 tab 不丢失任何 tab 的 state——你切走 Gmail 再切回,邮件草稿还在。

immediate-mode UI 的 tab 完全一样:**每帧根据 active tab,render 不同内容**。但每个 tab 的 state 在内部 storage 里持久——切换不丢失。

类比的关键洞察:**multi-view 架构的核心是"state isolation"**。每个 view 有独立 state,互不干扰。这在 retained-mode UI 要手动管(每个 panel 自己存 state),immediate-mode 自动管(通过 widget ID hash)。

更深一层:**浏览器 tab 之间还能通信**(localStorage、postMessage),UI view 之间也能共享 state(通过 GameContext 传递)。Casey 的设计是 GameContext 全局可访问,每个 view 从中取需要的数据。

### 2.2 多 view 集成的核心问题

集成多 view 有三个工程难点,让我逐一深入。

**问题 1:view 注册**。每个 view 怎么"加入" UI 系统?有两种方案:

**Static enum**(静态枚举):

```rust
#[derive(PartialEq, Copy, Clone)]
enum DebugView { Profiler, Variables, Entity, Memory }

struct DebugWindows {
    active: DebugView,
}
```

简单,编译时确定所有 view。缺点:**加新 view 要改 enum + match**,主代码改。Casey 早期版本用这个。

**Dynamic trait object**(动态 trait object):

```rust
trait DebugView {
    fn name(&self) -> &str;
    fn draw(&mut self, ui: &mut Ui, game: &mut Game);
}

struct DebugUi {
    views: Vec<Box<dyn DebugView>>,
    active_view: usize,
}
```

灵活,任何实现 DebugView 的类型都能注册。`Box<dyn DebugView>` 是 trait object——运行时多态。缺点:**vtable overhead**(每次 draw 通过 vtable 调用,比直接调用慢几纳秒)。但在 UI 代码这开销可忽略。

Casey 这天选 dynamic trait object,因为支持 plugin 扩展(后续 Day 200+ 加)。

**问题 2:state 隔离**。每个 view 有自己的 state(expanded tree、scroll position)。两个 view 的 widget ID 不能冲突——否则 state 串。

```rust
// 错误:两个 view 都有 "Save" button,widget ID = hash("Save")
// 两个 view 的 Save button state(按没按)互相干扰
fn draw_profiler_view(ui: &mut Ui) {
    if ui.button("Save") { /* ... */ }  // ID = hash("Save")
}
fn draw_variables_view(ui: &mut Ui) {
    if ui.button("Save") { /* ... */ }  // ID = hash("Save")  ← 冲突!
}
```

解决:**ID namespace**。每个 view 进入时 push 自己的名字作为 ID 前缀:

```rust
fn draw(&mut self, ui: &mut Ui, game: &mut Game) {
    ui.push_id(self.name());  // 进入 "profiler" namespace
    // 这里所有 ID 自动加 "profiler/" 前缀
    if ui.button("Save") { /* ... */ }  // ID = hash("profiler/Save")
    ui.pop_id();
}
```

`push_id` / `pop_id` 是 Dear ImGui 风格的 namespace stack。Casey 的 Day 197 也用这种模式。**所有 immediate-mode 框架都有这个机制**——egui 的 `ui.push_id()`、Dear ImGui 的 `ImGui::PushID()`。

**问题 3:生命周期**。View 可动态加载 / 卸载(plugin 风格)。例如 debug_extras.so 提供一个 "Memory Profiler" view,加载 .so 时注册,卸载时反注册。这要求 trait object 而非 enum——enum 编译时固定,无法动态加。

```rust
debug_ui.register(Box::new(ProfilerView::new()));
debug_ui.register(Box::new(VariablesView::new()));
debug_ui.register(Box::new(EntityInspectorView::new()));

// Plugin 加载
if let Some(plugin) = load_plugin("debug_extras.so") {
    plugin.register_views(&mut debug_ui);
}
```

dynamic registration 让 debug UI 可扩展——开发者加新 view 不动主代码。这是工业级 plugin 架构的基础。

### 2.3 enum 化 views:静态方案详解

让我把 static enum 方案详细写出来,你会看到 immediate-mode 的简洁。

```rust
#[derive(PartialEq, Copy, Clone, Debug)]
enum DebugView { Profiler, Variables, Entity, Memory }

struct DebugWindows {
    active: DebugView,
}

impl DebugWindows {
    fn draw(&mut self, ui: &mut Ui, game: &mut Game) {
        // tab bar:horizontal 排列 buttons
        ui.horizontal(|ui| {
            for view in [DebugView::Profiler, DebugView::Variables,
                         DebugView::Entity, DebugView::Memory] {
                let is_active = self.active == view;
                let label = format!("{} {}", if is_active { ">" } else { " " }, view);
                if ui.button(&label) {
                    self.active = view;
                }
            }
        });

        // active view 内容
        match self.active {
            DebugView::Profiler => draw_profiler_view(ui, game),
            DebugView::Variables => draw_variables_view(ui, game),
            DebugView::Entity => draw_entity_view(ui, game),
            DebugView::Memory => draw_memory_view(ui, game),
        }
    }
}
```

active view 的 render 函数被调,其他 view 不调——immediate-mode 自动 hide。注意"不调"是关键——节省 CPU。retained-mode 即便 view 隐藏,可能仍在背后 update(取决于实现),immediate-mode 完全跳过。

### 2.4 immediate-mode 的 closure pattern:布局抽象

`ui.horizontal(|ui| { ... })` 是 immediate-mode 的常见模式:**闭包内重新布局**。这是布局抽象的核心。

```rust
impl Ui {
    pub fn horizontal<F: FnOnce(&mut Ui)>(&mut self, f: F) {
        let saved_x = self.cursor_x;
        let saved_layout = self.layout;
        self.layout = Layout::Horizontal;
        f(self);  // 用户在闭包内画 widgets,自动 horizontal 布局
        self.layout = saved_layout;
        self.cursor_x = saved_x;
        // cursor_y 推进最大高度
    }

    pub fn vertical<F: FnOnce(&mut Ui)>(&mut self, f: F) {
        // 同理,vertical 布局
    }
}
```

`FnOnce` 是 Rust 的 closure trait——"调用一次"。`FnOnce(&mut Ui)` 表示闭包接受 `&mut Ui` 参数,返回 `()`。Closure 内可以画任意 widgets,布局自动 horizontal。

这种"layout scope"模式让 immediate-mode UI 嵌套布局变得简单:

```rust
ui.horizontal(|ui| {
    ui.label("Name:");
    ui.text_edit(&mut name);
});
ui.vertical(|ui| {
    for item in &items {
        ui.label(item);
    }
});
```

egui / Dear ImGui / iced 都用类似 closure API。Casey 的手写版本接近这个。

### 2.5 window 容器:可拖拽、可缩放

view 渲染在一个可拖拽的 window 里。让我把 window 抽象拆开。

```rust
pub struct Window {
    pub title: String,
    pub pos: (f32, f32),
    pub size: (f32, f32),
    pub open: bool,
    pub dragging: bool,
    pub drag_offset: (f32, f32),
}

impl Window {
    pub fn show(&mut self, ui: &mut Ui, content: impl FnOnce(&mut Ui)) {
        if !self.open { return; }

        // header(可拖拽,20px 高)
        let header_h = 20.0;
        draw_rect(self.pos.0, self.pos.1, self.size.0, header_h, 0xFF222222);
        draw_text(&self.title, self.pos.0 + 4, self.pos.1 + 4);

        // close X 按钮
        let close_x = self.pos.0 + self.size.0 - 20.0;
        if ui.button_at("X", close_x, self.pos.1, 16.0, 16.0) {
            self.open = false;
        }

        // 内容区域
        let content_y = self.pos.1 + header_h;
        ui.cursor_x = self.pos.0 + 4;
        ui.cursor_y = content_y + 4;
        content(ui);

        // 处理拖拽(见下节)
        self.handle_drag(ui);
    }

    fn handle_drag(&mut self, ui: &mut Ui) {
        let header_rect = (self.pos.0, self.pos.1, self.size.0, 20.0);
        if ui.mouse.left_pressed && in_rect(ui.mouse, header_rect) {
            self.dragging = true;
            self.drag_offset = (ui.mouse.x - self.pos.0, ui.mouse.y - self.pos.1);
        }
        if !ui.mouse.left_pressed {
            self.dragging = false;
        }
        if self.dragging {
            self.pos.0 = ui.mouse.x - self.drag_offset.0;
            self.pos.1 = ui.mouse.y - self.drag_offset.1;
        }
    }
}
```

window 的核心:**header 区域作为 drag handle**。鼠标在 header 按下时进入 drag 状态,记录 offset。鼠标拖动时,window 跟随鼠标。鼠标抬起时退出 drag 状态。

`drag_offset` 是必要的——否则 window 跳到鼠标位置(左上角贴鼠标),不自然。drag_offset 让 window "贴住鼠标按下的相对位置"——按下时鼠标在 header 中央,拖动时鼠标仍在 header 中央。

### 2.6 view 的依赖:context 模式

某些 view 依赖其他系统:

- ProfilerView 依赖 ProfilerState
- VariablesView 依赖 VariablesRegistry
- EntityInspectorView 依赖 ECS World

通过 trait + generic 传递依赖:

```rust
trait DebugView<Context> {
    fn draw(&mut self, ui: &mut Ui, ctx: &mut Context);
}

struct GameContext {
    profiler: ProfilerState,
    variables: VariablesRegistry,
    world: World,
}

impl DebugView<GameContext> for ProfilerView {
    fn draw(&mut self, ui: &mut Ui, ctx: &mut GameContext) {
        // 用 ctx.profiler
        for sample in &ctx.profiler.samples {
            ui.label(&format!("{}: {}us", sample.name, sample.duration_us));
        }
    }
}
```

泛型 + trait,编译期类型安全。但 trade-off:**trait object**(`Box<dyn DebugView<C>>`)需要 monomorphization,每个 Context 类型生成一份代码。如果只有一种 Context(GameContext),没问题。

工业实践:egui 用 `&mut Context` 直接传 egui 内部 context,用户 widget 函数接受 `&mut Ui` 参数。这是 closure 风格,而非 trait object。Casey 的手写版可以选任意一种。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏 debug UI 的"window 化"是工业级标配。让我对比几个引擎的实现:

**Unreal Engine 5** 用 **Slate** framework,完全 retained-mode。每个 editor panel 是 `SDockTab` 实例,通过 `FTabManager` 管理布局。Panel 可以 detach(独立浮动窗口)、dock(贴到主窗口某边)、tabify(多个 panel 共享一个区域,tab 切换)。Slate 是 retained——widget tree 存内存,property 改变触发 invalidate + redraw。优势是流畅(60 FPS UI)、复杂布局;劣势是代码冗长(声明一个 button 要 5+ 行 Slate macro)。

**Unity Editor** 用 **UI Toolkit / IMGUI** 双轨。UI Toolkit 是新系统(retained-mode, UXML + USS 类似 HTML/CSS),IMGUI 是老系统(immediate-mode,C# `OnGUI` 函数)。Unity Editor 主要 panel(Scene / Game / Hierarchy / Inspector / Console)是 IMGUI 实现——onGUI 每帧重画。新版本慢慢迁到 UI Toolkit。

**Godot Editor** 用自己 **Control** 系统(retained-mode,节点树)。每个 panel 是 Control 节点,布局用 Container 节点自动算。

**Casey HH** 用手写 immediate-mode,极简但够用。所有 view 用 tabs 切换,无 docking。够用,但限制大——不能同时看两个 view。

immediate-mode windows 的特点:**每帧重新算位置**(允许拖拽 / 缩放),无 widget tree。代码量少,适合小项目;大项目(Unreal / Unity Editor)用 retained-mode,因为 widget 数量多,immediate-mode CPU 开销大。

### 3.2 · Rust 生态视角

egui 的 `Window` API 是 immediate-mode 工业实现。让我详细看。

```rust
egui::Window::new("Profiler")
    .open(&mut self.window_open)
    .pos([100.0, 100.0])
    .resizable(true)
    .show(ctx, |ui| {
        ui.label("frame time");
        // 闭包内画任意 widget
        for sample in &self.samples {
            ui.label(&format!("{}: {}us", sample.name, sample.duration_us));
        }
    });
```

closure 内的 widget 自动属于这个 window。`open` 控制 window 显隐,`.show()` 触发 render。egui 内部管 state(window 位置、大小、scroll)通过 widget ID hash。

egui 的 multi-view 实现:

```rust
struct MyApp {
    windows: Windows,
}

#[derive(Default)]
struct Windows {
    profiler_open: bool,
    variables_open: bool,
    entity_open: bool,
}

impl MyApp {
    fn update(&mut self, ctx: &egui::Context, _: &mut eframe::Frame) {
        egui::TopBottomPanel::top("menu").show(ctx, |ui| {
            ui.menu_button("Views", |ui| {
                ui.checkbox(&mut self.windows.profiler_open, "Profiler");
                ui.checkbox(&mut self.windows.variables_open, "Variables");
                ui.checkbox(&mut self.windows.entity_open, "Entity");
            });
        });

        if self.windows.profiler_open {
            egui::Window::new("Profiler").show(ctx, |ui| {
                ui.label("Profiler content");
            });
        }
        // ... variables / entity
    }
}
```

每个 window 一个 bool 控制 open/close,顶层 menu 切换。这是 industrial immediate-mode 的标准模式——`bool` 控制可见性,Window struct 自动管 position / size / scroll state。

**iced** 是 Elm-inspired 的 Rust UI framework。每个 view 是 `Element<Message>`,通过 update 函数处理消息。Retained-mode + functional style。代码更"函数式",但学习曲线更陡。

### 3.3 · 性能考量

每帧重画所有 view(包括隐藏的)是浪费。Immediate-mode 的优化:**隐藏 view 跳过 draw**。

```rust
match self.active {
    DebugView::Profiler => draw_profiler_view(...),
    _ => {}  // 隐藏的不画
}
```

但 immediate-mode 框架的 `Window::show` 通常每帧都跑(避免数据 stale),只是 `visible=false` 时跳过 render。这是 trade-off——跳过 render 节省 80% 时间,但仍跑一些 book-keeping(更新 widget ID hash 等)。

Casey 早期版本不优化,后面 Day 200+ 加。性能数据:8 个 debug view,每个 100 widget,每 widget 1μs CPU 时间。全画 = 800μs/帧 = 5% 帧时间(16ms)。隐藏的不画 = 100μs/帧 = 0.6% 帧时间。差异显著。

immediate-mode 的另一个性能问题:**rebuild widget list**。每帧重新构造 widget tree,产生 allocation。Industrial 实现用 arena allocator 或 frame allocator,避免 heap alloc。egui 内部有 `epaint` 的 frame allocator。

## 5 · 对照与变奏

**多 view 集成的工业实现**:

- **Unreal Editor**:Editor UI 包含多个 panel(Outliner / Details / Viewport / Content Browser),retained-mode,SlATE framework
- **Unity Editor**:类似 Unity,UI Toolkit / IMGUI

这些系统的共同设计:
1. **panel / view 抽象**:统一的容器接口
2. **drag-and-drop 布局**:用户可重排
3. **plugin 扩展**:第三方加新 view

### Visual Studio Code 的 view 注册

VS Code 用 TypeScript API 注册 view:

```typescript
vscode.window.registerWebviewViewProvider('myExtension.view', {
    resolveWebviewView(webviewView) {
        webviewView.webview.html = '<h1>Hello</h1>';
    }
});
```

VS Code 主进程是 retained(Electron),webview 内部是 web(HTML/CSS)。插件通过 API 注入 view,VS Code 管 layout。

### IDE 的 docking system

IDE 的核心 UI 是 **docking**(面板可拖到任意边/标签页)。Qt 有 `QDockWidget`,WPF 有 `DockingManager`,VS Code 自己实现。

Casey 的 debug UI 不实现 docking(简化),所有 view 用 tabs 切换。够用,但限制大——不能同时看两个 view。

### Lv1 · 概念辨析

**题**:multi-view UI 中,active view 切换时,其他 view 的状态(比如变量编辑缓冲)要保留吗?

**参考解答**:
- immediate-mode UI 用 ID hash 存状态
- 只要 widget ID 一致(同 label),状态自动保留
- 切回 view 时,buffer 仍是切走时的值
- 这是 immediate-mode 的设计优势(retained mode 也保留,但更繁琐)

### Lv2 · 动手实践

**题**:写一个简单 tab bar:3 个 tab(Home/Settings/About),active 切换内容。

**参考解答**:

```rust
#[derive(PartialEq, Copy, Clone, Debug)]
enum Tab { Home, Settings, About }

struct App { active: Tab }

impl App {
    fn render(&mut self) {
        // tab bar
        for tab in [Tab::Home, Tab::Settings, Tab::About] {
            let marker = if self.active == tab { "*" } else { " " };
            print!("[{}{:?}] ", marker, tab);
        }
        println!();
        println!("---");

        // content
        match self.active {
            Tab::Home => println!("welcome home"),
            Tab::Settings => println!("settings: ..."),
            Tab::About => println!("about: v1.0"),
        }
    }
}

fn main() {
    let mut app = App { active: Tab::Home };
    // 模拟切换
    app.render();
    app.active = Tab::Settings;
    app.render();
    app.active = Tab::About;
    app.render();
}
```
