## 0 · 为什么要有这一天

你写游戏到现在,大概已经习惯了一种调试节奏:发现帧率掉了 → 在 `update` 里塞一行 `println!("frame = {}", frame_count)` → 重新编译 → 跑 → 看输出 → 再塞一行 `println!("player = {:?}", player)` → 再编译 → 再跑。**每次提问都要付一次"编译 + 重启"的代价**。

这套做法在 Phase 1-3 还能忍(代码量小、重启快),但到了 Phase 4 之后:

- 游戏代码热重载后状态丢失,你要重新走 5 分钟才回到出问题的场景
- 多线程程序里 `println` 会改变时序,加一行 print bug 就消失了(Heisenbug)
- 你想知道的不是"当前帧"而是"过去 60 帧的趋势",单次 print 给不出来
- 不同函数的耗时对比要靠你手动加 N 个 print,然后手算差值

工业级游戏引擎都有自己的答案:**内置 profiler + debug UI**。Unreal 用 Unreal Insights,Unity 用 Profiler,Casey 要亲手做一个。这不是炫技——**这是大型项目能继续推进的前提**。代码量过了 5 万行之后,没有 profiler 你根本不知道哪个函数在烧 CPU。

这一集 Casey 不写大代码,他要解决三个问题:

1. **目标定义**:我们要造的"debug 系统"具体是什么?它要解决哪些问题?
2. **架构原则**:profiler 代码不应该污染游戏代码(否则每次发版要手动删 print)。怎么做到?
3. **路径规划**:60 集怎么分?哪些先做哪些后做?

心理锚点:看完这集,你应该能用 30 秒回答"profiler 和 debug UI 的区别是什么",能用 1 分钟讲清"为什么 profiler 要做成零侵入的(自动包裹函数,而不是手动加 print)"。

## 2 · 心智模型

### 类比:debug 系统是飞机的"黑匣子 + 仪表盘"

飞行员开飞机,不能等飞机摔了再去查引擎。飞机上同时装了两个东西:

- **黑匣子**(flight data recorder):默默记录所有传感器读数,出事时拿出来回放
- **仪表盘**(cockpit instruments):飞行员抬头就能看,实时反馈引擎转速、油量、高度

游戏里的 debug 系统就是这两样:

- **profiler**(黑匣子):每函数每次调用记一次耗时,存到 ring buffer,出问题时回放
- **debug UI**(仪表盘):开发模式下叠加在游戏画面上,实时显示曲线图、字段值、树视图

这两个角色决定了不同的设计:**profiler 要快**(影响游戏帧率),**UI 要灵活**(开发模式才开)。

### 2.1 profiler 的核心:cycle 计数

要算"一个函数多快",最朴素的想法是用时间戳:

```rust
let start = std::time::Instant::now();
my_function();
let elapsed = start.elapsed();
println!("took {:?}", elapsed);
```

这能用,但有三个问题:

1. **粒度不够**:`Instant::now()` 在 Linux 上靠 `clock_gettime(CLOCK_MONOTONIC)`,精度 1 纳秒。但现代 CPU 一条指令才 0.3 纳秒,**函数耗时几百皮秒,Instant 测不准**
2. **干扰太大**:每次调 `Instant::now()` 自己就要 50-100 纳秒(vsyscall + 内核读时钟)。测 1 微秒的函数时,测量误差占 10%
3. **跨核不稳定**:`CLOCK_MONOTONIC` 在不同 CPU 核上读到的值会跳(内核要补偿)

x86_64 给了一个专门解决这件事的指令:`rdtsc`(Read Time-Stamp Counter)。它读 CPU 内部一个 64 位计数器,**每个时钟周期 +1**,从 CPU 通电开始累加。**`rdtsc` 本身只要 20-30 个 cycle(约 10 纳秒),不影响被测代码**。

```rust
#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    unsafe {
        let lo: u32;
        let hi: u32;
        core::arch::asm!(
            "rdtsc",
            out("eax") lo,
            out("edx") hi,
            options(nomem, nostack),
        );
        ((hi as u64) << 32) | (lo as u64)
    }
}
```

**Rust 注释**:
- `core::arch::asm!` — 内联汇编,Rust 1.45+ 的稳定语法
- `out("eax") lo` — 把 eax 寄存器的值读到变量 `lo`
- `rdtsc` 把 64 位计数器的高 32 位放 edx,低 32 位放 eax
- `options(nomem, nostack)` — 告诉编译器这段汇编不读内存、不用栈,可以激进优化

`rdtsc` 返回的不是秒,是**自 CPU 通电以来的 cycle 数**。要换算成秒,需要知道 CPU 频率:

```bash
# Linux 上读 CPU 频率
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_max_freq
# 输出: 4500000  (单位 kHz,即 4.5 GHz)
```

但 CPU 频率会动态变(睿频 / 节能),所以**直接把 cycle 转成秒是不准的**。Casey 的做法:**就用 cycle 数本身**,不转秒。看着 10000 cycle 还是 12000 cycle 你就知道这个函数快还是慢,具体多少秒交给生产环境的真 prof(perf / vtune)去做。

### 2.2 零侵入:用 RAII guard 取代宏

Casey 在 C 里用宏 `TIMED_BLOCK(name)`,展开成一个 struct + 自动 ctor/dtor。Rust 不用宏,用 RAII(资源获取即初始化)模式更自然:

```rust
pub struct ProfileSpan {
    name: &'static str,
    start: u64,
}

impl ProfileSpan {
    pub fn enter(name: &'static str) -> Self {
        Self { name, start: rdtsc() }
    }
}

impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        PROFILE_STATE.with(|s| s.borrow_mut().record(self.name, elapsed));
    }
}

// 用法
fn update_player() {
    let _span = ProfileSpan::enter("update_player");
    // ... 函数体
    // _span 离开作用域时自动 drop,自动记录耗时
}
```

**Rust 注释**:
- `impl Drop for ProfileSpan` — 当 ProfileSpan 离开作用域,Rust 自动调 `drop`。这就是 RAII,等价于 C++ 的析构函数,但比 C++ 更严格(确定性销毁,不会有 GC 延迟)
- `_span` 前面的下划线告诉编译器"我知道这个变量没被读,别 warn 我"。但**变量仍然存在,作用域结束才 drop**——这是新手常踩的坑:写成 `_ = ProfileSpan::enter(...)` 会立刻 drop,失去计时功能
- `PROFILE_STATE.with(...)` — thread-local 状态,Day 178 详细讲。现在理解为"每个线程一份独立的计数器"

这个设计的精妙之处:**游戏代码里只多了一行 `let _span = ...`,release build 时把 `enter` 改成 `pub fn enter(_: &'static str) {}` 编译成空,零开销**。

### 2.3 时间维度:ring buffer

光记当前帧的耗时没用——你要看趋势。Casey 用 ring buffer(环形缓冲)存最近 N 帧:

```
ring buffer (容量 N=300):
[frame_0][frame_1][frame_2]...[frame_299]
   ↑ head 指针,新数据写这里
写满后 wrap around,覆盖最老的
```

为什么不用 Vec 一直 append?因为游戏跑 1 小时就是 21.6 万帧,内存爆炸。Ring buffer 永远只占 N 帧的内存,**永远有最近 N 帧的数据**。

```rust
pub struct RingBuffer<T, const N: usize> {
    data: [T; N],   // 用 const generics,大小编译时确定
    head: usize,    // 下一个写入位置
    len: usize,     // 已写入多少(< N 时)
}

impl<T: Default + Copy, const N: usize> RingBuffer<T, N> {
    pub fn push(&mut self, v: T) {
        self.data[self.head] = v;
        self.head = (self.head + 1) % N;
        if self.len < N { self.len += 1; }
    }
    pub fn iter_recent(&self) -> impl Iterator<Item = &T> {
        let start = if self.len < N { 0 } else { self.head };
        let order = (0..self.len).map(move |i| (start + i) % N);
        order.map(move |i| &self.data[i])
    }
}
```

**Rust 注释**:
- `const N: usize` — Rust 1.51+ 的 const generics,数组大小编译时定。Stack 分配,无 heap,无 GC
- `% N` — 取模。`%` 在 Rust 里对无符号整数是 Euclid 模,不会负
- `impl Iterator<Item = &T>` — 返回一个迭代器,不分配。**`move` 闭包捕获 `start` by value**(因为 `start: Copy`)

### 2.4 immediate-mode UI 的预告

Casey 在 Day 196+ 才正式做 immediate-mode UI,但 Day 176 已经埋下设计原则:**UI 不持久化**。每帧重新声明整个 UI:

```rust
fn draw_debug_ui(ctx: &mut UiContext) {
    ctx.label("Frame time");
    ctx.plot_line("frame_times", &ring_buffer);
    if ctx.button("Reset") { /* reset */ }
}
```

每帧调用 `label` / `plot_line` / `button`。**没有持久的 Widget 对象**,UI 完全反映当前帧的代码状态。改了游戏代码 UI 自动变。

对比 retained-mode UI(Qt / WPF):你创建一个 `Button` 对象,挂在 `Window` 上,设置 callback。对象持久存在,改了要手动刷新。

**为什么 immediate-mode 在游戏里更好?** 因为游戏状态本身就是"每帧重算",UI 自动同步省心。Dear ImGui、egui 都是 immediate-mode。

### 3.1 · 🎮 游戏编程视角

商业游戏引擎的 debug 系统各有特色:

Casey 的设计哲学:**自己造,因为只有自己知道要测什么**。第三方 profiler(puffin / superluminal)更通用,但内置的能和游戏逻辑深度集成——比如 Day 207 的 introspection,可以点怪物查字段。

游戏开发圈普遍认同:**debug UI 不能拖慢游戏**。Casey 的目标:< 1% 帧时间花在 profiler 上。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上的时钟源对比:

| 时钟源 | 精度 | 开销 | 适用 |
|---|---|---|---|
| `time()` | 1 秒 | 极低 | 不用了 |
| `gettimeofday()` | 1 微秒 | 20-50 ns | 老代码 |
| `clock_gettime(CLOCK_MONOTONIC)` | 1 纳秒 | 20-30 ns | 通用 |
| `clock_gettime(CLOCK_MONOTONIC_RAW)` | 1 纳秒 | 10 ns | 不受 NTP 调整 |
| `rdtsc`(x86 指令) | < 1 纳秒 | 10 ns | cycle 级 |
| `rdpmc`(读 PMC 计数器) | < 1 纳秒 | 10 ns | 自定义事件 |

**关键认识**:`rdtsc` 不进内核,用户态直接执行,所以快。但**它不是真正的"墙上时间"**——CPU 频率动态调整时 rdtsc 不一定按墙上时间走(虽然 Intel 现代 CPU 上 `invariant TSC` 解决了这点)。Casey 不在乎墙时间,只在乎相对快慢,所以 rdtsc 够。

Linux 上验证你的 CPU 是否支持 invariant TSC:

```bash
grep -o constant_tsc /proc/cpuinfo | head -1
grep -o nonstop_tsc /proc/cpuinfo | head -1
# 输出: constant_tsc
# 输出: nonstop_tsc
# 两个都有 → 支持 invariant TSC,可以放心用 rdtsc
```

### 3.3 · 🦀 Rust 生态视角

Rust 生态里的 profiler:

| crate | 风格 | 是否需要宏 | Casey 对应 |
|---|---|---|---|
| `puffin` | RAII scope guard | 否,但建议用宏 | Day 177 的设计 |
| `superluminal`(闭源) | C API + macro | 是 | 商业版 |
| `tracy` | 宏 + frame 标记 | 是 | 类似 |
| `coz` | causal profiling | 是,实验性 | 不一样 |

`puffin` 是最接近 Casey 风格的,代码读起来:

```rust
let _p = puffin::profile_scope!("update_player");
// ... 函数体
```

`profile_scope!` 宏展开成 RAII guard,和 Casey 的 `ProfileSpan::enter` 一模一样。看 puffin 源码 `src/lib.rs` 可以学到工程级实现。

**Rust 特性**:
- `Drop` trait — Casey 在 C 里要写 `__attribute__((cleanup))` 或手动 ctor/dtor,Rust 用 trait 一行搞定
- `#[cfg(feature = "profiling")]` — Cargo feature gate,release build 关闭 profiling 时编译为 no-op
- `thread_local!` — Day 178 详细讲

```rust
// feature gate 的写法
#[cfg(feature = "profiling")]
pub fn enter(name: &'static str) -> ProfileSpan { ProfileSpan::new(name) }

#[cfg(not(feature = "profiling"))]
pub fn enter(_: &'static str) {}  // 编译为空,完全零开销
```

## 5 · 对照与变奏

**不同语言的 RAII 实现**:

| 语言 | 机制 | 何时触发 |
|---|---|---|
| Rust | `Drop` trait | 离开作用域(确定性) |
| C++ | 析构函数 | 离开作用域(确定性) |
| C# | `IDisposable` + `using` | using 块结束 |
| Java | `try-with-resources` | try 块结束 |
| Python | `with` 上下文管理器 | with 块结束 |
| Go | `defer` | 函数结束(不是块结束) |

只有 Rust 和 C++ 是真正"确定性 + 块级",所以最适合 profiler guard。

**CPU 频率动态调整的影响**:

现代 CPU 有睿频(超频到 5GHz)和节能(降到 800MHz)。如果你的 rdtsc 测出 1000 cycle,在 5GHz 时是 200ns,在 800MHz 时是 1.25 微秒——同一个 cycle 数对应不同时间。

Casey 不在乎这个差异,因为他只关心相对快慢。但**如果你要把 cycle 换算成秒,要么固定 CPU 频率(`cpupower frequency-set -g performance`),要么用 invariant TSC**。

```bash
# 锁定 CPU 频率到最高(用于 profiling 一致性)
sudo cpupower frequency-set -g performance
# 还原
sudo cpupower frequency-set -g powersave
```

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:profiler 和 debug UI 是两个东西,但都叫"debug 系统"。它们各自解决什么问题?为什么不能合成一个?

**参考解答**:
- **profiler**(profiler 后端)解决"**测什么**"的问题:每函数每次调用 cycle 数多少,谁最慢。它是**数据采集器**,要求极低开销(否则影响游戏运行),通常不需要可视化,数据可被外部工具读
- **debug UI**(profiler 前端)解决"**怎么展示**"的问题:把采集的数据画成图表 / 树 / 表。它跑在游戏画面上,只在 dev mode 开,允许较高开销(因为不影响 release)
- **不能合成一个**:因为 profiler 后端要 release 也能开(线上 trace 用),前端只在 dev mode 用;前端跑死不影响后端数据采集;前端可以独立替换(egui / Dear ImGui / 自绘)

记住:**采集和展示解耦**——这是观察系统的通用设计原则。

### Lv2 · 动手实践

**题**:写一个最小可跑的 profiler 原型,有这些要求:
- 用 `rdtsc()` 读 cycle 计数器
- `ProfileSpan::enter(name)` 创建 guard,Drop 时打印耗时
- `main` 里跑一个 100 万次循环(里面随便算个乘法),用 `ProfileSpan` 包住
- 运行后看到 `update: 1234567 cycles` 这样的输出

完成标准:`cargo run` 打印 cycle 数,且数字大于 1000(说明 rdtsc 工作)。

**参考解答**:

```rust
// src/main.rs
#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    unsafe {
        let lo: u32;
        let hi: u32;
        core::arch::asm!(
            "rdtsc",
            out("eax") lo,
            out("edx") hi,
            options(nomem, nostack),
        );
        ((hi as u64) << 32) | (lo as u64)
    }
}

#[cfg(not(target_arch = "x86_64"))]
fn rdtsc() -> u64 {
    use std::time::Instant;
    Instant::now().elapsed().as_nanos() as u64  // 非 x86 用纳秒代替
}

pub struct ProfileSpan {
    name: &'static str,
    start: u64,
}

impl ProfileSpan {
    pub fn enter(name: &'static str) -> Self {
        Self { name, start: rdtsc() }
    }
}

impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        println!("{}: {} cycles", self.name, elapsed);
    }
}

fn heavy_compute() -> u64 {
    let _span = ProfileSpan::enter("heavy_compute");
    let mut sum: u64 = 0;
    for i in 0u64..1_000_000 {
        sum = sum.wrapping_mul(i + 1).wrapping_add(i);
    }
    sum
}

fn main() {
    let _span = ProfileSpan::enter("main");
    let result = heavy_compute();
    std::hint::black_box(result);  // 防止编译器优化掉整个循环
}
```

**每行解释**:
- `core::arch::asm!` — Rust 1.45+ 稳定的内联汇编。`out("eax") lo` 把 eax 寄存器写到 `lo`
- `options(nomem, nostack)` — 这段汇编不读写内存,不用栈,允许编译器重排
- `wrapping_mul` / `wrapping_add` — Rust 默认 debug build 检查整数溢出,这里用 wrapping(环绕)版本明确说"我要 C 的溢出语义"
- `std::hint::black_box` — 防止优化器发现 `result` 没用就把整个循环删了
- 函数末尾 `_span` 自动 drop,先打印 `heavy_compute` 的耗时,然后 `main` 的 `_span` drop 打印 main 总耗时

运行输出类似:

```
heavy_compute: 823451 cycles
main: 823612 cycles
```

main 略大于 heavy_compute,差值就是创建 `_span` 和 `black_box` 的开销(约 100 cycle)。

### Lv3 · 迁移设计

**题**:profiler guard 在异步代码(`async fn`)里不能用——因为 `await` 跨越 await point 时 `Drop` 行为复杂。设计一个适用于 async 的 profiler API,需要哪些额外信息?**提示**:思考"一个 future 被暂停又恢复"时,如何把"实际执行时间"和"挂起时间"分开。

**提示**:
- Rust 的 Future 在 `poll` 之间会被 Drop / 重新创建(Pin 之前的 unsafe 模型)
- 不能依赖 RAII Drop,因为 future 可能在 await 时 yield,然后调度器才重新 poll 它
- 参照 `tracing` 的 `Span::enter()` 是怎么做的——它有 `Instrument` trait 给 future 包装

## 8 · Rust / Arch 落地代码

完整可跑项目(基于 §7 Lv2 扩展,加 feature gate):

```rust
// Cargo.toml
// [package]
// name = "mini-profiler"
// version = "0.1.0"
// edition = "2021"
//
// [features]
// default = ["profiling"]
// profiling = []

// src/main.rs
use std::hint::black_box;

#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    unsafe {
        let lo: u32;
        let hi: u32;
        core::arch::asm!(
            "rdtsc",
            out("eax") lo,
            out("edx") hi,
            options(nomem, nostack),
        );
        ((hi as u64) << 32) | (lo as u64)
    }
}

#[cfg(not(target_arch = "x86_64"))]
fn rdtsc() -> u64 {
    use std::time::Instant;
    Instant::now().duration_since(Instant::now()).as_nanos().max(0) as u64
}

#[cfg(feature = "profiling")]
pub struct ProfileSpan { name: &'static str, start: u64 }

#[cfg(feature = "profiling")]
impl ProfileSpan {
    pub fn enter(name: &'static str) -> Self {
        Self { name, start: rdtsc() }
    }
}

#[cfg(feature = "profiling")]
impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        eprintln!("[prof] {}: {} cycles", self.name, elapsed);
    }
}

#[cfg(not(feature = "profiling"))]
pub struct ProfileSpan;

#[cfg(not(feature = "profiling"))]
impl ProfileSpan {
    pub fn enter(_name: &'static str) -> Self { Self }
}

fn busy(n: u64) -> u64 {
    let _s = ProfileSpan::enter("busy");
    let mut x = 0u64;
    for i in 0..n { x = x.wrapping_add(i.wrapping_mul(7)); }
    x
}

fn main() {
    let _s = ProfileSpan::enter("main");
    let r = busy(2_000_000);
    black_box(r);
}
```

**Troubleshooting**:

- `error: inline assembly` — Rust 1.45 以下不支持 `asm!`,升级到 stable
- `error: use of unstable library feature` — `core::arch::asm!` 在 1.59 才稳定,老版本用 `core::arch::x86_64::_rdtsc()` unsafe intrinsic
- 不同次跑 cycle 数差异很大 — CPU 频率动态变,跑前 `sudo cpupower frequency-set -g performance` 锁频
