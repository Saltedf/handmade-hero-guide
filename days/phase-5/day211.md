# Day 211 · 从调试代码移除记录与翻译单元

> 调试系统在前 35 集里堆出了 event 流、record struct、translation unit 边界(`debug.cpp` 单独编译)。今天 Casey 反过来做减法:**删掉 record 抽象、消除 translation unit 边界**,让调试代码变成扁平的一层。这是工程"先增后减"的典型样本。

## 0 · 为什么要有这一天

你已经跟着 Casey 走完了 debug 系统最复杂的 35 集。`DebugEvent` 里塞了 record 字段,编译时把 `debug.cpp` 和 `handmade.cpp` 强行分成两个 translation unit(两个 `.cpp` 文件、两次编译、两套符号表)。当时这么做有理由:event 还没定型,先用 record 抽象数据块,留出未来扩展;translation unit 分开能强制"调试代码不依赖游戏代码类型",避免循环引用。

**但现在已经成熟了**。这两套机制暴露出真实的痛点:

- **Record 多套间接**:游戏代码 push 一条 event,先序列化成 record,再反序列化用。中间一次拷贝、一次内存分配。游戏 144 FPS 时每帧几千条 event,这些间接变成 profiler 自己的瓶颈——你想测游戏慢,profiler 自己先慢了。
- **Translation unit 切割带来 fake 隔离**:`debug.cpp` 不能直接看 `GameState` 的字段定义,只能通过 ID + 元数据间接查。结果是为了"隔离"付出的代价是大量元数据表 (member_descriptor) + 字符串 ID 查找,实际耦合没消除,只是改名换姓。
- **修改成本高**:每次给 debug event 加一个字段,要同时改 record struct、translation unit header、读写函数三处。改一处忘一处 → 编译报错 → 排查半小时。

Casey 今天反过来看:**这两个抽象带来的复杂度 > 它们带来的好处**。他直接把 record 拆掉,把 debug 代码 inline 进游戏代码所在 translation unit。**减少概念 = 减少 bug = 减少心智负担**。

这集在 Rust 视角下有一个特别的回响:Rust 没有"translation unit"这个概念,它的模块系统(crate / mod / pub)和 C 的预处理 + 编译单元完全不同。但**同样的设计哲学**——"先分层隔离再合并"——在 Rust 里也会出现(先用 trait object 隔离类型,再改回泛型 inlined)。理解 Casey 这次重构,你以后在自己 Rust 项目里做架构清理会更果断。

**心理锚点**:做完今天,你应该能用一句话回答"什么时候抽象应该被消除?",答案是:**当抽象带来的间接成本 > 它带来的隔离收益时**。这种判断力是工程能力的核心,只能通过看真实重构来获得。

## 1 · Casey 今天做了什么

Casey 这一天**没有加新功能**,而是做三件减法:

1. **删 Record 抽象**:`debug_event` 之前 push 的是 `DebugRecord` 结构(包含 type tag + value union),现在直接 push 一个 tagged enum `DebugValue`,不需要中间 record 类型
2. **合并 translation unit**:之前 `debug.cpp` 单独编译,今天把它合并进 `handmade.cpp`,所有 debug 函数 inline 进游戏代码。共享同一个 `GameState` 定义,debug UI 能直接读 struct 字段
3. **清理冗余头文件**:`debug.h` 里大量前向声明、ID 表全部删除,只保留对外接口

Casey 边删边解释每一处"为什么以前必须这么写,现在不必要"。这是一节**架构清理**的教科书。

## 2 · 心智模型

### 类比:从两间厨房合并成一间

想象你开了一家小餐馆,最初为了"前厅不闻油烟",把前厅点单和后厨做菜切成两个房间,中间有个服务员(record)传单。当时合理——你不确定菜单会怎么变,服务员缓冲一下能解耦。客人点一道菜,前厅把单子写在纸条上,服务员拿去后厨,后厨做完再让服务员端回来。两层间接,但每层都有它存在的理由:前厅不想看见灶台,后厨不想直接面对客人催单。

后来你发现:服务员是个瓶颈、传单出错率不低、菜单已经稳定了——这时候你**打通墙壁**,变成开放式厨房。点单和做菜在同一个空间,服务员(record)被裁掉,厨房直接听客人点单。客人喊一句"加一份牛肉面",后厨马上听见,马上做。中间没有纸条、没有服务员、没有往返延迟。这种"打通"听起来是退步(失去了优雅的隔离),但在小作坊里反而最快——因为传话的人不在了,沟通成本就消失了。

Casey 今天做的就是"打通墙壁"。`debug.cpp` 和 `handmade.cpp` 是两个房间,record 是服务员。今天合并成一个 translation unit(一个房间)。但这次打通是有代价的:你失去了"修改后厨不影响前厅"的隔离,改一处代码就要重新编译整个合并的文件。Casey 权衡下来认为**这个代价是值得的**,因为代码已经稳定,不会再频繁改动,而合并带来的简洁性是每天每帧都在享受的红利。

这个类比还可以再深一层:**抽象的成本不是抽象本身,而是"抽象之间的转换"**。两个房间不可怕,可怕的是中间必须有翻译。Casey 今天消除的不是"房间",而是"翻译"——record 就是那个翻译。一旦翻译没了,两个房间合并成一个,所有数据用同一种语言(同一个 GameState 结构)直接表达。

### 2.1 Record 抽象的本质与代价

C 里的 record(记录)是一种**数据布局约定**:把多个字段打包成连续内存,通过 offset 访问。Casey 之前定义了:

```c
// 之前的伪代码
struct debug_record {
    debug_event_type Type;       // 4 字节,事件类型枚举
    debug_event_value Value;     // 16 字节,tagged union
    u32 GUID;                    // 4 字节,全局唯一 ID
    u32 FrameIndex;              // 4 字节
    // 总共 28 字节,16 字节对齐后 32 字节
};
```

每次游戏代码 push 一条 event,流程是:

```
游戏代码 → 构造 debug_record(填字段、算 GUID)
          → push 进 events 数组
          → debug UI 读 events 数组,反序列化 record
```

中间 record 是个**中间表示**。原本游戏数据已经是结构化的(`Player.pos: Vec2`),序列化成 record 再反序列化,等于两次拷贝 + 一次类型擦除。

**消除 record 后**:

```
游戏代码 → push DebugValue::Vec2(player.pos)  // 直接 tagged enum
          → debug UI 模式匹配 enum,直接读
```

一次构造、一次读,无中间表示。

### 2.2 Translation Unit 在 C 中的真实含义

**翻译单元 (translation unit, TU)** 是 C/C++ 编译的输入单位:一个 `.c` 文件 + 它 `#include` 的所有头文件,展开成一个大的源文件,送给编译器。

```
debug.cpp + debug.h + handmade.h 的部分展开 = TU 1
handmade.cpp + handmade.h + debug.h 的部分展开 = TU 2
```

两个 TU 独立编译,生成两个 `.o` 文件,最后由链接器合并。**TU 边界带来的限制**:

- TU 1 不能直接使用 TU 2 定义的 struct 字段(除非该 struct 在共享 header 里完整定义)
- 跨 TU 调用函数要通过外部链接(extern declaration + 函数符号)
- 内联函数(inline / static)只在本 TU 内可见

Casey 之前让 `debug.cpp` 单独成 TU,目的是**强制 debug 代码不能直接访问游戏内部类型**。这是"通过编译器强制解耦"的设计模式。

**代价**:为了让 debug UI 显示 player.pos,必须:
1. 在游戏代码 introspect player struct
2. 把每个字段序列化成 `DebugValue` 加 ID 加名字
3. push 进 event 流
4. debug UI 读 event 流,通过 ID 查名字,显示

**4 步**才能显示一个字段。如果 debug 直接 inline 进游戏 TU:

```rust
// 合并后,debug UI 在 game TU 内
fn draw_debug_ui(state: &GameState) {
    ui_text(&format!("player.pos = {:?}", state.player.pos));
}
```

**1 步**。这就是消除 TU 边界的收益。

### 2.3 Rust 没有翻译单元,但有更精细的可见性

Rust 的编译单位是 **crate**(一个 `cargo build` 产出的 `.rlib` 或 `.so`)。crate 内部用 `mod` + `pub` 控制可见性。**Rust 没有"每个文件独立编译成 .o 再链接"** 这种 TU 概念,所有 mod 在同一 crate 内能互相看见(只要 `pub`)。

所以 Casey 今天的 "merge translation unit" 在 Rust 里基本是**自动得到**的——只要 `debug` 和 `game` 在同一个 crate,就共享所有定义。

但**同样的设计决策**——"先用类型擦除隔离,后改成具体类型直接访问"——在 Rust 里也会出现。例如:

```rust
// 阶段 1:trait object 隔离(DebugValue 像 Box<dyn Debug>)
pub trait DebugValueTrait {
    fn render(&self, ui: &mut Ui);
}
pub struct DebugValue(Box<dyn DebugValueTrait>);

// 阶段 2:直接 enum,无需 trait object
pub enum DebugValue {
    F32(f32),
    Vec2(Vec2),
    Entity(EntityId),
}
```

阶段 1 用 trait object(类似 record + TU 隔离)是为了"未来扩展",阶段 2 发现 enum 够用且更快,改回去。这正是 Casey 今天的思路。

### 2.4 抽象什么时候该被消除

给出可操作的判断标准:

1. **抽象带来的间接成本是否可测?**(性能 profile 看得到)
2. **抽象的扩展点是否用上了?**(为未来留的接口,实际从未用)
3. **抽象带来的心智负担**(每次改代码要改 3 处 vs 1 处)
4. **抽象是否能用更简单的原语替代**(enum 替代 record+type tag)

4 项有 2 项以上"是",就该消除抽象。Casey 今天 4 项全是"是",所以果断删除。

### 2.5 第一性原理推导:为什么"删代码"反而让系统更健壮

直觉上,加代码 = 加功能 = 系统能力变强。但软件工程的真实经验是:**很多 bug 不是缺少代码造成的,而是冗余代码之间的不一致造成的**。当一个数据形态在系统里有两个表达(record 和 event),你必须保证两者始终同步——一旦忘记同步,bug 就来了。

用第一性原理推导:系统的 bug 数大致和**代码行数 × 概念不一致概率**成正比。删一行代码,bug 期望值就少一点。删一整个抽象层(record + TU 边界),bug 期望值显著下降,因为消除了一整类"忘记同步"的可能。

具体到今天的 debug 系统:**没合并前**,Casey 每加一个 debug event 字段,要同时改 (a) `DebugRecord` struct、(b) record 序列化函数、(c) record 反序列化函数、(d) debug UI 显示逻辑。**合并后**,只需要改 (a) DebugEvent enum 和 (b) debug UI 显示。改动点从 4 个降到 2 个,bug 概率减半。

更微妙的一点是:**抽象的存在本身就是"邀请别人扩展"**。`DebugRecord` 留在那里,新来的工程师可能会以为"加新 event 应该走 record 抽象",导致抽象被错用。删掉 record,这种误用不可能发生。这就是"少即是多"在工程上的具体含义——**不是更少功能,而是更少误解空间**。

这条原理在你后面做 Rust 项目时反复出现:看到两个看起来功能重叠的 trait、两个看起来表达同样数据的 struct,先问"能不能删一个"。如果你犹豫"可能未来需要",Casey 给你的答案是:**未来真的需要时再加,代码会再次告诉你**。先删,真需要再加,比"先留着万一用"更省事。

### 2.6 Hot-reload 视角下的 TU 合并

HH 有个独特约束:游戏代码会**热重载**——改一行代码,不退出游戏,即时加载新版本。这意味着游戏代码必须是个独立的 dynamic library(`.so` / `.dll`),由平台层 dlopen 加载。这一点影响 TU 划分。

合并前:`debug.cpp` 编译进平台层(不热重载),`handmade.cpp` 编译进游戏 .so(热重载)。两者数据交换必须用稳定 ABI——这就是 record 抽象的真实理由:record 是"跨 ABI 边界的稳定数据格式"。

合并后:debug 代码搬进游戏 .so,**和游戏代码一起热重载**。这反而是好事:debug UI 改动也能热重载,即时看到效果。代价是:平台层看不到 debug 状态,但平台层本来就不需要看。

这条权衡只在 HH 的"平台层 + 热重载游戏层"架构里出现。一般的 Rust 项目没有热重载,TU 概念也弱很多,这种合并是"无脑正确"。但理解 HH 的特殊性能让你**判断自己项目的特殊约束**——这是工程直觉的来源。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发里"先建抽象再删抽象"是反复出现的节奏。原因:游戏需求变化快,代码量大,初版经常 over-engineer。

- **Unreal Engine 4 → 5**:Blueprint 抽象曾经是核心,UE5 大量改回 native C++(Nanite / Lumen 不再用 Blueprint 调度)。
- **Unity 的 GameObject → DOTS**:GameObject 是基于 component 的对象图(DOT),性能瓶颈后改 DOTS(Data-Oriented Technology,基于 ECS)。
- **Casey 的 debug 系统**:今天这次。

学到的教训:**没有抽象是永恒的**。你的角色是评估每个抽象的"现在还值得吗",而不是"忠于最初设计"。

### 3.2 · Linux 系统编程视角

Linux 内核里**翻译单元**和**头文件可见性**是日常。看内核源码:

```
kernel/sched/core.c    // 调度器主逻辑
kernel/sched/sched.h   // 调度器内部头(只 sched/ 内文件 include)
include/linux/sched.h  // 对外公开的 task_struct 等
```

`sched.h`(在 `kernel/sched/` 内)就是 Casey 说的 "shared private header",只给调度子系统内部用,不对外暴露。

对应到游戏项目:

```
src/debug/mod.rs       // pub 接口
src/debug/internal.rs  // crate 内 pub(crate),跨 crate 不可见
src/game/state.rs      // GameState
```

Rust 用 `pub(crate)` 表达"Crate 内可见,crate 外不可见",比 C 的"internal header"更精细。

### 3.3 · Rust 生态视角

Rust 对应 Casey 今天做法的工具:

1. **删除一个枚举变体的中间表示**:直接用 `enum` + 模式匹配,避免 trait object
2. **合并 mod**:`mod debug;` 改成 `mod debug { ... }`(inline mod)或者干脆把 `debug.rs` 内容搬到 `game.rs`
3. **避免 type erasure**:用 `&dyn Trait` 前先问"enum 够不够?"

代码示例(消除 record):

```rust
// === 阶段 1:有中间 record 抽象 ===
#[derive(Clone)]
pub struct DebugRecord {
    pub guid: u64,
    pub frame: u32,
    pub kind: DebugKind,
    pub value: DebugValue,
}

pub enum DebugKind { Counter, Watch, Profiler, }

pub enum DebugValue { F32(f32), Vec2([f32; 2]), U32(u32), }

pub fn push_record(events: &mut Vec<DebugRecord>, r: DebugRecord) {
    events.push(r);
}

// === 阶段 2:消除 record(今天 Casey 做的) ===
pub fn push_event(events: &mut Vec<DebugEvent>, e: DebugEvent) {
    events.push(e);
}

#[derive(Clone)]
pub struct DebugEvent {
    pub guid: u64,
    pub frame: u32,
    pub value: DebugValue,  // 直接挂 value,不要中间 kind
}
```

收益:少一个类型、少一次类型转换、少一个 doc page。每次改 event 结构少改一处。

### 3.5 · 🎨 图形学视角(补充)

图形学领域对"抽象该不该留"有非常明确的判断标准,因为 GPU pipeline 的每一层抽象都附带显著的性能税。

举一个具体例子:**vertex format 抽象**。初学者写渲染器,常常先定义一个万能 `Vertex { pos, normal, uv, color, tangent, ... }` 结构,然后所有 mesh 用同一个格式。看起来优雅——一种 vertex、一种 shader。但工业级引擎(DOOM Eternal、Cyberpunk 2077)的做法恰恰相反:**按用途拆分 vertex format**。

- 渲染 depth pre-pass 时,vertex 只需要 `pos`(12 字节)
- 渲染 G-buffer 时,vertex 需要 `pos + normal + uv`(32 字节)
- 渲染 shadow 时,vertex 只需要 `pos`(12 字节)

每个 pass 用最简的 vertex format,带宽最省。这是个"看似更复杂、实际更快"的反抽象例子。**Casey 今天删 record** 的思路完全对应:debug 数据有不同消费者(profiler graph、watch table、UI list),每个消费者用最直接的访问方式,而不是先经过统一的 record 中转。

另一个图形学对应:**OpenGL 的 VAO(Vetex Array Object)抽象**。早期 OpenGL 每次画都要 `glVertexAttribPointer` 一堆调用,2008 年引入 VAO 把这些状态打包。但很快发现:VAO 切换本身有成本,有些场景"不抽象"(直接每次设属性)反而更快。**抽象不等于快**——这点和 Casey 删 record 是同一个教训。

### 3.6 · 历史 / 演化视角

"删抽象"在软件史上有几个著名案例,值得横向对照:

**1. Linus Torvalds 删 BitKeeper 接口层(2005)**:Linux 内核原本用 BitKeeper 做版本控制,围绕它建了一堆 wrapper 抽象。BitKeeper 撤销免费许可后,Linus 干脆自己写 Git,直接干掉所有 wrapper。结果:Git 的内部数据结构(tree + blob + commit)极其简洁,从 BitKeeper 复杂的 client-server 模型退回到内容寻址的 DAG。

**2. Brendan Gregg 删 Java 中间代理层(Netflix,2014)**:Netflix 最初给每个 Java 服务加一层监控代理,代理本身消耗 CPU。Brendan 推广 eBPF 直接在内核采集,删了所有用户态代理。**少一层抽象 = 性能提升 10-100 倍**。

**3. Rust 标准库清理 alloc::boxed(2014-2018)**:Rust 早期 std 有一些过度抽象的 trait(`Box<Any>` 风格的 type erasure),2018 edition 大规模清理,直接用 enum 替代。结果是 std 编译时间下降、runtime 性能提升。

这些案例的共同模式:**成熟系统的演化方向是"减"不是"增"**。新建系统需要抽象来管理不确定性,成熟系统需要消除抽象来压榨性能和简洁度。Casey 今天做的就是 HH 项目内部的"edition 清理"。

## 4 · 认知地图

### 4.1 上级

- **架构清理(architecture cleanup)** — 删除不再承担收益的抽象
- **类型擦除与具体化** — record 是擦除类型,enum 是保留具体类型
- **编译模型** — TU / crate 是不同语言的编译单位

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Record + TU 隔离 | 类型擦除、强制边界 | 设计未定型、需要 ABI 稳定 | 阶段 1 |
| 直接 enum + 同 TU | 类型具体、无边界 | 设计成熟、性能优先 | ✅ 今天切到这个 |
| Trait object (dyn Trait) | 动态分发、可扩展 | 第三方插件 | HH 没用 |

### 4.3 下级

- **DebugEvent 结构** — 单一数据载体
- **DebugValue enum** — 类型化值容器
- **push_event 函数** — 单一 push 入口
- **draw_debug_ui** — 直接读 GameState

## 5 · 对照与变奏

### 同一问题在不同语言的表达

| 语言 | 隔离机制 | 合并机制 |
|---|---|---|
| C/C++ | 翻译单元(.c 文件边界) | 合并 .c 文件、共享 .h |
| Rust | crate + mod + pub(crate) | 合并 mod、改 pub(crate) 为 pub |
| Python | module + `__all__` | 合并 module |
| Java | package + access modifier | 合并 package |
| Go | package + 大小写首字母 | 合并 package |
| Zig | 文件即 module | 合并文件 |

每种语言都有"边界"和"合并"两套机制,但**判断"何时合并"的标准是通用的**:抽象成本 > 收益,就合并。

### 引擎对照:Unreal / Unity / Godot / Bevy

**Unreal Engine**:典型的"重抽象"代表。一个简单的 Actor 有 Component 层、Subsystem 层、Module 边界(每个 Module 是独立编译的 .dll)。UE5 的 Nanite / Lumen 反而开始打破这种抽象——直接在 native C++ 里写,不走 Blueprint 反射层。Casey 今天的"删 record"对应 UE 内部的"绕开 Blueprint 直接调 C++",思路一致:**成熟系统在关键路径上必须减少抽象**。

**Unity**:更激进。GameObject + MonoBehaviour 是经典 OOP 抽象,UE5 时代的 Unity 推 DOTS(Data-Oriented Technology Stack),直接把 GameObject 抽象替换成 ECS。这是引擎级别的"删抽象重写",代价是 API 不兼容,大量现有项目无法迁移。Casey 的做法温和得多:**保留 API,删除内部 record 中间层,用户代码无感**。

**Godot**:走中间路线。Node tree 是主要抽象,但内部实现简洁(GDVM、GDScript 编译器都不臃肿)。Godot 4 的 GDExtension 允许 C++ 直接访问 Node 内部,绕过脚本层——这同样是"为性能删抽象"的实践。

**Bevy**:Rust 原生 ECS,从一开始就用最简的 ECS 抽象(Component + Resource + System),没有 GameObject 这一层。Bevy 的设计哲学和 Casey 高度一致:**少抽象 = 少间接 = 高性能**。看 Bevy 源码你会感到熟悉——干净、直接、无 wrapper。

横向对比的结论:**所有现代游戏引擎都在"减抽象"的方向上演化**。Casey 在 2014-2016 做的这件事,行业在 2020+ 才大规模跟上。学 HH 等于提前体验这个趋势。

### 历史演化

C 时代由于头文件管理麻烦,TU 边界是工程师反复折腾的事。C++20 引入 **modules** 就是想消灭 `.h` + TU 这套古老机制,改成显式的 `import modulename;`。Rust 一开始就没有这套包袱,直接用 crate + mod。Casey 今天手工合并 TU,等于手工模拟 C++ modules 给你的好处。

C++ modules 的 adoption 异常缓慢(2020 标准化,2024 还没普及),原因:**大量既有代码依赖 .h 模型**。微软、Google、Boost 都有百万行级 C++ 代码,迁移成本极高。这是个反面教材——**抽象一旦普及,删掉比创建难 10 倍**。Casey 的 HH 项目从第一天起就保持精简,没有这种包袱,所以他能随时重构。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 今天同时删了两个抽象(record + TU 边界),它们各自解决什么问题?为什么"成熟后"两个都不再必要?

**参考解答**:
- **Record** 解决"事件数据未定型时,用一个中间数据结构容纳所有可能字段"——本质是类型擦除 buffer。定型后,enum 直接表达就够了。
- **TU 边界** 解决"防止 debug 代码意外依赖游戏内部类型,导致循环依赖"——本质是物理隔离。当 debug 和 game 已经稳定共享数据流(event ID + value),物理隔离变成纯负担。
- 成熟后两者都不必要,因为:**真正的耦合已经在数据流(event ID + value schema)里被显式表达了**,再叠加 record + TU 边界只是双重保险,成本超过收益。

### Lv2 · 动手实践

**题**:在你的 Rust 项目里,找出最近用过的"中间 record 风格"代码(任何把数据先打包成中间结构再处理的位置)。改造为直接 enum / 直接函数调用,然后用 `cargo bench` 或简单 `time` 测改造前后耗时差异。

完成标准:有 diff、有性能对比数字、写一段"为什么差异是这样"。

**参考解答**思路:
1. 典型场景:`Log` struct 里包了 `timestamp + level + message + metadata`,然后序列化成 JSON 再交给 logger 处理——中间 JSON 就是 record。
2. 改造:直接传 `Log { ... }` 给 logger,跳过 JSON 序列化(至少在 hot path)。
3. 测试:用 `criterion` 跑 bench,JSON 版本 ~200ns/次,直接 struct 版本 ~20ns/次,差 10 倍。
4. 解读:序列化是不必要的"中间表示",删除后直接访问字段,跳过字符串解析。

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

```rust
// Cargo.toml(空,纯 std)

use std::time::Instant;

// === 阶段 1:中间 record 抽象(改造前) ===
#[derive(Clone)]
struct DebugRecord {
    guid: u64,
    frame: u32,
    kind: RecordKind,
    value: RecordValue,
}

#[derive(Clone, Copy)]
enum RecordKind { Counter, Watch, }

#[derive(Clone)]
enum RecordValue { F32(f32), U32(u32), }

fn push_record(events: &mut Vec<DebugRecord>, r: DebugRecord) {
    events.push(r);
}

// === 阶段 2:消除 record(改造后) ===
#[derive(Clone)]
struct DebugEvent {
    guid: u64,
    frame: u32,
    value: RecordValue,  // 直接挂 value,不要 kind
}

fn push_event(events: &mut Vec<DebugEvent>, e: DebugEvent) {
    events.push(e);
}

fn main() {
    const N: usize = 100_000;

    // 测改造前
    let mut records: Vec<DebugRecord> = Vec::with_capacity(N);
    let t1 = Instant::now();
    for i in 0..N {
        push_record(&mut records, DebugRecord {
            guid: i as u64,
            frame: i as u32,
            kind: RecordKind::Counter,
            value: RecordValue::F32(i as f32),
        });
    }
    let dt1 = t1.elapsed();

    // 测改造后
    let mut events: Vec<DebugEvent> = Vec::with_capacity(N);
    let t2 = Instant::now();
    for i in 0..N {
        push_event(&mut events, DebugEvent {
            guid: i as u64,
            frame: i as u32,
            value: RecordValue::F32(i as f32),
        });
    }
    let dt2 = t2.elapsed();

    println!("record (with kind):  {:?}", dt1);
    println!("event  (no kind)  :  {:?}", dt2);
    println!("speedup: {:.2}x", dt1.as_secs_f64() / dt2.as_secs_f64());
    // 输出大约 speedup: 1.05x ~ 1.2x
    // 注意:差异不大,因为少了 1 字节 enum tag。Casey 收益主要在代码简洁度。
}
```

**关键 Rust 特性解释**:
- `#[derive(Clone)]` — 让 struct 可以 `.clone()`。这里我们 push 时转移所有权,实际不需要 Clone,但保险起见加上
- `RecordKind::Counter` — enum variant 标记,编译成 1 字节 discriminant
- `Vec::with_capacity(N)` — 预分配,避免 push 时反复 realloc
- `Instant::now()` — 单调时钟,测耗时用。比 `SystemTime` 更准(不受 NTP 调整影响)
- `dt1.as_secs_f64()` — 把 Duration 转 f64 秒,方便算比值

- perf 没权限 — `sudo perf stat`,或者改 `/proc/sys/kernel/perf_event_paranoid` 到 1
- `cargo rustc --emit asm` 输出文件找不到 — 用 `find target/release/deps/ -name "day211-*.s"` 搜,文件名带 hash
- speedup < 1.0 — 你的 record 和 event 字段几乎一样,差异主要在编译时(枚举少一个 tag),运行时确实差异不大。Casey 的主要收益是**代码简洁度**,不是 raw 性能。这点要诚实承认——并不是每次"删抽象"都能跑分提升,但每次都能减少心智负担
- 如果 record 里有 heap 数据(`String`、`Vec<T>`),clone 成本会显著,这时删 record 的收益就明显了。教学示例用 `f32` 是为了简洁,真实场景看数据类型
