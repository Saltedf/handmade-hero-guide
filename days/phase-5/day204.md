
# Day 204 · 鼠标光标反投影

> 鼠标在屏幕坐标 (mouse_x, mouse_y),游戏世界是 (world_x, world_y)。**反投影**就是把屏幕坐标转回世界坐标。今天 Casey 实现这个,后面就能"鼠标点屏幕选实体"。

## 0 · 为什么要有这一天

让我们把镜头拉到一个具体的开发场景。

你跟着 HH 走到 Day 203,debug UI 已经成熟——GUID 表、cache、各种视图。今天你想加一个新功能:**用鼠标点屏幕,选中地图上的实体**。这在编辑器、即时战略、塔防、RPG 都用得到。

你打开游戏,鼠标光标在屏幕坐标 `(640, 360)`(屏幕中心)。你知道世界里的玩家在 `(100, 100)`,但因为相机正在偏移和缩放,屏幕中心可能对应世界坐标 `(100, 100)` 也可能对应 `(500, 200)`。**鼠标在屏幕上的像素位置和它在世界里的真实位置,不是同一个东西**。

要把鼠标的"屏幕意图"变成"世界动作",你必须把屏幕坐标**反投影**回世界坐标。这是今天 Casey 做的事。

**为什么这件事不平凡?**

想象你在玩星际争霸。鼠标点屏幕左上角的小地图,实际你想攻击地图右上角的敌军基地。游戏要做的事:把"屏幕坐标 (200, 100)"映射到"世界坐标 (4500, 3800)",然后告诉游戏逻辑"玩家点了这个位置"。这个映射必须**精确**——误差 1 像素可能让部队走到错误的山头。

精确反投影要求你完整还原相机的所有变换。如果相机有平移(`camera.pos`)、缩放(`camera.zoom`)、旋转(`camera.angle`)、屏幕中心偏移(`screen_size / 2`),反投影要**逆序**逐个抵消:

```
正向:world → 减相机位置 → 缩放 → 加屏幕中心 → screen
反向:screen → 减屏幕中心 → 反缩放 → 加相机位置 → world
```

每一步都是上一步的"逆运算"。漏一步或顺序错,反投影结果偏离几十像素,鼠标点不准。

**这件事的核心数学**叫**仿射变换(affine transformation)**和它的**逆变换**。仿射变换 = 线性变换(缩放、旋转、剪切)+ 平移。它的逆变换是封闭的——仿射的逆还是仿射。这是为什么反投影可以"一步一步逆回去"。

2D 反投影出奇地简单——4 行 Rust 代码搞定。但同样的思路在 3D 里要复杂得多(4x4 矩阵 + 透视除法 + ray casting)。今天的 2D 是 3D 的预备课——理解 2D 仿射反投影,3D 的 unprojection 才有基础。

**学完今天,你应该能**:
- 写出 world_to_screen 和 screen_to_world,验证它们互逆
- 解释仿射变换为什么"逆变换封闭"(affine 的逆还是 affine)
- 处理相机旋转、缩放、平移组合时的逆序问题
- 保护 zoom=0 的奇异点(clamp + assert)
- 看懂 OpenGL 的 `gluUnProject` 在做什么(同构问题)
- 知道高 DPI 屏幕和不同 viewport 设置下,反投影需要哪些额外步骤
- 理解为什么 3D 拾取要用 ray casting 而不是直接 unproject

## 2 · 心智模型

### 2.1 费曼类比:Google 地图的拖动与点击

想象 Google 地图。屏幕上你看到城市街道——这是"屏幕坐标"。但地图的真实数据是经纬度——这是"世界坐标"。两个空间被一组变换连接。

- 拖动地图 = 改 camera.pos(地图中心)
- 滚轮缩放 = 改 camera.zoom(放大级别)
- 鼠标点屏幕上一个 pin = 反投影算经纬度

你在屏幕点 (640, 360),实际你想知道"这个点对应的真实地理坐标"。Google 必须做反投影:**从屏幕像素 (640, 360) 倒推出经纬度**。这个倒推过程必须**精确还原**——否则你点天安门,Google 把你定位到郊外。

游戏的相机一模一样,只是数学更简单。地图是球面(需要球面投影),游戏世界通常是平面(线性变换即可)。

这个类比的关键洞察:**屏幕坐标和世界坐标是同一空间的两份表示**。变换是它们之间的翻译字典。反投影是"反向查字典"。

### 2.2 从零推导:为什么仿射变换如此简单

让我们一步步从最朴素的问题推到完整反投影。

**Step 0:没有相机**。屏幕 = 世界。屏幕坐标 (100, 200) 就是世界坐标 (100, 200)。鼠标点击直接命中那个位置的 entity。

```rust
fn world_to_screen(world: Vec2) -> Vec2 { world }
fn screen_to_world(screen: Vec2) -> Vec2 { screen }
```

但游戏世界通常比屏幕大(开放世界游戏世界几公里,屏幕 1080p)。需要相机。

**Step 1:平移相机**。相机在世界坐标的某个位置,屏幕中心对应相机位置。世界坐标 → 屏幕坐标要减去相机位置,让相机对齐屏幕中心。

```rust
fn world_to_screen(world: Vec2, camera_pos: Vec2, screen_center: Vec2) -> Vec2 {
    Vec2::new(
        world.x - camera_pos.x + screen_center.x,
        world.y - camera_pos.y + screen_center.y,
    )
}

fn screen_to_world(screen: Vec2, camera_pos: Vec2, screen_center: Vec2) -> Vec2 {
    Vec2::new(
        screen.x - screen_center.x + camera_pos.x,
        screen.y - screen_center.y + camera_pos.y,
    )
}
```

**验证互逆**:`screen_to_world(world_to_screen(p)) = (world - camera + center) - center + camera = world`。✓

**Step 2:加缩放(zoom)**。世界单位可能和像素不同——比如 1 世界单位 = 2 像素。这意味着世界相对屏幕"放大 2 倍"。正向变换里,减完相机位置后乘以 zoom:

```rust
fn world_to_screen(world: Vec2, camera: &Camera) -> Vec2 {
    Vec2::new(
        (world.x - camera.pos.x) * camera.zoom + camera.screen_center.x,
        (world.y - camera.pos.y) * camera.zoom + camera.screen_center.y,
    )
}
```

反投影要除以 zoom:

```rust
fn screen_to_world(screen: Vec2, camera: &Camera) -> Vec2 {
    Vec2::new(
        (screen.x - camera.screen_center.x) / camera.zoom + camera.pos.x,
        (screen.y - camera.screen_center.y) / camera.zoom + camera.pos.y,
    )
}
```

**验证互逆**:
- 正向:`screen.x = (world.x - cam.x) * zoom + center.x`
- 反向:`world.x = (screen.x - center.x) / zoom + cam.x`
- 代入:`(screen.x - center.x) / zoom + cam.x = ((world.x - cam.x) * zoom + center.x - center.x) / zoom + cam.x = (world.x - cam.x) + cam.x = world.x` ✓

这是仿射变换的核心:**线性部分(缩放)+ 平移部分(平移)**,逆变换也是"逆线性 + 逆平移",顺序反过来。

**Step 3:加旋转**。相机绕 z 轴(垂直于屏幕)旋转 angle 弧度。这是 2D 旋转矩阵:

```
R(θ) = [cos(θ)  -sin(θ)]
       [sin(θ)   cos(θ)]
```

正向变换顺序:**translate(减相机) → rotate(转 -angle) → scale(乘 zoom) → translate(加屏幕中心)**。注意相机视角是"世界绕相机转 +angle",但实际算"点相对相机转 -angle"。

反向变换:**translate(减屏幕中心) → inverse-scale(除 zoom) → inverse-rotate(转 +angle) → translate(加相机)**。

```rust
fn screen_to_world_rotated(screen: Vec2, camera: &Camera) -> Vec2 {
    // 1. 减屏幕中心
    let p = screen - camera.screen_center;
    // 2. 反缩放
    let p = p / camera.zoom;
    // 3. 反旋转(+angle)
    let cos = camera.angle.cos();
    let sin = camera.angle.sin();
    let p = Vec2::new(
        p.x * cos + p.y * sin,    // 反向旋转
        -p.x * sin + p.y * cos,
    );
    // 4. 加相机位置
    p + camera.pos
}
```

**关键洞察**:每个变换的逆,顺序严格反向。这是线性代数的一个基本事实——**复合变换的逆 = 各分量逆的反向复合**。形式上:`(A * B * C)^-1 = C^-1 * B^-1 * A^-1`。

### 2.3 仿射变换的代数结构

为什么仿射变换的逆还是仿射?这是代数上的重要性质,让反投影"通用化"。

**定义**:仿射变换 `f: R^n → R^n` 满足 `f(x) = A*x + b`,其中 A 是线性变换(矩阵),b 是平移向量。

**复合**:`f ∘ g (x) = f(g(x)) = A*(C*x + d) + b = (A*C)*x + (A*d + b)`。结果还是 `A' * x + b'` 的形式——仿射。

**逆**:`f(x) = A*x + b = y` ⇒ `x = A^-1 * (y - b) = A^-1 * y - A^-1 * b`。即 `f^-1(y) = A^-1 * y - A^-1 * b`。还是仿射形式。

这意味着:**任何仿射变换,不管多复杂(多次旋转、缩放、平移组合),都可以写成一个矩阵 + 一个向量**。反投影只需要算一次逆矩阵 + 一次减法。

工业 3D 引擎用这个性质——把 model + view + projection 合并成 MVP matrix,顶点 shader 里乘一次。反投影 (unprojection) 只算 MVP 的逆,也是一次乘法。

### 2.4 齐次坐标(homogeneous coordinates)

3D 游戏用 4x4 矩阵统一所有变换。技巧是**齐次坐标**:把 (x, y) 加一维变成 (x, y, 1),这样平移也能用矩阵乘法表达:

```
[x']   [a b tx] [x]
[y'] = [c d ty] [y]
[1 ]   [0 0  1] [1]
```

第三行 `[0 0 1]` 保证 w 分量永远是 1。这是"齐次"的含义——所有点都加一个 1 的"虚拟维度"。

齐次坐标让"复合变换"就是矩阵连乘,无需要分情况处理平移和线性。3x3 的齐次矩阵可以表达所有 2D 仿射变换,4x4 的齐次矩阵可以表达所有 3D 仿射变换 + 透视投影。

```rust
// glam 的 2D 仿射
use glam::{Mat3, Vec2};

let m = Mat3::from_translation(Vec2::new(640.0, 360.0))
    * Mat3::from_scale(Vec2::new(2.0, 2.0));
let screen = m.transform_point2(world);

let inv = m.inverse();
let world_back = inv.transform_point2(screen);
```

`m.inverse()` 自动算逆——你不需要手动推公式。这是工业级数学库(glam, nalgebra)的价值。

### 2.5 高 DPI、视口、坐标系翻转

实际工程里有几个细节坑:

**高 DPI 屏幕**。Linux 上 `WAYLAND_DISPLAY` 和 X11 的窗口有时缩放因子(scale factor)≠ 1。鼠标坐标可能是"逻辑像素"或"物理像素",要统一。

```rust
let scale = window.scale_factor();  // 比如 2.0(视网膜屏)
let physical_mouse = logical_mouse * scale;
```

如果不统一,鼠标在屏幕"右下角"逻辑 (1280, 720),但物理坐标 (2560, 1440),反投影会偏差一半屏幕。

**Y 轴方向**。屏幕坐标系 y 向下(原点在左上),但数学坐标系 y 向上(原点在左下)。游戏世界通常 y 向下(和屏幕一致),但有时(物理模拟)y 向上。要明确约定,反投影时记得翻 y:

```rust
let flipped_screen = Vec2::new(screen.x, screen_size.y - screen.y);
```

**视口(viewport)偏移**。如果游戏窗口不是全屏,有边框、标题栏,鼠标相对窗口的位置 ≠ 鼠标相对屏幕的位置。要减去窗口位置:

```rust
let mouse_in_window = mouse_pos - window_pos;
```

这些细节每个游戏都要处理,容易漏。Casey 在 HH 里假设全屏 + 标准 DPI,简化教学。

### 2.6 zoom=0 的奇异点

`screen_to_world` 用 `screen.x / zoom`。zoom=0 时除零,f32 给出 ±∞ 或 NaN。NaN 会污染下游所有计算——一个 entity 的位置变 NaN,所有和它交互的 entity 也变 NaN,几个 frame 后整个游戏世界都是 NaN。

防御:

```rust
pub const MIN_ZOOM: f32 = 0.01;  // 100 倍缩小
pub const MAX_ZOOM: f32 = 100.0; // 100 倍放大

impl Camera {
    pub fn set_zoom(&mut self, zoom: f32) {
        self.zoom = zoom.clamp(MIN_ZOOM, MAX_ZOOM);
    }
}
```

clamp 保证 zoom 永远在合理范围。即便用户的输入设备(滚轮、传感器)给出极端值,也不会触发 NaN。

工程实践:**任何除法都要检查除数**。f32 除零不会 panic,但产生 NaN,这种 bug 极难追踪。clamp + assert 是防御性编程的标准答案。

### 2.7 大世界游戏的精度问题

f32 有 7 位有效数字(23 位尾数)。world 坐标很大时,小数部分精度差:

```
world_x = 100.5      → f32 精确
world_x = 10000.5    → f32 精确
world_x = 100000.5   → f32 表示为 100000.5(OK)
world_x = 1000000.5  → f32 表示为 1000000.5(OK)
world_x = 10000000.5 → f32 表示为 10000000.0(小数丢了)
world_x = 100000000.5 → 误差 0.5 像素
```

案例:**Minecraft** 世界边长可达 6000 万方块。如果用 f32,在距离原点 10000 方块的位置,精度已经差到玩家"卡墙"——坐标精度不够区分玩家和墙的边界。Minecraft 用"分块坐标系"——每块区域用本地坐标(0~1000),块之间用整数 ID。这是浮点精度的工程应对。

**Kerbal Space Program** 用 f64(双精度)做天体物理——因为星际距离巨大,f32 不够。代价是 CPU 慢、内存大。

Casey HH 世界小(< 10000 单位),f32 完全够。但工业游戏(MMO、太空模拟)必须考虑精度。

### 2.8 完整 Rust 实现

下面是 Casey 设计在 Rust 里的完整落地:

```rust
#[derive(Copy, Clone, Debug)]
pub struct Vec2 { pub x: f32, pub y: f32 }

impl Vec2 {
    pub fn new(x: f32, y: f32) -> Self { Self { x, y } }
    pub fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    pub fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
    pub fn scale(self, s: f32) -> Self { Self::new(self.x * s, self.y * s) }
    pub fn div(self, s: f32) -> Self { Self::new(self.x / s, self.y / s) }
}

pub const MIN_ZOOM: f32 = 0.1;
pub const MAX_ZOOM: f32 = 10.0;

#[derive(Copy, Clone)]
pub struct Camera {
    pub pos: Vec2,        // 相机中心在世界坐标
    pub zoom: f32,        // 缩放(像素 / 世界单位)
    pub screen_size: Vec2,// 屏幕分辨率
}

impl Camera {
    pub fn new(pos: Vec2, zoom: f32, screen_size: Vec2) -> Self {
        Self { pos, zoom: zoom.clamp(MIN_ZOOM, MAX_ZOOM), screen_size }
    }

    /// 正向:世界 → 屏幕
    pub fn world_to_screen(&self, world: Vec2) -> Vec2 {
        let center = self.screen_size.scale(0.5);
        Vec2::new(
            (world.x - self.pos.x) * self.zoom + center.x,
            (world.y - self.pos.y) * self.zoom + center.y,
        )
    }

    /// 反向:屏幕 → 世界(反投影)
    pub fn screen_to_world(&self, screen: Vec2) -> Vec2 {
        let center = self.screen_size.scale(0.5);
        Vec2::new(
            (screen.x - center.x) / self.zoom + self.pos.x,
            (screen.y - center.y) / self.zoom + self.pos.y,
        )
    }

    /// 改 zoom 时 clamp
    pub fn set_zoom(&mut self, zoom: f32) {
        self.zoom = zoom.clamp(MIN_ZOOM, MAX_ZOOM);
    }
}
```

**验证互逆**:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn world_screen_roundtrip() {
        let cam = Camera::new(
            Vec2::new(100.0, 100.0),
            2.0,
            Vec2::new(1280.0, 720.0),
        );
        for world in [
            Vec2::new(0.0, 0.0),
            Vec2::new(500.0, 300.0),
            Vec2::new(-100.0, -200.0),
            Vec2::new(100.0, 100.0),  // 相机中心
        ] {
            let screen = cam.world_to_screen(world);
            let world_back = cam.screen_to_world(screen);
            assert!((world.x - world_back.x).abs() < 0.001, "x mismatch");
            assert!((world.y - world_back.y).abs() < 0.001, "y mismatch");
        }
    }

    #[test]
    fn camera_center_at_screen_center() {
        let cam = Camera::new(Vec2::new(100.0, 100.0), 1.0, Vec2::new(1280.0, 720.0));
        let screen = cam.world_to_screen(Vec2::new(100.0, 100.0));
        assert_eq!(screen.x, 640.0);  // 屏幕中心 x
        assert_eq!(screen.y, 360.0);  // 屏幕中心 y
    }

    #[test]
    fn zoom_protected_from_zero() {
        let cam = Camera::new(Vec2::new(0.0, 0.0), 0.0, Vec2::new(1280.0, 720.0));
        assert!(cam.zoom >= MIN_ZOOM);  // clamp 起效
    }
}
```

跑 `cargo test`,三个测试都过。这就是工业级代码——每个边界条件都有测试。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业的相机系统各不相同。每种游戏类型有自己的相机需求。

**Side-scroller(超级马里奥、空洞骑士)**:相机水平跟随玩家,但 y 方向有限。玩家跳跃时相机不动(避免眩晕),玩家靠近屏幕边缘时相机突然上移(camera snap)。这种"分段锁定"用 camera bounds 实现——`camera.pos.clamp(world_min, world_max)`。

**Top-down RPG(塞尔达、暗黑破坏神)**:相机俯视,跟随玩家。玩家在屏幕中心,相机平移。zoom 固定(通常 1.0)。反投影用于鼠标点击移动、选中 NPC。

**RTS(星际争霸、AOE)**:相机**不跟随**玩家,玩家用 WASD 或鼠标到屏幕边缘拖动相机。zoom 也允许(鼠标滚轮)。反投影用于选择单位、命令移动、建造。RTS 的反投影要支持大世界(整个地图可能 256x256 tile)。

**Fighting game(街霸、铁拳)**:双人对焦——相机始终框住两个角色。相机位置 = (player1.pos + player2.pos) / 2,zoom 根据角色距离动态调整(远时缩小,近时放大)。反投影用得少,主要用于菜单。

**FPS(毁灭战士、CS)**:第一人称,相机=玩家眼睛。屏幕中心固定是十字准心。鼠标移动 = 旋转视角,反投影用于十字准心瞄准(其实就是屏幕中心 → 世界射线)。

**Open world(GTA、巫师 3)**:第三人称,相机跟随玩家但允许玩家自由旋转视角(右摇杆 / 鼠标)。这是最复杂的——相机有平移、yaw/pitch 旋转、距离参数(distance from player)。反投影用于玩家瞄准、点击交互。

每种风格的反投影数学都基于同一原理(仿射变换 + 逆),但参数和约束不同。Casey HH 是 top-down 风格(玩家在中心,相机俯视),反投影最简单。

### 3.2 · 🎨 图形学视角

图形管线里的"反投影"是固定阶段——vertex shader 把世界坐标转 NDC(normalized device coords),fragment shader 处理像素。反向(NDC → 世界)就是反投影。

```
world coords
    ↓ model matrix
object coords
    ↓ view matrix
eye/camera coords
    ↓ projection matrix
clip coords
    ↓ perspective divide (÷ w)
NDC ([-1, 1]^3)
    ↓ viewport transform
screen/window coords
```

每一步都有逆:

- inverse viewport:NDC = (screen / viewport_size) * 2 - 1
- inverse projection + view + model:MVP 的逆矩阵,乘以 NDC

3D 引擎(unreal、unity、bevy)的 unproject API 就是上面这串代码。

```glsl
// GLSL fragment shader 里的反投影(在屏幕 quad 上)
vec3 world_pos = inverse(view_proj) * vec4(ndc, depth, 1.0);
world_pos /= world_pos.w;
```

但 3D 反投影有个根本问题:**鼠标只有一个 2D 位置**,3D 世界是 3D 空间。鼠标位置对应**一条射线**,从 near plane 到 far plane。要知道具体 3D 位置,需要 depth buffer(深度信息)。

```rust
fn screen_to_world_3d(screen: Vec2, depth: f32, vp: &ViewProj) -> Vec3 {
    let ndc = Vec3::new(
        screen.x / viewport.w * 2.0 - 1.0,
        1.0 - screen.y / viewport.h * 2.0,  // y 翻转
        depth * 2.0 - 1.0,
    );
    let world = vp.inverse() * Vec4::new(ndc.x, ndc.y, ndc.z, 1.0);
    world.xyz() / world.w
}
```

3D 拾取的工业方法(后面 Day 71+ 会用):

**Ray casting**:鼠标 → 屏幕射线(用反投影算出 near plane + far plane 点,构造射线)。然后射线与所有物体的包围盒求交。最近的命中就是选中物体。最常用。

**Color picking**:每个物体渲染到 offscreen buffer 时分配唯一颜色(物体 ID)。鼠标位置读这个 offscreen 像素,颜色查物体。简单但贵(双 pass 渲染)。Unity 编辑器、RenderDoc 用这个。

**Depth picking**:读 depth buffer + 鼠标 x,y,反投影得到 3D 坐标。然后查这个坐标附近最近的物体。准确但依赖 depth buffer 精度。

## 5 · 对照与变奏

### 5.1 3D 拾取的工业方法

3D 游戏的反投影比 2D 复杂得多,因为鼠标只有 2D 输入但世界是 3D。工业界有三种方案:

**Ray casting**(最常用):鼠标 → 屏幕射线 → 与 3D 物体求交。

```rust
fn mouse_to_ray(mouse: Vec2, cam: &Camera3D) -> Ray {
    let ndc = vec3(
        (mouse.x / screen.w) * 2.0 - 1.0,
        1.0 - (mouse.y / screen.h) * 2.0,
        -1.0,  // near plane
    );
    let near = (cam.proj * cam.view).inverse() * vec4(ndc.x, ndc.y, ndc.z, 1.0);
    let near = near.xyz() / near.w;
    let far_ndc = vec3(ndc.x, ndc.y, 1.0);  // far plane
    let far = (cam.proj * cam.view).inverse() * vec4(far_ndc.x, far_ndc.y, far_ndc.z, 1.0);
    let far = far.xyz() / far.w;
    Ray::new(near, (far - near).normalize())
}
```

然后射线与每个物体的包围盒(AABB / sphere)求交,最近的命中就是选中物体。Unreal Editor、Unity Editor 用这个。

**Color picking**:每个物体渲染到 offscreen buffer 时分配唯一颜色(物体 ID 编码到 RGB)。鼠标位置读这个 offscreen 像素,颜色查物体。

```
渲染 pass 1:正常渲染到屏幕
渲染 pass 2:每个物体用唯一颜色重新渲染到 ID buffer
读鼠标位置像素:glReadPixels(mouse.x, mouse.y, ...)
颜色查表 → 物体 ID
```

优势:简单,任意复杂物体都能 pick(只需颜色)。劣势:贵(双 pass 渲染)。Unity 编辑器、RenderDoc 用这个。

**Depth picking**:读 depth buffer + 鼠标 x,y,反投影到 3D 坐标。

```rust
let depth: f32 = read_depth_buffer(mouse.x, mouse.y);  // [0, 1]
let world = screen_to_world_3d(mouse, depth, &vp);
// 然后查 world 附近的物体
```

准确,但依赖 depth buffer 精度(远距离精度差)。

### 5.2 OpenGL 的 gluUnProject

OpenGL 早期提供 `gluUnProject` API,内部做反投影:

```c
// screen → NDC
GLfloat ndc_x = (2 * screen_x) / viewport_w - 1;
GLfloat ndc_y = 1 - (2 * screen_y) / viewport_h;  // y 翻转

// NDC → world
vec4 world = inverse(proj * view) * vec4(ndc_x, ndc_y, depth, 1);
world /= world.w;  // perspective divide
```

现代 OpenGL 用 `glm::unProject`(C++)或 `glam` 等价 API。思路一样——乘 MVP 的逆矩阵,做透视除法。

### 5.3 VR / AR 的反投影

VR 双目相机,**鼠标概念不适用**(玩家戴头显,没有光标)。改用 controller ray(手柄方向)→ 与虚拟物体求交。

AR(增强现实)同样思路,但要求"虚拟物体与现实物体对齐"——SLAM(simultaneous localization and mapping)算法算相机相对真实世界的位置。ARKit(Apple)、ARCore(Google)内部用 SLAM。

### 5.4 不同范式的"反投影"

**Document editing(DOM)**:浏览器里点击 (x, y),要确定"哪个 HTML element 被点中"。`document.elementFromPoint(x, y)` 做这件事——递归 hit test DOM 树。

```js
const el = document.elementFromPoint(100, 200);
console.log(el.tagName);  // 比如 "BUTTON"
```

**Database**:从索引的"逻辑位置"反查物理存储位置。B+tree 的 leaf node 存 key → row pointer,这就是一种"反投影"。

**Filesystem**:文件路径 → inode。`stat /path/to/file` 反查文件元数据。这是路径到 inode 的反投影。

所有这些都是同一个抽象:**从一个表示(screen、path、index key)反查另一个表示(world、inode、row)**。游戏反投影到世界坐标,数据库反查到物理位置,文件系统反查到 inode。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:zoom=0 时 screen_to_world 会怎样?怎么处理?

**参考解答**:

`screen.x / zoom` 当 zoom=0 时产生 ±∞ 或 NaN。NaN 会通过所有运算传播——一个 NaN 让整个世界坐标变 NaN,entity 位置 NaN,碰撞检测 NaN,游戏崩。

数学上,zoom=0 对应"无限缩小"——世界投影到一个像素。物理无意义。

工程上,clamp zoom 到 [MIN_ZOOM, MAX_ZOOM]:

```rust
pub const MIN_ZOOM: f32 = 0.1;
pub const MAX_ZOOM: f32 = 10.0;

impl Camera {
    pub fn set_zoom(&mut self, zoom: f32) {
        self.zoom = zoom.clamp(MIN_ZOOM, MAX_ZOOM);
    }
}
```

clamp 在 setter 里强制。任何调 `set_zoom` 的代码都不可能让 zoom 变 0 或负。这是防御性编程的标准模式。

### Lv2 · 动手实践

**题**:实现 Camera + world_to_screen + screen_to_world,验证互逆。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
pub struct Vec2 { pub x: f32, pub y: f32 }
impl Vec2 {
    pub fn new(x: f32, y: f32) -> Self { Self { x, y } }
}

pub const MIN_ZOOM: f32 = 0.1;
pub const MAX_ZOOM: f32 = 10.0;

#[derive(Copy, Clone)]
pub struct Camera {
    pub pos: Vec2,
    pub zoom: f32,
    pub screen_size: Vec2,
}

impl Camera {
    pub fn world_to_screen(&self, world: Vec2) -> Vec2 {
        Vec2 {
            x: (world.x - self.pos.x) * self.zoom + self.screen_size.x / 2.0,
            y: (world.y - self.pos.y) * self.zoom + self.screen_size.y / 2.0,
        }
    }

    pub fn screen_to_world(&self, screen: Vec2) -> Vec2 {
        Vec2 {
            x: (screen.x - self.screen_size.x / 2.0) / self.zoom + self.pos.x,
            y: (screen.y - self.screen_size.y / 2.0) / self.zoom + self.pos.y,
        }
    }
}

fn main() {
    let cam = Camera {
        pos: Vec2::new(100.0, 100.0),
        zoom: 2.0,
        screen_size: Vec2::new(1280.0, 720.0),
    };

    // 测试 1:相机中心 → 屏幕中心
    let center = cam.world_to_screen(Vec2::new(100.0, 100.0));
    assert_eq!(center.x, 640.0);
    assert_eq!(center.y, 360.0);
    println!("PASS: camera center at screen center");

    // 测试 2:互逆
    let test_points = [
        Vec2::new(0.0, 0.0),
        Vec2::new(500.0, 300.0),
        Vec2::new(-100.0, -200.0),
        Vec2::new(100.0, 100.0),
    ];
    for world in test_points {
        let screen = cam.world_to_screen(world);
        let world_back = cam.screen_to_world(screen);
        assert!((world.x - world_back.x).abs() < 0.001, "x mismatch at {:?}", world);
        assert!((world.y - world_back.y).abs() < 0.001, "y mismatch at {:?}", world);
    }
    println!("PASS: roundtrip identity");

    // 测试 3:zoom 影响
    let mut zoomed = cam;
    zoomed.zoom = 4.0;
    let near = cam.world_to_screen(Vec2::new(110.0, 100.0));  // 相机右 10 单位
    let far = zoomed.world_to_screen(Vec2::new(110.0, 100.0)); // 同位置,zoom 2x
    assert_eq!(near.x, 660.0);  // (10 * 2) + 640 = 660
    assert_eq!(far.x, 680.0);   // (10 * 4) + 640 = 680
    println!("PASS: zoom scales distance from center");

    println!("All tests passed!");
}
```

### Lv3 · 迁移设计

**题**:加上相机旋转(rotation angle)。world_to_screen 和 screen_to_world 怎么改?

**设计思路**:

正向变换顺序:**translate(减相机)→ rotate(转 -angle)→ scale(乘 zoom)→ translate(加屏幕中心)**。

反向变换顺序严格相反:**translate(减屏幕中心)→ inverse-scale(除 zoom)→ inverse-rotate(转 +angle)→ translate(加相机)**。

**参考实现**:

```rust
#[derive(Copy, Clone)]
pub struct RotatedCamera {
    pub pos: Vec2,
    pub angle: f32,  // 弧度,逆时针为正
    pub zoom: f32,
    pub screen_size: Vec2,
}

impl RotatedCamera {
    pub fn world_to_screen(&self, world: Vec2) -> Vec2 {
        // 1. 减相机位置
        let p = Vec2::new(world.x - self.pos.x, world.y - self.pos.y);
        // 2. 旋转 -angle(相机视角)
        let cos = (-self.angle).cos();
        let sin = (-self.angle).sin();
        let p = Vec2::new(
            p.x * cos - p.y * sin,
            p.x * sin + p.y * cos,
        );
        // 3. 缩放
        let p = Vec2::new(p.x * self.zoom, p.y * self.zoom);
        // 4. 加屏幕中心
        Vec2::new(
            p.x + self.screen_size.x / 2.0,
            p.y + self.screen_size.y / 2.0,
        )
    }

    pub fn screen_to_world(&self, screen: Vec2) -> Vec2 {
        // 1. 减屏幕中心
        let p = Vec2::new(
            screen.x - self.screen_size.x / 2.0,
            screen.y - self.screen_size.y / 2.0,
        );
        // 2. 反缩放
        let p = Vec2::new(p.x / self.zoom, p.y / self.zoom);
        // 3. 反旋转(+angle)
        let cos = self.angle.cos();
        let sin = self.angle.sin();
        let p = Vec2::new(
            p.x * cos - p.y * sin,
            p.x * sin + p.y * cos,
        );
        // 4. 加相机位置
        Vec2::new(p.x + self.pos.x, p.y + self.pos.y)
    }
}
```

**验证**:写测试,验证 roundtrip identity。还要验证特定旋转下的结果——比如 angle=π/2 时,世界 (10, 0) 应该出现在屏幕的 (0, 10)(90度逆时针旋转)。

**注意**:旋转和缩放的顺序不能反。矩阵乘法不满足交换律:`A*B ≠ B*A`。如果你先 scale 再 rotate,结果和先 rotate 再 scale 不同。Casey 在 HH 里特别强调这一点。

        }
    }

    pub fn world_to_screen(&self, world: Vec2) -> Vec2 {
        Vec2 {
            x: (world.x - self.pos.x) * self.zoom + self.screen_size.x / 2.0,
            y: (world.y - self.pos.y) * self.zoom + self.screen_size.y / 2.0,
        }
    }

    pub fn screen_to_world(&self, screen: Vec2) -> Vec2 {
        Vec2 {
            x: (screen.x - self.screen_size.x / 2.0) / self.zoom + self.pos.x,
            y: (screen.y - self.screen_size.y / 2.0) / self.zoom + self.pos.y,
        }
    }
}

fn main() {
    let cam = Camera::new(
        Vec2::new(100.0, 100.0),
        2.0,
        Vec2::new(1280.0, 720.0),
    );

    // 模拟 entity 列表
    let entities = [
        ("player",   Vec2::new(100.0, 100.0)),
        ("enemy1",   Vec2::new(150.0, 100.0)),
        ("enemy2",   Vec2::new(200.0, 150.0)),
        ("npc",      Vec2::new(80.0,  90.0)),
    ];

    // 渲染:每个 entity 算屏幕位置
    println!("=== Render (world -> screen) ===");
    for (name, world) in &entities {
        let screen = cam.world_to_screen(*world);
        println!("  {} at world {:?} -> screen ({:.0}, {:.0})",
                 name, world, screen.x, screen.y);
    }

    // 模拟鼠标点击
    let mouse_screen = Vec2::new(680.0, 360.0);
    let mouse_world = cam.screen_to_world(mouse_screen);
    println!("\n=== Mouse pick ===");
    println!("  Mouse at screen ({:.0}, {:.0}) -> world ({:.1}, {:.1})",
             mouse_screen.x, mouse_screen.y, mouse_world.x, mouse_world.y);

    // 找最近的 entity(简化版 picking)
    let mut nearest: Option<(&str, f32)> = None;
    for (name, world) in &entities {
        let dx = world.x - mouse_world.x;
        let dy = world.y - mouse_world.y;
        let dist = (dx * dx + dy * dy).sqrt();
        if nearest.map(|(_, d)| dist < d).unwrap_or(true) {
            nearest = Some((*name, dist));
        }
    }
    if let Some((name, dist)) = nearest {
        println!("  Nearest entity: {} (distance: {:.2} world units)", name, dist);
    }
}

### 8.3 Troubleshooting

**问题1**:鼠标点击位置和实体位置不一致。
原因:y 轴方向反——屏幕 y 向下,世界 y 可能向上。
诊断:点击屏幕顶部,看世界 y 是正还是负。
修复:反投影时翻 y:`world.y = (screen_size.y - screen.y) / zoom + camera.y`。

**问题2**:zoom 改变后,鼠标命中位置偏移。
原因:zoom 的中心不是相机中心。比如鼠标在屏幕边缘,zoom 改变后那个边缘对应的世界位置变了。
修复:zoom 时保持鼠标位置不变——`mouse_world_before` 和 `mouse_world_after` 算出 camera.pos 的补偿。

```rust
let mouse_world_before = camera.screen_to_world(mouse.pos);
camera.set_zoom(new_zoom);
let mouse_world_after = camera.screen_to_world(mouse.pos);
camera.pos.x += mouse_world_before.x - mouse_world_after.x;
camera.pos.y += mouse_world_before.y - mouse_world_after.y;
```

这是 RTS / 地图应用的标准 zoom-to-cursor 实现。

**问题3**:高 DPI 屏幕上反投影偏差。
原因:鼠标坐标是 logical pixels,屏幕渲染用 physical pixels。
诊断:`window.scale_factor()`,如果是 2.0 说明是 retina。
修复:统一到 physical 坐标:`let physical_mouse = logical_mouse * scale;`。

**问题4**:NaN 污染。
原因:zoom=0 或 NaN 进入反投影。
诊断:assert `camera.zoom.is_finite()`,如果 panic 说明有 bug。
修复:clamp zoom;检查所有可能产生 NaN 的运算(0/0, ∞-∞, sqrt(负数))。

**问题5**:窗口非全屏,反投影偏差窗口位置。
原因:鼠标坐标相对桌面,但游戏窗口在桌面的某位置。
修复:减去窗口位置:`let mouse_in_window = mouse - window_pos;`。

### 8.4 性能基线

反投影性能:

| 操作 | 时间 |
|---|---|
| screen_to_world | ~10 ns |
| world_to_screen | ~10 ns |
| 3D unproject (with matrix inverse) | ~50 ns |
| Ray-AABB intersection | ~30 ns |
| Ray-triangle intersection | ~50 ns |

60 FPS 下,鼠标反投影每帧一次,10 ns 完全不是瓶颈。但如果做"鼠标拖动选择框,实时高亮框内所有 entity",要 N 次反投影——N=1000 时 10μs,仍然可忽略。
