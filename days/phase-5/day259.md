# Day 259 · OpenGL 与软件渲染器清理

> Day 235 你接了 OpenGL,Day 236-256 把 sprite / bitmap / 字体 / gamma 一个一个迁到 GPU。今天 Casey 看着自己代码,发现软件渲染器还留着、GL 路径里有重复、API 边界不齐整 —— 这一天不动功能,只动结构:把两条路径梳理干净,留一条可切换的"backend 抽象",为 Day 260 profiler 下钻和 Phase 5 收尾做准备。

## 0 · 为什么要有这一天

迁移完成不等于"做完"。一个能跑的代码库,跟一个**经得起后续开发**的代码库,中间隔着一次"清理"。Casey 在 Day 259 给我们示范了一次教科书级别的清理 —— 它不增加任何功能,但每个改动都在为后续 100 天铺路。

具体看 Casey 面临的真实问题:

1. **软件渲染器(softbuffer 路径)还活着** —— 但项目用 OpenGL 已经几周了,软渲染代码沦为"没人测试的化石",一旦哪天 GL 出 bug 想退回软渲染,大概率根本跑不起来。
2. **GL 后端里有重复代码** —— 上传 texture、设置 blend、blit framebuffer,每个 helper 各写一份,改一处要改 5 处。
3. **接口签名不齐** —— 软渲染器用 `push_bitmap(x, y, w, h, *u32)`,GL 路径用 `push_textured_quad(...)`,两条路径调用方式不同,改起来要在 game 层到处分支。
4. **gamma 修正没统一** —— Day 256 才发现 GL blit 没有 sRGB 转换导致颜色偏暗,这类问题反复出现说明"色彩管线"没收敛到一处。
5. **dead code 多** —— 软渲染时为性能写的 SIMD blitter、mipmap 生成器,GL 路径下根本用不上,但还在编译。

**为什么这件事重要**:迁移完成后立即清理,是软件工程里"第二次设计"的时机。第一次设计是写代码时凭直觉搭架子;迁移完回头看,你对系统的真实需求有了实证数据,可以基于真实使用重做架构。Casey 这次清理是 HH 全剧少有的"纯结构日" —— 没新功能,但每个改动都让后续开发更快。

从 Rust 学习者角度,这一天还示范了几个 Rust 特有的清理动作:
- **删除 feature flag 不再需要的分支**(条件编译清理)
- **统一 trait object**(把 soft / GL 两个 renderer 抽象成同一 trait)
- **借用检查器友好**的 API 设计(避免重复借用 framebuffer)

**心理锚点**:清理后你能在 `Cargo.toml` 里把 `--features software_renderer` 打开,跑同一段游戏代码,无需改任何 game 层逻辑,渲染路径自动切回软渲染。这是"backend 抽象"的标志 —— 切换后端 = 翻一个开关。

## 1 · Casey 今天做了什么

Casey 全程在 refactor,不动功能:

1. **审视软渲染器**:列出还有哪些函数被 game 层调,哪些没人调;没人调的全删
2. **审视 GL 后端**:把 GL 的 helper(纹理上传、blend 设置、clear)合并成一个 `OpenGLBackend` struct,统一状态管理
3. **统一 API**:让两条路径接受同样的调用 —— `push_bitmap` / `push_textured_quad` 合并成 `Renderer::draw(...)`,内部根据 `enum Backend { Software, OpenGL }` 分派
4. **统一 gamma**:在 `Renderer` 层做 sRGB ↔ linear 转换,不分散在 backend 里
5. **删除 dead code**:SIMD blitter、手写 mipmap、调试用的 RAW 图片加载 —— 全删
6. **`cargo check` 反复确认**:每删一段代码就 build,确保 game 层不破

**关键决策**:**保留软渲染路径**。Casey 没删软件渲染器,只是把它"折叠"到统一接口后面。理由是有些机器(虚拟机 / 远程 X11 / 老 GPU)GL 不可靠,有个软件 fallback 是工程保险。

**Casey 没做的事**:没把 backend 做成运行时可切换的插件。两条路径在编译期通过 `cfg` 选,运行时切不开。这是务实的 —— 运行时切 backend 会拖 API 设计,得不偿失。

## 2 · 心智模型

### 类比:两条产线,一道总装

想象一个工厂有两条生产线:一条手工(软件渲染,慢但确定),一条自动(GL,快但偶尔抽风)。两条线最终都产出"屏幕像素",但工序、机器、节奏完全不同。

清理前:客户(game 层)要分别跟两条线对接,订单格式都不一样。换线要重新签合同。
清理后:工厂设一个"总装车间"(`Renderer` trait),客户只跟总装对接,内部根据订单类型自动派给合适产线。客户不关心走哪条线,只看成品。

这个总装车间就是 **renderer abstraction**。HH 的版本极简,但思想清晰。

### 2.1 backend 抽象的本质

抽象的关键不是"做得漂亮",而是**定义清楚责任边界**。Casey 的 `Renderer` 接口就承担三件事:

1. **生命周期管理**:`new(width, height)` / `resize(w, h)` / `present()`
2. **资源上传**:`upload_texture(id, pixels, w, h)` / `free_texture(id)`
3. **绘制指令**:`clear(color)` / `draw_bitmap(x, y, w, h, pixels)` / `draw_text(...)`

三件事任何 backend 都得会,但每件事内部实现可以完全不同。这就是"接口与实现分离" —— 一个 OOP / trait 的教科书例子,但 Casey 用 C 函数指针表实现,Rust 用 trait + enum dispatch 更自然。

### 2.2 Rust trait dispatch 两种风格

Rust 表达"同一接口多个实现"有两种主流风格:

**风格 A:动态分发(trait object,`dyn Renderer`)**

```rust
pub trait Renderer {
    fn clear(&mut self, color: [f32; 4]);
    fn draw_bitmap(&mut self, x: i32, y: i32, w: u32, h: u32, pixels: &[u32]);
    fn present(&mut self);
}

pub struct SoftwareRenderer { /* ... */ }
pub struct OpenGLRenderer { /* ... */ }

impl Renderer for SoftwareRenderer { /* ... */ }
impl Renderer for OpenGLRenderer { /* ... */ }

// 用
let renderer: Box<dyn Renderer> = if use_gl {
    Box::new(OpenGLRenderer::new())
} else {
    Box::new(SoftwareRenderer::new())
};
renderer.draw_bitmap(...);  // 动态分派
```

**风格 B:enum dispatch(静态分发)**

```rust
pub enum Backend {
    Software(SoftwareRenderer),
    OpenGL(OpenGLRenderer),
}

impl Backend {
    pub fn draw_bitmap(&mut self, x: i32, y: i32, w: u32, h: u32, pixels: &[u32]) {
        match self {
            Backend::Software(r) => r.draw_bitmap(x, y, w, h, pixels),
            Backend::OpenGL(r) => r.draw_bitmap(x, y, w, h, pixels),
        }
    }
}
```

**两者对比**:

| | `dyn Trait` | enum dispatch |
|---|---|---|
| 性能 | 间接调用(vtable),稍慢 | 内联可能,稍快 |
| 扩展 | 加 impl 即可,无破坏 | 加 variant 要改所有 match |
| API 友好 | 灵活 | 显式 |
| 编译期检查 | 弱(动态) | 强(穷尽 match) |

Casey 在 C 里用函数指针表(类似 dyn Trait)。在 Rust 里,**enum dispatch 更适合固定 backend 集合**(你就两个,不会变)。HH 在 Rust 端推荐 enum dispatch。

### 2.3 gamma / 色彩空间统一

Day 256 的 bug:**软渲染输出的像素看起来正常,GL 输出偏暗**。原因是软渲染直接写 sRGB framebuffer,而 GL 默认 linear framebuffer + shader 输出 linear,没有 sRGB 转换就偏暗。

清理前,gamma 修正散落在各 backend:

```
SoftwareRenderer: 没做(本来就 sRGB)
OpenGLRenderer: shader 里手动 pow(color, 1/2.2)
Blit: GL_FRAMEBUFFER_SRGB 没启用
```

清理后,gamma 收敛到一处:

```rust
pub trait Renderer {
    /// pixels 输入是 **linear RGBA**(浮点),backend 负责转 sRGB 输出
    fn draw_bitmap_linear(&mut self, x: i32, y: i32, w: u32, h: u32, pixels: &[f32]);
}
```

两个 backend 都接受 linear 输入,各自负责转 sRGB:

- 软渲染:CPU 端 `to_srgb(linear)` 写入 framebuffer
- GL:启用 `GL_FRAMEBUFFER_SRGB`,驱动自动转

API 层统一,bug 自然消失。

### 2.4 dead code 识别

Casey 删代码靠三个信号:

1. **`#[allow(dead_code)]` 多了** —— 编译器已经告诉你哪些没被调
2. **grep 调用点没结果** —— `grep -rn "old_blitter" src/` 空
3. **测试覆盖为 0** —— 测试里都不出现的代码,大概率真没人用

Rust 的 `cargo` 工具链对此很友好:

```bash
cargo check 2>&1 | grep "never used"
cargo +nightly udeps  # 第三方工具,cargo-udeps,找未使用依赖
cargo machete         # 找未使用 Cargo.toml 依赖
```

### 2.5 接口收敛的标志

怎么知道清理"够了"?三个标志:

1. **game 层没 `if backend == GL` 分支** —— 后端切换不影响 game 代码
2. **每个 backend 文件独立** —— `software.rs` 不 `use crate::opengl::*`
3. **新增 backend 成本 < 200 行** —— 假设要加 Vulkan backend,只需要实现 trait,不动 game 层

达到这三条,backend 抽象就立住了。Casey 的 Day 259 目标就是这个。

---

**总结**:Day 259 是迁移后的"打扫战场"。Casey 把软渲染器和 GL 后端统一到 `Renderer` 抽象,删除 dead code,把 gamma 收敛到一处。Rust 端推荐用 enum dispatch(固定两个 backend)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏引擎都有"渲染后端抽象"。看几个对照:

- **SDL2 Renderer**:软件 / OpenGL / Direct3D / Metal 后端,运行时选 `SDL_CreateRenderer(window, -1, flags)`,flags 决定走哪个
- **bgfx**:跨平台渲染库,把 GL / Vulkan / Metal / D3D 全抽象,接口统一
- **Unreal RHI(Render Hardware Interface)**:抽象层,下游有 VulkanRHI / DirectX12RHI 等
- **wgpu**:Rust 生态主流,把 Vulkan / Metal / DX12 / GL / WebGPU 抽象成统一 API

**为什么大型引擎都做这层抽象**:跨平台 + 跨硬件。HH 是单平台教学,但 Casey 也做了一层 —— 因为软件 vs GPU 是天然的"两种硬件",值得抽象。

**抽象的代价**:抽象泄漏。GL 有些功能(VBO、shader)软渲染没有,反之亦然。抽象时要么:
- **取交集**(只暴露两边都有的功能,简单但限制)
- **加上 capability query**(`if backend.supports_shaders() { ... }`,灵活但复杂)

Casey 选交集,因为 HH 的渲染需求简单。商业引擎选 capability query,因为要榨干每种硬件。

### 3.2 · 🎨 图形学视角

**色彩空间是清理的重点**。图形学里"linear 工作流"是黄金准则:

1. **加载 texture**:文件 sRGB → 解码时转 linear(`pow(c, 2.2)`)
2. **shader 计算**(光照、混合):**全程在 linear 空间**(物理正确)
3. **输出 framebuffer**:linear → sRGB(`pow(c, 1/2.2)`)给显示器

中间任何一步跳过转换,颜色就不对。Day 256 的 bug 就是 step 3 缺了转换。

GL 提供两个工具自动化:

- **`GL_SRGB8_ALPHA8` 内部格式**:texture 上传时驱动自动 sRGB→linear
- **`GL_FRAMEBUFFER_SRGB`**:开启后 `glBlitFramebuffer` / shader 输出自动 linear→sRGB

软渲染没这两个工具,要在 CPU 端手算 `pow`。Casey 用 LUT(查找表)加速:256 项 linear→sRGB 查找表,避免每个像素 `pow`。

**清理时统一策略**:`Renderer` 接受 linear f32,backend 自行转 sRGB。这样上层写一遍 shader 公式适用所有 backend。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上 GL 后端常见两种实现:

- **desktop GL**(GLX,通过 X11 / Xwayland):`glxinfo` 看版本
- **EGL**(Wayland / 嵌入式):更现代,跨平台

```
# 查看 GL 版本和能力
glxinfo | grep "OpenGL version"
# OpenGL version string: 4.6 (Compatibility Profile) Mesa 23.1

# 查看是否支持 sRGB framebuffer
glxinfo | grep -i srgb
# GLX frame buffer configurations ... sRGB capable
```

软件渲染在 Linux 上常用:

- **XShm**(X11 共享内存扩展):避免 client→server 像素拷贝
- **DRM dumb buffer**:直接显示,无窗口系统
- **softbuffer crate**:HH 用的,封装跨平台

清理时,软件后端通常保留 `softbuffer` 路径,GL 后端用 `glutin` / `winit + glow`。两条路径共享 `winit` 窗口,只是绘图方式不同。

**Linux 调试工具**:

```bash
# 检查 X11 连接
xdpyinfo | grep "number of screens"

# 看进程的 GPU 上下文
cat /proc/$(pgrep game)/maps | grep -E "nvidia|mesa|dri"
```

### 3.4 · 🦀 Rust 生态视角

Rust 生态里 renderer 抽象的几种实现:

**方案 A:trait + dyn**

```rust
pub trait Renderer: Send {
    fn clear(&mut self, color: [f32; 4]);
    fn present(&mut self);
}

pub struct GlRenderer { /* ... */ }
pub struct SoftwareRenderer { /* ... */ }

impl Renderer for GlRenderer { /* ... */ }
impl Renderer for SoftwareRenderer { /* ... */ }

fn make_renderer(use_gl: bool) -> Box<dyn Renderer> {
    if use_gl { Box::new(GlRenderer::new()) }
    else { Box::new(SoftwareRenderer::new()) }
}
```

**方案 B:enum dispatch**

```rust
pub enum Renderer {
    Gl(GlRenderer),
    Software(SoftwareRenderer),
}

impl Renderer {
    pub fn clear(&mut self, color: [f32; 4]) {
        match self {
            Self::Gl(r) => r.clear(color),
            Self::Software(r) => r.clear(color),
        }
    }
}
```

**方案 C:generic + trait bound**

```rust
pub struct Game<R: Renderer> { renderer: R }

impl<R: Renderer> Game<R> {
    pub fn new(renderer: R) -> Self { Self { renderer } }
    pub fn update(&mut self) { self.renderer.clear([0., 0., 0., 1.]); }
}

// 编译期确定 backend,无运行时开销
let game = Game::new(GlRenderer::new());
```

方案 C 性能最好(完全静态分发,可内联),但泛型会"传染"—— 所有持有 `Game<R>` 的类型都得加 `<R>` 参数。Casey 在 C 里不可能用泛型,会选 A(函数指针)。Rust 实战推荐:

- **小项目、固定 backend**:enum dispatch(B)
- **大项目、扩展性强**:trait object(A)
- **极致性能**:generic(C),但要付出泛型传染代价

## 4 · 认知地图

### 4.1 上级

- **Backend 抽象** —— 把实现差异封装在统一接口后
- **重构(refactor)** —— 不动功能,只动结构
- **接口设计** —— 责任边界清晰、最小暴露

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| trait object (`dyn Trait`) | 动态分发、可扩展 | 多种实现、运行时切 | HH C 用函数指针表(等价) |
| enum dispatch | 静态分发、穷尽匹配 | 固定集合的 backend | Rust 端推荐 |
| generic `<R: Trait>` | 零开销、泛型传染 | 性能极致 | 不推荐(传染) |
| 编译期 `cfg` 选一 | 二选一,不共存 | 单平台目标 | HH 实际选(双轨保留) |

## 5 · 对照与变奏

### 商业引擎的 renderer 抽象尺度

| 引擎 | 抽象层名 | 后端数 | 抽象尺度 |
|---|---|---|---|
| HH | (无正式名) | 2 | 极简 |
| SDL2 | SDL_Renderer | 6+ | 中等 |
| bgfx | bgfx | 12+ | 大 |
| Unreal | RHI | 5+ | 大 |
| wgpu | wgpu | 5+ | 大 |

HH 抽象尺度小但够用。商业引擎抽象尺度大但复杂。

### 删除 vs 保留软渲染

| 立场 | 理由 | 反驳 |
|---|---|---|
| 删软渲染 | 死代码,降低维护 | 远程 X11 / VM 没 GL |
| 保留软渲染 | fallback | 维护成本 |

Casey 选保留,理由是 HH 强调"可移植性 + 调试性",软渲染在 GPU 出 bug 时是救命稻草。

### 同一抽象在 CPU / GPU 的不同表达

- **CPU 端(软渲染)**:函数指针 + struct 上下文
- **GPU 端(GL)**:shader + buffer object
- **抽象层**:把"调用函数"和"上传 buffer + 设 shader uniform"统一成 `draw_bitmap(x, y, w, h, pixels)`

这种"指令层抽象"跟驱动模型类似 —— CPU 给命令,GPU 执行,中间隔一层 IR(IR 在 GL 里是 GLSL,在 Vulkan 里是 SPIR-V)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 选择"保留软渲染路径"而不是直接删除?说出至少两个具体场景。

**参考解答**:

1. **远程显示场景**:SSH X11 转发 / VNC / 远程桌面,服务器端可能没 GPU 或 GL 加速不可靠。软渲染能在 CPU 上跑,显示延迟但能跑。
2. **虚拟机 / 容器**:Docker 内 GL 通常不可用(没 GPU 直通),软渲染 fallback。
3. **调试场景**:GL 行为异常时(颜色错 / 黑屏),切软渲染能立刻判断是 game 层 bug 还是 GL 层 bug。这是个强大的诊断工具。
4. **CI / 自动化测试**:headless 环境跑截图对比,软渲染确定性更好。

### Lv2 · 动手实践

**题**:用 enum dispatch 实现一个最小 renderer 抽象,有两个 backend:`Console`(在终端打印 ASCII)和 `Image`(写到 PNG 文件)。两者实现 trait `Renderer { fn draw_pixel(x, y, c); fn present(); }`。完成标准:写一个 game loop,根据 `--features console` 或 `--features image` 切换 backend,无需改 game 层代码。

**参考解答**:

```rust
// src/renderer.rs
pub trait Renderer {
    fn draw_pixel(&mut self, x: u32, y: u32, c: u8);  // 0-255 灰度
    fn present(&mut self);
}

pub struct ConsoleRenderer {
    width: u32,
    height: u32,
    buf: Vec<u8>,
}

impl ConsoleRenderer {
    pub fn new(w: u32, h: u32) -> Self {
        Self { width: w, height: h, buf: vec![0; (w * h) as usize] }
    }
}

impl Renderer for ConsoleRenderer {
    fn draw_pixel(&mut self, x: u32, y: u32, c: u8) {
        if x < self.width && y < self.height {
            self.buf[(y * self.width + x) as usize] = c;
        }
    }

    fn present(&mut self) {
        let chars = b" .:-=+*#%@";
        for y in 0..self.height {
            for x in 0..self.width {
                let v = self.buf[(y * self.width + x) as usize];
                let idx = (v as usize * chars.len()) / 256;
                print!("{}", chars[idx] as char);
            }
            println!();
        }
    }
}

pub struct ImageRenderer {
    width: u32,
    height: u32,
    buf: Vec<u8>,
    path: String,
}

impl ImageRenderer {
    pub fn new(w: u32, h: u32, path: &str) -> Self {
        Self { width: w, height: h, buf: vec![0; (w * h) as usize], path: path.into() }
    }
}

impl Renderer for ImageRenderer {
    fn draw_pixel(&mut self, x: u32, y: u32, c: u8) {
        if x < self.width && y < self.height {
            self.buf[(y * self.width + x) as usize] = c;
        }
    }

    fn present(&mut self) {
        // 简化:写 PGM(ASCII 灰度图)格式,无需依赖
        std::fs::write(&self.path, format!("P2\n{} {}\n255\n", self.width, self.height)).unwrap();
        // (省略实际写入像素,读者可补全)
    }
}

// game 层
fn game_loop<R: Renderer>(r: &mut R) {
    for y in 0..24 {
        for x in 0..80 {
            r.draw_pixel(x, y, ((x + y) % 256) as u8);
        }
    }
    r.present();
}

fn main() {
    #[cfg(feature = "image")]
    let mut r = ImageRenderer::new(80, 24, "out.pgm");
    #[cfg(not(feature = "image"))]
    let mut r = ConsoleRenderer::new(80, 24);

    game_loop(&mut r);
}
```

```rust
// src/renderer/software.rs
use super::Renderer;

pub struct SoftwareRenderer {
    width: u32,
    height: u32,
    framebuffer: Vec<u32>,  // sRGB packed RGBA
    textures: std::collections::HashMap<u32, Vec<u32>>,  // id → pixels
    next_id: u32,
}

impl SoftwareRenderer {
    pub fn new(w: u32, h: u32) -> Self {
        Self {
            width: w,
            height: h,
            framebuffer: vec![0; (w * h) as usize],
            textures: Default::default(),
            next_id: 1,
        }
    }

    /// linear → sRGB 查找表(256 项)
    fn linear_to_srgb_lut() -> &'static [u32; 256] {
        static LUT: std::sync::OnceLock<[u32; 256]> = std::sync::OnceLock::new();
        LUT.get_or_init(|| {
            let mut t = [0u32; 256];
            for (i, slot) in t.iter_mut().enumerate() {
                let lin = i as f32 / 255.0;
                let srgb = lin.powf(1.0 / 2.2);  // 近似 sRGB 曲线
                *slot = (srgb * 255.0) as u32;
            }
            t
        })
    }
}

impl Renderer for SoftwareRenderer {
    fn clear(&mut self, color: [f32; 4]) {
        let [r, g, b, _a] = color;
        // linear → sRGB
        let lut = Self::linear_to_srgb_lut();
        let r8 = lut[(r * 255.0) as usize];
        let g8 = lut[(g * 255.0) as usize];
        let b8 = lut[(b * 255.0) as usize];
        let packed = (255 << 24) | (b8 << 16) | (g8 << 8) | r8;
        self.framebuffer.fill(packed);
    }

    fn upload_texture(&mut self, w: u32, h: u32, pixels: &[u8]) -> u32 {
        assert_eq!(pixels.len(), (w * h * 4) as usize);
        let id = self.next_id;
        self.next_id += 1;
        let mut buf = vec![0u32; (w * h) as usize];
        for (i, chunk) in pixels.chunks(4).enumerate() {
            buf[i] = (chunk[3] as u32) << 24
                  | (chunk[2] as u32) << 16
                  | (chunk[1] as u32) << 8
                  | (chunk[0] as u32);
        }
        self.textures.insert(id, buf);
        id
    }

    fn free_texture(&mut self, id: u32) { self.textures.remove(&id); }

    fn draw_bitmap(&mut self, x: i32, y: i32, _id: u32) {
        // 简化:实际要从 textures 取像素,blit 到 framebuffer
        let _ = (x, y);
    }

    fn present(&mut self) {
        // 实际:把 framebuffer 拷给 softbuffer surface
    }

    fn resize(&mut self, w: u32, h: u32) {
        self.width = w;
        self.height = h;
        self.framebuffer.resize((w * h) as usize, 0);
    }
}
```

```rust
use super::Renderer;
use glow::HasContext;

pub struct OpenGLRenderer {
    gl: glow::Context,
    width: u32,
    height: u32,
    textures: std::collections::HashMap<u32, glow::Texture>,
    next_id: u32,
}

impl OpenGLRenderer {
    pub fn new(w: u32, h: u32) -> Result<Self, String> {
        // 实际从 glutin 拿 context
        let gl = unsafe { glow::ContextFromLoader::new(|s| /* get_proc_address */ std::ptr::null()) };
        let gl = unsafe { glow::Context::from_loader_function(|_| std::ptr::null()) };

        // 启用 sRGB framebuffer(Day 256 的 fix)
        unsafe { gl.enable(glow::FRAMEBUFFER_SRGB); }

        Ok(Self {
            gl: unsafe { std::mem::zeroed() },  // 简化:实际用上面的 gl
            width: w,
            height: h,
            textures: Default::default(),
            next_id: 1,
        })
    }
}

impl Renderer for OpenGLRenderer {
    fn clear(&mut self, color: [f32; 4]) {
        // GL 在 linear 空间 clear,FRAMEBUFFER_SRGB 启用后驱动自动转
        unsafe {
            self.gl.clear_color(color[0], color[1], color[2], color[3]);
            self.gl.clear(glow::COLOR_BUFFER_BIT);
        }
    }

    fn upload_texture(&mut self, w: u32, h: u32, pixels: &[u8]) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        unsafe {
            let tex = self.gl.create_texture().unwrap();
            self.gl.bind_texture(glow::TEXTURE_2D, Some(tex));
            // SRGB8_ALPHA8:驱动解码时 sRGB → linear
            self.gl.tex_image_2d(
                glow::TEXTURE_2D, 0, glow::SRGB8_ALPHA8 as i32,
                w as i32, h as i32, 0,
                glow::RGBA, glow::UNSIGNED_BYTE, Some(pixels),
            );
            self.textures.insert(id, tex);
        }
        id
    }

    fn free_texture(&mut self, id: u32) {
        if let Some(tex) = self.textures.remove(&id) {
            unsafe { self.gl.delete_texture(tex); }
        }
    }

    fn draw_bitmap(&mut self, _x: i32, _y: i32, _id: u32) {
        // 实际:bind VAO、bind texture、draw_arrays
    }

    fn present(&mut self) {
        // glutin context.swap_buffers()
    }

    fn resize(&mut self, w: u32, h: u32) {
        self.width = w;
        self.height = h;
        unsafe { self.gl.viewport(0, 0, w as i32, h as i32); }
    }
```

**Troubleshooting**:

- **`OpenGL init failed`** —— 没装 mesa / libgl。`sudo pacman -S mesa`
- **黑屏** —— 检查 `GL_FRAMEBUFFER_SRGB` 是否启用(Day 256 的 fix)
- **软件后端慢** —— release 模式编译,`cargo run --release`
- **`cannot find glow`** —— `cargo add glow`
- **panic on texture upload** —— 检查 pixels 大小是否 `w * h * 4`,不是 `w * h`
