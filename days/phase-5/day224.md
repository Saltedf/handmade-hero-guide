
# Day 224 · 预取过场动画层

> cutscene 的资源(纹理、音频)从磁盘加载要时间。如果不预取,layer 开始时卡顿。今天 casey 加 prefetch:每个 layer 在开始前 N 秒触发资源加载,加载完成后才显示。

## 0 · 为什么要有这一天

cutscene layer 的资源生命周期:

1. **加载**:从磁盘读到内存(几十 ms 到几秒,取决于大小)
2. **使用**:layer 显示期间(几秒到几分钟)
3. **释放**:layer 结束后回收(可选)

如果**用到才加载**(lazy),layer 开始那帧会等加载 → 卡顿 → 用户看到画面停滞。这是经典的"懒加载卡顿"问题。

casey 的方案:**预取(prefetch)**。每个 layer 在 `start_time - prefetch_lead` 时启动加载,等真正 `start_time` 时资源已经就位。

```rust
struct CutsceneLayer {
    start_time: f32,
    duration: f32,
    resource: ResourceId,
    prefetch_lead: f32,  // 提前多少秒加载
}
```

预取是非阻塞的:加载在 worker thread 跑,主线程继续渲染。layer 开始时检查 resource 是否就位,就位则显示,否则跳过(或显示 placeholder)。

心理锚点:看完今天,你能解释"为什么 web 浏览器 preload 静态资源"。

## 1 · Casey 今天做了什么

1. **加 ResourceLoader 后台**:worker thread 异步加载
2. **加 prefetch trigger**:cutscene update 时检查"快开始"的 layer,触发加载
3. **改 render**:layer 渲染前 check 资源状态
4. **加 fallback**:资源没就位时显示 placeholder

## 2 · 心智模型

### 类比:餐厅提前备菜

餐厅菜单上有"烤羊排"(准备 30 分钟)。客人点单后才备,客人等 30 分钟。专业餐厅在客人多时**预判**——晚 7 点高峰前提前备几份,客人点时立刻上。

casey 的 prefetch 是"提前备菜"——layer 开始前提前加载资源,开始时立刻显示。

### 2.1 预取时机

每个 layer 有 `start_time`。预取触发时机:

```
prefetch_trigger_time = layer.start_time - layer.prefetch_lead
```

例如 start_time=10s,prefetch_lead=3s,那 7s 时触发加载。

主循环每帧检查:

```rust
fn update(&mut self, current: f32, loader: &mut ResourceLoader) {
    for ac in &mut self.active {
        let local = current - ac.start_time;
        for layer in &ac.cutscene.layers {
            let trigger_at = layer.start_time - layer.prefetch_lead;
            if local >= trigger_at && !layer.is_loading && !layer.is_loaded {
                loader.load_async(layer.resource);
                layer.is_loading = true;
            }
        }
    }
}
```

### 2.2 异步加载

worker thread 加载:

```rust
use std::sync::mpsc;
use std::thread;

struct ResourceLoader {
    sender: mpsc::Sender<LoadRequest>,
    receiver: mpsc::Receiver<LoadResult>,
    loaded: HashMap<ResourceId, Resource>,
}

impl ResourceLoader {
    fn new() -> Self {
        let (tx_req, rx_req) = mpsc::channel();
        let (tx_res, rx_res) = mpsc::channel();
        thread::spawn(move || {
            for req in rx_req {
                let res = load_from_disk(&req.path);  // 假设函数
                tx_res.send(LoadResult { id: req.id, data: res }).ok();
            }
        });
        Self {
            sender: tx_req,
            receiver: rx_res,
            loaded: HashMap::new(),
        }
    }

    fn load_async(&self, id: ResourceId) {
        self.sender.send(LoadRequest { id, path: path_of(id) }).ok();
    }

    fn poll(&mut self) {
        while let Ok(result) = self.receiver.try_recv() {
            self.loaded.insert(result.id, result.data);
        }
    }

    fn is_loaded(&self, id: ResourceId) -> bool {
        self.loaded.contains_key(&id)
    }
}
```

mpsc = multi-producer single-consumer channel。worker thread 是 producer,主线程是 consumer。

### 2.3 Fallback

如果 layer.start_time 到了但资源没加载完:

```rust
fn sample(&self, t: f32, loader: &ResourceLoader) -> Option<Frame> {
    if t < self.start_time { return None; }
    if t > self.start_time + self.duration { return None; }
    if !loader.is_loaded(self.resource) {
        // 资源没就位
        return Some(self.placeholder_frame);
    }
    Some(self.actual_frame)
}
```

`placeholder_frame` 是 fallback 显示——可能是黑色矩形、loading 图标、上一帧延续。

### 2.4 预取预算

预取不能无限制——内存有限。casey 加预算:

```rust
struct PrefetchBudget {
    max_concurrent_loads: usize,
    current_loads: usize,
}

impl PrefetchBudget {
    fn can_start(&self) -> bool { self.current_loads < self.max_concurrent_loads }
}
```

如果预算满,新预取请求排队。这样避免一次性触发几十个 IO,把磁盘带宽占满。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏资源加载策略:

- **Preload**:游戏启动时全加载。简单但启动慢
- **Lazy**:用到才加载。快启动但卡顿
- **Prefetch**:预测性加载。最优但复杂
- **Streaming**:大世界连续加载(GTA、蜘蛛侠)。最复杂

casey 今天实现 prefetch,Day 270+ 会进化到 streaming。

### 3.2 · Linux 系统编程视角

Linux 内核的 prefetch:

- **readahead**:文件系统预测性读。`posix_fadvise(FADV_WILLNEED)`
- **page cache**:OS 自动缓存最近读过的页
- **swap prefetch**:换出页提前换回

```bash
# Linux readahead
posix_fadvise(fd, 0, 0, POSIX_FADV_WILLNEED);  // 提示内核预读
```

casey 的 prefetch 是用户态版本,思想一致。

### 3.3 · Rust 生态视角

Rust 异步资源加载:

```rust
// Pattern 1:thread + channel(casey 风格)
let (tx, rx) = std::sync::mpsc::channel();
std::thread::spawn(move || {
    let data = std::fs::read(path).unwrap();
    tx.send(data).ok();
});

// Pattern 2:async / await
async fn load(path: &str) -> Vec<u8> {
    tokio::fs::read(path).await.unwrap()
}

// Pattern 3:rayon parallel load
use rayon::prelude::*;
let results: Vec<_> = paths.par_iter().map(load).collect();
```

casey 选 Pattern 1(简单、显式控制)。现代 Rust 推 Pattern 2(tokio 生态),但游戏开发因为延迟敏感、避免 async runtime 复杂,常选 Pattern 1 或 3。

参考 crate:`rayon`、`tokio`、`async-std`。

### 3.4 · 内存管理视角

预取占用内存。如果 layer 1 预取完没立刻用,内存被占。casey 加 LRU:

```rust
struct LruCache<K, V> {
    map: LinkedHashMap<K, V>,
    capacity: usize,
}
```

资源太久没用 → LRU 淘汰。casey 的 cutscene 简单(几个 layer),不必上 LRU,但大游戏必须有。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:prefetch_lead 设太大或太小分别有什么问题?

**参考解答**:太大,资源加载完长期占内存(可能加载完 layer 还没开始,期间不能释放);太小,layer 开始时资源没加载完,显示 placeholder。理想值 = 资源加载时间 + 缓冲。例如加载 1 秒,设 1.5 秒 lead,留 0.5 秒缓冲应对加载抖动。

### Lv2 · 动手实践

**题**:实现 ResourceLoader + prefetch trigger + poll + is_loaded。

**参考解答**:

```rust
use std::collections::HashMap;
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
struct ResId(u32);

struct LoadRequest { id: ResId, fake_data: Vec<u8> }
struct LoadResult { id: ResId, data: Vec<u8> }

struct ResourceLoader {
    sender: mpsc::Sender<LoadRequest>,
    receiver: mpsc::Receiver<LoadResult>,
    loaded: HashMap<ResId, Vec<u8>>,
    pending: HashMap<ResId, bool>,
}

impl ResourceLoader {
    fn new() -> Self {
        let (tx_req, rx_req) = mpsc::channel();
        let (tx_res, rx_res) = mpsc::channel();
        thread::spawn(move || {
            for req in rx_req {
                thread::sleep(Duration::from_millis(50));  // 模拟加载延迟
                tx_res.send(LoadResult { id: req.id, data: req.fake_data }).ok();
            }
        });
        Self { sender: tx_req, receiver: rx_res, loaded: HashMap::new(), pending: HashMap::new() }
    }

    fn load_async(&mut self, id: ResId, data: Vec<u8>) {
        if self.loaded.contains_key(&id) || *self.pending.get(&id).unwrap_or(&false) {
            return;
        }
        self.sender.send(LoadRequest { id, fake_data: data }).ok();
        self.pending.insert(id, true);
    }

    fn poll(&mut self) {
        while let Ok(result) = self.receiver.try_recv() {
            self.loaded.insert(result.id, result.data);
            self.pending.remove(&result.id);
        }
    }

    fn is_loaded(&self, id: ResId) -> bool { self.loaded.contains_key(&id) }
}

fn main() {
    let mut loader = ResourceLoader::new();

    loader.load_async(ResId(1), vec![1, 2, 3]);
    println!("Immediately loaded? {}", loader.is_loaded(ResId(1)));  // false

    thread::sleep(Duration::from_millis(100));
    loader.poll();
    println!("After 100ms? {}", loader.is_loaded(ResId(1)));  // true
}
```

## 10 · 深入:预取的工业级实现

casey 今天讲的"预取 cutscene 层",是 IO 性能优化的核心技术。让我把工业级预取方案的所有变体列出来对比,你会看到 casey 的简化设计如何 scale 到生产规模。

### 10.1 五种预取策略

**策略 1:同步预加载**(casey 今天的方案)

```rust
// cutscene 开始前,加载所有 layer
fn start_cutscene(state: &mut State, template: &CutsceneTemplate) {
    for layer in &template.layers {
        let data = load_asset(&layer.asset_path);  // 阻塞 IO
        state.layer_cache.insert(layer.id, data);
    }
    state.cutscene_state = Playing;
}
```

- 优点:简单,启动后播放无停顿。
- 缺点:启动时卡(loading screen),用户等待。

**策略 2:lazy 按需加载**

```rust
// layer 第一次需要时才加载
fn sample_layer(state: &mut State, layer_id: LayerId, t: f32) -> f32 {
    if !state.layer_cache.contains(&layer_id) {
        let data = load_asset(&state.template.layers[layer_id].asset_path);
        state.layer_cache.insert(layer_id, data);
    }
    state.layer_cache[layer_id].sample(t)
}
```

- 优点:启动快,只用加载必要的。
- 缺点:播放过程中可能卡顿(第一次访问新 layer)。

**策略 3:预测式预取**(casey 今天的核心)

```rust
// 提前 N 帧加载未来要用的 layer
fn update(state: &mut State, dt: f32) {
    state.cutscene_time += dt;
    // 查找未来 5 秒内要访问的 layer
    for layer in &state.template.layers {
        let access_time = layer.first_access_time;
        if access_time > state.cutscene_time && access_time < state.cutscene_time + 5.0 {
            if !state.layer_cache.contains(&layer.id) {
                state.io_queue.push(layer.id);  // 异步加载队列
            }
        }
    }
    process_io_queue(state);  // 处理一部分队列
}
```

- 优点:启动快,播放无卡顿。
- 缺点:需要"未来访问时间"的元数据。casey 的 timeline template 提供这个信息。

**策略 4:background streaming**

```rust
// IO worker thread 一直跑,流式加载
fn io_worker(state: Arc<Mutex<State>>) {
    loop {
        let next_layer = {
            let s = state.lock().unwrap();
            s.io_queue.pop()
        };
        if let Some(layer_id) = next_layer {
            let data = load_asset_blocking(layer_id);
            state.lock().unwrap().layer_cache.insert(layer_id, data);
        } else {
            std::thread::sleep(Duration::from_millis(1));
        }
    }
}
```

- 优点:主线程零阻塞。
- 缺点:多线程同步复杂,共享状态要锁。

**策略 5:memory-mapped IO**

```rust
use memmap2::Mmap;

let file = std::fs::File::open("big_asset.bin")?;
let mmap = unsafe { Mmap::map(&file)? };
// 不实际读,访问时按需 page in
let byte = mmap[1024];  // 触发 page fault, OS 加载
```

- 优点:零代码,OS 自动管理。
- 缺点:page fault 不可预测,可能造成帧卡顿。

### 10.2 casey 的选择:策略 3

casey 选预测式预取,因为:

1. **HH 项目代码简单**:单线程,不用 background worker
2. **timeline 数据已知**:template 里 keyframe 时间清楚,知道未来要什么
3. **IO 量小**:每帧加载一个 layer,~1ms,主线程可承受

如果你的项目要 scale 到几百 MB asset,策略 4(background streaming)是必须。但 casey 的简化设计给教学基础,你看商业引擎的 streaming 系统时能理解其设计。

### 10.3 OS 层预取:Linux readahead

Linux 内核的 readahead 是策略 5 的内核级实现。当检测到顺序读模式,内核自动预读后续 page。

```bash
# 查看 block device 的 readahead 设置
sudo blockdev --getra /dev/sda1
# 输出: 256 (in 512-byte sectors, 即 128 KB)

# 设大 readahead(适合大文件流式读)
sudo blockdev --setra 4096 /dev/sda1
# 现在 readahead = 2 MB
```

应用程序也可以显式提示 OS:

```rust
use std::os::unix::io::AsRawFd;

let file = std::fs::File::open("big.bin")?;
let fd = file.as_raw_fd();
unsafe {
    // POSIX_FADV_WILLNEEWD:告诉内核"我将要读这段"
    libc::posix_fadvise(fd, 0, 0, libc::POSIX_FADV_WILLNEEED);
    // POSIX_FADV_SEQUENTIAL:提示顺序读模式
    libc::posix_fadvise(fd, 0, 0, libc::POSIX_FADV_SEQUENTIAL);
}
```

casey 的 HH 是 Windows 项目(用 CreateFile + ReadFile),但 Rust 翻译版在 Linux 上用 `posix_fadvise` 可以拿到 OS 级预取。

### 10.4 GPU 资源的预取

GPU 资源(texture、buffer)的预取更复杂——加载是两阶段:

1. **CPU 加载**:从磁盘读 RAM
2. **GPU upload**:从 RAM 传到 VRAM

预取要协调两个阶段:

```rust
struct GpuAsset {
    cpu_data: Option<Vec<u8>>,    // RAM 中的原始数据
    gpu_handle: Option<TextureHandle>,  // VRAM 中的纹理
}

fn prefetch(state: &mut State, asset_id: AssetId) {
    let asset = &mut state.assets[asset_id];
    if asset.cpu_data.is_none() {
        asset.cpu_data = Some(load_from_disk(asset_id));  // Stage 1
    }
    if asset.gpu_handle.is_none() {
        let handle = state.gpu.upload_texture(asset.cpu_data.as_ref().unwrap());
        asset.gpu_handle = Some(handle);  // Stage 2
    }
}
```

GPU upload 通常要 ~10ms(大纹理),不能放主循环。casey 在 day243+ 讨论"async texture download"——本质就是 GPU 资源的异步上传。

### 10.5 内存预算与 LRU 驱逐

预取的反面是**驱逐**(eviction)。如果预取太多,内存爆。需要 LRU(最近最少使用)策略。

```rust
use std::collections::HashMap;

struct LruCache<K, V> {
    map: HashMap<K, V>,
    order: Vec<K>,  // 最近用过的在尾部
    capacity: usize,
}

impl<K: Eq + std::hash::Hash + Clone, V> LruCache<K, V> {
    fn access(&mut self, key: &K) -> Option<&V> {
        if let Some(pos) = self.order.iter().position(|k| k == key) {
            self.order.remove(pos);
            self.order.push(key.clone());
            self.map.get(key)
        } else {
            None
        }
    }
    
    fn insert(&mut self, key: K, value: V) {
        if self.map.len() >= self.capacity {
            // 驱逐最老
            if let Some(old) = self.order.first().cloned() {
                self.order.remove(0);
                self.map.remove(&old);
            }
        }
        self.map.insert(key.clone(), value);
        self.order.push(key);
    }
}
```

casey 的简化版无 LRU(假设 cutscene 短,内存够用)。生产项目必须有 LRU——开放世界游戏的 streaming 系统,LRU 是核心。

### 10.6 实战:PS5 / Xbox Series X 的 SSD streaming

次世代主机的 SSD(5-7 GB/s)让预取变得几乎免费:

- **DirectStorage**(Xbox / Windows):绕过 OS IO stack,GPU 直接从 SSD 读
- **PS5 I/O complex**:硬件 decompression,SSD 数据流式解压到 GPU

这些技术让"无限开放世界"成为可能——玩家视野外 100m 的 asset 在 0.01s 内加载,无 loading screen。casey 在 day224 教学版预取是这种高级 streaming 的雏形。

### 10.7 预取失败的回退策略

预取不总是成功——IO 慢、磁盘满、文件损坏。生产系统要有回退:

```rust
fn get_asset(state: &mut State, id: AssetId) -> &Asset {
    if state.cache.contains(&id) {
        return &state.cache[id];  // 预取成功
    }
    // 回退 1:同步加载(可能卡 1 帧)
    if let Ok(data) = load_from_disk(id) {
        state.cache.insert(id, data);
        return &state.cache[id];
    }
    // 回退 2:用 placeholder
    return &state.placeholder;
}
```

casey 的简化版假设预取总是成功,但生产系统必须 graceful degrade。

### 10.8 性能度量:预取的命中率

判断预取系统好坏,关键指标是**命中率**(hit rate):

```rust
struct PrefetchStats {
    hits: u64,    // 预取的数据被用到
    misses: u64,  // 预取的数据被驱逐前没用
    forced_loads: u64,  // 未预取,被迫同步加载
}

impl PrefetchStats {
    fn hit_rate(&self) -> f32 {
        let total = self.hits + self.misses;
        if total == 0 { 0.0 } else { self.hits as f32 / total as f32 }
    }
}
```

理想:hit_rate > 95%,forced_loads 接近 0。casey 的 HH 项目目标 hit_rate 90%+。商业游戏 streaming 系统要求 99%+。

debug UI 显示这些指标,casey 反复强调"measure before optimize"。预取调优完全靠数据驱动——盲目加预取反而增加 IO 压力,降低性能。

### 10.9 多线程预取的实现模式

Rust 多线程预取的常见模式:

**模式 A:专用 IO 线程 + 任务队列**

```rust
use std::sync::mpsc;

struct IoRequest(AssetId);
struct IoResponse(AssetId, AssetData);

let (req_tx, req_rx) = mpsc::channel::<IoRequest>();
let (resp_tx, resp_rx) = mpsc::channel::<IoResponse>();

// IO worker
std::thread::spawn(move || {
    while let Ok(IoRequest(id)) = req_rx.recv() {
        if let Ok(data) = load_from_disk(id) {
            resp_tx.send(IoResponse(id, data)).unwrap();
        }
    }
});

// 主线程请求
req_tx.send(IoRequest(asset_id)).unwrap();

// 主线程 update 时检查响应
while let Ok(IoResponse(id, data)) = resp_rx.try_recv() {
    cache.insert(id, data);
}
```

**模式 B:async / await**

```rust
use tokio::{fs, task};

async fn prefetch(asset_id: AssetId) -> AssetData {
    let data = fs::read(format!("assets/{}.bin", asset_id)).await.unwrap();
    AssetData::from_bytes(&data)
}

// spawn 多个 prefetch 并发
let tasks: Vec<_> = asset_ids.iter()
    .map(|&id| task::spawn(prefetch(id)))
    .collect();
for task in tasks {
    let data = task.await.unwrap();
    cache.insert(data.id, data);
}
```

**模式 C:rayon parallel iterator**(适合 batch loading)

```rust
use rayon::prelude::*;

let loaded: Vec<AssetData> = asset_ids.par_iter()
    .map(|&id| load_from_disk(id).unwrap())
    .collect();
```

casey 单线程,但 Rust 翻译版可以根据场景选模式。IO 密集选 A 或 B,CPU 密集选 C。

### 10.10 工程教训:IO 优化的优先级

casey Day 224 的核心工程教训:**IO 优化按优先级**:

1. **减少 IO 量**(数据压缩、合并文件)— 一次加载更少字节
2. **批量化**(一次读多个)— 减少 syscall 次数
3. **预取**(提前加载)— 减少 stall
4. **缓存**(已读数据留 RAM)— 避免重复 IO
5. **并行**(多线程 / async)— 隐藏延迟

按顺序优化。如果 step 1-2 没做好,step 3-5 效果有限。casey 的 HH 项目主要在 step 3-4,因为 IO 量已经很小。大型项目(开放世界)必须从 step 1 开始优化。

### 10.11 真实世界的预取 bug

预取系统实战中容易出现的 bug:

**Bug 1:预取顺序错误**。预取队列 FIFO,但实际访问顺序乱序,导致刚驱逐的又被加载。

修复:用 priority queue,按"未来访问时间"排序,而不是 FIFO。

**Bug 2:预取抢主线程 IO**。预取 IO 太多,主线程同步 IO 阻塞。

修复:预取 IO 限速(每帧最多 N MB),或单独 IO 线程。

**Bug 3:预取的 layer 在播放前被 LRU 驱逐**。预取太早,内存压力大时被驱逐。

修复:用 "pinned" cache——预取的资源标记为不可驱逐,直到访问过一次。

**Bug 4:磁盘碎片导致预取慢**。HDD 上,预取多个文件时磁头跳跃,IO 慢。

修复:把 asset 打包成单个 .pak 文件(Idtech / Unreal 的 .uasset),顺序读单文件。

**Bug 5:SSD read-ahead 失效**。SSD 没有"物理位置"概念,readahead 行为不同。Linux NVMe driver 用 logical block 预取,可能误判。

修复:对 SSD 用更大的 readahead,或者完全跳过 readahead(纯应用层预取)。

casey 的 HH 项目这些 bug 都遇到过(他在视频里 debug 过)。学完 day224 的基础,你看 casey 后续修 bug 的视频能秒懂。

### 10.12 跨平台预取

不同平台的 IO 性能差异巨大,预取策略要适配:

- **Windows**:CreateFileW + ReadFile,可用 OVERLAPPED 异步 IO
- **Linux**:open + read,可用 io_uring(Linux 5.1+)或 epoll
- **macOS**:dispatch_io,GCD 风格异步
- **WebAssembly**:fetch API,异步必然
- **Mobile**:闪存 + 电池预算,IO 量受限

Rust 跨平台预取库:

- **tokio**:跨平台 async IO
- **async-std**:类似 tokio,API 不同
- **smol**:轻量 async runtime
- **glommio**:Linux io_uring 优先

casey 的 HH Windows 版用 Win32 API,Rust 翻译版推荐用 tokio 跨平台。

### 10.13 教学总结

day224 的核心要点:

1. **预取是 IO 优化核心**:从同步 IO(loading screen)演化到预测式预取(无感加载)
2. **数据驱动**:预取决策基于"未来访问时间",来自 timeline template
3. **测量优先**:hit rate 是关键指标,优化前先度量
4. **LRU 必需**:预取配套 LRU 驱逐,避免内存爆炸
5. **跨平台适配**:OS 提供 readahead / fadvise,应用层补充业务逻辑

casey 给教学基础,生产项目按这个模式 scale 到 GB 级 streaming。

### 10.14 真实数字:IO 性能基准

实测常见存储设备的 IO 性能:

```
存储设备         顺序读       随机读       适用场景
HDD 5400 RPM     100 MB/s     0.5 MB/s    归档,不推荐
HDD 7200 RPM     150 MB/s     1 MB/s     预算桌面
SATA SSD         550 MB/s     50 MB/s    桌面主流
NVMe SSD         7000 MB/s    500 MB/s   高端桌面
PS5 SSD          9000 MB/s    5500 MB/s  次世代主机
RAM              50000 MB/s   10000 MB/s 任何场景
L1 cache         1 TB/s       500 GB/s   CPU 内部
```

预取策略要匹配设备:

- HDD:必须大块预取(几 MB),减少 seek
- SATA SSD:小块预取(几十 KB)就够,random IO 不太慢
- NVMe:几乎不需要预取,random IO 也极快
- PS5:数据驱动 streaming,asset 直接从 SSD 到 GPU

casey 的 HH 项目假设 SATA SSD 以上,预取策略简单。开发新游戏要考虑最低配置(HDD?),决定预取激进程度。

这个表是任何 IO 优化决策的基础。casey 在 HH 里也用类似数据来决定 IO 量级。
