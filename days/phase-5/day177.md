# Day 177 · 自动性能计数器

> Day 176 把蓝图讲完了,今天 Casey 把第一块零件装上:**自动 cycle 计数**。原则是"游戏代码不能手动加计时"——你写 `update_player()` 不应该在里面写 `let t0 = rdtsc()`、`let t1 = rdtsc(); log(t1-t0)`。计时必须像影子一样,在你完全不知道的情况下完成。

## 0 · 为什么要有这一天

设想你在游戏里写 200 个函数,想测每个函数的耗时。最直接的写法:

```rust
fn update_player() {
    let t0 = rdtsc();
    // ... 函数体 50 行
    let t1 = rdtsc();
    log("update_player", t1 - t0);
}
```

这有 4 个问题:

1. **侵入式**:每个函数 200 个都要改,共 400 处插入
2. **遗漏 bug**:写新函数忘了加 → 测不到
3. **早返回 bug**:函数中间有 `return`,后面的 `t1 = rdtsc()` 跑不到 → 日志漏
4. **panic bug**:函数 panic 提前 unwind,`t1 = rdtsc()` 也不跑 → 数据假

工业级的解决方案只有一个:**让计时自动发生**。具体做法是用 RAII(资源获取即初始化)——在函数开头创建一个对象,函数结束(无论正常 return、早 return 还是 panic)对象自动 drop,drop 时记耗时。

心理锚点:看完今天,你应该能写出"任何函数加一行就自动计时"的 API,并能解释 RAII 为什么比宏更好(Rust 视角)。

## 1 · Casey 今天做了什么

Casey 在 C 里用宏 `TIMED_BLOCK()` 实现,宏展开成匿名的本地变量 + 自动析构。他强调:

1. 宏的名字要短(`TIMED_BLOCK`),否则没人愿意用
2. 宏生成**匿名变量**(C 里用 `__` 前缀 + 行号),防止重名
3. release build 用 `#if INTERNAL` 把宏体改成空,零开销

Rust 不需要匿名变量,因为 Rust 的 `let _ = ...` 模式天然适合这件事。Casey 顺带提了"为什么不能用宏而要手写一个 struct"——C 的宏在调试器里看不到真实调用栈,Rust 的 RAII 反而更清楚。

## 2 · 心智模型

### 类比:便利店的安全门铃

便利店的门装一个磁性门铃:门一开,磁铁分离,电路断开,门铃响。**你不用每次进店主动按铃**——只要门开了就响。这正是 RAII 的逻辑:**对象生命周期触发回调,而不是手动调用**。

把这套搬到 profiler:

- **门开**(scope 进入)→ `ProfileSpan::enter()` → 记录起始 rdtsc
- **门关**(scope 离开)→ `Drop::drop()` → 记录结束 rdtsc,差值上报

无论"门关"是正常 return、提前 return、还是 panic(unwind),门铃都响。

### 2.1 RAII 在 Rust 里的完整机制

```rust
pub struct ProfileSpan {
    name: &'static str,  // 函数名,编译期常量,无分配
    start: u64,
}

impl ProfileSpan {
    #[inline(always)]  // 强制内联,release build 完全消除函数调用
    pub fn enter(name: &'static str) -> Self {
        Self { name, start: rdtsc() }
    }
}

impl Drop for ProfileSpan {
    #[inline(always)]
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        // 上报到全局 thread-local 存储(Day 178 详细讲)
        RECORD.with(|r| r.borrow_mut().push(self.name, elapsed));
    }
}
```

**关键 Rust 概念**:

1. **`Drop` trait**:Rust 编译器保证——任何 `T: Drop` 的变量,离开作用域时自动调用 `drop`。**这是确定性销毁**,和 Java GC 不同(GC 是"最终"销毁,时间不定)
2. **panic 时也调 Drop**:panic 触发 unwind,unwind 沿调用栈反向调用每个变量的 Drop。所以**即便函数 panic,计时也会被记录**
3. **`#[inline(always)]`**:提示编译器强制内联。配合 release build,`ProfileSpan::enter` 会被消除成直接的 rdtsc + struct 构造,无函数调用开销
4. **`&'static str`**:函数名是字符串字面量,放在二进制的 `.rodata` 段,程序整个生命周期都可访问,无 lifetime 烦恼

### 2.2 为什么不用宏?

C 必须用宏,因为 C 没有 RAII。Rust 有 RAII,所以**理论上不需要宏**。但实际工程中,Rust 的 profiler 库(puffin / superluminal)还是会提供 `profile_scope!()` 宏,原因:

1. **简短**:写 `profile_scope!("update");` 比 `let _span = ProfileSpan::enter("update");` 短
2. **自动 file:line**:宏可以注入 `file!()`, `line!()`,记录调用位置
3. **唯一变量名**:宏用 `concat_idents!` 生成唯一变量名,防止 shadowing 警告

但宏不是必须的。Casey 自己的 C 版本是宏,Rust 翻译版可以纯 RAII。下面是一个不带宏的版本:

```rust
// 用法(每函数 1 行)
fn update_player(state: &mut State) {
    let _p = ProfileSpan::enter("update_player");
    // ... 函数体
}
```

### 2.3 全局 thread-local 存储

profiler 数据要存哪里?三个选项:

| 选项 | 优点 | 缺点 |
|---|---|---|
| 全局 `static` | 简单 | 多线程要加锁 |
| `thread_local!` | 无锁,每线程独立 | 汇总要遍历 |
| 参数传递 | 显式 | 侵入式,Casey 不要 |

thread_local 是最佳选择——profiler 是每线程独立采的,汇总时再合并。Day 178 详细讲跨线程合并,今天先实现单线程版:

```rust
use std::cell::RefCell;

thread_local! {
    static RECORD: RefCell<Vec<(&'static str, u64)>> = RefCell::new(Vec::new());
}

impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        RECORD.with(|r| r.borrow_mut().push((self.name, elapsed)));
    }
}
```

**Rust 注释**:
- `thread_local!` — 宏,声明每个线程独立的 static。第一次访问时惰性初始化
- `RefCell<Vec<...>>` — 提供**运行时借用检查**。同一时刻只能有一个 `borrow_mut()`。profiler 单线程访问,RefCell 够用
- `.with(|r| ...)` — thread_local 的访问 API,把当前线程的实例传给闭包

### 2.4 frame 边界

profiler 数据要按"帧"分组,不然没法看趋势。怎么定义一帧?在游戏主循环开头清空 record,结尾消费:

```rust
fn game_loop() {
    loop {
        // 帧开始:清空上一帧的 record
        RECORD.with(|r| r.borrow_mut().clear());

        let _frame_span = ProfileSpan::enter("frame");
        update();
        render();
        swap_buffers();

        // 帧结束:消费 record
        let records: Vec<_> = RECORD.with(|r| r.borrow().iter().cloned().collect());
        push_to_history(records);
    }
}
```

`_frame_span` 在循环体结束时 drop,所以 record 里**包含 frame 总耗时**。然后下一帧开头清空,继续。

### 2.5 从汇编层验证零开销

口说无凭,我们让编译器证明 RAII guard 在 release build 里被内联成"几条机器指令"。先写最小例子:

```rust
#[inline(always)]
fn rdtsc() -> u64 {
    unsafe {
        let lo: u32; let hi: u32;
        core::arch::asm!("rdtsc", out("eax") lo, out("edx") hi, options(nomem, nostack));
        ((hi as u64) << 32) | (lo as u64)
    }
}

pub struct Span { start: u64 }
impl Span { #[inline(always)] pub fn enter() -> Self { Self { start: rdtsc() } } }
impl Drop for Span { #[inline(always)] fn drop(&mut self) { let _ = rdtsc() - self.start; } }

#[no_mangle]
pub extern "C" fn measured() -> u64 {
    let _s = Span::enter();
    let mut x = 0u64;
    for i in 0..1000 { x = x.wrapping_add(i); }
    x
}
```

跑 `cargo rustc --release -- --emit asm`,然后在 `target/release/deps/` 找 `.s` 文件,搜 `measured:`。你会看到大致这样的汇编(AT&T 语法,源在左,目的在右):

```
measured:
    pushq   %rbx                  # 保存 callee-saved 寄存器
    rdtsc                         # 读时间戳,eax:edx = 64 位 cycle 数
    movq    %rax, %rbx            # 把起始 cycle 存到 rbx(对应 self.start)
    xorl    %eax, %eax            # i = 0
.Lloop:
    addq    %rax, %rdx            # x += i
    incq    %rax                  # i++
    cmpq    $1000, %rax
    jne     .Lloop
    rdtsc                         # 第二次读时间戳
    subq    %rbx, %rax            # 算差值(对应 drop 里的 elapsed)
    popq    %rbx
    retq
```

**每一行对应 Rust 源码的什么**:

- 第 2 行 `rdtsc` 对应 `Span::enter` 内部的 `rdtsc()`
- 第 3 行 `movq %rax, %rbx` 对应 `Self { start: ... }` 把 start 存到栈/寄存器
- 第 4-8 行对应 `for` 循环
- 第 9 行 `rdtsc` 对应 `Drop::drop` 里的 `rdtsc()`
- 第 10 行 `subq` 对应 `rdtsc() - self.start`

**关键观察**:**没有 `call` 指令**。`Span::enter`、`Drop::drop`、`rdtsc` 全部被内联消除了。这就是 Rust RAII 比 C 宏更好的地方——编译器把 guard 的整个生命周期优化成"两次 rdtsc 之间夹几条指令"。

### 2.6 Record 数据的内存布局

每帧的 record 是一个 `Vec<(&'static str, u64)>`。在内存里长这样(64 位 little-endian):

```
Vec 的内部 = (ptr, len, cap) 三元组,24 字节
+-------+-------+-------+
|  ptr  |  len  |  cap  |   8 + 8 + 8 = 24 字节,存在栈上
+-------+-------+-------+
    |
    v
堆上(每条 record 24 字节):
+-----------+-----------+-----------+-----------+
| "update"  | 523456    | "render"  | 234567    |  ...
| str ptr   | u64       | str ptr   | u64       |
| (8 byte)  | (8 byte)  | (8 byte)  | (8 byte)  |
+-----------+-----------+-----------+-----------+
    |
    v
指向 .rodata 段里的字符串字面量 "update\0"
```

每条 record 16 字节(8 字节指针 + 8 字节 cycle 数),但 Vec 要求元素是 `Sized`,所以实际 stride 是 16。一帧 100 个 span,1.6 KB——完全可以接受。

**为什么用 `&'static str` 而不是 `String`**:`String` 要在堆上分配字符数组,drop 时 free,慢且碎片化。`&'static str` 指向二进制的 `.rodata` 段,永不分配永不释放,创建耗时 < 1 ns。

### 2.7 测量本身的偏差(Heisenberg 效应)

物理学的测不准原理说:**测量行为改变被测对象**。profiler 也一样。每加一个 `ProfileSpan`,你至少引入:

1. **两次 rdtsc** — 约 20-40 cycle(10-20 ns)
2. **一次 RefCell::borrow_mut** — 约 5 cycle
3. **一次 Vec::push** — 平均 5 cycle(分摊),最坏 O(n) 扩容
4. **2 个 L1 cache line 写入** — 可能赶走别的热数据

合计约 30-50 cycle per span。如果函数本身耗时 1000 cycle,profiler 让它变成 1050 cycle,**测量误差 5%**。Casey 的目标是把 profiler 开销压在 **1% 以下**,所以这个误差可接受。

**减少偏差的工程手段**:

- 函数太短(< 100 cycle)就别加 span(测出来的都是 profiler 自己的开销)
- 用 `#[inline(always)]` 消除函数调用开销
- 用 arena / slab 替代 Vec,避免扩容
- 把 span 数据预先 reserve 到固定大小

### 3.1 · 🎮 游戏编程视角

### 3.2 · 🐧 Linux 系统编程视角

`thread_local!` 在 Linux 上的实现:

```bash
# 看 thread_local 的存储
readelf -l target/release/my_game | grep TLS
# 输出示例:
#  TLS    0x0000000000001234 0x0000000000003456 0x0000000000003456 0x200 0x400 R   0x8
```

TLS(Thread Local Storage)段是 ELF 的一个特殊段,内核在创建线程时为每个线程分配一份。访问 TLS 比 lock-free 的 atomic 还快(直接 `%fs:0x...` 寻址)。

Linux 上验证 TLS 工作正常:

```c
// 用 gcc 写个最小例子
__thread int counter = 0;
// 反汇编后,counter 的访问是 mov %fs:counter@tpoff, %eax
```

### 3.3 · 🦀 Rust 生态视角

Rust 的 thread_local 有两种宏:

- `thread_local!`(标准库)— 用 `LocalKey<T>`,惰性初始化
- `thread_local!(static FOO: T = init)` — 简写

替代品:`tokio::task_local!`——异步任务级隔离,适合 async 代码。

profiler 库的实际选择:
- puffin 用 `thread_local!`(同步代码)
- tracing 用 `tokio::task_local!`(异步代码)

**Rust 特性应用**:
- `Drop` trait — Casey 在 C 里要写 `__attribute__((cleanup(profiler_end)))`,Rust 一行搞定
- `&'static str` — 字面量无分配,完美适合记录函数名
- `RefCell<T>` — 运行时借用检查,适合 thread_local 内部

### 3.4 · 🎨 图形学视角

图形程序员的 profiler 比游戏通用 profiler 多一维关注:**GPU 时间**。CPU 端的 `rdtsc` 测不到 GPU——GPU 命令提交后异步执行,CPU 端的 `glDrawElements` 几微秒就返回,真正光栅化在 GPU 上要几百微秒。

GPU profiling 的标准做法用 **timer query**:

```c
// OpenGL(伪代码,Rust 等价用 glow / gl crate)
GLuint q;
glGenQueries(1, &q);
glBeginQuery(GL_TIME_ELAPSED, q);
glDrawElements(...);
glEndQuery(GL_TIME_ELAPSED);

// 几帧后查结果(query 异步完成)
GLint available = 0;
while (!available) glGetQueryObjectiv(q, GL_QUERY_RESULT_AVAILABLE, &available);
GLuint64 elapsed_ns;
glGetQueryObjectui64v(q, GL_QUERY_RESULT, &elapsed_ns);
```

**为什么是异步**:GPU 命令队列里可能积了几十帧的命令,你今天提的 draw 可能 16ms 后才真正跑完。所以查询结果"晚一帧"才出来。

工业 GPU profiler(Nsight / RenderDoc / GPUView)都基于 query,但加了:
- **Per-draw call 计时**(每个 draw 包一对 query)
- **Pipeline stage 分解**(vertex shader / fragment shader / rasterizer 各占多少)
- **可视化时间轴**(看到 GPU 内部流水线阻塞)

Casey 在 Phase 5 还没碰 GPU,Day 178+ 全在 CPU。但**设计上要预留 GPU 时间维度**:profiler 数据结构里加一个 `kind: Cpu | Gpu` 字段,日后扩。

### 3.5 · 🐧 Linux perf 工具链对比

Linux 内核自带一套比 rdtsc 更强大的工具:`perf`。它做**采样式**(sampled)profiling,而不是 Casey 的**插桩式**(instrumented)。两者的本质差别:

| 维度 | 插桩式(Casey / puffin) | 采样式(perf / vtune) |
|---|---|---|
| 数据来源 | 程序里手动埋点 | 内核定期中断程序读 PC |
| 精度 | 每次调用都记 | 每 1ms / 10ms 抽一次 |
| 开销 | 与埋点数成正比 | 固定 ~1-3% CPU |
| 看到什么 | 函数级 cycle 数 | 调用栈热点分布 |
| 看不到什么 | 没埋点的函数 | 短函数(没采样到) |
| 适合场景 | 自己的代码 | 含系统调用 / 第三方库 |

Casey 选插桩因为:**他对自己的代码完全可控**,知道哪里要埋点。perf 适合"全栈看一眼"——含驱动、内核态、libc。

```bash
# 采样式 profile 自己的程序
sudo perf record -F 99 -p $(pidof my_game) -g -- sleep 5
# -F 99   采样频率 99 Hz
# -p PID  指定进程
# -g      记录调用栈
# -- sleep 5  采 5 秒

# 看报告
sudo perf report --no-children
# 输出每函数占采样百分比:
#  23.5%  my_game   update_player
#  15.2%  my_game   render_batch
#   8.1%  libc.so   memcpy
#   ...
```

两个工具**互补**:perf 帮你发现"哪个函数慢",Casey 的内置 profiler 帮你"看这个函数每帧的趋势"。

### 4.1 上级

- **RAII**(资源获取即初始化)— Rust 内存管理的元模式
- **观察者模式**(Observer Pattern)— 当某事件发生时自动通知

| 自动计时方案 | 实现机制 | 优点 | 缺点 |
|---|---|---|---|
| RAII Drop | Rust/C++ | panic 也触发 | 语言依赖 |

| LSP instrumentation | DTrace / bpftrace | 二进制级别 | 性能开销大 |

### 4.3 下级

- `rdtsc()` — 时钟源
- `ProfileSpan` struct + `Drop` — 自动计时
- `thread_local!(RefCell<Vec<...>>)` — 每线程存储
- `#[inline(always)]` — 编译器指令
- frame 边界管理 — 数据分组

## 5 · 对照与变奏

**RAII vs GC 的内存安全对比**:

| 场景 | RAII(Rust) | GC(Java) |
|---|---|---|
| 文件关闭 | 离开作用域自动关 | 等 finalize(可能不调) |
| 锁释放 | 离开作用域自动 unlock | 等 GC(可能死锁) |
| 资源清理 | 确定性 | 不确定 |
| profiler 适用 | ✅ Drop 一定触发 | ❌ finalize 不保证 |

profiler 必须 RAII,GC 语言的 profiler 要用 try-with-resources / using 块模拟。

**Rust Drop 的边界 case**:

- `std::mem::forget(span)` → 不调 drop,数据丢失(unsafe 操作, profiler 不防)
- `ManuallyDrop::new(span)` → 同上
- `unsafe { panic::set_hook(...) }` abort 模式 → 不 unwind,不调 drop

正常代码不会遇到这些,profiler 假设 RAII 正常工作。

### 跨语言 RAII 对照

不同语言实现"自动清理"的方式差异极大,这影响了它们写 profiler 的难易:

**Rust / C++**:编译器在每个作用域出口插入 drop 调用(无 GC、确定性、零运行时开销)。profiler guard 在这两种语言里**最自然**——一行声明,编译器管剩下。

**Zig**:`defer` 关键字显式声明清理代码,语义接近 RAII 但要在每个 return 路径前看到 defer。比起 Rust 的隐式 drop,Zig 的 defer 更"手动",但避免了 Drop trait 的隐式行为争议。

**Go**:`defer` 在**函数返回**时执行(不是块结束),且按 LIFO 顺序。在循环里用 defer 会泄漏到函数结束,profiler 在 Go 里要谨慎。

**Swift**:用 `defer` 块,语义类似 Zig,但 ARC(自动引用计数)模式下对象的 deinit 也可作 guard。

**Java / C#**:完全靠 GC,finalizer 时机不可预测。这两种语言写 profiler 必须 `try-with-resources`(Java) / `using`(C#)显式包裹——略啰嗦但能用。

**Python**:`with` 上下文管理器(`__enter__` / `__exit__`),缩进敏感,函数嵌套深的代码不易读。

记忆口诀:**RAII 是 Rust/C++ 独有的隐式确定性销毁,其他语言要么显式(with/defer),要么非确定(GC)**。

### 与 puffin 的源码级对比

`puffin` 是 Rust 生态里 Casey 风格的 profiler。读 `puffin/src/lib.rs` 的 `ProfileScope`,可以对照 Casey 的 C 版本看设计差异:

- puffin 用 `ThreadInfo` 记录线程名,Casey 在 C 里手写 `GetThreadId()`
- puffin 用 `GlobalFrameData` 加锁聚合,Casey 后期用 lock-free(Phase 6+)
- puffin 的 frame data 序列化成 binary(支持远程 viewer),Casey 在内存用

学一个库的源码,要带着**"它解决了我的什么问题"** 的视角——纯粹读会迷路。Casey 推荐的方法:**先用,出 bug 再读**,这样每个 API 的意义都对应你的痛点。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:`ProfileSpan` 在函数开头创建,函数 panic 时会发生什么?panic 模式下还能拿到耗时数据吗?

**参考解答**:
- Rust 的 panic 默认是 **unwind** 模式,沿调用栈反向调用每个变量的 Drop
- 所以 `ProfileSpan::drop` 会被调用,耗时数据**会被记录**
- 但如果项目用了 `panic = "abort"`(Cargo.toml 配置),panic 直接终止进程,**Drop 不调,数据丢**
- 实际工程:dev mode 用 unwind(方便 debug),release 用 abort(二进制更小,无 unwind 表)

`Cargo.toml`:
```toml
[profile.release]
panic = "abort"
```

### Lv2 · 动手实践

**题**:实现完整可跑的 profiler,要求:
- `ProfileSpan` + `Drop`
- `thread_local!` 存 record
- `main` 里建嵌套函数(outer → inner),打印 outer 和 inner 各自的 cycle 数
- 验证:inner < outer(因为 outer 包含 inner)

**参考解答**:

```rust
use std::cell::RefCell;
use std::hint::black_box;

#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    unsafe {
        let lo: u32;
        let hi: u32;
        core::arch::asm!("rdtsc",
            out("eax") lo, out("edx") hi,
            options(nomem, nostack));
        ((hi as u64) << 32) | (lo as u64)
    }
}

thread_local! {
    static RECORD: RefCell<Vec<(&'static str, u64)>> = RefCell::new(Vec::new());
}

pub struct ProfileSpan { name: &'static str, start: u64 }

impl ProfileSpan {
    pub fn enter(name: &'static str) -> Self {
        Self { name, start: rdtsc() }
    }
}

impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        RECORD.with(|r| r.borrow_mut().push((self.name, elapsed)));
    }
}

fn inner(n: u64) -> u64 {
    let _s = ProfileSpan::enter("inner");
    let mut x = 0u64;
    for i in 0..n { x = x.wrapping_add(i); }
    x
}

fn outer(n: u64) -> u64 {
    let _s = ProfileSpan::enter("outer");
    let a = inner(n);
    let b = inner(n);
    a.wrapping_add(b)
}

fn main() {
    RECORD.with(|r| r.borrow_mut().clear());

    let result = outer(1_000_000);
    black_box(result);

    // 打印 record
    RECORD.with(|r| {
        for (name, cycles) in r.borrow().iter() {
            println!("{}: {} cycles", name, cycles);
        }
    });
}
```

**预期输出**(cycle 数会变,顺序固定):

```
inner: 523456 cycles
inner: 523478 cycles
outer: 1047123 cycles
```

outer > inner + inner,差值是函数调用 + 创建 ProfileSpan 的开销。

### Lv3 · 迁移设计

**题**:profiler guard 不能跨 `.await` 用。但你想测一个 async 函数的总执行时间(从第一次 poll 到完成)。设计 API,要求:
- 不阻塞 executor
- 测的是"墙时间"(总时间,包括 await 等待)
- 测的也是"任务时间"(实际 poll 的时间,不包括 await 等待)

**提示**:
- 用 `Pin<&mut Self>` 在 `poll` 入口和出口记 rdtsc
- 用 `tokio::time::Instant::now()` 测墙时间
- 写一个 `Instrumented<F: Future>` wrapper,impl Future
- **关键设计选择**:任务实际执行时间 vs 任务总等待时间要分开。前者累加每次 poll 的耗时,后者是 `Instant::now()` 差值。两者比 = CPU 利用率。
- **额外提示**:`poll` 可能被 waker 唤醒后调用,你可能要记录"被唤醒到完成"和"被调度到 poll"两个时间。
- **参考 tracing-opentelemetry 的 InstrumentedFuture 实现**

## 8 · Rust / Arch 落地代码

完整可跑项目(基于 Lv2,加 frame 边界):

```rust
// Cargo.toml:空,纯 std
// src/main.rs
use std::cell::RefCell;
use std::hint::black_box;

#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    unsafe {
        let lo: u32;
        let hi: u32;
        core::arch::asm!("rdtsc",
            out("eax") lo, out("edx") hi,
            options(nomem, nostack));
        ((hi as u64) << 32) | (lo as u64)
    }
}

#[derive(Default, Clone)]
pub struct FrameData {
    pub spans: Vec<(&'static str, u64)>,
}

thread_local! {
    static CURRENT_FRAME: RefCell<Vec<(&'static str, u64)>> = RefCell::new(Vec::new());
    static HISTORY: RefCell<Vec<FrameData>> = RefCell::new(Vec::new());
}

pub struct ProfileSpan { name: &'static str, start: u64 }

impl ProfileSpan {
    pub fn enter(name: &'static str) -> Self {
        Self { name, start: rdtsc() }
    }
}

impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        CURRENT_FRAME.with(|r| r.borrow_mut().push((self.name, elapsed)));
    }
}

fn end_frame() {
    let spans: Vec<_> = CURRENT_FRAME.with(|r| r.borrow_mut().drain(..).collect());
    HISTORY.with(|h| {
        let mut hist = h.borrow_mut();
        if hist.len() >= 60 { hist.remove(0); }
        hist.push(FrameData { spans });
    });
}

fn update() {
    let _s = ProfileSpan::enter("update");
    for _ in 0..100_000 { black_box(0u64.wrapping_add(1)); }
}

fn render() {
    let _s = ProfileSpan::enter("render");
    for _ in 0..50_000 { black_box(0u64.wrapping_add(1)); }
}

fn main() {
    for frame_num in 0..5 {
        let _frame = ProfileSpan::enter("frame");
        update();
        render();
        drop(_frame);  // 显式 drop,确保 frame 的 record 进 CURRENT_FRAME
        end_frame();
    }

    HISTORY.with(|h| {
        for (i, frame) in h.borrow().iter().enumerate() {
            println!("--- frame {} ---", i);
            let mut total = 0u64;
            for (name, c) in &frame.spans {
                println!("  {}: {} cycles", name, c);
                total += c;
            }
            let _ = total;
        }
    });
}
```

**Arch Linux 验证**:

```bash
cargo new --bin mini-profiler-2
cd mini-profiler-2
# 粘贴代码到 src/main.rs
cargo run --release

# 看汇编,确认 rdtsc 内联
cargo rustc --release -- --emit asm
find target/release/deps -name "mini_profiler*.s" | head -1 | xargs grep -c rdtsc
# 应该 >= 4(update + render + frame + Drop 调用)

# 测一下 ProfileSpan 的开销
# 写个 benchmark:循环 1_000_000 次创建 + drop span
# 平均应该 < 20 cycle
```

**Troubleshooting**:

- `BorrowMutError: already borrowed` — RefCell 不能在 borrow 时再 borrow。检查 Drop 实现里是不是不小心递归
- 数据数量不对 — 确认 `drop(_frame)` 在 `end_frame()` 之前;否则 frame span 不在 CURRENT_FRAME 里
- span 数量浮动 — 检查 release build 是否禁用了某些 span 的 `#[cfg]`,导致不同 build mode 数据差异大

**性能调优技巧**:

```bash
# 1. 测 profiler 自身开销
# 写一个空函数加 span,跑 1_000_000 次,看总耗时
# 期望:每次 span < 50 cycle,1_000_000 次总耗时 < 50ms

# 2. 用 perf 验证 rdtsc 被内联(不应有 call 指令)
cargo rustc --release -- --emit asm
grep -c "call.*rdtsc" target/release/deps/mini_profiler*.s
# 应该为 0(全部内联,rdtsc 是单指令)

# 3. 用 massif(Rust 的 valgrind 模式)看堆增长
cargo build
valgrind --tool=massif target/debug/mini-profiler-2
ms_print massif.out.* | head -50
# Vec<Record> 应该稳定,不无限增长(否则 ring buffer 写错)

# 4. 用 heaptrack 看分配热点(比 massif 友好)
sudo pacman -S heaptrack
heaptrack target/release/mini-profiler-2
heaptrack_print heaptrack.mini-profiler-2.*.gz | head
# 期望:99% 分配在 thread_local 的初始化上(一次),不在每帧

# 5. 看二进制大小,Drop trait 不会膨胀代码
ls -la target/release/mini-profiler-2
# 期望:< 500 KB(纯 std 项目)

# 6. 用 hyperfine 跑 benchmark
sudo pacman -S hyperfine
hyperfine --warmup 3 ./target/release/mini-profiler-2
# 期望:运行时间标准差 < 5%(说明 profiler 没引入抖动)
```

**关键陷阱**:如果你的 record Vec 不停增长,说明 `end_frame` 没正确清空。运行半小时后内存可能爆到几 GB——production 上是定时炸弹。预防:每 N 帧用 `Vec::shrink_to_fit` 回收,或固定 `Vec::with_capacity(1024)` 避免扩容。
