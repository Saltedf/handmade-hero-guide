
# Day 241 · OpenGL VSync 与 sRGB 扩展

> Day 240 你做完三层架构,跑游戏发现两个怪事:(1) FPS 飙到几千(显卡狂转);(2) 颜色看着比 Day 094 软件渲染的更"灰"。Casey 今天修这两个 bug:**VSync**(垂直同步,锁帧到显示器刷新率)+ **sRGB framebuffer**(GPU 自动 sRGB↔linear 转换)。Day 094 讲的 gamma 知识终于落地。

## 0 · 为什么要有这一天

Day 094 你学过 gamma / sRGB 的概念:**人眼对暗部变化更敏感,所以 sRGB 编码非线性地把更多位给暗部**。光照计算必须**在线性空间**,显示时**转回 sRGB**。

软件渲染时你手动做了:

```rust
// 输入:sRGB 纹理(8 位像素)
let linear = srgb_to_linear(srgb_pixel);
// 光照
let lit = lighting_calc(linear);
// 输出:转回 sRGB
let output = linear_to_srgb(lit);
```

Day 237 切到 OpenGL 后,你**没做这个转换**,直接 `frag_color = texture(tex, uv)`。结果:

- 输入像素被当 linear 用(实际是 sRGB)—— 光照算出来偏暗
- 输出像素直接 sRGB 显示(实际值已经是"被当 linear 算过的 sRGB")—— 又错一次

双重错误,颜色"看起来灰"。这是切到 OpenGL 后的常见 bug,叫"**gamma 不正确**"。

OpenGL 给的标准解法是 `GL_FRAMEBUFFER_SRGB` 扩展——启用后,GPU 在 fragment shader 输出后**自动**把 linear 转 sRGB 写入 framebuffer。你只要确保:

1. 纹理用 `GL_SRGB8_ALPHA8` 内部格式(GPU 自动 sRGB→linear 解码)
2. 启用 `GL_FRAMEBUFFER_SRGB`(shader 输出自动 linear→sRGB 编码)
3. shader 不用管 gamma,直接算光照

**第二个 bug:VSync**。FPS 飙到几千,显卡满载:

- CPU 算 `game_update` 1ms,`swap_buffers` 立刻返回,GPU 在后台画
- 主循环 1000+ 次/秒,每次 swap 都强制刷新 → 显卡过热

VSync 的作用:`swap_buffers` 等到显示器下一个垂直同步信号才换 buffer。60Hz 显示器上 swap 最多 60 次/秒,主循环自然限速到 60 FPS。

**心理锚点**:看完今天,你的游戏 FPS 稳定在 60(或显示器刷新率),颜色和 Day 094 软件渲染一致。

## 1 · Casey 今天做了什么

Casey 在 Day 240 的渲染器里加两个东西:

1. **VSync** —— 调 `wglSwapIntervalEXT(1)`(Windows)/ `glXSwapIntervalEXT`(Linux)/ `eglSwapInterval`(Wayland)启用 VSync
2. **sRGB framebuffer** —— 创建 framebuffer 时选 `GL_FRAMEBUFFER_SRGB_CAPABLE` 像素格式,然后调 `glEnable(GL_FRAMEBUFFER_SRGB)`

## 2 · 心智模型

### 类比:相机 vs 显示器

**显示器**(sRGB)和**软件光照**(linear)用不同"语言"。中间必须翻译。Day 094 你手动翻译:

```
sRGB 纹理 → 翻译 → linear → 光照 → 翻译 → sRGB → 显示
```

Day 241 你让 GPU 替你翻译:

```
sRGB 纹理 →[GPU 自动解码]→ linear → shader 光照 →[GPU 自动编码]→ sRGB → 显示
                  ^                                              ^
              用 SRGB 纹理格式                              启用 FRAMEBUFFER_SRGB
```

shader 只看 linear,GPU 自动转。免性能、免错误。

### 2.1 sRGB 公式回顾

sRGB → linear(解码):

```
linear = sRGB ≤ 0.04045 ? sRGB / 12.92 : ((sRGB + 0.055) / 1.055) ^ 2.4
```

linear → sRGB(编码):

```
sRGB = linear ≤ 0.0031308 ? linear * 12.92 : 1.055 * linear^(1/2.4) - 0.055
```

简化(常用近似):

```
linear ≈ sRGB^2.2
sRGB ≈ linear^(1/2.2)
```

**为什么 GPU 硬件做?** 因为转换是 per-pixel 的,1080p = 200 万像素 × 每帧,软件算很慢。GPU 在 texture unit 和 framebuffer output 单元**集成**了 sRGB 查表,几乎免费。

### 2.2 VSync 的工作原理

显示器刷新是**逐行扫描**(CRT 时代传统,LCD 沿用)。每秒扫 60 次(60Hz)。每次扫完到下次开始之间的"回程"叫**垂直空白期(vertical blanking interval, VBlank)**。

```
扫描时间: ~15ms
回程时间: ~1.7ms
总计: 16.7ms = 60Hz
            ↑
        VBlank 期间 swap
```

VSync 让 `swap_buffers` **等到 VBlank** 才换 buffer。好处:

1. **无撕裂(tearing)** —— 显示器扫到一半换 buffer,会出现"上半旧帧 + 下半新帧"
2. **节能** —— GPU 不会算超帧

坏处:

1. **延迟** —— 鼠标输入到画面变化延迟可能增一帧(16ms)
2. **卡顿** —— 如果一帧算 >16ms,VSync 会等下一帧(33ms),FPS 突降到 30

**现代变种**:

- **G-Sync / FreeSync** —— 显示器自适应刷新率,消除 VSync 的卡顿
- **Fast Sync / Enhanced Sync** —— GPU 算多少算多少,只显示最新帧,降延迟

跟 HH 用普通 VSync 起步,够用。

### 2.3 启用 VSync 的 API

不同平台 API 不同,glutin 帮你封装:

```rust
// glutin 0.30+
let window_context = glutin::context::NotCurrentContext::...;
// 在创建时指定 swap interval
// 或运行时:
let gl_display = ...;
gl_display.swap_interval(&window_context, glutin::surface::SwapInterval::Wait(1))?;
// Wait(1) = VSync on; DontWait = VSync off
```

底层 API(参考):

- Windows: `wglSwapIntervalEXT(1)`(WGL_EXT_swap_control 扩展)
- Linux X11: `glXSwapIntervalEXT(1)` 或 `glXSwapIntervalMESA(1)`
- Linux Wayland: `eglSwapInterval(display, 1)`
- macOS: `CGLSetParameter(ctx, kCGLCPSwapInterval, 1)`

glutin 抽象这些。

### 2.4 启用 sRGB framebuffer

**第一步:创建 context 时选 sRGB capable 的 pixel format**

```rust
let window_builder = glutin::GlutinWindowBuilder::new(wb)
    // glutin 自动选 sRGB capable format,无需手动
    ;
```

**第二步:启用 sRGB**

```rust
unsafe {
    gl.enable(glow::FRAMEBUFFER_SRGB);
}
```

启用后,GPU 在 fragment shader 输出后自动 linear→sRGB 转换。

**第三步:纹理用 sRGB 内部格式**

```rust
// 之前
gl.tex_image_2d(TEXTURE_2D, 0, glow::RGBA as i32, w, h, 0,
               glow::RGBA, glow::UNSIGNED_BYTE, Some(pixels));

// 现在
gl.tex_image_2d(TEXTURE_2D, 0, glow::SRGB8_ALPHA8 as i32, w, h, 0,
               glow::RGBA, glow::UNSIGNED_BYTE, Some(pixels));
//                  ^^^^^^^^^^^^^^^^^^^^
//        GPU 在 texture() 时自动 sRGB→linear
```

`SRGB8_ALPHA8` 表示 GPU 内部用 8 位 sRGB + 8 位 alpha 存储,采样时**自动**转 linear 给 shader。

### 2.5 验证颜色正确

写一个测试:渲染一个 50% 灰(128/255 = 0.502)的 sRGB 纹理,屏幕看到的应该是 50% 灰(像素值 = 188/255,因为 sRGB 编码后 50% linear ≈ 188 sRGB)。

```rust
let pixel = [188, 188, 188, 255];  // sRGB 188 表示约 50% linear
gl.tex_image_2d(... glow::SRGB8_ALPHA8 ... Some(&[pixel; ...]));
```

启用 sRGB framebuffer 后,fragment shader 输出 50% linear,framebuffer 自动转 188 sRGB,显示和原始 PNG 一致。

### 2.6 调试 gamma 错误的方法

```rust
// 临时禁用 sRGB 验证 bug:
gl.disable(glow::FRAMEBUFFER_SRGB);
// 如果画面"变亮",说明之前是双重校正(错)
// 如果画面"变暗",说明之前是没校正(也错,但相反方向)
```

或者用 RenderDoc:Capture 一帧,看 framebuffer 像素值,对比预期。

---

**总结**:VSync 锁帧节能 + 防撕裂,sRGB framebuffer 让 GPU 自动做颜色空间转换。两个开关都开了,游戏画面正确、不烧显卡。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

**FPS 限制策略**:

- **VSync** —— 锁到显示器刷新率(60/120/144Hz),最简单
- **Frame limiter** —— 软件限帧(游戏自己 sleep),不依赖显示器
- **Uncapped** —— 算多快跑多快,电竞游戏用(降延迟)
- **G-Sync / FreeSync** —— 显示器自适应,理想方案

Casey 选 VSync,简单可靠。如果用户有 G-Sync 显示器,VSync 会被 G-Sync 接管,效果更好。

**sRGB 在游戏里的传播**:

```
原画师画 PNG (sRGB)
   ↓
游戏加载
   ↓
GPU 上传纹理(标 SRGB 格式)
   ↓
shader 采样(自动 sRGB→linear)
   ↓
光照 / 后处理(linear 空间)
   ↓
tone mapping(linear → linear,颜色范围压缩)
   ↓
framebuffer(自动 linear→sRGB)
   ↓
显示器(sRGB 显示)
```

中间任何一步错标色彩空间,颜色就变。

**HDR(high dynamic range)** —— 更进一步的色彩管理:linear 用 f16 存储,后处理更精细,tone mapping 后转 sRGB 显示。Phase 6+ 会涉及。

### 3.2 · 🎨 图形学视角

**色彩空间基础**(Day 094 详细讲过,这里回顾):

- **linear** —— 物理光强的线性表示,光照计算必须在这里
- **sRGB** —— 显示器标准,gamma ≈ 2.2
- **ACES / Filmic** —— tone mapping curve,cinematic 效果
- **Rec.2020 / Display-P3** —— 宽色域,新显示器支持

**关键概念**:

- **gamma incorrect** —— 软件没做色彩空间转换,颜色错(典型症状:暗部太暗 / 高光太亮)
- **double gamma** —— 软件又做了一次转换,GPU 又自动做,双重校正(典型症状:画面整体偏白)

OpenGL 的 sRGB 自动转换解决这两个问题,前提是你正确标注纹理格式和启用 framebuffer sRGB。

**光强 vs 感知亮度**:人眼对光强 I 的感知 ≈ I^(1/2.2)。所以 50% 光强看起来像 73% 亮。sRGB 编码利用这一点,把更多位给暗部(暗部细节更精细)。

### 3.3 · 🐧 Linux 系统编程视角

**Wayland 上的 VSync**:

Wayland 协议**强制** VSync——compositor 决定何时显示 frame,client 不能强制 swap。所以你的 VSync 请求在 Wayland 上可能"无效"(由 compositor 接管)。

```bash
# 看 Wayland compositor 状态
echo $XDG_SESSION_TYPE  # wayland 或 x11
# 看 refresh rate
weston-info  # Weston compositor
# 或
gnome-session --version  # GNOME 用 mutter
```

**X11 上的 VSync**:

X11 用 `GLX_EXT_swap_control` 扩展。但 X11 本身是网络协议,延迟大,VSync 效果不如 Wayland 直接。

**DRM / KMS 的 VSync**:

直接 DRM 应用(游戏绕过 compositor)用 `drmModePageFlip` 的 `DRM_MODE_PAGE_FLIP_EVENT` 异步等待 VBlank。这是底层接口,glutin 已经封装。

```bash
# 看显示器刷新率
xrandr | grep -E "connected.*\*"
# 输出:DP-1 connected ... 3840x2160+0+0 ... 59.97Hz*
#                                                              ^^^^^^^ refresh rate
```

## 5 · 对照与变奏

### VSync 模式对比

| 模式 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| VSync off | 立即 swap | 最低延迟 | 撕裂 + 显卡狂转 |
| VSync on | 等 VBlank | 防撕裂 + 节能 | 多一帧延迟 |
| Fast Sync | 算多快算多快,丢中间帧 | 低延迟 + 无撕裂 | 显卡仍满载 |
| G-Sync / FreeSync | 显示器自适应 | 完美 | 需要硬件支持 |

跟 HH 用 VSync on,简单可靠。电竞玩家后面自己换 Fast Sync / G-Sync。

### gamma 校正方案对比

| 方案 | 准确度 | 性能 | 复杂度 |
|---|---|---|---|
| 不管(错) | 低 | 最快 | 0 |
| shader 手算 | 中 | 慢(每像素) | 中 |
| LUT(查找表) | 中 | 中 | 高 |
| GPU 硬件(SRGB) | 高 | 几乎免费 | 低 |

GPU 硬件胜出。Day 241 启用 `GL_FRAMEBUFFER_SRGB` 就是这个方案。

### 历史演化

- **1990s**:OpenGL 没有 sRGB,游戏普遍 gamma incorrect
- **2000s**:GL_EXT_framebuffer_sRGB 扩展出现
- **2010s**:sRGB 进入 OpenGL core spec,默认支持
- **2020s**:HDR / Display-P3 / Rec.2020 普及

你跟 HH 学的 OpenGL 3.3+,sRGB 是 core 功能,免费。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 shader 里直接 `texture(srgb_texture, uv)` 拿到的就是 linear 值?GPU 在哪里做的转换?

**参考解答**:GPU 在 **texture unit**(TMU,Texture Mapping Unit)里做转换。流程:

1. shader 调 `texture(sampler, uv)`
2. TMU 从纹理内存读 8 位 sRGB 像素值
3. TMU 内部的 sRGB→linear 查表(硬件电路)转换
4. 如果 filter 是 LINEAR,TMU 在 linear 空间做插值(关键!如果在 sRGB 空间插值会错)
5. 把 linear 值返回给 shader

shader 拿到的就是 linear。整个过程在 TMU 内部,shader 不感知。

### Lv2 · 动手实践

**题**:在 Day 240 的渲染器里启用 VSync 和 sRGB framebuffer。完成标准:FPS 锁到 60,渲染一个 50% linear 灰的 quad,显示 188/255 sRGB(用屏幕颜色拾取工具验证)。

**参考解答**:

```rust
// 1. 启用 VSync
// 在 glutin 创建 context 后
let surface = ...;
surface.set_swap_interval(&gl_display, glutin::surface::SwapInterval::Wait(1))?;

// 2. 启用 sRGB framebuffer
unsafe {
    gl.enable(glow::FRAMEBUFFER_SRGB);
}

// 3. 纹理用 sRGB 内部格式
let mut pixels = vec![0u8; 64 * 64 * 4];
for px in pixels.chunks_exact_mut(4) {
    // sRGB 188 表示约 50% linear
    px[0] = 188; px[1] = 188; px[2] = 188; px[3] = 255;
}
unsafe {
    gl.bind_texture(glow::TEXTURE_2D, Some(texture));
    gl.tex_image_2d(
        glow::TEXTURE_2D, 0,
        glow::SRGB8_ALPHA8 as i32,  // 关键:SRGB 格式
        64, 64, 0,
        glow::RGBA, glow::UNSIGNED_BYTE,
        Some(&pixels),
    );
}

// 4. fragment shader 不变,直接采样
// (GPU 在采样时自动 sRGB→linear,在输出时自动 linear→sRGB)
```

**验证**:

- 用屏幕颜色拾取工具(Gpick / KDE Color Picker)取屏幕上 quad 的颜色
- 应该是 (188, 188, 188),证明颜色正确传播

### Lv3 · 迁移设计

**题**:你想支持 HDR 显示器(显示 Rec.2020 色域)。怎么扩展当前 sRGB 系统?提示:HDR 用 fp16 格式 + PQ 编码,framebuffer 用 `GL_RGB16F`,加 tone mapping shader。

**提示**:
- 创建 framebuffer 用 `GL_RGB16F`(每通道 16 位 float,范围远超 [0,1])
- shader 输出 linear HDR 值(可能 > 1.0)
- 后处理 shader 做 tone mapping(如 ACES curve)把 HDR 压到 [0, 1]
- 显示器端用 PQ(Perceptual Quantizer)曲线或 scRGB 编码
- Vulkan 比 OpenGL 更好支持 HDR(OpenGL HDR 扩展零散)
- 现阶段 95% 用户还是 sRGB,HDR 是 future work

## 8 · Rust / Arch 落地代码

### Rust 启用 VSync + sRGB

```rust
use glow::HasContext;

fn make_srgb_checker(size: u32) -> Vec<u8> {
    let mut pixels = Vec::with_capacity((size * size * 4) as usize);
    for y in 0..size {
        for x in 0..size {
            let is_white = ((x / 8) + (y / 8)) % 2 == 0;
            let srgb_val = if is_white { 255 } else { 32 };  // 32 sRGB ≈ 3% linear
            pixels.extend_from_slice(&[srgb_val, srgb_val, srgb_val, 255]);
        }
    }
    pixels
}

fn main() {
    let event_loop = winit::event_loop::EventLoop::new().unwrap();
    let window_builder = winit::window::WindowBuilder::new()
        .with_title("Day 241 VSync + sRGB")
        .with_inner_size(winit::dpi::PhysicalSize::new(800, 600));

    // glutin 创建
    let (window, gl_config, window_context) = glutin::GlutinWindowBuilder::new(window_builder)
        .with_gl_api(glutin::config::GlApi::OpenGl)
        .with_gl_profile(glutin::context::GlProfile::Core)
        .with_gl_version(glutin::context::Version::new(3, 3))
        .build(&event_loop)
        .unwrap()
        .split();

    let gl_display = gl_config.display();
    let _ = unsafe { window_context.make_current() }.unwrap();

    // 启用 VSync
    let surface = unsafe {
        glutin::surface::Surface::from_window(
            &gl_display,
            &window,
            glutin::surface::WindowSurface,
        )
    }.unwrap();
    surface.set_swap_interval(&gl_display, glutin::surface::SwapInterval::Wait(1))
        .expect("VSync 设置失败");

    let gl = unsafe {
        glow::Context::from_loader_function_cstr(|s| {
            window.get_proc_address(s) as *const _
        })
    };

    // 启用 sRGB framebuffer
    unsafe {
        gl.enable(glow::FRAMEBUFFER_SRGB);
    }

    // 创建资源(同 Day 237-238)
    let program = ...;
    let vao = ...;
    let vbo = ...;

    // 上传 sRGB 纹理
    let texture = unsafe {
        let tex = gl.create_texture().unwrap();
        gl.bind_texture(glow::TEXTURE_2D, Some(tex));
        gl.tex_image_2d(
            glow::TEXTURE_2D, 0,
            glow::SRGB8_ALPHA8 as i32,  // sRGB 内部格式
            64, 64, 0,
            glow::RGBA, glow::UNSIGNED_BYTE,
            Some(&make_srgb_checker(64)),
        );
        gl.tex_parameter_i32(glow::TEXTURE_2D, glow::TEXTURE_MIN_FILTER, glow::LINEAR as i32);
        gl.tex_parameter_i32(glow::TEXTURE_2D, glow::TEXTURE_MAG_FILTER, glow::LINEAR as i32);
        tex
    };

    let mut frame_count = 0u64;
    let mut last_time = std::time::Instant::now();

    event_loop.run(move |event, target| {
        match event {
            winit::event::Event::AboutToWait => {
                frame_count += 1;
                let elapsed = last_time.elapsed();
                if elapsed.as_secs() >= 1 {
                    println!("FPS: {:.1}", frame_count as f64 / elapsed.as_secs_f64());
                    frame_count = 0;
                    last_time = std::time::Instant::now();
                }

                unsafe {
                    gl.clear_color(0.05, 0.05, 0.1, 1.0);
                    gl.clear(glow::COLOR_BUFFER_BIT);
                    // ... draw ...
                }
                surface.swap_buffers(&gl_display).expect("swap_buffers 失败");
            }
            winit::event::Event::WindowEvent { event, .. } => {
                if let winit::event::WindowEvent::CloseRequested = event {
                    target.exit();
                }
            }
            _ => {}
        }
    }).unwrap();
}
```

## 10 · 深入:VSync 与 sRGB 的工程细节

casey 在 day241 讨论 VSync(垂直同步)和 sRGB(色彩空间)——这两个看似简单实际充满坑的工程问题。

### 10.1 VSync:基础概念

VSync = Vertical Synchronization。屏幕每秒刷新 N 次(60Hz、144Hz、240Hz),VSync 让 GPU 在每个 refresh cycle 结束时 swap buffer,避免 tearing。

```
无 VSync:GPU 不等 refresh,直接 swap → 画面撕裂(tearing)
有 VSync:GPU 等 refresh cycle → 无撕裂,但延迟 +1 frame
```

### 10.2 VSync 的实现

OpenGL:

```rust
// wgl / glx SwapIntervalEXT
unsafe {
    SwapIntervalEXT(1);  // 1 = 启用 VSync,0 = 关闭
}

// glutin / winit
let ctx = glutin::ContextBuilder::new()
    .with_vsync(true)  // 自动调 SwapInterval
    .build_windowed(...)
    .unwrap();
```

### 10.3 VSync 的变体

**VSync off**:撕裂,但最低延迟。电竞游戏用。

**VSync on(传统)**:无撕裂,但延迟 +1 frame。普通游戏用。

**Adaptive VSync**:FPS 低于 refresh rate 时关 VSync(避免 30 FPS 限制),高于时开。NVIDIA G-Sync / AMD FreeSync 是变体。

**G-Sync / FreeSync**:显示器自带 VRR(Variable Refresh Rate),GPU 控制显示器刷新率。无撕裂 + 低延迟。需要兼容硬件。

casey HH 用传统 VSync,因为兼容性最好。

### 10.4 VSync 的延迟分析

144Hz 显示器,1 帧 6.9ms。

- VSync off:CPU 提交 → GPU 渲染 → 显示,延迟 ~10-15ms
- VSync on:CPU 提交 → 等 refresh → 显示,延迟 ~14ms(多 1 帧)

电竞玩家关 VSync 拿低延迟。普通玩家开 VSync 拿流畅。casey HH 是单机游戏,VSync 优先。

### 10.5 sRGB 色彩空间

sRGB 是标准色彩空间,1996 年 HP / Microsoft 提出。特点:

- **gamma 2.2 curve**:暗部更多 bit(人眼对暗部敏感)
- **8 bit/channel**:0-255 但实际等价 12 bit linear
- **行业标准**:网页、图片、视频都用 sRGB

### 10.6 sRGB 与渲染

GPU 渲染要在**线性空间**做光照计算,然后转 sRGB 输出。但默认情况下:

- 纹理按 sRGB 加载(GPU 不知道)
- shader 在 sRGB 空间计算(错误)
- 输出 framebuffer 也是 sRGB(double gamma)

正确做法:

1. 纹理标 `GL_SRGB8_ALPHA8`,GPU 自动转 linear
2. shader 在 linear 计算
3. framebuffer 标 sRGB(`GL_FRAMEBUFFER_SRGB`),GPU 自动转 sRGB 输出

```rust
// 1. 纹理 sRGB
gl.tex_storage_2d(glow::TEXTURE_2D, 1, glow::SRGB8_ALPHA8, w, h);

// 2. shader 在 linear(无需特殊处理,只要输入是 linear)

// 3. framebuffer sRGB
gl.enable(glow::FRAMEBUFFER_SRGB);
```

### 10.7 不用 sRGB 的后果

casey HH 早期没用 sRGB,出现:

- 中间灰度偏暗(gamma 2.2 double apply)
- 光照不正确(specular highlight 偏移)
- 颜色混合错(sRGB 空间 mix 不是 linear mix)

day241 修复后,颜色正确。casey 在视频里反复对比"修复前 vs 后",教学清晰。

### 10.8 HDR 渲染

HDR(High Dynamic Range)渲染:颜色 > 1.0(允许亮于白色)。

- 用 R16F / R32F 浮点 framebuffer
- 光照计算在 HDR linear space
- 最后 tone mapping 转回 SDR(Standard Dynamic Range)

HDR 显示器(2020+):直接显示 HDR 内容,亮度 1000+ nit。Windows HDR 模式 / PS5 / Xbox Series X 支持。

casey HH 不用 HDR(SDR 8-bit 就够)。商业 3A 游戏普遍用 HDR。

### 10.9 教学总结

day241 的核心要点:

1. **VSync**:防 tearing,代价是延迟 +1 frame
2. **Adaptive / G-Sync**:折中方案
3. **sRGB 是色彩空间**:不是 RGB 一样的"线性"
4. **正确 sRGB**:纹理 SRGB8_ALPHA8 + shader linear + framebuffer SRGB
5. **HDR 渲染**:未来方向,casey HH 不用

day241 让 casey HH 的颜色显示正确,VSync 平滑。这是 OpenGL 集成的细节优化。
