
# Day 178 · 线程安全的性能计数器

> Day 122 起游戏变成多线程——主线程跑游戏逻辑,工作线程做资产加载。Day 177 的 profiler 只有一个 thread_local record,工作线程上的 cycle 数据看不到。今天 Casey 让 profiler 跨线程:多线程同时记,汇总时合并。

## 0 · 为什么要有这一天

Day 177 的 profiler 在单线程下完美工作。但你启动第二个线程(比如后台加载纹理),会发生什么?

```rust
// 主线程
thread_local! { static RECORD: ... }

std::thread::spawn(|| {
    let _s = ProfileSpan::enter("load_texture");
    // 这个 span 写到的是**工作线程**的 thread_local
    // 主线程的 HISTORY 看不到这条记录
});
```

`thread_local!` 是**每线程独立**,这是它的优点(无锁、快),也是它的缺点(汇总麻烦)。

第二个问题:跨线程共享一个"总耗时"变量时,普通 `+= ` 会**数据竞争**(race condition):

```rust
static mut TOTAL_CYCLES: u64 = 0;
// 线程 A
TOTAL_CYCLES += 100;  // 读 + 加 + 写,3 条指令
// 线程 B 同时
TOTAL_CYCLES += 200;
// 结果可能是 100、200、300,不确定!
```

`+=` 在 CPU 上是 `read → add → write` 三步,中间任意一步被其他线程插入都会出错。这就是**数据竞争**——Rust 的 `unsafe` 之外的安全 Rust 不允许这种事发生(编译期拒绝)。

今天解决两件事:
1. 怎么用 atomic 操作(`AtomicU64`)做无锁累加
2. 怎么跨线程汇总 thread_local 数据

心理锚点:看完今天,你能写出**4 个线程同时记 cycle 不出错**的 profiler,并能解释 `Ordering::Relaxed` 为什么够(不需要 `SeqCst`)。

## 1 · Casey 今天做了什么

Casey 之前在 C 里用 `InterlockedAdd64`(Windows 原子加)。今天他把 profiler 改成多线程:

1. 每个 cycle 计数器改成 `volatile __int64`(等价 atomic)
2. 用 `InterlockedExchangeAdd64` 累加(对应 Linux 的 `__sync_fetch_and_add`)
3. frame 结束时,主线程读所有计数器,**清零**
4. 强调:profiler 数据**不需要强一致**,允许丢失某帧某线程的数据,只要"总体趋势"准

Rust 翻译版用 `AtomicU64`,API 更现代。

## 2 · 心智模型

### 类比:多个收银台同时记账

超市有 4 个收银台,每个收银员自己记今天收了多少钱(本地账本)。下班时,经理把 4 个本地账本加起来(汇总),得到当天总收入。

这个模式叫 **per-thread accumulation + aggregation**:
- **per-thread accumulation**:每个线程本地累加,**无锁**
- **aggregation**:汇总时主线程读所有线程的值,加总

对比"中央收银机"(共享 atomic):
- 共享 atomic:每次 `+1` 都要 atomic instruction,4 个线程竞争同一个 cache line,**慢**
- per-thread:每线程本地变量无锁,**快**,只有汇总时读一次

游戏 profiler 用 per-thread 模式更优。但**某些总计数器**(比如"游戏总运行 cycle")用共享 atomic 更合适,因为它要被多个线程实时读。

### 2.1 `AtomicU64` 基础

```rust
use std::sync::atomic::{AtomicU64, Ordering};

static TOTAL: AtomicU64 = AtomicU64::new(0);

// 累加,返回旧值
let old = TOTAL.fetch_add(100, Ordering::Relaxed);
// 等价于 atomic: TOTAL = TOTAL + 100; return old_TOTAL;

// 读
let val = TOTAL.load(Ordering::Relaxed);
// 写
TOTAL.store(0, Ordering::Relaxed);
```

**关键概念**:

1. **`AtomicU64`** — Rust 标准库的原子类型。`atomic` 在 CPU 层面是单条指令(x86_64 的 `lock xadd`),不可被打断
2. **`Ordering`** — 内存序,告诉 CPU 和编译器"我对这个原子操作有多严格":
   - `Relaxed`:无同步保证,只保证本原子操作自己原子。**profiler 用这个**
   - `Acquire` / `Release`:用于 mutex-like 同步
   - `SeqCst`(顺序一致):最强保证,所有线程看到同一顺序。**最慢,通常不需要**

### 2.2 为什么 profiler 用 Relaxed?

profiler 计数器的特点:

- **不参与跨线程数据传递**(线程 A 不会靠"写 counter"通知线程 B)
- **只关心计数本身原子**(不丢不多算)
- **允许"读到的值略旧"**(下一帧读到也行)

`Relaxed` 正好满足。`SeqCst` 强制全局顺序,profiler 不需要。

举例:

```rust
use std::sync::Arc;
use std::thread;

let counter = Arc::new(AtomicU64::new(0));

let handles: Vec<_> = (0..4).map(|_| {
    let c = counter.clone();
    thread::spawn(move || {
        for _ in 0..1_000_000 {
            c.fetch_add(1, Ordering::Relaxed);
        }
    })
}).collect();

for h in handles { h.join().unwrap(); }

assert_eq!(counter.load(Ordering::Relaxed), 4_000_000);
```

4 个线程各加 100 万次,最终精确等于 400 万。**任何 Ordering 都能保证这个**(Relaxed 也行)。

Ordering 的差别在"**有没有别的变量要同步**"。profiler 只累加一个数,不同步别的,所以最弱的 Relaxed 够。

### 2.3 per-thread 累加 + 汇总模式

```rust
use std::cell::RefCell;
use std::collections::HashMap;

thread_local! {
    static LOCAL_CYCLES: RefCell<HashMap<&'static str, u64>> = RefCell::new(HashMap::new());
}

static AGGREGATED: Mutex<HashMap<&'static str, u64>> = Mutex::new(HashMap::new());

// 每线程累加(无锁)
impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        LOCAL_CYCLES.with(|m| {
            *m.borrow_mut().entry(self.name).or_insert(0) += elapsed;
        });
    }
}

// 每帧结束时,主线程汇总
pub fn aggregate_to_global() {
    LOCAL_CYCLES.with(|m| {
        let local = std::mem::take(&mut *m.borrow_mut());
        let mut g = AGGREGATED.lock().unwrap();
        for (k, v) in local {
            *g.entry(k).or_insert(0) += v;
        }
    });
}
```

但这只汇总了**主线程的 local**。工作线程的 local 怎么汇总?

### 2.4 收集所有线程的 local

thread_local 的设计天然是"线程私有",主线程没法直接读其他线程的 local。两种解法:

**方案 A:线程结束时 register 到全局 list**

```rust
use std::sync::Mutex;

static ALL_LOCALS: Mutex<Vec<HashMap<&'static str, u64>>> = Mutex::new(Vec::new());

thread_local! {
    static LOCAL_CYCLES: RefCell<HashMap<&'static str, u64>> = RefCell::new(HashMap::new());
}

// 在每个线程退出时(用 Drop 注册)
pub struct ThreadRegistration;
thread_local! {
    static THREAD_GUARD: ThreadRegistration = ThreadRegistration;
}

impl Drop for ThreadRegistration {
    fn drop(&mut self) {
        LOCAL_CYCLES.with(|m| {
            let local = std::mem::take(&mut *m.borrow_mut());
            ALL_LOCALS.lock().unwrap().push(local);
        });
    }
}

// 在工作线程入口摸一下 THREAD_GUARD,确保退出时触发 Drop
fn worker_thread() {
    let _g = THREAD_GUARD.with(|_| ());  // force init
    // 干活
}
```

**方案 B:用全局共享 atomic 计数器**

更简单的做法:**每个 cycle 名对应一个全局 atomic**,profile span 直接 atomic add:

```rust
use std::sync::atomic::AtomicU64;
use std::collections::HashMap;
use std::sync::Mutex;

static COUNTERS: Mutex<HashMap<&'static str, AtomicU64>> = Mutex::new(HashMap::new());

impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        // 注意:这里仍然要 lock HashMap 才能拿到 AtomicU64
        // 想完全无 lock,要用别的设计(下面讲)
        let map = COUNTERS.lock().unwrap();
        if let Some(c) = map.get(self.name) {
            c.fetch_add(elapsed, Ordering::Relaxed);
        }
    }
}
```

但这每帧 N 次 drop 都要 lock,太慢。

**方案 C(最优)**:线程结束时把 thread_local 汇总到 atomic 全局

```rust
thread_local! {
    static LOCAL_CYCLES: RefCell<HashMap<u64 /* name hash */, u64>> = RefCell::new(HashMap::new());
}

// 全局:hash → atomic counter
use dashmap::DashMap;  // 或自己写 lock-free
static GLOBAL: DashMap<u64, AtomicU64> = DashMap::new();

// 每帧结束时(主线程),读自己的 LOCAL_CYCLES 累加到 GLOBAL
// 工作线程结束时,也把自己的累加(用 thread destructor)
```

Casey 在 day 178 用了类似方案 C 的设计。

### 2.5 线程 ID 快速获取

每个 span 还要记"哪个线程跑的",便于在 UI 里区分。怎么高效拿线程 ID?

Linux 上有三种:

```rust
// 1. syscall gettid(每次 ~50ns)
use libc::gettid;
let tid = unsafe { gettid() };

// 2. pthread_self (返回 pthread_t,可能是指针)
let ptid = unsafe { libc::pthread_self() };

// 3. thread_local cache(首次 gettid,之后直接读 TLS)
thread_local! { static CACHED_TID: u32 = unsafe { libc::gettid() }; }
let tid = CACHED_TID.with(|t| *t);  // 极快
```

Casey 在 day 182 详细优化这个(从 50ns 降到 5ns)。今天先用 syscall 版本。

### 2.6 happens-before 关系的直觉

`Ordering` 是 C++11 引入的内存模型概念,Rust 全盘继承。要理解为什么需要它,先看一个反面例子:

```
// 线程 A
data = 42;            // 普通写
ready = true;         // 普通写

// 线程 B
while (!ready) {}     // 普通读
print(data);          // 期望 42,但实际可能是 0!
```

为什么 `print(data)` 可能打出 0?因为编译器和 CPU 都会**重排指令**:

- x86_64 是强序架构(Store-Store 不重排,Load-Load 不重排),所以**实际上**不会出问题
- ARM / POWER 是弱序架构,`data = 42; ready = true;` 可能被重排成 `ready = true; data = 42;`
- 编译器(O2/O3)也可能重排普通变量

`Ordering::Release` 在写、`Ordering::Acquire` 在读,就建立 **happens-before** 关系:Release 之前的所有写,对 Acquire 之后的读可见。

```
// 线程 A
data = 42;
READY.store(true, Ordering::Release);  // 之前的写都"释放"

// 线程 B
while (!READY.load(Ordering::Acquire)) {}  // "获取"之前的所有写
print(data);  // 一定看到 data == 42
```

**回到 profiler**:profiler 的 `fetch_add(cycles, Relaxed)` 不建立 happens-before,因为它**不需要**——没人靠"counter 写完了"来推断别的数据准备好。`Relaxed` 在所有 CPU 上仍然保证**这条指令本身原子**,只是不约束重排。

记忆要点:
- **atomic 本身** = "这条指令不被打断,读改写整体完成" — 所有 Ordering 都保证
- **Ordering** = "顺带还约束其他内存操作的重排" — 强度递增:Relaxed < Release/Acquire < AcqRel < SeqCst

### 2.7 cache line 与 false sharing

x86_64 的 cache line 是 64 字节。CPU 加载 / 失效内存以 cache line 为单位。两个线程各自原子加**同一 cache line 上**的两个不同变量,会导致 cache line 反复失效再同步——这叫 **false sharing**(伪共享),性能损失 5-10 倍。

```
// bad:两个 atomic 在同一 cache line
struct Bad {
    a: AtomicU64,   // 偏移 0
    b: AtomicU64,   // 偏移 8 —— 和 a 在同一 64 字节 cache line
}

// good:用 padding 隔开
#[repr(align(64))]
struct Good {
    a: AtomicU64,
    _pad1: [u8; 56],  // 把 a 单独占一个 cache line
    b: AtomicU64,
    _pad2: [u8; 56],
}
```

Rust 的 `#[repr(align(64))]` 强制 struct 对齐到 64 字节边界。`crossbeam` 的 `CachePadded<T>` 封装了这个模式。

```bash
# Linux 上看你的 CPU 的 cache line 大小
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
# 输出: 64

# 看所有 cache level
lscpu | grep cache
# L1d cache: 48 KiB
# L1i cache: 32 KiB
# L2 cache:  1280 KiB
# L3 cache:  12288 KiB
```

**profiler 工程建议**:per-thread 的本地计数器天然在不同 cache line(每线程的 thread_local 是独立内存),无 false sharing。但**全局共享的 atomic** 要小心,如果它和其他热数据挤在一个 cache line,会被反复 invalidate。

### 2.8 多核可扩展性测量

理想的多线程 profiler:**线程数翻倍,profiler 开销不变**。实际测量方法:

```bash
# 1 线程跑 baseline
hyperfine --warmup 3 './target/release/bench --threads 1'
# 8 线程跑
hyperfine --warmup 3 './target/release/bench --threads 8'
# 如果 8 线程总时间 ≈ 1 线程总时间 → 完美扩展
# 如果 8 线程总时间 > 1 线程总时间 × 2 → 有 contention
```

Casey 的 per-thread 设计在 1-8 线程扩展接近线性(竞争主要在汇总时),完美。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

多线程 profiler 的典型用法:

- **主线程**:游戏逻辑、UI(主要耗时)
- **render 线程**:GPU 提交(中等耗时)
- **worker 池**:资产加载、AI 路径(N 个并行)
- **audio 线程**:音频混合(必须实时)

profiler 要能区分这些线程,UI 上能筛选。

### 3.2 · 🐧 Linux 系统编程视角

Linux atomic 的底层实现:

```bash
# 看 fetch_add 编译成什么
echo 'use std::sync::atomic::{AtomicU64, Ordering};
fn main() { let a = AtomicU64::new(0); a.fetch_add(1, Ordering::Relaxed); }' \
| rustc -O --emit asm -o /tmp/atomic.s -
grep -E "lock|xadd" /tmp/atomic.s
# 应该看到:lock xadd %rsi, (%rdi)
# lock 前缀让这条指令在所有 CPU 核上原子(锁 cache line)
```

`lock xadd` 在 x86_64 上是 1 条指令,但**带 lock 前缀**意味着:
- 其他 CPU 核不能同时修改同一 cache line
- 性能代价:1-10 cycle(看 cache line 状态),比普通 add 慢 5-10 倍

这就是为什么 per-thread accumulation 更快——避免竞争。

Linux 上看 cache line contention:

```bash
sudo perf stat -e cache-misses ./target/release/my_game
# cache-misses 高 → 多线程在抢同一 cache line,考虑 per-thread
```

### 3.3 · 🦀 Rust 生态视角

Rust 的 atomic 类型:

| 类型 | 大小 | 等价 CPU 指令 |
|---|---|---|
| `AtomicBool` | 1 | `lock xchg` / `lock cmpxchg` |
| `AtomicU8/U16/U32/U64` | 1/2/4/8 | `lock xadd` |
| `AtomicPtr<T>` | 8 | `lock cmpxchg`(双字 CAS) |
| `AtomicUsize` | 8(64位) | 同上 |

注意:**x86_64 没有 16 字节的原子操作**(要 cmpxchg16b,有些 CPU 不支持)。Rust 标准库没有 `AtomicU128`。

`portable-atomic` crate 提供 fallback,适合跨平台项目。

**Ordering 的 Rust 选择**:
- profiler / 计数器:`Relaxed`
- mutex / flag:`Acquire` / `Release`
- 全局严格顺序(罕见):`SeqCst`

### 3.4 · 🎨 图形学视角(多线程渲染管线)

现代游戏引擎的渲染是多线程的,但**GPU 提交**这个动作通常单线程化(因为 GL/Vulkan context 不是线程安全)。典型架构:

```
[game logic thread] → [render thread] → [GPU]
                            ↓
                       提交 command buffer
```

profiler 要能**跨这两个线程**展示"游戏逻辑等渲染线程的时间"。Casey 的设计:在 game thread 的 span 之间插一个 "wait for render" span,它实际是阻塞在 condvar 上。这样 UI 看到的"游戏线程等待时间"就是渲染没跟上来的时间。

Vulkan/D3D12 进一步把渲染分成多个线程(record / submit / present),每个都要单独 profiler。Casey 在 Phase 5 还在 OpenGL,多线程渲染要等 Phase 6+。

### 3.5 · 🐧 Linux futex 与 pthread_mutex 的内部

Rust 的 `Mutex` 在 Linux 上基于 `pthread_mutex_t`,而 `pthread_mutex` 在内核里用 **futex**(fast userspace mutex)实现:

- **不加锁时**(常见情况):atomic CAS 检测 lock 状态,失败返回。**纯用户态,~10 ns**
- **要等待时**:调 `futex(syscall)`,内核挂起当前线程。**~1-2 μs**

profiler 的 `COUNTERS.lock()` 在每帧结束时获取一次,几乎无竞争——所以实际开销 10 ns 量级,可接受。**但如果在 hot path 上 lock,就会爆**。Casey 的设计哲学:**hot path 永远在 thread_local,cold path 才 lock**。

```bash
# 看 futex 调用次数
sudo perf stat -e syscalls:sys_enter_futex ./target/release/my_game 2>&1 | grep futex
# 如果每秒几万次 → 锁竞争激烈,要改 lock-free
```

## 4 · 认知地图

### 4.1 上级

- **无锁编程(lock-free programming)** — 用原子操作代替锁
- **per-thread 模式** — 每线程一份状态,合并时汇总
- **数据竞争 vs 竞争(contention)** — 数据竞争是 bug,竞争是性能问题

### 4.2 同级

| 方案 | 多线程安全 | 性能 | 实现复杂度 |
|---|---|---|---|
| `Mutex<HashMap>` | 是 | 慢 | 低 |
| `AtomicU64` per key | 是 | 快 | 中 |
| per-thread + aggregate | 是 | 极快 | 中 |
| 全局 lock-free hash | 是 | 极快 | 高 |

### 4.3 下级

- `AtomicU64::fetch_add` — 累加原子
- `Ordering::Relaxed` — 最弱保证
- `thread_local!` + thread destructor — per-thread 数据汇总
- thread ID cache — 标记 span 归属

## 5 · 对照与变奏

**不同语言的 atomic**:

| 语言 | API |
|---|---|
| Rust | `AtomicU64::fetch_add(.., Relaxed)` |
| C++ | `std::atomic<uint64_t>::fetch_add(.., memory_order_relaxed)` |
| C | `__sync_fetch_and_add` (GCC) / `_InterlockedExchangeAdd64` (MSVC) |
| Java | `AtomicLong.addAndGet` |
| Go | `atomic.AddUint64` |

Rust 的 ordering 是**必须**写的(不能默认),这其实是好事——强迫你想清楚。

**profiler 的"丢失精度"哲学**:

Casey 反复强调:**profiler 允许丢数据**。比如某个 span 没记录到,没事,只要"趋势"对。这种"软"承诺让 profiler 可以用 lock-free 而不用阻塞游戏线程。

工业级 profiler(superluminal / vtune)更严格,但价格也高(钱 + 性能开销)。

### 历史脉络:从锁到无锁

1990 年代多 CPU 服务器普及前,绝大多数程序单线程,profiler 只关心"哪个函数慢"。2000 年代双核 / 四核消费 CPU 出现,大家开始用 `Mutex`——简单但 contention 高。

2000 年代中期,lock-free 数据结构(Michael-Scott 队列、Harris 链表)成熟,Rust 的 `crossbeam` 就是这条线。Casey 在 day 178 选 per-thread + aggregate 是更简单的方案——**多数游戏不需要 lock-free hash map**,thread_local 就够。

| 时代 | 主流方案 | 代表 |
|---|---|---|
| 1990 | 单线程 profiler | gprof |
| 2000 | Mutex 保护 | gperftools (Google) |
| 2010 | lock-free + per-thread | puffin / superluminal |
| 2020 | 分布式 / remote | Unreal Insights |

### 与 Bevy 引擎的对比

Bevy(Rust 生态主流 ECS 引擎)用 `bevy_utils::tracing` 做 profiling——本质是 `tracing` crate 的 `Span::enter()`。tracing 的设计哲学和 Casey 不同:

- **tracing**:订阅式(subscriber-based)。事件被订阅者收集,可以同时输出到多个目标(终端 / 文件 / 远程)
- **Casey**:push 式,直接写入 ring buffer,没有中间层

tracing 的优点:灵活、生态丰富(可对接 OpenTelemetry)。缺点:多了一层间接,延迟略高。Casey 的设计**直白**——直接写 buffer,适合教学和小项目。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:`Ordering::Relaxed` 和 `Ordering::SeqCst` 都能保证 atomic 操作本身原子。它们的差别是什么?profiler 为什么用 Relaxed?

**参考解答**:
- **atomic 操作原子**(都是 8 字节整体读写,不会被部分看到)— 任何 Ordering 都保证
- **Ordering 控制"其他内存操作能不能重排到 atomic 前后"**:
  - `Relaxed`:无限制,编译器和 CPU 可以自由重排。**只保证 atomic 本身**
  - `SeqCst`:所有 SeqCst 操作形成全局顺序,所有线程看到同一序列。**最强但最慢**
  - `Acquire` / `Release`:成对使用,Release 写 + Acquire 读建立 happens-before 关系
- profiler 用 Relaxed,因为:
  - counter 不参与跨线程同步(线程 A 不会靠"counter = 100"通知线程 B "数据好了")
  - 允许"读到略旧值"(下一帧再读也行)
  - 性能最好(无 fence,无 cache 同步)

### Lv2 · 动手实践

**题**:写一个多线程 profiler,要求:
- `ProfileSpan` 记 cycle 到 thread_local
- 工作线程结束时(用 Drop guard)汇总到全局 `AtomicU64`
- 启 4 个工作线程,各跑 1000 次 span
- 主线程最后打印"每个 cycle 名"的总数

**参考解答**:

```rust
use std::cell::RefCell;
use std::collections::HashMap;
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Mutex;
use std::hint::black_box;

#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    unsafe {
        let lo: u32; let hi: u32;
        core::arch::asm!("rdtsc",
            out("eax") lo, out("edx") hi,
            options(nomem, nostack));
        ((hi as u64) << 32) | (lo as u64)
    }
}

thread_local! {
    static LOCAL: RefCell<HashMap<&'static str, u64>> = RefCell::new(HashMap::new());
    static THREAD_REGISTERED: ThreadExitGuard = ThreadExitGuard;
}

// 全局 atomic 计数器
static COUNTERS: Mutex<HashMap<&'static str, AtomicU64>> = Mutex::new(HashMap::new());

fn ensure_counter(name: &'static str) -> &'static AtomicU64 {
    // 注意:这个简化版用 leak 保证 'static(教学用,生产用 Box::leak 或 lazy_static)
    let mut m = COUNTERS.lock().unwrap();
    if !m.contains_key(name) {
        // 真实代码:用 once_cell 或 lazy_static。这里简化
        m.insert(name, AtomicU64::new(0));
    }
    // 这是教学版,实际会有 lifetime 问题。生产代码用 OnceLock<HashMap> 包 Arc
    unsafe {
        let p = m.get(name).unwrap() as *const AtomicU64;
        &*p
    }
}

pub struct ProfileSpan { name: &'static str, start: u64 }
impl ProfileSpan {
    pub fn enter(name: &'static str) -> Self {
        Self { name, start: rdtsc() }
    }
}
impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        LOCAL.with(|m| *m.borrow_mut().entry(self.name).or_insert(0) += elapsed);
    }
}

// 线程退出时,把 LOCAL 汇总到全局
pub struct ThreadExitGuard;
impl Drop for ThreadExitGuard {
    fn drop(&mut self) {
        let local = std::mem::take(&mut *LOCAL.borrow_mut());
        let m = COUNTERS.lock().unwrap();
        for (k, v) in local {
            if let Some(c) = m.get(k) {
                c.fetch_add(v, Ordering::Relaxed);
            }
        }
    }
}

fn worker() {
    // 确保 THREAD_REGISTERED 初始化
    THREAD_REGISTERED.with(|_| ());
    for _ in 0..1000 {
        let _s = ProfileSpan::enter("worker_compute");
        for _ in 0..1000 { black_box(0u64.wrapping_add(1)); }
    }
}

fn main() {
    THREAD_REGISTERED.with(|_| ());
    let handles: Vec<_> = (0..4).map(|_| std::thread::spawn(worker)).collect();
    for h in handles { h.join().unwrap(); }

    let m = COUNTERS.lock().unwrap();
    for (k, v) in m.iter() {
        println!("{}: {} cycles", k, v.load(Ordering::Relaxed));
    }
}
```

**注意**:教学版用 `unsafe` 处理 lifetime。生产代码应该用 `OnceLock<HashMap<u64, Arc<AtomicU64>>>`。

**预期输出**:`worker_compute: ~<某大数> cycles`(4 个线程 × 1000 次 × ~1000 cycle ≈ 几百万 cycle)

## 8 · Rust / Arch 落地代码

完整可跑项目(简化版,无 unsafe):

```rust
// Cargo.toml
// [dependencies]
// once_cell = "1"

use once_cell::sync::Lazy;
use std::cell::RefCell;
use std::collections::HashMap;
use std::hint::black_box;
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Mutex;

#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    unsafe {
        let lo: u32; let hi: u32;
        core::arch::asm!("rdtsc",
            out("eax") lo, out("edx") hi,
            options(nomem, nostack));
        ((hi as u64) << 32) | (lo as u64)
    }
}

static COUNTERS: Lazy<Mutex<HashMap<&'static str, AtomicU64>>> =
    Lazy::new(|| Mutex::new(HashMap::new()));

thread_local! {
    static LOCAL: RefCell<HashMap<&'static str, u64>> = RefCell::new(HashMap::new());
    static THREAD_EXIT_GUARD: ThreadExitGuard = ThreadExitGuard;
}

pub struct ProfileSpan { name: &'static str, start: u64 }
impl ProfileSpan {
    pub fn enter(name: &'static str) -> Self { Self { name, start: rdtsc() } }
}
impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let elapsed = rdtsc() - self.start;
        LOCAL.with(|m| *m.borrow_mut().entry(self.name).or_insert(0) += elapsed);
    }
}

pub struct ThreadExitGuard;
impl Drop for ThreadExitGuard {
    fn drop(&mut self) {
        let local = std::mem::take(&mut *LOCAL.borrow_mut());
        let m = COUNTERS.lock().unwrap();
        for (k, v) in local {
            m.get(k).map(|c| c.fetch_add(v, Ordering::Relaxed));
        }
    }
}

pub fn register_thread() {
    THREAD_EXIT_GUARD.with(|_| ());
}

pub fn ensure_counter(name: &'static str) {
    let mut m = COUNTERS.lock().unwrap();
    m.entry(name).or_insert_with(|| AtomicU64::new(0));
}

fn worker(n: u32) {
    register_thread();
    ensure_counter("worker");
    for _ in 0..1_000 {
        let _s = ProfileSpan::enter("worker");
        for _ in 0..1_000 { black_box(0u64.wrapping_add(1)); }
    }
    println!("worker {} done", n);
}

fn main() {
    register_thread();
    ensure_counter("worker");

    let handles: Vec<_> = (0..4).map(|n| {
        std::thread::spawn(move || worker(n))
    }).collect();
    for h in handles { h.join().unwrap(); }

    println!("=== final counters ===");
    let m = COUNTERS.lock().unwrap();
    for (k, v) in m.iter() {
        println!("{}: {} cycles", k, v.load(Ordering::Relaxed));
    }
}
```

**Troubleshooting**:

- 编译时 `&'static AtomicU64` lifetime 错 — 用 `OnceLock` 或 `Lazy`(如上)
- 工作线程数据没汇总 — 确保 worker 函数开头调了 `register_thread()`
- 计数器 0 — Drop 触发时机:`join` 等线程退出,退出时 thread_local 才 drop
- **Cargo.toml 用 `Lazy` 报错** — `once_cell` 加到 `[dependencies]` 段
- **join 卡住** — 工作线程 panic 了,thread_local Drop 仍然触发(panic unwind),应该没问题;但如果是 `panic = "abort"`,Drop 不调,数据丢失
- **计数器永远 0** — main 也在写 worker_compute,但没 register。在 main 开头加 `register_thread();`
