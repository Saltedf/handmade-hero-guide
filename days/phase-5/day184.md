
# Day 184 · 整理调试事件

> 事件流存下来了,但**原始事件流没法直接看**——10000 条 event 闪过去什么都看不清。今天 Casey 把 event 流组织成"按 GUID 分组 + 按帧分组"的结构,为后面的 UI 渲染做准备。

## 0 · 为什么要有这一天

让我们停下来,真实地感受一下"原始 event 流"的痛。你在 Day 183 已经把 profiler 接通了,每帧能产生几千条 begin/end event。你 `cat events.log | head -n 100`,屏幕上滚过这样一片:

```
cycle=100 begin update_player
cycle=120 begin update_audio
cycle=140 end   update_audio
cycle=200 begin update_render
cycle=500 end   update_render
cycle=600 end   update_player
```

你看着这一万行,本能地问自己三个问题,但**没有一个能直接回答**:

第一个问题——"update_player 这帧总共花了多少?" 你不能简单求和所有标 update_player 的行,因为日志里只有 begin/end 各一条。你要先**配对**(找匹配的 begin 和 end),再**相减**(end.cycle - begin.cycle)。在脑子里你能算,但 10000 行你算不动。所以你需要一段代码替你算。

第二个问题——"update_player 平均花多少?" 这要跨多帧聚合。你要把每帧算出来的"该帧 update_player 的耗时"收集起来,统计均值、最大值、最小值。一个浮点除法的事,但你必须先有"每帧的耗时列表"才能算。这又回到上一个问题:必须先配对。

第三个问题——"update_player 被谁调用了?" 这是最难的。begin/end 是一条**线性的时间线**,但调用关系是**树状的**。你要从时间线"重建"出调用树:某个 update_player 的 begin 落在另一个 update_frame 的 begin 之后、end 之前,说明 player 是被 frame 调用的。这个"重建"就是今天 Casey 做的事。

换句话说,Day 183 的输出是**事实流**(facts),今天的输出是**理解流**(insights)。事实流是机械的,理解流需要数据建模。今天 Casey 做的 collation,就是把事实流**投影**到多个理解视图——按 GUID 聚合、按帧分组、按调用栈嵌套。

工业界这种"事实 → 理解"的转换有个通用名字叫 **collation**(整理、归并)。它出现在每一个 event-driven 系统里:Linux perf、Chrome tracing、Unreal Insights、Distributed tracing(Jaeger、Tempo)、SQL log analysis——所有这些都先收 raw event,再 collation 成可分析的视图。今天你亲手做一遍这件事,以后看任何 profiler 都不再觉得神秘。

整理后的目标数据结构,Casey 选了三个并列视图,各自回答一类问题:

```rust
// 视图 1:按 GUID 聚合——回答"这个函数表现如何?"
struct FrameSummary {
    frame_index: u64,
    spans_by_guid: HashMap<u64, SpanStats>,
}

struct SpanStats {
    count: u32,         // 这帧调用了几次
    total_cycles: u64,  // 这帧总耗时(含所有调用)
    max_cycles: u64,    // 这帧最长一次调用
    min_cycles: u64,    // 这帧最短一次调用
    children: Vec<u64>, // 嵌套的子 span GUID(用于调用图)
}

// 视图 2:按调用栈嵌套——回答"谁调用了谁?"
struct SpanNode {
    guid: u64,
    begin_cycle: u64,
    end_cycle: u64,
    children: Vec<SpanNode>,  // 递归
}

// 视图 3:跨帧趋势——回答"长期趋势如何?"
struct TrendStats {
    recent_avg: f64,    // 过去 60 帧均值
    recent_max: u64,    // 过去 60 帧最大值
    lifetime_avg: f64,  // 启动以来均值
}
```

这三个视图不是冗余,而是**正交**:`SpanStats` 让你横着看(同函数,跨调用),`SpanNode` 让你竖着看(同帧,跨函数),`TrendStats` 让你顺着时间看(同函数,跨帧)。一个完整的 profiler UI 通常需要三者都展示——这就是为什么 Chrome tracing、Tracy、Unreal Insights 的 UI 都有多个面板。

整理过程有一个关键性能指标:**O(N)**——一次扫描收集所有信息。10 万 event 应该在亚毫秒内整理完。如果 collation 比渲染还慢,profiler 自己成了瓶颈,就完全没意义了。所以今天我们一边写 collation,一边盯着每个分配、每个分支,确保它不会成为游戏主循环的负担。

**学完今天,你应该能**:
- 解释为什么"原始 event 流"无法直接展示,必须经过 collation
- 用栈算法把 begin/end 流配对成 span instances,处理严格嵌套
- 用 HashMap 把 span instances 聚合成按 GUID 的统计视图
- 用栈构建调用树,把 begin/end 流变成嵌套的 SpanNode
- 用 RingBuffer 保存历史趋势,在 UI 上画出 recent vs lifetime 对比
- 设计 zero-allocation 的 collator:buffer 复用,避免每帧 alloc/free

## 1 · Casey 今天做了什么

Casey 写了一个**整理阶段**(collation phase):

1. 帧结束时,主线程把所有 event 排序(按 cycle)
2. 用栈配对 begin/end(同线程内嵌套)
3. 配对成功后,聚合到当前帧的 SpanStats
4. 跨帧的 SpanStats 推到 ring buffer

他强调:**collation 是纯函数**——输入 event 流,输出 FrameSummary,无副作用。这样容易测试和优化。

## 2 · 心智模型

### 类比:图书馆的索引

图书馆每天进新书(原始 event),但要让人查得到,图书管理员要:
1. 按主题分类(配对 / 分组)
2. 写索引卡片(聚合 stats)
3. 卡片放索引柜(存到 ring buffer)

读者(UI)查卡片,不去翻书(event)。

### 2.1 配对算法的推导

我们要把"begin/end 流"还原成"span 实例列表"。先观察一个简单事实:**同步代码里,函数调用的 begin/end 永远是严格嵌套的**——为什么?因为同步调用栈本身就是 LIFO(后进先出)。函数 A 调用 B,B 先返回,然后 A 才能返回。所以 begin/end 的关系一定是:[A_begin, B_begin, B_end, A_end],不可能出现 [A_begin, B_begin, A_end, B_end](后者意味着 A 先返回了,但 A 还在调用 B)。

**严格嵌套 = LIFO = 栈**。这是关键洞察。任何 LIFO 关系都能用栈高效处理:遇到 begin push,遇到 end pop。pop 出来的就是与当前 end 匹配的 begin。整个过程 O(N) 一次扫描。

为什么不用别的方式?比如:
- **暴力匹配**:每条 end 都扫前面所有 begin 找匹配——O(N²),10 万 event 就是 10^10 次比较,跑几秒,不可接受。
- **哈希表记 begin**:每个 GUID 记最近的 begin cycle,end 来了直接查——但 GUID 在嵌套里可能重复(update_player 里有 update_player 的递归)。栈自然处理递归(每一层独立)。
- **排序**:已经按 cycle 排序了,但排序不能告诉你嵌套关系。

栈是**唯一**能在严格嵌套假设下,一次扫描完成配对的数据结构。Casey 的实现:

```rust
fn collate_thread_events(events: &[Event]) -> Vec<SpanInstance> {
    // 栈里存 (GUID, begin_cycle)。GUID 用于校验 end 是否匹配。
    let mut stack: Vec<(u64 /* guid */, u64 /* begin_cycle */)> = Vec::new();
    let mut spans = Vec::new();

    for e in events {
        match e.kind {
            EventKind::Begin => stack.push((e.guid, e.cycle)),
            EventKind::End => {
                // 弹栈,找匹配的 begin
                if let Some((guid, begin)) = stack.pop() {
                    if guid == e.guid {
                        spans.push(SpanInstance {
                            guid,
                            begin_cycle: begin,
                            end_cycle: e.cycle,
                            duration: e.cycle - begin,
                        });
                    } else {
                        // mismatched: end 来了但栈顶 begin 不是同一 GUID
                        // 这说明 event 流出了 bug(漏 begin 或漏 end)
                        eprintln!(
                            "WARN: mismatched end guid={}, stack top guid={}",
                            e.guid, guid
                        );
                        // 把它放回去,继续处理后续(尽量恢复)
                        stack.push((guid, begin));
                    }
                } else {
                    // 栈空但有 end:event 流损坏
                    eprintln!("WARN: end without begin guid={}", e.guid);
                }
            }
        }
    }
    spans
}
```

每一行的语义:
- `stack: Vec<(u64, u64)>` — 元组在 Rust 里是值类型,放栈上不会被 heap allocate(对短生命周期数据快)。
- `for e in events` — 借用迭代,不 consume。
- `stack.push((e.guid, e.cycle))` — 进入一个新 span,把"我开始记"的信息压栈。
- `stack.pop()` — 返回 `Option<(u64, u64)>`,空栈时 `None`。Rust 强制你处理 None。
- `e.cycle - begin` — cycle 计数器单调递增,end.cycle 一定 > begin.cycle,所以减法不会下溢。
- WARN 分支:运行时检测 event 流错误,不 panic。profiler 数据出错不应该让游戏崩——这是工具的"宽容"原则。

**注意**:`stack.pop()` 假设严格嵌套(LIFO)。如果你的代码有 `par_begin` / `par_end`(并行嵌套)或异步 await,这种配对会错。Casey 假设严格同步嵌套。**异步场景**是个真实的挑战:Rust 的 async/await 会让 future 在 await 点挂起,导致 begin 在一个 task、end 在另一个。要处理这种需要 task-aware profiler(tracing crate 的 instrument macro 做的就是这件事)。

### 2.2 嵌套关系

配对时,**栈深度就是嵌套层级**:

```
begin update_frame    (stack: [update_frame])           depth=1
  begin update_player (stack: [update_frame, player])   depth=2
  end   update_player (stack: [update_frame])           depth=1
  begin update_render (stack: [update_frame, render])   depth=2
  end   update_render (stack: [update_frame])           depth=1
end   update_frame    (stack: [])                       depth=0
```

配对时记下 depth,UI 能画火焰图。

```rust
fn collate_with_depth(events: &[Event]) -> Vec<SpanInstance> {
    let mut stack: Vec<(u64, u64)> = Vec::new();
    let mut spans = Vec::new();

    for e in events {
        match e.kind {
            EventKind::Begin => stack.push((e.guid, e.cycle)),
            EventKind::End => {
                let depth = stack.len() as u32 - 1;
                if let Some((guid, begin)) = stack.pop() {
                    if guid == e.guid {
                        spans.push(SpanInstance {
                            guid, begin_cycle: begin, end_cycle: e.cycle,
                            duration: e.cycle - begin, depth,
                        });
                    }
                }
            }
        }
    }
    spans
}
```

### 2.3 聚合到 SpanStats

```rust
pub fn aggregate(spans: &[SpanInstance]) -> HashMap<u64, SpanStats> {
    let mut map: HashMap<u64, SpanStats> = HashMap::new();
    for s in spans {
        let entry = map.entry(s.guid).or_insert_with(|| SpanStats {
            count: 0, total_cycles: 0, max_cycles: 0, min_cycles: u64::MAX,
        });
        entry.count += 1;
        entry.total_cycles += s.duration;
        entry.max_cycles = entry.max_cycles.max(s.duration);
        entry.min_cycles = entry.min_cycles.min(s.duration);
    }
    map
}
```

**Rust 注释**:
- `or_insert_with(|| ...)` — 不存在时调闭包创建,避免无意义 clone
- `entry.max_cycles.max(s.duration)` — `u64::max` 是 method,链式调

event 流跨帧时,每帧独立 collate。Casey 在 frame_begin 推一条**marker event**:

### 2.5 火焰图的数据结构

火焰图(flame graph)是 Brendan Gregg 2011 年发明的可视化,把调用栈的耗时分布画成一堆叠在一起的矩形。每层是一个函数调用,宽度 = 耗时。

```
┌────────────────────────────────────────────────┐
│              update_frame                      │  depth=0
│ ┌──────────────────┐  ┌──────────────────┐   │
│ │  update_player   │  │  update_render   │   │  depth=1
│ │ ┌──────────────┐ │  │ ┌──────────────┐ │   │
│ │ │ update_audio │ │  │ │ draw_mesh    │ │   │  depth=2
│ │ └──────────────┘ │  │ └──────────────┘ │   │
│ └──────────────────┘  └──────────────────┘   │
└────────────────────────────────────────────────┘
```

要在 UI 画火焰图,collation 输出不是简单的 `Vec<SpanInstance>`,而是**树**:

```rust
pub struct SpanNode {
    pub guid: u64,
    pub begin_cycle: u64,
    pub end_cycle: u64,
    pub children: Vec<SpanNode>,  // 递归
}
```

构建时,栈里维护当前活跃的节点:

```rust
fn build_tree(events: &[Event]) -> Vec<SpanNode> {
    let mut roots: Vec<SpanNode> = Vec::new();
    let mut stack: Vec<SpanNode> = Vec::new();

    for e in events {
        match e.kind {
            Kind::Begin => {
                let node = SpanNode { guid: e.guid, begin_cycle: e.cycle, end_cycle: 0, children: vec![] };
                stack.push(node);
            }
            Kind::End => {
                if let Some(mut node) = stack.pop() {
                    if node.guid == e.guid {
                        node.end_cycle = e.cycle;
                        if let Some(parent) = stack.last_mut() {
                            parent.children.push(node);
                        } else {
                            roots.push(node);
                        }
                    }
                }
            }
        }
    }
    roots
}
```

**关键洞察**:每帧的 roots 列表里每个元素就是一棵树。UI 递归画。

### 2.6 collation 的内存分配策略

每帧 collate 一次,要分配 `Vec<SpanInstance>` 和 `HashMap<u64, SpanStats>`。如果每帧 alloc + dealloc,会:

- **malloc/free 频繁**,触发内存碎片。Linux glibc 的 ptmalloc2 用 arenas + bins,小对象 alloc 很快但仍要锁;MSVC 的 CRT heap 慢得多。
- **cache miss 频繁**,新分配的内存冷(从未被读写过,L1/L2 cache 没有)。下次访问要等几百 cycle 从 DRAM 取。
- **page fault 风险**,如果分配尺寸超出了当前 mmap 区域,要扩 heap。

Casey 用**复用 buffer**:

```rust
struct Collator {
    span_buf: Vec<SpanInstance>,        // 复用
    stats_map: HashMap<u64, SpanStats>, // 复用
}

impl Collator {
    fn collate(&mut self, events: &[Event]) -> &HashMap<u64, SpanStats> {
        self.span_buf.clear();          // 不释放 capacity
        self.stats_map.clear();         // 同上
        // ... 填充 self.span_buf 和 self.stats_map
        &self.stats_map
    }
}
```

**`.clear()` vs `*v = Vec::new()`**:`clear()` 调 `set_len(0)` 但保留 capacity——内存还在你手里,下次 push 不 alloc。`Vec::new()` 是空 vec,赋值给旧变量会 drop 旧内容,然后下次 push 重新 alloc。**hot loop 永远用 clear**。

Rust 中的 capacity 行为可以观察:
```rust
let mut v: Vec<u32> = Vec::with_capacity(1000);
println!("cap={}, len={}", v.capacity(), v.len());  // cap=1000, len=0
for i in 0..1000 { v.push(i); }
println!("cap={}, len={}", v.capacity(), v.len());  // cap=1000, len=1000
v.clear();
println!("cap={}, len={}", v.capacity(), v.len());  // cap=1000, len=0  ← 保留了!
```

这是 data-oriented design 的核心原则之一:**separate the data from its lifetime**。buffer 是数据,filling 是 lifetime event。两者解耦,你就能反复 fill 同一个 buffer,而不用每次 free/alloc。

**HashMap 的 capacity 也有同样行为**,但有微妙差别:`HashMap::clear()` 在 Rust 标准库里保留 capacity(从 1.x 以来如此),但内部 table 仍可能有"tombstone"开销。如果你的 stats_map 在某些帧 GUID 数量爆炸(比如新加 subsystem),capacity 涨了就回不去。如果你想"瘦身",周期性 `shrink_to_fit`。但 hot loop 里不要这么做——`shrink_to_fit` 本身触发 realloc。Casey 选择让它涨到上限就稳定(60 fps 游戏,每帧 GUID 数稳定后 capacity 就不动)。

### 2.7 跨帧的趋势聚合

单帧的 SpanStats 不够看趋势,要**跨 N 帧聚合**:

```rust
pub struct TrendStats {
    pub recent_avg: f64,    // 过去 60 帧 avg(约 1 秒 @60fps)
    pub recent_max: u64,    // 过去 60 帧 max——spike 检测器
    pub lifetime_avg: f64,  // 启动以来 avg
}

impl TrendStats {
    pub fn update(&mut self, frame_stat: &SpanStats, history: &RingBuffer<SpanStats, 60>) {
        // recent_avg:迭代 60 帧的 total_cycles 求均值
        self.recent_avg = history.iter()
            .map(|s| s.total_cycles as f64)
            .sum::<f64>() / history.len() as f64;

        // recent_max:60 帧里的最大 max_cycles
        // 这个值回答"过去一秒最坏时哪个函数最慢"
        self.recent_max = history.iter()
            .map(|s| s.max_cycles)
            .max()
            .unwrap_or(0);

        // lifetime_avg:全局累加器(不能用 history,要单独存 sum 和 count)
        // 在 update 之外维护 self.lifetime_sum 和 self.lifetime_count
    }
}
```

UI 显示"update_player avg=5000 recent_max=15000"。**recent_max 是发现 spike 的关键**——一个偶发的 GC pause、IO 抖动、driver stall,会让 avg 不动但 max 飙到几倍。开发者一眼看 max 列就能定位"是哪个函数偶发性卡"。

这里有个权衡:RingBuffer 容量 60 = 1 秒 @ 60fps。如果你想看更长时间趋势(比如 10 秒),容量加到 600。但内存 = `600 帧 * N 个 GUID * sizeof(SpanStats)`。SpanStats ~40 bytes,N=200 个 GUID,共 4.8 MB——还行。如果 N=10000(精细 profiling),就要 480 MB,不能这么搞。工业级方案是**采样**:不是每帧都存,每 10 帧存一次,牺牲分辨率换内存。

## 3 · 四域深入

### 3.1 · 游戏编程视角

整理阶段的性能要求:**O(N) 或 O(N log N)**。10 万 event / 帧 / 60fps = 600 万 event / 秒。Rust 上扫一遍 Vec 100ns/1000个 event = 600ms/秒,**不能**。要优化到 60ns/1000个 event = 60ms/秒,留 10ms 给游戏逻辑。

Casey 的优化:
- 用 `Vec` 预分配
- 用 `sort_unstable_by_key`(比 stable 快)
- 避免 HashMap(用 GUID 直接索引数组)

### 3.2 · Linux 系统编程视角

Linux 内核的 perf_events 也有 collation:

```bash
sudo perf record -F 99 -ag -- sleep 1
sudo perf report --stdio
```

perf 在内核环形缓冲采 event,`perf report` 用户态做 collation。

### 3.3 · Rust 生态视角

Rust 处理 event 流的 crate:
- `itertools` — group_by, unique, etc.
- `rayon` — 并行处理 event
- `polars` — DataFrame,大数据处理

profiler 数据量不大(每帧 ~MB),不需要这些重型工具。手写 Rust 迭代器够。

### 3.4 · 🎮 游戏编程视角(工业级 profiler 的 collation)

Unreal Insights 的 collation 在 dedicated 线程跑——主线程只 push event 到 lock-free queue,collator 线程 drain + aggregate。这样:

- 主线程零等待
- collator 可以慢慢做(复杂分析)
- 数据可以序列化到磁盘 / 网络

Casey 的设计简化版:**主线程在帧结束时 collate**(此时游戏已经空闲)。trade-off:主线程多花 1ms 做 collation,但简单可靠。

| 设计 | 主线程开销 | 复杂度 |
|---|---|---|
| 主线程同步 collate(Casey) | 1ms / 帧 | 低 |
| 后台 collator 线程(Unreal) | ~0 | 高(需 IPC) |
| GPU compute shader collate | ~0 | 极高 |

### 3.5 · 🐧 Linux 系统编程视角(perf 的 userspace collation)

`perf record` 在内核环形缓冲采 event,`perf report` 在用户态 collate:

```bash
# 看 perf.data 文件大小(原始 event)
ls -la perf.data
# 1MB ≈ 10000 samples

# perf report 做 collation
sudo perf report --stdio --no-children | head -30
# 输出按函数聚合的 cycle 占比:
#  23.5%  my_game   update_player
#  15.2%  my_game   render_batch
#   ...
```

perf 的 collation 用 LBR(Last Branch Record)重建调用栈,比 profiler 的 begin/end 配对复杂——因为采样时只看到当前 PC,要靠 LBR 反推调用路径。Casey 用 begin/end 简单很多。

### 3.6 · 🦀 Rust 生态视角(rayon 并行 collation)

如果 collation 是瓶颈,可以用 `rayon` 并行处理多线程 event:

```rust
use rayon::prelude::*;

let per_thread_spans: Vec<Vec<SpanInstance>> = thread_events
    .par_iter()
    .map(|events| collate_thread(events))
    .collect();
```

但 collation 通常 < 1ms,不值得并行——并行开销(线程池 dispatch)反而拖慢。**先测,再优化**(Casey 的座右铭)。

## 5 · 对照与变奏

**event 配对的不同算法**:

| 场景 | 算法 |
|---|---|
| 同步严格嵌套 | 栈配对(O(N)) |
| 异步(future) | 全局 event table,复杂 |
| 并行(par) | 多栈 / 区间 |
| 网络分布式 | trace context propagation |

游戏 profiler 是"同步严格嵌套",最简单。

### 与 Tracy / puffin 的 collation 设计对比

**Tracy**(业界标准的 C++ profiler)的 collation:

- 服务端-客户端架构:游戏是 server,viewer 是 client
- 通过 socket 实时传输 event
- client 端 collate + 渲染
- 优点:可以远程分析,数据可持久化
- 缺点:网络延迟 + 协议复杂

**puffin**(Rust 轻量级 profiler)的 collation:

- 单进程:游戏 + UI 在一起
- 用 `Arc<Mutex<FrameData>>` 共享
- 每帧 collate 后 store,UI 读
- 优点:简单,跨平台
- 缺点:不能远程

**Casey**:类似 puffin,但**纯手写**,无第三方依赖。教学价值高,生产可用性中等。

### SQL-like 的 collation 抽象

工业 BI(商业智能)工具用 SQL 思路处理 event log:

```sql
SELECT guid, COUNT(*) as calls, AVG(duration) as avg, MAX(duration) as max
FROM spans
WHERE frame_index >= 1000 AND frame_index < 1100
GROUP BY guid
ORDER BY avg DESC
LIMIT 10;
```

如果 profiler 数据量大,可以**存 SQLite**,UI 写 SQL 查询。`rusqlite` crate 很轻量,适合嵌入式。Casey 没做这步(数据量小),但工业级 tracing 系统(Tempo / Jaeger)都基于 SQL/NoSQL 后端。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么配对算法用栈?如果 event 流是 `[A_begin, B_begin, A_end, B_end]`(交叉),栈配对会怎样?

**参考解答**:
- 栈假设严格嵌套(LIFO):`[A_begin, B_begin, B_end, A_end]`
- 交叉情况 `[A_begin, B_begin, A_end, B_end]`:
  - A_begin 入栈: [A]
  - B_begin 入栈: [A, B]
  - A_end 弹栈得 B(mismatched!),日志警告
  - B_end 弹栈得 A(mismatched!)
- 栈配对失败 → 这种 event 流不合法
- 实际同步代码不会交叉(线程内 LIFO 保证),异步代码可能交叉(但 Casey 不用 async)

### Lv2 · 动手实践

**题**:实现 collate 和 aggregate,要求:
- 输入 Vec<Event>
- 输出 Vec<SpanInstance>(带 depth)
- 然后聚合到 HashMap<u64, SpanStats>

**参考解答**:

```rust
#[derive(Clone, Copy, Debug)]
enum Kind { Begin, End }

#[derive(Clone, Copy, Debug)]
struct Event { cycle: u64, guid: u64, kind: Kind }

#[derive(Clone, Debug)]
struct SpanInstance {
    guid: u64, begin_cycle: u64, end_cycle: u64, duration: u64, depth: u32,
}

#[derive(Clone, Debug, Default)]
struct SpanStats {
    count: u32, total_cycles: u64, max_cycles: u64, min_cycles: u64,
}

fn collate(events: &[Event]) -> Vec<SpanInstance> {
    let mut stack: Vec<(u64, u64)> = Vec::new();
    let mut spans = Vec::new();
    for e in events {
        match e.kind {
            Kind::Begin => stack.push((e.guid, e.cycle)),
            Kind::End => {
                let depth = stack.len() as u32 - 1;
                if let Some((guid, begin)) = stack.pop() {
                    if guid == e.guid {
                        spans.push(SpanInstance {
                            guid, begin_cycle: begin, end_cycle: e.cycle,
                            duration: e.cycle - begin, depth,
                        });
                    } else {
                        eprintln!("WARN: mismatched end guid={}, expected={}", e.guid, guid);
                    }
                } else {
                    eprintln!("WARN: end without begin guid={}", e.guid);
                }
            }
        }
    }
    spans
}

fn aggregate(spans: &[SpanInstance]) -> std::collections::HashMap<u64, SpanStats> {
    let mut map = std::collections::HashMap::new();
    for s in spans {
        let entry = map.entry(s.guid).or_insert_with(|| SpanStats {
            count: 0, total_cycles: 0, max_cycles: 0, min_cycles: u64::MAX,
        });
        entry.count += 1;
        entry.total_cycles += s.duration;
        entry.max_cycles = entry.max_cycles.max(s.duration);
        entry.min_cycles = entry.min_cycles.min(s.duration);
    }
    map
}

fn main() {
    let events = vec![
        Event { cycle: 100, guid: 1, kind: Kind::Begin },
        Event { cycle: 110, guid: 2, kind: Kind::Begin },
        Event { cycle: 150, guid: 2, kind: Kind::End },
        Event { cycle: 160, guid: 3, kind: Kind::Begin },
        Event { cycle: 220, guid: 3, kind: Kind::End },
        Event { cycle: 230, guid: 1, kind: Kind::End },
    ];

    let spans = collate(&events);
    for s in &spans {
        println!("guid={} duration={} depth={}", s.guid, s.duration, s.depth);
    }

    let stats = aggregate(&spans);
    for (guid, st) in &stats {
        let avg = st.total_cycles / st.count as u64;
        println!("guid={}: count={} avg={} min={} max={}", guid, st.count, avg, st.min_cycles, st.max_cycles);
    }
}
```

### Lv3 · 迁移设计

**题**:写一个**火焰图数据**结构:每个 span 不仅记 depth,还记 parent_guid 和 children Vec。生成出来后能用 indent 打印树状结构。**提示**:collate 时记 parent。

**设计思路**(先思考再写代码):
1. 栈里除了 GUID、begin cycle,还要存"这个 span 是谁的 child"——也就是它 push 时的栈顶元素 ID。
2. 用一个全局的 `Vec<SpanNode>` 存储,栈里存 index(usize)而不是 owned node——避免借用问题。
3. 配对成功后:把当前 node 的 index 加入父 node 的 children(如果父存在),否则加入 roots。

**参考解答**:

```rust
#[derive(Debug, Default)]
struct SpanNode {
    guid: u64,
    begin_cycle: u64,
    end_cycle: u64,
    parent: Option<usize>,  // 父在 arena 里的 index
    children: Vec<usize>,   // 子在 arena 里的 index
}

struct SpanForest {
    nodes: Vec<SpanNode>,
    roots: Vec<usize>,
}

fn build_forest(events: &[Event]) -> SpanForest {
    let mut forest = SpanForest { nodes: vec![], roots: vec![] };
    // 栈存 (node_index)
    let mut stack: Vec<usize> = vec![];

    for e in events {
        match e.kind {
            Kind::Begin => {
                let parent = stack.last().copied();
                let node = SpanNode {
                    guid: e.guid, begin_cycle: e.cycle, end_cycle: 0,
                    parent, children: vec![],
                };
                let idx = forest.nodes.len();
                forest.nodes.push(node);
                // 加入父的 children(如果有)
                if let Some(p) = parent {
                    forest.nodes[p].children.push(idx);
                } else {
                    forest.roots.push(idx);
                }
                stack.push(idx);
            }
            Kind::End => {
                if let Some(&idx) = stack.last() {
                    if forest.nodes[idx].guid == e.guid {
                        forest.nodes[idx].end_cycle = e.cycle;
                        stack.pop();
                    } else {
                        eprintln!("WARN: mismatched at idx={}", idx);
                    }
                }
            }
        }
    }
    forest
}

fn print_indent(s: &SpanForest, idx: usize, depth: usize) {
    let n = &s.nodes[idx];
    println!("{}guid={} dur={}", "  ".repeat(depth), n.guid, n.end_cycle - n.begin_cycle);
    for &c in &n.children {
        print_indent(s, c, depth + 1);
    }
}

fn print_forest(s: &SpanForest) {
    for &r in &s.roots {
        print_indent(s, r, 0);
    }
}
```

**为什么用 arena (Vec<SpanNode>) 而不是递归 enum**?因为 Rust 的 ownership 不允许 `Box<SpanNode>` 里既存 children 又存 parent 引用——会形成环,违反 ownership tree。Arena + index 是处理图结构的通用 Rust 模式。 ECS(Bevy)、roslyn(微软 .NET 编译器)、 rspack(JS bundler)都用这个套路。

### 8.3 Troubleshooting

- **WARN mismatched** — event 流有 bug,检查 span enter / drop 顺序。最常见:某个函数提前 return,但 span 没用 RAII Drop,导致 end 漏掉。
- **depth 错位** — 注意 stack.len() 在 pop 前是当前 depth(从 1 开始)。如果想 0-indexed depth,pop 后用 `stack.len()`。
- **collation 慢** — 用 `cargo flamegraph` 看热点,通常是 HashMap 分配。改成 smallvec 或 direct array indexing。
- **stats_map clear 后 capacity 变小** — `clear()` 不释放 capacity,但如果之前调过 `shrink_to_fit` 就缩了。
- **rayon 并行更慢** — collation 本身 < 1ms,rayon 的 dispatch overhead > 收益。

### 8.5 内存优化的具体技巧

如果 collation 真的成为瓶颈(实测之后才发现),按这个顺序优化:

1. **避免 String**:GUID 用 `u64`(8 字节)而不是 `&str`(16 字节)或 `String`(24 字节)。Casey 一开始就用 u64。
2. **避免 HashMap**:如果 GUID 是连续小整数(0..N),用 `Vec<Option<SpanStats>>` 直接 index。比 HashMap 快 5-10 倍。
3. **smallvec**:如果 children 数量大多数是 0-4,用 `SmallVec<[u64; 4]>`,大多数情况不 alloc。
4. **缓存 begin_cycle**:栈用 `SmallVec<[(u64, u64); 32]>`,大多数调用栈 < 32 层。
5. **SIMD**:对超大 event 流,Rust 的 `std::simd`(nightly)可以一次处理 8 个 event。但这是极端优化,普通 collation 不需要。
