# Day 184 · 整理调试事件

> 事件流存下来了,但**原始事件流没法直接看**——10000 条 event 闪过去什么都看不清。今天 Casey 把 event 流组织成"按 GUID 分组 + 按帧分组"的结构,为后面的 UI 渲染做准备。

## 0 · 为什么要有这一天

Day 183 的 event log 长这样:

```
cycle=100 begin update_player
cycle=120 begin update_audio
cycle=140 end   update_audio
cycle=200 begin update_render
cycle=500 end   update_render
cycle=600 end   update_player
```

直接看这个流没用——你需要:
- "update_player 在这帧总耗时多少?"(配对 begin/end)
- "update_player 平均多长?"(跨帧聚合)
- "update_player 被谁调用了?"(嵌套关系)

要从原始 event 流回答这些,**必须整理**成更高阶的结构:

```rust
struct FrameSummary {
    frame_index: u64,
    spans_by_guid: HashMap<u64, SpanStats>,
}

struct SpanStats {
    count: u32,
    total_cycles: u64,
    max_cycles: u64,
    children: Vec<u64>,  // 嵌套的子 span GUID
}
```

整理一次,O(N) 时间。UI 直接读 FrameSummary,不用再扫原始 event。

心理锚点:看完今天,你能理解"原始日志"和"聚合视图"的差别,并能写出 event → SpanStats 的转换。

## 1 · Casey 今天做了什么

Casey 写了一个**整理阶段**(collation phase):

1. 帧结束时,主线程把所有 event 排序(按 cycle)
2. 用栈配对 begin/end(同线程内嵌套)
3. 配对成功后,聚合到当前帧的 SpanStats
4. 跨帧的 SpanStats 推到 ring buffer

他强调:**collation 是纯函数**——输入 event 流,输出 FrameSummary,无副作用。这样容易测试和优化。

## 2 · 心智模型

### 类比:图书馆的索引

图书馆每天进新书(原始 event),但要让人查得到,图书管理员要:
1. 按主题分类(配对 / 分组)
2. 写索引卡片(聚合 stats)
3. 卡片放索引柜(存到 ring buffer)

读者(UI)查卡片,不去翻书(event)。

profiler 一样:原始 event 是"书",整理后的 FrameSummary 是"索引卡"。

### 2.1 配对算法

event 流里 begin/end 可能不严格交替(同线程内基本是 stack-structured,跨线程可能错乱)。Casey 用**栈配对**:

```rust
fn collate_thread_events(events: &[Event]) -> Vec<SpanInstance> {
    let mut stack: Vec<(u64 /* guid */, u64 /* begin_cycle */)> = Vec::new();
    let mut spans = Vec::new();

    for e in events {
        match e.kind {
            EventKind::Begin => stack.push((e.guid, e.cycle)),
            EventKind::End => {
                // 弹栈,找匹配的 begin
                if let Some((guid, begin)) = stack.pop() {
                    if guid == e.guid {
                        spans.push(SpanInstance {
                            guid,
                            begin_cycle: begin,
                            end_cycle: e.cycle,
                            duration: e.cycle - begin,
                        });
                    } else {
                        // mismatched, log warning
                    }
                }
            }
        }
    }
    spans
}
```

**注意**:`stack.pop()` 假设严格嵌套(LIFO)。如果你的代码有 `par_begin` / `par_end`(并行嵌套)或异步 await,这种配对会错。Casey 假设严格同步嵌套。

### 2.2 嵌套关系

配对时,**栈深度就是嵌套层级**:

```
begin update_frame    (stack: [update_frame])           depth=1
  begin update_player (stack: [update_frame, player])   depth=2
  end   update_player (stack: [update_frame])           depth=1
  begin update_render (stack: [update_frame, render])   depth=2
  end   update_render (stack: [update_frame])           depth=1
end   update_frame    (stack: [])                       depth=0
```

配对时记下 depth,UI 能画火焰图。

```rust
fn collate_with_depth(events: &[Event]) -> Vec<SpanInstance> {
    let mut stack: Vec<(u64, u64)> = Vec::new();
    let mut spans = Vec::new();

    for e in events {
        match e.kind {
            EventKind::Begin => stack.push((e.guid, e.cycle)),
            EventKind::End => {
                let depth = stack.len() as u32 - 1;
                if let Some((guid, begin)) = stack.pop() {
                    if guid == e.guid {
                        spans.push(SpanInstance {
                            guid, begin_cycle: begin, end_cycle: e.cycle,
                            duration: e.cycle - begin, depth,
                        });
                    }
                }
            }
        }
    }
    spans
}
```

### 2.3 聚合到 SpanStats

```rust
pub fn aggregate(spans: &[SpanInstance]) -> HashMap<u64, SpanStats> {
    let mut map: HashMap<u64, SpanStats> = HashMap::new();
    for s in spans {
        let entry = map.entry(s.guid).or_insert_with(|| SpanStats {
            count: 0, total_cycles: 0, max_cycles: 0, min_cycles: u64::MAX,
        });
        entry.count += 1;
        entry.total_cycles += s.duration;
        entry.max_cycles = entry.max_cycles.max(s.duration);
        entry.min_cycles = entry.min_cycles.min(s.duration);
    }
    map
}
```

**Rust 注释**:
- `or_insert_with(|| ...)` — 不存在时调闭包创建,避免无意义 clone
- `entry.max_cycles.max(s.duration)` — `u64::max` 是 method,链式调

### 2.4 帧隔离

event 流跨帧时,每帧独立 collate。Casey 在 frame_begin 推一条**marker event**:

```rust
// 帧开始
push_event(MARKER_FRAME_BEGIN, frame_index);

// 帧结束
push_event(MARKER_FRAME_END, frame_index);
```

collation 时按 marker 切分 event 流,每段独立处理。

### 2.5 火焰图的数据结构

火焰图(flame graph)是 Brendan Gregg 2011 年发明的可视化,把调用栈的耗时分布画成一堆叠在一起的矩形。每层是一个函数调用,宽度 = 耗时。

```
┌────────────────────────────────────────────────┐
│              update_frame                      │  depth=0
│ ┌──────────────────┐  ┌──────────────────┐   │
│ │  update_player   │  │  update_render   │   │  depth=1
│ │ ┌──────────────┐ │  │ ┌──────────────┐ │   │
│ │ │ update_audio │ │  │ │ draw_mesh    │ │   │  depth=2
│ │ └──────────────┘ │  │ └──────────────┘ │   │
│ └──────────────────┘  └──────────────────┘   │
└────────────────────────────────────────────────┘
```

要在 UI 画火焰图,collation 输出不是简单的 `Vec<SpanInstance>`,而是**树**:

```rust
pub struct SpanNode {
    pub guid: u64,
    pub begin_cycle: u64,
    pub end_cycle: u64,
    pub children: Vec<SpanNode>,  // 递归
}
```

构建时,栈里维护当前活跃的节点:

```rust
fn build_tree(events: &[Event]) -> Vec<SpanNode> {
    let mut roots: Vec<SpanNode> = Vec::new();
    let mut stack: Vec<SpanNode> = Vec::new();

    for e in events {
        match e.kind {
            Kind::Begin => {
                let node = SpanNode { guid: e.guid, begin_cycle: e.cycle, end_cycle: 0, children: vec![] };
                stack.push(node);
            }
            Kind::End => {
                if let Some(mut node) = stack.pop() {
                    if node.guid == e.guid {
                        node.end_cycle = e.cycle;
                        if let Some(parent) = stack.last_mut() {
                            parent.children.push(node);
                        } else {
                            roots.push(node);
                        }
                    }
                }
            }
        }
    }
    roots
}
```

**关键洞察**:每帧的 roots 列表里每个元素就是一棵树。UI 递归画。

### 2.6 collation 的内存分配策略

每帧 collate 一次,要分配 `Vec<SpanInstance>` 和 `HashMap<u64, SpanStats>`。如果每帧 alloc + dealloc,会:

- **malloc/free 频繁**,触发内存碎片
- **cache miss 频繁**,新分配的内存冷

Casey 用**复用 buffer**:

```rust
struct Collator {
    span_buf: Vec<SpanInstance>,        // 复用
    stats_map: HashMap<u64, SpanStats>, // 复用
}

impl Collator {
    fn collate(&mut self, events: &[Event]) -> &HashMap<u64, SpanStats> {
        self.span_buf.clear();          // 不释放 capacity
        self.stats_map.clear();         // 同上
        // ... 填充 self.span_buf 和 self.stats_map
        &self.stats_map
    }
}
```

**`.clear()` vs `*v = Vec::new()`**:`clear()` 保留 capacity,后续 push 不 realloc。这是 hot loop 的标准优化。

### 2.7 跨帧的趋势聚合

单帧的 SpanStats 不够看趋势,要**跨 N 帧聚合**:

```rust
pub struct TrendStats {
    pub recent_avg: f64,    // 过去 60 帧 avg
    pub recent_max: u64,    // 过去 60 帧 max
    pub lifetime_avg: f64,  // 启动以来 avg
}

impl TrendStats {
    pub fn update(&mut self, frame_stat: &SpanStats, history: &RingBuffer<SpanStats, 60>) {
        self.recent_avg = history.iter().map(|s| s.total_cycles as f64).sum::<f64>() / history.len() as f64;
        self.recent_max = history.iter().map(|s| s.max_cycles).max().unwrap_or(0);
        // lifetime 用全局累加器
    }
}
```

UI 显示"update_player avg=5000 recent_max=15000"。recent_max 是发现 spike 的关键。

## 3 · 四域深入

### 3.1 · 游戏编程视角

整理阶段的性能要求:**O(N) 或 O(N log N)**。10 万 event / 帧 / 60fps = 600 万 event / 秒。Rust 上扫一遍 Vec 100ns/1000个 event = 600ms/秒,**不能**。要优化到 60ns/1000个 event = 60ms/秒,留 10ms 给游戏逻辑。

Casey 的优化:
- 用 `Vec` 预分配
- 用 `sort_unstable_by_key`(比 stable 快)
- 避免 HashMap(用 GUID 直接索引数组)

### 3.2 · Linux 系统编程视角

Linux 内核的 perf_events 也有 collation:

```bash
sudo perf record -F 99 -ag -- sleep 1
sudo perf report --stdio
```

perf 在内核环形缓冲采 event,`perf report` 用户态做 collation。

### 3.3 · Rust 生态视角

Rust 处理 event 流的 crate:
- `itertools` — group_by, unique, etc.
- `rayon` — 并行处理 event
- `polars` — DataFrame,大数据处理

profiler 数据量不大(每帧 ~MB),不需要这些重型工具。手写 Rust 迭代器够。

### 3.4 · 🎮 游戏编程视角(工业级 profiler 的 collation)

Unreal Insights 的 collation 在 dedicated 线程跑——主线程只 push event 到 lock-free queue,collator 线程 drain + aggregate。这样:

- 主线程零等待
- collator 可以慢慢做(复杂分析)
- 数据可以序列化到磁盘 / 网络

Casey 的设计简化版:**主线程在帧结束时 collate**(此时游戏已经空闲)。trade-off:主线程多花 1ms 做 collation,但简单可靠。

| 设计 | 主线程开销 | 复杂度 |
|---|---|---|
| 主线程同步 collate(Casey) | 1ms / 帧 | 低 |
| 后台 collator 线程(Unreal) | ~0 | 高(需 IPC) |
| GPU compute shader collate | ~0 | 极高 |

### 3.5 · 🐧 Linux 系统编程视角(perf 的 userspace collation)

`perf record` 在内核环形缓冲采 event,`perf report` 在用户态 collate:

```bash
# 看 perf.data 文件大小(原始 event)
ls -la perf.data
# 1MB ≈ 10000 samples

# perf report 做 collation
sudo perf report --stdio --no-children | head -30
# 输出按函数聚合的 cycle 占比:
#  23.5%  my_game   update_player
#  15.2%  my_game   render_batch
#   ...
```

perf 的 collation 用 LBR(Last Branch Record)重建调用栈,比 profiler 的 begin/end 配对复杂——因为采样时只看到当前 PC,要靠 LBR 反推调用路径。Casey 用 begin/end 简单很多。

### 3.6 · 🦀 Rust 生态视角(rayon 并行 collation)

如果 collation 是瓶颈,可以用 `rayon` 并行处理多线程 event:

```rust
use rayon::prelude::*;

let per_thread_spans: Vec<Vec<SpanInstance>> = thread_events
    .par_iter()
    .map(|events| collate_thread(events))
    .collect();
```

但 collation 通常 < 1ms,不值得并行——并行开销(线程池 dispatch)反而拖慢。**先测,再优化**(Casey 的座右铭)。

## 5 · 对照与变奏

**event 配对的不同算法**:

| 场景 | 算法 |
|---|---|
| 同步严格嵌套 | 栈配对(O(N)) |
| 异步(future) | 全局 event table,复杂 |
| 并行(par) | 多栈 / 区间 |
| 网络分布式 | trace context propagation |

游戏 profiler 是"同步严格嵌套",最简单。

### 与 Tracy / puffin 的 collation 设计对比

**Tracy**(业界标准的 C++ profiler)的 collation:

- 服务端-客户端架构:游戏是 server,viewer 是 client
- 通过 socket 实时传输 event
- client 端 collate + 渲染
- 优点:可以远程分析,数据可持久化
- 缺点:网络延迟 + 协议复杂

**puffin**(Rust 轻量级 profiler)的 collation:

- 单进程:游戏 + UI 在一起
- 用 `Arc<Mutex<FrameData>>` 共享
- 每帧 collate 后 store,UI 读
- 优点:简单,跨平台
- 缺点:不能远程

**Casey**:类似 puffin,但**纯手写**,无第三方依赖。教学价值高,生产可用性中等。

### SQL-like 的 collation 抽象

工业 BI(商业智能)工具用 SQL 思路处理 event log:

```sql
SELECT guid, COUNT(*) as calls, AVG(duration) as avg, MAX(duration) as max
FROM spans
WHERE frame_index >= 1000 AND frame_index < 1100
GROUP BY guid
ORDER BY avg DESC
LIMIT 10;
```

如果 profiler 数据量大,可以**存 SQLite**,UI 写 SQL 查询。`rusqlite` crate 很轻量,适合嵌入式。Casey 没做这步(数据量小),但工业级 tracing 系统(Tempo / Jaeger)都基于 SQL/NoSQL 后端。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么配对算法用栈?如果 event 流是 `[A_begin, B_begin, A_end, B_end]`(交叉),栈配对会怎样?

**参考解答**:
- 栈假设严格嵌套(LIFO):`[A_begin, B_begin, B_end, A_end]`
- 交叉情况 `[A_begin, B_begin, A_end, B_end]`:
  - A_begin 入栈: [A]
  - B_begin 入栈: [A, B]
  - A_end 弹栈得 B(mismatched!),日志警告
  - B_end 弹栈得 A(mismatched!)
- 栈配对失败 → 这种 event 流不合法
- 实际同步代码不会交叉(线程内 LIFO 保证),异步代码可能交叉(但 Casey 不用 async)

### Lv2 · 动手实践

**题**:实现 collate 和 aggregate,要求:
- 输入 Vec<Event>
- 输出 Vec<SpanInstance>(带 depth)
- 然后聚合到 HashMap<u64, SpanStats>

**参考解答**:

```rust
#[derive(Clone, Copy, Debug)]
enum Kind { Begin, End }

#[derive(Clone, Copy, Debug)]
struct Event { cycle: u64, guid: u64, kind: Kind }

#[derive(Clone, Debug)]
struct SpanInstance {
    guid: u64, begin_cycle: u64, end_cycle: u64, duration: u64, depth: u32,
}

#[derive(Clone, Debug, Default)]
struct SpanStats {
    count: u32, total_cycles: u64, max_cycles: u64, min_cycles: u64,
}

fn collate(events: &[Event]) -> Vec<SpanInstance> {
    let mut stack: Vec<(u64, u64)> = Vec::new();
    let mut spans = Vec::new();
    for e in events {
        match e.kind {
            Kind::Begin => stack.push((e.guid, e.cycle)),
            Kind::End => {
                let depth = stack.len() as u32 - 1;
                if let Some((guid, begin)) = stack.pop() {
                    if guid == e.guid {
                        spans.push(SpanInstance {
                            guid, begin_cycle: begin, end_cycle: e.cycle,
                            duration: e.cycle - begin, depth,
                        });
                    } else {
                        eprintln!("WARN: mismatched end guid={}, expected={}", e.guid, guid);
                    }
                } else {
                    eprintln!("WARN: end without begin guid={}", e.guid);
                }
            }
        }
    }
    spans
}

fn aggregate(spans: &[SpanInstance]) -> std::collections::HashMap<u64, SpanStats> {
    let mut map = std::collections::HashMap::new();
    for s in spans {
        let entry = map.entry(s.guid).or_insert_with(|| SpanStats {
            count: 0, total_cycles: 0, max_cycles: 0, min_cycles: u64::MAX,
        });
        entry.count += 1;
        entry.total_cycles += s.duration;
        entry.max_cycles = entry.max_cycles.max(s.duration);
        entry.min_cycles = entry.min_cycles.min(s.duration);
    }
    map
}

fn main() {
    let events = vec![
        Event { cycle: 100, guid: 1, kind: Kind::Begin },
        Event { cycle: 110, guid: 2, kind: Kind::Begin },
        Event { cycle: 150, guid: 2, kind: Kind::End },
        Event { cycle: 160, guid: 3, kind: Kind::Begin },
        Event { cycle: 220, guid: 3, kind: Kind::End },
        Event { cycle: 230, guid: 1, kind: Kind::End },
    ];

    let spans = collate(&events);
    for s in &spans {
        println!("guid={} duration={} depth={}", s.guid, s.duration, s.depth);
    }

    let stats = aggregate(&spans);
    for (guid, st) in &stats {
        let avg = st.total_cycles / st.count as u64;
        println!("guid={}: count={} avg={} min={} max={}", guid, st.count, avg, st.min_cycles, st.max_cycles);
    }
}
```
