# Day 222 · 过场动画布局

> 之前的过场动画是"全屏铺满",今天 casey 让 layer 能精确定位、缩放、旋转。每 layer 是一个矩形,可以放在屏幕任意位置。这是 2D UI 布局的基础。

## 0 · 为什么要有这一天

之前 layer 渲染时直接全屏画。但实际场景需要:

- 字幕条放底部 1/4
- 头像放左下角,占 1/6 屏幕宽
- 全屏背景视频
- 右上角小地图,占 1/8 屏幕宽

每个 layer 有独立位置、独立大小。casey 今天加 layout 系统:

```rust
struct LayerLayout {
    rect: Rect,       // 屏幕坐标矩形
    rotation: f32,    // 弧度
    scale: Vec2,      // 缩放因子
    anchor: Anchor,   // 锚点(屏幕坐标系)
}
```

每个 layer 在渲染时按 layout 变换:

```
原始图 → 缩放 → 旋转 → 平移到 anchor → 输出
```

这是 2D GUI 布局的核心。casey 用最朴素的 absolute layout(每 layer 显式 rect),为后面 Day 223-224 的更复杂布局打基础。

心理锚点:看完今天,你能解释 CSS absolute positioning / Android FrameLayout / Flutter Stack 的共同思想。

## 2 · 心智模型

### 类比:画框摆放

画廊墙上挂画:

- **绝对定位**:每幅画给"左上角 (x, y) + 宽 w + 高 h"
- **锚点定位**:每幅画给"中心 (x, y) + 宽 w + 高 h",画围绕中心放
- **流式布局**:画作按顺序从左到右、到边界换行

casey 今天实现绝对 + 锚点两种。

这个类比还能更精确:**画廊管理员要决定"画挂哪里"**。每幅画独立决定自己的位置,不互相影响(绝对定位)。也可以"以画廊中心为锚,对称挂画"(锚点定位)。挂画风格决定了 UI 范式——CSS 的 absolute / relative / flex 就是这三种风格的 web 版。

更深一层:**布局是 UI 的"几何基础"**。所有 UI 框架(Qt、GTK、Cocoa、WinForms、Android、iOS、Flutter)都有布局系统,核心都是"如何决定每个 UI 元素的位置和大小"。casey 今天实现的是最简单的 absolute layout,后续 Day 223-224 会扩展到 flow layout(线性布局)、grid layout(网格布局)。

类比还能引出**变换链**的概念。每幅画可以"先缩放,再旋转,再平移"——这是 2D 仿射变换。casey 的 LayerLayout 包含 rotation 和 scale,正是这个变换链。理解变换链,后面 3D 渲染的 model / view / projection 矩阵就是同一思想的 3D 扩展。

### 2.5 第一性原理推导:为什么 GUI 布局如此复杂

GUI 布局是软件工程最被低估的难题之一。从第一性原理推导为什么。

**前提**:UI 元素(按钮、文字、图像)有不同的尺寸,需要在有限的屏幕上排列。不同屏幕尺寸(手机 / 平板 / 桌面 / 4K)需要适配。

**约束**:
1. 元素不能重叠(除非用户明确要 z-stack)
2. 元素不能超出屏幕
3. 元素在不同分辨率下应该等比缩放
4. 元素之间的间距要协调(美学)
5. 布局要响应用户操作(窗口 resize)
6. 布局要支持国际化(阿拉伯文右到左,中文断字不同)

这些约束**互相冲突**——比如"不能重叠"和"必须塞下所有元素"在小屏幕上冲突。设计布局系统就是平衡这些约束。

**两种极端方案**:

**方案 A:纯绝对定位**。开发者给每个元素 `(x, y, w, h)`。优点:精确控制。缺点:不响应 resize,小屏幕溢出,大屏幕浪费。

**方案 B:纯自动布局**(Android LinearLayout / CSS Flexbox)。开发者声明"这些元素横向排列,中间间隔 10px",容器自动算位置。优点:响应 resize。缺点:复杂场景难表达(元素重叠、绝对定位混用)。

**生产方案:混合**。CSS Grid + Flex + absolute positioning 组合。Flutter Row/Column/Stack 组合。casey 今天实现 absolute,后续 Day 223+ 会加 flow / grid,最终达到工业级布局系统的雏形。

**为什么布局系统这么难?** 因为它在解决一个 NP-hard 优化问题:在多种约束下找最优位置。Android 的 ConstraintLayout 内部用 Cassowary 算法(线性规划求解器)。CSS Grid 用类似算法。casey 的简化版避开复杂算法,用直接 rect 表达,适合教学。

### 2.6 变换矩阵的数学

casey 的 LayerLayout 用 rect + rotation + scale,这是 2D 仿射变换。数学上用 3x3 矩阵表达:

```
| sx*cos  -sy*sin  tx |   | x |   | x' |
| sx*sin   sy*cos  ty | × | y | = | y' |
|  0        0       1  |   | 1 |   | 1  |
```

- (sx, sy):X/Y 缩放
- θ:旋转角度
- (tx, ty):平移

矩阵乘法把这些操作合并成一个。GPU 用统一矩阵表达所有 2D 变换,极快。

**为什么 3x3 而不是 2x2?** 2x2 只能表达线性变换(旋转、缩放、剪切),不能表达平移(平移是非线性)。加一行常数项(齐次坐标),3x3 矩阵能表达所有仿射变换。这是计算机图形学的基础技巧。

**仿射 vs 投影**:
- 仿射:平行线变换后仍平行(2D UI 用这个)
- 投影:平行线可以汇聚(3D 透视用,需要 4x4 矩阵)

casey 今天用仿射(2D UI),3D 渲染需要投影(Day 270+)。

**Anchor(锚点)的数学**:anchor 是"局部坐标系的原点对应屏幕坐标系的哪里"。比如 center anchor 表示"局部 (0, 0) = 屏幕中心"。变换时:
```
screen_pos = anchor_screen_pos + local_pos * scale * rotation
```

casey 的 Anchor enum 支持 TopLeft、Center、BottomRight 等枚举,每个对应一个屏幕坐标。

### 2.2 Anchor 系统

```rust
enum Anchor {
    TopLeft,
    TopCenter,
    TopRight,
    CenterLeft,
    Center,
    CenterRight,
    BottomLeft,
    BottomCenter,
    BottomRight,
}

fn anchor_offset(anchor: Anchor, screen: Vec2, rect_size: Vec2) -> Vec2 {
    use Anchor::*;
    let x = match anchor {
        TopLeft | CenterLeft | BottomLeft => 0.0,
        TopCenter | Center | BottomCenter => (screen.x - rect_size.x) / 2.0,
        TopRight | CenterRight | BottomRight => screen.x - rect_size.x,
    };
    let y = match anchor {
        TopLeft | TopCenter | TopRight => 0.0,
        CenterLeft | Center | CenterRight => (screen.y - rect_size.y) / 2.0,
        BottomLeft | BottomCenter | BottomRight => screen.y - rect_size.y,
    };
    Vec2 { x, y }
}
```

### 2.3 渲染时的变换

```
源像素 (u, v) 在 source_rect 内
→ 缩放到 layer rect(目标尺寸)
→ 旋转(围绕 rect 中心)
→ 平移(到 anchor 算出的位置)
→ 屏幕坐标 (x, y)
```

实现:

```rust
fn transform_pixel(u: f32, v: f32, layout: &LayerLayout, anchor_pos: Vec2) -> Vec2 {
    // 1. source_rect 内的位置已经是 (u, v)
    // 2. 缩放到 layer rect 大小(目标尺寸)
    let sx = u / layout.source_rect.w * layout.rect.w;
    let sy = v / layout.source_rect.h * layout.rect.h;
    // 3. 围绕 rect 中心旋转
    let cx = layout.rect.w / 2.0;
    let cy = layout.rect.h / 2.0;
    let dx = sx - cx;
    let dy = sy - cy;
    let rx = dx * layout.rotation.cos() - dy * layout.rotation.sin();
    let ry = dx * layout.rotation.sin() + dy * layout.rotation.cos();
    // 4. 平移
    Vec2 {
        x: layout.rect.x + anchor_pos.x + cx + rx,
        y: layout.rect.y + anchor_pos.y + cy + ry,
    }
}
```

这是 Day 44 反射向量之外又一个向量数学的实际应用。

### 2.4 Layout 的有效性

casey 加验证:

```rust
fn validate_layout(layout: &LayerLayout, screen: Vec2) -> Result<(), String> {
    if layout.rect.w < 0.0 || layout.rect.h < 0.0 {
        return Err(format!("negative size: {:?}", layout.rect));
    }
    // 允许超出屏幕(可能是动画过程),但不允许 NaN
    if layout.rect.x.is_nan() || layout.rect.y.is_nan() {
        return Err("NaN position".to_string());
    }
    Ok(())
}
```

### Lv1 · 概念辨析

**题**:为什么用 source_rect + dest_rect,而不是直接缩放整张图?

### Lv2 · 动手实践

**题**:实现 LayerLayout + anchor_offset + 简单渲染(画 ASCII 框)。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

#[derive(Copy, Clone, Debug)]
struct Rect { x: f32, y: f32, w: f32, h: f32 }

#[derive(Copy, Clone)]
enum Anchor { TopLeft, Center, BottomRight }

fn anchor_pos(a: Anchor, screen: Vec2, size: Vec2) -> Vec2 {
    match a {
        Anchor::TopLeft => Vec2 { x: 0.0, y: 0.0 },
        Anchor::Center => Vec2 { x: (screen.x - size.x) / 2.0, y: (screen.y - size.y) / 2.0 },
        Anchor::BottomRight => Vec2 { x: screen.x - size.x, y: screen.y - size.y },
    }
}

struct Layer {
    rect: Rect,
    anchor: Anchor,
    name: char,  // 简化:用单字符代替颜色
}

fn render_ascii(screen: Vec2, layers: &[Layer]) {
    let mut buf = vec![vec![' '; screen.x as usize]; screen.y as usize];
    for layer in layers {
        let size = Vec2 { x: layer.rect.w, y: layer.rect.h };
        let off = anchor_pos(layer.anchor, screen, size);
        let abs_x = layer.rect.x + off.x;
        let abs_y = layer.rect.y + off.y;
        for dy in 0..layer.rect.h as i32 {
            for dx in 0..layer.rect.w as i32 {
                let px = (abs_x as i32 + dx) as usize;
                let py = (abs_y as i32 + dy) as usize;
                if px < screen.x as usize && py < screen.y as usize {
                    buf[py][px] = layer.name;
                }
            }
        }
    }
    for row in &buf {
        println!("{}", row.iter().collect::<String>());
    }
}

fn main() {
    let screen = Vec2 { x: 40.0, y: 10.0 };
    let layers = vec![
        Layer {
            rect: Rect { x: 0.0, y: 0.0, w: 40.0, h: 10.0 },
            anchor: Anchor::TopLeft,
            name: '.',
        },
        Layer {
            rect: Rect { x: 0.0, y: 0.0, w: 10.0, h: 3.0 },
            anchor: Anchor::TopLeft,
            name: 'A',
        },
        Layer {
            rect: Rect { x: 0.0, y: 0.0, w: 8.0, h: 2.0 },
            anchor: Anchor::Center,
            name: 'B',
        },
        Layer {
            rect: Rect { x: 0.0, y: 0.0, w: 5.0, h: 1.0 },
            anchor: Anchor::BottomRight,
            name: 'C',
        },
    ];
    render_ascii(screen, &layers);
}
```

## 10 · 深入:UI 布局算法的全景

casey 今天做的 cutscene 布局——根据 anchor(position)和 size 自动算 rectangle——是 UI 框架的核心。所有 UI 框架(Qt、WPF、GTK、CSS、Unity UGUI)都在解决这个问题,但实现方式差异巨大。让我把所有方案的思路列出来对比。

### 10.1 五种 UI 布局范式

**1. 手动坐标**(casey / Win32 / 早期 GUI)

```rust
struct Widget {
    rect: Rect,  // x, y, width, height 全手填
}
```

优点:简单直接,O(1) 计算。
缺点:窗口 resize 时全乱;不同分辨率显示错位;国际化文本长度变化崩溃。

**2. Box layout**(GTK / Qt QHBoxLayout)

```rust
struct HBox {
    children: Vec<Widget>,
    spacing: f32,
    padding: f32,
}
// 计算:从左到右累加 x,每个 child 占自己的 width
```

子元素按水平/垂直排列,自动 layout。简单,适合"按钮排成一行"这种简单 UI。

**3. Grid layout**(CSS Grid / Qt QGridLayout)

```css
grid-template-columns: 1fr 2fr 1fr;
grid-template-rows: auto auto;
```

二维网格,每 cell 放 widget。复杂 UI 表单(注册表单、设置面板)用这个。

**4. Flexbox**(CSS Flex / web)

```css
display: flex;
flex-direction: row;
justify-content: space-between;
align-items: center;
```

弹性布局,自动分配剩余空间。现代 web 的主流。

**5. Constraint-based**(Cocoa Auto Layout / Android ConstraintLayout)

```swift
button.leadingAnchor.constraint(equalTo: view.leadingAnchor, constant: 20)
button.topAnchor.constraint(equalTo: label.bottomAnchor, constant: 8)
```

约束方程组,运行时用 simplex / Cassowary 算法求解。最强大但最复杂。

### 10.2 casey 选择:手动坐标 + anchor

casey 不用 box / grid / flex / constraint,而是"手动坐标 + anchor 偏移"。

```rust
struct CutsceneElement {
    anchor: Anchor,        // TopLeft, Center, BottomRight
    offset: Vec2,          // 相对 anchor 的偏移
    size: Vec2,            // 元素大小
}

fn compute_rect(e: &CutsceneElement, screen: Vec2) -> Rect {
    let center = match e.anchor {
        Anchor::TopLeft => Vec2::new(0.0, 0.0),
        Anchor::Center => screen * 0.5,
        Anchor::BottomRight => screen,
    };
    let pos = center + e.offset;
    Rect::new(pos, e.size)
}
```

为什么 casey 这么选?这是**调试/cutscene UI 的特殊需求**:

1. **窗口不 resize**:游戏窗口固定大小(或固定 aspect ratio),不需要响应式。
2. **元素少**:cutscene 通常 5-10 个元素,不需要复杂 layout。
3. **精确控制**:cutscene 导演要 pixel-perfect 定位,自动 layout 反而碍事。
4. **性能**:每帧 layout 几个元素,手动坐标最快。

### 10.3 何时升级到 box / flex

casey 的方案在以下场景**崩溃**:

- **设置面板**:十几个 label + input,要垂直排列,改一个 全都要重排。手动坐标维护噩梦。
- **本地化**:中文比英文短 30%,德语比英文长 30%,手动坐标会导致溢出或留白。
- **不同分辨率**:4K 屏和 720p 屏,手动坐标只能服务一个。

解决:升级到 box layout。Rust 生态的 egui 提供这个:

```rust
use egui::Ui;

fn draw_settings_panel(ui: &mut Ui, settings: &mut Settings) {
    ui.vertical(|ui| {  // VBox:子元素垂直排列
        ui.horizontal(|ui| {  // HBox:子元素水平
            ui.label("Volume:");
            ui.add(egui::Slider::new(&mut settings.volume, 0.0..=1.0));
        });
        ui.horizontal(|ui| {
            ui.label("Difficulty:");
            ui.radio_value(&mut settings.difficulty, Difficulty::Easy, "Easy");
            ui.radio_value(&mut settings.difficulty, Difficulty::Hard, "Hard");
        });
    });
}
```

egui 自动算每个 widget 的 rect,窗口 resize 时自适应。

### 10.4 casey 手写 vs 用 egui 的权衡

casey 手写 UI 布局的理由(教学):
- 让学生理解 layout 算法的内部
- 不依赖外部库,HH 项目代码自洽

生产项目的选择(实战):
- 用 egui,代码量减少 90%
- 自动支持 box layout、滚动、文本编辑、滑块、对话框
- 维护成本低

casey 在 day222 教你 layout 原理,生产中你应该用 egui 而不是手写。这是教学 vs 工程的常见分离。

### 10.5 字体度量与文本布局

UI 布局的一个隐藏难点:**文本大小不固定**。同样 "Hello",不同字体、不同字号、不同语言,占的像素不同。

```rust
struct TextLayout {
    font: Font,
    size: f32,
    text: String,
}

impl TextLayout {
    fn measure(&self, max_width: f32) -> Vec2 {
        // 测量文本在 max_width 下占多少像素
        // 需要调用字体光栅化 API
        font.measure(&self.text, self.size, max_width)
    }
}
```

文本布局算法:
1. **glyph advance**:每个字符在字体里查 advance width
2. **kerning**:相邻字符对的间距调整(AV 紧靠,AA 间隔)
3. **word wrap**:文本超出宽度时换行
4. **baseline alignment**:文本按 baseline 对齐,不是 top

casey 的 cutscene 系统简化——预定义文字 + bitmap font,跳过这些复杂度。生产 UI 必须解决,rusttype / ab_glyph / cosmic-text 是 Rust 生态的字体库。

### 10.6 DPI 缩放

不同屏幕 DPI 不同:手机 3x、Retina 2x、桌面 1x。UI 元素要么按物理像素(高 DPI 上变小),要么按逻辑像素(自动缩放)。

```rust
struct UiScale(f32);  // 1.0 = 桌面, 2.0 = Retina, 3.0 = 手机

impl Ui {
    fn logical_to_physical(&self, logical: f32) -> f32 {
        logical * self.scale.0
    }
}
```

casey 假设固定 DPI,简化。生产 UI 必须支持,否则 4K 屏 UI 小到看不见。

### 10.7 实战:用 egui 重写 casey 的 cutscene layout

如果用 egui 重写 casey 的 cutscene 系统,代码量大幅减少:

```rust
use egui::{Context, Pos2, Vec2, Rect, Align2};

struct CutsceneElement {
    anchor: Align2,         // egui 内置 9 种 anchor
    offset: Vec2,
    size: Vec2,
    kind: CutsceneKind,
}

fn draw_cutscene(ctx: &Context, screen: Vec2, elements: &[CutsceneElement]) {
    egui::Area::new("cutscene_layer")
        .order(egui::Order::Foreground)
        .anchor(Align2::CENTER_TOP, vec2(0.0, 0.0))
        .show(ctx, |ui| {
            for elem in elements {
                let pos = elem.anchor.pos_in_rect(&Rect::from_min_size(Pos2::ZERO, screen))
                    + elem.offset;
                egui::Area::new(format!("{:?}", elem.kind))
                    .fixed_pos(pos)
                    .show(ctx, |ui| {
                        match &elem.kind {
                            CutsceneKind::Text(s) => { ui.label(s); }
                            CutsceneKind::Image(t) => { ui.image(t); }
                            CutsceneKind::Button(s) => { ui.button(s); }
                        }
                    });
            }
        });
}
```

对比 casey 手写版本几十行 layout 代码,egui 用 ~30 行完成同样功能,且自动支持 DPI 缩放、文本测量、键盘焦点。

工程教训:**casey 的教学代码学原理,生产用 egui**。两者不冲突,只是不同抽象层级。

### 10.8 cutscene UI 的设计经验

最后,casey 在视频里讨论的几条 cutscene 设计经验:

**1. 元素少**。cutscene 屏幕元素 ≤ 5 个。多了观众眼花。

**2. 节奏控制**。每个元素停留 2-5 秒。短了看不清,长了无聊。

**3. 留白**。屏幕中央留空,文字偏角。给观众"看剧情"的空间。

**4. 字体大小**。cutscene 字体通常比 HUD 大 1.5-2x。观众远观,要清楚。

**5. 颜色对比**。文字背景半透明黑色,确保任何背景上可读。

这些是 cutscene 设计的"软规则",代码无法强制,但 casey 在 HH 里以身作则。

**6. 测试不同分辨率**。cutscene 元素位置必须 16:9、21:9、4:3 都能正常显示。窄屏可能裁切角元素,要 anchor 自动适配。

**7. 跳过按钮**。商业游戏 cutscene 必须可跳过(Escalate 键)。casey 的 cutscene 系统支持 timeline 跳到 end_time,这是基本要求。

## 11 · 工程教训:layout 系统的演化路径

casey 的 cutscene layout 系统给我们一个工程演化的模板。从 day221 的简单 timeline 到 day222 的 layout,我们看到一个常见路径:

### 11.1 演化阶段

**阶段 1:手写坐标**(day221-222 当前状态)
- 优点:简单、精确、教学清晰
- 缺点:维护成本随 UI 元素数量线性增长

**阶段 2:加 anchor 系统**(casey 当前)
- 元素支持"top-left / center / bottom-right"三种锚
- 屏幕尺寸变化时自动适配

**阶段 3:加 box layout**(未来)
- UI 元素分组,组内自动水平 / 垂直排列
- 引入 spacing、padding 概念

**阶段 4:加 flex / grid**(商业化)
- 二维布局,响应式
- 文本测量 + 国际化支持

**阶段 5:加 constraint**(高端 GUI)
- 约束方程组求解
- 自动 resize / 自适应

casey 的 HH 项目停在阶段 2,因为 debug UI 不需要更复杂。商业引擎(Unity / Unreal)做到阶段 4-5。

### 11.2 何时该升级

判断你的项目何时升级 layout 系统:

- 元素数 < 20:阶段 1-2 够
- 元素数 20-200:阶段 3(box layout)
- 元素数 200+:阶段 4(flex / grid)
- 不同分辨率 + 国际化:阶段 4 必需
- 桌面应用(响应窗口 resize):阶段 5

casey 的 cutscene 系统元素数 5-10,阶段 2 完全够。你的项目要按需升级。
