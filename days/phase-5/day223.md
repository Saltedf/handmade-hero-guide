
# Day 223 · 播放多个过场动画

> 之前同时只能播一个 cutscene。今天 casey 让游戏同时跑多个 cutscene——开场动画 + UI 提示 + 字幕,各自独立 timeline,合成显示。

## 0 · 为什么要有这一天

游戏实际场景:

- **战斗中**:角色大招过场 + UI 提示"按 Q 闪避" + 字幕"Boss 怒吼"
- **过场**:背景演示 + 玩家头像特写 + 字幕
- **菜单**:背景动画 + 按钮 hover 动画 + 鼠标光标

这些都是**多个 cutscene 同时跑**。之前 casey 只支持"一个 cutscene",切换时上一个立即停。今天升级成多 cutscene 并发,各独立 timeline,渲染时按 layer z-order 合成。

**并发 vs 并行**:

- **并发 (concurrent)**:多个 cutscene 逻辑上同时存在,各自有时间线
- **并行 (parallel)**:多个 CPU 核心同时执行

casey 今天是并发(单线程交替处理多个 cutscene)。Day 122+ 的多线程在 game update,但 cutscene 仍然单线程(避免同步复杂)。

心理锚点:看完今天,你能解释"为什么浏览器能同时开多个 tab、每个 tab 独立动画"。

## 1 · Casey 今天做了什么

1. **加 CutscenePlayer struct**:管理多个 active cutscene
2. **加 play / stop / pause API**
3. **改 update**:每帧更新所有 active cutscene
4. **改 render**:收集所有 cutscene 的所有 layer,统一按 z 合成

## 2 · 心智模型

### 类比:多浏览器 tab

浏览器每个 tab 独立:

- 独立 URL
- 独立 JavaScript 上下文
- 独立 DOM 树

但所有 tab 共享屏幕:可视化部分用同一窗口。Tab 之间切换 = 哪个 tab 在前台。

casey 的 cutscene player 类似:每个 cutscene 独立 timeline、独立 layer 集合。但渲染时所有 active cutscene 的 layer 合到一起,按 z 排序。

### 2.1 CutscenePlayer 设计

```rust
struct CutscenePlayer {
    active: Vec<ActiveCutscene>,
}

struct ActiveCutscene {
    cutscene: Cutscene,
    start_time: f32,    // 全局时间
    state: PlayState,
}

enum PlayState { Playing, Paused(f32), Stopped }

impl CutscenePlayer {
    fn play(&mut self, cutscene: Cutscene, current_time: f32) {
        self.active.push(ActiveCutscene {
            cutscene,
            start_time: current_time,
            state: PlayState::Playing,
        });
    }

    fn update(&mut self, current_time: f32) {
        for ac in &mut self.active {
            if let PlayState::Playing = ac.state {
                let local = current_time - ac.start_time;
                if local > ac.cutscene.total_duration() {
                    ac.state = PlayState::Stopped;
                }
            }
        }
        // 清理 stopped
        self.active.retain(|ac| !matches!(ac.state, PlayState::Stopped));
    }

    fn render(&self, current_time: f32) -> Vec<Frame> {
        let mut all_frames: Vec<(i32, Frame)> = vec![];
        for ac in &self.active {
            if let PlayState::Playing = ac.state {
                let local = current_time - ac.start_time;
                for layer in &ac.cutscene.layers {
                    if let Some(f) = layer.sample(local) {
                        all_frames.push((layer.z, f));
                    }
                }
            }
        }
        all_frames.sort_by_key(|(z, _)| *z);
        all_frames.into_iter().map(|(_, f)| f).collect()
    }
}
```

`Vec::retain` 是 Rust 的方法:保留满足条件的元素,删除其他。等价于 filter + 重新赋值,但 in-place。

### 2.2 Z-order 跨 cutscene

两个 cutscene 各自有 layer。渲染时怎么排 z?选项:

- **全局 z**:所有 layer 共享同一 z 空间,cutscene A 的 layer 可以比 cutscene B 的高
- **cutscene 优先级 + 局部 z**:cutscene A 整体 z=100,B 整体 z=200,各内部 layer 再细化

casey 选**全局 z**:简单,所有 layer 在同一平面竞争。例如 menu cutscene 的按钮 z=10,过场 cutscene 的背景 z=0,合成时按钮在背景上。

更复杂的做法(composite z):

```rust
fn composite_z(scene_z: i32, layer_z: i32) -> i32 {
    scene_z * 1000 + layer_z  // 假设每 cutscene 内 z < 1000
}
```

### 2.3 生命周期管理

cutscene 的生命周期:

```
Created → Playing → (Paused ↔ Playing) → Stopped → Removed
```

casey 用 enum 表达:

```rust
enum PlayState {
    Playing,
    Paused { paused_at: f32 },
    Stopped,
}
```

`Paused` 需要记录暂停时间(恢复时从那里继续)。`Stopped` 表示自然结束或被外部停止。

### 2.4 优先级

某些 cutscene 重要(过场动画),用户不能跳过;某些次要(UI 提示),可以被打断。casey 加 priority:

```rust
struct ActiveCutscene {
    cutscene: Cutscene,
    start_time: f32,
    state: PlayState,
    priority: Priority,
}

enum Priority { Low, Normal, High, Critical }
```

高优先级 cutscene 启动时可以打断低优先级:

```rust
fn play_with_priority(&mut self, c: Cutscene, p: Priority, t: f32) {
    if p == Priority::Critical {
        // 清掉所有 Low
        self.active.retain(|ac| ac.priority != Priority::Low);
    }
    self.active.push(ActiveCutscene {
        cutscene: c, start_time: t, state: PlayState::Playing, priority: p,
    });
}
```

### 3.1 · 游戏编程视角

- 各独立状态(PCB)
- 共享资源(CPU、内存、文件)

### 3.4 · 并发安全视角

casey 的 cutscene 单线程。如果要跨线程(例如 worker thread 触发 cutscene),需要 `Arc<Mutex<CutscenePlayer>>`。

Rust 视角:

```rust
use std::sync::{Arc, Mutex};

let player = Arc::new(Mutex::new(CutscenePlayer::new()));

// Worker thread
let p = Arc::clone(&player);
std::thread::spawn(move || {
    let mut guard = p.lock().unwrap();
    guard.play(cutscene, current_time);
});
```

casey 不展开(避免复杂度),Day 122+ 的多线程已经有 worker pattern 示范。

#### Rust async 与多 cutscene

如果用 async Rust 处理多 cutscene(用 task 表示每个播放):

```rust
use tokio::task::JoinSet;

let mut tasks = JoinSet::new();
for cutscene in cutscenes {
    tasks.spawn(async move {
        let mut t = 0.0;
        while t < cutscene.duration {
            cutscene.apply(t).await;
            tokio::time::sleep(Duration::from_millis(16)).await;
            t += 0.016;
        }
    });
}
while let Some(_) = tasks.join_next().await {}
```

每个 cutscene 是一个 task,并发执行。优点:逻辑清晰(顺序代码),cutscene 内部可以 await(等待音效、动画事件)。

缺点:tokio runtime 引入复杂度,cutscene 之间共享状态要 sync。游戏主循环通常不用 async,而是固定 tick update——async 更适合 IO 密集(网络、文件),游戏是计算密集。

### 3.5 · 🎮 游戏工业的多 timeline 实战

商业游戏的多 timeline 实例极常见:

**Boss 战**。boss 通常有多个状态机阶段(普通 / 狂暴 / 临死),每个阶段一个 timeline 实例。切换阶段时旧 instance 平滑退出,新 instance 进来。

**对话系统**。RPG 的对话是 timeline——每句对白一个 clip,character表情、相机角度、音效并行。多个对话可同时进行(主角 vs NPC1,NPC2 vs NPC3)。

**教程系统**。每个教程步骤是一个短 cutscene。多个教程可排队(完成 step 1 自动开始 step 2)。

**多人游戏**。每个玩家可能触发不同 cutscene,服务器要并行管理。casey 的 HH 是单人游戏不涉及,但商业游戏普遍。

### 3.6 · 工程模式:状态机 vs timeline

casey 用 timeline 表达 cutscene,但很多场景用状态机更合适。两者区别:

- **Timeline**:时间驱动,固定时序,适合"线性叙事"(cutscene、过场)
- **State machine**:事件驱动,响应外部输入,适合"反应式行为"(AI、菜单、对话树)

casey 在 day226 切换到"meta game modes"用状态机。cutscene 是 timeline,mode switch 是 state machine,两者协作。

复杂系统通常 hybrid:**外部是 state machine,内部某 state 触发 timeline**。比如 boss 战:
- state machine:boss 当前状态(普通 / 狂暴 / 死亡)
- state "狂暴"触发 timeline:播放 boss 嘶吼 cutscene,UI 闪红

casey 的 HH 项目逐步演化出这种 hybrid 模式。day223 是 timeline 的极简版,day226+ 是 state machine 的引入,后续它们融合。

### 3.7 · 测试 cutscene 系统

cutscene 系统的测试有几个特殊点:

**1. 时序测试**。cutscene 必须按预定时序播放——keyframe 在精确时刻触发。但帧率波动(60 vs 144 FPS)会让时间步长不同。解决:测试用**固定时间步**(每次 update(dt=1/60.0)),不依赖实际帧率。

**2. snapshot 测试**。cutscene 的最终视觉效果(frame N 的渲染结果)可以 snapshot,CI 检测回归。Rust 用 `insta` crate 做 snapshot 测试。

```rust
#[test]
fn test_cutscene_frame_60() {
    let mut cutscene = CutsceneInstance::new(test_template());
    for _ in 0..60 {
        cutscene.update(1.0 / 60.0);
    }
    let state = cutscene.sample();
    insta::assert_yaml_snapshot!(state);  // 第一次写,后续比对
}
```

**3. 跨平台一致性**。cutscene 的浮点运算可能在不同 CPU / 编译器产生不同结果(x87 80-bit vs SSE 32-bit)。cutscene 测试用 `assert_abs_diff_eq` 而非 `assert_eq`,容忍 1 ULP 误差。

**4. 时长测试**。cutscene 必须在预定时长内结束。测试:

```rust
#[test]
fn test_cutscene_completes() {
    let mut c = CutsceneInstance::new(template);
    let mut t = 0.0;
    while c.is_playing() {
        c.update(1.0 / 60.0);
        t += 1.0 / 60.0;
        assert!(t < template.duration + 1.0, "cutscene stuck");
    }
    assert_abs_diff_eq!(t, template.duration, epsilon = 1.0 / 30.0);
}
```

这些测试策略对所有时间驱动的游戏系统都适用——AI、动画、物理。casey 不在 HH 视频里详细讨论测试,但任何严肃项目都要写。

### 3.9 · 工程教训:多 timeline 的复杂度边界

casey Day 223 引入多 timeline 后,系统复杂度上升一档。我们应该意识到**复杂度边界**:

- **1 timeline**:trivial,所有 bug 直接 trace
- **2-3 timelines**:中等,需要 priority blend
- **10+ timelines**:复杂,需要 blend stack / 状态机
- **100+ timelines**:必须 ECS 化,数据驱动,人脑无法理解单个 timeline 的作用

casey 的 HH 项目停在 2-3 timeline 水平(够用)。商业 RPG / 动作游戏通常到 10-20(每个 NPC 一个 dialogue timeline,每个动画一个 anim timeline)。MMO 可能到几百。

如果你的项目要 scale,关键是**早期抽象到位**——区分 template / instance,数据驱动定义。casey Day 223 的简化版给我们起步模板,生产项目按这个模式扩展。

### 3.10 · 多 cutscene 在不同游戏类型的应用

不同游戏类型对多 cutscene 的需求差异:

**RPG**(巫师、博德之门):大量对话 cutscene,每个 NPC 一个 timeline。需要 complex blend(动画 + 表情 + 相机 + 对白同步)。

**动作游戏**(战神、黑暗之魂):少量但精美的 cutscene。boss 战 intro、剧情转折。每帧渲染要 60+ FPS,cutscene 不能阻塞主循环。

**MOBA / FPS**(LOL、CS):几乎无 cutscene,只有 round end / MVP 短动画。性能优先,UI 简洁。

**叙事游戏**(底特律变人):cutscene 是核心,游戏机制辅助。timeline 系统极复杂,分支叙事。

casey 的 HH 是 platformer / 动作冒险,cutscene 需求中等。Day 223 的方案对这个量级够用。

### Lv1 · 概念辨析

**题**:为什么 cutscene 用并发(单线程交替)而不是并行(多线程)?

**参考解答**:cutscene 渲染共享屏幕,合成必须串行。多线程并行处理反而要同步(谁先画、谁后画),复杂。单线程交替处理多个 cutscene,逻辑清晰、无锁、cache 友好。并行只在"重计算"(粒子物理、AI)有意义,渲染合成没必要。

### Lv2 · 动手实践

**题**:实现 CutscenePlayer,play / update / render。测试同时 2 个 cutscene,各 3 个 layer,在不同时刻激活。

完成标准:render 输出按 z 排序的 layer 列表。

**参考解答**:

```rust
#[derive(Clone, Copy, Debug)]
struct Frame { id: u32 }

struct Layer {
    start: f32,
    duration: f32,
    z: i32,
    frame_id: u32,
}

impl Layer {
    fn sample(&self, t: f32) -> Option<Frame> {
        if t >= self.start && t <= self.start + self.duration {
            Some(Frame { id: self.frame_id })
        } else { None }
    }
}

struct Cutscene { layers: Vec<Layer> }

enum PlayState { Playing, Stopped }

struct ActiveCutscene {
    cutscene: Cutscene,
    start_time: f32,
    state: PlayState,
}

struct CutscenePlayer { active: Vec<ActiveCutscene> }

impl CutscenePlayer {
    fn new() -> Self { Self { active: vec![] } }

    fn play(&mut self, c: Cutscene, t: f32) {
        self.active.push(ActiveCutscene {
            cutscene: c, start_time: t, state: PlayState::Playing,
        });
    }

    fn update(&mut self, current: f32) {
        let max_dur = |c: &Cutscene| c.layers.iter()
            .map(|l| l.start + l.duration).fold(0.0, f32::max);
        for ac in &mut self.active {
            if let PlayState::Playing = ac.state {
                if current - ac.start_time > max_dur(&ac.cutscene) {
                    ac.state = PlayState::Stopped;
                }
            }
        }
        self.active.retain(|ac| !matches!(ac.state, PlayState::Stopped));
    }

    fn render(&self, current: f32) -> Vec<Frame> {
        let mut frames: Vec<(i32, Frame)> = vec![];
        for ac in &self.active {
            if let PlayState::Playing = ac.state {
                let local = current - ac.start_time;
                for layer in &ac.cutscene.layers {
                    if let Some(f) = layer.sample(local) {
                        frames.push((layer.z, f));
                    }
                }
            }
        }
        frames.sort_by_key(|(z, _)| *z);
        frames.into_iter().map(|(_, f)| f).collect()
    }
}

fn main() {
    let mut player = CutscenePlayer::new();
    let cs1 = Cutscene { layers: vec![
        Layer { start: 0.0, duration: 10.0, z: 0, frame_id: 1 },
        Layer { start: 1.0, duration: 8.0, z: 5, frame_id: 2 },
    ]};
    let cs2 = Cutscene { layers: vec![
        Layer { start: 0.0, duration: 5.0, z: 3, frame_id: 10 },
    ]};
    player.play(cs1, 0.0);
    player.play(cs2, 2.0);

    for t in [0.0, 1.5, 3.0, 7.0, 12.0] {
        player.update(t);
        let frames = player.render(t);
        println!("t={:.1}: active={}, frames={:?}",
                 t, player.active.len(),
                 frames.iter().map(|f| f.id).collect::<Vec<_>>());
    }
}
```

## 10 · 深入:多 timeline 并行播放的实现细节

casey 今天让多个 cutscene 同时播放,本质上是"多 timeline 实例 + 各自时钟"。这种模式在游戏里无处不在,让我们把它彻底剖析。

### 10.1 timeline 实例 vs timeline 模板

工业级实现区分两个概念:

**Timeline Template**(模板):描述 cutscene 的"定义",包括所有 keyframe、轨道、时长。模板是不可变的,从 asset 加载。

**Timeline Instance**(实例):模板的一次运行时实例,记录当前时间、播放状态、各轨道当前值。同一模板可以有多个并行实例。

```rust
// 模板(共享)
struct CutsceneTemplate {
    duration: f32,
    tracks: Vec<TrackTemplate>,
}

// 实例(每播放一个,创建一个)
struct CutsceneInstance {
    template: Arc<CutsceneTemplate>,
    current_time: f32,
    play_state: PlayState,    // Playing / Paused / Stopped
    speed: f32,               // 倍速播放(0.5 = 慢放, 2.0 = 快放)
}

impl CutsceneInstance {
    fn update(&mut self, dt: f32) {
        if self.play_state == PlayState::Playing {
            self.current_time += dt * self.speed;
            if self.current_time >= self.template.duration {
                self.play_state = PlayState::Stopped;
                self.current_time = self.template.duration;
            }
        }
    }
    
    fn sample(&self) -> Vec<TrackValue> {
        self.template.tracks.iter()
            .map(|t| t.sample(self.current_time))
            .collect()
    }
}
```

casey 的简化版没区分 template / instance,但概念上一致。

### 10.2 多实例的资源管理

多个 instance 共享同一个 template,通过 `Arc<CutsceneTemplate>` 引用计数。casey 用 asset handle 实现等价效果。

```rust
struct GameState {
    cutscene_templates: AssetStore<CutsceneTemplate>,
    active_cutscenes: Vec<CutsceneInstance>,
}

fn spawn_cutscene(state: &mut GameState, template_id: AssetId) {
    let template = state.cutscene_templates.get(template_id);
    state.active_cutscenes.push(CutsceneInstance::new(template));
}

fn update(state: &mut GameState, dt: f32) {
    for cutscene in &mut state.active_cutscenes {
        cutscene.update(dt);
    }
    // 清理播放完成的
    state.active_cutscenes.retain(|c| c.play_state != PlayState::Stopped);
}
```

`retain` 是 Rust Vec 的实用方法——保留谓词为 true 的元素,删除其他。每帧调用,O(n) 但 n 通常小。

### 10.3 多 cutscene 的事件冲突

多个 cutscene 同时播放时,事件可能冲突。casey 在视频里讨论:

**冲突 1:同一目标 property**。两个 cutscene 都想设 player.position,后一个赢还是混合?

casey 选择:**优先级 + 混合**。高优先级 cutscene 的值赢,低优先级填空缺。这就是 day221 讨论的 priority blend。

**冲突 2:同时触发事件**。两个 cutscene 在同一帧都触发"play sound",会出现什么?

casey 选择:**事件队列**。所有事件进队列,update 末尾统一处理。这避免事件 handler 重入(一个事件触发另一个事件,无限递归)。

**冲突 3:cutscene 互相暂停**。cutscene A 暂停 cutscene B?casey 不支持(复杂),生产 timeline 支持。

### 10.4 实战:Unity Playable Director 多实例

Unity 的 PlayableDirector 支持多实例:

```csharp
// 同一 timeline 资源,多个 director 实例
public PlayableDirector director1;  // 挂在 GameObject A
public PlayableDirector director2;  // 挂在 GameObject B

void Start() {
    director1.Play();
    director2.Play();  // 同时播放
}
```

Unity 内部用 Playable Graph 管理,每个 director 一个独立 graph。多个 graph 并行求值,渲染时混合结果。

### 10.5 casey 的简化:为什么够用

casey 的多 cutscene 系统简化:
- 单一混合策略(priority blend)
- 无事件队列(同步触发)
- 无互相暂停(各自独立)

适合:**游戏过场动画**。商业 RPG / 动作游戏需要更复杂系统,但 casey 的 HH 项目停在"够用"水平。

### 10.6 性能考虑:多 cutscene 同时播放的开销

N 个 cutscene 同时播放,每帧 update + sample:

```
update:    N × O(1)         (时间累加)
sample:    N × O(K)         (K = 每个 cutscene 的 keyframe 数)
blend:     O(N × M)         (M = 影响的 property 数)
render:    O(M)             (绘制 property)
```

casey 的 HH 项目:典型 N=1-3,K=20,M=10。总每帧 ~100 操作,~1μs,完全可忽略。

商业游戏可能 N=20+(复杂场景),K=100+(精细 cutscene),M=1000+(每个 entity 都被影响)。这时 N × K × M = 200 万,~10ms,吃掉一帧。需要优化:

- **冻结远处 cutscene**:玩家不可见的 cutscene 不 update
- **预计算**:不变 cutscene 的 property 预计算成表,lookup O(1)
- **GPU 加速**:cutscene 矩阵在 GPU compute shader 计算

casey 不涉及这些,但他 Day 223 给的基础让你看商业引擎 cutscene 优化时,能理解优化方向。

### 10.7 多 cutscene 的状态管理

最后,讨论一个微妙问题:**多 cutscene 共享状态**。

假设 cutscene A 把 player.position 设为 (100, 0),cutscene B 也想设 player.position 为 (200, 0)。问题:

1. 哪个赢?
2. cutscene A 结束后,player.position 是回到 (0, 0) 还是保留 (100, 0)?
3. 玩家输入如何与 cutscene 输入混合?

casey 的设计:
- priority blend,高优先级赢
- cutscene 结束,property 回到"未控制状态",由游戏逻辑接管
- cutscene 期间禁用玩家输入

工业级方案更复杂:
- **blend stack**:每个 property 有一个堆栈,cutscene 入栈、出栈
- **additive blend**:cutscene 的 delta 累加到 base
- **state machine**:每个 property 知道当前被谁控制,根据状态机决定混合

casey 简化为"高优先级覆盖",是大多数 cutscene 系统的实际行为。复杂混合(Unity / Unreal 的复杂 timeline)是 R&D 级别功能,casey 不展开。

### 10.8 Rust 实战:用 ECS 实现多 cutscene

如果用 Bevy ECS 实现 casey 的多 cutscene 系统:

```rust
use bevy::prelude::*;

#[derive(Component)]
struct CutsceneInstance {
    template: Handle<CutsceneTemplate>,
    current_time: f32,
    speed: f32,
}

#[derive(Component)]
struct Player;

fn update_cutscenes(
    time: Res<Time>,
    templates: Res<Assets<CutsceneTemplate>>,
    mut cutscenes: Query<&mut CutsceneInstance>,
) {
    for mut cutscene in &mut cutscenes {
        cutscene.current_time += time.delta_seconds() * cutscene.speed;
        // sample template,设 property 略
    }
}

fn main() {
    App::new()
        .add_plugins(DefaultPlugins)
        .add_systems(Update, update_cutscenes)
        .run();
}
```

ECS 的天然并行性 + Bevy 的 schedule 让多 cutscene 系统比 casey 手写版简洁。但底层原理一致——timeline 模板 + 实例 + 时间更新。
