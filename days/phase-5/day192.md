# Day 192 · 实现自重编译

> Phase 1 已经做了热重载:游戏代码是 cdylib,改代码后 `cargo build`,libloading 重新加载。但你要**手动**触发 `cargo build`。今天 Casey 把这一步自动化:游戏自己跑 `cargo build`,完成后自动热重载。

## 0 · 为什么要有这一天

之前的开发流程:

1. 在编辑器改 Rust 代码
2. 切到终端,跑 `cargo build`
3. 切回游戏,按键触发热重载
4. 继续玩

3 步切来切去很烦。Casey 的优化:**游戏自己监视源码**,改了就自己 build。

这是**自重编译**(self-recompilation):程序运行时调编译器编译自己的下一版本。听起来很玄,其实就是:

```
loop:
    if 源码变了:
        跑 cargo build
        if 成功:
            重新加载 cdylib
        else:
            显示编译错误(在游戏画面上)
```

实现的关键:**Linux 上监视文件变化**(inotify / polling),**子进程跑 cargo**(`std::process::Command`)。

心理锚点:看完今天,你能用 Rust 跑子进程、解析其输出、监视文件变化。

## 1 · Casey 今天做了什么

Casey 加自重编译:

1. 平台层循环里检查"重新编译请求"(按键触发或源码变化)
2. 调 `CreateProcess`(Windows)/ `posix_spawn`(Linux)跑 `build.bat` / `cargo build`
3. 等待子进程结束,拿 exit code
4. 成功 → 调 libloading 重新加载
5. 失败 → 在游戏画面显示编译错误(读 stderr)

## 2 · 心智模型

### 类比:机器人自己造下一代

工厂里有机器人组装产品。一般流程:人改设计图,机器人按新图组装。

### 2.0 子进程 API 的根本机制

Linux 上 spawn 子进程用 `fork()` + `exec()`:fork 复制当前进程,exec 在子进程里加载新程序。Rust 的 `std::process::Command` 封装这个:

```rust
use std::process::Command;

let output = Command::new("cargo")
    .arg("build")
    .arg("--release")
    .current_dir("/path/to/project")
    .output()?;  // 等子进程结束,捕获 stdout/stderr

println!("exit: {}", output.status);
println!("stdout: {}", String::from_utf8_lossy(&output.stdout));
println!("stderr: {}", String::from_utf8_lossy(&output.stderr));
```

**关键参数**:
- `Command::new("cargo")` — 找 PATH 里的 cargo。Linux 上要走 `execvp` 查 PATH
- `.arg("build")` — 加参数,每个 `.arg()` 是一个独立 argv 元素(不会自动 split 空格)
- `.current_dir(...)` — 子进程的工作目录
- `.output()` — 同步等子进程结束,捕获输出。还有 `.status()`(不捕获输出)和 `.spawn()`(异步,返回 Child handle)

**异步 spawn 不阻塞游戏**:

```rust
let child = Command::new("cargo").arg("build").spawn()?;
// 游戏继续跑
// 后面定期检查 child.try_wait()
loop {
    match child.try_wait()? {
        Some(status) => {
            // 编译完成
            if status.success() { reload_lib(); }
            break;
        }
        None => {
            // 还在编译,继续游戏
            game_update();
        }
    }
}
```

`try_wait()` 不阻塞,立即返回(None = 还在跑,Some = 结束)。

### 2.1 文件监视:inotify vs polling

Linux 5.0+ 内核有 **inotify**,高效异步监视文件变化:

```rust
use notify::{Watcher, RecursiveMode, RecommendedWatcher};

let mut watcher = RecommendedWatcher::new(|res: Result<notify::Event, _>| {
    if let Ok(event) = res {
        println!("changed: {:?}", event.paths);
    }
})?;

watcher.watch("src/", RecursiveMode::Recursive)?;
// 后续文件变化触发回调
```

`notify` crate 跨平台封装。Linux 上用 inotify,macOS 用 FSEvents,Windows 用 ReadDirectoryChangesW。

**polling 备选**(简单但慢):

```rust
fn poll_files_changed(dir: &Path, last_modified: &mut SystemTime) -> bool {
    let mut changed = false;
    for entry in fs::read_dir(dir)? {
        let path = entry?.path();
        let mtime = fs::metadata(&path)?.modified()?;
        if mtime > *last_modified {
            *last_modified = mtime;
            changed = true;
        }
    }
    changed
}
```

Polling 每秒扫一次,慢但简单。Casey 教学版可以先用 polling,inotify 留作优化。

### 2.2 增量编译的重要性

`cargo build` 增量编译——只重编译改动的 crate。Rust 增量编译基于 **MIR**(Mid-level IR)缓存,每次编译后存到 `target/release/incremental/`。

```
改动 src/main.rs         → 只重编译 main crate(几百毫秒)
改动 lib/foo/src/lib.rs  → 重编译 foo crate + 依赖它的(几秒)
改 Cargo.toml 加依赖     → 全量重编译(几十秒)
```

**自重编译的体感**:小改动 1-2 秒,中等改动 5-10 秒,大改动几十秒。这是为什么 Casey 强调"代码组织要细粒度"——一个巨型 crate 改一行就全重编译。

### 2.3 编译错误在游戏画面显示

cargo 失败时,把 stderr 渲染到游戏画面——这是 Casey 的"流"工作流:

```
[ compile error ]
error[E0596]: cannot borrow `state` as mutable, as it is not declared as mutable
   --> src/game.rs:123:5
    |
123 |     state.update();
    |     ^^^^^ help: consider `let mut state`
```

错误用红色,警告用黄色。开发者**不离开游戏**就能看到错。这是 Unreal Live Coding / Unity Inspector 风格的设计。

### 2.4 自重编译的循环时间目标

理想:< 2 秒(改一行 → 看到效果)。

| 优化 | 效果 |
|---|---|
| 默认 | 5-10 秒 |
| 加 mold linker | -30%(链接快 10x) |
| 加 sccache | -20%(crate 级缓存) |
| 用 cargo nextest | 不影响 build,但 test 快 |
| 拆细 crate | 改动局部化,build 局部 |

Casey 的 HH 通常 1-3 秒,因为代码组织好。

### 2.5 防止 build 循环

如果自重编译代码本身有 bug,游戏崩,build 不再触发——死锁。

防御:
1. **build 命令独立**:不依赖游戏代码(build.rs 不调游戏)
2. **platform layer 不可热重载**:游戏层崩溃,平台层继续
3. **手动 fallback**:键盘快捷键触发 build,不依赖游戏逻辑

Casey 在 HH 反复强调:**平台层必须鲁棒**——游戏可以崩,平台不能崩。

## 3 · 四域深入

自重编译:**机器人自己改设计图,自己按新图组装自己**。听起来诡异,但代码层面就是"程序 spawn 一个 cargo 进程编译自己"。

### 2.1 子进程基础

Rust 跑子进程:

```rust
use std::process::Command;

let output = Command::new("cargo")
    .arg("build")
    .arg("--release")
    .current_dir("/path/to/project")
    .output();  // 等待完成,返回 Output

match output {
    Ok(o) => {
        if o.status.success() {
            println!("build OK");
        } else {
            println!("build failed:");
            println!("{}", String::from_utf8_lossy(&o.stderr));
        }
    }
    Err(e) => eprintln!("spawn failed: {}", e),
}
```

**Rust 注释**:
- `Command::new("cargo")` — 创建子进程,可执行文件名
- `.arg(...)` — 参数,空格分隔的要分开传
- `.current_dir(...)` — 子进程工作目录
- `.output()` — 同步等待,捕获 stdout / stderr
- `.status()` — 异步,返回 ExitStatus

### 2.2 异步构建(不阻塞游戏)

`output()` 会**阻塞当前线程**——游戏循环卡死等编译。要异步:

```rust
use std::process::Command;

let mut child = Command::new("cargo")
    .arg("build")
    .spawn()?;  // 立刻返回 Child

// 游戏循环继续跑
loop {
    // 检查 child 是否结束
    match child.try_wait() {
        Ok(Some(status)) => {
            println!("build done, status: {}", status);
            // 重新加载 cdylib
            break;
        }
        Ok(None) => {
            // 还在编译,继续游戏循环
        }
        Err(e) => eprintln!("error: {}", e),
    }
    game_update_and_render();
}
```

**`try_wait()`** — 不阻塞,立刻返回;`Ok(None)` 表示还在跑。

### 2.3 文件监视(inotify)

Linux 上监视文件变化用 `inotify`(kernel feature)。

```bash
# 命令行版
inotifywait -m -e modify src/  # 监视 src/ 修改
```

Rust 用 `notify` crate:

```rust
use notify::{Watcher, RecursiveMode, DebouncedEvent};

let (tx, rx) = std::sync::mpsc::channel();
let mut watcher: notify::RecommendedWatcher = Watcher::new_raw(tx)?;
watcher.watch("src/", RecursiveMode::Recursive)?;

// 在游戏循环
match rx.try_recv() {
    Ok(event) => {
        println!("file changed: {:?}", event);
        // 触发 build
    }
    Err(_) => {}  // 无事件
}
```

`notify` 跨平台(Linux 用 inotify,macOS 用 FSEvents,Windows 用 ReadDirectoryChangesW)。

### 2.4 触发热重载

```rust
pub struct HotReloader {
    last_mtime: std::time::SystemTime,
    lib: libloading::Library,
    build_in_progress: Option<std::process::Child>,
}

impl HotReloader {
    pub fn check_and_reload(&mut self, lib_path: &str) {
        // 如果正在编译,检查状态
        if let Some(child) = &mut self.build_in_progress {
            match child.try_wait() {
                Ok(Some(status)) if status.success() => {
                    // build 成功,重新加载
                    drop(self.lib);  // 先 drop 老的
                    self.lib = unsafe { libloading::Library::new(lib_path) }.unwrap();
                    self.build_in_progress = None;
                }
                Ok(Some(_)) => {
                    // build 失败
                    self.build_in_progress = None;
                }
                Ok(None) => {}  // 还在编译
                Err(_) => {}
            }
        }
    }

    pub fn trigger_build(&mut self) {
        self.build_in_progress = Some(
            std::process::Command::new("cargo").arg("build").spawn().unwrap()
        );
    }
}
```


### 3.1 · Linux 系统编程视角

Linux 进程创建:

Rust 的 `Command` 用 `posix_spawn`(快)或 `fork+exec`(兼容)。

### 3.6 · 🐧 Linux 系统编程视角(perf / ftrace / eBPF)

Linux 内核自带一整套 profiling 基础设施,工业 Linux 性能分析的所有工具都基于它。理解这套设施能让你看 Casey 的 profiler 处于什么位置。

**perf** 是 Linux 内核的标准 profiling 接口。`perf record ./my_game` 跑游戏,perf 通过 `perf_event_open(2)` 系统调用,让内核每隔 N 个 CPU cycle 采样一次指令指针(IP)。采到 N 万个样本后,`perf report` 显示每个函数被采到多少次——按比例还原 CPU 时间分布。这是**统计 sampling**——不记录每次调用,而是按概率采样。

```bash
# 在 Arch 上跑 perf(需要内核 CONFIG_PERF_EVENTS=y,默认开)
sudo pacman -S perf
sudo perf record ./target/release/my_game
sudo perf report --stdio | head -30
# 输出形如:
#   35.00%  my_game  my_game         [.] update_physics
#   18.00%  my_game  my_game         [.] render_geometry
#    8.00%  my_game  libc-2.31.so    [.] memcpy
```

**perf 的两种模式**:
- **Sample-based**:每 N cycle 采样,适合找 hot spot。优点开销小(1% CPU),缺点错过短函数。
- **Trace-based**:每次事件都记录,精确。Casey HH 的 profiler 是 trace-based——每条 begin/end event 都记,精确度高但开销大(~5% CPU)。

**ftrace** 是内核函数级 trace。`/sys/kernel/debug/tracing/` 暴露 trace 点:

```bash
# 启用 sched_switch trace
echo sched_switch > /sys/kernel/debug/tracing/set_event
echo 1 > /sys/kernel/debug/tracing/tracing_on
# 等几秒
cat /sys/kernel/debug/tracing/trace | head
# 看每个 context switch
```

ftrace 是内核 hook——你 enable `sched_switch`,内核每次 context switch 都写一条记录到 ring buffer。这就是 Casey HH profiler 的"内核版"——同样的 ring buffer 数据结构,同样的"事件流"思维。

**eBPF** 是 Linux 内核的革命性技术。eBPF 让你在内核运行安全的 bytecode,自定义 profiling / monitoring 逻辑。eBPF 程序用 C 子集写,编译成 BPF bytecode,加载到内核 hook 点(系统调用、网络包、trace point)。这是内核版"插件"——比 ftrace 灵活,比内核模块安全。

```bash
# 用 bpftrace 做 profiling
sudo pacman -S bpftrace
sudo bpftrace -e 'profile:hz:99 @[stack] = count();'
# 每秒采样 99 次,记录 call stack
```

**bpftrace** 一个脚本 = 一个 profiler。你可以一分钟内写"统计 malloc 调用"、"看哪个进程 IO 最多"、"找 page fault 来源"——这是 Linux 性能分析的现代化武器。

**/proc/[pid]/stat / status / maps** 暴露进程运行时状态:

```bash
# 看你当前进程的 stat(进程的运行时统计)
cat /proc/$$/stat
# 第 14 字段:utime(user CPU time)
# 第 15 字段:stime(kernel CPU time)

# 看 memory mapping
cat /proc/$$/maps
# 输出:地址范围 权限 偏移 设备 inode 文件名
```

工业 profiler 读这些文件得到 cross-process 信息。Casey HH 的 profiler 是 in-process 的(只看自己),不读 /proc——这简化了实现,但看不到 OS 视角。

**Tracy / OPTICK / Superluminal** 是工业 C++ profiler,都用类似架构:ring buffer + thread-local + sample/trace 混合。Tracy 是开源,有 WebSocket UI 跨机器查看;Superluminal 是商业,以"超低 overhead + 时间线视图"著名。Casey HH 的 profiler 简化,但**架构相同**——理解 Casey 的,你就懂了 Tracy 的核心。

### 3.7 · 🦀 Rust 生态视角

Rust 的 profiling 生态有几条主线。

**`tracing` crate** 是 Rust 应用的事实标准 logging / tracing 框架。它结合了 log(级别)和 OpenTracing(span):

```rust
use tracing::{span, info, instrument};

#[instrument]
fn update_physics(dt: f32) {
    // tracing 自动在函数 entry/exit 创建 span
    info!(dt, "physics step");
}

let _span = span!(tracing::Level::INFO, "frame").entered();
update_physics(0.016);
```

`#[instrument]` 是 derive macro——编译时生成 span 创建/退出代码。`tracing` 的 subscriber 决定如何处理 span——log 到文件、发到 tracing UI、profile 等。

**`tracing-tracy`** crate 把 tracing span 转成 Tracy 协议事件。你的 Rust 应用加 tracing + tracing-tracy,就能用 Tracy UI 看 profile。这是 Rust 生态接工业 profiler 的标准方式。

**`puffin`** 是 Rust-native profiler,immediate-mode UI 风格,专为游戏设计:

```rust
puffin::profile_scope!("physics");
update_physics(dt);
// 自动 entry/exit

// 在 egui UI 里
puffin_egui::profiler_window(egui_ctx);
```

puffin 的设计哲学和 Casey HH profiler 几乎一致——in-process、ring buffer、immediate-mode UI。Puffin 是开源,代码可读,是看"Rust 风格 profiler"的范本。

**`measureme`** 是 rustc 用的 profiler,分析 rustc 自己的编译性能。measureme 的设计原则是"低 overhead + 可序列化 + 跨工具分析"——Rust 团队用它优化 rustc。

**Rust 的 `Instant`** 是 std 提供的高精度计时器:

```rust
let start = std::time::Instant::now();
expensive_op();
let elapsed = start.elapsed();
// elapsed 是 Duration,纳秒精度
```

底层在 Linux 是 `clock_gettime(CLOCK_MONOTONIC)`,Windows 是 `QueryPerformanceCounter`,macOS 是 `mach_absolute_time`。这是跨平台高精度时间的标准答案。Casey HH 在不同平台用不同 API(Linux rdtsc、Windows QPC、macOS mach),用 Rust 应该用 `Instant` 抽象。

**Rust 的 atomic 计数**。profiler 多线程时,event push 可能从多个线程同时来。用 `Arc<Mutex<Profiler>`> 是简单方案,但有锁开销。Rust 的 `crossbeam-queue` 提供 lock-free queue,适合高并发 event push。或者用 thread-local buffer + 定期 flush,完全无锁。Tracy 用 thread-local buffer,每线程独立,profiler thread 用 lock-free merge 合并。

**Rust SIMD** 可以加速 collation。如果有 100 万 event 要 collate,用 SIMD(`std::simd` 或 `wide` crate)一次处理 4-8 条 event,duration 计算用 SIMD 减法 + 累加。Tracy 在 collation hot loop 用 AVX2 优化。Rust 的 SIMD 还在稳定化中(unstable `std::simd`),但 `wide` crate 提供稳定的 wrapper。

**Rust 的 `Bytes` / `Arc<[u8]>`** 让 event buffer 零拷贝共享。如果 event buffer 要被 UI thread 读取(同时被游戏 thread 写),用 `Bytes` 引用计数——读 thread 拷贝 Arc,写 thread 替换 Arc 指向新 buffer。这是 lock-free 数据交换的标准模式。

**Rust profiler 的内存安全优势**。C/C++ profiler 大量 ring buffer + 原子操作,容易写错(数据竞争、use-after-free)。Rust 的 borrow checker + Send/Sync + atomic API 让这些错误编译时被捕获。Puffin / measureme 的代码,你可以放心读——Rust 保证内存安全。

```bash
echo sched_switch > /sys/kernel/debug/tracing/set_event
echo 1 > /sys/kernel/debug/tracing/tracing_on
# 等几秒
cat /sys/kernel/debug/tracing/trace | head
# 看每个 context switch
```

ftrace 是内核 hook——你 enable `sched_switch`,内核每次 context switch 都写一条记录到 ring buffer。这就是 Casey HH profiler 的"内核版"——同样的 ring buffer 数据结构,同样的"事件流"思维。

**eBPF** 是 Linux 内核的革命性技术。eBPF 让你在内核运行安全的 bytecode,自定义 profiling / monitoring 逻辑。eBPF 程序用 C 子集写,编译成 BPF bytecode,加载到内核 hook 点(系统调用、网络包、trace point)。这是内核版"插件"——比 ftrace 灵活,比内核模块安全。

```bash
# 用 bpftrace 做 profiling
sudo pacman -S bpftrace
sudo bpftrace -e 'profile:hz:99 @[stack] = count();'
# 每秒采样 99 次,记录 call stack
```

**bpftrace** 一个脚本 = 一个 profiler。你可以一分钟内写"统计 malloc 调用"、"看哪个进程 IO 最多"、"找 page fault 来源"——这是 Linux 性能分析的现代化武器。

**/proc/[pid]/stat / status / maps** 暴露进程运行时状态:

```bash
# 看你当前进程的 stat(进程的运行时统计)
cat /proc/$$/stat
# 第 14 字段:utime(user CPU time)
# 第 15 字段:stime(kernel CPU time)

# 看 memory mapping
cat /proc/$$/maps
# 输出:地址范围 权限 偏移 设备 inode 文件名
```

工业 profiler 读这些文件得到 cross-process 信息。Casey HH 的 profiler 是 in-process 的(只看自己),不读 /proc——这简化了实现,但看不到 OS 视角。

**Tracy / OPTICK / Superluminal** 是工业 C++ profiler,都用类似架构:ring buffer + thread-local + sample/trace 混合。Tracy 是开源,有 WebSocket UI 跨机器查看;Superluminal 是商业,以"超低 overhead + 时间线视图"著名。Casey HH 的 profiler 简化,但**架构相同**——理解 Casey 的,你就懂了 Tracy 的核心。

### 3.9 · 🦀 Rust 生态视角(综合)

Rust 的 profiling 生态有几条主线。

**`tracing` crate** 是 Rust 应用的事实标准 logging / tracing 框架。它结合了 log(级别)和 OpenTracing(span):

```rust
use tracing::{span, info, instrument};

#[instrument]
fn update_physics(dt: f32) {
    // tracing 自动在函数 entry/exit 创建 span
    info!(dt, "physics step");
}

let _span = span!(tracing::Level::INFO, "frame").entered();
update_physics(0.016);
```

`#[instrument]` 是 derive macro——编译时生成 span 创建/退出代码。`tracing` 的 subscriber 决定如何处理 span——log 到文件、发到 tracing UI、profile 等。

**`tracing-tracy`** crate 把 tracing span 转成 Tracy 协议事件。你的 Rust 应用加 tracing + tracing-tracy,就能用 Tracy UI 看 profile。这是 Rust 生态接工业 profiler 的标准方式。

**`puffin`** 是 Rust-native profiler,immediate-mode UI 风格,专为游戏设计:

```rust
puffin::profile_scope!("physics");
update_physics(dt);
// 自动 entry/exit

// 在 egui UI 里
puffin_egui::profiler_window(egui_ctx);
```

puffin 的设计哲学和 Casey HH profiler 几乎一致——in-process、ring buffer、immediate-mode UI。Puffin 是开源,代码可读,是看"Rust 风格 profiler"的范本。

**`measureme`** 是 rustc 用的 profiler,分析 rustc 自己的编译性能。measureme 的设计原则是"低 overhead + 可序列化 + 跨工具分析"——Rust 团队用它优化 rustc。

**Rust 的 `Instant`** 是 std 提供的高精度计时器:

```rust
let start = std::time::Instant::now();
expensive_op();
let elapsed = start.elapsed();
// elapsed 是 Duration,纳秒精度
```

底层在 Linux 是 `clock_gettime(CLOCK_MONOTONIC)`,Windows 是 `QueryPerformanceCounter`,macOS 是 `mach_absolute_time`。这是跨平台高精度时间的标准答案。Casey HH 在不同平台用不同 API(Linux rdtsc、Windows QPC、macOS mach),用 Rust 应该用 `Instant` 抽象。

**Rust 的 atomic 计数**。profiler 多线程时,event push 可能从多个线程同时来。用 `Arc<Mutex<Profiler>`> 是简单方案,但有锁开销。Rust 的 `crossbeam-queue` 提供 lock-free queue,适合高并发 event push。或者用 thread-local buffer + 定期 flush,完全无锁。Tracy 用 thread-local buffer,每线程独立,profiler thread 用 lock-free merge 合并。

**Rust SIMD** 可以加速 collation。如果有 100 万 event 要 collate,用 SIMD(`std::simd` 或 `wide` crate)一次处理 4-8 条 event,duration 计算用 SIMD 减法 + 累加。Tracy 在 collation hot loop 用 AVX2 优化。Rust 的 SIMD 还在稳定化中(unstable `std::simd`),但 `wide` crate 提供稳定的 wrapper。

**Rust 的 `Bytes` / `Arc<[u8]>`** 让 event buffer 零拷贝共享。如果 event buffer 要被 UI thread 读取(同时被游戏 thread 写),用 `Bytes` 引用计数——读 thread 拷贝 Arc,写 thread 替换 Arc 指向新 buffer。这是 lock-free 数据交换的标准模式。

**Rust profiler 的内存安全优势**。C/C++ profiler 大量 ring buffer + 原子操作,容易写错(数据竞争、use-after-free)。Rust 的 borrow checker + Send/Sync + atomic API 让这些错误编译时被捕获。Puffin / measureme 的代码,你可以放心读——Rust 保证内存安全。

## 5 · 对照与变奏

**不同语言的 hot reload 生态**:

| 语言 | hot reload 机制 |
|---|---|
| C/C++ | dlopen-based(Unreal Live Coding) |
| Rust | cdylib + libloading(Casey 风格) |
| Go | pkg/plugin(限制多) |
| Java | JAR 热替换 + ClassLoader |
| C# | IL2CPP 重新编译 |
| Python | importlib.reload |
| JavaScript | HMR(Webpack/Vite) |
| Lisp | 真 hot reload(图像即代码) |

Lisp 是 hot reload 鼻祖——REPL 修改函数定义,运行中的程序立即用新版本。游戏开发圈 Clojure(play-cljc)和 Common Lisp 提供类似体验。

### cargo build vs make / ninja

`cargo build` 内部用 `cargo` 自己的依赖图 + 调 `rustc`。Rust 没用 make / ninja,因为 cargo 自己懂 Rust 语义(crate / feature / edition)。

但**大型项目**可能用 `bazel` / `buck2` 替代 cargo——它们更通用,支持多语言混合构建。Google / Meta 内部用 bazel。

对单语言 Rust 项目,cargo 足够。Casey HH 是纯 Rust(平台层 + 游戏层都是),cargo 一招吃天下。

### 与 watchexec / cargo-watch 的对比

`cargo-watch` 是 cargo 子命令,监听文件变化自动 `cargo run`:

```bash
cargo install cargo-watch
cargo watch -x run
# 改代码自动 build + run
```

但 cargo-watch **重启整个游戏**(进程级别),丢失状态。Casey 的自重编译**只换 cdylib**,状态保留——这是 hot reload vs warm restart 的本质差别。

| 方式 | 状态 | 启动时间 |
|---|---|---|
| Warm restart(cargo-watch) | 丢失 | 几秒 |
| Hot reload(Casey) | 保留 | < 1 秒 |

游戏 dev 优先 hot reload——丢失状态意味着重新走到 bug 现场(可能要几分钟)。

### Lv1 · 概念辨析

**题**:`Command::output()` 和 `Command::spawn() + try_wait()` 的差别?

**参考解答**:
- `output()` — **同步阻塞**,等子进程结束,返回 Output{status, stdout, stderr}
- `spawn()` — 立刻返回 Child,游戏循环不阻塞
- `try_wait()` — 检查 Child 是否结束,**非阻塞**
- `wait()` — 阻塞等待 Child 结束
- 游戏用 spawn + try_wait(异步,不卡帧)
- 一次性脚本用 output(简单)

## 8 · Rust / Arch 落地代码

完整可跑(子进程 + 文件监视):

```rust
// Cargo.toml
// [dependencies]
// notify = "6"

use notify::{Watcher, RecursiveMode};
use std::process::Command;
use std::sync::mpsc::channel;
use std::time::Duration;

fn main() {
    let (tx, rx) = channel();
    let mut watcher = notify::recommended_watcher(move |res: notify::Result<notify::Event>| {
        if let Ok(e) = res {
            tx.send(e).unwrap();
        }
    }).unwrap();
    watcher.watch(std::path::Path::new("src/"), RecursiveMode::Recursive).unwrap();

    println!("watching src/, change a file to trigger build");

    loop {
        match rx.recv_timeout(Duration::from_millis(100)) {
            Ok(event) => {
                println!("file changed: {:?}, triggering build", event.paths);
                let output = Command::new("cargo")
                    .arg("build")
                    .output()
                    .unwrap();
                if output.status.success() {
                    println!("build OK");
                } else {
                    println!("build failed:");
                    print!("{}", String::from_utf8_lossy(&output.stderr));
                }
            }
            Err(_) => {}
        }
    }
}
```

```bash
cargo new --bin self-rebuild
cd self-rebuild
mkdir src
echo 'notify = "6"' >> Cargo.toml
cargo run
# 另一个终端:touch src/foo.rs
# 第一个终端应该触发 build
```

**Arch Linux**:

```bash
# 装 inotify-tools
sudo pacman -S inotify-tools

# 直接用命令行测试
inotifywait -m src/ &
cargo watch -x build

# 看 cargo 子进程
ps auxf | grep cargo
```

**Troubleshooting**:

- watcher 不触发 — 路径错,用绝对路径测试
- event 太多 — 编辑器保存时多次写,用 debounced 模式
- spawn 失败 — PATH 问题,用绝对路径 `/usr/bin/cargo`
