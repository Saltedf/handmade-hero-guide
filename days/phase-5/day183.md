
# Day 183 · 平台层调试事件

> 游戏循环里的事件记下来了,但 Casey 意识到:**平台层**(开窗、消息循环、文件 IO)也有耗时要记。今天把 profiler 扩展到平台层,让 `swap_buffers`、`PeekMessage` 这些操作也有 span。

## 0 · 为什么要有这一天

回顾 Phase 1 的平台 / 游戏分离:

- **平台层**(platform layer):开窗、消息循环、文件 IO、时间——和 OS 紧密耦合的代码
- **游戏层**(game layer):游戏规则、AI、物理、渲染——纯逻辑代码

平台层在主循环外面包了一层:

```
while running {
    platform_poll_events();  // 平台层:读输入
    game_update_and_render(); // 游戏层
    platform_swap_buffers();  // 平台层:flip framebuffer
}
```

Day 181-182 的 profiler 只覆盖了游戏层。但**平台层的 `swap_buffers` 也可能慢**——尤其是 VSync 开了之后,要等下一帧扫描。如果只看游戏层的 span,你会以为"游戏逻辑很快"——但帧率仍然只有 30fps,因为被 swap 拖累。

今天 Casey 让 profiler 也覆盖平台层。这看起来只是"再多加几个 span",但有几个工程难点:

1. **平台层和游戏层是分开编译的**(cdylib 热重载)
2. **事件数据要在两边共享**(全局 ring buffer)
3. **平台层的事件和游戏层的事件要在同一时间轴上**(同一个 rdtsc 时间戳)

心理锚点:看完今天,你能理解"profiler 要覆盖整个进程,不能漏掉任何一段",并能用全局共享状态实现跨编译单元的事件收集。

## 1 · Casey 今天做了什么

Casey 把 profiler 改成"全局事件总线":

1. `DebugState` 从游戏层 static 变成全局可见(在 cdylib 里 export)
2. 平台层调用 `begin_profiler_event("platform_swap")`,直接写到同一个 ring buffer
3. 事件流不区分平台 / 游戏——都是 DebugEvent
4. UI 渲染时按时间戳排序,自然就能看到平台和游戏的交错

## 2 · 心智模型

### 类比:工厂的两条流水线

工厂有两条流水线:**包装线**(平台层)和**装配线**(游戏层)。它们交替工作——包装线交付原料给装配线,装配线交付成品给包装线。

要监控整个工厂的效率,你不能只看装配线。**两边的耗时都要记**,记到同一份日志里,才能看清楚流程瓶颈。

profiler 的事件流就是这样:**一条全局时间轴,所有层的事件都在上面**。

### 2.1 全局共享状态

回顾 Day 181 的设计:thread_local 存 event。但 thread_local 不跨编译单元(平台 / 游戏分开编译时,各自的 thread_local 是独立 TLS slot)。

需要改成**进程全局**:

```rust
use std::sync::Mutex;

pub struct GlobalDebugState {
    pub events: Mutex<Vec<DebugEvent>>,
}

// 在游戏 cdylib 里 export
#[no_mangle]
pub extern "C" fn get_debug_state() -> *mut GlobalDebugState {
    static STATE: Lazy<Box<GlobalDebugState>> = Lazy::new(|| Box::new(GlobalDebugState {
        events: Mutex::new(Vec::new()),
    }));
    &**STATE as *const _ as *mut _
}
```

平台层通过这个函数指针拿到状态,推送事件。

### 2.2 cdylib 的全局变量问题

Rust 的 `static` 在 cdylib 里是**模块级**的,不是进程级。所以:

```rust
// game.so
static GAME_STATE: Lazy<Vec<...>> = ...;
```

和

```rust
// platform.exe
static PLATFORM_STATE: Lazy<Vec<...>> = ...;
```

是**两个独立**的 static,不共享内存。

要让两边共享,有两条路:

1. **平台层分配,游戏层用指针访问**(Casey 的做法)
2. **C 全局变量**(用 `extern "C"` 声明)

Casey 用方法 1:平台层初始化时分配 `Box<GlobalDebugState>`,把指针传给游戏的 `update_and_render(memory, ...)`,游戏通过指针访问。

### 2.3 事件流的合并

```rust
// 平台层
fn platform_loop() {
    let state = get_global_state();
    loop {
        let _s1 = ProfilerSpan::enter_with(state, "platform_pump_events");
        pump_messages();

        let _s2 = ProfilerSpan::enter_with(state, "platform_swap_buffers");
        swap_buffers();

        game_update_and_render(state);  // 把 state 传进去
    }
}

// 游戏层
pub fn game_update_and_render(state: &GlobalDebugState) {
    let _s = ProfilerSpan::enter_with(state, "game_frame");
    update();
    render();
}
```

所有 span 写到同一个 state.events,按 cycle 排序后看完整时间轴。

### 2.4 排序问题

多线程的 rdtsc 时间戳是相对的(各 CPU 核的 TSC 同步但可能有微小偏差)。排序时要注意:

- **同一线程内**:严格有序(stack-based 配对)
- **跨线程**:大致有序,可能有偏差

Casey 的简化:**只排序不同线程的事件**,同线程用 stack 配对。这是工程折衷——精度够用,实现简单。

### 2.5 跨编译单元的 ABI 兼容性

`#[no_mangle] extern "C"` 是 Rust 跨编译单元的关键。但 ABI 兼容不只是函数声明——还有:

1. **结构体布局**:Rust 默认可能重排字段(优化),C 不一定。必须 `#[repr(C)]` 强制 C 布局
2. **枚举大小**:Rust 默认选最小整数,要 `#[repr(C)]` 或 `#[repr(u32)]` 固定
3. **字符串**:`String` 不能跨 ABI,用 `*const c_char`(C 字符串)或 `&'static str` 指针
4. **Option / Result**:不能跨 ABI,用原始指针 + error code
5. **泛型 / trait object**:不能跨 ABI,用 `extern "C"` 函数 + opaque 指针

```rust
// 错误:Rust 默认布局,跨 ABI 不安全
#[no_mangle]
pub extern "C" fn get_state() -> *mut GlobalDebugState { ... }
// GlobalDebugState 字段顺序在 release build 可能变

// 正确:固定 C 布局
#[repr(C)]
pub struct GlobalDebugState {
    pub events: *mut EventBuffer,  // opaque pointer
    pub frame_index: u64,
}

#[no_mangle]
pub extern "C" fn get_state() -> *mut GlobalDebugState { ... }
```

Casey 在 C 里没这些问题(C 默认就是 C ABI),Rust 翻译要加 `#[repr(C)]`。

**为什么 Rust 默认不保证字段顺序?** 编译器可以做"字段重排优化"——比如把两个 u8 放在一个 u16 的位置,节省 padding。Rust 的默认行为允许这种优化,跨 ABI 就坏。

**手推 repr(C) 的字段布局**:

```rust
#[repr(C)]
struct Foo {
    a: u8,    // 偏移 0,padding 1-7
    b: u64,   // 偏移 8(对齐到 8)
    c: u8,    // 偏移 16,padding 17-23
}
// 总大小:24 字节(对齐 8)
```

如果不加 `#[repr(C)]`,Rust 编译器可能重排成:

```rust
struct Foo {
    b: u64,   // 偏移 0(对齐到 8)
    a: u8,    // 偏移 8
    c: u8,    // 偏移 9,padding 10-15
}
// 总大小:16 字节(对齐 8)
```

省了 8 字节,但跨 ABI 时平台层和游戏层布局不同,**字段读到错位数据**。

### 2.5.1 opaque pointer 模式

跨 ABI 最安全的做法:**不暴露结构体内部**,只暴露 opaque 指针 + 操作函数:

```rust
// game.so 里
pub struct GameState { /* 内部字段不暴露 */ }

#[no_mangle]
pub extern "C" fn game_state_new() -> *mut GameState {
    Box::into_raw(Box::new(GameState::new()))
}

#[no_mangle]
pub extern "C" fn game_state_free(s: *mut GameState) {
    unsafe { drop(Box::from_raw(s)); }
}

#[no_mangle]
pub extern "C" fn game_state_update(s: *mut GameState, dt: f32) {
    let s = unsafe { &mut *s };
    s.update(dt);
}
```

平台层只看到 `*mut GameState`(opaque),不能直接访问字段。这是 C++ PIMPL(Pointer to IMPLementation)模式,COM(Windows)的根基,Qt / Chromium 都用。Casey 的 C 代码天然就是这种(无封装),Rust 翻译要用 opaque pointer 显式做。

### 2.5.2 cbindgen 与自动化绑定

手写 opaque pointer + extern "C" 容易出错。**cbindgen** 是 Rust 工具,自动从 Rust 代码生成 C header:

```bash
cargo install cbindgen
cbindgen --crate my_game --output my_game.h
```

它扫描你的 `#[no_mangle] extern "C"` 函数和 `#[repr(C)]` 结构体,生成对应的 C `.h`。这是 Rust → C 方向的标准工具。

反方向(C → Rust)用 **bindgen**:从 C header 生成 Rust binding。

```bash
cargo install bindgen-cli
bindgen platform.h -o src/platform_bindings.rs
```

Casey 在 C 里不担心这个(只有一个语言),Rust 翻译涉及跨语言 FFI。

### 2.6 平台层状态的生命周期

平台层先启动,分配 GlobalDebugState。游戏层 cdylib 通过 `libloading::Library::get` 拿函数指针:

```rust
// 平台层
let lib = libloading::Library::new("target/release/libgame.so")?;
let game_update: libloading::Symbol<extern "C" fn(*mut GlobalDebugState)> =
    unsafe { lib.get(b"game_update_and_render")? }?;

let state = Box::into_raw(Box::new(GlobalDebugState::new()));
loop {
    game_update(state);  // 把 state 传给游戏层
}
// 退出时
unsafe { drop(Box::from_raw(state)); }
```

**关键**:state 由平台层 `Box::into_raw` 分配,游戏层只持有 `*mut`。这样**热重载 game.so 时,state 不丢**——它在平台层的堆上,game.so 重新加载只是替换函数实现。

### 2.7 事件溢出的处理

每帧 1000-10000 个 span,如果 ring buffer 容量 100 万,撑 100-1000 帧。怎么处理溢出?

- **Casey 的做法**:容量选大(2^20),允许 wrap-around 覆盖老的
- **替代方案**:落盘到文件,用 perfetto / chrome trace viewer 看
- **错误处理**:记一条 special event "buffer overflow",后续 UI 标红

```rust
fn push(e: DebugEvent) {
    if self.head == self.tail.wrapping_sub(1) {
        // 满了,记 overflow
        self.events[self.head] = DebugEvent::overflow();
        // 不推进 head,丢弃新 event
        return;
    }
    self.events[self.head] = e;
    self.head = self.head.wrapping_add(1);
}
```

`wrapping_add/sub` 处理 usize 边界,不 panic。

### 2.8 平台层 span 的优先级

哪些平台层操作值得 span?

**必记**(每帧都跑,影响大):
- `swap_buffers`(可能等 VSync,几毫秒)
- `pump_events`(读输入,但消息多时慢)
- `opengl_clear`(GPU 等待)

**选记**(偶尔):
- `load_texture`(资产加载,可能阻塞主线程)
- `audio_callback`(音频欠载会爆音)

**不记**(没必要):
- `get_time`(几纳秒,profiler 自己开销都更多)
- `set_cursor_pos`(一次几纳秒)

Casey 的标准:**预期耗时 > 100 cycle 的操作必记**。这是 profiler 的"信号阈值"——低于这个值的 noise 反而干扰分析。

### 2.9 VSync 的诡异行为

`swap_buffers` 在 VSync 开启时,会**阻塞**到下一个 VSync(60Hz = 16.67ms)。如果游戏渲染只花 5ms,swap 还要等 11ms。这种"等"在 profiler 里显示为 11ms 的 swap_buffers,但**实际 GPU 早完工了**。

工业级 profiler 区分:
- **CPU wait**(swap 等 VSync)— CPU 空闲
- **GPU work**(实际渲染)— GPU 繁忙

GPU work 用 GL_TIME_ELAPSED query 测(Day 178 提过)。Casey day 235+ 切到 OpenGL 后才用。

### 3.1 · 🐧 Linux 系统编程视角

Linux 上跨编译单元的全局状态:

```bash
# 看 ELF 的 .bss 段(全局 static 在这里)
readelf -SW target/release/my_game | grep -E "\.bss|\.data"

# 看 symbol 导出
nm -D target/release/libgame.so | grep debug_state
# 输出:0000000000012345 T get_debug_state
# T = 在 .text 段(global)
# t = 在 .text 段(local,不导出)
```

跨 DSO(dynamic shared object)的全局变量很微妙:

- 每个进程有一份 ELF 地址空间
- 同一进程内的多个 .so 共享内存
- 但同一 .so 的 static 在 dlopen 多次时是各自的(罕见)

Casey 的"平台层分配"方案绕开这些问题——只有一份 state,所有代码访问它。

### 3.2 · 🦀 Rust 生态视角

Rust 的 `Lazy<T>` / `OnceLock<T>` 适合"进程级全局":

```rust
use std::sync::OnceLock;

static STATE: OnceLock<Mutex<Vec<DebugEvent>>> = OnceLock::new();

fn get_state() -> &'static Mutex<Vec<DebugEvent>> {
    STATE.get_or_init(|| Mutex::new(Vec::new()))
}
```

**Rust 注释**:
- `OnceLock<T>` — Rust 1.70+ 稳定的"初始化一次的全局"
- `get_or_init` — 第一次调用时调闭包,后续直接返回
- 返回 `&'static` — 生命周期是整个进程

### 3.4 · 🐧 Linux 系统编程视角(dlopen 与符号查找)

Linux 上 dlopen 一个 .so 后,通过 dlsym 找符号:

```c
void* handle = dlopen("./libgame.so", RTLD_NOW);
typedef void (*update_fn)(GlobalDebugState*);
update_fn game_update = (update_fn)dlsym(handle, "game_update_and_render");
```

`RTLD_NOW` 表示立即解析所有符号(慢但启动后稳)。`RTLD_LAZY` 表示用到时才解析(快但运行时可能 fail)。

**热重载流程**:
1. `dlclose(handle)` 卸载旧 .so
2. 重新编译:`cargo build`
3. `dlopen` 新 .so
4. `dlsym` 重新拿函数指针

```bash
# 看 .so 的导出符号
nm -D target/release/libgame.so | grep game_update
# 输出:0000000000012345 T game_update_and_render

# 看依赖
ldd target/release/libgame.so

# 看是否有未解析符号(运行时报 undefined symbol)
readelf -d target/release/libgame.so | grep NEEDED
```

### 3.5 · 🐧 Linux 系统编程视角(SO 的内存映射)

每个 dlopen 的 .so 在 /proc/[pid]/maps 里有一条记录:

```bash
# 假设游戏 PID 12345
cat /proc/12345/maps | grep libgame
# 输出:
# 7f1234560000-7f1234580000 r-xp 00000000 ... libgame.so  (代码段 .text)
# 7f1234580000-7f1234581000 r--p 00020000 ... libgame.so  (只读数据 .rodata)
# 7f1234581000-7f1234582000 rw-p 00021000 ... libgame.so  (全局可写 .data/.bss)
```

热重载时,旧的 .so 内存 unmap,新的 mmap。**全局 static 变量在 .bss 段,unmap 时丢失**——这就是为什么 Casey 把 state 放在平台层(平台层不重载)。

## 5 · 对照与变奏

**跨编译单元共享状态的不同语言**:

| 语言 | 机制 |
|---|---|
| Rust cdylib | `#[no_mangle] extern "C"` |

### 与 dlopen-based 热重载系统的对比

LLVM、Unreal Engine 4 的 Live Coding、Tic-80 的 hot reload 都是 dlopen-based:

- **LLVM**:JIT 引擎里 dlopen 已编译的 .so

- **Tic-80**:游戏脚本热重载(prote 协议)

Casey 的 HH 热重载是同一类——但**手工控制**(平台层代码写,不是 UE4 的自动)。状态保留靠"平台层分配"模式。

- **hot-lib-reloader` crate**:提供通用的 dlopen 热重载框架

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 cdylib 的 `static` 不能跨编译单元共享?具体是什么机制阻止了它?

**参考解答**:
- Rust 的 `static` 在编译时分配在 .data / .bss 段
- cdylib 是独立 DSO,有自己的 .data / .bss
- 平台层 .exe 加载 game.so 时,game.so 的 .bss 是它自己的
- 平台层访问 game.so 的 static 要通过 dlsym 函数(查符号地址)
- 所以 `static GAME_STATE` 在 game.so 里是私有的,平台层不能直接看到名字
- 要导出必须 `#[no_mangle] pub extern "C" fn get_state() -> ...`

### Lv2 · 动手实践

**题**:模拟"平台层 + 游戏层"共享状态:
- 写 `platform.rs` 和 `game.rs` 两个文件
- 用 `OnceLock<Mutex<Vec<Event>>>` 共享
- 各自 push 100 条 event
- 最后打印所有 event,验证顺序

**参考解答**:

```rust
use std::sync::{Mutex, OnceLock};

#[derive(Clone, Copy, Debug)]
struct Event { source: &'static str, cycle: u64 }

fn state() -> &'static Mutex<Vec<Event>> {
    static S: OnceLock<Mutex<Vec<Event>>> = OnceLock::new();
    S.get_or_init(|| Mutex::new(Vec::new()))
}

fn platform_work() {
    let _g = state().lock().unwrap();
    _g.push(Event { source: "platform", cycle: 100 });
    _g.push(Event { source: "platform", cycle: 200 });
}

fn game_work() {
    let _g = state().lock().unwrap();
    _g.push(Event { source: "game", cycle: 150 });
}

fn main() {
    platform_work();
    game_work();

    let g = state().lock().unwrap();
    for e in g.iter() {
        println!("{:?}", e);
    }
}
```

### Lv3 · 迁移设计

**题**:如果游戏层是 cdylib(热重载),state 应该存在哪里才能在重编译游戏后保留?**提示**:平台层分配,传指针给游戏。

**额外提示**:
- 平台层用 `Box::into_raw(Box::new(State::new()))` 分配,得到 `*mut State`
- 把指针传给游戏层函数:`game_update(state_ptr: *mut State)`
- 游戏层用 `unsafe { &mut *state_ptr }` 转回引用
- dlclose 旧 .so 时,state 不丢(它在平台层堆上)
- 退出时平台层用 `unsafe { Box::from_raw(state_ptr) }` 回收
- **避坑**:不能用全局 `static` 在游戏层——dlclose 时 .bss 段一起没了

完整可跑(模拟 cdylib + 平台层共享):

```rust
// Cargo.toml: 纯 std
use std::sync::{Mutex, OnceLock};
use std::hint::black_box;

#[derive(Clone, Copy, Debug)]
struct Event { source: &'static str, name: &'static str, cycle: u64 }

static STATE: OnceLock<Mutex<Vec<Event>>> = OnceLock::new();

fn state() -> &'static Mutex<Vec<Event>> {
    STATE.get_or_init(|| Mutex::new(Vec::new()))
}

fn push(source: &'static str, name: &'static str, cycle: u64) {
    state().lock().unwrap().push(Event { source, name, cycle });
}

fn platform_pump() {
    push("platform", "platform_pump_events", 100);
    push("platform", "platform_pump_events_end", 110);
}

fn platform_swap() {
    push("platform", "platform_swap", 5000);
    push("platform", "platform_swap_end", 6800);
}

fn game_update_and_render() {
    push("game", "game_frame", 200);
    push("game", "update", 210);
    push("game", "update_end", 1500);
    push("game", "render", 1510);
    push("game", "render_end", 4800);
    push("game", "game_frame_end", 4810);
}

fn main() {
    // 模拟 3 帧
    for _ in 0..3 {
        platform_pump();
        game_update_and_render();
        platform_swap();
    }

    let g = state().lock().unwrap();
    println!("total events: {}", g.len());
    for e in g.iter() {
        println!("  cycle={:5} [{}] {}", e.cycle, e.source, e.name);
    }

    // 按 cycle 排序看时间轴
    let mut sorted: Vec<Event> = g.iter().cloned().collect();
    sorted.sort_by_key(|e| e.cycle);
    println!("\n--- sorted timeline ---");
    for e in &sorted {
        println!("  cycle={:5} [{}] {}", e.cycle, e.source, e.name);
    }
}
```

**Troubleshooting**:

- Mutex 死锁 — 不要在一个函数里 lock 两次。lock guard 生命周期要短
- OnceLock 未初始化 — 第一次调用 `state()` 自动 init
- **跨 cdylib 时 symbol 找不到** — 用 `nm -D libgame.so | grep 函数名` 验证导出。`#[no_mangle]` 漏写最常见
- **结构体在平台 / 游戏层布局不一致** — 必须 `#[repr(C)]`,否则字段顺序可能不同
- **热重载后指针失效** — state 必须在平台层(不重载)分配,否则 game.so dlclose 后指针悬空
