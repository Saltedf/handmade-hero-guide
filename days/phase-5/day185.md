# Day 185 · 完成基础调试整理

> Day 184 把配对和聚合做完了,今天 Casey 收尾:加 frame_index 隔离、加 ring buffer 历史存储、清理数据结构。一个能用的 profiler 后端就完成了——明天开始做 UI。

## 0 · 为什么要有这一天

Day 184 把配对和聚合做完了——给定一段 event 流,我们能算出每个 span 的耗时和统计。但 Casey 把这个原型真正接进游戏时,发现三个让人头疼的问题,任何一个不解决都不能算"完成"。

**问题一:跨帧污染**。你的游戏跑了一个小时,profiler 累积了 216000 帧的 event 流(60 fps × 3600 秒)。你 `cargo run` 调用 `collate(&all_events)`——等等,这不对。collation 用栈配对,假设所有 begin/end 在同一段连续时间里。但你的 event 流跨帧:`update_frame` 的 begin 在帧 100,它的 end 在帧 101(中间隔了一个 frame boundary marker)。栈配对会把"上一帧没结束的 begin"配到"这一帧的 end",算出一个"百万 cycle"的假数据。这不是 collation 的 bug,是输入的问题——你需要先**切分**再 collate。

**问题二:看不到过去**。profiler 在跑,但 UI 想显示"过去 5 秒的趋势",你能拿到什么?Day 184 给的只有当前帧的 SpanStats。过去帧的数据被 drop 了——collate 一帧,展示一帧,下一帧就覆盖了。要解决这个,需要把每帧的 FrameSummary **存起来**,存多少?太多内存爆,太少看不远。Casey 用 Day 179 那个 ring buffer 存最近 300 帧(5 秒 @ 60fps)。旧的覆盖,内存恒定。

**问题三:API 不友好**。Day 184 的接口要调用方手动 `push_event(Begin)` / `push_event(End)`,容易漏 end(函数提前 return 时忘了)。今天 Casey 加一个 RAII guard——`Profiler::enter(name)` 返回一个 guard,drop 时自动 push end event。这样无论函数怎么退出(正常 return / 早 return / panic),end 都会被记录。

解决完这三件事,profiler 后端**定型**:

- API:`Profiler::enter(name)` 返回 guard,drop 时记 event
- 内部:event 流 + collation + ring buffer + frame marker
- 输出:`RingBuffer<FrameSummary, 300>`,UI 直接读

**学完今天,你应该能**:
- 解释为什么 frame marker 必须先切分 event 流,再 collation
- 设计 RAII guard API,保证 begin/end 永远配对(漏 end 的常见 bug 自动消失)
- 用 Rc<RefCell<>> 或 thread_local 处理单线程共享可变状态
- 写 property-based 测试验证 collation 的不变式(总耗时 = 各 span 耗时之和)
- 把 FrameSummary 推进 ring buffer,实现"过去 N 帧历史"的内存恒定存储

## 2 · 心智模型

### 类比:博物馆的展览整理

博物馆每天收一批新藏品(event 流),整理过程:

1. **按日切分**(frame marker)— 周一收的归周一,周二归周二
2. **分类归档**(collation)— 同类的放一起(同 GUID 的 spans)
3. **写日总结**(aggregate)— 周一瓷器 5 件、青铜 3 件
4. **存入档案室**(ring buffer)— 最近 30 天的总结,旧的扔

profiler 一模一样:按帧切分、按 GUID 聚合、写到 ring buffer。

### 2.1 Frame Marker

```rust
const MARKER_FRAME_BEGIN: u64 = 0xFFFF_FFFF_FFFF_FF00;
const MARKER_FRAME_END: u64 = 0xFFFF_FFFF_FFFF_FF01;

pub fn frame_begin(frame_index: u64) {
    push_event(Event {
        cycle: rdtsc(),
        guid: MARKER_FRAME_BEGIN,
        kind: Kind::Begin,
        payload: frame_index,
    });
}

pub fn frame_end(frame_index: u64) {
    push_event(Event {
        cycle: rdtsc(),
        guid: MARKER_FRAME_END,
        kind: Kind::End,
        payload: frame_index,
    });
}
```

每帧主循环开头 / 结尾调一次。

**注意 marker GUID**:Casey 用接近 u64::MAX 的"保留区"做 marker,避免和普通 span GUID 冲突。FNV-1a hash 不会产生这种高位的值。

### 2.2 按 marker 切分

```rust
pub fn collate_per_frame(events: &[Event]) -> Vec<Vec<Event>> {
    let mut frames = Vec::new();
    let mut current = Vec::new();
    for e in events {
        if e.guid == MARKER_FRAME_BEGIN {
            current = Vec::new();
            current.push(e.clone());
        } else if e.guid == MARKER_FRAME_END {
            current.push(e.clone());
            frames.push(std::mem::take(&mut current));
        } else {
            current.push(e.clone());
        }
    }
    frames
}
```

然后对每段调 `collate` + `aggregate`,得到一个 FrameSummary。

**优化**:`e.clone()` 对 Copy 类型是廉价,但可以更精简——直接传 slice:`events.iter().skip(begin_idx).take(end_idx - begin_idx)`。Casey 的 C 版本用指针 + length,Rust 用 iterator 更自然。

### 2.3 FrameSummary 结构


### 2.4 完整 collation pipeline

```rust
pub fn process_frame(events: &[Event]) -> Option<FrameSummary> {
    // 切分(假设 events 已经按 cycle 排序)
    let frame_events: Vec<&Event> = events.iter().collect();
    if frame_events.is_empty() { return None; }

    let begin = frame_events.first()?.cycle;
    let end = frame_events.last()?.cycle;

    // collate spans
    let spans = collate(&frame_events);

    // aggregate
    let stats = aggregate(&spans);

    Some(FrameSummary {
        frame_index: 0,  // 由调用方填
        begin_cycle: begin,
        end_cycle: end,
        total_cycles: end - begin,
        stats,
    })
}
```

### 2.5 Profiler API 封装与 RAII guard

Day 184 的接口是裸的 `push_event`——调用方手动 push begin/end。这有个经典 bug:函数里有多个 return 路径,某个 return 漏 push end,栈配对就错了。比如:

```rust
fn update_player(state: &mut State) {
    push_event(begin("update_player"));

    if state.dead { return; }  // BUG! 漏 push end

    state.pos += state.vel;
    push_event(end("update_player"));
}
```

Rust 的解决方案是 **RAII guard**——一个结构体,创建时 push begin,drop 时 push end。无论函数怎么退出,编译器保证 drop 调用。

```rust
pub struct ProfileSpan {
    state: Rc<RefCell<ProfilerState>>,
    guid: u64,
    begin_cycle: u64,
}

impl ProfileSpan {
    fn enter(name: &'static str, state: &Rc<RefCell<ProfilerState>>) -> Self {
        let guid = hash(name);
        let cycle = rdtsc();
        let s = state.borrow_mut();
        push_internal(s, Event { cycle, guid, kind: Kind::Begin, payload: 0 });
        Self {
            state: state.clone(),
            guid,
            begin_cycle: cycle,
        }
    }
}

impl Drop for ProfileSpan {
    fn drop(&mut self) {
        let cycle = rdtsc();
        let mut s = self.state.borrow_mut();
        push_internal(&mut s, Event { cycle, guid: self.guid, kind: Kind::End, payload: 0 });
    }
}
```

调用方现在写:

```rust
fn update_player(state: &mut State, profiler: &Profiler) {
    let _span = profiler.enter("update_player");  // 自动 push begin
                                                    // _span drop 时自动 push end

    if state.dead { return; }  // OK!Drop 仍会调用

    state.pos += state.vel;
    // 函数结束,_span drop,end event 被 push
}
```

`_span` 的下划线前缀告诉编译器"我知道这个变量没被读,但我要它的 drop 副作用"。如果写成 `_` 通配符(无绑定),drop 会**立即发生**,起不到 guard 作用——这是常见坑。

**为什么 guard 持有 Rc clone 而不是引用**?因为 guard 的 lifetime 可能比 `&Profiler` 长(虽然实际上不会,但 Rust 的 lifetime 分析无法证明)。持有 Rc clone 让 guard 自洽——它持有的引用计数保证 state 不被释放,即使 Profiler 离开作用域。这是 interior mutability pattern 的核心。

```rust
pub struct Profiler {
    state: Rc<RefCell<ProfilerState>>,
}

struct ProfilerState {
    events: Vec<Event>,
    frames: RingBuffer<FrameSummary, 300>,
    current_frame_index: u64,
}
```

**为什么用 Rc<RefCell<>> 而不是全局 static?** 全局 static 简单但有几个问题:

1. 多实例没法测试(全局 state 污染单测,测 A 影响 B)。
2. 初始化顺序复杂(`Lazy` / `OnceLock` 都各有 trade-off,初始化 panic 难恢复)。
3. 不能在测试中替换 mock(全局 static 是 fixed impl,不能 stub)。

`Rc<RefCell<>>` 让 profiler 成为"对象"——可以创建多个,可以传引用,可以测试。

**为什么不用 trait object**?profiler 内部不需要多态(只有一个实现)。trait object 加 vtable overhead,profiler 这种 hot path 不需要。Generics 也可以,但会污染调用方代码(每个调用方都要泛型参数)。

Casey 在 C 里就是全局 static,简单但难测试。Rust 翻译版用 Rc 更"Rust 风格"。

```rust
impl Profiler {
    pub fn new() -> Self {
        Self {
            state: Rc::new(RefCell::new(ProfilerState {
                events: Vec::new(),
                frames: RingBuffer::new(),
                current_frame_index: 0,
            })),
        }
    }

    pub fn enter(&self, name: &'static str) -> ProfileSpan {
        ProfileSpan::enter(name, &self.state)
    }

    pub fn begin_frame(&self) {
        let mut s = self.state.borrow_mut();
        push_internal(&mut s, frame_begin_event(s.current_frame_index));
    }

    pub fn end_frame(&self) {
        let mut s = self.state.borrow_mut();
        push_internal(&mut s, frame_end_event(s.current_frame_index));

        // collate 本帧
        // std::mem::take 把 Vec 取空,返回原 Vec(O(1)),避免 clone
        let events = std::mem::take(&mut s.events);
        if let Some(mut summary) = process_frame(&events) {
            summary.frame_index = s.current_frame_index;
            s.frames.push(summary);
        }

        s.current_frame_index += 1;
    }
}
```

**Rust 注释**:
- `Rc<RefCell<...>>` — 单线程"内部可变性"。多线程要 `Arc<Mutex<>>`。
- `borrow_mut()` — 运行时借用检查。如果当前已经 borrowed,panic。这是 hot path,要小心避免冲突。
- `std::mem::take(&mut vec)` — 把 Vec 取空,返回原 Vec(O(1))。等价于 `let old = std::mem::replace(&mut vec, Vec::new())`,但更短。

### 2.6 Rc<RefCell<>> 的 ownership 图

`Rc<RefCell<ProfilerState>>` 在内存里:

```
stack frame                heap
+------------+             +-------------------+
| Profiler { | --Rc-----> | RefCell {         |
|   state    |             |   borrow: None,   |
| }          |             |   value: ProfilerState { ... }
+------------+             | }                 |
                           +-------------------+
                                ^
                                | (Rc clone)
                           +----+----+
                           | span    |
                           | guard   |
                           +---------+
```

`Rc` 是引用计数(单线程),允许多个 owner。`RefCell` 提供 `borrow_mut`——运行时检查"现在能不能 mut"。Span guard 持有 Rc clone,所以即便 profiler 离开作用域,guard 还能用。

**Arc<Mutex<>>** 是多线程版:`Arc` = atomic Rc,`Mutex` = lock-based RefCell。多线程时换成这个。

### 2.7 测试 collation 的正确性

profiler 数据正确性怎么验证?**单元测试 + property-based testing**:

```rust

mod tests {

    #[test]
    fn test_simple_pair() {
        let events = vec![
            Event { cycle: 100, guid: 1, kind: Kind::Begin, payload: 0 },
            Event { cycle: 200, guid: 1, kind: Kind::End, payload: 0 },

    fn test_nested() {

            Event { cycle: 0, guid: 1, kind: Kind::Begin, payload: 0 },
            Event { cycle: 100, guid: 2, kind: Kind::Begin, payload: 0 },
            Event { cycle: 200, guid: 2, kind: Kind::End, payload: 0 },
            Event { cycle: 300, guid: 1, kind: Kind::End, payload: 0 },
        ];
        let summary = collate_and_aggregate(&events);
        assert_eq!(summary.stats.get(&1).unwrap().total_cycles, 300);
        assert_eq!(summary.stats.get(&2).unwrap().total_cycles, 100);
    }

    #[test]
    fn test_unmatched() {
        let events = vec![
            Event { cycle: 0, guid: 1, kind: Kind::Begin, payload: 0 },
            // 没有 end
        ];
        let summary = collate_and_aggregate(&events);
        assert!(summary.stats.get(&1).is_none());  // 没配对成功

}
```

### 3.1 · 游戏编程视角

帧隔离的重要性:

- 没切分:`begin update_frame`(帧 100)+ `end update_frame`(帧 101)→ 配对错,算出"百万 cycle"的假数据
- 切分后:每帧独立,不会混淆

商业引擎的 frame marker:
- Unreal:`TRACE_BOOKMARK("FrameEnd")`
- Unity:`Profiler.EndSample` after frame
- Casey:`MARKER_FRAME_END`

### 3.2 · Rust 生态视角

Rust 的"内部可变性"模式:

| 类型 | 单/多线程 | 借用检查 |
|---|---|---|
| `&mut T` | 任意 | 编译期 |
| `Cell<T>` | 单线程 | 编译期(运行时无开销,Copy only) |
| `RefCell<T>` | 单线程 | 运行时 |
| `Mutex<T>` | 多线程 | 运行时 + lock |
| `RwLock<T>` | 多线程 | 运行时 + 读/写锁 |
| `AtomicU32` 等 | 多线程 | 硬件原子 |

profiler 单线程版用 RefCell,跨线程切 Arc<Mutex> 或 thread_local。

### 3.3 · Linux 系统编程视角

Linux perf 的 frame marker 用 `perf_event_open` + `PERF_RECORD_LOST` / `PERF_RECORD_THROTTLE` 等。Casey 自己用 `MARKER_*` GUID 简化。

## 5 · 对照与变奏

** profiler 状态的不同 ownership 模式**:

| 模式 | 适合 |
|---|---|
| 全局 static | 简单,线程不安全 |
| Rc<RefCell> | 单线程,共享 |
| Arc<Mutex> | 多线程,简单 |
| thread_local | 多线程,每线程独立 |
| 传引用 | 显式,但侵入式 |

Casey 在 day 183 用"平台层分配 + 指针",等价"传引用"。

### 与 Unreal Insights / Tracy 的 frame marker 对比

工业级 profiler 的 frame marker 各有特色:

- **Unreal Insights**:`TRACE_BOOKMARK("Frame", frame_number)` — 字符串名 + payload,灵活
- **Tracy**:`TracyCFrameMark` — C API,自动用调用位置
- **Chrome Trace**:`Tracing.started("Frame")` + `Tracing.complete("Frame")` — 显式 begin/end
- **Casey**:`MARKER_FRAME_BEGIN/END` — 自定义 GUID,极简

Casey 的设计**最简单**,但限制是只有一个 frame 概念。如果想加"logic frame" / "render frame"两个层级,要扩展 marker 类型。

### Rc<RefCell<>> vs Arc<Mutex<>> 的取舍

Rust 的"内部可变性"有两套:

| 维度 | Rc<RefCell<>> | Arc<Mutex<>> |
|---|---|---|
| 线程 | 单 | 多 |
| 性能 | ~5 ns/access | ~50 ns/access(锁) |
| 死锁风险 | 无(运行时 panic) | 有 |
| 内存 | 引用计数非原子 | 引用计数原子 |

**profiler 单线程版**用 Rc<RefCell<>>,**多线程版**切 Arc<Mutex<>>。Casey 的游戏主线程单线程跑 profiler,工作线程用 thread_local——避免 Arc<Mutex<>> 的开销。

### Lv1 · 概念辨析

**题**:为什么要在 collation 前按 frame marker 切分,而不是直接配对所有 event?

**参考解答**:
- 直接配对会"跨帧"配:帧 100 的 begin 配到帧 101 的 end,数据错
- collation 假设输入是"一段连续时间"内的 event
- 切分保证每段是"一帧内的事件"
- 性能上,切分是 O(N),不增加额外开销

### Lv2 · 动手实践

**题**:基于 day 184 的代码,加:
1. frame marker
2. FrameSummary 结构
3. process_frame pipeline
4. main 里跑 5 帧,每帧有 3 个 span,打印每帧 summary

**参考解答**:

```rust
use std::collections::HashMap;

#[derive(Clone, Copy, Debug)]
enum Kind { Begin, End }

#[derive(Clone, Copy, Debug)]
struct Event { cycle: u64, guid: u64, kind: Kind, payload: u64 }

const MARKER_BEGIN: u64 = u64::MAX - 1;
const MARKER_END: u64 = u64::MAX - 2;

#[derive(Clone, Debug, Default)]
struct SpanStats { count: u32, total_cycles: u64 }

#[derive(Clone, Debug, Default)]
struct FrameSummary {
    frame_index: u64,
    total_cycles: u64,
    stats: HashMap<u64, SpanStats>,
}

fn collate_and_aggregate(events: &[Event]) -> FrameSummary {
    let mut stack: Vec<(u64, u64)> = Vec::new();
    let mut summary = FrameSummary::default();
    let mut frame_cycles = 0u64;

    for e in events {
        match e.kind {
            Kind::Begin => {
                if e.guid == MARKER_BEGIN {
                    summary.frame_index = e.payload;
                    continue;
                }
                stack.push((e.guid, e.cycle));
            }
            Kind::End => {
                if e.guid == MARKER_END {
                    continue;
                }
                if let Some((guid, begin)) = stack.pop() {
                    if guid == e.guid {
                        let dur = e.cycle - begin;
                        let s = summary.stats.entry(guid).or_default();
                        s.count += 1;
                        s.total_cycles += dur;
                        frame_cycles += dur;
                    }
                }
            }
        }
    }
    summary.total_cycles = frame_cycles;
    summary
}

fn main() {
    let mut all_events: Vec<Event> = Vec::new();
    let mut cycle = 1000u64;

    for frame in 0..5 {
        all_events.push(Event { cycle, guid: MARKER_BEGIN, kind: Kind::Begin, payload: frame });
        cycle += 10;

        for span_guid in 1..=3u64 {
            all_events.push(Event { cycle, guid: span_guid, kind: Kind::Begin, payload: 0 });
            cycle += 50 + span_guid * 10;  // 假耗时
            all_events.push(Event { cycle, guid: span_guid, kind: Kind::End, payload: 0 });
            cycle += 5;
        }

        all_events.push(Event { cycle, guid: MARKER_END, kind: Kind::End, payload: frame });
        cycle += 100;
    }

    // 切分 + collate
    let mut current: Vec<Event> = Vec::new();
    let mut summaries = Vec::new();
    for e in &all_events {
        current.push(e.clone());
        if e.guid == MARKER_END {
            summaries.push(collate_and_aggregate(&current));
            current.clear();
        }
    }

    for s in &summaries {
        println!("=== Frame {} (total {} cycles) ===", s.frame_index, s.total_cycles);
        for (guid, st) in &s.stats {
            println!("  guid={}: count={} avg={}", guid, st.count, st.total_cycles / st.count as u64);
        }
    }
}
```

### Lv3 · 迁移设计

**题**:profiler 现在是单线程。如果要支持"工作线程也能 enter span",怎么改?

**设计思路**(先思考再写):
1. **每线程独立 buffer**:每个线程有自己的 `thread_local! { static EVENTS: RefCell<Vec<Event>> }`,enter 时 push 到自己的 buffer,无锁。
2. **主线程 frame_end 时收集**:主线程在 `end_frame` 时,广播"给我你们的 events"给所有工作线程。工作线程把 events 转移(用 `std::mem::take`)给主线程,主线程合并。
3. **合并**:把多个线程的 event 流合并成一个,按 cycle 排序。注意:跨线程的 cycle 必须同步——`rdtsc()` 在多核之间不一定严格单调,要用 `clock_gettime(CLOCK_MONOTONIC)` 或确保 CPU 间 TSC 同步。
4. **collate 时区分线程**:casey 用 `thread_id` 字段,配对在 thread_id 内做。否则跨线程的 begin/end 会被错误配对。

**参考骨架**:

```rust
thread_local! {
    static THREAD_EVENTS: RefCell<Vec<Event>> = RefCell::new(Vec::new());
}

fn enter_span(name: &'static str) -> SpanGuard {
    let guid = hash(name);
    THREAD_EVENTS.with(|evs| {
        evs.borrow_mut().push(Event {
            cycle: rdtsc(),
            guid,
            kind: Kind::Begin,
            thread_id: thread::current().id(),
            payload: 0,
        });
    });
    SpanGuard { guid }
}

impl Drop for SpanGuard {
    fn drop(&mut self) {
        THREAD_EVENTS.with(|evs| {
            evs.borrow_mut().push(Event {
                cycle: rdtsc(),
                guid: self.guid,
                kind: Kind::End,
                thread_id: thread::current().id(),
                payload: 0,
            });
        });
    }
}

// 主线程在 end_frame 时:
fn end_frame(all_thread_handles: &[JoinHandle<()>]) {
    // 1. 等工作线程 idle(用 barrier / condvar)
    // 2. 收集 events(用 channel 或 shared mutex)
    // 3. 合并、按 cycle 排序
    // 4. collate(每个 thread_id 内独立配对)
}
```

**注意**:跨线程 profiler 是真实工程,有很多坑。Casey 在 HH 里只用单线程 profiler,但工业级(Tracy、puffin)都做了多线程支持。**简单版本**:所有 enter/end 只在主线程,工作线程用 channel 把"我做的事"发给主线程,主线程代为记录。

### 8.3 Troubleshooting

- **frame_index 都是 0** — 检查 marker event 的 payload 字段是否正确传递。Day 183 Event 结构里 payload 字段是否被 enter/end 路径覆盖。
- **ring buffer 没填** — frame_end 是否真的被调用。常见 bug:游戏主循环里只有 `begin_frame`,某个 return 路径漏 `end_frame`。
- **RefCell panic: already mutably borrowed** — 在 borrow 期间又 borrow,通常是因为 span guard 跨函数边界传递不当。检查 span guard 的 lifetime。debug build 触发 panic,release 也 panic(RefCell 的 borrow check 是 runtime 的,不分 build mode)。
- **summary.stats 漏数据** — 配对失败的 span 不会进 stats。检查 WARN mismatched 日志。
- **跨线程 Rc 错误** — `Rc` 不能跨线程(`Rc` 不是 `Sync`),改成 `Arc`;或者用 thread_local 让每线程独立 profiler。
- **Drop 时 borrow_mut panic** — guard 在 end_frame borrow_mut 期间被 drop,Drop 又 borrow_mut,冲突。解决:guard 持有的不是 RefCell 的借用,而是 Rc clone,drop 时再 borrow_mut。这样 end_frame 的 borrow 已经结束,guard 的 borrow 可以开始。

### 8.5 期望输出与解读

跑 Lv2 的 main,期望输出:

```
=== Frame 0 (total 165 cycles) ===
  guid=1: count=1 avg=165
  guid=2: count=1 avg=220
  guid=3: count=1 avg=275
=== Frame 1 (total 165 cycles) ===
  ...
```

每帧的 total_cycles 应该一致(因为假数据稳定),实际游戏中每帧不同——这就是 spike 和趋势的来源。

**怎么解读输出**:
- `count=1` 说明这个 GUID 在这帧被调用了一次。如果 count=100,说明被嵌套循环调了 100 次。
- `avg=165` 是 `total_cycles / count`,代表单次调用的平均耗时。
- 如果某帧 guid=3 的 avg 突然飙到 5000(其他帧是 275),那是 spike——可能是 IO、page fault、cache miss。
- trend 跨帧看:`cargo run | grep "guid=3" | awk '{print $4}'` 取 avg 列,看是否有上升趋势(可能是内存泄漏导致的逐渐变慢)。
