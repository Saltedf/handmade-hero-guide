
# Day 220 · 在层级中显示数据块

> 之前的层级树只显示简单变量(`physics/gravity = 9.8`)。但有些调试数据是"数据块"——例如一段 entity 数组、一个 struct、一段二进制 buffer。今天 casey 让层级树能展开任意数据块,显示其内部字段。

## 0 · 为什么要有这一天

debug 变量类型多样:

- **Scalar**:`gravity = 9.8`(单个 f32)
- **Vector**:`player_pos = (10, 20)`(2-3 个 f32)
- **String**:`npc_state = "patrol"`
- **Struct**:`player = { pos, hp, mana, ... }`(多个字段)
- **Array**:`enemies = [enemy1, enemy2, ...]`(多个元素)

前 3 类已经支持。今天加后 2 类:**struct 字段展开** + **array 元素列出**。

**casey 的方案**:用 introspection(Day 206)拿到 struct 的字段元数据,渲染时根据元数据展开。数组用长度 + 索引访问。

UI 上看到:

```
player/
  pos/
    x = 100.0
    y = 200.0
  hp = 75.0
  max_hp = 100.0
enemies/
  [0]/
    pos = (50, 60)
    hp = 30
  [1]/
    pos = (80, 90)
    hp = 20
```

每点击 struct / array,展开下一层。

心理锚点:看完今天,你的 debug hierarchy 应该和 Chrome DevTools 的 Object inspector 一样灵活——任意嵌套。

## 2 · 心智模型

### 类比:Chrome DevTools 的 Object panel

打开 DevTools,console 输入 `window`,你看到树:

```
window
├── document: Document
├── location: Location
├── navigator: Navigator
├── ...
```

点击 `document` 展开,又一层树。任意嵌套,任意类型。

casey 的 debug hierarchy 就是这个思想的"游戏机版本"。

这个类比还可以再深:DevTools 之所以能做到任意嵌套展开,是因为 JavaScript 本身就是动态类型——每个对象运行时知道自己的属性列表。Rust / C++ 这种静态类型语言没有内省,必须额外维护元数据(casey 的 introspect 系统)。这是动态类型和静态类型的本质权衡——动态灵活但慢,静态快但需要额外工程做内省。

类比也能引出**按需展开**的工程必要性:DevTools 不会一打开就把 `window` 全展开(几千属性,每属性又是嵌套对象,可能爆栈)。它只展开到当前可见层级,用户点击才递归展开。casey 的 debug hierarchy 完全对应——大 struct 不一次性画完,按用户点击逐层展开。

最后:**DevTools 的 expanded state 在刷新页面后丢失**,而 casey 的 debug hierarchy 通过 GUID 在 hot-reload 后保留展开状态。这是游戏开发的优势——长 session 调试不丢失 UI 状态。

### 2.1 DataBlock enum

```rust
enum DataBlock {
    Scalar(DebugValue),
    Struct { fields: Vec<(String, DataBlock)> },
    Array { elements: Vec<DataBlock> },
}
```

或者用动态查找更高效:

```rust
enum DataBlock {
    Scalar(DebugValue),
    Struct { type_id: TypeId, fields: FieldList },  // lazy
    Array { element_type: TypeId, len: usize, get: fn(usize) -> DataBlock },
}
```

casey 用前者(简单),工业级实现用后者(惰性,大 array 不一次性展开)。

### 2.5 第一性原理推导:为什么 introspection 是必需的

从第一性原理推导为什么静态类型语言必须有 introspection 系统。

**前提**:程序运行时,数据在内存里是字节流。比如 `Player { pos: Vec2 { x: 1.0, y: 2.0 }, hp: 100.0 }` 在内存里是 `[0x00, 0x00, 0x80, 0x3f, 0x00, 0x00, 0x00, 0x40, 0x00, 0x00, 0xc8, 0x42]`——12 字节连续数据,没有任何"字段名"或"类型"信息。

**问题**:debug UI 想显示这个 Player,需要知道:
- 这块内存是什么类型?
- 有哪些字段?
- 每个字段的偏移、类型?
- 如何递归展开嵌套字段?

**两种解决方案**:

**方案 A:运行时类型信息(RTTI)**。编译器在每个对象旁边存一份"类型描述"。C++ 的 `dynamic_cast` 用这种,Java 的 `getClass()` 也是。优点:零成本使用(信息已存在)。缺点:每个对象多 8-16 字节,内存膨胀。

**方案 B:外部 introspection 系统**。开发者显式注册"这个 struct 有这些字段"。casey 的 introspect system 是这种。优点:按需注册,内存可控。缺点:开发者要写注册代码(macro 帮忙)。

casey 选方案 B。Rust 翻译时用 `bevy_reflect` 这种 derive macro 自动生成注册代码,接近方案 A 的便利。

**为什么动态类型语言不需要 introspection 系统?** JavaScript、Python 的对象本身就是 "字典",属性名和值存在对象里。运行时拿 `Object.keys(obj)` 就有属性列表,天然可遍历。代价:每次属性访问是 hash lookup(~10ns),比 Rust 的编译时 offset(~1ns)慢 10 倍。

**结论**:**introspection 是静态类型语言为"性能"付出的代价**。casey 用 introspection 让 debug UI 接近 JS DevTools 的体验,同时保留 C/Rust 的零成本抽象。

### 2.6 Lazy evaluation 的工程价值

casey 的"按需展开"是 lazy evaluation 的应用。lazy 在工程上的几个收益:

**1. 避免无用工作**:`enemies[10000]` 如果立即展开,要访问 10000 个 enemy struct,每个有几十字段,总访问量 100 万次。99% 不会被用户看到(用户只看前 10 个),纯浪费。lazy 只在用户滚动到时才访问。

**2. 处理无限/极大数据**:程序化生成的内容(噪声地形、AI 行为树)可能"理论上无限"。lazy 让 UI 只渲染可见部分。

**3. 错误隔离**:如果 enemies[5000] 是个坏指针,立即展开会让程序立刻 crash。lazy 只在用户访问 5000 时才 crash,前面 4999 个正常显示。

**4. 内存可控**:立即展开 = 一次性分配大量 DataBlock struct。lazy = 只分配当前可见的 ~50 个,内存稳定。

**代价**:lazy 引入"thunk"(延迟计算),代码复杂度增加。但收益巨大,casey 接受。

**Haskell 是 lazy-first 语言**,所有值默认 thunk。Rust 是 eager-first,casey 手动加 lazy。两种风格都有适用场景。

### 2.2 展开状态

UI 渲染时,每个节点有"展开 / 收起"状态。casey 用 guid 关联:

```rust
struct ExpandedState {
    expanded: HashSet<u64>,  // 哪些 guid 当前展开
}

impl ExpandedState {
    fn toggle(&mut self, guid: u64) {
        if self.expanded.contains(&guid) {
            self.expanded.remove(&guid);
        } else {
            self.expanded.insert(guid);
        }
    }
}
```

注意:guid 在 hot-reload 后稳定,所以展开状态能在 hot-reload 后保留。

### 2.3 惰性展开大数组

`enemies[10000]` 不可能一次性画。casey 加分页:

```rust
fn draw_array(name: &str, array: &DataBlock, state: &mut ExpandedState, page: usize) {
    const PAGE_SIZE: usize = 50;
    let start = page * PAGE_SIZE;
    let end = (start + PAGE_SIZE).min(array.len());
    for i in start..end {
        draw_data_block(&format!("[{}]", i), &array.elements[i], state);
    }
    if end < array.len() {
        ui.button("Next page");
    }
}
```

只画 50 个,翻页加载下一批。

### 2.4 introspection 集成

Day 206 的 introspection 提供:

```rust
struct FieldInfo {
    name: &'static str,
    offset: usize,
    type_id: TypeId,
}

fn introspect(type_id: TypeId) -> &'static [FieldInfo];
```

debug hierarchy 用 introspect 拿到 struct 字段,然后通过 offset 访问实际值:

```rust
fn expand_struct(ptr: *const u8, type_id: TypeId) -> DataBlock {
    let fields = introspect(type_id);
    let expanded_fields: Vec<(String, DataBlock)> = fields.iter().map(|f| {
        let field_ptr = unsafe { ptr.add(f.offset) };
        (f.name.to_string(), read_data_block(field_ptr, f.type_id))
    }).collect();
    DataBlock::Struct { fields: expanded_fields }
}
```

`unsafe` 因为通过 offset 读取原始内存。Rust 视角下,这部分 casey 在 C 里没风险(C 全是 unsafe),翻译到 Rust 要明确 unsafe 边界。

- **rr(Record/Replay)**:可反向调试,任意展开变量

### 3.3 · Rust 生态视角

Rust 表达 introspection:

```rust
// 用 bevy_reflect
use bevy_reflect::Reflect;

#[derive(Reflect)]
struct Player {
    pos: Vec2,
    hp: f32,
}

// 运行时拿到字段列表
let player = Player { pos: Vec2::new(1.0, 2.0), hp: 100.0 };
let reflected: &dyn Reflect = &player;
for field in reflected.iter_fields() {
    println!("{}: {:?}", field.name(), field.value());
}
```

参考 crate:`bevy_reflect`、`serde`（序列化也是一种 introspection）、`interprocess` 等。

### 3.4 · unsafe 边界视角

casey 通过 offset 读取原始内存。Rust 翻译:

```rust
unsafe fn read_field<T>(base: *const u8, offset: usize) -> T {
    let ptr = base.add(offset) as *const T;
    ptr.read()
}
```

这个函数 unsafe 因为:

- `base.add(offset)` 越界 = UB
- `T` 类型不对齐 = UB
- `T` 不是 Copy = double free

Rust 通过 unsafe 边界把责任集中在这一处,其他地方安全。

### 3.5 · 🐧 Linux 系统编程视角(扩展)

Linux 的 introspection 工具谱系极丰富:

**1. /proc/kallsyms**:内核符号表,列出所有内核函数和变量地址。`cat /proc/kallsyms | grep schedule` 可以查内核函数地址。这是内核级的"introspection",开发者用这个写 eBPF probe。

**2. /sys/kernel/debug/**:debugfs,挂载后能看到内核数据结构的"快照"。比如 `cat /sys/kernel/debug/sched/debug` 显示调度器内部状态——所有运行队列、task 调度历史。这是 casey 的 debug hierarchy 的"内核版本"。

**3. BPF / eBPF**:运行时 probe 内核 struct。bpftrace 写 `tracepoint:sched:sched_switch { printf("%s -> %s", args->prev_comm, args->next_comm); }`,内核自动展开 `args` 的字段。eBPF verifier 内部用 kernel introspection 拿到字段 offset。

**4. gdb pretty-printer**:gdb 5.0+ 支持用 Python 脚本定义"如何展开 STL 容器"。比如 `std::vector<int>` 在 gdb 里默认显示成内存 hex,pretty-printer 把它展开成 `[1, 2, 3, ...]`。casey 的 DataBlock 展开完全对应。

**5. systemd-cgls**:递归显示 cgroup 树。`systemd-cgls` 输出像 `system.slice/├── sshd.service/...`,自动展开 cgroup 嵌套。casey 的 draw_node 是同款算法。

**6. pahole**:读 DWARF debug info,显示 struct 的字段布局、对齐、padding。开发者用 pahole 找出 struct 里浪费的 padding 字节。这是 casey introspect 系统的"离线版本"。

casey 的 introspect + DataBlock 是这些工具的最小集合,但思想一致——"程序运行时枚举自身结构"。

### 3.6 · 🎮 游戏工业对照

游戏引擎的内省系统:

**Unreal Engine UProperty + Reflection**:UE 用宏 `UPROPERTY(EditAnywhere)` 标记字段,Unreal Header Tool 在编译时生成 reflection data。运行时 `TFieldIterator<FProperty>` 遍历 struct 字段。Casey 的 introspect 是这个的最简版本。

**Unity MonoBehaviour + SerializeField**:Unity 的 `[SerializeField]` 标记字段,Inspector 自动显示。和 UE 类似但更简陋——Unity 不支持复杂嵌套展开,序列化深度有限制。

**Godot Variant + _get_property_list()**:Godot 用 Variant(动态类型)表达所有值,object 通过 `_get_property_list()` 返回属性列表。这是动态类型风格的 introspection,类似 JavaScript。

**Bevy Reflect**:Rust-native,`#[derive(Reflect)]` 生成 reflection 代码。完全类型安全,无 unsafe。casey 的 introspect 翻译到 Rust 推荐用 Bevy Reflect。

**对比结论**:Casey 的设计介于 Unity 和 Bevy 之间——比 Unity 更灵活(任意嵌套),比 Bevy 更手动(需要写 introspect 注册)。教学价值高,生产代码用 Bevy Reflect 更省事。

### 3.7 · 🎨 图形学视角

图形学的 introspection:

**1. Shader reflection**:Vulkan / OpenGL 在 pipeline 创建后,可以通过 `vkGetShaderStageInfo` 拿到 shader 的 uniform 列表、类型、binding。这是 GPU 端的 introspection。

**2. Material parameter UI**:基于 shader reflection,material editor 自动生成 UI(每个 uniform 一个 slider)。Unity Shader Graph、Unreal Material Editor、Substance Designer 都用这思路。

**3. Render pipeline introspection**:RenderDoc 捕获一帧后,能展开每个 draw call 的 vertex buffer、shader、texture、render state。这是图形调试器的"DataBlock 展开"。

**4. GPU performance counter**:`glGetQueryObjectui64v(GL_TIMESTAMP_QUERRY)` 等接口让 GPU "内省"自己的耗时。casey 后期(Day 240+)会用。

casey 的 introspect 是 CPU 端的,但和 GPU 端 shader reflection 思想完全一致——"程序运行时枚举自身结构"。

## 5 · 对照与变奏

不同工具的展开:

- **Chrome DevTools**:JS 对象,任意嵌套
- **VS Code Debugger**:变量树
- **rr / gdb**:struct 字段
- **Unity Inspector**:component 字段
- **Unreal Details Panel**:UObject 字段
- **Blender Outliner**:scene 树 + 数据
- **Maya Hypergraph**:节点图(扩展到 DAG,不只是 tree)
- ** Substance Designer**:节点图

所有这些都用"递归 + 按需展开 + 类型驱动"思想。casey 今天的实现是最小集合。

### 历史演化

**1980s**:Smalltalk 引入 object inspector,所有对象可展开
**1990s**:Visual Studio debugger 加"watch window",struct 展开
**2000s**:Web Inspector 出现(IE DevToolbar、Firebug),JS 对象树
**2010s**:游戏引擎 reflection 成熟(UE4 UProperty、Unity SerializeField)
**2014+**:Casey HH 实现 introspect + DataBlock
**2020+**:Bevy Reflect 把 introspection 推到 Rust 类型安全极致

casey 的实现位置很关键——他在游戏 reflection 系统成熟期,但还没流行 Rust derive 风格时,手写了一套 introspection。学懂他的设计,你看 Bevy Reflect 就懂"哦这是 casey 思路的 Rust idiomatic 版本"。

### Tree view 的退化形式

casey 的 TreeNode 是经典 tree,但有些场景需要更复杂结构:

**1. DAG(Directed Acyclic Graph)**:多父节点。Blender 的 object data 可能被多个 object 引用(同 mesh 多 instance)。展开时同一 mesh 数据可能显示多次。

**2. Graph with cycles**:节点互相引用。可视化难,通常用"展开深度限制"避免无限递归。

**3. Lazy stream**:理论上无限。游戏中的"事件流"可以一直生成,UI 显示前 N 个,翻页加载。

**4. Multi-root tree**:多个独立 root,而非单一 root。Unity Hierarchy 是这个,scene 里多个 root object。

casey 的 design 是 single-root strict-tree,最简形式。如果项目需要更复杂,Rust 用 `indextree` crate 或自己实现 arena-based DAG。

### Lv1 · 概念辨析

**题**:为什么"按需展开"比"全展开"快?具体哪些操作省了?

### Lv2 · 动手实践

**题**:实现 DataBlock + draw + expanded state。测试嵌套 struct 展开。

**参考解答**:

```rust
use std::collections::HashSet;

#[derive(Clone, Debug)]
enum DataBlock {
    Scalar(f32),
    Struct { fields: Vec<(String, DataBlock)> },
    Array { elements: Vec<DataBlock> },
}

struct Ui {
    expanded: HashSet<String>,  // path → expanded
}

impl Ui {
    fn new() -> Self { Self { expanded: HashSet::new() } }

    fn toggle(&mut self, path: &str) {
        if self.expanded.contains(path) {
            self.expanded.remove(path);
        } else {
            self.expanded.insert(path.to_string());
        }
    }

    fn is_expanded(&self, path: &str) -> bool {
        self.expanded.contains(path)
    }

    fn draw(&mut self, name: &str, block: &DataBlock, path: &str) {
        let indent = path.matches('/').count();
        let pad = "  ".repeat(indent);
        match block {
            DataBlock::Scalar(v) => println!("{}{} = {}", pad, name, v),
            DataBlock::Struct { fields } => {
                println!("{}{}/", pad, name);
                if self.is_expanded(path) {
                    for (field_name, field_block) in fields {
                        let field_path = format!("{}/{}", path, field_name);
                        self.draw(field_name, field_block, &field_path);
                    }
                }
            }
            DataBlock::Array { elements } => {
                println!("{}{}[{}]", pad, name, elements.len());
                if self.is_expanded(path) {
                    for (i, element) in elements.iter().enumerate() {
                        let elem_path = format!("{}/{}", path, i);
                        self.draw(&format!("[{}]", i), element, &elem_path);
                    }
                }
            }
        }
    }
}

fn main() {
    let player = DataBlock::Struct {
        fields: vec![
            ("pos".to_string(), DataBlock::Struct {
                fields: vec![
                    ("x".to_string(), DataBlock::Scalar(100.0)),
                    ("y".to_string(), DataBlock::Scalar(200.0)),
                ],
            }),
            ("hp".to_string(), DataBlock::Scalar(75.0)),
        ],
    };
    let enemies = DataBlock::Array {
        elements: vec![
            DataBlock::Scalar(30.0),
            DataBlock::Scalar(20.0),
            DataBlock::Scalar(50.0),
        ],
    };
    let root = DataBlock::Struct {
        fields: vec![
            ("player".to_string(), player),
            ("enemies".to_string(), enemies),
        ],
    };

    let mut ui = Ui::new();
    println!("=== Initial (collapsed) ===");
    ui.draw("root", &root, "");

    println!("\n=== Expand root/player ===");
    ui.toggle("root/player");
    ui.draw("root", &root, "");

    println!("\n=== Expand root/player/pos ===");
    ui.toggle("root/player/pos");
    ui.draw("root", &root, "");

    println!("\n=== Expand root/enemies ===");
    ui.toggle("root/enemies");
    ui.draw("root", &root, "");
}
```

### 实战补充:Introspection 在不同语言的实现成本

**Rust + bevy_reflect**:用 derive macro 自动生成。优点:零手写代码。缺点:derive macro 编译慢(增加 5-10s 编译时间)。

```rust
#[derive(Reflect)]
struct Player { pos: Vec2, hp: f32 }
// bevy_reflect 自动生成 Reflect impl,运行时 iter_fields() 可用
```

**C++ + Unreal UProperty**:用宏标记 + Unreal Header Tool(独立编译器)生成 reflection data。优点:运行时极快。缺点:UHT 是外部工具,有学习曲线。

**C casey 手写**:每个 struct 手写 introspect function。优点:零依赖、完全控制。缺点:工作量大。

**Java Reflection**:语言内置。优点:零工作量。缺点:运行时慢(method invocation ~100ns)。

**Go Reflection**:语言内置,interface 风格。优点:简单。缺点:性能一般,且 interface 包装让代码丑陋。

**结论**:Rust 的 derive macro 是当前最佳平衡——零运行时成本(数据编译时生成)、零手写代码(macro 自动)、强类型安全(type checker 验证)。casey 的 C 风格是历史包袱,Rust 翻译应该用 derive。

### 性能剖析:大 struct 展开的 CPU 成本

casey 在 Day 220 测过:

```
struct World {
    players: [Player; 1000],     // 1000 个玩家
    enemies: [Enemy; 5000],      // 5000 个敌人
    items: [Item; 10000],        // 10000 个物品
}
// 总字段数:16000 个嵌套字段
```

全展开:16000 × 100ns/字段 = 1.6ms。60 FPS 帧时间 16.6ms,debug 占 10%。**不可接受**。

按需展开:用户看 1 个 branch(100 字段)= 10μs。60 FPS 帧时间 16.6ms,debug 占 0.06%。**可接受**。

这就是 lazy evaluation 在游戏 debug 系统的实际价值——10ms 帧时间节省,等价于"debug overlay 不卡游戏"。

casey 在 HH 视频里反复强调:"debug 系统 CPU 时间必须 < 0.5ms/帧"。lazy 是达到这个目标的关键。

## 10 · 深入:immediate mode UI 的层级渲染

casey 在 day220 渲染 debug 层级时,用的是 immediate-mode UI(immediate-mode user interface)。这是 Casey 自己发明的术语,与现代 UI 框架(retained-mode)截然不同。让我们把它彻底讲透。

### 10.1 immediate vs retained:两种 UI 范式

**Retained-mode UI**(传统 GUI,Qt / WPF / GTK):

```cpp
// 启动时创建 widget 树
auto* button = create_button("Click me");
button->set_position(100, 100);
button->on_click = []{ ... };

// 框架内部维护 widget 树,每帧重新渲染这棵树
// 状态变化时显式通知:set_text("Clicked!")
```

特点:**状态持久**。按钮存在内存里,你创建一次,框架保留它直到显式删除。状态变化要显式更新。

**Immediate-mode UI**(casey / ImGui / egui):

```rust
// 每帧重新声明 UI
fn draw_ui(ui: &mut Ui, state: &mut State) {
    if ui.button("Click me") {
        state.count += 1;
    }
    ui.label(&format!("Count: {}", state.count));
}

// 每帧调用 draw_ui,没有持久 widget
```

特点:**无状态**。每帧从头声明 UI,框架即时处理输入和绘制。状态完全由调用方维护。

### 10.2 immediate mode 的核心机制

immediate mode 看似魔法——"每帧重新创建按钮,但是点击有效?"。机制是:**框架内部偷偷保留必要状态**。

casey 的 debug UI 实现里,每帧执行:

```
Frame N:
  1. mouse_pos, mouse_down 记录
  2. draw_ui() 遍历调用
     - 每个 ui.button("Click") 内部:
       - 计算当前位置(累积 layout)
       - 检查 mouse_pos 在不在 button rect 内
       - 检查 mouse_down 边沿(按下事件)
       - 如果命中且按下,返回 true(点击发生)
       - 立即绘制 button 外观
  3. 提交绘制
```

"按钮 ID" 是它的 label + parent ID 的 hash。框架每帧重建这个 ID,但 hash 是确定的——同一按钮每帧 hash 同值,框架能识别"这是上次那个按钮",保留 hover / focus 状态。

### 10.3 为什么 casey 用 immediate mode

casey 选择 immediate mode 的具体理由:

1. **无状态同步问题**。retained mode 必须在游戏状态变化时显式 update widget(`button->set_enabled(false)`)。immediate mode 直接读 game state,自动反映。casey 在视频里反复强调这点——debug UI 最怕"看到的数据和实际不一致",immediate mode 杜绝这个 bug。

2. **代码极简**。同一个函数里写游戏逻辑 + UI 显示,无 callback 地狱。debug UI 开发速度极快。

3. **无内存管理**。retained mode 要担心 widget 树的 alloc/dealloc,widget 泄漏。immediate mode 每帧重头开始,没有长期 widget 对象。

4. **死代码自动消失**。条件 UI:
   ```rust
   if state.debug_visible {
       ui.button("Close");
   }
   ```
   `debug_visible` 关掉时,这段代码不执行,button 物理不存在。retained mode 要 `button->hide()`,但 widget 还在内存。

### 10.4 immediate mode 的代价

代价也是真实存在的:

**1. CPU 开销**。每帧重新构造整个 UI,包括 layout、hit-test、绘制。retained mode 只在状态变化时重 layout。casey 的 debug overlay ~500 widget,每帧 ~0.3ms CPU,可接受。但大型 UI(Photoshop 那种 10000+ widget),immediate mode 就吃力了。

**2. 输入焦点管理**。retained mode 有明确"焦点 widget"概念,键盘事件路由到焦点。immediate mode 每帧重新声明,焦点靠 widget ID hash 维护,稍复杂。

**3. 动画困难**。retained mode 可以记录"button hover 动画进度 30%",每帧 +5%。immediate mode 没有持久 widget,要在外部 state 维护动画进度,代码侵入。

**4. ID 冲突**。两个按钮 label 相同,ID hash 冲突,框架误判。ImGui 提供 `push_id(...)` 临时修改 ID,但忘记 push 导致 bug 难调试。

### 10.5 Rust 生态的 immediate mode

Rust 主流 immediate mode UI 框架:

**egui**(最流行,Rust 生态 ImGui 风格)

```rust
use egui::{Context, Ui};

fn draw_debug(ctx: &Context, state: &mut GameState) {
    egui::Window::new("Debug").show(ctx, |ui| {
        ui.label(&format!("FPS: {}", state.fps));
        if ui.button("Reset").clicked() {
            state.reset();
        }
        for (name, value) in &mut state.debug_vars {
            ui.horizontal(|ui| {
                ui.label(name);
                ui.text_edit_singleline(value);
            });
        }
    });
}
```

egui 是 bevy / wgpu 项目的常用 debug UI。Rust 翻译版 HH 如果用 egui 替代 casey 手写的 debug UI,代码量减少 90%。

**iced**(Elm-style,model-update-view)

```rust
// iced 是 hybrid:声明式 + retained 部分状态
// 不纯 immediate,但比传统 retained 现代化
```

**slint**(原 60Hz,声明式 DSL)

```slint
// .slint 文件描述 UI,生成 Rust 代码
// 接近 QML,retained mode
```

casey 选自己手写 immediate mode 的原因:**教学**。手写能让学生理解 immediate mode 的机制,而不是用黑盒库。生产项目应该用 egui / iced 而不是手写。
