
# Day 215 · 清理调试事件整理

> 经过 day213-214 的重构,debug 事件流已经分裂成 toggle / permanent / transient 三类。原有的事件整理逻辑(collation)是为单一 event 流写的,现在分三路就要重写。今天 Casey 把 collation 重新组织,变成"分类 -> 路由 -> 单类整理"的流水线。

## 0 · 为什么要有这一天

事件整理(debug event collation)指的是把原始事件流(每帧上千条 events)整理成结构化的、UI 友好的形式。例如:

- 原始:`Begin(guid=42, frame=10, t=...)`、`End(guid=42, frame=10, t=...)`、`Value(guid=42, frame=10, val=3.14)`
- 整理后:`{ guid: 42, frame: 10, duration: ..., values: [3.14, ...], name: "physics_step" }`

之前 casey 把所有事件一股脑进同一个 collation,因为它简单。但 day213-214 加了 toggle 和 permanent 之后,这些事件被路由到不同的存储,但 collation 函数还试图处理所有类型——逻辑混乱、性能下降。

今天 casey 把 collation 拆成**单一职责**:

```
原始 events → 路由 → collate_transient
              ├────→ collate_toggle
              └────→ collate_permanent
```

每条 collation 函数只处理一类事件,逻辑简单、可独立测试。这是"分而治之"思想在事件流的应用。

心理锚点:看完今天,你应该能识别"一个函数试图处理多种异质数据"的代码味道,并拆分成多个函数。这种"分而治之"的能力是软件架构师的核心技能——它不是教条,而是基于"复杂度无法消除,只能分解"的认知。

更深一层看,今天的重构是 **Single Responsibility Principle(SRP)** 的实践——Robert Martin 在《Clean Architecture》里反复强调的 SOLID 原则之一。SRP 不是说"每个函数只做一件事"(那是过简的解读),而是说"每个模块只有一个变化的理由"。当 collation 函数同时处理 transient / toggle / permanent 三类事件,任何一类变化(比如 toggle 加新字段)都要改这个函数——多个变化的理由聚集在一处,违反 SRP。Casey 今天把它拆成三个,每个只有一个变化的理由。

这种"分而治之"的模式在工业代码库里到处都是:
- **编译器**:前端(parser)→ 中端(type check / IR)→ 后端(codegen)。每个阶段单一职责。
- **数据库**:parser → planner → optimizer → executor。SQL 进入,plan 出来。
- **Web framework**:routing → middleware → handler → response。请求按 pipeline 流转。
- **CI/CD**:lint → build → test → deploy。每个 stage 单一职责。
- **游戏引擎**:input → game logic → physics → render。每帧按顺序流转。

每个 pipeline 的关键设计点是"每阶段输入输出明确,无 cross-cutting concerns"。Casey 今天的 collation 重构就是把"一锅烩"改成"流水线",和工业级架构师的设计思路一致。

## 1 · Casey 今天做了什么

1. **拆 collate_events 函数**:之前 1 个大函数,现在 3 个小函数
2. **加路由层**:根据 event 类型分发到对应 collate 函数
3. **修一个 bug**:toggle 的 collation 之前会错误地把 toggle 也按 transient 处理(画曲线),修复后正确用阶跃图
4. **加测试**:对每种 collation 函数加单元测试

## 2 · 心智模型

### 类比:邮件分拣中心

邮局收到一袋混合邮件,有平信、挂号、包裹、EMS。最初一个分拣员要处理所有类型,边分边累。后来升级:加一个分拣台,先把邮件按类型分流到不同传送带,每个传送带只有一个专门的分拣员处理对应类型。

casey 今天的 collation 就是这个升级:加一个 routing 层,把事件分到三个专门的传送带。

这个类比还可以更深:邮局之所以分流,不是因为分拣员不够聪明,而是因为**每种邮件有不同的处理流程**。平信只需要盖章投递,挂号要签字扫描,包裹要称重贴标签,EMS 要优先派送。如果让一个分拣员处理所有类型,他要在不同流程间切换,效率极低。专职工人各自只关心一种流程,效率高很多。

软件里的对应:**单个函数处理多种数据,等于让一个 CPU 核心做上下文切换**。CPU cache 被反复刷新,分支预测器失灵,代码 locality 差。拆分后,每个函数的代码 locality 极佳,icache 友好。

类比还能再深:**邮局的传送带是"物理隔离"**——平信传送带上的分拣员看不到包裹传送带上的事。这是"功能隔离"的实现方式。软件里对应"函数隔离":每个函数只看一类输入,不会意外处理别的类型的边界情况。这就是 SRP 的物理基础。

### 2.1 单一职责原则(SRP)

软件设计的经典原则:**一个函数 / 类只做一件事**。判断"一件事"的标准是"它是否只有一个变化原因"。

原 collate_events 函数要做的事:

- 解析 event 类型
- 把 BeginBlock 和 EndBlock 配对,算 duration
- 把 Value 加到 watch history
- 把 Toggle 加到 toggle history
- 把 Permanent 更新到 permanent map

5 件事 → 5 个变化原因。SRP 违反。改后 3 个函数各自只做 1 件事。

### 2.2 Rust enum + match 实现路由

```rust
enum DebugEvent {
    BeginBlock { guid: u64 },
    EndBlock { guid: u64 },
    Value { guid: u64, value: DebugValue },
    Toggle { guid: u64, on: bool },
    Permanent { guid: u64, value: DebugValue },
}

fn route_event(state: &mut DebugState, event: DebugEvent) {
    match event {
        DebugEvent::BeginBlock { guid } => collate_transient_begin(state, guid),
        DebugEvent::EndBlock { guid } => collate_transient_end(state, guid),
        DebugEvent::Value { guid, value } => collate_transient_value(state, guid, value),
        DebugEvent::Toggle { guid, on } => collate_toggle(state, guid, on),
        DebugEvent::Permanent { guid, value } => collate_permanent(state, guid, value),
    }
}
```

Rust 的 `match` 在 enum 上是**穷尽的**——加新 variant 时,编译器强制你在所有 match 处加分支。这是 enum 比 C 的 tagged union + switch 优越的地方:**编译时保证不漏**。

### 2.3 Pair begin/end 的栈算法

profiler 的 BeginBlock / EndBlock 必须配对。算法:

```rust
struct CollationState {
    stack: Vec<u64>,  // 当前嵌套的 BeginBlock guid 栈
}

fn collate_transient_begin(state: &mut CollationState, guid: u64, t: u64) {
    state.stack.push(guid);
    state.start_time.insert(guid, t);
}

fn collate_transient_end(state: &mut CollationState, guid: u64, t: u64) {
    let popped = state.stack.pop();
    if popped != Some(guid) {
        // 配对错误,日志记录
        return;
    }
    let start = state.start_time.remove(&guid).unwrap();
    let duration = t - start;
    state.durations.insert(guid, duration);
}
```

栈是处理嵌套 Begin/End 的标准结构。HH 在 Day 177 已经用了,但今天 casey 把它从大 collate 函数抽出来,独立成函数。

### 2.4 第一性原理:为什么"分而治之"在事件处理里如此有效

软件设计里有个反复验证的经验:**单函数代码行数超过 ~200 行时,bug 密度开始指数上升**。原因是人脑工作记忆有限(7±2 个 chunk),200 行意味着你要同时记住几十个局部变量、控制流分支、状态转换。

但还有更深的层次——**编译器和 CPU 也不喜欢大函数**:
- LLVM 优化在 ~1000 行的函数上效果显著下降
- icache(指令缓存)是 32KB,大函数的循环可能跨 cache line
- branch predictor 在复杂控制流下命中率下降

Casey 之前的大 collate 函数有 ~300 行(5 种 event 类型 × 每种 ~50 行处理)。拆成 3 个 ~100 行的小函数后,每个函数都 fit in icache,编译器内联优化生效,性能和可读性双提升。

更微妙的一点:**测试隔离**。大函数测一种 event 的处理,要构造所有其他 event 的 mock 输入。小函数只测自己,输入简单。casey 在视频里反复强调"测试容易是 SRP 的客观指标"——不是审美,是可量化的工程价值。

最后,**演化能力**。Casey 现在想加新功能"profiler block 的内存分配追踪"。这个功能只涉及 transient 类型的 collation。拆分前要在大函数里加分支,可能影响其他类型(回归测试全跑)。拆分后只改 collate_transient,其他不动(回归测试只测这一个)。**演化成本 = 影响范围 × 改动深度**,拆分让两者都缩小。

### 2.5 Rust match 的穷尽性保证

Rust 的 `match` 在 enum 上是穷尽的(exhaustive)。这有一系列工程收益:

```rust
enum DebugEvent { A, B, C }

fn process(e: DebugEvent) {
    match e {
        DebugEvent::A => { ... }
        DebugEvent::B => { ... }
        // 编译错误:non-exhaustive patterns: `C` not covered
    }
}
```

加新 variant `D` 时,所有 match 处都会编译错误,强制你处理新 case。这是**编译时保证不漏**,不需要测试覆盖。

C 的 switch 没有这个保证:
```c
switch (e->type) {
    case A: ...
    case B: ...
    // 没处理 C,运行时 fallthrough 默认分支,bug
}
```

这是 Rust 比 C 在大型代码库上的核心优势之一。Casey 自己在 C 里靠纪律保证(每次加 variant 手动搜所有 switch),不可避免漏掉。Rust 编译器替你做这件事。

工程上,这意味着:**Rust 项目里"加 enum variant"是安全的重构**——编译器告诉你所有要改的地方。C 项目里同样操作要靠 grep + 经验 + 测试。Casey 用 Rust 翻译 HH 时,这一项收益最大。

### 2.6 Pair begin/end 算法的边界情况

casey 用栈配对 begin/end,但有几个边界情况要处理:

**1. 嵌套**:同 guid 的嵌套 begin(罕见但合法)
```
Begin(A) → Begin(A) → End(A) → End(A)
```
栈配对失败,因为栈顶是第二个 A,但 end 期望第一个 A。casey 用时间戳解决——每个 begin 存自己的时间,end 配对最近的同 guid begin。

**2. 跨帧 begin/end**:某帧 begin,下一帧才 end
```
帧1: Begin(A)
帧2: End(A)
```
casey 的 collation 在每帧结束时"清算"未配对的 begin,标记为 incomplete。UI 渲染时显示"incomplete block"警告。

**3. 重复 end**:同一个 begin 对应多个 end
```
Begin(A) → End(A) → End(A)
```
casey 检测第二个 end 时栈空,记 warning,忽略。

**4. Hot-reload 中途**:游戏代码热重载,可能丢失未配对的 begin
```
Begin(A) → hot-reload → End(A)
```
新版本游戏代码不知道有 begin,casey 让 collation 系统独立于游戏代码,hot-reload 时不影响 collation 状态。

这些边界情况在拆分前都混在大函数里,拆分后专门在 collate_transient_begin/end 函数里处理,**边界情况集中,容易审查**。这也是 SRP 的另一个收益——"边界情况处理集中"。

## 3 · 四域深入

### 3.1 · 游戏编程视角

事件分拣是 profiler 的核心。Chrome 的 tracing、Firefox Profiler、Unreal Insights 都用类似架构:

- 原始 trace event → 按类型分类 → 各自的 view

casey 今天做的就是给 HH 加上同样的 routing 层。

### 3.2 · Linux 系统编程视角

Linux 内核 tracepipe 也是分拣系统:

- trace event 原始流 → ftrace formatter 分类 → 各 tracer(function / sched / wakeup)处理

类似的思想:`systemd-journald` 把所有服务日志统一收集,然后按 priority / facility 路由。

### 3.3 · Rust 生态视角

Rust 的 enum + match 是表达"分拣"的最佳工具。对比 OOP:

```rust
// OOP 风格(虚拟分发)
trait DebugEvent { fn collate(&self, state: &mut DebugState); }
struct BeginBlock { guid: u64 }
impl DebugEvent for BeginBlock { fn collate(...) { ... } }

// Rust 风格(enum + match)
enum DebugEvent { ... }
fn collate(state: &mut DebugState, e: DebugEvent) { match e { ... } }
```

enum 风格:
- 数据集中(在一个 enum 定义里看到所有 variant)
- 控制流集中(在一个 match 里看到所有分支)
- 编译器保证穷尽

OOP 风格:
- 数据分散(每个 struct 一个 impl)
- 控制流分散(vtable 跳转)
- 加新类型容易,加新操作难

casey 选 enum。Rust 推荐同样选择。

### 3.4 · 测试视角

拆分后单元测试容易:

```rust
#[test]
fn collate_toggle_adds_to_history() {
    let mut state = DebugState::new();
    collate_toggle(&mut state, 42, true, 0);
    assert_eq!(state.toggle_history[&42], vec![true]);
}

#[test]
fn collate_permanent_updates_value() {
    let mut state = DebugState::new();
    collate_permanent(&mut state, 42, DebugValue::F32(3.14), 0);
    assert_eq!(state.permanent[&42], DebugValue::F32(3.14));
}
```

每个 collate 函数独立测试,不依赖其他类型的事件。

### 3.5 · 🐧 Linux 系统编程视角(扩展)

Linux 内核的 tracepipe、audit、perf 三个子系统都是事件路由 + 分发的实例,可以横向对照学习。

**1. ftrace 的 trace_event 系统**:每个 trace event(比如 `sched_switch`)注册一个 `trace_event_class`,包含 format string + print function + register/unregister 钩子。当事件发生,trace_event framework 路由到所有注册的 tracer(function tracer、sched_switch tracer 等)。每个 tracer 独立处理,和 Casey 的 collation 模式完全一样。

```c
// 内核里
DEFINE_EVENT_CLASS(sched_switch_template,
    TP_ARGS(struct task_struct *prev, struct task_struct *next),
    // ...
);

DEFINE_EVENT(sched_switch_template, sched_switch,
    TP_ARGS(struct task_struct *prev, struct task_struct *next));
```

**2. perf 的 PMU 路由**:硬件性能计数器(PMU)产生事件,perf 把事件路由到 user-space 的 consumer(perf record)或 in-kernel aggregator(perf stat)。每种 consumer 用独立 ring buffer。

**3. audit subsystem**:`/var/log/audit/audit.log` 来自 auditd daemon,内核里 audit 子系统把"系统调用事件"路由到 auditd 或丢弃,基于规则匹配。规则就是 Casey 的 route_event 逻辑,只是更复杂(支持字段过滤)。

对应到 Casey:**今天的 route_event 是这些工业级 trace 系统的最小可用版本**。如果你之后做"游戏 trace 服务器"或"远程 debug 协议",直接照搬这个 routing 模式。

### 3.6 · 🎮 游戏工业对照

游戏引擎里事件路由很常见:

**Unreal Insights**:UE 的 profiler,trace event 走统一的 routing channel,分发到不同 view(Timing view、Asset view、Networking view)。每个 view 独立处理自己关心的事件类型,casey 拆 3 个 collate 函数对应这种"多 view 独立处理"。

**Unity Profile Analyzer**:Unity 的 profiler 数据可以离线分析,事件按类型分类(timing、memory、render),每类独立分析。

**Bevy 的 Events 系统**:Bevy 用 `Event<T>` 类型,每个事件类型是独立 generic。System 用 `EventReader<T>` 读特定类型。这是 Casey route_event 的 ECS 版本——类型系统替你做路由,不需要手动 match。

**对比结论**:Casey 的 enum + match 是最轻量的实现。ECS 系统用 generic trait 做静态分发,更类型安全但代码量大。Unreal Insights 用宏 + 反射做动态分发,运行时灵活但慢。casey 选 enum 是 HH 项目的最佳平衡点——够类型安全、够快、够简单。

### 3.7 · 🎨 图形学视角

图形学里的事件路由也很常见,主要在 GPU profiling。

**GPU profiling 的 event 路由**:GPU 端的 timestamp query 也走类似 routing。每个 draw call 包一层 begin/end timestamp,渲染帧结束后读 GPU 端的 timestamp buffer,按类型分类:per-drawcall、per-pass、per-frame。

**Vulkan / DirectX 12 的 debug marker**:GPU command buffer 里可以放 `vkCmdBeginDebugUtilsLabelEXT("Forward Pass")`,GPU profiler 路由这些 marker 显示成可视化区间。每个 marker 是个 event,route 到不同 view。

**RenderDoc**:图形调试器,捕获一帧的所有 draw call,按 pass 路由分类。开发者可以"只看 shadow pass"或"只看 transparent pass"。这正是 Casey 的 route_event 在图形调试器里的应用。

这些都是"按事件类型分发到不同 view/processor"的工业实例。

## 5 · 对照与变奏

事件分拣在不同领域:

- **Web server**:HTTP request 路由到不同 handler
- **Database query planner**:SQL 语句路由到不同执行器
- **Compiler AST visitor**:语法树节点路由到不同 visitor
- **Game input system**:键盘事件路由到不同 binding
- **OS interrupt handler**:硬件中断路由到对应设备驱动
- **ECS System**:Entity 路由到查询它 component 的 system
- **Actor framework (Akka)**:Message 路由到对应 actor

所有这些都是 routing + collation 的实例。

### 路由模式的变体

**1. 静态分发(编译时)**:Rust 的 enum + match,casey 选的。优点:零开销、类型安全。缺点:加 variant 要重新编译。

**2. 动态分发(运行时)**:OOP 多态,trait object (`Box<dyn Trait>`)。优点:加 variant 不用改路由代码。缺点:vtable 间接、可能 deopt。

**3. 数据驱动**:用 hash map 把 "type id" 映射到函数指针。Lua、Python 的 method dispatch 是这种。优点:运行时可改路由表。缺点:慢、不安全。

**4. Pattern matching + 多重分发**:Scala、Haskell 的 case class + match。Rust 的 enum 接近这种,但 Rust 不支持多重分发(每次 match 一个 enum)。

**5. Actor message select**:Erlang / Akka 的 receive block,基于消息模式分发。适合分布式,不适合 Casey 的单线程场景。

casey 选 (1) 静态分发,因为性能和类型安全都重要。

### 历史演化

**1960s-1980s**:函数 + if-else 路由,简单粗暴
**1990s**:OOP 兴起,vtable 路由成主流
**2000s**:Java Spring 用反射做 routing,运行时灵活但慢
**2010s**:Rust / Haskell 复兴 algebraic data type + match,编译时类型安全回归
**2020+**:Bevy ECS、Actors、CRDT 都用 typed event routing,类型安全 + 性能并重

casey 的选择(rust enum)站在历史正确的一边。

### Lv1 · 概念辨析

**题**:为什么 casey 把 collation 拆成 3 个函数,而不是 1 个函数加 if-else?SRP 的"一件事"如何判断?

### Lv2 · 动手实践

**题**:实现 route_event + 3 个 collate 函数。测试每种 event 都被正确路由和整理。

完成标准:`cargo test` 通过。

**参考解答**:

```rust
use std::collections::{HashMap, VecDeque};

#[derive(Clone, Debug, PartialEq)]
enum DebugEvent {
    Begin(u64),
    End(u64),
    Value { guid: u64, v: f32 },
    Toggle { guid: u64, on: bool },
    Permanent { guid: u64, v: f32 },
}

struct DebugState {
    stack: Vec<u64>,
    durations: HashMap<u64, u64>,
    values: HashMap<u64, VecDeque<f32>>,
    toggles: HashMap<u64, bool>,
    permanent: HashMap<u64, f32>,
}

impl DebugState {
    fn new() -> Self {
        Self {
            stack: vec![],
            durations: HashMap::new(),
            values: HashMap::new(),
            toggles: HashMap::new(),
            permanent: HashMap::new(),
        }
    }
}

fn route(state: &mut DebugState, e: DebugEvent, t: u64) {
    match e {
        DebugEvent::Begin(g) => collate_transient_begin(state, g, t),
        DebugEvent::End(g) => collate_transient_end(state, g, t),
        DebugEvent::Value { guid, v } => collate_transient_value(state, guid, v),
        DebugEvent::Toggle { guid, on } => collate_toggle(state, guid, on),
        DebugEvent::Permanent { guid, v } => collate_permanent(state, guid, v),
    }
}

fn collate_transient_begin(state: &mut DebugState, g: u64, t: u64) {
    state.stack.push(g);
    state.durations.insert(g.wrapping_add(0xdeadbeef), t); // hack:存 start time
}

fn collate_transient_end(state: &mut DebugState, g: u64, t: u64) {
    state.stack.pop();
    let start = state.durations.remove(&(g.wrapping_add(0xdeadbeef))).unwrap_or(0);
    state.durations.insert(g, t - start);
}

fn collate_transient_value(state: &mut DebugState, g: u64, v: f32) {
    state.values.entry(g).or_default().push_back(v);
    if state.values[&g].len() > 300 {
        state.values.get_mut(&g).unwrap().pop_front();
    }
}

fn collate_toggle(state: &mut DebugState, g: u64, on: bool) {
    state.toggles.insert(g, on);
}

fn collate_permanent(state: &mut DebugState, g: u64, v: f32) {
    if state.permanent.get(&g) != Some(&v) {
        state.permanent.insert(g, v);
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn routing_works() {
        let mut s = DebugState::new();
        route(&mut s, DebugEvent::Begin(1), 10);
        route(&mut s, DebugEvent::End(1), 15);
        assert_eq!(s.durations[&1], 5);

        let mut s = DebugState::new();
        route(&mut s, DebugEvent::Toggle { guid: 2, on: true }, 0);
        assert_eq!(s.toggles[&2], true);

        let mut s = DebugState::new();
        route(&mut s, DebugEvent::Permanent { guid: 3, v: 9.8 }, 0);
        route(&mut s, DebugEvent::Permanent { guid: 3, v: 9.8 }, 0);  // 同值不更新
        assert_eq!(s.permanent.len(), 1);
    }
}
```

**预期输出**:

**Troubleshooting**:
- `match e` 报 non-exhaustive — 漏了 enum variant,加上
- route 函数 panic — 检查 collate_transient_end,栈空时 pop 返回 None,要 unwrap_or 处理
- `collate_transient_value` 累积无限 — 检查 ring buffer 的 pop_front 逻辑
- 性能差 — 看 flamegraph,HashMap lookup 可能是瓶颈,考虑用 FxHashMap(no hashing for small u64 keys)

### Rust 编译器收益:加 variant 的安全重构

试一下:在 DebugEvent enum 里加一个新 variant `Counter { guid: u64, delta: i32 }`。Rust 编译器会立刻在 `route` 函数报错"non-exhaustive patterns"。这是**编译时保证**,casey 在 C 里做不到(C 的 switch 不强制 default)。

实践意义:HH 项目后期(day 240+)casey 多次加 event variant,每次都能立刻定位所有要改的地方。Rust 翻译版的工程价值在这一刻最显著。
