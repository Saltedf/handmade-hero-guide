
# Day 221 · 实现多层过场动画

> 之前过场动画(cutscene)是单层——一张图、一段声音、一组字幕。今天 casey 加多层:背景层 + 角色层 + 字幕层 + 特效层,各自独立时间线,合成显示。

## 0 · 为什么要有这一天

电影工业的"合成"概念:画面由多个 layer 合成。例如一个新闻画面:

- Layer 1(底):主播视频
- Layer 2:字幕条
- Layer 3:台标 logo
- Layer 4:紧急通知横幅

每个 layer 独立:

- 时间不同(字幕 5 秒后出现,台标全程显示)
- 动画不同(字幕淡入,logo 闪烁)
- 资源不同(视频是 h264,字幕是文字,logo 是 PNG)

之前 casey 的 cutscene 是单层:一个时间线驱动一组资源。今天升级成多层,各 layer 独立时间线、独立资源、独立动画。

**这是 sort key 的应用场景**:每个 layer 在渲染时按优先级排序(背景先画、字幕后画),用 sort key 简化排序逻辑。

心理锚点:看完今天,你能解释"为什么视频编辑软件有 timeline / track / layer 三个概念",并在自己代码实现多层合成。

## 1 · Casey 今天做了什么

1. **加 CutsceneLayer struct**:包含时间线、资源、动画
2. **加 Cutscene struct**:多个 layer,独立播放
3. **加 layer 优先级**:每个 layer 有 sort key(z-order)
4. **改渲染器**:按 layer 优先级排序后画

## 2 · 心智模型

### 类比:Photoshop 图层

Photoshop 一张图:

- Background 层
- Image 层(主体)
- Text 层(标题)
- Adjustment 层(色彩调整)

每层独立编辑、独立透明度、独立混合模式。最终图像按层顺序合成。

casey 的多层 cutscene 就是游戏版的 Photoshop 图层——每 layer 独立、按 z 顺序合成。

类比还能更精确:Photoshop 层是"空间对齐"——所有层覆盖同一画布,按 z 顺序叠加。casey 的 cutscene layer 也是空间对齐(同一屏幕),只是每层内容不同(背景视频 vs 字幕文字)。

更深一层:**Photoshop 的层是用户感知的"独立单元"**,但底层实现是"位图堆栈"。游戏 cutscene 类似——用户感知 layer 独立,底层实现可以是"alpha blend 堆栈"。这种"用户感知 vs 底层实现"的分离是软件设计的核心——好的抽象让用户操作直觉,底层实现自由优化。

再深:**Photoshop 的 layer opacity / blend mode 是层的属性**,不是全局。casey 的 cutscene 也支持每 layer 独立 alpha 动画(淡入淡出)。这种"属性归 layer"的设计让 layer 完全自包含——可以独立测试、独立替换。

### 2.1 Layer 时间线

每 layer 有自己的"开始时间"和"持续时间"。例如:

- 背景视频:t=0 开始,持续 30 秒
- 字幕:t=5 开始,持续 5 秒
- 紧急横幅:t=10 开始,持续 3 秒

合成渲染时,根据全局时间 t 查询每 layer 的当前帧:

```rust
struct CutsceneLayer {
    start_time: f32,
    duration: f32,
    timeline: Timeline,  // 内部时间线
    z_order: i32,
}

impl CutsceneLayer {
    fn sample(&self, global_time: f32) -> Option<Frame> {
        if global_time < self.start_time { return None; }
        let local_time = global_time - self.start_time;
        if local_time > self.duration { return None; }
        self.timeline.sample(local_time)
    }
}
```

返回 `Option<Frame>` 表示该 layer 在当前时刻可能"不显示"(None)或"显示某帧"(Some)。

### 2.5 第一性原理推导:为什么"分层"是工程必然

从第一性原理推导为什么复杂场景必须分层。

**前提**:现实世界的复杂画面由多个独立元素组成——背景天空、主体角色、字幕文字、特效粒子。每个元素有不同的资源需求(图片、视频、文字)、不同的动画模式(静态、循环、一次性)、不同的生命周期(全程、片段)。

**问题**:如果用单一数据结构表达"画面所有元素",需要"通用元素"类型,包含所有可能的属性。这个类型会极其臃肿,大部分属性对大部分元素无意义(字幕没有"播放速度"属性,视频没有"字体"属性)。

**方案 A:单一臃肿类型**。`struct Element { texture: Option<Texture>, text: Option<String>, fps: Option<f32>, font: Option<Font>, ... }`。每个元素大部分字段 None,内存浪费,代码丑陋。

**方案 B:类型擦除**。`trait Element { fn render(&self); }`,每个具体类型实现。但运行时多态有 vtable 开销,且无法静态优化。

**方案 C:分层 + 类型化**。casey 选这个。每 layer 是 `enum LayerContent` 变体,有自己的字段集合。layer 之间通过统一的"sample 接口"组合。

**为什么方案 C 最优?** 用信息论推导:

- 方案 A 每元素带 N 个 Option 字段,每个 Option 是 1 bit 标记 + payload。N=20 字段时,每元素至少 20 bytes 浪费。
- 方案 C 用 enum 标记(N=4 时 1 byte)+ 各 variant 字段。总内存只占实际需要的字段。
- 1000 个 layer × 20 bytes 浪费 = 20 KB,方案 C 没有这 20 KB。

**更深一层**:分层让"每层独立演化"。背景视频可以换成 3D scene,字幕可以换字体,完全不影响。这种"模块化"是软件工程的核心目标——单模块改动不影响其他。

casey 的分层 cutscene 设计在游戏工业(Unity Timeline、UE Sequencer)是标准做法,不是 casey 发明。但他从第一性原理推导出这个设计,教学价值高。

### 2.6 Sort key 的扩展思路

casey 今天用 i32 z_order,简单。但他埋了伏笔——Day 229+ 会扩展成复合 sort key。先看完整 sort key 思想:

**复合 sort key 的结构**(64 位):

```
[16 bit layer][8 bit priority][8 bit transparency][16 bit depth][16 bit material]
```

每个字段编码一种排序维度:
- layer:背景/前景/UI
- priority:同 layer 内的细粒度优先级
- transparency:不透明物体先画,透明物体后画(避免 overdraw)
- depth:深度排序(画家算法)
- material:同 material 一起画,减少 state 切换

**为什么不用 struct + 多次 sort?** 一次 sort 比多次 sort 快 N 倍(每次 sort 是 O(N log N))。复合 key 把多次 sort 合成一次,极快。

**复合 key 的比较**:u64 整数比较,~1 cycle。比"先比较 layer,if equal 比较 priority,if equal 比较 ..." 快 10 倍以上。

**casey 的伏笔**:今天的 i32 z_order 是简化版,Day 229+ 会升级到 u64 复合 key。提前预告让读者有心理准备。

工业实践:
- **Unreal Engine**:渲染 sort 用 64-bit key,字段分配和 casey 类似
- **Unity SRP**:同上
- **DOOM Eternal**:renderer 论文里详细描述了 64-bit sort key 的字段分配

casey 的 sort key 设计是工业级的"教学版本"。

### 2.2 合成

```rust
struct Cutscene {
    layers: Vec<CutsceneLayer>,
}

impl Cutscene {
    fn render(&self, global_time: f32) -> Vec<Frame> {
        let mut active: Vec<(i32, Frame)> = vec![];
        for layer in &self.layers {
            if let Some(frame) = layer.sample(global_time) {
                active.push((layer.z_order, frame));
            }
        }
        // 按 z 升序排序
        active.sort_by_key(|(z, _)| *z);
        active.into_iter().map(|(_, f)| f).collect()
    }
}
```

`sort_by_key` 用 z_order 排序,小的先画(被大的覆盖)。

### 2.3 Layer 类型

casey 支持几种 layer 类型:

- **Image layer**:静态 PNG + 透明度动画
- **Animation layer**:精灵动画(序列帧)
- **Text layer**:字幕 + 淡入淡出
- **Effect layer**:全屏色调、模糊等

用 enum 表达:

```rust
enum LayerContent {
    Image { texture: TextureId, alpha: Animation<f32> },
    SpriteAnim { frames: Vec<TextureId>, fps: f32 },
    Text { content: String, alpha: Animation<f32> },
}
```

`Animation<T>` 是"时间到值的函数",可以是关键帧插值或程序化。

### 2.4 Sort key 的角色

casey 在 Day 229+ 会深入讲 sort key。今天先埋伏笔:每个 layer 的 z_order 就是一种 sort key。

sort key 的好处:

- 渲染排序简化(整数比较)
- 可以编码更多信息(layer + 优先级 + 透明度类别打包到一个 u64)
- GPU 渲染时按 key 排序减少状态切换

今天 casey 用最简单的 i32 z_order,Day 229+ 扩展成复合 sort key。

## 3 · 四域深入

### 3.1 · 游戏编程视角

多层合成在游戏里到处都是:

- **UI 层**(HUD、菜单)
- **世界层**(角色、地形)
- **背景层**(天空盒、远景)
- **特效层**(粒子、后处理)

每层独立渲染目标(render target),最后合成。casey 的多层 cutscene 是这个思想的过场版本。

### 3.2 · 图形学视角

图形学里 layer 通常对应 **render target**:

- 每个 layer 渲染到独立 framebuffer
- 最后一个 pass 把所有 layer 合成到屏幕

合成用 alpha blending:`dest = src * src_alpha + dest * (1 - src_alpha)`。

casey 今天还在 CPU 软渲染,直接按 z 顺序往 framebuffer 画,alpha blend 在像素级。Day 235+ 切 OpenGL 后,layer 会变成独立 render target。

### 3.3 · Linux 系统编程视角

Linux 图形栈也用 layer 概念:

- **Wayland**:每个 surface 是一个 layer,compositor 按 z 合成
- **DRM**(Direct Rendering Manager):硬件 plane,可叠加
- **X11 Composite extension**:同上

`weston`、`mutter`、`kwin` 这些 compositor 都是 layer 合成器。casey 的 cutscene 合成器是游戏内的迷你版。

### 3.4 · Rust 生态视角

Rust 表达 timeline + keyframe:

### 3.5 · 🐧 Linux 系统编程视角(扩展)

Linux 图形栈的 layer 概念深入:

**1. Wayland 的 layer-shell 协议**:每个 Wayland client 可以把自己的 surface 放到不同 layer:
- `Layer::Background`:桌面壁纸
- `Layer::Bottom`:桌面 widget
- `Layer::Top`:通知、tooltip
- `Layer::Overlay`:屏幕保护、锁屏

每 layer 内部按 z 顺序合成,layer 之间也按固定顺序。这是 casey 的 z_order 的工业级扩展。

**2. DRM (Direct Rendering Manager) 的 hardware plane**:现代 GPU 有多个硬件 plane,可以直接硬件合成。比如 Intel iGPU 有 3 个 plane:
- Plane 0:cursor(光标,硬件加速)
- Plane 1:primary(主 framebuffer)
- Plane 2:overlay(视频,YUV 格式)

硬件 plane 合成零 CPU 成本,比软件合成快。但 plane 数量有限,需要"plane allocation"算法决定哪个 surface 上哪个 plane。

**3. Compositor 的内部 layer**:`mutter`(GNOME)、`kwin`(KDE)、`weston`(reference) 这些 compositor 内部把 surface 分到不同 layer:
- 桌面 background layer
- 普通 window layer
- 全屏 layer
- popup / notification layer
- lock screen layer

每 layer 内部 z 排序,layer 之间固定顺序。casey 的 cutscene 完全对应。

**4. PipeWire / JACK 的 audio layer**:音频合成也是 layer 风格,每路音频流是 layer,mix 在一起。casey 后期会涉及(在 audio 集成时)。

### 3.6 · 🎮 游戏工业对照

游戏引擎的多层合成:

**Unity Canvas + Sorting Group**:Unity 的 UGUI 用 Canvas 组织 UI,Canvas 内多个 SortingGroup 排序。每 SortingGroup 有 sortingOrder,完全 casey 风格。

**Unreal Widget / UMG**:UMG 的 widget 树,ZOrder 字段决定排序。casey 的 z_order 是简化版。

**Godot CanvasLayer**:每个 CanvasLayer 有 layer index,数字大的覆盖数字小的。casey 的 z_order 完全对应。

**Bevy UI / Render Layers**:Bevy 用 component 表达 layer,`RenderLayers` bitmask 控制哪个 camera 看到哪些 entity。这是 ECS 风格的 layer 表达。

**对比结论**:整个游戏工业都用"layer + z_order"组织多层渲染。casey 不是发明者,他在教学项目里实现行业标准。

### 3.7 · 🎨 图形学视角

图形学里 layer 的多种实现:

**1. Render target layer**:每 layer 渲染到独立 framebuffer,最后合成。质量高(每层独立 depth buffer),但内存大(N 个 framebuffer)。

**2. Direct to backbuffer**:所有 layer 直接画到主 framebuffer,按 z 顺序覆盖。内存小,但透明 blend 复杂。

**3. Depth buffer based layer**:每 layer 占用特定 depth range,通过 depth test 排序。GPU 自动处理顺序。

**4. Stencil based layer**:用 stencil buffer 标记 layer 区域,layer 只画在自己 stencil 区域。复杂的 layer mask 用这种。

casey 今天是方案 2(直接画 framebuffer),Day 235+ 切 OpenGL 后用方案 1(独立 render target + 合成 pass)。

**Alpha blending 的数学**:
```
dest = src.rgb * src.alpha + dest.rgb * (1 - src.alpha)
```
- src.alpha = 1:完全不透明,完全覆盖 dest
- src.alpha = 0:完全透明,dest 不变
- src.alpha = 0.5:半透明,dest 和 src 各贡献 50%

casey 的 cutscene 淡入淡出就是 alpha 从 0 渐变到 1,然后从 1 渐变到 0。

**关键限制**:alpha blend 是"顺序敏感"的——A blend B blend C 不等于 C blend B blend A(因为不交换)。这就是为什么必须用 z_order 排序,不能乱序渲染。

### Lv1 · 概念辨析

**题**:为什么多层 cutscene 用 z_order 排序,而不是用 layer 在 Vec 里的顺序?

**参考解答**:z_order 显式表达意图,Vec 顺序是隐式。如果 layer 在 Vec 中重排,z_order 不变,合成结果不变。z_order 还允许"两个 layer 共享同一 z"(同 z 按 Vec 顺序)。Vec 顺序耦合存储与渲染,脆弱。

### Lv2 · 动手实践

**题**:实现 Cutscene + Layer + Timeline,模拟 3 个 layer 在不同时间淡入淡出。

**参考解答**:

```rust
#[derive(Clone, Copy, Debug)]
struct Frame { color: (u8, u8, u8, u8), name: &'static str }

struct Layer {
    start: f32,
    duration: f32,
    z: i32,
    frame: Frame,
}

impl Layer {
    fn sample(&self, t: f32) -> Option<Frame> {
        if t < self.start || t > self.start + self.duration {
            return None;
        }
        // 淡入淡出:前后 0.5 秒 alpha 渐变
        let local = t - self.start;
        let fade = 0.5;
        let alpha = if local < fade {
            (local / fade) as f32
        } else if local > self.duration - fade {
            ((self.duration - local) / fade) as f32
        } else {
            1.0
        };
        let mut f = self.frame;
        f.color.3 = (f.color.3 as f32 * alpha) as u8;
        Some(f)
    }
}

struct Cutscene { layers: Vec<Layer> }

impl Cutscene {
    fn render(&self, t: f32) -> Vec<Frame> {
        let mut active: Vec<(i32, Frame)> = vec![];
        for layer in &self.layers {
            if let Some(f) = layer.sample(t) {
                active.push((layer.z, f));
            }
        }
        active.sort_by_key(|(z, _)| *z);
        active.into_iter().map(|(_, f)| f).collect()
    }
}

fn main() {
    let cs = Cutscene {
        layers: vec![
            Layer { start: 0.0, duration: 10.0, z: 0,
                    frame: Frame { color: (0, 0, 255, 255), name: "background" } },
            Layer { start: 2.0, duration: 5.0, z: 1,
                    frame: Frame { color: (255, 0, 0, 255), name: "action" } },
            Layer { start: 5.0, duration: 3.0, z: 2,
                    frame: Frame { color: (255, 255, 255, 255), name: "subtitle" } },
        ],
    };
    for t in [0.0, 1.0, 3.0, 5.5, 7.5, 9.0] {
        let frames = cs.render(t);
        let names: Vec<&str> = frames.iter().map(|f| f.name).collect();
        println!("t={:.1}: active layers = {:?}", t, names);
    }
}
```

### 性能与扩展性

**Layer 数量上限**:casey 测试过 100 layer 同时活动,渲染时间增加 ~5ms(每 layer 几个 draw call)。1000 layer 时帧率明显下降。优化:同类型 layer 合批(layer batching),同 texture 的多个 layer 一次 draw call 画完。

**Cutscene 时长**:casey 测试过 1 小时长的 cutscene(极端情况),timeline keyframe 占内存 100KB,可接受。如果 keyframe 极多(100 万个),改成 stream load(按需加载当前时间段附近的 keyframe)。

**热重载支持**:cutscene 数据改了,热重载后立即看到新效果,不重启游戏。casey 的 GUID-based expanded state 让用户展开状态在热重载后保留。

## 10 · 深入:游戏过场动画的工业级实现

casey 今天开始的多层过场动画系统,是现代游戏引擎里"timeline"子系统的雏形。让我们把工业级 timeline 系统的设计要点列出来,你会看到 casey 的设计如何 scale 到商业项目。

### 10.1 timeline 的核心数据结构

游戏 timeline 的工业实现通常这样:

```rust
struct Timeline {
    duration: f32,                  // 总时长(秒)
    tracks: Vec<Track>,             // 多个并行的轨道
}

struct Track {
    name: String,                   // "Camera", "Audio", "Light"
    target: EntityId,               // 影响哪个 entity
    clips: Vec<Clip>,               // 时间段内的内容
}

struct Clip {
    start_time: f32,
    end_time: f32,
    blend_in: f32,                  // 淡入时长
    blend_out: f32,                 // 淡出时长
    kind: ClipKind,                 // 动画 / 音频 / 事件 / 信号
}

enum ClipKind {
    Animation { skeleton: AssetHandle<Skeleton>, anim: AssetHandle<Animation> },
    Audio { sound: AssetHandle<Sound>, loop_: bool },
    Event { name: String, payload: serde_json::Value },
    Signal { property: String, curve: AnimationCurve },
}
```

casey 的实现简化版:
- Track → "过场动画层"
- Clip → "层上的 keyframe 段"
- ClipKind → 只有"数值曲线"和"事件触发"两种

casey 的简化让他能在一集视频里讲完。商业引擎(Unity Timeline、Unreal Sequencer)的完整数据结构要复杂 10 倍。

### 10.2 多层混合的算法

casey 这集讲"多层过场动画",即多个 timeline 同时播放,最终值要混合。算法选项:

**Override(覆盖)**:最后一层的值赢。
```rust
let value = layers.last().unwrap().sample(time);
```

**Additive(叠加)**:每层的 delta 累加。
```rust
let mut value = base_value;
for layer in &layers {
    value += layer.sample(time);
}
```

**Blend with weight(加权混合)**:每层有权重,加权平均。
```rust
let total_weight: f32 = layers.iter().map(|l| l.weight).sum();
let value = layers.iter()
    .map(|l| l.sample(time) * l.weight)
    .sum::<f32>() / total_weight;
```

**Priority blend(优先级)**:高优先级 override,低优先级填空缺。
```rust
let mut value = None;
for layer in layers.iter().rev() {  // 从低到高优先级
    if let Some(v) = layer.sample_optional(time) {
        value = Some(v);
    }
}
```

casey 在 HH 视频里讨论这些混合模式,最终选 priority blend——上层(用户编辑器输入)优先,下层(cutscene 自动播放)填空缺。这是 debug overlay 的典型需求。

### 10.3 Unity Timeline 的实现

Unity 2017+ 引入 Timeline,数据结构类似:

```csharp
// Unity C# 公开 API(简化)
public class TimelineAsset : PlayableAsset {
    public TrackAsset[] outputs;
    public double duration;
}

public class AnimationTrack : TrackAsset {
    public AnimationClip[] clips;
    public AvatarMask avatarMask;
}

public class AnimationPlayableOutput : PlayableOutput {
    public Animator sourceObject;
}
```

Unity Timeline 的设计要点:
1. **Playable Graph**:每个 timeline 是一个有向图,node 是 Playable,edge 是数据流。运行时帧帧求值,casey 的多层也是这个思路。
2. **Track 类型化**:AnimationTrack、AudioTrack、ActivationTrack、SignalTrack,每种 track 处理特定领域。
3. **Director component**:`PlayableDirector` 组件挂在 GameObject 上,驱动 timeline 播放。

### 10.4 Unreal Sequencer 的实现

Unreal 的 Sequencer(替代旧 Matinee):

```cpp
class ULevelSequence : public UMovieSceneSequence {
    UMovieScene* MovieScene;
}

class UMovieScene {
    TArray<UMovieSceneTrack*> Tracks;
}

class UMovieSceneAnimationTrack : public UMovieSceneTrack {
    TArray<UMovieSceneSection*> AnimationSections;
}
```

Sequencer 设计要点:
1. **Section-based**:每段是独立 Section,可重叠(blend)。
2. **Property binding**:Track 通过 Unreal reflection 系统(FProperty)绑定到任意 UPROPERTY。
3. **C++ blueprint hybrid**:可在 Sequencer UI 拖拽,也可 C++ 代码创建。

### 10.5 casey 设计的 trade-off

casey 简化的设计:
- 单一数据类型(f32 数值)
- 无 reflection,手写绑定
- 无 UI 编辑器,数据直接代码定义

适合:**debug overlay 的简单动画**。不适合:**过场动画导演工具**(那个要 UI 编辑器、复杂 timeline、多轨道)。

如果你想做商业游戏的 cutscene 系统,casey 的代码可以学,但生产要用 Unity Timeline / Unreal Sequencer。casey 的目的是教学——理解原理,你能看懂商业引擎的设计选择。

### 10.6 Rust 生态的 timeline

Rust 没有专门的"游戏 timeline"crate,但有相关:

**bevy_tweening**:补间动画库,但不是完整 timeline。
**keyframe**:关键帧动画,可做 cutscene 基础。
**talent / wgpu-timeline**:实验性 timeline 库。

casey 的 HH Rust 翻译版如果要 cutscene,通常手写或基于 keyframe crate 扩展。

### 10.7 timeline 系统的测试策略

测试 timeline 系统时要注意几个易错点:

**1. 时间精度**。f32 时间在长 cutscene 下累积误差。10 分钟 cutscene = 600 秒,f32 精度 ~7 位有效数字,1/10^7 误差 = 60μs。在 keyframe 边界(精确触发),60μs 误差可能让 keyframe 错过。解决:用 f64 存时间,或每帧从 game_clock 重新计算 cutscene time。

**2. 倒放支持**。timeline 倒放需要每个 keyframe 提供 inverse interpolation。线性 keyframe 自然支持;bezier / cubic 需要 explicit inverse 函数。casey 的简化版本不要求倒放,生产 timeline 要。

**3. 暂停 / 跳转**。timeline 跳到任意时间,需要重新计算所有"累积"状态(比如粒子已经在播放中途)。casey 的简单数值 timeline 不涉及,但音频 / 动画 timeline 必须处理。

**4. 循环**。timeline 循环播放,要决定 keyframe 边界是 [start, end) 还是 [start, end]。选错会导致跳变。casey 选 [start, end) 半开区间,跳变避免。

这些是实战项目里的 timeline bug 常见来源。学完 casey 的基础版本,你看 Unity / Unreal timeline 的"为什么这样设计"就有判断力。
