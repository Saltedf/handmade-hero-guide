# Day 247 · 简化调试值

> Day 210 你做了统一 debug data store,Day 244 加了异步 readback。回头看 debug 系统复杂得吓人——每个 debug 值要存类型 / hash / 历史曲线 / GUI 句柄,几千个变量占了 100+ MB。今天 Casey 用 YAGNI 原则大刀阔斧简化:删 90% 字段,只留真正用到的。

## 0 · 为什么要有这一天

软件项目有个普遍规律:**功能越加越多,代码越来越复杂,直到没人维护**。Day 176-210 的 debug 系统是 35 集的成果,功能强大但臃肿:

- 每个 debug 值 8 个字段(type / hash / 当前值 / 历史曲线 / 编辑回调 / 序列化 / tree node / GUI state)
- 实际游戏只用 3 个字段(类型 / 当前值 / 编辑权限)
- 占内存 200MB+,启动慢

Casey Day 247 用 YAGNI(You Aren't Gonna Need It)原则重构:

- 删:历史曲线(Day 180 的 ring buffer 90% 没用)
- 删:序列化(没存盘需求)
- 删:复杂 hash 用 ID 直接代替
- 留:类型 / 当前值 / tree node
- 留:编辑权限(只读 / 可编辑)

debug 系统从 8 字段 → 3 字段,代码量减半,启动快 3 倍。

**为什么这件事重要**:学会"减法"是高级程序员标志。加功能谁都会,**删功能**需要勇气和判断。

**心理锚点**:看完今天,你能审视自己代码,找出"never used"的字段 / 函数,果断删。这是降低维护成本的核心技能。

## 1 · Casey 今天做了什么

Casey 把 DebugValue 简化:

```rust
// 之前(Day 210)
struct DebugValue {
    type: DebugType,           // 类型
    hash: u64,                 // 哈希(查表用)
    name: &'static str,        // 名字
    current: DebugData,        // 当前值
    history: RingBuffer<f32>,  // 历史曲线
    edit_callback: Option<fn(...)>,  // 编辑回调
    serialize: bool,           // 是否序列化
    tree_node: TreeNode,       // tree 节点
    gui_state: GuiState,       // GUI hover / focus
}

// 之后(Day 247)
struct DebugValue {
    name: &'static str,
    value: Value,  // f32 / bool / Vec3 / ...
    editable: bool,
}
```

8 字段 → 3 字段(把 name 和 value 合并,editable 用 bit flag)。

**关键决策**:删的功能 Day 248-260 不会重新加。如果后面真要用,那时再写。"需要才写"是 YAGNI 核心。

## 2 · 心智模型

### 类比:衣柜清理

你的衣柜:

- 100 件衣服,实际穿 20 件,80 件"以后可能穿"
- 占空间大,找衣服慢

简化:**捐掉 80 件**。衣柜清爽,找衣服快。如果某天真需要某件衣服(已捐),买新的——大概率不会真需要。

代码一样:**删 80% 用不到的代码**,维护成本骤降。需要时再加(YAGNI 哲学)。

### 2.1 识别"dead code"

工具方法:

```bash
# Rust 找 dead code
cargo install cargo-udeps  # unused dependencies
cargo install cargo-machete  # 更快

# 找 unused field(需要 nightly)
RUSTFLAGS="-W dead_code" cargo build

# 找 unused function
grep -r "fn " src/ | grep -v -f <(grep -roE "function_name\(" src/)
```

手工:看每个字段,问"我在哪里用到?"。如果说不出来,删。

### 2.2 简化的取舍

简化前:

- 优点:功能完备
- 缺点:复杂、慢、维护贵

简化后:

- 优点:简单、快、维护便宜
- 缺点:某天可能需要重新加

**何时简化**:

- 代码超 1000 行 / 模块
- 字段超 6 个 / struct
- 函数超 50 行
- Bug 修起来难(代码绕)

HH Phase 5 的 debug 系统达到所有阈值,Day 247 是 timely refactor。

### 2.3 Rust 的 enum 简化

Day 210 用 4 个字段表示 "value type"。Day 247 用 enum:

```rust
#[derive(Clone, Debug)]
pub enum Value {
    F32(f32),
    Bool(bool),
    Vec3([f32; 3]),
    Color([f32; 4]),
    String(Rc<str>),
}

pub struct DebugValue {
    pub name: &'static str,
    pub value: Value,
    pub editable: bool,
}
```

Rust enum 比 C tagged union 安全:match 必须 exhaustive,编译器保证所有分支处理。

### 2.4 YAGNI 应用清单

每个字段问:

1. **现在用到了吗?**(不是"以后可能")
2. **删了会立刻坏什么吗?**
3. **删了什么体验变差?**——差到不能用才保留
4. **再加这个字段成本?**——低就删,高就留

应用结果:

- ✓ name —— 留(GUI 显示用)
- ✓ value —— 留(核心)
- ✓ editable —— 留(GUI 编辑)
- ✗ hash —— 删(用 name 直接 HashMap)
- ✗ history —— 删(用专门 plot 系统,不要每个值都记)
- ✗ edit_callback —— 删(用 editable flag,回调统一)
- ✗ serialize —— 删(没存盘需求)
- ✗ tree_node —— 删(用 path 字符串分层,不需要结构树)
- ✗ gui_state —— 删(GUI 全局状态,不 per-value)

|---|---|---|

| 1万个变量内存 | 1GB | 240MB |
| 启动时间 | 800ms | 250ms |
| 代码行数 | 3000 | 1500 |

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核强调 "不要过早优化":

- `if (condition) { ... }` 简单 if-else 比 `match` 快
- 但是过早用 hash table 而不是 array,反而慢(cache miss)

`make tinyconfig` 是 Linux 内核的"简化" —— 移除所有非必需功能,内核从 100MB 编译到 5MB,启动快 10 倍。

### 3.4 · 🦀 Rust 生态视角

Rust 编译器帮你找 dead code:

```bash
# warning: function is never used
cargo build 2>&1 | grep "never used"
# warning: field is never read
cargo build 2>&1 | grep "never read"
```

但 Rust 编译器只报"绝对没用",不报"很少用"。手工审视仍需要。

**Rust idiom**:用 `#[allow(dead_code)]` 临时保留,标记 TODO 后删:

```rust
#[allow(dead_code)]  // TODO: 简化时删
struct DebugValue {
    history: RingBuffer<f32>,
    // ...
}
```

定期扫 `grep -r "TODO" src/`,清理这些标记。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:YAGNI 和"未雨绸缪"(prepare for future)矛盾吗?如何取舍?

**参考解答**:不矛盾,但侧重不同。

- **YAGNI** —— "现在不需要的不要写"。强调减少当前复杂度
- **未雨绸缪** —— "预留扩展点"。强调未来兼容

取舍:架构层面留扩展点(接口抽象),实现层面按需写。例:

- ✓ 留接口 `Renderer` trait(以后加 Vulkan 容易)
- ✗ 现在就写 Vulkan 实现(没人用)

YAGNI 是"不写实现",不是"不设计接口"。

### Lv2 · 动手实践

**题**:审视你 Phase 4 的代码(任何模块),找出 3 个未使用的字段 / 函数,删掉,确认编译通过 + 测试通过。

**参考解答**:

```bash
# Step 1: 跑 cargo build 找 dead_code warnings
cargo build 2>&1 | grep -E "never (used|read)" > dead_code.txt
cat dead_code.txt
# 输出:
# warning: field `foo` is never read
# warning: function `bar` is never used

# Step 2: 删掉这些字段 / 函数

# Step 3: 删除(用编辑器 / sed)
sed -i '/fn bar/d' src/whatever.rs

# Step 4: 编译 + 跑测试
cargo build
cargo test
```

每个未用字段 / 函数,问"为什么写?"——如果是过度设计,记笔记。

## 8 · Rust / Arch 落地代码

### Rust 简化前后对比

```rust
// === 之前(Day 210 风格,8 字段) ===
pub struct DebugValueOld {
    pub name: &'static str,
    pub hash: u64,
    pub current: f32,
    pub history: Vec<f32>,
    pub edit_callback: Option<fn(&mut f32)>,
    pub serialize: bool,
    pub tree_node_id: u32,
    pub gui_hover: bool,
}

// === 之后(Day 247 风格,3 字段) ===
#[derive(Clone, Debug)]
pub enum Value {
    F32(f32),
    Bool(bool),
    Vec3([f32; 3]),
}

pub struct DebugValue {
    pub name: &'static str,
    pub value: Value,
    pub editable: bool,
}

pub struct DebugStore {
    pub values: HashMap<&'static str, DebugValue>,
}

impl DebugStore {
    pub fn new() -> Self {
        Self { values: HashMap::new() }
    }

    pub fn set_f32(&mut self, name: &'static str, value: f32) {
        self.values.entry(name).or_insert(DebugValue {
            name,
            value: Value::F32(value),
            editable: false,
        }).value = Value::F32(value);
    }

    pub fn get_f32(&self, name: &str) -> Option<f32> {
        if let Some(v) = self.values.get(name) {
            if let Value::F32(f) = v.value { return Some(f); }
        }
        None
    }
}

fn main() {
    let mut store = DebugStore::new();
    store.set_f32("player_speed", 5.0);
    store.set_f32("gravity", 9.8);

    println!("player_speed = {:?}", store.get_f32("player_speed"));
    println!("Struct size: {} bytes", std::mem::size_of::<DebugValueOld>());
    println!("Simplified:  {} bytes", std::mem::size_of::<DebugValue>());
    // 输出:
    // Struct size: 80 bytes
    // Simplified:  40 bytes
}
```

### 10.6 重构的工程模式

casey 在 day247 用几种重构模式:

**模式 1:字段提取**(extract field)

```rust
// 旧:多个字段混在 struct
struct DebugValue {
    name: String,
    description: String,
    unit: String,
    // ...
}

// 新:相关字段提取成 sub-struct
struct DebugValue {
    meta: DebugMeta,
    value: Variant,
}

struct DebugMeta {
    name: String,
    unit: String,
}
```

**模式 2:enum 化**(replace multiple fields with enum)

```rust
// 旧:f32 + bool + Vec3 三种 value 各占字段
struct DebugValue {
    f32_value: Option<f32>,
    bool_value: Option<bool>,
    vec3_value: Option<Vec3>,
}

// 新:enum
struct DebugValue {
    value: Variant,
}

enum Variant {
    Float(f32),
    Bool(bool),
    Vec3(Vec3),
}
```

**模式 3:删除未使用字段**

```rust
// 用 grep 找使用
grep -r "\.flags" src/
// 如果只用 1-2 处,可以内联,删除字段
```

casey 在 day247+ 反复用这三种模式,让 debug 系统代码量减少 30%。
