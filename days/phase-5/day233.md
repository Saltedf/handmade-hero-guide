# Day 233 · 归并排序能原地做吗?

> Merge sort 简单清晰、稳定 O(n log n),但需要 O(n) 额外空间。能不能省掉?今天 casey 探讨原地归并 (in-place merge sort) 的可能性,以及为什么它在工业界很少用。

## 0 · 为什么要有这一天

Day 232 的 merge sort 用了 `Vec::with_capacity(n)` 作为临时空间。对于 n = 1M 元素,需要额外 8MB(i32)或 80MB(大 struct)。嵌入式 / 内存紧张场景这不可接受。

**问题**:能不能不用额外空间?

直觉:不可能——merge 两个有序数组时,合并结果往哪里写?如果原地写,会覆盖未合并部分。

**事实**:**理论可能,但常数巨大**。原地归并排序存在,但比标准 merge sort 慢 5-10 倍。工业界基本不用,直接接受 O(n) 空间代价。

casey 今天探讨这个 tradeoff:**理论 vs 实际,简洁 vs 复杂**。最终结论:工业用 O(n) 空间换 O(n log n) 时间 + 简洁实现,值得。

心理锚点:看完今天,你能识别"理论最优不等于实际最优"的案例,做工程决策。

## 1 · Casey 今天做了什么

1. **回顾 merge sort 的空间需求**:O(n) 临时 buffer
2. **介绍 in-place merge 算法**:复杂、慢
3. **对比常数因子**:in-place 慢 5-10 倍
4. **结论**:不值得,接受 O(n) 空间

## 2 · 心智模型

### 类比:搬家时的临时仓库

merge 两个有序堆:把左边和右边的物品合并成一堆。如果只有目的地(没临时仓库),要怎么办?

- 标准 merge:借个临时仓库,把两堆合并到临时仓库,再整体搬回原地
- In-place merge:不借仓库,用各种"翻转 / 旋转"技巧在原地交换

不借仓库的搬家更难、更慢,但省仓库成本。

### 2.1 标准 merge 为什么用 O(n) 空间

```rust
fn merge(arr: &mut [i32], mid: usize) {
    let mut merged = Vec::with_capacity(arr.len());
    let (mut i, mut j) = (0, mid);
    while i < mid && j < arr.len() {
        if arr[i] <= arr[j] { merged.push(arr[i]); i += 1; }
        else { merged.push(arr[j]); j += 1; }
    }
    // ... 把 merged 写回 arr
}
```

`merged` 是临时 buffer。如果不用它,直接写到 `arr`,会覆盖未比较的元素。

### 2.2 In-place merge 的思路

不用临时 buffer,用 **array rotation**(数组旋转)。

定义:rotate(arr, mid) = 把 arr[..mid] 和 arr[mid..] 位置交换。

```
[a b c | d e f] rotate → [d e f | a b c]
```

merge 用 rotate:

```
原: [1 3 5 | 2 4 6]
比较 1 和 2,1 小。i++
原: [1 3 5 | 2 4 6]
比较 3 和 2,2 小。需要把 2 移到 3 前面。
rotate [3 5 2] → [2 3 5]
原: [1 2 3 5 4 6]
...
```

但 rotate 本身是 O(k)(k 是 rotate 长度),总复杂度变 O(n²)。理论 O(n log n) 但常数大。

### 2.3 更聪明的 in-place merge

**Kronrod 算法**(1969):用 sqrt(n) 额外空间,做 in-place merge,O(n log n) 时间。但实现极复杂,常数大。

**更优算法**(2017):真正的 O(n log n) 时间 O(1) 额外空间,但常数大于普通 merge sort 几倍。

casey 今天的结论:**理论可行,实际没用**。工业标准直接用 O(n) 空间。

### 2.4 工程权衡

| 因素 | 标准 merge | In-place merge |
|---|---|---|
| 时间复杂度 | O(n log n) | O(n log n) |
| 空间复杂度 | O(n) | O(1) |
| 实际速度 | 1x | 0.1-0.3x |
| 代码复杂度 | 简单 | 复杂 |
| 稳定性 | 易实现 | 难 |

工业选标准 merge:**简洁 + 快**,空间 8MB 在现代机器无感。

### 2.5 Quicksort 的优势

quicksort 是另一种思路:**几乎原地**。

```
partition 原地,O(1) 额外空间(除递归栈 O(log n))
整体 O(log n) 额外空间(递归调用栈)
```

这是为什么 quicksort 比 merge sort 更流行——空间少,常数小。

casey Day 232 的 quicksort 实现已经是 in-place(只递归栈)。

### Lv2 · 动手实践

**题**:实现 array rotation,然后写一个简单(虽然 O(n²))的 in-place merge。对比性能。

**参考解答**:

```rust
fn rotate(arr: &mut [i32], mid: usize) {
    // [a b c | d e f] → [d e f | a b c]
    // 用三次 reverse
    arr[..mid].reverse();
    arr[mid..].reverse();
    arr.reverse();
}

fn in_place_merge(arr: &mut [i32], mid: usize) {
    let (mut i, mut j) = (0, mid);
    while i < j && j < arr.len() {
        if arr[i] <= arr[j] {
            i += 1;
        } else {
            // 把 arr[j] 移到 arr[i] 位置,rotate [i..=j]
            rotate(&mut arr[i..=j], j - i);
            i += 1;
            j += 1;
        }
    }
}

fn in_place_merge_sort(arr: &mut [i32]) {
    if arr.len() <= 1 { return; }
    let mid = arr.len() / 2;
    in_place_merge_sort(&mut arr[..mid]);
    in_place_merge_sort(&mut arr[mid..]);
    in_place_merge(arr, mid);
}

fn main() {
    let mut a = vec![1, 3, 5, 2, 4, 6];
    in_place_merge(&mut a, 3);
    println!("{:?}", a);  // [1, 2, 3, 4, 5, 6]

    let mut b = vec![5, 3, 8, 1, 9, 2, 7, 4, 6];
    in_place_merge_sort(&mut b);
    println!("{:?}", b);
}
```

注意:这个 in-place merge 是 O(n²),仅作教学。真正的 O(n log n) in-place merge 需要复杂技巧。

## 10 · 深入:原地 merge sort 的算法挑战

casey 在 day233 讨论"merge sort 能否原地"——这是经典算法挑战。让我们把它彻底讲透。

### 10.1 标准 merge sort 的空间问题

标准 merge sort 需要 O(n) 额外空间(临时 merge 数组):

```rust
fn merge_sort<T: Clone>(arr: &mut [T]) {
    if arr.len() <= 1 { return; }
    let mid = arr.len() / 2;
    merge_sort(&mut arr[..mid]);
    merge_sort(&mut arr[mid..]);
    
    // 需要 O(n) 临时数组
    let mut temp: Vec<T> = Vec::with_capacity(arr.len());
    let (mut i, mut j) = (0, mid);
    while i < mid && j < arr.len() {
        if arr[i] <= arr[j] {
            temp.push(arr[i].clone());
            i += 1;
        } else {
            temp.push(arr[j].clone());
            j += 1;
        }
    }
    // ... copy back
}
```

`temp` 数组占 O(n) 内存。对 100万元素,8 MB 额外内存。

### 10.2 原地 merge 的核心难题

为什么 merge 难以原地?merge 时两个有序段(L 和 R),输出位置可能重叠:

```
[L0, L1, L2, L3, R0, R1, R2, R3]  ← 排序前
      ↑ merge 后,L 和 R 的元素交错
```

如果 L1 > R0,R0 要去 L1 位置,但 L1 还没被读。覆盖就丢数据。

### 10.3 三种原地 merge 算法

**1. Block swap**(Knuth 算法)

把 L 的最后一个 block 和 R 的对应 block 交换。复杂但 O(n²) 最坏。

**2. In-place merge with rotation**

```
[L1, L2, R0, R1]  ← L1 > R0
       ↓ rotate
[R0, L1, L2, R1]  ← R0 到位,继续处理 L1 R1
```

每次找到正确位置,旋转数组。O(n²) 最坏,O(n log n) 平均(配合 binary search)。

**3. Stable in-place merge**(复杂)

学术论文级算法,O(n log n) 时间,O(1) 空间,稳定。代码复杂,生产很少用。

### 10.4 casey 的结论:不值得

casey 在 day233 测试三种算法,结论:**原地 merge sort 不值得**。

理由:
- 标准 merge sort O(n) 空间,实际只多 8 MB / 100万元素
- 原地 merge 复杂度高,常数大,实际更慢
- std sort(merge sort 变种)用 O(n) 空间,够用

casey 推荐:**接受 O(n) 空间换 O(n log n) 时间 + 稳定性**。

### 10.5 工业实现:Rust std 的 stable sort

Rust `slice::sort` 用 **Timsort** 的变种:

- 数据分"run"(已排序段)
- run 间用 merge sort
- 小 run 用 insertion sort 扩展
- merge 时用 O(n/2) 临时空间(优化)

平均 O(n log n),最坏 O(n log n),稳定,O(n/2) 空间。

### 10.6 替代方案:放弃稳定性

如果不要求稳定,用 `sort_unstable`(pdqsort)——O(1) 空间,O(n log n) 时间。

```rust
arr.sort_unstable();  // 0 额外内存
```

casey 在 day233 强调:**很多场景不需要稳定性**,用 unstable 更高效。

### 10.7 教学总结

day233 的核心要点:

1. **merge sort 难以真正原地**:学术算法复杂
2. **O(n) 空间可接受**:几 MB 内存换稳定性
3. **Rust std 已优化**:Timsort 变种
4. **不要求稳定性时用 unstable**:pdqsort 更快
5. **casey 推荐 radix for 整数**:O(n) 时间,O(n) 空间

day233 是排序系列的"边界探索"——讨论算法的极限,得出"够用就好"的工程结论。

## 11 · 深入:Timsort 与现代排序

casey 在 day233 讨论的是基础 merge sort,生产实际用 Timsort(2002 年 Tim Peters 发明,Python / Java 用)。让我们讲清楚。

### 11.1 Timsort 的核心思想

Timsort 观察:**真实数据通常已部分有序**。利用这点加速。

算法:

1. **找 run**:扫描数据,找已排序的连续段(升序或降序)
2. **扩展 run**:用 insertion sort 把 run 扩展到最小长度(通常 32-64)
3. **合并 run**:类似 merge sort,但用栈管理 run,根据 invariant 决定何时合并

```
[5, 1, 4, 2, 3, 6, 8, 7]
   ↓ 识别 run
run1: [5]
run2: [1, 4]  (升序)
run3: [2, 3, 6, 8]  (升序)
run4: [7]
   ↓ insertion sort 扩展 run1, run4
   ↓ merge
最终: [1, 2, 3, 4, 5, 6, 7, 8]
```

### 11.2 Timsort 的性能

- **已部分有序数据**:接近 O(n)(只 merge,不重排)
- **随机数据**:O(n log n)
- **最坏**:O(n log n)(guaranteed)
- **空间**:O(n/2)(merge 时临时)
- **稳定性**:稳定

Timsort 在真实数据上比标准 merge sort 快 2-3 倍,因为利用了数据的"部分有序性"。

### 11.3 Rust std 的 stable sort

Rust `slice::sort` 用的是 Timsort 变种:

```rust
let mut arr = vec![5, 1, 4, 2, 3];
arr.sort();  // Timsort
```

实际是 `slice::sort` 内部的"merge sort + insertion sort + galloping"组合。性能比纯 merge sort 快 2 倍。

### 11.4 pdqsort 的对比

Rust `slice::sort_unstable` 用 pdqsort:

- **pattern-defeating**:检测数据模式(全相等、已排序、反向),特化处理
- **quicksort 主体**:平均 O(n log n)
- **insertion sort 小 n**:n < 24 切换
- **heapsort fallback**:检测 bad pivot,切到 heapsort 防 O(n²)

pdqsort 比 Timsort 快 ~30%(因为不要求稳定),但 Timsort 在部分有序数据上更快。

### 11.5 casey 选择 radix 的理由

casey 在 day234 实现 radix sort,因为:

1. **sort key 是 u64**:radix 完美适用
2. **O(n) 时间**:比 Timsort/pdqsort 的 O(n log n) 快
3. **教学价值**:学生看到"突破比较下界"的算法
4. **HH 项目规模**:10000+ 元素,radix 显著快

casey 不用 Timsort 因为它复杂(几百行代码),radix 简洁(几十行)且 casey 场景下更快。

### 11.6 工业级选择

商业项目排序选择:

| 场景 | 选择 |
|---|---|
| 通用对象排序 | Rust std `sort` / `sort_unstable` |
| 整数 key + 大数据 | 自定义 radix sort |
| 已部分有序数据 | Timsort(用 std sort) |
| 不要求稳定 + 速度优先 | pdqsort(用 sort_unstable) |
| 极致性能 + GPU | GPU radix sort |

casey 的 day234 radix 适合"整数 key + 大数据"场景。其他场景用 std。

## 12 · 深入:排序算法的工程实战补充

最后,补充几个排序的工程细节。

### 12.1 sort key 的复合比较

某些场景 sort key 是复合的(多字段)。两种实现:

```rust
// 方式 1:tuple,自然字典序
arr.sort_by_key(|x| (x.layer, x.texture, x.depth));

// 方式 2:手动比较
arr.sort_by(|a, b| {
    a.layer.cmp(&b.layer)
        .then(a.texture.cmp(&b.texture))
        .then(b.depth.cmp(&a.depth))  // 反向
});
```

casey 的 day233 强调:**用 tuple 更简洁**,但 bit-encoded u64 更快(单次比较)。生产根据场景选。

### 12.2 sort 与 stable_sort 的 API 差异

Rust:

```rust
slice::sort                       // 稳定
slice::sort_unstable              // 不稳定,更快
slice::sort_by                    // 稳定,自定义比较
slice::sort_unstable_by           // 不稳定
slice::sort_by_key                // 稳定,自定义 key 提取
slice::sort_unstable_by_key       // 不稳定
```

6 个变体。生产项目按"是否需要稳定"选。

### 12.3 排序的 iterator 友好

Rust 不提供 sort iterator(`sorted()` 在 Vec 上,不 lazy):

```rust
// 错:没有 sorted_iter()
// for x in some_iter.sorted() { ... }

// 对:先 collect 再 sort
let mut v: Vec<_> = some_iter.collect();
v.sort();
```

Haskell / Python 有 lazy sort iterator,Rust 没有(数据所有权复杂)。

### 12.4 排序与并行

```rust
use rayon::prelude::*;

// 并行 sort
arr.par_sort_unstable();

// 并行 sort by key
arr.par_sort_unstable_by_key(|x| x.sort_key);
```

### 12.10 排序的极限探索

排序算法是计算机科学的"经典难题",几十年研究:

- **1950s**:bubble sort、insertion sort(基础)
- **1960s**:quicksort(Hoare)、merge sort、heapsort(Williams)
- **1970s**:理论分析(比较下界 O(n log n) 证明)
- **1980s**:radix sort 复兴(基于关键值的非比较排序)
- **1990s**:introsort(musser,quicksort + heapsort)
- **2000s**:Timsort(Peters,Python)
- **2010s**:pdqsort(Orson Peters,Rust 用)
- **2020s**:GPU sort、parallel sort、AI 加速 sort

### 12.11 排序算法的数学美

排序算法有很多数学美:

- **比较下界**:N! 种排列,log2(N!) ≈ N log N 比较才能区分
- **Stirling 近似**:log2(N!) = N log N - N log e + O(log N)
- **Quicksort 期望**:E[T] = 2(N+1)H_N - 4N,H_N 是 harmonic number
- **Heapsort 上界**:T ≤ 2N log N + O(N)
