
# Day 230 · 精化渲染器排序键

> Day 229 的 sort key 是初版。实际使用中发现需求增长:shader 切换、blend mode、viewport scissor。今天 casey 扩展 sort key,加入更多字段,精化排序粒度。

## 0 · 为什么要有这一天

Day 229 的 sort key 只考虑 layer + depth + texture。但 GPU 状态不止这些:

- **Shader 程序**:切换 `glUseProgram` 开销大(~微秒级)
- **Blend mode**:alpha blend / additive / opaque 切换
- **Stencil / depth test**:启用 / 禁用切换
- **Scissor rect**:裁剪区域切换
- **Viewport**:视图区域切换

每个状态切换都耗时。最优 sort key 应该让相同状态的 element 连续画。

casey 今天的方案:**精化 sort key**,把 shader / blend / depth-test 也编码进去。

新布局:

```
bits  63-56: layer
bits  55-48: blend_mode
bits  47-40: shader_id
bits  39-32: depth_test_mode
bits  31-16: depth_value
bits  15-0:  texture_id + sub
```

更多字段 → 切换更少 → 性能更高。代价:sort key 比较的位更多(但仍然 O(1))。

心理锚点:看完今天,你能识别"渲染瓶颈来自哪里"(shader 切换?纹理切换?),并优化 sort key 减少切换。

## 2 · 心智模型

### 类比:邮编 vs 详细地址

Day 229 的 sort key 像邮编——粗糙但快。今天的精化版像详细地址(省 + 市 + 区 + 街道 + 门牌)——精细,能更准确分组。

邮编排序:同邮编的邮件混在一起。详细地址排序:同街道的邮件挨着,投递顺序最优。

GPU 状态:同 shader + 同 blend + 同 texture 的 element 连续画,切换最少。

### 2.1 完整 SortKey

```rust
struct SortKey(u64);

impl SortKey {
    const LAYER_SHIFT: u32 = 56;
    const BLEND_SHIFT: u32 = 48;
    const SHADER_SHIFT: u32 = 40;
    const DEPTH_TEST_SHIFT: u32 = 32;
    const DEPTH_SHIFT: u32 = 16;
    const TEXTURE_SHIFT: u32 = 0;

    fn new(
        layer: u8, blend: u8, shader: u8,
        depth_test: u8, depth: u16, texture: u16,
    ) -> Self {
        let key = ((layer as u64) << Self::LAYER_SHIFT)
            | ((blend as u64) << Self::BLEND_SHIFT)
            | ((shader as u64) << Self::SHADER_SHIFT)
            | ((depth_test as u64) << Self::DEPTH_TEST_SHIFT)
            | ((depth as u64) << Self::DEPTH_SHIFT)
            | (texture as u64);
        Self(key)
    }
}
```

每个字段 8 或 16 bit,刚好填满 64 bit。

### 2.2 Blend mode 排序

blend mode 重要:opaque (no blend) 比 alpha blend 快,additive 又有不同表现。casey 把 blend 也编码进 key:

```rust
const BLEND_OPAQUE: u8 = 0;
const BLEND_ALPHA: u8 = 1;
const BLEND_ADDITIVE: u8 = 2;
const BLEND_MULTIPLY: u8 = 3;
```

同 blend 的连续画,GPU 不必反复切换 blend state。

### 2.3 Shader 排序

切换 shader 在 GPU 上慢(重新上传 uniforms、重设 rasterizer)。同 shader 的 element 应该连续画。

casey 给每个 shader 分配 shader_id:

```rust
const SHADER_SPRITE: u8 = 0;
const SHADER_TEXT: u8 = 1;
const SHADER_PARTICLE: u8 = 2;
const SHADER_POSTPROCESS: u8 = 3;
```

### 2.4 性能验证

加 profiling:

```rust
struct FrameStats {
    draw_calls: usize,
    texture_binds: usize,
    shader_binds: usize,
    blend_changes: usize,
}

fn render(elements: &[Element], stats: &mut FrameStats) {
    let mut last_texture = !0;
    let mut last_shader = !0;
    let mut last_blend = !0;
    for e in elements {
        if e.texture_id != last_texture {
            stats.texture_binds += 1;
            last_texture = e.texture_id;
        }
        if e.shader_id != last_shader {
            stats.shader_binds += 1;
            last_shader = e.shader_id;
        }
        if e.blend != last_blend {
            stats.blend_changes += 1;
            last_blend = e.blend;
        }
        stats.draw_calls += 1;
    }
}
```

排序前 draw_calls = 1000, texture_binds = 1000(每次切)。排序后 draw_calls 不变, texture_binds = 10(同 texture 连续)。**纹理切换从 1000 降到 10**,100 倍改善。

### Lv2 · 动手实践

**题**:实现完整 SortKey + FrameStats,验证排序前后 batching 改善。

**参考解答**:

```rust
#[derive(Clone, Debug)]
struct Element {
    name: &'static str,
    layer: u8,
    blend: u8,
    shader: u8,
    depth: u16,
    texture: u16,
}

impl Element {
    fn sort_key(&self) -> u64 {
        ((self.layer as u64) << 56)
        | ((self.blend as u64) << 48)
        | ((self.shader as u64) << 40)
        | ((self.depth as u64) << 16)
        | (self.texture as u64)
    }
}

#[derive(Default)]
struct Stats {
    draw_calls: usize,
    texture_binds: usize,
    shader_binds: usize,
    blend_changes: usize,
}

fn render(elements: &[Element], stats: &mut Stats) {
    let mut last_tex = !0;
    let mut last_shader = !0;
    let mut last_blend = !0;
    for e in elements {
        if e.texture != last_tex { stats.texture_binds += 1; last_tex = e.texture; }
        if e.shader != last_shader { stats.shader_binds += 1; last_shader = e.shader; }
        if e.blend != last_blend { stats.blend_changes += 1; last_blend = e.blend; }
        stats.draw_calls += 1;
    }
}

fn main() {
    // 模拟 1000 个 element,100 个不同纹理,5 个 shader
    let mut elements: Vec<Element> = vec![];
    for i in 0..1000 {
        elements.push(Element {
            name: "elem",
            layer: (i % 3) as u8,
            blend: (i % 2) as u8,
            shader: (i % 5) as u8,
            depth: i as u16,
            texture: (i % 100) as u16,
        });
    }

    // 未排序
    let mut stats = Stats::default();
    render(&elements, &mut stats);
    println!("Unsorted: {:?}", stats);

    // 排序后
    elements.sort_by_key(|e| e.sort_key());
    let mut stats2 = Stats::default();
    render(&elements, &mut stats2);
    println!("Sorted:   {:?}", stats2);
    // 应该看到 texture_binds / shader_binds / blend_changes 大幅减少
}
```

## 10 · 深入:sort key 字段设计的工业级思考

casey 在 day230 精化 sort key 的字段位数——这是数据驱动设计的典范。让我把"如何决定字段位数"这件事彻底讲透。

### 10.1 字段位数的影响因素

sort key 每个字段多少 bit,取决于:

**1. 字段值的范围**。layer 8 个值?4 bit 够。texture 65536 个值?16 bit。depth 16M 个值?24 bit。

**2. 排序优先级**。优先级高的字段放高位(bit 56-63),低的放低位。

**3. 总位数限制**。casey 用 u64,总 64 bit。各字段加起来不能超。

**4. 未来的扩展性**。如果游戏未来要加更多 layer,留点 bit 余量。

### 10.2 casey 的精化路径

day229 初版(理论):

```
Layer(8) | Texture(16) | Depth(24) | Flags(16) = 64 bit
```

day230 精化(实测后):

```
Layer(4) | Texture(24) | Depth(28) | Flags(8) = 64 bit
```

变化:
- Layer 4 bit 够用(游戏实际 5-10 个 layer)
- Texture 24 bit(超过 65536 个材质)
- Depth 28 bit(更精确,1mm 精度可达 260km)
- Flags 8 bit(精简)

精化基于实际数据——casey 测试发现 texture 16 bit 不够(过千材质),layer 8 bit 浪费(只用了 5)。

### 10.3 字段位数的设计模式

工业级 sort key 字段设计:

**Layer / Pass**(4-8 bit):渲染 pass 影响最大,放最高位。Shadow / Forward / UI / Debug 等。

**Material / Shader**(16-32 bit):决定 batch,GPU state switch 的主要触发。中等位数。

**Depth**(24-32 bit):精细排序,大量值。

**Flags**(8-16 bit):透明 / wireframe / vertex color 等。

总位数:64 bit(简单)、128 bit(复杂)、不定长(数据驱动)。

### 10.4 不定长 sort key

商业引擎有时不用固定 bit key,而是动态计算:

```rust
struct SortKey {
    layer: u32,
    material: u32,
    depth: u32,
    flags: u32,
}

impl Ord for SortKey {
    fn cmp(&self, other: &Self) -> Ordering {
        self.layer.cmp(&other.layer)
            .then(self.material.cmp(&other.material))
            .then(other.depth.cmp(&self.depth))  // 反向,远的先画
            .then(self.flags.cmp(&other.flags))
    }
}
```

优点:灵活,易扩展。缺点:多次比较,慢。

casey 的固定 bit key 性能更好,但灵活性差。Trade-off。

### 10.5 casey 的反深度技巧

casey 的 depth 字段有个小技巧:**反向存储**。

正常 depth:小数字 = 近,大数字 = 远。
排序时:远的先画(painter's algorithm),按 depth 升序。

但 layer / texture 字段都是"升序排最高效"。如何统一?

casey 把 depth 取反:`key_depth = u32::MAX - depth`。这样 depth 大(远)→ key_depth 小(在 u64 高位)→ 排在前面。

```rust
fn make_key(layer: u8, texture: u32, depth: u32, flags: u8) -> u64 {
    let inverted_depth = u32::MAX - depth;
    // ...
}
```

这样所有字段都用"升序排",统一逻辑。casey 在 day230 反复强调这个技巧——简单的位操作可以避免复杂的特殊处理。

### 10.6 sort key 的版本演化

casey 在 day229-234 共 6 集里,sort key 经历 3 个版本:

- **v1 (day229)**:初步设计,bit 分配不合理
- **v2 (day230)**:精化 bit 分配,符合实际数据
- **v3 (day234)**:配合 radix sort,极致性能

每个版本都基于前一个的实测数据。这是工业级开发的典范——不一次性写完美,而是渐进式优化。

### 10.7 字段冲突的避免

sort key 字段间不能重叠。casey 在 day230 测试时遇到 bug——layer 和 texture 字段重叠,导致 texture 改变影响 layer。

```rust
// 错误:bit 重叠
let layer_mask = 0xFF;
let texture_mask = 0xFF00;  // 8 bit
// 总 16 bit,但 depth 字段也想用 bit 8-15

// 正确:每个字段独立
let layer_mask = 0xF000_0000_0000_0000;  // bit 60-63
let texture_mask = 0x0FFF_0000_0000_0000;  // bit 48-59
// ...
```

casey 用 const + assert 静态检查:

```rust
const LAYER_BITS: u32 = 4;
const TEXTURE_BITS: u32 = 24;
const DEPTH_BITS: u32 = 28;
const FLAGS_BITS: u32 = 8;

const _: () = assert!(LAYER_BITS + TEXTURE_BITS + DEPTH_BITS + FLAGS_BITS == 64);
```

编译时检查,字段不重叠。这是 Rust const evaluation 的好用法。

### 10.8 字段顺序的重要性

casey 在 day230 测试发现:**字段顺序影响性能 30%**。

```
Layer | Texture | Depth | Flags:最优(layer 切分明确,texture 大批)
Texture | Layer | Depth | Flags:差(texture 没切分 layer,频繁 switch)
Layer | Depth | Texture | Flags:中等(depth 排序后,texture 散布)
```

最优顺序:**变化最少的字段放高位**。layer 切几段(5-10),texture 在每段内切批(几十),depth 在每批内排序。从粗到细,逐层收敛。

casey 的设计就是这个顺序——layer > texture > depth > flags,从粗到细。

### 10.9 教学总结

day230 的核心要点:

4. **反 depth 技巧**:统一升序逻辑

## 11 · 深入:GPU 渲染的 batching 经济学

sort key 的最终目的是减少 GPU state switch。让我把"为什么 batch 重要"讲透。

### 11.1 GPU draw call 的开销

每次 draw call,GPU driver 要:

1. 验证 vertex buffer / index buffer
2. 设置 shader(pipeline state)
3. 绑定 texture / uniform buffer
4. 提交 draw command 到 GPU queue
5. GPU 执行

每步 ~1-10μs,总 ~50μs / draw call。CPU 单核每秒 20,000 个 draw call 是上限。

如果 10000 个 sprite 不 batch(10000 draw call),CPU 0.5s,完全卡。如果 batch 成 100 个(100 draw call),CPU 5ms,可接受。

### 11.2 batch 的触发条件

GPU 能 batch 的条件:

1. **相同 shader**:vertex / fragment shader 一致
2. **相同 texture**:GPU 不切 texture binding
3. **相同 vertex format**:顶点布局一致
4. **相同 blend mode**:alpha blend 设置一致
5. **相同 cull mode**:背面剔除设置一致

任何一个不同,batch 中断。

casey 的 sort key 把这些维度编码到 flags + texture 字段,排序后同 batch 条件的元素连续。

### 11.3 GPU profile 工具

实测 batch 效果用 GPU profiler:

```bash

# OpenGL:Nsight Graphics / gDEBugger
# Linux:Mesa overlay (VK_LAYER_MESA_overlay)
```

VK_LAYER_MESAoverlay 显示:

casey 在 day230 反复强调"先 measure 再 optimize"。GPU profile 数据告诉你 batch 是否有效。

### 11.4 静态 batching vs 动态 batching

**静态 batching**:把永远不变的几何合并成单个 vertex buffer。例子:静态地形、固定建筑。

**动态 batching**:每帧重新合并,casey 的 sprite 系统。透明物体每帧位置变,只能动态 batch。

casey 的 HH 用动态 batching(sprite)。商业引擎两者都用——静态地形 batch 一次,动态角色 batch 每帧。

### 11.5 instanced rendering

如果同一 mesh 绘制多次(树林、人群),用 **instanced rendering**:

```rust
// Vulkan / OpenGL instanced draw
vkCmdDrawIndexed(cmd, index_count, instance_count, ...);
```

单次 draw call,绘制 N 个 instance。GPU 内部根据 instance ID 复用 vertex shader。极致 batch。

casey 的 HH 不用 instancing(sprite 各异),但商业游戏大量用。学完 day230 sort key,你能理解 instancing 的更高层抽象。

### 11.6 GPU driven rendering

最现代的渲染:**所有 batch 在 GPU 上完成**。

```
1. CPU 上传原始 entity data
2. GPU compute shader:cull + sort + batch
3. GPU indirect draw:无需 CPU 介入,自动 batch
4. GPU 渲染
```

CPU 0 工作,draw call 数千个也不卡。Direct3D 12 / Vulkan 都支持。PS5 / Xbox Series X 主打。

casey 的 day230 是 CPU 侧 sort,GPU driven 是下一步。学完 day230,你能理解 GPU driven 的设计动机。

### 11.8 Rust 实战:用 casey 的 sort key 排序

完整 Rust 实现:

```rust
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
struct RenderSortKey(u64);

impl RenderSortKey {
    fn new(layer: u8, texture: u32, depth: u32, flags: u8) -> Self {
        // day230 精化版本:Layer(4) | Texture(24) | Depth(28) | Flags(8) = 64 bit
        debug_assert!(layer < 16, "Layer must fit in 4 bits");
        debug_assert!(texture < (1 << 24), "Texture must fit in 24 bits");
        debug_assert!(depth < (1 << 28), "Depth must fit in 28 bits");
        
        let inverted_depth = ((1u32 << 28) - 1) - depth;  // 反向,painter's algo
        
        let k: u64 = ((layer as u64) << 60)
                   | ((texture as u64) << 36)
                   | ((inverted_depth as u64) << 8)
                   | (flags as u64);
        RenderSortKey(k)
    }
    
    fn layer(&self) -> u8 { ((self.0 >> 60) & 0xF) as u8 }
    fn texture(&self) -> u32 { ((self.0 >> 36) & 0xFFFFFF) as u32 }
    fn depth(&self) -> u32 {
        let inv = ((self.0 >> 8) & 0xFFFFFFF) as u32;
        ((1u32 << 28) - 1) - inv
    }
    fn flags(&self) -> u8 { (self.0 & 0xFF) as u8 }
}

fn main() {
    let mut items = vec![
        (RenderSortKey::new(1, 100, 50, 0), "Sprite A"),
        (RenderSortKey::new(1, 100, 30, 0), "Sprite B"),  // 同 layer texture,更近
        (RenderSortKey::new(1, 200, 50, 0), "Sprite C"),  // 同 layer,不同 texture
        (RenderSortKey::new(2, 100, 50, 0), "Sprite D"),  // 不同 layer
    ];
    items.sort_by_key(|(k, _)| *k);
    for (k, name) in &items {
        println!("{}: layer={} tex={} depth={}", name, k.layer(), k.texture(), k.depth());
    }
}
```

输出:

```
Sprite D: layer=2 tex=100 depth=50    (layer 高,先画)
Sprite B: layer=1 tex=100 depth=30    (depth 近,后画)
Sprite A: layer=1 tex=100 depth=50
Sprite C: layer=1 tex=200 depth=50    (texture 不同,最后)
```

注意 Sprite D(layer 2)排第一,因为 layer 高位优先。Sprite B 和 A 同 texture,B depth 近所以排在 A 后面(反向 depth 编码)。

### 11.11 字段演化的未来

casey 的 sort key 在 day230 定型。如果未来 HH 项目加更多需求,字段演化方向:

- **多 view 排序**:shadow / forward / debug 不同 view,需要 view-specific sort key
- **multi-thread sort**:每线程排一部分,merge
- **persistent sort**:多帧间复用上次排序结果(只 sort 改变的部分)
- **GPU compute sort**:shader 实现 radix sort,完全 GPU 侧

casey 不展开这些(超出教学范围),但学完 day230 的基础,你能根据需求演化。
