
# Day 212 · 调试 UI 集成到游戏代码

> 之前 debug UI 是"叠加在游戏上"的薄层——读 events、画图表、改 variable。今天 Casey 让**游戏代码自己也能调用 debug UI API**:游戏可以画自己的 debug 视图(比如玩家攻击范围圈、AI 视野扇形)。这是把 debug 从"外挂"变成"内嵌"的关键一步。

## 0 · 为什么要有这一天

之前 35 集,debug UI 是个**外挂**:游戏代码产生 events,debug UI 消费 events 显示。两者在数据流上分离,游戏代码不知道 debug 在干什么。

这种分离一开始是好的——简单。但很快遇到**无法解决的问题**:

- **场景 1**:你想画"玩家攻击范围圈"。这是个圆,只在 debug 模式下显示。游戏代码里有圆心和半径,但 debug UI 看不到——它只能通过 event 把 `(center, radius)` push 进去,debug UI 读出来画。中间多一次序列化。
- **场景 2**:你想画"AI 视野扇形"。AI 系统有朝向、视野角度、视野距离,debug UI 完全不知道这些字段的存在,因为它和 AI 系统是隔离的 TU。
- **场景 3**:你想在 NPC 头顶画当前状态("patrol" / "chase" / "attack")。这个状态在 NPC struct 里,但 debug UI 拿不到。

三个场景的共同点:**游戏代码自己有上下文,debug UI 没有**。强行让 debug UI 通过 event 流获取所有上下文,等于把游戏代码所有内部状态都序列化一遍——成本极高、收益极低。

**Casey 今天的方案**:让游戏代码**直接调用 debug UI 的绘制 API**。游戏代码自己知道画什么、怎么画、什么时候画。Debug UI 只提供"画一条线、画一个矩形、画一段文字"的 primitive。

这等于**反过来**:之前是"游戏产生数据 → debug 解读",现在是"游戏用 debug 工具自己画"。数据所有权回到游戏代码。

心理锚点:看完今天,你的 debug 系统应该支持"游戏内任何代码都能画一段调试可视化"。这是后面 Day 213-260 所有 debug 视图的基础。

## 1 · Casey 今天做了什么

1. **暴露 debug draw API**:把原本 debug UI 内部的 `DrawLine` / `DrawRect` / `DrawText` 函数变成 pub,游戏代码能调用
2. **加 immediate-mode 风格的 helper**:`debug_draw_line(from, to, color)` 这种函数,游戏代码每帧调用一次就画一帧
3. **修一个绘制顺序 bug**:debug overlay 之前画在游戏之上,现在游戏内的 debug draw(比如攻击范围圈)也要画在游戏之上、外置 overlay 之下。Casey 引入两层 z-order
4. **测试**:在 player 攻击逻辑里加一行 `debug_draw_circle(player.pos, attack_range, RED)`,立刻能看到效果

这是把 debug UI 从"消费者"变成"基础设施"的转折点。

## 2 · 心智模型

### 类比:debug UI 是画笔,游戏代码是画家

之前 debug UI 像一台"自动绘图机":游戏喂数据,机器自己决定画什么。你想画个特殊的圆,机器不认识"圆"这种数据,只能干瞪眼。游戏代码必须先把圆翻译成机器认识的格式(event + tuple),机器才能画。

今天 Casey 把画笔递给游戏:**画笔(debug_draw_*)是基础设施,游戏是画家**。游戏想画圆就 `debug_draw_circle`,想画文字就 `debug_draw_text`。Debug UI 只提供 primitive,不决定内容。画家想画什么,他自己知道;画笔只负责把颜料涂到画布上。

这是 immediate-mode UI 的核心思想(在 Day 196 已经讲过)延伸到 debug 可视化:**所有 UI 状态由当前帧的代码决定,不持久化**。这个思想可以再深挖一层:画家不需要每次画画都"注册一个画家身份",他拿笔就画。retained-mode UI 的"先创建 widget tree,再 set property"就像是"画家要先填表申请才能动笔",繁琐且容易漏填。

另一个角度:**immediate-mode 把"画图"这件事变成纯函数**。给定输入(player.pos、player.hp),输出(画的图)完全确定。纯函数好测试、好推理、好 hot-reload。retained mode 的 widget 有内部状态,是"有记忆的对象",bug 来源更多。

### 2.1 Immediate-mode debug draw 的本质

**Retained mode**:
```
// 一旦创建,持久存在,直到销毁
debug_overlay.add_circle(center, radius, color);  // 持久对象
// 100 帧后还在,除非 debug_overlay.remove_circle(...)
```

**Immediate mode**(Casey 选这个):
```
// 每帧调用一次,画一帧
fn draw_player_debug(player: &Player) {
    debug_draw_circle(player.pos, player.attack_range, RED);
}
// 下一帧又调一次,前一帧画的"消失"了(被新帧覆盖)
```

Immediate mode 的核心:**没有持久状态**。游戏代码每帧"重新声明"自己要画什么,不画了就不调函数,自动消失。

**收益**:
- 永远不会"忘记销毁" → 没有 leak
- 数据所有权清晰(游戏有 player,debug draw 函数借)
- 自动跟随游戏状态更新(player.pos 变了,圆自动跟着)

**代价**:
- 每帧重新画 → 不能"set and forget"
- 调用顺序敏感(后画的盖前面的)

### 2.2 调试可视化的 z-order

游戏画面有几层:

```
背景层(tile map)        z=0
游戏实体层(player, enemy) z=1
游戏内 debug 层(攻击圈) z=2  ← 今天新加
外置 debug overlay(FPS)  z=3
鼠标光标                  z=4
```

Casey 今天的关键改动是引入 **游戏内 debug 层(z=2)**。它的特征:

- 画在游戏实体之上(玩家能看到圈,不被地图盖住)
- 画在外置 overlay 之下(FPS 文字不被攻击圈遮)
- 只在 debug 模式下激活

实现上是个简单的 z-order 整数,渲染时按 z 升序画。

### 2.3 谁拥有数据?

"游戏代码直接画 debug" 引出一个微妙问题:**数据所有权**。在 Rust 里尤其重要。

```rust
// 错误版本(借用冲突)
fn game_update(state: &mut GameState, debug: &mut DebugUi) {
    state.player.pos.x += 1.0;  // 已经借了 state
    debug_draw_circle(&debug, state.player.pos, 10.0);  // 又借 state,同时借 debug
    // 编译器报错:cannot borrow `state` as immutable because it is also borrowed as mutable
}
```

Rust 不允许同时 `&mut state` 和 `&state.player.pos`。解决方法:

```rust
// 方法 1:先更新,再画
fn game_update(state: &mut GameState, debug: &mut DebugUi) {
    state.player.pos.x += 1.0;
    let pos = state.player.pos;  // Copy 出来
    debug_draw_circle(debug, pos, 10.0);  // 用副本
}

// 方法 2:debug_draw 函数接受值,不持有引用
fn debug_draw_circle(debug: &mut DebugUi, center: Vec2, radius: f32) {
    // center 是 Copy 类型,函数结束就释放
}
```

Casey 在 C 里没这问题(C 没有借用检查器),Rust 翻译时这是必须解决的。

### 2.4 immediate-mode 的代价:性能

每帧重新声明 UI 听起来浪费。实际上:

- 一帧画几百条 debug 线、几十个圆,几十 KB 数据,微秒级
- 没有"找到那个对象并改属性"的查找开销
- 没有"对象池"的内存碎片

Casey 在 Day 196 已经讲过,immediate mode 在 CPU 上比 retained mode **快**,因为:

- 没有 hash table 查找
- 没有指针追迹
- 数据局部性好(连续内存)

Rust 视角下,immediate mode 也更友好:**无持久状态 = 无生命周期管理 = 无 Arc<Mutex>**。

### 2.5 第一性原理:为什么"每帧重新画"反而比"创建一次保持"快

这听起来反直觉。让我用第一性原理推导。

retained mode 画一个圆:`overlay.add_circle(center, radius)` 创建一个 Circle 对象,存进 overlay 的 children list。每帧渲染时:遍历 children → 找到 Circle → 读它的字段 → 画。1000 帧 = 1000 次遍历 + 1000 次指针追迹。

immediate mode 画一个圆:每帧调用 `debug_draw_circle(center, radius)`,直接 push 进 vertex buffer。1000 帧 = 1000 次 push。push 是连续内存写,L1 cache hit,~1 cycle。指针追迹是 random memory access,L2/L3 miss,~30-100 cycles。

**1000 次 cache-friendly push < 1000 次 cache-miss pointer chase**。这就是 Casey 说的"immediate mode 快"的硬件原理。这是计算机体系结构决定的,不是任意一种 API 设计能改变的。

进一步:retained mode 还有"对象生命周期管理"的开销。Circle 什么时候销毁?某个 widget 不再显示时?retained mode 必须有 refcount 或 GC,这些都是额外的指令。immediate mode 根本没有"对象",只有"这一帧的绘制指令",无生命周期。

### 2.6 借用检查与 immediate mode 的天然契合

Rust 的借用检查器对 immediate mode 异常友好。retained mode 在 Rust 里要这样写:

```rust
// retained mode:必须用 Arc<Mutex> 或 Rc<RefCell>
let circle = Rc::new(RefCell::new(Circle::new(...)));
overlay.borrow_mut().add(circle.clone());  // 共享所有权
// 其他地方修改:
circle.borrow_mut().radius = 20.0;  // 运行时借用检查
```

immediate mode:

```rust
// immediate mode:每帧函数调用,所有权清晰
debug_draw_circle(&mut debug, center, radius);  // 编译时借用检查
// 不存在"共享 Circle 对象"这种事
```

immediate mode 用编译时借用检查,retained mode 用运行时借用检查(RefCell)。编译时检查零成本、不会 panic、性能更好。这是为什么 Rust 社区如此偏爱 immediate mode(egui、iced 的 renderer 都是 immediate style)。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏内 debug draw 是行业标准做法:

- **Box2D / Chipmunk**:物理引擎内置 debug draw API,画出 collider、关节、力
- **Unreal Engine**:`DrawDebugLine`、`DrawDebugSphere` 一类函数,游戏代码任意调用
- **Unity**:`Debug.DrawLine`、`Debug.DrawRay`,只在 Scene 视图和 development build 显示
- **Godot**:`draw_line` 在 `_draw()` override 里调用

行业共识:**所有游戏引擎都需要 immediate-mode debug draw**。Casey 今天做的就是 HH 版本。

### 3.2 · 图形学视角

debug draw 在图形学里属于 **overlay rendering**,特点:

- **简单几何**(线、点、矩形、圆)——通常 1-100 个顶点
- **不需要深度测试**(永远在最前)或需要但 z 写入关
- **不需要光照**(纯色 / alpha blend)
- **不需要纹理**(或单色纹理)

实现上,debug draw 有两种典型做法:

1. **Immediate mode GL**:`glBegin(GL_LINES); glVertex(...); glEnd();`(老 OpenGL)或 modern GL 用一个 per-frame 重建的 vertex buffer
2. **Batched line renderer**:把所有 debug 线收集到一个 vertex buffer,一次 draw call 画完

Casey 在 Day 235+ 切到 OpenGL 后会做 batched line renderer。今天(还在 CPU 软渲染)直接往 framebuffer 画像素,简单粗暴。

### 3.3 · Rust 生态视角

Rust 表达 immediate-mode debug draw 的典型 pattern:

```rust
pub struct DebugDraw {
    lines: Vec<LineVertex>,    // 每帧清空、重新填
    circles: Vec<CircleVertex>,
    text: Vec<TextVertex>,
}

impl DebugDraw {
    /// 画一条线。frame 结束时清空
    pub fn line(&mut self, from: Vec2, to: Vec2, color: Color) {
        self.lines.push(LineVertex { from, to, color });
    }

    /// 画一个圆(用 N 条线段近似)
    pub fn circle(&mut self, center: Vec2, radius: f32, color: Color) {
        const N: usize = 32;
        let mut prev = center + Vec2::new(radius, 0.0);
        for i in 1..=N {
            let angle = (i as f32) * std::f32::consts::TAU / N as f32;
            let curr = center + Vec2::new(angle.cos() * radius, angle.sin() * radius);
            self.line(prev, curr, color);
            prev = curr;
        }
    }

    /// 每帧开始时调用
    pub fn clear(&mut self) {
        self.lines.clear();
        self.circles.clear();
        self.text.clear();
    }
}
```

**关键 Rust 特性**:
- `Vec::clear()` 不释放底层内存,只把 len 设 0——下一帧 push 不会重新分配
- 所有方法 `&mut self`,但游戏代码只需要 `&mut DebugDraw`,不持有内部引用
- 没有 lifetime 参数,因为 LineVertex 全是 `Copy` 类型

参考 crate:`egui-epaint`(egui 的画图 primitive 集合)、`lyon`(几何 path tessellation)。

### 3.4 · Linux 系统编程视角

immediate-mode debug draw 在 Linux 工具里也有回响:

- **gdb `tui`**:每帧重画终端 UI
- **htop / btop**:每秒重画,无持久 widget
- **perf report --tui**:同样 immediate-mode 风格

这些工具的设计哲学和 Casey 今天的 debug UI 一致:**状态最少,简单可靠**。

更深入地看,Linux 内核的 `/proc` 文件系统也是 immediate-mode 风格:每次 `cat /proc/meminfo`,内核**当下生成**一份信息,不存历史。读 100 次,生成 100 次,每次都是"当下的快照"。这和 Casey 的 debug_draw 完全对应:**每次调用都是即时的、无状态的、当前帧的**。

对比:`/var/log/messages` 是 retained mode——日志写到磁盘,持久存在,可以回放。`/proc` 是 immediate mode——只反映当前状态。两种模式各有用途,Linux 把它们放在不同位置,让用户按需选择。游戏引擎的 debug overlay 也是 immediate mode,但可以**额外**把 immediate 数据写进 ring buffer 实现"历史回放"——这又是 Casey 在 Day 217 会做的"per-element storage"。

### 3.5 · 🎨 图形学深入:GPU 端的 debug draw

Casey 今天是 CPU 软渲染,直接往 framebuffer 写像素。但工业级 debug draw 通常用 GPU 画,这涉及几个图形学要点:

**1. Line rasterization 算法**:GPU 画线不像 CPU 那样逐像素 Bresenham,而是用两个三角形组成细长条带。抗锯齿靠 coverage 计算。这就是为什么 GPU 画的线有时候会"消失"(太细,小于 1 像素)。debug draw 通常强制最小线宽(比如 1.5px)避免这个问题。

**2. Depth test 处理**:debug 线如果开启 depth test,会被场景几何体遮挡。Casey 想要的"攻击圈始终可见"需要**关闭 depth test**(`glDisable(GL_DEPTH_TEST)`),或者**强制 depth = 0**(画在最前)。这是 debug draw 和正常渲染的关键差别。

**3. Blend mode**:debug overlay 通常用 alpha blending,半透明显示。GL 实现:`glEnable(GL_BLEND); glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA);`。这让红色攻击圈叠加在场景上,玩家能看到圈下面的游戏内容。

**4. Vertex buffer 重建**:immediate mode 每帧 vertex 不同,需要每帧重新上传 vertex buffer。OpenGL 3.0+ 用 `glBufferSubData` 或 `glMapBuffer` 做流式更新。具体策略:
   - 双缓冲 vertex buffer(两块交替使用,避免 GPU stall)
   - 用 `GL_DYNAMIC_DRAW` hint 而不是 `GL_STATIC_DRAW`
   - 批量 push 所有 debug draw 到一个大 buffer,一次 draw call 画完

这些细节 Casey 在 Day 235+ 切到 OpenGL 后逐步实现。今天(还在 CPU)只关心"API 长什么样",不关心"GPU 怎么实现"。**先设计 API,后优化实现**——这是好的工程顺序。

### 3.6 · 引擎对照

**Unreal `DrawDebugLine`**:UE 内置的 immediate-mode debug draw,签名 `DrawDebugLine(World, Start, End, Color, Persistent, LifeTime)`。`Persistent=true` 时变 retained(线条持久存在指定秒数),默认 `false` 是 immediate。Casey 选的"纯 immediate"是 UE 的默认行为。

**Unity `Debug.DrawLine`**:同样 immediate-mode,但有个 quirk——只在 Scene 视图显示,玩家看不到。Casey 的 debug overlay 在玩家屏幕上显示,这是为了"在真实游戏里调参,不切 editor"。

**Godot 的 `_draw` override**:Node2D 可以 override `_draw()` 函数,每帧重画。这是 immediate-mode,但调用频率受 Godot 控制(必须 `queue_redraw()` 才重画)。Casey 的 debug_draw 是无条件的——游戏代码主动调用就画,不受 framework 节流。

**Bevy 的 `Gizmos`**:Bevy 提供 `gizmos.line(...)`、`gizmos.circle(...)` API,完全 immediate-mode。System 里 `mut gizmos: Gizmos`,直接调用。这是 Rust 生态里和 Casey 最接近的实现。

## 5 · 对照与变奏

### Retained mode vs Immediate mode:历史演化

- **1980s-2000s**:retained mode 主流(MFC / Qt / Win32 / GTK),UI 控件是持久对象
- **2000s-2010s**:web 的 DOM 也是 retained mode(jQuery 时代)
- **2014**:Casey 在 HH 推 immediate-mode debug UI
- **2014-2015**:Dear ImGui 出现,把 immediate-mode 推广到工具 UI
- **2020+**:egui(rust)、Nuklear、RmlUi 等 immediate-mode UI 库成为游戏工具标准

casey 是这个潮流的早期布道者之一。

### 不同语言的 immediate-mode debug draw

| 语言/引擎 | API 风格 |
|---|---|
| HH C | `DebugDrawLine(...)` per-frame |
| Unity C# | `Debug.DrawLine(...)` per-frame |
| Unreal C++ | `DrawDebugLine(...)` per-frame |

惊人一致——说明这是个领域共识。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 选择 immediate-mode debug draw 而不是 retained mode?在 HH 的具体场景下,immediate mode 解决了什么 retained mode 解决不了的问题?

**参考解答**:HH 是 hot-reload 架构,游戏代码每帧被替换。retained mode 的"持久 widget"会在 hot-reload 后变成悬空指针。immediate mode 无持久状态,hot-reload 后下一帧自然恢复。

更一般地:immediate mode 自动和游戏状态同步(player.pos 变 → 圆自动跟着),retained mode 需要手动同步,容易漏。

### Lv2 · 动手实践

**题**:在你的 Rust 项目里实现 `DebugDraw` struct,包含 `line`, `circle`, `text`, `clear` 方法。写一个 main:画一个跟随"模拟玩家"位置的圆,玩家每帧 x += 1,圆跟着移动。

完成标准:`cargo run` 看到一个移动的圆(用 softbuffer 或终端 ASCII 都行)。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

#[derive(Copy, Clone)]
struct Color(u8, u8, u8);

struct DebugDraw {
    lines: Vec<(Vec2, Vec2, Color)>,
}

impl DebugDraw {
    fn new() -> Self { Self { lines: Vec::new() } }

    fn line(&mut self, from: Vec2, to: Vec2, c: Color) {
        self.lines.push((from, to, c));
    }

    fn circle(&mut self, center: Vec2, radius: f32, c: Color) {
        const N: usize = 32;
        let mut prev = Vec2 { x: center.x + radius, y: center.y };
        for i in 1..=N {
            let a = (i as f32) * std::f32::consts::TAU / N as f32;
            let curr = Vec2 {
                x: center.x + a.cos() * radius,
                y: center.y + a.sin() * radius,
            };
            self.line(prev, curr, c);
            prev = curr;
        }
    }

    fn clear(&mut self) { self.lines.clear(); }
}

fn main() {

    let mut debug = DebugDraw::new();

        debug.clear();

        println!("frame {}: lines={}", frame, debug.lines.len());
        // 应该看到 lines=32(circle 用 32 条线段)
    }
}
```

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例(扩展 Lv2,加 z-order 和 batched render)

```rust
// Cargo.toml(空,纯 std)

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

#[derive(Copy, Clone, Debug, PartialEq, Eq, PartialOrd, Ord)]
enum ZLayer {
    Background = 0,
    GameEntity = 1,
    DebugGame = 2,    // 游戏内 debug(攻击圈等)
    DebugOverlay = 3, // 外置 overlay(FPS)
    Cursor = 4,
}

#[derive(Copy, Clone)]
struct Color(u8, u8, u8, u8); // RGBA

#[derive(Clone)]
struct DrawCall {
    verts: Vec<(Vec2, Color)>,  // line strip
    z: ZLayer,
}

struct DebugDraw {
    calls: Vec<DrawCall>,
}

impl DebugDraw {
    fn new() -> Self { Self { calls: Vec::new() } }

    fn line(&mut self, from: Vec2, to: Vec2, c: Color, z: ZLayer) {
        self.calls.push(DrawCall {
            verts: vec![(from, c), (to, c)],
            z,
        });
    }

    fn circle(&mut self, center: Vec2, radius: f32, c: Color, z: ZLayer) {
        const N: usize = 32;
        let mut verts = Vec::with_capacity(N + 1);
        for i in 0..=N {
            let a = (i as f32) * std::f32::consts::TAU / N as f32;
            verts.push((Vec2 {
                x: center.x + a.cos() * radius,
                y: center.y + a.sin() * radius,
            }, c));
        }
        self.calls.push(DrawCall { verts, z });
    }

    /// 按z排序,然后"画"(这里只是打印)
    fn render_sorted(&self) {
        let mut sorted: Vec<&DrawCall> = self.calls.iter().collect();
        sorted.sort_by_key(|c| c.z);
        for call in sorted {
            println!("  z={:?} verts={}", call.z, call.verts.len());
        }
    }

    fn clear(&mut self) { self.calls.clear(); }
}

fn main() {
    let mut player = Vec2 { x: 100.0, y: 100.0 };
    let mut debug = DebugDraw::new();

    for frame in 0..3 {
        debug.clear();
        player.x += 10.0;

        // 游戏内 debug:攻击范围
        debug.circle(player, 30.0, Color(255, 0, 0, 255), ZLayer::DebugGame);
        // 外置 overlay:坐标文字(用线模拟)
        debug.line(Vec2 { x: 5.0, y: 5.0 }, Vec2 { x: 50.0, y: 5.0 },
                   Color(0, 255, 0, 255), ZLayer::DebugOverlay);

        println!("=== Frame {} ===", frame);
        debug.render_sorted();
    }
}
```

**关键 Rust 特性**:
- `enum ZLayer` derive `Ord` —— 让 sort_by_key 能用
- `Vec::with_capacity` —— 预分配 verts
- `&[DrawCall]` 借用而非 clone —— sort 不需要转移所有权
- `sort_by_key` 稳定排序,同 z 按插入顺序

### Hot-reload 注意

HH 的游戏代码是动态库,debug draw API 必须有稳定 ABI。Rust 翻译时如果保持 hot-reload,需要用 `#[repr(C)]` 标注 DrawCall 结构体,避免 Rust 编译器重新布局破坏 ABI。

```rust
#[repr(C)]  // 保证字段顺序、对齐按 C 规则,跨 .so 边界稳定
struct DrawCall {
    verts_ptr: *const (Vec2, Color),  // 用裸指针,避免 Vec 的 allocator 跨边界
    verts_len: usize,
    z: ZLayer,
}
```

如果不用 hot-reload(Rust 项目通常没有),不用管 ABI,普通 struct 即可。Phase 4 的 [day172](../phase-4/day172.md) 详细讲 ABI 稳定性。
