# Day 202 · 多次出现的调试值

> 一个变量(比如 player.speed)可能同时在 profiler UI 和 entity inspector 都显示。它们要同步——改一个,另一个也变。今天 Casey 解决"同一 debug value 在多处显示"。

## 0 · 为什么要有这一天

让我们把镜头拉到一个真实的开发场景里。

你跟着 Handmade Hero 走到 Day 201。你刚把整个 debug 系统用 Cargo feature 隔离好,release binary 干净了,心里美滋滋。然后你打开 debug UI,准备调一下玩家速度——你在 profiler 树的 `Player/Movement/Speed` 节点上看到了 `5.0`,顺手拖动 slider 改成 `7.0`。游戏里玩家确实变快了,你觉得 OK。

但是下一秒,你打开 **Animation Inspector**(动画树视图)调试同步问题。你发现动画速率没跟上——还是按速度 5.0 算的步频。你查代码,Animation 模块里也有一个 `player_speed` 显示节点。这个节点还显示 `5.0`。

你疑惑地拖这个节点的 slider——但这次只改了动画用的副本,游戏里玩家速度没变。**两个 slider,改一个另一个不动**。一会儿你又在 Performance Graph 上画了 `Player/Movement/Speed over time`,曲线显示的是 `5.0`,你忘了刚才拖的是哪个 slider。

这种"同一值,多处显示,改一处不同步"的问题,在 debug UI 出现的第二天就会撞上。Casey 之前的 debug 树设计有一个根本缺陷:**每个树节点自己持有一份值的拷贝**,而非"引用一个共享真相"。Profiler 树里 `Speed=5.0` 是一个独立的 `f32`,Animation Inspector 里另一个 `Speed=5.0` 是另一个独立的 `f32`。物理上两个变量,语义上一个概念。

**为什么不能就这么忍着?**

第一,认知负担。你要记"现在到底哪个 slider 是真的"。开发节奏被打断,你要在脑子里维护一张"哪个 slider 控制哪个真变量"的对照表,认知带宽被吃掉一半。

第二,真实 bug。游戏代码读哪一份?如果 player update 读 `Profiler/Movement/Speed`,animation update 读 `Animation/Speed`,两边不同步——你拖一个 slider 改了 player 行为但没改 animation,玩家在游戏里就会"滑步"(animation 速度不匹配 movement 速度)。这种 bug 看起来像"动画 bug",实际是"两份 debug 值漂移了"。

第三,扩展困难。明天你想加第三个视图——比如"AI 视角下的玩家速度"。又一份拷贝。后天你想"录制一段游戏然后用 timeline scrub 变量"——又一份。每加一个视图,你都要确保它读的是同一份值。**这种"手动同步"的代码,迟早会漏**。

工业界的标准答案叫 **single source of truth(单源真相)**:**一个值只存在一份,所有访问者通过引用、句柄或全局 registry 拿它**。改时改这一份,所有引用自动看到新值。

这套原则在软件工程里到处都是:
- **数据库设计**:基础表 + 多视图。改基础表,所有视图自动反映。
- **Redux/Flux**(前端):所有 state 在一个 store,组件订阅 store。改 store,组件自动 re-render。
- **Unreal Blackboard**(AI):AI 决策共享一个 state blackboard。
- **Unity ScriptableObject**:跨 prefab 共享配置资产。
- **Bevy Resource**:全局 singleton state,所有 system 通过 `Res<T>` 引用。

今天 Casey 把 debug 值重构成这个模式。核心抽象是:**一个全局 `DebugVariables` 表,树节点存"引用"(GUID + path),不存值**。改时改表,所有引用自动同步。

看起来只是"加一个 HashMap",但这一集讨论的设计权衡——GUID vs 指针、pull vs push、类型擦除 vs 类型安全、引用 vs 复制——是你以后做任何"共享数据"设计都要反复面对的问题。学完今天,你能:

- 解释为什么"共享指针"(Rc/Arc)在游戏 debug 场景不是最佳选择
- 设计一套 GUID-based 的 variable registry,跨视图自动同步
- 在 pull 和 push 更新模式之间做合理取舍
- 把这个模式迁移到任何"多个消费者需要看同一个变化值"的场景(配置、AI 共享状态、网络同步)
- 看懂 Bevy 的 Resource / Unreal 的 Blackboard / Redux 的 store 在结构上为什么是同一个东西

## 1 · Casey 今天做了什么

Casey 设计:

1. `DebugVariables: HashMap<GUID, DebugValue>` 全局表
2. 树节点持有 GUID,显示时查表
3. 编辑时改表,树自动看到
4. 多个视图(树、曲线图、inspector)都查同一表

## 2 · 心智模型

### 2.1 费曼类比:同一份病历与多个诊室

想象一家医院。病人张三的主治病历是**一份**——他只有一份病史、一份过敏列表、一份当前血压。但是张三今天要去看三个医生:心内科、呼吸科、皮肤科。

**错误的设计**:每个诊室都复印一份病历。心内科医生在复印件上写"开药 X",呼吸科医生**不知道**——他的复印件上还是旧的"未开药"。第二天张三吃了 X 又吃了呼吸科开的 Y,两种药冲突,病人进 ICU。

**正确的设计**:病历只放在档案室一份。每个诊室里只有一个**病历号**——医生要看时,拿号去档案室调阅。改完放回档案室。下一个医生来,拿同一个号,看到的是最新版。这就是 hospital chart system 的本质。

**debug 变量是病人,视图是诊室**。Profiler 树、Animation Inspector、Performance Graph 是三个诊室。每个诊室里不该自己复印一份 `player.speed`,应该只放一个**变量号(GUID)**——要看时去全局 registry 查。改时改 registry,所有诊室下次看都拿到新值。

这个类比的关键洞察:**冗余拷贝是 bug 的温床**。任何"同一信息存多份"的设计,迟早会忘了同步某一份。Single source of truth 不是抽象原则,是**反 bug 的工程防御**。

### 2.2 从零推导:GUID registry 的设计

让我们一步步从最朴素的方案推到 GUID registry,你会看到每一步为什么必须这样走。

**Step 0:最朴素的——直接共享变量**。

```rust
static mut PLAYER_SPEED: f32 = 5.0;
```

每个视图 `unsafe { PLAYER_SPEED }` 直接读。问题:`unsafe`、无类型隔离、并发不安全、无法枚举所有变量(Inspector 要列出"所有 debug 变量",static 变量没注册表)。

**Step 1:把变量装进 HashMap**。

```rust
struct DebugVars { map: HashMap<String, f32> }
```

字符串做 key——能枚举、能改、能在 UI 里显示名字。但 String 比较 O(n),每次 lookup 分配,hot path 慢。而且只能存 f32,想存 i32 / bool 要再加 HashMap。

**Step 2:用 hash 把 String 变 u64**。

```rust
let speed_guid: u64 = hash("player/speed");
```

现在 key 是 u64,HashMap 查询 O(1),key 是个整数,可以编译期算出来。Casey 的方案就是这个层次。

**Step 3:类型擦除——一个 HashMap 装多种类型**。

```rust
enum DebugValue {
    F32(f32),
    I32(i32),
    Bool(bool),
    String(String),
    Vec3([f32; 3]),
}

struct DebugVars { map: HashMap<u64, DebugValue> }
```

一个表装所有类型。代价:`get_f32(guid)` 时如果实际是 I32 要 panic 或返回 Err——runtime 检查。这是 Casey 的最终方案。

**Step 4(可选):内 Cell 避免 `&mut`**。

游戏主循环里到处是 `&State`,你不想为了改个 debug 值就要 `&mut State`(那要重 borrow 整个游戏状态)。Cell 提供内部可变性:

```rust
enum DebugValue {
    F32(Cell<f32>),  // &DebugValue 也能改
    I32(Cell<i32>),
    Bool(Cell<bool>),
}
```

`Cell<T>` 是 single-threaded interior mutability。游戏主循环单线程读 debug 值,Cell 够用。多线程要换 `AtomicU32`(把 f32 转 bits)。

**Step 5:视图存 GUID,不存值**。

```rust
struct DebugTreeNode {
    name: String,
    var_refs: Vec<(u64, /*display_name*/ String)>,
}
```

视图节点只持有 GUID。显示时 `store.get(guid)` 查值。改时 `store.set(guid, new_value)`。所有视图下次显示自动看到新值。

这五步走下来,你得到 Casey 在 Day 202 的完整设计。每一步都有具体的技术动机——不是凭空冒出来的。

### 2.3 备选方案对比:GUID 表 vs Rc<RefCell<T>>

Rust 程序员看到"共享值"会本能想到 `Rc<RefCell<T>>`。为什么不直接这样?

```rust
// Rc 方案
struct DebugVars {
    speed: Rc<RefCell<f32>>,
    hp: Rc<RefCell<i32>>,
}

let speed_clone = speed.clone();  // 视图持有一份 Rc clone
*speed_clone.borrow_mut() = 7.0;  // 改
```

这个方案技术上能工作。但对比 GUID 表:

**优势**:
- 类型安全(`Rc<RefCell<f32>>` 编译时知道是 f32,无 runtime 类型检查)
- 零 lookup(直接 deref)
- Rust 原生借用检查

**劣势**:
- **无法动态枚举**。UI 要列出"所有 debug 变量",`Rc<RefCell<f32>>` 是命名字段,不能 iterate。你得另外维护一份 `Vec<&str>` 名字列表,反而引入"名字和字段同步"的 bug。
- **序列化困难**。`Rc` 不能 Serialize,要 deref 拿值。GUID 表里 GUID 是 u64,天然 Serialize。
- **跨模块引用麻烦**。Animation 模块要用 player.speed,要拿 `Rc<RefCell<f32>>` 的 clone。这要么全局传递(污染所有函数签名),要么塞进 ECS Resource(回到"全局表"模式)。
- **生命周期管理**。Rc 循环引用泄漏。RefCell 运行时 borrow panic。

GUID 表的优势:
- 一个 HashMap 能 iterate(`for (guid, val) in &map`),UI 自动列出所有变量
- 序列化 trivial(JSON dump `{guid: value}`)
- 跨模块只传 `&DebugVars`,API 干净
- 没有 borrow check 问题(`Cell::set` 不会 panic)

代价:类型擦除 + runtime 类型检查。Casey 接受这个代价,因为 debug UI 不是 hot path,panic 也只是开发时炸。

### 2.4 引用 vs 复制:语义差异

一个微妙但关键的点:**视图"引用"还是"复制"值,语义完全不同**。

```rust
// 引用(每次都查)
fn update_player(vars: &DebugVars, player: &mut Player) {
    let speed = vars.get_f32(SPEED_GUID);  // 每帧查
    player.pos += player.vel * speed;
}

// 复制(只在 init 时查一次)
fn init_player(vars: &DebugVars, player: &mut Player) {
    player.speed = vars.get_f32(SPEED_GUID);  // 复制到 player
}
fn update_player(player: &mut Player) {
    player.pos += player.vel * player.speed;  // 之后不再查
}
```

引用风格:registry 一改,游戏代码立刻看到新值。**这就是 debug UI 的核心价值**——你拖 slider,游戏立刻反应。

复制风格:registry 改了,游戏代码看到的还是旧值。**这对 debug UI 毫无意义**——你拖了 slider 但游戏没反应。

Casey 选引用风格。代价是每帧 lookup(~100ns for HashMap),但游戏主循环每帧只查几十个 debug 值,总开销 < 5μs,可忽略。

但有个反例:**热路径里的 debug 值**。如果某个 debug 值在内层循环(比如每像素查一次),你不能每像素 lookup。这时复制风格更合理——预读一次进局部变量,内循环用局部变量。Casey 在视频里特别提到这个 trade-off。

### 2.5 pull vs push:更新通知模式

视图怎么知道"值变了"?两种模式:

**Pull 模式**:游戏代码每帧主动读。值变了自然反映到下一帧。

```rust
fn frame() {
    let speed = vars.get_f32(SPEED_GUID);  // 主动 pull
    update_player(speed);
    draw_debug_ui(&vars);  // UI 也 pull,显示最新
}
```

优点:简单,无状态。缺点:每帧每个值都查,即便没改。对 debug UI 这种"几十个值"的场景,开销可忽略。

**Push 模式**:值变时通知订阅者。

```rust
struct Var {
    value: f32,
    subscribers: Vec<fn(f32)>,  // callback 列表
}

impl Var {
    fn set(&mut self, new: f32) {
        self.value = new;
        for cb in &self.subscribers {
            cb(new);  // 通知所有订阅者
        }
    }
}
```

优点:读零开销(订阅者收到通知后自己决定是否更新)。缺点:复杂(callback 注册/注销、循环订阅、reentrancy)。

游戏 debug UI 用 pull 够了。push 适合:
- 视图很重(Inspector 树整个重建,只想在变化时重建)
- 视图很多(1000+ 视图,每帧 poll 太贵)
- 跨进程(网络同步)

工业级 reactive 系统(React 的 useState、Elm 的信号、RxJS 的 observable)都是 push 模式。但游戏 debug UI 不需要这个复杂度。

### 2.6 GUID 唯一性:hash 碰撞的工程防御

GUID 用 hash 字符串生成。hash 函数有碰撞——两个不同字符串 hash 出同一个 u64。概率极低(64-bit hash 碰撞概率约 2^-64),但工程上不能忽略。

**防御措施**:

1. **编译期 hash**。`const SPEED_GUID: u64 = const_fnv1a("player/speed");`。同样字符串编译期算出同样 GUID,拼写错误编译期就报错(undefined variable)。

2. **Namespace prefix**。`"player/speed"` 而非 `"speed"`,大幅减少跨模块碰撞。

3. **运行时注册表**。第一次 `register("player/speed", value)` 时检查 GUID 是否已存在——如果已存在但字符串不同,panic。

4. **FNV-1a 或 xxHash**。FNV-1a 简单可靠,几十行实现。xxHash 更快但代码量大。游戏 debug 用 FNV-1a 够。

```rust
const fn fnv1a(s: &str) -> u64 {
    let mut hash: u64 = 0xcbf29ce484222325;
    let bytes = s.as_bytes();
    let mut i = 0;
    while i < bytes.len() {
        hash ^= bytes[i] as u64;
        hash = hash.wrapping_mul(0x100000001b3);
        i += 1;
    }
    hash
}

const SPEED_GUID: u64 = fnv1a("player/speed");
```

`const fn` 让 hash 在编译期完成。GUID 不进 binary 字符串表(发行版也不泄露内部命名)。这是 Casey 的最终方案。

### 2.0 同一 debug 值的多个副本

游戏里同一个值可能在不同地方用:玩家速度既影响 Player.update,也影响 Animation.sync。如果 debug UI 显示两次,改一个另一个不同步。

**问题来源**:
- 全局 static 变量(各种 const)
- 硬编码 magic number(`5.0` 在多处出现)
- 多 owner 共享(指针 / Rc)

**解法**:**单一数据源**(single source of truth)。所有引用指向同一变量,改一个全变。

### 2.0.1 Single source of truth 的实现

```rust
// 中央 registry
pub struct DebugValues {
    values: HashMap<u64 /* guid */, DebugValue>,
}

enum DebugValue {
    F32(Cell<f32>),
    I32(Cell<i32>),
    Bool(Cell<bool>),
}

impl DebugValues {
    pub fn get_f32(&self, guid: u64) -> f32 {
        match self.values.get(&guid) {
            Some(DebugValue::F32(c)) => c.get(),
            _ => panic!("unknown guid"),
        }
    }

    pub fn set_f32(&self, guid: u64, value: f32) {
        match self.values.get(&guid) {
            Some(DebugValue::F32(c)) => c.set(value),
            _ => panic!("unknown guid"),
        }
    }
}

// 游戏代码
fn update_player(values: &DebugValues, player: &mut Player) {
    let speed = values.get_f32(hash("player/speed"));
    player.pos += player.vel * speed;
}
```

游戏代码从 registry 读,debug UI 写 registry。改 UI 自动反映到所有用这个值的地方。

### 2.0.2 引用 vs 复制

两种思路:

**引用**(Cell / RefCell):游戏代码读时调 `get_f32`,拿到当前值。改 registry 全自动同步。

**复制**:`let speed = values.get_f32(...); player.speed = speed;`。复制一次,之后 registry 改了 player.speed 不变。

 Casey day 202 的设计是引用风格——所有访问走 registry。

### 2.0.3 ID 冲突

如果两个不同概念都叫 "speed":

```
"player/speed"   → 5.0
"enemy/speed"    → 3.0
```

GUID(hash)不同,没冲突。但**手写错**(两个都用 "speed"):
```
"player/speed"   → 5.0
"enemy/speed"    → 3.0  // 写成 "enemy/speed" 又写 "speed"
"speed"          → ???  // 不应该
```

工程防御:**编译期 GUID**(`const SPEED_GUID: u64 = hash("player/speed");`),编译器检查拼写。

### 2.0.4 类型安全

HashMap<u64, f32> 不能存 i32 / bool。**类型擦除**:

```rust
enum DebugValue {
    F32(Cell<f32>),
    I32(Cell<i32>),
    Bool(Cell<bool>),
}
```

`get_f32` 时如果实际是 I32,panic。Runtime 检查,不安全。

**类型安全版**:每种类型一个 HashMap:

```rust
struct DebugValues {
    f32_values: HashMap<u64, Cell<f32>>,
    i32_values: HashMap<u64, Cell<i32>>,
    bool_values: HashMap<u64, Cell<bool>>,
}
```

但 API 膨胀(`get_f32` / `get_i32` / ...)。trade-off:**简洁 vs 安全**。

### 2.0.5 多 owner 的更新通知

UI 改值时,所有"用这个值的地方"要更新。两种模式:

**Pull 模式**(Casey):游戏代码每帧读,值变了自然反映。简单,但每次读有 lookup 开销。

**Push 模式**(Observer):值变时通知订阅者。复杂(Event system),但读零开销。

游戏 hot path 适合 pull(每帧读,< 100 ns)。UI 用 observer(避免每帧 polling)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业里"single source of truth"是引擎架构的根基。每个引擎都用自己的方式实现,但本质相同。

**Unreal Engine** 用 `UBlackboardComponent`(AI)和 `UGameInstance`(全局 state)。Blackboard 是 AI 决策共享的 KV 表——`Blackboard->SetValueAsFloat("PlayerSpeed", 7.0f)`,所有 behavior tree 节点下次 tick 看到新值。这和 Casey 的 DebugVariables 几乎是同构的——区别只是 Unreal 用 FName(unreal interned string)做 key,Casey 用 GUID(u64)。

**Unity** 用 `ScriptableObject`。这是 Unity 的"共享资产"机制——一个 ScriptableObject 实例可以引用多次,所有引用看到同一份数据。改 ScriptableObject,所有 prefab 实例立刻反映。Unity 设计师推荐"用 ScriptableObject 而非 static 变量"做共享配置,正是 single source of truth 的实践。

**Godot** 用 `Resource`。和 ScriptableObject 类似——Resource 是引用语义,赋值是引用而非复制。多个节点引用同一 Resource,改一处全变。

**Bevy** 用 `Resource`。Bevy ECS 的 Resource 是全局 singleton——`Res<MyConfig>` 和 `ResMut<MyConfig>` 通过 system 注入,所有 system 看到同一个实例。改 Resource 自动反映到所有 system。Bevy 还提供 `Changed<T>` filter 自动追踪变化,这是 GUID 表没有的(要手写 change detection)。

```rust
// Bevy 风格
#[derive(Resource)]
struct DebugVars { speed: f32, hp: i32 }

fn update_player(mut vars: ResMut<DebugVars>, mut query: Query<&mut Transform>) {
    vars.speed += 0.1;  // 改全局
    for mut transform in query.iter_mut() {
        transform.translation.x += vars.speed;  // 读
    }
}
```

Casey 的 GUID 表和这些方案相比,优势是**简单**——一个 HashMap,几十行代码。劣势是**无类型安全**(类型擦除)和**无 change detection**(pull 模式)。

**迁移建议**:你的 Rust 游戏项目,如果用 Bevy 就直接用 Resource;如果不用 ECS,Casey 的 GUID 表是最简单的方案。两者都是 single source of truth。

### 3.2 · 🐞 Debug 工具视角(本日核心域)

Debug 工具行业有几种"多视图同步"的实现。每种都有取舍。

**Immediate-mode UI(ImGui / egui)**:每帧重建所有 UI。值从源 pull,自然同步。这是 Casey 用的方式——ImGui 风格的 debug 树每帧重建,从 GUID 表查值,改时改表。Immediate-mode 的隐藏好处是"多视图同步"问题**根本不存在**——没有 cached state 需要同步,每帧从源重读。

**Retained-mode UI(Qt / GTK)**:控件树持久化,有 cached state。值变时要手动 invalidate 和 update。这套机制在 Qt 叫 signal-slot,在 GTK 叫 GObject notify。复杂、容易出错,但性能好(只更新变化的部分)。

**Web DevTools(Chrome / Firefox)**:用 `MutationObserver` 和 `Object.observe`(已废弃)做 change detection。React 用 virtual DOM diff——每次 setState 生成新 vDOM,diff 出真实 DOM 改动。Debug 工具里 vDOM diff 太重,React DevTools 直接 hook 进 React fiber。

** Tracy / Optick / RenderDoc profiler**:这些 profiler 用 ring buffer + frame metadata。每帧 profiler push 一份值进 ring,UI 从 ring pull。Ring buffer 大小固定,旧数据被覆盖——这是"时间序列的 single source of truth"。

**casey 在 HH 用的 ImGui debug overlay** 是 immediate-mode 风格——每帧重建,pull 模式。Day 202 加 GUID 表后,自然就解决了多视图同步。这是 ImGui 设计哲学的红利:**避免 retained state,从源头重读**。

工业级 debug 工具里值得学的:
- **Tracy** 的 frame metadata 模型(给值加时间戳)
- **pix** 的 capture/replay(把值序列化进 capture 文件)
- **RenderDoc** 的 resource tracking(给值加"来自哪个 draw call")

### 3.3 · 🐧 Linux 系统编程视角

Linux 系统里"共享 state"是个老话题。Linux 有几套机制:

**`/sys` 文件系统**:内核 state 暴露给用户态。`/sys/class/backlight/intel_backlight/brightness` 是一个文件,值是当前背光亮度。所有进程读这个文件看到同一值,写这个文件改内核 state。**这是内核态的 single source of truth**。

```bash
cat /sys/class/backlight/intel_backlight/brightness
echo 500 | sudo tee /sys/class/backlight/intel_backlight/brightness
```

**`/proc` 文件系统**:类似 `/sys`,但是进程信息。`/proc/self/status` 是当前进程状态,所有读它的工具(top / htop / ps)看到同一数据。

**D-Bus**:跨进程的 message bus。一个 service 暴露一个 property,所有客户端订阅。property 变时 service 发 signal,订阅者收到。**这是 push 模式的 single source of truth**。systemd / NetworkManager / BlueZ 都用 D-Bus 暴露 state。

**systemd 的 unit state**:`systemctl status xxx` 显示的 service state,来自 systemd 的内部 state machine。所有 client tool(journalctl / systemctl / systemd-cgls)看同一 state。

```bash
# 看 systemd 暴露的 properties(D-Bus 接口)
systemctl show sshd.service -p ActiveState -p SubState

# 看 D-Bus 服务的 properties
busctl get-property org.freedesktop.systemd1 \
    /org/freedesktop/systemd1/unit/sshd_2eservice \
    org.freedesktop.systemd1.Unit ActiveState
```

Linux 的"single source of truth"模式比 Casey 的 debug vars 更严肃——内核或 daemon 持有 state,所有客户端通过 IPC(sysfs / procfs / D-Bus)访问。这套机制能跨进程、跨用户、跨容器。

**你能学到的迁移**:你的 Rust 游戏如果要做"外部 debug 工具"(比如手机 app 控制游戏 debug vars),可以用 D-Bus 或 HTTP 暴露 GUID 表。外部工具改值 = 写 GUID 表,游戏自动看到。

### 3.4 · 🦀 Rust 生态视角

Rust 有几个"共享可变 state"的标准模式。我们对比在 debug vars 场景下的适用性。

**`Rc<RefCell<T>>`**(单线程引用计数 + 内部可变):
```rust
let speed: Rc<RefCell<f32>> = Rc::new(RefCell::new(5.0));
let speed_clone = speed.clone();
*speed_clone.borrow_mut() = 7.0;
```
类型安全,但无法动态枚举所有变量,序列化要 deref。适合"少数固定变量"。

**`Arc<Mutex<T>>`**(多线程版):
```rust
let speed: Arc<Mutex<f32>> = Arc::new(Mutex::new(5.0));
*speed.lock().unwrap() = 7.0;
```
锁开销大,适合跨线程共享。游戏 debug UI 主线程,不需要。

**`Arc<AtomicU32>`**(lock-free 多线程):
```rust
let speed_bits: Arc<AtomicU32> = Arc::new(AtomicU32::new(5.0f32.to_bits()));
let bits = speed_bits.load(Ordering::Relaxed);
let speed = f32::from_bits(bits);
```
零锁,但只能原子基础类型。游戏主循环跨线程共享单个值(如全局时间)用这个。

**`thread_local!`**(每线程独立):
```rust
thread_local! {
    static DEBUG_VARS: RefCell<HashMap<u64, DebugValue>> = RefCell::new(HashMap::new());
}
```
每线程一份独立表。适合 worker pool(每 worker 自己的 debug state)。

**Bevy Resource**:见 §3.1。

**`once_cell::sync::Lazy`**(全局 lazy):
```rust
static DEBUG_VARS: Lazy<RwLock<DebugVars>> = Lazy::new(|| RwLock::new(DebugVars::new()));
```
全局单例,首次访问初始化。Casey 在 HH 里没用 Rust(他写 C),但 Rust 移植版会这么写。

**Casey GUID 表的 Rust 实现**:
```rust
use std::sync::RwLock;
use once_cell::sync::Lazy;

static DEBUG_VARS: Lazy<RwLock<DebugVars>> = Lazy::new(|| {
    RwLock::new(DebugVars::new())
});

// 读(多个 reader 同时)
pub fn get_f32(guid: u64) -> f32 {
    DEBUG_VARS.read().unwrap().get_f32(guid)
}

// 写(独占 writer)
pub fn set_f32(guid: u64, val: f32) {
    DEBUG_VARS.write().unwrap().set_f32(guid, val)
}
```

`RwLock` 允许多 reader 单 writer——读多写少的 debug vars 场景特别合适。`Lazy` 避免初始化顺序问题。这是 Rust 生态里"全局 GUID 表"的 idiom。

**反模式警告**:不要用 `Rc<RefCell<T>>` 跨线程(panic);不要用 `Arc<Mutex<T>>` 在 hot loop(锁开销);不要用 `static mut`(unsafe,无 sync)。这三类错误在新手里很常见。

### 3.5 · 完整 Rust 实现示范

下面是 Casey 设计在 Rust 里的完整落地。先把所有类型摆出来:

```rust
use std::collections::HashMap;
use std::cell::Cell;

/// 全局变量表——single source of truth
pub struct DebugVariableStore {
    variables: HashMap<u64, DebugValue>,
}

/// 类型擦除的 debug 值
#[derive(Clone, Debug)]
pub enum DebugValue {
    Float(f32),
    Int(i64),
    Bool(bool),
    String(String),
}

/// 视图持有的"引用"——只是 GUID + 显示名,不含值
#[derive(Clone)]
pub struct VariableRef {
    pub guid: u64,
    pub display_name: String,
}

/// 树节点——子树 + 变量引用列表
pub struct DebugNode {
    pub name: String,
    pub children: HashMap<String, DebugNode>,
    pub variables: Vec<VariableRef>,
}

impl DebugVariableStore {
    pub fn new() -> Self {
        Self { variables: HashMap::new() }
    }

    pub fn get(&self, guid: u64) -> Option<&DebugValue> {
        self.variables.get(&guid)
    }

    pub fn set(&mut self, guid: u64, value: DebugValue) {
        self.variables.insert(guid, value);
    }

    /// 列出所有变量(UI inspector 用)
    pub fn iter_all(&self) -> impl Iterator<Item = (u64, &DebugValue)> {
        self.variables.iter().map(|(k, v)| (*k, v))
    }
}
```

`DebugVariableStore` 是数据真相。`VariableRef` 是"病历号"——视图持有它,显示时调 `store.get(guid)` 拿真值。改时调 `store.set(guid, new_value)`,所有视图下次 `get` 自动看到新值。

UI 渲染的代码读起来非常直接:

```rust
fn draw_variable(
    ui: &mut Ui,
    store: &DebugVariableStore,
    var_ref: &VariableRef,
) {
    // 每次绘制都从 store 拉最新值——这就是 pull 模式
    let value = store.get(var_ref.guid);
    let display = match value {
        Some(DebugValue::Float(f)) => format!("{:.2}", f),
        Some(DebugValue::Int(i)) => i.to_string(),
        Some(DebugValue::Bool(b)) => b.to_string(),
        Some(DebugValue::String(s)) => s.clone(),
        None => "(null)".to_string(),
    };
    ui.label(&format!("{}: {}", var_ref.display_name, display));
}
```

注意:这个函数**没有持有 cached 值**——每帧从 store 查。store 一改,下一帧 UI 立刻反映。这就是 immediate-mode UI + single source of truth 的威力。

编辑代码也类似:

```rust
fn edit_variable(
    ui: &mut Ui,
    store: &mut DebugVariableStore,
    var_ref: &VariableRef,
) -> bool {
    let mut changed = false;
    let value = store.get(var_ref.guid).cloned();
    if let Some(DebugValue::Float(f)) = value {
        let mut new_f = f;
        if ui.slider("value", &mut new_f, 0.0, 100.0) {
            // 拖动 slider 时改 store,而不是改本地变量
            store.set(var_ref.guid, DebugValue::Float(new_f));
            changed = true;
        }
    }
    changed
}
```

关键点:`store.set(var_ref.guid, ...)` 改的是 store,**不是 var_ref**。var_ref 只是 GUID 容器,改不动它(也不需要改)。改 store 后,任何持有这个 GUID 的视图,下次绘制都看到新值。

多视图同步演示:

```rust
fn main() {
    let mut store = DebugVariableStore::new();
    let speed_guid = hash("player_speed");
    store.set(speed_guid, DebugValue::Float(5.0));

    // 视图 1:树
    draw_tree(&store, /* ... */);
    // 改一处
    store.set(speed_guid, DebugValue::Float(7.0));
    // 视图 2:曲线图——重新读,自动看到 7.0
    if let Some(DebugValue::Float(f)) = store.get(speed_guid) {
        draw_history_graph(*f);  // 这里 f = 7.0
    }
}
```

所有视图从同一 store 读,自动看到最新值。**这就是 single source of truth 的力量**。

## 5 · 对照与变奏

### 5.1 Single source of truth 的工业模式

把同一问题在不同生态的答案并排放,你能看清核心抽象:

| 系统 | 单源数据 | 引用方式 | 变更传播 |
|---|---|---|---|
| Redux / Flux | store | selector / connect | reducer 生成新 state → subscriber 重渲 |
| Unreal Blackboard | UBlackboardComponent | FName(key) | 主动 pull(btree tick) |
| Unity ScriptableObject | .asset 文件 | 引用序列化 | 改 asset,所有引用立刻反映 |
| Bevy Resource | 全局 Resource | `Res<T>` / `ResMut<T>` | system 每帧 pull,或 `Changed<T>` filter |
| Reactive (RxJS/Elm) | signal / observable | subscription | push,值变自动通知 |
| Actor (Erlang/Akka) | actor 内部 state | PID + message | 异步 message passing |
| Casey GUID 表 | `HashMap<u64, DebugValue>` | u64 GUID | pull(每帧重读) |

这些方案在结构上**是同一个东西**——一个权威数据源 + 多个引用 + 一种变更传播机制。区别只在三个维度:

1. **引用怎么命名**:GUID(u64)、字符串(FName)、指针(Rc)、PID(actor)。命名方式决定序列化、调试、跨进程能力。
2. **变更怎么传播**:pull(每帧查)、push(订阅通知)、actor(消息队列)。决定延迟、复杂度、性能。
3. **类型怎么保证**:编译期类型安全(Bevy Resource、Rc<RefCell<T>>)、运行时检查(Casey GUID 表)、完全无类型(JavaScript)。决定可靠性和灵活性。

### 5.2 Redux 的不可变 state 模式

Redux 用**不可变 state**——每次改值生成新 state object。这是函数式编程的思路:

```js
// Redux reducer
function reducer(state = { speed: 5 }, action) {
    if (action.type === 'SET_SPEED') {
        return { ...state, speed: action.value };  // 新对象
    }
    return state;
}
```

不可变的好处:
- **undo / redo 容易**:保存历史 state snapshot,撤销时回到旧 state。
- **变更检测便宜**:`new_state !== old_state` 一行判断。
- **并发安全**:不可变对象天生 thread-safe。

代价是每次改要分配新对象。游戏 hot path(60 FPS,16ms/帧,内层循环可能跑几百万次)不能用,因为 GC 压力。但 debug UI 不是 hot path,可以用。

### 5.3 Reactive programming 的 push 模式

RxJS / Elm / Combine 用 **reactive**——值是流(stream),变就触发 callback。这是 push 模式。

```elixir
# Elm
speedChanged : Float -> Msg
speedChanged newSpeed = SpeedChanged newSpeed

update : Msg -> Model -> Model
update (SpeedChanged s) model = { model | speed = s }
```

```js
// RxJS
const speed$ = new BehaviorSubject(5.0);
speed$.subscribe(v => drawGraph(v));  // 订阅
speed$.next(7.0);  // 改,所有订阅者自动触发
```

reactive 的优势是**依赖关系自动追踪**——值 A 依赖值 B,B 变 A 自动重算。reactive 的劣势是**学习曲线陡**——callback 地狱、循环依赖、reentrancy 都是常见坑。游戏 debug UI 用不到这个复杂度,手写 pull 够。

### 5.4 Bevy 的 Change Detection

Bevy ECS 自动追踪 component 变化——这是 ECS 范式自带的"single source of truth + push notification":

```rust
fn update(speed_query: Query<&Speed, Changed<Speed>>) {
    for speed in speed_query.iter() {
        println!("Speed changed to: {}", speed.0);
    }
}
```

`Changed<T>` filter 只返回变化的 component。游戏代码改 component,system 自动看到。这是 ECS 的核心优势——**SOT 是自动的**,不需要手写 GUID 表。

Casey 不用 ECS,所以手写 GUID 表模拟。如果你用 Bevy,大部分 Casey 在 Day 202 手写的代码都可以省略——ECS 天然提供了 SOT。

### 5.5 数据库 View 的概念溯源

数据库的"基础表 + 视图"是 single source of truth 的最早实现之一(1970s Codd 关系模型)。视图(view)是一个虚拟表,内容是查询的结果:

```sql
CREATE VIEW active_players AS
SELECT id, name FROM players WHERE active = true;

-- 改基础表
UPDATE players SET active = false WHERE id = 42;

-- 视图自动反映
SELECT * FROM active_players;  -- id=42 不再出现
```

视图不存数据,只存查询。改基础表,下次查视图自动反映。**这正是 Casey 的 GUID 表**——GUID 是"虚拟变量名",查询时从基础表(HashMap)拿值。

这个概念在软件工程里被反复重发明——Redux 的 selector、Reactive 的 derived stream、Excel 的公式 cell——都是"view"的变体。理解了关系数据库的 view,你就理解了所有这些方案。

### 5.6 不同范式的全局 state

把"全局共享 state"在不同编程范式里的表达放一起:

- **命令式**:全局 static / singleton。Casey 的 GUID 表属于这种。
- **函数式**:状态 monad / state passing。State 不在全局,而是函数参数和返回值传递。
- **Reactive**:signal / observable。State 是流,变化自动传播。
- **Actor**:Erlang / Akka。每个 actor 内部 state,跨 actor 通过 message。
- **Logic**:Prolog / Datalog。State 是 fact 数据库,查询自动追踪依赖。

游戏 debug UI 用命令式 + 全局,最简单。其他范式有它们的优势(reactive 自动同步、actor 天生并发安全),但复杂度更高。Casey 选最简单的方案,符合 HH 的"够用"哲学。

### Lv1 · 概念辨析

**题**:为什么不直接 `Rc<RefCell<DebugValue>>` 共享,而用全局表 + GUID?

**参考解答**:
- Rc<RefCell>:直接引用,但所有权复杂,跨线程要 Arc<Mutex>

### Lv2 · 动手实践

**题**:实现 DebugVariableStore,加 3 个变量,2 个视图,改一处验证两处都更新。

**参考解答**:

```rust
use std::collections::HashMap;

#[derive(Clone, Debug, PartialEq)]
enum DebugValue { Float(f32), Int(i64), Bool(bool) }

struct Store { vars: HashMap<u64, DebugValue> }
impl Store {
    fn new() -> Self { Self { vars: HashMap::new() } }
    fn get(&self, g: u64) -> Option<&DebugValue> { self.vars.get(&g) }
    fn set(&mut self, g: u64, v: DebugValue) { self.vars.insert(g, v); }
}

fn view_tree(store: &Store, names: &[(u64, &str)]) {
    println!("=== Tree View ===");
    for (guid, name) in names {
        let val = match store.get(*guid) {
            Some(DebugValue::Float(f)) => format!("{:.2}", f),
            Some(DebugValue::Int(i)) => i.to_string(),
            Some(DebugValue::Bool(b)) => b.to_string(),
            None => "?".to_string(),
        };
        println!("  {}: {}", name, val);
    }
}

fn view_graph(store: &Store, guid: u64, label: &str) {
    println!("=== Graph View ({}) ===", label);
    if let Some(DebugValue::Float(f)) = store.get(guid) {
        let bars = (*f as i32 / 5).max(1);
        println!("  [{}]", "#".repeat(bars as usize));
    }
}

fn main() {
    let mut store = Store::new();
    let speed_guid = 1u64;
    let hp_guid = 2u64;
    let fov_guid = 3u64;
    store.set(speed_guid, DebugValue::Float(5.0));
    store.set(hp_guid, DebugValue::Int(100));
    store.set(fov_guid, DebugValue::Float(60.0));

    let names = [(speed_guid, "Speed"), (hp_guid, "HP"), (fov_guid, "FOV")];

    println!("--- initial ---");
    view_tree(&store, &names);
    view_graph(&store, speed_guid, "Speed");

    println!("\n--- change speed to 8.0 ---");
    store.set(speed_guid, DebugValue::Float(8.0));
    view_tree(&store, &names);
    view_graph(&store, speed_guid, "Speed");
}
```

### Lv3 · 迁移设计(push 通知扩展)

**题**:加"变量被改时通知 callback"。让某个视图知道变量变了,自动 refresh。这是把 pull 模式扩展成混合模式——pull 仍然是主路径,push 用于"重计算视图"。

**设计思路**:

1. 每个 GUID 维护一个 `Vec<callback>` 列表(订阅者)。
2. `set(guid, val)` 时除了改 HashMap,还要遍历调用所有 callback。
3. callback 签名要小心——不能拿 `&mut Store`,否则 reentrant `set` 会 panic(死锁或 RefCell borrow panic)。

**参考实现**:

```rust
use std::collections::HashMap;

type Callback = Box<dyn Fn(u64, &DebugValue) + 'static>;

struct NotifyingStore {
    vars: HashMap<u64, DebugValue>,
    subscribers: HashMap<u64, Vec<Callback>>,
}

impl NotifyingStore {
    fn new() -> Self {
        Self {
            vars: HashMap::new(),
            subscribers: HashMap::new(),
        }
    }

    fn get(&self, g: u64) -> Option<&DebugValue> {
        self.vars.get(&g)
    }

    fn set(&mut self, g: u64, v: DebugValue) {
        self.vars.insert(g, v.clone());
        // 通知所有订阅者——注意 callback 是 &self,不会 reentrant 改 store
        if let Some(cbs) = self.subscribers.get(&g) {
            let v_ref = self.vars.get(&g).unwrap();  // 刚 insert,肯定在
            for cb in cbs {
                cb(g, v_ref);
            }
        }
    }

    fn subscribe(&mut self, g: u64, cb: Callback) {
        self.subscribers.entry(g).or_default().push(cb);
    }
}

fn main() {
    let mut store = NotifyingStore::new();
    let speed_guid: u64 = 1;

    // 注册一个订阅者——speed 变就打印
    store.subscribe(speed_guid, Box::new(|guid, val| {
        if let DebugValue::Float(f) = val {
            println!("[callback] GUID {} changed to {:.2}", guid, f);
        }
    }));

    println!("Setting speed to 5.0...");
    store.set(speed_guid, DebugValue::Float(5.0));
    // 输出: [callback] GUID 1 changed to 5.00

    println!("Setting speed to 7.0...");
    store.set(speed_guid, DebugValue::Float(7.0));
    // 输出: [callback] GUID 1 changed to 7.00
}
```

**关键陷阱**:

1. **callback 签名**:`Fn(u64, &DebugValue)`——只读引用,不传 `&mut Store`。如果 callback 想改 store,要排队(延迟到下一帧),不能同步改。
2. **reentrancy**:callback 里调 `store.set()` 会递归 borrow,panic。防御:`set` 里先收集所有 callback 到本地 vec,再调。
3. **生命周期**:`Box<dyn Fn(...) + 'static>` 让 callback 可以闭包捕获 'static 数据。要捕获局部变量要用 `Rc<RefCell<T>>`。

```rust
// 安全的 reentrancy 防御
fn set(&mut self, g: u64, v: DebugValue) {
    self.vars.insert(g, v.clone());
    // 先克隆 callback 引用,避免 reentrancy 时 re-borrow self
    let cbs: Vec<_> = self.subscribers.get(&g)
        .into_iter()
        .flatten()
        .collect();
    let v_ref = self.vars.get(&g).unwrap();
    for cb in cbs {
        cb(g, v_ref);
    }
}
```

这种 push 扩展适合"重计算视图"(整个 Inspector 树重建很贵,只想在变化时重建)。但 pull 仍是主路径——push 只是优化。

`src/main.rs`——完整 GUID 表 + 多视图演示:

```rust
use std::collections::HashMap;
use std::sync::RwLock;
use once_cell::sync::Lazy;

// === 编译期 FNV-1a hash ===
const fn fnv1a(s: &str) -> u64 {
    let mut hash: u64 = 0xcbf29ce484222325;
    let bytes = s.as_bytes();
    let mut i = 0;
    while i < bytes.len() {
        hash ^= bytes[i] as u64;
        hash = hash.wrapping_mul(0x100000001b3);
        i += 1;
    }
    hash
}

// 编译期 GUID——拼写错误编译期就报
const GUID_SPEED: u64 = fnv1a("player/speed");
const GUID_HP:     u64 = fnv1a("player/hp");
const GUID_FOV:    u64 = fnv1a("camera/fov");

// === 类型擦除的 debug 值 ===
#[derive(Clone, Debug)]
enum DebugValue {
    Float(f32),
    Int(i64),
    Bool(bool),
}

// === 全局表(single source of truth) ===
struct DebugVars {
    map: HashMap<u64, DebugValue>,
}

static VARS: Lazy<RwLock<DebugVars>> = Lazy::new(|| {
    let mut map = HashMap::new();
    map.insert(GUID_SPEED, DebugValue::Float(5.0));
    map.insert(GUID_HP,     DebugValue::Int(100));
    map.insert(GUID_FOV,    DebugValue::Float(60.0));
    RwLock::new(DebugVars { map })
});

// 公开 API:读
fn get_f32(guid: u64) -> f32 {
    let vars = VARS.read().unwrap();
    match vars.map.get(&guid) {
        Some(DebugValue::Float(f)) => *f,
        _ => panic!("GUID {} not f32", guid),
    }
}

// 公开 API:写
fn set_f32(guid: u64, val: f32) {
    let mut vars = VARS.write().unwrap();
    vars.map.insert(guid, DebugValue::Float(val));
}

// === 视图 1:Profiler 树 ===
fn view_profiler_tree() {
    println!("=== Profiler Tree ===");
    println!("  Player/");
    println!("    Movement/");
    println!("      Speed: {:.2}", get_f32(GUID_SPEED));
    println!("      HP:    {}", match VARS.read().unwrap().map.get(&GUID_HP) {
        Some(DebugValue::Int(i)) => i.to_string(),
        _ => "?".to_string(),
    });
}

// === 视图 2:曲线图 ===
fn view_history_graph() {
    println!("=== History Graph (Speed) ===");
    let speed = get_f32(GUID_SPEED);
    let bars = (speed as i32 / 2).max(1);
    println!("  [{}]{:.1}", "#".repeat(bars as usize), speed);
}

// === 视图 3:Inspector(可编辑) ===
fn view_inspector_edit(new_speed: f32) {
    println!("=== Inspector (editing speed -> {:.2}) ===", new_speed);
    set_f32(GUID_SPEED, new_speed);
}

// === 游戏主循环(模拟) ===
fn game_update() {
    let speed = get_f32(GUID_SPEED);
    println!("[game] player moves at speed {:.2}", speed);
}

fn main() {
    println!("--- Frame 1 ---");
    view_profiler_tree();
    view_history_graph();
    game_update();

    println!("\n--- Inspector edits speed to 8.0 ---");
    view_inspector_edit(8.0);

    println!("\n--- Frame 2 (after edit) ---");
    view_profiler_tree();
    view_history_graph();
    game_update();
}
```

跑:
```bash
cargo run
```

预期输出:
```
--- Frame 1 ---
=== Profiler Tree ===
  Player/
    Movement/
      Speed: 5.00
      HP:    100
=== History Graph (Speed) ===  [##]5.0
[game] player moves at speed 5.00

--- Inspector edits speed to 8.0 ---
=== Inspector (editing speed -> 8.00) ===

--- Frame 2 (after edit) ===
=== Profiler Tree ===
  Player/
    Movement/
      Speed: 8.00
      HP:    100
=== History Graph (Speed) ===
  [####]8.0
[game] player moves at speed 8.00
```

**关键观察**:Inspector 改一次,Frame 2 里**所有三个视图**(Profiler Tree、History Graph、game update)都看到 8.0。这就是 single source of truth 的效果。如果你用旧的"每视图自己缓存"方案,Frame 2 里 Profiler Tree 可能还是 5.0(它没读 store,只读自己的缓存)。

### 8.5 Troubleshooting

**问题1**:Rust 里 `static VARS: Lazy<RwLock<DebugVars>>` 编译错误。
原因:`HashMap` 不是 `Sync`,直接放 `static` 不行。
解决:用 `RwLock` 包一层(RwLock 是 Sync)。或用 `once_cell::race::OnceBox`。

**问题2**:跨线程访问 `get_f32` panic,"poisoned lock"。
原因:某个线程 panic 时持有了锁,锁被标记为"poisoned"。
诊断:看 panic stack trace,找到先 panic 的线程。
修复:那个线程的 bug 修了,poisoned lock 自然不再发生。或临时用 `lock().unwrap_or_else(|e| e.into_inner())` 强制忽略 poison(不推荐)。

**问题3**:GUID 冲突——两个不同字符串 hash 出同一个 u64。
原因:FNV-1a 在 64-bit 下碰撞概率极低(2^-64),但如果字符串很多(>100万),碰撞概率上升。
诊断:启动时遍历所有注册的 GUID,HashSet 检测重复。
修复:换更强的 hash(XXH3、SipHash),或用更长 GUID(u128)。

**问题4**:视图显示的还是旧值。
原因:视图自己 cache 了值,没从 store 读。
诊断:在视图函数加 `println!("read at {:?}, val={}", Instant::now(), get_f32(GUID))`,确认每次都查 store。
修复:删掉视图的 cache 逻辑,每次都从 store 查。

**问题5**:`Cell<f32>` 改值后,UI 还是显示旧值。
原因:immediate-mode UI 每帧重画,但你的"主循环"没每帧调 UI 绘制函数。
修复:把 UI 绘制函数放进主循环,每帧调一次。

### 8.6 性能基线

GUID 表的性能开销:

| 操作 | 时间 | 说明 |
|---|---|---|
| `get_f32(GUID)` | ~30 ns | RwLock read + HashMap lookup |
| `set_f32(GUID, val)` | ~50 ns | RwLock write + HashMap insert |
| Iterate all vars | O(n) | N=100 时 ~3 μs |

游戏主循环每帧查 50 个 debug 值:50 × 30ns = 1.5 μs/帧。60 FPS 下占总 frame budget(16ms)的 0.01%。完全可忽略。

对比 ECS(Bevy Resource 查询):同样 ~30 ns。两者性能相当,但 Bevy 编译期类型安全。

### 8.7 进阶:类型安全的 GUID 表

如果嫌类型擦除不爽,可以这样:

```rust
// 用 PhantomData 标记 GUID 的类型
struct Guid<T>(u64, std::marker::PhantomData<T>);

impl Guid<f32> {
    const fn new_f32(s: &str) -> Self {
        Guid(fnv1a(s), std::marker::PhantomData)
    }
}

const SPEED: Guid<f32> = Guid::new_f32("player/speed");

// 类型安全的 get——编译期保证只能拿 f32
fn get<T: 'static + Copy>(guid: Guid<T>) -> T { /* ... */ }

let speed: f32 = get(SPEED);  // OK
// let hp: f32 = get(HP_GUID_I32);  // 编译错误!
```

这是 Rust 类型系统的妙用——把 Casey 在 C 里手写的 runtime 检查,变成 Rust 编译期检查。代价是 API 复杂。但 debug vars 这种"类型已知"的场景,值得这么写。
