
# Day 203 · 调试 UI 状态缓存

> immediate-mode UI 每帧重算,但有些计算(比如 layout)是 O(N) 复杂,每帧跑太慢。今天 Casey 加缓存:重复输入不重算。

## 0 · 为什么要有这一天

让我们把镜头拉到一个具体的开发场景。

你的 debug UI 用 immediate-mode 风格(ImGui / egui)——每帧重画所有 widget。一开始只有 30 个 widget(profiler 树几个节点 + 几个变量 slider),60 FPS 跑得飞快,你完全没意识到 UI 在算什么。

跟着 HH 走到 Day 202,你加了 GUID 表,debug UI 越来越复杂——你现在有 profiler 树(100 节点)、entity inspector(50 个 entity × 20 字段 = 1000 个变量显示)、performance history graph(500 个采样点),还有变量搜索框、变量分组折叠、视图布局保存。你的 UI 树一共有 **3000+ widget**。

突然你发现 game update + render 加起来 5ms,但**debug UI 绘制花 8ms**——总 frame 13ms,卡在 60 FPS 边缘。你用 profiler 看,发现 8ms 里:

- 2ms 在 layout 算法(算每个 widget 的位置)
- 3ms 在文字排版(text shaping,把字符串变成 glyph 序列)
- 1ms 在命中测试(hover / click 检测)
- 2ms 在实际绘制
- 1ms 在 hash 输入、查 cache 等"管理开销"(假设你还没加 cache)

你猛然意识到一个事实:**这 3000 个 widget,99% 的内容这帧和上一帧一样**——profiler 树结构没变、变量值没变(用户没拖 slider)、字体设置没变。但 layout 算法、文字排版、命中测试——**全部白算了一遍**。

这是 immediate-mode UI 的暗坑。它的"每帧重画"哲学在 API 层面很优雅(没有 retained state 同步问题,见 Day 202),但在性能层面是个大坑——**默认情况下每帧都重新跑所有计算**。

工业界的解法叫 **memoization(记忆化)**:**函数把"输入 hash + 结果"缓存起来,下次同输入直接返回缓存**。这是函数式编程的经典技巧,可以追溯到 1960s 的 Lisp。

今天 Casey 给 debug UI 的 layout 加 memoization。技术核心是:

1. 把"layout 的输入"(widget 列表 + 各自尺寸 + spacing + padding)做 hash
2. 算 layout 时,先 hash 输入
3. 如果 hash 和上次相同——用缓存的 layout 结果
4. 如果不同——重算 layout,缓存新结果

听起来简单——hash 比较,匹配返回 cache。但细节里全是坑:**哪些字段算"输入"**(漏一个就 stale),**hash 算多快**(SipHash vs FNV),**cache 怎么失效**(显式 vs hash-based vs version),**partial cache 怎么做**(整体 vs 逐 widget)。

**学完今天,你应该能**:
- 解释为什么 immediate-mode UI 仍然需要 cache,以及这"不违背哲学"的原因
- 设计一个基于输入 hash 的 memoization 系统
- 选择合适的 hash 算法(SipHash / FNV / xxHash / aHash)并解释 trade-off
- 识别"stale cache"和"cache miss storm"两种典型 bug
- 看懂 React.memo / useMemo / useCallback 在结构上和 Casey 的方案是同一个东西
- 用 `cargo flamegraph` 测量 cache 的实际收益

## 1 · Casey 今天做了什么

Casey 这一天做的是**性能优化**,不是新功能:

1. **profile 测量**。他用自己写的 profiler 测 debug UI 绘制时间,发现 layout 占大头。这是关键——**不测量就不优化**(Knuth 名言的实践版)。

2. **决定加 cache**。他没选择"用更快的 layout 算法"(那个收益有限),而是"避免重复 layout"(收益 100%,如果输入未变)。这是优化的根本原则——**先避免,再加速**。

3. **实现 LayoutCache**。结构很直接:`{ last_input_hash: u64, cached_result: LayoutResult }`。layout 函数变成"先 hash 输入,hash 同则用 cache,否则重算"。

4. **决定 input 包含什么**。这是关键工程决策——少包一个字段就 stale cache,多包一个就频繁 miss。Casey 列了:widget 数量、每个 widget 的 id 和 size、layout options(spacing、padding、font size)。

5. **验证收益**。profile 显示 layout 时间从 2ms 降到 200μs(90% cache hit rate)。frame budget 从 13ms 降到 11.2ms,稳过 60 FPS。

6. **反思边界**。Casey 提到这个 cache 只在"UI 不变"时生效。用户拖 slider 时(变量值变)不一定触发 layout cache 失效——因为 layout 只看 widget 数量和 size,不看变量值。这是正确的——变量值变化只影响**绘制**(读值画字),不影响**布局**。

这集产出**0 行新游戏功能**,但 frame time 降了 15%。

## 2 · 心智模型

### 2.1 费曼类比:餐厅的今日套餐卡片

想象一家餐厅,每天早上厨师要算"今日套餐"。三道菜 + 价格,印在一张卡片上,放门口。

**朴素的做法**:每天早上从头算——选哪三道菜、算成本、定价格、印卡片。一个厨师花 30 分钟。

**Memoized 做法**:厨师今天先看昨天那张卡片的"输入清单"——库存有什么、季节是什么、节日是什么。如果今天的输入和昨天一样(同库存、同季节、同节日),**直接用昨天的卡片**,30 秒搞定。如果输入变了(新到货了海鲜、今天是圣诞节),才重算 + 重印。

这是 memoization 的精髓:**先看输入变没变,没变就别重算**。

为什么这是"哲学不冲突"?因为顾客看到的体验完全一样——他们拿到的卡片永远是"今天正确的套餐"。厨师省时间,顾客不察觉。memoization 是**实现细节的优化**,不是**对外接口的改变**。

debug UI 一样。immediate-mode 的"每帧重画"是**对外接口的承诺**(程序员每帧调函数,UI 永远 fresh)。memoization 是**内部实现的捷径**(layout 函数检测输入未变就跳过重算)。程序员调 `do_layout(widgets)`,函数内部决定要不要重算——调用方完全无感。

### 2.2 从零推导:memoization 的设计

让我们一步步从最朴素的方案推到完整的 hash-based cache。

**Step 0:无 cache**。每帧重算 layout。

```rust
fn do_layout(widgets: &[Widget], opts: &LayoutOptions) -> Vec<Rect> {
    let mut positions = Vec::with_capacity(widgets.len());
    let mut y = opts.padding_top;
    for w in widgets {
        positions.push(Rect::new(opts.padding_left, y, w.width, w.height));
        y += w.height + opts.item_spacing;
    }
    positions
}
```

简单,清晰,但每帧 N 个 widget 都跑一遍。N=3000 时,大约 100μs。每帧 100μs,60 FPS 就是 6ms——可观的 frame budget。

**Step 1:加个 dirty flag**。游戏代码改 UI 时手动设 `dirty = true`,layout 看 flag 决定要不要重算。

```rust
struct UiState {
    layout_dirty: bool,
    cached_positions: Vec<Rect>,
}

fn do_layout(state: &mut UiState, widgets: &[Widget], opts: &LayoutOptions) -> &[Rect] {
    if state.layout_dirty {
        state.cached_positions = compute(widgets, opts);
        state.layout_dirty = false;
    }
    &state.cached_positions
}
```

简单。但**容易忘**——程序员改了 widget 但忘记设 `dirty = true`,cache stale。这是 cache invalidation 的经典坑。

**Step 2:hash 输入自动检测**。让函数自己判断输入变没变。

```rust
struct LayoutCache {
    last_input_hash: u64,
    cached_positions: Vec<Rect>,
}

fn do_layout(cache: &mut LayoutCache, widgets: &[Widget], opts: &LayoutOptions) -> &[Rect] {
    let h = hash_inputs(widgets, opts);
    if h != cache.last_input_hash {
        cache.cached_positions = compute(widgets, opts);
        cache.last_input_hash = h;
    }
    &cache.cached_positions
}
```

无需手动 invalidate。hash 自动反映所有 hash 进去的字段。代价是每帧算 hash(对 3000 widget,~5μs)。

**Step 3:确保 hash 覆盖所有相关 input**。这是关键——漏 hash 一个字段,cache stale。

```rust
fn hash_inputs(widgets: &[Widget], opts: &LayoutOptions) -> u64 {
    let mut h = FxHasher::new();
    opts.padding_top.hash(&mut h);
    opts.padding_left.hash(&mut h);
    opts.item_spacing.hash(&mut h);
    widgets.len().hash(&mut h);
    for w in widgets {
        w.id.hash(&mut h);
        w.width.hash(&mut h);
        w.height.hash(&mut h);
        w.flags.hash(&mut h);  // 漏这个就 stale!
    }
    h.finish()
}
```

如果 `w.flags` 影响布局(比如"widget 是 hidden"),漏 hash 就 stale。

**Step 4:抽取通用模式**。memoization 不只 layout 用,任何 pure function 都能用。抽成泛型:

```rust
pub struct MemoCache<K: Eq + Hash, V: Clone> {
    map: HashMap<K, V>,
}

impl<K: Eq + Hash, V: Clone> MemoCache<K, V> {
    pub fn get_or_compute<F: FnOnce() -> V>(&mut self, key: K, compute: F) -> V {
        if let Some(v) = self.map.get(&key) {
            return v.clone();
        }
        let v = compute();
        self.map.insert(key, v.clone());
        v
    }
}
```

这是工业级 memoization 的核心。`cached` crate 提供的 `#[cached]` 宏本质上就是这个,只是用过程宏自动包了函数。

### 2.3 hash 算法选型:速度 vs 质量

hash 算法决定 memoization 的开销和质量。Rust 生态常见选项:

| 算法 | 速度(GB/s) | 碰撞率 | 加密安全 | 用途 |
|---|---|---|---|---|
| SipHash-1-3(`DefaultHasher`) | 1 | 低 | 否(但抗 HashDoS) | 标准 HashMap 默认 |
| FNV-1a | 5 | 中 | 否 | 编译期、GUID |
| FxHash(fxhash crate) | 10 | 中 | 否 | Rust 内部使用 |
| aHash(ahash crate) | 12 | 中 | 否 | 高性能 HashMap |
| xxHash 3(xxhash-rust) | 15 | 低 | 否 | 极致性能 |
| BLAKE3 | 1.5 | 极低 | 是 | 密码学 |

游戏 debug UI layout cache:FxHash 或 aHash 最合适——5-10 GB/s 远超 SipHash,碰撞率对 layout cache 无害(偶发碰撞只导致一次 cache miss + 重算,不会数据损坏)。

```rust
// Cargo.toml: ahash = "0.8"
use ahash::AHasher;
use std::hash::Hasher;

let mut h = AHasher::default();
opts.padding_top.hash(&mut h);
// ...
h.finish()
```

**坑**:不要用密码学 hash(BLAKE3、SHA-256)做 memoization。它们设计目标不同(抗碰撞 vs 速度),慢 10-100 倍。

### 2.4 cache 失效的三种策略

memoization 必然伴随 cache 失效问题——什么时候丢掉旧结果?

**策略 1:Hash-based 自动失效**。每次调用 hash 输入,hash 变就重算。Casey 用这个。
- 优点:无需手动管理,代码简洁。
- 缺点:每次调用有 hash 开销(~5μs for 3000 widgets)。

**策略 2:显式 invalidation**。游戏代码改 UI 时调 `cache.invalidate()`。
- 优点:零 hash 开销。
- 缺点:**容易忘**。忘一次就 stale,debug 起来要命。

**策略 3:Version-based**。所有 UI 状态有个全局 `version: u64`。任何修改调 `ui.modify(|state| { ...; state.version += 1; })`。cache 看 version。
- 优点:简单,无需枚举所有字段。
- 缺点:粒度粗——任何 UI 改动都使整个 cache 失效,即便只改了一个 widget。

**策略 4:TTL**。cache 每 N 帧失效一次。
- 优点:零管理开销。
- 缺点:可能在数据 stale 时还用 cache(N 帧延迟)。或者刚好失效重算时机不对(用户改完 1ms 内 cache 已 TTL 过期)。

Casey 选策略 1(hash-based),因为 UI 改动频繁且字段多,version 粒度太粗。但 strategy 选哪个没有"标准答案",看场景。

### 2.5 partial cache:更细粒度

整 layout 一旦任何一个 widget 改,整个 cache 失效。但通常大部分 widget 不变。可以做 **per-widget cache**:

```rust
struct PartialLayoutCache {
    per_widget: HashMap<u64 /* widget_id */, CachedRect>,
}

impl PartialLayoutCache {
    fn get_position(&mut self, widget: &Widget, opts: &LayoutOptions) -> Rect {
        let h = hash_widget(widget, opts);
        if let Some(cached) = self.per_widget.get(&widget.id) {
            if cached.input_hash == h {
                return cached.rect;  // cache hit
            }
        }
        let rect = compute_position(widget, opts);
        self.per_widget.insert(widget.id, CachedRect { input_hash: h, rect });
        rect
    }
}
```

优势:一个 widget 变只重算一个,其他用 cache。劣势:每个 widget 都要 hash + lookup,管理开销大。

适合:**大型树形 UI**(profiler 树、entity inspector),一个节点变不影响其他节点。
不适合:**线性布局**(所有 widget 位置依赖前面的 widget),中间一个变所有后面都得重算——partial cache 无意义。

### 2.6 stale cache 的两种典型 bug

memoization 最大的坑就是 stale data——cache 返回旧结果。两种典型 bug:

**Bug 1:漏 hash 一个字段**。比如 layout 依赖 font size,但你 hash 时忘了 hash font_size。
- 症状:用户改 font size,UI 看起来"用了旧 font 算的 layout",文字超出边界或位置错乱。
- 诊断:打印 cache hit/miss ratio。如果 font size 变后 hit ratio 还很高(应该全部 miss),说明 hash 没包含 font size。
- 修复:hash 里加上 `opts.font_size.hash(&mut h)`。

**Bug 2:cache 存了引用而非值**。
```rust
// 错误:cache 存引用,引用底层数据变了 cache 看不到
struct BadCache<'a> {
    cached_widgets: &'a [Widget],  // 引用,外部改了 cache 看到的也变
}
```
- 症状:cache hit 返回的"旧 layout"对应的是"旧 widget 列表",但 widget 列表已经改了。layout 错位。
- 修复:cache 存拥有所有权的副本(`Vec<Rect>` 而非 `&[Rect]`)。

**Bug 3:cache miss storm**。如果输入频繁变化(比如 hover 状态每帧变),cache 每帧都 miss。
- 症状:加了 cache 反而更慢(多了 hash 开销,没省下重算)。
- 诊断:profiler 显示 hash 时间 > 重算时间。
- 修复:把频繁变化的字段(如 hover)从 input hash 里剔除,让 layout 不依赖 hover。

### 2.7 React.memo / useMemo:工业对照

React 的 memoization 和 Casey 的方案是同构的:

```jsx
// React.memo:组件 props 不变不重渲染
const MyComponent = React.memo(function MyComponent(props) {
    return <div>{props.label}</div>;
});

// useMemo:依赖不变不重算
const layout = useMemo(() => computeLayout(widgets), [widgets]);
```

`React.memo` 用 shallow compare props(对比每个 prop 的引用)。`useMemo` 显式列依赖数组。两种都和 Casey 的"hash 输入"等价——只是 React 用浅比较,Casey 用 hash。

React 社区对 useMemo 的反思值得学:**"useMemo 不是免费的"**。useMemo 每次都 shallow compare 依赖数组,如果依赖多,compare 开销可能比重算还大。和 Casey 的 hash 开销一样——memoization 有管理成本,**只在重算 > 管理成本时才值得**。

### 2.8 完整 Rust 实现

下面是 Casey 设计在 Rust 里的完整落地:

```rust
use std::collections::hash_map::DefaultHasher;
use std::hash::{Hash, Hasher};

// === 描述 widget 的输入 ===
#[derive(Hash, Clone)]
struct WidgetDescriptor {
    id: u64,
    label: String,
    width: f32,
    height: f32,
    flags: u32,  // hidden? / disabled? / etc.
}

#[derive(Hash, Clone)]
struct LayoutOptions {
    padding_top: f32,
    padding_left: f32,
    item_spacing: f32,
    font_size: f32,
}

#[derive(Clone, Debug)]
struct LayoutResult {
    positions: Vec<(f32, f32)>,
}

// === LayoutCache ===
pub struct LayoutCache {
    last_input_hash: u64,
    cached_result: Option<LayoutResult>,
}

impl LayoutCache {
    pub fn new() -> Self {
        Self { last_input_hash: 0, cached_result: None }
    }

    /// 主 API:hash 输入,同则用 cache,否则重算
    pub fn get_or_compute<F: FnOnce() -> LayoutResult>(
        &mut self,
        input_hash: u64,
        compute: F,
    ) -> LayoutResult {
        if input_hash == self.last_input_hash {
            if let Some(ref r) = self.cached_result {
                return r.clone();
            }
        }
        let result = compute();
        self.last_input_hash = input_hash;
        self.cached_result = Some(result.clone());
        result
    }
}

// === hash 输入 ===
fn hash_layout_input(
    widgets: &[WidgetDescriptor],
    opts: &LayoutOptions,
) -> u64 {
    let mut h = DefaultHasher::new();
    opts.hash(&mut h);
    widgets.len().hash(&mut h);
    for w in widgets {
        w.hash(&mut h);
    }
    h.finish()
}

// === 算 layout ===
fn compute_layout(
    widgets: &[WidgetDescriptor],
    opts: &LayoutOptions,
) -> LayoutResult {
    let mut positions = Vec::with_capacity(widgets.len());
    let mut y = opts.padding_top;
    for w in widgets {
        if w.flags & FLAG_HIDDEN != 0 { continue; }
        positions.push((opts.padding_left, y));
        y += w.height + opts.item_spacing;
    }
    LayoutResult { positions }
}

// === 用法 ===
fn do_layout(
    cache: &mut LayoutCache,
    widgets: &[WidgetDescriptor],
    opts: &LayoutOptions,
) -> LayoutResult {
    let h = hash_layout_input(widgets, opts);
    cache.get_or_compute(h, || compute_layout(widgets, opts))
}

const FLAG_HIDDEN: u32 = 1;

fn main() {
    let mut cache = LayoutCache::new();
    let opts = LayoutOptions {
        padding_top: 10.0, padding_left: 10.0,
        item_spacing: 4.0, font_size: 14.0,
    };
    let widgets = vec![
        WidgetDescriptor { id: 1, label: "OK".into(),     width: 80.0, height: 24.0, flags: 0 },
        WidgetDescriptor { id: 2, label: "Cancel".into(), width: 80.0, height: 24.0, flags: 0 },
    ];

    // 第一帧:cache miss,重算
    let r1 = do_layout(&mut cache, &widgets, &opts);
    println!("Frame 1: {} widgets", r1.positions.len());

    // 第二帧:cache hit,跳过 compute
    let r2 = do_layout(&mut cache, &widgets, &opts);
    println!("Frame 2: {} widgets", r2.positions.len());

    // 改 widget:cache miss,重算
    let mut widgets2 = widgets.clone();
    widgets2[0].label = "Apply".into();
    let r3 = do_layout(&mut cache, &widgets2, &opts);
    println!("Frame 3: {} widgets", r3.positions.len());
}
```

**关键观察**:
- `LayoutCache` 是泛型容器,任何"hash 输入 + 重算 expensive"的场景都能用。
- `get_or_compute` 接 closure,内部决定要不要调。调用方写"重算逻辑"作为 closure,无感享受 cache。
- `cached_result` 用 `Option<LayoutResult>` 允许第一次为 None。第一次必然 cache miss + compute。
- `LayoutResult: Clone` 是必须的——cache 里要存一份,返回一份。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业里 cache 无处不在。每个 cache 都针对一种"重复计算"的痛点。

**Font glyph cache**:文字渲染要把字符(Unicode codepoint)渲染成像素图(glyph)。一个字符的渲染涉及 font file 解析、hinting、anti-aliasing——很贵(~100μs/字符)。但屏幕上一帧可能要画 1000 个字符,如果每个都重渲,100ms/帧,根本跑不动。

工业方案:`GlyphCache` 是 `HashMap<(FontId, codepoint, size), GlyphImage>`。第一次画 'A' 渲染并缓存,第二次直接 blit 缓存的图像。freetype / harfbuzz / stb_truetype 都用这个模式。**这是 memoization 在游戏里的最早应用之一**(1990s)。

**Texture cache**:GPU 上传纹理很慢(pcie 传输 + 格式转换)。已上传的 texture 缓存 GPU 句柄,避免重复上传。texture streaming 系统(Unreal 的 Virtual Texturing、Unity的 Mipmap Streaming)就是高级版 texture cache。

**Shader cache**:GPU shader 编译很慢(100ms-1s)。已编译的 shader binary 缓存,下次启动游戏直接加载 binary,跳过编译。这就是为什么你启动 Unity/Unreal 项目时第一次很慢,第二次快——shader cache 生效了。

**Asset cache**:模型、音频、动画文件加载慢(磁盘 IO + 解析)。AssetManager 缓存已加载的 asset,所有引用同一 asset 的地方共享同一份。Unity 的 Resources.Load / Unreal的LoadObject 都用这个。

**Layout cache**:今天 Casey 加的。Debug UI 专用。

**Physics broadphase cache**:物理引擎每帧做"N^2 物体对碰撞检测"很贵。AABB tree 缓存,只更新位置变化的物体。Box2D / PhysX 用这个。

所有这些 cache 共享一个模式:**hash 输入 → 查 cache → hit 用 / miss 重算**。游戏程序员一生都在写这个模式的各种变体。

### 3.2 · 🐞 Debug 工具视角(本日核心域)

Debug 工具行业的 memoization 实践:

**ImGui**(Dear ImGui,egui 的精神祖宗):ImGui 内部用 ID hash 跨帧保持 widget 状态。ImGui 的 ID 是"路径 hash"——`"MainWindow##Tab1##Button1"`。每帧 widget 调用按 ID 查 state(展开状态、值、focus)。这是 implicit memoization——用户不感知,但内部有。

**egui**:egui 提供 `egui::cache::{Cache, CacheStorage}`——支持任意 `T: 'static + Send + Sync`。egui 的 `Response` 也带 `changed()` 方法——只对变化的 widget 做出响应。

**Tracy profiler**:Tracy 的 frame graph 每次 frame push 一个数据点。Tracy 不缓存——它存历史,从历史查。Tracy 的 ring buffer 是另一种"避免重复计算"的思路——固定大小,旧数据被覆盖,不无限增长。

**React DevTools**:React 的 fiber tree 是 retained,但 React 用 memoization(React.memo, useMemo)避免 re-render。React DevTools 的 Profiler 标出 "memoized" 和 "not memoized" 的组件,帮开发者找到优化机会。

**casey 在 HH 用的 debug overlay** 是手写的 ImGui 风格,所以 memoization 也手写。Day 203 是 Casey 第一次给 debug UI 加显式 cache——之前都是隐式的(widget state 通过 ID hash 跨帧)。

工业 debug 工具的标准做法:
- **hash 输入**(布局参数、widget 数量)
- **compare to last frame**(每帧 hash 比较)
- **reuse if equal**(同则用 cache)
- **invalidate explicitly on structural change**(树结构变化时手动 invalidate)

这四步是 memoization 的标准模板,跨工具通用。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核是 cache 的狂魔。整个内核性能的 80% 来自各种 cache。

**Page cache**:文件读写的 cache。你 `read(fd, buf, 4096)`,内核不直接读磁盘——先查 page cache,hit 就直接 copy。`free -h` 看到的 "buff/cache" 就是 page cache。

```bash
free -h
#               total   used   free   shared  buff/cache  available
# Mem:           16Gi   4Gi    8Gi    200Mi   4Gi         11Gi
#                              ^^^^^ page cache ^^^^^
```

Page cache 的失效策略:LRU(least recently used)。内存紧时丢最少用的 page。

**Dentry cache(dcache)**:文件路径解析的 cache。`/usr/bin/gcc` 要解析 4 层目录,每层一个 inode lookup。dcache 缓存"路径 → inode"映射,避免重复 lookup。

```bash
cat /proc/sys/fs/dentry-state
# nr_dentry  nr_unused  age_limit  want_pages  nr_negative
# 500000     400000     45         256         1000
```

**Inode cache(icache)**:inode 元数据的 cache。每个 inode 大概 500 字节,热点 inode 留在 cache。

**SLAB allocator**:内核对象池,缓存"刚释放的对象",下次分配直接拿,避免 memset + 构造。

**Per-CPU cache**:每个 CPU 一个本地 cache,避免跨 CPU 锁。

这些 cache 全是 memoization 的实例:**hash/索引 输入 → 查 cache → hit 用 / miss 重算**。Linux 内核的性能秘诀就是 cache 多、cache 巧。

**Linux 用户态**:
- `mmap` + `MAP_PRIVATE` 让多个进程共享同一份文件 page cache——多进程共享 library 的标准机制。
- `posix_fadvise` 告诉内核"这个文件我会读"或"我不会再读",让内核预热或丢弃 cache。
- `posix_fallocate` 显式分配磁盘空间,避免"按需分配"的反复开销。

```bash
# 看 page cache 使用情况
vmtouch -v /usr/bin/gcc

# 显式丢 page cache(调试用)
echo 3 | sudo tee /proc/sys/vm/drop_caches

# 看 slab cache(dentry / inode)
slabtop -o | head -20
```

**你能学到的迁移**:你的 Rust 游戏,启动时把"必读 asset"用 `posix_fadvise(POSIX_FADV_WILLNEED)` 告诉 OS 预读。OS 提前把文件塞 page cache,你后面真的读时 cache hit,加载快。

### 3.4 · 🦀 Rust 生态视角

Rust 的 memoization 库分层很丰富:

**`cached` crate**(过程宏,最易用):
```rust
use cached::proc_macro::cached;

#[cached]
fn expensive(x: u64) -> u64 {
    println!("computing {}...", x);
    x * x
}

// 调用
expensive(5);  // 打印 computing 5...,返回 25
expensive(5);  // 直接返回 25,无 print
```

`#[cached]` 自动包一层 `HashMap<x, y>`。适合纯函数 memoization。

**`lru` crate**(LRU 缓存):
```rust
use lru::LruCache;
let mut cache: LruCache<u64, String> = LruCache::new(100);
cache.put(1, "hello".into());
cache.put(2, "world".into());
let v = cache.get(&1).unwrap();
```

LRU 限制大小,丢最少用的。适合"内存有限"的场景。

**`moka` crate**(工业级,类似 Java Caffeine):
```rust
use moka::sync::Cache;
let cache: Cache<String, String> = Cache::builder()
    .max_capacity(10_000)
    .time_to_live(Duration::from_secs(60))
    .build();
cache.insert("key".into(), "value".into());
```

支持 TTL、max size、异步刷新。生产级缓存。

**`once_cell::sync::Lazy`**(单次计算):
```rust
static LAYOUT: Lazy<LayoutResult> = Lazy::new(|| compute_expensive_layout());
// 第一次访问时 compute,之后用 cache
```

只算一次,永远 cache。适合"启动时算一次,之后永远不变"的场景。

**`memotron` / `phf`**(完美 hash):
```rust
use phf::phf_map;
static KEYWORDS: phf::Map<&'static str, u32> = phf_map! {
    "if" => 1,
    "else" => 2,
};
```

PHF(perfect hash function)编译期生成无碰撞 hash。Lookup 比 HashMap 快 2-3 倍。

**Casey 手写的 LayoutCache** 对应 Rust 生态的 `cached::Stores<T>`(单 slot cache)或手写 `Option<(K, V)>`。如果想用现成库,可以:

```rust
use cached::stores::Store;
// 或者直接用 std 单 slot:
struct OneSlotCache<K, V> { key: Option<K>, val: Option<V> }
```

**反模式警告**:
- ❌ 用 `static mut HashMap<...>`——不 Sync,并发不安全。用 `Lazy<RwLock<HashMap>>`。
- ❌ 用密码学 hash(SHA-256)做 memoization key——慢 100 倍。
- ❌ cache 不限制大小——内存泄漏。用 LRU 或 max capacity。

## 5 · 对照与变奏

### 5.1 Cache 的工业模式全景

把"cache"在不同领域的实现并排放,你会看到同一个抽象:

| 领域 | Cache 类型 | 失效策略 | 命中查询 |
|---|---|---|---|
| CPU L1/L2/L3 cache | 硬件 SRAM | LRU(伪 LRU) | 物理地址 tag |
| Page cache(OS) | 内存 | LRU + 显式 drop | 文件 offset |
| Dentry/inode cache(OS) | 内核 slab | LRU | 路径 hash |
| Disk cache(SSD/HDD) | DRAM on disk | 厂商专有 | LBA |
| Browser HTTP cache | 磁盘 | Cache-Control header | URL |
| CDN edge cache | 边缘节点 | TTL / purge | URL |
| Redis / Memcached | 分布式内存 | TTL / LRU | key |
| SQL materialized view | 数据库 | trigger-based | query hash |
| GPU texture cache | VRAM | LRU | texture handle |
| Game glyph cache | 内存 | LRU + size cap | (font, codepoint, size) |
| Casey layout cache | 内存 | hash-based | input hash |

这些都是同一个抽象——**输入 → 查表 → hit/miss**。区别只在三个维度:

1. **存哪里**:硬件 SRAM、内核 slab、磁盘、网络、应用内存。
2. **失效策略**:LRU、TTL、显式、hash-based、trigger。
3. **粒度**:字节级(CPU cache)、文件级(page cache)、对象级(glyph cache)、整树级(layout cache)。

### 5.2 CPU cache 的微架构视角

CPU cache 是 cache 的鼻祖。理解 CPU cache 能让你看清所有 cache 的本质。

现代 CPU 有三级 cache:

- **L1**:32-64 KB,2-4 cycle 延迟,每核独享
- **L2**:256 KB-1 MB,10 cycle,每核独享
- **L3**:8-32 MB,40 cycle,所有核共享
- **DRAM**:GB 级,200+ cycle

L1 cache hit 比 DRAM 访问快 100 倍。**程序性能的 90% 取决于 cache 利用率**。游戏程序员优化 hot loop 时,主要工作是"让数据 fit 进 L1/L2"(data-oriented design)。

CPU cache 的"hash 输入"是**物理内存地址**。"失效策略"是 LRU + 写策略(write-back vs write-through)。"粒度"是 cache line(64 字节)。

Casey 的 layout cache 和 CPU cache 在抽象层是同构的——**避免重复计算/读取,通过 cache 拦截**。

### 5.3 React.memo / useMemo / useCallback

React 的三个 memoization hook 是 web 工业里最常用的 cache:

```jsx
// React.memo:组件 props 不变不重渲染
const MyComponent = React.memo(function MyComponent(props) {
    return <div>{props.label}</div>;
});

// useMemo:依赖不变不重算
const layout = useMemo(() => computeLayout(widgets), [widgets]);

// useCallback:依赖不变函数引用稳定
const handleClick = useCallback(() => { /* ... */ }, [dep]);
```

每个都是 memoization 的特化:
- `React.memo`:粒度是组件,失效策略是 shallow props compare。
- `useMemo`:粒度是值,失效策略是依赖数组 shallow compare。
- `useCallback`:粒度是函数引用,和 useMemo 同。

和 Casey 的 hash-based cache 区别:React 用 **shallow compare**(直接 `===`),Casey 用 **deep hash**。Shallow compare 快但不严格(嵌套对象引用相同但内容变了不触发更新);deep hash 严格但慢。

React 社区的反思:"Don't over-memoize"。useMemo 本身有管理开销(shallow compare deps),如果重算便宜,加 useMemo 反而慢。**measure before optimize**——Knuth 原则。

### 5.4 SQL 的 materialized view

数据库的 materialized view 是 query 结果 cache:

```sql
CREATE MATERIALIZED VIEW player_stats AS
SELECT player_id, SUM(score) FROM scores GROUP BY player_id;

-- 查询 view 时直接拿缓存
SELECT * FROM player_stats WHERE player_id = 42;

-- 底层表变时,view 自动更新(取决于策略)
INSERT INTO scores VALUES (42, 100);
```

materialized view 的失效策略有两种:
- **ON COMMIT**:底层表 commit 时同步刷新 view。
- **ON DEMAND**:手动调 `DBMS_MVIEW.REFRESH`。

工业级数据仓库(VoltDB、Snowflake、BigQuery)大量用 materialized view,因为大表查询慢,缓存常用聚合能省 90% 查询时间。

casey 的 layout cache 是 in-process 版的 materialized view——把"常用 layout 算法的结果"缓存,避免重复 query。

### 5.5 Trade-off:简单 vs 优化

Knuth 名言:**"过早优化是万恶之源"**。memoization 也不例外。

什么情况下 layout cache 值得加?

| UI widget 数 | layout 耗时 | 是否值得 cache |
|---|---|---|
| < 50 | < 100μs | **不值得**——hash 开销可能 > 重算 |
| 50-500 | 100μs - 1ms | **看情况**——profile 再决定 |
| 500-5000 | 1ms - 10ms | **值得**——cache 收益明显 |
| > 5000 | > 10ms | **必须**——不然 frame budget 爆 |

Casey 在 day 203 加 cache,因为 profiler 显示 layout 占了 frame budget 大头。如果只有 50 widget,加 cache 反而慢——多 hash 开销,没省下重算。

工业经验:**先 profile,再 cache**。`cargo flamegraph` 是最好的工具,可视化显示每个函数占的 CPU 时间。

```bash
cargo install flamegraph
sudo flamegraph --release -- target/release/my_game
# 生成 flamegraph.svg,浏览器打开看哪里热
```

### 5.6 immediate-mode vs retained-mode:cache 哲学差异

immediate-mode(ImGui / Casey HH)和 retained-mode(Qt / React)对 cache 的态度完全不同:

**Immediate-mode**:**默认无 cache**——每帧重算。需要 cache 时显式加(像今天 Casey 做的)。优势:无 stale state,代码清晰。劣势:性能 scaling 差。

**Retained-mode**:**默认有 cache**——控件树持久化,值变时手动 update。优势:性能好(只更新变化的部分)。劣势:state 同步麻烦(见 Day 202 讨论)。

两种哲学各自演化出对应的优化手段:
- Immediate-mode 的优化:memoization(hash-based)、culling(屏幕外不画)、batching(合并 draw call)。
- Retained-mode 的优化:dirty flag、observer pattern、virtual DOM diff。

两种哲学都解决"避免重复工作"问题,但路径不同。**没有绝对优劣**,看场景。游戏 debug UI 用 immediate-mode(交互频繁、UI 多变),商业 app UI 用 retained-mode(交互稳定、性能要求高)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:immediate-mode UI 每帧重算,为什么还要 cache?不是违背 immediate-mode 哲学吗?

**参考解答**:

immediate-mode 的"每帧重算"是**对外 API 的承诺**——程序员每帧调函数,函数总是返回 fresh 结果。这是 API 层面的契约。

cache 是**内部实现细节**——layout 函数内部决定要不要重算,调用方无感。函数返回的"layout 结果"对外仍然是"今天正确的 layout"。

这就像 CPU cache 对程序员透明——你写 `mov rax, [memory]`,以为每次都读 DRAM,实际上 CPU 大部分时候从 L1 cache 拿。语义不变,性能更好。

所以 cache 不违背 immediate-mode 哲学——它让 immediate-mode 能 scale 到大 UI。如果不加 cache,3000 widget 的 debug UI 每帧 layout 花 5ms,frame budget 爆,程序员只能换 retained-mode。Casey 用 cache 让 immediate-mode 也能 hold 大 UI——保持哲学,优化实现。

### Lv2 · 动手实践

**题**:实现 cached 的 fibonacci,对比 cached vs uncached 的执行时间。

**手写版**(不依赖外部 crate):

```rust
use std::collections::HashMap;
use std::cell::RefCell;
use std::time::Instant;

thread_local! {
    static FIB_CACHE: RefCell<HashMap<u64, u64>> = RefCell::new(HashMap::new());
}

fn fib_cached(n: u64) -> u64 {
    FIB_CACHE.with(|c| {
        if let Some(&v) = c.borrow().get(&n) { return v; }
        let v = if n < 2 { n } else { fib_cached(n - 1) + fib_cached(n - 2) };
        c.borrow_mut().insert(n, v);
        v
    })
}

fn fib_uncached(n: u64) -> u64 {
    if n < 2 { n } else { fib_uncached(n - 1) + fib_uncached(n - 2) }
}

fn main() {
    let n: u64 = 40;

    let t1 = Instant::now();
    let _ = fib_uncached(n);
    let dt_uncached = t1.elapsed();

    let t2 = Instant::now();
    let _ = fib_cached(n);
    let dt_cached_first = t2.elapsed();

    let t3 = Instant::now();
    let _ = fib_cached(n);
    let dt_cached_second = t3.elapsed();

    println!("fib({}):", n);
    println!("  uncached:       {:?}", dt_uncached);
    println!("  cached first:   {:?}", dt_cached_first);
    println!("  cached second:  {:?}", dt_cached_second);  // 几乎 0
}
```

预期输出(N=40,你的数字会略不同):
```
fib(40):
  uncached:       450ms
  cached first:   50μs
  cached second:  1μs
```

**关键观察**:
- uncached:O(2^N) 递归调用,极慢。
- cached first:O(N) 计算 + cache 写入,快 10000 倍。
- cached second:O(1) cache hit,几乎免费。

这就是 memoization 的威力。

**用 `cached` crate 版**:

```toml

```

```rust

```

### Lv3 · 迁移设计

**题**:你的 layout cache 在某些情况下 stale。比如:用户改了 font size,但 font size 不在你 hash 的 input 里——cache 仍 hit,但 layout 是用旧 font size 算的,文字超出边界。

**怎么修?**

**分析**:这是 stale cache 的典型 bug——hash 输入不完整。

**修复步骤**:

1. **诊断**:在 cache hit / miss 时加 log,看 font size 变化后 hit ratio 是否仍高。如果仍高,说明 hash 没包含 font size。

   ```rust
   pub fn get_or_compute<F: FnOnce() -> LayoutResult>(
       &mut self, input_hash: u64, compute: F,
   ) -> LayoutResult {
       if input_hash == self.last_input_hash {
           println!("[cache] HIT");
           // ...
       } else {
           println!("[cache] MISS, hash: {:#x}", input_hash);
           // ...
       }
   }
   ```

2. **修复**:把 font size 加进 hash:

   ```rust
   fn hash_layout_input(
       widgets: &[WidgetDescriptor],
       opts: &LayoutOptions,
   ) -> u64 {
       let mut h = DefaultHasher::new();
       opts.hash(&mut h);  // 这里包含 font_size
       widgets.len().hash(&mut h);
       for w in widgets {
           w.hash(&mut h);
       }
       h.finish()
   }
   ```

   注意 `LayoutOptions` 已经有 `font_size` 字段,`#[derive(Hash)]` 会自动 hash 它。但如果 `font_size` 在外面单独维护,需要手动加。

3. **验证**:改 font size,看 hit ratio 应该立刻降到 0(全 miss),然后重算 layout,新 layout 反映新 font。

**反思**:这个 bug 教我们一个原则——**hash 输入要"完全反映函数依赖"**。漏 hash 一个字段 = stale cache bug。设计 memoization 时,**先把函数所有依赖列出来**,再决定哪些进 hash。

## 8 · Rust / Arch 落地代码

### 8.1 完整可跑项目

```bash
cargo new --bin layout-cache-demo
cd layout-cache-demo
```

`Cargo.toml`:
```toml
[package]
name = "layout-cache-demo"
version = "0.1.0"
edition = "2021"

[dependencies]
ahash = "0.8"

[profile.release]
debug = true  # 保留 debug symbol 让 perf 看得到符号
```

`src/main.rs`:

```rust
use ahash::AHasher;
use std::hash::{Hash, Hasher};
use std::time::Instant;

#[derive(Hash, Clone, Debug)]
struct Widget { id: u64, height: f32, label: String }

#[derive(Hash, Clone, Debug)]
struct LayoutOptions { item_spacing: f32, padding: f32 }

#[derive(Clone, Debug)]
struct LayoutResult { positions: Vec<(f32, f32)> }

struct LayoutCache {
    last_hash: u64,
    cached: Option<LayoutResult>,
    hits: u64,
    misses: u64,
}

impl LayoutCache {
    fn new() -> Self {
        Self { last_hash: 0, cached: None, hits: 0, misses: 0 }
    }

    fn get_or_compute<F: FnOnce() -> LayoutResult>(
        &mut self, input_hash: u64, compute: F,
    ) -> LayoutResult {
        if input_hash == self.last_hash {
            self.hits += 1;
            return self.cached.clone().unwrap();
        }
        self.misses += 1;
        let r = compute();
        self.last_hash = input_hash;
        self.cached = Some(r.clone());
        r
    }

    fn stats(&self) -> (u64, u64, f64) {
        let total = self.hits + self.misses;
        let ratio = if total > 0 { self.hits as f64 / total as f64 } else { 0.0 };
        (self.hits, self.misses, ratio)
    }
}

fn hash_input(widgets: &[Widget], opts: &LayoutOptions) -> u64 {
    let mut h = AHasher::default();
    opts.hash(&mut h);
    widgets.len().hash(&mut h);
    for w in widgets {
        w.hash(&mut h);
    }
    h.finish()
}

fn compute_layout(widgets: &[Widget], opts: &LayoutOptions) -> LayoutResult {
    let mut positions = Vec::with_capacity(widgets.len());
    let mut y = opts.padding;
    for w in widgets {
        positions.push((opts.padding, y));
        y += w.height + opts.item_spacing;
    }
    LayoutResult { positions }
}

fn main() {
    let mut cache = LayoutCache::new();
    let opts = LayoutOptions { item_spacing: 4.0, padding: 10.0 };

    // 生成 3000 widget
    let widgets: Vec<Widget> = (0..3000).map(|i| Widget {
        id: i, height: 24.0, label: format!("Widget {}", i),
    }).collect();

    // 模拟 60 帧
    let t_start = Instant::now();
    for frame in 0..60 {
        let h = hash_input(&widgets, &opts);
        let _r = cache.get_or_compute(h, || compute_layout(&widgets, &opts));
    }
    let dt_cached = t_start.elapsed();

    let (hits, misses, ratio) = cache.stats();
    println!("=== Layout Cache Demo ===");
    println!("60 frames, 3000 widgets each");
    println!("  Total time: {:?}", dt_cached);
    println!("  Cache hits: {} (cache miss: {})", hits, misses);
    println!("  Hit ratio: {:.1}%", ratio * 100.0);
    println!("  Per-frame layout cost (cached): {:?}", dt_cached / 60);

    // 对比:无 cache 版
    let t_start = Instant::now();
    for _ in 0..60 {
        let _r = compute_layout(&widgets, &opts);
    }
    let dt_uncached = t_start.elapsed();
    println!("  Per-frame layout cost (uncached): {:?}", dt_uncached / 60);
    println!("  Speedup: {:.1}x", dt_uncached.as_secs_f64() / dt_cached.as_secs_f64());
}
```

### 8.4 Troubleshooting

**问题1**:加了 cache 反而更慢。
原因:hash 开销 > 重算开销。对 5-10 个 widget 的简单 layout,hash 本身比重算贵。
诊断:profiler 看 hash 时间 vs compute 时间。
修复:删 cache,或者只在 widget 数 > N 时启用 cache。

**问题2**:cache hit 但 layout 错位。
原因:hash 没覆盖所有依赖字段。漏了 font_size / flags / 隐藏状态。
诊断:每次 cache hit 时打印 hash 值,看变化是否和你的输入一致。
修复:把漏掉的字段加进 hash。

**问题3**:cache miss ratio 接近 100%。
原因:输入每帧都变。最常见罪魁——hover state、focus state、动画时间。
诊断:打印每次 cache miss 的 hash diff,找哪些字段变化。
修复:把"变化频繁但不影响 layout"的字段(如 hover)从 hash 里剔除。

**问题4**:内存增长。
原因:cache 不限大小,持续累积。
诊断:`valgrind --tool=massif` 或 `cargo bloat`。
修复:用 LRU 限制 cache 大小(`lru` crate)。

**问题5**:并发 panic("poisoned lock")。
原因:`cached` crate 默认用 thread-local,跨线程访问可能 panic。
诊断:stack trace 看哪个线程先 panic。
修复:用 `cached::SizedCache` + `Arc<RwLock<...>>` 多线程版,或避免跨线程。
