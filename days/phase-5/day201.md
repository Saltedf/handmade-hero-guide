
# Day 201 · 隔离调试代码

> 你的游戏要发布了。你跑 `cargo build --release`,生成一个 50 MB 的可执行文件。你双击运行——奇怪,主菜单上还残留着 debug overlay,按下 F1 还能调出 god mode,任务管理器里游戏占 600 MB 内存(本该 200 MB)。你猛然意识到:**过去半年你写的所有 debug 工具,全都打包进了发行版**。今天 Casey 用一个 Cargo feature,把这一切"一键蒸发"。

## 0 · 为什么要有这一天

让我们把镜头拉近,真实地体验一下这个场景。

你跟着 Handmade Hero 走到 Day 200。你的代码里有这些东西:**游戏主循环**(必需)、**渲染器**(必需)、**音效系统**(必需)、**调试性能监视器**(只在开发时用)、**实时变量编辑器**(只在开发时用)、**飞行相机 F2**(作弊用)、**逐帧单步 F3**(debug 用)、**完整 ImGui 风格的 debug overlay**(开发用)。后面这几样东西加起来,可能占了整个代码量的 30%。

开发时,这些东西是你的命。没有性能监视器你定位不了卡顿;没有变量编辑器你调不好光照;没有飞行相机你出不了地图外。**但是它们绝对不能进发行版**,理由有四条,从轻到重排:

**第一,体积**。一套完整的 immediate-mode debug UI,带字体、控件、布局、图表、序列化,几 MB 是少的。一个内置的 Tracy profiler runtime,又是一两 MB。这些字节数累加起来,你的发行版比别人胖 30%。在 Steam 上,这意味着用户多下 30% 的数据;在手机上,这意味着用户超出流量限额不愿下载;在 WebAssembly 上,这意味着首屏加载多转几秒。

**第二,性能**。immediate-mode UI 是出了名的吃 CPU——它每帧把整个 debug 面板重新构造、布局、渲染一遍。即便 debug 面板不显示,只要它"在编译产物里",开发者很容易写出 `if debug_visible { draw_debug_panel(); }`,那个 `if` 在 hot loop 里就够影响 branch predictor。一个粗劣的实现能让你的游戏从 144 FPS 掉到 110 FPS。在 release 你必须**彻底删掉**,不是 runtime 屏蔽。

**第三,代码整洁**。当 `game_update()` 函数里夹杂着 `debug_log("player pos = {:?}", pos);` 这种调试输出,半年后你回来读自己的代码,会发现自己每次都要"过滤掉这些 debug 噪音"才能读懂游戏逻辑。好的代码组织,应该让"游戏逻辑"和"调试支持"**物理隔离**,而不是混在一起。

**第四,也是最关键的:安全**。debug 代码泄露内部状态——变量名、玩家坐标、AI 决策路径、内部 ID。这些东西在你的开发机上无害,但发行版到了玩家手上,任何 reverse engineer 都能拿到你的 debug binary,运行起来,F1 一按,看见完整的 debug overlay。对于**反作弊**这是灾难(玩家用 debug 信息写出作弊器);对于**剧情向游戏**这是灾难(玩家提前看见剧透变量);对于**网络安全模型**这是灾难(攻击者知道你的 internal 数据结构,SQL 注入之类的好下手)。

工业界的标准答案叫 **conditional compilation**(条件编译):**让编译器在构建发行版时,自动把 debug 代码当垃圾扔掉**。生成的二进制文件里物理上不存在这些代码,不是"runtime 屏蔽",是"编译时消失"。

Rust 给这套机制的实现叫 **Cargo feature**。今天 Casey 把整个 debug 系统用 feature 包起来,演示从"开发时全开"到"发行时全无"的切换。看起来很简单——加几行 `#[cfg]` 就行——但 Casey 在这一集里讨论的权衡,是你以后写任何严肃项目都要反复面对的问题。

**学完今天,你应该能**:
- 解释为什么"runtime if (DEBUG)"不够,必须"compile-time cfg"
- 在自己的 Rust 项目里设计一套合理的 feature 体系
- 看懂大型开源项目(bevy / serde / tokio)的 Cargo.toml `[features]` 段在做什么
- 用 `cargo bloat` / `twiggy` 测量 binary 体积,定位哪些 debug 代码没删干净
- 理解 Cargo feature 的"unification"陷阱,避免 dep graph 里的隐式启用

## 1 · Casey 今天做了什么

Casey 这一天没有写新功能,而是做了一次**架构清理**:

1. **审视 debug 代码**。他列出 Day 176-200 期间写的所有 debug 工具:profiler overlay、变量编辑器、相机飞行模式、debug overlay、开发者 console。这些代码分散在 `handmade.rs`、`platform.rs`、`debug_ui.rs` 多个文件。

2. **决定隔离策略**。他用编译时 feature 而不是 runtime flag,理由是"二进制物理隔离比运行时判断更彻底、更安全"。他在视频里特别强调:**runtime if 在 release 里仍可能被逆向工程绕过**(给 patch 一个 byte 就能切到 debug 模式),而 cfg 隔离的代码"binary 里不存在",逆向也找不到。

3. **加 Cargo feature**。在 `Cargo.toml` 里加 `[features] default = ["debug"] debug = []`。

4. **批注 debug 代码**。所有 `mod debug_ui;`、`fn draw_debug_overlay`、相关 use 语句,都加 `#[cfg(feature = "debug")]`。

5. **验证 release 干净**。`cargo build --release --no-default-features`,然后用 `strings target/release/handmade_hero | grep -i debug` 检查二进制是否还有 debug 相关字符串。Casey 在视频里得意地展示输出为空。

6. **反思权衡**。Casey 提到一个微妙问题:他**不打算**把 profiler 完全 cfg 掉,因为发行版偶尔也需要"profile 一下玩家上报的卡顿"。所以 profiler 用 runtime flag,完整 debug overlay 用 cfg。这是混合策略。

这集产出**0 行新游戏代码**,但建立了一条以后每天都用的工程纪律。

## 2 · 心智模型

### 2.1 类比:工地与成品楼

我打个比方。你去看一栋正在施工的大楼。工地什么样?**脚手架**从地面搭到楼顶、**塔吊**立在旁边、**临时围挡**围着工地、**工人临时厕所**在角落、**建筑材料**堆在地上、**施工电梯**挂在楼外。这些"施工设施"是盖楼必需的——没有脚手架工人无法施工,没有塔吊材料运不上去。

但是当楼盖好、业主要入住时,这些施工设施**必须全部拆除**。你不希望业主住进去后发现"客厅里还有脚手架""电梯旁边挂着施工电梯"。拆除之后,只剩**楼本身**——结构、外墙、室内装修、永久电梯。

**debug 代码就是你游戏的"施工设施"**。开发时它们是必需的:profiler 是你的塔吊(定位性能瓶颈运到修复方案)、debug overlay 是你的脚手架(让你看见代码内部)、变量编辑器是你的临时电梯(快速调整参数不用重启)。

但发行版就是"业主入住"。玩家不想看见你的 debug UI、不想为你的 profiler 多交 CPU 税、不想因为你的开发残留物被 reverse engineer 攻击。

`#[cfg(feature = "debug")]` 就是"拆除施工设施"的那一铲子。第一铲下去,脚手架没了;第二铲,塔吊没了;最后你的发行版只剩"楼本身"——纯粹的游戏代码。

这个比方的关键洞察:**施工设施和楼本身是物理隔离的**。脚手架**贴着**外墙,但**不嵌入**外墙。如果你把脚手架**焊死**在外墙里(等价于把 debug 代码混在 game logic 里),拆的时候就要一块一块撬——撬不干净就残留。所以 Casey 今天做的事,本质是**把"已经焊进外墙的脚手架"拆出来,重新组织成"独立模块,可整体移除"**。

### 2.2 Rust 的条件编译:从源码到二进制的"消失"

你大概写过 `#[cfg(target_os = "linux")]`,但可能没仔细想过它**到底怎么工作**。让我把整个链路拆开,你会看到 Rust 的条件编译比 C 的 `#ifdef` 严谨得多。

源码进编译器要经过几个阶段:

```
源码 (.rs 文件)
   ↓ 1. Lexing:字符流 → token 流
   ↓ 2. Parsing:token → AST(抽象语法树)
   ↓ 3. Macro expansion:宏展开
   ↓ 4. cfg 求值:遍历 AST,删除不匹配的节点  ← 关键阶段
   ↓ 5. Name resolution:名字解析(import、path)
   ↓ 6. Type checking:类型检查
   ↓ 7. MIR:降级到中级中间表示
   ↓ 8. Codegen:LLVM IR → 机器码
   ↓ 9. Linking:链接成最终 binary
binary
```

`#[cfg(feature = "debug")]` 在**第 4 步**生效。编译器看到这个属性,**整个 AST 节点**被删除——不是"注释掉"、不是"设为 inactive",是 AST 里**根本不存在**了。这意味着:

- **第 5 步 name resolution** 看不到这个函数,所以你不能从外面调用它(除非也包在 cfg 里)
- **第 6 步类型检查** 不会检查这个函数体(代码不存在)
- **第 7-8 步** 不会为它生成任何 MIR / 机器码
- **第 9 步 linker** 看到的是"从来没这个函数"

最终 binary 里这个函数**物理不存在**——0 字节、0 CPU 周期、0 攻击面。

对比 C/C++ 的 `#ifdef DEBUG`:

```c
#ifdef DEBUG
void draw_debug_overlay() { ... }
#endif
```

C 的 `#ifdef` 是**预处理器**阶段,文本替换。预处理器不"理解"代码——它就是个带正则的 sed。漏写 `#endif`、嵌套 `#ifdef` 混乱、`#define` 名字打错——编译器一概不报错,直到运行时崩溃。Rust 的 `cfg` 在 AST 阶段处理,编译器**理解代码结构**,所以属性错位、cfg 不匹配会立刻报错。这是 Rust 在工程化上的一个关键进步。

### 2.3 三层"debug 隔离"策略

不同的隔离策略,代价和效果不同。让我把它们放在一张表上对比:

| 策略 | 时机 | 代价 | 二进制残留 | 安全性 | 灵活性 |
|---|---|---|---|---|---|
| Source-level cfg | 编译时 | 编译两次(debug/release) | **零** | 高(binary 不存在) | 低(切换要重编译) |
| Build-time constant | 编译时 | 一次编译 | 函数体在,调用站点被 optimizer 消除 | 中 | 低 |
| Runtime flag | 运行时 | 每次调用 if 判断 | 全部代码在 binary | 低(可被 patch) | 高(可动态开关) |
| Separate binary | 构建 | 维护两套代码 | 各自 binary 独立 | 高 | 极低(双份维护) |

Casey 的选择是**混合**:
- **完整 debug overlay、变量编辑器、ImGui 系统**:cfg 隔离。这些是大块代码,发行版完全不需要。
- **Profiler 数据收集(不开 UI 的部分)**:runtime flag。发行版偶尔要在玩家机器上 profile。
- **Logging**:`log` crate 的 level filter,runtime 控制。

这种分层策略是工业实践——**不是非黑即白,按需求分级**。Unreal Engine 也是这套:大部分 debug 用 `#if WITH_EDITOR`(cfg),少部分用 `UE_BUILD_DEBUG`(build config),logging 用 runtime verbosity。

### 2.4 feature 的"组合爆炸"陷阱

如果项目有 N 个独立的 feature,理论上有 2^N 种组合。N=5 时 32 种,还能管理。N=20 时 100 万种,你**根本无法全部测试**。

Cargo 还有一个"feature unification"特性会让事情更糟:如果依赖图里**多个 crate 都依赖同一个 crate 但启用不同 feature**,Cargo 会**取并集**——所有 feature 都被启用。这意味着:

```
[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"  # 内部依赖 serde 默认 features
```

如果你的某个 dependency 启用了 `serde` 的 `alloc` feature,即便你**没显式启用**,最终 build 里 `serde` 也是带 `alloc` 的。这导致"我在 Cargo.toml 里写 `default-features = false`,但最终 binary 里还是有 `std`"的怪事。

工业实践:
1. **feature 数量 < 20**。超过这个数,组合爆炸开始失控。
2. **三个测试组合**:`default` features、`--no-default-features`(最小)、`--all-features`(最大)。95% 用户用这三个之一。
3. **feature 互相正交**。比如 `debug_ui` 和 `profiling` 应该完全独立,不互相依赖。
4. **optional dependency 关联 feature**:`egui = { version = "0.27", optional = true }` + `features = { debug_ui = ["dep:egui"] }`,这样开 `debug_ui` 自动拉 egui,不开就不拉。
5. **避免 feature 互斥**。Rust 1.60 之前没法干净表达"二选一",1.60 之后用 `dep:` 前缀和 namespace features 可以,但仍然要小心。

### 2.5 cargo bloat / twiggy:测量比猜测可靠

你说"我把 debug 代码都 cfg 掉了",怎么验证?**测量**。

`cargo bloat` 是社区工具,跑一遍 `cargo bloat --release --crates`,它告诉你每个 crate 占了多少 binary 体积。如果你看见 `egui` 在 release binary 里还有 2 MB,说明你的 cfg 没生效。

`twiggy` 是 Rust 团队出的 WebAssembly 优先的体积分析工具,但也能跑 ELF。它分析 binary 的 code section,告诉你哪些函数最胖、哪些没用到(dead code)。

```bash
# 装
cargo install cargo-bloat
cargo install twiggy

# 看 release binary 的 top 50 函数
cargo bloat --release --crates -n 50

# 用 twiggy 分析 wasm(假设你编译到 wasm32-unknown-unknown)
twiggy top target/wasm32-unknown-unknown/release/my_game.wasm -n 20
```

这两条命令是你以后做 release optimization 的左膀右臂。**不测量就不优化**——Casey 在 HH 视频里反复强调这条原则。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

debug 隔离这件事,不同游戏引擎有不同做法。让我对比一下,你会看到 Rust 的 cfg 是众多合理方案之一。

**Unreal Engine 5** 用 C++ 的 `#if WITH_EDITOR` 和 `UGameInstance::GetIsEditor()` 双层保护。`WITH_EDITOR` 是 build-time 的宏,关掉后整个 editor-only 的类(UActorFactory、UPropertyDetails)在 shipping build 里物理消失。`GetIsEditor()` 是 runtime,因为有些功能在 "Standalone Game" 模式(从 .uproject 启动但不在 editor 里)需要 runtime 区分。Unreal 的代码 50% 是 editor 支持,shipping build 通常比 development build 小 60%。

**Unity** 用 C# 的 `[Conditional("DEBUG")]` attribute 和 `#if DEBUG` 预处理指令。`[Conditional]` 比较有意思——它告诉编译器**调用站点**可以删除,即便方法本身保留(类似 inline 的反向)。这是 C# 针对"debug 函数性能开销"的优雅答案。但 Unity 的根本问题是 IL2CPP 后端会 strip 类型,导致某些反射调用失败——这是过度优化的代价。

**Godot** 用 `tools` 模式和 `editor` build 区分。Godot 是节点树架构,debug 节点(如 `RemoteTransform2D` 用于 editor preview)在 shipping build 里被引擎自动跳过。Godot 的做法是**架构层隔离**而不是编译时隔离——debug 类被识别并跳过,而不是被编译掉。

**Bevy**(Rust 生态旗舰)用 Cargo feature,和今天 Casey 学的方案一脉相承。Bevy 的 `Cargo.toml` 里有几十个 feature:`bevy_audio`、`bevy_sprite`、`bevy_pbr`、`bevy_ui`...每个都是可选模块。这个设计让 Bevy 可以**按需嵌入**——一个只需要 ECS 的小项目可以禁用所有渲染 feature,binary 缩到几 MB。

Casey 的方案最像 Bevy——单 crate + Cargo feature。区别是 Casey 只有一个 `debug` feature,而 Bevy 有几十个。这是 Casey 的"够用"哲学:Handmade Hero 是单游戏项目,不需要模块化分发;Bevy 是引擎,要让用户按需启用。

**你能学到的迁移**:你的 Rust 游戏项目,在早期保持单 feature(`debug`)就好。等代码量超过 50K 行,开始按子系统拆 feature(`physics`、`audio`、`networking`),让 mod 社区或下游用户可以禁用他们不需要的部分。

### 3.2 · 🎨 图形学视角

图形程序员对 debug 隔离特别敏感,因为图形 debug 工具**特别贵**:

- **RenderDoc** 集成:你的引擎要"暴露每一帧的 draw call"给 RenderDoc 抓帧。这套集成代码在 shipping 里必须删——不然玩家用 RenderDoc 看你的渲染,作弊就太容易了。
- **PIX** (Windows) integration 类似。
- **Shader hot-reload**:开发时改 .hlsl / .glsl 文件,游戏实时重编译 shader。Shipping 里要删,否则玩家可以改 shader 实现 wallhack。
- **GPU marker / debug region**:命令流里插入 "begin region: shadow map pass"。Shipping 里要删——这些 marker 会让 GPU driver 多做工作。
- **Frame debugger overlay**:每帧右上角显示当前 FPS、draw call 数、VRAM 占用。Shipping 删。

这些工具都用 Cargo feature 包起来。Rust 图形社区(bevy_render、wgpu、rend3)的惯例是建一个 `trace` feature,开启后整个 GPU API 都插入 marker / scope,关闭后零开销。`tracing` crate 配合 `tracy` 后端做这个特别顺手。

```rust
#[cfg(feature = "trace")]
fn draw_call(pass: &mut RenderPass, cmd: &DrawCommand) {
    let _span = tracing::span!(tracing::Level::INFO, "draw_call").entered();
    // 实际 draw
}

#[cfg(not(feature = "trace"))]
fn draw_call(pass: &mut RenderPass, cmd: &DrawCmd) {
    // 直接 draw,无 span 开销
}
```

这就是工业图形程序员的日常。**每帧 5000 个 draw call,每个省 50ns 的 span 创建开销,就是 250μs/帧,1500万 cycle/秒**。看起来小,累加起来影响 frame budget。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核是"条件编译之王"。内核有几千个 `CONFIG_*` 配置项,编译时决定哪些驱动、哪些文件系统、哪些调度特性编进去。你的 Arch 内核:

```bash
# 看你当前内核的 config
zcat /proc/config.gz | grep CONFIG | wc -l
# 大概 7000-9000 行
```

每一条 `CONFIG_*` 都是一个条件编译开关。`CONFIG_SMP=y` 编进去多核支持,`=n` 不编。`CONFIG_MODULES=y` 编进去模块加载机制。这就是为什么 Linux 可以同时跑在路由器(2 MB binary)和服务器(50 MB binary)上——同一个源码树,不同 config。

内核的 `Kconfig` 系统比 Cargo feature 复杂——它有 dependency(`CONFIG_X86_64 depends on CONFIG_X86`)、default、choice(三选一)。Cargo 没这么复杂,但思路一样。

**Linux 用户态的工具链也大量用 cfg**:

```bash
# 看 ripgrep 编译时的 features
pacman -Qi ripgrep | grep -i features
# 看 systemd 的编译选项
pacman -Qi systemd | grep -i compile

# Arch 的 makepkg 可以传 feature
# 编辑 /etc/makepkg.conf:
#   CARGO_FEATURES=()
# 然后 makepkg 时禁用 default features
```

你以后给 Rust 项目打 Arch 包(AUR),要会看 PKGBUILD 里的 cargo flags。比如一个 PKGBUILD 片段:

```bash
# PKGBUILD
build() {
    cd "$srcdir/$pkgname-$pkgver"
    cargo build --release --frozen \
        --no-default-features \
        --features "pcre2,avx2"
}
```

这告诉 cargo:构建时禁用所有默认 feature,只开 `pcre2` 和 `avx2`。这是 Arch 维护者控制 binary 体积和依赖的常用手法。你给开源 Rust 项目打 Arch 包,要主动看 upstream 的 features 列表,决定哪些进包哪些不进。

### 3.4 · 🦀 Rust 生态视角

让我深度剖析 Rust 生态里 feature 设计的几个模式。

**模式一:Optional dependency**。最基础的——某个 feature 对应一个可选依赖:

```toml
[dependencies]
image = { version = "0.25", optional = true }

[features]
default = []
image-support = ["dep:image"]
```

`dep:image` 是 Rust 1.60 引入的语法,显式说"启用 image-support 这个 feature 时,要拉 image 这个 dependency"。Rust 1.60 之前 feature 名字和 dependency 名字会冲突,有了 `dep:` 前缀就清晰了。

**模式二:Feature namespace**(Rust 1.60+)。一个 crate 可以 expose 另一个 crate 的 feature,通过 namespace:

```toml
[features]
png = ["dep:image", "image?/png"]
jpeg = ["dep:image", "image?/jpeg"]
```

`image?/png` 的 `?` 意思是"如果 image 依赖被启用,就启用它的 png feature"。这让你做"插件式" feature——用户开 `png` 你自动拉 image 并开它的 png 模块。

**模式三:Pair pattern**。每个 feature 同时配 cfg 和 not:

```rust
#[cfg(feature = "debug")]
pub fn draw_debug(ctx: &mut Context) {
    // 几千行 debug UI
}

#[cfg(not(feature = "debug"))]
pub fn draw_debug(_ctx: &mut Context) {
    // no-op
}
```

调用方 `draw_debug(&mut ctx)` 永远能编译。debug 开时跑完整代码,关时跑空函数。optimizer 会内联空函数并消除调用,真正零开销。

**模式四:Macro 封装**。重复的 cfg 写起来烦,封成 macro:

```rust
macro_rules! debug_only {
    ($($tt:tt)*) => {
        #[cfg(feature = "debug")]
        $($tt)*
    };
}

debug_only! {
    pub fn draw_debug_overlay(state: &mut State) {
        // ...
    }
}
```

bevy 和 tokio 内部大量用这种 macro。

**模式五:feature gate 整个 module**。最干净——把 debug 代码全放一个 mod,然后门控整个 mod:

```rust
// src/lib.rs
#[cfg(feature = "debug")]
pub mod debug;

#[cfg(not(feature = "debug"))]
mod debug { /* 空 */ }
```

调用方写 `crate::debug::draw_overlay(...)`,无论 feature 是否开,代码都能编译。这是 Casey 今天在 HH 里采用的模式,适合 debug 代码量大的情况。

**反模式:不要这样**:
- ❌ `if cfg!(feature = "debug") { ... }` —— `cfg!()` 是宏,返回 bool,runtime 判断。和 `#[cfg]` 不一样。Release binary 里**代码还在**,只是 runtime 跳过。安全和性能都没达到。
- ❌ `#[cfg(debug_assertions)]` —— `debug_assertions` 是 Rust 自动给的,built-in 的 debug vs release 区分。听起来像我们要的,但**它只针对 `debug_assert!` 宏**,不是给用户用的。Cargo feature 才是用户控制的。
- ❌ 一个 feature 跨多个 unrelated subsystem。比如 `cool_things` feature 同时影响"debug UI"和"audio backend"——这违反 feature 正交原则。开 cool_things 的用户可能只想要其中一个。

学完这些模式,你看任何 Rust crate 的 Cargo.toml 都能秒懂。试试:

```bash
# 看 serde 的 features
cargo info serde 2>/dev/null || curl -s https://crates.io/api/v1/crates/serde | python3 -c "import sys,json; print(list(json.load(sys.stdin)['version']['features'].keys()))"
# 看 tokio 的 features
cargo info tokio 2>/dev/null || curl -s https://crates.io/api/v1/crates/tokio | python3 -c "import sys,json; print(list(json.load(sys.stdin)['version']['features'].keys()))"
# 看 bevy 的 features(很多)
cargo info bevy 2>/dev/null || curl -s https://crates.io/api/v1/crates/bevy | python3 -c "import sys,json; print(len(json.load(sys.stdin)['version']['features']))"
```

你会看到 serde 有十几个 features(derive / alloc / rc / unstable 等),tokio 有几十个,bevy 有上百个。这是工业级 Rust crate 的标配。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Conditional compilation** — 编译时排除代码的通用技术。在 C/C++ 是 `#ifdef`,在 Rust 是 `cfg`,在 Go 是 build tags,在 Java 是 ProGuard,在 JS 是 tree-shaking。
- **Feature flags** — 软件工程通用模式。但**编译时 feature**(今天讨论的)和**运行时 feature**(LaunchDarkly / Unleash 这种 SaaS feature flag 系统)是两件事,别混淆。
- **Dead code elimination** — Linker 自动删未引用代码。`#[cfg]` 是 source-level 删除,linker GC 是 binary-level 删除。两者配合,double kill。
- **Build configurations** — 整套"构建变体"管理。Debug / Release / RelWithDebInfo / MinSizeRel,每个组合一套特性。

### 4.2 同级(并行方案对比)

| 方案 | 时机 | 谁负责 | 优点 | 缺点 |
|---|---|---|---|---|
| `#[cfg(feature)]` | 编译时(source level) | Rust 编译器 | 最彻底,0 binary | 需要重编译切换 |
| `cfg!()` macro | 编译时表达式 | Rust 编译器 | 写代码更顺手 | 不真正删代码,只 runtime if |
| Build script (`build.rs`) | 构建脚本 | Cargo | 动态生成 cfg | 复杂 |
| Linker GC | 链接时 | linker | 自动,无需手标 | 只删 unused,used 但 runtime 跳过的不删 |
| Runtime flag | 运行时 | 应用代码 | 灵活,可动态切换 | binary 残留,有 runtime 开销 |
| Separate binary | 构建时 | 构建系统 | 物理隔离 | 维护两套代码 |

### 4.3 下级(内部零件)

- `#[cfg(...)]` attribute — 应用到任何 AST 节点
- `cfg!(...)` macro — 编译时表达式,返回 bool
- `[features]` in Cargo.toml — feature 定义
- `[dependencies] optional = true` — 可选依赖
- `dep:` namespace — Rust 1.60+ 的显式 dependency 引用
- `cargo build --features "foo,bar"` — 命令行启用
- `cargo build --no-default-features` — 禁用默认
- `cargo bloat` — 测量 binary 体积分布
- `twiggy` — WebAssembly 优先的 binary 分析
- `required-features` — Cargo.toml 里限制 binary/example 必须开的 feature

## 5 · 对照与变奏

### 5.1 跨语言的 debug 隔离

把同一问题在不同语言的答案并排放,你能看清权衡:

**C/C++**:
```c
#ifdef DEBUG_UI
void draw_debug_overlay(GameState* state) { ... }
#endif
```
预处理器文本替换。优点是简单直接;缺点是预处理器不"理解"代码,容易写错(漏 `#endif`、宏名打错不报错)。C++ 模板可以用 `if constexpr (debug_v)` 在编译时分支,但同样不能"删除代码"——只是不生成。

**Go**:
```go
// +build debug

package main

func drawDebugOverlay(state *GameState) { ... }
```
Go 用 build tags。文件级别——整个文件在 `+build debug` 标签下,不开就不编译。粒度比 Rust cfg 粗(文件级 vs 节点级),但更简单。Go 社区用 `//go:build debug`(Go 1.17+ 新语法)。

**Java/Kotlin (Android)**:
```java
class DebugOverlay {
    @DebugOnly
    void draw(GameState state) { ... }
}
```
然后 `assumenosideeffects` ProGuard rule 告诉 R8 编译器删除对 `DebugOverlay.*` 的所有调用。R8 静态分析,识别并消除。优点是字节码级;缺点是分析不完美,有时候会误删或漏删。Android 社区的 standard practice。

**JavaScript / TypeScript**:
```js
if (process.env.NODE_ENV === 'development') {
    drawDebugOverlay(state);
}
```
webpack / esbuild / vite 在 build 时识别 `process.env.NODE_ENV`,做 dead code elimination。比 Java 干净(不需要 annotation),但依赖 bundler 的 tree-shaking 能力。

**Rust**:
```rust
#[cfg(feature = "debug_ui")]
fn draw_debug_overlay(state: &mut State) { ... }
```
AST-level,编译器理解,IDE 支持(rust-analyzer 能看到 cfg 不匹配的代码),重构安全。**这是目前最好的方案**。代价是初学者要学 cfg 语法(不算太难)。

### 5.2 历史演化

debug 隔离这件事的演化,折射了软件工程整体从"手工管理"到"工具自动化"的趋势:

- **1970s** C 的 `#ifdef`。手写预处理器规则,易错。
- **1980s** make 的 build variants。`make DEBUG=1`。仍然是文本替换。
- **1990s** C++ template metaprogramming。可以编译时分支,但代码丑陋难写。
- **2000s** Java 的 build tools(Maven profiles, Gradle)。配置文件管 build variants。
- **2010s** Go build tags、Cargo features、CMake compile definitions。语言原生支持。
- **2020s** Rust 1.60+ 的 `dep:` 和 namespace features。更严格的语义,IDE 支持。

每个十年,工具都在进步,但**核心抽象不变**:**让代码的某些部分在某些构建配置下"消失"**。Casey 今天演示的,就是这个抽象的当代最佳实践。

### 5.3 发行版的"零信任"

现代游戏发行版假设**会被反编译**。所以重要逻辑(加密 / 反作弊 / 服务器密钥)用 server-side,client 只是壳。debug UI 必须裁剪(否则给反作弊绕过入口)。

工业级保护链路:
1. **Source-level cfg**:今天学的,debug 代码 binary 里不存在。
2. **Stripped binary**:`strip target/release/game` 去符号表。逆向看不到函数名。
3. **Obfuscation**:Lumino / VMProtect / Themida 把机器码虚拟化。逆向要解 VM。
4. **Anti-debug**:检测 debugger attached,exit 或 crash。
5. **Server-side validation**:关键状态(玩家位置、伤害计算)服务器验证,client 不能改。
6. **Anti-cheat software**:EAC / BattlEye / VAC。内核级检测。

Casey 用第 1 条起步。商业游戏全套上。**没有 1 是不行的**(binary 残留的 debug UI 给所有后续保护打 50% 折扣),所以今天这一集其实是反作弊工程的第一课。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:三种 debug 隔离策略(source cfg、runtime flag、separate binary)各自的安全性和性能代价是什么?为什么 Casey 最终选了混合策略?

**参考解答**:

| 策略 | 安全性 | 性能代价 | 何时用 |
|---|---|---|---|
| source cfg | 最高(binary 不存在) | 0(switch 要重编译) | 大块、永远不发行的 debug 代码 |
| runtime flag | 中(可被 patch byte 绕过) | 每帧 if 判断(虽小但累加) | 需要灵活切换的(发行版偶发 profile) |
| separate binary | 最高 | 维护两套代码 | 极端安全要求(军事 / 银行) |

Casey 混合策略:
- **完整 debug overlay**(ImGui 系统):cfg 隔离。这是大块 UI,发行版完全不需要。
- **Profiler 数据收集**:runtime flag。发行版偶尔要在玩家机器 profile(用户报卡顿,你让他开 profile 复现)。
- **Logging**:runtime level filter。玩家调试也要 log。

这种分层是工程现实主义——不是教条地"全 cfg"或"全 runtime",而是按"是否需要发行版访问"分级。

### Lv2 · 动手实践

**题**:用 cargo new 创建一个新项目 `feature-isolation-demo`,实现:
- 一个 `greet` feature(默认开)
- 开 greet 时,程序打印 "Hello, debug world!"
- 关 greet 时,程序什么都不打印(包括 binary 里没有这个字符串)

**完成标准**:
1. `cargo run` 打印 "Hello, debug world!"
2. `cargo run --no-default-features` 没输出
3. `cargo build --release --no-default-features && strings target/release/feature-isolation-demo | grep -c "Hello"` 返回 0

**参考解答**:

`Cargo.toml`:
```toml
[package]
name = "feature-isolation-demo"
version = "0.1.0"
edition = "2021"

[features]
default = ["greet"]   # 默认开
greet = []             # 空数组 = 只是个开关,不拉 dependency
```

`src/main.rs`:
```rust
// 开 greet feature 时,greet 函数有完整实现
#[cfg(feature = "greet")]
fn greet() {
    println!("Hello, debug world!");
}

// 关 greet feature 时,greet 是空函数(保持调用站点能编译)
#[cfg(not(feature = "greet"))]
fn greet() {}

fn main() {
    greet();
}
```

验证:
```bash
cargo new --bin feature-isolation-demo
cd feature-isolation-demo
# 把上面代码粘进 Cargo.toml 和 src/main.rs

# 1. 默认 build(开 greet)
cargo run
# 输出: Hello, debug world!

# 2. 禁用 default features
cargo run --no-default-features
# 没输出

# 3. release 验证 binary 不含 "Hello"
cargo build --release --no-default-features
strings target/release/feature-isolation-demo | grep -c "Hello"
# 输出: 0  ← 关键证据

# 对照:有 greet 的 binary
cargo build --release
strings target/release/feature-isolation-demo | grep -c "Hello"
# 输出: 1
```

**关键解释**:
- `[features]` 是 Cargo 的 feature 定义段。`default` 是默认启用的 feature 列表。
- `greet = []` 表示"这个 feature 不引入额外 dependency,只是个开关"。
- `#[cfg(feature = "greet")]` 告诉编译器:只在 greet feature 开启时编译这个函数。
- `#[cfg(not(feature = "greet"))]` 是反面——只在 greet 关闭时编译。两个函数同名,但永远只有一个被编译,所以没冲突。
- `strings` 命令打印 binary 里的可打印字符串。Hello 字符串不在 release binary,证明 cfg 真正删了代码。

### 8.1 从零到完整可跑的项目

我们做一个真实项目:`debug-isolated-game`,模拟游戏里 debug 隔离。这个项目有两个 build:
- Debug build:有完整 debug UI、profiler、cheat keys
- Release build:无任何 debug,二进制最小

```bash
# 创建项目
cargo new --bin debug-isolated-game
cd debug-isolated-game

# 加 dependencies(都在 optional 里)
cargo add log --optional
cargo add egui --optional --features eframe
```

`Cargo.toml` 完整内容:
```toml
[package]
name = "debug-isolated-game"
version = "0.1.0"
edition = "2021"

[features]
default = ["debug"]
debug = ["dep:log", "dep:egui"]

[dependencies]
log = { version = "0.4", optional = true }
egui = { version = "0.27", optional = true, features = ["eframe"] }

[profile.release]
strip = true         # 去 symbol table
lto = true           # 链接时优化
codegen-units = 1    # 单 codegen unit,更好优化
opt-level = "z"      # 体积优先(改 "s" 也行)
panic = "abort"      # unwind table 占体积
```

`src/main.rs`:
```rust
// 主入口永远编译
mod game;

// debug 模块只在 debug feature 开时存在
#[cfg(feature = "debug")]
mod debug;

fn main() {
    #[cfg(feature = "debug")]
    debug::init();
    
    game::run();
}
```

`src/game.rs`:
```rust
// 游戏核心代码,永远编译
pub fn run() {
    println!("Game started");
    
    // 主循环(简化)
    for frame in 0..3 {
        update(frame);
        render(frame);
    }
    
    println!("Game ended");
}

fn update(frame: u32) {
    // 游戏逻辑
    #[cfg(feature = "debug")]
    debug::on_frame_update(frame);  // 编译时被裁剪(如果 debug 关)
}

fn render(frame: u32) {
    // 渲染代码
    #[cfg(feature = "debug")]
    debug::on_frame_render(frame);
}
```

`src/debug.rs`:
```rust
// 整个模块只在 debug feature 开时编译
//! Debug utilities — only compiled with `debug` feature.

pub fn init() {
    println!("[debug] Initializing debug subsystem");
}

pub fn on_frame_update(frame: u32) {
    println!("[debug] update frame {}", frame);
}

pub fn on_frame_render(frame: u32) {
    println!("[debug] render frame {}", frame);
}
```

跑两种 build:
```bash
# Debug build(有 debug feature)
cargo run
# 输出:
# [debug] Initializing debug subsystem
# Game started
# [debug] update frame 0
# [debug] render frame 0
# [debug] update frame 1
# [debug] render frame 1
# [debug] update frame 2
# [debug] render frame 2
# Game ended

# Release build(关掉 debug)
cargo run --release --no-default-features
# 输出:
# Game started
# Game ended
```

### 8.4 用 twiggy 深入分析

```bash
# 装

# 假设你编译到 wasm(更明显的例子)
rustup target add wasm32-unknown-unknown
cargo build --release --target wasm32-unknown-unknown
twiggy top target/wasm32-unknown-unknown/release/debug_isolated_game.wasm -n 20
# 输出 wasm 里 top 20 函数

# 对比 debug 开/关
cargo build --release --target wasm32-unknown-unknown --no-default-features
twiggy top target/wasm32-unknown-unknown/release/debug_isolated_game.wasm -n 20
# 体积应该明显更小
```

### 8.5 CI 集成

你的项目 `.github/workflows/ci.yml` 应该测多个 feature 组合:

```yaml
jobs:
  test:
    strategy:
      matrix:
        features:
          - "--all-features"
          - "--no-default-features"
          - "--features default"
          - ""  # default features
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - run: cargo build ${{ matrix.features }}
      - run: cargo test ${{ matrix.features }}
```

这保证任何 feature 组合都能 build 和 test。如果你的 PR 改了 feature 体系,CI 会告诉你有没有 break 哪个组合。

### 8.6 Troubleshooting

**问题1**:`cargo build --no-default-features` 报错 `unresolved import egui`。
原因:某个 mod 顶部 `use egui;` 没被 cfg 包。
解决:
```rust
// 错误:无论 feature 是否开,use 都会被处理
use egui::Context;

// 正确:use 也包在 cfg 里
#[cfg(feature = "debug")]
use egui::Context;
```

**问题2**:release binary 体积没小。
原因:某些代码引用了 debug 模块,即便 debug feature 关,引用站点也要 `#[cfg]` 包。
诊断:`cargo bloat --release --no-default-features --crates`,看 egui 还在不在。

**问题3**:CI 里 `--all-features` 失败,本地 `--all-features` 成功。
原因:Cargo feature unification——你的某个 dependency 之间 feature 冲突。
诊断:`cargo tree -e features`,看 dep graph 里 feature 流。

**问题4**:发行版 binary 还能调出 debug UI。
原因:你不是用 `#[cfg]`,是用 `cfg!()` macro。`cfg!()` 返回 bool,代码还在 binary。
修复:把 `if cfg!(feature = "debug") { ... }` 改成 `#[cfg(feature = "debug")] { ... }`。

**问题5**:`cargo build` 报错 "feature `debug` and `debug` are in conflict"。
原因:你有两个 crate 都叫 `debug`,或者你 `default = ["debug"]` 同时又 `--no-default-features --features debug`,导致 ambiguous。
诊断:`cargo tree -e features --features debug`,追 feature 来源。

这些 troubleshooting 是真实开发里最常见的 5 类问题。遇到时按这个清单过一遍,90% 能解决。

### 8.7 Arch Linux 工具链

```bash
# 装 binary 分析工具

file target/release/debug-isolated-game

nm target/release/debug-isolated-game | head
# release profile 的 strip = true 会让这个空

objdump --dwarf=info target/release/debug-isolated-game | head

objdump -d target/release/debug-isolated-game | head

# 测量启动时间(验证 release 没多余初始化)
time ./target/release/debug-isolated-game
time ./target/release/debug-isolated-game-debug  # 旧版
```
