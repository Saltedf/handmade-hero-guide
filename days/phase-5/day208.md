
# Day 208 · 调试日志加数据块

> profiler 记 cycle 数,但有时你想"在某一帧 dump 一段数据"(比如玩家位置、敌人 AI 状态)。今天 Casey 加 "data block" 到 debug event:不只记时间,还记任意数据。

## 0 · 为什么要有这一天

让我们把镜头拉到一个具体的开发场景。

你的游戏有个 AI bug——怪物在某个特定情况下"卡墙"。你打开 profiler,看到怪物 AI update 的 frame cycle 数正常(0.5ms),没有性能问题。但**怪物在那一帧的决策明显错**——它撞墙后没改变方向。

你想看"那一帧怪物 AI 的内部状态"——目标位置、当前路径、状态机的 state、看到玩家的距离。但 profiler 只告诉你"AI update 用了 0.5ms",**没有数据**。

你打开 debug overlay,选中那个怪物(Day 205 picking)。inspector 显示**当前**状态。但 bug 发生在 3 秒前——你看的是"现在",不是"卡墙那瞬间"。**当前状态没 bug,bug 已经离开了**。

这是 profiler 的根本局限:**只记时间,不记数据**。你能知道"AI update 跑了",但不知道"AI update 跑时怪物看到了什么、决定了什么"。

工业级 debug 工具的解法叫 **event with data**——每个事件不只记时间戳和名称,还记**关联的任意数据**。这是 Casey 今天做的事。

```
cycle=100 begin update_ai [monster=42]
cycle=120 data target_pos=(150, 200), can_see_player=true, state=Chase
cycle=150 data path=[(150,200), (148,200), (146,200)], path_status=Blocked
cycle=180 data decision=ChangeDirection, new_target=(140, 220)
cycle=200 end   update_ai
```

回放这一帧时,你能看到怪物当时看到的所有数据、做的所有决策。**bug 现场被完整保存**。

**为什么这件事不平凡?**

技术上,"事件 + 数据"看起来只是加个字段。但有几个工程挑战:

**第一,数据类型不固定**。PlayerPosition 是 Vec2,EnemyAIState 是 enum,NetworkPacket 是 Vec<u8>。一个 event 系统要支持任意数据类型,不能 hardcode。Casey 用 `DebugValue` enum + `type_guid`——类型擦除 + 运行时解码。

**第二,性能**。每帧 log 100 个 data block,每个分配 String + 序列化,可能慢 1ms。profiler 自己不能成为瓶颈。Casey 用 binary payload + ring buffer,每次 log ~50ns。

**第三,数据 lifecycle**。100 万条 data block 占 20 MB,几小时录下来几 GB。要 ring buffer(循环覆盖)或采样(只录关心的 channel)。

**第四,UI 渲染**。profiler timeline 怎么显示"在 cycle=120 有个 data block"?Casey 把 data block 显示为"标签"挂在 timeline 上,UI 自动解码显示。

**第五,持久化**。录制文件要存 data block,文件格式要向后兼容(旧版本无 data,新版本有,两者要兼容读)。

今天 Casey 实现这个完整 pipeline。Day 209 用它显示缓冲数据。Day 210+ 扩展。

**学完今天,你应该能**:
- 设计 event + data block 的复合 log 模式
- 解释为什么用 binary payload 而非 format!() 字符串(性能 + 紧凑)
- 用 type_guid 区分不同 data block 类型,UI 根据 guid 自动选 decoder
- 设计 ring buffer 处理"百万级 data block"的内存压力
- 看懂 `tracing::info!(field = value, "msg")` 在结构上和 Casey 的 data block 是同一个东西
- 知道 Linux ftrace / Windows ETW / OpenTelemetry 都是 event-with-data 的变种

## 1 · Casey 今天做了什么

Casey 这一天给 event 系统加 data block:

1. **扩展 DebugEventKind**。原来只有 `Begin` / `End`,今天加 `Data { name, value }`。Data 是个新 variant,带字段名(name)和值(value)。

2. **设计 DebugValue enum**。这是类型擦除的值容器——Float / Int / Vec2 / String / 等。每个 variant 存对应类型的值。type_guid 在 event guid 里编码(每 name 一个稳定 guid)。

3. **push_data API**。`debug_data("player_pos", player.pos)` 单行调用,内部构造 Data event 推到 buffer。简单易用。

4. **collate 改造**。原来的 collate 只处理 Begin/End(入栈/出栈算 span duration)。今天加 Data 处理——直接 push 到 FrameSummary.data_blocks,不影响 span stack。

5. **UI 渲染**。timeline 里 data block 显示为"标签"——在对应 cycle 位置画一条小标记 + 数据值。点标记展开详情。

6. **录制文件扩展**。文件格式 v2 加 Data variant 写法——tag byte (2) + name 长度 + name 字节 + DebugValue。v1 (无 data) 仍能读。

7. **反思边界**。Casey 提到 data block 不能太多——内存爆。每帧限制(比如最多 100 个 data block),或采样(每 N 帧录一次)。后面 Day 209 详谈。

这集产出 event + data 的基础设施,Day 209 用它做"buffer visualization"。

## 2 · 心智模型

### 2.1 费曼类比:猎人采集标本

想象一个猎人。他每打到一只猎物,会做两件事:

1. **记时间和地点**:"上午 9 点,东山坡,打到一只鹿"——这是元数据。
2. **采集标本**:鹿角、皮毛、胃内容物、血样——这些是"那只鹿"的具体数据。

只有时间和地点不够——如果你想知道"为什么这只鹿瘦",光知道"上午 9 点东山坡"没用,要看胃内容物(吃了什么)、血样(健康指标)、皮毛(寄生虫)。

**标本是元数据之外的具体信息**。时间和地点是结构,标本是内容。

debug event 完全一样:
- **event 本身**:Begin/End 是结构,记录 cycle、thread、guid——"什么时候发生了什么"
- **data block**:标本,记录当时的具体变量值——"发生时世界是什么样"

没有 data block 的 profiler 只能告诉你"AI update 跑了 0.5ms",有 data block 的能告诉你"AI update 跑时怪物在 (150, 200),看到了玩家,决定追击"。**bug 现场被完整保存**。

这个类比的关键洞察:**调试需要"现场数据",不只是"事件序列"**。profiler 没有 data block 等于猎人只记时间和地点——找不到"为什么这只鹿瘦"的答案。

### 2.2 从零推导:data block 的设计

让我们一步步从 profiler 的局限推到完整 data block 系统。

**Step 0:只有时间戳**。

```rust
struct Event { cycle: u64, kind: EventKind }
enum EventKind { Begin(u64 /* guid */), End(u64) }
```

profiler 显示"AI update 用了 0.5ms"。但不知道 AI 在做什么——没数据。

**Step 1:加文本日志**。

```rust
fn log_text(msg: &str) {
    println!("[{}] {}", cycle, msg);
}

// 用法
log_text(&format!("pos=({}, {})", pos.x, pos.y));
```

每帧 format!() 字符串——分配 + 解析格式说明符,~500 ns/log。100 次 log/frame = 50 μs/frame = 3 ms/sec,占 frame budget 大头。**热路径不能用 format!()**。

**Step 2:typed value**。

```rust
enum DebugValue {
    Float(f32),
    Int(i64),
    Vec2(f32, f32),
    String(String),
}

fn log_data(name: &'static str, value: DebugValue) {
    push_event(Event {
        cycle: rdtsc(),
        kind: EventKind::Data { name, value },
    });
}

log_data("pos", DebugValue::Vec2(pos.x, pos.y));
```

类型化的 value,无字符串分配。enum 是 Copy(除了 String variant),~20 ns/log。**比 format!() 快 25 倍**。

**Step 3:批量优化**。

每帧 100 个 log,event buffer push 100 次。每次 push 涉及 mutex lock(多线程)。优化:**thread-local buffer + 每帧合并**。

```rust
thread_local! {
    static LOCAL_BUFFER: RefCell<Vec<Event>> = RefCell::new(Vec::with_capacity(1024));
}

fn log_data(name: &'static str, value: DebugValue) {
    LOCAL_BUFFER.with(|buf| {
        buf.borrow_mut().push(Event { /* ... */ });
    });
}

// 主线程每帧结束时合并所有 thread-local buffer
fn merge_thread_locals() -> Vec<Event> {
    let mut all = Vec::new();
    LOCAL_BUFFER.with(|buf| {
        all.append(&mut buf.borrow_mut());
    });
    all
}
```

每帧合并一次,锁开销摊到 1 次/frame。**100 个 log/frame 的开销从 100 × 50 ns = 5 μs 降到 1 × 1 μs**。

**Step 4:ring buffer 限制内存**。

```rust
struct RingBuffer<T> {
    data: Box<[T]>,
    head: usize,
}

impl<T: Default> RingBuffer<T> {
    fn new(capacity: usize) -> Self {
        assert!(capacity.is_power_of_two());
        Self {
            data: (0..capacity).map(|_| T::default()).collect(),
            head: 0,
        }
    }

    fn push(&mut self, item: T) {
        let idx = self.head;
        self.data[idx] = item;
        self.head = (self.head + 1) & (self.data.len() - 1);  // & 替代 %
    }
}
```

固定容量,新数据覆盖最老的。容量 1M 条,占 20 MB。`&` 比 `%` 快 ~5x(CPU 整数除法慢)。

**Step 5:type_guid 区分类型**。

```rust
struct DataBlock {
    timestamp: u64,
    type_guid: u64,    // hash("PlayerPosition") 等
    data: Vec<u8>,     // binary payload
}

// 注册 decoder
state.register_decoder(TYPE_PLAYER_POS, |data| {
    let x = f32::from_le_bytes(data[0..4].try_into().unwrap());
    let y = f32::from_le_bytes(data[4..8].try_into().unwrap());
    DebugView::Vec2(x, y)
});

// log
fn log_player_pos(pos: Vec2) {
    let mut data = Vec::with_capacity(8);
    data.extend_from_slice(&pos.x.to_le_bytes());
    data.extend_from_slice(&pos.y.to_le_bytes());
    push(DataBlock { timestamp: rdtsc(), type_guid: TYPE_PLAYER_POS, data });
}
```

**type_guid 模式**:
- 写时:程序员调 `log_player_pos`,内部知道 schema 是 `(f32, f32)`。
- 读时:UI 查 `decoders[type_guid]`,得到 decoder function,decode binary 为 typed value。
- 优势:binary payload 紧凑(8 字节 vs JSON 50 字节),decoder 集中管理。

这是 schema-on-write 模式——写时知道 schema,读时按 schema decode。casey 用这个,因为游戏代码和 UI 都在同一进程,共享 type_guid 常量。

**Step 6:与 introspection 结合**。

如果游戏 struct 已经有 introspection(Day 206),自动 log 整个 struct:

```rust
fn log_struct<T: Inspectable>(state: &mut DebugState, value: &T) {
    let views = value.inspect();
    for view in views {
        push_data(view.name(), view.into_value());
    }
}

log_struct(&mut state, &player);  // 自动 log 所有字段
```

无需手写 `log_player_pos`。inspect 已经枚举所有字段。**introspection 的另一个 consumer**(Day 207 同主题)。

### 2.3 binary vs text log 的 trade-off

| 维度 | Text (`format!`) | Binary (Casey) |
|---|---|---|
| 大小 | ~50 字节/log | ~10 字节/log |
| 写入时间 | ~500 ns(format + alloc) | ~50 ns(memcpy) |
| 可读性 | 高(grep / cat) | 低(需 decoder) |
| 查询 | 文本搜索(慢) | 按 name 索引(快) |
| Schema | 无 | type_guid |
| 工具生态 | rich(grep / awk / jq) | 自定义 |

工业实践:
- **生产/运维**:text log(syslog、journald text),人能直接看,grep 友好。
- **profiler / 高频 trace**:binary(ETW、ftrace binary、Casey data block),性能优先。
- **业务日志**:structured JSON(ELK stack),文本但结构化,介于两者之间。

Casey HH 是游戏 profiler,性能优先,选 binary。

### 2.4 命名 channel / topic

data block 不只一种——player_pos、enemy_ai、network_packet、gpu_marker...每种关心的工程师不同(AI 程序员看 enemy_ai,网络程序员看 network_packet)。**channel / topic** 让 UI 过滤:

```rust
const CH_PLAYER: u64 = hash("player");
const CH_ENEMY: u64 = hash("enemy");
const CH_NETWORK: u64 = hash("network");

log_data(CH_PLAYER, "pos", pos);
log_data(CH_ENEMY, "ai_state", state);
log_data(CH_NETWORK, "packet_size", size);
```

UI:
```rust
let visible_channels: HashSet<u64> = user_selected;
for block in &buffer {
    if visible_channels.contains(&block.channel) {
        draw_block(block);
    }
}
```

只看关心的 channel,UI 不被无关数据淹没。

Linux ftrace 有 facility / priority。systemd journald 有 SYSLOG_FACILITY。工业 logging 系统都有 channel 概念。Casey HH 简化,所有 data block 共享一个流,UI 用 name 前缀过滤。

### 2.5 录制文件格式

profiler 录制文件要支持回放。格式设计要考虑:

**向后兼容**:v1 没 data,v2 有 data。v2 reader 能读 v1 文件,反之不行。

```rust
fn write_event(f: &mut impl Write, e: &DebugEvent) -> io::Result<()> {
    f.write_all(&e.cycle.to_le_bytes())?;
    f.write_all(&e.thread_id.to_le_bytes())?;
    f.write_all(&e.guid.to_le_bytes())?;
    match &e.kind {
        EventKind::Begin => f.write_all(&[0u8])?,
        EventKind::End => f.write_all(&[1u8])?,
        EventKind::Data { name, value } => {
            f.write_all(&[2u8])?;
            f.write_all(&(name.len() as u32).to_le_bytes())?;
            f.write_all(name.as_bytes())?;
            write_value(f, value)?;
        }
    }
    Ok(())
}
```

1 byte tag(0=Begin, 1=End, 2=Data)。v2 加了 tag 2,v1 reader 看到 2 panic 或跳过(取决于严格性)。

**版本号**:文件头第一个 u32 是 version。reader 根据 version 选不同 decode 逻辑:

```rust
let version = read_u32(f)?;
match version {
    1 => decode_v1(f),
    2 => decode_v2(f),
    _ => panic!("unsupported version"),
}
```

这是文件格式的标准模式——casey HH、protobuf、Cap'n Proto、Image formats 都这样。

### 2.6 周期性 data block 的高效采样

某些 data 是周期性的——每帧 player.pos 都变。每帧 log 一条,1000 帧 1000 条。如果想看"长时间趋势"(比如玩家移动路径),需要全 log。但如果只想看"大致趋势",采样就够:

```rust
let frame_mod = 10;  // 每 10 帧记一次
if frame_index % frame_mod == 0 {
    log_data("player_pos", player.pos);
}
```

10x 内存节省,曲线仍然清晰(60 FPS 下每秒 6 个点,够画图)。

工业 telemetry 系统(Prometheus、InfluxDB)都支持采样——agent 端按间隔采样,server 端聚合。

### 2.0 data block 的设计

每个 data block 是一段任意字节数据 + 元数据(类型 + 长度 + 时间戳):

```rust
struct DataBlock {
    timestamp: u64,         // rdtsc
    type_guid: u64,         // 类型标识(hash of "PlayerPosition" 等)
    data: Vec<u8>,          // 二进制 payload
}

// push 数据
fn log_player_pos(state: &mut DebugState, pos: Vec2) {
    let mut data = Vec::with_capacity(8);
    data.extend_from_slice(&pos.x.to_le_bytes());
    data.extend_from_slice(&pos.y.to_le_bytes());
    state.data_blocks.push(DataBlock {
        timestamp: rdtsc(),
        type_guid: hash("PlayerPosition"),
        data,
    });
}
```

**type_guid** 让 UI 知道如何解码——`(f32, f32)` 当 Vec2,`(i32, String)` 当 ID + name,等。

### 2.0.1 类型注册

每帧 UI 渲染前,要注册"类型 → decoder"映射:

```rust
state.register_decoder(hash("PlayerPosition"), |data| {
    let x = f32::from_le_bytes(data[0..4].try_into().unwrap());
    let y = f32::from_le_bytes(data[4..8].try_into().unwrap());
    DebugView::Vec2(Vec2::new(x, y))
});
```

注册一次,后续 log 时不需要再次注册。这是 schema-on-write 模式(写时知道 schema)。

### 2.0.2 binary format 的紧凑性

| 格式 | PlayerPosition 大小 |
|---|---|
| JSON | ~50 字节(`{"x":1.234,"y":5.678}`) |
| 文本 log | ~30 字节(`"pos=(1.234, 5.678)"`) |
| Binary(LE) | 8 字节(2 × f32) |

binary 6-10x 紧凑。对 hot path(每帧 log 几次)重要。

### 2.0.3 与 introspection 的结合

如果游戏 struct 已经有 introspection:

```rust
fn log_struct<T: Introspect>(state: &mut DebugState, value: &T) {
    let mut data = Vec::new();
    for member in T::members() {
        data.extend_from_slice(unsafe { read_field_bytes(value as *const _ as *const u8, member) });
    }
    state.data_blocks.push(DataBlock {
        timestamp: rdtsc(),
        type_guid: T::type_guid(),
        data,
    });
}
```

`log_struct(&player)` 自动序列化整个 Player。无需手写每个字段的 packing 代码。

### 2.0.4 ring buffer + data block

data block 数量很大(每帧 N 条 × 60 fps × 几分钟 = 百万级)。用 ring buffer:

```rust
struct DataBlockBuffer {
    blocks: Box<[DataBlock]>,  // 固定容量
    head: usize,
}

impl DataBlockBuffer {
    fn push(&mut self, block: DataBlock) {
        self.blocks[self.head] = block;  // 覆盖老的
        self.head = (self.head + 1) & (self.blocks.len() - 1);
    }
}
```

容量选 2 的幂,& 替代 %。1M 条 × 20 字节 = 20 MB,可接受。

### 2.0.5 命名 channel / topic

data block 不只一种,有 player_pos / enemy_ai / network_packet 等。type_guid 区分。UI 可过滤"只看 player_pos"。

工业 logging 系统(syslog / journald)用 facility / priority 区分。结构相同。

## 3 · 四域深入

### 类比:打猎的标本

猎人打到一只鹿,不只记时间和地点,还**采集标本**(鹿角、皮毛、胃内容物)。标本是"那只鹿"的具体信息,时间和地点是元数据。

debug data block 一样:**event 是时间和位置,data block 是标本**。

### 2.3 collation 改造

data block 不是 begin/end,**单独处理**:

```rust
fn collate_event(e: &DebugEvent, frame: &mut FrameSummary) {
    match &e.kind {
        DebugEventKind::Begin => { /* 入栈 */ }
        DebugEventKind::End => { /* 出栈,算 duration */ }
        DebugEventKind::Data { name, value } => {
            // 不影响 span stack,只记录数据
            frame.data_blocks.push((e.cycle, name, value.clone()));
        }
    }
}
```

```rust
pub struct FrameSummary {

    pub stats: HashMap<u64, SpanStats>,

}
```

### 3.2 · Linux 系统编程视角

Linux ftrace 也有 data block:

```bash
echo 'comm == "bash"' > /sys/kernel/debug/tracing/events/sched/sched_switch/filter
# ftrace event 有 args 字段(数据)
cat /sys/kernel/debug/tracing/events/sched/sched_switch/format
```

format 字段定义 event 的 payload schema。Casey 的 DebugValue enum 是 Rust 风格的 schema。

### 3.3 · Rust 生态视角

`tracing` crate 的 event 也带 data:

```rust
tracing::info!(pos = ?player.pos, hp = player.hp, "update");
// "update" 是消息,pos 和 hp 是数据
```

tracing 用 macro,自动解构。Casey 用 explicit 函数,简单。

## 5 · 对照与变奏

**Logging 的工业实现**:

- **syslog**(Unix):facility + priority + message,文本
- **journald**(systemd):结构化 binary,可查询
- **Windows ETW**(Event Tracing for Windows):binary + provider
- **OpenTelemetry**:分布式 trace + span
- **log4j / slf4j**:Java 标准日志

每个都是"data block"的变种——时间戳 + 元数据 + payload。

### structured logging 的兴起

老式 logging:`print(f"player at {x}, {y}")`,文本字符串。难查询。

新式 structured logging:

```rust
// tracing crate
tracing::info!(player_x = x, player_y = y, "player moved");
```

字段是结构化的(可查询 "player_x > 100"),不是文本。日志聚合工具(ELK / Loki)自动解析。

Casey 的 data block 是更底层的 structured logging——binary payload + type_guid。比 tracing 更紧凑,但 API 更原始。

### binary vs text logging

**Text**(journald 默认):
- 优点:可读、grep 友好
- 缺点:大、解析慢

**Binary**(Casey / protobuf):
- 优点:紧凑、快
- 缺点:不可读、需要 decoder

工业实践:**生产用 binary**(性能),**debug 用 text**(可读)。两套 logger 并存。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:data block 为什么用 binary DebugValue 而不是 format!() 字符串?

**参考解答**:
- format!() 每次分配 String + 解析格式说明符(慢)
- DebugValue enum 直接存类型化数据(快,零分配 if Copy)
- 查询时,按 name 直接拿 value(UI 自动选 widget)
- 字符串还要解析才知道是 int 还是 float
- 录制文件小(8 字节 int vs 4+ 字节字符串)
- trade-off:DebugValue 不灵活(只支持 enum 内类型)

### Lv2 · 动手实践

**题**:扩展 event kind 加 Data,实现 debug_data API,collate 收集到 FrameSummary。

**参考解答**:

```rust
#[derive(Clone, Debug, PartialEq)]
enum DebugValue { Float(f32), Int(i64), Vec2(f32, f32) }

#[derive(Clone, Debug)]
enum EventKind { Begin, End, Data { name: &'static str, value: DebugValue } }

#[derive(Clone, Debug)]
struct Event { cycle: u64, guid: u64, kind: EventKind }

#[derive(Clone, Debug, Default)]
struct FrameSummary {
    spans: Vec<(u64, u64)>,  // (guid, duration)
    data_blocks: Vec<(u64, &'static str, DebugValue)>,
}

fn collate(events: &[Event]) -> FrameSummary {
    let mut frame = FrameSummary::default();
    let mut stack: Vec<(u64, u64)> = Vec::new();  // (guid, begin_cycle)
    for e in events {
        match &e.kind {
            EventKind::Begin => stack.push((e.guid, e.cycle)),
            EventKind::End => {
                if let Some((guid, begin)) = stack.pop() {
                    if guid == e.guid {
                        frame.spans.push((guid, e.cycle - begin));
                    }
                }
            }
            EventKind::Data { name, value } => {
                frame.data_blocks.push((e.cycle, name, value.clone()));
            }
        }
    }
    frame
}

fn main() {
    let events = vec![
        Event { cycle: 100, guid: 1, kind: EventKind::Begin },
        Event { cycle: 120, guid: 100, kind: EventKind::Data { name: "pos", value: DebugValue::Vec2(150.0, 200.0) } },
        Event { cycle: 130, guid: 101, kind: EventKind::Data { name: "hp", value: DebugValue::Int(75) } },
        Event { cycle: 200, guid: 1, kind: EventKind::End },
    ];
    let frame = collate(&events);
    println!("spans: {:?}", frame.spans);
    println!("data:");
    for (c, n, v) in &frame.data_blocks {
        println!("  cycle={} {}={:?}", c, n, v);
    }
}
```
