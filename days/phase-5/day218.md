# Day 218 · 调试元素哈希

> 调试元素的 ID 现在用字符串 hash(FNV-1a)。但 casey 发现 hash 冲突开始出现——两个不同字符串 hash 到同一个 u64。今天 casey 加"hash 段位"和"快速比较"机制,降低冲突概率并加运行时检测。

## 0 · 为什么要有这一天

之前用 FNV-1a 64-bit hash 给 debug 字符串分配 GUID:

```rust
const fn guid(s: &str) -> u64 {
    // FNV-1a
    ...
}
```

64-bit hash 空间 = 1.8 × 10^19 个值,直觉上冲突概率近乎 0。但生日悖论告诉我们:**只要 hash 数量到 ~5 billion,冲突概率就到 50%**。

游戏项目通常有几百到几千个 debug guid,远不到 5 billion。但还有另一种冲突源:**用户写错字符串**。例如:

```rust
let g1 = guid("debug/show_fps");
let g2 = guid("debug/show_fp");  // 漏了个 s,但可能 hash 到不同值,无关
let g3 = guid("Debug/Show_FPS");  // 大小写不同,可能 hash 到同 g1
```

更隐蔽的:**两个不同字符串可能 hash 同值**。FNV-1a 不是加密 hash,可以构造碰撞。

casey 今天的方案:

1. 加 hash 段位:除了 u64 hash,再附加字符串长度 + 前 8 字节,构成"复合 hash"
2. 启动时全表扫描,如果发现不同字符串 + 同 hash,assert 失败
3. 给关键 API 加 `debug_verify_no_collisions()`

心理锚点:看完今天,你能解释生日悖论、知道何时该用 64-bit hash、何时该用 128-bit。

## 1 · Casey 今天做了什么

1. **加 composite hash**:u64 + length + prefix,组合成"unique ID"
2. **加启动扫描**:debug 系统初始化时遍历所有 guid,检测冲突
3. **加 perf counter**:hash 函数本身的耗时被 profiler 监控(避免 hash 成为瓶颈)
4. **修一个 bug**:发现 `"physics/gravity"` 和另一个长字符串 hash 冲突,改字符串

## 2 · 心智模型

### 类比:身份证号的段位

身份证号 18 位:6 位地区码 + 8 位生日 + 3 位序号 + 1 位校验。即使生日相同(8 位),地区 + 序号还能区分。

hash 也是,如果只用一段(u64),有冲突风险;用多段组合,冲突概率显著降低。

这个类比的精髓:**单一来源的标识总有冲突风险,多源组合让冲突概率指数级下降**。身份证号如果只用生日 8 位,全国同年同月同日生的人都"冲突"。加上地区码 6 位,只冲突到同省同日生。再加序号 3 位,基本唯一(同省同日生最多 999 人)。

casey 的 composite hash 完全对应:FNV-1a 64 位 + 长度 32 位 + 前缀 32 位 = 总共 128 位组合空间。两个不同字符串要在这三个独立维度上同时撞,概率 ≈ 单维度概率的乘积,近乎零。

类比还能更深:**校验位**是身份证的最后一位,根据前 17 位算出来,防止录入错误。casey 的 composite hash 也有类似功能——如果两个字符串"FNV-1a 撞了",但长度不同,系统立刻发现,等于"自动校验"。这是**冗余校验**的工程价值,航天器、医疗设备都用类似思路。

### 2.1 生日悖论回顾

N 个人中至少两人生日相同的概率:

```
P(冲突) = 1 - 365!/(365^N × (365-N)!)
```

N=23 时 P≈50%,N=70 时 P≈99.9%。

hash 空间 H,冲突概率约 N²/(2H)。64-bit hash,H=2^64,N=10000 时:

```
P ≈ 10000²/(2 × 2^64) ≈ 2.7 × 10^-12
```

几乎不可能。但 N=5 billion 时:

```
P ≈ (5e9)²/(2 × 2^64) ≈ 0.5
```

50%。所以 64-bit hash 在大数据集上有冲突风险。

### 2.2 复合 hash

```rust
#[derive(Copy, Clone, PartialEq, Eq, Hash)]
struct DebugId {
    hash: u64,       // FNV-1a
    length: u32,     // 字符串长度
    prefix: u32,     // 字符串前 4 字节(LE)
}
```

两个不同字符串 hash 撞了,长度或前缀还要撞才真冲突。概率进一步降低 N²/(2 × 2^64 × 2^32 × 2^32) ≈ 几乎为 0。

### 2.3 启动时全表扫描

```rust
fn verify_no_collisions(registry: &[(String, DebugId)]) -> bool {
    let mut seen: HashMap<DebugId, &str> = HashMap::new();
    for (s, id) in registry {
        if let Some(prev) = seen.get(id) {
            if prev != &s.as_str() {
                panic!("Debug ID collision: {} vs {}", prev, s);
            }
        }
        seen.insert(*id, s.as_str());
    }
    true
}
```

启动时一次扫描,O(N²) 也行,N 通常 < 10000。

### 2.4 加密 hash vs 非加密 hash

- **加密 hash**(SHA-256、Blake3):抗碰撞、慢
- **非加密 hash**(FNV、Murmur、xxHash):快、可能有碰撞

debug 系统不需要抗恶意构造,只需抗意外冲突。FNV-1a + composite 足够。如果想更稳,xxHash 64-bit 在现代 CPU 上比 FNV 快几倍。

### 2.5 第一性原理推导:为什么 hash 是不可避免的

软件工程里 hash 反复出现,因为它是**唯一让"任意大小数据 → 固定大小标识"的方法**。从第一性原理推导为什么这是不可避免的。

**前提**:计算机里很多任务需要"快速判断两个数据是否相等"。直接比较需要 O(N)(N 是数据大小),太慢。如果数据是文件、URL、字符串、数据库行,N 可能是几 KB 到几 GB。

**思路**:把数据预先"压缩"成固定大小标识,以后比较标识而不是原数据。O(N) → O(1)。

**约束**:这个压缩必须**确定性**(同输入同输出),否则没意义。它**不必唯一**(不同输入可能同输出)——这就是冲突。

**结论**:hash 函数是这种"确定性压缩"。固定大小是它的核心优势,冲突是它的代价。任何 hash 都有冲突,只能降低概率,不能消除。

**冲突概率的数学**:
- n 位 hash,空间 = 2^n
- m 个不同输入,期望冲突数 ≈ m² / (2 × 2^n)(生日悖论近似)
- 64 位 hash,m = 1 million,冲突概率 ≈ 10^12 / (2 × 1.8 × 10^19) ≈ 3 × 10^-8(每 3000 万次运行可能 1 次)
- 128 位 hash,m = 1 billion,冲突概率 ≈ 10^18 / (2 × 3.4 × 10^38) ≈ 10^-21(宇宙年龄内不会冲突)

**工程选择**:
- 32 位 hash:1 million 数据,冲突概率 ~1%。**不安全**
- 64 位 hash:1 million 数据,冲突概率 ~10^-8。**够用,但要监控**
- 128 位 hash:几乎不可能冲突。**安全,空间大一倍**

casey 选 64 位 + composite(等价 ~96-128 位),平衡安全和性能。这是工业级选择。

### 2.6 Hash 函数的工程实现

FNV-1a 的代码极简,但每个细节都有理由:

```rust
const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

const fn fnv1a(s: &str) -> u64 {
    let b = s.as_bytes();
    let mut h = FNV_OFFSET;  // 任意非零起点
    let mut i = 0;
    while i < b.len() {
        h ^= b[i] as u64;     // XOR 字节进来
        h = h.wrapping_mul(FNV_PRIME);  // 乘素数扩散
        i += 1;
    }
    h
}
```

**关键设计点**:
- `FNV_OFFSET` 是 64 位随机数,固定常量(0xcbf29ce484222325)。任何非零起点都行,但官方选这个。
- `FNV_PRIME = 2^40 + 2^8 + 0xb3 = 0x100000001b3`。这是经过数学证明扩散性最好的素数之一。
- `XOR` 然后 `MUL`——XOR 引入数据,MUL 扩散到所有位。每次迭代把"上一个状态 + 当前字节"充分混合。
- `wrapping_mul`——Rust 默认整数 overflow panic,这里用 wrapping 允许溢出(hash 不关心数学正确性,只关心确定性)。

**为什么 FNV 比简单 sum 好?** Sum(s) = s[0] + s[1] + ... 也是确定性的,但所有字序重排同结果("ab" 和 "ba" 同 hash)。FNV 因为有 XOR,字序敏感。

**性能**:FNV-1a 在现代 CPU 上 ~0.5 ns/byte。30 字符字符串 ~15 ns。这比一次 L3 cache miss 还快(~30 ns)。FNV 在 hot path 上几乎免费。

**SIMD 优化**:FNV 本身不容易 SIMD 化(每字节依赖前一状态)。但 xxHash、CityHash 这些"块 hash"专门为 SIMD 设计,一次处理 32+ 字节,~0.1 ns/byte。casey 没用是因为 FNV 简单适合教学。

```rust
// 默认 hasher(SipHash 1-3,抗攻击但慢)
use std::collections::HashMap;

```

### 3.4 · 性能视角


### 3.5 · 🐧 Linux 系统编程视角(扩展)

Linux 内核用 hash 几十年,有大量工业级实例:

**1. `dput()` / `dget()` 的 dentry hash**:文件路径解析时,内核把"父 dentry + 子名"hash 起来,查 dentry cache。FNV-2 / MurmurHash 都用过。

**2. `tcp_v4_hash()` 的 socket hash**:TCP socket 用 4-tuple (src_ip, src_port, dst_ip, dst_port) hash 找 socket。每秒数百万包,hash 必须极快。Linux 用 Jenkins hash。

**3. `skb_get_hash()` 的 flow hash**:网络包 flow identification,用 Bob Jenkins hash。流量分析、负载均衡用。

**4. SLAB 的 freelist hash**:某些 SLAB allocator 用 hash 检测 use-after-free(把 free 的对象的 magic 数 hash 起来,看下次 alloc 时 magic 还在不在)。

**5. `/proc/<pid>/` 的 PID hash**:Linux 用 `pid_hash` 数组,PID → struct pid。`find_task_by_vpid()` 用这个 hash。

**6. RAID 5/6 的 checksum hash**:md 用 CRC32(也是 hash 的一种)检测数据损坏。

**7. ftrace 的 trace event hash**:每个 trace event 注册时,名字被 hash,运行时查找 O(1)。

casey 的 debug hash 是这些 kernel hash 的最简版本——思想一致,实现简化。理解 casey 的设计,你看 Linux 内核 hash 代码不会陌生。

### 3.6 · 🎮 游戏工业对照

游戏引擎的 hash 用途极广:

**1. Asset path → asset handle**:所有引擎都用。Unity 用 128-bit GUID,Unreal 用 64-bit FName hash,Godot 用 String hash,Bevy 用 `Handle<T>` 加 ECS。

**2. Animation state name → state index**:状态机查找,O(1) 而不是 O(N) 字符串比较。

**3. Network message ID**:每个 message 类型有 hash ID,client/server 双方用同 hash 同 ID。WebSocket 子协议、Protobuf、FlatBuffers 都用这思路。

**4. Shader uniforms**:GLSL uniform 名 → location,内部 hash 查找。

**5. ECS archetype hashing**:Bevy 把 component set hash,archetype cache 查询。

**6. Save file versioning**:游戏存档版本号 hash,加载时验证兼容性。

casey 的 debug guid 是这个家族的"调试字符串 interning"。学懂这个,你看任何游戏引擎代码都能识别"哦这里用 hash 是为了 X"。

### 3.7 · 🎨 图形学视角

图形学的 hash 应用:

**1. Texture hash**:防止重复加载相同纹理。引擎把纹理文件 hash 一下,加载前查 hash table,已加载就复用。

**2. Shader hash**:防止重复编译相同 shader。shader 源码 hash,缓存编译结果。

**3. Material hash**:相似 material 合并,减少 draw call 切换。Unreal 的 "draw call merging" 内部用 material hash。

**4. GPU resource handle**:Vulkan 的 pipeline cache、descriptor set 都有 hash 加速查找。

**5. CRC32 for asset integrity**:每个 asset 文件存 CRC32,加载时校验。如果改了文件( corruption 或 mod),CRC32 不匹配,引擎警告。

**6. Spatial hash for culling**:大世界游戏的粗粒度 culling 用 spatial hash。把世界分成 grid,每 cell 维护 entity list。entity 移动时 update hash 位置。

casey 的 hash 是单维(字符串 → ID),spatial hash 是多维(2D/3D 坐标 → cell)。底层思想一致。

## 5 · 对照与变奏

hash 在不同领域:

- **Git**:SHA-1(原)、SHA-256(新)。commit ID
- **Bitcoin**:SHA-256 × 2。proof of work
- **Bloom filter**:多 hash 函数组合,membership 测试
- **Merkle tree**:树状 hash,文件系统、blockchain
- **Cryptographic signature**:RSA + SHA-256,数字签名
- **Password hashing**:bcrypt / argon2,防止暴力破解
- **CDN cache key**:URL hash 决定 cache 位置
- **Hash partitioning**:数据库分片,sharding 用 hash

casey 的 debug hash 是最朴素的"字符串到 ID",但底层思想和这些一样。

### Hash 选择决策树

如何为项目选 hash:

```
需要加密安全吗?(签名、密码)
├─ 是 → SHA-256 / Blake3 / argon2(密码)
└─ 否 → 继续

需要抗 HashDoS 攻击吗?(web 服务器 HashMap)
├─ 是 → SipHash-2-4(Rust 默认)
└─ 否 → 继续

数据量 > 1 billion?
├─ 是 → 128-bit hash(Blake3、FARMHash 128)
└─ 否 → 继续

需要极快(每秒千万次)?
├─ 是 → xxHash / FxHash
└─ 否 → Murmur3 / FNV-1a(够用)
```

casey 的选择:FNV-1a,因为 (1) 非加密、(2) 不抗 DoS(debug only)、(3) 数据量 < 10000、(4) 编译时算,不需要极快——简单第一。

### 历史演化

**1960s**:CRC32 出现,通信校验
**1970s**:Unix 文件系统用简单 hash 加速 lookup
**1980s**:MD4 → MD5,密码学起步
**1990s**:SHA-1 主导,加密世界
**2000s**:MurmurHash、FNV,非加密 hash 兴起
**2010s**:xxHash、CityHash、FarmHash,极致性能
**2020+**:Blake3(SIMD 加密 hash)、Argon2(密码)

casey 用 FNV-1a(1991 年发布),不是因为它最快,而是因为它最简单适合教学。理解了 FNV,你看 xxHash 就懂"哦它用 SIMD 加速,但思想一致"。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 casey 用 const fn 而不是 macro 来生成 guid?

**参考解答**:const fn 是真正的函数,有类型检查、能在任何期望 u64 的地方用。macro 是文本替换,容易出错。const fn 在编译时算,等价于字面量,无运行时开销。Rust 1.31+ const fn 是 idiomatic 的"编译时计算"。

### Lv2 · 动手实践

**题**:实现 FNV-1a + composite hash + 启动扫描。测试:

- 相同字符串 hash 相同
- 不同字符串 hash 不同(测试一组真实字符串)
- 故意构造冲突,扫描检测到

**关键算法详解**:

FNV-1a 的核心是 `XOR-then-MUL` 循环。每个字节进来时,先 XOR 进 hash,XOR 后乘以 prime。这个顺序很关键:

```
错误版:XOR only(无 MUL)
hash ^= byte[0]; hash ^= byte[1]; hash ^= byte[2];
→ "abc" 和 "cba" 同 hash(因为 XOR 交换律)

正确版:XOR-then-MUL
hash ^= byte[0]; hash *= PRIME;
hash ^= byte[1]; hash *= PRIME;
→ MUL 让每次 XOR 的结果扩散到所有位,字序敏感
```

**为什么 PRIME 必须是奇数?** 偶数会让 hash 低位永远是 0(乘 2 的幂等价于左移),信息丢失。素数保证所有位都参与。

**为什么 PRIME ≈ 2^40?** 太小(MUL 单字节)扩散不够,太大(MUL 128 位)计算成本高。FNV 经过数学分析,2^40 + 2^8 + 0xb3 是 64 位版本最优。

**Composite hash 的设计**:
- `hash` u64:FNV-1a,主要识别
- `length` u32:防止长度不同的字符串被误判相等
- `prefix` u32:前 4 字节,快速预过滤

为什么这三段?因为它们**独立**——hash 是"全局摘要",length 是"简单计数",prefix 是"局部快照"。三个独立维度同时冲突的概率 = 单维度概率的乘积。从 10^-8 降到 10^-20。

**启动扫描的成本**:
- 10000 个 guid,O(N²) 比较 = 10^8 次,~100ms
- 一次性,启动时可以接受
- 如果 N > 100000,改用 hash table 检测,O(N),~1ms

**参考解答**:

```rust
use std::collections::HashMap;

const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME: u64 = 0x100000001b3;

const fn fnv1a(s: &str) -> u64 {
    let b = s.as_bytes();
    let mut h = FNV_OFFSET;
    let mut i = 0;
    while i < b.len() {
        h ^= b[i] as u64;
        h = h.wrapping_mul(FNV_PRIME);
        i += 1;
    }
    h
}

#[derive(Copy, Clone, PartialEq, Eq, Hash, Debug)]
struct DebugId {
    hash: u64,
    length: u32,
    prefix: u32,
}

fn make_id(s: &str) -> DebugId {
    let bytes = s.as_bytes();
    let mut prefix: u32 = 0;
    for (i, &b) in bytes.iter().take(4).enumerate() {
        prefix |= (b as u32) << (i * 8);
    }
    DebugId {
        hash: fnv1a(s),
        length: bytes.len() as u32,
        prefix,
    }
}

fn verify_no_collisions(strings: &[&str]) -> Result<(), String> {
    let mut seen: HashMap<u64, &str> = HashMap::new();
    for s in strings {
        let id = make_id(s);
        if let Some(prev) = seen.get(&id.hash) {
            // hash 冲突,检查 length + prefix
            if prev.len() as u32 != id.length || make_id(prev).prefix != id.prefix {
                return Err(format!("hash collision: '{}' vs '{}'", prev, s));
            }
        }
        seen.insert(id.hash, s);
    }
    Ok(())
}

    }

    #[test]
    fn no_collision_in_typical_set() {
        let strings = vec![
```

### Lv3 · 迁移设计

**题**:设计一个 bloom filter(多 hash 函数组合,检测"可能存在" vs "一定不存在")。给出 false positive 率公式。

**详细提示**:
- 数据结构:`BitVec` of size m,k 个 hash 函数
- Insert:对每个 hash i,设 bit[hash_i(key) % m] = 1
- Query:对每个 hash i,如果 bit[hash_i(key) % m] = 0,返回"一定不存在";否则返回"可能存在"
- False positive 率:(1 - e^(-kn/m))^k,其中 n = 已插入元素数
- 经验最佳 k = (m/n) × ln(2)

Rust 实现:
```rust
struct BloomFilter {
    bits: Vec<u64>,  // bit storage,64 bits per u64
    num_hashes: usize,
    capacity: usize,
}
impl BloomFilter {
    fn new(expected_items: usize, fp_rate: f64) -> Self;
    fn insert(&mut self, key: &[u8]);
    fn contains(&self, key: &[u8]) -> bool;
}
```

应用场景:
- Web cache:Cache aside 模式,bloom filter 先查"是否可能存在 cache",避免无效 cache lookup
- 数据库:PostgreSQL 的 bloom filter index,加速等值查询
- 分布式系统:Cassandra 用 bloom filter 判断 sstable 是否包含 row key
- 浏览器:Chrome 用 bloom filter 检查 URL 是否在 malware list

casey 的 composite hash 是 bloom filter 的"小子集"——一个 hash + 几个冗余字段,而不是 k 个独立 hash。但思想完全一致。

### 实战补充:Hash 碰撞的真实案例

Hash 碰撞在工程史上几次造成严重事故,值得了解:

**1. PHP HashDoS (2011)**:PHP 5.x 用 Java 风格的 string hash 攻击者发送 POST 数据 `a1=1&a2=1&...&aN=1`,所有 key hash 同值,触发 PHP 的 hash table 退化到 O(N²) 链表扫描。1MB POST 数据让 CPU 跑 100% 几分钟。修复:改用 SipHash(随机化 key),抗碰撞攻击。

**2. Rust HashMap 默认 SipHash**:Rust std 默认 HashMap 用 SipHash-2-4,有随机 key(per-process 随机 seed),抗 HashDoS。代价是 hash 慢(~10ns vs FNV 的 1ns)。Rust 的设计哲学:**默认安全,需要性能时换 hasher**。

**3. Python dict hash collision (2012)**:同 PHP,Python 也补了 randomization。

**4. Bitcoin Cash overflow (2018)**:某交易所用 64-bit hash 给交易 ID,1 年后 hash 碰撞,造成两笔不同交易被合并。修复:改用 SHA-256 256-bit。

**5. Casey HH 自己的碰撞 (Day 218)**:Casey 在视频里发现 "physics/gravity" 和另一个长字符串 hash 撞了,改字符串解决。这是真实开发中的"日常 bug",但 Casey 加了启动扫描后能立刻发现。

这些案例的共同教训:**hash 不是数学上的"等价类",是工程上的"近似等价"**。看似不冲突的 hash,在特定输入下会冲突。casey 的 composite + 启动扫描是工业级的防御性编程。

### Rust const fn 的能力演进

`const fn` 是 Rust 的"编译时计算"机制,Casey 的 FNV-1a 是经典用例。看它的能力演进:

- **Rust 1.31 (2018)**:const fn 引入,只支持基本算术和 if/while
- **Rust 1.46 (2020)**:支持 `match`、`if let`
- **Rust 1.57 (2021)**:支持 panic、`for` 循环、大部分控制流
- **Rust 1.65 (2022)**:支持 mutable static、`Vec` 分配(unstable)
- **Rust 1.79 (2024)**:支持 `&mut` in const,大部分 std lib 函数 const

casey 用的 const fn 用了 `while i < b.len()`(Rust 1.31 即可)。如果想用更现代写法:

```rust

const fn fnv1a(s: &str) -> u64 {
    let mut h = FNV_OFFSET;
    for &b in s.as_bytes() {
        h ^= b as u64;
        h = h.wrapping_mul(FNV_PRIME);
    }
    h
}
```

更简洁,但需要新版 Rust。教学版用 while 兼容老版本。

## 10 · 深入:hash 函数的密码学 vs 性能权衡

casey 选 FNV-1a(非加密 hash),是有具体工程理由的。让我们把"hash 函数该选哪个"这件事彻底讲透——这是每个 Rust 工程师迟早要面对的决策。

### 10.1 hash 函数的三个维度

**维度 1:速度**。每次 hash 计算多快?

| 函数 | 速度(short key) | 速度(long key, 1KB) | 适用 |
|---|---|---|---|
| FNV-1a | ~1 ns | ~3 GB/s | 短 key,内部 ID |
| xxHash3 | ~5 ns | ~30 GB/s | 长数据 hash |
| ahash | ~1 ns | ~10 GB/s | Rust HashMap 默认替代 |
| SipHash-2-4 | ~15 ns | ~1 GB/s | Rust HashMap 默认,抗 DoS |
| BLAKE3 | ~50 ns | ~10 GB/s | 加密级,抗碰撞 |

游戏 debug 系统的 hash 都是短字符串(几十字节),FNV-1a 几乎免费。但若 hash 大量数据(资产路径汇总、场景 state 哈希),换 xxHash3 显著快。

**维度 2:碰撞抗性**。两个不同输入得到同 hash 的难度。

- **FNV-1a**:弱。已知碰撞对可以构造(`"buzzle"` 和 `"psycho$"` hash 同值)。
- **xxHash3**:中。理论上 64-bit 输出有 2^32 量级生日碰撞,但需要构造。
- **BLAKE3**:强。加密级,抗 second-preimage 攻击。

casey 的 debug 系统**接受 FNV 的弱碰撞抗性**——内部数据,用户不可能构造恶意碰撞。但 Rust HashMap 必须抗碰撞(用户可能控制 key),所以默认 SipHash。

**维度 3:随机化 / seed**。同输入是否永远产生同 hash?

- **FNV-1a**:无 seed,确定性。
- **Rust HashMap SipHash**:per-process 随机 seed,同输入跨进程 hash 不同。
- **BLAKE3 with key**:有 32-byte key,可做 keyed hashing(MAC)。

随机化对抗**重放攻击**——攻击者无法预测 hash,不能预构造碰撞。代价:同输入跨进程结果不同,跨进程不能直接传 hash 值。

### 10.2 casey 为什么不加密

casey 选 FNV-1a 的具体理由:

1. **确定性需要**:debug guid 跨运行必须一致——上次的 save 文件里的 guid 这次还能识别。SipHash 的 random seed 让 guid 跨运行变化,save/load 不可用。
2. **性能**:每帧 hash 几百个 debug 字符串,SipHash 15ns × 500 = 7.5μs,FNV 1ns × 500 = 0.5μs。差 7μs/帧,debug only 但仍可见。
3. **碰撞可接受**:debug 数据本来就是开发用,碰撞导致 UI 显示错乱,不是安全问题。**casey 加运行时 assert 检测**就够了,不需要密码学抗性。

这个权衡的工程教训:**hash 函数选择要匹配场景**。不要无脑用 SHA-256(慢且过度),也不要无脑用 FNV(可能被 DoS)。casey 给了一个清晰的"按需求选 hash"的范例。

### 10.3 64-bit vs 128-bit hash

casey 用 64-bit hash。什么时候需要 128-bit?

**生日悖论下的碰撞概率**:
- 64-bit:5 billion hash 后 50% 冲突
- 128-bit:8.5 × 10^22 hash 后 50% 冲突(超出宇宙原子数)

**实战**:
- 内部 ID(几千到几百万):64-bit 完全够
- 跨网协议(可能被恶意构造):128-bit,加 randomization
- 加密签名(永久抗碰撞):256-bit(SHA-256 / BLAKE3)
- 区块链 / 长期存档:512-bit+

casey 的 debug GUID 是 64-bit,完全合适。如果 HH 项目要做多人模式(玩家 ID 跨网络),必须升到 128-bit + 随机 seed。
