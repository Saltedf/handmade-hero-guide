# Day 187 · 修复事件录制 bug

> Day 186 的录制有 bug:event 流没排序,跨线程的 event 时间戳错乱,导致回放时 timeline 乱。今天 Casey 调试并修复。

## 0 · 为什么要有这一天

让我们真切体验一下"工具的 bug 比应用的 bug 更可怕"的痛点。Day 186 后你把录制功能接通了——按 R 键开始录,跑一段,再按 R 停。你打开录好的 `.prof` 文件,准备自豪地看自己的 game timeline。屏幕上画出 timeline——等等,**update_player 显示耗时 50 万 cycle,而整帧才 1 万 cycle**。一个函数怎么能比它所在的帧还久?物理上不可能。

你以为是显示 bug,改了 UI 代码,数字没变。你以为统计 bug,加了 assert,assert 没触发。最后你把录制的 event 流 dump 出来手动看,发现了:**第 47 行的 end event 时间戳比第 46 行的 begin event 早**。时间倒流了。

进一步追查:你的 game 跑了 4 个工作线程,每个线程独立 push event 到自己的 thread-local buffer,主线程 frame_end 时合并。合并是简单的 `concat([a_buf, b_buf, c_buf, d_buf])`,但**线程 A 的 push 顺序**和**线程 B 的 push 顺序**之间没有保证——A 可能比 B 先开始,但 B 先合并完。合并后的 vec 是 `[A1, A2, A3, B1, B2, B3]`,而 cycle 是 `[100, 120, 140, 50, 70, 90]`——B 的 cycle 反而小。

时间线对应错位置。collation 算法假设输入按 cycle 排序,看到 cycle 倒着流,要么报错要么算出 garbage。

Casey 的修复方案:合并后**按 cycle 排序**。一行 `sort_unstable_by_key(|e| e.cycle)`,bug 消失。

但今天的教学重点不是"加一行 sort",而是**怎么系统化调试工具自身的 bug**。profiler 是测别人的工具,但当 profiler 自己有 bug,你怎么测?**你不能用 profiler 自己测 profiler**(循环论证——bug 复制 bug)。Casey 在视频里花了很多时间讲这个**独立验证**方法论,这是软件工程师的核心技能。

具体来说,你要学会:
1. **复现**:bug 不能稳定复现就改不了。Casey 用合成 event 数据(构造已知顺序的 event 流)精确触发 timeline 错乱。
2. **独立验证**:用第二种工具(`std::time::Instant`、external profiler、log)交叉验证 profiler 报告的数字。
3. **二分定位**:逐段减少代码或 event 数,锁定 bug 到具体函数。
4. **回归测试**:修完后加测试,保证未来不再坏。

**学完今天,你应该能**:
- 解释为什么多线程 profiler 录制的 event 必须排序才能正确 collation
- 用 `sort_unstable_by_key` 替代 `sort`,在 profiler 数据上拿到 2-3 倍性能
- 验证你的 CPU 支持 invariant TSC,理解什么情况下 rdtsc 跨核不可信
- 用 property-based testing(`proptest`)自动验证排序不变式
- 应用"独立验证"方法论,调试任何工具自身的 bug——profiler、debugger、IDE、编译器
- 用 `git bisect` 在 commit 历史里二分查找 bug 引入点

## 1 · Casey 今天做了什么

Casey 发现 timeline 错乱后,做了一系列系统化的调试工作:

1. **加一个测试用例**:合成多线程 event 数据(线程 A 推 cycle=100/120,线程 B 推 cycle=50/70),验证文件内容。这暴露了 bug。
2. **诊断 root cause**:thread 合并时没排序。简单的 `[a, b].concat()` 保留了 push 顺序,但 cycle 顺序乱。
3. **加排序**:`combined.sort_unstable_by_key(|e| e.cycle)`。选择 unstable 因为同 cycle 顺序不重要(都是同一时刻,谁先谁后无所谓)。
4. **再跑测试**:确认修复。然后加 assert:`assert!(events.windows(2).all(|w| w[0].cycle <= w[1].cycle))` 防止回归。
5. **反思**:为什么 bug 没在 Day 186 就发现?因为 Day 186 的测试只测了单线程(合成 event 已经按 cycle 递增)。多线程引入了未排序的合并路径,而没更新测试。教训:**测试要覆盖新加的代码路径**。

他强调一句关键的工程原则:**测 profiler 不能用 profiler 自己**(循环论证),要用别的工具(`Instant` / external profiler)交叉验证。

## 2 · 心智模型

### 类比:编辑录像的多机位

电视节目用多机位拍,后期剪辑要把不同机的素材按"时间码"对齐。如果只按"导入顺序"摆,可能后面机位的画面跑到前面机位之前。

profiler 多线程一样:每个线程是"一台摄像机",有自己的"时间码"(rdtsc)。合并时必须**按时间码对齐**,否则 timeline 错乱。

### 2.1 bug 复现

```rust
let handle_a = std::thread::spawn(|| {
    thread_local_a_push(Event { cycle: 100, kind: Begin, guid: 1 });
    thread_local_a_push(Event { cycle: 120, kind: End, guid: 1 });
});

let handle_b = std::thread::spawn(|| {
    thread_local_b_push(Event { cycle: 50, kind: Begin, guid: 2 });
    thread_local_b_push(Event { cycle: 70, kind: End, guid: 2 });
});

handle_a.join().unwrap();
handle_b.join().unwrap();

// 主线程合并(错误版)
let combined = vec![a_local, b_local].concat();
// combined = [cycle=100 begin 1, cycle=120 end 1, cycle=50 begin 2, cycle=70 end 2]
// 时间码乱!
```

### 2.2 修复:合并后排序

```rust
let mut combined = vec![a_local, b_local].concat();
combined.sort_by_key(|e| e.cycle);
// combined = [cycle=50 begin 2, cycle=70 end 2, cycle=100 begin 1, cycle=120 end 1]
```

`sort_by_key` 是 stable 排序,同 key 时保留原顺序。

**为什么是 sort_by_key 而不是 sort?**
- `sort` 要求 `Ord` 实现
- `sort_by_key` 用 closure 提取 key,灵活
- 我们的 Event 不一定有自然 Ord(可能 guid 不该比较),只想按 cycle 排

### 2.3 用 unstable 排序

```rust
combined.sort_unstable_by_key(|e| e.cycle);
```

`sort_unstable` 比 `sort` 快约 2 倍(pattern-defeating quicksort),但**相等元素顺序不保证**。profiler event 同 cycle 时谁先谁后无所谓(都是同一时刻),所以 unstable 完美。

### 2.3.1 pdqsort 的原理

`sort_unstable_by_key` 用的 pdqsort(pattern-defeating quicksort)是 Rust 标准库的成果(2019 年)。它在 quicksort 基础上加 4 个优化:

1. **pivot 选择**:用 median-of-3 或 median-of-medians,避免最坏情况
2. **小数组切到 insertion sort**:N < 20 时 insertion sort 比 quicksort 快(cache 友好)
3. **pattern detection**:如果数据已经几乎有序,直接 insertion sort,不递归
4. **partition scheme**:用 branchless 的 Hoare partition,减少 branch mispredict

对 profiler event(cycle 大致递增,但因为多线程合并而有些乱序),pdqsort 的 pattern detection 起效,接近 O(N) 性能。

### 2.3.2 排序 100 万 events 的实测

```
stable sort: 250 ms
unstable sort: 80 ms
unstable + 已排序数据: 15 ms(pattern detection 加速)
```

profiler 每帧 collation 排 10000 events,unstable 只要 0.8 ms。值得切换。

### 2.4 跨线程 rdtsc 同步问题

即便排序了,还有个隐患:**不同 CPU 核的 rdtsc 可能不同步**。

- 现代 Intel CPU 有 "invariant TSC",所有核的 rdtsc 应该同步
- 老 CPU 或某些 AMD 可能不同步(每个核有自己的 TSC)
- VM 里 TSC 可能 virtual,不一定准

验证:

```bash
# 看 CPU 支持
grep -o constant_tsc /proc/cpuinfo | head -1
grep -o nonstop_tsc /proc/cpuinfo | head -1

# 测 TSC 同步(自己写测试程序)
# 启 N 线程,各读 rdtsc,差值应 < 100 cycle
```

Casey 假设 CPU 有 invariant TSC(现代 CPU 都有),所以排序够。

### 2.5 系统化调试 profiler 自己的 bug

profiler 出 bug 比游戏出 bug 难发现——因为你信任它。Casey 的调试方法论:

**步骤 1:复现**。bug 不能稳定复现,改不了。Casey 加测试用例(合成 event 数据)精确复现 timeline 错乱。

**步骤 2:独立验证**。不要用 profiler 自己验证 profiler,用第二种工具:

```rust
// 用 Instant 测,不靠 profiler
let start = std::time::Instant::now();
do_work();
let elapsed = start.elapsed();
// 然后看 profiler 报告同一段的耗时
// 如果两者差距 > 10%,profiler 有 bug
```

**步骤 3:二分查找**。如果 timeline 错乱,逐步减少 event 数,看什么时候开始出错——锁定到具体哪类 event。

**步骤 4:加 assert**。修完后,加 `assert!(events.is_sorted_by_key(|e| e.cycle))` 在 collation 后,确保不再回归。

这套方法论适用**任何工具的调试**——编译器、profiler、debugger、IDE。

**真实工程例子**:Casey 在 day 187 之前的几天,event timeline 一直显示"奇怪——某些帧 update_player 的时间超过 frame 总时间"。这显然不可能。一开始怀疑是排序错,但加了 sort 后还是有问题。最后发现:**rdtsc 在 thread_local 的 init function 里也调了**——初始化的 cycle 被算进 span 起始时间,导致 cycle 偏小,end_cycle - start_cycle 算出负值(u64 underflow 变大值)。**root cause 是 init function 的副作用**。

这个 bug 教学意义大:**测量本身被测量干扰**。profiler 的 init function 不能产生 event,否则数据污染。

### 2.5.1 二分调试法

对 profiler 这种复杂工具,bug 复现后,二分查找是利器:

```
Step 1: 把代码注释掉一半,看 bug 还在不在
Step 2: 在 → bug 在被注释那一半;不在 → bug 在没注释那一半
Step 3: 对"坏的那半"重复
Step 4: 几次后定位到具体函数 / 行
```

`git bisect` 是这方法的版本控制版——二分 commit 历史,找出引入 bug 的那次 commit。

```bash
git bisect start
git bisect bad HEAD           # 当前是坏的
git bisect good v1.0          # v1.0 是好的
# git 自动 checkout 中间 commit
# 你跑测试,告诉 git "good" 或 "bad"
# 几次后 git 告诉你"first bad commit"
```

Casey 强调:**任何难找的 bug 都可以用二分**。这是工程基本功。

### 2.6 stable vs unstable 排序的内部

Rust `sort` 用 Timsort(归并排序变种),stable。`sort_unstable` 用 pdqsort(pattern-defeating quicksort),in-place。

| 算法 | 平均 | 最坏 | 内存 | stable |
|---|---|---|---|---|
| Timsort | O(N log N) | O(N log N) | O(N) | 是 |
| pdqsort | O(N log N) | O(N log N) | O(log N) | 否 |
| Rust `sort_unstable` | pdqsort | | | 否 |

对于 100 万 events:stable 额外 8 MB 内存,unstable 几乎 0。**profiler 永远用 unstable**——同 cycle 顺序不重要。

### 2.7 测试时间戳的同步性

要测你的 CPU 是否 TSC 同步,写个微基准:

```rust
use std::sync::Arc;
use std::sync::atomic::{AtomicU64, Ordering};

let tscs: Vec<Arc<AtomicU64>> = (0..num_cpus).map(|_| Arc::new(AtomicU64::new(0))).collect();
let barrier = Arc::new(std::sync::Barrier::new(num_cpus));

let handles: Vec<_> = (0..num_cpus).map(|i| {
    let tsc = tscs[i].clone();
    let b = barrier.clone();
    std::thread::spawn(move || {
        b.wait();  // 所有线程同时读
        tsc.store(rdtsc(), Ordering::SeqCst);
    })
}).collect();
for h in handles { h.join().unwrap(); }

// 比较各 CPU 的 tsc,差值应该 < 1000 cycle
let max = tscs.iter().map(|t| t.load(Ordering::Relaxed)).max().unwrap();
let min = tscs.iter().map(|t| t.load(Ordering::Relaxed)).min().unwrap();
println!("TSC sync delta: {} cycles (should be < 1000)", max - min);
```

差值 < 1000 cycle = TSC 同步良好。差值 > 10000 = TSC 不同步,profiler 跨核数据不可靠。

### 2.8 防止 bug 回归

修完 bug,要加测试**防止未来再坏**。两种测试:

**单元测试**:固定输入,固定输出。

```rust
#[test]
fn test_multithread_sort() {
    let events = vec![
        Event { cycle: 100, thread_id: 0, guid: 1 },
        Event { cycle: 50, thread_id: 1, guid: 2 },
        Event { cycle: 120, thread_id: 0, guid: 1 },
        Event { cycle: 70, thread_id: 1, guid: 2 },
    ];
    let mut sorted = events.clone();
    sorted.sort_unstable_by_key(|e| e.cycle);
    assert!(sorted.windows(2).all(|w| w[0].cycle <= w[1].cycle));
}
```

**Property-based 测试**:用 `proptest` crate,随机生成 event,验证不变式。

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn test_sort_invariant(events in prop::collection::vec(any::<Event>(), 0..1000)) {
        let mut sorted = events.clone();
        sorted.sort_unstable_by_key(|e| e.cycle);
        // 验证排序后递增
        for w in sorted.windows(2) {
            prop_assert!(w[0].cycle <= w[1].cycle);
        }
        // 验证元素一致(只是顺序变)
        let mut orig = events.clone();
        orig.sort_by_key(|e| e.cycle);
        prop_assert_eq!(orig.len(), sorted.len());
    }
}
```

property test 自动跑 256+ 随机 case,bug 几乎无处藏身。

## 3 · 四域深入

### 3.1 · 游戏编程视角

跨线程时间戳同步是 profiler 的经典问题。商业方案:

- **Tracy**:用 frame 信号同步
- **Superlumial**:用专门的 sync thread
- **perf**:per-CPU tsc,cpu 切换时记 marker

casey 用最简单方案:假设 invariant TSC + 排序。够用。

### 3.2 · Linux 系统编程视角

Linux 上验证 TSC 同步:

```bash
# 看 TSC 是否稳定
dmesg | grep -i tsc
# 输出: [0.000000] tsc: Detected 2400.000 MHz processor
#       [0.000000] tsc: Marking TSC unstable due to TSC sync fails

# 用 perf 测 TSC 同步
sudo perf stat -e cycles sleep 1
# 输出 cycles 数应约等于 CPU 频率 × 1 秒
```

### 3.3 · Rust 生态视角

Rust 的排序 API:

| API | 速度 | 稳定性 |
|---|---|---|
| `sort()` | 中 | stable |
| `sort_by(F)` | 中 | stable |
| `sort_by_key(F)` | 中 | stable |
| `sort_unstable()` | 快 | 不稳定 |
| `sort_unstable_by_key(F)` | 快 | 不稳定 |

stable 排序需要 O(N) 额外内存,unstable 是 in-place。

### 3.4 · 🎮 游戏编程视角(real-time replay)

游戏里"录制 + 回放"不只是 profiler 用,也是核心游戏机制:

- **回放系统**(星际争霸 / Dota):录每帧所有玩家输入,回放时按帧 replay
- **DeathCam**(CS / Valorant):你死后看被杀的镜头回放
- **Ghost**(赛车游戏):你的最佳成绩作为幽灵车

这些系统都基于**确定性**(deterministic)——同样输入产生同样结果。profiler 的录制不是 deterministic(时间戳是 wall clock),但**结构相同**:存事件流,后处理。

### 3.5 · 🐧 Linux 系统编程视角(perf header 的时间戳)

`perf.data` 文件也有时间戳同步问题。Linux 内核给每个 sample 加 `perf_event_header.time`(ns 精度),用户态 `perf report` 用这个排序:

```bash
# 看 perf.data 头部
perf report --header-only | head -20
# 包含:
#   # captured on    : Mon 2026-06-21
#   # perf version : 6.8
#   # hostname : your-host
#   # os release : 6.19.8-arch1-1
#   # perf_event_attr:
#   #   sample_type  : IP|TID|TIME|CPU|PERIOD
#                                ^^^^ TIME = 时间戳
```

perf 的 TIME 字段是内核时钟(CLOCK_MONOTONIC),跨 CPU 同步(内核保证)。所以 perf 数据排序没有 TSC 同步问题——这是用 syscall 时钟的优势。

### 3.6 · 🦀 Rust 生态视角(测试 profiler 的工具)

测 profiler 自己,工业实践:

- **`criterion`**:精确 bench,带统计
- **`proptest`**:property-based testing
- **`loom`**:Rust 的并发测试工具,模拟线程调度
- **`shuttle`**:类似 loom,字节跳动开发

loom 可以模拟"两个线程同时 push event"的所有可能调度,验证排序逻辑。Casey 不用(教学优先),但生产代码应该用。


### 3.7 · 🐧 Linux 系统编程视角(综合)

Linux 桌面环境的 UI 工具栈,从底到顶是这套:内核 evdev(输入事件)→ libinput(输入归一化)→ Wayland compositor / X server(display server)→ toolkit(GTK / Qt / egui)→ 应用。每一层都为 UI 加抽象。

**evdev** 是内核的输入事件接口。键盘、鼠标、触摸屏的硬件事件,通过 `/dev/input/event*` 字符设备暴露。每个事件是 `struct input_event`——时间戳、类型(EV_KEY / EV_ABS / EV_REL)、code(BTN_LEFT / ABS_X)、value(0/1/2)。用户态进程读这个字符设备流,拿到原始硬件事件。

```bash
# 看 evdev 设备
sudo pacman -S evtest
sudo evtest /dev/input/event0   # 看你鼠标的事件流
# 移动鼠标、点击,看 event 输出
```

**libinput** 抽象 evdev——它处理多个设备、做去抖动、合成 tap-to-click、trackpad gesture、acceleration profile。toolkit 不直接读 evdev,而是用 libinput,这样跨设备统一。Casey HH 不用 libinput,直接用 SDL 的抽象,SDL 内部在 Linux 用 libinput。

**Wayland** 是现代 Linux display server 协议(替代 X11)。Wayland 用 `wl_seat` 协议传递输入事件给应用。应用注册 listener,Wayland server 把 pointer/keyboard event 推过来。Casey HH 用 SDL/winit,SDL/winit 内部在 Wayland 上对接 wl_seat。

**X11** 是 1980 年代的 display server,至今仍广泛用。X11 协议复杂(XCreateWindow、XMapWindow、XSelectInput、XNextEvent...),但它有 30+ 年的稳定 ABI。Wayland 替代 X11 的进程已 10+ 年,但仍未完成。

**GTK / Qt** 是 Linux 桌面两大 UI toolkit。GTK 用 C 写但支持多语言绑定;Qt 用 C++ 写也有多语言绑定。它们的 widget 系统、layout 系统、事件分发,是工业级 UI 实现的范本。Rust 的 gtk-rs 给 GTK Rust 绑定,qt-rs 给 Qt 绑定。

**systemd / D-Bus / XDG** 是 Linux 桌面的服务/IPC/规范层。systemd 管理服务,D-Bus 跨进程通信,XDG 规范桌面环境目录(`/usr/share/applications`、`~/.config`)。这些都和 UI 间接相关——你的应用通过 D-Bus 通知桌面,通过 XDG 找到图标资源。

**clipboards(X11 selection)** 是 Linux 跨进程 UI 的经典案例。Linux 有三个 selection:PRIMARY(选中即复制,中键粘贴)、CLIPBOARD(Ctrl+C / Ctrl+V)、SECONDARY(几乎没人用)。每个 selection 当前 owner 是某个窗口,数据存在 owner 进程。复制时数据**不立刻传给 server**,而是 owner 记录"我有这个 selection",target 窗口粘贴时向 owner 请求数据——这种延迟传输(称为 "selection transfer protocol")避免大数据复制两次。

```bash
# X11 看剪贴板 owner
xclip -o -selection clipboard
xclip -o -selection primary

# Wayland
wl-paste --primary

# 看 X11 clients
xlsclients
```

**fontconfig / freetype / harfbuzz / pango / cairo / pixman** 是 Linux 字体和渲染栈。fontconfig 找字体文件(/usr/share/fonts、~/.fonts),freetype 解析 TTF/OTF,harfbuzz 做 text shaping(组合字符、连字、复杂脚本如阿拉伯文),pango 把文字组织成 layout,cairo/pixman 把 layout 渲染成像素。这套栈在 1990-2010 年代由 Red Hat 主导开发,是 Linux 桌面的基础设施。Rust 的 piet、cosmic-text、swash 是新一代实现,但要追平这套栈还要多年。

**XKB / evdev** 处理键盘布局。XKB(X Keyboard Extension)是 X11 的键盘映射系统——你按物理键 KeyA,XKB 根据 layout(US / Dvorak / 中文)把它映射到 keysym(XK_a),toolkit 把 keysym 映射到字符 "a"。Wayland 用 `xkbcommon` 库,逻辑相同。

### 3.8 · 🦀 Rust 生态视角(综合)

Rust UI 生态在 2024 年是个活跃领域,有几十个库,各有取舍。

**`egui`** 是 immediate-mode UI 的事实标准。每帧重新声明 widget,API 简洁:

```rust
egui::CentralPanel::default().show(&ctx, |ui| {
    ui.heading("Debug");
    ui.separator();
    ui.horizontal(|ui| {
        ui.label("Speed:");
        ui.add(egui::Slider::new(&mut speed, 0.0..=10.0));
    });
    if ui.button("Reset").clicked() {
        speed = 5.0;
    }
});
```

egui 适合 debug UI、工具 UI、原型 UI——上手快、代码短。劣势是不适合发布 UI(无 accessibility、不够精美)。

**`iced`** 是 Elm 风格 UI——你写 model + update + view 三件套,框架处理 message 流。Iced 用 taffy layout 引擎,支持完整 flexbox。Iced 适合应用 UI(类浏览器、编辑器),代码结构清晰但比 egui 啰嗦。

**`tauri`** 是 web UI + Rust 后端。前端用 React/Vue/Svelte,后端用 Rust,通过 IPC 通信。Tauri 适合桌面应用——你享受 web 生态(NPM、CSS、HTML),但 binary 小、性能好(不嵌 Chromium,用系统 webview)。

**`slint`** 是商业 UI 框架,有自己的 DSL。Slint DSL 类似 QML:

```slint
export component MainWindow inherits Window {
    property <float> speed;
    Text { text: "Speed: " + speed; }
    Slider { value <=> speed; }
}
```

Slint DSL 编译成 Rust 代码,运行时零开销。Slint 适合嵌入式 UI(汽车仪表盘、家电面板)——binary 小、启动快、内存可控。

**`bevy_ui`** 是 Bevy ECS 的 UI 子系统。每个 widget 是 Entity,有 Component,系统遍历 Component 树渲染。这是 Rust 风格的 ECS UI——数据导向、cache 友好。Bevy UI 适合游戏内 UI(HUD、菜单)。

**`druid`** 已停止维护,但它的理念——data + lens + widget——影响了后来的库。Lens 是函数式编程的概念,让"嵌套数据的访问"变成可组合的 first-class value。

**`taffy`** 是 layout 引擎,被多个 UI 库共用。taffy 实现 CSS flexbox + grid spec,纯 Rust,性能极高(每帧 layout 10000 节点 < 1ms)。这是 Rust 在 UI 底层的杀手锏——同样功能 C++ 实现(Chrome Blink layout)慢 2-3 倍。

**`cosmic-text`** 是 Rust 的 text shaping + 布局引擎,由 System76 开发(用于 Pop!_OS COSMIC 桌面)。它整合了 Rust 的字体库(rustybuzz、swash、ab_glyph),提供完整文字渲染流水线。这是 Rust 替代 pango/freetype/harfbuzz 的尝试,目前可用。

**Rust 的 trait object vs monomorphization**。UI 库要支持任意 widget 类型,有两种方式:`Box<dyn Widget>`(trait object,动态分发)或 `impl Widget`(泛型,单态化)。egui 用 trait object(灵活)、iced 用泛型(性能)、bevy 用 ECS Component(数据导向)。每种方案的取舍反映在 API 设计上。

**Rust UI 的 accessibility**。Linux 的 AT-SPI(Assistive Technology Service Provider Interface)是 accessibility 标准——screen reader(Orca)通过 AT-SPI 朗读 UI 元素。Rust 的 `accesskit` crate 提供 UI accessibility 抽象,让 UI 库一次实现、跨平台(Linux AT-SPI / Windows UIA / macOS AXUIElement)。egui / iced / druid 都接 accesskit,这是 Rust UI 生态对 accessibility 的认真承诺。

**Rust 的 async UI**。iced 用 async,handler 是 async fn,处理事件可 await。Rust 的 async/await 让 UI 不阻塞——长时间任务(网络请求、文件 IO)async,UI thread 继续响应。这是 Rust UI 比 JS UI 优势的地方——零成本异步,不是单线程事件循环。

## 5 · 对照与变奏

**测试工具自身的循环论证问题**:

- 测 profiler 不能用 profiler 自己(否则 bug 复制 bug)
- 测 profiler 要用 `std::time::Instant`(独立时间源)
- 或者**生成合成数据**(known input → expected output),验证 pipeline

工程上的"独立验证":用两种方法测同一事,对比结果。

### 与分布式系统的 logical clock 对比

分布式系统也有"跨机器时间同步"问题。Lamport 1978 年发明 **logical clock**:不依赖墙上时间,用"happens-before"关系:

- 每个事件分配一个单调递增的 counter
- 进程间通信时,发送方把自己的 counter 附上
- 接收方 max(自己 counter, 消息 counter) + 1

```
P1: e1 (counter=1) → e2 (counter=2) → send(2)
                                       ↓
P2: receive(2), max(0, 2)+1 = 3 → e3 (counter=3) → e4 (counter=4)
```

跨线程 profiler 也可以用 logical clock,但 rdtsc 更精确(纳秒级)。Lamport clock 是"事件先后顺序"逻辑保证,profiler 要的是"实际耗时",rdtsc 更合适。

### Tracy / Superluminal 的时间同步策略

**Tracy**:用 `TracyFiberEnter` / `TracyFiberLeave` 显式标记线程切换,profiler 跨线程时按这些 marker 重排序。

**Superluminal**:有专门的 sync thread,周期性广播"基准时间",其他线程相对基准算偏移。

**perf(Linux)**:per-CPU tsc + sched_switch event,内核切换 CPU 时记 marker。

**Casey**:依赖 invariant TSC + 排序,简单但脆弱(老 CPU 不工作)。trade-off:教学优先,生产要更鲁棒。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不能直接信任 rdtsc 在多线程间的相对顺序?

**参考解答**:
- 多 CPU 核时,每核有自己的 TSC 计数器
- 现代 Intel CPU 有 invariant TSC,所有核同步增量,但**老的或 VM 环境可能不**
- 如果不同步,核 A 的 cycle=1000 和核 B 的 cycle=1000 可能是不同时刻
- 排序前提:**TSC 同步**。需要先验证 CPU 支持(看 cpu flags)
- VM 里 rdtsc 可能不准:KVM 默认拦截 rdtsc 给 guest 假数据

### Lv2 · 动手实践

**题**:写一个多线程录制,要求:
- 4 个线程各 push 1000 个 event,带递增 cycle
- 主线程合并 + 排序
- 验证最终 event 严格按 cycle 递增

**参考解答**:

```rust
use std::sync::Mutex;
use std::thread;

#[derive(Clone, Copy, Debug, PartialEq)]
struct Event { cycle: u64, thread_id: u32, guid: u64 }

fn main() {
    let all_events: Mutex<Vec<Event>> = Mutex::new(Vec::new());
    let handles: Vec<_> = (0..4u32).map(|tid| {
        let all = &all_events;
        thread::spawn(move || {
            // 模拟 cycle(不真调 rdtsc,用 thread_id * 1000 + i)
            for i in 0..1000u64 {
                let cycle = (tid as u64) * 100_000 + i;  // 各线程不同 cycle 区间,模拟同步
                all.lock().unwrap().push(Event { cycle, thread_id: tid, guid: tid * 100 + i });
            }
        })
    }).collect();
    for h in handles { h.join().unwrap(); }

    let mut events = all_events.into_inner().unwrap();
    println!("before sort: {:?}", &events[0..5]);

    events.sort_unstable_by_key(|e| e.cycle);

    // 验证严格递增
    for i in 1..events.len() {
        assert!(events[i-1].cycle <= events[i].cycle, "not sorted at {}", i);
    }
    println!("sorted OK, {} events, range {}..={}",
        events.len(), events.first().unwrap().cycle, events.last().unwrap().cycle);
}
```

**注意**:`all = &all_events` 在闭包里要 'static lifetime。教学版用 static 替代:

```rust
use std::sync::LazyLock;
static ALL: LazyLock<Mutex<Vec<Event>>> = LazyLock::new(|| Mutex::new(Vec::new()));
```

### Lv3 · 迁移设计

**题**:如果 TSC 不同步(老 CPU / VM),怎么补救?**提示**:用 frame_begin event 作为"逻辑时间锚点",所有 event 的相对时间从最近的 frame_begin 算。

**额外提示**:
- 每个 event 记 `frame_index` + `cycle_in_frame`
- frame_index 由主线程每帧 +1,广播给工作线程
- cycle_in_frame 是相对 frame_begin 的 rdtsc 差(每线程独立,不会跨核冲突)
- 排序时按 (frame_index, cycle_in_frame) 字典序
- 这样即便 TSC 不同步,每帧内的相对时间正确
- **进阶**:工作线程在 frame_begin 时 sync 一次(读主线程的 rdtsc),之后用差值

#include <stdio.h>
#include <pthread.h>

static uint64_t rdtsc() {
    unsigned a, d; asm volatile("rdtsc" : "=a"(a), "=d"(d));
    return ((uint64_t)d << 32) | a;
}
void* worker(void* arg) {
    *(uint64_t*)arg = rdtsc();
    return NULL;
}
int main() {
    uint64_t t[4] = {0};
    pthread_t th[4];
    for (int i = 0; i < 4; i++) pthread_create(&th[i], NULL, worker, &t[i]);
    for (int i = 0; i < 4; i++) pthread_join(th[i], NULL);
    for (int i = 0; i < 4; i++) printf("core %d: %" PRIu64 "\n", i, t[i]);
    return 0;
}
