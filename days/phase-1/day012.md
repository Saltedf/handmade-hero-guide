## Q1:谁 owns `GameMemory`?

**问题**:Day 11 我说平台层分配 `GameMemory`,游戏代码修改它。但 Rust 所有权规则下,谁 should own?

**原理**:**唯一拥有者原则**——一块内存只能有一个 owner。但允许临时借用(`&mut`)。

具体到 `GameMemory`:

```rust
// 平台层(App struct)
struct App {
    memory: GameMemory,   // 平台拥有
    game: MyGame,
}

// 调用游戏时,临时借用
fn update(&mut self) {
    let mem = &mut self.memory;       // 借用
    self.game.update(mem, &input);    // 把借用传给 game
    // 借用结束
}
```

这里**编译期借用检查**保证:游戏在用 memory 时,平台不能同时改它。安全。

**坑**:**热重载**时,平台层换 game 函数,但 memory 不能动(否则游戏状态丢失)。所以:

- memory 是**平台层的字段**,跨热重载保留
- game 是**临时函数调用**,每次重新拿函数指针

这是 Casey `BITMAPINFO BitmapInfo` 全局变量 + 重新 LoadLibrary 的设计本质。

**答案**:平台层 owns `GameMemory`,通过 `&mut` 借用给游戏代码每次调用。

## Q2:cdylib 里 `String` 跨边界安全吗?

**问题**:我的 game 函数返回 `String`,平台层用,会不会内存崩?

**原理**:**Rust 的 String 内部布局依赖 Rust allocator**。跨 cdylib 边界(尤其不同 rustc 版本 / 不同 allocator),可能不一致。

具体:

```rust
// game crate(.so)
#[no_mangle]
pub extern "C" fn game_get_name() -> String {
    "MyGame".to_string()  // 用 Rust allocator 分配
}

// platform crate(.exe)
let name: String = game_get_name();  // 平台层把它当 String
drop(name);  // 用平台的 Rust allocator 释放!
// ↑↑ 错位释放,可能崩
```

问题:

- 同 rustc 编译 + 同 allocator:碰巧工作
- 不同 allocator:崩(jemalloc vs system malloc)
- 不同 rustc 版本:String 布局可能变(`{ptr, len, capacity}` vs 其他)

**正确做法**:**FFI 边界只用 C 类型**。

```rust
// C 兼容:char* 和长度,用 Rust 分配,提供 destroy 函数
#[no_mangle]
pub extern "C" fn game_get_name() -> *mut std::os::raw::c_char {
    let s = std::ffi::CString::new("MyGame").unwrap();
    s.into_raw()  // 放弃所有权,返回 *mut c_char
}

#[no_mangle]
pub extern "C" fn game_destroy_string(ptr: *mut std::os::raw::c_char) {
    unsafe {
        // 用同一个 crate 的 CString 回收
        let _ = std::ffi::CString::from_raw(ptr);
    }
}
```

平台层:

```rust
let ptr = game_get_name();
let name = unsafe { std::ffi::CStr::from_ptr(ptr) };
println!("{:?}", name);
game_destroy_string(ptr);  // 必须由 game crate 释放!
```

**经验法则**:**谁分配,谁释放**。跨 cdylib 时永远让分配方提供 destroy 函数。

**答案**:不安全。FFI 边界用 `*mut c_char` + 配套 destroy 函数,或干脆传 `&'static str`(字符串字面量,全局存储,无释放问题)。

## Q3:能不能多窗口?多线程每窗口一个游戏循环?

**问题**:我做开发工具,想要主窗口跑游戏,辅助窗口显示调试。能行吗?

**原理**:winit 支持多窗口,但 **winit 的 `EventLoop` 必须在主线程**(这是 macOS / Wayland 限制)。所以**多窗口可以,但循环单线程**。

```rust
struct App {
    main_window: Option<Window>,
    debug_window: Option<Window>,
    main_surface: Option<Surface>,
    debug_surface: Option<Surface>,
}

fn window_event(&mut self, _, window_id, event) {
    if window_id == self.main_window.as_ref().unwrap().id() {
        // 处理主窗口
    } else if window_id == self.debug_window.as_ref().unwrap().id() {
        // 处理调试窗口
    }
}
```

**多线程**(每个窗口一个线程跑游戏循环):**不可行**(winit 限制)。如果想"游戏循环在另一个线程,主线程只管窗口",Casey 风格用消息传递。

商业游戏引擎如 Bevy 用多线程,但通过 ECS 调度,不是简单"每窗口一线程"。

**答案**:多窗口可以(单 EventLoop),多线程游戏循环不行(winit 限制)。Phase 1 单线程足够。

## Q4:`extern "C"` 函数签名能用 Rust 类型吗?

**问题**:`extern "C" fn game_update(mem: &mut GameMemory)`,这里 GameMemory 是 Rust struct,行吗?

**原理**:**`extern "C"` 只保证 ABI 调用约定**(参数怎么传寄存器 / 栈),**不保证类型布局**。

如果 GameMemory 是 Rust struct:

- `#[repr(C)]`:固定布局,跨编译器一致(安全)
- 默认 `#[repr(Rust)]`:编译器自由布局(不安全跨边界)

```rust
// 安全
#[repr(C)]
pub struct GameMemory {
    pub permanent: *mut u8,
    pub permanent_size: usize,
    pub transient: *mut u8,
    pub transient_size: usize,
}

#[no_mangle]
pub extern "C" fn game_update(mem: *mut GameMemory) {
    // ...
}

// 不安全(默认 repr(Rust))
pub struct GameMemory {  // ← 没 #[repr(C)]
    a: u32,
    b: u8,
}
// 不同 rustc 版本可能字段顺序不同
```

**答案**:FFI 边界的 struct 必须 `#[repr(C)]`。函数参数优先用原始指针 `*mut T` / `*const T`,不用引用(引用带 lifetime,FFI 不识别)。

## Q5:softbuffer 的 `buffer_mut()` 返回的 slice 生命周期多长?

**问题**:

```rust
let mut buffer = surface.buffer_mut()?;
buffer[0] = ...;
buffer.present()?;
// buffer 在这里 drop。slice 还能用吗?
```

**原理**:`Surface::buffer_mut` 借用 `&mut self`,返回 `Buffer<'_>`,这是个**带 lifetime 的 owned 类型**。`present()` 消耗 self(`self.present()` 内部签 `fn present(self)`),所以 present 之后 buffer 不能再写。

```rust
let mut buffer = surface.buffer_mut()?;
// buffer: Buffer<'_>,借用 surface

// 写
for p in buffer.iter_mut() { *p = 0; }

// 必须先 present
buffer.present()?;  // buffer 被消耗,内部提交到 surface

// buffer 现在不能用了
// buffer[0] = 1;  // 编译错:buffer 已 moved
```

**陷阱**:如果你缓存了 buffer 引用:

```rust
let buffer = surface.buffer_mut()?;
let slice: &mut [u32] = &mut buffer;  // 借用 buffer
buffer.present()?;  // 编译错:buffer 被 &mut 借了
```

Rust 借用检查帮你抓这个 bug。**先 present,再丢 buffer**。

**答案**:Buffer 在 `present()` 后消耗。同一时刻只有一个 Buffer 活跃(`buffer_mut()` 借用 surface)。

## Q6:winit 的 `Window` 不 `Send`,cpal 的 `Stream` Send,为什么?

**问题**:这两个都是 GUI / 系统资源,为什么 Send 行为不同?

**原理**:**Send 和操作系统线程模型有关**。

- **winit Window**:在 macOS 上,所有窗口操作必须在主线程(NSWindow 限制)。所以 Rust 标记 Window 为 `!Send`(不能从主线程移到其他线程)。
- **cpal Stream**:内部用 ALSA / WASAPI / CoreAudio,这些 API 线程独立(每个 stream 可以在任何线程)。cpal 标记 `Stream: Send`(可以跨线程)。

Rust 的 `Send` / `!Send` 是**类型设计决策**,反映底层 API 约束。当你看到一个类型 `!Send`,理解为"它有线程约束,使用要小心"。

```rust
// 编译错:Window 不 Send
let window = Arc::new(window);
std::thread::spawn(move || {
    println!("{:?}", window);  // error: Window 不 Send
});

// 编译过:Stream Send
let stream = Arc::new(stream);
std::thread::spawn(move || {
    println!("{:?}", stream);  // ok
});
```

**答案**:平台约束。`Send` 是 Rust 类型系统强制线程安全的方式。

## Q7:`Arc<Mutex<T>>` vs `Arc<RwLock<T>>` 怎么选?

**问题**:多线程共享数据,Arc<Mutex> 和 Arc<RwLock> 哪个好?

**原理**:

- **Mutex<T>**:同一时刻**一个线程**能访问(读 / 写都互斥)。简单,但读多写少场景浪费。
- **RwLock<T>**:多个线程可**同时读**,但**写独占**。读多场景更快。

游戏场景:

- 输入状态(每帧读多,事件触发时写少):RwLock
- 游戏状态(主线程写,其他线程读):RwLock
- 计数器(频繁写):Mutex 或 Atomic

**坑**:`RwLock` 在 Linux 用 pthread(可能不公平,写饥饿)或 `parking_lot::RwLock`(更公平)。std `RwLock` 实现取决于平台。

**答案**:读多写少用 `RwLock`,写多用 `Mutex`。极高性能场景用 lock-free(atomic / crossbeam)。

## Q9:我卡在 X,怎么排查?

**问题**:开发过程会卡,常见排查思路?

**原理**:**分层排查**。从最底层(硬件 / OS)往最上层(你的代码)逐层检查。

排查 checklist:

1. **硬件**:GPU / 声卡 / 输入设备 ls / dmesg 看得到吗?
2. **驱动**:linux 内核加载了吗?(`lsmod | grep i915`)
3. **库**:依赖库装了吗?(`ldd binary` 看缺啥)
4. **服务**:音频 / 显示服务器跑了吗?(`systemctl --user status pipewire`)
5. **API 调用**:你的代码真的调了吗?(加 println 或 strace)
6. **数据**:输入数据正确吗?(打印 input 状态)
7. **逻辑**:算法对吗?(单步调试 gdb)

**典型 bug 排查工具**:

| 工具 | 用途 |
|---|---|
| `println!` / `dbg!` | 最简单,看变量值 |
| `gdb` | 单步调试,断点 |
| `strace -f` | 看系统调用 |
| `ltrace` | 看库调用 |
| `valgrind` | 内存泄漏 / 越界 |
| `perf stat / record` | 性能瓶颈 |
| `RUST_LOG=debug` | tracing 输出 |
| `cargo asm` | 看汇编(高级) |

**答案**:分层排查,从底层往上。每个工具用 1-2 次,不要堆所有工具。

## 5 · 对照与变奏

### Rust FFI 经验法则汇总

1. FFI 边界 struct 必须 `#[repr(C)]`
2. 用原始指针 `*mut T` / `*const T`,不用引用
3. 字符串用 `CString` / `CStr`,配套 destroy 函数
4. `Vec<T>` 跨边界:用 `into_raw_parts` / `from_raw_parts`,谁分配谁释放
5. 不跨边界传 trait object(`dyn Trait` 的 vtable 不稳定)
6. `Result<T, E>` 跨边界:转 C 风格 error code

### 常见 panic 排查

| panic 信息 | 原因 |
|---|---|
| `unwrap() on None` | Option 是 None,通常初始化顺序错 |
| `unwrap() on Err` | Result 是 Err,看错误信息 |
| `index out of bounds` | 数组越界,检查 size |
| `called Option::unwrap() on a None value` | 字段没初始化 |
| `panic in extern function` | FFI 调用崩,检查参数 |
| `BorrowMutError` | 同一时刻两个 &mut,检查所有权 |
| `capacity overflow` | Vec resize 时算错 |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:你看到 winit 文档说 `Window: !Send`。这具体意味着什么?给出 2 个会触发编译错误的代码片段。

**参考解答**:

`!Send` 意味着 `Window` **不能在线程间转移所有权**。即不能从线程 A move 到线程 B。

代码 1:把 Window move 到另一个线程

```rust
let window = event_loop.create_window(attrs)?;
std::thread::spawn(move || {
    println!("{}", window.inner_size());  // ← 编译错
});
// error: `Window` cannot be sent between threads safely
```

代码 2:把 Window 包在 `Arc` 跨线程共享

```rust
let window = Arc::new(event_loop.create_window(attrs)?);
let w2 = window.clone();
std::thread::spawn(move || {
    println!("{:?}", w2);  // ← 编译错
});
// error: `Arc<Window>` cannot be sent between threads
```

**为什么这样设计?** 因为 macOS 上 NSWindow 必须主线程访问,Rust 类型系统强制跨平台一致(在 Linux 上 Window 实际可以 Send,但 winit 为了一致性禁了)。

```
[pid 12345] write(2, "window_event: WindowEvent::CloseRequested\n", 41) = 41
根本原因:WindowProc 收到第一次 CloseRequested(创建窗口时系统发的)
        就 std::process::exit(0) 了
修复:在 close 处理加状态检查,只在用户主动按 X 时退
```

### Lv3 · 迁移设计

**题**:你卡在"resize 后画面黑屏"。设计一个系统化排查方案,逐项验证:

- softbuffer 的 resize 调了吗?
- buffer_mut 返回的 slice 长度是新尺寸吗?
- 你写的像素位置错了吗?
- present 调了吗?

写出排查代码(每个检查加 println 或 assert)。

**提示**:

```rust
// 检查 1
println!("resize called: {}x{}", w, h);
assert!(surface.resize(...).is_ok());

// 检查 2
let buf = surface.buffer_mut().unwrap();
println!("buf len: {}, expected: {}", buf.len(), (w * h) as usize);
assert_eq!(buf.len(), (w * h) as usize);

// 检查 3
// 你写的像素:
for y in 0..h { for x in 0..w {
    buf[(y * w + x) as usize] = compute(x, y);
}}
println!("wrote {} pixels", w * h);

// 检查 4
println!("before present");
buf.present().unwrap();
println!("after present");
```

每一步打印,找出哪一步失败。

### Rust 调试配置

```bash
# 1. 装 gdb + rust-gdb(集成 Rust pretty printer)
```

### 性能 profiling 模板

```bash
# 1. perf record(采 30 秒数据)
sudo perf record -F 99 -g -- ./target/release/handmade-hero &
sleep 30
sudo killall -INT perf  # 或 Ctrl-C 程序

# 2. 看 top 函数
sudo perf report --stdio | head -50

# 3. 生成火焰图(装 flamegraph)
cargo install flamegraph
sudo flamegraph -o /tmp/flame.svg -- ./target/release/handmade-hero
# 浏览器打开 /tmp/flame.svg

# 4. 看具体函数 CPU 时间
sudo perf stat -e cycles,instructions,cache-misses,branch-misses \
    ./target/release/handmade-hero
```

### Troubleshooting

- **`gdb: symbol lookup error`** — 装 `rust-gdb`(带 Rust 符号)
- **flamegraph 看不到函数名** — release 用 `debug = true`,见 Day 1 配置
- **`cargo test` 慢** — 用 `cargo test --release`(测试本身快时)
- **`valgrind: command not found`** — `sudo pacman -S valgrind`
