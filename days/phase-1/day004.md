
# Day 004 · 让后缓冲动起来:主循环首次跑通

> Day 3 我们画了一片**纯绿**,但它是静态的——一帧画完,永远不变。今天让它**动**起来:每一帧根据时间画不同的颜色,窗口里出现**横向渐变 + 滚动**。这一天的核心是把"游戏主循环"(main loop / game loop)真正跑通——后面 663 天每天都是在这个循环里加东西。

## 0 · 为什么要有这一天

到目前为止你的程序只做两件事:打开窗口、画一个静态颜色。这不像"游戏",像一个静态图片查看器。

游戏的核心是**变化**——每一帧画面都不一样,人眼看到的就是"动"。具体怎么变?

- 位置变:小人往右走 → x 每帧 +1
- 颜色变:血量低 → 屏幕闪红
- 时间变:夜深 → 整体变暗
- 视角变:相机跟着玩家

所有变化都遵循一个公式:

```
每一帧:
    dt = 这一帧耗时(秒)
    state = update(state, dt, input)   // 更新游戏状态
    render(state)                       // 把状态画出来
```

这个循环叫**游戏主循环**(game loop / main loop)。它是所有游戏、所有模拟器、所有动画程序的核心结构。

Casey Day 4 第一次跑通这个循环——他给后缓冲加了一个**时间相关的 X 偏移**,让屏幕的颜色梯度每帧偏移,看起来颜色在水平方向滚动。我们做一样的事,但用 Rust 的 `std::time::Instant` 替代 Win32 的 `QueryPerformanceCounter`。

**心理锚点**:读完今天,你能:

- 写出一个标准游戏主循环(`while !done { update; render; }`)
- 用 `std::time::Instant::now()` 测时间,算 `dt`
- 用循环索引写后缓冲,画一个横向渐变(每个 X 像素颜色不同)
- 解释 `ControlFlow::Poll` 和 `ControlFlow::Wait` 的差别,知道游戏必须用前者
- 用 `cargo run --release` 看出"debug 60 FPS, release 1000+ FPS"的差别

## 1 · Casey 今天做了什么

Casey Day 4 的核心动作:

1. 在 `WinMain` 加一个 `Running` 全局布尔,初始化 `true`
2. 把消息循环改成 `while (Running) { ... }`:每次循环先 `PeekMessage`(非阻塞取消息,有就处理,没有就跳过),然后**自己**调 `Win32UpdateWindow` 画一帧
3. 在 `Win32UpdateWindow` 里,**不再是静态颜色**,而是按 X 坐标算颜色:`Blue = X / Width * 255` 的简化版,屏幕从左到右是黑→蓝渐变
4. 加一个时间变量 `XOffset`,每帧 `XOffset += 1`,渐变的"起点"挪动 → 看起来颜色在水平滚动
5. 跑起来,看到屏幕从黑到蓝的渐变,而且每秒都在滚动

**关键转变**:之前 `GetMessage` 是**阻塞**的——没消息就停在那等。游戏不能这样(没用户输入画面就冻住)。换成 `PeekMessage`(非阻塞)后,**没消息也不停,程序主动去画**。

这是 Win32 GUI 程序和 Win32 游戏的根本区别。winit 这边对应:`ControlFlow::Poll`(不停调用回调)vs `ControlFlow::Wait`(等事件才调)。

## 2 · 心智模型

### 类比:游戏主循环是"心跳起搏器"

你的心脏每秒跳 60-100 次,每次泵一份血到全身。如果心跳停了,身体就死。**游戏主循环就是程序的心跳**:

- 每次循环 = 一次心跳 = 一帧
- 60 FPS = 60 次/秒 = 心跳 60
- 每次心跳做两件事:**更新**(update,处理逻辑)+ **渲染**(render,画一帧)

```
┌────────────────────────────────┐
│  while !done {                  │
│      1. 读输入(键盘 / 鼠标)    │
│      2. update(state, dt)       │ ← 心跳:更新状态
│      3. render(state)           │ ← 心跳:画一帧
│      4. 计算下一帧的 dt         │
│  }                              │
└────────────────────────────────┘
```

**核心特征**:循环必须**足够快**,每帧 < 16.67ms(60 FPS)。如果某帧超过,人感觉卡顿。

### dt:帧时间

`dt`(delta time)= 这一帧相对上一帧的耗时,单位秒。

```rust
let now = Instant::now();
let dt = now.duration_since(last_time);
last_time = now;
let dt_secs = dt.as_secs_f32();   // 比如 0.0167 = 60 FPS
```

**为什么用 dt 而不是固定步长?** 因为帧率不固定(可能 60,可能 144,可能突然掉到 30)。如果你写"每帧 x += 1",60 FPS 时 60 像素/秒,144 FPS 时 144 像素/秒——同样的代码在不同机器上速度不一样。**正确做法**:`x += speed * dt`,speed 是"像素/秒",这样不管 FPS 多少,小人速度恒定。

```
speed = 100 像素/秒
60 FPS  : dt = 1/60 = 0.0167,每帧 x += 100 * 0.0167 = 1.67,60 帧 = 100 ✓
144 FPS : dt = 1/144 = 0.00694,每帧 x += 0.694,144 帧 = 100 ✓
```

### 渐变算法

Day 3 我们写 `for pixel in buffer { *pixel = 0x00FF00 }`,所有像素同色。今天我们要让**每个像素颜色不同**——具体规则:**X 越大,蓝分量越大**(从左到右黑→蓝渐变)。

```rust
let blue = (x as f32 / width as f32 * 255.0) as u32;
let pixel = blue;   // 只填蓝分量,R=G=0
```

如果 x=0,blue=0(黑);x=width,blue=255(纯蓝)。中间是渐变。

### 滚动动画

要让渐变"滚动",每帧把渐变的"起点"挪一下:

```rust
// 全局状态
let mut x_offset = 0.0;

// 每帧
x_offset += dt * 100.0;  // 每秒偏移 100 像素
let blue = ((x as f32 + x_offset) % width as f32 / width as f32 * 255.0) as u32;
```

`% width` 让 blue 在 0~width 循环——超出右边从左边重新开始,看起来就是颜色不停从右往左流动。

### ControlFlow:Poll vs Wait

winit 的 `set_control_flow`:

```rust
event_loop.set_control_flow(ControlFlow::Poll);     // 不停调用回调
event_loop.set_control_flow(ControlFlow::Wait);     // 等事件才调用
```

**Poll**(游戏必选):
- 没事件时,循环也立刻回调(`AboutToWait` 事件)
- CPU 100% 占用一个核,一直转
- 你能 60 FPS / 144 FPS 不停渲染

**Wait**(普通 GUI):
- 没事件时,线程 sleep,几乎不占 CPU
- 有事件才唤醒
- 适合"用户不操作就不用动"的程序(文本编辑器、设置面板)

游戏用 `Poll`,否则没输入时画面冻住。

### `request_redraw` 的作用

winit 是事件驱动架构,渲染入口是 `WindowEvent::RedrawRequested`。但 `request_redraw()` **不是直接渲染**,而是"标记窗口脏了,下次循环请给我 RedrawRequested 事件"。配合 Poll 模式,每帧都触发一次:

```
AboutToWait(每帧一次) → 你调 request_redraw → 下次循环触发 RedrawRequested → 你渲染
```

为什么不直接在 `AboutToWait` 里渲染?因为渲染可能涉及 resize、surface 状态变化,winit 希望你在 `RedrawRequested` 里渲染——保证状态一致。

### 完整流程图

```
┌─────────────────────────────────────────────┐
│  resumed                                    │
│    → 创建 window                            │
│    → 创建 softbuffer surface                │
│    → 初始化 last_time = Instant::now()      │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  set_control_flow(Poll)                     │ ← 一次性
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  AboutToWait (每帧一次)                     │
│    → 计算 dt                                │
│    → 更新 state(如 x_offset += dt * 100)   │
│    → window.request_redraw()                │ ← 触发渲染
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  RedrawRequested (每帧一次)                 │
│    → surface.buffer_mut()                   │
│    → 按 state 填像素                        │
│    → buffer.present()                       │
└─────────────────────────────────────────────┘
                    │
                    ▼
              循环回 AboutToWait
```

## 3 · 四域深入

### 3.1 · 🐧 Linux 系统编程视角

#### `QueryPerformanceCounter` vs `Instant`

Casey 用 Win32 `QueryPerformanceCounter`(QPC)获取高精度时间戳:

```c
LARGE_INTEGER freq, start, end;
QueryPerformanceFrequency(&freq);     // 频率(每秒多少 count)
QueryPerformanceCounter(&start);       // 当前 count
// ... 做事
QueryPerformanceCounter(&end);
double secs = (end.QuadPart - start.QuadPart) / (double)freq.QuadPart;
```

QPC 是 Windows 上**唯一**可信的高精度计时器(单调、不受系统时间调整影响、纳秒精度)。在 Linux 上对应:

```c
struct timespec ts;
clock_gettime(CLOCK_MONOTONIC, &ts);
// ts.tv_sec = 秒,ts.tv_nsec = 纳秒
```

`CLOCK_MONOTONIC` 是**单调时钟**——从某个未指定起点开始累加,**绝不回退**(即使 NTP 调时间)。C 语言用 `clock_gettime`,Rust 用 `Instant::now()`:

```rust
use std::time::Instant;
let start = Instant::now();
// ... 做事
let elapsed = start.elapsed();   // Duration
let secs = elapsed.as_secs_f32();
```

`Instant` 内部用 `clock_gettime(CLOCK_MONOTONIC)`(在 Linux 上)。`Duration` 是 `(secs: u64, nanos: u32)` 结构体,表达一段时间。

**为什么不用 `SystemTime`?**

```rust
use std::time::SystemTime;
let now = SystemTime::now();   // 日历时间(墙钟时间)
```

`SystemTime` 是"墙钟时间"(可以前后跳——NTP 调整、用户改时间)。它适合"现在几点"这种场景,**不适合游戏循环**(NTP 调时间导致 dt 突然变负或巨大,游戏崩)。

**RDTSC vs QPC vs clock_gettime**:

| 计时器 | 精度 | 速度 | 单调性 |
|---|---|---|---|
| RDTSC(x86 指令) | 纳秒 | 最快(几纳秒) | 不保证(老 CPU 不单调) |
| QPC(Win32) | 100ns | 中等(几十纳秒) | 单调 |
| clock_gettime(MONOTONIC) | 纳秒 | 中等 | 单调 |
| gettimeofday(过时) | 微秒 | 快 | 墙钟,可能跳 |

Casey 在 Day 10 详细对比 QPC 和 RDTSC,讨论精度和性能。今天我们用 `Instant` 就够。

### 3.2 · 🦀 Rust 生态视角

#### `Duration` 和浮点转换

```rust
let dt: Duration = start.elapsed();
let secs_f64 = dt.as_secs_f64();        // 1.67e-2
let secs_f32 = dt.as_secs_f32();        // 1.67e-2(精度略低)
let millis = dt.as_millis();            // 16(u128)
let nanos = dt.as_nanos();              // 16700000(u128)
```

游戏一般用 `f32` 算物理(`f64` 慢一点,精度游戏用不到)。`as_secs_f32()` 直接给你 `f32`。

#### `f32` 转 `u32` 像素值

```rust
let ratio: f32 = x as f32 / width as f32;     // 0.0 ~ 1.0
let blue_f: f32 = ratio * 255.0;               // 0.0 ~ 255.0
let blue_u8: u8 = blue_f as u8;                // 截断(不四舍五入)
let blue_u32: u32 = blue_u8 as u32;
let pixel: u32 = blue_u32;                     // 0x000000XX
```

`as u8` 是**截断**(truncate)——浮点小数部分直接丢,2.9 变成 2。如果你要四舍五入,用 `.round() as u8`。

注意:`x as f32 / width as f32` 当 width=0 时除零,得 `NaN` 或 `inf`。`NaN as u8 = 0`,`inf as u8 = 255`(饱和)。最好显式判断 width > 0。

#### 性能:`for pixel in buffer.iter_mut()` 是 SIMD-friendly

```rust
for pixel in buffer.iter_mut() {
    *pixel = ...;
}
```

Rust 编译器在 release 模式会把这种"对每个元素做相同操作"的循环**自动向量化**(auto-vectorize)成 SIMD 指令(SSE / AVX)。一条指令处理 4-16 个像素,大幅加速。

怎么验证?

```bash
# 编 release
cargo build --release

# 反汇编看有没有 SIMD 指令
objdump -d target/release/handmade-hero | grep -E "movdqa|movups|padd|pmul" | head
# 看到这些就说明 SIMD 生效了
```

Day 112+ 我们手写 SIMD。今天编译器帮你做。

#### `mut self` 的所有权

```rust
impl ApplicationHandler for App {
    fn about_to_wait(&mut self, _event_loop: &ActiveEventLoop) {
        // 这里 &mut self 借用了 App,可以改字段
        self.x_offset += 0.1;
        // ...
    }
}
```

`&mut self` 是"独占可变借用"。winit 调用这个方法时,App 被 borrow,其他线程不能同时改它。这是 Rust 借用规则——保证单线程代码无数据竞争。

### 3.3 · 🎮 游戏编程视角

#### 固定时间步 vs 可变时间步

我们今天用**可变时间步**(variable timestep):每帧的 dt 不同,update 用真实 dt。简单但有坑:

- 某帧卡了(如系统调度),dt 突然很大(50ms),物理积分"爆炸"——小人穿墙、子弹乱飞
- 浮点精度:大量小 dt 累加,delta drift

**固定时间步**(fixed timestep):update 总是用固定 dt(如 1/60),无论真实帧率多少:

```
accumulator += real_dt;
while accumulator >= FIXED_DT {
    update(FIXED_DT);
    accumulator -= FIXED_DT;
}
render(state);
```

如果某帧慢,update 跑多次"追上";如果某帧快,update 跳过(下次再追)。这样物理永远稳定。

Casey 早期用可变时间步,后期(Day 100+)切固定。Phase 1 我们简单起见用可变,Day 18 详细讨论。

#### 主循环的位置:在 winit 回调里,还是独立线程?

两个选择:

1. **在 winit 回调里**(`about_to_wait`):简单,但和事件循环耦合。winit 卡了游戏也卡。
2. **独立线程**:游戏循环在另一个 thread,winit 主线程只管窗口 + 输入,通过 channel 通信。复杂但解耦。

Casey 单线程,本教程也单线程(Day 100+ 才考虑多线程)。简单 > 复杂,除非有性能瓶颈。

#### 帧率限制

60 FPS = 每帧 16.67ms。但你的 update + render 可能只要 5ms,跑 200 FPS 浪费电、烧 GPU。

两种限制:

1. **vsync**:让 `present()` 阻塞到下一个 VBLANK。简单,但帧率被锁到屏幕刷新率。
2. **手动 sleep**:`std::thread::sleep(Duration::from_millis(16) - dt)`。

softbuffer 默认开 vsync(取决于平台),所以一般不用手动 sleep。

### 3.4 · 🎨 图形学视角

#### 帧率、刷新率、人眼

| 帧率(FPS) | 观感 |
|---|---|
| < 24 | 明显卡顿,看不下 |
| 24-30 | 电影标准,游戏略不流畅 |
| 30-60 | 普通游戏,可接受 |
| 60-144 | 流畅,电竞入门 |
| 144-240 | 电竞级,普通人看不出差 |

注意:**FPS 不是越高越好**。如果 dt 不稳定(60 FPS 然后 30 FPS 然后 60 FPS),比稳定 30 FPS 还卡。这就是为什么"固定时间步"重要。

#### 像素坐标系

winit 给我们的 `inner_size()` 是**物理像素**。后缓冲的尺寸应该匹配。

坐标系:**屏幕左上角是 (0,0),X 向右增,Y 向下增**。这是大多数 2D API 的约定(和数学的"Y 向上"反)。

```
(0,0) ────────────► X+
  │
  │
  │
  ▼
  Y+
```

后缓冲是**一维** `Vec<u32>`,所以 `buffer[y * width + x] = pixel`。Y 在外层(行优先 row-major)。

## 5 · 对照与变奏

### Win32 vs winit 主循环

| 概念 | Win32(C) | winit 0.30(Rust) |
|---|---|---|
| 取消息 | `PeekMessage`(非阻塞) | 自动,通过回调派发 |
| 主循环 | `while (Running) { PeekMessage; Update; Render; }` | `event_loop.run_app(&mut app)` |
| 空闲时 | 自己调 Update/Render | winit 调 `about_to_wait` |
| 渲染时机 | 自己决定 | `RedrawRequested` 事件 |
| 退出 | `Running = false` | `event_loop.exit()` |

Win32 主循环**显式**(代码看得到 while),winit **隐式**(藏在 `run_app` 内部)。教学上 Casey 的方式更直观,工程上 winit 的方式更安全(不可能忘记处理某类事件)。

### 不同领域的主循环

| 领域 | 主循环结构 | 频率 |
|---|---|---|
| 游戏 | `while !done { update; render; }` | 60-144 Hz |
| GUI | `wait_event; handle_event; repaint_if_dirty;` | 用户驱动(可能 0 Hz) |
| 服务器 | `for connection in listener.accept() { handle(connection); }` | 连接驱动 |
| 数据处理 | `for chunk in stream { process(chunk); }` | 数据驱动 |
| CLI 工具 | `parse_args; do_work; exit` | 一次性 |

游戏主循环的特殊性:**不管外部输入,自己定时**——这就是"实时"的含义。

### 历史演化

- **1970s**:文字游戏,无主循环,玩家输入触发一切
- **1980s**:街机游戏,主循环和屏幕刷新同步(60 Hz)
- **1990s**:PC 游戏,主循环和 CPU 速度相关(快 CPU 游戏跑太快——经典 bug)
- **2000s**:`dt` 普及,帧率无关
- **2010s**:固定时间步 + 插值成为商业标准
- **2020s**:多线程主循环(渲染线程 + 模拟线程)

Casey 选择单线程 + dt 的"老式"做法是为了教学透明度。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:游戏主循环里,为什么 dt 要 clamp(如 `dt = dt.min(0.1)`)?

**参考解答**:

`dt` 极大值时会出 bug:

1. **物理爆炸**:Euler 积分 `v += a * dt`,dt=1 时 v 跳到 100,小人瞬移穿墙
2. **累加器溢出**:某些状态(如冷却)用 dt 累加,大 dt 直接清零
3. **网络同步**:大 dt 让客户端"瞬移",服务端可能踢人
4. **NaN 传播**:某些除法 `x / dt`,dt 极大或极小都可能导致异常值

**常见原因**:

- 系统挂起(笔记本合上再打开)→ 真实 dt 几小时
- 调试器暂停 → 真实 dt 几秒
- 第一次启动 → `Instant::now() - last_time` 初始时差可能大

**clamp 上限**:60 FPS 的游戏通常 `dt.min(1.0/15.0)`(最低 15 FPS 视觉),避免大 dt 撕坏物理。

### Lv2 · 动手实践

**题**:在 Day 3 代码上加主循环,让窗口显示**横向蓝渐变**,每秒向右滚动。完成标准:`cargo run` 后窗口从左到右黑→蓝渐变,渐变以每秒约 100 像素的速度向右滚动(到边后从左重新出现)。

**参考解答**:

```rust
// src/main.rs
use raw_window_handle::HasWindowHandle;
use softbuffer::Surface;
use std::num::NonZeroU32;
use std::time::{Duration, Instant};
use winit::application::ApplicationHandler;
use winit::event::WindowEvent;
use winit::event_loop::{ActiveEventLoop, ControlFlow, EventLoop};
use winit::window::{Window, WindowId};

struct App {
    window: Option<Window>,
    surface: Option<Surface>,
    /// 上次帧时间(算 dt)
    last_time: Option<Instant>,
    /// 滚动偏移
    x_offset: f32,
}

impl ApplicationHandler for App {
    fn resumed(&mut self, event_loop: &ActiveEventLoop) {
        let attrs = Window::default_attributes()
            .with_title("Handmade Hero — Day 4")
            .with_inner_size(winit::dpi::LogicalSize::new(1280, 720));
        let window = event_loop.create_window(attrs).unwrap();

        // softbuffer 初始化
        let context = unsafe {
            softbuffer::Context::new(event_loop.display_handle().unwrap().clone())
        }.unwrap();
        let surface = unsafe {
            context.create_surface(window.window_handle().unwrap().unwrap().clone())
        }.unwrap();

        self.window = Some(window);
        self.surface = Some(surface);
        self.last_time = Some(Instant::now());

        // 关键:Poll 模式,不停跑
        event_loop.set_control_flow(ControlFlow::Poll);
    }

    fn window_event(
        &mut self,
        event_loop: &ActiveEventLoop,
        _id: WindowId,
        event: WindowEvent,
    ) {
        match event {
            WindowEvent::CloseRequested => event_loop.exit(),
            WindowEvent::RedrawRequested => {
                self.render();
            }
            WindowEvent::Resized(size) => {
                if let Some(surface) = &mut self.surface {
                    if size.width > 0 && size.height > 0 {
                        surface.resize(
                            NonZeroU32::new(size.width).unwrap(),
                            NonZeroU32::new(size.height).unwrap(),
                        ).unwrap();
                    }
                }
            }
            _ => ()
        }
    }

    fn about_to_wait(&mut self, event_loop: &ActiveEventLoop) {
        // 每帧调一次(因为 Poll 模式)
        let now = Instant::now();
        let dt = if let Some(last) = self.last_time {
            now.duration_since(last).as_secs_f32()
        } else {
            0.0
        };
        self.last_time = Some(now);

        // clamp dt(避免挂起后大 dt)
        let dt = dt.min(0.1);

        // 更新状态:每秒滚动 100 像素
        self.x_offset += dt * 100.0;

        // 请求重画
        if let Some(window) = &self.window {
            window.request_redraw();
        }
        // event_loop 这里没用到
        let _ = event_loop;
    }
}

impl App {
    fn render(&mut self) {
        let surface = self.surface.as_mut().unwrap();
        let window = self.window.as_ref().unwrap();
        let size = window.inner_size();
        let (w, h) = (size.width, size.height);
        if w == 0 || h == 0 { return; }

        // resize(以防 RedrawRequested 在 Resized 之前到)
        surface.resize(
            NonZeroU32::new(w).unwrap(),
            NonZeroU32::new(h).unwrap(),
        ).unwrap();

        let mut buffer = surface.buffer_mut().unwrap();

        // 填渐变 + 滚动
        let offset = self.x_offset;
        let w_f = w as f32;
        for y in 0..h {
            for x in 0..w {
                // (x + offset) mod w 算出"颜色相位",0~w 对应 0~255
                let phase = ((x as f32 + offset) % w_f) / w_f;
                let blue = (phase * 255.0) as u32;
                // 加一点红,看起来不那么单色
                let red = (((y as f32 / h as f32) * 255.0) as u32) / 2;
                let pixel = (red << 16) | blue;
                buffer[(y * w + x) as usize] = pixel;
            }
        }

        buffer.present().unwrap();
    }
}

fn main() {
    let event_loop = EventLoop::new().unwrap();
    let mut app = App {
        window: None,
        surface: None,
        last_time: None,
        x_offset: 0.0,
    };
    event_loop.run_app(&mut app).unwrap();
}
```

### Troubleshooting

- **窗口出现但没动**:检查 `set_control_flow(ControlFlow::Poll)` 是否在 resumed 里调;检查 `request_redraw()` 是否在 about_to_wait 里调
- **画面撕裂**:可能 vsync 没开,或在多线程渲染,暂时无解(后期再处理)
- **CPU 100%**:Poll 模式正常。如果嫌浪费电,可以 `ControlFlow::WaitUntil(Instant::now() + Duration::from_millis(15))`
- **dt 总是 0**:可能你的机器太快,`as_secs_f32()` 截断成 0。用 `as_secs_f64()` 或 `as_nanos()`
- **release 比 debug 没快多少**:可能是 IO 限制(画 4K 像素),不是 CPU。试小窗口
