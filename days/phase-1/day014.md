# Day 014 · 平台无关的游戏内存:GameMemory 与内存分区

> Day 011 设计了平台 / 游戏分离的接口,Day 012 应用到音频,Day 013 应用到输入。今天 Day 014 应用到**最底层的东西:内存本身**。Casey 把整块游戏内存交到游戏代码手里,让游戏自己决定怎么用。这个看似简单的"递一块内存"动作,是 Day 021 热重载的**物理前提**——状态如果不外置,热重载就只能是一场灾难。

## 0 · 为什么要有这一天

你想象这样一个场景:你正在写游戏代码,需要一个临时数组存这帧的所有可见 sprite。你写 `let sprites: Vec<Sprite> = Vec::new();`——`Vec` 在堆上分配内存,函数返回时 Rust 自动 `drop`,内存释放。一切干净。

可你跑 profiler,发现每帧花了 3 毫秒在 `malloc` / `free` 上。为什么?因为 `Vec::new()` → push → drop 这个循环每秒重复 60 次,每次都走通用分配器(glibc malloc 或 jemalloc)的慢路径:扫 free list、合并相邻块、维护元数据。游戏每帧分配几百个小对象,通用分配器累得气喘吁吁。

更糟糕的是**内存碎片**。每帧分配的尺寸不一(有的 sprite 数组 1KB,有的 100KB),通用分配器反复切割和合并,久而久之堆里全是"夹缝",即使总空闲内存够,也分配不出连续大块。游戏跑半小时,内存使用从 100MB 涨到 500MB,然后 OOM(Out of Memory)崩溃。

这两个问题——**慢**和**碎片**——是游戏开发必须解决的。解法是:**绕开通用分配器,自己管一块大内存**。

Casey 这集做的事情就是这个:让平台层在启动时**一次性**向 OS 申请一大块内存(比如 1GB),把这块内存的指针 + 大小交给游戏代码。游戏代码在这块内存里自己分配,自己管理,不再走 `malloc`。这块内存叫 **GameMemory**。

为什么这件事必须在 Day 014 解决?因为 Day 021 热重载要求**游戏状态不在游戏代码的全局变量里**——状态必须存在这块 GameMemory 里,由平台层持有,跨 DLL 重载保留。今天 Casey 把这个"状态外置"的理论落地为代码。

**心理锚点**:读完今天,你能:

- 解释为什么游戏不直接用 `Vec` / `Box`,而要自己管内存
- 写出一个最小的 `Arena` 分配器(push allocation,指针前移)
- 把 Arena 包装成 safe API,把 unsafe 限制在最小内核
- 解释 permanent / transient 内存分区的设计动机
- 知道 Casey 的设计如何映射到 Rust 的 `bumpalo` crate
- 看懂一段 C 代码里 `game_state->permanent_storage` 这种指针操作在 Rust 里怎么安全地写

## 1 · Casey 今天做了什么

Day 014 Casey 的具体动作:

1. 在 `handmade.h` 里**定义 `game_memory` 结构**:两个裸指针 + 两个 size,分别指向 permanent storage(永久)和 transient storage(临时)。
2. 在 Win32 平台层里**分配这块内存**:用 `VirtualAlloc`(Windows 的内存分配 API,等价于 Linux 的 `mmap`)申请一大块,把指针填进 `game_memory`。
3. 把 `game_memory` 通过 `GameUpdateAndRender(memory, ...)` 传给游戏代码。
4. 游戏代码里**用裸指针**把 memory cast 成自己想要的类型——`game_state *state = (game_state *)memory->permanent_storage;`。
5. 关键:游戏代码**不再用 malloc**,所有长期数据放 permanent,所有临时数据放 transient。

Casey 这集没写多少新功能,他做的更多是**架构改造**:把 Day 1-13 那些"测试时随手用 malloc 写的代码"全部迁移到 GameMemory 模型。这是 Phase 1 的最后一块架构拼图,之后 Day 15-25 都建立在这个基础上。

## 2 · 心智模型

### 类比:GameMemory 是你给游戏的"大仓库"

想象你开一家工厂。两种办原料的方式:

**方式 A**:每次需要原料,派人去市场买(等价于 `malloc`)。
- 每次买都要走采购流程(慢)
- 每次买都要记账(分配器元数据)
- 市场价格波动(碎片)
- 紧急时来不及(分配失败)

**方式 B**:租一个超大仓库,一次性把一年需要的原料全买回来,堆在仓库里。工厂内部用一个**白板**记录"用到哪了"。
- 想要原料?去仓库拿,白板上画一条线表示"用了多少"——快
- 不需要时不用归还,白板清零就当"全部归还"——简单
- 仓库大小固定,永远不超出——可控
- 唯一约束:仓库得足够大

Casey 的 GameMemory 就是方式 B。仓库分两区:

- **permanent**(永久区):长期数据——玩家位置、关卡进度、解锁状态。整个游戏生命周期都在,只有退出才释放。
- **transient**(临时区):单帧数据——这帧的渲染命令、临时计算结果。每帧开头 reset,自动回收。

### 严谨:GameMemory 结构

Casey 在 C 里的定义大致是:

```c
// Casey 原版(C)
typedef struct game_memory {
    bool is_initialized;
    
    uint64 permanent_storage_size;
    void *permanent_storage;        // 永久区
    
    uint64 transient_storage_size;
    void *transient_storage;        // 临时区
} game_memory;
```

翻译成 Rust(直接对应版本,带 unsafe):

```rust
// Rust 直译版(还没包装)
#[repr(C)]
pub struct GameMemory {
    pub is_initialized: bool,
    
    pub permanent_storage_size: u64,
    pub permanent_storage: *mut u8,     // 裸指针,unsafe
    
    pub transient_storage_size: u64,
    pub transient_storage: *mut u8,     // 裸指针,unsafe
}
```

字段解释:

- `is_initialized: bool`——游戏代码第一次被调用时检查这个标志,如果是 `false`,说明是首次运行,要做初始化(设玩家初始位置等)。设为 `true` 后,后续帧(以及热重载后的帧)看到 `true`,**跳过初始化**。这是热重载保留状态的关键。
- `permanent_storage_size: u64`——永久区字节数。Casey 用 64 位无符号,因为是 64 位指针时代的代码。
- `permanent_storage: *mut u8`——永久区起始地址。`*mut u8` 是 Rust 的"指向可变字节的裸指针",对应 C 的 `void *`。**创建**不需要 unsafe,**解引用**需要。
- `transient_storage_size` / `transient_storage`——临时区,同上。

`#[repr(C)]` 告诉 Rust 编译器:**按 C 的内存布局排列字段**。Rust 默认会重排字段以优化对齐(空隙填充),但跨 FFI 边界时必须用 C 布局,否则 Casey 的 C 代码和我们的 Rust 代码看到的字段偏移会不一致,引发未定义行为。

### 落地:平台层如何分配这块内存

Windows 上 Casey 用 `VirtualAlloc`(预留 + 提交两步)。Linux 上等价的是 `mmap`(memory map,把匿名内存映射到进程地址空间)。Rust 标准库不直接暴露 mmap,但有几种选择:

**选择 1:用 `Vec<u8>`**(最简单,适合初学)

```rust
let permanent: Vec<u8> = vec![0u8; 64 * 1024 * 1024]; // 64MB
let transient: Vec<u8> = vec![0u8; 256 * 1024 * 1024]; // 256MB
```

`Vec<u8>` 内部就是 `malloc` + 一块连续内存。Rust 帮你自动 drop。简单。

**选择 2:用 `Box<[u8]>`**(更明确"固定大小")

```rust
let permanent: Box<[u8]> = vec![0u8; 64 * 1024 * 1024].into_boxed_slice();
```

`Box<[u8]>` 是"固定大小的堆分配",没有 `Vec` 的"容量"概念(不能再 push)。语义上更贴合 GameMemory"固定大小"的需求。

**选择 3:用 `mmap` 直接**(教学价值高,看 Linux 如何工作)

```rust
use std::ptr::null_mut;

unsafe {
    let ptr = libc::mmap(
        null_mut(),
        64 * 1024 * 1024,
        libc::PROT_READ | libc::PROT_WRITE,
        libc::MAP_PRIVATE | libc::MAP_ANONYMOUS,
        -1,
        0,
    );
    if ptr == libc::MAP_FAILED {
        panic!("mmap failed");
    }
    // ptr 现在指向 64MB 可读写内存
}
```

需要 `libc` crate(`cargo add libc`)。`mmap` 的参数:`PROT_READ | PROT_PROT_WRITE` 表示可读写,`MAP_PRIVATE | MAP_ANONYMOUS` 表示"私有匿名映射"(不与文件关联,不与其他进程共享)。

为什么用 mmap 而不是 malloc?有几个理由:
- **lazy allocation**:mmap 只是"预留"虚拟地址空间,真正写入某页时才分配物理内存。64MB 的 mmap 实际只占用你用到的部分。
- **大块更高效**:malloc 大块(几 MB)内部也是调 mmap,malloc 小块才用 sbrk。直接 mmap 省一层。
- **对齐保证**:mmap 返回的地址总是页对齐(4KB 边界),适合 DMA、SIMD 等需要严格对齐的场景。

但**初学用 Box<[u8]> 就够了**——Casey 用 VirtualAlloc 主要是教学(展示 Win32 API),生产代码用 Vec / Box 同样可行。Phase 1 我们用 Box<[u8]>,Day 305+ 才深入 mmap。

### 包装:把裸内存变成可用 Arena

裸指针太底层,游戏代码每行都写 `unsafe { *(((state as *mut u8).add(offset)) as *mut Player) }` 会爆炸。我们需要**包装**:对外暴露 safe API,内部限制 unsafe。

最小 Arena(arena = "竞技场",指一大块自己管理的内存):

```rust
use std::cell::Cell;

pub struct Arena {
    buffer: Box<[u8]>,           // 拥有的内存
    offset: Cell<usize>,         // 当前分配到哪(用 Cell 实现内部可变性)
}

impl Arena {
    /// 创建一个 capacity 字节的 Arena,内容全零
    pub fn new(capacity: usize) -> Self {
        Self {
            buffer: vec![0u8; capacity].into_boxed_slice(),
            offset: Cell::new(0),
        }
    }
    
    /// 分配 n 个 T,返回可变切片
    /// 
    /// # 泛型
    /// - `T: 'static` 表示 T 不能含借用引用(Arena 比 T 活得久,这是约束)
    /// 
    /// # 对齐
    /// 自动对齐到 T 的对齐要求(比如 u64 对齐到 8 字节)
    pub fn alloc<T>(&self, n: usize) -> &mut [T] {
        let size = n.checked_mul(std::mem::size_of::<T>())
            .expect("size overflow");
        let align = std::mem::align_of::<T>();
        let start = align_up(self.offset.get(), align);
        let end = start.checked_add(size).expect("arena overflow");
        assert!(end <= self.buffer.len(), "arena out of memory");
        self.offset.set(end);
        
        // 这是 unsafe,因为我们从 u8 buffer cast 到 T
        // 安全性由 align_up 保证:T 对齐正确,size 不越界
        unsafe {
            std::slice::from_raw_parts_mut(
                self.buffer.as_ptr().add(start) as *mut T,
                n,
            )
        }
    }
    
    /// 重置 Arena,所有之前的分配失效
    pub fn reset(&self) {
        self.offset.set(0);
    }
    
    /// 当前已分配字节数(调试用)
    pub fn used(&self) -> usize {
        self.offset.get()
    }
}

/// 把 x 向上取整到 align 的倍数(align 必须是 2 的幂)
fn align_up(x: usize, align: usize) -> usize {
    debug_assert!(align.is_power_of_two());
    (x + align - 1) & !(align - 1)
}
```

逐行解释:

- `Cell<usize>`——Rust 的**内部可变性**原语。`&self` 看起来不可变,但 `Cell` 让我们能改内部值。`Cell` 用于 `Copy` 类型(这里 `usize` 是 `Copy`),通过 `get()` / `set()` 操作,运行时无开销。
- `align_up`——对齐计算。比如当前 offset 是 5,要分配 u64(对齐 8),`align_up(5, 8) = 8`,跳过 5-7 字节。算法是位运算:`(x + align - 1) & !(align - 1)`,比循环快。
- `checked_mul` / `checked_add`——返回 `Option`,溢出时返回 `None`。比直接 `*` 安全(直接 `*` 在 debug 模式 panic,release 模式 wrap)。
- `std::slice::from_raw_parts_mut(ptr, n)`——把裸指针 + 长度转成可变切片。这是 unsafe,因为编译器无法保证 ptr 有效、对齐、不别名。**我们的安全论证**:`self.buffer.as_ptr().add(start)` 一定在 buffer 范围内(由 `assert!(end <= len)` 保证),且 start 已对齐到 T。
- `'static` 约束——Arena 返回的引用生命周期任意长。Rust 默认会把返回的 `&mut [T]` 的生命周期绑到 `&self`,但我们用 `'static` 约束防止用户把含借用的类型放进 Arena(Arena 比引用活得久,放进去会悬垂)。

使用例子:

```rust
let arena = Arena::new(1024);
let players: &mut [Player] = arena.alloc::<Player>(10);  // 10 个 Player
players[0].x = 100.0;
// 不需要 drop players,Arena reset 时自动"释放"
arena.reset();
// 此后 players 引用逻辑上失效(虽然 Rust 编译器还认为它有效)
```

注意最后一行——`arena.reset()` 后 `players` 引用 Rust 依然认为有效,但**逻辑上**已经失效。这是 Arena 的固有缺陷:Rust 借用检查器不能自动跟踪 Arena 的 reset 时机。生产代码用 `bumpalo` crate(它通过 `bumpalo::Bump::alloc` 返回特定 lifetime 的引用,稍微好一点),或者把 Arena 用法限制在紧密的代码块里。

### 用 Arena 重构 GameMemory

现在 GameMemory 可以包装得更安全:

```rust
pub struct GameMemory {
    pub is_initialized: bool,
    pub permanent: Arena,     // 永久区
    pub transient: Arena,     // 临时区(每帧 reset)
}

impl GameMemory {
    pub fn new(permanent_size: usize, transient_size: usize) -> Self {
        Self {
            is_initialized: false,
            permanent: Arena::new(permanent_size),
            transient: Arena::new(transient_size),
        }
    }
    
    /// 每帧开始时调用
    pub fn begin_frame(&mut self) {
        self.transient.reset();
    }
}
```

游戏代码:

```rust
pub fn update_and_render(memory: &mut GameMemory, input: &GameInput, dt: f32) {
    // 永久状态(跨帧保留)
    let state: &mut GameState = if !memory.is_initialized {
        let s = memory.permanent.alloc::<GameState>(1);
        s[0] = GameState::default();
        memory.is_initialized = true;
        &mut s[0]
    } else {
        // 取第一个 GameState(就是上面 alloc 的)
        let s = memory.permanent.alloc::<GameState>(1);
        &mut s[0]
    };
    // ⚠️ 这里有个 bug:第二次进来又 alloc 了一次!正确做法见下文
}
```

哎,上面的代码有 bug:第二次进来 `alloc::<GameState>(1)` 又分配了新空间。正确做法是**只在 is_initialized == false 时 alloc**,之后帧用一个**保存的指针**。但 Arena 模式下,指针怎么保存?这是 Arena 的本质缺陷——它不"记住"你分配过什么。

实际工程有两种解法:

**解法 1:GameMemory 里直接放 GameState 字段**(最简单,放弃 Arena 灵活性)

```rust
pub struct GameMemory {
    pub is_initialized: bool,
    pub state: GameState,           // 直接是字段
    pub transient: Arena,           // 临时区还是 Arena
}
```

Casey 在 HH 后期也是这样:把游戏状态作为 `GameMemory` 的固定字段。Arena 仅用于 transient。这放弃了"permanent 自己分配"的灵活性,但避免 bug,且更类型安全。

**解法 2:offset 固定**(用 Arena 但记住 offset)

```rust
pub struct GameMemory {
    pub is_initialized: bool,
    pub permanent: Arena,
    pub transient: Arena,
    pub state_offset: usize,  // GameState 在 permanent 里的偏移
}
```

第一次 alloc 时记 offset,后续帧用 offset 直接定位。复杂但灵活。Casey 在 Day 305 memory arena 阶段走这条路。

Phase 1 我们用**解法 1**,简单清楚。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发圈"自己管内存"是普遍实践,但形式各异:

**形式 1:Frame Arena(帧 Arena)**——最常见。每帧 reset 一块 Arena,所有单帧分配走它。Unity 的 `NativeSlice`、Unreal 的 `FMemStack` 都是这个模式。Casey 的 transient storage 就是。

**形式 2:Stack Allocator(栈分配器)**——Arena + 嵌套 pop。允许"分配 A → 分配 B → 释放 B → 释放 A",像栈一样 LIFO。用于"一段渲染 pass 的临时分配"。Casey Day 305+ 用这个。

**形式 3:Pool Allocator(池分配器)**——固定大小对象的池。比如所有 Particle 是 64 字节,池里每格 64 字节,分配 / 释放 O(1)。适合大量同类对象(粒子、子弹)。

**形式 4:Slab Allocator(slab 分配器)**——Linux 内核用。每个对象类型一个池(inode 池、task_struct 池等)。更精细的 pool。

Casey 的选择是**最简单的 Frame Arena**(两块大 buffer + offset)。教学最优。生产游戏会组合多种(渲染用 frame arena,粒子用 pool,资产用 slab)。

游戏开发圈另一个相关概念是 **Data-Oriented Design**(DOD,数据导向设计)。Casey 是 DOD 的倡导者,核心思想:**先想数据怎么放,再写代码**。比如不要 `struct Player { pos, vel, hp, sprite }` 然后 `Vec<Player>`(AoS),而是 `positions: Vec<Vec2>, vels: Vec<Vec2>, hps: Vec<f32>`(SoA)。理由:CPU cache 友好、SIMD 友好。GameMemory 是 DOD 的物理基础——你有一大块内存,自己决定怎么布局。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内存相关 API 是必须懂的(后面 Day 305+ 深入):

| API | 作用 | Casey Win32 等价 |
|---|---|---|
| `brk` / `sbrk` | 调整 data segment 大小(老式) | (无对应) |
| `mmap` | 把文件或匿名内存映射到地址空间 | `VirtualAlloc` |
| `munmap` | 释放 mmap 的内存 | `VirtualFree` |
| `mprotect` | 改内存保护(读/写/执行) | `VirtualProtect` |
| `madvise` | 给内核"用法提示"(顺序读、不要 swap 等) | (无标准等价) |
| `posix_memalign` | 分配对齐内存 | `_aligned_malloc` |

Casey 用 VirtualAlloc 的核心理由:**reserve without commit**。Windows 上 VirtualAlloc 可以"预留" 1TB 虚拟地址空间但不分配物理内存,真正写入时才 commit。Linux 的 mmap 默认就是 lazy allocation——`mmap(1TB)` 立刻返回,写入某页时才分配那页 4KB。所以 Linux 不需要"两段式",一段 mmap 就够。

实战命令(在 Arch 上手玩):

```bash
# 看你进程的内存映射
cat /proc/$$/maps
# 输出形如:
# 5601c2c00000-5601c2c01000 r--p ... /bin/zsh
# 5601c2c01000-5601c2c02000 r-xp ...   ← 代码段
# ...
# 7f0123400000-7f0123800000 rw-p ...   ← 堆/mmap 区

# 看进程虚拟内存使用
ps -o vsz,rss,cmd -p $$
# VSZ = 虚拟大小(预留),RSS = 物理大小(实际使用)
# RSS 通常远小于 VSZ(lazy allocation)

# 强制释放 page cache(模拟低内存环境)
sudo sh -c 'echo 1 > /proc/sys/vm/drop_caches'

# 看一个 mmap 区域的物理页映射
sudo pmap $$ | head
```

`/proc/<pid>/maps` 是 Linux 的礼物——你能看到进程地址空间的每一块,它的权限、来源(文件 / 匿名)、大小。Windows 没有这个透明度,Casey 得用 VMMap 之类的工具。Linux 这点完胜。

### 3.3 · 🦀 Rust 生态视角

Rust 表达 Arena 有几个层次:

**层次 1:自己写(像我们上面那样)**

适合学习。理解每行原理。生产可用但费时。

**层次 2:用 `bumpalo` crate**

```toml
[dependencies]
bumpalo = "3.16"
```

```rust
use bumpalo::Bump;

let bump = Bump::new();
let players: &[mut Player] = bump.alloc_slice_fill_default(10);
// 不需要 free,bump 在 drop 时释放
```

bumpalo 的特点:
- 工业级,经过 fuzz testing
- API 类似我们的 Arena,但生命周期更精细(`alloc` 返回的引用生命周期绑到 `&Bump`,而非 `'static`)
- 支持 `bumpalo::collections::Vec` / `String`——在 Arena 里用 Vec
- Bevy 引擎就用 bumpalo

**层次 3:用 typed-arena**(同类型对象)

```rust
let arena = typed_arena::Arena::new();
let p1 = arena.alloc(Player::new());
let p2 = arena.alloc(Player::new());
// 类型固定为 Player,不能混搭
```

简单类型安全,但只能放一种类型。

**层次 4:`Vec<T>` + 索引**(替代指针)

不是真正的 Arena,而是 Rust 圈常用的"避免指针"模式:

```rust
struct World {
    players: Vec<Player>,    // 所有玩家
}

let id = world.players.len();
world.players.push(Player::new());
// 之后用 world.players[id] 访问
```

避免了 Arena 的 unsafe,代价是 `Vec` 增长时要 realloc(可能搬地址)。如果用 `slotmap` crate(代际索引),还能解决"Vec 删除元素后索引失效"问题。

**所有权和 Arena 的张力**:Rust 所有权模型假设每个对象有明确 owner,owner 死了对象死。Arena 打破这个——所有对象都"挂在 Arena 上",Arena 死了全部死。这种"批量生命周期"在 Rust 里只能用 unsafe(像我们写的)或 lifetime 约束(像 bumpalo)。**没有完美解法**,这是 Arena 的固有 trade-off。

### 3.4 · 🎨 (跨领域)状态外置与可序列化

GameMemory 还有意外红利:**存档 / 读档变得极其简单**。

如果游戏状态散落在 `static` 变量、`Vec` 在堆上各处、全局 HashMap 里——要存档你得把每个状态一个个序列化。

如果游戏状态全在 GameMemory 里——存档就是**把整个 permanent storage dump 到文件**。读档就是**把文件内容 memcpy 回 permanent**。两行代码!

```rust
fn save(memory: &GameMemory, path: &str) -> std::io::Result<()> {
    let bytes: &[u8] = unsafe {
        std::slice::from_raw_parts(
            memory.permanent_storage,
            memory.permanent_storage_size as usize,
        )
    };
    std::fs::write(path, bytes)
}

fn load(memory: &mut GameMemory, path: &str) -> std::io::Result<()> {
    let bytes = std::fs::read(path)?;
    assert_eq!(bytes.len(), memory.permanent_storage_size as usize);
    unsafe {
        std::ptr::copy_nonoverlapping(
            bytes.as_ptr(),
            memory.permanent_storage,
            bytes.len(),
        );
    }
    memory.is_initialized = true;
    Ok(())
}
```

这种"raw memory dump"存档格式叫 **binary blob**。优点:快(几 MB 写入几毫秒)、简单(两行代码)。缺点:跨平台不兼容(字节序、指针重定位、结构体 padding 差异)。Casey 用这个方法,HH 全剧没有专门的序列化代码。

商业游戏存档更复杂(版本控制、跨平台),但思路相同:**状态集中,序列化简单**。

## 5 · 对照与变奏

### 同一问题的不同语言表达

**C**:直接 `void *permanent; uint64 size;`,裸指针 + 大小,代码最短。

**C++**:可能用 `std::unique_ptr<uint8_t[]>` 或 `gsl::span<uint8_t>`,加 RAII 但仍是裸字节。

**Rust(我们)**:`Arena { buffer: Box<[u8]>, offset: Cell<usize> }`,内部 unsafe,外层 safe。

**Zig**:`var permanent: []align(@alignOf(GameState)) u8 = ...,` Zig 内置对齐语法,代码比 Rust 简洁但比 C 多类型信息。

**Go**:`permanent := make([]byte, size)`,Go 的 slice 自带"指针 + 长度 + 容量",但 Go 是 GC 语言,Arena 优势消失(还是被 GC 跟踪)。

不同语言在"自己管内存"这件事上能力不同:C / C++ / Rust / Zig 可以做,Arena 模式有效;Java / Python / Go 等 GC 语言做不了(对象都被 GC 跟踪,Arena 失去意义)。这是 Casey 选 C 而不是 GC 语言的核心理由之一。

### 历史演化:从 malloc 到 mmap 到 Arena

- **1960s Unix**:只有 sbrk,调整 data segment 末端。malloc/free 在用户态管理这个 segment。
- **1980s BSD**:引入 mmap,把"文件映射"和"匿名内存"统一。从此 malloc 内部用 mmap 处理大块。
- **1990s 游戏机时代**:游戏机内存小(几 MB)、CPU 慢,通用 malloc 太重。所有游戏引擎自己写分配器。
- **2000s**:dlmalloc / jemalloc 等高性能通用分配器出现,小项目用 malloc 也够快。
- **2010s**:多核 + 大数据,Arena 模式复兴(避免锁竞争)。Web 浏览器、数据库、游戏引擎都回到 Arena。
- **2020s**:Linux io_uring / persistent memory 等新硬件,Arena 设计继续演化。

Casey 教的是 1990s 游戏机时代的智慧,但今天依然适用——硬件变了,内存层级(cache → RAM → SSD)的核心 trade-off 没变。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 把内存分 permanent 和 transient。"transient 每帧重置"是什么意思?为什么这样设计?

进一步:为什么不能所有内存都"每帧重置"?那不是最方便吗(永远不用 free)?

**参考解答**:

"transient 每帧重置"——每帧开始时,transient 的 offset 归零,所有之前在 transient 里的数据被认为"失效"。新分配从 0 开始覆盖。

游戏代码不释放 transient 内存——它知道这帧结束后整块会重置,所以分配后用完即可,不用 free。

**为什么不能所有内存都每帧重置**:有些状态需要**跨帧保留**——玩家位置、关卡进度、解锁状态。如果每帧 reset,玩家移动后下一帧位置归零,游戏没法玩。

所以需要两区:
- permanent:跨帧长期数据(玩家进度)
- transient:单帧临时数据(渲染命令)

这是**生命周期分治**:不同生命周期的数据分开管理,各自用最合适的策略。

### Lv2 · 动手实践

**题**:在我们的 Rust 项目里实现一个 `Arena` 类型,功能包括:

1. `Arena::new(capacity: usize) -> Arena`——创建 capacity 字节的全零 Arena
2. `arena.alloc::<T>(n: usize) -> &mut [T]`——分配 n 个 T,自动对齐
3. `arena.reset()`——重置 offset 到 0
4. `arena.used() -> usize`——返回当前已分配字节数

写一个测试:
- 创建 1KB Arena
- 分配 100 个 u8,检查 used = 100
- 分配 10 个 u64(对齐 8),检查 used 跳到 104(对齐填充 4 字节)然后 +80 = 184
- reset,检查 used = 0

完成标准:`cargo test` 全部通过。

**参考解答**:

```rust
use std::cell::Cell;

pub struct Arena {
    buffer: Box<[u8]>,
    offset: Cell<usize>,
}

impl Arena {
    pub fn new(capacity: usize) -> Self {
        Self {
            buffer: vec![0u8; capacity].into_boxed_slice(),
            offset: Cell::new(0),
        }
    }
    
    pub fn alloc<T>(&self, n: usize) -> &mut [T] {
        let size = n * std::mem::size_of::<T>();
        let align = std::mem::align_of::<T>();
        let start = align_up(self.offset.get(), align);
        let end = start + size;
        assert!(end <= self.buffer.len(), "arena out of memory: \
            requested {} bytes at offset {}, capacity {}",
            size, start, self.buffer.len());
        self.offset.set(end);
        unsafe {
            std::slice::from_raw_parts_mut(
                self.buffer.as_ptr().add(start) as *mut T,
                n,
            )
        }
    }
    
    pub fn reset(&self) { self.offset.set(0); }
    pub fn used(&self) -> usize { self.offset.get() }
}

fn align_up(x: usize, align: usize) -> usize {
    (x + align - 1) & !(align - 1)
}

#[cfg(test)]
mod tests {
    use super::*;
    
    #[test]
    fn alloc_u8() {
        let a = Arena::new(1024);
        let xs: &mut [u8] = a.alloc::<u8>(100);
        xs[0] = 42;
        assert_eq!(a.used(), 100);
    }
    
    #[test]
    fn alloc_with_alignment() {
        let a = Arena::new(1024);
        let _bytes: &mut [u8] = a.alloc::<u8>(100);  // used = 100
        let _nums: &mut [u64] = a.alloc::<u64>(10);  // 对齐到 8,跳到 104,加 80 = 184
        assert_eq!(a.used(), 184);
    }
    
    #[test]
    fn reset_works() {
        let a = Arena::new(1024);
        let _ = a.alloc::<u8>(500);
        assert_eq!(a.used(), 500);
        a.reset();
        assert_eq!(a.used(), 0);
    }
    
    #[test]
    #[should_panic(expected = "arena out of memory")]
    fn overflow_panics() {
        let a = Arena::new(100);
        let _ = a.alloc::<u8>(200);  // 应该 panic
    }
}
```

每行解释:

- `vec![0u8; capacity].into_boxed_slice()`——先创建 Vec,再转成 Box<[u8]>(固定大小,无容量字段)。
- `assert!(end <= self.buffer.len(), ...)`——带格式化消息的断言。失败时 panic 并打印详细信息。
- `std::slice::from_raw_parts_mut`——构造可变切片。安全论证:`start` 已对齐,`end` 不超 buffer。
- `#[should_panic(expected = "...")]`——测试属性,期望测试函数 panic 且消息含特定子串。

## 8 · Rust / Arch 落地代码

### Rust:把 Arena 接入 GameMemory

把上面的 Arena 集成进我们 Day 11 设计的平台 / 游戏架构:

```rust
// src/memory.rs(项目里的新文件)
use std::cell::Cell;

pub struct Arena {
    buffer: Box<[u8]>,
    offset: Cell<usize>,
}

impl Arena {
    pub fn new(capacity: usize) -> Self {
        Self {
            buffer: vec![0u8; capacity].into_boxed_slice(),
            offset: Cell::new(0),
        }
    }
    pub fn alloc<T>(&self, n: usize) -> &mut [T] {
        let size = n * std::mem::size_of::<T>();
        let align = std::mem::align_of::<T>();
        let start = align_up(self.offset.get(), align);
        let end = start.checked_add(size).expect("overflow");
        assert!(end <= self.buffer.len(), "arena OOM");
        self.offset.set(end);
        unsafe {
            std::slice::from_raw_parts_mut(
                self.buffer.as_ptr().add(start) as *mut T, n)
        }
    }
    pub fn reset(&self) { self.offset.set(0); }
    pub fn used(&self) -> usize { self.offset.get() }
    pub fn capacity(&self) -> usize { self.buffer.len() }
}

fn align_up(x: usize, align: usize) -> usize {
    (x + align - 1) & !(align - 1)
}

// 游戏状态(只是一个示例,实际更复杂)
#[derive(Default)]
pub struct GameState {
    pub player_x: f32,
    pub player_y: f32,
    pub tick_count: u64,
}

// 完整 GameMemory
pub struct GameMemory {
    pub is_initialized: bool,
    pub state: GameState,        // 直接字段,简单
    pub transient: Arena,        // 临时 Arena
}

impl GameMemory {
    pub fn new() -> Self {
        Self {
            is_initialized: false,
            state: GameState::default(),
            transient: Arena::new(64 * 1024 * 1024),  // 64MB 临时区
        }
    }
    
    pub fn begin_frame(&mut self) {
        self.transient.reset();
    }
}

// 测试模块
#[cfg(test)]
mod tests {
    use super::*;
    
    #[test]
    fn smoke() {
        let mut mem = GameMemory::new();
        assert!(!mem.is_initialized);
        mem.is_initialized = true;
        mem.state.player_x = 100.0;
        
        // 模拟一帧
        mem.begin_frame();
        let _temp: &mut [u32] = mem.transient.alloc::<u32>(1000);
        assert_eq!(mem.transient.used(), 4000);
        
        // 模拟下一帧,transient 应该 reset
        mem.begin_frame();
        assert_eq!(mem.transient.used(), 0);
        
        // 但永久状态还在
        assert_eq!(mem.state.player_x, 100.0);
        assert!(mem.is_initialized);
    }
}
```
