
# Day 005 · 图形 API 选择:为什么是 softbuffer

> Casey 在 Day 5 做了一集"Windows 图形回顾",逐个比较 Win32 的几条渲染路径:`SetPixel`、`BitBlt`、`StretchDIBits`、`DirectDraw`、`Direct3D`、`OpenGL`,解释他为什么选 `StretchDIBits`(GDI 的"提交一块内存")。今天我们做 Linux + Rust 版的对比:从直接写 `/dev/fb0` 到 `softbuffer` 到 `wgpu`/`Vulkan`,看每条路怎么走、什么代价。理解了这些,你才能在选择渲染 API 时心里有数。

## 0 · 为什么要有这一天

你昨天用 softbuffer 把后缓冲画到窗口,看着没什么。但你有没有想过:

- 为什么不直接调 Linux 的"画像素"syscall?
- 为什么必须经过窗口系统(X11 / Wayland)和合成器?
- 我能不能绕过窗口系统,直接画屏幕?
- 为什么 Casey 不用 D3D / OpenGL,反而用 GDI?GDI 不是"老古董"吗?
- Rust 这边为什么不用 `wgpu`?那样不就 GPU 加速了吗?

这些问题的答案不是"哪个最好"那么简单,而是一组**取舍**(tradeoff):**简单 vs 性能 / 透明 vs 抽象 / CPU vs GPU / 跨平台 vs 平台最优**。

理解这些取舍的价值在于:**当你的项目演化到某个阶段,你能识别"现在该换渲染 API 了"**。Phase 1 我们用 softbuffer,因为简单。Phase 5 切到 OpenGL,因为要 GPU。Phase 6+ 可能切 Vulkan,因为要极致性能。**每一步切换都是工程师的主动决策,不是被动跟随**。

**心理锚点**:读完今天,你能:

- 列出 Linux 上至少 5 种渲染路径,各说一句"它适合什么场景"
- 解释为什么 Casey 用 GDI 的 `StretchDIBits`,而不是 D3D
- 解释为什么我们用 softbuffer,不是直接写 `/dev/fb0`
- 看懂"立即模式渲染" vs "保留模式渲染"
- 知道什么时候该从 softbuffer 升级到 wgpu

## 1 · Casey 今天做了什么

Casey Day 5 是个**讨论集**(没多少代码)。他在黑板/画板上列了 Windows 上画像素的所有方案:

1. **`SetPixel(hdc, x, y, color)`** — 一次画一个像素,慢到不能用于游戏
2. **`BitBlt(hdc_dst, ..., hdc_src, ...)`** — 位块传送,从一个 DC 拷到另一个,但你的内存不在 DC 里
3. **`StretchDIBits(hdc, ..., *bits, &bmi, ...)`** — 拷贝一段设备无关位图(DIB)到 DC,可拉伸
4. **`DirectDraw`**(1990s) — 旧版 Windows 加速 API,已被 D3D 取代
5. **`Direct3D` / `OpenGL`** — GPU 加速,3D 渲染
6. **`D3D9`/`D3D11`/`D3D12`** — D3D 三个主要版本,11 是大多数游戏用的,12 接近 Vulkan 的低开销

Casey 选 **`StretchDIBits`**(GDI 路径),理由:

- 透明:你能看到每一步,适合教学
- 灵活:你想做什么软件渲染(光栅化、光线追踪、shader 模拟)都可以,CPU 上完全控制
- 跨平台对应物:每个 OS 都有等价物(X11 XShm / Wayland wl_shm / macOS CGImage)
- 没有驱动黑盒:GPU 路径有几十个厂商驱动变体,bug 难复现
- 不学"图形 API 套路",学"渲染原理":GDI 让你直面像素,而不是"如何把 vertex buffer 喂给 D3D"

代价:

- CPU 渲染慢,GPU 路径快 100 倍以上
- 后期(Day 235+)Casey 也切到 OpenGL

Phase 1 我们全程 softbuffer,完全对应 Casey 的"软件渲染"哲学。

## 2 · 心智模型

### 类比:渲染 API 是"出口"

想象你的程序是一间工厂,生产"像素"(产品)。你要把产品运到顾客(屏幕)手里,有几条路:

| 路径 | 类比 | 速度 | 复杂度 |
|---|---|---|---|
| 直接写 framebuffer | 用私家车直接送 | 取决于路况 | 司机要熟悉路 |
| 窗口系统 API(X11 / Wayland) | 走快递(物流公司) | 中等 | 包装规范 |
| GDI / softbuffer | 标准化快递 | 中等 | 简单规范 |
| OpenGL / D3D | 高速货运专列 | 极快 | 要学复杂调度 |
| Vulkan / D3D12 | 自驾专列(自己当司机) | 最快 | 极其复杂 |

**核心洞察**:没有"最好的路",只有"适合你的路"。教学时选 GDI(透明),性能时选 GPU API(快)。

### "渲染"在计算机里的层次栈

```
┌────────────────────────────────────┐
│  你的代码(Casey 的 game logic)    │  ← 高级意图("画一个红色方块")
├────────────────────────────────────┤
│  渲染 API(softbuffer / OpenGL /…) │  ← 把意图转成硬件操作
├────────────────────────────────────┤
│  驱动(Mesa / NVIDIA / AMD)       │  ← 把 API 调用翻译成 GPU 指令
├────────────────────────────────────┤
│  内核 DRM / KMS                    │  ← 调度 GPU,把帧推到显示
├────────────────────────────────────┤
│  硬件(GPU + 显示器)              │  ← 物理像素亮起
└────────────────────────────────────┘
```

每一层都抽象下层。你的代码只需要顶层 API,不用懂驱动 / 内核 / 硬件。但**理解全栈让你诊断问题更准**——比如"渲染慢",是 CPU 计算慢、还是驱动慢、还是 GPU 慢?

### Linux 上的 5 条渲染路径(详细)

#### 路径 1:直接写 `/dev/fb0`(framebuffer 设备)

```bash
# Linux 有时提供 /dev/fb0,代表"屏幕 framebuffer"
ls -l /dev/fb0
# crw-rw---- 1 root video 29, 0 ... /dev/fb0

# 可以 mmap 它,直接写像素
```

```c
int fd = open("/dev/fb0", O_RDWR);
char *fb = mmap(NULL, w*h*4, PROT_WRITE, MAP_SHARED, fd, 0);
fb[y * w * 4 + x * 4 + 0] = blue;
fb[y * w * 4 + x * 4 + 1] = green;
fb[y * w * 4 + x * 4 + 2] = red;
```

**问题**:

- 现代 Wayland / X11 桌面**不让用户访问 fb0**(被合成器占用)
- 即使能访问,你和别的程序同时写,互相覆盖
- 没有 vsync,撕裂严重
- 不跨平台(Windows 没有 fb0)

**何时用**:嵌入式 Linux 树莓派 + 7 寸触屏(没桌面环境),自己写 GUI。教学价值高。游戏 / 桌面应用**完全不用**。

#### 路径 2:X11 XShmPutImage(共享内存)

```c
// X11 + MIT-SHM 扩展
XShmSegmentInfo shminfo;
shminfo.shmid = shmget(IPC_PRIVATE, w*h*4, IPC_CREAT|0777);
shminfo.shmaddr = shmat(shminfo.shmid, 0, 0);
XShmAttach(display, &shminfo);
// 你写 shminfo.shmaddr,X server 读
XShmPutImage(display, window, gc, &image, 0, 0, 0, 0, w, h, False);
```

**优点**:无 copy(CPU 写共享内存,X server 直接读),性能好。
**缺点**:X11 专属,不跨 Wayland。

**这就是 softbuffer 在 X11 后端做的事**——它把 XShm 包装起来,你写 `Vec<u32>`,softbuffer 把它放到共享内存,再 `XShmPutImage`。

#### 路径 3:Wayland `wl_shm`(共享内存)

Wayland 协议自带共享内存支持:

```c
int fd = syscall(SYS_memfd_create, "buffer", 0);
ftruncate(fd, w*h*4);
void *data = mmap(NULL, w*h*4, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
// 写 data
struct wl_shm_pool *pool = wl_shm_create_pool(shm, fd, w*h*4);
struct wl_buffer *buf = wl_shm_pool_create_buffer(pool, 0, w, h, w*4, WL_SHM_FORMAT_XRGB8888);
wl_surface_attach(surface, buf, 0, 0);
wl_surface_commit(surface);
```

**优点**:比 X11 简单(协议设计现代)。
**缺点**:Wayland 专属。

softbuffer 的 Wayland 后端就这么做。

#### 路径 4:OpenGL / OpenGL ES

```c
// 创建 OpenGL context
glGenTextures(1, &tex);
glBindTexture(GL_TEXTURE_2D, tex);
glTexImage2D(GL_TEXTURE_2D, 0, GL_RGBA, w, h, 0, GL_RGBA, GL_UNSIGNED_BYTE, pixels);
// 用 shader 画一个全屏 quad,纹理就是这个 tex
```

**优点**:GPU 加速,跨平台,3D 友好。
**缺点**:

- 要懂 shader(GLSL),管线的概念多
- OpenGL 已 deprecated(macOS 不更新),实际是 OpenGL ES / WebGL 主流
- 驱动 bug 多(各家 GPU 厂商驱动质量参差)

我们 Phase 5 会切到这条路径。

#### 路径 5:Vulkan / D3D12

现代低开销 GPU API。代码长 5 倍以上,但性能极致:

```c
VkInstance instance;
VkPhysicalDevice physical;
VkDevice device;
VkQueue queue;
VkSwapchainKHR swapchain;
VkImage backbuffers[N];
// ... 几百行初始化
```

**优点**:显式控制一切(内存、同步、管线),性能最高。
**缺点**:

- 极其复杂(渲染一个三角形要 1500 行代码)
- 学习曲线陡
- 平台不一致(Vulkan 跨平台,D3D12 Windows 专属,Metal macOS 专属)

`wgpu` 是 Rust 的"Vulkan-lite"抽象——跨平台,但比 Vulkan 简单。Phase 6+ 备选。

### "立即模式" vs "保留模式"渲染

这是渲染 API 的两种设计哲学:

| 模式 | 含义 | 例子 |
|---|---|---|
| 立即模式(Immediate Mode) | 你说"现在画这个",API 立刻执行,不记住状态 | GDI / softbuffer / OpenGL 1.x |
| 保留模式(Retained Mode) | 你说"我有这些对象",API 维护场景树,自己决定何时画 | SVG / DOM / WPF / Scene Kit |

**立即模式**(本教程):

```rust
// 每帧你主动画
for pixel in buffer {
    *pixel = compute_pixel_color();
}
buffer.present();
```

**保留模式**(Web / WPF):

```html
<rect x="10" y="10" width="50" height="50" fill="red" />
```

DOM 维护这棵树,浏览器自己决定何时重画。

游戏几乎都是**立即模式**(控制欲强)。Web / GUI 应用是**保留模式**(描述状态,框架干活)。

### 为什么 Casey 不用 D3D/OpenGL?

具体原因:

1. **驱动 bug**:Casey 早年在游戏公司工作过,见过太多 GPU 驱动 bug。软件渲染"所见即所得",bug 在你代码里。
2. **教学**:HH 是教学项目,要让观众**理解像素怎么变亮的**,而不是"我把 vertex buffer 喂给 D3D,屏幕亮了,中间发生了什么不知道"。
3. **架构验证**:软件渲染跑得通,后面切 GPU 才有对照——同一个游戏,软件 60 FPS,GPU 600 FPS,差 10 倍,你就知道 GPU 价值在哪。
4. **可移植**:GDI 软件渲染算法完全可在 Linux / macOS / WebAssembly 复用。D3D 代码搬不过去。

我们的 Rust 实现继承这个哲学:**Phase 1-4 全 CPU 软渲染**,Phase 5 切 GPU。

## 3 · 四域深入

### 3.1 · 🐧 Linux 系统编程视角

#### DRM / KMS:Linux 显示的底层

Linux 内核的 **DRM**(Direct Rendering Manager)和 **KMS**(Kernel Mode Setting)是所有图形的根:

- **DRM**:管理 GPU 资源(显存、上下文、命令队列)。每个 GPU 有个 `/dev/dri/card0`。
- **KMS**:设置显示模式(分辨率、刷新率、显示输出)。每个显示器有个 `/dev/dri/card0` 上的 connector。

X server 和 Wayland compositor 都用 DRM/KMS 访问硬件。你的程序不直接调 DRM,而是经过窗口系统。

```bash
# 看 DRM 设备
ls -l /dev/dri/
# crw-rw---- 1 root video 226, 0 ... card0
# crw-rw---- 1 root video 226, 64 ... renderD128  ← 这是 GPU 计算(无显示)
# crw-rw---- 1 root video 226, 128 ... controlD64

# 看当前显示模式(用 modetest)
sudo pacman -S libdrm
modetest -M /dev/dri/card0
# 输出:连接器列表、支持分辨率、当前 mode
```

如果你的程序要绕过窗口系统(比如做 embedded kiosk),可以直接用 DRM/KMS。Rust 的 `kms` crate 提供封装。**今天的我们不需要**,但理解它存在。

#### GBM / EGL:窗口系统的 GPU 抽象

要在 Linux 上用 OpenGL / Vulkan,需要 "EGL context"——一个"GPU 渲染上下文"。Linux 用 **Mesa** 的 **GBM**(Generic Buffer Management)分配可被 GPU 用的缓冲。

```
应用 ──→ EGL ──→ GBM ──→ DRM ──→ GPU
                       ↑
                  (窗口系统可在这层介入)
```

X11 和 Wayland 都通过 EGL 给应用提供 OpenGL context。wgpu / glow / glutin 内部用 EGL。softbuffer **不用** EGL(它是 CPU 渲染,不需要 GPU context)。

### 3.2 · 🎨 图形学视角

#### CPU vs GPU 渲染对比

| 维度 | CPU(softbuffer) | GPU(OpenGL / wgpu) |
|---|---|---|
| 像素并行度 | 4-16(SIMD) | 几千(着色器核) |
| 适合 | 复杂控制流、少像素 | 大批量同质计算、多像素 |
| 编程模型 | 顺序(imperative) | 数据并行(SIMT) |
| 内存模型 | 自由访问任意地址 | 受限(纹理 / UBO / SSBO) |
| 状态管理 | 无(每帧重画) | 大量绑定状态 |
| 调试 | 容易(gdb) | 难(RenderDoc 等) |
| 学习曲线 | 低 | 中-高 |

#### 软件光栅化的位置

软件光栅化(software rasterization)是用 CPU 实现"三角形 → 像素"。Casey 在 Day 70-110 手写一个。它教你:

- 投影矩阵怎么把 3D 变 2D
- 重心坐标怎么决定像素属于哪个三角形
- 深度缓冲怎么解决遮挡
- 纹理映射怎么插值 UV

学完软件光栅化,GPU 光栅化就是"用 shader 表达同样的算法,跑在 GPU 上"。**Phase 3 我们会走这条**。

#### 颜色空间再次提醒

Day 3 提过 sRGB 非线性。今天补充:**GPU 渲染管线可以自动 sRGB↔Linear 转换**(通过纹理格式 `GL_SRGB8_ALPHA8` / `VK_FORMAT_SRGB8`)。CPU 渲染要自己手动转。这是 GPU 的一个隐藏好处。Casey 在 Day 83+ 详细处理。

### 3.3 · 🦀 Rust 生态视角

#### Rust 渲染生态全景

| crate | 抽象层级 | 用途 |
|---|---|---|
| `softbuffer` | 像素 blit | 2D 软件,教学 |
| `minifb` | 像素 blit + 自带窗口 | 极简 demo |
| `pixels` | 像素 blit(基于 wgpu) | 2D 像素艺术,emulator |
| `glow` | OpenGL 函数加载 | OpenGL 老项目 |
| `glutin` | OpenGL + 窗口 | OpenGL 项目 |
| `wgpu` | Vulkan/Metal/D3D12 抽象 | 现代跨平台 GPU |
| `vulkano` | Vulkan 安全封装 | Vulkan Rust 项目 |
| `ash` | Vulkan 原始绑定 | 想完全控制 |
| `bevy_render` | Bevy 引擎的渲染层 | 用 Bevy 时 |

#### 为什么选 softbuffer 而非 pixels?

`pixels` 看起来和 softbuffer 像——都是"像素 → 屏幕"。但:

- `pixels` 内部用 wgpu,意味着依赖整个 wgpu 栈(几 MB 二进制,首次启动慢)
- `pixels` 强制你接受 GPU 的 pipeline,即使是 2D 软件
- `softbuffer` 是纯 CPU + 窗口系统的"shm"路径,依赖少,启动快,代码透明

教学选 softbuffer:**你能看清每个像素怎么到屏幕的**。

#### GPU API 的所有权挑战

GPU 资源(buffer / texture / pipeline)的生命周期管理在 Rust 里很麻烦——GPU 对象是"异步创建、可能延迟销毁"。Rust 的所有权模型假设"drop 立刻释放",GPU 不一样。

`wgpu` 用 `Arc<WgpuResource>` + 引用计数解决。`vulkano` 用 lifetime 标注。这些设计都不简单,所以**先学软件渲染再学 GPU**,理解难度梯度。

### 3.4 · 🎮 游戏编程视角

#### 业界主流游戏怎么选?

- **AAA 3D 游戏**(《赛博朋克 2077》《艾尔登法环》):自研引擎 + D3D12 / Vulkan
- **跨平台 3D**(《原神》《Hades》):Unity / Unreal 内部封装
- **2D 独立游戏**(《Hollow Knight》《Stardew Valley》):Unity / SDL2 / XNA
- **像素艺术**(《Celeste》):MonoGame / SDL2
- **数学 / 模拟**(《Minecraft》Java 版):LWJGL(OpenGL)

Casey 的 HH 是**特例**:坚持软件渲染,纯粹教学。**没有任何商业游戏用 GDI / softbuffer 软件渲染当主要渲染路径**——因为太慢。但**所有游戏引擎的核心算法**(光栅化、光照、纹理)都是从软件算法开始,搬到 GPU。

学 HH 软件渲染的价值:**你理解了渲染原理,GPU API 只是工具**。

#### 渲染抽象层级

```
商业引擎(Unreal / Unity)
  ↓
渲染抽象(wgpu / RHI)
  ↓
GPU API(OpenGL / Vulkan / D3D12)
  ↓
驱动
  ↓
硬件

HH 走的路:
渲染算法(Casey 手写)
  ↓
软件渲染(CPU + softbuffer)
  ↓
窗口系统
  ↓
驱动
  ↓
硬件
```

理解软件渲染 = 理解算法。Phase 5 切 GPU = 把算法搬平台。

## 4 · 认知地图

### 4.1 上级

- **渲染管线**(Rendering Pipeline)— 从 3D 场景到 2D 像素的整套流程
- **图形 API**(Graphics API)— 程序员和 GPU / 显示子系统对话的接口
- **窗口系统 / 显示服务器**— 多程序共享屏幕的仲裁者

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| `/dev/fb0` 直写 | 绕过窗口系统 | embedded kiosk | 不用 |
| X11 XShm | 共享内存,CPU 渲染 | 老式 X11 应用 | softbuffer 后端 |
| Wayland wl_shm | 共享内存,现代 | Wayland 应用 | softbuffer 后端 |
| `softbuffer` | 跨平台 X11/Wayland/Win/macOS | 教学、2D 软件 | ✅ Phase 1-4 |
| OpenGL / `glow` | GPU 1.0/2.0 时代,跨平台 | 老项目,简单 3D | Phase 5 |
| `wgpu` | 现代 GPU 抽象 | 现代跨平台 | Phase 6+ 备选 |
| Vulkan / `ash` | 显式控制 | 极致性能 | 不用 |
| D3D11 / `windows-rs` | Windows 主流 | Windows-only | 不用 |

### 4.3 下级

- **framebuffer** — 像素数组(概念,可指任何层)
- **swapchain** — 多缓冲管理
- **surface** — 可渲染目标(窗口、屏幕区域)
- **present / swap** — 提交后缓冲
- **vsync** — 垂直同步
- **shm / shared memory** — 进程间共享内存

## 5 · 对照与变奏

### Casey 的 GDI vs 我们的 softbuffer

| 概念 | Win32 GDI | softbuffer |
|---|---|---|
| 后缓冲分配 | `CreateDIBSection` | `Vec<u32>` 或 `surface.buffer_mut()` |
| 像素格式 | `BITMAPINFO` 显式 | `XRGB8888` 隐式 |
| 提交 | `StretchDIBits` | `buffer.present()` |
| 窗口 resize | 自己处理(重分配 + 释放) | `surface.resize(w, h)` |
| 跨平台 | Windows 专属 | Linux / Win / macOS |

两者都是"立即模式 + 共享内存"模型,只是 API 风格不同(C 风格 vs Rust 风格)。

### 2D 渲染在 Web / 桌面 / 游戏的演化

| 时代 | Web | 桌面 | 游戏 |
|---|---|---|---|
| 1990s | (无) | GDI / QuickDraw | DOS 软件渲染 + VESA |
| 2000s | `<canvas>` 2D | GDI+ / Cairo / Core Graphics | D3D9 / OpenGL 2 |
| 2010s | WebGL / Canvas 2D 硬件加速 | Direct2D / Skia | D3D11 / OpenGL ES |
| 2020s | WebGPU / WebGPU | Direct2D + D3D12 / Skia + Vulkan | D3D12 / Vulkan / Metal |

每一代都在"更高抽象 + 更快硬件"间平衡。Casey 故意停留在 1990s 抽象(立即模式 + 共享内存)做教学。

### 历史演化:Linux 显示栈

- **1990s**:Linux framebuffer(`/dev/fb0`),用户态直接写
- **1990s-2010s**:X11 主导,XFree86 → X.Org
- **2008+**:Wayland 项目开始
- **2010s**:Mesa 实现 OpenGL / Vulkan,开源 GPU 驱动(radeon / nouveau / amdgpu / i915)
- **2020s**:Wayland 成为大多数发行版默认,X11 通过 Xwayland 兼容

你今天写 `cargo run` 跑出来的程序,默认走 Wayland(若 session 是 wayland),fallback X11。**这两个底层完全不同,但 softbuffer 让你看不到差异**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 说"`SetPixel` 太慢"。**为什么慢?** 具体原因是什么?如果只是"调一个函数画一个像素",为什么不能"每帧调 100 万次"?

**参考解答**:

`SetPixel(hdc, x, y, color)` 慢的原因:

1. **每次调用都是 syscall**(Win32 GDI 跨用户态/内核态边界)
2. **每次都要做裁剪、转换、状态检查**(GDI 不知道你是不是连续写)
3. **没有批量优化**:GPU 不能 SIMD 处理(每次单独的 API 调用)
4. **函数调用开销**:100 万次函数调用,即使每次 100ns,总共 100ms,60 FPS 跑不完

实测:`SetPixel` 画一个 1920×1080 屏要好几秒。`StretchDIBits` 一帧 < 5ms。差 1000 倍。

教训:**API 设计的"粒度"决定性能**。一个 API 让你"画一个像素"看似灵活,实际是性能陷阱。批量操作(一次给一大块)永远比单元素操作快。

```rust
// fb_demo/src/main.rs
use std::fs::OpenOptions;
use std::io::Write;
use std::mem::size_of;

fn main() -> std::io::Result<()> {
    // 打开 fb0
    let mut fb = OpenOptions::new()
        .read(true)
        .write(true)
        .open("/dev/fb0")?;

    // 假设 1920x1080,32bpp(实际要 ioctl 读 fb_var_screeninfo)
    let w = 1920_usize;
    let h = 1080_usize;
    let bytes_per_pixel = 4;

    // 准备一段全红像素(XRGB)
    let mut buf = vec![0u8; w * h * bytes_per_pixel];
    for px in buf.chunks_exact_mut(bytes_per_pixel) {
        // 假设 fb 是 BGRX(Linux fb 常见)
        px[0] = 0;    // B
        px[1] = 0;    // G
        px[2] = 255;  // R
        px[3] = 0;    // X
    }

    fb.write_all(&buf)?;
    println!("Framebuffer filled with red");

    // 恢复桌面
    Ok(())
}
```

### Troubleshooting

- **`/dev/fb0: Permission denied`** — 加 `video` 组:`sudo usermod -aG video $USER`,重新登录
- **Wayland 下 fb0 写了没反应** — Wayland 不让你写,这是设计
- **softbuffer 编译错误** — 确认装了 `libxkbcommon`、`libx11`、`wayland`
- **winit 创建窗口失败** — X11 / Wayland session 切换问题,看 `journalctl --user -b`
