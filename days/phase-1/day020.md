## 0 · 为什么要有这一天

你写代码 1 万行,你修 bug 的时间是写代码的 5 倍。这是工业界的统计——大部分工程师大部分时间在**理解为什么代码不工作**。

但奇怪的是,**大学不教调试**。学校教你数据结构、算法、设计模式,但没有人教"遇到 bug 怎么办"。默认假设是"老师会给你正确答案"。工作中没有老师,只有 bug。

Casey 这集展示的是**调试方法论**——一种系统化的、可学习的、可复用的能力。核心思想:

1. **把不可见的变可见**——内部状态打印出来 / 画出来
2. **假设 - 验证循环**——列举可能原因,逐个验证
3. **二分定位**——回退到 known good,逐步加新代码
4. **不放弃**——有些 bug 几小时,有些几天

**心理锚点**:读完今天,你能:

- 写出一个调试 bug 的标准流程(不是"凭感觉")
- 在 Rust 里用 `dbg!` / `println!` / `tracing` 可视化状态
- 用 `gdb` / `lldb` 设断点,看变量
- 用 `rr` 录制运行,反向执行(找"怎么到这里的")
- 用 `perf` 找性能瓶颈
- 用 `valgrind` 找内存错误
- 解释 `git bisect` 怎么自动二分定位回归 bug
- 知道 Arch Linux 上 `strace` / `ltrace` 怎么用

## 2 · 心智模型

### 类比:调试是侦探工作

你想象自己是个侦探,面对一起案件:

**做法 A:凭直觉**——猜一个嫌疑人,直接抓。可能抓错,真凶跑了。

**做法 B:系统化排查**——
1. 勘察现场(收集证据:log、core dump、crash 报告)
2. 列举嫌疑人(假设:可能是 X、可能是 Y、可能是 Z)
3. 对每个嫌疑人找证据(实验:验证假设)
4. 缩小范围(二分:确定时间线)
5. 锁定真凶(根因)
6. 写结案报告(写注释 / fix 代码 / 防止再发生)

工程师和侦探的共同点:**证据导向,不靠猜**。新手最常犯的错是"凭感觉改代码,看好了没,不行再改"——这叫 **shotgun debugging**(散弹枪调试),命中率极低,而且改坏了不知道为什么。

### 严谨:调试方法论

我把 Casey 的方法形式化:

#### 步骤 1:复现

bug 不能稳定复现,就没法调试。第一件事是**找到稳定复现路径**。

```
按 X 顺序操作 → bug 一定出现
```

如果 bug 偶发,试试:
- 增大负载(更多粒子、更多声音)
- 改变时机(降低 FPS、加大缓冲)
- 关闭其他程序(减少干扰)

Casey 这集的音频 bug:跑 30 秒必现——稳定复现,可以调试。

#### 步骤 2:可视化

打印或绘制内部状态。**人脑擅长看图,不擅长读数字**。

Casey 在屏幕上画 cursor 位置图:

```
frame 100  200  300  400  500
play  |----*----*----*----*----*    (理想:匀速直线)
write |----+----+----+----+----+
      
实际(有 bug):
play  |----*----*    *----*----*    (中间停了!bug 在这)
write |----+----+----+----+----+
```

可视化后立刻看到"play cursor 在 frame 300 停了一帧"——这就是问题。

Rust 里的可视化工具:

```rust
// 简单:打印
println!("frame={} play={} write={}", frame, play, write);

// 结构化:tracing
tracing::info!(frame, play, write, "cursor");

// 可视化:写到文件,用 gnuplot / Python 画
use std::io::Write;
let mut f = std::fs::File::create("cursor.csv").unwrap();
writeln!(f, "frame,play,write").unwrap();
for i in 0..1000 {
    writeln!(f, "{},{},{}", i, play[i], write[i]).unwrap();
}
// 然后:gnuplot -e "plot 'cursor.csv' using 1:2 with lines"
```

#### 步骤 3:假设 - 验证

列举所有可能原因,逐个设计实验:

```
假设 1:play cursor 返回过时值
  实验:连续读 5 次,看是否一样
  结果:[实验跑] → 是的,5 次返回相同值 → 假设 1 可能正确
  
假设 2:CPU 饿死音频线程
  实验:提高音频线程优先级,看是否改善
  结果:[实验跑] → 没改善 → 假设 2 不正确,排除
  
假设 3:buffer 大小算错
  实验:打印 buffer 大小,看是否预期
  结果:[实验跑] → 大小正确 → 假设 3 排除
```

每个实验**只改一个变量**——这是科学方法的核心。如果你同时改三个东西,bug 好了不知道哪个改对了,坏了不知道哪个改坏了。

#### 步骤 4:二分定位

如果上面三步没找到,用二分:

```
当前版本:bug 存在
3 个月前的版本:bug 不存在
→ bug 是过去 3 个月某次提交引入的

git bisect start
git bisect bad HEAD
git bisect good <3-months-ago-commit>
# git 自动 checkout 中间 commit
# 你测试 → good / bad → git 继续二分
# 几轮后定位到具体 commit
```

`git bisect` 是程序员的"时间机器"。Casey 在 C 里手动跑,你用 git 自动。

#### 步骤 5:根因

找到 bug 的根本原因,不是表面症状。比如:

- 表面:play cursor 返回过时值
- 根因:DirectSound 内部 cache,只在某些条件下刷新

**只修表面** = 加 workaround(读 5 次取最新),治标。
**修根因** = 用其他 API(WASAPI)绕开 DirectSound。Casey 选了 workaround,因为他用 DirectSound 教学,根因在 Microsoft。

工程上的取舍:**先 workaround(让游戏跑),后根因(彻底解决)**。Casey 在 HH 全剧多次这样做。

#### 步骤 6:防止再发生

修完后:
- 加 comment 解释 workaround
- 加 regression test(如果可能)
- 写笔记,记录这次发现

```
// DirectSound 的 GetCurrentPosition 在某些时刻返回过时值。
// 我们读 5 次取最大,模拟"刷新 cache"。
// 见 https://... 微软文档对此的说明。
// Day 020 调试发现,Casey 笔记。
```

未来读者(包括半年后的你)看到这段,知道为什么这么写。

### Rust 调试工具

| 工具 | 用途 |
|---|---|
| `dbg!()` | 快速打印变量值,返回原值 |
| `println!` | 经典打印 |
| `tracing` | 结构化日志,异步 / 多线程友好 |
| `gdb` / `lldb` | 断点、变量、调用栈 |
| `rr` | 录制运行,反向执行(Linux 神器) |
| `cargo flamegraph` | CPU 火焰图 |
| `perf` | 系统级性能 |
| `valgrind` | 内存错误(C / C++/ unsafe Rust) |
| `miri` | Rust UB 检测(only unsafe) |
| `clippy` | 静态 lint |
| `rust-analyzer` | IDE 集成,hover 看类型 |

实战例子:

```rust
// dbg! 打印并返回原值
let x = compute_something();
let x = dbg!(x);  // 打印 [src/main.rs:2] x = 42

// 用 dbg! 在表达式中间
let result = process(dbg!(input));  // 打印 input,然后传给 process

// tracing 异步日志
use tracing::{info, instrument};

#[instrument]  // 自动记录函数参数
fn process(input: i32) -> i32 {
    info!(input, "processing");  // 结构化 log
    input * 2
}
```

### Arch Linux 工具

```bash
# 1. strace:看系统调用
strace -f -e trace=open,read,write ./your-app
# -f follow fork
# -e 只看特定调用

# 2. ltrace:看库调用
ltrace -l libhandmade.so ./your-app

# 3. perf stat:CPU 计数
sudo perf stat -e cache-misses,faults,sched-migrations ./your-app

# 4. perf record + report:profile
sudo perf record -g -- ./your-app
sudo perf report

# 5. flamegraph(更直观)
sudo pacman -S flamegraph
cargo install cargo-flamegraph
cargo flamegraph --bin your-app

# 6. valgrind(慢 20×,但找内存错误)
valgrind --leak-check=full ./your-app

# 7. rr(录制 + 反向执行)
sudo pacman -S rr
rr record ./your-app
rr replay
# 在 rr 里:reverse-step / reverse-continue

# 8. gdb / lldb
rust-gdb ./your-app
# 或
lldb ./your-app
# 命令:break / run / next / step / print / continue

# 9. AddressSanitizer(需 nightly)
RUSTFLAGS="-Zsanitizer=address" cargo +nightly build
./your-app  # 自动检测内存错误

# 10. Miri(检查 unsafe Rust UB)
cargo +nightly miri test
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发特有的调试挑战:

- **多线程**:渲染线程 / 物理线程 / 音频线程,bug 在交错处
- **实时**:bug 偶发,改了又消失(时机敏感)
- **状态大**:整个游戏世界状态,某个变量出问题
- **黑盒**:很多底层库(gpu 驱动、音频驱动)出 bug 你看不到

业界工具:
- **Tracy**:游戏专用 profiler,实时帧级可视化,跨平台
- **RenderDoc**:GPU frame capture,逐 draw call 看
- **Pix**(Windows):DirectX 调试
- **VTune**(Intel):CPU 深度 profile
- **Superluminal**:Windows profiler

Casey 在 HH 后期(Day 180+)写自己的 debug system——画帧时间图、调用图、变量监视图。这是把"可视化"工程化。

### 3.2 · 🐧 Linux 系统编程视角

Linux 调试生态比 Windows 丰富(开源 + 命令行友好):

| 工具 | Linux 等价 | Windows 等价 |
|---|---|---|
| 反向调试 | rr | (无,Time Travel Debugging 仅企业版) |
| 系统调用追踪 | strace / ltrace | Process Monitor |
| 性能 profile | perf / flamegraph | xperf / VTune |
| 内存检查 | valgrind / ASan | Application Verifier |
| GPU 抓帧 | RenderDoc | RenderDoc(跨平台) |
| 网络抓包 | tcpdump / wireshark | Wireshark |
| 文件监控 | inotify / fatrace | Handle / Process Monitor |

**rr** 是 Linux 独有的神器——录制一次运行,**反向执行**找 bug。

```
rr record ./buggy-app
# 应用崩溃
rr replay
(rr) reverse-continue
# 反向走,停在导致崩溃的上一个事件
```

这对"内存释放后使用"(use-after-free)bug 极有用——正向调试看到崩溃,反向找到 free 的地方。

### 3.3 · 🦀 Rust 生态视角

Rust 的最大调试优势:**编译期消除大量 bug**。空指针、数据竞争、生命周期错误——Rust 编译就拒绝。剩下要调试的是:

- **逻辑错误**:算法错(物理穿透、AI 卡死)
- **unsafe UB**:Rust unsafe 块的错误(裸指针错)
- **并发时序**:即使 Rust 防数据竞争,逻辑层 deadlock 仍可能
- **性能**:Rust 写对了但慢

Rust 特有工具:

- **`cargo miri`**:运行 Rust 程序在虚拟机里,检测 UB(仅 unsafe 代码用)
- **`cargo clippy`**:lint,提示"可以更地道"
- **`dbg!`**:Rust 标配的快速打印
- **`Result` / `?`**:错误处理替代异常,stack trace 清晰

```rust
// Rust 处理错误的"防御性编程"
fn parse(s: &str) -> Result<i32, ParseError> {
    s.parse().map_err(|e| ParseError::from(e))
}

fn main() {
    match parse("abc") {
        Ok(n) => println!("got {}", n),
        Err(e) => eprintln!("error: {:?}", e),  // 清晰的错误链
    }
}
```

错误处理是调试的预防层——写得好,bug 少。

### 3.4 · 软件工程:调试哲学

调试的深层哲学:

**1. 证据导向**——不靠猜。每个结论有数据支持。

**2. 假设可证伪**——所有假设都要可测试。"可能是 X"必须能设计实验验证。如果不能验证,那不是假设,是空想。

**3. 奥卡姆剃刀**——多个解释选最简单的。bug 是"DirectSound 内部 cache"(简单)比"我的整个架构都错了"(复杂)更可能。

**4. 不要急着改**——改代码是最后一步。理解清楚 bug 后改,一次成功。改坏多次反而浪费时间。

**5. 隔离变量**——一次只改一个。否则不知道哪个改动有效。

**6. 写下来**——调试过程写注释 / 笔记。半年后忘了,你回来看笔记就知道为什么这么改。

**7. 二分万能**——不知道 bug 在哪,二分。代码可以二分(git bisect),输入可以二分(数据少了 90% 还崩吗?),时间可以二分(前 5 分钟跑得对吗?)。

Casey 这集展示的就是这套哲学的具体应用。

## 4 · 认知地图

### 4.1 上级

- **科学方法**(Scientific Method)——假设 / 实验 / 验证循环

## 5 · 对照与变奏

### Debug vs Reverse Engineering

调试 = 你的代码,你有源码,bug 是引入的。
逆向工程 = 别人的代码,你没源码,bug 在那(或恶意行为)。

但**方法相同**:可视化、假设验证、二分、根因。**调试能力 = 逆向能力**。这就是为什么黑客常是好的 debugger——同样的技能集。

业界:安全研究员调试恶意软件,用的就是这套方法。

### Bug 类型

| 类型 | 特征 | 工具 |
|---|---|---|
| Crash(段错误) | 立即停 | gdb core dump |
| Memory leak | 内存增长 | valgrind / heaptrack |
| Race condition | 偶发,时序敏感 | ThreadSanitizer / rr |
| Logic bug | 行为错但不崩 | 单元测试 + 可视化 |
| Performance | 慢但不崩 | perf / flamegraph |
| Intermittent | 偶发,难复现 | 加 log + 长跑 |

每种 bug 有最适合的工具。**先分类,再选工具**,不要无脑用 gdb。

### 历史演化:调试工具

- **1970s**:printf + core dump。Unix 哲学。
- **1980s**:gdb 出现,断点调试普及。
- **1990s**:IDE 集成(Visual Studio debugger)。
- **2000s**:性能 profiler(VTune / perf),valgrind。
- **2010s**:rr(reverse debugging),分布式追踪(Zipkin / Jaeger)。
- **2020s**:AI 辅助调试(Copilot 解释错误),机器学习找 bug。

Casey 在 HH 用 1990s 风格(printf + 可视化)。现代工具有 rr / Tracy,但 Casey 偏好简单工具——因为不依赖工具就是好工具。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 调试音频 bug 的第一步是"画 cursor 位置图"。为什么这一步比"猜原因改代码"更有效?

进一步:你遇到一个**性能问题**(游戏卡顿),但不知道是渲染慢还是物理慢,你的"可视化"会做什么?

**参考解答**:

**可视化优先**因为"现象 - 假设 - 验证"循环里,可视化帮你**生成精准假设**。

凭空猜:"可能是 cursor 不准 / 可能是线程问题 / 可能是 buffer 算错"——漫无目的,要试很多。
可视化后,看到 cursor 在某帧停了——立刻知道"问题在写入侧"。假设范围缩小 10×。

**性能卡顿的可视化**:

1. **帧时间图**:每帧画一条,长度=耗时。一眼看出哪帧慢
2. **阶段耗时**:每帧分阶段(物理 / 渲染 / AI / 音频),堆叠图
3. **事件计数**:每帧画多少 sprite / particle。看是否某帧突然多
4. **memory footprint**:看是否 GC(虽然 Rust 没有,但 page fault 类似)

工具:`mangohud`(看 FPS / 帧时间)、`Tracy`(CPU profiler)、`renderdoc`(GPU frame capture)。

### Lv2 · 动手实践

**题**:写一个 Rust 程序,故意引入一个 bug(比如 off-by-one、use-after-free with unsafe、整数溢出),然后**用工具找它**。

要求:
1. 程序跑起来偶发 crash(随机性,模拟真实 bug)
2. 用 gdb 找 crash 位置
3. 用 valgrind / ASan / miri 找根因(根据 bug 类型选)
4. 解释根因,写出 fix

完成标准:写一份"调试报告"——什么 bug、怎么找、怎么修。

**参考解答**(示例 bug:整数溢出):

```rust
// 故意 bug:累加大量数据,溢出
fn sum(data: &[u32]) -> u32 {
    let mut s: u32 = 0;
    for &x in data {
        s += x;  // 溢出时 debug panic,release wrap
    }
    s
}

fn main() {
    let data: Vec<u32> = (0..1_000_000).map(|_| u32::MAX / 2).collect();
    let s = sum(&data);
    println!("sum = {}", s);
}
```

调试过程:

```bash
# 1. debug 模式跑(自动 panic on overflow)
cargo run
# 输出:thread 'main' panicked at 'attempt to add with overflow'

# 2. release 模式(默认 wrap,不 panic)
cargo run --release
# 输出:sum = <某个不对的数字>

# 3. 加 ASan(在 nightly)
RUSTFLAGS="-Zsanitizer=address" cargo +nightly run
# 但 ASan 检测内存错误,不检测溢出

# 4. 检测溢出的工具:overflow-checks(强制 release 也检查)
RUSTFLAGS="-C overflow-checks=on" cargo run --release
# 现在也 panic

# 5. fix:用 u64 或 checked_add
fn sum(data: &[u32]) -> u64 {
    data.iter().map(|&x| x as u64).sum()
}
```

**调试报告**:
- bug 类型:整数溢出
- 症状:release 模式输出错数字(无 crash)
- 工具:`-C overflow-checks=on`(强制检查)
- 根因:`u32` 不够装 100 万 × (u32::MAX / 2)
- fix:用 u64

## 8 · Rust / Arch 落地代码

### Rust:调试一个 demo

```rust
// src/debug_demo.rs
// 故意有 bug:模拟 use-after-free

use std::sync::atomic::{AtomicUsize, Ordering};

static DROP_COUNT: AtomicUsize = AtomicUsize::new(0);

struct Resource {
    data: Vec<u8>,
}

impl Drop for Resource {
    fn drop(&mut self) {
        DROP_COUNT.fetch_add(1, Ordering::SeqCst);
    }
}

fn main() {
    let mut resources: Vec<Resource> = (0..100)
        .map(|i| Resource { data: vec![i as u8; 1024] })
        .collect();
    
    // 故意 bug:保留一个原始指针
    let leaked_ptr: *const Resource = &resources[50];
    
    // 删一些
    resources.clear();
    
    // 用 leaked_ptr(unsafe,UAF)
    unsafe {
        let r = &*leaked_ptr;
        println!("accessing after free: {}", r.data[0]);  // UB!
    }
    
    println!("dropped {} resources", DROP_COUNT.load(Ordering::SeqCst));
}
```

调试:

```bash
# 1. 编译(允许 unsafe)
cargo build --release

# 2. 直接跑(可能不崩,因为内存还没被覆盖)
./target/release/debug_demo

# 3. 跑 valgrind
valgrind --leak-check=full ./target/release/debug_demo
# 输出:
# Invalid read of size 8
#    at 0x...: debug_demo::main (src/debug_demo.rs:30)
# Address 0x... is 0 bytes inside a block of size 16 free'd

# 4. 用 Miri(更精确,只检测 Rust UB)
cargo +nightly miri run
# 输出:
# error: Undefined Behavior: pointer out of bounds
#    --> src/debug_demo.rs:30:24
```

valgrind 和 Miri 都能找到这个 bug。Miri 更精确(它知道 Rust 类型系统),但只能在 nightly 跑且慢。

### gdb 调试示例

```bash
# 1. 用 gdb 跑(debug build,带符号)
```

### rr(反向调试)

```bash
# 1. 装 rr
sudo pacman -S rr

# 2. 录制
rr record ./target/debug/debug_demo
# rr 把整个运行录下来,包括崩溃

# 3. 回放
rr replay

# rr-prompt 内
(rr) break debug_demo::main
(rr) run
(rr) next
(rr) print resources
# 看到 leaked_ptr 指向的资源
(rr) continue  # 走到崩溃

# 4. 反向
(rr) reverse-continue  # 反向走到上一个断点 / 事件
(rr) reverse-step  # 反向单步
```

`rr` 的杀手锏:**反向执行**。看到崩溃,`reverse-continue` 反向走,停在上一个有意义的事件(比如资源被 free 的时刻)。这是普通 gdb 做不到的。

```bash
sudo wireshark capture.pcap

# 8. 文件访问监控
sudo fatrace | grep your-app
# 实时看你的程序访问哪些文件
```
