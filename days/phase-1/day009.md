
# Day 009 · 音频回调设计:从方波到变调正弦

> Day 7 我们让程序发出蜂鸣,但很简陋——回调里硬编码 440Hz 方波。今天把它做成**可变频率的正弦波**:键盘控制音高,听到从低到高的滑音。在这个过程中理解"音频回调的状态机"——回调里维护"当前频率 + 当前相位",主线程通过 channel 发命令改频率。这是后面所有游戏音效的模板。

## 0 · 为什么要有这一天

Day 7 的代码有个隐藏问题:**频率写死在回调里**。如果要让玩家按键改变音高,主线程怎么通知音频线程?

最朴素的尝试:

```rust
// 全局变量
static FREQ: AtomicU32 = AtomicU32::new(440);

// 主线程
FREQ.store(880, Ordering::Relaxed);

// 回调
let f = FREQ.load(Ordering::Relaxed) as f32;
```

这能用,但只支持"当前频率"。游戏需要更多:

- 触发音效(攻击声)
- 停止音效
- 调整音量
- 切换乐器(方波 / 正弦 / 锯齿)

最自然的设计:**主线程通过 channel 发命令,音频线程消费**。这是经典"消息传递并发"模式。

另外,Day 7 用方波(刺耳),今天换正弦波(纯音)。还要处理一个**关键 bug**:如果只在回调里写 `sin(2π * f * t)`,当 f 变化时 t 还在累加 → 波形不连续 → 咔嗒杂音。要解决"相位连续"问题。

**心理锚点**:读完今天,你能:

- 用 `crossbeam_channel` 在主线程和音频线程间传命令
- 实现"频率滑音"(按键改变音高,平滑过渡)
- 解释"相位累积"为什么必要(否则波形断)
- 实现简单的 ADSR 包络(Attack / Decay / Sustain / Release,音效淡入淡出)
- 听到键盘控制的不同音高

## 1 · Casey 今天做了什么

Casey Day 9 的核心动作:

1. 把方波换成正弦波(`sin(2π * f * t)`)
2. 实现"变调":用 XInput 的左摇杆 X 轴控制频率(向右移 = 高频)
3. 解决一个**关键 bug**:每帧切换频率时,他原本直接写 `t = sample_offset / sample_rate`,频率变了之后,新的 `t` 计算错位 → 咔嗒声。修复:维护"相位"而非"绝对 t"
4. 加 sin 函数:`OutputSineWave(...)` 内部用 X87 FPU 的 `fsin` 指令(后来 Casey 改用软件 sin)

关键洞察:**音频回调必须有"状态"**——它不是纯函数,而是个状态机。每次调用,基于上次的状态继续生成。

我们这边用 cpal 的回调 + Rust 的 channel,做等价的事。但 Rust 的类型系统强迫我们更严谨——状态怎么共享、谁拥有、谁借用,都要明确。

## 2 · 心智模型

### 类比:音频回调是个"持续运转的发动机"

发动机每秒转 48000 圈(每圈 = 一个采样)。你不能停它,也不能让它"突然换挡"——要在它转动时**平滑**换挡,否则齿轮坏(杂音)。

回调里你要维护:

- **当前相位**(phase):波形的"角度",从 0 到 2π 周期循环
- **当前频率**(freq):决定相位累加速度
- **当前音量**(amp):输出乘数

每帧(每秒 48000 次):

```
phase += 2π * freq / sample_rate
if phase > 2π { phase -= 2π }
sample = sin(phase) * amp
```

**关键**:频率变了,**相位不重置**。否则波形从 0 突然跳到 0(正弦零点),但中间是任意角度 → 咔嗒。

### 相位连续(phase continuity)的物理意义

声音是压力波的连续变化。如果你的样本序列是 `0.5, 0.7, 0.9, 1.0, 0.0, 0.2`,中间 1.0 → 0.0 是个跳跃——人耳听到"咔嗒"。

频率切换时,如果你重置 phase = 0,而上一帧 phase 在 π,下一帧从 0 开始 → 跳跃。

正确做法:**继续累加 phase**,只改"累加速度"(频率)。

```rust
// 错:freq 改变时重置 phase
let t = sample_i / sample_rate;
let sample = sin(2π * freq * t);
// 当 freq 从 440 跳到 880,t 是同一点,2π*440*t 和 2π*880*t 可能差很大
// 波形跳跃!

// 对:维护 phase,持续累加
phase += 2π * freq / sample_rate;
if phase > 2π { phase -= 2π; }
let sample = sin(phase);
// freq 改变只影响累加速度,phase 连续
```

### 命令通道(channel)模型

```
┌─────────────────┐  NoteOn(440)   ┌─────────────────┐
│  主线程          │ ────────────→  │  音频线程        │
│ (game logic)    │  SetVolume(0.5) │  (cpal callback)│
│                 │  NoteOff        │                 │
│  改 game state  │ ────────────→   │  消费命令,更新  │
└─────────────────┘                 │  phase/freq/amp │
                                    │  生成 sample    │
                                    └─────────────────┘
```

主线程"生产"命令,音频线程"消费"。**异步**:主线程不必等音频线程处理,只把命令丢进 channel。

### Rust 的 channel 选择

| crate | 类型 | 特点 |
|---|---|---|
| `std::sync::mpsc` | 多生产者单消费者 | std 内置,简单 |
| `crossbeam-channel` | 多生产者多消费者 | 高性能,API 类似 Go |
| `flume` | 类 crossbeam | 另一个选择 |
| `tokio::sync::mpsc` | 异步 | tokio 项目用 |

我们用 `crossbeam-channel`(游戏常用,API 简单,无异步运行时)。

```rust
use crossbeam_channel::{unbounded, Sender, Receiver};

let (tx, rx) = unbounded::<AudioCommand>();

// 主线程
tx.send(AudioCommand::SetFreq(440.0)).unwrap();

// 音频回调
match rx.try_recv() {
    Ok(cmd) => apply_command(cmd),
    Err(_) => { /* 无新命令 */ }
}
```

`try_recv` 不阻塞(回调里不能阻塞)。

### 命令类型设计

```rust
enum AudioCommand {
    /// 设置当前频率
    SetFreq(f32),
    /// 设置音量(0.0 ~ 1.0)
    SetVolume(f32),
    /// 触发音效(音色 + 频率 + 时长)
    PlaySfx { freq: f32, duration_secs: f32 },
    /// 停止所有
    StopAll,
}
```

enum 是 Rust 表达"多种命令"的最佳方式。每条命令是 enum 的一个变体,带不同数据。

### ADSR 包络(预告)

真实音效不会瞬间开始 / 结束(那是机械的"嘀")。**ADSR** 模型:

- **A**ttack:从 0 上升到峰值(几毫秒到几十毫秒)。模拟"按下键到完全发声"
- **D**ecay:从峰值下降到 sustain 水平(几十毫秒)
- **S**ustain:持续在 sustain 水平,直到松键
- **R**elease:松键后从 sustain 下降到 0(几百毫秒)

```
amp
 │     /\
 │    /  \____
 │   /        \____
 │  /              \____
 │ /                    \____
 │/                          \____
 └───────────────────────────────→ t
     A   D    S                R
```

实现:回调里维护"当前 ADSR 阶段 + 当前 amp",每帧根据阶段更新 amp。

我们今天先实现简化版"音量淡入淡出"(attack + release)。完整 ADSR 留给 Day 12+。

### 主线程和音频线程的同步

主线程 60 FPS,每帧 ~16ms。音频回调 ~10ms 一次。它们独立运行。

主线程发命令的时机:

- 用户按键 → 立刻发 `PlaySfx`
- 用户松键 → 立刻发 `StopAll`
- 用户改音量滑块 → 发 `SetVolume`

音频线程**异步**处理——它下次回调时 `try_recv`,看到命令就执行。延迟 = 一个回调周期(~10ms),可接受。

如果延迟必须 < 1ms(专业音频),用 ring buffer + atomic flag,而不是 channel。我们够用就行。

## 3 · 四域深入

### 3.1 · 🐧 Linux 系统编程视角

#### 线程优先级和 SCHED_FIFO

音频线程必须**按时被调度**。Linux 提供 `SCHED_FIFO` / `SCHED_RR` 实时调度策略:

```bash
# 看你音频线程的优先级
ps -eLo pid,tid,policy,rtprio,nice,comm | grep handmade

# policy 列:-  = SCHED_OTHER(普通)
#           ff = SCHED_FIFO(实时)
#           rr = SCHED_RR(实时,round-robin)
# rtprio:实时优先级(1-99,越高越优先)
```

cpal 自己处理这些——它在创建音频线程时尝试用 `SCHED_FIFO`,需要 `CAP_SYS_NICE` capability(或用户在 `audio` 组)。

```bash
# 把用户加入 audio 组(部分发行版需要)
sudo usermod -aG audio $USER
# 重新登录生效
```

PipeWire 也需要类似权限:

```bash
# PipeWire 的实时调度
systemctl --user status pipewire
# 看"Limits"段落,有 RTLimit 之类

# 启用 RLIMIT RTPRIO
sudo pacman -S realtime-privileges
sudo usermod -aG realtime $USER
```

#### 共享内存和 false sharing

如果主线程和音频线程**共享一个 struct**(用 `Mutex`),要小心 false sharing:CPU cache line 被两个核频繁同步,性能差。

解决:加 padding,让共享数据各占一条 cache line(64 字节):

```rust
#[repr(C, align(64))]
struct CachePadded<T> {
    data: T,
    _pad: [u8; 64 - std::mem::size_of::<T>()],
}
```

Rust crate `cache_padded` 提供这个。我们教学用 channel,不直接共享,不用考虑。但要知道这个坑存在。

### 3.2 · 🦀 Rust 生态视角

#### `Send` 和 `Sync`

- `Send`:类型可以**在线程间转移所有权**(T 从 A 线程 move 到 B 线程)
- `Sync`:类型可以**被多线程共享**(&T 在多线程安全)

`crossbeam_channel::Sender<T>` 是 `Send + Sync`(只要 T 是 Send)。所以多个线程能共享 sender。

`Receiver<T>` 是 `Send` 但**不** `Sync`(只能一个线程消费)。

```rust
let (tx, rx) = unbounded::<AudioCommand>();
// tx: 可以 clone,多线程共享
// rx: 只能一个线程持有(音频线程)

// 主线程拿 tx 的 clone,音频线程的回调捕获 rx
let tx2 = tx.clone();
let stream = device.build_output_stream(
    &config,
    move |data, _| {
        // rx 在这里,只能这一个回调用
        match rx.try_recv() { ... }
    },
    ...
).unwrap();
```

#### `Arc` 共享所有权

如果多个地方都要持有 sender:

```rust
use std::sync::Arc;
let tx = Arc::new(tx);  // 共享所有权
let tx_clone = tx.clone();
```

但 `crossbeam_channel::Sender` 已经内部支持 `clone`,所以不需要 Arc。`Arc` 适合**不可 Clone 的对象**(比如 cpal 的 Stream)。

#### Mutex 在音频回调里

```rust
use std::sync::Mutex;
let state = Arc::new(Mutex::new(AudioState::default()));

// 回调里(陷阱!)
let mut s = state.lock().unwrap();  // ← 阻塞!
```

`Mutex::lock` 阻塞,回调里禁用。改用:

- `try_lock`(非阻塞,失败跳过这帧)
- `parking_lot::Mutex`(更快的 lock,但仍然不能在回调用)
- `crossbeam_channel`(推荐)
- `atomic`(简单状态)
- `crossbeam_queue::SegQueue`(lock-free 队列)

我们用 channel,避免所有 mutex 问题。

#### `Atomic` 简单状态

```rust
use std::sync::atomic::{AtomicU32, Ordering};

let volume = AtomicU32::new(100);  // 0-100,整数(AtomicF32 不存在)

// 主线程
volume.store(50, Ordering::Relaxed);

// 回调
let v = volume.load(Ordering::Relaxed) as f32 / 100.0;
```

`Ordering::Relaxed` 是最弱的内存序,适合"我只关心这个值,不关心其他变量的顺序"。音频用 `Relaxed` 足够(我们要的是"看到最新值",不要严格 happens-before)。

Rust 没有 `AtomicF32`(硬件没原生支持),用 `AtomicU32` + `f32::to_bits` / `f32::from_bits`:

```rust
let vol_atomic = AtomicU32::new(0.5f32.to_bits());
let v = f32::from_bits(vol_atomic.load(Ordering::Relaxed));
vol_atomic.store(0.7f32.to_bits(), Ordering::Relaxed);
```

### 3.3 · 🎮 游戏编程视角

#### 游戏音频架构演化

- **简单(我们当前)**:一个回调,channel 收命令,直接生成样本
- **中等**:回调拉预生成的样本(从 WAV),mix 多个声音
- **高级(bevy_audio / kira)**:多 voice(每个声源一个),自动 mix,DSP 效果(混响 / 滤波)

我们走 Casey 的路:**手写**所有音频逻辑。Phase 2+ 才涉及多 voice mix。

#### 音频 mix 公式

多个声音同时播放:

```rust
let mixed = (sound1_sample + sound2_sample + sound3_sample) / 3.0;
```

或者:

```rust
let mixed = sound1_sample * 0.3 + sound2_sample * 0.3 + sound3_sample * 0.4;
```

**避免 clip**:如果三声都 ±1.0,直接加 = ±3.0,超 1.0 失真。要么除以声数(简单但音量小),要么用 dynamic range compression(自动调音量,复杂)。

Casey 在 Day 60+ 详细讨论 mix。我们 Day 9 只一个声音,不 mix。

#### 实时 vs 离线音频

- **实时**(游戏):持续生成,延迟敏感
- **离线**(音乐制作):预先渲染,质量优先,无延迟要求

游戏音频代码不能照搬音乐制作代码——它们的优化方向不同。

不直接涉及。但有个类比:**音频回调 = 渲染回调**。

## 5 · 对照与变奏

### DirectSound 环形缓冲 vs cpal 回调

| 维度 | DirectSound(Casey) | cpal(Rust) |
|---|---|---|
| 数据流 | push(你写,库读) | pull(库调你,你填) |
| 缓冲 | 环形缓冲(Lock + 写 + Unlock) | 库内部管,你只填 `&mut [f32]` |
| 同步 | `GetCurrentPosition` 查询"现在播放到哪" | 自动(回调被定时调用) |
| 线程 | 主线程直接写 | cpal 音频线程 |
| 复杂度 | 高(自己算位置) | 低(回调里只算样本) |

cpal 的 pull 模型更现代,简化了大量代码。但代价:回调的"实时性"必须严格(不能阻塞)。

### Casey 的相位 bug

Casey 在 Day 9 演示了经典 bug:

```c
// 错误版
void OutputSineWave(uint32 sample_offset, float freq) {
    for (int i = 0; i < samples_per_frame; i++) {
        float t = (sample_offset + i) / sample_rate;
        float sample = sin(2π * freq * t);  // freq 变了,t 还是绝对的
        // 咔嗒!
    }
}
```

正确版(他后续修正):

```c
// 维护全局 phase
static float phase = 0;
void OutputSineWave(float freq) {
    float phase_inc = 2π * freq / sample_rate;
    for (int i = 0; i < samples_per_frame; i++) {
        phase += phase_inc;
        if (phase > 2π) phase -= 2π;
        float sample = sin(phase);
    }
}
```

Casey 通过这个 bug 教学:**音频是连续的,你不能"重置时间"**。这个洞察贯穿所有实时音频编程。

### 不同波形的音色

| 波形 | 公式 | 听感 |
|---|---|---|
| 正弦 | `sin(2π * f * t)` | 纯净,音叉感 |
| 方波 | `sign(sin(2π * f * t))` | 蜂鸣,8-bit 游戏感 |
| 三角波 | `(2/π) * asin(sin(2π * f * t))` | 圆润,长笛感 |
| 锯齿波 | `2 * (t * f - floor(t * f + 0.5))` | 尖锐,弦乐感 |

今天我们用正弦(纯净,易理解)。Day 12+ 你可以做"波形选择"。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"频率切换时不重置 phase"?如果重置会发生什么?

**参考解答**:

考虑切换瞬间:

```
旧 freq=440Hz,当前 phase=π/2,sin(π/2)=1.0(峰值)
现在 freq=880Hz

错误做法:重置 phase=0,下一帧 sin(0)=0(零点)
样本序列:..., 1.0, 0.0, ...   ← 跳跃!咔嗒声

正确做法:继续累加 phase,只改增量
下一帧 phase=π/2 + 2π*880/48000 ≈ π/2 + 0.115 = 1.585
sin(1.585) ≈ 0.99997  ← 接近 1.0,平滑
```

人耳对波形跳跃敏感——一个 0.01ms 的跳跃都能听到"咔嗒"。所以相位必须连续,频率切换只改"累加速度"。

类比:开车换挡,齿轮不能停。车速(频率)变了,但齿轮(相位)在转。

### Lv2 · 动手实践

**题**:把 Day 7 的方波蜂鸣改成 Day 9 设计:**键盘控制频率**,左右方向键调整音高(200Hz ~ 2000Hz),空格触发/停止声音。完成标准:

- 按住 Right,音高上升
- 按住 Left,音高下降
- 按空格,开始/停止声音
- 频率切换时**无咔嗒声**(验证 phase 连续)

**参考解答**:

```bash
# 加 channel 依赖
cargo add crossbeam-channel
```

```rust
// src/main.rs(关键部分)

use cpal::traits::{DeviceTrait, HostTrait, StreamTrait};
use cpal::SampleFormat;
use crossbeam_channel::{unbounded, Receiver, Sender};
use std::sync::Arc;
use winit::application::ApplicationHandler;
use winit::event::{ElementState, KeyCode, KeyEvent, WindowEvent};
use winit::event_loop::{ActiveEventLoop, EventLoop};
use winit::keyboard::PhysicalKey;
use winit::window::{Window, WindowId};

/// 给音频线程的命令
enum AudioCommand {
    SetFreq(f32),     // 改频率
    SetActive(bool),  // 开/关声音
}

/// 音频状态(回调内部用)
struct AudioState {
    /// 当前相位(连续累加,防咔嗒)
    phase: f32,
    /// 当前频率
    freq: f32,
    /// 当前音量(0 = 静音,1 = 全音量)
    amp: f32,
    /// 目标音量(用 SetActive 设)
    target_amp: f32,
    /// 采样率
    sample_rate: f32,
}

impl AudioState {
    fn new(sample_rate: f32) -> Self {
        Self {
            phase: 0.0,
            freq: 440.0,
            amp: 0.0,
            target_amp: 0.0,
            sample_rate,
        }
    }

    fn process(&mut self, data: &mut [f32], rx: &Receiver<AudioCommand>) {
        // 1. 消费所有 pending 命令(非阻塞)
        while let Ok(cmd) = rx.try_recv() {
            match cmd {
                AudioCommand::SetFreq(f) => self.freq = f.max(20.0).min(20000.0),
                AudioCommand::SetActive(active) => {
                    self.target_amp = if active { 0.2 } else { 0.0 };
                }
            }
        }

        // 2. 生成样本
        let phase_inc = 2.0 * std::f32::consts::PI * self.freq / self.sample_rate;
        // 平滑 amp(模拟 attack/release,避免瞬间开关咔嗒)
        let amp_inc = (self.target_amp - self.amp) * 0.001;  // 慢慢追上

        for sample in data.iter_mut() {
            // 累加 phase(连续!)
            self.phase += phase_inc;
            if self.phase > 2.0 * std::f32::consts::PI {
                self.phase -= 2.0 * std::f32::consts::PI;
            }

            // amp 趋近 target
            self.amp += amp_inc;

            // 生成正弦波样本
            *sample = self.phase.sin() * self.amp;
        }
    }
}

struct App {
    window: Option<Window>,
    /// 给音频线程的命令通道
    audio_tx: Sender<AudioCommand>,
    /// 音频流(持有它,否则停)
    audio_stream: Option<cpal::Stream>,
    /// 当前频率(主线程显示用)
    current_freq: f32,
    /// 是否在响
    active: bool,
}

impl ApplicationHandler for App {
    fn resumed(&mut self, event_loop: &ActiveEventLoop) {
        if self.window.is_some() { return; }  // 只创建一次

        self.window = Some(event_loop.create_window(attrs).unwrap());

        // 创建音频流(只一次)
        let host = cpal::default_host();
        let device = host.default_output_device().unwrap();
        let supported = device.default_output_config().unwrap();
        let sample_rate = supported.sample_rate().0 as f32;
        let config: cpal::StreamConfig = supported.into();
        let sample_format = supported.sample_format();

        // rx 移动到回调里
        let rx = self.audio_tx.clone_receiver();  // 假设的方法,实际要重构
        // (实际代码:rx 在创建 channel 时拿,不能 clone)
        // 这里简化:在 main 里创建 channel,把 rx 传给 App,App 创建 stream 时移动 rx 到闭包

        // ... 实际见完整代码
    }

    fn window_event(
        &mut self,
        _event_loop: &ActiveEventLoop,
        _id: WindowId,
        event: WindowEvent,
    ) {
        match event {
            WindowEvent::CloseRequested => std::process::exit(0),

            WindowEvent::KeyboardInput {
                event: KeyEvent { state, physical_key, .. },
                ..

                        (ElementState::Pressed, KeyCode::Space) => {

                        }

                            let _ = self.audio_tx.send(
                                AudioCommand::SetFreq(self.current_freq)
                            );
                            println!("Freq: {:.1} Hz", self.current_freq);
                        }
                        (ElementState::Pressed, KeyCode::ArrowDown) => {

                            let _ = self.audio_tx.send(
                                AudioCommand::SetFreq(self.current_freq)

                        }
                        _ => ()
                    }
                }
            }
            _ => ()

    }

    fn about_to_wait(&mut self, _event_loop: &ActiveEventLoop) {
        // 这里没渲染,纯音频测试
    }
}

fn main() {
    // 1. 创建 channel(在 main,不在 App)
    let (audio_tx, audio_rx) = unbounded::<AudioCommand>();

    // 2. 创建音频流(主线程做,但 stream 在内部跑音频线程)
    let host = cpal::default_host();
    let device = host.default_output_device().expect("no output device");
    let supported = device.default_output_config().expect("no config");
    let sample_rate = supported.sample_rate().0 as f32;
    let config: cpal::StreamConfig = supported.into();
    let sample_format = supported.sample_format();

    let mut audio_state = AudioState::new(sample_rate);
    let stream = match sample_format {
        SampleFormat::F32 => device.build_output_stream(
            &config,
            move |data: &mut [f32], _: &cpal::OutputCallbackInfo| {
                audio_state.process(data, &audio_rx);
            },
            |err| eprintln!("audio err: {}", err),
            None,
        ).unwrap(),
        _ => panic!("unsupported format"),
    };
    stream.play().unwrap();

    // 3. 创建 winit 应用
    let event_loop = EventLoop::new().unwrap();
    let mut app = App {
        window: None,
        audio_tx,
        audio_stream: Some(stream),
        current_freq: 440.0,
        active: false,
    };
    event_loop.run_app(&mut app).unwrap();
}
```

### 测试 phase 连续

跑 Day 9 程序,快速按 Up 几次,频率快速跳。**没有咔嗒声**说明 phase 连续。如果有咔嗒,检查代码:

```rust
// 错(会咔嗒):
self.phase = 0.0;  // 重置了!

// 对(平滑):
self.phase += phase_inc;
if self.phase > TAU { self.phase -= TAU; }
```

### Rust 模式:`TAU` 常量

```rust
// Rust 1.67+ 有 std::f32::consts::TAU(= 2π)
use std::f32::consts::TAU;

self.phase += TAU * self.freq / self.sample_rate;
if self.phase > TAU { self.phase -= TAU; }
let sample = self.phase.sin();
```

`TAU = 2π` 是"一整圈"。用 TAU 比 `2.0 * PI` 清晰(表达"完整周期")。

### Troubleshooting

- **咔嗒声**:phase 没连续,或 amp 突变(没 attack/release)。检查代码
- **音量突变**:target_amp 直接 += amp,没插值。加 `amp += (target - amp) * 0.001`
- **频率不准**:phase_inc 公式错。应是 `2π * freq / sample_rate`,确认 sample_rate 对
- **panic in callback**:cpal 会断开流。看 stderr,通常闭包不 Send
- **回调里 lock**:把 Mutex 换成 channel,这是模式问题
