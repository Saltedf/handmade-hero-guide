# Day 008 · 窗口缩放:多 DPI 与状态同步

> Day 4 主循环跑通,Day 6 加了键盘,看起来挺顺。但有个隐患:**用户拖动窗口边缘改大小**,程序怎么办?如果后缓冲不更新尺寸,画出来的图像会被拉伸 / 错位;如果 resize 时崩溃,玩家直接骂街。今天专门处理窗口 resize,顺带讲 HiDPI(4K 屏缩放)和窗口状态同步。

## 0 · 为什么要有这一天

你以为 resize 就是"窗口大小变了,后缓冲跟着变"。实际上有一堆坑:

1. **时机问题**:`Resized` 事件 vs `RedrawRequested` 事件,先调谁?
2. **大小为零**:窗口最小化时尺寸是 0×0,你 resize 到 0×0 会 panic
3. **DPI 变化**:用户从 1080p 显示器拖到 4K 显示器,窗口物理像素可能翻倍
4. **跨线程**:resize 在主线程发生,但音频 / 网络线程可能引用旧尺寸
5. **频繁触发**:用户拖动边缘时每像素触发一次 resize,每次重分配 4MB 内存会卡

casey Day 3 就遇过这个坑——他先 resize 后缓冲,但忘了清空旧内容,resize 后画面有"残影"。Day 4 才修。

**心理锚点**:读完今天,你能:

- 在 `Resized` 事件里安全 resize softbuffer surface
- 解释"物理像素" vs "逻辑像素" vs "scale factor"
- 在 winit 0.30 里处理 `ScaleFactorChanged` 事件
- 用一个 `clamp_min_size` 函数防止 0×0 崩溃
- 解释为什么 resize 时要丢弃旧后缓冲内容

## 1 · Casey 今天做了什么

Casey Day 8 不是专门讲 resize(他在 Day 3 / Day 4 顺带处理了),但今天我们专门展开这个话题。Casey 的做法:

1. 在 `WindowProc` 的 `WM_SIZE` 分支调 `Win32ResizeDIBSection(width, height)`
2. `Win32ResizeDIBSection` 内部:`DeleteObject(BitmapHandle)`(释放旧的)+ `CreateDIBSection(...)`(分配新的)
3. 不保留旧像素——直接用新分配(可能含未初始化数据)

Casey 没处理 DPI(Windows 高 DPI 支持烂,Casey 假设 96 DPI)。我们这边 winit 提供了完整 DPI 支持,要学。

## 2 · 心智模型

### 类比:resize 是"换画布"

画家在画布上画画。画到一半,客户说"画布大小改一下"。

- **简单做法**:撕掉旧画布,买新画布,从头画
- **优雅做法**:把旧画剪贴到新画布上(可能拉伸 / 留白)

游戏选简单做法——**resize 时丢弃旧内容,下一帧重画**。原因:

1. 游戏每帧都重画整个画面,旧内容没价值
2. 把旧内容拉伸到新尺寸,反而看着丑(模糊)
3. 简单实现 + 性能好

但**GUI 应用**选优雅做法(用户输入到一半不能丢)。游戏和 GUI 不一样。

### 物理 vs 逻辑像素

**物理像素**(Physical Pixel):屏幕实际的像素点数。4K 屏 = 3840×2160 物理像素。

**逻辑像素**(Logical Pixel):程序看到的像素数,经过 DPI 缩放。4K 屏 + scale=2.0 → 程序看 1920×1080 逻辑像素,每个"逻辑像素"实际占 2×2 物理像素。

**scale factor** = 物理 / 逻辑。

为什么搞两套?

- 1080p 时代:1 个程序像素 = 1 个屏幕像素,scale=1.0
- 4K 时代:屏幕点变密了,如果程序还按 1080p 像素画,东西看起来"很小"——文字看不清。设 scale=2.0,程序按 1080p 像素画,系统每个像素放大 2×2,看起来正常

操作系统帮你做这件事。winit 给你两个 API:

```rust
let logical: LogicalSize<u32> = window.inner_size().to_logical(session.scale_factor());
let physical: PhysicalSize<u32> = window.inner_size();  // 默认是物理

let scale = window.scale_factor();   // 1.0 / 1.25 / 1.5 / 2.0
```

游戏后缓冲**用物理像素**(因为像素就是物理的)。游戏逻辑**用逻辑像素或自定义世界坐标**(更稳定)。

### winit 的 resize 事件流

```
用户拖动窗口边缘
    ↓
窗口系统发 WM_SIZE / wl_surface.configure
    ↓
winit 把它转成 WindowEvent::Resized(PhysicalSize)
    ↓
你的 window_event 回调接收
    ↓
你调 surface.resize(new_w, new_h)
    ↓
下一次 RedrawRequested,buffer_mut() 返回新尺寸的缓冲
```

**关键时序**:`Resized` 在 `RedrawRequested` 之前到。如果你在 `RedrawRequested` 里才调 `surface.resize`,可能这帧的 `buffer_mut()` 还是旧尺寸——错位。

最安全的做法:**两个地方都 resize**(幂等操作,重复调没事):

```rust
WindowEvent::Resized(size) => {
    self.resize_surface(size);
}
WindowEvent::RedrawRequested => {
    self.resize_surface(window.inner_size());  // 兜底
    self.render();
}
```

### 0×0 处理

```rust
WindowEvent::Resized(PhysicalSize { width: 0, height: 0 }) => {
    // 窗口最小化,别 resize,跳过
    return;
}
```

`NonZeroU32::new(0)` 返回 `None`,`unwrap()` 会 panic。必须显式判断。

### ScaleFactorChanged 事件

```rust
WindowEvent::ScaleFactorChanged {
    scale_factor,
    inner_size_writer,
} => {
    println!("Scale factor changed to {}", scale_factor);
    // inner_size_writer 让你决定新尺寸(默认按比例缩放)
}
```

这个事件在用户拖窗口到不同 DPI 的显示器时触发(比如从 1080p 拖到 4K)。游戏一般不特殊处理,接受默认行为。

## 3 · 四域深入

### 3.1 · 🎨 图形学视角

#### 分辨率独立渲染

理想游戏架构:

- **游戏世界坐标**:固定,如 1920×1080(或物理世界单位,如米)
- **后缓冲尺寸**:匹配窗口物理像素
- **渲染**:把世界坐标投影到后缓冲,自动 scale

这样不管玩家窗口多大,游戏世界逻辑不变,只是渲染时缩放。Casey 在 Day 100+ 才分离这两个概念,但前期就该想清楚。

我们 Phase 1 简化:**后缓冲 = 窗口物理尺寸**(不区分)。Day 8 暂时这样。

#### 多窗口多显示器

```rust
// 用 MonitorHandle 枚举显示器
let monitors = event_loop.available_monitors();
for m in monitors {
    println!("Monitor: {}, {}x{}, scale {}",
             m.name().unwrap_or("?".into()),
             m.size().width, m.size().height,
             m.scale_factor());
}
```

游戏可能跨多显示器(全屏主显示器 + 副屏调试 UI)。窗口可以"拖到另一个显示器"——触发 ScaleFactorChanged + Resized。

### 3.2 · 🐧 Linux 系统编程视角

#### X11 的 resize

X11 通过 `ConfigureNotify` 事件报告窗口大小变化。X server 主动 push,你的程序 receive。

X11 还报告"窗口位置变化"(Move) 和"z-order 变化"(RaiseWindow)等,一堆事件。winit 把它们过滤分类。

#### Wayland 的 resize

Wayland 设计不同——**客户端不能自己改窗口大小**。窗口大小由"窗口装饰(XDG toplevel)"协商:

1. 用户拖边缘 → compositor 收到
2. compositor 发 `wl_surface.configure` 给客户端
3. 客户端必须接受新尺寸,attach 新 buffer

所以 Wayland 下,你**不能** `window.set_inner_size(...)` 强制改大小(compositor 可以无视)。只能 `request_inner_size`,compositor 决定。

这是 Wayland 安全模型一部分(防恶意客户端"霸屏")。

#### DPI 在 Linux 上

- X11:DPI 通过 `Xft.dpi` X resource 配置,或 `xrandr --dpi`
- Wayland:每个显示器独立 DPI,compositor 自动 mix

winit 抽象了这些差异,你只看 `scale_factor`。

### 3.3 · 🦀 Rust 生态视角

#### 类型系统防 0×0

```rust
use std::num::NonZeroU32;

surface.resize(
    NonZeroU32::new(w)?,
    NonZeroU32::new(h)?,
)?;
```

`NonZeroU32` 在编译期保证非 0,`new(0)` 返回 `None`。`?` 把 `Option` 转 `Result`,把 `None` 转 `Err`。这强迫你处理 0×0 情况。

#### `PhysicalSize` 和 `LogicalSize`

```rust
let phys: PhysicalSize<u32> = window.inner_size();
let logical: LogicalSize<f64> = phys.to_logical(window.scale_factor());
let phys_again: PhysicalSize<u32> = logical.to_physical(window.scale_factor());
```

winit 用泛型类型表达单位,避免混淆。Rust 类型系统保证你不会"把逻辑像素当物理像素用"。

#### App 状态结构

```rust
struct App {
    window: Option<Window>,
    surface: Option<Surface>,
    /// 当前后缓冲尺寸(物理像素)
    bb_size: PhysicalSize<u32>,
}
```

`bb_size` 记录当前缓冲尺寸。每次 resize 更新。render 时用这个值,而不是 `window.inner_size()`(可能不一致)。

### 3.4 · 🎮 游戏编程视角

#### 游戏对 resize 的处理策略

1. **即时调整**(我们用):resize → 立刻重分配 → 下一帧用新尺寸。简单,但 resize 频繁时性能差。
2. **延迟调整**:resize 标记 dirty,主循环每秒最多重分配 1 次。流畅但有时序复杂。
3. **固定逻辑分辨率**:后缓冲永远是 1920×1080,显示时按窗口大小缩放。游戏逻辑简单。

商业游戏用第 3 种。"游戏画面"和"窗口"解耦。Day 100+ 我们也会走这条路。

#### 全屏切换

```rust
// 切到全屏
window.set_fullscreen(Some(Fullscreen::Borderless(None)));

// 切回窗口
window.set_fullscreen(None);
```

全屏切换会触发 Resized(物理尺寸变成屏幕尺寸)。游戏一般按 F11 切换。

## 5 · 对照与变奏

### 不同平台 resize

| 平台 | 谁能改窗口大小 |
|---|---|
| Windows | 程序 + 用户都可(通过 `SetWindowPos` / 拖边缘) |
| macOS | 程序 + 用户都可 |
| X11 | 程序 + 用户都可 |
| Wayland | **只有 compositor 能**;程序只能请求 |

Wayland 是个特例,体现"安全优先"的现代设计。

### HiDPI 历史

- **1980s-2010s**:显示器 96 DPI 是标准
- **2014**:Apple 推出 Retina iMac(5K),macOS 引入"_scale=2.0"模型
- **2015+**:Windows 10 改进 DPI 处理(Per-monitor v2)
- **2020+**:4K / 8K 显示器普及,所有 OS 都支持 HiDPI

游戏开发者必须考虑 HiDPI,否则在 Retina / 4K 屏上文字看起来像针尖。

### Casey 在 Win32 处理 resize

Casey 在 `WM_SIZE` 直接调 `Win32ResizeDIBSection`,简单粗暴。但他**不处理 DPI**——Casey 假设 96 DPI(Windows 默认)。如果用户在 Retina 屏跑 Casey 的代码,画面会"太小"。

我们这边 winit 帮我们处理 DPI,所以代码稍复杂,但功能完整。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 resize 时要"丢弃旧后缓冲内容",而不是保留?

**参考解答**:

游戏选丢弃,原因:

1. **下一帧会重画整个画面**:旧内容没用,不丢也会被覆盖
2. **保留要拷贝**:旧 W×H 拷到新 W×H,可能拉伸(模糊)或留边(难看)
3. **简化逻辑**:不拷贝 = 代码简单 + 没有"半旧半新"中间态

GUI 应用选保留(用户输入不能丢),但游戏选丢弃是合理工程决策。

代价:resize 那一瞬间,新缓冲可能是**未初始化内存**(随机像素)或全黑。我们用 `vec![0; w*h]` 确保全黑(下一帧立刻覆盖)。

### Lv2 · 动手实践

**题**:在 Day 6 代码基础上加 resize 处理。完成标准:

- 拖动窗口边缘改大小,渐变正确填充新尺寸
- 最小化窗口(任务栏),不崩溃
- 最大化 / 还复,正确响应
- 在终端打印新尺寸(便于调试)

**参考解答**:

```rust
// 在 window_event 里
fn window_event(
    &mut self,
    _event_loop: &ActiveEventLoop,
    _id: WindowId,
    event: WindowEvent,
) {
    match event {
        WindowEvent::CloseRequested => std::process::exit(0),

        WindowEvent::Resized(size) => {
            // 注意:0×0 最小化,跳过
            if size.width > 0 && size.height > 0 {
                println!("Resized to {}x{}", size.width, size.height);
                if let Some(surface) = &mut self.surface {
                    surface.resize(
                        NonZeroU32::new(size.width).unwrap(),
                        NonZeroU32::new(size.height).unwrap(),
                    ).unwrap();
                }
                self.bb_size = size;
            } else {
                println!("Window minimized (size 0x0), skipping");
            }
        }

        WindowEvent::ScaleFactorChanged {
            scale_factor,
            inner_size_writer,
        } => {
            println!("Scale factor changed to {}", scale_factor);
            // 不调 inner_size_writer,接受默认(按比例缩放)
        }

        WindowEvent::RedrawRequested => {
            self.render();
        }

        _ => ()
    }
}

fn render(&mut self) {
    let surface = self.surface.as_mut().unwrap();
    let window = self.window.as_ref().unwrap();
    let size = window.inner_size();
    let (w, h) = (size.width, size.height);
    if w == 0 || h == 0 { return; }

    // 兜底:确保 surface 尺寸匹配
    surface.resize(
        NonZeroU32::new(w).unwrap(),
        NonZeroU32::new(h).unwrap(),
    ).unwrap();

    let mut buffer = surface.buffer_mut().unwrap();
    // ... 用 w, h 填像素
    buffer.present().unwrap();
}
```

### Lv3 · 迁移设计

**题**:你想做"全屏切换":按 F11 在窗口和全屏间切换。如何实现?注意:

- 切换会触发 Resized
- 全屏时 mouse cursor 应隐藏
- 全屏时不能用 Escape 退出(改用 F11 / Alt+Enter)

写出关键代码骨架。

**提示**:

```rust
// 状态

KeyCode::F11 => {
    let window = self.window.as_ref().unwrap();
    if self.is_fullscreen {
        window.set_fullscreen(None);
        window.set_cursor_visible(true);
        self.is_fullscreen = false;
```

- Exclusive:独占显示模式,切换时屏幕短暂黑屏。延迟最低。

游戏一般 Borderless(用户体验好,切换快)。

## 8 · Rust / Arch 落地代码

### 完整 resize + DPI 处理片段

```rust
// src/main.rs 的关键部分

use std::num::NonZeroU32;
use winit::dpi::{LogicalSize, PhysicalSize};
use winit::window::Window;

struct App {
    window: Option<Window>,
    surface: Option<Surface>,
    /// 后缓冲尺寸(物理像素),resize 时更新
    bb_size: PhysicalSize<u32>,
    /// 上次报告的 scale factor(用于打印 DPI 变化)
    last_scale: f64,
}

impl App {
    fn handle_resize(&mut self, new_size: PhysicalSize<u32>) {
        if new_size.width == 0 || new_size.height == 0 {
            println!("Skipping zero-size resize");
            return;
        }
        if new_size == self.bb_size {
            return;  // 没变化,跳过
        }
        println!("Resizing backbuffer: {:?} -> {:?}",
                 self.bb_size, new_size);

        if let Some(surface) = &mut self.surface {
            surface.resize(
                NonZeroU32::new(new_size.width).unwrap(),
                NonZeroU32::new(new_size.height).unwrap(),
            ).expect("surface.resize failed");
        }
        self.bb_size = new_size;
    }

    fn handle_scale_change(&mut self, new_scale: f64) {
        if (new_scale - self.last_scale).abs() < 0.001 {
            return;
        }
        println!("Scale factor: {} -> {}", self.last_scale, new_scale);
        self.last_scale = new_scale;
    }
}
```

### Troubleshooting

- **resize 后变黑**:`surface.resize` 没调,或调了但 buffer_mut 之前还是旧尺寸。两个地方都调 resize。
- **panic "NonZero"**:0×0 没处理。在 Resized 分支判断 `width > 0 && height > 0`。
- **resize 慢/卡**:每次 resize 重分配 4MB,频繁触发卡。可以用 `Arc<Mutex<Vec<u32>>>` 复用内存。或者节流(每秒最多 resize 一次)。
- **DPI 切换后字体糊**:你的字体是位图,不是矢量。用 vector 字体(我们 Day 70+ 会用 `glyphon`)。
- **Wayland 下 set_inner_size 无效**:Wayland 不让客户端改大小,这是设计。改用 set_fullscreen 或 xdg toplevel 请求。

### Rust 模式:clamp_min_size 辅助函数

```rust
fn clamp_min_size(size: PhysicalSize<u32>, min_w: u32, min_h: u32) -> PhysicalSize<u32> {
    PhysicalSize::new(
        size.width.max(min_w),
        size.height.max(min_h),
    )
}

// 用法:
let safe_size = clamp_min_size(new_size, 320, 240);  // 最小 320x240
```

这避免窗口太小看不清。
