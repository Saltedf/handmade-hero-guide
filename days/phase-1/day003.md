
# Day 003 · 分配后缓冲:Vec<u32> 与 softbuffer

> 有了窗口还没用——我们想在屏幕上画像素。今天分配一块"后缓冲"(backbuffer):一个 `Vec<u32>`,每 32 位代表一个像素的颜色。然后用 `softbuffer` 把这块内存贴到窗口上。跑完后,你的窗口会显示**纯绿色**——第一次真正画像素。

## 0 · 为什么要有这一天

Day 2 你打开了一个空白窗口,白色背景,winit 在等你渲染。但 winit 自己**不能渲染**——它只是窗口管理器。要画像素,需要另一层 API。

你大概会问:为什么不直接 `window.set_pixel(x, y, color)`?因为现代窗口系统**不让你这么干**。原因:

1. **性能**:每次画一个像素都做系统调用,慢到不可接受(60 FPS 1280×720 = 1.1 亿次调用/秒)
2. **同步**:你画的时候屏幕可能正在显示这一帧,画一半看到撕裂(tearing)
3. **空间**:屏幕分辨率变化时,你的"像素数组"要 resize

所以**所有现代窗口系统**都让你:

1. 在**自己的进程内存里**画一帧(几百万像素,完全 CPU 操作,无系统调用)
2. 把这整帧"提交"(present)给窗口系统
3. 窗口系统和 GPU / 显示驱动把这帧贴到屏幕(可能用 DMA,极快)

这块"自己的内存"就叫**后缓冲**(backbuffer)。**前缓冲**(frontbuffer)是屏幕正在显示的那块——你永远不直接画前缓冲。

Casey Day 3 的核心动作就是:**在游戏内存里分配一块 `BITMAPINFO` + 一块 byte 数组,画完用 `StretchDIBits` 提交给 Windows GDI**。我们在 Rust 里等价做法:

- 后缓冲:`Vec<u32>`(每个像素 4 字节,RGBA 或 XRGB)
- 提交:`softbuffer` crate(把 `&[u32]` 贴到 winit 窗口)

**心理锚点**:读完今天,你能:

- 解释"后缓冲 / 前缓冲"双缓冲模型,知道为什么不能直接画屏幕
- 用 `Vec<u32>` 分配一块 `width * height` 的像素缓冲
- 用位运算把 RGB 三个值编码成 32 位像素
- 用 `softbuffer::Surface` 把 `Vec<u32>` 贴到 winit 窗口
- 跑出第一个绿色窗口

## 1 · Casey 今天做了什么

Casey Day 3 的核心动作:

1. 在 `win32_handmade.cpp` 里定义全局后缓冲:`BITMAPINFO BitmapInfo; void *BitmapMemory; int BitmapWidth; int BitmapHeight;`
2. 写 `Win32ResizeDIBSection(Width, Height)`:用 `CreateDIBSection`(Win32 GDI 函数)分配一块 Windows 管理的位图内存,拿到指针 `BitmapMemory`
3. 在 `WindowProc` 的 `WM_SIZE` 分支里调 `Win32ResizeDIBSection(width, height)`(窗口大小变 → 后缓冲重分配)
4. 在 `WindowProc` 的 `WM_PAINT` 分支里调 `StretchDIBits(hdc, ..., BitmapMemory, &BitmapInfo, ...)` 把后缓冲贴到窗口
5. 跑起来,**还没画任何东西**,所以窗口是黑屏。但"画一个像素就能显示"的管道已经搭好

我们 Rust 翻译:`Vec<u32>` 替代 `CreateDIBSection`,`softbuffer` 替代 `StretchDIBits`,逻辑同构。

Casey 还讲了一个细节:**字节对齐**。Windows GDI 要求位图每行字节数 4 字节对齐(因为 CPU 一次读 4 字节)。我们 `Vec<u32>` 天然 4 字节对齐(每个元素就是 4 字节),所以不用额外处理。但理解这个对齐概念很重要,后面讲性能(SIMD)还会回来。

## 2 · 心智模型

### 类比:后缓冲是"草稿纸"

你画画时不会直接在画布上画——会先用铅笔打草稿,擦改几遍,满意了再描上去。**后缓冲是草稿纸,前缓冲是最终画布**。

```
你的程序 ──画──> 后缓冲(草稿)
                    │
                    │ 提交(present)
                    ▼
              前缓冲(画布,屏幕正在显示)
```

"提交"是个原子操作——要么整块都到前缓冲,要么都没有。这就是**双缓冲**(double buffering)。**三缓冲**(triple buffering)多一个缓冲,允许 GPU 在画第 N+1 帧时 CPU 已经在画 N+2 帧,适合高帧率。

### 像素在内存里长什么样

一个像素 = 红 + 绿 + 蓝三个分量。每个分量 8 位(0~255),共 24 位。但现代 CPU 偏好 32 位对齐,所以**每个像素用 32 位(4 字节)**,多出来的 8 位要么不用(X),要么放 alpha(透明度,A)。

两种主流格式:

| 格式 | 字节顺序(内存地址 0 → 3) | 备注 |
|---|---|---|
| `XRGB8888`(也叫 `0RGB`) | X, R, G, B(小端:0x00RRGGBB) | Windows GDI / softbuffer 默认 |
| `ARGB8888` | A, R, G, B | 带 alpha |
| `RGBA8888`(字节序) | R, G, B, A | Web (`<canvas>`)常用 |
| `BGRA8888` | B, G, R, A | macOS Core Graphics |

我们 Rust 这边用 softbuffer,它默认要 `XRGB8888`,即 `0x00RRGGBB` 在 u32 里(小端机器上,内存里实际是 `BB GG RR 00`)。

**编码公式**:

```rust
fn pack_rgb(r: u8, g: u8, b: u8) -> u32 {
    // r/g/b 0-255,转成 0x00RRGGBB
    ((r as u32) << 16) | ((g as u32) << 8) | (b as u32)
}

// 解码:
fn unpack_rgb(pixel: u32) -> (u8, u8, u8) {
    let r = ((pixel >> 16) & 0xFF) as u8;
    let g = ((pixel >> 8) & 0xFF) as u8;
    let b = (pixel & 0xFF) as u8;
    (r, g, b)
}
```

**位运算解释**:

- `<< 16` — 左移 16 位。`r = 0xAB = 10101011`,左移 16 后是 `0xAB0000`,放在 u32 的高 8 位(位置 16-23)
- `|` — 按位或。`0xAB0000 | 0x00CD00 | 0x0000EF` = `0xABCDEF`,把三段拼起来
- `& 0xFF` — 按位与。`0xAB & 0xFF = 0xAB`,提取最低 8 位
- `>> 16` — 右移 16 位,把高 8 位挪到低 8 位

**绿色像素**:`pack_rgb(0, 255, 0)` = `0x0000FF00`。后缓冲里全填这个值,窗口就是纯绿色。

### `Vec<u32>`:Rust 的"动态数组"

```rust
let width = 1280;
let height = 720;
let mut backbuffer: Vec<u32> = vec![0; width * height];

// backbuffer.len() == 921_600
// backbuffer 的内存布局:连续 921600 * 4 = 3_686_400 字节
// 在堆(heap)上分配,由 Rust 的 allocator 管
```

**关键概念**:

- `Vec<u32>` 是个"胖指针"——含 `{ ptr, len, capacity }` 三字段
- `ptr` 指向堆上连续的 `u32` 数组
- `len` 是当前元素数,`capacity` 是已分配容量(`capacity >= len`)
- `vec![0; N]` 等价于 `Vec::with_capacity(N)` + 把前 N 个填 0
- 当 `len == capacity` 还要 push,Vec 自动扩容(capacity * 2,新分配,memcpy 旧数据,释放旧)

**为什么不用 `[u32; 921600]`?** 因为数组大小必须是编译期常量,1280×720 写死,改分辨率要改代码。`Vec<u32>` 运行时分配,任意大小。

**为什么不用 `Box<[u32]>`?** `Box<[u32]>` 也行——它没有 capacity(固定长度),内存稍小。但游戏窗口 resize 频繁,`Vec` 能复用容量(只在变更大时重分配),`Box<[u32]>` 每次 resize 都要重分配。所以 **`Vec<u32>` 是首选**。

### softbuffer:把 Vec<u32> 贴到窗口

`softbuffer` 是 Rust 生态最简单的"CPU 像素 → 屏幕"库。它的工作:

1. 你给它一个 winit 的 `Window`,它创建一个 `Surface`(渲染表面)
2. 你调 `surface.resize(width, height)`,它准备好接受新尺寸的像素
3. 你调 `surface.buffer_mut()`,它给你一个 `&mut [u32]`(它内部的缓冲,长度 = width*height)
4. 你往里写像素值
5. 你调 `buffer.present().unwrap()`,它把这帧提交给窗口系统

```rust
use softbuffer::Surface;
use std::num::NonZeroU32;

// 创建 surface(在 window 已经创建之后)
let context = softbuffer::Context::new(display_handle)?;
let mut surface = context.create_surface(window_handle)?;

// 每帧:
surface.resize(NonZeroU32::new(width)?, NonZeroU32::new(height)?)?;
let mut buffer = surface.buffer_mut()?;
for pixel in buffer.iter_mut() {
    *pixel = 0x0000FF00;  // 绿色
}
buffer.present()?;
```

**关键 API**:

- `Context::new(display_handle)` — 创建上下文,需要 winit 窗口的 `DisplayHandle`
- `Surface::new(context, window_handle)` — 创建表面,需要 `WindowHandle`
- `resize(w, h)` — 告诉 softbuffer 接下来要这个尺寸的像素
- `buffer_mut()` — 拿到可写缓冲
- `present()` — 提交

**`NonZeroU32` 是什么?** Rust 的 `u32` 可以是 0,但 `resize(0, 0)` 没意义。`NonZeroU32` 编译期保证非 0,让 softbuffer 内部不用运行时检查。这是 Rust 的"零成本抽象"经典例子——类型系统帮你消除运行时检查。

### winit + softbuffer 接线

winit 的 `Window` 没有直接给 softbuffer 的 `WindowHandle`,要用 `rwh_06`(raw-window-handle 0.6)trait 转换:

```rust
use raw_window_handle::HasWindowHandle;

let window_handle = window.window_handle()?;
let surface = context.create_surface(window_handle?)?;
```

winit 实现了 `HasWindowHandle`,所以 `window.window_handle()` 返回 `Result<WindowHandle>`。softbuffer 接受这个 trait object,内部根据平台拿到真正的 HWND / X11 Window / Wayland surface。

这是 Rust 生态的"分离依赖"模式——winit 和 softbuffer 不直接知道对方,通过 `raw-window-handle` 这个共享 trait 通信。这让任何窗口库(GLFW、SDL)都能配合任何渲染库。

## 3 · 四域深入

### 3.1 · 🎨 图形学视角

#### 像素和颜色空间

我们用 `XRGB8888` 把 RGB 编码进 32 位。但**这些数值是线性的还是非线性的?**

**sRGB**(标准 RGB)是显示器默认的色彩空间,它是**非线性**的:数值 128 不是数值 0 的两倍亮度,而是大约 21.4% 亮度。因为人眼对暗色更敏感,sRGB 让有限位深(8 位)在人眼看来分布均匀。

这意味着**当你在后缓冲写 `(128, 128, 128)` 时,屏幕显示的灰度不是 50%,是 21.4%**。如果你想做光照计算(光叠加),必须先转线性空间,算完再转回 sRGB:

```
linear = sRGB_to_linear(sRGB_value)
linear_result = linear_a + linear_b
sRGB_result = linear_to_sRGB(linear_result)
```

公式:

```
sRGB → linear:
    if v <= 0.04045: linear = v / 12.92
    else: linear = ((v + 0.055) / 1.055) ^ 2.4
```

Casey 在 Phase 2 前期不深究这个——纯绿、纯红、纯蓝都是 sRGB 极值,不会暴露这个问题。Day 83+ 进入真实光照后,他要专门讨论 sRGB / Linear。**今天的你只需要知道"8 位像素值不是线性亮度"**,埋下这颗种子。

#### 双缓冲和 vsync

**双缓冲**(double buffer):后缓冲 + 前缓冲。CPU 画后缓冲,GPU/显示驱动把后缓冲 swap 到前缓冲。一次 swap 是原子的,避免撕裂。

**vsync**(vertical synchronization):swap 必须发生在显示器的"垂直消隐期"(vertical blanking interval,VBLANK),这是 CRT 显示器电子枪从屏幕底回到顶的时间。LCD 没有真正的 VBLANK,但保留了概念。

- 不开 vsync:CPU 画完立刻 swap,可能 swap 在屏幕刷新中途 → **画面撕裂**(上半旧帧下半新帧)
- 开 vsync:swap 等到 VBLANK → 无撕裂,但**帧率被锁定为显示器刷新率的整数倍**(60Hz 显示器:60 / 30 / 20 / 15 FPS,不能 50 FPS)
- 三缓冲(triple buffering):多一个缓冲,CPU 不必等 swap,但延迟增加一帧

softbuffer 默认开 vsync(取决于平台实现)。Day 18 我们讨论"如何强制帧率"。

#### 分辨率和 DPI

1280×720 是**逻辑像素**(logical pixel)还是**物理像素**(physical pixel)?

- 物理像素 = 屏幕上实际的像素点数(4K 屏 = 3840×2160 物理像素)
- 逻辑像素 = 程序看到的像素数(可能被 DPI scaling 缩放)
- scale factor = 物理 / 逻辑(4K 屏 + scale 2.0 = 逻辑 1920×1080)

winit 区分:`PhysicalSize` 和 `LogicalSize`。softbuffer 用**物理像素**(因为像素是物理的)。Day 8 处理 resize 时会展开。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上 softbuffer 怎么把 `Vec<u32>` 贴到窗口?**取决于窗口系统**:

- **X11**:用 `XShmPutImage`(MIT-SHM 扩展,共享内存)或 `XPutImage`(普通拷贝)。前者通过 `shmget` 创建共享内存段,CPU 写、X server 读,无 copy。
- **Wayland**:用 `wl_shm` 协议,绑定共享内存文件(fd 传递),compositor 直接读。
- **DRM / KMS**(无窗口系统,直接 framebuffer):写到 `/dev/fb0` 或通过 DRM ioctl。softbuffer 不直接支持,要 `kms` crate。

**用 strace 看 softbuffer 调了哪些 syscall**:

```bash
strace -f -e trace=mmap,openat,ioctl target/debug/handmade-hero 2>&1 | head -50
# 应该看到:
# openat(AT_FDCWD, "/proc/self/fd/...", ...) = ...
# mmap(NULL, 3686400, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0) = ...
# (在 X11 上还会看到 ioctl(fd, X11_SHM_*) )
```

`mmap` 是 Linux 的"内存映射"syscall——把文件或共享内存段映射到进程地址空间,读写这段内存等价于读写文件。softbuffer 用 mmap 共享像素缓冲给 X server / Wayland compositor。

**和 Win32 的对照**:

| 操作 | Win32 | Linux X11 | Linux Wayland |
|---|---|---|---|
| 分配共享内存 | `CreateDIBSection` | `shmget` + `shmat` | `mmap` + memfd |
| 拷贝像素到窗口 | `StretchDIBits` | `XShmPutImage` / `XPutImage` | `wl_surface_attach` + `wl_surface_commit` |
| vsync | D3D / OpenGL swap | XRandR / GLX | Wayland presentation feedback |

softbuffer 把这些差异全藏起来。

### 3.3 · 🦀 Rust 生态视角

#### Vec<u32> 的所有权和生命周期

```rust
struct App {
    backbuffer: Vec<u32>,   // 拥有这块堆内存
    width: usize,
    height: usize,
}
```

`backbuffer` 是 App 的字段,App 拥有它。App drop 时(程序退出),Vec drop 自动释放堆内存——Rust 的 RAII。**Casey 在 C 里要手动 `VirtualFree(BitmapMemory)`,容易忘 → 内存泄漏**。

#### Slice(&[u32] 和 &mut [u32])

softbuffer 的 `buffer_mut()` 返回 `&mut [u32]`,一个**可变借用**(mutable borrow)。

```rust
let mut backbuffer: Vec<u32> = vec![0; 1280 * 720];
let slice: &mut [u32] = &mut backbuffer;   // 借用
slice[0] = 0x00FF0000;                       // 写第一个像素
```

`Vec<u32>` 和 `&mut [u32]` 关系:

- `Vec` 是 owned(拥有),长度可变,有 capacity
- `&mut [u32]` 是借用(不拥有),长度固定,但你可以读写
- 自动 deref:写 `backbuffer[0]` 等价 `(&mut backbuffer)[0]`

借用规则:**同一时刻只能有一个 `&mut`**,或多个 `&`。这保证内存安全——不会有"两个指针同时改 Vec"。

#### `NonZeroU32` 和类型驱动设计

```rust
use std::num::NonZeroU32;

let width = NonZeroU32::new(1280).unwrap();    // 编译期保证非 0
surface.resize(width, height)?;
```

如果你写 `NonZeroU32::new(0)`,返回 `None`(因为 0 无效)。`unwrap()` 在 `None` 时 panic。

softbuffer 的 `resize` 签名:`fn resize(&mut self, width: NonZeroU32, height: NonZeroU32) -> Result<()>`。**参数类型强制调用者保证非 0**,函数内部不用 `if width == 0` 检查。这是 Rust 的"parse, don't validate"哲学——把不变量编码进类型,而不是在运行时检查。

#### 完整 App 状态

```rust
use softbuffer::Surface;
use std::num::NonZeroU32;
use winit::window::Window;

struct App {
    /// 窗口(Option 因为 resumed 之前不存在)
    window: Option<Window>,
    /// softbuffer 表面(同样 Option)
    surface: Option<Surface>,
    /// 后缓冲
    backbuffer: Vec<u32>,
    /// 后缓冲尺寸(像素)
    bb_width: u32,
    bb_height: u32,
}
```

为什么 backbuffer 不放 Option?因为 `Vec<u32>` 的"空"状态就是 `vec![]`,不需要 Option 包裹。**别 Option 套 Vec / HashMap / String**,它们自己有空状态,套了反而是反模式。

### 3.4 · 🎮 游戏编程视角

#### 为什么 Casey 不用 OpenGL / D3D,而是用 GDI?

Casey 选择 GDI(`StretchDIBits`)而非 D3D / OpenGL,理由:

1. **教学透明度**:GDI 的"提交一块内存"模型最简单,你能看清每一步
2. **跨平台对应物**:每个 OS 都有等价物(X11 XShm,Wayland wl_shm,macOS CGImage)
3. **延迟可控**:CPU 直接写,没有驱动黑盒
4. **软件渲染是底层基础**:你后面写 SIMD、写多线程、写光栅化器,都在 CPU 上,后缓冲是这些的"出口"

#### 后缓冲尺寸 = 窗口尺寸?

不一定。两种策略:

- **匹配窗口尺寸**:每次 resize 重分配后缓冲。简单,但 resize 时卡顿(分配几十 MB 内存)
- **固定逻辑分辨率**:后缓冲固定 1920×1080,显示时按窗口大小缩放。简化游戏逻辑(永远 1920×1080 的世界坐标),代价是 resize 时画质模糊

Casey 早期(Day 3-5)用第一种,后面(Day 100+)切第二种(渲染分辨率和游戏分辨率分离)。Phase 1 我们先用第一种,够用。

## 5 · 对照与变奏

### Win32 GDI vs softbuffer

| 操作 | Win32 GDI(C) | softbuffer(Rust) |
|---|---|---|
| 分配后缓冲 | `CreateDIBSection(...)` 拿 `HBITMAP` + `void*` | `Vec<u32>`(或 `surface.buffer_mut()`) |
| 像素格式 | `BITMAPINFO` 描述(biBitCount=32) | 隐式 `XRGB8888` |
| 提交 | `StretchDIBits(hdc, ..., bits, &bmi, ...)` | `buffer.present()` |
| Resize | 调用 `DeleteObject` + `CreateDIBSection` 重分配 | `surface.resize(w, h)` |
| 内存所有权 | 手动管理(易泄漏) | RAII(Vec drop 自动释放) |

### 不同像素格式对照

| 格式 | 内存(LSB → MSB) | 用于 |
|---|---|---|
| XRGB8888 | B, G, R, X(小端) | softbuffer / GDI |
| RGBA8888 | R, G, B, A | Web canvas, SDL |
| BGRA8888 | B, G, R, A | macOS |
| RGB565 | R5 G6 B5(16 位) | 嵌入式 / 老 GPU |
| RGBA16F | 4 个 16 位浮点 | HDR 渲染 |

softbuffer 0.30+ 默认 XRGB8888,但部分平台支持其他格式(通过 feature)。

### 历史演化

- **1980s**:Windows GDI + `BITMAPINFO`,VGA 显卡的 frame buffer
- **1990s**:OpenGL / DirectX 引入硬件加速 + 双缓冲 + vsync
- **2000s**:渲染到纹理(render-to-texture)出现,后缓冲从 CPU 移到 GPU
- **2010s**:Wayland 引入显式 `wl_shm`,客户端共享内存直接给合成器
- **2020s**:Vulkan / DX12 暴露多缓冲细节,程序可控 swapchain

softbuffer 是这条演化线的**简化版**——只暴露"画 + 提交",把所有复杂细节藏起来,适合教学和 2D 软件。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不能"直接画前缓冲",必须用后缓冲?如果只有一块缓冲,会发生什么?

**参考解答**:

假设只有一块缓冲,CPU 直接写它,屏幕显示它。问题:

1. **撕裂(tearing)**:CPU 写到一半(比如写完了上半屏),屏幕扫到下半屏开始读——上半是新的、下半是旧的,中间出现一条明显的"撕裂线"
2. **不可见更新**:你画一个像素,但屏幕扫过了那个位置,要等下一帧才看到,导致动画看起来卡
3. **数据竞争**:CPU 写 + 显示控制器读,无同步,可能读到中间状态

后缓冲让 CPU 在自己的"草稿纸"上画完一整帧,然后**原子地** swap 给前缓冲。swap 发生在 VBLANK(屏幕扫完一帧回到顶端的间隙),保证整帧一起更新。

### Lv2 · 动手实践

**题**:在 Day 2 代码基础上,加 softbuffer,让窗口显示**纯绿色**(RGB = 0, 255, 0)。完成标准:`cargo run` 后窗口一片纯绿,无报错。

**参考解答**:

```bash
# 加依赖
cargo add softbuffer
cargo add raw-window-handle
```

```rust
// src/main.rs

use raw_window_handle::HasWindowHandle;
use softbuffer::Surface;
use std::num::NonZeroU32;
use winit::application::ApplicationHandler;
use winit::event::WindowEvent;
use winit::event_loop::{ActiveEventLoop, EventLoop};
use winit::window::{Window, WindowId};

struct App {
    window: Option<Window>,
    surface: Option<Surface>,
}

impl App {
    fn new() -> Self {
        Self { window: None, surface: None }
    }
}

impl ApplicationHandler for App {
    fn resumed(&mut self, event_loop: &ActiveEventLoop) {
        // 1. 创建窗口
        let attrs = Window::default_attributes()
            .with_title("Handmade Hero — Day 3")
            .with_inner_size(winit::dpi::LogicalSize::new(1280, 720));
        let window = event_loop.create_window(attrs).unwrap();

        // 2. 创建 softbuffer 上下文和 surface
        // Context 需要 display handle(从 event_loop 拿)
        let context = unsafe {
            softbuffer::Context::new(
                event_loop.display_handle().unwrap().clone()
            )
        }.unwrap();
        let surface = unsafe {
            context.create_surface(
                window.window_handle().unwrap().unwrap().clone()
            )
        }.unwrap();

        // 3. 保存
        self.window = Some(window);
        self.surface = Some(surface);

        // 4. 立刻触发一次重画(让窗口一显示就是绿色)
        if let Some(w) = &self.window {
            w.request_redraw();
        }
    }

    fn window_event(
        &mut self,
        _event_loop: &ActiveEventLoop,
        _id: WindowId,
        event: WindowEvent,
    ) {
        match event {
            WindowEvent::CloseRequested => {
                std::process::exit(0);
            }
            WindowEvent::RedrawRequested => {
                self.render();
            }
            WindowEvent::Resized(physical_size) => {
                // 让 softbuffer 知道新尺寸
                if let Some(surface) = &mut self.surface {
                    if physical_size.width > 0 && physical_size.height > 0 {
                        surface.resize(
                            NonZeroU32::new(physical_size.width).unwrap(),
                            NonZeroU32::new(physical_size.height).unwrap(),
                        ).unwrap();
                    }
                }
            }
            _ => ()
        }
    }
}

impl App {
    fn render(&mut self) {
        let surface = self.surface.as_mut().unwrap();
        let window = self.window.as_ref().unwrap();

        // 拿窗口物理尺寸
        let size = window.inner_size();
        let (w, h) = (size.width, size.height);
        if w == 0 || h == 0 { return; }

        // 拿到可写缓冲
        let mut buffer = surface.buffer_mut().unwrap();

        // 全部填绿色 XRGB8888 = 0x00FF00(注意 R 在高位)
        // pack(0, 255, 0) = (0 << 16) | (255 << 8) | 0 = 0x0000FF00
        for pixel in buffer.iter_mut() {
            *pixel = 0x0000FF00;
        }

        // 提交
        buffer.present().unwrap();
    }
}

fn main() {
    let event_loop = EventLoop::new().unwrap();
    let mut app = App::new();
    event_loop.run_app(&mut app).unwrap();
}
```

**关键点**:

- `unsafe { Context::new(...) }` — softbuffer 0.4 的 API 要求 `unsafe`,因为它要求 `HasDisplayHandle` 的实现保证线程安全(我们的 winit 满足)。Rust 把这个责任转给调用者。
- `event_loop.display_handle()` — 拿到 display handle(代表整个连接,不是单个窗口)
- `window.window_handle()` — 拿到 window handle(代表具体窗口)
- `window.request_redraw()` — 主动要求重画(否则窗口要等系统催才画)
- `WindowEvent::Resized` 分支 resize surface(否则窗口变大后,缓冲还是旧尺寸,显示错位)

### Troubleshooting

- `error: failed to create surface` — display handle 没传对,检查 `Context::new` 参数
- 窗口出现但空白 / 黑屏 — `request_redraw()` 没调,或在 `RedrawRequested` 没真的渲染
- resize 后变黑 — `WindowEvent::Resized` 分支没调 `surface.resize`
- panic `buffer length mismatch` — 后缓冲尺寸和 surface 期望不符,确认 resize 在 buffer_mut 之前
- 编译时 `linker 'cc' not found` — `sudo pacman -S base-devel`(装 linker)
