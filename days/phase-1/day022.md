# Day 022 · 瞬时实时代码编辑:更细粒度的 reload

> Day 021 实现了热重载——每帧检查 mtime,变了就 reload。延迟最多 16ms(一帧)。听起来够快了,但 Casey 嫌不够。Day 022 探索**更细粒度**的 reload:游戏代码正在画 1000 个 sprite,你改代码,画第 501 个时就用新代码。这听起来不可能(函数正在执行怎么换?),Casey 这集尝试几种方案。这集的核心不是"找出最佳方案",而是**展示一种工程心态**:够用之后还问"能不能更好?"。Day 023 Casey 反思:过度工程化,退回帧级 reload。

## 0 · 为什么要有这一天

Day 021 的帧级 reload 在 60 FPS 下延迟 16.67ms。听起来无感,但 Casey 提出一个场景:

你在调试渲染管线,每帧画 10000 个 sprite。你改一行 shader 代码,reload,**这帧的 5000 个 sprite 已经画完用旧代码**,5000 个用新代码。看起来应该一致——但实际你看到的是"5000 个旧 + 5000 个新"的混合画面,这帧的视觉效果不对。

如果 reload 在每帧**开始**时发生,你看到的是完整一帧新代码——但下一帧才是"完整新代码的完整帧",这一帧仍是过渡帧。

Casey 的需求:**reload 在画第 1 个 sprite 之前发生**,这样一帧内所有 sprite 用同一份代码。Day 021 已经做到——reload 在帧间。Day 022 探索更激进:**reload 在每个 sprite 之前都检查**。

听起来过度,但 Casey 在调试时确实有这种需求——一次调试多个相关变量,要立刻看到效果。16ms 延迟(60 FPS)他都觉得慢。

**心理锚点**:读完今天,你能:

- 解释"帧级 reload" vs "消息级 reload" vs "指令级 reload"的差别
- 知道为什么 Casey 想要消息级,又为什么退回帧级
- 理解 YAGNI 原则(You Aren't Gonna Need It)
- 写出"检查点"模式的代码(cooperative reload)
- 知道 OS 抢占式调度 vs 协作式调度的差别
- 解释为什么"反思 + 退回"是好的工程师品质

## 1 · Casey 今天做了什么

Day 022 Casey 的探索:

1. **识别问题**:Day 021 的帧级 reload 延迟 16ms,Casey 嫌不够快。
2. **设计方案 A:消息级 reload**——把整帧函数拆成"单步函数",平台层每步调一次。每步之间检查 reload。
3. **实现**:重构主循环,游戏代码不再是一次调用,而是多次小调用。
4. **测试**:跑起来,确实更细粒度。
5. **反思**:实现复杂度大幅上升,游戏代码要能"被打断",状态机变复杂。
6. **犹豫**:收益(快 16ms)vs 代价(代码复杂),值不值得?

Day 023 Casey 最终决定:**不值得,退回 Day 021 的帧级**。

这集教学的核心不是技术(代码并不复杂),而是**心态**:够用之后还能反思"能不能更好",尝试后觉得不值得能退回。**过度工程化是新手常见陷阱**(什么都想做完美),Casey 这集演示了反例。

## 2 · 心智模型

### 类比:reload 粒度像"餐厅上菜"

你点菜,厨师做。三种上菜方式:

**方式 A:整盘端上**(帧级 reload)——厨师做完一整道菜才端。如果你改菜单("加点辣"),要等下一道菜。
- 延迟:一道菜的时间(几分钟)
- 简单:厨师做完一道再做下一道

**方式 B:逐口喂**(消息级 reload)——厨师每做一口就端给你。改"加点辣",下一口就是辣的。
- 延迟:一口的时间(几秒)
- 复杂:厨师要边做边问"还做吗?改吗?"

**方式 C:分子级**(指令级 reload)——厨师做菜的每个分子都根据你的指令调整。
- 延迟:微秒
- 极复杂:需要 OS 抢占或 JIT

Casey Day 021 用 A,Day 022 试 B,Day 023 退回 A。

### 严谨:reload 粒度的实现

**帧级(Day 021)**:

```rust
loop {
    check_reload();              // 每帧开始时检查
    update_and_render();          // 整帧函数
    present();
}
```

reload 只在每帧**开始**发生。一帧 16ms 内 reload 不触发。最坏延迟 16ms。

**消息级(Day 022 尝试)**:

```rust
loop {
    check_reload();
    update_input();               // 步骤 1
    check_reload();
    update_physics();             // 步骤 2
    check_reload();
    update_ai();                  // 步骤 3
    check_reload();
    render_sprites();             // 步骤 4
    check_reload();
    present();
}
```

每步之间检查 reload。延迟最多一步(几 ms)。

**指令级**(理论):每个 CPU 指令后都能 reload。需要 OS 抢占式 + JIT,Casey 不做。

### 合作式 vs 抢占式 reload

**合作式(cooperative)**:游戏代码主动调 `check_reload()`,自己控制何时让出。Casey Day 022 用这种。
**抢占式(preemptive)**:OS 或运行时打断游戏代码,在任意指令处 reload。需要 OS 支持或 JIT。

合作式简单,但要求游戏代码"自觉"——程序员要在合适的位置加 `check_reload()`。如果忘了,那一段就不能 reload。

抢占式复杂,但游戏代码不用改——OS 自动打断。Linux 用信号(SIGINT / SIGUSR1)可以实现,但 reload 时机不确定。

业界都用合作式。抢占式只有 JIT 环境(V8 / JVM 的 HotSwap)能用。

### YAGNI 原则

**YAGNI**(You Aren't Gonna Need It):**别预先想象需求**。

Casey Day 022 的故事完美演绎:

1. Casey 想"也许我需要更细粒度 reload"
2. 设计 + 实现 消息级 reload
3. 用几天,发现"帧级完全够用"
4. 反思:消息级代码复杂,没收益
5. **退回帧级**

新手常犯的错:**先做再问**。Casey 的反思是"先问再做"——需求模糊时选简单方案,真的不够再优化。

YAGNI 不是"永远不优化",是"不预先优化"。Casey 在 HH 后期(Day 175+)做了大量性能优化,但都是**测过有需求**才做。

### 工程成熟度:能退回

Casey Day 022 → Day 023 退回。这种"敢于推翻自己代码"是工程成熟度的标志。

很多开发者舍不得删代码——"我花了一天写的,删了好可惜"。结果代码越堆越乱,后期没人敢动。Casey 这集展示:**写完审视,不够好就退回**。

实战:

- 你写了 200 行实现 X,跑起来发现 30 行的简单方案够用
- **新手**:留着 200 行(怕"万一以后用得上")
- **资深**:删 200 行,留 30 行。说明为什么删(commit message:"simplify X, 30 lines enough")

代码量不是资产,是负债。每行代码都要读、要改、要维护。少就是多。

### 反思:什么时候真的需要细粒度 reload?

Casey 退回帧级,因为 HH 不需要更细。但有些场景真的需要:

**需要细粒度 reload 的场景**:
- **长时间单帧**:光线追踪一帧 1 秒。reload 延迟 1 秒,不可接受。细粒度 reload 在每个像素采样之间。
- **批处理**:数据库迁移几小时。中途改算法,reload。
- **服务器**:Web 服务器进程不停,代码不停换。Java HotSwap、Erlang 热重载。

**不需要细粒度 reload 的场景**:
- **实时游戏**(HH):16ms 帧时间,reload 在帧间足够快
- **简单 GUI 应用**:60 FPS 足够
- **CLI 工具**:每次跑完就退出,没 reload 概念

Casey 的 HH 是"实时游戏",帧级 reload 够。你做"光线追踪器"或"Web 服务器",可能要细粒度。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏圈热重载粒度的实践:

**Unity**:每帧 reload(类似 Casey)。但 Unity 编辑器本身就是开发模式,概念略不同。
**Unreal**:每帧 reload(Hot Reload 插件)。
**Bevy**:目前不支持真热重载,只能"重启"。
**Emacs / Vim**:用户脚本可热重载,粒度到单个表达式。
**Lisp / Smalltalk**:函数级热重载,改函数立即生效(最细粒度,因为语言运行时支持)。

游戏圈主流是帧级 reload——16ms 对人感知够快,没必要更细。Casey Day 022 是少数探索更细粒度的案例。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上的"抢占式 reload":

**信号**:OS 在任意指令打断进程,调 signal handler。
```c
signal(SIGUSR1, reload_handler);
// 任意时刻收到 SIGUSR1,handler 运行
```
但 signal handler 里能做的事受限(不能 malloc、不能锁),不适合复杂 reload。

**ptrace**:debugger 用,可以单步、断点。性能差,不适合生产。

**ftrace / kprobe**:内核级 hook,改函数入口跳转。Linux 内核 livepatch 用。用户态也有类似工具(DynamoRIO、PIN)。

**JIT**:运行时生成代码,自然支持任意时刻 reload。Java / JS / C# 用。

实战命令:

```bash
# 给进程发信号(模拟"reload 请求")
kill -USR1 $(pgrep your-app)
# 进程的 SIGUSR1 handler 触发 reload

# 看 ftrace(内核 hook)
sudo cat /sys/kernel/debug/tracing/trace

# 看进程的 signal handlers
cat /proc/$(pgrep your-app)/status | grep Sig
# 输出:SigQ / SigPnd / SigShd 等
```

### 3.3 · 🦀 Rust 生态视角

Rust 没有 signal handler 的"优雅"方式——signal handler 里能做的事很受限(async-signal-safe 函数)。

Rust 推荐用 `signal-hook` crate:

```rust
use signal_hook::consts::SIGUSR1;
use signal_hook::flag;

let reload_flag = Arc::new(AtomicBool::new(false));
flag::register_usign(SIGUSR1, Arc::clone(&reload_flag))?;

// 主循环
loop {
    if reload_flag.swap(false, Ordering::SeqCst) {
        do_reload();
    }
    // ...
}
```

signal handler 只设 flag,主循环检查 flag——这是 async-signal-safe 模式。

Rust 的"协作式 reload"实现:

```rust
macro_rules! check_reload {
    ($app:expr) => {
        if $app.reload_requested.swap(false, Ordering::SeqCst) {
            $app.do_reload();
        }
    };
}

fn update_and_render(app: &mut App) {
    check_reload!(app);
    update_input(app);
    check_reload!(app);
    update_physics(app);
    check_reload!(app);
    // ...
}
```

宏让"加检查点"更简洁。Casey 在 C 里用宏。

### 3.4 · 软件工程:过度工程化

Casey Day 022 的教训:**别预先想象需求**。

新手常见过度工程化的例子:

1. **过早抽象**:写一个简单功能,先抽象成 trait / interface,加 5 个实现。"万一以后要换?"。实际只用了 1 个实现,trait 成了负担。
2. **过早优化**:写代码前先想"这能不能 SIMD / 多线程"。实际数据量 100 个,完全不需要。
3. **过早配置化**:把硬编码的常量做成 config 文件。"万一以后要调?"。实际不调,config 反而难懂。
4. **过早通用化**:写一个解析器,设计成"支持任意格式"。实际只解析一种格式。

**实战 YAGNI**:

写代码前问自己:

- "现在有需求吗?"(不是"将来可能有")
- "简单方案能用吗?"(不是"复杂方案更优雅")
- "测过有性能问题吗?"(不是"我觉得应该会慢")

如果三个都"否",用简单方案。Casey Day 022 → Day 023 是这个原则的应用。

## 5 · 对照与变奏

### 同一概念:粒度选择

粒度选择在所有工程领域:

| 领域 | 粗粒度 | 细粒度 |
|---|---|---|
| 版本控制 | 一次 commit 一周工作 | 一个 commit 一个字符 |
| 数据库 transaction | 一个大事务 | 多个小事务 |
| 内存管理 | 整个程序 GC | 每对象手动 free |
| 网络 | 一次传 1MB | 一次传 1KB |
| UI 反馈 | 点击后 1 秒响应 | 鼠标移动即时响应 |

粗粒度简单(代码少,推理容易),细粒度灵活(响应快,精确)。**最佳粒度取决于场景**。

### 历史:协作式 vs 抢占式调度

OS 调度演化:

- **1960s**:协作式(进程主动让出 CPU)
- **1970s Unix**:抢占式(time slice,OS 强制切换)
- **1990s**:实时 OS(RTOS),微秒级抢占
- **2000s**:虚拟化,VM 级抢占
- **2010s**:容器,namespace 隔离
- **2020s**:serverless,函数粒度

协作式有回归趋势——协程(coroutine)/ async / fiber 是用户态协作调度,比 OS 抢占快。Casey Day 022 的"消息级 reload"类似协程,但 Casey 决定不用。

### "反思 + 退回"案例

业界知名"反思 + 退回"案例:

- **Rails**:早期很"魔法"(convention over configuration),后期 Merb 合并后变简单
- **Python 2 → 3**:大改不向后兼容,过渡 10 年。社区反思:太激进
- **Rust**:早期有很多特性(GC、green thread),后期砍掉。简化赢
- **Linux DE 反思**:KDE 4 → 5 大改,Plasma 6 又回简单。GNOME 3 → 40 重设计

**好工程师 / 好团队**:写完后审视,不够好就退回。**差工程师 / 差团队**:写完不动,bug 也不修。

Casey 这集是好工程师的示范。

### Lv2 · 动手实践

**题**:在你的 day021 热重载项目里,加 `check_reload()` 检查点,实现消息级 reload。

要求:
1. 游戏代码里多个步骤之间加 check_reload
2. 用一个全局 `Arc<AtomicBool>` 作为 reload 请求标志
3. 主线程设定标志后,游戏代码下一次 check_reload 时触发

完成标准:加 print 看 reload 触发时机,确认在游戏代码"步骤之间",不是"帧间"。

**参考解答**:

```rust
// game_lib/src/lib.rs
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;

#[repr(C)]
pub struct PlatformAPI {
    pub reload_requested: *const AtomicBool,  // 平台层暴露
    pub request_reload: extern "C" fn(),       // 平台层暴露
}

#[no_mangle]
pub unsafe extern "C" fn update_and_render(
    memory: *mut GameMemory,
    platform: *const PlatformAPI,
) {
    let platform = &*platform;
    
    macro_rules! check_reload {
        () => {
            if (*platform.reload_requested).load(Ordering::SeqCst) {
                println!("reload at step boundary");
                // 这里实际上不能直接 reload(函数正在执行)
                // 真正的 reload 由平台层在控制权返回后做
                // 这里只是标记"我想 reload"
            }
        };
    }
    
    check_reload!();
    println!("step 1: input");
    check_reload!();
    println!("step 2: physics");
    check_reload!();
    println!("step 3: ai");
    check_reload!();
    println!("step 4: render");
}
```

注意:真正的"消息级 reload"需要游戏代码 yield 回平台层,平台层 reload,再回到游戏代码。这要求游戏代码是状态机或协程,实现复杂。Casey Day 022 尝试简化版,Day 023 放弃。

```rust
// platform/src/main.rs
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;

#[repr(C)]
struct PlatformAPI {
    reload_requested: *const AtomicBool,
    request_reload: extern "C" fn(),
}

extern "C" fn request_reload() {
    // 触发 reload 标志
    unsafe {
        (*RELOAD_FLAG).store(true, Ordering::SeqCst);
    }
}

static mut RELOAD_FLAG: *const AtomicBool = std::ptr::null();

fn main() {
    let flag = Arc::new(AtomicBool::new(false));
    unsafe { RELOAD_FLAG = Arc::as_ptr(&flag); }
    
    let api = PlatformAPI {
        reload_requested: Arc::as_ptr(&flag),
        request_reload: request_reload,
    };
    
    // ... 主循环
}
```

### Lv3 · 迁移设计

**题**:你被要求做一个**长时间运行的科学计算**(模拟 1 周的物理过程)。用户可以在计算中改算法参数(比如时间步长)。怎么实现"中途改参数"?

和帧级 reload(16ms)对比,科学计算"一帧"可能几小时。你必须要细粒度 reload。具体设计?

**提示**:
- 计算分小步骤(N 个迭代),每步之间检查参数
- 参数存在共享内存(主线程改,计算线程读)
- 计算线程要 cache-friendly(不能用锁太频繁)

### Rust:实现 check_reload 检查点模式

```rust
// src/cooperative_reload.rs
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;

/// 全局 reload 标志
pub struct ReloadFlag {
    flag: Arc<AtomicBool>,
}

impl ReloadFlag {
    pub fn new() -> Self {
        Self { flag: Arc::new(AtomicBool::new(false)) }
    }
    
    pub fn request(&self) {
        self.flag.store(true, Ordering::SeqCst);
    }
    
    pub fn take(&self) -> bool {
        self.flag.swap(false, Ordering::SeqCst)
    }
    
    pub fn ptr(&self) -> *const AtomicBool {
        Arc::as_ptr(&self.flag)
    }
}

/// 检查点宏:在每个步骤边界调用
#[macro_export]
macro_rules! checkpoint {
    ($flag:expr) => {
        if $flag.take() {
            return ReloadRequest::Requested;
        }
    };
}

pub enum ReloadRequest {
    Continue,
    Requested,
}

// 测试:消息级 reload
#[cfg(test)]
mod tests {
    use super::*;
    
    #[test]
    fn reload_at_checkpoint() {
        let flag = ReloadFlag::new();
        
        // 模拟主线程请求 reload
        flag.request();
        
        // 模拟游戏代码执行,检查点
        assert!(flag.take());  // 第一次 take 返回 true
        assert!(!flag.take()); // 第二次 false(已 take)
    }
}
```

### Arch Linux 工具链:监听文件变化

