
# Day 011 · 平台 API 设计:HH 全剧最重要的架构决策

> 今天是个**里程碑**。Casey 在 Day 11 做了 HH 全剧最重要的架构决策:**把"平台代码"和"游戏代码"彻底分开**。平台代码(Win32 / Linux)是"舞台",游戏代码(规则 / 物理 / AI)是"演员"。两者通过一个明确接口通信。这个决策让 HH 后续 600 集健康演化——Casey 可以换平台、换渲染 API、加热重载,游戏代码不动。今天我们理解这个架构,并在 Rust 里规划它的实现。

## 0 · 为什么要有这一天

到 Day 10 为止,你的所有代码都堆在 `main.rs` 里——窗口、输入、音频、渲染、游戏状态、键盘逻辑全在一起。这看起来没事,但实际上是个**架构债**:

1. **跨平台噩梦**:你想把游戏搬到 WebAssembly,要重写所有 winit/softbuffer 代码,游戏逻辑也跟着改
2. **测试噩梦**:想测试"小人撞墙反弹"的逻辑,你必须启动整个图形 / 音频环境
3. **热重载噩梦**:改一行游戏逻辑要重启程序,asset 重新加载,等到崩溃现场
4. **协作噩梦**:你的合作者改"游戏规则",但代码和"窗口管理"混在一起,容易动错地方

Casey Day 11 提出**架构分离**:

- **平台层(platform layer)**:管窗口、输入、音频、文件 IO、时间。**调用**游戏代码
- **游戏层(game layer)**:管游戏状态、规则、AI、渲染指令。**被调用**

两层之间通过**约定的接口**通信:平台调 `game_update_and_render(input, memory)`,游戏返回"我希望画这些像素 + 播这些声音"。

这种分离的**最大好处**:

- **换平台不动游戏**:Win32 → Linux → WebAssembly → Android,游戏代码一行不改
- **热重载**:游戏代码可以编译成动态库,平台层在运行时重新加载,改游戏代码不重启程序(Day 21)
- **测试**:可以写"headless 测试"——只跑游戏逻辑,不启动窗口
- **多人协作**:有人专做平台,有人专做游戏,接口清晰

**心理锚点**:读完今天,你能:

- 解释 Casey 的平台/游戏分离架构,画出接口图
- 解释为什么游戏代码不直接调用 winit / softbuffer / cpal
- 设计 Rust 版的接口:游戏是个 trait?或一组函数指针?
- 知道 Day 21 用 cdylib + libloading 怎么落地
- 解释"依赖倒置原则"(DIP)在这个架构里的体现

## 1 · Casey 今天做了什么

Casey Day 11 是讨论 + 重构日:

1. **画出新的架构图**:平台层(Win32)→ 调用 `GameUpdateAndRender(GameMemory*, GameInput*)` → 游戏层(纯 C,不依赖 Win32)
2. **定义 `GameMemory`**:游戏代码的"全局状态"——一个大的 byte 数组,游戏代码自己解释里面是什么(实体数组、关卡数据、资产……)
3. **定义 `GameInput`**:平台层从窗口系统收集输入(键盘 / 鼠标 / 手柄),打包成 `GameInput` 给游戏
4. **定义 `GameSoundOutputBuffer`**:游戏告诉平台"我要播这些样本",平台层把它送到 DirectSound
5. **定义 `GameOffscreenBuffer`**:游戏告诉平台"这是后缓冲像素",平台层把它送到 GDI
6. Casey 这一天**只设计接口**,不动游戏逻辑——下一集才把现有代码搬进去

这是软件工程最关键的一集。**理解它,你就理解了"为什么 HH 后面 600 集都不重构架构"**——因为 Day 11 的架构选对了。

## 2 · 心智模型

### 类比:剧场

戏剧演出有:

- **舞台 + 灯光 + 音响 + 道具管理**(平台层):由剧场负责,演员不管
- **剧本 + 演员**(游戏层):由剧团负责,剧场不管
- **合同**:剧场给演员"灯光、麦克风、道具",演员返回"表演"

剧场和剧团通过**合同**协作,互不知道对方内部细节。剧场换了(从 A 剧场搬到 B 剧场),剧本不变。剧本改编了(同一个剧团换戏),剧场不变。

HH 的平台 / 游戏分离就是这个模型:

```
平台层(剧场)                    游戏层(剧团)
─────────────                    ─────────
winit / 窗口                     游戏状态
softbuffer / 渲染          ───   游戏规则
cpal / 音频                      物理
gilrs / 输入                     AI
                          ←─→    渲染指令
                  合同:
            GameUpdateAndRender
                  GameInput
                  GameMemory
                  SoundBuffer
                  PixelBuffer
```

### 核心原则:依赖倒置

**传统分层**(错误做法):

```
游戏代码 ──调用──> Win32 API
         ──调用──> GDI / DirectSound
```

游戏代码"依赖"具体平台 API。换平台要改游戏代码。

**依赖倒置**(Casey 的做法):

```
平台代码 ──调用──> 游戏接口(抽象)
游戏代码 ──不调用──> 平台 API
```

游戏代码只依赖**抽象接口**(`GameUpdateAndRender`),不知道平台存在。平台代码实现这些接口,调游戏。

这就是 **Dependency Inversion Principle**(DIP,SOLID 中的 D)。**高层策略不依赖低层细节,两者都依赖抽象**。

### 接口设计的具体形状

Casey 的 C 接口:

```c
// 游戏代码导出的函数
#define GAME_UPDATE_AND_RENDER(name) void name(GameMemory* memory, GameInput* input, GameOffscreenBuffer* buffer)

typedef GAME_UPDATE_AND_RENDER(game_update_and_render);
// game_update_and_render 是个函数指针类型

// 游戏代码:
extern "C" GAME_UPDATE_AND_RENDER(GameUpdateAndRender) {
    // 用 memory 读游戏状态
    // 用 input 决定行为
    // 写 buffer 画像素
}
```

平台代码:

```c
game_update_and_render* fn = ...;  // 从动态库加载
fn(&memory, &input, &buffer);
```

这是**函数指针 + 动态库**的搭配,实现:

- **接口稳定**:函数签名固定,游戏内部怎么改都不影响平台
- **热重载**:动态库改了重新加载,平台层重新拿函数指针
- **跨平台**:平台层是 Win32 还是 Linux,游戏不知道

### Rust 版的接口设计选择

在 Rust 里有几种实现风格,各有取舍:

#### 风格 1:Trait + 泛型

```rust
trait Game {
    fn update_and_render(
        &mut self,
        input: &GameInput,
        memory: &mut GameMemory,
        buffer: &mut GameOffscreenBuffer,
    );
}

// 平台代码
struct Platform<G: Game> { game: G }
impl<G: Game> Platform<G> {
    fn run(&mut self) {
        loop {
            self.game.update_and_render(&input, &mut mem, &mut buf);
        }
    }
}
```

**优点**:类型安全,Rust 风格。
**缺点**:**不能热重载**(类型 `G` 编译时固定)。

#### 风格 2:函数指针(模拟 Casey)

```rust
type GameUpdateAndRender = extern "C" fn(
    input: &GameInput,
    memory: &mut GameMemory,
    buffer: &mut GameOffscreenBuffer,
);

// 平台从动态库加载
let lib = libloading::Library::new("libgame.so")?;
let fn_ptr: GameUpdateAndRender = unsafe {
    *lib.get::<GameUpdateAndRender>(b"game_update_and_render\0")?
};

// 调
fn_ptr(&input, &mut mem, &mut buf);
```

**优点**:支持热重载,等价 Casey 设计。
**缺点**:`extern "C"` ABI,不能用 Rust 类型(只能 C 兼容类型,如 `*mut`)。

#### 风格 3:Trait Object(`dyn Game`)

```rust
let game: Box<dyn Game> = Box::new(MyGame::new());
game.update_and_render(&input, &mut mem, &mut buf);
```

**优点**:动态分发,简单。
**缺点**:**不能跨动态库**(`dyn Trait` 的 vtable 是 ABI 不稳定的,不同 rustc 版本布局不同)。

#### 我们的选择

Phase 1 用**风格 1**(trait + 泛型)——简单,类型安全,不热重载。Day 21 切到**风格 2**(函数指针 + cdylib)实现热重载。

这是渐进式架构:**先做对的事情,再做好**。

### `GameMemory` 的设计

Casey 的核心想法:**游戏状态是一个大的 byte 数组,游戏代码自己解释**。

```rust
struct GameMemory {
    /// 持久存储(整个游戏期间存在)
    permanent_storage: Vec<u8>,
    /// 临时存储(每帧重置)
    transient_storage: Vec<u8>,
}
```

游戏代码内部把 `permanent_storage` cast 成自己的 struct:

```rust
struct GameState {
    player_x: f32,
    player_y: f32,
    entities: [Entity; 100],
    // ...
}

let state: &mut GameState = unsafe {
    &mut *(memory.permanent_storage.as_mut_ptr() as *mut GameState)
};
```

**为什么这样设计**?

- **热重载**:游戏代码改了,平台层不重新初始化 memory,memory 里的数据保留——你改代码后小人还在原位置
- **跨平台**:memory 是 byte 数组,Win32 / Linux / WebAssembly 都一样
- **保存 / 加载**:整块 memory 序列化到文件,就是存档

Rust 这边可以用 `MaybeUninit` 或 typed 包装:

```rust
struct GameMemory<T> {
    state: T,
}

let mut memory = GameMemory {
    state: GameState::new(),
};
memory.state.player_x += 1.0;
```

类型安全,但**热重载时类型 T 变了,旧 memory 不兼容**。Casey 用 byte 数组绕过这个问题。我们 Day 21 再深入。

### `GameInput` 的设计

```rust
struct GameInput {
    /// 一组按钮(键盘 / 鼠标 / 手柄,统一抽象)
    controllers: [GameController; 5],  // 4 手柄 + 1 键盘
    /// 帧时间
    dt_for_frame: f32,
}

struct GameController {
    /// 是否连接
    is_connected: bool,
    /// 各按钮:数组下标 = 按钮枚举,值 = (上一帧, 这一帧)
    buttons: [GameButtonState; 16],
    /// 摇杆
    stick_average_x: f32,
    stick_average_y: f32,
}

struct GameButtonState {
    ended_down: bool,    // 当前按下
    half_transition_count: u32,  // 这帧按下/松开的次数
}
```

游戏代码:

```rust
let input = &inputs.controllers[0];  // 玩家 1
if input.buttons[BUTTON_UP].ended_down {
    // 持续按下,持续走
}
if input.buttons[BUTTON_JUMP].half_transition_count > 0 {
    // 这帧按过(瞬间触发),跳
}
```

抽象的好处:**键盘和手柄代码完全一样**。玩家配置"键盘上 = 手柄上",游戏看到的是统一的"BUTTON_UP"。

我们 Day 13 详细实现这个。

### `GameOffscreenBuffer` 和 `GameSoundOutputBuffer`

```rust
struct GameOffscreenBuffer {
    /// 后缓冲内存(像素数组)
    memory: *mut u32,  // 或 Vec<u32>
    width: u32,
    height: u32,
    /// 一行多少字节(width * 4)
    pitch: usize,
}

struct GameSoundOutputBuffer {
    /// 样本数组(interleaved stereo: L R L R ...)
    samples: Vec<i16>,  // 或 Vec<f32>
    samples_per_second: u32,
    channels: u32,
}
```

游戏代码写这两个 buffer,平台层"消费"它们(送 winit / cpal)。

### 数据流

```
┌─────────────────────────────────────────────┐
│  平台层主循环                                 │
│  ────────────────                            │
│  while !done {                              │
│      1. 收集输入(键盘 / 鼠标 / 手柄)        │
│         → 填 GameInput                       │
│                                             │
│      2. 调用 game_update_and_render(         │
│             &input, &mut memory,             │
│             &mut pixel_buffer,               │
│             &mut sound_buffer)               │
│                                             │
│         游戏代码:                            │
│           - 读 input 更新 state             │
│           - 写 pixel_buffer 画画面           │
│           - 写 sound_buffer 给声音           │
│                                             │
│      3. 提交 pixel_buffer 到 softbuffer      │
│      4. 推送 sound_buffer 到 cpal            │
│  }                                          │
└─────────────────────────────────────────────┘
```

平台层做"框架",游戏层做"内容"。Casey 在 Day 12-15 逐个把这些接口细化。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

#### 业界的平台分离

商业游戏引擎都用类似架构:

- **Unreal Engine**:`FGenericPlatform`,不同 OS 是 `FWindowsPlatform`、`FLinuxPlatform` 等子类
- **Unity**:Engine C++ + Platform plugins
- **Godot**:OS abstraction layer

每个引擎都认识到:**平台代码不能和游戏代码混**。Casey 在教学项目演示这个最佳实践。

#### SDL / GLFW 的局限

SDL / GLFW 是"窗口 + 输入 + 音频 + 网络的合集"。它们抽象了平台,但**没有强制游戏/平台分离**——你可以把所有代码堆在 main 里调 SDL。

Casey 的设计更严格:**接口在源头分开**。Rust 这边 winit + softbuffer + cpal 是分离的小 crate,我们手动写"平台层"把它们的抽象包起来。

#### 数据导向设计(Data-Oriented Design)

Casey 的 `GameMemory` 体现 DOD 思想:**数据是核心,代码处理数据**。

传统 OOP:

```rust
struct Player {
    pos: Vec2,
    health: f32,
    fn update(&mut self, dt) { ... }
}
struct Enemy {
    pos: Vec2,
    fn update(&mut self, dt) { ... }
}
```

DOD:

```rust
struct World {
    positions: Vec<Vec2>,    // 所有实体的位置连续
    velocities: Vec<Vec2>,
    healths: Vec<f32>,
    kinds: Vec<EntityKind>,  // 区分实体类型
}

fn update_world(w: &mut World, dt: f32) {
    for (pos, vel) in w.positions.iter_mut().zip(&w.velocities) {
        *pos += *vel * dt;
    }
}
```

DOD 性能好(cache-friendly, SIMD 友好),但代码组织不同。Casey 在 HH Day 200+ 详细讨论。我们 Day 11 暂时用传统 struct 表达。

### 3.2 · 🦀 Rust 生态视角

#### Trait 设计

```rust
pub trait Game: 'static {
    fn new(memory: &mut GameMemory) -> Self;
    fn update_and_render(
        &mut self,
        input: &GameInput,
        memory: &mut GameMemory,
        pixels: &mut [u32],
        pixel_buffer_width: u32,
        pixel_buffer_height: u32,
        sound: &mut GameSoundBuffer,
    );
}
```

**`'static` 约束**:游戏类型不能含借用(否则热重载、跨线程都难)。

#### ABI 和 `extern "C"`

热重载要求游戏代码编成 `.so` / `.dll`,平台用 `dlopen` 加载。Rust 的 cdylib 类型:

```toml
# Cargo.toml
[lib]
crate-type = ["cdylib"]
```

导出函数:

```rust
#[no_mangle]
pub extern "C" fn game_update_and_render(
    input: *const GameInput,
    memory: *mut GameMemory,
    pixels: *mut u32,
    width: u32,
    height: u32,
    sound: *mut GameSoundBuffer,
) {
    // ...
}
```

`#[no_mangle]` 防止 Rust 改函数名(Rust 默认 mangling)。`extern "C"` 用 C ABI(跨编译器一致)。`*mut` 是原始指针,绕过借用检查(unsafe)。

Day 21 详细做这个。

#### Trait Object vs Generic

```rust
// Generic(编译期单态化)
struct Platform<G: Game> {
    game: G,
}
// 编译期就知道 G 具体类型,内联优化好

// Trait object(运行期动态分发)
struct Platform {
    game: Box<dyn Game>,
}
// 运行期查 vtable,稍慢但灵活
```

游戏循环每帧调一次 `update`,vtable 查询开销可忽略。但如果**热重载**,必须用 trait object 或函数指针(generic 不能跨 so)。

#### Workspace 分包

到 Day 11 我们应该把项目分成多个 crate:

```toml
# 顶层 Cargo.toml(workspace)
[workspace]
members = [
    "handmade-platform",   # 平台层(main.rs + winit + softbuffer + cpal)
    "handmade-game",       # 游戏层(game logic + types)
    "handmade-common",     # 共享类型(GameInput / GameMemory 等)
]
```

这样:

- 平台层依赖游戏层(调用游戏)
- 游戏层**不**依赖平台层(反过来,通过 trait / 函数指针)
- 共享类型放 common

依赖图:

```
handmade-platform ──→ handmade-game ──→ handmade-common
handmade-platform ──→ handmade-common
```

游戏层只看 common,不知道平台层存在。

### 3.3 · 🐧 Linux 系统编程视角

#### dlopen / dlsym

Linux 加载动态库:

```c
void* lib = dlopen("./libgame.so", RTLD_NOW);
void* fn = dlsym(lib, "game_update_and_render");
typedef void(*Fn)(...);
Fn game_fn = (Fn)fn;
game_fn(&input, &mem);
```

`dlopen` 把 .so 加载进进程地址空间。`dlsym` 查找符号(函数 / 全局变量)。

Rust 的 `libloading` crate 封装:

```rust
let lib = libloading::Library::new("libgame.so")?;
let fn_ptr: extern "C" fn(...) = unsafe {
    *lib.get::<extern "C" fn(...)>(b"game_update_and_render\0")?
};
fn_ptr(&input, &mem);
```

`lib.get::<T>` 返回 `Result<Symbol<T>>`,`Symbol` deref 成函数指针。`unsafe` 因为调用未检查的代码。

Day 21 详细做。

#### 信号 + 热重载

热重载的一个坑:旧库还在被调用,你不能 unload。Casey 用 `dlclose` 释放,但要确保没线程在用。

Linux 下平台层是这样:

```rust
// 检测 .so 文件 mtime 变化
let mtime = std::fs::metadata("libgame.so")?.modified()?;
if mtime != last_mtime {
    last_mtime = mtime;
    // 重新加载
    drop(old_lib);  // dlclose
    let new_lib = libloading::Library::new("libgame.so")?;
    let new_fn = new_lib.get::<...>(b"game_update_and_render\0")?;
    // 调 new_fn
}
```

文件 mtime 监控可以用 `inotify`(Linux),Day 22 详细做。

### 3.4 · 🎨 图形学视角

平台分离让"渲染后端"可换。游戏只关心"画像素",不关心是 softbuffer 还是 OpenGL 还是 Vulkan:

```
游戏层: 写 pixels: &mut [u32]
   ↓
平台层: 选后端
   ├── softbuffer → CPU 渲染(Phase 1-4)
   ├── OpenGL → GPU 渲染(Phase 5+)
   └── Vulkan → 极致 GPU(可能 Phase 6+)
```

游戏代码不动,平台层换"渲染后端"。这是 Casey 切 OpenGL 时(Day 235)能轻松做的关键。

## 4 · 认知地图

### 4.1 上级

- **架构模式**(Architectural Pattern)— 大尺度软件组织方式
- **关注点分离**(Separation of Concerns)— 不同模块各管各的事
- **依赖倒置原则**(DIP)— 高层不依赖低层细节,都依赖抽象

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 函数指针 + cdylib | Casey 风格,支持热重载 | 跨平台严肃项目 | ✅ Day 21+ |
| Trait + Generic | 编译期分发,类型安全 | 单平台项目,不热重载 | Phase 1 临时 |
| Trait Object (`dyn`) | 运行期分发,简单 | 中等灵活 | 不用 |
| 直接堆 main | 反面教材 | demo | 不用 |

### 4.3 下级

- `GameInput` / `GameMemory` / `GameOffscreenBuffer` — 共享数据类型
- `game_update_and_render` 函数 — 接口签名
- 平台层 — 调用者
- 游戏层 — 被调用者
- cdylib / libloading — Rust 热重载基础

## 5 · 对照与变奏

### 不同语言的等价架构

| 语言 | 接口表达 | 热重载 |
|---|---|---|
| C(Casey) | 函数指针 + .dll | 是 |
| C++ | 虚函数 / 函数指针 | 是 |
| Rust | trait / 函数指针 + cdylib | 是 |
| Go | interface | 是(plugin 包) |
| Java | interface | 是(classloader) |
| Python | duck typing | 是(直接 importlib.reload) |
| Lua | metatable | 是(游戏常用) |

每个语言都支持这个架构,表达方式不同。

### 历史:游戏引擎架构演化

- **1980s**:所有代码堆一起,平台耦合
- **1990s**:Id Software(Doom / Quake)开始分离"引擎"和"游戏逻辑",Quake 用 QuakeC 让游戏逻辑可改
- **2000s**:Unity / Unreal 把"引擎"商业化,游戏代码用脚本(C# / UnrealScript)
- **2010s+**:热重载普及(Unreal Hot Reload,Unity Edit-Continue),代码架构必须支持

Casey Day 11 是这条演化的精华。**手写**平台/游戏分离,理解每个细节。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 说"游戏代码不能 include `<windows.h>`"。为什么?具体会发生什么坏事?

**参考解答**:

如果游戏代码 `#include <windows.h>`:

1. **跨平台丧失**:Linux / macOS 没有 `windows.h`,代码编不过
2. **耦合**:游戏代码"知道"是 Windows,换平台必须改
3. **测试难**:想在 CI 上跑 headless 测试(没 Windows GUI),游戏代码崩
4. **热重载难**:游戏代码调 `MessageBox` 之类 Win32 函数,函数地址在 game.dll 加载时绑定;重新加载 game.dll,绑定失效

正确:**游戏代码只用游戏自己定义的类型**(`GameInput`, `GameMemory`, ...)。平台相关的"做事"由平台层做,通过接口告诉游戏。

类比:演员不能直接调剧场灯光开关,要通过合同告诉灯光师"现在要红光"。

use handmade_common::{Game, GameInput, GameSoundBuffer};

pub struct MyGame {
    pub freq: f32,
    pub phase: f32,
    pub amp: f32,
    pub target_amp: f32,
}

impl Game for MyGame {
    fn new() -> Self {
        Self {
            freq: 440.0,
            phase: 0.0,
            amp: 0.0,
            target_amp: 0.0,
        }
    }

    fn update_and_render(
        &mut self,
        input: &GameInput,
        sound: &mut GameSoundBuffer,
    ) {
        // 更新频率
        if input.move_up { self.freq *= 1.01; }
        if input.move_down { self.freq /= 1.01; }
        self.freq = self.freq.clamp(20.0, 20000.0);

        // 触发声音
        if input.trigger_sound {
            self.target_amp = if self.target_amp > 0.0 { 0.0 } else { 0.2 };
        }

        // 生成样本
        let phase_inc = 2.0 * std::f32::consts::PI * self.freq / sound.sample_rate as f32;
        sound.samples.resize(sound.samples.len(), 0.0);  // 假设平台层已经 resize
        for sample in sound.samples.iter_mut() {
            self.phase += phase_inc;
            if self.phase > 2.0 * std::f32::consts::PI {
                self.phase -= 2.0 * std::f32::consts::PI;
            }
            self.amp += (self.target_amp - self.amp) * 0.001;
            *sample = self.phase.sin() * self.amp;
        }
    }
}
EOF

`main.rs` 的核心:

```rust
use handmade_common::{Game, GameInput, GameSoundBuffer};
use handmade_game::MyGame;

struct App {
    window: Option<winit::window::Window>,
    game: MyGame,
    current_input: GameInput,
}

impl ApplicationHandler for App {
    fn window_event(&mut self, _, _, event: WindowEvent) {
        match event {
            WindowEvent::KeyboardInput { event, .. } => {
                if let PhysicalKey::Code(code) = event.physical_key {
                    match (event.state, code) {
                        (ElementState::Pressed, KeyCode::ArrowUp) =>
                            self.current_input.move_up = true,
                        (ElementState::Released, KeyCode::ArrowUp) =>
                            self.current_input.move_up = false,
                        (ElementState::Pressed, KeyCode::ArrowDown) =>
                            self.current_input.move_down = true,
                        (ElementState::Released, KeyCode::ArrowDown) =>
                            self.current_input.move_down = false,
                        (ElementState::Pressed, KeyCode::Space) =>
                            self.current_input.trigger_sound = true,
                        _ => ()
                    }
                }
            }
            _ => ()
        }
    }

    fn about_to_wait(&mut self, _) {
        // 把 input 喂给 game
        let mut sound_buf = GameSoundBuffer {
            samples: vec![0.0; 480],  // 480 samples / call (10ms at 48kHz)
            sample_rate: 48000,
        };
        self.game.update_and_render(&self.current_input, &mut sound_buf);
        // 把 sound_buf.samples 送 cpal
        // (实际架构:cpal 回调拉,这里 push)
        // 触发消费
        if self.current_input.trigger_sound {
            self.current_input.trigger_sound = false;  // 单次触发
        }
    }
}
```

### Troubleshooting

- **`error: crate 'handmade_common' not found`** — workspace 配置错,检查顶层 Cargo.toml
- **`unresolved import 'handmade_game'`** — handmade-platform 的 Cargo.toml 没加依赖
- **trait `Game` not implemented** — `MyGame` 没 impl Game trait
- **跨 crate 类型不匹配** — 共享类型必须从 common 导入,不要每 crate 各自定义
