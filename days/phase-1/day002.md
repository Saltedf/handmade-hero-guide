# Day 002 · 打开一个窗口:从 Win32 到 winit

> 今天目标极简:在屏幕上**显示一个空白窗口**。Casey 调用 Win32 API(`CreateWindowExW`、`ShowWindow`、`GetMessage`/`DispatchMessage` 一整套)在 Windows 上开窗口。我们换工具:用 `winit` crate,在 Linux 上开一个 Wayland/X11 窗口。窗口里**什么都不画**——这是后面 11 天的"画布"。

## 0 · 为什么要有这一天

你可能会觉得"开个窗口有什么难的,我用 Python `tkinter` 一行就开了"。但你想过没有:

- 你的程序怎么告诉操作系统"我要一个窗口"?
- 操作系统怎么把这个窗口放到桌面上、加入 Alt-Tab 切换序列?
- 用户点 X 关闭按钮,谁来通知你的程序"该退出了"?
- 用户拖动窗口改大小,谁来通知你"重画"?
- 你按键盘按键,操作系统怎么知道这个键是要发给你的窗口还是别的程序?

这些问题的答案就是**窗口系统**(Window System)。Windows 上叫 **Win32 API + USER/GDI 子系统**,Linux 上叫 **X11** 或 **Wayland**,macOS 上叫 **Cocoa/AppKit**。每个系统 API 都不一样(几千个函数,几百个结构体),而且**互不兼容**。

如果你直接调 X11 或 Wayland 的 API,代码会复杂到难以置信(光是 X11 开一个窗口要 100+ 行 C 代码)。所以**几乎所有人**都用封装层:

- C/C++:SDL2 / GLFW / raylib
- Rust:**winit**(本教程用)、`glfw`、`sdl2`
- Python:`pygame`(包 SDL)

**winit** 是 Rust 生态最主流的窗口库,**Bevy** 游戏引擎、**iced** GUI 库都用它。它的设计哲学:**只负责窗口 + 输入,不负责渲染**——所以叫 winit(Window + Init)。渲染交给 `wgpu` / `softbuffer` / `glow` 等下一层。

**心理锚点**:读完今天,你能:

- 解释"窗口系统"在操作系统里扮演什么角色
- 写出一个 Rust 程序,跑起来在桌面显示一个空白窗口
- 解释 winit 的 `EventLoop`(事件循环)为什么是 callback 风格而不是 polling
- 用 `cargo add winit` 加依赖并跑通最小例子
- 知道 X11 和 Wayland 的差别,在 Arch 上验证你的 winit 跑的是哪个

## 1 · Casey 今天做了什么

Casey Day 2 视频的核心动作:

1. 在 `handmade.cpp` 里写 WinMain 入口(Windows GUI 程序不用标准 `main`,用 `WinMain`)
2. 调 `RegisterClassExW` 注册一个"窗口类"(Windows 强制要先注册才能创建)
3. 调 `CreateWindowExW` 创建窗口,拿到窗口句柄 HWND(`HWND` 是 Win32 的核心 opaque pointer)
4. 调 `ShowWindow` 让窗口出现
5. 进入消息循环:`while (GetMessage(&msg, ...)) { TranslateMessage(&msg); DispatchMessage(&msg); }`
6. 写一个 `WindowProc` 回调函数,处理 `WM_PAINT`(重画)、`WM_DESTROY`(关闭)等消息
7. 跑起来,屏幕中央出现一个空白窗口

整套 Win32 编程是**事件驱动**(event-driven)风格:你的程序不是"主动做某事",而是"等待操作系统通知,然后响应"。这个模型在 Rust 里被 winit 完美继承(`EventLoop` + `event_handler` 闭包)。

Casey 这一天还吐槽了 Visual Studio 的"向导"会生成 50 行你完全看不懂的代码,所以他**手写每一行**,你能跟得上。本教程跟着他的精神走——**所有代码手写,不用 IDE 向导**。

## 2 · 心智模型

### 类比:窗口系统是"前台"

想象你住在一家酒店。你是房客(应用程序),酒店是大楼(操作系统)。你想做事:

- 想吃饭 → 你不用自己做饭,你打内线电话给前台("我要在 11 楼开一个房间"),前台安排
- 别人按你门铃 → 前台告诉你"有人按门铃了,你去应门"
- 大楼着火 → 前台通知所有房客"撤离"

**窗口系统就是前台**。你的程序:

- 想开窗口 → 调用窗口系统 API(打前台电话)
- 用户点你的窗口的 X → 窗口系统给你发"关闭事件"(前台通知你)
- 用户按键盘 → 窗口系统决定哪个窗口是焦点(focus),给那个窗口发"键盘事件"

**为什么必须有个前台?** 因为屏幕是共享资源——同时可能有 20 个程序在跑,每个都想画屏幕,都想读键盘。如果没有前台仲裁,程序互相覆盖,系统乱套。

### 事件循环:程序的心跳

窗口程序的核心结构永远是这个:

```
1. 初始化(注册窗口类、创建窗口、显示)
2. while 程序没退出:
   a. 从窗口系统的消息队列里取一条消息(如果没有,阻塞等待)
   b. 派发消息到对应的处理函数
   c. 处理函数根据消息类型做事(重画、响应键盘、退出等)
3. 清理退出
```

这个 `while` 叫**事件循环**(event loop / message loop)。它是 GUI 程序的"心跳"——程序永远在"等消息 → 处理消息",直到收到退出消息。

为什么不能"主动渲染"而要等消息?因为如果你 1 秒渲染 60 帧,但你 1 秒只收到 1 个"用户输入"消息,其余 59 帧渲染就是浪费。事件循环让你"有事才动",CPU 利用率高。**但游戏不一样——游戏要 60 FPS 一直渲染,不管有没有事件**。这就是为什么游戏的事件循环有特殊模式(下面讲)。

### 窗口创建的本质:句柄 / HWND / XID

窗口系统给你的程序返回一个**不透明指针**(opaque pointer)或**整数 ID**,代表"你创建的那个窗口"。这个值对你的程序没意义,你只能把它**还给**窗口系统让它操作。

- Windows:`HWND`(Handle to WiNDow),是指向内核对象的指针
- X11:`Window`,是个 32 位整数 ID
- Wayland:`wl_surface *`,是个 C 指针

**为什么用 ID/指针而不直接传结构体?** 因为窗口的**真实状态**(位置、大小、装饰、z-order)存在**窗口系统的进程里**,你的程序只能通过 IPC(进程间通信)读写。这种设计让窗口系统崩溃不会拖死你的程序,反之亦然。

### winit 的 API 设计

winit 把窗口系统的复杂性抽象成两个核心类型:

```rust
// EventLoop:事件循环,负责"等消息 -> 派发"
let event_loop = EventLoop::new();

// Window:窗口对象,负责"创建、显示、改属性"
let window = Window::new(&event_loop).unwrap();

// 事件循环跑起来,把所有事件派发给闭包
event_loop.run(move |event, control_flow| {
    match event {
        Event::WindowEvent { event: WindowEvent::CloseRequested, .. } => {
            control_flow.exit();  // 收到关闭请求 -> 退出
        }
        _ => ()
    }
});
```

关键 API:

- `EventLoop::new()` — 创建事件循环(连接到 X11 / Wayland / Windows)
- `Window::new(&event_loop)` — 创建窗口
- `event_loop.run(closure)` — **进入**事件循环,阻塞当前线程
- 闭包参数:
  - `event: Event<...>` — 当前事件(枚举,有 `WindowEvent`、`NewEvents`、`AboutToWait` 等变体)
  - `control_flow: &mut ControlFlow` — 控制循环行为(`Poll` / `Wait` / `Exit`)

**`Poll` vs `Wait`**:

- `Poll`:即使没事件,**也立刻再调用闭包**(空转)。适合游戏(60 FPS 一直渲染)
- `Wait`:没事件时**阻塞**,等到有事件才调用。适合普通 GUI(省电)
- `WaitUntil(Instant)`:等下次事件,或者到指定时间(用于定时动画)

游戏必须用 `Poll`(或 `WaitUntil`),否则没用户输入时游戏画面冻住。

### 事件类型

winit 的 `Event` 是个大枚举,常用的几个:

```rust
enum Event<T> {
    NewEvents(StartCause),       // 一轮开始(告诉你为什么开始:ResumeAfter, Init 等)
    WindowEvent {                // 窗口相关事件
        window_id: WindowId,
        event: WindowEvent,
    },
    DeviceEvent {                // 设备相关(全局,不限焦点)
        device_id: DeviceId,
        event: DeviceEvent,
    },
    AboutToWait,                 // 即将进入等待(渲染的最后一刻)
    LoopExited,                  // 循环退出
    UserEvent(T),                // 用户自定义事件(从其他线程发送)
}

enum WindowEvent {
    Resized(PhysicalSize<u32>),  // 窗口大小变了
    CloseRequested,              // 用户点了 X
    KeyboardInput { ... },       // 键盘按下/抬起
    MouseInput { ... },          // 鼠标按下/抬起
    CursorMoved { ... },         // 鼠标移动
    RedrawRequested,             // 系统要求你重画
    Focused(bool),               // 窗口获得/失去焦点
    ScaleFactorChanged { ... },  // HiDPI 缩放变了(从 4K 屏换到 1080p)
    ...
}
```

游戏循环典型的处理顺序:

1. `NewEvents(_)` → 开始一帧,读输入
2. 多个 `WindowEvent::KeyboardInput` → 累积输入状态
3. `AboutToWait` → 调用 `window.request_redraw()` 触发下一帧的渲染
4. `WindowEvent::RedrawRequested` → 真正渲染

注意 winit 0.30 引入了**应用流程改造**(ApplicationHandler trait),不再是闭包风格。下面代码用新 API。

## 3 · 四域深入

### 3.1 · 🐧 Linux 系统编程视角

Linux 桌面有两套窗口系统并存:

**X11**(X Window System,1984 年 MIT 发明):

- 客户端 / 服务器架构:X server(画屏幕、读键盘)和 X client(你的程序)分离,通过 socket 通信
- 网络透明:你可以跑在远程机器上的 GUI 程序,显示在本地
- 设计古老(40 年前),很多包袱(安全模型、HiDPI、多 monitor 支持烂)
- Arch 上包名 `xorg-server`

**Wayland**(2008 年开始,现代替代):

- 显示服务器协议(不是程序),参考实现叫 `weston` 或 `sway` / `gnome-shell` / `kwin_wayland`
- 客户端直接和合成器(compositor)通信,更简单、更安全、更高效
- 不再网络透明(但有人用 wayvnc 补)
- Arch 上包名 `wayland`

**2024 年状态**:大部分发行版默认 Wayland(GNOME、KDE 都默认 Wayland session)。但 X11 仍可用(`Xwayland` 兼容层让 X11 程序在 Wayland 上跑)。

**怎么知道你当前用的是哪个?**

```bash
# 检查当前 session 类型
echo $XDG_SESSION_TYPE
# 输出:x11 或 wayland

# 或者
loginctl show-session $(loginctl | grep $USER | awk '{print $1}') -p Type
# Type=wayland
```

**winit 怎么选 X11 还是 Wayland?**

winit 在编译时和运行时都尝试两个后端,优先 Wayland。如果你的 session 是 wayland,winit 默认用 wayland;如果 X11,winit 用 x11。可以通过环境变量强制:

```bash
WINIT_X11_SCALE_FACTOR=1       # 强制 X11 HiDPI 缩放为 1
WAYLAND_DISPLAY=wayland-0      # 指定 Wayland 显示
```

**底层 API**(不用 winit 时直接调):

| 系统 | C API | Rust binding |
|---|---|---|
| X11 | `Xlib`(老)或 `XCB`(新) | `x11rb`、`xlib-rs` |
| Wayland | `libwayland-client` | `wayland-client` |
| Windows | `User32.dll`(`CreateWindowExW` 等) | `windows-rs`、`winapi` |
| macOS | Cocoa / AppKit | `cocoa-rs`、`objc` |

写一次跑所有平台,这就是 winit 的价值。Casey 在 Windows 上手写 Win32,我们 Rust 这边手写太亏——`windows-rs` 的 API 比 winit 复杂 10 倍。**用 winit 是工程务实**。

### 3.2 · 🦀 Rust 生态视角

#### winit 0.30 的 API 大改(2024)

winit 0.30 把 `event_loop.run(closure)` 改成了 `trait ApplicationHandler` 实现。原因:闭包风格难以表达"多个窗口"、"自定义事件"、"重入"等复杂场景。

新 API 长这样:

```rust
use winit::application::ApplicationHandler;
use winit::event::WindowEvent;
use winit::event_loop::{ActiveEventLoop, EventLoop};
use winit::window::{Window, WindowId};

#[derive(Default)]
struct App {
    window: Option<Window>,
}

impl ApplicationHandler for App {
    fn resumed(&mut self, event_loop: &ActiveEventLoop) {
        // 应用被恢复(系统准备好窗口了),在这里创建窗口
        let attrs = Window::default_attributes()
            .with_title("Handmade Hero");
        self.window = Some(event_loop.create_window(attrs).unwrap());
    }

    fn window_event(
        &mut self,
        event_loop: &ActiveEventLoop,
        _id: WindowId,
        event: WindowEvent,
    ) {
        match event {
            WindowEvent::CloseRequested => event_loop.exit(),
            _ => (),
        }
    }

    // 还可以重写 about_to_wait、user_event 等
}

fn main() {
    let event_loop = EventLoop::new().unwrap();
    event_loop.run_app(&mut App::default()).unwrap();
}
```

**关键 Rust 特性**:

- `Option<Window>` — 窗口可能还没创建(`resumed` 之前),用 Option 表达"可能不存在"
- `&mut self` — 每个 event 修改 app 状态
- trait impl — 把所有 handler 写在一起,清晰
- `event_loop.exit()` — 不立刻退出,但告诉 winit"处理完当前事件就退出"

#### 为什么窗口要放在 Option 里?

winit 0.30 的设计哲学:**窗口对象不能跨 `resumed` / `suspended` 状态存在**。当系统挂起你的 app(比如 macOS 切到其他 app),窗口可能被销毁,`resumed` 时要重建。Rust 用 `Option` 表达这个生命周期,所有权清晰。

#### `unwrap()` 和错误处理

winit 的多数 API 返回 `Result<T, ...>`(因为创建窗口可能失败:显卡驱动崩了、Wayland 拒绝连接等)。`unwrap()` 简单粗暴:成功取值,失败 panic。

```rust
let event_loop = EventLoop::new().unwrap();
// 等价于
let event_loop = match EventLoop::new() {
    Ok(el) => el,
    Err(e) => panic!("EventLoop creation failed: {:?}", e),
};
```

教程示例里用 `unwrap()` 简洁。**生产代码**用 `?` + `Result` 链式传播,或 `expect("具体原因")` 帮 debug。

### 3.3 · 🎮 游戏编程视角

游戏和普通 GUI 程序在窗口处理上有一个**关键差异**:

- **GUI 程序**:被动响应。没事件 = 不动 = 省 CPU。1Password 不在你输入时不重画。
- **游戏**:主动渲染。即使没事件也要 60 FPS 重画,因为世界在动(动画、AI、物理)。

winit 的事件循环默认 `Wait`(省电),游戏要主动改 `Poll`:

```rust
// 在 window_event 或 resumed 里:
event_loop.set_control_flow(ControlFlow::Poll);
```

或者更精细:`WaitUntil(Instant)` 让你"等下次 vsync 或自定义时间"。

**另一个差异**:游戏窗口通常**完全占据焦点**。GUI 程序可能 20 个窗口同屏,游戏一般全屏或大窗口独占。所以游戏不太关心"窗口失去焦点时怎么办"(直接暂停游戏即可)。

Casey 在 Day 4+ 处理这些细节(窗口 resize、frame rate 控制),我们在 Day 4 / Day 8 也会展开。

### 3.4 · 🎨 图形学视角

今天我们不渲染任何东西,但要提前理解:**窗口和"渲染表面"是两件事**。

- **窗口**(window):屏幕上的一块矩形区域,由窗口系统管
- **渲染表面**(surface):可以画像素的内存区域,由图形 API 管

winit 给你**窗口**。但你要画像素,需要拿到一个 surface,这要靠下一层的 API:

- `softbuffer`:最简单,把 `Vec<u32>` 直接 blit 到窗口,像素级控制(我们 Day 3 用)
- `wgpu`:跨平台 GPU 抽象,可以画 3D,复杂但强大
- `glow` / `glutin`:OpenGL,经典图形 API
- `vulkano` / `ash`:Vulkan,现代低开销

Casey 选的是 Win32 GDI(`StretchDIBits`)——Windows 原生,等价于 softbuffer 的"CPU 画 + blit"。Phase 1 我们全程 softbuffer;Phase 5 切 OpenGL;Phase 6+ 可能切 Vulkan。

## 4 · 认知地图

### 4.1 上级

- **窗口系统**(Window System)— 操作系统里负责管理多个程序窗口的子系统
- **图形用户界面**(GUI)— 用窗口 / 鼠标 / 键盘和用户交互的范式
- **事件驱动编程**(Event-driven Programming)— 程序结构围绕"等待事件 -> 响应事件"

### 4.2 同级(并列方案)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| `winit` | Rust 原生,跨平台,只管窗口 + 输入 | Rust GUI / 游戏跨平台 | ✅ |
| `glfw` | C 起家,Rust binding,老牌但 API 不太现代 | OpenGL 项目传统选择 | 不用 |
| `sdl2` | 跨平台多媒体库,功能多(图像/音频/手柄) | C / C++ 游戏跨平台 | 不用 |
| `tao` | winit fork(bevy 的维护者不满 winit 而分叉) | tao + wry 跨平台 GUI | 不用 |
| `fltk-rs` | 老式 widget GUI(自带按钮 / 输入框) | 桌面应用而非游戏 | 不用 |
| 直接调 X11/Wayland | 学习目的 | 教学 | 不用(只在 §3.1 提到) |

### 4.3 下级

- **EventLoop** — 等待事件并派发
- **Window** — 窗口对象(句柄)
- **WindowEvent / DeviceEvent** — 事件类型
- **ApplicationHandler** trait — Rust 风格的事件回调
- **ControlFlow** — 循环行为(Poll / Wait / Exit)
- **PhysicalSize / LogicalSize** — 像素尺寸 vs 逻辑尺寸(HiDPI)

## 5 · 对照与变奏

### Win32 vs winit:同一件事的不同表达

| 操作 | Win32(C) | winit 0.30(Rust) |
|---|---|---|
| 注册窗口类 | `RegisterClassExW(&wcex)` | (内部自动,不需要) |
| 创建窗口 | `CreateWindowExW(...)` | `event_loop.create_window(attrs)` |
| 显示窗口 | `ShowWindow(hwnd, SW_SHOW)` | (创建即显示) |
| 消息循环 | `while GetMessage(...)` | `event_loop.run_app(&mut app)` |
| 处理消息 | `WindowProc(hwnd, msg, ...)` | `ApplicationHandler::window_event` |
| 退出 | `PostQuitMessage(0)` | `event_loop.exit()` |

Win32 多了几步"窗口类注册"——因为 Windows 要求你声明窗口的图标、光标、菜单等元数据。winit 给了一套默认,需要时用 `WindowAttributes` builder 改。

### Casey 的 HWND vs winit 的 Window

```c
// Win32
HWND hwnd = CreateWindowExW(...);  // 一个不透明指针
ShowWindow(hwnd, SW_SHOW);
// 你只能把 hwnd 传回给 Win32 函数,不能直接读写它指向的内存
```

```rust
// winit
let window = event_loop.create_window(attrs)?;
// window 是个 owned 对象,drop 时自动销毁窗口
// 你可以调它的方法:set_title, set_cursor, request_redraw 等
```

Rust 的 `Window` 是 RAII(Resource Acquisition Is Initialization)——**对象生命周期 = 窗口生命周期**,不需要手动 destroy。Casey 在 C 里要记得 `DestroyWindow(hwnd)` 否则内存泄漏。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:winit 的 `Event` 枚举里有 `WindowEvent` 和 `DeviceEvent`。它们差别是什么?为什么游戏读全局键盘时要用 `DeviceEvent`?

**参考解答**:

- `WindowEvent`:发给"有焦点的窗口"的事件。比如 `WindowEvent::KeyboardInput`,只有焦点窗口能收到。
- `DeviceEvent`:设备级事件,**不管焦点**。比如鼠标在屏幕任何地方移动都触发 `DeviceEvent::MouseMotion`,即使你的窗口没焦点。

游戏场景:FPS 游戏的"鼠标视角控制"用 `DeviceEvent::MouseMotion`,因为鼠标移动应该一直生效(即使玩家切到 Discord 聊天一会儿,游戏还要继续读)。但常规"按键弹起"用 `WindowEvent::KeyboardInput` 就够,因为游戏失焦时不需要响应键盘。

`DeviceEvent` 的代价:Linux X11 上要"grab device",可能让其他程序读不到那个设备,所以只在确实需要时用。

// src/main.rs
use winit::application::ApplicationHandler;          // trait 我们要实现
use winit::event::WindowEvent;
use winit::event_loop::{ActiveEventLoop, EventLoop};
use winit::window::{Window, WindowId};

// App 是我们的"应用状态",ApplicationHandler 把事件回调写成方法
#[derive(Default)]
struct App {
    window: Option<Window>,    // Option 因为窗口在 resumed 之后才存在
}

impl ApplicationHandler for App {
    // resumed:窗口系统准备好,可以创建窗口了
    fn resumed(&mut self, event_loop: &ActiveEventLoop) {
        let attrs = Window::default_attributes()
            .with_title("Handmade Hero")             // 标题
            .with_inner_size(winit::dpi::LogicalSize::new(1280, 720));  // 1280x720
        self.window = Some(event_loop.create_window(attrs).unwrap());
    }

    // window_event:每个窗口事件触发
    fn window_event(
        &mut self,
        event_loop: &ActiveEventLoop,
        _id: WindowId,
        event: WindowEvent,
    ) {
        match event {
            // 用户点了 X(或者 Alt+F4)
            WindowEvent::CloseRequested => {
                println!("Window closed");
                event_loop.exit();
            }
            _ => ()
        }
    }
}

fn main() {
    let event_loop = EventLoop::new().unwrap();
    let mut app = App::default();
    event_loop.run_app(&mut app).unwrap();
}

```rust
// src/main.rs(可运行的最小例子)

use winit::application::ApplicationHandler;
use winit::event::WindowEvent;
use winit::event_loop::{ActiveEventLoop, ControlFlow, EventLoop};
use winit::window::{Window, WindowId};

/// 应用状态
#[derive(Default)]
struct App {
    /// 窗口对象。Option 因为窗口在 resumed() 之前不存在。
    window: Option<Window>,
    /// 已收到的 close 事件计数(用于演示状态保存)
    close_requested_count: u32,
}

/// ApplicationHandler 是 winit 0.30 的核心 trait。
/// 所有事件回调都通过它实现。
impl ApplicationHandler for App {
    /// 当应用被"恢复"(可显示)时调用。在这里创建窗口。
    fn resumed(&mut self, event_loop: &ActiveEventLoop) {
        // 设置控制流为 Poll —— 不停调用回调,即使没事件
        // (游戏必须这样,否则画面冻住)
        event_loop.set_control_flow(ControlFlow::Poll);

        // 用 builder pattern 配置窗口属性
        let attrs = Window::default_attributes()
            .with_title("Handmade Hero — Day 2")
            .with_inner_size(winit::dpi::LogicalSize::new(1280, 720))
            .with_resizable(true);

        // 创建窗口。create_window 返回 Result,unwrap 简化(生产用 ?)
        self.window = Some(event_loop.create_window(attrs).unwrap());
        println!("[resumed] window created");
    }

    /// 当应用被"挂起"(可能被销毁)时调用。
    fn suspended(&mut self, _event_loop: &ActiveEventLoop) {
        // 释放窗口(因为它的 surface 可能被系统收走)
        self.window = None;
        println!("[suspended] window dropped");
    }

    /// 每个窗口事件触发。window_id 区分多窗口。
    fn window_event(
        &mut self,
        event_loop: &ActiveEventLoop,
        _window_id: WindowId,
        event: WindowEvent,
    ) {
        match event {
            WindowEvent::CloseRequested => {
                self.close_requested_count += 1;
                println!(
                    "[window_event] CloseRequested (count = {})",
                    self.close_requested_count
                );
                event_loop.exit();
            }
            WindowEvent::Resized(size) => {
                println!("[window_event] Resized to {}x{}", size.width, size.height);
            }
            WindowEvent::KeyboardInput { event, .. } => {
                println!("[window_event] key: {:?}", event);
                // 按下 Escape 也退出
                use winit::event::{ElementState, KeyCode};
                if event.state == ElementState::Pressed
                    && event.physical_key == KeyCode::Escape.into()
                {
                    event_loop.exit();
                }
            }
            _ => ()
        }
    }

    /// 事件循环空闲时(没事件可处理)触发。配合 Poll 模式每帧调用一次。
    fn about_to_wait(&mut self, _event_loop: &ActiveEventLoop) {
        // 这里后面会调用 window.request_redraw() 触发下一帧渲染
        // 今天不渲染,所以什么都不做
    }
}

fn main() {
    // 创建事件循环(连接 X11 / Wayland / Windows)
    let event_loop = EventLoop::new().unwrap();

    // 创建应用状态
    let mut app = App::default();

    // 进入事件循环(阻塞主线程,直到 exit 被调用)
    event_loop.run_app(&mut app).unwrap();
}
```

**关键 Rust 概念解释**:

- `#[derive(Default)]` — 自动生成 `Default::default()`,把所有字段初始化为默认值(`Option<Window>` 是 `None`,`u32` 是 `0`)。要求所有字段都实现 `Default`。
- `event_loop: &ActiveEventLoop` — 一个共享引用(不可变借用)。但 `event_loop.exit()` 看起来是修改?其实 `exit` 内部用原子操作或 cell,所以接口是 `&self`。
- `match event { ... }` — Rust 的模式匹配,每个 `WindowEvent` 变体一个分支。`_ => ()` 是通配符"其他都忽略"。
- `KeyCode::Escape.into()` — `KeyCode` 转 `PhysicalKey`,用 `Into` trait。winit 0.30 类型设计严格,按键的"物理位置"和"虚拟键码"分开。
- `event.physical_key` — 物理按键(按位置,如美式键盘左上角是 Q,德式是 Q)。比 virtual key 跨平台稳定。
