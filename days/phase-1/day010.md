
# Day 010 · 时间精度:Instant / clock / TSC 的真相

> 你已经用 `Instant::now()` 算 dt,以为"时间"是个简单概念。今天打开黑盒:`Instant` 在 Linux 上调什么 syscall?`clock_gettime` 的 `CLOCK_MONOTONIC` 怎么工作?为什么 x86 有专门的 `RDTSC` 指令?理解这些,你才能在性能调优、多线程同步、定时器精度时心里有底。Casey 这一天专门讨论 Win32 的 `QueryPerformanceCounter` vs `__rdtsc()`,我们在 Linux 上做等价的探索。

## 0 · 为什么要有这一天

你以为"时间"就是 `let now = Instant::now()`。实际上,**计算机里的"时间"是个复杂概念**:

- **墙钟时间**(wall clock):2026 年 6 月 20 日 14:30。可调(NTP),会跳
- **单调时间**(monotonic):从某个未指定起点开始的累计秒数,只增不减
- **CPU 时间**(CPU time):你的进程占用了 CPU 多少秒
- **周期数**(cycle count):CPU 跑了多少周期

每种"时间"用途不同:

- 算 dt:用单调时间(不会被 NTP 调乱)
- 算"我的程序跑多久":用 CPU 时间(不包括 sleep)
- 微基准测试:用周期数(精度纳秒)

不区分它们会导致:

- 算的 dt 突然变负(NTP 调时间)
- 性能测试结果不可信(测的是 sleep 不是计算)
- 多机比较时数据不一致(不同 CPU 周期长度不同)

Casey Day 10 详细讲这些,因为 HH 后面要写"性能计时器",对精度要求高。我们今天走同样的旅程。

**心理锚点**:读完今天,你能:

- 解释 `Instant` 在 Linux 上调什么 syscall
- 解释 `clock_gettime(CLOCK_MONOTONIC, ...)` 和 `clock_gettime(CLOCK_REALTIME, ...)` 差别
- 解释为什么 x86 引入 `RDTSC` 指令,它做什么
- 知道什么场景用 `Instant`,什么场景用 `Duration`,什么场景直接读 TSC
- 用 `perf stat` 测一段代码的实际 CPU 周期数

## 1 · Casey 今天做了什么

Casey Day 10 是讨论集,核心动作:

1. 解释 Win32 `QueryPerformanceCounter`(QPC)的"黑盒"——它调什么,精度多少,有没有副作用
2. 讨论 `__rdtsc()`(x86 时间戳计数器指令),它是 CPU 直接给的"周期数"
3. 对比 QPC vs RDTSC:
   - QPC:操作系统保证单调、稳定,但慢(几百纳秒)
   - RDTSC:CPU 直接读寄存器,极快(几纳秒),但语义不稳定(老 CPU 不保证单调,TSC 频率可能漂)
4. Casey 选择:用 QPC 做游戏时间(稳定优先),用 RDTSC 做微基准(精度优先)

Casey 还讲了 **out-of-order execution**(乱序执行)对 RDTSC 的影响:CPU 可能在你 `__rdtsc()` 之后重排指令,导致 TSC 读到的不是你想要的"那个时刻"。解决:`__rdtscp()` 或加 `cpuid` serializing。

我们 Linux 上对应:`Instant::now()` = `clock_gettime(CLOCK_MONOTONIC)`,精度纳秒。`std::thread::sleep` 用 `nanosleep`。微基准用 `perf stat` 或 `core-arch` crate 的 `rdtscp()`。

## 2 · 心智模型

### 类比:时间就像"不同的表"

想象你有三块表:

1. **手机表**:显示日期时间(2026/06/20 14:30)。可以手动调,NTP 自动同步——这是**墙钟时间**。
2. **秒表**:按一下开始,一直跑,只增不减——这是**单调时间**。
3. **CPU 内部计数器**:每秒走 30 亿下,你只关心"差值",不知道绝对时间——这是**周期计数**。

游戏循环用秒表(单调),日志用手机(可读),性能测试用 CPU 计数(精度)。

### Linux 时间源

#### 1. `clock_gettime` syscall

```c
struct timespec ts;
clock_gettime(CLOCK_MONOTONIC, &ts);
// ts.tv_sec:  秒(从系统启动算)
// ts.tv_nsec: 纳秒(0 ~ 999_999_999)
```

`CLOCK_MONOTONIC` 是单调时钟,不受 NTP 调时间影响。Rust 的 `Instant::now()` 内部用它。

变种:

- `CLOCK_MONOTONIC`:单调,但会被 NTP 的"频率调整"影响(慢慢校准)
- `CLOCK_MONOTONIC_RAW`:纯硬件时钟,完全不调
- `CLOCK_BOOTTIME`:包括 suspend 时间
- `CLOCK_REALTIME`:墙钟,可跳

游戏用 `MONOTONIC`(默认)。

#### 2. `time` 和 `gettimeofday`(过时)

```c
time_t t = time(NULL);   // 秒精度
gettimeofday(&tv, NULL); // 微秒精度
```

这些是**墙钟**时间。NTP 调整时可能跳。Rust 的 `SystemTime::now()` 内部用类似机制。**游戏循环不要用**。

#### 3. `RDTSC` 指令(x86)

```c
unsigned long long tsc = __rdtsc();
// 返回 CPU 自启动以来的周期数
```

每秒 ~30 亿(看 CPU 主频)。精度纳秒,延迟几纳秒。但:

- 不保证单调(老 CPU 多核可能不一致)
- 频率可能漂(睿频 / 节能)
- 需要 serialization 防止乱序

#### 4. `perf_event_open`(性能计数器)

```c
struct perf_event_attr pe = { ... };
int fd = syscall(SYS_perf_event_open, &pe, 0, -1, -1, 0);
read(fd, &count, sizeof(count));
```

读 CPU 内部"实际周期数"、"指令数"、"cache miss"等。`perf stat` 命令用这个。精度极高。

### `Instant::now()` 在 Rust 里的实现

```rust
// 简化版
pub fn now() -> Instant {
    let mut ts: libc::timespec = unsafe { std::mem::zeroed() };
    unsafe {
        libc::clock_gettime(libc::CLOCK_MONOTONIC, &mut ts);
    }
    Instant { t: ts.tv_sec as u64 * 1_000_000_000 + ts.tv_nsec as u64 }
}
```

实际 Rust std 用 `vdso`(虚拟动态共享对象)优化——`clock_gettime` 在用户态直接读内核数据,不走 syscall(快 10 倍)。

```bash
# 看 vdso
cat /proc/self/maps | grep vdso
# 7ffc2f7fe000-7ffc2f800000 r-xp ... [vdso]

# ldd 不会列 vdso,但每个程序都有
```

vdso 让 `Instant::now()` 只要几纳秒,而不是几百纳秒(syscall 开销)。

### 精度对比

| 时间源 | 典型延迟(读一次) | 精度 |
|---|---|---|
| `clock_gettime`(syscall) | 几百纳秒 | 纳秒 |
| `clock_gettime`(vdso) | 几纳秒 | 纳秒 |
| `RDTSC` | 几纳秒 | 子纳秒 |
| `RDTSCP`(serialized) | 几十纳秒 | 子纳秒 |
| `time(NULL)` | 几十纳秒 | 秒 |

游戏主循环每帧调一次 `Instant::now()`,几十纳秒可忽略。微基准测试(测一个函数耗时)可能要循环 1000 次平均,因为单次太短精度不够。

### 乱序执行和 serialization

现代 CPU **乱序执行**——指令顺序不一定按你写的顺序跑。如果你写:

```c
unsigned long long t1 = __rdtsc();
do_something();
unsigned long long t2 = __rdtsc();
```

CPU 可能把 `do_something` 提前或推后,导致 `t2 - t1` 不准。

解决:**serializing instruction**,强制 CPU 排序:

- `RDTSCP`:RDTSC 的 serialized 版本,但只在读取后 serialize
- `CPUID`:系统指令,强制 serialize(在 RDTSC 前后都加 CPUID)
- `LFENCE`:加载屏障(x86)

```c
unsigned long long t1, t2;
_cpuid();  // serialize
t1 = __rdtsc();
do_something();
t2 = __rdtscp();  // serialize
_cpuid();
```

Rust 没有内置 RDTSC(稳定版),用 `core_arch` crate:

```rust
// 实际可能要 nightly 或 third-party
use std::arch::x86_64::_rdtsc;
let t = unsafe { _rdtsc() };
```

### 周期数 vs 秒数

TSC 是"周期数",不是"秒数"。要换算:

```rust
let cycles_per_sec = 3_000_000_000;  // 3 GHz CPU
let cycles = end_tsc - start_tsc;
let secs = cycles as f64 / cycles_per_sec as f64;
```

但 CPU 频率可能变(节能 / 睿频)。如果你测的代码运行时 CPU 在 1GHz 节能,你的"TSC 差"对应真实时间长。

**怎么知道 CPU 频率**:

```bash
lscpu | grep MHz
# CPU MHz:               2400.000
# CPU max MHz:           3400.0000
# CPU min MHz:           800.0000

# 实时频率
cat /proc/cpuinfo | grep "cpu MHz" | head
# cpu MHz:  2400.000
```

### `Duration` 类型和数学

```rust
use std::time::{Duration, Instant};

let start = Instant::now();
do_something();
let elapsed: Duration = start.elapsed();

let nanos = elapsed.as_nanos();      // u128
let micros = elapsed.as_micros();    // u128
let millis = elapsed.as_millis();    // u128
let secs = elapsed.as_secs();        // u64
let secs_f = elapsed.as_secs_f32();  // f32
let secs_f64 = elapsed.as_secs_f64();// f64

// Duration 数学
let d1 = Duration::from_millis(100);
let d2 = Duration::from_secs(1);
let sum = d1 + d2;        // 1100ms
let diff = d2 - d1;       // 900ms
let scaled = d1 * 5;      // 500ms
let halved = d1 / 2;      // 50ms
```

`Duration` 内部是 `(secs: u64, nanos: u32)`,精度纳秒,范围 ~580 亿年。够用。

## 3 · 四域深入

### 3.1 · 🐧 Linux 系统编程视角

#### 时间在内核里

Linux 内核维护多个时钟:

- **xtime**:墙钟时间,从 1970-01-01 算
- **jiffies**:内核启动后的"tick"数(HZ 配置,通常 250 / 1000 Hz)
- **ktime**:纳秒级内部时间
- **CLOCK_MONOTONIC**:基于 xtime + NTP 调整,但单调

硬件时钟源(内核可读):

- **TSC**(Time Stamp Counter):x86 指令
- **HPET**(High Precision Event Timer):主板芯片
- **ACPI PM Timer**:电源管理计时器

内核选择最快的:`dmesg | grep clocksource`:

```bash
dmesg | grep -i clocksource | head
# 输出:
# tsc: Marking TSC unstable due to TSCs unsynchronized
# Clocksource: Switched to clocksource tsc
# (或 hpet)

# 当前 clocksource
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
# tsc

# 可选 clocksource
cat /sys/devices/system/clocksource/clocksource0/available_clocksource
# tsc hpet acpi_pm
```

如果 TSC 不稳定(老 CPU / 节能问题),内核 fallback 到 HPET(慢但稳)。

#### `timerfd` 和 `epoll`

Linux 的"定时器"用 `timerfd_create` 把定时器变成文件描述符,然后 epoll 等:

```c
int tfd = timerfd_create(CLOCK_MONOTONIC, 0);
struct itimerspec spec = { ... };
timerfd_settime(tfd, 0, &spec, NULL);
// 然后 epoll_wait 等待 fd 可读(每周期一次)
```

游戏循环不用 timerfd(我们 Poll 模式不睡),但 GUI 程序 / 服务器用。

#### NTP 调整的影响

NTP(Network Time Protocol)定期校准系统时间:

- **慢调整(slew)**:微调频率,几 ppm,慢慢对齐
- **快调整(step)**:突然跳几秒(只在差距大时)

`CLOCK_MONOTONIC` 不受 step 影响,但受 slew 影响(频率变)。`CLOCK_MONOTONIC_RAW` 完全不调,但 drift 累积。

游戏用 `MONOTONIC`,因为 slew 影响极小(几 ppm)。

### 3.2 · 🦀 Rust 生态视角

#### std::time API 设计

```rust
pub struct Instant { /* 不透明 */ }
pub struct SystemTime { /* 不透明 */ }
pub struct Duration { secs: u64, nanos: u32 }
```

`Instant` 和 `SystemTime` 是**不透明类型**(字段私有),你只能通过方法访问。这让 Rust 标准库在不同平台用不同实现,而 API 一致。

#### Duration::MAX

```rust
println!("{:?}", Duration::MAX);
// 106751991167300d 15h 30m 7s 585ms 575ns
// 大约 292 亿年
```

足够覆盖任何真实场景。如果做"超长时间模拟"(宇宙演化),注意可能溢出。

#### `tokio::time` 和异步定时器

异步运行时(tokio)有自己的时间 API:

```rust
tokio::time::sleep(Duration::from_secs(1)).await;
```

它基于 reactor + timer wheel,适合大量并发定时器。游戏一般不用 tokio,用同步 + 自己的循环。

#### 微基准测试:`criterion` crate

```rust
// benches/my_bench.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn bench_sin(c: &mut Criterion) {
    c.bench_function("sin", |b| {
        b.iter(|| {
            let x = black_box(0.5f32);
            x.sin()
        })
    });
}

criterion_group!(benches, bench_sin);
criterion_main!(benches);
```

跑 `cargo bench`,criterion 自动:

- 跑多次取平均
- 算标准差
    - 检测异常值
- 输出 HTML 报告

它内部用 `Instant::now()`(精度够),不需要 RDTSC。

### 3.3 · 🎮 游戏编程视角

#### 帧时间和帧率

```rust
let dt = start.elapsed().as_secs_f32();
let fps = 1.0 / dt;
```

注意:**FPS 是 dt 的倒数**,不直接显示。要平滑 FPS 显示:

```rust
let smoothed_fps = 0.9 * old_fps + 0.1 * (1.0 / dt);
```

否则数字抖动剧烈(60 → 65 → 58 → 62)。

#### dt 的精度

60 FPS dt ≈ 0.0167。`f32` 精度 ~7 位有效数字,0.0167 没问题。但**累加**有问题:

```rust
let mut t = 0.0f32;
loop {
    t += dt;  // 每次 + 0.0167
}
// 1 小时后 t = 216000,精度损失
```

`f32` 在大数附近精度变差。解决:

- 用 `f64` 累加时间
- 或用整数纳秒累加

Casey 在 HH 后期(Day 100+)改用 `f64` 做时间累加。

#### 跨平台时间 API 选择

| 平台 | API |
|---|---|
| Windows | `QueryPerformanceCounter`(纳秒) |
| Linux | `clock_gettime(CLOCK_MONOTONIC)` |
| macOS | `mach_absolute_time` |
| Web | `performance.now()` |

`Instant::now()` 抽象了这些,跨平台一致。

### 3.4 · 🎨 图形学视角

#### 帧时间 vs 显示刷新

显示器刷新率:

- 60 Hz:每 16.67ms 一次
- 120 Hz:每 8.33ms 一次
- 144 Hz:每 6.94ms 一次

游戏循环 dt 可能 ≠ 显示器周期。比如 144 Hz 显示器上跑 60 FPS 游戏,每帧 16.67ms,但显示器每 6.94ms 刷新——两次刷新显示同一帧(画面"卡")。

解决:G-Sync / FreeSync——显示器动态调刷新率匹配游戏帧率。或者 vsync 把游戏锁到显示器刷新率。

Day 18 我们讨论"强制帧率"。

#### VRR(可变刷新率)

VRR 显示器让游戏自由帧率,显示器跟随。这是近年来 PC 游戏体验最大改进之一。Linux 上 Wayland + AMD GPU 支持 VRR:

```bash
# 看你的显示器是否支持 VRR
cat /sys/class/drm/card0-*/*/vrr_capable 2>/dev/null
# 1 = 支持

# 启用(在 sway / kwin 配置)
```

## 5 · 对照与变奏

### Casey 的 QPC vs 我们的 Instant

| 维度 | Win32 QPC | Rust `Instant` |
|---|---|---|
| 实现 | 内核态调用 | vdso 优化(用户态) |
| 精度 | 100ns | 1ns |
| 单调性 | 是 | 是 |
| 跨核一致 | 是(QPC 用 HPET 或 stabilized TSC) | 是(Linux MONOTONIC) |
| 延迟 | 几百纳秒 | 几纳秒(vdso) |

Rust `Instant` 在 Linux 上比 QPC 快(因为 vdso)。

### QPC 和 RDTSC 的争议

Casey 提到的争议:

- **QPC 调用慢**:几百纳秒,频繁调用影响性能
- **RDTSC 不稳定**:老 CPU 多核 TSC 不同步

现代 CPU(2010+)TSC 稳定(invariant TSC),Linux 用它作 clocksource,QPC 在 Windows 上也用稳定 TSC。所以争议过时了——现在两者都基于 TSC。

但 vdso 让 Rust `Instant::now()` 几纳秒,比 RDTSC + serialization 还快(因为 vdso 已经预算好了)。

### 历史演化

- **1970s**:Unix `time()` 系统调用,秒精度
- **1980s**:BSD `gettimeofday`,微秒精度
- **1990s**:`clock_gettime`,纳秒精度
- **1997**:x86 引入 RDTSC
- **2000s**:Windows QPC 普及
- **2010s**:Linux vdso 优化,免 syscall
- **2020s**:invariant TSC 普及,所有现代 CPU 稳定

时间 API 越来越快越来越准。但 Casey 教学 Day 10 提醒:**理解底层,不要把库当黑盒**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 `CLOCK_REALTIME` 不能用来算游戏 dt?给出一个具体的失败场景。

**参考解答**:

`CLOCK_REALTIME` 是墙钟时间,NTP 可以**前后调整**它。具体失败场景:

1. 玩家在玩游戏,系统后台 NTP 客户端发现时间慢了 5 秒
2. NTP 把 `CLOCK_REALTIME` 跳 +5 秒(突然)
3. 你的 dt 计算用 REALTIME:`dt = now - last`,这一帧 dt = 5.0167 秒
4. 你 update 用这个 dt:小人 x += 100 * 5.0167 = 501.67 像素,瞬间穿墙
5. 物理爆炸,游戏崩

`CLOCK_MONOTONIC` 永远不跳(只增不减),所以 dt 始终是真实的帧间隔。

教训:**任何"差值"计算用单调时钟**。绝对时间(日志、保存的"创建时间")才用墙钟。

### Lv2 · 动手实践

**题**:测 `Instant::now()` 的实际延迟。完成标准:算出单次调用的纳秒数。

**参考解答**:

```rust
use std::time::{Duration, Instant};

fn main() {
    // 预热(避免第一次冷启动)
    let warmup_start = Instant::now();
    for _ in 0..1000 {
        let _ = Instant::now();
    }
    println!("warmup: {:?}", warmup_start.elapsed());

    // 测 N 次调用的总耗时,除以 N
    const N: u32 = 1_000_000;
    let start = Instant::now();
    let mut last = start;
    for _ in 0..N {
        last = Instant::now();  // 真正调的
    }
    let total: Duration = start.elapsed();
    let per_call_ns = total.as_nanos() as f64 / N as f64;
    println!("Total: {:?}, per call: {:.1} ns", total, per_call_ns);
    // 典型:per call ~15-30 ns(vdso)
    // 第一次冷启动:几百纳秒(这就是为什么要预热)

    // 测"什么都不做"的循环开销
    let baseline_start = Instant::now();
    for _ in 0..N {
        std::hint::black_box(());
    }
    let baseline = baseline_start.elapsed();
    println!("Baseline loop: {:?}", baseline);
    // 应该比 Instant 版小很多
}
```

跑:

```bash

# 输出:
# warmup: 30.245µs
# Total: 24.3ms (1M calls), per call: 24.3 ns
# Baseline loop: 1.2ms
```

`black_box` 防止编译器把循环优化掉。

### Lv3 · 迁移设计

**题**:你想实现一个"高精度 FPS 限制器"——把游戏锁到恰好 60 FPS(不是 60 左右)。基于 `Instant` + `thread::sleep` 的实现可能有几 ms 误差,因为 sleep 精度低。如何让它精确?

**提示**:

- `thread::sleep` 在 Linux 用 `nanosleep`,但内核调度粒度是 1-10ms
- 解决:sleep 到 deadline 前 2ms,然后 busy-wait(空转)到精确时间
- busy-wait 浪费 CPU,但精度高

写出关键代码:

```rust
fn precise_sleep_until(deadline: Instant) {
    let now = Instant::now();
    if now >= deadline { return; }
    
    // 先 sleep 大部分时间(省电)
    let remaining = deadline - now;
    if remaining > Duration::from_millis(2) {
        std::thread::sleep(remaining - Duration::from_millis(2));
    }
    
    // 剩余 2ms 内 busy-wait(精确)
    while Instant::now() < deadline {
        std::hint::spin_loop();  // CPU 提示"我在自旋,别调度走"
    }
}
```

思考:这个方法的精度上限是什么?(答案:`Instant::now()` 的延迟,~25ns。)

### Troubleshooting

- **`Instant` 不单调 panic**:某些老内核 + suspend 可能导致。升级内核。
- **dt 总是 0**:精度问题,用 `as_nanos` 而不是 `as_secs_f32`
- **dt 抖动大**:其他进程占 CPU,用 `taskset` 绑核:`taskset -c 0 cargo run --release`
- **vdso 不工作**:某些 seccomp 阻止,检查容器配置

### Rust 模式:测量宏

```rust
macro_rules! time_it {
    ($name:expr, $body:block) => {
        let __start = std::time::Instant::now();
        $body;
        println!("{}: {:?}", $name, __start.elapsed());
    };
}

fn main() {
    time_it!("compute", {
        let mut sum = 0u64;
        for i in 0..1_000_000 { sum += i; }
        println!("{}", sum);
    });
    // 输出:compute: 4.23ms
}
```
