# Day 019 · 平台 / 游戏边界重构(上):音频同步与时钟协调

> Day 011 设计了平台 / 游戏分离,Day 014-018 把抽象落地到内存、输入、帧率。Day 019-020 是 Casey 的"回头看"——他用了一阵子这个架构,发现几个**边界处的痛**。今天聚焦**音频同步**:CPU 时钟产样本,声卡时钟消费样本,两个时钟不一样快,长时间累积漂移导致声音卡顿。Casey 重构平台层,让"产 / 消"速度自适应。这集教学价值不在新功能,而在**怎么发现架构问题、怎么重构不破坏既有接口**。

## 0 · 为什么要有这一天

你跑 Day 012 的音频代码,前 5 秒声音正常,30 秒后开始"咔哒咔哒"。你重新启动,问题消失,30 秒后回来。这是为什么?

**根因**:**CPU 时钟和声卡时钟不同步**。

CPU 时钟(由 Instant / QPC 测)告诉你"这一帧产 N 个样本"。但 N 怎么算?简单做法:`N = 44100 / 60 = 735`(每秒 44100 样本 / 60 FPS)。你每帧产 735 样本,声卡每秒消费 44100,看起来匹配。

但**实际不匹配**:

1. **CPU 时钟略偏**:你的 60 FPS 实际是 60.001 FPS(误差千分之一)。每帧实际时间 16.666ms 而不是 16.667ms。
2. **声卡时钟略偏**:声卡标称 44100 Hz,实际可能是 44099 或 44101(晶振精度 ±100ppm)。
3. **OS 调度抖动**:某帧 OS 调度慢,你产了 735 + 5 个样本才赶上。

每帧 1 个样本的误差,几分钟后累积成几十毫秒——buffer underrun(被读光,咔哒声)或 overrun(满了,丢样本)。

**Day 019 的核心**:不要假设"CPU 时钟产 = 声卡消费",而要**测量**实际状态,动态调整。

这是分布式系统的经典问题——**生产者消费者速度不匹配**。Kafka、消息队列、视频流都有类似设计。Casey 在游戏里解决它,原理通用。

**心理锚点**:读完今天,你能:

- 解释为什么"固定每帧产 N 样本"在长时间会 drift
- 写一个基于 play cursor 的动态样本数算法
- 解释"音频缓冲延迟 vs 稳定性"的 trade-off
- 知道 cpal 的回调驱动如何自动解决 CPU/声卡时钟漂移
- 在你的 Rust + cpal 项目里实现稳健的音频 pipeline
- 知道 Linux ALSA / PipeWire / cpal 在这件事上的层次

## 1 · Casey 今天做了什么

Day 019 Casey 的具体动作:

1. **发现问题**:Day 012 的音频在长时间运行后卡顿。
2. **诊断**:打印 play cursor 和 write cursor 位置,看到它们随时间相对 drift。
3. **重构**:平台层暴露 `get_samples_to_write()` 函数,游戏代码每帧调它,**问平台层"这帧应该产多少样本"**。
4. **算法**:`samples_needed = target_latency - samples_in_flight`。`samples_in_flight = write_cursor - play_cursor`(已写未播)。

游戏代码不再固定产 735 样本,而是问平台层。平台层根据声卡实际进度算出"应该产多少",自动纠正 drift。

Casey 这集还遇到一个 **bug**:DirectSound 的 `GetCurrentPosition` 返回的 play cursor 有时有几毫秒延迟(它内部 cache)。这个 bug Day 020 专门调试。

## 2 · 心智模型

### 类比:音频管线是"传送带"

想象传送带:

```
[CPU 产样本] → [传送带(buffer)] → [声卡消费]
```

传送带长度 = buffer 大小(比如 4410 样本 = 100ms)。

理想:CPU 每秒产 44100 样本,声卡每秒消费 44100,传送带液位稳定。

现实:CPU 实际每秒产 44101(快 1 个),声卡消费 44100。1 秒液位涨 1,100 秒涨 100,1500 秒(25 分钟)液位满——overrun,丢样本。

反过来,CPU 慢:液位降,0 时 underrun。

**Casey 的解法**:让 CPU 看"传送带液位",液位低就多产,液位高就少产。**反馈控制**(feedback control)。

```
              ┌─ 看 play cursor ──→ CPU 算"该产多少"
              │                       │
              ↓                       │
[声卡消费] ← [buffer] ← [CPU 产样本] ←┘
```

这是**闭环系统**(closed-loop)。Day 012 是开环——CPU 不看声卡状态,盲产。开环系统在时钟不匹配时必然漂移。

### 严谨:play cursor 和 write cursor

DirectSound(和 ALSA、CoreAudio)环形 buffer 有两个指针:

- **play cursor**:声卡**正在播放**的样本位置(只读)
- **write cursor**:声卡**安全可写**的样本位置(从这里开始写不会被覆盖)

```
buffer:    [.....w=====p.....]
                ^    ^
                |    |
                |    └ play cursor(声卡在这读)
                └ write cursor(从这里开始写安全)
                
       [p, w] 之间是"声卡正在读 + 即将读"的区域,不能写
       [w, p) 之间(环形回绕)是"可写"区域
```

游戏代码每帧:
1. 读 play cursor 和 write cursor
2. 算 `samples_in_flight = write_cursor - play_cursor`(已写未播)
3. 算 `samples_needed = target_latency - samples_in_flight`
4. 产 `samples_needed` 个样本,写入 buffer 的 `write_cursor` 位置

**`target_latency`**:目标缓冲液位。比如 2 帧 = 1470 样本 = 33ms。意味着声卡现在播的样本是 33ms 前产的——你听到的"现在"实际是 33ms 前。

### Casey 的算法(Rust 版)

```rust
pub struct AudioSync {
    target_latency_samples: i32,  // 目标液位(比如 1470)
    bytes_per_sample: i32,        // stereo i16 = 4 字节
}

impl AudioSync {
    pub fn new(sample_rate: u32, channels: u32, target_latency_ms: u32) -> Self {
        let target_latency_samples = 
            (sample_rate as i32 * target_latency_ms as i32) / 1000 * channels as i32;
        Self {
            target_latency_samples,
            bytes_per_sample: (channels * 2) as i32,  // i16 = 2 字节
        }
    }
    
    /// 算"这一帧应该产多少样本"(per channel)
    pub fn samples_to_write(&self, play_cursor_bytes: i32, write_cursor_bytes: i32) -> i32 {
        // bytes 转样本
        let play = play_cursor_bytes / self.bytes_per_sample;
        let write = write_cursor_bytes / self.bytes_per_sample;
        
        // 已写未播(环形 buffer 处理)
        let in_flight = if write >= play {
            write - play
        } else {
            // 环形回绕:write 在 play 后面,加 buffer 大小
            // 这里简化,实际需要 buffer_size
            write + 44100 - play  // 假设 1 秒 buffer
        };
        
        // 应该写多少补到 target
        let needed = self.target_latency_samples - in_flight;
        needed.max(0)
    }
}
```

游戏代码:

```rust
fn update_and_render(memory: &mut GameMemory, sound_buffer: &mut SoundBuffer, ...) {
    // 旧:固定 735 样本(错)
    // let samples_to_write = 735;
    
    // 新:问平台层
    let (play, write) = sound_buffer.get_cursors();
    let n = audio_sync.samples_to_write(play, write);
    let samples: Vec<f32> = generate_samples(n);  // 游戏代码产 n 样本
    sound_buffer.write_samples(&samples);
}
```

`generate_samples` 要能产**任意数量**样本,而不是固定 735。这是重构的核心——**让游戏代码适应平台需求**,而不是相反。

### cpal 怎么解决这件事(更优雅)

cpal 用**回调驱动**,自动解决 drift:

```rust
let stream = device.build_output_stream(
    &config,
    |data: &mut [f32], _: &_| {
        // 声卡需要 data.len() 个样本,你填它
        // cpal 自动处理 play/write cursor,你不用管
        for sample in data.iter_mut() {
            *sample = generate_next_sample();
        }
    },
    |err| eprintln!("{}", err),
    None,
)?;
```

cpal 的回调**由声卡驱动**——声卡需要数据时调你,**告诉你需要多少**。你不需要预测样本数。

为什么这样自动解决 drift?因为回调频率 = 声卡时钟,不是 CPU 时钟。如果声卡慢一点(44099 Hz),它调你的频率略低,你产略少——自动平衡。**CPU/声卡时钟差自动归零**。

Casey 在 C 里手写 cursor 算法,因为 DirectSound 是 pull 模型(你 push 数据)。cpal 是 push 模型(声卡 pull 你的回调),更高层抽象,自动处理。

**理解 Casey 的算法对设计自定义音频系统重要**——比如你做网络音频流(play cursor 在远端),或低延迟乐器(需要精确时钟),cpal 不够用,你要自己实现 cursor 逻辑。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏音频同步的演化:

**早期(DOS 时代)**:直接写声卡寄存器,IRQ 驱动。程序员要管一切。

**DirectSound 时代**(Casey 用):环形 buffer + cursor 查询。程序员手动算样本数。

**WASAPI 时代**(Windows Vista+):更精确的 timestamp API。低延迟模式。

**现代跨平台(cpal / Core Audio / ALSA)**:回调驱动,自动平衡。程序员只关心样本内容。

业界工具:
- **Wwise / FMOD**:专业音频中间件,内置同步
- **JACK**:Linux 专业音频,极低延迟(5ms)
- **PipeWire**:现代 Linux,默认 21ms 延迟,可调

游戏音频延迟目标:

| 类型 | 延迟 |
|---|---|
| 节奏游戏(吉他英雄) | < 30ms |
| FPS 射击 | < 50ms |
| 一般游戏 | < 100ms |
| 卡牌 / 慢节奏 | < 200ms 都可接受 |

### 3.2 · 🎨 图形学视角(生产者消费者)

音频 cursor 模型在图形学里也有变体——**多缓冲**(double / triple buffering):

```
Triple buffering:
[CPU 写] → [buf 1] → [buf 2] → [buf 3] → [显示器读]
```

CPU 一直写最旧的 buffer,显示器一直读最新的。中间 buffer 是"在途"(in-flight),和音频的 `samples_in_flight` 概念一样。

Vulkan 的 frame-in-flight 是同一概念:`max_frames_in_flight = 2`,CPU 在画第 N+1 帧,GPU 在渲染第 N 帧,显示器在第 N-1 帧。三个并行工作。

**输入延迟**(input latency)= in-flight frames × 帧时间。in-flight 多 = 吞吐量高但延迟大。

### 3.3 · 🐧 Linux 系统编程视角

Linux 音频栈(Casey 的 DirectSound 在 Linux 的对应):

```
┌────────────────────────────────────────┐
│ 你的游戏                                │
├────────────────────────────────────────┤
│ cpal(Rust 抽象)                       │
├────────────────────────────────────────┤
│ PipeWire / PulseAudio(用户态声音服务器)│
├────────────────────────────────────────┤
│ ALSA(libsound,用户态)                │
├────────────────────────────────────────┤
│ 内核 snd-* 驱动                         │
├────────────────────────────────────────┤
│ 声卡硬件                                │
└────────────────────────────────────────┘
```

每层都有自己的 cursor / buffer 概念:

- **ALSA**:`snd_pcm_avail` / `snd_pcm_delay` 暴露 play/write cursor
- **PulseAudio**:`pa_stream_writable_size` / `pa_stream_get_timing_info`
- **PipeWire**:`pw_buffer_get_data` + `pw_queue_buffer`

cpal 在 PipeWire 后端用回调,在 ALSA 后端用 polling。**对 Rust 用户透明**——你只看到 callback。

### 3.4 · 🦀 Rust 生态视角

Rust 音频的几个层次:

**cpal(我们用)**:回调驱动,跨平台,自动 cursor 管理。

**rust-src / coreaudio-rs**:更底层,直接 ALSA / CoreAudio。Casey DirectSound 风格。

**Jack(rockdiesel)**:JACK 高级音频,专业低延迟。

**Rust + audio graph(类似 Wwise)**:`basedrop` / `audio-graph` 等,音频节点图。

**Rust 特有挑战**:

1. **回调里不能 alloc / lock**——会导致 underrun。Rust 借用检查器防止你"借用太久",但 `Arc<Mutex>` 在回调里 lock 长时间是允许的(运行时崩溃才暴露)。
2. **回调跨线程**:cpal 回调在另一个线程。共享状态 `Arc<Mutex<T>>` 或 `Arc<parking_lot::Mutex<T>>`(后者更快)。
3. **回调生命周期**:cpal `Stream` object 不能 drop(否则停止),要 `let _stream = stream;` 保活。

```rust
// 典型 Rust 音频 pipeline
use cpal::traits::{DeviceTrait, HostTrait, StreamTrait};
use std::sync::{Arc, Mutex};

fn main() {
    let host = cpal::default_host();
    let device = host.default_output_device().unwrap();
    let config = device.default_output_config().unwrap();
    
    let shared_state = Arc::new(Mutex::new(SharedState::default()));
    let state_for_callback = shared_state.clone();
    
    let stream = device.build_output_stream(
        &config.into(),
        move |data: &mut [f32], _: &_| {
            // 锁持有尽量短
            let mut state = state_for_callback.lock().unwrap();
            // 填 data
            for sample in data.iter_mut() {
                *sample = state.generate_next_sample();
            }
            // 锁释放
        },
        |err| eprintln!("{}", err),
        None,
    ).unwrap();
    
    stream.play().unwrap();
    
    // 主线程做其他事,保持 stream 活着
    loop {
        std::thread::sleep(std::time::Duration::from_secs(1));
    }
}
```

**实战建议**:Phase 1 用 cpal + 简单 mixer。Phase 4+ 考虑 kira 或自己写音频图引擎。

## 5 · 对照与变奏

### Push vs Pull 模型

**Push(DirectSound / ALSA)**:你 push 数据到 buffer。你要算"产多少"。
**Pull(cpal / Core Audio)**:声卡 pull 数据从你的回调。你被问"给多少"。

Pull 更高级——自动平衡生产消费速度。但 Pull 的代价是**回调里不能阻塞**,否则 underrun。

| | Push | Pull |
|---|---|---|
| 谁主导 | CPU 决定何时产 | 声卡决定何时取 |
| Drift 处理 | 手动算 cursor | 自动 |
| 阻塞影响 | CPU 慢就产少,缓冲液位降 | 阻塞回调会 underrun |
| 实现复杂度 | 高 | 中 |

业界趋势:**Pull 主流**(cpal / Core Audio / WASAPI shared mode)。Push 留给专业场景(ASIO / JACK)。

### 同一问题:网络流媒体

视频流媒体也是生产者消费者——服务器产,客户端消费,网络延迟抖动。

Netflix 的解决:**自适应 buffer**。客户端 buffer 满 → 请求高码率;buffer 低 → 请求低码率。和 Casey 的 cursor 反馈一样。

ABR(Adaptive Bitrate)算法:BOLA、MPC、Rate-based。研究课题。

游戏音频的反馈更简单(只是产量),但思路相同:**测量状态,调整生产**。

### 历史演化:音频同步

- **1990s**:固定样本数,经常 drift,玩家接受
- **2000s**:cursor 算法(Casey 用),稳定
- **2010s**:回调驱动,跨平台自动
- **2020s**:硬件 timestamp + 软件预测,微秒级精度

Casey Day 019 走 2000s 路线,你用 cpal 走 2010s 路线。原理相同,抽象层不同。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 的音频同步算法是"反馈控制"。它和 cpal 的回调驱动相比,各自优缺点?

进一步:如果你做一个**网络多人游戏**,玩家 A 的声音通过网络送给玩家 B,你怎么同步?(网络延迟比声卡延迟大得多)

**参考解答**:

**Casey cursor 算法**:
- 优点:精确控制 buffer 液位
- 缺点:依赖 DirectSound 的 cursor 准确性(Day 020 发现 bug)

**cpal 回调驱动**:
- 优点:自动平衡,不依赖 cursor
- 缺点:回调里不能阻塞 / alloc

**网络多人游戏音频同步**:
- 网络延迟 50-200ms,远大于声卡 30ms 延迟
- 解法:**抖动缓冲**(jitter buffer)——客户端 buffer 200-500ms,吸收网络抖动
- 加 FEC(前向纠错)防丢包
- 加 OPUS 编解码(低延迟,丢包鲁棒)

业界方案:Mumble / Discord 用 OPUS + 抖动缓冲。游戏圈 Vivox / Dissonance。

### Lv2 · 动手实践

**题**:在 Rust + cpal 项目里实现"动态样本产量"——你虽然用 cpal(回调驱动),但模拟 Casey 的 cursor 算法。

要求:
1. 用一个 Ring Buffer(自己实现或用 `ringbuf` crate)存样本
2. 主线程每帧产 N 样本到 ring buffer,N 根据 ring buffer 液位反馈调整
3. cpal 回调从 ring buffer 读
4. 打印每帧 N 的值,看它怎么自适应

完成标准:跑 1 分钟,N 应该稳定在某个值(不漂移),ring buffer 不空也不满。

**参考解答**:

```rust
use ringbuf::{HeapCons, HeapProd, HeapRb};
use std::sync::Arc;
use std::time::{Duration, Instant};

fn main() {
    let rb: HeapRb<f32> = HeapRb::new(44100 * 2);  // 2 秒 buffer
    let (mut prod, cons) = rb.split();
    let cons = Arc::new(cons);
    
    // cpal 回调线程
    let host = cpal::default_host();
    let device = host.default_output_device().unwrap();
    let config = device.default_output_config().unwrap();
    let sample_rate = config.sample_rate().0;
    let cons_for_cb = cons.clone();
    let stream = device.build_output_stream(
        &config.into(),
        move |data: &mut [f32], _: &_| {
            for sample in data.iter_mut() {
                *sample = cons_for_cb.pop().unwrap_or(0.0);  // 空就静音
            }
        },
        |err| eprintln!("{}", err),
        None,
    ).unwrap();
    stream.play().unwrap();
    
    // 主线程:产样本
    let target_latency = 4410;  // 100ms
    let mut t = 0.0f32;
    let mut last_print = Instant::now();
    loop {
        // 当前液位
        let current = cons.len();
        // 反馈:补到 target
        let to_produce = (target_latency as i64 - current as i64).max(0) as usize;
        
        // 产 to_produce 样本(简单的 440Hz 正弦)
        for _ in 0..to_produce.min(1024) {  // 限制每帧最多产 1024
            let s = (2.0 * std::f32::consts::PI * 440.0 * t / sample_rate as f32).sin() * 0.1;
            prod.push(s).ok();
            t += 1.0;
        }
        
        // 打印
        if last_print.elapsed() > Duration::from_millis(500) {
            println!("buffer level: {}, last N: {}", current, to_produce);
            last_print = Instant::now();
        }
        
        std::thread::sleep(Duration::from_millis(16));
    }
}
```

注意:

- `ringbuf` crate 提供线程安全的 ring buffer。
- 主线程产,音频线程消费,自动同步。
- `target_latency = 4410`(100ms)是 buffer 目标液位。如果液位低,主线程多产;液位高,少产。
- 看输出:`buffer level` 应该稳定在 4410 附近,`last N` 也稳定。

### Rust:稳定音频 pipeline

```rust
// src/audio_pipeline.rs
use cpal::traits::{DeviceTrait, HostTrait, StreamTrait};
use cpal::SampleFormat;
use std::sync::{Arc, Mutex};
use std::sync::atomic::{AtomicBool, Ordering};

pub struct AudioPipeline {
    pub state: Arc<Mutex<MixerState>>,
    pub stream: Option<cpal::Stream>,
    pub running: Arc<AtomicBool>,
}

#[derive(Default)]
pub struct MixerState {
    pub oscillator_phase: f32,
    pub oscillator_freq: f32,
    pub volume: f32,
}

impl AudioPipeline {
    pub fn new() -> Self {
        Self {
            state: Arc::new(Mutex::new(MixerState {
                oscillator_phase: 0.0,
                oscillator_freq: 440.0,
                volume: 0.3,
            })),
            stream: None,
            running: Arc::new(AtomicBool::new(false)),
        }
    }
    
    pub fn start(&mut self) -> Result<(), Box<dyn std::error::Error>> {
        let host = cpal::default_host();
        let device = host.default_output_device()
            .ok_or("no output device")?;
        let config = device.default_output_config()?;
        let sample_rate = config.sample_rate().0 as f32;
        let channels = config.channels() as usize;
        
        let state = self.state.clone();
        let running = self.running.clone();
        running.store(true, Ordering::SeqCst);
        
        let stream = match config.sample_format() {
            SampleFormat::F32 => device.build_output_stream(
                &config.into(),
                move |data: &mut [f32], _: &_| {
                    let mut state = state.lock().unwrap();
                    let phase_step = 2.0 * std::f32::consts::PI 
                        * state.oscillator_freq / sample_rate;
                    
                    for frame in data.chunks_mut(channels) {
                        let sample = state.oscillator_phase.sin() * state.volume;
                        state.oscillator_phase += phase_step;
                        if state.oscillator_phase > 2.0 * std::f32::consts::PI {
                            state.oscillator_phase -= 2.0 * std::f32::consts::PI;
                        }
                        for ch in frame.iter_mut() {
                            *ch = sample;
                        }
                    }
                },
                |err| eprintln!("audio error: {}", err),
                None,
            )?,
            _ => return Err("unsupported sample format".into()),
        };
        
        stream.play()?;
        self.stream = Some(stream);
        Ok(())
    }
    
    pub fn set_freq(&self, freq: f32) {
        self.state.lock().unwrap().oscillator_freq = freq;
    }
    
    pub fn set_volume(&self, vol: f32) {
        self.state.lock().unwrap().volume = vol;
    }
}

impl Drop for AudioPipeline {
    fn drop(&mut self) {
        self.running.store(false, Ordering::SeqCst);
        // stream drop 时自动停止
    }
}

// 用法
fn main() {
    let mut audio = AudioPipeline::new();
    audio.start().unwrap();
    println!("Playing 440 Hz");
    std::thread::sleep(std::time::Duration::from_secs(2));
    
    audio.set_freq(880.0);  // 切到高音
    println!("Playing 880 Hz");
    std::thread::sleep(std::time::Duration::from_secs(2));
    
    // drop 时音频停
}
```

**Troubleshooting**:

- **听到咔哒声**:underrun,增大 buffer 或减少锁持有时间
- **完全没声音**:check PipeWire 运行(`systemctl --user status pipewire`)

- **CPU 占用高**:回调里 alloc / 复杂计算,优化
