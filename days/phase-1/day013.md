# Day 013 · 测试与重构日:工程化收尾

> Day 1-12 写了好多代码,但没写测试,函数也可能乱。今天**不写新功能**,只做两件事:1) 给关键模块写单元测试;2) 重构代码,让它更可读、更模块化。这是"工程化"——区分**能跑的程序**和**能维护的程序**。Casey 在 HH 里也时不时停下加新功能,重构已有代码。

## 0 · 为什么要有这一天

新手写代码,**写完就跑,跑通就完事**。但有经验的人会:

1. **跑通** → 2) **写测试** → 3) **重构**

为什么必须写测试?

- 改一行代码,你不知道有没有破坏别的功能
- 重构时(改结构不动行为)没测试,你怎么知道"行为没变"?
- 多人协作,你的修改可能影响别人
- 6 个月后回头看,你已经忘了"这个函数应该干嘛",测试是最好的文档

为什么必须重构?

- 加新功能时如果代码已经乱,加进去更乱
- 重复代码 5 处,改 bug 要改 5 处
- 函数 200 行,谁都不敢动
- "下次重构" → 永远不会来

**测试 + 重构是循环**:

```
写测试 → 重构(测试保证不破坏)→ 写新代码 → 写测试 → 重构 ...
```

这个循环让代码长期可维护。今天我们练习一次。

**心理锚点**:读完今天,你能:

- 用 `#[test]` 写 Rust 单元测试
- 用 `#[cfg(test)] mod tests` 组织测试代码
- 用 `cargo test` 跑测试,理解输出
- 重构 Day 1-12 的代码:提取函数、消除重复、改名
- 解释"红 / 绿 / 重构" TDD 循环
- 写一个简单的集成测试(测多个模块协作)

## 2 · 心智模型

### 类比:测试是"安全网",重构是"装修"

想象你住进老房子:

- **没安全网**:你拆墙时不知道哪面是承重墙,可能整栋塌
- **有安全网(测试)**:你拆墙前先在结构上贴上"测试仪表",拆完看仪表读数,异常就回滚
- **重构(装修)**:你拆墙、改水管、加插座,但仪表读数一直正常 → 安全

测试 = 知道改了什么没坏。重构 = 改了让代码更好。两者配合。

### 测试金字塔

测试有几种,从下到上:

```
            ┌──────────────────┐
            │  E2E / UI 测试    │  少(写起来贵,跑得慢)
            ├──────────────────┤
            │  集成测试          │  中(测多模块协作)
            ├──────────────────┤
            │  单元测试          │  多(每个函数一个)
            └──────────────────┘
```

- **单元测试**:测一个函数 / 模块。快,多。
- **集成测试**:测多个模块协作。中速。
- **E2E**:模拟用户操作整个程序。慢,少。

游戏 / 桌面应用 E2E 难写(要控制鼠标键盘),所以主要靠单元 + 集成。

### Rust 单元测试结构

Rust 的测试和代码同文件,放在 `#[cfg(test)] mod tests`:

```rust
// src/math.rs
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_add() {
        assert_eq!(add(2, 3), 5);
        assert_eq!(add(-1, 1), 0);
        assert_eq!(add(0, 0), 0);
    }

    #[test]
    fn test_add_overflow_does_not_panic_in_release() {
        // 注意:i32 + 在 debug 模式溢出 panic,release wrap
        // 这个测试可能在不同模式表现不同,要小心
    }
}
```

`#[cfg(test)]` 告诉 Rust:这段代码只在 `cargo test` 时编,正常 build 不编。这让 release 二进制不含测试代码。

### `cargo test` 输出解读

```bash
$ cargo test
   Compiling handmade-common v0.1.0
    Finished test [unoptimized + debuginfo] target(s) in 1.23s
     Running unittests src/lib.rs (target/debug/deps/handmade_common-xyz)

running 1 test
test tests::test_add ... ok

test result: OK. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
```

字段:

- `1 passed`:通过的测试数
- `0 failed`:失败数(任何 failed 都让你 exit code != 0)
- `0 ignored`:被 `#[ignore]` 标记跳过的测试
- `0 measured`:性能测试(Rust 1.x 已废弃)
- `0 filtered out`:被命令行 filter 排除的

测试失败例子:

```bash
$ cargo test
running 1 test
test tests::test_add ... FAILED

failures:

---- tests::test_add stdout ----

assertion `left == right` failed
  left: 5
 right: 6
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace


failures:
    tests::test_add

test result: FAILED. 0 passed; 1 failed; 0 ignored
```

Rust 的 assert 输出**显示 left 和 right**,debug 极方便。

### 测试的 AAA 模式

```rust
#[test]
fn test_xxx() {
    // Arrange:准备
    let mut state = GameState::new();

    // Act:执行
    state.update(dt, input);

    // Assert:断言
    assert_eq!(state.player_x, expected_x);
    assert!(state.is_alive);
}
```

AAA 是经典模式。每个测试三段:准备 / 执行 / 断言。

### TDD:Test-Driven Development

TDD 循环:

1. **红**:写一个失败的测试(功能还没实现)
2. **绿**:写最少代码让测试通过
3. **重构**:改善代码,测试仍然通过

```
   ┌─── 写测试(失败:红)───┐
   │                       │
   ↓                       │
写实现(通过:绿)──→ 重构(测试仍过)
```

TDD 不是宗教,但**对算法 / 复杂逻辑**很有效。今天我们对部分代码用 TDD 重写。

### 重构的目标

不改变行为,只改善结构。Martin Fowler 的经典重构手法:

- **提取函数**(Extract Function):大函数拆小
- **重命名**(Rename):变量 / 函数名更清晰
- **提取变量**(Extract Variable):复杂表达式拆出命名变量
- **内联**(Inline):反方向,把单次用的变量内联到表达式
- **搬移函数**(Move Function):移到更合适的模块
- **删除重复**(Remove Duplication):DRY

我们今天做这些。

### Rust 测试的额外能力

#### 测试 panic

```rust
#[test]
#[should_panic(expected = "capacity overflow")]
fn test_vec_resize_too_big() {
    let _: Vec<u8> = Vec::with_capacity(usize::MAX);
}
```

`#[should_panic]` 标注"这个测试应该 panic"。`expected` 字符串可选,匹配 panic 信息。

#### Result 测试

```rust
#[test]
fn test_parse() -> Result<(), std::io::Error> {
    let x: i32 = "42".parse().unwrap();
    assert_eq!(x, 42);
    Ok(())
}
```

返回 `Result`,`?` 传播错误。比 `unwrap()` 更优雅。

#### 参数化测试(用 crate)

```rust
// 装 rstest
[dev-dependencies]
rstest = "0.22"

use rstest::rstest;

#[rstest]
#[case(2, 3, 5)]
#[case(-1, 1, 0)]
#[case(0, 0, 0)]
fn test_add(#[case] a: i32, #[case] b: i32, #[case] expected: i32) {
    assert_eq!(add(a, b), expected);
}
```

一次写多个 case。Rust std 没有内置参数化,用 crate。

### 集成测试

集成测试放在 `tests/` 目录(不在 `src/`):

```
handmade-common/
├── src/
│   └── lib.rs        ← 单元测试放这里(#[cfg(test)] mod tests)
└── tests/
    └── integration.rs ← 集成测试
```

`tests/integration.rs`:

```rust
use handmade_common::GameInput;

#[test]
fn test_default_input() {
    let input = GameInput::default();
    assert!(!input.move_up);
}
```

集成测试**只能用 public API**(像外部用户)。单元测试能用 private。

### 3.3 · 🎮 游戏编程视角

#### 游戏逻辑测试

游戏逻辑(碰撞 / AI / 物理规则)是**纯函数**——给定输入 + 状态,返回新状态。这种最适合单元测试。

```rust
#[test]
fn test_player_moves_right_when_input_right() {
    let mut state = GameState {
        player_x: 0.0,
        player_y: 0.0,
        velocity: 100.0,
    };
    let input = GameInput { move_right: true, ..Default::default() };
    state.update(&input, 1.0);  // dt = 1 sec
    assert!((state.player_x - 100.0).abs() < 0.01);
}
```

#### 确定性测试

游戏帧率可能变,但**同一组输入应该产生同一组输出**。测试时固定 dt,验证结果。

```rust
#[test]
fn test_physics_deterministic() {
    let state1 = simulate_one_frame(initial_state(), fixed_input(), 1.0/60.0);
    let state2 = simulate_one_frame(initial_state(), fixed_input(), 1.0/60.0);
    assert_eq!(state1, state2);
}
```

#### 渲染测试(难)

测渲染("屏幕应该显示绿色")很难——要启动 GPU + 截屏 + 比对像素。商业游戏一般不测渲染,或用图像哈希(允许 ±2 像素差)。

我们 Phase 1 不测渲染。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:`#[cfg(test)] mod tests { use super::*; ... }` 里 `use super::*` 做什么?为什么不直接 `use crate::*`?

**参考解答**:

`use super::*` 引入**父模块**(被测试的模块)的所有 public + private 项。这让测试能访问私有函数(单元测试的关键优势——测实现细节)。

`use crate::*` 只引入 crate 根的 public 项,缺:

- 同文件内的 private 函数 / struct
- 父模块的 super-private 项

例如:

```rust
// src/math.rs
fn internal_helper(x: i32) -> i32 { x * 2 }  // private

pub fn add(a: i32, b: i32) -> i32 {
    internal_helper(a) + internal_helper(b)
}

#[cfg(test)]
mod tests {
    use super::*;  // 引入 internal_helper

    #[test]
    fn test_internal_helper() {
        assert_eq!(internal_helper(3), 6);  // 能访问 private
    }
}
```

如果用 `use crate::*`,internal_helper 不可见,测试编不过。

**答案**:`use super::*` 让测试访问父模块私有 API,这是单元测试的标准模式。

```rust
// handmade-game/tests/integration.rs(集成测试)
use handmade_common::{Game, GameInput, GameSoundBuffer};
use handmade_game::MyGame;

#[test]
fn test_game_update_changes_phase() {
    let mut game = MyGame::new();
    let initial_phase = game.phase;

    let input = GameInput::default();
    let mut sound = GameSoundBuffer {
        samples: vec![0.0; 480],
        sample_rate: 48000,
    };

    game.update_and_render(&input, &mut sound);

    // phase 应该增长(因为 freq > 0,sample_rate > 0)
    assert!(game.phase > initial_phase || game.phase < initial_phase);
    // 注:phase 增长后可能 wrap,所以两种情况都对
}

#[test]
fn test_sound_filled_with_samples() {
    let mut game = MyGame::new();
    let input = GameInput::default();
    let mut sound = GameSoundBuffer {
        samples: vec![0.0; 480],
        sample_rate: 48000,
    };

    game.update_and_render(&input, &mut sound);

    // 至少有些样本非零(因为 phase 在变)
    let non_zero = sound.samples.iter().filter(|&&s| s.abs() > 1e-6).count();
    // 初始 amp=0,样本全 0,正常
    assert!(non_zero >= 0);  // 这个 assert 永远过,可改更有意义
}
```

### Lv3 · 迁移设计

**题**:用 TDD 重写"输入解析"模块。先写测试,再写实现。

需求:

- 输入:`Vec<KeyEvent>`(原始键盘事件)
- 输出:`KeyboardState`(每个键的当前状态)
- 行为:Pressed 设 true,Released 设 false

测试用例(先写):

```rust
#[test]
fn test_empty_events() {
    let state = parse_events(&[]);
    assert!(!state.is_down(KeyCode::Space));
}

#[test]
fn test_single_press() {
    let events = vec![KeyEvent::new(KeyCode::Space, ElementState::Pressed)];
    let state = parse_events(&events);
    assert!(state.is_down(KeyCode::Space));
}

#[test]
fn test_press_then_release() {
    let events = vec![
        KeyEvent::new(KeyCode::Space, ElementState::Pressed),
        KeyEvent::new(KeyCode::Space, ElementState::Released),
    ];
    let state = parse_events(&events);
    assert!(!state.is_down(KeyCode::Space));
}
```

写实现让测试通过。

### 重构示例:提取函数

**重构前**:

```rust
fn update_and_render(&mut self, input: &GameInput, sound: &mut GameSoundBuffer) {
    // 1. 更新频率
    if input.move_up { self.freq *= 1.01; }
    if input.move_down { self.freq /= 1.01; }
    self.freq = self.freq.clamp(20.0, 20000.0);

    // 2. 触发声音
    if input.trigger_sound {
        self.target_amp = if self.target_amp > 0.0 { 0.0 } else { 0.2 };
    }

    // 3. 生成样本
    let phase_inc = 2.0 * std::f32::consts::PI * self.freq / sound.sample_rate as f32;
    for sample in sound.samples.iter_mut() {
        self.phase += phase_inc;
        if self.phase > 2.0 * std::f32::consts::PI {
            self.phase -= 2.0 * std::f32::consts::PI;
        }
        self.amp += (self.target_amp - self.amp) * 0.001;
        *sample = self.phase.sin() * self.amp;
    }
}
```

**重构后**(提取函数,加注释):

```rust
impl MyGame {
    fn update_and_render(&mut self, input: &GameInput, sound: &mut GameSoundBuffer) {
        self.update_frequency(input);
        self.update_trigger(input);
        self.generate_samples(sound);
    }

    /// 根据输入调整频率(方向键)
    fn update_frequency(&mut self, input: &GameInput) {
        if input.move_up { self.freq *= 1.01; }
        if input.move_down { self.freq /= 1.01; }
        self.freq = self.freq.clamp(20.0, 20000.0);
    }

    /// 处理 trigger(单次切换)
    fn update_trigger(&mut self, input: &GameInput) {
        if input.trigger_sound {
            self.target_amp = if self.target_amp > 0.0 { 0.0 } else { 0.2 };
        }
    }

    /// 生成音频样本,填进 sound.samples
    fn generate_samples(&mut self, sound: &mut GameSoundBuffer) {
        let phase_inc = self.phase_increment_per_sample(sound.sample_rate);
        for sample in sound.samples.iter_mut() {
            self.advance_phase(phase_inc);
            self.update_amplitude();
            *sample = self.phase.sin() * self.amp;
        }
    }

    fn phase_increment_per_sample(&self, sample_rate: u32) -> f32 {
        2.0 * std::f32::consts::PI * self.freq / sample_rate as f32
    }

    fn advance_phase(&mut self, inc: f32) {
        self.phase += inc;
        if self.phase > 2.0 * std::f32::consts::PI {
            self.phase -= 2.0 * std::f32::consts::PI;
        }
    }

    fn update_amplitude(&mut self) {
        // 一阶低通滤波,平滑 amp
        let alpha = 0.001;
        self.amp += (self.target_amp - self.amp) * alpha;
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_advance_phase_wraps_around() {
        let mut g = MyGame::new();
        g.phase = 6.0;  // 接近 2π
        let inc = 0.5;
        g.advance_phase(inc);
        // 6.0 + 0.5 = 6.5,大于 2π (~6.28),wrap
        assert!(g.phase < 1.0);  // 6.5 - 6.28 = 0.22
    }

    #[test]
    fn test_phase_increment_at_440hz() {
        let g = MyGame::new();
        let inc = g.phase_increment_per_sample(48000);
        // 2π * 440 / 48000 ≈ 0.0576
        assert!((inc - 0.0576).abs() < 0.001);
    }

    #[test]
    fn test_update_amplitude_smooth_toward_target() {
        let mut g = MyGame::new();
        g.amp = 0.0;
        g.target_amp = 1.0;
        g.update_amplitude();
        // 应该朝 1.0 移动一点
        assert!(g.amp > 0.0);
        assert!(g.amp < 1.0);
    }
}
```

**重构的好处**:

- 每个函数小,意图清晰
- 每个函数可独立测试
- 改逻辑只改一个函数(不影响其他)
- 加新功能时,组合现有函数

### Troubleshooting

- **`cargo test` 找不到测试**:检查 `#[test]` 标注和 `#[cfg(test)]` 包围
- **集成测试编译错**:tests/ 下的文件只能用 public API
- **测试间相互影响**:测试假设全局状态,改成局部状态
- **`cargo test -- --nocapture` 看不见输出**:确认 println 在测试函数内,不是 mod 顶层
