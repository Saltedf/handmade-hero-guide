# Day 018 · 帧率控制与 VSync:精度、抖动、混合策略

> Day 004 你写了基于 dt 的动画——方块以"每秒 200 像素"匀速运动,无论帧率多少。但如果你跑游戏,测一下 FPS——可能 200、可能 1000、可能 5000。CPU 全速跑,每帧 0.2ms,30000 FPS。这浪费电、烫 CPU、笔记本风扇狂响。Day 018 解决"**怎么把帧率锁定到 60 FPS**"。听起来一行 `sleep` 就够,实际牵扯 OS 调度精度、显示器刷新、抖动等深水区。理解它你就理解了所有实时系统的"时间管理"。

## 0 · 为什么要有这一天

你不锁帧率,游戏跑 5000 FPS,问题:

1. **CPU/GPU 100% 占用**——烫、费电、风扇响。笔记本 10 分钟没电。
2. ** tearing(画面撕裂)**——你写后缓冲时屏幕正在读,出现"上半帧 / 下半帧"割裂。
3. **物理不稳定**——dt 太小(0.0002 秒),浮点误差累积,物理模拟漂移。
4. **多任务影响**——你的游戏霸占 CPU,其他程序卡。
5. **玩家感受**——60 FPS 和 5000 FPS 视觉差不多(屏幕只有 60-144 Hz),但能耗差 80 倍。

最朴素的解法:`sleep(剩余时间)`。比如目标 16.67ms,你这帧用了 12ms,sleep 4.67ms。

听起来对,实际有问题:

**问题 1:sleep 精度差**。Windows 默认 timer 精度 15.6ms——你 `sleep(4)` 实际睡 15ms。从 60 FPS 掉到 30 FPS。Linux 精度好一些(几 ms),但也不到 ms。

**问题 2:OS 调度抖动**。sleep 4ms 完后,OS 不一定立刻调度你,可能再过 2ms 才上 CPU。抖动 ±2ms 看起来 60 FPS,实际 50-70 FPS 飘。

**问题 3:VSync 是另一回事**。显示器每 16.67ms 刷新一次(60Hz)。GPU 可以等刷新——叫 VSync。但 VSync 只解决 tearing,不解决 CPU 占用(你还要"按时"工作,不能早不能晚)。

Casey 这集的目标:**精确锁 60 FPS,抖动 < 1ms,CPU 占用低**。他用了一个混合策略:sleep 大部分时间(省 CPU),spin-wait 最后 1ms(精度高)。这种"sleep + spin"组合是工程上的经典 trade-off。

**心理锚点**:读完今天,你能:

- 解释为什么直接 `sleep` 锁帧率不准
- 写出 sleep + spin_loop 混合策略的 Rust 代码
- 知道 Windows `timeBeginPeriod(1)` 和 Linux 默认精度的差别
- 解释 VSync 的本质,以及为什么 FPS 玩家关 VSync
- 知道 G-Sync / FreeSync 是 VSync 的进化
- 用 mangohud 实时看游戏的 FPS / 帧时间

## 1 · Casey 今天做了什么

Day 018 Casey 的核心动作:

1. **目标 60 FPS**:每帧目标耗时 16.67ms(1/60 秒)。
2. **测量当前帧耗时**:`QueryPerformanceCounter` 拿开始 / 结束 tick,差值除以频率得秒。
3. **sleep 大部分**:如果剩余 > 2ms,`Sleep(剩余 - 1)`。
4. **spin 最后 1ms**:`while QueryPerformanceCounter < target {}`。
5. **Win32 特定 trick**:`timeBeginPeriod(1)` 提升系统 timer 精度到 1ms(全局影响,程序退出时 `timeEndPeriod(1)` 还原)。

混合策略的妙处:sleep 14ms,spin 1ms,总 15ms。CPU 实际"忙"只 1ms,其余 sleep,占用低;但精度由 spin 决定,纳秒级。

Casey 这集还讨论了"VSync 是另一回事"——VSync 由 GPU / 显示器处理,和软件锁帧率是独立的。你可以两者都用(VSync on + 软件锁 60),也可以只 VSync(软件不锁,但 SwapBuffers 自动等)。

## 2 · 心智模型

### 类比:帧率锁定是"定速巡航"

你开车想保持 60 km/h。三种做法:

**做法 A:全油门**——车跑 200 km/h,超速,危险。(等价于不锁帧率,跑 5000 FPS)

**做法 B:踩一下松一下**——油门踩下加速到 65,松开减速到 55,循环。速度在 55-65 抖动,不精确。(等价于纯 sleep,精度差)

**做法 C:定速巡航(混合)**——油门自动调整,大部分时间中等油门(省油 = 省 CPU),接近目标时精细微调(精确)。(等价于 sleep + spin 混合)

Casey 选 C——既省 CPU 又精确。

### 严谨:精确锁帧率

目标:每帧固定 16.67ms(60 FPS)。算法:

```
frame_start = now()
do_work()
work_elapsed = now() - frame_start
remaining = 16.67ms - work_elapsed
if remaining > 2ms:
    sleep(remaining - 1ms)   # 故意早醒 1ms
while now() - frame_start < 16.67ms:
    spin_loop()              # 忙等剩余时间
```

为什么 sleep 后还要 spin?因为 sleep 不准。`sleep(4)` 可能睡 3ms 或 8ms。

- 睡 3ms(早醒):还差 1.67ms,spin 1.67ms。OK。
- 睡 8ms(过睡):已经超时了,直接进下一帧。FPS 略低,但不会跳变。

故意"早醒"的 1ms 余量是为了避免"过睡"。过睡可怕——FPS 直接掉一帧(60→30)。早醒没事——spin 补回来。

Rust 实现:

```rust
use std::time::{Duration, Instant};

/// 精确 sleep 到 target_dt 时间过完
/// 
/// # 算法
/// - 如果剩余 > 2ms:sleep(剩余 - 1ms),故意早醒
/// - 然后 spin-wait 剩余时间(忙等,精度高)
pub fn precise_sleep(target_dt: Duration, frame_start: Instant) {
    let elapsed = frame_start.elapsed();
    let remaining = target_dt.checked_sub(elapsed).unwrap_or(Duration::ZERO);
    
    if remaining > Duration::from_millis(2) {
        // 大部分时间真睡,留 1ms 余量
        std::thread::sleep(remaining - Duration::from_millis(1));
    }
    
    // 剩余时间忙等(精度高)
    while frame_start.elapsed() < target_dt {
        std::hint::spin_loop();
    }
}
```

逐行解释:

- `checked_sub`——返回 `Option<Duration>`,如果结果为负(已经超时)返回 `None`。`.unwrap_or(Duration::ZERO)` 处理这个情况。
- `thread::sleep(remaining - 1ms)`——真睡,让出 CPU。OS 调度其他线程。1ms 余量防过睡。
- `std::hint::spin_loop()`——CPU hint,告诉它"我在 spin"。x86 编译成 `PAUSE` 指令,降功耗 + 防止流水线 stall。比纯 `{}` 循环好。

`spin_loop` 不省 CPU(还是 100% 一个核),但只是几毫秒,影响小。

### 主循环里用

```rust
const TARGET_FPS: u32 = 60;
const TARGET_DT: Duration = Duration::from_secs_f32(1.0 / TARGET_FPS as f32);

fn main() {
    let event_loop = ...;
    let mut app = App::new();
    
    event_loop.run_app(&mut app).unwrap();
}

// 在 App 的 window_event 处理 RedrawRequested 时
fn window_event(...) {
    if let WindowEvent::RedrawRequested = event {
        let frame_start = Instant::now();
        
        app.update(app.input.dt);
        app.render();
        
        // 锁帧率
        precise_sleep(TARGET_DT, frame_start);
        
        // 重新调度下一帧
        window.request_redraw();
    }
}
```

注意:在 winit 的事件循环里,**不能直接 block 主循环**——winit 的事件循环不是你控制的。你需要在 `AboutToWait` 事件里调度 redraw,或在单独线程跑游戏循环。

简化方案:用 `std::thread::sleep` 不 spin,接受几 ms 抖动。生产代码用更精细的方案(下面 §5)。

### VSync:另一回事

VSync(Vertical Synchronization,垂直同步)是 GPU / 显示器层级的概念:

- 显示器每 16.67ms 刷新一次(60Hz),从上到下扫描像素
- VSync = SwapBuffers 等下一次刷新再 swap,保证 swap 在"V blank"(垂直消隐,扫描线回到顶部)时发生
- VSync on:无 tearing,但延迟最高一帧(16ms)
- VSync off:tearing(画面撕裂),但延迟最低

VSync 解决"画面撕裂",不解决"帧率锁定"。即使 VSync on,你的程序还是要每帧"准备好"。

**FPS 玩家为什么关 VSync**:延迟。开 VSync,你按键 → 屏幕变化要等下一次 V blank,最多 16ms 延迟。FPS 玩家要 < 5ms 延迟,关 VSync 接受 tearing。

**G-Sync / FreeSync**(可变刷新率):显示器自身刷新率可变,跟着 GPU 输出节奏。144Hz 显示器在 60-144 之间任意刷新。VSync 进化版——既无 tearing,又低延迟。需要显示器 + 显卡都支持。

### Rust + winit / softbuffer 怎么开 VSync

winit 本身不暴露 VSync(VSync 是 GPU 概念,winit 不管渲染)。需要用 glutin / wgpu / softbuffer:

- **softbuffer**:`Surface` 默认走 wl_shm,自动由合成器(KWin)处理 VSync
- **glutin**:`ContextBuilder::with_vsync(true)`
- **wgpu**:`PresentMode::Fifo`(等价 VSync on) / `PresentMode::Mailbox`(低延迟 VSync) / `PresentMode::Immediate`(VSync off)

Wayland 下,VSync 由合成器强制(KWin 控制何时让你画)。你的 sleep 时间可能和 KWin 期望不一致——winit 帮你处理,你只需要响应 `RedrawRequested`。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏帧率目标的传统 wisdom:

| 游戏类型 | 目标 FPS | 理由 |
|---|---|---|
| 电影 / 过场 | 24 FPS | 电影标准,有"电影感" |
| 控制台游戏 | 30 FPS | 电视 + 沙发距离,30 够流畅 |
| PC 游戏 | 60 FPS | 标准目标 |
| 竞技 FPS | 144+ FPS | 低延迟,玩家反应快 |
| VR 游戏 | 90+ FPS | 防 VR 晕眩 |

**fixed timestep vs variable timestep**:

**Variable timestep**(Casey 用):每帧 dt 不同,游戏逻辑用 `* dt` 缩放。简单,帧率自适应。物理可能有微小不一致。

**Fixed timestep**:固定 dt = 1/60,如果实际帧时间长,一帧内 update 多次。物理一致(每次 update 步长一样),但实现复杂。

```rust
// fixed timestep 算法
let mut accumulator = 0.0;
const FIXED_DT: f32 = 1.0 / 60.0;

loop {
    let frame_dt = measure_dt();
    accumulator += frame_dt;
    
    while accumulator >= FIXED_DT {
        update(FIXED_DT);  // 物理 update 用固定 dt
        accumulator -= FIXED_DT;
    }
    
    render();  // 渲染用插值
}
```

Casey 在 Day 018 用 variable timestep。后期 Day 50+(碰撞检测)发现物理穿透问题,会讨论 fixed timestep。

### 3.2 · 🎨 图形学视角

帧率相关的图形学概念:

**Frame pacing**:每帧时间一致,无抖动。比"高 FPS"更重要——60 FPS 平均但 30-90 跳变,比稳定 60 看起来卡。mangohud / Steam 内置 FPS 图表可视化 frame pacing。

**Input latency**(输入延迟):按键 → 屏幕变化的时间。组成:
- 输入设备 → OS:1-5ms(USB / Bluetooth)
- OS → 应用:1-5ms(事件队列)
- 应用处理 → 渲染完:5-15ms(一帧)
- 渲染 → 显示:5-15ms(显示延迟)
- 总:12-40ms

**Game mode / low latency mode**:现代显示器和 GPU 有"低延迟模式",关闭 VSync buffer,降低显示延迟。Valve Source 引擎的"raw input"也是降低输入 → 应用延迟。

**帧生成时间**(frame generation time):你写代码的快慢。和帧率锁定是两回事——你写一帧 5ms,sleep 11ms 锁 60 FPS。如果代码慢到 20ms,即使你想锁 60,实际 50 FPS。

**DLSS / FSR 帧生成**:GPU 用 AI 在两帧之间"插值"出新帧,把 30 FPS 变 60 FPS。但有副作用(artifact,延迟增加)。Casey 在 HH 全剧不用(2014 年项目,这些技术后来才有)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的 timer 相关 API:

| API | 精度 | 用途 |
|---|---|---|
| `sleep(3)` / `usleep(3)` | ~10ms | POSIX 老接口 |
| `nanosleep(2)` | ~1ms | POSIX 标准 |
| `clock_nanosleep(2)` | ~100μs | 高精度,可指定 clock |
| `timerfd_create(2)` | ~100μs | 文件描述符 timer,可 epoll |
| `futex(2)` | ~1μs | fast mutex,内部用 |
| `pthread_cond_timedwait` | ~100μs | 条件变量超时 |

Rust 的 `std::thread::sleep` 在 Linux 走 `nanosleep` / `clock_nanosleep`。理论纳秒级,实际毫秒级(取决于 HZ 内核配置,通常 250 或 1000)。

**check 内核 HZ**:

```bash
# 内核时钟频率(每秒多少 tick)
cat /proc/sys/kernel/hz  # 不一定有
# 或
getconf CLK_TCK
# 输出:100  ← 默认 100 Hz,tick 10ms

# 实际上桌面内核通常 1000 Hz(tick 1ms)
zcat /proc/config.gz | grep CONFIG_HZ
# CONFIG_HZ_1000=y
# CONFIG_HZ=1000
```

1000 Hz 意味着 timer 精度 1ms。`sleep(1)` 实际可能睡 1-2ms。够游戏用。

**NO_HZ_FULL**(tickless kernel):某些核心不接收 timer tick,深度睡眠省电。服务器 / 笔记本省电关键。游戏机模式可以关 NO_HZ_FULL 保证低延迟。

**实时调度**(SCHED_FIFO / SCHED_RR):告诉 OS"我是高优先级,别抢我 CPU"。专业音频(JACK)用,游戏一般不用(影响其他程序)。

实战命令:

```bash
# 1. 看进程优先级
ps -eo pid,nice,cmd | grep your-game
# nice 值 -20 到 19,越低优先级越高

# 2. 提高游戏优先级
sudo renice -10 -p $(pgrep your-game)

# 3. 用 SCHED_FIFO 跑(需要 root)
sudo chrt -f 80 ./your-game
# -f = SCHED_FIFO, 80 = 优先级

# 4. 隔离 CPU 核心(防止其他程序抢)
sudo tuna --cpus=2,3 --isolate
# CPU 2,3 给游戏专用

# 5. 实时帧率监测
mangohud ./your-game
# 屏幕角落显示 FPS / 帧时间 / CPU / GPU

# 6. 看帧时间分布
mangohud-vklayer-control
# 详细图表
```

### 3.4 · 🦀 Rust 生态视角

Rust 标准库的 timer:

```rust
use std::time::{Duration, Instant};

// 测时间
let start = Instant::now();
do_something();
let elapsed = start.elapsed();  // Duration

// sleep
std::thread::sleep(Duration::from_millis(16));

// 精确 sleep(我们的实现)

```

Rust 的 `Instant` 在 Linux 上用 `clock_gettime(CLOCK_MONOTONIC)`,纳秒精度,几十纳秒开销。Casey 在 C 里用 `QueryPerformanceCounter`,Windows 等价物。

**Rust crate**:
- `timer` crate:更高层,带 callback
- `tokio::time`:async 风格 sleep
- `fluvio` / `smol`:轻量 async runtime

**profile crate**:
- `puffin`:游戏内 profiler,实时可视化
- `superluminal`:Windows 专用
- `tracy`:跨平台,游戏标准
- `mangohud`:Linux 系统级 HUD,不用代码改动

**实战**:Phase 1 用 `Instant` + 我们的 `precise_sleep`,够用。Day 113+ 性能调优阶段接 Tracy。

**Rust 编译时间和锁帧率无关,但影响"热重载体感"**——`cargo build` 几秒,加上 sleep 锁帧率,你改代码到看到效果是几秒 + 16ms ≈ 几秒。不算瓶颈。

## 4 · 认知地图

### 4.1 上级

- **实时系统**(Real-time System)——必须在 deadline 前响应的系统
- **时间管理**(Time Management)——程序怎么感知 / 控制 时间
- **OS 调度**——OS 怎么分配 CPU 时间给进程
- **精度 vs 功耗 trade-off**——精度高 = spin(费 CPU),精度低 = sleep(省电)

### 4.2 同级

| 方案 | 精度 | CPU 占用 | 复杂度 | 何时用 |
|---|---|---|---|---|
| 纯 sleep | 低(~10ms) | 低 | 简单 | 非关键应用 |
| 纯 spin | 极高(纳秒) | 100% | 极简 | 短期忙等 |
| sleep + spin 混合 | 高(< 1ms) | 低 | 中 | 实时游戏(Casey 用) |
| VSync | 高(由显示器) | 极低 | 简单 | 标准图形应用 |
| RTOS(实时 OS) | 极高(微秒) | 中 | 极复杂 | 工业控制 / 无人机 |

### 4.3 下级

- **Instant / Duration**(Rust std)——时间 API
- **spin_loop hint**——CPU 提示,降功耗 spin
- **`thread::sleep`**——让出 CPU 的 sleep
- **`timeBeginPeriod(1)`**(Win32)——提高 Windows timer 精度
- **`nanosleep` / `clock_nanosleep`**(POSIX)——Linux 高精度 sleep
- **G-Sync / FreeSync**——可变刷新率显示器
- **frame pacing**——帧节奏平滑性

## 5 · 对照与变奏

### 同一问题:不同 OS 的 timer 精度

| OS | 默认 timer 精度 | 提高 |
|---|---|---|
| Windows | 15.6ms | `timeBeginPeriod(1)` → 1ms |
| Linux | 1ms(1000Hz 内核) | `SCHED_FIFO` + mlock |
| macOS | 1ms | 类似 Linux |
| RTOS(VxWorks / FreeRTOS) | 微秒 | 默认就高 |

Windows 的 15.6ms 默认精度是历史遗留(节能考虑)。Casey 在 HH 调用 `timeBeginPeriod(1)`,代价是系统全局功耗略升。

**Linux 比 Windows 适合游戏开发的一个原因**——timer 精度天然高,不需要全局副作用。

### CPU 速度 vs GPU 速度 vs 显示器速度

游戏三个时钟:

- **CPU 时钟**:几 GHz,每秒几十亿指令。处理游戏逻辑、物理、AI。
- **GPU 时钟**:同样几 GHz,但并行。处理渲染。
- **显示器刷新**:60-240 Hz。最终用户看到的。

游戏循环要协调三者:

```
CPU update → GPU render → 显示器 refresh
 16ms        16ms          16ms
```

理想:三者节奏一致(16ms / 60 FPS)。现实:CPU 和 GPU 可能快(0.5ms 完成),sleep 等;也可能慢(20ms),掉帧。

**Double buffering**:CPU/GPU 写后缓冲,显示器读前缓冲。swap 时切换。这避免了"边写边读"的 tearing。

**Triple buffering**:多一个缓冲。CPU/GPU 不等 swap,继续画下一帧。延迟略高但帧率不掉。

Casey 在 Day 003 用 double buffering(GDI 自动处理),后期切 OpenGL 时升级到 triple。

### 历史演化:游戏帧率 40 年

- **1980s**:60 FPS(NTSC) / 50 FPS(PAL)——和电视同步,固定
- **1990s PC**:30-60 FPS,dt-based 动画起步
- **2000s**:60 FPS 标准,部分游戏 30(主机性能限制)
- **2010s**:120 / 144 Hz 显示器普及,FPS 玩家要求更高
- **2020s**:240 / 360 Hz 显示器,帧率竞赛 + 低延迟优化

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 在 sleep 后还要 spin-wait 剩余时间。为什么不直接 sleep 到 target?具体说明 sleep 不准的原因。

进一步:为什么故意"早醒 1ms"?如果"过睡 1ms"会怎样?

**参考解答**:

**sleep 不准的原因**:

1. **OS timer 精度**:Linux 1000Hz 内核,tick 1ms。`sleep(4)` 可能睡 4-5ms。
2. **OS 调度延迟**:sleep 时间到,OS 不一定立刻调度你,可能再过 1-2ms。
3. **硬件中断**:其他硬件中断(网卡、USB)打断 OS,延后调度。

**早醒 vs 过睡**:

- **早醒 1ms**:还差 1ms 到 target,spin 1ms 补回。OK,精度高。
- **过睡 1ms**:已经超时,直接进下一帧。如果目标 16.67ms,实际 17.67ms,FPS = 56.6。下一帧 dt 大,可能再超时,连锁反应。**严重**时 spiral of death——每帧越来越慢。

故意早醒 1ms 是"防御性编程"——给 OS 留余量,避免过睡。代价是 spin 1ms 的 CPU(很小)。

```rust
use std::time::{Duration, Instant};

pub fn precise_sleep(target_dt: Duration, frame_start: Instant) {
    let elapsed = frame_start.elapsed();
    let remaining = target_dt.checked_sub(elapsed).unwrap_or(Duration::ZERO);
    
    if remaining > Duration::from_millis(2) {
        std::thread::sleep(remaining - Duration::from_millis(1));
    }
    
    while frame_start.elapsed() < target_dt {
        std::hint::spin_loop();
    }
}

fn main() {
    const TARGET: Duration = Duration::from_nanos(16_666_667);  // 16.67ms
    const N: usize = 1000;
    
    let mut frame_times = Vec::with_capacity(N);
    
    // warmup
    for _ in 0..10 {
        let start = Instant::now();
        precise_sleep(TARGET, start);
    }
    
    // 测试
    for _ in 0..N {
        let start = Instant::now();
        precise_sleep(TARGET, start);
        frame_times.push(start.elapsed());
    }
    
    // 统计
    let total: Duration = frame_times.iter().sum();
    let avg = total / N as u32;
    let max = frame_times.iter().max().unwrap();
    let min = frame_times.iter().min().unwrap();
    
    // 抖动 = max - min
    let jitter = *max - *min;
    
    println!("Target: {:?}", TARGET);
    println!("Average: {:?}", avg);
    println!("Min: {:?}", min);
    println!("Max: {:?}", max);
    println!("Jitter: {:?}", jitter);
    
    // 验证
    assert!(jitter < Duration::from_millis(2), "Jitter too high: {:?}", jitter);
    println!("All checks passed!");
}
```

### Rust:把帧率锁定接入 winit 主循环

winit 的事件循环不直接让你"主循环",需要在事件回调里调度。

```rust
// src/fps_demo.rs
use winit::application::ApplicationHandler;
use winit::event::{WindowEvent, ElementState, KeyEvent};
use winit::event_loop::EventLoop;
use winit::keyboard::{KeyCode, PhysicalKey};
use winit::window::Window;
use std::sync::Arc;
use std::time::{Duration, Instant};

const WIDTH: u32 = 960;
const HEIGHT: u32 = 540;
const TARGET_FPS: u32 = 60;
const TARGET_DT: Duration = Duration::from_secs_f32(1.0 / TARGET_FPS as f32);

pub fn precise_sleep(target_dt: Duration, frame_start: Instant) {
    let elapsed = frame_start.elapsed();
    let remaining = target_dt.checked_sub(elapsed).unwrap_or(Duration::ZERO);
    if remaining > Duration::from_millis(2) {
        std::thread::sleep(remaining - Duration::from_millis(1));
    }
    while frame_start.elapsed() < target_dt {
        std::hint::spin_loop();
    }
}

struct App {
    window: Option<Arc<Window>>,
    surface: Option<softbuffer::Surface<Arc<Window>, Arc<Window>>>,
    frame_count: u64,
    last_fps_print: Instant,
    fps: u32,
    x: f32,
}

impl App {
    fn new() -> Self {
        Self {
            window: None, surface: None,
            frame_count: 0,
            last_fps_print: Instant::now(),
            fps: 0,
            x: 0.0,
        }
    }
}

impl ApplicationHandler for App {
    fn resumed(&mut self, event_loop: &winit::event_loop::ActiveEventLoop) {
        let window = Arc::new(event_loop.create_window(
            Window::default_attributes()
                .with_title("Day 018 FPS Lock")
                .with_inner_size(winit::dpi::LogicalSize::new(WIDTH, HEIGHT))
        ).unwrap());
        let context = softbuffer::Context::new(window.clone()).unwrap();
        let mut surface = softbuffer::Surface::new(&context, window.clone()).unwrap();
        let _ = surface.resize(
            std::num::NonZeroU32::new(WIDTH).unwrap(),
            std::num::NonZeroU32::new(HEIGHT).unwrap(),
        );
        self.window = Some(window);
        self.surface = Some(surface);
    }
    
    fn about_to_wait(&mut self, _event_loop: &winit::event_loop::ActiveEventLoop) {
        // winit 空闲时调度下一帧
        if let Some(w) = &self.window { w.request_redraw(); }
    }
    
    fn window_event(&mut self, event_loop: &winit::event_loop::ActiveEventLoop,
                    _id: winit::window::WindowId, event: WindowEvent) {
        match event {
            WindowEvent::CloseRequested => event_loop.exit(),
            WindowEvent::KeyboardInput { event: KeyEvent {
                physical_key: PhysicalKey::Code(code), ..
            }, .. } => {
                if code == KeyCode::Escape { event_loop.exit(); }
            }
            WindowEvent::RedrawRequested => {
                let frame_start = Instant::now();
                
                // 更新(简单:方块左右移动)
                self.x += 200.0 * TARGET_DT.as_secs_f32();
                if self.x > WIDTH as f32 { self.x = 0.0; }
                
                // 渲染
                if let Some(surface) = &mut self.surface {
                    if let Ok(mut buf) = surface.buffer_mut() {
                        for px in buf.iter_mut() { *px = 0xFF_00_00_00; }  // 黑底
                        let xi = self.x as i32;
                        for dy in 0..50 {
                            for dx in 0..50 {
                                let x = xi + dx;
                                let y = 250 + dy;
                                if x >= 0 && (x as u32) < WIDTH 
                                    && y >= 0 && (y as u32) < HEIGHT {
                                    buf[y as usize * WIDTH as usize + x as usize] = 0xFF_00_FF_00;
                                }
                            }
                        }
                        let _ = buf.present();
                    }
                }
                
                // 锁帧率
                precise_sleep(TARGET_DT, frame_start);
                
                // FPS 统计
                self.frame_count += 1;
                let now = Instant::now();
                if now - self.last_fps_print >= Duration::from_secs(1) {
                    self.fps = self.frame_count as u32;
                    self.frame_count = 0;
                    self.last_fps_print = now;
                    println!("FPS: {}", self.fps);
                }
            }
            _ => ()
        }
    }
}

fn main() {
    let event_loop = EventLoop::new().unwrap();
    let mut app = App::new();
    event_loop.run_app(&mut app).unwrap();
}
```

跑起来:

```bash

# 终端打印 FPS: 60 / 60 / 60 ...
```

**Troubleshooting**:

- **FPS 不稳(50-70 跳)**:check `timeBeginPeriod` 等价物——Linux 默认 1000Hz,够了。可能 winit 事件循环干扰,试试纯 sleep 模式
- **FPS 远低于 60**:你写代码太慢(> 16ms)。用 perf 找热点
- **FPS 远高于 60**:锁帧率逻辑没生效。检查 precise_sleep 调用位置
- **CPU 100%**:spin 太多,减少 spin 时间(增加 sleep 比例)
- **画面 tearing**:Wayland 下应该无 tearing(KWin 处理),X11 下可能要开 VSync
