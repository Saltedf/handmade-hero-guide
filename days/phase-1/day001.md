
# Day 001 · 搭建构建环境:从 build.bat 到 cargo

> 在写第一行游戏代码之前,必须先把"从源码到能跑的程序"这条路修通。Casey 用 `build.bat` 调 `cl.exe`(微软 MSVC 编译器)直接编出 `win32_handmade.exe`。我们在 Linux 上换一套等价工具:`cargo` 编出 Rust 二进制。今天不讲游戏,只把工具链搞明白,后面 12 天都站在它上面。

## 0 · 为什么要有这一天

你刚刚学完 Phase 0,会一些 Rust 基础语法,装好了 Arch Linux。你打开终端,敲 `vim main.rs`,写了 50 行 hello world,然后用 `rustc main.rs` 编出来跑——成功。你以为"构建"就这么简单。

但真做项目时立刻撞墙:

- 你的代码拆成 5 个 `.rs` 文件,`rustc main.rs` 报"找不到 module"
- 你想用别人写的库(`winit` 开窗口),`rustc` 说"unresolved import"
- 你改一行代码,要手动敲一长串命令重新编,改成 100 次手就废了
- 你想让 debug 版本快编、release 版本开优化,不知道怎么切
- 你和合作者用不同版本的 `rustc`,编出来的二进制行为不一样

这些都是 **build system**(构建系统)要解决的事。一个项目一旦超过 100 行,必须用构建系统,否则维护噩梦。Casey 在 Day 1 第一件事就是写 `build.bat`——不是因为他是"老派",而是**他要在第一天就把"源码 → exe"这条管道打通,后面 666 天每天就是改一行代码、跑一行命令**。

我们不用 `build.bat`(那是 Windows 专属的批处理),也不直接调 `rustc`(那是手动挡)。我们用 **cargo**——Rust 官方构建工具,相当于 Rust 版的 `make` + `npm` + `pip` 三合一。

**心理锚点**:读完今天,你能:

- 用 `cargo new` 起一个新项目,解释 `Cargo.toml` / `Cargo.lock` / `src/` / `target/` 各是什么
- 用 `cargo build` / `cargo run` / `cargo check` / `cargo build --release` 编译运行,知道它们各自干什么
- 在 `Cargo.toml` 里加依赖(`winit`, `softbuffer` 等),让 cargo 自动下载编译
- 用 `cargo fmt` / `cargo clippy` 保持代码风格统一
- 解释 cargo 编出的二进制放在 `target/debug/` 还是 `target/release/`,为什么

## 1 · Casey 今天做了什么

Casey Day 1 视频前 20 分钟全在搞工具链,核心动作:

1. 新建项目目录 `handmadehero/`,在里面再建子目录 `code/`(放源码)、`build/`(放编出的 exe)
2. 写一个 `build.bat` 批处理文件,内容是:调 `cl`(微软 C 编译器),传一堆参数(`-Zi` 调试信息、`-Od` 关优化、`kernel32.lib user32.lib` 链接系统库……),输出 `handmade.exe` 到 `build/`
3. 在 `code/` 里建 `handmade.cpp`,只写一个最小 `WinMain`(Windows GUI 程序的入口),里面 `MessageBox(0, "Hello", "Handmade Hero", 0)` 弹个对话框
4. 双击 `build.bat`,等几秒,`build/handmade.exe` 出现
5. 双击 `handmade.exe`,看到弹窗 "Hello"——**构建链路打通**

整个视频的核心不是 C 代码,是**"构建系统的设计哲学"**:Casey 坚持用最简单的脚本(`build.bat`),不碰 Visual Studio 工程,因为 IDE 把构建细节藏起来,他要"对每一步完全控制"。这个哲学在 Rust 里就是:**别用 IDE 的 Run 按钮,直接 `cargo build`**,你能看清每一步在做什么。

## 2 · 心智模型

### 类比:构建系统是"自动化的厨师长"

想象你开了一家餐厅。一开始你自己切菜、自己炒菜、自己端盘子——你掌控一切,但每道菜耗时巨大。后来你雇了一个**厨师长**,你只需要把"菜单"(`Cargo.toml`)给他,他就负责:去买食材(下载依赖)、洗切配料(编译依赖)、按顺序炒(链路)、最后端到桌上(产出二进制)。

**cargo 就是这个厨师长**。你写一份"菜单"告诉他要什么,剩下的他全管。

### 严格分离:源码 / 中间产物 / 最终产物

学构建系统最关键的概念是**这三个东西必须放在不同地方**:

```
handmade-hero/             ← 项目根目录
├── Cargo.toml             ← 菜单(项目元数据 + 依赖列表)
├── Cargo.lock             ← 锁定的依赖版本(自动生成,提交进 git)
├── src/                   ← 源码(你写的)
│   └── main.rs
└── target/                ← 中间产物 + 最终产物(自动生成,gitignore)
    ├── debug/             ← debug 构建的产物
    │   └── handmade_hero  ← 编出来的二进制
    └── release/           ← release 构建的产物
```

**为什么 `target/` 要 gitignore?**

- 它体积巨大(随便几百 MB,因为 cargo 把所有依赖都编一遍)
- 它可重建(从源码 `cargo build` 就回来了)
- 它平台相关(Windows 编出来的 `.exe` 和 Linux 编出来的 ELF 不能共用)

**为什么 `Cargo.lock` 要提交进 git?**(对于二进制项目)

- 它锁定了"今天我用 winit 0.30.5 这个精确版本",明天 winit 出 0.30.6 不会自动升级把你的代码搞坏
- 它让队友 clone 你仓库后编出来的二进制和你完全一样(可重现构建 reproducible build)

注意:对于**库项目**(被别人作为依赖引入),`Cargo.lock` 反而**不**提交——库不应该锁定下游用户的依赖版本。这个区别 The Rust Book FAQ 里有,我们后面遇到再说。

### `Cargo.toml`:菜单的语法

```toml
[package]                       # 这个 cargo 项目是个"包"
name = "handmade-hero"          # 包名( crates.io 上的唯一标识,也是二进制名)
version = "0.1.0"               # 语义化版本 major.minor.patch
edition = "2021"                # Rust edition(语言方言版本,2021 是当前推荐)

[dependencies]                  # 依赖列表
winit = "0.30"                  # 用 winit 0.30.x 最新版本( caret 要求 )
softbuffer = "0.4"              # 同上

[profile.release]               # release 构建的自定义
debug = true                    # 即使 release 也保留 debug 符号(我们调试用)
```

**关键字段解释**:

- `name` — 也是输出二进制名(`target/debug/handmade-hero`)
- `version` — **语义化版本**(Semantic Versioning)三段数字 `MAJOR.MINOR.PATCH`:
  - `MAJOR` 改了 = 接口破坏性变更,用户代码可能编不过
  - `MINOR` 改了 = 加了新功能但向后兼容
  - `PATCH` 改了 = 只修 bug
  - `winit = "0.30"` 这个写法等价于 `"^0.30"`,意思是 ">=0.30.0, <0.31.0",允许 MINOR 和 PATCH 升级,锁死 MAJOR
- `edition` — Rust 每三年发一个 edition(2015/2018/2021/2024),edition 改变**语言语法**(比如 2018 引入 `async`/`await` 关键字)。`edition = "2021"` 让你用最新语法,但编译器仍兼容老 edition 的依赖

### `cargo` 的核心命令

| 命令 | 做什么 | 速度 | 何时用 |
|---|---|---|---|
| `cargo check` | 只做类型检查,不生成代码 | 最快 | 改代码时频繁跑,看有没有 type 错误 |
| `cargo build` | 编译并链接,生成可执行文件 | 中等 | 第一次构建,或想跑前最后一次确认 |
| `cargo run` | `cargo build` + 立刻运行 | 中等 | 平时开发主用 |
| `cargo build --release` | 开优化(O3 / inline / SIMD) | 最慢(几分钟) | 性能测试、最终发布 |
| `cargo test` | 跑所有 `#[test]` 标记的函数 | 看 test 数量 | 写了单元测试时 |
| `cargo fmt` | 自动格式化代码 | 极快 | 提交前统一风格 |
| `cargo clippy` | 静态 lint(常见错误 / 改进建议) | 中等 | 提交前必跑 |
| `cargo doc --open` | 生成项目文档 HTML 并打开 | 中等 | 想看自己 / 依赖的 API |

**`check` vs `build` 的差别**:Rust 编译分两阶段——类型检查(borrow check 等)+ 代码生成(LLVM IR → 机器码)。`cargo check` 只跑第一阶段,**5 倍以上**比 `build` 快。改一行代码时跑 `check`,真的要跑程序时才 `build`。

### Debug vs Release:差别不只是"快慢"

很多人以为 release 就是"开了优化",其实差别更深:

| 维度 | debug | release |
|---|---|---|
| 优化等级 | `-O0`(完全不优化) | `-O3` 或 `-C opt-level=3` |
| 整数溢出 | panic(帮你抓 bug) | wrap around(性能优先) |
| `debug_assert!` | 启用 | 跳过 |
| `assert!` 检查 | 都启用 | 都启用(别用 release 关 assert) |
| 日志级别 | 通常 `debug` / `trace` 开 | 通常只 `info` 以上 |
| 编译时间 | 快(几秒) | 慢(几分钟) |
| 二进制大小 | 大(含调试符号) | 小(可 strip 符号) |

**整数溢出**这点要特别记住:在 debug 模式 `255u8 + 1` 会 panic,在 release 模式它静默 wrap 成 0。**绝对不要靠 debug 模式的 panic 检测生产 bug**——你应该写显式 `checked_add` / `wrapping_add`,让代码在任何模式都行为一致。

### 依赖怎么"下载"?— crates.io 生态

当你在 `Cargo.toml` 写 `winit = "0.30"`,第一次 `cargo build` 时,cargo 会:

1. 去 `https://crates.io/api/v1/crates/winit/0.30.5`(具体版本号从 index 查)下载 `.crate` 文件(本质是个 `.tar.gz`)
2. 解压到 `~/.cargo/registry/src/index.crates.io-HASH/winit-0.30.5/`
3. 编译 winit,把编出的 `.rlib`(Rust library)放进 `target/debug/deps/`
4. 链接进你的二进制

**整个过程全自动**。这就是 cargo 相对 `make` / CMake 的最大优势——**依赖管理内建**,不用 `pkg-config`、不用 `vcpkg`、不用 `apt install libfoo-dev`。

`crates.io` 是 Rust 官方的 crate registry(类比 npm 的 npmjs.com、Python 的 pypi.org)。任何人 `cargo publish` 都能发布,所以**质量参差**——后面 Lv4 会教你如何评估一个 crate 健康度。

## 3 · 四域深入

### 3.1 · 🐧 Linux 系统编程视角

Casey 的 `build.bat` 在 Linux 上对应什么?Linux 程序员不用 `.bat`(那是 Windows cmd 解释器脚本),传统 Unix 用 **shell 脚本**(`.sh`)或 **Makefile**。但 cargo 已经把这些都包了——你写 `Cargo.toml`,cargo 内部帮你跑 `rustc` + `ld` + `ar` 这一串。

不过,理解 cargo 背后跑的命令链路,有助于 debug 链接错误。**手动跑一遍最简单的 Rust 编译**:

```bash
# 1. 写一个 hello.rs
cat > /tmp/hello.rs <<'EOF'
fn main() {
    println!("hello from handmade hero");
}
EOF

# 2. 用 rustc 直接编(rustc 是 cargo 的底层)
rustc /tmp/hello.rs -o /tmp/hello
# 输出:空(rustc 成功就静默)

# 3. 看编出来的是什么
file /tmp/hello
# 输出:/tmp/hello: ELF 64-bit LSB shared object, x86-64, version 1 (SYSV),
#       dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, ...
# 注意 "ELF"——Linux 可执行格式。Windows 上编出来是 PE/COFF(.exe)。

# 4. 看它依赖哪些动态库
ldd /tmp/hello
# 输出类似:
#         linux-vdso.so.1 (0x...)
#         libgcc_s.so.1 => /usr/lib/libgcc_s.so.1 (0x...)
#         libc.so.6 => /usr/lib/libc.so.6 (0x...)
#         /lib64/ld-linux-x86-64.so.2 (0x...)
# libc 是 glibc,Linux 上的 C 标准库,几乎所有程序都依赖

# 5. 跑它
/tmp/hello
# 输出:hello from handmade hero
```

**关键概念:ELF**。Linux 上的可执行文件格式叫 **ELF**(Executable and Linkable Format)。它和 Windows 的 `.exe`(PE 格式)、macOS 的 **Mach-O** 是平级的——都是操作系统"加载器(loader)"认识的二进制布局。一个 ELF 文件内部有:

- `.text` 段:你编出来的机器指令
- `.rodata` 段:只读数据(字符串常量)
- `.data` 段:可读写全局变量
- `.bss` 段:未初始化全局变量(占位,不占文件空间)
- 程序头表:告诉内核"加载哪段到哪个虚拟地址"

这些东西 cargo 自动处理,你 99% 时间不用关心。但 Day 21 热重载时,我们会再回来聊 ELF 的 `.dynsym` 段(动态符号表),那是 `dlopen` 找符号的依据。

**Arch Linux 上的 cargo 安装**:

```bash
# 方式 1:用 pacman(系统包管理器,但版本可能滞后)
sudo pacman -S rust
rustc --version    # 应该输出类似 rustc 1.81.0

# 方式 2(推荐):用 rustup(官方多版本管理器)
sudo pacman -S rustup
rustup default stable
rustup show        # 显示当前工具链
# 输出:Default host: x86_64-unknown-linux-gnu
#       rustc 1.81.0 (eeb90cda1 2024-09-04)
```

**为什么推荐 rustup**?

- 不同项目可能要不同 Rust 版本,`rustup override set nightly` 可以为某个目录锁定 nightly
- 工具链组件(`clippy`, `rustfmt`, `rust-src`)通过 `rustup component add` 添加
- 跨平台一致(Windows / macOS 也用 rustup)

### 3.2 · 🦀 Rust 生态视角

cargo 不仅是构建工具,它还是 Rust 生态的"中枢神经":

- **包管理**:`Cargo.toml` 声明依赖,cargo 自动解析版本树(若两个依赖各需 winit 不同版本,cargo 会尝试 semver 兼容地选一个,冲突时报错)
- **构建脚本**:某些 crate 需要编译 C 代码或生成 Rust 代码(如 `bindgen`),通过 `build.rs` 实现
- **feature flags**:`Cargo.toml` 里写 `[features]`,允许条件编译(比如 `winit` 有 `serde` feature 来支持序列化)
- **workspace**:多个相关 crate 共享一个 `Cargo.lock` 和 `target/`,适合 monorepo
- **文档生成**:`cargo doc` 从 doc comment 生成 HTML
- **测试**:`cargo test` 跑 `#[test]`、`#[cfg(test)]` 模块、文档测试(```` ```rust ````代码块)

**workspace 示例**(本项目后面会用):

```toml
# 顶层 Cargo.toml
[workspace]
members = [
    "handmade-hero",      # 主二进制
    "handmade-platform",  # 平台层(后面 Day 11+)
    "handmade-game",      # 游戏层(后面 Day 11+)
]
resolver = "2"
```

每个 member 是自己的 crate,有自己的 `Cargo.toml` 和 `src/`。但它们共享一个 `target/`(避免重复编译)和 `Cargo.lock`(版本一致)。

### 3.3 · 🎮 游戏编程视角

游戏开发的构建需求比一般项目苛刻:

- **快速迭代**:改一行代码,从保存到看见效果必须 < 5 秒,否则流状态(Flow state)被破坏
- **多 target**:同一份代码要编 Windows / macOS / Linux / WebAssembly,每个平台用不同的图形 / 音频后端
- **资产打包**:游戏要打包贴图 / 模型 / 声音,传统做法是 `make` 把这些塞进 `.pak` 文件
- **热重载**:理想情况是改游戏逻辑代码不用重启游戏

Casey 的 Day 1 没解决所有这些(后面 22 天逐步解决),但**他第一天就把"改代码 → 看 exe 更新"这条链路压到几秒**——通过 `-Od`(关优化)+ `cl` 直接编(不走 IDE)。我们 Rust 这边对应:

- `cargo check`(秒级类型检查)代替 `cargo build` 验证
- `cargo run`(不重编依赖)直接跑
- Day 21+ 用 `cargo watch` + cdylib,改代码自动重编,程序里 `libloading` 重新加载

### 3.4 · 🎨 图形学视角

今天不涉及图形学(只是搭工具链)。但有一个边角:Rust 编出来的二进制默认 link **libc**,而 libc 在 Linux 上不会主动 link **X11 / Wayland** 库。当我们后面用 `winit` 开窗口时,winit 内部会 link `libX11.so` / `libwayland-client.so`——这些库**必须**系统装好(`sudo pacman -S libx11 wayland`),否则 cargo 编译时 link 报错。Day 2 会展开这个细节。

## 4 · 认知地图

### 4.1 上级

- **构建系统**(Build System)— 把源码变成可运行产物的工具集合(make / CMake / cargo / Bazel / Buck2)
- **包管理器**(Package Manager)— 管理依赖、版本、发布的工具(cargo / npm / pip / maven)
- **工具链**(Toolchain)— 编译器 + 链接器 + 标准库 + 调试器的合集

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| `cargo` | Rust 官方,内置依赖管理、文档、测试 | Rust 项目 | ✅ |
| `make` + `Makefile` | 通用,手动写规则,无依赖管理 | C/C++ 项目、混合语言 | 不用 |
| `CMake` | 跨平台 make 生成器,语法烂 | 跨平台 C/C++ | 不用 |
| `Bazel` / `Buck2` | 大规模 monorepo,增量编译极致 | Google / Meta 内部 | 不用 |
| `nix flakes` | 函数式、可重现、学习曲线陡 | DevOps / NixOS 用户 | 不用 |
| `just` | 只是命令快捷方式,不构建 | 辅助 cargo,跑脚本 | Day 22+ 可能用 |

### 4.3 下级

- **`rustc`** — 真正的 Rust 编译器,cargo 的底层
- **`Cargo.toml`** — 项目元数据 + 依赖声明
- **`Cargo.lock`** — 依赖版本锁(自动生成)
- **`target/`** — 所有构建产物
- **crates.io** — 依赖来源

## 5 · 对照与变奏

### Casey 的 `build.bat` vs cargo

| 维度 | Casey 的 `build.bat` | cargo |
|---|---|---|
| 文件 | `build.bat`(20 行左右) | `Cargo.toml` + `Cargo.lock` |
| 依赖管理 | 手动(`#include <windows.h>`,系统库) | 自动(`crates.io`) |
| 增量编译 | 手动(每次全编) | 自动(基于文件 hash) |
| 平台 | Windows 专属 | 跨平台 |
| 透明度 | 极高(每行 cl 命令都看得见) | 中等(默认输出简洁,`-v` 看 verbose) |
| 学习曲线 | 低(就是 shell 脚本) | 中(要学 toml 语法、feature、workspace) |

**关键洞察**:Casey 选 `build.bat` 不是因为它"更好",而是因为 Handmade Hero 是教学项目,**他要让你看清每一步**。生产环境(尤其是 Rust 项目),cargo 的依赖管理 + 增量编译 + 跨平台价值远高于"完全控制"。

### 跨语言对比

| 语言 | 构建工具 | 依赖来源 | 标志性问题 |
|---|---|---|---|
| C/C++ | make / CMake / Ninja | 系统包管理器 + 手动 | 依赖地狱 |
| Java / Kotlin | Gradle / Maven | Maven Central | 配置冗长 |
| Go | `go build`(内建) | Go modules | 简单但灵活性低 |
| Rust | cargo | crates.io | **平衡好**(社区共识) |
| Python | pip / poetry / uv | PyPI | 历史包袱重 |
| Node.js | npm / pnpm / yarn | npmjs.com | `node_modules` 黑洞 |

Rust 社区普遍认为 cargo 是 Rust 成功的关键之一——**零碎片化**,几乎所有 Rust 项目都用 cargo,IDE 集成、CI、文档生成、发布都基于它。

### 历史演化

- **1976**:Make 诞生(Bell Labs),最早处理 C 编译依赖

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:你 `cargo new --bin foo` 后,目录里出现 `Cargo.toml`、`Cargo.lock`、`src/main.rs`、`target/`。哪些应该提交进 git,哪些应该 `.gitignore`?为什么?

**参考解答**:

| 文件 | 提交 / gitignore | 理由 |
|---|---|---|
| `Cargo.toml` | ✅ 提交 | 项目元数据,合作者需要知道你用了哪些依赖 |
| `Cargo.lock` | ✅ 提交(二进制)/ ❌(库) | 二进制要可重现;库不该锁下游 |
| `src/main.rs` | ✅ 提交 | 你的源码 |
| `target/` | ❌ gitignore | 体积巨大、可重建、平台相关 |
| `.gitignore` | ✅ 提交 | 让队友不用手动 ignore |

特别地,`cargo new` 自动生成了 `.gitignore` 写了 `/target`,你不用改。

## 8 · Rust / Arch 落地代码

### 完整 Rust 示例:`cargo new` 后的目录布局

执行下面命令,得到本教程后面所有天的起点:

```bash
# 1. 在你选的工作目录(假设 ~/src)
cd ~/src
cargo new --bin handmade-hero
cd handmade-hero

# 2. 把 Cargo.toml 改成下面内容
cat > Cargo.toml <<'EOF'
[package]
name = "handmade-hero"
version = "0.1.0"
edition = "2021"
authors = ["Your Name <you@example.com>"]

[dependencies]
# Phase 1 后面几天会加:
# winit = "0.30"
# softbuffer = "0.4"
# cpal = "0.15"
# gilrs = "0.10"
# libloading = "0.8"

[profile.release]
debug = true   # 保留调试符号,即使 release
opt-level = 3  # 最高优化
EOF

# 3. main.rs 加一个能区分 debug / release 的 hello
cat > src/main.rs <<'EOF'
fn main() {
    // cfg! 宏在编译期求值,告诉你当前是不是 release
    if cfg!(debug_assertions) {
        println!("[debug] Handmade Hero Day 1");
    } else {
        println!("[release] Handmade Hero Day 1");
    }

    // 打印 cargo 注入的环境变量(证明 cargo 在帮你做事)
    println!("CARGO_PKG_NAME = {}", env!("CARGO_PKG_NAME"));
    println!("CARGO_PKG_VERSION = {}", env!("CARGO_PKG_VERSION"));
}
EOF

# 4. debug 跑
cargo run
# [debug] Handmade Hero Day 1
# CARGO_PKG_NAME = handmade-hero
# CARGO_PKG_VERSION = 0.1.0

# 5. release 跑
cargo run --release
# [release] Handmade Hero Day 1
# CARGO_PKG_NAME = handmade-hero
# CARGO_PKG_VERSION = 0.1.0
```

**Rust 关键特性解释**:

- `cfg!(debug_assertions)` — 编译期常量。cargo 在 debug profile 默认传 `-C debug-assertions=on`,在 release 传 `=off`。`cfg!` 宏把它变成 `bool`。
- `env!("CARGO_PKG_NAME")` — cargo 在编译时通过环境变量注入项目元数据,`env!` 在编译期读取并嵌进二进制。这两个宏都不消耗运行时。

### Arch Linux 工具链验证

```bash
# 1. 看 rust 工具链版本
rustc --version
# rustc 1.81.0 (eeb90cda1 2024-09-04)

cargo --version
# cargo 1.81.0 (2dbb1af80 2024-09-25)

# 2. 装额外组件(若用 rustup)
rustup component add rustfmt clippy rust-src

# 3. 看 cargo 缓存了多少 crate(以后你会用很多)
ls ~/.cargo/registry/cache/index.crates.io-*/  2>/dev/null | wc -l
# 第一次:0;装过几个 crate 后:几十到几百

# 4. 看 cargo 编出来的二进制是什么格式
file target/debug/handmade-hero
# 输出:ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV),
#       dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2,
#       BuildID[sha1]=..., for GNU/Linux 3.2.0, not stripped

# 5. 看它依赖哪些库(此时无外部依赖,只有 libc)
ldd target/debug/handmade-hero
#         linux-vdso.so.1
#         libgcc_s.so.1 => /usr/lib/libgcc_s.so.1
#         libc.so.6 => /usr/lib/libc.so.6
#         /lib64/ld-linux-x86-64.so.2

# 6. 反汇编 main 看 cargo 编译出的汇编
objdump -d target/release/handmade-hero | grep -A 30 "<handmade_hero::main>:"
# 能看到 call instruction 调用 _RNvN...println_args 这样的符号
# rust 默认 release 不 strip 名字(因为有 debug=true),你可以看 mangled name

# 7. 用 rustfilt 解码 mangled name(装一下)
sudo pacman -S rustfilt
objdump -d target/release/handmade-hero | rustfilt | grep "<handmade_hero::main>:" -A 20
# 现在看到可读的 <handmade_hero::main>:
```

**Troubleshooting**:

- `error: linker 'cc' not found` — 装一下系统 linker:`sudo pacman -S base-devel`
- `error: failed to lookup source` — `Cargo.toml` 里 edition 写错了,改成 `"2021"`
- `cargo run` 时报 `error[E0463]` — 删 `target/` 重编:`cargo clean && cargo build`
- `warning: unused variable` — Rust 默认开所有 warning,你可以 `let _x = ...` 标记为故意不用
