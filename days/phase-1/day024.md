# Day 024 · 平台层清理:重构与文档化

> Day 1-23 你写了一堆代码——开窗、显示、输入、音频、内存、热重载。功能都跑通,但代码可能乱:函数太长、变量名临时、重复代码 5 处、没文档。Day 024 **不加新功能**,Casey 花一整集**整理代码**:重命名、提取函数、删死代码、加注释。这是软件工程的核心技能——**重构**(refactoring)。新手跳过这一步,代码越来越乱;资深定期整理,代码长期可维护。

## 0 · 为什么要有这一天

你回顾 Day 1-23 的代码。想象以下场景:

- 找一个函数:`Win32InitWindow`?`init_window`?`window_init`?变量名不统一,IDE 搜不到
- 改一个 bug:同一段逻辑在 3 处复制粘贴,改 1 处漏 2 处
- 接手别人代码:函数 500 行,没有注释,看 1 小时不知道干嘛
- 6 个月后回看自己的代码:忘了为什么这么写

这些是**技术债**(technical debt)的典型症状。技术债像信用卡债务——你不还,利息越滚越大。Day 24 是"还款日"——花一天整理代码,避免后期利息压垮项目。

**重构的核心原则**:

1. **不改行为**——重构时功能完全不变。如果改了行为,那是改 bug,不是重构。
2. **小步前进**——一次改一点,跑一下,确认没坏,再改下一点。
3. **有测试最好**——重构前有自动化测试,改完跑测试确认行为没变。HH 没有,Casey 靠"跑游戏看行为"验证。
4. **命名是文档**——好名字比注释更有效。`process_data` 差,`parse_png_header` 好。

**心理锚点**:读完今天,你能:

- 解释什么是重构,和"改 bug"、"加功能"的区别
- 用 Casey 的几种重构模式:重命名、提取函数、移除死代码、整理结构
- 用 Rust 工具加速重构:rust-analyzer rename、clippy、rustfmt
- 写好的 doc comment(/// 三斜杠)替代"长篇注释"
- 知道 Boy Scout Rule(童子军规则)——离开时比来时更干净
- 解释技术债的"复利"——为什么定期重构重要

## 2 · 心智模型

### 类比:重构是"装修"

你住进老房子。两种状态:

**没装修**(没重构):电线乱拉、水管堵、墙皮掉。每天生活受影响——找不到东西、漏水、断电。最后要么搬家(重写项目)要么花大钱修(大重构)。

**装修后**(重构过):电线走墙里、水管通、墙刷白。生活舒适。装修花时间,但日常效率高。

**定期小装修**(Boy Scout Rule):每天顺手整理一点,代码始终干净。Casey 推荐这种。

### 重构的几种模式

#### 模式 1:重命名(Rename)

最常见、最高 ROI(收益投入比)的重构。

```rust
// ❌ 坏命名(看不出意图)
let d = read_file("data.bin")?;
let r = process(&d);
write_file("out.bin", &r)?;

// ✅ 好命名(意图清晰)
let input_bytes = read_file("data.bin")?;
let processed_bytes = process_data(&input_bytes)?;
write_file("out.bin", &processed_bytes)?;
```

规则:

- 名字描述"做什么",不是"是什么"。`user_list` 差,`active_users` 好。
- 函数名是动词:`get_user` / `parse_input` / `render_scene`。
- 类型名是名词:`User` / `InputData` / `Scene`。
- 布尔变量是 `is_` / `has_` / `should_`:`is_visible` / `has_permission` / `should_retry`。
- 避免缩写(除非很常见):`usr` 差,`user` 好;`url` 好(URL 通用缩写)。

Rust 工具:rust-analyzer 的 rename(F2 在 VS Code)——自动改所有引用,几秒完成。

#### 模式 2:提取函数(Extract Function)

把大函数里的一段逻辑提取成独立函数。

```rust
// ❌ 长 main(300 行)
fn main() {
    // ... 100 行初始化窗口 ...
    // ... 100 行初始化音频 ...
    // ... 100 行主循环 ...
}

// ✅ 拆分后
fn main() {
    let window = init_window();
    let audio = init_audio();
    run_main_loop(window, audio);
}

fn init_window() -> Window { /* ... */ }
fn init_audio() -> AudioSystem { /* ... */ }
fn run_main_loop(window: Window, audio: AudioSystem) { /* ... */ }
```

好处:

- 每个函数职责单一,易理解
- 易测试(可以单独测 `init_window`)
- 易复用(其他 main 可以调)
- 函数名本身就是文档

Rust 工具:rust-analyzer 的 "Extract function" 重构(右键菜单)。

#### 模式 3:移除死代码

实验时写的代码后来不用了,删掉。

```rust
// ❌ 保留死代码(占行数,易混淆)
fn old_algorithm() {
    // Day 1 实验用,后来用 new_algorithm 替代
}

fn main() {
    new_algorithm();
}

// ✅ 删掉
fn main() {
    new_algorithm();
}
```

Rust 编译器警告帮你找:

```bash
cargo build 2>&1 | grep "never used"
# warning: function `old_algorithm` is never used
```

加 `#![deny(dead_code)]` 让 dead code 变 error,强制清理。

#### 模式 4:整理结构(模块化)

相关代码放一起,无关拆开。Rust 用 mod 系统。

```rust
// ❌ 全在 main.rs
fn main() { /* window + audio + input + render */ }
fn init_window() {}
fn init_audio() {}
fn handle_keyboard() {}
fn handle_gamepad() {}
fn render_pixels() {}

// ✅ 拆到模块
// src/main.rs
mod window;
mod audio;
mod input;
mod render;

fn main() {
    let w = window::init();
    let a = audio::init();
    let i = input::init();
    render::run_loop(w, a, i);
}

// src/window.rs
pub fn init() -> Window { /* ... */ }

// src/audio.rs
pub fn init() -> AudioSystem { /* ... */ }

// src/input.rs
pub fn init() -> InputState { /* ... */ }

// src/render.rs
pub fn run_loop(w: Window, a: AudioSystem, i: InputState) { /* ... */ }
```

每个模块独立,关注点分离。Rust 的 mod 系统:
- `mod foo;` 声明子模块,代码在 `src/foo.rs` 或 `src/foo/mod.rs`
- `pub fn` / `pub struct` 才对外可见
- `use foo::bar` 引入

#### 模式 5:统一风格

变量 / 函数命名风格统一:

```rust
// ❌ 风格混乱
let Player_HP = 100;        // snake + SCREAMING 混
fn GetPlayerHp() -> i32 {} // PascalCase 函数(C# 风格)
const maxhp: i32 = 999;     // 小写 const(Rust 风格是 SCREAMING_SNAKE)

// ✅ Rust 风格统一
let player_hp = 100;
fn get_player_hp() -> i32 {}
const MAX_HP: i32 = 999;
```

Rust 风格:`snake_case` 变量 / 函数,`PascalCase` 类型 / trait,`SCREAMING_SNAKE_CASE` 常量。

Rust 工具:

- `cargo fmt`——自动格式化
- `cargo clippy`——lint,提示"可以更地道"

```bash
cargo fmt  # 自动格式化所有文件
cargo clippy --fix  # 自动应用 clippy 建议(谨慎)
```

#### 模式 6:文档化

复杂逻辑加 doc comment。

```rust
// ❌ 普通注释(读者要自己想为什么)
// apply gravity
player.vy += 800.0 * dt;

// ✅ doc comment(解释为什么)
/// 重力加速度,单位像素/秒²
///
/// 800 ≈ 真实地球重力的游戏化值。真实地球 9.8 m/s²,
/// 但游戏里 9.8 太慢,玩家觉得跳跃"飘"。Casey 在 HH
/// 用 800,约等于"超人世界"的重力。
const GRAVITY: f32 = 800.0;

player.vy += GRAVITY * dt;
```

Rust doc comment 用 `///`(单行)或 `/** */`(块),编译器生成 HTML 文档(`cargo doc`)。

```bash
cargo doc --open
# 浏览器打开文档
```

### 重构的纪律

**纪律 1:小步前进**

不要"大重构"(一次改 500 行)。改一点,跑一下,确认没坏,再改。

```bash
# 重构流程
git checkout -b refactor/init-extract
# 改:把 init_window 从 main 提取出来
cargo run  # 确认能跑
git commit -m "extract init_window"
# 再改:extract init_audio
cargo run
git commit -m "extract init_audio"
# ...
```

每个 commit 都可独立验证。改坏了知道是哪个 commit。

**纪律 2:不改行为**

重构时**功能完全不变**。如果有 bug,等重构完再修。混合重构和改 bug,改坏了不知道是哪个引起的。

**纪律 3:有测试再重构**

理想:重构前有自动化测试。改完跑测试,行为没变。

```rust
#[test]
fn test_player_moves_with_input() {
    let mut p = Player::new();
    let input = mock_input_right();
    p.update(&input, 0.016);
    assert!(p.x > 0.0);  // 输入右,玩家 x 增加
}
```

测试是你重构时的"安全网"。Casey 在 HH 没有自动化测试,他靠"跑游戏看行为"——主观验证,不够稳健。Rust 项目应该写测试。

**纪律 4:不追求完美**

重构是"改善",不是"完美"。改到 80% 好就行,剩下 20% 下次重构。

完美主义导致"大重构永远做不完",反而比小步前进差。

### Boy Scout Rule

**童子军规则**(Boy Scout Rule):"离开营地时比来时更干净。"

应用到代码:**每次改代码,顺手整理一点**。

```rust
// 你被要求改一个 bug,顺便:
fn process_data(input: &str) -> Result<Output> {
    // 顺手:重命名 input → input_str(更清楚)
    let input_str = input;
    // 顺手:提取验证逻辑
    validate(input_str)?;
    // 顺手:加 doc comment
    /// ... 处理逻辑 ...
}
```

每次一点,代码长期干净。**这是 Casey HH 25 集还能保持代码整洁的秘诀**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发重构的特殊挑战:

- **性能敏感**:重构后不能变慢。profiler 验证
- **多线程**:并发代码重构更难,容易引入 race condition
- **跨平台**:不同平台代码可能有差异,重构要保持所有平台工作
- **大代码量**:商业游戏几十万行,大重构不可能

业界实践:
- **ECS 重构**:很多游戏从 OOP 重构到 ECS,需要重写大量代码
- **服务化拆分**:大游戏(网游)从单体重构到服务化,几个月工程
- **引擎升级**:从 Unreal 4 重构到 5,资产和代码都要改

Casey HH 是单机单人游戏,重构简单。商业游戏重构是巨大工程。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核本身就是**重构的教科书**:

- Linux 1.0(1994):简单单体内核
- Linux 2.0(1996):加 SMP 支持,大量重构
- Linux 2.6(2003):抢占式内核,大改调度器
- Linux 3.0(2011):其实没什么大改,版本号 marketing
- Linux 5.0+ +:持续重构,加 io_uring / BPF / cgroup v2 等

Linus 的原则:**重构 + 改 bug 分开**。一个 commit 一个目的。git log 清晰。

实战命令:

```bash
# 看 Linux 内核的 commit 历史(有教学价值)
git clone --depth 1 https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
cd linux
git log --oneline | head -20

# 看一个具体 commit 的 message
git show <commit-hash>
# Linus 的 commit message 通常很长,详细解释

# 用 git log 找"refactor"相关 commit
git log --oneline --grep="refactor" | head
```

读 Linus 的 commit message 是软件工程教育。每个 commit:
- 标题简明(< 50 字符)
- body 解释"为什么"(不只"做什么")
- 必要时引用讨论邮件列表

### 3.4 · 软件工程:重构经典

业界重构经典:**Martin Fowler《Refactoring》**(1999)。Fowler 总结 70+ 种重构模式:

- Extract Function / Inline Function
- Extract Variable / Inline Variable
- Rename
- Move Function
- Replace Conditional with Polymorphism
- Replace Inheritance with Delegation
- ...

每种模式有"动机 / 步骤 / 例子"三段式。Casey Day 024 用的几种都是 Fowler 经典模式。

Fowler 的核心洞察:**重构 + 加功能分开**。

- 加功能时重构:专注力分散,容易改坏
- 重构时加功能:同上
- 重构时重构:专注,稳定
- 加功能时加功能:专注,稳定

**两种状态切换,不要混合**。

实战:

- 你要加一个新功能。先看代码——如果当前结构适合加,直接加。
- 如果当前结构不适合(比如要复制粘贴 5 处),先重构(让它容易加),再加功能。
- 这是 Fowler 的"两次帽子":重构帽子 / 加功能帽子。

### 技术债

技术债(technical debt):你写代码时偷懒(快速实现)欠下的"债务"。后期维护成本增加 = "利息"。

技术债分类:

| 类型 | 描述 | 处理 |
|---|---|---|
| 故意 + 谨慎 | 知道有更好方案,但时间紧。记录下来 | 计划重构 |
| 故意 + 粗心 | 不知道有更好方案,胡乱写 | 学习 + 重构 |
| 无意 + 谨慎 | 写时懂,后来需求变化变成债 | 重构 |
| 无意 + 粗心 | 新手代码,自己也不知道烂 | 学习 + 大重构 |

技术债像信用卡:合理使用(故意 + 谨慎)是工具;滥用(粗心)是灾难。

Casey HH 大部分技术债是"故意 + 谨慎"——他知道"这里可以用更优雅的方案,但教学目的够用"。

## 4 · 认知地图

### 4.1 上级

- **Refactoring**(重构)——不改行为改结构
- **Technical Debt**(技术债)——欠下的代码质量债
- **Code Quality**(代码质量)——可读 / 可维护 / 可测试
- **Boy Scout Rule**——离开比来时更干净

### 4.2 同级

| 方法 | 关键差别 | 何时用 |
|---|---|---|
| 小步重构 | 一次一点,稳定 | 日常(Day 24 用) |
| 大重构 | 一次大改,风险高 | 大型架构升级 |
| 重写 | 删了从头写 | 项目死了或彻底失败 |
| Strangler Pattern | 新系统逐步替换老 | 大型遗留系统迁移 |

### 4.3 下级

- **Rename**——重命名,最常见重构
- **Extract Function**——提取函数
- **Remove Dead Code**——删死代码
- **Modularize**——拆模块
- **Unify Style**——统一风格
- **Document**——加 doc comment
- **rust-analyzer / cargo fmt / clippy**——Rust 工具

### 历史:重构概念演化

- **1990s**:Martin Fowler《Refactoring》出版,概念普及
- **2000s**:IDE 集成(Eclipse / IntelliJ 自动重构)
- **2010s**:LSP 协议,跨编辑器共享语言工具
- **2020s**:AI 辅助重构(GitHub Copilot 帮你重构)

Casey 在 HH 用 1990s 风格(手动重构),但思想是 Fowler 经典。

### 何时 NOT 重构

重构不是万能。有些场景不该重构:

- **抛原型**:你写一个 demo 验证想法,验证完就扔。重构无意义。
- **即将重写**:整个模块要被替换。重构浪费时间。
- **deadline 紧**:发布前别重构,等发布后。
- **测试不全 + 系统关键**:没测试保护,重构可能引入 bug。

Casey HH 的 Day 24 重构是"已完成阶段性工作,后面要扩展"——这是重构的恰当时机。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 这集花一整集重构。为什么不"等功能写完再统一重构"?提示:想想技术债的复利效应。

**参考解答**:

**因为技术债是复利**。

代码混乱时,加新功能成本 = "写新功能" + "理解旧代码" + "绕过混乱"。代码越乱,这三块成本都涨。

- Day 25:小乱,成本 1.0×
- Day 100:中乱,成本 2×
- Day 500:大乱,重构不可能,只能重写整个项目

### Lv2 · 动手实践

**题**:回顾你 Day 1-23 的代码,用 Casey 的几种模式重构:

1. 找 3 个命名不清楚的变量 / 函数,重命名(用 rust-analyzer F2)
2. 找一个超过 100 行的函数,提取子函数
3. 删任何 `cargo build` 警告的死代码
4. 给 2 个复杂函数加 doc comment
5. 用 `cargo fmt` 自动格式化

完成标准:`cargo build` 通过,跑起来行为不变,代码更清晰。

**参考解答**(示例):

```rust
// ❌ 重构前
fn render(buf: &mut [u32], w: usize, x: f32, y: f32, c: u32) {
    let xi = x as i32;
    let yi = y as i32;
    if xi >= 0 && (xi as usize) < w && yi >= 0 {
        let idx = yi as usize * w + xi as usize;
        if idx < buf.len() {
            buf[idx] = c;
        }
    }
}

// ✅ 重构后
/// 在 framebuffer 的 (x, y) 处画一个像素
/// 
/// # 参数
/// - `buffer`: framebuffer,长度 = width * height
/// - `width`: framebuffer 宽度
/// - `x`, `y`: 像素坐标(浮点,内部 cast 为 i32)
/// - `color`: ARGB 颜色(0xAARRGGBB)
/// 
/// # 越界处理
/// 坐标超出 framebuffer 范围时静默忽略(不 panic)
pub fn draw_pixel(
    buffer: &mut [u32],
    width: usize,
    x: f32,
    y: f32,
    color: u32,
) {
    let xi = x as i32;
    let yi = y as i32;
    if xi < 0 || yi < 0 {
        return;
    }
    let (xi, yi) = (xi as usize, yi as usize);
    if xi >= width {
        return;
    }
    let idx = yi * width + xi;
    if idx < buffer.len() {
        buffer[idx] = color;
    }
}
```

改动:

- `render` → `draw_pixel`(更具体)
- `buf` → `buffer`(完整词)
- `w` → `width`(完整词)
- `c` → `color`(完整词)
- 加 doc comment(解释参数、越界行为)
- 早 return 简化嵌套

## 8 · Rust / Arch 落地代码

### Rust:重构流程示例

```bash
# 1. 装 Rust 工具
rustup component add rustfmt clippy rust-analyzer
cargo install cargo-audit  # 安全检查

# 2. 重构前的安全检查
cd ~/src/handmade-hero-rs

# 先跑测试,确认 baseline 工作
cargo test

# 跑 clippy,看现有 warning
cargo clippy 2>&1 | tee /tmp/clippy-before.txt

# 跑 fmt 检查(不修改,只看 diff)
cargo fmt --check

# 3. 开始重构(新分支)
git checkout -b refactor/day024-cleanup

# 4. 重命名(用 rust-analyzer)
# 在 VS Code / Neovim,F2 在变量名上,改名,自动更新所有引用
# 命令行可以用 sed,但要小心:
grep -rn "old_name" src/
sed -i 's/old_name/new_name/g' src/*.rs
# 验证: cargo check

# 5. 提取函数
# 在 IDE 里选中代码,右键 "Extract function"
# 或手动重构

# 6. 删死代码
# 看 cargo build 的 warning,删 "never used" 的代码
cargo build 2>&1 | grep "never used"

# 7. 加 doc comment
# 给所有 pub fn / pub struct 加 ///

# 8. 格式化
cargo fmt

# 9. clippy + fix
cargo clippy --fix --allow-dirty
cargo clippy  # 再次检查,应该 clean

# 10. 测试 + 跑
cargo test
cargo run

# 11. commit
git add .
git commit -m "refactor: day 024 code cleanup

- rename variables for clarity (buf → buffer, w → width)
- extract init_window, init_audio from main
- remove dead code (old_experiment_fn)
- add doc comments to public API
- apply rustfmt + clippy"
```
