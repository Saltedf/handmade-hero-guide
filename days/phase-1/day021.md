
# Day 021 · 动态加载游戏代码:热重载的起点

> Day 011 设计的平台 / 游戏分离今天结出**杀手级果实**——热重载(hot reload)。从今天起,你改一行游戏代码,保存,1-2 秒后游戏画面就反映新代码,**不重启进程,游戏状态(玩家位置 / 关卡进度)完整保留**。这是 HH 整个项目的杀手锏之一——Casey 用它两年开发 667 集,迭代速度提升 50×。理解热重载你就理解了"动态链接 / 加载"的本质,这也是后面 Day 192 self-recompilation 的基础。

## 0 · 为什么要有这一天

你开发一个游戏。当前流程:

1. 改代码(编辑器)
2. 切到终端,跑 `cargo build`(几秒)
3. 启动游戏(几秒)
4. 进关卡(几秒,可能要走菜单)
5. 触发要测试的场景(几秒)
6. 看效果
7. 发现 bug,改代码,从 2 开始

每次循环 30-60 秒。一天改 100 次?50-100 分钟纯等待。一年?500 小时。**热重载把这 500 小时压到 10 小时**。

具体差别:
- **没有热重载**:改一行 → build → 关游戏 → 重启 → 进关卡 → 测试。30 秒一次。
- **有热重载**:改一行 → 保存 → 自动 build → 游戏自动 reload → **画面立刻反映**。1-3 秒一次。

50× 加速不是夸张,是真实工程数据。

为什么热重载可能?**Day 011 的架构决策**——平台 / 游戏分离,游戏状态由平台层持有(`GameMemory`),游戏代码是无状态函数。换"函数指针"时,状态不动。新代码立刻接管,游戏无缝继续。

类比:换汽车发动机。普通重启 = 停车 → 关引擎 → 换 → 重启 → 起步。热重载 = 边开边换,乘客(状态)完全无感。听起来不可能,但代码世界可以——因为代码和数据是分离的。

**心理锚点**:读完今天,你能:

- 解释热重载的物理前提(状态外置 + 接口一致)
- 写出"游戏代码编 cdylib + 平台用 libloading 加载"的最小实现
- 知道 ELF(Linux) / DLL(Windows) / Mach-O(macOS) 的差别
- 用 `libloading` crate 加载 .so 文件、查找符号、调用
- 解释 `#[no_mangle]` 和 `extern "C"` 的作用
- 处理 Rust 的 Symbol 借用 Library 的所有权陷阱
- 用 `cargo-watch` 自动 build,实现"保存即 reload"
- 知道为什么全局 `static mut` 在热重载下会出问题

## 1 · Casey 今天做了什么

Day 021 Casey 的具体动作:

1. **把游戏代码改成 DLL 编译**:原本游戏代码静态链接进 exe,改成动态链接库(.dll / .so / cdylib)。Cargo.toml 加 `[lib] crate-type = ["cdylib"]`。
2. **平台层启动时 LoadLibrary / dlopen**:加载 DLL,获得句柄。
3. **GetProcAddress / dlsym 查找 update_and_render**:拿到游戏主函数的指针。
4. **主循环通过函数指针调用**:`update_and_render(memory, input, dt)` 改成 `func_ptr(memory, input, dt)`。
5. **检测 DLL 文件变化**:每帧检查 mtime,变了就准备 reload。
6. **reload 流程**:drop 旧函数指针 → FreeLibrary / dlclose 卸载旧 → LoadLibrary / dlopen 加载新 → GetProcAddress 拿新函数指针 → **`GameMemory` 不动** → 下一帧调用新代码。

实现完成后,Casey 演示:游戏跑着,他改一行代码"颜色从红变蓝",build,游戏窗口里方块立刻变蓝,玩家位置不变。这是 HH 整个项目的"magic moment"——观众第一次看到热重载,屏住呼吸。

## 2 · 心智模型

### 类比:热重载是"边开边换发动机"

你坐飞机。普通情况下,换发动机要着陆、关引擎、修理工换、重启、起飞。整个过程 1 小时。

热重载是**飞行中换发动机**:

1. 旧发动机还在转
2. 新发动机准备好(在机翼上待命)
3. 切换瞬间:旧发动机断开,新发动机接上
4. 乘客(状态)完全无感——只感觉"瞬间过去了"

怎么做到?**乘客和发动机解耦**。乘客不知道发动机是什么型号,只感受到"推力"。新发动机只要能提供推力(接口一致),立刻接管。

游戏世界:
- "发动机" = 游戏代码(update_and_render 函数)
- "乘客" = GameMemory(玩家位置 / 关卡进度)
- "接口" = 函数签名(`fn(&mut GameMemory, &GameInput, dt)`)

换代码时:卸载旧 .so → 加载新 .so → 拿新函数指针 → 状态不动 → 下一帧调新代码。

### 严谨:动态链接基础

回顾:静态链接 vs 动态链接。

**静态链接**(static linking):编译时,所有依赖库的代码"复制"进最终可执行文件。结果:`./my-game` 一个文件,自包含。优点:无依赖,简单。缺点:库改了要重编整个。

**动态链接**(dynamic linking):编译时只记录"我用库 X 的函数 f",运行时由动态链接器(ld-linux / dyld)查找。结果:`./my-game` 依赖 `libX.so`,运行时一起加载。优点:库改了不用重编,内存共享。缺点:运行时依赖。

**热重载更进一步**:同一进程,运行时**反复**加载 / 卸载同一个库的不同版本。普通动态链接是启动时加载一次,热重载是反复加载。

Linux 上:

```bash
# 看你程序的动态依赖
ldd ./your-app
# 输出:
#     libhandmade.so => ./libhandmade.so (0x...)
#     libstd-*.so => /usr/lib/...
#     libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x...)
#     ld-linux-x86-64.so.2 => /lib/.../ld-linux-x86-64.so.2 (0x...)
```

每个 `=>` 表示动态链接器找到的库。

### dlopen / dlsym(Linux API)

C 的动态加载 API(POSIX):

```c
void *lib = dlopen("./libhandmade.so", RTLD_NOW);  // 加载
void *sym = dlsym(lib, "update_and_render");         // 查找符号
typedef void Fn(Memory*, Input*, float);
Fn *func = (Fn*)sym;                                  // cast 成函数指针
func(memory, input, dt);                              // 调用
dlclose(lib);                                          // 卸载
```

Rust 用 `libloading` crate 封装:

```rust
use libloading::Library;

let lib = unsafe { Library::new("./libhandmade.so") }?;
let func: libloading::Symbol<unsafe extern "C" fn(*mut Memory, *const Input, f32)> =
    unsafe { lib.get(b"update_and_render") }?;
unsafe { func(memory, input, dt) };
drop(lib);  // 卸载
```

`Symbol<Fn>` 是函数指针的封装,借用 `Library`(Rust 借用检查器保证 Library 活着时 Symbol 才能用)。

### Rust cdylib

要让 Rust 编译出可被 dlopen 加载的 .so,在 `Cargo.toml`:

```toml
[lib]
name = "handmade"
crate-type = ["cdylib"]
# cdylib = C-compatible dynamic library
# 其他选项:rlib(Rust 静态库)、dylib(Rust 动态库,带 Rust 元数据)、staticlib(C 静态库)
```

`cdylib` 表示"导出 C ABI 的动态库",可以被任何语言(C / Python / 其他 Rust 程序)加载。Linux 是 `.so`,Windows 是 `.dll`,macOS 是 `.dylib`。

游戏代码里导出函数:

```rust
// src/lib.rs(handmade crate,cdylib)

#[no_mangle]  // 不要 mangling 函数名
pub extern "C" fn update_and_render(
    memory: *mut GameMemory,
    input: *const GameInput,
    dt: f32,
) {
    // 游戏逻辑
    let memory = unsafe { &mut *memory };
    let input = unsafe { &*input };
    
    // 改变背景色(测试热重载)
    let color = memory.state.test_color;  // 跨 reload 保留
    for px in memory.back_buffer.iter_mut() {
        *px = color;
    }
}
```

每个关键字解释:

- `#[no_mangle]`——Rust 默认会 mangle 函数名(加 hash 等,因为 Rust 允许泛型重载)。`#[no_mangle]` 告诉编译器"保持原名",这样 `dlsym("update_and_render")` 能找到。
- `extern "C"`——使用 C ABI(调用约定、参数传递规则)。Rust 默认是 Rust ABI(不稳定,版本间可能变)。`extern "C"` 是稳定 ABI,跨编译器 / 版本兼容。
- `*mut GameMemory`——裸指针。**为什么用裸指针而不是 `&mut`?** 因为跨 FFI 边界,Rust 的引用生命周期太复杂,C 不理解。裸指针简单——就是一个地址。
- `unsafe { &mut *memory }`——把裸指针转引用。unsafe 因为编译器不能保证指针有效、对齐、不别名。我们的安全论证:平台层传入的是有效的、唯一的、对齐的指针。

### 完整 reload pipeline

平台层代码:

```rust
use libloading::Library;
use std::path::Path;
use std::time::SystemTime;

struct GameCode {
    library: Library,
    update_and_render: Symbol<...>,
    last_loaded: SystemTime,
}

impl App {
    fn load_game_code(&mut self) {
        let path = "./libhandmade.so";
        let lib = unsafe { Library::new(path) }.expect("load library");
        let func: libloading::Symbol<unsafe extern "C" fn(*mut GameMemory, *const GameInput, f32)> = 
            unsafe { lib.get(b"update_and_render") }.expect("symbol");
        let last_loaded = std::fs::metadata(path).unwrap().modified().unwrap();
        
        self.game_code = Some(GameCode {
            library: lib,
            update_and_render: func,
            last_loaded,
        });
    }
    
    fn check_and_reload(&mut self) {
        let path = "./libhandmade.so";
        let mtime = std::fs::metadata(path).unwrap().modified().unwrap();
        if mtime > self.game_code.as_ref().unwrap().last_loaded {
            println!("🔄 Reloading...");
            self.load_game_code();  // drop 旧 Library,加载新
        }
    }
    
    fn run_frame(&mut self) {
        self.check_and_reload();
        
        // 通过函数指针调用
        let code = self.game_code.as_ref().unwrap();
        let memory_ptr = &mut self.memory as *mut GameMemory;
        let input_ptr = &self.input as *const GameInput;
        unsafe {
            (code.update_and_render)(memory_ptr, input_ptr, self.dt);
        }
    }
}
```

**Rust 所有权陷阱**:`Symbol<...>` 借用 `Library`。`Library` 是 `GameCode` 的字段,`Symbol` 也是。Rust 编译器会拒绝:"Symbol 借用 library,library 是 self 字段,你拿 Symbol 的引用时 self 不能改 library"。

解法:用 `Box::leak` 让 Library 永生,或用 `Arc<Library>`。或更简单的:**把 Library 和 Symbol 分开存**:

```rust
struct App {
    library: Box<Library>,         // Box 让 library 在堆上,地址稳定
    update_and_render: unsafe extern "C" fn(*mut GameMemory, *const GameInput, f32),
    // ↑ 直接存函数指针,不存 Symbol(规避借用)
}

impl App {
    fn load_game_code(&mut self) {
        let lib = unsafe { Library::new("./libhandmade.so") }.unwrap();
        let lib_boxed = Box::new(lib);
        let ptr = unsafe {
            let sym: libloading::Symbol<...> = lib_boxed.as_ref().get(b"update_and_render").unwrap();
            sym.into_raw()  // 放弃 Symbol 的借用,得到原始函数指针
        };
        self.library = lib_boxed;
        self.update_and_render = std::mem::transmute(ptr);
    }
}
```

`into_raw` 放弃 Symbol 借用,返回原始函数指针(不受 Library 借用约束)。但你要保证 Library 活着,否则函数指针指向无效内存。

更安全的方案:用 `libloading` 文档推荐的 `Box::leak`:

```rust
// 把 Library 永久泄漏(程序结束时由 OS 清理)
let lib = unsafe { Library::new(path) }.unwrap();
let lib_ref: &'static Library = Box::leak(Box::new(lib));
// lib_ref 的生命周期是 'static,Symbol<'static> 可以独立持有
let sym: libloading::Symbol<'static, ...> = unsafe { lib_ref.get(b"...") }.unwrap();
```

代价:Library 永不释放。对热重载场景 OK(reload 时旧的不释放也行,最多泄漏一些内存)。

### 第二个坑:全局 static 变量

如果游戏代码有:

```rust
// handmade crate 里
static mut PLAYER_HP: i32 = 100;
```

这个 `PLAYER_HP` 在 .so 文件的数据段。**reload 时**:
- 旧 .so 卸载,它的数据段(包括 PLAYER_HP)释放
- 新 .so 加载,数据段重新初始化(PLAYER_HP = 100)
- 玩家打到一半 HP=30,reload 后 HP=100 ← **bug!**

**正确做法**:所有状态放 `GameMemory`,不放 static。Day 014 强调状态外置,这就是为什么——它是热重载的物理前提。

```rust
// handmade crate 里
// ❌ static mut PLAYER_HP: i32 = 100;
// ✅
struct GameState { player_hp: i32, ... }

pub extern "C" fn update_and_render(memory: *mut GameMemory, ...) {
    let memory = unsafe { &mut *memory };
    // memory.state.player_hp
}
```

### cargo-watch:自动 build

手动 `cargo build` 太烦。装 `cargo-watch`:

```bash
cargo install cargo-watch
```

然后:

```bash
cargo watch -x "build -p handmade"  # 监听 handmade crate,变化就 build
```

工作流:

```
终端 1:cargo watch -x "build -p handmade"
终端 2:cargo run --bin platform(跑游戏)
终端 3:编辑器
```

改代码 → cargo-watch 自动 build → 平台层检测到 .so mtime 变化 → reload → 下一帧用新代码。

整个循环 1-3 秒,你完全在编辑器里干活。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏开发圈的热重载实践:

**Casey HH**(C / Win32):DLL + LoadLibrary,Casey 手写。
**Rust HH**(我们的):cdylib + libloading + cargo-watch,基本同思路。
**Bevy**:用 bevy-inspector-egui + bevy-mod-debugdump,但不是真热重载(是状态可视化)。
**Unity**:用 Editor 模式,改 C# 脚本立刻生效。但 build 出来运行时不能热重载。
**Unreal**:Hot Reload 插件,改 C++ 代码运行时重编。但复杂。
**Godot**:GDScript 热重载(脚本语言天然支持)。C# 部分(CLR)也支持。

**真热重载 vs 模拟**:
- **真**:换代码,状态保留。Casey / 我们做的。
- **假**:重启进程,但启动快(< 1 秒)。Unity / Unreal 大部分场景。
- **脚本**:代码本身就是解释执行,改了就生效。Lua / Python / GDScript。

业界趋势:越来越多引擎支持真热重载。但实现复杂(C++ 全局变量问题、模板代码生成等),普及慢。

### 3.2 · 🐧 Linux 系统编程视角

Linux 动态加载 API:

| API | 作用 |
|---|---|
| `dlopen(path, flags)` | 加载 .so 文件 |
| `dlsym(handle, name)` | 查找符号 |
| `dlclose(handle)` | 卸载 |
| `dlerror()` | 错误信息 |
| `dladdr(addr)` | 反查:地址属于哪个 .so 的哪个符号 |

flags:`RTLD_LAZY`(延迟解析符号,首次调用时解析)/ `RTLD_NOW`(立即解析所有符号,加载时发现错误)/ `RTLD_GLOBAL`(符号全局可见,后续 dlopen 可用)/ `RTLD_LOCAL`(符号私有,默认)。

实战命令:

```bash
# 1. 看可执行文件的动态依赖
ldd ./your-app
# 列出所有 .so 依赖

# 2. 看 .so 文件导出的符号
nm -D ./libhandmade.so | grep update
# T 表示在 .text 段(函数定义)
# 应该看到:0000000000001120 T update_and_render

# 3. 反汇编 .so
objdump -d ./libhandmade.so | head
# 看汇编代码

# 4. 看 .so 的 ELF 结构
readelf -a ./libhandmade.so | head -40
# ELF header / section / symbol table 等

# 5. 实时监控动态加载
strace -e trace=openat,mmap ./your-app
# 看到打开 .so 文件、mmap 到地址空间

# 6. 看进程当前加载的库
cat /proc/$(pgrep your-app)/maps | grep "\.so"
# 列出所有 .so 映射
```

**Linux vs Windows 的 dl 差别**:

- Linux 的 .so 在 dlclose 后真正卸载(物理 unmap)
- Windows 的 DLL 在 FreeLibrary 后引用计数减一,到 0 才卸载
- Linux 允许同名 .so 反复 dlopen/dlclose(每次新映射)
- Windows 有时 DLL 文件被占用不能改(必须先 unload)

Linux 对热重载友好——文件可以随时改,运行中也能加载新版本。

### 3.3 · 🦀 Rust 生态视角

Rust 热重载生态:

**libloading**(底层):跨平台 dlopen,我们用。
**hot-lib-reloader**(高层):基于 libloading,自动化 mtime 检测、reload。
**cargo-watch**(配套):文件变化自动 build。

```toml
# Cargo.toml
[dependencies]
libloading = "0.8"
```

```rust
use hot_lib_reloader::HotLibReloader;

let lib_reloader = HotLibReloader::new("./target/debug", "handmade")?;
// 自动监听变化、reload
let update_fn: extern "C" fn(...) = lib_reloader.get("update_and_render")?;
```

**Rust 特有挑战**:

1. **Symbol 借用 Library**——上面讲过,用 Box::leak 或 hot-lib-reloader 绕过
2. **类型签名匹配严格**——`#[no_mangle]` + `extern "C"` 保证 ABI 兼容
3. **静态变量重置**——所有状态放 GameMemory,不放 static
4. **不同 rustc 版本**——如果平台和游戏用不同 rustc,String / Vec 布局可能不同。**只用 C 类型在 FFI 边界**(*mut, i32, f32 等)
5. **incremental compilation**——cargo 增量编译,改一行代码 build 几百 ms。但 cdylib 可能要 LTO,慢一些

**Rust 编译速度** 是热重载体验的关键。casey 在 C 里用 cl.exe,几秒 incremental。Rust 用 rustc,几秒到十几秒。比 C 慢,但有缓解:

- `cargo check`(只检查,不codegen)快
- `sccache`(分布式缓存)
- `cranelift` backend(实验,更快 codegen)
- mold linker(比 ld 快 10×)

### 3.4 · ELF / DLL / Mach-O 文件格式

可执行文件 / 库的格式:

| 格式 | 平台 | 库扩展 |
|---|---|---|
| PE / COFF | Windows | .dll / .exe |
| ELF | Linux / BSD | .so / 可执行 |
| Mach-O | macOS / iOS | .dylib / 可执行 |

格式不同,但都解决"打包代码 + 数据 + 元信息"的问题。

ELF 结构(简化):

```
+------------------+
| ELF Header       |  ← 魔数、版本、入口地址
+------------------+
| Program Headers  |  ← 描述 segments(运行时视图)
+------------------+
| Section Headers  |  ← 描述 sections(链接视图)
+------------------+
| .text            |  ← 代码(机器码)
+------------------+
| .rodata          |  ← 只读数据(字符串常量等)
+------------------+
| .data            |  ← 可读写数据(已初始化全局变量)
+------------------+
| .bss             |  ← 未初始化数据(运行时清零)
+------------------+
| .symtab          |  ← 符号表(函数 / 变量名 → 地址)
+------------------+
| .strtab          |  ← 字符串表(符号名)
+------------------+
| .dynsym          |  ← 动态符号表(dlopen 可见)
+------------------+
```

`dlsym("update_and_render")` 查 `.dynsym` 找到函数地址。

`#[no_mangle]` 让函数出现在 `.dynsym` 而不只是 `.symtab`(后者只链接时用)。

```bash
# 看 .so 的动态符号表
readelf --dyn-syms ./libhandmade.so | grep update
# 输出:
# Num: Value          Size Type Bind Vis Ndx Name
#  10: 000000000001120  100 FUNC GLOBAL DEFAULT 11 update_and_render
```

Type FUNC 表示函数,GLOBAL 表示外部可见。

## 4 · 认知地图

### 4.1 上级

- **动态链接 / 加载**(Dynamic Linking / Loading)——运行时把代码映射到内存
- **状态外置**(State Externalization)——热重载的前提
- **接口稳定性**(Interface Stability)——签名不变是 reload 的契约
- **Dev loop**(开发循环)——改 → build → 测试,热重载加速

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 静态链接 | 编译时合并,无运行时开销 | 最终发布 | ❌ |
| 动态链接(启动加载) | 启动时 dlopen,运行时调用 | 插件系统 | (备选) |
| 热重载(运行时 reload) | 反复加载卸载,状态保留 | 开发阶段 | ✅ |
| JIT(运行时生成) | 运行时编译新代码 | JVM / V8 / Lua | HH 不用 |
| 脚本语言 | 代码本身就解释执行 | 游戏脚本(Lua / Python) | (备选) |

### 4.3 下级

- **cdylib crate-type**——Rust 编译 C ABI 的动态库
- **`#[no_mangle]`**——保持函数名不被 mangle
- **`extern "C"`**——C ABI(稳定调用约定)
- **Library handle**(libloading::Library)——OS 资源
- **Symbol<Fn>**——函数指针封装
- **mtime 检测**——文件变化检测
- **cargo-watch**——文件监听 + 自动 build
- **状态外置**——所有状态放 GameMemory

## 5 · 对照与变奏

### 热重载跨领域

热重载思想在很多领域出现:

**Web 前端**:webpack HMR(Hot Module Replacement)。改 React 组件,webpack 推新模块,浏览器替换该模块,**组件状态保留**。和 Casey 一样的思想。

**数据库 schema 迁移**:pg-rewrite / pt-online-schema-change。新 schema 表建好,双写,后台拷贝,完成后切。不停服务。

**Java Spring**:DevTools 监听 .class 变化,重启 ApplicationContext(< 1 秒)。粒度比 Casey 粗。

**Linux 内核 kpatch / livepatch**:换内核函数不重启系统。ftrace 把原函数入口改成跳转新函数。运行中的内核调用自动走新函数。**最激进的热重载**——内核不能停。

**Erlang / Elixir**:BEAM VM 原生支持热重载。电信系统 30 年不重启。

共同原则:**状态外置 + 代码替换 + 接口一致**。

### 静态 vs 动态链接 trade-off

| | 静态 | 动态 |
|---|---|---|
| 启动速度 | 快(无加载) | 慢(dlopen 时间) |
| 内存 | 多(每个 exe 自带库) | 少(库共享) |
| 依赖 | 无 | 必须有 .so |
| 升级 | 重编整个 | 替换 .so |
| 热重载 | 不可能 | 可能 |
| 发布 | 简单 | 复杂(带依赖) |

**实战**:
- 开发:动态 + 热重载(快迭代)
- 发布:静态(自包含,用户友好)

Rust 项目可以两种 build 模式切换:`cargo build`(dev,cdylib)+ `cargo build --release`(static link)。

### 历史演化:热重载

- **1970s Lisp**:Lisp 机器,代码即数据,改函数即生效
- **1980s Smalltalk**:图像化开发,改方法立即生效
- **1990s**:Java HotSwap,debugger 改方法体(JVM 支持)
- **2000s**:Rails / Django,文件变化自动重启进程(假热重载)
- **2010s**:HMR(Webpack),前端热重载成熟
- **2020s**:Rust cdylib + libloading,Casey 思路搬到 Rust

Casey 在 2014 年手写,2020s 的我们用 cargo-watch + libloading,体验更好。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:热重载要求"状态外置"(game_memory 由平台层管,不在游戏代码的全局变量)。如果状态在游戏代码的全局变量里,会发生什么?

进一步:Rust 的 `static` 变量和 C 的 `static` 变量在热重载下行为一致吗?有什么差别?

**参考解答**:

**因为 DLL 重载时全局变量重置**。.so 里如果有 `static mut PLAYER_HP: i32 = 100;`,这个变量在 .so 的 .data 段(或 .bss 段)。.so 卸载时这段内存释放,新 .so 加载时数据段重新初始化为 100。所以玩家打到一半(HP=30),reload → HP 重置为 100 → bug。

状态在 `game_memory` 里(平台层分配,跨 reload 保留):reload 时 game_memory 不动,新 .so 拿到的是 HP=30,继续。

**Rust 和 C 的 static 在热重载下基本一致**(都是 .data 段),但 Rust 多一个坑:

```rust
// Rust 的 static 不能 mut(安全限制)
static PLAYER_HP: i32 = 100;  // 不可变,无问题

// 要可变,用 AtomicU64 或 unsafe
static PLAYER_HP: AtomicU64 = AtomicU64::new(100);  // OK
// 或
static mut PLAYER_HP: i32 = 100;  // unsafe 访问
```

Rust 鼓励用 atomic 而非 static mut,后者在多线程下 UB。但单线程游戏循环里两种都行,且都会在 reload 时重置——**所有状态仍要放 game_memory**。

### Lv2 · 动手实践

**题**:做一个最小热重载 demo。两个 crate:

- `game_lib`(cdylib):导出 `update_and_render(counter: *const AtomicU64)`,把计数器 +1 并打印
- `platform`(bin):加载 game_lib,每秒调一次,检测 mtime 变化时 reload

跑 platform,看到计数器递增。改 game_lib 里打印的消息,cargo build,看 platform 立刻打印新消息。**计数器不重置**。

完成标准:连续 reload 3 次,计数器持续递增(0→1→2→...→N)。

**参考解答**:

```rust
// game_lib/Cargo.toml
// [lib]
// name = "game_lib"
// crate-type = ["cdylib"]

// game_lib/src/lib.rs
use std::sync::atomic::{AtomicU64, Ordering};

#[no_mangle]
pub unsafe extern "C" fn update_and_render(counter: *const AtomicU64) {
    let n = (*counter).fetch_add(1, Ordering::SeqCst);
    println!("🔥 Day 021 hot reload! counter = {} (改我试试!)", n);
}
```

```rust
// platform/Cargo.toml
// [dependencies]
// libloading = "0.8"

// platform/src/main.rs
use libloading::Library;
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Arc;
use std::time::Duration;

fn main() {
    let counter = Arc::new(AtomicU64::new(0));
    let counter_ptr = Arc::as_ptr(&counter);
    let path = "./target/debug/libgame_lib.so";
    
    let mut lib = unsafe { Library::new(path) }.unwrap();
    let mut last_mtime = std::fs::metadata(path).unwrap().modified().unwrap();
    
    loop {
        // 检测 reload
        let mtime = std::fs::metadata(path).unwrap().modified().unwrap();
        if mtime != last_mtime {
            println!("🔄 Reloading...");
            // 等待 .so 写完整(避免读到半成品)
            std::thread::sleep(Duration::from_millis(100));
            lib = unsafe { Library::new(path) }.unwrap();
            last_mtime = mtime;
        }
        
        // 调用
        let func: libloading::Symbol<unsafe extern "C" fn(*const AtomicU64)> = 
            unsafe { lib.get(b"update_and_render") }.unwrap();
        unsafe { func(counter_ptr) };
        
        std::thread::sleep(Duration::from_secs(1));
    }
}
```

### Rust:完整热重载 demo

把 Lv2 扩展,加可视化效果(颜色变化):

```rust
// game_lib/src/lib.rs
use std::sync::atomic::{AtomicU64, Ordering};

#[repr(C)]
pub struct GameMemory {
    pub is_initialized: bool,
    pub test_color: u32,
    pub frame_count: u64,
}

#[no_mangle]
pub unsafe extern "C" fn update_and_render(memory: *mut GameMemory) {
    let memory = &mut *memory;
    
    if !memory.is_initialized {
        memory.test_color = 0xFFFF0000;  // 初始红色
        memory.is_initialized = true;
        println!("first init");
    }
    
    memory.frame_count += 1;
    if memory.frame_count % 60 == 0 {
        // 每 60 帧 print 一次
        println!("frame {}, color = 0x{:08X}", memory.frame_count, memory.test_color);
    }
}

// 测试 reload 的辅助:改这里 → build → 看 print 变化
// 当前颜色 = 0xFFFF0000(红色)。改成 0xFF00FF00(绿色),build,看游戏颜色变化
// (frame_count 应该持续递增,不重置)
```

```rust
// platform/src/main.rs
use libloading::Library;
use std::time::{Duration, Instant};

#[repr(C)]
pub struct GameMemory {
    pub is_initialized: bool,
    pub test_color: u32,
    pub frame_count: u64,
}

fn main() {
    let mut memory = GameMemory {
        is_initialized: false,
        test_color: 0,
        frame_count: 0,
    };
    
    let path = "./target/debug/libgame_lib.so";
    let mut lib = unsafe { Library::new(path) }.expect("load library");
    let mut last_mtime = std::fs::metadata(path).unwrap().modified().unwrap();
    let mut last_call = Instant::now();
    
    loop {
        // 检测 reload
        let mtime = match std::fs::metadata(path) {
            Ok(m) => m.modified().unwrap(),
            Err(_) => { 
                std::thread::sleep(Duration::from_millis(100));
                continue;
            }
        };
        if mtime != last_mtime {
            println!("🔄 Reloading {}...", path);
            std::thread::sleep(Duration::from_millis(50));  // 等写入完成
            match unsafe { Library::new(path) } {
                Ok(new_lib) => {
                    lib = new_lib;
                    last_mtime = mtime;
                    println!("✅ Reloaded");
                }
                Err(e) => {
                    eprintln!("❌ Reload failed (build error?): {}", e);
                    // 保留旧 lib,游戏继续跑旧代码
                    last_mtime = mtime;  // 不再触发 reload
                }
            }
        }
        
        // 调用
        let func: libloading::Symbol<unsafe extern "C" fn(*mut GameMemory)> = 
            unsafe { lib.get(b"update_and_render") }.expect("symbol");
        unsafe { func(&mut memory as *mut GameMemory) };
        
        // 锁 60 FPS(简化,不精确)
        std::thread::sleep(Duration::from_millis(16));
        last_call = Instant::now();
    }
}
```

**Troubleshooting**:

- **reload 时 crash**:`update_and_render` 签名变了。**签名必须跨 reload 一致**
- **`undefined symbol: update_and_render`**:`#[no_mangle]` 漏了,或 extern "C" 漏了
- **读到半成品 .so**:文件正在写时 dlopen 失败。加 sleep(100ms) 等写完
- **build 太慢**:cargo check 比 build 快,只检查不 codegen
- **Linux 找不到 .so**:`./libgame_lib.so` 是相对路径,确保 cwd 正确。或用绝对路径
