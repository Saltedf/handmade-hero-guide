
# Day 407 · 开始调试体积纹理

> 昨天(Day 406)你把图形调试器 RenderDoc 接进了 Rust 项目,抓到了那一帧。但抓帧只是起点——你看到 GPU 端的 3D 体积纹理(volume texture)里**全是 0**,却不知道是哪一步把数据搞丢了。今天 Casey 做**侦探工作**:沿着"CPU 端体素数据 → 打包 → `glTexSubImage3D` 上传 → GPU 端采样"的链路逐节检查,缩小可疑范围,直到锁定那个具体的 bug。这一集是图形调试方法论最完整的一课,几乎每个 GPU bug 你都用得上。

## 0 · 为什么要有这一天

把你拉回到那个具体场景:你昨天花了一小时抓 trace,今天打开 RenderDoc 的 Texture Viewer,选到 volume texture 那张,**每个像素都是 0**。你心里咯噔一下——这意味着你的 CPU 端体素里那 32×32×32 共 32768 个 RGB 光照值,有一辆卡车在去 GPU 的路上翻车了。但你不知道在哪翻的。

可能性很多。**第一种可能**:你 CPU 端的体素数组本来就全是 0——光照传播根本没跑,或者跑了但写到错的地方。**第二种可能**:CPU 体素有值,但你打包成上传 buffer 时内存布局不对——比如你把 `Vec3` 当 `f32x3`,但 `Vec3` 在 Rust 里因为有 alignment 是 16 字节,中间空了 4 字节。**第三种可能**:buffer 布局对,但你调用 `glTexSubImage3D` 时 `internal_format` 参数写错了——比如指定 `GL_RGBA8` 但实际传 RGB 数据。**第四种可能**:upload 都对,但 fragment shader 在采样时用了错误的 `sampler3D` uniform 绑定,采样的是另一张空 texture。

光看 RenderDoc 的"texture is all zeros"这一条信息,**你无法区分这四种情况**。所以今天的核心工作是**沿着数据链路一段段验证**:CPU 端打印出来对不对?打包出来的 buffer 头几个字节是什么?trace 里 `glTexSubImage3D` 这一行参数填的对不对?上传之后立即用 `glGetTexSubImage`(OpenGL 4.5+)拷贝回来看是不是真的进去了?fragment shader 采样点的 uvw 坐标是不是落在 texture 范围内?

这套方法论叫**二分调试**(binary-search debugging)。你不知道 bug 在链路哪头,但你每次验证一段,**把可疑范围减半**。这是工程师和初学者最大的区别——初学者改改这里改改那里碰运气,工程师**用证据驱动每一步**。

为什么必须认真学这个?因为**图形 bug 不会随你水平提高而变少,只会变难**。Casey 写了 25 年图形代码,Day 407 这一集仍花了整小时才定位一个 texture upload bug。这是因为 GPU 编程的本质决定了它**不透明**——你看到的是结果,中间过程藏在 GPU 里。掌握"沿数据链路逐段验证"的方法论,你以后遇到任何 GPU bug——shader 黑屏、纹理错位、深度冲突、颜色通道调换——都能用同一套思路解开。

心理锚点:今天之后,你能:(1) 看着一个空的 GPU texture 系统地列出 4-5 个可疑点并按优先级排查;(2) 在 Rust 里把 CPU 端的体素数据 dump 成 PPM 或 PNG 看一眼,确认源头;(3) 在 trace 里找到 `glTexSubImage3D` 调用,逐个核对 11 个参数;(4) 用 `glGetTexSubImage` 把上传后的 texture 拷回 CPU,做"自洽性检查"。**这是图形工程师一辈子的看家功夫**。

## 1 · Casey 今天做了什么(HH 脉络)

Day 406 结束时 Casey 已经在 Visual Studio Graphics Debugger 里抓到了那一帧,看到体积纹理在 GPU 端是空的。Day 407 他系统地排查:

1. **重新抓一次 trace**——确认 texture 全 0 不是偶然。复现性是 debug 的前提。他重启程序、重新抓帧、再看一次,texture 还是全 0。这就排除了"上一次抓帧时刚好赶上 upload 还没发生"的可能。

2. **从 CPU 端源头查**:他在 Rust 里写了一段代码,在调用 `glTexSubImage3D` **之前**遍历整个体素数组,用 `println!` 打印头几个非零体素的值。结果发现 CPU 端体素里有正常的浮点光照值——不是 0。这一步排除了"源头为空"的可能。

3. **检查打包 buffer 的内存布局**:他怀疑 Rust 把 `Vec<RGB>` 序列化到上传 buffer 时布局错。`Vec<RGB>` 在 Rust 里是 `[(f32, f32, f32); N]`,连续内存;但他写的打包代码用了 `chunks(3)` 处理 `&[f32]`,可能在边界处理出错。Casey 打印打包 buffer 的前 32 字节十六进制,看到的是合理值。

4. **检查 `glTexSubImage3D` 的参数**:他在 trace 里找到这一行,**逐个参数对照文档**。11 个参数:`target`, `level`, `xoffset`, `yoffset`, `zoffset`, `width`, `height`, `depth`, `format`, `type`, `data`。他发现 `format` 写成了 `GL_RGB`,但 internal format 是 `GL_RGBA16F`(创建 texture 时指定的)。OpenGL 规范允许 `format` 和 `internal_format` 的 component 数不同,GL 会自动 pad——但**仅在 format 是 `GL_RGB` 且 internal 是 `GL_RGBA` 的情况下,alpha 补 1**。如果 internal 是浮点格式,这个自动转换不一定支持。这是可疑点。

5. **试改 format 为 `GL_RGBA`**——他用 RGBA buffer(每个体素后补 1.0 alpha),`glTexSubImage3D` 用 `GL_RGBA` 上传。重新抓帧:texture 不再全 0!**部分体素有值**。但仍然不是预期画面——可能还有别的 bug。

到 Day 407 结束,Casey 把"GPU texture 全 0"这个大 bug 拆成了两层:(a) format 不匹配,**已修**;(b) texture 有值但渲染结果仍不对,**留给 Day 408**。

## 2 · 心智模型

### 类比:GPU 数据搬运是"跨国邮寄"

想象你从中国寄一个包裹到美国。包裹要走过的环节:打包 → 国内快递 → 海关 → 国际运输 → 美国海关 → 美国快递 → 收件人手里。中间任何一环都可能出问题——打包用了错误的箱子尺寸、运单写错国家代码、海关扣留、地址看不清。如果你只看到"收件人没收到包裹",你完全不知道是哪一环出问题。

GPU 数据搬运完全一样。CPU 里一份 `Vec<RGB>` 体素数据要走的环节:

```
1. CPU 内存里的 Vec<RGB>      (源头)
       ↓
2. 打包成 &const [u8] 或 &const [f32]   (序列化,可能错)
       ↓
3. 调用 glTexSubImage3D         (11 个参数,可能错)
       ↓
4. OpenGL 驱动接收调用,排队等 GPU 处理   (异步,可能 race)
       ↓
5. GPU DMA 把数据从 CPU 内存搬到显存       (DMA,可能 OOM)
       ↓
6. GPU 端的 texture object 被填充         (目标)
       ↓
7. fragment shader 用 sampler3D 采样      (采样,uvw 可能错)
       ↓
8. 最终像素颜色                            (结果)
```

**任何一环出错,最终像素就是黑的**。看"像素黑"你无法定位是哪一环。Casey Day 407 的方法论是:**逐节验证,二分缩小可疑范围**。

### 严谨原理:GPU 数据搬运的 8 个环节

我们把这 8 个环节展开讲清楚。**每一环都有典型 bug 模式**,记住这些 bug 你以后能秒定位。

#### 环节 1:CPU 端源数据

这是你 Rust 代码里维护的数据结构。典型形状:

```rust
#[derive(Copy, Clone)]
pub struct Rgb { pub r: f32, pub g: f32, pub b: f32 }  // 12 字节,4 字节对齐

pub struct VoxelGrid {
    pub cells: Box<[Rgb; 32 * 32 * 32]>,  // 32768 个 cell
    // ...
}
```

**典型 bug**:
- 光照传播没跑(Gauss-Seidel 迭代写错),cells 全是初始的 0
- 写到错的下标(`cells[x + y * W + z * W * H]` 写成了 `cells[x + z * W + y * W * H]`,把 y 和 z 调换)
- 浮点 NaN / Inf 混进去,后续 `max(0, val)` 之类运算产生意外结果

**验证方法**:在 `glTexSubImage3D` 调用之前,在 Rust 里遍历 cells,**用 println 打印头几个非零 cell**:

```rust
let nonzero_count = grid.cells.iter().filter(|c| c.r > 0.0 || c.g > 0.0 || c.b > 0.0).count();
println!("上传前:cells 总数 = {}, 非零 = {}", grid.cells.len(), nonzero_count);
let first_nonzero = grid.cells.iter().find(|c| c.r > 0.0);
println!("第一个非零 cell = {:?}", first_nonzero);
```

预期:`非零 = 几百到几千`(光源周围);如果 `非零 = 0`,源头错了,**别往 GPU 方向查**。

#### 环节 2:序列化打包

OpenGL 接受的是**裸字节流**(`*const std::ffi::c_void`)。你要把 `Box<[Rgb; 32768]>` 转成一段连续的 `f32` 或 `u8` 字节。

```rust
// 把 [Rgb; N] 转成 &[f32; N*3]
// 安全的关键:Rgb 的内存布局必须是 (f32, f32, f32) 无 padding
let flat: &[f32] = unsafe {
    std::slice::from_raw_parts(grid.cells.as_ptr() as *const f32, grid.cells.len() * 3)
};
```

**典型 bug**:
- `Rgb` 加了字段但 `from_raw_parts` 还按 3 个 f32 算
- `Rgb` 有 `#[repr(C)]` 但加了 alignment 属性,变成 16 字节(而不是 12)
- `Rgb` 是 `repr(Rust)`,编译器可能重排字段

**验证方法**:打印 `size_of::<Rgb>()` 和 `size_of_val(&grid.cells[..])`:

```rust
println!("sizeof(Rgb) = {}", std::mem::size_of::<Rgb>());        // 应该是 12
println!("sizeof(cells) = {}", std::mem::size_of_val(&grid.cells[..]));  // 应该是 12 * 32768 = 393216
```

如果 `sizeof(Rgb) != 12`,你加了 `#[repr(C)]` 吗?`repr(Rust)` 默认可能给结构体加 padding 让它对齐到 4 字节(对 Rgb 已经够,但若有 `f64` 字段就会重排)。

#### 环节 3:glTexSubImage3D 的 11 个参数

这是 bug 最密集的一环。函数签名:

```c
void glTexSubImage3D(
    GLenum target,         // 1. GL_TEXTURE_3D
    GLint level,           // 2. mipmap 层级(0 = 原始)
    GLint xoffset,         // 3. x 偏移
    GLint yoffset,         // 4. y 偏移
    GLint zoffset,         // 5. z 偏移
    GLsizei width,         // 6. 宽
    GLsizei height,        // 7. 高
    GLsizei depth,         // 8. 深
    GLenum format,         // 9. 数据格式(GL_RGB / GL_RGBA / GL_RED ...)
    GLenum type,           // 10. 数据类型(GL_FLOAT / GL_UNSIGNED_BYTE ...)
    const GLvoid *data     // 11. 数据指针
);
```

**典型 bug**:
- `target` 写错成 `GL_TEXTURE_2D`(volume 必须是 `GL_TEXTURE_3D`)
- `level` 不是 0(如果你没建 mipmap,level=1 upload 失败)
- `xoffset/yoffset/zoffset` 不为 0(upload 部分区域,而不是整张)
- `width/height/depth` 比 texture 创建时的尺寸大(GL 报错或行为未定义)
- `format` 和 `internal_format` 不匹配(详见下文)
- `type` 写错(比如 internal 是 `GL_RGBA16F` 但 type 是 `GL_UNSIGNED_BYTE`)
- `data` 是 NULL 或野指针

**验证方法**:在 trace 里点开这一行,**逐个参数对照**。RenderDoc 显示参数详情;apitrace 也显示。

#### 环节 4:format 和 internal_format 的关系

这是 OpenGL 最坑爹的设计之一。两个 format 参数在不同函数:

- `glTexImage3D(target, level, internal_format, ...)` —— 创建 texture 时指定,**告诉 GPU 怎么存**:`GL_RGBA8` / `GL_RGBA16F` / `GL_R32F` ...
- `glTexSubImage3D(target, level, ..., format, type, data)` —— 上传时指定,**告诉 OpenGL 你的 CPU 数据是什么格式**:`GL_RED` / `GL_RGB` / `GL_RGBA` ...

**两者关系**:OpenGL 允许它们不匹配,会做转换。比如 internal 是 `GL_RGBA8`(8 bit per channel,RGBA 共 32 bit),你 upload 时 `format=GL_RGB`,`type=GL_UNSIGNED_BYTE`,OpenGL 自动在每个像素后补 alpha=255。**但是**:不是所有组合都支持,**且驱动行为可能不一致**。

工业代码的**最佳实践**:**让 format 完全匹配 internal_format 的 component 数**。internal 是 RGBA,upload 就用 GL_RGBA;internal 是 RGB,upload 就用 GL_RGB。绝不依赖驱动自动转换——它在 NVIDIA 上可能 work,在 Intel 集显上可能不 work。

Casey Day 407 的第一个 bug 就是这个——internal 是 RGBA16F(4 通道),但 upload 用了 GL_RGB(3 通道),Intel 集显上驱动没补 alpha,直接传成全 0。

#### 环节 5:GPU 异步性

你调用 `glTexSubImage3D` 返回时,GPU **没有**完成上传。GPU 把任务丢进队列,继续做别的事。CPU 端如果你立即修改 buffer(同一个 `&[f32]`),会发生**data race**——GPU 还在读,你已经改了。

**正确做法**:用 **Pixel Buffer Object (PBO)**。创建 PBO,把数据填进 PBO,然后从 PBO upload 到 texture:

```rust
// 1. 绑定 PBO
gl.bind_buffer(glow::PIXEL_UNPACK_BUFFER, Some(pbo));
// 2. 把数据写进 PBO(这一步返回后 CPU 可以立刻用 data 做别的事)
gl.buffer_data_u8_slice(glow::PIXEL_UNPACK_BUFFER, data, glow::STREAM_COPY);
// 3. 触发 upload(PBO 数据 → texture)
gl.tex_sub_image_3d(texture, 0, 0, 0, 0, W, H, D, glow::RGB, glow::FLOAT, glow::PixelUnpackData::BufferOffset(0));
```

PBO 给 OpenGL 一个"你 guaranteed 不会再碰这段数据"的承诺,OpenGL 可以放心地安排 DMA。

**典型 bug**:不用 PBO,直接传 `&[f32]` 的指针。glow 在底层把这个指针交给 OpenGL,OpenGL 实现可能立即拷贝、也可能延迟拷贝。**Debug 模式下**经常 work,**Release 模式下**因为优化更激进,常出现 race。

#### 环节 6:DMA 传输

GPU 通过 DMA(Direct Memory Access)从 CPU 内存搬运数据到显存。这一步是**硬件**完成的,不在你代码控制下。但有两个隐藏陷阱:

- **内存对齐**:DMA 通常要求每行数据对齐到特定字节(常见 4 或 8 字节)。如果你的 row size 是 33 字节(奇数),DMA 可能拒绝或加 padding。用 `glPixelStorei(GL_UNPACK_ALIGNMENT, 1)` 关闭对齐检查,或保证 row size 是 4 的倍数。
- **可见性**:CPU 写的内存,GPU 不一定立即看到。多核 CPU、缓存一致性问题,需要 memory barrier(`__sync_synchronize()` 或 Rust 的 `atomic::fence`)。OpenGL 在内部帮你处理了这些,但如果你用 Vulkan 自己管理,必须显式做。

#### 环节 7:GPU 端 texture 被填充

upload 完成后,GPU 端 texture object 的对应区域有了数据。**但 OpenGL 不告诉你 upload 完成了**——它是 fire-and-forget。如果你立即采样,可能采到旧数据。

**同步方法**:用 fence:

```rust
let sync = gl.fence_sync(glow::SYNC_GPU_COMMANDS_COMPLETE, 0);
// 等等渲染下一帧前
let status = gl.client_wait_sync(sync, 0, glow::TIMEOUT_IGNORED);
// status == SIGNALED 表示 GPU 完成
```

#### 环节 8:fragment shader 采样

texture 有数据,不代表 shader 采到了。**采样 bug** 类型:

- `sampler3D` uniform 没绑定到正确 unit(`glUniform1i(loc, 0)` 但 `glActiveTexture(GL_TEXTURE0)` 没绑)
- uvw 坐标越界(超出 [0,1]),`GL_CLAMP_TO_EDGE` 边界处理把它截到边界像素,看起来像"只有边缘有光"
- 用了 `textureLod(sampler, uvw, lod)` 但 lod 不对
- shader 编译失败但没检查(GL 静默用上一个 program)

**验证方法**:在 fragment shader 里写 `gl_FragColor = vec4(texture(uSampler3D, vec3(uvw)).rgb, 1.0);` 直接把采样结果当颜色输出,**看屏幕上画出来的 texture**。

### 二分调试法:沿着链路找 bug

把上面 8 个环节串起来,**任何 GPU 数据问题**都用同一种思路排查:

```
1. 源头对了?(CPU 端数据非零,布局正确)
2. 打包对了?(size_of 验证,前几个字节 hexdump)
3. 调用对了?(11 个参数逐个核对 trace)
4. format 匹配?(internal_format vs format)
5. 同步对了?(PBO、fence、alignment)
6. GPU 存了?(glGetTexSubImage 拷回 CPU 验证)
7. 采样对了?(shader 里直接输出采样结果)
```

按这个顺序排查,**每一步都可能发现问题**。Day 407 Casey 的问题在第 4 步(format 不匹配),Day 408 的问题会在第 7 步(采样坐标错)。

### 工具:glGetTexSubImage 自洽性检查

OpenGL 4.5 提供了"反向"upload 的函数:**把 GPU 端 texture 拷回 CPU**。这是验证 upload 是否成功的金标准。

```rust
// 拷回 CPU
let mut readback = vec![0.0f32; W * H * D * 3];
unsafe {
    gl.get_tex_sub_image(
        glow::TEXTURE_3D, 0,
        0, 0, 0, W as i32, H as i32, D as i32,
        glow::RGB, glow::FLOAT,
        std::slice::from_raw_parts_mut(readback.as_mut_ptr() as *mut u8, readback.len() * 4),
    );
}
println!("GPU 端第 0 个 cell = {:?}", &readback[0..3]);
```

如果 readback 的值和 CPU 端源头一致,**upload 成功**,bug 在采样环节。如果不一致,**upload 失败**,bug 在 1-5 环节。

**注意**:`glGetTexSubImage` 在某些驱动上很慢(因为 GPU→CPU 拷贝慢),不要每帧调用。只在 debug 时调用一次。

## 3 · 四域深入

### 3.1 · 🎨 图形学视角

体积纹理(volume texture,也叫 3D texture)在图形学里有三大用途:

1. **光照体积(Light Propagation Volume)**——Casey 当前场景。把空间离散成 3D 网格,每格存 RGB 光强,渲染时 fragment shader 从 texture 采样。这是 2010 年 Crytek 提出、被 Unreal Engine 4 用过的 GI 方案。
2. **医疗影像**(CT / MRI):一组 2D 切片堆叠成 3D,fragment shader 用 ray marching 渲染体积。
3. **体素地形 / 流体**:把烟雾、火焰、水做成 3D texture,fragment shader 在每个像素发射射线穿过 texture 累积不透明度。

体积纹理和 2D texture 的核心差别是**内存和带宽开销**。32×32×32 的 RGB16F texture = 32³ × 3 × 2 字节 = 196608 字节(192 KB),看起来不大;但 256³ 就是 96 MB,带宽开销显著。所以工程上体积纹理通常做**多网格**(multi-grid):粗网格 32³ 存全局光照,细网格 64³ 存细节,渲染时混合。

**采样方式**:2D texture 用 uv(2 维),volume 用 uvw(3 维)。uvw 在 [0,1]³ 空间内,**整数边界对应 voxel 中心**:`uvw = (x + 0.5) / W`。如果你写成 `uvw = x / W`,会采到 voxel 边界,触发 `GL_CLAMP_TO_EDGE`,所有采样值退化为边缘的 0。

**三线性插值**:OpenGL 默认 `GL_LINEAR` filter 对 3D texture 做 trilinear 插值——同时插值 8 个相邻 voxel。这是体积纹理平滑的关键。如果设 `GL_NEAREST`,你会看到 voxel 边界的方块感,Casey 在 Day 408 会改这个。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上有几个工具帮你 debug 3D texture:

**apitrace + qapitrace**:已经讲过(Day 406)。在 trace 里点开 `glTexSubImage3D` 这一行,右侧显示参数,底部"State"标签页能看到当前 texture object 的 internal_format / size。

**RenderDoc**:更强大的 visual 工具。Texture Viewer 里能看到每个 texture 的实际像素,3D texture 显示为多层切片(slice)。点击"Save Image"能把 texture dump 成 PNG,你离线分析。

**mesa-demos 里的 glxinfo**:

```bash
glxinfo | grep "OpenGL version"
# OpenGL version string: 4.6 (Compatibility Profile) Mesa 24.0
```

确认你的驱动支持 4.5+(才有 `glGetTexSubImage`)。Mesa 是 Linux 上 NVIDIA / AMD / Intel 开源 driver 的集合。

**intel_gpu_top** 监控 GPU 利用率:

```bash
sudo pacman -S intel-gpu-tools
sudo intel_gpu_top
# 看到 GPU 使用率、内存带宽
```


### 3.3 · 🦀 Rust 生态视角

Rust 调 GL 涉及的几个 crate:

| Crate | 作用 | Day 407 用到 |
|---|---|---|
| `glow` | GL 函数 wrapper | 调 `tex_sub_image_3d` |
| `bytemuck` | 把 Rust struct 安全转成字节 | 打包 `&[Rgb]` 到 `&[u8]` |
| `glam` | 数学库 | voxel 坐标变换 |
| `image` / `png` | 图片 I/O | 把 slice dump 成 PNG |

**`bytemuck` 的角色**:Rust 默认不允许把 `&[Rgb]` 直接 cast 成 `&[u8]`,因为编译器不知道 `Rgb` 是否可以"按字节复制"(trivially copyable)。`bytemuck` 提供 `Pod` trait(trivially copyable 的 marker)和 `cast_slice`:

```rust
use bytemuck::{Pod, Zeroable};

#[derive(Copy, Clone, Pod, Zeroable)]
#[repr(C)]
pub struct Rgb { pub r: f32, pub g: f32, pub b: f32 }

let cells: &[Rgb] = &grid.cells[..];
let bytes: &[u8] = bytemuck::cast_slice(cells);
// 现在可以传给 glow::tex_sub_image_3d
```

**为什么 unsafe**:`cast_slice` 内部是 unsafe(可能是 UB),但 `Pod` trait 保证 `Rgb` 是"位模式合法"的(没有 padding、没有 enum、没有 reference),所以这个 unsafe 实际是 sound 的。这就是 Rust 设计哲学——把 unsafe 推到边界,只要边界守住,内部就安全。

**dump 成 PNG 的辅助代码**(为 debug 用):

```rust
fn dump_voxel_slice_to_png(grid: &VoxelGrid, z: usize, path: &str) {
    // 取 z 层的切片
    let mut img = image::RgbImage::new(32, 32);
    for y in 0..32 {
        for x in 0..32 {
            let cell = grid.cells[x + y * 32 + z * 32 * 32];
            let r = (cell.r.clamp(0.0, 1.0) * 255.0) as u8;
            let g = (cell.g.clamp(0.0, 1.0) * 255.0) as u8;
            let b = (cell.b.clamp(0.0, 1.0) * 255.0) as u8;
            img.put_pixel(x as u32, y as u32, image::Rgb([r, g, b]));
        }
    }
    img.save(path).unwrap();
}
// 用法:dump_voxel_slice_to_png(&grid, 16, "voxel_z16.png");
// 然后用 image viewer 看,确认光照分布符合预期
```

**所有权角度**:`tex_sub_image_3d` 接受 `&[u8]`(借用),内部把指针给 GL,返回后**你不能立即修改这个 slice**——GL 可能还在读。最安全做法是:**调用后保留 slice 直到下一帧 swap buffer**,或者用 PBO 让 GL 复制走再立即返回。

### 3.4 · 🔢 数学视角(体积纹理的几何)

体积纹理是**离散化的 3D 场**。数学上是一个 `f: R³ → R³` 函数(每点一个 RGB 值),但只采样在 32×32×32 网格上。

**重建**:`texture(uvw, sampler)` 通过 trilinear 插值从离散网格重建连续函数。uvw 是归一化坐标 [0,1]³:

```
uvw = (world_pos - grid_min) / grid_size
```

如果 `world_pos` 在 grid 范围外,uvw 越界,`GL_CLAMP_TO_EDGE` 截到边界值(边缘 voxel 的值),渲染时常表现"边界光晕"。Casey 在 Day 408 会处理这个——用 `GL_REPEAT` 让光在网格边缘环绕(适合均匀场),或扩大网格避免越界。

**多重网格插值(multi-grid)**:Casey 用多层 LPV(粗 32³、细 64³、更细 128³)。每个点采多层并按权重混合:

```
final_light = w0 * sample(coarse, uvw_coarse) +
              w1 * sample(fine,   uvw_fine)   +
              w2 * sample(finer,  uvw_finer)
```

权重 `w0, w1, w2` 按距离和层级选。这套思路和图像 mipmap 完全一样——只是从 2D 推到 3D。

## 5 · 对照与变奏

### 2D texture vs 3D texture

| 维度 | 2D texture | 3D texture(volume) |
|---|---|---|
| 维度 | uv ∈ [0,1]² | uvw ∈ [0,1]³ |
| 内存 | W × H × components | W × H × D × components |
| 典型用途 | sprite、UI、surface texture | 光照场、CT/MRI、体素 |
| 采样开销 | 1 次(双线性,4 个 texel) | 1.5 次(三线性,8 个 texel) |
| Mipmap | 层级递减 W/2,H/2 | 层级递减 W/2,H/2,D/2(各向异性更复杂) |
| `glTexImage2D/3D` 参数 | 8 个(无 depth) | 9 个(多 depth) |

工业游戏里 3D texture 用得比 2D 少得多,但每个用上 3D 的地方都是核心技术:LPV、体积云、流体、LUT(颜色查找表)、3D 噪声(程序化地形)。学会它你就打开了图形学一大类应用。

### 同一问题的不同 API

| 任务 | OpenGL | Vulkan | D3D12 | Metal |
|---|---|---|---|---|
| 创建 3D texture | `glTexImage3D` | `vkCreateImage` + `vkAllocateMemory` | `CreateCommittedResource` | `newTexture(descriptor:)` |
| Upload | `glTexSubImage3D` + PBO | `vkCmdCopyBufferToImage` | `CopyTextureRegion` | `replaceRegion` |
| Shader 采样 | `sampler3D` / `texture()` | `texture(t, sampler, vec3)` | `Texture3D.Sample(sampler, float3)` | `texture.sample(sampler, float3)` |

OpenGL 最简洁但隐藏细节;Vulkan 最 explicit 但代码量 5 倍;D3D12 类似 Vulkan;Metal 中等。Casey 在 HH 用 OpenGL,他后期 Day 540+ 提到 Vulkan 是图形 API 的未来。

### 历史演化

- **1996 OpenGL 1.0**:只有 1D / 2D texture
- **2001 OpenGL 1.2**:加入 3D texture(`glTexImage3D`)
- **2004 OpenGL 2.0**:GLSL 1.0 支持 `sampler3D`
- **2010 OpenGL 4.0**:Tessellation、间接 draw
- **2015+ Vulkan / D3D12**:explicit API,3D texture 概念不变但创建流程完全不同

Casey Day 407 用 OpenGL 4.3,这是因为大多数 debug 工具(VSGD、RenderDoc、apitrace)对 4.3 支持最稳定。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:`glTexImage3D` 和 `glTexSubImage3D` 有什么区别?为什么需要两个函数?如果只用 `glTexImage3D` 会怎样?

**参考解答**:
- `glTexImage3D(target, level, internal_format, W, H, D, border, format, type, data)` —— **创建**或**完全重新分配**一个 3D texture。它会 free 原来的存储,分配新的,然后把 data 写进去。**调用代价高**(分配内存 + 数据搬运)。
- `glTexSubImage3D(target, level, xoff, yoff, zoff, W, H, D, format, type, data)` —— **只更新**已存在 texture 的一个子区域。**不重新分配**,只搬运数据。**调用代价低**。

如果每帧都用 `glTexImage3D`,GPU 每帧都要 free + alloc 内存,**碎片化严重、性能差**。`glTexSubImage3D` 复用已分配的内存,只换数据,这是高性能渲染的标准做法。

类比:`glTexImage3D` 是"拆掉旧房子盖新的",`glTexSubImage3D` 是"装修现有房子"。前者慢但彻底,后者快但要求房子已经在。

### Lv2 · 动手实践

**题**:写一个最小的 Rust 程序,创建 4×4×4 的 `GL_RGBA8` 3D texture,用 `glTexSubImage3D` 上传一段测试数据(每个 cell 都是 `Rgb { r: 1.0, g: 0.5, b: 0.25 }`),用 `glGetTexSubImage` 读回,**确认读回值等于写入值**。

完成标准:
- 程序在 headless 环境跑(不需要窗口,用 `glutin` 的 headless context 或 `glium` 的 testing context)
- 打印 `写入值` 和 `读回值`,数值一致(允许浮点 1e-6 误差)
- 改成 `GL_RGBA16F`,再次验证(浮点 texture)

**参考解答**:这个练习的关键是**用对 crate**。Rust 上做 headless GL 测试,推荐 `glutin` + `glow`:

```toml
# Cargo.toml
[dependencies]
glutin = "0.31"
glow = "0.13"
bytemuck = "1.14"
raw-window-handle = "0.5"
```

```rust
use glow::HasContext;
use bytemuck::{Pod, Zeroable};

#[derive(Copy, Clone, Pod, Zeroable)]
#[repr(C)]
struct Rgb { r: f32, g: f32, b: f32 }

fn main() {
    // 创建 headless GL context(简化版,实际要用 glutin 的 ContextBuilder)
    // 这里只展示核心 upload/readback 逻辑

    let W = 4; let H = 4; let D = 4;
    let cells = vec![Rgb { r: 1.0, g: 0.5, b: 0.25 }; W * H * D];

    // 假设 gl: glow::Context 已经初始化
    let gl = unsafe { glow::Context::from_loader_function(|s| /* ... */ std::ptr::null()) };

    // 1. 创建 texture
    let texture = unsafe { gl.create_texture() }.unwrap();
    unsafe {
        gl.bind_texture(glow::TEXTURE_3D, Some(texture));
        gl.tex_image_3d(
            glow::TEXTURE_3D, 0,
            glow::RGBA8 as i32,  // internal_format
            W as i32, H as i32, D as i32,
            0,
            glow::RGB,           // format(3 components)
            glow::UNSIGNED_BYTE, // type(byte)
            glow::PixelUnpackData::Slice(Some(bytemuck::cast_slice(&cells))),
        );
        // 注意:这里我们 cast 成 byte,AUTO 转换精度损失(1.0 -> 255)
        // 所以读回时也是 byte 范围

        // 2. 读回
        let mut readback = vec![0u8; W * H * D * 4];  // RGBA
        gl.get_tex_sub_image(
            glow::TEXTURE_3D, 0,
            0, 0, 0, W as i32, H as i32, D as i32,
            glow::RGBA, glow::UNSIGNED_BYTE,
            &mut readback,
        );

        println!("写入 cell[0]: Rgb(1.0, 0.5, 0.25)");
        println!("读回 byte[0..4]: {:?}", &readback[0..4]);
        // 应该是 [255, 128, 64, 255](alpha 默认补 255)
    }
}
```

**关键点**:
- `internal_format = GL_RGBA8` 但 `format = GL_RGB` 时,GL 自动补 alpha=255
- `UNSIGNED_BYTE` 把 [0.0,1.0] 浮点映射到 [0,255] byte(线性映射)
- `glGetTexSubImage` 需要在 `glBindTexture` 之后调用

```rust
// src/lpv/debug.rs
use glow::HasContext;
use bytemuck::{Pod, Zeroable};

#[derive(Copy, Clone, Pod, Zeroable)]
#[repr(C)]
pub struct Rgb { pub r: f32, pub g: f32, pub b: f32 }

#[derive(Default)]
pub struct VoxelGrid {
    pub cells: Vec<Rgb>,           // 32*32*32 = 32768 个
    pub width: usize,
    pub height: usize,
    pub depth: usize,
}

impl VoxelGrid {
    pub fn new(w: usize, h: usize, d: usize) -> Self {
        Self {
            cells: vec![Rgb { r: 0.0, g: 0.0, b: 0.0 }; w * h * d],
            width: w, height: h, depth: d,
        }
    }
    pub fn get(&self, x: usize, y: usize, z: usize) -> Rgb {
        self.cells[x + y * self.width + z * self.width * self.height]
    }
    pub fn set(&mut self, x: usize, y: usize, z: usize, c: Rgb) {
        self.cells[x + y * self.width + z * self.width * self.height] = c;
    }
}

/// 第 1 步:验证 CPU 端源头
pub fn check_source(grid: &VoxelGrid) {
    let nonzero = grid.cells.iter()
        .filter(|c| c.r > 0.0 || c.g > 0.0 || c.b > 0.0)
        .count();
    println!("[debug] cells 总数 = {}, 非零 = {}", grid.cells.len(), nonzero);
    if nonzero == 0 {
        println!("[debug] WARNING:源头全零!bug 在 CPU 光照传播,不在 GPU upload");
    } else if let Some(first) = grid.cells.iter().find(|c| c.r > 0.0) {
        println!("[debug] 第一个非零 cell = {:?}", first);
    }
}

/// 第 2 步:验证打包 buffer 内存布局
pub fn check_layout() {
    println!("[debug] sizeof(Rgb) = {} bytes", std::mem::size_of::<Rgb>());
    println!("[debug] sizeof(32768 个 Rgb) = {} bytes", std::mem::size_of::<Rgb>() * 32768);
    // 应该输出:sizeof(Rgb) = 12, sizeof(32768 个 Rgb) = 393216
    // 如果不是 12,你的 #[repr(C)] / 字段对齐有问题
    assert_eq!(std::mem::size_of::<Rgb>(), 12, "Rgb 应该是 12 字节");
}

/// 第 3 步:打印 glTexSubImage3D 调用前的参数
pub fn trace_upload_args(grid: &VoxelGrid) {
    println!("[debug] glTexSubImage3D 参数:");
    println!("  target = GL_TEXTURE_3D");
    println!("  level = 0");
    println!("  xoffset = 0, yoffset = 0, zoffset = 0");
    println!("  width = {}, height = {}, depth = {}", grid.width, grid.height, grid.depth);
    println!("  format = GL_RGBA (注意 RGBA, 不是 RGB)");
    println!("  type = GL_FLOAT");
    println!("  data = &cells (length = {})", grid.cells.len());
}

/// 第 6 步:upload 后用 glGetTexSubImage 拷回,做自洽性检查
pub fn check_gpu_side(gl: &glow::Context, grid: &VoxelGrid, texture: glow::Texture) {
    let w = grid.width as i32;
    let h = grid.height as i32;
    let d = grid.depth as i32;
    let mut readback: Vec<Rgb> = vec![Rgb { r: -1.0, g: -1.0, b: -1.0 }; grid.cells.len()];

    unsafe {
        gl.bind_texture(glow::TEXTURE_3D, Some(texture));
        // glGetTexSubImage:GL_RGBA16F texture 用 GL_RGB + GL_FLOAT 读(只读 RGB 不读 alpha)
        let bytes: &mut [u8] = std::slice::from_raw_parts_mut(
            readback.as_mut_ptr() as *mut u8,
            readback.len() * std::mem::size_of::<Rgb>(),
        );
        gl.get_tex_sub_image(
            glow::TEXTURE_3D, 0,
            0, 0, 0, w, h, d,
            glow::RGB, glow::FLOAT,
            bytes,
        );
    }

    // 比较 CPU 端和 GPU 端
    let mismatch_count = grid.cells.iter().zip(readback.iter())
        .filter(|(a, b)| (a.r - b.r).abs() > 1e-3 || (a.g - b.g).abs() > 1e-3 || (a.b - b.b).abs() > 1e-3)
        .count();
    println!("[debug] GPU 端 vs CPU 端 mismatch = {}", mismatch_count);
    if mismatch_count == 0 {
        println!("[debug] upload 成功!bug 在采样环节");
    } else {
        println!("[debug] upload 失败,bug 在 1-5 环节");
        // 打印头几个 mismatch
        for (i, (a, b)) in grid.cells.iter().zip(readback.iter()).enumerate() {
            if (a.r - b.r).abs() > 1e-3 {
                println!("[debug] cell[{}]:CPU={:?}, GPU={:?}", i, a, b);
                break;
            }
        }
    }
}
```

### 用 image crate 把 voxel 切片 dump 成 PNG

```rust
// 在 Cargo.toml 加:image = "0.25"

use image::{RgbImage, Rgb as ImgRgb};

pub fn dump_voxel_slice_to_png(grid: &VoxelGrid, z: usize, path: &str) {
    let mut img = RgbImage::new(grid.width as u32, grid.height as u32);
    for y in 0..grid.height {
        for x in 0..grid.width {
            let cell = grid.get(x, y, z);
            // HDR 值(>1.0)用 tone mapping(简化版 Reinhard)
            let tonemap = |v: f32| -> u8 {
                let mapped = v / (v + 1.0);  // Reinhard
                (mapped.clamp(0.0, 1.0) * 255.0) as u8
            };
            img.put_pixel(x as u32, y as u32, ImgRgb([tonemap(cell.r), tonemap(cell.g), tonemap(cell.b)]));
        }
    }
    img.save(path).unwrap();
    println!("[debug] voxel 切片 z={} dump 到 {}", z, path);
}
```

**Troubleshooting**:

- `glGetTexSubImage 没找到`:你的驱动不支持 OpenGL 4.5。Mesa 上更新驱动 `sudo pacman -Syu mesa`,或换用 RenderDoc 的"Save Image"功能替代。
- `RenderDoc 启动后程序立即崩`:RenderDoc 不支持你的 GL 版本组合,降低 context 创建参数(从 4.5 降到 4.3 core profile)。
- `apitrace trace 是空的`:程序没调用 GL 函数,或被 strip 掉符号了。试 `apitrace trace --api=gl --symbol-prefix=` 重新抓。
- `readback 全 0,但 CPU 端 cells 非零`:format 不匹配(见 §2 环节 4)。改成 RGBA buffer + GL_RGBA format。
