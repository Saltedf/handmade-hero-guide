# Day 282 · Z 轴移动与相机运动

> 今天 Casey 把"2.5D"概念引入游戏——角色除了 X/Y,还可以有"高度"Z。Z 影响视觉(角色精灵按高度缩放 / 偏移)、影响游戏逻辑(高处可以"飞过"低处障碍)、影响相机(视差效果)。

## 0 · 为什么要有这一天

到目前为止你的游戏是纯 2D:X/Y 决定位置。但是类 Zelda 游戏经常有"高度"概念:

- 角色可以**跳**(短暂的 Z > 0)
- 角色**站在高处**(桥上、台阶上)
- 飞行怪物有 Z(不像地面怪物贴地)
- 投射物(箭 / 火球)有抛物线轨迹

这些机制都依赖"第三个维度"。但 HH 不是 3D 游戏——它是"2.5D":用 2D 渲染,但加上 Z 轴模拟深度。

Z 轴的几个用途:

1. **视觉**:`screen_y = world_y - z * scale`(z 高的角色画在更高的位置),并按 z 缩放(远小近大)
2. **碰撞**:不同 z 的物体不互相碰撞(桥上 vs 桥下)
3. **相机**:z 高的物体进入"前景",相机视差感更强

心理锚点:做完这个,你的游戏有"深度",玩家能感觉到角色立体。

## 1 · Casey 今天做了什么

Casey 把 Z 轴加入 player 和 entity:

1. Player 加 `z: f32` 字段
2. Entity 加 `z: f32` 字段
3. 跳跃:按 Space 时给 z_velocity 一个向上初速度,每帧 z_velocity -= gravity * dt
4. 渲染时:`screen_y = world_y - z`,精灵按 z 缩放(z 越大越大,模拟近大远小)
5. 相机:z 不影响相机位置,但影响**渲染顺序**(z 大的画在前面)

Casey 演示了"跳过洼地"的场景:玩家跑步跳起,在空中飞过一段地面的水,落到对岸。Z > 0 时玩家精灵"飘"在空中,落下时回到地面。

最后 Casey 处理了"阴影":角色在空中时,地面应该有一个"影子"标记落点。这个细节让 Z 视觉更清晰。

## 2 · 心智模型

### 类比:俯视的桌面游戏

想象你在桌子上方俯视桌面,桌面上有棋子。棋子可以:

- 沿桌面滑动(X/Y 移动)
- 被你拿起来悬空(Z > 0)

你看到的画面是:

- 棋子还在桌面上某个位置(X/Y)
- 但它的"图像"漂浮在桌面位置之上(Z 高 = 视觉上偏上)
- 棋子下面在桌面有一个"阴影"(它的实际 X/Y 位置)

这就是 2.5D 的视觉模型——Z 影响渲染时的偏移和缩放,但不影响俯视的位置。

### 严谨原理:Z 轴的物理 + 视觉

#### 数据结构

```rust
struct Player {
    pos: Vec2,   // X/Y 在地面上的位置
    z: f32,      // Z 高度(0 = 地面)
    z_velocity: f32,  // 垂直速度
}
```

#### 跳跃物理

```rust
const GRAVITY: f32 = 800.0;  // 像素/秒²
const JUMP_VELOCITY: f32 = 300.0;  // 跳起的初速度

impl Player {
    fn jump(&mut self) {
        if self.z == 0.0 {  // 只有在地面上才能跳
            self.z_velocity = JUMP_VELOCITY;
        }
    }

    fn update(&mut self, dt: f32) {
        // Z 物理
        self.z += self.z_velocity * dt;
        self.z_velocity -= GRAVITY * dt;
        // 落地检测
        if self.z < 0.0 {
            self.z = 0.0;
            self.z_velocity = 0.0;
        }
    }
}
```

跳跃的物理是经典抛物线:

- t=0:z=0, z_velocity=300
- t=0.375:z ≈ 56, z_velocity = 0(最高点)
- t=0.75:z=0, z_velocity = -300(落地)

总跳跃时长约 0.75 秒。

#### 渲染:Z 偏移 + 缩放

```rust
fn render_player(buf: &mut [u32], player: &Player, camera_offset: Vec2) {
    // X/Y 是地面位置(阴影位置)
    let ground_x = player.pos.x - camera_offset.x;
    let ground_y = player.pos.y - camera_offset.y;

    // 渲染时 y 减去 z(z 高 = 精灵向上偏移)
    let sprite_x = ground_x;
    let sprite_y = ground_y - player.z;

    // 缩放:z 高一点(模拟"近大远小"的反向——其实更"靠近相机")
    let scale = 1.0 + player.z * 0.001;  // 每像素 z 增加 0.1%
    let size = 16.0 * scale;

    // 画阴影(原 X/Y 位置)
    draw_shadow(buf, ground_x, ground_y, 16.0);

    // 画精灵(sprite_x, sprite_y)
    draw_sprite(buf, sprite_x, sprite_y, size);
}
```

阴影是关键的视觉提示——没有阴影,玩家看不出角色"跳起来了"(因为只有精灵位置变,没有参照)。

#### Z 和碰撞

不同 Z 的物体可以重叠但不碰撞:

- 玩家 Z=0(地面),怪物 Z=0 → 正常碰撞
- 玩家 Z=50(跳跃中),怪物 Z=0 → 不碰撞(玩家飞过)
- 桥上物体 Z=20,桥下物体 Z=0 → 不碰撞

```rust
fn check_collision(a: &Entity, b: &Entity) -> bool {
    // X/Y 重叠
    let xy_overlap = (a.pos - b.pos).length() < (a.size + b.size);
    if !xy_overlap { return false; }

    // Z 重叠(允许 16 像素的 Z 容差)
    let z_overlap = (a.z - b.z).abs() < 16.0;
    z_overlap
}
```

#### 相机和 Z

Z 不直接影响相机位置,但影响:

1. **渲染顺序**:Z 大的(高处)画在 Z 小的之上(模拟"前面的物体遮挡后面的")
2. **视差**:背景层 Z 不同时,移动速度不同(远处的山移动慢,近处的树移动快)

```rust
// 按渲染顺序排序
let mut visible: Vec<&Entity> = entities.iter()
    .filter(|e| is_visible(e, camera))
    .collect();
visible.sort_by_key(|e| e.z as i32);  // Z 升序,Z 大的在后画(上层)

for entity in visible {
    render_entity(buf, entity, camera);
}
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

2.5D 在游戏里很常见:

- **The Legend of Zelda: Link's Awakening**:2.5D,有跳跃和高低
- **Stardew Valley**:纯 2D,但用 sort-by-y 模拟"前后关系"
- **Octopath Traveler**:HD-2D,2D 精灵 + 3D 场景
- **Diablo 2**:等距 2.5D

业界术语:

- **Top-down 2D**:纯俯视(早期 Zelda)
- **2.5D**:2D 渲染 + Z 深度(今天做的)
- **Isometric**:等距 2.5D(Diablo)
- **3D**:真 3D 模型 + 透视相机

Casey 的 HH 是 2.5D。

#### Y-sort 技巧

不需要真正的 Z,只按 Y 坐标排序也能模拟前后:

```rust
entities.sort_by_key(|e| e.pos.y as i32);  // Y 小的(屏幕上方)先画
```

这样屏幕下方的角色"遮挡"屏幕上方的——视觉上像"前面挡后面"。Stardew Valley 用这种技巧。

但是 Y-sort 不能做"跳跃"(因为跳起时 Y 不变,只是视觉上抬高)。Z 轴更灵活。

### 3.2 · 🎨 图形学视角

Z 在图形学里是真正的深度维度。3D 渲染:

- vertex 有 (x, y, z)
- 透视投影:z 大的物体看起来小
- 深度缓冲(z-buffer):每个像素存 z,绘制时只覆盖 z 更小的

2.5D 借用 z 的概念但简化:

- 不做透视投影(2D 渲染无透视)
- 不用 z-buffer(用 sort-by-z 替代)
- z 只影响"渲染位置偏移"和"排序"

#### 深度排序 vs Z-buffer

- **深度排序**:CPU 算,按 z 排序绘制,简单
- **Z-buffer**:GPU 算,每像素存 z,精确但内存开销

HH 用深度排序(无 GPU),后面切到 OpenGL 可以用 z-buffer。

### 3.3 · 🐧 Linux 系统编程视角

Linux 桌面环境的 Z:

- **Wayland / X11**:窗口有 Z(stack order),Z 大的在上
- **CSS z-index**:Web 元素的 Z(2.5D)
- **compositing manager**:合成多个图层

这些都是"2.5D"的实例——本质 2D,但加上 Z 维度处理遮挡。

### Lv1 · 概念辨析

**题**:为什么需要"阴影"来让 Z 视觉清晰?给出至少 3 个理由。

**参考解答**:
1. **深度感知**:人眼通过阴影判断物体离地高度。无阴影时大脑看不出"角色飘起来了",只看到"角色位置变了"
2. **落地预判**:玩家跳起时,阴影显示落点。没有阴影玩家不知道会落到哪
3. **遮挡提示**:阴影让玩家理解"地面在下面,角色在上面"的空间关系
4. **美学**:阴影增加画面层次,否则角色像"贴在背景上"
5. **遮挡判断**:玩家能从阴影位置判断"角色实际 X/Y",辅助碰撞判断
6. **减少眩晕**:跳起时如果没有阴影,玩家会感觉"角色漂走了",阴影提供稳定的参照

### Lv2 · 动手实践

**题**:实现 Player 的 Z 跳跃 + 渲染偏移 + 阴影。

测试:

- Player 初始 z=0
- 按空格跳,z_velocity = 300
- 模拟 1 秒,验证 z 经历"上升 → 顶点 → 下降 → 0"过程

完成标准:z 在 0.375 秒到达顶点,0.75 秒落地。

**参考解答**:

```rust
const GRAVITY: f32 = 800.0;
const JUMP_VELOCITY: f32 = 300.0;

#[derive(Clone, Copy, Debug)]
struct Vec2 { x: f32, y: f32 }

struct Player {
    pos: Vec2,
    z: f32,
    z_velocity: f32,
}

impl Player {
    fn new(pos: Vec2) -> Self {
        Self { pos, z: 0.0, z_velocity: 0.0 }
    }

    fn jump(&mut self) {
        if self.z == 0.0 {
            self.z_velocity = JUMP_VELOCITY;
        }
    }

    fn update(&mut self, dt: f32) {
        self.z += self.z_velocity * dt;
        self.z_velocity -= GRAVITY * dt;
        if self.z < 0.0 {
            self.z = 0.0;
            self.z_velocity = 0.0;
        }
    }
}

fn main() {
    let mut player = Player::new(Vec2 { x: 100.0, y: 200.0 });

    player.jump();
    println!("t, z, z_velocity");

    let dt = 0.01;
    let mut t = 0.0;
    let mut max_z = 0.0;
    let mut max_z_t = 0.0;

    for step in 0..100 {
        player.update(dt);
        t += dt;
        if player.z > max_z {
            max_z = player.z;
            max_z_t = t;
        }
        if step % 10 == 0 {
            println!("{:.2}, {:.2}, {:.2}", t, player.z, player.z_velocity);
        }
        if player.z == 0.0 && step > 0 {
            println!("Landed at t={:.2}", t);
            break;
        }
    }

    println!("\nMax z = {:.2} at t = {:.2}", max_z, max_z_t);
    // 理论值:max z = v²/(2g) = 300²/1600 = 56.25,在 t = 0.375

    let err = (max_z - 56.25).abs();
    println!("Error: {:.4}", err);
    assert!(err < 1.0, "Max z should be ~56.25");
}
```

**每行解释**:
- `z_velocity -= GRAVITY * dt`:重力是负方向(向下)
- `z < 0.0` 落地检测,clamp 到 0
- 抛物线物理:max z = v² / (2g) = 300² / (2*800) = 56.25
- 数值积分有小误差,Euler 法精度 O(dt),dt=0.01 误差约 0.1%

## 8 · Rust / Arch 落地代码

### 完整可跑:Z 跳跃 + 阴影 + 视差

```rust
// Cargo.toml:
// [dependencies]
// minifb = "0.27"

use minifb::{Key, KeyRepeat, Window, WindowOptions};
use std::time::Instant;

const WIDTH: usize = 800;
const HEIGHT: usize = 600;
const GRAVITY: f32 = 800.0;
const JUMP_VELOCITY: f32 = 350.0;
const PLAYER_SPEED: f32 = 200.0;

#[derive(Clone, Copy, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
}

struct Player {
    pos: Vec2,
    z: f32,
    z_velocity: f32,
}

impl Player {
    fn new(pos: Vec2) -> Self {
        Self { pos, z: 0.0, z_velocity: 0.0 }
    }

    fn update(&mut self, dt: f32, window: &minifb::Window) {
        // X/Y 移动
        let mut dx = 0.0;
        let mut dy = 0.0;
        if window.is_key_down(Key::A) { dx -= 1.0; }
        if window.is_key_down(Key::D) { dx += 1.0; }
        if window.is_key_down(Key::W) { dy -= 1.0; }
        if window.is_key_down(Key::S) { dy += 1.0; }
        let len = (dx*dx + dy*dy).sqrt();
        if len > 0.0 {
            self.pos.x += (dx / len) * PLAYER_SPEED * dt;
            self.pos.y += (dy / len) * PLAYER_SPEED * dt;
        }

        // Z 物理(跳跃)
        self.z += self.z_velocity * dt;
        self.z_velocity -= GRAVITY * dt;
        if self.z < 0.0 {
            self.z = 0.0;
            self.z_velocity = 0.0;
        }
    }

    fn jump(&mut self) {
        if self.z == 0.0 {
            self.z_velocity = JUMP_VELOCITY;
        }
    }
}

struct Obstacle {
    pos: Vec2,
    size: f32,
    color: u32,
    is_water: bool,  // 水坑(z>0 才能跨过)
}

fn draw_rect(buf: &mut [u32], buf_w: usize, buf_h: usize, x: i32, y: i32, w: i32, h: i32, color: u32) {
    for py in y.max(0)..(y + h).min(buf_h as i32) {
        for px in x.max(0)..(x + w).min(buf_w as i32) {
            buf[(py as usize) * buf_w + (px as usize)] = color;
        }
    }
}

fn draw_shadow(buf: &mut [u32], buf_w: usize, buf_h: usize, x: i32, y: i32, size: i32, opacity: u32) {
    // 椭圆阴影(简化为矩形)
    let half = size / 2;
    let alpha = opacity;  // 0-255
    for py in (y - half/2).max(0)..(y + half/2).min(buf_h as i32) {
        for px in (x - half).max(0)..(x + half).min(buf_w as i32) {
            let idx = (py as usize) * buf_w + (px as usize);
            // 简化:直接覆盖颜色(实际应该 blend)
            let original = buf[idx];
            let r = ((original >> 16) & 0xFF) * (255 - alpha) / 255;
            let g = ((original >> 8) & 0xFF) * (255 - alpha) / 255;
            let b = (original & 0xFF) * (255 - alpha) / 255;
            buf[idx] = (r << 16) | (g << 8) | b;
        }
    }
}

fn main() {
    let mut window = Window::new(
        "Z Movement Demo", WIDTH, HEIGHT,
        WindowOptions::default(),
    ).expect("Failed to open window");

    let mut buffer = vec![0u32; WIDTH * HEIGHT];
    let mut last_time = Instant::now();
    let mut total_time = 0.0_f32;

    let mut player = Player::new(Vec2::new(WIDTH as f32 / 2.0, HEIGHT as f32 / 2.0));

    // 几个障碍物
    let obstacles = vec![
        Obstacle { pos: Vec2::new(300.0, 300.0), size: 60.0, color: 0xFF0000A0, is_water: true },
        Obstacle { pos: Vec2::new(500.0, 400.0), size: 80.0, color: 0xFF000080, is_water: true },
        Obstacle { pos: Vec2::new(200.0, 450.0), size: 40.0, color: 0xFF604040, is_water: false },
    ];

    while window.is_open() && !window.is_key_down(Key::Escape) {
        let now = Instant::now();
        let dt = now.duration_since(last_time).as_secs_f32().min(0.05);
        last_time = now;
        total_time += dt;

        // 输入
        if window.is_key_pressed(Key::Space, KeyRepeat::No) {
            player.jump();
        }

        // 更新
        player.update(dt, &window);
        player.pos.x = player.pos.x.max(20.0).min((WIDTH - 20) as f32);
        player.pos.y = player.pos.y.max(20.0).min((HEIGHT - 20) as f32);

        // 渲染
        for px in buffer.iter_mut() { *px = 0xFF101010; }

        // 画障碍物(水面有动画)
        for obs in &obstacles {
            let color = if obs.is_water {
                // 水面有波动
                let wave = (total_time * 3.0 + obs.pos.x * 0.01).sin() * 0x20;
                let base = 0xA0u32;
                let v = base.saturating_add(wave as u32);
                0xFF000000 | (v << 16) | 0x40  // 偏蓝
            } else {
                obs.color
            };
            draw_rect(&mut buffer, WIDTH, HEIGHT,
                      (obs.pos.x - obs.size/2.0) as i32,
                      (obs.pos.y - obs.size/2.0) as i32,
                      obs.size as i32, obs.size as i32, color);
        }

        // 画玩家阴影(地面位置,根据 z 减小不透明度)
        let shadow_opacity = (255.0 - player.z * 2.0).max(50.0) as u32;
        draw_shadow(&mut buffer, WIDTH, HEIGHT,
                    player.pos.x as i32, player.pos.y as i32,
                    24, shadow_opacity);

        // 画玩家精灵(ground_pos.y - z 偏移)
        let sprite_y = player.pos.y - player.z;
        let scale = 1.0 + player.z * 0.005;
        let size = (16.0 * scale) as i32;

        // 身体
        draw_rect(&mut buffer, WIDTH, HEIGHT,
                  (player.pos.x - size as f32 / 2.0) as i32,
                  (sprite_y - size as f32 / 2.0) as i32,
                  size, size, 0xFFFF6040);

        // 眼睛
        draw_rect(&mut buffer, WIDTH, HEIGHT,
                  (player.pos.x - size as f32 / 4.0) as i32,
                  (sprite_y - size as f32 / 4.0) as i32,
                  3, 3, 0xFFFFFFFF);
        draw_rect(&mut buffer, WIDTH, HEIGHT,
                  (player.pos.x + size as f32 / 8.0) as i32,
                  (sprite_y - size as f32 / 4.0) as i32,
                  3, 3, 0xFFFFFFFF);

        // HUD:显示 Z
        let z_label_color = if player.z > 0.0 { 0xFFFFFF40 } else { 0xFF404040 };
        draw_rect(&mut buffer, WIDTH, HEIGHT, 10, 10, 100, 20, z_label_color);

        window.update_with_buffer(&buffer, WIDTH, HEIGHT).unwrap();
    }
}
```

**关键 Rust 特性解释**:
- `jump()` 只在 z==0(地面)时生效,防止空中二段跳
- 阴影 opacity 随 z 减小(z 高时阴影淡)
- 精灵按 z 缩放(z 高时精灵稍大,模拟"靠近相机")
- 水面颜色随时间正弦变化(简单波动效果)
- 阴影画在地面位置,精灵画在 `ground_y - z`(z 越大越往上)

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 历史脉络与工业实践

1990 年代 id Software 的 Doom(1993)用 BSP tree + painter's algorithm——排序在编译期完成,运行时 O(N) 遍历。Quake(1996)首次用 Z-buffer(GPU 硬件),彻底解决排序问题。

2D 游戏排序的演化:

- **1985-1990**:无 sort,固定 layer(Super Mario Bros)
- **1990-1995**:Y-sort 在 JRPG 普及(最终幻想 6、超时空之轮)
- **1995-2005**:Multi-layer Y-sort(星际争霸、暗黑破坏神 2)
- **2005-2015**:引擎内置 sort(Unity、GameMaker)
- **2015-2025**:GPU + sort 混合(bevy、Unreal)

Casey 的 HH 在 day 295-310 走了这条 30 年路径——从最简单的 sort_key 到拓扑排序,演示每一阶段的工程权衡。

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。
