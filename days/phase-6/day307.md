## 2 · 心智模型

### 2.1 类比:派对上的人群

把 sprite 想象成派对上的人。"遮挡关系"对应"人和人说话"——A 和 B 说话(B 站在 A 后面),他们在一组;C 和 D 说话,他们在另一组;E 站在角落不和任何人说话,他单独一组。

派对结束后,人群**自然分成几个连通分量**——同组的人通过对话链互相可达,不同组之间没人说过话。

数学定义:**图中两节点 u, v 在同一连通分量 ⟺ 存在 u 到 v 的路径(忽略边的方向)**。

对于**有向图**(如遮挡图,有方向 A 遮挡 B ≠ B 遮挡 A),要分**强连通分量(SCC)**和**弱连通分量(WCC)**:

- **SCC**:u 到 v 有路径,**且** v 到 u 也有路径。意味着 u, v 在一个环里。
- **WCC**:把所有边当无向,看 u, v 是否连通。弱连通即可。

**HH 用哪个**?

游戏 sprite 的遮挡图通常**没有环**——如果 A 在 B 前面(bottom_y_A > bottom_y_B),那么 B 不可能也在 A 前面(bottom_y_B > bottom_y_A 矛盾)。所以 HH 的图是无环有向图(DAG)。在 DAG 里,**WCC = SCC**(没环,SCC 都是单点),所以用 WCC 就够。

如果出现环,说明**游戏逻辑有 bug**(比如两个 sprite 互相遮挡,可能是 Y 坐标算错)。Day 308 专门处理这种异常。

### 2.2 DFS 找连通分量(完整代码 + 逐行注释)

```rust
/// 找无向图的所有连通分量。
/// 输入:无向图(用邻接表表示)
/// 输出:Vec<Vec<usize>>,每个内层 Vec 是一个连通分量的节点列表
fn connected_components(g: &Graph) -> Vec<Vec<usize>> {
    let n = g.n;
    let mut visited = vec![false; n];   // 标记数组,避免重复访问
    let mut components = vec![];

    for start in 0..n {
        if visited[start] {
            continue;  // 已在其他分量里,跳过
        }
        // 从 start 开始一个新分量,DFS
        let mut comp = vec![];
        let mut stack = vec![start];

        while let Some(node) = stack.pop() {
            if visited[node] {
                continue;  // 可能多次 push,跳过已访问
            }
            visited[node] = true;
            comp.push(node);

            // 把所有未访问邻居加入 stack
            for &next in &g.adj[node] {
                if !visited[next] {
                    stack.push(next);
                }
            }
        }
        components.push(comp);
    }

    components
}
```

**复杂度**:O(V+E)。每个节点访问一次,每条边遍历一次。

**为什么用栈不用递归**?Rust 默认栈 8 MB,每帧递归调用占几百字节。10000 sprite 最深递归 10000 层 = 8 MB,刚好爆。栈版本用堆内存,不受栈大小限制。

**有向图的处理**:

HH 的遮挡图是有向的(A 在 B 前 → 边 A→B)。要找弱连通分量,需要**同时遍历出边和入边**:

```rust
fn weakly_connected_components(g: &DirectedGraph) -> Vec<Vec<usize>> {
    let n = g.n;
    let mut visited = vec![false; n];
    let mut components = vec![];

    for start in 0..n {
        if visited[start] { continue; }
        let mut comp = vec![];
        let mut stack = vec![start];
        while let Some(node) = stack.pop() {
            if visited[node] { continue; }
            visited[node] = true;
            comp.push(node);
            // 出边:node → next(node 在 next 前面)
            for &next in &g.adj_out[node] {
                if !visited[next] { stack.push(next); }
            }
            // 入边:prev → node(prev 在 node 前面)
            // 把入边也当作无向边,反向走
            for &prev in &g.adj_in[node] {
                if !visited[prev] { stack.push(prev); }
            }
        }
        components.push(comp);
    }
    components
}
```

需要同时存 `adj_out` 和 `adj_in` 两个邻接表。或扫描所有边找入边(O(E) 每节点,慢)。

### 2.3 并查集(Union-Find):另一种思路

并查集是另一种找连通分量的方法,适合**动态加边**的场景(边一条条加进来,实时查询连通性)。

```rust
/// 并查集:用路径压缩 + 按 rank 合并,平均 O(α(n)) ≈ O(1) per op
struct UnionFind {
    parent: Vec<usize>,  // parent[i] = i 的父节点
    rank: Vec<u32>,      // rank[i] = 以 i 为根的树的高度上限
}

impl UnionFind {
    fn new(n: usize) -> Self {
        Self {
            parent: (0..n).collect(),  // 初始每个节点是自己的根
            rank: vec![0; n],
        }
    }

    /// find:找 x 的根(所在分量的代表),路径压缩
    fn find(&mut self, x: usize) -> usize {
        if self.parent[x] != x {
            // 路径压缩:把 x 直接指向根,下次 O(1)
            self.parent[x] = self.find(self.parent[x]);
        }
        self.parent[x]
    }

    /// union:把 x 和 y 所在分量合并
    fn union(&mut self, x: usize, y: usize) {
        let rx = self.find(x);
        let ry = self.find(y);
        if rx == ry {
            return;  // 已在同一分量
        }
        // 按 rank 合并:小树挂到大树下,避免退化成链
        if self.rank[rx] < self.rank[ry] {
            self.parent[rx] = ry;
        } else if self.rank[rx] > self.rank[ry] {
            self.parent[ry] = rx;
        } else {
            // rank 相等,任选一个当根,根的 rank + 1
            self.parent[ry] = rx;
            self.rank[rx] += 1;
        }
    }
}

fn components_uf(g: &Graph) -> Vec<Vec<usize>> {
    let n = g.n;
    let mut uf = UnionFind::new(n);
    // 把每条边的两端 union
    for i in 0..n {
        for &j in &g.adj[i] {
            uf.union(i, j);
        }
    }
    // 收集每个根下的所有节点
    let mut comps: Vec<Vec<usize>> = vec![vec![]; n];
    for i in 0..n {
        let root = uf.find(i);
        comps[root].push(i);
    }
    // 过滤掉空的(没成为任何节点根的位置)
    comps.into_iter().filter(|c| !c.is_empty()).collect()
}
```

**两个优化**:

- **路径压缩(path compression)**:find 时把节点直接指向根,下次 O(1)。让树扁平化。
- **按 rank 合并(union by rank)**:小树挂大树下,避免树退化成链表(链表 find 是 O(n))。

加上这两个优化,均摊每次操作 O(α(n)),α 是反 Ackermann 函数,**对所有实际输入 ≤ 4**(比 log log log n 还小)。**实用上等于 O(1)**。

**DFS vs Union-Find 何时选**:

| | DFS | Union-Find |
|---|---|---|
| 静态图(已知所有边) | 简单,O(V+E) | 也行,但要先 union 所有边 |
| 动态图(边一条条加) | 每次加边要重新算 O(V+E) | 每次 union O(1),实时查询 |
| 实现复杂度 | 简单 | 中等(两个优化要写对) |
| 内存 | visited 数组 | parent + rank 数组(2x) |

HH 是静态图(每帧重新构图),用 DFS 简单。如果做实时交互(玩家拖 sprite 实时更新遮挡),Union-Find 更合适。

### 2.5 验证拓扑排序:用分量自动检查

有了分量,你能**自动验证拓扑排序的正确性**:

```rust
/// 验证拓扑排序在每个分量内是否正确。
/// 正确 = 同分量内,如果 a → b 有边,那么 order[a] < order[b]
fn validate_topo_order(
    order: &[usize],          // 拓扑排序结果
    components: &[Vec<usize>],
    graph: &DirectedGraph,
) -> bool {
    // 构建"节点 → 在 order 中的位置"映射,O(N)
    let mut position = vec![0usize; graph.n];
    for (i, &node) in order.iter().enumerate() {
        position[node] = i;
    }

    // 检查每条边 u → v:position[u] < position[v]
    for u in 0..graph.n {
        for &v in &graph.adj_out[u] {
            if position[u] >= position[v] {
                // u 应该在 v 前面,但实际在后面——错误
                return false;
            }
        }
    }
    true
}
```

注意这个验证**不需要 components**——只要检查所有边的顺序即可。但用 components 概念能帮你**理解错误范围**:

- 如果验证失败,看具体哪条边错了
- 那条边所在的分量就是"出错区域"
- 其他分量可能是对的,只要修出错分量

这种"局部化错误"的思维对调试非常有用。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的"组"概念比比皆是,每个领域都有自己的"连通分量":

**Render batches**:同 material(同 shader + 同 texture)的 sprite 一组,GPU 一次 draw call 画完。这是 GPU 渲染的核心优化——每次 draw call 有 ~10μs 的 CPU-GPU 同步开销,1000 sprite 单独画 = 10ms,完全没法 60 FPS。Batch 后 1000 sprite 一个 draw call,只要 0.1ms。

**Spatial partitions**:同空间区域的 entity 一组。Quadtree / BSP / grid 把世界分成 cell,查询"我附近的敌人"只看当前 cell,而不是扫描全部 entity。Casey 在 Day 309+ 会处理 grid partitioning。

**Network replication**:同 network region 的 entity 一组。MMO 服务器把世界分成 zone,玩家在 zone A 不收 zone B 的更新,减少带宽。

**Physics islands**:同 collision graph 的物体一组。Box2D / PhysX 用 island sleeping——一个 island 内所有物体都静止时,整个 island 跳过物理积分,大幅省 CPU。这正是连通分量的物理应用。

**AI behavior groups**:同 squad 的 NPC 一组。战略游戏里 12 个步兵组成一个 squad,squad 内共享感知(看见敌人互相通报),squad 间独立行动。这种"squad"概念就是连通分量的 AI 应用。

Casey 今天用连通分量可视化 sprite 排序,但**概念相通——分而治之**,处理 N 个小组比处理一个 N 倍大的组更高效。这是计算科学的通用原则。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核到处是"连通分量"的应用:

**cgroup**(control group):进程分组,资源隔离。Docker / Kubernetes 用 cgroup 限制每个容器的 CPU / memory。
```bash
# 看自己所在 cgroup
cat /proc/self/cgroup
# 输出:0::/user.slice/user-1000.slice/session-1.scope

# 看所有 cgroup
systemd-cgls
# 树状显示所有 cgroup 及其进程

# 看某进程的 cgroup 限制
cat /sys/fs/cgroup/user.slice/cpu.max
# 输出:max max  ← 不限制
```

**namespace**:进程的"视图"分组。同 namespace 的进程看到相同的资源(网络、PID、mount),不同 namespace 隔离。Docker 每个容器有自己的 namespace。

**process tree**:同 parent 的进程一组。`pstree` 命令可视化:
```bash
pstree -p $$  # 当前 shell 的进程树
# 输出类似:
# zsh(1234)───vim(5678)───{vim}(5679)
```

**CPU scheduling domains**:Linux SMP 调度器把 CPU 核心分组(domain),同 domain 内迁移进程代价小(cache 还热),跨 domain 代价大(NUMA)。`lscpu` 显示 domain:
```bash
lscpu | grep -i numa
# NUMA node(s): 2
# NUMA node0 CPU(s): 0-7
# NUMA node1 CPU(s): 8-15
```

cgroup / namespace / process tree / scheduling domain 都是"连通分量"概念在 OS 层的应用——把全局问题局部化。

### 3.4 · 🎨 图形学视角

图形学的"分量"对应 **draw call batching**——同 material 的物体一组,一次 draw call 画完。GPU 状态切换昂贵(set shader、bind texture、set uniform 都要几十到几百 cycle),batching 是性能优化核心。

具体例子:假设你画 1000 个 sprite,每个用不同 texture。每个 sprite 一次 draw call,1000 次 texture bind,每次 100μs GPU 同步,共 100ms——**远超 60 FPS 的 16ms 预算**。

优化:把所有 sprite 的 texture 合并成 atlas(大 texture),所有 sprite 共享 material。一次 draw call 画 1000 sprite,~0.5ms。**性能提升 200 倍**。

**OpenGL 里的 batching**:

```glsl
// 用 instancing,一次 draw call 画 N 个 sprite
// OpenGL 3.3+ 的 glDrawArraysInstanced
glDrawArraysInstanced(GL_TRIANGLES, 0, 6, 1000);
// 6 个顶点(两个三角形组成一个 quad),1000 个实例
```

每个实例的 transform / color 通过 instanced attribute 传:

```glsl
// vertex shader
in vec2 position;       // 普通 attribute(每顶点)
in mat4 instance_mvp;   // instanced attribute(每实例一次)
in vec4 instance_color;

void main() {
    gl_Position = instance_mvp * vec4(position, 0.0, 1.0);
    vertex_color = instance_color;
}
```

今天的"连通分量"是 batching 的概念基础。同分量内 sprite 顺序有关,但**分量间** sprite 顺序无关——可以**任意重组**,合并到一次 draw call。Casey 在 Phase 8 切 OpenGL 后会用这个观察做 GPU batching。

**Z-buffering vs sorting**:另一种渲染 sprite 的方法是不排序,用 Z-buffer 让 GPU 自动遮挡。但 Z-buffer 不能处理半透明(透明物体之间需要正确混合顺序),所以 alpha sprite 仍要 CPU 排序。今天的连通分量概念对透明排序同样有用——分量间可任意顺序,分量内严格排序。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **连通分量(connected component)** — 图论基础概念。图论是离散数学分支,处理"节点 + 边"的结构。
- **分而治之(divide and conquer)** — 算法设计原则。把大问题拆成独立小问题,逐个击破。
- **动态连通性(dynamic connectivity)** — 并查集解决的问题。判断"两个节点是否连通",边可以动态加。
- **可视化验证(visual verification)** — 调试方法论。把抽象画成视觉,bug 显形。

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 复杂度 | 本项目选了哪个 |
|---|---|---|---|---|
| DFS 连通分量 | 静态图 | 一次构图一次查询 | O(V+E) | ✅ 今天 |
| BFS 连通分量 | 同 DFS,queue 替 stack | 同上 | O(V+E) | 也可以 |
| Union-Find | 动态加边 | 流式加边,实时查询 | 平均 O(α(n)) | 不用 |
| Tarjan SCC | 找强连通分量(有环) | 复杂有向图 | O(V+E) | day 308+ |
| Kosaraju SCC | 另一种 SCC | 同上 | O(V+E) | 不用 |

### 4.3 下级(内部零件)

- **visited 数组** — DFS 的标记,避免重复访问
- **stack 遍历** — 显式栈替代递归,避免爆栈
- **path compression** — Union-Find 的优化,均摊 O(1)
- **union by rank** — Union-Find 的优化,避免退化链表
- **adjacency list** — 邻接表表示图,O(V+E) 遍历
- **按分量上色** — 可视化的具体实现

## 5 · 对照与变奏

### 5.1 连通分量的跨领域应用

| 场景 | 用途 | 算法 |
|---|---|---|
| 社交网络 | 找"朋友圈"(friend circles) | DFS / UF |
| 图像处理 | 找连通区域(blobs) | BFS / 2-pass |
| 编译器 | 死代码检测 + 强连通分量循环 | Tarjan SCC |
| 网络 | 找网络分区(autonomous systems) | DFS |
| 数据库 | 找关系链(reachability query) | DFS / UF |
| HH(今天) | sprite 独立组,验证拓扑排序 | DFS |

连通分量是**通用图算法**——任何"哪些节点相关"的问题都可能用到它。

### 5.2 历史演化

- **1970s**:Tarjan 发明线性时间 SCC 算法(O(V+E)),图论算法黄金时代。
- **1980s**:并查集的路径压缩 + 按 rank 合并被严格证明 O(α(n))。
- **1990s**:分布式连通性算法——大规模图(Pregel / MapReduce)。
- **2010s**:图数据库(Neo4j、ArangoDB)把图算法工业化。
- **2020s**:GPU 加速图算法(Gunrock、CuGraph)。Twitch / Twitter 实时分析。

### 5.3 数据结构选择:邻接表 vs 邻接矩阵

| | 邻接表 | 邻接矩阵 |
|---|---|---|
| 空间 | O(V+E) | O(V²) |
| 查"u 和 v 是否相邻" | O(degree(u)) | O(1) |
| 遍历邻居 | O(degree(u)) | O(V) |
| 适合 | 稀疏图(E ≈ V) | 稠密图(E ≈ V²) |
| HH sprite 图 | ✅ 稀疏 | ❌ 大多数 sprite 不重叠 |

HH sprite 遮挡图是稀疏的(平均每 sprite 和 2-3 个其他 sprite 重叠),邻接表更合适。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:为什么 HH 用"弱连通分量(WCC)"而非"强连通分量(SCC)"?

**参考解答**:

HH 的遮挡图通常**没有环**——如果 A 在 B 前面(`bottom_y_A > bottom_y_B`),那么 B 不可能也在 A 前面(`bottom_y_B > bottom_y_A` 矛盾)。所以遮挡图是 DAG(Directed Acyclic Graph)。

在 DAG 里:
- **SCC**:每个 SCC 只有一个节点(没有环,无法形成多节点 SCC)
- **WCC**:可能有多个节点的 WCC(忽略方向时连通)

所以 HH 用 WCC 就够——SCC 在 DAG 上是退化的(全单点)。如果出现 SCC 多节点,说明**有环**,即 bug——Day 308 专门检测这种情况。

**WCC 实现也更简单**——只需要 DFS 遍历出边和入边,不需要 Tarjan 那种两次 DFS 的复杂算法。

### Lv2 · 动手实践

**题**:实现 DFS 连通分量,测试 6 个 sprite 分成 2 个分量。

完成标准:输出分量列表,每组 3 个 sprite,assert 通过。

**完整可跑代码**:

```rust
#[derive(Debug)]
struct Graph {
    n: usize,
    adj: Vec<Vec<usize>>,  // 无向图,邻接表
}

impl Graph {
    fn new(n: usize) -> Self {
        Self { n, adj: vec![vec![]; n] }
    }

    fn add_undirected(&mut self, a: usize, b: usize) {
        self.adj[a].push(b);
        self.adj[b].push(a);
    }
}

fn connected_components(g: &Graph) -> Vec<Vec<usize>> {
    let mut visited = vec![false; g.n];
    let mut comps = vec![];

    for start in 0..g.n {
        if visited[start] { continue; }

        let mut comp = vec![];
        let mut stack = vec![start];

        while let Some(node) = stack.pop() {
            if visited[node] { continue; }
            visited[node] = true;
            comp.push(node);
            for &next in &g.adj[node] {
                if !visited[next] { stack.push(next); }
            }
        }
        comps.push(comp);
    }
    comps
}

fn main() {
    // 6 个节点,两组:
    // Group A: 0-1-2(三角连接)
    // Group B: 3-4-5(三角连接)
    let mut g = Graph::new(6);
    g.add_undirected(0, 1);
    g.add_undirected(1, 2);
    g.add_undirected(0, 2);
    g.add_undirected(3, 4);
    g.add_undirected(4, 5);
    g.add_undirected(3, 5);

    let comps = connected_components(&g);
    for (i, comp) in comps.iter().enumerate() {
        println!("Component {}: {:?}", i, comp);
    }
    assert_eq!(comps.len(), 2);
    println!("Connected components test passed!");
}
```

**每行解释**:

- `add_undirected(a, b)` — 同时加 a→b 和 b→a,模拟无向图。
- `visited` — bool 数组,标记每个节点是否已访问。开始全 false。
- 外层 `for start in 0..n` — 尝试每个节点作为分量起点。
- `if visited[start] { continue; }` — 已访问说明在之前的分量里,跳过。
- 内层 DFS — 从 start 出发,stack 推进,pop 一个访问,把邻居 push。
- `if visited[node] { continue; }` — 同一节点可能多次 push(多个邻居都推它),跳过已访问。
- 每次 stack 空了,说明这个分量遍历完,加入 `comps`。

### 8.1 完整可视化 demo

把今天的概念做成一个完整可跑 demo:模拟 sprite 排序 + 连通分量 + 可视化。

```rust
use std::collections::HashSet;

#[derive(Debug, Clone)]
struct Rect {
    x: f32, y: f32, w: f32, h: f32,
}

impl Rect {
    fn overlaps(&self, other: &Rect) -> bool {
        self.x < other.x + other.w
            && self.x + self.w > other.x
            && self.y < other.y + other.h
            && self.y + self.h > other.y
    }
}

#[derive(Debug)]
struct Sprite {
    name: String,
    bounds: Rect,
}

/// 构建遮挡图:重叠的 sprite 互相有边
fn build_overlap_graph(sprites: &[Sprite]) -> Vec<Vec<usize>> {
    let n = sprites.len();
    let mut adj = vec![vec![]; n];
    for i in 0..n {
        for j in (i + 1)..n {
            if sprites[i].bounds.overlaps(&sprites[j].bounds) {
                adj[i].push(j);
                adj[j].push(i);
            }
        }
    }
    adj
}

/// DFS 找连通分量
fn connected_components(n: usize, adj: &[Vec<usize>]) -> Vec<Vec<usize>> {
    let mut visited = vec![false; n];
    let mut comps = vec![];

    for start in 0..n {
        if visited[start] { continue; }
        let mut comp = vec![];
        let mut stack = vec![start];
        while let Some(node) = stack.pop() {
            if visited[node] { continue; }
            visited[node] = true;
            comp.push(node);
            for &next in &adj[node] {
                if !visited[next] { stack.push(next); }
            }
        }
        comps.push(comp);
    }
    comps
}

/// 可视化:文本输出,用字母 A B C... 标记分量
fn visualize_components(sprites: &[Sprite], comps: &[Vec<usize>]) {
    let symbols = ['A', 'B', 'C', 'D', 'E', 'F', 'G', 'H'];
    println!("\n=== Sprite groups ===");
    for (i, comp) in comps.iter().enumerate() {
        let sym = symbols[i % symbols.len()];
        println!("Group {} ({} sprites):", sym, comp.len());
        for &idx in comp {
            println!("  - {} at ({:.0}, {:.0})",
                sprites[idx].name,
                sprites[idx].bounds.x,
                sprites[idx].bounds.y);
        }
    }
}

fn main() {
    let sprites = vec![
        Sprite { name: "tree1".into(),  bounds: Rect { x: 0.0,   y: 0.0,  w: 50.0, h: 50.0 } },
        Sprite { name: "tree2".into(),  bounds: Rect { x: 30.0,  y: 0.0,  w: 50.0, h: 50.0 } },  // overlaps tree1
        Sprite { name: "rock1".into(),  bounds: Rect { x: 15.0,  y: 30.0, w: 30.0, h: 30.0 } },  // overlaps tree1, tree2
        Sprite { name: "hero".into(),   bounds: Rect { x: 500.0, y: 0.0,  w: 32.0, h: 48.0 } },
        Sprite { name: "enemy".into(),  bounds: Rect { x: 520.0, y: 0.0,  w: 32.0, h: 48.0 } },  // overlaps hero
        Sprite { name: "cloud".into(),  bounds: Rect { x: 800.0, y: 0.0,  w: 100.0, h: 40.0 } }, // 独立
    ];

    let adj = build_overlap_graph(&sprites);
    let comps = connected_components(sprites.len(), &adj);

    println!("Total sprites: {}", sprites.len());
    println!("Connected components: {}", comps.len());

    visualize_components(&sprites, &comps);

    // 验证:tree1/2/rock1 应在一组,hero/enemy 一组,cloud 独立
    assert_eq!(comps.len(), 3);
    println!("\nAll assertions passed!");
}
```
