
# Day 325 · 票据互斥锁

> 昨天 Casey 用了标准库的 Mutex 做异步加载。今天他从零实现一个"票据锁(ticket mutex)"——一种保证公平的互斥锁,每个等待者按到达顺序获得锁,避免某些线程饿死。

## 0 · 为什么要有这一天

到目前为止你用过的锁大概是 `std::sync::Mutex`(Rust)或 `pthread_mutex`(C)。这些是"黑盒"——你不知道内部怎么实现,只知道"加锁、解锁"。

但游戏开发里锁的性能和公平性很重要。考虑这个场景:8 个线程同时竞争一个锁,如果用"普通自旋锁",可能出现**线程饿死(starvation)**——某个线程运气差永远抢不到锁。

业界设计了多种锁保证不同特性:

1. **自旋锁(spinlock)**:忙等,不睡眠。快但不公平。
2. **互斥锁(mutex)**:不能获锁时睡眠,OS 调度。公平性取决于 OS。
3. **票据锁(ticket lock)**:每个等待者取号,按号顺序获锁。完全公平。
4. **MCS 锁**:每个等待者 spinning 在自己的 cache line 上,cache 友好。

今天 Casey 从零实现**票据锁**——最直观的"公平锁"。它的工作方式像面包店排队:

1. 进店取号(原子 +1)
2. 等待叫号(轮询自己的号是否到)
3. 当前号处理完,叫下一个号(原子 +1)

```
ticket_lock:
    lock:
        my_ticket = atomic_fetch_add(next_ticket, 1)  // 取号
        while atomic_load(now_serving) != my_ticket:  // 等叫号
            cpu_relax()  // 提示 CPU "我在等,降低功耗"
    
    unlock:
        atomic_fetch_add(now_serving, 1)  // 叫下一个号
```

两个原子变量:`next_ticket`(下个新取的号)和 `now_serving`(当前服务的号)。新来的取号递增,服务的号解锁后递增。等待者轮询自己的号 == now_serving。

这种锁的关键特性:**完全 FIFO 公平**。先到的线程先获锁,不存在饿死。代价是性能比 MCS 略差(所有等待者轮询同一个 `now_serving`,cache 抖动),但比朴素自旋锁好得多。

心理锚点:今天之后你理解"锁的本质"——它就是一个原子变量加轮询。Rust `std::sync::Mutex` 内部更复杂(用 futex 系统调用避免忙等),但概念上和今天的票据锁一样。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_thread.cpp`(自写线程库),实现了 ticket mutex。

具体动作:

1. 定义 `ticket_mutex` 结构,包含 `next_ticket` 和 `now_serving` 两个 atomic
2. 实现 `ticket_lock`:原子取号 + 自旋等号
3. 实现 `ticket_unlock`:原子递增 now_serving
4. 测试:多线程同时 lock/unlock,验证 FIFO 顺序

Casey 的 C 实现:

```c
typedef struct {
    atomic_uint64 next_ticket;
    atomic_uint64 now_serving;
} ticket_mutex;

void ticket_lock(ticket_mutex *m) {
    uint64 my_ticket = atomic_fetch_add(&m->next_ticket, 1);
    while (atomic_load(&m->now_serving) != my_ticket) {
        _mm_pause();  // x86 pause 指令,降低功耗
    }
}

void ticket_unlock(ticket_mutex *m) {
    atomic_fetch_add(&m->now_serving, 1);
}
```

Casey 在视频里讨论了几个关键细节:

1. **`_mm_pause()`** vs `_mm_yield()`:pause 是 CPU 提示(降低流水线功耗),不调度;yield 是 OS 提示(让出 CPU 给其他线程)。pause 更快但不公平,yield 更公平但慢。Casey 选 pause(优先性能)。
2. **memory order**:`atomic_load` 默认 `memory_order_seq_cst`(最强屏障),性能差。改成 `memory_order_acquire`(读屏障),足够保证可见性。Casey 在 Rust 翻译用 acquire/release。
3. **backoff**:如果自旋很多次还没拿到锁,可以"短暂 sleep"省 CPU。但 Casey 简化为无 backoff,游戏里临界区短(微秒级),自旋足够。

Casey 还对比了 ticket mutex 和 `std::sync::Mutex`:

- ticket mutex:**公平**,但**自旋**(忙等)
- std::sync::Mutex:不保证公平,但**睡眠**(让出 CPU)

游戏里临界区短(微秒),自旋更快(无 syscall)。系统编程里临界区长(毫秒),睡眠更省 CPU。

## 2 · 心智模型

### 类比:面包店排队

把票据锁想象成面包店排队买面包。

```
进门取号:[1] [2] [3] [4] [5]
柜台叫号:now_serving = 3

号 1, 2:已经买完走了
号 3:正在买
号 4, 5:等待,盯着"叫号"显示
```

每个新进来的人取一个递增的号。柜台每服务完一个人,叫下一个号。等待者**只看显示牌上的号**——如果叫到自己的号,就上前买。

这种"取号 + 叫号"机制保证完全 FIFO:号小的人先买,不存在"号大的人挤前面"(饿死号小的人)。

### 严谨原理:原子操作

票据锁的核心是**原子操作**——CPU 保证操作"不可分割"。

```rust
use std::sync::atomic::{AtomicU64, Ordering};

let next_ticket = AtomicU64::new(0);
let my_ticket = next_ticket.fetch_add(1, Ordering::Relaxed);
// fetch_add 是"读旧值 + 加 1"的原子操作
// 返回值是加之前的旧值(我的号)
```

`Ordering` 控制"内存屏障"的强度:

- `Relaxed`:无屏障,只保证操作本身原子。用于"我只关心这个变量"。
- `Acquire`(读):本线程之后的读写不能重排到此操作之前。用于"读取后我要用"。
- `Release`(写):本线程之前的读写不能重排到此操作之后。用于"我写完了,别人可见"。
- `AcqRel`(读写):Acquire + Release,用于 RMW 操作。
- `SeqCst`:最强,全局顺序,但性能最差。

票据锁:

- `fetch_add(next_ticket, Relaxed)`:只关心自己的号,不需要屏障
- `load(now_serving, Acquire)`:读后要用(决定是否获锁),需要 Acquire 屏障
- `fetch_add(now_serving, Release)`:写后别人能看到,需要 Release 屏障

### 自旋 vs 睡眠

票据锁是"自旋锁"——不获锁时忙等(`while ... {}`),不让出 CPU。优点:

- **快**:无 syscall,纳秒级响应
- **简单**:几行代码

缺点:

- **浪费 CPU**:等待时占满一个核
- **不适合长临界区**:CPU 时间浪费严重

`std::sync::Mutex` 是"睡眠锁"——不获锁时调用 `futex`(Linux)或类似 syscall 让 OS 调度。优点:

- **省 CPU**:等待时不占核
- **适合长临界区**

缺点:

- **慢**:syscall 几微秒,临界区短时反而慢

游戏里临界区通常微秒级(更新几个 entity),自旋锁更快。系统编程里临界区毫秒级(磁盘 IO、网络),睡眠锁更合适。

### Rust 实现

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::hint::spin_loop;

pub struct TicketMutex {
    next_ticket: AtomicU64,
    now_serving: AtomicU64,
}

impl TicketMutex {
    pub const fn new() -> Self {
        Self {
            next_ticket: AtomicU64::new(0),
            now_serving: AtomicU64::new(0),
        }
    }
    
    pub fn lock(&self) -> TicketGuard {
        let my_ticket = self.next_ticket.fetch_add(1, Ordering::Relaxed);
        while self.now_serving.load(Ordering::Acquire) != my_ticket {
            spin_loop();  // x86 编译成 _mm_pause
        }
        TicketGuard { mutex: self }
    }
    
    pub fn unlock(&self) {
        self.now_serving.fetch_add(1, Ordering::Release);
    }
}

pub struct TicketGuard<'a> {
    mutex: &'a TicketMutex,
}

impl Drop for TicketGuard<'_> {
    fn drop(&mut self) {
        self.mutex.unlock();
    }
}
```

`TicketGuard` 是 RAII——构造时 lock,drop 时 unlock。这是 Rust 的标准 idiom,避免忘记 unlock。`spin_loop()` 是 Rust 标准库的"自旋提示",在 x86 上编译成 `_mm_pause` 指令。

`Drop for TicketGuard` 是 RAII 实现——`{ let _g = mutex.lock(); /* critical */ }` 离开作用域时自动 drop,自动 unlock。

### `pause` 指令的妙用

x86 的 `_mm_pause` 指令(汇编 `pause`)告诉 CPU:"我在自旋等待,你可以降低流水线功耗"。具体效果:

1. **降低功耗**:CPU 检测到 pause,降低该核的功耗(节能 ~50%)
2. **避免流水线惩罚**:自旋循环的 CPU 流水线会"分支预测失败"重罚,pause 提示避免
3. **超线程友好**:让出执行资源给同核的另一线程

ARM 上的等价指令是 `yield`,RISC-V 是 `pause`,都是"提示性质"。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的锁选择:

- **游戏主循环**:单线程,不用锁
- **资产加载**:Mutex(临界区短,自旋锁)
- **物理模拟**:per-thread 数据,不用锁
- **网络**:Mutex + condvar(临界区可能长)
- **跨 thread 数据共享**:lock-free queue(MPMC)

主流游戏引擎自写锁:

- Unreal:`FCriticalSection`(Windows 用 CriticalSection,Linux 用 pthread_mutex)
- Unity:内部用 OS mutex
- Casey HH:今天自写 ticket mutex

游戏行业的共识:**避免锁,改用 message passing**。线程之间不直接共享数据,而是通过无锁队列发消息。Unity DOTS / Unreal Mass Entity 都用这种模式。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核里的锁:

- **spinlock**:内核态自旋锁(类似今天的 ticket mutex)
- **mutex**:内核态睡眠锁
- **futex**(fast user mutex):用户态 fast path + 内核 slow path,Rust 标准库用它
- **seqlock**:读多写少场景,读不阻塞写
- **RCU**(Read-Copy-Update):无锁读,写用副本

Linux 内核的 spinlock 在 2.6.25 之前是 ticket lock,2.6.25 之后换成 MCS lock(更 cache 友好)。Casey 教 ticket mutex 因为它最简单易懂。

```c
// Linux 内核 ticket spinlock(老版本)
typedef struct {
    volatile unsigned int head;  // next_ticket
    volatile unsigned int tail;  // now_serving
} spinlock_t;

static inline void spin_lock(spinlock_t *lock) {
    unsigned int my_ticket = xchgadd(&lock->head, 1);
    while (lock->tail != my_ticket) {
        cpu_relax();
    }
}
```

`xchgadd` 是 x86 的 `lock xadd` 指令,等价于 Rust 的 `fetch_add`。

### 3.3 · 🦀 Rust 生态视角

Rust 的锁生态:

- **`std::sync::Mutex`**:标准库,futex 实现,通用
- **`parking_lot::Mutex`**:第三方,性能比标准库快 2-3 倍
- **`spin::Mutex`**:自旋锁,适合极短临界区
- **`std::sync::atomic::*`**:原子操作,直接构建 lock-free 算法

```toml
[dependencies]
parking_lot = "0.12"
```

`parking_lot` 的优势:

1. **不会 poison**:std Mutex 在 panic 时 poison(后续 lock 返回 Err),parking_lot 不会
2. **更快**:futex + 自旋结合,临界区短时快 2-3x
3. **const fn**:可以 `static` 初始化

Rust 表达票据锁(今天的代码):

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::hint::spin_loop;

pub struct TicketMutex {
    next_ticket: AtomicU64,
    now_serving: AtomicU64,
}

impl TicketMutex {
    pub const fn new() -> Self {
        Self {
            next_ticket: AtomicU64::new(0),
            now_serving: AtomicU64::new(0),
        }
    }
    
    pub fn lock(&self) -> TicketGuard<'_> {
        let my_ticket = self.next_ticket.fetch_add(1, Ordering::Relaxed);
        while self.now_serving.load(Ordering::Acquire) != my_ticket {
            spin_loop();
        }
        TicketGuard { mutex: self }
    }
    
    fn unlock_internal(&self) {
        self.now_serving.fetch_add(1, Ordering::Release);
    }
}

pub struct TicketGuard<'a> {
    mutex: &'a TicketMutex,
}

impl Drop for TicketGuard<'_> {
    fn drop(&mut self) {
        self.mutex.unlock_internal();
    }
}

// 安全:TicketMutex 内部用 atomic,跨线程共享安全
unsafe impl Sync for TicketMutex {}
unsafe impl Send for TicketMutex {}
```

注意 `unsafe impl Sync`——Rust 编译器不自动推断 atomic 类型 Sync(因为它不知道语义),我们要手动标记。这是"我知道我在做什么"的承诺。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:票据锁为什么"完全公平"?给出至少 2 个理由。

**参考解答**:

1. **FIFO 顺序**:每个等待者取一个递增号,获锁顺序由号决定。先到号小先获锁,后到号大后获锁,不存在"号大者插队"。
2. **无饿死**:任何等待者最多等待 N 个先到者(N = 当前队列长度),有限时间内必获锁。
3. **确定性**:无论调度器如何调度,获锁顺序固定。便于测试和验证。

朴素自旋锁(测试设置锁)不能保证公平——某线程运气好每次抢到,其他线程饿死。票据锁通过"号"消除运气因素。

## 8 · Rust / Arch 落地代码

### Rust:完整 ticket mutex(完整可跑)

```rust
// Cargo.toml: 无依赖
// src/main.rs

use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Arc;
use std::thread;
use std::hint::spin_loop;
use std::time::{Duration, Instant};

/// 票据锁:FIFO 公平自旋锁
pub struct TicketMutex {
    next_ticket: AtomicU64,
    now_serving: AtomicU64,
}

impl TicketMutex {
    pub const fn new() -> Self {
        Self {
            next_ticket: AtomicU64::new(0),
            now_serving: AtomicU64::new(0),
        }
    }
    
    /// 加锁。取号 + 自旋等叫号。
    pub fn lock(&self) -> TicketGuard<'_> {
        let my_ticket = self.next_ticket.fetch_add(1, Ordering::Relaxed);
        // 自旋等待
        let start = Instant::now();
        while self.now_serving.load(Ordering::Acquire) != my_ticket {
            spin_loop();  // x86 _mm_pause,降功耗
        }
        let waited = start.elapsed();
        if waited > Duration::from_millis(1) {
            // 长时间等待,记录一下(实际项目用 metrics)
        }
        TicketGuard { mutex: self, ticket: my_ticket }
    }
    
    fn unlock_internal(&self) {
        // 通知下一个等待者
        self.now_serving.fetch_add(1, Ordering::Release);
    }
}

unsafe impl Sync for TicketMutex {}
unsafe impl Send for TicketMutex {}

/// RAII guard,drop 时自动 unlock
pub struct TicketGuard<'a> {
    mutex: &'a TicketMutex,
    #[allow(dead_code)]
    ticket: u64,
}

impl Drop for TicketGuard<'_> {
    fn drop(&mut self) {
        self.mutex.unlock_internal();
    }
}

fn main() {
    println!("=== Day 325: 票据锁演示 ===\n");
    
    let mutex = Arc::new(TicketMutex::new());
    let log = Arc::new(std::sync::Mutex::new(Vec::<(u64, u64)>::new()));
    
    let mut handles = Vec::new();
    let start_time = Instant::now();
    
    // 启动 5 个线程,各自 lock → work → unlock
    for i in 0..5u64 {
        let mutex = Arc::clone(&mutex);
        let log = Arc::clone(&log);
        handles.push(thread::spawn(move || {
            // 让先启动的先取号(简化,实际不严格保证)
            thread::sleep(Duration::from_millis(i * 20));
            
            let lock_start = start_time.elapsed().as_millis() as u64;
            let _guard = mutex.lock();
            let lock_acquired = start_time.elapsed().as_millis() as u64;
            
            log.lock().unwrap().push((i, lock_acquired));
            
            println!("Thread {} locked at {}ms (waited {}ms)", 
                     i, lock_acquired, lock_acquired - lock_start);
            
            thread::sleep(Duration::from_millis(50));  // 持锁 50ms
            // _guard 离开作用域自动 unlock
        }));
    }
    
    for h in handles { h.join().unwrap(); }
    
    println!("\n=== Lock acquire order ===");
    let log = log.lock().unwrap();
    for (tid, time) in log.iter() {
        println!("Thread {} acquired at {}ms", tid, time);
    }
    
    // 验证 FIFO:Thread 0 应该先(因为它最早 sleep 0ms),Thread 4 最后
    let tids: Vec<_> = log.iter().map(|(t, _)| *t).collect();
    println!("\nLock order: {:?}", tids);
    println!("FIFO? {}", tids == vec![0, 1, 2, 3, 4]);
}
```

```

Thread 1 locked at 50ms (waited 30ms)
Thread 2 locked at 100ms (waited 60ms)

Thread 4 locked at 200ms (waited 120ms)

=== Lock acquire order ===
Thread 0 acquired at 0ms
Thread 1 acquired at 50ms
Thread 2 acquired at 100ms
Thread 3 acquired at 150ms
Thread 4 acquired at 200ms
```

每个线程持锁 50ms,后一个线程等前一个释放才能获锁。完全 FIFO,无饿死。

## 10 · 深度补充:工程视角

票据锁的工业演化:Linux 内核 2.6.25 之前用 ticket spinlock,2.6.25 之后换 MCS lock(cache 友好)。MCS 的核心思想:每个等待者在自己的 cache line 上 spin,避免所有人在同一个变量上 cache 抖动。Casey 教 ticket 因为它最直观,但工业级 Linux 用 MCS。Rust 的 parking_lot 用类似 MCS 的设计。

## 11 · 延伸讨论

锁的性能 benchmark:标准库 Mutex vs parking_lot vs 自写 ticket mutex vs spin 自旋锁。临界区极短(<100ns)时 spin 最快;中长(100ns-10us)parking_lot 最快;长(>10us)std Mutex 最快(让出 CPU)。futex syscall ~1us,所以临界区 <1us 自旋值。
