
# Day 417 · 加光照点调试视图

> Day 411-416 把光照系统改成基于矩形 + 多采样,但采样的过程**看不见**——采样点在 3D 空间,渲染出来后只是最终的墙面亮度。今天 Casey 加一个**调试视图**:把每个采样点画成小立方体,让你**亲眼看见**光照计算在哪里发生,采样密度够不够,矩形覆盖是否正确。

## 0 · 为什么要有这一天

调试光照系统时,你看到的只有最终图像——墙上的亮度分布。但**亮度背后的过程**是黑盒:

- 矩形光源的 4x4 = 16 个采样点都在哪?
- 它们是否覆盖了你期望的区域?
- 采样点的间距是否均匀?
- 采样点是否落在墙的另一边(穿模)?

光看亮度无法回答这些问题。工业调试的解决方案:**可视化中间状态**——把不可见的采样点、光线、包围盒画成可见的几何体,叠加在主场景上。

这是 debug overlay 的高级形式。Day 264 的 profiler 是"用文字和图表显示数据",day417 是"用 3D 几何显示数据"。后者更直观,也更难实现——你需要在主渲染完成后,在 3D 场景上叠加调试几何,这要求:

1. **调试几何管线独立于主渲染**(不影响主图)
2. **简单图元 API**:画点、线、立方体、球
3. **着色特殊**:不受光照影响,固定颜色
4. **生命周期**:一帧后丢弃

工业叫 **Immediate Mode Debug Draw**。Casey 今天实现它。这个工具后续会用无数次——day419 调缺失光照、day426 调持久化、day427 调闪烁,全都靠它。

心理锚点:今天之后,你能写自己的 debug draw API,能在渲染管线任意阶段"插入"调试几何,能在屏幕上画出你脑子里想到的任何东西。这是图形学工程师的核心能力。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 实现了一个叫 `debug_draw_*` 的 API 系列:

```c
debug_draw_point(p, color, size);
debug_draw_line(p1, p2, color);
debug_draw_aabb(bounds, color);
debug_draw_sphere(center, radius, color);
```

每帧调用这些 API,数据存进一个全局 buffer,渲染时独立绘制。Casey 在光照计算函数里加了 `debug_draw_point(p, color_yellow, 0.1)` 调用,把每个采样点画成小黄立方体。

他遇到一个问题:**采样点太多**(几千个),小立方体堆叠,看不清。他加了**密度调节**——F3 切换,只画 1/10 的点,或者只画某矩形的采样点。

Casey 强调:**调试代码本身要可以彻底关掉**。发布时一行 `#ifdef DEBUG` 或者运行时 flag 关掉,完全不影响性能。Rust 用 `cfg!(debug_assertions)` 或 `#[cfg(feature = "debug_draw")]`。

## 2 · 心智模型

### 类比:工程师的 X 光眼镜

想象一个机械工程师看着一台发动机。从外面看,只能看到金属外壳——内部活塞、齿轮、轴承的工作看不见。但如果有"X 光眼镜",能透视发动机,看到活塞往复运动、齿轮啮合,工程师立刻能定位异常。

Debug draw 就是图形学的 X 光眼镜。最终图像是"发动机外壳",亮度是"发动机行为"。但内部的光线、采样点、包围盒、纹理坐标——你看不见。把它们的几何画出来,问题立刻显形。

### 严谨原理:调试几何管线

调试几何的数据流:

```
游戏逻辑代码
    ↓ debug_draw_point(p, color, size)
调试 buffer(Vec<DebugVertex>)
    ↓
独立的 shader(无光照,固定颜色)
    ↓
混合到主画面(深度测试可关)
```

关键设计:

1. **每帧重建**:调试几何只活一帧,下一帧重新构建。这避免"画了不删"的 bug
2. **简单 vertex**:`{position: Vec3, color: Vec3}`,没有 uv、normal
3. **简单 shader**:`gl_Position = mvp * position; out_color = color;`,几行
4. **不透明 vs 透明**:默认不透明,可设 wireframe(线框)显示内部

### 工业模式:Immediate Mode

```rust
// 全局或线程局部
thread_local! {
    static DEBUG_DRAW_LIST: RefCell<DebugDrawList> = RefCell::new(DebugDrawList::new());
}

pub fn debug_draw_point(p: Vec3, color: Vec3, size: f32) {
    DEBUG_DRAW_LIST.with(|list| {
        list.borrow_mut().push_point(p, color, size);
    });
}

pub fn debug_render(camera: &Camera) {
    DEBUG_DRAW_LIST.with(|list| {
        let mut list = list.borrow_mut();
        list.render(camera);
        list.clear();  // 一帧后丢弃
    });
}
```

`thread_local!` 让全局变量线程安全——多个线程可以并行 push,各自有自己的 buffer。`RefCell` 提供 borrow check,运行时验证。

### Rust 视角:零成本调试

```rust
pub struct DebugDrawList {
    points: Vec<DebugPoint>,
    lines: Vec<DebugLine>,
    aabbs: Vec<DebugAabb>,
}

impl DebugDrawList {
    pub fn push_point(&mut self, p: Vec3, color: Vec3, size: f32) {
        self.points.push(DebugPoint { pos: p, color, size });
    }

    pub fn render(&self, camera: &Camera) {
        unsafe {
            gl::UseProgram(DEBUG_SHADER);
            let mvp = camera.view_proj();
            gl::UniformMatrix4fv(DEBUG_MVP_LOC, 1, 0, mvp.as_ref().as_ptr());
            for p in &self.points {
                let half = p.size * 0.5;
                // 画一个小 AABB(立方体)
                draw_cube(p.pos - half, p.pos + half, p.color);
            }
        }
    }

    pub fn clear(&mut self) {
        self.points.clear();
        self.lines.clear();
        self.aabbs.clear();
    }
}
```

`clear()` 不释放内存(`Vec` 保留 capacity),下一帧直接复用——避免每帧分配。

### 调试光照采样的可视化

在光照计算函数里插入:

```rust
pub fn compute_primitive_lighting(...) {
    for i in 0..n {
        for j in 0..n {
            let u = (i as f32 + 0.5) / n as f32;
            let v = (j as f32 + 0.5) / n as f32;
            let p = primitive.sample_point(u, v);

            // === 调试可视化 ===
            if debug_enabled() {
                // 采样点:黄色小立方体
                debug_draw_point(p, Vec3::new(1.0, 1.0, 0.0), 0.05);
                // 到光源的连线:绿色细线
                for light in lights {
                    debug_draw_line(p, light.pos, Vec3::new(0.0, 1.0, 0.0));
                }
            }

            // === 实际计算 ===
            let lighting = compute_point_lighting(p, ...);
            accum += lighting;
        }
    }
}
```

`if debug_enabled()` 是运行时分支。开 debug 时画,关时不画——零成本。

### 颜色编码

工业惯例的颜色:

- 黄色:采样点、特征点
- 绿色:成功连接(光线无遮挡)
- 红色:失败连接(光线被遮挡)
- 蓝色:包围盒
- 紫色:法线

### 3.2 · 🎨 图形学视角

Debug draw 的几个技术点:

- **wireframe 渲染**:`glPolygonMode(GL_FRONT_AND_BACK, GL_LINE)` 把所有三角形画成线框
- **depth test 关闭**:让调试几何始终可见(穿过物体也显示)
- **depth test 开启**:让调试几何被遮挡(真实空间感)
- **blending**:半透明叠加,看清内部

Casey 默认 depth test 关(让采样点始终可见),重要时再开。

### 3.3 · 🐧 Linux 系统编程视角

Linux 的"调试可视化"工具:

- **strace**:可视化系统调用
- **perf flamegraph**:可视化函数调用栈
- **bpftrace**:可视化内核事件
- **Wireshark**:可视化网络包

这些工具和 debug draw 同构——把不可见的内部状态画出来。Casey 的 debug draw 是图形学版的 strace。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 debug draw 必须用"每帧重建"模式,而不是"画一次后保持"?

**参考解答**:光照采样点每帧不同——矩形光源可能移动,采样位置可能随机变化(分层随机),物体可能改变。如果"画一次后保持",旧的采样点残留,新的叠加,屏幕越来越乱。

每帧重建保证调试几何始终反映**当前帧**的状态。开销是多算一次,但 debug draw 本身就只在 debug 模式下用,可接受。

更深层:**调试几何的语义是"瞬态观察"**——它描述代码此刻在做什么,不是"标记场景中的某个点"。一旦观察结束,几何应该消失。如果需要"标记",用主渲染的实体(添加一个有 ID 的调试实体),而不是 debug draw。

    pub points: Vec<DebugPoint>,
    pub lines: Vec<DebugLine>,
    pub enabled: bool,

    pub fn new() -> Self {
        Self { points: Vec::with_capacity(1024), lines: Vec::with_capacity(2048), enabled: false }
    }

    pub fn point(&mut self, p: Vec3, color: Vec3, size: f32) {
        if self.enabled { self.points.push(DebugPoint { pos: p, color, size }); }
    }

    pub fn line(&mut self, from: Vec3, to: Vec3, color: Vec3) {
        if self.enabled { self.lines.push(DebugLine { from, to, color }); }

    pub fn aabb(&mut self, min: Vec3, max: Vec3, color: Vec3) {
        if !self.enabled { return; }
        // 12 条边

            Vec3::new(max.x, min.y, min.z),
            Vec3::new(min.x, max.y, min.z),
            Vec3::new(max.x, max.y, min.z),
            Vec3::new(min.x, min.y, max.z),
            Vec3::new(max.x, min.y, max.z),
            Vec3::new(min.x, max.y, max.z),

            (0,1),(1,3),(3,2),(2,0),  // 前
            (4,5),(5,7),(7,6),(6,4),  // 后
            (0,4),(1,5),(2,6),(3,7),  // 侧
        ];
        for (a, b) in edges {
            self.line(c[a], c[b], color);
        }
    }

        // 实际 OpenGL/Vulkan 渲染代码
        // 这里只打印计数
        println!("Debug: {} points, {} lines", self.points.len(), self.lines.len());

        self.points.clear();
        self.lines.clear();

use std::cell::RefCell;

pub struct DebugDrawList {
    points: Vec<DebugPoint>,
    lines: Vec<DebugLine>,
    pub enabled: bool,
}

#[derive(Copy, Clone)]
struct DebugPoint { pos: Vec3, color: Vec3, size: f32 }
#[derive(Copy, Clone)]
struct DebugLine { from: Vec3, to: Vec3, color: Vec3 }

impl DebugDrawList {

            points: Vec::with_capacity(4096),
            lines: Vec::with_capacity(8192),
            enabled: false,
        }

    pub fn point(&mut self, p: Vec3, color: Vec3, size: f32) {
        if self.enabled {
            self.points.push(DebugPoint { pos: p, color, size });
        }
    }

            self.lines.push(DebugLine { from, to, color });

            Vec3::new(max.x, min.y, min.z),
            Vec3::new(min.x, max.y, min.z),
            Vec3::new(max.x, max.y, min.z),
            Vec3::new(min.x, min.y, max.z),
            Vec3::new(max.x, min.y, max.z),
            Vec3::new(min.x, max.y, max.z),
            max,
        ];
        for (a, b) in [(0,1),(1,3),(3,2),(2,0),(4,5),(5,7),(7,6),(6,4),(0,4),(1,5),(2,6),(3,7)] {
            self.line(corners[a], corners[b], color);
        }
    }

    pub fn render(&self, _vp: Mat4) {
        // 这里写实际 OpenGL 绘制代码
        // 1. 绑定 debug shader(无光照,固定颜色)
        // 2. 上传 mvp uniform
        // 3. glDisable(GL_DEPTH_TEST)(可选)
        // 4. 画 lines:GL_LINES
        // 5. 画 points:每个 point 是一个 12 三角形的小立方体
    }

    pub fn clear(&mut self) {
        self.points.clear();
        self.lines.clear();
    }
}

    static DEBUG: RefCell<DebugDrawList> = RefCell::new(DebugDrawList::new());
}

pub fn debug_point(p: Vec3, color: Vec3, size: f32) {
    DEBUG.with(|d| d.borrow_mut().point(p, color, size));
}

pub fn debug_line(from: Vec3, to: Vec3, color: Vec3) {
    DEBUG.with(|d| d.borrow_mut().line(from, to, color));

    DEBUG.with(|d| d.borrow_mut().aabb(min, max, color));
}

pub fn debug_toggle() {
    DEBUG.with(|d| d.borrow_mut().enabled = !d.borrow().enabled);
}

    DEBUG.with(|d| {
        d.borrow().render(vp);
        d.borrow_mut().clear();
    });
}

// 在光照函数里调用
pub fn compute_primitive_lighting_debug(
    min: Vec3, max: Vec3, normal: Vec3,
    light_pos: Vec3, samples: u32,
) -> Vec3 {
    let n = samples;
    let mut accum = Vec3::ZERO;
    for i in 0..n {
        for j in 0..n {
            let u = (i as f32 + 0.5) / n as f32;
            let v = (j as f32 + 0.5) / n as f32;
            let p = Vec3::new(
                min.x + (max.x - min.x) * u,
                min.y + (max.y - min.y) * v,
                min.z,
            );
            // 调试可视化
            debug_point(p, Vec3::new(1.0, 1.0, 0.0), 0.05);
            debug_line(p, light_pos, Vec3::new(0.0, 1.0, 0.0));

            // 实际光照计算
            let to_light = light_pos - p;
            let dist2 = to_light.length_squared();
            let n_dot_l = normal.dot(to_light / dist2.sqrt()).max(0.0);
            accum += Vec3::ONE * n_dot_l / dist2;
        }
    }
    accum / (n * n) as f32
}

fn main() {
    debug_toggle();
    let _ = compute_primitive_lighting_debug(
        Vec3::ZERO, Vec3::new(2.0, 2.0, 0.0),
        Vec3::Z, Vec3::new(1.0, 1.0, 3.0), 4,
    );
    debug_render(Mat4::IDENTITY);
    println!("Frame done");
}

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
