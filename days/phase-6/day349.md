
# Day 349 · 运行多个模拟区域

> 之前 HH 只有一个 sim region(玩家附近),所有模拟都在那里跑。今天 Casey 打破这个限制——同时跑**多个 sim region**,每个有独立的玩家/相机/物理。这是 split-screen 多人游戏的基础,也是 Day 350 多线程模拟的预备。

## 0 · 为什么要有这一天

想象 split-screen(分屏)游戏:两个玩家共用一个屏幕,每人占一半。物理上他们可能在世界两端,各自附近的活动都要模拟。

如果只有一个 sim region:

- 玩家 1 在 (0, 0),sim region 跟他
- 玩家 2 在 (1000, 1000),完全在 sim region 外
- 玩家 2 附近的怪物不动、粒子不飞——"卡住"

简单方案:把 sim region 扩大,覆盖两个玩家。问题:模拟成本 O(n²) 上升,因为 sim region 是 N×N,两个玩家分别在两角,N 要很大才能都覆盖。

更好的方案:**多个 sim region**。每个玩家一个,各 100×100 大小。模拟成本只增加 2 倍,而非 N² 倍。

```
世界 (10000 x 10000):
  Player 1 (0, 0)         Player 2 (1000, 1000)
     ┌─────┐                  ┌─────┐
     │ R1  │                  │ R2  │
     │100² │                  │100² │
     └─────┘                  └─────┘
```

**今天的任务**:让游戏循环跑 N 个 sim region,每个独立更新,渲染时各自投影到屏幕的一半。

挑战:

1. **资源分享**:两个 sim region 共享同一份 entity 数据(玩家 A 看得到玩家 B 吗?)
2. **跨区域事件**:玩家 A 在 R1 里射出子弹,飞到 R2 里的玩家 B——子弹怎么"穿越"
3. **渲染顺序**:R1 先画还是 R2 先画?viewport 怎么分

Casey Day 349 不解决全部,只解决"如何同时跑两个独立 sim region"。跨区域是 Day 350+ 的事。

心理锚点:今天之后你能解释"为什么 sim region 是个可扩展概念",理解"虚拟玩家/相机"如何让多玩家共享一个引擎,知道 split-screen 多人游戏的核心架构。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天重构游戏循环:

1. **抽出 sim region 概念**:`struct sim_region`,有自己的相机、玩家、entities
2. **存储多 region**:`world.sim_regions: [sim_region; MAX_PLAYERS]`
3. **更新循环**:`for region in &mut world.sim_regions { region.update(dt) }`
4. **渲染循环**:`for (i, region) in world.sim_regions.iter().enumerate() { render_in_viewport(region, viewports[i]) }`
5. **输入分发**:玩家 1 的键盘事件发到 `sim_regions[0]`,玩家 2 的发到 `sim_regions[1]`

Casey 不解决"两个 region 重叠时怎么办"——他在 HH 里假设每个玩家有独立 sim region,互相不重叠(物理上不在同一区域)。Day 350 加多线程后才考虑复杂场景。

## 2 · 心智模型

### 类比:多会议室的酒店

想象酒店有 N 个会议室,每个会议室开一场独立的会。

- 单会议(老版本):所有人在一个大会议室,所有人看同一个投影
- 多会议(今天):N 个小会议室,各自开会,各自投影

会议间可能"互相影响"——比如走廊上的对话、共用咖啡机——但会议本身独立。

游戏 sim region 同构:

- 单 region(老版本):一个相机,所有 entity 在它的"视野"里
- 多 region(今天):N 个相机,N 个 entity 集合,各自模拟

跨 region 影响:玩家 A 的子弹飞到 region B —— 像"走廊上的对话",需要专门处理(今天不做)。

### Sim Region 的独立性

要让两个 sim region 独立运行,每个 region 必须"自带上下文":

```rust
struct SimRegion {
    // 自带相机
    camera_pos: Vec3,
    // 自带 entities(本地引用)
    entities: Vec<EntityId>,  // ID 引用,真实数据在 world
    // 自带 sim_origin(模拟空间原点)
    sim_origin: Vec3,
    // 自带粒子系统
    particles: ParticleSystem,
}
```

不要共享 `camera_pos`——多个相机各自维护。

更新时:

```rust
fn update(world: &mut World, dt: f32) {
    for region in &mut world.sim_regions {
        // 每个 region 独立更新
        region.update(dt, world);
    }
}
```

### 多 region 的"虚拟化"

Casey 今天的核心思想:**虚拟化玩家/相机**。老版本"玩家 = 全局唯一的 special entity",新版本"玩家 = 普通实体,sim region 里多了一个'控制焦点'"。

```rust
// 老版本:
struct World {
    player: Entity,  // 全局唯一
    entities: Vec<Entity>,
}

// 新版本:
struct World {
    entities: Vec<Entity>,  // 所有实体,玩家也是其中之一
    sim_regions: Vec<SimRegion>,  // 每个 region 跟踪一个"焦点"
}

struct SimRegion {
    focus_entity_id: EntityId,  // 这个 region 跟踪谁(玩家 1 / 玩家 2 / NPC)
    // ...
}
```

虚拟化是软件架构的常见模式:

- **进程**(操作系统):每个进程以为自己独占 CPU,实际多个进程"虚拟"共享
- **容器**(Docker):每个容器以为自己在独立 OS
- **玩家视图**:每个玩家以为自己玩的是完整游戏,实际只是 N 个 region 中的一个

### 渲染的 viewport 分割

split-screen 把屏幕分成两半,各画各的:

```rust
fn render(world: &World, screen_w: u32, screen_h: u32) {
    let viewport_w = screen_w / 2;
    for (i, region) in world.sim_regions.iter().enumerate() {
        let viewport_x = i as u32 * viewport_w;
        // 设置 OpenGL viewport
        unsafe { gl::Viewport(viewport_x as i32, 0, viewport_w as i32, screen_h as i32); }
        // 在这个 viewport 里渲染 region
        render_region(region);
    }
}
```

OpenGL 的 `glViewport` 把后续渲染限制在屏幕的指定矩形。两次调用,两次渲染,各画一半。

### 输入分发

每个玩家用不同输入设备:

- 玩家 1:键盘 WASD
- 玩家 2:键盘方向键 或 手柄 1
- 玩家 3:手柄 2

```rust
fn handle_input(world: &mut World, inputs: &InputState) {
    // 玩家 1
    let p1_input = PlayerInput {
        move_x: (inputs.key_d as i8) - (inputs.key_a as i8),
        move_y: (inputs.key_s as i8) - (inputs.key_w as i8),
        action: inputs.key_space,
    };
    world.sim_regions[0].apply_input(p1_input);

    // 玩家 2
    let p2_input = PlayerInput {
        move_x: (inputs.key_right as i8) - (inputs.key_left as i8),
        move_y: (inputs.key_down as i8) - (inputs.key_up as i8),
        action: inputs.key_enter,
    };
    world.sim_regions[1].apply_input(p2_input);
}
```

### 共享数据的策略

`world.entities` 是所有 entity 的真实存储。多个 sim region 共享。如何避免冲突?

**策略 1:每个 region 只看自己附近的 entities**(Casey 今天的方式)

```rust
impl SimRegion {
    fn visible_entities(&self, world: &World) -> Vec<&Entity> {
        world.entities.iter()
            .filter(|e| (e.pos - self.camera_pos).length() < 100.0)
            .collect()
    }
}
```

**策略 2:每个 region 有自己的 entities 副本**(完全独立)

```rust
impl SimRegion {
    entities: Vec<Entity>,  // 独立副本
}
```

代价:内存翻倍,跨 region 同步困难。

**策略 3:分片(sharded)** —— 每个区域负责一组 entity(根据空间位置)

```rust
fn entity_region(entity_pos: Vec3) -> usize {
    // 根据 entity 位置决定归属
    ((entity_pos.x / 100.0).floor() + (entity_pos.y / 100.0).floor() * 100.0) as usize
}
```

适合大规模 MMO。

Casey 选策略 1:简单,适合 HH 单机多玩家场景。

### Rust 所有权和共享

Rust 表达"多个 region 共享 entities"用 `&World` 或 `Rc<RefCell<World>>`:

```rust
// 简单:借用
fn update(regions: &mut [SimRegion], world: &World) {
    for region in regions.iter_mut() {
        region.update(world);  // 只读 world
    }
}

// 复杂:可变共享(需要 RefCell 或锁)
fn update(regions: &mut [SimRegion], world: &Rc<RefCell<World>>) {
    for region in regions.iter_mut() {
        let w = world.borrow();
        region.update(&w);
    }
}
```

Casey 在 C 里裸指针 + 单线程,随便共享。Rust 必须显式 lifetime/RefCell。Day 350 多线程时还要加锁或 Arc<Mutex>。

## 3 · 四域深入

### 3.1 · 游戏编程视角

多人游戏的几种模式:

**1. Split-screen(分屏)**:今天 Casey 的方式。同一台机器,多个玩家,共享屏幕。

**2. Network multiplayer**:每个玩家一台机器,网络同步状态。HH 不涉及。

**3. Hot-seat(热椅)**:轮流操作,只有一个控制焦点,不同时。

**4. Asymmetric(非对称)**:一个玩家 VR,另一个 PC, asymmetric gameplay。如 *Keep Talking and Nobody Explodes*。

**5. MMO**:大量玩家同时在线,需要服务器 + 分片(sharding)。

业界 split-screen 案例:

- **Halo 系列**:经典 2-4 人 split-screen
- **Mario Kart**:2-4 人分屏
- **Super Smash Bros**:同屏(不分屏,所有人在一个屏幕)
- **Portal 2**:co-op 模式 2 人分屏

Casey Day 349 的多 sim region 思想适用于 1、3,不直接适用 4、5。

### 3.2 · 图形学视角

多 viewport 渲染的技术:

**1. OpenGL `glViewport`**:今天 Casey 的方式。简单,但每次切换 viewport 有开销。

**2. Framebuffer Object(FBO)**:每个 region 渲染到独立 FBO,最后合成。GPU 友好,现代引擎用。

**3. Single-pass stereo(VR)**:一次 draw call 渲染左右眼,GPU 硬件加速。VR 专用。

Casey 用方案 1(简单,教学友好)。生产引擎用方案 2(性能)。

### 3.3 · Linux 系统编程视角

Linux 多用户/多会话概念:

**虚拟终端(Ctrl+Alt+F1-F6)**:Linux 有 6 个虚拟终端,每个独立登录。像多 sim region 的操作系统级版本。

**X11 / Wayland 多 monitor**:每个显示器一个 screen,各自渲染。

**chroot / containers**:每个容器以为自己在独立系统。概念上和"多 sim region"一致——隔离执行环境。

**进程 vs 线程**:多进程 = 多 sim region(独立内存),多线程 = 单 region 多 worker(共享内存)。

### 3.4 · Rust 生态视角

Rust 表达"多 sim region"的几种模式:

**1. `Vec<SimRegion>`**:简单,适合固定数量。

**2. `HashMap<PlayerId, SimRegion>`**:动态玩家,可加可删。

**3. ECS 多玩家**:用 entity component 表示"region 概念"。Bevy 的 `Query<(&Player, &Transform)>` 可以一次拿到所有玩家。

**4. Actor model**:每个 region 是个 actor,通过 channel 通信。`actix` crate。

Casey 在 HH 用方案 1(数组),简单。生产用方案 3(ECS)。

**Bevy 多玩家**:

```rust
fn player_system(
    keyboard: Res<Input<KeyCode>>,
    mut players: Query<(&Player, &mut Transform)>,
) {
    for (player, mut transform) in &mut players {
        // 每个玩家独立处理
        let input = player.get_input(&keyboard);
        transform.translation += input * dt;
    }
}
```

Bevy 自动遍历所有 Player,无需手动循环 region。

## 5 · 对照与变奏

### 同一"多实例"思想在不同领域

**Web 服务器**:每个请求一个 handler 实例(线程 / 协程 / 进程)。

**数据库**:每个 session 一个 transaction context。

**编辑器**:每个打开的文件一个 buffer。

**沙盒**:每个浏览器 tab 一个进程(Chrome)。

**虚拟机**:每个 VM 一个完整 OS 实例。

所有都是"同一逻辑多个并行实例"——sim region 是这个模式在游戏里的实例。

### 多 sim region 的演化

- **1990s**:split-screen 是主流(PS1 / N64 时代)
- **2000s**:online 取代 split-screen,但本地 co-op 仍在(Halo)
- **2010s**:cross-platform multiplayer(手机 + PC + 主机同玩)
- **2020s**:cloud gaming(Stadia / GeForce Now)—— 服务器跑多实例

### 多 region 的"通信"问题

今天 Casey 假设 regions 互不重叠,通信问题简化。但真实游戏:

- 子弹穿越:玩家 A 射出,飞到 region B → 怎么"移交"
- 视觉互动:玩家 A 看到玩家 B 的影子(跨 region 渲染)
- 共享物理:两人推同一个箱子

业界做法:**事件队列**。所有跨 region 操作排队,帧末统一处理。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"扩大单 sim region"比"多 sim region"差?至少 3 个原因。

**参考解答**:

3 个原因:
1. **成本 O(N²)**:单 region 扩大到 N×N 模拟成本,多 region 是 k×(n×n) (k 个 region,每个 n×n)。两个玩家分别在 (0,0) 和 (1000,1000),要覆盖两者单 region 要 ~2000×2000,多 region 只要 2×100×100,差 200 倍。
2. **精度问题**:单 region 覆盖范围大,sim space 概念失效(粒子的 sim_pos 距 sim_origin 可能很远)。多 region 各自 sim_origin 接近各自中心。
3. **不相干内容浪费**:玩家 A 附近的怪物对玩家 B 无意义,但单 region 全模拟。多 region 只模拟"各自关心的"。

### Lv2 · 动手实践

**题**:实现一个 2 玩家 split-screen 模拟(纯文本输出,不真渲染)。两个玩家各自一个 region,各自移动,渲染时各自打印"看到的 entities"。

完成标准:跑 5 帧,看到两个玩家各自移动,各自打印视野内的 entities。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
    fn length(self) -> f32 { (self.x * self.x + self.y * self.y).sqrt() }
}

#[derive(Debug)]
struct Entity { id: u32, pos: Vec2, kind: &'static str }

struct World {
    entities: Vec<Entity>,
    next_id: u32,
}

impl World {
    fn new() -> Self { Self { entities: vec![], next_id: 1 } }
    fn spawn(&mut self, pos: Vec2, kind: &'static str) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        self.entities.push(Entity { id, pos, kind });
        id
    }
}

struct SimRegion {
    focus_id: u32,    // 这个 region 跟踪谁
    camera_pos: Vec2,
    view_radius: f32,
}

impl SimRegion {
    fn visible_entities(&self, world: &World) -> Vec<&Entity> {
        world.entities.iter()
            .filter(|e| e.pos.sub(self.camera_pos).length() < self.view_radius)
            .collect()
    }

    fn update(&mut self, world: &World, dt: f32, move_dir: Vec2) {
        // 让 focus entity 移动
        let focus = world.entities.iter()
            .find(|e| e.id == self.focus_id)
            .unwrap();
        // 注意:这里 world.entities 是不可变的,所以不能直接改 entity.pos
        // 真实实现需要 &mut world 和 entity mut access
        self.camera_pos = focus.pos;  // 相机跟随
        let _ = (dt, move_dir);  // 简化
    }
}

fn main() {
    let mut world = World::new();

    // 两个玩家
    let p1 = world.spawn(Vec2::new(0.0, 0.0), "player");
    let p2 = world.spawn(Vec2::new(1000.0, 1000.0), "player");

    // 一些 entities
    for i in 0..5 {
        world.spawn(Vec2::new(i as f32 * 10.0, 0.0), "tree");
    }
    for i in 0..5 {
        world.spawn(Vec2::new(1000.0 + i as f32 * 10.0, 1000.0), "rock");
    }

    let mut regions = vec![
        SimRegion { focus_id: p1, camera_pos: Vec2::new(0.0, 0.0), view_radius: 50.0 },
        SimRegion { focus_id: p2, camera_pos: Vec2::new(1000.0, 1000.0), view_radius: 50.0 },
    ];

    for frame in 0..3 {
        println!("\n--- Frame {} ---", frame);
        for (i, region) in regions.iter().enumerate() {
            let visible = region.visible_entities(&world);
            println!("Region {}: camera={:?} sees {} entities:",
                     i, region.camera_pos, visible.len());
            for e in visible.iter().take(3) {
                println!("  id={} kind={} pos={:?}", e.id, e.kind, e.pos);
            }
        }
    }
}
```

**关键解释**:
- `focus_id`:region 跟踪的 entity(玩家)
- `view_radius`:可见范围(50 米内)
- `visible_entities` 过滤,每个 region 只看附近
- 两个 region 看到完全不同的 entities(玩家 1 看 trees,玩家 2 看 rocks)

### 完整可跑示例

扩展 Lv2,加上玩家移动 + 多 region 真实模拟。

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
    fn length(self) -> f32 { (self.x * self.x + self.y * self.y).sqrt() }
}

#[derive(Debug)]
struct Entity { id: u32, pos: Vec2, kind: &'static str, vel: Vec2 }

struct World {
    entities: Vec<Entity>,
    next_id: u32,
}

impl World {
    fn new() -> Self { Self { entities: vec![], next_id: 1 } }
    fn spawn(&mut self, pos: Vec2, kind: &'static str) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        self.entities.push(Entity { id, pos, kind, vel: Vec2::new(0.0, 0.0) });
        id
    }
    fn get_mut(&mut self, id: u32) -> Option<&mut Entity> {
        self.entities.iter_mut().find(|e| e.id == id)
    }
    fn get(&self, id: u32) -> Option<&Entity> {
        self.entities.iter().find(|e| e.id == id)
    }
}

struct PlayerInput { dx: f32, dy: f32 }

struct SimRegion {
    focus_id: u32,
    camera_pos: Vec2,
    view_radius: f32,
    accumulated_input: PlayerInput,
}

impl SimRegion {
    fn new(focus_id: u32, camera_pos: Vec2) -> Self {
        Self {
            focus_id,
            camera_pos,
            view_radius: 50.0,
            accumulated_input: PlayerInput { dx: 0.0, dy: 0.0 },
        }
    }

    fn apply_input(&mut self, input: PlayerInput) {
        self.accumulated_input.dx += input.dx;
        self.accumulated_input.dy += input.dy;
    }

    fn update(&mut self, world: &mut World, dt: f32) {
        // 移动 focus entity
        if let Some(focus) = world.get_mut(self.focus_id) {
            focus.pos.x += self.accumulated_input.dx * dt;
            focus.pos.y += self.accumulated_input.dy * dt;
        }
        // 重置 accumulated
        self.accumulated_input = PlayerInput { dx: 0.0, dy: 0.0 };

        // 相机跟随
        if let Some(focus) = world.get(self.focus_id) {
            self.camera_pos = focus.pos;
        }
    }

    fn render(&self, world: &World) {
        println!("  Camera at {:?}", self.camera_pos);
        let visible: Vec<&Entity> = world.entities.iter()
            .filter(|e| e.pos.sub(self.camera_pos).length() < self.view_radius)
            .collect();
        println!("  Visible: {} entities", visible.len());
        for e in visible.iter().take(5) {
            println!("    - id={} kind={} pos={:?}", e.id, e.kind, e.pos);
        }
    }
}

fn main() {
    let mut world = World::new();

    let p1 = world.spawn(Vec2::new(0.0, 0.0), "player");
    let p2 = world.spawn(Vec2::new(1000.0, 1000.0), "player");

    for i in 0..5 {
        world.spawn(Vec2::new(i as f32 * 10.0, 0.0), "tree");
    }
    for i in 0..5 {
        world.spawn(Vec2::new(1000.0 + i as f32 * 10.0, 1000.0), "rock");
    }

    let mut regions = vec![
        SimRegion::new(p1, Vec2::new(0.0, 0.0)),
        SimRegion::new(p2, Vec2::new(1000.0, 1000.0)),
    ];

    let dt = 1.0 / 60.0;
    for frame in 0..5 {
        println!("\n=== Frame {} ===", frame);

        // 输入:玩家 1 向右,玩家 2 向上
        regions[0].apply_input(PlayerInput { dx: 10.0, dy: 0.0 });
        regions[1].apply_input(PlayerInput { dx: 0.0, dy: 10.0 });

        // 更新各 region
        for region in regions.iter_mut() {
            region.update(&mut world, dt);
        }

        // 渲染各 region
        for (i, region) in regions.iter().enumerate() {
            println!("Region {}:", i);
            region.render(&world);
        }
    }

    // 最终位置
    println!("\n=== Final positions ===");
    println!("P1 at {:?}", world.get(p1).unwrap().pos);
    println!("P2 at {:?}", world.get(p2).unwrap().pos);
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
