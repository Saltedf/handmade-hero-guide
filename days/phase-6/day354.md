
# Day 354 · 简单 LZ 压缩

> RLE 只能压"连续重复",对真实数据(文本、代码、序列化)几乎无效。今天 Casey 实现更强大的 **LZ77**(Lempel-Ziv 1977):找"前面出现过的子串",用 (offset, length) 对替代。LZ 是 ZIP / GZIP / PNG 的核心算法,理解 LZ 等于理解现代压缩的 80%。

## 0 · 为什么要有这一天

RLE 的局限:只看**连续**重复。但真实数据的冗余更微妙:

```
"the cat sat on the mat"
```

`the` 出现 2 次,但不连续。RLE 抓不到。LZ 抓得到:

```
编码:the cat sat on [回引 4 字节,长度 3] mat
                    ↑ 指向前面的 "the"
```

LZ77 的核心思想:**用 (offset, length) 引用前面的子串**,而非显式存储。

这种"回引引用"对几乎所有真实数据有效:

- 文本:单词、短语重复
- 代码:语法结构、关键字重复
- 序列化:字段名、结构重复
- 游戏数据:tile pattern、entity 模板重复

LZ77 是后续算法的祖先:

- **LZSS**:LZ77 优化版,加 literal flag
- **LZW**:LZ 变体,用字典(专利过期后用于 GIF)
- **Deflate**:LZ77 + Huffman(PNG / ZIP 用)
- **LZMA**:LZ + 大字典 + range coding(7zip)
- **LZ4**:LZ 极速版
- **Zstd**:LZ + FSE(Facebook)

今天 Casey 实现最朴素的 LZ77——50 行代码,但揭示核心思想。

心理锚点:今天之后你能解释"滑动窗口"概念,理解 (offset, length) 引用,知道为什么 ZIP / GZIP 比 RLE 强 10 倍。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑 Day 353 的 RLE,发现真实游戏数据(序列化 entity、物品 list)压缩率不好——entity 字段重复但不连续。

Casey 实现 LZ77:

1. **滑动窗口**:维护"最近 N 字节"作为"回引搜索区"(N = 4096)
2. **匹配搜索**:当前位置向前找最长的"已出现过的子串"
3. **输出**:literal byte 或 (offset, length, next_literal)
4. **解码**:literal 直接写,(offset, length) 从输出 buffer 复制

结果:

- RLE 压缩 100KB 测试数据 → 80KB(20% 压缩率)
- LZ77 同数据 → 40KB(60% 压缩率)

LZ77 复杂但效果好。后续算法在此基础上优化。

## 2 · 心智模型

### 类比:图书馆借书记录

图书管理员记录借书:

```
借出:Python 编程,Python 编程,C++ Primer,Python 编程
```

直接记录 4 本书名。但如果用"回引":

```
借出:Python 编程,(重复 0 号 1 本),C++ Primer,(重复 0 号 1 本)
```

每次重复都引用前面记录,LZ 思想。

解码时:看到 "(重复 0 号 1 本)" 就回头查记录第 0 号,复制内容。

### LZ77 的滑动窗口

LZ77 维护一个**滑动窗口**,通常是最近 N 字节(N = 4096 是经典值)。

```
[已经编码的 buffer | 当前位置 | 待编码]
[ ─── 滑动窗口 ─── ]
```

每次编码:

1. 在滑动窗口里找"和当前位置开始的最长匹配子串"
2. 如果找到匹配长度 >= 3,输出 (offset, length) 引用
3. 否则输出 literal byte
4. 窗口向前滑动 length 字节

```
示例:
原始:the cat sat on the mat
     ↑

Step 1: 窗口为空,无匹配。输出 literal 'the cat sat on '。
       窗口前进到 'the cat sat on | the mat'

Step 2: 在窗口搜索 'the mat'。
        窗口里有 'the'(位置 0),匹配长度 3。
        输出 (offset=15, length=3)。
        然后输出 literal 'mat' 里的 'm'。

最终:[literal 'the cat sat on '][(offset=15, length=3) 'the'][literal ' mat']
```

### (offset, length) 编码

每个引用 = (offset, length) 对:

- offset:回引距离(从当前位置往回多少字节)
- length:匹配长度

```
buffer:        the cat sat on the mat
                              ↑ (当前位置)
                └─offset=15─┘
                找到匹配 "the",length=3
```

注意 offset 是"距离",不是"绝对位置"。这避免解压时依赖绝对位置。

### 输出格式

最简 LZ77 输出每三元组:

```
[(offset, length, next_literal)] 序列
```

每个三元组:

- 找匹配(可能找不到,length=0)
- 输出匹配(offset, length)
- 输出一个字面字符 next_literal(推进 buffer)

```
原始:       ABCABC
Step 1:     无匹配,offset=0,length=0,next='A'
Step 2:     无匹配,offset=0,length=0,next='B'
Step 3:     无匹配,offset=0,length=0,next='C'
Step 4:     匹配 "ABC" 在位置 0,offset=3,length=3
            匹配后再输出一个 literal 推进
            但 buffer 已到末尾,放一个 dummy 'A'
```

实际 LZSS 改进:literal 和 reference 分开,避免每次都强制输出 literal。

### LZSS:更聪明的格式

LZ77 的缺陷:每次都输出 3 元组,即使无匹配也要 `(0, 0, char)` 3 字节存 1 字节 literal——膨胀 3 倍。

**LZSS**(LZ77 + Storer-Szymanski)改进:

- 加 1 bit flag:0 = literal,1 = reference
- literal:flag + byte = 9 bit
- reference:flag + offset + length = 1 + 12 + 4 = 17 bit(典型)

无匹配时只膨胀 12.5%(9 bit / 8 bit),而非 300%。

**PackBits 也用类似思想**(Day 353 提到的 escape byte)。

Deflate 更进一步:用 Huffman 编码 flag、offset、length,进一步压缩。

### 匹配搜索的复杂度

朴素的 LZ77 匹配:

```rust
for start in (current_pos - WINDOW_SIZE)..current_pos {
    let mut match_len = 0;
    while buffer[start + match_len] == buffer[current_pos + match_len]
        && current_pos + match_len < buffer.len()
        && match_len < MAX_LENGTH
    {
        match_len += 1;
    }
    if match_len > best_match_len {
        best_match_len = match_len;
        best_offset = current_pos - start;
    }
}
```

复杂度:O(WINDOW_SIZE × MAX_LENGTH) 每字节。WINDOW_SIZE = 4096,MAX_LENGTH = 18,即每字节 73K 操作。压缩 1MB = 73G 操作,慢。

**优化**:**hash table 索引**——把"最近见过的 3 字节序列"建 hash,快速找候选匹配。Deflate 用这优化,1MB 压缩毫秒级。

```rust
let mut hash_table: HashMap<[u8; 3], Vec<usize>> = HashMap::new();

// 编码时:
let key = [buffer[i], buffer[i+1], buffer[i+2]];
let candidates = hash_table.get(&key).cloned().unwrap_or_default();
// 只在 candidates 里搜,而不是整个窗口
```

Casey Day 354 用朴素版(教学),生产用 hash 版。

### 解码速度

LZ 解压极快:就是"复制"。

```rust
fn lz_decode(input: &[(u16, u8, u8)], output: &mut Vec<u8>) {
    for (offset, length, literal) in input {
        // 复制匹配
        if *length > 0 {
            let start = output.len() - *offset as usize;
            for i in 0..*length as usize {
                let byte = output[start + i];
                output.push(byte);
            }
        }
        // 复制 literal
        output.push(*literal);
    }
}
```

**注意**:`output[start + i]` 可能是**刚刚 push 的字节**——LZ 允许"重叠引用"(`length > offset`),实现"复制扩展模式":

```
原始:        AB??  (?? 是要生成的)
匹配:        offset=2, length=4

Step 1: 复制 output[0]='A',output = "ABA"
Step 2: 复制 output[1]='B',output = "ABAB"
Step 3: 复制 output[2]='A',output = "ABABA"
Step 4: 复制 output[3]='B',output = "ABABAB"
```

`offset=2, length=4` 把 "AB" 扩展成 "ABABAB"。这种"重叠复制"对生成重复模式很有用(RLE 的远亲)。

### Rust 实现

完整 LZ77 编码器(简化):

```rust
const WINDOW_SIZE: usize = 4096;
const MAX_MATCH: usize = 18;
const MIN_MATCH: usize = 3;

fn lz_encode(input: &[u8]) -> Vec<(u16, u8, u8)> {
    let mut output = vec![];
    let mut i = 0;
    while i < input.len() {
        let (best_offset, best_length) = find_best_match(input, i);

        if best_length >= MIN_MATCH {
            // 输出 reference + literal
            let literal = if i + best_length < input.len() {
                input[i + best_length]
            } else {
                0  // dummy
            };
            output.push((best_offset as u16, best_length as u8, literal));
            i += best_length + 1;
        } else {
            // 输出 literal only
            output.push((0, 0, input[i]));
            i += 1;
        }
    }
    output
}

fn find_best_match(input: &[u8], pos: usize) -> (usize, usize) {
    let window_start = pos.saturating_sub(WINDOW_SIZE);
    let mut best_offset = 0;
    let mut best_length = 0;

    for start in window_start..pos {
        let mut length = 0;
        while pos + length < input.len()
            && length < MAX_MATCH
            && input[start + length] == input[pos + length]
        {
            length += 1;
        }
        if length > best_length {
            best_length = length;
            best_offset = pos - start;
        }
    }
    (best_offset, best_length)
}
```

简化版用 `Vec<(u16, u8, u8)>`——每个三元组 4 字节(实际 3 字节但 Rust 对齐)。生产用 bit-stream 紧凑编码。

## 5 · 对照与变奏

### LZ77 vs LZ78 vs LZW

**LZ77**(1977):滑动窗口 + (offset, length) 对。今天 Casey 实现的。

**LZ78**(1978):显式字典。维护"已见过的串列表",输出字典 index。

**LZW**(1984):LZ78 改进,字典自动构建(不需要传字典给解码器)。GIF 用,曾经有专利。

Deflate = LZ77 + Huffman。ZIP / GZIP / PNG 都用 Deflate。

### 不同 LZ 的窗口大小

- **LZ77 经典**:32 KB
- **LZSS**:通常 4-32 KB
- **LZMA**:64 MB - 1.5 GB(大字典!)
- **LZ4**:64 KB
- **Zstd**:可选,最大 8 MB

窗口越大找越多匹配,但内存和搜索时间增加。

### 历史演化

- **1977**:Lempel-Ziv 发表 LZ77
- **1978**:LZ78
- **1984**:Welch 改进成 LZW
- **1990s**:Deflate / ZIP / GZIP 流行
- **2000s**:LZMA(7zip),压缩率突破
- **2010s**:LZ4 / Zstd,速度突破
- **2020s**:机器学习压缩,但还未广泛部署

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:LZ77 的 (offset, length) 引用,offset 是"距离"还是"绝对位置"?为什么这样设计?

**参考解答**:**距离**。

原因:

1. **解码器不维护位置**:解码器只看输出 buffer,不知道"原文位置"
2. **适应任意位置**:同样的 (offset, length) 在 buffer 不同位置都能解
3. **避免数值范围问题**:offset 总在 [1, WINDOW_SIZE],绝对位置随 buffer 增长无界

举例:buffer = "ABAB",当前位置 2。

- 绝对位置引用:输出 (pos=0, length=2),解码时回头看 buffer[0..2]
- 距离引用:输出 (offset=2, length=2),解码时回头看 buffer[len-2..len]

距离引用让解码器逻辑极简:总是 `output[len() - offset]`。

### Lv2 · 动手实践

**题**:实现 LZ77 编码/解码。测试输入 `"the cat sat on the mat"`,验证压缩率 < 80%,解码数据正确。

完成标准:编码数据 < 80% 原始,解码 == 原始。

**参考解答**:

```rust
const WINDOW_SIZE: usize = 4096;
const MAX_MATCH: usize = 18;
const MIN_MATCH: usize = 3;

fn find_best_match(input: &[u8], pos: usize) -> (usize, usize) {
    let window_start = pos.saturating_sub(WINDOW_SIZE);
    let mut best_offset = 0;
    let mut best_length = 0;
    for start in window_start..pos {
        let mut length = 0;
        while pos + length < input.len()
            && length < MAX_MATCH
            && input[start + length] == input[pos + length]
        {
            length += 1;
        }
        if length > best_length {
            best_length = length;
            best_offset = pos - start;
        }
    }
    (best_offset, best_length)
}

fn lz_encode(input: &[u8]) -> Vec<(u16, u8, u8)> {
    let mut output = vec![];
    let mut i = 0;
    while i < input.len() {
        let (best_offset, best_length) = find_best_match(input, i);
        if best_length >= MIN_MATCH {
            let literal = if i + best_length < input.len() {
                input[i + best_length]
            } else {
                0
            };
            output.push((best_offset as u16, best_length as u8, literal));
            i += best_length + 1;
        } else {
            output.push((0, 0, input[i]));
            i += 1;
        }
    }
    output
}

fn lz_decode(encoded: &[(u16, u8, u8)]) -> Vec<u8> {
    let mut output = vec![];
    for (offset, length, literal) in encoded {
        if *length > 0 {
            let start = output.len() - *offset as usize;
            for i in 0..*length as usize {
                let byte = output[start + i];
                output.push(byte);
            }
        }
        output.push(*literal);
    }
    output
}

fn main() {
    let input = b"the cat sat on the mat the cat the cat the cat the cat";
    println!("Original: {} bytes", input.len());

    let encoded = lz_encode(input);
    let encoded_size = encoded.len() * 4;  // 每三元组 4 字节(简化)
    println!("Encoded: {} triples ({} bytes)", encoded.len(), encoded_size);
    println!("Compression ratio: {:.1}%",
             encoded_size as f64 / input.len() as f64 * 100.0);

    let decoded = lz_decode(&encoded);
    println!("Decoded matches: {}", decoded == input);

    // 看一些三元组
    println!("\nFirst 10 triples:");
    for (i, t) in encoded.iter().take(10).enumerate() {
        println!("  [{}]: offset={} length={} literal='{}' ({})",
                 i, t.0, t.1, t.2 as char, t.2);
    }
}
```

**预期输出**:
```
Original: 56 bytes
Encoded: ~25 triples (100 bytes)
Compression ratio: ~180%
```

注意:简化版每三元组 4 字节,对小输入会膨胀(三元组开销 > 字面)。生产 LZ 用 bit-stream 紧凑,~50% 压缩率。

**改进**:用 LZSS 风格 bit flag,或更长输入。试试输入 1000 字节重复 "the cat " 100 次,看效果。

## 8 · Rust / Arch 落地代码

### 完整可跑示例:bit-stream LZSS

```rust
const WINDOW_SIZE: usize = 4096;
const MAX_MATCH: usize = 18;
const MIN_MATCH: usize = 3;

fn find_best_match(input: &[u8], pos: usize) -> (usize, usize) {
    let window_start = pos.saturating_sub(WINDOW_SIZE);
    let mut best_offset = 0;
    let mut best_length = 0;
    for start in window_start..pos {
        let mut length = 0;
        while pos + length < input.len()
            && length < MAX_MATCH
            && input[start + length] == input[pos + length]
        {
            length += 1;
        }
        if length > best_length {
            best_length = length;
            best_offset = pos - start;
        }
    }
    (best_offset, best_length)
}

// 简化版 LZSS:用 byte 序列,每对 (flag, data)
// flag = 0:literal (data 是 1 字节)
// flag = 1:reference (data 是 offset_lo, offset_hi, length 3 字节)
fn lzss_encode(input: &[u8]) -> Vec<u8> {
    let mut output = vec![];
    let mut i = 0;
    while i < input.len() {
        let (offset, length) = find_best_match(input, i);
        if length >= MIN_MATCH {
            output.push(1);  // reference flag
            output.push((offset & 0xFF) as u8);
            output.push((offset >> 8) as u8);
            output.push(length as u8);
            i += length;
        } else {
            output.push(0);  // literal flag
            output.push(input[i]);
            i += 1;
        }
    }
    output
}

fn lzss_decode(input: &[u8]) -> Result<Vec<u8>, &'static str> {
    let mut output = vec![];
    let mut i = 0;
    while i < input.len() {
        let flag = input[i];
        i += 1;
        match flag {
            0 => {
                if i >= input.len() { return Err("truncated literal"); }
                output.push(input[i]);
                i += 1;
            }
            1 => {
                if i + 2 >= input.len() { return Err("truncated reference"); }
                let offset_lo = input[i] as usize;
                let offset_hi = input[i + 1] as usize;
                let length = input[i + 2] as usize;
                let offset = offset_lo | (offset_hi << 8);
                i += 3;

                let start = output.len().checked_sub(offset)
                    .ok_or("invalid offset")?;
                for j in 0..length {
                    let byte = output[start + j];
                    output.push(byte);
                }
            }
            _ => return Err("invalid flag"),
        }
    }
    Ok(output)
}

fn main() {
    let input = b"the cat sat on the mat the cat sat on the mat the cat";
    println!("Original: {} bytes", input.len());

    let encoded = lzss_encode(input);
    println!("LZSS encoded: {} bytes", encoded.len());
    println!("Compression: {:.1}%",
             encoded.len() as f64 / input.len() as f64 * 100.0);

    let decoded = lzss_decode(&encoded).unwrap();
    assert_eq!(input.as_ref(), decoded.as_slice());
    println!("Decoded correctly: true");

    // 大输入测试
    let big_input: Vec<u8> = (0..10000).map(|i| (i % 256) as u8).collect();
    let big_encoded = lzss_encode(&big_input);
    println!("\nBig input: {} -> {} bytes ({:.1}%)",
             big_input.len(), big_encoded.len(),
             big_encoded.len() as f64 / big_input.len() as f64 * 100.0);

    let big_decoded = lzss_decode(&big_encoded).unwrap();
    assert_eq!(big_input, big_decoded);
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
