# Day 434 · 替换伪随机数生成器

> HH 之前用的 PRNG(伪随机数生成器)是 Casey 早期写的简单 LCG(线性同余)。它在某些场景下**分布不均**,导致光照出现"伪影"——某些采样位置过于密集,某些过于稀疏。今天 Casey 替换成 **PCG(Permuted Congruential Generator)**——现代高质量、极快、统计优秀的 PRNG。这是工业主流。

## 0 · 为什么要有这一天

PRNG 是图形学的隐藏基础设施——采样、蒙特卡洛、随机方向、概率分布都依赖它。质量差的 PRNG 让结果**有偏**(biased),蒙特卡洛积分发散。

Casey 之前的 LCG:

```c
state = state * 1664525 + 1013904223;
return state / UINT_MAX;
```

简单极快,但:

1. **低位不随机**:LCG 低位有规律(状态低位是高位 mod 2^n)
2. **高维不均**:多维采样时,点在超平面上聚集(Marsaglia 效应)
3. **统计性差**:Diehard 测试不通过

具体到光照:用 LCG 采 16 个样本做矩形光源,样本可能在某些行/列聚集,光照有方向性偏差,看起来"条纹"。

PCG 解决这些问题:

- **质量极高**:通过所有统计测试(TestU01 Big Crush)
- **极快**:和 LCG 同速
- **周期长**:2^64
- **多维友好**:每维独立,无 Marsaglia
- **简洁**:核心算法 5 行 C

PCG 的作者 Melissa O'Neill 2014 年论文,目标是"质量比 MT19937(质量高但慢)好,速度比 LCG 快"。她做到了。今天 PCG 是 Rust `rand` crate 默认的 PRNG 之一。

更广义:**Rust `rand` 生态**提供多种 PRNG:

- `StdRng`:ChaCha12(密码学安全)
- `SmallRng`:PCG 或 Xoshiro(快)
- `thread_rng()`:线程本地,自动选最优

Casey 不用 `rand` crate(独立实现),手写 PCG。学习目的——理解算法。

心理锚点:今天之后,你能解释 PRNG 的质量指标(周期、分布、统计性),知道为什么工业用 PCG / Xoshiro,能在自己的项目选择合适的 PRNG。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 把 LCG 替换成 PCG:

```c
// 旧:LCG
u32 next_random(u32* state) {
    *state = *state * 1664525 + 1013904223;
    return *state;
}

// 新:PCG32
u32 next_pcg(u64* state) {
    u64 old = *state;
    *state = old * 6364136223846793005ULL + 1442695040888963407ULL;
    u32 xorshifted = ((old >> 18u) ^ old) >> 27u;
    u32 rot = old >> 59u;
    return (xorshifted >> rot) | (xorshifted << ((-rot) & 31));
}
```

PCG32 算法:

1. 更新状态:`state = state * multiplier + increment`(LCG-like)
2. 计算 xorshifted:`((old >> 18) ^ old) >> 27`(非线性变换)
3. 旋转:`rot = old >> 59`,把 xorshifted 旋转 rot 位
4. 返回旋转后的值

第 2-3 步是 PCG 的精髓——LCG 的低位有规律,但高位随机性好。xorshift + 旋转"扩散"高位随机性到所有位。

Casey 验证:用 PCG 跑 16 个采样,样本分布均匀,无聚集。视觉上光照平滑,无条纹。

## 2 · 心智模型

### 类比:洗牌

想象你洗牌。

- **差洗牌**(LCG):每次切牌方式固定,对手能预测。某些牌总是聚集。
- **好洗牌**(PCG):多次切牌 + riffle shuffle,统计上每张牌位置均匀。

PRNG 完全同构。**LCG 是"差洗牌"**——某些位有规律。**PCG 是"好洗牌"**——额外的 xorshift + rotation 让所有位均匀。

### 严谨原理:PRNG 的质量指标

好的 PRNG 满足:

1. **长周期**:状态不重复的最大长度。LCG 用 u32 状态周期 2^32,PCG32 用 u64 状态周期 2^64
2. **均匀分布**:生成的数在 [0, 1] 均匀分布
3. **统计独立**:连续生成的数无相关性
4. **多维均匀**:(x_1, x_2, ..., x_d) 在 d 维超立方体均匀
5. **不可预测**(密码学场景):不知道 next,不能猜 prev

LCG 满足 1、2 但不满足 3-5。PCG 满足 1-4(非密码学)。ChaCha 满足所有(密码学)。

### Marsaglia 效应

1968 年 Marsaglia 证明:**所有 LCG 在多维空间生成点都在少数超平面上**。具体:

- 3D 点 (x, y, z) = (rand, rand, rand),用 LCG 生成
- 这些点不在 3D 空间均匀分布,而在不到 3000 个平面上

视觉上,LCG 生成的"随机方向"在某些方向聚集。光照采样有方向偏差。

PCG 不是 LCG(虽然内部用 LCG 状态),通过 xorshift + rotation 让输出**不在固定平面上**。

### PCG 算法细节

PCG32 状态 u64,输出 u32:

```
1. old = state
2. state = old * 6364136223846793005 + 1442695040888963407
3. xorshifted = ((old >> 18) ^ old) >> 27
4. rot = old >> 59
5. output = (xorshifted >> rot) | (xorshifted << (32 - rot))
```

每步作用:

- **Step 2**:LCG 状态更新,周期长
- **Step 3**:xorshift,非线性,让高位影响低位
- **Step 4-5**:旋转,均匀分布位

输出函数(Step 3-5)是 PCG 的创新。LCG 的输出就是状态本身,PCG 输出是状态的"快速哈希"。

### Rust 视角:PCG32 实现

```rust
pub struct Pcg32 {
    state: u64,
    increment: u64,
}

impl Pcg32 {
    pub fn new(seed: u64, stream: u64) -> Self {
        // stream 必须是奇数(否则退化)
        let increment = (stream << 1) | 1;
        let mut rng = Self { state: 0, increment };
        rng.next();  // 抛弃第一个
        rng.state = rng.state.wrapping_add(seed);
        rng.next();  // 抛弃第二个
        rng
    }

    pub fn next_u32(&mut self) -> u32 {
        let old = self.state;
        self.state = old.wrapping_mul(6364136223846793005)
            .wrapping_add(self.increment);
        let xorshifted = (((old >> 18) ^ old) >> 27) as u32;
        let rot = (old >> 59) as u32;
        (xorshifted >> rot) | (xorshifted << ((!rot).wrapping_add(1) & 31))
    }

    pub fn next_f32(&mut self) -> f32 {
        // [0, 1)
        (self.next_u32() >> 8) as f32 / (1u32 << 24) as f32
    }
}
```

`wrapping_mul` / `wrapping_add` 是 Rust 的整数环绕运算(不 panic)。PCG 算法**依赖**整数环绕——高位被丢弃是设计的一部分。

### 用 PCG 替换 LCG

```rust
// 旧
let mut state = 42u32;
fn next_random(state: &mut u32) -> f32 {
    *state = state.wrapping_mul(1664525).wrapping_add(1013904223);
    *state as f32 / u32::MAX as f32
}

// 新
let mut rng = Pcg32::new(42, 0);
fn next_random(rng: &mut Pcg32) -> f32 {
    rng.next_f32()
}
```

接口相同,内部不同。Casey 的光照代码不用大改,只换 PRNG 类型。

### Xoshiro 替代

另一个现代 PRNG:**Xoshiro256**(Vigna 2018)。比 PCG 还快,质量好。

```rust
pub struct Xoshiro256 {
    state: [u64; 4],
}
```

Xoshiro 用 4 个 u64 状态(共 256 位),xor + 旋转生成 u64。质量极高,速度比 PCG 还快。

Rust `rand_xoshiro` crate 提供。Casey 选 PCG 是因为状态小(u64 vs 4×u64)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业 PRNG 选择:

- **`rand::StdRng`**:ChaCha12,密码学安全,默认
- **`rand::SmallRng`**:Xoshiro256++,游戏用
- **`rand::thread_rng()`**:线程本地 SmallRng
- **`pcg` crate**:PCG 单独 crate

工业游戏常用 Xoshiro(快)+ 给玩家**共享种子**(deterministic multiplayer)。

### 3.2 · 🎨 图形学视角

图形学 PRNG 应用:

- **蒙特卡洛积分**:光照采样
- **抖动**(jittered sampling):抗锯齿
- **程序化生成**:地形、纹理
- **粒子系统**:速度、生命周期

质量差 PRNG 让图形"看起来不对"——粒子聚集、采样偏差。PCG / Xoshiro 是工业标准。

### 3.3 · 🐧 Linux 系统编程视角

Linux 的随机:

- **`/dev/random`**:内核收集熵,密码学安全
- **`/dev/urandom`**:非阻塞,熵不足时也输出
- **`getrandom(2)`**:系统调用,推荐
- **glibc `rand()`**:LCG-based,质量差(类似 Casey 之前用的)

Linux 应用:密码学用 getrandom,普通用 rand。但 glibc rand 质量差是公认问题。

### 3.4 · 🦀 Rust 生态视角

Rust `rand` 生态:

```rust
use rand::{Rng, SeedableRng};
use rand::rngs::StdRng;

let mut rng = StdRng::seed_from_u64(42);
let x: f32 = rng.gen();
let y: u32 = rng.gen_range(0..100);
```

`StdRng` 自动用 ChaCha12(稳定后),跨平台一致。`SeedableRng` 让结果可复现(同种子同结果,利于调试)。

Casey 手写 PCG 是教学目的,实际项目用 `rand` crate。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"PRNG 质量"在图形学中比"PRNG 速度"更重要?具体说,质量差会带来什么问题?

**参考解答**:图形学大量使用蒙特卡洛积分——用 N 个随机样本估积分。**无偏估计**要求样本统计独立、均匀分布。质量差 PRNG:

1. **样本聚集**(Marsaglia 效应):某些区域密集,某些稀疏,积分有偏
2. **统计相关**:连续样本相关,方差比理论大,N 个样本不等效 N 个独立样本
3. **可见伪影**:粒子聚集、采样条纹、噪声不均匀

速度方面,PCG 和 LCG **几乎同速**(几个 ns),所以质量优势"免费"。即使 ChaCha(慢一点)也在 ns 级,游戏帧率影响小。

唯一例外:**密码学不安全**对游戏不是问题(玩家不预测随机数)。所以选 PRNG 时,**质量优先**。

### Lv2 · 动手实践

**题**:实现 PCG32,替换 LCG,验证质量。完成标准:

```rust
        let mut rng = Self { state: 0, increment };
        rng.next_u32();
        rng.state = rng.state.wrapping_add(seed);
        rng.next_u32();

    pub fn next_u32(&mut self) -> u32 {
        let old = self.state;
        self.state = old.wrapping_mul(6364136223846793005)
            .wrapping_add(self.increment);
        let xorshifted = (((old >> 18) ^ old) >> 27) as u32;

    let n = 1_000_000;
    let mut lcg = Lcg32::new(42);
    let mut pcg = Pcg32::new(42, 0);

    let mut lcg_sum = 0.0_f64;
    let mut pcg_sum = 0.0_f64;
    for _ in 0..n {
        lcg_sum += lcg.next_f32() as f64;
        pcg_sum += pcg.next_f32() as f64;

    let lcg_mean = lcg_sum / n as f64;
    let pcg_mean = pcg_sum / n as f64;
    println!("LCG mean: {:.6} (expected 0.5, error {:.4})",

        pcg_sq_sum += (x - 0.5).powi(2);

    let n = 100_000_000;
    let mut lcg = Lcg32::new(42);
    let start = std::time::Instant::now();
    for _ in 0..n {
        std::hint::black_box(lcg.next_u32());
    }
    let lcg_time = start.elapsed();
    println!("\nLCG {} numbers: {:?}", n, lcg_time);

    let mut pcg = Pcg32::new(42, 0);
    let start = std::time::Instant::now();
    for _ in 0..n {
        std::hint::black_box(pcg.next_u32());
    }
    let pcg_time = start.elapsed();
    println!("PCG {} numbers: {:?}", n, pcg_time);
    println!("Speed ratio: LCG/PCG = {:.2}x", lcg_time.as_secs_f64() / pcg_time.as_secs_f64());
```

## 8 · Rust / Arch 落地代码

```rust
#[derive(Clone, Debug)]
pub struct Pcg32 {
    state: u64,
    increment: u64,
}

impl Pcg32 {
    pub const DEFAULT_INCREMENT: u64 = 1442695040888963407;

    pub fn new(seed: u64, stream: u64) -> Self {
        let increment = (stream << 1) | 1;
        let mut rng = Self { state: 0, increment };
        rng.next_u32();
        rng.state = rng.state.wrapping_add(seed);
        rng.next_u32();
        rng
    }

    pub fn from_seed(seed: u64) -> Self {
        Self::new(seed, 0)
    }

    #[inline]
    pub fn next_u32(&mut self) -> u32 {
        let old = self.state;
        self.state = old.wrapping_mul(6364136223846793005)
            .wrapping_add(self.increment);
        let xorshifted = (((old >> 18) ^ old) >> 27) as u32;
        let rot = (old >> 59) as u32;
        if rot == 0 {
            xorshifted
        } else {
            (xorshifted >> rot) | (xorshifted << (32 - rot))
        }
    }

    #[inline]
    pub fn next_u64(&mut self) -> u64 {
        let lo = self.next_u32() as u64;
        let hi = self.next_u32() as u64;
        (hi << 32) | lo
    }

    /// 返回 [0, 1) 的 f32
    #[inline]
    pub fn next_f32(&mut self) -> f32 {
        // 用 24 位(避免 f32 精度损失)
        (self.next_u32() >> 8) as f32 * (1.0_f32 / (1u32 << 24) as f32)
    }

    /// 返回 [0, 1) 的 f64
    #[inline]
    pub fn next_f64(&mut self) -> f64 {
        (self.next_u32() >> 5) as f64 * (1.0_f64 / (1u32 << 27) as f64)
    }

    /// 返回 [low, high) 范围的 u32
    pub fn range_u32(&mut self, low: u32, high: u32) -> u32 {
        let span = high - low;
        low + (self.next_u32() % span)
    }
}

// 简单的 LCG,用于对比

    state: u32,
}

impl Lcg32 {
    pub fn new(seed: u32) -> Self { Self { state: seed } }

        self.state = self.state.wrapping_mul(1664525).wrapping_add(1013904223);
        self.state
    }
    pub fn next_f32(&mut self) -> f32 {
        self.next_u32() as f32 / u32::MAX as f32
    }
}

fn main() {
    println!("=== PCG32 vs LCG32 quality test ===\n");

    let n = 1_000_000;
    let mut lcg = Lcg32::new(42);
    let mut pcg = Pcg32::from_seed(42);

    // 均值
    let mut lcg_sum = 0.0_f64;
    let mut pcg_sum = 0.0_f64;
    for _ in 0..n {
        lcg_sum += lcg.next_f32() as f64;
        pcg_sum += pcg.next_f32() as f64;
    }
    println!("Mean over {} samples:", n);
    println!("  LCG: {:.6} (error {:.6})", lcg_sum / n as f64, (lcg_sum / n as f64 - 0.5).abs());
    println!("  PCG: {:.6} (error {:.6})", pcg_sum / n as f64, (pcg_sum / n as f64 - 0.5).abs());

    // 方差(均匀分布期望方差 1/12 ≈ 0.0833)
    let mut lcg = Lcg32::new(42);
    let mut pcg = Pcg32::from_seed(42);
    let mut lcg_var = 0.0_f64;
    let mut pcg_var = 0.0_f64;
    for _ in 0..n {
        let x = lcg.next_f32() as f64;
        lcg_var += (x - 0.5).powi(2);
        let x = pcg.next_f32() as f64;
        pcg_var += (x - 0.5).powi(2);
    }
    println!("\nVariance over {} samples (expected {:.4}):", n, 1.0 / 12.0);
    println!("  LCG: {:.6}", lcg_var / n as f64);
    println!("  PCG: {:.6}", pcg_var / n as f64);

    // 前 10 个值
    println!("\nFirst 10 values:");
    let mut lcg = Lcg32::new(42);
    let mut pcg = Pcg32::from_seed(42);
    for i in 0..10 {
        println!("  [{}] LCG={:.6} PCG={:.6}", i, lcg.next_f32(), pcg.next_f32());
    }

    // 性能
    println!("\nPerformance (100M numbers):");
    let n = 100_000_000;
    let mut lcg = Lcg32::new(42);
    let start = std::time::Instant::now();
    for _ in 0..n {
        std::hint::black_box(lcg.next_u32());
    }
    let lcg_time = start.elapsed();
    println!("  LCG: {:?} ({:.2} ns/op)", lcg_time, lcg_time.as_nanos() as f64 / n as f64);

    let mut pcg = Pcg32::from_seed(42);
    let start = std::time::Instant::now();
    for _ in 0..n {
        std::hint::black_box(pcg.next_u32());
    }
    let pcg_time = start.elapsed();
    println!("  PCG: {:?} ({:.2} ns/op)", pcg_time, pcg_time.as_nanos() as f64 / n as f64);
}
```

**Troubleshooting**:

- **PCG 输出有规律** — rot=0 时特例处理,直接返回 xorshifted
- **首次值异常** — PCG 构造时调用 next 两次"暖身",抛弃初始值

- **多线程** — Pcg32 不 Send + Sync(内部状态),每线程独立实例


### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
