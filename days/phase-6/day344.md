# Day 344 · 选择性内存恢复

> 给昨天的 save/restore 加一个"选择哪些块恢复"的能力——某些 arena 是"配置数据"不应该被 restore 抹掉,另一些是"瞬时状态"应该回滚。今天我们把单 token 恢复升级成"标记 + 选择性恢复"。

## 0 · 为什么要有这一天

昨天的 save/restore 是"全或无"——restore 把整个 arena 拨回去。但实战中你常常需要**部分恢复**:

考虑热重载场景。你改了一段 C 代码,重新编译了 cdylib,要把游戏状态从旧库迁移到新库。游戏状态包括:

1. **配置数据**(tile atlas、对话脚本、关卡定义):从磁盘加载的"静态"数据,不应被 restore 抹掉
2. **运行时状态**(entity 位置、当前生命值、敌人 AI):在玩家操作下变化,需要 restore 到改代码前的状态
3. **临时缓冲**(物理模拟中间结果):restore 时应该直接丢弃

如果用昨天的"全或无 restore",这三类数据要么全保留(包括临时缓冲,内存浪费),要么全 restore(包括配置数据,需要重新从磁盘加载)。

今天的方案:**给每个 arena 区段打标签**,restore 时按标签决定"恢复还是保留"。Casey 的具体实现是给 arena 加一个 `flags` 字段,然后 `restore_with_flags(snap, ARENA_RESTORE_PERMANENT)` 表示"只恢复标了 PERMANENT 的区段"。

这是 Casey 走过的"配置数据 vs 运行时数据"分界——他在 HH 里把整个内存分成两大类:

- **Permanent**:游戏从启动到退出都活着的内存(资源、配置、玩家档案),热重载不刷新
- **Transient**:每帧重新计算的内存(物理状态、渲染队列、AI 决策),热重载时应该 reset

今天加的"选择性恢复"是把这套二分法变成可编程接口。配置一个 arena 是"永久",另一个是"瞬时",restore 时只动"瞬时"的。

心理锚点:今天之后你能让某些 arena"穿越热重载",另一些"每帧重置"。这是状态管理的关键工具。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 在 day343 的 snapshot 之上加了一层"标记":

```c
typedef enum {
    ARENA_FLAG_PERMANENT = 0x1,    // 永久区,restore 不动
    ARENA_FLAG_TRANSIENT = 0x2,    // 瞬时区,restore 时 reset
    ARENA_FLAG_DEBUG = 0x4,        // 调试数据
} arena_flags;

typedef struct memory_arena {
    // ... day343 字段
    arena_flags flags;
} memory_arena;

void restore_arena_selective(arena_snapshot snap, arena_flags mask) {
    memory_arena *arena = snap.arena;
    if (arena->flags & mask) {
        restore_arena(snap);
    }
    // 否则不动
}
```

Casey 的实际实现更精细:他给每个**块**而不是 arena 整体打标签,允许"同一 arena 内的某些块是 PERMANENT,某些是 TRANSIENT"。但这需要块结构里加 `flags` 字段,稍微复杂。教学版我们用 arena 级别的标签。

另一个 Casey 改的细节:**热重载时怎么调用**。他的热重载代码大致:

```c
void hot_reload(void) {
    arena_snapshot snap = save_arena(transient_arena);
    unload_game_code();
    load_game_code();   // 新 .so/.dll
    // 注意 permanent_arena 没动
    restore_arena(snap);  // 瞬时状态保留,游戏继续
}
```

瞬时 arena 被 save→reload→restore 完整闭环。永久 arena 在 reload 期间不动,新代码直接看到。

Casey 强调一个设计哲学:**最小化"状态"概念**。游戏的"状态"应该清楚分类——永久 vs 瞬时——这样热重载、序列化、调试都能简化。这套二分法贯穿整个 HH 的状态管理。

## 2 · 心智模型

### 类比:工作中转 vs 永久档案

把内存想象成办公室:

- **永久档案柜**:员工档案、合同、合规文件——重要,不能丢
- **工作桌**:今天的待办、便签、草稿——下班清空
- **会议室白板**:会议记录、临时讨论——会议结束擦掉

热重载 = 办公室装修。装修时:

- 永久档案柜**不动**(保留)
- 工作桌**拍照存档**(save),装修完后**摆回原样**(restore)
- 会议室白板**直接擦掉**(reset)

这是今天"选择性恢复"的语义——不同区域不同对待。

### 严谨原理:为什么分两类就够

你可能会问:为什么不细分成 N 类(配置、关卡、玩家、AI、渲染、物理)?

工程经验:**类别越多,管理的认知负担越大**。Casey 的二分法(永久 vs 瞬时)覆盖 90% 场景:

- 永久类:从磁盘加载的资源、玩家档案、配置——所有"如果丢就要重新加载"的
- 瞬时类:帧内计算、临时缓冲、AI 决策——所有"丢了重新算就行"的

剩下 10% 用"多 arena"解决——给每个特殊场景开单独的 arena,各自有 flags。比如:

- `audio_arena`:音频缓冲,瞬时但需要低延迟
- `network_arena`:网络包,瞬时但需要序列化
- `script_arena`:Lua/Python 脚本状态,半永久(可以热重载但保留)

每个 arena 用 flags 标记行为,restore 时按 flags 选择性应用。

### 数据结构:多 arena + flags

```rust
struct GameState {
    permanent: Arena,      // 永久区(配置、资源)
    transient: Arena,      // 瞬时区(物理、渲染)
    debug: Arena,          // 调试区(profiler、log)

    // 每个 arena 有自己的 flags
}
```

热重载:

```rust
fn hot_reload(state: &mut GameState) {
    let snap = state.transient.save();
    // permanent 不 save,直接保留
    // debug 不 save,直接 reset
    unload_game_code();
    load_game_code();
    state.transient.restore(snap);
    state.debug.reset();
}
```

每个 arena 独立处理,逻辑清晰。

### 为什么不用同一个 arena + "段标签"?

理论上可以在同一 arena 内打"段标签":

```rust
let section1 = arena.mark_section(PERMANENT);
let section2 = arena.mark_section(TRANSIENT);
```

但实现复杂:

- 每次 alloc 都要决定放哪个段
- restore 时要遍历所有块,根据块标签选择保留还是释放
- 块链表变成"段链表",复杂度爆炸

简单方案:**一个 arena 一种 flags**。需要不同 flags 就开多个 arena。这是 Casey 的选择,也是 Unreal / Unity 的做法。

### Rust 表达

```rust
bitflags::bitflags! {
    pub struct ArenaFlags: u32 {
        const PERMANENT = 0x1;
        const TRANSIENT = 0x2;
        const DEBUG     = 0x4;
    }
}

pub struct Arena {
    flags: ArenaFlags,
    // ... 其他字段
}

impl Arena {
    pub fn restore_selective(&self, snap: Snapshot, mask: ArenaFlags) {
        if self.flags.intersects(mask) {
            self.restore(snap);
        }
    }
}
```

`bitflags` crate 是 Rust 标准的 bitflag 工具,生成 `intersects`、`contains`、`insert`、`remove` 方法。我们今天不用 crate,手写一个最小版本。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

主流引擎的状态分类:

- **Unreal**:`UPROPERTY(SaveGame)` 标签——只有这个标签的属性会被序列化,等价于"永久"标记
- **Unity**:`[SerializeField]` 标签——同样语义
- **Bevy**:组件级 `Reflect` trait,决定哪些字段被序列化

Casey 的 arena 级分类比这些粗,但实现简单——不需要反射系统,不需要 per-field 标记。

热重载场景:

- Unity 改 C# 脚本:全部 C# 状态丢(因为 Mono runtime 重启),资源保留
- Unreal 改 C++ 代码:全部重启(包括 C# 部分)
- Unreal 改蓝图:蓝图 VM 状态热重载,数据保留
- Casey HH:瞬时 arena save/restore,永久 arena 保留,代码层 cdylib 重载

Casey 的方案最完整——只有 cdylib 重载,数据全保留。这是手工打造引擎才能做到的精细度。

### 3.2 · 🐧 Linux 系统编程视角

Linux 进程状态有类似的"分类"概念:

- **Text segment(代码段)**:可执行代码,只读,共享
- **Data segment(数据段)**:全局变量,初始化的初始值
- **BSS**:未初始化全局变量(运行时清零)
- **Heap**:malloc 分配,可增长
- **Stack**:函数调用栈,LIFO
- **mmap 区**:文件映射 / 大块匿名内存

每一类有不同的处理方式:

- exec 重载 text
- 启动时初始化 data + bss
- fork 时 COW 复制所有
- 内存压力下 stack 大小可调(rlimit)

Casey 的"永久 vs 瞬时"在游戏引擎层做了类似分类,粒度比 OS 粗(没有 text/data/bss 区分),但概念上等价。

#### /proc/self/smaps 看内存分类

```bash
cat /proc/self/smaps | head -30
# 输出每个内存段的详细分类:
# 00400000-0057b000 r-xp ...     ← 代码段(text)
# 0057c000-0057d000 r--p ...     ← 只读数据
# 0057d000-0057e000 rw-p ...     ← 数据段
# ...
```

操作系统天然分类内存。游戏引擎的 arena 是在 heap / mmap 之上再做一次"应用层分类",让游戏代码不需要懂 OS 细节。

### 3.3 · 🦀 Rust 生态视角

Rust 标准库没有 arena flags 概念。`bitflags` crate 是社区标准:

```rust
[dependencies]
bitflags = "2"
```

但我们今天手写,避免依赖:

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
pub struct ArenaFlags(u32);

impl ArenaFlags {
    pub const PERMANENT: Self = Self(0x1);
    pub const TRANSIENT: Self = Self(0x2);
    pub const DEBUG: Self = Self(0x4);

    pub fn intersects(self, other: Self) -> bool {
        (self.0 & other.0) != 0
    }
}
```

这个手动版本不到 30 行,完全等价于 `bitflags` crate 的功能。

#### 多 arena 在 Rust 里怎么管理

```rust
pub struct Memory {
    pub permanent: Arena,
    pub transient: Arena,
    pub debug: Arena,
}

impl Memory {
    pub fn restore_all_transient(&self, snap: &TransientSnapshot) {
        self.transient.restore(snap.transient);
        // permanent 不动
        self.debug.reset();
    }
}
```

每个 arena 独立,不互相借用——这让多线程更容易(每个线程拿一个 arena,无锁)。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **State partitioning(状态分区)** — 把应用状态按生命周期/性质分类
- **Multi-arena architecture(多 arena 架构)** — 不同 arena 不同用途,主流引擎标配
- **Memory tiering(内存分层)** — 类似 CPU cache L1/L2/L3,不同层不同速度

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 单 arena + flags | 一个 arena,多 flags | 简单场景 | ✅ 今天加 |
| 多 arena(永久 + 瞬时) | 完全独立 arena | 主流做法 | ✅ 也用 |
| per-field 标签 | 每个字段标 SaveGame | 序列化粒度 | 不用,粒度太细 |
| OS 进程级 fork | 整个进程 COW | 单进程隔离 | 不用,太重 |
| 序列化到磁盘 | 完整 dump | 跨重启 | Phase 7 才做 |

### 4.3 下级(内部零件)

- **`ArenaFlags` 位标志** — PERMANENT / TRANSIENT / DEBUG
- **`restore_selective` API** — 按 mask 选择
- **多 arena 结构** — `Memory { permanent, transient, debug }`
- **不变量** — 同 flags 的 arena 才能 save/restore

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不直接给每个 arena 加一个 `is_permanent: bool`,而用 flags 位标志?

**参考解答**:

1. **可扩展**:flags 可以加新类型(DEBUG、NETWORK、SCRIPT),bool 只有两态
2. **可组合**:`PERMANENT | DEBUG` 表达"既是永久又是调试",bool 不行
3. **mask 语义**:restore 时传 mask 批量选择,API 优雅
4. **C 历史**:C 程序员习惯位运算,性能可预测
5. **零开销**:u32 = 4 字节,和 bool(1 字节)接近但功能更强

### Lv2 · 动手实践

**题**:在 day343 的 arena 上加 flags,实现:

- `ArenaFlags` 位标志结构
- `restore_selective(snap, mask)` 按 mask 选择是否 restore
- 多个 arena,每个有不同 flags
- 一个 `Memory` 结构持有多个 arena

测试:permanent arena 在 restore_selective(PERMANENT mask)时不动,transient arena 动。

完成标准:断言通过。

**参考解答**:

```rust
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub struct ArenaFlags(u32);

impl ArenaFlags {
    pub const NONE: Self = Self(0);
    pub const PERMANENT: Self = Self(0x1);
    pub const TRANSIENT: Self = Self(0x2);
    pub const DEBUG: Self = Self(0x4);

    pub fn intersects(self, other: Self) -> bool {
        (self.0 & other.0) != 0
    }

    pub fn contains(self, other: Self) -> bool {
        (self.0 & other.0) == other.0
    }

    pub fn insert(&mut self, other: Self) {
        self.0 |= other.0;
    }
}

// 简化 arena,只演示 flags 概念
pub struct Arena {
    pub flags: ArenaFlags,
    used: std::cell::Cell<usize>,
}

impl Arena {
    pub fn new(flags: ArenaFlags) -> Self {
        Self { flags, used: std::cell::Cell::new(0) }
    }

    pub fn alloc(&self, n: usize) {
        self.used.set(self.used.get() + n);
    }

    pub fn used(&self) -> usize { self.used.get() }

    pub fn save(&self) -> usize { self.used.get() }

    pub fn restore(&self, saved_used: usize) {
        self.used.set(saved_used);
    }

    pub fn restore_selective(&self, saved_used: usize, mask: ArenaFlags) {
        if self.flags.intersects(mask) {
            self.restore(saved_used);
        }
    }
}

pub struct Memory {
    pub permanent: Arena,
    pub transient: Arena,
    pub debug: Arena,
}

impl Memory {
    pub fn new() -> Self {
        Self {
            permanent: Arena::new(ArenaFlags::PERMANENT),
            transient: Arena::new(ArenaFlags::TRANSIENT),
            debug: Arena::new(ArenaFlags::DEBUG),
        }
    }
}

fn main() {
    let mem = Memory::new();

    // 在每个 arena 分配点东西
    mem.permanent.alloc(100);
    mem.transient.alloc(200);
    mem.debug.alloc(50);

    let perm_snap = mem.permanent.save();
    let trans_snap = mem.transient.save();

    // 继续分配
    mem.permanent.alloc(50);
    mem.transient.alloc(100);
    println!("Before restore: perm={}, trans={}, debug={}",
             mem.permanent.used(), mem.transient.used(), mem.debug.used());

    // 选择性 restore:只恢复 TRANSIENT 标记的
    mem.permanent.restore_selective(perm_snap, ArenaFlags::TRANSIENT);
    mem.transient.restore_selective(trans_snap, ArenaFlags::TRANSIENT);
    println!("After restore TRANSIENT mask: perm={}, trans={}, debug={}",
             mem.permanent.used(), mem.transient.used(), mem.debug.used());

    // permanent 没动(它不是 TRANSIENT),transient 动了
    assert_eq!(mem.permanent.used(), 150);  // 100 + 50
    assert_eq!(mem.transient.used(), 200);  // 回到 save 时

    println!("OK");
}
```

## 8 · Rust / Arch 落地代码

完整 demo:

```rust
// src/main.rs
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub struct ArenaFlags(u32);

impl ArenaFlags {
    pub const NONE: Self = Self(0);
    pub const PERMANENT: Self = Self(0x1);
    pub const TRANSIENT: Self = Self(0x2);
    pub const DEBUG: Self = Self(0x4);

    pub fn intersects(self, other: Self) -> bool { (self.0 & other.0) != 0 }
    pub fn contains(self, other: Self) -> bool { (self.0 & other.0) == other.0 }
    pub fn insert(&mut self, other: Self) { self.0 |= other.0; }
    pub fn remove(&mut self, other: Self) { self.0 &= !other.0; }
}

pub struct Arena {
    pub flags: ArenaFlags,
    used: std::cell::Cell<usize>,
}

impl Arena {
    pub fn new(flags: ArenaFlags) -> Self {
        Self { flags, used: std::cell::Cell::new(0) }
    }
    pub fn alloc(&self, n: usize) { self.used.set(self.used.get() + n); }
    pub fn used(&self) -> usize { self.used.get() }
    pub fn save(&self) -> usize { self.used.get() }
    pub fn restore(&self, saved_used: usize) { self.used.set(saved_used); }
    pub fn restore_selective(&self, saved_used: usize, mask: ArenaFlags) {
        if self.flags.intersects(mask) {
            self.restore(saved_used);
        }
    }
}

pub struct Memory {
    pub permanent: Arena,
    pub transient: Arena,
    pub debug: Arena,
}

impl Memory {
    pub fn new() -> Self {
        Self {
            permanent: Arena::new(ArenaFlags::PERMANENT),
            transient: Arena::new(ArenaFlags::TRANSIENT),
            debug: Arena::new(ArenaFlags::DEBUG),
        }
    }

    pub fn hot_reload_snapshot(&self) -> (usize, usize, usize) {
        (self.permanent.save(), self.transient.save(), self.debug.save())
    }

    pub fn hot_reload_restore(&self, snap: (usize, usize, usize)) {
        // PERMANENT 不动
        self.transient.restore(snap.1);
        self.debug.restore(snap.2);  // DEBUG 在热重载时也 reset
    }
}

fn main() {
    let mem = Memory::new();

    mem.permanent.alloc(1000);   // 玩家档案
    mem.transient.alloc(500);    // 当前物理状态
    mem.debug.alloc(200);        // profile 数据

    let snap = mem.hot_reload_snapshot();

    // 继续游戏
    mem.permanent.alloc(50);     // 玩家继续升级(应该保留)
    mem.transient.alloc(100);    // 物理推进(应该恢复)
    mem.debug.alloc(50);         // profile 累积(应该恢复)

    println!("Before hot reload: perm={}, trans={}, debug={}",
             mem.permanent.used(), mem.transient.used(), mem.debug.used());

    // 模拟热重载
    mem.hot_reload_restore(snap);

    println!("After hot reload:  perm={}, trans={}, debug={}",
             mem.permanent.used(), mem.transient.used(), mem.debug.used());

    // permanent 保留(玩家升级没丢),transient/debug 回到 snapshot
    assert_eq!(mem.permanent.used(), 1050);
    assert_eq!(mem.transient.used(), 500);
    assert_eq!(mem.debug.used(), 200);
    println!("Hot reload: state preserved correctly");
}
```

```
After hot reload:  perm=1050, trans=500, debug=200
Hot reload: state preserved correctly
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
