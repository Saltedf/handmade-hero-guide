
# Day 395 · 基础多网格光照向下迭代

> 昨天的"向上迭代"(coarse-to-fine)解决了**长距离传播**——粗网格快速传播全局光照。但只有"向上"不够:细网格里的**局部高频细节**(角落阴影、边缘渐变)无法在粗网格表达,会丢失。今天 Casey 加**向下迭代**(fine-to-coarse),构成完整的 **V-cycle**。

## 0 · 为什么要有这一天

Day 394 的向上迭代从粗到细,得到全场景的近似光照。但有个问题:**粗网格的解"过平滑"**——细网格继承了粗的平滑度,**局部细节丢失**。

举例:角落和缝隙应该很暗(因为环境光被遮挡),但粗网格的体素太大,把"角落"和"开阔地"合并为一个体素,得到中间值(半亮)。插值到细网格后,角落还是半亮,不真实。

**向下迭代**的思路:

1. 在细网格做几次迭代,得到"接近真实"的解 L_fine
2. 计算细网格的"局部细节"(L_fine - L_smooth,即高频部分)
3. 把这个细节"注入"回粗网格(让粗网格"知道"细网格有什么细节)
4. 粗网格再做几次迭代,基于新信息精修
5. 把粗网格的解再插值回细网格

这是 **V-cycle 的 down 部分**。和昨天的 up 结合,得到完整 V-cycle:

```
细 →(pre-smooth)→ 残差 → 粗 →(solve)→ 校正 → 细 →(post-smooth)
```

完整 V-cycle 是 multigrid 的标准做法,但实现复杂。Casey 的简化版本:

- **Up**:粗迭代 → 插值到细 → 细迭代(Day 394)
- **Down**:细迭代 → 平均到粗 → 粗迭代 → 插值回细(Day 395)

**今天的产出**:V-cycle 完整,光照质量提升——角落和边缘有更准确的明暗变化。

心理锚点:看完今天,你能(1)解释 V-cycle 的两个方向;(2)实现 restriction(细 → 粗平均);(3)理解为什么需要"残差"概念;(4)调试 multigrid 的收敛性。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 流程:

1. **承认 Day 394 局限**:向上迭代得到的解"过平滑",局部细节丢失。
2. **引入残差(residual)**:`r = b - A × x`,其中 b 是目标(emission),A × x 是当前估计。残差告诉你"还差多少"。

4. **粗网格解残差**:在粗网格上迭代解 A × e = r,得到误差 e。
5. **插值校正**:把 e 插值回细网格,加到 L_fine。
6. **post-smoothing**:细网格再迭代几次,平滑。
7. **跑 demo**:对比 Day 394 和 Day 395 的结果,角落更暗了,细节更丰富

## 2 · 心智模型

### 类比:大炮打蚊子 + 显微镜

想象你修一张 1000 万像素的照片,有灰尘(局部瑕疵)和模糊(全局问题)。

**朴素方法**:逐像素修。慢(1000 万次)。

**向上方法**(Day 394):先缩小到 1000 像素,修模糊,再放大回 1000 万。模糊修好了,但灰尘还在(放大让小瑕疵"消失"或"放大")。

**向下方法**(今天):放大后修模糊,但发现"角落还有些不该有的灰尘"——这种细节在缩小的照片里看不到。**所以再缩小一次,告诉小图"角落有灰尘"**(残差传递),小图修这个灰尘,再放大回来,灰尘被正确处理。

完整 multigrid 是**多尺度协同**:大尺度处理大问题,小尺度处理小问题,信息在两个尺度间双向流动。

### 严谨原理:残差(Residual)

求解线性系统 `A × x = b`(A 是反射矩阵,x 是光照,b 是 emission)。

迭代法产生估计 x^(k)。**残差**:`r^(k) = b - A × x^(k)`。

含义:**用当前估计算出的 A × x^(k) 和目标 b 的差距**。如果 r = 0,方程被精确求解。如果 r > 0,还需要迭代。

**用残差改进迭代**:

- 不是直接迭代 `x^(k+1) = ... x^(k) ...`
- 而是迭代**误差** `e = x_exact - x^(k)`
- 误差满足:`A × e = r`(因为 A × x_exact = b,A × x^(k) ≈ b - r)

**multigrid 的核心洞察**:**残差是低频(光滑)+ 高频(细节)**。粗网格能解低频,细网格能解高频。把残差分两个尺度处理。

### 限制(Restriction,细 → 粗)

把细网格的残差"投影"到粗网格。

**简单方法**:粗网格点取对应的细网格点的值(下采样)。

**完整三线性**:粗网格点取**对应细网格 8 个邻居**的加权平均。

```
粗网格点 (i, j, k) 对应细网格点 (2i, 2j, 2k)
粗网格值 = (1/8) × sum of 8 neighbors in fine grid
```

代码:

```rust
fn restrict(fine: &[f32], fine_dims: usize, coarse: &mut [f32], coarse_dims: usize) {
    for k in 0..coarse_dims {
        for j in 0..coarse_dims {
            for i in 0..coarse_dims {
                let fi = 2 * i;
                let fj = 2 * j;
                let fk = 2 * k;
                let mut sum = 0.0;
                let mut count = 0;
                for dk in 0..=1 {
                    for dj in 0..=1 {
                        for di in 0..=1 {
                            let ni = fi + di;
                            let nj = fj + dj;
                            let nk = fk + dk;
                            if ni < fine_dims && nj < fine_dims && nk < fine_dims {
                                sum += fine[nk * fine_dims * fine_dims + nj * fine_dims + ni];
                                count += 1;
                            }
                        }
                    }
                }
                coarse[k * coarse_dims * coarse_dims + j * coarse_dims + i] = sum / count as f32;
            }
        }
    }
}
```

### 完整 V-cycle

```rust
fn v_cycle(grid: &mut Vec<f32>, dims: usize, emission: &[f32]) {
    if dims <= 16 {
        // 最粗网格,直接迭代到收敛
        for _ in 0..10 {
            jacobi_step(grid, dims, emission);
        }
        return;
    }

    // 1. Pre-smoothing
    for _ in 0..3 { jacobi_step(grid, dims, emission); }

    // 2. 计算残差 r = emission - A × x
    let residual = compute_residual(grid, dims, emission);

    // 3. Restrict 残差到粗一级网格
    let coarse_dims = dims / 2;
    let mut coarse_residual = vec![0.0; coarse_dims.pow(3)];
    restrict(&residual, dims, &mut coarse_residual, coarse_dims);

    // 4. 递归 V-cycle(粗网格解 A × e = r)
    let mut coarse_error = vec![0.0; coarse_dims.pow(3)];
    v_cycle(&mut coarse_error, coarse_dims, &coarse_residual);

    // 5. Interpolate error 回细网格,加到 x
    let mut fine_error = vec![0.0; dims.pow(3)];
    upsample(&coarse_error, &mut fine_error, dims);
    for i in 0..grid.len() {
        grid[i] += fine_error[i];
    }

    // 6. Post-smoothing
    for _ in 0..3 { jacobi_step(grid, dims, emission); }
}
```

这是经典 multigrid V-cycle。

### 简化版(Casey 用)

Casey 不做完整 V-cycle,简化为:

```
4. 插值 32³ → 64³
5. 细 64³ 迭代 4 次

7. 中 32³ 再迭代 4 次(基于新信息)
8. Restrict 32³ → 16³
9. 粗 16³ 再迭代 4 次

```

简化版没有显式的残差计算,用"双向插值 + 迭代"近似 V-cycle 的效果。

### 收敛性验证

如何知道 multigrid 收敛了?

**残差范数**:`||r|| = sqrt(sum of r_i²)`。每次 V-cycle 后,残差应该减少 0.1-0.3(典型)。10 次 V-cycle 应该让残差减少到原值的 1e-10(机器精度)。

如果残差**不减少**,可能:

- 迭代不收敛(松弛因子太大)
- 边界条件错(光照泄漏)
- 实现有 bug

**Casey 调试**:加 debug 输出,每帧打印残差范数,观察下降趋势。

### GPU 实现的复杂度

完整 V-cycle 在 GPU 上:

- 每个 grid level 一个 image3D
- Pre/post-smoothing 各 1 个 compute shader dispatch
- Restrict 1 个 dispatch
- Prolong(interpolate)1 个 dispatch
- 多级递归 V-cycle

GPU 优势:每级网格并行 dispatch,几百微秒一级,总几毫秒一帧。

Casey 用简化版,**3 级网格,几毫秒一帧**,可接受。

### 3.4 · 🦀 Rust 生态视角

Rust 实现完整 V-cycle:

```rust
pub struct MultigridSolver {
    grids: Vec<Vec<f32>>,  // 多级网格
    dims: Vec<usize>,
}

impl MultigridSolver {
    pub fn new(finest_dims: usize, levels: usize) -> Self {
        let mut grids = Vec::new();
        let mut dims = Vec::new();
        let mut d = finest_dims;
        for _ in 0..levels {
            grids.push(vec![0.0; d.pow(3)]);
            dims.push(d);
            d /= 2;
        }
        Self { grids, dims }
    }

    pub fn v_cycle(&mut self, level: usize, emission: &[f32]) {
        let dims = self.dims[level];
        if level == self.dims.len() - 1 {
            // 最粗,直接迭代
            for _ in 0..10 {
                jacobi_step(&mut self.grids[level], dims, emission);
            }
            return;
        }
        // Pre-smooth
        for _ in 0..3 {
            jacobi_step(&mut self.grids[level], dims, emission);
        }
        // Restrict residual
        let residual = compute_residual(&self.grids[level], dims, emission);
        let coarse_dims = self.dims[level + 1];
        let mut coarse_residual = vec![0.0; coarse_dims.pow(3)];
        restrict(&residual, dims, &mut coarse_residual, coarse_dims);
        // Recursive V-cycle on coarse
        self.v_cycle(level + 1, &coarse_residual);
        // Prolong coarse error to fine
        let mut fine_error = vec![0.0; dims.pow(3)];
        upsample(&self.grids[level + 1], &mut fine_error, dims);
        for i in 0..self.grids[level].len() {
            self.grids[level][i] += fine_error[i];
        }
        // Post-smooth
        for _ in 0..3 {
            jacobi_step(&mut self.grids[level], dims, emission);
        }
    }
}
```

**关键**:

- `grids` 多级,每级 dims 一半
- `v_cycle` 递归
- 边界条件:最粗 level 直接迭代

### 历史演化

- **1970s**:Brandt multigrid
- **1980s**:Hierarchical basis multigrid
- **1990s**:Algebraic multigrid(AMG)
- **2000s**:GPU multigrid
- **2010s+**:Deep learning + multigrid(神经 PDE 求解器)

### V-cycle vs W-cycle

- **V-cycle**:每级 recursion 进入一次下一级
- **W-cycle**:每级 recursion 进入两次下一级(更稳定但更慢)
- **Full multigrid(FMG)**:嵌套 V-cycle,从最粗开始

工业界 V-cycle 够用,W-cycle 用于难解的问题。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:V-cycle 的 pre-smoothing 和 post-smoothing 各自的作用?

**参考解答**:

**Pre-smoothing**(进入粗网格前的迭代):**消除高频误差**。在细网格上,jacobi 迭代"擅长"消除高频(相邻体素差异大),但"不擅长"消除低频(全局模式)。Pre-smoothing 把高频消除,留下的低频误差通过 restriction 传到粗网格,粗网格解决低频。

**Post-smoothing**(离开粗网格后的迭代):**消除插值产生的高频伪影**。粗网格的解插值到细网格时,可能在边界产生"锯齿"(高频噪声)。Post-smoothing 把这些噪声消除。

**总结**:Pre-smoothing "准备"细网格的低频误差传给粗网格,Post-smoothing "清理"粗网格插值回来的噪声。两者配合让 V-cycle 收敛快。

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
