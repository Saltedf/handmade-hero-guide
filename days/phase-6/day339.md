
# Day 339 · 调试粒子相机偏移运动

> 昨天把粒子从世界坐标切到模拟坐标,理论上一切美好。但 Casey 一跑游戏,粒子像被相机粘住——相机动,粒子跟着动。这是个经典的"相对坐标系"bug,今天的全部内容是 Casey 如何定位、复现、修复。

## 0 · 为什么要有这一天

写代码不是难的部分,**调试**才是。Casey 在 Day 338 的实现里犯了一个微妙错误:`sim_pos -= delta` 写成了 `sim_pos += delta`。一行代码,符号反了。但症状不明显——粒子看起来"在飞",只是飞得不正常。

为什么这个 bug 难发现?

1. **没有崩溃**:程序正常运行,只是粒子位置错。
2. **症状模糊**:粒子在屏幕上,看起来在动——是正常运动还是 bug?
3. **复现条件**:相机必须移动,粒子和相机都在视野里——大部分时间静止时一切正常。
4. **多个可能原因**:速度算错?方向算错?sim_origin 算错?delta 算错?

业界说法:**最难调的 bug 是"看起来在动"**——程序不崩,但行为微妙错误。这种 bug 需要"系统性排查"而不是"插个 print 看一眼"。

今天 Casey 给你做一次完整的 debug 演示,从"复现 bug"到"二分定位"到"找到根因"再到"修复 + 回归测试"。这是 Casey 在 HH 里少数几集 debug 实战,极其珍贵。

心理锚点:今天之后你能用 Casey 的 debug 方法系统性排查任何"微妙行为错误"——不只是粒子,任何代码。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑 Day 338 的代码,看到粒子"跟着相机走"。他立刻知道是 sim space 实现有问题。调试过程:

1. **复现**:让相机明显移动(用 debug overlay 强制相机走一段轨迹),观察粒子
2. **观察**:粒子在屏幕上的位置变化和相机移动方向**同向**——预期是"不动"(模拟空间反向偏移应该抵消)
3. **二分**:把粒子数减到 1,只看一颗。问题依然存在,说明不是"批量错误"
4. **打印**:在 `recenter` 前后打印粒子的 sim_pos 和 world_pos
5. **看数据**:发现 sim_pos 在 recenter 后变**大**,而不是变小
6. **检查公式**:`world = sim_pos + sim_origin`。recenter 后 sim_origin 变大,sim_pos 应该变小,world 才不变。但 sim_pos 变大了。
7. **看代码**:`for p in &mut sim_pos { *p = p.add(delta); }`——加号!应该是减号
8. **修复**:`*p = p.sub(delta);`
9. **回归测试**:跑游戏,粒子不再被相机拖走
10. **加 debug assertion**:每帧检查 |world_pos - expected_world_pos| < epsilon

Casey 还顺手发现了第二个 bug:粒子死亡时 swap-remove 改变了数组顺序,但活粒子计数没同步,导致部分粒子被"重复更新"。修复后行为正确。

## 2 · 心智模型

### 类比:侦探破案

Debug 像侦探破案:嫌疑人(可能 bug)、证据(运行时数据)、不在场证明(代码逻辑)、作案动机(为什么这么写)。

侦探不会一上来就抓人,**先收集证据**:犯罪现场什么样子?目击者说什么?监控拍到什么?**等所有证据都指向同一嫌疑人**,才动手。

Debug 同理:不要"猜一行改一行试一下"——这是新手陷阱。专业 debug:

1. **稳定复现**:100% 重现 bug 的最小步骤
2. **缩小范围**:二分搜索找出"哪个函数、哪个循环、哪行代码"
3. **观察状态**:打印关键变量,对比"预期 vs 实际"
4. **形成假设**:基于证据,猜测根因
5. **验证假设**:改一行,看 bug 是否消失
6. **回归测试**:加测试,确保 bug 永不复活

### 系统化 debug 的方法论

**第 1 步:复现**

bug 不能稳定复现 = bug 不能修。第一步永远是"找到 100% 重现路径"。

```rust
// 测试代码:强制相机移动
let camera_path = vec![
    Vec3::new(0.0, 0.0, 0.0),
    Vec3::new(10.0, 0.0, 0.0),
    Vec3::new(20.0, 0.0, 0.0),
    Vec3::new(30.0, 0.0, 0.0),
];
for new_pos in camera_path {
    game.camera.pos = new_pos;
    game.update();
    game.render();
    // 观察:粒子相对世界坐标系应该不动
}
```

如果只能"偶尔复现",往往有未初始化内存 / 数据竞争 / 多线程同步问题。Casey Day 339 的 bug 是确定性的,容易复现。

**第 2 步:最小化**

把场景缩小到最小:1 颗粒子、相机走直线、忽略渲染。问题还在,说明根因在核心逻辑。

**第 3 步:观察状态**

在关键点打印变量:

```rust
fn recenter(&mut self, new_origin: Vec2) {
    let delta = new_origin.sub(self.sim_origin);
    println!("BEFORE: sim_origin={:?} delta={:?}", self.sim_origin, delta);
    for (i, p) in self.sim_pos.iter_mut().enumerate() {
        println!("  particle[{}] sim_pos before = {:?}", i, p);
        *p = p.add(delta);  // BUG HERE
        println!("  particle[{}] sim_pos after  = {:?}", i, p);
    }
    self.sim_origin = new_origin;
    println!("AFTER: sim_origin={:?}", self.sim_origin);
}
```

输出:

```
BEFORE: sim_origin=Vec2{x:0,y:0} delta=Vec2{x:10,y:0}
  particle[0] sim_pos before = Vec2{x:1.5,y:0.0}
  particle[0] sim_pos after  = Vec2{x:11.5,y:0.0}    ← 错!应该 -10 = -8.5
AFTER: sim_origin=Vec2{x:10,y:0}

World pos after: sim_pos + sim_origin = (11.5 + 10) = 21.5
但预期不变 = 1.5 + 0(旧)→ 1.5 + 0(新)+ ??? 错位
```

**第 4 步:形成假设**

数据告诉:sim_pos 在 recenter 后变大,sim_origin 也变大,所以 world = sim_pos + sim_origin 变得**更大**——粒子被往相机移动方向拉。

**第 5 步:验证**

把 `+=` 改成 `-=`:

```rust
*p = p.sub(delta);
```

跑测试,粒子位置稳定。假设验证。

**第 6 步:回归测试**

加测试,保证以后不会有人再写错:

```rust
#[test]
fn test_recenter_preserves_world_pos() {
    let mut ps = ParticleSystem::new();
    ps.sim_origin = Vec2::new(0.0, 0.0);
    ps.sim_pos = vec![Vec2::new(1.5, 0.0)];

    let world_before = ps.sim_pos[0].add(ps.sim_origin);
    ps.recenter(Vec2::new(10.0, 0.0));
    let world_after = ps.sim_pos[0].add(ps.sim_origin);

    assert!((world_before.sub(world_after).x).abs() < 1e-5);
}
```

### 为什么 + 和 - 的 bug 这么常见?

**类型不安全**:`f32 - f32` 和 `f32 + f32` 类型相同,编译器不警告。Rust 的 newtype(`WorldPos` vs `SimPos`)能解决部分,但 `Vec2 → Vec2` 仍可加减。

**直觉误导**:"相机走 +10,粒子也走 +10"在物理世界是对的(人在车内看车外)——但在 sim space 里"模拟原点是相机",原点变了,粒子相对原点的位置反向变。

**符号歧义**:`delta` 可能是 `new - old`,也可能是 `old - new`。Casey 写代码时心里想的 delta 定义可能和实际不同。

防御性编程:**用语义清晰的函数名**:`apply_origin_shift` 而不是 `+= delta`,函数体内固定方向。

### 第二个 bug:swap-remove 顺序问题

Casey 还发现:`kill_particle(i)` 用 swap-remove 把末尾元素搬到位置 i,但循环里 `i += 1` 跳过了搬来的粒子。结果:每帧有几颗粒子被"跳过更新",看起来运动不连续。

```rust
// 错误:for 循环 i 永远递增
for i in 0..self.particles.len() {
    self.update_particle(i);
    if self.particles[i].dead() {
        self.kill(i);  // swap-remove:把末尾搬到 i
        // 下一轮 i+1,但 i 位置是新搬来的粒子,被跳过!
    }
}

// 正确:while 循环,只在没死时 i++
let mut i = 0;
while i < self.particles.len() {
    self.update_particle(i);
    if self.particles[i].dead() {
        self.kill(i);
        // 不 i++,因为 kill 把新粒子搬到 i,需要重新处理
    } else {
        i += 1;
    }
}
```

这种 bug 在 day336 应该已经发现,但 Casey 在 Day 339 因为加了 sim space 才注意到——粒子的 sim_pos 在 swap-remove 后被错误地参与了下一轮 recenter,导致累积偏移。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发 debug 的特点是**状态多、并行多、可视化必要**。

**专业工具**:

- **printf debugging**:Casey 主要用这个,简单粗暴
- **debug overlay**:在游戏内画文字/线条,实时看状态
- **frame debugger**:逐帧回放(FIFO 记录所有状态)
- **memory snapshot**:某时刻内存快照,对比差异
- **logger**:结构化日志,带时间戳和分类
- **profiler**:不只是性能,也能看到调用栈

Casey 在 HH 里大量用 debug overlay(`game_debug.cpp`)。Day 339 他在屏幕一角打印粒子数、sim_origin、第一颗粒子的 sim_pos——实时看到 bug 发生。

**业界 debug 神器**:

- **Pix**(Windows,DirectX):逐帧捕获,看每个 draw call
- **RenderDoc**(跨平台,Vulkan/OpenGL):类似 Pix,开源
- ** Tracy**(跨平台,实时 prof):纳秒级 profiler
- **MTuner**:内存 profiler

Linux 上:`RenderDoc` / `Tracy` 是 Rust 游戏开发者必备。

### 3.2 · 图形学视角

图形 debug 的特殊挑战:**bug 表现是"像素错位"或"颜色错"**——你看到结果错,但不知道哪行代码错。

经典图形 bug:

- **黑色屏幕**:shader 编译失败 / framebuffer 没清 / 深度测试错
- **拉伸的几何**:投影矩阵错 / viewport 错
- **闪烁**:z-fighting(深度冲突)/ 双 buffer 同步错
- **粒子被相机拖**(今天):sim space 错
- **远距离闪烁**:f32 精度
- **alpha blend 错**:渲染顺序 / blend mode

工具:

- **frame debugger**:看一次 draw call 的输入(vertex/index/texture/shader)和输出(framebuffer 状态)
- **shader printf**(GLSL 4.6+):在 shader 里打印
- **glGetError() / GL_DEBUG_OUTPUT**:OpenGL 错误回调

Rust 的 `glow` / `wgpu` crate 都有 debug callback 接口。生产代码必开。

### 3.3 · Linux 系统编程视角

Linux 上的 debug 工具链:

**进程级**:

- **gdb**:断点、单步、watch 变量、调用栈
- **lldb**:LLVM 版 gdb,Clang 默认
- **strace**:看 syscall
- **ltrace**:看库函数调用

**内存级**:

- **valgrind --tool=memcheck**:未初始化内存、内存泄漏、悬垂指针
- **valgrind --tool=helgrind / drd**:数据竞争
- **AddressSanitizer**(`-fsanitize=address`):编译期注入,运行时检查越界、释放后访问
- **MemorySanitizer**:未初始化内存
- **ThreadSanitizer**:数据竞争

**Rust 特定**:

- **miri**:Rust 解释器,检查 unsafe 代码 UB
- **cargo-clippy**:lint
- **cargo-nextest**:更好的测试 runner

Casey 在 Windows 用 Visual Studio debugger。Linux 上等价是 gdb + vscode 集成,或 rr(record and replay)。

### 3.4 · Rust 生态视角

Rust 编译期消除大部分 bug:

- **空指针**:Option<T>
- **悬垂引用**:lifetime
- **数据竞争**(单线程也安全):Send / Sync
- **整数溢溢出**(debug 模式):panic
- **未初始化内存**:所有类型必须初始化

但消除不了:

- **逻辑错误**:`+= delta` vs `-= delta`
- **精度问题**:f32 误差
- **API 误用**:`swap_remove` 后迭代
- **并发竞争**(unsafe 代码)

**Rust debug 工具链**:


```rust
use tracing::{info, debug, instrument};

#[instrument(skip(self))]
fn recenter(&mut self, new_origin: Vec2) {
    let delta = new_origin.sub(self.sim_origin);
    debug!(?delta, old_origin=?self.sim_origin, "recenter");
    for (i, p) in self.sim_pos.iter_mut().enumerate() {
        debug!(i, before=?*p, "particle sim_pos");
        *p = p.sub(delta);
        debug!(i, after=?*p, "particle sim_pos");

    self.sim_origin = new_origin;

```

## 4 · 认知地图

### 4.1 上级

- **软件调试方法论** —— 系统化定位 bug 的科学方法

## 5 · 对照与变奏

### Debug 不同种类 bug 的策略

**Crash bug**(段错误、panic):
- 用 gdb 看 backtrace
- 用 ASan 看具体原因
- 简单:找根因通常 5 分钟

**Memory bug**(泄漏、悬垂):
- valgrind / ASan
- 简单:工具直接指出

**Performance bug**(慢):
- perf / flamegraph
- 中等:需要理解 hot path

**Logic bug**(今天这种):
- printf / log / overlay
- 困难:没人告诉你哪里错

**Race condition**:
- TSan / Helgrind
- 极难:可能千分之一概率触发

### Debug 工具的演化

- **1970s**:printf + core dump
- **1980s**:gdb 出现
- **1990s**:可视化 debugger(Visual Studio)
- **2000s**:valgrind / ASan / TSan
- **2010s**:分布式 tracing(OpenTelemetry / Jaeger)
- **2020s**:AI 辅助 debug(GitHub Copilot)

### Casey 的 debug 风格

Casey 在 HH 里几乎只用:

1. printf / DebugLog
2. 游戏内 debug overlay
3. 注释代码二分

不用 gdb / valgrind(他认为这些"侵入式"——你要停下程序才能看)。Casey 喜欢"实时观察":程序在跑,他在屏幕一角看数据。

这种方法对游戏开发特别合适:游戏 bug 很多是"动态行为",停下就消失了。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 调试时为什么"先复现,再缩小范围"?直接读代码不能找出 bug 吗?

**参考解答**:**读代码找 bug 适合简单、最近的代码改动**。如果改动多、跨多文件、复杂逻辑,读代码耗时且不可靠——你会"看自己写的代码,觉得没问题"。

复现 + 缩小范围的好处:
1. **客观**:程序在跑,数据是真实状态,不是你想的样子
2. **二分高效**:每次缩小一半范围,10 次缩小到 1/1024,大代码库也能定位
3. **回归测试基础**:稳定复现路径 = 自动化测试用例

读代码作为**辅助**:复现后,你已经知道"大概是哪里",再读代码细节找具体行。

### Lv2 · 动手实践

**题**:实现一个"故意有 bug"的 sim space 系统(把 `-= delta` 写成 `+= delta`),写一个 debug 程序:

1. 复现:相机移动时粒子也移动
2. 打印 recenter 前后的 sim_pos / world_pos
3. 从输出看出 bug 在 recenter

完成标准:从打印输出能直接看出"sim_pos 错误地变大了"。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, Default)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
}

struct BuggySim {
    sim_pos: Vec<Vec2>,
    sim_origin: Vec2,
}

impl BuggySim {
    fn buggy_recenter(&mut self, new_origin: Vec2) {
        let delta = new_origin.sub(self.sim_origin);
        println!("\n=== recenter ===");
        println!("delta = {:?}", delta);
        for (i, p) in self.sim_pos.iter_mut().enumerate() {
            println!("[{}] sim_pos before = {:?}", i, p);
            // BUG: 应该 -= delta,这里写成 +=
            *p = p.add(delta);
            println!("[{}] sim_pos after  = {:?}", i, p);
        }
        self.sim_origin = new_origin;
        println!("sim_origin = {:?}", self.sim_origin);
    }

    fn world_pos(&self, i: usize) -> Vec2 {
        self.sim_pos[i].add(self.sim_origin)
    }
}

fn main() {
    let mut sim = BuggySim {
        sim_pos: vec![Vec2::new(5.0, 0.0)],
        sim_origin: Vec2::new(0.0, 0.0),
    };
    println!("Initial world_pos[0] = {:?}", sim.world_pos(0));

    // 相机走 +10 X
    sim.buggy_recenter(Vec2::new(10.0, 0.0));
    println!("After recenter, world_pos[0] = {:?}", sim.world_pos(0));
    println!("Expected (粒子不动) = Vec2{{x: 5.0, y: 0.0}}");

    // 检查偏移
    let drift = sim.world_pos(0).sub(Vec2::new(5.0, 0.0));
    println!("DRIFT = {:?}  (should be 0)", drift);
}
```

**预期输出**:
```
Initial world_pos[0] = Vec2 { x: 5.0, y: 0.0 }

=== recenter ===
delta = Vec2 { x: 10.0, y: 0.0 }
[0] sim_pos before = Vec2 { x: 5.0, y: 0.0 }
[0] sim_pos after  = Vec2 { x: 15.0, y: 0.0 }
sim_origin = Vec2 { x: 10.0, y: 0.0 }
After recenter, world_pos[0] = Vec2 { x: 25.0, y: 0.0 }
Expected (粒子不动) = Vec2 { x: 5.0, y: 0.0 }
DRIFT = Vec2 { x: 20.0, y: 0.0 }  (should be 0)
```

**如何从输出看出 bug**:
1. sim_pos 从 5 变成 15——变大,但应该是变小(因为 sim_origin 变大了)
2. world_pos 从 5 变成 25——粒子被相机拉走
3. DRIFT = 20,正好是 2 * delta(10),说明 sim_pos 错误地"加"了 delta,应该"减"

**修复**:把 `*p = p.add(delta)` 改成 `*p = p.sub(delta)`,DRIFT 变 0。

```rust
#[derive(Copy, Clone, Debug, Default, PartialEq)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
}

// === 通用接口 ===
trait Recenterable {
    fn recenter(&mut self, new_origin: Vec2);
    fn world_pos(&self, i: usize) -> Vec2;
}

// === BUG 版本 ===
struct BuggySim { sim_pos: Vec<Vec2>, sim_origin: Vec2 }
impl Recenterable for BuggySim {
    fn recenter(&mut self, new_origin: Vec2) {
        let delta = new_origin.sub(self.sim_origin);
        for p in &mut self.sim_pos {
            *p = p.add(delta);  // BUG: 应该 sub
        }
        self.sim_origin = new_origin;
    }
    fn world_pos(&self, i: usize) -> Vec2 {
        self.sim_pos[i].add(self.sim_origin)
    }
}

// === 修复版本 ===
struct FixedSim { sim_pos: Vec<Vec2>, sim_origin: Vec2 }
impl Recenterable for FixedSim {
    fn recenter(&mut self, new_origin: Vec2) {
        let delta = new_origin.sub(self.sim_origin);
        for p in &mut self.sim_pos {
            *p = p.sub(delta);  // FIXED
        }
        self.sim_origin = new_origin;
    }
    fn world_pos(&self, i: usize) -> Vec2 {
        self.sim_pos[i].add(self.sim_origin)
    }
}

// === 通用 debug 工具 ===
fn debug_recenter<R: Recenterable>(sim: &mut R, new_origin: Vec2, label: &str) {
    let world_before: Vec<Vec2> = (0..1).map(|i| sim.world_pos(i)).collect();
    sim.recenter(new_origin);
    let world_after: Vec<Vec2> = (0..1).map(|i| sim.world_pos(i)).collect();
    let drift = world_after[0].sub(world_before[0]);
    println!("[{}] world[0] before={:?} after={:?} drift={:?}",
             label, world_before[0], world_after[0], drift);
}

fn main() {
    // BUG 版本
    let mut buggy = BuggySim {
        sim_pos: vec![Vec2::new(5.0, 0.0)],
        sim_origin: Vec2::new(0.0, 0.0),
    };
    debug_recenter(&mut buggy, Vec2::new(10.0, 0.0), "BUGGY");

    // 修复版本
    let mut fixed = FixedSim {
        sim_pos: vec![Vec2::new(5.0, 0.0)],
        sim_origin: Vec2::new(0.0, 0.0),
    };
    debug_recenter(&mut fixed, Vec2::new(10.0, 0.0), "FIXED");

    // 自动化检查
    println!("\n--- 回归测试 ---");
    let drift_buggy = buggy.world_pos(0).sub(Vec2::new(5.0, 0.0)).x.abs();
    let drift_fixed = fixed.world_pos(0).sub(Vec2::new(5.0, 0.0)).x.abs();
    assert!(drift_buggy > 1.0, "BUGGY 应该有 drift");
    assert!(drift_fixed < 0.001, "FIXED 应该无 drift");
    println!("PASS: Buggy drift={}, Fixed drift={}", drift_buggy, drift_fixed);
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
