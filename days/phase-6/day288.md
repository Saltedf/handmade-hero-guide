# Day 288 · 完成大脑

> 昨天加的 brain 让玩家能动、怪物能追。今天 Casey 把 brain 系统的"毛边"修掉——所有未填 brain 的实体都填上、所有重复代码都抽象、所有 edge case 都处理。**Brain 从"能用"变成"好用"**。

## 0 · 为什么要有这一天

软件工程里有一句俗话:**第一版让代码跑起来,第二版让代码对,第三版让代码快**。Day 286-287 做的是"让代码跑起来",今天做的是"让代码对"。听起来不性感,但这是工业级代码和玩具代码的分水岭。

具体到 brain 系统,跑起来后留了一堆尾巴:
- 有的实体没填 brain,行为退化(怪物不动了,因为它本应是 MonsterChase 但 brain 是 None)
- brain 函数里有些重复代码(三个不同 brain 都算"到目标的距离",粘贴三次)
- brain 函数签名不统一(有的接收 ctx,有的接收 raw player_pos)——加新 brain 时不知道该用哪个版本
- 有些 brain 没处理边界情况(玩家死了怎么办?target 找不到怎么办?)

为什么必须修这些?因为后面 day 291-294 要加 4 种新 brain(蛇、随从、跳跃怪物、手套),如果今天不把基础打牢,加一个新 brain 就要在四个不同地方做相同修改,**散弹枪改动**会指数级增长。今天 Casey 的工作是**防止未来代码腐烂**。

心理锚点:看完今天,你打开 brain 系统的代码,应该觉得"加一个新 brain 5 分钟搞定,没有惊讶"。如果你打开代码还要思考"这个函数该用哪个签名""那个状态该放哪",今天没真正完成。

## 1 · Casey 今天做了什么

Casey 今天的几个关键动作:

1. **审查所有 entity**:每个 Type 都配上正确的 brain——遗漏的补上,错误的修正。
2. **统一 brain 函数签名**:所有 brain 函数都是 `(e: &mut Entity, ctx: &Context, dt: f32)`,不再有特例。
3. **抽公共代码**:三个 brain 都用"朝目标移动"——抽出一个 `seek(e, target_pos, speed)` helper。
4. **处理 edge case**:target_id 找不到时 vel 清零,而不是 panic 或保持旧 vel。
5. **测试每种 brain**:写一个小 demo 验证每种 brain 的行为符合预期。

今天的产出是**brain 系统的稳定版**,为后面加新实体铺好路。

## 2 · 心智模型

### 类比:家具打磨阶段

把 brain 系统想象成做一把椅子。Day 286 设计图纸(enum 结构),Day 287 把零件拼起来(填上函数),今天**Day 288 是打磨**——把毛刺磨掉、刷漆、检查每个螺丝是否拧紧。

打磨不改变椅子的"能坐"功能,但它让椅子**耐久**——能再坐十年而不松动。代码也是一样:**跑起来的代码可能三个月后腐烂,打磨过的代码三年后仍然好用**。

打磨的具体动作是消除"代码气味"(code smells)。什么是代码气味?**任何让你下次改代码时觉得"咦这里怪怪的"的地方**。比如:

- 三个 brain 都用 `(target - pos).normalize() * speed`,这个模式重复三次——气味:重复。
- `brain_player` 接收 `input` 参数,`brain_monster` 接收 `ctx` 参数——气味:签名不统一。
- `monster.brain = None` 时 update 跳过它,但程序没崩溃也没 warning——气味:静默错误。
- Player brain 函数有 30 行,中间还嵌套 if——气味:函数过长。

每个气味单独看不大,但积累起来代码就**难改、难读、难维护**。今天的任务是消除它们。

### 2.1 统一签名:为什么这么较真?

看下面两个签名:

```rust
// 旧版本:不统一
fn brain_player(e: &mut Entity, input: &Input);
fn brain_monster(e: &mut Entity, player_pos: Vec2);
fn brain_snake(e: &mut Entity, dt: f32, rng: &mut Rng);
```

不统一带来三个问题:
1. **调用方痛苦**——update 主循环要为每种 brain 准备不同参数。
2. **加新 brain 痛苦**——你要决定"我的 brain 要哪些参数",每次重写。
3. **测试痛苦**——每个 brain 函数测试都要构造不同参数。

统一签名:

```rust
// 新版本:全部统一
fn brain_player(e: &mut Entity, ctx: &Context, dt: f32);
fn brain_monster(e: &mut Entity, ctx: &Context, dt: f32);
fn brain_snake(e: &mut Entity, ctx: &Context, dt: f32);
```

调用方就是一行:`brain_fn(e, &ctx, dt)`,不管哪个 brain。Context 里包含 input、world、rng、time——任何 brain 都可能用到的"环境信息"。dt 是物理时间,所有 brain 都可能用。

**关键原则**:**函数签名统一,内部用自己需要的部分**。`brain_player` 只用 `ctx.input`,`brain_monster` 只用 `ctx.world`,但签名一致。这是 plugin 架构的核心。

### 2.2 抽 helper:什么时候抽,什么时候不抽?

考虑三个 brain 都有:

```rust
let dir = (target - e.pos).normalize();
e.vel = dir * speed;
```

抽成 helper:

```rust
fn seek(e: &mut Entity, target: Vec2, speed: f32) {
    let d = target - e.pos;
    if d.length() > 1e-3 {
        e.vel = d.normalize() * speed;
    } else {
        e.vel = Vec2::ZERO;
    }
}
```

什么时候该抽 helper?

- **重复 ≥ 3 次** —— 一次抽出来值。
- **逻辑有边界情况**(除零、长度为零)—— 抽出来集中处理,不在每处单独写。
- **未来可能扩展** —— 比如 `seek` 以后可能加"最大转角限制",抽出来后只改一处。

什么时候不抽?

- **重复 < 3 次** —— 抽了反而增加间接层,可读性下降。
- **逻辑细微不同** —— A brain 用 `normalize() * speed`,B brain 用 `normalize() * speed * (1.0 - fatigue)`,看似一样实际不同,强抽出来要加参数,反而复杂。
- **可读性更重要** —— `e.vel = dir * 60.0` 比 `seek(e, target, 60.0)` 直接,虽然长但一眼明白。

Casey 今天抽 `seek` 是合理的,因为三个 brain 用同样的逻辑。但他不会抽 `e.vel = input.dir() * 80.0`——只有 player 用,抽出来无意义。

### 2.3 Edge case:静默错误 vs 显式失败

看下面两段:

**静默错误**:
```rust
fn brain_monster(e: &mut Entity, ctx: &Context, _dt: f32) {
    if let Some(target) = ctx.world.get(e.target_id) {
        let d = target.pos - e.pos;
        e.vel = d.normalize() * 40.0;
    }
    // 如果 target 找不到,e.vel 保持上一帧的值——怪物继续往旧方向走
}
```

**显式处理**:
```rust
fn brain_monster(e: &mut Entity, ctx: &Context, _dt: f32) {
    match ctx.world.get(e.target_id) {
        Some(target) => {
            let d = target.pos - e.pos;
            e.vel = if d.length() > 1e-3 { d.normalize() * 40.0 } else { Vec2::ZERO };
        }
        None => {
            // target 不存在(可能死了),停下来
            e.vel = Vec2::ZERO;
        }
    }
}
```

后者多 5 行,但行为明确:**target 不存在时怪物停**。前者怪物会"幻觉"地继续往旧方向走,玩家看到会觉得 bug。

**原则**:**每个分支都要有明确行为**。`if let Some(...)` 没有显式 else 时,Rust 不报错,但行为是"什么都不做"——这通常是 bug 源。要么 `match` 显式两个臂,要么 `if let Some(...) {} else { /* explicit */ }`。

### 2.4 Brain 是"决策树"不是"动作集"

考虑这个 brain:

```rust
fn brain_player(e: &mut Entity, ctx: &Context, _dt: f32) {
    let mut dir = Vec2::ZERO;
    if ctx.input.left  { dir.x -= 1.0; }
    if ctx.input.right { dir.x += 1.0; }
    if ctx.input.up    { dir.y -= 1.0; }
    if ctx.input.down  { dir.y += 1.0; }
    if dir.length() > 1e-3 {
        dir = dir.normalize();
    }
    e.vel = dir * 80.0;
}
```

注意:这个函数**只决定 vel**,不直接改 pos,不调 audio,不 spawn 粒子。Brain 是**决策器**,不是**执行器**。

为什么这么严格?因为:
- **测试简单** —— 测 brain 只需要给定 input,断言 vel,不依赖 audio/graphics。
- **复用简单** —— brain 可能在不同语境下用(local play、remote play、replay),执行器不同但决策相同。
- **调试简单** —— 出 bug 时只看决策对不对,不用想"是不是音频卡了"。

Casey 的 brain 函数严格遵守:**只算 vel,不碰其他**。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对"打磨阶段"的态度很有趣。**小团队常跳过打磨**(没时间),**大团队有专门的"feature polish"阶段**(每个 milestone 后留 1-2 周打磨)。Valve 的开发流程里,polish 占总时间的 30%——他们相信"打磨是乐趣的来源"。

具体到 brain 系统,工业代码的"耐久"标准:

- 每种 brain 在 10000 帧测试中不崩溃
- brain 函数有单元测试,给定输入断言输出
- 性能 profile 里 brain 总耗时 < 1ms(1000 实体时)
- 加新 brain 不超过 100 行新代码

Casey 在 day 288 做的是前两条——保证 brain 正确、稳定。性能留到 Phase 8。

游戏行业另一个相关概念是 **"code rot"**——代码不维护就慢慢腐烂。每天加新功能、不修旧代码,三个月后你的代码就成了"自己写过的最讨厌的代码"。今天的"打磨"就是反 code rot 的实践。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核里有专门的 **cleanup patch**——开发者定期清理重复代码、统一函数签名、修 edge case。Linus 在邮件列表里多次强调:**新功能可以等,cleanup 不能等**。Linux 能跑 30 年,这是关键。

具体例子:`list_head` 在 Linux 里到处用,早期不同模块有不同实现。Linus 在 2.6 时代强制统一到 `<linux/list.h>`,所有模块用同一套 API。今天看 Linux 源码,所有 list 操作都是 `list_add`、`list_del`、`list_for_each_entry`——签名统一,行为一致。

Casey 今天做的统一 brain 签名,是同一思路的小型版本。

另一个相关:**Linux 的 `goto cleanup` 模式**。错误处理时,Linux 喜欢 `goto out;`,在函数末尾统一 cleanup(释放锁、free 内存)。Rust 用 RAII 自动 cleanup,但精神类似——**所有路径都要明确处理**。

### 3.3 · 🦀 Rust 生态视角

Rust 编译器强制帮你消除几种"代码气味":

**1. 未处理 enum variant**

```rust
match brain {
    Brain::Player => { ... }
    Brain::MonsterChase => { ... }
    // 忘了 SnakeWander: 编译报错 non-exhaustive patterns
}
```

加 variant 时所有 match 报错——编译器提醒你修每一处。

**2. 未处理的 Result/Option**

```rust
let x = ctx.world.get(id);  // Option<Entity>
x.pos  // 编译报错:Option<Entity> 没有字段 pos
```

强制你处理 None。

**3. Unused 字段**

```rust
struct Entity {
    pos: Vec2,
    wander_dir: Vec2,  // 编译 warning: never read
}
```

`cargo build` 有 `unused` 警告,帮你发现"加了字段忘了用"。

但 Rust 不强制的是:

- **签名统一** —— Rust 允许你写任意签名,但工程上统一更好。
- **代码重复** —— Rust 不检测"复制粘贴 5 次",需要 `clippy::same_item_push` 等 lint。
- **edge case 显式处理** —— `if let Some()` 没 else 是合法的,你要靠 code review 抓。

Rust 工程师常用 clippy 抓"非编译错误但应该改"的代码:

```bash
cargo clippy -- -W clippy::pedantic
```

Pedantic 模式开 ~270 个 lint,包括:
- `clippy::cognitive_complexity` —— 函数太复杂警告
- `clippy::too_many_arguments` —— 参数太多警告(>6 个)
- `clippy::similar_names` —— 类似变量名(`player_pos` vs `player_pso`)
- `clippy::needless_pass_by_value` —— 不必要的 by-value 传递

工业 Rust 项目 CI 里都开 clippy,这是 Casey"打磨"的 Rust 化版本。

## 5 · 对照与变奏

### 三种"打磨"路径

**路径 A:集中打磨(今天 Casey 做的)**

每天或每个 milestone 留一段时间,专门 cleanup。优点:整体一致性好;缺点:加新功能慢。

**路径 B:持续小修**

每次改代码时,顺手把附近的烂代码改了。优点:代码长期保持干净;缺点:容易跑题(本来要修 bug,结果重构了整个模块)。

**路径 C:Boy Scout Rule**

每次提交前问"代码比我刚来时更干净了吗?"——哪怕只改了一行。优点:温和,不强迫;缺点:依赖个人纪律。

工业实践三种都用。Casey 偏 A+B——day 288 是集中打磨,平时是持续小修。

### Rust clippy 等级对照

| 等级 | 范围 | 影响 |
|---|---|---|
| default | 基础错误(空 match、unused) | 编译器强制 |
| `clippy::correctness` | 逻辑错误 | CI 应开 |
| `clippy::style` | 风格统一 | 推荐开 |
| `clippy::complexity` | 复杂代码 | 推荐开 |
| `clippy::pedantic` | 严格(270+ lint) | 个人项目开 |
| `clippy::restriction` | 极严(disallow some pattern) | 高安全项目开 |

Bevy 等大项目开到 complexity,glium 等小项目开到 pedantic。HH 教学代码建议 style + complexity。

### 历史演化

- **1968**:Dijkstra《Go To Statement Considered Harmful》,首次系统谈代码结构
- **1999**:Martin Fowler《Refactoring》,确立重构为学科
- **2003**:Uncle Bob《Clean Code》,推广"打磨"文化
- **2010s**:Static analyzer(clippy、clang-tidy、golangci-lint)普及
- **2020s**:AI 辅助 cleanup(Copilot、Cursor)

Casey 在 2014 做 HH 时手工 cleanup,今天我们有 clippy 和 AI——但**判断什么该 cleanup 仍是人的责任**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 选择"统一所有 brain 函数签名为 `(e, ctx, dt)`",而不是给每个 brain 函数不同的"定制"签名。请解释这个选择背后的工程原则。

**参考解答**:三方面:

1. **可扩展性**:加新 brain 时不用想"我需要什么签名"——直接 `(e, ctx, dt)`,需要什么从 ctx 里取。降低加新功能的认知负担。
2. **可调用性**:主循环只需 `match brain { Player => brain_player, Monster => brain_monster, ... }` 然后 `f(e, &ctx, dt)`——一行 dispatch。不统一签名就要为每种 brain 写不同调用代码。
3. **可测试性**:测试 brain 只需 mock `Context`——一个类型搞定所有 brain。签名不统一就要为每种 brain 写不同的 mock setup。

牺牲的是:**有的 brain 不用 ctx 的某些字段**(snake 不用 input,player 不用 world),表面上"浪费"了。但这个浪费比起上面三个好处,微不足道。

这是工程上的"**接口一致性 > 局部最优**"原则。

### Lv2 · 动手实践

**题**:用 day287 的 brain 代码,做今天的"打磨"工作:
1. 统一签名(所有 brain 函数都是 `(e, ctx, dt)`)
2. 抽 `seek(e, target, speed)` helper
3. 处理 edge case(target_id 找不到时 vel = 0)
4. 运行 clippy,看有哪些 warning,修掉

完成标准:`cargo clippy -- -W clippy::pedantic` 无 warning(允许 `must_use` 类的)。

**参考解答**:

```rust
#![warn(clippy::pedantic)]
// 允许一些过严的 lint
#![allow(clippy::module_name_repetitions)]
#![allow(clippy::needless_pass_by_value)]

#[derive(Copy, Clone, Debug)]
pub struct Vec2 { pub x: f32, pub y: f32 }

impl Vec2 {
    pub const ZERO: Self = Self { x: 0.0, y: 0.0 };
    pub fn new(x: f32, y: f32) -> Self { Self { x, y } }
    pub fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    pub fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
    pub fn length(self) -> f32 { self.x.mul_add(self.x, self.y * self.y).sqrt() }
    pub fn normalize(self) -> Self {
        let l = self.length();
        if l > 1e-6 { self.mul(1.0 / l) } else { Self::ZERO }
    }
}

#[derive(Copy, Clone)]
pub enum Brain {
    Player,
    MonsterChase { target_id: u32 },
    Flee { threat_id: u32, radius: f32 },
}

pub struct Entity {
    pub id: u32,
    pub pos: Vec2,
    pub vel: Vec2,
    pub brain: Option<Brain>,
}

pub struct Input { pub dir: Vec2 }

pub struct Context<'a> {
    pub world: &'a World,
    pub input: Input,
}

pub struct World {
    pub entities: Vec<Entity>,
    next_id: u32,
}

impl World {
    pub fn new() -> Self { Self { entities: vec![], next_id: 0 } }

    pub fn spawn(&mut self, pos: Vec2, brain: Option<Brain>) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        self.entities.push(Entity { id, pos, vel: Vec2::ZERO, brain });
        id
    }

    pub fn find_pos(&self, id: u32) -> Option<Vec2> {
        self.entities.iter().find(|e| e.id == id).map(|e| e.pos)
    }
}

impl Default for World {
    fn default() -> Self { Self::new() }
}

// 公共 helper:朝目标移动
fn seek(e: &mut Entity, target: Vec2, speed: f32) {
    let d = target.sub(e.pos);
    e.vel = if d.length() > 1e-3 { d.normalize().mul(speed) } else { Vec2::ZERO };
}

// 统一签名的 brain 函数
fn brain_player(e: &mut Entity, ctx: &Context, _dt: f32) {
    e.vel = ctx.input.dir.mul(80.0);
}

fn brain_monster_chase(e: &mut Entity, ctx: &Context, _dt: f32) {
    let Some(Brain::MonsterChase { target_id }) = e.brain else { return; };
    match ctx.world.find_pos(target_id) {
        Some(target) => seek(e, target, 40.0),
        None => e.vel = Vec2::ZERO,  // edge case: target 不存在
    }
}

fn brain_flee(e: &mut Entity, ctx: &Context, _dt: f32) {
    let Some(Brain::Flee { threat_id, radius }) = e.brain else { return; };
    match ctx.world.find_pos(threat_id) {
        Some(threat) => {
            let d = e.pos.sub(threat);
            let dist = d.length();
            if dist < radius && dist > 1e-3 {
                e.vel = d.normalize().mul(60.0);
            } else {
                e.vel = Vec2::ZERO;
            }
        }
        None => e.vel = Vec2::ZERO,  // edge case: threat 不存在
    }
}

pub fn update_world(world: &mut World, input: Input, dt: f32) {
    let ctx = Context { world: &*world, input };

    // 复制所有位置避免借用冲突
    let positions: Vec<(usize, Vec2)> = world.entities
        .iter().enumerate()
        .map(|(i, e)| (i, e.pos))
        .collect();

    // 第一阶段:算 vel
    for (i, _pos) in positions.iter() {
        let e = &mut world.entities[*i];
        match e.brain {
            Some(Brain::Player) => brain_player(e, &ctx, dt),
            Some(Brain::MonsterChase { .. }) => brain_monster_chase(e, &ctx, dt),
            Some(Brain::Flee { .. }) => brain_flee(e, &ctx, dt),
            None => {}
        }
    }

    // 第二阶段:应用 vel
    for e in world.entities.iter_mut() {
        e.pos.x += e.vel.x * dt;
        e.pos.y += e.vel.y * dt;
    }
}

fn main() {
    let mut w = World::new();
    let player = w.spawn(Vec2::new(0.0, 0.0), Some(Brain::Player));
    let _monster = w.spawn(Vec2::new(100.0, 0.0),
        Some(Brain::MonsterChase { target_id: player }));

    for step in 0..10 {
        let input = Input { dir: Vec2::new(1.0, 0.0) };
        update_world(&mut w, input, 0.1);
        println!("step {}: monster at {:?}", step, w.entities[1].pos);
    }
}
```

**每行解释**:
- `#![warn(clippy::pedantic)]` —— 全 crate 开启 pedantic lint。
- `Vec2::ZERO` 常量 —— 比每次 `Vec2::new(0.0, 0.0)` 简洁。
- `Default for World` —— clippy 推荐,因为 `new()` 无参数时建议实现 Default。
- `seek` helper —— 三个 brain 都用,集中除零保护。
- 复制 positions 到 Vec —— 解决借用冲突(`&*world` 借用 world,但 `&mut world.entities[i]` 又 mut 借用)。

### 进一步展开:从概念到落地的完整路径

要把今天讨论的抽象概念变成可运行的代码,我们必须经历几个具体阶段。这一节展开每一步的工程细节。

**阶段一:定义接口**。Casey 在动手实现前,先想清楚 API。Rust 的 trait 是定义接口的工具:

```rust
trait Sortable {
    fn sort_key(&self) -> u64;
    fn bounds(&self) -> Aabb;
    fn layer(&self) -> u8;
}
```

trait 让代码可测试、可替换。Casey 经常说"先写 trait,再写 impl"——这强迫你思考抽象边界。

**阶段二:单元测试**。每个 sort_rule 分支都应有对应测试:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_basic_ordering() {
        let a = TestEntity { layer: 1, y: 100.0 };
        let b = TestEntity { layer: 1, y: 200.0 };
        assert_eq!(a.sort_key() < b.sort_key(), true);
    }

    #[test]
    fn test_layer_priority() {
        let a = TestEntity { layer: 2, y: 100.0 };
        let b = TestEntity { layer: 1, y: 200.0 };
        // layer 1 优先(a 在 b 后面)
        assert_eq!(a.sort_key() > b.sort_key(), true);
    }
}
```

跑 `cargo test`,所有测试必须通过才能进入下一阶段。

**阶段三:集成测试**。单元测试覆盖单个函数,集成测试覆盖整个系统。游戏里的集成测试通常是"加载场景,跑一帧,截图,对比期望截图"——visual regression test。这是 Casey debug 流程的标准化版本。

**阶段四:性能剖析**。用 `cargo flamegraph` 或 `perf record` 看 CPU 时间花在哪。如果 sort 占 0.5%,不用优化。占 20%,必优化。

```bash
sudo pacman -S flamegraph
cargo install flamegraph
cargo flamegraph --bin game
# 生成的 SVG 在浏览器打开,看热路径
```

**阶段五:跨平台验证**。Linux 测试用 `vulkaninfo | grep "Device name"` 看 GPU;Windows 测试用 dxdiag。同一代码在 Intel / AMD / NVIDIA / Apple Silicon GPU 上可能有微妙差异——精度、driver bug、性能特性。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
