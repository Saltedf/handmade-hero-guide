# Day 293 · 移动随从

> 昨天 snake 验证了复杂 brain 也能加。今天 Casey 完善 Familiar(随从)AI——它要**平滑跟随**玩家,而不是僵硬地紧跟。这需要"插值"和"延迟"两个数学工具。

## 0 · 为什么要有这一天

游戏里"随从"是经典角色——《暗黑破坏神》的雇佣兵、《以撒的结合》的宝宝、《塞尔达》的小精灵。它们的共同特征:**跟随玩家但保持一定距离**,玩家停下时随从凑过来,玩家狂奔时随从滞后。

如果随从"瞬间"跟随玩家位置(每帧 `e.pos = player.pos`),有两个问题:

1. **看起来假**——随从像粘在玩家身上,玩家拐弯随从瞬间拐弯
2. **碰撞抖动**——随从和玩家碰撞挤在一起,然后弹开,反复抖动

正确做法是**平滑跟随**:随从每帧朝玩家方向移动一小步,慢慢追上玩家。这需要两个工具:

- **lerp(线性插值)** —— `pos' = pos + (target - pos) * alpha`,alpha 越小越平滑
- **距离阈值** —— 太近时不移动(避免挤在玩家身上)

加 familiar 是 Day 286-292 解耦系列的**收官战**——你已经能加各种 brain,今天加个最优雅的。看完今天你应该有"加 AI 不再是难事"的自信。

心理锚点:看完今天,你应该能用 lerp 写出"相机平滑跟随玩家"的代码——同一种数学工具解决多个游戏问题。

## 2 · 心智模型

### 类比:弹簧跟随

把 familiar 想象成用**弹簧**挂在玩家身上。玩家移动时,弹簧拉伸,familiar 被弹簧拉向玩家。弹簧越紧(alpha 越大),跟随越快;弹簧越松(alpha 越小),跟随越慢。

物理上,这是**阻尼弹簧**(damped spring)——弹簧有阻尼,所以不会无限震荡,最终 familiar 静止在玩家位置。

数学上,这就是 lerp:`pos' = pos + (target - pos) * alpha`,alpha 是 0 到 1 之间的"弹簧系数"。alpha = 0 时 familiar 不动,alpha = 1 时 familiar 瞬移到 target,alpha = 0.1 时 familiar 每帧移动剩余距离的 10%。

### 2.1 lerp 的数学

`lerp(a, b, t) = a + (b - a) * t`,t 在 [0, 1] 之间。

- t = 0:a(完全不动)
- t = 1:b(完全到达)
- t = 0.5:中点

```rust
fn lerp(a: Vec2, b: Vec2, t: f32) -> Vec2 {
    Vec2::new(a.x + (b.x - a.x) * t, a.y + (b.y - a.y) * t)
}
```

但游戏里 lerp 通常配合时间。考虑每帧用固定 alpha:

```rust
e.pos = lerp(e.pos, target, 0.1);  // 每帧移动 10%
```

问题:**alpha 依赖帧率**。60 FPS 时每帧 10%,6 帧后接近 target;30 FPS 时每帧也 10%,但帧数减半,需要更长时间。**帧率依赖**是 lerp 的常见坑。

### 2.2 帧率无关的 lerp

正确写法是把 alpha 表达成 `1 - exp(-rate * dt)`,rate 是"每秒衰减率":

```rust
fn lerp_dt(a: Vec2, b: Vec2, rate: f32, dt: f32) -> Vec2 {
    let t = 1.0 - (-rate * dt).exp();
    lerp(a, b, t)
}

// 用法
e.pos = lerp_dt(e.pos, target, 5.0, dt);  // rate=5/秒,不管帧率
```

数学原理:指数衰减。`1 - exp(-rate * dt)` 在 dt 趋于 0 时约等于 `rate * dt`(线性),dt 大时趋于 1(完全到达)。这保证不管 dt 多大,效果一致。

简化版(近似):

```rust
let alpha = (rate * dt).min(1.0);  // dt 小时近似,dt 大时钳制
e.pos = lerp(e.pos, target, alpha);
```

牺牲精度换性能,游戏里足够用。

### 2.3 距离阈值

不加阈值时,familiar 永远到不了玩家(因为 lerp 是渐近的,每帧移动剩余距离的 alpha)。看起来 familiar 在玩家身上抖动——一帧超前,一帧滞后,反复。

加阈值:`if dist > THRESHOLD { move } else { stop }`。

```rust
fn brain_familiar(e: &mut Entity, target: Vec2, dt: f32) {
    let d = target.sub(e.pos);
    let dist = d.length();
    if dist < 5.0 {
        e.vel = Vec2::ZERO;
        return;
    }
    // 平滑跟随
    let alpha = 0.1.min(1.0);
    e.pos = lerp(e.pos, target, alpha);
}
```

注意:lerp 直接改 pos,不通过 vel——这违反了 Day 288 的"brain 只设 vel"原则。Casey 在这种特殊场景下接受违反,因为 lerp 本质是"瞬间位置插值",不能用 vel 表达。

替代方案:把 lerp 算出的位置变化转成 vel:

```rust
let new_pos = lerp(e.pos, target, alpha);
e.vel = new_pos.sub(e.pos).mul(1.0 / dt);
e.pos = new_pos;
```

这样 vel 反映了实际运动,碰撞和动画能正确处理。

### 2.4 限速跟随

游戏里另一个常见需求:**familiar 跟随玩家但有最大速度**。玩家狂奔时 familiar 滞后(因为 max_speed 限制),玩家停下时 familiar 慢慢追上。

```rust
fn brain_familiar_limited(e: &mut Entity, target: Vec2, dt: f32) {
    let d = target.sub(e.pos);
    let dist = d.length();
    if dist < 5.0 {
        e.vel = Vec2::ZERO;
        return;
    }
    let dir = d.normalize();
    // 理想速度:dist * 5(lerp 等价)
    // 但限制最大 100
    let desired_speed = (dist * 5.0).min(100.0);
    let desired_vel = dir.mul(desired_speed);
    // vel 也平滑过渡(避免突然加速)
    e.vel = lerp(e.vel, desired_vel, 0.2);
}
```

这种"两层平滑"——位置平滑 + 速度平滑——给最自然的运动感。Casey 在 day 293 用类似但不完全一样的实现。

---

**总结**:今天的核心工具是 **lerp**——线性插值。配合距离阈值,实现"平滑跟随"。lerp 的坑是帧率依赖,正确写法用 `1 - exp(-rate * dt)`。Lerp 在游戏里到处用:相机跟随、随从、UI 动画、颜色渐变。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

lerp 是游戏开发**最常用的数学工具**之一。除了 familiar 跟随,还用在:

- **相机跟随**:`camera.pos = lerp(camera.pos, player.pos, 0.1)`(Day 285+ Casey 用过)
- **UI 动画**:按钮 hover 时颜色渐变 `color = lerp(color, hover_color, 0.2)`
- **声音淡入淡出**:`volume = lerp(volume, target_volume, 0.05)`
- **角色转身**:`facing = lerp_angle(facing, target_facing, 0.1)`(lerp_angle 处理角度环绕)
- **伤害闪烁**:`flash = lerp(flash, 0.0, 0.1)`(受伤后 flash 从 1 渐变到 0)

工业级游戏引擎都内置 lerp 工具:Unity 的 `Mathf.Lerp`、Unreal 的 `FMath::Lerp`、Bevy 的 `Vec2::lerp`(在 glam 里)。

游戏行业关于 familiar 的设计哲学:**familiar 应该有"个性"**——不只是数值加成,而是有视觉表现力。Casey 在 HH 里 familiar 是球状精灵,但商业游戏会加更多细节:不同 familiar 不同移动模式(直线、波浪、抛物线)、不同 idle 动画(漂浮、震动、旋转)。

### 3.2 · 🎨 图形学视角

图形学里 lerp 用在**插值**(interpolation)。最常见:

- **双线性插值**(bilinear):纹理放大时,4 个像素 lerp 出中间值
- **三线性插值**(trilinear):mipmap level 之间也 lerp
- **顶点插值**:GPU 在三角形内部 lerp 顶点属性(UV、颜色、法线)
- **动画混合**:角色两种动画之间 lerp(如 idle 到 walk 的过渡)

数学上,lerp 是**线性插值**——最简单的一种。更高级的有:

- **Catmull-Rom spline**:经过控制点的平滑曲线
- **Bezier curve**:由控制点定义的曲线
- **Hermite 插值**:考虑切线的插值

游戏动画系统(Mecanim、Anim Tree)建立在 Hermite 之上,处理"动画 A 过渡到 B"时考虑速度连续性。

### 3.3 · 🐧 Linux 系统编程视角

Linux 里"插值"对应**数值平滑**:

- **CPU frequency governor**:`cpufreq` 调频时不是瞬间跳到最高频,而是逐步调整(`ondemand` governor 用类似 lerp 算法)
- **TCP congestion control**:cwnd(congestion window)不是瞬间翻倍,而是逐步增加(AIMD:Additive Increase, Multiplicative Decrease)
- **load average**:Linux 的 load average(平均负载)是指数移动平均(EMA),本质就是 lerp

```bash
# 看 load average
cat /proc/loadavg
# 输出:0.50 0.45 0.40 2/200 12345
# 0.50 是 1 分钟平均,0.45 是 5 分钟,0.40 是 15 分钟
# 算法:load[t] = load[t-1] * exp(-dt/period) + current_load * (1 - exp(-dt/period))
# 就是 lerp 的连续时间版本
```

EMA 和今天讲的 lerp_dt 是同一个公式,只是名字不同。Linux 内核 30 年前就用这个平滑。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 lerp:

```rust
trait Lerp {

impl Lerp for f32 {
    fn lerp(self, other: f32, t: f32) -> f32 {
        self + (other - self) * t
    }
}

// 用 generic 表达"任何能 lerp 的类型"

impl Lerp for Color { /* ... */ }
```


## 4 · 认知地图

### 4.1 上级

- **插值(Interpolation)** — 在两个值之间生成中间值
- **指数移动平均(EMA)** — lerp 的连续版本
- **阻尼弹簧(Damped Spring)** — 物理类比
- **缓动函数(Easing)** — 非线性插值

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 直接赋值 | `pos = target` | 瞬移 | 不用 |
| lerp | `pos += (target-pos)*a` | 平滑 | ✅ Familiar 用 |
| 弹簧物理 | 包含 vel + 力 | 真实物理 | 复杂场景 |
| Tween 库 | ease in/out 曲线 | UI 动画 | bevy_tweening |

### 4.3 下级

- **alpha 系数** — 0 到 1 的插值比例
- **dt 兼容** — `1 - exp(-rate * dt)`
- **距离阈值** — 太近时停止
- **限速** — `speed.min(MAX_SPEED)`

## 5 · 对照与变奏

### lerp 的多种应用

| 场景 | 公式 | 用途 |
|---|---|---|
| 位置跟随 | `pos = lerp(pos, target, 0.1)` | Familiar、相机 |
| 颜色渐变 | `col = lerp(col, target_col, 0.05)` | 受伤闪烁 |
| 数值平滑 | `hp_bar = lerp(hp_bar, hp, 0.2)` | 血条延迟 |
| 角度插值 | `angle = lerp_angle(angle, target, 0.1)` | 转身 |
| 大小渐变 | `scale = lerp(scale, 1.0, 0.1)` | 受击缩放 |

同一个 lerp,不同场景。这是"工具"与"应用"的区别——好工具到处能用。

### ease in/out(缓动)

lerp 是**线性**(匀速)。游戏里常用**非线性**让运动更"自然":

- **ease in**:开始慢,结束快(加速)
- **ease out**:开始快,结束慢(减速)
- **ease in-out**:两端慢,中间快(更自然)

数学:`ease_out(t) = 1 - (1-t)^2`。

工业级 tween 库有几十种 ease 函数。Casey 在 HH 用纯 lerp,简单够用。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"每帧 lerp 10%"(`alpha=0.1`)是帧率依赖的?给出具体计算:60 FPS 和 30 FPS 下,1 秒后到达 target 的百分比分别是多少?

**参考解答**:

每帧 lerp 10% 意味着 `pos = pos * 0.9 + target * 0.1`。N 帧后,剩余距离 = `0.9^N`。

- 60 FPS,1 秒 = 60 帧:`0.9^60 ≈ 0.0018`。剩余 0.18%,到达 99.82%。
- 30 FPS,1 秒 = 30 帧:`0.9^30 ≈ 0.042`。剩余 4.2%,到达 95.8%。

差别 4 倍——同样 1 秒,60 FPS 几乎到达,30 FPS 才到 96%。**帧率越高,跟随越快**。

帧率无关版本:`alpha = 1 - exp(-rate * dt)`。rate = 5 时:
- 60 FPS,dt = 1/60:`alpha = 1 - exp(-5/60) ≈ 0.080`
- 30 FPS,dt = 1/30:`alpha = 1 - exp(-5/30) ≈ 0.154`

每秒衰减率都是 `1 - exp(-5) ≈ 0.993`,与帧率无关。

### Lv2 · 动手实践

**题**:实现帧率无关的 familiar 跟随,rate = 4。验证:60 FPS 跑 1 秒、30 FPS 跑 1 秒、20 FPS 跑 1 秒,familiar 到达 target 的距离百分比相同。

完成标准:打印三个版本的最终距离,差异 < 1%。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
    fn length(self) -> f32 { (self.x * self.x + self.y * self.y).sqrt() }
}

fn lerp_dt(pos: Vec2, target: Vec2, rate: f32, dt: f32) -> Vec2 {
    let alpha = 1.0 - (-rate * dt).exp();
    pos.add(target.sub(pos).mul(alpha))
}

impl Vec2 {
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
}

fn simulate(fps: f32, duration: f32, rate: f32) -> Vec2 {
    let mut pos = Vec2::new(0.0, 0.0);
    let target = Vec2::new(100.0, 0.0);
    let dt = 1.0 / fps;
    let steps = (duration * fps) as i32;
    for _ in 0..steps {
        pos = lerp_dt(pos, target, rate, dt);
    }
    pos
}

fn main() {
    let rate = 4.0;
    let duration = 1.0;

    let pos60 = simulate(60.0, duration, rate);
    let pos30 = simulate(30.0, duration, rate);
    let pos20 = simulate(20.0, duration, rate);

    println!("60 FPS: pos.x = {:.3}", pos60.x);
    println!("30 FPS: pos.x = {:.3}", pos30.x);
    println!("20 FPS: pos.x = {:.3}", pos20.x);

    let target = 100.0;
    let err60 = (pos60.x - target).abs();
    let err30 = (pos30.x - target).abs();
    let err20 = (pos20.x - target).abs();
    println!("errors: 60={:.3} 30={:.3} 20={:.3}", err60, err30, err20);
    // 三者应该接近(差异 < 1%)

    // 数学预期:1 - exp(-4) ≈ 0.982,所以 1 秒后到达 98.2%
    assert!((err60 - 1.8).abs() < 0.5);
    assert!((err30 - 1.8).abs() < 0.5);
    assert!((err20 - 1.8).abs() < 0.5);

    println!("Framerate-independent lerp test passed!");
}
```

**每行解释**:
- `(-rate * dt).exp()` —— Rust 的 `f32::exp()` 是 `e^x`,数学库函数
- `pos.add(target.sub(pos).mul(alpha))` —— 等价于 `pos + (target - pos) * alpha`
- 三个 FPS 跑相同 duration,结果应该一致(差 < 1%)—— 这就是帧率无关

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

§7 Lv2 完整可跑。这里加 visual 部分:

```rust
// 在 §7 基础上加熟悉 brain
struct FamiliarBrain {
    pos: Vec2,
    idle_bob: f32,  // 上下浮动相位
}

impl FamiliarBrain {
    fn update(&mut self, target: Vec2, dt: f32, time: f32) {
        // 平滑跟随
        self.pos = lerp_dt(self.pos, target, 4.0, dt);
        // 距离阈值
        if self.pos.sub(target).length() < 5.0 {
            // 太近时上下浮动(idle 动画)
            self.idle_bob = (time * 3.0).sin() * 3.0;
        } else {
            self.idle_bob = 0.0;
        }
    }

    fn visual_pos(&self) -> Vec2 {
        Vec2::new(self.pos.x, self.pos.y + self.idle_bob)
    }
}

fn main() {
    let mut fam = FamiliarBrain {
        pos: Vec2::new(0.0, 0.0),
        idle_bob: 0.0,
    };
    let target = Vec2::new(50.0, 50.0);

    let mut t = 0.0;
    let dt = 0.016;  // 60 FPS
    while t < 2.0 {
        fam.update(target, dt, t);
        if t > 0.9 && t < 1.1 {
            println!("t={:.2}: pos=({:.2},{:.2}) visual=({:.2},{:.2})",
                t, fam.pos.x, fam.pos.y,
                fam.visual_pos().x, fam.visual_pos().y);
        }
        t += dt;
    }
}
```

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 历史脉络与工业实践

1990 年代 id Software 的 Doom(1993)用 BSP tree + painter's algorithm——排序在编译期完成,运行时 O(N) 遍历。Quake(1996)首次用 Z-buffer(GPU 硬件),彻底解决排序问题。

2D 游戏排序的演化:

- **1985-1990**:无 sort,固定 layer(Super Mario Bros)
- **1990-1995**:Y-sort 在 JRPG 普及(最终幻想 6、超时空之轮)
- **1995-2005**:Multi-layer Y-sort(星际争霸、暗黑破坏神 2)
- **2005-2015**:引擎内置 sort(Unity、GameMaker)
- **2015-2025**:GPU + sort 混合(bevy、Unreal)

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
