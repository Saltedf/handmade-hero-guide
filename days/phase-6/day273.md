# Day 273 · 动画概览

> 今天的集子和 Day 041(游戏数学概览)很像——Casey 不写代码,他在黑板上把接下来 10 多集要用到的动画概念全部摆开。理解这一集,后面 Day 274-285 你就知道每一步在做什么。

## 0 · 为什么要有这一天

你的角色现在能按方向键移动,但它看起来是个**没有生命的方块**——从 A 到 B 平移过去,没有任何"动作"。真正的游戏角色不是这样:

- **走路**:腿部交替前后摆动,身体微微上下颠簸
- **跑步**:摆动幅度更大,身体前倾
- **空闲呼吸**:身体微微缩放,头发飘动
- **攻击**:挥剑时身体扭转,手臂前伸
- **受伤**:身体向后仰,变红

这些"动作"统称**动画**(animation)。动画的本质是**让物体随时间呈现不同的姿态**,让大脑感知到"运动"和"生命"。

Casey 接下来 10 多集要给角色加各种动画:走路、跑步、攻击、空闲、撞墙。每一类动画有自己的实现技术:

- **关键帧动画**(Skeletal Animation):多张预设姿态之间插值,角色精灵切换
- **程序化动画**(Procedural Animation):用代码生成姿态,如弹簧、IK
- **物理动画**(Physics-based):用物理引擎模拟,如布料、头发
- **粒子动画**:大量小粒子,如火焰、爆炸

今天 Casey 不实现任何一种,只做"地图":**告诉观众接下来每集会涉及什么动画技术,这些技术的数学/物理基础是什么**。

心理锚点:看完这一集,你能用 30 秒解释"sprite 切换 vs 程序化动画"的差异,知道每种适合什么场景。

## 2 · 心智模型

### 类比:电影胶片 vs 翻页书 vs 木偶戏

三种"让画面动起来"的方式,对应三种动画技术:

**翻页书(Sprite 切换)**:你在便签本每页画一个姿态,快速翻动就看到连续动作。每秒翻 12 页,看起来就是流畅动画。2D 游戏的角色精灵就是这种:每帧一张图,每秒切 12-15 帧。

**电影胶片(预渲染)**:整段动画先录好,播放时按帧读。游戏里的过场动画(Cutscene)就是这种。

**木偶戏(程序化 / 骨骼)**:角色有"骨骼",你控制骨骼角度,皮肤跟着动。3D 游戏的标准。HH 后面会有简单的骨骼动画(头 + 身体),但不复杂。

Casey 选**翻页书**为主,**木偶戏**(程序化运动)为辅。这是 2D 动作游戏的标配。

### 严谨原理:动画的核心抽象

#### 时间 → 姿态

动画本质是一个函数:`pose(time) -> CharacterPose`。给定时间,返回角色当前的姿态。

对于 sprite 切换:

```
pose(t):
    frame_index = floor(t / frame_duration) % total_frames
    return sprites[frame_index]
```

每 `frame_duration` 秒切一帧,循环。

对于程序化运动(如呼吸):

```
pose(t):
    breath_scale = 1.0 + 0.05 * sin(t * 2 * PI / 3.0)  // 3 秒周期
    return CharacterPose { scale: breath_scale, ... }
```

用正弦函数让 scale 在 0.95-1.05 之间振荡,模拟呼吸。

#### 帧率(frame rate)

动画的"流畅度"由帧率决定:

- 12 FPS:传统手绘动画(迪士尼)
- 24 FPS:电影
- 30 FPS:早期游戏
- 60 FPS:现代游戏标准
- 120+ FPS:VR / 高端电竞

但**动画帧率 ≠ 游戏帧率**。游戏可能跑 144 FPS,但动画只切 30 帧/秒(每 5 个游戏帧切一次动画帧)。这样动画不会过快,游戏渲染保持流畅。

#### 缓动(easing)

线性动画(匀速)看起来"机械"。真实运动有加速、减速、过冲。缓动函数模拟这种:

```
linear(t)      = t                      // 匀速
ease_in(t)     = t * t                   // 起步慢
ease_out(t)    = 1 - (1-t) * (1-t)       // 结束慢
ease_in_out(t) = t * t * (3 - 2 * t)     // 两端慢中间快(smooth step)
overshoot(t)   = 1 + 2.7 * (t-1)^3 + 1.7 * (t-1)^2  // 过冲(后弹回)
```

 Casey 在 Day 274 讲弹簧动画,本质是一种物理化的缓动(基于弹簧微分方程)。

#### 状态机驱动

动画要跟随角色状态:

- Idle 状态:播放空闲动画(呼吸 + 偶尔转头)
- Moving 状态:播放走路 / 跑步动画(腿摆动)
- Attacking 状态:播放挥剑动画(固定时长)

切换状态时,动画要"过渡":从走路最后一帧平滑切换到攻击第一帧。这是**动画混合**(blending),复杂的引擎(Unreal)支持多层混合,HH 简化为"直接切换"。

### 动画的数据结构

#### Sprite 切换

```rust
struct SpriteAnimation {
    frames: Vec<SpriteId>,
    frame_duration: f32,  // 每帧秒数
    looping: bool,
}

struct AnimationPlayer {
    animation: Option<SpriteAnimation>,
    elapsed: f32,  // 已播放时间
}

impl AnimationPlayer {
    fn current_frame(&self) -> Option<SpriteId> {
        let anim = self.animation.as_ref()?;
        let frame_idx = (self.elapsed / anim.frame_duration) as usize;
        let frame_idx = if anim.looping {
            frame_idx % anim.frames.len()
        } else {
            frame_idx.min(anim.frames.len() - 1)
        };
        Some(anim.frames[frame_idx])
    }

    fn update(&mut self, dt: f32) {
        if self.animation.is_some() {
            self.elapsed += dt;
        }
    }
}
```

#### 程序化运动

```rust
struct ProceduralAnim {
    time: f32,
}

impl ProceduralAnim {
    fn breath_scale(&self) -> f32 {
        1.0 + 0.05 * (self.time * 2.0 * std::f32::consts::PI / 3.0).sin()
    }

    fn walk_bob(&self) -> f32 {
        // 走路时身体上下颠簸,周期 0.4 秒
        2.0 * (self.time * 2.0 * std::f32::consts::PI / 0.4).sin().abs()
    }
}
```

程序化动画的好处:**不用美术资源**。坏处:**风格受限**(很难做出复杂姿态)。

### 动画的渲染

无论动画类型,最终都要渲染。2D sprite 渲染:

```rust
fn render_player(buf: &mut [u32], player: &Player, anim_player: &AnimationPlayer) {
    let sprite_id = anim_player.current_frame().unwrap_or(DEFAULT_SPRITE);
    let sprite = get_sprite(sprite_id);
    draw_sprite(buf, player.pos.x, player.pos.y, sprite);
}
```

如果是程序化动画,可能渲染时改 transform:

```rust
fn render_player_proc(buf: &mut [u32], player: &Player, anim: &ProceduralAnim) {
    let scale = anim.breath_scale();
    let sprite = get_sprite(PLAYER_SPRITE);
    draw_sprite_scaled(buf, player.pos.x, player.pos.y, sprite, scale);
}
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏动画有几个关键概念:

#### 动画状态机(ASM)

主流引擎(Unreal / Unity)都有专门的"动画状态机",和角色逻辑状态机联动:

- 角色状态 Idle → 动画状态 Idle_Loop
- 角色状态 Moving → 动画状态 Walk_Loop 或 Run_Loop(取决于速度)
- 切换时播放过渡(transition)

#### 反向动力学(IK)

3D 游戏的高级技术:给定手脚"目标位置",自动算骨骼角度。例如:角色踩在不平的地面上,脚要贴合地面,IK 自动算。

#### 物理动画(ragdoll)

角色死亡时变成布偶,关节受物理影响倒下。需要物理引擎支持(Unreal Chaos、Unity Havok)。

#### blend shapes / morph targets

3D 模型的面部表情:预定义多个表情"目标",插值得到中间状态。

Casey 的 HH 只用 sprite 切换 + 程序化运动,够 2D 动作游戏用。

### 3.2 · 🎨 图形学视角

动画在图形学里是"随时间变化的几何 / 颜色数据"。几个关键点:

1. **时间累积**:`elapsed += dt` 是基础。dt 大时动画快,dt 小时慢。游戏在 30 FPS 跑动画看起来和 60 FPS 一样(因为按时间)
2. **抗锯齿**:sprite 旋转 / 缩放时边缘锯齿明显,需要 AA。现代 GPU 用 MSAA / FXAA
3. **子像素**:sprite 位置浮点时,渲染要四舍五入或插值,避免抖动
4. **双缓冲**:切换 sprite 时不能"撕裂",需要双缓冲(下一帧准备好再切换)

#### 插值算法

sprite 切换是"硬切换"(无插值)。如果要做平滑切换:

- **Crossfade**:两张 sprite 同时画,alpha 从 0 到 1 过渡
- **Morph**:两张 sprite 顶点插值(适合骨骼)
- **Rotozoom**:旋转 + 缩放插值

Casey 在 Day 275 讲"旋转和剪切"时涉及这些。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的动画工具:

- **GIF**:2D 动画的鼻祖,256 色,简单
- **APNG**:animated PNG,真彩色 + alpha
- **WebM / VP9**:视频,适合长动画
- **Lottie**:矢量动画(JSON 描述),Adobe After Effects 导出

游戏里的 sprite 一般是 PNG sequence(一帧一个 PNG),加载时打成 atlas(图集)。

Linux 上制作 sprite 的工具:

### 3.4 · 🦀 Rust 生态视角

Rust 表达动画几个考量:

#### 用 enum 表达动画类型

```rust
enum Animation {
    Sprite(SpriteAnimation),
    Procedural(ProceduralAnim),
    Blend { from: Box<Animation>, to: Box<Animation>, progress: f32 },
}
```

enum 自然支持多种动画类型 + 嵌套混合。

#### Keyframe 数据

```rust
struct Keyframe<T> {
    time: f32,
    value: T,
}

struct Track<T> {
    keyframes: Vec<Keyframe<T>>,
}

impl<T: Clone + Lerp> Track<T> {
    fn sample(&self, time: f32) -> T {
        // 找到 time 所在的两个 keyframe,线性插值
        for i in 0..self.keyframes.len() - 1 {
            let a = &self.keyframes[i];
            let b = &self.keyframes[i + 1];
            if time >= a.time && time <= b.time {
                let t = (time - a.time) / (b.time - a.time);
                return a.value.lerp(&b.value, t);
            }
        }
        // 超出范围:返回最后一个值
        self.keyframes.last().unwrap().value.clone()
    }
}

trait Lerp {
    fn lerp(&self, other: &Self, t: f32) -> Self;
}

impl Lerp for f32 {
    fn lerp(&self, other: &Self, t: f32) -> Self {
        self + (other - self) * t
    }
}
```

`Lerp` trait 是表达"线性插值"的 Rust 方式。任何能 lerp 的类型(数字、颜色、向量)都可以做 keyframe 动画。

#### 现成 crate

- **`keyframe`**:函数式动画 + 缓动
- **`spine-rs`**:Spine 2D 动画运行时
- **`bevy_animation`**:Bevy 引擎内置

教学阶段我们手写,生产项目可以用 crate。

### 3.5 · 数学:周期函数

动画的数学基础大量涉及**周期函数**(periodic function):

```
f(t + T) = f(t)  对所有 t 成立
```

T 叫周期。常见周期函数:

- **sin / cos**:周期 2π
- **方波**:周期 1,值在 -1 / +1 跳跃
- **三角波**:周期 1,值线性 -1 → +1 → -1
- **锯齿波**:周期 1,值线性 -1 → +1 突然回 -1

游戏动画里 sin / cos 用得最多,因为平滑(可导)。方波 / 锯齿波用于"硬切换"动画(像素艺术常风格)。

#### 频率与周期

频率 f 和周期 T 的关系:`T = 1 / f`。

- 走路动画:f = 1.5 Hz(每秒 1.5 个循环),T ≈ 0.67 秒
- 跑步:f = 2.5 Hz,T = 0.4 秒
- 呼吸:f = 0.3 Hz,T = 3.3 秒
- 心跳:f = 1.2 Hz,T = 0.83 秒

理解这些数字能让你的动画节奏自然。

## 5 · 对照与变奏

### 2D vs 3D 动画

| 维度 | 2D 动画 | 3D 动画 |
|---|---|---|
| 基本单位 | Sprite(像素图) | Mesh + Skeleton |
| 变换 | translate / scale / rotate(2D) | translate / scale / rotate(3D) |
| 姿态 | 帧切换 | 骨骼角度组合 |
| 资源量 | 大(每帧一张) | 小(一个模型) |
| 工具 | Aseprite / Spine | Blender / Maya |
| 性能 | 内存换 CPU | CPU 换内存 |

Casey 选 2D sprite,因为 HH 是 2D 游戏。

### 帧率 vs 时间

```
帧率方式(frame_index += 1 每帧):
  问题:游戏帧率不稳时动画速度也变
  适合:固定帧率游戏(老 NES 游戏)

时间方式(elapsed += dt 每帧,按时间切帧):
  优势:动画速度恒定,不受游戏帧率影响
  适合:现代游戏(变帧率)
```

Casey 选时间方式,HH 用变帧率,动画速度稳定。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:动画"按时间切帧"(`elapsed += dt`)比"按游戏帧切帧"(`frame_count += 1`)好。请给出至少 3 个理由。

**参考解答**:
1. **帧率独立性**:游戏在 30 FPS 或 144 FPS 跑,动画速度一致。按游戏帧切则 144 FPS 时动画快 5 倍,体验灾难
2. **暂停一致**:游戏暂停时(dt = 0),动画也暂停。按游戏帧切则动画继续切帧
3. **慢动作支持**:游戏做"慢动作"(dt 乘以 0.5)时,动画也变慢。按帧切做不到这种效果
4. **跨设备一致**:不同设备帧率不同(60Hz 手机 vs 144Hz 显示器),按时间切让所有玩家体验一致
5. **物理同步**:角色物理(位置 / 速度)也是按时间积分,动画按时间才能和物理同步
6. **可重现性**:固定时间种子下,动画可重现(调试用);按帧切则取决于游戏帧率

### Lv2 · 动手实践

**题**:实现一个 `SpriteAnimation` + `AnimationPlayer`:

- SpriteAnimation 包含 frames: Vec<usize>(sprite id 列表), frame_duration: f32, looping: bool
- AnimationPlayer 有 elapsed: f32 字段
- current_frame() 返回当前应该显示的 sprite id
- update(dt) 累积时间

测试:5 帧,每帧 0.1 秒,looping=true。模拟 0.75 秒,看 current_frame 返回什么。

完成标准:0.75 秒时 current_frame 应该返回 frames[7 % 5] = frames[2]。

**参考解答**:

```rust
#[derive(Clone, Debug)]
struct SpriteAnimation {
    frames: Vec<usize>,
    frame_duration: f32,
    looping: bool,
}

#[derive(Clone, Debug)]
struct AnimationPlayer {
    animation: Option<SpriteAnimation>,
    elapsed: f32,
}

impl AnimationPlayer {
    fn new() -> Self {
        Self { animation: None, elapsed: 0.0 }
    }

    fn play(&mut self, anim: SpriteAnimation) {
        self.animation = Some(anim);
        self.elapsed = 0.0;
    }

    fn update(&mut self, dt: f32) {
        if self.animation.is_some() {
            self.elapsed += dt;
        }
    }

    fn current_frame(&self) -> Option<usize> {
        let anim = self.animation.as_ref()?;
        if anim.frames.is_empty() { return None; }

        let frame_idx = (self.elapsed / anim.frame_duration) as usize;
        let frame_idx = if anim.looping {
            frame_idx % anim.frames.len()
        } else {
            frame_idx.min(anim.frames.len() - 1)
        };
        Some(anim.frames[frame_idx])
    }
}

fn main() {
    let mut player = AnimationPlayer::new();
    let anim = SpriteAnimation {
        frames: vec![0, 1, 2, 3, 4],  // 5 帧
        frame_duration: 0.1,
        looping: true,
    };
    player.play(anim);

    // 模拟 0.75 秒,每步 0.05 秒
    let dt = 0.05;
    for step in 0..15 {
        player.update(dt);
        let t = (step + 1) as f32 * dt;
        if let Some(frame) = player.current_frame() {
            println!("t={:.2}s, frame={}", t, frame);
        }
    }
    // 应该看到 t=0.75s 时 frame=2(因为 0.75/0.1=7.5 → floor = 7,7 % 5 = 2)

    // 验证:0.75 / 0.1 = 7.5,as usize = 7
    // 7 % 5 = 2 ✓
}
```

**每行解释**:
- `frame_idx = (elapsed / frame_duration) as usize` 算出"第几帧"
- `% frames.len()` 让 looping 时回绕
- `.min(frames.len() - 1)` 让非 looping 时停在最后一帧
- `if anim.frames.is_empty() return None` 保护空数组

### Lv3 · 迁移设计

**题**:实现一个**程序化呼吸动画**:角色的 scale 在 0.95 到 1.05 之间正弦振荡,周期 3 秒。

要求:

- 函数 `breath_scale(time: f32) -> f32`

### 完整可跑:动画播放器 + sprite 切换 + 程序化呼吸

```rust
// Cargo.toml:
// [dependencies]
// minifb = "0.27"

use minifb::{Key, Window, WindowOptions};
use std::time::Instant;

const WIDTH: usize = 800;
const HEIGHT: usize = 600;

// ---------- Sprite 动画 ----------

#[derive(Clone, Debug)]
struct SpriteAnimation {
    frames: Vec<usize>,
    frame_duration: f32,
    looping: bool,
}

#[derive(Clone, Debug)]
struct AnimationPlayer {
    animation: Option<SpriteAnimation>,
    elapsed: f32,
}

impl AnimationPlayer {
    fn new() -> Self { Self { animation: None, elapsed: 0.0 } }
    fn play(&mut self, anim: SpriteAnimation) {
        self.animation = Some(anim);
        self.elapsed = 0.0;
    }
    fn update(&mut self, dt: f32) {
        if self.animation.is_some() { self.elapsed += dt; }
    }
    fn current_frame(&self) -> Option<usize> {
        let anim = self.animation.as_ref()?;
        if anim.frames.is_empty() { return None; }
        let idx = (self.elapsed / anim.frame_duration) as usize;
        let idx = if anim.looping {
            idx % anim.frames.len()
        } else {
            idx.min(anim.frames.len() - 1)
        };
        Some(anim.frames[idx])
    }
}

// ---------- 程序化呼吸动画 ----------

fn breath_scale(time: f32) -> f32 {
    // 周期 3 秒,幅度 0.05
    let phase = (time * 2.0 * std::f32::consts::PI / 3.0).sin();
    1.0 + 0.05 * phase
}

// ---------- 模拟 sprite 渲染 ----------

fn draw_player(buf: &mut [u32], buf_w: usize, buf_h: usize,
               cx: i32, cy: i32, scale: f32, frame_idx: usize) {
    // 基础大小 32x32,scale 缩放
    let size = (32.0 * scale) as i32;
    let half = size / 2;

    // 不同帧用不同颜色(模拟 sprite 切换)
    let base_color = match frame_idx {
        0 => 0xFFFF4040,
        1 => 0xFFFF6040,
        2 => 0xFFFF8040,
        3 => 0xFFFF6040,
        _ => 0xFFFF4040,
    };

    for py in (cy - half).max(0)..(cy + half).min(buf_h as i32) {
        for px in (cx - half).max(0)..(cx + half).min(buf_w as i32) {
            buf[(py as usize) * buf_w + (px as usize)] = base_color;
        }
    }

    // 画眼睛(让方块看起来像角色)
    let eye_color = 0xFFFFFFFF;
    let eye_size = (3.0 * scale) as i32;
    for py in cy - half / 3 - eye_size/2..cy - half / 3 + eye_size/2 {
        for px in cx - half / 3 - eye_size/2..cx - half / 3 + eye_size/2 {
            if px >= 0 && (px as usize) < buf_w && py >= 0 && (py as usize) < buf_h {
                buf[(py as usize) * buf_w + (px as usize)] = eye_color;
            }
        }
        let _ = py;  // 抑制警告
    }
}

fn draw_rect(buf: &mut [u32], buf_w: usize, buf_h: usize, x: i32, y: i32, w: i32, h: i32, color: u32) {
    for py in y.max(0)..(y + h).min(buf_h as i32) {
        for px in x.max(0)..(x + w).min(buf_w as i32) {
            buf[(py as usize) * buf_w + (px as usize)] = color;
        }
    }
}

fn main() {
    let mut window = Window::new(
        "Animation Overview Demo", WIDTH, HEIGHT,
        WindowOptions::default(),
    ).expect("Failed to open window");

    let mut buffer = vec![0u32; WIDTH * HEIGHT];
    let mut last_time = Instant::now();
    let mut total_time = 0.0_f32;

    // 走路动画:4 帧循环,每帧 0.15 秒
    let walk_anim = SpriteAnimation {
        frames: vec![0, 1, 2, 3],
        frame_duration: 0.15,
        looping: true,
    };

    let mut anim_player = AnimationPlayer::new();
    anim_player.play(walk_anim);

    while window.is_open() && !window.is_key_down(Key::Escape) {
        let now = Instant::now();
        let dt = now.duration_since(last_time).as_secs_f32();
        last_time = now;
        total_time += dt;

        // 更新动画
        anim_player.update(dt);

        // 渲染
        for px in buffer.iter_mut() { *px = 0xFF101010; }

        // 左侧:sprite 动画(无程序化)
        let frame_left = anim_player.current_frame().unwrap_or(0);
        draw_player(&mut buffer, WIDTH, HEIGHT, 200, 300, 1.0, frame_left);

        // 中间:sprite 动画 + 呼吸缩放
        let frame_mid = anim_player.current_frame().unwrap_or(0);
        let scale_mid = breath_scale(total_time);
        draw_player(&mut buffer, WIDTH, HEIGHT, 400, 300, scale_mid, frame_mid);

        // 右侧:只呼吸,无 sprite 切换
        let scale_right = breath_scale(total_time + 1.5);  // 不同 phase
        draw_player(&mut buffer, WIDTH, HEIGHT, 600, 300, scale_right, 0);

        // 顶部标签
        draw_rect(&mut buffer, WIDTH, HEIGHT, 100, 50, 200, 30, 0xFF303030);
        draw_rect(&mut buffer, WIDTH, HEIGHT, 300, 50, 200, 30, 0xFF303030);
        draw_rect(&mut buffer, WIDTH, HEIGHT, 500, 50, 200, 30, 0xFF303030);

        window.update_with_buffer(&buffer, WIDTH, HEIGHT).unwrap();
    }
}
```

**关键 Rust 特性解释**:
- `SpriteAnimation` 和 `AnimationPlayer` 分离,符合"数据 + 行为"模式
- `breath_scale` 是纯函数,无状态,易测试
- `total_time` 累积全局时间,作为程序化动画的输入
- 三个 player 对比展示:sprite-only、sprite + breath、breath-only

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
