
# Day 294 · 加手套

> 玩家现在能跑、能撞、有随从。但还**不能攻击**。今天加一个 glove(手套)实体——玩家可以"挥拳"攻击怪物。这引入新概念:**owner(所属者)**——一个实体归属另一个实体。

## 0 · 为什么要有这一天

游戏里"装备"是核心系统——武器、防具、饰品。HH 加 glove 是装备系统的最小原型。手套的特点:

- 它**不属于自己**——它是玩家的延伸,位置跟随玩家
- 它有**生命周期**——挥拳时显示,挥完后消失
- 它能**触发伤害**——碰到怪物时怪物掉血

这三个特性都指向同一个设计:**owner 字段**。手套实体有个 `owner_id: u32` 字段,指向玩家 ID。每帧 update 时,手套位置 = 玩家位置 + 偏移;攻击命中时,伤害来源是 owner(玩家)而不是手套本身。

owner 字段在游戏开发里极其常见:

- 子弹(`owner = 射击者`)——区分敌我
- 召唤物(`owner = 召唤者`)——死亡时一起消失
- 投掷武器(`owner = 投掷者`)——伤害来源
- 治疗光环(`owner = 施法者`)——只治疗队友

为什么需要 owner?**因为不是所有"游戏对象"都是平等的**——有的是主体(玩家、怪物),有的是附属(装备、特效)。附属必须依附主体,主体消失时附属也要消失。owner 字段表达这种依附关系。

今天的代码量也少——加 `Glove` brain variant、写 brain_glove 函数、加攻击 hitbox 检测。如果 Day 286-293 的解耦做对了,今天 100 行代码搞定。

心理锚点:看完今天,你应该理解"附属实体"的概念,能设计武器、buff、投射物等系统。

## 1 · Casey 今天做了什么

Casey 今天的实现:

1. **加 Glove brain**——payload 包含 `owner_id: u32`(归属玩家)、`active: bool`(当前是否激活)、`active_timer: f32`(激活剩余时间)
2. **写 brain_glove**——active 时画在玩家面前(玩家朝向 * 偏移),active_timer 减到 0 时变 inactive
3. **加攻击输入**——玩家按攻击键时,找到自己的 glove,设 active = true,active_timer = 0.3 秒
4. **加碰撞伤害**——glove active 时碰到怪物,怪物掉血,glove 变 inactive(避免连击)

这是 HH 第一个"附属实体",开启了 weapon/effect/aura 系统的先河。

## 2 · 心智模型

### 类比:手套和手

把手套实体想象成真实的手套——它**不会自己动**,只有戴在手上才有意义。手在哪手套就在哪,手停下手套也停。

数据上,手套独立存在(一个 entity),但逻辑上依附于"手"(玩家)。这种"独立但依附"的关系就是 owner 字段。

考虑手套的几种状态:

- **未装备**:不存在(玩家没拿)
- **装备但闲置**:存在,但不可见(挂在腰间)
- **激活(挥拳)**:存在,可见,在玩家前方
- **激活并命中**:存在,可见,造成伤害
- **闲置**(挥完):回到不可见

转换:玩家按攻击键 → 激活;0.3 秒后 → 闲置;命中怪物 → 立即闲置。

### 2.1 owner 字段的设计

```rust
struct GloveBrain {
    owner_id: u32,
    active: bool,
    active_timer: f32,
    hit_targets: Vec<u32>,  // 本次激活已命中的目标(避免重复伤害)
}
```

为什么需要 `hit_targets`?如果不记,每帧 glove 和怪物重叠,就持续伤害——一个怪物 0.3 秒内被伤害 18 次(60 FPS)。这违背设计意图——玩家会看到一个拳头打 18 次连击。

`hit_targets` 记录"本次激活已经伤害过谁",命中后加入,下次不再伤害。激活结束时(变 inactive)清空 hit_targets。

```rust
fn brain_glove(e: &mut Entity, ctx: &Context, dt: f32) {
    let Some(Brain::Glove { owner_id, active, active_timer, hit_targets }) = e.brain else { return; };

    if *active {
        // 跟随 owner,位置在 owner 前方
        if let Some(owner) = ctx.world.get(*owner_id) {
            let dir = owner.facing_dir;
            e.pos.x = owner.pos.x + dir.x * 30.0;
            e.pos.y = owner.pos.y + dir.y * 30.0;
        }
        *active_timer -= dt;
        if *active_timer <= 0.0 {
            *active = false;
            hit_targets.clear();
        }
    } else {
        // 闲置:隐藏在 owner 身上
        if let Some(owner) = ctx.world.get(*owner_id) {
            e.pos = owner.pos;
        }
    }
}

fn trigger_attack(glove: &mut Entity) {
    if let Some(Brain::Glove { active, active_timer, hit_targets, .. }) = &mut glove.brain {
        *active = true;
        *active_timer = 0.3;
        hit_targets.clear();
    }
}
```

### 2.2 碰撞伤害

```rust
fn check_glove_hits(world: &mut World) {
    // 找所有 active glove
    let mut damages: Vec<(u32, u32)> = vec![];  // (target_id, owner_id)
    for glove in &world.entities {
        let Some(Brain::Glove { owner_id, active, hit_targets, .. }) = &glove.brain else { continue; };
        if !*active { continue; }
        for target in &world.entities {
            // 不能伤害 owner 自己,也不能重复伤害
            if target.id == *owner_id { continue; }
            if hit_targets.contains(&target.id) { continue; }
            // AABB 碰撞
            if aabb_overlap(glove.pos, target.pos, GLOVE_RADIUS, TARGET_RADIUS) {
                damages.push((target.id, *owner_id));
            }
        }
    }
    // 应用伤害
    for (target_id, owner_id) in damages {
        // 找到 glove,加 target 到 hit_targets
        for glove in &mut world.entities {
            if let Some(Brain::Glove { owner_id: o, hit_targets, .. }) = &mut glove.brain {
                if *o == owner_id {
                    hit_targets.push(target_id);
                    // 找到 target,掉血
                    if let Some(t) = world.entities.iter_mut().find(|e| e.id == target_id) {
                        t.hp -= 10;
                    }
                    break;
                }
            }
        }
    }
}
```

这个实现有些复杂,因为 Rust 的借用检查器要求仔细组织 mut 访问。在 C 里 Casey 用指针 + 暂存 list 简化,效果一样。

### 2.3 owner 死亡时的清理

如果 owner 死亡,glove 应该一起消失。Casey 的做法:

```rust
fn cleanup_orphan_attachments(world: &mut World) {
    // 找所有 owner_id,构建集合
    let alive_ids: HashSet<u32> = world.entities.iter().map(|e| e.id).collect();
    // 找所有 attachment,如果 owner 不在 alive_ids,删除
    world.entities.retain(|e| {
        if let Some(Brain::Glove { owner_id, .. }) = e.brain {
            alive_ids.contains(&owner_id)
        } else {
            true
        }
    });
}
```

`retain` 是 Rust 的"过滤保留"——返回 false 的元素被删除。

fn spawn_glove_for_player(world: &mut World, player_id: u32) {

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对"装备 / 武器系统"有成熟设计模式:

- **绑定到骨骼**(3D 游戏):武器挂在角色手骨上,动画自动驱动位置
- **Buff 系统**:buff 也是 attachment,有 owner、duration、effect
- **投射物**:子弹是 attachment(短暂),有 owner 决定敌我
- **Aura(光环)**:队友光环影响所有同队单位

工业级游戏引擎都有 "child entity" 或 "socket"概念:

- Unity:`transform.SetParent(playerTransform)`
- Unreal:`AttachToComponent(playerMesh, "hand_socket")`
- Bevy:`Parent` Component,自动同步 transform

Casey 在 HH 不用骨骼(2D 游戏),用简单的"position 跟随"实现 attachment。

**damage 来源**的设计:

- 子弹打中怪物 → 怪物死亡 → 击杀奖励给谁?给 owner(射击者)
- 玩家被自己子弹打中?很多游戏允许("自杀"),有些禁止(owner 不能伤害 owner)
- 友军伤害?PvP 游戏区分 friendly fire,PvE 一般不区分

owner 字段是所有这些规则的基础。

### 3.2 · 🐧 Linux 系统编程视角

Linux 里"附属关系"对应**进程树**。每个进程有 parent PID,父进程死时子进程被 init(PID 1)收养。这就是 owner 模式的内核版:

- 进程 = entity
- parent PID = owner_id
- init 进程 = "fallback owner"(永远不死)

```bash
# 看进程树
ps -ef --forest
# 输出:
# PID  PPID ...
# 1    0    init
# 100  1    systemd-journald
# 200  1    sshd
# 300  200  sshd: user
# 301  300  bash
# 302  301  vim
```

PPID(parent PID)就是 owner。`vim`(302)的 owner 是 `bash`(301),`bash` 的 owner 是 `sshd`(300),`sshd` 的 owner 是 `init`(1)。

Linux 内核清理孤儿进程:

```c
// kernel/exit.c(简化)
static void forget_original_parent(struct task_struct *father) {
    reparent_children(father, init_task);  // 父死后,孩子过继给 init
}
```

这就是 Casey 的 `cleanup_orphan_attachments` 的内核版。

### 3.3 · 🦀 Rust 生态视角

Rust 表达 attachment 有几种模式:

**模式 1:owner_id 字段(今天 Casey)**

```rust
struct Glove { owner_id: u32 }
```

简单直接。需要查询时遍历 world 找 owner。

**模式 2:HashMap<owner_id, Vec<attachment_id>>**

```rust
struct World {
    attachments: HashMap<u32, Vec<u32>>,  // owner_id -> [attachment_id]
}
```

查询快(O(1)),但要维护同步。

**模式 3:Bevy 的 Parent Component**

```rust
#[derive(Component)]
struct Glove;

#[derive(Component)]
struct Parent(Entity);  // Bevy 内置

// spawn glove 时
commands.entity(player_entity).with_children(|parent| {
    parent.spawn(Glove).insert(Transform::from_xyz(30.0, 0.0, 0.0));
});
```

Bevy 自动同步 child transform 到 parent。这是工业级 attachment 系统。

**借用问题**:Casey 的 `check_glove_hits` 在 Rust 里要小心:

```rust
// 错误:同时 mut 借用 world.entities 多次
for glove in &mut world.entities {
    for target in &mut world.entities {  // 借用冲突!
        ...
    }
}
```

解决:分两阶段——先收集"要伤害的 (glove, target) 对",再统一应用。

```rust
let mut to_damage: Vec<(u32, u32)> = vec![];  // (glove_id, target_id)
{
    let entities = &world.entities;
    for g in entities.iter() {
        for t in entities.iter() {
            if should_damage(g, t) { to_damage.push((g.id, t.id)); }
        }
    }
}
// 应用
for (g_id, t_id) in to_damage {
    // ...
}
```

这是 Rust 借用检查器的常见模式——**收集 → 应用**两阶段。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 glove 需要 `hit_targets` 列表?不加会发生什么?

**参考解答**:不加 hit_targets 时,每帧 glove active 都会触发伤害。glove active 持续 0.3 秒,60 FPS 下是 18 帧,所以一个怪物被命中 18 次,总伤害 180——而设计意图是 10。这就是"连击 bug"。

加 hit_targets 后,每个目标在一次 active 期间只能被伤害一次,符合"挥一次拳头打一下"的直觉。

工业级游戏还加 **invulnerability frames**(无敌帧)——被击中后 0.5 秒不能再被击中,避免连招爆炸。

### Lv2 · 动手实践

**题**:实现 glove 系统:
- 玩家按 A 键触发攻击,glove active 0.3 秒
- glove 在玩家前方 30 像素
- glove 碰到怪物掉血 10
- 怪物掉血后 0.5 秒无敌
- 用 owner_id 区分

完成标准:跑测试场景,玩家攻击一次,怪物掉 10 血(不是 180)。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn length(self) -> f32 { (self.x * self.x + self.y * self.y).sqrt() }
}

#[derive(Clone, Debug)]
enum Brain {
    Player { facing: Vec2, attack_pressed: bool },
    Monster { hp: i32, invuln_timer: f32 },
    Glove { owner_id: u32, active: bool, active_timer: f32, hit_targets: Vec<u32> },
}

#[derive(Clone, Debug)]
struct Entity {
    id: u32,
    pos: Vec2,
    brain: Brain,
}

struct World {
    entities: Vec<Entity>,
    next_id: u32,
}

impl World {
    fn get(&self, id: u32) -> Option<&Entity> {
        self.entities.iter().find(|e| e.id == id)
    }
    fn get_mut(&mut self, id: u32) -> Option<&mut Entity> {
        self.entities.iter_mut().find(|e| e.id == id)
    }
    fn snapshot(&self, id: u32) -> Option<(Vec2, Brain)> {
        self.get(id).map(|e| (e.pos, e.brain.clone()))
    }
}

fn update(world: &mut World, dt: f32) {
    // 阶段 1:触发 attack(玩家)
    let mut to_activate: Vec<u32> = vec![];  // glove ids to activate
    for e in &world.entities {
        if let Brain::Player { attack_pressed: true, .. } = e.brain {
            // 找到自己的 glove
            for g in &world.entities {
                if let Brain::Glove { owner_id, active: false, .. } = g.brain {
                    if owner_id == e.id { to_activate.push(g.id); break; }
                }
            }
        }
    }
    for gid in &to_activate {
        if let Some(g) = world.get_mut(*gid) {
            if let Brain::Glove { active, active_timer, hit_targets, .. } = &mut g.brain {
                *active = true;
                *active_timer = 0.3;
                hit_targets.clear();
            }
        }
    }
    // 重置 attack_pressed
    for e in &mut world.entities {
        if let Brain::Player { attack_pressed, .. } = &mut e.brain {
            *attack_pressed = false;
        }
    }

    // 阶段 2:更新 glove 位置
    let owner_data: Vec<(u32, Vec2, Vec2)> = world.entities.iter()
        .filter_map(|e| match e.brain {
            Brain::Player { facing, .. } => Some((e.id, e.pos, facing)),
            _ => None,
        })
        .collect();
    for e in &mut world.entities {
        if let Brain::Glove { owner_id, active, .. } = &mut e.brain {
            if let Some((_, pos, facing)) = owner_data.iter().find(|(id, _, _)| *id == *owner_id) {
                if *active {
                    e.pos = Vec2::new(pos.x + facing.x * 30.0, pos.y + facing.y * 30.0);
                } else {
                    e.pos = *pos;
                }
            }
        }
    }

    // 阶段 3:active_timer 减
    for e in &mut world.entities {
        if let Brain::Glove { active, active_timer, hit_targets, .. } = &mut e.brain {
            if *active {
                *active_timer -= dt;
                if *active_timer <= 0.0 {
                    *active = false;
                    hit_targets.clear();
                }
            }
        }
    }

    // 阶段 4:碰撞检测 + 伤害
    let mut damages: Vec<(u32, u32)> = vec![];  // (glove_id, target_id)
    for g in &world.entities {
        if let Brain::Glove { owner_id, active: true, hit_targets, .. } = &g.brain {
            for t in &world.entities {
                if t.id == *owner_id { continue; }
                if hit_targets.contains(&t.id) { continue; }
                if let Brain::Monster { invuln_timer: it, .. } = t.brain {
                    if it > 0.0 { continue; }
                }
                if g.pos.sub(t.pos).length() < 30.0 {
                    damages.push((g.id, t.id));
                }
            }
        }
    }
    for (gid, tid) in damages {
        if let Some(g) = world.get_mut(gid) {
            if let Brain::Glove { hit_targets, .. } = &mut g.brain {
                hit_targets.push(tid);
            }
        }
        if let Some(t) = world.get_mut(tid) {
            if let Brain::Monster { hp, invuln_timer, .. } = &mut t.brain {
                *hp -= 10;
                *invuln_timer = 0.5;
                println!("Monster {} hit by glove {}, hp={}", tid, gid, hp);
            }
        }
    }

    // 阶段 5:更新 monster invuln
    for e in &mut world.entities {
        if let Brain::Monster { invuln_timer, .. } = &mut e.brain {
            if *invuln_timer > 0.0 {
                *invuln_timer -= dt;
            }
        }
    }
}

fn main() {
    let mut w = World { entities: vec![], next_id: 0 };
    // 玩家
    let player_id = w.next_id; w.next_id += 1;
    w.entities.push(Entity {
        id: player_id,
        pos: Vec2::new(0.0, 0.0),
        brain: Brain::Player { facing: Vec2::new(1.0, 0.0), attack_pressed: false },
    });
    // 怪物
    let mon_id = w.next_id; w.next_id += 1;
    w.entities.push(Entity {
        id: mon_id,
        pos: Vec2::new(40.0, 0.0),  // 在玩家攻击范围内
        brain: Monster_brain(),
    });
    // 手套
    let glove_id = w.next_id; w.next_id += 1;
    w.entities.push(Entity {
        id: glove_id,
        pos: Vec2::new(0.0, 0.0),
        brain: Brain::Glove { owner_id: player_id, active: false, active_timer: 0.0, hit_targets: vec![] },
    });

    // 按下攻击
    if let Some(p) = w.get_mut(player_id) {
        if let Brain::Player { attack_pressed, .. } = &mut p.brain {
            *attack_pressed = true;
        }
    }

    // 跑 0.5 秒
    let dt = 0.016;
    for _ in 0..30 {
        update(&mut w, dt);
    }

    // 验证:怪物掉 10 血(不是更多)
    let m = w.get(mon_id).unwrap();
    if let Brain::Monster { hp, .. } = m.brain {
        println!("Final monster hp: {}", hp);
        assert_eq!(hp, 90);  // 100 - 10
    }
}

fn Monster_brain() -> Brain {
    Brain::Monster { hp: 100, invuln_timer: 0.0 }
}
```

**每行解释**:
- 阶段 1-5 拆分是因为 Rust 借用检查——不能同时遍历 mut world.entities 多次。
- `to_activate` 收集阶段 1 的结果,阶段 1.5 应用——经典的"两阶段"模式。
- `owner_data` 快照避免阶段 2 借用冲突。
- hit_targets 保证不重复伤害,invuln_timer 提供额外保护。

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
