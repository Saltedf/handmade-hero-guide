
# Day 357 · 基于房间的相机缩放

> HH 是俯视 2D 游戏,玩家在不同房间(室内小、室外大)走动。如果相机 zoom 固定,小房间看不全细节,大房间看不到全貌。今天 Casey 加 **room-based zoom**:相机根据当前房间大小自动调整缩放。

## 0 · 为什么要有这一天

游戏设计的核心问题:**信息密度**。

- 小房间(密室):玩家需要看清楚每个细节(开关、道具)→ 相机放大
- 大房间(户外):玩家需要看周围环境(敌人位置) → 相机缩小
- 走廊:视野要长 → 相机缩到中等

固定 zoom 无法兼顾。游戏设计师需要**根据场景调整 zoom**。

业界做法:

1. **手动标记**:设计师在编辑器里给每个房间标 zoom 值
2. **自动计算**:根据房间包围盒自动算 zoom
3. **玩家控制**:玩家用滚轮调 zoom(策略游戏常用)
4. **混合**:大部分自动,关键时刻手动 override

今天 Casey 实现 1 + 2:每个 room 有 bounding box,相机自动算 zoom 让 bbox 完整显示。这是基础,后续可以加手动 override。

数学上,zoom 计算 = "fit bbox to screen" 问题。给定:

- bbox 宽高(room_width × room_height)
- 屏幕宽高(screen_width × screen_height)
- 求 zoom factor,让 bbox 整个放进屏幕

这是 2D 投影的核心,本质是**保持长宽比(aspect ratio)**的缩放。

心理锚点:今天之后你能实现"自动适应内容大小"的相机,理解长宽比的概念,知道怎么用 zoom 给游戏更好的视觉体验。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 给每个 room 加 `bounding_box` 字段。每帧:

1. 检测玩家当前在哪个 room
2. 拿到该 room 的 bbox
3. 计算合适的 zoom(让 bbox 完整显示)
4. 平滑过渡到新 zoom(避免突变)

核心代码:

```c
f32 compute_room_zoom(room *r, f32 screen_aspect) {
    f32 room_aspect = r->bbox.width / r->bbox.height;
    if (room_aspect > screen_aspect) {
        // 房间比屏幕宽:用宽度决定 zoom
        return screen_width / r->bbox.width;
    } else {
        // 房间比屏幕高:用高度决定 zoom
        return screen_height / r->bbox.height;
    }
}
```

加上平滑过渡:

```c
camera.target_zoom = compute_room_zoom(current_room, screen_aspect);
camera.zoom = lerp(camera.zoom, camera.target_zoom, dt * 5.0);
```

`lerp(a, b, t) = a + (b - a) * t` 是线性插值。`t = dt * 5.0` 表示"每秒靠近 5 倍 dt"——大约 0.2 秒收敛。

## 2 · 心智模型

### 类比:相机取景框

拿手机拍照片,你可以:

- 放大(变焦):看清远处细节,但视野变窄
- 缩小(广角):看更多场景,但细节变模糊

游戏相机同构:

- zoom 大:看得清,但视野窄(适合小房间)
- zoom 小:看得广,但细节糊(适合大房间)

### 长宽比和 fit 算法

屏幕宽高比 = `screen_width / screen_height`(典型 16:9 = 1.78)。

房间 bbox 宽高比 = `room_width / room_height`。

要让 bbox 完整显示:

- 如果房间比屏幕"更长"(room_aspect > screen_aspect):房间的宽是限制因素,zoom = screen_width / room_width
- 如果房间比屏幕"更高"(room_aspect < screen_aspect):房间的高是限制因素,zoom = screen_height / room_height

视觉化:

```
屏幕 16:9        屏幕 16:9
房间 4:3         房间 21:9
┌──────┐        ┌──────────┐
│ ┌──┐ │        │┌────────┐│
│ │  │ │        ││        ││
│ └──┘ │        │└────────┘│
└──────┘        └──────────┘
zoom 受高度限制  zoom 受宽度限制
```

代码:

```rust
fn compute_zoom(room_w: f32, room_h: f32, screen_w: f32, screen_h: f32) -> f32 {
    let room_aspect = room_w / room_h;
    let screen_aspect = screen_w / screen_h;
    if room_aspect > screen_aspect {
        screen_w / room_w  // 房间宽占满屏幕宽
    } else {
        screen_h / room_h  // 房间高占满屏幕高
    }
}
```

### 平滑过渡

zoom 突变会让玩家晕。需要**平滑过渡**——线性插值(lerp):

```rust
fn lerp(a: f32, b: f32, t: f32) -> f32 {
    a + (b - a) * t
}

// 每帧
camera.zoom = lerp(camera.zoom, camera.target_zoom, dt * speed);
```

`speed` 越大,收敛越快。`speed = 5.0` 表示约 0.2 秒到达目标。

更高级:** critically damped spring**——弹簧物理,无超调:

```rust
camera.zoom_vel += (camera.target_zoom - camera.zoom) * stiffness * dt;
camera.zoom_vel *= 1.0 - damping * dt;
camera.zoom += camera.zoom_vel * dt;
```

`stiffness` 是弹簧硬度,`damping` 是阻尼。调好参数,zoom 平滑无超调。

### Room 检测

每帧检测"玩家在哪个 room":

```rust
fn find_current_room(player_pos: Vec2, rooms: &[Room]) -> Option<&Room> {
    rooms.iter().find(|r| {
        player_pos.x >= r.bbox.min_x && player_pos.x <= r.bbox.max_x &&
        player_pos.y >= r.bbox.min_y && player_pos.y <= r.bbox.max_y
    })
}
```

复杂度 O(N)(N 是 room 数)。对大多数游戏 N < 100,够用。

如果 N 大,用空间索引(quadtrees / grid),Day 055 讲过。

### 房间过渡

玩家从 room A 走到 room B:

- 短暂在两个 room 边界(可能在 A 也可能在 B)
- zoom 从 A 的值过渡到 B 的值

如果直接切,玩家走边界时 zoom 反复跳。需要**滞回(hysteresis)**:进入 B 需要走到 B 中心一定距离,而不是 B 边界。

```rust
struct CameraState {
    current_room: usize,
    // 切换房间的"缓冲区"宽度
    hysteresis_margin: f32,
}

impl CameraState {
    fn update(&mut self, player_pos: Vec2, rooms: &[Room]) {
        let cur_room = &rooms[self.current_room];
        // 玩家走出当前 room 边界 + margin 才切
        let inside = player_pos.x > cur_room.bbox.min_x - self.hysteresis_margin &&
                     player_pos.x < cur_room.bbox.max_x + self.hysteresis_margin &&
                     player_pos.y > cur_room.bbox.min_y - self.hysteresis_margin &&
                     player_pos.y < cur_room.bbox.max_y + self.hysteresis_margin;
        if !inside {
            // 找新 room
            if let Some((i, _)) = rooms.iter().enumerate().find(|(_, r)| {
                player_pos.x >= r.bbox.min_x && player_pos.x <= r.bbox.max_x &&
                player_pos.y >= r.bbox.min_y && player_pos.y <= r.bbox.max_y
            }) {
                self.current_room = i;
            }
        }
    }
}
```

### 3.2 · 图形学视角

2D 相机的 zoom 数学:

```
view_matrix = translate(-camera.pos) * scale(camera.zoom)
proj_matrix = orthographic(0, screen_w, 0, screen_h)
final = proj_matrix * view_matrix * world_pos
```

zoom 大于 1 = 放大,zoom 小于 1 = 缩小。

3D 相机的 zoom = FOV(Field of View):

- FOV 大:广角,看更多但变形
- FOV 小:长焦,看远但视野窄

3D 的 zoom 不能像 2D 那样任意——FOV 影响透视投影,极值导致视觉扭曲。

### 3.3 · Linux 系统编程视角

Linux 系统里"根据内容大小调整"的概念:

- **终端 resize**:窗口大小变,文字布局调整
- **图片缩略图**:Nautilus / Thunar 根据可用空间算缩略图大小
- **font hinting**:字体根据 DPI 调整

都是 "fit content to viewport" 模式。

### 3.4 · Rust 生态视角

Rust 实现相机:

```rust
struct Camera2D {
    pos: Vec2,
    zoom: f32,
    target_zoom: f32,
}

impl Camera2D {
    fn update(&mut self, dt: f32, target_pos: Vec2) {
        // 平滑跟随位置
        self.pos = self.pos.lerp(target_pos, dt * 5.0);
        // 平滑过渡 zoom
        self.zoom = self.zoom.lerp(self.target_zoom, dt * 5.0);
    }

    fn world_to_screen(&self, world: Vec2, screen_w: f32, screen_h: f32) -> Vec2 {
        let centered = world - self.pos;
        let scaled = centered * self.zoom;
        Vec2::new(scaled.x + screen_w / 2.0, scaled.y + screen_h / 2.0)
    }
}
```

`glam::Vec2` 已经有 `lerp` 方法。Casey 手写,教学目的。

`macroquad` / `bevy` 都有内置 Camera2D,封装好 zoom、position、rotation。

## 5 · 对照与变奏

### Zoom 的不同算法

**1. Fit(让内容完整显示)**:今天 Casey 的方式。

**2. Fill(让内容填满,可能裁切)**:类似 cover in CSS。

**3. Stretch(拉伸,变形)**:不保持长宽比,丑陋。

**4. Crop + Fit(混合)**:大方向 fit,某方向允许少量裁切。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 zoom 切换要"平滑过渡"而不是"立刻切"?

**参考解答**:

立刻切的问题:

1. **视觉跳变**:玩家瞬间看到不同 zoom,眼睛不适
2. **方向感丢失**:玩家不知道自己在哪(zoom 变了,周围物体大小变)
3. **运动病**:频繁切换引发晕眩(类似 FPS 的镜头切换)

平滑过渡:

1. **眼睛能跟踪**:lerp 给眼睛适应时间
2. **保持方向感**:变化连续,玩家理解"我在移动到新区域"
3. **舒适**:无突变,无晕眩

游戏开发通用规则:**视觉变化要平滑**。除非剧情需要"瞬移",所有镜头/zoom/位置变化都该有过渡。

### Lv2 · 动手实践

**题**:实现 room-based zoom 系统。3 个房间(小、中、大),玩家在房间间切换,zoom 自动调整 + 平滑过渡。

完成标准:跑 100 帧,打印每帧 zoom,看到 zoom 平滑过渡(不是突变)。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn lerp(self, other: Self, t: f32) -> Self {
        Self::new(self.x + (other.x - self.x) * t, self.y + (other.y - self.y) * t)
    }
}

#[derive(Copy, Clone, Debug)]
struct BBox { min: Vec2, max: Vec2 }
impl BBox {
    fn new(min: Vec2, max: Vec2) -> Self { Self { min, max } }
    fn width(&self) -> f32 { self.max.x - self.min.x }
    fn height(&self) -> f32 { self.max.y - self.min.y }
    fn contains(&self, p: Vec2) -> bool {
        p.x >= self.min.x && p.x <= self.max.x &&
        p.y >= self.min.y && p.y <= self.max.y
    }
}

struct Room { bbox: BBox, name: &'static str }

struct Camera {
    pos: Vec2,
    zoom: f32,
    target_zoom: f32,
    current_room: usize,
}

impl Camera {
    fn new() -> Self {
        Self {
            pos: Vec2::new(0.0, 0.0),
            zoom: 1.0,
            target_zoom: 1.0,
            current_room: 0,
        }
    }

    fn compute_room_zoom(room: &Room, screen_w: f32, screen_h: f32) -> f32 {
        let room_aspect = room.bbox.width() / room.bbox.height();
        let screen_aspect = screen_w / screen_h;
        if room_aspect > screen_aspect {
            screen_w / room.bbox.width()
        } else {
            screen_h / room.bbox.height()
        }
    }

    fn update(&mut self, player_pos: Vec2, rooms: &[Room], screen_w: f32, screen_h: f32, dt: f32) {
        // 找当前房间
        for (i, r) in rooms.iter().enumerate() {
            if r.bbox.contains(player_pos) {
                self.current_room = i;
                break;
            }
        }

        // 计算 target zoom
        self.target_zoom = Self::compute_room_zoom(&rooms[self.current_room], screen_w, screen_h);

        // 平滑过渡
        let speed = 5.0;
        self.zoom = lerp_f32(self.zoom, self.target_zoom, (dt * speed).min(1.0));
        self.pos = self.pos.lerp(player_pos, (dt * speed).min(1.0));
    }
}

fn lerp_f32(a: f32, b: f32, t: f32) -> f32 {
    a + (b - a) * t
}

fn main() {
    let rooms = vec![
        Room { bbox: BBox::new(Vec2::new(0.0, 0.0), Vec2::new(10.0, 10.0)), name: "small" },
        Room { bbox: BBox::new(Vec2::new(10.0, 0.0), Vec2::new(40.0, 30.0)), name: "medium" },
        Room { bbox: BBox::new(Vec2::new(40.0, 0.0), Vec2::new(140.0, 80.0)), name: "large" },
    ];

    let mut camera = Camera::new();
    let screen_w = 1920.0;
    let screen_h = 1080.0;
    let dt = 1.0 / 60.0;

    let player_path = vec![
        Vec2::new(5.0, 5.0),    // 在 small room
        Vec2::new(5.0, 5.0),    // 待 30 帧
        Vec2::new(5.0, 5.0),
        Vec2::new(20.0, 15.0),  // 走到 medium
        Vec2::new(20.0, 15.0),
        Vec2::new(20.0, 15.0),
        Vec2::new(80.0, 40.0),  // 走到 large
        Vec2::new(80.0, 40.0),
        Vec2::new(80.0, 40.0),
    ];

    println!("Frame | Player Pos       | Room    | Target Zoom | Current Zoom");
    for (frame, &pos) in player_path.iter().enumerate() {
        camera.update(pos, &rooms, screen_w, screen_h, dt);
        println!("{:5} | ({:6.1}, {:6.1}) | {:7} | {:11.3} | {:13.3}",
                 frame, pos.x, pos.y,
                 rooms[camera.current_room].name,
                 camera.target_zoom, camera.zoom);
    }
}
```

...

## 8 · Rust / Arch 落地代码

### 完整可跑示例

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
    fn scale(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
    fn lerp(self, other: Self, t: f32) -> Self {
        Self::new(self.x + (other.x - self.x) * t, self.y + (other.y - self.y) * t)
    }
}

#[derive(Copy, Clone, Debug)]
struct BBox { min: Vec2, max: Vec2 }
impl BBox {
    fn from_center(center: Vec2, half_w: f32, half_h: f32) -> Self {
        Self {
            min: Vec2::new(center.x - half_w, center.y - half_h),
            max: Vec2::new(center.x + half_w, center.y + half_h),
        }
    }
    fn width(&self) -> f32 { self.max.x - self.min.x }
    fn height(&self) -> f32 { self.max.y - self.min.y }
    fn contains(&self, p: Vec2) -> bool {
        p.x >= self.min.x && p.x <= self.max.x &&
        p.y >= self.min.y && p.y <= self.max.y
    }
    fn center(&self) -> Vec2 {
        Vec2::new(
            (self.min.x + self.max.x) / 2.0,
            (self.min.y + self.max.y) / 2.0,
        )
    }
}

struct Room {
    bbox: BBox,
    name: &'static str,
}

impl Room {
    fn new(name: &'static str, center: Vec2, half_w: f32, half_h: f32) -> Self {
        Self { bbox: BBox::from_center(center, half_w, half_h), name }
    }
}

struct Camera {
    pos: Vec2,
    zoom: f32,
    target_zoom: f32,
    current_room_idx: Option<usize>,
    transition_speed: f32,
}

impl Camera {
    fn new() -> Self {
        Self {
            pos: Vec2::new(0.0, 0.0),
            zoom: 1.0,
            target_zoom: 1.0,
            current_room_idx: None,
            transition_speed: 5.0,
        }
    }

    fn compute_room_zoom(room: &Room, screen_w: f32, screen_h: f32) -> f32 {
        let room_aspect = room.bbox.width() / room.bbox.height();
        let screen_aspect = screen_w / screen_h;
        let zoom = if room_aspect > screen_aspect {
            screen_w / room.bbox.width()
        } else {
            screen_h / room.bbox.height()
        };
        zoom * 0.9  // 留 10% margin
    }

    fn update(&mut self, player_pos: Vec2, rooms: &[Room], screen_w: f32, screen_h: f32, dt: f32) {
        // 找当前房间
        self.current_room_idx = rooms.iter().position(|r| r.bbox.contains(player_pos));

        // 计算 target
        if let Some(idx) = self.current_room_idx {
            self.target_zoom = Self::compute_room_zoom(&rooms[idx], screen_w, screen_h);
        }

        // 平滑过渡
        let t = (dt * self.transition_speed).min(1.0);
        self.zoom = self.zoom + (self.target_zoom - self.zoom) * t;
        self.pos = self.pos.lerp(player_pos, t);
    }

    fn world_to_screen(&self, world: Vec2, screen_w: f32, screen_h: f32) -> Vec2 {
        let centered = world.sub(self.pos);
        let scaled = centered.scale(self.zoom);
        scaled.add(Vec2::new(screen_w / 2.0, screen_h / 2.0))
    }
}

fn main() {
    let rooms = vec![
        Room::new("hallway", Vec2::new(0.0, 0.0), 50.0, 5.0),
        Room::new("small", Vec2::new(60.0, 0.0), 10.0, 10.0),
        Room::new("medium", Vec2::new(100.0, 0.0), 30.0, 20.0),
        Room::new("large", Vec2::new(180.0, 0.0), 80.0, 60.0),
    ];

    let mut camera = Camera::new();
    let screen_w = 1920.0;
    let screen_h = 1080.0;
    let dt = 1.0 / 60.0;

    // 模拟玩家移动
    let player_positions: Vec<Vec2> = (0..100).map(|i| {
        let t = i as f32 / 100.0;
        Vec2::new(t * 250.0, 0.0)  // 从 0 走到 250
    }).collect();

    println!("Frame | Player     | Room     | Target Zoom | Zoom       | Screen Pos");
    for (frame, &pos) in player_positions.iter().enumerate().step_by(10) {
        camera.update(pos, &rooms, screen_w, screen_h, dt);
        let screen = camera.world_to_screen(pos, screen_w, screen_h);
        let room_name = camera.current_room_idx
            .map(|i| rooms[i].name)
            .unwrap_or("outside");
        println!("{:5} | ({:6.1}, 0) | {:8} | {:11.2} | {:10.2} | ({:6.0}, {:6.0})",
                 frame, pos.x, room_name, camera.target_zoom, camera.zoom,
                 screen.x, screen.y);
    }
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
