
# Day 428 · 光跟踪与每秒光子数成比例

> 之前的光照单位是"任意"——`intensity: f32` 没明确含义,调参靠试错。今天 Casey 把光照单位**物理化**——`intensity` 单位变成"每秒发射的光子数",光照计算变成"接收到的光子数比例"。这让多个光源相加自然、参数有物理意义、调参不再玄学。

## 0 · 为什么要有这一天

具体场景:你给一个手电筒光源设 `intensity = 50`,给天花板灯设 `intensity = 100`。两个光叠加,某些区域可能爆白(总和 > 1,被 clamp),某些区域可能太暗(总和太小)。怎么平衡?

如果光照单位是"任意数字",你只能试错——改一个,看效果,再改。10 个光源的平衡需要几百次试错。

物理化光照:**intensity 单位 = 流明 / 瓦 / 坎德拉**(实际物理量)。两个 100 流明的灯叠加 = 200 流明,物理正确。光源参数有真实意义(手电筒 ~100 流明,LED 灯泡 ~800 流明,汽车大灯 ~1200 流明)。

更深层:**渲染中的"亮度"应该和真实物理一致**。人眼对 100 流明 + 100 流明的感知 = 200 流明的感知(线性),而不是某种"叠加算法"。物理化让渲染**符合直觉**。

工业的物理光照:

- **流明(lumen)**:总光通量(光源发出的可见光功率)
- **坎德拉(candela)**:单位立体角的光通量
- **勒克斯(lux)**:单位面积接收的光通量
- **尼特(nit)**:单位面积的发光强度

游戏引擎(Unreal、Unity)都用真实物理单位,光源面板显示流明。Casey 今天把 HH 改成物理单位。

实现:用"每秒光子数"(photons/s)作为最基础单位。其他单位(流明)可以转换。光照计算变成"接收光子数 = 发射 × 几何衰减 × 可见性"。

心理锚点:今天之后,你能解释流明、勒克斯、坎德拉的区别,能在游戏中用真实物理参数调光照,理解为什么 PBR(physically based rendering)必须用物理单位。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 把光照系统改成物理单位:

1. **单位定义**:`intensity: f32` 单位变成"瓦特(光辐射功率)",或"流明(可见光通量)"
2. **物理衰减**:用平方反比定律,不再有"我自定义的衰减函数"
3. **光谱响应**:考虑人眼对不同波长的敏感度(V(λ)函数)
4. **多光源叠加**:简单加法,无 clamp(在 tone mapping 阶段才 clamp)

具体代码改动:

```rust
// 旧:intensity 没单位,衰减自定义
fn attenuation(dist: f32) -> f32 {
    1.0 / (1.0 + dist * 0.1)  // 经验公式
}

// 新:intensity = 流明,衰减 = 物理平方反比
fn attenuation(dist: f32) -> f32 {
    1.0 / (dist * dist)  // 物理正确
}
```

Casey 强调:**物理正确不等于视觉好**。物理平方反比在小距离时光强爆炸(1m² = 1, 0.1m² = 100),需要 tone mapping 压缩。但物理正确保证**多光源叠加自然**。

## 2 · 心智模型

### 类比:水管注水

想象你用一根水管往水池注水。水管的流量单位是"升/秒"。两根水管同时注水,总流量 = 流量 1 + 流量 2。

光照完全同构。光源 = 水管,"光子/秒" = "升/秒"。两个光源照同一面墙,总光子数 = 各自的和。

水池的"水位"= 墙的"亮度"。水位(亮度)随时间累积,直到平衡(光源关闭后水位不变,但光照是即时的,所以亮度等于"当前流量"乘以某个系数)。

物理单位让你**用直觉调参**:想加亮一倍,把流明 x 2;想让远处一样亮,把流明按距离平方放大。

### 严谨原理:辐射度量学

辐射度量学(radiometry)定义了几个核心量:

| 量 | 单位 | 含义 |
|---|---|---|
| Radiant flux(辐射通量) | W (瓦特) | 总辐射能量 / 时间 |
| Radiance(辐射度) | W/(m²·sr) | 单位面积单位立体角的能量 |
| Irradiance(辐照度) | W/m² | 单位面积接收的能量 |
| Radiant intensity(辐射强度) | W/sr | 单位立体角的能量 |

光度学(photometry)对应:

| 量 | 单位 | 含义 |
|---|---|---|
| Luminous flux(光通量) | lumen(流明) | 可见光辐射通量(人眼加权) |
| Luminance(亮度) | cd/m²(尼特) | 单位面积单位立体角 |
| Illuminance(照度) | lux(勒克斯) | 单位面积接收 |
| Luminous intensity(发光强度) | candela(坎德拉) | 单位立体角 |

转换:`1 流明 = 1/683 瓦特`(在 555nm 绿光最敏感波长)。

### 平方反比定律

点光源的辐射:总功率 P 均匀分布在球面。距离 r 处的球面面积 = 4πr²,单位面积接收 = P / (4πr²)。

**距离翻倍,亮度变 1/4**(平方反比)。这是物理定律,不可违反。

工业光照用平方反比,加上"反平方修正"避免近距离爆炸(距离 < 0.1m 时 clamp)。

### Rust 视角:物理光照

```rust
pub struct LightSource {
    pub luminous_flux: f32,  // 流明
    pub color: Vec3,         // RGB,描述光谱
    pub position: Vec3,
}

impl LightSource {
    pub fn illuminate(&self, point: Vec3, normal: Vec3) -> Vec3 {
        let dir = self.position - point;
        let dist = dir.length();
        if dist < 0.01 { return Vec3::ZERO; }  // 反平方修正
        let n_dot_l = normal.dot(dir / dist).max(0.0);
        if n_dot_l == 0.0 { return Vec3::ZERO; }

        // 平方反比
        let attenuation = 1.0 / (dist * dist);

        // 总光通量 × 衰减 × 余弦 = 该点照度(lux)
        let illuminance = self.luminous_flux * attenuation * n_dot_l;

        // 颜色加权(模拟光谱)
        self.color * illuminance
    }
}
```

`luminous_flux * attenuation` 单位分析:

- luminous_flux: 流明 = 坎德拉 × 球面度
- attenuation: 1/m²
- 乘积: 坎德拉 × 球面度 / m² = 勒克斯(lux)

物理正确。

### Tone Mapping

物理单位的光照值范围广(0.001 lux 月光 到 100000 lux 太阳)。直接显示会爆白。**tone mapping** 把 HDR 值映射到 [0, 1] 显示:

```rust
pub fn tonemap_aces(hdr: Vec3) -> Vec3 {
    // ACES filmic tone mapping
    let a = 2.51;
    let b = 0.03;
    let c = 2.43;
    let d = 0.59;
    let e = 0.14;
    (hdr * (hdr * a + Vec3::splat(b)))
        / (hdr * (hdr * Vec3::splat(c) + Vec3::splat(d)) + Vec3::splat(e))
        .clamp(Vec3::ZERO, Vec3::ONE)
}
```

ACES 是工业主流,Unreal、Unity 都用。Casey 用更简单的 Reinhard:`x / (1 + x)`。

### 多光源叠加

```rust
let total_lighting: Vec3 = scene.lights.iter()
    .map(|l| l.illuminate(point, normal))
    .sum();
let display = tonemap(total_lighting);
```

物理正确——每个光源贡献照度(lux),总和是总照度。tone mapping 一次性处理 HDR → LDR。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么平方反比定律在游戏中容易出 bug?具体说,什么情况下会爆白?

**参考解答**:平方反比:`attenuation = 1 / dist²`。当 dist 很小时:

- dist = 1m:attenuation = 1
- dist = 0.1m:attenuation = 100
- dist = 0.01m:attenuation = 10000
- dist = 0.001m:attenuation = 1百万

光源非常靠近被照亮物体时,亮度爆炸。游戏场景里,玩家贴墙站立时火把距离墙 ~0.1m,attenuation = 100,墙面爆白。

工业解决:

1. **最小距离 clamp**:`dist = max(dist, 0.1)`,避免距离过小
2. **平滑函数**:`1 / (dist² + 0.1²)`,在 dist→0 时收敛到 100(不爆炸)
3. **Tone mapping**:HDR → [0, 1],自动压缩高亮

第 2 种叫"反平方加 epsilon",工业最常用。

### Lv2 · 动手实践

**题**:实现物理光照(流明 + 平方反比 + ACES tone mapping)。完成标准:
- 不同流明的光源视觉差异符合直觉(100 流明弱,1000 流明亮)
- 两光源叠加无爆白(由 tone mapping 压缩)
- 距离平方反比:1m 远 4 倍暗于 0.5m 远

**参考解答**:

```rust
use glam::Vec3;

pub struct PhysicalLight {
    pub luminous_flux: f32,  // 流明
    pub color: Vec3,
    pub position: Vec3,
}

impl PhysicalLight {
    pub fn illuminate(&self, point: Vec3, normal: Vec3) -> Vec3 {
        let dir = self.position - point;
        let dist2 = dir.length_squared();
        // 反平方加 epsilon,避免距离过近爆炸
        let eps = 0.01;
        let attenuation = 1.0 / (dist2 + eps);
        let dist = dist2.sqrt();
        if dist < 1e-6 { return Vec3::ZERO; }
        let n_dot_l = normal.dot(dir / dist).max(0.0);
        if n_dot_l == 0.0 { return Vec3::ZERO; }
        // illuminance (lux) = lumens × attenuation × cos(theta)
        let illuminance = self.luminous_flux * attenuation * n_dot_l;
        self.color * illuminance
    }
}

pub fn tonemap_aces(hdr: Vec3) -> Vec3 {
    let a = 2.51; let b = 0.03;
    let c = 2.43; let d = 0.59; let e = 0.14;
    let num = hdr * (hdr * a + b);
    let den = hdr * (hdr * c + d) + e;
    (num / den).clamp(Vec3::ZERO, Vec3::ONE)
}

pub fn tonemap_reinhard(hdr: Vec3) -> Vec3 {
    hdr / (Vec3::ONE + hdr)
}

fn main() {
    let normal = Vec3::Y;
    let point = Vec3::ZERO;

    let torch = PhysicalLight {
        luminous_flux: 100.0,  // 火把 ~100 流明
        color: Vec3::new(1.0, 0.8, 0.5),
        position: Vec3::new(0.0, 1.0, 0.0),  // 1m 远
    };

    let ceiling = PhysicalLight {
        luminous_flux: 1500.0,  // LED 灯 ~1500 流明
        color: Vec3::ONE,
        position: Vec3::new(0.0, 3.0, 0.0),  // 3m 远
    };

    // 单光源
    let l1 = torch.illuminate(point, normal);
    let l2 = ceiling.illuminate(point, normal);
    let total = l1 + l2;
    println!("Torch illuminance: {:?}", l1);
    println!("Ceiling illuminance: {:?}", l2);
    println!("Total HDR: {:?}", total);
    println!("ACES tone mapped: {:?}", tonemap_aces(total));
    println!("Reinhard tone mapped: {:?}", tonemap_reinhard(total));

    // 验证距离平方反比
    let l_near = torch.illuminate(Vec3::new(0.0, 0.5, 0.0), normal);  // 0.5m
    let l_far = torch.illuminate(Vec3::new(0.0, 1.0, 0.0), normal);   // 1.0m
    let ratio = l_near.x / l_far.x;
    println!("\nDistance ratio: 0.5m / 1.0m");
    println!("  Light ratio: {:.2} (expected ~4, due to inverse square)", ratio);
}
```

## 8 · Rust / Arch 落地代码

```rust
use glam::Vec3;

/// 流明(newtype,编译期防止单位混用)
#[derive(Copy, Clone, Debug, PartialEq, PartialOrd)]
pub struct Lumen(pub f32);

/// 勒克斯
#[derive(Copy, Clone, Debug, PartialEq, PartialOrd)]
pub struct Lux(pub f32);

impl std::ops::Add for Lumen {
    type Output = Lumen;
    fn add(self, other: Lumen) -> Lumen { Lumen(self.0 + other.0) }
}

pub struct PhysicalLight {
    pub luminous_flux: Lumen,
    pub color: Vec3,
    pub position: Vec3,
}

impl PhysicalLight {
    pub fn illuminate(&self, point: Vec3, normal: Vec3) -> Lux {
        let dir = self.position - point;
        let dist2 = dir.length_squared();
        if dist2 < 1e-6 { return Lux(0.0); }
        let dist = dist2.sqrt();
        // 反平方 + epsilon 防爆炸
        let attenuation = 1.0 / (dist2 + 0.01);
        let n_dot_l = normal.dot(dir / dist).max(0.0);
        if n_dot_l == 0.0 { return Lux(0.0); }
        Lux(self.luminous_flux.0 * attenuation * n_dot_l)
    }

    pub fn illuminate_colored(&self, point: Vec3, normal: Vec3) -> Vec3 {
        let illuminance = self.illuminate(point, normal);
        self.color * illuminance.0
    }
}

pub fn tonemap_aces(hdr: Vec3) -> Vec3 {
    let a = 2.51; let b = 0.03;
    let c = 2.43; let d = 0.59; let e = 0.14;
    let num = hdr * (hdr * a + b);
    let den = hdr * (hdr * c + d) + e;
    (num / den).clamp(Vec3::ZERO, Vec3::ONE)
}

pub fn tonemap_reinhard(hdr: Vec3) -> Vec3 {
    hdr / (Vec3::ONE + hdr)
}

pub fn tonemap_exposure(hdr: Vec3, exposure: f32) -> Vec3 {
    hdr * exposure
}

fn main() {
    println!("=== Physical lighting demo ===\n");

    let lights = vec![
        PhysicalLight {
            luminous_flux: Lumen(100.0),  // 火把
            color: Vec3::new(1.0, 0.8, 0.5),
            position: Vec3::new(1.0, 1.0, 0.0),
        },
        PhysicalLight {
            luminous_flux: Lumen(1500.0),  // LED
            color: Vec3::ONE,
            position: Vec3::new(0.0, 3.0, 0.0),
        },
        PhysicalLight {
            luminous_flux: Lumen(12000.0),  // 汽车大灯
            color: Vec3::new(1.0, 1.0, 0.9),
            position: Vec3::new(0.0, 0.5, 5.0),
        },
    ];

    let point = Vec3::ZERO;
    let normal = Vec3::Y;

    // 单光源照度
    for (i, light) in lights.iter().enumerate() {
        let lux = light.illuminate(point, normal);
        println!("Light {}: flux={} lm -> illuminance={:.2} lux",
            i, light.luminous_flux.0, lux.0);
    }

    // 总照度(物理正确叠加)
    let total: Lux = lights.iter()
        .map(|l| l.illuminate(point, normal))
        .fold(Lux(0.0), |acc, x| Lux(acc.0 + x.0));
    println!("\nTotal illuminance: {:.2} lux", total.0);
    println!("(For reference: full daylight ~10000 lux, office ~500 lux)");

    // 彩色叠加
    let total_colored: Vec3 = lights.iter()
        .map(|l| l.illuminate_colored(point, normal))
        .sum();
    println!("\nTotal HDR color: {:?}", total_colored);
    println!("ACES tonemap: {:?}", tonemap_aces(total_colored));
    println!("Reinhard tonemap: {:?}", tonemap_reinhard(total_colored));
    println!("Exposure(0.01): {:?}", tonemap_exposure(total_colored, 0.01));

    // 距离平方反比验证
    println!("\n=== Inverse square law ===");
    let torch = &lights[0];
    let distances = [0.5, 1.0, 2.0, 4.0];
    for d in distances {
        let p = Vec3::new(d, 1.0, 0.0);
        let lux = torch.illuminate(p, normal);
        println!("  dist={} -> {:.2} lux", d, lux.0);
    }
}
```

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
