
# Day 299 · 改进排序键 第二部分

> 昨天的 64 位 sort key 解决了"多因素排序"。但今天 Casey 发现新问题:**有些实体的 sprite 不是点,是矩形**——用 sprite 中心点排序会错位。今天引入 **sprite bounds**(sprite 边界),用 sprite 底部 y 而非中心 y 排序。

## 0 · 为什么要有这一天

考虑一个高 sprite(2 米高的巨人)和一个矮 sprite(0.5 米高的矮人)。如果用中心点 y 排序:

- 巨人中心 y = 100
- 矮人中心 y = 100

两者 y 相同,sort 不区分。但**视觉上**:巨人在矮人后面,矮人应该被巨人遮住(因为巨人更高,挡视线)。

正确的排序应该是按 **sprite 底部 y**(脚的位置):

- 巨人底部 y = 130(中心 y=100,高度 60,底部在 100+30=130)
- 矮人底部 y = 110(中心 y=100,高度 20,底部在 100+10=110)

按底部 y 排:矮人(110)在巨人(130)前面画——视觉上矮人在巨人前。

这就是今天的工作:**sort key 用 sprite 底部 y,而非中心 y**。

听起来简单,但实现时要处理:

- **每个 sprite 的 bounds**——宽、高、相对中心的偏移
- **底部 y 计算**——`bottom_y = pos.y + sprite.half_height`(或类似)
- **debug 验证**——画 debug 线显示 bottom_y,确认正确

心理锚点:看完今天,你应该理解"sprite 不是点,有尺寸",sort key 要考虑这个尺寸。

## 1 · Casey 今天做了什么

Casey 今天的动作:

1. **给 Visual 加 bounds**——每个 sprite 有 width/height/offset
2. **修改 sort_key 用 bottom_y**——`bottom_y = pos.y + bounds.bottom_offset`
3. **加 debug 可视化**——画 sprite bounds 框 + bottom y 标线
4. **测试**——高 sprite 和矮 sprite 重叠,验证遮挡正确

今天的核心是**几何思维**——sprite 是矩形,sort key 要用矩形边界而非中心点。

## 2 · 心智模型

### 类比:舞台上的演员站位

想象舞台上多个演员。导演要决定谁站前面谁站后面。如果只看演员的"中心"位置,你不知道演员的身高——一个 2 米巨人和一个 1 米小孩站在同一中心点,谁前?

正确做法是看**脚的位置**——脚在前的人在前面(更靠近观众)。巨人脚在 1.5m 处,小孩脚在 0.5m 处(假设都站在 1.5m 平台上,巨人更高所以脚位置更高?),等等——这个类比要重新想。

更好的类比:**纸片人**。每个 sprite 是一张纸片,纸片底部贴在地面上,纸片高度不同。从相机视角,纸片底部的 y 决定它在画面上的"前后"——底部 y 大(屏幕下方)的更前,底部 y 小(屏幕上方)的更后。

```
屏幕坐标(y 向下为正):
巨人:   [头部]    sprite 高 60,bottom_y = 100+30=130
矮人:   [头]     sprite 高 20,bottom_y = 100+10=110
平面:   ___         ___
        \___________/
              y=100(中心)
```

巨人底部 130 > 矮人底部 110,所以巨人更前(底部更靠近屏幕下方)。但实际上视觉上:**矮人应该被巨人挡住**(巨人更高,在矮人后面挡住一半)?

这取决于游戏设计——通常"在地面上的物体"按底部 y 排,底部 y 大(下方)的更前。**巨人更高,但巨人脚的位置在哪?**

如果巨人脚和矮人脚在同一地面(y=120),巨人头部到 y=60(高 60),矮人头部到 y=100(高 20)。底部都是 120。同底部 y——按 spawn_id 或 x 决定。

如果巨人脚在 y=130(更前),矮人脚在 y=120(更后),巨人更前——遮挡矮人。

关键:**sprite 的 bottom y 决定它在画面前后**。今天 Casey 用 bottom_y 排序。

### 2.1 sprite bounds 结构

```rust
#[derive(Copy, Clone)]
struct SpriteBounds {
    width: f32,         // sprite 宽(像素)
    height: f32,        // sprite 高(像素)
    center_offset: Vec2,  // sprite 中心相对 entity pos 的偏移(0,0 = sprite 中心对齐 pos)
}

impl SpriteBounds {
    fn bottom_y(&self, pos: Vec2) -> f32 {
        pos.y + self.center_offset.y + self.height / 2.0
    }
}
```

每个 sprite 在资产加载时确定 bounds。比如:

- Player sprite:32x48,center_offset (0, 0),bottom_y = pos.y + 24
- Monster sprite:64x80,center_offset (0, -8),bottom_y = pos.y + 32
- Tile sprite:32x32,center_offset (0, 0),bottom_y = pos.y + 16

### 2.2 修改 sort_key

```rust
fn sort_key(e: &Entity, sprite_table: &SpriteTable) -> u64 {
    let layer = e.layer as u64;
    let bounds = sprite_table.get(e.visual);
    let bottom_y = bounds.bottom_y(e.pos).max(0.0).min(65535.0) as u64;
    let x = (e.pos.x.max(0.0).min(65535.0)) as u64;
    let spawn = e.spawn_id as u64;
    (layer << 56) | (bottom_y << 40) | (x << 24) | spawn
}
```

注意:`bottom_y` 替代了之前的 `pos.y`。其他因素不变。

### 2.3 debug 可视化

```rust
fn render_debug(e: &Entity, sprite_table: &SpriteTable) {
    let bounds = sprite_table.get(e.visual);
    let bottom_y = bounds.bottom_y(e.pos);
    // 画 sprite bounds 框
    draw_rect_outline(
        e.pos.x - bounds.width / 2.0 + bounds.center_offset.x,
        e.pos.y - bounds.height / 2.0 + bounds.center_offset.y,
        bounds.width, bounds.height,
        Color::GREEN,
    );
    // 画 bottom y 标线
    draw_line(
        e.pos.x - 20.0, bottom_y,
        e.pos.x + 20.0, bottom_y,
        Color::RED,
    );
}
```

红线显示 bottom_y,绿框显示 sprite bounds。这样开发时能立刻看出 sort key 是否合理。

### 2.4 tile 的特殊处理

地面 tile 不需要按 bottom_y 排序——所有 tile 在同一层,bottom_y 都差不多。它们按 (x, y) 网格位置排:

```rust
fn sort_key(e: &Entity, sprite_table: &SpriteTable) -> u64 {
    let layer = e.layer as u64;
    let key = match e.layer {
        Layer::Ground => {
            // tile:按 网格 排
            let grid_x = (e.pos.x / 32.0) as u64;
            let grid_y = (e.pos.y / 32.0) as u64;
            grid_y << 16 | grid_x
        }
        Layer::Entity => {
            // 实体:按 bottom_y + x
            let bounds = sprite_table.get(e.visual);
            let bottom_y = bounds.bottom_y(e.pos).max(0.0) as u64;
            let x = e.pos.x.max(0.0) as u64;
            (bottom_y << 16) | x
        }
        _ => 0,
    };
    (layer << 56) | key
}
```

不同 layer 内部用不同排序策略——分层架构的灵活性。

---

**总结**:今天的核心是 **sprite bounds + bottom_y 排序**。高 sprite 和矮 sprite 按"脚的位置"排,不是按中心排。debug 用红线显示 bottom_y,绿框显示 bounds。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业关于 sprite bounds 有标准做法:

- **pivot point**(锚点):sprite 的"基准点",通常是底部中心(角色)、中心(道具)、左上角(UI)
- **anchor**:sprite 在 entity 上的对齐方式——bottom_center、top_left、center
- **origin**:同 pivot,不同引擎叫法不同

Unity 的 Sprite 有 `pivot` 属性,美术在 Sprite Editor 设置。Casey 在 HH 自己实现等价物。

工业级 Y-sort 的细节:

- 角色按脚 pivot 排序(脚在前 = 屏幕下方 = 离相机近)
- 道具按中心 pivot(无脚概念)
- 飞行单位按"影子位置"排(影子的 y 决定前后)
- 摆动的尾巴 / 头发等附属物随主体排,不独立

### 3.2 · 🎨 图形学视角

3D 图形学的"sort"对应 **depth**——每个顶点有 z 值。但 sprite 是 2D,没有真 z,用 sort key 模拟。

3D 渲染里类似的考虑:

- **billboard sprite**:3D 场景中的 2D sprite(如树木),通常按"sprite 到 camera 的距离"排
- **particle system**:粒子按 depth 排,半透明粒子从后向前画
- ** impostor**(替代体):远处复杂物体用 sprite 替代,sort 类似 billboard

Casey 在 Phase 8 切到 OpenGL 后会处理这些。

### 3.3 · 🐧 Linux 系统编程视角

Linux 里"按边界排序"对应**矩形区域合并**。比如:

- **damage tracking**(compositor):窗口部分区域被遮挡,只在可见区域合成
- **clip region**:Graphics 库(GTK、Cairo)用矩形 list 表示 clip 区域,按位置 sort 优化

Wayland 协议有 `wl_surface.damage(x, y, w, h)`——告诉合成器"这块区域脏了"。合成器收集多个 damage rect,合并后高效更新。合并算法里 sort 是关键。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 sprite bounds:

```rust
#[derive(Copy, Clone, Debug)]
struct Rect { x: f32, y: f32, w: f32, h: f32 }

impl Rect {
    fn bottom(&self) -> f32 { self.y + self.h }
    fn top(&self) -> f32 { self.y }
    fn center(&self) -> Vec2 { Vec2::new(self.x + self.w / 2.0, self.y + self.h / 2.0) }
}
```

`bevy_sprite::Sprite` 有 `custom_size: Option<Vec2>` 和 `anchor: Anchor`,对应今天的 bounds。

工业代码用 Rect 表达 sprite 边界,sort key 用 `rect.bottom()`。

## 5 · 对照与变奏

### sprite pivot 在不同游戏

| 游戏 | 默认 pivot |
|---|---|
| 2D 像素(Stardew Valley) | 底部中心 |
| 动作平台(Hollow Knight) | 底部中心,部分用中心 |
| RPG(RPG Maker) | 中心 |
| RTS(Starcraft) | 底部 |
| 卡牌游戏(Hearthstone) | 中心 |

底部中心最适合 Y-sort,因为"脚的位置"自然映射到"前后"。

### 不同视角的 sort

| 视角 | Sort 标准 |
|---|---|
| Top-down(俯视) | y(屏幕 y) |
| Side-scroll(横版) | z(深度,通常 entity 在前,背景在后) |
| Isometric(等距) | y + x 组合 |
| 3D 第三人称 | depth(distance to camera) |

Casey HH 是 top-down 视角,y-sort。

### 历史演化

- **1980s**:简单按 y 排,无 pivot 概念
- **1990s**:引入 pivot / anchor(SNES RPG)
- **2000s**:Unity 等引擎把 pivot 作为标准属性
- **2010s**:bevy 等 ECS 引擎支持自定义 pivot
- **2020s**:GPU instancing 让 pivot 计算更高效

**题**:实现 sprite bounds 系统,3 个实体:

- 矮人:中心 (100, 100),size (16, 32)
- 树:中心 (100, 100),size (48, 80)

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug)]
struct Bounds { w: f32, h: f32 }

impl Bounds {
    fn bottom_y(&self, pos: Vec2) -> f32 {
        pos.y + self.h / 2.0
    }
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec2,
    bounds: Bounds,
    name: &'static str,
}

fn main() {
    let mut entities = vec![
        Entity { pos: Vec2::new(100.0, 100.0), bounds: Bounds { w: 32.0, h: 64.0 }, name: "Giant" },
        Entity { pos: Vec2::new(100.0, 100.0), bounds: Bounds { w: 16.0, h: 32.0 }, name: "Dwarf" },
        Entity { pos: Vec2::new(100.0, 100.0), bounds: Bounds { w: 48.0, h: 80.0 }, name: "Tree" },
    ];

    entities.sort_by_key(|e| e.bounds.bottom_y(e.pos) as u64);
    for e in &entities {
        println!("{} bottom_y = {}", e.name, e.bounds.bottom_y(e.pos));
    }

    assert_eq!(entities[0].name, "Dwarf");
    assert_eq!(entities[1].name, "Giant");
    assert_eq!(entities[2].name, "Tree");
    println!("Sprite bounds sort test passed!");
}
```

**每行解释**:
- `Bounds { w, h }` — sprite 尺寸
- `bottom_y = pos.y + h/2` — 中心 y + 半高 = 底部 y
- 按底部 y 排,矮人(116)< 巨人(132)< 树(140)

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
