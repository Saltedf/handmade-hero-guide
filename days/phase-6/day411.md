
# Day 411 · 切换到矩形光照元素

> 之前的光照采样都是"点"——一个无穷小的位置上有一点光。今天 Casey 把光源从点扩展到**矩形面积光(rectangular area light)**,让阴影从硬边变柔和,让墙面上的光照分布从"一个亮斑"变成"一片渐变"。这是离真实渲染最近的一步,也直接逼出后续一系列空间层次与 SIMD 优化。

## 0 · 为什么要有这一天

把你拽回一个具体问题:你的角色拿火把站在墙边。火把是一个有体积的物体,火苗本身大约十厘米宽。如果你用**点光源**照亮墙面,墙上的亮斑形状是一个**完美圆**,从中心向边缘锐利衰减——这是错的。真实的火把在墙上留下的是一个**模糊的椭圆**,因为火苗本身有面积,墙上每一点"看见"火苗的角度不同,看见的部分越大,这一点就越亮。

这个"墙上每个点接收多少光"的问题,本质上是**对面光源做积分**:把面光源拆成无数个小点,每个点对墙面某点的贡献累加,最后归一化。点光源做不到这个效果,因为它是狄拉克 δ 函数(空间中的一点),积分退化成单点采样。

工业渲染器解决这个问题的标准做法叫**面积光(area light)**。它的几何描述是:用一个有面积的形状(矩形、圆盘、球体)代替一个点,然后**对每个被照亮的像素**做"它看见了光源的多少面积"的积分。这一步在 2014 年的 Mitsuba / 2016 年的 Unreal ASEAN 之后才进入工业主流,Casey 现在用纯 CPU 实现一个朴素版本——为后续 SIMD 光线追踪铺路。

为什么必须切换到矩形?有两个工程上的硬理由。第一,HH 的光照是基于**体素(voxel)光照传播**的——把空间切成小立方体,每个体素存光强,然后光在体素间扩散。如果光源是点,只有光所在的那个体素有光,周围体素靠"传播"得到光。这导致**强锯齿**:体素网格越粗,亮斑形状越像方块。如果光源本身是矩形,可以覆盖多个体素,初始分布就柔和。第二,矩形可以直接做 ray-AABB 相交(后续 day422),而圆/球需要更复杂的解析公式。**矩形是工程上最划算的"够好"选择**。

心理锚点:今天之后,你能解释"为什么点光源不能产生柔和阴影",能用一个 `Bounds3` 结构表达面积光,能在代码里看到从"一个点采一个值"到"在一个矩形里采多个值求平均"的范式跃迁。这一天是 SIMD 之前最后一次"几何重定义",理解了它,后面 day431 的 4-wide 光线投射就有了清晰的几何目标。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 在前几集已经把点光源接到体素光照传播管线里。今天他做了一个看起来小、实际牵动整个管线的改动:**把光源的存储从单个 `Vec3 p` 改成 `Bounds3 rect`**,然后**让光照计算在每个矩形里采样多个点**,而不是只看矩形中心一个点。

具体动作:

1. 在光源 struct 里新增 `min_corner: Vec3` 和 `max_corner: Vec3`,保留中心 `p` 作为只读派生量。
2. 在体素光照注入函数里,把"对光所在体素注入光强"改成"对光覆盖的所有体素注入光强"——通过遍历矩形覆盖的 AABB 实现。
3. 在 per-pixel 着色阶段,把"对每个像素从光源中心连一条 ray"改成"在矩形里随机/网格采样 N 个点,每个点连一条 ray,平均"。
4. 引入**采样数 N**作为可调参数,N=1 等价于点光源,N=16 已经看起来柔和。

Casey 没一次写完。他先在白板上画了"矩形覆盖哪些体素"的二维图,然后纠结于"边界体素怎么算"——矩形可能正好压在体素网格线上,严格几何上只覆盖半个体素,工程上要么向上要么向下取整。他选了**保守放大**:把矩形外扩到覆盖任何被它接触的体素,宁可多一些体素也别漏。这是后续光照过多 bug 的伏笔(day419)。

最后他强调:这一步**不是为了视觉效果**(此时采样数还是 1,效果和点光源几乎一样),而是为了**重构数据结构**,让后续真正能用多采样时不用再改 struct。

## 2 · 心智模型

### 类比:从"灯泡"到"灯管"

想象两种光源。**白炽灯泡**:一个玻璃球,从中心点发光,房间里的影子是硬边——你站在墙前,影子轮廓清晰。**日光灯管**:一根长管子,沿着整根管都在发光,墙上的影子是软的——靠近灯管中段影子更硬,远离的部分影子完全模糊。

为什么软?因为墙上**每一个点**看见灯管的角度不同。站在灯管正下方的点,看见整根管;偏一点,看见的管就短;偏得更远,只看见管的端点。**影子边缘正是"从这一点看,光源被物体部分遮挡"的区域**——只有部分光源可见,所以光强按可见比例衰减,影子就软了。

这个"每个像素看见多少光源"的量,叫**可见立体角(solid angle)**。点光源的立体角是无穷小的 δ,要么完全可见要么完全不可见——所以影子是硬的。面积光的立体角是连续的——可以部分可见——所以影子是软的。

### 严谨原理:对面积光积分

数学上,被照亮的点 x 接收的辐射度(radiance)是:

```
L(x) = ∫∫_A  L_emit(p) * V(x, p) * G(x, p)  dp
```

- A 是面积光的表面(矩形面积)
- p 是光源上的一个点
- L_emit(p) 是 p 处的发光强度
- V(x, p) 是可见性(从 x 看 p 没被遮挡为 1,否则为 0)
- G(x, p) 是几何项(包括距离衰减和余弦定律)

这个二重积分**没有解析解**(因为 V 函数取决于场景几何)。所以工业上只能用蒙特卡洛积分:**随机采样 N 个 p,平均它们的贡献**:

```
L(x) ≈ (A / N) * Σ  L_emit(p_i) * V(x, p_i) * G(x, p_i)
              i=1..N
```

N 越大,方差越小,图像越干净。N=1 就是单点采样,等价于点光源(但光的"位置"每帧随机,会闪烁——day427 调的就是这个)。

### 矩形采样的两种策略

**网格采样(stratified)**:把矩形切成 N 个等分,每个等分中心采一个点。优点:分布均匀,方差小。缺点:有规律,容易产生摩尔纹。

**随机采样(uniform random)**:在矩形内随机采 N 个点。优点:无摩尔纹。缺点:方差大,需要更多样本才能收敛。

**分层随机(stratified random)**:把矩形切成 N 个等分,每个等分内随机采一个点。两者优点合并——这是工业主流。Casey 今天先用网格,day430 切到分层 + 多线程。

### 体素覆盖:矩形如何映射到体素网格

体素网格是空间的均匀切片。每个体素是一个小立方体。一个矩形覆盖哪些体素?只需要把矩形的 `min` 和 `max` 映射到体素索引空间:

```
imin = floor((rect.min - grid_origin) / voxel_size)
imax = floor((rect.max - grid_origin) / voxel_size)
for iz in imin.z..=imax.z:
  for iy in imin.y..=imax.y:
    for ix in imin.x..=imax.x:
      voxel[ix][iy][iz] += light_contribution
```

注意是 `floor` 不是 `round`——保守放大,任何被矩形触碰的体素都被注入光。Casey 选这个方向(向上保守)是为了避免漏光。

### Rust 视角:从 `Vec3` 到 `Bounds3`

数据结构的演变,直接对应抽象的演变:

```rust
// 旧:点光源
pub struct PointLight {
    pub pos: Vec3,
    pub color: Vec3,
    pub intensity: f32,
}

// 新:矩形面积光
pub struct RectLight {
    pub min: Vec3,    // 矩形最小角(假设矩形与坐标轴对齐,AABB)
    pub max: Vec3,    // 矩形最大角
    pub color: Vec3,
    pub intensity: f32,
}

impl RectLight {
    pub fn center(&self) -> Vec3 {
        (self.min + self.max) * 0.5
    }
    pub fn area(&self) -> f32 {
        // 矩形面积,假设某个维度退化为零(平面)
        let d = self.max - self.min;
        d.x * d.y + d.y * d.z + d.x * d.z  // 粗略,实际取最大面
    }
    pub fn sample(&self, u: f32, v: f32) -> Vec3 {
        // u, v ∈ [0, 1] —— 矩形参数化采样
        self.min + (self.max - self.min) * Vec3::new(u, v, 0.0)
    }
}
```

`Bounds3` 是图形学里的常见结构。Bevy 用 `Aabb`,glam 没原生支持,需要自己写。今天 Casey 自己手写——后续 day422 的 ray-AABB 相交直接复用。

### 几何与代数:从"一个点"到"一片面"

记住一个深刻事实:**渲染中所有"光"都是面光源的近似**。点光源是面积趋于零的极限;方向光是面积趋于无穷、距离也趋于无穷的极限。真实世界没有点光源——LED 灯珠也有 1mm² 的发光面,恒星也有视面积(只是很小)。

所以从点切换到矩形不是"加功能",而是"修正错误"。一旦你看穿了这一点,后面的所有采样理论都顺水推舟。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业的面积光用法:

- **区域照明(Quake/Source 系)**:用 env_projectedtexture 模拟手电筒,本质是一个截锥体面积光
- **天光(sky light)**:把天空当作无穷大的上半球面积光,这是户外场景柔和阴影的来源
- **RTGI (Ray-Traced Global Illumination)**:Cyberpunk 2077 的 Path Tracing 模式,所有光源都是面积光,实时光线追踪

游戏中"看起来真实"的灯,99% 都是面积光的某种近似。Unity 的 HDRP、Unreal 的 Lumen 都内置面积光支持。Casey 现在用 CPU 做朴素版,是为了让你**理解原理**,而不是抄引擎 API。

**坑**:面积光的阴影质量取决于采样数。N=4 时阴影边缘有噪点,N=64 才平滑,但成本是 16 倍。游戏工业用**时序累积(temporal accumulation)**——上一帧的采样和这一帧平均,4 个采样经过 16 帧累积看起来像 64 采样。day418 就是做这个。

### 3.2 · 🎨 图形学视角

面积光的精确解析解只对**简单几何**(球、圆盘)在**简单遮挡**(无遮挡或全遮挡)下存在。Eric Heitz 2013 年的论文给出了多边形面积光的解析解,但很复杂。Casey 不追求解析,直接用蒙特卡洛。

**重要概念**:

- **辐射度(radiance)**:单位面积单位立体角的能量,W·m⁻²·sr⁻¹
- **辐照度(irradiance)**:单位面积接收的能量,W·m⁻²
- **辐射通量(radiant flux)**:总能量,W

光照积分算的是辐照度(像素接收的能量),从光源的辐射度(光源每点发出的能量)通过几何项转换。

矩形面积光的辐射度假设均匀(整片矩形发光一样强),所以积分可以简化。

**余弦定律**:光强按 `cos θ` 衰减,θ 是入射方向与表面法线的夹角。这是为什么正午阳光强(θ=0)、黄昏阳光弱(θ≈π/2)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上和"矩形采样"最像的概念是**页对齐(page alignment)**和**缓存行(cache line)**。

矩形采样遍历的体素是 3D 网格中连续的一片。在 CPU 缓存上,这些体素的内存布局决定了遍历效率:

- **结构数组(AoS)**:`struct Voxel { r, g, b, ... }` 数组——遍历相邻体素时连续读,缓存友好
- **数组结构(SoA)**:`struct { r: [f32; N], g: [f32; N], ... }`——SIMD 友好但遍历不连续

Casey 的体素网格用 AoS(只读 RGB),后续 day431 SIMD 时会切到 SoA。Linux 上验证缓存命中的工具是 `perf stat -e cache-misses ./game`。

### 3.4 · 🦀 Rust 生态视角

Rust 表达矩形:

```rust
#[derive(Copy, Clone, Debug)]
pub struct Bounds3 {
    pub min: Vec3,
    pub max: Vec3,
}

impl Bounds3 {
    pub fn from_center_extent(center: Vec3, extent: Vec3) -> Self {
        Self {
            min: center - extent * 0.5,
            max: center + extent * 0.5,
        }
    }
    pub fn size(&self) -> Vec3 { self.max - self.min }
    pub fn center(&self) -> Vec3 { (self.min + self.max) * 0.5 }
    pub fn contains(&self, p: Vec3) -> bool {
        p.x >= self.min.x && p.x <= self.max.x
        && p.y >= self.min.y && p.y <= self.max.y
        && p.z >= self.min.z && p.z <= self.max.z
    }
    pub fn iter_voxels(&self, grid: &VoxelGrid) -> impl Iterator<Item = (i32, i32, i32)> {
        let imin = grid.world_to_idx(self.min);
        let imax = grid.world_to_idx(self.max);
        (imin.0..=imax.0).flat_map(move |x|
            (imin.1..=imax.1).flat_map(move |y|
                (imin.2..=imax.2).map(move |z| (x, y, z))))
    }
}
```

`iter_voxels` 返回一个 `impl Iterator`,零成本抽象。Rust 的迭代器会被 monomorphization 内联成紧凑的 for 循环,和手写一样快。

## 4 · 认知地图

### 4.1 上级

- **面积光(Area Light)** —— 把光源抽象成有面积的几何体,本日的主角
- **光照传播(Light Propagation)** —— HH 体素光照系统的总称,矩形是其中的几何单元
- **采样理论(Sampling Theory)** —— 连续信号(光照积分)到离散值(像素亮度)的转换

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 点光源 | 单点,无面积 | 严格解析光照 | 弃用 |
| 矩形面积光 | 轴对齐矩形,ray-AABB 廉价 | 中等成本,柔和阴影 | ✅ |
| 球形面积光 | 球,ray-Sphere 中等 | 光源像灯泡 | 不用 |
| 圆盘面积光 | 圆,ray-Disk 中等 | 光源像聚光灯 | 不用 |
| 多边形面积光 | 任意多边形,Heitz 解析 | 高质量,但代码复杂 | 不用 |
| 方向光 | 无穷远,无位置 | 太阳光 | HH 另有处理 |

矩形是**最便宜的有面积光**——ray-AABB 只需要 6 次比较,而 ray-Sphere 需要解二次方程。

### 4.3 下级

- **AABB(Bounds3)** —— 轴对齐包围盒,矩形的几何存储
- **蒙特卡洛采样** —— 用 N 个随机点近似积分
- **分层采样(stratified)** —— 把矩形切格子,每格采一点
- **可见性测试 V(x,p)** —— 从被照点到光源某点是否被遮挡
- **几何项 G(x,p)** —— 距离衰减和余弦定律的组合

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:点光源不能产生柔和阴影,根本原因是什么?为什么"增加点光源数量"也不能完美逼近面积光?

**参考解答**:点光源在空间中是一个无穷小点。从被照亮的像素看,这个点要么被遮挡(影子)、要么不被遮挡(亮),二值。所以阴影是硬的。

增加点光源数量可以逼近——但只是逼近。问题是每个点光源都需要完整的光照计算(可见性 ray-cast + 余弦定律 + 距离衰减),N 个点光源成本是 1 个的 N 倍。而真正的面积光用蒙特卡洛采样,可以用**重要性采样**让方差收敛更快。工程上,16 个点光源 ≠ 16 个蒙特卡洛样本,因为点光源之间不共享可见性测试。

更深一层:点光源的"位置"是固定的,不会因为采样策略变化;面积光的采样位置可以**随帧变化**(分层随机),累积出更平滑的结果。这是 day418 时序平滑的原理。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:实现 `Bounds3` struct + `RectLight`,把光源从点切换到矩形,完成标准:
- `cargo run` 后,墙面上的光照分布从单点亮斑变成柔和渐变
- 调整矩形大小,亮斑变大
- F2 显示当前采样数 N,N 越大越平滑

**参考解答**:

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug)]
pub struct Bounds3 {
    pub min: Vec3,
    pub max: Vec3,
}

impl Bounds3 {
    pub fn from_center_extent(center: Vec3, extent: Vec3) -> Self {
        // extent 是矩形的"全宽",不是半宽
        Self {
            min: center - extent * 0.5,
            max: center + extent * 0.5,
        }
    }
    pub fn sample(&self, u: f32, v: f32) -> Vec3 {
        // u, v ∈ [0, 1] —— 在矩形平面内采样
        // 假设矩形在 XY 平面(Z 固定)
        Vec3::new(
            self.min.x + (self.max.x - self.min.x) * u,
            self.min.y + (self.max.y - self.min.y) * v,
            self.min.z,
        )
    }
}

pub struct RectLight {
    pub bounds: Bounds3,
    pub color: Vec3,
    pub intensity: f32,
    pub sample_count: u32,  // N
}

impl RectLight {
    pub fn illuminate(&self, point: Vec3, normal: Vec3, scene: &Scene) -> Vec3 {
        let n = self.sample_count.max(1);
        let mut accum = Vec3::ZERO;
        for i in 0..n {
            for j in 0..n {
                let u = (i as f32 + 0.5) / n as f32;  // 网格采样
                let v = (j as f32 + 0.5) / n as f32;
                let p = self.bounds.sample(u, v);
                let dir = (p - point).normalize();
                let dist2 = (p - point).length_squared();
                let cos_theta = normal.dot(dir).max(0.0);
                if cos_theta <= 0.0 { continue; }
                if scene.is_occluded(point, p) { continue; }
                // 距离平方反比 + 余弦 + 发光强度
                accum += self.color * self.intensity * cos_theta / dist2;
            }
        }
        let n_total = (n * n) as f32;
        accum / n_total  // 归一化
    }
}
```

**关键解释**:

- `from_center_extent` 用全宽不是半宽,因为直觉上"我想要 2 米宽的灯"比"我要半宽 1 米"自然
- `sample` 假设矩形在 XY 平面,Z 固定——这是简化,实际 Casey 后续让矩形任意朝向(day421)
- 双层 for 循环产生 N×N 个采样点,网格分布
- `cos_theta <= 0.0` 检查:背面不接收光(余弦定律)
- `dist2` 距离平方反比衰减,符合物理
- `is_occluded` 是可见性测试,占成本最大(day431 SIMD 加速的就是这个)

### Rust:矩形面积光 + 多采样

```rust
// Cargo.toml: glam = "0.29"

use glam::Vec3;

#[derive(Copy, Clone, Debug)]
pub struct Bounds3 {
    pub min: Vec3,
    pub max: Vec3,
}

impl Bounds3 {
    pub fn from_center_extent(center: Vec3, extent: Vec3) -> Self {
        Self {
            min: center - extent * 0.5,
            max: center + extent * 0.5,
        }
    }
    pub fn center(&self) -> Vec3 { (self.min + self.max) * 0.5 }
    pub fn size(&self) -> Vec3 { self.max - self.min }
    pub fn area_xy(&self) -> f32 {
        let d = self.size();
        d.x * d.y
    }
    pub fn sample(&self, u: f32, v: f32) -> Vec3 {
        Vec3::new(
            self.min.x + (self.max.x - self.min.x) * u,
            self.min.y + (self.max.y - self.min.y) * v,
            self.min.z,
        )
    }
    pub fn contains(&self, p: Vec3) -> bool {
        p.x >= self.min.x && p.x <= self.max.x
            && p.y >= self.min.y && p.y <= self.max.y
            && p.z >= self.min.z && p.z <= self.max.z
    }
}

pub struct RectLight {
    pub bounds: Bounds3,
    pub color: Vec3,       // 线性 RGB,范围 [0, +∞)
    pub intensity: f32,    // 辐射度,W/sr/m²
    pub sample_count: u32,
}

impl RectLight {
    pub fn illuminate_point(
        &self,
        point: Vec3,
        normal: Vec3,
        occlusion_test: impl Fn(Vec3, Vec3) -> bool,
    ) -> Vec3 {
        let n = self.sample_count.max(1);
        let mut accum = Vec3::ZERO;
        let mut hit = 0u32;
        for i in 0..n {
            for j in 0..n {
                let u = (i as f32 + 0.5) / n as f32;
                let v = (j as f32 + 0.5) / n as f32;
                let p = self.bounds.sample(u, v);
                let to_light = p - point;
                let dist = to_light.length();
                if dist < 1e-6 { continue; }
                let dir = to_light / dist;
                let cos_theta = normal.dot(dir);
                if cos_theta <= 0.0 { continue; }
                if occlusion_test(point, p) { continue; }
                // 距离平方反比衰减
                let falloff = 1.0 / (dist * dist);
                accum += self.color * self.intensity * cos_theta * falloff;
                hit += 1;
            }
        }
        // 归一化:除以总采样数(不是 hit 数,因为漏采样的应该贡献 0)
        let n_total = (n * n) as f32;
        accum / n_total
    }
}

fn main() {
    let light = RectLight {
        bounds: Bounds3::from_center_extent(
            Vec3::new(0.0, 5.0, 0.0),
            Vec3::new(2.0, 2.0, 0.0),
        ),
        color: Vec3::new(1.0, 0.95, 0.8),
        intensity: 100.0,
        sample_count: 4,
    };

    let point = Vec3::new(0.0, 0.0, 0.0);
    let normal = Vec3::new(0.0, 1.0, 0.0);

    // 假设无遮挡
    let result = light.illuminate_point(point, normal, |_, _| false);
    println!("Illuminance at point: {:?}", result);
    // Illuminance at point: Vec3(~[0.95, 0.9, 0.76]) -- 大约的辐射度
}
```

**Troubleshooting**:

- **亮斑形状还是方的** —— `sample_count = 1` 时退化成点光源,要 ≥ 2
- **亮度过高** —— `intensity` 单位是辐射度,平方反比衰减后在小距离时会爆;加 `max_value` clamp
- **采样点在矩形外** —— 检查 `u, v` 是否 ∈ [0, 1];`(i + 0.5) / n` 必须用浮点除法
- **`falloff` 除零** —— `dist` 接近零时跳过(`dist < 1e-6`)
- **背面也亮** —— `cos_theta <= 0.0` 必须 `continue`,不是 clamp 到 0

要把今天讨论的抽象概念变成可运行的代码,我们必须经历几个具体阶段。这一节展开每一步的工程细节。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
