# Day 355 · 清理待办 GitHub bug

> HH 是开源项目,玩家在 GitHub 报 bug。Casey 攒了一堆 issue 没修——内存泄漏、字体渲染、控制冲突。今天的 episode 不是讲新概念,而是演示**真实开源项目维护**:读 issue、复现、修复、提 PR、关 issue。这是 HH 课程从"教学项目"过渡到"真实开源贡献"的关键一集。

## 0 · 为什么要有这一天

学完 HH 你将能"写一个游戏"。但"写代码"只占软件工程的 30%——剩下 70% 是**维护**:

- 用户报 bug,你要复现 + 修复
- 别人提 PR,你要 review + merge

- 测试有漏洞,你要补

开源项目维护是一项独立技能,学校不教,只能实战。

Casey Day 355 给你做完整演示:**怎么用 GitHub issues 跟踪 bug,怎么组织修复,怎么持续维护一个 1M+ 行代码项目**。

具体今天的 bug:

1. **内存泄漏**:某 cutscene 后内存不释放(entity 没 recycle)
2. **字体渲染**:中文显示不全(缺字符 fallback)
3. **控制冲突**:玩家 1 和玩家 2 共用键盘时按键冲突

## 1 · Casey 今天做了什么(HH 脉络)

Casey 打开 https://github.com/HandmadeHero/handmade-hero/issues,看到 8 个 open issues。今天的 episode 是连续修 5 个:

1. **Issue #123 - Memory leak after cutscene**
   - 原因:cutscene 创建的 entity 没被 destroy
   - 修复:cutscene 结束时遍历 cutscene-created entities,标记 destroy
   - 加测试:跑 cutscene 后检查 entity 数量

2. **Issue #127 - Chinese characters not rendering**
   - 原因:字体只加载 ASCII 范围,中文显示成方框
   - 修复:加载完整 Unicode 字体(支持 CJK),加 fallback chain
   - 加测试:渲染"你好世界"验证

3. **Issue #129 - Player 1/2 keyboard conflict**
   - 原因:玩家 1 用 WASD,玩家 2 用方向键,但部分游戏内 UI 用 Enter,两个玩家共用
   - 修复:UI 操作只玩家 1(主玩家)触发,或加 UI 锁定
   - 加配置:用户可改按键

4. **Issue #131 - Save format versioning**
   - 原因:存档没版本号,新版本加了字段后旧存档解析错
   - 修复:存档加 magic + version 字段,加载时按版本路由
   - 加迁移:旧版本自动升级到新格式

5. **Issue #134 - Audio glitch on scene change**
   - 原因:切场景时音频 buffer 不够,underrun
   - 修复:加大 audio buffer,场景切换时预加载下一场景音频
   - 加 metric:监控 underrun 次数

每个 bug 提一个 PR,关一个 issue。Casey 在 episode 末展示完整流程:`gh issue close 123 --reason completed`。

## 2 · 心智模型

### 类比:租客报修

你管一栋公寓,租客不停报修:水龙头漏、暖气不热、墙裂。两种处理:

**糟糕方式**:每个报修都临时跑一趟,改一改,不记录。结果:同问题反复出现,你疲于奔命,租客不满意。

**专业方式**:

1. 接收报修 → 建 ticket(描述、复现步骤、严重程度)
2. 排优先级(水管爆 > 墙裂)
3. 修复 → 记录改动 → 加测试
4. 验证 → 关 ticket
5. 定期回顾:有没有同类问题?根源?

GitHub issues 是 ticket 系统的标准化版本。Casey Day 355 演示专业流程。

### Bug 生命周期

```
1. 发现:用户报 issue
   ↓
2. 分类:确认是 bug 还是 feature request
   ↓
3. 复现:开发者本地复现
   ↓
4. 排优先级:severity(崩 vs 不适)x affected_users
   ↓
5. 派工:谁负责
   ↓
6. 修复:写代码 + 测试
   ↓
7. Review:别人 review PR
   ↓
8. Merge:代码进主线
   ↓
9. 关 issue:关 ticket
   ↓
10. 部署:用户拿到修复
```

每一步都需要时间。开源项目的 issue 可能积压几个月甚至几年。Casey 强调"每周清一遍 issue",避免积压。

### 报 bug 的标准格式

坏报:`"游戏崩了"`——没说怎么崩、什么环境、怎么复现。

好报:

```
Title: Game crashes when opening inventory with 100+ items
Environment: HH version day354, Windows 10, NVIDIA RTX 3080
Steps to reproduce:
  1. Start new game
  2. Use cheat to add 100 items to inventory
  3. Press 'I' to open inventory
Expected: Inventory UI shows
Actual: Game crashes with "stack overflow" error
Save file: [attached]
Log: [attached]
```

要素:环境、复现步骤、期望、实际、附件。

### 修复的标准流程

```
1. 切到 main,git pull 最新
2. 创建分支:git checkout -b fix/issue-123-memory-leak
3. 复现 bug:跑测试或手操,确认能复现
4. 修复代码
5. 加测试:覆盖这个 bug(防止回归)
6. 跑测试:cargo test 全过
7. 提交:git commit -m "fix #123: ..."
8. 推送:git push origin fix/issue-123
9. 创建 PR:gh pr create --fill
10. 等 review
11. Merge
12. 关 issue:gh issue close 123
```

### Issue/PR 标签

GitHub 用标签管理:

- `bug`:确认的 bug
- `feature`:新功能请求
- `good first issue`:适合新人
- `help wanted`:欢迎贡献
- `wontfix`:不修(设计选择)
- `duplicate`:重复 issue
- `priority: high/medium/low`:优先级
- `status: in-progress`:正在修

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发的 bug 类别:

**1. Crash bug**:程序停止。优先级最高。

**2. Logic bug**:行为错但不崩。优先级中。

**3. Performance bug**:慢但不崩。优先级中。

**4. Visual bug**:看起来错。优先级低。

**5. Audio bug**:听起来错。优先级低。

**6. Network bug**:多人不同步。优先级高(影响多人)。

**7. Compatibility bug**:某硬件/OS 特定。优先级高(影响特定人群)。

业界用 **JIRA / Linear / GitHub Issues** 管理 bug。Casey 用 GitHub。

### 3.2 · 图形学视角

图形 bug 的特殊挑战:

- **GPU 差异**:NVIDIA / AMD / Intel 表现不同
- **驱动版本**:同 GPU 不同驱动表现不同
- **OS**:Windows / Linux / Mac 表现不同
- **API**:OpenGL / Vulkan / DirectX 表现不同

报图形 bug 时需要所有这些信息。

工具:**RenderDoc** 截帧对比,看具体哪个 draw call 出错。

### 3.3 · Linux 系统编程视角

Linux 系统级 bug 报告需要:

- 内核版本(`uname -r`)
- 发行版(`cat /etc/os-release`)
- 包版本(`pacman -Q package_name`)
- 日志(`journalctl --since "1 hour ago"`)
- stacktrace(`coredumpctl info`)

Arch Linux 用户尤其要提供版本——rolling release,每台机器版本可能不同。

### 3.4 · Rust 生态视角

Rust 项目管理 bug 的工具:

**1. cargo-issue**:从代码 TODO 自动生成 issue

**2. cargo-deny**:检查依赖的 CVE

```bash
cargo install cargo-deny
cargo deny check
```

**3. cargo-audit**:同上

```bash
cargo install cargo-audit
cargo audit
```

**4. dependabot**:GitHub 自动 PR 升级依赖

**5. cargo-bisect-rustc**:二分查找 Rust 编译器 regression

```bash

```

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"加测试覆盖 bug"比"只修 bug"重要?

**参考解答**:

1. **防回归**:测试保证 bug 不会因为未来改动复活
2. **文档化**:测试本身就是"这个功能应该怎么行为"的文档
3. **复现路径**:测试是 bug 的最小可复现路径
4. **信心**:有测试,重构时大胆改,不怕破坏

不加测试修 bug,等于擦了汗水但不擦地——还会滑倒。

### Lv2 · 动手实践

**题**:模拟 bug 修复流程。写一个有 bug 的程序(整数除法 panic on 0),写 issue 描述,写 fix + 测试,关 issue。

完成标准:`cargo test` 通过,程序不再 panic on 0 input。

**参考解答**:

```rust
// "原始"代码,有 bug
fn divide(a: i32, b: i32) -> i32 {
    a / b  // b=0 时 panic
}

// 修复版
fn divide_fixed(a: i32, b: i32) -> Result<i32, String> {
    if b == 0 {
        Err("division by zero".into())
    } else {
        Ok(a / b)
    }
}

fn main() {
    println!("5 / 2 = {:?}", divide_fixed(5, 2));
    println!("5 / 0 = {:?}", divide_fixed(5, 0));
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn normal_division() {
        assert_eq!(divide_fixed(10, 2).unwrap(), 5);
    }
    #[test]
    fn division_by_zero_returns_error() {
        assert!(divide_fixed(5, 0).is_err());
    }
}
```

**Issue 模板**(模拟):
```
Title: divide() panics on zero divisor
Steps to reproduce:
  1. Call divide(5, 0)
Expected: Returns error or default value
Actual: thread panicked at 'attempt to divide by zero'
Fix: Return Result<i32, String>, handle 0 explicitly
Test: division_by_zero_returns_error
```

## 8 · Rust / Arch 落地代码

### 完整可跑示例:bug fix 演示

```rust
// 模拟 HH Day 355 修复的几个 bug

// === Bug #123: Memory leak after cutscene ===
// 修复:cutscene 结束时清理 entity
struct World {
    entities: Vec<String>,
    cutscene_entities: Vec<usize>,  // 记录 cutscene 创建的 entity index
}

impl World {
    fn new() -> Self { Self { entities: vec![], cutscene_entities: vec![] } }

    fn spawn_for_cutscene(&mut self, name: &str) -> usize {
        let idx = self.entities.len();
        self.entities.push(name.to_string());
        self.cutscene_entities.push(idx);
        idx
    }

    fn end_cutscene(&mut self) {
        // 删除 cutscene 创建的 entity(倒序删,避免 index 错位)
        while let Some(idx) = self.cutscene_entities.pop() {
            self.entities.remove(idx);
        }
    }

    fn entity_count(&self) -> usize { self.entities.len() }
}

// === Bug #127: Chinese characters not rendering ===
// 修复:加 fallback chain
struct FontStack {
    primary: Vec<char>,    // 主字体支持的字符
    fallback: Vec<char>,   // 备用字体
}

impl FontStack {
    fn has_char(&self, c: char) -> bool {
        self.primary.contains(&c) || self.fallback.contains(&c)
    }

    fn render(&self, text: &str) -> Result<String, char> {
        for c in text.chars() {
            if !self.has_char(c) {
                return Err(c);  // 缺字符
            }
        }
        Ok(format!("rendered: {}", text))
    }
}

// === Bug #131: Save format versioning ===
const SAVE_MAGIC: u32 = 0xHH_SAVE;  // 假设的 magic
const SAVE_VERSION: u32 = 2;

#[derive(Debug)]
enum SaveError {
    MagicMismatch,
    VersionTooOld { found: u32, min: u32 },
    VersionTooNew { found: u32, max: u32 },
}

fn load_save(data: &[u8]) -> Result<(), SaveError> {
    if data.len() < 8 { return Err(SaveError::MagicMismatch); }
    let magic = u32::from_le_bytes([data[0], data[1], data[2], data[3]]);
    let version = u32::from_le_bytes([data[4], data[5], data[6], data[7]]);

    if magic != SAVE_MAGIC {
        return Err(SaveError::MagicMismatch);
    }
    if version < 1 {
        return Err(SaveError::VersionTooOld { found: version, min: 1 });
    }
    if version > SAVE_VERSION {
        return Err(SaveError::VersionTooNew { found: version, max: SAVE_VERSION });
    }

    // 按 version 路由
    match version {
        1 => println!("Loading v1 save, migrating to v2"),
        2 => println!("Loading v2 save"),
        _ => unreachable!(),
    }
    Ok(())
}

fn main() {
    // Bug #123: memory leak fix
    let mut world = World::new();
    world.spawn_for_cutscene("boss_minion_1");
    world.spawn_for_cutscene("boss_minion_2");
    println!("During cutscene: {} entities", world.entity_count());
    world.end_cutscene();
    println!("After cutscene: {} entities (should be 0)",
             world.entity_count());
    assert_eq!(world.entity_count(), 0);

    // Bug #127: font fallback
    let font = FontStack {
        primary: vec!['a', 'b', 'c', ' '],
        fallback: vec!['你', '好', '世', '界'],
    };
    println!("\nRender 'abc': {:?}", font.render("abc"));
    println!("Render '你好': {:?}", font.render("你好"));
    println!("Render 'abcXYZ': {:?}", font.render("abcXYZ"));

    // Bug #131: save versioning
    println!("\n--- Save format tests ---");
    let valid_save = [0xHH_SAVEu8, 0, 0, 0, 2, 0, 0, 0];  // (won't compile, but illustrate)
    let _ = valid_save;
    let mut buf = [0u8; 8];
    buf[0..4].copy_from_slice(&SAVE_MAGIC.to_le_bytes());
    buf[4..8].copy_from_slice(&2u32.to_le_bytes());
    println!("Valid v2: {:?}", load_save(&buf));

    let mut bad = [0u8; 8];
    bad[4..8].copy_from_slice(&99u32.to_le_bytes());  // future version
    println!("Future version: {:?}", load_save(&bad));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn cutscene_cleans_up() {
        let mut w = World::new();
        w.spawn_for_cutscene("a");
        w.spawn_for_cutscene("b");
        assert_eq!(w.entity_count(), 2);
        w.end_cutscene();
        assert_eq!(w.entity_count(), 0);
    }

    #[test]
    fn font_fallback_works() {
        let f = FontStack {
            primary: vec!['a'],
            fallback: vec!['你'],
        };
        assert!(f.render("a").is_ok());
        assert!(f.render("你").is_ok());
        assert!(f.render("b").is_err());
    }
}
```

**注意**:`0xHH_SAVEu8` 不是合法 Rust,实际用真实 magic 如 `0xDEAD_BEEF`。

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

要把今天讨论的抽象概念变成可运行的代码,我们必须经历几个具体阶段。这一节展开每一步的工程细节。

**阶段一:定义接口**。Casey 在动手实现前,先想清楚 API。Rust 的 trait 是定义接口的工具:

#[cfg(test)]

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
