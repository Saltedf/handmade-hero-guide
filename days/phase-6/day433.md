
# Day 433 · 优化光线 vs AABB 相交

> Day 432 完成 SIMD 集成,但 Casey 测性能发现 ray-AABB 仍是热路径。今天他尝试**算法级优化**——替换 slab method,用更高效的"分支减少"版本。还尝试**数据布局优化**——把 AABB 用 SoA 存储。这些优化加起来再快 1.5-2x。

## 0 · 为什么要有这一天

回顾 day422 的 slab method 算法:每条光线 3 个轴,每轴 2 次除法、4 次比较、2 次 max/min。共 6 次除法、12 次比较、6 次 max/min。约 30 个浮点运算。

工业的优化:

1. **避免除法**:除法比乘法慢 5-20 倍。预算 `1/d`,用乘法代替。Day 422 已用,但仍能改进。
2. **避免分支**:`if d < 0 swap(t1, t2)` 是分支预测失败热点。用 `_mm_min_ps` / `_mm_max_ps` 的"无分支 swap"。
3. **数据布局**:AABB `[min: Vec3, max: Vec3]` 是 AoS,SIMD 加载需要 shuffle。改成 `[mins_x: __m128, ...]` 更高效。
4. **预计算**:对每条光线,预算 `inv_d`、`sign`(方向符号)、`bound_minmax[3][2]`(根据符号选 min/max),让 ray-AABB 退化成"6 次比较"。

Casey 今天试这些优化。**最高级的版本是"Iron License"(branchless)**,6 次比较 + 6 次乘法,极简极快。

心理锚点:今天之后,你能识别 ray-AABB 的性能瓶颈(分支、除法),知道如何用 SIMD intrinsics 的"无分支"特性,理解"算法 vs 实现"两层优化的差别。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 用 day264 的 profiler 看 ray-AABB 占比,发现仍是 40%。优化路径:

1. **预计算 inv_d**:在 ray 构造时算 `1/d` 三次,后续全用乘法
2. **预计算 sign**:每轴 `dir < 0 ? 1 : 0`,作为索引
3. **重排 AABB**:按 sign 顺序读 `min` 或 `max`,避免分支

具体代码:

```rust
pub struct OptimizedRay {
    pub origin: Vec3,
    pub inv_d: Vec3,        // 预计算 1/d
    pub sign: [usize; 3],   // 预计算方向符号(0 或 1)
}

pub fn ray_vs_aabb_optimized(ray: &OptimizedRay, aabb: &AABB) -> bool {
    // 用 sign 索引,避免分支
    // sign=0: 先 max 再 min(ray 沿正方向)
    // sign=1: 先 min 再 max(ray 沿负方向)
    let bounds = [
        [aabb.min.x, aabb.max.x],  // [0] = min, [1] = max
        [aabb.min.y, aabb.max.y],
        [aabb.min.z, aabb.max.z],
    ];

    let mut t_min = (bounds[0][ray.sign[0]].x - ray.origin.x) * ray.inv_d.x;
    let mut t_max = (bounds[1 - ray.sign[0]].x - ray.origin.x) * ray.inv_d.x;

    let ty_min = (bounds[0][ray.sign[1]].y - ray.origin.y) * ray.inv_d.y;
    let ty_max = (bounds[1 - ray.sign[1]].y - ray.origin.y) * ray.inv_d.y;

    if t_min > ty_max || ty_min > t_max { return false; }
    t_min = t_min.max(ty_min);
    t_max = t_max.min(ty_max);

    let tz_min = (bounds[0][ray.sign[2]].z - ray.origin.z) * ray.inv_d.z;
    let tz_max = (bounds[1 - ray.sign[2]].z - ray.origin.z) * ray.inv_d.z;

    if t_min > tz_max || tz_min > t_max { return false; }
    t_min = t_min.max(tz_min);
    t_max = t_max.min(tz_max);

    t_max >= 0.0
}
```

这是**Smit's algorithm**的优化版,叫 **"branchless slab test"**(虽然还有 if,但无 swap 分支)。

进一步:**完全 branchless** 用 SIMD,所有 max/min 用 `_mm_max_ps` / `_mm_min_ps`,无 if。

## 2 · 心智模型

### 类比:消除红绿灯

想象开车。如果路上每公里一个红绿灯,你频繁停走,慢。如果改成"环岛"或"立交"(无停),流畅快。

ray-AABB 的 if 是"红绿灯"——CPU 流水线要停,检查条件,跳转。**branchless** 用无副作用的运算(max/min)代替,无停顿,流水线满速跑。

CPU 流水线深(14-20 级),分支预测失败代价 10-20 周期。每条光线 3 次 if 失败 = 60 周期浪费。

### 严谨原理:分支预测

现代 CPU 用**分支预测器**猜 if 走向,提前执行猜中的路径。预测对,无开销。预测错,清空流水线,损失 10-20 周期。

ray-AABB 的 `if t1 > t2 swap(t1, t2)`:光线方向变化,swap 有时需要有时不需要,预测率 50%,几乎每次都失败。

branchless 版本:`t_enter = min(t1, t2); t_exit = max(t1, t2)`。无 if,CPU 直接执行两个 SSE 指令,无预测失败。

### 预计算 inv_d

除法 vs 乘法成本(x86_64):

- `divss`(除法):20-30 周期
- `mulss`(乘法):3-5 周期

预算 `inv_d = 1.0 / d`(一次除法),后续全用 `* inv_d`(多次乘法)。**N 次除法 → 1 次除法 + N 次乘法**,大幅省成本。

### 预计算 sign

`dir < 0` 时,`t1 > t2` 需要交换。预计算 `sign[axis] = (dir[axis] < 0) as usize`,作为索引选 min/max,避免运行时 if。

### 数据布局优化

AABB 的存储:

- AoS:`[AABB; N]`,内存 `min max min max ...`
- SoA:`mins_x: [f32; N], maxs_x: [f32; N], mins_y: ..., ...`,内存 `mxxxx mxxxx ...`

SIMD 处理 4 条光线 vs 1 个 AABB(本日 day431),AABB 需要"广播"(每条光线看到同一个 min/max)。AoS 需要 shuffle,SoA 直接 `_mm_set1_ps`。

如果 BVH 节点存 SoA AABB,遍历时无 shuffle,快 1.5x。

```rust
pub fn ray_vs_aabb_branchless(ray: &OptimizedRay, aabb: &AABB) -> bool {
    // 用 sign 作为索引,无 if
    let bounds_x = [aabb.min.x, aabb.max.x];
    let bounds_y = [aabb.min.y, aabb.max.y];
    let bounds_z = [aabb.min.z, aabb.max.z];

    let t_min = (bounds_x[ray.sign[0] as usize] - ray.origin.x) * ray.inv_d.x;
    let t_max = (bounds_x[1 - ray.sign[0] as usize] - ray.origin.x) * ray.inv_d.x;

    let ty_min = (bounds_y[ray.sign[1] as usize] - ray.origin.y) * ray.inv_d.y;
    let ty_max = (bounds_y[1 - ray.sign[1] as usize] - ray.origin.y) * ray.inv_d.y;

    if t_min > ty_max || ty_min > t_max { return false; }

    let tz_min = (bounds_z[ray.sign[2] as usize] - ray.origin.z) * ray.inv_d.z;
    let tz_max = (bounds_z[1 - ray.sign[2] as usize] - ray.origin.z) * ray.inv_d.z;

    if t_min.max(ty_min) > tz_max || tz_min > t_max.min(ty_max) { return false; }

    t_max.min(ty_max).min(tz_max) >= 0.0
}
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业的优化技术:

- **Data-oriented design**:数据布局按访问模式优化
- **Cache-aware**:数据紧凑,缓存命中率高
- **SIMD**:批量处理
- **Branchless**:无分支预测失败

Mike Acton(工业专家)的演讲"data-oriented design"是经典。Casey 现在落实这些思想。

### 3.2 · 🎨 图形学视角

ray-AABB 算法的几个变种:

- **Smit's**(基础):本日原始版
- **Smit's optimized**:`inv_d + sign`,本日优化版
- **Branchless slab**:完全无 if
- **Plücker**:基于坐标,适合三角形
- **CPU SIMD**:`__m128` 4-wide

工业 ray tracer 都用 optimized 版,可以再加 SSE/AVX。Intel 的 embree 库有 AVX-512 版本,8-wide ray-AABB。

### 3.3 · 🐧 Linux 系统编程视角

Linux 的"避免分支"思想:

- **likely/unlikely 宏**:告诉编译器分支走向,优化预测
- **bitmap 操作**:`set_bit`,无 if
- **bloom filter**:多次 hash 后位运算,无 if

`likely/unlikely` 是 Linux 的常见宏,告诉 CPU 分支预测器"这个分支几乎总走"。Rust 用 `#[cold]` 标记罕见分支。

### 3.4 · 🦀 Rust 生态视角

Rust 帮助优化:

- `#[repr(C)]`:保证内存布局
- `#[inline]` / `#[inline(always)]`:跨 crate 内联
- `core::arch::*`:SIMD intrinsics
- `std::hint::black_box`:benchmark 时防优化

Rust 的 zero-cost abstraction 让"高层数据结构"和"底层优化"共存——结构体有方法,但运行时无虚函数开销。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:branchless 编程在什么场景下"加速明显"?什么场景下"反而慢"?

**参考解答**:**加速明显的场景**:

- 分支预测失败率高(> 10%):branchless 避免预测失败
- 大批量同样操作:SIMD 友好,branchless 让 SIMD lane 利用率高
- 热点循环:每次省 10-20 周期,累积显著

**反而慢的场景**:

- 分支预测率高(> 95%):预测对,无开销;branchless 多算几个 op,慢
- 单次操作:branchless 的额外运算抵消无分支的红利
- 编译器优化好的 if(编译器可能自动 branchless)

实践:profile 看分支预测失败率(`perf stat -e branch-misses`),失败多才 branchless。

```rust
use glam::Vec3;

#[derive(Copy, Clone)]
pub struct Ray { pub origin: Vec3, pub dir: Vec3 }

#[derive(Copy, Clone)]
pub struct OptimizedRay {
    pub origin: Vec3,
    pub inv_d: Vec3,
    pub sign: [usize; 3],
}

impl OptimizedRay {
    pub fn new(origin: Vec3, dir: Vec3) -> Self {
        Self {
            origin,
            inv_d: Vec3::new(1.0 / dir.x, 1.0 / dir.y, 1.0 / dir.z),
            sign: [
                (dir.x < 0.0) as usize,
                (dir.y < 0.0) as usize,
                (dir.z < 0.0) as usize,
            ],
        }
    }
}

#[derive(Copy, Clone)]
pub struct AABB { pub min: Vec3, pub max: Vec3 }

pub fn ray_vs_aabb_original(ray: &Ray, aabb: &AABB) -> bool {
    let mut t_min = f32::NEG_INFINITY;
    let mut t_max = f32::INFINITY;
    for axis in 0..3 {
        let o = ray.origin[axis]; let d = ray.dir[axis];
        let lo = aabb.min[axis]; let hi = aabb.max[axis];
        if d.abs() < 1e-8 {
            if o < lo || o > hi { return false; }
        } else {
            let inv_d = 1.0 / d;  // 每次都除
            let t1 = (lo - o) * inv_d;
            let t2 = (hi - o) * inv_d;
            let (te, tx) = if t1 < t2 { (t1, t2) } else { (t2, t1) };  // 分支
            t_min = t_min.max(te);
            t_max = t_max.min(tx);
            if t_min > t_max { return false; }
        }
    }
    t_max >= 0.0
}

pub fn ray_vs_aabb_optimized(ray: &OptimizedRay, aabb: &AABB) -> bool {
    // 用 sign 作为索引,无 swap 分支
    let bounds_x = [aabb.min.x, aabb.max.x];
    let bounds_y = [aabb.min.y, aabb.max.y];
    let bounds_z = [aabb.min.z, aabb.max.z];

    let sx = ray.sign[0];
    let sy = ray.sign[1];
    let sz = ray.sign[2];

    let mut t_min = (bounds_x[sx] - ray.origin.x) * ray.inv_d.x;
    let mut t_max = (bounds_x[1 - sx] - ray.origin.x) * ray.inv_d.x;

    let ty_min = (bounds_y[sy] - ray.origin.y) * ray.inv_d.y;
    let ty_max = (bounds_y[1 - sy] - ray.origin.y) * ray.inv_d.y;

    if t_min > ty_max || ty_min > t_max { return false; }
    if ty_min > t_min { t_min = ty_min; }
    if ty_max < t_max { t_max = ty_max; }

    let tz_min = (bounds_z[sz] - ray.origin.z) * ray.inv_d.z;
    let tz_max = (bounds_z[1 - sz] - ray.origin.z) * ray.inv_d.z;

    if t_min > tz_max || tz_min > t_max { return false; }
    if tz_min > t_min { t_min = tz_min; }
    if tz_max < t_max { t_max = tz_max; }

    t_max >= 0.0
}

fn main() {
    let aabb = AABB {
        min: Vec3::new(-1.0, -1.0, -1.0),
        max: Vec3::new(1.0, 1.0, 1.0),
    };

    // 测试 4 条光线,不同方向
    let rays: Vec<Ray> = vec![
        Ray { origin: Vec3::new(-5.0, 0.0, 0.0), dir: Vec3::new(1.0, 0.1, 0.0).normalize() },
        Ray { origin: Vec3::new(5.0, 0.0, 0.0), dir: Vec3::new(-1.0, -0.2, 0.0).normalize() },
        Ray { origin: Vec3::new(0.0, -5.0, 0.0), dir: Vec3::new(0.0, 1.0, 0.1).normalize() },
        Ray { origin: Vec3::new(0.0, 5.0, 0.0), dir: Vec3::new(0.0, -1.0, -0.1).normalize() },
    ];

    // 验证正确性
    for (i, r) in rays.iter().enumerate() {
        let result_orig = ray_vs_aabb_original(r, &aabb);
        let opt_ray = OptimizedRay::new(r.origin, r.dir);
        let result_opt = ray_vs_aabb_optimized(&opt_ray, &aabb);
        println!("Ray {}: orig={} opt={}", i, result_orig, result_opt);
        assert_eq!(result_orig, result_opt);
    }

    // 性能对比
    let n = 10_000_000;
    let start = std::time::Instant::now();
    for _ in 0..n {
        for r in &rays {
            std::hint::black_box(ray_vs_aabb_original(r, &aabb));
        }
    }
    let orig_time = start.elapsed();
    println!("\nOriginal {} x 4 rays: {:?}", n, orig_time);

    let opt_rays: Vec<OptimizedRay> = rays.iter()
        .map(|r| OptimizedRay::new(r.origin, r.dir))
        .collect();
    let start = std::time::Instant::now();
    for _ in 0..n {
        for r in &opt_rays {
            std::hint::black_box(ray_vs_aabb_optimized(r, &aabb));
        }
    }
    let opt_time = start.elapsed();
    println!("Optimized {} x 4 rays: {:?}", n, opt_time);
    println!("Speedup: {:.2}x", orig_time.as_secs_f64() / opt_time.as_secs_f64());

    // 分支预测失败率
    println!("\nUse: perf stat -e branch-misses,branches ./target/release/handmade_hero");
}
```

## 8 · Rust / Arch 落地代码

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug)]
pub struct Ray { pub origin: Vec3, pub dir: Vec3 }

#[derive(Copy, Clone, Debug)]
pub struct OptimizedRay {
    pub origin: Vec3,
    pub inv_d: Vec3,
    pub sign: [usize; 3],
}

impl OptimizedRay {
    pub fn new(origin: Vec3, dir: Vec3) -> Self {
        // 处理 d=0 的特殊情况(避免 inf)
        let safe_inv = |d: f32| if d.abs() < 1e-8 { 1e8 } else { 1.0 / d };
        Self {
            origin,
            inv_d: Vec3::new(safe_inv(dir.x), safe_inv(dir.y), safe_inv(dir.z)),
            sign: [
                (dir.x < 0.0) as usize,
                (dir.y < 0.0) as usize,
                (dir.z < 0.0) as usize,
            ],
        }
    }

    pub fn from_ray(ray: &Ray) -> Self {
        Self::new(ray.origin, ray.dir)
    }
}

#[derive(Copy, Clone, Debug)]
pub struct AABB { pub min: Vec3, pub max: Vec3 }

/// 原始 slab method
pub fn ray_vs_aabb_original(ray: &Ray, aabb: &AABB) -> Option<f32> {
    let mut t_min = f32::NEG_INFINITY;
    let mut t_max = f32::INFINITY;
    for axis in 0..3 {
        let o = ray.origin[axis]; let d = ray.dir[axis];
        let lo = aabb.min[axis]; let hi = aabb.max[axis];
        if d.abs() < 1e-8 {
            if o < lo || o > hi { return None; }
        } else {
            let inv_d = 1.0 / d;
            let t1 = (lo - o) * inv_d;
            let t2 = (hi - o) * inv_d;
            let (te, tx) = if t1 < t2 { (t1, t2) } else { (t2, t1) };
            t_min = t_min.max(te);
            t_max = t_max.min(tx);
            if t_min > t_max { return None; }
        }
    }
    if t_max < 0.0 { return None; }
    Some(t_min.max(0.0))
}

/// 优化版(inv_d + sign)
pub fn ray_vs_aabb_optimized(ray: &OptimizedRay, aabb: &AABB) -> Option<f32> {
    let bounds_x = [aabb.min.x, aabb.max.x];
    let bounds_y = [aabb.min.y, aabb.max.y];
    let bounds_z = [aabb.min.z, aabb.max.z];

    let mut t_min = (bounds_x[ray.sign[0]] - ray.origin.x) * ray.inv_d.x;
    let mut t_max = (bounds_x[1 - ray.sign[0]] - ray.origin.x) * ray.inv_d.x;

    let ty_min = (bounds_y[ray.sign[1]] - ray.origin.y) * ray.inv_d.y;
    let ty_max = (bounds_y[1 - ray.sign[1]] - ray.origin.y) * ray.inv_d.y;

    if t_min > ty_max || ty_min > t_max { return None; }
    if ty_min > t_min { t_min = ty_min; }
    if ty_max < t_max { t_max = ty_max; }

    let tz_min = (bounds_z[ray.sign[2]] - ray.origin.z) * ray.inv_d.z;
    let tz_max = (bounds_z[1 - ray.sign[2]] - ray.origin.z) * ray.inv_d.z;

    if t_min > tz_max || tz_min > t_max { return None; }
    if tz_min > t_min { t_min = tz_min; }
    if tz_max < t_max { t_max = tz_max; }

    if t_max < 0.0 { return None; }
    Some(t_min.max(0.0))
}

fn main() {
    let aabb = AABB {
        min: Vec3::new(-1.0, -1.0, -1.0),
        max: Vec3::new(1.0, 1.0, 1.0),
    };

    let test_rays: Vec<(Ray, &str, bool)> = vec![
        (Ray { origin: Vec3::new(-5.0, 0.0, 0.0), dir: Vec3::new(1.0, 0.0, 0.0) }, "hit center", true),
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
