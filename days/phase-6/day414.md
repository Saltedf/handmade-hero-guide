
# Day 414 · 改进光分布

> Day 413 把光值编码紧凑后,Casey 发现矩形光源覆盖的体素亮度不均匀——某些体素过亮(光强集中在矩形中心),某些过暗(矩形角落没采到)。今天他改进**光分布算法**:让光强在矩形覆盖的所有体素里**按面积均匀分布**,而不是按"采样命中次数"分布。

## 0 · 为什么要有这一天

具体场景:你有一个 2x2 米的矩形光源,放在 1x1 米的体素网格上。矩形覆盖 4 个体素。如果你用 Day 411 的方法——把矩形采样 N×N 个点,每个点注入它所在的体素——你会看到:

- 矩形中心的体素收到最多采样点(它们都落在中心体素)
- 矩形边缘的体素收到较少采样点(采样点稀疏)
- 整体光强分布是高斯形的(中间高、边缘低),不是均匀的

但实际上,矩形光源每平方米发出的能量是均匀的——整片矩形每点光强一样,所以**覆盖的每个体素应该收到相同的光强**。Day 411 的算法有偏差,因为采样数与体素命中不成比例。

正确的做法:**根据矩形在每个体素内的面积比例分配光强**。如果矩形有 30% 的面积在体素 A,70% 在体素 B,那么 A 收 30% 总光强,B 收 70%。这叫**面积加权分布**。

数学上,这等价于**蒙特卡洛重要性采样**:用面积作为权重,而不是均匀采样。结果是**无偏估计(unbiased estimate)**——期望值等于真值。

工业渲染器(Mitsuba、pbrt)都这么做。HH 之前用朴素采样,因为简单;现在追求正确性,必须改进。

心理锚点:今天之后,你能解释"采样无偏"和"采样有偏"的区别,能自己实现面积加权分布,能识别"亮度不均匀 bug"的成因。这是从"看起来对"到"数学上对"的跃迁。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑游戏,看到矩形光源下的墙面亮度有"中间亮、四周暗"的不均匀分布。他的修复步骤:

1. **画图分析**:在白板上画矩形和体素网格,标出每个体素被矩形覆盖的面积
2. **算几何**:矩形和体素相交,面积是矩形和体素 AABB 的**交集面积**
3. **写代码**:对每个被矩形覆盖的体素,算交集面积,按面积比例分配总光强
4. **优化**:因为矩形和体素都是 AABB,交集就是 `min.max - max.min` 在每个维度上的乘积,公式极简
5. **验证**:打印每个体素收到的光强,确认均匀(误差 < 1%)

Casey 没改采样数 N——他在**注入阶段**做面积加权,而不是在**像素采样阶段**。这样既保持了矩形面积光的柔和阴影(N 采样),又消除了体素层的不均匀。

## 2 · 心智模型

### 类比:倒水入方格

想象一个 1x1 米的方格地板,你在上面倒水。水均匀洒在一片 2x2 米的区域(部分在方格外)。问题是:**每个方格收到多少水**?

如果水均匀洒(每平方米水一样多),那么:
- 完全在区域内的方格:收到 1 平方米的水
- 部分在区域内的方格:按"在区域内的面积"收
- 完全在区域外的方格:0

这就是面积加权分布。Day 411 的 bug 在于:**水不是均匀洒的**,而是按"采样点命中"决定每个方格收多少——采样点在矩形中心密集,在边缘稀疏,所以中间方格收太多,边缘方格收太少。

### 严谨原理:AABB-AABB 交集面积

两个轴对齐包围盒(AABB)的交集仍是 AABB。设 A 的 min/max 是 `a_min, a_max`,B 的是 `b_min, b_max`:

```
intersection.min = max(a_min, b_min)
intersection.max = min(a_max, b_max)
```

如果 `intersection.min.x > intersection.max.x`(任一维度),则无交集,面积为 0。否则:

```
size = intersection.max - intersection.min
volume = size.x * size.y * size.z  (3D)
area   = size.x * size.y            (2D,假设 z 方向无延伸)
```

矩形光源是 2D(平面),所以算 2D 面积;3D 物体覆盖的体素算 3D 体积。

### 面积加权分布算法

```
total_area = sum over all voxels of intersection_area(rect, voxel)
for each voxel covered by rect:
    a = intersection_area(rect, voxel)
    weight = a / total_area
    voxel.light += rect.total_intensity * weight
```

`total_intensity` 是矩形光源的总辐射通量(W)。按面积比例分到每个体素,总和 = total_intensity(能量守恒)。

### 数学:为什么这是无偏的

定义:无偏估计 = 期望等于真值。

设矩形总能量 E,覆盖区域 R,体素 v 在 R 中的面积 a(v)。真值:v 应该收到 `E * a(v) / area(R)`。

蒙特卡洛采样:在 R 内均匀采样 N 个点,每点注入 E/N 给它所在的体素。体素 v 收到的期望 = N * (a(v)/area(R)) * (E/N) = E * a(v) / area(R)。所以**蒙特卡洛是无偏的**,但**有限 N 有方差**。

Day 411 的 bug:蒙特卡洛的方差让小 N 时看起来有偏差(中心高、边缘低)。N 越大越接近真值,但成本越高。

面积加权分布**不用采样**——直接算 a(v)/area(R)。无方差,精确,但只能用在矩形(规则形状)。复杂形状仍需采样。

### Rust 视角

```rust
pub fn distribute_light_to_voxels(
    grid: &mut VoxelGrid,
    rect: Bounds3,
    total_intensity: Vec3,
) {
    // 算矩形覆盖的体素范围
    let imin = grid.world_to_idx(rect.min).unwrap_or((0, 0, 0));
    let imax = grid.world_to_idx(rect.max).unwrap_or(grid.dims_minus_one());

    // 第一步:算总面积(2D,假设矩形在 XY 平面)
    let mut total_area = 0.0;
    for i in imin.0..=imax.0 {
        for j in imin.1..=imax.1 {
            let voxel_bounds = grid.voxel_bounds(i, j, 0);
            let a = intersection_area_2d(rect, voxel_bounds);
            total_area += a;
        }
    }

    if total_area < 1e-6 { return; }

    // 第二步:按面积比例分配
    for i in imin.0..=imax.0 {
        for j in imin.1..=imax.1 {
            let voxel_bounds = grid.voxel_bounds(i, j, 0);
            let a = intersection_area_2d(rect, voxel_bounds);
            let weight = a / total_area;
            grid.add_light(i, j, 0, total_intensity * weight);
        }
    }
}

fn intersection_area_2d(a: Bounds3, b: Bounds3) -> f32 {
    let dx = (a.max.x.min(b.max.x) - a.min.x.max(b.min.x)).max(0.0);
    let dy = (a.max.y.min(b.max.y) - a.min.y.max(b.min.y)).max(0.0);
    dx * dy
}
```

`(a.max.x.min(b.max.x) - a.min.x.max(b.min.x)).max(0.0)` 是单维交集长度,三步:
1. `a.max.x.min(b.max.x)`:两个 max 的较小者
2. `- a.min.x.max(b.min.x)`:减去两个 min 的较大者
3. `.max(0.0)`:负数(无交集)归零

### 性能考虑

总面积 = 矩形面积(在网格内的部分)。所以可以省第一步:

```rust
let total_area = rect.area_xy();  // 矩形自己的面积
// 假设矩形完全在网格内
```

但如果矩形部分在网格外,要 clip。Casey 的简化:保证光源总在网格内,省去 clip。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业的体素光照分布:

- **LPV(Light Propagation Volumes)**:用球谐函数(SH)存光强,每个体素 4 个 SH 系数。分布时按面积比例,但 SH 编码让分布平滑
- **Lumen(Unreal 5)**:类似 LPV,但用更密的网格 + 多分辨率
- **Voxel Cone Tracing**:不用传播,直接对体素做 cone 追踪

LPV 是 Crytek 2009 年提出的,核心思想就是"光从体素网格传播"。分布算法用 SH,比 Casey 的朴素 RGB 复杂,但能编码方向(光来自哪个方向)。

### 3.2 · 🎨 图形学视角

数学上,"光分布到体素"是**卷积**:

```
output(x) = ∫ input(y) * kernel(x - y) dy
```

其中 `input(y)` 是连续光强场,`kernel` 是体素的盒式滤波器(box filter,体素内 = 1,外 = 0)。卷积结果是体素化的光强。

盒式滤波器是最简单的,工业用**高斯滤波器**让体素边界更平滑,避免锯齿。

### 3.3 · 🐧 Linux 系统编程视角

Linux 文件系统有类似"按比例分配"的代码:

- **磁盘配额(quota)**:用户使用空间超过限制时,按比例拒绝分配
- **cgroup CPU shares**:多个 cgroup 按权重分配 CPU 时间
- **内存 cgroup**:按权重分配内存压力

权重分配的核心思想:总数固定,按权重比例分配,总和守恒。

### 3.4 · 🦀 Rust 生态视角

Rust 表达"权重分配":

```rust
pub fn distribute_weighted<T: Copy + std::ops::AddAssign + std::ops::Mul<f32, Output = T>>(
    buckets: &mut [T],
    weights: &[f32],
    total: T,
) {
    let sum: f32 = weights.iter().sum();
    if sum < 1e-6 { return; }
    for (bucket, &w) in buckets.iter_mut().zip(weights) {
        *bucket += total * (w / sum);
    }
}
```

泛型 `T` 让函数复用——可以分配 Vec3(光照)、f32(标量资源)、或任何支持加法和标量乘法的类型。这是 Rust 类型系统的力量。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么面积加权分布是"无偏"的?蒙特卡洛采样"无偏但有方差",这两个性质如何区分?

**参考解答**:无偏性指**期望**等于真值——大量重复实验的平均结果收敛到真值。方差指**单次实验**与期望的偏离程度。

蒙特卡洛采样 N 个点,体素 v 收到的期望 = E * a(v) / area(R)(真值),所以无偏。但单次实验的方差 = ... > 0,所以单次结果偏离真值。

面积加权分布**直接算 a(v) / area(R)**,没有随机性,没有方差,等于真值(无偏且零方差)。但它**只适用于规则形状**(AABB),复杂形状不可用。

use glam::Vec3;

#[derive(Copy, Clone, Debug)]
pub struct Bounds3 { pub min: Vec3, pub max: Vec3 }

fn intersection_area_2d(a: Bounds3, b: Bounds3) -> f32 {
    let dx = (a.max.x.min(b.max.x) - a.min.x.max(b.min.x)).max(0.0);
    let dy = (a.max.y.min(b.max.y) - a.min.y.max(b.min.y)).max(0.0);
    dx * dy
}

pub struct VoxelGrid2D {
    pub origin: Vec3,
    pub voxel_size: f32,
    pub dims: (usize, usize),
    pub light: Vec<Vec3>,
}

impl VoxelGrid2D {
    pub fn distribute(&mut self, rect: Bounds3, total: Vec3) {
        let imin_x = ((rect.min.x - self.origin.x) / self.voxel_size).floor() as i32;
        let imax_x = ((rect.max.x - self.origin.x) / self.voxel_size).floor() as i32;
        let imin_y = ((rect.min.y - self.origin.y) / self.voxel_size).floor() as i32;
        let imax_y = ((rect.max.y - self.origin.y) / self.voxel_size).floor() as i32;

        // 算总面积(假设矩形完全在网格内)
        let mut total_area = 0.0;
        let mut areas = Vec::new();
        for i in imin_x..=imax_x {
            for j in imin_y..=imax_y {
                if i < 0 || j < 0 { continue; }
                let (i, j) = (i as usize, j as usize);
                if i >= self.dims.0 || j >= self.dims.1 { continue; }
                let vb = Bounds3 {
                    min: self.origin + Vec3::new(i as f32, j as f32, 0.0) * self.voxel_size,
                    max: self.origin + Vec3::new((i + 1) as f32, (j + 1) as f32, 0.0) * self.voxel_size,
                };
                let a = intersection_area_2d(rect, vb);
                areas.push(((i, j), a));
                total_area += a;
            }
        }

        if total_area < 1e-6 { return; }

        for ((i, j), a) in areas {
            let weight = a / total_area;
            let idx = i + j * self.dims.0;
            self.light[idx] += total * weight;
        }
    }
}

## 8 · Rust / Arch 落地代码

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug)]
pub struct Bounds3 { pub min: Vec3, pub max: Vec3 }

impl Bounds3 {
    pub fn area_xy(&self) -> f32 {
        let d = self.max - self.min;
        d.x * d.y
    }
}

fn intersection_area_2d(a: Bounds3, b: Bounds3) -> f32 {
    let dx = (a.max.x.min(b.max.x) - a.min.x.max(b.min.x)).max(0.0);
    let dy = (a.max.y.min(b.max.y) - a.min.y.max(b.min.y)).max(0.0);
    dx * dy
}

pub struct VoxelGrid2D {
    pub origin: Vec3,
    pub voxel_size: f32,
    pub dims: (usize, usize),
    pub light: Vec<Vec3>,
}

impl VoxelGrid2D {
    pub fn new(dims: (usize, usize)) -> Self {
        Self {
            origin: Vec3::ZERO,
            voxel_size: 1.0,
            dims,
            light: vec![Vec3::ZERO; dims.0 * dims.1],
        }
    }

    fn voxel_bounds(&self, i: usize, j: usize) -> Bounds3 {
        Bounds3 {
            min: self.origin + Vec3::new(i as f32, j as f32, 0.0) * self.voxel_size,
            max: self.origin + Vec3::new((i+1) as f32, (j+1) as f32, 0.0) * self.voxel_size,
        }
    }

    pub fn distribute(&mut self, rect: Bounds3, total: Vec3) {
        let imin_x = ((rect.min.x - self.origin.x) / self.voxel_size).floor() as i32;
        let imax_x = ((rect.max.x - self.origin.x) / self.voxel_size).floor() as i32;
        let imin_y = ((rect.min.y - self.origin.y) / self.voxel_size).floor() as i32;
        let imax_y = ((rect.max.y - self.origin.y) / self.voxel_size).floor() as i32;

        let mut total_area = 0.0;
        let mut areas: Vec<((usize, usize), f32)> = Vec::new();

        for i in imin_x..=imax_x {
            for j in imin_y..=imax_y {
                if i < 0 || j < 0 { continue; }
                let (i, j) = (i as usize, j as usize);
                if i >= self.dims.0 || j >= self.dims.1 { continue; }
                let vb = self.voxel_bounds(i, j);
                let a = intersection_area_2d(rect, vb);
                if a > 0.0 {
                    areas.push(((i, j), a));
                    total_area += a;
                }
            }
        }

        if total_area < 1e-6 { return; }

        for ((i, j), a) in areas {
            let weight = a / total_area;
            let idx = i + j * self.dims.0;
            self.light[idx] += total * weight;
        }
    }

    pub fn total(&self) -> Vec3 {
        self.light.iter().sum()
    }
}

fn main() {
    let mut g = VoxelGrid2D::new((8, 8));
    let rect = Bounds3 {
        min: Vec3::new(1.0, 1.0, 0.0),
        max: Vec3::new(4.0, 3.0, 0.0),
    };
    let total = Vec3::new(12.0, 12.0, 12.0);
    g.distribute(rect, total);

    println!("Total after distribute: {:?}", g.total());
    // 应该 ~[12, 12, 12],能量守恒

    for j in 0..8 {
        let mut line = String::new();
        for i in 0..8 {
            let v = g.light[i + j * 8];
            let c = if v.x > 0.5 { '#' } else if v.x > 0.0 { '.' } else { ' ' };
            line.push(c);
        }
        println!("{}", line);
    }
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
