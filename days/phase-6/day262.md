# Day 262 · 绘制多帧性能图表

> 昨天把性能分析数据搬进环形数组后,今天 Casey 让那些原本"只活在当前帧"的数据**穿越时间**——画出最近 N 帧的柱状图叠在一起,周期性卡顿一眼就能看出来。

## 0 · 为什么要有这一天

你昨天的 profiler 已经能画出**当前这一帧**的火焰图。但是你打开它跑了一会儿,看到一个奇怪的卡顿:每隔 3-4 秒画面会顿一下。是 GC?是 IO?是某个特殊事件触发的?你盯着当前帧的火焰图看不出来——因为正常帧和卡顿帧看起来都差不多。

你想问的是"**时间维度**"的问题:这种卡顿是周期性的还是偶发的?周期是多少?跟谁相关?

单帧火焰图回答不了这个问题。你需要在屏幕上画出**最近 60 帧的 frame_dt 折线图**——横轴是帧序号(或时间),纵轴是这一帧的耗时。一条平直线表示稳定,一个尖峰表示卡顿。一眼能看出周期性的尖峰排列。

这就是工业级 profiler(`perf` / `chrome://tracing` / Unreal Profiler)标配的 "timeline view"。今天 Casey 把它做出来,效果上你能在游戏画面角落看到一条波动的小折线,实时反映最近 1 秒的帧时间。

实现这件事的难点不在数据(昨天已经准备好了),而在**绘制**:

1. 怎么把 64 个数据点画成一条折线
2. 怎么让坐标轴自动适应数据范围(否则数据稍变就被压扁)
3. 怎么避免数据更新时整条线"跳"——需要稳定的视觉锚点
4. 怎么用现有的"画矩形"原语拼出折线(没有 GPU 线段渲染,只能模拟)

心理锚点:完成本日练习后,你的 profiler 多了一个"望远镜视图",能看清过去,而不只是当下。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 拿出昨天的环形数组,加了一个新功能:**绘制折线图**。具体步骤:

1. 在 debug overlay 的右下角开一个矩形区域(比如 400×100 像素)用作画布
2. 遍历环形数组里的 64 个 `FrameProfile`,取出每帧的 `frame_dt`
3. 把 dt 映射到画布高度:dt=16.67ms → 高度 0(顶部);dt=33ms → 高度 100(底部)。这是简单的线性映射
4. 横轴方向每帧占 `画布宽 / 64 ≈ 6` 像素
5. 用"画垂直线段"的 primitive 把每帧画成一根竖线
6. 加一条参考线:dt=16.67ms 处画一条绿色横线(理想 60FPS)

Casey 在视频里反复强调"不要搞复杂":不上 GPU,不用 shader,就用现有的"画矩形"原语叠加出折线图。每根"折线段"实际是几十个 1×1 像素的小矩形拼起来的——丑但够用。

接着 Casey 处理了一个小坑:**Y 轴的 scale 要稳定**。如果每帧都重新计算 min/max,Y 轴会跳,折线图反而难读。解决方法:scale 在每 5 秒刷新一次,中间保持不变。

最后 Casey 加了一个**鼠标 hover 显示具体数值**的小功能:鼠标移到某根竖线上方,显示 "frame 4230: dt=18.2ms"。这让 profiler 从"看趋势"升级到"读数值"。

## 2 · 心智模型

### 类比:心电图 vs 单次血压

单帧火焰图就像测一次血压——给你一个数字,你看不出趋势。多帧折线图就像心电图——连续记录每秒几百次心跳,周期性的心律不齐一眼可见。

心电图的设计原则在游戏 profiler 里同样适用:

1. **时间窗固定**:不是显示最近 10 秒就是最近 30 秒,不能滚动太快
2. **Y 轴稳定**:尺度跳来跳去的话眼睛会乱,要把尺度锁定到合理范围
3. **网格线**:每 16.67ms (60FPS) 一条横线作为参考,看你离理想有多远
4. **颜色编码**:正常帧绿色、慢帧黄色、卡顿帧红色

### 严谨原理:从数据到像素的映射

我们有 64 个数据点 `{ dt_i | i ∈ [0, 64) }`,每个 `dt_i` 是这一帧的耗时(微秒或纳秒)。要把它们画成一个 400×100 像素的图,需要做两步映射。

#### X 轴:数据索引 → 像素 X

最简单的线性映射:

```
pixel_x(i) = canvas_x + (i / 64) * canvas_w
```

其中 `canvas_x = 0`, `canvas_w = 400`。所以第 0 个数据在 X=0,第 63 个在 X≈393(因为 64 不整除 400,我们用 floor)。或者反过来画(最新的在左边),取决于习惯——Casey 选了"最旧在左、最新在右",和阅读顺序一致。

#### Y 轴:dt 值 → 像素 Y

```
pixel_y(dt) = canvas_y + canvas_h - (dt / scale) * canvas_h
```

其中 `scale` 是 Y 轴最大值。`canvas_h=100`,`scale=33ms`(双倍 60FPS 时间),所以 dt=16.67ms → y=50(图的中线),dt=33ms → y=100(底部)。

注意 `canvas_h - (dt/scale)*canvas_h` 是**反转**——dt 越大,Y 像素越大,但屏幕坐标 Y 越大越往下,所以"耗时长的帧"显示在底部?不对——直觉上"耗时长的帧"应该显示得"高",因为它"超出预算"。所以 Casey 把它反着画:dt 越大,Y 越小(越靠上),让卡顿帧表现为"尖峰向上"。这是工业 profiler 的惯例(Unreal / RenderDoc 都这样)。

```
pixel_y(dt) = canvas_y + (1 - dt / scale) * canvas_h
```

dt=0 时 y=canvas_y+canvas_h(底部),dt=scale 时 y=canvas_y(顶部)。卡顿帧尖峰朝上,正常帧在底部,直观。

#### 绘制策略:逐列垂直矩形

我们只有"画填充矩形"的原语(`draw_filled_rect(x, y, w, h, color)`)。要画折线图,最简单的办法是:**每帧画一根竖线**(宽度 1 像素,从底部到该帧的 Y 值)。

```rust
for (i, frame) in history.iter().enumerate() {
    let x = canvas_x + (i * canvas_w / 64) as i32;
    let top_y = canvas_y + ((1.0 - frame.dt / scale) * canvas_h as f32) as i32;
    let bottom_y = canvas_y + canvas_h;
    let color = if frame.dt < 18_000 { GREEN }
                else if frame.dt < 25_000 { YELLOW }
                else { RED };
    draw_filled_rect(x, top_y, 1, (bottom_y - top_y) as u32, color);
}
```

这样每帧是一根从底部到 top_y 的竖条。64 根竖条紧挨着,看起来像柱状图——视觉上够清晰,能看出趋势。

如果你想画"连线"而不是"柱状",可以在两个相邻数据点之间插值,但实现复杂度大增——Casey 选择不做。

#### Y 轴 scale 的稳定性

如果你每帧重新计算 `scale = max(history.dt)`,折线会随着 max 跳动而上下抖——视觉混乱。解决方法:

```rust
// 每 5 秒刷新一次 scale
if now - last_scale_update > 5_000 {
    self.scale = history.iter().map(|f| f.dt).max().max(16_666) as f32 * 1.1;
    last_scale_update = now;
}
```

`max(16_666)` 保证 scale 至少是 60FPS 的预算(避免空跑时 scale 过小);`* 1.1` 留 10% margin,避免最高数据贴顶。

### 鼠标 hover 显示数值

这是用户体验细节,但能让 profiler 从"玩具"变成"工具"。实现:

1. 每帧检测鼠标位置
2. 如果鼠标在 canvas 区域内,反推它对应的 frame index:`i = (mouse_x - canvas_x) * 64 / canvas_w`
3. 在鼠标附近画一个 tooltip 矩形 + 文字 "frame N: dt=X ms"

注意 frame index 是历史里的位置——如果你画的是"最近 64 帧",那么 history[60] 是 60 帧前,index=0 是当前帧,反推时要换算。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏 profiler 是工具子系统的典范,**它的失败模式是"工具自己卡"**:

- 每帧画 64 根矩形 + 一个 tooltip,在 1080p 上也就 64 次 draw call,毫秒级
- 但如果 scale 抖动、颜色乱选,用户根本看不清数据
- 所以 profiler 自己也要被 profiling——画 profiler 这段代码本身要在性能预算内

业界常见做法:**profiler 的绘制不在游戏主循环里,而在单独的 UI 线程**。Casey 没有这么做(HH 是单线程),但他确保 profiler 绘制本身极快(<0.5ms)。

游戏 profiler 的"时间视图"还有几个变种:

1. **柱状图**(今天做的):简单,但看不出"哪些 block 慢"
2. **火焰图堆积**(每帧画多个区段叠加):信息量大,但实现复杂
3. **timeline 滚动视图**(随时间向左滚动):最像 Chrome tracing,但实现需要双缓冲避免撕裂
4. **icicle graph**(火焰图倒挂):树形从上往下展开

Unreal Insights、RenderDoc、Pix 都用 2-3 的组合。Casey 选最简单的 1,够教学用。

### 3.2 · 🎨 图形学视角

把数据画成图是"数据可视化"这个领域的入门问题。游戏 profiler 的可视化有几个特殊约束:

1. **实时更新**(每帧 60Hz):静态图能慢慢渲染,这里必须 16ms 内完成
2. **抗锯齿可选**:柱状图 1 像素宽,锯齿不严重;折线图就需要 AA
3. **色彩编码**:不能用 RGB(色盲不友好),要用亮度 / 饱和度变化

色彩这一条多说一句。常见的错误是"红黄绿三色"——红绿色盲看不出来。更好的做法是"蓝(慢) → 紫(更慢) → 红(卡顿)",用色相变化加亮度变化。Casey 用红黄绿是因为这是教科书默认,工业级 profiler 会用色盲友好配色。

折线图绘制在 GPU 时代有更优雅的方案:**用 `GL_LINES` 一次 draw call 画整条线**。但 HH 在 Day 262 还没切到 GPU(后面才切),只能用 CPU 矩形堆叠。这是教学项目"先做对再优化"的体现。

### 3.3 · 🦀 Rust 生态视角

Rust 表达"折线图数据"有几个考量:

#### 用 `&[FrameProfile]` slice 引用

环形数组的迭代器返回 `impl Iterator<Item = &FrameProfile>`,可以 `.collect::<Vec<_>>()` 收集成 Vec——但这又分配了!正确做法是直接在迭代器上做映射:

```rust
for (i, frame) in profiler.iter_history().enumerate() {
    let x = ...;
    // 直接绘制
}
```

零分配,符合昨天的"无运行时分配"原则。

#### iterator 的链式调用

Rust 的 iterator 是惰性的,链式 `.map().filter().for_each()` 不会构造中间集合:

```rust
profiler.iter_history()
    .map(|f| f.frame_dt)
    .max()  // 一次遍历求 max,零分配
```

这比"先 collect 再 max"高效得多。Casey 的 C 版本做不到这种表达力——C 没有 iterator 抽象,只能写显式循环。Rust 在这里完胜。

#### 闭包捕获和借用

如果你想把绘制函数封装成 `fn draw_chart(canvas: &mut Canvas, data: impl Iterator<Item = &FrameProfile>)`,会遇到借用检查问题:

```rust
profiler.draw(|frames| {
    // 这里借用 frames
    for f in frames {
        // 但 canvas 已经被 draw 借走
    }
});
```

报错:`cannot borrow profiler.frames as mutable because profiler.canvas is also borrowed`。解决方法是把数据先 clone 出来(违背零分配原则),或者把 draw 拆成"计算像素坐标"和"画矩形"两步,中间用迭代器解耦。

### 3.4 · 数学和坐标系

把数据值映射到像素坐标是个**仿射变换**(affine transform),形式上:

```
[ pixel_x ]   [ a  b ] [ data_x ]   [ c ]
[ pixel_y ] = [ d  e ] [ data_y ] + [ f ]
```

但在 2D 简单情形下,b=d=0(没有旋转 / 错切),剩下:

```
pixel_x = a * data_x + c   (a 是 X 方向缩放,c 是 X 偏移)
pixel_y = e * data_y + f   (e 是 Y 方向缩放,f 是 Y 偏移)
```

这就是我们前面写的线性映射。注意 e 通常是负数(因为屏幕 Y 轴向下,数据 Y 轴向上),这正是为什么我们写 `1 - dt/scale` 而不是 `dt/scale`。

理解这一步,后面 Day 275+ 的"旋转 + 剪切"传给渲染器,本质也是仿射变换,只是 b/d 不为零。

## 5 · 对照与变奏

### Chrome tracing vs Unreal Insights vs HH profiler

| 工具 | 数据源 | 时间视图 | 内存占用 |
|---|---|---|---|
| Chrome tracing | 浏览器内置 | 滚动 + 缩放 | 几百 MB |
| Unreal Insights | Unreal 引擎 | 多视图 + flame | GB 级 |
| RenderDoc | GPU 截帧 | 单帧静态 | 几百 MB / 帧 |
| HH profiler | 游戏内置 | 64 帧柱状 | 几 KB |

HH 的简单是因为它只解决"当前游戏开发",不是通用工具。工业级工具用 SQLite 存历史数据(可以 GB),HH 只用环形数组。这告诉我们:**工具的复杂度应该匹配它的目的**。

### 不同 Y 轴 scale 策略

| 策略 | 何时刷新 | 优点 | 缺点 |
|---|---|---|---|
| 每帧重算 | 每帧 | 始终贴合数据 | 抖动严重 |
| 每 N 秒刷新 | 每 5s | 稳定 | 滞后于突变 |
| 上界固定 | 永不 | 最稳定 | 数据小则浪费 |
| 平滑过渡 | 每帧但缓动 | 平滑 | 实现复杂 |

Casey 选"每 5 秒刷新",折中方案。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 选择"柱状图(每帧一根竖条)"而不是"折线图(连线)"?给出至少 2 个理由。

**参考解答**:
1. **原语简单**:柱状图只需"画矩形"原语,折线图需要"画线段"或"画三角形"——HH 当前还没有这个原语,加它成本高
2. **抗锯齿**:1 像素宽的竖条不需要抗锯齿,1 像素宽的斜线锯齿明显——CPU 抗锯齿算法开销大
3. **视觉清晰**:柱状图的颜色编码(每根条独立着色)更直观,折线图的颜色不好做(整条线一个色)
4. **数据稀疏时仍可见**:64 根 1 像素宽的竖条占据画布大部分宽度,即使 dt=0 也能看到柱子在那里——折线图如果某些点 0 值,可能整段贴底看不清

### Lv2 · 动手实践

**题**:实现一个 `draw_chart` 函数,输入是 `&[f32]`(数据点)和 `&mut Canvas`,在画布上画出柱状图。要求:

- 颜色按值编码:< 0.5 蓝色,[0.5, 0.8) 黄色,≥ 0.8 红色
- Y 轴 scale 固定为 1.0
- canvas 假设是 400×100 像素

测试:数据为 `[0.1, 0.3, 0.5, 0.7, 0.9, 0.4, 0.2]`,画出 7 根柱子。

完成标准:`cargo run` 不 panic,你能在屏幕上看到 7 根柱子,颜色依次为蓝、蓝、黄、黄、红、黄、蓝。

**参考解答**:

```rust
const CANVAS_W: i32 = 400;
const CANVAS_H: i32 = 100;

struct Canvas {
    pixels: Vec<u32>,   // 假设 0xAABBGGRR 格式
    width: i32,
    height: i32,
}

impl Canvas {
    fn new(w: i32, h: i32) -> Self {
        Self {
            pixels: vec![0, w as usize * h as usize],
            width: w,
            height: h,
        }
    }

    fn fill_rect(&mut self, x: i32, y: i32, w: i32, h: i32, color: u32) {
        // 简单填充,不做裁剪(实际项目要做)
        for py in y..(y + h) {
            for px in x..(x + w) {
                if px >= 0 && px < self.width && py >= 0 && py < self.height {
                    self.pixels[(py * self.width + px) as usize] = color;
                }
            }
        }
    }
}

fn classify(value: f32) -> u32 {
    // 返回 ARGB 或 packed RGBA,这里用简单的 0xRRGGBB
    if value < 0.5 { 0x0000FF }       // 蓝
    else if value < 0.8 { 0xFFFF00 }  // 黄
    else { 0xFF0000 }                 // 红
}

fn draw_chart(canvas: &mut Canvas, data: &[f32]) {
    let n = data.len();
    if n == 0 { return; }

    // X 轴:每个数据点占多少像素
    let bar_w = CANVAS_W / n as i32;
    // Y 轴 scale 固定为 1.0
    let scale = 1.0_f32;

    for (i, v) in data.iter().enumerate() {
        let x = i as i32 * bar_w;
        // dt 越大,Y 越小(尖峰朝上)
        let top_y = ((1.0 - v / scale).max(0.0) * CANVAS_H as f32) as i32;
        let bottom_y = CANVAS_H;
        let color = classify(*v);
        // 注意:Canvas 自己有偏移,这里假设全屏坐标系
        canvas.fill_rect(x, top_y, bar_w, bottom_y - top_y, color);
    }
}

fn main() {
    let mut canvas = Canvas::new(CANVAS_W, CANVAS_H);
    let data = [0.1, 0.3, 0.5, 0.7, 0.9, 0.4, 0.2];
    draw_chart(&mut canvas, &data);
    println!("Chart drawn with {} pixels", canvas.pixels.iter().filter(|p| **p != 0).count());
    // 应该看到非零像素数(柱子覆盖的部分)
}
```

**每行解释**:
- `vec![0; n]` 创建长度为 n 的 Vec,初始全 0
- `classify` 返回 packed RGB(注意 byte order:在小端机器上,`0x0000FF` 存为 `FF 00 00`,显示时如果是 RGBA 就是 `R=FF, G=00, B=00` 红色——所以这里其实是简化)
- `(1.0 - v / scale).max(0.0)` 用 `max(0.0)` 保护 `v > scale` 时变成负数,负数 cast 成 i32 会得到一个巨大的值(`as i32` 是饱和的)
- `bar_w` 如果不是整数会有 truncation,导致最后一根柱子比前面的窄——可以预留一个 `pad_x` 解决,这里省略

### 完整可跑示例:把今天的柱状图集成进窗口

```rust
// Cargo.toml:
// [dependencies]
// minifb = "0.27"  // 简单的开窗库,Phase 0 应该已经装过

use minifb::{Key, Window, WindowOptions};
use std::time::Instant;

const WIDTH: usize = 800;
const HEIGHT: usize = 600;
const HISTORY: usize = 64;

fn main() {
    let mut window = Window::new(
        "Profiler Chart Demo",
        WIDTH,
        HEIGHT,
        WindowOptions::default(),
    ).expect("Failed to open window");

    let mut buffer: Vec<u32> = vec![0; WIDTH * HEIGHT];
    let mut history: [f32; HISTORY] = [0.0; HISTORY];
    let mut head: usize = 0;
    let mut initialized: usize = 0;
    let mut last_time = Instant::now();
    let mut frame_count = 0u64;

    while window.is_open() && !window.is_key_down(Key::Escape) {
        // 1. 算 dt
        let now = Instant::now();
        let dt = now.duration_since(last_time);
        last_time = now;
        let dt_ms = dt.as_secs_f32() * 1000.0;

        // 2. 记录到环形数组
        history[head] = dt_ms;
        head = (head + 1) % HISTORY;
        if initialized < HISTORY { initialized += 1; }

        // 3. 清屏(深灰背景)
        for px in buffer.iter_mut() {
            *px = 0xFF181818; // ARGB
        }

        // 4. 画柱状图(右下角 400×100 区域)
        let chart_x = (WIDTH - 400) as i32;
        let chart_y = (HEIGHT - 100) as i32;
        let chart_w = 400i32;
        let chart_h = 100i32;

        // 5. 画背景(浅灰,区分主画面)
        for py in chart_y..(chart_y + chart_h) {
            for px in chart_x..(chart_x + chart_w) {
                if px >= 0 && (px as usize) < WIDTH && py >= 0 && (py as usize) < HEIGHT {
                    buffer[(py as usize) * WIDTH + (px as usize)] = 0xFF303030;
                }
            }
        }

        // 6. 画 16.67ms 参考线(60FPS)
        let ref_y = chart_y + ((1.0 - 16.67 / 33.0) * chart_h as f32) as i32;
        for px in chart_x..(chart_x + chart_w) {
            if (px as usize) < WIDTH && (ref_y as usize) < HEIGHT {
                buffer[(ref_y as usize) * WIDTH + (px as usize)] = 0xFF00FF00;
            }
        }

        // 7. 画柱子
        let scale = 33.0_f32; // Y 轴 max
        let start = if initialized < HISTORY { 0 } else { head };
        for i in 0..initialized {
            let frame_idx = (start + i) % HISTORY;
            let v = history[frame_idx];
            let bar_w = chart_w / HISTORY as i32;
            let bx = chart_x + (i as i32) * bar_w;
            let top_y = chart_y + ((1.0 - v / scale).max(0.0).min(1.0) * chart_h as f32) as i32;
            let bottom_y = chart_y + chart_h;

            // 颜色编码
            let color = if v < 18.0 { 0xFF4040FF }   // 蓝(快)
                        else if v < 25.0 { 0xFFFFFF40 } // 黄
                        else { 0xFFFF4040 };            // 红(慢)

            for py in top_y..bottom_y {
                for px_off in 0..bar_w {
                    let px = bx + px_off;
                    if px >= 0 && (px as usize) < WIDTH && py >= 0 && (py as usize) < HEIGHT {
                        buffer[(py as usize) * WIDTH + (px as usize)] = color;
                    }
                }
            }
        }

        window.update_with_buffer(&buffer, WIDTH, HEIGHT).unwrap();
        frame_count += 1;
    }

    println!("Rendered {} frames total", frame_count);
}
```

**关键 Rust 特性解释**:

- `minifb` 是一个跨平台的开窗 + 像素 buffer 推送库,Phase 0 已用过
- `Instant::now()` 返回单调时钟(不受 NTP 调整影响),`duration_since` 算 dt
- `as i32` / `as usize` 转换要小心:f32 → i32 在溢出时会饱和,但负数会变 `-1`
- `.max(0.0).min(1.0)` 双向 clamp,防止 v > scale 时 top_y 越界
- `0xFFRRGGBB` 是 packed ARGB,小端机器上 byte 顺序是 BB GG RR AA,正好是大多数 framebuffer 的 BGRA 序

### 进一步展开:从概念到落地的完整路径

要把今天讨论的抽象概念变成可运行的代码,我们必须经历几个具体阶段。这一节展开每一步的工程细节。

**阶段一:定义接口**。Casey 在动手实现前,先想清楚 API。Rust 的 trait 是定义接口的工具:

```rust
trait Sortable {
    fn sort_key(&self) -> u64;
    fn bounds(&self) -> Aabb;
    fn layer(&self) -> u8;
}
```

trait 让代码可测试、可替换。Casey 经常说"先写 trait,再写 impl"——这强迫你思考抽象边界。

**阶段二:单元测试**。每个 sort_rule 分支都应有对应测试:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_basic_ordering() {
        let a = TestEntity { layer: 1, y: 100.0 };
        let b = TestEntity { layer: 1, y: 200.0 };
        assert_eq!(a.sort_key() < b.sort_key(), true);
    }

    #[test]
    fn test_layer_priority() {
        let a = TestEntity { layer: 2, y: 100.0 };
        let b = TestEntity { layer: 1, y: 200.0 };
        // layer 1 优先(a 在 b 后面)
        assert_eq!(a.sort_key() > b.sort_key(), true);
    }
}
```

跑 `cargo test`,所有测试必须通过才能进入下一阶段。

**阶段三:集成测试**。单元测试覆盖单个函数,集成测试覆盖整个系统。游戏里的集成测试通常是"加载场景,跑一帧,截图,对比期望截图"——visual regression test。这是 Casey debug 流程的标准化版本。

**阶段四:性能剖析**。用 `cargo flamegraph` 或 `perf record` 看 CPU 时间花在哪。如果 sort 占 0.5%,不用优化。占 20%,必优化。

```bash
sudo pacman -S flamegraph
cargo install flamegraph
cargo flamegraph --bin game
# 生成的 SVG 在浏览器打开,看热路径
```

**阶段五:跨平台验证**。Linux 测试用 `vulkaninfo | grep "Device name"` 看 GPU;Windows 测试用 dxdiag。同一代码在 Intel / AMD / NVIDIA / Apple Silicon GPU 上可能有微妙差异——精度、driver bug、性能特性。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
