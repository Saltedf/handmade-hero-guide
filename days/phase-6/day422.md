# Day 422 · 直接对 AABB 做光线投射

> 光照采样、可见性测试、阴影判定——所有这些都归结为一个问题:一条光线从 A 出发到 B,中间有没有碰到某个 AABB(轴对齐包围盒)?今天 Casey 实现这个核心算法,**slab method**(也叫"slab test"),只用 6 次比较 + 几次除法,极简且高效。这是后续 day431 SIMD 优化的基础。

## 0 · 为什么要有这一天

回到具体场景:你站在墙前,想知道墙上某个点是否能看见光源。怎么做?

简单做法:从墙上这点到光源连一条直线(光线),检查这条线**是否穿过任何障碍物**(其他墙、家具)。如果有遮挡,这点看不到光,画影子。

数学上,所有障碍物用 AABB 包围(轴对齐盒子)。问题归结为:**这条光线和这个 AABB 是否相交?如果相交,交点在哪?**

这个问题的标准解法叫 **slab method**(板法)。原理:3D AABB 是三个"无限板"的交集——X 方向两个板(垂直 X 轴的平面)、Y 方向两个板、Z 方向两个板。光线进入 AABB 的条件:光线**同时**在三个方向的板"内部"。

每对板的算法:

```
t_x_min = (aabb.min.x - ray.origin.x) / ray.dir.x
t_x_max = (aabb.max.x - ray.origin.x) / ray.dir.x
如果 t_x_min > t_x_max,交换(保证 min < max)
```

`t` 是光线参数:`point(t) = origin + t * dir`。`t_x_min` 是光线进入 X 板的时刻,`t_x_max` 是离开的时刻。

光线**进入 AABB 的时刻** = max(t_x_min, t_y_min, t_z_min)——三个方向都进入。
光线**离开 AABB 的时刻** = min(t_x_max, t_y_max, t_z_max)——任一方向离开。

如果**进入时刻 < 离开时刻**,光线在 AABB 内停留一段时间,即相交。

总共:6 次除法、6 次比较、2 次交换。极快。这就是工业 ray tracer 的核心热点。

Casey 今天实现这个算法,准备替换 HH 现有的(基于三角形遍历的)遮挡测试。三角形遮挡贵(几十次浮点运算),AABB 遮挡便宜(几次),性能提升 10-100 倍。

心理锚点:今天之后,你能写自己的 ray-AABB 相交算法,理解 slab method 的几何意义,知道为什么工业 ray tracer 都用它,能为后续 day431 的 SIMD 4-wide 实现做好单线程基础。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 在白板上画 2D 简化版(只有 X 和 Y 方向),手推公式。然后扩展到 3D:

```c
bool ray_vs_aabb(Vec3 origin, Vec3 dir, AABB aabb) {
    // 每个维度算 t_min, t_max
    float t_min = -INFINITY;
    float t_max = +INFINITY;
    for each axis in [x, y, z]:
        float t1 = (aabb.min[axis] - origin[axis]) / dir[axis];
        float t2 = (aabb.max[axis] - origin[axis]) / dir[axis];
        if t1 > t2 swap(t1, t2);
        t_min = max(t_min, t1);
        t_max = min(t_max, t2);
        if t_min > t_max return false;
    return true;
}
```

之后他把这个算法接到 HH 的可见性测试上:对每个图元的每个采样点,ray 到光源,遍历所有 AABB,任何一个相交就标记为遮挡。

性能测试:之前用三角形遍历,可见性测试 5ms/帧;换成 AABB 后 0.2ms/帧,25 倍提速。这就是工业 ray tracer 的核心优化。

## 2 · 心智模型

### 类比:照激光笔穿盒子

想象你拿激光笔从一点照向另一个点。中间有一个透明的矩形盒子(轴对齐)。激光是否穿过盒子?

简单方法:从侧面看(投影到 XY 平面),激光在 XY 平面是一条线段,盒子是一个矩形,看它们是否相交。如果相交,从顶面看(XZ 平面)再检查一次。如果两个投影都相交,**激光穿过 3D 盒子**。

slab method 是这个思路的精确数学化:

- "X 板"对应盒子在 X 方向的两个面(垂直 X 轴)
- 光线在 X 方向"进入盒子"的时刻:`(min.x - origin.x) / dir.x`——光线沿 X 方向走到 min.x 需要的时间
- 同理"离开"是 max.x

3D 盒子是 X 板、Y 板、Z 板的交集。光线同时在三对板内部 = 在盒子内。

### 严谨原理:slab method 推导

定义:

- 光线:`P(t) = O + t * D`,O 是原点,D 是方向(单位向量)
- AABB:`[min, max]`,两个角点

每对板的进入/离开时刻:

```
t_lo[axis] = (min[axis] - O[axis]) / D[axis]
t_hi[axis] = (max[axis] - O[axis]) / D[axis]
```

注意:`D[axis]` 可能负(光线沿该轴负方向),此时 `t_lo > t_hi`,要交换。一般化:

```
t1 = (min[axis] - O[axis]) / D[axis]
t2 = (max[axis] - O[axis]) / D[axis]
t_enter_axis = min(t1, t2)
t_exit_axis = max(t1, t2)
```

光线**进入盒子**的时刻 = 三个轴的 `t_enter_axis` 的最大值——所有轴都进入才进入。
光线**离开盒子**的时刻 = 三个轴的 `t_exit_axis` 的最小值——任一轴离开就离开。

相交条件:`t_enter <= t_exit`,且 `t_exit >= 0`(盒子在前方)。

### 边界情况

- **D[axis] == 0**:光线平行于该轴的板。检查 O[axis] 是否在 [min, max] 内,否则不相交
- **光线起点在盒内**:`t_enter < 0 < t_exit`,仍然算相交(返回 true)
- **光线反方向**:`t_exit < 0`,盒子在光线背后,不算相交(返回 false,除非允许)

Casey 的简化:`D[axis] == 0` 时,设 `t1 = -INFINITY, t2 = +INFINITY`(无约束),让其他轴决定。

### Rust 视角

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug)]
pub struct AABB { pub min: Vec3, pub max: Vec3 }

#[derive(Copy, Clone, Debug)]
pub struct Ray { pub origin: Vec3, pub dir: Vec3 }

pub fn ray_vs_aabb(ray: Ray, aabb: AABB) -> bool {
    let mut t_min = f32::NEG_INFINITY;
    let mut t_max = f32::INFINITY;

    for axis in 0..3 {
        let o = ray.origin[axis];
        let d = ray.dir[axis];
        let lo = aabb.min[axis];
        let hi = aabb.max[axis];

        if d.abs() < 1e-6 {
            // 光线平行于板
            if o < lo || o > hi { return false; }
        } else {
            let t1 = (lo - o) / d;
            let t2 = (hi - o) / d;
            let (t_enter, t_exit) = if t1 < t2 { (t1, t2) } else { (t2, t1) };
            t_min = t_min.max(t_enter);
            t_max = t_max.min(t_exit);
            if t_min > t_max { return false; }
        }
    }
    t_max >= 0.0  // 盒子在前方
}
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

ray-AABB 的工业用法:

- **鼠标拾取(picking)**:从相机发射光线到鼠标位置,找最近相交的 AABB
- **可见性测试**:光源到像素,是否被遮挡
- **碰撞检测**:子弹轨迹是否撞到物体
- **AI 视线**:NPC 是否看到玩家

所有这些都需要"光线和盒子相交",slab method 是工业标准。

### 3.2 · 🎨 图形学视角

数学上,slab method 是**线性方程组的高效求解**:

- 光线方程:3 个方程(每个轴一个)
- 盒子约束:6 个不等式

暴力求解:列方程组,解线性规划。slab method 利用盒子的"轴对齐"特性,把 3D 问题拆成 3 个 1D 问题,极快。

如果不是 AABB(OBB),需要先变换到局部空间(day421),变成 ray-AABB。这就是为什么 OBB 测试比 AABB 贵——多一次坐标变换。

### 3.3 · 🐧 Linux 系统编程视角

Linux 不做光线投射,但**线性方程组**概念同构:

- **网络包过滤**(iptables):包 = 光线,规则 = AABB
- **进程调度**:进程 = 光线,优先级区间 = AABB
- **文件路径解析**:路径 = 光线,目录树节点 = AABB

每个都是"某个对象是否落在某个范围内",和 ray-AABB 同构。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:slab method 为什么对 AABB 极快,但对 OBB 慢?具体说,OBB 需要额外多少成本?

**参考解答**:AABB 在每个轴上,板的法线就是坐标轴,光线和板的位置只取决于该轴的坐标。Slab method 把 3D 相交拆成 3 个独立的 1D 问题,每个轴只需要 1 次除法 + 2 次比较。

OBB 的板法线是任意方向(由 orientation 决定)。光线和 OBB 板的相交需要**点积**(光线方向和板法线),每对板 3 次乘加。三个轴总共 9 次乘加,vs AABB 的 3 次除法。

但更聪明的做法:**先把 ray 变到 OBB 局部空间**(用 orientation.inverse()),OBB 在局部空间就是 AABB。变换成本:1 次向量旋转(orientation.inverse() * ray.origin 和 dir)。然后 slab method 在局部空间跑,3 次除法 + 6 次比较。总成本:1 次旋转 + 3 次除法 + 6 次比较,vs AABB 的 3 次除法 + 6 次比较。**多了一次旋转**(约 9 次乘加)。

### Lv2 · 动手实践

**题**:实现 `ray_vs_aabb` + 单元测试。完成标准:
- 光线穿过盒子中心 → true,且 t = 进入时刻
- 光线平行 X 板,在板外 → false
- 光线反向 → false(盒子在背后)
- 光线穿过盒子的角落 → true
- 性能 benchmark:1M 次 ray-AABB < 50ms

**参考解答**:

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug)]
pub struct AABB { pub min: Vec3, pub max: Vec3 }

#[derive(Copy, Clone, Debug)]
pub struct Ray { pub origin: Vec3, pub dir: Vec3 }

impl Ray {
    pub fn new(origin: Vec3, dir: Vec3) -> Self {
        Self { origin, dir: dir.normalize() }
    }
}

pub fn ray_vs_aabb(ray: Ray, aabb: AABB) -> Option<f32> {
    let mut t_min = f32::NEG_INFINITY;
    let mut t_max = f32::INFINITY;

    for axis in 0..3 {
        let o = ray.origin[axis];
        let d = ray.dir[axis];
        let lo = aabb.min[axis];
        let hi = aabb.max[axis];

        if d.abs() < 1e-8 {
            // 光线平行于该轴的板
            if o < lo || o > hi {
                return None;
            }
        } else {
            // 算两个 t
            let t1 = (lo - o) / d;
            let t2 = (hi - o) / d;
            // 保证 t1 < t2
            let (t_enter, t_exit) = if t1 < t2 { (t1, t2) } else { (t2, t1) };
            t_min = t_min.max(t_enter);
            t_max = t_max.min(t_exit);
            if t_min > t_max {
                return None;
            }
        }
    }

    if t_max < 0.0 {
        return None;  // 盒子在光线背后
    }
    Some(t_min.max(0.0))  // 最近交点的 t
}
```

## 8 · Rust / Arch 落地代码

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug)]
pub struct AABB { pub min: Vec3, pub max: Vec3 }

#[derive(Copy, Clone, Debug)]
pub struct Ray { pub origin: Vec3, pub dir: Vec3 }

pub fn ray_vs_aabb(ray: Ray, aabb: AABB) -> Option<f32> {
    let mut t_min = f32::NEG_INFINITY;
    let mut t_max = f32::INFINITY;
    for axis in 0..3 {
        let o = ray.origin[axis];
        let d = ray.dir[axis];
        let lo = aabb.min[axis];
        let hi = aabb.max[axis];
        if d.abs() < 1e-8 {
            if o < lo || o > hi { return None; }
        } else {
            let inv_d = 1.0 / d;  // 乘法比除法快
            let t1 = (lo - o) * inv_d;
            let t2 = (hi - o) * inv_d;
            let (t_enter, t_exit) = if t1 < t2 { (t1, t2) } else { (t2, t1) };
            t_min = t_min.max(t_enter);
            t_max = t_max.min(t_exit);
            if t_min > t_max { return None; }
        }
    }
    if t_max < 0.0 { return None; }
    Some(t_min.max(0.0))
}

// 找最近相交的 AABB
pub fn ray_vs_aabbs_first_hit(ray: Ray, aabbs: &[AABB]) -> Option<(usize, f32)> {
    let mut best: Option<(usize, f32)> = None;
    for (i, aabb) in aabbs.iter().enumerate() {
        if let Some(t) = ray_vs_aabb(ray, *aabb) {
            if best.map_or(true, |(_, bt)| t < bt) {
                best = Some((i, t));
            }
        }
    }
    best
}

// 可见性测试:从 from 到 to,任何 AABB 相交就是遮挡
pub fn is_visible(from: Vec3, to: Vec3, occluders: &[AABB]) -> bool {
    let dir = to - from;
    let dist = dir.length();
    let ray = Ray { origin: from, dir: dir / dist };
    for aabb in occluders {
        if let Some(t) = ray_vs_aabb(ray, *aabb) {
            if t < dist {
                return false;  // 被遮挡
            }
        }
    }
    true
}

fn main() {
    let aabb = AABB { min: Vec3::new(-1.0, -1.0, -1.0), max: Vec3::new(1.0, 1.0, 1.0) };
    let ray = Ray { origin: Vec3::new(-5.0, 0.0, 0.0), dir: Vec3::new(1.0, 0.0, 0.0) };
    let hit = ray_vs_aabb(ray, aabb);
    println!("Hit: {:?}", hit);  // Some(4.0)

    let scene = vec![
        AABB { min: Vec3::new(-1.0, -1.0, -1.0), max: Vec3::new(1.0, 1.0, 1.0) },
        AABB { min: Vec3::new(3.0, -1.0, -1.0), max: Vec3::new(5.0, 1.0, 1.0) },
    ];
    let from = Vec3::new(-10.0, 0.0, 0.0);
    let to = Vec3::new(10.0, 0.0, 0.0);
    let vis = is_visible(from, to, &scene);
    println!("Visible: {}", vis);  // false(被两个盒子挡)

    let from = Vec3::new(2.0, 0.0, 0.0);  // 在两个盒子之间
    let to = Vec3::new(4.0, 0.0, 0.0);
    let vis = is_visible(from, to, &scene);
    println!("Visible from gap: {}", vis);  // true

    // 找最近命中
    let first = ray_vs_aabbs_first_hit(ray, &scene);

}
```

**Troubleshooting**:

- **t 计算错** — `inv_d = 1.0 / d`,然后用 `(lo - o) * inv_d`,不要除两次
- **D=0 处理** — `d.abs() < 1e-8` 而不是 `== 0.0`(浮点精度)
- **返回 t** — `t_min.max(0.0)` 保证非负,起点在盒内时返回 0
- **平行板检测错** — 检查 `o < lo || o > hi`,不是 `<= / >=`(边界情况)
- **找最近时漏** — `best.map_or(true, |(_, bt)| t < bt)` 写法,初始 best = None


### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
