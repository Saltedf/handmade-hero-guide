
# Day 370 · shader 回退 sRGB

> 不是所有 OpenGL 驱动都支持 sRGB framebuffer 扩展,玩家可能跑的是 10 年前的集显。今天 Casey 写一段 **shader fallback**:驱动支持 sRGB → 让 GPU 自动 gamma 校正;不支持 → 在 fragment shader 里手动做 sRGB 转换。

## 0 · 为什么要有这一天

你发布游戏到 Steam。第一批玩家报告:**"我电脑上画面发白/发暗,跟 YouTube 视频里不一样"**。你远程协助,发现玩家笔记本用的是 Intel HD 4000(2012 年集显),你游戏里启用的 `GL_FRAMEBUFFER_SRGB` 驱动直接忽略,sRGB 转换根本没做。

**sRGB 是什么**?这是一个**色彩空间标准**(standard RGB),1996 年由 HP 和微软联合提出,定义了显示器如何把 RGB 数值转成实际光强。关键点:**sRGB 是非线性的**——RGB 值 0.5 在屏幕上不是 50% 光强,而是约 21%。原因是人眼对暗色更敏感(对数感知),所以 sRGB 把暗色区域"分配更多数值"。

```
线性光强 = 0.5 (50% 实际光强)
        ↓ sRGB 编码(让暗色更精细)
        sRGB 值 ≈ 0.735 (约 187/255)

线性光强 = 0.5        显示器显示:
        ↑ sRGB 解码(反向)
        sRGB 值 = 0.735 → 亮度 ≈ 50%
```

**为什么这是个坑**?因为**光照计算必须在线性空间**。如果你的 shader 直接读 sRGB 纹理(数值 0.735)当线性光强(50%)用,所有光照公式都错。画面会过曝或欠曝,颜色不准。Casey 在 [day041](../phase-2/day041.md) 提到过:**光照计算必须在线性空间**,这是图形学的"第一条铁律"。

正确流程:
```
纹理(sRGB 编码)→ 解码到线性 → 光照计算 → 编码回 sRGB → 显示
```

**谁负责这个转换**?
- **硬件 framebuffer 支持 sRGB** (ARB_framebuffer_sRGB 扩展):GPU 在 fragment shader 输出时自动编码到 sRGB,纹理采样时自动解码。零开销,正确性保证
- **不支持**:你必须在 shader 里手动 `pow(color, 1.0/2.2)` 编码,纹理用 `GL_SRGB8_ALPHA8` 内部格式自动解码

Casey 今天的工作:**检测驱动支持,有则用硬件 sRGB,无则在 shader 里做 fallback**。这是个工程化任务,但揭示了图形学一个深层概念:**色彩管线(color pipeline)**。

心理锚点:今天之后,你能解释 sRGB 为什么非线性,知道什么时候要做 sRGB 转换,能在不支持 sRGB framebuffer 的硬件上写出 fallback shader。

## 1 · Casey 今天做了什么(HH 脉络)

Day 369 写完 vertex / fragment shader 概念后,Casey 发现一个细节:**fragment shader 输出的颜色,直接送到 framebuffer**,如果 framebuffer 不是 sRGB,颜色没经过 gamma 校正,画面看起来发暗。他要做的是:

1. **检测 ARB_framebuffer_sRGB 扩展**:`glGetString(GL_EXTENSIONS)` 找扩展字符串
2. **如果支持**:启用 `glEnable(GL_FRAMEBUFFER_SRGB)`,GPU 自动处理 sRGB 编解码
3. **如果不支持**:在 fragment shader 末尾加一行 `frag_color.rgb = pow(frag_color.rgb, vec3(1.0/2.2));`,手动做 sRGB 编码
4. **纹理加载也处理**:支持时用 `GL_SRGB8_ALPHA8` 内部格式(GPU 自动解码);不支持时 shader 里手动 `pow(tex_color.rgb, vec3(2.2))`

Casey 用一个 `#define SRGB_FALLBACK` 在 shader 里切换两种模式,编译时选择。这要求维护两份 shader 路径,增加复杂度。

Casey 在视频里展示了**正确 / 错误 sRGB 的对比图**:错误版本画面发暗、颜色饱和度低;正确版本画面明亮、色彩还原准确。

## 2 · 心智模型

### 类比:sRGB 就像相机的 RAW → JPEG

想象你用单反相机拍照。传感器记录的原始数据是**线性光强**(RAW 文件),数值和光子数成正比。但相机存储成 JPEG 时,会做 sRGB 转换——把线性数据"压缩"到 sRGB 色彩空间,让显示器能正确显示。

```
传感器 RAW(线性)  →  相机处理  →  JPEG(sRGB 编码)
[0.0 ~ 1.0 线性]                  [0.0 ~ 1.0 sRGB = pow(linear, 1/2.2)]
```

显示器播放 JPEG 时反向转换:JPEG(sRGB)→ 显示器电路 → 线性光强 → 你眼睛。

游戏渲染做同样的事:
```
fragment shader 计算(线性光强)  →  sRGB 编码  →  framebuffer  →  显示器
```

如果你不做 sRGB 编码,fragment shader 输出的 0.5(50% 光强)直接当 sRGB 值传给显示器,显示器以为这个值代表 50% sRGB 编码,显示 ~21% 光强。**画面整体发暗**,因为漏了一步。

### 严谨原理:sRGB 转换公式

sRGB 和线性 RGB 的转换关系:

**线性 → sRGB**(fragment shader 输出时):
```
sRGB = 1.055 * linear^(1/2.4) - 0.055   (近似)
```

简化版(游戏工业常用,gamma 2.2 近似):
```
sRGB = linear^(1/2.2)
```

**sRGB → 线性**(纹理采样时):
```
linear = sRGB^2.2
```

精确版分段函数(piecewise):

```
线性 → sRGB:
  if linear <= 0.0031308:
    sRGB = 12.92 * linear
  else:
    sRGB = 1.055 * linear^(1/2.4) - 0.055

sRGB → 线性:
  if sRGB <= 0.04045:
    linear = sRGB / 12.92
  else:
    linear = ((sRGB + 0.055) / 1.055)^2.4
```

分段是为了在暗部保留更高精度。游戏工业大部分用 gamma 2.2 近似,差距肉眼不可见。

### 色彩管线的三种实现

**方案 1:全程硬件 sRGB**(最理想)

```
纹理格式:GL_SRGB8_ALPHA8  (GPU 采样时自动 sRGB → 线性)
shader 里:所有计算都在线性空间
framebuffer 格式:sRGB(写入时自动 线性 → sRGB)
驱动 API:glEnable(GL_FRAMEBUFFER_SRGB)
```

零 shader 代码改动,全部 GPU 自动。要求 OpenGL 3.0+(ARB_framebuffer_sRGB)。

**方案 2:半硬件(纹理自动,shader 输出手动)**

```
纹理格式:GL_SRGB8_ALPHA8  (GPU 自动解码)
shader 里:计算完后手动编码
  frag_color.rgb = pow(frag_color.rgb, vec3(1.0/2.2));
```

适合不支持 framebuffer_sRGB 的驱动。

**方案 3:全软件**(最不理想)

```
纹理格式:GL_RGBA8  (普通线性)
shader 里:
  vec3 tex_linear = pow(texture(tex, uv).rgb, vec3(2.2));   // 解码
  // 计算
  frag_color.rgb = pow(color, vec3(1.0/2.2));               // 编码
```

性能差(每次纹理采样做 pow),正确性依赖 shader 实现质量。

Casey 选择**方案 1 + 方案 2 fallback**:支持 framebuffer_sRGB 用方案 1,不支持用方案 2。

### OpenGL API

检测扩展(老式):

```rust
unsafe {
    let ext_str_ptr = gl::GetString(gl::EXTENSIONS) as *const i8;
    let ext_str = std::ffi::CStr::from_ptr(ext_str_ptr).to_str().unwrap();
    let has_srgb = ext_str.contains("GL_ARB_framebuffer_sRGB");
}
```

OpenGL 3.0+ 提供更好 API:

```rust
unsafe {
    let mut num_extensions = 0;
    gl::GetIntegerv(gl::NUM_EXTENSIONS, &mut num_extensions);
    let mut has_srgb = false;
    for i in 0..num_extensions {
        let ext_ptr = gl::GetStringi(gl::EXTENSIONS, i as GLuint) as *const i8;
        let ext = std::ffi::CStr::from_ptr(ext_ptr).to_str().unwrap();
        if ext == "GL_ARB_framebuffer_sRGB" {
            has_srgb = true;
            break;
        }
    }
}
```

启用硬件 sRGB:

```rust
unsafe { gl::Enable(gl::FRAMEBUFFER_SRGB); }
```

创建 sRGB 纹理:

```rust
// 注意:internalformat 用 GL_SRGB8_ALPHA8
unsafe {
    gl::TexImage2D(
        gl::TEXTURE_2D, 0,
        gl::SRGB8_ALPHA8 as GLint,   // sRGB 内部格式
        width, height, 0,
        gl::RGBA, gl::UNSIGNED_BYTE,
        pixels.as_ptr() as *const _,
    );
}
```

### Fragment Shader 的 fallback

```glsl
#version 330 core

out vec4 frag_color;
uniform bool u_srgb_fallback;   // CPU 上传 true 时做手动 sRGB

void main() {
    vec3 color = /* 计算 */;

    if (u_srgb_fallback) {
        // 手动 sRGB 编码
        color = pow(color, vec3(1.0 / 2.2));
    }
    // 否则 framebuffer_sRGB 自动做

    frag_color = vec4(color, 1.0);
}
```

注意:`if (uniform)` 在 GPU 上是 **constant branch**,所有 fragment 走同一分支,GPU 优化为不分支。性能无损失。

### Rust 视角:封装色彩管线

```rust
pub struct ColorPipeline {
    pub framebuffer_srgb_supported: bool,
    pub srgb_enabled: bool,
}

impl ColorPipeline {
    pub fn detect() -> Self {
        let supported = unsafe {
            let mut n = 0;
            gl::GetIntegerv(gl::NUM_EXTENSIONS, &mut n);
            (0..n).any(|i| {
                let ext = gl::GetStringi(gl::EXTENSIONS, i as GLuint);
                let c_str = std::ffi::CStr::from_ptr(ext as *const i8);
                c_str.to_string_lossy() == "GL_ARB_framebuffer_sRGB"
            })
        };

        if supported {
            unsafe { gl::Enable(gl::FRAMEBUFFER_SRGB); }
        }

        Self {
            framebuffer_srgb_supported: supported,
            srgb_enabled: supported,
        }
    }

    pub fn shader_uniform_value(&self) -> i32 {
        // 给 shader 的 u_srgb_fallback uniform:不支持时返回 1
        if self.framebuffer_srgb_supported { 0 } else { 1 }
    }

    pub fn texture_internal_format(&self) -> GLenum {
        // 不支持时降级到普通 RGBA8
        if self.framebuffer_srgb_supported { gl::SRGB8_ALPHA8 } else { gl::RGBA8 }
    }
}
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业的色彩管理演化:

- **1990s**: 不做 sRGB,直接当线性。画面普遍偏暗,但玩家习惯了
- **2000s**: 美术开始在 Photoshop 里"用线性光强画 sRGB 显示",主观补偿
- **2010s**: 引擎普遍支持 sRGB framebuffer,光照计算在线性空间
- **2020s**: HDR 显示器普及,引入 HDR10 / scRGB / Rec.2020,色彩空间更复杂

**游戏色彩管线的现代标准**:
- 输入纹理:sRGB(美术用显示器画,显示器用 sRGB)
- 中间计算:线性(物理正确)
- LDR 输出(普通显示器):sRGB
- HDR 输出(HDR 显示器):scRGB linear 或 HDR10 PQ

**HDR 带来的复杂度**:HDR 显示器峰值亮度可达 1000 nit(普通 sRGB 100 nit),色彩 gamut 更广(Rec.2020 比 sRGB 大 50%)。光照计算必须用 float precision(线性空间下),最后做 tone mapping 到 HDR 输出范围。

Casey 现在(LDR)做的是 2010 年代标准,够用。Phase 8+ 才会涉及 HDR。

### 3.2 · 🎨 图形学视角

色彩空间是个深坑。除了 sRGB 还有:

| 色彩空间 | 用途 | 特点 |
|---|---|---|
| sRGB | 普通 LCD 显示器 | gamma 2.2 近似 |
| Display P3 | Apple iMac / iPhone | 比 sRGB 多 25% 色域 |
| Rec.2020 | 4K HDR 电视 | 比 sRGB 多 75% 色域 |
| Adobe RGB | 专业摄影 | 比 sRGB 多 35% 色域 |
| ACEScg / ACES2065-1 | 电影工业 | 极宽色域 + 极宽动态范围 |
| Linear sRGB | 计算中间格式 | sRGB 色域但线性光强 |

**Gamma vs 线性**:

Gamma 是 sRGB 的"非线性编码"部分,把线性光强做 `pow(x, 1/2.2)` 变换,让暗色精度更高。**所有光照计算必须在线性空间**,然后做 gamma 编码输出。

**为什么 pow(x, 1/2.2) 而不是 1/2.4**?sRGB 标准用 2.4,但显示器实际平均 gamma 是 2.2,所以工业用 2.2 简化。

**色彩管理在现代引擎**:

```
纹理(sRGB)→ 线性化 → 计算 → tonemap → gamma 编码 → 显示
       ↓              ↓       ↓       ↓           ↓
     sRGB          Linear   Linear  LDR        sRGB
   (8-bit)         (f32)   (f32)   (8-bit)   (8-bit)
```

HDR 显示器则:
```
纹理(sRGB)→ 线性化 → 计算(HDR float)→ HDR tonemap → HDR10 PQ → 显示
       ↓              ↓                  ↓              ↓
     sRGB          Linear             Linear HDR    HDR10 10-bit
```

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么光照计算必须在线性空间?如果直接用 sRGB 值(没解码)做 Lambert 光照,会发生什么?

**参考解答**:Lambert 光照公式 `diffuse = max(0, N·L) × base_color`,这个乘法假设 base_color 是线性光强(数值 0.5 = 50% 光强)。如果 base_color 是 sRGB 编码的(数值 0.5 = 21% 光强),乘法得到的不是正确的 21% × 50% = 10.5% 光强,而是 0.5 × 0.5 = 0.25 的"sRGB 数值",经显示器解码变成约 5% 光强。**结果比正确值暗一倍**。

更严重的是**两个光源叠加**:`0.5 + 0.5 = 1.0`。线性空间正确(50% + 50% = 100%);sRGB 直接相加:0.5 sRGB + 0.5 sRGB = 1.0 sRGB,但 0.5 sRGB = 21% 光强,1.0 sRGB = 100% 光强,**21% + 21% ≠ 100%**。画面在亮处过曝(多个光源相加被压缩)。

### Lv2 · 动手实践

**题**:写两个 fragment shader,渲染同一张 sRGB 纹理。一个正确(解码 sRGB → 计算 → 编码),一个错误(不做任何 sRGB 处理)。完成标准:两个 shader 渲染结果**视觉上有明显差别**(正确版本中间调亮,错误版本中间调暗)。

**参考解答**:

```glsl
// 错误版本(error.frag):不做 sRGB 处理
#version 330 core
in vec2 v_uv;
out vec4 frag_color;
uniform sampler2D u_tex;
void main() {
    vec3 c = texture(u_tex, v_uv).rgb;
    // 加点光照
    c *= 1.5;
    frag_color = vec4(c, 1.0);
}
```

```glsl
// 正确版本(correct.frag):手工 sRGB 处理
#version 330 core
in vec2 v_uv;
out vec4 frag_color;
uniform sampler2D u_tex;
void main() {
    // 解码 sRGB → 线性
    vec3 c = texture(u_tex, v_uv).rgb;
    c = pow(c, vec3(2.2));          // sRGB → 线性

    // 在线性空间做光照
    c *= 1.5;

    // 编码 线性 → sRGB
    c = pow(c, vec3(1.0 / 2.2));

    frag_color = vec4(c, 1.0);
}
```

**关键解释**:
- 两个 shader 唯一差别是 sRGB 解码 / 编码
- 切换看效果,正确版本中间调(0.3-0.7)更亮,错误版本中间调更暗
- 实际项目中应该用 `GL_SRGB8_ALPHA8` 纹理格式让 GPU 自动解码,这里手动做是为了教学

### Rust:带 fallback 的 sRGB 检测和 shader 切换

```rust
// Cargo.toml: gl = "0.14"

use gl::types::*;
use std::ffi::CString;

pub struct SrgbState {
    pub hardware_supported: bool,
    pub enabled: bool,
}

impl SrgbState {
    pub fn detect_and_enable() -> Self {
        let supported = Self::check_extension("GL_ARB_framebuffer_sRGB");

        if supported {
            unsafe { gl::Enable(gl::FRAMEBUFFER_SRGB); }
            println!("sRGB: hardware path enabled");
        } else {
            println!("sRGB: hardware not supported, using shader fallback");
        }

        Self {
            hardware_supported: supported,
            enabled: supported,
        }
    }

    fn check_extension(name: &str) -> bool {
        let mut num_extensions = 0;
        unsafe {
            gl::GetIntegerv(gl::NUM_EXTENSIONS, &mut num_extensions);
        }

        for i in 0..num_extensions {
            unsafe {
                let ext_ptr = gl::GetStringi(gl::EXTENSIONS, i as GLuint);
                if !ext_ptr.is_null() {
                    let c_str = std::ffi::CStr::from_ptr(ext_ptr as *const i8);
                    if c_str.to_string_lossy() == name {
                        return true;
                    }
                }
            }
        }
        false
    }

    /// 返回给 shader 的 u_srgb_fallback uniform 值
    /// true(1)= 手动做 sRGB,false(0)= 硬件自动
    pub fn shader_uniform(&self) -> i32 {
        if self.hardware_supported { 0 } else { 1 }
    }

    /// 纹理内部格式:sRGB 支持时用 SRGB8_ALPHA8,否则降级
    pub fn texture_internal_format(&self) -> GLenum {
        if self.hardware_supported {
            gl::SRGB8_ALPHA8
        } else {
            gl::RGBA8
        }
    }
}

const VERT_SRC: &str = r#"
#version 330 core
layout(location = 0) in vec3 a_pos;
layout(location = 2) in vec2 a_uv;
out vec2 v_uv;
uniform mat4 u_mvp;
void main() {
    gl_Position = u_mvp * vec4(a_pos, 1.0);
    v_uv = a_uv;
}
"#;

// 注意 SRGB_FALLBACK 是 #define,在编译时根据硬件选择
fn frag_src(srgb_fallback: bool) -> String {
    let define = if srgb_fallback {
        "#define SRGB_FALLBACK 1"
    } else {
        "#define SRGB_FALLBACK 0"
    };

    format!(r#"
#version 330 core
{}
in vec2 v_uv;
out vec4 frag_color;
uniform sampler2D u_tex;
uniform vec3 u_light_dir;

void main() {{
    // 纹理采样

#if SRGB_FALLBACK
    // 手动 sRGB → 线性
    base = pow(base, vec3(2.2));
#endif

    // 在线性空间做光照
    float light = 0.5 + 0.5 * u_light_dir.x;  // 简化:fake diffuse
    vec3 color = base * light;

#if SRGB_FALLBACK
    // 手动 线性 → sRGB
    color = pow(color, vec3(1.0 / 2.2));
#endif

    frag_color = vec4(color, 1.0);
}}
"#, define)
}
```

**关键 Rust 特性解释**:
- `gl::GetStringi(gl::EXTENSIONS, i)` — OpenGL 3.0+ 的扩展查询 API,按索引取扩展名
- `to_string_lossy()` — `CStr` 转 Rust `String`,非 UTF-8 字节用 `?` 替代(安全)

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
