# Day 303 · 尝试 Y 与 Z 分离排序

> 昨天 Casey 在 Day 302 严格证明了"sprite 排序没有全序"(没有一种线性顺序能表达所有遮挡关系)。今天的尝试:**Y 和 Z 维度分开**——Y 维度(屏幕上下)sort、Z 维度(深度,如 layer)单独处理。这是个**失败的尝试**——代码写了,测试发现不行,Casey 当天就回退。但失败本身有教学价值——你看到 Casey 怎么验证假设、推翻自己、止损切换。

## 0 · 为什么要有这一天

让我先描述 Casey 此时的思维状态。Day 302 证明没有全序后,他陷入两难:

- 用拓扑排序(Day 304 即将登场)能精确解决,但实现复杂
- 用简化 sort_key(Day 300 已经写)大部分场景有效,但偶尔错
- 有没有"中间方案"——比 sort_key 更精确,比拓扑排序更简单?

**今天的假设**:Y 和 Z 分开 sort。具体来说:

- **Z 维度**(垂直于屏幕,远近):用 `z_layer` 字段决定 sprite 在哪个深度层
- **Y 维度**(屏幕上下):同层内按 `bottom_y` 排序

两遍 sort:先按 Z 分组,组内按 Y 排序。看起来优雅,因为它把"复杂问题"拆成"两个简单问题"——Z 排序是简单整数比较,Y 排序是简单浮点比较。

但**实际验证失败**。Casey 在视频里构造反例:玩家在桥上,桥下有水,玩家走到桥边缘,玩家位置在桥的 Y 范围内但 Z 在桥上方。这种**跨层遮挡**无法用"Z 分组、Y 排序"表达。

**今天的核心价值**不是解决方案(失败),而是**工程思维方法论**:

**学完今天,你应该能**:

- 解释"假设 → 实验 → 推翻"的科学方法在工程中的应用
- 描述为什么"维度分离"看起来优雅但常失败——维度间的耦合
- 构造 Y/Z 耦合的具体反例,证明分离 sort 不工作
- 知道何时**止损**:尝试多久后判断方案不可行
- 用 `git revert` 干净回退失败实验,而不是"修修补补"
- 区分"看起来对的算法"(happy path 通过)和"对的算法"(corner case 也通过)
- 理解为什么 Day 304 的拓扑排序是正确解——它处理了 Y/Z 耦合
- 对比工业游戏引擎的渲染排序方案:layer + y + sort_rule、depth peeling、A-buffer

**今天的方法论价值**超过具体代码。学会**快速试错、及时止损**的工程师,比"死磕一个方案到底"的工程师高效 10 倍。

**第三,如何利用失败**。Casey 在视频里详细分析失败原因——Y/Z 耦合——这帮他**理解问题本质**,直接导向 Day 304 的拓扑排序方案。**失败的尝试照亮正确路径**。

## 2 · 心智模型

### 2.1 类比:三维空间投影到二维

把 sprite 想象成 3D 空间中的卡片,有 X、Y、Z 坐标。相机从前方(Z 远)看。

- **Z 维度**:卡片远近,远的先画(被近的遮挡)
- **Y 维度**:卡片上下,下的更近(2.5D 中"下面更前")
- **X 维度**:卡片左右,无遮挡关系

Y 和 Z 看起来独立——不同 Z 决定层,Y 决定层内顺序。**理论上的简化**:Z sort 决定层,每层内 Y sort。

但**实际验证发现耦合**:

考虑:

- 一张大卡片(Y 范围 100-200,Z=1,后景)
- 一张小卡片(Y 范围 50-150,Z=2,前景)

按 Z 分离:大卡片(Z=1)先画,小卡片(Z=2)后画。视觉上**小卡片的上半(50-100)**其实没和大卡片重叠(它在 Z=1 的"上面",但 Z=1 那里没东西)——所以这部分 Z 决定无意义。**小卡片的下半(100-150)**和大卡片重叠,Z=2 决定小卡片在前——正确。

这个简单例子 Z 分离**正确**。失败需要更复杂配置。

**真正的反例**:**两张卡片 Z 相同但 Y 重叠**。Z 维度无法决定,Y 按 bottom_y 决定——但 bottom_y 相同时仍 ambiguity。这是 Day 302 的"没有全序"——Z 分离**没有解决**部分序问题,只是把 sort_key 表达方式重新组织。Casey 今天的尝试相当于"重组 sort_key",没本质突破。

### 2.2 Y 和 Z 的深层耦合

更深的耦合:**某些 sprite 的 Y 顺序依赖另一个的 Z**。

考虑楼梯场景:

- 玩家在楼梯上(Y 在某一层,Z 由楼梯位置决定)
- 玩家从楼梯下走上楼梯:Y 变化时,Z 也跟着变(从 Z=0 楼梯下 到 Z=1 楼梯上)

**Z 不是 sprite 的独立属性,是 Y 的函数**。这种耦合让"分离 sort"无意义——你不能先 sort Z 再 sort Y,因为 Z 由 Y 决定。

更具体:**玩家在楼梯中间**(Y 在楼梯的 Y 范围中段)。这时玩家是 Z=0 还是 Z=1?

- 如果 Z=0(楼梯下):玩家被楼梯遮挡(楼梯在玩家上面)
- 如果 Z=1(楼梯上):玩家在楼梯前(玩家踩在楼梯上)

视觉上**两者都不对**——玩家的脚被楼梯遮挡(脚在楼梯下),但玩家的头在楼梯上(头比楼梯高)。这种**半遮挡**用单值 Z 无法表达。

工业游戏引擎(Unreal、Unity)处理半遮挡的方法:

- **Multiple sprite**:把玩家拆成"脚 sprite"(Z=0)和"身体 sprite"(Z=1)。但拆分增加 asset 工作量。
- **Depth mask**:用 mask texture 指定 sprite 每像素的 Z。GPU 渲染时 per-pixel Z 比较。但 CPU sort 不适用。
- **Layer + custom shader**:shader 里动态决定 Z,绕过 CPU sort。需要 GPU 编程。

Casey 今天的 Y/Z 分离没解决这些场景。失败是必然的——**单值 Z + 单值 Y 表达不了半遮挡**。

### 2.3 今天的代码(尝试性)

```rust
struct Entity {
    pos: Vec2,
    z_layer: u8,       // 新增:Z 维度
    bounds: Aabb,
    name: &'static str,
}

fn separate_sort(entities: &mut [Entity]) {
    // 第一遍:整体按 z_layer sort
    entities.sort_by_key(|e| e.z_layer);

    // 第二遍:同 z_layer 内按 bottom_y sort
    let mut start = 0;
    while start < entities.len() {
        let z = entities[start].z_layer;
        let mut end = start + 1;
        while end < entities.len() && entities[end].z_layer == z {
            end += 1;
        }
        entities[start..end].sort_by_key(|e| e.bounds.bottom() as u32);
        start = end;
    }
}
```

两遍 sort,看起来优雅。但 Day 302 证明这种"两遍独立"无法处理部分序。

**等效的复合 sort**(Rust 风格):

```rust
fn composite_sort(entities: &mut [Entity]) {
    entities.sort_by(|a, b| {
        a.z_layer.cmp(&b.z_layer)
            .then_with(|| {
                a.bounds.bottom()
                    .partial_cmp(&b.bounds.bottom())
                    .unwrap_or(Ordering::Equal)
            })
    });
}
```

两者等价——都是"先 Z 后 Y"的 lexicographic order。但 lexicographic order 假设**维度独立**——Z 和 Y 各自决定顺序,组合不影响。**耦合的维度不能用 lexicographic order**。

### 2.4 失败诊断:用反例证明

Casey 写反例测试:

- 多个 sprite,部分跨 Z 层
- 部分 sprite 的"视觉前后"和 Z 排序结果矛盾
- 例如:玩家被远处的墙遮挡,虽然玩家更前

具体反例:**玩家在桥边缘**

```rust
let entities = vec![
    Entity { name: "Water",  pos: (100, 130), z: 0, bounds: ... },  // 水 Z=0
    Entity { name: "Bridge", pos: (100, 100), z: 1, bounds: ... },  // 桥 Z=1
    Entity { name: "Player", pos: (100,  80), z: 2, bounds: ... },  // 玩家 Z=2(桥上)
];

// Y/Z 分离 sort 输出:Water → Bridge → Player
// 视觉直觉:玩家在桥上,玩家踩着桥,水在桥下——顺序对

// 但如果玩家走到桥边缘,Y 范围开始和桥重叠 + 部分悬空到水的 Y 范围:
Entity { name: "Player", pos: (100, 110), z: ?, bounds: covers both bridge AND water Y ranges }
// 现在 Z=2(玩家在桥上)但玩家部分悬空到水之上
// 视觉上:水的某些部分应该在玩家之上(因为水比玩家"靠下")
// 但 Z 分离说 Water Z=0 比 Player Z=2 后画——水被玩家遮挡
// 错!
```

**结论**:Z 分离**对玩家完全在桥上的场景对**,对**玩家半在桥上半悬空**错。后者是 2.5D 游戏常见配置(玩家跨越多个 layer)。

### 2.5 止损:回退到 Day 300 方案

今天结束时,Casey 回退代码,保留 Day 300 的 `sort_rule + sprite bounds`。承认这条路不通。

**回退的方法论**:

```bash
# 1. 看今天的 commit
git log --oneline -5

# 2. 确认失败(revert 测试也失败)
git revert HEAD~1  # 回退今天的 commit

# 3. 或者用 reset(更激进,丢历史)
git reset --hard HEAD~1

# 4. 保留今天的代码作为参考(在另一个 branch)
git branch y-z-experiment-failed  # 保留
git checkout main
git revert HEAD
```

**止损原则**:

1. **明确失败标准**:开始尝试前定"什么时候算失败"。Casey 的标准:"反例测试失败"。
2. **客观验证**:不要"我感觉不对"——写测试,跑数据。
3. **时间盒**:给尝试设时限(几小时到一天)。超时未成功,止损。
4. **保留知识**:把失败原因写下来(代码注释、commit message、issue),下次有人想同样方案时知道此路不通。
5. **不要修修补补**:发现根本性问题(Y/Z 耦合)时,不要加 hack 绕过——hack 会越来越复杂,最后比直接用拓扑排序还乱。

**总结**:今天是一次失败的尝试——Y 和 Z 分离 sort 看起来合理但实际不工作,因为它们耦合。工程价值:展示如何**快速验证假设**并止损。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对"独立 sort 维度"的探索历史悠久:

**layer + y sort**(今天尝试的):部分有效。商业 2D 游戏大多用这个方案,接受边缘情况错乱。RPG Maker、GameMaker Studio、Godot 2D 默认提供。

**multi-pass render**:每 pass 处理一层。但透明物体仍需 sort——本质没解决。

**depth peeling**:GPU 多 pass,每 pass 剥一层最前透明像素。完美但慢(N-pass = N 倍渲染时间)。NVIDIA 2001 论文推广。

**per-pixel sort(A-buffer)**:像素级 sort,每像素存所有覆盖它的 fragment。完美但内存大(每像素 list)。Carpenter 1984 论文,用于电影渲染。

**Z-buffer + alpha testing**:对不透明用 Z-buffer(完美),对透明用 alpha testing(硬边缘,无真正半透明)。Minecraft 用这种——草、树叶用 alpha test。

商业游戏大多用 layer + y + sort_rule,接受边缘情况错乱。少数高要求(如 CryEngine)用 depth peeling 或 A-buffer。

Casey 在 HH 选择**拓扑排序**——比 layer + y 精确,比 depth peeling 简单。中间方案。

### 3.2 · 🎨 图形学视角

图形学的"独立维度"是 **separate axes**(分离轴)。某些渲染算法用分离轴理论(SAT:Separating Axis Theorem):

- **Collision detection**:两个凸多边形不重叠 ⟺ 存在一条轴使它们投影不重叠。SAT 把"2D 重叠检测"转成"多个 1D 投影检测"。
- **Light culling**:沿 X 轴的 light 不影响 Y 轴物体——分轴裁剪。
- **Frustum culling**:把视锥分成 6 个 plane,每 plane 独立裁剪。

但**最终像素颜色**是所有轴的合成——不能完全独立。今天的 Y/Z 分离失败本质类似——视觉是 Y 和 Z 的合成,不能完全独立 sort。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的"分维度排序"对应**多 key sort**:

- process priority(优先级)
- vruntime(虚拟运行时间)
- nice value(用户设置)

CFS(Completely Fair Scheduler)用 vruntime 作为主 key,priority 作为 tie-breaker。但 priority 影响 vruntime 计算权重——**不是真独立**。

游戏 sort 的 Y/Z 耦合和这个类似——**两个看似独立的 key 实际互相影响**。

**Linux 调度器的妥协**:接受"完美公平不可能",用启发式(heuristic)接近公平。游戏 sort 也是——接受"完美排序不可能"(Day 302 已证),用拓扑排序接近正确。

### 3.4 · 🦀 Rust 生态视角

Rust 的 `slice::sort_by` 允许任意比较函数。今天的尝试是写一个**复合 sort**:

```rust
fn sort_by_y_then_z(entities: &mut [Entity]) {
    entities.sort_by(|a, b| {
        a.z_layer.cmp(&b.z_layer)
            .then(a.bounds.bottom()
                .partial_cmp(&b.bounds.bottom())
                .unwrap_or(Ordering::Equal))
    });
}
```

**lexicographic ordering**——先比第一个 key,相同再比第二个。Rust 的 `cmp::then` 实现这个。

但发现这种"复合"无法表达所有 sprite 关系——**lexicographic 假设维度独立**,而 Y/Z 不独立。

**Rust 替代方案**:

- **自定义 Ord**:实现 `Ord` trait,返回任意顺序。但 `Ord` 要求全序(transitive + antisymmetric + total),Day 302 证明 sprite 关系不满足全序——**实现 Ord 会违反 contract**。
- **Sort by key**:用 `sort_by_key`,但 key 必须是 `Ord`。
- **Topological sort**:不假设全序,处理 DAG。这是 Day 304 的方案。

工业 Rust 项目遇到"非全序 sort"时,**不用 std sort**,改用拓扑排序或自定义排序算法。今天的失败是教 Rust 程序员识别这个边界。

### 5.2 历史上的失败算法

- **Bubble sort for big data**:O(n²),只适合教学。

- **Naive Bayes for correlated features**:独立性假设错。
- **Google Wave(2010)**:实时协作失败,但技术成 Google Docs。
- **Apple Newton(1993)**:手写识别失败,但孵化了 iOS。
- **今天的 Y/Z 分离**:看似对,实际不工作。

**失败的价值**:它告诉我们问题本质。Perceptron 失败催生 multi-layer network。Google Wave 失败催生 Slack。今天 Y/Z 分离失败催生 Day 304 拓扑排序。

### 5.3 止损的工业实践

**Time-boxing**:给任务设固定时间,超时未完成必须停止。Agile / Scrum 的核心实践。

**Fail fast**:快速失败,快速学习。硅谷创业文化的核心。

**Sunk cost fallacy**:沉没成本谬误。已经投入的时间不能成为"继续错路"的理由。Casey 今天没陷入这个——他试了一天,发现根本问题,立即回退。

**A/B testing**:同时跑两个方案,看哪个更好。互联网公司标准实践。Casey 没用 A/B(单人开发),但**心智模型相似**——保持 Day 300 方案,试 Day 303 方案,对比后选更好的(回到 Day 300)。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:为什么 Y 和 Z 分离 sort 在 HH 这种 2.5D 场景失败?具体哪个场景让它失效?

**参考解答**:

失败场景:**跨 Z 层的 sprite 互相遮挡**。具体反例:

- 楼梯 sprite(Z=0)在屏幕下方
- 玩家 sprite(Z=0,在楼梯下)在楼梯之上
- 玩家走上楼梯,现在 Z=1,但 Y 位置在楼梯的 Y 范围内

如果按 Z 分离:Z=0 全画,Z=1 全画。但玩家的下半身(走在楼梯上)应该被楼梯遮挡——这种"半遮挡"无法用 Z 分离表达。

更经典的反例:**玩家在桥上,桥下有水**。

- 水 Z=0
- 玩家 Z=1(在桥上)
- 桥 Z=0.5(玩家踩在桥上)

按 Z 分离:水 → 桥 → 玩家。**这个简单 case actually 对**。

但当玩家走到桥边缘,玩家 Y 范围开始覆盖水的 Y 范围:

- 玩家底部 Y 现在低于桥底部 Y(玩家悬挂到水之上)
- 视觉上:水面的某些部分应该在玩家之上(因为水比玩家"靠下")
- 但 Z 分离说 Water Z=0 < Player Z=2,所以水先画,玩家后画——水被玩家遮挡

**错!** 视觉直觉是"水在玩家之上"(水更近镜头下方)。

**Y 和 Z 的耦合本质**:**垂直方向**(Z,深度)和**屏幕上下**(Y,屏幕坐标)在某些场景混淆。半遮挡 sprite 无法用单值 Z 表达。

### Lv2 · 动手实践

**题**:实现 Y/Z 分离 sort,然后**构造一个反例**证明它失败。

完成标准:写出 sort 函数,然后给出具体 entity 配置,显示 sort 输出"错"(和视觉直觉不符)。

**完整代码**:

```rust
use std::cmp::Ordering;

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug)]
struct Aabb {
    x: f32, y: f32, w: f32, h: f32,
}
impl Aabb {
    fn from_center(p: Vec2, w: f32, h: f32) -> Self {
        Self { x: p.x - w/2.0, y: p.y - h/2.0, w, h }
    }
    fn bottom(&self) -> f32 { self.y + self.h }
    fn overlaps(&self, o: &Self) -> bool {
        self.x < o.x + o.w && self.x + self.w > o.x
            && self.y < o.y + o.h && self.y + self.h > o.y
    }
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec2,
    z: u8,
    bounds: Aabb,
    name: &'static str,
}

fn y_z_separate_sort(entities: &mut [Entity]) {
    entities.sort_by(|a, b| {
        a.z.cmp(&b.z)
            .then(a.bounds.bottom()
                .partial_cmp(&b.bounds.bottom())
                .unwrap_or(Ordering::Equal))
    });
}

fn main() {
    // 反例:玩家走到桥边缘,半悬空到水之上
    let mut entities = vec![
        // 桥
        Entity {
            pos: Vec2::new(100.0, 100.0),
            z: 1,
            bounds: Aabb::from_center(Vec2::new(100.0, 100.0), 200.0, 32.0),
            name: "Bridge",
        },
        // 水(在桥下)
        Entity {
            pos: Vec2::new(100.0, 140.0),
            z: 0,
            bounds: Aabb::from_center(Vec2::new(100.0, 140.0), 300.0, 64.0),
            name: "Water",
        },
        // 玩家(走到桥边缘,Y 范围覆盖水和桥)
        Entity {
            pos: Vec2::new(100.0, 130.0),
            z: 2,  // 玩家在桥上
            bounds: Aabb::from_center(Vec2::new(100.0, 130.0), 32.0, 80.0),
            // bounds: y=90 to y=170(覆盖桥 84-116 和水 108-172)
            name: "Player",
        },
    ];

    println!("Before sort:");
    for e in &entities {
        println!("  {} z={} bottom={:.0} y_range=[{:.0}, {:.0}]",
            e.name, e.z, e.bounds.bottom(),
            e.bounds.y, e.bounds.y + e.bounds.h);
    }

    y_z_separate_sort(&mut entities);

    println!("\nAfter Y/Z separate sort:");
    for (i, e) in entities.iter().enumerate() {
        println!("  #{}: {} z={} bottom={:.0}", i, e.name, e.z, e.bounds.bottom());
    }
    // 输出:Water → Bridge → Player
    //       (z=0)  (z=1)   (z=2)

    println!("\nVisual analysis:");
    println!("  Player's bottom ({:.0}) is below Water's top ({:.0})",
        entities[2].bounds.bottom(),
        entities[0].bounds.y + entities[0].bounds.h);
    println!("  → Water SHOULD partially cover player's legs");
    println!("  But Y/Z sort says: Water drawn FIRST, Player drawn LAST");
    println!("  → Player covers Water. WRONG!");
}
```

**承认**:这个反例的真实"视觉错乱"程度依赖具体 sprite 形状。Casey 在视频里花了一整集才构造出无可辩驳的反例。**教学价值是"展示尝试 + 失败"的过程**,不是反例本身。

### 8.1 完整诊断 demo

把今天的概念做成完整可跑 demo:Y/Z 分离 sort + 失败诊断。

```rust
use std::cmp::Ordering;

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug)]
struct Aabb { x: f32, y: f32, w: f32, h: f32 }
impl Aabb {
    fn from_center(p: Vec2, w: f32, h: f32) -> Self {
        Self { x: p.x - w/2.0, y: p.y - h/2.0, w, h }
    }
    fn bottom(&self) -> f32 { self.y + self.h }
    fn overlaps(&self, o: &Self) -> bool {
        self.x < o.x + o.w && self.x + self.w > o.x
            && self.y < o.y + o.h && self.y + self.h > o.y
    }
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec2,
    z: u8,
    bounds: Aabb,
    name: &'static str,
}

fn y_z_separate_sort(entities: &mut [Entity]) {
    entities.sort_by(|a, b| {
        a.z.cmp(&b.z)
            .then(a.bounds.bottom()
                .partial_cmp(&b.bounds.bottom())
                .unwrap_or(Ordering::Equal))
    });
}

/// 诊断 Y/Z 独立性:返回所有"Y 重叠但 Z 不同"的 sprite 对
fn diagnose_coupling(entities: &[Entity]) -> Vec<(usize, usize)> {
    let mut coupled = vec![];
    for i in 0..entities.len() {
        for j in (i+1)..entities.len() {
            let (a, b) = (&entities[i], &entities[j]);
            if a.bounds.overlaps(&b.bounds) && a.z != b.z {
                coupled.push((i, j));
            }
        }
    }
    coupled
}

fn main() {
    let entities = vec![
        Entity {
            pos: Vec2::new(100.0, 100.0),
            z: 1,
            bounds: Aabb::from_center(Vec2::new(100.0, 100.0), 200.0, 32.0),
            name: "Bridge",
        },
        Entity {
            pos: Vec2::new(100.0, 140.0),
            z: 0,
            bounds: Aabb::from_center(Vec2::new(100.0, 140.0), 300.0, 64.0),
            name: "Water",
        },
        Entity {
            pos: Vec2::new(100.0, 130.0),
            z: 2,
            bounds: Aabb::from_center(Vec2::new(100.0, 130.0), 32.0, 80.0),
            name: "Player",
        },
    ];

    let mut sorted = entities.clone();
    y_z_separate_sort(&mut sorted);

    println!("=== Y/Z Separate Sort Result ===");
    for (i, e) in sorted.iter().enumerate() {
        println!("  #{}: {} z={} bottom={:.0}",
            i, e.name, e.z, e.bounds.bottom());
    }

    let coupled = diagnose_coupling(&entities);
    println!("\n=== Coupling Diagnosis ===");
    println!("Found {} potentially coupled pairs:", coupled.len());
    for (i, j) in &coupled {
        println!("  {} (z={}) ↔ {} (z={}) — different Z but bounds overlap",
            entities[*i].name, entities[*i].z,
            entities[*j].name, entities[*j].z);
    }
    if !coupled.is_empty() {
        println!("\nWarning: Y/Z coupling detected. Separate sort may give wrong results.");
        println!("Consider topological sort (day 304).");
    }
}
```
