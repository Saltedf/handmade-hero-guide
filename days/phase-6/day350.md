# Day 350 · 多线程世界模拟

> 前 349 天 HH 全是单线程。今天 Casey 跨入多线程:让游戏 update 在多个 CPU 核心上并行跑。这是 HH 的转折点——从"用满 1 个核心"到"用满 N 个核心"。Rust 的所有权和 Send/Sync 让多线程不再可怕。

## 0 · 为什么要有这一天

你的 CPU 不是 1 个核心,是 8 个、16 个、32 个。但单线程游戏只用 1 个——剩下 7 个闲着。CPU 利用率 12.5%,7/8 的算力浪费。

为什么 HH 前 349 天不用多线程?

1. **复杂**:多线程引入数据竞争、死锁、竞态,debug 难度爆炸
2. **不确定**:同一代码两次运行结果可能不同
3. **教学顺序**:Casey 先把单线程逻辑写干净,再考虑并行

但到了 Day 350,游戏复杂度足够(多 sim region、大量 entity、复杂物理),单线程 60 FPS 撑不住。必须并行。

**多线程并行的核心问题**:**数据竞争**(data race)。

```
Thread A: world.entities[5].pos.x += 1
Thread B: world.entities[5].pos.x += 1
```

两个线程同时 +1,可能结果只 +1(丢失更新)。或者更糟:一个线程读到半修改状态(pos.x 改了,pos.y 没改)。

业界三种解决方案:

**方案 1:锁(Mutex)**

每个共享数据加锁。简单,但锁粒度大就退化成串行,粒度小就死锁。

**方案 2:消息传递(channel)**

线程不共享数据,通过消息通信。Actor model。Rust 的 `mpsc::channel` 实现这个。

**方案 3:数据并行(rayon / ECS)**

把数据分片,每个线程处理一片,无共享。Rust 的 `rayon` 库做这个。

Casey Day 350 用方案 3 + 一点方案 1:每个 sim region 在独立线程跑,共享数据用锁保护。Day 351 优化。

**Rust 的优势**:`Send` / `Sync` trait 编译期消除数据竞争。`unsafe` 才能绕过。Casey 在 C 里全靠自己小心,Rust 翻译编译器强制安全。

心理锚点:今天之后你能解释 `Send` / `Sync` / `Mutex` / `Arc`,能写简单的多线程游戏代码,理解"为什么 Rust 是多线程友好语言"。

## 2 · 心智模型

### 类比:多人协作厨房

单线程厨房(1 个厨师):所有事顺序做——切菜、炒菜、上盘。简单,慢。

多线程厨房(8 个厨师):怎么协作?

- **乱来**(数据竞争):8 个人抢同一把刀,撞在一起
- **锁**(mutex):刀只有 1 把,排队用,实际等于单线程
- **任务分发**(rayon):每人分到独立的菜,各切各的
- **消息传递**(actor):有专门"切菜"和"炒菜"的人,通过传送带通信

游戏多线程:**每个 sim region 是独立任务**,worker 拉取执行。任务之间共享的只有"global world state"(用锁或快照)。

### 线程 vs 进程

- **进程**:独立地址空间,严格隔离(Linux fork / exec)
- **线程**:共享地址空间,需要同步(Linux pthread / Rust std::thread)
- **协程**:用户态"轻量线程",单线程内多任务(tokio / async)

游戏开发:**多线程**为主(共享大世界状态),协程辅助(网络 IO),多进程极少(子进程做 asset 编译)。

### Rust 的 Send / Sync

Rust 编译期检查多线程安全:

- `Send`:类型可以**在线程间转移所有权**(`T` 从 thread A move 到 thread B 安全)
- `Sync`:类型可以**被多线程共享引用**(`&T` 给多线程安全)

大部分类型自动 `Send + Sync`(没有内部可变性 + 没有裸指针)。

不安全的:

- `Rc<T>`:非原子引用计数,多线程会错(`!Send`)
- `Cell<T>` / `RefCell<T>`:非同步内部可变(`!Sync`)
- 裸指针 `*mut T` / `*const T`:`!Send + !Sync`

安全的替代:

- `Arc<T>`:原子 `Rc`,线程安全
- `Mutex<T>` / `RwLock<T>`:同步内部可变
- `AtomicU32` 等:原子原语

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..8 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut num = counter.lock().unwrap();
        *num += 1;
    }));
}

for h in handles { h.join().unwrap(); }
println!("Counter = {}", *counter.lock().unwrap());  // 8
```

**关键**:`Arc<Mutex<T>>` 是 Rust 多线程可变共享的标配。

### Rayon:数据并行

`rayon` crate 让并行循环超简单:

```toml
rayon = "1.8"
```

```rust
use rayon::prelude::*;

let v: Vec<i32> = (0..1000).collect();
let sum: i32 = v.par_iter().map(|&x| x * 2).sum();
// 自动分给 N 个线程
```

`par_iter()` 替代 `iter()`,rayon 自动并行。底层是 work-stealing 线程池(每个 worker 有本地队列,闲了从别人队列偷)。

游戏开发可以用 rayon 给 sim region 并行:

```rust
regions.par_iter_mut().for_each(|r| {
    r.update(dt);
});
```

每个 region 在独立线程(实际是 rayon worker)更新。

Casey 在 HH 手写线程池(教学目的)。Rust 翻译可以用 rayon 直接简化。差别:

### 多线程的"游戏循环"

```
主线程:
  while running {
    input = read_input()
    tasks = build_tasks(input, dt)
    queue.push_all(tasks)
    wait_all_done()
    render()
    present()
  }

Worker 线程(N 个):
  loop {
    task = queue.pop()
    task.execute()
    mark_done()
  }
```

主线程提交任务、等结果、渲染。worker 跑任务。

**关键同步**:

1. 任务队列:`Mutex<VecDeque<Task>>` 或 lock-free queue
2. 等待完成:`Condvar` 或 `Barrier` 或 rayon 的隐式同步
3. 结果收集:`Arc<Mutex<Results>>` 或 rayon 的 `collect`

### 死锁与活锁

**死锁**(deadlock):两个线程互相等锁。

```
Thread A: lock(M1), then try lock(M2)  // 等 M2
Thread B: lock(M2), then try lock(M1)  // 等 M1
```

防御:**锁顺序固定**(所有线程按相同顺序锁多个 mutex)。

**活锁**(livelock):线程反复响应对方,没进度。

```
走廊里两人互相让路,同时左移,同时右移...
```

防御:随机退避(backoff)。

Rust 不消除死锁——`Mutex` 是运行时检查。但 `parking_lot::Mutex` 比标准库更快更安全。

### 数据并行的最佳实践

游戏多线程最优模式:**按空间分片**(spatial sharding)。

```
World 切成 4 个 spatial 区域:
+----+----+
| R1 | R2 |
+----+----+
| R3 | R4 |
+----+----+

每个 worker 处理一个区域。
边界 entity 可能跨区域 —— 单独"边界 pass"串行处理。
```

这种"map-reduce" 模式:并行处理内部,串行处理边界。Casey Day 351 会优化这种。

## 5 · 对照与变奏

### 同步 vs 异步 vs 并行

- **同步**(sync):调用者等结果(`a(); b();` 顺序)
- **异步**(async):调用者不等,以后查结果(`a().await` 协作调度)
- **并行**(parallel):多任务同时执行(`a` 在 thread 1,`b` 在 thread 2)

游戏开发:**并行**用于计算密集(update / 物理),**异步**用于 IO(网络 / 文件)。

### Lv1 · 概念辨析

**题**:`Rc<T>` 和 `Arc<T>` 区别?为什么前者不能跨线程?

**参考解答**:

- **`Rc<T>`**(Reference Counted):非原子引用计数。每次 `clone()` 时 `count += 1`,但这个 += 不是原子操作。
- **`Arc<T>`**(Atomically Reference Counted):原子引用计数,用原子指令 `fetch_add` 改 count。

`Rc` 不能跨线程的原因:两个线程同时 `clone()`,各自读 count(假设都是 1),各自 +1(都是 2),各自写回(都是 2),但应该是 3——**丢失更新**。最终 `Rc` 析构时 count 没归零,内存泄漏;或归零过早,UAF。

`Arc` 用原子指令避免这个问题:`fetch_add(1)` 是一条指令,CPU 保证不被打断。

性能代价:`Arc` 的 clone 比 `Rc` 慢约 10 倍(原子指令比普通加法慢)。所以单线程用 `Rc`,多线程用 `Arc`。

### Lv2 · 动手实践

**题**:用 rayon 并行更新 4 个 sim region,验证总耗时 < 单线程。

完成标准:并行版本比单线程快至少 1.5x。

**参考解答**:

```rust
// Cargo.toml:
// [dependencies]
// rayon = "1.8"

use rayon::prelude::*;
use std::time::Instant;

const N_REGIONS: usize = 4;
const ENTITIES_PER_REGION: usize = 100_000;

#[derive(Copy, Clone)]
struct Entity {
    pos: [f32; 2],
    vel: [f32; 2],
}

struct SimRegion {
    entities: Vec<Entity>,
}

impl SimRegion {
    fn new() -> Self {
        let entities = (0..ENTITIES_PER_REGION).map(|_| Entity {
            pos: [0.0, 0.0],
            vel: [1.0, 1.0],
        }).collect();
        Self { entities }
    }

    fn update(&mut self, dt: f32) {
        for e in &mut self.entities {
            e.pos[0] += e.vel[0] * dt;
            e.pos[1] += e.vel[1] * dt;
        }
    }
}

fn main() {
    let mut regions: Vec<SimRegion> = (0..N_REGIONS).map(|_| SimRegion::new()).collect();
    let iters = 100;
    let dt = 0.016;

    // 单线程
    let mut seq_regions = regions.clone();
    let t = Instant::now();
    for _ in 0..iters {
        for r in &mut seq_regions {
            r.update(dt);
        }
    }
    let seq_ms = t.elapsed().as_millis();

    // 并行(rayon)
    let t = Instant::now();
    for _ in 0..iters {
        regions.par_iter_mut().for_each(|r| r.update(dt));
    }
    let par_ms = t.elapsed().as_millis();

    println!("Sequential: {} ms", seq_ms);
    println!("Parallel:   {} ms (rayon)", par_ms);
    println!("Speedup:    {:.2}x", seq_ms as f64 / par_ms.max(1) as f64);
}
```

**关键解释**:
- `regions.clone()`:深拷贝,保证两个版本初始状态相同
- `par_iter_mut()`:并行可变迭代
- rayon 自动用所有 CPU 核心

**预期输出**(8 核机器):
```
Sequential: 800 ms
Parallel:   220 ms (rayon)
Speedup:    3.6x
```

不是 4x 因为有调度开销和 cache miss。

## 8 · Rust / Arch 落地代码

### 完整可跑示例:线程池 + 共享状态

```rust
use std::sync::{Arc, Mutex};
use std::sync::atomic::{AtomicU32, Ordering};
use std::thread;
use std::time::{Duration, Instant};

// 共享计数器(原子)
struct Counter {
    value: AtomicU32,
}

impl Counter {
    fn new() -> Self { Self { value: AtomicU32::new(0) } }
    fn inc(&self) { self.value.fetch_add(1, Ordering::SeqCst); }
    fn get(&self) -> u32 { self.value.load(Ordering::SeqCst) }
}

// 共享 vector(Mutex 保护)
struct SharedVec {
    data: Mutex<Vec<u32>>,
}

impl SharedVec {
    fn new() -> Self { Self { data: Mutex::new(vec![]) } }
    fn push(&self, x: u32) {
        self.data.lock().unwrap().push(x);
    }
    fn len(&self) -> usize {
        self.data.lock().unwrap().len()
    }
}

fn main() {
    let n_workers = 4;
    let counter = Arc::new(Counter::new());
    let vec = Arc::new(SharedVec::new());

    let start = Instant::now();

    let handles: Vec<_> = (0..n_workers).map(|worker_id| {
        let counter = Arc::clone(&counter);
        let vec = Arc::clone(&vec);
        thread::spawn(move || {
            for i in 0..1000 {
                counter.inc();
                vec.push(worker_id * 1000 + i);
            }
            worker_id  // 返回 worker_id
        })
    }).collect();

    // 等所有 worker 完成
    for h in handles {
        let id = h.join().unwrap();
        println!("Worker {} done", id);
    }

    let elapsed = start.elapsed();

    println!("\nResults:");
    println!("  Counter = {} (expected {})", counter.get(), n_workers * 1000);
    println!("  Vec len = {} (expected {})", vec.len(), n_workers * 1000);
    println!("  Time = {:?}", elapsed);

    // 验证
    assert_eq!(counter.get(), n_workers as u32 * 1000);
    assert_eq!(vec.len(), n_workers * 1000);
    println!("\nAll assertions passed!");
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
