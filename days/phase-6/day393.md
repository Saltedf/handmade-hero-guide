
# Day 393 · 从深度剥离规划光照

> Day 392 把深度剥离扩展为 G-buffer。今天 Casey **规划**:如何用这些 G-buffer 数据驱动多网格光照传播?具体是把 G-buffer(屏幕空间)和体素网格(世界空间)连接起来——**体素化**(voxelization)。这是 Day 394-395 多网格传播的前置准备。

## 0 · 为什么要有这一天

G-buffer 在**屏幕空间**(每像素一份),多网格光照传播在**世界空间**(每体素一份)。两个空间要**桥接**——把屏幕像素的几何信息"贡献"到对应的体素。

**桥接的核心问题**:

1. **屏幕到体素的映射**:每像素的 position 属于哪个体素?
2. **多像素到一个体素**:多个像素可能映射到同一体素(像素密集时),如何处理?
3. **一个像素到多体素**:大三角形覆盖多体素,如何在每体素记录?
4. **半透明多层**:深度剥离有 K 层,每层都要体素化
5. **体素属性聚合**:多个像素贡献同一体素,如何聚合 albedo / normal?

**Casey 的方案**:

1. **像素到体素**:用 `floor(position / voxel_size)` 算体素索引
2. **聚合策略**:取**第一个**贡献的像素(简化,不做平均),或**平均**(更准确)
3. **多层处理**:每层独立体素化,体素存"最近层"的数据
4. **属性聚合**:albedo 取平均,normal 取面积加权平均

**今天的产出**:G-buffer 数据被"投影"到 3D 体素网格。后续光照传播在这个体素网格上做。这一步是从"渲染空间"到"算法空间"的转换。

心理锚点:看完今天,你能(1)解释屏幕空间和世界空间的差别;(2)实现 pixel-to-voxel 的映射;(3)处理多像素到一体素的聚合;(4)理解为什么 GI 算法用体素化作为前置。

Casey 流程:

## 2 · 心智模型

### 类比:选举计票

想象选举——1000 万张选票(屏幕像素),每个选票属于某个选区(体素)。你要**统计每个选区的结果**:

- 每张选票根据地址(position)分类到选区(voxel_idx)
- 同一选区的多张选票聚合(求和 / 平均)
- 最终得到每选区的统计(体素属性)

GPU 上的体素化就是这种"分类 + 聚合"。挑战:**多张选票同时到同一选区**(并发写),需要原子操作保证不丢数据。

### 严谨原理:像素到体素的映射

给定像素的 world position `p`,计算所属体素索引:

```rust
fn position_to_voxel(p: Vec3, grid_min: Vec3, voxel_size: f32) -> (usize, usize, usize) {
    let relative = (p - grid_min) / voxel_size;
    let i = relative.x.floor() as usize;
    let j = relative.y.floor() as usize;
    let k = relative.z.floor() as usize;
    (i, j, k)
}
```

**注意**:

- `floor` 保证负数也正确(`-0.5 → -1`)
- `as usize` 截断(负数变成 huge usize,需要 clamp)
- voxel_size 必须 > 0(否则除零)

**边界处理**:像素的 position 可能在网格外,clamp 到边界或丢弃。

### 体素网格的数据结构

```rust
pub struct VoxelGrid {
    pub dimensions: (u32, u32, u32),  // 例如 (64, 64, 64)
    pub voxel_size: f32,
    pub origin: Vec3,  // 网格最小点的世界坐标
    pub voxels: Vec<Voxel>,  // 长度 = dimensions.0 * 1 * 2
}

#[derive(Copy, Clone, Default)]
pub struct Voxel {
    pub albedo: [f32; 3],
    pub normal: [f32; 3],
    pub emission: [f32; 3],
    pub incident_light: [f32; 3],  // 多网格传播用
    pub coverage: f32,  // 多少像素贡献了此体素
}

impl VoxelGrid {
    pub fn voxel_index(&self, i: u32, j: u32, k: u32) -> usize {
        (k * self.dimensions.0 * self.dimensions.1 + j * self.dimensions.0 + i) as usize
    }

    pub fn voxel_at(&self, i: u32, j: u32, k: u32) -> &Voxel {
        &self.voxels[self.voxel_index(i, j, k)]
    }

    pub fn voxel_at_mut(&mut self, i: u32, j: u32, k: u32) -> &mut Voxel {
        &mut self.voxels[self.voxel_index(i, j, k)]
    }
}
```

**64³ 体素 = 262144 cells**,每 cell ~64 字节 = 16 MB。可接受。

### 体素化的并发问题

GPU 上多 fragment 同时写同一体素会**冲突**(race condition)。例如,屏幕上两个相邻像素都属于体素 (10, 20, 30),它们都想写 albedo。

**解法**:

1. **Atomic add**(GPU 原子加):用 `GL_R32UI` 纹理(image2D / image3D),`atomicAdd` 累加。
2. **Per-pixel first**(简化):只接受第一个像素的写,后续丢弃(可能用 z-test 实现)。
3. **Two-pass**:pass 1 算每体素的像素数;pass 2 累加并除以数量。

Casey 选 1(atomic add),因为正确性最高。代价:atomic 慢,但稀疏写入场景影响小。

GLSL 实现(用 image3D):

```glsl
#version 430
#extension GL_ARB_shader_image_load_store : require

layout(binding = 0, rgba32f) uniform image3D voxel_albedo;
layout(binding = 1, rgba32f) uniform image3D voxel_normal;

uniform vec3 grid_min;
uniform float voxel_size;
uniform ivec3 grid_dims;

in vec3 v_world_position;
in vec3 v_world_normal;

void main() {
    vec3 relative = (v_world_position - grid_min) / voxel_size;
    ivec3 idx = ivec3(floor(relative));
    if (any(lessThan(idx, ivec3(0))) || any(greaterThanEqual(idx, grid_dims))) {
        return;  // 越界,跳过
    }
    // 累加(原子操作)
    vec4 albedo = vec4(v_albedo_color, 1.0);  // alpha=1 用于计数
    imageAtomicAdd(voxel_albedo, idx, albedo);
    // 后面 normalize 时除以 alpha
}
```

但 `imageAtomicAdd` 对 float 纹理不支持(OpenGL 4.2 只支持 int / uint 原子)。需要**编码 float 为 uint**:

```glsl
// float → uint 编码(pack)
uint pack_float_to_uint(float f) {
    return floatBitsToUint(f);
}

// 累加 uint(实际上要 reinterpret float bits,复杂)
```

**实际**:用 `GL_R32UI` 纹理存 uint,通过 shared atomic 加 floatBitsToUint / uintBitsToFloat 编码。这种 hack 复杂,生产代码用 **SSBO**(Shader Storage Buffer Object)代替:

```glsl
layout(std430, binding = 0) buffer VoxelBuffer {
    vec4 voxel_data[];  // 平铺存储
};

void main() {
    // ...
    uint idx = i + j * dims.x + k * dims.x * dims.y;
    // 用 atomicAdd(对 uint)/ 实际用 SSBO 不支持原子 float,需要 lock-free 算法
    voxel_data[idx] += vec4(albedo, 1.0);  // 不安全!race condition
}
```

**简化方案**(Casey 用):**单线程 CPU 体素化**——读 G-buffer 回 CPU,Rust 端顺序处理,无并发。代价是慢(800 万像素的回读要几毫秒),但**正确性保证**。后续优化才搬到 GPU。

### 多层处理

深度剥离有 K 层,每层都要体素化。**简化**:每体素只存"最近层"的数据(用 z-test 决定)。多层物体(玻璃前面 + 后面)只记录前面。

**精确版本**:每体素存 K 个 layer 数据(类似 K-buffer)。但显存翻 K 倍,Casey 不做。

### 体素化的几何覆盖

一个**大三角形**覆盖多个体素(三角形面积 >> 体素大小)。G-buffer 只存三角形表面的几个像素,这些像素都属于一个面,但物理上**三角形覆盖多个体素**。

**正确体素化**应该"扫过"三角形覆盖的所有体素,而非只记录像素位置的体素。这叫 **voxelization with conservative rasterization**——三角形的"保守光栅化"。

工业界做法:

- **Conservative rasterization**(OpenGL 4.2+):光栅化时考虑三角形"覆盖"的所有像素(不只是中心)
- **Slice-by-slice voxelization**:在三角形所在平面逐层扫,每层做 2D 光栅化

Casey 用**简化版**——只体素化 G-buffer 像素,不考虑三角形覆盖。代价:大三角形可能"漏"体素(覆盖区域中心没有像素),但实际游戏场景物体小,影响小。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业界体素化:

- **Sparse Voxel Octree**(SVO):稀疏体素八叉树,只存非空体素。CryEngine 用过。
- **3D texture mip-mapped**:clipmap 体素,只加载玩家附近的体素。
- **Voxel cone tracing**(VXGI):NVIDIA 的方案,cone tracing 算 GI。

体素化是**离线 / 实时**的折衷:

- 离线:预计算,质量高,场景不变
- 实时:每帧重算,支持动态场景,质量稍低

Casey 选**实时体素化**(场景可变),代价是分辨率有限。

### 3.2 · 🎨 图形学视角

**Voxelization 的算法分类**:

- **Surface voxelization**:只体素化表面(三角形面)
- **Solid voxelization**:体素化整个体积(内部填满)
- **Conservative**:保证覆盖三角形的所有体素
- **Non-conservative**:只取三角形中心位置

GI 用 surface voxelization(光只和表面交互,不需要内部)。

**Sparse vs Dense**:

- Dense:固定分辨率,所有体素都存
- Sparse:八叉树 / hash grid,只存非空

Casey 用 dense(简单),64³ = 262k cells,可接受。

### 3.4 · 🦀 Rust 生态视角

Rust 端 CPU 体素化:

```rust
use glam::Vec3;

pub fn voxelize_gbuffer(
    gbuffer_position: &[Vec3],
    gbuffer_normal: &[Vec3],
    gbuffer_albedo: &[Vec3],
    grid: &mut VoxelGrid,
) {
    // 重置 coverage
    for v in &mut grid.voxels {
        v.coverage = 0.0;
        v.albedo = [0.0; 3];
        v.normal = [0.0; 3];
    }

    // 遍历 G-buffer
    for i in 0..gbuffer_position.len() {
        let pos = gbuffer_position[i];
        let nrm = gbuffer_normal[i];
        let alb = gbuffer_albedo[i];

        // 计算体素索引
        let relative = (pos - grid.origin) / grid.voxel_size;
        if relative.x < 0.0 || relative.y < 0.0 || relative.z < 0.0 { continue; }
        let idx = (
            relative.x as u32,
            relative.y as u32,
            relative.z as u32,
        );
        if idx.0 >= grid.dimensions.0
            || idx.1 >= grid.dimensions.1
            || idx.2 >= grid.dimensions.2 { continue; }

        // 累加
        let voxel = grid.voxel_at_mut(idx.0, idx.1, idx.2);
        voxel.albedo[0] += alb.x;
        voxel.albedo[1] += alb.y;
        voxel.albedo[2] += alb.z;
        voxel.normal[0] += nrm.x;
        voxel.normal[1] += nrm.y;
        voxel.normal[2] += nrm.z;
        voxel.coverage += 1.0;
    }

    // 归一化(除以 coverage)
    for v in &mut grid.voxels {
        if v.coverage > 0.0 {
            let inv = 1.0 / v.coverage;
            v.albedo[0] *= inv;
            v.albedo[1] *= inv;
            v.albedo[2] *= inv;
            let n = Vec3::new(v.normal[0], v.normal[1], v.normal[2]);
            let n = n.normalize_or_zero();
            v.normal[0] = n.x;
            v.normal[1] = n.y;
            v.normal[2] = n.z;
        }
    }
}
```

**关键**:

- 累加 albedo 和 normal,最后除以 coverage 归一化
- normal 归一化(因为累加后长度变化)
- `normalize_or_zero` 处理零向量(不贡献的体素)

**SIMD 优化**:用 `std::arch::x86_64::_mm_*` 处理 Vec3 操作,4 个像素并行。

## 4 · 认知地图

### 4.1 上级

- **体素化**(Voxelization)— 把连续几何转离散体素
- **空间离散化**(Spatial Discretization)— 一类算法,把世界切格子
- **G-buffer → 算法空间桥接** — 渲染空间到计算空间的转换

### 4.2 同级

| 空间离散 | 适合 | 显存 |
|---|---|---|
| 3D 网格(Dense) | 小场景,简单 | 高(全空也存) |
| 八叉树 | 大场景,稀疏 | 低 |
| Hash grid | 动态场景 | 低 |
| Clipmap | 大场景,玩家附近 | 中 |
| BVH | 一般加速结构 | 低 |

### 4.3 下级

- **Voxel** — 单个体素,存属性
- **Position-to-voxel mapping** — 像素 / 顶点到体素的索引计算
- **Coverage** — 多像素聚合时记录贡献数
- **Atomic add** — GPU 并发原子操作
- **Conservative rasterization** — 三角形覆盖所有体素

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么体素化时要"coverage"字段,不能直接累加?

**参考解答**:

直接累加的问题:**多个像素贡献同一体素时**,albedo 累加结果会"过亮"。例如 3 个像素都贡献 albedo = (0.5, 0.3, 0.2),累加得到 (1.5, 0.9, 0.6),过曝。

正确做法:**累加 + 计数**,最后除以计数得到**平均** albedo。`coverage` 字段记录有多少像素贡献,用于归一化。

更精确的版本:**加权平均**(按像素覆盖面积 / 角度加权),但简单 coverage 已经够用。

### Lv2 · 动手实践

**题**:在 Rust 里实现一个最小化 CPU 体素化。给定:

- G-buffer position 数组(Vec3 列表)
- 32³ 体素网格,voxel_size = 0.1,origin = (-1.6, -1.6, -1.6)

完成体素化,打印非空体素的 albedo 平均值。

**参考解答**:

```rust
use glam::Vec3;

#[derive(Copy, Clone, Default)]
struct Voxel {
    albedo_sum: [f32; 3],
    coverage: u32,
}

struct VoxelGrid {
    dims: u32,
    voxel_size: f32,
    origin: Vec3,
    voxels: Vec<Voxel>,
}

impl VoxelGrid {
    fn new(dims: u32, voxel_size: f32, origin: Vec3) -> Self {
        Self {
            dims,
            voxel_size,
            origin,
            voxels: vec![Voxel::default(); (dims as usize).pow(3)],
        }
    }

    fn idx(&self, x: u32, y: u32, z: u32) -> usize {
        (z as usize) * (self.dims as usize).pow(2)
            + (y as usize) * (self.dims as usize)
            + x as usize
    }
}

fn voxelize(grid: &mut VoxelGrid, positions: &[Vec3], albedos: &[Vec3]) {
    for (p, a) in positions.iter().zip(albedos.iter()) {
        let rel = (*p - grid.origin) / grid.voxel_size;
        if rel.x < 0.0 || rel.y < 0.0 || rel.z < 0.0 { continue; }
        let x = rel.x as u32;
        let y = rel.y as u32;
        let z = rel.z as u32;
        if x >= grid.dims || y >= grid.dims || z >= grid.dims { continue; }
        let v = &mut grid.voxels[grid.idx(x, y, z)];
        v.albedo_sum[0] += a.x;
        v.albedo_sum[1] += a.y;
        v.albedo_sum[2] += a.z;
        v.coverage += 1;
    }
}

fn main() {
    let mut grid = VoxelGrid::new(32, 0.1, Vec3::new(-1.6, -1.6, -1.6));

    // 模拟 G-buffer:几个像素 position 和 albedo
    let positions = vec![
        Vec3::new(0.0, 0.0, 0.0),
        Vec3::new(0.05, 0.05, 0.05),
        Vec3::new(0.1, 0.1, 0.1),
        Vec3::new(1.0, 1.0, 1.0),
    ];
    let albedos = vec![
        Vec3::new(1.0, 0.0, 0.0),
        Vec3::new(0.8, 0.0, 0.0),
        Vec3::new(0.6, 0.0, 0.0),
        Vec3::new(0.0, 1.0, 0.0),
    ];

    voxelize(&mut grid, &positions, &albedos);

    // 打印非空体素
    let mut count = 0;
    for (i, v) in grid.voxels.iter().enumerate() {
        if v.coverage > 0 {
            let avg = [
                v.albedo_sum[0] / v.coverage as f32,
                v.albedo_sum[1] / v.coverage as f32,
                v.albedo_sum[2] / v.coverage as f32,
            ];
            let z = i / (32 * 32);
            let y = (i / 32) % 32;
            let x = i % 32;
            println!("Voxel ({}, {}, {}): coverage={}, avg albedo=({:.2}, {:.2}, {:.2})",
                x, y, z, v.coverage, avg[0], avg[1], avg[2]);
            count += 1;
        }
    }
    println!("Total non-empty voxels: {}", count);
}
```

**预期输出**:

- 像素 (0, 0, 0) 和 (0.05, 0.05, 0.05) 都在体素 (16, 16, 16),coverage=2
- 像素 (0.1, 0.1, 0.1) 在体素 (17, 17, 17),coverage=1
- 像素 (1.0, 1.0, 1.0) 在体素 (26, 26, 26),coverage=1

```rust
// src/main.rs
use glam::Vec3;
use std::time::Instant;

#[derive(Copy, Clone, Default)]
pub struct Voxel {
    pub albedo_sum: [f32; 3],
    pub normal_sum: [f32; 3],
    pub coverage: u32,
}

pub struct VoxelGrid {
    pub dims: (u32, u32, u32),
    pub voxel_size: f32,
    pub origin: Vec3,
    pub voxels: Vec<Voxel>,
}

impl VoxelGrid {
    pub fn new(dims: (u32, u32, u32), voxel_size: f32, origin: Vec3) -> Self {
        let total = (dims.0 * dims.1 * dims.2) as usize;
        Self {
            dims,
            voxel_size,
            origin,
            voxels: vec![Voxel::default(); total],
        }
    }

    pub fn voxel_index(&self, x: u32, y: u32, z: u32) -> usize {
        (z as usize) * (self.dims.0 * self.dims.1) as usize
            + (y as usize) * self.dims.0 as usize
            + x as usize
    }

    pub fn voxel_at_mut(&mut self, x: u32, y: u32, z: u32) -> &mut Voxel {
        &mut self.voxels[self.voxel_index(x, y, z)]
    }
}

pub fn voxelize(
    grid: &mut VoxelGrid,
    positions: &[Vec3],
    normals: &[Vec3],
    albedos: &[Vec3],
) {
    let start = Instant::now();

    for i in 0..positions.len() {
        let p = positions[i];
        let rel = (p - grid.origin) / grid.voxel_size;
        if rel.x < 0.0 || rel.y < 0.0 || rel.z < 0.0 { continue; }
        let x = rel.x as u32;
        let y = rel.y as u32;
        let z = rel.z as u32;
        if x >= grid.dims.0 || y >= grid.dims.1 || z >= grid.dims.2 { continue; }
        let voxel = grid.voxel_at_mut(x, y, z);
        voxel.albedo_sum[0] += albedos[i].x;
        voxel.albedo_sum[1] += albedos[i].y;
        voxel.albedo_sum[2] += albedos[i].z;
        voxel.normal_sum[0] += normals[i].x;
        voxel.normal_sum[1] += normals[i].y;
        voxel.normal_sum[2] += normals[i].z;
        voxel.coverage += 1;
    }

    let elapsed = start.elapsed();
    println!("Voxelized {} positions in {:?}", positions.len(), elapsed);
}

/// 归一化所有体素(coverage > 0 的除以 coverage,normal 重新归一化)
pub fn normalize_voxels(grid: &mut VoxelGrid) {
    for v in &mut grid.voxels {
        if v.coverage > 0 {
            let inv = 1.0 / v.coverage as f32;
            v.albedo_sum[0] *= inv;
            v.albedo_sum[1] *= inv;
            v.albedo_sum[2] *= inv;
            let n = Vec3::new(v.normal_sum[0], v.normal_sum[1], v.normal_sum[2]);
            let n = n.normalize_or_zero();
            v.normal_sum[0] = n.x;
            v.normal_sum[1] = n.y;
            v.normal_sum[2] = n.z;
        }
    }
}

/// 生成球面随机点(测试用)
fn random_sphere_points(n: usize) -> Vec<Vec3> {
    use std::f32::consts::PI;
    (0..n).map(|i| {
        let theta = (i as f32 / n as f32) * PI;
        let phi = (i as f32 * 0.618 * 2.0 * PI) % (2.0 * PI);
        Vec3::new(
            theta.sin() * phi.cos(),
            theta.cos(),
            theta.sin() * phi.sin(),
        )
    }).collect()
}

fn main() {
    let mut grid = VoxelGrid::new((64, 64, 64), 0.05, Vec3::new(-1.6, -1.6, -1.6));

    // 模拟球面上的 G-buffer
    let positions = random_sphere_points(10000);
    let normals: Vec<Vec3> = positions.iter().map(|p| p.normalize()).collect();
    let albedos: Vec<Vec3> = positions.iter().enumerate().map(|(i, _)| {
        Vec3::new(
            (i as f32 / 10000.0).sin().abs(),
            0.3,
            0.5,
        )
    }).collect();

    voxelize(&mut grid, &positions, &normals, &albedos);
    normalize_voxels(&mut grid);

    let non_empty = grid.voxels.iter().filter(|v| v.coverage > 0).count();
    println!("Non-empty voxels: {}/{}", non_empty, grid.voxels.len());
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
