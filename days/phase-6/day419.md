
# Day 419 · 调试缺失光照

> Day 418 加了时序累积后,Casey 看到一些墙面**完全黑色**——光照消失了。但他知道光源在那里,矩形覆盖了墙。今天他调试这个 bug,发现根源是时序累积的"swap 后访问错位"——他读了 history 写了 current,但渲染用了 history,导致每帧用的是旧值,新光照永远没显示出来。

## 0 · 为什么要有这一天

调试光照缺失需要**反向溯源**:

1. **现象**:墙黑(亮度 = 0)
2. **位置**:哪里黑?(整个墙、部分墙、某些体素?)
3. **数据**:这个体素的 current/history 值是多少?
4. **来源**:值是怎么算出来的?(光照注入函数)
5. **bug 点**:注入函数正确吗?注入到了哪里?swap 后访问对了吗?

每一步都需要**验证**——你不能假设任何一步是对的,必须打印中间值。Day 417 的 debug draw 工具今天派上用场:它能可视化"采样点在哪""光线打到哪"。

工业的"光照缺失"调试方法:

- **截屏对比**:正常帧 vs 异常帧,看亮度差
- **debug draw**:画采样点和光线
- **值打印**:`println!("voxel[{}]={:?}", idx, voxel.value)`
- **二分法**:关掉一半代码,看 bug 在不在,逐步缩小范围

Casey 今天用前三种方法。具体发现:他在 `update` 函数里写了 `swap(history, current)`,然后在渲染里**仍然读 history**——以为 history 是"刚算的当前值"。但 swap 后,history 是"过去的当前",刚算的值到了 current!所以渲染的是过时数据。

这是一个**典型的 swap 时机 bug**。Rust 的 ownership 让这种 bug 比较容易发现——`swap` 之后,两个变量名"对调",你必须明确知道哪个是哪个。但 Casey 在写时没仔细想,踩了坑。

心理锚点:今天之后,你能用 debug draw + 值打印定位"光照缺失"的根源,能识别"双缓冲 swap 后访问错位"的 bug 模式,知道**调试图形学问题的标准流程**:现象 → 数据 → 来源 → bug。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑游戏,看到一些墙黑了。他的调试步骤:

1. **截屏**记录现象,标出黑色区域
2. **加 debug draw**:在采样点画小立方体,看是否被正确执行
3. **打印体素值**:`println!("voxel[5][5][5] current={:?} history={:?}", ...)`
4. **定位**:打印显示 current 有值,history 是 0,渲染用的是 history
5. **修复**:swap 时机错位——把 swap 移到渲染之前,或渲染时用 current 而不是 history

Casey 选第二种:**渲染用 current**。逻辑变成:

```
compute_frame(&mut current)
EMA: current = α*current + (1-α)*history
render(current)  ← 用 current 不是 history
swap(history, current)  ← 为下一帧准备
```

这样语义清晰:current 永远是"最新值",history 是"上一帧"。渲染用 current,之后才 swap。

他还发现一个**次生 bug**:首帧 history 是 0,EMA 后 `0.1 * current + 0.9 * 0 = 0.1 * current`,亮度只有真值的 10%。这导致首帧很暗,慢慢累积才正常。修复:**首帧直接复制 current 到 history**(alpha=1.0 那一帧)。

## 2 · 心智模型

### 类比:邮件归档的 inbox 和 archive

想象 Gmail 的 inbox 和 archive。Inbox 是当前未读邮件,archive 是已读归档。

正确的处理:

1. 收到新邮件 → inbox
2. 读取并标记 → inbox(已读)
3. 归档 → 移到 archive

错误的处理:

1. 收到新邮件 → inbox
2. **立刻归档**(swap)→ inbox 是空,archive 有
3. 读取 → 读 archive(过时的)

时序累积的双缓冲和这个完全同构。current = inbox(最新计算结果),history = archive(上一帧累积)。你必须**先用 current**,再 swap,不能先 swap 再用。

### 严谨原理:双缓冲的正确语义

双缓冲的目标:**同时读写不冲突**。在 GPU 上,你不能"边读边写"同一个 buffer,需要双缓冲。

但 CPU 上,**单线程读写不冲突**——你只是在改 Vec 的内容。双缓冲在单线程的目的是**保存历史**(上一帧状态),不是并发。

正确的双缓冲语义:

```
模式 A:current 永远最新
    compute(&mut current);   // 写 current
    ema(&current, &mut history);  // 用 current 更新 history
    render(&current);        // 渲染 current
    // 不 swap!current 一直是最新的

模式 B:ping-pong(交替)
    if frame % 2 == 0:
        compute(&mut buffer_a);
        render(&buffer_a);
    else:
        compute(&mut buffer_b);
        render(&buffer_b);
    // 完全对称,不需要区分 history/current
```

Casey 想用模式 B,但代码里写错了——既 swap 又用 history,导致混乱。修复后用模式 A:不 swap,直接用 current 渲染,history 只用于 EMA。

### Rust 视角:所有权和命名

Rust 的 ownership 帮助避免这种 bug。看下面两种写法:

**易错版**(Casey 原来的):

```rust
fn update(&mut self) {
    compute(&mut self.current);
    ema(&self.current, &mut self.history);
    std::mem::swap(&mut self.history, &mut self.current);
    // 现在 history 是"刚算的 current",current 是"过去的 history"
    // 容易混淆!
}

fn render(&self) {
    use_history_to_render();  // 这里的 history 到底是啥?
}
```

**清晰版**(Casey 修复后):

```rust
fn update(&mut self) {
    compute(&mut self.current);  // 写 current
    ema(&self.current, &mut self.history);  // history 跟随 current 平滑
    // 不 swap!
}

fn render(&self) {
    use_current_to_render();  // 永远用 current
}
```

清晰版的语义:**current 是最新的,history 是上一帧累积,render 用 current**。这种命名让代码自文档化。

### 调试方法论

图形学 bug 调试的标准步骤:

1. **复现**:稳定复现 bug,不能是偶发
2. **最小化**:剥离无关代码,直到只剩 bug 本身
3. **可视化**:用 debug draw 画出可疑数据
4. **二分**:用 git bisect 找到引入 bug 的提交
5. **打印**:在关键点 `println!` 中间值
6. **假设验证**:形成假设,设计实验验证

Casey 今天用了 3、5、6 三步。Day 412 的体素插值 bug 调试也是这套方法。

### 排除其他可能

调试时**不要先入为主**——"光照缺失"有多个可能原因:

1. 时序累积 swap bug(本日)
2. 体素插值映射错(day412)
3. 光照注入函数没被调用
4. 矩形覆盖区域算错
5. 渲染时用错 buffer
6. swap chain 漏

Casey 排除其他可能的方法:**逐个验证**。他在每个环节加 println,看数据流。如果某环节的输出符合预期,跳过;不符合,深入。

这种"线性排查"看似慢,实际比"猜测"快——猜测可能反复改代码,但每次改都不知道有没有改对。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 修复后用"不 swap"模式?这个模式有什么缺点?

**参考解答**:**不 swap 模式**让语义清晰:current 永远最新,history 永远是上一帧累积。命名直接反映角色,代码自文档化。

缺点:**多线程不安全**。如果 compute 和 render 在不同线程同时跑,会读写同一个 current,数据竞争。模式 B(ping-pong)可以多线程——一个线程写 buffer_a,另一个读 buffer_b,swap 时切换。

单线程游戏(HH 当前状态)不需要担心,所以不 swap 更清晰。Casey 后续如果做异步计算(day430 多线程光照),可能切到 ping-pong。

use glam::Vec3;

pub struct VoxelGrid { pub data: Vec<Vec3> }
impl VoxelGrid {
    pub fn new(n: usize) -> Self { Self { data: vec![Vec3::ZERO; n] } }
}

pub struct TemporalAccumulator {
    pub history: VoxelGrid,
    pub current: VoxelGrid,
    pub alpha: f32,
    pub bugged: bool,  // 模拟 Casey 的 bug
}

impl TemporalAccumulator {
    pub fn update_and_render(&mut self) -> Vec3 {
        // Phase 1: 算当前帧(模拟光照 = 1.0)
        for v in self.current.data.iter_mut() {
            *v = Vec3::splat(1.0);
        }
        // Phase 2: EMA
        for (cur, hist) in self.current.data.iter_mut().zip(self.history.data.iter()) {
            *cur = *cur * self.alpha + *hist * (1.0 - self.alpha);
        }

        let rendered = if self.bugged {
            // BUG: swap 后用 history(其实是上一帧的 current)
            std::mem::swap(&mut self.history, &mut self.current);
            self.history.data[0]  // 这是"过去的"值
        } else {
            // FIX: 用 current,不 swap
            let v = self.current.data[0];
            std::mem::swap(&mut self.history, &mut self.current);
            v
        };
        rendered
    }
}

fn main() {
    println!("=== Buggy version ===");
    let mut acc = TemporalAccumulator {
        history: VoxelGrid::new(1),
        current: VoxelGrid::new(1),
        alpha: 0.1,
        bugged: true,
    };
    for f in 0..5 {
        let v = acc.update_and_render();
        println!("  Frame {}: rendered = {:?}", f, v);
    }

    println!("\n=== Fixed version ===");
    let mut acc = TemporalAccumulator {
        history: VoxelGrid::new(1),
        current: VoxelGrid::new(1),
        alpha: 0.1,
        bugged: false,
    };
    for f in 0..5 {
        let v = acc.update_and_render();
        println!("  Frame {}: rendered = {:?}", f, v);
    }
}

```rust
use glam::Vec3;

#[derive(Clone)]
pub struct VoxelGrid {
    pub dims: (usize, usize, usize),
    pub data: Vec<Vec3>,
}

impl VoxelGrid {
    pub fn new(dims: (usize, usize, usize)) -> Self {
        Self { dims, data: vec![Vec3::ZERO; dims.0 * dims.1 * dims.2] }
    }
}

pub struct TemporalAccumulator {
    history: VoxelGrid,
    current: VoxelGrid,
    pub alpha: f32,
    pub frame: u32,
}

impl TemporalAccumulator {
    pub fn new(dims: (usize, usize, usize), alpha: f32) -> Self {
        Self {
            history: VoxelGrid::new(dims),
            current: VoxelGrid::new(dims),
            alpha,
            frame: 0,
        }
    }

    /// 正确版:current 永远是最新的
    pub fn update_and_get_result(&mut self) -> &VoxelGrid {
        // Phase 1: 计算当前帧光照
        let target_value = if self.frame == 0 {
            Vec3::splat(1.0)  // 首帧直接给目标值
        } else {
            Vec3::splat(1.0 + (self.frame as f32 * 0.13).sin() * 0.3)
        };
        for v in self.current.data.iter_mut() {
            *v = target_value;
        }

        // Phase 2: EMA (history 跟随 current 平滑)
        // 首帧特殊处理:alpha = 1.0(直接复制)
        let effective_alpha = if self.frame == 0 { 1.0 } else { self.alpha };
        for (cur, hist) in self.current.data.iter().zip(self.history.data.iter_mut()) {
            *hist = *cur * effective_alpha + *hist * (1.0 - effective_alpha);
        }

        self.frame += 1;
        &self.history  // 用 history,因为它已经是 EMA 后的最新累积
    }
}

fn main() {
    let mut acc = TemporalAccumulator::new((4, 4, 4), 0.1);

    println!("Frame | target | history (rendered)");
    for _ in 0..10 {
        let target = if acc.frame == 0 { 1.0 } else { 1.0 + (acc.frame as f32 * 0.13).sin() * 0.3 };
        let result = acc.update_and_get_result();
        println!("  {:3} | {:.3}  | {:?}", acc.frame - 1, target, result.data[0]);
    }
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
