# Day 301 · 用精灵边界排序

> Day 300 引入 sort_rule 后,今天 Casey 把 sprite bounds 真正纳入排序逻辑——重叠的 sprite 用 bounds 几何决定顺序。这是 sort_rule 的第一个实战应用。

## 0 · 为什么要有这一天

Day 300 的 sort_rule 实现还是粗略——只有 layer + bottom_y + x + spawn_id 四级。今天 Casey 加入更精细的判断:**两个 sprite 的 bounds 重叠时,根据"哪个更遮挡视线"决定顺序**。

具体场景:

- 玩家走进树丛——玩家 sprite 和树 sprite 部分重叠
- 玩家在树后(树遮挡玩家):玩家先画,树后画
- 玩家在树前(玩家遮挡树):树先画,玩家后画
- 完全重叠:取决于视觉直觉(通常按"脚的位置")

旧 sort_rule 只看 bottom_y,无法处理"sprite A 上半身和 sprite B 下半身重叠"这种复杂情况。今天 Casey 用 **bounds 几何**判断:

```
如果 A 的 bottom > B 的 top 且 B 的 bottom > A 的 top:
    它们真的重叠
    按 bottom_y 排
否则:
    不真的重叠,bottom_y 排序也行
```

实际上 sort_rule 加 bounds overlap 检查并不复杂,但**心智上**的清晰很关键——你不再"假装"sort 是全序,而是承认它是部分序,在 sort_rule 里处理重叠。

今天的代码量:扩展 sort_rule,加 bounds overlap 检查。然后测试多种 sprite 配置,验证排序符合视觉直觉。

心理锚点:看完今天,你应该能"看着两个 sprite 的位置,在脑中算出 sort_rule 的返回值"。

### 历史背景:SNES 时代的 Y-sort

1990 年代,SFC/SNES 游戏第一次大规模使用 Y-sort。硬件限制:sprite 数量 128 个/帧,有 OAM(Object Attribute Memory)限制,大小固定 8×8 / 16×16 / 32×32 / 64×64。游戏《时空之轮》(Square, 1995)的精灵都是 16x24 像素,需要拼成 4 个 8x8 tile。

那时的 Y-sort 算法:

```
对每个 OAM entry:
    entry.y = sprite.world_y >> 3  // 转 tile 坐标
按 entry.y 排序所有 entries
按排好的顺序写入 OAM
```

硬件自动按 OAM 顺序渲染(后面的覆盖前面的)。Y 越大,OAM entry 越靠后,覆盖越强——这就是 Y-sort 在硬件层的实现。

Casey 的 HH 是软渲染(还没切 GPU),所以 Y-sort 在 CPU 用 Rust `sort_by`。算法本质相同,只是平台不同。

现代引擎(Unity、Godot、bevy_sprite)都用类似的 sort_rule 系统,允许美术在 inspector 里调 layer、order in layer、sorting layer 等参数。

### 排序稳定性

Rust 的 `sort_by` 是**稳定排序**(stable sort)——相等元素保持原顺序。这对游戏很重要:

- 同 bottom_y 的两个 sprite,先 spawn 的先画(visual consistency)
- 不会因为排序"摇晃"(flicker),sprite 之间没有视觉抖动

`sort_unstable_by` 更快(快 20-30%),但破坏相等元素的顺序。游戏通常用稳定排序保证视觉一致。如果性能瓶颈在排序,可以用 `sort_unstable_by` + 显式 spawn_id tie-breaker(把"稳定性"塞进 sort key)。

## 2 · 心智模型

### 类比:剧院座位

把 sprite 排序想象成剧院座位安排。每个 sprite 是一个观众,有身高(sprite height)。座位排数是 layer,排内位置是 y。

观众 A 在第 3 排,A 头顶到第 2 排座位——A 可能挡住 B(在 A 后面)的视线。怎么决定 A 和 B 的座位关系?

- 看**脚的位置**:脚在前排(屏幕下方)的更靠前,挡后排的
- 如果脚的位置相同(A 和 B 在同一排),看身高——高的挡矮的
- 如果身高也相同,按"哪个先到剧院"决定(spawn_id)

今天 Casey 的 sort_rule 就是这个逻辑——layer(排数)→ bottom_y(脚的位置)→ bounds(身高)→ spawn_id。

### 2.1 完整 sort_rule

```rust
fn sort_rule(a: &Entity, b: &Entity, sprite_table: &SpriteTable) -> Ordering {
    let a_bounds = sprite_table.get(a.visual);
    let b_bounds = sprite_table.get(b.visual);

    a.layer.cmp(&b.layer)
        .then_with(|| {
            // 重叠检查
            if bounds_overlap(a.pos, a_bounds, b.pos, b_bounds) {
                // 重叠:看谁的 bottom 更下(更前)
                let a_bottom = a_bounds.bottom_y(a.pos);
                let b_bottom = b_bounds.bottom_y(b.pos);
                a_bottom.partial_cmp(&b_bottom).unwrap_or(Ordering::Equal)
            } else {
                // 不重叠:也按 bottom 排(但视觉上不会互相遮挡)
                let a_bottom = a_bounds.bottom_y(a.pos);
                let b_bottom = b_bounds.bottom_y(b.pos);
                a_bottom.partial_cmp(&b_bottom).unwrap_or(Ordering::Equal)
            }
        })
        .then_with(|| a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
        .then(a.spawn_id.cmp(&b.spawn_id))
}
```

重叠和不重叠用同样逻辑——这只是占位,实际可以加分支处理特殊场景。

### 2.2 重叠的视觉判断

```
场景 1:玩家在树前
            [tree top]
            [tree mid]
[player head]   <- 玩家头顶高度
[player mid]    <- 树遮挡这部分
[tree bot]
[player bot]    <- 玩家 bottom 在树 bottom 下方

bottom_y: player=140, tree=120
sort: tree(120) < player(140),先画 tree
视觉效果:玩家在树前(正确)
```

```
场景 2:玩家在树后
[player head]   <- 玩家头顶(被树遮挡)
[tree top]
[tree mid]
[tree bot]
[player bot]    <- 玩家 bottom 在树 bottom 下方

bottom_y: player=140, tree=120
sort: tree(120) < player(140),先画 tree
视觉效果:玩家在树后(正确,因为玩家 bottom 比 tree 大,但 tree 遮挡玩家上半)
```

等等——两种场景的 bottom_y 关系一样?不对。让我重新想:

```
玩家在树前:
- 玩家位置 (100, 100), bounds 32x48, bottom_y = 100 + 24 = 124
- 树位置 (100, 80), bounds 48x80, bottom_y = 80 + 40 = 120
- 树 bottom_y < 玩家 bottom_y,树先画,玩家后画
- 视觉:玩家遮挡树 ✓

玩家在树后:
- 玩家位置 (100, 60), bounds 32x48, bottom_y = 60 + 24 = 84
- 树位置 (100, 80), bounds 48x80, bottom_y = 80 + 40 = 120
- 玩家 bottom_y < 树 bottom_y,玩家先画,树后画
- 视觉:树遮挡玩家 ✓
```

bottom_y 大的 sprite 后画,遮挡 bottom_y 小的。这就是 Y-sort 的本质——"屏幕下方"的更前。

### 2.3 bounds overlap 的特殊情况

考虑玩家半透明(half alpha),玩家和怪物的 bounds 完全重叠:

- bottom_y 相同,sort 不区分
- 视觉上:两个半透明 sprite 互相遮挡,但都应该看到
- 单一 sort 无法处理——必须**两遍 blend**(depth peeling)

Casey 在 day 301 不处理半透明重叠,假设 sprite 都不透明。

### 3.3 · 🐧 Linux 系统编程视角

Linux 里"几何重叠"对应**damage region**。Wayland compositor 收到多个 damage rect,要合并:

```c
// 合并两个 rect
struct rect merge(struct rect a, struct rect b) {
    if (!overlap(a, b)) return a;  // 不重叠
    return (struct rect){
        .x = min(a.x, b.x),
        .y = min(a.y, b.y),
        .w = max(a.x + a.w, b.x + b.w) - min(a.x, b.x),
        .h = max(a.y + a.h, b.y + b.h) - min(a.y, b.y),
    };
}
```

合并后区域更少,合成器只需更新这一块。游戏 sort_rule 的 overlap 检查和这个 overlap 检查完全一样的算法。

### 3.4 · 🦀 Rust 生态视角

Rust 实现 bounds:

```rust
#[derive(Copy, Clone, Debug)]
struct Aabb { x: f32, y: f32, w: f32, h: f32 }

impl Aabb {
    fn from_center(pos: Vec2, w: f32, h: f32) -> Self {
        Self { x: pos.x - w/2.0, y: pos.y - h/2.0, w, h }
    }

    fn bottom(&self) -> f32 { self.y + self.h }
    fn top(&self) -> f32 { self.y }
    fn left(&self) -> f32 { self.x }
    fn right(&self) -> f32 { self.x + self.w }

    fn overlaps(&self, other: &Self) -> bool {
        self.x < other.x + other.w
            && self.x + self.w > other.x
            && self.y < other.y + other.h
            && self.y + self.h > other.y
    }
}
```

工业游戏库都内置 Aabb:`parry2d::Aabb`、`bevy_rapier::Aabb`。

```rust
use std::cmp::Ordering;

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug)]
struct Aabb { x: f32, y: f32, w: f32, h: f32 }

impl Aabb {
    fn from_center(pos: Vec2, w: f32, h: f32) -> Self {
        Self { x: pos.x - w/2.0, y: pos.y - h/2.0, w, h }
    }
    fn bottom(&self) -> f32 { self.y + self.h }
    fn overlaps(&self, other: &Self) -> bool {
        self.x < other.x + other.w && self.x + self.w > other.x
            && self.y < other.y + other.h && self.y + self.h > other.y
    }
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    layer: u8,
    pos: Vec2,
    bounds: Aabb,
    spawn_id: u16,
    name: &'static str,
}

fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            let a_bot = a.bounds.bottom();
            let b_bot = b.bounds.bottom();
            a_bot.partial_cmp(&b_bot).unwrap_or(Ordering::Equal)
        })
        .then_with(|| a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
        .then(a.spawn_id.cmp(&b.spawn_id))
}

fn main() {
    let mut entities = vec![
        Entity {
            layer: 1,
            pos: Vec2::new(100.0, 100.0),
            bounds: Aabb::from_center(Vec2::new(100.0, 100.0), 32.0, 48.0),
            spawn_id: 1,
            name: "Player",
        },
        Entity {
            layer: 1,
            pos: Vec2::new(100.0, 80.0),
            bounds: Aabb::from_center(Vec2::new(100.0, 80.0), 48.0, 80.0),
            spawn_id: 2,
            name: "Tree",
        },
        Entity {
            layer: 1,
            pos: Vec2::new(50.0, 100.0),
            bounds: Aabb::from_center(Vec2::new(50.0, 100.0), 24.0, 24.0),
            spawn_id: 3,
            name: "Stone",
        },
    ];

    entities.sort_by(sort_rule);
    for (i, e) in entities.iter().enumerate() {
        println!("#{}: {} bottom={:.0}", i, e.name, e.bounds.bottom());
    }
    // 预期:
    // Stone(50,100,bottom=112)
    // Tree(100,80,bottom=120)
    // Player(100,100,bottom=124)
    // 即 Stone 最先(底部最低),Player 最后(底部最高,最前)
}
```

**每行解释**:
- Tree bounds.bottom() = 80 + 80/2 = 120(从 pos.y=80 算)
- Player bounds.bottom() = 100 + 48/2 = 124
- Stone bounds.bottom() = 100 + 24/2 = 112
- 排序:Stone(112) < Tree(120) < Player(124)
- Player 最后画,在最前

### AABB overlap 的数学推导

AABB(Axis-Aligned Bounding Box)是 2D/3D 中最简单的几何体——它的边和坐标轴对齐,所以重叠测试只需检查每条轴的投影。

两个 AABB A 和 B,在 x 轴上的投影是两个区间 `[A.x, A.x+A.w]` 和 `[B.x, B.x+B.w]`。两区间**不相交**的条件是:

```
A.x + A.w < B.x  或  B.x + B.w < A.x
```

(注意:用 `<` 而不是 `<=`,边界 touching 不算重叠。这是 sort_rule 的选择,可以改成 `<=` 视场景而定。)

两区间**相交**就是上面两个条件都不满足:

```
NOT (A.x + A.w < B.x  或  B.x + B.w < A.x)
= A.x + A.w >= B.x  且  B.x + B.w >= A.x
= A.right >= B.left  且  B.right >= A.left
```

等价地,写成更紧凑的形式:

```
A.left < B.right  且  B.left < A.right
```

(注意:用 `<` 不是 `<=`,因为 touching 算"贴近"不算"重叠"。)

x 轴和 y 轴**都相交**,才说明 AABB 重叠。这就是 §3.4 Rust 代码里的 4 个比较:

```rust
self.x < other.x + other.w       // A.left < B.right
    && self.x + self.w > other.x // A.right > B.left
    && self.y < other.y + other.h // A.top < B.bottom
    && self.y + self.h > other.y  // A.bottom > other.top
```

这 4 个比较都是无分支的,Rust 编译器会编译成 4 个 `cmpss` SSE 指令,然后一个 AND——单指令多数据。现代 CPU 上一个 AABB overlap 测试 4-6 周期就能完成,1 ns 级别。

### SAT(Separating Axis Theorem)推广

AABB overlap 的原理叫 **Separating Axis Theorem**(分离轴定理)。定理:两个凸多边形不相交 ⟺ 存在一条轴,使它们在该轴上的投影不相交。

对 AABB,可能的分离轴就是 x 和 y——所以只需 2 次投影测试。对任意凸多边形,可能的分离轴是每条边的法线(2D)或每个面法线 + 边 cross 边(3D)。

OBB(Oriented Bounding Box,带旋转的盒子)有 4 条边(2D),要测试 4 条边的法线——比 AABB 多 4 倍代价。这就是为什么 2D 游戏坚持用 AABB——性能更好。

### Sprite bounds 与像素艺术的视觉锚点

像素艺术游戏中,sprite 通常有一个**锚点**(anchor point)——纹理里的某个像素,代表 sprite 在世界中的"位置"。常见锚点:

- **底部中心**(bottom-center):RPG 角色最常用——sprite 的"脚"在实体位置
- **中心**(center):UI 元素、弹幕——sprite 居中
- **左上角**(top-left):tile、背景——网格对齐

锚点选择影响 bottom_y 的计算:

```rust
fn bottom_y(anchor: Anchor, pos_y: f32, h: f32) -> f32 {
    match anchor {
        Anchor::BottomCenter => pos_y,                  // 实体位置就是底部
        Anchor::Center => pos_y + h / 2.0,              // 底部在 pos 下方 h/2
        Anchor::TopLeft => pos_y + h,                   // 底部在 pos 下方 h
    }
}
```

像素艺术要避免**亚像素**——sprite 必须对齐到整数像素,否则缩放时抖动。所以 pos_y 和 h 通常是 f32,但 bottom_y 算出来后 round 到整数:

```rust
let bottom_y_int = bottom_y.round() as i32;
let sort_key = bottom_y_int as u64;
```

整数 bottom_y 比较没有 f32 的 NaN/inf 问题,sort_key 更稳定。

### 部分序与拓扑排序(预告 Day 304)

今天的 sort_rule 用 `then_with` 链式比较,强制产生**全序**(total order)——任何两个 sprite 都有一个明确的前后。但**真相是**:sprite 之间的关系是**部分序**(partial order)——有些 pair 没有自然的"前后"关系。

举例:两个不重叠的 sprite,bottom_y 也不同,但视觉上无遮挡——它们的前后无所谓。强制全序会导致排序"看起来对,但本质是任意"。

更糟的情况:**循环依赖**——sprite A 应该在 B 前,B 在 C 前,C 在 A 前(三角形互相穿插)。强制全序会产生**错误**——某个 sprite 必然错位。

正确的解决方案是**拓扑排序**(topological sort)——承认部分序,只在有明确依赖的 pair 之间约束,其他任意。Day 304 Casey 会做这个。今天的 sort_rule 是"中间过渡"——还用全序,但已经为 Day 304 铺路。

### 工程权衡:sort_rule 的可维护性

sort_rule 函数会随项目复杂度膨胀。从 Day 295 的 3 行(仅 layer + y),到 Day 301 的 10+ 行(加 bounds + overlap + tie-breaker),再到 Day 304 的拓扑排序——每加一个游戏机制,sort_rule 就要扩展。

工程上的几个原则:

**1. sort_rule 的语义可测**。每个 sort_rule 分支都应有对应的单元测试场景:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn player_in_front_of_tree() {
        let player = make_entity("player", 100.0, 100.0, 32, 48);
        let tree = make_entity("tree", 100.0, 80.0, 48, 80);
        assert_eq!(sort_rule(&tree, &player), Ordering::Less);
        // tree 应该先画(在 player 后面)
    }

    #[test]
    fn non_overlapping_sprites_same_y() {
        let a = make_entity("a", 0.0, 100.0, 32, 32);
        let b = make_entity("b", 200.0, 100.0, 32, 32);
        // 不重叠,bottom_y 相同——sort_rule 任意,但不应该 panic
        let _ = sort_rule(&a, &b);
    }
}
```

这种"对每个游戏场景一个测试"是 sprite 系统的标准做法,防止回归。

**2. sort_rule 应该是 pure function**。不能有副作用(I/O、修改全局状态)——它是 sort 回调,会被调用 O(n log n) 次。任何副作用都会放大成 O(n log n) 次副作用。

**3. sort_rule 应该快**。每帧调用,百万级 sprite 时是性能瓶颈。优化:

- 内联
- 避免 heap allocation(用 `&Entity` 而非 `Entity`)
- branch 减到最少
- 用 `Ord` 而非 `PartialOrd`(避免 NaN check)

**4. 多 sort_rule 共存**。游戏中 UI 层、ground 层、sky 层可以分别用不同 sort_rule。Casey 的设计是单 sort_rule + layer 字段——简单但灵活。更复杂游戏(《原神》《塞尔达》)用多 pass sort。

### 性能基准

1000 个 sprite 排序的基准(参考数据,实际看硬件):

```
sort_by (Rust stable)        ~120 μs
sort_unstable_by (Rust)      ~85 μs
radix sort (固定 key)        ~40 μs
bitonic sort (并行)          ~25 μs(GPU 上)
```

60 FPS 帧时间预算 16.6 ms,1000 sprite 的 sort 占 0.5%-1%——可接受。但若 10万 sprite(MOBA 大规模战斗),就成瓶颈——需要 GPU sort。

### Rust 生命周期与 sort_rule

`sort_rule(a: &Entity, b: &Entity) -> Ordering` 用引用避免 copy。`Vec::sort_by` 接受 `FnMut(&T, &T) -> Ordering`——闭包。Casey 经常用闭包捕获 sprite_table:

```rust
entities.sort_by(|a, b| {
    let a_b = sprite_table.get(a.visual);
    let b_b = sprite_table.get(b.visual);
    // ... 比较
});
```

闭包捕获 `&sprite_table` 借用,sort 期间不能修改 sprite_table——Rust borrow checker 强制保证一致性。这是 Rust 相对 C 的安全优势。

### Wayland compositor 中的类似问题

Linux 桌面 Wayland 合成器(Sway、Mutter)也要"排序"窗口——按 z-order(用户堆叠顺序)+ layer(背景、底部、正常、顶部、overlay)。Weston 协议定义了 `wl_subsurface` 的同步/异步,本质和 Casey 的 sort_rule 同源。

阅读 Weston 源码 `libweston/output.c` 的 `weston_output_repaint`,能看到完全相同的 sort-by-layer-then-z 逻辑。工业级实现处理了 100+ 窗口、动画、damage region——比 Casey 的复杂,但骨架一致。

### Casey 的渐进设计哲学

Day 295 → 302 这七天的演化路径值得反复品味:
