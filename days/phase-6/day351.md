# Day 351 · 优化多线程模拟区域

> 昨天加了多线程,FPS 提升了,但没达到理论 N 倍。原因:同步开销、cache miss、任务太细、false sharing。今天 Casey 调优——把多线程的"理论性能"逼出来。

## 0 · 为什么要有这一天

8 核 CPU 多线程理论加速 8 倍。实际通常 3-5 倍。剩下 30-60% 哪去了?

**多线程的"隐形开销"**:

1. **同步开销**:加锁、解锁、原子操作。每秒几百万次锁,锁开销累积
2. **false sharing**:两个线程的变量在同一 cache line,互相 invalidate cache,变成串行
3. **任务调度开销**:每个 task 太小,创建/派发开销 > 计算开销
4. **cache miss**:多线程切换核心时,L1/L2 cache 失效
5. **NUMA 跨节点**:多 socket 系统,远端内存访问慢

业界有一整套优化技术:**NUMA awareness、cache-line align、批量任务、lock-free data structures**。

今天 Casey 主要解决:

- **任务粒度**:把"每 entity 一个 task"改成"每 region 一个 task"(减少调度)
- **cache-line 对齐**:避免 false sharing
- **批量提交**:一次推 N 个 task,减少锁竞争

心理锚点:今天之后你能用 perf 找多线程瓶颈,理解 false sharing 的成因,会用 `#[repr(align(64))]` 对齐数据。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑 Day 350 的代码,profile 发现:

1. **任务太细**:每 entity 推一个 task,8 核机器每帧 10000+ tasks,调度开销 5ms
2. **false sharing**:`worker_stats: [WorkerStat; 8]`,每个 WorkerStat 是 32 字节,两个相邻 worker 在同一 cache line,导致 cache 失效
3. **锁竞争**:`global_queue: Mutex<VecDeque<Task>>`,所有 worker 抢同一锁

修复:

1. **任务粒度**:每 region 一个 task,每帧 4-8 个 task,调度开销 < 0.1ms
2. **cache-line align**:`#[repr(align(64))] struct WorkerStat`,每个 worker 独占一个 cache line
3. **本地队列**:每个 worker 有自己的本地队列,大部分任务本地 push/pop,只有 work-stealing 才碰全局锁

结果:FPS 从 90 → 130,接近理论 8 核加速。

## 2 · 心智模型

### 类比:厨房优化

昨天开了 8 个厨师(线程),但效率只 50%。看现场:

- 每道菜切成 100 个小任务("切一根胡萝卜丝"),厨师疯狂取任务,实际切菜时间 < 取任务时间
- 8 个厨师共用 1 个水池,排队洗手
- 两个厨师的砧板靠太近,互相让对方 cache miss

优化:

1. 任务变粗("切一盘胡萝卜"),减少取任务次数
2. 每厨师独立水池,只在必要时共用
3. 砧板间距拉大,互不干扰

游戏多线程同构:**任务变粗、本地队列、cache 对齐**。

### False Sharing 详解

CPU cache 以 **cache line** 为单位(64 字节)。两个变量在同一 cache line,即使逻辑独立,也会互相干扰。

```
内存布局(不对齐):
[WorkerStat 0 (32 bytes)] [WorkerStat 1 (32 bytes)]
└──────── cache line 0 (64 bytes) ──────────┘

Thread 0 改 WorkerStat 0.count += 1
Thread 1 改 WorkerStat 1.count += 1

CPU 协议(MESI):任何 cache line 修改,其他核的 cache 副本 invalidate
Thread 0 改 → Thread 1 的 cache 失效 → Thread 1 重新读 → 改 → Thread 0 失效...

结果:两个线程互相 invalidate cache,实际串行,性能 1x 而非 2x。
```

**修复**:每个 WorkerStat 独占 cache line。

```rust
#[repr(align(64))]
struct WorkerStat {
    count: u64,
    // 编译器自动 padding 到 64 字节
}

// 数组现在每个元素独占 cache line
let stats: [WorkerStat; 8] = [...];
```

`#[repr(align(64))]` 告诉编译器"这个类型按 64 字节边界对齐"。每个 WorkerStat 占 64 字节(count 用 8 字节,剩下 56 字节 padding)。

代价:内存多用 56 * 8 = 448 字节。微不足道。

收益:消除 false sharing,性能可能 2x 提升。

### Rust 的 atomic ordering

`AtomicU32::fetch_add(1, Ordering::???)` 的 Ordering 选择:

- `Relaxed`:无内存顺序保证,最快。适合"只关心原子性,不关心顺序"(如统计计数)
- `Acquire` / `Release`:读用 Acquire,写用 Release。适合 mutex / channel
- `SeqCst`(顺序一致):全局顺序,最慢。最安全,默认选择

```rust
use std::sync::atomic::{AtomicU64, Ordering};

let counter = AtomicU64::new(0);
counter.fetch_add(1, Ordering::Relaxed);  // 最快
counter.fetch_add(1, Ordering::SeqCst);   // 最慢
```

性能差 5-10 倍。**生产代码用最小 Ordering**(大多数场景 Relaxed 够)。

### Lock-free vs Mutex

`Mutex<T>` 简单,但开销:

- 加锁:futex syscall(~微秒级,内核态切换)
- 解锁:唤醒等待者

`lock-free` 数据结构(无锁队列、无锁 stack)用原子操作,无系统调用,纳秒级。但实现复杂,易错。

**实战**:

- 通用共享数据 → `Mutex<T>` 或 `parking_lot::Mutex`
- 高频计数器 → `AtomicU64`
- 任务队列 → `crossbeam::queue::ArrayQueue` 或 `crossbeam-deque`
- 单生产单消费 → `std::sync::mpsc::channel`

不要盲目追求 lock-free——Mutex 大多数时候够快。

### 任务粒度

并行任务的"最优大小":

- **太小**(< 1μs):调度开销 > 计算开销
- **太大**(< 10ms):负载不均,有的核心忙死,有的闲死
- **最优**(10μs ~ 1ms):调度开销占比小,负载较均

游戏 update:每个 sim region 1ms+ 的工作量,正好。每 entity 一个 task(< 1μs),太小。

Rayon 自动合并小任务:

```rust
vec.par_iter().for_each(|x| { ... });
// 如果 vec.len() 很大,rayon 自动切成 N 块,每块一个 worker
```

但如果元素是"独立 entity"且每个 update 1μs,1M 个 = 1s 总时长。Rayon 分 8 块,每块 125ms,8 核并行 → 125ms 完成。可以。

但如果你想"每 region 一个 task",显式:

```rust
regions.par_iter_mut().for_each(|r| r.update(dt));
// 4 region,每个 200ms update,4 核 → 200ms 完成
```

### NUMA 和线程亲和

多 socket 系统(2+ CPU):每个 socket 有自己的内存(NUMA node)。线程访问远端内存慢 2-4 倍。

```
Socket 0 (cores 0-7, memory node 0)
Socket 1 (cores 8-15, memory node 1)

Thread on core 0 访问 node 1 内存:慢 2-3x
```

**NUMA aware** 编程:数据分配在"会用它的核心"对应的 NUMA node。Linux `numactl` / `libnuma`。

游戏开发:大多数 PC 单 socket,NUMA 不是问题。服务器(双路 Xeon)才考虑。

Arch Linux 看 NUMA:

```bash
sudo pacman -S hwloc numactl
lstopo  # 看拓扑
numactl --hardware  # 看 NUMA nodes
```

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏多线程优化的常见技巧:

**1. 帧间无依赖**

每帧独立,无跨帧状态。线程 A 跑 frame N+1 update,线程 B 渲染 frame N。两个线程几乎不互相等。

**2. 双缓冲**

线程 A 写 buffer 1,线程 B 读 buffer 2。下一帧交换。避免读写冲突。

**3. 任务图(task graph)**

把每帧分解成任务,标注依赖。调度器按依赖并行:

```
Task A (input)
Task B (physics, depends on A)
Task C (AI, depends on A)
Task D (render, depends on B and C)
```

B 和 C 并行,D 等待 B 和 C。

**4. 渲染线程独立**

CPU 渲染(OpenGL draw call)在独立线程,不阻塞 update。Frame N update 时,渲染线程跑 Frame N-1 的 draw calls。

Bevy 引擎的 schedule 就是任务图。

### 3.2 · 图形学视角

GPU 的"false sharing"叫 **bank conflict**:GPU 内存分 bank,访问同 bank 不同地址会串行。shader 编程要避免。

GPU 多线程是 SIMT(单指令多线程),程序员不暴露 thread,但 warp 内的 thread 必须同步执行同一指令。divergence(分支)性能损失大。

CPU 多线程的经验可以迁移到 GPU,但要适应 SIMT 模型。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:什么是 false sharing?为什么 `#[repr(align(64))]` 能解决?

**参考解答**:

False sharing:两个变量(逻辑独立)在同一 cache line(64 字节)。一个线程改一个,另一个线程的 cache line 副本 invalidate,必须重新读。两个线程互相 invalidate,实际串行。

`#[repr(align(64))]` 让类型按 64 字节边界对齐,编译器自动 padding 到 64 字节倍数。每个变量独占 cache line,不同线程改不同变量,cache line 不冲突。

代价:每变量多占内存(最多 56 字节 padding)。但对游戏内的高频计数器(每秒改 1M 次),消除 false sharing 收益远超内存代价。

### Lv2 · 动手实践

**题**:实现 false sharing 对比测试。8 个线程各自对一个 atomic counter 加 1M 次。一个版本数组(可能 false sharing),一个版本 cache-padded 数组。对比耗时。

完成标准:cache-padded 版本至少 2x 快。

**参考解答**:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::thread;
use std::time::Instant;

const N_THREADS: usize = 8;
const ITERS: u64 = 1_000_000;

// 不对齐(可能 false sharing)
struct UnalignedCounter(AtomicU64);
impl Default for UnalignedCounter {
    fn default() -> Self { Self(AtomicU64::new(0)) }
}

// 对齐到 cache line(防 false sharing)
#[repr(align(64))]
struct AlignedCounter(AtomicU64);
impl Default for AlignedCounter {
    fn default() -> Self { Self(AtomicU64::new(0)) }
}

fn bench_unaligned() -> std::time::Duration {
    let counters: Vec<UnalignedCounter> = (0..N_THREADS).map(|_| Default::default()).collect();
    let counters_ref: &'static [_] = Box::leak(counters.into_boxed_slice());

    let t = Instant::now();
    let handles: Vec<_> = (0..N_THREADS).map(|i| {
        let c = &counters_ref[i];
        thread::spawn(move || {
            for _ in 0..ITERS {
                c.0.fetch_add(1, Ordering::Relaxed);
            }
        })
    }).collect();
    for h in handles { h.join().unwrap(); }
    t.elapsed()
}

fn bench_aligned() -> std::time::Duration {
    let counters: Vec<AlignedCounter> = (0..N_THREADS).map(|_| Default::default()).collect();
    let counters_ref: &'static [_] = Box::leak(counters.into_boxed_slice());

    let t = Instant::now();
    let handles: Vec<_> = (0..N_THREADS).map(|i| {
        let c = &counters_ref[i];
        thread::spawn(move || {
            for _ in 0..ITERS {
                c.0.fetch_add(1, Ordering::Relaxed);
            }
        })
    }).collect();
    for h in handles { h.join().unwrap(); }
    t.elapsed()
}

fn main() {
    // 预热
    bench_unaligned();
    bench_aligned();

    let t1 = bench_unaligned();
    let t2 = bench_aligned();
    println!("Unaligned: {:?}", t1);
    println!("Aligned:   {:?}", t2);
    println!("Speedup:   {:.2}x", t1.as_secs_f64() / t2.as_secs_f64());
}
```

**预期**(8 核):Unaligned 50ms,Aligned 15ms,Speedup 3x。

**关键解释**:
- `Box::leak`:把 Vec 变 'static 引用,避免 lifetime 痛苦
- `Ordering::Relaxed`:最快,因为我们只关心原子性,不关心顺序
- 预热:第一次跑会加载代码、初始化 cache,跑两次取第二次

## 8 · Rust / Arch 落地代码

### 完整可跑示例:多线程优化全套

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::sync::Arc;
use std::thread;
use std::time::Instant;
use rayon::prelude::*;

// === Cache-padded 原子计数器 ===
#[repr(align(64))]
struct PaddedCounter(AtomicU64);

struct WorkerPool {
    counters: Vec<PaddedCounter>,
}

impl WorkerPool {
    fn new(n: usize) -> Self {
        let counters = (0..n).map(|_| PaddedCounter(AtomicU64::new(0))).collect();
        Self { counters }
    }

    fn inc(&self, worker_id: usize) {
        self.counters[worker_id].0.fetch_add(1, Ordering::Relaxed);
    }

    fn total(&self) -> u64 {
        self.counters.iter().map(|c| c.0.load(Ordering::Relaxed)).sum()
    }
}

// === 任务粒度对比 ===
const N_ENTITIES: usize = 100_000;

#[derive(Copy, Clone)]
struct Entity { pos: [f32; 2], vel: [f32; 2] }

fn update_entities_fine(entities: &mut [Entity], dt: f32) {
    // 细粒度:每 entity 一个 task(实际不用 rayon 这么做,这里是模拟)
    entities.iter_mut().for_each(|e| {
        e.pos[0] += e.vel[0] * dt;
        e.pos[1] += e.vel[1] * dt;
    });
}

fn update_entities_coarse(entities: &mut [Entity], dt: f32) {
    // 粗粒度:切片成 N 块,每块一个 task
    entities.par_chunks_mut(N_ENTITIES / 8).for_each(|chunk| {
        for e in chunk {
            e.pos[0] += e.vel[0] * dt;
            e.pos[1] += e.vel[1] * dt;
        }
    });
}

fn main() {
    // === Test 1: Cache padded counters ===
    println!("=== Test 1: Cache-padded counters ===");
    let pool = Arc::new(WorkerPool::new(8));
    let t = Instant::now();
    let handles: Vec<_> = (0..8).map(|i| {
        let p = Arc::clone(&pool);
        thread::spawn(move || {
            for _ in 0..1_000_000 {
                p.inc(i);
            }
        })
    }).collect();
    for h in handles { h.join().unwrap(); }
    println!("Time: {:?}, Total: {}", t.elapsed(), pool.total());

    // === Test 2: Task granularity ===
    println!("\n=== Test 2: Task granularity ===");
    let dt = 0.016;
    let iters = 1000;

    let mut entities_fine: Vec<Entity> = (0..N_ENTITIES).map(|_| Entity {
        pos: [0.0, 0.0], vel: [1.0, 1.0]
    }).collect();
    let t = Instant::now();
    for _ in 0..iters {
        update_entities_fine(&mut entities_fine, dt);
    }
    let fine_ms = t.elapsed().as_millis();

    let mut entities_coarse: Vec<Entity> = (0..N_ENTITIES).map(|_| Entity {
        pos: [0.0, 0.0], vel: [1.0, 1.0]
    }).collect();
    let t = Instant::now();
    for _ in 0..iters {
        update_entities_coarse(&mut entities_coarse, dt);
    }
    let coarse_ms = t.elapsed().as_millis();

    println!("Fine-grained (single-thread): {} ms", fine_ms);
    println!("Coarse-grained (8 chunks):    {} ms", coarse_ms);
    println!("Speedup: {:.2}x", fine_ms as f64 / coarse_ms.max(1) as f64);

    // === Test 3: Ordering comparison ===
    println!("\n=== Test 3: Atomic ordering ===");
    let counter = Arc::new(AtomicU64::new(0));

    let c2 = Arc::clone(&counter);
    let t = Instant::now();
    let h = thread::spawn(move || {
        for _ in 0..10_000_000 {
            c2.fetch_add(1, Ordering::Relaxed);
        }
    });
    h.join().unwrap();
    let relaxed_ns = t.elapsed().as_nanos() / 10_000_000;

    let c3 = Arc::clone(&counter);
    let t = Instant::now();
    let h = thread::spawn(move || {
        for _ in 0..10_000_000 {
            c3.fetch_add(1, Ordering::SeqCst);
        }
    });
    h.join().unwrap();
    let seqcst_ns = t.elapsed().as_nanos() / 10_000_000;

    println!("Relaxed: {} ns/op", relaxed_ns);
    println!("SeqCst:  {} ns/op", seqcst_ns);
    println!("Speedup: {:.2}x", seqcst_ns as f64 / relaxed_ns as f64);
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
