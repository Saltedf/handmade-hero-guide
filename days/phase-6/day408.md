
# Day 408 · 完成调试体积纹理

> Day 407 你修了第一个 bug——`glTexSubImage3D` 的 `format` 和 `internal_format` 不匹配,导致驱动在某些 GPU 上把数据扔了。现在 volume texture **有数据了**,但渲染结果还是不对:有些体素采样值看起来对,有些是奇怪的边缘色,有的位置突然变黑。今天 Casey 收尾这个 bug——他的诊断方法已经从"逐段二分"切换到"逐像素追踪":**选一个画面上错误的像素,跟着 fragment shader 的执行路径一步步反推,直到找到第一个错误的中间值**。这是图形调试的终极武器,掌握它你以后任何渲染 bug 都能解决。

## 0 · 为什么要有这一天

Day 407 之后的画面状态是这样的:你在 RenderDoc 的 Texture Viewer 里看 volume texture,数据是有的——你能看到火把附近的体素亮、墙后体素暗、远处体素接近 0,**和预期符合**。但你切到"渲染目标"看实际渲染结果,**画面上某些像素仍然不对**:走廊地板异常亮、墙脚阴影偏到了不该在的位置、远处的体素边缘有奇怪的光晕。

这意味着你的 bug **不在 upload 链路**(那部分昨天修好了),而在**采样链路**——fragment shader 从 texture 取值的过程。具体可能的错误:

- **采样坐标 uvw 算错了**:你在 shader 里把世界坐标投影到体素空间的变换矩阵错了
- **采样 filter 不对**:texture 创建时 `GL_NEAREST` vs `GL_LINEAR`,导致采到错的体素
- **边界处理错了**:`GL_CLAMP_TO_EDGE` 让边界体素"溢出"到所有越界采样,产生奇怪光晕
- **多重网格层次混合权重错**:你采了三层 LPV(32³、64³、128³),权重算错导致某一层主导,其他层被忽略
- **shader 里数值溢出 / NaN**:某个除法分母为 0,或 `pow(x, n)` 当 x<0 时 NaN,被 silently 写成 0

这种"画面整体对了但局部错"的 bug 最难定位,因为**每一步都"几乎"对**——你光看代码、看 trace 都觉得没问题,但画面就是错的。Casey Day 408 的方法是**沿着单像素的执行路径一步步看中间值**。RenderDoc 提供了"Pixel History"和"Shader Debugger"两个工具,合起来能让你**对画面上任意一个像素,看到它怎么从初始的黑色一步步变成现在这个颜色**。

为什么这个能力重要?因为**图形 bug 永远不会随经验减少,只会变隐蔽**。初级 bug 是"全屏黑",一眼能看出来;中级 bug 是"光照位置偏了一格",看 trace 也能发现;高级 bug 是"特定角度下特定区域的颜色比预期暗 20%",**没有 pixel-level debug 你永远定位不了**。今天的训练让你掌握**专业图形工程师的 debug 工作流**:抓帧 → 选可疑像素 → 看 shader disassembly → 单步调试 → 定位错值。

心理锚点:今天之后,你能:(1) 在 RenderDoc 里用 Pixel History 看一个像素经历了哪些 draw call;(2) 用 Shader Debugger 单步执行 fragment shader,看每个临时变量的值;(3) 把 shader 里某个中间值改成"调试颜色"输出到屏幕,快速验证假设;(4) 写一个可复用的"shader debug print"机制(用 `imageStore` 写到 SSBO,shader 退出后 CPU 端读出来)。**这是图形工程师一辈子用得到的工具链**。

## 1 · Casey 今天做了什么(HH 脉络)

Day 407 结束时 volume texture 有值,但渲染结果不对。Day 408 Casey 做了三件事:

1. **选一个明显错误的像素**:走廊地板某处的颜色太亮。Casey 在 VSGD 里点击这个像素,选"Debug This Pixel",工具自动打开 Pixel History——一个时间线,显示这个像素经历了哪些 draw call,每个 draw call 把像素改成什么颜色。Casey 发现像素经过了:Background draw(黑色)→ World draw(地板纹理)→ LPV lighting draw(应该是叠加一点间接光)。**问题在 LPV lighting draw 之后**,像素变成了接近白色(过度亮)。

2. **单步执行 fragment shader**:VSGD 提供 Shader Debugger,它能"重放"这一次 fragment shader 调用,**用当前采样点的所有上下文**重新跑一遍 GLSL 代码。Casey 启动 Shader Debugger,看到 shader 里某个中间值 `vec3 indirect_light = texture(uVoxelTex, uvw).rgb;` —— 他原本预期 `indirect_light ≈ vec3(0.2, 0.15, 0.1)`(略带暖色),实际是 `vec3(0.95, 0.9, 0.85)`(几乎白)。**采样值偏离预期 5 倍**。

3. **追查 uvw 怎么来的**:`uvw` 是 fragment shader 里算的"世界坐标 → 体素归一化坐标"。Casey 单步看 `uvw` 的值:`vec3(1.05, 0.5, 0.7)`——**x 分量 1.05 超过 1.0**!这意味着采样点在体素网格外,`GL_CLAMP_TO_EDGE` 把 x 截到 1.0,实际采到的是网格 x=31 那一列的体素。这一列恰好是光源头所在体素,**所以采到了光的强度值**。

**根因**:CPU 端把世界坐标转体素坐标的代码有 bug。Casey 用了:

```c
// 错误代码
vec3 uvw = (world_pos - grid_min) / grid_size;
```

但 `grid_size` 是网格**宽度**(比如 32 米),不是网格**步长**(1 米 / 32 = 0.03125 米/voxel)。正确的归一化应该是:

```c
// 正确
vec3 uvw = (world_pos - grid_min) / (grid_max - grid_min);
```

`grid_max - grid_min` 才是网格的实际范围(比如从世界 (0,0,0) 到 (32,32,32)),归一化后 uvw 在 [0,1]³。

Casey 修了这个 bug,画面立即正常。**整个 bug 调试花了两天(Day 407 + 408)**,但留下了一个完整的图形调试工作流。

## 2 · 心智模型

### 类比:像素级调试是"刑侦现场还原"

想象你调查一起交通事故。你有事故现场的照片(画面),你有车辆轨迹的 GPS 数据(trace),但你想知道**那辆车为什么在那个时刻打方向**。如果你有车辆 EDR(Event Data Recorder,黑匣子),你能看到事故前 5 秒**每个传感器读数**:方向盘角度、刹车踏板力度、车速、发动机转速——你能精确定位"3.2 秒时方向盘突然偏了 30°,但司机没动方向盘"——于是你怀疑是机械故障。

**Pixel History + Shader Debugger 就是 GPU 的 EDR**。Pixel History 告诉你"这个像素经历了什么"——从背景黑色,到地板纹理,到光照叠加,到最终颜色。Shader Debugger 让你**重放一次 fragment shader 调用,看每一步中间变量的值**。

这两件事合起来,你能像刑侦人员一样**回放事故,定位第一个错误变量**。

### 严谨原理:fragment shader 的执行模型

为了用 Shader Debugger,**你必须理解 fragment shader 的执行模型**——它不是普通的程序,有几个特殊性质:

#### 2.1 单 fragment 单执行

fragment shader 在每个被光栅化覆盖的像素上**独立执行一次**。一个 fragment 是"一个像素位置 + 它对应的插值数据"。fragment shader 的输入:

- `gl_FragCoord` —— 像素坐标(vec4,x,y,z,w),z 是深度
- `varying` 变量 —— 从 vertex shader 输出插值到 fragment 的值(比如世界坐标、法线、uv)
- `uniform` 变量 —— 全局常量,所有 fragment 共享(texture、矩阵、光照参数)

输出:

- `gl_FragColor`(GLSL 1.20 以下)/ `out vec4 fragColor`(GLSL 3.30+)
- 可选:`gl_FragDepth`(深度输出)

#### 2.2 为什么"重放"是可能的

fragment shader 是**纯函数**(没有副作用):给定相同的输入(varying、uniform),输出相同。**只要工具记录了输入**,就能在事后用 CPU 重放这个 shader 调用,看每一步中间变量的值。

RenderDoc 的 Shader Debugger 就是这么工作的:抓帧时记录每个 fragment 调用的所有输入;打开 Shader Debugger 时,CPU 重放这个调用,按 GLSL 源码逐步执行,**显示每个表达式的值**。

#### 2.3 GLSL 没有 printf

GLSL 是 GPU 上执行的,没有 stdout。你不能在 shader 里写 `printf("%f", x)`。**这是 GPU 编程最大的不便**。替代方案:

- **调试输出(Debug Output, OpenGL 4.3+)**:`glDebugMessageInsert` 让 shader 通过特定扩展把值写到 log。但这个机制开销大,只用于开发。
- **imageStore 写 SSBO**:在 shader 里用 `imageStore` 把值写到 Shader Storage Buffer Object,shader 结束后 CPU 读 SSBO 看值。Casey 在 Day 408 之后用这个方法。
- **把 debug 值当颜色输出**:`gl_FragColor = vec4(vec3(debug_value), 1.0);` 把要 debug 的值映射到 [0,1] 当颜色输出,看屏幕。简单但不精确。
- **Shader Debugger**:RenderDoc 提供,精确到每个变量,但只能 debug 一帧。

**最常用的快速 debug 是第 3 种**——把中间值当颜色输出。比如你想知道某个 fragment 的 uvw:

```glsl
// fragment shader
#version 430
in vec3 vWorldPos;
out vec4 fragColor;
uniform sampler3D uVoxelTex;
uniform vec3 uGridMin;
uniform vec3 uGridMax;

void main() {
    vec3 uvw = (vWorldPos - uGridMin) / (uGridMax - uGridMin);

    // 正常渲染
    // vec3 light = texture(uVoxelTex, uvw).rgb;
    // fragColor = vec4(light, 1.0);

    // DEBUG:把 uvw 当颜色输出(把 [-1,2] 映射到 [0,1])
    vec3 debug_color = clamp((uvw + 1.0) / 3.0, 0.0, 1.0);
    fragColor = vec4(debug_color, 1.0);
}
```

屏幕上看到的颜色就是 uvw 的可视化——如果某区域是黑色,uvw 接近 -1(越界);如果是红色,uvw 接近 2(也越界);如果是 1/3 灰,uvw 接近 0(网格原点)。**Casey 在 Day 408 就是用这个方法发现 uvw 的 x 分量超过 1**。

### Pixel History:像素的"传记"

Pixel History 是 RenderDoc 的核心 debug 工具之一。你点击画面上任意一个像素,Pixel History 显示**这个像素位置经历了哪些 draw call,每个 draw call 把像素改成什么颜色**。结构:

```
初始:      RGBA(0, 0, 0, 1)         ← 黑色背景
Draw #5:   RGBA(0.3, 0.25, 0.2, 1)  ← 地板纹理
  └─ source: RGBA(0.3, 0.25, 0.2, 1), blend: replace
Draw #12:  RGBA(0.5, 0.4, 0.3, 1)   ← 光照叠加
  └─ source: RGBA(0.2, 0.15, 0.1, 1), blend: add
最终:      RGBA(0.5, 0.4, 0.3, 1)
```

你能在 Pixel History 里点任意一行,**跳转到那个 draw call 的 Shader Debugger**,看 fragment shader 在那个像素位置的执行。

**关键用法**:当像素颜色错,**用 Pixel History 看哪一步变错**。如果初始对、中间对、最后一步变错——bug 在最后一步的 shader;如果初始对、中间变错——bug 在中间的 shader。

### Shader Debugger:shader 单步执行

Shader Debugger 让你**单步执行 fragment shader**,看每个临时变量的值。它在你点击的像素位置,**用该像素的 varying、uniform、texture data 重放**这次 shader 调用。

功能:
- 单步(next / step in / step out)
- 查看所有变量(局部、uniform、texture sample)
- 修改变量值并重新执行
- 查看反汇编(GPU 端的 ISA 指令,如 NVIDIA 的 NVIR)

**关键用法**:当 fragment shader 的输出错,**用 Shader Debugger 单步看哪个中间值开始变错**。比如:

```
1. vWorldPos = (5.2, 1.0, 3.5)          ← 正确
2. uGridMin = (0, 0, 0)                  ← 正确
3. uGridMax = (4, 4, 4)                  ← 正确(!注意 4 不是 32)
4. uvw = (vWorldPos - uGridMin) / (uGridMax - uGridMin)
   uvw = (5.2, 1.0, 3.5) / (4, 4, 4)
   uvw = (1.3, 0.25, 0.875)              ← x 分量超过 1!越界!
5. sample = texture(uVoxelTex, uvw)
   sample = (0.95, 0.9, 0.85)            ← 采到边界(光源头)
6. fragColor = vec4(sample, 1.0)         ← 错误输出
```

**在第 4 步**你发现 uvw.x = 1.3 越界,这就是 bug 的第一个征兆。往前看,uGridMax 是 (4,4,4) 还是 (32,32,32)?这就是 CPU 端传给 shader 的 uniform 值,RenderDoc 的 State tab 能看到。如果 CPU 端传的是 4 但网格实际是 32,**bug 在 CPU 端传 uniform 的代码**。

### 多重网格混合的 bug 模式

LPV 用多层(32³、64³、128³)混合。每层有自己的 uvw 计算和权重:

```glsl
vec3 uvw_coarse = (worldPos - grid0Min) / (grid0Max - grid0Min);
vec3 uvw_medium = (worldPos - grid1Min) / (grid1Max - grid1Min);
vec3 uvw_fine   = (worldPos - grid2Min) / (grid2Max - grid2Min);

vec3 light_coarse = texture(uVoxel0, uvw_coarse).rgb;
vec3 light_medium = texture(uVoxel1, uvw_medium).rgb;
vec3 light_fine   = texture(uVoxel2, uvw_fine).rgb;

vec3 final_light = w0 * light_coarse + w1 * light_medium + w2 * light_fine;
```

**常见 bug**:
- `grid0Min` 和 `grid0Max` 用错层(本来是 32³ 范围传成 64³ 范围)
- 权重 w0/w1/w2 没归一化(`w0 + w1 + w2 = 1.5` 而不是 `1.0`)
- 某层 uvw 越界被 clamp 到边界,引入虚假光

**debug 方法**:在 Shader Debugger 里**逐层查看 light_coarse、light_medium、light_fine 的值**。哪层明显偏离预期,那层有 bug。

### Shader Disassembly:看 GPU 真正在做什么

RenderDoc 能显示 shader 的**反汇编**(disassembly)——GPU 真正执行的指令,不是 GLSL 源码。NVIDIA GPU 的 ISA 叫 SASS(SASS Assembly),AMD 叫 GCN,Intel 叫 GEN。

为什么看 disassembly?**有时 GLSL 编译器优化出 bug**。比如你写 `if (x > 0) { ... } else { ... }`,编译器可能把整个 if flatten(展平),让两个分支都执行但用 mask 选择结果。如果优化出 bug,你 GLSL 看不出问题,但 disassembly 能看出**指令顺序不对**。

普通应用层 debug 用不上 disassembly,但**开发 shader 编译器、做 shader 优化**时必备。Casey 偶尔会看,但 99% 的 bug 在 GLSL 源码层。

## 3 · 四域深入

### 3.1 · 🎨 图形学视角

Pixel-level debugging 是图形工程师的核心技能。每个工业渲染管线都有专门的工具:

- **Unity**: Frame Debugger(免费)+ RenderDoc integration
- **Unreal Engine**: Built-in GPU Visualizer + RenderDoc plugin
- **Godot 4**: Frame profiler + shader hot-reload
- **Web**: Spector.js(WebGL)、WebGPU Inspector
- **DirectX**: PIX(VSGD 后继)、RenderDoc
- **Vulkan**: RenderDoc、NVIDIA Nsight Graphics、AMD Radeon GPU Profiler、Intel Graphics Frame Analyzer

**共性**:每个工具都提供 trace 抓帧、texture viewer、pixel history、shader debugger。**学会一个,其他都会用**——这是行业共识的 debug 工作流。

**图形 bug 的工业分类**(根据定位难度):

| 类别 | 典型 bug | 工具 |
|---|---|---|
| 全屏黑/白 | shader 编译失败、uniform 未设、绑定点错 | glGetError + log |
| 几何错位 | vertex shader 矩阵错、VAO/VBO 错绑 | RenderDoc mesh viewer |
| 纹理错位 | uv 算错、texture unit 错绑、format 错 | RenderDoc texture viewer |
| 颜色值异常 | 采样越界、混合公式错、精度溢出 | Pixel History + Shader Debugger |
| 性能慢 | overdraw、texture 太大、shader 太重 | Nsight / Radeon profiler |
| 渲染顺序错 | depth test 没开、blend state 错 | RenderDoc state viewer |

Day 408 的 bug 属于"颜色值异常",这是最难的——所有上层都"看起来"对,只在某个像素的某个采样点出问题。**Pixel History + Shader Debugger 是唯一武器**。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上几个对应的工具:

**apitrace**:更轻量,适合快速看 trace。功能比 RenderDoc 少,但启动快、占内存少。apitrace 没有 Pixel History,但有"看任意 GL 调用"功能,你能点 `glDrawElements` 看那一次 draw 的所有 state。

**RenderDoc**:Linux 上同样支持,功能完整。是 Day 408 Casey 工作流的标准工具。Linux 版 GUI 用 Qt 写,稳定。

**NVIDIA Nsight Graphics**:NVIDIA 专有,需要专有驱动。功能最完整,但绑死 NVIDIA。

**AMD Radeon GPU Profiler**:AMD 专有,类似 Nsight。

**Intel Graphics Frame Analyzer**:Intel 集显用。

**Glad / GLSL Analyzer**:命令行工具,验证 shader 能否在当前驱动编译,看编译错误。

**Arch 上装的命令**:

```bash
sudo pacman -S renderdoc apitrace mesa-utils
# mesa-utils 提供 glxinfo 和 glxgears

# 测试 shader 是否编译:用 glslangValidator
sudo pacman -S glslang
glslangValidator -V my_shader.vert  # -V 是 Vulkan,GLSL 用 -G
glslangValidator -G my_shader.frag
# 输出编译错误
```

**为什么 GPU debug 工具大多用 Qt**?因为 Qt 跨平台(Linux / Windows / macOS 都能用同一套代码),且 Qt 的 model/view 架构适合做大型数据列表(trace 里几千个 draw call)。Mesa、RenderDoc、AMD GPU Profiler、Intel GPA 都是 Qt。

### 3.3 · 🦀 Rust 生态视角

Rust 调用 GL 时,**shader 源码作为字符串嵌入 Rust 程序**:

```rust
const VERTEX_SHADER: &str = r#"
#version 430
layout(location = 0) in vec3 aPos;
layout(location = 1) in vec3 aNormal;
uniform mat4 uMVP;
out vec3 vWorldPos;
out vec3 vNormal;
void main() {
    gl_Position = uMVP * vec4(aPos, 1.0);
    vWorldPos = aPos;  // 假设模型空间 = 世界空间
    vNormal = aNormal;
}
"#;

const FRAGMENT_SHADER: &str = r#"
#version 430
in vec3 vWorldPos;
in vec3 vNormal;
out vec4 fragColor;
uniform sampler3D uVoxelTex;
uniform vec3 uGridMin;
uniform vec3 uGridMax;
void main() {
    vec3 uvw = (vWorldPos - uGridMin) / (uGridMax - uGridMin);
    vec3 light = texture(uVoxelTex, uvw).rgb;
    fragColor = vec4(light, 1.0);
}
"#;
```

**问题**:shader 写错(语法错、类型错),glow 在 `compile_shader` 时**返回 Err**,但**错误信息是 GLSL 编译器输出的**,很长、很难读。Rust 这边要处理:

```rust
fn compile_shader(gl: &glow::Context, ty: u32, src: &str) -> Result<glow::Shader, String> {
    let shader = unsafe { gl.create_shader(ty) }.map_err(|e| format!("create_shader: {:?}", e))?;
    unsafe {
        gl.shader_source(shader, src);
        gl.compile_shader(shader);
    }
    let compiled = unsafe { gl.get_shader_compile_status(shader) };
    if !compiled {
        let log = unsafe { gl.get_shader_info_log(shader) };
        unsafe { gl.delete_shader(shader); }
        return Err(format!("Shader compile failed:\n{}", log));
    }
    Ok(shader)
}

fn main() {
    // ...
    let vert = compile_shader(&gl, glow::VERTEX_SHADER, VERTEX_SHADER)
        .unwrap_or_else(|e| panic!("{}", e));
}
```

**关键**:**每次 shader 编译失败,要打印完整 GLSL info log**。如果没打印,你会看到"程序崩溃但不知道为什么",这是新手最大的坑。

**Rust 端的 debug 输出**:

```rust
// 启用 OpenGL debug output(4.3+)
unsafe {
    gl.enable(glow::DEBUG_OUTPUT);
    gl.debug_message_callback(|_src, ty, id, sev, msg| {
        println!("[GL {}] id={} sev={:?}: {}", ty, id, sev, msg);
    });
}
```

这会让 OpenGL 把所有 warning/error 通过 callback 推到你的 Rust 程序。**debug 模式必开**——很多 GL 用法错(例如绑定点冲突、uniform 未设)会触发 warning,你立刻知道。

**Rust + glow + bytemuck 完整 debug 链路**:

1. CPU 端:Rust 写 voxel grid,bytemuck 转 bytes,upload 到 GPU
2. CPU 端:`println!` 验证 upload 前数据
3. GPU 端 upload:用 `glGetTexSubImage` 验证 texture 有值
4. CPU 端设 uniform:`glUniform3f(uGridMin_loc, 0.0, 0.0, 0.0)` —— 检查 location 不为 -1
5. GPU 端 shader:用 RenderDoc Shader Debugger 单步
6. GPU 端 fragment color:RenderDoc Pixel History

这一套链路是 Casey Day 407-408 教给你的"完整武器库"。

### 3.4 · 🔢 数学视角

uvw 坐标变换的数学:把世界坐标 `p_world` 映射到体素归一化坐标 `uvw ∈ [0,1]³`。

```
uvw = (p_world - grid_min) / (grid_max - grid_min)
```

`grid_min` 和 `grid_max` 是网格在世界空间的边界。比如网格覆盖世界 (0,0,0) 到 (32,32,32),则 `grid_min = (0,0,0)`,`grid_max = (32,32,32)`。一个世界坐标 (16, 8, 4) 映射到 uvw = (0.5, 0.25, 0.125)——网格中心 x 方向、y 方向 1/4、z 方向 1/8。

**为什么归一化**?因为 texture 坐标永远是 [0,1],与 texture 尺寸无关。32³ 和 1024³ 的 texture 用同样的 uvw,OpenGL 内部按 texture 尺寸映射。

**越界处理**:`uvw` 在 [0,1] 外的处理由 `glTexParameteri(GL_TEXTURE_WRAP_S/T/R, mode)` 决定:

| Mode | 行为 |
|---|---|
| `GL_REPEAT` | 取小数部分,uvw=1.3 当 0.3 用,适合 tileable pattern |
| `GL_MIRRORED_REPEAT` | 镜像 repeat,uvw=1.3 当 0.7 |
| `GL_CLAMP_TO_EDGE` | 截到边界,uvw=1.3 当 1.0,**适合非 tileable 数据**(LPV 用) |
| `GL_CLAMP_TO_BORDER` | 截到边界,超出范围用 border color |

Casey Day 408 的 bug 是 uvw 越界被 `CLAMP_TO_EDGE` 截到边界,采到光源头体素。**修法**:不是改 wrap mode,而是**修 uvw 计算**让它不越界——确保所有被采样的世界点都在网格内。

**多重网格权重**:多层 LPV 混合,权重选择是个数学问题。常见策略:

- **距离权重**:网格越粗,作用范围越大;按距离选层(近处用细层,远处用粗层)
- **Hermite 平滑**:用 smoothstep 在层之间过渡,避免硬切换
- **频率权重**:高频细节用细层,低频全局用粗层(类似 mipmap 的 trilinear blend)

Casey 在 Day 409 用距离 + Hermite 平滑混合。

### CPU debug vs GPU debug

| 维度 | CPU(Rust) | GPU(GLSL) |
|---|---|---|
| 打印 | `println!` 任意值 | 不支持,要用 imageStore / debug color |
| 断点 | gdb / lldb | RenderDoc Shader Debugger |
| 内存检查 | valgrind / miri | glGetTexSubImage / RenderDoc texture viewer |
| 单步 | gdb next/step | Shader Debugger step in |
| 性能 | perf / flamegraph | Nsight / Radeon profiler |
| 复现性 | 通常确定性 | 多线程渲染可能非确定性 |

GPU debug **永远比 CPU debug 难**,因为 GPU 是异步、并行、不透明的。但 Casey 在 Day 407-408 展示的方法论——**抓帧 → 二分缩小 → 像素级追踪 → 单步**——是 30 年行业沉淀的最佳实践。

### 工业级 debug 工具的演化

- **1990s**:GL + `printf`,无 GUI 工具,debug 全靠经验
- **2000s**:gDEBugger(后被 AMD 收购改 AMD GPU PerfStudio)出现,第一个商用图形 debugger
- **2010s**:RenderDoc 开源(2013)、PIX 回归(D3D12)、apitrace 成熟
- **2020s**:Vulkan validation layer(LunarG)、WebGPU Inspector、Nsight Aftermath(崩溃后调试)

**趋势**:工具越来越智能,自动检测常见 bug(uniform 未设、绑定点冲突、纹理未上传)。但**根本方法论不变**:抓帧 + 像素追踪 + 单步。

### Lv1 · 概念辨析

**题**:fragment shader 里没有 `printf`,你有 5 个常见 debug 方法:(a) debug output callback,(b) imageStore 到 SSBO,(c) 改 fragment 输出当颜色,(d) Shader Debugger,(e) 改 shader 然后重新抓帧。每种方法的优缺点是什么?什么场景用哪个?

**参考解答**:

| 方法 | 优点 | 缺点 | 何时用 |
|---|---|---|---|
| debug output callback | 实时,无开销 | 只能输出字符串,无结构化数据 | 验证 shader 是否执行到某点 |
| imageStore 到 SSBO | 大批量结构化数据 | 需要额外代码 + 同步 | 收集每个 fragment 的中间值做统计分析 |
| 改 fragment 当颜色 | 最快 | 只能看 0-1 范围,精度低 | 快速验证假设(uvw 越界、uniform 错) |
| Shader Debugger | 精确,可单步 | 慢,只能看一个 fragment | 定位"具体哪个值开始错" |
| 改 shader + 重新抓帧 | 任何调试 | 慢,要重编译重抓帧 | 改完 bug 验证修复 |

### Lv2 · 动手实践

**题**:写一个最小的 Rust + glow 程序,创建一个 4×4×4 的 RGBA8 3D texture,每个 cell 存它的 `(x, y, z)` 坐标当颜色(归一化到 [0,1])。然后**写一个 fragment shader**,在一个全屏 quad 上,**采样 texture 中心点(uvw = (0.5, 0.5, 0.5))**,把采样结果输出到屏幕。

预期:屏幕是浅紫色(R=0.5, G=0.5, B=0.5)——纹理中心点的颜色。

完成标准:
- 程序跑起来显示一个窗口
- 屏幕颜色接近 (128, 128, 128)(0-255 范围)
- 修改 uvw 为 (0.0, 0.0, 0.0),屏幕变黑色;uvw 为 (1.0, 1.0, 1.0),屏幕变白色

**参考解答**:这个练习的关键是**理解 uvw 怎么映射到 cell**。OpenGL 的 `LINEAR` 采样用 `uvw * (size - 1)` 找到 cell 边界。uvw = 0.5 在 4×4×4 texture 上对应 cell 1.5(在 cell 1 和 cell 2 之间),trilinear 插值得到平均。

```rust
// 关键 shader
const FRAG: &str = r#"
#version 430
out vec4 fragColor;
uniform sampler3D uTex;
uniform vec3 uUvw;
void main() {
    vec4 c = texture(uTex, uUvw);
    fragColor = c;
}
"#;

// Rust 端填 texture 数据
let mut data = vec![0u8; 4 * 4 * 4 * 4];  // RGBA8,4x4x4 cells
for z in 0..4 {
    for y in 0..4 {
        for x in 0..4 {
            let i = (x + y * 4 + z * 16) * 4;
            data[i]   = (x as f32 / 3.0 * 255.0) as u8;  // R
            data[i+1] = (y as f32 / 3.0 * 255.0) as u8;  // G
            data[i+2] = (z as f32 / 3.0 * 255.0) as u8;  // B
            data[i+3] = 255;                              // A
        }
    }
}

// 上传
unsafe {
    gl.bind_texture(glow::TEXTURE_3D, Some(texture));
    gl.tex_image_3d(
        glow::TEXTURE_3D, 0, glow::RGBA8 as i32,
        4, 4, 4, 0,
        glow::RGBA, glow::UNSIGNED_BYTE,
        glow::PixelUnpackData::Slice(Some(&data)),
    );
    gl.tex_parameter_i32(glow::TEXTURE_3D, glow::TEXTURE_MIN_FILTER, glow::LINEAR as i32);
    gl.tex_parameter_i32(glow::TEXTURE_3D, glow::TEXTURE_MAG_FILTER, glow::LINEAR as i32);
    gl.tex_parameter_i32(glow::TEXTURE_3D, glow::TEXTURE_WRAP_S, glow::CLAMP_TO_EDGE as i32);
    gl.tex_parameter_i32(glow::TEXTURE_3D, glow::TEXTURE_WRAP_T, glow::CLAMP_TO_EDGE as i32);
    gl.tex_parameter_i32(glow::TEXTURE_3D, glow::TEXTURE_WRAP_R, glow::CLAMP_TO_EDGE as i32);
}
```

### Lv3 · 迁移设计

**题**:你被要求做一个**2D LUT 颜色校正**——一张 32×32 的 texture 存"输入颜色 → 输出颜色"的映射。Fragment shader 拿当前像素的亮度 L ∈ [0,1] 作为 v 坐标,u=0.5,采样 LUT 得到校正后的颜色。如果某像素采样出**完全错的颜色**(比如红色变绿),你的 debug 步骤是什么?列出至少 5 个可疑点。

**提示**:
- LUT 上传对不对?(数据是不是按你以为的格式)
- v 坐标算对不对?(L 是不是真的在 [0,1])
- LUT 内部数据对不对?(用 glGetTexSubImage 验证)
- texture filter 对不对?(LINEAR 还是 NEAREST)
- wrap mode 对不对?(v 接近 0 或 1 时怎么处理)

### 完整 Pixel-level debug 流程

下面是 Day 408 教你的完整工作流,**可重复用于任何 fragment shader bug**。

```rust
// src/debug/pixel_debug.rs
use glow::HasContext;

/// 启用 OpenGL debug output
/// 让 GL 把所有 warning/error 通过 callback 推到 Rust
pub fn enable_gl_debug(gl: &glow::Context) {
    unsafe {
        gl.enable(glow::DEBUG_OUTPUT);
        gl.debug_message_callback(|_src, ty, id, sev, msg| {
            // ty 标识来源(SHADER / DEPRECATED behavior / OTHER 等)
            // sev 标识严重程度(HIGH / MEDIUM / LOW / NOTIFICATION)
            let sev_str = match sev {
                glow::DEBUG_SEVERITY_HIGH => "HIGH",
                glow::DEBUG_SEVERITY_MEDIUM => "MED",
                glow::DEBUG_SEVERITY_LOW => "LOW",
                _ => "NOTIFY",
            };
            // 只打印 MED 以上,NOTIFICATION 太烦
            if sev != glow::DEBUG_SEVERITY_NOTIFICATION {
                println!("[GL {} ty={} id={}] {}", sev_str, ty, id, msg);
            }
        });
        println!("[debug] OpenGL debug output enabled");
    }
}

/// 把任意 vec3 中间值当颜色输出,快速看分布
pub fn debug_shader_value_as_color() -> &'static str {
    // 在你的 fragment shader 里加一个 debug uniform:
    // uniform int uDebugMode;  // 0=正常, 1=显示 uvw, 2=显示法线, 3=显示世界坐标
    //
    // vec3 final_color;
    // if (uDebugMode == 0) final_color = compute_lighting();
    // else if (uDebugMode == 1) final_color = uvw;
    // else if (uDebugMode == 2) final_color = normalize(vNormal) * 0.5 + 0.5;
    // else if (uDebugMode == 3) final_color = vWorldPos / 10.0;
    // fragColor = vec4(final_color, 1.0);
    r#"
#version 430
in vec3 vWorldPos;
in vec3 vNormal;
out vec4 fragColor;
uniform sampler3D uVoxelTex;
uniform vec3 uGridMin;
uniform vec3 uGridMax;
uniform int uDebugMode;  // 0=正常, 1=uvw, 2=法线, 3=世界坐标, 4=uvw 越界高亮

void main() {
    vec3 uvw = (vWorldPos - uGridMin) / (uGridMax - uGridMin);

    if (uDebugMode == 0) {
        // 正常渲染
        vec3 light = texture(uVoxelTex, uvw).rgb;
        fragColor = vec4(light, 1.0);
    } else if (uDebugMode == 1) {
        // 显示 uvw(越界会被 wrap/clamp,所以能看到异常)
        fragColor = vec4(uvw, 1.0);
    } else if (uDebugMode == 2) {
        // 显示法线([-1,1] 映射到 [0,1])
        fragColor = vec4(normalize(vNormal) * 0.5 + 0.5, 1.0);
    } else if (uDebugMode == 3) {
        // 显示世界坐标(除 32 归一化)
        fragColor = vec4(vWorldPos / 32.0, 1.0);
    } else if (uDebugMode == 4) {
        // 越界高亮:uvw 任一分量 <0 或 >1 时红色
        bool out_of_bounds = any(lessThan(uvw, vec3(0.0))) || any(greaterThan(uvw, vec3(1.0)));
        if (out_of_bounds) {
            fragColor = vec4(1.0, 0.0, 0.0, 1.0);  // 红色
        } else {
            vec3 light = texture(uVoxelTex, uvw).rgb;
            fragColor = vec4(light, 1.0);
        }
    }
}
"#
}

/// 在 Rust 端切换 debug mode(用 keyboard)
pub fn handle_debug_keys(gl: &glow::Context, program: glow::Program, key_pressed: u32, debug_mode: &mut i32) {
    // 假设 1/2/3/4/5 键切换 debug mode
    let new_mode = match key_pressed {
        1 => 0,  // 正常
        2 => 1,  // uvw
        3 => 2,  // 法线
        4 => 3,  // 世界坐标
        5 => 4,  // 越界高亮
        _ => return,
    };
    *debug_mode = new_mode;
    unsafe {
        let loc = gl.get_uniform_location(program, "uDebugMode");
        if loc >= 0 {
            gl.uniform_1_i32(Some(loc), new_mode);
        }
    }
    println!("[debug] debug mode = {}", new_mode);
}
```

- `uvw 在 fragment shader 里全是 0`:varying `vWorldPos` 没从 vertex shader 正确传递。检查 vertex shader 是否写了 `out vec3 vWorldPos`。
