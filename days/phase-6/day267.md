
# Day 267 · 加逐元素裁剪矩形

> Top Clocks 视图有很多文字和进度条,如果它们超出"视图区域"就会画到按钮上。今天 Casey 给每个 UI 元素加一个**裁剪矩形**(clip rect),超出范围的像素直接丢弃——这是所有 UI 框架的基本功,也是 GPU scissor test 的前身。

## 0 · 为什么要有这一天

你的 Top Clocks 视图能显示前 20 名条目,每条占 20 像素高。如果某次刷新结果有 30 个条目,你画前 20 个时第 20 个的进度条会**超出视图底部**——画到下面的滑块上。屏幕看起来错乱:进度条压在滑块上,鼠标交互错位。

更糟糕的情况是文字。Top Clocks 里函数名可能很长(如 `render_entity_with_particles`),如果文字渲染没截断,会一直画到屏幕右边,挡住其他 UI。

解决这类问题的标准方案是**裁剪矩形**(clip rectangle,也叫 scissor rect):告诉绘制原语"只能在 (x, y, w, h) 这个矩形内画,超出部分丢弃"。

这是一个看似简单但实现上要小心的功能:

1. **每个元素有自己的 clip rect**:按钮的 clip 是按钮矩形,Top Clocks 视图的 clip 是视图矩形
2. **clip 可以嵌套**:视图内的进度条,clip = 视图 rect ∩ 进度条 rect
3. **clip 影响所有原语**:画矩形、画线、画文字都要检查 clip

实现 clip 有两种方式:

- **软件裁剪**:每个 draw 函数内部判断 clip,超出的像素不写
- **硬件裁剪**:GPU 的 scissor test,显卡自动丢弃超出范围的像素

HH 今天做软件裁剪(还在 CPU 渲染阶段),Day 270+ 切到 OpenGL 后改用 GPU scissor。

心理锚点:做完这个,你的 UI 不会再"画到外面",所有元素都规规矩矩待在自己的区域里。

## 1 · Casey 今天做了什么

Casey 给所有绘制原语加了 clip rect 参数:

1. `draw_rect(buffer, ..., clip: Rect)` ——画矩形时每个像素检查是否在 clip 内
2. 引入"当前 clip"栈(`stack<Rect>`),push 一个新 clip 后所有绘制用它,pop 后恢复
3. Top Clocks 视图先 push 自己的 view_rect 作为 clip,然后画进度条和文字——超出自动被裁剪
4. 按钮、滑块等控件也用同样的机制(它们自己的 rect 作为 clip)

Casey 在视频里演示了一个关键 trick:**clip 的交集**。当 Top Clocks 视图里有进度条,进度条的 clip 不是它自己的 rect,而是 `view_clip ∩ progress_rect`——这样既不会画到视图外,也不会画到进度条外。

最后 Casey 优化了性能:**先做矩形相交测试**,如果 clip 和 draw rect 完全不相交,直接 return 不画。这是"early-out"优化,避免每个像素都做边界判断。

## 2 · 心智模型

### 类比:窗户外的风景

想象你站在屋内,透过一扇窗户看外面。窗外有山、有树、有人——但你能看到的**只是窗户框里的部分**。窗外的物体本身没变,只是你的视野被窗户限制了。

UI clip 就是这扇"窗户"。屏幕上所有内容都存在,但每个 UI 元素只能"看到"自己 clip 矩形内的像素。画出去的部分被窗户框挡住,不显示。

更精细的类比:**套娃式窗户**。一个大窗户里有几个小窗户,每个小窗户的视野更窄。UI 的嵌套 clip 就是这种结构。

### 严谨原理:矩形相交(Intersection)

两个矩形 A 和 B 的相交,是一个新矩形 C:

```
C.x = max(A.x, B.x)
C.y = max(A.y, B.y)
C.right = min(A.x + A.w, B.x + B.w)
C.bottom = min(A.y + A.h, B.y + B.h)
C.w = max(0, C.right - C.x)
C.h = max(0, C.bottom - C.y)
```

如果 `C.w == 0` 或 `C.h == 0`,说明不相交(取 max(0, ...) 保证非负)。

```rust
fn intersect(a: Rect, b: Rect) -> Rect {
    let x = a.x.max(b.x);
    let y = a.y.max(b.y);
    let right = (a.x + a.w).min(b.x + b.w);
    let bottom = (a.y + a.h).min(b.y + b.h);
    let w = (right - x).max(0);
    let h = (bottom - y).max(0);
    Rect { x, y, w, h }
}
```

这是计算机图形学的基础算法,几乎所有 2D 引擎都要实现。

### 像素级 clip 的两种实现

#### 方式 1:per-pixel 检查

```rust
fn draw_rect(buffer: &mut [u32], buf_w: usize, buf_h: usize, r: Rect, clip: Rect, color: u32) {
    for py in r.y..(r.y + r.h) {
        for px in r.x..(r.x + r.w) {
            // 检查像素是否在 clip 内
            if px >= clip.x && px < clip.x + clip.w
                && py >= clip.y && py < clip.y + clip.h
            {
                if px >= 0 && (px as usize) < buf_w && py >= 0 && (py as usize) < buf_h {
                    buffer[(py as usize) * buf_w + (px as usize)] = color;
                }
            }
        }
    }
}
```

简单直接,但每个像素都要 4 个比较 + 2 个 range check。对 100x100 的矩形是 40 万次比较。

#### 方式 2:预先 intersect 矩形

```rust
fn draw_rect(buffer: &mut [u32], buf_w: usize, buf_h: usize, r: Rect, clip: Rect, color: u32) {
    // 先求交集
    let ir = intersect(r, clip);
    if ir.w == 0 || ir.h == 0 { return; }  // early-out

    // 只画交集内的像素
    for py in ir.y.max(0)..(ir.y + ir.h).min(buf_h as i32) {
        for px in ir.x.max(0)..(ir.x + ir.w).min(buf_w as i32) {
            buffer[(py as usize) * buf_w + (px as usize)] = color;
        }
    }
}
```

预先 intersect 后,内部循环不需要 per-pixel clip check——交集内的像素一定在 clip 内。这是 O(intersect_area) 而不是 O(rect_area),完全不相交时是 O(1)。

Casey 选方式 2,这是工业级的标准实现。

### Clip 栈

嵌套 UI(视图内有按钮,按钮内有文字)需要"clip 栈":

```rust
struct DrawContext {
    clip_stack: Vec<Rect>,
}

impl DrawContext {
    fn push_clip(&mut self, rect: Rect) {
        let new_clip = if let Some(&current) = self.clip_stack.last() {
            intersect(current, rect)  // 取交集
        } else {
            rect
        };
        self.clip_stack.push(new_clip);
    }
    fn pop_clip(&mut self) {
        self.clip_stack.pop();
    }
    fn current_clip(&self) -> Rect {
        *self.clip_stack.last().unwrap_or(&FULL_SCREEN_RECT)
    }
}
```

每次 push_clip 取当前 clip 和新 rect 的交集,这样嵌套越深,clip 越小。这是 HTML CSS overflow / Qt QClipRegion / GPU scissor stack 的标准做法。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏 UI 的 clip 有几个常见场景:

1. **滚动列表**:背包有 100 个物品,屏幕只能显示 10 个。clip = 列表可见区域,超出部分被裁
2. **下拉菜单**:菜单弹出时不应该挡住下面的内容,用 clip 限制
3. **小地图**:小地图是一个 200×200 的窗口,大地图内容超出要裁
4. **HUD 弧形血条**:血条不是矩形,但 clip 配合 mask 可以做出弧形效果

游戏引擎的 UI 系统(Unreal UMG / Unity Canvas / Godot Control)都有 clip 配置:`ClipChildren = true` 表示子元素超出父元素时裁剪。

### 3.2 · 🎨 图形学视角

GPU 渲染管线有专门的 clip 阶段:

1. **Vertex shader 后**:三角形顶点先做 view-frustum clip(视锥裁剪),完全在视锥外的三角形丢弃
2. **Rasterization 前**:三角形做 scissor test,基于 `glScissor(x, y, w, h)` 设置的矩形裁剪
3. **Pixel shader 后**:stencil test / depth test 进一步过滤像素

`glScissor` 是 OpenGL 的标准 API,签名:

```c
void glScissor(GLint x, GLint y, GLsizei width, GLsizei height);
```

调用后,所有 draw call 的像素写入只在 内。Casey 后面切到 OpenGL 后会用这个 API,今天的软件 clip 就是它的 CPU 版模拟。

OpenGL 还有 `glEnable(GL_SCISSOR_TEST)` / `glDisable(GL_SCISSOR_TEST)` 控制 clip 开关,因为 GPU clip 也有少量开销,不需要时关掉。

### 3.3 · 🐧 Linux 系统编程视角

X11 / Wayland 上的窗口本身就受"屏幕 clip"约束:

- 一个窗口的绘制只在自己 window rect 内有效,超出部分 X server 自动丢弃
- 子窗口(parent-child)的 clip 是父窗口 clip ∩ 自己 rect
- X11 的 `XSetClipMask` / `XSetClipRectangles` 让 GC(graphics context)只画在指定矩形内

这些 API 思想完全一致:**clip 是图形绘制的基本能力,从硬件到软件全栈都有**。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 clip 几个风格:

#### 风格 1:函数参数

```rust
fn draw_rect(buf: &mut [u32], w: usize, h: usize, r: Rect, clip: Rect, color: u32);
fn draw_text(buf: &mut [u32], w: usize, h: usize, s: &str, x: i32, y: i32, clip: Rect);
```

每个 draw 函数都加 clip 参数,简单但啰嗦。

#### 风格 2:DrawContext 对象

```rust
struct Ctx<'a> {
    buf: &'a mut [u32],
    w: usize,
    h: usize,
    clip_stack: Vec<Rect>,
}

impl<'a> Ctx<'a> {
    fn draw_rect(&mut self, r: Rect, color: u32) {
        // 用 self.clip_stack.last() 作为 clip
    }
    fn draw_text(&mut self, s: &str, x: i32, y: i32) {
        // 用 self.clip_stack.last()
    }
    fn with_clip<R>(&mut self, clip: Rect, f: impl FnOnce(&mut Self) -> R) -> R {
        let new_clip = intersect(*self.clip_stack.last().unwrap(), clip);
        self.clip_stack.push(new_clip);
        let result = f(self);
        self.clip_stack.pop();
        result
    }
}
```

`with_clip` 是 RAII 风格的 clip push/pop,确保 pop 一定执行(即使闭包 panic)。这是 Rust 表达"作用域内有效资源"的惯用法。

#### 风格 3:Iterator + filter

```rust
fn pixels_in(r: Rect, clip: Rect) -> impl Iterator<Item = (i32, i32)> {
    let ir = intersect(r, clip);
    (ir.y..ir.y + ir.h).flat_map(move |y| {
        (ir.x..ir.x + ir.w).map(move |x| (x, y))
    })
}
```

函数式风格,优雅但迭代器嵌套编译器可能不会优化到完美。

### 3.5 · 几何算法:矩形运算

矩形运算在图形学里有几个核心 API:

- **intersect(A, B)**:今天的主角
- **union(A, B)**:包含 A 和 B 的最小矩形
- **contains(A, point)**:点是否在矩形内
- **overlaps(A, B)**:两矩形是否相交(布尔版)
- **subtract(A, B)**:A 减去 B 的区域(可能产生 4 个矩形)

这些是 2D 引擎的基础设施。Casey 在后面做 tile-based rendering、scrolling、视锥裁剪时都用得到。

| 系统 | clip 形状 | 实现 |
|---|---|---|
| HH(今天) | 矩形 | 软件预先 intersect |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 选择"预先 intersect 再画"而不是"per-pixel 边界检查"?给出至少 3 个理由。

**参考解答**:
1. **性能**:预先 intersect 后内部循环不需要边界判断,100x100 矩形从 40 万次比较减少到 0(完全不相交时)
2. **缓存友好**:预先 intersect 后访问的像素是连续的小矩形,cache hit 高;per-pixel 检查也是连续但分支预测失败率高
3. **代码清晰**:intersect 是独立函数,可单独测试;per-pixel 检查散在 draw 函数内,逻辑混合
4. **早返回优化**:intersect 后如果 w=0 或 h=0,直接 return 不画,完全不相交的元素 0 开销
5. **支持嵌套**:clip_stack 配合 intersect 自然支持嵌套(取交集),per-pixel 检查要每层都判断,代码复杂

### Lv2 · 动手实践

**题**:实现 `intersect(a: Rect, b: Rect) -> Rect`,并在 draw_rect 里用它做 clip。

测试:

- `intersect(Rect{0,0,100,100}, Rect{50,50,100,100})` 应该返回 `Rect{50,50,50,50}`
- `intersect(Rect{0,0,100,100}, Rect{200,200,50,50})` 应该返回 `Rect{?,?,0,0}`(不相交)
- `intersect(Rect{0,0,100,100}, Rect{0,0,100,100})` 应该返回 `Rect{0,0,100,100}`(完全重合)

完成标准:三个测试通过。

**参考解答**:

```rust
#[derive(Clone, Copy, Debug, PartialEq)]
struct Rect { x: i32, y: i32, w: i32, h: i32 }

fn intersect(a: Rect, b: Rect) -> Rect {
    let x = a.x.max(b.x);
    let y = a.y.max(b.y);
    let right = (a.x + a.w).min(b.x + b.w);
    let bottom = (a.y + a.h).min(b.y + b.h);
    let w = (right - x).max(0);
    let h = (bottom - y).max(0);
    Rect { x, y, w, h }
}

fn draw_rect(buf: &mut [u32], buf_w: usize, buf_h: usize, r: Rect, clip: Rect, color: u32) {
    let ir = intersect(r, clip);
    if ir.w == 0 || ir.h == 0 { return; }

    for py in ir.y.max(0)..(ir.y + ir.h).min(buf_h as i32) {
        for px in ir.x.max(0)..(ir.x + ir.w).min(buf_w as i32) {
            buf[(py as usize) * buf_w + (px as usize)] = color;
        }
    }
}

fn main() {
    // 测试 1: 部分相交
    let r = intersect(Rect{x:0,y:0,w:100,h:100}, Rect{x:50,y:50,w:100,h:100});
    assert_eq!(r, Rect{x:50,y:50,w:50,h:50});
    println!("Test 1 OK: {:?}", r);

    // 测试 2: 完全不相交
    let r = intersect(Rect{x:0,y:0,w:100,h:100}, Rect{x:200,y:200,w:50,h:50});
    assert_eq!(r.w, 0);
    assert_eq!(r.h, 0);
    println!("Test 2 OK: {:?} (w=0, h=0)", r);

    // 测试 3: 完全重合
    let r = intersect(Rect{x:0,y:0,w:100,h:100}, Rect{x:0,y:0,w:100,h:100});
    assert_eq!(r, Rect{x:0,y:0,w:100,h:100});
    println!("Test 3 OK: {:?}", r);

    // 测试 4: draw_rect 用 clip
    let mut buf = vec![0u32; 100 * 100];
    draw_rect(&mut buf, 100, 100,
              Rect{x:0,y:0,w:50,h:50},
              Rect{x:30,y:30,w:50,h:50},
              0xFFFFFFFF);
    // 应该只有 (30,30)-(50,50) 这个 20x20 区域被画
    let painted = buf.iter().filter(|p| **p == 0xFFFFFFFF).count();
    assert_eq!(painted, 20 * 20);
    println!("Test 4 OK: {} pixels painted", painted);
}
```

**每行解释**:
- `(right - x).max(0)` 用 max(0) 处理不相交时的负数情况
- `if ir.w == 0 || ir.h == 0 { return; }` 是 early-out 优化
- 内层循环用 `ir.x.max(0)` 而不是 `r.x.max(0)`,因为 ir 已经是交集,可能在 buf 范围外(被 ir 处理过边界,但 buf 越界还要 check)

```rust
}

impl<'a> Ctx<'a> {
    fn new(buf: &'a mut [u32], w: usize, h: usize) -> Self {
        let mut ctx = Self {
            buf, w, h,
            clip_stack: Vec::with_capacity(8),
        };
        // 初始 clip = 全屏
        ctx.clip_stack.push(Rect::new(0, 0, w as i32, h as i32));
        ctx
    }

    fn current_clip(&self) -> Rect {
        *self.clip_stack.last().unwrap()
    }

    fn push_clip(&mut self, rect: Rect) {
        let new_clip = intersect(self.current_clip(), rect);
        self.clip_stack.push(new_clip);
    }

    fn pop_clip(&mut self) {
        if self.clip_stack.len() > 1 {
            self.clip_stack.pop();
        }
    }

    /// RAII 风格的 clip push/pop
    fn with_clip<R>(&mut self, rect: Rect, f: impl FnOnce(&mut Self) -> R) -> R {
        self.push_clip(rect);
        let result = f(self);
        self.pop_clip();
        result
    }

    fn draw_rect(&mut self, r: Rect, color: u32) {
        let clip = self.current_clip();
        let ir = intersect(r, clip);
        if ir.w == 0 || ir.h == 0 { return; }

        for py in ir.y.max(0)..(ir.y + ir.h).min(self.h as i32) {
            for px in ir.x.max(0)..(ir.x + ir.w).min(self.w as i32) {
                self.buf[(py as usize) * self.w + (px as usize)] = color;
            }
        }
    }
}

fn main() {
    let mut window = Window::new(
        "Clip Rect Demo", WIDTH, HEIGHT,
        WindowOptions::default(),
    ).expect("Failed to open window");

    let mut buffer = vec![0u32; WIDTH * HEIGHT];
    let mut frame = 0u32;

    while window.is_open() && !window.is_key_down(Key::Escape) {
        // 清屏
        for px in buffer.iter_mut() { *px = 0xFF101010; }

        let mut ctx = Ctx::new(&mut buffer, WIDTH, HEIGHT);

        // 画一个视图区域(蓝色边框)
        let view_rect = Rect::new(100, 100, 600, 300);
        ctx.draw_rect(view_rect, 0xFF202020);

        // 进入视图 clip,画一些会超出视图的内容
        ctx.with_clip(view_rect, |ctx| {
            // 这条进度条会超出视图右边
            let long_bar = Rect::new(50, 150, 1000, 30);
            ctx.draw_rect(long_bar, 0xFF4040FF);
            // 实际只画 (100, 150) - (700, 180) 这一段

            // 嵌套 clip:进度条内部的子元素
            ctx.with_clip(Rect::new(150, 160, 200, 10), |ctx| {
                ctx.draw_rect(Rect::new(100, 160, 1000, 10), 0xFFFF4040);
                // 这个红色块只画 (150, 160) - (350, 170)
            });

            // 文字行,模拟 Top Clocks 的多行
            for i in 0..30 {
                let y = 200 + i as i32 * 15;
                let line = Rect::new(80, y, 1000, 12);
                let color = if i % 2 == 0 { 0xFF404040 } else { 0xFF505050 };
                ctx.draw_rect(line, color);
                // 超出视图底部(>400)的行被自动裁剪
            }
        });

        // 在视图外画一个对比矩形(不被视图 clip 影响)
        ctx.draw_rect(Rect::new(50, 50, 700, 30), 0xFF804020);

        window.update_with_buffer(&buffer, WIDTH, HEIGHT).unwrap();
        frame += 1;

        if frame % 60 == 0 {
            println!("Frame {}, clip stack depth max = OK", frame);
        }
    }
}
```

**关键 Rust 特性解释**:

- `Ctx<'a>` 用 lifetime 参数绑定 buffer 的生命周期,确保 Ctx 不超过 buffer
- `Vec::with_capacity(8)` 预分配 clip 栈容量,避免 push 时 realloc
- `with_clip` 接受 `impl FnOnce(&mut Self) -> R`,任何闭包都可以,自动 pop
- `self.clip_stack.last().unwrap()` 安全,因为构造时已经 push 一个全屏 clip
- `pop_clip` 的 `if len > 1` 保护,防止把初始全屏 clip 也 pop 掉

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
