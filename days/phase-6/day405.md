# Day 405 · 用片段 shader 让直播崩溃

> Casey 在直播写 fragment shader 时,**程序崩溃了**——直播中断。这是个真实事故,被观众全程录制。今天他重现崩溃,用工具定位**根因**——shader 写法引发的 GPU 驱动 bug 或 GPU hang。这集是"事故调查"(postmortem),真实工程的宝贵经验——展示**生产环境崩溃的完整 debug 流程**。

## 0 · 为什么要有这一天

让我先描述这个真实场景。Casey 在 Day 405 的直播中写 shader。他写完一个 fragment shader,跑起来,期望看到一个特效。结果:

- 画面卡住 1-2 秒不动
- 整个桌面冻结(其他窗口也不响应)
- 2 秒后,游戏窗口消失
- Windows 任务栏弹出"显示驱动停止响应,已恢复"

这是 **GPU TDR**(Timeout Detection and Recovery)——Windows 检测到 GPU 任务超过 2 秒,认为驱动挂起,强制重置 GPU 驱动。Linux 上等价机制是 **GPU reset**(Mesa + DRM 内核驱动)。

直播观众纷纷在聊天室报告同样崩溃——**不是 Casey 机器特例**。这意味着是 shader bug,不是环境问题。

图形程序的崩溃类型:

**GPU hang**(GPU 挂起):shader 死循环(while(true))让 GPU 卡死。GPU 没有"中断"机制——一旦 shader 启动,必须等它跑完。如果它进入死循环,整个 GPU 卡死,所有应用都受影响。

**OOM**(Out of Memory):分配过大纹理 / buffer 耗尽显存。GPU 显存通常 4-16 GB,大场景 + 高分辨率纹理容易爆。

**Driver crash**:GPU 驱动 bug,触发蓝屏 / TDR / kernel panic。驱动是复杂软件(几百万行代码),任何 shader 写法都可能触发角落 case bug。

**Validation error**:OpenGL / Vulkan 用法错(类型不匹配、绑定点冲突、未初始化资源)。Vulkan 的 validation layer 能在运行时检测大部分这种错。

**Casey 今天的崩溃属于 GPU hang**——shader 内的某个循环可能上界无限大,触发 GPU 长时间执行。

**调试思路**:

1. **简化复现**:最小化 shader 触发崩溃(把 shader 逐步删减)
2. **隔离**:换 GPU(AMD / NVIDIA / Intel)看是否相同。如果只在一个厂商崩,是 driver bug
3. **驱动更新**:试不同驱动版本(Mesa main vs stable)
4. **替代写法**:用等价但不同形式的 shader,看是否绕开 bug

**学完今天,你应该能**:

- 区分 CPU 崩溃(segfault、panic)和 GPU 崩溃(TDR、reset、driver crash)
- 用 `dmesg`、kernel log、TDR log 诊断 GPU 崩溃
- 理解 GPU 编程的核心约束:有界循环、无递归、有限时间
- 解释 TDR 机制为什么存在(防止一个坏 shader 锁死整个系统)
- 应对"不可复现"的崩溃——加 logging、try/catch GPU 操作、用 validation layer
- 写"防御性" shader——所有循环有界、所有数组索引 clamp、所有除法检查零
- 用 Mesa / Vulkan validation layer 提前发现 shader bug
- 报告 GPU driver bug 给 Mesa / NVIDIA / AMD(Minimal reproducer 是关键)

**今天的方法论价值**:**生产环境 debug 心态**。直播崩溃是商业游戏发布的灾难——如果 Casey 在 Steam 发布后崩溃,差评轰炸、退款、声誉损失。学会在直播环境(高压、有观众、时间紧)debug,是高级工程师的能力。

### 为什么 GPU 编程特殊

让我深度剖析 GPU 编程的独特约束。

**CPU 代码**:
- 能 panic / segfault,操作系统接管
- 能 SIGINT / Ctrl+C,优雅退出
- 能调试器断点,逐步看变量
- 内存保护(MMU),越界 = segfault 不 = 全局崩溃

**GPU shader**:
- 不能 panic,GPU 没有"异常"概念
- 不能中断(用户层)——一旦启动必须跑完
- 不能设断点(传统 API),只能 `printf` (GLSL `debugPrintfEXT`)
- 没 MMU 保护,越界访问 = 未定义行为,可能崩溃整 GPU

**为什么 GPU 没"中断"**?

GPU 在**数千个并行 thread**上运行同一 shader。如果允许中断:

1. **同步问题**:某些 thread 完成,某些没完成,无法继续下一阶段(render pass 需要 all-or-nothing)
2. **资源锁定**:GPU 不能在 shader 中间释放资源(texture binding、framebuffer state)
3. **OS 检测**:OS 用**整个 GPU**的超时(TDR,2 秒)→ 整 GPU reset,不是单个 shader

所以 GPU shader 必须**自己保证终止**——有界循环、无递归、明确退出条件。这是 GPU 编程的核心约束,**新人最容易忽视**。

工业案例:

- **Cyberpunk 2077 发售崩溃**:大量玩家报告 GPU crash。原因:shader 在某些场景死循环。CD Projekt Red 几周内推出多个 patch。
- **Star Citizen 长跑崩溃**:玩家玩几小时后 GPU driver crash。原因:shader 累积浮点误差,某些值变 NaN,触发 driver bug。
- **Minecraft RTX崩溃**:某些 ray tracing shader 在特定几何下崩溃。社区 workaround:关闭某些特效。

每次都是 GPU 编程独特约束的代价。**学会 GPU 安全编程**让你避免成为下一个案例。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 流程:

**第一,重现崩溃**。在直播中跑某 shader,崩溃。Casey 录下来,之后回放分析。

**第二,简化**。逐步删除 shader 代码,找到**最小崩溃版本**——只保留触发崩溃的核心逻辑。这一步关键——原 shader 可能几百行,但崩溃只需要 10 行。最小化让根因清晰。

**第三,测试不同 GPU**。直播观众报告:

- AMD GPU:崩
- NVIDIA GPU:不崩
- Intel GPU:部分崩

这指向**driver bug**而非算法 bug——shader 在 AMD 和 Intel 的 driver 实现有角落 case bug。

**第四,诊断**。Casey 发现 shader 里的某个 for 循环可能**上界不是编译时常数**,触发某些 driver 的"unrolled loop"优化,生成有 bug 的机器码。

**第五,修法**。把循环改成有界版本,明确编译时常数上界:

```glsl
// Bad: 上界不是编译时常数
int n = texture(count_tex, uv).r * 1000;
for (int i = 0; i < n; ++i) { ... }

// Good: 编译时常数上界
const int MAX_STEPS = 64;
for (int i = 0; i < MAX_STEPS; ++i) { ... }
```

**第六,验证**。重新跑,无崩溃。在 AMD / NVIDIA / Intel 都通过。

**第七,教训**。Casey 在视频结尾总结:**shader 必须有界循环,GPU 没有"中断"**。这一条规则,所有 GPU 程序员必须记住。

**这集教学价值**:**GPU 编程的安全实践**——shader 不同于 CPU 代码,不能依赖超时 / 异常处理。任何"可能无限"的操作都必须**显式加边界**。这种思维在嵌入式编程、内核开发也有——任何"必须终止"的代码都要显式保证。

## 2 · 心智模型

### 2.1 类比:开车 vs 自动驾驶

CPU 代码像**开车**——你能踩刹车、能停车、能改方向。出问题你重启车。

GPU shader 像**自动驾驶**——一旦启动,你不能中断,只能等它跑完。如果它进入死循环,**整辆车(GPU)**卡死,其他车(其他 shader)等不到。

GPU 的"自动驾驶"必须有**有限路线**(有界循环、有限递归——实际 GLSL 不允许递归)。司机(shader 作者)在发车前必须确认路线终点。

工业类比:**飞行控制软件**(DO-178C 标准)。飞机的飞控代码必须**证明终止**(WCET:Worst-Case Execution Time)。任何可能的死循环都会导致空难。GPU shader 不是飞控,但同样的原则——**必须保证终止**。

### 2.2 严谨原理:GPU Hang / TDR

**TDR**(Timeout Detection and Recovery):Windows 的机制。GPU 任务超过 2 秒(默认)→ Windows 认为 GPU 挂起 → 重置 GPU 驱动 → 应用收到错误。

TDR 的两层:

- **TDR Level 1**(默认):GPU driver 重置,应用收到"device removed"错误,可以重建 context 继续
- **TDR Level 2**(更严重):整个 GPU 重置,所有应用崩溃,需要重启系统

Windows 注册表里可以调 TDR 超时:

```powershell
# 注册表(管理员权限)
# HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\GraphicsDrivers
# TdrLevel: 0=禁用, 1=只检测, 2=检测+恢复(默认), 3=蓝屏
# TdrDelay: 超时秒数(默认 2)
```

**Linux 等价**:

- **AMD**(amdgpu driver):长任务触发 GPU reset,应用收到 DRM error
- **Intel**(i915 driver):同上
- **NVIDIA**(proprietary driver):`NVRM` 错误,driver reset,可能 X server 重启

**查看崩溃日志**:

```bash
# dmesg 看 kernel log
sudo dmesg | grep -i "gpu\|drm\|amdgpu\|i915"
# 崩溃时会有 "GPU reset" / "ring timeout" 等

# 实时监控
sudo dmesg -w | grep -i gpu

# AMD GPU 详细日志
sudo cat /sys/class/drm/card0/device/gpu_reset_count

# 看最近的 GPU 事件
sudo journalctl -k --since "10 minutes ago" | grep -i gpu
```

### 2.3 常见 GPU 崩溃原因

**1. 死循环**

```glsl
// 危险!while 可能死循环
int i = 0;
while (voxel_is_empty(pos)) {
    pos += dir;
    i++;
    if (i > 1000) break;  // 必须有界
}
```

**修法**:用 for 循环,明确上界:

```glsl
for (int i = 0; i < 1000; ++i) {
    if (!voxel_is_empty(pos)) break;
    pos += dir;
}
```

**2. 无限递归**

GLSL 不允许递归(编译器拒绝),但间接递归(通过函数指针,某些扩展允许)可能。Vulkan SPIR-V 允许有限递归,但性能极差。

**3. 数组越界**

```glsl
int arr[16];
int idx = texture(some_tex, uv).r * 1000;  // 可能 > 16
float val = arr[idx];  // 未定义行为,可能崩溃
```

**修法**:clamp 索引:

```glsl
idx = clamp(idx, 0, 15);
```

**4. 整数溢出**

```glsl
uint big = 0xFFFFFFFFu;
big = big * 2;  // 溢出(实际 GLSL wrap,但不直观)
```

**修法**:用 64-bit(uint64_t)或显式检查。

**5. 内存耗尽**

太大纹理 / SSBO,GPU 显存不够,driver 报错或崩溃。

```glsl
// 危险:超大数组
float huge[1000000];  // 编译错或运行时崩
```

**修法**:用 SSBO 或 image,合理大小。

**6. NaN / Inf 传播**

某些 driver 在 NaN 输入时崩溃(虽然 IEEE 754 规定应继续):

```glsl
float v = texture(tex, uv).r;
float inv = 1.0 / v;  // v=0 时 Inf
float neg = log(v);    // v<0 时 NaN
```

**修法**:clamp 输入:

```glsl
v = max(v, 1e-6);
```

### 2.4 Shader 编译器的"沉默错误"

GLSL 编译器有时**不报错**,但 shader 行为异常:

- **未初始化变量**:可能为任意值(虽然 spec 说 undefined,driver 通常清零,但不保证)
- **精度损失**:lowp / mediump 在某些 GPU 上精度不够
- **隐式转换**:int / uint 混用可能 wrap

**Debug 工具**:

```bash
# shader 编译日志
glGetShaderInfoLog(shader, ...);
# 输出 warning / error

# 用 glslangValidator 离线检查
sudo pacman -S glslang
glslangValidator -V my_shader.frag
# -V: Vulkan SPIR-V 输出
# -G: OpenGL SPIR-V 输出
# -l: 链接多个 shader

# Vulkan validation layer
vulkaninfo --summary
VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation ./your_game
```

### 2.5 GPU 驱动 bug

GPU 驱动(GL/Vulkan/D3D 实现)是复杂软件,有 bug。某些 shader 写法触发 driver bug,导致崩溃。

**Mesa**(开源 OpenGL/Vulkan 实现)的 GPU hang bug 通常需要:

- **Minimal reproducer**(最小复现):精简 shader + 简单几何
- **Affected driver version**:具体哪个 Mesa 版本
- **GPU model**:具体显卡型号
- **Stack trace**:崩溃时的 backtrace

**应对**:

- **更新驱动**:厂商修 bug
- **Workaround**:换 shader 写法绕过 bug
- **报告**:提交 bug report 到 Mesa(https://gitlab.freedesktop.org/mesa/mesa)/ NVIDIA / AMD

工业案例:Mesa 2020 年的 radeonsi driver 在某些 SSBO 写法下崩,社区 workaround 是用 image 替代,几周后 Mesa 修复。

### 2.6 Mesa 的 GPU reset 恢复

Mesa 在 Linux 上有 GPU reset 恢复机制:

```bash
# 看 reset 计数
cat /sys/class/drm/card0/device/gpu_reset_count

# 启用 verbose GPU log
echo 1 | sudo tee /sys/module/drm/parameters/debug
dmesg -w | grep -i "drm\|gpu"

# AMD GPU 专门日志
cat /sys/kernel/debug/dri/0/amdgpu_gpu_recover  # 需要 root

# Intel GPU 工具
sudo pacman -S igt-gpu-tools
sudo intel_gpu_top   # 实时 GPU 占用率
sudo intel_gpu_time  # 单帧 GPU 时间
```



## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业界 shader 安全实践:

- **Static loop bounds**:shader 内 for 循环必须有编译时常数上界。Vulkan SPIR-V 强制要求;GLSL 编译器警告
- **No recursion**:GLSL 禁止递归(某些 SPIR-V 允许但性能差)
- **Validation layers**:Vulkan / DX12 有 validation layer,运行时检查
- **CI shader compile**:每次 commit 编译所有 shader,失败拒绝合并
- **GPU vendor CI**:在 AMD / NVIDIA / Intel 三家都跑,确保跨厂商兼容

**商业引擎的 shader 安全**:

**Unreal Engine** 用 HLSL → 中间表示 → 多平台后端(Metal / Vulkan / DX12)。UE 的 shader compiler 检查 loop bounds,warning 如果上界不是常数。

**Unity SRP** 类似,加 Built-in Shader Validator 检查常见错误。

**Bevy** 用 wgsl(WGPU Shading Language),编译时严格检查。Bevy 0.13+ 加了 shader validation pass。

**godot** 用自己的 shader language(类 GLSL),编译时强制 loop bounds。

### 3.2 · 🎨 图形学视角

**Shader 编译 vs 运行时**:

- **编译时**:语法 / 类型检查
- **链接时**:多个 shader stage 的 IO 匹配
- **运行时**:资源绑定 / 数值异常

GLSL 编译器**不能**捕获所有 bug——某些 bug 只在特定输入 / 特定 GPU 触发。

**Driver 编译优化**:

GLSL 进入 driver 后,driver 编译成 GPU-specific 机器码。不同 driver(NVIDIA / AMD / Intel)有不同优化策略,**生成不同机器码**——可能一个有 bug 一个没有。

工业实践:**用 SPIR-V**(Vulkan 的中间表示)绕过 driver 编译。SPIR-V 是规范化的二进制,driver 只做机器码生成,不做语义优化。bug 更可重现。

### 3.4 · 🦀 Rust 生态视角

Rust 端错误处理:

```rust
// glium / wgpu 的 Result 错误传播
fn render(target: &mut glium::Frame) -> Result<(), glium::DrawError> {
    target.draw(...)?;
    Ok(())
}

fn main() {
    let event_loop = glutin::event_loop::EventLoop::new();
    let display = glium::Display::new(...).unwrap();

    event_loop.run(move |event, _, control_flow| {
        if let Event::RedrawRequested(_) = event {
            let mut target = display.draw();
            match render(&mut target) {
                Ok(_) => {}
                Err(e) => {
                    eprintln!("Render error: {:?}", e);
                    // 可能 driver 崩溃,检查 dmesg
                }
            }
            target.finish().unwrap();
        }
    });
}
```

**Panic handler**(进程崩溃时调用):

```rust
fn main() {
    std::panic::set_hook(Box::new(|info| {
        eprintln!("Panic: {}", info);
        // 写崩溃 log 到文件
        std::fs::write("crash.log", format!("{}", info)).ok();

        // 收集 backtrace
        let bt = std::backtrace::Backtrace::force_capture();
        std::fs::write("crash_bt.log", format!("{}\n", bt)).ok();
    }));
    // ...
}
```

**GPU 错误处理的最佳实践**:

1. **每个 GPU 调用都 match Result**,不 `unwrap()`(release 中可能 panic)
2. **Panic handler** 写崩溃日志,方便事后分析
3. **重启策略**:GPU crash 后尝试重建 context,失败则退出
4. **Telemetry**:发布版上报崩溃栈给服务器,追踪稀有 bug

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 GPU shader 不能像 CPU 代码那样有"超时"机制?

**参考解答**:

GPU shader 在**数千个并行 thread**上运行。如果加超时:

1. **同步问题**:某些 thread 完成,某些没完成,无法继续下一阶段
2. **资源锁定**:GPU 不能在 shader 中间释放资源
3. **OS 检测**:OS 用**整个 GPU**的超时(TDR,2 秒)→ 整 GPU reset,不是单个 shader

所以 GPU shader 必须**自己保证终止**——有界循环、无递归、明确退出条件。

CPU 代码可以"试试看,超时取消",GPU 不能。这是 GPU 编程的核心约束。

### Lv2 · 动手实践

**题**:写一个会"卡"GPU 的 shader(while(true) 或极大循环)。**警告**:这会让你的桌面卡几秒。在虚拟终端(Ctrl+Alt+F2)运行,准备好 `pkill` 命令。

```glsl
// 危险 shader,仅用于学习
void main() {
    int sum = 0;
    for (int i = 0; i < 1000000000; ++i) {
        sum += i;  // 巨多迭代
    }
    frag = vec4(float(sum) * 0.000001, 0, 0, 1);
}
```

观察:

- 程序卡住几秒
- 桌面可能冻结
- 可能触发 GPU reset(查 dmesg)

**修法**:用合理循环数(64 / 128)。

### Lv3 · 迁移设计

**题**:GPU shader 限制思路迁移到**嵌入式系统**——你写微控制器代码,没有 OS、没有 MMU、没有 abort。如何保证程序稳定?

需求:

- STM32 / Arduino 等微控制器
- 没有进程隔离,任何 crash 都是物理硬件 crash
- 没有 watchdog 自动恢复(除非显式加)
- 有限 RAM(几 KB 到几 MB)

设计文档:

```rust
// 嵌入式 Rust 的安全实践
#![no_std]
#![no_main]

use panic_halt as handler;  // panic 时停止(不 unwind)

#[arduino_hal::entry]
fn main() -> ! {
    let dp = arduino_hal::Peripherals::take().unwrap();

    // 启用 watchdog timer(WDT)
    dp.WDT.enable_wdt(Timeout::Ms1000);

    loop {
        // 主循环:每次循环必须 < 1 秒
        do_something();
        dp.WDT.feed();  // 重置 watchdog

        // 如果 do_something 卡住,watchdog 1 秒后 reset MCU
    }
}
```

**嵌入式 vs GPU shader 共同点**:

| 维度 | 嵌入式 | GPU shader |
|---|---|---|
| 隔离 | 无(裸金属) | 无(同 GPU 共享) |
| 异常处理 | 无 panic handler | 无 shader exception |
| 超时 | Watchdog timer | TDR / GPU reset |
| 必须保证 | 终止 | 终止 |

写出 5 条嵌入式安全规则,对比 GPU shader 的"必须有界"。

### 安全 shader 加超时检测

```toml
[package]
name = "shader_safety"
version = "0.1.0"
edition = "2021"
[dependencies]
glium = "0.34"
```

```rust
use glium::{glutin, Surface, implement_vertex, program, index};
use std::time::{Duration, Instant};

#[derive(Copy, Clone)]
struct Vertex { position: [f32; 2] }
implement_vertex!(Vertex, position);

fn main() {
    let event_loop = glutin::event_loop::EventLoop::new();
    let wb = glutin::window::WindowBuilder::new()
        .with_inner_size(glutin::dpi::LogicalSize::new(400, 300));
    let cb = glutin::ContextBuilder::new();
    let display = glium::Display::new(wb, cb, &event_loop).unwrap();

    let verts = vec![
        Vertex { position: [-1., -1.] },
        Vertex { position: [ 1., -1.] },
        Vertex { position: [ 0.,  1.] },
    ];
    let vbuf = glium::VertexBuffer::new(&display, &verts).unwrap();
    let indices = index::NoIndices(index::PrimitiveType::TrianglesList);

    // "安全"的 shader:有界循环
    let safe_program = program!(&display,
        330 es => {
            vertex: r#"#version 330
                in vec2 position;
                void main() { gl_Position = vec4(position, 0., 1.); }
            "#,
            fragment: r#"#version 330
                out vec4 frag;
                void main() {
                    int sum = 0;
                    // 有界循环,编译器知道上界
                    for (int i = 0; i < 64; ++i) {
                        sum += i;
                    }
                    frag = vec4(float(sum) / 2000.0, 0.3, 0.5, 1.0);
                }
            "#,
        }).unwrap();

    event_loop.run(move |event, _, control_flow| {
        use glutin::event::{Event, WindowEvent};
        use glutin::event_loop::ControlFlow;
        *control_flow = ControlFlow::Wait;

        if let Event::RedrawRequested(_) = event {
            let start = Instant::now();
            
            let mut target = display.draw();
            target.clear_color(0., 0., 0., 1.0);
            target.draw(&vbuf, &indices, &safe_program,
                &glium::uniforms::EmptyUniforms,
                &Default::default()).unwrap();
            target.finish().unwrap();
            
            let elapsed = start.elapsed();
            if elapsed > Duration::from_millis(100) {
                eprintln!("Warning: Frame took {:?} (check for shader hang)", elapsed);
            }
        }

        if let Event::WindowEvent { event: WindowEvent::CloseRequested, .. } = event {
            *control_flow = ControlFlow::Exit;
        }
    });
}
```

### 进一步展开:从概念到落地的完整路径

要把今天讨论的抽象概念变成可运行的代码,我们必须经历几个具体阶段。这一节展开每一步的工程细节。

**阶段一:定义接口**。Casey 在动手实现前,先想清楚 API。Rust 的 trait 是定义接口的工具:

```rust
trait Sortable {
    fn sort_key(&self) -> u64;
    fn bounds(&self) -> Aabb;
    fn layer(&self) -> u8;
}
```

trait 让代码可测试、可替换。Casey 经常说"先写 trait,再写 impl"——这强迫你思考抽象边界。

**阶段二:单元测试**。每个 sort_rule 分支都应有对应测试:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_basic_ordering() {
        let a = TestEntity { layer: 1, y: 100.0 };
        let b = TestEntity { layer: 1, y: 200.0 };
        assert_eq!(a.sort_key() < b.sort_key(), true);
    }

    #[test]
    fn test_layer_priority() {
        let a = TestEntity { layer: 2, y: 100.0 };
        let b = TestEntity { layer: 1, y: 200.0 };
        // layer 1 优先(a 在 b 后面)
        assert_eq!(a.sort_key() > b.sort_key(), true);
    }
}
```

跑 `cargo test`,所有测试必须通过才能进入下一阶段。

**阶段三:集成测试**。单元测试覆盖单个函数,集成测试覆盖整个系统。游戏里的集成测试通常是"加载场景,跑一帧,截图,对比期望截图"——visual regression test。这是 Casey debug 流程的标准化版本。

**阶段四:性能剖析**。用 `cargo flamegraph` 或 `perf record` 看 CPU 时间花在哪。如果 sort 占 0.5%,不用优化。占 20%,必优化。

```bash

```

**阶段五:跨平台验证**。Linux 测试用 `vulkaninfo | grep "Device name"` 看 GPU;Windows 测试用 dxdiag。同一代码在 Intel / AMD / NVIDIA / Apple Silicon GPU 上可能有微妙差异——精度、driver bug、性能特性。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
