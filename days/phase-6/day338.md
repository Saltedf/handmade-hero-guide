# Day 338 · 模拟空间粒子

> 你屏幕上飞舞的火花永远在"屏幕坐标"里吗?不一定。Casey 今天把粒子从"世界空间"切到"模拟空间"——粒子相对于"模拟原点"(通常是相机或玩家)计算位置,而不是相对世界原点。这一改看似无关痛痒,却把"浮点精度"问题彻底解决,让大世界游戏的粒子永远稳定不抖。

## 0 · 为什么要有这一天

想象你的游戏地图是 10km × 10km。世界坐标原点在地图左下角 (0, 0),右上角是 (10000, 10000)。玩家走到 (7500, 4200),发射一颗火花。

火花的速度是 (1.2, -0.5) m/s。每帧位移:`pos += vel * dt`。在 (7500, 4200) 附近,`pos.x` 是 `7500.0`,加上 `1.2 * 0.016 = 0.0192`,新位置 `7500.019`。

问题:**f32 只有 7 位有效数字**。`7500.019` 实际能表示的精度大约是 `7500.0190430`(误差 ~0.0001)。在 60 FPS 下,这种误差累积起来,**粒子在屏幕上抖动**——你看不见每帧 0.0001 的跳动,但能看见"火花不光滑、有微抖"。

更严重:**远距离渲染**。玩家在 (10000, 0),相机也在那。一个粒子从 (10000, 0) 飞到 (10010, 0)——10 米的位移在 10000 米基础上只有 4 位有效数字,精度 1mm。粒子在屏幕上能看见"格子化"。

业界(所有大世界游戏:GTA、Witcher 3、Star Citizen)的解决方案:**模拟空间**。把粒子相对**相机**(或玩家、某个"参考点")计算,而不是相对世界原点。这样粒子坐标永远在 (0, 0) 附近,f32 精度全保留。

今天 Casey 把粒子系统改成模拟空间——一个看似平凡但解决实际大问题的工程改造。

心理锚点:今天之后你能解释"为什么 f32 在大世界游戏里不够用",知道"相对坐标"和"绝对坐标"的取舍,理解 Casey 把"模拟原点"从世界原点切换到相机/玩家的工程动机。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_particles.cpp` 和 `handmade_world.cpp`,做几件事:

1. **定义"模拟空间"概念**:粒子位置存"相对相机偏移",不是世界绝对坐标
2. **改粒子发射**:发射时记录"相机当时的位置",粒子初始位置 = 世界位置 - 相机位置
3. **改粒子更新**:`pos += vel * dt` 在模拟空间做
4. **改粒子渲染**:渲染时把模拟空间位置加回"当前相机位置",得到世界位置,然后投影
5. **处理相机移动**:相机移动时,所有模拟空间粒子**反向偏移**——保持世界位置不变

最 tricky 的是第 5 点。如果相机从 (1000, 0) 走到 (1010, 0),模拟空间里所有粒子要减去 (10, 0),否则粒子会被相机拖着走。

Casey 写一个 `RecenterSimSpace(camera_pos)` 函数,在每帧开头调用,把所有粒子的模拟空间位置 -= `delta_camera_pos`。

## 2 · 心智模型

### 类比:画在地图上 vs 画在透明纸上

想象你在地图上标记飞船位置。两种方式:

**方式 A(世界空间)**:把飞船画在 1:1000 比例地图上。地图左下角是 (0, 0),右上角 (10000, 10000)。飞船当前在 (7500, 4200)。你拿一支粗笔,笔尖粗 1mm——在 7500 米位置上,1mm 笔粗对应实际 1 米。你想精确到 0.1 米?笔太粗了。

**方式 B(模拟空间)**:拿一张小透明纸,贴在地图上你的当前位置(飞船位置)。透明纸的坐标原点就是飞船位置——纸上的 (0, 0) 是飞船,纸上的 (10, 0) 是飞船右 10 米。你画粒子轨迹,精度全保留(因为纸面坐标只在 ±100 米范围)。

飞船移动时,透明纸跟着移动——但**纸上的画**也要相应反向移动:粒子相对飞船的位置变了,纸上坐标要更新。

这就是模拟空间的核心:**坐标原点是参考点(相机/玩家),粒子相对参考点计算**。

### 数学:f32 精度随距离衰减

IEEE 754 单精度浮点数 f32 的精度分布:

- 0 ~ 1 范围:精度 2^-24 ≈ 0.0000001(7 位有效数字)
- 1 ~ 2:精度 2^-23 ≈ 0.0000001
- 1000 ~ 2000:精度 2^-13 ≈ 0.0001
- 10000 ~ 20000:精度 2^-10 ≈ 0.001
- 100000 ~ 200000:精度 2^-7 ≈ 0.008

公式:f32 有 23 位尾数(mantissa),所以精度 = `value * 2^-23 ≈ value * 1.2e-7`。

```
绝对误差 ≈ value * 1.2e-7
```

`value = 10000` 时,误差 0.0012 米。每帧位置加 0.02 米,但 f32 只能表示 0.001 的精度——20% 的位移被四舍五入丢失。**累积 60 帧后,粒子位置错位几厘米**。

解决:**让 value 永远在 0 附近**。模拟空间下 `value = 粒子相对相机偏移`,通常 < 100 米。误差 0.00001 米——精度比世界坐标高 100 倍。

### 工程实现:三层坐标

游戏里有三层坐标:

```
世界空间 (world space)
    |    - 玩家在 (1000, 2000, 0)
    |    - 粒子世界位置 = sim_pos + sim_origin
    v
模拟空间 (sim space)
    |    - 粒子相对 sim_origin 的位置
    |    - sim_origin = 相机当前位置(每帧更新)
    v
屏幕空间 (screen space)
    |    - 投影后的像素坐标
    |    - 渲染时计算
    v
显示
```

**关键变换**:

```rust
// 世界 → 模拟
let sim_pos = world_pos - sim_origin;
// 模拟 → 世界
let world_pos = sim_pos + sim_origin;
// 世界 → 屏幕(投影)
let screen = project(world_pos, camera_proj);
```

**sim_origin 的更新**:

```rust
// 每帧开始
let new_sim_origin = camera.pos;
let delta = new_sim_origin - self.sim_origin;

// 所有粒子的 sim_pos 减 delta,保持 world_pos 不变
for p in &mut self.particles.pos_x {
    // 注意:粒子存 sim_pos,我们改 sim_pos 让 world_pos 不变
    // world_pos = sim_pos + sim_origin(旧)
    //           = sim_pos(新) + sim_origin(新)
    // 所以 sim_pos(新) = sim_pos(旧) + (sim_origin(旧) - sim_origin(新))
    //                  = sim_pos(旧) - delta
}
self.sim_origin = new_sim_origin;
```

### 粒子相对相机的更新流程

每帧:

```rust
// 1. 更新 sim_origin
let delta = camera.pos - self.sim_origin;
if delta.length_sq() > 0.0 {
    for i in 0..self.particles.len() {
        self.particles.pos_x[i] -= delta.x;
        self.particles.pos_y[i] -= delta.y;
        self.particles.pos_z[i] -= delta.z;
    }
    self.sim_origin = camera.pos;
}

// 2. 粒子在模拟空间里自由飞
for i in 0..self.particles.len() {
    self.particles.pos_x[i] += self.particles.vel_x[i] * dt;
    self.particles.pos_y[i] += self.particles.vel_y[i] * dt;
    self.particles.pos_z[i] += self.particles.vel_z[i] * dt;
    self.particles.age[i] += dt;
}

// 3. 渲染时:世界坐标 = 模拟坐标 + sim_origin
for i in 0..self.particles.len() {
    let world = Vec3::new(
        self.particles.pos_x[i] + self.sim_origin.x,
        self.particles.pos_y[i] + self.sim_origin.y,
        self.particles.pos_z[i] + self.sim_origin.z,
    );
    draw_particle(world, ...);
}
```

注意第 3 步:`world = sim + origin`,这里又出现"大数 + 小数"——但渲染时只做一次,误差小,不会累积。

### 为什么不直接 f64?

简单方案:把所有位置改成 f64。精度问题消失。

但代价:

1. **内存翻倍**:f64 8 字节,f32 4 字节。粒子池 4096 个,32 字节 Particle → 64 字节。所有"位置"数据翻倍。
2. **SIMD 减半**:一个 xmm 寄存器装 4 个 f32,只装 2 个 f64。SIMD 优势减半。
3. **GPU 不友好**:大多数 GPU shader 用 f32,f64 慢且贵。
4. **不解决根本问题**:在 (1000000, 0) 处,f64 精度 1e-10——很好,但你还是要相对计算。

**业界惯例**:大世界游戏用"模拟空间 / 分区(floating origin)"而不是 f64。GTA、Witcher、Cyberpunk 都这么干。

少数例外:**Kerbal Space Program** 用 f64,因为太阳系尺度 + 物理仿真精度要求高。代价:模拟代码复杂,GPU 需要分精度。

## 3 · 四域深入

### 3.1 · 游戏编程视角

"模拟空间" / "floating origin" 是大世界游戏的标配。Casey 今天的做法属于"floating origin"——原点随相机浮动。

**几种 floating origin 策略**:

1. **相机为原点**:Casey 今天的方案。相机移动时所有物体反向偏移。
2. **玩家为原点**:类似,但参考点是玩家。第一人称游戏常用。
3. **分区原点**(tile origin):地图分成 1km × 1km 区块,每块有自己的原点。物体坐标相对区块原点。渲染时把区块原点 + 物体偏移得到世界。
4. **每物体最近原点**:每个物体存"最近整数原点 + 偏移"。物理仿真精度极高。

**业界 case**:

- **Minecraft** 用区块 + 相对原点(每块 16×16,区块内坐标 < 16)
- **Star Citizen** 用 f64 + floating origin(双重保险)
- **Witcher 3** 用 floating origin(相机为原点)
- **Cyberpunk 2077** 用 floating origin + chunk origin

**陷阱**:`sim_origin` 跳变时,要同步更新所有 sim_pos。漏了一个数组就出现"粒子飞向相机 / 飞离相机"bug。Casey 今天调试这种 bug 不少。

### 3.2 · 图形学视角

GPU 端的精度问题比 CPU 还严重——shader 默认 f32,但有些老 GPU 把 f32 实现成 f24(GF2/GF4 时代)。现代 GPU f32 是真 f32,但 f64 极慢(1/8 ~ 1/32 速度)。

**OpenGL 的 `GL_DEPTH_BUFFER_BIT`** 在 z 测试时也用 f32,但深度精度分配不均匀(近处精度高,远处精度低)——这是 Day 358 深度缓冲的核心问题。模拟空间不影响深度,但影响"屏幕投影"的精度:如果世界坐标 (10000, 0, 0) 投影到屏幕,精度丢失会让像素位置抖动。

**业界做法**:vertex shader 接收"相对相机"的坐标:

```glsl
uniform vec3 u_camera_pos;
attribute vec3 a_world_pos;

void main() {
    vec3 sim_pos = a_world_pos - u_camera_pos;  // 相对相机
    vec4 view_pos = u_view_matrix * vec4(sim_pos, 1.0);
    gl_Position = u_proj_matrix * view_pos;
}
```

GPU 不直接做"减原点",是 vertex shader 在 GLSL 里做。和 CPU 端 sim space 同一思想。

**Casey 的方案**:CPU 端做 sim_pos 计算,GPU 直接拿 sim_pos + sim_origin = world_pos,然后投影。CPU 端已经处理精度,GPU 端不需要再做。

### 3.3 · Linux 系统编程视角

精度问题在 Linux 系统编程里也有体现:

**高精度时间戳**:`clock_gettime(CLOCK_MONOTONIC, ...)` 返回 `struct timespec { time_t tv_sec; long tv_nsec; }`。`time_t` 是 64 位秒,`tv_nsec` 是 0 ~ 999999999 纳秒。系统启动后 `tv_sec` 越来越大,但拆成"秒 + 纳秒"避免了精度问题——和"sim_origin + sim_pos"是同一思想。

**网络协议**:TCP 序列号是 32 位,但发送方维护"高 32 位"(implicit)——和 sim_origin 一样,核心数据小,大基数另存。

**文件偏移**:`lseek` 用 `off_t`,32 位系统上 4GB 上限。Linux 用 `_FILE_OFFSET_BITS=64` 把 off_t 升级到 64 位,绕过限制——和 sim space 是相反思路(用 f64 而非 sim space),适用于"无法分割"的场景。

**真实工程**:你的程序如果跑在 64 位 Linux 上,大部分坐标问题用 f64 + careful casting 就够了。游戏开发是少数 f64 不够(性能)的特殊场景。

### 3.4 · Rust 生态视角

Rust 表达"模拟空间"主要靠**类型安全**——不让 world_pos 和 sim_pos 混淆。

```rust
// 新类型模式(newtype)
#[derive(Copy, Clone, Debug)]
struct WorldPos(pub Vec3);

#[derive(Copy, Clone, Debug)]
struct SimPos(pub Vec3);

impl std::ops::Sub for WorldPos {
    type Output = SimPos;
    fn sub(self, rhs: WorldPos) -> SimPos {
        SimPos(self.0 - rhs.0)
    }
}

impl std::ops::Add<SimPos> for WorldPos {
    type Output = WorldPos;
    fn add(self, rhs: SimPos) -> WorldPos {
        WorldPos(self.0 + rhs.0)
    }
}
```

**好处**:编译期防止"把 world_pos 当 sim_pos 用"的 bug。一旦你写 `world_pos_a - world_pos_b`,编译器自动推断结果是 `SimPos`,不能赋给 `WorldPos`。

**坏处**:每个运算符都要 impl,代码量大。社区有 `nutype` / `derive_more` crate 减少样板。

**Casey 在 C 里**:`typedef Vec3 WorldPos` 不够,C 不区分——Casey 靠注释和纪律。Rust 的 newtype 让这种区分免费。

**f32 / f64 抽象**:Rust 标准库的 `f32` 和 `f64` 类型独立,但你写"任意精度向量"要泛型:

```rust
use num_traits::Float;
struct Vec3<T: Float> { x: T, y: T, z: T }
```

`num_traits` crate 提供 `Float` trait,统一 f32 / f64 接口。代价:泛型代码编译慢、运行时可能慢(泛型 dispatch)。

**真实 crate**:
- `glam::DVec3` — f64 版本,用于大世界物理
- `cgmath::Vector3<f64>` — 类似
- `mint` crate — 数学类型 interop 标准

## 5 · 对照与变奏

### 模拟空间在不同维度的变体

**2D 模拟空间**(今天 HH 是 2D 俯视游戏):sim_pos 是 `(f32, f32)` 或 `(f32, f32, f32)`(z 用于排序)。Casey Day 338 实际只用 2D。

**3D 模拟空间**(3D 游戏):所有 Vec3 都用,但 z 轴(深度)精度问题最严重——因为透视投影后远处物体压缩,小误差变大。

**多原点模拟空间**:不同子系统用不同原点。玩家用相机原点,远处的鸟用世界原点 + f64。混合策略。

### 历史演化

- **1980s**:游戏世界小(几个屏幕),坐标都是整数,无精度问题
- **1990s**:3D 出现,世界仍小,f32 够用
- **2000s**:GTA 等大世界游戏兴起,精度问题凸显,首次用 floating origin
- **2010s**:大世界标配,floating origin 成业界常识
- **2020s**:Kerbal Space Program 证明 f64 + floating origin 可以并存(双保险)

### CPU 和 GPU 的精度协作

| 层级 | 类型 | 精度 |
|---|---|---|
| 物理 | f64 或 f32 + sim space | 极高 |
| 游戏逻辑 | f32 + sim space | 高 |
| CPU 渲染数据 | f32 + sim space | 中 |
| GPU vertex shader | f32(sim space 抵消后) | 中 |
| GPU fragment shader | f32,但实际精度受 framebuffer 限制 | 低 |

每层都做"相对计算",精度逐层降低也安全。Casey 的方案是 CPU 做完所有 sim space 处理,GPU 看到的坐标已经是低绝对值的"相对坐标"。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 `sim_pos -= delta` 而不是 `sim_pos += delta`?如果用错符号,会看到什么现象?

**参考解答**:`delta = new_sim_origin - old_sim_origin`,即相机移动量。

要保持粒子的**世界位置不变**,需要 `world = sim_pos(新) + sim_origin(新) = sim_pos(旧) + sim_origin(旧)`。所以 `sim_pos(新) = sim_pos(旧) + sim_origin(旧) - sim_origin(新) = sim_pos(旧) - delta`。

符号错(用 `+=`)的话:粒子世界位置会跟着相机走 —— 相机往右 10 米,所有粒子也往右 10 米。视觉上:相机移动,粒子像"贴在相机镜头上",整个屏幕粒子滑动。这是典型的 sim space bug。

### Lv2 · 动手实践

**题**:实现一个简化的模拟空间粒子系统。粒子 100 颗,初始世界坐标在 (1000, 1000) 附近。相机从 (1000, 1000) 移动到 (1050, 1050)。每帧更新粒子(模拟空间)和 sim_origin。最后验证:粒子的"世界坐标 = sim_pos + sim_origin"始终等于初始世界坐标(粒子不动)。

完成标准:`cargo run` 打印 `max_drift < 0.001`,即世界坐标偏移不超过 0.001。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, Default)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
}

struct ParticleSim {
    sim_pos: Vec<Vec2>,  // 模拟空间坐标
    sim_origin: Vec2,    // 当前模拟原点(世界坐标)
}

impl ParticleSim {
    fn new(world_positions: &[Vec2], origin: Vec2) -> Self {
        let sim_pos: Vec<Vec2> = world_positions.iter()
            .map(|p| p.sub(origin))
            .collect();
        Self { sim_pos, sim_origin: origin }
    }

    // 相机移动时调用
    fn recenter(&mut self, new_origin: Vec2) {
        let delta = new_origin.sub(self.sim_origin);
        for p in &mut self.sim_pos {
            *p = p.sub(delta);  // 反向偏移
        }
        self.sim_origin = new_origin;
    }

    // 获取粒子世界位置(渲染用)
    fn world_pos(&self, i: usize) -> Vec2 {
        self.sim_pos[i].add(self.sim_origin)
    }
}

fn main() {
    // 100 颗粒子,初始世界坐标 (1000, 1000) 附近
    let initial: Vec<Vec2> = (0..100).map(|i| {
        Vec2::new(1000.0 + i as f32 * 0.1, 1000.0 + i as f32 * 0.1)
    }).collect();

    let mut sim = ParticleSim::new(&initial, Vec2::new(1000.0, 1000.0));

    // 相机从 (1000, 1000) 移动到 (1050, 1050),分 50 步
    for step in 1..=50 {
        let new_origin = Vec2::new(1000.0 + step as f32, 1000.0 + step as f32);
        sim.recenter(new_origin);
    }

    // 验证:粒子的世界位置应该等于初始位置
    let mut max_drift = 0.0f32;
    for (i, p) in initial.iter().enumerate() {
        let world = sim.world_pos(i);
        let drift = (world.x - p.x).abs().max((world.y - p.y).abs());
        max_drift = max_drift.max(drift);
    }
    println!("max_drift = {}", max_drift);
    assert!(max_drift < 0.001, "drift too big!");
    println!("OK");
}
```

**关键解释**:
- `recenter` 必须在每帧 sim_origin 变化时调用
- `world_pos` 是渲染时的"投影前位置"
- 验证用 `max_drift` 检查累积误差——理论上应为 0,f32 累积误差 < 0.001

### Lv3 · 迁移设计

**题**:把"模拟空间"思想用到**网络同步**:玩家在 (100000, 0),你每帧发位置包给客户端。如果直接发 (100000, 0) 这种大数,f32 误差大。

设计:发"相对上次位置 delta" + 累计基点。要求:

1. 服务器维护 `basis: Vec2`,初始 = 玩家初始位置
2. 每次发包,只发 `player.pos - basis`(小数)
3. 客户端累加:`player.pos += delta_packet`
4. 当 `basis` 离玩家太远(> 1000),发"basis 重置"包

提示:这是"差分编码 + 浮点原点"在网络的应用,叫 **delta compression + floating origin**。

## 8 · Rust / Arch 落地代码

### 完整可跑示例

扩展 Lv2,加上"粒子在模拟空间自由飞行 + 相机移动"的演示。

```rust
#[derive(Copy, Clone, Debug, Default)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
}

struct ParticleSystem {
    // 模拟空间坐标(sim_pos),低绝对值
    sim_pos: Vec<Vec2>,
    sim_vel: Vec<Vec2>,
    age: Vec<f32>,
    life: Vec<f32>,
    sim_origin: Vec2,
}

impl ParticleSystem {
    fn new() -> Self {
        Self {
            sim_pos: vec![],
            sim_vel: vec![],
            age: vec![],
            life: vec![],
            sim_origin: Vec2::new(0.0, 0.0),
        }
    }

    // 世界坐标发射粒子
    fn emit(&mut self, world_pos: Vec2, world_vel: Vec2, life: f32) {
        let sim_pos = world_pos.sub(self.sim_origin);
        let sim_vel = world_vel;  // 速度不变(差分量)
        self.sim_pos.push(sim_pos);
        self.sim_vel.push(sim_vel);
        self.age.push(0.0);
        self.life.push(life);
    }

    // 相机移动时调用
    fn recenter(&mut self, new_origin: Vec2) {
        let delta = new_origin.sub(self.sim_origin);
        if delta.x == 0.0 && delta.y == 0.0 { return; }
        for p in &mut self.sim_pos {
            *p = p.sub(delta);
        }
        self.sim_origin = new_origin;
    }

    // 一帧更新
    fn update(&mut self, dt: f32) {
        let mut i = 0;
        while i < self.sim_pos.len() {
            // 模拟空间内自由飞行
            self.sim_pos[i] = self.sim_pos[i].add(self.sim_vel[i].mul(dt));
            self.age[i] += dt;

            // 死亡 swap-remove
            if self.age[i] >= self.life[i] {
                let last = self.sim_pos.len() - 1;
                if i != last {
                    self.sim_pos[i] = self.sim_pos[last];
                    self.sim_vel[i] = self.sim_vel[last];
                    self.age[i] = self.age[last];
                    self.life[i] = self.life[last];
                }
                self.sim_pos.pop();
                self.sim_vel.pop();
                self.age.pop();
                self.life.pop();
            } else {
                i += 1;
            }
        }
    }

    // 获取世界坐标(渲染用)
    fn world_positions(&self) -> Vec<Vec2> {
        self.sim_pos.iter().map(|p| p.add(self.sim_origin)).collect()
    }
}

fn main() {
    let mut ps = ParticleSystem::new();

    // 玩家初始位置
    let player_start = Vec2::new(5000.0, 5000.0);
    ps.sim_origin = player_start;

    // 在玩家附近喷 10 颗粒子(世界坐标)
    for i in 0..10 {
        let wp = player_start.add(Vec2::new(i as f32 * 0.5, 0.0));
        ps.emit(wp, Vec2::new(1.0, 0.0), 5.0);
    }
    println!("Initial particle world positions:");
    for (i, p) in ps.world_positions().iter().take(3).enumerate() {
        println!("  [{}] = ({:.3}, {:.3})", i, p.x, p.y);
    }

    // 模拟 60 帧,相机不动,粒子飞
    for _ in 0..60 {
        ps.update(1.0 / 60.0);
    }
    println!("\nAfter 60 frames (camera still):");
    for (i, p) in ps.world_positions().iter().take(3).enumerate() {
        println!("  [{}] = ({:.3}, {:.3})", i, p.x, p.y);
    }

    // 相机往右走 10 米,粒子在模拟空间反向偏移
    ps.recenter(player_start.add(Vec2::new(10.0, 0.0)));
    println!("\nAfter camera moved +10 X:");
    for (i, p) in ps.world_positions().iter().take(3).enumerate() {
        println!("  [{}] = ({:.3}, {:.3})", i, p.x, p.y);
    }
    // 世界坐标应该和上次几乎一样(粒子没动,只是相机动了)
    // 注意第 60 帧后粒子也飞了 1 秒,所以位置已经变了
}
```

**关键 Rust 特性**:
- `Vec<Vec2>` 而非 `Vec2[]`:动态长度,适合"喷发"场景。固定大小场景用 `[Vec2; N]`。
- `swap_remove` 风格的死亡处理:O(1) 删除,代价是顺序乱。
- `sim_pos` 和 `sim_vel` 分两个 Vec:为 Day 337 的 SoA SIMD 留扩展空间。
- `world_positions()` 返回 `Vec<Vec2>`:每次新建,有 alloc 开销。生产代码应传 closure: `for_each_world_pos(|i, p| render(p))`。

**Troubleshooting**:
- "粒子抖动" — 检查 `recenter` 是否在每帧 sim_origin 变化时调用
- "粒子飞向相机" — `sim_pos -= delta` 符号错(应该是 -=,不是 +=)
- "渲染位置错" — 确认 `world_pos = sim_pos + sim_origin`,不是 `sim_pos + camera_pos`(可能 sim_origin 和 camera_pos 不同步)
- "精度还是很差" — 检查 sim_origin 是否每帧更新,缓存 sim_pos 旧值会让 delta 失真
