
# Day 425 · 基于实体的光照存储

> 之前光源存在一个全局 `Vec<LightSource>` 里,遍历所有图元时遍历所有光源。今天 Casey 把光源改造成**实体(Entity)**——和玩家、怪物、家具一样,有自己的 ID、位置、组件。这是 ECS 架构的扩展:光照不再是"特殊"数据,而是实体的一种组件。

## 0 · 为什么要有这一天

回顾 HH 的实体系统(Phase 2 引入):每个游戏对象是一个 entity,有 Position、Velocity、Sprite 等 component。光照之前**没有融入** ECS——它是个全局列表,独立于 entity 系统。

这导致**不一致**:你创建一个怪物用 `spawn_entity(pos, Monster)`,创建一个火把却用 `spawn_light(pos, color, intensity)`。两套 API,两套数据结构,两套生命周期。

工业 ECS 的原则:**所有游戏对象都是 entity**。火把和怪物一样,有 Position(位置)、Light(component 描述发光属性)、可能还有 Particle(火焰粒子)。这样:

- 火把可以被 ECS 查询找到(像其他 entity)
- 火把可以附加其他 component(比如 Sound,发出燃烧声)
- 火把的生命周期统一(entity 销毁时光也消失)
- 火把的位置变化自动通过 ECS 的 Position 同步

Casey 今天把 `Light` 变成 entity 的 component。数据迁移:

```rust
// 旧
pub struct Game {
    lights: Vec<LightSource>,  // 独立列表
    entities: Vec<Entity>,
}

// 新
pub struct Game {
    entities: Vec<Entity>,  // 所有对象,包括光
}

// entity 之一
struct Entity {
    id: u32,
    position: Vec3,
    light: Option<LightComponent>,  // 有的话就是光源
    // ... 其他 component
}
```

光照查询从"遍历 lights 列表"变成"ECS 查询所有有 Light component 的 entity"。

心理锚点:今天之后,你能解释为什么 ECS 让代码统一,能把任何"特殊对象"(光、相机、声源、触发器)改造成 entity + component,理解工业 ECS 引擎(Bevy、Unity DOTS、Flecs)的"一切皆 entity"思想。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 重构光照存储:

1. **新增 LightComponent**:`struct LightComponent { color: Vec3, intensity: f32, classification: LightClassification, ... }`
2. **Entity 加 light 字段**:`struct Entity { ..., light: Option<LightComponent> }`
3. **删除 lights 全局列表**
4. **光照系统遍历 ECS**:`for entity in entities.filter(has_light) { ... }`
5. **生成新光源的 API 改成 spawn_entity + LightComponent**

Casey 强调:**重构纪律**。视觉输出应该和之前完全一致。他用 day263 帧滑块对比新旧版本,确认一致。

副效应:**Bug 自动消失**。之前 entity 销毁时光没自动消失(因为是独立列表),现在 entity 销毁时 LightComponent 一起销毁。这是 ECS 的"统一生命周期"红利。

## 2 · 心智模型

### 类比:超市商品管理

想象超市两种管理方式:

- **分散管理**(旧):生鲜区有自己的商品列表,日用品区有自己的列表,电器区有自己的列表。每个区独立管理,员工不通用。
- **统一管理**(新,本日):所有商品在一个大库存系统,每件商品有 ID + 位置 + 属性(生鲜 / 日用品 / 电器是属性)。员工查询"所有临期商品",系统跨区找。

ECS 的"统一管理"优势:

- 跨类型查询简单("找出所有发光的东西")
- 统一生命周期(商品下架,所有相关数据消失)
- 灵活组合(商品可以既是"生鲜"又是"促销")

光照融入 ECS 完全同构。光源只是"有发光属性"的 entity。

### 严谨原理:ECS 三要素

ECS(Entity Component System)三个核心概念:

1. **Entity**:ID,无数据。可以是 `u32` 或 `Entity(u32, generation)`。
2. **Component**:纯数据,挂在 entity 上。`Position`、`Velocity`、`Light` 都是 component。
3. **System**:函数,操作有特定 component 集合的 entity。"光照系统"操作有 `Position + Light` 的 entity。

光照融入 ECS:

```rust
// Entity 只是 ID
#[derive(Copy, Clone, Debug, PartialEq, Eq)]
pub struct Entity(pub u32);

// Component:数据
#[derive(Clone, Default)]
pub struct Position(pub Vec3);

#[derive(Clone)]
pub struct LightComponent {
    pub color: Vec3,
    pub intensity: f32,
    pub classification: LightClassification,
    // ...
}

// System:操作有特定 component 的 entity
pub fn lighting_system(entities: &[(Entity, &Position, &LightComponent)]) {
    for (_, pos, light) in entities {
        // 算光照
    }
}
```

HH 用**简单的 SoA**——一个 `Vec<Entity>`,每 entity 一个 struct,struct 有所有 component 的 Option。更工业的 ECS 用 sparse set 或 archetype,但思路一致。

### Rust 视角:简单 ECS

```rust
#[derive(Clone, Default)]
pub struct Entity {
    pub id: u32,
    pub position: Option<Vec3>,
    pub velocity: Option<Vec3>,
    pub sprite: Option<SpriteComponent>,
    pub light: Option<LightComponent>,
    // ... 其他 component
}

pub struct World {
    pub entities: Vec<Entity>,
    pub next_id: u32,
}

impl World {
    pub fn spawn(&mut self) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        self.entities.push(Entity { id, ..Default::default() });
        id
    }

    pub fn despawn(&mut self, id: u32) {
        self.entities.retain(|e| e.id != id);
    }

    pub fn lights(&self) -> impl Iterator<Item = (u32, Vec3, &LightComponent)> {
        self.entities.iter()
            .filter_map(|e| {
                let pos = e.position?;
                let light = e.light.as_ref()?;
                Some((e.id, pos, light))
            })
    }
}
```

`lights()` 返回一个迭代器,惰性查询所有有 Position + Light 的 entity。零分配,零拷贝。

### 数据迁移

旧代码:

```rust
let mut lights = vec![
    LightSource { pos: Vec3::new(5, 5, 0), color: WHITE, intensity: 100.0, ... },
];
```

新代码:

```rust
let torch_id = world.spawn();
world.entities.last_mut().unwrap().position = Some(Vec3::new(5, 5, 0));
world.entities.last_mut().unwrap().light = Some(LightComponent {
    color: WHITE,
    intensity: 100.0,
    ...
});
```

更长的代码,但**一致性**更强。新代码自动获得 ECS 的所有红利(查询、生命周期、组合)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业 ECS 引擎:

- **Bevy**:Rust 原生 ECS,所有都是 entity + component
- **Unity DOTS**:C# ECS,大型游戏
- **Unreal Mass Entity**:UE5 的 ECS
- **Flecs**:C/C++ ECS,开源

Bevy 的设计原则:**没有"特殊的"对象**。相机是 entity(Camera3d component),光是 entity(PointLight component),玩家是 entity(Player component + Transform + Mesh)。

Casey 的简化 ECS 是 Bevy 的极简版,够 HH 用。Phase 7+ 如果需要更复杂场景,可能切到 Bevy ECS。

### 3.2 · 🎨 图形学视角

光照融入 ECS 后,可以更灵活:

- **Attach 光源到角色**:角色 entity 加 LightComponent,光跟随角色位置
- **Attach 光源到武器**:武器是 entity,加 LightComponent,光跟随武器
- **粒子光源**:每个火焰粒子是 entity,有 LightComponent,数量上千

工业的"粒子光源"(Frostbite 引擎)用 ECS 实现每个粒子都是 entity,可以挂 LightComponent。粒子发射器自动产生 + 销毁 entity,光随之出现 + 消失。

### 3.3 · 🐧 Linux 系统编程视角

Linux 的"一切皆文件"和"一切皆 entity"同构:

- Linux:**所有 IO 资源**(文件、socket、设备、进程)都有 fd,统一 API
- ECS:**所有游戏对象**(玩家、光、相机、触发器)都是 entity,统一查询

Linux 的统一让 `read/write` 适用于任何 fd,ECS 的统一让 `query` 适用于任何 entity。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么把光照融入 ECS 是"好的重构",而不是"为了用 ECS 而用 ECS"?

**参考解答**:**好的重构**带来具体收益:

1. **生命周期统一**:entity 销毁时光自动消失(之前要手动从 lights 列表删除)
2. **查询统一**:找"所有发光的 entity"用 ECS 查询,和找"所有移动的 entity"用同一接口
3. **组合灵活**:光源可以同时有 Sound、Particle 等其他 component
4. **API 一致**:spawn 火把用 spawn_entity,不再有特殊的 spawn_light

**为了用 ECS 而用 ECS** 是反例:如果收益只是"看起来用了 ECS",没有具体功能改进,就是过度工程。Casey 这次重构有 1-4 的具体收益,所以值得。

```rust
#[derive(Copy, Clone, Debug, PartialEq, Eq)]
pub enum LightClassification { Direct, Propagated }

#[derive(Clone)]
pub struct LightComponent {
    pub color: Vec3,
    pub intensity: f32,
    pub classification: LightClassification,
}

#[derive(Clone, Default)]
pub struct Entity {
    pub id: u32,
    pub position: Option<Vec3>,
    pub light: Option<LightComponent>,
    pub name: Option<String>,
}

pub struct World {
    pub entities: Vec<Entity>,
    next_id: u32,
}

impl World {
    pub fn new() -> Self { Self { entities: Vec::new(), next_id: 0 } }

    pub fn spawn(&mut self) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        self.entities.push(Entity { id, ..Default::default() });
        id
    }

    pub fn despawn(&mut self, id: u32) {
        self.entities.retain(|e| e.id != id);
    }

    pub fn get_mut(&mut self, id: u32) -> Option<&mut Entity> {
        self.entities.iter_mut().find(|e| e.id == id)
    }

    /// 查询所有有 Position + Light 的 entity
    pub fn lights(&self) -> impl Iterator<Item = (u32, Vec3, &LightComponent)> {
        self.entities.iter().filter_map(|e| {
            let pos = e.position?;
            let light = e.light.as_ref()?;
            Some((e.id, pos, light))
        })
    }
}

fn main() {
    let mut world = World::new();

    // 创建一个火把 entity
    let torch = world.spawn();
    {
        let e = world.get_mut(torch).unwrap();
        e.position = Some(Vec3::new(5.0, 0.0, 5.0));
        e.light = Some(LightComponent {
            color: Vec3::new(1.0, 0.8, 0.5),
            intensity: 50.0,
            classification: LightClassification::Direct,
        });
        e.name = Some("Torch".to_string());
    }

    // 创建一个天花板灯
    let ceiling = world.spawn();
    {
        let e = world.get_mut(ceiling).unwrap();
        e.position = Some(Vec3::new(0.0, 10.0, 0.0));
        e.light = Some(LightComponent {
            color: Vec3::ONE,
            intensity: 100.0,
            classification: LightClassification::Propagated,
        });
    }

    // 创建一个不带 light 的 entity(玩家)
    let player = world.spawn();
    world.get_mut(player).unwrap().position = Some(Vec3::ZERO);

    // 查询
    println!("Lights in world:");
    for (id, pos, light) in world.lights() {
        println!("  id={} pos={:?} color={:?} intensity={}",
            id, pos, light.color, light.intensity);
    }
    // 应该输出 torch 和 ceiling,不包括 player

    // 销毁 torch,验证 lights() 不再包含
    world.despawn(torch);
    println!("\nAfter despawn torch:");
    for (id, _, _) in world.lights() {
        println!("  id={}", id);
    }
    // 只剩 ceiling
}
```

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
pub enum LightClassification { Direct, Propagated, Baked }

#[derive(Clone, Debug)]
pub struct LightComponent {
    pub color: Vec3,
    pub intensity: f32,
    pub classification: LightClassification,
    pub radius: f32,
}

impl Default for LightComponent {
    fn default() -> Self {
        Self {
            color: Vec3::ONE,
            intensity: 1.0,
            classification: LightClassification::Direct,
            radius: 10.0,
        }
    }
}

#[derive(Clone, Default)]
pub struct Entity {
    pub id: u32,
    pub position: Option<Vec3>,
    pub velocity: Option<Vec3>,
    pub name: Option<String>,
    pub light: Option<LightComponent>,
}

impl Entity {
    pub fn has_light(&self) -> bool { self.light.is_some() }
}

pub struct World {
    pub entities: Vec<Entity>,
    next_id: u32,
}

impl World {
    pub fn new() -> Self { Self { entities: Vec::new(), next_id: 0 } }

    pub fn spawn(&mut self) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        self.entities.push(Entity { id, ..Default::default() });
        id
    }

    pub fn despawn(&mut self, id: u32) -> bool {
        let before = self.entities.len();
        self.entities.retain(|e| e.id != id);
        self.entities.len() < before
    }

    pub fn get(&self, id: u32) -> Option<&Entity> {
        self.entities.iter().find(|e| e.id == id)
    }

    pub fn get_mut(&mut self, id: u32) -> Option<&mut Entity> {
        self.entities.iter_mut().find(|e| e.id == id)
    }

    pub fn lights(&self) -> impl Iterator<Item = (u32, Vec3, &LightComponent)> {
        self.entities.iter().filter_map(|e| {
            Some((e.id, e.position?, e.light.as_ref()?))
        })
    }

    pub fn lights_by_classification(&self, c: LightClassification)
        -> impl Iterator<Item = (u32, Vec3, &LightComponent)> {
        self.lights().filter(move |(_, _, l)| l.classification == c)
    }

    pub fn count_lights(&self) -> usize {
        self.entities.iter().filter(|e| e.has_light()).count()
    }
}

fn main() {
    let mut world = World::new();

    // 玩家手持火把
    let torch = world.spawn();
    {
        let e = world.get_mut(torch).unwrap();
        e.name = Some("Torch".into());
        e.position = Some(Vec3::new(5.0, 1.5, 5.0));
        e.light = Some(LightComponent {
            color: Vec3::new(1.0, 0.8, 0.4),
            intensity: 30.0,
            classification: LightClassification::Direct,
            radius: 15.0,
        });
    }

    // 天花板固定灯
    let ceiling = world.spawn();
    {
        let e = world.get_mut(ceiling).unwrap();
        e.name = Some("Ceiling Light".into());
        e.position = Some(Vec3::new(0.0, 10.0, 0.0));
        e.light = Some(LightComponent {
            color: Vec3::ONE,
            intensity: 100.0,
            classification: LightClassification::Propagated,
            radius: 50.0,
        });
    }

    // 玩家(无光)
    let player = world.spawn();
    world.get_mut(player).unwrap().name = Some("Player".into());
    world.get_mut(player).unwrap().position = Some(Vec3::ZERO);

    println!("World has {} lights", world.count_lights());

    println!("\nDirect lights:");
    for (id, pos, l) in world.lights_by_classification(LightClassification::Direct) {
        let name = world.get(id).and_then(|e| e.name.as_deref()).unwrap_or("?");
        println!("  {} (id={}): pos={:?} intensity={}", name, id, pos, l.intensity);
    }

    println!("\nPropagated lights:");
    for (id, pos, l) in world.lights_by_classification(LightClassification::Propagated) {
        let name = world.get(id).and_then(|e| e.name.as_deref()).unwrap_or("?");
        println!("  {} (id={}): pos={:?} intensity={}", name, id, pos, l.intensity);
    }

    // 销毁 torch
    println!("\nDespawning torch...");
    assert!(world.despawn(torch));
    println!("Lights now: {}", world.count_lights());

    // 性能测试
    let mut big_world = World::new();
    for i in 0..100_000 {
        let id = big_world.spawn();
        let e = big_world.get_mut(id).unwrap();
        e.position = Some(Vec3::new(i as f32, 0.0, 0.0));
        if i % 10 == 0 {
            e.light = Some(LightComponent::default());
        }
    }
    let start = std::time::Instant::now();
    let count = big_world.lights().count();
    let elapsed = start.elapsed();
    println!("\nQuery {} entities, found {} lights in {:?}",
        big_world.entities.len(), count, elapsed);
}
```

**Troubleshooting**:

- **despawn 后 lights() 仍包含** — `retain` 后查询缓存(若有),需刷新
- **借用错误** — `world.get_mut` 和 `world.lights()` 不能同时,先释放再查询
- **性能慢** — `find(|e| e.id == id)` 是 O(N),工业 ECS 用 HashMap 索引
- **LightComponent 默认值不对** — `Default` 实现要给合理值,不要全 0
- **多线程共享** — `World` 不是 Sync,要并行用 `Arc<RwLock<World>>` 或 split


### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
