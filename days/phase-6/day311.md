# Day 311 · 允许手动排序

> 之前 entity 的绘制顺序完全由"Y 坐标 + 索引"自动算出来,今天 Casey 给某些 entity 开一道后门:让你在编辑器里手动指定它排在第几层。这是"自动规则 + 人工覆盖"在游戏数据系统里的经典落地。

## 0 · 为什么要有这一天

把你的游戏世界想象成一个画展。每个 entity 是一幅画,挂画的人(渲染器)需要决定**谁挂前面、谁挂后面**。在 Day 041 前后,Casey 已经定下来一条铁规则:**画家算法(painter's algorithm)**——按"屏幕 Y 坐标 + entity 的索引"自动排序,Y 小的(屏幕上方)先画,Y 大的(屏幕下方,也就是离观察者更近的)后画。这条规则简单、可预测、零配置,99% 的 2D 游戏都够用。

但你迟早会踩到坑。想象这几个场景:

1. **悬挂的吊灯**:吊灯的 Y 坐标很高(在天花板附近),但玩家可以从吊灯下方走过,吊灯应该始终盖在玩家头上。如果按 Y 排序,吊灯会被画在玩家后面,玩家从吊灯下走过时"踩到灯"——视觉错乱。
2. **桌面上的杯子和书**:杯子比书 Y 小(更靠后),按规则杯子画在前面,书画在后面。但你想要书永远压在杯子下面(美术风格选择)。这跟自动规则冲突。
3. **粒子特效**:爆炸的火花 Y 坐标不断变化,如果跟着 Y 排序,一会儿在怪前一会儿在怪后,看起来像穿模。

每一个都是真实的视觉 bug,光靠 Y 排序解决不了。业界的标准做法是:**保留自动排序作为默认,但给每个 entity 一个"手动排序键(manual sort key)",有这个键的 entity 跳过自动规则**。今天 Casey 干的就是这件事。

更深一层的动机:**数据驱动 vs 代码硬编码**。Casey 早期把"按 Y 排序"硬编码在渲染器里,任何特殊需求都要回去改渲染器代码。今天他把"排序键"变成 entity 的一个字段(存在 entity 的 `Traversable` 或 `Drawable` 组件里),美术在编辑器填一下值就能改排序,**不需要重新编译**。这是从"程序员掌控一切"到"数据 + 美术协作"的工程进化。

心理锚点:今天之后你的引擎支持"3 类 entity"——纯自动排序的(默认)、强制最前(特效/箭头)、强制最后(地板/装饰)。你能在编辑器里调出正确的遮挡关系,而不是在代码里写一堆 `if entity.type == TABLE { z_bias = -5 }` 这种魔法常量。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_render.cpp` 和 `handmade_entity.cpp`,做了一次"小而精"的 API 改造。原来 entity 的排序发生在 `DrawBitmap` 调用前,渲染器遍历 sim region 里的 entity,按 `(entity->P.y, entity->Index)` 排序,然后逐个画。

Casey 今天做的事:

1. 给 `entity` / `entity_reference` 加了一个新字段 `SortKey`(类型是 `uint32`,0 表示"用默认 Y 排序",非 0 表示"用这个值排")
2. 把 `PushBitmap` 的签名扩展,接受可选的 `SortKey` 参数
3. 修改 `RenderGroup` 内部的排序逻辑:如果 entity 有 `SortKey`,用 `SortKey`;否则用原来的 `(Y, Index)` 组合

关键决策:**SortKey 是 `uint32`,不是 `int32`,也不是 `float`**。原因有二:第一,整数比较比浮点快(虽然现代 CPU 上差不多,但精神上"排序键"是离散的,不该是浮点);第二,`uint32` 可以编码"高位 + 低位"——高位是 entity 类别(地板=0,普通=1,粒子=2,特效=3),低位是同类内部的精细顺序。这种"打包到一个整数"是 Casey 在 Day 041 教过的 trick,今天再用一次。

Casey 强调:**默认值 0 必须等价于"旧行为"**,这样不破坏现有 entity。所有现有 entity 不传 `SortKey`,排序键就用 `Y * SCALE + Index`,行为不变。只有新加的、需要特殊排序的 entity 才传显式 `SortKey`。这是"向后兼容"在数据结构演进里的标准做法。

代码改动很小,但 Casey 花了相当篇幅讲一个微妙问题:**SortKey 应该是 entity 的字段,还是 bitmap 的字段?** 也就是说,同一个 entity 的"身体"和"头"能不能有不同 SortKey?Casey 的选择是:**bitmap 级别**——因为后面 Day 313-314 会把 entity 拆成多个 sprite(脚、身、头),不同 sprite 可能要不同排序(头始终在身体之上)。今天先做最小版,但 API 留出扩展空间。

## 2 · 心智模型

### 类比:排队买菜

想象食堂排队买菜。默认规则是"按身高排"(高的站后面),这是自动排序。但今天你加了一条新规则:**老师可以插队**。老师不需要看身高,直接站最前面。

这里"老师"就是有 `SortKey` 的 entity,它的位置由 `SortKey` 决定,身高(Y 坐标)不再参与。普通学生(entity 没传 SortKey)依然按身高排。两种规则并行,但 **SortKey 优先级高于 Y**——有 SortKey 的 entity 优先按 SortKey 排,没有的按 Y 排,两组之间怎么混合?Casey 的设计是:**把 Y 也"映射"成一个 SortKey**,这样所有人都在同一个 uint32 比较空间里。

### 严谨原理:把 Y 编码成 SortKey

具体怎么把"Y 坐标 + Index"打包成一个 uint32?假设你的世界 Y 范围是 [-100, +100](共 200 个单位的浮点),你想要:

- Y = 100(最靠前)对应 SortKey 最大
- Y = -100(最后)对应 SortKey 最小
- 同样 Y 的多个 entity,Index 小的排前面

公式可以是:

```
SortKey = (uint32)((Y + 200) * 1000) * 1024 + Index
```

这里 `(Y + 200) * 1000` 把 [-100, 100] 映射到 [100000, 300000] 的整数空间,留出余量;再乘 1024 给 Index 留 10 位空间(支持同一 Y 坐标有最多 1024 个 entity)。这个公式不是 Casey 的实际公式,但思路一致。

有了"自动 entity 也有 SortKey"这个统一空间,真正的排序就退化成"按一个 uint32 字段排序"。把两种 entity(有手动 SortKey 的、自动的)混在一起,统一比较。手动 SortKey 可以选一个超出 Y 范围的值(比如 `UINT32_MAX` 表示永远最前,`0` 表示永远最后,只要不和自动值冲突就行)。

### 为什么不用 float 排序

排序性能上现代 CPU 浮点和整数差不多(都是一条 `cmp` 指令),但精神上"SortKey"是离散的——它不是物理量,是"我让你排第几"的人工约定。用 `uint32` 表达"约定"比 `float` 更准确,而且**整数比较可移植**(浮点的 NaN 在不同硬件上行为不同,会搞乱排序)。这是 Casey 反复强调的"选择正确类型表达意图"哲学。

### Painters vs Z-buffer

```
画家算法(今天讨论)        Z-buffer(后面的 Day 358)
─────────────────────       ──────────────────
排序 entity,从后往前画       每像素存 z,近覆盖远
按 entity 整体排序           按 fragment(像素)粒度
不正确处理交叉                完美处理交叉
快(一次排序 + N 次 blit)     慢(每像素一次比较 + 内存写)
```

Casey 现在还在用画家算法,因为 2D 模式下 entity 之间通常不交叉(脚不穿墙),画家算法够用。Day 358 切到 3D 后,画家算法在"两个三角形互相穿插"场景失效,Casey 才会切到 Z-buffer。今天的工作是给画家算法加"人工干预"能力,让它更灵活——但底层还是画家算法。

### 编辑器集成

数据驱动的关键是:**美术在编辑器里填 SortKey,渲染器读 SortKey**。今天 Casey 在 entity 结构里加 `SortKey` 字段后,编辑器(`handmade_world_mode` 的 entity 编辑 UI)立刻就支持读这个字段——因为 entity 字段都是 hot-loaded 的。这种"加了字段编辑器自动看到"的设计,是 Casey 在 Phase 4 已经搭好的 hot-reload 基础设施的回报。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业里"渲染排序"的层次结构:

1. **Layer(层)**:最粗粒度,比如"背景层 / 游戏层 / UI 层"。Unity 和 Godot 都有,Casey 在 Day 316 多渲染目标里会做类似的分层。
2. **SortKey(排序键)**:层内细粒度排序,可以编码多层信息(类目 + Y + Index)。今天 Casey 加的就是这层。
3. **Z-buffer(深度缓冲)**:像素粒度的遮挡,Day 358 后启用。和 SortKey 并存——SortKey 决定 entity 之间, Z-buffer 决定同一 entity 内像素之间。

主流 2D 引擎的排序方案:

- **Unity 2D**:`SortingLayer`(字符串名)+ `OrderInLayer`(整数)。本质和今天 Casey 的方案一样,只是用字符串做层名。
- **Godot 2D**:`z_index`(整数,负数画前面)+ `y_sort_enabled`(布尔,是否按 Y 自动排)。比 Casey 更灵活——同时支持手动 z_index 和自动 Y sort。
- **Phaser(JS)**:`depth`(整数),没有自动 Y sort,完全手动。
- **GameMaker**:`depth`(整数,小=前),和 Phaser 类似。

Casey 的方案介于 Unity 和 Godot 之间:**默认自动,有 SortKey 就用手动**。这种"渐进式"设计的好处是迁移成本低——旧 entity 不改任何代码,新 entity 加字段即可。

游戏行业的另一个共识:**排序键和"渲染队列(render queue)"是两件事**。排序键决定"画顺序",渲染队列决定"用哪个 shader / 哪个材质 batch"。比如所有用"半透明 shader"的 entity 必须画在所有"不透明 shader"的 entity 之后(独立于它们的 Y)。Casey 现在只有一种 shader(纯 blit),没有这个问题,Day 360 引入光照后会出现。

### 3.2 · 🎨 图形学视角

图形学里排序的根本问题是:**正确处理遮挡(occlusion)**。三种主流方案:

| 方案 | 粒度 | 复杂度 | 适用 |
|---|---|---|---|
| 画家算法 | object 级 | O(N log N) | 2D / 不交叉 3D |
| Z-buffer | pixel 级 | O(N × 像素数) | 通用 3D |
| BSP / Portal | 空间分割 | O(log N) 查询 | 静态场景(Quake 风格) |

今天的 SortKey 是画家算法的"补丁"——不改变算法本质,但让"哪些画前、哪些画后"可配置。图形学里这种"加人工干预到自动算法"的模式很常见,比如 shader 里的 `discard` 关键字、Z-buffer 的 `glDepthMask`(允许临时关闭深度写入)、texture 的 `borderColor`(超出 UV 范围时手动指定颜色)。

排序的另一个图形学话题是**稳定性(stability)**。稳定排序保证"键相同的元素保持原相对顺序",在游戏里意味着"Y 相同的两个 entity,Index 小的先画"。Rust `slice::sort_by` 是稳定的,Casey 在 C 里用 `qsort` 是不稳定的——这是 Rust 翻译时的一个隐藏行为差异。如果用不稳定排序,同样 Y 的两个 entity 可能因为排序算法内部状态而交换顺序,导致闪烁(flicker)。Casey 在 Day 312 会通过"SortKey 里嵌入 Index"避免这个问题。

### 3.3 · 🐧 Linux 系统编程视角

虽然今天没有直接涉及 Linux API,但"排序"在系统编程里无处不在:

- **`sort` 命令**:`sort -n` 按数字排序,`sort -k2` 按第二列排序。可以指定多个 `-k` 组成"多键排序",和今天 SortKey 编码多信息思想一致。
- **进程优先级(`nice`)**:`nice` 值类似 SortKey——CPU 调度器按 nice 排序决定哪个进程先跑。`nice -20` 是最高优先级(类似 SortKey 最大),`nice +19` 是最低。
- **链路层队列**:`tc`(traffic control)的 `prio` qdisc 按 priority 字段排序网络包,完全等价于 entity 排序。

这些例子告诉你:**排序键 + 默认值 + 人工覆盖**是跨领域的通用模式。理解今天的 entity 排序,你以后看任何"优先级队列"都能秒懂。

### 3.4 · 🦀 Rust 生态视角

Rust 标准库的排序 API:

```rust
// slice 上的稳定排序
slice.sort_by(|a, b| a.sort_key().cmp(&b.sort_key()));

// 不稳定但更快
slice.sort_unstable_by(|a, b| a.sort_key().cmp(&b.sort_key()));
```

`sort_by` 是稳定排序(同键保持原序),`sort_unstable_by` 不保证稳定但通常快 1.5-2 倍。游戏里如果 SortKey 已经嵌入 Index(每个 entity 唯一),可以用 `sort_unstable_by` 拿性能。如果 SortKey 可能重复,必须用 `sort_by` 保持稳定。

`u32::cmp` 返回 `std::cmp::Ordering`(`Less` / `Equal` / `Greater`)。闭包 `|a, b| ...` 是 Rust 的"比较函数"惯用法,等价于 C 的 `int cmp(const void*, const void*)` 但更安全(类型推导 + 编译期检查)。

Rust 的 `Ord` trait 让排序更优雅:

```rust
#[derive(Eq, PartialEq, Ord, PartialOrd)]
struct SortKey(u32);  // newtype 包一层,避免和其他 u32 混淆

// 现在可以直接 sort(),不需要 sort_by()
entities.sort_by_key(|e| e.sort_key);
```

`newtype` 模式(`struct SortKey(u32)`)是 Rust 的零开销类型抽象——编译后和 `u32` 完全一样,但语义上区分"排序键"和"普通 u32",防止误用。这是 Rust 比 C 强的一点。

## 5 · 对照与变奏

### 历史演化

- **1980s 8-bit 游戏**:几乎都是"硬编码绘制顺序"——代码里写死"先画背景、再画角色、最后画 UI"。没有排序概念,因为同时屏幕上 entity 少。
- **1990s 16-bit**:开始有"按 Y 排序"概念,但实现还是硬编码的(if-else 树)。
- **2000s 3D 时代**:Z-buffer 普及,2D 游戏也开始借鉴——Unity / Godot 在 2010s 加了 Layer 系统。
- **2020s 现代引擎**:Layer + SortKey + Y-sort 三层共存,美术自由组合。Casey 的 HH 在 2014-2017 录制,做的是"Y + 手动键"的中间方案。

### 跨语言变体

| 引擎 | 排序字段 | 类型 |
|---|---|---|
| Casey HH | SortKey | uint32(可选) |
| Unity 2D | SortingLayer + OrderInLayer | string + int |
| Godot 2D | z_index + y_sort | int + bool |
| Phaser | depth | int |
| Bevy | `bevy_render::RenderPhase` 的 sort | 自定义 comparator |

Rust 引擎 Bevy 的设计最有意思——它把排序做成 `System`,你写一个 `fn sort_entities(mut query: Query<...>)`,在 `App::add_systems(Update, ...)` 注册。这是"排序作为 ECS 系统"的现代范式,比 Casey 的"硬编码在渲染器里"更模块化,但学习曲线更陡。

### 工业级 vs 教学版

| 特性 | 教学版(今天) | 工业版(Unity) |
|---|---|---|
| 默认排序 | Y + Index | SortingLayer.Default + Y |
| 人工覆盖 | SortKey 字段 | SortingLayer 自定义层 |
| 性能 | qsort 单次 | 多层桶排序 |
| 编辑器集成 | hot-reload 字段 | Unity Inspector |
| 多 sprite | PushBitmap 各自 SortKey | SpriteRenderer 各自 Order |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 选择把"自动 Y 排序"也编码成 SortKey,然后所有 entity 用同一个 uint32 字段排序。为什么不保留两套逻辑——"有手动键的走手动、没手动键的走 Y"两套独立比较?给出至少 2 个理由。

**参考解答**:

1. **统一比较空间**:只有一套比较函数,代码简单。两套的话需要在比较函数里写 `if a.has_manual() && b.has_manual() { ... } else if a.has_manual() { ... } else if b.has_manual() { ... } else { compare_y() }`,四象限分支,容易写错。
2. **性能**:统一排序一次 `sort_by_key` 完成。两套混合的话,要么先分组再排序(两次排序),要么用复杂 comparator(慢)。
3. **可扩展性**:未来加 z-index 或别的维度时,只要扩展 SortKey 编码,比较函数不变。

### Lv2 · 动手实践

**题**:在 Rust 里实现一个最小的 entity 排序系统,要求:

- `Entity` 结构包含 `y: f32`, `index: u32`, `sort_key: Option<u32>`
- `sort_key` 为 `None` 时,用 `(y, index)` 自动排序
- `sort_key` 为 `Some(k)` 时,用 `k` 排序
- 把 Y 编码进 SortKey 空间(`(y + 1000.0) as u32` 大致),保证两套在同一 uint32 比较空间

写一段测试:造 5 个 entity(3 个自动、2 个手动,其中 1 个手动键设为 `u32::MAX` 强制最前),排序后打印顺序,确认符合预期。

**参考解答**:

```rust
#[derive(Debug, Clone)]
struct Entity {
    y: f32,
    index: u32,
    sort_key: Option<u32>,  // None = 自动,Some(k) = 手动
}

impl Entity {
    fn effective_sort_key(&self) -> u32 {
        match self.sort_key {
            // 手动键:直接用
            Some(k) => k,
            // 自动键:把 (y, index) 编码进 u32
            // 假设 Y 范围 [-500, 500],映射到 [0, 1_000_000]
            None => {
                let y_int = ((self.y + 500.0) * 1000.0) as u32;
                // Y 占高位 20 bit,Index 占低位 12 bit(支持 4096 个 entity 同 Y)
                (y_int << 12) | (self.index & 0xFFF)
            }
        }
    }
}

fn main() {
    let mut ents = vec![
        Entity { y: 100.0, index: 0, sort_key: None },              // 自动
        Entity { y: 50.0,  index: 1, sort_key: None },              // 自动
        Entity { y: 0.0,   index: 2, sort_key: None },              // 自动
        Entity { y: 999.0, index: 3, sort_key: Some(u32::MAX) },    // 手动:永远最前
        Entity { y: -999.0,index: 4, sort_key: Some(0) },           // 手动:永远最后
    ];
    // sort_by_key 内部用 stable sort,同 effective_key 保持原序
    ents.sort_by_key(|e| e.effective_sort_key());
    // 预期顺序:手动=0 → 自动(Y=-999 实际不参与,但 manual=0 最小)
    //          → 自动按 Y 升序 → 手动=MAX 最大最后
    for e in &ents {
        println!("y={:6.1} idx={} key={:?} eff={}", 
                 e.y, e.index, e.sort_key, e.effective_sort_key());
    }
}
```

预期输出顺序:`y=999(手动0)` → `y=0(自动)` → `y=50(自动)` → `y=100(自动)` → `y=-999(手动MAX)`。

注意:**手动=0 的 entity 排在所有自动之前**(因为自动 effective_key 至少是 `(0 + 500) * 1000 << 12 = ~2e9`,而手动 0 远小)。这是设计——手动键 0 强制最前,自动按 Y 填中间。

### Lv3 · 迁移设计

**题**:你的网络层要给 packet 排优先级。有三种 packet:控制包(必须最高优先级)、文件数据包(按 seq 排序)、心跳包(优先级最低)。设计一个 `PacketPriority` 类型,要求既能自动按 seq 排序,又支持手动指定优先级,所有 packet 在同一个 priority 比较空间。

提示:借鉴今天 SortKey 的"编码进 uint32"思想,但要考虑 packet 类型作为最高位、seq 作为低位。也要考虑 seq 是 u64 不是 u32,需要降采样或截断。

**提示方向**:

- 3 bit 类型(0=心跳,1=数据,2=控制)放最高位
- 中间位放 seq 的高位(u64 截成 u32)
- 最低位放 hop count 或 timestamp 用于同 seq 内部排序
- 参考 Linux 内核的 `skb->priority` 设计

### Rust:entity 排序系统(完整可跑)

```rust
// Cargo.toml: 无依赖
// src/main.rs

/// Entity 的渲染排序键。
/// 用 newtype 包一层,避免和其他 u32 混淆。
/// Rust 的 newtype 是零开销的(编译后和 u32 一样大),但编译器层面类型隔离。
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
struct SortKey(u32);

impl SortKey {
    /// "永远最前"的哨兵值(渲染时画在最后,即最靠近观察者)
    const FRONT: SortKey = SortKey(u32::MAX);
    /// "永远最后"的哨兵值
    const BACK: SortKey = SortKey(0);

    /// 把 (y, index) 编码成 SortKey。
    /// 假设 y ∈ [-500, 500],映射到 [0, 1_000_000]。
    /// Index 占低 12 bit(支持 4096 个同 Y entity)。
    fn from_auto(y: f32, index: u32) -> Self {
        // 加 500 把负数变正数,再乘 1000 拉开精度
        let y_int = ((y + 500.0).max(0.0).min(1000.0) * 1000.0) as u32;
        // Y << 12 给 index 留位,index & 0xFFF 截断到 12 bit
        SortKey((y_int << 12) | (index & 0xFFF))
    }
}

/// Entity 结构。Option<SortKey> = None 表示"用自动排序"。
#[derive(Debug, Clone)]
struct Entity {
    y: f32,
    index: u32,
    sort_key: Option<SortKey>,
}

impl Entity {
    /// 计算"有效排序键"——有手动键用手动,没有用自动。
    fn effective_key(&self) -> SortKey {
        self.sort_key.unwrap_or_else(|| SortKey::from_auto(self.y, self.index))
    }
}

/// 渲染一组 entity。先排序,再按顺序"画"(这里用打印模拟)。
fn render_entities(entities: &mut Vec<Entity>) {
    // sort_by_key 是稳定排序,同 key 保持原序
    // 稳定性对 entity 闪烁问题至关重要——同 Y 的两个 entity
    // 必须每帧顺序一致,否则会"闪烁"
    entities.sort_by_key(|e| e.effective_key());
    
    println!("--- Render order ---");
    for (drawn_idx, e) in entities.iter().enumerate() {
        println!("[{}] y={:7.1} idx={} key={:?}",
                 drawn_idx, e.y, e.index, e.sort_key);
    }
}

fn main() {
    let mut ents = vec![
        Entity { y: 100.0, index: 0, sort_key: None },                       // 自动
        Entity { y:  50.0, index: 1, sort_key: None },                       // 自动
        Entity { y:   0.0, index: 2, sort_key: None },                       // 自动
        // 吊灯:Y 高但应该永远在玩家头上(画在最前)
        Entity { y: 800.0, index: 3, sort_key: Some(SortKey::FRONT) },
        // 地板装饰:Y 低但永远最后画
        Entity { y: -800.0,index: 4, sort_key: Some(SortKey::BACK) },
    ];
    render_entities(&mut ents);
}
```

**预期输出**:

```
--- Render order ---
[0] y= -800.0 idx=4 key=Some(SortKey(0))
[1] y=   0.0 idx=2 key=None
[2] y=  50.0 idx=1 key=None
[3] y= 100.0 idx=0 key=None
[4] y= 800.0 idx=3 key=Some(SortKey(4294967295))
```

顺序解读:地板(BACK=0)最先画 → 自动 entity 按 Y 升序 → 吊灯(FRONT=MAX)最后画。这就是画家算法 + 手动 SortKey 的完整效果。

**Troubleshooting**:

- **排序结果和预期反了** — 检查 SortKey 的方向。Rust 默认升序(小→大),画家算法要"小的先画(屏幕后面),大的后画(屏幕前面)",所以 effective_key 越大越后画是对的
- **同 Y entity 闪烁** — `sort_by_key` 是稳定的,但 `sort_unstable_by_key` 不是。如果换成 unstable 必须把 index 编进 key
- **整数溢出 panic** — `y + 500` 如果 y 是 NaN 或 Infinity,会 panic。生产代码用 `y.clamp(-500.0, 500.0)` 先夹取
