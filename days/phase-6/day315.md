# Day 315 · 反转排序键顺序

> 昨天 Casey 把 sprite 拆成多层后发现一个 bug:虽然头有更大的 local_sort_bias(=2),但有时候武器反而画在头后面。今天 Casey 排查到根本原因——SortKey 编码方向反了,要做一次"反转"修正。

## 0 · 为什么要有这一天

软件工程里有一个经典经验:**第一次写的代码,~80% 的概率有"方向"错误**。比如循环应该是 `<` 写成了 `>`,坐标应该是 Y 减小画在前面写成了 Y 增大,排序应该是升序结果升序反了。这种 bug 不影响编译运行,只在视觉/行为上表现出"反"。

Casey 在前几天的 SortKey 编码里就踩到了这种坑。他最初的设计是:**SortKey 越大,画在越后面(屏幕前面)**。这看似合理——Y 越大(屏幕下方)越靠近观察者,应该后画。但实际跑起来发现:

1. **头部(更大 bias)被武器(更小 bias)挡住**——因为武器 bias 比 head bias 大,排序后武器在后画,盖住了头。但用户预期"头应该在武器之上"(因为武器在手上,头在手之上)。
2. **Y 大的 entity 应该挡住 Y 小的**——这是正确的。但 sprite 层内部,"头的 sprite" Y 编码部分不应该影响排序,只该看 local_sort_bias。

Casey 的解决方案:**重新审视 SortKey 编码,反转某些字段的"方向"**。具体说,layer 字段"越小画前面"(原来越大画前面),这样 Background 层(Layer=0)反而最先画(屏幕最远)——这是正确的。但 sprite 的 local_sort_bias "越大画前面"(原来越大画后面),这样 head bias=2 比 legs bias=0 更后画(屏幕前面)——这也是正确的。

今天的核心 lesson 不是"加新功能",而是 **"代码演进中如何识别并修正设计错误"**。这是软件工程最常被忽视的能力——新手只学"怎么写新代码",不懂"怎么修旧代码的设计错误"。

心理锚点:今天之后你的 SortKey 编码"方向一致"——所有字段都"越大画前面",不存在反向字段。代码读起来直觉一致,bug 减少。这种"概念一致性"是工程审美的核心。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_render.cpp`,发现一个问题:渲染出来的画面"层级反了"——背景画在前景之上,角色被背景挡住。

经过调试,他发现 SortKey 编码里有一处方向反了。原来:

```c
// 原编码(错):
uint32 SortKey = (Layer << 28) | (Y_encoded << 12) | sprite_offset;
// 升序排序:SortKey 小的先画
// Layer=0(Background) → SortKey 最小 → 先画 → 屏幕后面 ✅
// Layer=3(UI) → SortKey 最大 → 后画 → 屏幕前面 ✅
// 这部分对了

// 但是 Y 方向:
// Y_encoded 越大 → SortKey 越大 → 后画 → 屏幕前面
// 实际游戏中 Y 越大(屏幕下方)越靠近观察者 → 应该后画 ✅
// 这部分也对了

// 问题在哪?
```

Casey 排查后发现:**问题在"屏幕 Y 坐标"vs"世界 Y 坐标"的方向差异**。世界 Y 越大(游戏坐标系下)是"北",对应屏幕上"上"。但屏幕 Y(渲染时)越大是"下"。在屏幕上,"下"是更靠近观察者的——所以世界 Y 越大应该后画,但 Casey 在某处用错了。

修复方案:**统一约定 SortKey 中"越大对应屏幕越前面"**,所有字段一致:

- Layer 越大 → 越前(UI 最前)
- 世界 Y 越大 → 越后(因为世界 Y 大是屏幕下方,更靠近观察者)→ 等等这不对

Casey 重新审视后,选择最简单方案:**让 SortKey 升序排序,小的先画(屏幕后面),大的后画(屏幕前面)**。所有字段"越大越前":

- Layer 大 → 前(UI)
- 世界 Y 大 → 前(南边靠近观察者)
- sprite local bias 大 → 前(头比脚前)

这个统一后,所有字段方向一致,代码可读性提升。

Casey 强调:"修这种 bug 不要试图在比较函数里加 `!`,而要修数据编码方向。在比较函数里加 `!` 是 hack,会导致代码里到处是反向逻辑,后续维护灾难。"

## 2 · 心智模型

### 类比:书页排序

把渲染想成装订一本书。书的页码:

```
第 1 页:封面内
第 2 页:目录
...
第 100 页:封底内
```

页码小 = 装订时先放 = 翻开书时在"后面"。页码大 = 后放 = 翻开书时在"前面"。

如果"页码越大越前面"和"页码越小越前面"两种规则混用——比如目录用"页码大优先",正文用"页码小优先"——装订顺序就乱套了。正确做法:**全本书统一"页码小先装订"**。

今天 Casey 干的事就是这种"统一排序方向"——所有字段都"越大越前",方向一致。

### 严谨原理:SortKey 方向

回顾 SortKey 编码:

```
SortKey (32 bit):
┌─────────┬─────────────────┬──────────┐
│ Layer   │ Y_encoded       │ sprite_idx│
│ 4 bit   │ 16 bit          │ 12 bit   │
└─────────┴─────────────────┴──────────┘
```

**升序排序**(小→大)的语义:**SortKey 小的先画**。

| 字段 | 大值含义 | 应该先画? | 正确方向 |
|---|---|---|---|
| Layer | UI(=5) | 否(UI 后画) | Layer 大 → 后画 ✅(升序中 Layer 大的 SortKey 大) |
| Y_encoded | 世界 Y 大(屏幕下方) | 否(屏幕下方后画,靠近观察者) | Y 大 → 后画 ✅ |
| sprite_idx | head(=2) | 否(head 后画,屏幕前面) | sprite_idx 大 → 后画 ✅ |

所有字段方向一致:**大 → 后画**(升序排序)。Casey 在最初版本里某处搞反了,今天修正。

### 反转技巧:bitwise NOT

如果某个字段方向反了,可以用 bitwise NOT 反转:

```c
// 假设 Layer 方向反了(Layer 小应该后画,但编码成了小先画)
uint32 SortKey = ((~Layer & 0xF) << 28) | ...
// ~0 = 0xF(15),~3 = 0xC(12),~5 = 0xA(10)
// 现在 Layer=0(Background)变成高位 15,SortKey 最大,后画 ✅
```

但 Casey 不推荐这种方式——`~` 增加认知负担,看代码的人要 reverse-engineer。**正确做法是改 Layer 枚举值**,让 Background=最大、UI=最小,这样不用 `~` 就一致。

```rust
#[repr(u8)]
enum Layer {
    UI          = 0,  // 最先画(后面),所以 SortKey 最小
    Particles   = 1,
    Foreground  = 2,
    Game        = 3,
    Tile        = 4,
    Background  = 5,  // 最后画(后面),所以 SortKey 最大... 等等
}
```

等一下,这又反了!正确的方向应该是 Background 先画(它最远),所以 SortKey 最小:

```rust
enum Layer {
    Background = 0,  // 先画(远)
    Tile = 1,
    Game = 2,
    Foreground = 3,
    Particles = 4,
    UI = 5,  // 后画(近)
}
```

升序排序时,Background(0)最小,先画;UI(5)最大,后画。这就是"升序 + Layer 越大越前"的一致约定。Casey 最初的版本就是这样,但他可能在某处又用反了——今天的修复是回到这个一致约定。

### 为什么不在比较函数里加 NOT

考虑这种代码:

```c
// 错误做法:在比较函数里加 NOT
int compare(Entity* a, Entity* b) {
    return -((int)a->sort_key - (int)b->sort_key);  // 反向
}
```

这看似能修 bug,但:

1. **认知负担**:看代码的人要意识到"这里反向了",容易忘
2. **维护灾难**:如果以后加新字段,谁该正向谁该反向?无法 predict
3. **性能损失**:额外的负号运算(虽然微小)

正确做法:**修数据编码**,让所有字段方向一致,比较函数永远 `a.sort_key - b.sort_key`(升序)。这就是 Casey 强调的"在源头修,不在下游 hack"。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业里"排序方向"的常见坑:

- **Y 方向**:Unity 世界 Y 朝上(数学约定),但屏幕 Y 朝下(图形学约定)。一个 sprite 在 Unity 世界 Y=10,对应屏幕 Y=-10(屏幕上方)。这种"两个 Y 方向相反"是新手最大的困惑源。
- **Z 方向**:Unity 默认 +Z 朝相机(右手坐标系),Unreal 默认 +Z 朝上(左手坐标系),Godot 默认 +Z 朝下(也是右手但解释不同)。3D 引擎的 Z 方向不统一,迁移项目时小心。
- **angle 方向**:2D 角度,数学约定"逆时针为正",但图形学有时用"顺时针为正"(因为屏幕 Y 反)。Casey 在 Day 044 反射向量时踩过这个坑。

行业共识:**所有方向统一约定并写在文档里**,不要"按场景"决定方向。比如 Unity 文档明确"Y 朝上、Z 朝相机",所有 API 一致。

### 3.2 · 🎨 图形学视角

图形学里"排序方向"在两个层面:

1. **画家算法**:从后往前画(远先画),所以 SortKey 升序排序,小的先画。
2. **Z-buffer**:每像素存 Z,**近覆盖远**(近的 Z 小,远的 Z 大,新像素 Z 小则覆盖)。所以 Z-buffer 是"Z 小优先"。

注意画家算法和 Z-buffer 方向**相反**——画家算法"先画的在后面"(被覆盖),Z-buffer"小 Z 的覆盖"(在前面)。这种"算法不同方向不同"是图形学的常见混淆。

OpenGL 的深度测试默认 `GL_LESS` —— 新 fragment 的 Z 比 buffer 里的小就通过测试(覆盖)。所以 OpenGL 里"近"= Z 小。但 Direct3D 默认相反,Direct3D 习惯用 `GL_GREATER` + reversed-Z(避免 Z 冲突)。这种"API 之间方向不统一"是 3D 编程的另一个坑。

Casey 的渲染器是 CPU 端画家算法,默认"小先画"。和 OpenGL 的"小近"一致。

### 3.3 · 🐧 Linux 系统编程视角

Linux 命令行里"排序方向"用 `-r` 反转:

```bash
# 默认升序
sort nums.txt
1
2
3

# 降序
sort -r nums.txt
3
2
1

# 数字排序(避免 "10" < "2" 字典序问题)
sort -n nums.txt
```

`-r` flag 在 `ls`(显示顺序)、`grep`(匹配顺序)里也用。Linux 的设计哲学:**默认升序,加 flag 反向**——和 Casey 的"统一方向,不用反向 flag"哲学相反。Linux 这样是因为命令行需要灵活性(临时反向),Casey 那样是因为引擎追求一致性。

### 3.4 · 🦀 Rust 生态视角

Rust 排序的方向控制:

```rust
// 升序(默认)
v.sort();

// 降序(用 reverse 比较器)
v.sort_by(|a, b| b.cmp(a));

// 或 sort_by_key + 逆变
v.sort_by_key(|x| std::cmp::Reverse(*x));
// std::cmp::Reverse 是个 newtype 包装,反转 Ord 实现
```

`std::cmp::Reverse` 是 Rust 标准库提供的"反转比较"工具——它是个 newtype(`Reverse<T>(T)`),derive `Ord` 时反转内部 `T` 的比较方向。这是干净的"反转",不污染数据本身。

```rust
use std::cmp::Reverse;

let mut v = vec![3, 1, 4, 1, 5];
v.sort_by_key(|x| Reverse(*x));  // 降序
// 结果:[5, 4, 3, 1, 1]
```

Rust 的 `Reverse` 比 C 的 `~` 或加负号更类型安全——`Reverse<T>` 在编译期就知道它是反向的,不会混淆。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Concept consistency(概念一致性)** — 所有字段方向一致,代码可读
- **Bug category: direction error(方向错误)** — 一类常见 bug
- **Convention over configuration(约定优于配置)** — 统一约定,减少选项

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 统一方向(今天) | 所有字段方向一致 | 长期维护 | ✅ 今天的修复 |
| 比较函数反向 | 比较时加 NOT | 临时修复 | 不推荐 |
| Reverse<T>(Rust) | newtype 包装 | 临时反向 | 备选 |
| 多套 SortKey | 不同场景不同 key | 极复杂场景 | 暂不需要 |

### 4.3 下级(内部零件)

- **字段方向约定** — Layer/Y/sprite_idx 各自含义
- **Layer 枚举值** — 从小到大对应"远→近"
- **Y 编码方向** — 世界 Y 大 = 屏幕下 = 近
- **sprite_idx 方向** — bias 大 = 前(头比脚前)
- **统一比较函数** — `sort_by_key(|e| e.sort_key)` 永远升序

## 5 · 对照与变奏

### 历史演化

- **早期 CPU 渲染**:每个引擎自定义 SortKey,方向五花八门。
- **OpenGL 普及后**:OpenGL 的"Z 小近"成为事实标准,但 Direct3D 反向,引擎要根据 API 调整。
- **reversed-Z 技术**:2010s 后为了 Z 精度,主流引擎都用 reversed-Z(把"近"映射到 Z=1,远的到 Z=0),配合 `GL_GREATER` 深度测试。reversed-Z 提高深度精度,减少 Z 冲突。
- **现代 GPU-driven**:GPU 端排序用 compute shader,方向由 shader 代码决定,但 CPU 端依然需要 SortKey 概念做"绘制顺序"决策。

### 工业级 vs 教学版

| 特性 | 教学版(今天) | 工业版(Unreal) |
|---|---|---|
| 排序方向 | 统一"大后画" | 同统一,但支持 reversed-Z |
| 字段数量 | 3(Layer, Y, sprite) | 5+(Layer, section, Y, mesh, face) |
| 调试工具 | printf | RenderDoc 看每 draw 的 SortKey |
| 文档 | 代码注释 | 引擎文档 + 教程 |

### 跨语言变体

| 引擎 | 排序方向 |
|---|---|
| Casey HH | Layer 大 → 前(升序) |
| Unity 2D | SortingLayer 在 SortingLayer 表里大 → 前 |
| Godot | z_index 大 → 前 |
| OpenGL Z | 默认 Z 小 → 前(GL_LESS) |
| Direct3D Z | 默认 Z 大 → 前(但 reversed-Z 常见) |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 强调"修方向 bug 不要在比较函数里加 NOT,要修数据编码"。这种说法的根本原因是什么?给出至少 2 个理由。

**参考解答**:

1. **认知一致性**:数据编码方向一致,读代码的人不需要"在心里反转"。比较函数里加 NOT 强迫读者每次读都要反向思考,认知负担大。
2. **维护性**:数据编码修一次,所有调用方自动正确。比较函数里加 NOT 是"局部修复",每加一个新字段都要决定"要不要 NOT",容易漏。
3. **类型安全**:Rust 的 `Reverse<T>` 是 newtype,编译期就标记"这是反向",不会混淆。C 的负号或 `~` 是运算符,没有类型保护,容易写错。
4. **可调试性**:数据一致时,printf SortKey 就能看出顺序对错。如果比较函数反向,printf 出来的值和实际顺序对不上,调试困难。

### Lv2 · 动手实践

**题**:用 Rust 模拟"方向 bug + 修复"过程。要求:

1. 先写一个"故意方向反"的 SortKey 编码——比如让 Layer=UI(原本该最后画)的 SortKey 最小(导致最先画)
2. 创建几个 entity,排序后看到错误的画面(UI 在背景下面)
3. 修编码,让 Layer=UI 的 SortKey 最大(正确)
4. 验证修复

**参考解答**:

```rust
// ============ BUGGY 版本 ============
fn encode_buggy(layer: u8, y: f32, sprite_idx: u16) -> u32 {
    // 故意让 Layer 反向(大 Layer 先画,导致 UI 在背景下面)
    let layer_bits = ((0xF - (layer & 0xF)) as u32) << 28;  // 反向!
    let y_enc = (((y + 500.0) / 1000.0) * 65535.0) as u32 & 0xFFFF;
    layer_bits | (y_enc << 12) | (sprite_idx as u32 & 0xFFF)
}

// ============ FIXED 版本 ============
fn encode_fixed(layer: u8, y: f32, sprite_idx: u16) -> u32 {
    let layer_bits = (layer as u32) << 28;
    let y_enc = (((y + 500.0) / 1000.0) * 65535.0) as u32 & 0xFFFF;
    layer_bits | (y_enc << 12) | (sprite_idx as u32 & 0xFFF)
}

fn main() {
    let ents: Vec<(&str, u8, f32)> = vec![
        ("Background", 0, -500.0),
        ("Game",       2, 50.0),
        ("UI",         5, 999.0),
    ];
    
    println!("--- BUGGY (UI 反向,UI 会在最前画) ---");
    let mut v: Vec<(u32, &str)> = ents.iter()
        .map(|(n, l, y)| (encode_buggy(*l, *y, 0), *n))
        .collect();
    v.sort_by_key(|e| e.0);
    for (i, (k, n)) in v.iter().enumerate() {
        println!("[{}] sort_key={:#010x} name={}", i, k, n);
    }
    // 输出错误:Background 最后画(应该在最前画)
    
    println!("\n--- FIXED (统一方向) ---");
    let mut v: Vec<(u32, &str)> = ents.iter()
        .map(|(n, l, y)| (encode_fixed(*l, *y, 0), *n))
        .collect();
    v.sort_by_key(|e| e.0);
    for (i, (k, n)) in v.iter().enumerate() {
        println!("[{}] sort_key={:#010x} name={}", i, k, n);
    }
    // 输出正确:Background 先画 → Game → UI
}
```

预期输出:
- BUGGY 顺序:UI → Game → Background(UI 先画,屏幕最远,被 Game 和 Background 盖住)
- FIXED 顺序:Background → Game → UI(UI 最后画,屏幕最前,正确)

### Lv3 · 迁移设计

**题**:你的"撤销栈"(undo stack)有方向 bug——用户按 Ctrl+Z 应该回到上一个状态,但实际跳到了下一个状态。排查后发现是栈的 push/pop 方向反了。设计一个统一的"时间方向"约定,让 undo/redo、动画时间线、网络延迟补偿都用同一方向。

提示:借鉴今天的"统一方向"哲学。约定"时间增加 = 向未来走",undo 是"减小时间",redo 是"增加时间"。栈、缓冲区、时间戳都用这个方向。

**提示方向**:

- 用 i64 表示"逻辑时间",0 = 当前,负 = 过去,正 = 未来
- undo stack push 当前状态,标 timestamp=0,push 后所有旧状态 timestamp -= 1
- redo 反向

### Rust:方向一致 + 修复演示(完整可跑)

```rust
// Cargo.toml: 无依赖
// src/main.rs

use std::cmp::Reverse;

/// Layer 枚举,值表示"越大越靠前(屏幕前面)"
#[repr(u8)]
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
enum Layer {
    Background = 0,
    Tile = 1,
    Game = 2,
    Foreground = 3,
    Particles = 4,
    UI = 5,
}

/// 正确的 SortKey 编码:所有字段"越大越前"(升序排序)
fn encode(layer: Layer, y: f32, sprite_idx: u16) -> u32 {
    let layer_bits = (layer as u32) << 28;
    let y_clamped = y.clamp(-500.0, 500.0);
    let y_enc = (((y_clamped + 500.0) / 1000.0) * 65535.0) as u32 & 0xFFFF;
    let y_bits = y_enc << 12;
    let sprite_bits = (sprite_idx as u32) & 0xFFF;
    layer_bits | y_bits | sprite_bits
}

#[derive(Debug, Clone)]
struct RenderEntry {
    sort_key: u32,
    layer: Layer,
    y: f32,
    name: &'static str,
}

fn collect_and_sort(entries: &mut Vec<RenderEntry>, label: &str, reverse: bool) {
    if reverse {
        // 用 Reverse<T> 反转方向,不改数据
        entries.sort_by_key(|e| Reverse(e.sort_key));
    } else {
        // 默认升序:小的先画(屏幕后面)
        entries.sort_by_key(|e| e.sort_key);
    }
    println!("=== {} ===", label);
    for (i, e) in entries.iter().enumerate() {
        println!("[{}] layer={:?} y={:7.1} name={:10} key={:#010x}",
                 i, e.layer, e.y, e.name, e.sort_key);
    }
    println!();
}

fn main() {
    let mut entries = vec![
        RenderEntry { sort_key: encode(Layer::Background, -500.0, 0), layer: Layer::Background, y: -500.0, name: "Mountain" },
        RenderEntry { sort_key: encode(Layer::Game, 50.0, 0),        layer: Layer::Game,       y: 50.0,   name: "Player"  },
        RenderEntry { sort_key: encode(Layer::Game, 50.0, 2),        layer: Layer::Game,       y: 50.0,   name: "P-Head"  },
        RenderEntry { sort_key: encode(Layer::UI, 999.0, 0),         layer: Layer::UI,         y: 999.0,  name: "Cursor"  },
    ];
    
    // 正常:升序排序,小→大,小先画
    collect_and_sort(&mut entries.clone(), "ASCENDING (default, correct)", false);
    // 输出:Mountain → Player → P-Head → Cursor
    
    // 反转:用 Reverse<T>,大→小,大先画
    // 这相当于"画家算法反向",会导致 UI 被背景盖住
    collect_and_sort(&mut entries.clone(), "DESCENDING (Reverse<T>, wrong direction)", true);
    // 输出:Cursor → P-Head → Player → Mountain(灾难!)
}
```

**预期输出**:

```
=== ASCENDING (default, correct) ===
[0] layer=Background y= -500.0 name=Mountain  key=0x00000000
[1] layer=Game       y=  50.0  name=Player    key=0x281f4000
[2] layer=Game       y=  50.0  name=P-Head    key=0x281f4002
[3] layer=UI         y= 999.0  name=Cursor    key=0x5fff0000

=== DESCENDING (Reverse<T>, wrong direction) ===
[0] layer=UI         y= 999.0  name=Cursor    key=0x5fff0000
[1] layer=Game       y=  50.0  name=P-Head    key=0x281f4002
[2] layer=Game       y=  50.0  name=Player    key=0x281f4000
[3] layer=Background y= -500.0 name=Mountain  key=0x00000000
```

解读:升序是正确的(背景先画),降序是错误的(UI 先画,会被后续 entity 盖住)。`Reverse<T>` 是工具,但要用对方向。
