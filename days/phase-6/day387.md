# Day 387 · 多重采样深度剥离的进一步尝试

> Day 386 写了自定义 resolve,深度不再平均。但 Casey 发现**真正的 MSAA 深度剥离**应该是 per-sample 的——每像素 4 个采样,每个采样独立做 N 层 peel。今天他尝试实现这个,**还是遇到问题**——又是"卡住"的一天。

## 0 · 为什么要有这一天

Day 386 的 resolve 解决了"深度不能平均"的问题,但**暴露了更深的**:深度剥离本身是 per-pixel 的,即每像素只有一个"第一层深度"和一个"第二层深度"。但 MSAA 下每像素 4 个采样,**4 个采样各自的"第一层"和"第二层"可能不同**。

举例:像素 P 的 4 个采样:

- 采样 0:在不透明地面(z=0.5),第一层
- 采样 1:在玻璃前表面(z=0.3),第一层(玻璃比地面近)
- 采样 2:在玻璃前表面(z=0.3),第一层
- 采样 3:在玻璃后表面(z=0.4),第二层(被前表面挡)

如果用 Day 386 的"取最小"resolve,P 的第一层 = 0.3(采样 1, 2)。但**采样 0 不在第一层**(它在 0.5,被忽略)。然后第二层:应该取"严格大于 0.3 的最小深度"——是采样 0 (0.5) 还是采样 3 (0.4)?

**问题**:Day 386 的 resolve 是**先 resolve 第一层深度**,再 resolve 第二层深度。但**采样 0 和采样 3 各有自己的"第二层语义"**——采样 0 的第二层是无(它的第一层就是地面,没有更远的层),采样 3 的第二层是 0.4(玻璃后表面)。两者**不能合并**为一个"像素第二层"。

**真正的 MSAA 深度剥离** 应该 per-sample:

- 每个采样独立做 N 层 peel
- 合成时,每个采样独立算"我的合成颜色"
- 最后 resolve 时,4 个采样的合成颜色**平均**

这是 Casey 今天尝试的方向。但实现复杂:multisample texture 存 N 层 × 4 采样 = 4N 个浮点数 per pixel。然后**合成 shader 也要 per-sample**——需要 `glMinSampleShadingARB(1.0)` 强制每采样执行 fragment shader。

**今天的产出**:Casey 试了 per-sample peel,但**bug 不断**——某些采样的第二层缺失,合成出现空洞;某些 GPU 上 sample shading 不工作(Mesa bug);性能下降严重(4 倍 fragment shader)。Casey 决定**明天(Day 388)** 改用简化方案。

心理锚点:看完今天,你能(1)解释 per-pixel 和 per-sample 深度剥离的差别;(2)知道 sample shading 怎么开;(3)理解为什么 sample shading 性能差;(4)看到"完美主义 vs 工程妥协"的真实权衡。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 流程:

1. **承认 Day 386 局限**:resolve 把多采样合并为单采样,丢失了"per-sample 层"的语义。
2. **重新设计**:per-sample 深度剥离——multisample texture 的每个采样独立 peel。
3. **实现**:
   - Multisample color + depth texture
   - Fragment shader 用 `gl_SampleID` 区分采样
   - 用 sample shading(`glMinSampleShadingARB(1.0)`)
4. **遇到 bug 1**:NVIDIA 上 sample shading 工作,但 Intel / Mesa 上不工作(fragment shader 还是每像素一次)。
5. **遇到 bug 2**:某些采样的"第二层"为空(没有更远的 fragment),合成时这些采样贡献黑色,边缘发暗。
6. **遇到 bug 3**:性能 4 倍下降,sample shading 开销巨大。
7. **决定**:接受一个**简化方案**——不 per-sample,而是用 "alpha to coverage"(把 alpha 映射到 sample mask),让 MSAA 的边缘采样自动选择哪层。明天(Day 388)实现。

这集教学价值:**完美方案 vs 工程现实**。理论上 per-sample 是对的,但驱动 / 硬件 / 性能约束让你做不到。妥协是真实工程。

## 2 · 心智模型

### 类比:精算师 vs 统计师

设想你要估算"一群人每月支出"。

**Per-pixel(粗糙)**:把所有人**取平均**得到一个数字。简单但失真——高消费者和低消费者被平均成中位数。

**Per-sample(精细)**:把人分成 N 组,每组独立估算,最后**组内取平均 + 组间合并**。精确但贵——N 倍工作量。

**妥协**:不用 N 组,用"加权平均"(高消费者权重高)。这就是 alpha to coverage 的思路——不真的 N 倍计算,而是用 sample mask 模拟。

### 严谨原理:Per-sample vs per-pixel

**Per-pixel fragment shader**(默认):每像素执行一次,4 个采样共享一个 fragment shader 输出。

```
Pixel (x, y):
    Sample 0: (x+0.125, y+0.125) -> 在三角形内吗?
    Sample 1: (x+0.375, y+0.625) -> 在三角形内吗?
    Sample 2: (x+0.875, y+0.125) -> 在三角形内吗?
    Sample 3: (x+0.625, y+0.875) -> 在三角形内吗?
    
    coverage = 0b0011  // 假设采样 0,1 在内,采样 2,3 在外
    
    // fragment shader 在像素中心 (x+0.5, y+0.5) 执行一次
    color = fragment_shader(pixel_center)
    
    // 写入到所有 coverage 内的采样
    for sample in coverage:
        framebuffer[sample] = color
```

**Per-sample fragment shader**(sample shading):每采样执行一次。

```
Pixel (x, y):
    coverage = 0b0011
    
    for sample in coverage:
        sample_pos = sample_position(sample)
        color = fragment_shader(sample_pos)  // 每采样执行一次!
        framebuffer[sample] = color
```

开销:fragment shader 执行次数 = coverage 数(平均 2 次,边缘像素)到 4 次(全在三角形内)。

**GLSL 触发 sample shading**:`glMinSampleShadingARB(f)`(`f` 是 0..1):

- `f=0`:per-pixel(默认)
- `f=1`:per-sample(每 coverage 内的采样都执行)
- `f=0.5`:至少执行 `ceil(f * N)` = 2 次

在 fragment shader 里,`gl_SampleID` 内置变量给出当前采样 ID(0..N-1)。

### Per-sample 深度剥离的实现

```glsl
#version 450
#extension GL_ARB_sample_shading : require

uniform sampler2DMS prev_depth_ms;
out vec4 frag_color;
out float frag_depth;

void main() {
    int sample_id = gl_SampleID;
    ivec2 px = ivec2(gl_FragCoord.xy);
    float prev_depth = texelFetch(prev_depth_ms, px, sample_id).r;
    
    // 当前 fragment 的深度
    float z = gl_FragCoord.z;
    
    // 严格大于 prev_depth 才通过(第二层 peel)
    if (z <= prev_depth + 1e-4) {
        discard;
    }
    
    frag_color = compute_color();
    frag_depth = z;
}
```

注意:

- `gl_SampleID` 自动给当前采样 ID
- `texelFetch(prev_depth_ms, px, sample_id)` 读**该采样的**深度(不是平均)
- 必须 `#extension GL_ARB_sample_shading : require` + CPU 端开 `glMinSampleShadingARB(1.0)`

### Alpha to coverage(备选方案)

Alpha to coverage 把 fragment 的 alpha 映射到 sample mask:

- `alpha = 1.0`:全部 4 个采样通过
- `alpha = 0.5`:2 个采样通过(哪些由 GPU 决定)
- `alpha = 0.25`:1 个采样通过

OpenGL 开启:`glEnable(GL_SAMPLE_ALPHA_TO_COVERAGE)`。

**优点**:

- 不需要 sample shading(开销 1x,不是 4x)
- MSAA 自动处理 alpha 边缘(透明度 50% 的像素,4 采样中 2 个画、2 个不画,看起来平滑)

**缺点**:

- **不是真深度剥离**——alpha to coverage 把"半透明"变成"部分采样不画",丢失了"玻璃后面的物体可见"的语义
- 不适合多层半透明(alpha 不能精确控制"第几层")

Casey Day 387 试 per-sample 失败,Day 388 决定用 alpha to coverage 作为**折衷**——边缘抗锯齿(主要目标),深度剥离简化(只对不透明边缘做 MSAA,半透明物体保持普通深度剥离)。

### 为什么 per-sample 在 Mesa 上失败?

Mesa(开源 OpenGL 实现)对 sample shading 的支持参差不齐:

- **radeonsi**(AMD):完整支持
- **iris**(Intel Gen 8+):完整支持
- **llvmpipe**(软件):支持但慢
- **crocus**(Intel Gen 4-7):部分支持,可能不工作

Casey 在 NVIDIA proprietary 上测试通过,但**社区用户报告 Mesa 上不工作**。这是开源驱动的现实——某些扩展在开源驱动上不可靠。

**修法**:不依赖 sample shading,改用 alpha to coverage(更广泛支持)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业界游戏**几乎不用 per-sample 深度剥离**——太贵了。常见方案:

- **不用深度剥离**:大多数游戏对半透明物体用画家算法 + 排序 hack
- **WBOIT**(单 pass OIT):不需要 per-sample,但近似
- **Alpha to coverage**:半透明物体改为"随机采样",边缘抗锯齿
- **Stochastic transparency**:每帧随机选一个采样,跨帧累积(TAA)

Casey 选深度剥离是**教学目的**——展示精确算法。生产游戏做权衡。

### 3.2 · 🎨 图形学视角

**End-to-end MSAA pipeline**:

1. Geometry pass:每像素多采样几何测试
2. Fragment shader:per-pixel 或 per-sample
3. Blend:每采样独立 blend(默认)或 per-pixel blend
4. Resolve:合并多采样到单采样

深度剥离卡在 step 2(每采样独立 shader)和 step 4(每采样独立 resolve)。

**Sample shading 的真实开销**:

- Pixel center 的 gradient 计算失效(不同采样有不同 gradient)
- Texture fetch 增加(每采样独立采样)
- Branching 增加(不同采样的 if 分支不同)

工业界用 sample shading 的场景:

- **VR rendering**:左右眼各一份 sample shading,避免边缘闪烁
- **Procedural textures**:程序纹理的边缘细节
- **Custom AA**:某些自定义抗锯齿算法

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:per-pixel fragment shader 和 per-sample fragment shader 的根本区别是什么?为什么后者贵 4 倍?

**参考解答**:

**Per-pixel**(默认):每像素执行一次 fragment shader,在像素中心采样。4 个采样的 coverage(在三角形内的位图)决定 shader 输出写入哪些采样,但 shader 本身只算一次。

**Per-sample**(`glMinSampleShadingARB(1.0)`):每个 coverage 内的采样独立执行 fragment shader。如果像素 4 个采样都在三角形内,fragment shader 执行 4 次;2 个在内执行 2 次;等等。

**贵 4 倍**:worst case(全在三角形内)= 4 次执行,所以 4x 开销。avg case(边缘像素 50% coverage)= 2x。但 GPU 调度开销让实际更接近 4x。

### Per-sample 深度剥离(尝试版)

```toml
[package]
name = "persample_attempt"
version = "0.1.0"
edition = "2021"
[dependencies]
glium = "0.34"
```

```rust
// src/main.rs
use glium::{glutin, Surface, program, index, texture, framebuffer, implement_vertex, uniform};
use std::cell::Cell;

#[derive(Copy, Clone)]
struct Vertex { position: [f32; 2] }
implement_vertex!(Vertex, position);

#[derive(Copy, Clone)]
struct Settings { sample_shading: bool }
impl Default for Settings { fn default() -> Self { Self { sample_shading: false } } }

fn main() {
    let event_loop = glutin::event_loop::EventLoop::new();
    let wb = glutin::window::WindowBuilder::new()
        .with_inner_size(glutin::dpi::LogicalSize::new(800, 600));
    let cb = glutin::ContextBuilder::new();
    let display = glium::Display::new(wb, cb, &event_loop).unwrap();

    // 获取 raw OpenGL 函数指针(用于 sample shading)
    let gl = display.gl();

    let settings = Cell::new(Settings::default());

    let (w, h) = (800u32, 600u32);
    let msaa_samples = 4u32;

    let color_ms = texture::Texture2DMultisample::new(
        &display, texture::UncompressedFloatFormat::F32F32F32F32,
        w, h, msaa_samples, true).unwrap();
    let depth_ms = texture::DepthTexture2DMultisample::new(
        &display, texture::DepthFormat::F32, w, h, msaa_samples, true).unwrap();

    let mut fbo_ms = framebuffer::SimpleFrameBuffer::with_depth_texture(
        &display, &color_ms, &depth_ms).unwrap();

    let verts = vec![
        Vertex { position: [-0.7, -0.7] },
        Vertex { position: [ 0.7, -0.7] },
        Vertex { position: [ 0.0,  0.7] },
    ];
    let vbuf = glium::VertexBuffer::new(&display, &verts).unwrap();
    let indices = index::NoIndices(index::PrimitiveType::TrianglesList);

    // Per-sample fragment shader(用 gl_SampleID 显示采样 ID)
    let program = program!(&display,
        450 core => {
            vertex: r#"#version 450
                in vec2 position;
                void main() { gl_Position = vec4(position, 0.5, 1.0); }
            "#,
            fragment: r#"#version 450
                #extension GL_ARB_sample_shading : require
                out vec4 frag;
                void main() {
                    // 用 gl_SampleID 着色,如果 sample shading 工作会有变化
                    float t = float(gl_SampleID) / 4.0;
                    frag = vec4(t, 1.0 - t, 0.5, 1.0);
                }
            "#,
        }).unwrap();

    event_loop.run(move |event, _, control_flow| {
        use glutin::event::{Event, WindowEvent, KeyboardInput, ElementState, VirtualKeyCode};
        use glutin::event_loop::ControlFlow;
        *control_flow = ControlFlow::Wait;

        match event {
            Event::WindowEvent { event: WindowEvent::KeyboardInput {
                input: KeyboardInput { state: ElementState::Pressed,
                                       virtual_keycode: Some(VirtualKeyCode::F4), .. }, ..
            }, .. } => {
                let mut s = settings.get();
                s.sample_shading = !s.sample_shading;
                settings.set(s);
                println!("sample_shading: {}", s.sample_shading);
            }
            Event::RedrawRequested(_) => {
                let s = settings.get();

                // 切换 sample shading
                unsafe {
                    if s.sample_shading {
                        // gl::Enable(gl::SAMPLE_SHADING);  // 需要 raw gl 调用
                        // gl::MinSampleShadingARB(1.0);
                    } else {
                        // gl::Disable(gl::SAMPLE_SHADING);
                    }
                }

                let mut target = display.draw();
                target.clear_color(0.1, 0.1, 0.1, 1.0);
                target.draw(&vbuf, &indices, &program, &glium::uniforms::EmptyUniforms,
                    &Default::default()).unwrap();
                target.finish().unwrap();
            }
            Event::WindowEvent { event: WindowEvent::CloseRequested, .. } => {
                *control_flow = ControlFlow::Exit;
            }
            _ => {}
        }
    });
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
