
# Day 314 · 拆分精灵为层

> 把"角色 = 一张图"升级成"角色 = 多张图(脚 / 身 / 头)",让美术能独立画每个部分、动画能独立动每个部分、排序能独立排每个部分。这是 2D 角色动画工业标准做法的起点。

## 0 · 为什么要有这一天

到目前为止,你的游戏角色是一张完整的 sprite——玩家是一个 32×64 的 PNG,走路时整张图切换。这种方式有两个根本问题:

1. **动画帧数爆炸**:走路 8 帧 × 朝向 4 个 = 32 张图。跑步再加 8 帧 × 4 = 64 张。攻击 6 帧 × 4 = 24 张。一个角色轻松 100+ 帧。美术画到崩溃,内存吃到撑。
2. **无法组合**:"边走边挥剑"需要走路 + 攻击同时播放,但你只有"走路动画"和"攻击动画"两套独立序列,合成不了。除非美术单独画"走+挥"的 32 张图。

业界早在 1980s 就找到了答案:**sprite 拆分**。把角色拆成独立部件:

- 脚(legs):独立动画(走路循环)
- 身(torso):独立动画(呼吸、攻击)
- 头(head):独立动画(转头、眨眼)
- 武器(weapon):独立动画(挥砍)

每个部件独立画、独立动画、独立排序。组合起来:

- 走路时:脚播走路循环,身和头静止(或微动)
- 挥剑时:脚静止,身播挥剑,武器播挥砍
- 边走边挥:脚走路 + 身挥剑 + 武器挥砍,**不需要额外美术**

动画帧数从 100+ 降到 30 左右,内存省一半,美术工作量减半。这是 2D 游戏(尤其是 RPG、动作游戏)的工业标准做法——`Factorio`、`Don't Starve`、`Stardew Valley` 都用这种技术。

今天的 Casey 工作:**把 entity 的 sprite 从单张升级为多层 sprite**。每个 entity 可以有 `legs_sprite`、`torso_sprite`、`head_sprite` 三个独立 sprite,各有自己的 SortKey(身前的画在身后,头永远在身之上)。这恰好用上昨天和前天铺垫的 SortKey + Layer 系统。

心理锚点:今天之后你的角色是"组合体"——脚、身、头独立动画,武器挂在手上独立挥砍。这是从"贴图游戏"迈向"动画化游戏"的关键一步。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_entity.cpp`,给 entity 的"可绘制部分"做了一次结构升级。原来是:

```c
struct entity {
    // ...
    bitmap_id HeroBitmap;  // 单张图
};
```

今天改成:

```c
struct entity {
    // ...
    // 多个 sprite 层(脚 / 身 / 头),每层独立 bitmap 和 SortKey
    entity_sprite_layer SpriteLayers[4];
    uint32 LayerCount;
};

struct entity_sprite_layer {
    bitmap_id Bitmap;
    uint32 SortKey;       // 局部 SortKey,会加到 entity 的全局 key 上
    v2 Offset;            // 相对 entity 中心的偏移
};
```

关键动作:

1. 给 `entity` 加 `SpriteLayers` 数组(最多 4 层,留余量)
2. 修改 `PushBitmap` 渲染入口,循环遍历所有层,每层独立 push
3. 每层的 SortKey 在 entity 全局 SortKey 基础上**加局部偏移**——`head` 加 +2,`torso` 加 +1,`legs` 加 0,保证头永远在身之上

Casey 在视频里讨论了一个设计选择:**SpriteLayers 是数组还是 enum 字段**(显式 `Legs`、`Torso`、`Head` 字段)。最终选择数组,因为:

- 未来加新层(比如"披风"、"光环")不用改 struct
- 排序时直接遍历,不用 if-else
- 数组可以用 SIMD 批量 push

但代价是:**美术在编辑器里要记每个 index 对应什么**(0=脚,1=身,2=头)。Casey 在 `handmade_render.h` 写了详细注释。

另一个关键点:**每层的 Offset 相对 entity 中心,不是绝对屏幕坐标**。这让"entity 移动时所有 sprite 一起跟着移",不用单独更新每个 sprite 的位置。这是 DOD(Data-Oriented Design)思想——把"位置"放在 entity 上,"偏移"放在 sprite 层上。

Casey 还花时间讨论了一个细节:**层之间的"重叠"是否要做抗锯齿**。比如头部 sprite 的边缘如果和身部 sprite 的边缘恰好重叠 1 像素,alpha 混合会变成"半透明边"。Casey 选择"美术负责不重叠",引擎不做特殊处理。这是工程上的简化,工业引擎(Unity)会用 "depth bias" 自动避免。

## 2 · 心智模型

### 类比:纸片人偶

把游戏角色想象成一个**多层纸片人偶**:

```
剪出 4 张纸片:
[头]
[身]
[脚]
[剑]

用图钉穿过 4 张纸片的中心点 → 一个木偶
图钉 = entity 中心 = sprite_offset(0, 0)
纸片相对图钉的偏移 = sprite_offset

走路动画 = 把"脚"纸片左右晃,其他不动
挥剑动画 = 把"剑"和"身"纸片旋转,其他不动
```

每张纸片(每层 sprite)独立摆动、独立排序。整体看起来就是一个会动的角色。这种"纸片人偶"模型在动画制作里叫 **cut-out animation**(剪纸动画),是 South Park、Monty Python 等作品的招牌风格。

### 严谨原理:每层独立 SortKey

每个 sprite 层有自己的局部 SortKey(在 entity 全局 SortKey 基础上加偏移):

```
Entity global SortKey: 0x281f4000  (Game 层, Y=50)
├─ 脚 sprite: 0x281f4000 + 0 = 0x281f4000
├─ 身 sprite: 0x281f4000 + 1 = 0x281f4001
└─ 头 sprite: 0x281f4000 + 2 = 0x281f4002
```

排序后:脚先画(身后),身中间,头最后画(身前)。视觉上就是"头的画面盖在身上,身的画面盖在脚上"——这就是 cut-out 效果。

### 跨实体穿插的实现

考虑玩家(Y=50)和箱子(Y=55),玩家拆 3 层(脚/身/头),箱子拆 2 层(底/顶)。它们的 SortKey:

```
玩家脚: 0x281f4000
玩家身: 0x281f4001
玩家头: 0x281f4002
箱子底: 0x2820c000   (Y=55, 比 Y=50 大)
箱子顶: 0x2820c001
```

排序后:`玩家脚 < 玩家身 < 玩家头 < 箱子底 < 箱子顶`。这是"玩家整体在箱子前面"——因为玩家 Y < 箱子 Y。

但如果你想要"玩家的头盖在箱子顶上"(玩家躲在箱子后面探出头),需要给玩家头一个手动 SortKey,让它的 Y 编码大于箱子:

```
玩家头(手动): 0x28210002   (假装 Y=60,大于箱子 Y=55)
```

排序后:`玩家脚 < 玩家身 < 箱子底 < 箱子顶 < 玩家头`。视觉上"玩家的头从箱子后面探出来,盖在箱子顶上"。

这就是 Day 312 "跨实体手动排序"在 sprite 层的具体应用。

### 动画系统的好处

拆分后,动画变成"每层独立播放"。

```
走路动画(脚):
  frame 0: 脚偏移 (0, 0)
  frame 1: 脚偏移 (1, 0)
  frame 2: 脚偏移 (2, -1)
  ...

攻击动画(身 + 武器):
  frame 0: 身旋转 0°,   武器偏移 (5, 5)
  frame 1: 身旋转 30°,  武器偏移 (10, 0)
  ...

组合:走路 + 攻击同时播
  脚播走路 frame 0,1,2...
  身 + 武器播攻击 frame 0,1,2...
  头静止(或呼吸动画)
```

每层独立动画 → 自由组合,不需要预先美术合成。这是 sprite 拆分的核心价值。

### Rust 数据结构

```rust
/// 单层 sprite
struct SpriteLayer {
    bitmap: BitmapId,
    offset: Vec2,         // 相对 entity 中心
    local_sort_bias: u32, // 加到 entity 全局 SortKey 上
    animation: Option<AnimationClip>,  // 可选独立动画
}

/// Entity 的可绘制部分
struct Drawable {
    layers: Vec<SpriteLayer>,  // 最多 4 层
}

impl Drawable {
    fn push_to(&self, group: &mut RenderGroup, entity_global_key: u32, entity_pos: Vec2) {
        for layer in &self.layers {
            let sort_key = entity_global_key.wrapping_add(layer.local_sort_bias);
            let world_pos = entity_pos + layer.offset;
            group.push_bitmap(layer.bitmap, sort_key, world_pos);
        }
    }
}
```

`wrapping_add` 是 u32 的"环绕加",即使溢出也不 panic(在 SortKey 编码里溢出无意义,但不会破坏排序正确性——所有 sprite 同样溢出,相对顺序不变)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

主流游戏的 sprite 拆分方案:

- **Factorio**:机器拆成"底座 / 主体 / 顶部",独立动画(灯闪烁、传送带转动)
- **Don't Starve**:角色拆 ~20 个部件(头、身、四肢各部分),用骨骼动画驱动
- **Stardew Valley**:角色拆头 + 身,不同装备(帽子)只换头部的子 sprite
- **Hollow Knight**:角色拆~10 个部件,用 Unity Bone 动画驱动

游戏行业共识:**RPG / 动作游戏必须 sprite 拆分,解谜 / 飞行射击可以单张**。判断标准是"动画帧数 × 角色数量"——如果 > 1000 帧,必须拆分,否则美术和内存都炸。

sprite 拆分的另一个好处:**装备系统**。玩家换武器,只需要换"武器"那一层 sprite,其他不变。如果用单张,每个武器组合(空手 / 剑 / 弓 / 法杖 × 不同防具组合)都要单独画——指数爆炸。拆分后只是"换一层",线性代价。

### 3.2 · 🎨 图形学视角

sprite 拆分在图形学里对应 **skeletal animation**(骨骼动画)的 2D 版本。每个 sprite 层对应一个"骨骼",骨骼之间有父子关系(头骨挂在颈骨上,颈骨挂在脊椎上),动画通过骨骼变换传播。

主流 2D 骨骼动画工具:

- **Spine**(Esoteric Software):业界标准,导出 JSON + atlas + PNG
- **DragonBones**:开源,中国团队,Cocos 引擎御用
- **Spriter**:免费版 + Pro 版
- **Live2D**:专门做"立绘动画",原神 / FGO / 偶像大师用

Casey 没用这些工具,自己写了一个简化版(直接 sprite 层数组),适合教学。工业级会引入骨骼系统(更复杂的层次结构),今天先做最小版。

骨骼动画的图形学核心是 **matrix palette skinning**——每个顶点受多个骨骼影响,通过权重混合变换矩阵。这是 3D 角色动画的标准,GPU 上用 vertex shader 实现。Day 410 之后 Casey 会引入。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上"sprite 拆分"对应的概念是 **layered resource**(分层资源):

- **SVG**(Scalable Vector Graphics):每个图形元素是独立"层",可以单独编辑
- **PDF**:用"XObject Form"表达可复用的图形块
- **Wayland subsurface**:一个 surface 可以有多个 subsurface,独立位置和变换

Wayland subsurface 的设计和今天的 sprite 层几乎一模一样——父 surface 是 entity 中心,子 subsurface 是 sprite 层,各有 offset。Wayland 用 `wl_subsurface_set_position` 设置子位置,游戏引擎用 `push_bitmap(layer, offset)` push 子 sprite。这种"父子分层"是跨领域的通用模式。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 sprite 层的最佳实践:

```rust
/// 用 enum 表达层类型(更类型安全)
#[derive(Clone, Copy, Debug)]
enum SpriteLayerKind {
    Legs,
    Torso,
    Head,
    Weapon,
}

impl SpriteLayerKind {
    fn default_sort_bias(self) -> u32 {
        match self {
            Self::Legs   => 0,
            Self::Torso  => 1,
            Self::Head   => 2,
            Self::Weapon => 3,
        }
    }
}

struct SpriteLayer {
    kind: SpriteLayerKind,
    bitmap: BitmapId,
    offset: Vec2,
    sort_bias: u32,  // 默认用 kind 的,但允许覆盖
}

impl SpriteLayer {
    fn new(kind: SpriteLayerKind, bitmap: BitmapId, offset: Vec2) -> Self {
        Self {
            kind,
            bitmap,
            offset,
            sort_bias: kind.default_sort_bias(),
        }
    }
}
```

`enum` + `match` 的好处是编译器警告漏处理新加的 variant(强制 exhaustive match)。如果你加一个 `SpriteLayerKind::Cape`,所有 match 处都需要更新,编译器会警告。

Rust 生态里 `bevy_sprite` 用 `SpriteSheetBundle` + `TextureAtlas` 表达 sprite 切片,但拆分到"层"需要用户自己写 component。今天我们自写,Phase 7 之后可以试试 bevy 生态。

### 历史演化

- **1990s 16-bit**:`超级银河战士》等用"换头部 sprite"表达萨姆斯装甲升级

| 特性 | 教学版(今天) | 工业版(Spine) |
|---|---|---|
| 层数 | 4 | 无限 |

### 跨语言变体

| 引擎 | sprite 拆分方式 |
|---|---|
| Casey HH(C) | `entity_sprite_layer[]` 数组 |

Bevy 的设计最灵活——所有东西是 Component,你可以用 `Parent` / `Children` 表达层次,用 `Transform` 表达变换。Unity 的 GameObject 也是类似设计。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 选择用数组存储 sprite 层(而不是显式 `legs`、`torso`、`head` 字段),给出至少 2 个理由。这种选择有什么代价?

**参考解答**:

**理由**:

1. **可扩展**:加新层(披风、光环、特效)不需要改 struct,加 push 即可
2. **遍历高效**:渲染时 `for layer in layers`,SIMD 友好,无 if-else 分支
3. **数据驱动**:层列表可以从文件加载,运行时调整不用重编译

**代价**:

- 美术在编辑器里看到的是数字索引(0,1,2),不是语义名(脚,身,头),需要文档解释
- 编译期类型检查弱——可以 push 任意数量层,容易写错(比如两层都是 head)
- 不便于做"特定层的特殊逻辑"(比如"头部必须有眨眼动画")—— 需要 if-else match

### Lv2 · 动手实践

**题**:在 Rust 里实现 sprite 层系统,要求:

- `SpriteLayer` 包含 bitmap 名(用 `&'static str` 模拟)、offset(Vec2)、local_sort_bias
- `Entity` 有 `Drawable { layers: Vec<SpriteLayer> }`
- 实现 `Drawable::push_to(group, entity_global_key, entity_pos)`,把每层展开成 RenderEntry
- 测试:一个 entity 有 3 层(脚/身/头),push 后排序,验证头在身之上

**参考解答**:

```rust
#[derive(Clone, Copy, Debug)]
struct Vec2 { x: f32, y: f32 }

#[derive(Clone, Debug)]
struct SpriteLayer {
    bitmap: &'static str,
    offset: Vec2,
    local_sort_bias: u32,
}

#[derive(Clone, Debug)]
struct Drawable {
    layers: Vec<SpriteLayer>,
}

impl Drawable {
    fn push_to(&self, entries: &mut Vec<(u32, Vec2, &'static str)>,
               entity_global_key: u32, entity_pos: Vec2) {
        for layer in &self.layers {
            // 局部 bias 加到全局 key 上(wrapping 防溢出 panic)
            let key = entity_global_key.wrapping_add(layer.local_sort_bias);
            let world_pos = Vec2 {
                x: entity_pos.x + layer.offset.x,
                y: entity_pos.y + layer.offset.y,
            };
            entries.push((key, world_pos, layer.bitmap));
        }
    }
}

fn main() {
    let drawable = Drawable {
        layers: vec![
            SpriteLayer { bitmap: "hero_legs",   offset: Vec2 { x: 0.0, y: -16.0 }, local_sort_bias: 0 },
            SpriteLayer { bitmap: "hero_torso",  offset: Vec2 { x: 0.0, y: 0.0   }, local_sort_bias: 1 },
            SpriteLayer { bitmap: "hero_head",   offset: Vec2 { x: 0.0, y: 16.0  }, local_sort_bias: 2 },
        ],
    };
    
    let mut entries: Vec<(u32, Vec2, &'static str)> = Vec::new();
    drawable.push_to(&mut entries, 0x281f4000, Vec2 { x: 100.0, y: 100.0 });
    entries.sort_by_key(|e| e.0);
    
    println!("=== Sprite layers in render order ===");
    for (i, (key, pos, name)) in entries.iter().enumerate() {
        println!("[{}] key={:#010x} pos=({:6.1}, {:6.1}) bitmap={}",
                 i, key, pos.x, pos.y, name);
    }
}
```

预期输出:`hero_legs(bias 0) → hero_torso(bias 1) → hero_head(bias 2)`。每个 sprite 的 world_pos 不同(相对 entity 中心偏移),但 SortKey 递增——保证头画在身之上。

### Lv3 · 迁移设计

**题**:你的 UI 系统要支持"按钮 = 多层(背景 / 边框 / 文字 / 图标)"。设计一个 `Button` 类型,要求:

- 4 层独立画、独立动画
- 文字层可以在按钮 hover 时变颜色
- 图标层可以独立旋转(loading 转圈)
- 所有层共享一个 hit-box(按钮的可点击区域)

### Rust:sprite 层系统(完整可跑)

```rust
// Cargo.toml: 无依赖
// src/main.rs

#[derive(Clone, Copy, Debug, PartialEq)]
struct Vec2 { x: f32, y: f32 }

impl std::ops::Add for Vec2 {
    type Output = Self;
    fn add(self, rhs: Self) -> Self {
        Self { x: self.x + rhs.x, y: self.y + rhs.y }
    }
}

/// 用 enum 表达层类型,获得类型安全和 exhaustive match
#[derive(Clone, Copy, Debug, PartialEq)]
enum SpriteLayerKind {
    Legs,
    Torso,
    Head,
    Weapon,
    Cape,    // 披风(扩展时新加)
}

impl SpriteLayerKind {
    /// 默认局部 SortKey 偏移
    fn default_sort_bias(self) -> u32 {
        match self {
            Self::Legs   => 0,   // 最先画(在身后)
            Self::Cape   => 1,   // 披风在身后面
            Self::Torso  => 2,
            Self::Head   => 3,
            Self::Weapon => 4,   // 武器在最前
        }
    }
}

/// 单层 sprite
#[derive(Clone, Debug)]
struct SpriteLayer {
    kind: SpriteLayerKind,
    bitmap: &'static str,
    offset: Vec2,
    sort_bias: u32,         // 默认用 kind 的,允许覆盖
}

impl SpriteLayer {
    fn new(kind: SpriteLayerKind, bitmap: &'static str, offset: Vec2) -> Self {
        Self {
            kind,
            bitmap,
            offset,
            sort_bias: kind.default_sort_bias(),
        }
    }
}

/// 可绘制部分:多层 sprite
#[derive(Clone, Debug, Default)]
struct Drawable {
    layers: Vec<SpriteLayer>,
}

/// 渲染条目
#[derive(Clone, Debug)]
struct RenderEntry {
    sort_key: u32,
    world_pos: Vec2,
    bitmap: &'static str,
    layer_kind: SpriteLayerKind,
}

struct RenderGroup {
    entries: Vec<RenderEntry>,
}

impl RenderGroup {
    fn new() -> Self { Self { entries: Vec::new() } }
    
    fn push_drawable(&mut self, drawable: &Drawable, entity_key: u32, entity_pos: Vec2) {
        for layer in &drawable.layers {
            // 全局 SortKey = entity_key + 局部 bias(wrapping 防溢出)
            let sort_key = entity_key.wrapping_add(layer.sort_bias);
            // 世界位置 = entity 中心 + 层偏移
            let world_pos = entity_pos + layer.offset;
            self.entries.push(RenderEntry {
                sort_key,
                world_pos,
                bitmap: layer.bitmap,
                layer_kind: layer.kind,
            });
        }
    }
    
    fn render(&mut self) {
        self.entries.sort_by_key(|e| e.sort_key);
        println!("=== Layered sprite render order ===");
        for (i, e) in self.entries.iter().enumerate() {
            println!("[{}] key={:#010x} kind={:?} pos=({:6.1},{:6.1}) bitmap={}",
                     i, e.sort_key, e.layer_kind, e.world_pos.x, e.world_pos.y, e.bitmap);
        }
    }
}

fn main() {
    // 玩家:5 层 sprite
    let player = Drawable {
        layers: vec![
            SpriteLayer::new(SpriteLayerKind::Legs,   "hero_legs",   Vec2 { x: 0.0, y: -16.0 }),
            SpriteLayer::new(SpriteLayerKind::Cape,   "hero_cape",   Vec2 { x: 0.0, y: -8.0  }),
            SpriteLayer::new(SpriteLayerKind::Torso,  "hero_torso",  Vec2 { x: 0.0, y: 0.0   }),
            SpriteLayer::new(SpriteLayerKind::Head,   "hero_head",   Vec2 { x: 0.0, y: 16.0  }),
            SpriteLayer::new(SpriteLayerKind::Weapon, "hero_sword",  Vec2 { x: 12.0, y: 0.0 }),
        ],
    };
    
    let mut group = RenderGroup::new();
    // entity 全局 SortKey 假设是 0x281f4000(Game 层, Y=50)
    group.push_drawable(&player, 0x281f4000, Vec2 { x: 200.0, y: 150.0 });
    group.render();
}
```

**预期输出**:

```
=== Layered sprite render order ===
[0] key=0x281f4000 kind=Legs   pos=( 200.0, 134.0) bitmap=hero_legs
[1] key=0x281f4001 kind=Cape   pos=( 200.0, 142.0) bitmap=hero_cape
[2] key=0x281f4002 kind=Torso  pos=( 200.0, 150.0) bitmap=hero_torso
[3] key=0x281f4003 kind=Head   pos=( 200.0, 166.0) bitmap=hero_head
[4] key=0x281f4004 kind=Weapon pos=( 212.0, 150.0) bitmap=hero_sword
```

注意每个 sprite 的 world_pos 都不同(相对 entity 中心(200, 150) + offset),但都共享 entity 全局 SortKey 的高位。layer 的 sort_bias 决定同 entity 内的渲染顺序——Legs 先画,Weapon 最后画(在前)。

**Troubleshooting**:

- **同一层 sprite 排序错** — 检查 `local_sort_bias` 是否递增,以及 entity 全局 SortKey 是否正确
- **wrap_add 溢出** — 这是预期行为,SortKey 编码里溢出不影响相对顺序
- **`enum` 内存大** — 加 `#[repr(u8)]` 让 enum 是 1 字节,加 `#[derive(Clone, Copy)]` 让它能 by-value 传递

## 10 · 深度补充:工程视角

Sprite 拆分的工业实践:Spine 工具的骨骼动画系统是 sprite 拆分的极致——每个骨骼有 transform(位置/旋转/缩放),父子层次传播。Spine 导出 JSON + atlas + PNG,引擎读 JSON 重建层次结构。Casey 的实现是 Spine 的极简版——扁平 layers 数组,无父子层次。但概念一致:每层独立 + sort bias 决定渲染顺序。
