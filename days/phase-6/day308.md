# Day 308 · 调试环检测

> Day 302 预告了"环"的可能性,Day 304 的拓扑排序理论上有环检测(如果排序后还有未处理节点,说明有环)。但今天 Casey 测试发现**实际场景里环检测漏报**——某些应该有环的图被当成 DAG,导致渲染顺序错乱。今天专门 debug 这个 bug,顺便深度学习图论中**环检测的三种算法**(Kahn 入度、DFS 三色、Tarjan SCC)以及它们的权衡。

## 0 · 为什么要有这一天

让我先回顾背景。Day 304 的拓扑排序代码:

```rust
fn topo_sort(g: &Graph) -> Option<Vec<usize>> {
    let mut in_degree = /* ... */;
    let mut queue = /* 起始 in_degree=0 的节点 */;
    let mut order = vec![];
    while let Some(node) = queue.pop() {
        order.push(node);
        for &next in &g.adj_out[node] {
            in_degree[next] -= 1;
            if in_degree[next] == 0 { queue.push(next); }
        }
    }
    if order.len() == g.n { Some(order) } else { None }
    //                                       ↑ None = 有环
}
```

返回 `None` 表示"拓扑排序失败 = 图有环"。这是经典的环检测手段。

**理论看起来直白**。但今天 Casey 写测试用例,发现一个诡异现象:他**手动构造了一个已知有环的图**(玩家 → 树 → 怪人 → 玩家),但 `topo_sort` 返回 `Some(order)`,没检测到环!

这是**算法 bug 中最阴险的类型**——"silent failure"(静默失败):代码不报错,但结果错。如果 Casey 没仔细看渲染结果,这个 bug 可能藏几个月。

**漏报的可能原因**:

- **边构建漏了某些边**:本该有边 A→B 没加,导致环没形成,图变成 DAG。
- **bounds 重叠判断错**:两个 sprite 实际重叠但被算成不重叠,边漏加。
- **拓扑排序实现错**:`queue.pop` 顺序导致漏处理某些节点(早期 bug,Casey Day 304 已经修过)。
- **数据问题**:某些 sprite 的 bounds 数据错,导致图本身就不对。

每一类 bug 需要**不同的 debug 工具**。今天 Casey 用**多重验证**(三种算法对比)定位漏报原因。

**学完今天,你应该能**:

- 解释三种环检测算法(Kahn / DFS 三色 / Tarjan SCC)的原理、复杂度、适用场景
- 写出 DFS 三色环检测代码,理解 White / Gray / Black 三态的含义
- 知道为什么"多重算法对比"是定位算法 bug 的有效手段
- 处理"环检测漏报"——bug 不是出在环检测本身,而是出在**边构建**
- 设计环的处理策略:报错 / 删边破环 / tie-breaker 强制顺序
- 把图论概念迁移到操作系统(死锁)、包管理器(循环依赖)、Rust 编译器(recursive type)
- 用 petgraph 的 `is_cyclic_directed` / `tarjan_scc` 解决工业图论问题
- 理解为什么 HH 用 Kahn 而非 Tarjan——够用原则

### 为什么"静默失败"最难调

让我深度剖析"silent failure"为什么可怕。

**显式失败**(panic / crash / error):用户看到错误信息,可以报告、定位。
**静默失败**:程序继续运行,但行为错。用户感觉"游戏怪怪的",但不知道为什么。

工业案例:

- **2003 年美国东北大停电**:一个监控软件有 silent bug,没报告电线过载,导致级联停电,5000 万人受影响。
- **2018 年波音 737 MAX 空难**:MCAS 系统在传感器故障时 silent 启用,把飞机推下。两起空难 346 人死亡。
- **2021 年 Facebook 6 小时大断网**:DNS 配置变更 silent 失效,工程师无法 SSH 进路由器修复。

游戏行业的 silent failure:

- 玩家被远处 sprite 遮挡(今天 Casey 的 bug)
- 物理 collider 偶尔失效,玩家穿墙
- 音效随机不响

这些 bug **不会崩溃**,但**破坏体验**。今天 Casey 调的就是这种——游戏不崩溃,但渲染错乱。

**调试 silent failure 的核心原则**:**Assert + 多重验证**。代码每个假设用 assert 钉死,多种算法对比验证一致性。今天 Casey 就是用 Kahn / DFS / Tarjan 三种算法对比,谁不一致谁有 bug。

## 2 · 心智模型

### 2.1 类比:操作系统死锁检测

操作系统的**死锁(deadlock)**就是"环"——进程 A 等待 B 持有的资源,B 等待 A 持有的资源,形成等待环。操作系统检测到死锁,要么 kill 一个进程打破环,要么让整个系统挂起。

游戏 sprite 的"环"类似——A 遮挡 B,B 遮挡 A,无法决定顺序。**逻辑上矛盾**,渲染器无法处理。

```
有环:A -> B -> C -> A(三角形循环)
- A 应该在 B 后面画(被 B 遮挡)
- B 应该在 C 后面画
- C 应该在 A 后面画
- 矛盾:A 必须在 A 后面画——不可能

打破:删除一条边(如 C -> A),变成 A -> B -> C(线性)
- A 后画 B,B 后画 C,可解
```

游戏通常用 **spawn_id tie-breaker** 打破——同环内节点按 `spawn_id` 顺序强制排,不进拓扑排序。物理上不准确(可能略微视觉错),但**玩家不会注意**(三个 sprite 几乎同样近,谁前谁后看不出来)。

工业上 tie-breaker 是处理"逻辑矛盾"的通用方法——既然无解,就**人为指定一个解**,继续运行。数据库的 isolation level、分布式的 consistency model 都用 tie-breaker 解决无解场景。

### 2.2 环检测方法 1:Kahn 入度法

最简单的环检测——拓扑排序后看是否所有节点都处理了:

```rust
fn has_cycle_kahn(g: &Graph) -> bool {
    let n = g.n;
    let mut in_degree: Vec<usize> = (0..n)
        .map(|i| g.adj_in[i].len())
        .collect();
    let mut queue: Vec<usize> = (0..n)
        .filter(|&i| in_degree[i] == 0)
        .collect();
    let mut processed = 0;

    while let Some(node) = queue.pop() {
        processed += 1;
        for &next in &g.adj_out[node] {
            in_degree[next] -= 1;
            if in_degree[next] == 0 {
                queue.push(next);
            }
        }
    }

    // 如果没处理完,剩下的节点都在环里(入度永远 > 0)
    processed < n
}
```

**原理**:环里的节点入度永远 ≥ 1(环里至少有一条入边),所以永远不会进 queue。处理后剩下的就是环内节点。

**优点**:简单,复用 Kahn 拓扑排序代码。
**缺点**:不能告诉**环在哪**——只知道"有环",不知道环由哪些节点组成。
**复杂度**:O(V+E),空间 O(V)。

### 2.3 环检测方法 2:DFS 三色标记

经典的图算法——DFS 时维护三色:

- **White**:未访问
- **Gray**:正在访问(在当前 DFS 栈里)
- **Black**:完全访问(子树都处理完)

如果 DFS 遇到 Gray 节点,说明回到自己——有环。

```rust
#[derive(Copy, Clone, PartialEq, Eq)]
enum Color { White, Gray, Black }

fn has_cycle_dfs(g: &Graph) -> bool {
    let n = g.n;
    let mut color = vec![Color::White; n];

    fn visit(g: &Graph, node: usize, color: &mut [Color]) -> bool {
        color[node] = Color::Gray;  // 标记当前路径
        for &next in &g.adj_out[node] {
            match color[next] {
                Color::Gray => return true,  // 回到当前路径——环!
                Color::White => {
                    if visit(g, next, color) { return true; }
                }
                Color::Black => {}  // 已完成,跳过
            }
        }
        color[node] = Color::Black;  // 完成
        false
    }

    for start in 0..n {
        if color[start] == Color::White {
            if visit(g, start, &mut color) { return true; }
        }
    }
    false
}
```

**三色的意义**:

- **White → Gray**:进入节点,开始 DFS
- **Gray → Black**:节点子树完全访问
- **遇 Gray = 环**:Gray 节点在当前 DFS 路径上,回到它说明有路径回到祖先——环

**优点**:直观,递归实现简单。
**缺点**:递归深度 = 图深度,大图可能爆栈。改用显式栈可避免。
**复杂度**:O(V+E),空间 O(V)。

### 2.4 环检测方法 3:Tarjan SCC

最强的环检测——**Tarjan 强连通分量算法**。一次 DFS 找出所有 SCC,大小 > 1 的 SCC 含环。

```rust
// Tarjan SCC 简化伪代码(完整实现在 petgraph)
fn tarjan_scc(g: &Graph) -> Vec<Vec<usize>> {
    let mut index = 0;
    let mut indices = vec![None; g.n];
    let mut lowlinks = vec![0; g.n];
    let mut on_stack = vec![false; g.n];
    let mut stack = vec![];
    let mut sccs = vec![];

    fn strongconnect(
        v: usize, g: &Graph,
        index: &mut usize, indices: &mut Vec<Option<usize>>,
        lowlinks: &mut Vec<usize>, on_stack: &mut Vec<bool>,
        stack: &mut Vec<usize>, sccs: &mut Vec<Vec<usize>>,
    ) {
        indices[v] = Some(*index);
        lowlinks[v] = *index;
        *index += 1;
        stack.push(v);
        on_stack[v] = true;

        for &w in &g.adj_out[v] {
            match indices[w] {
                None => {
                    strongconnect(w, g, index, indices, lowlinks, on_stack, stack, sccs);
                    lowlinks[v] = lowlinks[v].min(lowlinks[w]);
                }
                Some(_) if on_stack[w] => {
                    lowlinks[v] = lowlinks[v].min(indices[w].unwrap());
                }
                _ => {}
            }
        }

        if lowlinks[v] == indices[v].unwrap() {
            let mut scc = vec![];
            loop {
                let w = stack.pop().unwrap();
                on_stack[w] = false;
                scc.push(w);
                if w == v { break; }
            }
            sccs.push(scc);
        }
    }

    for v in 0..g.n {
        if indices[v].is_none() {
            strongconnect(v, g, &mut index, &mut indices, &mut lowlinks,
                &mut on_stack, &mut stack, &mut sccs);
        }
    }
    sccs
}

fn find_cycles(g: &Graph) -> Vec<Vec<usize>> {
    tarjan_scc(g).into_iter().filter(|scc| scc.len() > 1).collect()
}
```

**核心思想**:

- **index**:节点被发现的顺序
- **lowlink**:节点能回到的最早祖先的 index
- **stack**:当前 SCC 候选
- **on_stack**:节点是否在 stack 上

当 `lowlink[v] == index[v]`,v 是一个 SCC 的根,pop stack 到 v 形成一个 SCC。

**优点**:O(V+E) 一次找全部 SCC,大小 > 1 的 SCC 是环。
**缺点**:实现复杂,递归(生产用迭代版)。
**复杂度**:O(V+E),空间 O(V)。

**何时用**:

| 需求 | 算法 |
|---|---|
| 只判断有没有环 | Kahn 或 DFS |
| 找出环由哪些节点组成 | Tarjan SCC |
| 找出所有简单环(枚举) | Johnson's algorithm(指数级) |

HH 用 Kahn——简单够用。如果未来要做"高亮显示环内 sprite",换 Tarjan。

### 2.5 多重算法对比 debug

**今天 Casey debug 的关键工具**:同时跑 Kahn / DFS / Tarjan,看是否一致。不一致就是 bug 入口。

```rust
fn debug_cycle_detection(g: &Graph) {
    println!("=== Cycle Detection Debug ===");
    println!("Graph: {} nodes, {} edges",
        g.n,
        g.adj_out.iter().map(|v| v.len()).sum::<usize>());

    // 方法 1: Kahn
    let cycle_kahn = has_cycle_kahn(g);
    println!("Kahn:   cycle = {}", cycle_kahn);

    // 方法 2: DFS 三色
    let cycle_dfs = has_cycle_dfs(g);
    println!("DFS:    cycle = {}", cycle_dfs);

    // 方法 3: Tarjan SCC
    let sccs = tarjan_scc(g);
    let cycle_tarjan = sccs.iter().any(|s| s.len() > 1);
    println!("Tarjan: cycle = {}", cycle_tarjan);
    if cycle_tarjan {
        let cycles: Vec<_> = sccs.iter().filter(|s| s.len() > 1).collect();
        println!("  Cycles:");
        for c in &cycles {
            println!("    {:?}", c);
        }
    }

    // 三种应该一致
    if cycle_kahn != cycle_dfs || cycle_kahn != cycle_tarjan {
        println!("BUG: algorithms disagree!");
        println!("  This means one implementation is wrong.");
    }
}
```

**核心思路**:**三个独立实现给出同一答案,可信度高**。不一致,某个实现 bug。

这是工业软件验证的"3-variant programming"原则——航天(NASA)、核电、自动驾驶 用 3 套独立实现投票,避免单一实现 bug 导致灾难。

### 2.6 环的处理策略

检测到环后,三种处理方式:

**策略 1:报错退出**——拒绝渲染,告诉用户"配置错"。
```rust
match topo_sort(&g) {
    Some(order) => render(&order),
    None => panic!("Cycle detected! Check sprite configuration."),
}
```
适合:开发期。游戏发布后崩溃体验差。

**策略 2:删边破环**——找一条边删除,重新拓扑排序。
```rust
fn break_cycle(g: &mut Graph, cycle: &[usize]) {
    // 删除 cycle[0] -> cycle[1]
    let from = cycle[0];
    let to = cycle[1];
    g.adj_out[from].retain(|&x| x != to);
    g.adj_in[to].retain(|&x| x != from);
}
```
适合:数据有错但游戏继续运行。但选哪条边删是任意——可能破坏视觉。

**策略 3:tie-breaker 强制顺序**——环内节点用 spawn_id 排序,不进拓扑。
```rust
fn sort_with_cycles(entities: &[Entity], g: &Graph) -> Vec<usize> {
    let sccs = tarjan_scc(g);
    let mut in_cycle: HashSet<usize> = HashSet::new();
    for scc in &sccs {
        if scc.len() > 1 {
            for &n in scc { in_cycle.insert(n); }
        }
    }

    // DAG 部分正常拓扑排序
    let dag_nodes: Vec<_> = (0..g.n).filter(|i| !in_cycle.contains(i)).collect();
    let order_dag = topo_sort_subset(g, &dag_nodes);

    // 环内节点按 spawn_id 排序
    let mut cycle_nodes: Vec<_> = in_cycle.iter().copied().collect();
    cycle_nodes.sort_by_key(|i| entities[*i].spawn_id);

    // 合并:cycle 节点在 DAG 之间(简化:放最后)
    let mut order = order_dag;
    order.extend(cycle_nodes);
    order
}
```
Casey 用这个——对游戏体验影响最小(玩家不会注意环内 sprite 顺序)。

### 2.7 实际 HH 的"环"是什么

考虑玩家、树、怪人三角配置:

- 玩家在树前(玩家 bottom_y > 树 bottom_y)
- 树在怪人前(树 bottom_y > 怪人 bottom_y)
- 怪人在玩家前(怪人 bottom_y > 玩家 bottom_y)

如果三者 bottom_y **严格递增**(`玩家 > 树 > 怪人 > 玩家`),这是数学矛盾——不可能。所以**正常 sprite 排序永远不会有环**。

环出现的真实原因:**bounds 计算错**。Casey 今天的 bug:某些 sprite 的 bounds 应该重叠但被算成不重叠,导致应该有的边没加。**没加边 ≠ 没环**,而是**实际有环但图里看不出来**(因为关键的边漏了)。这就是漏报的本质。

修 bounds 计算后,图正确反映"实际有环",环检测正确报错,游戏用 tie-breaker 处理,渲染正确。

**教训**:**算法正确 ≠ 系统正确**。算法(Kahn)正确,但输入数据(图)错,系统输出错。**端到端测试**比单元测试更重要——单元测 Kahn 正确,但端到端才发现"图构建错"。

---

**总结**:今天的核心是**环检测算法**——Kahn(简单)、DFS 三色(直观)、Tarjan SCC(精确)。三种方法对比 debug,找到漏报原因是 bounds 计算错。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的"环"概念比比皆是:

**Asset 依赖环**:asset A 依赖 B,B 依赖 A——加载失败。游戏 asset 系统(build 系统)必须检测环,加载时报错并指出环路径。Unity AssetDatabase、Unreal AssetManager 都内置环检测。

**State machine cycle**:状态 A 转 B,B 转 A。**这通常正常**——例如 idle ↔ walk 来回切换。但当状态机期望"无环"(如剧情进度)时,环是 bug。

**Recursion cycle**:递归调用自己。游戏 AI 的行为树(Behavior Tree)有时递归,需要 base case 防止无限递归。

**Build system 环**:游戏 build 系统(CMake、Bazel、Unreal Build Tool)检测 C++ 依赖环。例如 `a.h` include `b.h`,`b.h` include `a.h`,编译失败。C++ 的 `#pragma once` / include guard 是防 include 环的机制。

**Render graph 环**:现代渲染引擎(Unreal RG、Unity SRP)用 render graph 描述渲染管线。Pass A 输出给 Pass B,B 输出给 A,形成环——管线错。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核的"环":

**Module circular dependency**:内核模块 A 依赖 B(`modprobe A` 先加载 B),B 依赖 A——加载失败。`modprobe` 检测环报错。

```bash
# 模拟环(假设)
modprobe my_mod_a
# FATAL: Module cycle detected in my_mod_a -> my_mod_b -> my_mod_a
```

**Deadlock**:进程互相等资源。内核的 lockdep 子系统检测死锁:

```bash
# 开启 lockdep
echo 1 > /proc/sys/kernel/lockdep
# 跑代码,触发死锁时 dmesg 报告:
#  Possible circular locking dependency detected
```

**kobject hierarchy cycle**:设备层次环。例如 USB 设备 A 是 B 的 parent,B 是 A 的 parent——不可能,但 bug 可能造成。

**Circular symlink**:符号链接环。`a -> b, b -> a`。文件系统遍历要检测(参见 Day 154)。

内核用类似 DFS 三色的算法检测环——简洁、O(V+E)。

### 3.3 · 🦀 Rust 生态视角

Rust 编译器的"环"检测:

**Trait bound cycle**:trait A 要求 B(`A: B`),B 要求 A(`B: A`)——编译错:
```rust
trait A: B {}
trait B: A {}
// error: cycle detected when evaluating type bounds
```

**Recursive type without indirection**:`struct Node { next: Node }`——无限大,编译错。必须用 `Box<Node>` 或 `Rc<Node>` 加间接层:
```rust
struct Node {
    next: Box<Node>,  // OK,指针打破"size 无限"
}
```

**Lifetime cycle**:Rust 不允许 lifetime 互相依赖。`'a: 'b` 和 `'b: 'a` 同时存在意味着 `'a == 'b`,Rust 编译器强制简化。

**Macro recursion cycle**:宏展开形成环——编译器报"recursion limit reached"。

Rust 编译器靠这些"环检测"避免无限循环——**所有 self-reference 都必须用某种 indirection 打破**。

```rust
// 编译错:recursive type has infinite size
struct Bad {
    next: Bad,
}
// 修:用 Box 加间接
struct Good {
    next: Box<Good>,
}
```

### 3.4 · 🎨 图形学视角

图形学的"环":

**Shader dependency cycle**:shader A 引用 B 的函数,B 引用 A——GLSL/HLSL 编译错。

**Render pass cycle**:Pass A 输出 texture 给 B,B 输出给 A——管线错。Vulkan 的 render pass 显式 DAG 结构,违反就 reject。

**Texture feedback loop**:渲染到 texture T,然后再采样 T 作下一步输入——可能 GPU 死锁。Vulkan 用 `vkCmdPipelineBarrier` 控制依赖,部分场景允许 feedback(同一 texture 不同 subresource)。

**GPU pipeline cycle**:vertex shader 输出给 fragment shader,fragment 不能给回 vertex——管线单向。如果代码试图反向,无效。

**Frame graph 现代引擎**:Unreal RG、Unity SRP 用 DAG 描述渲染管线。引擎自动检测环,违反报错。

### 4.1 上级(它属于哪个更大抽象?)

- **环检测(cycle detection)** — 图论基础概念

## 5 · 对照与变奏

### 5.1 环检测的不同复杂度

| 方法 | 时间 | 空间 | 输出 |
|---|---|---|---|
| Kahn | O(V+E) | O(V) | bool |
| DFS 三色 | O(V+E) | O(V) | bool |
| Tarjan SCC | O(V+E) | O(V) | Vec<Vec<node>> |
| Kosaraju SCC | O(V+E) | O(V) | Vec<Vec<node>>(两次 DFS) |
| Johnson's algorithm | O((V+E)*c) | O(V+E) | 枚举所有简单环 |

**枚举所有环**非常贵(指数级),通常只检测有无或找 SCC。

### 5.2 历史演化

- **1970s**:Tarjan SCC 算法(O(V+E) 单次 DFS,天才设计)。
- **1980s**:分布式死锁检测(Edge Chasing、Path Pushing)。
- **1990s**:依赖环在包管理器(npm、cargo、pip)。Cargo 用 Kahn 检测 build script 环。
- **2000s**:CI/CD 流水线环检测。GitLab CI 用 DAG 描述 job,自动检测环。
- **2010s**:图数据库(Neo4j、ArangoDB)内置环查询。
- **2020s**:AI 检测代码环(Semgrep、CodeQL 静态分析)。

### 5.3 跨领域应用

| 场景 | 用途 | 算法 |
|---|---|---|
| HH(今天) | sprite 排序环检测 | Kahn |
| 操作系统 | 死锁检测 | DFS / Resource allocation graph |
| 包管理器 | 循环依赖 | Kahn / DFS |
| 编译器 | type bound / recursive type | Compile-time check |
| 数据库 | transaction wait-for graph | DFS |
| 网络 | routing loop | TTL + hop limit |
| 区块链 | DAG-based ledger | Tarjan |

环检测是**通用图算法**——任何"逻辑矛盾"都需要检测。

### Lv1 · 概念辨析(读懂)

**题**:Casey 发现的"漏报环"bug 最终原因是 bounds 计算错。具体怎么错的?为什么导致漏报?

**参考解答**:

bug:**bounds 计算时把 `bounds.bottom()` 写成了 `bounds.top()`**——导致判断"哪个 sprite 更下"时反过来。

举例:

- 实际 A.bottom=120,B.bottom=140(B 更下,B 应遮挡 A,加边 A→B)
- bug 算成 A.top=80,B.top=100(取了顶部,误判方向)

**漏报原因**:边方向反 + 某些边漏加的组合。具体来说:

- 本该加 A→B(因为 B.bottom > A.bottom)
- bug 算成"算 top",方向反,可能加 B→A
- 同时漏加某些 sprite 对的边(因为 top 计算让某些本该重叠的被算成不重叠)
- 漏加的边导致**本该形成的环没形成**
- 图被误判为 DAG,topo_sort 返回 Some,环检测漏报

**为什么 silent failure**:游戏不崩溃,但渲染顺序错乱。Casey 通过观察视觉异常才发现。

**修复**:`top()` 改回 `bottom()`,边方向和数量都正确,环正确检测。

**教训**:**算法正确 ≠ 系统正确**。算法单元测试(Kahn 检测已知环)通过,但端到端(图构建 + Kahn)失败。**集成测试比单元测试更宝贵**。

### Lv2 · 动手实践

**题**:实现 DFS 三色环检测,测试一个有环和一个无环的图。

完成标准:有环返回 true,无环返回 false,assert 通过。

**完整代码**:

```rust
#[derive(Copy, Clone, PartialEq, Eq)]
enum Color { White, Gray, Black }

struct Graph {
    n: usize,
    adj: Vec<Vec<usize>>,
}

impl Graph {
    fn new(n: usize) -> Self {
        Self { n, adj: vec![vec![]; n] }
    }
    fn add_edge(&mut self, from: usize, to: usize) {
        self.adj[from].push(to);
    }
}

fn has_cycle(g: &Graph) -> bool {
    let mut color = vec![Color::White; g.n];

    fn visit(g: &Graph, node: usize, color: &mut [Color]) -> bool {
        color[node] = Color::Gray;
        for &next in &g.adj[node] {
            match color[next] {
                Color::Gray => return true,  // 回到当前路径
                Color::White => {
                    if visit(g, next, color) { return true; }
                }
                Color::Black => {}
            }
        }
        color[node] = Color::Black;
        false
    }

    for s in 0..g.n {
        if color[s] == Color::White {
            if visit(g, s, &mut color) { return true; }
        }
    }
    false
}

fn main() {
    // 无环图:A -> B -> C
    let mut g1 = Graph::new(3);
    g1.add_edge(0, 1);
    g1.add_edge(1, 2);
    assert!(!has_cycle(&g1));

    // 有环图:A -> B -> C -> A
    let mut g2 = Graph::new(3);
    g2.add_edge(0, 1);
    g2.add_edge(1, 2);
    g2.add_edge(2, 0);
    assert!(has_cycle(&g2));

    // 自环:A -> A
    let mut g3 = Graph::new(1);
    g3.add_edge(0, 0);
    assert!(has_cycle(&g3));

    // 双向:A <-> B
    let mut g4 = Graph::new(2);
    g4.add_edge(0, 1);
    g4.add_edge(1, 0);
    assert!(has_cycle(&g4));

    // 长链:A -> B -> C -> D -> E
    let mut g5 = Graph::new(5);
    for i in 0..4 { g5.add_edge(i, i + 1); }
    assert!(!has_cycle(&g5));

    println!("All cycle detection tests passed!");
}
```

**每行解释**:

- `Color::White` → 未访问,初始状态
- `Color::Gray` → 访问中(在当前 DFS 栈上)
- `Color::Black` → 完全访问(子树处理完)
- 遇 `Gray` → 回到自己 → 环
- 遇 `White` → 递归访问
- 遇 `Black` → 跳过

### Lv3 · 迁移设计

**题**:把环检测迁移到**包管理器**——检测 A 依赖 B、B 依赖 A 的循环依赖。

需求:

- 节点 = 包
- 边 = 依赖关系(`A depends on B` → 边 A→B)
- 检测循环依赖
- 报错时输出环路径(用 Tarjan SCC 找出环)

设计文档:

```rust
struct PackageGraph {
    packages: Vec<String>,          // 包名
    deps: Vec<Vec<usize>>,          // deps[i] = i 依赖的包 id 列表
}

impl PackageGraph {
    fn check_cycles(&self) -> Result<(), Vec<Vec<usize>>> {
        let sccs = tarjan_scc(&self.as_graph());
        let cycles: Vec<_> = sccs.into_iter()
            .filter(|s| s.len() > 1 || self.has_self_dep(s[0]))
            .collect();
        if cycles.is_empty() {
            Ok(())
        } else {
            Err(cycles)
        }
    }

    fn report_cycles(&self) {
        match self.check_cycles() {
            Ok(()) => println!("No cycles detected"),
            Err(cycles) => {
                eprintln!("ERROR: Circular dependencies detected!");
                for cycle in &cycles {
                    let names: Vec<_> = cycle.iter()
                        .map(|&i| &self.packages[i])
                        .collect();
                    eprintln!("  Cycle: {}", names.join(" -> "));
                }
            }
        }
    }
}
```

实现完整,跑 5 个包(含一个环)的测试。

### 8.1 完整 demo:三算法对比

把今天的概念做成完整可跑 demo:三种环检测算法 + 多重验证 debug 工具。

```rust
#[derive(Debug)]
struct Graph {
    n: usize,
    adj_out: Vec<Vec<usize>>,
    adj_in: Vec<Vec<usize>>,
}

impl Graph {
    fn new(n: usize) -> Self {
        Self {
            n,
            adj_out: vec![vec![]; n],
            adj_in: vec![vec![]; n],
        }
    }

    fn add_edge(&mut self, from: usize, to: usize) {
        self.adj_out[from].push(to);
        self.adj_in[to].push(from);
    }
}

// 方法 1: Kahn 入度法
fn has_cycle_kahn(g: &Graph) -> bool {
    let mut in_degree: Vec<usize> = g.adj_in.iter().map(|v| v.len()).collect();
    let mut queue: Vec<usize> = (0..g.n)
        .filter(|&i| in_degree[i] == 0)
        .collect();
    let mut processed = 0;

    while let Some(node) = queue.pop() {
        processed += 1;
        for &next in &g.adj_out[node] {
            in_degree[next] -= 1;
            if in_degree[next] == 0 { queue.push(next); }
        }
    }
    processed < g.n
}

// 方法 2: DFS 三色
#[derive(Copy, Clone, PartialEq, Eq)]
enum Color { White, Gray, Black }

fn has_cycle_dfs(g: &Graph) -> bool {
    let mut color = vec![Color::White; g.n];

    fn visit(g: &Graph, node: usize, color: &mut [Color]) -> bool {
        color[node] = Color::Gray;
        for &next in &g.adj_out[node] {
            match color[next] {
                Color::Gray => return true,
                Color::White => if visit(g, next, color) { return true; },
                Color::Black => {}
            }
        }
        color[node] = Color::Black;
        false
    }

    for s in 0..g.n {
        if color[s] == Color::White {
            if visit(g, s, &mut color) { return true; }
        }
    }
    false
}

// 三算法对比 debug
fn debug_cycle(g: &Graph) {
    println!("\n=== Cycle Detection Debug ===");
    println!("Graph: {} nodes, {} edges",
        g.n, g.adj_out.iter().map(|v| v.len()).sum::<usize>());

    let kahn = has_cycle_kahn(g);
    let dfs = has_cycle_dfs(g);
    println!("Kahn: cycle = {}", kahn);
    println!("DFS:  cycle = {}", dfs);

    if kahn != dfs {
        println!("BUG: algorithms disagree!");
    } else {
        println!("Algorithms agree.");
    }
}

fn main() {
    // 测试 1: 无环 DAG
    let mut g1 = Graph::new(5);
    g1.add_edge(0, 1);
    g1.add_edge(0, 2);
    g1.add_edge(1, 3);
    g1.add_edge(2, 3);
    g1.add_edge(3, 4);
    println!("Test 1: DAG");
    debug_cycle(&g1);

    // 测试 2: 有环
    let mut g2 = Graph::new(4);
    g2.add_edge(0, 1);
    g2.add_edge(1, 2);
    g2.add_edge(2, 0);  // 环 0-1-2-0
    g2.add_edge(2, 3);
    println!("\nTest 2: With cycle (0-1-2-0)");
    debug_cycle(&g2);

    // 测试 3: 自环
    let mut g3 = Graph::new(1);
    g3.add_edge(0, 0);
    println!("\nTest 3: Self-loop");
    debug_cycle(&g3);
}
```
