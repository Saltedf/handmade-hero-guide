# Day 309 · 重叠测试的网格划分

> 拓扑排序的图构建是 O(n²)——1000 个 sprite 时是 100 万次比较。今天 Casey 用 **grid partitioning**(网格划分)加速:把世界分成格子,只比较同格子和相邻格子的 sprite。复杂度降到接近 O(n)。

## 0 · 为什么要有这一天

O(n²) 在小场景没问题,但 HH 的世界越来越大:

- 100 sprite:10000 比较,微秒级
- 1000 sprite:1M 比较,毫秒级
- 10000 sprite:100M 比较,十毫秒级

60 FPS 帧预算 16.67ms,10000 sprite 已经吃掉大半。

加速思路:**sprite 不可能与远处的 sprite 重叠**。所以远处 sprite 对无需比较。

具体做法:**网格划分**。把世界分成 64x64(或其他大小)的格子,每个 sprite 注册到它覆盖的格子。判断重叠时只看同格子或相邻格子的 sprite。

数学上:平均每格子 sprite 数 ≈ 总 sprite 数 / 总格子数。如果世界大、sprite 分散,每格子 sprite 数很少(常 1-5)。每 sprite 只和这几 sprite 比较——总比较 O(n*k),k 是常数。

这是**空间划分**(spatial partitioning)的最简单形式。更高级的:quadtree、BVH、k-d tree。grid 是入门级,容易理解和实现。

今天的代码量:加 Grid 结构、加 insert/query 方法、改图构建用 grid。

心理锚点:看完今天,你应该理解"空间划分加速碰撞/重叠查询"的核心思想。

## 1 · Casey 今天做了什么

Casey 今天的实现:

1. **设计 Grid 结构**——cell_size + cells: Vec<Vec<usize>>
2. **insert(sprite)**——根据 sprite 位置算 cell,加入 cell 的 sprite 列表
3. **query_neighbors(pos)**——返回同 cell 和 8 个相邻 cell 的 sprite
4. **改图构建**——只对 neighbors 比较重叠,O(n*k)

今天的核心是**空间数据结构**——为高频查询优化的数据布局。

## 2 · 心智模型

### 类比:图书馆找书

要在图书馆找"和某本书主题相近"的书。两种方法:

1. **遍历法**:把所有书一本本看,每本判断是否主题相近。O(n)
2. **分区法**:图书馆按主题分区(科幻、历史、文学)。你只去"科幻"分区找,可能加"历史"相邻分区(因为有些书跨界)。O(少量)

图书馆分区就是 grid partitioning——预先把书"按位置"分组,查询时只看相关分区。

### 2.1 Grid 结构

```rust
struct Grid {
    cell_size: f32,           // 每格大小(像素)
    cols: usize,              // 列数
    rows: usize,              // 行数
    cells: Vec<Vec<usize>>,   // 每个 cell 存 sprite index 列表
}

impl Grid {
    fn new(world_w: f32, world_h: f32, cell_size: f32) -> Self {
        let cols = (world_w / cell_size).ceil() as usize;
        let rows = (world_h / cell_size).ceil() as usize;
        Self {
            cell_size,
            cols,
            rows,
            cells: vec![vec![]; cols * rows],
        }
    }

    fn cell_index(&self, x: f32, y: f32) -> Option<usize> {
        if x < 0.0 || y < 0.0 { return None; }
        let cx = (x / self.cell_size) as usize;
        let cy = (y / self.cell_size) as usize;
        if cx >= self.cols || cy >= self.rows { return None; }
        Some(cy * self.cols + cx)
    }

    fn insert(&mut self, idx: usize, pos: Vec2) {
        if let Some(ci) = self.cell_index(pos.x, pos.y) {
            self.cells[ci].push(idx);
        }
    }

    fn query_neighbors(&self, pos: Vec2) -> Vec<usize> {
        let mut result = vec![];
        let cx = (pos.x / self.cell_size) as isize;
        let cy = (pos.y / self.cell_size) as isize;
        // 3x3 邻居(包括自己)
        for dy in -1..=1 {
            for dx in -1..=1 {
                let nx = cx + dx;
                let ny = cy + dy;
                if nx < 0 || ny < 0 || nx >= self.cols as isize || ny >= self.rows as isize {
                    continue;
                }
                let ni = (ny as usize) * self.cols + (nx as usize);
                result.extend_from_slice(&self.cells[ni]);
            }
        }
        result
    }
}
```

cell_size 是 trade-off:

- 小 cell:每 cell sprite 少,查询快,但 cell 数多,内存大
- 大 cell:每 cell sprite 多,查询慢,但 cell 数少

通常 cell_size = 2 * max_sprite_size,平衡好。

### 2.2 用 Grid 加速图构建

```rust
fn build_graph_with_grid(entities: &[Entity], grid: &Grid) -> Graph {
    let mut g = Graph::new(entities.len());

    for (i, e) in entities.iter().enumerate() {
        let neighbors = grid.query_neighbors(e.pos);
        for &j in &neighbors {
            if i == j { continue; }
            if entities[i].bounds.overlaps(&entities[j].bounds) {
                if entities[j].bounds.bottom() > entities[i].bounds.bottom() {
                    g.add_edge(i, j);
                } else if entities[i].bounds.bottom() > entities[j].bounds.bottom() {
                    g.add_edge(j, i);
                }
            }
        }
    }

    g
}
```

每 sprite 只和 neighbors 比较,neighbors 通常 < 10。总比较 O(n * 10) ≈ O(n),远快于 O(n²)。

### 2.3 cell_size 选择

cell_size 影响性能:

| cell_size | cells 数 | 每 cell sprite | 查询复杂度 |
|---|---|---|---|
| 32 px(小) | 768(800/32 * 600/32) | ~1 | 极快 |
| 64 px(中) | ~200 | ~5 | 快 |
| 128 px(大) | ~40 | ~25 | 中等 |
| 256 px(超大) | ~10 | ~100 | 慢 |
| 全屏(无 grid) | 1 | 1000 | O(n²) |

如果 sprite 最大 64px,cell_size = 128(2倍最大)合适——neighbors 3x3=9 个 cell,涵盖 384x384 范围,大于任何 sprite 的 bounds。

### 2.4 Grid 的更新

sprite 移动后,要从旧 cell 移除,加到新 cell。两种实现:

**实现 1:每帧重建**

```rust
fn frame_update(grid: &mut Grid, entities: &[Entity]) {
    for cell in &mut grid.cells { cell.clear(); }
    for (i, e) in entities.iter().enumerate() {
        grid.insert(i, e.pos);
    }
}
```

简单,每帧清空重建。HH sprite 数 < 1000 时 O(n),可接受。

**实现 2:增量更新**

```rust
fn move_entity(grid: &mut Grid, idx: usize, old_pos: Vec2, new_pos: Vec2) {
    let old_ci = grid.cell_index(old_pos.x, old_pos.y);
    let new_ci = grid.cell_index(new_pos.x, new_pos.y);
    if old_ci == new_ci { return; }  // 没换 cell
    // 从旧 cell 移除
    if let Some(ci) = old_ci {
        grid.cells[ci].retain(|&x| x != idx);
    }
    // 加到新 cell
    if let Some(ci) = new_ci {
        grid.cells[ci].push(idx);
    }
}
```

复杂,但避免每帧全清。适合超多 sprite 的场景。

Casey 在 day 309 用实现 1,简单够用。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的空间划分层次:

- **Brute force**:O(n²),简单
- **Uniform grid**(今天):O(n),简单
- **Hierarchical grid**:多层 grid,适合大小变化大的场景
- **Quadtree**:递归 4 分,适合稀疏场景
- **BVH(Bounding Volume Hierarchy)**:树状 bounding box
- **k-d tree**:二叉空间划分

商业引擎(Unity、Unreal)用 BVH 或 hierarchical grid,因为 entity 大小变化大。

Casey 在 HH 用 uniform grid——简单,适合教学。Phase 8 可能升级 quadtree。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核的"空间划分":

- **Page table**:多级页表(虚拟地址 → 物理地址)
- **buddy allocator**:按 size class 分配
- **extent tree**(ext4):文件块的层次索引
- **radix tree**:页 cache 的索引

每个都是"按某种 key 分桶加速查询"。grid 按 (x, y) 分桶,page table 按 virtual address 分桶——精神一致。

### 3.3 · 🦀 Rust 生态视角

Rust 的空间划分库:

- **rstar**:R-tree 实现

### 3.4 · 🎨 图形学视角

图形学的"空间划分"对应 **culling**:

- **Frustum culling**:相机外的物体不渲染
- **Occlusion culling**:被遮挡的物体不渲染
- **Backface culling**:背面不渲染
- **Portal rendering**:用 portal 分割场景

## 5 · 对照与变奏

### 碰撞检测两阶段

```
Broad phase(粗):快速找"可能碰撞"对
  - grid / quadtree / BVH
  - O(n) 或 O(n log n)

Narrow phase(细):精确判断每对是否真碰撞
  - AABB / SAT / GJK
  - O(k),k 是粗筛后的对数
```

grid 是 broad phase 的标准选择。今天的 overlap 测试相当于"自己和自己"的碰撞——broad phase 加速。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 grid 加速的查询是 O(n) 而不是 O(1)?

**参考解答**:每个 sprite 的查询是 O(k)(k = neighbors 数,常 ~10)。但 n 个 sprite 都要查询,总 O(n*k)。k 是常数,所以总 O(n)。

但如果 cell_size 太小,某些 cell 可能为空(0 sprite);如果太大,某些 cell 可能很多 sprite(>100)。最坏情况:所有 sprite 在同一 cell,O(n²) 退化。

均匀分布是 grid 的最佳场景——退化是 grid 的弱点。Quadtree / BVH 更鲁棒(自适应分裂)。

### Lv2 · 动手实践

**题**:实现 Grid,测试 100 个 sprite 用 grid 加速图构建,对比 O(n²) 性能。

完成标准:grid 版比 O(n²) 版快 5-10x。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug)]
struct Aabb { x: f32, y: f32, w: f32, h: f32 }
impl Aabb {
    fn overlaps(&self, o: &Self) -> bool {
        self.x < o.x + o.w && self.x + self.w > o.x
            && self.y < o.y + o.h && self.y + self.h > o.y
    }
}

#[derive(Copy, Clone, Debug)]
struct Entity { pos: Vec2, bounds: Aabb }

struct Grid {
    cell_size: f32,
    cols: usize,
    rows: usize,
    cells: Vec<Vec<usize>>,
}

impl Grid {
    fn new(w: f32, h: f32, cs: f32) -> Self {
        let cols = (w / cs).ceil() as usize;
        let rows = (h / cs).ceil() as usize;
        Self { cell_size: cs, cols, rows, cells: vec![vec![]; cols * rows] }
    }

    fn cell_of(&self, p: Vec2) -> Option<usize> {
        if p.x < 0.0 || p.y < 0.0 { return None; }
        let cx = (p.x / self.cell_size) as usize;
        let cy = (p.y / self.cell_size) as usize;
        if cx >= self.cols || cy >= self.rows { return None; }
        Some(cy * self.cols + cx)
    }

    fn insert(&mut self, idx: usize, p: Vec2) {
        if let Some(ci) = self.cell_of(p) {
            self.cells[ci].push(idx);
        }
    }

    fn neighbors(&self, p: Vec2) -> Vec<usize> {
        let mut result = vec![];
        let cx = (p.x / self.cell_size) as isize;
        let cy = (p.y / self.cell_size) as isize;
        for dy in -1..=1 {
            for dx in -1..=1 {
                let nx = cx + dx;
                let ny = cy + dy;
                if nx < 0 || ny < 0 { continue; }
                if nx >= self.cols as isize || ny >= self.rows as isize { continue; }
                let ni = ny as usize * self.cols + nx as usize;
                result.extend_from_slice(&self.cells[ni]);
            }
        }
        result
    }
}

fn count_overlaps_brute(entities: &[Entity]) -> usize {
    let mut count = 0;
    for i in 0..entities.len() {
        for j in (i+1)..entities.len() {
            if entities[i].bounds.overlaps(&entities[j].bounds) {
                count += 1;
            }
        }
    }
    count
}

fn count_overlaps_grid(entities: &[Entity], grid: &Grid) -> usize {
    let mut count = 0;
    let mut checked = std::collections::HashSet::new();
    for (i, e) in entities.iter().enumerate() {
        let nbrs = grid.neighbors(e.pos);
        for &j in &nbrs {
            if i == j { continue; }
            let key = if i < j { (i, j) } else { (j, i) };
            if checked.contains(&key) { continue; }
            checked.insert(key);
            if entities[i].bounds.overlaps(&entities[j].bounds) {
                count += 1;
            }
        }
    }
    count
}

fn main() {
    use std::time::Instant;
    // 100 个 sprite 随机分布
    let mut entities = vec![];
    for i in 0..100 {
        let x = (i as f32 * 7.3) % 780.0;
        let y = (i as f32 * 3.1) % 580.0;
        entities.push(Entity {
            pos: Vec2::new(x, y),
            bounds: Aabb { x: x - 16.0, y: y - 16.0, w: 32.0, h: 32.0 },
        });
    }

    let t1 = Instant::now();
    let c1 = count_overlaps_brute(&entities);
    let d1 = t1.elapsed().as_nanos();

    let mut grid = Grid::new(800.0, 600.0, 64.0);
    for (i, e) in entities.iter().enumerate() {
        grid.insert(i, e.pos);
    }
    let t2 = Instant::now();
    let c2 = count_overlaps_grid(&entities, &grid);
    let d2 = t2.elapsed().as_nanos();

    println!("Brute: {} overlaps in {} ns", c1, d1);
    println!("Grid:  {} overlaps in {} ns", c2, d2);
    println!("Grid is {:.1}x faster", d1 as f64 / d2 as f64);

    assert_eq!(c1, c2);  // 结果必须一致
    println!("Grid partitioning test passed!");
}
```

**每行解释**:
- `HashSet` 去重——neighbors 可能返回重复对(同对出现在两个 cell)
- key 规范化:`if i < j (i,j) else (j,i)`——保证 (1,5) 和 (5,1) 视为同对
- assert_eq!(c1, c2) 验证 grid 没漏 overlap

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
