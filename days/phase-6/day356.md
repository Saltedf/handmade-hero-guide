# Day 356 · 让调试系统兼容 CLANG

> HH 默认用 MSVC 编译(Windows + Visual Studio)。但社区有用 Clang 的(Mac、Linux、clang on Windows)。Casey 的 debug 系统用了 MSVC 特定的 `__FILE__` / `__LINE__` 宏和 `__cdecl` 调用约定,Clang 编译报错。今天的工作:**让代码跨编译器**。

## 0 · 为什么要有这一天

开源项目要支持多种环境。如果你的代码只能在 MSVC 跑,Mac / Linux 用户用不了,你失去 50% 潜在用户。

跨编译器(Cross-compiler)的常见痛点:

1. **预处理器宏不同**:`__FILE__`、`__LINE__` 是标准,但 `__FUNCTION__`、`__PRETTY_FUNCTION__` 各家不同
2. **调用约定不同**:MSVC 的 `__cdecl` / `__stdcall` / `__fastcall` 在 Clang 上需要写 `_Nonnull` / `_Nullable`
3. **特性不同**:MSVC 的 `__declspec(dllexport)` vs Clang 的 `__attribute__((visibility("default")))`
4. **内联汇编语法不同**:MSVC 用 Intel 语法,Clang 默认 AT&T
5. **SIMD intrinsic 命名**:大部分一致,但 `__m128` 在某些 Clang 版本表现不同

HH 的 debug 系统大量用宏做"运行时数据收集":每个函数自动记录 `__FILE__` / `__LINE__` / `__FUNCTION__`,运行时 overlay 显示。这些宏在 MSVC 工作,在 Clang 部分报错。

今天的 episode:Casey 用 `#ifdef _MSC_VER` / `#ifdef __clang__` 区分,加 Clang 兼容的宏,让代码同时支持 MSVC 和 Clang。

Rust 翻译:Rust 本身跨平台,这种"跨编译器"痛点小。但跨 OS(Linux/Mac/Windows)仍要处理。

心理锚点:今天之后你能写跨编译器的 C/C++ 代码,理解 `#ifdef` 条件编译,知道为什么大项目都有 `platform.h` 之类的抽象层。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑 HH 用 Clang 编译,看到一堆错误:

1. `__FUNCTION__` 在 Clang 不是标准,要用 `__func__`
2. `__declspec(dllexport)` 在 Clang 用 `__attribute__((visibility("default")))`
3. `__stdcall` 在 Clang 用 `__attribute__((stdcall))`
4. 一些 Windows 特定头文件 Clang 找不到

Casey 加 `#ifdef` 处理:

```c
// 跨编译器的 FUNCTION 宏
#if defined(_MSC_VER)
    #define HH_FUNCTION __FUNCTION__
#elif defined(__clang__) || defined(__GNUC__)
    #define HH_FUNCTION __func__
#else
    #define HH_FUNCTION "???"
#endif

// 跨编译器的 dllexport
#if defined(_MSC_VER)
    #define HH_EXPORT __declspec(dllexport)
#elif defined(__clang__) || defined(__GNUC__)
    #define HH_EXPORT __attribute__((visibility("default")))
#else
    #define HH_EXPORT
#endif
```

之后 Clang 能完整编译 HH。Casey 在 README 加 "How to build with Clang" 章节。

## 2 · 心智模型

### 类比:同一道菜,不同厨房

你写菜谱(代码),给不同厨房(编译器)做。每个厨房的:

- 灶台不同(MSVC 用 Intel 语法,Clang 默认 AT&T)
- 调料名不同(`__FUNCTION__` vs `__func__`)
- 工具不同(MSVC 的 dllexport vs Clang 的 visibility)

菜谱要"通用",要么:

- 用"标准"调料(ISO C11 / C++17)——但标准不全
- 用条件分支(`#ifdef`)——明确给每种厨房不同指令
- 抽象一层(`platform.h`)——把差异隔离

 Casey 用 `#ifdef` + `platform.h`。

### 跨编译器宏的标准模式

```c
// platform.h
#pragma once

#if defined(_MSC_VER)
    // MSVC specific
    #define HH_FORCE_INLINE __forceinline
    #define HH_NORETURN __declspec(noreturn)
    #define HH_ALIGN(x) __declspec(align(x))
#elif defined(__clang__) || defined(__GNUC__)
    // Clang / GCC
    #define HH_FORCE_INLINE inline __attribute__((always_inline))
    #define HH_NORETURN __attribute__((noreturn))
    #define HH_ALIGN(x) __attribute__((aligned(x)))
#else
    #error "Unsupported compiler"
#endif
```

每个差异都封装成 `HH_*` 宏,业务代码用 `HH_FORCE_INLINE` 而不是 `__forceinline` 或 `__attribute__((always_inline))`。

### 预定义宏

每个编译器预定义的宏:

| 宏 | MSVC | Clang | GCC |
|---|---|---|---|
| `_MSC_VER` | ✓(值=版本) | ✗ | ✗ |
| `__clang__` | ✗ | ✓ | ✗ |
| `__GNUC__` | ✗ | ✓(兼容) | ✓ |
| `_WIN32` | ✓ | ✓(on Windows) | ✓(on Windows) |
| `__linux__` | ✗ | ✓(on Linux) | ✓(on Linux) |
| `__APPLE__` | ✗ | ✓(on Mac) | ✓(on Mac) |
| `__x86_64__` | ✗ | ✓(on x64) | ✓(on x64) |
| `__arm64__` | ✗ | ✓(on ARM64) | ✓(on ARM64) |

```c
#if defined(_WIN32)
    // Windows specific
#elif defined(__linux__)
    // Linux specific
#elif defined(__APPLE__)
    // Mac specific
#endif
```

### Rust 的跨平台优势

Rust 标准库跨平台,大部分代码不用改:

```rust
use std::fs::File;
let f = File::open("test.txt")?;  // 自动适配 Windows / Linux / Mac
```

特定平台代码用 `#[cfg(...)]`:

```rust
#[cfg(target_os = "windows")]
fn windows_only() { /* ... */ }

#[cfg(target_os = "linux")]
fn linux_only() { /* ... */ }
```

不需要手写宏,编译器内置支持。

Rust 没有"跨编译器"问题——只有 rustc(LLVM 后端),所有平台一致。这是 Rust 比 C++ 大的优势。

### C++ 跨编译器的"现实"

实际项目通常:

1. 用 C++17 标准(标准化的部分)
2. 用 `#ifdef` 包非标准部分
3. 用 `cmake` 测试多平台

但跨编译器不是免费的:

- 每个 `#ifdef` 是测试负担
- 不同编译器的 stdlib 实现(MSVC vs libstdc++ vs libc++)有微妙差别
- SIMD intrinsic 各家实现略不同

- **`__declspec` vs `__attribute__`** —— 属性声明

- **`#[cfg(...)]`** —— Rust 条件编译

## 5 · 对照与变奏

### 跨编译器 vs 跨 OS

跨编译器:同 OS,不同编译器(MSVC vs Clang on Windows)。

跨 OS:同编译器(可能),不同 OS(GCC on Linux vs GCC on Mac)。

跨架构:同 OS + 编译器,不同 CPU(x86 vs ARM)。

Rust 一并解决:`#[cfg(target_arch, target_os, target_compiler)]`。

### 平台抽象层

大项目通常有:

- `platform.h` —— 跨编译器宏
- `os.h` —— 跨 OS 函数
- `arch.h` —— 跨架构 SIMD

例如 Unreal 的 `Core/Public/Containers`、Bevy 的 `bevy_utils`。

### 历史演化

- **1980s**:每编译器都"私有扩展",跨编译器地狱
- **1990s**:ANSI C / ISO C++ 标准化,部分统一
- **2000s**:cmake / autotools 自动检测
- **2010s**:Clang 兼容 GCC,跨编译器变好
- **2020s**:Rust / Zig 不需要"跨编译器",只有 rustc / zig cc

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 `__FUNCTION__` 是非标准但 `__func__` 是标准?

**参考解答**:

`__FUNCTION__`:MSVC 在 1990s 引入的扩展,把"当前函数名"作为字符串字面量。其他编译器跟风但用不同名字(GCC `__FUNCTION__`,Clang `__func__`)。

`__func__`:C99 标准(C++11 加入)。每个函数隐式声明 `static const char __func__[] = "function-name";`。所有标准 C++ 编译器都支持。

跨编译器代码应该用 `__func__`(标准)。`__FUNCTION__` 是 MSVC 老 API,新代码不用。

Casey 在 Day 356 把所有 `__FUNCTION__` 改成 `__func__`,跨编译器兼容。

### Lv2 · 动手实践

**题**:Rust 实现跨平台 "load library" 函数。Windows 用 `LoadLibraryW`,Linux 用 `dlopen`。

完成标准:同一份代码在 Linux 编译运行,加载 .so;在 Windows 编译运行,加载 .dll。

**参考解答**:

```rust
// Cargo.toml: 不需要依赖,用 std

#[cfg(target_os = "windows")]
mod platform {
    use std::os::windows::ffi::OsStrExt;
    use std::os::windows::io::FromRawHandle;

    pub struct Library(*mut std::ffi::c_void);

    impl Library {
        pub fn load(name: &str) -> Result<Self, String> {
            // 实际用 windows crate,这里简化
            Err("Windows LoadLibrary not implemented in demo".into())
        }
        pub fn get_sym(&self, _name: &str) -> Result<*mut std::ffi::c_void, String> {
            Err("not implemented".into())
        }
    }
}

#[cfg(target_os = "linux")]
mod platform {
    pub struct Library(*mut std::ffi::c_void);

    impl Library {
        pub fn load(name: &str) -> Result<Self, String> {
            unsafe {
                let cname = std::ffi::CString::new(name).map_err(|e| e.to_string())?;
                let handle = libc::dlopen(cname.as_ptr(), libc::RTLD_NOW);
                if handle.is_null() {
                    let err = std::ffi::CStr::from_ptr(libc::dlerror());
                    return Err(err.to_string_lossy().into_owned());
                }
                Ok(Self(handle))
            }
        }

        pub fn get_sym(&self, name: &str) -> Result<*mut std::ffi::c_void, String> {
            unsafe {
                let cname = std::ffi::CString::new(name).map_err(|e| e.to_string())?;
                let sym = libc::dlsym(self.0, cname.as_ptr());
                if sym.is_null() {
                    return Err("symbol not found".into());
                }
                Ok(sym)
            }
        }
    }

    // 需要 libc crate:Cargo.toml 加 libc = "0.2"
}

fn main() {
    let lib_name = if cfg!(target_os = "linux") {
        "libdl.so.2"
    } else if cfg!(target_os = "windows") {
        "kernel32.dll"
    } else {
        "libm.so.6"
    };

    match platform::Library::load(lib_name) {
        Ok(lib) => println!("Loaded {}", lib_name),
        Err(e) => println!("Failed: {}", e),
    }
}
```

**关键解释**:
- `#[cfg(target_os = "...")]`:模块按 OS 选择
- `cfg!(...)`:运行时知道是不是某 OS(返回 bool)
- 实际项目用 `libloading` crate,封装好

## 8 · Rust / Arch 落地代码

### 完整可跑示例:跨编译器宏模拟

```rust
// 模拟 C 的跨编译器宏,在 Rust 里用 cfg 表达

// 编译器检测(Rust 只有 rustc,但能检测 LLVM 版本)
const RUSTC_VERSION: &str = env!("CARGO_PKG_RUST_VERSION");

// 平台检测
fn current_platform() -> &'static str {
    if cfg!(target_os = "windows") {
        "Windows"
    } else if cfg!(target_os = "linux") {
        "Linux"
    } else if cfg!(target_os = "macos") {
        "macOS"
    } else {
        "Unknown"
    }
}

// 架构检测
fn current_arch() -> &'static str {
    if cfg!(target_arch = "x86_64") {
        "x86_64"
    } else if cfg!(target_arch = "aarch64") {
        "ARM64"
    } else if cfg!(target_arch = "wasm32") {
        "WASM"
    } else {
        "Other"
    }
}

// 位数
fn pointer_width() -> &'static str {
    if cfg!(target_pointer_width = "64") {
        "64-bit"
    } else if cfg!(target_pointer_width = "32") {
        "32-bit"
    } else {
        "?"
    }
}

// 跨平台的"page size"
fn page_size() -> usize {
    #[cfg(target_os = "windows")]
    {
        // 实际用 GetSystemInfo
        4096  // 大多数 Windows
    }
    #[cfg(not(target_os = "windows"))]
    {
        unsafe {
            let v = libc::sysconf(libc::_SC_PAGESIZE);
            if v > 0 { v as usize } else { 4096 }
        }
    }
}

fn main() {
    println!("=== Build Environment ===");
    println!("Platform:  {}", current_platform());
    println!("Arch:      {}", current_arch());
    println!("Pointers:  {}", pointer_width());
    println!("Page size: {} bytes", page_size());

    println!("\n=== Conditional Compilation ===");
    #[cfg(target_os = "linux")]
    println!("Running on Linux: can use epoll, inotify, etc.");
    #[cfg(target_os = "windows")]
    println!("Running on Windows: can use IOCP, WaitForMultipleObjects");
    #[cfg(target_os = "macos")]
    println!("Running on macOS: can use kqueue, dispatch");

    println!("\n=== Endianness ===");
    if cfg!(target_endian = "little") {
        println!("Little-endian (x86, ARM in LE mode)");
    } else {
        println!("Big-endian (some ARM, PowerPC)");
    }

    // 浮点 ABI(ARM 特定)
    #[cfg(target_arch = "aarch64")]
    println!("\nARM64: float ABI = hard (always hard on aarch64)");
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

**阶段一:定义接口**。Casey 在动手实现前,先想清楚 API。Rust 的 trait 是定义接口的工具:

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
