# Day 353 · 简单 RLE 压缩

> HH 进入"压缩"子主题。今天 Casey 从最简单的 RLE(Run-Length Encoding,行程长度编码)开始——把连续重复的字节用一个"长度+值"对替代。RLE 是入门压缩的最佳教材,5 行代码就能跑,但揭示所有压缩算法的核心思想:**利用冗余**。

## 0 · 为什么要有这一天

游戏里数据量大:

- 地图:每个 tile 4 字节(类型 + flags),10km × 10km 地图 = 25M tiles = 100 MB
- 存档:entity 状态、物品、对话进度 → 50 MB
- 网络包:实时同步玩家位置、动作 → 每秒几 MB

不压缩,RAM / 磁盘 / 带宽都浪费。压缩是必备技能。

**压缩的两种类型**:

1. **无损压缩**:解压后数据完全一样。游戏存档、网络包(必须无损)
2. **有损压缩**:解压后近似(JPEG、MP3)。游戏贴图、音频可以用

今天 Casey 讲无损压缩,从 RLE 开始。

**RLE 的核心思想**:如果数据里有连续重复,把"重复 N 次 X"压成"(N, X)"。

例子:

```
原始:    AAAABBBCCDAA
RLE 压缩: (4,A)(3,B)(2,C)(1,D)(2,A) = 5 个 (count, byte) 对
```

12 字节压成 10 字节(假设每对 2 字节)。压缩率 83%。如果数据更重复(如 `AAAAA...`1000 个),压缩率 0.2%。

**何时 RLE 有效**:数据有大量连续重复。如:

- 简单图形(SVG / BMP):大片同色像素
- 简单地图:大片同类型 tile(草地、水)
- 文本里的空格、tab

**何时 RLE 无效**:数据无连续重复。如:

- 已经压缩的 JPEG / PNG
- 加密数据(随机性高)
- 复杂游戏关卡

但即使 RLE 本身不适合某些数据,**它的思想是所有压缩算法的基础**——找冗余,编码冗余。后续 Day 354(LZ)、Phase 7(PNG)、Phase 8(Huffman)都是变体。

心理锚点:今天之后你能写 RLE 编码/解码,理解"压缩率"概念,知道何时 RLE 有效何时无效。

## 2 · 心智模型

### 类比:超市扫码记录

你记录超市一天扫描的所有商品:

```
苹果 苹果 苹果 苹果 香蕉 香蕉 牛奶 牛奶 牛奶 牛奶 牛奶
```

12 个条目。如果每条目占 10 字节,120 字节。

RLE 风格:

```
4×苹果 2×香蕉 5×牛奶
```

3 条目,如果"4×苹果"占 12 字节(数量 + 商品名),共 36 字节。压缩率 30%。

**关键**:数据有"连续重复"才能压。如果商品是随机(苹果 香蕉 牛奶 苹果 牛奶 香蕉...),RLE 反而增大(每条目变成 `(1, 商品名)` 还多个"1")。

### RLE 的字节级实现

最简版:

```rust
fn rle_encode(input: &[u8]) -> Vec<u8> {
    let mut output = vec![];
    let mut i = 0;
    while i < input.len() {
        let cur = input[i];
        // 数连续重复
        let mut count = 1;
        while i + count < input.len() && input[i + count] == cur && count < 255 {
            count += 1;
        }
        // 写入(count, byte) 对
        output.push(count as u8);
        output.push(cur);
        i += count;
    }
    output
}
```

输入 `[A, A, A, A, B, B, C, D, A, A]` 输出 `[4, A, 2, B, 1, C, 1, D, 2, A]`(10 字节)。

解码:

```rust
fn rle_decode(input: &[u8]) -> Result<Vec<u8>, &'static str> {
    if input.len() % 2 != 0 {
        return Err("invalid RLE: odd length");
    }
    let mut output = vec![];
    let mut i = 0;
    while i < input.len() {
        let count = input[i] as usize;
        let byte = input[i + 1];
        for _ in 0..count {
            output.push(byte);
        }
        i += 2;
    }
    Ok(output)
}
```

### RLE 的"魔鬼细节"

**1. count 限制**

如果连续重复超过 255 次(8 位 count 上限),要分多次:

```
原始:300 个 A
RLE:  (255, A)(45, A) = 4 字节
```

300 字节压成 4 字节。压缩率 1.3%。

**2. 无重复数据膨胀**

如果数据无连续重复(`A B C D E F`),RLE 输出 `(1, A)(1, B)(1, C)...` = 12 字节,从 6 字节膨胀到 12 字节。**压缩率 200%**(变差)。

**3. 优化:不同的 escape**

为避免"无重复数据膨胀",可以用 escape 字节标记:

```
策略 A:全 RLE(简单,但无重复时膨胀)
策略 B:RLE + literal(复杂,但避免膨胀)
```

策略 B 例子:

```
原始:A B C D D D D E
编码: [LITERAL] 3 [A B C] [RUN] 4 [D] [LITERAL] 1 [E]
       ↑ escape    ↑ literal count
```

`LITERAL` 是 escape 字节,告诉解码器"接下来 N 字节是原文,不重复"。

**4. 二进制 vs 文本**

文本 RLE 通常用 ASCII 字符(如 `\0` 当 escape)。二进制 RLE 用 length-prefix(每对显式 count)。

Casey Day 353 用最简版(策略 A,全 RLE)——简单,适合教学。生产 PNG 用策略 B(PCX 风格)。

### 压缩率的数学

**信息熵(Entropy)**:数据的"信息量"。

```
熵 H = -Σ p(x) * log2(p(x))
```

`p(x)` 是字节 x 出现的概率。

均匀分布(每个字节等概率):熵 = 8 bit/byte(最大,无压缩空间)
全相同(全是 A):熵 = 0 bit/byte(完美 RLE 能压到 2 字节:count + byte)

**RLE 的极限**:对全相同数据,压缩率 = 2 / N(N 是长度)。对无重复数据,膨胀率 = 2x。

**Shannon 极限**:无损压缩平均不能超过熵。RLE 是熵编码的近似(对某些数据最优,对某些最差)。

后续 Day 354 的 LZ、Phase 8 的 Huffman 都更接近 Shannon 极限。

### 为什么 RLE 仍然重要

RLE 看似简陋,但**实际有用场景**:

1. **PNG 的 filter 模式**:PNG 内部用类似 RLE 的 filter 优化连续相同字节
2. **BMP / PCX**:老格式直接用 RLE
3. **传真**:CCITT Group 3/4 基于 RLE(白黑像素连续段)
4. **JPEG 的 0 游程**:JPEG 编码时大量 0 用 RLE 压缩
5. **游戏地图**:简单 tile map

**Casey 用 RLE 压 tile**:HH 地图是 tile grid,大片同类型(草地、水、墙),RLE 压缩率 5x+。

### 3.2 · 图形学视角

图形数据的压缩:

**1. 颜色 RLE**

简单图像(漫画、像素画)有大片同色像素,RLE 极有效。

**2. PNG filter**

PNG 不是直接 RLE,而是先 **filter**(把每行像素减去上行),让连续相同变成 0 序列,再 Deflate(LZ77 + Huffman)。

filter 模式:

```
None:    原样
Up:      当前像素 -= 上行像素
Sub:     当前像素 -= 左像素
Average: 当前像素 -= (上 + 左) / 2
Paeth:   当前像素 -= 预测(基于 上、左、左上)
```

filter 后的 0 序列 Deflate 压得极好。Casey Phase 7 详细讲。

**3. 纹理压缩(DXT / ETC / ASTC)**

GPU 直接采样压缩纹理。不是 RLE,是**块压缩**(把 4×4 像素压成 8 字节)。Phase 8 讲。

## 5 · 对照与变奏

### RLE 的多种变体

**PackBits**(Mac / PCX):

```
escape byte n:
  n < 128:  接下来 n+1 字节是 literal
  n >= 128: 接下来 1 字节重复 (257 - n) 次
```

更紧凑,无重复时不膨胀。

**CCITT Group 3**(传真):

每行单独编码,白黑段交替。专门优化二值图像。

**PCX**(老图像格式):

扫描线 RLE,带 escape。

**JPEG 的 0 游程**:

JPEG 的 DCT 系数大量 0,用 RLE 表示"连续 N 个 0"。配合 Huffman 编码。

### 不同数据类型的 RLE 效果

| 数据 | 压缩率 |
|---|---|
| 全相同(`AAAA...`) | 极好(~99%) |
| 大块同质(tile map) | 好(~80%) |
| 普通文本 | 差(~110%,膨胀) |
| 随机二进制 | 极差(~200%,膨胀) |
| 已压缩数据 | 极差(无法再压) |

### 历史演化

- **1960s**:RLE 早期用于传真
- **1970s**:LZ77 / LZW 出现,通用压缩兴起
- **1980s**:Deflate (LZ + Huffman),ZIP / GZIP
- **1990s**:bzip2(Burrows-Wheeler Transform)
- **2010s**:Zstd / Brotli,机器学习辅助压缩
- **2020s**:AI 压缩(neural compression)

RLE 是这条演化链的起点。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 RLE 压"普通文本"会膨胀?给个具体例子。

**参考解答**:

普通英文文本每个字符不同("Hello, World!"),RLE 编码每个字符变 `(1, char)`,2 字节,膨胀 100%。

例子:`"Hello"` 5 字节,RLE 编码 `(1,H)(1,e)(1,l)(1,l)(1,o)` 10 字节。膨胀 2x。

更糟:`"H"`(只有 1 字节)RLE 编码 `(1, H)` 2 字节,膨胀 2x。

只有"连续重复"才能压。普通文本应该用 LZ(找"前面出现过的串")或 Huffman(根据频率分配变长编码)。

```rust
fn rle_encode(input: &[u8]) -> Vec<u8> {
    let mut output = vec![];
    let mut i = 0;
    while i < input.len() {
        let cur = input[i];
        let mut count = 1usize;

            && input[i + count] == cur
            && count < 255

        output.push(cur);

    if input.len() % 2 != 0 {
        return Err("odd length");
    }
    let mut output = vec![];
    let mut i = 0;
    while i < input.len() {
        let count = input[i] as usize;
        let byte = input[i + 1];
        for _ in 0..count {
            output.push(byte);
        }
        i += 2;
    }
    Ok(output)
}

fn test_compression(name: &str, data: &[u8]) {
    let encoded = rle_encode(data);
    let decoded = rle_decode(&encoded).unwrap();
    let ratio = encoded.len() as f64 / data.len() as f64 * 100.0;
    let correct = data == decoded.as_slice();
    println!("[{}] orig={} enc={} ratio={:.1}% decoded_correct={}",
             name, data.len(), encoded.len(), ratio, correct);
}

fn main() {
    // 全相同
    let uniform = vec![b'A'; 1000];
    test_compression("uniform", &uniform);

    // 有重复(tile map 模拟)
    let mut tiled = vec![];

    let unique: Vec<u8> = (0..200u8).collect();

    // 真实文本

}
```

```rust
    let decoded = rle_decode(&encoded).unwrap();
    assert_eq!(tile_map, decoded);
    println!("Decoded correctly: true");

    // 2. 模拟无重复数据
    let random: Vec<u8> = (0..200u8).collect();
    let encoded_rand = rle_encode(&random);
    println!("\nRandom data: {} bytes -> {} bytes (ratio {:.1}%)",
             random.len(), encoded_rand.len(),
             encoded_rand.len() as f64 / random.len() as f64 * 100.0);
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
