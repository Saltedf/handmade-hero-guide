# Day 336 · 加粒子系统缓存

> 当你屏幕上有几千颗粒子时,"为每一颗粒子单独分配内存"和"为整片粒子统一预分配一大块缓存"差着两个数量级的性能。今天 Casey 把粒子系统从"按需分配"重构到"预分配缓存"——这是把内存模式从"系统调用堆栈"切到"数据导向设计"的典型一课。

## 0 · 为什么要有这一天

想象你在做一款 ARPG,主角一刀砍出去,剑刃拖出一片火花。这些火花是粒子:每个粒子有位置、速度、生命周期、颜色,可能还带一张小贴图。一次挥砍你想喷 200 颗,战斗里同时有 10 个角色在挥砍——屏幕上瞬间 2000 颗粒子。

如果每颗粒子诞生时你 `malloc(sizeof(Particle))`,死亡时 `free`,那么一帧里你要做 2000+ 次 `malloc/free`。`malloc` 是 glibc 的 ptmalloc,它会:

1. 加锁(线程 arena 锁)
2. 在 free list 里找合适大小
3. 切分 / 合并 chunk
4. 写元数据(chunk header)
5. 解锁

每次 ~100 纳秒,2000 次 = 200 微秒/帧,纯内存分配占了 1.2% 帧时间(60 FPS 一帧 16.6ms)。听上去不多?但问题不止性能:**内存碎片**。粒子频繁生死,堆里全是 64 字节的小洞,长时间运行后 `malloc` 找不到大块连续内存,要么返回 NULL,要么操作系统把 `brk` 推得很高(RSS 飙升)。

业界的标准答案:**对象池(object pool)**。游戏启动时一次性分配 `MAX_PARTICLES = 8192` 个粒子的连续数组,所有粒子从这个池里取,死掉归位。零 `malloc`、零碎片、完美 cache 局部性(CPU 一次 cache line 64 字节正好装 1-2 个粒子)。

今天 Casey 把这个模式套到 HH 的粒子系统上,他管它叫 **particle system cache**——一个为粒子专门设计的、固定大小的内存池。

心理锚点:今天之后你能解释为什么 `Vec<Particle>` 在游戏里是反模式,能自己写一个 `ParticlePool` 容器,能理解为什么 Casey 反复说"内存布局决定性能"。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_particles.cpp`(他在 Day 332 左右建的文件),看到一个不和谐的画面:每喷一颗粒子就 `Push` 到一个 `particle_list`(动态数组),每死一颗就 `SwapRemove`。问题是 `SwapRemove` 改变数组顺序,而 SIMD 批处理粒子需要"连续同一组",顺序乱跳等于 SIMD 失效。

Casey 决定换思路:

1. 不再用动态数组,改用**预分配的固定数组 + 自由链表**
2. 数组大小固定(`MAX_PARTICLES = 4096`),用 `u32` 索引引用粒子,而不是裸指针
3. 死掉的粒子把索引还回自由链表(不真删)
4. 活粒子在数组前段连续排列(SIMD 友好)

他在 `game_state` 里加了一个新字段 `particle_cache`,类型是个手写的池子。今天的核心是这个池子的数据结构和入池/出池操作。

## 2 · 心智模型

### 类比:酒店房间管理

想象你经营一家有 4096 间房的酒店。客人(粒子)来来去去。两种管理方式:

**方式 A(动态数组 / `Vec<Particle>`)**:每来一个客人,你租一块新地皮盖房间(`malloc`);客人走了,你拆房子(`free`)。地皮越来越碎,新建房子要绕着碎片找空地。

**方式 B(对象池 / particle cache)**:你一次性盖好 4096 间房。用一个登记本来记"哪些房间空着"。客人来了,从登记本顶部拿一间空的;客人走了,把房间号写回登记本顶。房子永远在那里,只是被记成"空"还是"有人"。

方式 B 的优势:

- **零分配**:启动后再无 `malloc/free`
- **零碎片**:所有房间同等大小、连续排列
- **cache 友好**:同一个 SIMD 寄存器可以一次处理 4 个相邻房间
- **可预测**:4096 是硬上限,内存使用永远不超过 `4096 * sizeof(Particle)`

代价:**有上限**。如果一帧里需要 4097 颗粒子,多出来的那颗会被丢弃(或者抢掉最老的一颗)。这是工程权衡:游戏粒子有上限是常识。

### 数据结构:三个数组 + 一个游标

最小可用对象池需要三个组件:

```rust
struct ParticleCache {
    // 1. 实际存储:固定大小的粒子数组
    particles: [Particle; MAX_PARTICLES],
    // 2. 自由链表:每个空槽记录"下一个空槽的索引"
    //    用 u32::MAX 表示"链表末端"
    next_free: [u32; MAX_PARTICLES],
    // 3. 游标:链表头
    free_head: u32,
    // 4. 计数:当前活粒子数(便于诊断,不参与逻辑)
    alive_count: u32,
}

const MAX_PARTICLES: usize = 4096;
const NULL: u32 = u32::MAX;
```

**关键观察**:`next_free` 复用了"空槽位"的存储空间——空槽本来就没数据,正好用来存"链表指针"。这是嵌入式系统里经典的 **intrusive linked list**(侵入式链表)技巧。

**初始化**:所有槽都空,所以 `next_free[i] = i+1`,最后一个 `= NULL`。`free_head = 0`。

```rust
impl ParticleCache {
    fn new() -> Self {
        let mut cache = Self {
            particles: [Particle::ZERO; MAX_PARTICLES],
            next_free: [0; MAX_PARTICLES],
            free_head: 0,
            alive_count: 0,
        };
        // 串成链表:0 -> 1 -> 2 -> ... -> 4095 -> NULL
        for i in 0..MAX_PARTICLES {
            cache.next_free[i] = if i + 1 < MAX_PARTICLES {
                (i + 1) as u32
            } else {
                NULL
            };
        }
        cache
    }
}
```

**分配一颗**:从链表头摘一个槽。

```rust
impl ParticleCache {
    fn alloc(&mut self) -> Option<u32> {
        if self.free_head == NULL {
            return None;  // 池满了
        }
        let slot = self.free_head;
        self.free_head = self.next_free[slot as usize];
        self.next_free[slot as usize] = NULL;  // 防御性:已分配的槽不在链表中
        self.alive_count += 1;
        Some(slot)
    }
}
```

**释放一颗**:把槽塞回链表头。

```rust
impl ParticleCache {
    fn dealloc(&mut self, slot: u32) {
        debug_assert!(slot as usize <= MAX_PARTICLES);
        debug_assert!(self.next_free[slot as usize] == NULL, "double free!");
        self.next_free[slot as usize] = self.free_head;
        self.free_head = slot;
        self.alive_count -= 1;
    }
}
```

**复杂度**:`alloc` / `dealloc` 都是 **O(1)**,无锁(单线程)或一把锁(多线程)。

### 与 `Vec<Particle>` 的对比

| 维度 | `Vec<Particle>` | `ParticleCache` |
|---|---|---|
| 内存分配 | 满了 `realloc`(可能拷贝整块) | 启动后零分配 |
| 删除 | `swap_remove` O(1) 但乱序 | O(1),不影响其它粒子位置 |
| 上限 | 只受 RAM 限制 | 固定 `MAX_PARTICLES` |
| SIMD | 删除后顺序乱,SIMD 利用率低 | 活粒子自然紧凑,SIMD 友好 |
| Cache miss | 偶尔 `realloc` 后地址全变 | 永远同一地址 |
| 实现 | 一行 `vec![]` | 手写 ~50 行 |

游戏开发里**所有高频创建/销毁的对象**都该走池:粒子、子弹、临时音效源、网络包缓冲、bullet hell 里的弹幕。Rust 标准库不提供,因为通用池子设计空间太大,但生态有 `bumpalo`(arena)、`slotmap`(带世代的池)、`heapless`(嵌入式)等。

### 索引 vs 指针:为什么用 `u32`

`ParticleCache` 内部用 `u32` 索引而不是 `&mut Particle`。原因:

1. **借检查器友好**:`&mut cache` 和 `&mut cache.particles[i]` 同时存在会让 Rust 借用检查报错。用索引则可以"先取索引,再操作"。
2. **空间**:32 位索引 4 字节,64 位指针 8 字节。粒子里很多引用,省一半内存。
3. **重定位安全**:池子整个移动(比如从 `Box<Game>` 移到 `Box<OtherGame>`),索引仍然有效,指针全失效。
4. **debug 友好**:索引可以打印成"第 1234 号槽",指针打印成 `0x7f3c2a001230` 看不懂。

代价:**间接寻址**。访问 `cache.particles[idx as usize]` 多一次地址计算,但 CPU cache 友好的连续数组让这个开销几乎为零。

### 世代(generation):防止悬空引用

如果某段代码持有索引 `slot = 42`,然后该槽被释放、又被分配给一颗新粒子——老代码不知道,会用 `slot=42` 操作新粒子,bug 极难复现。

解决方案:**世代计数**。每个槽加 `generation: [u32; MAX]`,分配时 `+=1`。引用不仅存 `slot`,还存 `generation`:

```rust
#[derive(Copy, Clone, PartialEq)]
struct ParticleHandle { slot: u32, generation: u32 }

fn get(&self, h: ParticleHandle) -> Option<&Particle> {
    if self.generation[h.slot as usize] == h.generation {
        Some(&self.particles[h.slot as usize])
    } else {
        None  // 老引用,已失效
    }
}
```

Casey 在 HH 里 Day 336 还没做世代,因为粒子系统是 fire-and-forget——发射后就只遍历更新,不持有外部引用。但 `slotmap` crate 把这个模式做成工业级,后面 Day 341 用到时可以切过去。

## 3 · 四域深入

### 3.1 · 游戏编程视角

对象池在游戏里是基础数据结构。Casey 在 Day 336 之前的 Day 328-335 已经搭好粒子系统的雏形(发射器、积分更新、SIMD 加速),但内存是 `Vec<Particle>`。今天升级到 cache。

**为什么 Casey 不用现成 crate?** 因为 HH 是教学项目,他要让你看清池子的每一行代码。生产代码你会用 `slotmap::SlotMap` 或 `bumpalo::Bump`,但原理就是这个。

**粒子系统的真实世界分布**:

- **Unreal Engine** Niagara:GPU 上做粒子,内存是 GPU buffer,模式类似但跑在 shader 里
- **Unity** Particle System:CPU 池 + GPU 实例化,有内置池
- **Bevy** `bevy_hanabi`:Rust 写的 GPU 粒子,数据存 `Vec` 但每帧重建(因为 GPU 端)
- **Godot** GPUParticles2D/3D:类似 Unity

所有引擎的 CPU 粒子都用对象池。这是图形程序员面试必考题。

### 3.2 · 图形学视角

粒子系统的内存布局直接影响 SIMD 和 GPU 实例化的效率。

**AoS(Array of Structs)** vs **SoA(Struct of Arrays)**:

```rust
// AoS:每个粒子是连续的 32 字节
struct Particle { pos: Vec3, vel: Vec3, age: f32, life: f32 }
particles: [Particle; 4096]   // 4096*32 = 128 KB

// SoA:每个字段分开
struct Particles {
    pos_x: [f32; 4096],
    pos_y: [f32; 4096],
    pos_z: [f32; 4096],
    vel_x: [f32; 4096],
    // ...
}
```

**SIMD 角度**:更新粒子位置时 `pos += vel * dt`。AoS 一次 SIMD 操作能处理 1 个粒子(`[pos_x, pos_y, pos_z, age]` 不是同质数据);SoA 一次能处理 4 个粒子的 `pos_x`(四个 f32 塞进一个 `__m128`)。

**Casey 的 Day 337 选择**:他 Day 336 用 AoS(简单),Day 337 切 SoA(SIMD 友好)。今天是 AoS,明天是 SoA,你能直接对比两个布局的代码差异。

**GPU 实例化**:如果粒子要送 GPU 绘制,数据布局必须是 SoA——vertex buffer 按字段分 buffer。Casey 在 Phase 7(资产管线)会讲。

### 3.3 · Linux 系统编程视角

Linux 内核里"对象池"叫 **slab allocator**。`kmalloc` 不像 `malloc` 那样通用,而是分 slab:每个 slab 是固定大小对象的池子(32B / 64B / 128B ...)。

```bash
# Linux 内核的 slab 池子
cat /proc/slabinfo | head -20
# 输出:
# name            <active_objs> <num_objs> <objsize> ...
# nf_conntrack_ffff8801   32  32  320 ...
# dentry            8192  8192   192 ...
# inode_cache      16384 16384   608 ...
```

每行是一个池子:固定 objsize(对象大小),一次分配一大块 page,切成等大对象。和我们的 `ParticleCache` 完全是同一思想——只是内核版处理 1000 种不同大小的对象,我们处理 1 种。

**Linux 内存分配的层级**:

1. `mmap` / `brk` — 向操作系统要页(4KB)
2. `malloc` (ptmalloc) — 在用户态把页切成小块
3. `arena` / `pool` — 应用层针对固定模式做的池子
4. **栈分配** — 函数返回自动回收,零开销

游戏里,**粒子池是第 3 层**:你已知粒子大小固定、生死模式固定,绕开 ptmalloc 自己管更快。

**用 perf 看 malloc 开销**:

```bash
sudo pacman -S perf
perf stat -e 'syscalls:sys_enter_brk,syscalls:sys_enter_mmap' ./your_game
# 数量大说明分配频繁,该上池子了
```

### 3.4 · Rust 生态视角

Rust 表达对象池的几个流派:

#### 流派 1:手写(今天 Casey 用的)

```rust
struct ParticleCache {
    particles: [Particle; MAX],
    next_free: [u32; MAX],
    free_head: u32,
}
```

零依赖,完全控制,**借检查器在 alloc/dealloc 时偶尔需要 `unsafe` 或拆分借用**。Casey 在 C 里没这问题。

#### 流派 2:`slotmap` crate(带世代)

```toml
slotmap = "1.0"
```

```rust
use slotmap::SlotMap;
slotmap::new_key_type! { struct ParticleKey; }
let mut particles: SlotMap<ParticleKey, Particle> = SlotMap::with_capacity(4096);
let k: ParticleKey = particles.insert(Particle::new());
// k 自带 generation,悬空访问返回 None
```

工业级,自带世代、迭代器、序列化。代价:每次 `insert` 比 PoC 版贵(算世代 + 可能 rehash)。

#### 流派 3:`bumpalo`(arena,帧分配)

```rust
use bumpalo::Bump;
let bump = Bump::new();
let p: &mut Particle = bump.alloc(Particle::new());
// 不需要 free——整个 bump 在帧结束时 reset
```

适合"一帧内全部分配、帧末统一回收"的临时对象(粒子、UI 临时节点)。最简单最快。代价:**没有个体 free**,要么全留要么全清。

#### 流派 4:`heapless`(no_std / 嵌入式)

```rust
use heapless::Vec;
let mut v: heapless::Vec<Particle, 4096> = heapless::Vec::new();
v.push(Particle::new()).unwrap();  // 满了报错
```

固定容量,无堆。适合嵌入式 / WASM。

#### 借检查器痛点

Rust 写池子最痛的一点:**`&mut self.alloc()` 和 `&mut self.particles[slot]` 不能同时存在**。常见解法:

```rust
// 错误:借检查器报错
let slot = self.alloc()?;
self.particles[slot] = Particle::new();  // 双重借用

// 正确 1:先 alloc 返回索引,再用索引访问
let slot = self.alloc()?;
self.particles[slot as usize] = Particle::new();  // 这里没"借" alloc 的引用了

// 正确 2:unsafe(慎用)
let slot = self.alloc()?;
unsafe {
    let p = self.particles.get_unchecked_mut(slot as usize);
    *p = Particle::new();
}

// 正确 3:拆分借用(split borrow)
let Self { particles, next_free, free_head, .. } = self;
// 现在可以独立借用 particles 和 next_free
```

Casey 在 C 里没这烦恼。Rust 表达池子要绕一下,但**安全保证值得**——空指针、悬垂引用、double free 全部编译期消除。

## 4 · 认知地图

### 4.1 上级

- **数据导向设计(Data-Oriented Design)** —— 把数据布局而不是对象抽象放在第一位
- **内存管理** —— 谁分配、谁释放、怎么高效
- **资源池化** —— 通用模式:连接池、线程池、对象池
- **cache-friendly programming** —— 围绕 CPU cache line(64B)组织数据

### 4.2 同级(并行方案)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| `Vec<Particle>` + swap_remove | 简单,会扩容 | 原型、低频生死 | ❌(Day 336 前) |
| `Vec<Particle>` + tombstone | 不破坏顺序 | 需要 SIMD 紧凑 | 偶尔 |
| 固定数组 + 自由链表(今天) | 零分配、紧凑 | 高频粒子 | ✅ |
| 固定数组 + 世代 | 防悬垂 | 长生命周期对象 | 后续可升级 |
| `bumpalo::Bump`(帧分配) | 无个体 free | 一帧内临时 | UI、debug overlay |
| `slotmap::SlotMap` | 带世代的工业池 | 通用对象 | ECS 实体 |

### 4.3 下级

- **粒子数组** `[Particle; MAX]` —— 实际存储
- **自由链表** `next_free + free_head` —— O(1) 分配回收
- **世代计数**(可选) —— 防悬垂引用
- **SIMD 友好布局**(SoA) —— Day 337 改造
- **池满策略**(丢弃最老 / 拒绝) —— 业务决策

## 5 · 对照与变奏

### 同一模式在不同场景的变体

**粒子系统**(高频生死、固定大小):今天的 `ParticleCache`。

**ECS 实体**(低频生、生命周期长):`slotmap` / `hecs` 用世代 + 自由链表,因为外部代码会长期持有 entity handle。

**网络包缓冲**(固定大小、瞬时使用):`bumpalo`,每帧重置,因为包处理完就丢。

**数据库连接池**(固定大小、长生命周期):`r2d2` / `bb8`,带超时、健康检查、最大连接数——比粒子池复杂得多,但内核是同一个自由链表。

**线程池**(固定大小 worker):`rayon` / `tokio`,内核是 task 队列而非自由链表,但思想类似:预分配 worker,任务调度。

### 历史演化

- **1960s**:操作系统最早用池(磁盘块缓存、inode 缓存)
- **1990s**:游戏开发发现 `malloc` 太慢,各家引擎自带池(GameCube / PS2 SDK 内置)
- **2000s**:对象池成为引擎标配,数据导向设计兴起
- **2010s**:Rust / Swift 把"零成本抽象"普及,`SlotMap` / `Bump` crate 成熟
- **2020s**:GPU 粒子崛起,CPU 池退居调度角色

### 紧凑数组(compact array)

另一个变体:**活粒子始终在数组前段连续排列**。这样 SIMD 不需要扫描"死槽":

```rust
struct CompactPool {
    particles: [Particle; MAX],   // 前 alive_count 是活的
    alive_count: usize,
}

// 分配:加到末尾
fn alloc(&mut self) -> usize {
    let i = self.alive_count;
    self.alive_count += 1;
    i
}

// 释放:把末尾元素搬到删除位置
fn dealloc(&mut self, i: usize) {
    let last = self.alive_count - 1;
    self.particles[i] = self.particles[last];
    self.alive_count -= 1;
}

// 遍历:只看前 alive_count
for i in 0..self.alive_count {
    self.particles[i].update(dt);
}
```

优点:**SIMD 完美**,无 tombstone。缺点:**索引会失效**(搬运后,原来引用末尾粒子的代码拿到错粒子)。Casey 在 Day 337 会用这个模式做 SIMD。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 用 `u32` 索引而不是 `&Particle` 引用?至少说出 3 个原因。另外,`u32` 而不是 `usize` 有什么好处和坏处?

**参考解答**:

3 个原因:
1. **借检查器友好**:`&mut cache` 和 `&cache.particles[i]` 同时存在编译失败;索引则可分离。
2. **空间**:`u32` 4 字节,`&Particle`(64 位指针)8 字节。粒子内部很多引用,省一半。
3. **重定位安全**:cache 整体移动后索引仍有效,指针全失效。利于把 cache 放在 `Box` 里重新分配。

`u32` vs `usize`:
- 好处:32 位节省空间;明确表达"最大 40 亿"(够用了);跨平台一致。
- 坏处:`particles[idx as usize]` 多一次类型转换;`usize` 才是 Rust 数组原生索引类型;超过 40 亿槽子会溢出(实际不可能)。

工程取舍:**池子用 `u32`,数组下标用 `usize`**,这是 Rust 社区惯例。

### Lv2 · 动手实践

**题**:实现一个完整的 `ParticleCache`,包含 `new`, `alloc`, `dealloc`,以及一个 `for_each_alive` 方法。写一个 main 测试:分配 10 颗粒子,释放其中 3 颗,再分配 5 颗,验证 `alive_count` = 12 且池子没崩。

完成标准:`cargo run` 打印 `alive=12, ok=true`。

**参考解答**:

```rust
const MAX: usize = 4096;
const NULL: u32 = u32::MAX;

#[derive(Copy, Clone, Debug)]
struct Particle { id: u32 }  // 简化:只放个 id
impl Particle { const ZERO: Particle = Particle { id: 0 }; }

struct ParticleCache {
    particles: [Particle; MAX],
    next_free: [u32; MAX],
    free_head: u32,
    alive_count: u32,
}

impl ParticleCache {
    fn new() -> Self {
        let mut c = Self {
            particles: [Particle::ZERO; MAX],
            next_free: [0; MAX],
            free_head: 0,
            alive_count: 0,
        };
        // 串链表:0->1->2->...->MAX-1->NULL
        let mut i = 0;
        while i < MAX {
            c.next_free[i] = if i + 1 < MAX { (i + 1) as u32 } else { NULL };
            i += 1;
        }
        c
    }

    fn alloc(&mut self) -> Option<u32> {
        if self.free_head == NULL { return None; }
        let slot = self.free_head;
        self.free_head = self.next_free[slot as usize];
        self.next_free[slot as usize] = NULL;
        self.alive_count += 1;
        Some(slot)
    }

    fn dealloc(&mut self, slot: u32) {
        debug_assert!(self.next_free[slot as usize] == NULL, "double free");
        self.next_free[slot as usize] = self.free_head;
        self.free_head = slot;
        self.alive_count -= 1;
    }

    fn for_each_alive(&self, mut f: impl FnMut(usize, &Particle)) {
        // 简化版:全扫描(实际应该用活粒子位图)
        // 注意:这里我们扫所有槽,需要标记哪些活的——
        // 教学版简化:跟踪活粒子集合
        for i in 0..MAX {
            // 这里跳过,实际需要额外标记
            let _ = i;
        }
        let _ = &mut f;
        // 真实实现见 §8
    }
}

fn main() {
    let mut cache = ParticleCache::new();
    let mut handles = Vec::new();
    for _ in 0..10 {
        handles.push(cache.alloc().unwrap());
    }
    // 释放第 0, 3, 7 个
    cache.dealloc(handles.remove(0));
    cache.dealloc(handles.remove(2));  // 注意 remove 后 index 变
    cache.dealloc(handles.remove(5));
    // 再分配 5 个
    for _ in 0..5 {
        cache.alloc().unwrap();
    }
    let ok = cache.alive_count == 12;  // 10-3+5
    println!("alive={}, ok={}", cache.alive_count, ok);
}
```

**关键解释**:
- `next_free[i] = NULL` 在 alloc 后,是为了 `debug_assert!(... == NULL)` 防 double free。
- `dealloc` 把槽塞回链表头,所以"刚释放的槽"会被下次 alloc 优先取——LIFO 行为,利于 cache(刚用的槽刚被复用)。
- `remove` 改变 Vec 长度,所以释放时要小心索引——上面的代码用 `remove` 后 `handles` 变短,后续索引要调整。

## 8 · Rust / Arch 落地代码

### 完整可跑的 Rust 实现

把 Lv2 扩展成完整版,加活粒子位图 + 紧凑迭代。

```rust
// Cargo.toml: 纯 std,无依赖

const MAX_PARTICLES: usize = 4096;
const NULL: u32 = u32::MAX;

#[derive(Copy, Clone, Debug)]
struct Particle {
    pos: [f32; 3],
    vel: [f32; 3],
    age: f32,
    life: f32,
}

impl Particle {
    const ZERO: Particle = Particle {
        pos: [0.0; 3], vel: [0.0; 3], age: 0.0, life: 0.0,
    };

    fn alive(&self) -> bool { self.age < self.life }
}

struct ParticleCache {
    // 活粒子紧凑存于前 alive_count 个槽
    particles: [Particle; MAX_PARTICLES],
    // 每个槽的"反向索引":如果该槽被搬到 slot i,这里记原 idx
    // 简化:本例我们用 compact pool,不需要 next_free
    alive_count: usize,
}

impl ParticleCache {
    fn new() -> Self {
        Self {
            particles: [Particle::ZERO; MAX_PARTICLES],
            alive_count: 0,
        }
    }

    // 紧凑池:alloc 就是 alive_count++
    fn spawn(&mut self, p: Particle) -> Option<usize> {
        if self.alive_count >= MAX_PARTICLES {
            return None;  // 池满
        }
        let i = self.alive_count;
        self.particles[i] = p;
        self.alive_count += 1;
        Some(i)
    }

    // 紧凑池:kill 把末尾搬到目标位置
    fn kill(&mut self, i: usize) {
        debug_assert!(i < self.alive_count);
        let last = self.alive_count - 1;
        if i != last {
            self.particles[i] = self.particles[last];  // swap-move
        }
        self.alive_count -= 1;
    }

    // 关键:每帧扫一遍,kill 死掉的
    fn update(&mut self, dt: f32) {
        let mut i = 0;
        while i < self.alive_count {
            let p = &mut self.particles[i];
            p.age += dt;
            // Euler 积分:pos += vel * dt
            p.pos[0] += p.vel[0] * dt;
            p.pos[1] += p.vel[1] * dt;
            p.pos[2] += p.vel[2] * dt;

            if !p.alive() {
                self.kill(i);
                // 不 i++,因为 kill 把新粒子搬到了 i
            } else {
                i += 1;
            }
        }
    }

    fn iter(&self) -> &[Particle] {
        &self.particles[..self.alive_count]
    }
}

fn main() {
    let mut cache = ParticleCache::new();

    // 喷 100 颗粒子,寿命 2 秒
    for k in 0..100 {
        let p = Particle {
            pos: [0.0, 0.0, 0.0],
            vel: [k as f32 * 0.1, 1.0, 0.0],
            age: 0.0,
            life: 2.0,
        };
        cache.spawn(p);
    }
    println!("Spawned: alive = {}", cache.alive_count);  // 100

    // 推进 1 秒
    cache.update(1.0);
    println!("After 1s: alive = {}", cache.alive_count);  // 100(都没死)

    // 再推进 1.5 秒,全部应该死掉(age > life)
    cache.update(1.5);
    println!("After 2.5s: alive = {}", cache.alive_count);  // 0

    // 验证:再喷 5 颗
    for _ in 0..5 {
        cache.spawn(Particle {
            pos: [0.0; 3], vel: [1.0; 3], age: 0.0, life: 5.0,
        });
    }
    println!("Final: alive = {}", cache.alive_count);  // 5
}
```

**每行解释**:
- `[Particle::ZERO; MAX]` — Rust 1.51+ 的 const generics 表达式初始化。`Particle::ZERO` 必须是 `const fn` 或 const 关联常量。
- `swap-move`:把末尾元素搬到删除位置,O(1) 删除但**破坏顺序**——对粒子无影响,因为粒子无身份。
- `while i < self.alive_count` 而非 `for i in 0..`:`kill` 会改 `alive_count`,迭代器会 panic。
- `iter()` 返回切片而非迭代器:让调用方既能 `for p in cache.iter()` 也能 `cache.iter()[i]`。

**关键 Rust 特性**:
- **const generics** `[T; N]` 中 `N` 是编译期常量。`MAX_PARTICLES = 4096` 写死在二进制里。
- **`Copy`** for `Particle`:所有字段都是 `Copy`(f32 数组),所以 `Particle` 也是。可以无成本按值传递。
- **`debug_assert!`**:debug 模式检查,release 模式编译掉。Game dev 常用——开发期检查,生产期不付代价。
- **`Option<usize>`**:`spawn` 池满返回 `None`,迫使调用方处理。比 `panic!` 更 Rust。
