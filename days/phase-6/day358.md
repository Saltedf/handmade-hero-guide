# Day 358 · 深度缓冲入门

> HH 进入图形学深水区。今天 Casey 讲 **depth buffer**(深度缓冲,Z-buffer)——3D 渲染的核心算法。问题:多个三角形可能投影到同一像素,谁该被画上去?最直观答案:"最近的那个"。但"最近"怎么算?这就是 depth buffer 解决的。

## 0 · 为什么要有这一天

3D 渲染的根本问题:**屏幕是 2D,世界是 3D**。多个 3D 点可能投影到同一 2D 像素:

```
3D:                          2D 屏幕:
       P3 (远处)               ┌────┐
       /                       │    │ ← 像素 (100, 50)
      /                        │    │
     P2 (中)                   └────┘
    /
   P1 (近) ← 应该画这个!
  /
 /  ← 玩家相机
```

P1、P2、P3 都投影到像素 (100, 50)。**谁该被画?**

视觉直觉:**最近的(P1)**。但渲染管线不知道"近"——它一次画一个三角形,不知道后面还有什么。

**最朴素的方案**:**Painter's Algorithm**(画家算法)。先画远的,后画近的——后画的覆盖先画的。

问题:**复杂场景排序困难**。

```
三个三角形互相穿插:A 的一部分在 B 前面,B 的一部分在 A 前面...
无法排序,画家算法失败。
```

**深度缓冲的解决方案**:**每个像素不仅存颜色,还存深度**。每个三角形画时,逐像素检查"我的深度 < 已存的深度?"如果是,覆盖颜色 + 更新深度;否则不动。

```
depth_buffer: [inf, inf, inf, ...]  // 初始无穷大
color_buffer: [   ?,    ?,    ?, ...]

绘制三角形 T1 (深度 5):
  像素 (0,0): T1 深度 5 < inf → 画!depth_buffer[0,0] = 5

绘制三角形 T2 (深度 3):
  像素 (0,0): T2 深度 3 < 5 → 画!depth_buffer[0,0] = 3

绘制三角形 T3 (深度 7):
  像素 (0,0): T3 深度 7 > 3 → 不画
```

最终 (0,0) 显示 T2 的颜色,depth_buffer 记录 3。**正确**。

这种"每个像素独立判断深度"的算法简单、高效、对三角形顺序不敏感。是 GPU 渲染的核心。

**为什么到 Day 358 才讲?** Casey 之前在 2D 模式下渲染,没有"前后"概念——所有 sprite 在同一平面,画家算法够用。Day 358 开始 Casey 真正进入 3D 视觉效果(精灵卡片堆叠),需要 depth buffer。

心理锚点:今天之后你能解释 depth buffer 算法,理解 z-fighting(深度冲突)的成因,知道为什么 GPU 渲染需要 depth attachment,理解 1/z 非线性的精度分布。

## 2 · 心智模型

### 类比:玻璃画叠加

想象你画油画,一层层叠加:

- **画家算法**:你按"远→近"顺序画,后画覆盖前画
- **深度缓冲**:每个位置记录"已画的最浅颜色深度"。你画新笔触时,如果新笔触比记录的浅(更近),画上去 + 更新记录;否则跳过

画家算法依赖"按顺序",深度缓冲每个位置独立判断。

深度缓冲的优势:

1. **顺序无关**:不管按什么顺序画,结果一致
2. **正确处理穿插**:三角形互相穿插也正确
3. **简单实现**:逐像素比较,O(1) per pixel

劣势:

1. **内存开销**:每像素一个深度值(24 或 32 位),1920×1080 = 8MB
2. **不能处理透明**:透明物体需要"混合"已有颜色,深度测试不够
3. **精度问题**:远处物体深度精度差,导致 z-fighting

### 深度的数学定义

3D 渲染管线:

```
model space → world space → view space → clip space → NDC → screen space
```

**深度**通常指 **NDC z 坐标**(Normalized Device Coordinate)。NDC 是 [-1, 1] 立方体(OpenGL)或 [0, 1](DirectX)。

```
NDC z = -1: 近平面(near plane)
NDC z = +1: 远平面(far plane)
```

深度值就是 NDC z 经过 [0, 1] 映射:`depth = (z + 1) / 2`(OpenGL)。

**透视投影后,z 不是线性的**:

```
view_z (相机空间 z,线性):     1, 2, 4, 8, 16, 32, 64
clip_z (透视除法后,非线性):    0.99, 0.5, 0.25, 0.125, ...
```

`clip_z ≈ 1 / view_z`(对透视投影)。

**关键洞察**:`1/z` 是非线性的——近处精度极高,远处精度极低。

```
近处 (z=1):   depth = 0.0
              z=2:   depth = 0.5  (50% 的深度精度用于 1~2 范围)
              z=4:   depth = 0.75 (25% 用于 2~4)
              z=8:   depth = 0.875 (12.5% 用于 4~8)
              ...
远处 (z=1000): depth = 0.999
```

这意味着:**远处物体深度差异极小**,depth buffer 区分不开,导致 **z-fighting**(深度冲突)——两个相近深度的物体,某些像素 A 在前,某些 B 在前,看起来闪烁。

**解决方案**:

1. **减小 far / near 比**:near=0.1 far=100 比 near=0.001 far=1000 精度好
2. **用 24 或 32 位 depth buffer**:16 位精度差
3. **Reversed-Z**:把 near 设最大值,far 设最小值,利用浮点精度分布特性。现代引擎标配。
4. **多 depth buffer**(分块):不同距离用不同精度

### 深度测试算法

```
for each triangle T:
    for each pixel (x, y) covered by T:
        z = interpolate_depth(T, x, y)  // 重心坐标插值
        if z < depth_buffer[x, y]:       // OpenGL 默认 "less"
            depth_buffer[x, y] = z
            color_buffer[x, y] = T.color_at(x, y)
```

复杂度:O(像素数 × 三角形覆盖) per frame。GPU 并行处理像素,极快。

**深度函数(depth function)**:

- `LESS`(默认):新 z 小于已存 z 通过
- `LEQUAL`:小于等于(让等深度也通过)
- `GREATER`:用于 reversed-Z
- `EQUAL`:stencil-like 用途
- `ALWAYS`:不做深度测试(等价无 depth buffer)

### 深度的插值

三角形三个顶点 A、B、C 有深度 z_A、z_B、z_C。三角形内部某点 P 的深度怎么算?

**重心坐标**(barycentric):

```
P = α * A + β * B + γ * C
其中 α + β + γ = 1
```

P 的属性 = α * A_attr + β * B_attr + γ * C_attr。

但**透视投影下深度的插值不是线性的**!正确的插值是**透视正确插值**:

```
depth_at_P = 1 / (α/z_A + β/z_B + γ/z_C)
```

而不是 `α * z_A + β * z_B + γ * z_C`。

直觉:远处物体在屏幕上"压缩",线性的重心坐标会失真。透视正确插值抵消这种压缩。

GPU 硬件自动做透视正确插值。CPU 软渲染要自己实现。

### Depth Buffer 的内存布局

```
1920 x 1080 屏幕
+---------------+
| color buffer  |  4 字节/像素 (RGBA8) = 8.3 MB
+---------------+
| depth buffer  |  4 字节/像素 (DEPTH24_STENCIL8) = 8.3 MB
+---------------+
```

depth buffer 和 color buffer 同样大小,每像素 4 字节(24 位深度 + 8 位 stencil)。

**stencil buffer**(模板缓冲)是另一概念:每像素 8 位,用作"mask"——标记哪些像素允许画。常用于阴影、镜面反射。

### Z-Fighting

两个面共面或几乎共面,depth buffer 精度区分不开,导致**某些像素 A 在前,某些 B 在前**,看起来闪烁。

```
面 A 深度 0.5
面 B 深度 0.5000001

每像素 depth 测试:
像素 (10, 10): A 插值深度 0.5000001, B 插值深度 0.5000000 → B 通过
像素 (10, 11): A 插值深度 0.5000000, B 插值深度 0.5000001 → A 通过
...
```

视觉上:两个面在屏幕上"撕裂",随相机移动闪烁。

**解决方案**:

1. **polygon offset**:渲染时给深度加小偏移,强制分离
2. **避免共面几何**:设计时让两个面有微小高度差
3. **增大 near plane**:near 越大,精度越好
4. **Reversed-Z**:`depth = far - z + near`,利用浮点精度

### Reversed-Z(现代标准)

传统 OpenGL:`depth = (z - near) / (far - near)` → 近处精度高,远处低。

Reversed-Z:`depth = (far - z) / (far - near)` → 近处精度低,远处高。

结合 **floating-point depth buffer**(不是 fixed-point),`depth ∈ [0, 1]` 的浮点分布在 0 附近精度极高(指数编码),刚好匹配 reversed-Z 的"近处精度高"需求。

效果:**far/near = 10000 也能避免 z-fighting**(传统需要 far/near < 1000)。

现代引擎(Unreal、Unity、Bevy)默认 reversed-Z。Casey HH Day 364 切 OpenGL 时用传统 OpenGL 默认(但可以配置 reversed-Z)。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏渲染的深度相关技术:

**1. 基础深度测试**:今天的核心。

**2. 深度写入**:画物体时是否更新 depth buffer。透明物体通常 `depth_write = false`(否则挡住后面)。

**3. 深度预处理(z-prepass)**:先只画深度(不画颜色),再画颜色。减少 fragment shader 调用(被深度 cull 的像素不调 shader)。

**4. 阴影映射(shadow mapping)**:从光源视角渲染深度,得到"shadow map"。主渲染时检查某点在 shadow map 里的深度,判断是否在阴影里。

**5. 反射(reflection)**:类似阴影,从镜子视角渲染深度 + 颜色。

**6. 顺序无关透明(OIT)**:透明物体不深度测试,而是收集所有层次,事后合成。复杂但正确。

### 3.2 · 图形学视角

GPU 渲染 pipeline 的深度阶段:

```
Vertex Shader → Clipping → Perspective Divide → Viewport → Rasterizer
                                                                  ↓
                                                              Fragment Shader
                                                                  ↓
                                                            Depth Test (early-z)
                                                                  ↓
                                                              Depth Write
                                                                  ↓
                                                              Color Write
```

**Early-Z**(early depth test):在 fragment shader 之前做深度测试。如果深度测试失败,跳过 fragment shader,节省大量计算。条件:fragment shader 不修改深度(`gl_FragDepth` 未写)。

**Late-Z**:fragment shader 之后做深度测试。当 shader 修改深度时必须用 late-z。

现代 GPU 都有 early-z 优化。

### 3.3 · Linux 系统编程视角

Linux 内核也有"depth"概念:

- **进程优先级**(nice):`-20 ~ 19`,低 nice 高优先级
- **路由 metric**:多路由时选 metric 低的
- **dependency depth**:`systemd-analyze critical-chain` 显示启动依赖深度

都是"多个候选选最优"的变体,和 depth buffer 同构。

### 3.4 · Rust 生态视角

Rust 实现软渲染 depth buffer:

```rust
struct Framebuffer {
    color: Vec<u32>,    // WIDTH * HEIGHT
    depth: Vec<f32>,    // WIDTH * HEIGHT,初始无穷大
}

impl Framebuffer {
    fn new(w: usize, h: usize) -> Self {
        Self {
            color: vec![0; w * h],
            depth: vec![f32::INFINITY; w * h],
        }
    }

    fn draw_pixel(&mut self, x: usize, y: usize, z: f32, color: u32) {
        let idx = y * self.width + x;
        if z < self.depth[idx] {
            self.depth[idx] = z;
            self.color[idx] = color;
        }
    }
}
```

## 5 · 对照与变奏

### 不同隐藏面消除算法

**1. Backface culling**(背面剔除):不画背对相机的三角形。优化,但不解决"两个正面三角形谁前"。

**2. Painter's**:按"远→近"顺序画。简单,排序复杂场景困难。

**3. BSP tree**(Binary Space Partitioning):预计算空间分割,Doom / Quake 用。复杂但精确。

**4. Depth buffer**:今天的主题。GPU 标准。

**5. Ray tracing**:对每像素发射光线,找最近交点。慢但精确,光线追踪渲染器用。

### 深度的不同表示

- **view space z**(线性):`z ∈ [near, far]`,线性
- **NDC z**(归一化):`z ∈ [-1, 1]` 或 `[0, 1]`
- **window z**(depth buffer 值):`z ∈ [0, 2^B - 1]`(B = depth buffer 位深,16/24/32)

转换:`window_z = (NDC_z + 1) / 2 * (2^B - 1)`。

### 历史演化

- **1974**:depth buffer 概念提出(Evans & Sutherland)
- **1980s**:工作站有硬件 depth buffer
- **1990s**:消费级 GPU 出现(3dfx Voodoo),depth buffer 普及
- **2000s**:24 位 depth + 8 位 stencil 标配
- **2010s**:floating-point depth + reversed-Z 普及
- **2020s**:variable rate shading + 深度感知优化

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 depth buffer 比画家算法好?具体说出 3 个场景画家算法失败但 depth buffer 正确。

**参考解答**:

3 个场景:

1. **三角形互相穿插**:A 的一部分在 B 前,B 的一部分在 A 前。无法全局排序。depth buffer 每像素独立判断,正确。
2. **凹多边形**:自相交多边形,部分挡自己。画家算法要分裂多边形,depth buffer 直接画。
3. **动态场景**:每帧重新排序所有三角形成本高,而且顺序可能跳变导致闪烁。depth buffer 顺序无关,稳定。

### Lv2 · 动手实践

**题**:CPU 软渲染实现 depth buffer。两个三角形互相穿插,验证 depth buffer 正确(画家算法失败)。

完成标准:`cargo run` 打印像素,看到两个三角形正确穿插显示。

**参考解答**:

```rust
const W: usize = 40;
const H: usize = 20;

struct Framebuffer {
    color: Vec<char>,
    depth: Vec<f32>,
}

impl Framebuffer {
    fn new() -> Self {
        Self {
            color: vec![' '; W * H],
            depth: vec![f32::INFINITY; W * H],
        }
    }

    fn draw_pixel(&mut self, x: usize, y: usize, z: f32, c: char) {
        if x >= W || y >= H { return; }
        let idx = y * W + x;
        if z < self.depth[idx] {
            self.depth[idx] = z;
            self.color[idx] = c;
        }
    }

    fn draw_line_depth(&mut self, x0: f32, y0: f32, z0: f32, x1: f32, y1: f32, z1: f32, c: char) {
        let steps = 50;
        for i in 0..=steps {
            let t = i as f32 / steps as f32;
            let x = x0 + (x1 - x0) * t;
            let y = y0 + (y1 - y0) * t;
            let z = z0 + (z1 - z0) * t;
            self.draw_pixel(x as usize, y as usize, z, c);
        }
    }

    fn display(&self) {
        for y in 0..H {
            let row: String = (0..W).map(|x| self.color[y * W + x]).collect();
            println!("{}", row);
        }
    }
}

fn main() {
    let mut fb = Framebuffer::new();

    // 三角形 A:深度从 0.1 到 0.9
    fb.draw_line_depth(2.0, 2.0, 0.1, 38.0, 18.0, 0.9, 'A');
    fb.draw_line_depth(38.0, 2.0, 0.9, 2.0, 18.0, 0.1, 'A');

    // 三角形 B:深度从 0.9 到 0.1(反向)
    fb.draw_line_depth(2.0, 2.0, 0.9, 38.0, 18.0, 0.1, 'B');
    fb.draw_line_depth(38.0, 2.0, 0.1, 2.0, 18.0, 0.9, 'B');

    fb.display();
    println!("\nWith depth buffer: both triangles correctly interleave.");
}
```

**预期**:屏幕上看到 'A' 和 'B' 交替出现(因为深度交叉),正确穿插。

**关键解释**:
- 每像素独立判断深度,无全局排序
- draw_line_depth 在像素 (x, y) 算出该线段在此点的深度 z
- depth 测试:z < current ? 覆盖 : 不画

### 完整可跑示例

```rust
const W: usize = 60;
const H: usize = 30;

struct Framebuffer {
    width: usize,
    color: Vec<char>,
    depth: Vec<f32>,
}

impl Framebuffer {
    fn new(w: usize, h: usize) -> Self {
        Self {
            width: w,
            color: vec![' '; w * h],
            depth: vec![f32::INFINITY; w * h],
        }
    }

    fn draw_pixel(&mut self, x: isize, y: isize, z: f32, c: char) {
        if x < 0 || y < 0 || x as usize >= self.width { return; }
        let idx = y as usize * self.width + x as usize;
        if idx >= self.color.len() { return; }
        if z < self.depth[idx] {
            self.depth[idx] = z;
            self.color[idx] = c;
        }
    }

    fn draw_filled_triangle(
        &mut self,
        v0: (f32, f32, f32),
        v1: (f32, f32, f32),
        v2: (f32, f32, f32),
        c: char,
    ) {
        // 找 bbox
        let min_x = v0.0.min(v1.0).min(v2.0).floor() as isize;
        let max_x = v0.0.max(v1.0).max(v2.0).ceil() as isize;
        let min_y = v0.1.min(v1.1).min(v2.1).floor() as isize;
        let max_y = v0.1.max(v1.1).max(v2.1).ceil() as isize;

        // 重心坐标插值
        let denom = (v1.1 - v2.1) * (v0.0 - v2.0) + (v2.0 - v1.0) * (v0.1 - v2.1);
        if denom.abs() < 1e-6 { return; }  // 退化三角形

        for y in min_y..=max_y {
            for x in min_x..=max_x {
                let px = x as f32 + 0.5;
                let py = y as f32 + 0.5;
                let a = ((v1.1 - v2.1) * (px - v2.0) + (v2.0 - v1.0) * (py - v2.1)) / denom;
                let b = ((v2.1 - v0.1) * (px - v2.0) + (v0.0 - v2.0) * (py - v2.1)) / denom;
                let g = 1.0 - a - b;

                if a >= 0.0 && b >= 0.0 && g >= 0.0 {
                    // 重心坐标插值深度(注意:不是透视正确,简化教学)
                    let z = a * v0.2 + b * v1.2 + g * v2.2;
                    self.draw_pixel(x, y, z, c);
                }
            }
        }
    }

    fn display(&self) {
        for y in 0..H {
            let row: String = (0..self.width).map(|x| self.color[y * self.width + x]).collect();
            println!("{}", row);
        }
    }
}

fn main() {
    let mut fb = Framebuffer::new(W, H);

    // 背景大三角形(远,深度 0.9)
    fb.draw_filled_triangle(
        (5.0, 5.0, 0.9),
        (55.0, 5.0, 0.9),
        (30.0, 25.0, 0.9),
        '.',
    );

    // 前景小三角形(近,深度 0.3)
    fb.draw_filled_triangle(
        (20.0, 10.0, 0.3),
        (40.0, 10.0, 0.3),
        (30.0, 22.0, 0.3),
        '#',
    );

    // 第三个三角形(穿插,深度 0.6)
    fb.draw_filled_triangle(
        (10.0, 15.0, 0.6),
        (50.0, 15.0, 0.6),
        (30.0, 5.0, 0.6),
        'o',
    );

    fb.display();
}
```

**关键解释**:
- 重心坐标 `(a, b, g)` 必须都 >= 0 才在三角形内
- 深度 `z = a*v0.z + b*v1.z + g*v2.z`(教学简化,生产用 1/z)
- depth 测试在每个 draw_pixel 内自动做

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
