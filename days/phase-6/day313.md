
# Day 313 · 回到 Z 层工作

> 昨天 Casey 把 SortKey 推到跨实体级别,今天回到一个老话题:**Z 层**——把游戏世界切成"地板 / 装饰 / 角色 / UI"几个层,每个层独立渲染再合成。这是 2D 游戏里"分层渲染"的起点。

## 0 · 为什么要有这一天

到目前为止,你的渲染器是一个"扁平"的模型——所有 entity 在同一个 SortKey 空间排序,然后一次性画到屏幕上。这种方式简单,但在大型场景里会暴露问题:

1. **背景滚动速度不同**(视差,parallax):远山慢移、近景快移,你想要"远山"独立画在"背景层",不和角色混在一起。如果都混在扁平排序里,需要给远山手动设 SortKey=BACK,但这是 hack 不是设计。
2. **后处理**(post-process):你想加"全屏模糊"或"色调映射",效果只作用于"游戏层",不影响 UI 层。扁平模型做不到——所有东西都画在一个 framebuffer,处理时一锅炖。
3. **离屏渲染**:有些层(比如光照层)先画到离屏 framebuffer,再合成到主屏幕。这需要"多 framebuffer"概念,Day 316 会引入。

业界的标准做法是 **layer-based rendering**(分层渲染):把游戏世界分成几个**渲染层(render layer)**,每层独立排序、独立画、独立后处理,最后合成。这是 Unity / Godot / Phaser 等所有主流 2D 引擎的基础架构。

今天的 Casey 工作:**回到 Z 层话题,把它和昨天的 SortKey 结合**。具体说,SortKey 的最高几位编码"层 ID",比如:

- 高 4 bit:层 ID(0=背景,1=装饰,2=游戏角色,3=UI)
- 中 16 bit:Y 编码
- 低 12 bit:sprite 局部偏移

这样既保留了"层"的离散感(背景永远是背景),又保留了 SortKey 的精细排序(层内按 Y)。

更深一层的动机:**为后面多渲染目标铺垫**。Day 316 Casey 会引入"多个软件渲染目标"——每个层画到独立的 framebuffer,然后合成。今天先把"层"的概念在 SortKey 里表达出来,Day 316 才能把层映射到不同 framebuffer。

心理锚点:今天之后你的引擎支持"分层渲染"的语义层——美术可以指定"这个 entity 属于背景层还是游戏层",渲染器按层分组。这是从"扁平 painter's algorithm"到"分层 + 合成"的关键过渡。

## 1 · Casey 今天做了什么(HH 脂络)

Casey 今天打开 `handmade_render.cpp`,做了一次"概念整合"。原来的代码里 SortKey 是单层的(只编码 Y 和 sprite_offset),今天他改成"多层"——把最高几位预留给"层 ID"。

具体动作:

1. 定义枚举 `RenderLayer { Background = 0, Game = 1, Foreground = 2, UI = 3, ... }`
2. 修改 `PushBitmap` 签名,增加 `Layer` 参数
3. 修改 SortKey 编码:把 Layer 放最高 4 bit,把原 SortKey 位移 4 位腾出空间

Casey 在视频里详细讨论了一个设计选择:**Layer 应该是 enum 还是数字**。最终选择 enum,因为:

- 类型安全(传错 layer 编译失败,不是运行时 bug)
- 自文档化(`RenderLayer::Background` 比 `0` 清晰)
- 编译器能警告漏处理(用 `match` 强制 exhaustive)

但 Casey 也指出,enum 在性能关键路径上有微小开销(类型转换),如果用 `repr(u8)` 标记 enum 让它在内存里就是 u8,开销消失。

另一个细节:**Layer 之间的"过渡区域"**。比如玩家从游戏层跳到背景层(用门传送到远处),玩家在动画过程中应该属于哪层?Casey 选择"硬切"——传送到新位置时立刻切换 layer,不做渐变。这种简化是为了避免复杂的"插值排序"问题。

## 2 · 心智模型

### 类比:Photoshop 的图层

把游戏世界想象成 Photoshop 的一张图,里面有多个图层:

```
[Layer 3: UI]        ← 最上层
[Layer 2: Game]      ← 角色和怪物
[Layer 1: Foreground]← 草丛、装饰
[Layer 0: Background]← 远山、天空
```

Photoshop 里每个图层独立编辑,你可以"单独打开/关闭"某个图层,可以单独调整某个图层的不透明度。游戏引擎的"分层渲染"完全一样——每层独立处理,最后合成。

和"扁平 SortKey"的差别:**分层是离散的**(只有 4 个值),**SortKey 是连续的**(2^32 个值)。分层用于"粗分类"(背景 vs 角色),SortKey 用于"细排序"(同层的多个角色按 Y 排)。

### 严谨原理:Layer + SortKey 编码

把 Layer 编码进 SortKey 的最高位:

```
SortKey (32 bit):
┌─────────┬───────────────────┬──────────────┐
│ Layer   │ Y encoded         │ sprite_idx   │
│ (4 bit) │ (16 bit)          │ (12 bit)     │
└─────────┴───────────────────┴──────────────┘
  高位 ←─────────────────────────────────────→ 低位
```

- **Layer(4 bit)**:16 个层(0-15)。0 = 最底,15 = 最顶
- **Y encoded(16 bit)**:Y 坐标编码,层内排序
- **sprite_idx(12 bit)**:同 entity 的 sprite 局部序号

举例:背景层(Layer=0)的一个远山,Y=200,sprite_idx=0,它的 SortKey 是 `0x0000C350`(0 << 28 | Y_enc << 12 | 0)。游戏层(Layer=1)的玩家,Y=0,sprite_idx=0,SortKey 是 `0x10000000`(1 << 28 | ... )。比较时 `0x10000000 > 0x0000C350`,玩家排在远山后面(后画,即屏幕前面)。这就是"层 + Y"统一排序。

### 为什么 Layer 放最高位

考虑三个东西:背景远山(Layer=0)、玩家(Layer=1)、UI 鼠标(Layer=3)。它们的 Y 都不重要——背景永远在最后,UI 永远在最前。如果 Layer 不在最高位,UI 的 Y 编码可能比玩家小,导致 UI 被画在玩家后面。

Layer 放最高位保证:**层之间是绝对优先级**。无论 Y 和 sprite_idx 怎么变,UI 层(3)永远大于 Game 层(1),所以 UI 永远在最前。这是"粗分类 > 细排序"的设计哲学。

### 离屏渲染的预告

```
当前(扁平):           未来(分层 + 离屏):
┌────────────┐         ┌────┐ ┌────┐ ┌────┐
│            │   →    │ BG │ │Game│ │ UI │
│ 一锅炖     │         └────┘ └────┘ └────┘
│            │           │      │      │
└────────────┘           └──────┼──────┘
                                ↓
                          ┌──────────┐
                          │ Composite│ → 屏幕
                          └──────────┘
```

今天 Casey 还没切到离屏,只是把 Layer 在 SortKey 里编码出来。Day 316 才会真正做"每层独立 framebuffer"。但今天的设计已经为那时铺好了路——只要把"Layer N 的 entity 画到 framebuffer N",数据结构完全不变。

### Rust 表达

```rust
#[repr(u8)]
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
enum RenderLayer {
    Background = 0,    // 远景
    Tile = 1,          // 地砖
    Game = 2,          // 游戏角色
    Foreground = 3,    // 前景装饰
    Particles = 4,     // 粒子
    UI = 5,            // UI
}

fn encode_sort_key(layer: RenderLayer, y: f32, sprite_idx: u16) -> u32 {
    let layer_bits = (layer as u32) << 28;           // 高 4 bit
    let y_enc = ((y + 500.0).max(0.0) * 65.53) as u32 & 0xFFFF;  // 16 bit
    let y_bits = y_enc << 12;
    let sprite_bits = (sprite_idx as u32) & 0xFFF;   // 低 12 bit
    layer_bits | y_bits | sprite_bits
}
```

`#[repr(u8)]` 让 enum 在内存里就是 1 字节(没有判别位开销),`as u32` 转换直接拿值。`& 0xFFFF` / `& 0xFFF` 是位掩码,防止溢出污染其他字段。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

主流 2D 引擎的分层:

| 引擎 | 层概念 | 实现 |
|---|---|---|
| Unity | SortingLayer(字符串) | 字符串映射到 int,排序时按 int |
| Godot | CanvasLayer(node) | 每层独立 Canvas 节点,先画低层 |
| Phaser | Scene + depth | 多 scene 分层,scene 内用 depth |
| Casey HH | Layer enum + SortKey | 今天的设计 |

Unity 用字符串做层名的好处是**编辑器友好**(美术在 inspector 选 "Background"),坏处是**字符串比较慢**(虽然只在初始化时映射到 int,运行时无开销)。Casey 用 enum 是**程序员友好**,但美术在编辑器里看到的是数字(0,1,2),需要文档解释。

游戏行业共识:**4-8 个层足够大多数游戏**。再多就该用 SortKey 的精细排序而非堆层。Casey 的设计 4 bit = 16 层,留出空间但不滥用。

分层的另一个用处:**热加载**。背景层的纹理可以"延迟加载"(玩家进入新区域才加载),游戏层立刻加载,UI 层永远在内存。这种"按层分级加载"在大世界游戏(GTA、塞尔达)里是标配。

### 3.2 · 🎨 图形学视角

图形学里"分层"对应的概念是 **render target**(渲染目标)。每个 render target 是一块独立的 framebuffer,渲染管线可以把不同东西画到不同 target,最后合成(composite)。

现代 GPU 支持的 **Multiple Render Targets(MRT)** 技术允许 shader 一次 draw call 同时写到 8 个 render target。这是 deferred shading(延迟着色)的基础——把位置、法线、颜色分别写到 4 个 G-buffer,最后用光照 pass 合成。Casey 在 Day 321 会做 OpenGL 多渲染目标。

分层的另一个图形学概念是 **compositing**(合成)。把多个 layer 合成到屏幕的算法:

- **Over operator**:`C_out = C_src * alpha + C_dst * (1 - alpha)` —— 标准 alpha blending
- **Add operator**:`C_out = C_src + C_dst` —— 加法混合,常用于发光效果
- **Multiply**:`C_out = C_src * C_dst` —— 乘法混合,常用于阴影

Casey 现在只用 Over,Day 317 会扩展支持多 target 的混合。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上"分层"对应的概念是 **stackable filesystem**(可堆叠文件系统):

- **overlayfs**:把"upper"和"lower"两个文件系统叠加,upper 是可写的,lower 是只读的(类似游戏层:UI 上层可改,背景下层只读)
- **unionfs / aufs**:类似 overlayfs,把多个目录"层叠"成单一视图

这些文件系统的"层级合并"和今天的"渲染层合成"思路一致——多个层独立维护,需要时合并成一个统一视图。Linux 用这个机制做 Docker 镜像(每层一个文件系统变更),游戏引擎用它做渲染分层。

另一个 Linux 概念是 **Compositor**(合成器)——Wayland / X11 的合成器把多个窗口合成到屏幕,和今天讲的渲染层合成完全等价。Wayland 用 libweston 或 mutter(GNOME),X11 用 picom 之类的合成器。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 Layer 的最佳实践:

```rust
/// 用 repr(u8) 让 enum 内存布局就是 u8
#[repr(u8)]
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
enum Layer {
    Background = 0,
    Game = 1,
    Foreground = 2,
    UI = 3,
}

impl Layer {
    /// 转 SortKey 高位
    fn to_high_bits(self) -> u32 {
        (self as u32) << 28
    }
}

struct RenderEntry {
    layer: Layer,
    sort_key: u32,
    // ...
}

// 排序时,SortKey 已经包含了 Layer,直接 sort_by_key 就行
entries.sort_by_key(|e| e.sort_key);
```

`#[repr(u8)]` 是关键——没有这个,Rust 的 enum 可能用 4 字节(取决于平台和 variant 数)。`#[repr(u8)]` 强制 1 字节,和 C 的 `uint8_t` 一致,FFI 友好。

Rust 生态里 `bevy_render` 用 `RenderPhase` 和 `RenderLayers` 组件表达分层,设计思路和今天类似但更通用——支持任意 mask 而不是固定 enum。

## 5 · 对照与变奏

### 历史演化

- **1980s 街机**:几乎都是单层,因为硬件只有一个 framebuffer。
- **1990s 16-bit**:Super Nintendo 引入"背景层 + 精灵层",硬件支持 4 个 BG 层。这是游戏机分层渲染的起点。
- **2000s PS2/GC**:硬件支持多 framebuffer,游戏开始用离屏渲染做光晕、阴影。
- **2010s GPU 通用化**:分层移到 shader,游戏代码层面只声明"我要画到 layer N"。
- **2020s 现代**:Unity URP / Godot 3.x 都用"Render Pipeline"抽象,分层是 pipeline 的一环。

### 工业级 vs 教学版

| 特性 | 教学版(今天) | 工业版(Unity URP) |
|---|---|---|
| 层数 | 16 | 32 |
| 层间过渡 | 硬切 | 可交叉 |
| 后处理 | 无 | 每层独立 |
| 性能 | 单 framebuffer | 多 framebuffer |
| 编辑器集成 | hot-reload 字段 | Unity Inspector |

工业级最复杂的部分是"层间过渡"——比如玩家从前景走到背景,玩家精灵的"层"会平滑过渡,不是硬切。Casey 简化为硬切,因为 HH 不需要这种复杂效果。

### 跨语言变体

| 引擎 | 层表达 |
|---|---|
| Casey HH(C) | enum + bit shift |
| Unity(C#) | string SortingLayer + int OrderInLayer |
| Godot(GDScript) | CanvasLayer node |
| Unreal(C++) | `DepthPriority` + render pass |
| Bevy(Rust) | `RenderLayers` component(BitFlags) |

Bevy 的设计有意思——它用 **BitFlags** 表达"一个 entity 可以同时在多个 layer"。比如一个发光特效既属于 Game 层又属于 Effect 层,渲染时两个层都画。比 Casey 的"一个 entity 一个 layer"更灵活。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 选择把 Layer 放 SortKey 的最高 4 bit,而不是单独维护一个"层列表"。这两种设计有什么差别?给出至少 2 个理由。

**参考解答**:

1. **统一排序空间**:Layer 在 SortKey 里,所有 entity 一个 `sort_by_key` 就完成排序。如果层独立,需要先按层分组,每层单独排序,再合并——多次排序 + 合并,慢且复杂。
2. **跨层排序可能**:某些特殊场景需要"UI 元素和 Game 角色互相穿插"(比如 hover tooltip 跟随角色)。如果层绝对分离,做不到。Layer 在 SortKey 里可以手动指定 SortKey 跨层。
3. **缓存友好**:所有 entry 在一个 Vec,连续内存,排序时 cache 命中率高。多列表分散,cache miss 多。

代价:Layer 数量受限于 SortKey 的位数(4 bit = 16 层)。

### Lv2 · 动手实践

**题**:在 Rust 里实现一个"分层 + SortKey"系统,要求:

- `Layer` enum 有 4 个值(Background=0, Game=1, Foreground=2, UI=3)
- SortKey 用最高 4 bit 编码 Layer,中 16 bit Y,低 12 bit sprite_idx
- 创建 5 个 entity 分布在不同层,排序后输出,验证层间绝对优先

**参考解答**:

```rust
#[repr(u8)]
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
enum Layer {
    Background = 0,
    Game = 1,
    Foreground = 2,
    UI = 3,
}

fn encode(layer: Layer, y: f32, sprite_idx: u16) -> u32 {
    let layer_bits = (layer as u32) << 28;
    // Y ∈ [-500, 500] → [0, 65535]
    let y_enc = (((y + 500.0).max(0.0).min(1000.0)) * 65.535) as u32 & 0xFFFF;
    let y_bits = y_enc << 12;
    let sprite_bits = (sprite_idx as u32) & 0xFFF;
    layer_bits | y_bits | sprite_bits
}

#[derive(Debug)]
struct Entry {
    layer: Layer,
    y: f32,
    name: &'static str,
    sort_key: u32,
}

fn main() {
    let mut entries = vec![
        Entry { layer: Layer::UI,         y: 999.0,  name: "Mouse",     sort_key: encode(Layer::UI, 999.0, 0) },
        Entry { layer: Layer::Background, y: -999.0, name: "Mountain",  sort_key: encode(Layer::Background, -999.0, 0) },
        Entry { layer: Layer::Game,       y: 50.0,   name: "Player",    sort_key: encode(Layer::Game, 50.0, 0) },
        Entry { layer: Layer::Game,       y: 30.0,   name: "Enemy",     sort_key: encode(Layer::Game, 30.0, 0) },
        Entry { layer: Layer::Foreground, y: 999.0,  name: "Grass",     sort_key: encode(Layer::Foreground, 999.0, 0) },
    ];
    entries.sort_by_key(|e| e.sort_key);
    for e in &entries {
        println!("layer={:?} y={:7.1} name={:10} key={:#010x}",
                 e.layer, e.y, e.name, e.sort_key);
    }
}
```

预期输出顺序:`Mountain(BG) → Enemy(Game) → Player(Game) → Grass(FG) → Mouse(UI)`。注意 Mountain 虽然 Y=-999(最远)但属于 Background,Enemy 虽然 Y=30 但属于 Game,Layer 高位主导让 Background 永远在前(先画)。

- 高 4 bit:Track 类型(8 种,留余量)

### Rust:分层 + SortKey 完整可跑

```rust
// Cargo.toml: 无依赖
// src/main.rs

/// 渲染层。repr(u8) 让 enum 内存就是 1 字节。
#[repr(u8)]
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
enum Layer {
    Background = 0,
    Tile = 1,
    Game = 2,
    Foreground = 3,
    Particles = 4,
    UI = 5,
}

/// 全局 SortKey,用 newtype 防误用
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
struct SortKey(u32);

impl SortKey {
    /// 从 (layer, y, sprite_idx) 编码
    fn encode(layer: Layer, y: f32, sprite_idx: u16) -> Self {
        // 4 bit layer + 16 bit y + 12 bit sprite_idx = 32 bit
        let layer_bits = (layer as u32) << 28;
        let y_clamped = y.clamp(-500.0, 500.0);
        let y_enc = (((y_clamped + 500.0) / 1000.0) * 65535.0) as u32 & 0xFFFF;
        let y_bits = y_enc << 12;
        let sprite_bits = (sprite_idx as u32) & 0xFFF;
        SortKey(layer_bits | y_bits | sprite_bits)
    }
    
    /// 强制最前 / 最后
    const FRONT: Self = SortKey(u32::MAX);
    const BACK: Self = SortKey(0);
}

/// Entity 元数据
#[derive(Debug, Clone)]
struct Entity {
    layer: Layer,
    y: f32,
    name: &'static str,
    sprite_count: u16,
}

/// 渲染条目(展开 sprite 后)
#[derive(Debug, Clone)]
struct RenderEntry {
    sort_key: SortKey,
    layer: Layer,
    y: f32,
    sprite_idx: u16,
    entity_name: &'static str,
}

struct RenderGroup {
    entries: Vec<RenderEntry>,
}

impl RenderGroup {
    fn new() -> Self { Self { entries: Vec::new() } }
    
    fn push_entity(&mut self, e: &Entity) {
        for sprite_idx in 0..e.sprite_count {
            let key = SortKey::encode(e.layer, e.y, sprite_idx);
            self.entries.push(RenderEntry {
                sort_key: key,
                layer: e.layer,
                y: e.y,
                sprite_idx,
                entity_name: e.name,
            });
        }
    }
    
    fn render(&mut self) {
        // 稳定排序,同 key 保持 push 顺序
        self.entries.sort_by_key(|e| e.sort_key);
        println!("=== Layered render order ===");
        for (i, e) in self.entries.iter().enumerate() {
            println!("[{:2}] layer={:?} y={:7.1} sprite={} entity={:10} key={:#010x}",
                     i, e.layer, e.y, e.sprite_idx, e.entity_name, e.sort_key.0);
        }
    }
}

fn main() {
    let entities = vec![
        Entity { layer: Layer::Background, y: -500.0, name: "Mountain", sprite_count: 1 },
        Entity { layer: Layer::Background, y: -450.0, name: "Cloud",    sprite_count: 1 },
        Entity { layer: Layer::Tile,       y: 0.0,    name: "Floor",    sprite_count: 1 },
        Entity { layer: Layer::Game,       y: 50.0,   name: "Player",   sprite_count: 3 },  // 3 sprite(脚/身/头)
        Entity { layer: Layer::Game,       y: 60.0,   name: "Enemy",    sprite_count: 2 },
        Entity { layer: Layer::Foreground, y: 100.0,  name: "Grass",    sprite_count: 1 },
        Entity { layer: Layer::Particles,  y: 55.0,   name: "Spark",    sprite_count: 1 },
        Entity { layer: Layer::UI,         y: 499.0,  name: "Cursor",   sprite_count: 1 },
    ];
    
    let mut group = RenderGroup::new();
    for e in &entities {
        group.push_entity(e);
    }
    group.render();
}
```

**预期输出**(节选):

```

[ 0] layer=Background y= -500.0 sprite=0 entity=Mountain   key=0x00000000
[ 1] layer=Background y= -450.0 sprite=0 entity=Cloud      key=0x000b3300
[ 2] layer=Tile       y=   0.0 sprite=0 entity=Floor       key=0x18000000
[ 3] layer=Game       y=  50.0 sprite=0 entity=Player      key=0x281f4000
[ 4] layer=Game       y=  50.0 sprite=1 entity=Player      key=0x281f4001
[ 5] layer=Game       y=  50.0 sprite=2 entity=Player      key=0x281f4002
```

**Troubleshooting**:

- **Layer 编译后不是 1 字节** — 检查 `#[repr(u8)]` 是否漏写
- **SortKey 编码后层间顺序反** — 检查 Layer 值是否对应到 SortKey 顺序(BACKGROUND 应该最小,UI 最大)

## 10 · 深度补充:工程视角

Layer 系统的跨引擎深度对比:Unity SortingLayer 字符串映射到 int 排序;Godot 用 z_index + y_sort_enabled 双重配置;Casey 用 enum + bit shift 编码进 SortKey 高位。Casey 方案的优势是 cache 友好(单一 uint32 比较),劣势是层名难记(0,1,2 数字)。工业级引擎通常给美术 GUI,Casey 给程序员。
