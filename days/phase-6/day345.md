
# Day 345 · 为下溢检测保护内存页

> 利用 OS 的虚拟内存机制(页保护)给 arena 加一道"安全哨兵"——任何越界写超出当前块边界的行为立刻触发 SIGSEGV,而不是悄悄写坏邻近数据让你两小时后才发现。这是把 OS 当成"免费调试器"的高级技巧。

## 0 · 为什么要有这一天

到目前为止你的 arena 都有一个潜在 bug:**越界写不会立刻报错**。考虑:

```rust
let buf: &mut [u8] = arena.alloc_slice(100);  // 分配 100 字节
buf[200] = 0xff;  // 越界写!但是……
```

在普通 arena 里,这个 `buf[200] = 0xff` 会**默默写坏同一 arena 内 100 字节后的另一个对象**。游戏不会立刻崩,你可能要跑几分钟后才看到诡异行为:某 entity 莫名其妙位置错乱,某 sprite 颜色变红,某物理对象速度异常。

调试这种 bug 是噩梦——你需要二分代码、加 printf、装 valgrind,可能花一整天。

操作系统提供了更优雅的方案:**页保护**(page protection)。Linux 的 `mprotect` 系统调用可以让某段虚拟地址变成"只读"或"不可访问",任何写操作立刻 SIGSEGV。我们可以利用这个机制给 arena 加"哨兵页"——在两个相邻块之间放一页不可访问的内存,任何越界写立刻被 OS 抓到。

这个技巧在 90 年代的游戏机引擎里就有,在 PC 上由于 `mprotect` 的开销和粒度限制(页大小 4 KB)用得较少。但 Casey 在 HH 里专门做了这一集——因为 debug build 下保证"越界立刻 crash"是引擎可维护性的关键。

今天的核心:**给 arena 的每个块末尾加一个 guard page**(哨兵页),任何越界写立刻 SIGSEGV,而不是悄悄写坏数据。

心理锚点:今天之后你 `cargo run` 时一旦写越界,游戏立刻 crash 给你一个清晰的 backtrace,而不是诡异行为两小时。这是从"教学项目"到"产品级引擎"的另一个关键步——debug build 必须捕获内存错误。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 在 Win32 平台层调用 `VirtualAlloc` 时多申请一页(`PAGE_GUARD` 标志),让越界访问触发异常。Linux 对应的系统调用是 `mmap` + `mprotect`,核心代码大致:

```c
// 申请 (block_size + page_size) 字节,前 block_size 可写,最后 page_size 不可访问
size_t total = block_size + PAGE_SIZE;
uint8_t *mem = mmap(NULL, total, PROT_READ | PROT_WRITE,
                    MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
// 把最后 PAGE_SIZE 设为 PROT_NONE
mprotect(mem + block_size, PAGE_SIZE, PROT_NONE);
arena->base = mem;
arena->size = block_size;  // 注意:size 不包括 guard page
```

任何 `arena->base + arena->size` 之后的写都触发 SIGSEGV。OS 当场把进程杀掉,gdb 里能看到精确的越界点。

Casey 在视频里强调几个细节:

1. **guard page 算在 arena 总占用里**:统计内存时要算上,不能假装没占用
2. **每次 mmap 多一页,块数多了开销累积**:1 MB 块 + 4 KB guard ≈ 0.4% 开销,可接受
3. **release build 可以关掉**:为了性能,正式版用 `#ifdef INTERNAL` 包起来
4. **页对齐**:guard page 必须 4 KB 对齐,所以 block 内部也得 4 KB 对齐(`align` 参数 ≥ 12)

Casey 还讨论了**下溢检测**(underflow detection):不是越界往后写,而是往前写——`buf[-1] = 0xff`。这个稍微复杂,要在块**开头**也放 guard page。Casey 选择只做上溢(over*flow*),因为下溢在 arena 里少见(指针往前推不合法),不值得。

## 2 · 心智模型

### 类比:商场防火门

把 arena 想象成商场,每个 block 是一个店铺。普通 arena 是"店铺之间没有隔断",一个小偷从 A 店越界到 B 店无人发现。

加 guard page = "店铺之间装防火门"——撞开门立刻报警(报警 = SIGSEGV)。 商场整体仍然连通(都在 arena 内),但跨店铺的行为立刻被发现。

防火门的代价:每家店多一扇门的空间(4 KB guard),开门关门慢一点(`mmap` 调用多一点)。但安全收益巨大。

### 严谨原理:虚拟内存保护

Linux 的虚拟内存系统给每个进程一个独立的虚拟地址空间(64 位下 48 位有效 = 256 TB)。虚拟地址通过页表(page table)映射到物理地址。每一页(page,通常 4 KB)有自己的保护标志:

- `PROT_READ`:可读
- `PROT_WRITE`:可写
- `PROT_EXEC`:可执行
- `PROT_NONE`:不可访问(任何访问触发 SIGSEGV)

`mprotect(addr, len, prot)` 系统调用修改一段虚拟地址的保护标志:

```c
#include <sys/mman.h>
int mprotect(void *addr, size_t len, int prot);
```

- `addr` 必须**页对齐**(4 KB 倍数)
- `len` 会向上取整到页倍数
- `prot` 是上面四个的位或
- 返回 0 成功,-1 失败(`errno` 看错误)

任何对 `PROT_NONE` 区域的访问,CPU 的 MMU(memory management unit)硬件立刻触发 page fault,内核转成 SIGSEGV 信号发给进程——默认行为是 kill 进程 + core dump。

这套机制在硬件级别,几乎零开销(只有第一次访问触发的 fault 有微秒级开销,但正常访问走 cache 不触发)。

### 页对齐

页(page)是 OS 管理内存的最小单位。Linux x86_64 默认页大小 4 KB(4096 字节)。所有 `mmap` / `mprotect` 操作必须以页为单位。

```bash
getconf PAGE_SIZE
# 输出 4096
```

所谓"页对齐"指地址是 4096 的倍数。`mprotect` 强制要求 addr 页对齐,否则返回 EINVAL。

如果你的 arena 块大小是 1 MB(0x100000),块内偏移任意,但块的**起始地址**必须页对齐——`mmap` 默认就返回页对齐的地址,所以不用额外处理。

### 实现:Rust 版

```rust
use std::io;

const PAGE_SIZE: usize = 4096;

extern "C" {
    fn mmap(addr: *mut u8, len: usize, prot: i32, flags: i32,
            fd: i32, offset: i64) -> *mut u8;
    fn mprotect(addr: *mut u8, len: usize, prot: i32) -> i32;
    fn munmap(addr: *mut u8, len: usize) -> i32;
}

const PROT_READ: i32 = 1;
const PROT_WRITE: i32 = 2;
const PROT_NONE: i32 = 0;
const MAP_PRIVATE: i32 = 0x2;
const MAP_ANONYMOUS: i32 = 0x20;
const MAP_FAILED: *mut u8 = !0usize as *mut u8;

fn alloc_block_with_guard(size: usize) -> io::Result<*mut u8> {
    let total = size + PAGE_SIZE;
    unsafe {
        let base = mmap(std::ptr::null_mut(), total,
                        PROT_READ | PROT_WRITE,
                        MAP_PRIVATE | MAP_ANONYMOUS,
                        -1, 0);
        if base == MAP_FAILED {
            return Err(io::Error::last_os_error());
        }
        // 末尾 PAGE_SIZE 设为 PROT_NONE
        let guard_addr = base.add(size);
        // guard_addr 必须页对齐——size 是 1 MB(已对齐),base 也对齐,所以 guard 也对齐
        if mprotect(guard_addr, PAGE_SIZE, PROT_NONE) != 0 {
            munmap(base, total);
            return Err(io::Error::last_os_error());
        }
        Ok(base)
    }
}
```

注意 mmap 的签名在 Linux 上 `addr` 是 `void*`(等价 `*mut u8`),`offset` 是 `off_t`(等价 `i64`)。`-1` 的 fd 表示"匿名映射"(无文件后端)。

### 信号处理:SIGSEGV 怎么变成有用信息

默认 SIGSEGV 杀进程。但你想知道**哪个 arena 哪个偏移越界**。可以装一个信号处理函数:

```rust
use std::ffi::c_int;

extern "C" {
    fn signal(signum: c_int, handler: usize) -> usize;
    fn write(fd: c_int, buf: *const u8, count: usize) -> isize;
}

extern "C" fn segfault_handler(_sig: c_int) {
    let msg = b"SEGFAULT: arena guard page violated\n";
    unsafe {
        write(2, msg.as_ptr(), msg.len());  // stderr
        std::process::abort();
    }
}

fn install_handler() {
    unsafe { signal(11 /* SIGSEGV */, segfault_handler as usize); }
}
```

不过更专业的做法是用 `sigaction` 配合 `SA_SIGINFO`,处理函数能拿到触发 fault 的精确地址(`siginfo_t.si_addr`)。然后你用 arena 的 base 范围对照,定位是哪个 arena。

### 性能开销

guard page 的开销:

1. **内存**:每个块多 4 KB。100 个块多 400 KB,可接受
2. **mmap 调用**:每次 arena 增长多一次 `mprotect` 调用,几微秒,只在增长时
3. **运行时**:零——MMU 是硬件,正常访问走 cache 不经过 OS
4. **TLB 压力**:每块多一条 page table entry,TLB miss 可能增加 0.1-1%。在 arena 块大小 ≥ 1 MB 时不可见

总体:**debug build 开启,release build 关闭**,这是产业共识。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

主流引擎都用 guard page:

- **Unreal**:`GMalloc` 的 `FMallocBinned2` 有 guard page 模式(debug build)
- **Unity**:Mono runtime 的 malloc,有 `MEMORY_GUARDS` 宏
- **DOOM 3**:`idHeap` 在 debug 模式下每个 block 前后都有 guard
- **Chrome / Firefox**:JavaScript 引擎的 GC heap 用 guard page 保护

业界共识:**debug build 必须有 guard page,release build 关闭以省内存**。这相当于"测试时用保险带,正式跑去掉"。

#### Address Sanitizer 对比

现代 C/C++ 有 ASan(Address Sanitizer),编译器插桩检测越界。Rust 有 `-Zsanitizer=address`,在 nightly。ASan 比 guard page 更细粒度(检测单字节越界),但慢 2-3 倍。

guard page 是 ASan 的"轻量级版本":只检测页级越界(4 KB 粒度),但运行时几乎零开销。

| 方案 | 粒度 | 开销 | 复杂度 |
|---|---|---|---|
| guard page | 4 KB | 几乎零 | 低 |
| ASan | 字节 | 2-3x | 高(编译器支持) |
| valgrind | 字节 | 20-50x | 高(运行时) |
| electric-fence | 4 KB | 几乎零 | 低(库) |

Casey 用 guard page 是"手动 electric-fence"——不依赖外部库,跨平台可控。

### 3.2 · 🐧 Linux 系统编程视角

Linux 的内存保护 API:

- `mmap` 创建映射时指定 `prot`
- `mprotect` 修改已有映射的 prot
- `mlock` 锁定内存(防止 swap,低延迟场景)
- `mincore` 查询页是否在物理内存

#### PROT_NONE 的隐藏用法

`PROT_NONE` 除了做 guard page,还有其他用途:

1. **Stack guard**:线程栈末尾的 guard page,栈溢出时触发(Java 默认有,Linux pthread 默认有)
2. **Lazy commit**:Windows 用 `MEM_RESERVE` 先占虚拟地址,需要时再 `MEM_COMMIT`。Linux 类似用 `PROT_NONE` mmap + 后续 `mprotect`
3. **Memory-mapped files**:某些场景把文件 mmap 进来但暂时不可访问,需要时 mprotect 打开

Linux 的 `/proc/<pid>/smaps` 可以看每段内存的 prot:

```bash
cat /proc/self/smaps | grep -E '^[0-9]|Permissions' | head -10
# 输出:
# 00400000-0057b000 r-xp ...   ← 代码段(r-x)
# 0057c000-0057d000 r--p ...   ← 只读数据(r--)
# 0057d000-0057e000 rw-p ...   ← 数据段(rw-)
# ...
```

每行最后一个字段 `p` 或 `s` 表示 private/shared。前三个字符 `rwx` 表示权限。

#### guard page + signal handler 的最佳实践

```rust
use std::ffi::c_int;

#[repr(C)]
struct SigInfo {
    si_signo: c_int,
    si_errno: c_int,
    si_code: c_int,
    // ...
    si_addr: *mut u8,  // 触发 fault 的地址
}

extern "C" {
    fn sigaction(signum: c_int, act: *const SigAction,
                 oldact: *mut SigAction) -> c_int;
}

#[repr(C)]
struct SigAction {
    sa_sigaction: usize,
    sa_mask: [u64; 16],
    sa_flags: c_int,
    sa_restorer: usize,
}

const SA_SIGINFO: c_int = 4;

extern "C" fn handler(_sig: c_int, info: *mut SigInfo, _ctx: *mut u8) {
    let addr = unsafe { (*info).si_addr };
    eprintln!("SEGFAULT at {:p}", addr);
    // 这里可以查 arena 范围,定位哪个 arena 越界
    std::process::abort();
}

fn install_segfault_handler() {
    let act = SigAction {
        sa_sigaction: handler as usize,
        sa_mask: [0; 16],
        sa_flags: SA_SIGINFO,
        sa_restorer: 0,
    };
    unsafe { sigaction(11, &act, std::ptr::null_mut()); }
}
```

这套机制可以精确告诉用户"在地址 0x7f1234567890 越界",对应 arena 的哪个块。

### 3.3 · 🦀 Rust 生态视角

Rust 的 safe code 不可能写越界——slice 有边界检查,越界 panic。guard page 主要保护 **unsafe 代码**:

```rust
let buf: &mut [u8] = arena.alloc_slice_unchecked(100);  // unsafe
// 如果内部实现错了,buf.len() 可能大于实际,这里越界
buf[200] = 0xff;  // panic?不一定,因为 alloc_slice_unchecked 可能撒谎
```

Rust 安全保证的"前提"是 unsafe 代码正确。guard page 是 unsafe 代码的"额外保险"——即使 unsafe 实现错了,OS 还能抓住。

#### `libc` crate

Rust 标准库不直接暴露 mmap/mprotect,需要 `libc` crate:

```toml
[dependencies]
libc = "0.2"
```

然后:

```rust
use libc::{mmap, mprotect, munmap, PROT_READ, PROT_WRITE, PROT_NONE,
            MAP_PRIVATE, MAP_ANONYMOUS, MAP_FAILED};
```

教学版我们 extern "C" 手动声明,避免依赖。生产代码用 libc crate。

#### `nix` crate

更高级的封装是 `nix` crate,提供类型安全的 Rust API:

```rust
use nix::sys::mman::{mmap, mprotect, ProtFlags, MapFlags};

let ptr = unsafe {
    mmap(std::ptr::null(), len,
         ProtFlags::PROT_READ | ProtFlags::PROT_WRITE,
         MapFlags::MAP_PRIVATE | MapFlags::MAP_ANONYMOUS,
         -1, 0)?
};
```

返回 `Result`,错误处理优雅。教学项目坚持 extern "C",生产代码用 nix。

## 5 · 对照与变奏

### 不同 OS 的等价机制

| OS | API |
|---|---|
| Linux | `mmap` + `mprotect` |
| macOS | 同 Linux(BSD 系) |
| Windows | `VirtualAlloc` + `VirtualProtect`,有 `PAGE_GUARD` 标志 |
| FreeBSD | 同 Linux |
| 嵌入式 RTOS | 通常没有 MMU,无法做 guard page |

Windows 的 `PAGE_GUARD` 是个特殊标志——访问时触发 STATUS_GUARD_PAGE 异常(不是直接 segfault),应用程序可以 catch 并继续。Linux 没有等价的"软 guard",只有 `PROT_NONE` 直接 SIGSEGV。

### 历史演化

- **1970s UNIX**:VAX 的 MMU 出现,虚拟内存成熟
- **1980s**:BSD UNIX 引入 `mmap`
- **1990s**:POSIX 标准化 `mprotect`
- **2000s**:electric-fence / DUMA 等库普及
- **2010s**:ASan 出现,字级检测
- **2020s**:guard page 仍然是 debug build 主流

guard page 的概念 50 年没变,因为 OS 的虚拟内存模型没变。

### 不同语言的实现

| 语言 | guard page 易用性 |
|---|---|
| C/C++ | 直接 syscalls,简单 |
| Rust | 需要 `libc` 或 extern "C",稍麻烦但可行 |
| Zig | 同 C,直接 syscalls |
| Go | runtime 屏蔽了,需要 cgo |
| Python | 不可能,interpreter 自己管内存 |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 guard page 必须在 debug build 开启,release build 关闭?如果 release build 也开,会发生什么?

**参考解答**:

1. **内存浪费**:每块多 4 KB,几百块累计几 MB,对最终用户内存预算有影响
2. **mmap 调用增加**:启动慢一点(每块两次 mmap/mprotect)
3. **运行时几乎零开销**:MMU 硬件不走代码,但 TLB 压力略增
4. **崩溃敏感性**:release 用户可能遇到"罕见的边界 case",guard page 让小 bug 变成崩溃,影响体验
5. **CI / 内部 build 仍然开**:QA 必须能复现 debug 的所有保护

业界共识:debug 开启,release 关闭,但 crash reporter 上传前做"最近一次 debug 跑的 guard report"。

### Lv2 · 动手实践

**题**:在 day341 的 arena 上加 guard page,要求:

- mmap 块时多申请 4 KB,末尾设 `PROT_NONE`
- 块大小必须是 4 KB 倍数(简化对齐)
- 越界写触发 SIGSEGV
- Drop 时 `munmap` 整段(包括 guard)

测试:写一个 demo,故意 `*p.add(size) = 42`(越界写),应该 segfault。

完成标准:demo 跑出 segfault,`echo $?` 输出 139(128+11,SIGSEGV)。

**参考解答**:

```rust
use std::io;

const PAGE_SIZE: usize = 4096;

extern "C" {
    fn mmap(addr: *mut u8, len: usize, prot: i32, flags: i32,
            fd: i32, offset: i64) -> *mut u8;
    fn mprotect(addr: *mut u8, len: usize, prot: i32) -> i32;
    fn munmap(addr: *mut u8, len: usize) -> i32;
}

const PROT_READ: i32 = 1;
const PROT_WRITE: i32 = 2;
const PROT_NONE: i32 = 0;
const MAP_PRIVATE: i32 = 0x2;
const MAP_ANONYMOUS: i32 = 0x20;
const MAP_FAILED: isize = -1;

pub struct GuardedBlock {
    base: *mut u8,
    total_size: usize,   // 包括 guard page
    usable_size: usize,  // 不包括 guard
}

impl GuardedBlock {
    pub fn new(usable_size: usize) -> io::Result<Self> {
        // usable_size 向上对齐到 PAGE_SIZE
        let usable = (usable_size + PAGE_SIZE - 1) & !(PAGE_SIZE - 1);
        let total = usable + PAGE_SIZE;
        unsafe {
            let base = mmap(std::ptr::null_mut(), total,
                            PROT_READ | PROT_WRITE,
                            MAP_PRIVATE | MAP_ANONYMOUS,
                            -1, 0);
            if base as isize == MAP_FAILED {
                return Err(io::Error::last_os_error());
            }
            // 末尾 PAGE_SIZE 设为 PROT_NONE
            let guard = base.add(usable);
            if mprotect(guard, PAGE_SIZE, PROT_NONE) != 0 {
                munmap(base, total);
                return Err(io::Error::last_os_error());
            }
            Ok(Self { base, total_size: total, usable_size: usable })
        }
    }

    pub fn base(&self) -> *mut u8 { self.base }
    pub fn usable_size(&self) -> usize { self.usable_size }
}

impl Drop for GuardedBlock {
    fn drop(&mut self) {
        unsafe { munmap(self.base, self.total_size); }
    }
}

fn main() {
    let block = GuardedBlock::new(1 << 20).expect("alloc");
    println!("Got block at {:p}, size {} KB",
             block.base(), block.usable_size() / 1024);

    // 故意越界写——应该 segfault
    let overflow_ptr = unsafe { block.base().add(block.usable_size()) };
    println!("About to write to guard page at {:p}", overflow_ptr);
    unsafe { *overflow_ptr = 42; }  // 触发 SIGSEGV
    println!("This should not print");
}
```

```

About to write to guard page at 0x7f...
```

## 8 · Rust / Arch 落地代码

完整 demo,包括 SIGSEGV 处理:

```rust
// Cargo.toml: 无依赖
// src/main.rs

use std::ffi::c_int;
use std::io;

const PAGE_SIZE: usize = 4096;

extern "C" {
    fn mmap(addr: *mut u8, len: usize, prot: i32, flags: i32,
            fd: i32, offset: i64) -> *mut u8;
    fn mprotect(addr: *mut u8, len: usize, prot: i32) -> i32;
    fn munmap(addr: *mut u8, len: usize) -> i32;
    fn write(fd: c_int, buf: *const u8, count: usize) -> isize;
    fn signal(signum: c_int, handler: usize) -> usize;
    fn abort() -> !;
}

const PROT_READ: i32 = 1;
const PROT_WRITE: i32 = 2;
const PROT_NONE: i32 = 0;
const MAP_PRIVATE: i32 = 0x2;
const MAP_ANONYMOUS: i32 = 0x20;

extern "C" fn segfault_handler(_sig: c_int) {
    let msg = b"\n*** SIGSEGV caught! Likely arena guard page violation ***\n";
    unsafe {
        write(2, msg.as_ptr(), msg.len());
        abort();
    }
}

fn install_segfault_handler() {
    unsafe { signal(11, segfault_handler as usize); }
}

pub struct GuardedBlock {
    base: *mut u8,
    total_size: usize,
    usable_size: usize,
}

impl GuardedBlock {
    pub fn new(usable_size: usize) -> io::Result<Self> {
        let usable = (usable_size + PAGE_SIZE - 1) & !(PAGE_SIZE - 1);
        let total = usable + PAGE_SIZE;
        unsafe {
            let base = mmap(std::ptr::null_mut(), total,
                            PROT_READ | PROT_WRITE,
                            MAP_PRIVATE | MAP_ANONYMOUS,
                            -1, 0);
            if base as isize == -1 {
                return Err(io::Error::last_os_error());
            }
            let guard = base.add(usable);
            if mprotect(guard, PAGE_SIZE, PROT_NONE) != 0 {
                munmap(base, total);
                return Err(io::Error::last_os_error());
            }
            Ok(Self { base, total_size: total, usable_size: usable })
        }
    }
    pub fn base(&self) -> *mut u8 { self.base }
    pub fn usable_size(&self) -> usize { self.usable_size }
}

impl Drop for GuardedBlock {
    fn drop(&mut self) {
        unsafe { munmap(self.base, self.total_size); }
    }
}

fn main() {
    install_segfault_handler();
    println!("=== Guard page demo ===");

    let block = GuardedBlock::new(1 << 20).expect("alloc");
    println!("Block at {:p}, usable {} KB",
             block.base(), block.usable_size() / 1024);

    // 合法写入
    unsafe {
        for i in 0..100 {
            *block.base().add(i) = i as u8;
        }
    }
    println!("100 legit bytes written");

    // 越界写——应该 segfault
    println!("Now writing PAST the end...");
    unsafe {
        let bad = block.base().add(block.usable_size());
        *bad = 42;  // 这里触发 SIGSEGV
    }
    println!("This shouldn't print");
}
```

**预期输出**:

```
=== Guard page demo ===
Block at 0x7f1234567890, usable 1024 KB
100 legit bytes written
Now writing PAST the end...

*** SIGSEGV caught! Likely arena guard page violation ***
Aborted (core dumped)
$ echo $?
134
```

### 进一步展开:从概念到落地的完整路径

要把今天讨论的抽象概念变成可运行的代码,我们必须经历几个具体阶段。这一节展开每一步的工程细节。

**阶段一:定义接口**。Casey 在动手实现前,先想清楚 API。Rust 的 trait 是定义接口的工具:

```rust
trait Sortable {
```

trait 让代码可测试、可替换。Casey 经常说"先写 trait,再写 impl"——这强迫你思考抽象边界。

**阶段二:单元测试**。每个 sort_rule 分支都应有对应测试:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    fn test_basic_ordering() {
        let a = TestEntity { layer: 1, y: 100.0 };
        let b = TestEntity { layer: 1, y: 200.0 };
```

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
