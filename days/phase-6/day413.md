
# Day 413 · 编码光值

> 体素光照的存储格式怎么选?直接用 `f32x3`(线性 RGB)简单但占 12 字节,一个 32³ 体素网格就要 1.5 MB。今天 Casey 把光值**编码**成更紧凑的格式,同时保证动态范围足够大、解码足够便宜。这是数据导向设计(Data-Oriented Design)的经典实战。

## 0 · 为什么要有这一天

把这个问题摆在你面前:你想存一个 64×64×64 的体素光照网格,每个体素存 RGB 光强。如果用 `f32x3`(12 字节),整个网格占 `64³ × 12 = 3.1 MB`。一帧需要 3 个网格(当前帧 + 上一帧 + 间接光),近 10 MB,每次光照传播全扫一遍,缓存压力大。

但**你真的需要 f32 的精度吗**?光照值的物理范围:最暗的角落约 0.001 lux,正午阳光约 100000 lux。差 8 个数量级。f32 的尾数 23 位只有 7 位有效数字,8 个数量级需要 log2(10^8) ≈ 26.6 位——刚好接近 f32 极限,但**人眼对光强的感知是对数的**,所以光强可以压缩到对数空间存储。

更关键的:**人眼能区分的亮度差**约 1%(韦伯-费希纳定律)。f32 的 23 位尾数远超人眼分辨能力,大量精度被浪费。如果用 16 位浮点(f16),精度仍然是人眼分辨率的 100 倍,但存储减半——1.5 MB 而不是 3 MB。

或者更激进:**RGBE 编码**(RGB + 共享指数),像 Radiance HDR 文件用的格式,每个像素 4 字节而不是 12 字节,但能表达 76 个数量级的动态范围。

Casey 今天的目标:找一个 HH 体素光照"刚好够用"的编码。他最终选了什么?**对数空间 f16x3 或类似的紧凑格式**。这一步看起来是性能优化,实际是教你一个核心思想:**存储格式决定算法的可行边界**。

心理锚点:今天之后,你能解释 HDR、log-space、RGBE 这些工业渲染术语的含义,能在自己的项目里做"格式 vs 性能"的权衡,知道为什么 Unreal 用 R9G9B9E5 共享指数格式存 Lumen 的体素光照。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 在白板上列了几种候选编码:

1. `f32x3`(线性 RGB,12 字节)—— 基线
2. `f16x3`(半精度,6 字节)—— 简单压缩
3. RGBE(3 字节 RGB + 1 字节共享指数,4 字节)—— HDR 业界标准
4. LogLuv(4 字节,亮度和色度分离)—— 高效但解码贵
5. R11G11B10(无符号,4 字节,无指数)—— GPU 友好但动态范围小

他纠结于两点:**动态范围够不够**(光强可能远大于 1)和**解码成本**(每像素采样都要解码,贵的格式影响帧率)。

最终他选了**自己的紧凑编码**:类似 RGBE,但简化。具体:

```c
struct encoded_light {
    u8 r, g, b;      // 颜色(已归一化)
    u8 exponent;     // 共享指数
};
// 4 字节,但 exponent 用 7 位 + 1 位符号(可表达 1e-38 到 1e+38)
```

解码:`color = (r/255, g/255, b/255) * 2^(exponent - 128)`。这给 256 个数量级的动态范围,远远够用。

Casey 强调:**编码不是为了节省内存**(虽然省了 3 倍),而是为了让 SIMD 一次处理 4 个值——day431 的 4-wide SIMD 需要 16 字节对齐的输入,4 字节编码 × 4 = 16 字节,正好。

## 2 · 心智模型

### 类比:科学记数法

回忆中学物理:`光速 = 3.0 × 10^8 m/s`。这里 `3.0` 是尾数(mantissa),`10^8` 是指数(exponent)。任何范围内的数字都可以这样表达——这就是科学记数法。

浮点数就是用二进制做科学记数法。`f32` 有 23 位尾数(7 位有效数字)+ 8 位指数(覆盖 10^±38)+ 1 位符号。共 32 位 = 4 字节。

但**很多时候你不需要 8 位指数**。比如光照值,实际范围 0 到 1000(个数量级),只需要 4 位指数就够。剩下来的位可以分给尾数提高精度,或者干脆省掉(节省存储)。

这就是**编码(encoding)**:用更紧凑的格式存同样的信息,接受精度损失换取空间和速度。

### 严谨原理:浮点数的结构

IEEE 754 f32 的位布局:

```
位 31     位 30-23     位 22-0
[符号]    [指数 8 位]  [尾数 23 位]
```

值 = `(-1)^sign × 1.mantissa × 2^(exponent - 127)`

`f16` 同理,但只有 5 位指数 + 10 位尾数,范围 10^±4,精度约 3 位有效数字。

RGBE 编码:**所有三个通道共享一个指数**。RGB 通常相关(亮一点的白色 = 三个通道都大),所以共享指数损失不大。位分配:R/G/B 各 8 位(0-255),E 8 位指数。

```
encoded:  R  G  B  E
解码:     value_r = R / 255 * 2^(E - 128)
          (G, B 同理)
```

编码时:找到三个值中最大的,算它的指数,所有值除以 `2^指数`,归一化到 [0, 255]。

### 对数空间编码

更激进的方案:存光强的**对数**而不是光强本身。`log(L)` 的范围比 `L` 小很多——L 从 0.001 到 1000 是 6 个数量级,log(L) 从 -7 到 +7 只有 14 单位。

```
encoded = log(L + epsilon)  // 加 epsilon 避免 log(0)
decoded = exp(encoded) - epsilon
```

对数空间的好处:**乘法变加法**。两个光强相乘(反射 × 入射)在对数空间是相加,便宜。

### Casey 的实际选择

Casey 没用 log,因为解码 `exp` 比 `pow` 慢。他用了**类 RGBE** 的格式。具体代码(伪):

```rust
#[derive(Copy, Clone)]
#[repr(C)]  // 保证内存布局,4 字节
pub struct PackedLight {
    pub r: u8,
    pub g: u8,
    pub b: u8,
    pub e: u8,  // exponent
}

impl PackedLight {
    pub fn pack(rgb: Vec3) -> Self {
        // 找最大值
        let max = rgb.x.max(rgb.y).max(rgb.z).max(1e-6);
        // 算指数:log2(max) + 128,clamp 到 [0, 255]
        let e = ((max.log2() + 128.0).round() as i32).clamp(0, 255) as u8;
        // 归一化:rgb / 2^(e-128) * 255
        let scale = 255.0 / (2.0_f32).powf((e as f32) - 128.0);
        Self {
            r: (rgb.x * scale).clamp(0.0, 255.0) as u8,
            g: (rgb.y * scale).clamp(0.0, 255.0) as u8,
            b: (rgb.z * scale).clamp(0.0, 255.0) as u8,
            e,
        }
    }

    pub fn unpack(&self) -> Vec3 {
        let scale = (2.0_f32).powf((self.e as f32) - 128.0) / 255.0;
        Vec3::new(
            self.r as f32 * scale,
            self.g as f32 * scale,
            self.b as f32 * scale,
        )
    }
}
```

`#[repr(C)]` 保证 Rust 不重排字段,内存布局确定,可以放心 `memcpy` 和 SIMD。

### 动态范围 vs 精度

权衡的核心:

- **动态范围**:能表达多大范围的值,取决于指数位数
- **精度**:每个值的相对误差,取决于尾数位数

8 位指数给 ~10^38 范围(超够),8 位尾数(每通道)给 ~1% 精度。Casey 认为光照 1% 精度人眼不可分辨,够用。

工业格式 `R11G11B10`:11+11+10 = 32 位,无符号,无指数。范围只能 [0, 大值),需要预乘一个全局曝光值。GPU 原生支持,速度快。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏工业的 HDR 编码:

- **Unreal Lumen**:用 R9G9B9E5(9 位尾数 + 5 位共享指数)体素光照,4 字节
- **Unity HDRP**:类似 R9G9B9E5
- **Cyberpunk Lumen**:R16G16B16A16_FLOAT(8 字节)前向,精度优先
- **PS5 独占游戏**:GPU 硬件原生 R11G11B10,几乎免费

游戏工业选 R9G9B9E5 而不是 RGBE 的原因:**GPU 硬件原生支持采样和解码**。PC 的 OpenGL/Vulkan 有 `GL_RGB9_E5` 格式,硬件免费转换。Casey 在 CPU 上,自己写解码,选 RGBE 简单。

### 3.2 · 🎨 图形学视角

HDR 渲染的核心概念:

- **LDR(Low Dynamic Range)**:每通道 8 位,范围 [0, 255]——传统 sRGB 显示
- **HDR(High Dynamic Range)**:浮点或带指数,范围 >> 255——现代渲染
- **色调映射(Tone Mapping)**:把 HDR 转成 LDR 显示,常用 ACES、Reinhard

光照中间值在 HDR 空间计算,最后才 tone map。如果光照用 LDR,光强超过 1 就被截断,高光区域全是死白,失去细节。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里"编码"无处不在:

- **页表项(PTE)**:64 位存物理地址 + 权限位,某种编码
- **inode**:文件元数据编码成磁盘格式(ext4 inode 256 字节)
- **/proc 文件**:内核数据结构编码成文本,可读但效率低

学习编码的核心:**选择合适的表达方式,让存储和计算都高效**。

### 3.4 · 🦀 Rust 生态视角

Rust 表达紧凑编码:

```rust
#[derive(Copy, Clone)]
#[repr(C, packed)]  // 紧凑,无 padding
pub struct PackedLight {
    r: u8,
    g: u8,
    b: u8,
    e: u8,
}

impl PackedLight {
    pub const ZERO: Self = Self { r: 0, g: 0, b: 0, e: 0 };

    // 安全转换:#[repr(C, packed)] 保证 4 字节
    pub fn from_bytes(bytes: [u8; 4]) -> Self {
        // SAFETY: PackedLight is #[repr(C, packed)] with 4 u8 fields
        unsafe { std::mem::transmute(bytes) }
    }

    pub fn to_bytes(&self) -> [u8; 4] {
        // SAFETY: same as above
        unsafe { std::mem::transmute(*self) }
    }
}

// 验证大小
const _: () = assert!(std::mem::size_of::<PackedLight>() == 4);
```

`const _: () = assert!(...)` 是编译期断言,保证结构体大小符合预期。如果以后加字段忘了检查,编译失败。

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:为什么 RGBE 比 f32x3 省 3 倍空间,但动态范围反而更大?这是什么权衡?

**参考解答**:RGBE 共享一个指数给三个通道,而 f32x3 每个通道独立有 8 位指数。共享损失的是"三个通道可以独立有不同指数"的能力——但光照的 RGB 通常比例接近(白色光 r=g=b,黄色光 r≈g>>b),共享指数损失小。

8 位 f32 指数给 ~10^±38 范围,8 位 RGBE 指数给 ~10^±38 范围,相同。但 RGBE 尾数只有 8 位/通道,精度 ~1%,而 f32 尾数 23 位,精度 ~10^-7。

**核心权衡**:用精度换空间。光照的精度需求低(人眼分辨 ~1%),所以 8 位尾数够,省 3 倍空间值得。

- 4 字节大小断言生效

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug, PartialEq)]
#[repr(C)]
pub struct PackedLight {
    pub r: u8,
    pub g: u8,
    pub b: u8,
    pub e: u8,
}

const _: () = assert!(std::mem::size_of::<PackedLight>() == 4);
const _: () = assert!(std::mem::align_of::<PackedLight>() == 1);

impl PackedLight {
    pub const ZERO: Self = Self { r: 0, g: 0, b: 0, e: 0 };

    pub fn pack(rgb: Vec3) -> Self {
        let max = rgb.x.max(rgb.y).max(rgb.z);
        if max <= 1e-6 {
            return Self::ZERO;
        }
        // 指数:让最大值归一化到 [128, 255] 范围
        // 这样最大值解码后接近 max,小值不会下溢
        let e = ((max.log2().ceil() + 128.0) as i32).clamp(0, 255) as u8;
        let scale = 255.0 * (2.0_f32).powf(128.0 - e as f32);
        Self {
            r: (rgb.x * scale).clamp(0.0, 255.0).round() as u8,
            g: (rgb.y * scale).clamp(0.0, 255.0).round() as u8,
            b: (rgb.z * scale).clamp(0.0, 255.0).round() as u8,
            e,
        }
    }

    pub fn unpack(&self) -> Vec3 {
        let scale = (2.0_f32).powf(self.e as f32 - 128.0) / 255.0;
        Vec3::new(
            self.r as f32 * scale,
            self.g as f32 * scale,
            self.b as f32 * scale,
        )
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn size_is_4() {
        assert_eq!(std::mem::size_of::<PackedLight>(), 4);
    }

    #[test]
    fn round_trip_white() {
        let p = PackedLight::pack(Vec3::new(1.0, 1.0, 1.0));
        let v = p.unpack();
        assert!((v - Vec3::new(1.0, 1.0, 1.0)).length() < 0.01);
    }

    #[test]
    fn round_trip_bright() {
        let p = PackedLight::pack(Vec3::new(1000.0, 1000.0, 1000.0));
        let v = p.unpack();
        assert!((v - Vec3::new(1000.0, 1000.0, 1000.0)).length() < 10.0);
    }

    #[test]
    fn round_trip_dim() {
        let p = PackedLight::pack(Vec3::new(0.001, 0.001, 0.001));
        let v = p.unpack();
        assert!((v - Vec3::new(0.001, 0.001, 0.001)).length() < 0.0001);
    }

    #[test]
    fn zero_packs_to_zero() {
        let p = PackedLight::pack(Vec3::ZERO);
        assert_eq!(p, PackedLight::ZERO);
    }
```

## 8 · Rust / Arch 落地代码

### Rust:RGBE 编解码 + 内存布局验证

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug, PartialEq)]
#[repr(C)]
pub struct PackedLight {
    pub r: u8,
    pub g: u8,
    pub b: u8,
    pub e: u8,
}

// 编译期断言:大小 4 字节,对齐 1 字节
const _: () = assert!(std::mem::size_of::<PackedLight>() == 4);
const _: () = assert!(std::mem::align_of::<PackedLight>() == 1);

impl PackedLight {
    pub const ZERO: Self = Self { r: 0, g: 0, b: 0, e: 0 };

    pub fn pack(rgb: Vec3) -> Self {
        let max = rgb.x.max(rgb.y).max(rgb.z);
        if max <= 1e-6 {
            return Self::ZERO;
        }
        let e = ((max.log2().ceil() + 128.0) as i32).clamp(0, 255) as u8;
        let scale = 255.0 * (2.0_f32).powf(128.0 - e as f32);
        Self {
            r: (rgb.x * scale).clamp(0.0, 255.0).round() as u8,
            g: (rgb.y * scale).clamp(0.0, 255.0).round() as u8,
            b: (rgb.z * scale).clamp(0.0, 255.0).round() as u8,
            e,
        }
    }

    pub fn unpack(&self) -> Vec3 {
        if self.e == 0 { return Vec3::ZERO; }
        let scale = (2.0_f32).powf(self.e as f32 - 128.0) / 255.0;
        Vec3::new(
            self.r as f32 * scale,
            self.g as f32 * scale,
            self.b as f32 * scale,
        )
    }

    pub fn add(&self, other: &Self) -> Self {
        // 解包相加再打包
        Self::pack(self.unpack() + other.unpack())
    }
}

pub struct VoxelGrid {
    pub dims: (usize, usize, usize),
    pub voxels: Vec<PackedLight>,
}

impl VoxelGrid {
    pub fn new(dims: (usize, usize, usize)) -> Self {
        let total = dims.0 * dims.1 * dims.2;
        Self { dims, voxels: vec![PackedLight::ZERO; total] }
    }

    pub fn memory_usage_bytes(&self) -> usize {
        self.voxels.len() * std::mem::size_of::<PackedLight>()
    }
}

fn main() {
    println!("PackedLight size: {} bytes", std::mem::size_of::<PackedLight>());
    // PackedLight size: 4 bytes

    let grid = VoxelGrid::new((64, 64, 64));
    println!("Grid memory: {} KB", grid.memory_usage_bytes() / 1024);
    // Grid memory: 1024 KB (1 MB,vs f32x3 的 3 MB)

    let original = Vec3::new(0.5, 1.7, 3.2);
    let packed = PackedLight::pack(original);
    let restored = packed.unpack();
    let err = (restored - original).length();
    println!("Original: {:?}, Packed: {:?}, Restored: {:?}, Error: {}",
        original, packed, restored, err);
    // Original: [0.5, 1.7, 3.2], Packed: PackedLight{..}, Restored: ~[0.5, 1.7, 3.2], Error: ~0.01
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
