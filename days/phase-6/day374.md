## 0 · 为什么要有这一天

你写完鼠标拾取,自己测试:鼠标在屏幕中央,射线应该指向相机正前方。但你看到射线偏了一个角度——**不是相机看的地方**。

你以为代码错了,检查矩阵、检查 NDC 翻转、检查 perspective divide,都对。但射线还是偏。

**真相**:**投影矩阵对 Z 的变换非线性**。Z 从相机空间的 `[near, far]` 被映射到 NDC 的 `[-1, +1]`,但这个映射不是线性插值——它**对靠近 near plane 的 Z 更敏感**(对数压缩)。这是 perspective projection 的本质,但反推时如果你不注意,容易出错。

更深一层:**深度缓冲(depth buffer)**存的不是相机空间的 Z,而是 NDC 的 Z(已经经过 perspective divide 后的值)。深度 0.5 对应的不是相机空间 (near + far) / 2,而是某个**严重偏近**的值。这导致:
- z-fighting(深度冲突):两个面靠太近,深度精度不够,无法区分
- depth bias(深度偏置):用 `glPolygonOffset` 加偏置,避免 z-fighting,但偏置影响反推

**今天的工作**:Casey 调试一个"鼠标射线不对"的 bug,深入到 Z 变换和深度偏置的细节,发现是 `glPolygonOffset` 影响了 Z 值,修 bug。

更深层主题:**深度精度**(depth precision)。这是图形学里微妙但重要的概念。理解它你就理解了为什么用 logarithmic depth buffer、为什么 reverse-Z 是工业标准、为什么 z-fighting 这么常见。

心理锚点:今天之后,你能调试 Z 相关的诡异 bug,理解 perspective projection 对深度的非线性映射,知道怎么避免 z-fighting。

## 2 · 心智模型

### 类比:Z 变换是"放大近处"

想象你看一条直线,从你眼睛到远方。直线上的点是连续的,从 0(眼睛)到无穷(地平线)。你想把这直线压成 [0, 1] 区间存到深度 buffer。

**线性映射**:`z_buffer = z_camera / far`。问题:近处精度不够。如果你 near=0.1, far=100,深度 0.001 对应 z=0.1(near plane),0.002 对应 z=0.2。0.1 米和 0.2 米差 0.1 米,但深度只差 0.001。当深度是 24 位(0~16M),0.001 差不多是 16000 个值——这意味着近处 0.1 米内有 16000 个深度级,**实际上完全够用**。

但问题是远处。深度 0.999 对应 z=99.9 米,深度 1.000 对应 z=100 米。**1 米的差距只占 0.001 的深度范围**。16000 个深度值,意味着 0.1 米的精度——**这远远不够**。两栋相距 0.05 米的楼在远处会"打架"(z-fighting)。

**非线性映射(perspective projection)**:

```
z_buffer = (far * (z - near)) / (z * (far - near))
```

这个映射让近处的 Z 占更多深度区间,远处的 Z 占更少。具体:z=near → z_buffer=0,z=far → z_buffer=1,中间不均匀。

```
传统 depth buffer 的精度分布:

z_camera:    near ──────── 1m ──────────── far
              ↓             ↓                ↓
z_buffer:     0 ───── 0.5 ──────────────── 1
                  (50% 深度给 1m 内!)
```

这是为什么 z-fighting 在远处常见:近处精度足够(50% 给 1m 内),远处精度稀疏(1m 内只占 0.001 深度)。

### Reversed-Z:工业优化

观察:传统深度 buffer 在近处精度过剩(50% 给 1m 内),远处精度不足。但实际游戏里,玩家关心的是近处的物体(自己周围的),远处用 fog 蒙住。

**Reversed-Z 策略**:
- 深度 buffer 存 1 - traditional_z
- z=near → z_buffer=1
- z=far → z_buffer=0
- 浮点深度 buffer(f32)在 1 附近精度极高(浮点数 0.5~1.0 占一半精度)

**结合浮点深度 buffer**:f32 在 [0.5, 1.0] 占一半精度(2^22 = 4M 个值),1.0 是 near plane,0.0 是 far plane。**近处精度爆炸**(4M 个值给 0.1m~1m),远处精度仍可用(4M 个值给 99m~100m)。z-fighting 几乎消失。

工业 100% 用 reversed-Z + float depth buffer(DirectX 11+ / OpenGL 4.5+ / Vulkan)。Casey 今天调试发现的 bug,就是没用 reversed-Z 导致近处 z-fighting。

### Z 变换的数学

投影矩阵 P 把相机空间 z 变到 NDC z:

```
正向:z_clip = z_camera * P[2][2] + P[3][2]
        P[2][2] = -(far + near) / (far - near)
        P[3][2] = -2 * far * near / (far - near)
NDC:z_ndc = z_clip / w_clip = z_clip / (-z_camera)
       (注意:w_clip = -z_camera,因为 OpenGL 用右手相机,z 朝外为负)
```

简化的最终公式:

```
z_ndc = (far + near - 2 * far * near / z_camera) / (far - near)
```

观察:`z_camera` 在分母。这意味着 z_ndc 对 z_camera 是**反比函数**(双曲线)。z_camera = near 时,z_ndc = -1;z_camera = far 时,z_ndc = +1。中间是双曲线,近处变化快,远处变化慢。

### Reversed-Z 公式

Reversed-Z 让 z_buffer 从 1(near)递减到 0(far):

```
z_buffer_reversed = 1 - (z_ndc + 1) / 2  // 把 [-1, +1] 映射到 [1, 0]
```

或者投影矩阵改写:

```
P_reversed[2][2] = (near - far) / near  // 反号
P_reversed[3][2] = far
P_reversed[2][3] = -1
```

`glam` 用 reversed-Z 风格,所以 Casey 的 `glam::Mat4::perspective_lh` 已经是 reversed-Z。

### glPolygonOffset 和深度偏置

`glPolygonOffset(factor, units)` 给 polygon 加深度偏置:

```
z_final = z_shader + factor * DZ + units * r
```

其中 DZ 是 polygon 斜率(最大深度梯度),r 是最小可分辨深度差。**用途**:画 decals / shadow maps 时,避免和底层几何 z-fighting。

但 polygon offset 改变了 fragment 的最终 Z,**反推时如果不考虑,会出错**。Casey 今天的 bug 一部分来自这里。

### Z 反推的完整流程

```
screen_pos (pixel)
  ↓ 视口反变换
ndc_xy (∈ [-1, +1])
  ↓ 选 z(深度 buffer 读或假设)
ndc (x, y, z)
  ↓ 构造 clip(x, y, z, w=1)
clip
  ↓ × inv_projection
camera
  ↓ × inv_view
world
```

**关键**:z 选 -1(near plane)还是 +1(far plane),决定射线的具体起点。如果选 0(中间),得到穿过中间深度的世界点。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

Z 变换在游戏里的常见 bug:

**Z-fighting(深度冲突)**

两个面共面或几乎共面时,深度 buffer 无法区分,渲染时**闪烁**(帧间哪个在前不定)。

解决方案:
1. **几何调整**:让两个面稍微分开(0.001 单位),最简单
2. **glPolygonOffset**:给上层 polygon 加偏置
3. **Reversed-Z + float depth**:用浮点深度 buffer,Z 精度爆炸,z-fighting 几乎消失

**Shadow acne(阴影痤疮)**

Shadow mapping 时,shadow map 的深度和几何实际深度有精度差,导致几何面"自阴影"出现条纹。用 `glPolygonOffset` 加偏置解决。

**Skybox 画到 framebuffer 末尾**

Skybox 应该在所有 3D 几何之后画,Z 设为 far plane(depth = 1,或 reversed-Z 的 0)。这样几何不会遮挡天空。

### 3.2 · 🎨 图形学视角

深度精度的图形学深入:

**整数 vs 浮点深度 buffer**

```
整数 depth (GL_DEPTH_COMPONENT24): 24 位,均匀分布
浮点 depth (GL_DEPTH_COMPONENT32F): 32 位 float,精度集中在 [0.5, 1.0]
```

**为什么浮点精度集中在 [0.5, 1.0]**?IEEE 754 单精度浮点数,符号位 1,指数位 8,尾数位 23。指数 0 表示 0~0.5(精度低,因为 subnormal),指数 -1 表示 0.5~1.0(精度高,23 位尾数 = 8M 个值)。

Reversed-Z 让 near plane 在深度 1.0,这正好是浮点精度最高的区域。结合 reversed-Z + float depth,近处精度可达 1nm(纳米级),完全够游戏使用。

**Logarithmic depth buffer**

更激进的方案:深度 buffer 存 `log(z_camera)`,精度对 z 是均匀的(对数尺度)。需要 shader 里手写 `gl_FragDepth`,有性能损失。某些大型开放世界游戏用(Witcher 3, Just Cause 3)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上深度 buffer 由 Mesa 管理。可以选择不同格式:

```rust
// 创建 framebuffer 时选 depth format
unsafe {
    gl::BindRenderbuffer(gl::RENDERBUFFER, rbo);
    gl::RenderbufferStorage(
        gl::RENDERBUFFER,
        gl::DEPTH_COMPONENT32F,   // 或 DEPTH_COMPONENT24, DEPTH_COMPONENT32F
        width, height,
    );
}
```

**Mesa 的实现**:
- DEPTH_COMPONENT24:24 位整数深度,8 位 stencil(共 32 位)
- DEPTH_COMPONENT32F:32 位 float 深度,无 stencil
- DEPTH24_STENCIL8:24 位深度 + 8 位 stencil,常见格式

**性能差异**:

```bash
# 测试不同 depth format 的性能
# 用 perf 记录 GPU 时钟
perf stat -e instructions,cycles,GTSEIdle ./target/release/handmade_hero
# 不同 format 性能差 5-15%,深度测试是热点
```

### 3.4 · 🦀 Rust 生态视角

Rust 处理 Z 变换的常见错误:

**错误 1:混淆 left-handed 和 right-handed**

```rust
// 错误:混用 lh 和 rh
let view = Mat4::look_at_lh(...);
let proj = Mat4::perspective_rh(...);  // ← rh!和 view 不匹配
let vp = proj * view;  // 矩阵错乱
```

**修复**:全部用 `_lh` 或全部用 `_rh`。

**错误 2:Z 反推时 NDC z 范围错**

```rust
// 错误:假设 NDC z ∈ [0, 1](DirectX 风格)
let ndc_near = Vec4::new(x, y, 0.0, 1.0);  // ← 错!OpenGL 是 [-1, +1]

// 修复:OpenGL NDC z ∈ [-1, +1]
let ndc_near = Vec4::new(x, y, -1.0, 1.0);
```

**错误 3:reversed-Z 没处理**

```rust
// 如果用 reversed-Z,深度 buffer 存的是 1 - traditional_z
// 但 NDC z 还是 [-1, +1](reversed-Z 不改变 NDC,只改变 depth buffer 编码)
```

**Debug 技巧**:

```rust
// 打印矩阵看数值
println!("Projection:\n{}", proj);    // glam 的 Display
println!("View:\n{}", view);
println!("VP:\n{:?}", vp);

// 验证 inverse
let inv = vp.inverse();
let recovered = inv * vp;
println!("identity check (should be I):\n{:?}", recovered);
// 对角线 1,其他 0,精度 1e-5 内
```

## 4 · 认知地图

### 4.1 上级

- **Depth Buffer**(深度缓冲) —— 存像素深度,用于深度测试
- **Perspective Projection**(透视投影) —— 3D → 2D 的非线性投影,丢失深度方向
- **Coordinate Spaces**(坐标空间) —— model / world / camera / clip / NDC / screen

### 4.2 同级(并行方案)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Traditional Z | near→0, far→1 | 默认 OpenGL | 旧 |
| Reversed-Z | near→1, far→0 + float depth | 工业 AAA | ✅ |
| Logarithmic Z | 精度对数均匀 | 开放世界 | 不用 |
| glPolygonOffset | 加偏置避免 z-fighting | Decals / shadow | 用过 |

### 4.3 下级

- **`glDepthFunc`** —— 深度测试函数(GL_LESS, GL_LEQUAL 等)
- **`glDepthRange`** —— NDC z 到 depth buffer 的映射范围
- **`glPolygonOffset`** —— 多边形深度偏置
- **`glClearDepth`** —— 清深度 buffer 用的值(1.0 传统,0.0 reversed-Z)
- **Reversed-Z projection matrix** —— 改写的投影矩阵

## 5 · 对照与变奏

### 同一问题在不同 API 的表达

**问题**:启用 reversed-Z。

| API | 实现 |
|---|---|
| OpenGL | `glClipControl(GL_LOWER_LEFT, GL_ZERO_TO_ONE)` + 改投影矩阵 |
| Vulkan | `VkPipelineDepthStencilStateCreateInfo.depthCompareReference` |
| DirectX 11/12 | 默认就是 reversed-Z 风格(depth [0,1]) |
| Metal | `MTLDepthDescriptor.depthCompareFunction` |
| WebGPU | `wgpu::CompareFunction::Greater` |

OpenGL 4.5 的 `glClipControl` 是 reversed-Z 关键 API。它改变 NDC z 范围从 [-1, +1] 到 [0, 1],匹配 DirectX。

### 历史演化

- **1990s**: 整数深度 buffer,Traditional Z,1mm 精度
- **2008**: float depth buffer(ARB_depth_buffer_float)
- **2010**: Reversed-Z 流行,AAA 引擎普遍采用
- **2015 (OpenGL 4.5)**: `glClipControl` API,标准化 reversed-Z
- **2020+**:几乎所有现代引擎用 reversed-Z + float depth

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么传统 Z 在远处容易 z-fighting,而 reversed-Z + float depth 几乎消除 z-fighting?

**参考解答**:传统 Z 是线性映射 `z_buf = (z - near) / (far - near)`,整数 depth buffer(24 位)精度均匀。远处的 1m 占 `(1/100) × 16M = 160k` 个深度值,理论够,但**实际几何在远处的相对距离很小**(两栋楼 0.01m 差距),160k / 0.01m = 16M/m 看起来够,但**深度测试比较的不是绝对值,而是相对像素**。当一个像素的深度 = 0.9990,另一个 = 0.9991,这俩像素之间还有其他物体的像素,每个像素的深度从 fragment shader 计算时都有舍入误差,导致 z-fighting。

Reversed-Z + float depth:
- Reversed-Z 让 near plane 在深度 1.0,float 在 1.0 附近精度爆炸(8M 个值给 [0.5, 1.0])
- 远处(深度接近 0)精度仍可用(8M 个值给 [0, 0.5]),但 0~1m 占了 16M 个值,远超传统 Z

实测:reversed-Z + float depth 让 1km 远的 1mm 物体仍能区分。这就是工业标准。

### Lv2 · 动手实践

**题**:在 Rust 项目里实现 reversed-Z + float depth。完成标准:
- 深度 buffer 格式 `GL_DEPTH_COMPONENT32F`
- 投影矩阵用 reversed-Z 风格
- `glClearDepth(0.0)`(清深度时填 0,对应 reversed-Z 的 far)
- `glDepthFunc(GL_GREATER)`(深度大的优先,对应 reversed-Z)
- 验证:渲染两个相距 0.001 单位的平面,远处不闪烁

**参考解答**:

```rust
use glam::Mat4;

pub fn reversed_z_perspective(fov_y: f32, aspect: f32, near: f32, far: f32) -> Mat4 {
    // Reversed-Z 投影矩阵
    // 标准 perspective_lh 后反转 z 行
    let mut p = Mat4::perspective_lh(fov_y, aspect, near, far);
    // 反转 z 列让 z=near 映射到 1,z=far 映射到 0
    // glam 实际上提供 reversed_z 版本,但也可以手写
    // 简化:用 glam 的 perspective_lh 后手动反转
    p.z_axis *= -1.0;  // 反转 z 列(简化版)
    p
}

fn setup_reversed_z() {
    unsafe {
        // 1. 选 float depth buffer 格式
        // (在创建 framebuffer 时)
        // gl::RenderbufferStorage(gl::RENDERBUFFER, gl::DEPTH_COMPONENT32F, w, h);

        // 2. 清深度用 0(reversed-Z 的 far)
        gl::ClearDepth(0.0);

        // 3. 深度测试:大的优先
        gl::DepthFunc(gl::GEQUAL);

        // 4. 深度写入启用
        gl::DepthMask(gl::TRUE);
        gl::Enable(gl::DEPTH_TEST);
    }
}

fn render(camera: &Camera) {
    let proj = reversed_z_perspective(
        camera.fov_y, camera.aspect, camera.near, camera.far
    );
    let view = camera.view();
    let vp = proj * view;

    unsafe {
        gl::Clear(gl::DEPTH_BUFFER_BIT);
        // shader.use_program();
        // shader.set_uniform("u_mvp", vp);
        // mesh.draw();
    }
}
```

**关键解释**:
- `glClearDepth(0.0)` — 清深度 buffer 用 0(reversed-Z 的 far plane),不是传统的 1.0
- `glDepthFunc(gl::GEQUAL)` — 深度 >= buffer 的通过(reversed-Z:大的 = 近的)
- `perspective_lh` 后反转 z_axis 是简化做法,严格应用 reversed-Z 投影矩阵公式
- 注意:reversed-Z 必须配合 `glClipControl(GL_LOWER_LEFT, GL_ZERO_TO_ONE)`(OpenGL 4.5+)让 NDC z 范围变 [0, 1]

### Rust:Z 变换调试工具

```rust
// Cargo.toml: gl = "0.14", glam = "0.29"

use glam::{Mat4, Vec3, Vec4};

/// Debug Z 变换的工具
pub struct ZDebugger {
    pub near: f32,
    pub far: f32,
}

impl ZDebugger {
    pub fn linear_z_to_buffer(&self, z_camera: f32) -> f32 {
        // 线性映射:z ∈ [near, far] → [0, 1]
        (z_camera - self.near) / (self.far - self.near)
    }

    pub fn perspective_z_to_buffer(&self, z_camera: f32) -> f32 {
        // 非线性映射(perspective projection)
        let a = z_camera * (self.far + self.near);
        let b = 2.0 * self.far * self.near;
        let c = z_camera * (self.far - self.near);
        (a - b) / c  // 标准化到 [-1, +1] 的中间形式
    }

    pub fn print_z_distribution(&self) {
        println!("Z buffer distribution (perspective projection):");
        println!("  Camera Z  |  Buffer Z");
        println!("  --------- | ---------");
        // 用对数采样:近处密,远处疏
        for i in 0..20 {
            let t = i as f32 / 19.0;
            // 对数采样
            let z_camera = self.near * (self.far / self.near).powf(t);
            let z_buffer = self.perspective_z_to_buffer(z_camera);
            let bar = "█".repeat(((z_buffer + 1.0) * 25.0) as usize);
            println!("  {:9.4} | {:.6} {}", z_camera, z_buffer, bar);
        }
    }
}

pub fn assert_matrix_inverse_correctness(m: Mat4, label: &str) {
    let inv = m.inverse();
    let identity = inv * m;

    // 验证 inv * m ≈ I
    let expected = Mat4::IDENTITY;
    let max_err = (identity.to_cols_array().iter()
        .zip(expected.to_cols_array().iter())
        .map(|(a, b)| (a - b).abs())
        .fold(0.0f32, f32::max));

    println!("Matrix {} inverse check: max error = {:.2e}", label, max_err);
    if max_err > 1e-4 {
        eprintln!("WARNING: Matrix inverse has large error!");
    }
}

fn main() {
    let debugger = ZDebugger { near: 0.1, far: 100.0 };
    debugger.print_z_distribution();

    // 看近处精度:0.1m 和 0.2m 对应的 buffer Z 差多少
    let z1 = debugger.perspective_z_to_buffer(0.1);
    let z2 = debugger.perspective_z_to_buffer(0.2);
    let z10 = debugger.perspective_z_to_buffer(10.0);
    let z11 = debugger.perspective_z_to_buffer(11.0);
    println!("\nZ precision analysis:");
    println!("  ΔZ=0.1 at z=0.1m:  buffer Δ = {:.6}", (z2 - z1).abs());
    println!("  ΔZ=1.0 at z=10m:   buffer Δ = {:.6}", (z11 - z10).abs());
    // 应该看到近处 Δ >> 远处 Δ

    // 验证矩阵求逆精度
    let proj = Mat4::perspective_lh(
        std::f32::consts::FRAC_PI_4, 16.0 / 9.0, 0.1, 100.0,
    );
    assert_matrix_inverse_correctness(proj, "Projection");

    let view = Mat4::look_at_lh(
        Vec3::new(0.0, 5.0, 0.0),
        Vec3::new(0.0, 0.0, 0.0),
        Vec3::new(0.0, 0.0, 1.0),
    );
    assert_matrix_inverse_correctness(view, "View");

    let vp = proj * view;
    assert_matrix_inverse_correctness(vp, "VP");

    // 反推测试
    let inv_vp = vp.inverse();
    let ndc = Vec4::new(0.0, 0.0, -1.0, 1.0);  // NDC (0, 0, -1) = near plane center
    let world = inv_vp * ndc;
    let world = world / world.w;
    println!("\nScreen center (0,0) at near plane → World ({:.3}, {:.3}, {:.3})",
        world.x, world.y, world.z);
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
