
# Day 415 · 逐图元光照样本

> 之前的光照采样是"每个像素采 N 次"。今天 Casey 改成**每个图元(primitive)采 M 次,然后图元内所有像素共享这 M 个采样结果**。这把光照成本从"像素数 × N"降到"图元数 × M",通常降两个数量级。

## 0 · 为什么要有这一天

具体场景:你的屏幕 1920x1080,大约 200 万像素。每个像素做 16 次光照采样(为了柔和阴影),总共 3200 万次 ray-cast。CPU 上每帧 16 毫秒,光这一项就要吃掉大部分时间。

但你想:这 200 万像素中,**很多像素在同一个三角形上**——一个 100x100 像素的大墙,有 1 万像素,但只有 1 个三角形。光照采样在这 1 万像素上做几乎一样的事(从墙上的点看向光源),结果几乎一样。重复计算 1 万次没意义。

**逐图元采样**的核心思想:每个三角形采 M 个点(三角形内随机位置),对这 M 个点做光照计算(包括遮挡测试),然后**三角形内所有像素共享这个结果**。

这样成本从 `pixels × N = 2M × 16 = 32M` 降到 `primitives × M = 10K × 16 = 160K`,快 200 倍。这就是工业渲染器的标准做法——**G-Buffer + Deferred Shading** 是它的 GPU 版本。

代价:**图元内的光照变化丢失**。如果三角形很大(墙),它的不同部分应该有不同的阴影(边缘软),但共享 M 个采样后,所有像素用同一个平均值,阴影看起来"贴在三角形上"而不是"贴在墙上"。所以三角形必须足够小。

Casey 的 HH 项目,三角形是手工拼装的小方块,适合这个方法。大场景可能需要把大三角形细分成小的(subdivide)。

心理锚点:今天之后,你能解释 Deferred Shading 的原理,知道为什么 G-Buffer 是 1920x1080 的几张纹理,能用 Rust 实现逐图元采样的核心逻辑,理解工业 GPU 渲染管线的本质优化。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 重构了光照计算的循环结构。之前是:

```
for each pixel:
    for each light:
        for each sample in N:
            cast ray
```

改成:

```
for each primitive (triangle/quad):
    sample M points on the primitive surface
    for each light:
        for each sample in M:
            cast ray
    average the M results -> primitive_light
    for each pixel covered by this primitive:
        use primitive_light
```

具体动作:

1. **光照缓冲区**:加一个 `primitive_lights: Vec<Vec3>`,每个图元一个光照值
2. **光照计算阶段**:在光栅化之前,遍历所有图元,算每个图元的光照
3. **光栅化阶段**:光栅化时直接查 `primitive_lights[i]`,不再每像素算光照
4. **图元采样**:每个图元采 M = 4 个点(重心坐标均匀分布)

Casey 强调:**采样位置很重要**。如果 M = 4 都采在三角形中心,等于 M = 1,失去意义。必须**分散采样**——三角形内均匀分布,或分层随机。

## 2 · 心智模型

### 类比:民意调查

想象你做民意调查,问"这个城市的居民支持率如何"。两种方法:

- **逐人调查**(per-pixel):问城市每个居民。1000 万居民问 1000 万次,精确但贵
- **抽样调查**(per-primitive):把城市分成 100 个区,每区抽 4 人,问 400 次,然后**每个区的居民共享这 4 人结果**

抽样快 25000 倍,但精度低——同区居民被假设意见相同。如果区内居民意见分歧大(区是异质的),抽样结果失真。

逐图元光照完全同构。**图元 = 区**,**像素 = 居民**,**光照计算 = 民调**。如果图元内光照变化大(在大三角形上,接近阴影边缘),逐图元采样失真。

工业解决方案:**让图元足够小**——细分大三角形,让每个图元内的光照变化可以忽略。

### 严谨原理:重心坐标采样

在三角形上采样,标准方法是**重心坐标(barycentric coordinates)**。三角形顶点 A、B、C,任意内部点 P 可以表达为:

```
P = α*A + β*B + γ*C
α + β + γ = 1
α, β, γ ≥ 0
```

均匀采样:在 `(α, β)` 空间内均匀取点,但要保证 `α ≥ 0, β ≥ 0, α + β ≤ 1`。

标准算法:

```
r1, r2 = uniform_random_01(), uniform_random_01()
if r1 + r2 > 1:
    r1 = 1 - r1
    r2 = 1 - r2
α = r1
β = r2
γ = 1 - α - β
P = α*A + β*B + γ*C
```

这个 `if` 是必要的——直接在单位正方形采样,有一半的点会落在三角形外。`if` 把外面的点翻折回来。

### 矩形上采样

HH 的图元大多是矩形(墙、地板),不是三角形。矩形参数化:

```
P = min + (max - min) * Vec2(u, v)
u, v ∈ [0, 1]
```

网格采样:`u = (i + 0.5) / M_x`,`v = (j + 0.5) / M_y`,i = 0..M_x, j = 0..M_y。

### 光照计算公式

每个采样点 P,计算:

```
total_light = ambient
for each light:
    if not occluded(P, light):
        contribution = light.intensity * dot(normal, light_dir) / distance²
        total_light += contribution
primitive_light = average(total_light for each P)
```

所有像素共享 `primitive_light`。

### Rust 视角

```rust
pub struct PrimitiveLightingResult {
    pub primitive_id: u32,
    pub diffuse: Vec3,
    pub specular: Vec3,
}

pub fn compute_primitive_lighting(
    primitive: &Primitive,
    lights: &[Light],
    occlusion_test: &impl Fn(Vec3, Vec3) -> bool,
    samples_per_primitive: u32,
) -> PrimitiveLightingResult {
    let mut accum_diffuse = Vec3::ZERO;
    let mut accum_specular = Vec3::ZERO;
    let n = samples_per_primitive;
    for i in 0..n {
        for j in 0..n {
            let u = (i as f32 + 0.5) / n as f32;
            let v = (j as f32 + 0.5) / n as f32;
            let p = primitive.sample_point(u, v);
            let (d, s) = compute_point_lighting(p, primitive.normal, lights, occlusion_test);
            accum_diffuse += d;
            accum_specular += s;
        }
    }
    let total = (n * n) as f32;
    PrimitiveLightingResult {
        primitive_id: primitive.id,
        diffuse: accum_diffuse / total,
        specular: accum_specular / total,
    }
}
```

`sample_point(u, v)` 是图元方法,矩形返回 `min + (max - min) * (u, v, 0)`,三角形返回重心坐标插值。

### 性能数字

假设 10000 个图元,M = 4,8 个光源:

- 之前(per-pixel):2M pixels × 8 lights × 4 samples × 1 ray-cast = 64M ray-casts
- 现在(per-primitive):10K prims × 4 samples × 8 lights × 1 ray-cast = 320K ray-casts
- 加速:200x

实际可能 50-100x(光栅化本身有成本),但仍然是巨大的提升。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业的 per-primitive lighting:

- **Forward Rendering**:per-pixel(传统),每个像素算光照
- **Deferred Shading**:per-pixel,但光照在屏幕空间一次性算(用 G-Buffer)
- **Forward+ / Clustered Forward**:把屏幕分块,每块只算影响该块的光源
- **Visibility Buffer**:类似 Deferred,但用图元 ID,光照后算

Casey 的方法在工业叫 **per-vertex lighting**(如果在顶点采样)或 **per-primitive lighting**(如果在图元采样)。这是 Gouraud shading(1971)的现代化,简单但失真。

工业游戏用 per-pixel,但 GPU 并行度高,200 万像素的光照在 GPU 上不算什么。CPU 上必须 per-primitive。

### 3.2 · 🎨 图形学视角

数学上,逐图元采样是**有限采样近似积分**:

```
L(primitive) = (1/N) Σ L(sample_i) ≈ ∫∫ L(p) dA / Area
```

如果 N 足够大,这是无偏估计。N=4 时方差大,但比 per-pixel 的 N=16 平均,**每个图元的精度**反而高(N=4 vs N=16 平均 = 等价于该图元 16 个采样,因为 4 个采样覆盖整个图元面积)。

工业 GPU 的 G-Buffer 实际是 per-pixel,因为 GPU 算力够,但思路是分离**几何阶段**和**光照阶段**——和 Casey 一样。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的 per-CPU 变量是类似思想:

- 每变量 N 个副本(N = CPU 核心数)
- 每个核心访问自己的副本,无锁
- 全局视图聚合所有副本

类比:per-CPU = per-primitive(每核心一份),per-thread = per-pixel(每线程一份)。前者减少共享,后者精确但慢。

### 3.4 · 🦀 Rust 生态视角

Rust 表达逐图元光照:

```rust
use rayon::prelude::*;

pub fn compute_all_primitive_lighting(
    primitives: &[Primitive],
    lights: &[Light],
    occlusion: &impl Fn(Vec3, Vec3) -> bool + Sync,
) -> Vec<PrimitiveLightingResult> {
    primitives.par_iter().map(|p| {
        compute_primitive_lighting(p, lights, &occlusion, 4)
    }).collect()
}
```

`rayon` 的 `par_iter` 自动并行化,每个图元独立计算。Rust 的 ownership 保证 `occlusion` 是 `Sync`,多线程安全。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 per-primitive lighting 在大三角形上效果差?具体说,什么时候会出现"光照贴在三角形上"的视觉伪影?

**参考解答**:per-primitive 假设整个图元的光照均匀(用 M 个采样的平均值代表)。如果三角形很大,**内部光照实际有变化**(比如三角形跨越阴影边界,一半亮一半暗),M 个采样的平均值是中间灰,贴到所有像素,看起来"光照贴在三角形上",失去真实感。

具体场景:一个 5x5 米的墙三角形,光源在三角形中心正前方,墙上有一个 1x1 米的物体挡光,形成阴影。墙的左半亮(直接受光),右半暗(在阴影里)。per-primitive 用 4 个采样,如果采到 2 个亮 2 个暗,平均是中等亮度,贴到所有像素——整面墙看起来中等灰,没有阴影边界。

解决:细分三角形,让每个小三角形内的光照变化可以忽略。

```rust
use glam::Vec3;
use std::time::Instant;

#[derive(Copy, Clone)]
pub struct Quad {
    pub min: Vec3,
    pub max: Vec3,
    pub normal: Vec3,
}

impl Quad {
    pub fn sample_point(&self, u: f32, v: f32) -> Vec3 {
        Vec3::new(
            self.min.x + (self.max.x - self.min.x) * u,
            self.min.y + (self.max.y - self.min.y) * v,
            self.min.z,
        )
    }
    pub fn area(&self) -> f32 {
        let d = self.max - self.min;
        d.x * d.y
    }
}

pub struct PointLight {
    pub pos: Vec3,
    pub color: Vec3,
}

pub fn compute_per_primitive(
    quads: &[Quad],
    lights: &[PointLight],
    samples: u32,
    occlusion: impl Fn(Vec3, Vec3) -> bool,
) -> Vec<Vec3> {
    let n = samples;
    quads.iter().map(|q| {
        let mut accum = Vec3::ZERO;
        for i in 0..n {
            for j in 0..n {
                let u = (i as f32 + 0.5) / n as f32;
                let v = (j as f32 + 0.5) / n as f32;
                let p = q.sample_point(u, v);
                for light in lights {
                    let dir = light.pos - p;
                    let dist2 = dir.length_squared();
                    if dist2 < 1e-6 { continue; }
                    let n_dot_l = q.normal.dot(dir.normalize()).max(0.0);
                    if n_dot_l == 0.0 { continue; }
                    if occlusion(p, light.pos) { continue; }
                    accum += light.color * n_dot_l / dist2;
                }
            }
        }
        accum / (n * n) as f32
    }).collect()
}

pub fn compute_per_pixel(
    quads: &[Quad],
    pixels_per_quad: u32,
    lights: &[PointLight],
    samples: u32,
    occlusion: impl Fn(Vec3, Vec3) -> bool,
) -> u64 {
    // 模拟:每图元 pixels_per_quad 个像素,每像素 samples 个采样
    let mut total_rays = 0u64;
    for q in quads {
        for _ in 0..pixels_per_quad {
            for _ in 0..samples {
                for _ in lights {
                    total_rays += 1;
                }
            }
        }
    }
    total_rays
}

fn main() {
    let quads: Vec<Quad> = (0..1000).map(|i| Quad {
        min: Vec3::new(i as f32, 0.0, 0.0),
        max: Vec3::new(i as f32 + 1.0, 1.0, 0.0),
        normal: Vec3::Z,
    }).collect();
    let lights = vec![
        PointLight { pos: Vec3::new(500.0, 2.0, 5.0), color: Vec3::ONE },
    ];

    let t1 = Instant::now();
    let _ = compute_per_primitive(&quads, &lights, 4, |_, _| false);
    let per_prim_time = t1.elapsed();
    let per_prim_rays = (1000 * 4 * lights.len()) as u64;
    println!("Per-primitive: {:?}, {} rays", per_prim_time, per_prim_rays);

    let per_pixel_rays = compute_per_pixel(&quads, 1000, &lights, 4, |_, _| false);
    println!("Per-pixel equivalent: {} rays (no actual run)", per_pixel_rays);

    let speedup = per_pixel_rays as f64 / per_prim_rays as f64;
    println!("Speedup: {:.1}x fewer ray-casts", speedup);
}
```

## 8 · Rust / Arch 落地代码

```rust
use glam::Vec3;
use rayon::prelude::*;

#[derive(Copy, Clone)]
pub struct Quad {
    pub min: Vec3,
    pub max: Vec3,
    pub normal: Vec3,
    pub id: u32,
}

impl Quad {
    pub fn sample_point(&self, u: f32, v: f32) -> Vec3 {
        Vec3::new(
            self.min.x + (self.max.x - self.min.x) * u,
            self.min.y + (self.max.y - self.min.y) * v,
            self.min.z,
        )
    }
}

pub struct PointLight {
    pub pos: Vec3,
    pub color: Vec3,
    pub intensity: f32,
}

pub struct Scene {
    pub quads: Vec<Quad>,
    pub lights: Vec<PointLight>,
}

impl Scene {
    pub fn compute_primitive_lighting(&self, samples: u32) -> Vec<Vec3> {
        let n = samples;
        // 用 rayon 并行,每个图元独立计算
        self.quads.par_iter().map(|q| {
            let mut accum = Vec3::ZERO;
            for i in 0..n {
                for j in 0..n {
                    let u = (i as f32 + 0.5) / n as f32;
                    let v = (j as f32 + 0.5) / n as f32;
                    let p = q.sample_point(u, v);
                    for light in &self.lights {
                        let dir = light.pos - p;
                        let dist2 = dir.length_squared();
                        if dist2 < 1e-6 { continue; }
                        let n_dot_l = q.normal.dot(dir / dist2.sqrt()).max(0.0);
                        if n_dot_l == 0.0 { continue; }
                        // 假设无遮挡
                        accum += light.color * light.intensity * n_dot_l / dist2;
                    }
                }
            }
            accum / (n * n) as f32
        }).collect()
    }
}

fn main() {
    let scene = Scene {
        quads: (0..5000).map(|i| Quad {
            min: Vec3::new(i as f32 * 1.0, 0.0, 0.0),
            max: Vec3::new(i as f32 * 1.0 + 1.0, 1.0, 0.0),
            normal: Vec3::Z,
            id: i,
        }).collect(),
        lights: vec![
            PointLight { pos: Vec3::new(100.0, 5.0, 5.0), color: Vec3::ONE, intensity: 100.0 },
            PointLight { pos: Vec3::new(1000.0, 5.0, 5.0), color: Vec3::ONE, intensity: 100.0 },
        ],
    };

    let start = std::time::Instant::now();
    let lighting = scene.compute_primitive_lighting(4);
    let elapsed = start.elapsed();
    println!("Computed lighting for {} primitives in {:?}",
        scene.quads.len(), elapsed);
    println!("First quad lighting: {:?}", lighting[0]);
    println!("Sample lighting: {:?}", lighting[scene.quads.len() / 2]);

    println!("\nRay casts: {} (vs per-pixel ~{})",
        scene.quads.len() * 4 * 4 * scene.lights.len(),
        1920 * 1080 * 4 * scene.lights.len());
}
```

**Troubleshooting**:

- **rayon 报 Send/Sync 错误** —— `Scene` 内部 `Vec<Quad>` 是 Sync,但闭包捕获要小心
- **图元 ID 错位** —— 并行 `par_iter` 顺序不确定,但 `collect` 后顺序与输入一致
- **采样都在中心** —— `(i + 0.5) / n` 必须 +0.5,不能 `i / n`(会采到边界)
- **法线点积负** — `.max(0.0)` clamp,背面不收光


### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
