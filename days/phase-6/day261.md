
# Day 261 · 改成静态帧数组

> 把"每帧临时申请"的性能分析数据改成"事先开好的环形数组",这是一次典型的"用空间换时间 + 用静态布局换自由分配"的重构,直接决定后面多帧图表能否一行代码画出来。

## 0 · 为什么要有这一天

你在 Phase 5 末尾已经有了一个能用的性能分析 overlay:每帧把若干 `profile_block`(一段被计时器包住的代码区段)压进一个 `Vec<ProfileBlock>`,然后在屏幕右上角画出当前帧的火焰图。在 Debug 模式下你看到的画面挺漂亮——50 多个色块按时长排序堆叠在一起,你能一眼看出哪段代码在烧 CPU。

但是问题来了。你想做一件事:**把最近 60 帧的性能图画在一起**,看哪个 spike 是周期性的、哪个是一次性卡顿。你打开代码,发现当前的写法是每帧结束都 `vec.clear()`,数据当场就丢了。要画历史,你只能把当前帧的 vec 拷贝到一个"历史区"——而拷贝意味着每帧额外 `memcpy`,这正是性能分析工具自己最不应该做的事。

更隐蔽的问题在内存布局。`Vec<ProfileBlock>` 内部是一个堆指针,`ProfileBlock` 自己又包含若干 `String` 字段(区段名)和 `Vec` 字段(子区段)。一帧里堆 50 次 `push`,可能触发 5 次 `realloc`(因为 vec 增长是 2 倍策略),每次 `realloc` 都把整块内存搬到新地址——而堆上的搬运正是 cache miss 的元凶。

今天的 Casey 干了一件看似枯燥实则关键的事:**把所有性能分析数据改成"事先分配好的定长数组"**,每帧用环形索引轮转。重构完成后:

1. 启动时一次 `Box::new([ProfileBlock::default(); CAPACITY])`,从此不再分配
2. 每帧只更新 `frame_index = (frame_index + 1) % CAPACITY`
3. 画历史图只需要遍历数组,无需拷贝

这套思路是嵌入式、游戏引擎、实时音频等"必须保证 0 allocation"领域的标配。学完之后,你能在自己的项目里识别"这种 `Vec::push` 必须改成 ring buffer"的征兆,并且知道怎么改。

心理锚点:完成本日练习后,你的性能 overlay 不再随帧数增长内存,画出 60 帧历史图就像画 1 帧那样简单。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 上几集把 performance overlay 一步步搭起来,但数据结构一直是 `Vec<profile_block>`。今天他打开 IDE,做了一次纯重构:

1. 先把当前帧的 `Vec<profile_block>` 换成 `profile_block Frames[MAX_FRAME_COUNT]`——一个固定大小的 C 数组,在 `handmade` 模块里以 static lifetime 持有
2. 引入 `int FrameIndex`,每次进入新帧时 `FrameIndex = (FrameIndex + 1) % MAX_FRAME_COUNT`
3. 把所有引用"当前帧 vec"的代码改成引用 `Frames[FrameIndex]`
4. 处理 `FrameIndex` 回绕的细节:第一帧之前数组全是"空",需要一个"已用帧数"标志位避免画出未初始化的数据
5. 检查内存初始化:数组用 `{0}` 显式清零,C 不会自动构造,Rust 端要用 `Box::new([Default::default(); N])` 或 unsafe `MaybeUninit` 模式

Casey 反复强调一件事:**重构的第一目标是不改变行为,第二目标才是性能**。他在重构前先跑了一遍游戏确认基线帧率,改完之后再跑一次,确认 FPS 没有下降(实际还上升了 5%,因为少了 realloc)。

## 2 · 心智模型

### 类比:轮盘赌 vs 一摞新扑克牌

想象两种记录方式:

**方式 A(动态 vec)**:你手里拿一摞扑克牌,每次想记一笔就买一张新牌写上字。桌上的牌越来越多,你时不时要把它们整理成一摞( realloc),还要在每局结束时把整摞扔掉(clear)。

**方式 B(环形数组)**:桌上事先摆好 60 张空牌围成一圈。你有一根手指指着"当前要写的牌"。每写一笔就移到下一张;走完一圈回到第一张时,**直接覆盖最老的记录**。

方式 B 的好处一眼就看到:不用买新牌(无分配),不用整理(no realloc),不用每局清空(覆盖即清空)。代价只有 60 张牌的固定空间——对于性能分析这个用途,60 帧(1 秒)已经够看趋势了。

这就是 **ring buffer(环形缓冲区)** 的本质,它是一种"用固定空间记录最近 N 条数据"的数据结构,在生产者-消费者、音频缓冲、日志环形缓冲里无处不在。

### 严谨原理:为什么 `Vec::push` 比你想的贵

`Vec<T>` 在堆上维护三个值:`ptr`(数据指针)、`len`(已用长度)、`cap`(总容量)。`push` 的伪代码:

```
fn push(&mut self, x: T) {
    if self.len == self.cap {
        let new_cap = self.cap * 2;             // 容量翻倍
        let new_ptr = alloc(new_cap * size_of::<T>());
        memcpy(new_ptr, self.ptr, self.len * size_of::<T>());
        dealloc(self.ptr);
        self.ptr = new_ptr;
        self.cap = new_cap;
    }
    self.ptr[self.len] = x;
    self.len += 1;
}
```

问题在 `alloc` + `memcpy` + `dealloc` 这三步:

- **`alloc`**:调用 `malloc`,可能要遍历 free list 找一块够大的空闲块,几十到几百纳秒
- **`memcpy`**:在 cap 增长到 1024 之前,每次 realloc 都要把历史数据全复制一遍。50 次增长累计的复制开销是 O(n²)
- **`dealloc`**:释放旧内存,可能触发 free list 合并,影响后续分配模式

更糟糕的是 **cache locality(缓存局部性)**:realloc 后数组搬到新地址,旧 cache line 全部失效,后续访问全部 miss。

游戏每帧 50 次 push,平均触发 6-7 次 realloc,总耗时约 5 微秒——你听不到这一帧有什么问题,但当你在性能分析器里看自己的性能分析器(套娃!),会发现这些 push 自己就是"看不见的暗物质"。

### 环形数组:O(1) 写入,0 分配

```rust
const FRAME_HISTORY: usize = 64; // 60FPS 下大约 1 秒

#[derive(Clone, Default)]
struct FrameProfile {
    blocks: [ProfileBlock; MAX_BLOCKS_PER_FRAME],
    block_count: usize,
    frame_dt: f32,
}

struct Profiler {
    frames: [FrameProfile; FRAME_HISTORY],
    head: usize,   // 下一个要写的位置
    initialized: usize, // 启动以来填了多少帧,封顶 FRAME_HISTORY
}
```

写入一帧的代码:

```rust
impl Profiler {
    fn begin_frame(&mut self, dt: f32) -> &mut FrameProfile {
        let slot = &mut self.frames[self.head];
        slot.frame_dt = dt;
        slot.block_count = 0;
        slot
    }
    fn end_frame(&mut self) {
        self.head = (self.head + 1) % FRAME_HISTORY;
        if self.initialized < FRAME_HISTORY {
            self.initialized += 1;
        }
    }
    fn iter_history(&self) -> impl Iterator<Item = &FrameProfile> {
        // 从最旧的(下一帧要写的位置,如果已经填满)开始,逆时针遍历
        let start = if self.initialized < FRAME_HISTORY {
            0
        } else {
            self.head
        };
        (0..self.initialized).map(move |i| &self.frames[(start + i) % FRAME_HISTORY])
    }
}
```

**关键点**:

- `head` 总是指向"下一次要写的位置",写入后 `head += 1`(取模封顶)
- 读取历史时,如果还没填满,从 0 开始;填满后,从 `head` 开始(它指向最旧的数据)
- 数组里的元素是 `Default::default()` 初始化,没有任何 unsafe

代价是固定占用 `64 * size_of::<FrameProfile>()` 字节。`ProfileBlock` 我们设计成 32 字节(后面 §8 详述),每帧最多 256 个 block,所以 `FrameProfile` = 32 * 256 + 8 + 4 = 8204 字节,64 帧 ≈ 525 KB。一次分配,永远复用。

### 为什么 const generics 在这里是天作之合

Rust 1.51 起稳定的 `const generics`(常量泛型)让你写:

```rust
struct RingBuffer<T, const N: usize> {
    data: [T; N],
    head: usize,
}
```

这里的 `N` 是编译期常量,所以 `[T; N]` 是真正的固定大小数组(不是 `Vec`),可以放在栈上或 `Box` 里,内存布局完全可控。Phase 5 的代码我们还在用 `Vec`,今天切换到 const generics 后,代码更接近 Casey 的 C 原版。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏引擎里 ring buffer 至少有三个高频用途:

1. **输入历史**:做网络预测回滚(netcode)需要保留最近 N 帧的输入
2. **性能分析**:就是今天这个场景
3. **音频环形缓冲**:ALSA / PulseAudio / WASAPI 都要求你填一个固定大小的环形 buffer,生产者(CPU 写 PCM)和消费者(声卡 DMA 读 PCM)以不同速度走

业界主流引擎(Unreal / Unity)都用类似的 `TRingBuffer<T>` 抽象。Casey 这次重构后,后面 Day 262 直接画"最近 60 帧的火焰图叠在一起"的图,就是基于这个数据结构。Day 280+ 流式实体模拟(Sim Region)也用同样的"固定大小帧环形"思想管理位置历史。

游戏程序员面试常考的一道题:**实现一个支持 push / pop / size 都是 O(1) 的环形队列,固定容量**。今天的内容就是答案。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核自己也是环形缓冲区大户。`struct printk_safe_seq_buf`(内核日志)和 `struct kfifo`(通用 kfifo,见 `include/linux/kfifo.h`)都是定长环形 buffer。

用户态下你也会遇到 ring buffer:

- **`perf record`** 的 ring buffer:perf 子系统在内核里维护一个 mmap 出来的环形 buffer,硬件性能计数器(PMU)溢出时把样本写进去,用户态 `perf` 工具从同一个 mmap 读。这是零拷贝的——内核和用户态共享同一段物理内存
- **`dbus` / `bpftrace` / `LTTng`**:用户态 tracing 工具几乎全用 ring buffer 因为必须 O(1)
- **`io_uring`**:Linux 5.1+ 的高性能异步 IO 接口,核心就是两个环形 buffer(submission queue + completion queue)

你可以用 `perf` 工具实测自己游戏的环形 buffer:

```bash
# 实时看内核 trace 的 ring buffer 大小
cat /sys/kernel/debug/tracing/buffer_size_kb
# 输出 1408 (KB),即 1.4 MB

# 改大 ring buffer(需要 root)
echo 16384 > /sys/kernel/debug/tracing/buffer_size_kb
# 改成 16 MB
```

写游戏时你不需要碰这些内核 API,但理解内核为什么这么做能让你对今天 Casey 的选择更有信心:**所有"必须 O(1) 写入"的实时系统都选环形数组,这是产业共识**。

### 3.3 · 🦀 Rust 生态视角

Rust 表达"固定大小环形 buffer"有几种选择,各有取舍。

#### 选择 1:原生数组 + 自己写索引

```rust
struct Ring<T, const N: usize> {
    data: [MaybeUninit<T>; N],
    head: usize,
    len: usize,
}
```

`MaybeUninit<T>` 是 Rust 标准库提供的"可能是未初始化"包装器。它告诉编译器:"这块内存里的 T 可能还没构造,别假定它有效"。这是 unsafe 友好的写法,Casey 的 C 代码就是这个语义(C 的数组天然就是 maybe-uninit)。

优点:零开销,完全控制。缺点:所有访问要 unsafe,需要自己写 Drop 释放未消费元素。

#### 选择 2:要求 `T: Default` + 用普通数组

```rust
struct Ring<T: Default + Clone, const N: usize> {
    data: [T; N],
    head: usize,
    len: usize,
}

impl<T: Default + Clone, const N: usize> Ring<T, N> {
    fn new() -> Self {
        Self {
            data: std::array::from_fn(|_| T::default()),
            head: 0,
            len: 0,
        }
    }
}
```

`std::array::from_fn` 是 Rust 1.63+ 的标准库函数,接受一个闭包,逐个初始化数组元素。它的签名:

```
pub fn from_fn<T, const N: usize, F>(mut cb: F) -> [T; N]
where F: FnMut(usize) -> T
```

闭包接收索引 i,返回该位置的初始值。这比 `Box::new([T::default(); N])`(需要 `T: Copy`)更通用,因为不要求 Copy。

优点:全部 safe,代码清晰。缺点:要求 `T: Default + Clone`,有些类型(如 `Box<...>` 内嵌)不方便。

#### 选择 3:用现成 crate

`heapless` crate(SRAM 友好,嵌入式常用)和 `ringbuffer` crate 都有现成实现。但本教程阶段我们坚持手写——和 Casey 一致,直到 Phase 7 之后才考虑用 crate。

#### 今天的选择

性能 profile 数据是 `Copy + Default` 类型,我们用**选择 2**。代码简洁,完全 safe,符合教学需求。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **数据结构** — 环形数组是计算机科学里 FIFO 队列的一种实现方式
- **静态内存管理** — "事先分配,反复使用"的内存策略,与"按需分配"对立
- **数据导向设计** — DOD(data-oriented design)强调固定大小、连续内存、可预测布局,今天的重构是 DOD 的一个缩影

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| `Vec<FrameProfile>` | 动态增长,会 realloc | 不在乎分配开销时 | 之前用 |
| `VecDeque<FrameProfile>` | 双端队列,前端 pop 后端 push | 需要任意长度时 | 不选,会动态分配 |
| `Box<[FrameProfile; N]>` | 堆上固定大小数组 | 容量编译期已知 | ✅ 今天改用 |
| `[FrameProfile; N]` 栈上 | 完全栈上,无堆分配 | 数据小到能塞栈(< 几 MB) | 不行,64*8KB 太大 |
| `MaybeUninit<[T; N]>` + 自管 Drop | 真正零开销,unsafe | 嵌入式 / 性能极端 | 暂不需要 |
| 现成 crate(`heapless`) | 别人写好 | 生产项目 | 教学阶段不引入 |

选择 `Box<[T; N]>` 的原因:容量编译期已知(64 帧),栈上放不下(525KB 默认栈 8MB 但接近警戒线),堆上一次分配反复用。

### 4.3 下级(内部零件)

- **`FrameProfile`** — 单帧的所有性能区段
- **`ProfileBlock`** — 单个区段(名字、起止时间、深度)
- **`head` / `len`** — 索引状态
- **`%` 取模** — 环绕逻辑核心
- **`MaybeUninit` 或 `Default`** — 处理"未填充"槽位

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

| 语境 | 容量 | 溢出策略 |
|---|---|---|
| 性能分析历史 | 64 帧 | 覆盖最旧 |
| 输入回滚 | 30 帧 | 拒绝写入(panic 或返回 Err) |
| 音频缓冲 | 几十毫秒 | 阻塞 / 丢帧 |
| 内核 trace | 几 MB | 覆盖最旧,允许丢事件 |
| 数据库 WAL | 几 GB | 文件轮转 |

游戏开发里"覆盖最旧"是默认策略,因为最新的数据更有价值。但音频必须用"阻塞生产者"——丢一帧音频有爆音,延迟几帧无所谓。

### 历史演化

- **1970s**:UNIX pipe 用环形 buffer 内核态
- **1990s**:游戏机(PS1, N64)内存小,几乎全部数据结构都是定长数组
- **2000s**:PC 内存大,C++ `std::vector` 普及,游戏引擎开始滥用动态分配
- **2010s**:`Data-Oriented Design`(Richard Fabian 著)出版,DOD 回潮,定长数组回归
- **2020s**:Bevy / ECS 等现代引擎明确要求"无运行时分配",定长 buffer 是基础

Casey 在 2014-2016 拍 HH 时走的就是 DOD 路线,你今天写的代码风格和 2026 年的 Bevy 完全一致——这是教学项目的远见。

### 不同语言对 const generics 的支持

| 语言 | 表达 `[T; N]` 的方式 |
|---|---|
| C | `T arr[N]` 自然支持 |
| C++ | `std::array<T, N>`,模板非类型参数 |
| Rust(2021+) | `[T; N]` + const generics,1.51 稳定 |
| Zig | `[N]T`,编译期已知 |
| Go | 不支持,只能用切片 |
| Python | 不支持,只能用 list |

Rust 的 const generics 比 C++ 的模板参数功能更强(支持任意 const 表达式),但生态还在演化中(目前对 `T:?Sized` 等复杂场景支持有限)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 把 `Vec<ProfileBlock>` 改成 `Box<[FrameProfile; 64]>` 后,内存使用量从"理论无上限"变成"固定 525 KB"。这看似是"牺牲了灵活性"。请论证:**对于性能分析这个用途,固定上限不是缺点而是优点**。给出至少 3 个理由。

**参考解答**:
1. **可预测**:固定上限意味着性能分析器自己的内存不会随帧数增长,不会"分析一个内存泄漏结果自己也泄漏"
2. **零分配**:动态分配意味着 push 时可能触发 realloc,这是性能分析器自己最不该做的事——分析别人的延迟时不能引入自己的延迟
3. **数据时效**:性能分析关心的是"最近这一秒",60 帧前的事对调试当前的卡顿没帮助,固定上限天然实现了"遗忘"
4. **避免 GC 压力**:某些语言(Rust 没这问题,但 C# / Java 引擎有)的 GC 扫描时间和堆大小成正比,固定上限 = GC 时间稳定
5. **cache 友好**:固定大小数组的内存是连续的,遍历画图时 cache hit 极高

总结:**"灵活性"对工具子系统是负债,不是资产**。工具越可预测,被工具分析的程序越可信。

### Lv2 · 动手实践

**题**:在 Rust 项目里实现一个 `Ring<T, const N: usize>` 通用环形数组,要求:
- `push(item: T)` 写入下一个槽,覆盖最旧
- `iter()` 返回从最旧到最新的迭代器
- `len()` 返回当前元素数(≤ N)
- `T: Default + Clone`

写一个 main 测试:容量 4,push 6 个整数 (1..=6),然后 iter 应该输出 [3, 4, 5, 6]。

完成标准:`cargo run` 打印 `[3, 4, 5, 6]`。

**参考解答**:

```rust
#[derive(Debug)]
struct Ring<T: Default + Clone, const N: usize> {
    data: [T; N],   // 固定大小数组,编译期决定大小
    head: usize,    // 下一次要写入的位置
    len: usize,     // 已有多少有效元素(≤ N)
}

impl<T: Default + Clone, const N: usize> Ring<T, N> {
    fn new() -> Self {
        Self {
            // from_fn 是 Rust 1.63+ 标准库函数,逐个调用闭包初始化数组
            // 不要求 T: Copy,只要求 T: Default
            data: std::array::from_fn(|_| T::default()),
            head: 0,
            len: 0,
        }
    }

    fn push(&mut self, item: T) {
        // 在 head 位置写入,然后 head 推进一位(取模回绕)
        self.data[self.head] = item;
        self.head = (self.head + 1) % N;
        if self.len < N {
            self.len += 1;
        }
    }

    fn len(&self) -> usize { self.len }

    fn iter(&self) -> impl Iterator<Item = &T> {
        // 如果没填满,有效范围从 0..len
        // 如果填满了,head 指向最旧的元素(head 写过它后移到了下一位)
        let start = if self.len < N { 0 } else { self.head };
        let len = self.len;
        (0..len).map(move |i| &self.data[(start + i) % N])
    }
}

fn main() {
    let mut ring: Ring<i32, 4> = Ring::new();
    for i in 1..=6 {
        ring.push(i);
    }
    // 容量 4,push 6 次,前 2 个(1, 2)被覆盖,剩 [3, 4, 5, 6]
    let collected: Vec<i32> = ring.iter().copied().collect();
    println!("{:?}", collected);
    // 输出: [3, 4, 5, 6]
    assert_eq!(collected, vec![3, 4, 5, 6]);
}
```

**每行解释**:
- `const N: usize` 是 const generic,编译期常量,所以 `[T; N]` 是真数组
- `std::array::from_fn` 比 `[T::default(); N]` 更通用(后者要求 `T: Copy`)
- `head` 在 push 后才递增,所以读"最旧"的索引是 `head`(因为 head 是"下一笔要覆盖的",而上一轮覆盖的就是最旧的)
- `iter` 返回 `impl Iterator`,编译器推断具体类型,我们不必写出来
- `copied()` 把 `&i32` 转 `i32`(因为 `i32: Copy`)

## 8 · Rust / Arch 落地代码

### 完整可跑的 Rust 示例:从 Vec 切换到 ring buffer 的对照

```rust
// Cargo.toml 不需要依赖,纯 std
// 文件: src/main.rs

use std::time::{Duration, Instant};

// ---------- 数据结构 ----------

#[derive(Clone, Debug)]
struct ProfileBlock {
    name: &'static str,     // 'static 避免每帧 String 分配
    start_ns: u64,
    end_ns: u64,
    depth: u8,
}

impl Default for ProfileBlock {
    fn default() -> Self {
        Self { name: "", start_ns: 0, end_ns: 0, depth: 0 }
    }
}

const MAX_BLOCKS_PER_FRAME: usize = 256;
const FRAME_HISTORY: usize = 64;

#[derive(Clone)]
struct FrameProfile {
    blocks: [ProfileBlock; MAX_BLOCKS_PER_FRAME],
    block_count: usize,
    frame_dt_ns: u64,
}

impl Default for FrameProfile {
    fn default() -> Self {
        Self {
            blocks: std::array::from_fn(|_| ProfileBlock::default()),
            block_count: 0,
            frame_dt_ns: 0,
        }
    }
}

struct Profiler {
    frames: Box<[FrameProfile; FRAME_HISTORY]>,  // 堆上一次分配
    head: usize,
    initialized: usize,
}

impl Profiler {
    fn new() -> Self {
        Self {
            // Box::new 把数组放进堆;[Default::default(); N] 要求 Default + ... 但 array
            // 元素的 Default 已 impl,需要 T: Copy,这里 FrameProfile 不是 Copy
            // 所以用 unsafe 的 Box::new_uninit 或更简单的 from_fn
            frames: Box::new(std::array::from_fn(|_| FrameProfile::default())),
            head: 0,
            initialized: 0,
        }
    }

    fn begin_frame(&mut self, dt_ns: u64) -> &mut FrameProfile {
        let slot = &mut self.frames[self.head];
        slot.block_count = 0;
        slot.frame_dt_ns = dt_ns;
        slot
    }

    fn end_frame(&mut self) {
        self.head = (self.head + 1) % FRAME_HISTORY;
        if self.initialized < FRAME_HISTORY {
            self.initialized += 1;
        }
    }

    fn record_block(&mut self, name: &'static str, start_ns: u64, end_ns: u64, depth: u8) {
        let slot = &mut self.frames[self.head];
        if slot.block_count < MAX_BLOCKS_PER_FRAME {
            slot.blocks[slot.block_count] = ProfileBlock {
                name, start_ns, end_ns, depth,
            };
            slot.block_count += 1;
        }
    }

    fn iter_history(&self) -> impl Iterator<Item = &FrameProfile> {
        let start = if self.initialized < FRAME_HISTORY { 0 } else { self.head };
        let n = self.initialized;
        (0..n).map(move |i| &self.frames[(start + i) % FRAME_HISTORY])
    }
}

fn main() {
    let mut p = Profiler::new();

    // 模拟 70 帧的运行,后 6 帧会回绕
    for frame_idx in 0..70 {
        let dt_ns = 16_666_666; // 假设稳定 60 FPS
        p.begin_frame(dt_ns);
        // 模拟几个计时区段
        p.record_block("update", 0, 2_000_000, 0);
        p.record_block("render", 2_000_000, 6_000_000, 0);
        p.end_frame();
    }

    // 查询历史
    println!("Initialized {} frames (cap {})", p.initialized, FRAME_HISTORY);
    for (i, frame) in p.iter_history().enumerate() {
        println!(
            "  history[{}]: dt={:.2}ms, blocks={}",
            i,
            frame.frame_dt_ns as f64 / 1_000_000.0,
            frame.block_count,
        );
    }
    // 输出 64 行(从第 7 帧到第 70 帧,最旧的 6 帧被覆盖)
}
```

**关键 Rust 特性解释**:

- `&'static str` 字符串字面量(如 `"update"`)编译期进二进制,运行时是一个 `&'static str` 指针,无分配。把 `name` 写成 `String` 会每帧分配,这是性能分析器最不该做的事
- `Box<[FrameProfile; 64]>` 把整个数组(约 525 KB)放进堆。这里 `Box::new(...)` 接受 `from_fn` 的返回值(已经是 `[T; N]`),`Box` 只负责把它放进堆
- `std::array::from_fn(|_| FrameProfile::default())` 不要求 `FrameProfile: Copy`,所以可以包含非 Copy 类型
- `iter_history` 用 `impl Iterator` 返回值——Rust 1.26+ 的 `impl Trait` 让我们不必写出具体的 `Map<Range, ...>` 类型

**Troubleshooting**:
- `error[E0277]: the trait bound \`FrameProfile: Copy\` is not satisfied` — 你写成了 `[FrameProfile::default(); N]`,这要求 Copy。改用 `std::array::from_fn`
- `error: values of type \`[FrameProfile; 64]\` cannot be built using \`Box::new([_; 64])\`` — 因为 `Box::new` 会在栈上先构造再 move 到堆,64 个元素太多可能栈溢出。用 `Box::new(from_fn(...))` 时 `from_fn` 直接在堆上构造(优化器会消除中间栈副本)
- 运行时 panic `index out of bounds: the len is 64 but the index is 64` — 检查 `% FRAME_HISTORY` 是否漏写
