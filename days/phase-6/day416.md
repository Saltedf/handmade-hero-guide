# Day 416 · 分离光照与几何提交

> Day 415 让光照计算独立于光栅化。今天 Casey 进一步**重构**——把"光照计算"和"几何提交到渲染器"分成两个完全独立的阶段,中间用一个 `RenderQueue` 缓冲。这是工业渲染器的标准架构,叫"渲染图元(Render Passes)"或"渲染图(Render Graph)"。

## 0 · 为什么要有这一天

你的代码现在长这样:

```
fn render_frame() {
    for entity in entities {
        let lighting = compute_lighting(entity);
        submit_geometry(entity, lighting);
    }
}
```

看起来合理,但**耦合**了三件事:

1. **场景遍历**:决定画哪些实体
2. **光照计算**:每个实体的光照
3. **几何提交**:把数据丢给 GPU 或光栅化器

耦合的问题:

- **无法重排序**:如果你想先画所有不透明物体再画透明物体,得遍历两次,但光照计算跟着遍历走,浪费
- **无法批处理**:相同材质的实体应该合并成一次绘制,但当前结构每实体单独提交
- **无法并行**:光照和提交是流式的,rayon 难以切入
- **无法缓存**:如果场景没变,光照结果应该复用,但现在每帧重算

工业的解决方案:**渲染队列(Render Queue)**。把场景遍历的输出存成 `Vec<RenderItem>`,这是渲染"待办事项"。然后:

1. **排序**:按材质、深度、透明度排序
2. **批处理**:相同材质合并
3. **光照计算**:在已排序的队列上做,可并行
4. **提交**:按顺序提交到 GPU

这就是 Casey 今天做的事。代码改动不大,但**架构跃迁**——从"立即模式渲染"到"延迟模式渲染"。

心理锚点:今天之后,你能看懂工业渲染器(vulkan render pass、bevy render graph、unreal mesh draw pipeline)的代码,理解为什么它们都用"render queue"或"render graph"模式,能在自己的渲染器里实现这个分层。

## 2 · 心智模型

### 类比:餐厅点单系统

想象一家餐厅。点菜流程:

- **耦合版**(立即模式):客人坐下,服务员直接去厨房传话,厨师做菜,做完服务员端回。简单,但服务员被绑死在这桌,无法处理别的桌。
- **解耦版**(队列模式):服务员把订单写在便签上,贴到订单板。厨师从订单板上拿单,做完放到取餐口。服务员从取餐口端菜。

解耦版的优势:

1. **批处理**:厨师一次做几份一样的菜(汉堡),效率高
2. **重排序**:VIP 客人优先,调整订单板顺序
3. **并行**:多个厨师同时做不同订单
4. **缓存**:同一道菜 5 分钟内重复点,可以复用

渲染队列完全同构。`RenderItem` = 便签,`RenderQueue` = 订单板,光照计算 = 厨师做菜,rasterize = 端菜。

### 严谨原理:三段式渲染管线

```
Phase 1: Collect (场景遍历)
    输入:entities, camera
    输出:Vec<RenderItem>
    每个 RenderItem 包含:geometry, transform, material, distance_to_camera

Phase 2: Sort & Batch (排序批处理)
    输入:Vec<RenderItem>
    输出:Vec<RenderBatch>(同材质的合并)
    排序键:material_id, depth

Phase 3: Compute Lighting (光照计算)
    输入:Vec<RenderBatch>
    输出:Vec<LightingResult>
    可并行(rayon)

Phase 4: Submit (提交到光栅化器/GPU)
    输入:Vec<RenderBatch>, Vec<LightingResult>
    输出:像素
    按顺序绘制
```

每阶段的输入输出明确,可以独立测试、独立优化、独立替换。

### RenderItem 数据结构

```rust
#[derive(Clone)]
pub struct RenderItem {
    pub geometry_id: u32,       // 引用 vertex/index buffer
    pub transform: Mat4,         // 世界矩阵
    pub material_id: u32,        // 引用 shader 和纹理
    pub bounding_sphere: Vec4,   // 视锥剔除用
    pub depth: f32,              // 排序用,距相机距离
    pub flags: RenderFlags,      // 透明、双面等
}

#[derive(Clone, Copy, Default)]
pub struct RenderFlags: u8 {
    const TRANSPARENT = 1 << 0;
    const DOUBLE_SIDED = 1 << 1;
    const CAST_SHADOW = 1 << 2;
    const RECEIVE_SHADOW = 1 << 3;
}
```

`bitflags` 让多个布尔标志紧凑存在一个 byte。Rust 用 `bitflags` crate 自动生成接口。

### 排序策略

不同 pass 的排序键不同:

- **不透明 pass**:按 depth 升序(近的先画,利用 early-z 剔除)
- **透明 pass**:按 depth 降序(远的先画,保证混合正确)
- **同 depth**:按 material_id(减少状态切换)

`sort_by_key(|item| (item.pass, item.material_id, item.depth_bits))` 一次完成。

### Rust 视角

```rust
pub struct RenderQueue {
    items: Vec<RenderItem>,
}

impl RenderQueue {
    pub fn new() -> Self { Self { items: Vec::new() } }

    pub fn push(&mut self, item: RenderItem) {
        self.items.push(item);
    }

    pub fn sort(&mut self) {
        self.items.sort_unstable_by_key(|item| {
            // 透明物体排到最后(用倒序 depth)
            // 不透明物体按 depth 升序,同 depth 按 material
            let pass = if item.flags.contains(RenderFlags::TRANSPARENT) { 1 } else { 0 };
            let depth_key = if item.flags.contains(RenderFlags::TRANSPARENT) {
                // 透明:倒序,大的先(远的先画)
                (item.depth * -1000.0) as i32
            } else {
                // 不透明:正序,小的先(近的先画,early-z)
                (item.depth * 1000.0) as i32
            };
            (pass, item.material_id, depth_key)
        });
    }

    pub fn iter(&self) -> impl Iterator<Item = &RenderItem> {
        self.items.iter()
    }

    pub fn drain(self) -> Vec<RenderItem> {
        self.items
    }
}
```

`sort_unstable_by_key` 比 `sort_by_key` 快(不保证相等元素的相对顺序,但渲染队列里相等元素本身无意义)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业的渲染队列:

- **Unity SRP(Scriptable Render Pipeline)**:`RenderQueue` 标签 + 自定义 pass
- **Unreal Mesh Draw Pipeline**:ParallelMeshDrawList,多线程收集
- **Bevy Render Phase**:每相机的 `RenderPhase`,排序后批处理
- **Godot RenderingDevice**:Vulkan-style render pass

所有现代引擎都走这条路。原因:**GPU 状态切换极贵**(切 shader 100us,切纹理 50us),批处理节省的成本比单个绘制还多。

### 3.2 · 🎨 图形学视角

数学上,渲染队列是**图的拓扑排序**:

- 节点 = render pass
- 边 = 数据依赖(pass A 的输出是 pass B 的输入)
- 拓扑排序保证依赖顺序正确

工业的 Render Graph(如 Unreal RDG、Bevy render graph、vkguide render graph)把这个图自动化——你声明 pass 和依赖,框架算出最优顺序、自动管理资源。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的 **IO 调度器**完全同构:

- 进程发 IO 请求 → 内核放进 IO 队列(类似 RenderQueue.push)
- 调度器排序(类似 sort):deadline、cfq、bfq 等算法
- 提交到磁盘(类似 rasterize)

IO 调度的目标:减少磁盘寻道(类似减少 GPU 状态切换)。同一个磁盘块上的请求合并,不同块的请求按物理位置排序。

### 3.4 · 🦀 Rust 生态视角

Bevy 的渲染队列示例:


Bevy 的 `PhaseItem` 是 trait,定义 sort_key 和 render 方法。Casey 的 HH 是简化版,但模式相同。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不透明物体按 depth 升序(近的先画),透明物体按 depth 降序(远的先画)?

**参考解答**:**深度测试**和**混合**的工作方式不同。

不透明物体:每个像素写入时,深度缓冲检查"已有深度 vs 新深度",新深度近的覆盖。如果**先画远的**,它的像素写入,然后**画近的**,近的覆盖远的——但远的写入是浪费(必被覆盖)。所以**先画近的**(利用 early-z),近的写入深度缓冲,远的被深度测试直接丢弃,不写入颜色,**省 pixel shader 成本**。

透明物体:深度测试写入,但**颜色混合**(alpha blending)需要"已有颜色 × (1 - alpha) + 新颜色 × alpha"。如果先画近的,颜色写入;再画远的,远的颜色与已有混合——但**远的被近的挡住,应该看不见!**深度测试丢弃它,但深度测试只看深度(透明物体在更远位置,深度测试通过),所以远的不被丢弃,错误地参与混合。

正确做法:**远的先画**(按 depth 降序),写入颜色;**近的后画**,近的颜色与已有混合,正确的透明效果。深度测试仍然工作(写入深度),但顺序保证了视觉正确。

```rust
use glam::{Mat4, Vec4};
use bitflags::bitflags;

bitflags! {
    #[derive(Clone, Copy, Default)]
    pub struct RenderFlags: u8 {
        const TRANSPARENT = 1 << 0;
        const DOUBLE_SIDED = 1 << 1;
        const CAST_SHADOW = 1 << 2;
    }
}

#[derive(Clone)]
pub struct RenderItem {
    pub geometry_id: u32,
    pub transform: Mat4,
    pub material_id: u32,
    pub bounding_sphere: Vec4,
    pub depth: f32,
    pub flags: RenderFlags,
}

pub struct RenderQueue {
    items: Vec<RenderItem>,
}

impl RenderQueue {
    pub fn new() -> Self { Self { items: Vec::with_capacity(1024) } }
    pub fn push(&mut self, item: RenderItem) { self.items.push(item); }
    pub fn clear(&mut self) { self.items.clear(); }
    pub fn len(&self) -> usize { self.items.len() }

    pub fn sort(&mut self) {
        self.items.sort_unstable_by_key(|item| {
            let pass = if item.flags.contains(RenderFlags::TRANSPARENT) { 1u8 } else { 0 };
            // 不透明按 depth 升序;透明按 depth 降序(取负)
            let depth_bits = if item.flags.contains(RenderFlags::TRANSPARENT) {
                ((-item.depth) * 1000.0) as i32
            } else {
                (item.depth * 1000.0) as i32
            };
            (pass, item.material_id, depth_bits)
        });
    }

    pub fn iter(&self) -> std::slice::Iter<'_, RenderItem> { self.items.iter() }
}

fn render_frame(queue: &mut RenderQueue, scene: &Scene) {
    // Phase 1: Collect
    queue.clear();
    for entity in &scene.entities {
        if !camera_sees(entity) { continue; }  // 视锥剔除
        queue.push(RenderItem {
            geometry_id: entity.geometry_id,
            transform: entity.transform,
            material_id: entity.material_id,
            bounding_sphere: entity.bounding_sphere,
            depth: (entity.position - camera.position).length(),
            flags: entity.flags,
        });
    }

    // Phase 2: Sort
    queue.sort();

    // Phase 3: Compute lighting (可并行)
    let lightings: Vec<_> = queue.iter().map(|item| {
        compute_lighting_for_item(item, &scene.lights)
    }).collect();

    // Phase 4: Submit
    for (item, lighting) in queue.iter().zip(lightings.iter()) {
        rasterize(item, lighting);
    }
}

fn camera_sees(_e: &Entity) -> bool { true }
fn compute_lighting_for_item(_i: &RenderItem, _l: &[Light]) -> Vec3 { Vec3::ONE }
fn rasterize(_i: &RenderItem, _l: &Vec3) {}
```

```rust
use glam::{Mat4, Vec3, Vec4};
use bitflags::bitflags;

bitflags! {
    #[derive(Clone, Copy, Default, Debug)]
    pub struct RenderFlags: u8 {
        const TRANSPARENT = 1 << 0;
        const DOUBLE_SIDED = 1 << 1;
        const CAST_SHADOW = 1 << 2;
        const RECEIVE_SHADOW = 1 << 3;
    }
}

#[derive(Clone, Debug)]
pub struct RenderItem {
    pub geometry_id: u32,
    pub transform: Mat4,
    pub material_id: u32,
    pub depth: f32,
    pub flags: RenderFlags,
}

pub struct RenderQueue {
    items: Vec<RenderItem>,
}

impl RenderQueue {
    pub fn new() -> Self {
        Self { items: Vec::with_capacity(2048) }
    }

    pub fn push(&mut self, item: RenderItem) {
        self.items.push(item);
    }

    pub fn clear(&mut self) {
        self.items.clear();
    }

    pub fn sort(&mut self) {
        self.items.sort_unstable_by(|a, b| {
            let pa = if a.flags.contains(RenderFlags::TRANSPARENT) { 1u8 } else { 0 };
            let pb = if b.flags.contains(RenderFlags::TRANSPARENT) { 1u8 } else { 0 };
            pa.cmp(&pb)
                .then_with(|| a.material_id.cmp(&b.material_id))
                .then_with(|| {
                    let da = if a.flags.contains(RenderFlags::TRANSPARENT) { -a.depth } else { a.depth };
                    let db = if b.flags.contains(RenderFlags::TRANSPARENT) { -b.depth } else { b.depth };
                    da.partial_cmp(&db).unwrap_or(std::cmp::Ordering::Equal)
                })
        });
    }

    pub fn iter(&self) -> std::slice::Iter<'_, RenderItem> { self.items.iter() }
    pub fn len(&self) -> usize { self.items.len() }
    pub fn is_empty(&self) -> bool { self.items.is_empty() }
}

fn main() {
    let mut q = RenderQueue::new();

    // 模拟场景:不透明、透明混合
    for i in 0..100 {
        q.push(RenderItem {
            geometry_id: i,
            transform: Mat4::IDENTITY,
            material_id: i % 5,
            depth: (i as f32) * 0.5,
            flags: RenderFlags::empty(),
        });
    }
    for i in 0..10 {
        q.push(RenderItem {
            geometry_id: 1000 + i,
            transform: Mat4::IDENTITY,
            material_id: 99,
            depth: (i as f32) * 1.0 + 5.0,
            flags: RenderFlags::TRANSPARENT,
        });
    }

    println!("Before sort: {} items", q.len());
    q.sort();
    println!("After sort (first 5):");
    for item in q.iter().take(5) {
        println!("  geom={} mat={} depth={:.2} flags={:?}",
            item.geometry_id, item.material_id, item.depth, item.flags);
    }
    println!("Last 5 (should be transparent):");
    for item in q.iter().rev().take(5) {
        println!("  geom={} mat={} depth={:.2} flags={:?}",
            item.geometry_id, item.material_id, item.depth, item.flags);
    }
}
```

**Troubleshooting**:

- **透明物体在不透明前面** —— 检查 `pass` 比较的顺序,透明应该 pass = 1,排到后面
- **同 depth 物体闪烁** —— 排序不稳定,但 `sort_unstable_by` 不保证相等元素顺序,加 tie-breaker
- **深度缓冲冲突** —— 不透明画完后,透明物体的深度测试可能错误,需要 `glDisable(GL_DEPTH_WRITEMASK)` 在透明 pass
- **Rayon 报 Send 错误** —— `RenderItem` 必须 `Send + Sync`,检查字段类型


### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
