# Day 324 · 弃用多个 OpenGL 上下文

> Casey 之前用"两个 OpenGL context"实现 hot reload——游戏代码 context 1 渲染,asset 加载 context 2。但多 context 带来一堆共享资源 bug。今天他重构回单 context,改用其他方式做异步加载。

## 0 · 为什么要有这一天

OpenGL 的"上下文(context)"是 GPU 资源的全局状态机——所有 OpenGL 调用都作用于"当前 context"。一个进程可以有多个 context(每个窗口一个,或同窗口多个 share context),但同一时刻一个线程只有一个 context 是 current。

Casey 之前为了"后台异步加载纹理",用了双 context 设计:

- **Context A(主)**:游戏渲染,所有 draw call
- **Context B(后台)**:加载纹理,解码 PNG,upload 到 GPU

两个 context 共享对象(纹理、buffer、shader),通过 `glShareLists`(Windows)/ 共享对象创建(WGL/GLX)。理论上设计很美——渲染和加载并行,没有卡顿。

但实际使用踩到一堆坑:

1. **共享对象的同步**:context B 创建的纹理,context A 看到的瞬间可能还没 ready,导致渲染空纹理
2. **驱动差异**:不同 GPU 厂商(NVIDIA / AMD / Intel)对 share context 行为不一致,某些 driver 在 share context 上传纹理时崩溃
3. **macOS 限制**:macOS 上的 OpenGL 实现(Apple 的 deprecated 实现)对 share context 支持极差
4. **debug 困难**:RenderDoc 在多 context 下表现异常,无法 capture 完整状态

经过几周的挣扎,Casey 决定**弃用多 context,回到单 context**,改用其他方式做异步加载。这是工程上的"撤退"——放弃理论优雅换工程稳定。

心理锚点:今天之后你的 OpenGL 渲染只用一个 context,异步加载用 thread + sync(后面 Day 350 多线程会讲)。代码简单、驱动友好、debug 容易。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_opengl.cpp`,做了一次"架构重构"。原来的结构:

```c
struct opengl_state {
    HGLRC RenderContext;    // 主渲染 context
    HGLRC WorkerContext;    // 后台加载 context
    // ...
};

void InitOpenGL(...) {
    RenderContext = wglCreateContext(...);
    WorkerContext = wglCreateContext(...);
    wglShareLists(RenderContext, WorkerContext);  // 共享对象
}

void LoadTexture(...) {
    // 在 worker thread
    wglMakeCurrent(WorkerContext);
    GLuint tex = glGenTextures(...);
    // upload PNG data
    // tex 立即可见到 RenderContext(理论上)
}
```

今天重构为:

```c
struct opengl_state {
    HGLRC RenderContext;    // 只有一个 context
    // 删除 WorkerContext
};

void LoadTexture(...) {
    // 在主 thread
    // 解码 PNG 在 worker thread
    // upload 到 GPU 在主 thread
}
```

关键变化:**纹理上传(`glTexImage2D`)必须在主 thread**。PNG 解码可以异步,但 GPU 上传必须主 thread。

Casey 引入了一个"加载队列"——worker thread 异步解码 PNG,把解码后的像素数据放到队列,主 thread 每帧从队列取出做 `glTexImage2D`。

```rust
struct LoadRequest {
    path: String,
    decoded_pixels: Option<Vec<u8>>,  // worker 填充
}

struct Loader {
    queue: Arc<Mutex<Vec<LoadRequest>>>,
}

// Worker thread
fn decode_thread(loader: &Loader) {
    loop {
        let req = loader.queue.lock().unwrap().iter_mut()
            .find(|r| r.decoded_pixels.is_none());
        if let Some(req) = req {
            let data = std::fs::read(&req.path).unwrap();
            let pixels = decode_png(&data);
            req.decoded_pixels = Some(pixels);
        }
        std::thread::sleep(Duration::from_millis(10));
    }
}

// Main thread
fn upload_textures(loader: &Loader, gl: &Context) {
    let mut queue = loader.queue.lock().unwrap();
    queue.retain(|req| {
        if let Some(pixels) = req.decoded_pixels.take() {
            let tex = unsafe { gl.create_texture() }.unwrap();
            unsafe {
                gl.bind_texture(TEXTURE_2D, Some(tex));
                gl.tex_image_2d(..., Some(&pixels));
            }
            false  // 从队列移除
        } else {
            true  // 还没解码,保留
        }
    });
}
```

主 thread 每帧调用 `upload_textures`,把已解码的纹理上传到 GPU。这样 OpenGL 调用都在主 thread,但 PNG 解码(耗时操作)在 worker thread 异步。

## 2 · 心智模型

### 类比:厨房的灶台

把 OpenGL context 想象成厨房的灶台。

- **单 context**:一个灶台,所有菜在这里做。简单,但只能一个厨师。
- **多 context**:多个灶台,多个厨师并行。理论高效,但灶台之间传菜(共享食材)要协调,容易混乱。
- **异步加载 + 单灶台**:还是单灶台,但备菜(切菜、洗菜)在另一个房间做,灶台只负责炒。

第三种是 Casey 今天的选择——主 thread 是灶台(OpenGL 调用),worker thread 是备菜间(PNG 解码)。备菜异步做,灶台高效用。

### 严谨原理:OpenGL 上下文

OpenGL context 的核心约束:

1. **一个 thread 一个 current context**:`wglMakeCurrent` / `glXMakeCurrent` 设置当前 context,thread 内所有 GL 调用作用于它
2. **一个 context 同时只能 current 在一个 thread**:不能两个 thread 共用同一 context
3. **多 context 间共享对象**:`wglShareLists` 共享纹理、buffer、shader 等;但 VAO、FBO 通常不共享
4. **共享对象的同步**:GL 没有内置同步原语,需要用 `glFenceSync` 显式同步

约束 4 是"为什么多 context 难用"的根本原因。两个 context 共享纹理时,context B 上传后,context A 看到的是"上传中"还是"已完成"?GL 标准没规定,驱动各自实现,导致行为不一致。

### 异步加载 + 主线程上传

正确的多线程 OpenGL 加载模式:

```
Worker thread              Main thread
─────────────              ───────────
read file                  render game
decode PNG to pixels       
put pixels to queue  →     poll queue
                           if pixels ready:
                             glTexImage2D (上传到 GPU)
                           render with new texture
```

这个模式叫 **"async decode + sync upload"**:

- 异步部分:**慢 CPU 操作**(文件 IO + PNG 解码)
- 同步部分:**GPU 操作**(GL 调用)

GPU 操作必须主 thread 是 OpenGL 的限制。新一代 API(Vulkan / D3D12)允许多 thread record command buffer,然后主 thread submit,但 OpenGL 不行。

### 替代方案:Persistent Mapping

OpenGL 4.4 引入 `glBufferStorage` + `GL_MAP_PERSISTENT_BIT`,允许"持久映射"——CPU 写内存,GPU 直接读,无需 upload。这种"zero-copy"模式让多 thread 写 buffer 更高效。

```c
// 创建 buffer with persistent mapping
GLuint buf;
glGenBuffers(1, &buf);
glBindBuffer(GL_COPY_WRITE_TARGET, buf);
glBufferStorage(GL_COPY_WRITE_TARGET, size, NULL, 
                GL_MAP_WRITE_BIT | GL_MAP_PERSISTENT_BIT | GL_MAP_COHERENT_BIT);
void *ptr = glMapBufferRange(GL_COPY_WRITE_TARGET, 0, size, 
                              GL_MAP_WRITE_BIT | GL_MAP_PERSISTENT_BIT | GL_MAP_COHERENT_BIT);
// 现在 ptr 可以多 thread 写,GPU 直接看
```

但 Casey 还在 OpenGL 3.3,用不了。Vulkan / wgpu 是更现代的选择。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的加载策略:

1. **同步加载**:游戏开始加载所有资产,加载时显示 loading screen。简单但有等待。
2. **异步加载 + 主线程 upload**(今天):worker 解码,主线程 upload。中等复杂度,主流选择。
3. **多 thread + command buffer**(Vulkan/D3D12):每 thread 录制 command,主线程 submit。复杂但极致性能。
4. **Streaming**(流式加载):跑动中加载新区域(GTA、塞尔达),需要 LOD + priority queue。

主流引擎的资产管线:

- Unity:`Resources.LoadAsync` + `AssetBundle`,引擎内部管理多 thread
- Unreal:`StreamableManager` + `FStreamableHandle`,类似
- Godot:`ResourceLoader::load_interactive`,协程式

游戏行业的共识:**避免多 OpenGL context,改用 async decode + sync upload**。Casey 经过痛苦摸索得出的结论,行业早就这么做了。

### 3.2 · 🎨 图形学视角

图形 API 的多线程演进:

- **OpenGL**(1992):单 thread,context 全局状态
- **OpenGL 多 context**(2000s):允许 share,但同步复杂
- **Vulkan / D3D12**(2015+):command buffer 多 thread 录制,主 thread submit
- **WebGPU**(2021+):类似 Vulkan,但更安全

Vulkan 的核心抽象:**command buffer**——CPU 录制 GPU 指令到 buffer,buffer 可以多 thread 录制,然后 queue submit 给 GPU。这种"录制 / 提交分离"让多线程友好,不用共享 context。

今天的 OpenGL 单 context + async decode 是过渡方案——能跑得不错,但不是终极方案。Casey 在 Phase 8 可能会切到 wgpu。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上 OpenGL 上下文创建:

- **GLX**(X11):`glXCreateContext` / `glXCreateContextAttribsARB`
- **EGL**(Wayland / 嵌入式):`eglCreateContext`

```c
// GLX 创建 share context
GLXContext share = NULL;  // 共享的已有 context
GLXContext ctx = glXCreateContextAttribsARB(
    display, fbconfig, share, True,  // direct rendering
    attribs
);
```

Wayland 时代 EGL 是主流。EGL 的 share context 通过 `eglCreateContext` 的 `share_context` 参数:

```c
EGLContext share = EGL_NO_CONTEXT;
EGLContext ctx = eglCreateContext(display, config, share, attribs);
```

Linux 上的"多 context"主要用于"多窗口"(每窗口一个 context),不是"多线程同窗口"。Casey 的双 context 设计在 Linux 上也有同样问题——驱动不一致。

### 3.4 · 🦀 Rust 生态视角

Rust 处理多线程 OpenGL 加载:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

struct Loader {
    pending: Arc<Mutex<Vec<LoadJob>>>,
}

struct LoadJob {
    path: String,
    decoded: Option<DecodedImage>,
}

impl Loader {
    fn submit(&self, path: &str) {
        self.pending.lock().unwrap().push(LoadJob {
            path: path.to_string(),
            decoded: None,
        });
    }
    
    fn spawn_worker(loader: Arc<Loader>) {
        thread::spawn(move || {
            loop {
                let job = {
                    let mut pending = loader.pending.lock().unwrap();
                    pending.iter_mut().find(|j| j.decoded.is_none()).map(|j| &j.path).cloned()
                };
                if let Some(path) = job {
                    let data = std::fs::read(&path).unwrap();
                    let decoded = decode_png(&data);
                    let mut pending = loader.pending.lock().unwrap();
                    if let Some(j) = pending.iter_mut().find(|j| j.path == path) {
                        j.decoded = Some(decoded);
                    }
                } else {
                    thread::sleep(std::time::Duration::from_millis(10));
                }
            }
        });
    }
    
    /// 主线程每帧调用,上传已解码纹理
    fn upload_ready(&self, gl: &Context) -> Vec<GLuint> {
        let mut pending = self.pending.lock().unwrap();
        let mut uploaded = Vec::new();
        pending.retain(|job| {
            if let Some(img) = job.decoded.take() {
                let tex = create_texture(gl, &img);
                uploaded.push(tex);
                false
            } else {
                true
            }
        });
        uploaded
    }
}
```

`Arc<Mutex<Vec<LoadJob>>>` 是 Rust 标准的"跨线程共享可变状态"——`Arc` 引用计数,`Mutex` 互斥锁,`Vec` 数据。这种"3 件套"是 Rust 多线程编程的基础设施。

`Send + Sync` 是 Rust 的 marker trait——`LoadJob` 必须实现这两个才能跨线程。Rust 编译器自动推导,大部分类型自动满足。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"多 OpenGL context 共享对象"在实践中难用?给出至少 3 个理由。

**参考解答**:

1. **同步语义不明**:GL 标准没规定"共享对象的可见性",驱动各自实现。NVIDIA 上工作的代码 AMD 上可能崩。
2. **资源类型限制**:VAO、FBO 通常不能共享,只能共享 texture/buffer/shader。这强制多 context 重新创建非共享对象。
3. **debug 工具不友好**:RenderDoc、apitrace 在多 context 下表现异常,capture 不完整。
4. **macOS 支持差**:Apple 的 deprecated OpenGL 对 share context 支持极差。
5. **性能不一定提升**:多 context 间同步开销可能抵消并行收益。

### Lv2 · 动手实践

**题**:在 Rust 里实现"async decode + sync upload"模式,要求:

- 主线程 submit 加载任务
- worker thread 异步解码(用 `std::thread::spawn`)
- 主线程每帧 poll,upload ready 的
- 模拟"纹理上传"用 println

**参考解答**:

```rust
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

#[derive(Clone, Debug)]
struct DecodedImage {
    width: u32,
    height: u32,
    pixels: Vec<u8>,
}

struct LoadJob {
    path: String,
    decoded: Option<DecodedImage>,
}

struct Loader {
    pending: Arc<Mutex<Vec<LoadJob>>>,
}

impl Loader {
    fn new() -> Self {
        let loader = Self {
            pending: Arc::new(Mutex::new(Vec::new())),
        };
        // Spawn worker thread
        let pending = Arc::clone(&loader.pending);
        thread::spawn(move || {
            loop {
                // 找一个待解码任务
                let path = {
                    let mut p = pending.lock().unwrap();
                    p.iter_mut()
                        .find(|j| j.decoded.is_none())
                        .map(|j| j.path.clone())
                };
                
                if let Some(path) = path {
                    println!("[worker] decoding {}", path);
                    thread::sleep(Duration::from_millis(500));  // 模拟解码
                    let img = DecodedImage {
                        width: 256, height: 256,
                        pixels: vec![0; 256 * 256 * 4],
                    };
                    let mut p = pending.lock().unwrap();
                    if let Some(j) = p.iter_mut().find(|j| j.path == path) {
                        j.decoded = Some(img);
                    }
                    println!("[worker] decoded {}", path);
                } else {
                    thread::sleep(Duration::from_millis(10));
                }
            }
        });
        loader
    }
    
    fn submit(&self, path: &str) {
        self.pending.lock().unwrap().push(LoadJob {
            path: path.to_string(),
            decoded: None,
        });
        println!("[main] submitted {}", path);
    }
    
    fn upload_ready(&self) -> Vec<String> {
        let mut p = self.pending.lock().unwrap();
        let mut uploaded = Vec::new();
        p.retain(|job| {
            if job.decoded.is_some() {
                println!("[main] uploading {} to GPU", job.path);
                uploaded.push(job.path.clone());
                false
            } else {
                true
            }
        });
        uploaded
    }
}

fn main() {
    let loader = Loader::new();
    
    // Submit a few loads
    loader.submit("assets/hero.png");
    loader.submit("assets/enemy.png");
    loader.submit("assets/tile.png");
    
    // Simulate main loop
    for frame in 0..20 {
        let uploaded = loader.upload_ready();
        if !uploaded.is_empty() {
            println!("[main] frame {}: uploaded {} textures", frame, uploaded.len());
        }
        thread::sleep(Duration::from_millis(100));
    }
}
```

## 8 · Rust / Arch 落地代码

### Rust:单 context 异步加载(完整可跑)

```rust
// Cargo.toml: 无依赖
// src/main.rs

use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

/// 解码后的图像数据
#[derive(Clone, Debug)]
struct DecodedImage {
    width: u32,
    height: u32,
    pixels: Vec<u8>,
}

/// 加载任务
struct LoadJob {
    path: String,
    decoded: Option<DecodedImage>,
    priority: u32,
}

/// 加载器
struct Loader {
    pending: Arc<Mutex<Vec<LoadJob>>>,
}

impl Loader {
    fn new() -> Self {
        let pending = Arc::new(Mutex::new(Vec::new()));
        
        // Spawn worker thread(模拟 PNG 解码)
        let worker_pending = Arc::clone(&pending);
        thread::spawn(move || {
            loop {
                // 找最高优先级的待解码任务
                let target_path = {
                    let p = worker_pending.lock().unwrap();
                    let mut candidates: Vec<_> = p.iter()
                        .filter(|j| j.decoded.is_none())
                        .collect();
                    candidates.sort_by(|a, b| b.priority.cmp(&a.priority));
                    candidates.first().map(|j| j.path.clone())
                };
                
                if let Some(path) = target_path {
                    println!("  [worker] decoding {}...", path);
                    thread::sleep(Duration::from_millis(300));
                    
                    // 模拟解码
                    let img = DecodedImage {
                        width: 256, height: 256,
                        pixels: vec![200u8; 256 * 256 * 4],  // 灰色
                    };
                    
                    let mut p = worker_pending.lock().unwrap();
                    if let Some(j) = p.iter_mut().find(|j| j.path == path) {
                        j.decoded = Some(img);
                    }
                    println!("  [worker] done {}", path);
                } else {
                    thread::sleep(Duration::from_millis(10));
                }
            }
        });
        
        Self { pending }
    }
    
    fn submit(&self, path: &str, priority: u32) {
        self.pending.lock().unwrap().push(LoadJob {
            path: path.to_string(),
            decoded: None,
            priority,
        });
        println!("[main] submitted {} (priority={})", path, priority);
    }
    
    /// 主线程每帧调用,upload 已解码的纹理到 GPU
    fn upload_ready(&self) -> Vec<String> {
        let mut p = self.pending.lock().unwrap();
        let mut uploaded = Vec::new();
        p.retain(|job| {
            if let Some(img) = job.decoded.take() {
                // 这里会调用 OpenGL API,因为是主线程所以安全
                // 模拟:
                println!("[main] uploading {} to GPU ({}x{})",
                         job.path, img.width, img.height);
                uploaded.push(job.path.clone());
                false
            } else {
                true
            }
        });
        uploaded
    }
}

fn main() {
    println!("=== Day 324: 单 context 异步加载 ===\n");
    
    let loader = Loader::new();
    
    // Submit 多个加载任务
    loader.submit("assets/hero.png", 10);    // 高优先级
    loader.submit("assets/tile.png", 5);     // 低
    loader.submit("assets/enemy.png", 8);    // 中
    
    // 模拟主循环
    let mut frame = 0;
    let mut total_uploaded = 0;
    while total_uploaded < 3 {
        let uploaded = loader.upload_ready();
        total_uploaded += uploaded.len();
        
        if !uploaded.is_empty() {
            println!("[main] frame {}: uploaded {} (total {})", 
                     frame, uploaded.len(), total_uploaded);
        } else {
            // 主线程正常渲染,不阻塞
            print!(".");
            use std::io::Write;
            std::io::stdout().flush().unwrap();
        }
        
        thread::sleep(Duration::from_millis(50));
        frame += 1;
        if frame > 40 { break; }
    }
    
    println!("\n\n所有资产加载完成!");
}
```

**Troubleshooting**:

- **死锁** — 检查 Mutex 持有时间,worker 不要长期持锁
- **数据竞争** — Rust 编译期保证 `Send + Sync`,但 unsafe 代码可能绕过
- **worker 找不到任务** — 检查 path 字符串比较,trim 空格
