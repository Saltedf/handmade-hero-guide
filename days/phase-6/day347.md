
# Day 347 · 调试 Win32 内存列表损坏

> 昨天合并块头之后,Casey 跑游戏,程序在某个时刻崩溃——但是"随机崩溃"。有时跑 10 分钟,有时跑 1 秒,有时根本不崩。这是程序员最怕的"内存损坏(memory corruption)"bug,今天的全部内容是 Casey 如何用"内存页保护"和"侵入式检查"定位根因。这是 HH 里最难的 debug 集之一。

## 0 · 为什么要有这一天

**内存损坏(memory corruption)** 是 C/C++ 程序员最恐惧的 bug 类型:

- **症状随机**:你写错一个字节,可能 10 分钟后才触发崩溃——崩溃位置和 bug 位置完全无关
- **复现困难**:同样的操作有时崩有时不崩,取决于"那个字节被什么覆盖"
- **工具难用**:gdb/valgrind 有用,但内存损坏可能跨多小时运行才触发
- **代码已写完才发现**:你的代码可能 30 天前就埋下 bug,现在才显现

具体症状:Casey 在 Day 346 合并块头后,游戏随机崩溃在"完全无关"的代码里——比如渲染粒子时崩,但 bug 根因在内存分配。怎么定位?

**Casey 的方法论**:

1. **加 invariant 检查**:每个内存块头加 magic number(如 `0xDEADBEEF`),每次访问校验
2. **使用 Win32 的 VirtualProtect**:把内存页标记为不可访问,任何写触发段错误
3. **二分注释**:逐步禁用代码,看哪个调用引发损坏
4. **二进制日志**:记录每次 alloc/free,事后重放定位

Linux/Arch 等价物:`mprotect`(系统调用)、`Electric Fence`(库)、`ASan`(编译器)。Rust 等价物:`miri`、`#[track_caller]`。

今天 Casey 用 Win32 的 `VirtualProtect` 把损坏位置"逼"出来——把"10 分钟后崩"变成"立刻崩"。这是 debug 内存损坏的金科玉律:**让 bug 早现,而不是晚现**。

心理锚点:今天之后你能处理"随机崩溃"类 bug,会用内存保护工具,理解"防御性编程"的实战价值。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑 Day 346 的代码,发现游戏在 ~5 分钟后崩在 `world_render()` 里。崩溃位置访问一个 NULL 指针——但 NULL 指针来自哪里?

调试过程:

1. **重复运行**:跑 10 次,每次崩在不同地方。共通点:崩溃前都调过 `arena.alloc()`
2. **怀疑内存损坏**:某个 alloc 写坏了内存,影响后续代码
3. **加 magic number**:每个 `memory_block` 头加 `u32 Magic = 0xABCD1234`,dealloc 时校验
4. **运行**:发现某些块的 Magic 被改成乱数——确认是越界写
5. **加 VirtualProtect**:把每个 block 后面留一页(4096B)设为 `PAGE_NOACCESS`,越界写立即段错误
6. **重新运行**:崩在 `sim_region.update_particle(42)` —— 第 42 号粒子的 `vel` 字段越界写
7. **检查代码**:`update_particle` 的循环条件 `i <= count` 应该是 `i < count`,多写了一个槽位
8. **修复**:`i < count`
9. **回归**:加边界检查测试,bug 不再复现

今天的核心不是修 bug,而是 Casey 演示的 debug 思路:**让随机崩变成确定崩,让确定崩指向根因**。

## 2 · 心智模型

### 类比:水下管道泄漏

想象家里水管漏水,水滴到你楼下邻居的天花板。你看不到漏点,只知道"邻居天花板湿了"。

- **直接定位**:打开墙看每根管子——成本极高
- **压力测试**:把水压加到极限,漏点会喷水——立刻可见
- **染色剂**:在水里加染料,看哪个墙渗色——精确到点
- **分段隔离**:关掉一段水管的阀门,看泄漏是否停——二分定位

内存损坏同构:

- **直接定位**:review 所有代码,看哪里越界——不可行(代码太多)
- **压力测试**:加 magic number,被覆盖就立刻发现——染色剂
- **VirtualProtect**:把"假墙"设为不可写,越界写立刻段错误——压力测试
- **二分注释**:逐段禁用代码,看损坏是否停——分段隔离

### Magic Number(染色剂)

每个内存块头加一个固定值,正常永远不被改:

```rust
const MAGIC: u32 = 0xABCD_1234;

struct MemoryBlock {
    magic: u32,        // 头部 magic
    size: usize,
    used: usize,
    // ...
    tail_magic: u32,  // 尾部 magic(紧跟 data 之后)
}

impl MemoryBlock {
    fn validate(&self) -> bool {
        self.magic == MAGIC && self.tail_magic == MAGIC
    }
}
```

每次访问前校验 `validate()`。如果 magic 不对,说明**有人越界写了**——可能是上一个块的尾部被踩,或者本块被踩。

**进阶**:不同状态用不同 magic:

- `MAGIC_ALLOCATED = 0xABCD1234`:已分配
- `MAGIC_FREED = 0xDCBA4321`:已释放

如果某块释放后 magic 仍是 `MAGIC_ALLOCATED`,说明**释放后仍被访问(use-after-free)**。

### VirtualProtect(压力测试)

Windows 的 `VirtualMemory` API 把内存页(4KB)标记为 `PAGE_NOACCESS`。任何读写触发段错误。

```c
// Windows
DWORD oldProtect;
VirtualProtect(page, 4096, PAGE_NOACCESS, &oldProtect);
// 任何后续访问 page[0..4096] 都会触发 EXCEPTION_ACCESS_VIOLATION
```

Linux/Mac 等价物 `mprotect`:

```c
// POSIX
mprotect(page, 4096, PROT_NONE);
// 访问触发 SIGSEGV
```

**用法**:在每两个内存块之间塞一个"哨兵页"(guard page),标记为 `PROT_NONE`。任何越界写越过块边界就撞哨兵页,**立刻段错误**——栈顶告诉你越界位置。

```rust
fn allocate_with_guard(size: usize) -> *mut u8 {
    let page_size = 4096;
    let total = page_size + size + page_size;  // 前 guard + data + 后 guard
    let layout = Layout::from_size_align(total, page_size).unwrap();
    unsafe {
        let base = std::alloc::alloc(layout);
        if base.is_null() { panic!("OOM"); }
        // 前 guard
        std::alloc::alloc::alloc_zeroed
        // 标记前后 guard 为 PROT_NONE
        libc::mprotect(base as *mut libc::c_void, page_size, libc::PROT_NONE);
        libc::mprotect(base.add(size + page_size) as *mut libc::c_void, page_size, libc::PROT_NONE);
        // 返回中间 data 指针
        base.add(page_size)
    }
}
```

**`Electric Fence` / `efence`**:Linux 库,自动给每个 `malloc` 加 guard page。链接 `-lefence` 即可。

### AddressSanitizer:自动化的 magic + guard

GCC/Clang 编译选项 `-fsanitize=address` 自动给每个 alloc 加 magic 和 guard,运行时检查越界。开销 ~2x 慢,但**零代码改动**。

```bash
RUSTFLAGS="-Zsanitizer=address" cargo +nightly build --release
./target/release/my_game
# 越界访问会立刻报错:
# ==12345==ERROR: AddressSanitizer: heap-buffer-overflow
# READ of size 4 at 0x... created by main::alloc_particles
```

Rust nightly 才支持 ASan。Stable Rust 用户用 `miri`(更精确但慢得多):

```bash
cargo +nightly miri run
# miri 解释执行,检查所有 unsafe 行为
```

### Rust 的优势

Rust 编译期消除大多数内存 bug:

- **数组越界**:运行时 panic(默认)或编译期拒绝(const generics)
- **空指针**:`Option<T>` 强制处理
- **悬垂引用**:lifetime
- **释放后访问**:所有权

但 unsafe 代码绕过这些检查。Casey 的内存系统在 C 里全是"unsafe"——Rust 翻译要么用 `unsafe` 块(要自己保证正确),要么用安全 API(性能略损)。

实战:**Rust 写内存系统主要靠 `unsafe`,但每个 unsafe 块都加 safety comment**:

```rust
// SAFETY: `ptr` is valid because we just allocated it with `alloc(layout)`,
// and `offset < size` is checked by the caller.
unsafe {
    *ptr.add(offset) = byte;
}
```

`#[track_caller]` 让 panic 指向调用方,debug 更快:

```rust
#[track_caller]
fn get(&self, i: usize) -> &T {
    self.data.get(i).expect("index out of bounds")
}
```

```rust
    unsafe { *ptr.add(offset) = byte; }
}

// debug_assert + #[track_caller]
#[track_caller]

    debug_assert!(i < self.len, "index {} out of bounds", i);
    unsafe { &*self.ptr.add(i) }
}
```

## 5 · 对照与变奏

### Debug 不同内存 bug 的策略

**Heap buffer overflow**(今天):
- ASan 立刻报
- 或 guard page
- 或 magic number

**Use-after-free**:
- ASan 检测
- 或 quarantine(释放的内存不立即复用,保留 N 时间)

**Double free**:
- 释放后改 magic 为 FREED
- 再次 free 校验 magic

**Stack buffer overflow**:
- `-fstack-protector` 编译选项
- 栈 canary(每个函数栈底加 magic)

**Uninitialized read**:
- MSan
- 或初始化所有变量(防御性)

### 调试时间分布

业界统计:**80% 时间在找 bug,20% 在修 bug**。Casey Day 347 花了整整一天找一行错。这是常态。

专业开发者必备技能:**减少"找 bug"时间**。方法:

1. **可测试代码**(单元测试、属性测试)
2. **可观察代码**(log、metric)
3. **可重现 bug**(简化复现路径)

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"随机崩溃"比"确定崩溃"难调?为什么 Casey 用 VirtualProtect 把"随机"变"确定"?

**参考解答**:

随机崩溃难调:

1. **复现困难**:同样操作不一定崩,你需要"等"
2. **崩溃位置≠bug 位置**:你看到的是"症状",不是"病因"
3. **数据被改**:崩溃时内存已经损坏,难以追溯
4. **变量太多**:可能多个 bug 互相影响

VirtualProtect 把"随机"变"确定":

1. **越界立即崩**:不再"等"内存损坏累积到崩溃,而是当场段错误
2. **崩溃位置 = bug 位置**:谁越界,谁触发,栈顶直接指向 bug 行
3. **可复现**:每次越界都崩,容易重现场景
4. **隔离**:不同 alloc 各自 guard page,bug 不互相影响

### Lv2 · 动手实践

**题**:实现一个带 magic number + guard page 的内存块。测试:正常读写 OK,越界读写 panic。

完成标准:正常用例通过,越界用例 panic。

**参考解答**:

```rust
const MAGIC_ALLOC: u32 = 0xABCD_1234;
const MAGIC_FREED: u32 = 0xDEAD_BEEF;

struct GuardedBlock {
    data: Vec<u8>,
}

impl GuardedBlock {
    fn new(size: usize) -> Self {
        // 头 4 字节 magic + 数据 + 尾 4 字节 magic
        let total = 4 + size + 4;
        let mut data = vec![0u8; total];

        // 头 magic
        let head = MAGIC_ALLOC.to_le_bytes();
        data[0..4].copy_from_slice(&head);

        // 尾 magic
        let tail = MAGIC_ALLOC.to_le_bytes();
        data[4 + size..4 + size + 4].copy_from_slice(&tail);

        Self { data }
    }

    fn user_ptr_range(&self) -> (usize, usize) {
        (4, 4 + self.data.len() - 8)
    }

    fn write(&mut self, offset: usize, byte: u8) {
        let (start, end) = self.user_ptr_range();
        assert!(offset < end - start,
                "write at offset {} out of bounds (user size {})",
                offset, end - start);
        self.data[start + offset] = byte;
    }

    fn validate(&self) -> bool {
        let head = u32::from_le_bytes(self.data[0..4].try_into().unwrap());
        let tail_pos = self.data.len() - 4;
        let tail = u32::from_le_bytes(self.data[tail_pos..tail_pos + 4].try_into().unwrap());
        head == MAGIC_ALLOC && tail == MAGIC_ALLOC
    }
}

fn main() {
    let mut block = GuardedBlock::new(16);
    println!("allocated block, user size = {}", {
        let (s, e) = block.user_ptr_range();
        e - s
    });

    // 正常写
    block.write(0, 0xAB);
    block.write(15, 0xCD);
    println!("normal writes OK");
    println!("magic valid: {}", block.validate());

    // 模拟"越界":直接写头 magic(模拟 buffer underrun)
    block.data[0] = 0;  // 破坏头
    println!("after corruption, magic valid: {}", block.validate());

    // 真正的越界检查(用 write 函数会 assert)
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        let mut b = GuardedBlock::new(16);
        b.write(16, 0xFF);  // 越界
    }));
    println!("out-of-bounds write panicked: {}", result.is_err());
}
```

**关键解释**:
- `MAGIC_ALLOC` / `MAGIC_FREED`:不同状态不同 magic
- 头尾各放 magic:既能检测"前面被踩"又能检测"后面越界"
- `validate()` 在每次访问前调,被破坏立即发现
- `catch_unwind` 捕获 panic,让测试不退出

### Lv3 · 迁移设计

**题**:把 magic number 思路用到**文件格式**:你存游戏存档,每个 record 前后加 magic。文件被破坏(磁盘坏块、传输错误)时,加载阶段就检测出来,而不是"加载后随机崩"。

### 完整可跑示例:guard page + magic

```rust
use std::alloc::{alloc, dealloc, Layout};

const MAGIC_ALLOC: u32 = 0xABCD_1234;

struct MallocBlock {
    ptr: *mut u8,
    layout: Layout,
    user_size: usize,
}

impl MallocBlock {
    fn new(user_size: usize) -> Self {
        // 头 16 字节(magic + size)+ user + 尾 16 字节(magic)
        let total = 16 + user_size + 16;
        let layout = Layout::from_size_align(total, 16).unwrap();
        unsafe {
            let ptr = alloc(layout);
            if ptr.is_null() { panic!("OOM"); }

            // 头 magic
            let magic = MAGIC_ALLOC.to_le_bytes();
            std::ptr::copy_nonoverlapping(magic.as_ptr(), ptr, 4);
            // 头 size
            let size_bytes = (user_size as u64).to_le_bytes();
            std::ptr::copy_nonoverlapping(size_bytes.as_ptr(), ptr.add(8), 8);

            // 尾 magic
            std::ptr::copy_nonoverlapping(magic.as_ptr(), ptr.add(16 + user_size), 4);

            Self { ptr, layout, user_size }
        }
    }

    fn user_ptr(&self) -> *mut u8 {
        unsafe { self.ptr.add(16) }
    }

    fn write(&mut self, offset: usize, byte: u8) {
        assert!(offset < self.user_size,
                "offset {} out of bounds for user_size {}",
                offset, self.user_size);
        unsafe {
            *self.user_ptr().add(offset) = byte;
        }
    }

    fn validate(&self) -> bool {
        unsafe {
            let head_magic = u32::from_le_bytes(
                std::slice::from_raw_parts(self.ptr, 4).try_into().unwrap()
            );
            let tail_offset = 16 + self.user_size;
            let tail_magic = u32::from_le_bytes(
                std::slice::from_raw_parts(self.ptr.add(tail_offset), 4).try_into().unwrap()
            );
            head_magic == MAGIC_ALLOC && tail_magic == MAGIC_ALLOC
        }
    }
}

impl Drop for MallocBlock {
    fn drop(&mut self) {
        unsafe { dealloc(self.ptr, self.layout); }
    }
}

fn main() {
    let mut block = MallocBlock::new(64);
    println!("allocated 64-byte block");
    println!("validate: {}", block.validate());

    // 正常写
    block.write(0, 0xAA);
    block.write(63, 0xBB);
    println!("after normal writes, validate: {}", block.validate());

    // 模拟越界(直接 unsafe 越界写,绕过 write 函数的 assert)
    // 如果有 ASan 或 guard page,这里会立刻段错误
    unsafe {
        // 越界写尾 magic
        let tail_ptr = block.user_ptr().add(64);
        *tail_ptr = 0xFF;  // 破坏尾 magic 第一个字节
    }
    println!("after corruption, validate: {}", block.validate());  // false

    // 正常用 write 函数的越界检测
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        let mut b = MallocBlock::new(16);
        b.write(16, 0xFF);  // assert 触发
    }));
    println!("write bounds check: panic = {}", result.is_err());
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
