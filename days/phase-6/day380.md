**为什么展示失败**?
1. **教学诚实**:告诉学习者"调试不是直线"
2. **理论深入**:每个失败都揭示时间测量的微妙之处
3. **同理心**:让学习者知道 Casey 也会失败,不是天才

**时钟为什么这么难**?因为时间在计算机里**不是单一概念**:
- **Wall clock time**(墙上时钟):日历时间,可被 NTP 调整,可能"倒流"
- **Monotonic time**(单调时钟):保证不倒流,但起点未定义
- **CPU time**(CPU 时间):程序占 CPU 的时间,不含 sleep
- **Real time**(实际时间):从某个起点的实际秒数
- **TSC**(时间戳计数器):CPU 周期计数,精度极高但语义复杂

游戏需要的是 **monotonic real time**,但取这个时间在不同 OS / 不同硬件上行为差异巨大。

心理锚点:今天之后,你能解释计算机时钟的几种类型,知道游戏循环里该用哪个,理解为什么"看似简单"的 dt 计算实际充满陷阱。

## 2 · 心智模型

### 类比:时间在计算机里像"多个时钟,各有用途"

想象你家有几个钟:
- **墙上挂钟**:客厅,显示日历时间。可能被你拨快/拨慢(像 NTP 调整)
- **秒表**:运动用,从 0 开始计时。单调(不会倒流),但起点未定义
- **厨房定时器**:做菜用,倒计时。精度有限
- **智能手表原子钟**:超高精度,但贵且复杂

游戏循环需要的:**秒表**(monotonic,不会倒流)+ 精度足够(纳秒级)。

但操作系统提供好几个 API,每个对应不同时钟,选错了行为怪异。

### 时间 API 的层次

**Layer 1:Wall Clock**(墙上时钟)

```rust
let now = std::time::SystemTime::now();
// Unix epoch(1970-01-01)以来的秒数
// 可被 NTP 调整,可能"倒流"(系统时间被改回)
// 精度:微秒到毫秒
```

**Layer 2:Monotonic Clock**(单调时钟)

```rust
let now = std::time::Instant::now();
// 程序启动以来的单调时间,保证不倒流
// 起点 OS 决定(Linux 是 boot 时间,Windows 是某个固定点)
// 精度:纳秒
```

**Layer 3:Hardware Counter**(硬件计数)

```rust
// x86 RDTSC(Read Time-Stamp Counter)
// 每次 CPU 周期 +1
// 精度:纳秒级(< 1ns)
// 问题:多核 CPU 每核独立 TSC,可能不同步
```

**Layer 4:Network Time**(网络时间)

```rust
// NTP / PTP,同步到外部时间源
// 精度:毫秒(NTP)到纳秒(PTP)
// 用于分布式系统,游戏不用
```

游戏循环用 Layer 2(monotonic),精度足够,稳定。

### Delta Time 计算的正确做法

```rust
let mut last_time = Instant::now();
loop {
    let now = Instant::now();
    let dt = (now - last_time).as_secs_f32();
    last_time = now;

    update(dt);
    render();
}
```

简单,但有几个坑:

**坑 1:第一次 dt 异常**

```rust
let mut last_time = Instant::now();  // program start
// 第一次循环时,可能 last_time 和 now 之间几十毫秒(初始化时间长)
// dt 可能 = 0.5 秒,导致第一帧"跳跃"
```

修复:第一次跳过 update。

**坑 2:暂停后 dt 异常**

```rust
// 玩家切到其他窗口,游戏暂停
// 切回来时,last_time 是几秒前
// dt = 5 秒,玩家瞬间跳过 5 秒内容
```

修复:clamp dt 到合理范围(如 0.1 秒)。

**坑 3:HiDPI 显示器导致 VSync 不同**

```rust
// 60Hz 显示器:dt ≈ 16.67ms
// 144Hz 显示器:dt ≈ 6.94ms
// 玩家移动 = velocity * dt
// 60Hz: 5 * 0.01667 = 0.083 米/帧
// 144Hz: 5 * 0.00694 = 0.0347 米/帧
// 但每秒都是 5 米(0.083 * 60 = 0.0347 * 144 = 5)
// 所以正确实现是 dt 独立的
```

只要 dt 计算正确,**游戏在不同刷新率下速度一致**。Casey 的 bug 是 dt 算错(可能用了固定 dt 0.01667 而非真实 dt)。

**坑 4:VSync 不准**

```rust
// VSync 让 swap buffer 同步到显示器刷新
// 但有些驱动 VSync 不准
// dt 实际可能是 16.6 / 33.3 / 50 ms(2帧、3帧合成)
// 不平稳
```

修复:用 frame time average 平滑,但要小心延迟。

### Rust 的 Instant

```rust
use std::time::Instant;

let start = Instant::now();
// do work
let elapsed = start.elapsed();
println!("{:?}", elapsed);
// Duration { secs: 0, nanos: 12345 }
```

`Instant::now()` 在:
- Linux:用 `clock_gettime(CLOCK_MONOTONIC)`
- macOS:用 `mach_absolute_time`
- Windows:用 `QueryPerformanceCounter`

跨平台一致,但底层 API 不同。Rust 的封装正确处理了跨平台差异。

### 时间测量的精度问题

```rust
let start = Instant::now();
let work = do_something();
let elapsed = start.elapsed();
// elapsed 是 Duration,内部 { secs: i64, nanos: u32 }

// 假设 do_something 极快(几纳秒)
// elapsed 可能 = 0 ns(精度不够)
// 或者 = 100 ns(包含 Instant::now() 自身开销)
```

`Instant::now()` 本身开销约 50-100ns。测量更短的时间不准。

工业方案:**多次重复 + 平均**:

```rust
const N: u32 = 1000;
let start = Instant::now();
for _ in 0..N {
    do_something();
}
let total = start.elapsed();
let per_call = total / N;
```

### 多核 TSC 问题(高级)

x86 RDTSC 指令读 CPU 时间戳计数器:

```rust
unsafe {
    let lo: u32;
    let hi: u32;
    core::arch::asm!("rdtsc", out("eax") lo, out("edx") hi);
    let tsc = ((hi as u64) << 32) | (lo as u64);
}
```

每个 CPU 核有独立 TSC。多核系统上,如果线程在核间迁移,读到的 TSC 可能不一致(每核 TSC 没完美同步)。

修复:
1. **Invariant TSC**(现代 CPU 支持):所有核 TSC 同步,可直接用
2. **CPU affinity**:绑定线程到单核
3. **RDTSCP**:序列化指令,保证读到正确核的 TSC

Linux 提供 `clock_gettime(CLOCK_MONOTONIC_RAW)`,绕开 NTP 调整,直接用硬件 TSC。

```c
struct timespec ts;
clock_gettime(CLOCK_MONOTONIC_RAW, &ts);
// 不受 NTP 影响
```

Rust 没直接暴露 `CLOCK_MONOTONIC_RAW`,要用 libc crate:

```rust
use libc::{clock_gettime, CLOCK_MONOTONIC_RAW, timespec};

let mut ts = timespec { tv_sec: 0, tv_nsec: 0 };
unsafe { clock_gettime(CLOCK_MONOTONIC_RAW, &mut ts); }
let nanos = ts.tv_sec as u64 * 1_000_000_000 + ts.tv_nsec as u64;
```

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏循环的 dt 处理标准:

**Fixed timestep**(固定步长):

```rust
const FIXED_DT: f32 = 1.0 / 60.0;
let mut accumulator = 0.0;

loop {
    let frame_time = get_frame_time();
    accumulator += frame_time;

    while accumulator >= FIXED_DT {
        update(FIXED_DT);
        accumulator -= FIXED_DT;
    }

    render();
}
```

物理稳定,但渲染插值复杂。

**Variable timestep**(可变步长):

```rust
loop {
    let dt = get_dt();
    update(dt);
    render();
}
```

简单,但物理可能有数值稳定性问题。

**混合**:Casey 用混合方案,update 用 fixed,render 用 variable。

### 3.2 · 🎨 图形学视角

时间在图形学的应用:

**Frame time budget**(帧时间预算)

60 FPS:16.67 ms/帧。包括:
- Game logic:1-2 ms
- Render CPU side:2-5 ms
- Render GPU side:5-10 ms
- Driver overhead:1-3 ms

**Input latency**(输入延迟)

从玩家按键到屏幕反馈的延迟:
- 输入采样:1 帧(16.67ms)
- 处理:1 帧
- 渲染:1 帧
- 显示器刷新:1 帧

总:4 帧 = 67ms。玩家可感知。VR 要求 < 20ms,需要预测渲染。

**TAA(Temporal Anti-Aliasing)**

利用历史帧信息做抗锯齿。dt 不稳会"鬼影"(历史帧对不上)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 时间 API 详解:

**clock_gettime**:

```c
#include <time.h>

struct timespec ts;
clock_gettime(CLOCK_MONOTONIC, &ts);
// CLOCK_REALTIME: 系统时钟,可被 NTP 调整
// CLOCK_MONOTONIC: 单调时钟,不受 NTP 影响但受 NTP 频率调整
// CLOCK_MONOTONIC_RAW: 纯硬件,完全不受 NTP
// CLOCK_PROCESS_CPUTIME_ID: 进程 CPU 时间
// CLOCK_THREAD_CPUTIME_ID: 线程 CPU 时间
```

**timerfd**(Linux 特有):

```c
int fd = timerfd_create(CLOCK_MONOTONIC, 0);
struct itimerspec spec = { ... };
timerfd_settime(fd, 0, &spec, NULL);
// 可以 select / epoll 等 timer fd
```

游戏循环通常用 `clock_gettime + busy loop` 或 `epoll timerfd + block`。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 wall clock 不能用于游戏循环?NTP 调整对游戏有什么具体影响?

**参考解答**:Wall clock(系统时间)可被 NTP 调整。NTP 服务商定期同步系统时钟到参考时间(原子钟),可能:
- **向前调**(系统慢了):瞬间跳几秒,游戏内 dt 巨大,玩家瞬间穿越
- **向后调**(系统快了):时间倒流,dt 负数,游戏循环逻辑崩

具体场景:玩家玩 MMO,NTP 后台运行。突然游戏内 dt = -0.5 秒,所有运动反向,角色掉到地下。

修复:用 monotonic clock,它**保证不倒流**(虽然可能频率调整,但绝对值不减少)。

### Lv2 · 动手实践

**题**:在 Rust 项目里实现稳定的 dt 计算。完成标准:
- 用 `std::time::Instant`
- dt 在 60Hz 和 144Hz 显示器上都对(60Hz: ~16.67ms,144Hz: ~6.94ms)
- 暂停后 dt clamp 到 0.1 秒
- 第一次循环跳过 update(避免初始化长 dt)

**参考解答**:

```rust
use std::time::{Duration, Instant};

pub struct GameClock {
    last_time: Instant,
    first_frame: bool,
    max_dt: Duration,
}

impl GameClock {
    pub fn new() -> Self {
        Self {
            last_time: Instant::now(),
            first_frame: true,
            max_dt: Duration::from_millis(100),  // 100ms clamp
        }
    }

    pub fn next_dt(&mut self) -> Option<f32> {
        let now = Instant::now();
        let raw_dt = now - self.last_time;
        self.last_time = now;

        // 第一次循环:不返回 dt(让游戏跳过 update)
        if self.first_frame {
            self.first_frame = false;
            return None;
        }

        // clamp 防止暂停后大 dt
        let dt = raw_dt.min(self.max_dt);

        Some(dt.as_secs_f32())
    }
}

fn main() {
    let mut clock = GameClock::new();

    loop {
        if let Some(dt) = clock.next_dt() {
            println!("Frame dt: {:.3} ms ({:.1} FPS)",
                dt * 1000.0, 1.0 / dt);
            // update(dt);
        }
        // render();
    }
}
```

**关键解释**:
- `Duration::min(self, other)` — 取较小值,clamp 实现
- `as_secs_f32()` — Duration 转 f32 秒,用于游戏逻辑
- `first_frame` 跳过第一帧的 update,避免初始化长 dt
- 60Hz 显示器:dt ≈ 0.01667;144Hz:dt ≈ 0.00694,自动适配

## 8 · Rust / Arch 落地代码

### Rust:多时钟实现 + 对比

```rust
// Cargo.toml: libc = "0.2"

use std::time::{Duration, Instant};

pub struct MonotonicClock {
    last: Instant,
}

impl MonotonicClock {
    pub fn new() -> Self {
        Self { last: Instant::now() }
    }

    pub fn next_dt(&mut self) -> f32 {
        let now = Instant::now();
        let dt = now - self.last;
        self.last = now;
        dt.as_secs_f32()
    }
}

// Linux 特定:clock_gettime 直接调
#[cfg(target_os = "linux")]
pub struct LinuxRawClock {
    last_ns: u64,
}

#[cfg(target_os = "linux")]
impl LinuxRawClock {
    pub fn new() -> Self {
        Self { last_ns: Self::now_ns() }
    }

    fn now_ns() -> u64 {
        unsafe {
            let mut ts = libc::timespec { tv_sec: 0, tv_nsec: 0 };
            libc::clock_gettime(libc::CLOCK_MONOTONIC_RAW, &mut ts);
            ts.tv_sec as u64 * 1_000_000_000 + ts.tv_nsec as u64
        }
    }

    pub fn next_dt(&mut self) -> f32 {
        let now = Self::now_ns();
        let dt_ns = now.saturating_sub(self.last_ns);
        self.last_ns = now;
        dt_ns as f32 / 1e9
    }
}

fn main() {
    let mut std_clock = MonotonicClock::new();
    #[cfg(target_os = "linux")]
    let mut linux_clock = LinuxRawClock::new();

    // 验证:两种时钟 dt 应该接近
    for i in 0..100 {
        // 模拟一些工作
        std::thread::sleep(Duration::from_millis(16));
        let dt_std = std_clock.next_dt();
        #[cfg(target_os = "linux")]
        let dt_linux = linux_clock.next_dt();

        #[cfg(target_os = "linux")]
        println!("[{}] std: {:.6}s, linux_raw: {:.6}s, diff: {:.3}us",
            i, dt_std, dt_linux, (dt_std - dt_linux).abs() * 1e6);

        #[cfg(not(target_os = "linux"))]
        println!("[{}] std: {:.6}s", i, dt_std);
    }
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
