
# Day 269 · 清理菜单绘制

> 昨天 link + group 系统加进来后,菜单绘制代码变得啰嗦——每个菜单项都要手写"画背景 + 画文字 + 注册 link"。今天 Casey 把这些样板代码抽成 helper 函数,菜单绘制从几十行变成几行。

## 0 · 为什么要有这一天

打开你的代码,看 Top Clocks 视图的绘制函数。每个条目大概长这样:

```rust
// 画排名
draw_rect(buf, ..., Rect::new(10, y, 30, 16), 0xFF4040A0);
// 画文字区背景
draw_rect(buf, ..., Rect::new(50, y, 180, 16), 0xFF404040);
// 画进度条
draw_rect(buf, ..., Rect::new(250, y, bar_w, 16), bar_color);
// 注册 link(点击跳转)
links.push(DebugLink {
    hot_rect: Rect::new(10, y, 240, 16),
    target: LinkTarget::OpenSource { file: "render.rs", line: 42 },
    tooltip: Some("render_entity"),
});
```

20 个条目 = 80 行重复代码,只是 y 坐标和 label 不同。这是**复制粘贴编程**(copy-paste programming)的典型症状。

复制粘贴有几个明显问题:

1. **改一处要改 20 处**:决定把文字区背景色改深,要改 20 行
2. **容易写错**:某个条目忘记注册 link,变成"死链接"
3. **代码膨胀**:函数从 50 行变成 500 行,阅读吃力
4. **意图被淹没**:看代码的人要扫几百行才能看出"哦就是画一个带 link 的菜单项"

今天的重构把这些样板代码抽成 `draw_menu_item` helper:

```rust
draw_menu_item(&mut ctx, &mut links, "render_entity", 482, |c| {
    c.link(LinkTarget::OpenSource { file: "render.rs", line: 42 })
});
```

一行调用做完原来 4 件事。20 个条目变成 20 行调用,可读性翻倍。

心理锚点:做完这个,你的代码"重复度"大幅下降,加新功能时改一处即可。

## 1 · Casey 今天做了什么

Casey 做了一次纯重构,没有新功能:

1. 识别出"重复模式"——菜单项的画背景 + 文字 + 进度条 + link 是固定结构
2. 抽出 `draw_menu_item(ctx, links, label, value, configure)` 函数
3. 用闭包让调用者决定 link target 和颜色(否则函数参数太多)
4. 把 Top Clocks、Bar Chart、Memory 视图都改用 helper 函数
5. 重构后跑一遍,确认视觉一致(像素级 diff)

Casey 在视频里展示了"识别重复模式"的过程:他选中第一个条目的代码,在 IDE 里搜"相似代码",找出 20 个匹配位置。然后他把公共部分提取,差异部分作为参数。这是教科书级别的"Extract Function"重构(Martin Fowler 的经典方法之一)。

## 2 · 心智模型

### 类比:快餐店的"套餐"按钮

麦当劳的点餐机有个"巨无霸套餐"按钮,一键下单:巨无霸 + 中薯条 + 中可乐。你不需分别按 3 个按钮。

`draw_menu_item` 就是这个"套餐按钮":一次调用做 4 件事(背景 + 文字 + 进度条 + link),你不用手动按 4 次。

### 严谨原理:Extract Function 重构

Martin Fowler 在《Refactoring》里定义的 "Extract Function" 步骤:

1. **识别重复**:找到一段被复制多次的代码
2. **找差异**:不同地方的代码哪里不同(变量、参数)
3. **创建新函数**:把公共部分提取,差异部分作为参数
4. **替换调用**:用函数调用替代原来的重复代码
5. **测试**:确认行为不变

具体到今天:

**重复模式**:

```rust
// 画排名区
draw_rect(buf, ..., Rect::new(10, y, 30, 16), 0xFF4040A0);
// 画文字背景
draw_rect(buf, ..., Rect::new(50, y, 180, 16), 0xFF404040);
// 画进度条
let bar_w = (value / max * 400.0) as i32;
draw_rect(buf, ..., Rect::new(250, y, bar_w, 16), bar_color);
// 注册 link
links.push(DebugLink {
    hot_rect: Rect::new(10, y, 240, 16),
    target: ...,
    tooltip: ...,
});
```

**差异**:`y`(位置)、`value`(数据)、`bar_color`(颜色)、`target`(link 目标)、`tooltip`(文字)。

**提取函数**:

```rust
fn draw_menu_item(
    ctx: &mut Ctx,
    links: &mut Vec<DebugLink>,
    y: i32,
    rank_color: u32,
    label: &str,
    value: f32,
    max_value: f32,
    bar_color: u32,
    target: Option<LinkTarget>,
    tooltip: Option<&str>,
) {
    draw_rect(ctx, Rect::new(10, y, 30, 16), rank_color);
    draw_rect(ctx, Rect::new(50, y, 180, 16), 0xFF404040);
    let bar_w = (value / max_value * 400.0) as i32;
    draw_rect(ctx, Rect::new(250, y, bar_w, 16), bar_color);
    if let Some(t) = target {
        links.push(DebugLink {
            hot_rect: Rect::new(10, y, 240, 16),
            target: t,
            tooltip,
        });
    }
}
```

参数太多(9 个),可读性差。Rust 的解决方案:**用 struct 封装参数** 或 **用 builder pattern**。

### 用 struct 封装参数

```rust
struct MenuItemSpec<'a> {
    y: i32,
    rank_color: u32,
    label: &'a str,
    value: f32,
    max_value: f32,
    bar_color: u32,
    target: Option<LinkTarget>,
    tooltip: Option<&'a str>,
}

fn draw_menu_item(ctx: &mut Ctx, links: &mut Vec<DebugLink>, spec: MenuItemSpec) {
    // 内部代码同上,用 spec.xxx 替代参数
}
```

调用方:

```rust
draw_menu_item(&mut ctx, &mut links, MenuItemSpec {
    y: 30,
    rank_color: 0xFF4040A0,
    label: "render_entity",
    value: 482.0,
    max_value: 1000.0,
    bar_color: 0xFFFF4040,
    target: Some(LinkTarget::OpenSource { file: "render.rs", line: 42 }),
    tooltip: Some("render_entity"),
});
```

字段多但每个都有名字,比 9 个位置参数可读性好。

### Builder Pattern

```rust
struct MenuItemBuilder<'a> {
    y: i32,
    rank_color: u32,
    label: &'a str,
    value: f32,
    max_value: f32,
    bar_color: u32,
    target: Option<LinkTarget>,
    tooltip: Option<&'a str>,
}

impl<'a> MenuItemBuilder<'a> {
    fn new(label: &'a str, y: i32) -> Self {
        Self {
            y, label,
            rank_color: 0xFF4040A0,
            value: 0.0,
            max_value: 1.0,
            bar_color: 0xFF808080,
            target: None,
            tooltip: None,
        }
    }
    fn value(mut self, v: f32, max: f32) -> Self { self.value = v; self.max_value = max; self }
    fn color(mut self, c: u32) -> Self { self.bar_color = c; self }
    fn link(mut self, t: LinkTarget) -> Self { self.target = Some(t); self }
    fn build(self, ctx: &mut Ctx, links: &mut Vec<DebugLink>) {
        // 实际绘制
    }
}

// 调用
MenuItemBuilder::new("render_entity", 30)
    .value(482.0, 1000.0)
    .color(0xFFFF4040)
    .link(LinkTarget::OpenSource { file: "render.rs", line: 42 })
    .build(&mut ctx, &mut links);
```

链式调用,优雅,但需要写 builder 类型——代码量大。Casey 用更朴素的 struct 参数,Rust 端我们也走这条路。

### 哪些重复不该提取?

不是所有重复都该提取。Martin Fowler 提出几个反例:

- **偶然重复**:两段代码看起来一样,但意图不同(改一个不该改另一个)
- **跨模块重复**:两个模块各自实现了 list,提取到公共可能不合适(模块独立性受影响)
- **测试代码**:测试里的重复有时反而清晰(显式列出每个测试用例)

Casey 在视频里强调:**提取的目的是"减少修改成本",不是为了消除重复**。如果两段代码未来不会一起改,提取反而增加间接层。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏引擎里"重复代码"很常见,因为很多系统结构相似(每种 entity 的渲染、每种 projectile 的物理)。常见抽象:

- **ECS(System + Component)**:把"循环遍历 entity + 操作 component"提取为 system
- **Helper functions**:`draw_sprite`, `play_sound` 等简单 helper
- **Template Method 模式**:基类定义算法骨架,子类填具体步骤(经典 OOP 模式)
- **Policy / Strategy 模式**:把"可替换的算法"作为参数传入(如不同的排序策略)

Casey 用 helper 函数 + struct 参数,简单直接。生产项目可能用 ECS 或模板方法。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核的"重复代码"管理很有意思——内核社区对"提取公共代码"非常保守,Linus 多次在邮件列表里反对过度抽象。Linus 的名言:

> "抽象是廉价的,但错误的抽象是昂贵的。"

内核里的 helper(如 `list_for_each_entry`)是经过长期演化才提取的,不是一开始就抽象的。这和 Fowler 的观点一致:**先有重复,再提取,而不是预先抽象**。

你的 profiler 也是这样:Day 266 写了 20 个条目的重复代码,今天才提取。如果你 Day 266 就提取了"看似会重复但其实没数据"的代码,反而限制了未来灵活性。

### 3.3 · 🦀 Rust 生态视角

Rust 表达"helper 函数 + 参数封装"几个风格:

#### 风格 1:普通函数 + 多参数

```rust
fn draw_menu_item(y: i32, label: &str, value: f32, ...);
```

简单,但参数多时难读。

#### 风格 2:struct 参数

```rust
fn draw_menu_item(spec: MenuItemSpec);
```

字段有名字,可读性好。Rust struct literal 写起来也简洁(`Spec { field: value, ... }`)。

#### 风格 3:Builder pattern

```rust
MenuItemBuilder::new(...).value(...).color(...).build();
```

优雅,但代码量大。

#### 风格 4:Closure(回调)

```rust
fn draw_menu_item<F>(y: i32, label: &str, configure: F)
where F: FnOnce(&mut MenuItemCtx) -> ()
{
    let mut item_ctx = MenuItemCtx::new(y, label);
    configure(&mut item_ctx);
    item_ctx.render();
}

// 调用
draw_menu_item(30, "render_entity", |item| {
    item.set_value(482.0, 1000.0);
    item.set_color(0xFFFF4040);
    item.set_link(...);
});
```

闭包让调用者灵活定制,但闭包内不能"借用外部变量又写外部变量",Rust 借用检查可能限制。

#### Casey 风格:函数 + 多参数 + 注释

C 的 Casey 用最朴素的方式:

```c
draw_menu_item(y, "render_entity", 482.0, 1000.0, 0xFFFF4040, &link_target, "tooltip");
```

C 没有命名参数,可读性差,但简单。Rust 端我们用 struct 参数(`Spec { ... }`)即可,不需要 builder。

### 3.4 · 软件工程:重构原则

今天是第二次重构(Day 265 是第一次)。Fowler 的重构原则:

1. **小步前进**:每次只重构一处,跑测试
2. **行为不变**:重构不引入新功能
3. **测试覆盖**:重构前要有测试,否则无法验证行为不变
4. **commit 粒度**:每次重构一个 commit
5. **不要混合重构和新功能**:重构 commit 里只有重构,新功能另一个 commit

Casey 严格遵守这些。今天他做的:
- 不改 UI 视觉
- 不改业务逻辑
- 不加新 view
- 只改"如何画 menu item"

## 5 · 对照与变奏

### 不同语言的 helper 抽象

| 语言 | 风格 | 例子 |
|---|---|---|
| C | 函数 + 多参数 | `draw_menu_item(y, label, value, ...)` |
| C++ | 函数 + struct + 可选 builder | 类似 C + 方法 |
| Rust | struct 参数 | `Spec { ... }` |
| Python | keyword arguments | `draw(y=30, label="...")` |
| JavaScript | options object | `draw({ y: 30, label: "..." })` |
| Swift | labeled arguments | `draw(y: 30, label: "...")` |

Rust 没有 named arguments,但 struct 字段名效果类似。

### Macro vs Function

Rust 的 macro 也能消除重复:

```rust
macro_rules! menu_item {
    ($y:expr, $label:expr, $value:expr, $color:expr) => {
        draw_rect(...);
        links.push(DebugLink { ... });
    };
}
```

macro 在编译期展开,无运行时开销,但调试困难(报错信息指向展开后的代码)。Casey 的 C 也用 macro(`#define`),但 Rust 端我们倾向用普通函数——可读性和调试体验更好。

### 抽象的代价

抽象不是免费:

1. **间接层增加**:读代码要跳到 helper 函数才能看实现
2. **参数列表增长**:helper 参数越多,调用越啰嗦
3. **灵活性下降**:helper 写死后,特殊场景要绕过

Fowler 的建议:**先写重复代码,等重复 3 次以上再提取**(Rule of Three)。今天的 menu item 已经重复 20 次,远超阈值。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:有人说"重构应该和新功能一起做,节省时间"。请反驳,给出至少 3 个理由说明"重构和新功能必须分开 commit"。

**参考解答**:
1. **git blame 清晰**:重构 commit 不改行为,git blame 能正确归因——看到一行代码,知道它是"何时引入的功能"还是"何时换的实现"。混合 commit 让 blame 失效
2. **回退方便**:重构 commit 永远安全(行为不变),可以随时 revert。功能 commit 可能引入 bug,要单独 revert。混合时 revert 会一起丢功能
3. **review 友好**:review 一个 1000 行的"重构 + 新功能"PR 极其痛苦;分开成"500 行重构(纯移动)+ 500 行新功能"则清晰
4. **bug 定位**:重构引入的 bug 在"重构 commit 单独测试"时立即暴露;混合 commit 里 bug 可能被误归因为新功能
5. **心智负担**:重构时大脑切换到"结构改善"模式,新功能时切换到"问题解决"模式。混合 commit 需要频繁切换,效率下降
6. **CI 反馈**:重构 PR 跑测试 100% 通过(行为不变),如果有失败说明重构引入 bug,立即发现。混合 PR 的失败可能是新功能的预期失败

Fowler 在《Refactoring》第二版里反复强调:**重构和新功能交替进行(红绿重构循环),不要在同一次改动里混合**。

### Lv2 · 动手实践

**题**:重构下面的重复代码,提取一个 `draw_menu_item` helper。重构前后行为一致。

重构前:

```rust
// 条目 1
draw_rect(buf, ..., Rect::new(10, 30, 30, 16), 0xFF4040A0);
draw_rect(buf, ..., Rect::new(50, 30, 180, 16), 0xFF404040);
draw_rect(buf, ..., Rect::new(250, 30, 482, 16), 0xFFFF4040);
links.push(DebugLink { hot_rect: Rect::new(10, 30, 240, 16), target: ..., tooltip: ... });

// 条目 2
draw_rect(buf, ..., Rect::new(10, 50, 30, 16), 0xFF4040A0);
draw_rect(buf, ..., Rect::new(50, 50, 180, 16), 0xFF404040);
draw_rect(buf, ..., Rect::new(250, 50, 312, 16), 0xFFFFFF40);
links.push(DebugLink { hot_rect: Rect::new(10, 50, 240, 16), target: ..., tooltip: ... });

// ... 18 个类似条目
```

完成标准:重构后每个条目用一行调用,代码总行数减少 70% 以上。

**参考解答**:

```rust
#[derive(Clone, Copy)]
struct Rect { x: i32, y: i32, w: i32, h: i32 }

#[derive(Clone)]
struct MenuItemSpec {
    y: i32,
    bar_w: i32,
    bar_color: u32,
    target: LinkTarget,
    tooltip: &'static str,
}

#[derive(Clone, Copy)]
enum LinkTarget {
    Source { line: u32 },
    // ...
}

fn draw_rect(buf: &mut [u32], buf_w: usize, buf_h: usize, r: Rect, color: u32) {
    for py in r.y.max(0)..(r.y + r.h).min(buf_h as i32) {
        for px in r.x.max(0)..(r.x + r.w).min(buf_w as i32) {
            buf[(py as usize) * buf_w + (px as usize)] = color;
        }
    }
}

fn draw_menu_item(
    buf: &mut [u32],
    buf_w: usize,
    buf_h: usize,
    links: &mut Vec<(Rect, LinkTarget, &'static str)>,
    spec: MenuItemSpec,
) {
    draw_rect(buf, buf_w, buf_h, Rect::new(10, spec.y, 30, 16), 0xFF4040A0);
    draw_rect(buf, buf_w, buf_h, Rect::new(50, spec.y, 180, 16), 0xFF404040);
    draw_rect(buf, buf_w, buf_h, Rect::new(250, spec.y, spec.bar_w, 16), spec.bar_color);
    links.push((Rect::new(10, spec.y, 240, 16), spec.target, spec.tooltip));
}

fn main() {
    let mut buf = vec![0u32; 800 * 600];
    let mut links: Vec<(Rect, LinkTarget, &'static str)> = Vec::new();

    // 重构后:每个条目一行
    let specs = [
        MenuItemSpec { y: 30, bar_w: 482, bar_color: 0xFFFF4040, target: LinkTarget::Source { line: 42 }, tooltip: "render_entity" },
        MenuItemSpec { y: 50, bar_w: 312, bar_color: 0xFFFFFF40, target: LinkTarget::Source { line: 87 }, tooltip: "update_physics" },
        MenuItemSpec { y: 70, bar_w: 234, bar_color: 0xFFFFFF40, target: LinkTarget::Source { line: 110 }, tooltip: "load_texture" },
        // ... 更多
    ];

    for spec in specs.iter() {
        draw_menu_item(&mut buf, 800, 600, &mut links, spec.clone());
    }

    println!("Drew {} menu items, registered {} links",
             specs.len(), links.len());
}
```

**每行解释**:
- `MenuItemSpec` 把所有可变参数集中,字段有名字
- `draw_menu_item` 接受 spec,内部用 spec.xxx
- 调用方变成"构造 spec + 调用函数",可读性大幅提升
- `for spec in specs.iter()` 循环处理所有条目,消除了 18 个重复的代码块

### 完整重构:profiler 用 helper 函数

```rust
// Cargo.toml:
// [dependencies]
// minifb = "0.27"

use minifb::{Key, Window, WindowOptions};

const WIDTH: usize = 800;
const HEIGHT: usize = 600;

#[derive(Clone, Copy, Debug)]
struct Rect { x: i32, y: i32, w: i32, h: i32 }

impl Rect {
    fn new(x: i32, y: i32, w: i32, h: i32) -> Self { Self { x, y, w, h } }
}

#[derive(Clone, Copy, Debug)]
enum ViewMode { BarChart, TopClocks, Memory }

#[derive(Clone, Copy, Debug)]
enum LinkTarget {
    OpenSource { line: u32 },
    SwitchView(ViewMode),
}

#[derive(Clone, Debug)]
struct MenuItemSpec {
    label: &'static str,
    bar_w: i32,
    bar_color: u32,
    target: LinkTarget,
}

fn draw_rect(buf: &mut [u32], buf_w: usize, buf_h: usize, r: Rect, color: u32) {
    for py in r.y.max(0)..(r.y + r.h).min(buf_h as i32) {
        for px in r.x.max(0)..(r.x + r.w).min(buf_w as i32) {
            buf[(py as usize) * buf_w + (px as usize)] = color;
        }
    }
}

/// 重构的核心:helper 函数,接受 spec 一行画完所有元素
fn draw_menu_item(
    buf: &mut [u32],
    buf_w: usize,
    buf_h: usize,
    y: i32,
    spec: &MenuItemSpec,
) {
    // 排名区
    draw_rect(buf, buf_w, buf_h, Rect::new(10, y, 30, 16), 0xFF4040A0);
    // 文字背景
    draw_rect(buf, buf_w, buf_h, Rect::new(50, y, 180, 16), 0xFF404040);
    // 进度条
    draw_rect(buf, buf_w, buf_h, Rect::new(250, y, spec.bar_w, 16), spec.bar_color);
    // 颜色编码条目尾
    draw_rect(buf, buf_w, buf_h,
              Rect::new(250 + spec.bar_w, y, 200 - spec.bar_w.max(0).min(200), 16),
              0xFF202020);
}

fn main() {
    let mut window = Window::new(
        "Menu Item Helper Refactor", WIDTH, HEIGHT,
        WindowOptions::default(),
    ).expect("Failed to open window");

    let mut buffer = vec![0u32; WIDTH * HEIGHT];
    let mut frame_count = 0u64;

    // 用 helper 后,Top Clocks 数据是简单数组
    let menu_items: Vec<MenuItemSpec> = vec![
        MenuItemSpec { label: "render_entity",  bar_w: 482, bar_color: 0xFFFF4040, target: LinkTarget::OpenSource { line: 42 } },
        MenuItemSpec { label: "update_physics", bar_w: 312, bar_color: 0xFFFFFF40, target: LinkTarget::OpenSource { line: 87 } },
        MenuItemSpec { label: "load_texture",   bar_w: 234, bar_color: 0xFFFFFF40, target: LinkTarget::OpenSource { line: 110 } },
        MenuItemSpec { label: "audio_mix",      bar_w: 87,  bar_color: 0xFF40FF40, target: LinkTarget::OpenSource { line: 156 } },
        MenuItemSpec { label: "debug_overlay",  bar_w: 52,  bar_color: 0xFF40FF40, target: LinkTarget::OpenSource { line: 200 } },
        MenuItemSpec { label: "anim_update",    bar_w: 45,  bar_color: 0xFF40FF40, target: LinkTarget::OpenSource { line: 230 } },
        MenuItemSpec { label: "particle_sim",   bar_w: 38,  bar_color: 0xFF40FF40, target: LinkTarget::OpenSource { line: 245 } },
        MenuItemSpec { label: "input_process",  bar_w: 12,  bar_color: 0xFF40FF40, target: LinkTarget::OpenSource { line: 260 } },
    ];

    while window.is_open() && !window.is_key_down(Key::Escape) {
        // 清屏
        for px in buffer.iter_mut() { *px = 0xFF101010; }

        // Top Clocks 视图
        let title_rect = Rect::new(20, 20, 760, 30);
        draw_rect(&mut buffer, WIDTH, HEIGHT, title_rect, 0xFF303030);

        // 用 helper 画每个条目:8 行 vs 32 行
        for (i, spec) in menu_items.iter().enumerate() {
            let y = 70 + i as i32 * 20;
            draw_menu_item(&mut buffer, WIDTH, HEIGHT, y, spec);
        }

        window.update_with_buffer(&buffer, WIDTH, HEIGHT).unwrap();
        frame_count += 1;
    }

    println!("Rendered {} frames", frame_count);
}
```

**关键 Rust 特性解释**:

- `MenuItemSpec` 是 `Clone`,因为 `for ... enumerate()` 给的是引用,但 helper 接受 `&MenuItemSpec`(用引用避免 clone)
- helper 内部只画矩形,不处理 link(简化示例,实际把 link 也封装进去)
- `for (i, spec) in menu_items.iter().enumerate()` 同时得到索引和元素
- 8 个条目用 8 行循环 + 1 行 helper 定义,代替了 32 行重复代码

### 进一步展开:从概念到落地的完整路径

要把今天讨论的抽象概念变成可运行的代码,我们必须经历几个具体阶段。这一节展开每一步的工程细节。

**阶段一:定义接口**。Casey 在动手实现前,先想清楚 API。Rust 的 trait 是定义接口的工具:

```rust
trait Sortable {

    fn bounds(&self) -> Aabb;
    fn layer(&self) -> u8;
}
```

trait 让代码可测试、可替换。Casey 经常说"先写 trait,再写 impl"——这强迫你思考抽象边界。

**阶段二:单元测试**。每个 sort_rule 分支都应有对应测试:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_basic_ordering() {
        let a = TestEntity { layer: 1, y: 100.0 };
        let b = TestEntity { layer: 1, y: 200.0 };
```

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
