# Day 364 · 启用 OpenGL 深度缓冲

> Day 358 讲了 depth buffer 概念,Day 359-363 数学铺垫完毕。今天 Casey 真正**启用 OpenGL 的 depth buffer**——从 CPU 软渲染的"自己管理 depth",切到 GPU 硬件 depth test。短短几行 OpenGL 调用,但意义深远:HH 正式进入"硬件加速 3D 渲染"。

## 0 · 为什么要有这一天

Day 358 Casey 在 CPU 实现了 depth buffer。慢。1920×1080 framebuffer,每像素 f32 depth = 8MB,每帧 fill 一次 + 每三角形比较,纯 CPU 算力浪费。

GPU 硬件深度测试:

1. **专用硬件**:ROP 单元做 depth test,数百并行
2. **Early-Z**:fragment shader 之前做深度测试,跳过被遮挡的 fragment
3. **Hi-Z**:分层深度缓冲,粗筛加速
4. **压缩**:深度缓冲硬件压缩,带宽减少 4x

性能:CPU 1ms vs GPU 0.01ms(同样分辨率)。

今天的代码改动**极少**(10 行 OpenGL 调用),但**意义重大**——HH 从软渲染正式切到硬件 3D 渲染。后续 Phase 7+ 全部依赖 GPU。

心理锚点:今天之后你能配置 OpenGL depth buffer,理解深度测试 / 深度写入的区别,知道何时禁用深度(透明物体)。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 打开 OpenGL 初始化代码,加几行:

```c
// 1. 创建带 depth buffer 的 framebuffer
GLuint fbo;
glGenFramebuffers(1, &fbo);
glBindFramebuffer(GL_FRAMEBUFFER, fbo);

GLuint color_tex, depth_tex;
glGenTextures(1, &color_tex);
glBindTexture(GL_TEXTURE_2D, color_tex);
glTexImage2D(GL_TEXTURE_2D, 0, GL_RGBA8, w, h, 0, GL_RGBA, GL_UNSIGNED_BYTE, NULL);
glFramebufferTexture2D(GL_FRAMEBUFFER, GL_COLOR_ATTACHMENT0, GL_TEXTURE_2D, color_tex, 0);

// 关键:加 depth texture
glGenTextures(1, &depth_tex);
glBindTexture(GL_TEXTURE_2D, depth_tex);
glTexImage2D(GL_TEXTURE_2D, 0, GL_DEPTH_COMPONENT24, w, h, 0, GL_DEPTH_COMPONENT, GL_FLOAT, NULL);
glFramebufferTexture2D(GL_FRAMEBUFFER, GL_DEPTH_ATTACHMENT, GL_TEXTURE_2D, depth_tex, 0);

// 2. 启用深度测试
glEnable(GL_DEPTH_TEST);
glDepthFunc(GL_LESS);  // 默认值,新 z 小于已存 z 通过
glDepthMask(GL_TRUE);  // 允许写深度

// 3. 每帧清屏时也清深度
glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT);
glClearDepthf(1.0);  // 清成最大深度(远)
```

Casey 验证:多个 sprite card 在 3D 空间,正确遮挡。之前 2D 排序的代码可以删掉——depth buffer 自动处理。

## 2 · 心智模型

### 类比:GPU 是"超级厨房"

CPU 是个会做菜的厨师,一个一个做。GPU 是有 10000 个厨师的厨房,同时做。

depth buffer 是"判断菜是否被覆盖"的步骤。CPU 厨师一个个比较(慢),GPU 厨房并行比较每个像素(快)。

Casey Day 364 的改动:**把"比较 depth"任务外包给 GPU**。CPU 只负责"画什么三角形",GPU 负责"哪个像素该画"。

### OpenGL Depth Buffer 的状态机

OpenGL 是状态机。depth 相关状态:

```
glEnable(GL_DEPTH_TEST);   // 开/关 depth test
glDisable(GL_DEPTH_TEST);

glDepthFunc(func);          // 比较函数:LESS / LEQUAL / GREATER / ALWAYS...
glDepthMask(true/false);    // 是否写 depth buffer

glClearDepthf(1.0);         // 清屏时的 depth 值(通常 1.0 = 远)
glClear(GL_DEPTH_BUFFER_BIT);  // 清 depth buffer
```

默认状态:

- `GL_DEPTH_TEST`:禁用
- `GL_DEPTH_FUNC`:GL_LESS
- `GL_DEPTH_MASK`:GL_TRUE(写)

启用 depth buffer:`glEnable(GL_DEPTH_TEST)` + 每帧 `glClear`。

### Depth Function 选择

```
GL_LESS:     新 z < 已存 z 通过(默认,标准)
GL_LEQUAL:   新 z <= 已存 z(画等深度物体时用,如 decals)
GL_GREATER:  新 z > 已存 z(用于 reversed-Z)
GL_GEQUAL:   新 z >= 已存 z
GL_EQUAL:    新 z == 已存 z(stencil 风格)
GL_NOTEQUAL: 新 z != 已存 z
GL_ALWAYS:   总通过(等价禁用 depth test)
GL_NEVER:    总失败(用不到)
```

Casey Day 364 用默认 GL_LESS。后续如果切 reversed-Z,用 GL_GREATER。

### Depth Mask(深度写入)

`glDepthMask(GL_FALSE)` 让 depth test 仍进行,但**不更新** depth buffer。

用途:**透明物体**。

透明物体(玻璃、水)不挡后面的东西,所以不该写 depth(否则后面被遮挡)。但仍需 depth test(透明物体前的更透明物体可以正确叠加)。

```c
// 画不透明物体
glDepthMask(GL_TRUE);
draw_opaque_objects();

// 切透明模式
glEnable(GL_BLEND);
glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA);
glDepthMask(GL_FALSE);  // 不写深度

// 透明物体按距离从远到近排序
draw_transparent_objects_sorted();

glDepthMask(GL_TRUE);
glDisable(GL_BLEND);
```

### Depth Buffer 的格式

```
GL_DEPTH_COMPONENT16:  16 位 depth,精度低(慎用)
GL_DEPTH_COMPONENT24:  24 位 depth,主流
GL_DEPTH_COMPONENT32:  32 位(整型),少用
GL_DEPTH_COMPONENT32F: 32 位浮点,用于 reversed-Z
GL_DEPTH24_STENCIL8:   24 位 depth + 8 位 stencil,主流(DXGI 标准格式)
GL_DEPTH32F_STENCIL8:  32 位浮点 depth + 8 位 stencil,现代引擎标配
```

Casey Day 364 用 DEPTH_COMPONENT24(兼容性好)。生产用 DEPTH24_STENCIL8(同时得到 stencil)。

### Clear 操作

每帧开始必须清屏:

```c
glClearColor(0.2, 0.3, 0.4, 1.0);  // 颜色清成深蓝灰
glClearDepthf(1.0);                  // depth 清成 1.0(最远)
glClearStencil(0);                   // stencil 清成 0
glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT | GL_STENCIL_BUFFER_BIT);
```

不清 depth buffer 会导致"上一帧的深度残留",新物体错误地被遮挡。

`glClearDepthf(1.0)` 是清成最远(z=1.0 in OpenGL NDC)。reversed-Z 则清成 0.0。

### Polygon Offset

两个面共面(z-fighting),用 polygon offset 强制分离:

```c
glEnable(GL_POLYGON_OFFSET_FILL);
glPolygonOffset(factor, units);
// factor:基于深度斜率的偏移
// units:固定偏移
```

常用于 decals(墙上的弹孔贴在墙上,可能 z-fight)。

### Early-Z 优化

如果 fragment shader 不修改深度(`gl_FragDepth` 未写),GPU 可以**在 fragment shader 之前**做 depth test。被遮挡的像素直接跳过 fragment shader,极大省时间。

```glsl
// fragment shader
#version 330 core
// 注意:不要写 gl_FragDepth,GPU 自动用插值的深度
out vec4 frag_color;
void main() {
    frag_color = ...;
    // gl_FragDepth = ...;  // 写这个会禁用 early-Z!
}
```

Casey HH 不修改 gl_FragDepth,自然享受 early-Z 加速。

### Rust + glow 示例

```rust
use glow::*;

let gl = ...;

// 启用 depth test
unsafe {
    gl.enable(DEPTH_TEST);
    gl.depth_func(LESS);  // 比较:新 z < 已存 z 通过
    gl.depth_mask(true);

    // 每帧清屏
    gl.clear_color(0.2, 0.3, 0.4, 1.0);
    gl.clear_depth_f32(1.0);
    gl.clear(COLOR_BUFFER_BIT | DEPTH_BUFFER_BIT);
}
```

### 3.2 · 图形学视角

深度精度问题:

- **Z-fighting**:共面物体闪烁(前述)

- **近裁剪过近**:near=0.001 严重浪费精度

业界经验:

- near 别太小(0.1 起步,不是 0.001)
- far 别太大(够用就行)
- 24 位 depth 够大多数场景
- 大场景用 reversed-Z

## 5 · 对照与变奏

### Depth Buffer vs Stencil Buffer

- **Depth**:每像素 f32(或 24 位定点),表示"多深"
- **Stencil**:每像素 u8,用作"是否允许画"的 mask

两者常一起用(DEPTH24_STENCIL8 格式)。Stencil 用于:

- 阴影体(shadow volume)
- 镜面反射
- 透视裁剪(只画屏幕某区域)

### 不同 API 的 depth

- **OpenGL**:`glEnable(GL_DEPTH_TEST)`,NDC z ∈ [-1, 1]
- **Vulkan**:`vkCmdSetDepthTestEnable`,NDC z ∈ [0, 1]
- **DirectX 12**:`DepthEnable = TRUE`,NDC z ∈ [0, 1]
- **Metal**:`depthAttachmentPixelFormat`,NDC z ∈ [0, 1]

API 差异主要是 NDC z 范围(影响投影矩阵)。

### 历史演化

- **1990s**:OpenGL 1.0 有 depth buffer
- **2000s**:24 位 depth + 8 位 stencil 成主流
- **2010s**:reversed-Z + 浮点深度普及
- **2020s**:Variable Rate Shading + 深度感知优化

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么透明物体要 `glDepthMask(GL_FALSE)`?

**参考解答**:透明物体(玻璃、水)不完全挡后面的东西——后面的物体应该透过透明物体部分可见。

如果透明物体写 depth buffer:depth buffer 记录"透明物体在这里",后面的物体 depth test 失败,**完全被遮挡**——错误。

`glDepthMask(GL_FALSE)` 让透明物体**仍做 depth test**(透明物体前的更近透明物体仍正确叠加),但**不更新 depth buffer**(后面物体仍能通过 depth test)。

配合 alpha blending:`glEnable(GL_BLEND); glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)`。

### Lv2 · 动手实践

**题**:用 glow 创建带 depth buffer 的 OpenGL context,画两个深度不同的方块,验证 depth test 工作。

完成标准:深度大的方块被深度小的方块遮挡(绘制顺序无关)。

**参考解答**(伪代码,实际需要 window 创建):

```rust
// 完整代码需要 winit + glow,这里只展示关键 API
use glow::*;

fn setup_depth(gl: &Context) {
    unsafe {
        // 启用 depth test
        gl.enable(DEPTH_TEST);
        gl.depth_func(LESS);  // 默认就是 LESS,显式说明
        gl.depth_mask(true);
    }
}

fn render_frame(gl: &Context) {
    unsafe {
        // 每帧清屏 + 清深度
        gl.clear_color(0.2, 0.3, 0.4, 1.0);
        gl.clear_depth_f32(1.0);  // 清成最远
        gl.clear(COLOR_BUFFER_BIT | DEPTH_BUFFER_BIT);

        // 画前面的方块(z = -5)
        gl.use_program(Some(front_shader));
        gl.uniform_matrix4f(Some(&front_mvp_loc), false, &mvp_front);
        gl.draw_arrays(TRIANGLES, 0, 6);

        // 画后面的方块(z = -10)
        // 即使后画,因为 z 更远,depth test 会失败,前面方块仍可见
        gl.use_program(Some(back_shader));
        gl.uniform_matrix4f(Some(&back_mvp_loc), false, &mvp_back);
        gl.draw_arrays(TRIANGLES, 0, 6);
    }
}

// 验证:把上面两个 draw_arrays 顺序对调,结果一样
// 没有 depth test 时,顺序对调结果不同(后画覆盖)
```

**简化版**(纯概念,不实际跑 OpenGL):

```rust
// 模拟 depth buffer
struct FakeGPU {
    color: Vec<[u8; 4]>,  // WIDTH * HEIGHT
    depth: Vec<f32>,      // WIDTH * HEIGHT,初始 1.0
    depth_test_enabled: bool,
    depth_mask: bool,
}

impl FakeGPU {
    fn draw_pixel(&mut self, x: usize, y: usize, z: f32, color: [u8; 4]) {
        let idx = y * 1920 + x;
        if self.depth_test_enabled {
            if z >= self.depth[idx] {
                return;  // 深度测试失败
            }
        }
        self.color[idx] = color;
        if self.depth_mask {
            self.depth[idx] = z;
        }
    }
}

fn main() {
    let w = 1920;
    let h = 1080;
    let mut gpu = FakeGPU {
        color: vec![[0; 4]; w * h],
        depth: vec![1.0; w * h],
        depth_test_enabled: true,
        depth_mask: true,
    };

    // 先画远处方块(z=0.8)
    for x in 100..200 {
        for y in 100..200 {
            gpu.draw_pixel(x, y, 0.8, [255, 0, 0, 255]);  // 红
        }
    }

    // 后画近处方块(z=0.3)
    for x in 150..250 {
        for y in 150..250 {
            gpu.draw_pixel(x, y, 0.3, [0, 255, 0, 255]);  // 绿
        }
    }

    // 检查重叠区域(150-200, 150-200)
    // 应该是绿色(近处方块覆盖远处)
    let px = gpu.color[150 * 1920 + 150];
    println!("Overlap pixel: {:?} (expected green)", px);
    assert_eq!(px, [0, 255, 0, 255]);

    // 检查未重叠的远处方块
    let px = gpu.color[100 * 1920 + 100];
    println!("Far-only pixel: {:?} (expected red)", px);
    assert_eq!(px, [255, 0, 0, 255]);

    println!("Depth test works!");
}
```

## 8 · Rust / Arch 落地代码

### 完整可跑示例:模拟 depth buffer

```rust
const W: usize = 80;
const H: usize = 40;

struct FakeGPU {
    color: Vec<char>,
    depth: Vec<f32>,
    depth_test: bool,
    depth_write: bool,
    depth_func: DepthFunc,
}

#[derive(PartialEq)]
enum DepthFunc { Less, Lequal, Greater, Always }

impl FakeGPU {
    fn new() -> Self {
        Self {
            color: vec![' '; W * H],
            depth: vec![1.0; W * H],
            depth_test: true,
            depth_write: true,
            depth_func: DepthFunc::Less,
        }
    }

    fn clear(&mut self) {
        for c in &mut self.color { *c = ' '; }
        for d in &mut self.depth { *d = 1.0; }
    }

    fn test(&self, new_z: f32, old_z: f32) -> bool {
        match self.depth_func {
            DepthFunc::Less => new_z < old_z,
            DepthFunc::Lequal => new_z <= old_z,
            DepthFunc::Greater => new_z > old_z,
            DepthFunc::Always => true,
        }
    }

    fn draw_pixel(&mut self, x: usize, y: usize, z: f32, c: char) {
        if x >= W || y >= H { return; }
        let idx = y * W + x;
        if self.depth_test && !self.test(z, self.depth[idx]) {
            return;
        }
        self.color[idx] = c;
        if self.depth_write {
            self.depth[idx] = z;
        }
    }

    fn fill_rect(&mut self, x0: usize, y0: usize, x1: usize, y1: usize, z: f32, c: char) {
        for y in y0..y1 {
            for x in x0..x1 {
                self.draw_pixel(x, y, z, c);
            }
        }
    }

    fn display(&self) {
        for y in 0..H {
            let row: String = (0..W).map(|x| self.color[y * W + x]).collect();
            println!("{}", row);
        }
    }
}

fn main() {
    let mut gpu = FakeGPU::new();

    println!("=== Test 1: depth test on, draw far then near ===");
    gpu.clear();
    gpu.fill_rect(5, 5, 50, 30, 0.8, 'F');  // Far
    gpu.fill_rect(20, 15, 70, 35, 0.3, 'N'); // Near
    gpu.display();
    println!("(Near 'N' should overlap Far 'F')\n");

    println!("=== Test 2: depth test disabled ===");
    gpu.clear();
    gpu.depth_test = false;
    gpu.fill_rect(5, 5, 50, 30, 0.8, 'F');  // 先画 F
    gpu.fill_rect(20, 15, 70, 35, 0.3, 'N'); // N 覆盖 F(无视深度)
    gpu.display();
    println!("(N covers F even though drawn 'far first' - depth ignored)\n");
    gpu.depth_test = true;

    println!("=== Test 3: depth_write disabled (transparent) ===");
    gpu.clear();
    gpu.depth_write = false;
    gpu.fill_rect(5, 5, 50, 30, 0.5, 'T');  // 透明(不写 depth)
    gpu.depth_write = true;
    // 在 T 后面画一个,应该不被 T 挡(因为 T 没写 depth)
    gpu.fill_rect(25, 10, 60, 35, 0.7, 'B'); // B 比 T 远,但因为 T 没写 depth,B 仍画
    gpu.display();
    println!("(Both T and B visible - T didn't write depth)\n");

    println!("=== Test 4: different depth functions ===");
    let mut gpu2 = FakeGPU::new();
    gpu2.clear();
    gpu2.depth_func = DepthFunc::Greater;
    gpu2.fill_rect(5, 5, 50, 30, 0.3, 'A');  // 较近 z=0.3
    // Greater:新 z > 已存 z 通过
    // 已存 0.3,要画 z=0.8 大于 0.3 → 通过
    gpu2.fill_rect(20, 15, 70, 35, 0.8, 'B');
    gpu2.display();
    println!("(Reversed-Z style: B (far) covers A (near))");
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
