# Day 430 · 分层与多线程化光照

> 光照计算是 CPU 密集任务,但你的 CPU 有 8 个核心。之前只用 1 个,7 个闲着。今天 Casey 用 `rayon` 并行化光照计算——每个图元独立算,rayon 自动分配到所有核心。8 核 CPU 上理论 8 倍加速,实际 4-6 倍(因缓存竞争和同步开销)。

## 0 · 为什么要有这一天

回顾 day415:每个图元的光照计算独立。这是个**令人尴尬的并行问题**(embarrassingly parallel)——把每个图元交给不同核心,互不干扰。

之前 Casey 用单线程 for 循环:

```rust
for primitive in &primitives {
    lighting[i] = compute(primitive);
}
```

CPU 利用率 1/8,7 个核心闲着。

改用 rayon:

```rust
let lighting: Vec<_> = primitives.par_iter()
    .map(|p| compute(p))
    .collect();
```

`par_iter()` 替代 `iter()`,rayon 自动并行。8 核 CPU 上,**理论 8 倍加速**。

实际收益:

- 单线程 50ms/帧 → 多线程 10ms/帧
- 帧率从 20 FPS → 100 FPS
- 多余的 CPU 时间可以加更多光源、更多采样

但并行有"坑":

1. **数据竞争**:多个线程同时修改共享数据,Rust ownership 帮助避免
2. **缓存竞争**:多个核心访问同一缓存行,性能退化(false sharing)
3. **同步开销**:线程间通信有成本,小任务可能反而慢
4. **确定性丢失**:多线程顺序不定,bug 难复现

Casey 今天解决这些问题。重点:**halton 序列让多线程也能确定性**(每线程独立 sampler,起点不同但结果一致)。

工业的所有现代游戏引擎(Bevy、Unreal、Unity DOTS)都默认多线程光照。Casey 现在跟上。

心理锚点:今天之后,你能用 rayon 并行化任意 for 循环,理解多线程的常见坑,知道 Rust 的 ownership 如何让并行安全,能为自己的项目榨干 CPU。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 把光照计算改成并行:

1. **加 rayon 依赖**:`rayon = "1"`
2. **改 `iter` 为 `par_iter`**:光照循环变成并行
3. **处理 sampler**:每线程独立 HaltonSampler,起始 index 不同

- 单线程:50ms
- 8 核:12ms(4.2x)
- 16 核:8ms(理论 8x,但缓存竞争限制)

接近"令人尴尬的并行"的理论上限。

## 2 · 心智模型

### 类比:多人协作

想象你和小伙伴整理书架。1 个人按顺序整理,慢。8 个人分工,每人整理 1 层,快——前提是**互不干扰**(各整理各的层)。

如果你们同时拿同一本书,就乱了(数据竞争)。如果你们要互相确认"这本书放哪",慢(同步开销)。

rayon 是"自动分工"——你给它一个 `par_iter`,它把工作切成小块,分给可用的核心,自动同步。Rust 的 ownership 保证"不互相干扰"——编译器拒绝有竞争的代码。

### 严谨原理:Work-stealing 调度

rayon 用 **work-stealing**(工作窃取)调度:

1. 工作切成小任务,放进每核心的本地队列
2. 核心从自己队列取任务
3. 队列空了,从其他核心"偷"任务
4. 自动负载均衡

优点:

- 动态均衡(任务长短不一)
- 无锁(每核心本地队列)
- 缓存友好(任务在本地核心上跑)

`par_iter` 内部把迭代器切成 chunks,每个 chunk 是一个任务。chunk 大小自动调整(动态)。

### 数据并行 vs 任务并行

**数据并行**(本日):**同样**的操作应用到**不同**的数据。每图元算光照,数据是图元,操作是计算。

**任务并行**:**不同**的操作,各自有数据。一个线程跑物理,一个跑 AI,一个跑音频。

rayon 主要做数据并行。任务并行用 `tokio` 或裸 `std::thread`。

### Rust 视角:rayon 用法

```rust
use rayon::prelude::*;

let primitives = vec![/* ... */];

// 单线程
let results: Vec<_> = primitives.iter().map(|p| compute(p)).collect();

// 多线程
let results: Vec<_> = primitives.par_iter().map(|p| compute(p)).collect();
```

`par_iter()` 返回 `ParallelIterator`,API 和 `Iterator` 类似(map、filter、collect)。学习成本极低。

并行要求:

- 闭包 `|p| compute(p)` 必须 `Send + Sync`(可以跨线程)
- 闭包内部不能有 `&mut` 共享状态
- 返回值 `T` 必须 `Send`

Rust 编译器检查这些,违反就编译失败。所以"数据竞争"在 Rust + rayon 里**编译期消除**。

### 处理 sampler

day427 提到:多线程共享 RNG 不安全。解决:**每线程独立 sampler**。

```rust
use rayon::prelude::*;

let results: Vec<_> = primitives.par_iter().enumerate().map(|(i, p)| {
    // i 是图元索引,作为 halton 起点
    let mut sampler = HaltonSampler::new((i as u32) * 16 + 1);
    compute_lighting(p, &mut sampler)
}).collect();
```

每个图元独立 sampler,起点由索引决定。**确定性 + 多线程安全**。

### 处理共享数据

光照计算需要访问:

- 场景几何(BVH)— 只读,rayon 共享
- 光源列表 — 只读
- 输出 buffer — 写入,但每线程写不同位置

```rust
let mut lighting = vec![Vec3::ZERO; primitives.len()];
lighting.par_iter_mut().enumerate().for_each(|(i, slot)| {
    *slot = compute(&primitives[i]);
});
```

`par_iter_mut` 给每个线程独立的 `&mut` 引用(指向不同位置),无竞争。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 rayon 在小任务上反而比单线程慢?具体说,什么任务大小是 rayon 的"甜区"?

**参考解答**:rayon 有开销:

1. **任务分发**:把工作切 chunks,放进队列
2. **线程同步**:任务结束要汇总结果
3. **缓存失效**:数据可能在不同核心的缓存间迁移

如果任务本身比这些开销小,并行反而慢。比如 `map(|x| x + 1)`,1ms 任务,rayon 开销 0.5ms,8 核并行总时间 0.6ms,比单线程 1ms 快不多——但加上 task spawn 开销可能 2ms,反而慢。

甜区:**任务 > 10 微秒**。光照计算(每图元几十微秒)合适,简单加法(几纳秒)不合适。

rayon 的 `with_min_len` 可以设置最小 chunk 大小,避免任务太细。

### Lv2 · 动手实践

**题**:用 rayon 并行化光照,验证 4-8 倍加速。完成标准:
- 单线程基线:50ms(1000 图元)
- rayon 并行:~10ms
- CPU 利用率从 12% 升到 80%+
- 视觉结果与单线程完全一致(确定性)

**参考解答**:

```rust
use glam::Vec3;
use rayon::prelude::*;
use std::time::Instant;

pub struct Primitive {
    pub center: Vec3,
    pub normal: Vec3,
}

pub struct Light {
    pub position: Vec3,
    pub color: Vec3,
    pub luminous_flux: f32,
}

pub fn compute_single(prims: &[Primitive], lights: &[Light]) -> Vec<Vec3> {
    prims.iter().map(|p| {
        let mut accum = Vec3::ZERO;
        for light in lights {
            let dir = light.position - p.center;
            let dist2 = dir.length_squared();
            if dist2 < 1e-6 { continue; }
            let n_dot_l = p.normal.dot(dir / dist2.sqrt()).max(0.0);
            if n_dot_l == 0.0 { continue; }
            let att = 1.0 / (dist2 + 0.01);
            accum += light.color * light.luminous_flux * n_dot_l * att;
        }
        accum
    }).collect()
}

pub fn compute_parallel(prims: &[Primitive], lights: &[Light]) -> Vec<Vec3> {
    prims.par_iter().map(|p| {
        let mut accum = Vec3::ZERO;
        for light in lights {
            let dir = light.position - p.center;
            let dist2 = dir.length_squared();
            if dist2 < 1e-6 { continue; }
            let n_dot_l = p.normal.dot(dir / dist2.sqrt()).max(0.0);
            if n_dot_l == 0.0 { continue; }
            let att = 1.0 / (dist2 + 0.01);
            accum += light.color * light.luminous_flux * n_dot_l * att;
        }
        accum
    }).collect()
}

fn main() {
    let n_prims = 10000;
    let prims: Vec<Primitive> = (0..n_prims).map(|i| Primitive {
        center: Vec3::new(i as f32 * 0.5, 0.0, 0.0),
        normal: Vec3::Y,
    }).collect();
    let lights: Vec<Light> = (0..10).map(|i| Light {
        position: Vec3::new(i as f32 * 50.0, 5.0, 0.0),
        color: Vec3::ONE,
        luminous_flux: 1000.0,
    }).collect();

    // 单线程基线
    let start = Instant::now();
    let result_single = compute_single(&prims, &lights);
    let single_time = start.elapsed();
    println!("Single thread: {:?} for {} prims", single_time, n_prims);

    // 多线程
    let start = Instant::now();
    let result_parallel = compute_parallel(&prims, &lights);
    let parallel_time = start.elapsed();
    println!("Parallel ({} threads): {:?}",
        rayon::current_num_threads(), parallel_time);

    // 验证结果一致
    let max_diff = result_single.iter().zip(result_parallel.iter())
        .map(|(a, b)| (a - b).length())
        .fold(0.0_f32, f32::max);
    println!("Max difference: {}", max_diff);

    let speedup = single_time.as_secs_f64() / parallel_time.as_secs_f64();
    println!("Speedup: {:.2}x", speedup);
}
```

```rust
use glam::Vec3;
use rayon::prelude::*;
use std::time::Instant;

#[derive(Clone)]
pub struct Primitive {
    pub center: Vec3,
    pub normal: Vec3,
    pub id: u32,
}

#[derive(Clone)]
pub struct Light {
    pub position: Vec3,
    pub color: Vec3,
    pub luminous_flux: f32,
}

pub fn halton(mut index: u32, base: u32) -> f32 {
    let mut f = 1.0_f32;
    let mut r = 0.0_f32;
    while index > 0 {
        f /= base as f32;
        r += f * (index % base) as f32;
        index /= base;
    }
    r
}

pub struct HaltonSampler {
    base_index: u32,
}

impl HaltonSampler {
    pub fn new(start: u32) -> Self { Self { base_index: start.max(1) } }
    pub fn next_2d(&mut self) -> (f32, f32) {
        let u = halton(self.base_index, 2);
        let v = halton(self.base_index, 3);
        self.base_index += 1;
        (u, v)
    }
}

/// 单线程基线
pub fn compute_single(prims: &[Primitive], lights: &[Light]) -> Vec<Vec3> {
    prims.iter().enumerate().map(|(i, p)| {
        let mut sampler = HaltonSampler::new((i as u32) * 16 + 1);
        compute_one(p, lights, &mut sampler, 4)
    }).collect()
}

/// rayon 并行
pub fn compute_parallel(prims: &[Primitive], lights: &[Light]) -> Vec<Vec3> {
    prims.par_iter().enumerate().map(|(i, p)| {
        let mut sampler = HaltonSampler::new((i as u32) * 16 + 1);
        compute_one(p, lights, &mut sampler, 4)
    }).collect()
}

fn compute_one(p: &Primitive, lights: &[Light], sampler: &mut HaltonSampler, samples: u32) -> Vec3 {
    let mut accum = Vec3::ZERO;
    for light in lights {
        // 在光源周围采样 samples 次
        for _ in 0..samples {
            let (u, v) = sampler.next_2d();
            let offset = Vec3::new((u - 0.5) * 0.5, (v - 0.5) * 0.5, 0.0);
            let light_pos = light.position + offset;
            let dir = light_pos - p.center;
            let dist2 = dir.length_squared();
            if dist2 < 1e-6 { continue; }
            let n_dot_l = p.normal.dot(dir / dist2.sqrt()).max(0.0);
            if n_dot_l == 0.0 { continue; }
            let att = 1.0 / (dist2 + 0.01);
            accum += light.color * light.luminous_flux * n_dot_l * att;
        }
    }
    accum / samples as f32
}

fn main() {
    println!("Rayon threads: {}", rayon::current_num_threads());

    let n_prims = 10000;
    let prims: Vec<Primitive> = (0..n_prims).map(|i| Primitive {
        center: Vec3::new(i as f32 * 0.5, 0.0, 0.0),
        normal: Vec3::Y,
        id: i as u32,
    }).collect();
    let lights: Vec<Light> = (0..10).map(|i| Light {
        position: Vec3::new(i as f32 * 50.0, 5.0, 0.0),
        color: Vec3::ONE,
        luminous_flux: 1000.0,
    }).collect();

    // warmup
    let _ = compute_parallel(&prims, &lights);

    let start = Instant::now();
    let result_single = compute_single(&prims, &lights);
    let single_time = start.elapsed();
    println!("Single thread: {:?} for {} prims x {} lights",
        single_time, n_prims, lights.len());

    let start = Instant::now();
    let result_parallel = compute_parallel(&prims, &lights);
    let parallel_time = start.elapsed();
    println!("Parallel: {:?} for {} prims x {} lights",
        parallel_time, n_prims, lights.len());

    let max_diff = result_single.iter().zip(result_parallel.iter())
        .map(|(a, b)| (a - b).length())
        .fold(0.0_f32, f32::max);
    println!("Max diff: {} (should be 0, deterministic)", max_diff);

    let speedup = single_time.as_secs_f64() / parallel_time.as_secs_f64();
    println!("Speedup: {:.2}x", speedup);

    // 用 perf 看 CPU 利用率
    println!("\nUse perf to verify CPU utilization:");
    println!("  perf stat -e task-clock ./target/release/handmade_hero");
    println!("  task-clock / wall-clock should be close to num_threads");
}
```

**Troubleshooting**:

- **结果不一致** — sampler 起点必须确定(用 `i as u32 * samples`),不能依赖 RNG
- **没有加速** — 任务太小,加 `with_min_len(100)`
- **Send/Sync 编译错误** — 检查闭包捕获,所有引用必须是 `&` 或 `&mut` 唯一引用
- **panic 半路** — rayon 遇到 panic 全局停止,加 `std::panic::catch_unwind`
- **线程数不对** — `rayon::current_num_threads()`,默认是 CPU 核心数,可以 `RAYON_NUM_THREADS=N` 调


### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
