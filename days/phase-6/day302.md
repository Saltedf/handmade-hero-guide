# Day 302 · 确认没有全序

> 经过 day 298-301 的多次尝试,Casey 今天**承认**一个数学事实:HH 的 entity 排序**没有全序**。任何尝试用单一线性顺序的方案都有 bug。今天做的是**验证这个事实**,为 day 304 的拓扑排序铺垫。

## 0 · 为什么要有这一天

数学上,**全序(total order)**要求满足四个条件:反自反性、反对称性、传递性、完全性。前三个好理解,关键是**完全性**——任意两个元素 a, b,必有 a ≤ b 或 b ≤ a(可以比较)。

2D 游戏的 entity 排序**违反完全性**。考虑:

- 玩家 sprite(中心 100, size 32x48)
- 树 sprite(中心 110, size 48x80)

它们的 bounds 在 x 方向部分重叠(玩家 84-116,树 86-134)。在 y 方向:

- 玩家 bounds:76-124
- 树 bounds:40-120

玩家头顶(76)在树顶之上(40-76 是树,76-120 是玩家+树重叠,120-124 是玩家独有)。**玩家上半身在树后**(被树挡),**玩家下半身在树前**(挡树)。

这种情况下:

- "玩家在树前"——错(玩家上半被树挡)
- "树在玩家前"——错(玩家下半挡树)
- "玩家和树同层"——错(它们明显有遮挡)

**它们无法用单一顺序排**。这就是没有全序。

承认这点后,Casey 面临选择:

1. **接受简化**——强行加 tie-breaker(spawn_id),接受"半遮挡"渲染错(工业游戏大多这样)
2. **拓扑排序**——承认部分序,把每个 sprite 切成多个"遮挡关系"边,拓扑排序
3. **Depth peeling**——多 pass 渲染,每 pass 解决一层(昂贵)

Casey 今天先确认问题,day 304 用拓扑排序解决。

心理锚点:看完今天,你应该理解**为什么 2D sprite 排序本质是部分序**,以及为什么工业游戏大多接受"近似"。

## 2 · 心智模型

### 类比:石头剪刀布

石头剪刀布是经典的**循环**——石头赢剪刀,剪刀赢布,布赢石头。如果你要"排序"它们,无法——它们形成环。

```
rock > scissors > paper > rock > ...
```

这种循环关系叫**不可传递**(non-transitive)。游戏 sort 的"违反传递性"类似——A 在 B 前,B 在 C 前,C 在 A 前,无法线性排。

具体构造反例:

- A:大 sprite,中心 (100, 100),size 100x100,bounds (50-150, 50-150)
- B:小 sprite,中心 (50, 100),size 50x50,bounds (25-75, 75-125)
- C:小 sprite,中心 (150, 100),size 50x50,bounds (125-175, 75-125)

A 的 bounds 完全覆盖 B 和 C 的 y 范围,部分覆盖 x 范围。B 和 C 不重叠。

按 bottom_y 排:

- A bottom = 150
- B bottom = 125
- C bottom = 125

排序:B/C(125) → A(150)。A 在 B 和 C 前(后画)。

但实际视觉:

- A 应该遮挡 B(B 的部分在 A 内)
- A 应该遮挡 C(C 的部分在 A 内)
- B 和 C 不重叠,谁先无所谓

排序是对的!那为什么 Casey 说"没有全序"?

更复杂的反例:**两个 sprite 完全重叠且 bottom_y 相同**。这时无论怎么排都"半遮挡"。但这是边缘情况,实际游戏很少出现。

Casey 真正担心的是**复杂场景**——多个 sprite 相互部分重叠,每个重叠关系是"图的一条边",如果有环就无法线性排。

### 2.2 传递性违反

考虑三个 sprite:

- A 高,bounds (0-100, 0-200)
- B 中,bounds (50-150, 100-200)
- C 矮,bounds (100-200, 0-100)

A 和 B 重叠(50-100, 100-200)。
B 和 C 重叠(100-150, 100)。
A 和 C 重叠(100, 0-100)。

bottom_y:A=200, B=200, C=100。

按 bottom_y:A/B 同,C 最先。

视觉关系:

- A 应该遮挡 C(A 在 C 后,但 bottom_y 都大,A 后画遮挡 C)
- A 应该遮挡 B
- B 应该遮挡 C

OK 这看起来还是线性的(A 最前,B 中,C 最远)。再构造有环的:

- A 左上(0-100, 0-100)
- B 右上(50-150, 0-100)
- C 中下(50-100, 50-150)

A 和 B 重叠(50-100, 0-100)。
A 和 C 重叠(50-100, 50-100)。
B 和 C 重叠(50-100, 50-100)。

bottom_y 都相同(100)。

按 spawn_id 排——但这没视觉意义。实际:

- A 和 B 谁前?(同 bottom,看 x)
- C 和 A/B 谁前?(同 bottom)

任何顺序都有"半遮挡"。这就是部分序的本质——无法表达为单一序列。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业关于"没有全序"的认识:

- **大多数游戏接受简化**——Y-sort + spawn_id 够用
- **高端 3D 游戏**用 GPU depth buffer(全序)
- **2.5D 游戏**用 depth buffer + Y-sort
- **少数研究项目**用 topological sort(论文级)

Casey 在 HH 教学用拓扑排序——因为它**思想深**,而不一定工业实用。学完后你能理解为什么 GPU depth buffer 是终极方案。

实际游戏开发的"sort bug":

- 角色"穿"过桌子的腿(应该被桌腿挡)
- 武器"穿过"墙壁(应该被墙挡)
- 影子"穿过"楼梯(应该被楼梯挡)

这些 bug 大多因为简化 sort 没处理复杂重叠。商业游戏美术会"作弊"——把桌子腿做成多个独立 sprite,每个独立 sort,减少重叠复杂度。

### 3.2 · 🎨 图形学视角

图形学对"部分序"的终极方案是 **Z-buffer**(深度缓冲):

```
for each pixel:
    for each fragment drawn to it:
        keep the one with smallest z
```

Z-buffer 是像素级的全序——每个像素独立决定谁前。这是 1972 年的发明,改变了 3D 渲染。

但 Z-buffer 不处理透明物体——透明物体必须 sort + blend。这是 OIT 研究的动机。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里"部分序"对应**初始化依赖**:

- 模块 A 依赖 B(B 必须先 init)
- B 依赖 C
- C 不依赖任何

init 顺序:C → B → A(拓扑排序)。

如果出现循环依赖(A 依赖 B,B 依赖 A),内核报错——拒绝启动。

```bash
# 看启动日志
dmesg | grep -i "circular"
# 可能输出:circular dependency detected
```

游戏 sort 的"环"类似——A 在 B 前,B 在 C 前,C 在 A 前。拓扑排序检测到环会失败。

### 3.4 · 🦀 Rust 生态视角

Rust 的 `Topo` 或 `petgraph` crate 处理拓扑排序:

```rust
use petgraph::algo::toposort;
use petgraph::Graph;

let mut g = Graph::new();
let a = g.add_node("A");
let b = g.add_node("B");
let c = g.add_node("C");
g.add_edge(a, b, ());  // A 在 B 前
g.add_edge(b, c, ());  // B 在 C 前

match toposort(&g, None) {
    Ok(order) => println!("Topo order: {:?}", order),
    Err(cycle) => println!("Cycle detected: {:?}", cycle),
}
```

`petgraph` 是工业级图库。Casey 在 HH 自己实现拓扑排序(教学),但生产代码用 petgraph。

**题**:构造一个 3 个 sprite 的配置,使得它们形成"环"——A 在 B 前,B 在 C 前,C 在 A 前。用具体坐标和 bounds。

**参考解答**:

- B:位置 (75, 75),bounds 32x32(实际 59-91, 59-91)
- C:位置 (50, 75),bounds 32x32(实际 34-66, 59-91)

A 和 C 重叠(34-66, 59-66)。

bottom_y 都相同(66)。但视觉关系:

- A 应该在 B 后(A 中心 y=50 < B 中心 y=75,A"更远")

### Lv2 · 动手实践

**题**:实现一个验证函数 `is_total_order(entities) -> bool`,检查给定的 sort_rule 是否真的对所有对都传递。如果不是,返回 false 并打印反例。

完成标准:构造 day 300 的 sort_rule,验证在某些 sprite 配置下返回 false。

**参考解答**:

```rust
use std::cmp::Ordering;

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug)]
struct Aabb { x: f32, y: f32, w: f32, h: f32 }

impl Aabb {
    fn from_center(p: Vec2, w: f32, h: f32) -> Self {
        Self { x: p.x - w/2.0, y: p.y - h/2.0, w, h }
    }
    fn bottom(&self) -> f32 { self.y + self.h }
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec2,
    bounds: Aabb,
    name: &'static str,
}

fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.bounds.bottom().partial_cmp(&b.bounds.bottom()).unwrap_or(Ordering::Equal)
}

// 检查传递性:对任意 a < b 且 b < c,必有 a < c
fn check_transitivity(entities: &[Entity]) -> Option<String> {
    for i in 0..entities.len() {
        for j in 0..entities.len() {
            for k in 0..entities.len() {
                let ab = sort_rule(&entities[i], &entities[j]);
                let bc = sort_rule(&entities[j], &entities[k]);
                let ac = sort_rule(&entities[i], &entities[k]);
                if ab == Ordering::Less && bc == Ordering::Less && ac != Ordering::Less {
                    return Some(format!(
                        "Transitivity violated: {} < {} < {} but {} not < {}",
                        entities[i].name, entities[j].name, entities[k].name,
                        entities[i].name, entities[k].name
                    ));
                }
            }
        }
    }
    None
}

fn main() {
    let entities = vec![
        Entity {
            pos: Vec2::new(100.0, 100.0),
            bounds: Aabb::from_center(Vec2::new(100.0, 100.0), 32.0, 48.0),
            name: "A",
        },
        Entity {
            pos: Vec2::new(100.0, 80.0),
            bounds: Aabb::from_center(Vec2::new(100.0, 80.0), 48.0, 80.0),
            name: "B",
        },
    ];

    match check_transitivity(&entities) {
        Some(err) => println!("NOT total order: {}", err),
        None => println!("Possibly total order (transitivity OK)"),
    }
}
```

**每行解释**:
- `check_transitivity` 遍历所有三元组,验证传递性
- 传递性违反 = 不是全序
- 单一 bottom_y 实际满足传递性(f32 比较),所以这个例子的输出是"OK"
- 真正的"没有全序"是 bounds 重叠时,需要更复杂的 sort_rule 才会暴露

```rust
// 构建遮挡关系图
struct OcclusionGraph {
    edges: Vec<(usize, usize)>,  // (occluded, occluder) — occluder 后画
}

fn build_occlusion_graph(entities: &[Entity]) -> OcclusionGraph {
    let mut edges = vec![];
    for i in 0..entities.len() {
        for j in 0..entities.len() {
            if i == j { continue; }
            let a = &entities[i];
            let b = &entities[j];
            // a 被 b 遮挡 当且仅当:
            // 1. bounds 重叠
            // 2. b.bottom_y > a.bottom_y
            if bounds_overlap(&a.bounds, &b.bounds) && b.bounds.bottom() > a.bounds.bottom() {
                edges.push((i, j));
            }
        }
    }
    OcclusionGraph { edges }
}

fn main() {
    // ... entities
    let g = build_occlusion_graph(&entities);
    println!("Occlusion edges: {:?}", g.edges);
    // 输出哪些 sprite 遮挡哪些
}
```

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

1990 年代 id Software 的 Doom(1993)用 BSP tree + painter's algorithm——排序在编译期完成,运行时 O(N) 遍历。Quake(1996)首次用 Z-buffer(GPU 硬件),彻底解决排序问题。

2D 游戏排序的演化:

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
