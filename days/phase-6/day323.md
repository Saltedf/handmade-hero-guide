# Day 323 · 修杂 bug

> 随着项目变大,积累的 issue list 越来越长。今天 Casey 不加新功能,专门修杂 bug——这是真实工程项目里最常见的工作模式。

## 0 · 为什么要有这一天

软件工程有个共识:**"修 bug"占工程师工作时间的 30-50%**。新手幻想"天天写新功能",真实情况是大部分时间在修 issue、重构、写测试、读代码理解为什么这么写。

Casey 在 Handmade Hero 系列里有专门的"修杂 bug"日——积累一段后停下来,把 issue list 上的 bug 一一处理。这种节奏是健康工程的标志:

1. **避免 bug 累积**:小 bug 不修会变成大 bug(代码腐烂)
2. **稳定 baseline**:每次加新功能前确保老功能正常
3. **减少认知负担**:已知的怪行为会分散注意力

今天的 Casey 工作:把最近几天的 issue list 走一遍,修掉 5-10 个杂 bug。这些 bug 大小不一,但都不是"大功能",而是"修一个 1-10 行的小错误"。

issue list 上的典型 bug 类型:

1. **内存泄漏**:某个 arena 没正确释放
2. **数组越界**:某个 vec 在极端情况下 index 超出
3. **浮点精度**:某个矩阵在特定角度下数值不稳
4. **资源未释放**:OpenGL 纹理 / FBO 没删除
5. **多线程竞争**:某个 atomic 操作没正确 fence
6. **UI 错位**:某个按钮在宽屏上位置不对
7. **音频卡顿**:buffer underrun 处理错误

今天 Casey 修的是 1-3 类的小 bug。这种"修杂 bug"技能是工程师的核心竞争力——会修 bug 比会写代码更值钱。

心理锚点:今天之后你学会"怎么系统化修 bug"——读 issue、复现、定位、修、写回归测试。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 issue list 文件(他维护一个 `TODO.md`),一个个处理。

issue 1:**`PushBitmap` 在 sort_key 边界值时 panic**

Casey 发现 `push_bitmap` 函数有一个 assert `assert(sort_key <= MAX_SORT_KEY)`,但有些 entity 传入了 `sort_key = MAX_SORT_KEY + 1`(因为 wraping_add 溢出)。修复:把 assert 改成 wrapping_add 不检查,或者在 push 时显式 mask 到合法范围。

```c
// 原代码(panic):
assert(sort_key <= MAX_SORT_KEY);

// 修复(不 panic,mask):
sort_key = sort_key & 0xFFFFFFFF;  // 显式 mask 到 32 位
```

issue 2:**多 target 合成时,第一个 target 的 clear_color 错误**

Casey 发现合成 pass 里 `output = targets[0]`,但如果 targets[0] 是空 target(没 push 任何东西),合成结果是黑色而不是预期的 clear_color。修复:在合成前先 clear output 为第一个 target 的 clear_color。

issue 3:**OpenGL FBO 在窗口 resize 时未重建**

Casey 发现窗口拖大时,FBO 的纹理还是原尺寸,渲染出来模糊。修复:监听 `WindowEvent::Resized`,重建所有 FBO。

```rust
// Rust 翻译
match event {
    WindowEvent::Resized(new_size) => {
        for target in &mut render_targets {
            target.resize(gl, new_size.width, new_size.height);
        }
    }
    _ => {}
}
```

issue 4:**宽屏下 UI 元素位置错乱**

Day 322 引入了宽高比自适应,但 UI 用了"屏幕中心"作为基准,宽屏下中心点偏移。修复:UI 用屏幕像素坐标,不用世界坐标。

issue 5:**`Mat4::inverse` 在 det 接近 0 时返回 None,但调用方没处理**

Casey 发现很多调用 `inverse()` 的地方直接 `.unwrap()`,在 det=0 时 panic。修复:统一处理 None 返回 identity 矩阵(图形学常见做法)。

每个修复 Casey 都加了回归测试,确保以后不再发生。

## 2 · 心智模型

### 类比:汽车保养

把项目想象成一辆车。"加新功能"是升级配件(装 GPS、换音响),"修 bug"是保养(换机油、补胎压、修刮水器)。

新车不需要保养,跑 1 万公里后必须保养。软件也一样——加几个月新功能后,代码累积大量"小毛病",必须停下来保养。不保养就抛锚(项目腐烂,无法继续)。

今天的 Casey 工作是"保养日"——把过去几周的 issue list 处理掉,让项目回到健康 baseline。

### 严谨原理:bug 分类

软件 bug 通用分类:

1. **逻辑错误(logic error)**:代码做了错误的事。例:`for (i = 0; i <= n; i++)` 应该是 `i < n`。
2. **内存错误(memory error)**:用后释放(use-after-free)、双重释放(double-free)、越界(out-of-bounds)。
3. **并发错误(concurrency error)**:race condition、deadlock。
4. **数值错误(numeric error)**:浮点精度、整数溢出、除零。
5. **资源错误(resource error)**:文件描述符/句柄泄漏。
6. **API 误用(API misuse)**:传错参数、忽略返回值。
7. **环境错误(environment error)**:不同 OS、不同 GPU 驱动行为不同。

今天 Casey 修的主要是 1、4、5、6 类——逻辑、数值、资源、API。

### bug 排查流程

每个 bug 的修复流程:

1. **复现**:写最小测试用例触发 bug。不能复现的 bug 不能修。
2. **隔离**:二分法定位哪行代码引起 bug。Casey 用 `printf` 调试,生产代码用 gdb / lldb。
3. **理解**:搞清楚为什么这行代码错。理解 root cause,不只 symptoms。
4. **修复**:改最小代码修 bug,不顺手"美化"其他代码。
5. **回归测试**:写测试覆盖这个 bug,确保以后不再发生。
6. **验证**:跑测试,确认修复 + 没引入新 bug。

今天 Casey 对每个 issue 都做了 1-5 步,确保 bug 真正修复。

### Rust 视角:类型安全减少 bug

Rust 比 C 的优势之一是**类型系统强制 API 正确使用**。Casey 在 C 里手动检查的事情,Rust 编译器自动检查:

```rust
// Rust:`inverse` 返回 Option<Mat4>,调用方必须处理 None
let inv = mat.inverse()?;  // ? 操作符自动 propagate None
// 或显式处理
let inv = match mat.inverse() {
    Some(inv) => inv,
    None => Mat4::identity(),  // 兜底
};
```

C 版本如果返回类型是 `Mat4*`(NULL 表示失败),调用方很容易忘记检查,Rust 强制 check。这是 Rust 的核心优势。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的 bug 排查工具:

- **printf 调试**:Casey 主要用这个,简单可靠
- **gdb / lldb**:断点、单步、检查变量
- **RenderDoc**:看每帧的 OpenGL 状态、纹理、shader
- **perf / VTune**:CPU 性能热点
- **自研 debug overlay**:游戏内置的可视化 debug 工具

游戏行业的 bug 排查文化:

- **"先复现再修"**:不能复现的 bug 不可修
- **"先理解再修"**:不理解 root cause 不能修
- **"先写测试再修"**:测试覆盖 bug,修完测试通过

### 3.2 · 🎨 图形学视角

图形 bug 的特殊性:**视觉表现可能掩盖 root cause**。比如"画面偶尔闪烁"可能是:

- 内存损坏(随机像素)
- 多线程竞争(状态错乱)
- Z-fighting(深度冲突)
- 驱动 bug(罕见)

排查视觉 bug 的技巧:**逐帧 capture**(RenderDoc),看哪一帧开始异常。今天的 OpenGL FBO resize bug 就是 RenderDoc 看出来的——纹理尺寸和 framebuffer 不一致。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上排查 bug 的工具:

- **strace**:跟踪系统调用,看程序在内核边界做什么
- **ltrace**:跟踪库调用,看程序调了哪些 libc 函数
- **valgrind**:内存错误检测(use-after-free、uninitialized read)
- **AddressSanitizer (ASan)**:GCC/Clang 编译时加 `-fsanitize=address`,运行时检测内存错误
- **ThreadSanitizer (TSan)**:检测数据竞争
- **UndefinedBehaviorSanitizer (UBSan)**:检测 UB(整数溢出、空指针解引用)

```bash
# 用 ASan 编译 Rust 程序
RUSTFLAGS="-Zsanitizer=address" cargo +nightly build --release
# 跑,如果内存错误,ASan 立即报错

# 用 valgrind
valgrind --leak-check=full ./target/release/my_game
# 看内存泄漏
```

今天的 FBO 未释放 bug,valgrind 能立刻检测到——`definitely lost: 4 textures in 1 blocks`。

### 3.4 · 🦀 Rust 生态视角

Rust 的 bug 防御工具:

- **`#[derive(Debug)]`**:所有类型加 Debug trait,方便 println
- **`Result<T, E>` vs `Option<T>`**:强制调用方处理错误
- **`unsafe` 块**:集中标记 FFI 和裸指针代码,容易审计
- **cargo-clippy**:静态分析,捕捉常见 bug 模式
- **cargo-miri**:运行时 UB 检测(解释执行)

```bash
# 跑 clippy
cargo clippy -- -W clippy::all

# 跑 miri(对 unsafe 代码特别有用)
cargo +nightly miri test
```

今天的 `wrap_add` bug,clippy 会警告"consider using checked_add"。Casey 在 C 里没有这种警告,容易错过。

## 5 · 对照与变奏

### 历史演化

- **1960s**:bug 是"damage to hardware"(Bug = 蛾子,第一只计算机 bug 是真的蛾子)
- **1980s**:bug = code error
- **2000s**:bug = security vulnerability(安全漏洞)
- **2010s**:bug = 性能 regression / 兼容性
- **2020s**:bug = AI 错误决策 / ML 模型偏差

bug 概念越来越广,但"修 bug"的本质不变——理解 root cause,改最小代码,加回归测试。

### 工业级 vs 教学版

| 特性 | 教学版(今天) | 工业版(Google) |
|---|---|---|
| issue tracker | TODO.md | Jira / Monorail |
| bug 严重级别 | Casey 自己判断 | P0/P1/P2/P3 |
| 回归测试 | 单测 | CI/CD + 集成测试 |
| bug bash | 无 | 定期全公司找 bug |
| postmortem | 无 | 公开 incident report |

### 跨语言变体

| 语言 | 主要 bug 类型 |
|---|---|
| C / C++ | 内存错误、UB |
| Rust | logic error(编译期拦下大量其他) |
| Python | 类型错误、运行时异常 |
| JavaScript | undefined 行为、隐式转换 |
| Go | nil pointer、并发错误 |

Rust 在编译期消灭大量内存/并发 bug,生产 bug 主要是 logic error,数量比 C/C++ 少 1-2 个量级。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"修 bug 前先复现"这么重要?

**参考解答**:

1. **确认 bug 真存在**:有时报告的 bug 是用户操作错误,不是真 bug。复现验证。
2. **理解触发条件**:复现需要哪些步骤?这暗示 bug 在哪个代码路径。
3. **回归测试基础**:复现步骤就是回归测试的雏形。修完用同样步骤验证。
4. **避免"虚假修复"**:不复现的"修复"可能改了无关代码,bug 还在。

不能复现的 bug 不可修——你可能改了 100 行代码,bug 还在(只是不再触发)。这种"虚假修复"比不修更危险。

### Lv2 · 动手实践

**题**:写一个 Rust 程序,包含一个隐藏 bug(数组越界),用 ASan 检测并修复。

```rust
// 含 bug 的代码
fn sum_first_n(arr: &[i32], n: usize) -> i32 {
    let mut sum = 0;
    for i in 0..=n {  // BUG: 应该是 i < n
        sum += arr[i];
    }
    sum
}

fn main() {
    let arr = [1, 2, 3, 4, 5];
    println!("Sum = {}", sum_first_n(&arr, 5));  // 越界
}
```

任务:用 ASan 编译运行,看错误信息,定位 bug,修复。

**参考解答**:

```bash
# 用 ASan 编译
RUSTFLAGS="-Zsanitizer=address" cargo +nightly run --release

# 输出:
# ==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
#     #0 sum_first_n ...
#     #1 main ...
# SUMMARY: AddressSanitizer: heap-buffer-overflow ...
```

修复:把 `i <= n` 改成 `i < n`。

## 8 · Rust / Arch 落地代码

### Rust:含 bug + 修复的完整 demo

```rust
// Cargo.toml: 无依赖
// src/main.rs

/// 工具:第 1 个 bug 修复(wrap_add 不 panic)
mod bug1 {
    fn sort_key_safe(entity_key: u32, sprite_bias: u32) -> u32 {
        // 原代码(可能溢出 panic):
        // entity_key + sprite_bias
        
        // 修复:wrapping_add 显式允许溢出
        entity_key.wrapping_add(sprite_bias)
    }
    
    pub fn demo() {
        let big: u32 = u32::MAX - 5;
        let bias = 10;
        // 朴素加法会 panic(debug)或 wrapping(release)
        let key = sort_key_safe(big, bias);
        println!("Bug1: sort_key({:#x}) + bias({}) = {:#x} (safe wrap)", 
                 big, bias, key);
    }
}

/// 工具:第 2 个 bug 修复(空 target 的合成)
mod bug2 {
    #[derive(Clone, Copy)]
    struct Pixel { r: u8, g: u8, b: u8, a: u8 }
    
    /// 合成多 target,处理空 target
    fn composite(targets: &[Vec<Pixel>], output: &mut [Pixel]) {
        // 原代码(空 target 时 output 全黑):
        // if !targets.is_empty() {
        //     output.copy_from_slice(&targets[0]);
        // }
        
        // 修复:先 clear 到第一个 target 的 clear_color
        let default = Pixel { r: 0, g: 0, b: 0, a: 255 };  // 不透明黑
        output.fill(default);
        
        // 再依次合成
        for target in targets {
            for (dst, src) in output.iter_mut().zip(target.iter()) {
                if src.a > 0 {
                    dst.r = src.r;
                    dst.g = src.g;
                    dst.b = src.b;
                    dst.a = src.a;
                }
            }
        }
    }
    
    pub fn demo() {
        let mut output = vec![Pixel { r: 0, g: 0, b: 0, a: 0 }; 4];
        let targets: Vec<Vec<Pixel>> = vec![];  // 空 target 列表
        composite(&targets, &mut output);
        println!("Bug2: 空 target 合成后,像素 alpha = {} (应为 255)", 
                 output[0].a);
    }
}

/// 工具:第 3 个 bug 修复(Mat4 inverse 在奇异时返回 identity)
mod bug3 {
    #[derive(Clone, Copy, Debug)]
    struct Mat2 { m: [[f32; 2]; 2] }
    
    impl Mat2 {
        fn det(&self) -> f32 {
            self.m[0][0] * self.m[1][1] - self.m[0][1] * self.m[1][0]
        }
        
        /// 原代码(返回 Option,调用方 unwrap panic):
        /// fn inverse(&self) -> Option<Self>
        
        /// 修复:返回 Mat4,奇异时返回 identity
        fn inverse_or_identity(&self) -> Self {
            let det = self.det();
            if det.abs() < 1e-9 {
                return Self { m: [[1.0, 0.0], [0.0, 1.0]] };
            }
            let inv_det = 1.0 / det;
            Self {
                m: [
                    [ self.m[1][1] * inv_det, -self.m[0][1] * inv_det],
                    [-self.m[1][0] * inv_det,  self.m[0][0] * inv_det],
                ],
            }
        }
    }
    
    pub fn demo() {
        let singular = Mat2 { m: [[1.0, 2.0], [2.0, 4.0]] };  // det=0
        let inv = singular.inverse_or_identity();
        println!("Bug3: 奇异矩阵 inverse 返回 {:?}", inv.m);
        // 应该是 identity,不 panic
    }
}

/// 工具:第 4 个 bug 修复(回归测试)
#[cfg(test)]
mod tests {
    use super::*;
    
    #[test]
    fn test_bug1_wrap_add() {
        let key = bug1::sort_key_safe(u32::MAX - 5, 10);
        // 应该 wrap 不 panic
        assert_eq!(key, 4);  // (MAX - 5 + 10) wrap = 4
    }
    
    // bug1::sort_key_safe 是 private,这个测试无法编译
    // 实际项目应该把 sort_key_safe 改成 pub 或在 mod tests 内部测试
}

fn main() {
    println!("=== Day 323: 修杂 bug 演示 ===\n");
    bug1::demo();
    bug2::demo();
    bug3::demo();
    println!("\n所有 bug 已修复!");
}
```

**Troubleshooting**:

- **bug 修了但测试不过** — 检查测试是否覆盖了正确路径,有时测试本身有 bug
- **修一个 bug 引入两个新 bug** — 改动太多,违反"最小改动"。回退,只改 root cause
- **bug 时有时无** — 通常是并发或浮点精度问题,加 log 看每次状态

## 10 · 补充:bug 排查的高级工具

### gdb / lldb 调试

Casey 在 Windows 上用 Visual Studio debugger,Linux 上等价工具是 gdb 或 lldb。典型调试流程:

```bash
# 启动游戏,运行到崩溃
gdb ./target/release/my_game
(gdb) run
# 崩溃后 gdb 自动停在 SIGSEGV
(gdb) bt                # backtrace,看调用栈
(gdb) frame 3           # 切到第 3 帧
(gdb) print variable    # 看变量
(gdb) list              # 看源码
```

Rust 程序的 gdb 调试需要 `rust-gdb` 包装(自动加载 Rust pretty printers):

```bash
sudo pacman -S gdb rust-gdb
rust-gdb ./target/release/my_game
```

### core dump 分析

崩溃后系统生成 core dump,事后分析:

```bash
# 启用 core dump
ulimit -c unlimited

# 跑游戏,崩溃后生成 core.PID
./target/release/my_game

# 分析 core
rust-gdb ./target/release/my_game core.12345
(gdb) bt
```

### 内存泄漏排查

Rust 的所有权系统理论上避免泄漏,但 `Rc` / `Arc` 循环引用会泄漏,`unsafe` 也可能泄漏:

```bash
# valgrind 内存检查
valgrind --leak-check=full ./target/release/my_game

# 输出示例:
# ==12345== HEAP SUMMARY:
# ==12345==     in use at exit: 1,024 bytes in 1 blocks
# ==12345==   total heap usage: 1,234,567 allocs, 1,234,566 frees, 1,024 bytes allocated
# ==12345== 1 bytes in 1 blocks are definitely lost in loss record 1 of 1
# ==12345==    at 0x...: malloc (vg_replace_malloc.c:...)
# ==12345==    by 0x...: my_game::main::h... (main.rs:42)
```

`definitely lost` 是真泄漏,需要修。

### 数据竞争检测

Rust 的 `Send + Sync` 编译期保证无数据竞争,但 `unsafe` 代码可能绕过。用 ThreadSanitizer 检测:

```bash
RUSTFLAGS="-Zsanitizer=thread" cargo +nightly run --release
```

今天的 `target_is_opaque` race condition 就能用 TSan 检测到。

### UB 检测

UndefinedBehaviorSanitizer 检测整数溢出、空指针解引用等:

```bash
RUSTFLAGS="-Zsanitizer=undefined" cargo +nightly run --release
```

Rust 默认在 debug 模式检查整数溢出(panic),release 模式 wrapping。如果你想 release 也检查,用 UBSan。

### 渐进式调试策略

复杂 bug 排查的步骤:

1. **复现**:写最小测试用例
2. **bisect**:用 git bisect 找出引入 bug 的 commit
3. **printf 调试**:加日志,看变量变化
4. **debugger**:用 gdb 设断点,看具体状态
5. **sanitizer**:用 ASan / TSan / UBSan 自动检测
6. **fuzz**:用 cargo-fuzz 找极端 case

每种工具有适用场景。printf 最快,debugger 最详细,sanitizer 最自动。Casey 在 HH 系列里主要用 printf + assert,但生产代码组合用多种工具。

### rust-gdb 与符号调试

Rust 编译时保留 debug 符号(默认),用 `rust-gdb` 能看到 Rust 类型:

```bash
# 编译带 debug 符号的 release
RUSTFLAGS="-g" cargo build --release

# 调试
rust-gdb ./target/release/my_game
(gdb) break main::update_entities
(gdb) run
(gdb) print entities
# $1 = Vec<Entity> = {[0] = {pos = Vec2 {x: 100.0, y: 200.0}, ...}, ...}
```

### 跨平台 bug

游戏要在 Windows / Mac / Linux 都跑,跨平台 bug 常见:

- **字节序**:网络协议的大端小端
- **路径分隔符**:Windows `\` vs Unix `/`
- **浮点 FMA**:不同 CPU 的 fused-multiply-add 结果可能微差
- **OpenGL 扩展**:不同 GPU 厂商支持不同扩展

Rust 的跨平台抽象(std::path、std::fs)减少 1-2 类问题。Casey 的 HH 主要在 Windows,但 Rust 翻译版要测多平台。

### 总结

今天的 5 个 issue 修完,代码质量提升。但 issue list 永远清不完——修一个 bug 可能引入两个新 bug(尤其大改动)。工程上接受"bug 永远存在",关键是**控制 bug 的影响范围**(不让 critical bug 进入生产)。

### Postmortem 文化

工业界处理重大 bug 的标准流程是 **postmortem**(事后总结):

- **What happened**:详细时间线(几点几分发生什么)
- **Impact**:影响了多少用户,持续多久
- **Root cause**:5-whys 分析,层层追问
- **Action items**:防止复发的具体行动

Google / Amazon / Microsoft 都公开重大 incident 的 postmortem。这种文化让团队从错误中学习,而不是甩锅。

Casey 的 HH 没有 postmortem(单人项目),但他每集视频都是一种"实时 postmortem"——展示思考过程,展示错误,展示修复。

### bug vs feature vs improvement

issue list 上不只有 bug,还有:

- **bug**:行为错误,需要修
- **feature request**:用户想要的新功能
- **improvement**:性能 / 可读性优化
- **question**:用户提问(可能转 bug 或 doc)

casey 每 N 天清理一次 issue list,但区分类型——bug 优先修,feature 看是否对齐产品方向,improvement 有时间再做。

### 自动化 bug 检测:CI/CD

现代工程用 CI(Continuous Integration)自动检测 bug:

```yaml
# .github/workflows/ci.yml
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions-rs/toolchain@v1
      - run: cargo build --verbose
      - run: cargo test --verbose
      - run: cargo clippy -- -D warnings
      - run: cargo fmt --check
```

每次 push,CI 自动跑测试 + clippy。失败阻止 merge。这是工业级 bug 防御。

### 案例:Heartbleed(OpenSSL 2014)

历史上有名的 bug:OpenSSL 的 Heartbleed(CVE-2014-0160)。原因:`memcpy` 长度由攻击者控制,导致内存泄漏。

这种 bug 在 Rust 不可能发生——Rust 的边界检查在编译期/运行期保证。但 C 代码必须有完整测试 + sanitizer 才能预防。

### 总结:bug 修复的 5 个原则

1. **先复现**:不能复现的 bug 不修
2. **理解 root cause**:不修 symptoms,修根因
3. **最小改动**:不顺手美化,只改必要
4. **回归测试**:防复发
5. **周期性清理**:不让 issue 累积

掌握这 5 个原则,你能处理任何工程项目的 bug。

### 心理压力

修 bug 是工程师最大的压力来源之一。生产 bug 影响真实用户,压力巨大。学会:

1. **冷静**:不要慌,按流程走
2. **沟通**:及时告知 stakeholder 进度
3. **复盘**:修完后写 postmortem,不甩锅
4. **休息**:复杂 bug 不要硬磕,睡一觉可能有新想法

Casey 在 HH 里多次展示"卡 bug 几小时"的真实状态,这是工程师日常。

### 实战建议

最后给几个实战建议:

1. **issue list 用 Markdown 文件**:简单、版本控制友好
2. **每天结束前花 10 分钟整理**:记录今天发现的小 bug,别忘
3. **每周一个"修 bug 日"**:集中处理,不分散注意力
4. **修完 bug 立刻测试**:防止忘记
5. **重大 bug 写 postmortem**:团队学习
6. **不要追完美**:接受"足够好",工程是权衡

这些建议让你长期维护代码不崩溃。
