
# Day 296 · 层的雾与 alpha

> 昨天 Z 层调试时,Casey 发现不同层之间缺乏视觉区分——上层房间和下层房间看起来一模一样。今天他加 **fog(雾)** 和 **alpha(透明度)**,让远处的层略暗、半透明,模拟"深度感"。

## 0 · 为什么要有这一天

游戏画面的"深度感"不靠真 3D——靠**视觉提示**:

- 远处的物体偏蓝灰(大气透视)
- 远处的物体半透明(透过它能看见后面)
- 远处的物体对比度低(雾化)
- 远处的物体略小(透视)

HH 是 2D,但仍可以用这些技巧模拟多层房间的"深度":每个 Z 层有自己的 fog(色调 + alpha),让玩家直觉上知道"哪个层在前,哪个在后"。

为什么今天做这个?因为昨天堆叠房间视图虽然帮 debug,但**正式游戏中**堆叠是看不见的——玩家看到的是单一画面,多层重叠。没有视觉区分,玩家分不清实体在哪层。

今天的代码量也少:加一个 `layer_fog: HashMap<u32, Fog>` 数据结构,渲染时按 layer 应用 fog。Fog 本质是 `color tint + alpha multiplier`。

数学工具:**alpha blending**(透明度混合)。要把半透明 sprite 画到背景上,公式:

```
result = sprite_color * sprite_alpha + bg_color * (1 - sprite_alpha)
```

这是**标准 alpha 混合公式**,所有 GPU 都用。今天 Casey 在 CPU 端实现这个公式,因为没有 GPU。

心理锚点:看完今天,你应该理解 alpha blending 公式,能解释"为什么画半透明物体必须从后向前画"。

## 1 · Casey 今天做了什么

Casey 今天的实现:

1. **加 Fog 数据结构**——`{ tint: Color, alpha: f32 }`
2. **每层配 Fog**——地面层 fog = 无(完全显示),地下层 fog = 半透明黑色,空中层 fog = 半透明白色(模拟云)
3. **alpha blending 实现**——`result = sprite * a + bg * (1-a)`
4. **渲染顺序修正**——半透明物体必须从远到近画

今天的核心数学是 **alpha blending**。Casey 在 C 里手写,我们用 Rust 同样实现。

## 2 · 心智模型

### 类比:玻璃窗和窗帘

把 fog 想象成窗户上的窗帘。窗帘有颜色和透明度:

- 完全透明的窗帘(alpha=0)——窗外景色完全可见
- 完全不透明的窗帘(alpha=1)——只看到窗帘
- 半透明蓝色窗帘(alpha=0.5,蓝色)——窗外景色偏蓝,模糊

数学上,你看到的"窗外景色 + 窗帘颜色"混合:

```
你看到的 = 窗帘颜色 * 窗帘不透明度 + 窗外景色 * (1 - 窗帘不透明度)
```

如果窗帘半透明蓝(alpha=0.5),你看到的是:`蓝色 * 0.5 + 景色 * 0.5 = 景色偏蓝一半`。

fog 应用到游戏层,就是这个原理。地下层 fog 是"半透明黑窗帘",所以地下层看起来偏暗——模拟"地下"的感觉。

### 2.1 alpha blending 公式

```rust
fn alpha_blend(bg: Color, fg: Color, alpha: f32) -> Color {
    Color {
        r: (fg.r as f32 * alpha + bg.r as f32 * (1.0 - alpha)) as u8,
        g: (fg.g as f32 * alpha + bg.g as f32 * (1.0 - alpha)) as u8,
        b: (fg.b as f32 * alpha + bg.b as f32 * (1.0 - alpha)) as u8,
        a: 255,
    }
}
```

公式:`result = fg * alpha + bg * (1 - alpha)`。

- alpha = 1:result = fg(完全不透明,fg 完全覆盖 bg)
- alpha = 0:result = bg(完全透明,fg 不影响)
- alpha = 0.5:result = fg 和 bg 的平均

### 2.2 Color 结构

```rust
#[derive(Copy, Clone, Debug)]
struct Color { r: u8, g: u8, b: u8, a: u8 }

impl Color {
    const BLACK: Color = Color { r: 0, g: 0, b: 0, a: 255 };
    const WHITE: Color = Color { r: 255, g: 255, b: 255, a: 255 };
    const BLUE: Color = Color { r: 100, g: 100, b: 200, a: 255 };
}
```

RGB 各 8 位,共 24 位颜色。Alpha 单独 8 位(透明度)。合起来 32 位(ARGB 或 RGBA,取决于 byte order)。

### 2.3 Fog 数据结构

```rust
#[derive(Copy, Clone)]
struct Fog {
    tint: Color,    // 雾的颜色(通常偏蓝灰)
    alpha: f32,     // 雾的强度 0-1
}

impl Fog {
    const NONE: Fog = Fog { tint: Color::WHITE, alpha: 0.0 };
}

fn apply_fog(original: Color, fog: Fog) -> Color {
    alpha_blend(original, fog.tint, fog.alpha)
}
```

每层有自己的 Fog。地面层 Fog::NONE(完全显示),地下层 Fog { 黑色, 0.5 }(半暗)。

### 2.4 渲染顺序与半透明

半透明物体的渲染有特殊规则:**必须从后向前画**。

为什么?考虑两个半透明物体 A(远) 和 B(近):

**正确顺序(先 A 后 B)**:
```
1. 画 A:bg -> bg * 0.5 + A * 0.5 = mix1
2. 画 B:mix1 -> mix1 * 0.5 + B * 0.5 = final
```
final 是 A、B、bg 三者的加权平均,符合直觉。

**错误顺序(先 B 后 A)**:
```
1. 画 B:bg -> bg * 0.5 + B * 0.5 = mix1
2. 画 A:mix1 -> mix1 * 0.5 + A * 0.5 = final
```
看起来公式一样,实际**算的是 mix1 而非 bg**——但 mix1 已经包含 B 的颜色,A 混合的是"bg+B",不是纯 bg。

数学上,半透明混合**不可交换**:`blend(blend(bg, A), B) ≠ blend(blend(bg, B), A)`。正确顺序是从后向前(先远后近)。

这就是为什么 Z-sort 重要——必须从远到近画,半透明才正确。

---

**总结**:今天的核心是 alpha blending 公式 + fog。每层有自己的 fog 模拟深度感。半透明物体必须从后向前画,所以 Z-sort 仍然重要。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对"雾"和"深度感"有几种实现:

- **Vertex fog**:顶点颜色混合雾色,简单但粗糙
- **Distance fog**:按距离衰减,3D 游戏常见
- **Height fog**:按高度衰减,模拟"低洼雾"
- **Layer fog**(今天):按层级 fog,2D 多层场景

商业游戏用 GPU shader 实现 fog,几行 GLSL:

```glsl
// fragment shader
float fog_factor = 1.0 - exp(-distance * fog_density);
vec3 color = mix(original_color, fog_color, fog_factor);
```

Casey 在 CPU 端做同样事,因为 HH 不用 GPU(暂时)。Phase 8+ 切到 OpenGL 后会迁移到 shader。

**预乘 alpha(pre-multiplied alpha)**:工业级渲染管线常用预乘 alpha——RGB 在存储时已经乘以 alpha。好处:边缘更干净,混合更正确。Casey 在 day 296 不做预乘 alpha,但 Phase 7 处理 PNG 时会用。

### 3.2 · 🎨 图形学视角

alpha blending 在图形学是**核心操作**。GPU 有专门的 blending unit,可配置:

```glsl
// OpenGL blending config
glEnable(GL_BLEND);
glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA);
// = src * src_alpha + dst * (1 - src_alpha)
```

不同 blending 模式:

- **Normal**:`src * a + dst * (1-a)`(今天用的)
- **Additive**:`src * a + dst`(发光效果,如火焰)
- **Multiply**:`src * dst`(暗化,如墨镜)
- **Screen**:`1 - (1-src) * (1-dst)`(反向 multiply,变亮)

游戏用不同 blending 创造效果。Normal 用于普通半透明,Additive 用于发光特效。

**sRGB 陷阱**:颜色空间影响 blending。sRGB 是非线性的,在 sRGB 空间做 blending 是错的(颜色不准)。正确做法:转 linear → blend → 转 sRGB。Casey 在 day 296 不处理(简化教学),Phase 7 详细讲。

### 3.3 · 🐧 Linux 系统编程视角

Linux 的窗口合成器(Weston、Mutter、KWin)用 alpha blending 合成窗口:

```c
// 简化的合成循环
for (y = 0; y < screen_h; y++) {
    for (x = 0; x < screen_w; x++) {
        Color result = bg_color;
        for each window from bottom to top {
            if (window has alpha at (x, y)) {
                result = alpha_blend(result, window_pixel, window_alpha);
            }
        }
        framebuffer[y][x] = result;
    }
}
```

合成器要正确处理窗口的 alpha channel(ARGB),否则透明窗口边缘会有黑边。这是 1990s-2000s 窗口管理器的常见 bug。

Linux DRM/KMS 接口允许 hardware cursor with alpha——光标是 ARGB surface,GPU 自动 blend。

### 3.4 · 🦀 Rust 生态视角

Rust 表达 alpha blending:

```rust
#[derive(Copy, Clone, Debug)]
struct Color { r: u8, g: u8, b: u8, a: u8 }

impl Color {
    fn blend_over(self, bg: Color) -> Color {
        let sa = self.a as f32 / 255.0;
        let ba = bg.a as f32 / 255.0;
        // 颜色通道按 src alpha 混合
        let r = (self.r as f32 * sa + bg.r as f32 * (1.0 - sa)) as u8;
        let g = (self.g as f32 * sa + bg.g as f32 * (1.0 - sa)) as u8;
        let b = (self.b as f32 * sa + bg.b as f32 * (1.0 - sa)) as u8;
        // 结果 alpha 是 1 - (1-sa)(1-ba)
        let a = (1.0 - (1.0 - sa) * (1.0 - ba)) * 255.0;
        Color { r, g, b, a: a as u8 }
    }
}
```

**SIMD 优化**:alpha blending 是典型的 SIMD 友好操作——4 个 u8(rgba)适合一条 SSE 指令。Rust:

```rust
use std::arch::x86_64::*;

#[cfg(target_arch = "x86_64")]
unsafe fn blend_simd(fg: &[Color], bg: &[Color], out: &mut [Color]) {
    // 一次处理 4 个像素
    for chunk in fg.chunks_exact(4).zip(bg.chunks_exact(4)).zip(out.chunks_exact_mut(4)) {
        let ((f, b), o) = chunk;
        // load 4 colors as __m128i
        let fv = _mm_loadu_si128(f.as_ptr() as *const __m128i);
        let bv = _mm_loadu_si128(b.as_ptr() as *const __m128i);
        // ... SIMD blending
        _mm_storeu_si128(o.as_mut_ptr() as *mut __m128i, /* result */);
    }
}
```

工业级渲染器都 SIMD 化 blending。Casey 在 Phase 4+ 的 day 112 也讲过 SIMD 基础。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:半透明物体为什么必须从后向前画?给出反例(从前向后画)的错误结果。

**参考解答**:考虑两个半透明红色和蓝色块,各 alpha=0.5,red 在远,blue 在近。背景白色。

**正确(从后向前:先 red 后 blue)**:
```
画 red:white -> white*0.5 + red*0.5 = (128, 0, 0)
画 blue:(128,0,0) -> (128,0,0)*0.5 + blue*0.5 = (64, 0, 128)
```
结果:暗紫色——红色和蓝色混合,偏暗。

**错误(从前向后:先 blue 后 red)**:
```
画 blue:white -> white*0.5 + blue*0.5 = (0, 0, 128)
画 red:(0,0,128) -> (0,0,128)*0.5 + red*0.5 = (128, 0, 64)
```
结果:暗紫偏红——不一样!

差别原因:**第二画的物体看到的是"背景+第一物体",而非纯背景**。从后向前保证每个物体都和"实际后面"的混合,符合物理直觉。

### Lv2 · 动手实践

**题**:实现 alpha blending,把一个红色 alpha=0.5 的 sprite 画到白色背景上。结果是 (128, 0, 0)。

完成标准:`assert_eq!(blend(WHITE, RED_HALF, 0.5), Color { r: 128, g: 0, b: 0, a: 255 })`。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Color { r: u8, g: u8, b: u8, a: u8 }

const WHITE: Color = Color { r: 255, g: 255, b: 255, a: 255 };
const RED: Color = Color { r: 255, g: 0, b: 0, a: 255 };

fn blend(bg: Color, fg: Color, alpha: f32) -> Color {
    Color {
        r: (fg.r as f32 * alpha + bg.r as f32 * (1.0 - alpha)).round() as u8,
        g: (fg.g as f32 * alpha + bg.g as f32 * (1.0 - alpha)).round() as u8,
        b: (fg.b as f32 * alpha + bg.b as f32 * (1.0 - alpha)).round() as u8,
        a: 255,
    }
}

fn main() {
    let result = blend(WHITE, RED, 0.5);
    println!("Red 0.5 over white: {:?}", result);
    assert_eq!(result, Color { r: 128, g: 128, b: 128, a: 255 });
    // 注:255 * 0.5 + 255 * 0.5 = 255,所以 r/g/b 都应该 128 红 + 128 白 = ?
    // 让我重算:r = 255*0.5 + 255*0.5 = 255 (white bg has r=255, fg red has r=255)
    // 等等,red 的 r 是 255,white 的 r 也是 255
    // 所以 r 不变 = 255
    // 但 g 是:0 * 0.5 + 255 * 0.5 = 127.5 -> 128
    // b 类似
    // 所以结果是 (255, 128, 128)
}
```

让我修正:

```rust
fn main() {
    let result = blend(WHITE, RED, 0.5);
    println!("Red 0.5 over white: {:?}", result);
    // red.r=255, white.r=255: r = 255*0.5 + 255*0.5 = 255
    // red.g=0, white.g=255:   g = 0*0.5 + 255*0.5 = 127.5 -> 128
    // red.b=0, white.b=255:   b = 0*0.5 + 255*0.5 = 127.5 -> 128
    assert_eq!(result, Color { r: 255, g: 128, b: 128, a: 255 });
    println!("Alpha blend test passed!");
}
```

**每行解释**:
- `(fg.r as f32 * alpha + bg.r as f32 * (1.0 - alpha))` —— alpha blending 公式,通道独立
- `.round() as u8` —— f32 转 u8,四舍五入避免向下偏
- 红色 + 白色 0.5 混合 -> 粉色(255, 128, 128),这就是"红色被白色稀释"的视觉

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

```rust
// src/main.rs
// 雾化效果演示:不同层不同 fog

#[derive(Copy, Clone, Debug, PartialEq)]
struct Color { r: u8, g: u8, b: u8, a: u8 }

impl Color {
    const fn new(r: u8, g: u8, b: u8) -> Self { Self { r, g, b, a: 255 } }
    const WHITE: Self = Self::new(255, 255, 255);
    const BLACK: Self = Self::new(0, 0, 0);
    const GREEN: Self = Self::new(50, 200, 80);
    const BLUE_FOG: Self = Self::new(120, 140, 180);
}

#[derive(Copy, Clone)]
struct Fog {
    tint: Color,
    alpha: f32,
}

impl Fog {
    const NONE: Fog = Fog { tint: Color::WHITE, alpha: 0.0 };
    const UNDERGROUND: Fog = Fog { tint: Color::BLACK, alpha: 0.4 };
    const AIR: Fog = Fog { tint: Color::BLUE_FOG, alpha: 0.3 };
}

fn blend(bg: Color, fg: Color, alpha: f32) -> Color {
    Color {
        r: (fg.r as f32 * alpha + bg.r as f32 * (1.0 - alpha)).round() as u8,
        g: (fg.g as f32 * alpha + bg.g as f32 * (1.0 - alpha)).round() as u8,
        b: (fg.b as f32 * alpha + bg.b as f32 * (1.0 - alpha)).round() as u8,
        a: 255,
    }
}

fn apply_fog(original: Color, fog: Fog) -> Color {
    blend(original, fog.tint, fog.alpha)
}

fn main() {
    let monster_color = Color::GREEN;

    println!("Original monster: {:?}", monster_color);

    // 三层 fog 效果
    let fogs = [
        ("Ground (no fog)", Fog::NONE),
        ("Underground", Fog::UNDERGROUND),
        ("Air", Fog::AIR),
    ];

    for (name, fog) in &fogs {
        let with_fog = apply_fog(monster_color, *fog);
        println!("{}: {:?}", name, with_fog);
    }

    // 验证:Ground 层颜色不变,Underground 变暗,Air 偏蓝
    assert_eq!(apply_fog(monster_color, Fog::NONE), monster_color);

    let underground = apply_fog(monster_color, Fog::UNDERGROUND);
    assert!(underground.r < monster_color.r);
    assert!(underground.g < monster_color.g);

    println!("Fog tests passed!");
}
```

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 历史脉络与工业实践

1990 年代 id Software 的 Doom(1993)用 BSP tree + painter's algorithm——排序在编译期完成,运行时 O(N) 遍历。Quake(1996)首次用 Z-buffer(GPU 硬件),彻底解决排序问题。

2D 游戏排序的演化:

- **1985-1990**:无 sort,固定 layer(Super Mario Bros)
- **1990-1995**:Y-sort 在 JRPG 普及(最终幻想 6、超时空之轮)
- **1995-2005**:Multi-layer Y-sort(星际争霸、暗黑破坏神 2)
- **2005-2015**:引擎内置 sort(Unity、GameMaker)
- **2015-2025**:GPU + sort 混合(bevy、Unreal)

Casey 的 HH 在 day 295-310 走了这条 30 年路径——从最简单的 sort_key 到拓扑排序,演示每一阶段的工程权衡。

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
