
# Day 306 · 调试基于图的排序

> Day 304 加了拓扑排序,Day 305 用 arena 加速内存分配。但今天 Casey 测试发现排序**仍然有时错乱**——某些 sprite 顺序不对:玩家被远处的地面 tile 遮挡,怪人在玩家后面却画在玩家前面。今天是典型的"bug 日",Casey 用各种 debug 工具(可视化图、print 中间状态、二分查找、最小复现)追根溯源,最终发现是遮挡判断里 `bottom_y` 算错。今天教的是**调试方法论**——比修这个具体 bug 更重要的,是修任何复杂 bug 的工具箱。

## 0 · 为什么要有这一天

让我先描述一个真实场景。你跟着 Handmade Hero 走到 Day 305。你的拓扑排序代码工作正常——给你的测试场景,它输出"看起来正确"的顺序。你打开游戏,看到大部分时间 sprite 渲染对——玩家在树前,怪人在玩家后。

但突然你走到一个特定位置,玩家被远处的一块地面 tile **完全遮挡**了。你按方向键移动,问题消失——但回到原位又出现。

这是**最难调的 bug 类型**:间歇性、依赖位置、小概率。**90% 时间正常,10% 时间错乱**。

debug 这种 bug 的难点在于:**算法本身正确**(拓扑排序没 bug),但**输入数据错**(图构建时加了错误的边)。具体来说,可能的出错点:

- **遮挡关系的判断逻辑错**:本该 A 遮挡 B,实际加了 B 遮挡 A 的边。这种"边方向反"在图里很难看出来。
- **bounds 计算错**:sprite 实际比 bounds 大或小,导致 overlaps 判断错。
- **图构建时漏了某些对**:本该加边没加,排序以为两个 sprite 独立。
- **拓扑排序的 tie-breaker 不一致**:同样入度 0 的节点,出队顺序不稳定。每帧顺序可能不同。
- **浮点精度**:bottom_y 是浮点,两个 sprite 的 bottom_y 几乎相等时比较结果不稳。

每一类 bug 需要**不同的 debug 工具**。今天 Casey 演示一套**系统化调试流程**,这流程对任何"算法 + 数据"的 bug 都适用。

**学完今天,你应该能**:

- 解释为什么"算法正确但输入错"的 bug 比纯算法 bug 更难调
- 列出 5 类常见 graph bug:错边方向、漏边、bounds 错、tie-breaker、浮点精度
- 把图导出为 Graphviz dot 文件,可视化判断关系对错
- 在 Kahn 算法里加 print 中间状态,逐步看入度变化
- 对大场景(1000+ sprite)做数据二分,定位问题 sprite
- 把最小复现写成单元测试,钉死 bug
- 用 Rust 的 `dbg!` / `tracing` / gdb / cargo-miri 做精细调试
- 知道何时切换工具:可视化优先 → print 简单 → gdb 精细 → miri 查 UB

**今天的方法论价值远超今天的具体 bug**。"如何系统排查 bug"是工程师一辈子的能力——每个项目都会遇到"看起来对但偶尔错"的诡异 bug。

### 为什么"算法对但数据错"最难调

让我深度剖析一下。纯算法 bug 相对好调:

- 崩溃 → gdb 看栈,定位代码
- 总是错 → 单元测试覆盖,失败时复现
- 性能差 → profiler 看热点

但"算法对 + 数据错"的 bug:

- **算法层面所有测试都通过**(拓扑排序正确)
- **某些特定输入**才触发
- **同一代码不同数据**,有时对有时错
- **复现难**——可能依赖浮点累加、内存布局、随机数种子

工业案例:CSS Grid Layout 在 Firefox/Chrome 早期实现有很多"99% 情况对,1% 错乱"的 bug,花了几年才完全解决。原因正是算法对但**特定 DOM 结构**触发边界 case。

今天 Casey 演示的 sprite 排序 bug 也是这种——大部分场景正常,特定 sprite 位置触发。**学会调这种 bug** 让你处理任何"间歇性诡异行为"都从容。

## 2 · 心智模型

### 2.1 类比:侦探破案

把 debug 想象成侦探破案。

- **报告 bug**:有人报警("玩家被遮挡")
- **现场勘查**:看可视化(画图,相当于现场照片)
- **审问证人**:print 中间状态(图、入度、出队——证人证词)
- **找嫌疑犯**:列出可能的出错代码段(嫌疑人列表)
- **审讯**:逐个怀疑点验证(询问不在场证明)
- **定罪**:找到 bug,修(破案)
- **结案**:验证修复 + 加测试防回归(结案 + 记录)

侦探工作不是猜,是**系统地排除可能性**。每个怀疑点验证,直到只剩一个——那就是 root cause。debug 也一样。

工业 debug 的核心原则:**假设驱动调试(Hypothesis-Driven Debugging)**。每个 print / 每个断点都对应一个具体假设("我认为是 X 出错")。验证后要么假设成立(继续修),要么排除(下一个假设)。**不要无目的 print**——那是浪费。

### 2.2 可视化图:Graphviz dot 格式

最强大的 debug 工具之一:**把图画出来**。代码生成 dot 文件,用 Graphviz 渲染 PNG。

```rust
fn graph_to_dot(g: &Graph, entities: &[Entity]) -> String {
    let mut s = String::from("digraph G {\n");
    s.push_str("  rankdir=LR;\n");      // 横向布局
    s.push_str("  node [shape=box];\n"); // 节点用方框

    // 输出节点
    for i in 0..g.n {
        s.push_str(&format!(
            "  {} [label=\"{}\\nbottom_y={:.0}\"];\n",
            i, entities[i].name, entities[i].bounds.bottom()
        ));
    }
    // 输出边
    for i in 0..g.n {
        for &j in &g.adj_out[i] {
            s.push_str(&format!("  {} -> {};\n", i, j));
        }
    }
    s.push_str("}\n");
    s
}
```

输出 dot 文本:

```
digraph G {
  rankdir=LR;
  node [shape=box];
  0 [label="Ground\nbottom_y=50"];
  1 [label="Tree\nbottom_y=120"];
  2 [label="Player\nbottom_y=124"];
  0 -> 1;
  1 -> 2;
}
```

用 Graphviz 渲染:

```bash
cargo run > graph.dot
dot -Tpng graph.dot -o graph.png
feh graph.png  # 或 sxiv / 任何看图工具
```

看到图后立刻发现:

- **哪些边应该有但没有**:两个 sprite 重叠但没有边——bounds.overlaps() 错或漏了对。
- **哪些边不应该有但有**:两个 sprite 不重叠但有边——bounds 错。
- **边的方向反**:玩家应该在树前(玩家→树),但图里是树→玩家——遮挡判断条件反了。
- **环**:如果边形成环,拓扑排序会失败(节点无法全部出队)。环 = "A 在 B 前, B 在 C 前, C 在 A 前"——逻辑矛盾,说明数据错。

Graphviz 是工业图算法 debug 的标准工具。Linux 内核、LLVM、PostgreSQL 都用 dot 格式可视化内部数据结构。

### 2.3 print 中间状态:Kahn 算法每步

第二个强大工具:**print 算法每步状态**。看哪步意外,定位错。

```rust
fn debug_topo_sort(g: &Graph) -> Vec<usize> {
    let n = g.n;
    let mut in_degree: Vec<usize> = (0..n)
        .map(|i| g.adj_in[i].len())
        .collect();

    println!("=== Topological Sort Debug ===");
    println!("\nInitial in-degrees:");
    for i in 0..n {
        println!("  node {}: in={} (name={})",
            i, in_degree[i], entities[i].name);
    }

    let mut queue: Vec<usize> = (0..n)
        .filter(|&i| in_degree[i] == 0)
        .collect();
    println!("\nInitial queue (in_degree == 0): {:?}", queue);

    let mut order = vec![];
    while let Some(node) = queue.pop() {
        println!("\nProcessing node {} ({})", node, entities[node].name);
        order.push(node);

        for &next in &g.adj_out[node] {
            in_degree[next] -= 1;
            println!("  Decreased in-degree of {} ({}) to {}",
                next, entities[next].name, in_degree[next]);
            if in_degree[next] == 0 {
                queue.push(next);
                println!("  Added {} to queue", next);
            }
        }
    }

    println!("\nFinal order: {:?}", order);
    println!("Order names: {:?}",
        order.iter().map(|&i| &entities[i].name).collect::<Vec<_>>());

    if order.len() != n {
        println!("BUG: not all nodes processed!");
        println!("Missing: {:?}",
            (0..n).filter(|i| !order.contains(i)).collect::<Vec<_>>());
        println!("(Likely a cycle in the graph)");
    }
    order
}
```

每次运行打印大量信息。**看哪一步和预期不同**——那里就是 bug 入口。

**Debug print 的纪律**:

- 用清晰分隔符(`===` / `---`)分节
- 每个 print 带上下文(node id + name + 相关值)
- 不要散落各处,集中在被调函数里
- 用 `#[cfg(debug_assertions)]` 包起来,release 不打
- 用 `tracing` crate 替代 println,可动态开关 level

### 2.4 二分查找 bug:大数据集定位

大场景(1000 个 sprite)有 bug 时,逐个看太多。**二分定位**:

```rust
fn bisect_bug(entities: &[Entity]) -> Vec<usize> {
    let mut size = entities.len() / 2;
    while size > 1 {
        let subset = &entities[..size];
        let g = build_occlusion_graph(subset);
        if has_bug(&g, subset) {
            println!("Bug reproduced with {} entities", size);
            // bug 在这一半,继续缩小
            size /= 2;
        } else {
            println!("No bug with {}, trying more", size);
            // bug 需要更多 entity 触发
            size += size / 2;
        }
    }
    (0..size).collect()
}
```

二分思路:把 entity 列表减半,看 bug 还在不在。在 → bug 在这一半,继续减;不在 → bug 需要另一半的某些 entity 触发,加上去再试。

**git bisect 是同一思想在版本维度**——版本 A 正常,版本 Z 有 bug,二分 commit 找出引入 bug 的那个 commit:

```bash
git bisect start
git bisect bad HEAD         # 当前版本有 bug
git bisect good v1.0        # v1.0 时没 bug
# git 自动 checkout 中间版本,你测一下
git bisect good  # 或 bad
# 重复 ~log2(N) 次,定位到具体 commit
git bisect reset
```

数据二分(今天)和版本二分(git bisect)都是 O(log N) 定位 bug,工业 debug 必备。

### 2.5 最小复现:钉死 bug

找到 1-2 个触发 bug 的 sprite 后,做最小复现单元测试:

```rust
#[test]
fn test_minimal_repro_day306_bug() {
    // 玩家和树在特定坐标触发 bug
    let entities = vec![
        Entity::new("Tree",   pos(100.0, 110.0), bounds(50.0, 80.0)),
        Entity::new("Player", pos(100.0, 100.0), bounds(32.0, 48.0)),
    ];
    let g = build_occlusion_graph(&entities);
    let order = topo_sort(&g).unwrap();

    // 期望:Player 先(bottom_y=124), Tree 后(bottom_y=150)
    // 实际 bug:Tree 先,Player 后
    assert_eq!(order, vec![1, 0], "Player should be before Tree");
}
```

这个测试一旦失败,bug 复现。修后测试通过,bug 解决。**回归测试**(regression test)防止以后某次重构又引入同样的 bug。

工业实践:**每个 bug fix 必须配一个回归测试**。Bevy、tokio、ripgrep 等大型项目都强制 PR 带 test。

---

**总结**:今天的核心是**调试方法论**——可视化(Graphviz)、print(中间状态)、二分(数据 / 版本)、最小复现(单元测试)。具体 bug 各不相同,但工具通用。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的 debug 工具箱比其他领域都丰富——因为游戏输出复杂、状态多、实时性强:

- **可视化 overlay**:屏幕上画 sprite bounds、collider、AI 路径、视野范围。Unity 有 Gizmos,Unreal 有 Debug Draw,Bevy 有 bevy_inspector_egui。
- **debug draw**:画线、画框、画文字,即时反馈。每帧重新画,跟着游戏状态变。
- **慢动作 / 暂停**:逐帧 step,看每帧状态。Unity 的 Time.timeScale = 0.1,Unreal 的 Slomo 命令。
- **state inspector**:实时看 Entity 数据。Bevy 的 bevy_inspector_egui 显示整个 ECS world 树。
- **record + replay**:录游戏过程,bug 后回放。Unreal 的 Demo Recording,Unity 的 Record。
- **profiler overlay**:每帧显示 CPU/GPU 时间分布。Casey Day 255 加的 profiler。
- **collision debug**:可视化物理引擎内部——contact point、manifold、broadphase cells。Box2D 的 `b2Draw`。

Casey 在 HH 的 debug overlay 已经有 profiler(Day 255)。今天加 sprite 排序可视化。**每加一个 debug 工具,后续 bug 都受益**。

工业级 debug overlay 设计原则:

1. **每个工具一个 hotkey**(F1 profiler, F2 sort viz, F3 physics, ...)——快速切换
2. **颜色编码**(红=bad, 绿=good, 蓝=info)——视觉一致
3. **可暂停**——按 P 暂停游戏,看当前状态
4. **可截图**——按 PrintScreen 保存当前帧,事后分析
5. **可记录**——按 R 开始录制 30 秒,看 bug 触发瞬间

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核 debug 工具栈是世界上**最完整的 debug 生态**:

- **printk**:内核 print。`dmesg` 看。`printk_ratelimited()` 防刷屏。
- **ftrace**(function trace):函数调用追踪。`/sys/kernel/debug/tracing/`。
- **kprobes**:动态插桩,任意指令地址打断点。
- **eBPF**:可编程追踪。`bpftrace`、`BCC` 工具集。**最强大的现代 debug 工具**。
- **SystemTap**:高级追踪脚本语言。
- **kgdb / kdb**:内核 gdb。
- **crash dump**:内核崩溃后 dump 内存,事后分析。

```bash
# ftrace 看函数调用
echo function > /sys/kernel/debug/tracing/current_tracer
echo 'schedule' > /sys/kernel/debug/tracing/set_ftrace_filter
echo 1 > /sys/kernel/debug/tracing/tracing_on
# 跑代码
cat /sys/kernel/debug/tracing/trace | head -20

# eBPF(更现代)
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
# 实时显示哪些进程调用 openat

# 看内核崩溃日志
journalctl -k --since "10 minutes ago"

# 看进程状态(/proc 文件系统)
cat /proc/$(pidof my_game)/status
cat /proc/$(pidof my_game)/maps  # 内存映射
```

每个工具解决特定 debug 场景:

| 工具 | 何时用 |
|---|---|
| printk | 简单 print,看流程 |
| ftrace | 函数调用图,定位执行路径 |
| eBPF | 复杂分析,聚合统计 |
| kprobes | 特定地址状态 |
| kgdb | 单步调试 |
| crash dump | 崩溃后分析 |

Rust 游戏的 debug 工具**类似但不完全等同**——没有 eBPF 这种万能工具,但有可视化 overlay 这种游戏特有工具。

### 3.3 · 🦀 Rust 生态视角

Rust 的 debug 工具栈:

- **`dbg!` 宏**:快速 print 表达式值。比 `println!` 友好——自动带文件名行号。
  ```rust
  let x = compute();
  dbg!(x);  // 输出 [src/main.rs:10] x = 42
  dbg!(entities.len());  // 输出 [src/main.rs:11] entities.len() = 1000
  ```

- **`#[derive(Debug)]`**:struct 自动实现 Debug trait,可用 `{:?}` 格式化。
  ```rust
  #[derive(Debug)]
  struct Sprite { name: String, x: f32, y: f32 }
  // println!("{:?}", sprite) 自动工作
  ```

- **`tracing` crate**:结构化日志。比 println 强大——支持 level、span、filtering。
  ```rust
  use tracing::{info, debug, instrument};

  #[instrument]
  fn topo_sort(g: &Graph) -> Vec<usize> {
      debug!(nodes = g.n, "Starting sort");
      // ...
  }
  ```

- **gdb / lldb**:断点、单步、变量查看。
  ```bash
  rust-gdb target/debug/game
  (gdb) break build_occlusion_graph
  (gdb) run
  (gdb) next
  (gdb) print entities
  (gdb) info locals
  ```

- **`cargo-miri`**:UB(Undefined Behavior)检测。运行时检查内存安全、未定义行为、data race。
  ```bash
  cargo +nightly miri test
  ```

- **`cargo-tarpaulin`**:覆盖率。看哪些代码没被测试覆盖。
  ```bash
  cargo tarpaulin --out Html
  ```

- **`cargo-flamegraph`**:性能火焰图,看 CPU 时间分布。
  ```bash
  cargo flamegraph --bin game
  ```

工业 Rust 工程师每天用 dbg! + tracing 做基础 debug,gdb 做精细,miri 查 UB,flamegraph 看性能。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **调试方法论(debugging methodology)** — 系统化排查 bug 的通用方法
- **可视化优先(visualize first)** — 画出来比读代码快
- **二分查找(bisection)** — 缩小问题范围,O(log N)
- **最小复现(minimal repro)** — 单元测试钉死 bug
- **假设驱动调试(hypothesis-driven debugging)** — 每个 print 对应一个假设

### Lv1 · 概念辨析(读懂)

**题**:Casey 发现的 bug 是"遮挡关系判断里 `bottom_y` 计算错"。具体怎么错的?用 Day 299 的 bounds 知识解释。

**参考解答**:

bug 原因:遮挡关系判断时用了 `pos.y`(sprite 中心 y)而非 `bounds.bottom_y(pos)`(sprite 底部 y)。

举例说明为什么错:

考虑玩家和树。`pos.y` 是 sprite 中心位置,`bounds.bottom_y = pos.y + bounds.height / 2`(假设 bounds 以 pos 为中心)。

**正确 case**(用 pos.y 凑巧也对):

- 玩家 `pos.y=100`,height=48,`bottom_y=124`
- 树 `pos.y=80`,height=80,`bottom_y=120`

用 `pos.y`:玩家 100 > 树 80,玩家"更前"。✓
用 `bottom_y`:玩家 124 > 树 120,玩家"更前"。✓
**凑巧都对**。

**反例**(pos.y 错,bottom_y 对):

- 玩家 `pos.y=100`,height=48,`bottom_y=124`
- 树 `pos.y=110`,height=80,`bottom_y=150`

用 `pos.y`:玩家 100 < 树 110,**树更前**。✗ 错!
用 `bottom_y`:玩家 124 < 树 150,**树更前**。✓ 对!

为什么 pos.y 错?因为树很高(80 像素),它的底部 150 比玩家底部 124 低,所以**树底部更靠屏幕下方**(玩家视角的"前面")。但树中心 110 比玩家中心 100 高,如果用中心判断就会错。

**结论**:sprite 遮挡要用**底部 y**(谁更靠近屏幕底)判断,而不是中心 y。这是 2D 游戏的标准 z-ordering。

### Lv2 · 动手实践

**题**:实现 `graph_to_dot` 函数,把 Day 304 的图导出为 dot 文件,用 Graphviz 渲染。

完成标准:`cargo run > graph.dot && dot -Tpng graph.dot -o graph.png` 成功,图里能看到节点(含 sprite name + bottom_y)和边。

**完整代码**:

```rust
#[derive(Debug, Clone)]
struct Aabb {
    cx: f32, cy: f32,  // 中心
    w: f32, h: f32,    // 宽高
}

impl Aabb {
    fn bottom(&self) -> f32 {
        self.cy + self.h / 2.0  // 底部 y(屏幕坐标,y 向下)
    }
    fn overlaps(&self, other: &Self) -> bool {
        (self.cx - other.cx).abs() < (self.w + other.w) / 2.0
            && (self.cy - other.cy).abs() < (self.h + other.h) / 2.0
    }
}

#[derive(Debug)]
struct Entity {
    name: String,
    bounds: Aabb,
}

#[derive(Debug)]
struct Graph {
    n: usize,
    adj_out: Vec<Vec<usize>>,
}

fn build_occlusion_graph(entities: &[Entity]) -> Graph {
    let n = entities.len();
    let mut adj_out = vec![vec![]; n];
    for i in 0..n {
        for j in 0..n {
            if i == j { continue; }
            let (a, b) = (&entities[i], &entities[j]);
            if a.bounds.overlaps(&b.bounds) && a.bounds.bottom() < b.bounds.bottom() {
                // a 的底部更低,a 在 b 前面
                adj_out[i].push(j);
            }
        }
    }
    Graph { n, adj_out }
}

fn graph_to_dot(g: &Graph, entities: &[Entity]) -> String {
    let mut s = String::new();
    s.push_str("digraph Occlusion {\n");
    s.push_str("  rankdir=LR;\n");
    s.push_str("  node [shape=box];\n");
    for i in 0..g.n {
        s.push_str(&format!(
            "  {} [label=\"{}\\nbottom={:.0}\"];\n",
            i, entities[i].name, entities[i].bounds.bottom()
        ));
    }
    for i in 0..g.n {
        for &j in &g.adj_out[i] {
            s.push_str(&format!("  {} -> {};\n", i, j));
        }
    }
    s.push_str("}\n");
    s
}

fn main() {
    let entities = vec![
        Entity { name: "Ground".into(), bounds: Aabb { cx: 0.0, cy: 0.0,  w: 1000.0, h: 100.0 } },
        Entity { name: "Tree".into(),   bounds: Aabb { cx: 0.0, cy: 100.0, w: 50.0,   h: 80.0 } },
        Entity { name: "Player".into(), bounds: Aabb { cx: 0.0, cy: 100.0, w: 32.0,   h: 48.0 } },
    ];

    let g = build_occlusion_graph(&entities);
    println!("{}", graph_to_dot(&g, &entities));
}
```

**渲染**:


**每行解释**:

- `rankdir=LR` — 横向布局(从左到右),适合线性顺序图
- `node [shape=box]` — 节点用方框(默认椭圆),信息更清晰
- `label="{}\\nbottom={}"` — 节点标签含 name + bottom_y,看图时直接判断对错
- 边 `i -> j` 表示 i 在 j 前(应先画)

### Lv3 · 迁移设计

**题**:把"可视化 debug"迁移到**网络协议栈**——TCP 状态机的状态转移图。

需求:

- 节点 = TCP 状态(LISTEN、SYN_SENT、ESTABLISHED、...)
- 边 = 状态转移(收到包 / 应用调用时切换)
- 用 Graphviz 渲染,验证协议实现是否对

设计文档:

```rust
enum TcpState { Listen, SynSent, SynReceived, Established, FinWait1, /* ... */ }

struct TcpStateMachine {
    // transitions[state] = Vec<(event, next_state)>
    transitions: Vec<Vec<(TcpEvent, TcpState)>>,
}

fn state_machine_to_dot(sm: &TcpStateMachine) -> String {
    let mut s = String::from("digraph TCP {\n  rankdir=LR;\n");
    for (i, state) in TcpState::all().iter().enumerate() {
        s.push_str(&format!("  {} [label=\"{:?}\"];\n", i, state));
    }
    for (i, transitions) in sm.transitions.iter().enumerate() {
        for (event, next) in transitions {
            let j = TcpState::all().iter().position(|s| *s == *next).unwrap();
            s.push_str(&format!("  {} -> {} [label=\"{:?}\"];\n", i, j, event));
        }
    }
    s.push_str("}\n");
    s
}
```

这个工具帮你验证 TCP 实现——把 RFC 793 的状态机画出来,对比你的代码生成的图,差异就是 bug。

### 8.1 完整 debug demo

把今天的概念做成完整可跑 demo:模拟 sprite 排序 bug + debug 工具链。

```rust
#[derive(Debug, Clone)]
struct Aabb {
    cx: f32, cy: f32, w: f32, h: f32,
}

impl Aabb {
    fn bottom(&self) -> f32 { self.cy + self.h / 2.0 }
    fn overlaps(&self, other: &Self) -> bool {
        (self.cx - other.cx).abs() < (self.w + other.w) / 2.0
            && (self.cy - other.cy).abs() < (self.h + other.h) / 2.0
    }
}

#[derive(Debug)]
struct Entity {
    name: String,
    bounds: Aabb,
}

#[derive(Debug)]
struct Graph {
    n: usize,
    adj_out: Vec<Vec<usize>>,
    adj_in: Vec<Vec<usize>>,
}

fn build_occlusion_graph(entities: &[Entity]) -> Graph {
    let n = entities.len();
    let mut adj_out = vec![vec![]; n];
    let mut adj_in = vec![vec![]; n];
    for i in 0..n {
        for j in 0..n {
            if i == j { continue; }
            let (a, b) = (&entities[i], &entities[j]);
            if a.bounds.overlaps(&b.bounds) && a.bounds.bottom() < b.bounds.bottom() {
                adj_out[i].push(j);
                adj_in[j].push(i);
            }
        }
    }
    Graph { n, adj_out, adj_in }
}

/// Debug 版本,print 每个判断
fn debug_build_graph(entities: &[Entity]) -> Graph {
    let n = entities.len();
    let mut adj_out = vec![vec![]; n];
    let mut adj_in = vec![vec![]; n];
    println!("\n=== Building occlusion graph ===");
    for i in 0..n {
        for j in 0..n {
            if i == j { continue; }
            let (a, b) = (&entities[i], &entities[j]);
            let overlaps = a.bounds.overlaps(&b.bounds);
            let a_first = a.bounds.bottom() < b.bounds.bottom();
            println!(
                "  Check {}(bottom={:.0}) vs {}(bottom={:.0}): overlaps={}, a_first={}",
                a.name, a.bounds.bottom(),
                b.name, b.bounds.bottom(),
                overlaps, a_first
            );
            if overlaps && a_first {
                adj_out[i].push(j);
                adj_in[j].push(i);
                println!("    → ADDED edge {} -> {}", i, j);
            }
        }
    }
    Graph { n, adj_out, adj_in }
}

fn topo_sort(g: &Graph) -> Option<Vec<usize>> {
    let mut in_degree: Vec<usize> = g.adj_in.iter().map(|v| v.len()).collect();
    let mut queue: Vec<usize> = (0..g.n).filter(|&i| in_degree[i] == 0).collect();
    let mut order = vec![];
    while let Some(node) = queue.pop() {
        order.push(node);
        for &next in &g.adj_out[node] {
            in_degree[next] -= 1;
            if in_degree[next] == 0 { queue.push(next); }
        }
    }
    if order.len() == g.n { Some(order) } else { None }
}

fn main() {
    let entities = vec![
        Entity { name: "Ground".into(), bounds: Aabb { cx: 0.0, cy: 0.0,  w: 1000.0, h: 100.0 } },
        Entity { name: "Tree".into(),   bounds: Aabb { cx: 0.0, cy: 100.0, w: 50.0, h: 80.0 } },
        Entity { name: "Player".into(), bounds: Aabb { cx: 0.0, cy: 100.0, w: 32.0, h: 48.0 } },
    ];

    // Debug 模式:print 每步
    let g = debug_build_graph(&entities);
    println!("\nGraph: {} nodes", g.n);
    for i in 0..g.n {
        println!("  Node {} out: {:?}", i, g.adj_out[i]);
    }

    let order = topo_sort(&g);
    match order {
        Some(o) => {
            println!("\nTopo order: {:?}", o);
            println!("Render order: {:?}",
                o.iter().map(|&i| &entities[i].name).collect::<Vec<_>>());
        }
        None => println!("\nBUG: cycle detected!"),
    }
}
```
