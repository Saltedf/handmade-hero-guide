# Day 382 · 深度剥离合成

> 昨天 Casey 写出了深度剥离的两个渲染 pass,但**最后的"把多层颜色叠成一张图"这一步还没做**。今天他把合成(compositing)的 GLSL shader 写完,debug 直到画面正确。合成看似简单(就一个 fullscreen quad),但里面藏着**色彩空间**和**alpha 预乘**两个坑。

## 0 · 为什么要有这一天

Day 381 你写了两个 pass,得到 `color0`(最近一层)+ `color1`(第二层)。可是这两层是**两张纹理**,不是最终画面。要把它们变成屏幕上的一张图,需要 **合成 pass**(composite pass):用 fullscreen quad 覆盖屏幕,fragment shader 同时采样两层纹理,按 α-blend 公式合并。

合成听起来就一行 GLSL:`final = layer0 * layer0.a + layer1 * (1 - layer0.a);`。**为什么花一整集**?

因为有两个真实工程问题:

1. **色彩空间**:如果 layer0 和 layer1 写入纹理时是**线性 RGB**,合成直接对。但 OpenGL 默认 framebuffer 是 **sRGB** 非线性空间,自动转换会"二次 gamma 编码",颜色发暗。Casey 必须搞清楚哪一步在哪个空间。
2. **Alpha 预乘**(premultiplied alpha):GLSL 里 `out_color = vec4(rgb, a)`,RGB 是**非预乘**(straight alpha)。但 PNG 解码后常常是**预乘**(RGB 已经乘了 alpha)。两种格式混合时合成公式不一样,搞错会出现"halo"(光晕)伪影。

这两件事在普通渲染里不太显眼(单层不透明没有合成),但**一旦做多层合成,立刻成问题**。

**今天的产出**:画面真正"透过玻璃能看到玻璃后面的东西",而且**颜色对**。Casey 反复用 RenderDoc 抓帧,看每个 draw call 的纹理数值,确认合成公式没写反。

心理锚点:看完今天,你能(1)在 GLSL 里写出正确的双层合成 shader;(2)解释 linear vs sRGB 在合成中的角色;(3)知道什么时候用预乘 alpha,什么时候用 straight alpha;(4)用 RenderDoc 排查合成 shader 的颜色错乱。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 流程:

1. **看 Day 381 的输出**:画面里**第二层根本看不见**,或者颜色发暗。Casey 一开始以为是 Pass 1 没写,后来发现是合成 shader 没接上。
2. **写合成 shader**:最简单的 `over` 操作——`color0 over color1`:`final = color0.rgb * color0.a + color1.rgb * (1 - color0.a)`。
3. **第一次跑**:颜色发暗,像隔了层雾。Casey 怀疑 sRGB。
4. **检查 framebuffer**:layer0 / layer1 的纹理格式是 RGBA32F(线性),但默认 framebuffer 是 sRGB8,OpenGL 启用了 `GL_FRAMEBUFFER_SRGB` 后写入自动做 gamma 编码。Casey 关掉 SRGB,看效果。
5. **重新检查**:颜色对了,但 alpha=0 的像素(没有任何 fragment 的"空白区")变成了黑色——这是因为合成公式没考虑 dst 透明的情况。

7. **再跑一遍**:这次对。Casey 在 demo 里把球放在球后面,透过前球看见后球,颜色正确。

这集的核心:**合成不是"写公式",而是"搞清楚每一步的色彩空间和 alpha 语义"**。这是工程实战,不是数学课。

## 2 · 心智模型

### 类比:Photoshop 的"图层"

你在 Photoshop 里叠两张照片,看到的就是**合成结果**。Photoshop 的默认混合模式叫 **Normal**,对应公式:

```
output = top_layer * top_opacity + bottom_layer * (1 - top_opacity)
```

这叫 **Over operator**(Porter-Duff 1984),是最常见的合成方式。深度剥离的合成就是 **Over**,只是 `top_opacity` 来自 `layer.a`,`top_layer` 是 `layer0.rgb`。

注意 Over 的**层级**:

- 如果你叠 3 张图:`A over B over C`,先合成 `B over C`,再合成 `A over (B over C)`
- 必须从**最底层**(背景)开始,**最顶层**最后合成
- 深度剥离的多层合成:**最远的层先合成,最近的层最后合成**

### 严谨原理:Over operator

Porter-Duff 定义了一组**合成算子**(compositing operators),Over 是其中一个。形式化定义:

给定两个"图层" `A`(前景,有 alpha `αA`)和 `B`(背景,有 alpha `αB`):

```
A over B:
    color = A.rgb * αA + B.rgb * (1 - αA)
    alpha = αA + αB * (1 - αA)
```

注意 **alpha 输出**:两层都不透明时(`αA=1, αB=1`),输出 alpha = 1。一层透明时(`αA=0`),输出 alpha = αB(等于背景)。

这个公式对**预乘 alpha**(premultiplied alpha)和 **straight alpha**(非预乘)有不同写法:

**Straight alpha**(非预乘,RGB 没乘 alpha):
```
out.rgb = A.rgb * A.a + B.rgb * B.a * (1 - A.a)
out.a   = A.a + B.a * (1 - A.a)
```

注意 straight 版本里背景也要乘自己的 alpha——因为背景的 RGB 不含 alpha 信息,如果背景是透明的话,B.rgb 不该贡献。

**Premultiplied alpha**(RGB 已经乘过 alpha):
```
out.rgb = A.rgb + B.rgb * (1 - A.a)
out.a   = A.a + B.a * (1 - A.a)
```

预乘版本更简洁(前景的 RGB 不再乘 alpha,因为存的时候乘过了)。这是 **PNG 默认格式**(很多 PNG 解码器输出预乘)和**现代渲染管线推荐格式**。

GLSL 里的合成代码:

```glsl
// 假设 layer0/layer1 是预乘 alpha 格式
vec4 composite_premul(vec4 top, vec4 bot) {
    vec4 out;
    out.rgb = top.rgb + bot.rgb * (1.0 - top.a);
    out.a   = top.a + bot.a * (1.0 - top.a);
    return out;
}

// 假设 layer0/layer1 是 straight alpha 格式
vec4 composite_straight(vec4 top, vec4 bot) {
    vec4 out;
    out.rgb = top.rgb * top.a + bot.rgb * bot.a * (1.0 - top.a);
    out.a   = top.a + bot.a * (1.0 - top.a);
    return out;
}
```

**关键洞察**:你**必须知道你的纹理是哪种格式**,否则写错公式导致 halo。Casey 在 Day 382 调试时反复确认这一点。

### 色彩空间:Linear vs sRGB

sRGB 是大多数显示器和 PNG 文件用的色彩空间,它的特点是**对暗部精度更高**(非线性编码)。**但所有光照 / 混合计算必须在 Linear 空间做**,否则:

- 暗部变暗(γ 错误累积)
- 半透明边缘出现"黑边"(因为 sRGB 边缘的 RGB 错误地被直接 lerp)
- 光照过曝

合成流程应该是:

```
1. 从 sRGB 纹理读取 → 转 Linear:  linear = sRGB^2.2(或精确公式)
2. 在 Linear 空间合成(Over operator)
3. 从 Linear 写入 sRGB framebuffer:sRGB = linear^(1/2.2)
```

OpenGL 有两个机制帮你自动做这个转换:

1. **GL_FRAMEBUFFER_SRGB**(全局开关):开启后,fragment shader 输出的颜色会自动做 `Linear → sRGB` 转换再写入 sRGB framebuffer。
2. **GL_SRGB8_ALPHA8 内部格式**:纹理用这个格式时,采样时**自动做 `sRGB → Linear`**。

Casey 在 Day 382 的关键决定:

- layer0 / layer1 纹理用 **RGBA32F**(线性浮点,不做 sRGB 转换)
- 最终 framebuffer 用 **sRGB8**,开 `GL_FRAMEBUFFER_SRGB`

这样:合成 shader 看到的 layer0/1 是线性的,合成结果线性,写入 sRGB framebuffer 时 OpenGL 自动转 sRGB。

### Alpha 预乘 vs Straight

**Straight alpha**(非预乘)的语义:`rgb` 是"如果完全不透明时的颜色",`a` 是"实际不透明度"。

**Premultiplied alpha**(预乘)的语义:`rgb` 已经乘了 `a`,所以 `a=0` 时 `rgb` 也必须是 0(黑色)。

预乘的好处:

1. **合成公式更简单**(少一次乘法)
2. **alpha 边缘更干净**(没有 halo)
3. **支持 additive blending**(加法混合)等扩展模式

预乘的坏处:

1. 文件存储或传输前要乘 alpha(或保留 alpha 让解码器乘)
2. 直觉上不直观(看到 RGB `(0.5, 0, 0)` 不知道是"50% 红"还是"100% 红 alpha 0.5")

**Casey 的选择**:**用预乘 alpha**,因为他后面要做光照(Phong),光照在预乘空间更干净。

### 一段最简化的合成 GLSL

```glsl
#version 330

uniform sampler2D layer0;   // 近一层(预乘)
uniform sampler2D layer1;   // 远一层(预乘)
uniform sampler2D opaque;   // 不透明背景
in vec2 uv;
out vec4 frag_color;

void main() {
    vec4 c0 = texture(layer0, uv);   // 预乘
    vec4 c1 = texture(layer1, uv);   // 预乘
    vec4 bg = texture(opaque, uv);   // 预乘(a=1)

    // 从远到近:先 c1 在 bg 上,再 c0 在 (c1 over bg) 上
    vec4 step1 = vec4(
        c1.rgb + bg.rgb * (1.0 - c1.a),
        c1.a + bg.a * (1.0 - c1.a)
    );
    vec4 final = vec4(
        c0.rgb + step1.rgb * (1.0 - c0.a),
        c0.a + step1.a * (1.0 - c0.a)
    );

    frag_color = final;
}
```

注意三个细节:

1. `texture()` 默认做**双线性插值**(在 4 个相邻像素之间插值)。深度剥离的纹理采样,**理论上线性插值是正确的**(因为颜色和 alpha 都是连续的),但有时会出现"边缘模糊",Casey 在 Day 389+ 会用 `texelFetch` 改为最近邻。
2. `in vec2 uv` 来自 vertex shader。Fullscreen quad 的 uv 是 [0,1] 范围,左下 (0,0) 右上 (1,1)。
3. `out vec4 frag_color` — OpenGL 3.3+ 用 explicit output 声明。

### 三种常见的合成顺序错误

Casey 调试时反复犯的错:

1. **顺序反了**:`final = c1 over c0` 而不是 `c0 over c1`(把远近搞反),结果是远的盖了近的,画面看起来像"玻璃在墙后"。
2. **忘 alpha 通道**:只写 `frag_color.rgb`,alpha 默认 1.0,导致合成结果 alpha 错误(对最终显示不影响,但做后续 post-processing 会出问题)。
3. **空间错乱**:layer0/1 是 linear,合成结果写入 sRGB framebuffer 时**没开** `GL_FRAMEBUFFER_SRGB`,结果颜色发暗(缺一次 gamma 编码)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏里的"合成"出现频率比想象的高:

- **UI 渲染**:HUD、菜单、文字,都是半透明 quad,合成顺序必须从后到前(IMGUI 框架如 `egui` 默认是按提交顺序画,所以提交顺序就是合成顺序)
- **粒子后处理**:爆炸的火焰、烟、火星,渲染到一张临时纹理,再合成到主 framebuffer
- **后期特效**(post-processing):bloom(光晕)、motion blur(动态模糊)、depth of field(景深)都是合成
- **3D 渲染**:每一帧的最后一个 pass 通常是合成 pass,把 G-buffer 和 lighting buffer 合成

**Casey 在 HH 后面 Day 396+** 会反复用合成 pass:把光照结果合成回几何渲染,这需要正确的 Over operator 和色彩空间。

游戏开发常见陷阱:**sRGB 在 editor 里看对了,build 后看错了**。原因是 editor 可能开了 sRGB framebuffer,build 时关了。养成习惯:**每次合成 pass 都明确 framebuffer 的格式**(用 `glGetFramebufferAttachmentParameteriv` 检查)。

### 3.2 · 🎨 图形学视角

**Porter-Duff 1984** 的论文 "Compositing Digital Images" 定义了 12 种合成算子,Over 只是其中一个。其他常见的:

- **Over**:A 在 B 上面(默认)
- **Under**:B 在 A 上面(等价于 `B over A`)
- **In**:A 只在 B 不透明的地方显示
- **Out**:A 只在 B 透明的地方显示
- **Atop**:A 在 B 不透明的地方显示
- **Xor**:A 和 B 在不重叠的地方显示
- **Plus**(加法):`A.rgb + B.rgb`,颜色可能超过 1.0(用于发光效果)
- **Multiply**(乘法):`A.rgb * B.rgb`,颜色变暗(用于阴影叠加)

游戏开发 90% 用 Over,但偶尔用 Plus(发光)和 Multiply(阴影)。

**预乘 alpha 在现代渲染的地位**:

- **OpenGL 推荐预乘**:enable `GL_BLEND` with `GL_ONE, GL_ONE_MINUS_SRC_ALPHA`(预乘版本的 blend factor)
- **Vulkan 强制预乘**:`VK_COMPOSITE_ALPHA_PRE_MULTIPLIED_BIT_KHR`
- **WebGPU 默认预乘**:swapchain 创建时指定

**Casey 选预乘是因为**后面做光照(Phong / PBR)在预乘空间更干净。Casey 后面 Day 389+ 用的合成公式都是预乘版本。

### 3.3 · 🐧 Linux 系统编程视角

合成在 Linux 桌面**无处不在**:

- **Wayland compositor**(mutter、wlroots、KWin):每个客户端 surface 是一张纹理,compositor 把它们合成到屏幕
- **X11 composite extension**:X server 把窗口画到 offscreen pixmap,composite manager 合成
- **PNG / WebP 解码**:图像格式解码器输出 RGBA,可能是预乘或非预乘

**Linux 上的合成工具**:

```bash
# 看 X11 上当前使用的 composite manager
ps aux | grep -E "compton|picom|xcompmgr"
# picom 是 X11 上流行的 compositor

# 看 Wayland compositor
echo $XDG_SESSION_TYPE
# wayland 或 x11

# 用 ImageMagick 测试合成
convert -size 100x100 xc:red red.png
convert -size 100x100 xc:'rgba(0,0,255,0.5)' blue_half.png
composite blue_half.png red.png result.png
# result.png 应该是紫色(蓝 50% 在红上)

# 检查 PNG 是不是预乘
identify -verbose result.png | grep -i "colorspace\|alpha"
# PNG 标准本身不强制预乘,但解码器输出可能是预乘
```

Wayland 的预乘 alpha:**Wayland 协议规定客户端 surface 是预乘**。如果你给 Wayland compositor 一个非预乘纹理,会出现"光晕"伪影。

### 3.4 · 🦀 Rust 生态视角

Rust 里做合成的常见 crate:

- `image`(image-rs)— PNG 解码,可以选预乘或非预乘输出
- `fast_image_resize` — 高性能 resize,支持预乘 alpha
- `tiny-skia` — 2D 矢量渲染,Skia 的 Rust 移植,内部用预乘 alpha
- `vello` — Vello,Vec 渲染器,Wayland / WebGPU 友好

**Rust 里写合成函数**:

```rust
/// Over operator(straight alpha 版本)
fn over_straight(top: [f32; 4], bot: [f32; 4]) -> [f32; 4] {
    let ta = top[3];
    let ba = bot[3];
    let out_a = ta + ba * (1.0 - ta);
    if out_a < 1e-6 {
        return [0.0, 0.0, 0.0, 0.0];
    }
    [
        (top[0] * ta + bot[0] * ba * (1.0 - ta)) / out_a,
        (top[1] * ta + bot[1] * ba * (1.0 - ta)) / out_a,
        (top[2] * ta + bot[2] * ba * (1.0 - ta)) / out_a,
        out_a,
    ]
}

/// Over operator(预乘 alpha 版本)
fn over_premul(top: [f32; 4], bot: [f32; 4]) -> [f32; 4] {
    let ta = top[3];
    let out_a = ta + bot[3] * (1.0 - ta);
    [
        top[0] + bot[0] * (1.0 - ta),
        top[1] + bot[1] * (1.0 - ta),
        top[2] + bot[2] * (1.0 - ta),
        out_a,
    ]
}
```

**对比**:预乘版本少 3 次乘法,简洁。straight 版本除以 out_a 是"去除 alpha 缩放",如果不需要后续用 alpha 可以不除。

**SIMD 优化**:用 `std::arch::x86_64::_mm_mul_ps` 一次处理 RGBA 4 通道:

```rust
#[cfg(target_arch = "x86_64")]
unsafe fn over_premul_simd(top: __m128, bot: __m128) -> __m128 {
    use std::arch::x86_64::*;
    let one = _mm_set1_ps(1.0);
    let ta = _mm_shuffle_ps(top, top, 0b11_11_11_11); // 把 alpha 广播到 4 通道
    // one_minus_ta = (1, 1, 1, 1) - (ta, ta, ta, ta)
    let one_minus_ta = _mm_sub_ps(one, ta);
    // bot * one_minus_ta
    let bot_scaled = _mm_mul_ps(bot, one_minus_ta);
    // top + bot_scaled
    _mm_add_ps(top, bot_scaled)
}
```

每行注释:
- `_mm_shuffle_ps(top, top, 0b11_11_11_11)` — 把 top 的第 3 通道(alpha)复制到 4 个通道。这个二进制 mask 编码"哪些源通道放到哪些目标通道"。
- `_mm_set1_ps(1.0)` — 4 个通道都设 1.0。
- `_mm_sub_ps` / `_mm_mul_ps` / `_mm_add_ps` — 标量运算的 SIMD 版本,4 个 f32 同时算。
- 结果是 RGBA 4 通道,合成的 out.rgb 和 out.a 都对(rgb 是 `top.rgb + bot.rgb * (1-ta)`,a 是 `top.a + bot.a * (1-ta)`,正好是同一个 SIMD 操作的结果)。

## 4 · 认知地图

### 4.1 上级

- **Compositing(合成)** — 把多个图层合成成一张图的过程
- **Post-processing(后处理)** — 渲染管线最后一步,合成 + 滤镜(模糊、bloom、tonemap)
- **Blending(混合)** — OpenGL 的 blend pipeline,over operator 是默认 blend 模式

### 4.2 同级

| 方案 | 关键差别 | 何时用 | HH 选 |
|---|---|---|---|
| Manual composite shader | fullscreen quad + GLSL | 多层合成 / 自定义 blend | ✅ |
| `glBlendFunc` 固定管线 | OpenGL 内置 blend | 单层混合 / 简单 alpha | 早期用 |
| Compute shader composite | GPGPU 并行 | 大量像素 + 复杂合成 | HH 不用 |
| CPU composite | 纯 Rust SIMD | 软件渲染 / 测试 | Day 399 用 |

**详细**:
- **Manual composite shader**:最灵活,GLSL 想写啥都行。Casey 选这个,因为要精确控制。
- **glBlendFunc**:简单(一行代码),但只支持几个预设模式(over、additive、multiply),自定义不行。
- **Compute shader**:GPU 并行,但启动开销大,适合上千次像素操作。
- **CPU composite**:Rust 端纯计算,适合 unit test(无 GPU 依赖)。

### 4.3 下级

- **Over operator** — A over B 的数学定义
- **Porter-Duff operators** — Over / In / Out / Atop / Xor / Plus / Multiply
- **Premultiplied alpha** — RGB 已经乘 alpha,合成公式更简洁
- **Linear vs sRGB** — 合成必须在 linear 空间
- **GL_FRAMEBUFFER_SRGB** — OpenGL 自动 sRGB 转换的开关
- **Fullscreen quad** — 覆盖屏幕的四边形,合成 shader 的"画布"

## 5 · 对照与变奏

### 同一问题在不同语境下的变体

**问题**:把 N 个半透明图层合成成一张图。

| 语境 | 实现 | 顺序 |
|---|---|---|
| Photoshop 图层 | 软件实现,逐像素 over | 顶层 over 底层 over ... |
| OpenGL 后处理 | fullscreen quad + GLSL | 远到近 |
| Wayland compositor | GPU 合成所有客户端 surface | z-order 排序后 over |
| 影视后期(Nuke) | 节点图,每个节点一个 over | 用户定义顺序 |
| 数学上 | `reduce(over, layers)` | 折叠操作 |

数学上合成是 **reduce**(折叠)操作:`over(over(over(A, B), C), D)` = `A over B over C over D`。Over 满足结合律(`(A over B) over C = A over (B over C)`),所以折叠顺序不影响结果(只要**原始图层顺序**不变)。

### 历史演化

- **1984**:Porter-Duff 论文定义 12 种合成算子,奠定现代合成理论。
- **1990s**:Photoshop 等软件实现这些算子。
- **2000s**:GPU 的 `glBlendFunc` 提供硬件加速合成(但只支持几个预设)。
- **2010s**:Fullscreen quad + GLSL composite shader 成为标准,自定义合成算子普及。
- **2020s**:Wayland 强制预乘 alpha,WebGPU 也默认预乘。

### CPU 合成 vs GPU 合成

| | CPU 合成 | GPU 合成 |
|---|---|---|
| 单位 | Rust 线程 + SIMD | GPU shader 核心 |
| 适合 | 小尺寸 / 单元测试 | 全屏 1080p+ |
| 代码 | Rust 标准库 + `std::arch` | GLSL / WGSL |
| 调试 | `println!` / `assert!` | RenderDoc / Nsight |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Premultiplied alpha 和 straight alpha 在合成的 RGB 计算上有何不同?给出两个版本的 over 公式,并解释为什么预乘版本"更简洁"。

**参考解答**:

**Straight alpha** 的 over:
```
out.rgb = A.rgb * A.a + B.rgb * B.a * (1 - A.a)
out.a   = A.a + B.a * (1 - A.a)
```

**Premultiplied alpha** 的 over:
```
out.rgb = A.rgb + B.rgb * (1 - A.a)
out.a   = A.a + B.a * (1 - A.a)
```

预乘版本"更简洁"因为:

1. A.rgb 已经乘过 A.a,所以公式里直接是 `A.rgb`,不需要 `* A.a`
2. B.rgb 也已经乘过 B.a,所以 `(B.rgb) * (1 - A.a)` 是预乘后的 B 缩放(注意 `(B.rgb * B.a) * (1 - A.a)` 在预乘版本里就是 `B.rgb * (1 - A.a)`,因为 B.rgb 已经是预乘的)
3. 少了两次乘法,GPU 端每个像素少 6 次 fma 操作

代价:存纹理前要预乘一次(`rgb *= a`),解码 PNG 后要做这步。但存储和采样是同样的格式,采样器透明处理。

### Lv2 · 动手实践

**题**:在 Rust 里实现 `over_premul` 和 `over_straight` 两个函数,写单元测试验证两者的等价性(给定同一组输入,两种版本输出相同的最终不透明颜色)。

完成标准:`cargo test` 通过,两个函数对同一输入给出相同的 `(r, g, b)`(alpha 可能不同但 RGB 应该一致)。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Pixel { r: f32, g: f32, b: f32, a: f32 }

fn over_straight(top: Pixel, bot: Pixel) -> Pixel {
    let ta = top.a;
    let ba = bot.a;
    let out_a = ta + ba * (1.0 - ta);
    if out_a < 1e-6 {
        return Pixel { r: 0., g: 0., b: 0., a: 0. };
    }
    Pixel {
        r: (top.r * ta + bot.r * ba * (1.0 - ta)) / out_a,
        g: (top.g * ta + bot.g * ba * (1.0 - ta)) / out_a,
        b: (top.b * ta + bot.b * ba * (1.0 - ta)) / out_a,
        a: out_a,
    }
}

fn over_premul(top: Pixel, bot: Pixel) -> Pixel {
    let ta = top.a;
    let out_a = ta + bot.a * (1.0 - ta);
    Pixel {
        r: top.r + bot.r * (1.0 - ta),
        g: top.g + bot.g * (1.0 - ta),
        b: top.b + bot.b * (1.0 - ta),
        a: out_a,
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    fn approx_eq(a: f32, b: f32) -> bool { (a - b).abs() < 1e-5 }

    #[test]
    fn straight_and_premul_match_rgb() {
        // Straight 输入
        let top_s = Pixel { r: 1.0, g: 0.0, b: 0.0, a: 0.5 };
        let bot_s = Pixel { r: 0.0, g: 0.0, b: 1.0, a: 0.5 };

        // 转预乘:r *= a, g *= a, b *= a
        let top_p = Pixel { r: top_s.r * top_s.a, g: top_s.g * top_s.a, b: top_s.b * top_s.a, a: top_s.a };
        let bot_p = Pixel { r: bot_s.r * bot_s.a, g: bot_s.g * bot_s.a, b: bot_s.b * bot_s.a, a: bot_s.a };

        let out_s = over_straight(top_s, bot_s);
        let out_p_premul = over_premul(top_p, bot_p);

        // 预乘结果的 RGB 需要除以 alpha 才能跟 straight 的 RGB 比较
        // (因为 straight 的 RGB 是"如果不透明时的颜色",预乘是"已经乘 alpha")
        let out_p_straight = if out_p_premul.a > 1e-6 {
            Pixel {
                r: out_p_premul.r / out_p_premul.a,
                g: out_p_premul.g / out_p_premul.a,
                b: out_p_premul.b / out_p_premul.a,
                a: out_p_premul.a,
            }
        } else {
            out_p_premul
        };

        assert!(approx_eq(out_s.r, out_p_straight.r), "R: {} vs {}", out_s.r, out_p_straight.r);
        assert!(approx_eq(out_s.g, out_p_straight.g), "G: {} vs {}", out_s.g, out_p_straight.g);
        assert!(approx_eq(out_s.b, out_p_straight.b), "B: {} vs {}", out_s.b, out_p_straight.b);
        assert!(approx_eq(out_s.a, out_p_straight.a), "A: {} vs {}", out_s.a, out_p_straight.a);
    }

    #[test]
    fn opaque_top_ignores_bot() {
        let top = Pixel { r: 1.0, g: 0.5, b: 0.0, a: 1.0 };
        let bot = Pixel { r: 0.0, g: 1.0, b: 0.0, a: 1.0 };
        let out = over_straight(top, bot);
        assert!(approx_eq(out.r, 1.0));
        assert!(approx_eq(out.g, 0.5));
        assert!(approx_eq(out.b, 0.0));
    }

    #[test]
    fn transparent_top_returns_bot() {
        let top = Pixel { r: 1.0, g: 0.0, b: 0.0, a: 0.0 };
        let bot = Pixel { r: 0.0, g: 0.0, b: 1.0, a: 1.0 };
        let out = over_straight(top, bot);
        assert!(approx_eq(out.r, 0.0));
        assert!(approx_eq(out.g, 0.0));
        assert!(approx_eq(out.b, 1.0));
    }
}
```

**每段解释**:
- straight 版本的最后 `/ out_a` —— 因为 straight 的 RGB 是"如果不透明时的颜色",而 `(top.r * ta + bot.r * ba * (1-ta))` 是"实际贡献"(已乘各自的 alpha),除以总 alpha 才能得到"如果不透明时的颜色"。
- 预乘版本没这个除法,因为预乘的 RGB 就是"实际贡献",直接相加。
- `approx_eq` 用 1e-5 容差,因为 f32 浮点运算有累积误差。
- 单元测试覆盖三种边界:两层都半透明 / 顶层不透明 / 顶层全透明。

### 完整 Rust + glium 合成 demo

```toml
# Cargo.toml
[package]
name = "composite_demo"
version = "0.1.0"
edition = "2021"

[dependencies]
glium = "0.34"
```

```rust
// src/main.rs
// 合成两张半透明纹理,验证 Over operator

use glium::{glutin, Surface, implement_vertex, uniform, program, index, texture};

#[derive(Copy, Clone)]
struct Vertex { position: [f32; 2], uv: [f32; 2] }
implement_vertex!(Vertex, position, uv);

fn main() {
    let event_loop = glutin::event_loop::EventLoop::new();
    let wb = glutin::window::WindowBuilder::new()
        .with_inner_size(glutin::dpi::LogicalSize::new(512, 512));
    let cb = glutin::ContextBuilder::new();
    let display = glium::Display::new(wb, cb, &event_loop).unwrap();

    // 1. 创建两张 256x256 纹理(模拟深度剥离的两层)
    let layer0_pixels: Vec<[f32; 4]> = (0..256*256).map(|i| {
        let x = (i % 256) as f32 / 255.0;
        // layer0: 横向红色梯度,alpha=0.5(半透明红)
        [x, 0.0, 0.0, 0.5]
    }).collect();
    let layer1_pixels: Vec<[f32; 4]> = (0..256*256).map(|i| {
        let y = (i / 256) as f32 / 255.0;
        // layer1: 纵向蓝色梯度,alpha=0.5(半透明蓝)
        [0.0, 0.0, y, 0.5]
    }).collect();

    let tex0 = texture::Texture2d::with_format(
        &display,
        texture::RawImage2d {
            data: std::borrow::Cow::Owned(bytemuck_cast(&layer0_pixels)),
            width: 256, height: 256, format: texture::ClientFormat::F32F32F32F32,
        },
        texture::UncompressedFloatFormat::F32F32F32F32,
        texture::MipmapsOption::NoMipmap,
    ).unwrap();
    let tex1 = texture::Texture2d::with_format(
        &display,
        texture::RawImage2d {
            data: std::borrow::Cow::Owned(bytemuck_cast(&layer1_pixels)),
            width: 256, height: 256, format: texture::ClientFormat::F32F32F32F32,
        },
        texture::UncompressedFloatFormat::F32F32F32F32,
        texture::MipmapsOption::NoMipmap,
    ).unwrap();

    // 2. Fullscreen quad
    let verts = vec![
        Vertex { position: [-1., -1.], uv: [0., 0.] },
        Vertex { position: [ 1., -1.], uv: [1., 0.] },
        Vertex { position: [-1.,  1.], uv: [0., 1.] },
        Vertex { position: [ 1.,  1.], uv: [1., 1.] },
    ];
    let vbuf = glium::VertexBuffer::new(&display, &verts).unwrap();
    let indices = index::NoIndices(index::PrimitiveType::TriangleStrip);

    // 3. 合成 shader
    let program = program!(&display,
        330 es => {
            vertex: r#"
                #version 330
                in vec2 position;
                in vec2 uv;
                out vec2 v_uv;
                void main() {
                    v_uv = uv;
                    gl_Position = vec4(position, 0.0, 1.0);
                }
            "#,
            fragment: r#"
                #version 330
                in vec2 v_uv;
                out vec4 frag;
                uniform sampler2D layer0;
                uniform sampler2D layer1;
                void main() {
                    vec4 c0 = texture(layer0, v_uv);  // 近
                    vec4 c1 = texture(layer1, v_uv);  // 远
                    // Over:straight alpha 版本
                    vec3 rgb = c0.rgb * c0.a + c1.rgb * c1.a * (1.0 - c0.a);
                    float a = c0.a + c1.a * (1.0 - c0.a);
                    // 除以 alpha 得到"如果不透明时的颜色"
                    if (a > 1e-6) rgb /= a;
                    frag = vec4(rgb, 1.0);  // 写入不透明 framebuffer
                }
            "#,
        }).unwrap();

    event_loop.run(move |event, _, control_flow| {
        use glutin::event::{Event, WindowEvent};
        use glutin::event_loop::ControlFlow;
        *control_flow = ControlFlow::Wait;

        if let Event::RedrawRequested(_) = event {
            let mut target = display.draw();
            target.clear_color(0.1, 0.1, 0.1, 1.0);  // 暗灰背景
            let uniforms = uniform! { layer0: &tex0, layer1: &tex1 };
            target.draw(&vbuf, &indices, &program, &uniforms, &Default::default()).unwrap();
            target.finish().unwrap();
        }

        if let Event::WindowEvent { event: WindowEvent::CloseRequested, .. } = event {
            *control_flow = ControlFlow::Exit;
        }
    });
}

// 简单的 bytemuck 替代(避免加依赖)
fn bytemuck_cast(pixels: &[[f32; 4]]) -> Vec<u8> {
    let mut bytes = Vec::with_capacity(pixels.len() * 16);
    for p in pixels {
        bytes.extend_from_slice(bytemuck::bytes_of(p));
    }
    bytes
}
```

**解释**:
- `ClientFormat::F32F32F32F32` — 客户端数据的格式(RGBA32F)
- `UncompressedFloatFormat::F32F32F32F32` — GPU 内部存储格式(同上)
- 合成 shader 用 straight alpha 版本(更易理解),最后除以 alpha 得到不透明颜色,因为默认 framebuffer 是不透明
- `gl_Position = vec4(position, 0.0, 1.0)` — fullscreen quad 的 z 设 0,不参与深度测试(默认 framebuffer 也有深度 buffer,但我们不用)
