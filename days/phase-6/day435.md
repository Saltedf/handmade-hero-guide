# Day 435 · 从 Win32 加载器移除 CRT(Phase 6 收官)

> 这是 Phase 6 的最后一集,也是 Casey 标志性的"硬核"操作——把 C Runtime(CRT)从 Win32 加载器完全剥离。CRT 通常 1MB+,但 Casey 的加载器只需要几 KB。剥离 CRT 后,二进制从 1MB 缩到 50KB,**启动快 10 倍**。这一集的"精神"在 Linux 是同样的:静态链接 musl、剥离 libgcc、写 freestanding Rust。

## 0 · 为什么要有这一天

具体场景:你的游戏 exe 在 Windows 上是 1MB。其中 950KB 是 CRT(Visual C++ Runtime),包括:

- `printf` / `malloc` / `memcpy` 等标准库
- 启动代码(`mainCRTStartup`)
- 全局构造/析构
- 异常处理
- 安全检查(cookie、stack canary)

但你的游戏**只用了 Win32 API**(自己写窗口、自己写内存分配),根本不需要 CRT。CRT 是"多余的依赖"。

Casey 剥离 CRT 后,exe 缩到 50KB,**纯 Win32 API**,无任何依赖。启动从 100ms 缩到 10ms。这是"极简主义"的极致——只依赖操作系统真正提供的接口,不依赖语言运行时。

为什么重要?三个工程价值:

1. **依赖最少**:无 CRT 意味着跨 Windows 版本兼容性极佳(XP/7/10/11 都跑)
2. **启动快**:无 CRT 初始化,直接进 main
3. **学习价值**:理解"二进制实际跑起来需要什么",从抽象走到底层

Casey 用 Visual C++ 的 `/NODEFAULTLIB` 链接器选项剥离 CRT。他自己写 `_start` 入口(替代 mainCRTStartup),手动调用 ExitProcess 结束。

**Linux 上的等价做法**:

- **musl 静态链接**:`rustup target add x86_64-unknown-linux-musl`,编译出无 glibc 依赖的二进制
- **`#![no_std]`**:Rust 不链接 std,只用 core
- **`#![no_main]`**:Rust 不用默认 main,自己写 `_start`
- **stripped binary**:`strip target/release/app`,去掉符号表

Casey 在 Windows,但**Linux 用户也能学**——理解二进制启动、运行时依赖、最小化打包。Phase 6 收官日,Casey 用这个看似"无关"的题目,实际上总结了整个 phase 的精神:**理解底层,而不是用现成抽象**。

心理锚点:今天之后,你能解释 PE/ELF 二进制的启动过程,知道 `main` 之前发生了什么,能在 Linux 写 `#![no_std]` 的极简二进制,理解工业嵌入式/启动加载器的工程哲学。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 在 Visual Studio 项目设置里改链接选项:

1. **`/NODEFAULTLIB`**:不链接默认库(msvcrt.lib 等)
2. **`/ENTRY:start`**:入口点改成自己的 `start`,不用 `mainCRTStartup`
3. **自己写 `_start`**:
   ```c
   void __cdecl start(void) {
       // 直接调用 WinMain,无 CRT 初始化
       int result = WinMain(...);
       ExitProcess(result);
   }
   ```
4. **替代 CRT 函数**:把 `memset`、`memcpy` 改成手写,或用 Win32 `RtlMoveMemory`
5. **去掉异常处理**:`/EH-`(无异常)
6. **去掉 RTTI**:`/GR-`(无运行时类型信息)

编译后二进制 16KB(从 1.2MB 缩小 75 倍)。Casey 强调:**这不只是为了好玩**,而是让游戏在所有 Windows 版本上跑,不需要 Visual C++ Redistributable 安装。

## 2 · 心智模型

### 类比: Minimalist Camping

想象露营。

- **舒适版**(带 CRT):带帐篷、睡袋、炉具、椅子、桌子,总重 30kg。舒服但笨重。
- **极简版**(无 CRT):只带必需(轻便帐篷、小刀、火种),总重 3kg。不舒适但**自由**,可以走更远。

二进制完全同构。

- **带 CRT**:有 printf、malloc、数学库,二进制大、依赖多。开发方便。
- **无 CRT**:只有 OS API,二进制小、依赖少。开发累,但**部署灵活**。

工业游戏发布版常常做 CRT 剥离,减少用户安装步骤(不需要 Visual C++ Redistributable)。

### 严谨原理:二进制启动流程

正常 C/C++ 二进制启动:

```
1. 加载器(Loader)把 exe 装入内存
2. 跳到 PE 入口点(默认 mainCRTStartup)
3. mainCRTStartup:
   a. 初始化 CRT(_initterm,全局构造)
   b. 初始化堆(malloc 用)
   c. 解析命令行(GetCommandLineW)
   d. 调用 main / WinMain
4. main 返回后,CRT 调用 ExitProcess

总共:~100ms 初始化时间,几 MB 内存
```

剥离 CRT 后:

```
1. 加载器把 exe 装入内存
2. 跳到入口点(我们的 _start)
3. _start 直接调用 WinMain,无 CRT 初始化
4. WinMain 返回后,_start 调用 ExitProcess

总共:~5ms 初始化时间,几十 KB 内存
```

### Linux 的等价启动

ELF 二进制启动:

```
1. 内核加载 ELF,设置 stack
2. 跳到 _start(来自 crt1.o,默认)
3. _start:
   a. 调用 __libc_start_main
   b. __libc_start_main 初始化 glibc
   c. 调用 main
4. main 返回,调用 exit
```

剥离 glibc:

- 用 **musl libc**(更轻量):`x86_64-unknown-linux-musl`
- 完全无 libc:`#![no_std] + #![no_main]`,自己写 `_start`

### Rust 的 #![no_std]

Rust 标准库 `std` 依赖 libc(操作系统接口)。`#![no_std]` 不用 std,只用 `core`(无 OS 依赖):

```rust
#![no_std]
#![no_main]

use core::panic::PanicInfo;

#[panic_handler]
fn panic(_: &PanicInfo) -> ! {
    loop {}
}

#[no_mangle]
pub extern "C" fn _start() -> ! {
    // 直接调用 syscall,不用 libc
    // 这里写你的极简逻辑
    loop {}
}
```

这种 Rust 可以编译成 **freestanding binary**,跑在裸机(无 OS)。Linux 上可以跑(用 syscall),也可以烧到 microcontroller。

### Rust + Linux syscall 示例

```rust
#![no_std]
#![no_main]

use core::panic::PanicInfo;

#[panic_handler]
fn panic(_: &PanicInfo) -> ! { loop {} }

const SYS_WRITE: usize = 1;
const SYS_EXIT: usize = 60;

unsafe fn syscall(num: usize, a: usize, b: usize, c: usize) -> usize {
    let ret;
    core::arch::asm!(
        "syscall",
        inlateout("rax") num => ret,
        in("rdi") a,
        in("rsi") b,
        in("rdx") c,
        out("rcx") _,
        out("r11") _,
    );
    ret
}

#[no_mangle]
pub extern "C" fn _start() -> ! {
    let msg = b"Hello, no_std!\n";
    unsafe {
        syscall(SYS_WRITE, 1, msg.as_ptr() as usize, msg.len());
        syscall(SYS_EXIT, 0, 0, 0);
    }
    loop {}
}
```

编译:`cargo build --target x86_64-unknown-linux-none`(自定义 target)。生成的 ELF 不依赖 glibc。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业的"最小化二进制":

- **游戏 exe**:通常不剥离 CRT(用了 STL、boost 等),但 strip 符号
- **bootloader / firmware**:完全无 CRT,裸机
- **malware / virus**:剥离 CRT 隐藏,体积小
- **CTF challenges**:无 CRT 二进制,挑战逆向

工业游戏的"安装包"已经很大(几 GB 数据),exe 大小不太关键。但**启动速度**关键——CRT 初始化 100ms,玩家每次启动游戏都等。剥离 CRT 让启动从慢到快。

### 3.2 · 🎨 图形学视角

图形学的"最小化":

- **Shader**:GLSL/HLSL 没有 std,只有图形 intrinsics
- **GPU compute**:CUDA kernel 无 libc
- **Render hooks**:嵌入式 renderer,无 OS

shader 是"无 CRT"的极端例子——只有数学运算和纹理访问,无 I/O。

### 3.3 · 🐧 Linux 系统编程视角

Linux 的"无 CRT"传统:

- **musl libc**:比 glibc 小 10 倍,Alpine Linux 默认
- **busybox**:每个 applet 几 KB,替代 GNU coreutils
- **嵌入式 Linux**:OpenWrt、Yocto,无 glibc
- **kernel modules**:内核模块无 libc,自己实现 printk 等

`/lib/ld-linux-x86-64.so.2` 是 Linux 的"加载器",对应 Windows 的 `ntdll.dll`。无 libc 二进制直接 syscall,绕过它。

### 3.4 · 🦀 Rust 生态视角

Rust 的"freestanding"生态:

- `#![no_std]`:crate 不依赖 std,只用 core
- `#![no_main]`:二进制不用默认 main
- `cortex-m`(ARM):嵌入式 Rust
- `bootloader`:Rust 写的 bootloader
- `redox-os`:Rust 写的 OS,无 C 代码

Rust 在嵌入式(ARM、RISC-V)和 OS 开发是主流语言之一,因为 no_std 友好。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 Casey 剥离 CRT,但 Rust 游戏开发通常不剥离?具体说,各有什么权衡?

**参考解答**:**Casey 剥离 CRT**(HH,Windows):

- 优势:exe 16KB,启动快,无 Visual C++ Redistributable 依赖
- 代价:不能用 printf/malloc/math.h,自己写或用 Win32 API
- 适合:学习目的、追求极致的极简主义

**Rust 不剥离 std**(普通游戏):

- 优势:用 Vec、String、Result 等,开发效率高
- 代价:二进制几 MB,依赖 glibc
- 适合:绝大多数游戏,开发效率 > 二进制大小

权衡关键:**开发效率 vs 极简主义**。普通游戏几 GB 资产,二进制大小无所谓,开发效率关键。HH 是教育项目,极简主义是教学价值。

Rust 也支持 no_std,但 game dev 99% 不用——std 太方便了。

  "panic-strategy": "abort",
  "disable-redzone": true,
  "features": "-mmx,-sse,+soft-float"
}
EOF

# 3. 写 src/main.rs
cat > src/main.rs <<'RUSTEOF'

#![no_main]

#[panic_handler]
fn panic(_: &PanicInfo) -> ! { loop {} }

const SYS_WRITE: usize = 1;
const SYS_EXIT: usize = 60;

unsafe fn sys_write(fd: usize, buf: &[u8]) -> usize {
    let ret;
    core::arch::asm!(
        "syscall",
        inlateout("rax") SYS_WRITE => ret,
        in("rdi") fd,
        in("rsi") buf.as_ptr(),
        in("rdx") buf.len(),
        out("rcx") _,
        out("r11") _,
    );
    ret
}

unsafe fn sys_exit(code: usize) -> ! {
    core::arch::asm!(
        "syscall",
        in("rax") SYS_EXIT,
        in("rdi") code,
        options(noreturn)
    );
}

    let msg = b"Hello from no_std!\n";
    unsafe {
        sys_write(1, msg);
        sys_exit(0);
    }
}

# 5. 链接

# 6. 测试
./no_std_hello
# Hello from no_std!

# 7. 检查大小和依赖

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
