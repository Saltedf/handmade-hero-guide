
# Day 300 · 从排序键改为排序规则

> Day 300 是 HH 的里程碑——三分之一进度。今天 Casey 做一个**架构级**决定:把 sort key(整数比较)换成 sort rules(规则函数)。原因是 day 299 发现 sprite bounds 有时**无法压进一个整数**——某些排序逻辑是"部分序"而非"全序"。

## 0 · 为什么要有这一天

到目前为止,sort key 是 `u64`——一个数字,小到大排。这种方式有个隐含假设:**所有实体可以线性排序**。但今天 Casey 发现有些情况不满足:

考虑两个 sprite:

- 玩家 sprite(中心 100, bounds 32x48),bounds 在 (84, 76) 到 (116, 124)
- 怪物 sprite(中心 110, bounds 64x32),bounds 在 (78, 94) 到 (142, 126)

它们的 bounds **重叠**(94 < 124, 76 < 110,等)。这种情况下:

- 用 bottom_y 排:玩家 124,怪物 126,怪物在前(126 > 124)
- 但实际视觉上,玩家在怪物前(玩家头在怪物头之上)

或者考虑两个**交叉**的 sprite:A 的 bottom 在 B 的中间——A 应该在 B 前还是后?**没有单一答案**,取决于"哪个更靠下"。这种"部分序"无法用一个 sort_key 表达。

更糟糕的:**有些实体的 sort 规则依赖动态状态**。比如"无敌时玩家在最前",无敌结束恢复——sort_key 必须每帧重算,且不一定是单调的整数。

Casey 的解决方案:**放弃 sort_key,改用 sort rules**。每对实体问一次"谁在前",答案是 `<`、`=`、`>`。这种"比较函数"是**部分序**——可以处理 bounds 重叠等复杂情况。

代价:慢。sort_key 是 O(n log n) 比较 u64,sort_rules 是 O(n log n) 比较,但每次比较要执行函数(可能复杂)。但对 100-1000 实体的场景,这点开销可以接受。

今天的代码量:重写 sort 调用,从 `sort_by_key` 改成 `sort_by` + 比较函数。设计比较函数处理多种情况。

心理锚点:看完今天,你应该理解"全序 vs 部分序"的区别,知道何时该用 sort_key、何时该用 sort_rules。

## 2 · 心智模型

### 类比:文件资源管理器的多列排序

Windows 资源管理器可以按多列排序——先按类型,再按修改日期,再按大小。每列点击切换升序/降序。这种排序不能压进一个整数——因为"类型"是字符串、"日期"是时间戳、"大小"是数字,类型不同。

文件管理器的实现:用**比较函数**——逐列比较,返回 Ordering。这个函数本质就是 sort_rule。

```
fn file_compare(a: &File, b: &File) -> Ordering {
    // 第一优先级:类型
    match a.type.cmp(&b.type) {
        Ordering::Equal => {},
        ord => return ord,
    }
    // 第二优先级:日期(降序)
    match b.date.cmp(&a.date) {
        Ordering::Equal => {},
        ord => return ord,
    }
    // 第三优先级:大小
    a.size.cmp(&b.size)
}
```

HH 今天的 sort_rule 类似——多层规则,逐级比较。

### 2.1 全序 vs 部分序

**全序(total order)**:任意两个元素 a 和 b,可以确定 a < b 或 a == b 或 a > b。u64 排序是全序。

**部分序(partial order)**:有些对无法比较——既不是 < 也不是 > 也不是 ==。比如集合的"子集"关系——{1, 2} 和 {2, 3} 既不是子集也不是超集。

游戏 entity 的 sort 是部分序:sprite A 和 B 的 bounds 重叠时,无法简单说谁在前——可能 A 在 B 的左上,也可能 B 在 A 的右下。

**部分序的挑战**:不能直接用 sort——sort 假设全序。两种处理:

1. **加 tie-breaker**——强制变全序,如"重叠时按 spawn_id"。简单但可能不"对"
2. **拓扑排序**——承认是 DAG(有向无环图),按拓扑顺序。复杂但正确

Casey 今天用方法 1(加 tie-breaker),day 304 用方法 2(拓扑排序)。

### 2.2 sort_rule 函数签名

```rust
use std::cmp::Ordering;

fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    // 第一级:layer
    match a.layer.cmp(&b.layer) {
        Ordering::Equal => {},
        ord => return ord,
    }
    // 第二级:bounds 重叠检查
    if !bounds_overlap(a, b) {
        // 不重叠:按 bottom_y 排
        return bottom_y(a).cmp(&bottom_y(b));
    }
    // 重叠:复杂情况,加 tie-breaker
    // 第三级:bottom_y
    match bottom_y(a).cmp(&bottom_y(b)) {
        Ordering::Equal => {},
        ord => return ord,
    }
    // 第四级:x
    match a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal) {
        Ordering::Equal => {},
        ord => return ord,
    }
    // 第五级:spawn_id(tie-breaker)
    a.spawn_id.cmp(&b.spawn_id)
}
```

每级返回 Ordering,如果 Equal 继续下一级。最后是 spawn_id——保证全序(不会无限 Equal)。

### 2.3 bounds_overlap 检查

```rust
fn bounds_overlap(a: &Entity, b: &Entity) -> bool {
    let a_rect = a.bounds.rect(a.pos);
    let b_rect = b.bounds.rect(b.pos);
    a_rect.x < b_rect.x + b_rect.w &&
    a_rect.x + a_rect.w > b_rect.x &&
    a_rect.y < b_rect.y + b_rect.h &&
    a_rect.y + a_rect.h > b_rect.y
}
```

标准 AABB(轴对齐边界框)重叠测试。Day 050 教过。

### 2.4 性能考量

sort_by(sort_rule) 比 sort_by_key(sort_key) 慢:

- sort_by_key 每个元素算一次 key(O(n)),sort 是 O(n log n) 比较 key
- sort_by 每次比较都执行函数(O(n log n) 次函数调用)

对 1000 个实体,sort_by 可能多 5-10ms。这是 60 FPS 游戏 16.67ms 帧预算的 1/3——明显。

优化:

1. **缓存 bottom_y**:rule 函数内不每次算 bottom_y,提前算好存 entity 字段
2. **快速路径**:大部分情况 layer 不同,先比 layer,Equal 才进复杂逻辑
3. **混合策略**:大部分用 sort_key(快),少数复杂情况用 sort_rule

Casey 今天先实现正确性,性能优化留到后续 day。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对 sort 的几种思路:

- **Z-buffer**(GPU):像素级 depth,完全消除 sort 问题
- **Sort key**(整数):简单快,但只能全序
- **Sort rule**(比较函数):灵活,处理部分序
- **Topological sort**:严格 DAG 排序,处理"互相遮挡"

商业游戏常用混合:大部分 entity 用 sort key(快),特殊物体(大 sprite、复杂几何)用 sort rule。

工业级"sort"在 Source engine 的 visibility system 里复杂——结合 BSP、PVS、sort 多种算法。Casey HH 远不到那个规模,但概念相通。

### 3.2 · 🎨 图形学视角

图形学里"部分序"对应**Order-Independent Transparency(OIT)**:

- W-buffer:精确 depth 但 alpha 难处理
- A-buffer:每个像素存 fragment list,最后 sort + blend
- Depth peeling:多 pass,每 pass 找下一层最前 fragment
- Weighted blended OIT:近似算法,不需 sort,但物理不准

OIT 是研究热点,Casey 在 Phase 8+ 切 OpenGL 后会接触。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里"比较函数排序"对应**comparator-based sort**。内核的 `list_sort`、`sort` 都是 comparator 形式:

```c
// linux/lib/sort.c
void sort(void *base, size_t num, size_t size,
    int (*cmp_func)(const void *, const void *),
    void (*swap_func)(void *, void *, int size));
```

`cmp_func` 是比较函数,返回负/零/正(类似 Rust 的 Ordering)。Casey 今天做的 sort_rule 是内核 sort 的 Rust 化。

具体例子:Linux scheduler 的 task 排序,用 `sched_slice` 等比较函数,综合考虑 vruntime、nice、优先级——多层规则。

### 3.4 · 🦀 Rust 生态视角

Rust 的 `sort_by`:

```rust
entities.sort_by(|a, b| sort_rule(a, b));
// 或
entities.sort_by(sort_rule);  // 函数作为参数
```

`sort_by` 是稳定排序——同 sort_rule 返回 Equal 的元素保持原顺序。`sort_unstable_by` 不稳定但快。

Rust 的 `Ordering` enum:

```rust
enum Ordering { Less, Equal, Greater }
```

类似 C 的 `int (-1, 0, 1)`,但更类型安全。

**写 sort_rule 的 Rust 惯用法**:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| bottom_y(a).cmp(&bottom_y(b)))
        .then_with(|| a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
        .then(a.spawn_id.cmp(&b.spawn_id))
}
```

`then` 和 `then_with` 是 Ordering 的 method——前一个 Equal 时执行下一个。比 match 写法简洁。

## 5 · 对照与变奏

### 不同语言的比较函数

| 语言 | 写法 |
|---|---|
| Rust | `fn(a, b) -> Ordering` |
| C | `int cmp(const void* a, const void* b)` 返回 -1/0/1 |
| C++ | `bool operator()(a, b)`(返回 a < b) |
| Python | `key=lambda x: ...` 或 `functools.cmp_to_key` |
| Go | `func(i, j int) bool`(返回 less[i] < less[j]) |
| JS | `function(a, b) -> number` 返回 -1/0/1 |

C++ 的 comparator 只返回 bool(less),所以"相等"和"不小于"都是 false。Rust 返回 Ordering 更明确。

### sort 算法的稳定性

| 算法 | 稳定 | 时间 |
|---|---|---|
| Rust sort_by | 是 | O(n log n) |
| Rust sort_unstable_by | 否 | O(n log n) 但快 30-50% |
| C qsort | 否 | O(n log n) |
| C++ std::sort | 否 | O(n log n) |
| C++ std::stable_sort | 是 | O(n log² n) |

游戏 entity sort 通常不在乎稳定性(同 sort_rule 的实体顺序无所谓),用 unstable。

### Lv2 · 动手实践

**题**:实现 sort_rule,有 4 级:layer、bottom_y、x、spawn_id。验证排序正确。

完成标准:测试 5 个实体,排序结果符合多级规则。

**参考解答**:

```rust
use std::cmp::Ordering;

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
struct Entity {
    layer: u8,
    pos: Vec2,
    spawn_id: u16,
    name: &'static str,
}

fn bottom_y(e: &Entity) -> f32 {
    e.pos.y  // 假设 bounds 在中心
}

fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| bottom_y(a).partial_cmp(&bottom_y(b)).unwrap_or(Ordering::Equal))
        .then_with(|| a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
        .then(a.spawn_id.cmp(&b.spawn_id))
}

fn main() {
    let mut entities = vec![
        Entity { layer: 1, pos: Vec2::new(100.0, 100.0), spawn_id: 1, name: "A" },
        Entity { layer: 1, pos: Vec2::new(50.0, 100.0), spawn_id: 2, name: "B" },
        Entity { layer: 0, pos: Vec2::new(100.0, 100.0), spawn_id: 3, name: "C" },
        Entity { layer: 1, pos: Vec2::new(100.0, 50.0), spawn_id: 4, name: "D" },
        Entity { layer: 1, pos: Vec2::new(100.0, 100.0), spawn_id: 5, name: "E" },
    ];

    entities.sort_by(sort_rule);
    for (i, e) in entities.iter().enumerate() {
        println!("#{}: {} layer={} pos=({},{}) spawn={}",
            i, e.name, e.layer, e.pos.x, e.pos.y, e.spawn_id);
    }

    // 预期排序:
    // C (layer 0 最先)
    // D (layer 1, y=50)
    // B (layer 1, y=100, x=50)
    // A (layer 1, y=100, x=100, spawn=1)
    // E (layer 1, y=100, x=100, spawn=5)
    assert_eq!(entities[0].name, "C");
    assert_eq!(entities[1].name, "D");
    assert_eq!(entities[2].name, "B");
    assert_eq!(entities[3].name, "A");
    assert_eq!(entities[4].name, "E");
    println!("Sort rule test passed!");
}
```

**每行解释**:
- `.then_with(|| ...)` — 前 Equal 时调 closure 算下一个比较
- `.then(...)` — 同 then_with 但接收已计算的 Ordering
- 链式比较非常清晰——读起来就是规则列表

### Rust 完整可跑示例

§7 Lv2 完整可跑。这里加 bounds 重叠检查:

```rust
#[derive(Copy, Clone, Debug)]
struct Bounds { w: f32, h: f32 }
impl Bounds {
    fn rect(&self, pos: Vec2) -> (f32, f32, f32, f32) {
        (pos.x - self.w/2.0, pos.y - self.h/2.0, self.w, self.h)
    }
    fn bottom_y(&self, pos: Vec2) -> f32 { pos.y + self.h / 2.0 }
}

fn bounds_overlap(a_pos: Vec2, a_b: &Bounds, b_pos: Vec2, b_b: &Bounds) -> bool {
    let (ax, ay, aw, ah) = a_b.rect(a_pos);
    let (bx, by, bw, bh) = b_b.rect(b_pos);
    ax < bx + bw && ax + aw > bx && ay < by + bh && ay + ah > by
}

fn main() {
    let p1 = Vec2::new(100.0, 100.0);
    let p2 = Vec2::new(110.0, 100.0);
    let b1 = Bounds { w: 32.0, h: 48.0 };
    let b2 = Bounds { w: 32.0, h: 48.0 };

    println!("Overlap: {}", bounds_overlap(p1, &b1, p2, &b2));
    // 距离 10 < 32,应该重叠

    let p3 = Vec2::new(200.0, 100.0);
    println!("Far overlap: {}", bounds_overlap(p1, &b1, p3, &b2));
    // 距离 100 > 32,不重叠
}
```

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 历史脉络与工业实践

1990 年代 id Software 的 Doom(1993)用 BSP tree + painter's algorithm——排序在编译期完成,运行时 O(N) 遍历。Quake(1996)首次用 Z-buffer(GPU 硬件),彻底解决排序问题。

2D 游戏排序的演化:

- **1990-1995**:Y-sort 在 JRPG 普及(最终幻想 6、超时空之轮)
- **1995-2005**:Multi-layer Y-sort(星际争霸、暗黑破坏神 2)
- **2005-2015**:引擎内置 sort(Unity、GameMaker)
- **2015-2025**:GPU + sort 混合(bevy、Unreal)

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
