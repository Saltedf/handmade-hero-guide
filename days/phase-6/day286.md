
# Day 286 · 开始解耦实体行为

> 你的游戏现在能跑、能渲染、能热重载,但 `update` 函数里塞满了 `if entity.kind == PLAYER { ... } else if entity.kind == MONSTAR { ... } else if ...`。Casey 今天要做的不是"加新怪物",而是**把行为从 switch 里抠出来,放到数据里**——为后面 25 天的新怪物(AI 蛇、随从、手套道具)做铺垫。

## 0 · 为什么要有这一天

你现在的代码大概长这样:一个巨型 `match` 或 `switch` 把每种实体分开处理。玩家有玩家的更新逻辑、怪物有怪物的更新逻辑、家具有家具的更新逻辑。**看起来很自然,但只要你再多加三种实体,这个 `match` 就会变成一个 500 行的怪物**。Casey 今天做的事看起来只是"重构",但它背后是一个比任何算法都重要的思想——**数据和行为的解耦**。

为什么这件事重要?游戏开发里有一个反复出现的痛:**你每加一个新角色,就要改十处代码**。改 update 一处、改 render 一处、改 collision 一处、改 debug overlay 一处……这些"散弹枪改动"(Shotgun Surgery)是典型的反模式——它让你**害怕加新东西**,因为它要触及每一处代码。Casey 今天的工作目标是:**加新实体类型时,只改一个地方**。

具体到 HH 的语境,Casey 接下来要加三种实体:`Snake`(蛇,Day 292)、`Familiar`(随从,Day 293)、`Glove`(手套道具,Day 294)。每种都有自己的 update 逻辑、自己的碰撞反应、自己的渲染需求。如果不先解耦,他每加一种就要回到 100 个 `match` 臂里加分支——这就是为什么今天必须先做"行为解耦"。

**心理锚点**:看完今天,你应该能用一句话回答"如果我要加一种新的实体,需要改哪些代码",答案应该是"只改一个文件里的一两个新函数"。如果还是"要改十几处",那今天没真正学会。

## 1 · Casey 今天做了什么

Casey 在 day 285 之前,每个实体的更新逻辑是写死在 game update 主循环里的 `switch (Entity->Type)`。今天他动手:

1. **引入 "Brain" 概念**——把"实体怎么思考"从"实体是什么"中分离出来。一个桌子没有 brain,一个怪物有 brain。
2. **在 entity 结构里加一个 `Brain` 字段**(实际上是一个枚举或 ID),而不是直接根据 `Type` 分支。
3. **重写 update 循环**——先看实体有没有 brain,如果有,根据 brain 类型 dispatch 到对应函数;没有就直接跳过(纯装饰物)。
4. **不立刻删掉旧的 switch**——他保留了 Type 字段,因为渲染还用得到。今天只解耦**行为**(update),不解耦**视觉**(render)。

这是典型的"分步骤重构":**一次只动一个维度**。如果同时动行为和视觉,出了 bug 你不知道是哪边出问题。Casey 这种克制是工程上的成熟。

## 2 · 心智模型

### 类比:演员、剧本和角色

把游戏里的实体想象成话剧舞台上的**演员**。一个演员能演很多角色——今天演哈姆雷特,明天演罗密欧,后台还能换个服装立刻变麦克白。

旧代码的世界观:**一个演员 = 一个角色**。Casey 在写 `Player` 类型时,把"玩家的行为"焊死在 Player 这个标签上——你不可能让一个桌子突然走起来,因为桌子类型没有 `update_movement` 函数。

新代码的世界观:**演员、剧本、服装分离**。
- **演员**(Entity)是数据容器——位置、速度、朝向、生命值。
- **剧本**(Brain)规定演员怎么演——这一帧往哪走、什么时候攻击、什么时候死。
- **服装**(Visual)规定演员长什么样——是 sprite A 还是 sprite B、什么颜色、什么动画帧。

这样一来,你想让一棵树突然"活过来"追玩家,只要给它挂一个 `Brain::Chase` 就行——不用新建 `TreeMonster` 类型。这就是行为和数据解耦的威力。

### 2.1 数据导向视角

从数据布局看,这个解耦还有第二层收益。考虑一个有 1000 个实体的场景,假设 900 个是静态家具(桌子、树、石头),只有 100 个是"活的"(玩家、怪物、随从)。旧代码每帧要遍历 1000 个实体,每个都进 `match Type`,即使 Type 是 Furniture 也走一遍分支。

新代码下,你只对"有 brain 的"实体做思考更新,静态家具完全跳过更新阶段——**性能自然提升**。这就是数据导向设计(DOD)的一个核心收益:**用数据本身决定走什么路径,而不是用 if/else 检查**。

### 2.2 Rust enum dispatch vs trait dispatch

Rust 里表达"实体有不同的 brain"有两种主流做法:

**做法一:enum + match**

```rust
enum Brain {
    Player,           // 玩家由输入控制
    MonsterChase,     // 怪物追玩家
    SnakeWander,      // 蛇随机游走
    FamiliarFollow,   // 随从跟随玩家
}

struct Entity {
    pos: Vec2,
    brain: Option<Brain>,  // None = 静态物
}

fn update(e: &mut Entity, input: &Input, player_pos: Vec2) {
    match e.brain {
        Some(Brain::Player) => { e.pos += input.dir(); }
        Some(Brain::MonsterChase) => { /* 朝 player_pos 移动 */ }
        Some(Brain::SnakeWander) => { /* 随机 */ }
        Some(Brain::FamiliarFollow) => { /* 跟玩家 */ }
        None => { /* 静态,什么都不做 */ }
    }
}
```

**做法二:trait object (`Box<dyn Brain>`)**

```rust
trait Brain {
    fn think(&mut self, e: &mut Entity, ctx: &Context);
}

struct PlayerBrain;
struct MonsterChaseBrain;

impl Brain for PlayerBrain {
    fn think(&mut self, e: &mut Entity, ctx: &Context) {
        e.pos += ctx.input.dir();
    }
}

struct Entity {
    pos: Vec2,
    brain: Option<Box<dyn Brain>>,
}
```

两者都合法,但取舍不同:

- **enum** 是 cache 友好的(数据连续,match 编译成跳表),编译器能内联,但加新 Brain 要改 enum 定义。
- **trait object** 是开放扩展的(加新 Brain 不动老代码),但每次调用是虚函数(动态分发,无法内联,要 load vtable)。

游戏开发里**几乎都选 enum**。原因:Brain 种类通常不会上几十种(10 种以内),性能远比"开放扩展"重要,而且 enum 让所有 brain 都集中在一个文件,易于审视全局。Casey 在 C 里也是用 enum + switch 模式。

### 2.3 "类型" vs "行为" vs "视觉"三维

旧代码混淆了三个独立维度:

- **Type**:玩家 / 怪物 / 蛇 / 树 / 桌子——决定"是什么"
- **Brain**:移动 / 攻击 / AI / 静止——决定"怎么动"
- **Visual**:精灵 A / 精灵 B / 动画组——决定"长什么样"

今天 Casey 解开 Type 和 Brain,但 Visual 还焊死在 Type 上。这是有意的——**一次只解一个维度**,让重构有可追溯的边界。Day 289 才解 Visual。

举例:旧代码"怪物"既表示"它会追玩家"(Brain),也表示"它画成红色像素块"(Visual)。新代码后,这两个属性可以独立配置——一个戴着怪物皮肤的随从(Familiar),它的 Visual 是怪物,Brain 是 FamiliarFollow。这种组合在旧代码里需要新建类型,新代码里只要组合两个字段。

---

**总结**:今天的目标不是改逻辑,而是改**结构**。把 `match Type` 拆成 `match Brain`,让"怎么思考"和"是什么"解耦。这是开放扩展的第一步。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对"实体行为解耦"有三十年的探索。三个里程碑:

1. **OOP 继承(1990s)**:Quake、Unreal 早期——`class Entity` 派生 `class Player : Entity`、`class Monster : Entity`。问题:继承深度爆炸,`FlyingMonster : Monster`,但 `SwimmingMonster : Monster`,那 `FlyingSwimmingMonster` 怎么办?菱形继承地狱。
2. **组合优于继承(2000s)**:`Entity` 持有 `Component` 数组,`HealthComponent`、`PhysicsComponent`、`RenderComponent`。Unity、Unreal 4 走这条路。
3. **ECS(Entity-Component-System,2010s)**:Bevy、Unity DOTS——彻底把数据(SoA)和系统(函数)分开。`struct Health(Vec<f32>)`,系统遍历这个数组。

Casey 的 "Brain enum" 介于 1 和 2 之间——他在用 C 结构体重现"组合"。这种风格在性能敏感的引擎里非常常见,因为它能 cache 友好。

实际工业代码里加一个新 AI 的流程:

- 写一个 `brain_snake_wander` 函数
- 在 enum 加 `Brain_SnakeWander`
- 在 update dispatch switch 里加一个 case 调用 `brain_snake_wander`
- 不动渲染、不动碰撞、不动 UI——它们靠 Brain 自己决定

这是 Casey 在 day 292 加蛇时的真实流程,加蛇只改了 30 行代码。换做旧架构,他要改十几个 `switch Type`。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核里到处是"行为解耦"。最典型的:**VFS(Virtual File System)**。

Linux 把所有"文件"抽象成四个操作:`read`、`write`、`open`、`close`。具体怎么实现是底层文件系统的事:ext4 走磁盘、nfs 走网络、proc 走内存。`struct file_operations` 就是文件系统的"Brain":

```c
// linux/fs.h(简化)
struct file_operations {
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*open)(struct inode *, struct file *);
    int (*release)(struct inode *, struct file *);
    // ...
};
```

每个文件系统注册自己的 `file_operations`——ext4 一份、nfs 一份、proc 一份。内核不知道也不关心"这个 inode 背后是磁盘还是网络",只调函数指针。

这就是 Casey 今天做的事的**大型版本**:把"具体怎么做"留给数据(函数指针表),把"什么时候做"留在调用方。Linux 把这件事做到了极致——你甚至可以给一个进程的 stdin 接一个内存文件(tmpfs),或者一个 socket。

更精确的对应:**`driver model`**。每个 PCI 设备驱动注册一个 `pci_driver`,里面有 `probe`、`remove`、`suspend`、`resume`。内核遍历设备时,根据设备 ID 找到对应的 driver,调它的 `probe`。**设备是数据,driver 是行为**。

### 3.3 · 🦀 Rust 生态视角

Rust 表达"行为解耦"的工具:

| 工具 | 适用场景 | 性能 |
|---|---|---|
| `enum + match` | 闭集(枚举值有限) | 最快(编译成跳表,可内联) |
| `trait object (Box<dyn T>)` | 开集(运行时可加) | 慢(虚函数,不可内联) |
| `enum_dispatch` crate | enum 但要 trait 接口 | 接近 enum |
| 函数指针 `fn(&mut Entity)` | 行为就是函数 | 中等(无法内联) |

游戏里加 brain 的标准 Rust 模式:

```rust
#[derive(Copy, Clone)]
enum Brain {
    Player,
    MonsterChase { target_id: u32 },  // 带数据
    SnakeWander { wander_dir: Vec2, timer: f32 },
    FamiliarFollow { owner_id: u32, lerp: f32 },
}

struct Entity {
    id: u32,
    pos: Vec2,
    brain: Option<Brain>,
}

fn update_entity(e: &mut Entity, world: &World, input: &Input, dt: f32) {
    let Some(brain) = e.brain else { return; };  // 静态物跳过
    match brain {
        Brain::Player => {
            e.pos += input.dir() * 60.0 * dt;
        }
        Brain::MonsterChase { target_id } => {
            if let Some(target) = world.get(target_id) {
                let dir = (target.pos - e.pos).normalize();
                e.pos += dir * 30.0 * dt;
            }
        }
        Brain::SnakeWander { ref mut wander_dir, ref mut timer } => {
            *timer -= dt;
            if *timer <= 0.0 {
                *timer = 1.5;
                *wander_dir = Vec2::new(rand::random(), rand::random()).normalize();
            }
            e.pos += *wander_dir * 20.0 * dt;
        }
        Brain::FamiliarFollow { owner_id, ref mut lerp } => {
            if let Some(owner) = world.get(owner_id) {
                *lerp = (*lerp + dt * 4.0).min(1.0);
                e.pos = e.pos.lerp(owner.pos - Vec2::new(0.0, 16.0), *lerp * dt * 4.0);
            }
        }
    }
}
```

**关键 Rust 特性**:

- `Option<Brain>` 替代 "null"——`None` 表示无 brain(静态物),编译器强制你处理 `None` 分支(`let Some(...) else { return; }` 是 Rust 1.65+ 的 let-else 语法)。
- `ref mut` 在 `match` 臂里"借用可变引用"——让 match 既匹配又修改 payload 数据(如 `SnakeWander` 的 timer)。
- enum 的 payload 直接带状态(`MonsterChase { target_id }`)——比"在 entity 上加 target_id 字段"更精确,因为只有 MonsterChase 需要 target。
- `Box<dyn Brain>` 是另一种选择,但 Casey 风格不要——他不要堆分配、不要虚函数、不要 vtable。

## 4 · 认知地图

### 4.1 上级

- **关注点分离(Separation of Concerns)** — 把不同关注点放到不同模块
- **数据导向设计(DOD)** — 按数据布局组织代码
- **组合优于继承** — 用组合而非继承实现复用
- **开放-封闭原则(OCP)** — 对扩展开放,对修改封闭

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 巨型 switch on Type | Type 决定一切 | 简单原型 | day285 之前 |
| enum Brain + 函数 | Brain 独立于 Type | 中等复杂度 | ✅ Casey 选了 |
| Trait object (dyn) | 运行时多态 | 不关心性能 | 不用 |
| ECS(Bevy 风格) | 数据 SoA + 系统 | 大规模实体 | day300+ 才预告 |

### 4.3 下级

- **enum 定义** — Brain 的所有可能值
- **match dispatch** — 根据 Brain 分派到处理函数
- **payload 携带状态** — 每个 Brain variant 自带必要数据
- **None 表示无 brain** — 用 Option 而非"标志位"

## 5 · 对照与变奏

### 同一问题在不同语言/语境下的解法

**问题**:"一个对象有多种行为,怎么组织代码?"

| 语境 | 主流方案 | 代价 |
|---|---|---|
| C(Casey HH) | struct + function pointer | 手动管理,内存泄漏风险 |
| Rust(enum) | match dispatch | 加 variant 改 enum |
| Rust(trait) | Box<dyn Trait> | 虚函数,不可内联 |
| C++ | virtual function / template | vtable 或编译膨胀 |
| Java/Go | interface | GC + 虚函数 |
| Python | duck typing | 运行时错误 |

**关键洞察**:**所有"多态"本质都是"按某种标签分派到不同代码"**。enum 是编译期分派,虚函数是运行时分派。游戏选前者,web 后端选后者——因为游戏要 60 FPS,web 要灵活部署。

### 历史演化

- **1970s**:C 用函数指针(`struct stat` 里的 `callback`)
- **1990s**:C++/Java 用虚函数,GoF《设计模式》推广 Strategy / State
- **2000s**:游戏引擎(CryEngine、Unreal)转向组合优于继承
- **2010s**:ECS 兴起(Artemis、Bevy、Unity DOTS)
- **2020s**:数据导向设计成为共识,Casey 早在 2014 就走这条路

Casey 是数据导向的早期实践者——他不是发明者,但他把"工业级 DOD"用教学方式呈现给社区。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 今天保留了 `Type` 字段没动,只引入 `Brain`。为什么不一步到位把 `Type` 全删掉换成 `Brain`?

**参考解答**:三方面原因:
1. **可追溯的边界**:如果同时动 Type 和 Brain,出 bug 你不知道是哪边出问题。Casey 一集只动一个维度,第二天再动另一个。
2. **Type 仍承载 Visual 信息**:今天的主题是"行为解耦",Visual 解耦在 day289 做。删掉 Type 会让 Visual 也无处挂靠。
3. **可分步验证**:留 Type 让他今天能验证"Brain 解耦没破坏现有行为"——因为渲染仍按 Type 工作。删了 Type,渲染就坏了,他没法独立验证 Brain 改动是否正确。

这是工程上"小步快跑"的纪律:**每一改可单独编译、可单独验证**。

### Lv2 · 动手实践

**题**:在 Rust 里写一个最小化的"实体 + brain"系统,有三种 brain:`Static`(不动)、`LinearMove { dir: Vec2 }`(匀速移动)、`Bounce`(撞墙反弹)。写一个 `update_all` 函数遍历所有实体并按 brain 更新。

完成标准:`cargo run` 后,三个实体的位置变化符合预期——静态的不动,LinearMove 的朝 dir 移动,Bounce 的撞屏幕边界后反向。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn mul(self, k: f32) -> Self { Self { x: self.x * k, y: self.y * k } }
}

// Brain 枚举:Static 不带数据,LinearMove 带 dir,Bounce 带 dir + speed
#[derive(Copy, Clone)]
enum Brain {
    Static,
    LinearMove { dir: Vec2, speed: f32 },
    Bounce { dir: Vec2, speed: f32 },  // dir 必须是单位向量
}

struct Entity {
    pos: Vec2,
    brain: Brain,
}

// 屏幕边界
const WIDTH: f32 = 800.0;
const HEIGHT: f32 = 600.0;

fn update_entity(e: &mut Entity, dt: f32) {
    match e.brain {
        Brain::Static => { /* 啥也不做 */ }
        Brain::LinearMove { dir, speed } => {
            e.pos.x += dir.x * speed * dt;
            e.pos.y += dir.y * speed * dt;
        }
        Brain::Bounce { ref mut dir, speed } => {
            e.pos.x += dir.x * speed * dt;
            e.pos.y += dir.y * speed * dt;
            // 撞墙反转
            if e.pos.x < 0.0 || e.pos.x > WIDTH { dir.x = -dir.x; }
            if e.pos.y < 0.0 || e.pos.y > HEIGHT { dir.y = -dir.y; }
            // 钳制
            e.pos.x = e.pos.x.clamp(0.0, WIDTH);
            e.pos.y = e.pos.y.clamp(0.0, HEIGHT);
        }
    }
}

fn update_all(entities: &mut [Entity], dt: f32) {
    for e in entities.iter_mut() {
        update_entity(e, dt);
    }
}

fn main() {
    let mut es = vec![
        Entity { pos: Vec2::new(100.0, 100.0), brain: Brain::Static },
        Entity { pos: Vec2::new(200.0, 200.0),
                 brain: Brain::LinearMove { dir: Vec2::new(1.0, 0.0), speed: 50.0 } },
        Entity { pos: Vec2::new(400.0, 300.0),
                 brain: Brain::Bounce { dir: Vec2::new(1.0, 1.0), speed: 80.0 } },
    ];
    let dt = 0.5;  // 半秒,便于观察
    update_all(&mut es, dt);
    println!("{:?}", es[0].pos);  // (100, 100) 不动
    println!("{:?}", es[1].pos);  // (225, 200) 往右移 25
    println!("{:?}", es[2].pos);  // 朝右下移 40
}
```

**每行解释**:
- `enum Brain` 用 struct-variant 携带数据——比"在 Entity 上加一堆字段"更精确,因为只有特定 brain 才需要特定数据。
- `ref mut dir` 在 match 臂里借用可变引用,允许在 match 内修改 dir(Bounce 反弹时改方向)。
- `clamp` 把值限制在范围内——Rust 的 `f32::clamp` 在 1.50 稳定。
- `iter_mut()` 借用整个数组的可变视图,无需索引检查——比 `for i in 0..len` 更安全。

### Lv3 · 迁移设计

**题**:你被要求做一个**粒子系统**——每个粒子有自己的生命周期、颜色、运动方式。有的粒子匀速直线飞、有的受重力影响、有的螺旋运动、有的脉冲(透明度变化)。如何用今天学的"行为解耦"思想设计?**不要**写一个 `match ParticleType` 巨型函数。

**提示**:
- 把"运动方式"做成一个 `enum Motion { Linear { vel }, Gravity { vel, mass }, Spiral { center, radius, angular } }`
- 把"外观变化"做成另一个 `enum Appearance { Static, Fade { rate }, Pulse { freq } }`
- 一个 `Particle` 持有 `motion: Motion` 和 `appearance: Appearance`
- update 函数先 match motion 更新位置,再 match appearance 更新颜色

**额外挑战**:有的粒子需要"碰撞后分裂"——这是第三个维度,叫 `OnDeath`,可以是 `Disappear` 或 `Split { count }`。怎么集成进去?

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

把 §7 Lv2 扩展为完整可跑程序,加上"运行时切换 Brain"功能(展示解耦的灵活性):

```rust
// src/main.rs
// 用 brain enum 给一个实体动态切换行为,验证解耦的价值

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
}

#[derive(Copy, Clone)]
enum Brain {
    Static,
    LinearMove { dx: f32, dy: f32, speed: f32 },
    Bounce { dx: f32, dy: f32, speed: f32 },
}

struct Entity {
    name: &'static str,
    pos: Vec2,
    brain: Brain,
}

impl Entity {
    fn new(name: &'static str, pos: Vec2, brain: Brain) -> Self {
        Self { name, pos, brain }
    }

    // 运行时切换 brain——旧代码下需要改 Type,现在只改 brain 字段
    fn switch_brain(&mut self, brain: Brain) {
        self.brain = brain;
        println!("[{}] brain switched", self.name);
    }

    fn update(&mut self, dt: f32, width: f32, height: f32) {
        match self.brain {
            Brain::Static => {}
            Brain::LinearMove { dx, dy, speed } => {
                self.pos.x += dx * speed * dt;
                self.pos.y += dy * speed * dt;
            }
            Brain::Bounce { ref mut dx, ref mut dy, speed } => {
                self.pos.x += *dx * speed * dt;
                self.pos.y += *dy * speed * dt;
                if self.pos.x < 0.0 || self.pos.x > width { *dx = -*dx; }
                if self.pos.y < 0.0 || self.pos.y > height { *dy = -*dy; }
                self.pos.x = self.pos.x.clamp(0.0, width);
                self.pos.y = self.pos.y.clamp(0.0, height);
            }
        }
    }
}

fn main() {
    let mut e = Entity::new("wizard", Vec2::new(400.0, 300.0),
        Brain::LinearMove { dx: 1.0, dy: 0.0, speed: 100.0 });

    const W: f32 = 800.0;
    const H: f32 = 600.0;
    let dt = 0.1;

    // 10 帧直线
    for i in 0..10 {
        e.update(dt, W, H);
        println!("t={:.1}: pos=({:.1},{:.1})", i as f32 * dt, e.pos.x, e.pos.y);
    }

    // 切换到 Bounce
    e.switch_brain(Brain::Bounce { dx: -1.0, dy: 1.0, speed: 200.0 });

    // 10 帧 bounce
    for i in 0..10 {
        e.update(dt, W, H);
        println!("t={:.1}: pos=({:.1},{:.1})", (10 + i) as f32 * dt, e.pos.x, e.pos.y);
    }
}
```

**关键点**:`switch_brain` 一行就能改变实体行为——这就是"组合优于继承"的直观验证。OOP 继承下你不可能在运行时把一个 `Player` 变成 `Monster`,但 Brain 解耦后,一行赋值就行。
