
# Day 289 · 视觉与实体类型解耦

> Day 286 解耦了 Brain(行为)。今天 Casey 解耦第二个维度:**Visual(视觉)**——一个实体画成什么样,不再焊死在它"是什么"。这让你能给任何实体戴任何"皮肤",组合自由度爆炸式增长。

## 0 · 为什么要有这一天

旧代码里,渲染是这样的:`match entity.Type { PLAYER => draw_sprite(PLAYER_SPRITE), MONSTER => draw_sprite(MONSTER_SPRITE), ... }`。每加一种 Type 就要找一张新 sprite;反过来,你想让一个怪物用"中毒"皮肤的 sprite,就要新建一个 `PoisonedMonster` Type——这是反直觉的。

为什么这是个问题?考虑以下需求:

- 玩家吃了"无敌药水",所有 sprite 闪烁(不同 visual,同一个 brain)
- 怪物有 4 个变种(红、蓝、绿、紫),行为相同但视觉不同
- 道具被捡起前是地面 sprite,被捡起后是 UI 图标
- 角色死亡后变成"鬼魂" sprite,但仍受玩家控制

旧代码下,每个需求都要新建 Type 或加 flag。加 flag 多了,`match Type` 就变成 `match (Type, Status)`——组合爆炸。

解耦的思路:**Visual 是 entity 的属性,不是 entity 的身份**。一个实体有 `pos`、`brain`、`visual`——三件独立的事。`visual` 决定画什么 sprite、什么颜色、什么动画帧,与 `brain` 完全独立。

这个解耦有什么实际收益?

1. **加新皮肤零代码改动**——你只要在数据里加 sprite ID,不用改渲染代码
2. **运行时换装**——一个角色穿不同盔甲,只改 `visual` 字段
3. **debug overlay 友好**——debug 时让所有实体都用相同的"灰色方块" sprite,专注逻辑
4. **资产管线简化**——美术加新 sprite,程序不用改代码

心理锚点:看完今天,你应该能用一句话回答"我想让玩家看起来像怪物,行为还是玩家",答案是"把 player.visual 改成 MONSTER_SPRITE,不动 brain"。如果答案还是"要新建一个 PlayerMonster Type",今天没真正解耦。

## 1 · Casey 今天做了什么

Casey 今天的几个动作:

1. **引入 `Visual` 概念**——一个枚举(或 ID),规定"画成什么样"。
2. **把 entity 的 Type 字段拆分**——Type 不再决定视觉,改由独立的 Visual 字段决定。
3. **重写 render 函数**——根据 Visual 决定 sprite,不再根据 Type。
4. **保留 Type**(暂时)——Type 仍承载 Brain 默认值,作为便捷构造器。
5. **修复所有原有的渲染调用**——之前写死的 `match Type` 都改成 `match Visual`。

注意:今天**只解耦视觉**,不动其他维度。Brain 已经在 Day 286-288 解耦。这是"一维度一维度地解耦"的纪律。

## 2 · 心智模型

### 类比:演员、剧本、服装(续)

回到 Day 286 的类比:演员(Entity)、剧本(Brain)、服装(Visual)。Day 286 把"剧本"独立出来,今天把"服装"独立出来。

旧代码下,你不可能让张三穿李四的服装——因为"服装"焊死在"演员"身份上,张三永远穿张三的服装。今天解耦后:**演员可以临时换任何服装**。这就是为什么解耦威力巨大。

一个具体的游戏场景:**Boss 战**。Boss 在三个阶段有三种形态——50% 血量前是大体型,50%-25% 是中等体型,25% 以下是小型高速。三个阶段的 brain 也不同(前期追击,中期召唤小怪,后期狂暴)。旧代码下,这是三个 Type。新代码下,这是**一个 entity,运行时切换 visual 和 brain**。代码量减半,逻辑清晰。

### 2.1 三维独立的好处

旧代码:
```rust
enum Type { Player, Monster, Snake, Furniture }

struct Entity {
    pos: Vec2,
    typ: Type,  // 决定一切
}

fn update(e: &mut Entity) {
    match e.typ {
        Type::Player => { /* 玩家逻辑 */ }
        Type::Monster => { /* 怪物逻辑 */ }
        // ...
    }
}

fn render(e: &Entity) {
    match e.typ {
        Type::Player => draw_sprite(PLAYER_SPRITE, e.pos),
        Type::Monster => draw_sprite(MONSTER_SPRITE, e.pos),
        // ...
    }
}
```

新代码:
```rust
enum Brain { Player, MonsterChase, SnakeWander, /* ... */ }
enum Visual { PlayerSprite, MonsterSprite, SnakeSprite, FurnitureSprite, /* ... */ }

struct Entity {
    pos: Vec2,
    brain: Option<Brain>,
    visual: Visual,
}

fn update(e: &mut Entity) {
    match e.brain {
        Some(Brain::Player) => { /* ... */ }
        Some(Brain::MonsterChase) => { /* ... */ }
        // ...
        None => {}
    }
}

fn render(e: &Entity) {
    match e.visual {
        Visual::PlayerSprite => draw_sprite(PLAYER_SPRITE, e.pos),
        Visual::MonsterSprite => draw_sprite(MONSTER_SPRITE, e.pos),
        // ...
    }
}
```

独立后,任意组合:
```rust
// 玩家穿怪物皮(visual = monster,brain = player)
let e = Entity {
    pos: Vec2::new(0.0, 0.0),
    brain: Some(Brain::Player),
    visual: Visual::MonsterSprite,
};
```

这种组合在旧代码下不可能,新代码下一行赋值搞定。

### 2.2 Visual 不只是 sprite

Visual 听起来就是"用哪张图",但实际上它包含更多:

```rust
enum Visual {
    Sprite { id: SpriteId, color: u32 },       // 单张 sprite + 颜色调制
    Animated { id: AnimId, frame: f32 },        // 动画(多帧 sprite 序列)
    Particle { emitter: EmitterId },            // 粒子(如火焰、烟雾)
    DebugRect { color: u32, size: Vec2 },       // debug 矩形(开发用)
    Invisible,                                   // 不画(用于"隐形"敌人)
}
```

每种 visual 有自己的渲染逻辑。Animated 要更新 frame;Particle 要更新 emitter;Sprite 静态。Visual 自己也带状态(frame、emitter 等),这是它的"小 brain"——但这个 brain 只关心"怎么画",不关心"怎么动"。

### 2.3 Type 的角色:便捷构造器

解耦后 Type 还有没有用?**有,但只是便捷构造器**:

```rust
fn make_player(pos: Vec2) -> Entity {
    Entity {
        pos,
        brain: Some(Brain::Player),
        visual: Visual::Sprite { id: PLAYER_SPRITE, color: 0xFFFFFFFF },
    }
}

fn make_monster(pos: Vec2) -> Entity {
    Entity {
        pos,
        brain: Some(Brain::MonsterChase { target_id: 0 }),
        visual: Visual::Sprite { id: MONSTER_SPRITE, color: 0xFFFFFFFF },
    }
}
```

构造函数告诉你"一个典型玩家长什么样、怎么思考"。但 entity 一旦构造,你可以任意改 visual 和 brain,不受 Type 约束。

实际项目里有时连 Type 都没有,直接在 spawn 函数里写:
```rust
let e = Entity { pos, brain: Some(Brain::Player), visual: Visual::PlayerSprite };
```

Type 是为了 ergonomics(易用性)保留的,不是为约束。

### 2.4 解耦的另一面:组合爆炸

解耦也有代价:**组合可能性爆炸**。如果 Brain 有 5 种、Visual 有 8 种,理论上有 5×8=40 种组合。但很多组合不合理——"玩家 brain 配桌子 visual"在游戏里没意义。

怎么管理这个?两个办法:

1. **构造函数限制**:在 `make_player` 等函数里只产出"合理"的组合。运行时虽然可改,但你不主动改。
2. **数据驱动**:从 JSON/CSV 读"合法组合"表,美术填表,程序读表。

Casey 在 HH 教学阶段用第一种——手动构造函数,够用。商业项目会演化到数据驱动(Phase 7 的资产管线)。

---

**总结**:今天解耦视觉,和昨天解耦行为一样,**让 Visual 字段独立决定"画什么"**。结果是 entity 成为三个独立字段(pos、brain、visual)的组合,可表达任意游戏对象。这是从"写死"到"数据驱动"的关键一步。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对"视觉与身份解耦"有专门术语:**皮肤系统(skin system)**。每个角色有一组 skin,玩家可以切换。英雄联盟、CS:GO、原神都重度依赖。

但 skin 系统只是 Visual 解耦的最简单形式。更复杂的:

- **动画状态机**——Visual 里包含"当前在哪个动画、第几帧",由状态机驱动(idle、walk、attack 三个动画,根据 vel 和 input 切换)
- **morph target**——Visual 里混合多个网格(角色胖瘦、面部表情)
- **material override**——Visual 里改 material 参数(光泽度、发光)

工业级 entity 的 visual 字段可能比 brain 还复杂——因为玩家看到的"东西"比玩家感受到的"行为"信息量大得多。Unreal Engine 的 `USkeletalMeshComponent`、Unity 的 `SkinnedMeshRenderer` 都是 visual 的工业化形态。

Casey 在 HH 用最简单的 sprite enum,但**精神与工业级一致**——visual 是数据,不是身份。

### 3.2 · 🎨 图形学视角

图形学里"Visual"叫 **appearance**(外观)。Appearance 包括:

- **几何**(Geometry):mesh、shape——决定"形状"
- **材质**(Material):颜色、纹理、BRDF——决定"光如何反射"
- **光照响应**(Lighting response):受不受光、自发光、阴影投射——决定"和光的交互"

游戏 entity 的 visual 字段对应到 appearance 的几何 + 材质子集。光照响应通常由 material 决定,不在 entity 上单独配置。

3D 渲染管线里,visual 解耦的好处更明显:**同一个 mesh 配不同 material,可以是 100 种不同角色**。比如 Skyrim 的 NPC 系统,几十种 NPC 用同一个 "human_male.nif" mesh,配不同 material 和 texture,变成不同角色。

### 3.3 · 🐧 Linux 系统编程视角

Linux 里类似的概念:**文件 vs inode**。文件名是"visual"(用户看到的名字),inode 是"实体"(实际数据)。一个 inode 可以有多个文件名(hard link),一个文件名可以指向不同 inode(改名/移动)。

```bash
# 同一个 inode,两个名字
echo "hello" > a.txt
ln a.txt b.txt  # hard link, 同 inode
ls -i a.txt b.txt
# 输出:1234567 a.txt  1234567 b.txt  (inode 号相同)

# 同一个名字,不同时间指向不同 inode
mv a.txt c.txt   # 改名,实际上换 inode 引用
```

`a.txt`、`b.txt` 是 visual(用户看到的名字),inode 是 entity(实际数据)。它们解耦——你给文件起什么名不影响内容,改内容不影响名字。

另一个例子:**进程 vs 可执行文件**。一个进程(`/proc/PID/exe`)指向一个可执行文件,但**同一可执行文件可以同时跑多个进程**——同一 visual(可执行文件名),不同 entity(进程)。也可以换 visual:`execve()` 让进程"现场换装",变成另一个程序,但 PID 不变。

### 3.4 · 🦀 Rust 生态视角

Rust 表达"visual 独立"和 brain 类似,用 enum:

```rust
#[derive(Copy, Clone)]
pub enum Visual {
    Sprite(SpriteId),
    Animated { anim: AnimId, frame: f32, looping: bool },
    DebugRect { color: u32, w: f32, h: f32 },
    Invisible,
}

pub struct Entity {
    pub pos: Vec2,
    pub brain: Option<Brain>,
    pub visual: Visual,
}
```

但 Visual 比脑更可能扩展——美术不断加新 sprite。如果 enum 加新 variant 要改所有 match,你会很烦。两个 Rust 解决方案:

**方案 A:`#[non_exhaustive]` 标记**

```rust
#[non_exhaustive]
#[derive(Copy, Clone)]
pub enum Visual {
    Sprite(SpriteId),
    Animated { anim: AnimId, frame: f32, looping: bool },
    // 未来加新 variant 不破坏下游代码
}
```

下游代码 `match visual { ... }` 编译器强制加 `_ => ...` 通配,允许 enum 后续扩展。

**方案 B:tag + data 分离**

```rust
struct Visual {
    sprite_id: SpriteId,  // 默认值或 None
    color: Color,
    scale: f32,
    rotation: f32,
    // ...
}
```

把 visual 做成 struct 而非 enum,所有字段都有默认值。加新字段是向后兼容的。这种适合"visual 是连续可配置"的场景。

Casey 风格用 enum——简单、有穷、强类型。等 sprite 多了再说。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 今天解耦 visual 后,**保留 Type 字段**(虽然它不再决定视觉)。为什么不直接删 Type?

**参考解答**:
1. **便捷构造器**:Type 作为"实体模板"——`make_player()` 内部用 `Type::Player` 查表得到默认 visual/brain。删了 Type 就要写硬编码构造器,反而啰嗦。
2. **debug 用**:debug overlay 显示 entity 信息,`Type` 给出"这个 entity 本质是什么",便于人理解。
3. **存档用**:save/load 时存 Type 比存 (brain, visual) 元组更紧凑——存 Type 然后从表查默认 brain/visual。
4. **性能**:Type 是简单 enum,match 它编译成跳表。某些代码路径仍按 Type 分支(如 collision),因为 Type 暗示了 collider 形状。

主要原因是 1 和 4——便捷 + 性能。Type 是"主类别",visual 和 brain 是"附加修饰"。

### Lv2 · 动手实践

**题**:实现一个解耦的 entity 系统,有 3 种 visual(`Sprite(id)`, `DebugRect(color, size)`, `Invisible`)和 2 种 brain(`Player`, `MonsterChase`)。验证组合:`Player + DebugRect`(玩家被画成 debug 矩形)能正常工作。

完成标准:写一个 main,创建 4 个实体(Player+Sprite, Player+DebugRect, MonsterChase+Sprite, MonsterChase+Invisible),update 一步,render 一步,打印每个实体的渲染调用。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
    fn length(self) -> f32 { (self.x * self.x + self.y * self.y).sqrt() }
    fn normalize(self) -> Self {
        let l = self.length();
        if l > 1e-6 { self.mul(1.0 / l) } else { Self::new(0.0, 0.0) }
    }
}

#[derive(Copy, Clone, Debug)]
enum Brain { Player, MonsterChase { target_id: u32 } }

#[derive(Copy, Clone, Debug)]
enum Visual {
    Sprite(u32),
    DebugRect { color: u32, w: f32, h: f32 },
    Invisible,
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    id: u32,
    pos: Vec2,
    brain: Option<Brain>,
    visual: Visual,
}

struct World {
    entities: Vec<Entity>,
}

impl World {
    fn find_pos(&self, id: u32) -> Option<Vec2> {
        self.entities.iter().find(|e| e.id == id).map(|e| e.pos)
    }
}

fn update(e: &mut Entity, world: &World, input_dir: Vec2, dt: f32) {
    let Some(brain) = e.brain else { return; };
    match brain {
        Brain::Player => {
            e.pos.x += input_dir.x * 80.0 * dt;
            e.pos.y += input_dir.y * 80.0 * dt;
        }
        Brain::MonsterChase { target_id } => {
            if let Some(target) = world.find_pos(target_id) {
                let d = target.sub(e.pos);
                if d.length() > 1e-3 {
                    let n = d.normalize();
                    e.pos.x += n.x * 40.0 * dt;
                    e.pos.y += n.y * 40.0 * dt;
                }
            }
        }
    }
}

fn render(e: &Entity) -> String {
    match e.visual {
        Visual::Sprite(id) => format!("  draw_sprite(id={}, pos=({},{}))", id, e.pos.x, e.pos.y),
        Visual::DebugRect { color, w, h } => {
            format!("  draw_rect(color={:#x}, w={}, h={}, pos=({},{}))",
                color, w, h, e.pos.x, e.pos.y)
        }
        Visual::Invisible => "  (invisible, skip render)".to_string(),
    }
}

fn main() {
    let mut w = World {
        entities: vec![
            Entity { id: 0, pos: Vec2::new(0.0, 0.0), brain: Some(Brain::Player),
                     visual: Visual::Sprite(1) },
            // 玩家被画成 debug 矩形——visual 和 brain 独立组合
            Entity { id: 1, pos: Vec2::new(50.0, 0.0), brain: Some(Brain::Player),
                     visual: Visual::DebugRect { color: 0xFF0000FF, w: 32.0, h: 32.0 } },
            Entity { id: 2, pos: Vec2::new(200.0, 0.0),
                     brain: Some(Brain::MonsterChase { target_id: 0 }),
                     visual: Visual::Sprite(2) },
            // 怪物 brain,但不渲染(invisible)
            Entity { id: 3, pos: Vec2::new(300.0, 0.0),
                     brain: Some(Brain::MonsterChase { target_id: 0 }),
                     visual: Visual::Invisible },
        ],
    };

    let dt = 0.1;
    let input_dir = Vec2::new(1.0, 0.0);

    // 快照避免借用冲突
    let snapshot: Vec<(usize, Entity)> = w.entities.iter().enumerate()
        .map(|(i, e)| (i, *e)).collect();
    for (i, _) in snapshot.iter() {
        let e = &mut w.entities[*i];
        update(e, &w, input_dir, dt);
    }

    println!("Render calls:");
    for e in &w.entities {
        println!("{}", render(e));
    }
}
```

**每行解释**:
- `Visual::Invisible` —— 一个"不画"的 variant,体现了 visual 独立控制——你可以让实体"消失"但行为不变。
- `Entity { id: 1, ..., brain: Player, visual: DebugRect {...} }` —— 演示独立组合:玩家行为(WSAD 移动)+ 矩形视觉(不画 sprite)。
- 快照 snapshot 复制 entity 后,`update(&mut w.entities[i], &w, ...)` 仍有借用冲突——因为 `&w` 同时被借用。修复办法见下文。

借用冲突修复(更优):把 world 的查询提前到 update 外面:

```rust
let positions: Vec<Vec2> = w.entities.iter().map(|e| e.pos).collect();
for (i, e) in w.entities.iter_mut().enumerate() {
    let input_dir = input_dir;
    let target = match e.brain {
        Some(Brain::MonsterChase { target_id }) => positions.get(target_id as usize).copied(),
        _ => None,
    };
    update_with_target(e, target, input_dir, dt);
}
```

### Rust 完整可跑示例

§7 Lv2 的代码完整可跑,这里补充 visual 解耦的另一种 Rust 模式——**用 trait 而非 enum**:

```rust
// 替代方案:visual 用 trait object
// 这种适合 visual 种类运行时动态注册

trait Visual: std::fmt::Debug {
    fn render(&self, pos: Vec2) -> String;
}

#[derive(Debug)]
struct SpriteVisual { id: u32 }
impl Visual for SpriteVisual {
    fn render(&self, pos: Vec2) -> String {
        format!("draw_sprite(id={}, pos=({},{})", self.id, pos.x, pos.y)
    }
}

#[derive(Debug)]
struct DebugRectVisual { color: u32, w: f32, h: f32 }
impl Visual for DebugRectVisual {
    fn render(&self, pos: Vec2) -> String {
        format!("draw_rect(color={:#x}, pos=({},{})", self.color, pos.x, pos.y)
    }
}

#[derive(Debug)]
struct InvisibleVisual;
impl Visual for InvisibleVisual {
    fn render(&self, _pos: Vec2) -> String { "(invisible)".to_string() }
}

struct Entity {
    id: u32,
    pos: Vec2,
    visual: Box<dyn Visual>,  // trait object
}

fn main() {
    let e = Entity {
        id: 0,
        pos: Vec2::new(10.0, 20.0),
        visual: Box::new(SpriteVisual { id: 1 }),
    };
    println!("{}", e.visual.render(e.pos));

    // 运行时换 visual 类型
    let mut e2 = Entity {
        id: 1,
        pos: Vec2::new(30.0, 40.0),
        visual: Box::new(DebugRectVisual { color: 0xFF0000FF, w: 32.0, h: 32.0 }),
    };
    println!("{}", e2.visual.render(e2.pos));

    // 换装
    e2.visual = Box::new(InvisibleVisual);
    println!("{}", e2.visual.render(e2.pos));
}
```

**何时用 trait 而非 enum?**

- Visual 种类运行时动态注册(插件系统)
- Visual 在不同 crate 定义(模块化)
- Visual 行为复杂(每个 variant 几十行,放 enum 内 match 太长)

**何时用 enum?**

- Visual 种类固定且少量(<10)
- 性能敏感(避免堆分配 + 虚函数)
- 想要穷尽性检查(加 variant 编译报错提醒)

Casey 选 enum,HH 用不到 trait 的灵活性。
