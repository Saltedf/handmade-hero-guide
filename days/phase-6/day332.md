
# Day 332 · 为调试覆盖层禁用排序

> 游戏的 debug overlay(FPS、坐标、hitbox 可视化)每帧画几百条线 + 几百个文字。这些 UI 元素走"画家算法 + SortKey" 排序是浪费——它们就是想按 push 顺序画。今天 Casey 给 debug overlay 加一个"立即模式"(immediate mode)路径,跳过排序。

## 0 · 为什么要有这一天

到目前为止你的渲染器统一走 SortKey 排序——所有 entity、所有 UI、所有 debug overlay 都 push 到同一个 entries Vec,sort,render。

但 debug overlay 有特殊性:

1. **顺序敏感**:你 push "FPS: 60" 然后 push "Pos: (100, 200)",期望 FPS 显示在上面。如果走 SortKey 排序,顺序可能乱。
2. **数量大**:debug 模式下每帧画几百条 hitbox 线 + 几百个文字标签,sort 占可观时间。
3. **生命周期短**:每帧重新 push,不需要 SortKey 的"跨帧稳定"性质。

业界的解决方案是 **immediate-mode UI**(立即模式 UI)——UI 元素每帧画时立即 push 到一个"立即渲染"队列,不走 SortKey,按 push 顺序直接画。

```
游戏 entity 渲染:                Debug overlay 渲染:
───────────────────              ───────────────────
push to entries vec              push to immediate vec
sort by SortKey                  (不排序)
render                           render(在 entity 之后)
```

这种"双轨制"让 debug UI 简单高效,不影响游戏 entity 的排序语义。主流引擎都有类似机制:

- Unity:`OnGUI`(immediate mode,但已过时)+ `IMGUI`(debug overlay)
- Casey HH:今天的 immediate overlay
- Dear ImGui:Rust / C++ 通用的 immediate UI 库

心理锚点:今天之后你的 debug overlay 不受 SortKey 干扰,按你 push 的顺序精确显示。这是日常 debug 的实用工具。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_debug.cpp` 和 `handmade_render.cpp`,加 immediate-mode overlay 路径。

具体动作:

1. 给 `render_group` 加 `immediate_entries: Vec<RenderEntry>` 字段(独立于普通 entries)
2. 加 `push_immediate_bitmap` / `push_immediate_text` API,直接 push 到 immediate_entries(不传 SortKey)
3. 渲染时:先排序 + 画普通 entries,然后按 push 顺序画 immediate entries
4. debug overlay 的所有 push 都改成 immediate API

```c
void PushImmediateBitmap(render_group *group, bitmap_id id, v2 pos) {
    render_entry entry = {0};
    entry.bitmap = id;
    entry.pos = pos;
    // 不设置 sort_key,用 push 顺序
    array_push(group->immediate_entries, entry);
}

void RenderGroupToOutput(render_group *group, offscreen_buffer *buffer) {
    // 1. 排序 + 画普通 entries
    sort_entries(group);
    for (int i = 0; i < group->entry_count; i++) {
        draw_entry(buffer, &group->entries[i]);
    }
    
    // 2. 按 push 顺序画 immediate(在普通之后,所以 UI 在最上层)
    for (int i = 0; i < group->immediate_count; i++) {
        draw_entry(buffer, &group->immediate_entries[i]);
    }
}
```

Casey 在视频里讨论了几个细节:

1. **immediate 在普通之后**:debug overlay 应该在最上层,所以画在普通 entries 之后
2. **每帧清空 immediate_entries**:immediate 是"本帧临时",不持久化。每帧开始清空,重新 push
3. **immediate 的 alpha**:仍然支持 alpha blending,只是不排序

Casey 还讨论了一个微妙问题:**immediate 之间是否排序?** 答案是不排——push 顺序就是绘制顺序。这要求程序员"按视觉顺序 push"——先 push 背景,再 push 前景。这种"按调用顺序画"的简单性是 immediate-mode UI 的核心吸引力。

## 2 · 心智模型

### 类比:白板上的便利贴

把渲染想象成白板上贴便利贴。

- **排序模式**(普通 entity):每张便利贴有"重要度"标签,贴完后按标签从低到高重新排列
- **立即模式**(debug overlay):便利贴按你贴的顺序留在白板上,不重排

debug UI 用立即模式因为"重要度"概念不适用——你 push 顺序就是显示顺序,不需要重排。

### 严谨原理:immediate-mode UI

immediate-mode UI 的核心特征:

1. **无状态保留**:每帧重新声明所有 UI 元素,不存"当前 UI 树"
2. **按调用顺序渲染**:push 顺序 = 绘制顺序
3. **简洁 API**:`DrawText("FPS: 60", pos)` 一行搞定,不需要"创建 TextWidget 对象"

对比 retained-mode UI(传统 UI 库):

```cpp
// Retained mode(Qt / wxWidgets):
auto *label = new Label("FPS: 60");
label->setPosition(10, 10);
label->show();
// 后续修改要 label->setText("FPS: 59");

// Immediate mode(今天的 overlay):
DrawText("FPS: 60", {10, 10});
// 每帧重新调用,自动用当前值
```

Immediate mode 的优势:

- **简单**:无状态,无对象生命周期
- **数据驱动**:直接用当前数据(`fps` 变量)
- **易理解**:看代码就知道 UI 长什么样

劣势:

- **每帧重复工作**:大量 UI 时性能不如 retained(但 debug overlay 元素少)
- **无动画状态**:动画需要外部存储(状态不在 UI 库里)

游戏 debug overlay 普遍用 immediate mode。商业 UI(主菜单)可能用 retained mode 以支持复杂动画。

### 双轨制渲染

```
游戏 entity 走 SortKey:           Debug overlay 走 immediate:
─────────────────────             ─────────────────────────
push(entity, sort_key)            push_immediate(text)
sort by sort_key                  不排,直接 push
draw                              draw(在 entity 之后)
```

两套系统共存,互不干扰。这是工程上的"分离关注点"——游戏逻辑用排序系统,debug 工具用立即系统。

### Rust 实现

```rust
struct RenderGroup {
    sorted_entries: Vec<SortedEntry>,
    immediate_entries: Vec<ImmediateEntry>,
}

impl RenderGroup {
    fn push_sorted(&mut self, entry: SortedEntry) {
        self.sorted_entries.push(entry);
    }
    
    fn push_immediate(&mut self, entry: ImmediateEntry) {
        self.immediate_entries.push(entry);
    }
    
    fn render(&mut self) {
        // 1. 排序 + 画 sorted
        self.sorted_entries.sort_by_key(|e| e.sort_key);
        for e in &self.sorted_entries {
            draw(e);
        }
        // 2. 按 push 顺序画 immediate
        for e in &self.immediate_entries {
            draw_immediate(e);
        }
        // 3. 每帧清空 immediate
        self.immediate_entries.clear();
    }
}
```

`Vec::clear` 不释放内存,只重置 len。下一帧 push 时不重新分配,高效。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

Immediate-mode UI 的标杆是 **Dear ImGui**(https://github.com/ocornut/imgui)。它的核心 API:

```cpp
ImGui::Begin("Debug");

```

每帧调用这些函数,ImGui 自动处理输入、布局、绘制。代码极简,debug UI 一天搞定。

主流游戏的 debug UI:

- 大部分 3A 工作室自研 imgui 风格工具
- Unity 用 IMGUI(类似 immediate)+ UI Toolkit(retained,新)
- Unreal 用 Slate(retained)+ UMG(retained,蓝图)

游戏行业的共识:**debug UI 用 immediate,production UI 用 retained**。Casey 今天的实现是 immediate 的最简版。

### 3.2 · 🎨 图形学视角

图形学里 immediate mode 还有个旧含义——**immediate-mode rendering**(立即模式渲染),指 OpenGL 1.x 的 `glBegin` / `glEnd` 风格。这种模式现在已经过时(性能差),被 **retained-mode / batched rendering** 取代(VBO + draw call)。

今天的 immediate-mode UI 和那个 OpenGL 旧概念没关系,只是名字相同。**Immediate-mode UI** 是"立即声明",**immediate-mode rendering** 是"立即绘制原语"。

debug overlay 的图形实现仍然是 batched——把所有 immediate entry 收集到 vec,一次性 draw call。性能没问题。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的"立即模式"对应:

- **/proc 文件系统**:每次 read `/proc/cpuinfo`,内核立即生成内容,不存"文件"
- **sysfs**:类似,每次 read 实时计算
- **pipe**:`echo "hello" | cat`,数据流过不留存

对比"保留模式":

- **常规文件**:`echo "hello" > file.txt`,数据存到磁盘,持久化

Linux 内核的 `/proc` 是 immediate mode——read 时实时算,read 完不保留。这种设计让内核能"无状态"地暴露实时数据,避免缓存一致性问题。今天的 debug overlay 思路一致。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Immediate-mode UI(立即模式 UI)** — 每帧重新声明 UI 元素
- **Retained-mode UI(保留模式 UI)** — UI 状态持久化,事件驱动
- **Render pass separation(渲染 pass 分离)** — 不同渲染需求走不同路径

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| SortKey 排序(原) | 全部 entity 排序 | 游戏 entity | 主路径 |
| Immediate(今天) | push 顺序画 | debug UI | ✅ debug |
| Retained UI | 状态保留 | 复杂 UI | 主菜单可能 |
| Hybrid | 两者混合 | 大型游戏 | 备选 |

### 4.3 下级(内部零件)

- **`immediate_entries: Vec`** — 独立队列
- **`push_immediate_*` API** — 立即模式入口
- **不排序直接画** — push 顺序 = 绘制顺序
- **每帧 clear** — 不持久化
- **画在 sorted 之后** — UI 在最上层

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 debug overlay 用 immediate mode 而不是 SortKey 排序?给出至少 3 个理由。

**参考解答**:

1. **顺序敏感**:你 push "FPS" 然后 push "Pos",期望 FPS 显示在 Pos 上面。SortKey 可能打乱。
2. **不需要排序**:debug UI 元素都在最上层(UI layer),互相之间没有遮挡关系,SortKey 无意义。
3. **性能**:debug 模式下几百 UI 元素,sort 浪费 CPU。Immediate 直接 push 不排,快。
4. **简单**:immediate API 一行 push,不用算 SortKey。
5. **生命周期短**:每帧重新 push,不需要"跨帧稳定排序"。

### Lv2 · 动手实践

**题**:在 Rust 里实现双轨制渲染:sorted entries + immediate entries。

**参考解答**:

```rust
#[derive(Clone, Debug)]
struct SortedEntry {
    sort_key: u32,
    name: &'static str,
}

#[derive(Clone, Debug)]
struct ImmediateEntry {
    name: &'static str,
}

struct RenderGroup {
    sorted_entries: Vec<SortedEntry>,
    immediate_entries: Vec<ImmediateEntry>,
}

impl RenderGroup {
    fn new() -> Self {
        Self {
            sorted_entries: Vec::new(),
            immediate_entries: Vec::new(),
        }
    }
    
    fn push_sorted(&mut self, sort_key: u32, name: &'static str) {
        self.sorted_entries.push(SortedEntry { sort_key, name });
    }
    
    fn push_immediate(&mut self, name: &'static str) {
        self.immediate_entries.push(ImmediateEntry { name });
    }
    
    fn render(&mut self) {
        println!("--- Sorted (by SortKey) ---");
        self.sorted_entries.sort_by_key(|e| e.sort_key);
        for e in &self.sorted_entries {
            println!("  key={:#06x} {}", e.sort_key, e.name);
        }
        println!("--- Immediate (push order) ---");
        for e in &self.immediate_entries {
            println!("  {}", e.name);
        }
        // 每帧清空 immediate
        self.immediate_entries.clear();
    }
}

fn main() {
    let mut group = RenderGroup::new();
    
    // 模拟一帧
    group.push_sorted(0x20000000, "Player");
    group.push_sorted(0x10000000, "Floor");
    group.push_sorted(0x30000000, "Monster");
    
    // Debug overlay(immediate)
    group.push_immediate("=== DEBUG ===");
    group.push_immediate("FPS: 60.0");
    group.push_immediate("Player pos: (100, 200)");
    group.push_immediate("Monsters: 5");
    
    group.render();
    
    // 模拟下一帧
    println!("\n--- 下一帧 ---");
    group.push_sorted(0x20000000, "Player");
    group.push_immediate("FPS: 59.8");  // immediate 每帧重新
    group.render();
}
```

## 8 · Rust / Arch 落地代码

### Rust:双轨制渲染(完整可跑)

```rust
// Cargo.toml: 无依赖
// src/main.rs

#[derive(Clone, Debug)]
struct SortedEntry {
    sort_key: u32,
    layer: u8,
    name: &'static str,
}

#[derive(Clone, Debug)]
struct ImmediateEntry {
    name: &'static str,
    z_offset: u32,  // immediate 之间的微调(可选)
}

struct RenderGroup {
    sorted_entries: Vec<SortedEntry>,
    immediate_entries: Vec<ImmediateEntry>,
    draw_call_count: usize,
}

impl RenderGroup {
    fn new() -> Self {
        Self {
            sorted_entries: Vec::new(),
            immediate_entries: Vec::new(),
            draw_call_count: 0,
        }
    }
    
    fn push_sorted(&mut self, layer: u8, y: f32, name: &'static str) {
        let sort_key = ((layer as u32) << 28) 
                     | (((y + 500.0) as u32 & 0xFFFF) << 12);
        self.sorted_entries.push(SortedEntry { sort_key, layer, name });
    }
    
    fn push_immediate(&mut self, name: &'static str) {
        self.immediate_entries.push(ImmediateEntry { name, z_offset: 0 });
    }
    
    fn push_immediate_with_offset(&mut self, name: &'static str, offset: u32) {
        self.immediate_entries.push(ImmediateEntry { name, z_offset: offset });
    }
    
    fn render(&mut self) {
        // 1. 排序 + 画 sorted entries
        self.sorted_entries.sort_by_key(|e| e.sort_key);
        println!("--- Sorted entries ({} 个) ---", self.sorted_entries.len());
        for e in &self.sorted_entries {
            println!("  [layer={}] key={:#010x} {}", e.layer, e.sort_key, e.name);
            self.draw_call_count += 1;
        }
        
        // 2. Immediate entries 按 push 顺序画(在 sorted 之后)
        // 如果需要 immediate 之间的排序,用 z_offset
        let mut sorted_immediate: Vec<_> = self.immediate_entries.iter().enumerate().collect();
        sorted_immediate.sort_by_key(|(_, e)| e.z_offset);
        
        println!("\n--- Immediate entries ({} 个,push 顺序) ---", self.immediate_entries.len());
        for (_, e) in &sorted_immediate {
            println!("  {} (z_offset={})", e.name, e.z_offset);
            self.draw_call_count += 1;
        }
        
        // 3. 每帧清空 immediate
        self.immediate_entries.clear();
        // sorted_entries 也清空(每帧重建)
        self.sorted_entries.clear();
    }
    
    fn draw_calls(&self) -> usize {
        self.draw_call_count
    }
}

fn main() {
    println!("=== Day 332: 双轨制渲染(debug overlay) ===\n");
    
    let mut group = RenderGroup::new();
    
    // 模拟游戏主循环
    for frame in 0..3 {
        println!("==================");
        println!("=== Frame {} ===", frame);
        println!("==================\n");
        
        // 游戏 entity(SortKey 排序)
        group.push_sorted(0, -500.0, "Mountain (BG)");
        group.push_sorted(2, 50.0, "Player");
        group.push_sorted(2, 60.0, "Monster");
        group.push_sorted(3, 100.0, "Grass (FG)");
        
        // Debug overlay(立即模式)
        group.push_immediate("┌──────────────────┐");
        group.push_immediate("│ DEBUG OVERLAY    │");
        group.push_immediate("├──────────────────┤");
        group.push_immediate(&format!("│ Frame: {:<9}│", frame));
        group.push_immediate("│ FPS:   60.0      │");
        group.push_immediate("│ Entity: 4        │");
        group.push_immediate("└──────────────────┘");
        
        // Hitbox 可视化(立即)
        group.push_immediate_with_offset("[Hitbox] Player", 1);
        group.push_immediate_with_offset("[Hitbox] Monster", 1);
        
        group.render();
        println!("Total draw calls: {}\n", group.draw_calls());
    }
}
```

## 10 · 深度补充:工程视角

Immediate-mode UI 的设计哲学:Dear ImGui 的作者 ocornut 强调 immediate mode 不是技术,是设计哲学。核心是 数据驱动 + 无状态 ——每帧重新声明 UI,数据决定显示。这种哲学扩展到:数据序列化(JSON 而非 OOP 对象)、版本控制(immutable 数据 + diff)、并发(无共享状态,消息传递)。Casey 的 immediate overlay 是这种哲学的最小体现。

### 跨领域的方向一致性

工程上很多抽象都跨领域通用。今天的概念在多个领域都有对应。

- **游戏引擎**:Core abstraction 表达
- **图形学**:GPU 硬件或软件算法实现
- **Linux 内核**:类似抽象在 OS 层
- **Rust 生态**:类型安全表达

理解一个抽象的多领域映射,你就能在不同技术栈间自由切换。

### 历史演化与未来趋势

每个技术都有演化历史和未来趋势。Casey 在 HH 系列展示的是 当下最佳实践,但技术会演进。学会识别 哪些是永恒原理(数据结构、算法)、哪些是时代选择(API 设计、语言特性),让你长期保持竞争力。

永恒原理:排序、矩阵乘法、alpha 合成、内存分配、并发原语。这些 50 年不变。

时代选择:OpenGL vs Vulkan vs WebGPU、Rust vs C++、ECS vs OOP。这些 5-10 年一变。

### 给读者的建议

1. **理解原理**:每个抽象都问 为什么这样设计
2. **多语言对比**:同一个抽象在 C / Rust / Python 各怎么表达
3. **历史视角**:看技术演化,理解 为什么现在这样做
4. **实践**:每个概念都写代码,不止看
5. **开源贡献**:看真实代码怎么用,提 PR 加深理解

Casey HH 系列是教学,但更是一种 工程师心态 训练——遇到问题怎么拆解、怎么实现、怎么优化、怎么修 bug。这种心态比具体知识更重要。

## 11 · 延伸讨论

Immediate mode 的极限:Dear ImGui 在 60 FPS 下渲染 1000 个 widget,每帧 1ms 左右。Retained mode(Qt)同样 widget 渲染需要 5-10ms(布局 + 事件传播)。Immediate mode 的性能优势让它成为游戏 debug UI 标配。但 production UI(主菜单)需要动画和状态,retained 更适合。

### 工程决策的权衡

每个技术选择都涉及权衡。今天的主题在 Casey 的 HH 里选了某条路,但其他路也合理。理解权衡让你能在新场景做正确选择。

### Rust 生态的演进

Rust 生态每 6 个月一个 edition,API 和最佳实践会变。但核心原理(所有权 / 借用 / Send/Sync / Trait)稳定。学会识别'什么是稳定基础'vs'什么是流行 API',让你长期有效。

### 开源贡献的实践

今天的 Lv4 题目指向真实开源项目。实践建议:

1. **找 good-first-issue**:GitHub 上 label:'good first issue'
2. **读代码 + 文档**:理解项目架构
3. **fork + 改 + 测试**:本地验证
4. **写 PR 描述**:动机 / 改动 / 测试
5. **接受 review**:维护者反馈,可能要改
6. **merge**:成为项目 contributor

PR 不一定要大——文档改进、测试补充、小 bug 修复都是贡献。重要的是参与。

完成 Phase 6 后,你应该能:

Phase 7 / 8 会进入更高级话题(PNG 解码 / 编辑器 / 光照优化),但 Phase 6 的基础是关键。
