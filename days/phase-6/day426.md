
# Day 426 · 调试光照持久化

> Day 425 把光照融入 ECS 后,Casey 跑游戏发现 bug——保存场景后再加载,光源都消失了!其他 entity(玩家、墙)正常恢复,但光没了。今天他调试这个 bug,发现根源是**序列化遗漏**:保存代码遍历 entity 时,只处理了"已知 component"(position、velocity),没处理新加的 LightComponent。

## 0 · 为什么要有这一天

光照融入 ECS 后,所有 entity 共享一个数据结构。但**序列化**仍然需要逐 component 处理——每个 component 类型要在 save/load 代码里显式写。

Casey 的 save 函数(简化):

```rust
fn save_entity(e: &Entity) -> Json {
    json!({
        "id": e.id,
        "position": e.position,
        "velocity": e.velocity,
        // 火把加 LightComponent 后,这里没加 "light" 字段
    })
}
```

加载时:

```rust
fn load_entity(json: &Json) -> Entity {
    let mut e = Entity::default();
    e.id = json["id"];
    e.position = json["position"];
    e.velocity = json["velocity"];
    // 没加载 "light"
    e
}
```

加载的 entity 没有 light,所以光源消失了。

这是经典的"新加字段忘更新序列化" bug。Rust 的 ownership 不能消除——序列化是逻辑代码,需要程序员显式处理每个字段。

工业的解决方案:

1. **派生 Serialize/Deserialize**:`serde` crate 自动从 struct 定义生成代码,加字段自动序列化
2. **版本号**:文件格式带 version,加载时检查,旧版本走旧代码
3. **Schema 验证**:文件有 schema,加载时验证字段完整

Casey 今天切换到 `serde`,自动序列化。以后加字段不用改 save/load。

心理锚点:今天之后,你能用 serde 自动序列化任意 struct,理解为什么 Rust 生态几乎都用 serde,知道"手动序列化"是 bug 温床,能在自己的项目实现可扩展的存档系统。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑游戏存档,加载后发现光源消失。调试步骤:

1. **复现**:保存有光源的场景,加载,看光源消失
2. **检查 save 文件**:打开 JSON,看是否有 "light" 字段。没有!
3. **检查 save 代码**:`save_entity` 函数没处理 light 字段
4. **修复 1**(手动):在 save_entity 加 `"light": e.light,`,load_entity 加 `e.light = json["light"]`
5. **更深层修复**:用 `serde` 派生,自动序列化,避免以后忘

Casey 选择长期方案——用 serde。Entity 和所有 component 都加 `#[derive(Serialize, Deserialize)]`。save/load 退化成两行:

```rust
fn save_world(world: &World) -> String {
    serde_json::to_string(world).unwrap()
}

fn load_world(json: &str) -> World {
    serde_json::from_str(json).unwrap()
}
```

后续加任何 component,自动序列化。Bug 类型彻底消除。

## 2 · 心智模型

### 类比:搬家清单

想象你搬家,列清单:

- 衣服:5 箱
- 书:3 箱
- 电器:2 箱

到了新家清点,发现少了"灯具"——为什么?清单上没列!你买了灯具但忘了加进清单。

手动序列化完全同构。程序员列字段清单,加字段忘了更新清单,新字段不被保存。

`serde` 的"派生"是"自动列清单"——只要 struct 有字段,serde 自动算清单,加减字段自动同步。

### 严谨原理:serde 派生

`#[derive(Serialize, Deserialize)]` 让 Rust 在编译期为 struct 生成序列化代码。生成的代码等价于:

```rust
impl Serialize for Entity {
    fn serialize<S: Serializer>(&self, ser: S) -> Result<S::Ok, S::Error> {
        let mut s = ser.serialize_struct("Entity", 4)?;
        s.serialize_field("id", &self.id)?;
        s.serialize_field("position", &self.position)?;
        s.serialize_field("velocity", &self.velocity)?;
        s.serialize_field("light", &self.light)?;
        s.end()
    }
}
```

每个字段都被序列化,没有遗漏。加字段只需 `cargo build`,派生代码自动更新。

### 版本兼容

游戏存档需要**版本兼容**——旧版本保存的存档,新版本应该能加载(可能字段缺失,用默认值)。serde 提供几种方案:

1. **`#[serde(default)]`**:字段缺失时用 `Default::default()`
2. **`#[serde(rename = "old_name")]`**:重命名字段,旧存档仍能加载
3. **Option 字段**:缺失自动 None

```rust
#[derive(Serialize, Deserialize)]
pub struct Entity {
    pub id: u32,
    #[serde(default)]
    pub position: Option<Vec3>,
    #[serde(default)]
    pub light: Option<LightComponent>,
    // 新字段:#[serde(default)] 旧存档加载时用 default
}
```

### Rust 视角:serde 实战

Cargo.toml:

```toml
[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
glam = { version = "0.29", features = ["serde"] }
```

`glam` 的 `serde` feature 让 Vec3/Mat4 可序列化。

代码:

```rust
use serde::{Serialize, Deserialize};
use glam::Vec3;

#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct LightComponent {
    pub color: Vec3,
    pub intensity: f32,
}

#[derive(Serialize, Deserialize, Clone, Default, Debug)]
pub struct Entity {
    pub id: u32,
    #[serde(default)]
    pub position: Option<Vec3>,
    #[serde(default)]
    pub light: Option<LightComponent>,
}

fn main() {
    let e = Entity {
        id: 1,
        position: Some(Vec3::new(5.0, 0.0, 5.0)),
        light: Some(LightComponent {
            color: Vec3::ONE,
            intensity: 100.0,
        }),
    };

    let json = serde_json::to_string_pretty(&e).unwrap();
    println!("{}", json);

    let loaded: Entity = serde_json::from_str(&json).unwrap();
    println!("Loaded: {:?}", loaded);
}
```

输出:

```json
{
  "id": 1,
  "position": [5.0, 0.0, 5.0],
  "light": {
    "color": [1.0, 1.0, 1.0],
    "intensity": 100.0
  }
}
```

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"手动序列化"是 bug 温床?serde 怎么消除这类 bug?

**参考解答**:手动序列化需要程序员**手动列出所有字段**。加字段时必须同步更新 save 和 load 代码——如果忘了,新字段不被保存(数据丢失),或加载时找不到字段(panic 或 None)。

人类在"同步多份信息"上极易出错。10 个字段 × 2 个函数(save + load) = 20 处必须一致。任何一个不一致就 bug。

serde 派生从 struct 定义**自动生成** save 和 load 代码。struct 加字段,派生自动更新。**单一数据源**(struct 定义),不可能不同步。

这是"机械替代人工"的经典案例。所有重复性工作都应该自动化。

### Lv2 · 动手实践

**题**:用 serde 派生给 Entity + LightComponent 加序列化。完成标准:
- save 后 JSON 含所有字段
- load 后 Entity 完全一致(包括 light)

**参考解答**:

```rust
// Cargo.toml:
// serde = { version = "1", features = ["derive"] }
// serde_json = "1"
// bincode = "1"
// glam = { version = "0.29", features = ["serde"] }

use serde::{Serialize, Deserialize};
use glam::Vec3;

#[derive(Serialize, Deserialize, Clone, Debug, PartialEq)]
pub struct LightComponent {
    pub color: Vec3,
    pub intensity: f32,
    #[serde(default)]
    pub radius: f32,
}

impl Default for LightComponent {
    fn default() -> Self {
        Self { color: Vec3::ONE, intensity: 1.0, radius: 10.0 }
    }
}

#[derive(Serialize, Deserialize, Clone, Debug, PartialEq, Default)]
pub struct Entity {
    pub id: u32,
    #[serde(default)]
    pub position: Option<Vec3>,
    #[serde(default)]
    pub light: Option<LightComponent>,
}

fn main() {
    let e = Entity {
        id: 1,
        position: Some(Vec3::new(5.0, 0.0, 5.0)),
        light: Some(LightComponent {
            color: Vec3::new(1.0, 0.8, 0.5),
            intensity: 50.0,
            radius: 12.0,
        }),
    };

    // JSON 序列化
    let json = serde_json::to_string_pretty(&e).unwrap();
    println!("JSON:\n{}", json);
    println!("JSON size: {} bytes", json.len());

    let loaded_json: Entity = serde_json::from_str(&json).unwrap();
    assert_eq!(e, loaded_json);
    println!("JSON round-trip: OK\n");

    // bincode 序列化
    let bincode_bytes = bincode::serialize(&e).unwrap();
    println!("Bincode size: {} bytes", bincode_bytes.len());

    let loaded_bin: Entity = bincode::deserialize(&bincode_bytes).unwrap();
    assert_eq!(e, loaded_bin);
    println!("Bincode round-trip: OK\n");

    // 版本兼容测试:从旧 JSON(没有 radius)加载
    let old_json = r#"{
        "id": 2,
        "position": [0.0, 0.0, 0.0],
        "light": {
            "color": [1.0, 1.0, 1.0],
            "intensity": 100.0
        }
    }"#;
    let old_loaded: Entity = serde_json::from_str(old_json).unwrap();
    println!("Old format loaded: {:?}", old_loaded);
    // radius 用 default (10.0)
    assert_eq!(old_loaded.light.as_ref().unwrap().radius, 10.0);
    println!("Version compatibility: OK");
}
```

use serde::{Serialize, Deserialize};
use glam::Vec3;

#[derive(Copy, Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
pub enum LightClassification {
    Direct,
    Propagated,
    Baked,
}

#[derive(Serialize, Deserialize, Clone, Debug)]
pub struct LightComponent {
    pub color: Vec3,
    pub intensity: f32,
    #[serde(default = "default_radius")]
    pub radius: f32,
    pub classification: LightClassification,
}

fn default_radius() -> f32 { 10.0 }

impl Default for LightComponent {
    fn default() -> Self {
        Self {
            color: Vec3::ONE,
            intensity: 1.0,
            radius: 10.0,
            classification: LightClassification::Direct,
        }
    }
}

#[derive(Serialize, Deserialize, Clone, Debug, Default)]
pub struct Entity {
    pub id: u32,
    #[serde(default)]
    pub position: Option<Vec3>,
    #[serde(default)]
    pub velocity: Option<Vec3>,
    #[serde(default)]
    pub name: Option<String>,
    #[serde(default)]
    pub light: Option<LightComponent>,
}

#[derive(Serialize, Deserialize, Clone, Debug, Default)]
pub struct World {
    pub entities: Vec<Entity>,
    #[serde(default)]
    pub next_id: u32,
    #[serde(default = "default_version")]
    pub version: u32,
}

fn default_version() -> u32 { 1 }

impl World {
    pub fn save_to_json(&self) -> Result<String, serde_json::Error> {
        serde_json::to_string_pretty(self)
    }

    pub fn save_to_bincode(&self) -> Result<Vec<u8>, bincode::Error> {
        bincode::serialize(self)
    }

    pub fn load_from_json(json: &str) -> Result<Self, serde_json::Error> {
        serde_json::from_str(json)
    }

    pub fn load_from_bincode(bytes: &[u8]) -> Result<Self, bincode::Error> {
        bincode::deserialize(bytes)
    }
}

fn main() {
    let mut world = World::default();
    world.next_id = 3;
    world.version = 2;

    world.entities.push(Entity {
        id: 0,
        name: Some("Torch".to_string()),
        position: Some(Vec3::new(5.0, 1.0, 5.0)),
        velocity: None,
        light: Some(LightComponent {
            color: Vec3::new(1.0, 0.8, 0.4),
            intensity: 30.0,
            radius: 12.0,
            classification: LightClassification::Direct,
        }),
    });
    world.entities.push(Entity {
        id: 1,
        name: Some("Ceiling".to_string()),
        position: Some(Vec3::new(0.0, 10.0, 0.0)),
        velocity: None,
        light: Some(LightComponent {
            color: Vec3::ONE,
            intensity: 100.0,
            radius: 50.0,
            classification: LightClassification::Propagated,
        }),
    });
    world.entities.push(Entity {
        id: 2,
        name: Some("Player".to_string()),
        position: Some(Vec3::ZERO),
        velocity: Some(Vec3::ZERO),
        light: None,
    });

    // 保存
    let json = world.save_to_json().unwrap();
    let bincode = world.save_to_bincode().unwrap();
    println!("JSON size: {} bytes", json.len());
    println!("Bincode size: {} bytes", bincode.len());
    println!("Compression: {:.1}x", json.len() as f64 / bincode.len() as f64);

    // 加载
    let json_world = World::load_from_json(&json).unwrap();
    let bin_world = World::load_from_bincode(&bincode).unwrap();
    assert_eq!(json_world.entities.len(), 3);
    assert_eq!(bin_world.entities.len(), 3);

    // 验证光源
    let torch = &json_world.entities[0];
    assert!(torch.light.is_some());
    println!("\nTorch loaded: name={:?} light={:?}",
        torch.name, torch.light.as_ref().map(|l| l.intensity));

    // 旧版本兼容测试(没 version 字段)
    let old_format = r#"{"entities": [], "next_id": 0}"#;
    let old_world = World::load_from_json(old_format).unwrap();
    println!("\nOld format loaded: version={}", old_world.version);
    // version 用 default(1)
    assert_eq!(old_world.version, 1);
}

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
