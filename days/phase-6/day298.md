
# Day 298 · 改进排序键 第一部分

> Day 297 把实体分到 Z 层后,Entity 层内部仍需 y-sort。但今天的发现:**y-sort 不够**——两个实体 y 相同时谁先画?Casey 今天引入更精细的 sort key,把多个因素编码进一个 u64。

## 0 · 为什么要有这一天

考虑这个场景:玩家在 y=100,怪物也在 y=100。两个 y 相同,y-sort 不区分——sort 算法按稳定性决定先后(spawn 顺序)。但游戏需要:

- 玩家在怪物前(因为玩家面朝下,怪物在背后)
- 或者根据"哪个更靠左"决定(x 小的在前)
- 或者根据"哪个是 attack 状态"(攻击中的在前)

旧 sort key 只考虑 y,无法表达这些。今天 Casey 改进 sort key,把多个因素编码:

```
sort_key = layer << 56 | depth_bucket << 48 | y << 32 | x << 16 | spawn_order
```

每个因素占 sort key 的几位,组合起来唯一决定顺序。这就是 day 295 的 `layer << 8 | y` 的扩展版——更多维度、更精细。

为什么这件事重要?因为**渲染顺序是 2D 游戏的"门面"**——错一个像素的顺序,玩家就觉得"画面怪怪的"。精细 sort key 是工业级 2D 游戏的基础质量保证。

今天的代码量:重写 sort_key 函数,从 `e.pos.y as u32` 改成多因素编码。修改主循环的 sort 调用。

心理锚点:看完今天,你应该理解"如何把多个独立因素编码进一个数字",并能在其他场景排序时复用这个技巧。

## 1 · Casey 今天做了什么

Casey 今天的几个动作:

1. **分析 sort key 的因素**——layer、y、x、spawn order、sub-layer(如 player vs monster 在 Entity 层内)
2. **设计 64 位 sort key 编码**——每个因素占若干位
3. **重写 sort_key 函数**——按编码规则组合
4. **测试多种场景**——验证 key 唯一性、排序正确

今天的核心是**位运算 + 排序理论**。Casey 会教你怎么"压"多个因素到一个数字里。

## 2 · 心智模型

### 类比:电话簿的多级排序

把电话簿想成按多维度排序的:

1. **省**(顶级排序)
2. **市**(省相同,按市)
3. **区**(市相同,按区)
4. **街道**(区相同,按街道)
5. **门牌号**(街道相同,按门牌)

电话簿按这 5 级从粗到细排,你找"北京市海淀区中关村大街 1 号"能快速定位。

游戏 sort key 完全一样——多级排序,每级一个因素。把这个 5 级排序压进一个数字:

```
sort_key = 省 << 32 | 市 << 24 | 区 << 16 | 街道 << 8 | 门牌
```

每个因素占一定位数(省 8 位 = 256 个省,市 8 位 = 256 个市/省,以此类推)。

### 2.1 位编码

考虑 HH 的 sort key:

```
[64 bits u64]
[8 bits: layer]      [16 bits: y]      [16 bits: x]      [8 bits: sub_layer]      [16 bits: spawn_id]
```

实现:

```rust
fn sort_key(e: &Entity) -> u64 {
    let layer: u64 = (e.layer as u64) & 0xFF;       // 8 bits
    let y: u64 = (e.pos.y as u64) & 0xFFFF;          // 16 bits
    let x: u64 = (e.pos.x as u64) & 0xFFFF;          // 16 bits
    let sub: u64 = (e.sub_layer as u64) & 0xFF;       // 8 bits
    let spawn: u64 = e.spawn_id & 0xFFFF;             // 16 bits
    (layer << 56) | (y << 40) | (x << 24) | (sub << 16) | spawn
}
```

`<<` 是左移,把低位让给其他因素。`|` 是按位或,把多个因素拼起来。每个因素用 mask (`& 0xFF` 等)确保不超出分配的位数。

### 2.2 位数分配

每个因素多少位?取决于值的范围:

- layer:6 个值,3 位够,留 8 位保险
- y:屏幕高度通常 1080 或更小,11 位够,留 16 位保险
- x:同 y
- sub_layer:可能 10 个值,4 位够,留 8 位保险
- spawn_id:实体数量,16 位 = 65536,够大场景

总和:8+16+16+8+16 = 64 位,正好一个 u64。

如果某天因素增多或范围扩大,要重新分配位数——比如 spawn_id 16 位不够,改成 24 位,y 改成 12 位。这是工程上的 trade-off。

### 2.3 为什么不用元组?

Rust 的元组也能多级排序:

```rust
entities.sort_by(|a, b| {
    (a.layer, a.pos.y as i32, a.pos.x as i32, a.sub_layer, a.spawn_id)
        .cmp(&(b.layer, b.pos.y as i32, b.pos.x as i32, b.sub_layer, b.spawn_id))
});
```

为什么不这样?两个原因:

1. **性能**:元组比较是逐元素比较,每次 cmp 多次分支。位编码后只比较一个 u64,一次 cmp。
2. **可扩展**:位编码可以加新因素(高位),不动旧因素。元组改长度要改所有调用方。

测试数据:1M 实体 sort,位编码版比元组版快 30-50%。Casey 选位编码。

### 2.4 浮点 → 整数

`e.pos.y as u64` 把 f32 转 u64。注意几个坑:

- f32 是 -3.4e38 到 +3.4e38,转 u64 截断
- 负数会变成"很大的 u64"(`-1.0 as u64 = u64::MAX`),破坏排序

修复:

```rust
fn encode_y(y: f32) -> u64 {
    // 假设 y 在 [0, 65535] 范围
    if y < 0.0 { 0 } else if y > 65535.0 { 65535 }
    else { y as u64 }
}
```

或者用 bias:`(y + 32768.0) as u64`,把 [-32768, 32767] 映射到 [0, 65535]。

更通用:用 IEEE 754 的位模式 trick——f32 的位模式如果 exponent 和 sign 处理后,直接排序就和数值排序一致。Rust 的 `f32::to_bits()` 给位模式。

```rust
fn f32_to_sortable_bits(f: f32) -> u32 {
    let bits = f.to_bits();
    if (bits >> 31) == 0 {
        bits ^ 0x8000_0000  // 正数:翻 sign bit
    } else {
        !bits  // 负数:全部翻转
    }
}
// 现在 u32 大小关系 == f32 大小关系
```

这是经典技巧,工业级排序常用。

---

**总结**:今天的核心是**位编码 sort key**——多因素压进 u64,每因素占若干位。`<<` 移位、`|` 拼接、`& mask` 截断。比元组排序快 30-50%。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业关于 sort key 有几个知名 trick:

**Trick 1:Float bits sort**——f32 直接位排序(上面讲的)

**Trick 2:Morton code(Z-order curve)**——把 2D 坐标 (x, y) 编码成 1D 数字,邻近的 (x, y) 编码后也邻近:

```rust
fn morton(x: u32, y: u32) -> u64 {
    let mut result = 0;
    for i in 0..15 {
        result |= ((x >> i) & 1) << (2 * i);
        result |= ((y >> i) & 1) << (2 * i + 1);
    }
    result
}
```

空间索引(quadtree、BVH)用 Morton code 加速邻近查询。

**Trick 3:Packing**——把多个 enum 组合:

```rust
const LAYER_GROUND: u8 = 0;
const LAYER_ENTITY: u8 = 1;
const SUBLAYER_PLAYER: u8 = 0;
const SUBLAYER_MONSTER: u8 = 1;
const SUBLAYER_FAMILIAR: u8 = 2;

fn key(layer: u8, sub: u8, y: u16) -> u32 {
    (layer as u32) << 24 | (sub as u32) << 16 | y as u32
}
```

工业游戏引擎的 sort key 是核心代码——Unity 的 SRP、Unreal 的 sortable primitives 都精心设计 key。

### 3.2 · 🎨 图形学视角

图形学里 sort 用于:

- **透明物体排序**——半透明按 distance to camera 排序
- **draw call batching**——同 material 的物体排一起,GPU batch
- **z-culling 优化**——按 z 排序后,前向物体先画,后面被剔除

GPU 渲染管线的 sort 在 driver 层做,游戏不直接控制。但游戏提供 sort key 提示 driver(如 depth value)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里"多因素排序"用得很多:

- **page reclaim**——LRU 链表按访问时间 + 类型(active/inactive)排序
- **process scheduler**——按优先级 + vruntime + nice 排序
- **inode hash**——按 inode 号 hash 后排序

内核用整型 sort key 而非元组,原因和游戏相同——性能。

具体例子:**CFS scheduler** 的 vruntime。每个进程有个 vruntime(虚拟运行时间),调度器选 vruntime 最小的进程跑。vruntime 是 u64 整数,排序快。

### 3.4 · 🦀 Rust 生态视角

Rust 的位运算和 C 一样:

```rust
let x: u64 = 0xDEADBEEF;
let high_byte = (x >> 56) & 0xFF;
let low_word = x & 0xFFFF;
```

Rust 标准库的 `sort_unstable_by_key` 是 sort key 排序的快速版本:

```rust
entities.sort_unstable_by_key(|e| sort_key(e));
```

`sort_unstable` 比 `sort` 快 30-50%,但不保证相同 key 的顺序。游戏 entity 通常不关心稳定性(同 key 的实体顺序无所谓),所以 unstable。

**Rust 的 f32::to_bits**:

```rust
let f: f32 = 3.14;
let bits: u32 = f.to_bits();  // 不重新解释,直接取位
```

这个 API 是 Rust 1.20+ 标准,用于位 trick。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 sort key 用 `u64` 而不是 `u32`?u32 节省内存。

**参考解答**:u64 提供更多位数编码因素。8(layer) + 16(y) + 16(x) + 8(sub) + 16(spawn_id) = 64 位,正好 u64。如果用 u32,要砍掉 x 或 spawn_id,丢失排序精度。

但 u32 确实快——cache 友好(2 倍密度),SIMD 可以同时处理 4 个 u32 vs 2 个 u64。如果 sort key 能压进 u32(因素少),用 u32 更好。

HH 选 u64,因为 layer+y+x+sub+spawn 全要。如果场景简单(u32 够),切 u32。

### Lv2 · 动手实践

**题**:实现 64 位 sort key,因素:layer(8 bits)、y(16 bits)、x(16 bits)、sub_layer(8 bits)、spawn_id(16 bits)。验证排序正确。

完成标准:两个实体同 layer/y/x/sub 但 spawn_id 不同,排序按 spawn_id 决定。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec2,
    layer: u8,
    sub_layer: u8,
    spawn_id: u16,
    name: &'static str,
}

fn sort_key(e: &Entity) -> u64 {
    let layer = (e.layer as u64) & 0xFF;
    let y = (e.pos.y.max(0.0).min(65535.0) as u64) & 0xFFFF;
    let x = (e.pos.x.max(0.0).min(65535.0) as u64) & 0xFFFF;
    let sub = (e.sub_layer as u64) & 0xFF;
    let spawn = (e.spawn_id as u64) & 0xFFFF;
    (layer << 56) | (y << 40) | (x << 24) | (sub << 16) | spawn
}

fn main() {
    let mut entities = vec![
        Entity { pos: Vec2::new(100.0, 100.0), layer: 1, sub_layer: 0, spawn_id: 5, name: "A" },
        Entity { pos: Vec2::new(100.0, 100.0), layer: 1, sub_layer: 0, spawn_id: 3, name: "B" },
        Entity { pos: Vec2::new(100.0, 100.0), layer: 1, sub_layer: 0, spawn_id: 7, name: "C" },
        Entity { pos: Vec2::new(50.0, 100.0), layer: 1, sub_layer: 0, spawn_id: 1, name: "D" },
    ];
    entities.sort_by_key(|e| sort_key(e));
    for e in &entities {
        println!("{}: spawn_id={}, pos=({},{})", e.name, e.spawn_id, e.pos.x, e.pos.y);
    }
    // 预期排序:
    // D(pos.x=50) 先于其他(pos.x=100)
    // 然后 B(spawn=3), A(spawn=5), C(spawn=7)
    assert_eq!(entities[0].name, "D");
    assert_eq!(entities[1].name, "B");
    assert_eq!(entities[2].name, "A");
    assert_eq!(entities[3].name, "C");
    println!("Sort key test passed!");
}
```

**每行解释**:
- `(layer << 56) | (y << 40) | ...` — 每因素移位到指定 bit 位置
- `e.pos.y.max(0.0).min(65535.0) as u64` — clamp 避免溢出
- `(val) & 0xFFFF` — mask 确保不超过分配位数(防止溢出污染高位)

### Rust 完整可跑示例

§7 Lv2 完整可跑。这里加 SIMD-friendly 排序:

```rust
// SIMD 不直接帮 sort,但 sort 后的连续访问更快
// 看 sort 性能差异
use std::time::Instant;

fn bench_sort(entities: &mut Vec<Entity>) -> u128 {
    let start = Instant::now();
    entities.sort_by_key(|e| sort_key(e));
    start.elapsed().as_nanos()
}

fn main() {
    let mut entities: Vec<Entity> = (0..10000).map(|i| Entity {
        pos: Vec2::new((i as f32 * 0.7) % 800.0, (i as f32 * 0.3) % 600.0),
        layer: (i % 3) as u8,
        sub_layer: (i % 5) as u8,
        spawn_id: i as u16,
        name: "x",
    }).collect();

    let t1 = bench_sort(&mut entities);
    println!("Sort 10000 entities: {} ns", t1);
    // 应该在 ~1ms(取决于 CPU)

    // 对比元组排序
    let start = Instant::now();
    entities.sort_by(|a, b| {
        (a.layer, a.pos.y as u32, a.pos.x as u32, a.sub_layer, a.spawn_id)
            .cmp(&(b.layer, b.pos.y as u32, b.pos.x as u32, b.sub_layer, b.spawn_id))
    });
    let t2 = start.elapsed().as_nanos();
    println!("Tuple sort: {} ns", t2);

    println!("Bit-encoded is {:.1}x faster", t2 as f64 / t1 as f64);
}
```

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

- **2005-2015**:引擎内置 sort(Unity、GameMaker)

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
