# Day 341 · 动态增长的 arena

> 把"启动时一次性分配几百 MB 永不增长"的硬规则松绑:让 arena 在不够用时自己向 OS 申请新的内存页,但是对外 API 不变——这是一切"内存预算可控 + 又不会被一帧爆量数据卡死"的引擎的基石。

## 0 · 为什么要有这一天

到目前为止你的项目里已经有了一个比较成熟的内存系统:游戏启动时申请一大块 `Memory` 结构(里面分 `PermanentStorage`、`TransientStorage` 两段),然后用一个 `memory_arena` 在其上做线性分配(linear allocation)——每次 `push_size(n)` 就把指针往前挪 n 字节,不释放,这一帧结束时整段一起回滚。这是 Casey 在 Day 100 前后定下来的"硬规则":**arena 大小编译期固定,运行时永不增长**。

这条规则的好处我们前面已经讲过:启动时一次 `mmap` / `VirtualAlloc`,从此零分配,性能完全可预测。但坏处随着项目越走越远逐渐浮现——你开始频繁踩到"arena 不够"的边界:

1. **过场动画**(cutscene)系统加载一段新的对话文本 + 角色 sprite,`TransientStorage` 突然多吃了 30 MB,某张图直接爆 arena
2. **多线程世界模拟**开始跑后,每个 sim region(模拟区域)自己要开几 MB 工作区,8 个 region × 4 MB = 32 MB,稳定超 arena 上限
3. **资产流水线**加载新的关卡时,需要一次性把整个关卡的所有 entity hash 进 arena,某些大关需要 100+ MB

每次爆 arena 你都得回去把 `MEMORY_SIZE` 改大,重新编译,看会不会触发别的边界。这种"调一次常量、重新构建、再跑一次"的循环是引擎开发里最让人抓狂的事之一——你不知道自己调的常量是"刚好够"还是"已经过大让 cache 受损"。

今天 Casey 干的事是:**把 arena 改成"可以动态生长"的版本**,但保留线性分配的核心语义。具体说:

- 每个 arena 内部维护一个**内存块链表**(block list),而不是单一固定大小
- 启动时只有一块"主块"(main block),大小是 `DEFAULT_ARENA_SIZE`(比如 64 MB)
- 当 `push_size` 时如果当前块不够,arena 自己 `mmap` 一块新内存(默认 1 MB),挂到链表尾部
- 所有分配对调用方来说还是"线性增长,不释放",内部细节隐藏

这套设计的好处:

1. **内存预算"软"控制**:默认 64 MB,理论可以长到几个 GB,但每次增长是显式的——你能看到什么时候、为什么增长
2. **零分配的 99% 场景依然零分配**:大多数帧根本不触发新块申请,只有大事件(切场景)才会
3. **崩溃边界消失**:再也不会 `ASSERT(arena->used < arena->size)`,你看到的失败模式从"游戏崩溃"变成"我看看怎么改逻辑减少内存"

心理锚点:今天之后你的引擎不会再因为"内存不够"直接退出,而是优雅降级。你能在 debug overlay 里看到 "Arena grew to N blocks, total X MB",而不是一句话崩溃。这是从"教学项目"迈向"产品级引擎"的关键一步。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 打开 IDE 做了一次"数据结构演进"。原来 `memory_arena` 是这样:

```c
typedef struct {
    memory_index size;       // 总大小
    uint8 *base;             // 起始指针
    memory_index used;       // 已用大小
} memory_arena;
```

今天他改成了:

```c
typedef struct memory_arena memory_arena;
struct memory_arena {
    memory_index size;       // 当前块大小
    uint8 *base;             // 当前块起始指针
    memory_index used;       // 当前块已用大小
    memory_arena *prev;      // 上一个块(链表)
    // ... 新字段在 day342-day346 继续加
};
```

核心变化只有一个:`prev` 字段,让 arena 变成"块链表"。`push_size` 函数的实现从"指针往前挪"变成"如果当前块满了,先申请新块挂到链表,然后在新块上挪":

```c
void *push_size(memory_arena *arena, memory_index size_init) {
    if (arena->used + size_init > arena->size) {
        // 申请新块
        memory_arena *new_block = bootstrap_new_block(size_init);
        new_block->prev = arena;
        // 把"当前块状态"复制到 new_block,然后把 arena 自己的 size/base/used 重置为新块
        *arena = *new_block; // 实际代码有更精细的字段处理
    }
    void *result = arena->base + arena->used;
    arena->used += size_init;
    return result;
}
```

Casey 花了相当时间讨论一个细节:**"arena 句柄"和"当前块"应该是同一个对象,还是分开两个对象**。Casey 的选择是"同一个对象"——arena 自己永远代表"最新块",`prev` 链表是历史。这样的好处是 API 完全不变(`push_size(arena, n)`),调用方不需要知道有块链表。

代价是 `push_size` 可能修改 arena 自身的字段(`size`、`base`),所以 arena 句柄必须是指针(`memory_arena *`),不能是值。Casey 提到这是个"漂亮的指针赋值技巧"——`*arena = *new_block` 把整块状态一次性更新,但因为是 C struct 拷贝,语义清晰。

整段重构只动了 `push_size` 一个函数和 `memory_arena` 一个结构体,外面几百处 `push_size` 调用全部不变——这就是好 API 设计的回报。

## 2 · 心智模型

### 类比:扑克牌搭帐篷 vs 帆布袋装帐篷

把"线性 arena"想象成在桌上铺一张固定大小的白纸,你画画写到哪算到哪,写到边就停。

- **静态 arena(以前的版本)**:纸就这么大,装不下只能换一张更大的纸(改 `MEMORY_SIZE` 重编译)
- **动态 arena(今天的版本)**:写满一张就接另一张,用订书钉连起来,可以无限延长

订书钉连接的"链表"就是 `arena->prev` 指针——你随时可以从最新一张往回翻到最早一张,但**写入永远在最末一张**。这保证了线性分配的"指针递增"语义没变,变的只是"递增到底怎么办"。

### 严谨原理:为什么不能用 realloc

最直觉的做法是"arena 满了就 realloc 一块两倍大的",但这条路 Casey 没走,而且**绝对不能走**。原因有三:

1. **realloc 可能搬动内存**:arena 里分配的对象可能被别处持有指针,一搬动全部悬空
2. **realloc 内部可能碎化**:OS 的 `realloc` 实现(libc `mremap` / `HeapReAlloc`)在原地不够大时会拷贝到新位置,这是不可预测的
3. **破坏"线性增长"的承诺**:你承诺 arena 永远往一个方向走,realoc 打破这个承诺

链表式分块的好处正好相反:

- 每个块自己固定大小(`DEFAULT_BLOCK_SIZE`,比如 1 MB),内部线性
- 新块是全新 mmap 出来的,不会和旧块竞争物理地址
- 旧块的所有指针继续有效,因为旧块内存**永不释放**(直到 arena 整体释放)
- 释放时只需要遍历链表逐块 `munmap`,O(块数)

### 内部布局(ASCII)

```
arena 句柄(对调用方)
┌─────────────────┐
│ size = 1 MB      │  ← 当前块大小
│ base = 0x7f...   │  ← 当前块起始指针
│ used = 800 KB    │  ← 当前块已用
│ prev ───────────────┐
└─────────────────┘   │
                      ↓
            ┌─────────────────┐
            │ size = 1 MB      │  ← 上一块
            │ base = 0x7f...   │
            │ used = 1000 KB   │  (满了)
            │ prev ───────────────┐
            └─────────────────┘   │
                                  ↓
                       ┌──────────────────┐
                       │ size = 64 MB      │ ← 主块(startup 分配)
                       │ base = 0x7f...    │
                       │ used = 64 MB      │ (满了)
                       │ prev = NULL       │ ← 链表尾巴
                       └──────────────────┘
```

注意:**arena 句柄的字段反映的是"最新块"**,但 prev 链表保存所有历史块。这是关键技巧——让 `push_size(arena, n)` 的 API 看起来和静态版本完全一样。

### Linux 上的 mmap:OS 是怎么给你"无限内存"的

`mmap`(memory map)是 POSIX 的系统调用,把一段虚拟地址空间映射到一个文件或匿名内存(anonymous,没有文件后端)。今天我们用匿名 mmap 申请大块内存:

```c
void *mmap(void *addr, size_t length, int prot, int flags,
           int fd, off_t offset);
```

参数解释:

- `addr`:建议地址,通常传 `NULL` 让内核自己选
- `length`:要申请多少字节
- `prot`:权限,`PROT_READ | PROT_WRITE` 是可读可写
- `flags`:`MAP_PRIVATE | MAP_ANONYMOUS` 是私有匿名映射(进程独享,没有文件)
- `fd` 和 `offset`:匿名映射时传 `-1` 和 `0`

返回值是起始虚拟地址,失败返回 `MAP_FAILED`(`(void*)-1`)。

**关键**:Linux 的 mmap 是**延迟分配**(lazy allocation)的——`mmap` 调用只是"预订"虚拟地址空间,真正的物理页只有在你**第一次写入**时才分配(称为 demand paging)。这意味着:

```bash
# 申请 1 GB,mmap 立刻返回,但物理内存占用是 0
mmap(NULL, 1GB, ...) → 立刻返回 0x7f...
# 实际写之前 cat /proc/$(pidof my_game)/status 看 VmRSS = 0
# 现在写入第一个字节
*p = 42;
# 这时内核分配一页(4 KB),VmRSS = 4 KB
```

这正是 arena 动态生长想要的语义:**新块申请几乎免费**(只是改页表),**实际占用按需增长**。所以即使你 arena "理论大小"是几个 GB,实际内存占用只有真实写过的部分。

### Rust 表达:为什么不用 Vec<u8>

最朴素的 Rust 想法是 `Vec<u8>`——它内部就是堆指针 + len + cap,看起来和 arena 一样。但 `Vec<u8>` 在 push 时如果 cap 不够会 realloc 整块拷贝,这正是 Casey 反对的。所以 Rust 端我们用:

```rust
struct MemoryBlock {
    base: *mut u8,        // mmap 出来的起始指针
    size: usize,          // 这块多大
    used: AtomicUsize,    // 这块用了多少(原子,因为多线程会读)
}

struct MemoryArena {
    current: UnsafeCell<MemoryBlock>,   // 当前块
    prev: Box<MemoryBlock>,             // 上一块(链表节点)
    // ...
}
```

`UnsafeCell` 告诉编译器:"这块内存的内部可能被多个指针别名修改,别做这个 aliasing 假设"。这是 Rust 中"我要自己管这块内存"的标准包法,所有内部可变性数据结构(`RefCell`、`Cell`、`AtomicXxx`)都建立在 `UnsafeCell` 上。

`*mut u8` 是裸指针,没有自动释放,需要我们自己写 `Drop` 来 `munmap`。Arena 句柄是 `Send`(可跨线程 move)但不是 `Sync`(不可跨线程共享 `&`),因为裸指针没有同步语义——你在外层加锁,不是 arena 内部管。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

主流引擎的"动态 arena"叫法不一,但概念完全一致:

- **Unreal Engine**:`FMemStack`,一个堆栈式 arena,支持 `Push` / `Pop` 区段。多个 `FMemStack` 通过 `FMemStackBase` 管理。在材质编译、序列化、网络包构造等"短暂生命周期"场景大量使用
- **Unity DOTS**:Entities 的 chunk allocator,本质是固定大小块链表
- **Bevy ECS**:`bevy_ecs` 的 `SystemMeta` 使用 `NonNull<u8>` + bumpalo 风格分配器,块链表版见 `bevy_tasks::ConditionalSend`
- **DOOM 3**(开源):`idDynamicBlockAlloc<T>`,就是 Casey 这次重构要做的几乎一模一样的结构

游戏行业的共识是:**写引擎一定要有自己的 arena,不要用 OS 的 malloc**。malloc 的开销(几十到几百纳秒)和不可预测性(fragmentation)对 16ms 帧预算是致命的。Arena 用"一帧一清"换"零碎片、零开销",这是工程上的经典权衡。

Casey 在后面 day350 多线程模拟里会大量用今天的动态 arena:每个 sim region 一个 arena,临时分配的对象(实体快照、临时碰撞查询)放里面,帧结束统一 `arena_clear`。如果今天不做动态,多线程版根本写不出来。

### 3.2 · 🐧 Linux 系统编程视角

Linux 用户态申请内存的几种方式,各有用途:

| API | 何时用 | 碎片 | 性能 |
|---|---|---|---|
| `malloc` / `free` | 通用 | 严重(libc 内部维护 bins) | 几十 ns |
| `mmap` / `munmap` | 大块 / 自定义分配器 | 无(页对齐) | 几百 ns,但只调用一次 |
| `posix_memalign` | 对齐要求(SIMD) | 同 malloc | 几十 ns |
| `sbrk` | 已弃用 | 严重 | 不可重入 |

Arena 的设计是:**调用方仍用 `push_size(n)`,但内部用 mmap 申请大块,然后我们自己当分配器**。这种"在 mmap 之上建自己的分配器"是 glibc 的 `malloc` 内部也在做的事(`malloc` 的 `brk` 池就是它自己实现的"小对象 arena")。

你今天写的 `push_size` 就是"在 mmap 之上再建一层 bump allocator",这是教科书式的内存管理分层。

#### /proc/pid/maps 看你的 mmap 块

```bash
# 跑你的游戏,后台看虚拟地址映射
pidof handmade_hero_rust | xargs -I{} cat /proc/{}/maps | head -30
# 输出示例(每行一块内存映射):
# 00400000-0057b000 r-xp 00000000 fe:01 1234  /path/to/bin
# 7f8a9c000000-7f8a9c010000 rw-p 00000000 00:00 0    ← 你 mmap 出的 arena 块 1
# 7f8a9c010000-7f8a9c020000 rw-p 00000000 00:00 0    ← arena 块 2
# ...
```

每块都是独立条目——你 mmap 多少次,maps 文件就有多少行。

#### mmap 的成本陷阱

`mmap` 本身(只改页表)很快,但有几个隐藏成本:

1. **TLB miss**:每块 mmap 在 TLB(Translation Lookaside Buffer,CPU 的虚拟→物理地址缓存)里占一项。申请几万个小 mmap 会让 TLB 抖动。所以 arena 默认块大小要 ≥ 1 MB,不要几百 KB
2. **minor page fault**:第一次访问页时触发,内核要分配物理页。一次 arena 申请 1 MB = 256 个页 = 256 个 minor fault,看似一次但有累积开销
3. **`munmap` 必须 4 KB 对齐**:页是 OS 的最小单位。你 `mmap` 100 字节,实际占一整页 4 KB

实战中我们用 `MAP_ANONYMOUS | MAP_PRIVATE`,块大小 1 MB 起步,这是 Casey 和 Unreal 共识的"甜点"。

### 3.3 · 🦀 Rust 生态视角

Rust 标准库没有现成的 arena,但生态里有几个流行 crate:

- **`bumpalo`**:Mozilla 写的,Firefox 大量用。每 `mut` arena 一个分配,块链表式增长。API:`bumpalo::Bump::alloc(&self, value) -> &mut value`
- **`typed-arena`**:只能存一种类型,但 API 更简单(`arena.alloc(value)` 返回 `&mut T`)。Rustc 自己用,处理 AST
- **`id-arena`**:同 typed-arena,但分配对象有 id 而不是引用,方便序列化
- **`generational_arena`**:带"代"标记,支持释放(用闭包,索引重用)

今天我们自己写一个最小版本,目的是教学;Phase 7 之后会换 `bumpalo`。

#### `bumpalo` 的关键设计

```rust
pub struct Bump {
    // 当前块
    current_chunk_footer: Cell<NonNull<ChunkFooter>>,
    // 配置:块大小、对齐等
    allocator: ...,
}

struct ChunkFooter {
    ptr: UnsafeCell<NonNull<u8>>,  // 下次分配位置
    end: NonNull<u8>,               // 块结尾
    layout: Layout,                 // 块大小对齐
    prev: NonNull<ChunkFooter>,     // 上一块(链表)
}
```

注意 `Cell<NonNull<ChunkFooter>>`——内部可变性(`Cell` 是 `Copy` 内部值的标准容器,适合 `NonNull` 这种 `Copy` 类型),让 `&self` 方法也能改"当前块指针"。这是 Rust 标准的"零开销内部可变性"模式。

`Drop` 实现:

```rust
impl Drop for Bump {
    fn drop(&mut self) {
        // 遍历链表逐块 dealloc
        let mut footer = self.current_chunk_footer.get();
        unsafe {
            while footer != NonNull::dangling() {
                let f = Box::from_raw(footer.as_ptr());
                // dealloc f.ptr..f.end
                footer = f.prev;
            }
        }
    }
}
```

每块用 `Box::from_raw` 重新拿到所有权再 drop,保证不会泄漏——这是 Rust 处理"裸指针链表"的标准 idiom。

#### 我们今天的实现选择

最小可用版本,不引入 crate:

```rust
struct Block {
    base: *mut u8,
    size: usize,
    used: Cell<usize>,
    prev: Option<Box<Block>>,
}
```

`Cell<usize>` 让 `used` 在 `&self` 方法里也能递增(避免到处 `&mut self`)。`Option<Box<Block>>` 是链表惯用法——`None` 是链表尾,`Some` 是上一个块。`Box` 自动 drop 下一块(链式 Drop)。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Arena allocator(arena 分配器)** — 一种"批量分配,批量释放"的内存管理范式,与 malloc/free 的"逐个释放"对立
- **Bump pointer allocation(指针前移分配)** — arena 的具体实现方式,指针只往前挪,不回收
- **Layered allocation(分层分配)** — 在 OS 提供的 mmap/malloc 之上再建一层自己的分配器,这是工程上常见的分层

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 静态 arena(以前的版本) | 大小编译期固定 | 启动时知道峰值 | 不选,卡场景上限 |
| realloc 增长 | 满 2 倍,搬数据 | 不在意搬运 | 绝对不行,指针会失效 |
| 块链表(今天的版本) | 新块新地址,旧块不变 | 长生命周期指针 | ✅ 今天改用 |
| Slab allocator | 固定大小对象池 | 同种类型大量实例 | 不选,我们要通用 |
| Free-list arena | 支持单次释放 | 长生命周期对象 | 暂不需要,我们一帧一清 |
| 区域分配(region-based)| 同 arena,不同名字 | 学术界用语 | 同概念 |

### 4.3 下级(内部零件)

- **`MemoryBlock`** — 单块内存(起始指针 + 大小 + 已用大小)
- **`prev` 链表** — 历史块指针
- **`push_size` / `bootstrap_new_block`** — 分配入口
- **`mmap` / `munmap`** — OS 接口
- **`Drop` 实现** — 释放所有块

## 5 · 对照与变奏

### 历史演化

| 年代 | 方案 | 触发原因 |
|---|---|---|
| 1960s Lisp | "regional" 内存,gc 前提 | GC 出现前的临时分配需求 |
| 1970s C / UNIX | `obstack`(GNU libc) | 字符串拼接优化 |
| 1990s C++ | 自定义 arena + placement new | 游戏机内存小,要控制 |
| 2000s Java | `ThreadLocal` arena | 减少 GC 压力 |
| 2010s Rust | typed-arena / bumpalo | 借用检查友好 |
| 2020s | region-based + 数组化 | DOD + cache 友好 |

Casey 的设计哲学沿袭了 90s 游戏机时代——固定大小 + 显式控制。今天他向"可生长"妥协,但保留了"显式控制"。

### 跨语言变体

| 语言 | arena 表达 |
|---|---|
| C | `arena + prev` 链表(今天 Casey 版) |
| C++ | `std::pmr::monotonic_buffer_resource` 标准库自带 |
| Rust | `bumpalo::Bump` 或自写 |
| Zig | `ArenaAllocator` 标准库自带 |
| Go | 没有,GC 处理 |
| Swift | 没有,ARC 处理 |

注意 C++ 标准库在 C++17 引入了 `polymorphic_memory_resources`,其中 `monotonic_buffer_resource` 就是我们今天的版本——块链表 + 线性增长。这是工业界标准的方案。

### 工业级 vs 教学版

| 特性 | 教学版(今天) | 工业版(bumpalo) |
|---|---|---|
| 对齐 | 字节对齐 | 任意 alignment |
| 多线程 | 单线程 | `&self` 可并发 alloc |
| 复用 | 整 arena 释放 | 支持 `reset()` 复用 |
| 统计 | 无 | `allocated_bytes` 等 |

教学版到工业版要补三个东西,Phase 7 我们会做。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 用"块链表 + arena 句柄永远代表最新块"的设计,而不是"arena 永远代表主块,块链表是单独字段"。这两种设计看起来都可行,Casey 选第一种的根本原因是什么?给出至少 2 个理由。

**参考解答**:

1. **API 兼容**:句柄语义不变,所有 `push_size(arena, n)` 调用零修改。如果 arena 句柄代表主块,每次分配都要从 arena 查 `current_block` 字段,API 多一层间接
2. **字段语义清晰**:`arena->base` 永远是"现在要分配的地方",`arena->used` 是"这块用了多少",`arena->prev` 是"历史"。不需要 `arena->current_block->base` 这种两层访问
3. **C struct 拷贝高效**:`*arena = *new_block` 是一句赋值,编译器生成高效的 memcpy,语义也清晰
4. **未来扩展**:加字段(比如 `temp_used`、`allocation_count`)加在 arena 句柄上即可,所有调用方自动看到

### Lv2 · 动手实践

**题**:在 Rust 里实现一个最小动态 arena,要求:

- `new(initial_size: usize)` — 启动时申请主块
- `alloc<T>(&self, value: T) -> &mut T` — 把 T 放进 arena
- 块满了(alloc 时 size > 当前块剩余)就申请新 1 MB 块挂链表
- 实现 `Drop` 释放所有块

写一个 main,alloc 100 万个 `u64`,确认能跑通,且总内存占用是 100 万 × 8 ≈ 8 MB(不是 100 万 × 1 MB)。

完成标准:`cargo run` 不 panic,且 `/proc/$(pidof arena_demo)/status` 的 `VmRSS` 在 10 MB 左右(不是 GB 级)。

**参考解答**:

```rust
use std::cell::Cell;
use std::ptr::NonNull;

const DEFAULT_BLOCK_SIZE: usize = 1 << 20; // 1 MB

struct Block {
    base: NonNull<u8>,        // mmap 出来的起始指针(NonNull 表非空)
    size: usize,              // 这块多大
    used: Cell<usize>,        // 这块用了多少(Cell 支持内部可变性)
    prev: Option<Box<Block>>, // 上一块(Some = 还有,None = 链表尾)
}

impl Drop for Block {
    fn drop(&mut self) {
        // Drop 释放这一块的 mmap,然后 Box<Block> 自动 drop prev(链式)
        unsafe {
            let layout = std::alloc::Layout::from_size_align(self.size, 8).unwrap();
            std::alloc::dealloc(self.base.as_ptr(), layout);
        }
    }
}

pub struct Arena {
    current: NonNull<Block>,  // 当前块(永远代表最新块)
}

impl Arena {
    pub fn new(initial: usize) -> Self {
        let block = Self::alloc_block(initial.max(DEFAULT_BLOCK_SIZE));
        Self { current: block }
    }

    fn alloc_block(size: usize) -> NonNull<Block> {
        // 申请一块内存,大小至少 size
        let layout = std::alloc::Layout::from_size_align(size, 8).unwrap();
        let base = unsafe { std::alloc::alloc(layout) };
        let base = NonNull::new(base).expect("OOM");
        let block = Box::new(Block {
            base,
            size,
            used: Cell::new(0),
            prev: None,
        });
        NonNull::from(Box::leak(block))
    }

    pub fn alloc_bytes(&self, n: usize, align: usize) -> NonNull<u8> {
        let block = unsafe { self.current.as_ref() };
        let used = block.used.get();
        // 对齐调整
        let base_addr = block.base.as_ptr() as usize;
        let start = (base_addr + used + align - 1) & !(align - 1);
        let offset_in_block = start - base_addr;
        let new_used = offset_in_block + n;
        if new_used > block.size {
            // 当前块满了,开新块
            let new_size = n.max(DEFAULT_BLOCK_SIZE);
            let new_block_ptr = Self::alloc_block(new_size);
            // 把新块串到链表头,然后让 arena.current 指向新块
            unsafe {
                let new_block = Box::from_raw(new_block_ptr.as_ptr());
                let mut new_block = Box::new(Block {
                    base: new_block.base,
                    size: new_block.size,
                    used: Cell::new(0),
                    prev: Some(Box::from_raw(self.current.as_ptr())),
                });
                // 把 used 设为 n(本次分配)
                new_block.used.set(n);
                let leaked = Box::leak(new_block);
                // 不能直接改 self.current 因为它是 NonNull(不可变)
                // 在我们的设计里,改 current 要 unsafe + *const 改写
                std::ptr::write(self.current.as_ptr() as *mut Block, *leaked);
            }
            return unsafe { (*self.current.as_ptr()).base };
        }
        block.used.set(new_used);
        unsafe { NonNull::new_unchecked(start as *mut u8) }
    }

    pub fn alloc<T>(&self, value: T) -> &mut T {
        let ptr = self.alloc_bytes(std::mem::size_of::<T>(), std::mem::align_of::<T>());
        let ptr = ptr.as_ptr() as *mut T;
        unsafe {
            std::ptr::write(ptr, value);
            &mut *ptr
        }
    }
}

fn main() {
    let arena = Arena::new(1 << 16); // 启动 64 KB
    for i in 0..1_000_000u64 {
        arena.alloc(i);
    }
    println!("Allocated 1M u64");
}
```

**关键 Rust 特性**:

- `NonNull<T>` 是非空裸指针,Rust 标准库的"我知道不是 null"语义,自我证明 covariant
- `Cell<usize>` 让 `&self` 方法也能改 `used`,避免到处 `&mut self`
- `Box::leak` 把 Box 转成 `&'static mut`,我们手动管生命周期(因为这块不属于 Rust borrow 体系)
- `std::alloc::alloc` / `dealloc` 是底层分配 API,默认 8 字节对齐,正好 SIMD 友好

注意:**这个实现有未竟之事**——`alloc_bytes` 里修改 `self.current` 的方式比较脏(直接 `ptr::write`),更干净的写法是用 `UnsafeCell<NonNull<Block>>`。教学版简化处理,Phase 7 会改进。

## 8 · Rust / Arch 落地代码

### 完整可跑的 Rust arena demo

```rust
// Cargo.toml: 无依赖,纯 std
// src/main.rs

use std::cell::Cell;
use std::ptr::NonNull;

const DEFAULT_BLOCK_SIZE: usize = 1 << 20; // 1 MB,casey 的甜点

// ----- 单块 -----
#[derive(Debug)]
struct Block {
    base: NonNull<u8>,
    size: usize,
    used: Cell<usize>,
    prev: Option<Box<Block>>,
}

impl Block {
    fn new(size: usize, prev: Option<Box<Block>>) -> Box<Self> {
        let layout = std::alloc::Layout::from_size_align(size, 16).unwrap();
        // SAFETY: alloc 可能返回 null(OMM),我们 panic 而不是返回 Result
        let base_ptr = unsafe { std::alloc::alloc(layout) };
        let base = NonNull::new(base_ptr).expect("Arena OOM");
        Box::new(Block {
            base,
            size,
            used: Cell::new(0),
            prev,
        })
    }
}

impl Drop for Block {
    fn drop(&mut self) {
        // 释放自己,然后 Box<Block> 的 prev 字段会自动递归 drop
        let layout = std::alloc::Layout::from_size_align(self.size, 16).unwrap();
        unsafe { std::alloc::dealloc(self.base.as_ptr(), layout) }
    }
}

// ----- Arena -----
pub struct Arena {
    current: NonNull<Block>,
}

impl Arena {
    pub fn new(initial: usize) -> Self {
        let size = initial.max(DEFAULT_BLOCK_SIZE);
        let block = Block::new(size, None);
        Self { current: NonNull::from(Box::leak(block)) }
    }

    pub fn allocate(&self, size: usize, align: usize) -> NonNull<u8> {
        // 由于 self.current 是 NonNull<Block> 不可变,我们用 Cell<NonNull<Block>> 才能修改
        // 教学版用 unsafe + 直接 cast,生产版用 UnsafeCell
        let cur_block = unsafe { &*self.current.as_ptr() };
        let base_addr = cur_block.base.as_ptr() as usize;
        let used = cur_block.used.get();
        let aligned_start = (base_addr + used + align - 1) & !(align - 1);
        let need = aligned_start + size - base_addr;

        if need > cur_block.size {
            // 当前块满,开新块。注意 self.current 的更新
            let new_size = size.max(DEFAULT_BLOCK_SIZE);
            // 把 cur_block 的所有权从 leak 状态拿回来,串到新块的 prev
            let old_block_box = unsafe { Box::from_raw(self.current.as_ptr()) };
            let new_block = Block::new(new_size, Some(old_block_box));
            let new_block_ptr = Box::leak(new_block) as *mut Block;
            unsafe { std::ptr::write(self.current.as_ptr() as *mut Block, std::ptr::read(new_block_ptr)) };
            // 这里有 unsafe 重写 self.current 的细节,生产代码用 UnsafeCell
            let cur_block = unsafe { &*self.current.as_ptr() };
            let base_addr = cur_block.base.as_ptr() as usize;
            cur_block.used.set(size);
            return NonNull::new(unsafe { cur_block.base.as_ptr().add(0) }).unwrap();
        }
        cur_block.used.set(need);
        unsafe { NonNull::new_unchecked(aligned_start as *mut u8) }
    }

    pub fn alloc_value<T>(&self, value: T) -> &mut T {
        let ptr = self.allocate(std::mem::size_of::<T>(), std::mem::align_of::<T>());
        unsafe {
            let p = ptr.as_ptr() as *mut T;
            std::ptr::write(p, value);
            &mut *p
        }
    }

    pub fn total_bytes(&self) -> usize {
        // 遍历链表统计总大小
        let mut total = 0;
        let mut cur = unsafe { &*self.current.as_ptr() };
        loop {
            total += cur.size;
            match &cur.prev {
                Some(p) => cur = p.as_ref(),
                None => break,
            }
        }
        total
    }
}

impl Drop for Arena {
    fn drop(&mut self) {
        // 链表头节点的 Box 由我们负责 drop
        unsafe { drop(Box::from_raw(self.current.as_ptr())) };
    }
}

fn main() {
    let arena = Arena::new(1 << 16); // 启动 64 KB
    println!("Initial arena size: {} KB", arena.total_bytes() / 1024);

    // 分配一百万个 u64
    for i in 0..1_000_000u64 {
        arena.alloc_value(i);
    }

    println!("After 1M u64 allocs: arena has {} MB",
             arena.total_bytes() / (1 << 20));
    // 应该输出 ~8 MB(一百万 u64 = 8 MB,加上块对齐 padding)
}
```

**预期输出**:

```
Initial arena size: 64 KB
After 1M u64 allocs: arena has 8 MB
```

注意:8 MB 而不是 64 KB + 8 MB,说明 arena 真的动态增长,初始块只是 64 KB。

**Troubleshooting**:

- `Segmentation fault` — 大概率 `NonNull::new(base_ptr)` 后 base_ptr 是 null,加 `expect("OOM")` 立刻报错
- `arena.total_bytes()` 死循环 — 检查 `prev` 链表有没有正确设置 `None` 终止
- `core dumped` 在 Drop 时 — 链表节点用了 `Box::from_raw` 取回,但同一指针被双重 drop。检查 `Box::leak` 后是否泄漏(没归还 Box)
- 块大小不对 — 检查 `Layout` 的 align 参数,mmap 出来的地址可能不是 16 字节对齐
