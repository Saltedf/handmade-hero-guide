
# Day 418 · 随时间平滑光照样本

> 矩形面积光用 4 个采样,直接出图——阴影边缘有噪点。提高采样数到 64,干净了,但帧率掉到 5 FPS。今天 Casey 用**时序累积(temporal accumulation)**:每帧只用 4 个采样,但和上一帧的结果加权平均,16 帧后等效 64 采样,人眼几乎看不出噪点。

## 0 · 为什么要有这一天

光照采样是个**统计问题**。每帧你做 N 个随机采样,得到的亮度是真实亮度的**估计值**。N 小,估计不准——画面出现噪点(随机波动)。N 大,估计准——画面干净,但成本高。

工业的巧妙做法:**采样位置随时间变化**。第 1 帧采 (0.1, 0.1), 第 2 帧采 (0.6, 0.3), 第 3 帧采 (0.2, 0.7) ...。如果你对每个像素保留**过去 K 帧的累积**,K 帧后你有了 K×N 个不同的采样,平均起来等效 K×N 个采样,但每帧只算 N 个。

这就是**时序累积**,工业叫 TAA(Temporal Anti-Aliasing)的弟弟。TAA 用 1 个采样,8 帧累积看起来像 8x MSAA。

但有时序累积有个**致命问题**:**物体移动时,旧帧的累积是错的**。如果你的角色往前走了一步,他原本遮挡的墙面露出来了——这面墙在上一帧是被遮挡的,累积值是 0,直接平均会有一帧"暗斑"。工业叫**ghosting artifact**。

解决 ghosting 的标准方法:**reprojection**——把上一帧的像素位置根据物体运动"投射"到当前帧,如果投不到(被遮挡或新出现),抛弃旧累积。Casey 今天做简化版:**指数衰减平均**,不做 reprojection,接受少量 ghosting。

心理锚点:今天之后,你能解释 TAA 的工作原理,知道为什么现代游戏都用 TAA,能用 Rust 实现时序累积,理解"时序"在图形学里的核心地位。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 在体素光照网格上加了一个**历史缓冲**:

```c
voxel_lighting_current[frame_id % 2]
voxel_lighting_previous[(frame_id + 1) % 2]
```

每帧的更新:

1. 算当前帧光照 `current`
2. 与上一帧加权平均:`smoothed = lerp(previous, current, alpha)`
3. 把 `smoothed` 写入 `current`,供下一帧用
4. `alpha` 取 0.1,意味着 10 帧等效 1 个新采样

他用了**双缓冲**:两个相同的体素网格,交替读写。这避免了"读到正在写的同一帧"的竞争。

Casey 强调**alpha 的权衡**:alpha 小,平滑好,但物体移动时 ghosting 严重(旧帧残留时间长);alpha 大,平滑差,但响应快。他试了几个值,选 0.2 作为平衡点。

## 2 · 心智模型

### 类比:温水煮青蛙式平均

想象你在测水温。水温有微小波动(水管震动),你想知道"平均水温"。两种方法:

- **单次测量**:测一次。简单,但波动让你的读数跳来跳去。
- **多次平均**:测 N 次,平均。准,但要等。
- **指数衰减平均**(本日):每测一次,新读数 = 0.9 × 旧读数 + 0.1 × 当前值。10 次测量后,旧读数只占 0.9^10 ≈ 35%,新读数累积成主要部分。

指数衰减平均的优点:**不需要存历史**。只存"上一个平均",实时更新。每帧的 alpha 控制平滑强度。

数学上,指数衰减平均的"等效样本数"是 1/alpha。alpha = 0.1,等效 10 帧;alpha = 0.02,等效 50 帧。

### 严谨原理:指数移动平均(EMA)

公式:

```
y[t] = α * x[t] + (1 - α) * y[t-1]
```

- `x[t]`:第 t 帧的新观测
- `y[t-1]`:上一帧的累积值
- `y[t]`:当前累积值
- `α`:平滑系数,∈ (0, 1]

α = 1 时,无累积,直接用新值(单采样)。
α → 0 时,几乎不更新,极端平滑。

α 决定**响应速度**(对新变化的反应)和**平滑强度**(滤噪能力)。两者矛盾——响应快必然噪点重,平滑必然响应慢。

### 时序累积的方差

如果每帧采样 N 次,每帧方差 σ²。时序累积后,等效采样数 ≈ N/α,等效方差 ≈ σ² × α。

α = 0.1,N = 4 时:等效 40 个采样,方差缩小到 1/10。视觉上噪点大幅减少。

### Ghosting 的成因

物体移动时,**像素的"看到的东西"改变了**。具体:

- 第 t 帧:像素 P 看到红色墙面,光照 = 1.0
- 第 t+1 帧:角色走过,像素 P 看到蓝色角色,光照 = 0.5

如果直接 EMA:y[t+1] = 0.9 * 1.0 + 0.1 * 0.5 = 0.95。但**真值是 0.5**(像素现在看到蓝色)。误差 0.45,视觉上是"角色身上有个红色残影",这就是 ghosting。

工业解决:**检测像素运动**,如果运动大,抛弃旧累积(α = 1)。检测方法:用 motion vector(像素的 2D 运动量),motion vector 大,说明物体移动,reset。

Casey 不做 motion vector,接受少量 ghosting。光照场景物体移动少(墙、地板静止),ghosting 不严重。day430 多线程光照时再优化。

### Rust 视角

```rust
pub struct TemporalAccumulator {
    pub history: VoxelGrid,   // 上一帧累积
    pub current: VoxelGrid,   // 当前帧
    pub alpha: f32,           // 平滑系数
}

impl TemporalAccumulator {
    pub fn update(&mut self, new_lighting: &VoxelGrid) {
        // y[t] = α * x[t] + (1-α) * y[t-1]
        for i in 0..self.current.data.len() {
            let prev = self.history.data[i];
            let new = new_lighting.data[i];
            self.current.data[i] = new * self.alpha + prev * (1.0 - self.alpha);
        }
        // swap: 当前帧变成下一帧的历史
        std::mem::swap(&mut self.history, &mut self.current);
    }
}
```

`std::mem::swap` 是零拷贝交换两个 Vec——只交换内部指针。Rust ownership 保证交换后双方都有效。

### 双缓冲

```rust
pub struct DoubleBufferedGrid {
    pub buffers: [VoxelGrid; 2],
    pub current_index: usize,
}

impl DoubleBufferedGrid {
    pub fn current(&self) -> &VoxelGrid { &self.buffers[self.current_index] }
    pub fn previous(&self) -> &VoxelGrid { &self.buffers[1 - self.current_index] }
    pub fn current_mut(&mut self) -> &mut VoxelGrid { &mut self.buffers[self.current_index] }
    pub fn swap(&mut self) { self.current_index = 1 - self.current_index; }
}
```

`current_index` 在 0 和 1 之间切换。`previous()` 用 `1 - current_index`。这是图形学最常见的模式之一,叫 **ping-pong buffers**。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业时序方法:

- **TAA(Temporal Anti-Aliasing)**:每像素 1 采样 + 历史累积 + motion vector
- **DLSS / FSR**:用神经网络做时序上采样,4 倍分辨率
- **SGE(Spatial Gradient Estimation)**:实时反射,时序累积
- **LPV(Light Propagation Volumes)**:间接光,时序累积

TAA 是现代游戏的标配——几乎所有 2018 年后的 3A 游戏都用 TAA 替代 MSAA。原因:TAA 成本极低(每像素几条指令),效果好,且兼容延迟渲染。

### 3.2 · 🎨 图形学视角

时序累积的数学基础:**蒙特卡洛积分 + importance sampling over time**。把积分的样本分散到多帧,用时间换空间。

但有时间bug:**albedo flickering**(材质颜色闪烁),**specular ghosting**(高光残影),**stationary movement**(静止场景里偶尔抖动)。TAA 是个有副作用的工具,工业用各种 hack 抑制副作用(blur、sharpen、clamping)。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的 EMA:

- **load average**(1/5/15 分钟负载):指数移动平均,内核持续更新
- **TCP RTT 估计**:平滑往返时间,EMA
- **CPU frequency governor**:平滑频率

EMA 在系统编程里无处不在。Casey 的光照 EMA 和 load average 完全同构——都是平滑时间序列。

### 3.4 · 🦀 Rust 生态视角

Rust 的并发 EMA:

```rust
use std::sync::atomic::{AtomicU32, Ordering};
use std::sync::atomic::fence;

pub struct AtomicEma {
    // 用 u32 存 f32 的位模式
    bits: AtomicU32,
    alpha_bits: u32,
}

impl AtomicEma {
    pub fn new(initial: f32, alpha: f32) -> Self {
        Self {
            bits: AtomicUma::new(initial.to_bits()),
            alpha_bits: alpha.to_bits(),
        }
    }

    pub fn update(&self, new: f32) -> f32 {
        // CAS 循环
        loop {
            let prev_bits = self.bits.load(Ordering::Relaxed);
            let prev = f32::from_bits(prev_bits);
            let alpha = f32::from_bits(self.alpha_bits);
            let next = alpha * new + (1.0 - alpha) * prev;
            let next_bits = next.to_bits();
            if self.bits.compare_exchange_weak(
                prev_bits, next_bits,
                Ordering::Relaxed, Ordering::Relaxed,
            ).is_ok() {
                return next;
            }
        }
    }
}
```

CAS 循环(Compare-And-Swap)是多线程无锁更新的标准方法。Rust 的 `AtomicU32` + `compare_exchange_weak` 提供硬件原语,无锁更新 EMA。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 α = 0.1 比直接 64 采样便宜得多?具体说,α = 0.1 等效多少采样?

**参考解答**:α = 0.1 时,每帧用 0.1 权重的当前帧 + 0.9 权重的历史累积。10 帧后,历史累积里有 10 个不同帧的样本,等效 10 个采样。如果每帧本身是 4 个采样,总等效 = 4 × 10 = 40 个采样。

实际计算成本:每帧只算 4 个新采样 + 1 次像素级 lerp(便宜)。所以**等效 40 个采样的成本 = 4 个采样 + lerp**,远低于直接 40 个采样。

α = 0.1 时,旧样本权重 0.9^N,大约 22 帧后衰减到 10%。所以**实际等效样本数 ≈ 1/α = 10**(更精确,因为指数衰减)。

```rust
use glam::Vec3;

pub struct VoxelGrid {
    pub dims: (usize, usize, usize),
    pub data: Vec<Vec3>,
}

impl VoxelGrid {
    pub fn new(dims: (usize, usize, usize)) -> Self {
        Self { dims, data: vec![Vec3::ZERO; dims.0 * dims.1 * dims.2] }
    }
}

pub struct TemporalAccumulator {
    pub history: VoxelGrid,
    pub current: VoxelGrid,
    pub alpha: f32,
}

impl TemporalAccumulator {
    pub fn new(dims: (usize, usize, usize), alpha: f32) -> Self {
        Self {
            history: VoxelGrid::new(dims),
            current: VoxelGrid::new(dims),
            alpha,
        }
    }

    pub fn update<F>(&mut self, mut compute_frame: F)
    where F: FnMut(&mut VoxelGrid) {
        // Phase 1: 算当前帧新光照,写入 current
        compute_frame(&mut self.current);

        // Phase 2: EMA,与 history 混合
        for (cur, hist) in self.current.data.iter_mut().zip(self.history.data.iter()) {
            *cur = *cur * self.alpha + *hist * (1.0 - self.alpha);
        }

        // Phase 3: swap,current 变成下一帧的 history
        std::mem::swap(&mut self.history, &mut self.current);
    }

    pub fn result(&self) -> &VoxelGrid {
        &self.history
    }
}

fn main() {
    let mut acc = TemporalAccumulator::new((4, 4, 4), 0.1);
    let mut frame = 0;

    // 模拟 20 帧,每帧采样的光照是 1.0 + 噪声
    for _ in 0..20 {
        acc.update(|grid| {
            // 模拟 4 个采样,带噪声
            for v in grid.data.iter_mut() {
                let noise = (frame as f32 * 17.0).sin() * 0.5;  // 假"随机"
                *v = Vec3::splat(1.0 + noise);
            }
        });
        let avg = acc.result().data[0].x;
        println!("Frame {}: avg = {:.3}", frame, avg);
        frame += 1;
    }
}
```

```rust
use glam::Vec3;

#[derive(Clone)]
pub struct VoxelGrid {
    pub dims: (usize, usize, usize),
    pub data: Vec<Vec3>,
}

impl VoxelGrid {
    pub fn new(dims: (usize, usize, usize)) -> Self {
        Self { dims, data: vec![Vec3::ZERO; dims.0 * dims.1 * dims.2] }
    }

    pub fn fill_with_noise(&mut self, frame: u32) {
        // 模拟随机采样的光照,带噪声
        let noise = (frame as f32 * 7.0).sin() * 0.3;
        for v in self.data.iter_mut() {
            *v = Vec3::splat(1.0 + noise);
        }
    }
}

pub struct TemporalAccumulator {
    history: VoxelGrid,
    current: VoxelGrid,
    pub alpha: f32,
}

impl TemporalAccumulator {
    pub fn new(dims: (usize, usize, usize), alpha: f32) -> Self {
        Self {
            history: VoxelGrid::new(dims),
            current: VoxelGrid::new(dims),
            alpha,
        }
    }

    pub fn update_with_frame(&mut self, frame: u32) {
        // Phase 1: 算当前帧新光照
        self.current.fill_with_noise(frame);

        // Phase 2: EMA
        // 用迭代器 zip 同时遍历两个 Vec
        for (cur, hist) in self.current.data.iter_mut().zip(self.history.data.iter()) {
            // y[t] = α * x[t] + (1-α) * y[t-1]
            *cur = *cur * self.alpha + *hist * (1.0 - self.alpha);
        }

        // Phase 3: swap
        std::mem::swap(&mut self.history, &mut self.current);
    }

    pub fn result(&self) -> &VoxelGrid { &self.history }
}

fn main() {
    println!("=== α = 1.0 (无累积,完全用新值) ===");
    let mut acc = TemporalAccumulator::new((4, 4, 4), 1.0);
    for f in 0..10 {
        acc.update_with_frame(f);
        println!("  Frame {}: value = {:.3}", f, acc.result().data[0].x);
    }

    println!("\n=== α = 0.1 (强平滑) ===");
    let mut acc = TemporalAccumulator::new((4, 4, 4), 0.1);
    for f in 0..10 {
        acc.update_with_frame(f);
        println!("  Frame {}: value = {:.3}", f, acc.result().data[0].x);
    }
}
```

**Troubleshooting**:

- **Ghosting 严重** —— α 调大(0.3-0.5),牺牲平滑
- **噪点重** —— α 调小(0.05-0.1)
- **首帧值异常** —— history 初始化为 0,首帧被 0 拖低;可初始化为当前帧

- **f32 精度问题** —— 累积很多帧后,小变化被淹没;周期性 reset


### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
