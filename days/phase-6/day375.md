# Day 375 · 加基于距离的雾

> 你的场景有地板、墙、立方体,但远处毫无氛围感——所有距离的物体颜色饱和度一样。今天 Casey 加 **distance fog(基于距离的雾)**:远处物体逐渐融入背景色,产生大气透视,场景立即有"立体感"。

## 0 · 为什么要有这一天

你的游戏画面"对",但**没有氛围**。所有距离的物体看起来一样清楚,没有"远近"的感觉。真实世界不是这样——远处物体被空气中的水汽、灰尘遮蔽,看起来**逐渐变白(或蓝灰)模糊**。这种视觉效果叫 **atmospheric perspective(大气透视)**,达芬奇在《蒙娜丽莎》的背景里就用了。

游戏里模拟这种效果的技术叫 **fog(雾)**。雾的本质:**像素颜色 = 物体颜色 × (1 - 雾强度) + 雾颜色 × 雾强度**。雾强度从 0(无雾)到 1(完全雾),按距离递增。

雾的几个用途:
1. **氛围**:远处朦胧,场景有深度感
2. **隐藏 LOD 切换**:远处用低 LOD 模型,雾遮住切换突变
3. **隐藏远裁面**:相机 far plane 之外的不渲染,雾把接近 far plane 的物体溶进背景,避免突然消失
4. **天气效果**:水下 / 沙暴 / 浓雾场景

**为什么"基于距离"**?基于距离(distance-based)的雾用像素到相机的距离作为雾强度参数。简单高效。其他雾:
- **基于高度**(height fog):雾在低海拔,高处清晰(模拟云海)
- **基于体积**(volume fog):雾在某个 3D 区域,需要 ray marching,复杂
- **基于光照**(light-based fog):雾被光照(crepuscular rays / god rays),需要后处理

Casey 今天做**基于距离的线性 / 指数雾**,最简单也最常用。

**实现位置**:fragment shader 末尾。算出像素颜色后,根据 fragment 到相机距离算雾强度,混合雾颜色。

心理锚点:今天之后,你能实现工业级 distance fog,理解混合(blend)的数学,知道 shader 里怎么获取相机距离。

## 1 · Casey 今天做了什么(HH 脉络)

Day 374 调试完 Z 变换后,Casey 决定加视觉效果。选择 fog 的原因:

1. **简单**:fragment shader 几行代码,无新 API
2. **效果明显**:视觉立刻有"层次"
3. **为后面铺路**:Day 389 光照、Day 400 环境光遮蔽都涉及类似的颜色混合

具体动作:

1. **fragment shader 加 fog 计算**:输入 camera world pos + fragment world pos,算距离,根据距离算雾强度
2. **shader uniform 上传**:雾颜色、雾起始距离、雾结束距离
3. **线性 vs 指数 fog**:Casey 选线性(更可控),但代码里支持切换到指数
4. **debug overlay 加 fog 参数调节**:运行时调 fog start/end/color

Casey 在 shader 里写的核心代码:

```glsl
// fragment shader:
uniform vec3 u_camera_pos;
uniform vec3 u_fog_color;
uniform float u_fog_start;
uniform float u_fog_end;

in vec3 v_world_pos;
out vec4 frag_color;

void main() {
    vec3 base_color = /* 计算 */;
    float dist = length(v_world_pos - u_camera_pos);

    // 线性雾:0 在 start,1 在 end,clamp 到 [0, 1]
    float fog_factor = clamp((dist - u_fog_start) / (u_fog_end - u_fog_start), 0.0, 1.0);

    // 混合
    vec3 final_color = mix(base_color, u_fog_color, fog_factor);
    frag_color = vec4(final_color, 1.0);
}
```

Casey 用 `mix(a, b, t)` 函数,它就是 `a * (1-t) + b * t`,GLSL 内置。

## 2 · 心智模型

### 类比:雾是"空气的吸收和散射"

想象你在森林里看远方。远处一棵树的光线传到你眼睛,途中被空气中的水滴、灰尘**部分吸收和散射**。结果:从树到你的光一部分丢失,被空气里的光(主要是天空蓝、太阳光散射)替代。距离越远,丢失越多,空气替代越多。

数学上:

```
到达你眼睛的光 = 树的光 × 透过率 + 空气光 × (1 - 透过率)
                  ↑ 物体颜色       ↑ 雾颜色
```

透过率(transmittance)随距离指数衰减(比尔朗伯定律):

```
透过率 = exp(-density * distance)
```

简化游戏实现常用**线性近似**(start 距离开始有雾,end 距离完全雾):

```
雾强度 = (distance - start) / (end - start),限制在 [0, 1]
```

线性雾在远处"硬切",但视觉上可接受。指数雾更"自然",但参数难调。

### 线性 vs 指数雾

**线性雾**(glFog GL_LINEAR,旧 OpenGL API):

```glsl
float fog_factor = clamp((dist - fog_start) / (fog_end - fog_start), 0.0, 1.0);
```

```
雾强度
  1.0 ┤                          ╱─────
      │                        ╱
      │                      ╱
      │                    ╱
      │                  ╱
  0.0 ┼─────────────────
      └─┬───────────────┬───── distance
       start           end
```

特点:简单,start / end 控制雾的"开始"和"完全"距离。

**指数雾**(GL_EXP):

```glsl
float fog_factor = 1.0 - exp(-density * dist);
```

```
雾强度
  1.0 ┤                              ╱
      │                          ╱
      │                      ╱
      │                  ╱
      │             ╱
  0.0 ┼────────
      └─┬─────────────────────── distance
        0
```

特点:更接近物理(比尔朗伯),density 控制雾"浓度"。

**平方指数雾**(GL_EXP2):

```glsl
float fog_factor = 1.0 - exp(-pow(density * dist, 2.0));
```

特点:近处雾更淡,远处变化更剧烈。视觉上"空气感"更强。

Casey 用线性(简单直观),但代码注释里提到指数的写法。

### Fragment Shader 里怎么获取距离

需要 fragment 在**世界空间的位置**。两种获取方式:

**方式 1:vertex shader 输出 v_world_pos**

```glsl
// vertex shader:
out vec3 v_world_pos;
uniform mat4 u_model;

void main() {
    vec4 world_pos = u_model * vec4(a_pos, 1.0);
    v_world_pos = world_pos.xyz;
    gl_Position = u_mvp * vec4(a_pos, 1.0);
}

// fragment shader:
in vec3 v_world_pos;
uniform vec3 u_camera_pos;

void main() {
    float dist = length(v_world_pos - u_camera_pos);
    // ...
}
```

**方式 2:从 gl_FragCoord 反推**

```glsl
// fragment shader:
uniform mat4 u_inv_view_proj;

void main() {
    vec4 world_pos = u_inv_view_proj * vec4(gl_FragCoord.xyz, 1.0);
    world_pos /= world_pos.w;
    float dist = length(world_pos.xyz - u_camera_pos);
}
```

方式 1 更高效(只在 vertex shader 算一次,fragment shader 插值用)。Casey 用方式 1。

### 混合(Blend)的数学

```glsl
vec3 final_color = mix(base_color, fog_color, fog_factor);
```

`mix(a, b, t) = a * (1-t) + b * t`。

fog_factor = 0:final = base(无雾)
fog_factor = 1:final = fog_color(完全雾)
fog_factor = 0.5:final = (base + fog) / 2

**注意**:混合必须**在线性空间**。如果 base_color 是 sRGB,fog_color 是 sRGB,直接 mix 不准。正确做法:
1. base_color 和 fog_color 解码到线性
2. mix 在线性空间
3. 编码回 sRGB

如果硬件 framebuffer_sRGB 启用(Day 370),fragment shader 输出时 GPU 自动编码到 sRGB,但 mix 内部应该在线性做。Casey 在 shader 末尾 `pow(color, 1/2.2)` (如果 fallback 模式),自动处理。

### Rust 视角:Fog 参数管理

```rust
pub struct FogParams {
    pub color: Vec3,        // 雾颜色(线性空间)
    pub start: f32,         // 起始距离
    pub end: f32,           // 完全雾距离
    pub enabled: bool,
}

impl FogParams {
    pub fn apply_to_shader(&self, shader: &Shader) {
        shader.use_program();
        shader.set_uniform_3f("u_fog_color", self.color);
        shader.set_uniform_1f("u_fog_start", self.start);
        shader.set_uniform_1f("u_fog_end", self.end);
        shader.set_uniform_1i("u_fog_enabled", if self.enabled { 1 } else { 0 });
    }
}
```

### 3.1 · 🎮 游戏编程视角

游戏工业的雾:

- **Silent Hill 2**(2001):浓雾掩盖 PS2 远裁面限制,反而成了艺术风格

**雾的工程意义**:

2. **LOD 隐藏**:远处用低 LOD mesh(简化几何),雾让 LOD 切换不明显
3. **Streaming**:大世界 chunk 加载,雾遮盖加载边界
4. **氛围**:恐怖游戏浓雾 / 战争游戏硝烟 / 科幻游戏虚空感

**实现层级的雾**:

| 层级 | 实现 | 复杂度 |
|---|---|---|
| Shader 内 fog | fragment shader 几行 | 简单,Casey 用 |
| 后处理 fog | 单独 pass,从 depth buffer 反推距离 | 中等,灵活 |
| 体积雾 | ray marching / voxel grid | 复杂,AA 级 |
| 光照雾 | crepuscular rays,后处理 | 复杂 |

### 3.2 · 🎨 图形学视角

雾在图形学上的几个深层概念:

**Beer-Lambert Law(比尔朗伯定律)**

物理上光穿过介质的衰减:

```
I_out = I_in * exp(-σ * d)
```

σ 是消散系数(与介质密度成正比),d 是光程。这是**指数雾**的物理基础。

更精细的模型(**Lambertian + 单次散射**):

```
L_out = L_in * exp(-σd) + ∫ σ * L_sun * exp(-σ(x_to_sun)) dx
                                 ↑ 散射到视线方向的光
```

积分项复杂,工业用近似(ray marching / voxel)。

**颜色 vs 大气**

雾的颜色不一定是白色:
- **晴天雾**:偏白(散射太阳光)
- **阴天雾**:偏灰(散射云光)
- **黄昏雾**:偏橙(散射长波长光)
- **高空俯视**:偏蓝(瑞利散射)

工业 PBR 引擎计算雾颜色用**天空盒采样** + **太阳方向**:

```glsl
vec3 fog_color = texture(skybox, view_dir).rgb * sun_attenuation;
```

这让雾颜色随天气和时间变化。

**Fog vs Depth of Field(景深)**

雾是"远处模糊颜色",景深是"远处模糊但保留细节"。两者不同:
- 雾:用雾色替换,丢失物体颜色
- DoF:模糊物体颜色,不替换

现代游戏两者都用,雾给"远距离"感觉,DoF 给"焦点"效果。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上雾的实现完全在 GPU shader,不涉及系统调用。但有几个性能细节:

**Shader 优化**

```glsl
// 优化前:用 length (sqrt)
float dist = length(v_world_pos - u_camera_pos);

// 优化后:用 dot(length^2)用于比较
float dist_sq = dot(diff, diff);
float fog_factor = clamp((dist_sq - fog_start_sq) / (fog_end_sq - fog_start_sq), 0.0, 1.0);
// 避免 sqrt,直接用距离平方
```

对于线性雾,可以省 sqrt(雾参数也用平方)。指数雾必须 sqrt,因为 exp。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么雾的颜色混合必须在线性空间?如果直接在 sRGB 空间 mix(base_color, fog_color, 0.5),结果会怎样?

**参考解答**:sRGB 是非线性编码,gamma 2.2 近似。在 sRGB 空间做 mix(0.5) 实际混合的"光强"不是 50%。具体:
- base_color sRGB = 0.5,对应线性光强 ≈ 0.218
- fog_color sRGB = 1.0,对应线性光强 = 1.0
- 在 sRGB 空间 mix:(0.5 + 1.0) / 2 = 0.75 sRGB
- 在线性空间 mix:0.218 + (1.0 - 0.218) × 0.5 = 0.609 线性 → 0.792 sRGB

差别约 5%,肉眼可见。线性空间混合更"自然",sRGB 空间混合雾看起来比预期浓。

工业做法:fragment shader 内部全线性计算(包括 fog mix),最后 framebuffer_sRGB 自动编码回 sRGB。

### Lv2 · 动手实践

**题**:在 fragment shader 末尾加 distance fog,支持运行时调节 fog start/end/color。完成标准:
- debug overlay 显示 fog 参数,可调
- 立方体远处变雾色,近处清晰
- 雾效果在线性空间混合(可选 fallback 模式)

**参考解答**:

```glsl
// fragment shader
#version 330 core

in vec3 v_world_pos;
in vec3 v_normal;
in vec2 v_uv;

out vec4 frag_color;

uniform vec3 u_camera_pos;
uniform sampler2D u_texture;
uniform vec3 u_light_dir;

uniform vec3 u_fog_color;        // 线性空间的雾色
uniform float u_fog_start;
uniform float u_fog_end;
uniform int u_fog_enabled;

void main() {
    // 基础颜色(纹理)
    vec3 base = texture(u_texture, v_uv).rgb;

    // 假设这是 sRGB 纹理,转线性(如果硬件不自动做)
    base = pow(base, vec3(2.2));

    // Lambert 光照(线性空间)
    vec3 N = normalize(v_normal);
    vec3 L = normalize(u_light_dir);
    float diff = max(0.0, dot(N, L));
    base *= diff * 0.8 + 0.2;  // ambient + diffuse

    // 雾
    vec3 color = base;
    if (u_fog_enabled != 0) {
        float dist = length(v_world_pos - u_camera_pos);
        float fog_factor = clamp((dist - u_fog_start) / (u_fog_end - u_fog_start), 0.0, 1.0);

        // 线性空间混合(因为 base 和 fog_color 都已转线性)
        color = mix(base, u_fog_color, fog_factor);
    }

    // 转回 sRGB(如果硬件不自动做)
    color = pow(color, vec3(1.0 / 2.2));

    frag_color = vec4(color, 1.0);
}
```

**Rust 端上传 uniform**:

```rust
let fog = FogParams {
    color: Vec3::new(0.7, 0.8, 0.9),  // 浅蓝灰
    start: 20.0,
    end: 80.0,
    enabled: true,
};

shader.use_program();
shader.set_uniform_3f("u_fog_color", fog.color);
shader.set_uniform_1f("u_fog_start", fog.start);
shader.set_uniform_1f("u_fog_end", fog.end);
shader.set_uniform_1i("u_fog_enabled", if fog.enabled { 1 } else { 0 });
shader.set_uniform_3f("u_camera_pos", camera.pos);
```

**关键解释**:
- `length(vec)` — GLSL 内置向量长度,等价 sqrt(dot(v,v))
- `clamp(x, min, max)` — 钳制函数,fog_factor 不超过 [0, 1]
- `mix(a, b, t)` — 等价 `a * (1-t) + b * t`
- 雾计算在所有光照后,最后输出前

### Lv3 · 迁移设计

```glsl
float height_fog = clamp((u_fog_max_height - v_world_pos.y) / (u_fog_max_height - u_fog_min_height), 0.0, 1.0);
```

### Rust:完整 distance fog 实现

```rust
// Cargo.toml: gl = "0.14", glfw = "0.55", glam = "0.29", bytemuck = "1.14"

use gl::types::*;
use glam::{Mat4, Vec3};
use std::ffi::CString;

pub struct FogParams {
    pub color: Vec3,
    pub start: f32,
    pub end: f32,
    pub enabled: bool,
    pub exponential: bool,
    pub density: f32,  // 指数雾用
}

impl Default for FogParams {
    fn default() -> Self {
        Self {
            color: Vec3::new(0.6, 0.7, 0.85),
            start: 30.0,
            end: 100.0,
            enabled: true,
            exponential: false,
            density: 0.02,
        }
    }
}

impl FogParams {
    pub fn apply_to_shader(&self, shader_program: GLuint, camera_pos: Vec3) {
        unsafe {
            let set_uniform = |name: &str, value: &dyn std::any::Any| {
                let c_name = CString::new(name).unwrap();
                let loc = gl::GetUniformLocation(shader_program, c_name.as_ptr());

                if loc < 0 { return; }

                if let Some(v) = value.downcast_ref::<f32>() {
                    gl::Uniform1f(loc, *v);
                } else if let Some(v) = value.downcast_ref::<i32>() {
                    gl::Uniform1i(loc, *v);
                } else if let Some(v) = value.downcast_ref::<Vec3>() {
                    gl::Uniform3f(loc, v.x, v.y, v.z);
                }
            };

            set_uniform("u_fog_color", &self.color);
            set_uniform("u_fog_start", &self.start);
            set_uniform("u_fog_end", &self.end);
            set_uniform("u_fog_enabled", &(if self.enabled { 1 } else { 0 }));
            set_uniform("u_fog_exponential", &(if self.exponential { 1 } else { 0 }));
            set_uniform("u_fog_density", &self.density);
            set_uniform("u_camera_pos", &camera_pos);
        }
    }
}

const FOG_FRAGMENT_SRC: &str = r#"
#version 330 core

in vec3 v_world_pos;
in vec3 v_normal;
in vec2 v_uv;

out vec4 frag_color;

uniform vec3 u_camera_pos;
uniform sampler2D u_texture;
uniform vec3 u_light_dir;

uniform vec3 u_fog_color;
uniform float u_fog_start;
uniform float u_fog_end;
uniform int u_fog_enabled;
uniform int u_fog_exponential;
uniform float u_fog_density;

void main() {
    // 基础颜色 + 光照(简化)
    vec3 base = texture(u_texture, v_uv).rgb;
    base = pow(base, vec3(2.2));   // sRGB → 线性

    vec3 N = normalize(v_normal);
    vec3 L = normalize(u_light_dir);
    float diff = max(0.0, dot(N, L));
    vec3 color = base * (diff * 0.8 + 0.2);

    // 雾
    if (u_fog_enabled != 0) {
        float dist = length(v_world_pos - u_camera_pos);
        float fog_factor;

        if (u_fog_exponential != 0) {
            // 指数雾:1 - exp(-density * dist)
            fog_factor = 1.0 - exp(-u_fog_density * dist);
        } else {
            // 线性雾
            fog_factor = clamp(
                (dist - u_fog_start) / (u_fog_end - u_fog_start),
                0.0, 1.0
            );
        }

        color = mix(color, u_fog_color, fog_factor);
    }

    // 线性 → sRGB
    color = pow(color, vec3(1.0 / 2.2));

    frag_color = vec4(color, 1.0);
}
"#;
```

**Troubleshooting**:

- **远处物体不"溶进"背景色** — fog_color 不对,或 fog_factor 算错。打印中间值
- **近处物体也变雾色** — fog_start 太小。检查 fog_start 距离
- **雾色看起来"过浓"** — sRGB 处理错。fragment shader 内 mix 在线性空间吗?最后 pow(1/2.2) 编码吗?
- **指数雾密度过大** — density 一般 < 0.1。0.02 是好起点
- **uniform "u_fog_color" not found** — shader 里没用(被编译器优化掉),或者名字写错


### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
