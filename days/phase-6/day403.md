
# Day 403 · 离线光照与逐顶点反射器

> 实时 GI 每帧算,代价高。**离线光照**(offline lighting)在游戏加载时预计算,运行时只采样。今天 Casey 加**逐顶点反射器**(per-vertex reflectors)——把离线光照"烘焙"到场景几何的顶点上,运行时廉价采样。

## 0 · 为什么要有这一天

每帧实时算 V-cycle + AO + shadow 几毫秒,在低端硬件可能拖累帧率。**离线光照**思路:

1. **预计算阶段**(游戏加载 / 开发期):跑完整 V-cycle 几千次,让光照收敛到"稳态"
2. **存储**:把稳态光照烘焙到顶点(per-vertex)或纹理(lightmap)
3. **运行时**:每像素只查表,不再跑 V-cycle

**逐顶点反射器**(per-vertex reflector):每顶点存一个"反射探针"(reflection probe),记录该位置的间接光分布。fragment shader 在顶点之间**插值**。

**优点**:

- 运行时极快(每像素 1 次纹理采样)
- 适合静态场景(建筑、地形)
- 跨平台(移动端友好)

**缺点**:

- 不支持动态光源(光源变了,预计算作废)
- 大场景存储大(每顶点几 KB)
- 插值误差(顶点之间)

**今天的产出**:静态场景的间接光**烘焙到顶点**,运行时实时渲染无 V-cycle 开销。动态光源仍用 V-cycle(混合方案)。

心理锚点:看完今天,你能(1)解释离线光照和实时 GI 的取舍;(2)实现 per-vertex reflector;(3)在顶点之间插值光照;(4)理解 lightmap 的概念。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 流程:

1. **回顾**:实时 GI 每帧算,慢。
2. **引入离线**:V-cycle 跑到收敛(几千次),得到稳态。

## 2 · 心智模型

### 类比:菜谱 vs 即时做菜

**即时做菜**(实时 GI):客人点单后开始切菜、炒菜、上桌。**慢**,但灵活(可改菜单)。

**预制菜**(离线光照):提前做好半成品,客人点单只需加热。**快**,但菜单固定。

混合:固定菜单预制,临时菜单即时做。游戏开发一样——静态场景预计算,动态物体实时算。

### 严谨原理:Per-vertex Reflectors

**顶点 attribute 扩展**:除了 position 和 normal,加 `indirect_light: [f32; 3]`。

```rust
#[derive(Copy, Clone)]
struct Vertex {
    position: [f32; 3],
    normal: [f32; 3],
    indirect_light: [f32; 3],  // 离线烘焙
}
```

**离线烘焙流程**:

```rust
pub fn bake_vertex_lighting(
    mesh: &Mesh,
    voxel_grid: &VoxelGrid,
) -> Vec<[f32; 3]> {
    // 跑 V-cycle 到收敛
    let mut grid = voxel_grid.clone();
    for _ in 0..1000 {
        jacobi_step(&mut grid);
    }

    // 每顶点采样 voxel_light
    let mut vertex_lights = Vec::with_capacity(mesh.vertices.len());
    for v in &mesh.vertices {
        let light = sample_voxel_light(&grid, v.position);
        vertex_lights.push([light.x, light.y, light.z]);
    }
    vertex_lights
}
```

### Vertex Shader(读 indirect_light)

```glsl
#version 330

in vec3 position;
in vec3 normal;
in vec3 indirect_light;  // 离线烘焙

uniform mat4 mvp;

out vec3 v_world_normal;
out vec3 v_indirect_light;

void main() {
    v_world_normal = normal;  // 假设世界空间
    v_indirect_light = indirect_light;
    gl_Position = mvp * vec4(position, 1.0);
}
```

### Fragment Shader(插值 indirect_light)

```glsl
#version 330

in vec3 v_world_normal;
in vec3 v_indirect_light;  // 已经被光栅器插值
in vec2 v_uv;

uniform sampler2D albedo_tex;
// ...

void main() {
    vec3 albedo = texture(albedo_tex, v_uv).rgb;
    vec3 N = normalize(v_world_normal);
    // ...

    // Phong(直接光)
    vec3 phong = ambient + diffuse + specular;

    // GI:用顶点插值的 indirect_light
    vec3 gi = albedo * v_indirect_light;

    vec3 final = phong + gi;
    // Tone map + 输出
}
```

**关键**:`v_indirect_light` 由 vertex shader 输出,光栅器**自动插值**(三角形内的 fragment 得到三顶点的重心坐标插值)。

### 插值的问题

顶点之间是**重心坐标插值**(barycentric interpolation)——平滑但可能不准。例如,三角形跨越角落(角落暗)和开阔地(亮),插值得到中间值,**角落的暗化丢失**。

**修法**:

- **更细几何**:增加顶点密度
- **Lightmap**:不用顶点,用纹理(每像素 1 个采样)
- **Per-pixel probe**:用 3D 纹理(per-vertex 的升级版, Casey Day 404 做)

### Lightmap vs Per-vertex

| | Per-vertex | Lightmap |
|---|---|---|
| 精度 | 低(顶点插值) | 高(纹理像素) |
| 显存 | 每顶点 RGB | 一张纹理 |
| 适合 | 低面数几何 | 高面数 / 复杂 |
| UV | 不需要 | 需要第二套 UV |

工业界主流 lightmap(Unreal / Unity)。Casey 用 per-vertex(简单,教学清晰)。

### 离线烘焙工具

**bake 流程**:

1. 加载场景
2. 跑 V-cycle 几千次,稳态
3. 每顶点采样
4. 写回 mesh 数据(新 attribute)
5. 保存到文件

**开发期**:开发者跑 bake,生成 "mesh_with_lighting.gltf"。

**运行时**:加载 mesh_with_lighting.gltf,直接渲染,无 V-cycle。

```rust
pub fn bake_and_save(
    mesh_path: &str,
    output_path: &str,
    voxel_grid: &VoxelGrid,
) -> Result<(), Box<dyn std::error::Error>> {
    let mut mesh = load_mesh(mesh_path)?;
    let vertex_lights = bake_vertex_lighting(&mesh, voxel_grid);
    
    // 把 vertex_lights 加到 mesh
    mesh.add_attribute("indirect_light", vertex_lights);
    
    save_mesh(&mesh, output_path)?;
    println!("Baked lighting saved to {}", output_path);
    Ok(())
}
```

Dynamic objects(NPC、可移动物品):实时跑 V-cycle

### 烘焙的物理模型:Radiosity 方程的稳态

要真正理解"为什么 V-cycle 跑几千次就收敛",必须回到物理。GI 的核心方程叫 **radiosity equation**(辐射度方程),它把"物体表面每点发出的光"和"所有其他表面反射过来的光"耦合起来:

```
B(x) = E(x) + ρ(x) · ∫_Ω B(y) · G(x, y) · V(x, y) dA_y
```

其中:
- `B(x)` 是点 x 处的**辐射度**(radiosity,出射光能量,单位 W/m²)
- `E(x)` 是 x 处的自发光(emission,光源发出)
- `ρ(x)` 是 x 的反射率(albedo,0~1)
- `G(x, y)` 是**几何因子**(geometry factor)——取决于 x 和 y 的距离、相对方向,公式 `cos θ_x · cos θ_y / (π · r²)`
- `V(x, y)` 是可见性函数——x 能看到 y 为 1,被遮挡为 0
- 积分遍历场景所有表面 Ω

这是一个**第二类 Fredholm 积分方程**。它**没有解析解**——表面之间互相反射,你中有我,我中有你。**唯一**的办法是**迭代**:猜一个 B(0) = E,代入方程右边得到 B(1) = E + ρ∫B(0)G V dA,再代入得到 B(2),依此类推。

数学定理:当 ρ < 1(没有完全反射的镜子),这个迭代**必然收敛**到唯一稳态 B*。每一步 B(n+1) 和 B(n) 的差越来越小——因为每次反射能量损失一部分(被吸收)。物理学家叫做"光线弹跳衰减"。

V-cycle 就是这个迭代的**离散化版本**:体素网格把连续积分变成有限和。Jacobi step 把 B(n) 同时算所有体素的 B(n+1),不是逐个更新。Gauss-Seidel 改成"边算边用新值",收敛快 2 倍。但 Jacobi 并行友好(GPU 友好),所以 V-cycle 用 Jacobi。

跑 1000 次的依据:经验上 64³ 网格、平均 albedo = 0.3 的场景,大约 200-500 步能量降到初始 0.1% 以下。1000 步是安全余量,确保不管 albedo 多高都收敛。可以监控"前后两步差的最大值",小于阈值就停,省时间:

```rust
fn bake_until_converged(grid: &mut VoxelGrid, max_iters: u32, eps: f32) -> u32 {
    for i in 0..max_iters {
        let delta = jacobi_step(grid);  // 返回最大变化量
        if delta < eps {
            return i + 1;  // 收敛
        }
    }
    max_iters
}
```

收敛后的 B* 就是稳态——**这就是我们烘焙要存的东西**。它独立于时间,因为光源不变就永远不变。所以可以离线算一次,运行时直接用。

### 重心坐标插值的数学推导

Per-vertex 方案的关键是 fragment shader 接收**插值后的** indirect_light。让我们把"插值"这个词拆开,看光栅器到底做了什么。

三角形有三个顶点 A、B、C,fragment 在三角形内某点 P。P 可以用**重心坐标** (α, β, γ) 表示:

```
P = α·A + β·B + γ·C,  其中 α + β + γ = 1
```

求解 α、β、γ 用叉积:

```rust
fn barycentric(p: Vec2, a: Vec2, b: Vec2, c: Vec2) -> (f32, f32, f32) {
    let v0 = b - a;
    let v1 = c - a;
    let v2 = p - a;
    let d00 = v0.dot(v0);
    let d01 = v0.dot(v1);
    let d11 = v1.dot(v1);
    let d20 = v2.dot(v0);
    let d21 = v2.dot(v1);
    let denom = d00 * d11 - d01 * d01;
    let beta = (d11 * d20 - d01 * d21) / denom;
    let gamma = (d00 * d21 - d01 * d20) / denom;
    let alpha = 1.0 - beta - gamma;
    (alpha, beta, gamma)
}
```

光栅器对 fragment 算出 (α, β, γ),然后用它们对**顶点 attribute** 加权:

```
indirect_light(P) = α · indirect_light(A) + β · indirect_light(B) + γ · indirect_light(C)
```

这是**线性插值**——三角形内任一点的 attribute 是顶点 attribute 的线性组合。在三角形**内部**,线性插值光滑连续;但**跨越三角形边**,导数不连续(从一个三角形的斜率跳到另一个的)。

这就是 per-vertex GI 在角落失效的原因:角落是**光照的高频变化**(突变),而线性插值本质上是低通滤波,把高频抹平了。Per-pixel(3D 纹理)采样没有这个问题——它在像素的世界位置直接读体素,不经过三角形顶点的"中转"。

**透视纠正插值**(perspective-correct interpolation):严格说,GPU 不是直接用重心坐标插值,而是先除以 w(clip space 的第四分量)再插值,最后再乘回 w。这避免了远处三角形 attribute 失真。GLSL 的 `noperspective` 修饰符关掉这个纠正,用于屏幕空间数据(如 UI 坐标)。

### Vertex attribute 显存代价

每顶点 indirect_light 用 RGB 三浮点 = 12 字节。一个典型场景:

- 100 万顶点的 mesh,12 MB(仅 attribute)
- 加上 position(12) + normal(12) + uv(8) = 44 字节/顶点
- 总 44 MB 顶点数据,跨 PCIe 到 GPU

100 万顶点对现代 GPU 是中等规模。但若用 half(2 字节 / 通道,精度 1/1024 也够 indirect light),可降到 6 字节/顶点 → 总 38 MB。开发者经常在"精度"和"带宽"之间权衡。

lightmap(纹理版本)显存代价:**32 像素/米**的 lightmap,场景面积 1000 m² → 32000 像素 = 32000 × RGB8 = 96 KB。比 per-vertex(每顶点)更省!这是工业界选 lightmap 的关键原因。

### Bake 的工程化

工业 bake pipeline:

1. **预处理**:合并静态 mesh、剔除不可见三角形、生成 lightmap UV atlas
2. **Voxelization**:把场景转成体素网格(64³~256³)
3. **Direct light**:对每体素发射射线,直接光照(含 shadow)
4. **Indirect V-cycle**:Jacobi 迭代到收敛
5. **Sample back**:每顶点 / lightmap 像素采样体素网格
6. **Denoise**:降噪(因为 V-cycle 离散化有噪声)
7. **Compress**:BC6H / ASTC 压缩存盘
8. **打包**:整合到游戏 .pak / .cascadia 文件

每步都有专门的工具和工程优化。Unreal 的 Lightmass 是 C++ 写的独立进程,通过 TCP 和编辑器通信,跑在所有 CPU 核心上,典型 bake 时间 5-30 分钟。Unity 的 Enlighten 是实时的(预计算"传输矩阵",运行时迭代)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:离线光照和实时 GI 的取舍?什么场景该用哪个?

**参考解答**:

**离线光照**(lightmap / per-vertex)适合:

- 静态场景(建筑、地形):不变,可以预计算
- 性能优先(移动端、VR)
- 高质量需求(可以跑几小时烘焙)

**实时 GI** 适合:

- 动态场景(可破坏物体、动态光源)
- 玩家自由编辑(关卡编辑器)
- 开发期快速迭代

**混合**:静态物体用离线,动态物体用实时。这是工业界主流(Unreal / Unity 默认)。

### Lv2 · 动手实践

**题**:实现 per-vertex indirect light。给定 mesh(几顶点)和 voxel grid(预填数据),计算每顶点的 indirect light,作为 attribute 加到 mesh。

**参考解答**:

```rust
#[derive(Clone)]
struct Mesh {
    vertices: Vec<Vec3>,
    normals: Vec<Vec3>,
    indices: Vec<u32>,
    indirect_light: Vec<[f32; 3]>,  // 烘焙
}

fn bake_vertex_lighting(mesh: &mut Mesh, grid: &VoxelGrid) {
    mesh.indirect_light.clear();
    for v in &mesh.vertices {
        let rel = (*v - grid.origin) / grid.voxel_size;
        let light = if rel.x >= 0.0 && rel.y >= 0.0 && rel.z >= 0.0
            && rel.x < grid.dims.0 as f32
            && rel.y < grid.dims.1 as f32
            && rel.z < grid.dims.2 as f32 {
            let idx = (rel.z as u32 * grid.dims.0 * grid.dims.1
                + rel.y as u32 * grid.dims.0 + rel.x as u32) as usize;
            grid.voxels[idx].light
        } else {
            [0.0; 3]
        };
        mesh.indirect_light.push(light);
    }
}
```

```rust
use glam::Vec3;
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Clone)]
pub struct BakedMesh {
    pub vertices: Vec<[f32; 3]>,
    pub normals: Vec<[f32; 3]>,
    pub indirect_light: Vec<[f32; 3]>,
    pub indices: Vec<u32>,
}

impl BakedMesh {
    pub fn new_simple() -> Self {
        Self {
            vertices: vec![
                [-0.5, -0.5, 0.0], [0.5, -0.5, 0.0], [0.0, 0.5, 0.0],
            ],
            normals: vec![[0., 0., 1.]; 3],
            indirect_light: vec![[0.0; 3]; 3],
            indices: vec![0, 1, 2],
        }
    }

    pub fn bake(&mut self, grid_origin: Vec3, grid_dims: u32, voxel_size: f32, voxel_data: &[([f32; 3], [f32; 3])]) {
        for (i, v) in self.vertices.iter().enumerate() {
            let v = Vec3::from_array(*v);
            let rel = (v - grid_origin) / voxel_size;
            let idx = if rel.x >= 0.0 && rel.y >= 0.0 && rel.z >= 0.0 {
                let xi = rel.x as u32;
                let yi = rel.y as u32;
                let zi = rel.z as u32;
                if xi < grid_dims && yi < grid_dims && zi < grid_dims {
                    Some((zi * grid_dims * grid_dims + yi * grid_dims + xi) as usize)
                } else { None }
            } else { None };
            self.indirect_light[i] = idx
                .and_then(|i| voxel_data.get(i))
                .map(|(_, l)| *l)
                .unwrap_or([0.0; 3]);
        }
    }

    pub fn save(&self, path: &str) -> Result<(), Box<dyn std::error::Error>> {
        let f = std::fs::File::create(path)?;
        bincode::serialize_into(std::io::BufWriter::new(f), self)?;
        Ok(())
    }

    pub fn load(path: &str) -> Result<Self, Box<dyn std::error::Error>> {
        let f = std::fs::File::open(path)?;
        Ok(bincode::deserialize_from(std::io::BufReader::new(f))?)
    }
}

fn main() {
    let mut mesh = BakedMesh::new_simple();
    
    // 模拟 voxel 数据
    let mut voxel_data = vec![([0.0; 3], [0.0; 3]); 16 * 16 * 16];
    for v in &mut voxel_data {
        v.1 = [0.3, 0.5, 0.7];  // 间接光
    }
    
    mesh.bake(Vec3::new(-0.8, -0.8, -0.8), 16, 0.1, &voxel_data);
    println!("Baked indirect light:");
    for (i, l) in mesh.indirect_light.iter().enumerate() {
        println!("  Vertex {}: ({:.2}, {:.2}, {:.2})", i, l[0], l[1], l[2]);
    }
    
    mesh.save("mesh_baked.bin").unwrap();
    println!("Saved to mesh_baked.bin");
    
    let loaded = BakedMesh::load("mesh_baked.bin").unwrap();
    println!("Loaded back: {} vertices", loaded.vertices.len());
}
```

### 进一步展开:从概念到落地的完整路径

要把今天讨论的抽象概念变成可运行的代码,我们必须经历几个具体阶段。这一节展开每一步的工程细节。

**阶段一:定义接口**。Casey 在动手实现前,先想清楚 API。Rust 的 trait 是定义接口的工具:

```rust
trait Sortable {
    fn sort_key(&self) -> u64;
    fn bounds(&self) -> Aabb;
    fn layer(&self) -> u8;
}
```

trait 让代码可测试、可替换。Casey 经常说"先写 trait,再写 impl"——这强迫你思考抽象边界。

**阶段二:单元测试**。每个 sort_rule 分支都应有对应测试:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_basic_ordering() {
        let a = TestEntity { layer: 1, y: 100.0 };
        let b = TestEntity { layer: 1, y: 200.0 };

```

**阶段三:集成测试**。单元测试覆盖单个函数,集成测试覆盖整个系统。游戏里的集成测试通常是"加载场景,跑一帧,截图,对比期望截图"——visual regression test。这是 Casey debug 流程的标准化版本。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。

### 深度推导:Lambert 漫反射的物理基础

Per-vertex reflector 烘焙的是**漫反射间接光**。为什么间接光主要是漫反射?因为镜面反射是**方向性**的(只沿反射方向传播),不会均匀照亮整个房间;而漫反射把光向所有方向散射,经多次弹跳后形成**均匀环境光**——这就是 GI 的主体。

Lambert 漫反射定律:

```
L_o = (ρ / π) · E · cos θ
```

其中 L_o 是出射辐射度(radiance,W/(m²·sr)),ρ 是 albedo,E 是入射辐照度(irradiance,W/m²),θ 是入射方向和表面法线的夹角,1/π 是归一化常数(因为漫反射假设出射在半球上均匀分布,半球的积分 = π 球面度)。

V-cycle 在体素网格里求解的就是这个方程的离散版本:每体素存一个 RGB 辐射度,每步把当前辐射度按 cos θ · G(x,y) 散射到邻居。当步骤数趋于无穷,这个迭代收敛到 radiosity 方程的稳态解。

### 烘焙后的颜色空间注意

烘焙结果必须存**线性空间**(linear RGB),不是 sRGB。原因:

- V-cycle 在线性空间做加权和(物理正确)
- 渲染时,直接光和间接光也在线性空间相加
- 最后输出到屏幕才转 sRGB(gamma 校正)

如果烘焙时存了 sRGB,fragment shader 加 direct + indirect 时相当于"先 gamma 后相加",物理错误,颜色过曝。

glTF 2.0 标准:`KHR_materials_unlit` 扩展支持 per-vertex color 在线性空间。Opengl 的 `GL_SRGB8_ALPHA8` 内部格式自动处理 sRGB 解码。

### Bake 的可重现性

工业 bake 是确定性任务:同样的 mesh + 光源 + voxel 参数,必须得到同样的烘焙结果。保证可重现:

- 用固定随机种子(若 bake 用蒙特卡洛)
- 不依赖浮点不确定性(避免不同 CPU 架构结果不同)
- 版本控制 bake 配置(mesh hash + 灯光 hash + 参数 hash)

```rust
pub fn bake_hash(mesh: &Mesh, lights: &[Light], params: &BakeParams) -> u64 {
    use std::collections::hash_map::DefaultHasher;
    use std::hash::{Hash, Hasher};
    let mut h = DefaultHasher::new();
    mesh.hash(&mut h);
    for l in lights { l.hash(&mut h); }
    params.hash(&mut h);
    h.finish()
}
```

把 hash 写到 bake 文件名:`scene_0xab12cd34.baked`,下次加载时和当前 mesh+light hash 对比,不匹配就重新 bake。这是 Unreal 的"build lighting"机制。
