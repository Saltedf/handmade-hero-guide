
# Day 420 · 直接推送光照信息

> 之前的光照信息存在体素网格,通过传播算法扩散。今天 Casey 加一个新通道——**直接推送(direct push)**:某些光源(玩家手持火把)直接把光照信息推送到**它影响的所有图元**,跳过体素网格传播。这是混合渲染管线的雏形:动态光源直接,静态光源传播。

## 0 · 为什么要有这一天

体素光照传播有**延迟**:光源出现后,要等几帧光才扩散到周围。原因:传播算法每帧只把光从体素传给**直接邻居**,远处的体素需要多帧才看到光。这叫"扩散时延",在工业叫"iterative light propagation"。

延迟对**静态光源**(天花板灯、地火)无所谓——它们总亮着,延迟只影响"开灯那一刻"。但对**动态光源**(玩家手持火把)很糟——玩家每秒移动几米,光要跟随玩家,但传播延迟让光"滞后于"玩家位置,看起来像拖尾巴。

工业的解决方案:**混合光照**。静态光源用体素传播(便宜但延迟),动态光源直接计算(贵但即时)。两套结果在 shader 里混合。

Casey 今天加直接推送通道:玩家光源直接遍历周围图元,每个图元做完整光照计算(包括遮挡),结果直接写入图元的 `lighting` 字段。体素传播仍在跑(给静态光),但动态光走"快车道"。

为什么这是大事?因为它揭示了**渲染管线的分层**:不是所有光都走同一条路。工业叫 **light classification**——光源按特性分到不同管线。这是 Unreal Lumen、Unity HDRP 的核心架构。

心理锚点:今天之后,你能解释为什么 Lumen 有"直接光 + 间接光"两个通道,能在自己的渲染器里实现光源分类,知道哪种光用什么算法最划算。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 在 RenderQueue 上加了一个新字段:`direct_lighting: Option<Vec3>`。光照计算分两条路:

1. **直接推送**(本日):遍历所有"标记为直接"的光源,直接给每个图元算光照,结果存 `direct_lighting`
2. **体素传播**(已有):矩形光源把光注入体素网格,传播算法扩散,渲染时图元从网格采样

最终光照 = `direct_lighting + indirect_lighting`(加法)。

具体动作:

1. 给 `LightSource` 加 `enum Type { Direct, Propagated }`
2. 在 `compute_primitive_lighting` 里,只处理 `Type::Direct` 的光,直接累加到 `direct_lighting`
3. 体素传播阶段只处理 `Type::Propagated` 的光
4. 渲染时:`final = direct.unwrap_or(ZERO) + grid.sample(pos)`

Casey 强调**两条通道独立**:直接通道的修改不影响传播通道,反之亦然。这种隔离让代码可测试、可调试。

## 2 · 心智模型

### 类比:快递公司的两条线

想象快递公司有两条业务线:

- **平邮**(传播):便宜,慢。从仓库 → 分拣中心 → 地方站 → 投递员 → 客户。每步要时间。
- **快递**(直接):贵,快。从仓库直接派车送到客户。

平邮适合大订单(几十件相同货物,集中分发),快递适合小急件(必须立刻送到)。

光照系统同构:

- **传播**(平邮):适合静态光源(总亮),批量处理多个图元
- **直接**(快递):适合动态光源(位置变),每帧单独算,实时

两条线**共享最终目的地**(图元的 lighting 字段),但**走不同路径**。

### 严谨原理:光源分类

光源按属性分类:

- **按位置稳定性**:静态(总在一个地方) vs 动态(每帧移动)
- **按数量**:少量(主要光) vs 多量(粒子光源、装饰光)
- **按影响范围**:全局(方向光) vs 局部(点光源、聚光)
- **按可见频率**:每帧都见(太阳) vs 偶尔见(闪电)

每类有最划算的算法:

| 类型 | 最划算算法 |
|---|---|
| 静态大光源 | 烘焙(lightmap) |
| 静态小光源 | 体素传播 |
| 动态少光源 | 直接光照(per-pixel 或 per-primitive) |
| 动态多光源 | Cluster forward / tiled deferred |
| 全局方向光 | 单次计算,所有像素共享 |

Casey 今天加的是"动态少光源"的直接通道。

### Rust 视角:Option 表达"无直接光"

```rust
pub struct RenderItem {
    // ...
    pub direct_lighting: Vec3,   // 默认 ZERO
    pub indirect_lighting: Vec3, // 从体素网格采样
}

impl RenderItem {
    pub fn final_lighting(&self) -> Vec3 {
        self.direct_lighting + self.indirect_lighting
    }
}
```

不用 `Option`,因为默认 `Vec3::ZERO` 等价于"没有直接光"。`Option<Vec3>` 浪费 16 字节(Option 有 padding)。

### 两条通道的伪代码

```rust
fn compute_lighting(queue: &mut RenderQueue, lights: &[Light]) {
    let direct_lights: Vec<_> = lights.iter().filter(|l| l.is_direct()).collect();
    let propagated_lights: Vec<_> = lights.iter().filter(|l| l.is_propagated()).collect();

    // 通道 1:直接光照
    for item in queue.items.iter_mut() {
        item.direct_lighting = Vec3::ZERO;
        for light in &direct_lights {
            item.direct_lighting += compute_direct(item, light);
        }
    }

    // 通道 2:体素传播(单独阶段,异步跑)
    voxel_grid.clear();
    for light in &propagated_lights {
        voxel_grid.inject(light);
    }
    voxel_grid.propagate();

    // 通道 2 采样:每图元从网格采样
    for item in queue.items.iter_mut() {
        item.indirect_lighting = voxel_grid.sample(item.center());
    }
}

fn render(queue: &RenderQueue) {
    for item in queue.items.iter() {
        let lighting = item.final_lighting();
        rasterize(item, lighting);
    }
}
```

两条通道**完全解耦**——可以并行(day430)、可以异步(传播延一帧)、可以独立调试。

### 直接光照计算

直接光照公式(点光源,简化):

```
L = sum over direct lights:
    L_i * (N · L_dir_i)+ / dist_i²
```

每个直接光源对每个图元算一次,累加。

矩形光源的直接光照还要采样矩形 N 个点,但**每帧重新采样**(不像传播那样累积)。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业的混合光照:

- **Unreal Lumen**:直接光(per-pixel)+ 间接光(Lumen 卡斯尔网格)+ 反射(SSR / RT)
- **Unity HDRP**:类似,直接 + GI
- **Cyberpunk RT**:路径追踪,所有光合并(但内部仍有分类)
- **Minecraft**:简单,所有光走 voxel propagation

Lumen 是工业标杆,用一套复杂的多分辨率网格存间接光,直接光走 GPU shader。Casey 的实现是简化版,但分层一致。

### 3.2 · 🎨 图形学视角

数学上,**直接光照**和**间接光照**对应渲染方程的两项:

```
L(x) = ∫ BRDF * L_direct(y) dy  +  ∫ BRDF * L_indirect(y) dy
```

- `L_direct`:来自光源直射
- `L_indirect`:来自其他表面反射

工业的"全局光照(GI)"就是算 `L_indirect`。Casey 的体素传播是 GI 的简化——把光"漏"到周围体素,近似间接反射。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核的"直接 vs 传播"同构:

- **直接系统调用**(`open/read/write`):立即执行,直接返回结果
- **异步 IO**(`io_uring`):提交到队列,内核"传播"(处理),返回结果

`io_uring` 是 Linux 的"光照传播"——批量处理,延迟低但不是立即。直接系统调用是"直接光照"——立即,但单次成本高。

### 3.4 · 🦀 Rust 生态视角

Rust 表达两条通道:

```rust
pub enum LightClassification {
    Direct,           // 走 per-primitive 直接通道
    Propagated,       // 走体素传播通道
    Baked,            // 烘焙到 lightmap(预计算)
}

pub struct LightSource {
    pub classification: LightClassification,
    pub pos: Vec3,
    pub color: Vec3,
    pub intensity: f32,
    // ...
}

pub fn classify_light(light: &LightSource, frame_context: &FrameContext) -> LightClassification {
    // 静态光走传播,动态走直接
    if light.is_static {
        LightClassification::Propagated
    } else {
        LightClassification::Direct
    }
}
```

`enum` 让分类显式,Rust 的 match 强制处理每种情况。

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |

| 单一体素传播 | 所有光一样 | 简单、静态场景 | 弃用 |

| 全部直接(per-pixel) | 每像素算所有光 | GPU 算力极强 | 不用 |
| 全部烘焙 | 离线预计算 | 静态场景、不动态 | 不用 |

- **两个独立计算阶段** —— 直接通道在渲染前,传播通道可异步

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"玩家手持火把"应该走直接通道,而"天花板固定灯"走传播通道?反过来会有什么问题?

**参考解答**:火把每帧跟随玩家位置移动。如果走传播通道,光"漏"到周围体素,但玩家移动后,旧位置体素仍有光(没立即清零),新位置体素没光(还在传播中)。视觉上是"拖光尾"——玩家身后的墙仍亮,身前的墙仍暗,虽然玩家已经移到前面。

直接通道:每帧重新计算玩家位置的光照,直接给周围图元。玩家移动后,旧图元的 direct_lighting 立刻变 0(没有玩家光源影响),新图元立刻有光。无尾迹。

天花板灯总亮、位置固定。传播通道的延迟只在"开灯那一刻"明显,稳定后所有体素都有光。直接通道成本高(每帧遍历所有图元),不划算。

反过来:
- 火把走传播 → 拖尾
- 天花板灯走直接 → 性能浪费(光位置不变,每帧重算光照)

```rust
use glam::Vec3;

#[derive(Copy, Clone, PartialEq)]
pub enum LightClassification { Direct, Propagated }

pub struct LightSource {
    pub classification: LightClassification,
    pub pos: Vec3,
    pub color: Vec3,
    pub intensity: f32,
    pub radius: f32,
}

#[derive(Clone, Default)]
pub struct RenderItem {
    pub center: Vec3,
    pub normal: Vec3,
    pub direct_lighting: Vec3,
    pub indirect_lighting: Vec3,
}

impl RenderItem {
    pub fn final_lighting(&self) -> Vec3 {
        self.direct_lighting + self.indirect_lighting
    }
}

pub struct Scene {
    pub lights: Vec<LightSource>,
    pub items: Vec<RenderItem>,
}

impl Scene {
    pub fn compute_direct_lighting(&mut self) {
        let direct_lights: Vec<&LightSource> = self.lights.iter()
            .filter(|l| l.classification == LightClassification::Direct)
            .collect();
        for item in self.items.iter_mut() {
            item.direct_lighting = Vec3::ZERO;
            for light in &direct_lights {
                let dir = light.pos - item.center;
                let dist2 = dir.length_squared();
                if dist2 > light.radius * light.radius { continue; }
                let dist = dist2.sqrt();
                let n_dot_l = item.normal.dot(dir / dist).max(0.0);
                if n_dot_l == 0.0 { continue; }
                let falloff = (1.0 - dist / light.radius).max(0.0);
                item.direct_lighting += light.color * light.intensity * n_dot_l * falloff / dist2;
            }
        }
    }

    pub fn compute_indirect_lighting(&mut self, voxel_grid: &VoxelGrid) {
        for item in self.items.iter_mut() {
            item.indirect_lighting = voxel_grid.sample(item.center);
        }
    }
}

pub struct VoxelGrid {
    pub data: Vec<Vec3>,
    pub voxel_size: f32,
}

impl VoxelGrid {
    pub fn sample(&self, p: Vec3) -> Vec3 {
        let idx = (p.x as usize) + (p.y as usize) * 8 + (p.z as usize) * 64;
        self.data.get(idx).copied().unwrap_or(Vec3::ZERO)
    }
}

fn main() {
    let mut scene = Scene {
        lights: vec![
            LightSource {
                classification: LightClassification::Direct,
                pos: Vec3::new(5.0, 1.0, 5.0),
                color: Vec3::new(1.0, 0.8, 0.5),
                intensity: 50.0,
                radius: 10.0,
            },
            LightSource {
                classification: LightClassification::Propagated,
                pos: Vec3::new(0.0, 10.0, 0.0),
                color: Vec3::ONE,
                intensity: 30.0,
                radius: 50.0,
            },
        ],
        items: vec![
            RenderItem {
                center: Vec3::new(5.0, 0.0, 5.0),
                normal: Vec3::Y,
                ..Default::default()
            },
            RenderItem {
                center: Vec3::new(0.0, 0.0, 0.0),
                normal: Vec3::Y,
                ..Default::default()
            },
        ],
    };

    scene.compute_direct_lighting();
    // 模拟体素传播结果
    let voxel = VoxelGrid {
        data: vec![Vec3::new(0.1, 0.1, 0.1); 512],
        voxel_size: 1.0,
    };
    scene.compute_indirect_lighting(&voxel);

    for (i, item) in scene.items.iter().enumerate() {
        println!("Item {}: direct={:?} indirect={:?} final={:?}",
            i, item.direct_lighting, item.indirect_lighting, item.final_lighting());
    }
}
```

```rust
use glam::Vec3;

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
pub enum LightClassification {
    Direct,
    Propagated,
}

#[derive(Clone)]
pub struct LightSource {
    pub classification: LightClassification,
    pub pos: Vec3,
    pub color: Vec3,
    pub intensity: f32,
    pub radius: f32,
    pub is_static: bool,  // 提示分类
}

impl LightSource {
    pub fn torch(pos: Vec3) -> Self {
        Self {
            classification: LightClassification::Direct,
            pos,
            color: Vec3::new(1.0, 0.8, 0.5),
            intensity: 30.0,
            radius: 12.0,
            is_static: false,
        }
    }
    pub fn ceiling(pos: Vec3) -> Self {
        Self {
            classification: LightClassification::Propagated,
            pos,
            color: Vec3::ONE,
            intensity: 100.0,
            radius: 100.0,
            is_static: true,
        }
    }
}

#[derive(Clone, Default)]
pub struct RenderItem {
    pub center: Vec3,
    pub normal: Vec3,
    pub direct_lighting: Vec3,
    pub indirect_lighting: Vec3,
}

impl RenderItem {
    pub fn final_lighting(&self) -> Vec3 {
        self.direct_lighting + self.indirect_lighting
    }
}

pub fn compute_direct_channel(items: &mut [RenderItem], lights: &[LightSource]) {
    let directs: Vec<&LightSource> = lights.iter()
        .filter(|l| l.classification == LightClassification::Direct)
        .collect();
    for item in items.iter_mut() {
        item.direct_lighting = Vec3::ZERO;
        for light in &directs {
            let dir = light.pos - item.center;
            let dist2 = dir.length_squared();
            let radius2 = light.radius * light.radius;
            if dist2 > radius2 || dist2 < 1e-6 { continue; }
            let dist = dist2.sqrt();
            let n_dot_l = item.normal.dot(dir / dist).max(0.0);
            if n_dot_l == 0.0 { continue; }
            // Smooth falloff
            let t = 1.0 - dist / light.radius;
            let falloff = t * t;
            item.direct_lighting += light.color * light.intensity * n_dot_l * falloff / dist2;
        }
    }
}

pub struct VoxelGrid {
    pub data: Vec<Vec3>,
    pub dims: (usize, usize, usize),
    pub voxel_size: f32,
}

impl VoxelGrid {
    pub fn sample(&self, p: Vec3) -> Vec3 {
        let i = ((p.x / self.voxel_size).floor() as usize).min(self.dims.0 - 1);
        let j = ((p.y / self.voxel_size).floor() as usize).min(self.dims.1 - 1);
        let k = ((p.z / self.voxel_size).floor() as usize).min(self.dims.2 - 1);
        self.data[i + j * self.dims.0 + k * self.dims.0 * self.dims.1]
    }
}

fn main() {
    let lights = vec![
        LightSource::torch(Vec3::new(5.0, 1.5, 5.0)),
        LightSource::ceiling(Vec3::new(0.0, 10.0, 0.0)),
    ];
    let mut items: Vec<RenderItem> = (0..10).map(|i| RenderItem {
        center: Vec3::new(i as f32, 0.0, 5.0),
        normal: Vec3::Y,
        ..Default::default()
    }).collect();

    // 通道 1: 直接
    compute_direct_channel(&mut items, &lights);

    // 通道 2: 体素传播(简化,假设已经有结果)
    let mut voxel = VoxelGrid {
        data: vec![Vec3::new(0.05, 0.05, 0.05); 8*8*8],
        dims: (8, 8, 8),
        voxel_size: 1.0,
    };
    // 给天花板灯的体素加光
    voxel.data[0 + 5 * 8 + 0 * 64] = Vec3::new(0.3, 0.3, 0.3);

    for item in items.iter_mut() {
        item.indirect_lighting = voxel.sample(item.center);
    }

    println!("Item positions and lighting:");
    for (i, item) in items.iter().enumerate() {
        println!("  [{}] pos={:?} direct={:.3} indirect={:.3} final={:.3}",
            i, item.center,
            item.direct_lighting.x, item.indirect_lighting.x, item.final_lighting().x);
    }
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
