# Day 290 · 完成分离的渲染

> Day 289 解耦了 Visual 概念,但残留了一堆"还按 Type 渲染"的旧代码。今天 Casey 把所有渲染调用都切到 Visual,删掉无用的 Type 分支,清理 stale 字段。**架构重构的最后一步:清除残留**。

## 0 · 为什么要有这一天

软件工程里有"幽灵代码"现象——重构后,旧代码的影子还在。比如 Day 289 你引入了 Visual,但有些地方还在 `match Type { PLAYER => draw_player(...), ... }`。这些"幽灵"看起来不影响功能,但它们是**未来 bug 的种子**。

为什么必须修?考虑以下场景:

- 你加了新 visual `Visual::PlayerSprite`,但有一处渲染代码忘了切,还在 `match Type::Player => draw_player()`——这处代码用的是旧 PLAYER_SPRITE 硬编码
- 后来美术换 PLAYER_SPRITE 的图,你的游戏里"一半玩家用新图,一半用旧图"
- 这种 bug 不报错,只有肉眼可见的不一致——最难调试

**今天的目标**:让 Visual 真正成为渲染的**唯一**入口,Type 在渲染路径上完全消失。完成这条原则后,**任何视觉改动只改一处**——visual 定义或 entity 的 visual 字段。

具体来说,今天要做:

1. **扫所有渲染调用**,找到还按 Type 分支的
2. **每处都改成按 Visual 分支**
3. **删除"已经没人用"的 Type variant**(如 Type::Sword,如果它的 visual 是动态的)
4. **统一 sprite 资源加载**——所有 visual 用同一个 sprite asset table
5. **验证**——加一种新 visual,只改一处,所有路径自动走新 visual

心理锚点:看完今天,你应该能用 `grep "Type::" src/render*.rs` 命令检查,输出**为空**——render 模块完全不依赖 Type。如果还有,今天没清理干净。

## 1 · Casey 今天做了什么

Casey 今天的动作:

1. **遍历所有渲染代码**,找 `Entity->Type` 的引用——每处都问"这里为什么要 Type?"
2. **逐个迁移**——大部分能改成 visual,小部分真的需要 Type(如 debug overlay 显示"这是 Player")
3. **删除冗余字段**——某些 entity 字段(如 `entity.sprite_offset`)被 visual 覆盖,删掉
4. **统一 sprite 加载**——所有 sprite 通过 sprite table 加载,不再硬编码 ID
5. **写一个 sanity check**——给每个 Type 一个"默认 visual",验证所有实体都有 visual

Casey 在今天的代码里要做的最后一件事是**确认 day 291 加新怪物(hopping monstar)时,代码不需要大改**。如果加新怪物要改十处,说明解耦没完成。如果只改 2-3 处(加 enum variant + 给构造函数),解耦成功。

## 2 · 心智模型

### 类比:搬家后的清理

把架构重构想象成搬家。Day 289 你把 visual 概念"搬进新家"(visual 字段),但旧家(Type 决定视觉)的东西还在——有的双份,有的没人用,有的混乱散落。今天是**整理新家、清理旧家**:

- 把还在用旧家(Type)的物品搬到新家(visual)——逐个迁移
- 扔掉没人用的东西(死代码)——删除冗余
- 整理新家储物(visual 字段有清晰组织)——加 sanity check
- 关上旧家门(禁止再访问旧家)——把 Type 字段标 `#[deprecated]` 或删掉

搬家后清理容易拖延——"功能跑着呢,改了万一坏?"。但**不清理就是技术债**。三个月后你忘了哪些是搬了的、哪些没搬,debug 时被一堆旧代码误导。

### 2.1 死代码的检测

死代码(dead code)是"定义了但从不被调用的代码"。Rust 帮你检测:

```bash
cargo build 2>&1 | grep "never used\|never read"
```

但 Rust 只检测**完全没人用**的代码。如果**还有人用,但不该用**(如还在用 Type 分支渲染),Rust 不报错。这种"半死不活"的代码只能靠人肉审查。

审查的工具:

- `grep -rn "match.*Type" src/` —— 找所有 match Type
- `grep -rn "Entity->Type" src/` —— C 风格引用
- IDE 的 "find usages" —— 看 Type 字段被哪些函数读

工业项目还用 **depcheck** 或 **knip**(JS 生态)做更深的死代码检测。Rust 生态有 `cargo-udeps`(检测未用依赖)和 `cargo-modules`(看模块依赖图)。

### 2.2 渐进式迁移

Casey 不是一次性把所有 Type 引用全删——而是**渐进式**:

```
Day 286: 加 Brain 字段,不动 Type
Day 287-288: 给 Brain 填值,验证
Day 289: 加 Visual 字段,render 切到 Visual
Day 290 (今天): 清除 Type 在 render 路径的所有引用
Day 291+: 用解耦好的架构加新实体,验证零代码改动
```

为什么不一天搞定?因为**代码量大,一次改容易出错**。每次改一小步,编译通过、测试通过,再下一步。这是软件工程的"小步快跑"。

工业项目叫这种节奏 **"Strangler Fig Pattern"**(绞杀者模式)——新代码长出来,逐步替代旧代码,旧代码死掉后被删。Martin Fowler 在 2004 年提出,与 Casey 的做法不谋而合。

### 2.3 Sanity check:防御性编程

"完成分离"不只是删旧代码,还要**加防御新错误的机制**。Casey 加的 sanity check:

```rust
// 每个 entity 必须有 visual(构造时强制)
impl Entity {
    fn new(pos: Vec2, brain: Option<Brain>, visual: Visual) -> Self {
        Self { pos, brain, visual, /* ... */ }
    }
    // 没有"无 visual"构造器——编译器强制
}

// 或者:用 Option<Visual>,render 时 panic
fn render(e: &Entity) {
    let visual = e.visual.expect("every entity must have a visual");
    match visual {
        Visual::Sprite(id) => draw_sprite(id, e.pos),
        // ...
    }
}
```

第一种(强制 visual)更好——编译期保证。第二种(运行时 panic)是"动态语言风格",Rust 不推荐。

工业项目还用 **debug-mode assertion**:

```rust
fn render(e: &Entity) {
    debug_assert!(e.visual.is_some(), "entity {:?} has no visual", e.id);
    // ...
}
```

`debug_assert!` 在 release 模式编译掉,debug 模式触发。这是"开发时严格,生产时快"的折中。

### 2.4 资产加载的统一

旧代码下,sprite ID 是 magic number:

```rust
const PLAYER_SPRITE: u32 = 1;
const MONSTER_SPRITE: u32 = 2;
const SWORD_SPRITE: u32 = 3;
// ...

fn render(e: &Entity) {
    match e.typ {
        Type::Player => draw_sprite(PLAYER_SPRITE, e.pos),
        // ...
    }
}
```

加新 sprite 要:加 const + 加 Type variant + 改 render match。三处改动。

新代码下,sprite 通过 visual 引用:

```rust
enum Visual {
    Sprite(SpriteId),
    // ...
}

fn render(e: &Entity) {
    match e.visual {
        Visual::Sprite(id) => draw_sprite(id, e.pos),
        // ...
    }
}
```

加新 sprite 只要:加 SpriteId + 在 entity 构造时设 visual。**两处改动**——而且都是"加",不是"改"。增量开发友好。

工业级资产管线进一步:SpriteId 是字符串 hash,美术在数据文件里命名(`"player_walk_1"`),程序加载时 hash 成 u64。加新 sprite 美术改数据文件就行,程序不重编译。这是 Phase 7 的内容。

---

**总结**:今天的任务是清除"幽灵代码",让 visual 真正成为渲染唯一入口。做法:逐个迁移 Type 引用、删冗余、加 sanity check、统一资产加载。这是架构重构的收尾,为 day 291+ 加新实体铺平道路。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

游戏行业对"重构收尾"的态度有两极:

- **小团队/独立游戏**:经常跳过,因为时间紧。结果代码"能跑但烂",三年后烂到不能改。
- **大工作室**:有专门的"重构 lock 期"——一个 milestone 结束后,留 1-2 周专门清理。Naughty Dog、Id Software 都这么做。

Id Software 的 John Carmack 在 Quake 开发中说过:**"重构应当和功能开发同等优先"**。如果一直加功能不重构,代码很快变成"只有作者能改"的状态,新人 onboarding 极难。

具体到 HH,Casey 在 Phase 6 这一系列"Finishing XXX"day(day 288、290、300、310...)就是他的重构收尾节奏。每开一个新特性前,先收尾上一个。这种节奏让代码长期可维护。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核对"清除死代码"非常严格。每个版本都有 cleanup patch:

- 删未用的 static 函数
- 统一函数签名
- 删 deprecated API

Linus 在邮件列表里多次说:**"if it's not used, delete it"**。理由是死代码会**误导新人**——他们读到 `old_api()`,以为是新 API,绕弯路。

具体例子:Linux 5.10 删了一堆 `CONFIG_TRACING_LEGACY_SUPPORT` 相关老代码,因为新的 trace 框架完全取代了。删完后内核源码少了几千行,维护成本降低。

Rust 类似,`cargo build` 默认警告 `dead_code`,Clippy 更严格(`clippy::dead_code` lint)。Casey 在 HH 早期手工追踪,Day 290 是收尾日。

### 3.3 · 🦀 Rust 生态视角

Rust 的工具链帮你做大部分 cleanup:

**1. `cargo fix --edition`** —— 自动迁移到新 edition
**2. `cargo clippy --fix`** —— 自动修 lint
**3. `cargo udeps`** —— 检测未用依赖
**4. `cargo machete`** —— 另一个未用依赖检测(更准)
**5. `cargo modules`** —— 看模块依赖图,发现孤立模块

具体命令:

```bash
# 装
cargo install cargo-udeps cargo-machete cargo-modules

# 用
cargo +nightly udeps
# 输出:Unused dependency: 'serde' in crate 'foo'

cargo machete .
# 输出:/path/to/Cargo.toml: unused: serde

cargo modules generate graph
# 输出 module 依赖图,看孤立节点
```

但工具不能替代人脑——比如 visual 解耦后,"还在 match Type 渲染"是**合法代码**,工具不报。要靠 code review 或 grep。

**Rust 特有的清理模式**:

```rust
// 标记 deprecated
#[deprecated(since = "0.2.0", note = "use Visual::Sprite instead")]
fn draw_player_sprite(pos: Vec2) { /* ... */ }

// 调用方编译器警告:warning: use of deprecated function
```

Casey 不用 deprecated(他在 C 里没这功能),Rust 工程师应该用——它在重构期保留旧 API 一段时间,下游有时间迁移。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 在清理时**保留 Type 字段**(虽然不再决定视觉),但**删除了一些 Type variant**(如 `Type::Sword`,如果它没有独立 brain)。怎么决定哪个 variant 留、哪个删?

**参考解答**:三个判断标准:

1. **Type 是否被多维度引用?** —— 如果 Type 只决定 visual,删掉,直接用 visual;如果 Type 决定 brain 和 visual 两个维度,且这两维度高度相关,保留 Type 作为便捷构造。
2. **是否影响其他系统?** —— 如果 save/load 存 Type,或 debug overlay 显示 Type,保留;如果完全没人读,删。
3. **未来是否会用?** —— 如果"我以后可能加一个 Sword Brain",保留 Type::Sword;如果永远不会,删。

Casey 的实际原则:**宁可删,不要保留**。删错了加回来比保留死代码好。这是"YAGNI(You Aren't Gonna Need It)"原则。

### Lv2 · 动手实践

**题**:用 day289 的代码,做今天的"清理":

1. 写一个 `match Type` 的旧 render 函数(模拟遗留)
2. 用 `match Visual` 替代它
3. 标记旧函数 `#[deprecated]`
4. 用 `grep` 验证 render 模块不再有 Type 引用

完成标准:`grep "Type::" src/main.rs` 输出为空(或仅在构造函数里)。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
}

#[derive(Copy, Clone, Debug)]
enum Type { Player, Monster, Sword }

#[derive(Copy, Clone, Debug)]
enum Brain { Player, MonsterChase }

#[derive(Copy, Clone, Debug)]
enum Visual {
    PlayerSprite,
    MonsterSprite,
    SwordSprite,
    Invisible,
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec2,
    typ: Type,
    brain: Option<Brain>,
    visual: Option<Visual>,
}

// 旧 render —— 按类型分支(标记 deprecated)
#[deprecated(since = "0.2", note = "use render_by_visual instead")]
fn render_by_type(e: &Entity) -> &'static str {
    match e.typ {
        Type::Player => "PLAYER_SPRITE",
        Type::Monster => "MONSTER_SPRITE",
        Type::Sword => "SWORD_SPRITE",
    }
}

// 新 render —— 按 visual 分支
fn render_by_visual(e: &Entity) -> &'static str {
    match e.visual {
        Some(Visual::PlayerSprite) => "PLAYER_SPRITE",
        Some(Visual::MonsterSprite) => "MONSTER_SPRITE",
        Some(Visual::SwordSprite) => "SWORD_SPRITE",
        Some(Visual::Invisible) | None => "(invisible)",
    }
}

// 构造函数:Type 决定 brain + visual 的默认组合
fn make(typ: Type, pos: Vec2) -> Entity {
    let (brain, visual) = match typ {
        Type::Player => (Some(Brain::Player), Some(Visual::PlayerSprite)),
        Type::Monster => (Some(Brain::MonsterChase), Some(Visual::MonsterSprite)),
        Type::Sword => (None, Some(Visual::SwordSprite)),
    };
    Entity { pos, typ, brain, visual }
}

fn main() {
    let e = make(Type::Player, Vec2::new(0.0, 0.0));

    // 旧调用(会有 deprecation warning)
    #[allow(deprecated)]
    let s1 = render_by_type(&e);

    // 新调用
    let s2 = render_by_visual(&e);

    println!("old: {}", s1);
    println!("new: {}", s2);
    assert_eq!(s1, s2);

    // 验证:visual 解耦后,可以换 visual 不动 typ
    let mut e2 = make(Type::Player, Vec2::new(10.0, 0.0));
    e2.visual = Some(Visual::MonsterSprite);  // 玩家穿怪物皮
    println!("player in monster skin: {}", render_by_visual(&e2));
    // 输出: MONSTER_SPRITE
    // 但 e2.typ 仍是 Player——brain 不变
}
```

**每行解释**:
- `#[deprecated(since, note)]` —— 标记旧 API,Rust 编译器警告调用方
- `#[allow(deprecated)]` —— 临时允许调用 deprecated(测试用)
- 构造函数 `make` 仍接收 Type——Type 作为便捷构造器,内部生成 brain + visual 元组
- `e2.visual = Some(Visual::MonsterSprite)` —— 演示解耦的灵活性

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

§7 Lv2 的代码是核心。这里加自动化检测脚本:

```rust
// src/main.rs 顶部加 lint 配置
#![warn(deprecated)]
#![warn(dead_code)]
#![warn(unused_imports)]

// 标记"即将删除"的字段
#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec2,
    #[deprecated(since = "0.2", note = "use visual instead")]
    typ: Type,
    brain: Option<Brain>,
    visual: Option<Visual>,
}

// 测试代码里检测 deprecation
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_visual_render() {
        let e = make(Type::Player, Vec2::new(0.0, 0.0));
        assert_eq!(render_by_visual(&e), "PLAYER_SPRITE");
    }

    #[test]
    fn test_visual_swap() {
        let mut e = make(Type::Player, Vec2::new(0.0, 0.0));
        e.visual = Some(Visual::MonsterSprite);
        // visual 改了,但 typ 没改——证明解耦
        assert_eq!(e.typ, Type::Player);
        assert_eq!(render_by_visual(&e), "MONSTER_SPRITE");
    }
}
```

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 历史脉络与工业实践

1990 年代 id Software 的 Doom(1993)用 BSP tree + painter's algorithm——排序在编译期完成,运行时 O(N) 遍历。Quake(1996)首次用 Z-buffer(GPU 硬件),彻底解决排序问题。

2D 游戏排序的演化:

- **1985-1990**:无 sort,固定 layer(Super Mario Bros)
- **1990-1995**:Y-sort 在 JRPG 普及(最终幻想 6、超时空之轮)
- **1995-2005**:Multi-layer Y-sort(星际争霸、暗黑破坏神 2)
- **2005-2015**:引擎内置 sort(Unity、GameMaker)
- **2015-2025**:GPU + sort 混合(bevy、Unreal)

Casey 的 HH 在 day 295-310 走了这条 30 年路径——从最简单的 sort_key 到拓扑排序,演示每一阶段的工程权衡。

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。
