
# Day 348 · 调试过场动画 Z 与可遍历物创建

> 昨天调试完内存损坏,Casey 跑游戏想试试过场动画(cutscene)。结果发现:过场里玩家"飞起来"了——Z 坐标莫名其妙变化,且某些"可踩上去的平台"创建出来玩家却踩不到。今天的 debug 主题是**业务逻辑 bug**——非崩溃、非内存,但功能不对。

## 0 · 为什么要有这一天

游戏 bug 大致两类:

1. **崩溃 bug**:程序停止,segfault 或 panic。Day 347 这种。
2. **逻辑 bug**:程序跑,但行为错。Day 348 这种。

逻辑 bug 比 crash bug 难调——程序不告诉你"哪里错"。你看不到崩溃栈,只看到"玩家飞起来"。

今天的两个症状:

**症状 1:过场 Z 异常**

过场(cutscene)是脚本驱动的固定动画序列,玩家"放手看戏"。Casey 写了过场系统,玩家在过场中沿预定路径移动。但跑起来发现:玩家 Z 坐标莫名其妙变化——明明脚本写的是平面移动,玩家却飞起来又落下。

**症状 2:可遍历物创建问题**

"可遍历物"(traversable)是 HH 的术语:玩家可以踩上去的平台。Casey 在过场里创建新平台,结果玩家踩不到——平台"在",但碰撞检测没识别为"可踩"。

两个 bug 看似无关,根因都是**时序问题**:

- 过场系统更新 Z 在物理模拟之前,物理模拟又把 Z 改回去 → 抖动
- 平台创建在物理模拟之后,本帧的碰撞检测看不到这个平台 → 玩家穿过

时序 bug 是游戏开发最常见的逻辑 bug。Casey 今天演示如何**可视化时间线**找出"先后顺序"问题。

心理锚点:今天之后你能识别"时序 bug",会用 debug overlay 实时看变量演化,理解"更新顺序"对游戏行为的影响。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑游戏,启动过场。看到玩家飞起来。

调试过程:

1. **观察**:玩家 Z 在过场启动后开始变化。每帧 Z += 0.5 之类的
2. **打印**:在 `update_entity` 里打印玩家 Z。看每帧的变化
3. **二分**:发现有两个地方在改 Z —— 过场系统和物理模拟
4. **检查时序**:游戏循环是 `cutscene.update() -> physics.update()`,物理模拟后 Z 被重力改回
5. **修复**:过场系统改 Z 后,标记玩家"在过场里,不受物理影响"
6. **回归**:过场里 Z 稳定

第二个 bug(可遍历物):Casey 创建新平台后,玩家踩不到。

1. **观察**:平台画出来,但玩家穿过
2. **检查 collision**:发现 collision 检测遍历的"平台列表"在物理模拟开始时已经构建,新增平台不在列表里
3. **修复**:把"创建平台"移到物理模拟之前
4. **回归**:玩家能踩到

今天的核心:**调试更新顺序**——游戏里多个子系统(update / physics / render)的执行顺序决定行为。

## 2 · 心智模型

### 类比:厨房流水线顺序

想象厨房流水线:

```
洗菜 → 切菜 → 炒菜 → 上盘
```

如果顺序乱(切菜 → 洗菜 → 炒菜),结果错(没洗就切)。

游戏 update 同理:

```
读输入 → 玩家意愿 → 物理 → AI → 渲染
```

每一阶段依赖前一阶段的输出。顺序错,行为错。

### 游戏循环的"标准顺序"

Casey 的 HH 游戏循环大致:

```
1. 读输入(键盘、鼠标)
2. 计算 dt
3. cutscene.update(可能改 entity 状态)
4. sim_region.update(物理、AI、粒子)
5. sim_region.handle_collision
6. world.commit(sim_region 状态回写到 world)
7. renderer.draw(world)
8. 下一帧
```

**关键**:`cutscene.update` 在 `sim_region.update` 之前——过场先改状态,然后物理跑。如果反了,物理会把过场的修改"撤销"(重力把玩家拉回)。

Casey Day 348 的 bug 是过场系统的修改没"标记",物理不知道玩家"在过场里",按正常重力处理 → 玩家被拉回。

### 时序 bug 的特征

时序 bug 表现:

1. **不稳定**:有时复现,有时不复现(取决于"哪一帧"先执行)
2. **变量值"反复"**:你 set 了,下一帧又变了
3. **依赖调度**:多线程时尤其严重(线程调度顺序影响)

debug 策略:

1. **可视化时间线**:把每帧的变量值画成图,看"在哪里反转"
2. **检查所有写入点**:变量被改的地方有几个?时序如何?
3. **加状态标志**:某些状态明确标记(如 `in_cutscene`),避免被无关代码改

### Rust 表达"独占状态"

Rust 的所有权系统能防止某些时序 bug:

```rust
// 错误:两个地方同时持有 entity 的 &mut
let e1: &mut Entity = world.get_entity(player_id);
let e2: &mut Entity = world.get_entity(player_id);  // 借检查器拒绝
```

但游戏里 entity 经常"被多个系统访问",所以通常用 `&world` + `&mut world` 在系统层面排他,而非 entity 层面。

**Cell / RefCell** 用于"内部可变",慎用:

```rust
use std::cell::Cell;

struct Entity {
    z: Cell<f32>,  // 任何 &Entity 都能改 z
}

let e: &Entity = world.get_entity(0);
e.z.set(5.0);  // 看起来不可变,实际改了
```

Cell 方便,但**绕过了"谁负责改"的清晰度**。Casey 在 C 里全是"任意位置可改"(等价 Cell),靠纪律维护。Rust 用 `&mut` 显式排他,bug 更少。

### Cutscene 系统的抽象

过场是个**脚本驱动**的子系统:

```rust
struct Cutscene {
    timeline: Vec<CutsceneEvent>,
    current_time: f32,
    is_active: bool,
}

enum CutsceneEvent {
    MoveEntity { entity_id: u32, target: Vec3, duration: f32 },
    PlayAnimation { entity_id: u32, anim: AnimationId },
    CameraLookAt { target: Vec3, duration: f32 },
    SpawnEntity { ... },
}

impl Cutscene {
    fn update(&mut self, world: &mut World, dt: f32) {
        if !self.is_active { return; }
        self.current_time += dt;
        for event in &self.timeline {
            if event.start_time <= self.current_time && !event.fired {
                event.fire(world);
                event.fired = true;
            }
        }
    }
}
```

事件按时间触发,触发后修改 world。**关键是触发的修改要"被识别"**——比如 MoveEntity 改了 entity.pos,后续物理模拟必须知道"这个 entity 暂时不要重力"。

Casey 的方案:加 `entity.flags |= IN_CUTSCENE`,物理模拟跳过这些 entity。

### Traversable 的创建时机

"可遍历物"是 HH 的实体类型:玩家可以踩。

```rust
struct Traversable {
    platform_a: Vec3,
    platform_b: Vec3,  // 一条线段表示平台
    width: f32,
}

fn create_traversable(world: &mut World, t: Traversable) -> EntityId {
    world.spawn(Entity::Traversable(t))
}
```

问题:在物理模拟**中途**调用 `create_traversable`,这个新实体**这一帧**会被碰撞检测到吗?

答案:**取决于碰撞检测的列表是何时构建的**。如果碰撞检测在物理模拟开始时构建一次"候选列表",中途创建的不在列表里。

**修复**:把所有"创建实体"的操作延迟到下一帧开始(或物理模拟之前)。

```rust
// 错误:在物理模拟中创建(中途加入,看不到)
fn physics_step(world: &mut World) {
    for entity in world.entities.iter() {
        if entity.should_spawn_platform() {
            world.spawn(Traversable::new(...));  // 不会被本帧 collision 看到
        }
        handle_collision(world);
    }
}

// 正确:延迟到下一帧
fn physics_step(world: &mut World) {
    for entity in world.entities.iter() {
        if entity.should_spawn_platform() {
            world.pending_spawns.push(Traversable::new(...));
        }
        handle_collision(world);
    }
}

// 帧末:
fn frame_end(world: &mut World) {
    for spawn in world.pending_spawns.drain(..) {
        world.entities.push(spawn);
    }
}
```

"延迟到下一帧"是 ECS 系统的标准做法,Bevy 的 `Commands::spawn` 就是延迟的。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏开发的"时序"是必修课。每个子系统都有自己的 update,顺序决定行为:

```
典型顺序:
1. 输入采样
2. 网络包处理(如果是网游)
3. 玩家意图(把输入映射成动作)
4. AI 决策
5. 物理模拟
6. 碰撞响应
7. 动画更新
8. 粒子更新
9. 相机更新
10. 渲染
11. 音频
```

**Unity 的 Update / LateUpdate / FixedUpdate**:三种 update,分别用于"逻辑 / 后处理 / 物理"。用户在 Inspector 里勾选,Unity 排序。

**Unreal 的 Tick**:类似,但更复杂(依赖关系图)。

**Bevy 的 System 排序**:用户用 `.before()` / `.after()` 显式指定。

**Casey 的 HH**:硬编码顺序,简单。

### 3.2 · 图形学视角

渲染 pipeline 也有时序:

```
1. 提交 vertex/index buffer
2. 设置 shader / texture
3. draw call
4. (GPU 异步执行)
5. swapchain present
```

CPU 和 GPU 异步——CPU 提交后不等待 GPU 完成。如果 CPU 写一个 buffer,GPU 正在读,数据竞争。

解决:**双缓冲 / 三缓冲**:

- CPU 写 buffer A,GPU 读 buffer B
- 下一帧:CPU 写 B,GPU 读 A
- 永不冲突

Vulkan / DX12 显式管理,OpenGL 隐式。

### 3.3 · Linux 系统编程视角

Linux 内核的"时序":

- 中断处理:top half(立即) + bottom half(延迟到软中断)
- 系统调用:用户态 → 内核态切换(微秒级)
- 进程调度:优先级 + 时间片

应用层时序:

- **信号处理**:异步,可能在任意点打断主程序
- **多线程**:线程调度不确定,需要同步原语
- **IO 多路复用**(epoll):事件驱动

游戏开发:**单线程游戏循环 + 多线程渲染/物理**(常见模式)。Casey Day 350 进入多线程。

### 3.4 · Rust 生态视角

Rust 表达"时序":

**1. 类型状态(type state)**

```rust
struct Unfired;
struct Fired;

struct Event<State> { state: std::marker::PhantomData<State> }

impl Event<Unfired> {
    fn fire(self) -> Event<Fired> { ... }
}
```

编译期保证"事件只触发一次"。

**2. Builder pattern**

```rust
let cutscene = Cutscene::builder()
    .move_entity(...)
    .play_anim(...)
    .build();
```

build 之前不能用,build 之后不能改。

**3. Channel(消息传递)**

```rust
let (tx, rx) = std::sync::mpsc::channel();
tx.send(SpawnEvent { ... });
// 在帧末:
while let Ok(event) = rx.try_recv() {
    handle_event(event);
}
```

延迟事件到指定时刻。Bevy 的 `Events` 系统类似。

**4. tokio / async(异步时序)**

```rust
tokio::spawn(async move {
    tokio::time::sleep(Duration::from_secs(1)).await;
    create_traversable().await;
});
```

异步任务按调度顺序执行,避免阻塞。

## 5 · 对照与变奏

### 不同时序 bug 模式

**重置 bug**(今天 cutscene):一个系统 set 了变量,另一个系统改回去。修复:加状态标志。

**stale data bug**:碰撞检测读的是"上一帧的位置",玩家位置已变。修复:重新计算或读最新。

**spawn timing bug**(今天 traversable):新实体没被本帧 collision 看到。修复:延迟 spawn。

**race condition**:多线程同时改一个变量。修复:锁 / 原子。

### 游戏引擎的"事件系统"

- **Unreal**:Gameplay tags + events,blueprint 可视化
- **Unity**:C# events + UnityEvents,序列化
- **Bevy**:`Events<T>` 资源,系统读写
- **Godot**:Signal 系统,节点间通信

所有都是"延迟 + 解耦"的变体。

### 历史演化

- **1980s**:单线程,顺序简单
- **1990s**:多线程渲染,时序复杂化
- **2000s**:job system / task parallelism
- **2010s**:ECS + 显式系统排序
- **2020s**:data-oriented + 显式 schedule

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"过场里玩家飞起来"是时序 bug,不是数值 bug?

**参考解答**:

数值 bug 是"公式错"——比如重力 = 100 而非 9.8,玩家飞快。改公式就好。

时序 bug 是"执行顺序错"——同样的代码,顺序不同,行为不同。

今天的 bug:过场系统 set Z = 5.0,然后物理模拟 set Z = 0(重力把玩家拉回地面)。代码各自正确,合起来错。

判断:**如果两个系统单独运行都对,合起来错**——大概率是时序 bug。

### Lv3 · 迁移设计

**题**:同样的"时序 bug"思路用在**网络同步**:服务器把玩家位置同步到客户端,客户端也接受本地输入改位置。

要求:

1. 服务器每 50ms 发一次位置快照
2. 客户端每帧接受输入改本地位置
3. 收到服务器快照时,本地位置"跳"到服务器位置
4. 现象:玩家自己移动时,会被服务器"拉回"(时序 bug)

提示:这是网游经典"server reconciliation"问题。修复:服务器把"已经处理的输入 id"放在快照里,客户端丢弃"已处理"的输入,只重放"未处理"的。

## 8 · Rust / Arch 落地代码

### 完整可跑示例:延迟 spawn

```rust
#[derive(Debug)]
struct Entity {
    id: u32,
    pos: (f32, f32, f32),
    kind: &'static str,
}

struct World {
    entities: Vec<Entity>,
    pending_spawns: Vec<Entity>,
    next_id: u32,
    frame: u32,
}

impl World {
    fn new() -> Self {
        Self {
            entities: vec![Entity { id: 0, pos: (0.0, 0.0, 0.0), kind: "player" }],
            pending_spawns: vec![],
            next_id: 1,
            frame: 0,
        }
    }

    // 延迟 spawn
    fn spawn(&mut self, kind: &'static str, pos: (f32, f32, f32)) {
        let id = self.next_id;
        self.next_id += 1;
        self.pending_spawns.push(Entity { id, pos, kind });
        println!("[frame {}] queued spawn: id={} kind={}", self.frame, id, kind);
    }

    // 物理模拟:遍历 entities(不含 pending)
    fn physics_step(&mut self) {
        let entity_count = self.entities.len();
        for entity in &self.entities {
            // 假装做碰撞检测
            if entity.kind == "player" {
                // 玩家头顶有平台吗?
                let has_platform_above = self.entities.iter().any(|e| {
                    e.kind == "traversable" && e.pos.2 > entity.pos.2
                });
                println!("[frame {}] physics: player sees {} platforms above",
                         self.frame, if has_platform_above { "platform" } else { "no platform" });
            }
        }
        println!("[frame {}] physics: {} entities this frame", self.frame, entity_count);
    }

    // 帧末:执行 pending spawns
    fn end_frame(&mut self) {
        self.frame += 1;
        for entity in self.pending_spawns.drain(..) {
            println!("[frame {}] spawn committed: id={} kind={}", self.frame, entity.id, entity.kind);
            self.entities.push(entity);
        }
    }

    fn step(&mut self, want_spawn: bool) {
        if want_spawn {
            self.spawn("traversable", (0.0, 0.0, 5.0));
        }
        self.physics_step();
        self.end_frame();
    }
}

fn main() {
    let mut world = World::new();

    println!("=== Frame 1: request spawn, but physics doesn't see it yet ===");
    world.step(true);

    println!("\n=== Frame 2: spawn committed last frame, physics now sees it ===");
    world.step(false);

    println!("\n=== Frame 3: still sees ===");
    world.step(false);
}
```

**预期输出**:
```
=== Frame 1: request spawn, but physics doesn't see it yet ===
[frame 0] queued spawn: id=1 kind=traversable
[frame 0] physics: player sees no platform above
[frame 0] physics: 1 entities this frame
[frame 1] spawn committed: id=1 kind=traversable

=== Frame 2: spawn committed last frame, physics now sees it ===
[frame 1] physics: player sees platform above
[frame 1] physics: 2 entities this frame
[frame 2] spawn committed: id=... (none)

=== Frame 3: still sees ===
[frame 2] physics: player sees platform above
...
```

**关键解释**:
- 第 1 帧 spawn 请求 → 加入 pending_spawns
- 第 1 帧 physics 只看 entities(1 个,无 platform)
- 第 1 帧 end_frame → pending_spawns 提交到 entities
- 第 2 帧 physics 看到 entities(2 个,有 platform)

如果不延迟(直接 spawn 加入 entities),第 1 帧 physics 就看到了——但这种"立即生效"在复杂场景里会引发"两阶段状态"(部分实体新,部分老),bug 多。

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
