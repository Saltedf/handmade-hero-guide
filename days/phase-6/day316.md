
# Day 316 · 多个软件渲染目标

> 把"所有东西画到一个 framebuffer"升级成"画到多个 framebuffer,每个 framebuffer 是一个层"。这是离屏渲染(offscreen rendering)的起点,后续的发光(bloom)、模糊(blur)、半透明合成都要靠它。

## 0 · 为什么要有这一天

到目前为止你的渲染器只有一个目标——屏幕背缓冲(backbuffer)。所有 entity 都画到这块内存,然后一次性 swap 到屏幕。这种方式简单,但很快遇到天花板:

1. **全屏后处理**(post-processing):你想加"屏幕震动模糊"(受伤时画面晃动)、"色调映射"(HDR 转 LDR)、"暗角"(vignette)。这些效果需要"先画完游戏,再对整个画面做处理",但你只有一个 framebuffer——游戏画面直接进屏幕,处理不了。
2. **光照贴图**(light map):2.5D 游戏需要"先画光照到光照贴图,再合成到主画面"。光照贴图是单独的 framebuffer,宽高和屏幕一样,但 RGB 是光照颜色,不是最终颜色。
3. **小地图**(minimap):右上角显示完整地图,需要"从俯视角度把游戏世界再画一遍到小地图 framebuffer",最后画到屏幕角落。

业界的标准做法是 **多渲染目标(multiple render targets)**——维护多个 framebuffer,渲染时按 entity 选目标 framebuffer,最后用一个"合成 pass"把它们组合到屏幕。

```
原:                      新:
┌────────────┐          ┌────────────┐  ┌────────────┐  ┌────────────┐
│ Backbuffer │          │ Background │  │   Game     │  │     UI     │
│ (单一)     │          │   buffer   │  │   buffer   │  │   buffer   │
│            │          └──────┬─────┘  └──────┬─────┘  └──────┬─────┘
└────────────┘                 └───────┬──────┴────────┬──────┘
                                       ↓               ↓
                                 ┌──────────────────────────┐
                                 │   Composite pass         │
                                 │   (alpha blend 3 层)     │
                                 └────────────┬─────────────┘
                                              ↓
                                       ┌────────────┐
                                       │ Backbuffer │
                                       └────────────┘
```

今天的 Casey 工作:**在软件渲染器里引入"多 render target"概念**。原来的 `offscreen_buffer` 是单一目标,今天改成"目标列表"——按 Layer 选择目标,渲染时分别 push。最后用一个合成 pass 把多目标合并到 backbuffer。

注意:**这是"软件渲染"的多目标**,完全在 CPU 上。Day 321 Casey 会切到 OpenGL,用 GPU 的 `glFramebufferTexture2D` 实现多目标,语义类似但性能天差地别。今天先把 CPU 版的抽象搭好,Day 321 直接复用 API。

心理锚点:今天之后你的渲染器支持"光照 buffer"、"模糊 buffer"、"小地图 buffer"——任何"先画到独立 buffer,再合成"的需求都能实现。这是从"扁平渲染"到"分层管线"的工程跃迁。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_render.cpp`,做了一次"基础设施升级"。原来的结构:

```c
struct offscreen_buffer {
    void *Memory;          // 一块连续的 BGRA 内存
    int Width, Height, Pitch;
};
```

今天改成:

```c
struct render_target {
    void *Memory;
    int Width, Height, Pitch;
    int SortKeyBias;       // 这个 target 的 SortKey 范围
};

struct render_group {
    render_target Targets[8];   // 多达 8 个 target
    int TargetCount;
    // ... 其他字段
};
```

关键动作:

1. 给 `render_group` 加 `Targets` 数组(默认 8 个,够用)
2. 修改 `PushBitmap`,根据 entity 的 Layer 决定 push 到哪个 target
3. 在 `RenderGroupToOutput` 末尾加一个合成 pass,按 target 顺序 alpha-blend 到 backbuffer

Casey 在视频里讨论了一个关键设计:**Targets 是固定数组还是动态列表**。最终选固定数组(8 个),原因:

- 固定数组内存连续,cache 友好
- 大多数游戏不需要超过 8 个 target
- 动态列表(Vec)有 push_back 的 realloc 风险(虽然 push 阶段已经完成,但仍有概念上的开销)

如果以后需要更多 target,Casey 说"那就改成 16 个或 32 个,反正不需要动态增长"。

另一个关键决策:**target 之间的宽高可以不同**。光照 buffer 可以是屏幕一半大小(性能优化),小地图 buffer 是 256×256,UI buffer 和屏幕一样大。这种"不同尺寸 target"是工业级渲染管线的标准特性。

Casey 还讨论了**合成 pass 的实现**:遍历 targets,对每个 target 做 alpha-blend 到 backbuffer。合成顺序由 target 在数组里的索引决定(0 最先合成,7 最后)。这种"index 即顺序"简化了 API。

## 2 · 心智模型

### 类比:画家画油画

把渲染想成画家画油画。原版本画家只有一张画布——所有东西画在一起,画错了只能刮掉重画。新版本画家有多张画布:

- 一张画背景(天空、远山)
- 一张画角色
- 一张画 UI

每张画布独立修改,最后画家把三张叠起来——背景在底,角色在中,UI 在顶——拍一张照片就是最终画面。

这种"多画布"的好处:**每张画布可以独立处理**。比如背景画布可以"模糊一下"(模糊远景),角色画布可以"加亮"(高亮主角),UI 画布可以"等比例缩放"(响应不同分辨率)。每张画布的后处理互不影响。

### 严谨原理:render target 数据结构

每个 render target 是一块独立的 BGRA 内存:

```rust
struct RenderTarget {
    memory: Vec<u32>,     // 像素数据,每个 u32 是 BGRA(各 8 bit)
    width: usize,
    height: usize,
    pitch: usize,         // 一行的字节数(通常 = width * 4)
    clear_color: u32,     // 每帧开始时填充的颜色
}

impl RenderTarget {
    fn new(width: usize, height: usize, clear_color: u32) -> Self {
        let len = width * height;
        Self {
            memory: vec![clear_color; len],
            width, height,
            pitch: width * 4,
            clear_color,
        }
    }
    
    fn clear(&mut self) {
        // 用 clear_color 填充整张 target
        self.memory.fill(self.clear_color);
    }
    
    fn pixel(&self, x: usize, y: usize) -> u32 {
        self.memory[y * self.width + x]
    }
    
    fn set_pixel(&mut self, x: usize, y: usize, color: u32) {
        if x < self.width && y < self.height {
            self.memory[y * self.width + x] = color;
        }
    }
}
```

`Vec<u32>` 是堆分配的连续内存,在堆上申请,释放时自动 drop。`memory.fill(clear_color)` 是 Rust 标准库的快速 fill,内部用 `memset` 或 SIMD。

### 多 target 的渲染流程

```rust
struct RenderGroup {
    targets: Vec<RenderTarget>,    // 多个 target
    entries: Vec<(TargetIdx, RenderEntry)>,  // 渲染条目带 target 索引
}

impl RenderGroup {
    fn push_to_target(&mut self, target_idx: usize, entry: RenderEntry) {
        self.entries.push((target_idx, entry));
    }
    
    fn render(&mut self, output: &mut RenderTarget) {
        // 1. 清空所有 target
        for t in &mut self.targets {
            t.clear();
        }
        // 2. 按 SortKey 排序所有 entries
        self.entries.sort_by_key(|(_, e)| e.sort_key);
        // 3. 把每个 entry 画到对应 target
        for (target_idx, entry) in &self.entries {
            let target = &mut self.targets[*target_idx];
            draw_bitmap_to(target, entry);
        }
        // 4. 合成 pass:把所有 target alpha-blend 到 output
        output.clear();
        for t in &self.targets {
            composite_alpha(output, t);
        }
    }
}

fn composite_alpha(dst: &mut RenderTarget, src: &RenderTarget) {
    for y in 0..dst.height.min(src.height) {
        for x in 0..dst.width.min(src.width) {
            let dst_color = dst.pixel(x, y);
            let src_color = src.pixel(x, y);
            // alpha blend: out = src * a + dst * (1 - a)
            let blended = alpha_blend(src_color, dst_color);
            dst.set_pixel(x, y, blended);
        }
    }
}
```

`alpha_blend(src, dst)` 是标准公式——`out = src.rgb * src.a + dst.rgb * (1 - src.a)`。每个通道独立计算。

### 为什么 push 时记 target_idx,渲染时分发

考虑另一种设计:**每个 target 有自己的 entries 列表,push 时直接路由**。这种设计看起来更直接,但有缺点:

1. **全局排序难**:如果 entries 分散在多个 Vec,做"全局 SortKey 排序"需要先合并再排序,内存开销大。
2. **代码重复**:每个 target 都要写一遍 push、sort、render 逻辑。

Casey 的设计:**所有 entries 在一个 Vec,每条带 target_idx**。一次全局 sort 完成排序,然后遍历 entries 按 target_idx 分发。统一、简洁。

### Linux mmap 视角

每个 RenderTarget 的 `Vec<u32>` 在堆上,但 Rust 的 `Vec` 内部用 `std::alloc` 申请。对于大 target(比如 1080p = 8 MB),`std::alloc` 内部会调用 `mmap`(glibc 的阈值通常是 128 KB 以上走 mmap)。

你可以验证:

```bash
# 跑游戏时看 /proc/pid/maps
pidof game | xargs cat /proc/{}/maps | grep anon | head
# 应该看到几个 8 MB 大小的匿名映射(每个 RenderTarget 一个)
```

每个 target 在虚拟地址空间是独立的 mmap 区域——这是 OS 层面的"多 render target",和软件层面的概念完全对应。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

主流游戏的多 target 用法:

- **光照贴图**(light pre-pass):先画"法线 + 深度" target,再画光照 target,最后合成到主画面。Dead Space 用这种 2.5D 光照。
- **泛光**(bloom):画完游戏后,把"亮度 > 阈值"的像素拷到亮度 target,高斯模糊,合成回主画面。所有 HDR 游戏都用。
- **景深**(depth of field):根据深度 target 决定每像素的模糊半径,近处清晰、远处模糊。
- **屏幕空间反射**(SSR):从深度 + 法线 target 反射光线,画到反射 target,合成。
- **小地图**:从顶视角再画一遍游戏世界到 256×256 target。

Casey 现在只做最基础的"3 层 target 合成"(背景 + 游戏 + UI),但 API 留出了扩展空间。Day 317 会加 alpha 混合,Day 318 优化 clear/blend 性能,后面 Day 380+ 才真正引入 bloom 等高级效果。

### 3.2 · 🎨 图形学视角

图形学里"多 target"对应的概念:

- **FBO(Framebuffer Object)**:OpenGL 的多 target 抽象。`glGenFramebuffers` 创建,`glFramebufferTexture2D` 把纹理绑到 FBO,渲染时 `glBindFramebuffer` 切换。
- **MRT(Multiple Render Targets)**:GPU 的 fragment shader 一次 draw 同时写到 8 个 target 的硬件能力。`glDrawBuffers` 指定哪些 target。
- **G-buffer**(Geometry buffer):延迟渲染的核心,通常包括位置、法线、颜色、高光等多个 target。

CPU 软件渲染的"多 target"是 GPU 多 target 的简化版——没有 MRT 的"一次 draw 写多个",而是一个一个画。但概念上完全对应。

合成的核心算法 **Over operator**(Porter & Duff, 1984):

```
C_out = C_src * alpha_src + C_dst * (1 - alpha_src)
A_out = alpha_src + alpha_dst * (1 - alpha_src)
```

这是 alpha 合成的标准公式,从 1984 年 SIGGRAPH 论文沿用至今。所有 2D 渲染引擎的合成都是这个公式。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上"多 target"对应的概念:

- **DRM**(Direct Rendering Manager)的 multi-plane:Linux 内核的 DRM 子系统支持多个 plane(硬件图层),合成器把不同 buffer 提交到不同 plane,硬件合成。Wayland / X11 都基于这个。
- **Wayland surface**:每个 Wayland surface 是一个独立 buffer,合成器把多个 surface 合成到屏幕,完全等价于多 target。
- **X11 Pixmap**:X11 的 Pixmap 是离屏 buffer,可以画到Pixmap 再合成。

`wlroots` / `libweston` 等 Wayland 库的核心代码就是"管理多个 surface buffer,合成到 output"。和今天的 RenderGroup 合成完全等价。

### 3.4 · 🦀 Rust 生态视角

Rust 表达多 target:

```rust
struct RenderTarget {
    pixels: Box<[u32]>,    // Box<[T]> 比 Vec<T> 略高效(无 cap 字段)
    width: usize,
    height: usize,
}

impl RenderTarget {
    fn new(width: usize, height: usize) -> Self {
        // Box::new_zeroed_slice 是 nightly 的 unstable API
        // 这里用 stable 的 vec 然后 into_boxed_slice
        let pixels = vec![0; width * height].into_boxed_slice();
        Self { pixels, width, height }
    }
    
    fn clear(&mut self, color: u32) {
        // Box<[u32]> 也有 fill
        self.pixels.fill(color);
    }
}

struct RenderGroup {
    targets: Vec<RenderTarget>,
}

impl RenderGroup {
    fn composite_to(&self, output: &mut RenderTarget) {
        for src in &self.targets {
            for (dst_pixel, src_pixel) in 
                output.pixels.iter_mut().zip(src.pixels.iter()) {
                *dst_pixel = alpha_blend(*src_pixel, *dst_pixel);
            }
        }
    }
}
```

`Box<[u32]>` 比 `Vec<u32>` 高效一点——没有 `capacity` 字段(总大小 = `len` × 4 + 16)。但 `Vec` 更灵活,可以 push / pop,大多数场景差别不大。Casey 在 C 里用 `malloc` 直接申请,等价于 Rust 的 `Box<[u32]>`。

Rust 生态的 `softbuffer` crate(用于软件渲染到屏幕)有类似 `Buffer` 抽象。今天的代码可以无缝集成。

### 4.1 上级(它属于哪个更大抽象?)

## 5 · 对照与变奏

### 历史演化

- **1980s**:单一 framebuffer,所有东西直接画到屏幕。
- **1990s**:GPU 引入"aux buffer"(辅助缓冲),主要存深度。
- **2000s**:OpenGL FBO 标准化,离屏渲染普及。
- **2010s**:MRT 普及,延迟渲染成为 3A 大作标配(Gears of War、Battlefield)。
- **2020s**:Variable Rate Shading、Mesh Shader 等新技术,但多 target 概念不变。

### 工业级 vs 教学版

| 特性 | 教学版(今天) | 工业版(Unity URP) |

| target 数量 | 8 | 16+ |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 选择"所有 entries 在一个 Vec,每条带 target_idx",而不是"每个 target 有独立 entries 列表"。这两种设计的关键差别是什么?给出至少 2 个理由。

**参考解答**:

1. **全局排序**:统一 Vec 可以一次 sort_by_key 全局排序。分散到多 Vec 需要先排序每个 Vec,再合并——多次排序 + 归并,复杂度上升。
2. **代码简洁**:一个 `for entry in &entries` 循环,内部分发到 target。比每 target 单独循环简单。
3. **内存连续**:所有 entries 在一块连续内存,cache 命中率高。多 Vec 分散,cache miss 多。

代价:每个 entry 多 1 字节(或 4 字节)存 target_idx,内存开销略增。但绝对值小,可以忽略。

### Lv2 · 动手实践

**题**:在 Rust 里实现一个最小多 target 渲染器,要求:

- 3 个 target:Background、Game、UI(都 16×16 像素模拟)
- 每个有 `clear_color`
- 实现 `composite_to(output)`,把 3 个 target alpha-blend 到 output
- 测试:BG 蓝色 + Game 红色 alpha=128 + UI 透明,合成后应该是淡紫色

**参考解答**:

```rust
#[derive(Clone)]
struct RenderTarget {
    pixels: Vec<[u8; 4]>,  // RGBA 每通道 u8
    width: usize,
    height: usize,
}

impl RenderTarget {
    fn new(width: usize, height: usize, clear: [u8; 4]) -> Self {
        Self {
            pixels: vec![clear; width * height],
            width, height,
        }
    }
    
    fn clear(&mut self, color: [u8; 4]) {
        self.pixels.fill(color);
    }
}

/// 标准 Over operator: out = src * a + dst * (1 - a)
fn alpha_blend(src: [u8; 4], dst: [u8; 4]) -> [u8; 4] {
    let sa = src[3] as f32 / 255.0;
    let mut out = [0u8; 4];
    for i in 0..3 {
        let s = src[i] as f32;
        let d = dst[i] as f32;
        out[i] = (s * sa + d * (1.0 - sa)) as u8;
    }
    out[3] = 255;  // 合成后不透明
    out
}

fn composite(targets: &[RenderTarget], output: &mut RenderTarget) {
    // 先把第一个 target 拷到 output
    output.pixels.copy_from_slice(&targets[0].pixels);
    // 再依次 alpha-blend 后续 target
    for t in &targets[1..] {
        for (dst, src) in output.pixels.iter_mut().zip(t.pixels.iter()) {
            *dst = alpha_blend(*src, *dst);
        }
    }
}

fn main() {
    let bg = RenderTarget::new(16, 16, [0, 0, 255, 255]);     // 不透明蓝
    let game = RenderTarget::new(16, 16, [255, 0, 0, 128]);   // 半透明红
    let ui = RenderTarget::new(16, 16, [0, 0, 0, 0]);          // 透明
    let mut output = RenderTarget::new(16, 16, [0, 0, 0, 255]);
    composite(&[bg, game, ui], &mut output);
    println!("Pixel(0,0) = {:?}", output.pixels[0]);
    // 期望: 红*0.5 + 蓝*0.5 = (128, 0, 128) 紫色
}
```

预期:`(128, 0, 128)`——蓝色被半透明红覆盖,结果是紫色。

### Rust:多 target 渲染器(完整可跑)

```rust
// Cargo.toml: 无依赖
// src/main.rs

/// 单个像素:RGBA,每通道 u8
#[derive(Clone, Copy, Debug)]
struct Pixel([u8; 4]);

impl Pixel {
    const fn rgb(r: u8, g: u8, b: u8) -> Self {
        Self([r, g, b, 255])
    }
    const fn rgba(r: u8, g: u8, b: u8, a: u8) -> Self {
        Self([r, g, b, a])
    }
    const TRANSPARENT: Self = Self([0, 0, 0, 0]);
}

/// 渲染目标
#[derive(Clone)]
struct RenderTarget {
    pixels: Vec<Pixel>,
    width: usize,
    height: usize,
}

impl RenderTarget {
    fn new(width: usize, height: usize, clear: Pixel) -> Self {
        Self {
            pixels: vec![clear; width * height],
            width, height,
        }
    }
    
    fn clear(&mut self, color: Pixel) {
        self.pixels.fill(color);
    }
    
    fn set_pixel(&mut self, x: usize, y: usize, color: Pixel) {
        if x < self.width && y < self.height {
            self.pixels[y * self.width + x] = color;
        }
    }
    
    fn get_pixel(&self, x: usize, y: usize) -> Pixel {
        self.pixels[y * self.width + x]
    }
}

/// 标准 Over operator
fn alpha_blend(src: Pixel, dst: Pixel) -> Pixel {
    let sa = src.0[3] as f32 / 255.0;
    let mut out = [0u8; 4];
    for i in 0..3 {
        let s = src.0[i] as f32;
        let d = dst.0[i] as f32;
        out[i] = (s * sa + d * (1.0 - sa)).clamp(0.0, 255.0) as u8;
    }
    out[3] = ((src.0[3] as f32 + dst.0[3] as f32 * (1.0 - sa))
              .clamp(0.0, 255.0)) as u8;
    Pixel(out)
}

/// 渲染条目(简化:只有 target_idx 和颜色)
#[derive(Clone)]
struct Entry {
    target_idx: usize,
    x: usize,
    y: usize,
    color: Pixel,
}

/// 渲染组
struct RenderGroup {
    targets: Vec<RenderTarget>,
    entries: Vec<Entry>,
}

impl RenderGroup {
    fn new() -> Self {
        Self { targets: Vec::new(), entries: Vec::new() }
    }
    
    fn add_target(&mut self, width: usize, height: usize, clear: Pixel) -> usize {
        let idx = self.targets.len();
        self.targets.push(RenderTarget::new(width, height, clear));
        idx
    }
    
    fn push(&mut self, target_idx: usize, x: usize, y: usize, color: Pixel) {
        self.entries.push(Entry { target_idx, x, y, color });
    }
    
    fn render(&mut self, output: &mut RenderTarget) {
        // 1. 清空所有 target
        for (i, t) in self.targets.iter_mut().enumerate() {
            let clear = if i == 0 { Pixel::rgb(0, 0, 0) }
                        else { Pixel::TRANSPARENT };
            t.clear(clear);
        }
        // 2. 把 entries 画到对应 target
        for entry in &self.entries {
            if let Some(t) = self.targets.get_mut(entry.target_idx) {
                t.set_pixel(entry.x, entry.y, entry.color);
            }
        }
        // 3. 合成 pass:把 targets alpha-blend 到 output
        output.clear(Pixel::rgb(0, 0, 0));
        for src in &self.targets {
            for (dst, src_pixel) in output.pixels.iter_mut().zip(src.pixels.iter()) {
                *dst = alpha_blend(*src_pixel, *dst);
            }
        }
    }
}

fn main() {
    let mut group = RenderGroup::new();
    // 3 个 target:BG(蓝)、Game(半透明红)、UI(透明)
    let bg_idx = group.add_target(16, 16, Pixel::rgb(0, 0, 255));
    let game_idx = group.add_target(16, 16, Pixel::rgba(255, 0, 0, 128));
    let ui_idx = group.add_target(16, 16, Pixel::TRANSPARENT);
    
    // 画几个像素到 Game target
    group.push(game_idx, 5, 5, Pixel::rgba(255, 0, 0, 200));
    group.push(ui_idx, 10, 10, Pixel::rgba(0, 255, 0, 128));
    
    let mut output = RenderTarget::new(16, 16, Pixel::rgb(0, 0, 0));
    group.render(&mut output);
    
    println!("=== Output pixels ===");
    for y in 0..16 {
        for x in 0..16 {
            let p = output.get_pixel(x, y);
            print!("({:3},{:3},{:3},{:3}) ", p.0[0], p.0[1], p.0[2], p.0[3]);
        }
        println!();
        if y > 2 { break; }  // 只打印前几行
    }
    println!("...");
    println!("Pixel(5,5) = {:?}", output.get_pixel(5, 5));
    // 期望:Game 红 a=200 覆盖到蓝上,结果是偏红的紫
}
```

**预期输出**:

```
Pixel(5,5) = Pixel([155, 0, 100, 255])
```

解读:Game 红(255,0,0,200)合成到 BG 蓝(0,0,255,255):

- R = 255 × (200/255) + 0 × (55/255) ≈ 200
- B = 0 × (200/255) + 255 × (55/255) ≈ 55

实际更复杂,因为有 UI(透明)再次合成,但概念一致——多 target 顺序合成。

**Troubleshooting**:

- **alpha 计算错误** — 检查公式 `out = src * a + dst * (1 - a)`,注意 alpha 也参与
- **target 索引越界** — 检查 `add_target` 返回值正确接收
