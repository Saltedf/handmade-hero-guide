
# Day 297 · 实体分离到 Z 层

> 之前实体都在一个平坦数组里,sort key 决定渲染顺序。今天 Casey 把实体**物理分离**到不同 Z 层数组——每层一个 Vec<Entity>。这是为后续 day 298-300 优化 sort 做准备。

## 0 · 为什么要有这一天

Day 295-296 的 Z-sort 是单一数组 + sort_by_key。这种方式有几个问题:

1. **每次 sort 都遍历所有实体**——1000 个实体每帧 sort 一次,即使其中 900 个是地面 tile
2. **不同层的 sort 逻辑不同**——地面 tile 不需要 y-sort,只需要 layer 顺序;角色需要 y-sort;UI 不需要 sort
3. **同 sort_key 抖动**——大量 tile 共享同一 sort_key,排序算法不稳定时画面抖动

解法:**按层分桶**。把实体按 Z 层分到不同数组,每层独立 sort + 渲染。这样:

- 每层 sort 只需考虑该层实体,数据量小
- 每层 sort 逻辑可独立配置(tile 层不 sort、角色层 y-sort)
- 同 sort_key 抖动只在同层内出现,易于诊断

这是经典的**桶排序**(bucket sort)思想——用空间换时间。Z 层固定(如 6 层),桶数量固定,每桶 sort 简单。

今天的代码量:重构 entity storage,从 `Vec<Entity>` 改成 `Vec<Vec<Entity>>`(每个内层 Vec 是一个 Z 层)。改动涉及 spawn、update、render 三处主循环。

心理锚点:看完今天,你应该理解"数据结构影响算法效率"——同样数据用不同结构,性能差几个数量级。

## 1 · Casey 今天做了什么

Casey 今天的几个动作:

1. **定义 Z 层枚举**——`enum ZLayer { Ground, Wall, Entity, Air, UI }`
2. **改造 entity storage**——`entities: Vec<Vec<Entity>>` 或 `HashMap<ZLayer, Vec<Entity>>`
3. **改 spawn 逻辑**——根据 entity 类型分配到对应 Z 层
4. **改 update 逻辑**——遍历所有 Z 层(但只更新 entity 和 air 层,ground/wall/ui 静态)
5. **改 render 逻辑**——按 Z 层顺序渲染,每层内部独立 sort

今天的产出是 entity storage 的**新形态**——分层数组。为 day 298-300 的 sort 优化铺路。

## 2 · 心智模型

### 类比:衣柜的分层抽屉

把 entity storage 想象成衣柜。旧代码下,所有衣服堆在一个大柜子里,你想找一件红 T 恤要翻整个柜子。新代码下,衣柜有多个抽屉——袜子抽屉、内衣抽屉、T 恤抽屉、外套抽屉。你找什么直接开对应抽屉,不用全翻。

Z 层就是抽屉:地面 tile 在 Ground 抽屉,角色在 Entity 抽屉,UI 在 UI 抽屉。渲染时按抽屉顺序打开(Ground → Entity → UI),每个抽屉内部简单 sort 一下就能画。

数据结构变化:

```
旧:Vec<Entity>  // 一个大柜子
新:Vec<Vec<Entity>>  // 多个抽屉,每个抽屉是 Vec<Entity>
```

查询变化:

```
旧:找所有 Player —— 遍历 1000 个 entity
新:找所有 Player —— 只遍历 Entity 抽屉(可能 50 个)
```

### 2.1 Z 层枚举

```rust
#[derive(Copy, Clone, Debug, PartialEq, Eq, Hash)]
enum ZLayer {
    Background = 0,   // 远景天空
    Ground = 1,        // 地面 tile
    Wall = 2,          // 墙
    Entity = 3,        // 角色、怪物
    Air = 4,           // 空中怪物
    UI = 5,            // UI overlay
}

impl ZLayer {
    fn render_order() -> [ZLayer; 6] {
        [ZLayer::Background, ZLayer::Ground, ZLayer::Wall,
         ZLayer::Entity, ZLayer::Air, ZLayer::UI]
    }
}
```

枚举值(0-5)就是渲染顺序——从小到大画。这样保证 Background 最先,UI 最后。

### 2.2 分层 storage

```rust
struct World {
    layers: Vec<Vec<Entity>>,  // index 是 ZLayer 的 usize
}

impl World {
    fn new() -> Self {
        Self { layers: vec![vec![], vec![], vec![], vec![], vec![], vec![]] }
    }

    fn spawn(&mut self, layer: ZLayer, entity: Entity) -> u32 {
        let id = self.next_id();
        let mut entity = entity;
        entity.id = id;
        self.layers[layer as usize].push(entity);
        id
    }

    fn layer(&self, l: ZLayer) -> &[Entity] {
        &self.layers[l as usize]
    }

    fn layer_mut(&mut self, l: ZLayer) -> &mut Vec<Entity> {
        &mut self.layers[l as usize]
    }
}
```

存储用 `Vec<Vec<Entity>>` 而非 `HashMap<ZLayer, Vec<Entity>>`,因为 Z 层固定 6 个,数组索引比 hash 快。

### 2.3 跨层查询

某些操作要跨层查询,如"怪物追玩家"——怪物在 Entity 层,玩家也在 Entity 层(同层);但"找最近空闲树"——familiar 在 Entity 层,树在 Ground 层(跨层)。

```rust
impl World {
    fn find_in_any_layer(&self, id: u32) -> Option<&Entity> {
        for layer in &self.layers {
            if let Some(e) = layer.iter().find(|e| e.id == id) {
                return Some(e);
            }
        }
        None
    }

    fn find_nearest_tree(&self, from: Vec2) -> Option<u32> {
        let mut best: Option<(u32, f32)> = None;
        // 树在 Ground 层
        for tree in &self.layers[ZLayer::Ground as usize] {
            if !self.is_tree_free(tree.id) { continue; }
            let dist = (tree.pos - from).length();
            match best {
                None => best = Some((tree.id, dist)),
                Some((_, d)) if dist < d => best = Some((tree.id, dist)),
                _ => {}
            }
        }
        best.map(|(id, _)| id)
    }
}
```

跨层查询遍历多个 layer,稍慢但只在需要时调用。

### 2.4 渲染流程

```rust
fn render(world: &World) {
    for layer in ZLayer::render_order() {
        let entities = world.layer(layer);
        let mut sorted = entities.iter().collect();
        sorted.sort_by_key(|e| intra_layer_sort_key(e, layer));
        for e in sorted {
            draw(e, world.fog_for_layer(layer));
        }
    }
}

fn intra_layer_sort_key(e: &Entity, layer: ZLayer) -> u32 {
    match layer {
        ZLayer::Background | ZLayer::Ground | ZLayer::Wall | ZLayer::UI => 0,
        // 这些层不 sort(顺序无所谓,或按 spawn 顺序)
        ZLayer::Entity | ZLayer::Air => e.pos.y as u32,  // 按 y sort
    }
}
```

每层 sort 逻辑独立——这是分层架构的额外收益。

---

**总结**:今天的核心是**数据结构重构**——entity 从单一数组改成 Z 层数组。每层独立 sort,跨层查询遍历多桶。这是为 day 298-300 的 sort 算法优化做准备。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

分层 storage 是 2D 游戏行业标准。Unity 的 SpriteRenderer 有 `sortingLayer`,Godot 有 `z_index`,Bevy 有 `RenderLayers` Component。

工业级分层的好处:

- **批量渲染**——同层的 sprite 用同一 material,GPU 可以 batch(一次 draw call 画多个 sprite)
- **culling 简单**——某层不可见时(如关闭 UI),整层跳过
- **debug 友好**——可视化时只画某层

Casey 在 day 297 做最小版本,商业引擎的 RenderLayers 还处理 camera 可见性、material batch 等。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核里类似分层:**per-CPU 数据**。每个 CPU 有自己的数据数组,避免锁竞争。

```c
// linux/percpu-defs.h(简化)
DEFINE_PER_CPU(int, my_counter);
// 展开成:extern int my_counter[NR_CPUS];

// 访问
this_cpu_inc(my_counter);  // 当前 CPU 的 counter++,无需锁
```

游戏 entity 按 Z 层分桶,内核数据按 CPU 分桶——都是"用空间分桶避免全局竞争"。

另一个对应:**slab allocator**。Linux 内存分配按对象大小分桶(8 bytes、16 bytes、32 bytes...),分配时找对应大小的桶。比通用的 malloc 快几个数量级。

### 3.3 · 🦀 Rust 生态视角

Rust 表达分层 storage 有几种模式:

**模式 1:Vec<Vec<Entity>>(今天 Casey)**

```rust
struct World { layers: Vec<Vec<Entity>> }
```

简单。索引是 usize,数组访问快。

**模式 2:HashMap<ZLayer, Vec<Entity>>**

```rust
struct World { layers: HashMap<ZLayer, Vec<Entity>> }
```

灵活(可动态加层),但 hash 慢。

**模式 3:typed fields**

```rust
struct World {
    background: Vec<Entity>,
    ground: Vec<Entity>,
    wall: Vec<Entity>,
    entity: Vec<Entity>,
    air: Vec<Entity>,
    ui: Vec<Entity>,
}
```

类型最安全(每层有名字),但加层要改 struct。

Casey 在 HH 选模式 1——平衡灵活和性能。

**Rust 所有权注意**:`layer_mut` 返回 `&mut Vec<Entity>`,借用整个 `self.layers[layer]`。如果要同时 mut 借用多个 layer:

```rust

// 编译错:同时 mut 借用 world.layers 两处
```

解决:`split_at_mut` 或 `split_first_mut`:

```rust
let (ground_part, rest) = world.layers.split_at_mut(ZLayer::Ground as usize);
let ground = &mut ground_part[ZLayer::Ground as usize - 1];  // 不直观
// 更简洁:用 helper
```

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么不用 `HashMap<u32, Vec<Entity>>` 而用 `Vec<Vec<Entity>>`?HashMap 更灵活不是吗?

**参考解答**:对 Z 层场景,`Vec<Vec>` 比 `HashMap` 优:

1. **索引快**:Vec 索引是 O(1) 直接指针加法,HashMap 是 O(1) 但要 hash + 探测
2. **缓存友好**:Vec 在内存连续,HashMap 内部桶分散
3. **层固定**:Z 层就 6 个,固定索引 0-5 就够。HashMap 的灵活性浪费

HashMap 适合"层动态扩展"场景——但 Z 层不会动态扩展,所以 Vec 更合适。

### Lv2 · 动手实践

**题**:实现分层 World,有 3 层(Ground、Entity、UI)。spawn 一些实体到不同层,渲染时按层顺序画。

完成标准:渲染顺序为 Ground → Entity → UI,验证同层内按 y sort。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, PartialEq, Eq, Hash)]
enum ZLayer { Ground = 0, Entity = 1, UI = 2 }

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

#[derive(Copy, Clone, Debug)]
struct Entity {
    id: u32,
    pos: Vec2,
    name: &'static str,
}

struct World {
    layers: Vec<Vec<Entity>>,
    next_id: u32,
}

impl World {
    fn new() -> Self {
        Self { layers: vec![vec![], vec![], vec![]], next_id: 0 }
    }

    fn spawn(&mut self, layer: ZLayer, pos: Vec2, name: &'static str) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        self.layers[layer as usize].push(Entity { id, pos, name });
        id
    }

    fn render(&self) {
        for layer in [ZLayer::Ground, ZLayer::Entity, ZLayer::UI] {
            println!("Layer {:?}", layer);
            let mut sorted: Vec<&Entity> = self.layers[layer as usize].iter().collect();
            // Entity 层按 y sort,其他层按 id(即 spawn 顺序)
            match layer {
                ZLayer::Entity => sorted.sort_by_key(|e| e.pos.y as u32),
                _ => sorted.sort_by_key(|e| e.id),
            }
            for e in &sorted {
                println!("  {} at y={:.0}", e.name, e.pos.y);
            }
        }
    }
}

fn main() {
    let mut w = World::new();
    // Ground
    w.spawn(ZLayer::Ground, Vec2::new(0.0, 100.0), "grass1");
    w.spawn(ZLayer::Ground, Vec2::new(0.0, 200.0), "grass2");
    // Entity
    w.spawn(ZLayer::Entity, Vec2::new(50.0, 200.0), "monster");
    w.spawn(ZLayer::Entity, Vec2::new(50.0, 100.0), "player");
    // UI
    w.spawn(ZLayer::UI, Vec2::new(0.0, 0.0), "hp_bar");

    w.render();

    // 验证:Entity 层应按 y 排序(player y=100 先,monster y=200 后)
}
```

**每行解释**:
- `Vec<Vec<Entity>>` — 三层桶
- `layers[layer as usize]` — usize 索引,ZLayer 是 enum 需 as 转换
- `sort_by_key` 不同层用不同 key——体现分层架构的灵活性

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 历史脉络与工业实践

1990 年代 id Software 的 Doom(1993)用 BSP tree + painter's algorithm——排序在编译期完成,运行时 O(N) 遍历。Quake(1996)首次用 Z-buffer(GPU 硬件),彻底解决排序问题。

2D 游戏排序的演化:

- **1985-1990**:无 sort,固定 layer(Super Mario Bros)
- **1990-1995**:Y-sort 在 JRPG 普及(最终幻想 6、超时空之轮)
- **1995-2005**:Multi-layer Y-sort(星际争霸、暗黑破坏神 2)
- **2005-2015**:引擎内置 sort(Unity、GameMaker)
- **2015-2025**:GPU + sort 混合(bevy、Unreal)

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
