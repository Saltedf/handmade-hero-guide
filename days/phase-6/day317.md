# Day 317 · 多渲染目标 alpha 混合

> 昨天 Casey 引入了多 target,但合成 pass 用的是"朴素 alpha blend"——每像素 src+dst 浮点运算。今天 Casey 把 alpha 混合做得正确、高效,并讨论半透明合成的几个细节陷阱。

## 0 · 为什么要有这一天

昨天的多 target 合成有个隐含 bug:**alpha 通道处理不正确**。具体说,如果你有 3 个 target(BG、Game、UI),前两个都是不透明,UI 有半透明:

```
BG (alpha=255) → Game (alpha=255) → UI (alpha=128)
```

朴素 alpha blend(`out = src*src.a + dst*(1-src.a)`)在合成 BG 时,把 BG 的 alpha 混进 output 的 alpha;合成 Game 时又混一次;合成 UI 时再混一次。最后 output 的 alpha 是个奇怪的累加值——可能是 200,可能是 230,取决于混合顺序。

这在屏幕上看不出来(屏幕不需要 alpha),但如果 output 还要继续合成到更大的画布(比如小地图合成到主画面),错误 alpha 会导致半透明错误。

业界的标准做法叫 **预乘 alpha(premultiplied alpha)**——纹理存储时把 RGB 预先乘以 alpha,合成时用更简单的公式:

```
朴素后乘 alpha:                    预乘 alpha:
out.rgb = src.rgb * src.a          out.rgb = src.rgb + dst.rgb * (1 - src.a)
       + dst.rgb * (1 - src.a)     out.a   = src.a + dst.a * (1 - src.a)
out.a   = src.a + dst.a * (1 - src.a)
```

预乘 alpha 的合成少一次乘法(`src.rgb * src.a` 已经预存在纹理里),性能提升;更重要的是**数学正确**——预乘 alpha 在多次合成后结果一致,不会出现朴素 alpha 的顺序依赖 bug。

今天的 Casey 工作:**把多 target 合成从朴素 alpha 改成预乘 alpha**。这需要:

1. 所有 target 的 clear_color 改成预乘格式(透明像素 = (0,0,0,0),不透明 = (R,G,B,255))
2. push bitmap 时把 src 的 RGB 预乘 alpha
3. 合成公式简化:`out = src + dst * (1 - src.a)`

心理锚点:今天之后你的合成管线"数学正确",无论合成多少层结果都一致。这是工业级渲染管线的标准做法,Photoshop / After Effects / Unity / Unreal 都用预乘 alpha。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_render.cpp`,把昨天的 alpha blend 重写。原来的代码:

```c
void CompositePixel(uint32 *dst, uint32 src) {
    // 朴素 alpha(错误)
    float a = (src >> 24) & 0xFF) / 255.0f;
    uint32 result_rgb = src_rgb * a + dst_rgb * (1 - a);
    *dst = (result_rgb << 8) | ...;
}
```

今天改成:

```c
void CompositePixelPremul(uint32 *dst, uint32 src) {
    // 预乘 alpha
    float a = (src >> 24) & 0xFF) / 255.0f;
    uint32 result_rgb = src_rgb + dst_rgb * (1 - a);
    // 注意:src_rgb 已经预乘,不用再乘 a
    *dst = (result_rgb << 8) | ...;
}
```

关键动作:

1. 修改 `BitmapLoad` 函数,加载 PNG 时把 RGB 预乘 alpha
2. 修改 `PushBitmap`,假设纹理已经是预乘格式,直接画
3. 修改 `CompositePixel`,用预乘公式
4. 修改 `ClearTarget`,clear_color 用预乘格式

Casey 在视频里详细讨论了 **"为什么要预乘 alpha"** 这一经典话题。他指出三个原因:

1. **数学一致**:`(A over B) over C = A over (B over C)`。朴素 alpha 不满足这个结合律,合成顺序敏感。
2. **性能**:预乘后合成公式少一次乘法。每像素 1 次乘法 vs 2 次,1080p 下差别可观。
3. **抗锯齿**:边缘像素的 alpha < 255,预乘后边缘正确混合,朴素 alpha 容易出现"暗边"。

Casey 还提到一个反直觉的事实:**预乘 alpha 后,RGB 值永远不会超过 alpha 对应的"亮度"**。比如 alpha=128 的红色,预乘后 RGB 是 (128, 0, 0),不可能 (255, 0, 0)。这种约束让"哪些颜色组合合法"更明确。

## 2 · 心智模型

### 类比:有色玻璃叠加

把 alpha blend 想象成有色玻璃叠加。每层玻璃有颜色 + 不透明度(alpha)。

- **朴素 alpha**(后乘):每层玻璃的颜色"透明度衰减"——颜色 = 实际颜色 × 透明度。叠加时计算 `新色 = 上层实际色 × 上层透明度 + 下层色 × (1 - 上层透明度)`。
- **预乘 alpha**:玻璃出厂时就把"实际色 × 透明度"标在上面。叠加时直接加 `新色 = 上层预乘色 + 下层色 × (1 - 上层透明度)`,少一步乘法。

预乘的好处:**多层玻璃叠加时,顺序不影响结果**。你可以先叠 A+B 再叠 C,也可以先叠 B+C 再叠 A,结果一样。这是因为预乘让合成操作变成"加权平均"的纯线性运算。

### 严谨原理:alpha 数学

#### 朴素 alpha(non-premultiplied)

```
合成 A over B:
out.rgb = A.rgb × A.a + B.rgb × (1 - A.a)
out.a   = A.a + B.a × (1 - A.a)
```

测试结合律:`(A over B) over C` 是否等于 `A over (B over C)`?

计算 `(A over B) over C`:

```
Step 1: AB.rgb = A.rgb × A.a + B.rgb × (1 - A.a)
Step 2: (AB over C).rgb = AB.rgb × AB.a + C.rgb × (1 - AB.a)
       = [A.rgb × A.a + B.rgb × (1 - A.a)] × [A.a + B.a × (1 - A.a)]
         + C.rgb × (1 - [A.a + B.a × (1 - A.a)])
```

复杂。展开后不等于 `A over (B over C)`。所以**朴素 alpha 不满足结合律**。

#### 预乘 alpha(premultiplied)

```
合成 A over B:
out.rgb = A.rgb + B.rgb × (1 - A.a)        // A.rgb 已经预乘,不再 ×a
out.a   = A.a + B.a × (1 - A.a)
```

测试结合律:`(A over B) over C`:

```
Step 1: AB.rgb = A.rgb + B.rgb × (1 - A.a)
Step 2: (AB over C).rgb = AB.rgb + C.rgb × (1 - AB.a)
       = A.rgb + B.rgb × (1 - A.a) + C.rgb × (1 - [A.a + B.a × (1 - A.a)])
       = A.rgb + B.rgb × (1 - A.a) + C.rgb × (1 - A.a)(1 - B.a)
```

展开 B over C 部分:

```
BC.rgb = B.rgb + C.rgb × (1 - B.a)
A over (BC):
     = A.rgb + BC.rgb × (1 - A.a)
     = A.rgb + [B.rgb + C.rgb × (1 - B.a)] × (1 - A.a)
     = A.rgb + B.rgb × (1 - A.a) + C.rgb × (1 - B.a)(1 - A.a)
```

完全相等!所以**预乘 alpha 满足结合律**。这是它数学正确的核心证明。

### 实现细节:加载时预乘

PNG 文件存储的是后乘 alpha(标准格式),加载时需要转换:

```rust
fn load_png_premul(data: &[u8]) -> Vec<[u8; 4]> {
    // 假设 data 是 RGBA,后乘
    let mut out = Vec::with_capacity(data.len() / 4);
    for chunk in data.chunks(4) {
        let r = chunk[0] as u32;
        let g = chunk[1] as u32;
        let b = chunk[2] as u32;
        let a = chunk[3] as u32;
        // 预乘:rgb = rgb * a / 255
        let pr = (r * a / 255) as u8;
        let pg = (g * a / 255) as u8;
        let pb = (b * a / 255) as u8;
        out.push([pr, pg, pb, a as u8]);
    }
    out
}
```

注意 `(r * a / 255)` 用 u32 计算,避免 u8 溢出。结果是 `[pr, pg, pb, a]`——RGB 已乘 alpha。

### 边缘问题:暗边(dark fringing)

朴素 alpha 在合成半透明边缘时会出现"暗边"——边缘像素 RGB 没有乘 alpha,合成时被错误地"以全亮度混入"。预乘 alpha 自动避免,因为边缘像素的 RGB 已经被 alpha 衰减。

```
朴素:                         预乘:
红色像素 (255, 0, 0, 1):     红色像素 (1, 0, 0, 1):
  合成到白底 (255,255,255):     合成到白底:
  out = (255*1/255 + 255*254/255)     out = (1 + 255*254/255)
      = (255, 254, 254) ≈ 白          = (1, 254, 254) ≈ 白
  但边缘像素 alpha 不是 1 而是 0/1:  边缘像素:
  out = (255*0/255 + 255*255/255)    out = (0 + 255) = 255 正确
      = 255 没问题
  
  但如果 RGB 不是纯色:           同样情况下:
  像素 (200, 0, 0, 1):          像素 (200/255, 0, 0, 1):
  out = (200*1/255 + ...)       out = (200/255 + ...) 正确
```

预乘在边缘细节上更准确,这是图像编辑器标配。

### Rust 表达

```rust
#[derive(Clone, Copy, Debug)]
struct PremulPixel {
    r: u8, g: u8, b: u8, a: u8,
}

impl PremulPixel {
    /// 预乘 alpha 合成
    fn over(self, dst: Self) -> Self {
        let inv_a = 255 - self.a as u32;
        let r = self.r as u32 + (dst.r as u32 * inv_a + 128) / 255;
        let g = self.g as u32 + (dst.g as u32 * inv_a + 128) / 255;
        let b = self.b as u32 + (dst.b as u32 * inv_a + 128) / 255;
        let a = self.a as u32 + (dst.a as u32 * inv_a + 128) / 255;
        Self {
            r: r.min(255) as u8,
            g: g.min(255) as u8,
            b: b.min(255) as u8,
            a: a.min(255) as u8,
        }
    }
}
```

注意 `(x + 128) / 255` 是"四舍五入"技巧——比 `x / 255`(直接截断)精度高。Casey 在 Day 041 的整数化技巧里讲过类似的。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的 alpha 合成标准:

- **Unity**:默认预乘(在 Import Settings 可选)
- **Unreal**:默认预乘
- **Godot**:默认后乘,但有"Premultiplied Alpha" 选项
- **Casey HH**:今天改为预乘

游戏行业的另一个话题是 **alpha blending 的混合模式(blend mode)**:

- **Normal**:`out = src + dst * (1 - src.a)` —— 标准合成,今天讨论的
- **Additive**:`out = src + dst` —— 加法混合,常用于火花、爆炸
- **Multiply**:`out = src * dst` —— 乘法,常用于阴影、滤镜
- **Screen**:`out = 1 - (1-src) * (1-dst)` —— 滤色,常用于光照

不同混合模式需要不同 shader 代码,GPU 用 `glBlendFunc` 配置。Casey 今天只做 Normal,Day 380 之后会加 Additive(发光特效)。

### 3.2 · 🎨 图形学视角

图形学里"预乘 alpha"概念是 Jim Blinn 和 Marc Olano 在 1998 年 SIGGRAPH 论文《Premultiplied Alpha》里系统化的,但思想可追溯到 1980s Pixar 的 RenderMan。

预乘 alpha 的图形学优势:

1. **线性空间混合正确**:线性 RGB 空间下合成,预乘保证结果正确。
2. **mipmap 正确**:纹理缩小时,边缘像素的 RGB 和 alpha 一起线性平均,避免后乘的"暗边"。
3. **GPU 友好**:GPU 的 `glBlendFunc(GL_ONE, GL_ONE_MINUS_SRC_ALPHA)` 是预乘公式,直接对应。

OpenGL 的标准混合配置:

```c
// 后乘 alpha(不推荐):
glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA);

// 预乘 alpha(推荐):
glBlendFunc(GL_ONE, GL_ONE_MINUS_SRC_ALPHA);
```

差别在第一个参数——后乘是 `GL_SRC_ALPHA`(让 GPU 在合成时再乘),预乘是 `GL_ONE`(已经预乘,不再乘)。性能差别微小,但正确性差别大。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的合成器(Weston / Mutter / picom)都默认预乘 alpha。Wayland 协议规定 `wl_buffer` 的内容必须是预乘格式(`WL_SHM_FORMAT_ARGB8888` 的预乘版)。

```c
// Wayland 客户端必须提供预乘 buffer
wl_shm_pool_create_buffer(pool, offset, width, height, stride, 
                          WL_SHM_FORMAT_ARGB8888);  // 这是预乘
```

如果你传后乘格式,合成器会用预乘公式合成,导致"半透明区域颜色偏暗"。Linux 上的"预乘 alpha"是事实标准,不可绕过。

PNG 解码库 `libpng` 默认输出后乘,需要在解码后手动转预乘。`stb_image` 同理。

### 3.4 · 🦀 Rust 生态视角

Rust 的图像处理 crate `image` 默认输出后乘 alpha。要做预乘需要手动转换:

```rust
use image::{GenericImageView, RgbaImage};

fn to_premul(img: &RgbaImage) -> RgbaImage {
    let mut out = RgbaImage::new(img.width(), img.height());
    for (x, y, pixel) in img.pixels().enumerate() {
        let a = pixel[3] as u32;
        out.put_pixel(x as u32, y as u32, 
            image::Rgba([
                (pixel[0] as u32 * a / 255) as u8,
                (pixel[1] as u32 * a / 255) as u8,
                (pixel[2] as u32 * a / 255) as u8,
                pixel[3],
            ]));
    }
    out
}
```

Rust 生态里 `png` crate 直接解码 PNG,不预乘;`image` crate 包装 png,也不预乘。Casey 的 HH 项目自己写 PNG 解码(Phase 7 的 Day 436+),所以可以一开始就预乘。

## 5 · 对照与变奏

### 历史演化

- **1970s 早期渲染**:没有 alpha 概念,所有 sprite 都不透明(用 color key 模拟透明,如绿色背景)
- **1980s alpha 概念**:Pixar / ILM 引入 alpha 通道,但后乘
- **1990s 预乘普及**:RenderMan、Photoshop 4.0 标配预乘
- **2000s GPU 标准化**:OpenGL 1.x 的 blend func 同时支持两种
- **2010s 现代引擎**:全部默认预乘,后乘仅保留 legacy 支持
- **2020s**:HDR + linear rendering 标配,预乘成为唯一正确选择

### 工业级 vs 教学版

| 特性 | 教学版(今天) | 工业版(Unreal) |
|---|---|---|
| 加载时预乘 | 是 | 是 |
| SIMD 合成 | 无 | 是(一次 8 像素) |
| GPU 加速 | 无 | shader 实现 |
| 混合模式 | 1 种(Normal) | 10+ |
| LUT | 无 | 颜色查找表 |

工业级用 **SIMD** 加速合成——一条指令处理 8-16 像素。Casey 的 CPU 版一次一像素,1080p 合成要几十毫秒;SIMD 版只要几毫秒。Day 431 Casey 会用 SIMD raycast,合成 SIMD 化是类似的优化。

### Lv1 · 概念辨析

**题**:预乘 alpha 比朴素 alpha 有什么本质优势?给出至少 3 个理由。

**参考解答**:

1. **数学正确(满足结合律)**:`(A over B) over C = A over (B over C)`,合成顺序不影响结果。朴素 alpha 不满足,导致"先合成 BG+Game 还是 Game+UI"结果不同。
2. **性能**:合成公式少一次乘法,1080p 下差别可观。

5. **mipmap 正确**:纹理缩小时,边缘像素的 RGB 和 alpha 一起平均,后乘会出现"暗色光环"。

### Lv2 · 动手实践

**题**:在 Rust 里实现预乘 alpha 合成,验证结合律。要求:

- `PremulPixel::over(dst)` 方法
- 测试 `(A over B) over C == A over (B over C)`,A、B、C 各自不同 alpha
- 对比朴素 alpha 不满足结合律

**参考解答**:

```rust
#[derive(Clone, Copy, Debug, PartialEq)]
struct PremulPixel { r: u8, g: u8, b: u8, a: u8 }

impl PremulPixel {
    fn over(self, dst: Self) -> Self {
        let inv_a = 255 - self.a as u32;
        Self {
            r: (self.r as u32 + (dst.r as u32 * inv_a + 128) / 255).min(255) as u8,
            g: (self.g as u32 + (dst.g as u32 * inv_a + 128) / 255).min(255) as u8,
            b: (self.b as u32 + (dst.b as u32 * inv_a + 128) / 255).min(255) as u8,
            a: (self.a as u32 + (dst.a as u32 * inv_a + 128) / 255).min(255) as u8,
        }
    }
}

#[derive(Clone, Copy, Debug)]
struct NaivePixel { r: u8, g: u8, b: u8, a: u8 }

impl NaivePixel {
    fn over(self, dst: Self) -> Self {
        let sa = self.a as f32 / 255.0;
        Self {
            r: (self.r as f32 * sa + dst.r as f32 * (1.0 - sa)) as u8,
            g: (self.g as f32 * sa + dst.g as f32 * (1.0 - sa)) as u8,
            b: (self.b as f32 * sa + dst.b as f32 * (1.0 - sa)) as u8,
            a: ((self.a as f32 + dst.a as f32 * (1.0 - sa)).min(255.0)) as u8,
        }
    }
}

fn main() {
    // 预乘 alpha:验证 (A over B) over C == A over (B over C)
    let a = PremulPixel { r: 200, g: 100, b: 50, a: 200 };
    let b = PremulPixel { r: 100, g: 50, b: 200, a: 128 };
    let c = PremulPixel { r: 50, g: 200, b: 100, a: 255 };
    
    let ab = a.over(b);
    let ab_c = ab.over(c);
    let bc = b.over(c);
    let a_bc = a.over(bc);
    
    println!("PREMUL: (A over B) over C = {:?}", ab_c);
    println!("PREMUL: A over (B over C) = {:?}", a_bc);
    println!("Equal? {}", ab_c == a_bc);  // true
    
    // 朴素 alpha:验证不满足
    let a = NaivePixel { r: 200, g: 100, b: 50, a: 200 };
    let b = NaivePixel { r: 100, g: 50, b: 200, a: 128 };
    let c = NaivePixel { r: 50, g: 200, b: 100, a: 255 };
    
    let ab_c = a.over(b).over(c);
    let a_bc = a.over(b.over(c));
    println!("\nNAIVE: (A over B) over C = {:?}", ab_c);
    println!("NAIVE: A over (B over C) = {:?}", a_bc);
    println!("Equal? {}", ab_c.r == a_bc.r && ab_c.g == a_bc.g);  // 可能 false
}
```

### Lv3 · 迁移设计

**题**:你的网络协议要支持"分包传输 + 合成"。一个文件分成 N 个 chunk,每个 chunk 有"重要性 alpha"。设计一个 chunk 合成 API,要求:

- 任意顺序合成结果一致
- 可以"撤销"已合成的 chunk
- chunk 数据是预乘格式

提示:预乘 alpha 满足结合律,所以任意顺序合成结果一致。"撤销"需要存储原始数据。

### Rust:预乘 alpha 合成(完整可跑)

```rust
// Cargo.toml: 无依赖
// src/main.rs

/// 预乘 alpha 像素
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
struct PremulPixel {
    r: u8, g: u8, b: u8, a: u8,
}

impl PremulPixel {
    const BLACK_OPAQUE: Self = Self { r: 0, g: 0, b: 0, a: 255 };
    const TRANSPARENT: Self = Self { r: 0, g: 0, b: 0, a: 0 };
    
    /// 从后乘 RGBA 创建预乘像素
    fn from_naive(r: u8, g: u8, b: u8, a: u8) -> Self {
        let af = a as u32;
        Self {
            r: ((r as u32 * af + 128) / 255).min(255) as u8,
            g: ((g as u32 * af + 128) / 255).min(255) as u8,
            b: ((b as u32 * af + 128) / 255).min(255) as u8,
            a,
        }
    }
    
    /// Over operator: self over dst
    fn over(self, dst: Self) -> Self {
        let inv_a = 255 - self.a as u32;
        Self {
            r: (self.r as u32 + (dst.r as u32 * inv_a + 128) / 255).min(255) as u8,
            g: (self.g as u32 + (dst.g as u32 * inv_a + 128) / 255).min(255) as u8,
            b: (self.b as u32 + (dst.b as u32 * inv_a + 128) / 255).min(255) as u8,
            a: (self.a as u32 + (dst.a as u32 * inv_a + 128) / 255).min(255) as u8,
        }
    }
}

/// 渲染 target,所有像素都是预乘格式
#[derive(Clone)]
struct PremulTarget {
    pixels: Vec<PremulPixel>,
    width: usize,
    height: usize,
}

impl PremulTarget {
    fn new(width: usize, height: usize, clear: PremulPixel) -> Self {
        Self {
            pixels: vec![clear; width * height],
            width, height,
        }
    }
    
    /// 把另一个 target 合成到自己(逐像素 over)
    fn composite_over(&mut self, src: &PremulTarget) {
        for (dst, s) in self.pixels.iter_mut().zip(src.pixels.iter()) {
            *dst = s.over(*dst);
        }
    }
}

fn main() {
    let width = 8;
    let height = 8;
    
    // 3 个 target:BG(蓝)、Game(半透明红)、UI(透明)
    let bg = PremulTarget::new(width, height, 
        PremulPixel::from_naive(0, 0, 255, 255));
    let game = PremulTarget::new(width, height,
        PremulPixel::from_naive(255, 0, 0, 128));
    let ui = PremulTarget::new(width, height,
        PremulPixel::TRANSPARENT);
    
    // 合成:BG -> Game -> UI
    let mut output = bg.clone();
    output.composite_over(&game);
    output.composite_over(&ui);
    
    println!("=== Output pixels (row 0) ===");
    for x in 0..width {
        let p = output.pixels[x];
        print!("({:3},{:3},{:3},{:3}) ", p.r, p.g, p.b, p.a);
    }
    println!();
    
    // 验证结合律:换顺序合成
    let mut alt = game.clone();
    alt.composite_over(&ui);
    let mut alt2 = bg.clone();
    alt2.composite_over(&alt);
    
    println!("\n=== 结合律验证 ===");
    println!("BG over (Game over UI) == (BG over Game) over UI? {}",
             output.pixels[0] == alt2.pixels[0]);
}
```

**预期输出**:

```
=== Output pixels (row 0) ===
(127,0,128,255) (127,0,128,255) ...

=== 结合律验证 ===
BG over (Game over UI) == (BG over Game) over UI? true
```

解读:蓝色 (0,0,255) 被半透明红 (255,0,0,128=预乘后 128,0,0,128) 合成,结果 (128, 0, 128) 紫色。结合律验证为 true,证明预乘 alpha 数学正确。

**Troubleshooting**:

- **结果颜色偏暗** — 检查 `from_naive` 是否预乘 RGB,合成时 src 不再乘 alpha
- **结合律验证失败** — 检查 `(x + 128) / 255` 的四舍五入,不同舍入策略可能微差
- **alpha 通道异常** — `out.a = src.a + dst.a * (1 - src.a)`,不要漏 alpha 合成
