# Day 305 · 在平台层使用内存 arena

> 拓扑排序需要临时分配图结构(节点、边、邻接表),每帧分配导致性能问题。今天 Casey 引入**内存 arena**——一大块预分配内存,临时数据从中"线性"分配,结束时整块重置。这是 HH 早期(day 026)就引入的 arena 的更深应用。

## 0 · 为什么要有这一天

游戏每帧 60 Hz,每帧做大量临时分配:

- 拓扑排序的图结构
- 中间排序结果
- 字符串拼接(debug 输出)
- 碰撞检测的对列表

每帧用 `Vec::push` 或 `Box::new` 会频繁分配/释放堆,导致:

1. **碎片化**——堆变零散,大块分配失败
2. **慢**——malloc/free 不是 O(1),有锁、有 metadata
3. **不可预测**——GC 语言尤其,但 Rust 的 allocator 也有抖动

解决方案:**arena allocator**(也叫 bump allocator、linear allocator)。

Arena 的核心思想:

1. 启动时分配一大块(几 MB)
2. 临时分配从这块"线性 bump"——指针往前推
3. 整个 frame 结束时,指针重置到起点
4. 没有单独 free,只有整块重置

性能:bump 是几条指令(指针加法),比 malloc 快 100 倍。无锁、无 metadata、无碎片。

Casey 在 day 026 引入 arena,但那是"游戏状态"的 arena(持久)。今天加**帧临时 arena**(frame transient arena)——每帧重置。

心理锚点:看完今天,你应该理解为什么高性能代码用 arena 而非 heap,以及 Rust 怎么安全地实现。

## 1 · Casey 今天做了什么

Casey 今天的动作:

1. **设计 frame arena**——大块内存 + 当前指针
2. **加 alloc 方法**——bump 分配,返回 &mut T
3. **加 reset 方法**——每帧开始时调用,指针回到起点
4. **把拓扑排序迁移到 arena**——图节点、边都用 arena 分配
5. **验证**——内存使用稳定,不再 malloc/free 抖动

今天的核心是**内存管理**——为高频临时数据设计的特殊分配器。

## 2 · 心智模型

### 类比:食堂的托盘

把 arena 想象成食堂的一摞托盘。

- 普通堆分配:每个客人来,服务员去仓库找一个托盘(malloc),吃完再放回仓库(free)。仓库越来越乱。
- Arena:启动时一摞托盘放在台面上。客人来了从台面上拿一个(bump pointer),吃完放回台面顶端(bump pointer 回退)。结束时把整摞托盘送洗(reset)。

托盘不"归还"到仓库,而是留在台面上反复用。无查找、无整理。

arena 的"指针"就是台面上的"下一个空位"——分配时往上走,重置时回到桌平面。

### 2.1 arena 结构

```rust
struct Arena {
    buffer: Box<[u8]>,   // 大块内存
    offset: usize,        // 当前分配位置
}

impl Arena {
    fn new(size: usize) -> Self {
        Self {
            buffer: vec![0u8; size].into_boxed_slice(),
            offset: 0,
        }
    }

    fn alloc<T>(&mut self, value: T) -> &mut T {
        // 对齐
        let align = std::mem::align_of::<T>();
        let aligned_offset = (self.offset + align - 1) & !(align - 1);
        let end = aligned_offset + std::mem::size_of::<T>();
        assert!(end <= self.buffer.len(), "arena out of memory");

        // 写入值
        let ptr = self.buffer[aligned_offset..].as_mut_ptr() as *mut T;
        unsafe {
            std::ptr::write(ptr, value);
        }
        self.offset = end;
        unsafe { &mut *ptr }
    }

    fn alloc_slice<T: Copy>(&mut self, len: usize) -> &mut [T] {
        let align = std::mem::align_of::<T>();
        let aligned_offset = (self.offset + align - 1) & !(align - 1);
        let end = aligned_offset + len * std::mem::size_of::<T>();
        assert!(end <= self.buffer.len());

        let ptr = self.buffer[aligned_offset..].as_mut_ptr() as *mut T;
        self.offset = end;
        unsafe { std::slice::from_raw_parts_mut(ptr, len) }
    }

    fn reset(&mut self) {
        self.offset = 0;
    }
}
```

**unsafe 用法**:`std::ptr::write` 写入裸指针,绕过 Rust 的所有权。这需要 unsafe——Rust 不知道我们写入的内存是不是有效。

**对齐**:`(offset + align - 1) & !(align - 1)` 是经典的"向上对齐"trick。例如 align=8,offset=5: `(5+7) & !7 = 12 & 0xFFF8 = 8`。8 是 5 之后的第一个 8 倍数。

### 2.2 在 arena 里构建图

```rust
fn build_graph_in_arena<'a>(
    arena: &'a mut Arena,
    entities: &[Entity],
) -> &'a mut GraphRef<'a> {
    let n = entities.len();
    let nodes: &mut [usize] = arena.alloc_slice(n);  // 每节点入度
    for x in nodes.iter_mut() { *x = 0; }

    // 假设我们先算所有边的数量(简化,实际可能 O(n²) 遍历)
    let max_edges = n * n;
    let edges: &mut [(usize, usize)] = arena.alloc_slice(max_edges);
    let mut edge_count = 0;

    for i in 0..n {
        for j in 0..n {
            if i == j { continue; }
            if occludes(&entities[i], &entities[j]) {
                edges[edge_count] = (i, j);
                edge_count += 1;
                nodes[j] += 1;
            }
        }
    }

    let graph = GraphRef {
        n,
        edges: &edges[..edge_count],
        in_degree: nodes,
    };
    arena.alloc(graph)
}
```

所有数据都在 arena 里,不调 malloc。

### 2.3 frame 流程

```rust
fn game_frame(arena: &mut Arena, entities: &[Entity]) {
    arena.reset();  // 清空上一帧的临时数据

    // 1. 构建图(临时)
    let graph = build_graph_in_arena(arena, entities);

    // 2. 拓扑排序(临时)
    let order = topo_sort_in_arena(arena, graph);

    // 3. 渲染
    for &idx in order {
        draw(&entities[idx]);
    }

    // 4. 不需要 free——下一帧 reset 自动清
}
```

整个 frame 只 reset 一次,中间没有 malloc/free。

### 2.4 lifetime 的处理

```rust
fn build_graph_in_arena<'a>(arena: &'a mut Arena, ...) -> &'a mut GraphRef<'a>
```

`'a` 是 arena 的借用的 lifetime。返回的 GraphRef 借用 arena,'a 内有效。下一帧 reset 前,GraphRef 必须丢弃。

Rust 借用检查器强制这点:

```rust
let graph = build_graph_in_arena(&mut arena, ...);  // 借用 arena
arena.reset();  // 编译错:arena 已被借用
```

修复:先 drop graph:

```rust
{
    let graph = build_graph_in_arena(&mut arena, ...);
    // 用 graph
}  // graph drop,arena 借用释放
arena.reset();  // OK
```

这是 Rust 所有权在 arena 模式下的纪律。

---

**总结**:今天的核心是**内存 arena**——预分配大块 + bump pointer。性能比 malloc 快 100 倍。Rust 实现需要 unsafe + lifetime,但更安全(借用检查器保证不悬空)。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核的内存分配层次:

- **Buddy allocator**:页级分配(4KB+)
- **Slab allocator**:小对象(8-8192 bytes)
- **kmalloc**:内核通用分配
- **vmalloc**:虚拟连续内存
- **per-CPU allocator**:每 CPU 独立,避免锁

游戏 arena 类似 Linux 的 slab——预分配固定大小对象池。但 arena 更激进,允许"整块重置"。

```bash

```

### 3.3 · 🦀 Rust 生态视角

Rust 的 arena 生态:

- **bumpalo**:流行 arena crate,API 友好
- **typed-arena**:类型化 arena(单一类型)
- **id-arena**:arena + id 引用(避免引用悬空)
- **generational_arena**:加 generation 防 ABA

`bumpalo` 的用法:

```rust
use bumpalo::Bump;
use bumpalo::collections::Vec;

let bump = Bump::new();
let v: Vec<i32> = Vec::new_in(&bump);
for i in 0..1000 {
    v.push(i);  // 不调 malloc,从 bump 分配
}
// v drop 不释放内存,只标记
// bump drop 才真正释放
```

`bumpalo::collections::Vec` 是 std Vec 的 arena 版,接口一致。

**Rust 所有权 vs Arena**:

Rust 的所有权模型在 arena 下有点别扭——arena 分配的对象 lifetime 是"直到 reset",Rust 借用检查器要确保这期间不悬空。bumpalo 用 `'bump` lifetime 解决,但用户要小心。

工业 Rust 游戏引擎(Bevy)用**Resource + System**模式间接避免 arena——Resource 是 global,系统的临时数据从 Resource 借。但底层仍可能用 arena。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:arena 的 reset 是 O(1) 还是 O(n)?为什么?

**参考解答**:O(1)。reset 只把 `offset = 0`,不遍历已分配数据。

已分配的数据虽然"逻辑上"释放了,但物理上还在 buffer 里——下一帧的分配会覆盖。Rust 的 Drop 在这种情况下**不调用**——arena 拿走所有权后,不 drop 内部对象。

这意味着:**arena 里不能放需要 Drop 的对象**(如 Box、String、Vec)——它们 drop 时不会清理内部资源。Arena 适合 Copy 或简单数据(数字、引用、array of primitives)。

### Lv2 · 动手实践

**题**:实现 Arena 和 alloc,测试:

1. 分配 100 个 i32,验证地址连续
2. reset 后再分配,地址从 0 开始
3. 分配超过容量时 panic

完成标准:`cargo run` 打印 100 个 i32 地址(连续),reset 后第一个新分配地址等于初始地址。

**参考解答**:

```rust
struct Arena {
    buffer: Box<[u8]>,
    offset: usize,
}

impl Arena {
    fn new(size: usize) -> Self {
        Self {
            buffer: vec![0u8; size].into_boxed_slice(),
            offset: 0,
        }
    }

    fn alloc<T>(&mut self, value: T) -> &mut T {
        let align = std::mem::align_of::<T>();
        let size = std::mem::size_of::<T>();
        let aligned = (self.offset + align - 1) & !(align - 1);
        let end = aligned + size;
        assert!(end <= self.buffer.len(), "arena OOM");

        let ptr = self.buffer[aligned..].as_mut_ptr() as *mut T;
        unsafe { std::ptr::write(ptr, value); }
        self.offset = end;
        unsafe { &mut *ptr }
    }

    fn reset(&mut self) {
        self.offset = 0;
    }
}

fn main() {
    let mut arena = Arena::new(4096);

    // 分配 100 个 i32,验证地址连续
    let mut addrs: Vec<usize> = vec![];
    for i in 0..10 {
        let v: &mut i32 = arena.alloc(i);
        addrs.push(v as *const i32 as usize);
    }
    println!("Addresses: {:x?}", addrs);
    // 验证连续:每两个相邻地址差 4(i32 大小)
    for w in addrs.windows(2) {
        assert_eq!(w[1] - w[0], 4, "Addresses not contiguous");
    }

    let first_before_reset = addrs[0];

    arena.reset();

    let v: &mut i32 = arena.alloc(42);
    let first_after_reset = v as *const i32 as usize;
    println!("After reset: {:x}", first_after_reset);

    // 重置后地址应该等于初始地址
    assert_eq!(first_before_reset, first_after_reset);

    println!("Arena tests passed!");
}
```

**每行解释**:
- `vec![0u8; size].into_boxed_slice()` — 分配堆内存并转 Box(独占所有权)
- `(offset + align - 1) & !(align - 1)` — 经典向上对齐
- `std::ptr::write` — unsafe 写入裸指针
- 重置后地址相同——证明 arena 复用同一块内存

use std::time::Instant;

fn bench_heap(n: usize) -> u128 {
    let start = Instant::now();
    let mut v: Vec<Box<i32>> = vec![];
    for i in 0..n {
        v.push(Box::new(i as i32));
    }
    start.elapsed().as_nanos()
}

fn bench_arena(n: usize, arena: &mut Arena) -> u128 {
    arena.reset();
    let start = Instant::now();
    let mut ptrs: Vec<*mut i32> = vec![];
    for i in 0..n {
        let p = arena.alloc(i as i32);
        ptrs.push(p as *mut i32);
    }
    start.elapsed().as_nanos()
}

fn main() {
    let n = 10000;
    let mut arena = Arena::new(1024 * 1024);  // 1MB

    let t1 = bench_heap(n);
    let t2 = bench_arena(n, &mut arena);

    println!("Heap: {} ns ({} ns/op)", t1, t1 / n as u128);
    println!("Arena: {} ns ({} ns/op)", t2, t2 / n as u128);
    println!("Arena is {:.1}x faster", t1 as f64 / t2 as f64);
    // 通常 10-50x
}

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
