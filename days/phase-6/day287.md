# Day 287 · 加大脑(AI)

> 昨天你把 `Brain` 这个概念从 `Type` 里抽出来了,但空的——所有实体的 brain 都是 `None`。今天 Casey 给每种实体填上具体的 brain:玩家有 PlayerBrain,怪物有 MonsterBrain,等等。**Brain 不再是占位符,它是 AI 的载体**。

## 0 · 为什么要有这一天

游戏里"AI"这个词被滥用得很厉害。讨论 RPG 时它指 NPC 的对白树,讨论 FPS 时它指敌人的射击逻辑,讨论 RTS 时它指资源采集策略。**Handmade Hero 的 AI 范围很窄但很典型**:让一个怪物追玩家、让一个随从跟着玩家、让一只蛇随机游走。这些是 2D 动作游戏 AI 的最小集合。

为什么这件事不能昨天一起做完?因为昨天的工作是**结构性的**——把 Brain 字段挂上,让代码结构支持"分离的行为"。今天的工作是**内容性的**——往这个结构里填具体的 AI 函数。**结构和内容分离**是工程上避免混乱的纪律:昨天 Casey 没想 AI 该怎么写,今天他不操心结构该怎么改。

加 brain 听起来简单——不就是个 match 加几行吗?但 Casey 在今天的实现里要做一个关键决定:**brain 函数怎么访问世界信息**。怪物要追玩家,它必须知道玩家在哪;蛇要随机游走,它必须有状态(当前方向、剩余时间)。这些都是 brain 的"输入和状态",设计错了,后面加 5 种 brain 会越来越痛苦。

**心理锚点**:看完今天,你应该能清晰地说出"如果我加一个新的 AI,我需要给 brain 函数传什么参数,brain 自己持久化什么状态"。这两个边界划清楚了,加 AI 就是机械工作。

## 1 · Casey 今天做了什么

Casey 在昨天建立的 Brain 结构上:

1. **为每种实体填上 brain**:`Player` 实体的 brain 是 `Player`(从 input 读方向),`Monster` 实体的 brain 是 `Monster`(追玩家)。
2. **设计 brain 函数签名**——它要拿到 entity 自己的 mut 引用、世界状态、输入、dt。这是个"上下文"(context)概念。
3. **brain 函数里做实际 AI 决策**——玩家 brain 读 input 设 velocity;怪物 brain 算到玩家的方向、设 velocity。
4. **保留 brain 的状态**——某些 AI 需要"记住"东西(蛇的游走方向、随从的当前位置),这些状态放在 brain payload 里。

注意:今天只填**基础的** brain。复杂的(Snake 的螺旋、Familiar 的弹性跟随)在 day 291-294 才填。

## 2 · 心智模型

### 类比:工作中的员工和经理

把每个实体想象成公司里的**员工**。员工每天来上班(每帧 update),他要做的不是按"我是张三"的标签干活,而是按"今天经理给了我什么任务"干活。

旧代码的世界观:张三的代码写在他名字下——`if name == "张三" { 写报告 }`。这意味着张三不能干别的活,因为他的活焊死在名字上。

新代码的世界观:**经理**(game loop)每天给每个员工发一份**任务书**(brain payload),员工照着任务书做事。今天张三拿的任务书是"追客户",明天可能换成"做表格",他照做——他不管自己叫什么,只管任务书。

"任务书"里可以带**状态**(客户在哪、几点要做完),也可以是**空**(没有特别指示,原地待命)。任务书每周可以换——昨天填"追客户",今天填"做表格",员工的"身份"不变。

这就是 brain 的工作方式。`update_entity` 是经理的派活函数,brain payload 是任务书,entity 是员工。

### 2.1 Brain 函数的签名

Brain 函数要做什么决策?以"怪物追玩家"为例,它需要:

- **知道玩家在哪**(world state)
- **知道自己在哪**(entity state)
- **写自己的速度**(mut access to entity velocity)
- **考虑时间**(dt)

所以签名至少:

```rust
fn brain_monster_chase(
    e: &mut Entity,         // 自己,需要改 velocity
    ctx: &Context,          // 只读世界状态
    dt: f32,
)
```

`Context` 是个**只读快照**——所有 brain 共享同一份,谁都不能改它。如果 brain 要改世界(比如怪物死亡时要删除怪物),那这个改动要在 update 主循环里做,不在 brain 里做。这是为了**避免 brain 互相踩**(A brain 删除了 B brain 还在用的实体)。

### 2.2 状态:在 brain payload 还是 entity 上?

考虑蛇的"游走方向"。这个状态只对蛇有意义,对玩家毫无意义。两种放法:

**放法 A**:每个 entity 都有 `wander_dir: Vec2` 字段,只有蛇用它。
```rust
struct Entity {
    pos: Vec2,
    vel: Vec2,
    wander_dir: Vec2,   // 大多数实体的浪费
    wander_timer: f32,
}
```

**放法 B**:蛇的 brain payload 自带这些字段,其他 brain 不需要。
```rust
enum Brain {
    Player,
    MonsterChase,
    SnakeWander { wander_dir: Vec2, wander_timer: f32 },  // 只在这里
}

struct Entity {
    pos: Vec2,
    vel: Vec2,
    brain: Brain,  // 紧凑
}
```

放法 B 更好,因为:
1. **空间效率**——蛇的状态只在蛇身上,玩家没有这些字段。
2. **类型安全**——你不能误用玩家的 `wander_dir`(因为它根本不存在)。
3. **加新 brain 不动 Entity 结构**——Entity 永远只有 pos/vel/brain,brain 内部扩展。

这是 Rust enum 比"加一堆 Optional 字段"优越的核心原因:**enum payload 强制每个 variant 只访问自己的数据**。

### 2.3 Brain 的"思考"和"执行"分离

Casey 的设计里,brain **只决定速度**,不直接改位置。位置更新是统一的物理代码:

```rust
fn update_entity(e: &mut Entity, ctx: &Context, input: &Input, dt: f32) {
    // 1. Brain 决定速度
    match e.brain {
        Some(Brain::Player) => {
            e.vel = input.dir() * 80.0;
        }
        Some(Brain::MonsterChase { .. }) => {
            if let Some(player) = ctx.player() {
                e.vel = (player.pos - e.pos).normalize() * 40.0;
            }
        }
        _ => {}
    }

    // 2. 物理统一应用速度
    e.pos += e.vel * dt;

    // 3. 碰撞统一处理(后面 day288)
}
```

这种**思考 vs 执行分离**让代码极其清晰:brain 只想"我要去哪",物理代码统一"怎么去"。如果碰撞出 bug,你知道是物理代码出问题;如果方向错,你知道是 brain 出问题。

### 2.4 Brain 的 Context 参数

`Context` 里有什么?所有 brain 都可能用到的世界信息:

```rust
struct Context<'a> {
    world: &'a World,         // 实体查询
    player_id: u32,           // 玩家 ID
    time: f32,                // 游戏总时间
    input: &'a Input,         // 输入
}
```

为什么不用全局变量?因为:
- 全局变量难追踪——任何 brain 都可能改任何全局,bug 难定位。
- 测试难——单元测试 brain 时,你要 mock 全局状态。
- 多线程难——Day 312+ Casey 会并行光照传播,这时全局 state 是噩梦。

Context 作为参数传入,所有依赖**显式**——一眼看出这个 brain 用了什么。

---

**总结**:今天的目标是把 brain 的"签名"和"内容"都填实。Brain 函数拿到 context + 自己的 mut 引用,决定 velocity。位置和碰撞留给统一的物理代码。状态只放在自己的 brain payload 里,不污染 Entity 通用字段。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

AI 设计在游戏行业是个**专门的学科**。最低层是"反应式 AI"(reactive):每帧根据当前状态决策——Casey 用的就是这种。再上一层是"行为树"(Behavior Tree):决策有层次,如"先找玩家 → 再决定攻击还是逃跑"。再上是"效用 AI"(Utility AI):每个行为打分,选最高分的执行(《模拟人生》用)。最上是"学习式 AI"(ML):神经网络,近年兴起。

**为什么 Casey 选反应式**?因为反应式简单、可预测、好调试。玩家不会问"这只怪物为什么刚才追我又突然跑了"——因为反应式 AI 没有突然变化,只有"如果你在视野内,就追"。复杂 AI 在 HH 这种"过程化探索"项目里是过度设计。

但 Casey 的设计**留了门**——因为 brain 是 enum,你以后可以扩展成"带状态机"的 brain,如 `MonsterBrain { state: MonsterState }`,其中 `MonsterState` 是 `Idle/Chasing/Attacking`。今天先做最简单的,留扩展空间。

工业实践里一个常见错误:**AI 决策太频繁**。如果每个怪物每帧都重新算"玩家在哪、最短路径",1000 个怪物的 AI 计算会爆 CPU。解决:**节流**(throttle)——大部分怪物每 10 帧决策一次。今天 Casey 不优化,但你要记住这是后面 Day 312+ 性能优化的方向。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核里"brain 函数"的对应物是**事件回调**。比如网络协议栈——每个协议(TCP、UDP、ICMP)注册一组回调,内核收到包时根据协议号调对应回调:

```c
// linux/net/protocol.h(简化)
struct net_protocol {
    void (*handler)(struct sk_buff *skb);  // 收到包时调用
    int  (*error_handler)(...);
    // ...
};
```

每个协议**只决定"这个包怎么处理"**,不改网络栈本身。这就是 brain 模式——决策和执行分离。

更直接的对位:**中断处理**。每个驱动注册一个 `irq_handler_t`,硬件触发中断时内核调它。中断处理函数**只读寄存器、设标志位**,真正的处理(如唤醒进程)在"下半部"(tasklet、workqueue)做。为什么分开?因为中断处理在中断上下文,不能睡眠、不能复杂操作。游戏里的对应:**brain 函数只算速度,不做重活**(如分配新实体、删除实体),重活留给主循环。

### 3.3 · 🦀 Rust 生态视角

Rust 表达 brain 函数有几种方式:

**方式 A:free function + match**

```rust
fn update_entity(e: &mut Entity, ctx: &Context, input: &Input, dt: f32) {
    match &mut e.brain {
        Some(Brain::Player) => brain_player(e, input),
        Some(Brain::MonsterChase { target_id }) => brain_monster_chase(e, ctx, *target_id),
        Some(Brain::SnakeWander { ref mut dir, ref mut timer }) => {
            brain_snake_wander(e, dir, timer, dt);
        }
        None => {}
    }
}

fn brain_player(e: &mut Entity, input: &Input) {
    e.vel = input.dir() * 80.0;
}

fn brain_monster_chase(e: &mut Entity, ctx: &Context, target_id: u32) {
    if let Some(target) = ctx.world.get(target_id) {
        let d = target.pos - e.pos;
        if d.length() > 1e-3 {
            e.vel = d.normalize() * 40.0;
        }
    }
}
```

**方式 B:method on Brain**

```rust
impl Brain {
    fn think(&mut self, e: &mut Entity, ctx: &Context, input: &Input, dt: f32) {
        match self {
            Brain::Player => brain_player(e, input),
            // ...
        }
    }
}
```

Casey 风格更接近 A——free function。原因:C 没有方法,只有函数, Casey 的思维模式是"函数 + switch"。Rust 里两种都常见,差别主要在风格。

**Rust 的所有权问题**:`brain_player(e, input)` 借用 `e: &mut Entity` 和 `input: &Input`。如果 input 来自 Entity 自己的字段,就有借用冲突——这就是为什么 input 单独传,不是 Entity 的字段。

**Box<dyn Brain>** 替代方案:

```rust
trait Brain {
    fn think(&mut self, e: &mut Entity, ctx: &Context, input: &Input, dt: f32);
}

struct Entity {
    pos: Vec2,
    vel: Vec2,
    brain: Option<Box<dyn Brain>>,
}
```

对比:
- Box<dyn Brain> 在堆上(每个 brain 一个 Box),分配开销
- Box<dyn Brain> 每次调用是虚函数(不可内联)
- Box<dyn Brain> 状态在 trait object 里(每个 brain struct 自己定义字段)

Casey 选 enum,因为 HH 不想要堆分配、不想要虚函数、所有 brain 状态集中在 enum 定义里一目了然。**Rust 游戏开发里 enum >> trait object**,除非 brain 种类运行时动态扩展。

## 4 · 认知地图

### 4.1 上级

- **反应式 AI(Reactive AI)** — 无状态或最小状态,每帧决策
- **状态/行为分离(State-Action Separation)** — 数据(状态)和逻辑(行为)分模块
- **上下文对象(Context Object)** — 把所有"环境信息"打包传递
- **类型状态模式(Type-State Pattern)** — 让类型系统帮你管状态机

### 4.2 同级

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| Reaction AI | 无状态,每帧重新决策 | 简单游戏 | ✅ Casey 选了 |
| FSM(Finite State Machine) | 有显式状态机 | NPC 对话、Boss 战 | HH 后续 Boss 可能用 |
| Behavior Tree | 树状决策,层次化 | 复杂 NPC | 不用,过度设计 |
| Utility AI | 多行为打分选最高 | 模拟人生类 | 不用 |
| GOAP | AI 自动规划路径 | FEAR、复杂 AI | 不用 |

### 4.3 下级

- **Brain 函数签名** — `(e, ctx, dt)` 三件套
- **Context 结构** — 只读世界快照
- **Brain payload 状态** — 每个 variant 自己的数据
- **决策-执行分离** — brain 只设 vel,不直接改 pos

## 5 · 对照与变奏

### AI 状态放哪:三种方案对比

| 方案 | 例子 | 优点 | 缺点 |
|---|---|---|---|
| 在 entity 通用字段 | `wander_dir: Option<Vec2>` | 简单 | 大多数实体浪费 |
| 在 brain payload | `SnakeWander { dir, timer }` | 紧凑,类型安全 | 加 variant 改 enum |
| 在外部 store | `snake_states: HashMap<Id, SnakeState>` | 解耦彻底 | 间接寻址慢 |

Casey 选第二种。第三种是 ECS 的做法,但 HH 还没到 ECS。

### 同一 AI 的不同表达

"追玩家"在三种实现下的样子:

**Reaction(今天)**:
```rust
fn chase(e: &mut Entity, target: Vec2) {
    e.vel = (target - e.pos).normalize() * 40.0;
}
```
怪物立刻调整方向,响应快但行为机械。

**带平滑(平滑追踪)**:
```rust
fn chase_smooth(e: &mut Entity, target: Vec2, dt: f32) {
    let desired = (target - e.pos).normalize() * 40.0;
    e.vel = e.vel.lerp(desired, dt * 4.0);  // 慢慢转向
}
```
怪物不会瞬间急转,看起来更自然。Casey 在 day 293(Familiar)用这个。

**带预测(动态追击)**:
```rust
fn chase_predict(e: &mut Entity, target: &Entity, dt: f32) {
    let lead = target.pos + target.vel * 0.5;  // 预测 0.5s 后位置
    e.vel = (lead - e.pos).normalize() * 40.0;
}
```
怪物会"提前量"——玩家直线跑时,怪物斜插拦截。这是高级 AI。

工业代码里这三种都有用,Casey 先用最简单的,后面慢慢加复杂度。这是工程上"先简单后优化"的标准节奏。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 的 brain 函数**只设 velocity,不设 position**。为什么不直接 `e.pos += dir * speed * dt` 在 brain 里?

**参考解答**:三方面原因:

1. **碰撞统一**:如果在 brain 里改 pos,每个 brain 都要单独处理碰撞——重复代码。统一在物理代码里改 pos,只写一次碰撞。
2. **可调试**:出 bug 时,你能清楚定位——"方向错了"在 brain,"穿墙了"在物理代码。如果 brain 改 pos,bug 可能同时来自两处。
3. **多步整合**:有些游戏要"前向欧拉"、"后向欧拉"、"Verlet",物理代码是单一控制点。brain 只输出 vel,物理代码怎么用 vel 是它的事。

这是经典的**关注点分离**:brain 想"要去哪",物理决定"怎么去"。

### Lv2 · 动手实践

**题**:实现一个 `Flee` brain——怪物在玩家靠近时逃跑。当玩家距离 < 200 时,monster 远离玩家;距离 >= 200 时,原地不动。

完成标准:写测试,玩家在 (0,0),怪物在 (100, 0),brain 输出 vel 朝 (-1, 0) 方向;玩家移到 (300, 0),brain 输出 vel 为零。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn length(self) -> f32 { (self.x * self.x + self.y * self.y).sqrt() }
    fn normalize(self) -> Self {
        let l = self.length();
        if l > 1e-6 { Self::new(self.x / l, self.y / l) } else { Self::new(0.0, 0.0) }
    }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
}

const FLEE_RADIUS: f32 = 200.0;
const FLEE_SPEED: f32 = 60.0;

// Flee brain:玩家近了就远离玩家
fn brain_flee(monster_pos: Vec2, player_pos: Vec2) -> Vec2 {
    let to_player = player_pos.sub(monster_pos);
    let dist = to_player.length();
    if dist < FLEE_RADIUS && dist > 1e-3 {
        // 反方向(远离玩家)
        to_player.normalize().mul(-FLEE_SPEED)
    } else {
        Vec2::new(0.0, 0.0)
    }
}

fn main() {
    // 玩家在原点,怪物在 (100, 0),距离 100 < 200,逃跑方向应是 (-1, 0)
    let v1 = brain_flee(Vec2::new(100.0, 0.0), Vec2::new(0.0, 0.0));
    println!("Close: ({}, {})", v1.x, v1.y);
    assert!(v1.x < 0.0 && v1.x.abs() > 50.0);  // 朝左
    assert!(v1.y.abs() < 1.0);

    // 玩家在 (300, 0),距离 300 > 200,不动
    let v2 = brain_flee(Vec2::new(100.0, 0.0), Vec2::new(300.0, 0.0));
    println!("Far: ({}, {})", v2.x, v2.y);
    assert!(v2.x.abs() < 1e-3 && v2.y.abs() < 1e-3);

    println!("Flee brain tests passed!");
}
```

**每行解释**:
- `to_player.normalize().mul(-FLEE_SPEED)` —— 归一化后乘负速度,得到朝相反方向的 vel。`-` 在向量的"反方向"语义下用 `mul(-k)` 表达(Rust 不强制实现 `Neg`,但 glam 等库都有)。
- `dist > 1e-3` 防止除零(怪物和玩家完全重叠时不能归一化)。
- FLEE_RADIUS 是 magic number——工业代码会放进 config 文件,但学习阶段直接写死够用。

### Rust 完整可跑示例

扩展 §7 Lv2,做成完整的多实体系统:

```rust
// src/main.rs
// 玩家追鼠标,怪物追玩家,演示 brain 模式

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y) }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
    fn length(self) -> f32 { self.x.mul_add(self.x, self.y * self.y).sqrt() }
    fn normalize(self) -> Self {
        let l = self.length();
        if l > 1e-6 { self.mul(1.0 / l) } else { Self::new(0.0, 0.0) }
    }
}

#[derive(Copy, Clone)]
enum Brain {
    Player,                                      // 由输入控制
    MonsterChase { target_id: u32 },             // 追玩家
    Flee { threat_id: u32, radius: f32 },        // 远离威胁
}

struct Entity {
    id: u32,
    pos: Vec2,
    vel: Vec2,
    brain: Option<Brain>,
}

struct World {
    entities: Vec<Entity>,
    next_id: u32,
}

impl World {
    fn new() -> Self { Self { entities: vec![], next_id: 0 } }

    fn spawn(&mut self, pos: Vec2, brain: Option<Brain>) -> u32 {
        let id = self.next_id;
        self.next_id += 1;
        self.entities.push(Entity { id, pos, vel: Vec2::new(0.0, 0.0), brain });
        id
    }

    fn get(&self, id: u32) -> Option<&Entity> {
        self.entities.iter().find(|e| e.id == id)
    }

    fn player_pos(&self) -> Vec2 {
        // 假设 id 0 是玩家
        self.get(0).map(|e| e.pos).unwrap_or(Vec2::new(0.0, 0.0))
    }

    fn update(&mut self, input_dir: Vec2, dt: f32) {
        let player_pos = self.player_pos();

        // 第一阶段:每个 brain 设 vel
        for e in self.entities.iter_mut() {
            let Some(brain) = e.brain else { continue; };
            match brain {
                Brain::Player => {
                    e.vel = input_dir.mul(80.0);
                }
                Brain::MonsterChase { target_id } => {
                    if let Some(t) = self.find(target_id) {
                        let d = t.sub(e.pos);
                        if d.length() > 1e-3 {
                            e.vel = d.normalize().mul(40.0);
                        } else {
                            e.vel = Vec2::new(0.0, 0.0);
                        }
                    }
                }
                Brain::Flee { threat_id, radius } => {
                    if let Some(t) = self.find(threat_id) {
                        let d = e.pos.sub(t);
                        let dist = d.length();
                        if dist < radius && dist > 1e-3 {
                            e.vel = d.normalize().mul(60.0);
                        } else {
                            e.vel = Vec2::new(0.0, 0.0);
                        }
                    }
                }
            }
        }

        // 第二阶段:统一应用 vel
        for e in self.entities.iter_mut() {
            e.pos = e.pos.add(e.vel.mul(dt));
        }
    }

    // 借用冲突解决:单独的 find 方法返回 Option<Vec2>(复制)
    fn find(&self, id: u32) -> Option<Vec2> {
        self.entities.iter().find(|e| e.id == id).map(|e| e.pos)
    }
}

fn main() {
    let mut w = World::new();
    let player = w.spawn(Vec2::new(0.0, 0.0), Some(Brain::Player));
    let monster = w.spawn(Vec2::new(100.0, 0.0), Some(Brain::MonsterChase { target_id: player }));
    let _ = w.spawn(Vec2::new(200.0, 0.0), Some(Brain::Flee { threat_id: player, radius: 150.0 }));

    let dt = 0.1;
    for step in 0..10 {
        // 模拟玩家朝右移动
        let input_dir = Vec2::new(1.0, 0.0);
        w.update(input_dir, dt);
        let m = w.get(monster).unwrap();
        println!("step {}: monster at ({:.1}, {:.1})", step, m.pos.x, m.pos.y);
    }
}
```

**关键 Rust 特性**:

- `find(&self, id) -> Option<Vec2>` 复制位置返回——避免"在 iter_mut 里同时读其他实体"的借用冲突。这是 Rust 借用检查器强制的纪律:**不能在同一作用域里同时 mut 借用 self 又 immut 借用 self**。
- `let Some(brain) = e.brain else { continue; };` 是 let-else,处理 None 后立刻 continue。
- `match brain { ... }` 在 `Some(Brain::Player)` 下 unpack——这里 brain 是 Copy,直接 by-value match。
