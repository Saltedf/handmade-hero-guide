
# Day 427 · 调试光照闪烁

> Day 418 加了时序累积,效果很好,但 Casey 跑游戏发现**新的 bug**——某些光源位置的墙面**闪烁**(亮度跳变),不是平滑过渡。今天他调试这个 bug,发现根源是**采样位置每帧完全随机**,导致某些帧采样到遮挡物,某些帧采样到空隙,平均后亮度跳变。

## 0 · 为什么要有这一天

回顾 day418:时序累积用 EMA,每帧 4 个采样 + 历史累积。理论上方差小,平滑。但实际跑起来,有些墙面闪烁。

为什么?时序累积假设"每帧的样本是**无偏估计**"——期望等于真值。但**矩形面积的随机采样**有个微妙问题:

如果用**纯随机**采样(每帧用随机数生成器采 u, v ∈ [0, 1]),某帧可能采到全部在遮挡物后面的点(亮度 0),下一帧采到全部可见的点(亮度满)。EMA 后,亮度从 0 缓慢升到满,但人眼看到的是**抖动**。

工业解决方案:

1. **分层随机(stratified random)**:把矩形切 N 个等分,每等分内随机采一点。保证样本在矩形上**均匀分布**,不会聚在某一区域
2. **blue noise 采样**:更高级,样本间距均匀,抗噪
3. **低差异性序列(halton、hammersley)**:确定性序列,看起来随机但分布均匀,跨帧累积效果好

Casey 今天用**halton 序列**——一个低差异性(low-discrepancy)序列,每帧用不同的 halton 索引,跨帧累积等效于均匀采样。

更深层 bug:Casey 发现他的 RNG(随机数生成器)在**多线程下不安全**。rayon 并行执行时,多个线程共享一个 RNG,种子被覆盖,产生的"随机数"实际是周期性的,看起来像"闪烁"。

Rust 解决:**每线程独立 RNG**(`thread_local!` 或 `ThreadRng`),或用确定性的 halton 序列(不需要 RNG,跨线程一致)。

心理锚点:今天之后,你能识别"采样闪烁"的根源,知道 halton 序列 vs 纯随机的区别,能在多线程场景下用确定性序列避免竞争。

```rust
fn halton(index: u32, base: u32) -> f32 {
    let mut f = 1.0;
    let mut r = 0.0;
    let mut i = index;
    while i > 0 {
        f /= base as f32;
        r += f * (i % base) as f32;
        i /= base;
    }
    r
}

// 用法

let v = halton(frame_id, 3);  // base 3
let sample = rect.sample(u, v);
```

每帧 frame_id 增加,halton 序列产生均匀分布的点。多帧累积,样本越来越均匀。

## 2 · 心智模型

### 类比:测量教室面积

想象你估测教室面积。两种方法:

- **纯随机采样**:在教室里随机扔 100 个点,数多少落在教室里。方差大——某次扔点集中在中间,下次集中在边缘,估测值波动。
- **分层随机**:把教室分 100 格,每格随机扔 1 点。均匀覆盖,方差小。

纯随机的问题:**可能聚集**(clumping),某些区域采样多,某些区域无。分层强制均匀。

halton 序列是"分层随机"的更高级形态——**确定性序列**,每个新点自动填充之前的空隙,无需预先切格。

### 严谨原理:低差异性序列

**差异性(discrepancy)**:衡量点集均匀程度的数学量。纯随机的差异性高(可能聚集),低差异性序列的差异性低(均匀)。

**halton 序列**:基于不同素数基的反转数字序列。base 2 序列:1/2, 1/4, 3/4, 1/8, 5/8, 3/8, 7/8, ...。这些数字在 [0, 1] 内均匀分布,且每个新点和之前的点距离最大。

base 2 和 base 3 组合形成 2D 序列,均匀分布 [0, 1]²。

**hammersley 序列**:类似 halton,但一个维度用 index/total,适合固定数量采样。

工业的**Sobol 序列**是另一种低差异性序列,质量更好但实现复杂。pbrt 用 Sobol。

### 闪烁的数学根源

时序累积公式:`y[t] = α * x[t] + (1-α) * y[t-1]`。

如果 `x[t]` 在两帧之间剧烈变化(纯随机的极端情况),`y[t]` 会跳变。

具体:设 x = {0, 1, 0, 1, 0, 1, ...}(每帧采到全遮挡或全可见),α = 0.1。EMA:

- y[0] = 0.1*0 = 0
- y[1] = 0.1*1 + 0.9*0 = 0.1
- y[2] = 0.1*0 + 0.9*0.1 = 0.09
- y[3] = 0.1*1 + 0.9*0.09 = 0.181
- ...

`y[t]` 在 0.09 和 0.18 之间振荡,人眼看到"闪烁"。

正确采样(分层或 halton):`x[t]` 总是接近真值(比如 0.5),`y[t]` 平滑收敛到 0.5,无闪烁。

### Rust 视角:halton 实现

```rust
pub fn halton(mut index: u32, base: u32) -> f32 {
    let mut f = 1.0_f32;
    let mut r = 0.0_f32;
    while index > 0 {
        f /= base as f32;
        r += f * (index % base) as f32;
        index /= base;
    }
    r
}

pub struct HaltonSampler {
    pub frame_index: u32,
}

impl HaltonSampler {
    pub fn next_2d(&mut self) -> (f32, f32) {
        let u = halton(self.frame_index, 2);
        let v = halton(self.frame_index, 3);
        self.frame_index += 1;
        (u, v)
    }
}
```

每帧 `frame_index` 增加,产生新点。无 RNG,无状态,多线程安全。

### 多线程 RNG 的 bug

Casey 之前的 RNG 代码:

```rust
// bug 版
static mut RNG_STATE: u32 = 0;
fn next_random() -> f32 {
    unsafe {
        RNG_STATE = RNG_STATE.wrapping_mul(1664525).wrapping_add(1013904223);
        RNG_STATE as f32 / u32::MAX as f32
    }
}
```

`static mut` 共享状态,多线程读写竞争。rayon 并行执行时,两个线程同时改 RNG_STATE,产生"垃圾"随机数。

修复:用 `thread_local!` 或 `ThreadRng`(rand crate):

```rust
use rand::{thread_rng, Rng};

fn next_random() -> f32 {
    thread_rng().gen::<f32>()
}
```

`thread_rng` 每线程独立,无竞争。但**确定性丢失**——每次运行结果不同,不利于复现 bug。

最佳:**halton 序列**(确定性 + 多线程安全)。

### 3.2 · 🎨 图形学视角

低差异性序列的数学:

- **差异性问题**:在 [0, 1]^d 内放 N 个点,使得对任意子集 S 的体积和点数比例最小
- **最优解**:格点(lattice),但格点有规律性,有时不适用
- **halton**:基础解,实现简单
- **Sobol**:更高质量,工业主流

低差异性序列在**蒙特卡洛积分**里至关重要——同样样本数,方差比纯随机低几个数量级。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么纯随机采样会产生闪烁,而 halton 序列不会?具体说,在静态场景下,纯随机的方差是什么?

**参考解答**:纯随机采样,每帧的样本是独立同分布(IID)。每个样本有相同的方差 σ²。N 个样本的均值方差 = σ²/N。但每帧的"哪 N 个样本"不同,均值本身在帧间波动,波动幅度 = σ²/N。

静态场景下,真值(光的实际亮度)固定。但每帧估计值围绕真值波动,波动的"轨迹"看起来像闪烁。

halton 序列**不是 IID**——每个新点和之前点有相关性(自动填充空隙)。N 帧累积后,样本均匀分布,等效于"完美的均匀采样",方差几乎 0。所以无闪烁。

更技术性:halton 序列的"差异性"(discrepancy)是 O(log N / N),纯随机是 O(1/sqrt(N))。N=100 时,halton 的差异性比纯随机低 10 倍。

use glam::Vec3;

pub fn halton(mut index: u32, base: u32) -> f32 {
    let mut f = 1.0_f32;
    let mut r = 0.0_f32;
    while index > 0 {
        f /= base as f32;
        r += f * (index % base) as f32;
        index /= base;
    }
    r
}

pub struct HaltonSampler {
    pub base_index: u32,
}

impl HaltonSampler {
    pub fn new() -> Self { Self { base_index: 1 } }  // 0 给 NaN

    pub fn next_2d(&mut self) -> (f32, f32) {
        let u = halton(self.base_index, 2);
        let v = halton(self.base_index, 3);
        self.base_index += 1;
        (u, v)
    }

    pub fn next_n_2d(&mut self, n: u32) -> Vec<(f32, f32)> {
        (0..n).map(|_| self.next_2d()).collect()
    }
}

// 模拟光照计算
pub fn compute_lighting_at(samples: &[(f32, f32)], occlusion_pattern: fn(f32, f32) -> bool) -> f32 {
    // occlusion_pattern 返回 true 表示被遮挡(0 光),false 表示可见(1 光)
    let visible_count = samples.iter()
        .filter(|(u, v)| !occlusion_pattern(*u, *v))
        .count();
    visible_count as f32 / samples.len() as f32
}

fn main() {
    // 模拟:矩形光源,一半被遮挡
    let occlusion = |u: f32, v: f32| u < 0.5;  // 左半遮挡

    // 纯随机(模拟)
    let mut rng_state = 12345u32;
    let mut random_state = vec![];
    for _ in 0..16 {
        rng_state = rng_state.wrapping_mul(1664525).wrapping_add(1013904223);
        let u = rng_state as f32 / u32::MAX as f32;
        rng_state = rng_state.wrapping_mul(1664525).wrapping_add(1013904223);
        let v = rng_state as f32 / u32::MAX as f32;
        random_state.push((u, v));
    }

    println!("Pure random samples (16):");
    for (i, (u, v)) in random_state.iter().take(5).enumerate() {
        println!("  [{}] ({:.3}, {:.3})", i, u, v);
    }
    let r1 = compute_lighting_at(&random_state, occlusion);
    println!("  Result: {:.3} (expected ~0.5)\n", r1);

    // Halton
    let mut sampler = HaltonSampler::new();
    let halton_samples = sampler.next_n_2d(16);

    println!("Halton samples (16):");
    for (i, (u, v)) in halton_samples.iter().take(5).enumerate() {
        println!("  [{}] ({:.3}, {:.3})", i, u, v);
    }
    let h1 = compute_lighting_at(&halton_samples, occlusion);
    println!("  Result: {:.3} (expected ~0.5)\n", h1);

    // 多次运行,对比方差
    println!("Multi-run variance test (10 runs, 16 samples each):");
    let mut random_results = vec![];
    let mut halton_results = vec![];
    for run in 0..10 {
        // 模拟 RNG 不同种子
        rng_state = 12345 + run * 1000;
        let mut rs = vec![];
        for _ in 0..16 {
            rng_state = rng_state.wrapping_mul(1664525).wrapping_add(1013904223);
            let u = rng_state as f32 / u32::MAX as f32;
            rng_state = rng_state.wrapping_mul(1664525).wrapping_add(1013904223);
            let v = rng_state as f32 / u32::MAX as f32;
            rs.push((u, v));
        }
        random_results.push(compute_lighting_at(&rs, occlusion));

        let mut hs = HaltonSampler::new();
        hs.base_index = 1 + run * 16;  // 每次不同的起点
        let h_samples = hs.next_n_2d(16);
        halton_results.push(compute_lighting_at(&h_samples, occlusion));
    }

    let r_mean = random_results.iter().sum::<f32>() / 10.0;
    let r_var = random_results.iter().map(|x| (x - r_mean).powi(2)).sum::<f32>() / 10.0;
    let h_mean = halton_results.iter().sum::<f32>() / 10.0;
    let h_var = halton_results.iter().map(|x| (x - h_mean).powi(2)).sum::<f32>() / 10.0;

    println!("  Random: mean={:.3} variance={:.4}", r_mean, r_var);
    println!("  Halton: mean={:.3} variance={:.4}", h_mean, h_var);
    println!("  Halton is {:.1}x more stable", r_var / h_var);
}

```rust
use glam::Vec3;
use rayon::prelude::*;

pub fn halton(mut index: u32, base: u32) -> f32 {
    let mut f = 1.0_f32;
    let mut r = 0.0_f32;
    while index > 0 {
        f /= base as f32;
        r += f * (index % base) as f32;
        index /= base;
    }
    r
}

pub struct HaltonSampler {
    base_index: u32,
}

impl HaltonSampler {
    pub fn new(start: u32) -> Self {
        Self { base_index: start.max(1) }  // 0 给 NaN
    }

    pub fn next_2d(&mut self) -> (f32, f32) {
        let u = halton(self.base_index, 2);
        let v = halton(self.base_index, 3);
        self.base_index += 1;
        (u, v)
    }
}

#[derive(Clone)]
pub struct RectLight {
    pub center: Vec3,
    pub half_extent: Vec3,
    pub color: Vec3,
    pub intensity: f32,
}

impl RectLight {
    pub fn sample(&self, u: f32, v: f32) -> Vec3 {
        Vec3::new(
            self.center.x + (u - 0.5) * 2.0 * self.half_extent.x,
            self.center.y + (v - 0.5) * 2.0 * self.half_extent.y,
            self.center.z,
        )
    }

    pub fn illuminate_at(
        &self,
        point: Vec3,
        normal: Vec3,
        sampler: &mut HaltonSampler,
        samples: u32,
        occlusion: impl Fn(Vec3, Vec3) -> bool,
    ) -> Vec3 {
        let mut accum = Vec3::ZERO;
        for _ in 0..samples {
            let (u, v) = sampler.next_2d();
            let p = self.sample(u, v);
            let dir = p - point;
            let dist2 = dir.length_squared();
            if dist2 < 1e-6 { continue; }
            let n_dot_l = normal.dot(dir / dist2.sqrt()).max(0.0);
            if n_dot_l == 0.0 { continue; }
            if occlusion(point, p) { continue; }
            accum += self.color * self.intensity * n_dot_l / dist2;
        }
        accum / samples as f32
    }
}

fn main() {
    let light = RectLight {
        center: Vec3::new(5.0, 5.0, 0.0),
        half_extent: Vec3::new(1.0, 1.0, 0.0),
        color: Vec3::ONE,
        intensity: 100.0,
    };

    let point = Vec3::new(5.0, 0.0, 0.0);
    let normal = Vec3::Y;

    // 模拟 10 帧时序累积,看每帧亮度
    let mut history = Vec3::ZERO;
    let alpha = 0.3;
    let frame_count = 10;
    let samples_per_frame = 4;

    println!("Frame | new sample | EMA accumulated");
    let mut sampler = HaltonSampler::new(1);
    for frame in 0..frame_count {
        let new = light.illuminate_at(point, normal, &mut sampler, samples_per_frame, |_, _| false);
        history = new * alpha + history * (1.0 - alpha);
        println!("  {:3}  | {:.4}     | {:.4}", frame, new.x, history.x);
    }

    // 多线程测试:每个线程独立 sampler
    let frame_indices: Vec<u32> = (1..=8).collect();
    let results: Vec<Vec3> = frame_indices.par_iter().map(|&start| {
        let mut s = HaltonSampler::new(start);
        light.illuminate_at(point, normal, &mut s, 16, |_, _| false)
    }).collect();
    println!("\nMulti-thread results: {:?}", results);
    // 应该都接近真值,稳定
}

#    9  | (close to true) | (close to true)
# 收敛到稳定值,无闪烁

# 多线程结果:所有线程结果接近,无 RNG 竞争

cargo test halton
```

**Troubleshooting**:

- **halton(0, base) 返回 0** — index 从 1 开始,不要用 0
- **闪烁仍存在** — 检查是否还有 RNG 在某处用,替换为 halton
- **多线程结果不一致** — 每线程独立 sampler,起始 index 不同
- **halton 序列偏差** — 用 base 2 和 base 3(素数),不要用合数
- **多帧后亮度漂移** — α 太小,旧帧权重过大,调到 0.2-0.4


### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。

### 深度概念:数据导向设计

Casey Muratori 的标志性观点是 **Data-Oriented Design**(DOD,数据导向设计),与传统的 Object-Oriented Programming(OOP)对立。今天的代码隐含 DOD 思想。

OOP 把数据和方法绑定:

```rust
// OOP 风格
struct Player {
    pos: Vec3,
    inventory: Vec<Item>,
    fn update(&mut self, dt: f32) { ... }
    fn render(&self, canvas: &mut Canvas) { ... }
}
```

每 Player 是个"对象",有数据有方法。看起来自然,但 cache 不友好——Player 的 pos、inventory、方法指针散在不同内存区域,CPU 访问要跳来跳去。

DOP 把数据按"访问模式"分组:

```rust
// DOP 风格
struct World {
    positions: Vec<Vec3>,      // 所有实体的位置
    velocities: Vec<Vec3>,     // 所有实体的速度
    inventories: Vec<Vec<Item>>,  // 所有实体的库存
}

fn update_positions(world: &mut World, dt: f32) {
    for (pos, vel) in world.positions.iter_mut().zip(&world.velocities) {
        *pos += *vel * dt;
    }
}
```

所有 positions 在一段连续内存,CPU prefetcher 跟得上,cache 命中率 99%+。100 万实体的 update 在现代 CPU 上 < 1 ms。

Casey 在 HH day 305+ 大量用 DOD,memory arena 是基础设施。今天的 sort_rule 也隐含 DOD——按 layer + bottom_y 排序,本质上是把"位置数据"和"渲染顺序"分开。

**与 ECS 的关系**。Entity-Component-System(ECS)是 DOD 的极致化:数据完全按 Component 分(Component = 数据,无方法),System 是函数(Component → 行为)。bevy / Unity DOTS / Unreal Mass 都用 ECS。

学完 HH 你能直接读懂 bevy 源码——它的 `Query<(&Transform, &mut Velocity)>` 就是 Casey 的"positions + velocities"。

### 渲染管线的完整链路

今天讨论的 sort_rule 是渲染管线的一小步。完整的渲染流程:

```
1. 游戏逻辑更新(物理、AI、输入)
2. 收集渲染数据(可见性裁剪、LOD 选择)
3. 构建 sort_rule(今天的重点)
4. 排序所有可见 sprite
5. 提交到 GPU(或软渲染)
6. GPU 顶点 shader
7. 光栅化
8. 片段 shader(光照、纹理)
9. 后处理(色调映射、bloom、AA)
10. 显示
```

步骤 3-5 是 CPU 渲染,6-9 是 GPU 渲染。今天的 sort_rule 在步骤 3——决定绘制顺序。Phase 8 切 GPU 后,步骤 4-5 改为 batch + indirect draw,但 sort 仍在 CPU(因为 GPU sort 复杂,且通常不是瓶颈)。

工业级渲染引擎(Unreal Lumen、Unity HDRP)在每一步都做了大量优化:

- 步骤 2:用 BVH 加速可见性
- 步骤 4:用 radix sort + SIMD
- 步骤 5:用 indirect draw + MultiDrawIndirect
- 步骤 8:用 Bindless resources 减少 descriptor 更新

这些优化在 Casey HH 后期逐步引入。

### 常见 bug 与解决方案

**Bug 1: Sprite flicker**(闪烁)。两 sprite sort key 相同,每帧顺序不同。解决:加 spawn_id tie-breaker,保证稳定。

**Bug 2: Z-fighting**(深度冲突)。3D 渲染时两个 polygon 在同一深度,GPU depth buffer 精度不够,出现条纹。解决:用 reverse-Z(Phase 8)或调整 near plane。

**Bug 3: Sprite 在帧间跳跃**。物理引擎和渲染不同步,显示的 sprite 位置和实际位置差一帧。解决:固定时间步 + 插值渲染(Game Loop Pattern)。

**Bug 4: NaN 在 sort_key**。某 sprite 的 pos 计算出错产生 NaN,sort_key 是 NaN,sort 顺序不确定。解决:`partial_cmp(...).unwrap_or(Equal)`,且 debug 时检测 NaN 并 panic。

**Bug 5: 排序逆方向**。`sort_by(|a, b| ...)` 写反了 a 和 b,导致排序颠倒。解决:加单元测试覆盖每个分支,且跑 visual test 验证。

每个 bug 都是 Casey 在 HH 里真实遇到并解决的——HH 的价值就在这些"踩坑教学"。
