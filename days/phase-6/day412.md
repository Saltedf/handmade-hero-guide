
# Day 412 · 调试体素插值

> Day 411 把光源从点换成矩形后,墙面出现了不该有的"棋盘格"——一些体素亮、相邻体素暗,边界明显。今天 Casey 调试这个问题,发现根源是**体素插值**的边界处理 bug:他用了 `floor` 还是 `round`,用的方式不一致,导致采样点的归属在两个体素之间反复横跳。

## 0 · 为什么要有这一天

把矩形面积光接到体素光照系统后,Casey 看到**视觉伪影**:墙面光照不是平滑渐变,而是像棋盘一样一格亮一格暗,大小正好等于体素尺寸。这种伪影有个学名叫**走样(aliasing)**——连续信号(矩形面积)被离散网格(体素)采样时,采样频率不够高,高频分量混叠回低频。

为什么会走样?根本原因是**离散化误差**。想象你有一个 0.1 米宽的体素网格,一个 0.15 米宽的矩形光源。矩形的边缘正好压在两个体素的分界线上——你不知道把这部分光强算到左体素还是右体素。如果你的代码在某种情况下分给左、另一种情况下分给右,就会产生棋盘。

调试这种问题需要三个能力:
1. **能识别伪影**——知道"棋盘"不是渲染 bug,而是采样 bug
2. **能定位根源**——是数据结构、数学公式,还是边界条件
3. **能复现和验证**——构造最小可复现,改完一行验证

工业游戏开发中,80% 的图形 bug 是这种"看起来神秘、根源平凡"的问题。Casey 今天花了整集在它上面,这就是真实工程的样子。这个 bug 本身不复杂,但调试方法值得学。

心理锚点:今天之后,你能在自己的渲染器里识别"棋盘走样"的成因,知道 `floor` 和 `round` 在体素映射里的微妙差别,能用 ASCII 画一个 2D 体素网格的示意图来定位边界 bug。这种"画出问题"的能力,比写代码本身更重要。

## 1 · Casey 今天做了什么(HH 脉络)

Day 411 改完代码,Casey 跑起来看到棋盘格,意识到是体素插值的边界 bug。他的调试步骤:

1. **截一张问题图**,在视频里画红圈标出棋盘区域,用 ASCII 在白板重画
2. **缩小到最小复现**:写一个 2×2 体素的玩具场景,把矩形放在正中,看到光强被错误地分给一个体素而不是均匀分给四个
3. **打印中间值**:在体素注入函数里 `printf` 出每个被采样的点归属哪个体素索引,发现某些点在 `i=2` 和 `i=3` 之间漂移
4. **定位 bug**:`world_to_idx` 用 `floor`,但 `idx_to_world`(体素中心位置)用 `+0.5` 偏移,导致采样点在世界坐标和体素索引之间映射不一致
5. **修法**:统一用 `floor`,且 `idx_to_world(idx) = origin + (idx + 0.5) * voxel_size`(体素中心),让正反映射一致

Casey 强调,这种 bug 在静态数据上发现不了,只有当采样位置随时间变化(矩形中心可能略微抖动)时才暴露。这是**浮点数精度**和**整数索引**的边界冲突。

## 2 · 心智模型

### 类比:邮编与地图

想象你用邮编定位一个地址。邮编是离散的(整数),地址是连续的(经纬度)。一个地址属于哪个邮编?简单的规则:**看地址在哪个邮编区域内**。这就像体素:空间中的点属于哪个体素,看它在哪个立方体内。

但邮编有边界问题。如果地址正好压在两个邮编的分界线上(假设这条街东西两侧邮编不同),它属于哪个?现实中人为规定"以街中心为界"。代码里我们用 `floor` 或 `round`,但**两边的代码必须用同一个规则**。

如果定位代码用 `floor`(向下取整,0.9 → 0),而显示代码用 `round`(四舍五入,0.9 → 1),那么定位成"我在 0 号邮编",显示成"我在 1 号邮编",你就**找不到自己的地址**。这就是 Casey 的 bug。

### 严谨原理:坐标到体素的映射

设体素网格的原点是 `O`,体素边长 `s`。世界坐标 `p` 对应的体素索引 `i`:

```
i = floor((p - O) / s)
```

为什么用 `floor` 不用 `round`?**因为 floor 保证连续区间映射到连续整数区间**。考虑 p 从 0 到 s 连续变化:

- `floor((p - 0) / s)`:p=0 → 0,p=s/2 → 0,p=s-ε → 0,p=s → 1
- `round((p - 0) / s)`:p=0 → 0,p=s/2 → 0 or 1(取决于四舍五入规则),p=s → 1

`floor` 让 [0, s) 整个区间映射到 0,清晰且单调。`round` 在 s/2 处会跳变,导致同一区间分裂。

但 `round` 也有用——当你想找"最近的体素中心"时,应该用 `round((p - O - s/2) / s)`,这等价于"哪个体素的中心离 p 最近"。

### 体素中心的位置

体素 `i` 的中心在哪里?是 `O + (i + 0.5) * s`,不是 `O + i * s`(那是体素的"左下角")。这个 `+0.5` 偏移是 Casey bug 的关键——他某些地方用了中心,某些地方用了角。

### 反映射一致性

正确的代码:

```rust
fn world_to_idx(p: Vec3, origin: Vec3, voxel_size: f32) -> (i32, i32, i32) {
    let d = (p - origin) / voxel_size;
    (d.x.floor() as i32, d.y.floor() as i32, d.z.floor() as i32)
}

fn idx_to_world_center(i: i32, origin: Vec3, voxel_size: f32) -> Vec3 {
    origin + Vec3::new(
        (i as f32 + 0.5) * voxel_size,
        (i as f32 + 0.5) * voxel_size,
        (i as f32 + 0.5) * voxel_size,
    )
}
```

验证一致性:`world_to_idx(idx_to_world_center(i))` 应该返回 `i`。代入:

```
d = (O + (i + 0.5) * s - O) / s = i + 0.5
floor(i + 0.5) = i  ✓
```

正确。Casey 的 bug 是某个地方写了 `(i + 0.0)` 或 `(i + 1.0)`,破坏了这个一致性。

### 插值:三线性插值

光照从体素网格采样到任意点(像素位置)时,通常用**三线性插值(trilinear interpolation)**。给定一个点 p,它落在 8 个相邻体素之间,按权重混合 8 个体素的值。

```
取 floor 得到 8 个体素的左下角索引
取小数部分 (p - p_floor) / s 作为权重
分别在 x、y、z 三个方向上做线性插值
```

线性插值公式:`lerp(a, b, t) = a + (b - a) * t`,t ∈ [0, 1]。

三线性插值就是先在 x 方向插 4 次(得到 4 个 yz 平面的值),再在 y 方向插 2 次,最后在 z 方向插 1 次,共 7 次 lerp。

如果 `floor` 用错了(比如 `round`),插值权重会算错,某些点取相邻体素而不是这个体素的值,产生棋盘。

### 浮点数精度

更阴险的 bug:浮点数的精度问题。`(p - origin) / voxel_size` 在 p 接近某个体素边界时,可能由于浮点误差稍微小于整数(比如 2.9999... 而不是 3.0),`floor` 给出 2,但本来应该是 3。这导致"采样点正好在边界上"时归属不确定。

工业代码常加一个 epsilon:`floor((p - origin) / voxel_size + 1e-6)`。但加 epsilon 也可能引入新的边界 bug(把刚好属于体素 i 的点推到 i+1)。Casey 没加,保持简单。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

体素游戏(Minecraft、Teardown)对体素插值极度敏感:

- **Minecraft**:方块边界清晰,不需要插值,但光照(天空光、火把光)用体素网格存储,插值不当时洞穴里出现"棋盘光"
- **Teardown**:用 SDF(有符号距离场)+ 体素,光照在体素间过渡必须平滑

工业的解决方案:**光照贴图(lightmap)**——把光照预计算到 UV 空间(每三角形有自己的光照纹理),运行时只采样纹理,不做实时体素插值。但预计算时间长,不适合动态光源。HH 必须实时,所以插值必须做对。

### 3.2 · 🎨 图形学视角

体素插值是**信号重建**问题。连续信号被离散采样(存体素),再从离散重建连续(三线性插值)。Shannon 采样定理告诉我们:**采样频率必须大于信号最高频的两倍**。

矩形光源在边缘处有"高频"(从亮到暗的跳变),如果体素网格不够细,采样频率不足,就会出现走样。理论上要解决需要**低通滤波**——在存入体素前先把光强做空间平均,去掉高频分量。

Casey 没做严格低通,但 day429 的"多分辨率"是一种近似:用不同分辨率的体素网格分别存储不同频率的光照,合成时取长补短。

### 3.3 · 🐧 Linux 系统编程视角

Linux 文件系统的"块(block)"类比于体素。文件大小不是块大小的整数倍时,最后一个块浪费空间。文件系统用 `ceil(size / block_size) * block_size` 算占用。

这和体素的 `floor` 不同,因为文件系统**向上取整**(必须给完整块),体素映射**向下取整**(采样点属于哪个块看它落在哪个区间)。两种语义不同,但都是"连续到离散"的映射,都需要规则一致。

### 3.4 · 🦀 Rust 生态视角

Rust 表达体素网格:

```rust
pub struct VoxelGrid {
    pub origin: Vec3,
    pub voxel_size: f32,
    pub dims: (usize, usize, usize),
    pub data: Vec<Voxel>,  // 长度 dims.0 * dims.1 * dims.2
}

impl VoxelGrid {
    pub fn world_to_idx(&self, p: Vec3) -> Option<(i32, i32, i32)> {
        let d = (p - self.origin) / self.voxel_size;
        let i = d.x.floor() as i32;
        let j = d.y.floor() as i32;
        let k = d.z.floor() as i32;
        if i < 0 || j < 0 || k < 0 { return None; }
        if (i as usize) >= self.dims.0
            || (j as usize) >= self.dims.1
            || (k as usize) >= self.dims.2 { return None; }
        Some((i, j, k))
    }

    pub fn idx_to_center(&self, i: i32, j: i32, k: i32) -> Vec3 {
        self.origin + Vec3::new(
            (i as f32 + 0.5) * self.voxel_size,
            (j as f32 + 0.5) * self.voxel_size,
            (k as f32 + 0.5) * self.voxel_size,
        )
    }

    pub fn sample_trilinear(&self, p: Vec3) -> Vec3 {
        let d = (p - self.origin) / self.voxel_size;
        let i = d.x.floor() as i32;
        let j = d.y.floor() as i32;
        let k = d.z.floor() as i32;
        let tx = d.x - i as f32;
        let ty = d.y - j as f32;
        let tz = d.z - k as f32;

        // 8 个角点
        let mut corners = [[[Vec3::ZERO; 2]; 2]; 2];
        for dk in 0..2 {
            for dj in 0..2 {
                for di in 0..2 {
                    corners[di][dj][dk] = self.get(i + di, j + dj, k + dk);
                }
            }
        }

        // x 方向插值
        let c00 = corners[0][0][0].lerp(corners[1][0][0], tx);
        let c01 = corners[0][0][1].lerp(corners[1][0][1], tx);
        let c10 = corners[0][1][0].lerp(corners[1][1][0], tx);
        let c11 = corners[0][1][1].lerp(corners[1][1][1], tx);

        // y 方向插值
        let c0 = c00.lerp(c10, ty);
        let c1 = c01.lerp(c11, ty);

        // z 方向插值
        c0.lerp(c1, tz)
    }

    fn get(&self, i: i32, j: i32, k: i32) -> Vec3 {
        if i < 0 || j < 0 || k < 0 { return Vec3::ZERO; }
        let (i, j, k) = (i as usize, j as usize, k as usize);
        if i >= self.dims.0 || j >= self.dims.1 || k >= self.dims.2 { return Vec3::ZERO; }
        let idx = i + j * self.dims.0 + k * self.dims.0 * self.dims.1;
        self.data[idx].light
    }
}
```

注意 `+0.5` 偏移的一致性:`idx_to_center` 用 `(i + 0.5) * size`,`sample_trilinear` 的小数部分是 `d - floor(d)`,两者数学上互为反映射。

## 4 · 认知地图

### 4.1 上级

- **体素网格(Voxel Grid)** —— 3D 空间的均匀离散化,本日的主角
- **离散-连续映射** —— 任何把连续信号存到离散网格的代码都要面对这个抽象
- **三线性插值(Trilinear Interpolation)** —— 从体素网格重建连续信号的标准方法

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| 最近邻(Nearest) | 取最近体素的值 | 像素化效果 | 不用 |
| 三线性插值 | 8 个体素加权平均 | 平滑过渡 | ✅ |
| 三次插值(Cubic) | 64 个体素,样条 | 极致平滑,贵 | 不用 |
| 高斯插值 | 加权按高斯分布 | 抗走样 | 不用 |
| SDF 插值 | 距离场专用 | Teardown | 不用 |

三线性是性价比最高的选择,工业 GPU 硬件原生支持(`texture()` 函数自动三线性)。

### 4.3 下级

- **floor 映射** —— 连续坐标到整数索引的标准做法
- **lerp 函数** —— 线性插值,所有更高阶插值的原子
- **体素中心偏移 +0.5** —— 保证正反映射一致
- **8 角点查询** —— 三线性需要 8 个邻居
- **边界 clamp** —— 体素索引越界返回 0

## 5 · 对照与变奏

**同一问题在不同语境下的变体**:

| 语境 | 插值的形态 |

## 7 · 变式训练

### Lv1 · 概念辨析(读懂)

**题**:`floor` 和 `round` 在体素映射里都能用,但 Casey 选 `floor`,为什么?给一个具体场景,用 `round` 会产生 `floor` 不会的 bug。

**参考解答**:`floor` 保证连续区间映射到连续整数区间,无跳变。考虑 p 从 0 到 voxel_size 变化,`floor((p - O) / s)` 给出 [0, s) 全是 0,s 处跳到 1,单调。

`round` 在 p = s/2 处会跳变(0.5 → 1,四舍五入),导致 p 略小于 s/2 算 0,略大于 s/2 算 1。这意味着 `[0, s/2)` 和 `[s/2, s)` 分到不同体素——但 `[s/2, s)` 应该和 `[0, s/2)` 是同一个体素!这就是 bug。

具体场景:矩形光源中心在 `O + s/2`(正好在某体素边界),它的两个采样点 `(O + s/2 - ε)` 和 `(O + s/2 + ε)` 用 `round` 分别算到体素 0 和体素 1,导致光被分到两个体素,每个只有半强度。用 `floor` 时,两个采样点都算到体素 0,光全在那个体素,正确。

### Lv2 · 动手实践(改/写 Rust 代码)

**题**:写一个最小复现——2×2 体素网格,矩形光源覆盖全部 4 个体素。验证每个体素被注入的光强是否一致。完成标准:
- 用你的 `world_to_idx` + 注入逻辑,4 个体素亮度差异 < 1%
- 故意改用 `round`,看到棋盘(对角两亮两暗)
- 改回 `floor`,看到均匀

**参考解答**:

```rust
use glam::Vec3;

struct VoxelGrid {
    data: Vec<f32>,  // 长度 4
    voxel_size: f32,
}

impl VoxelGrid {
    fn world_to_idx(&self, p: f32) -> i32 {
        // 正确版:floor
        (p / self.voxel_size).floor() as i32
        // bug 版:((p / self.voxel_size).round()) as i32
    }

    fn inject(&mut self, p: f32, amount: f32) {
        let i = self.world_to_idx(p);
        if i >= 0 && (i as usize) < self.data.len() {
            self.data[i as usize] += amount;
        }
    }
}

fn main() {
    let mut grid = VoxelGrid { data: vec![0.0; 4], voxel_size: 1.0 };
    // 矩形光源覆盖 [0.4, 1.6],4 个体素 [0,1), [1,2), [2,3), [3,4)
    // 但我们只有 4 个体素 [0,1), [1,2), [2,3), [3,4)
    // 0.4-1.6 覆盖 [0,1) 完全,[1,2) 完全,[2,3) 部分(只到 1.6)
    // 实际我们模拟 2x2 体素, voxel_size = 1
    // 注入 10 个采样点
    for i in 0..10 {
        let p = 0.4 + 1.2 * (i as f32 + 0.5) / 10.0;
        grid.inject(p, 1.0);
    }
    println!("Voxels: {:?}", grid.data);
    // floor 版:大致 [2.x, 4.x, 3.x, 0] 或类似,但和棋盘的区别在对角线对称性
    // round 版:会出现"对角亮对角暗"棋盘
}
```

**关键解释**:
- 用 `floor` 时,采样点 [0.4, 1.6] 均匀分布到体素 0、1、2,数量大致相等
- 用 `round` 时,采样点 0.5 处四舍五入到 1(应该到 0),采样点 1.5 处到 2(应该到 1),导致每两个体素之间的边界处跳变
- 测试时把 `world_to_idx` 的两行交替注释,对比 `Voxels: [...]` 输出

use glam::Vec3;

#[derive(Clone)]
pub struct VoxelGrid {
    pub origin: Vec3,
    pub voxel_size: f32,
    pub dims: (usize, usize, usize),
    pub data: Vec<Vec3>,
}

impl VoxelGrid {
    pub fn new(origin: Vec3, voxel_size: f32, dims: (usize, usize, usize)) -> Self {
        let total = dims.0 * dims.1 * dims.2;
        Self { origin, voxel_size, dims, data: vec![Vec3::ZERO; total] }
    }

    pub fn world_to_idx(&self, p: Vec3) -> Option<(usize, usize, usize)> {
        let d = (p - self.origin) / self.voxel_size;
        let i = d.x.floor() as i64;
        let j = d.y.floor() as i64;
        let k = d.z.floor() as i64;
        if i < 0 || j < 0 || k < 0 { return None; }
        let (i, j, k) = (i as usize, j as usize, k as usize);
        if i >= self.dims.0 || j >= self.dims.1 || k >= self.dims.2 { return None; }
        Some((i, j, k))
    }

    pub fn idx_to_world_center(&self, i: usize, j: usize, k: usize) -> Vec3 {
        self.origin + Vec3::new(
            (i as f32 + 0.5) * self.voxel_size,
            (j as f32 + 0.5) * self.voxel_size,
            (k as f32 + 0.5) * self.voxel_size,
        )
    }

    pub fn get(&self, i: i64, j: i64, k: i64) -> Vec3 {
        if i < 0 || j < 0 || k < 0 { return Vec3::ZERO; }
        let (i, j, k) = (i as usize, j as usize, k as usize);
        if i >= self.dims.0 || j >= self.dims.1 || k >= self.dims.2 { return Vec3::ZERO; }
        let idx = i + j * self.dims.0 + k * self.dims.0 * self.dims.1;
        self.data[idx]
    }

    pub fn set(&mut self, i: usize, j: usize, k: usize, v: Vec3) {
        let idx = i + j * self.dims.0 + k * self.dims.0 * self.dims.1;
        self.data[idx] = v;
    }

    pub fn sample_trilinear(&self, p: Vec3) -> Vec3 {
        let d = (p - self.origin) / self.voxel_size;
        let i = d.x.floor() as i64;
        let j = d.y.floor() as i64;
        let k = d.z.floor() as i64;
        let tx = d.x - i as f32;
        let ty = d.y - j as f32;
        let tz = d.z - k as f32;

        let c000 = self.get(i, j, k);
        let c100 = self.get(i + 1, j, k);
        let c010 = self.get(i, j + 1, k);
        let c110 = self.get(i + 1, j + 1, k);
        let c001 = self.get(i, j, k + 1);
        let c101 = self.get(i + 1, j, k + 1);
        let c011 = self.get(i, j + 1, k + 1);
        let c111 = self.get(i + 1, j + 1, k + 1);

        let c00 = c000.lerp(c100, tx);
        let c01 = c001.lerp(c101, tx);
        let c10 = c010.lerp(c110, tx);
        let c11 = c011.lerp(c111, tx);

        let c0 = c00.lerp(c10, ty);
        let c1 = c01.lerp(c11, ty);

        c0.lerp(c1, tz)
    }
}

mod tests {
    use super::*;

    #[test]
    fn idx_round_trip() {
        // 验证 world_to_idx 和 idx_to_world_center 互为反映射
        let grid = VoxelGrid::new(Vec3::ZERO, 1.0, (4, 4, 4));
        for i in 0..4 {
            for j in 0..4 {
                for k in 0..4 {

            }
        }

        let mut grid = VoxelGrid::new(Vec3::ZERO, 1.0, (4, 4, 4));

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
