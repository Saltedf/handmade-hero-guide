# Day 340 · 清理世界/模拟区域交互

> 三天的 sim space 改造让粒子能动了,但留下了一地烂摊子:`world` 和 `sim_region` 两个模块边界模糊,函数互相调用、数据互相穿越。今天 Casey 不加新功能,他做软件工程最难的事——**重构**:让代码结构匹配概念结构,为后续 Day 349(多 sim region)和 Day 350(多线程)打基础。

## 0 · 为什么要有这一天

写出能跑的代码,只完成了 30%。剩下 70% 是**让代码长期可维护**:别人(包括三个月后的你)能看懂、能改、能扩展而不破坏。

前三天的 sim space 改造把粒子从世界坐标切到模拟坐标,但 Casey 写得急——粒子系统直接读 `world.camera_pos`,sim_region 直接访问 `world.particles` 修改,世界更新和模拟更新边界模糊。

后果:

1. **改一处崩多处**:你改 `world.camera_pos` 的类型,5 个文件编译错
2. **复用困难**:想把粒子系统搬到另一个项目,要撕掉一堆 `world` 依赖
3. **测试困难**:测粒子模拟要构造整个 world,不能孤立
4. **多线程风险**:`world` 被多 sim_region 共享,加锁、改值会出现数据竞争

Day 340 的目标:**清理**。把 `world` 和 `sim_region` 的接口定义清楚——`world` 只管"持久数据 + 跨区域协调",`sim_region` 只管"局部模拟 + 粒子"。两个模块通过明确的 API 通信,不互相戳私有数据。

这种"先弄乱再清理"的循环是软件开发的常态。Casey 在 HH 里反复演示:**先写能跑的代码,跑通了再重构**。不要追求"一开始就完美",完美主义会让你写不出第一行。

心理锚点:今天之后你能解释"模块边界"和"接口设计"的工程价值,能识别"过度耦合"的代码坏味道,能做小规模重构而不引入 bug。

## 2 · 心智模型

### 类比:厨房整理

想象厨房乱套了:刀放在锅旁边,调料藏在碗柜里,食材堆在灶台上。你能做出饭,但效率低、易出错(盐当糖放)。

整理 = 把东西按"职责"归类:

- 刀具区:刀、剪刀、磨刀石
- 烹饪区:锅、铲、灶
- 调料区:油盐酱醋
- 食材区:菜肉蛋奶

整理后做菜:每一步去对应区域拿东西,不会"找东西找不到"或"放错位置"。

代码整理同构:**让数据放在用它的代码附近,让接口清晰表达"我能做什么"**,而不是"我有这些数据你随便拿"。

### 模块边界的两个原则

**原则 1:单一职责(Single Responsibility)**

每个模块只做一件事。

- `world`:存所有持久数据,回答"什么是当前的实体、tile、相机位置"
- `sim_region`:在本帧的"模拟区域"里跑物理、AI、粒子
- `renderer`:把 sim_region 状态画到屏幕

如果 `sim_region` 里出现了"删除一个 entity"的逻辑——错了,删除 entity 是 `world` 的职责。`sim_region` 只能"标记某 entity 为死亡",由 `world` 在帧末统一清理。

**原则 2:依赖单向(Dependency Inversion)**

模块 A 依赖 B,A 不应该知道 B 的内部数据结构,只知道 B 的**接口**。

```
错误(耦合):
sim_region.particles[i].world_pos.x = ...;  // sim_region 直接改 world 的内部

正确(接口):
sim_region.move_particle(i, offset);  // sim_region 调用自己的接口
// 内部:particles[i].sim_pos += offset
```

Casey Day 340 主要做这个:把"`world` 直接戳 `sim_region.particles`"改成"通过 `sim_region` 暴露的 API 调用"。

### 实际重构:从直接访问到接口

**Before**:

```rust
// 渲染代码,直接读 world 的粒子
fn render(world: &World) {
    for p in &world.particles.sim_pos {
        let world_pos = p.add(world.camera.pos);
        draw_dot(world_pos);
    }
}
```

问题:渲染代码知道 `world.particles.sim_pos` 是 `Vec<Vec2>`,知道 `world.camera.pos` 是 `Vec2`。`world` 内部一改,渲染代码要跟着改。

**After**:

```rust
// world 暴露迭代器接口
impl World {
    fn particle_world_positions(&self) -> impl Iterator<Item = Vec2> + '_ {
        self.particles.sim_pos.iter()
            .map(move |p| p.add(self.camera.pos))
    }
}

// 渲染代码只用接口
fn render(world: &World) {
    for world_pos in world.particle_world_positions() {
        draw_dot(world_pos);
    }
}
```

好处:`world` 内部随便改(`sim_pos` 改成 SoA、`camera.pos` 改成 f64),只要 `particle_world_positions()` 接口稳定,渲染代码不动。

### 数据所有权:谁拥有数据

Rust 的所有权系统强制你思考:**谁拥有数据**。

```rust
// 错误:两个模块都拥有 particles
struct World { particles: Vec<Particle> }
struct SimRegion { particles: Vec<Particle> }  // 复制了一份?

// 正确:world 拥有,sim_region 借用
struct World { particles: Vec<Particle> }
struct SimRegion<'a> {
    particles: &'a mut [Particle],  // 借用 world 的一片
    origin: Vec2,
}
```

`SimRegion<'a>` 的 `'a` 是 lifetime——告诉编译器"这个 SimRegion 活着时,World 不能动"。借检查器保证不会"sim_region 还在用,world 已经释放"。

Casey Day 340 之前的代码有点"模糊借用"——某些指针是裸的,跨帧传递。Rust 强制你写清楚 lifetime,从源头消除悬垂引用。

### Sim Region 的概念

HH 的 **sim region**(模拟区域)是个特定概念:**当前帧需要模拟的一块世界区域**。

世界很大(10km × 10km),但玩家只能看到周围 100m。没必要每帧模拟整个世界——只模拟"玩家附近的区域",这就是 sim region。

```
世界 (10000 x 10000)
  ┌─────────────────────────────────┐
  │                                 │
  │      ┌─────────────┐            │
  │      │ sim region  │ <- 玩家附近 │
  │      │  100 x 100  │            │
  │      └─────────────┘            │
  │                                 │
  └─────────────────────────────────┘
```

sim region 里:

- 玩家本人
- 附近的怪物(50 只)
- 附近的粒子(1000 颗)
- 附近的 tile(只有可视范围)

外面的怪物、粒子、tile **不更新**——节省 CPU。玩家移动时,sim region 跟着移,新的内容滚入,旧的滚出。

这种"流式模拟"是大世界游戏的核心。Minecraft 的 chunk、GTA 的 lod 都是变体。

今天的清理:**让 sim region 的边界明确**——只有 sim region 内的代码在跑,world 只在帧边界(每帧开始/结束)和 sim region 通信。

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏架构演化:

**1990s 单体架构**(Doom / Quake):
- 所有状态全局可见(`g_entities`, `g_particles`)
- 简单粗暴,小团队够用
- 不可扩展,引擎做大就崩

**2000s 模块化**(Source / Unreal):
- 分 subsystem:renderer / physics / audio / game logic
- 子系统通过事件总线通信
- 接口清晰但运行时开销

**2010s ECS**(Unity / Bevy):
- 数据和逻辑彻底分离
- 系统(system)操作组件(component),实体(entity)只是 ID
- cache 友好,SIMD 友好,多线程友好

Casey 在 HH 里**没有用 ECS**——他的 entity 是个"胖结构体",所有字段挤一起。这其实更接近 1990s 风格,但 Casey 用了**严格的模块边界**避免混乱。

**Casey 风格 vs ECS 的取舍**:

- Casey 风格:简单、直接、好读;cache 不友好(单 entity 跨多个 cache line)
- ECS:cache 友好、SIMD 友好;复杂、间接

教学项目用 Casey 风格,生产引擎用 ECS。

### 3.2 · 图形学视角

图形 pipeline 的天然分层:

```
World(持久数据)
   ↓
SimRegion(当前帧模拟状态)
   ↓
RenderPacket(渲染命令)
   ↓
GPU(实际绘制)
```

每层职责:

- World:数据源
- SimRegion:更新数据
- RenderPacket:转 GPU 命令
- GPU:执行

层与层之间通过**值传递**或**只读借用**,不共享可变状态。这是 multi-threaded rendering 的基础。

Casey Day 340 的清理:**让 World → SimRegion 的接口明确**,为后面 Day 350 多线程渲染打基础。

**业界 case**:Unreal 的 `UWorld` → `ULevel` → `Actor`,Bevy 的 `World` → `Query` → `System`,都是这种分层。

### 3.3 · Linux 系统编程视角

Linux 内核的"模块边界"是教科书级:

- **VFS**(虚拟文件系统):所有文件系统(ext4 / btrfs / nfs)实现统一接口 `file_operations`
- **块设备层**:`block_device_operations`,SSD / HDD / NVMe 都实现
- **网络栈**:`sock` 接口,TCP / UDP / Unix socket 都符合

内核鼓励"接口隔离":一个驱动不知道另一个驱动的内部,只通过 `ops` 结构体通信。

应用层借鉴这种思想:**用 trait 定义接口,实现可替换**。Casey 的 sim region 接口在 Rust 里可以写成:

```rust
trait SimRegion {
    fn update(&mut self, dt: f32);
    fn entities(&self) -> &[Entity];
    fn particles(&self) -> ParticleView<'_>;
}
```

不同实现(单线程版 / 多线程版 / 网络版)可以无缝替换。

### 3.4 · Rust 生态视角

Rust 强制你思考模块边界的几个特性:

**1. 可见性(pub / pub(crate) / 私有)**

```rust
pub struct World {
    pub camera: Camera,           // 公开
    pub(crate) particles: Particles,  // 同 crate 可见
    entities: Vec<Entity>,        // 私有(只在 world.rs 可见)
}
```

私有字段强制"必须通过方法访问",防止外部直接戳。

**2. Trait 接口**

```rust
pub trait ParticleSource {
    fn iter_world_positions(&self) -> impl Iterator<Item = Vec3> + '_;
}
```

调用方只依赖 trait,不依赖具体类型。可以替换实现而不改调用方。

**3. Lifetime 隔离**

```rust
struct SimRegion<'w> {
    world: &'w World,        // 借用 world
    entities: Vec<usize>,    // 拥有 index 列表
}
```

`'w` 强制 sim_region 的生命周期不超过 world。编译期消除悬垂引用。

**4. Interior Mutability(必要时)**

```rust
use std::cell::RefCell;
struct World {
    particles: RefCell<Vec<Particle>>,  // 运行时借用检查
}
```

`RefCell` 让你"看起来不可变地"修改内部,运行时检查借用规则。**慎用**——大多数场景应该用 `&mut`,只有接口设计需要时才用 `RefCell`。

### 真实 crate 参考

- **`bevy_ecs`**:`World` + `Query` + `System` 三层抽象,工业级 ECS
- **`hecs`**:轻量 ECS,API 简单
- **`specs`**:并行 ECS,适合重度模拟

这些 crate 的"边界设计"可以借鉴——但 HH 教程的目标是手写,理解原理。

## 5 · 对照与变奏

### 重构的不同种类

**Extract Function**(提取函数):一段代码独立成函数。最常见,风险低。

**Move Function**(移动函数):函数从模块 A 搬到 B。中等风险,需要看依赖。

**Extract Module**(提取模块):把模块的一部分独立成新模块。Casey 今天主要做这个。

**Change Signature**(改签名):函数参数变。高风险,所有调用方要改。

**Replace Conditional with Polymorphism**(条件改多态):switch 改 trait + impl。重构圣经,适合代码积累多后做。

### 重构的风险与防御

**风险 1:行为悄悄改变**

重构中改了一行,功能变了但没人发现。防御:**测试**——重构前必须有一组测试,重构后跑测试,失败立刻发现。

**风险 2:引入 panic**

借用规则、lifetime、越界,容易引入 panic。防御:**编译器**——Rust 编译期消除大部分。

**风险 3:性能退化**

多一层间接调用,可能慢。防御:**bench**——重构前后跑基准,退化 > 5% 要分析。

### Casey 的重构节奏

Casey 在 HH 里大约每 5-10 天做一次小重构,每 30-50 天一次大重构。今天是大重构之一。

**节奏原则**:

- 加新功能前,如果代码味道不对,先重构再加
- 重构期间不混合新功能(否则 bug 难定位)
- 重构后必须跑一遍游戏,确认行为不变

### 历史演化

- **1960s**:"goto considered harmful",结构化编程兴起
- **1990s**:面向对象,封装
- **2000s**:设计模式,反模式
- **2010s**:函数式、不可变、纯函数
- **2020s**:数据导向,ECS

每个时代有自己的"好代码"标准。今天 Casey 的风格融合多种:**数据导向** + **严格接口** + **明确所有权**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"sim_region 直接访问 world.particles[i]"是坏设计?至少说出 3 个理由。

**参考解答**:

3 个理由:
1. **耦合**:sim_region 知道 world 的内部数据结构(particles 是 Vec、Particle 有 sim_pos 字段)。world 改 struct,sim_region 要跟着改。
2. **测试困难**:测 sim_region 要构造完整 world,不能孤立测模拟逻辑。
3. **并发障碍**:多线程时,world.particles 被多个 sim_region 共享,加锁粒度难定。

接口设计应该让 sim_region 只依赖"输入参数 + 自己持有的状态",而不是"world 的内部"。

### Lv2 · 动手实践

**题**:写一个"耦合版本"和"重构版本"的对比。耦合版本:`Renderer` 直接读 `World.particles`。重构版本:`Renderer` 通过 `World::particle_iter()` 接口访问。要求:

1. 重构版本里,把 `World.particles` 改成 SoA(三个 Vec<f32>),`Renderer` 不需要改一行
2. 验证两个版本输出相同

完成标准:`cargo run` 两个版本都打印 `total_particles_drawn = 100`。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

// === 耦合版本 ===
mod coupled {
    use super::Vec2;

    pub struct World {
        pub particles: Vec<Vec2>,  // pub!
    }

    pub struct Renderer;
    impl Renderer {
        pub fn draw(&self, world: &World) -> usize {
            let mut count = 0;
            for p in &world.particles {  // 直接戳内部
                let _ = p;
                count += 1;
            }
            count
        }
    }
}

// === 重构版本 ===
mod refactored {
    use super::Vec2;

    pub struct World {
        // 私有!内部随便改
        particle_x: Vec<f32>,
        particle_y: Vec<f32>,
    }

    impl World {
        pub fn new() -> Self {
            Self { particle_x: vec![], particle_y: vec![] }
        }
        pub fn push(&mut self, p: Vec2) {
            self.particle_x.push(p.x);
            self.particle_y.push(p.y);
        }
        // 接口:返回迭代器
        pub fn particle_iter(&self) -> impl Iterator<Item = Vec2> + '_ {
            self.particle_x.iter().zip(self.particle_y.iter())
                .map(|(&x, &y)| Vec2 { x, y })
        }
    }

    pub struct Renderer;
    impl Renderer {
        pub fn draw(&self, world: &World) -> usize {
            world.particle_iter().count()  // 通过接口
        }
    }
}

fn main() {
    let n = 100;

    // 耦合版
    let mut w1 = coupled::World { particles: vec![] };
    for i in 0..n { w1.particles.push(Vec2 { x: i as f32, y: 0.0 }); }
    let r1 = coupled::Renderer;
    println!("coupled: total_drawn = {}", r1.draw(&w1));

    // 重构版(内部已是 SoA,Renderer 不感知)
    let mut w2 = refactored::World::new();
    for i in 0..n { w2.push(Vec2 { x: i as f32, y: 0.0 }); }
    let r2 = refactored::Renderer;
    println!("refactored: total_drawn = {}", r2.draw(&w2));
}
```

**关键解释**:
- `refactored::World` 内部已经从 `Vec<Vec2>` 改成 SoA(`Vec<f32>` × 2),但 `Renderer::draw` 一字未改——这就是接口隔离的力量
- `particle_iter(&self) -> impl Iterator + '_`:`'_` 表示迭代器 lifetime 绑定到 self
- `pub fn` 让外部能调用,`particle_x: Vec<f32>`(无 pub)让外部不能直接访问

### Lv3 · 迁移设计

**题**:把"模块边界"思想用到**网络层**:游戏客户端要处理 TCP 包(收发)+ 状态机(连接中 / 已认证 / 已断开)。

要求:

1. 设计两个模块:`PacketIO`(原始字节传输)和 `ConnectionState`(状态机)
2. 接口:`PacketIO::send(bytes)` / `recv() -> bytes`,`ConnectionState::on_recv(bytes) -> Option<Message>`
3. 上层 `GameClient` 只通过这两个接口工作,不直接戳 socket

提示:`ConnectionState` 不知道 TCP 细节,`PacketIO` 不知道协议。两边都通过 bytes 通信。

### 完整可跑的重构演示

把 Lv2 扩展,加上"边界违规检测"——debug_assert 防止"耦合版"被用作"重构版"。

```rust
use std::cell::RefCell;
use std::rc::Rc;

#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }

// === World:持有持久数据 ===
struct World {
    // 私有,外部不可见
    particle_x: Vec<f32>,
    particle_y: Vec<f32>,
    camera_pos: Vec2,
}

impl World {
    fn new() -> Self {
        Self {
            particle_x: vec![],
            particle_y: vec![],
            camera_pos: Vec2 { x: 0.0, y: 0.0 },
        }
    }

    fn spawn_particle(&mut self, world_pos: Vec2) {
        // 内部转换到模拟空间
        let sim_x = world_pos.x - self.camera_pos.x;
        let sim_y = world_pos.y - self.camera_pos.y;
        self.particle_x.push(sim_x);
        self.particle_y.push(sim_y);
    }

    // === 接口:模拟成"对象集合" ===
    fn particle_count(&self) -> usize { self.particle_x.len() }

    fn particle_world_pos(&self, i: usize) -> Vec2 {
        Vec2 {
            x: self.particle_x[i] + self.camera_pos.x,
            y: self.particle_y[i] + self.camera_pos.y,
        }
    }

    fn move_camera(&mut self, new_pos: Vec2) {
        // 模拟空间反向偏移:保持 world_pos 不变
        let dx = new_pos.x - self.camera_pos.x;
        let dy = new_pos.y - self.camera_pos.y;
        for x in &mut self.particle_x { *x -= dx; }
        for y in &mut self.particle_y { *y -= dy; }
        self.camera_pos = new_pos;
    }
}

// === SimRegion:借用 World 的一段时间窗 ===
struct SimRegion<'a> {
    world: &'a mut World,
}

impl<'a> SimRegion<'a> {
    fn new(world: &'a mut World) -> Self {
        Self { world }
    }

    fn update(&mut self, dt: f32) {
        // 只更新自己的 sim_pos,不触碰 world.camera_pos
        for i in 0..self.world.particle_count() {
            // 简单 Euler:让粒子向右飞
            self.world.particle_x[i] += 1.0 * dt;
        }
    }

    fn spawn(&mut self, world_pos: Vec2) {
        self.world.spawn_particle(world_pos);
    }
}

// === Renderer:只通过接口访问 ===
struct Renderer;
impl Renderer {
    fn draw(&self, world: &World) -> usize {
        for i in 0..world.particle_count() {
            let p = world.particle_world_pos(i);
            // 假装画到屏幕
            let _ = p;
        }
        world.particle_count()
    }
}

fn main() {
    let mut world = World::new();
    let mut sim = SimRegion::new(&mut world);

    // 喷 100 颗粒子
    for i in 0..100 {
        sim.spawn(Vec2 { x: i as f32, y: 0.0 });
    }

    // 模拟一帧
    sim.update(0.016);

    // 移动相机
    drop(sim);  // 释放 world 的借用
    world.move_camera(Vec2 { x: 50.0, y: 0.0 });

    // 渲染
    let renderer = Renderer;
    let count = renderer.draw(&world);
    println!("drew {} particles", count);
    println!("particle[0] world_pos = {:?}", world.particle_world_pos(0));
    println!("particle[50] world_pos = {:?}", world.particle_world_pos(50));

    // 边界检查
    debug_assert_eq!(count, 100);
}
```

**关键 Rust 特性**:
- `SimRegion<'a>` 用 lifetime 借用 World。`world: &'a mut World` 强制 SimRegion 活着时,其他代码不能改 World。
- `drop(sim)` 显式释放借用,之后 `world.move_camera` 可以 `&mut self`。
- 私有字段 `particle_x: Vec<f32>` 强制外部必须通过接口访问。
- `particle_count` / `particle_world_pos` / `move_camera` 都是接口,内部实现可换。

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
