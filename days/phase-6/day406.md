
# Day 406 · 让图形调试器跑起来

> 你已经写了好几天的多网格光照传播(Multi-Grid Light Propagation Volume,以下简称 LPV),体素里有光、有衰减、有面光源,但画面就是"不对"——某个体素太亮、某个面是黑的、墙壁内部反而透光。光用 `printf` 已经定位不了问题,因为问题藏在三维体素网格和 GPU 上传链路的某一环里。今天 Casey 做的是图形程序员必须会做但极少有人教的事:**把图形调试器(Graphics Debugger)接入项目,亲眼看见 GPU 在画什么**。

## 0 · 为什么要有这一天

回到一个让你彻夜难眠的具体场景。你的 LPV 渲染管线已经包含:CPU 端把空间离散成 32×32×32 的体素,体素里存了 RGB 光照;CPU 跑 Gauss-Seidel 多重网格迭代把光扩散开;CPU 把结果打包成一张 3D 纹理(volume texture),通过 `glTexSubImage3D` 上传到 GPU;vertex shader 把世界点投影到屏幕,fragment shader 用 `textureProj` 或三线性采样从体素纹理取出光强,加到最终像素。你看到的结果是:走廊地板异常亮,天花板是黑的,墙脚阴影偏到了不该在的位置。你怀疑某个步骤出错了——但**每个步骤你都用 `printf` 检查过**,数据看似都对。

这就是图形调试器的价值:**它能在 GPU 真实执行的每一步"暂停",让你看到 vertex shader 输入的顶点是什么、fragment shader 收到的 uv 是什么、纹理在这一帧被采样出来的值是什么、深度缓冲长什么样、渲染目标的 alpha 通道是不是被意外清空了**。Linux 上做这件事的标准工具是 Mesa 自带的 `apitrace`,以及 NVIDIA 的 Nsight Graphics、AMD 的 RenderDoc、Intel 的 Graphics Debugger。Casey 在 Windows 上用 Visual Studio Graphics Debugger(简称 Pix 或 VS Graphics Integration);今天我们的任务是把同样的工作流搬到 Arch Linux,用 **RenderDoc** 和 **apitrace** 替代。

为什么必须用图形调试器?因为 OpenGL/Vulkan 是**有状态的、隐式的**——你 `glUseProgram` 后,后续所有 draw call 都用这个 program;你 `glBindTexture` 到某个 unit 后,后续所有 sampler2D 都从这个 unit 取。任何一个 `glActiveTexture` 漏掉、任何一次 `glBindFramebuffer` 没复位、任何一个 uniform 没设,结果都是"全屏黑"或"颜色错位",而 `glGetError` 只告诉你"有错"不告诉你"哪个调用错"。图形调试器把每次 GL 调用记录成时间线,你能在任何一帧 scrub 状态、看当前上下文绑了什么、看 texture 内存里的真实数据。**没有图形调试器,你只能猜;有了它,你能证明**。

心理锚点:今天之后,你能:(1) 在 Arch 上用 `pacman` 装 RenderDoc 和 apitrace;(2) 把 HH 的 Rust + glow(glow 是 OpenGL wrapper)项目接到这两个工具;(3) 抓一帧并定位"为什么这个体素是黑的";(4) 看 GPU 端 texture upload 是否正确。**这是一辈子有用的工程能力**,不是 HH 特有。

## 1 · Casey 今天做了什么(HH 脉络)

## 2 · 心智模型

### 类比:图形调试器是 GPU 的"行车记录仪 + 慢镜头回放"

想象你在调试一台复杂的自动售货机。货道、传感器、找零、出货门,所有部件都在毫秒级配合工作。机器卡了,你拆开外壳用万用表量每个传感器——你只能看到"当前电压",但不知道"5 秒前那一刻哪个传感器先发了信号"。一台行车记录仪式的售货机调试器会做什么:它录下整次交易的所有信号时序,你能在事后 scrub 到"按了按钮后 1.2 秒"那一点,看到那一刻所有传感器的状态。这就是图形调试器对 GPU 做的事。

具体地,**一帧图形调试器记录包括**:

- **Frame:** 一次完整渲染(从 swapbuffers 到下次 swapbuffers)
- **Draw Call:** 一次 `glDrawElements` / `glDrawArrays` 调用,包含绑定的 VAO / VBO / program / textures / uniforms
- **State:** 在每个 draw call 之前的完整 GL 状态(混合模式、深度测试、绑定的 FBO 等)
- **Texture Memory:** 每个 texture 在某个 draw call 时的真实像素数据
- **Buffer Memory:** VBO / IBO 的真实数据
- **Shader Source:** 编译过的 GLSL / HLSL 源码和编译后的字节码
- **Pixel History:** 屏幕上某一个像素,经历过哪些 draw call,每次 draw 后变成什么颜色

这七样东西一起,**完整复现 GPU 在那一帧做了什么**。你不再猜,你直接看。

### 严谨原理:GL 调用 trace 与状态快照

apitrace 的工作原理是:`LD_PRELOAD` 一个 .so(libgltrace.so),这个库拦截所有 GL 调用,把调用的名字和参数序列化到文件里(`.trace` 文件)。这是经典的 **library interposition** 技术,Linux 上几十年前就有。RenderDoc 用类似机制,但它更进一步,会在每个 draw call 前后**复制 GPU 内存**,形成完整快照(snapshot)。

为什么需要快照?因为 GL 是异步的——你 `glDrawElements` 调用返回,并不意味着 GPU 已经画完。CPU 和 GPU 是并行的,GPU 可能在几十微秒后才真正执行这次 draw。如果 trace 只记录"调用",你看到的 state 是"CPU 调用时刻的 state",不一定等于"GPU 执行时刻的 state"。RenderDoc 用 GPU 侧的 marker 和 fence 确保快照对应"GPU 真正执行那一刻"的状态,这就是为什么它比 apitrace 更精确但开销更大。

我们用一个简化的图:

```
CPU timeline: glUseProgram → glBindTexture → glUniform → glDraw → glDraw → ...
GPU timeline:                          ↑ 真正开始执行 ↑
                                          ↑
                                  RenderDoc 在这里做 snapshot
```

apitrace 不做 snapshot,它只记 CPU 调用顺序。如果 CPU 设了 `glBindTexture(GL_TEXTURE0, tex_a)`,然后 `glDraw()`,GPU 执行时确实是 tex_a,因为 GL 保证 state 持续到下次改变。但如果你的代码有 race(多线程同时改 GL state),apitrace 可能记错了。所以**多线程渲染要用 RenderDoc,单线程用 apitrace 就够**。

### Rust + glow 项目怎么接入

HH 的 Rust 翻译用 `glutin` 创建 GL context,用 `glow` 这个 crate 调用 GL 函数。glow 是个零开销 wrapper(本质是 `type Fn = unsafe extern "C" fn(...)`),它不会改变 GL 行为,所以 apitrace 和 RenderDoc 都能直接挂载。

接入步骤(后文 §8 详细给):

1. 把你的程序编译成 release(图形调试器对 debug 版慢得无法接受)
2. apitrace:`apitrace trace --api=gl ./target/release/handmade_hero`,生成 `handmade_hero.trace`
3. `qapitrace handmade_hero.trace` 打开 GUI,scrub 到出错那一帧
4. RenderDoc:`renderdoccmd capture ./target/release/handmade_hero`,或在 GUI 里 "Launch Application"

### 一个具体问题:为什么体素 texture 在 GPU 是空的?

Casey 在 Day 406 抓帧后发现 GPU 端 texture 全 0。可能的原因(后文会逐个排查):

| 可能原因 | 检查方法 | 修复 |
|---|---|---|
| `glTexSubImage3D` 的 size 参数错(传了 0) | 看 trace 里这一行的参数 | 改成正确的 width/height/depth |
| unpack alignment 不对(`glPixelStorei(GL_UNPACK_ALIGNMENT, ...)`) | 看纹理数据每行字节数 | 设成 1 或 4,匹配数据布局 |
| PBO 还没 upload 就采样 | 看 trace 里 `glFenceSync` 是否同步 | 加 fence 等 upload 完成 |
| internal format 和 upload format 不匹配 | 比如 internal=GL_RGB16F 但 format=GL_RGBA | 统一 |
| 多重网格层次选错了(传了 level 0 但采样 level 1) | 看 `glTexParameteri(GL_TEXTURE_MIN_FILTER, GL_LINEAR_MIPMAP_LINEAR)` | 改成 `GL_LINEAR` 或显式指定 level |

**这些原因你光靠 println 永远找不到**,因为它们都发生在 GPU 侧。Trace + Pixel History 是唯一方法。

## 3 · 四域深入

### 3.1 · 🎨 图形学视角

图形调试器在工业渲染管线里的位置:

- **CAD / 设计软件**(Maya, Blender):内置 viewport debugger,能看每个 draw 的 mesh 和 material
- **游戏引擎**(Unity Frame Debugger, Unreal RenderDoc plugin):每帧可暂停、可重放
- **浏览器**(Chrome 的 WebGL Inspector, Firefox 的 Shader Editor):WebGL 同样的需求
- **科研可视化**:ParaView 用类似的 trace 机制做大型数据集渲染调试

**共性抽象**:无论哪个领域,渲染都是"CPU 准备数据 → GPU 执行 → 屏幕/纹理输出"的循环。任何一步出错,调试器都能定位。Casey 在 Day 406 教的不是"用某个工具",是**图形调试的心智模型**——这个模型迁移到任何图形 API(Vulkan / D3D12 / Metal / WebGPU)都适用。

**重要细节:GPU 内存读取**。在 OpenGL 里,你 `glBufferData` 把数据传到 GPU 后,CPU 不能直接读这些字节(必须 `glGetBufferSubData` 拷贝回来,慢)。图形调试器在 trace 时**已经把这些字节拷贝了一份**,所以你看 texture memory 是免费的(零开销读取已拷贝数据)。这教你一件事:**调试 GPU 程序的本质是"复制 GPU 状态到 CPU 可见",调试器把这件事自动化了**。

### 3.2 · 🐧 Linux 系统编程视角

Linux 上图形调试的几个层次:

**Layer 1: Library interposition(LD_PRELOAD)**

apitrace 用这个机制。`LD_PRELOAD=libgltrace.so ./your_app` 让 libgltrace.so 的 GL 函数符号先被加载器解析,你的 app 调用 `glDrawElements` 时实际进的是 trace 库的版本,trace 库记日志后再转发到真正的 GL 库(libGL.so)。

```bash
# 查看 apitrace 的 trace 库在哪
pacman -Ql apitrace | grep '\.so'
# /usr/lib/apitrace/wrappers/libgltrace.so
# /usr/lib/apitrace/wrappers/libegltrace.so

# 看 apitrace 命令到底做了什么
strace -f -e trace=execve apitrace trace --api=gl ./my_app 2>&1 | head -20
# 应该看到 LD_PRELOAD=.../libgltrace.so 被设进子进程的环境
```

**Layer 2: Vulkan / OpenGL explicit layers**

Vulkan 是 explicit layer model(显式层):应用启动时可以请求加载某些 layer,layer 用 VK_LAYER_xxx 命名。RenderDoc 的 Vulkan layer 是 `VK_LAYER_LUNARG_renderdoc`,可以全局开启(`/usr/share/vulkan/implicit_layer.d/`)或按需开启。

OpenGL 也有类似机制:`glTexImage3D` 等 OpenGL 函数通过 EGL/GLX 加载,GLX 没有官方 layer 模型,所以 OpenGL 必须用 LD_PRELOAD,而 Vulkan 可以用官方 layer。这就是为什么 apitrace 对 OpenGL 用 LD_PRELOAD、对 Vulkan 用 layer。

**Layer 3: DRM / KMS hooks**

极致的调试需要在 kernel DRM(Direct Rendering Manager)层挂。这是 Kernel Mode Setting (KMS) 的工作领域,GPU driver 的 ioctl 在这里被截获。普通应用层调试不需要这一层,但开发 GPU driver 必须懂。

Arch 上你可以装 `mesa-demos` 看一些 GL 测试程序,用 apitrace 跑它们练手:

```bash
sudo pacman -S mesa-demos apitrace renderdoc
# 试:抓一帧 glxgears 的 trace
apitrace trace --api=gl glxgears
# ctrl+C 退出后,目录下有 glxgears.trace
qapitrace glxgears.trace
```

### 3.3 · 🦀 Rust 生态视角

Rust 调用 GL 的主流 crate:

| Crate | 角色 | 在 HH 用途 |
|---|---|---|
| `glutin` | 创建 GL context(绑定到 winit 窗口) | 平台层窗口 |
| `glow` | GL 函数加载和调用 wrapper | 调用 glDraw 等 |
| `gl` | 自动生成的 GL binding(类似 GLEW) | 备选,但不如 glow 灵活 |
| `surfman` | 跨平台 context(更底层) | HH 不用 |

为什么 HH 选 glow?因为它**platform-agnostic**(OpenGL ES / WebGL / Desktop OpenGL 都用同一 API),且 API 是 `&GlContext` 引用而非全局函数,适合 Rust 的所有权模型。

**接入 apitrace 的 Rust 配置**:

```toml
# Cargo.toml
[dependencies]
glutin = "0.31"
glow = "0.13"
```

```rust
// src/main.rs(节选)
use glow::HasContext;

fn main() {
    let (gl, event_loop, windowed_context, _context) = {
        let event_loop = glutin::event_loop::EventLoop::new();
        let window_builder = glutin::window::WindowBuilder::new()
            .with_title("Handmade Hero")
            .with_inner_size(glutin::dpi::LogicalSize::new(960, 540));
        // 注意:必须用 GL_CORE_PROFILE,且尽量用 4.3 而非 4.5
        // RenderDoc 当前稳定版对 4.5 的 support 不如 4.3
        let windowed_context = glutin::ContextBuilder::new()
            .with_gl(glutin::GlRequest::Specific(
                glutin::Api::OpenGl, (4, 3)))
            .with_gl_profile(glutin::GlProfile::Core)
            .with_vsync(true)
            .build_windowed(window_builder, &event_loop)
            .unwrap();
        let windowed_context = unsafe { windowed_context.make_current().unwrap() };
        let gl = glow::Context::from_loader_function(|s| {
            windowed_context.get_proc_address(s) as *const _
        });
        (gl, event_loop, windowed_context, ())
    };
    // ... 渲染循环
}
```

**`from_loader_function` 的作用**:GL 函数地址是运行时查询的(通过 `glXGetProcAddressARB` 或 `wglGetProcAddress`),不是编译时链接。glow 用闭包包装这个查询过程,所以同一个 binary 能在不同 driver 上跑。apitrace 拦截的是 libGL.so 里的 `glXGetProcAddressARB`,所以 glow 的所有调用都会被 trace 到。

**坑:release-only bug**。图形 bug 经常只在 release 出现,因为 debug build 不开 SIMD 优化、不开 driver 的 fast path。要在 release 调试,你必须确保 `Cargo.toml` 里有:

```toml
[profile.release]
debug = true  # 在 release 也保留调试符号,这是图形调试器能映射回源码的关键
```

## 4 · 认知地图

### 4.1 上级

- **GPU 程序可视化**(GPU program visualization) — 把黑盒 GPU 执行过程变可观测
- **Invasive Instrumentation**(侵入式插桩) — 通过拦截库调用观察行为
- **Reproducible Execution**(可重现执行) — 录制一次执行以便事后回放

### 4.2 同级(并行方案)

| 工具 | 接入方式 | 适用 API | 在 HH 选了哪个 |
|---|---|---|---|
| **apitrace** | LD_PRELOAD | OpenGL, EGL | 抓 trace 时的首选(快) |
| **RenderDoc** | Library preload / Vulkan layer | OpenGL, Vulkan, D3D11/12 | 深度调试(可看 Pixel History) |
| **gfxreconstruct** | Vulkan layer | Vulkan only | HH 不用 |
| **Intel Graphics Analyzer** | Vulkan layer | Intel iGPU only | 不通用 |
| **Nsight Graphics** | CUDA / GL / Vulkan | NVIDIA only | 不通用 |
| **printf + glGetTexImage** | 手动 | All | 仅最后兜底 |

详细说明:apitrace 启动开销小(~5%),抓 60 帧每秒没问题;RenderDoc 启动开销大(~30%),只在定位具体 bug 时用。Casey 在 Day 406 用 VSGD(Windows),我们用 apitrace + RenderDoc 替代。

### 4.3 下级

- **Trace file format**(.trace / .cap) — 序列化的调用记录
- **State snapshot** — 每次快照的完整 GL state
- **Pixel History** — 像素级溯源
- **Shader disassembly** — 把 GPU 编译后的 shader 反汇编,看硬件真的执行什么
- **Timeline scrubbing** — 时间线 scrub
- **Replay** — 在另一台机器重放 trace

## 5 · 对照与变奏

### CPU 调试 vs GPU 调试

| | CPU | GPU |
|---|---|---|
| 设状态 | gdb step | 不可直接 step,只能 trace + replay |
| 看变量 | `print var` | 通过 trace 看 texture/buffer memory |
| 断点 | gdb breakpoint | 在某次 draw call 前 pause(replay 模式) |
| 修改状态 | `set var = ...` | RenderDoc 支持,apitrace 不支持 |
| 多线程 | 多核同时跑 | 数千 shader core 同时跑 |
| 异步 | 同步语义 | 异步语义(draw 返回不等于完成) |

**核心差异**:CPU 是"步进调试"的,gdb 让你在某行源码停住看变量;GPU 是"事后回放"的,你不能让 4096 个 shader core 在某行 shader 同时停住,只能录下来之后看每个 draw 的输入输出。这个范式差异是图形调试的核心。

### 历史演化

- **2000s 初**:显卡厂商各自提供调试工具,NVIDIA NVPerfHUD、AMD GPU PerfStudio,极度厂商绑定
- **2012**:apitrace 开源,成为跨厂商 trace 工具
- **2013**:RenderDoc 开源,Crytek 起步,后来 AMD 赞助
- **2015**:Vulkan 出现,官方 layer model 让调试更标准化
- **2020+**:Nsight / RenderDoc 都支持 mesh shader / ray tracing,工具跟上 API 演进

跟 HH 学,你站在工具成熟期。Casey 在 2015-2016 写这些天,VSGD 是当时唯一的 Windows 选项,他多次抱怨"VSGD 不支持 OpenGL 4.5 core profile",这就是为什么 Day 406 他把 context 降到 4.3。Linux 上我们没这个限制,但**降级 context 仍是兼容老 GPU 的好习惯**。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:apitrace 和 RenderDoc 都能 trace OpenGL,但二者有什么本质差异?在哪种情况下你会选 apitrace 不选 RenderDoc,反之?

**参考解答**:本质差异:**apitrace 只录 CPU 调用顺序,RenderDoc 在 GPU 真实执行前后做 state snapshot**。

apitrace 更轻量,启动开销小(~5%),适合"抓一帧 trace 后慢慢看";RenderDoc 更重(~30%),但支持 Pixel History、Shader Editing(在 trace 里改 shader 重放)、Texture Viewer(看 texture 内存里的真实像素)。

**选 apitrace**:在你只想看"程序的 GL 调用顺序对不对"时。例:怀疑漏调了 `glEnable(GL_DEPTH_TEST)`。
**选 RenderDoc**:在你需要看"GPU 端 texture 内存里的值是什么"时。例:Casey Day 406 的 bug——CPU 数据没传到 GPU。

### Lv2 · 动手实践

**题**:在你的 Rust + glow 项目里,装好 apitrace 和 RenderDoc,跑通下面流程:

1. `sudo pacman -S apitrace renderdoc`
2. `cargo build --release`
3. `apitrace trace --api=gl ./target/release/your_app`,运行 5 秒后 Ctrl+C

5. 找到调用 `glDrawElements` 的那一行,记下绑定的 VAO id 和 texture id

完成标准:你能截一张 RenderDoc 的 Pixel History 截图,标出某个像素经历的 draw call。

### Lv3 · 迁移设计

**题**:假设你在调试一个**非图形**的程序——比如 Rust 的一个 tokio 异步服务器,你想"在某个 HTTP 请求处理过程中,看每一步的状态"。设计一个最小可行的"trace 系统",模仿 apitrace 的思路。提示:tokio 的 task 不是 GL 调用,但你可以**包装**它。给出函数签名 `fn instrument<F: FnOnce() -> R>(name: &str, f: F) -> R`,并说明它如何写到 trace 文件里。

**提示**:
- 用 RAII 模式:进入函数时写一条 BEGIN,name + 时间戳;离开函数时写一条 END
- trace 文件可以用 JSON Lines(每行一个 JSON 对象),后续用 `jq` 分析
- 真实工程里这叫 distributed tracing,工业实现有 OpenTelemetry、Jaeger

## 8 · Rust / Arch 落地代码

### Rust 完整示例:最小的 glow 程序 + apitrace 接入

```rust
// Cargo.toml
// [dependencies]
// glutin = "0.31"
// glow = "0.13"
// [profile.release]
// debug = true

use glow::HasContext;
use std::num::NonZeroU32;

fn main() {
    // 1. 创建 GL context(glutin 创建窗口 + context)
    let event_loop = glutin::event_loop::EventLoop::new();
    let wb = glutin::window::WindowBuilder::new()
        .with_title("Day 406 demo")
        .with_inner_size(glutin::dpi::LogicalSize::new(640, 480));
    // 注意:用 (4, 3) 而非 (4, 5),兼容性更好(RenderDoc 对 4.3 支持最稳)
    let cb = glutin::ContextBuilder::new()
        .with_gl(glutin::GlRequest::Specific(glutin::Api::OpenGl, (4, 3)))
        .with_gl_profile(glutin::GlProfile::Core)
        .with_vsync(true);
    let windowed_context = cb.build_windowed(wb, &event_loop).unwrap();
    let windowed_context = unsafe { windowed_context.make_current().unwrap() };

    // 2. 用 glow 加载 GL 函数(每个函数指针通过 get_proc_address 查询)
    let gl = glow::Context::from_loader_function(|s| {
        windowed_context.get_proc_address(s) as *const _
    });

    // 3. 打印 GL 信息(确认 context 创建对了)
    unsafe {
        let version = gl.get_parameter_string(glow::VERSION);
        let renderer = gl.get_parameter_string(glow::RENDERER);
        let vendor = gl.get_parameter_string(glow::VENDOR);
        println!("GL version: {}", version);     // 例:4.3 (Core Profile) Mesa 24.x
        println!("Renderer: {}", renderer);       // 例:AMD Radeon ...
        println!("Vendor: {}", vendor);           // 例:AMD
    }

    // 4. 创建一个简单的 VAO(OpenGL Core Profile 必须有 VAO 才能画)
    let vertex_shader = unsafe {
        let shader = gl.create_shader(glow::VERTEX_SHADER).unwrap();
        gl.shader_source(shader, r#"
            #version 430
            out vec2 uv;
            void main() {
                vec2 pos = vec2((gl_VertexID == 1) ? 3.0 : -1.0,
                                (gl_VertexID == 2) ? 3.0 : -1.0);
                gl_Position = vec4(pos, 0.0, 1.0);
                uv = pos * 0.5 + 0.5;
            }
        "#);
        gl.compile_shader(shader);
        shader
    };

    let fragment_shader = unsafe {
        let shader = gl.create_shader(glow::FRAGMENT_SHADER).unwrap();
        gl.shader_source(shader, r#"
            #version 430
            in vec2 uv;
            out vec4 frag;
            void main() {
                frag = vec4(uv, 0.0, 1.0);
            }
        "#);
        gl.compile_shader(shader);
        shader
    };

    let program = unsafe {
        let program = gl.create_program().unwrap();
        gl.attach_shader(program, vertex_shader);
        gl.attach_shader(program, fragment_shader);
        gl.link_program(program);
        gl.detach_shader(program, vertex_shader);
        gl.detach_shader(program, fragment_shader);
        gl.delete_shader(vertex_shader);
        gl.delete_shader(fragment_shader);
        program
    };

    // 5. 一个空的 VAO(Core Profile 要求 bind 一个 VAO 才能 draw)
    let vao = unsafe { gl.create_vertex_array().unwrap() };

    // 6. 事件循环
    event_loop.run(move |event, _, control_flow| {
        *control_flow = glutin::event_loop::ControlFlow::Wait;
        match event {
            glutin::event::Event::WindowEvent { event, .. } => match event {
                glutin::event::WindowEvent::CloseRequested => {
                    *control_flow = glutin::event_loop::ControlFlow::Exit;
                }
                glutin::event::WindowEvent::Resized(physical_size) => {
                    windowed_context.resize(physical_size);
                }
                _ => {}
            },
            glutin::event::Event::RedrawRequested(_) => {
                unsafe {
                    gl.clear_color(0.1, 0.1, 0.1, 1.0);
                    gl.clear(glow::COLOR_BUFFER_BIT);
                    gl.use_program(Some(program));
                    gl.bind_vertex_array(Some(vao));
                    gl.draw_arrays(glow::TRIANGLES, 0, 3);
                }
                windowed_context.swap_buffers().unwrap();
            }
            _ => {}
        }
    });
}
```

**每行解释**:
- `HasContext` 是 glow 的 trait,提供 `gl.clear_color` 等方法,必须 `use` 进来
- `with_gl_profile(GlProfile::Core)` — 用 Core Profile,不包含 legacy OpenGL(glBegin/glEnd)
- `from_loader_function` — 闭包包装 `get_proc_address`,把 C 函数指针查询封装成 Rust 安全 API
- `get_parameter_string(VERSION)` — 查询当前 context 的版本字符串,类似 `glGetString(GL_VERSION)`
- `gl_VertexID == 1 ? 3.0 : -1.0` — 用 vertex id 生成 fullscreen triangle(3 个顶点覆盖整个屏幕,不需要 VBO)
- `gl.create_vertex_array` 返回 `Option<NonZeroU32>`,因为 0 是 GL 的"无 VAO"标记,glow 用 NonZeroU32 表达
- `swap_buffers` — glutin 把 backbuffer 显示到屏幕,GL 默认是双缓冲

**Troubleshooting**:

- **`apitrace: error: failed to dlopen libGL.so`** — 你的系统是 NVIDIA 专有驱动,libGL.so 在 `/usr/lib/nvidia-xxx/`,apitrace 找不到。解决:`LD_LIBRARY_PATH=/usr/lib/nvidia-xxx apitrace trace ...`
- **`RenderDoc: Failed to inject into process`** — 程序的 setuid 或 namespace 阻止了 inject。用普通用户跑程序,别 sudo
- **`qapitrace: cannot connect to X server`** — Wayland 上 qapitrace 需要 XWayland。装 `xorg-server-xwayland`,确认 `echo $WAYLAND_DISPLAY` 不为空
- **trace 文件巨大(几个 GB)** — 程序在 main loop 里频繁调用 GL,trace 太多。解决:在程序里加按键触发抓帧(只抓特定一帧)
