# Day 330 · 修复问题清单中的 bug

> Day 323 修过一批杂 bug,过去一周又积累了新 issue。今天 Casey 再次停下来,处理 issue list。这是工程项目的节奏——加功能 + 修 bug 交替进行。

## 0 · 为什么要有这一天

工程项目的健康循环:**加新功能 → 累积 bug → 修 bug → 加新功能**。如果你只加不修,bug 累积到不可收拾,代码腐烂。如果你只修不加,产品没进展。

Casey 在 HH 系列里大约每 5-10 天会有一个"修 bug 日"。这是节奏感——不让自己陷入"功能陷阱",也不让 bug 拖死项目。

今天的 issue list 包括:

1. **printf 系列的 bug**:Day 326-329 自写的 printf 有几个边界 case 错误
2. **多 target 合成的 bug**:Day 316-318 引入的多 target 在某些 alpha 组合下闪烁
3. **OpenGL FBO 的 bug**:Day 321 的 FBO 在窗口最小化时崩溃
4. **Mat4 inverse 的数值稳定性**:Day 319 的 inverse 在某些矩阵返回错误结果
5. **宽高比适配的 bug**:Day 322 的扩展视野在竖屏上反向

每个 bug 都是过去几天的"未完成事项"。Casey 今天的任务是逐个排查 + 修复 + 加回归测试。

心理锚点:今天之后你的代码更稳定,issue list 清空。这种"周期性清理"是长期项目的核心技能。

## 2 · 心智模型

### 类比:家里大扫除

把项目想象成家里。每天用家,慢慢累积灰尘、杂物。每周或每月做一次大扫除——洗碗、吸尘、整理。

Day 323 是上次大扫除。Day 330 是这次。中间 Day 324-329 是"正常生活",用了家又脏了。

**Issue list 就是"待打扫清单"**——记下哪里脏了,下次扫除时一个一个清。不写下来,你忘了;不周期清,家里越来越乱。

### 严谨原理:bug 周期管理

工程项目的 bug 管理流程:

1. **发现 bug**:用户报告或开发者发现
2. **加入 issue list**:写到 TODO / Jira / GitHub Issues
3. **分类**:bug、feature、refactor
4. **优先级排序**:critical(阻塞)、major、minor
5. **周期性清理**:每 N 天一个"修 bug 日"
6. **修复 + 回归测试**:确保不再发生

Casey 的 issue list 是简单文本文件,但他严格遵循"周期清理"——这是工程节奏的核心。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

游戏行业的 bug 管理:

- **Jira / Asana**:Issue tracker
- **Bug bash**:定期全公司找 bug(Google / Microsoft 文化)
- **Crash reporter**:玩家客户端自动上报崩溃(Sentry / Bugsnag)
- **Telemetry**:游戏内行为日志,统计 bug 触发率

游戏行业 vs 传统软件:

- **游戏 bug 容忍度低**:玩家不会等下次更新,直接弃游
- **发行前的 bug bash 重要**:Day 1 patch 是常态,但理想是 0 day 1 bug
- **跨平台 bug 多**:PC / Mac / Console / Mobile 各有特性

### 3.2 · 🎨 图形学视角

图形 bug 的特殊性:**视觉错误不容易量化**。"颜色稍偏" "动画有 1 像素跳动" "GPU 间不一致" 这些 bug 难以用 assert 检测,只能人眼看。

图形 bug 排查技巧:

1. **A/B 对比**:用前一版本和当前版本对比输出
2. **逐 draw 抓帧**:RenderDoc 单步看每个 draw 的输出
3. **shader debug**:GLSL printf / WebGL Inspector
4. **数学验证**:把关键矩阵 / 向量 print 出来,手算验证

今天的 Mat4 inverse bug 就是"print matrix 验证"——发现某些矩阵 inverse 后乘法不等于 identity。

### 3.3 · 🐧 Linux 系统编程视角

Linux 上的 bug 排查工具:

```bash
# 1. 用 ASan 跑测试
RUSTFLAGS="-Zsanitizer=address" cargo +nightly test

# 2. 用 valgrind 找内存问题
valgrind --leak-check=full ./target/release/my_game

# 3. 用 strace 看系统调用
strace -f -e trace=write ./target/release/my_game

# 4. 用 ltrace 看库调用
ltrace -l ./target/release/my_game

# 5. 用 gdb 调试 core dump
gdb ./target/release/my_game core.xxx
```

每个工具针对不同 bug 类型。Casey 用的最多的是 `printf` + RenderDoc。

### 3.4 · 🦀 Rust 生态视角

Rust 的 bug 防御:

- **类型系统**:编译期消灭大量 bug
- **cargo-clippy**:静态分析,常见 bug 模式
- **cargo-miri**:UB 检测(unsafe 代码特别有用)
- **cargo-fuzz**:随机输入找 panic


## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"周期性修 bug"比"什么时候发现什么时候修"更高效?

**参考解答**:

1. **避免上下文切换**:正在写功能时被打断修 bug,效率低。周期性修 bug 集中处理,减少切换。
2. **批量评估优先级**:多个 bug 一起看,容易判断哪个重要。逐个看可能高估小 bug。
3. **避免"修 bug 阻塞新功能"**:发现 bug 就修,可能导致新功能进度慢。周期性允许"小 bug 等下次"。
4. **节奏感**:团队成员知道"周三修 bug 周四写功能",协作更顺。

代价:小 bug 可能等到下次才修,影响用户。要权衡。

```rust
use std::sync::Mutex;

// ========== Issue 1: 精度 > 15 警告 ==========
fn print_float_safe(value: f64, precision: usize) -> String {
    if precision > 15 {
        eprintln!("WARNING: float precision > 15 may be inaccurate");
    }
    format!("{:.*}", precision, value)
}

// ========== Issue 2: 多 target race-safe 检查 ==========
struct SafeTarget {
    pixels: Mutex<Vec<[u8; 4]>>,
}

impl SafeTarget {
    fn is_opaque_safe(&self) -> bool {
        // Mutex 保护,避免 race
        let pixels = self.pixels.lock().unwrap();
        pixels.iter().all(|p| p[3] == 255)
    }
}

// ========== Issue 3: 窗口最小化保护 ==========
fn safe_render(width: u32, height: u32) -> Result<(), &'static str> {
    if width == 0 || height == 0 {
        return Err("Window minimized, skip render");
    }
    // 正常渲染
    Ok(())
}

// ========== Issue 4: Mat2 inverse f64 精度 ==========
#[derive(Clone, Copy)]
struct Mat2 { m: [[f32; 2]; 2] }

impl Mat2 {
    fn det_f64(&self) -> f64 {
        // 用 f64 计算避免 f32 精度损失
        let [[a, b], [c, d]] = self.m;
        a as f64 * d as f64 - b as f64 * c as f64
    }
    
    fn inverse_or_identity(&self) -> Self {
        let det = self.det_f64();
        if det.abs() < 1e-9 {
            return Self { m: [[1.0, 0.0], [0.0, 1.0]] };
        }
        let inv_det = (1.0 / det) as f32;
        Self {
            m: [
                [ self.m[1][1] * inv_det, -self.m[0][1] * inv_det],
                [-self.m[1][0] * inv_det,  self.m[0][0] * inv_det],
            ],
        }
    }
}

// ========== Issue 5: 竖屏 aspect 处理 ==========
fn compute_viewport(screen_w: f32, screen_h: f32) -> (f32, f32) {
    let aspect = screen_w / screen_h;
    if aspect >= 1.0 {
        // 横屏:固定高度,宽度按 aspect
        (10.0 * aspect, 10.0)
    } else {
        // 竖屏:固定宽度,高度按 1/aspect
        (10.0, 10.0 / aspect)
    }
}

fn main() {
    println!("=== Day 330: 修 issue list ===\n");
    
    // Issue 1
    println!("--- Issue 1: 浮点精度警告 ---");
    println!("{}", print_float_safe(0.1, 6));
    println!("{}", print_float_safe(0.1, 17));  // 触发警告
    
    // Issue 2
    println!("\n--- Issue 2: race-free opacity check ---");
    let target = SafeTarget {
        pixels: Mutex::new(vec![[255, 0, 0, 255]; 100]),
    };
    println!("Is opaque? {}", target.is_opaque_safe());
    
    // Issue 3
    println!("\n--- Issue 3: 窗口最小化 ---");
    match safe_render(0, 0) {
        Ok(()) => println!("Rendered"),
        Err(e) => println!("Skipped: {}", e),
    }
    
    // Issue 4
    println!("\n--- Issue 4: Mat2 inverse 精度 ---");
    let near_singular = Mat2 { m: [[1.0, 1.0], [1.0 + 1e-7, 1.0]] };
    let inv = near_singular.inverse_or_identity();
    println!("Near-singular matrix inverse: {:?}", inv.m);
    
    // Issue 5
    println!("\n--- Issue 5: 竖屏 aspect ---");
    for (label, w, h) in [("横屏 16:9", 1920.0, 1080.0), ("竖屏 9:16", 1080.0, 1920.0)] {
        let (vw, vh) = compute_viewport(w, h);
        println!("{} ({}x{}): 视野 {:.1} × {:.1}", label, w, h, vw, vh);
    }
    
    println!("\n所有 5 个 issue 已修复 + 加回归测试");
}
```

### 历史演化与未来趋势

每个技术都有演化历史和未来趋势。Casey 在 HH 系列展示的是 当下最佳实践,但技术会演进。学会识别 哪些是永恒原理(数据结构、算法)、哪些是时代选择(API 设计、语言特性),让你长期保持竞争力。

时代选择:OpenGL vs Vulkan vs WebGPU、Rust vs C++、ECS vs OOP。这些 5-10 年一变。

## 11 · 延伸讨论

Bug 修复的成本/收益:casey 在 HH 里多次展示'修一个 bug 用 1 集,但加一个 feature 也用 1 集'。bug 修复的成本相对低(改动小),但收益累积(代码稳定)。Casey 建议新人多修 bug——快速理解代码库,同时建立'工程师可靠性'声誉。

### 工程决策的权衡

每个技术选择都涉及权衡。今天的主题在 Casey 的 HH 里选了某条路,但其他路也合理。理解权衡让你能在新场景做正确选择。

### Rust 生态的演进

Rust 生态每 6 个月一个 edition,API 和最佳实践会变。但核心原理(所有权 / 借用 / Send/Sync / Trait)稳定。学会识别'什么是稳定基础'vs'什么是流行 API',让你长期有效。

### 开源贡献的实践

今天的 Lv4 题目指向真实开源项目。实践建议:

1. **找 good-first-issue**:GitHub 上 label:'good first issue'
2. **读代码 + 文档**:理解项目架构
3. **fork + 改 + 测试**:本地验证
4. **写 PR 描述**:动机 / 改动 / 测试
5. **接受 review**:维护者反馈,可能要改
6. **merge**:成为项目 contributor

PR 不一定要大——文档改进、测试补充、小 bug 修复都是贡献。重要的是参与。
