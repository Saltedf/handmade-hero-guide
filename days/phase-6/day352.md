# Day 352 · 隔离相机更新代码

> 多线程前,相机更新散在 `world_update` 各处——cutscene 改 camera_pos,玩家移动改 camera_pos,动画改 camera_pos。Day 350 多线程后这成了大问题:多线程同时改相机,数据竞争。今天的 refactor:**把所有相机更新集中到一个函数**,先收集"相机意图",再统一应用。

## 0 · 为什么要有这一天

多线程最大的敌人是**共享可变状态**。如果 camera_pos 被多个子系统随时改,多线程下必然竞争。

但游戏里相机确实要"被很多因素影响":

- 玩家移动 → 相机跟随
- 玩家受伤 → 相机震动
- 过场动画 → 相机沿预定路径
- 玩家选择 → 相机缩放
- AI NPC 重要事件 → 相机短暂关注
- 鼠标边缘滚动 → 相机平移(策略游戏)

老版本:每个子系统直接改 `world.camera.pos`。简单,但**多线程下地狱**。

新版本:**每个子系统产出"相机意图(CameraIntent)"**,集中到队列。每帧末,一个专门的 `camera_update` 函数读所有意图,决定最终 camera_pos。

这种"意图收集 → 集中应用"模式叫 **command pattern**(命令模式)或 **unidirectional data flow**(单向数据流)。React/Redux 的核心思想。游戏开发也越来越流行。

心理锚点:今天之后你能解释"为什么相机更新要集中",知道 command pattern 在游戏里的实例,理解 Casey 为什么在多线程前必须先 refactor。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 跑 Day 351 的多线程游戏,profile 发现:

1. 相机位置每帧被多个线程改,出现"data race 症状"——相机抖动
2. 即使加锁,锁竞争开销不小
3. 重构是更优解

Casey 重构:

1. **定义 `camera_intent` 类型**:描述"我希望相机做啥"
2. **每子系统产生 intent**:不直接改 camera,而是 push 到 intents 队列
3. **专门的 `update_camera` 函数**:每帧末调用,合并所有 intents,产出最终 camera_pos
4. **多线程安全**:intents 队列每帧重建(无跨帧状态),不需要锁

具体改动:

```c
// 老版本
void cutscene_update() {
    world->camera.pos = script_pos;  // 直接改
}

// 新版本
void cutscene_update() {
    camera_push_intent((camera_intent){
        .kind = CAMERA_SET_POS,
        .pos = script_pos,
        .priority = 100,
    });
}

    // 按优先级排序
    // 合并(最高优先级 SET 胜出,或多个 OFFSET 叠加)
```

## 2 · 心智模型

### 类比:公司决策流程

老版本:每个员工想干啥直接执行——销售改价格、研发改产品、运营改营销。混乱,互相覆盖。

新版本:每个员工提"提案(intent)"到决策委员会。委员会每周末开一次会,合并提案,决定下周动作。

相机同构:多个子系统提"我希望相机这样",委员会(camera_update)合并,决定最终位置。

### Command Pattern

软件设计的经典模式。把"做什么"打包成对象,延迟执行。

```rust
enum CameraCommand {
    SetPos(Vec3),
    Offset(Vec3),
    Shake { amplitude: f32, duration: f32 },
    Zoom(f32),
    LookAt(Vec3),
}

struct CameraCommandBuffer {
    commands: Vec<CameraCommand>,
}

impl CameraCommandBuffer {
    fn push(&mut self, cmd: CameraCommand) {
        self.commands.push(cmd);
    }

    fn execute(&mut self, camera: &mut Camera) {
        for cmd in self.commands.drain(..) {
            match cmd {
                CameraCommand::SetPos(p) => camera.pos = p,
                CameraCommand::Offset(o) => camera.pos += o,
                CameraCommand::Shake { amplitude, duration } => {
                    camera.shake_state = Some(ShakeState { amplitude, duration });
                }
                // ...
            }
        }
    }
}
```

好处:

1. **延迟执行**:多个 push 后一次 execute,锁开销只一次
2. **可重放**:记录 commands,事后回放(测试 / debug)
3. **可序列化**:commands 可以发到网络,客户端重放
4. **可组合**:多个 command 合并成新 command

ECS 系统广泛用这个模式。Bevy 的 `Commands` 就是 command buffer。

### 单向数据流(Unidirectional Data Flow)

数据流:

```
子系统 → intent → camera_update → camera state → renderer
```

单向,不回流。每个子系统不读 camera state,只 push intent。这样:

- 无循环依赖(子系统不依赖 camera state)
- 无 race(子系统之间不竞争)
- 易测试(给 intents,看 camera state 是否对)

React/Redux 是这种模式的前端实现,游戏开发借鉴。

### Rust 实现:所有权优势

Rust 表达 command buffer 的优势:

```rust
// 多线程版本
use std::sync::Mutex;
struct ThreadSafeBuffer(Mutex<Vec<CameraCommand>>);

impl ThreadSafeBuffer {
    fn push(&self, cmd: CameraCommand) {
        self.0.lock().unwrap().push(cmd);
    }
    fn drain(&self) -> Vec<CameraCommand> {
        std::mem::take(&mut *self.0.lock().unwrap())
    }
}
```

锁只一次(drain 时),push 时虽有锁但操作简单(Vec::push)。

**更进一步**:无锁队列(crossbeam),或者每线程本地 buffer + 帧末合并。

```rust
use std::cell::RefCell;
thread_local! {
    static LOCAL_BUFFER: RefCell<Vec<CameraCommand>> = RefCell::new(vec![]);
}

// 每线程 push 到本地(无锁)
LOCAL_BUFFER.with(|b| b.borrow_mut().push(cmd));

// 帧末:主线程合并所有线程的本地 buffer
```

这是 game engine 的常用优化:**thread-local command buffer + 主线程合并**。

### 相机的多种"影响源"

游戏里影响相机的来源:

1. **玩家位置**(follow cam):相机始终跟随玩家
2. **过场动画**(cutscene):相机沿脚本路径
3. **事件震动**(screen shake):爆炸、地震
4. **UI 操作**(zoom):玩家滚轮缩放
5. **AI 关注**(look-at):剧情中 NPC 说话时相机转向 NPC
6. **物理限制**(collision):相机不能穿墙

每个"源"产出一个 intent。`update_camera` 按优先级合并:

```
priority 高 → 低:
1. cutscene (固定路径,优先级最高)
2. look-at (临时关注,次高)
3. shake (震动叠加)
4. follow (基础跟随)
```

合并规则:

- 同类(都是 SetPos):最高优先级胜出
- 不同类:follow 给基础位置,shake 给偏移,叠加

## 3 · 四域深入

### 3.1 · 游戏编程视角

游戏引擎的"集中式更新"思想:

- **Unity 的 LateUpdate**:专门用于"在所有 Update 后处理"——相机、动画等
- **Unreal 的 Tick Post-physics**:物理后处理
- **Bevy 的 System ordering**:`.after(update_physics)`

所有都是"把相关代码集中到特定阶段"的变体。

Casey Day 352 是手工实现:在 `world_update` 末尾加 `update_camera`,所有相机相关代码搬过去。

**业界 case**:**The Last of Us 2** 的相机系统极其复杂(多个相机源、平滑过渡、电影感), Naughty Dog 用专门 camera director 统一管理。

### 3.2 · 图形学视角

相机是渲染 pipeline 的源头:`view_matrix = look_at(camera.pos, camera.target, up)`。view_matrix 影响所有 vertex shader。所以相机更新必须在渲染前完成。

相机抖动 → 整个画面抖动。所以相机更新必须**稳定**——一帧只更新一次,中途不变。

Casey Day 350 多线程下,如果 camera_pos 在渲染中途被某线程改,vertex shader 用了部分新部分旧位置,**画面撕裂**。Day 352 隔离后,渲染前 camera_pos 是稳定的最终值。

### 3.3 · Linux 系统编程视角

Linux 的"集中配置"思想:

- **systemd**:所有服务配置集中在 `/etc/systemd/system/`,而非散在 init.d 脚本
- **udev**:设备规则集中在 `/etc/udev/rules.d/`,而非散在内核
- **iptables**:防火墙规则集中表,而非散在 socket option

所有都是"配置延迟 + 集中应用"模式。

**Linux 输入子系统**:类似 command buffer:

- evdev 收集所有输入事件到 `/dev/input/eventX`
- libinput 读事件,做 gesture 识别
- X server / Wayland 接收处理后的输入

输入事件流和 Casey 的 camera intent 流同构。

## 5 · 对照与变奏

### Command Pattern 在不同语言

- **C++ / C**:函数指针 + 数据,或 switch-case
- **Rust**:enum + match(类型安全)
- **Java / C#**:interface + 实现 class(OOP 风格)
- **Python / JS**:callable 对象或 lambda

Rust 的 enum 是天然 fit:

```rust
enum Cmd { A(i32), B(String), C { x: f32, y: f32 } }
// 不需要 OOP 多态,枚举即可
```

### 集中更新的不同场景

- **相机**:今天
- **物理 velocity accumulation**:多个力(重力、推力、摩擦)累加,一次积分
- **damage application**:多个伤害源累加,一次扣血
- **inventory changes**:多个拾取/消耗,一次提交

所有都是"多源影响单一状态"的实例。

### 历史演化

- **1980s**:Gang of Four 设计模式书
- **1990s**:OOP 流行,command class 满天飞
- **2010s**:函数式回潮,enum + 闭包替代 OOP
- **2020s**:数据导向 + ECS,commands 用 enum 或 sparse set

Rust 的 enum + match 是函数式精华,比传统 OOP command 简洁。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么"直接改 camera"在多线程下不行?command buffer 模式怎么解决?

**参考解答**:

直接改 camera 的问题:

1. **数据竞争**:多个线程同时改 camera.pos,需要锁,锁竞争开销大
2. **顺序依赖**:线程 A 改 → 线程 B 读 → 线程 B 改 → 线程 A 读,顺序错就错
3. **可测试差**:相机状态由多个调用栈共同决定,难以复现

command buffer 解决:

1. **延迟**:线程 push 命令到本地 buffer(无锁),主线程 drain + 执行(单线程,无竞争)
2. **集中**:所有相机逻辑在 `update_camera`,顺序固定,易调试
3. **可测试**:给一组 commands,验证 camera state

### Lv2 · 动手实践

**题**:实现一个 camera command buffer。三个子系统(follow / shake / cutscene)各 push intent,update_camera 合并。

完成标准:模拟 5 帧,camera 状态符合预期(follow 给基础位置,shake 给偏移叠加,cutscene 优先级最高)。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y, self.z + o.z) }
}

#[derive(Clone, Debug)]
enum CameraCommand {
    // 跟随某点(优先级低)
    Follow(Vec3),
    // 偏移(震动,优先级中,叠加)
    Offset(Vec3),
    // 强制设置(过场,优先级高)
    ForceSet(Vec3),
}

struct Camera {
    pos: Vec3,
    commands: Vec<CameraCommand>,
}

impl Camera {
    fn new() -> Self { Self { pos: Vec3::new(0.0, 0.0, 0.0), commands: vec![] } }
    fn push(&mut self, cmd: CameraCommand) { self.commands.push(cmd); }

    fn update(&mut self) {
        // 收集所有命令
        let cmds = std::mem::take(&mut self.commands);

        // 优先级:ForceSet 最高(若有,直接用);其次 Follow;最后 Offset
        let mut follow_pos: Option<Vec3> = None;
        let mut total_offset = Vec3::new(0.0, 0.0, 0.0);
        let mut force_set: Option<Vec3> = None;

        for cmd in &cmds {
            match cmd {
                CameraCommand::Follow(p) => follow_pos = Some(*p),
                CameraCommand::Offset(o) => total_offset = total_offset.add(*o),
                CameraCommand::ForceSet(p) => force_set = Some(*p),
            }
        }

        // 应用
        if let Some(p) = force_set {
            self.pos = p;  // 最高优先级,忽略其他
        } else if let Some(p) = follow_pos {
            self.pos = p.add(total_offset);
        } else {
            self.pos = self.pos.add(total_offset);
        }
    }
}

fn main() {
    let mut camera = Camera::new();

    for frame in 0..5 {
        println!("\n--- Frame {} ---", frame);

        // 模拟多个子系统 push 命令
        // 1. Follow 系统:相机跟随玩家
        camera.push(CameraCommand::Follow(Vec3::new(frame as f32 * 1.0, 0.0, 0.0)));

        // 2. Shake 系统:每帧随机抖动
        if frame == 2 {
            camera.push(CameraCommand::Offset(Vec3::new(0.5, 0.0, 0.0)));
        }

        // 3. Cutscene 系统:frame 3 强制位置
        if frame == 3 {
            camera.push(CameraCommand::ForceSet(Vec3::new(100.0, 0.0, 0.0)));
        }

        camera.update();
        println!("Camera pos: {:?}", camera.pos);
    }
}
```

**预期输出**:
```
Frame 0: pos (0, 0, 0)
Frame 1: pos (1, 0, 0)
Frame 2: pos (2.5, 0, 0)  (follow 2 + offset 0.5)
Frame 3: pos (100, 0, 0)  (force_set 覆盖)
Frame 4: pos (4, 0, 0)
```

## 8 · Rust / Arch 落地代码

### 完整可跑示例

扩展 Lv2,加上"thread-local buffer + 主线程合并"的多线程安全版本。

```rust
use std::cell::RefCell;

#[derive(Copy, Clone, Debug)]
struct Vec3 { x: f32, y: f32, z: f32 }
impl Vec3 {
    fn new(x: f32, y: f32, z: f32) -> Self { Self { x, y, z } }
    fn add(self, o: Self) -> Self { Self::new(self.x + o.x, self.y + o.y, self.z + o.z) }
}

#[derive(Clone, Debug)]
enum CameraCommand {
    Follow(Vec3),
    Offset(Vec3),
    ForceSet(Vec3),
}

// Thread-local buffer:每线程独立,无锁
thread_local! {
    static LOCAL_BUFFER: RefCell<Vec<CameraCommand>> = RefCell::new(vec![]);
}

fn push_local(cmd: CameraCommand) {
    LOCAL_BUFFER.with(|b| b.borrow_mut().push(cmd));
}

// 主线程:drain 自己的 buffer
fn drain_local() -> Vec<CameraCommand> {
    LOCAL_BUFFER.with(|b| std::mem::take(&mut *b.borrow_mut()))
}

struct Camera {
    pos: Vec3,
}

impl Camera {
    fn new() -> Self { Self { pos: Vec3::new(0.0, 0.0, 0.0) } }

    fn apply_commands(&mut self, cmds: Vec<CameraCommand>) {
        let mut follow_pos: Option<Vec3> = None;
        let mut total_offset = Vec3::new(0.0, 0.0, 0.0);
        let mut force_set: Option<Vec3> = None;

        for cmd in cmds {
            match cmd {
                CameraCommand::Follow(p) => follow_pos = Some(p),
                CameraCommand::Offset(o) => total_offset = total_offset.add(o),
                CameraCommand::ForceSet(p) => force_set = Some(p),
            }
        }

        if let Some(p) = force_set {
            self.pos = p;
        } else if let Some(p) = follow_pos {
            self.pos = p.add(total_offset);
        } else {
            self.pos = self.pos.add(total_offset);
        }
    }
}

use std::thread;

fn main() {
    let mut camera = Camera::new();

    // 模拟多线程:多个线程 push 命令
    let handles: Vec<_> = (0..3).map(|tid| {
        thread::spawn(move || {
            // 每个线程 push 几个命令到 thread-local
            push_local(CameraCommand::Follow(Vec3::new(tid as f32, 0.0, 0.0)));
            push_local(CameraCommand::Offset(Vec3::new(0.1 * tid as f32, 0.0, 0.0)));
        })
    }).collect();
    for h in handles { h.join().unwrap(); }

    // 主线程也 push 一些
    push_local(CameraCommand::ForceSet(Vec3::new(99.0, 0.0, 0.0)));

    // 收集主线程的 buffer
    let mut all_cmds = drain_local();
    // 注意:子线程的 buffer 在子线程的 thread_local,主线程拿不到
    // 真实场景:每个 worker 把自己的 buffer 发回主线程(channel)
    // 这里简化:只演示主线程

    camera.apply_commands(all_cmds);
    println!("Camera pos: {:?}", camera.pos);  // ForceSet 99

    // 模拟下一帧(无 ForceSet)
    push_local(CameraCommand::Follow(Vec3::new(5.0, 0.0, 0.0)));
    push_local(CameraCommand::Offset(Vec3::new(0.5, 0.0, 0.0)));
    camera.apply_commands(drain_local());
    println!("Camera pos: {:?}", camera.pos);  // 5 + 0.5 = 5.5
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
