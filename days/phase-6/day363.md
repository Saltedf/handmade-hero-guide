# Day 363 · 制作轨道调试相机

> 两天数学铺垫(361 旋转,362 顺序),今天实战:**轨道相机**。开发者用鼠标拖动旋转视角,滚轮缩放,中键平移。这是 Blender / Maya / Unreal 编辑器的标配,3D 调试必备工具。

## 0 · 为什么要有这一天

3D 游戏开发没有轨道相机等于盲飞——你看到场景但不能从任意角度看。轨道相机的核心:

- **左键拖动**:绕焦点旋转(orbit)
- **右键拖动**:平移(pan)
- **滚轮**:缩放(zoom)
- **中键**:重置视角

数学上,轨道相机 = 球坐标(spherical coordinates)。焦点是球心,相机在球面上。鼠标拖动改变球的 θ(垂直)和 φ(水平)角度,滚轮改变半径。

实现需要:

1. 球坐标 ↔ 笛卡尔坐标转换
2. 鼠标输入到角度变化
3. view matrix 计算(look-at)
4. 防止 gimbal lock(限制 θ 范围)

今天的 episode 是 Day 361-362 数学的综合应用。

心理锚点:今天之后你能实现编辑器风格的 3D 相机,理解球坐标,知道 look-at 矩阵的构造。

## 2 · 心智模型

### 类比:摄影师拍雕像

雕像在中心,摄影师绕着雕像走:

- **绕雕像转**(yaw):水平绕,左走右走
- **上下移**(pitch):蹲下站起,看雕像头顶或底座
- **前后走**(distance):靠近看细节,退后看全貌

雕像位置 = target(焦点)。摄影师位置 = camera_pos(球面上的点)。

### 球坐标

3D 点的两种表示:

**笛卡尔** `(x, y, z)`:三个轴分量。

**球坐标** `(r, θ, φ)`:

- r:半径(离原点距离)
- θ(theta):垂直角(从 +Y 轴量),通常 [0, π]
- φ(phi):水平角(从 +Z 轴量),通常 [0, 2π]

转换(数学约定):

```
x = r * sin(θ) * cos(φ)
y = r * cos(θ)
z = r * sin(θ) * sin(φ)
```

游戏里常用(y 向上):

```
x = r * cos(pitch) * sin(yaw)
y = r * sin(pitch)
z = r * cos(pitch) * cos(yaw)
```

其中 pitch ∈ [-π/2, π/2](从水平线量),yaw ∈ [0, 2π]。

### Look-At 矩阵

给定:

- eye:相机位置
- target:看向的点
- up:世界 up 向量(通常 (0, 1, 0))

构造 view matrix(世界 → 相机):

```
forward = normalize(target - eye)
right = normalize(cross(forward, up))
up_new = cross(right, forward)

view = [right.x   right.y   right.z   -dot(right, eye)]
       [up_new.x  up_new.y  up_new.z  -dot(up_new, eye)]
       [-forward.x -forward.y -forward.z dot(forward, eye)]
       [0         0         0         1]
```

注意:forward 行取负,因为相机看 -Z(view space)。

Rust 实现:

```rust
fn look_at(eye: [f32; 3], target: [f32; 3], up: [f32; 3]) -> [[f32; 4]; 4] {
    let f = normalize([target[0] - eye[0], target[1] - eye[1], target[2] - eye[2]]);
    let r = normalize(cross(f, up));
    let u = cross(r, f);

    [
        [r[0], r[1], r[2], -dot(r, eye)],
        [u[0], u[1], u[2], -dot(u, eye)],
        [-f[0], -f[1], -f[2], dot(f, eye)],
        [0.0, 0.0, 0.0, 1.0],
    ]
}

fn dot(a: [f32; 3], b: [f32; 3]) -> f32 {
    a[0]*b[0] + a[1]*b[1] + a[2]*b[2]
}

fn cross(a: [f32; 3], b: [f32; 3]) -> [f32; 3] {
    [
        a[1]*b[2] - a[2]*b[1],
        a[2]*b[0] - a[0]*b[2],
        a[0]*b[1] - a[1]*b[0],
    ]
}

fn normalize(v: [f32; 3]) -> [f32; 3] {
    let len = (v[0]*v[0] + v[1]*v[1] + v[2]*v[2]).sqrt();
    if len > 1e-6 { [v[0]/len, v[1]/len, v[2]/len] } else { [0.0, 0.0, 0.0] }
}
```

### 防止 gimbal lock

pitch 不能到 ±90°——否则 yaw 和 roll 等价。

```rust
pitch = pitch.clamp(-PI/2 + 0.01, PI/2 - 0.01);
```

留 0.01 弧度(约 0.6°)避免完全垂直。

### Pan(平移)

右键拖动 = 平移焦点。数学:把鼠标 dx/dy 转成世界 dx/dy(在相机平面)。

```rust
let right = ...; // 相机的 right 向量
let up_new = ...; // 相机的 up 向量

let world_dx = -mouse_dx * sensitivity * distance;
let world_dy = mouse_dy * sensitivity * distance;

target = target + right * world_dx + up_new * world_dy;
```

注意:`* distance` 让远处 pan 更快(否则远距离几乎不动)。

### Zoom(缩放)

滚轮改变 distance:

```rust
distance *= 1.0 - wheel_delta * 0.1;
distance = distance.max(0.1).min(1000.0);
```

`wheel_delta > 0` 是向上滚(放大,distance 减小)。

指数缩放(`*= 0.9`)比线性(`-= 1.0`)更自然——近处慢、远处快。

### 3.2 · 图形学视角

相机的数学本质:**view matrix** = inverse(camera world transform)。

`view = inverse(model_camera)`。但 look_at 直接构造 view,不必先建 model 再 inverse。

正交 vs 透视:

- **正交**:平行投影,适合编辑器(无失真)
- **透视**:近大远小,适合游戏(自然)

Blender 编辑器默认正交(看场景清晰),Unity/Unreal 默认透视。

### 3.4 · Rust 生态视角

Rust 实现轨道相机:

```rust
struct OrbitCamera {
    target: Vec3,
    distance: f32,
    yaw: f32,
    pitch: f32,
}

impl OrbitCamera {
    fn position(&self) -> Vec3 {
        Vec3::new(
            self.distance * self.pitch.cos() * self.yaw.sin(),
            self.distance * self.pitch.sin(),
            self.distance * self.pitch.cos() * self.yaw.cos(),
        ) + self.target
    }

    fn view_matrix(&self) -> Mat4 {
        Mat4::look_at_rh(self.position(), self.target, Vec3::Y)
    }

    fn orbit(&mut self, dx: f32, dy: f32) {
        self.yaw += dx * 0.01;
        self.pitch = (self.pitch + dy * 0.01).clamp(-1.55, 1.55);  // ~89°
    }

    fn zoom(&mut self, delta: f32) {
        self.distance *= 1.0 - delta * 0.1;
        self.distance = self.distance.max(0.1);
    }

    fn pan(&mut self, dx: f32, dy: f32, right: Vec3, up: Vec3) {
        let scale = self.distance * 0.001;
        self.target -= right * dx * scale;
        self.target += up * dy * scale;
    }
}
```

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 pitch 要 clamp 在 ±90° 附近?如果 pitch = 90° 会发生什么?

**参考解答**:pitch = 90°(垂直向上)时,相机的 forward 向量 = +Y,与 up 向量 (0, 1, 0) 共线。look_at 计算 `right = cross(forward, up)`,共线向量叉积 = 零向量,normalize 失败。view matrix 退化,渲染崩。

这就是 **gimbal lock** 的一种表现——pitch = 90° 时 yaw 失去意义(任何 yaw 都给出同样相机姿态)。

防御:pitch clamp 在 ±(π/2 - ε),ε ≈ 0.01 弧度。相机永远不"完全垂直",forward 和 up 始终不正交。

fn look_at(eye: [f32; 3], target: [f32; 3], up: [f32; 3]) -> [[f32; 4]; 4] {
    let f = normalize([target[0] - eye[0], target[1] - eye[1], target[2] - eye[2]]);
    let r = normalize(cross(f, up));
    let u = cross(r, f);
    [
        [r[0], r[1], r[2], -dot(r, eye)],
        [u[0], u[1], u[2], -dot(u, eye)],
        [-f[0], -f[1], -f[2], dot(f, eye)],
        [0.0, 0.0, 0.0, 1.0],
    ]
}

fn dot(a: [f32; 3], b: [f32; 3]) -> f32 { a[0]*b[0] + a[1]*b[1] + a[2]*b[2] }
fn cross(a: [f32; 3], b: [f32; 3]) -> [f32; 3] {
    [a[1]*b[2] - a[2]*b[1], a[2]*b[0] - a[0]*b[2], a[0]*b[1] - a[1]*b[0]]
}
fn normalize(v: [f32; 3]) -> [f32; 3] {
    let len = (v[0]*v[0] + v[1]*v[1] + v[2]*v[2]).sqrt();
    if len > 1e-6 { [v[0]/len, v[1]/len, v[2]/len] } else { [0.0; 3] }
}

struct OrbitCamera {
    target: [f32; 3],
    distance: f32,
    yaw: f32,
    pitch: f32,
}

impl OrbitCamera {
    fn new(target: [f32; 3], distance: f32) -> Self {
        Self { target, distance, yaw: 0.0, pitch: 0.5 }
    }

    fn position(&self) -> [f32; 3] {
        let cp = self.pitch.cos();
        [
            self.target[0] + self.distance * cp * self.yaw.sin(),
            self.target[1] + self.distance * self.pitch.sin(),
            self.target[2] + self.distance * cp * self.yaw.cos(),
        ]
    }

    fn view_matrix(&self) -> [[f32; 4]; 4] {
        look_at(self.position(), self.target, [0.0, 1.0, 0.0])
    }

    fn orbit(&mut self, dx: f32, dy: f32) {
        self.yaw += dx * 0.005;
        self.pitch = (self.pitch - dy * 0.005).clamp(-1.55, 1.55);
    }

    fn zoom(&mut self, wheel: f32) {
        self.distance = (self.distance * (1.0 - wheel * 0.1)).clamp(0.1, 1000.0);
    }

    fn pan(&mut self, dx: f32, dy: f32) {
        // 计算 right 和 up
        let pos = self.position();
        let forward = normalize([
            self.target[0] - pos[0],
            self.target[1] - pos[1],
            self.target[2] - pos[2],
        ]);
        let right = normalize(cross(forward, [0.0, 1.0, 0.0]));
        let up = cross(right, forward);

        let scale = self.distance * 0.002;
        for i in 0..3 {
            self.target[i] -= right[i] * dx * scale;
            self.target[i] += up[i] * dy * scale;
        }
    }
}

    println!("=== Orbit Camera Demo ===\n");

    // 序列 1:绕 Y 轴 orbit
    println!("--- Sequence 1: orbit (yaw += π/2) ---");
    for step in 0..5 {
        cam.orbit(100.0, 0.0);  // 模拟鼠标 dx=100
        let pos = cam.position();
        println!("step {}: pos=({:>6.2}, {:>6.2}, {:>6.2}), yaw={:.2}",
                 step, pos[0], pos[1], pos[2], cam.yaw);
    }

    // 序列 2:zoom
    println!("\n--- Sequence 2: zoom in ---");
    for step in 0..5 {
        cam.zoom(0.5);  // 模拟滚轮
        println!("step {}: distance={:.2}", step, cam.distance);
    }

    // 序列 3:pitch(上下)
    println!("\n--- Sequence 3: pitch up ---");
    for step in 0..5 {
        cam.orbit(0.0, 50.0);
        let pos = cam.position();
        println!("step {}: pos=({:>6.2}, {:>6.2}, {:>6.2}), pitch={:.2}",
                 step, pos[0], pos[1], pos[2], cam.pitch);
    }

    // 序列 4:pan
    println!("\n--- Sequence 4: pan ---");
    let target_before = cam.target;
    cam.pan(100.0, 0.0);
    let target_after = cam.target;

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
