# Day 291 · 跳跃的怪物与占据树

> 解耦完成后第一次实战:加一个会**跳跃**的怪物和一个会**占据树**的随从。如果 Day 286-290 的解耦做对了,今天代码量应该极少——这就是"开放扩展"的回报。

## 0 · 为什么要有这一天

过去五天你做了一堆"看不见收益"的重构——把 Type 拆成 Brain 和 Visual,清理代码,加 sanity check。今天终于到了**验证解耦是否成功**的时刻。

具体做法是加两个新实体,看代码改动量:

- **Hopping Monstar**:一种怪物,定期跳跃——每 2 秒跳一次,跳跃过程中高度变化(visual 上是 sprite 偏移),落地后再次追玩家。这个 brain 需要"定时器"和"垂直位置状态",不是简单的 chase。
- **Occupying Trees**:一个随从会**占据树**——找到最近的空闲树,飞过去,"附身"树。这个 brain 需要"找最近树"的查询能力,以及多阶段状态(寻路、飞行、附身)。

1. 加 Brain variant(`MonsterHopping`、`FamiliarOccupyTree`)
2. 加 Visual variant(如果有新 sprite)
3. 实现 brain 函数(`brain_monster_hopping`、`brain_familiar_occupy`)
4. 加构造函数(`make_hopping_monster`、`make_familiar`)

**不需要改**:render 主循环、update dispatch、collision 系统、debug overlay——它们都通过 brain/visual 间接工作。

如果加新实体要改十处,说明解耦没做对,要回去补。今天的核心是**验证 + 实战**。

心理锚点:看完今天,你应该体验到"架构对了加功能像玩 Lego"的感觉。每次新功能应该 30-100 行代码搞定,不动旧代码。这是好架构的衡量标准。

## 1 · Casey 今天做了什么

Casey 今天的实现:

1. **加 `MonsterHopping` brain**——payload 包含 `jump_timer: f32`(下次跳跃倒计时)、`jump_vel_z: f32`(垂直速度,模拟跳跃)、`z: f32`(当前高度)
2. **加 `Familiar` brain**——payload 包含 `state: FamiliarState`(`Seeking`、`Traveling`、`Occupying`)、`target_tree_id: Option<u32>`

4. **sprite 渲染考虑 z**——hopping 怪物的 sprite 画在 (pos.x, pos.y - z) 位置,模拟"跳起来"
5. **debug overlay 显示 brain payload**——验证状态机正确

今天的代码量约 200-300 行,**全部是新加的**,没动旧代码。这就是解耦的回报。

## 2 · 心智模型

### 类比:Lego 积木

把解耦好的游戏代码想象成 Lego 积木。每个 entity 是几块积木拼起来——一块"位置"、一块"行为"、一块"视觉"。加新 entity 是**拿新积木拼**,不用**重新造积木**。

旧代码下,加新 entity 要造积木——写新 Type、写新 update 分支、写新 render 分支、写新 collision 分支。每个分支都要改主循环。

新代码下,加新 entity 是拼积木——在 brain enum 加 variant(造新积木),写 brain 函数(描述怎么用),主循环**完全不动**。这是好架构的本质:**加功能不改主路径**。

今天的两个新实体正好验证这两点:

- **Hopping Monstar**:用现有 visual(monstar sprite),只是 brain 新——验证"brain 独立扩展"
- **Occupying Trees**:用现有 visual(tree 和 familiar sprite),brain 有多阶段——验证"复杂 brain 也能加"

如果两个都能加,解耦就成功。

### 2.1 跳跃的物理:2.5D 的简化

HH 是 2D 游戏,但跳跃需要"高度"。Casey 的做法是**2.5D**——视觉上加 z 轴,但逻辑上仍 2D。

```rust
struct HoppingBrain {
    jump_timer: f32,   // 距离下次跳跃的倒计时(秒)
    z: f32,            // 当前高度(像素)
    vel_z: f32,        // 垂直速度
}

fn brain_hopping_monster(e: &mut Entity, ctx: &Context, dt: f32) {
    let Some(Brain::MonsterHopping { ref mut jump_timer, ref mut z, ref mut vel_z }) = e.brain else { return; };

    // 第一阶段:水平移动(追玩家)
    if let Some(player_pos) = ctx.player_pos() {
        let d = (player_pos - e.pos).normalize();
        e.vel = d * 30.0;
    }

    // 第二阶段:跳跃逻辑
    *jump_timer -= dt;
    if *jump_timer <= 0.0 {
        *jump_timer = 2.0;  // 重置 2 秒
        *vel_z = 200.0;     // 起跳初速度
    }
    // 重力
    *vel_z -= 800.0 * dt;
    *z += *vel_z * dt;
    if *z < 0.0 {
        *z = 0.0;
        *vel_z = 0.0;
    }
}

fn render_hopping_monster(e: &Entity) {
    let z = match e.brain {
        Some(Brain::MonsterHopping { z, .. }) => z,
        _ => 0.0,
    };
    draw_sprite(MONSTER_SPRITE, e.pos.x, e.pos.y - z);  // 视觉上抬高 z 像素
}
```

**关键概念**:
- **2.5D**——逻辑 2D,视觉模拟 3D。游戏行业常见(Sonic、Hollow Knight 的部分场景)。
- **重力公式**:`v -= g*dt; z += v*dt` 是 Euler 积分。Casey 在 day 043 教过同样的运动方程,这里应用到 z 轴。
- **跳跃脉冲**:每 N 秒给 z 一个初速度,然后重力把它拉回来——形成抛物线轨迹。

### 2.2 多阶段 brain:状态机

Familiar(随从)的 brain 有三个状态:

```rust
enum FamiliarState {
    Seeking,        // 找最近的空闲树
    Traveling { tree_id: u32 },  // 飞向某树
    Occupying { tree_id: u32 },  // 附身在该树上
}

struct FamiliarBrain {
    state: FamiliarState,
}
```

状态机转换:
- `Seeking` → 找到树 → `Traveling`
- `Traveling` → 到达树 → `Occupying`
- `Occupying` → 玩家走远 → `Seeking`

实现:

```rust
fn brain_familiar(e: &mut Entity, ctx: &Context, dt: f32) {
    let Some(Brain::Familiar { ref mut state }) = e.brain else { return; };

    match state {
        FamiliarState::Seeking => {
            if let Some(tree_id) = ctx.find_nearest_free_tree(e.pos) {
                *state = FamiliarState::Traveling { tree_id };
            } else {
                // 没有空闲树,跟随玩家
                seek_player(e, ctx);
            }
        }
        FamiliarState::Traveling { tree_id } => {
            if let Some(tree_pos) = ctx.tree_pos(*tree_id) {
                let d = tree_pos - e.pos;
                let dist = d.length();
                if dist < 5.0 {
                    *state = FamiliarState::Occupying { tree_id: *tree_id };
                } else {
                    e.vel = d.normalize() * 100.0;
                }
            } else {
                // 树没了,回 Seeking
                *state = FamiliarState::Seeking;
            }
        }
        FamiliarState::Occupying { tree_id } => {
            // 附身在树上,位置吸附
            if let Some(tree_pos) = ctx.tree_pos(*tree_id) {
                e.pos = tree_pos;
                e.vel = Vec2::ZERO;
            }
        }
    }

    // 应用 vel
    e.pos.x += e.vel.x * dt;
    e.pos.y += e.vel.y * dt;
}
```

**关键概念**:
- **状态机(FSM)**——一组状态 + 状态间转换规则。今天 Casey 第一次在 HH 用 FSM,虽然 day 286 的 brain enum 已经是雏形。
- **状态转换触发**:状态内部检查条件,满足时切换。比如 Traveling 时检查 `dist < 5.0` 触发到 Occupying。
- **payload 携带状态相关数据**:Traveling 携带 `tree_id`(正在飞向哪棵树),Occupying 携带 `tree_id`(附身哪棵)。其他状态不需要。

### 2.3 "占据树"的查询

`ctx.find_nearest_free_tree` 怎么实现?

```rust
impl Context<'_> {
    fn find_nearest_free_tree(&self, from: Vec2) -> Option<u32> {
        let mut best: Option<(u32, f32)> = None;
        for tree in &self.world.entities {
            // 检查这棵树是不是 "tree" visual 且没人占据
            if !self.is_tree_free(tree.id) { continue; }
            let dist = (tree.pos - from).length();
            match best {
                None => best = Some((tree.id, dist)),
                Some((_, d)) if dist < d => best = Some((tree.id, dist)),
                _ => {}
            }
        }
        best.map(|(id, _)| id)
    }

    fn is_tree_free(&self, tree_id: u32) -> bool {
        // 遍历所有 familiar,看是否有 occupying 这棵树的
        !self.world.entities.iter().any(|e| {
            matches!(
                e.brain,
                Some(Brain::Familiar { state: FamiliarState::Occupying { tree_id: t } })
                    if t == tree_id
            )
        })
    }
}
```

这是 O(n*m)——n 是树数量,m 是 familiar 数量。100 棵树和 10 个 familiar 时是 1000 次比较,可以接受。1000 棵树就要优化——典型优化是**空间划分**(grid、quadtree),Day 309 会讲。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

"会跳跃的怪物"在游戏行业有专门术语:**rhythm enemy**——按节奏攻击的敌人。比如《空洞骑士》的跳跃苍蝇、《黑暗之魂》的骑士。设计核心是**节奏感**——玩家学会"它跳完后有 1 秒空隙,这时攻击"。

Casey 的 hopping monstar 是最简单版本——固定 2 秒跳一次。商业游戏会加随机化(2 秒 ± 0.5 秒)、连锁(连跳三次)、攻击(跳跃落地造成 AOE 伤害)。这些扩展都能在 brain 函数里加,不动架构。

"占据树"对应游戏行业的 **possessing AI**——附身到场景物体上。《艾尔登法环》的某些 boss 会附身雕像;《以撒的结合》的敌人会附身道具。设计核心是**多阶段战斗**——每个阶段 boss 行为不同,玩家要学会应对。

工业级的多阶段 brain 比今天 Casey 的复杂得多,可能用 Behavior Tree 或 Utility AI。但**状态机是基础**——Casey 今天教的就是 FSM 入门。

### 3.2 · 🎨 图形学视角

2.5D 跳跃的渲染有个微妙点:**阴影**。真实跳跃时,物体在地面有阴影,跳跃高度越高阴影越小、越模糊。Casey 在 day 291 暂时不画阴影,但工业实现:

```rust
fn render_hopping_monster(e: &Entity) {
    let z = match e.brain {
        Some(Brain::MonsterHopping { z, .. }) => z,
        _ => 0.0,
    };
    // 阴影:画在地面,大小随 z 缩小
    let shadow_scale = 1.0 - (z / 200.0).min(0.7);
    draw_shadow(e.pos.x, e.pos.y, shadow_scale);
    // 实体:画在 (pos.x, pos.y - z)
    draw_sprite(MONSTER_SPRITE, e.pos.x, e.pos.y - z);
}
```

阴影提供"高度"的视觉线索,没有阴影的跳跃看起来像"原地伸缩",不真实。Casey 在 Phase 7+ 加光照时会处理。

另一个图形学点:**sprite 拉伸**。跳跃起跳瞬间拉伸(竖直拉长),落地瞬间压缩(水平拉宽)。这是 Disney 12 动画原则中的"挤压拉伸",让动作有冲击力。

```rust
let scale_y = if vel_z > 100.0 { 1.2 } else if vel_z < -100.0 { 0.9 } else { 1.0 };
draw_sprite_scaled(MONSTER_SPRITE, e.pos.x, e.pos.y - z, 1.0, scale_y);
```

Casey 在 day 291 不做这种细节,但好的游戏都会做。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里"状态机"无处不在。最典型:**TCP 协议栈**。每个 TCP 连接是个状态机,状态包括 `CLOSED`、`LISTEN`、`SYN_SENT`、`ESTABLISHED`、`CLOSE_WAIT` 等 11 个状态。每次收到包,根据当前状态 + 包类型决定动作 + 转换到新状态。

```
CLOSED → (应用调 connect) → SYN_SENT
SYN_SENT → (收到 SYN+ACK) → ESTABLISHED
ESTABLISHED → (应用调 close) → FIN_WAIT_1
...
```

Casey 今天的 FamiliarState 是这个的小型版本——三状态 FSM,brain 函数检查当前状态决定动作。Linux 的 TCP FSM 是 Casey 这个模式的工业级形态。

另一个例子:**调度器任务状态**。Linux 进程有 `TASK_RUNNING`、`TASK_INTERRUPTIBLE`、`TASK_UNINTERRUPTIBLE`、`TASK_STOPPED` 等状态。调度器根据状态决定调度行为。

### 3.4 · 🦀 Rust 生态视角

Rust 表达状态机有几个模式:

**模式 1:enum + match(今天 Casey 用的)**

```rust
enum FamiliarState {
    Seeking,
    Traveling { tree_id: u32 },
    Occupying { tree_id: u32 },
}
```

简单、清晰、类型安全。缺点:状态转换靠人肉 match。

**模式 2:Type-state(类型状态模式)**

```rust
struct Seeking;
struct Traveling { tree_id: u32 }
struct Occupying { tree_id: u32 }

trait FamiliarState {}
impl FamiliarState for Seeking {}
impl FamiliarState for Traveling {}
impl FamiliarState for Occupying {}

struct Familiar<S: FamiliarState> {
    pos: Vec2,
    state: S,
}

// 转换通过 method 实现
impl Familiar<Seeking> {
    fn travel(self, tree_id: u32) -> Familiar<Traveling> {
        Familiar { pos: self.pos, state: Traveling { tree_id } }
    }
}
```

每个状态是不同**类型**,转换消耗 self 产生新类型——**编译器保证转换合法**。代价:每个状态一个类型,Familiar 不能存在 `Vec<Familiar<dyn State>>`(类型不统一)。

**模式 3:crate `statig`(状态机库)**

```rust
use statig::StateMachine;

#[derive(StateMachine)]
enum FamiliarState {
    #[state(entry_action = "enter_seeking")]
    Seeking,
    #[state(superstate = "traveling_or_occupying")]
    Traveling { tree_id: u32 },
    #[state(superstate = "traveling_or_occupying")]
    Occupying { tree_id: u32 },
}
```

`statig` 用 macro 生成状态机代码,处理转换、entry/exit action。但学习曲线陡,HH 教学不用。

**Casey 选模式 1**——最简单、最直观、教学友好。生产代码可能选模式 3,因为复杂状态机用 enum 容易写错。

## 5 · 对照与变奏

### 同一 AI 的不同实现

**问题**:让 NPC 每 5 秒朝玩家移动 1 秒,然后停下 4 秒。

**Reaction 版**:
```rust
struct PeriodicChase { phase_timer: f32 }
fn think(e: &mut Entity, dt: f32) {
    e.brain.unwrap().phase_timer -= dt;
    if (e.brain.unwrap().phase_timer % 5.0) < 1.0 {
        e.vel = chase_dir();
    } else {
        e.vel = Vec2::ZERO;
    }
}
```
能用,但状态隐含在 timer 里。

**FSM 版**:
```rust
enum State { Chasing, Idle }
fn think(e: &mut Entity, dt: f32) {
    match state {
        Chasing => { e.vel = chase_dir(); timer -= dt; if timer <= 0 { state = Idle; timer = 4.0 } }
        Idle => { e.vel = Vec2::ZERO; timer -= dt; if timer <= 0 { state = Chasing; timer = 1.0 } }
    }
}
```
状态显式,可读性更好。

**Behavior Tree 版**:用 selector + sequence + condition 节点组合。最灵活但最复杂。

Casey 用 FSM——平衡复杂度和清晰度。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 的 hopping monster 跳跃高度由 `vel_z` 初速度决定。要让它跳得更高,初速度应该大还是小?为什么?

**参考解答**:初速度应该**更大**。物理上,跳跃高度 `h = v²/(2g)`(由 `0 = v² - 2*g*h` 推出),所以 `h` 与 `v²` 成正比。要让 `h` 翻倍,`v` 要 √2 倍(约 1.414 倍)。

这就是为什么游戏里"跳两倍高"的感觉差异比"跳两倍远"小——`h` 是 v 的二次函数,需要 v 增长更多。

### Lv2 · 动手实践

**题**:实现一个 hopping monster brain:
- 每 2 秒跳一次,初速度 `vel_z = 200`
- 重力 `g = 800`
- 水平移动追玩家(`vel = (player - pos).normalize() * 30`)
- 跳跃过程中 vel 不变(水平不变)
- 渲染时 sprite 位置 `y = pos.y - z`

完成标准:写测试,2 秒后 z 不为零,3 秒后 z 又回到零(因为下次起跳前的某个时刻落地)。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn mul(self, k: f32) -> Self { Self::new(self.x * k, self.y * k) }
    fn length(self) -> f32 { (self.x * self.x + self.y * self.y).sqrt() }
    fn normalize(self) -> Self {
        let l = self.length();
        if l > 1e-6 { self.mul(1.0 / l) } else { Self::new(0.0, 0.0) }
    }
}

#[derive(Copy, Clone, Debug)]
struct HoppingBrain {
    jump_timer: f32,
    z: f32,
    vel_z: f32,
}

#[derive(Copy, Clone, Debug)]
struct Entity {
    pos: Vec2,
    vel: Vec2,
    brain: HoppingBrain,
}

const GRAVITY: f32 = 800.0;
const JUMP_VEL: f32 = 200.0;
const JUMP_INTERVAL: f32 = 2.0;
const MOVE_SPEED: f32 = 30.0;

fn brain_hopping(e: &mut Entity, player_pos: Vec2, dt: f32) {
    // 水平:追玩家
    let d = player_pos.sub(e.pos);
    if d.length() > 1e-3 {
        e.vel = d.normalize().mul(MOVE_SPEED);
    }

    // 垂直:跳跃
    e.brain.jump_timer -= dt;
    if e.brain.jump_timer <= 0.0 {
        e.brain.jump_timer = JUMP_INTERVAL;
        e.brain.vel_z = JUMP_VEL;
    }
    e.brain.vel_z -= GRAVITY * dt;
    e.brain.z += e.brain.vel_z * dt;
    if e.brain.z < 0.0 {
        e.brain.z = 0.0;
        e.brain.vel_z = 0.0;
    }
}

fn apply_vel(e: &mut Entity, dt: f32) {
    e.pos.x += e.vel.x * dt;
    e.pos.y += e.vel.y * dt;
}

fn main() {
    let mut e = Entity {
        pos: Vec2::new(0.0, 0.0),
        vel: Vec2::new(0.0, 0.0),
        brain: HoppingBrain { jump_timer: 2.0, z: 0.0, vel_z: 0.0 },
    };
    let player_pos = Vec2::new(100.0, 0.0);
    let dt = 0.05;  // 20 FPS 仿真

    // 跑 4 秒,看 z 变化
    let mut t = 0.0;
    while t < 4.0 {
        brain_hopping(&mut e, player_pos, dt);
        apply_vel(&mut e, dt);
        if t > 1.9 && t < 2.1 {
            println!("t={:.2}: z={:.2} (jumping)", t, e.brain.z);
        }
        t += dt;
    }

    // 验证:跳跃期间 z > 0
    let mut e2 = Entity {
        pos: Vec2::new(0.0, 0.0),
        vel: Vec2::new(0.0, 0.0),
        brain: HoppingBrain { jump_timer: 2.0, z: 0.0, vel_z: 0.0 },
    };
    // 跑到 t = 2.5(刚跳了 0.5 秒)
    for _ in 0..50 { brain_hopping(&mut e2, player_pos, 0.05); }
    println!("After 2.5s: z={:.2}", e2.brain.z);  // 应 > 0
    assert!(e2.brain.z > 0.0, "should be airborne at t=2.5");

    // 跑到 t = 3.9(几乎下次起跳)
    for _ in 0..28 { brain_hopping(&mut e2, player_pos, 0.05); }
    println!("After 3.9s: z={:.2}", e2.brain.z);  // 应 = 0
    assert!(e2.brain.z.abs() < 1e-3, "should be grounded");

    println!("Hopping brain tests passed!");
}
```

**每行解释**:
- 跳跃物理与 day 043 完全一致——位置/速度/加速度的 Euler 积分,只是 z 维度独立
- `jump_timer` 是 FSM 隐式状态——非零表示"在地面等待",vel_z > 0 表示"起跳上升中",vel_z < 0 表示"下落中",z == 0 表示"落地"
- GRAVITY 是游戏调出来的——800 给一个"有力但不过分"的感觉

**Troubleshooting**:

- z 不变 —— `e.brain.vel_z` 是 Copy,改函数参数不持久。要 `&mut` 引用
- 跳跃"飘" —— 重力太小,加大 GRAVITY
- 跳跃"过快" —— 初速度太大,减小 JUMP_VEL
- 跳跃不同步 —— dt 太大导致 Euler 积分误差,降到 0.016(60 FPS)
