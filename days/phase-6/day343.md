
# Day 343 · 保存与恢复动态分配的内存页

> 把"动态 arena 的当前状态"快照保存到一个 token,后续可以恢复——这是热重载(hot reload)、状态回滚(state rewind)、断点续传(checkpoint/restart)的共同基石。

## 0 · 为什么要有这一天

你在写一个游戏编辑器,允许设计师按 Ctrl+Z 撤销刚才的关卡改动。最简单的做法是:每次修改前保存整个游戏状态的快照,撤销时恢复。

但游戏状态可能几百 MB:所有 entity 位置、tile map、AI 状态、对话历史、所有动态 arena 的内容。你不能每次操作都拷贝 100 MB,那 60 FPS 下磁盘要爆。

更聪明的做法:**保存 arena 的"配置"而不是内容**。具体说,arena 内部的状态是:

1. 当前块的指针
2. 每个块的 used 偏移
3. 链表结构

只要这些不变,arena 的"分配行为"就一致。如果同时**保留底层数据不被覆盖**,就能"恢复"到任意快照点。

今天的核心是:**给 arena 加 save/restore 接口**,save 返回一个 token(几十字节),restore(token) 把 arena 状态恢复到 save 时。底层内存**不被释放**,但 allocator 视角上看是"回到过去了"。

这种"快照保存"有四个真实用途:

1. **热重载**:游戏运行时改代码,编译,重新加载 cdylib。你需要保存当前游戏状态,加载新库,然后恢复状态——不能让玩家看到画面跳变
2. **关卡撤销**:编辑器里 Ctrl+Z,撤销最后一个关卡编辑
3. **网络回滚**:客户端预测失败时,回退到服务器确认的那个帧,重新模拟
4. **调试快照**:断点处保存状态,继续跑几秒,看不清就回到断点重新观察

Casey 这套设计的妙处是:**零拷贝**。token 只记几个指针偏移,内容原地保留。restore 时把指针拨回去,旧内容自动被"未来分配"覆盖(如果你接受这种行为)。

心理锚点:今天之后你能在任何时候 `let snap = arena.save()`,后面 `arena.restore(snap)` 一行代码"穿越"回去。这是从"线性时间"的分配器到"可回放时间"的分配器。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 在 day342 的 arena 上加了一个新 API:

```c
typedef struct {
    memory_arena *arena;
    memory_arena *saved_block;       // 当时的 current block
    memory_index saved_used;          // 当时的 used 偏移
    int saved_temp_count;             // 当时的 temp_count
} arena_snapshot;

arena_snapshot save_arena(memory_arena *arena);
void restore_arena(arena_snapshot snap);
```

实现很直接:

```c
arena_snapshot save_arena(memory_arena *arena) {
    arena_snapshot snap;
    snap.arena = arena;
    snap.saved_block = arena;
    snap.saved_used = arena->used;
    snap.saved_temp_count = arena->temp_count;
    return snap;
}

void restore_arena(arena_snapshot snap) {
    memory_arena *arena = snap.arena;
    arena = snap.saved_block;
    arena->used = snap.saved_used;
    arena->temp_count = snap.saved_temp_count;
}
```

注意:**Casey 不释放 save 后开的临时块**——它们留在链表里,只是不再被分配器引用。下一次 alloc 会从 saved_block 的 saved_used 继续,旧块可以被"重用"——但 Casey 选择不动它们,等下次 arena 增长时优先用这些已存在的块。

Casey 在视频里讨论了几个细节:

1. **save/restore 不影响底层内存**:旧块上的内容依然存在,如果你 save 后写过一些数据,restore 后这些数据"看不见",但物理上还在,可以通过特殊手段读到(调试用)
2. **restore 的不变量**:restore 之前不能有任何 temp 在范围内(`ASSERT(temp_count == saved_temp_count)`),否则状态错乱
3. **嵌套 save**:save1 → save2 → restore2 → restore1 是合法的,LIFO

这是相对 day342 的 temp memory 的进一步抽象——temp 是"短期 begin/end",save 是"长期跨函数快照"。

## 2 · 心智模型

### 类比:文件系统的快照

Linux 文件系统有"快照"功能(COW = copy on write):

- `snapshot create` 立刻返回,快照里只是"当时的 metadata"
- 你继续往文件系统写,新数据写到新位置
- `snapshot rollback` 把文件系统恢复到当时的状态

底层物理空间不立即释放(因为快照可能引用旧块),只有删除快照时才能回收。

arena 的 save/restore 是同样的语义:

- `save` 返回 token,只记指针和偏移
- 后续 alloc 继续往前写
- `restore` 把分配器指针拨回 save 时的位置
- 期间写的块数据物理上还在,但分配器不再引用它们

### 严谨原理:状态 = (current block, used, temp_count)

arena 的"状态"就这三个值。为什么够?

- `current block` 决定下一次分配在哪
- `used` 决定下一次分配的偏移
- `temp_count` 决定有多少未关闭 temp(诊断用,也是正确性约束)

链表 `prev` 字段是"历史"——它指向更早的块。但分配器视角上"链表"是隐式的:从 current block 顺着 prev 就能遍历所有历史块。所以 save 不需要记整个链表,只需要记 current 的入口。

restore 时把 current 指针拨回去,链表自动"截断"——后面的块还在内存里但分配器看不到。

### 为什么不释放 save 后的块?

直接释放有诱惑力(立即回收内存),但 Casey 不这么做,原因:

1. **O(1) restore**:释放要遍历链表 O(N),restore 应该是 O(1) 的廉价操作
2. **保留给未来用**:下一次 arena 增长时,优先复用已存在的块,而不是重新 mmap——`mmap` 有几百纳秒成本
3. **调试便利**:restore 后旧数据还在,调试器能读到"上一个状态",诊断 bug

代价是物理内存占用比"理想释放"略高。但实践中 save/restore 通常配对使用(短时间内 begin/end),所以旧块很快被新分配覆盖,占用不会失控。

### 实现:Rust 版的 Snapshot

```rust
pub struct ArenaSnapshot {
    arena: *const Arena,         // 保存时哪个 arena(防止跨 arena restore)
    saved_block: NonNull<Block>,
    saved_used: usize,
    saved_temp_count: usize,
}
```

`*const Arena` 是裸指针,不带 lifetime——这是关键。snapshot 可能被存到 `Vec<ArenaSnapshot>` 里(撤销栈),它的生命周期超过创建时的 borrow。但这要求调用方保证:restore 时 arena 还活着,否则 UB。

更严格的版本(我们选):snapshot 自带 arena 引用 `&'a Arena`。这样编译器保证 arena 还活着,代价是 snapshot 不能 escape 当前作用域的 arena borrow。Casey 用 C 没有 lifetime,所以可以更灵活;Rust 我们用 `&'a` 保险。

### save 和 begin_temp 的区别

| 特性 | `begin_temp` | `save` |
|---|---|---|
| 用途 | 函数内临时存储 | 跨函数的状态快照 |
| 关闭方式 | 必须 LIFO 关闭 | 任意时刻 restore,也可以丢弃 |
| 是否释放 | 是(restore 释放临时块) | 否(restore 不释放,保留旧块) |
| 典型场景 | 函数返回前自动关 | 编辑器撤销栈 |

它们是互补的:temp 是"短期 LIFO",save 是"长期任意"。Casey 的设计用同一个 `saved_state` 字段,但行为不同——`end_temp` 释放临时块,`restore` 不释放。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

save/restore 在游戏里的主要用途:

1. **关卡编辑器撤销栈**:每次编辑前 save,撤销时 restore 栈顶。Unity / Unreal 都有这个,他们叫 `Undo.RegisterSnapshot`
2. **AI 决策回滚**:AI 模拟未来几步,如果发现走错,restore 到分支起点重选。这是 minimax / MCTS 算法的核心
3. **网络预测回滚**:客户端预测 N 帧后,服务器校正"实际状态",客户端 restore 到确认帧,重新模拟
4. **热重载**: Casey 在 HH 里大量用这个——改代码后 save state,重启游戏(其实是 cdylib 重载),restore state,玩家无感知

主流引擎的实现差异:

- **Unreal**:`FTransaction` 系统,记录每个对象的"修改前状态",撤销时反向应用。粒度细(单字段),开销大
- **Unity**:`Undo` 类似,但 C# 对象图遍历复杂,有 GC 互动
- **Casey**:**arena 级 save/restore**,粒度粗,但极快(几纳秒)

Casey 的取舍:游戏开发 95% 的撤销操作是"我刚才改坏了,整段重来",细粒度的字段级 undo 收益不大。arena 级 undo 更简单更快。

### 3.2 · 🐧 Linux 系统编程视角

Linux 内核的 checkpoint/restart(C/R)项目尝试过类似功能——把整个进程状态保存到磁盘,后续恢复。但这个项目没合并到主线,因为太复杂。

简化版:Linux 的 `fork()` 是"进程级 snapshot":

- `fork` 创建子进程,复制父进程的所有内存(COW 优化,只有改时才真复制)
- 子进程独立运行,父进程继续
- 父进程崩溃时,可以从子进程"恢复"

游戏引擎的 save/restore 是"轻量级 fork"——只在 arena 层,不涉及其他进程状态。

#### 用 `fork` 实现热重载

某些游戏(如游戏服务端)用 fork 做热重载:

```bash
# 跑着的服务进程
./game_server &
# 想热重载,发信号
kill -USR1 $(pidof game_server)
# server 进程 fork 出新进程,exec 新二进制,旧进程退出
# 但游戏状态需要在 fork-exec 之间通过共享内存迁移
```

这套机制比 Casey 的"arena save/restore + cdylib reload"更复杂。Casey 的方案更优雅。

#### CRIU(Checkpoint/Restore In Userspace)

Linux 有 CRIU 项目(https://criu.org/),能 dump 任意进程到磁盘,稍后 restore。常用于容器迁移。这套方案对游戏热重载来说太重(整个进程包括栈、文件描述符、socket 状态),但概念上和 arena save/restore 一致。

### 3.3 · 🦀 Rust 生态视角

Rust 没有标准化的 arena save/restore crate,但每个引擎都自己实现。Bevy 的 `bevy_ecs` 有 `World::as_any()` 把整个世界序列化,但不是"原地快照",而是"深拷贝"。

#### Lifetime 选择

```rust
// 方案 A: snapshot 借用 arena
pub struct Snapshot<'a> {
    arena: &'a Arena,
    // ...
}
fn save<'a>(arena: &'a Arena) -> Snapshot<'a> { ... }
fn restore<'a>(snap: Snapshot<'a>) { ... }

// 方案 B: snapshot 持有裸指针
pub struct Snapshot {
    arena: *const Arena,
}
unsafe impl Send for Snapshot {}
```

方案 A 更安全但灵活度低(snapshot 不能 escape arena borrow)。方案 B 灵活但需要 unsafe。

教学版我们选方案 A,生产代码可以两者结合(snapshot 内部 unsafe,外部包装 safe API)。

#### 借用检查冲突

借用 arena 来 save 没问题,但 restore 时要修改 arena——和 save 时的 immutable borrow 冲突:

```rust
let arena = Arena::new();
let snap = arena.save();          // immutable borrow
arena.alloc(...);                 // 也需要 immutable borrow (alloc_bytes 接收 &self)
let snap2 = arena.save();
arena.restore(snap);              // restore 接收 &self 吗?
```

我们设计 `restore(&self, snap)`——内部用 UnsafeCell 修改字段。这样 lifetime 不冲突。

但要注意:同时存在多个 snapshot 时,restore 一个会让其他 snapshot 失效(指向已"截断"的链表)。这是语义上的责任,不是编译器能强制的。

## 4 · 认知地图

### 4.1 上级(它属于哪个更大抽象?)

- **Copy-on-write snapshot(COW 快照)** — 文件系统、虚拟机、容器都用类似机制
- **Persistence(持久化)** — 把"易失状态"保存到"持久介质"——arena snapshot 是"内存内的持久化"
- **Time travel debugging(时光旅行调试)** — 调试器级别的高级功能,save/restore 是底层支持

### 4.2 同级(并行方案对比)

| 方案 | 关键差别 | 何时用 | 本项目选了哪个 |
|---|---|---|---|
| arena save/restore | 几字节 token,原地不释放 | 跨函数长期快照 | ✅ 今天加 |
| temp memory | LIFO 严格,释放临时块 | 函数内临时 | 已有(day342) |
| 深拷贝 | 完整复制内容 | 跨进程 / 跨机器 | 太慢,不选 |
| 序列化到磁盘 | 写文件 | 跨重启 | Phase 7 才做 |
| COW page( mmap + fork ) | OS 级 | 单进程 fork | 不用,粒度太大 |

### 4.3 下级(内部零件)

- **`ArenaSnapshot` 结构** — saved_block, saved_used, saved_temp_count
- **`save_arena` / `restore_arena`** — API 入口
- **快照栈** — 撤销场景需要 `Vec<ArenaSnapshot>`
- **不变量**:temp_count 必须一致

## 5 · 对照与变奏

### 不同语言的快照机制

| 语言/系统 | 机制 |
|---|---|
| HH(今天 Casey 版) | arena save/restore,几字节 token |
| C++ | 类似 RAII guard,析构可自动 restore |
| Lisp | "unwind-protect",动态作用域 |
| Java | `clone()`(深拷贝)+ 序列化 |
| Python | `pickle`,深拷贝序列化 |
| Erlang / Elixir | "single assignment",所有状态自动快照 |

Erlang 的"每个变量只赋值一次"是语言级 save/restore——任何"过去状态"都还在内存里(直到 GC),天然支持时间旅行。代价是性能(每次修改都 copy)。

### 历史演化

- **1960s Lisp**:GC + immutable 数据,自然快照
- **1970s Smalltalk**:`become:` 操作做对象级 swap
- **1980s**:商用 DB 的 MVCC(multi-version concurrency control)
- **1990s 游戏机**:内存小,save/restore 几乎不用(直接重新启动)
- **2000s PC**:内存大,save/restore 流行,Unreal 的 transaction 系统成熟
- **2010s Rust**:lifetime 系统让"快照借用的对象"变得安全
- **2020s**:Time-travel debugging(TTD)在 Chrome、Edge 内置,概念普及

### 工业级 vs 教学版

| 特性 | 教学版 | 工业版 |
|---|---|---|
| 跨 arena restore 检查 | panic | 类型系统保证 |
| Snapshot 老化检测 | 无 | "snapshot 指向已截断链表"诊断 |
| 增量 save | 无 | 只记变化部分 |
| Snapshot 压缩 | 无 | 把旧块合并 |

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 的 save/restore 不释放底层块。某开发者提议"restore 时释放掉 save 后开的块,避免内存浪费"。论证:为什么不释放是更好的设计?

**参考解答**:

1. **O(1) restore**:释放要遍历链表 O(N),restore 应该几纳秒
2. **复用已分配块**:下次 arena 增长时优先用这些块,避免 mmap 的几百纳秒
3. **调试便利**:旧数据物理上还在,调试器能读到
4. **配合多线程**:多线程下"释放"涉及锁,O(1) restore 避免锁
5. **简化不变量**:不释放意味着所有块地址不变,持有指针的代码继续工作

权衡:内存占用略高,但实践中 save/restore 配对使用,不会累积。是合理 trade-off。

### Lv2 · 动手实践

**题**:在 day342 的 arena 上加 save/restore,要求:

- `save(&Arena) -> Snapshot`(借用 arena)
- `restore(&Arena, Snapshot)`(恢复状态)
- save 后开的块不释放,restore 时只拨指针
- snapshot 持有 `&'a Arena`,编译器保证 arena 还活着

测试:save 后 alloc 一堆,restore,确认 alloc 接着 save 时的位置继续。

完成标准:测试断言"restore 后下一次 alloc 的地址 == save 时的 used 偏移 + base 地址"。

**参考解答**:

```rust
use std::cell::{Cell, UnsafeCell};
use std::ptr::NonNull;

const DEFAULT_BLOCK_SIZE: usize = 1 << 20;

struct Block {
    base: NonNull<u8>,
    size: usize,
    used: Cell<usize>,
    prev: Option<Box<Block>>,
}

impl Block {
    fn new(size: usize, prev: Option<Box<Block>>) -> Box<Self> {
        let layout = std::alloc::Layout::from_size_align(size, 16).unwrap();
        let ptr = unsafe { std::alloc::alloc(layout) };
        let base = NonNull::new(ptr).expect("OOM");
        Box::new(Block { base, size, used: Cell::new(0), prev })
    }
}

impl Drop for Block {
    fn drop(&mut self) {
        let layout = std::alloc::Layout::from_size_align(self.size, 16).unwrap();
        unsafe { std::alloc::dealloc(self.base.as_ptr(), layout) }
    }
}

pub struct Arena {
    current: UnsafeCell<NonNull<Block>>,
    temp_count: Cell<usize>,
}

pub struct Snapshot<'a> {
    arena: &'a Arena,
    saved_block: NonNull<Block>,
    saved_used: usize,
}

impl Arena {
    pub fn new(initial: usize) -> Self {
        let size = initial.max(DEFAULT_BLOCK_SIZE);
        let block = Block::new(size, None);
        Self {
            current: UnsafeCell::new(NonNull::from(Box::leak(block))),
            temp_count: Cell::new(0),
        }
    }

    pub fn alloc_bytes(&self, n: usize, align: usize) -> NonNull<u8> {
        let block = unsafe { &**self.current.get() };
        let base_addr = block.base.as_ptr() as usize;
        let used = block.used.get();
        let aligned = (base_addr + used + align - 1) & !(align - 1);
        let new_used = aligned + n - base_addr;
        if new_used > block.size {
            let new_size = n.max(DEFAULT_BLOCK_SIZE);
            unsafe {
                let cur = *self.current.get();
                let old_box = Box::from_raw(cur.as_ptr());
                let new_block = Block::new(new_size, Some(old_box));
                *self.current.get() = NonNull::from(Box::leak(new_block));
            }
            let block = unsafe { &**self.current.get() };
            block.used.set(n);
            return block.base;
        }
        block.used.set(new_used);
        unsafe { NonNull::new_unchecked(aligned as *mut u8) }
    }

    pub fn save(&self) -> Snapshot<'_> {
        let block = unsafe { **self.current.get() };
        Snapshot {
            arena: self,
            saved_block: block,
            saved_used: unsafe { block.as_ref().used.get() },
        }
    }

    pub fn restore(&self, snap: Snapshot<'_>) {
        // 注意:snap 的 lifetime 借用 self,所以 restore 期间 snap 还活着
        // restore 完成后,snap 失效(它消耗掉)
        assert!(std::ptr::eq(snap.arena, self), "cross-arena restore");
        unsafe {
            *self.current.get() = snap.saved_block;
            (*snap.saved_block.as_ptr()).used.set(snap.saved_used);
        }
    }

    pub fn current_used_offset(&self) -> usize {
        unsafe { (**self.current.get()).used.get() }
    }
}

impl Drop for Arena {
    fn drop(&mut self) {
        unsafe { drop(Box::from_raw((*self.current.get()).as_ptr())) }
    }
}

fn main() {
    let arena = Arena::new(1 << 16);
    let snap = arena.save();
    let saved_offset = arena.current_used_offset();
    println!("Saved at offset {}", saved_offset);

    // 分配 100 字节,可能开新块
    let _ = unsafe { arena.alloc_bytes(100, 1) };
    println!("After 100B alloc: offset = {}", arena.current_used_offset());

    // restore
    arena.restore(snap);
    println!("After restore: offset = {}", arena.current_used_offset());

    // 验证 offset 回到了 saved
    assert_eq!(arena.current_used_offset(), saved_offset);
    println!("OK: restore worked");
}
```

注意 `restore(snap: Snapshot<'_>)`——snapshot 在 restore 后被消耗,不能重复 restore。如果想多次 restore,把 `restore(&self, &Snapshot)` 改成传引用。

### Lv3 · 迁移设计

**题**:用 save/restore 实现一个"AI 决策回滚"系统:

- AI 模拟未来 K 步,每步产生 game state
- 如果某分支输掉,restore 到分支起点换决策
- 多个分支并行尝试(类似 minimax 树)

设计:每个树节点持有 snapshot,失败时 restore 父节点 snapshot。注意:多个 snapshot 同时存在,restore 一个不影响其他(只要顺序对)。

提示:arena save/restore 是 O(1),所以可以激进保存——每个 AI 决策点都 save。

## 8 · Rust / Arch 落地代码

完整可跑的 save/restore demo:

```rust
// Cargo.toml: 无依赖
// src/main.rs

use std::cell::{Cell, UnsafeCell};
use std::ptr::NonNull;

const DEFAULT_BLOCK_SIZE: usize = 1 << 20;

struct Block {
    base: NonNull<u8>,
    size: usize,
    used: Cell<usize>,
    prev: Option<Box<Block>>,
}

impl Block {
    fn new(size: usize, prev: Option<Box<Block>>) -> Box<Self> {
        let layout = std::alloc::Layout::from_size_align(size, 16).unwrap();
        let ptr = unsafe { std::alloc::alloc(layout) };
        let base = NonNull::new(ptr).expect("OOM");
        Box::new(Block { base, size, used: Cell::new(0), prev })
    }
}

impl Drop for Block {
    fn drop(&mut self) {
        let layout = std::alloc::Layout::from_size_align(self.size, 16).unwrap();
        unsafe { std::alloc::dealloc(self.base.as_ptr(), layout) }
    }
}

pub struct Arena {
    current: UnsafeCell<NonNull<Block>>,
    temp_count: Cell<usize>,
}

pub struct Snapshot<'a> {
    arena: &'a Arena,
    saved_block: NonNull<Block>,
    saved_used: usize,
}

impl Arena {
    pub fn new(initial: usize) -> Self {
        let size = initial.max(DEFAULT_BLOCK_SIZE);
        let block = Block::new(size, None);
        Self {
            current: UnsafeCell::new(NonNull::from(Box::leak(block))),
            temp_count: Cell::new(0),
        }
    }

    pub fn alloc_bytes(&self, n: usize, align: usize) -> NonNull<u8> {
        let block = unsafe { &**self.current.get() };
        let base_addr = block.base.as_ptr() as usize;
        let used = block.used.get();
        let aligned = (base_addr + used + align - 1) & !(align - 1);
        let new_used = aligned + n - base_addr;
        if new_used > block.size {
            let new_size = n.max(DEFAULT_BLOCK_SIZE);
            unsafe {
                let cur = *self.current.get();
                let old_box = Box::from_raw(cur.as_ptr());
                let new_block = Block::new(new_size, Some(old_box));
                *self.current.get() = NonNull::from(Box::leak(new_block));
            }
            let block = unsafe { &**self.current.get() };
            block.used.set(n);
            return block.base;
        }
        block.used.set(new_used);
        unsafe { NonNull::new_unchecked(aligned as *mut u8) }
    }

    pub fn save(&self) -> Snapshot<'_> {
        let block = unsafe { **self.current.get() };
        Snapshot {
            arena: self,
            saved_block: block,
            saved_used: unsafe { block.as_ref().used.get() },
        }
    }

    pub fn restore(&self, snap: Snapshot<'_>) {
        assert!(std::ptr::eq(snap.arena, self));
        unsafe {
            *self.current.get() = snap.saved_block;
            (*snap.saved_block.as_ptr()).used.set(snap.saved_used);
        }
    }

    pub fn current_used(&self) -> usize {
        unsafe { (**self.current.get()).used.get() }
    }
}

impl Drop for Arena {
    fn drop(&mut self) {
        unsafe { drop(Box::from_raw((*self.current.get()).as_ptr())) }
    }
}

// 一个简单的撤销栈
struct UndoStack<'a> {
    arena: &'a Arena,
    stack: Vec<Snapshot<'a>>,
}

impl<'a> UndoStack<'a> {
    fn new(arena: &'a Arena) -> Self {
        Self { arena, stack: vec![] }
    }

    fn checkpoint(&mut self) {
        self.stack.push(self.arena.save());
    }

    fn undo(&mut self) -> bool {
        if let Some(snap) = self.stack.pop() {
            self.arena.restore(snap);
            true
        } else {
            false
        }
    }
}

fn main() {
    let arena = Arena::new(1 << 16);
    let mut undo = UndoStack::new(&arena);

    println!("Initial used: {} bytes", arena.current_used());

    undo.checkpoint();  // snapshot #0
    for _ in 0..1000 {
        let _ = unsafe { arena.alloc_bytes(64, 8) };
    }
    println!("After edit 1: {} bytes", arena.current_used());

    undo.checkpoint();  // snapshot #1
    for _ in 0..500 {
        let _ = unsafe { arena.alloc_bytes(128, 8) };
    }
    println!("After edit 2: {} bytes", arena.current_used());

    // 撤销 edit 2
    undo.undo();
    println!("After undo 1: {} bytes", arena.current_used());

    // 撤销 edit 1
    undo.undo();
    println!("After undo 2: {} bytes", arena.current_used());

    // 没有更多历史
    assert!(!undo.undo());
    println!("No more undo");
}
```

**预期输出**:

```
Initial used: 0 bytes
After edit 1: 64000 bytes
After edit 2: 128000 bytes
After undo 1: 64000 bytes
After undo 2: 0 bytes
No more undo
```
