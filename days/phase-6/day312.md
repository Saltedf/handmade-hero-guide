# Day 312 · 跨实体手动排序

> 昨天 Casey 给 entity 加了 `SortKey` 字段,但只能"自己和自己比"——同一个 entity 内部的 sprite。今天把 SortKey 推广到**跨实体**:让 entity A 的"头"能排在 entity B 的"身体"前面,这是多人游戏里"我挡住你"的核心机制。

## 0 · 为什么要有这一天

昨天的 SortKey 解决了"单个 entity 内部的特殊排序"——吊灯永远在玩家头上,书永远压在杯子下面。但有一种情况它处理不了:**两个不同 entity 之间的精细排序**。

具体场景:你在做一个俯视角 RPG。玩家站着,前面是一个矮箱子,后面是一面墙。三者的 Y 坐标:玩家 Y=0,箱子 Y=10,墙 Y=20。按 Y 自动排序,玩家最远(先画),箱子中间,墙最近(后画)——但箱子**只到玩家腰部**,玩家**只到墙腰**。正确的视觉应该是:箱子的下半部分被玩家挡住、玩家的下半部分被墙挡住。但画家算法不支持"半个 entity 挡半个 entity"。

业界的标准解法是 **sprite 拆分**——把玩家拆成"腿"和"上半身"两个 sprite,把箱子也拆成"下半"和"上半"。然后排序时不是按 entity 整体,而是按 sprite 单独排:

- 玩家的腿(脚部)
- 箱子的下半
- 玩家的上半身
- 箱子的上半
- 墙的下半
- 墙的上半

这样玩家的腿挡住箱子下半,箱子下半挡住玩家上半身,以此类推——视觉上"互相穿插"的效果就出来了。今天的"跨实体手动排序"就是为这种 sprite 级排序做铺垫。

更深的动机:**SortKey 必须是全局唯一的**。如果两个 entity 各自独立计算 SortKey,可能撞键——比如玩家和箱子的"上半"都用了 SortKey=42,排序时谁先谁后不确定。Casey 今天的设计是:**全局 SortKey 空间**,所有 entity 的所有 sprite 在同一个 uint32 比较空间里。每个 sprite 用一个唯一 SortKey(或编码方式),保证排序结果确定。

心理锚点:今天之后你的渲染器支持"精灵级排序"——同一个 entity 的脚、身、头能分别和其他 entity 的部分交错。这是 2.5D 游戏(用 2D sprite 模拟 3D 遮挡)的基础。Casey 在 Day 313-314 会真正实现 sprite 拆分,今天先做"全局 SortKey 空间"的基础设施。

## 1 · Casey 今天做了什么(HH 脉络)

Casey 今天打开 `handmade_render.cpp`,处理一个昨天 SortKey 留下的 bug:**两个 entity 如果都用了 `Some(sort_key)`,可能出现同一个 key,导致闪烁**。

具体动作:

1. 把 `PushBitmap` 的签名再次扩展,SortKey 参数从 `Option<uint32>` 变成 `uint32`(不再可选,默认值由调用方传)
2. 引入一个"全局 SortKey 分配器"——给每个 entity 算出一个基础 key,然后用"sprite 局部偏移"区分同一 entity 的不同 sprite
3. 修改 sim region 内的 entity 遍历:不再按 entity 排序,而是按 sprite 排序(每个 entity 可能 push 多个 bitmap)

关键决策:**SortKey 永远是 `uint32`,不是 `Option`**。原因:`Option<u32>` 在 Rust 里是 8 字节(带判别位),`u32` 是 4 字节——内存翻倍。在渲染热路径上(每帧几万次 push),内存开销累积。另外,统一类型让"比较函数"更简单(不用 match)。代价是调用方要记住"什么值表示自动"——Casey 选了 `0` 作为"自动"哨兵(因为 entity 默认 SortKey=0,等价于"我没设置")。

另一个关键决策:**SortKey 在 push bitmap 时就计算好,不是渲染时算**。也就是说,调用 `PushBitmap(group, bitmap, sort_key, ...)` 时 sort_key 是最终值,渲染器内部不再做编码转换。这让"调试时看到的 SortKey"和"实际排序用的 key"一致,排查 bug 方便。代价是调用方需要懂 SortKey 编码规则—— Casey 在 `handmade_render.h` 写了详细注释。

Casey 在视频里特别强调一个设计原则:**SortKey 是渲染器的"内部细节",不应该泄漏到 entity 逻辑层**。也就是说,游戏逻辑代码(移动、AI、碰撞)永远不碰 SortKey,只有"绘制代码"(`PushBitmap` 调用)才碰。这种"逻辑 / 渲染分离"是 Casey 从 Phase 1 就贯彻的设计哲学。

## 2 · 心智模型

### 类比:图书馆书架

想象图书馆的书架。每本书有两个属性:**类别(小说/教材/杂志)**和**位置(架子第几层第几本)**。默认按类别排(小说一区、教材二区),同类别内按位置排。这就是昨天的"entity 内部 SortKey"。

今天的新需求:有人想看"跨类别"的排序——比如"所有红色的书排一起",不管它是小说还是教材。这就需要一个**全局统一的位置编码**,让所有书在同一个数字空间里。

具体实现:把书的位置编码成 `(类别 * 1000000) + 架子位置`,所有书的位置都是唯一 uint32。然后排序就退化成"按这个数字排",跨类别自动正确。

### 严谨原理:全局 SortKey 空间

把所有"需要画的东西"放在同一个比较空间。假设有 N 个 entity,每个 entity 可能 push 多个 bitmap。我们希望:

1. 每个 bitmap 有一个唯一 SortKey(或在自动空间里按 (Y, Index) 编码)
2. 跨 entity 的 bitmap 在同一个 uint32 比较空间
3. 同一 entity 的多个 bitmap(脚、身、头)按它们的局部顺序排

Casey 的方案:

```
SortKey = (entity_global_y << 16) | sprite_local_index
```

- 高 16 bit:`entity_global_y` 编码后的值(0 到 65535),决定 entity 之间的相对位置
- 低 16 bit:`sprite_local_index`(0=脚,1=身,2=头),决定同一 entity 内 sprite 的相对位置

这样两个 entity 的"身体"会按 entity_global_y 比较,而同一 entity 的"脚和身"按 sprite_local_index 比较。一个 uint32 同时表达两层信息。

### 关键技巧:为什么把 Y 放高位

考虑两个 entity:玩家(Y=10)和墙(Y=20)。它们的 sprite 都有 0/1/2(脚/身/头)。如果 Y 放高位:

```
玩家脚: key = (10 << 16) | 0 = 655360
玩家身: key = (10 << 16) | 1 = 655361
玩家头: key = (10 << 16) | 2 = 655362
墙脚:   key = (20 << 16) | 0 = 1310720
墙身:   key = (20 << 16) | 1 = 1310721
墙头:   key = (20 << 16) | 2 = 1310722
```

排序后:`玩家脚 < 玩家身 < 玩家头 < 墙脚 < 墙身 < 墙头`。即"玩家整体先画,墙整体后画"。

如果 Y 放低位:

```
玩家脚: key = (0 << 16) | 10 = 10
玩家身: key = (1 << 16) | 10 = 65546
玩家头: key = (2 << 16) | 10 = 131082
墙脚:   key = (0 << 16) | 20 = 20
墙身:   key = (1 << 16) | 20 = 65556
墙头:   key = (2 << 16) | 20 = 131092
```

排序后:`玩家脚(10) < 墙脚(20) < 玩家身(65546) < 墙身(65556) < ...`。即"脚先画,身再画"——但跨 entity 的脚一起画,这不是我们想要的(玩家的脚应该在墙的脚前面,因为玩家 Y 小)。

所以 **Y 放高位是正确选择**——保证"先 entity 后 sprite 局部"的层次结构。

### 跨实体碰撞的特殊处理

现在考虑"互相穿插"——玩家 Y=10,箱子 Y=15。我们希望玩家的脚在箱子脚下,但玩家的身体在箱子顶部之上。这就需要"打破"Y 优先规则——把玩家拆成"脚(Y_eff=10)"和"身(Y_eff=20,人为推后)"两个 sprite。

具体说,给玩家身体的 sprite 传一个手动 SortKey,把它的 Y 编码部分加 10(相当于"伪装"它的 Y 是 20),它就排在箱子(Y=15)后面了。这就是"跨实体手动排序"——同一个 entity 的不同 sprite 可以人为调整 Y 编码,达到穿插效果。

### Rust 数据结构

```rust
struct RenderEntry {
    bitmap: BitmapId,        // 画哪张图
    sort_key: u32,           // 全局 SortKey
    world_pos: Vec2,         // 屏幕位置
    // ... 颜色、缩放等
}

struct RenderGroup {
    entries: Vec<RenderEntry>,  // 所有要画的 entries
}

impl RenderGroup {
    fn push_bitmap(&mut self, bitmap: BitmapId, sort_key: u32, pos: Vec2) {
        self.entries.push(RenderEntry { bitmap, sort_key, world_pos: pos });
    }
    fn render(&mut self) {
        // 排序:小 key 先画(画家算法)
        self.entries.sort_by_key(|e| e.sort_key);
        for entry in &self.entries {
            draw_bitmap(entry.bitmap, entry.world_pos);
        }
    }
}
```

注意 `entries: Vec<RenderEntry>` 不分 entity——所有 entity 的所有 sprite 混在一起,统一 sort。这就是"全局 SortKey 空间"的实现。

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

主流 2D 游戏的"跨实体排序"实现:

- **Stardew Valley**(C#):每个 sprite 有 `drawAboveFrontLayer` 标志,分两层画。简单但灵活度低。
- **Dead Cells**(自定义 C#):基于"骨骼动画 + 动态 Z"——每个骨骼部件单独有 Z 值,完全跨 entity 排序。和今天 Casey 的方案最接近。
- **Hollow Knight**(Unity):用 Unity 的 SortingLayer + OrderInLayer,每个 sprite 是独立 GameObject,跨 Layer 排序。
- **Risk of Rain 2**(3D):用 GPU Z-buffer,根本不做 sprite 排序。

游戏行业共识:**2D/2.5D 游戏必须有自己的 sprite 排序系统,不能依赖引擎默认**。原因:引擎默认(Unity/Godot)的排序粒度是 GameObject,但游戏里的"互相穿插"需求是 sprite 级别,GameObject 太粗。

跨实体排序的另一个坑:**动画系统**。如果玩家的"脚"sprite 在动画切换时 Y 偏移变(比如跑步动画脚抬高),排序就会跳变,看起来"穿模"。解决:动画 Y 偏移不能影响 SortKey,只影响渲染位置。Casey 在 Day 041 教过这个分离。

### 3.2 · 🎨 图形学视角

图形学里"sprite 拆分"对应的概念是 **billboard decomposition**(广告牌分解)——把一个 3D 物体拆成多个 2D billboard(sprite),每个 billboard 独立排序。这种技术广泛用于:

- **植被渲染**(树/草):树干一个 billboard,树叶多个,避免树叶和远处物体穿插
- **粒子系统**:每个粒子是一个独立 billboard,SortKey 决定粒子之间和粒子 vs 物体的排序
- **粒子级 OIT**(Order-Independent Transparency):半透明粒子不排序,用 per-pixel linked list 实现 OIT,Day 381 Casey 会讲

图形学经典算法 **Newell's algorithm** 是"画家算法的强化版"——专门处理 polygon 互相穿插。它检测两个 polygon 是否穿插,如果穿插就拆分其中一个。Casey 没用 Newell,因为 2D sprite 拆分由美术手动做(把玩家拆成"脚/身/头"),而不是算法自动拆。

### 3.3 · 🐧 Linux 系统编程视角

Linux 内核里"跨实体排序"对应的概念是 **scheduler priority**(调度器优先级):

- CFS(Completely Fair Scheduler,默认调度器):按 vruntime 排序(类似 entity 按 Y 排)
- RT(Real-Time)调度器:按 priority 排序(类似 entity 按 SortKey 排),0-99 优先级,数值大先跑
- `nice` 值(-20 到 +19):普通进程的"软优先级",和 SortKey 思路一致——默认 0,可以人工调

内核里的"per-process SortKey"叫 `task_struct->prio`,它是动态计算的——RT 进程用 RT priority,普通进程用 `nice + 120` 转换。这就是"全局统一优先级空间",和今天 SortKey 设计完全一致。

### 3.4 · 🦀 Rust 生态视角

Rust 表达"全局 SortKey 空间"的最佳模式:

```rust
/// Newtype 包一层,编译期防混淆
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
struct SortKey(u32);

impl SortKey {
    /// 从 (Y, sprite_index) 编码
    fn encode(y_enc: u16, sprite_idx: u16) -> Self {
        // 高 16 bit Y,低 16 bit sprite_idx
        SortKey(((y_enc as u32) << 16) | (sprite_idx as u32))
    }
    
    /// 强制最前/最后
    const FRONT: Self = SortKey(u32::MAX);
    const BACK: Self = SortKey(0);
}

// 排序时直接用
entries.sort_by_key(|e| e.sort_key);
```

`newtype` + derive `Ord` 是 Rust 标准模式,编译后零开销。注意 `Ord` 要求类型实现 `Eq + PartialOrd`,而 `u32` 都满足,所以可以直接 derive。

如果想要更类型安全,可以用 `enum`:

```rust
enum SortKey {
    Auto { y_enc: u16, sprite_idx: u16 },
    Manual(u32),
}

impl SortKey {
    fn as_u32(&self) -> u32 {
        match self {
            Self::Auto { y_enc, sprite_idx } => 
                ((*y_enc as u32) << 16) | (*sprite_idx as u32),
            Self::Manual(k) => *k,
        }
    }
}
```

这种 `enum` 版本更明确表达"两种模式",但每次排序都要 `as_u32()`,有微小开销。Casey 选的是简单版(直接 u32),Rust 翻译看你偏好。

## 5 · 对照与变奏

### 历史演化

- **1980s 单 sprite 时代**:每个 entity 一张图,排序简单(按 Y)。
- **1990s 多 sprite 角色**:格斗游戏把角色拆"上段/下段",支持"勾拳挡住头"。SNK 的 KOF 系列代表。
- **2000s bone animation**:骨骼动画普及,sprite 概念退化(被 mesh 取代)。但 2D 游戏仍用 sprite。
- **2010s sprite + light**:Dead Cells / Ori 等用"sprite + 实时光照",需要 sprite 级 SortKey 配合法线贴图光照。
- **2020s GPU-driven**:越来越多 2D 游戏用 GPU 渲染,sprite 排序移到 shader,但 CPU 端的 SortKey 设计不变。

### 工业级 vs 教学版

| 特性 | 教学版(今天) | 工业版(Dead Cells) |
|---|---|---|
| SortKey 类型 | uint32 | uint64(更精细) |
| 编码层 | 2 层(Y, sprite) | 4 层(Layer, Y, Bone, sprite) |
| 排序算法 | std sort | radix sort(O(N)) |
| 跨 entity 优化 | 无 | 共享 SortKey 段 |
| 编辑器集成 | hot-reload 字段 | Unity Inspector |

工业级用 **radix sort** 替代比较排序——uint32 key 的 radix sort 是 O(N),比 qsort 的 O(N log N) 快很多。Casey 没用 radix sort,因为 HH 项目 entity 数量(几千个)用 std sort 完全够快(微秒级)。但在万人 MMO 场景下,radix sort 是必须的。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 SortKey 的"Y 部分"放在 uint32 的高位,而不是低位?如果把 Y 放低位会发生什么问题?

**参考解答**:高位放 Y 保证"先按 entity 整体排,再按 sprite 局部排"的层次。如果 Y 放低位,不同 entity 的同 sprite_idx 会聚在一起(所有"脚"sprite 一起画),但跨 entity 的"玩家脚在墙脚前面"会失效——因为它们的 sprite_idx 都是 0,高位 Y 没参与比较。

更准确说:**SortKey 高位决定粗粒度排序,低位决定细粒度排序**。我们希望"entity 之间"是粗粒度,"entity 内 sprite"是细粒度,所以 Y(决定 entity)放高位,sprite_idx 放低位。

### Lv2 · 动手实践

**题**:在 Rust 里实现一个跨实体 sprite 排序系统,要求:

- `Entity` 有 `y: f32` 和多个 `Sprite`(每个有 `local_offset: i32`)
- 把每个 sprite 编码成全局 SortKey:`((y_encoded) << 16) | (local_offset as u16)`
- 所有 entity 的所有 sprite 收集到一个 `Vec<RenderEntry>`,排序后输出
- 测试:3 个 entity,每个有 2 个 sprite,验证排序后 sprite 跨 entity 交错

**参考解答**:

```rust
#[derive(Debug, Clone, Copy)]
struct Sprite {
    local_offset: u16,  // 同 entity 内的 sprite 序号
    name: &'static str,
}

#[derive(Debug, Clone)]
struct Entity {
    y: f32,
    sprites: Vec<Sprite>,
}

#[derive(Debug, Clone, Copy)]
struct RenderEntry {
    sort_key: u32,
    entity_y: f32,
    sprite_name: &'static str,
}

fn encode_sort_key(y: f32, sprite_offset: u16) -> u32 {
    // 把 y ∈ [-500, 500] 映射到 [0, 65535]
    let y_enc = ((y + 500.0).max(0.0).min(1000.0) / 1000.0 * 65535.0) as u16;
    ((y_enc as u32) << 16) | (sprite_offset as u32)
}

fn collect_entries(entities: &[Entity]) -> Vec<RenderEntry> {
    let mut entries = Vec::new();
    for e in entities {
        for s in &e.sprites {
            entries.push(RenderEntry {
                sort_key: encode_sort_key(e.y, s.local_offset),
                entity_y: e.y,
                sprite_name: s.name,
            });
        }
    }
    entries
}

fn main() {
    let ents = vec![
        Entity { y: 0.0, sprites: vec![
            Sprite { local_offset: 0, name: "P-feet" },
            Sprite { local_offset: 1, name: "P-body" },
        ]},
        Entity { y: 50.0, sprites: vec![
            Sprite { local_offset: 0, name: "B-feet" },
            Sprite { local_offset: 1, name: "B-body" },
        ]},
        Entity { y: 100.0, sprites: vec![
            Sprite { local_offset: 0, name: "W-feet" },
            Sprite { local_offset: 1, name: "W-body" },
        ]},
    ];
    let mut entries = collect_entries(&ents);
    entries.sort_by_key(|e| e.sort_key);
    println!("--- Cross-entity sprite order ---");
    for e in &entries {
        println!("key={:#010x} y={:6.1} sprite={}",
                 e.sort_key, e.entity_y, e.sprite_name);
    }
}
```

预期输出顺序:`P-feet → P-body → B-feet → B-body → W-feet → W-body`。注意"跨实体交错"——P-body 在 B-feet 前面,因为 P 的 Y < B 的 Y,而 Y 在高位主导。

### Lv3 · 迁移设计

**题**:你的 UI 系统也要排序——窗口、按钮、tooltip 各有 z 层。设计一个 UI 元素排序系统,要求:

- 同一窗口的子元素(button、label)排在父窗口之后
- 多个窗口之间按用户点击顺序排(最近点击的在前)
- tooltip 始终最前

提示:借鉴今天的"高位粗粒度 + 低位细粒度"。窗口排序用"点击时间戳"作为高位,子元素用"层级深度"作为低位。tooltip 用哨兵值。

**提示方向**:

- z_layer 占最高 4 bit(0=背景,1=普通窗口,2=dialog,3=tooltip)
- 窗口点击顺序 timestamp 占中 20 bit
- 子元素 tree depth 占低 8 bit
- 参考 React 的 z-index 体系或 Tailwind 的 z-0/z-50 分层

## 8 · Rust / Arch 落地代码

### Rust:跨实体 sprite 排序系统(完整可跑)

```rust
// Cargo.toml: 无依赖
// src/main.rs

/// 全局 SortKey,用 newtype 包一层防误用
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
struct SortKey(u32);

impl SortKey {
    /// 从 Y 坐标 + sprite 局部偏移编码
    /// Y 范围 [-500, 500] → [0, 65535]
    /// sprite_offset 范围 [0, 65535]
    fn from_y_and_sprite(y: f32, sprite_offset: u16) -> Self {
        let y_clamped = y.clamp(-500.0, 500.0);
        let y_enc = ((y_clamped + 500.0) / 1000.0 * 65535.0) as u16;
        SortKey(((y_enc as u32) << 16) | (sprite_offset as u32))
    }
    
    /// 强制最前 / 最后(哨兵值)
    const FRONT: Self = SortKey(u32::MAX);
    const BACK: Self = SortKey(0);
}

/// Sprite 元数据
#[derive(Debug, Clone)]
struct Sprite {
    name: &'static str,
    local_offset: u16,    // 同 entity 内的局部序号
}

/// Entity
#[derive(Debug, Clone)]
struct Entity {
    y: f32,
    sprites: Vec<Sprite>,
    /// 强制 SortKey:None 表示用自动编码,Some 表示手动
    manual_sort_key: Option<SortKey>,
}

/// 渲染条目:每个 sprite 一条
#[derive(Debug, Clone)]
struct RenderEntry {
    sort_key: SortKey,
    entity_idx: usize,
    sprite_name: &'static str,
    pos_y: f32,
}

struct RenderGroup {
    entries: Vec<RenderEntry>,
}

impl RenderGroup {
    fn new() -> Self { Self { entries: Vec::new() } }
    
    /// 从 entity 列表收集所有 sprite,计算 SortKey
    fn collect_from(&mut self, entities: &[Entity]) {
        for (idx, e) in entities.iter().enumerate() {
            for sprite in &e.sprites {
                let key = match e.manual_sort_key {
                    // 手动键:直接用(忽略 sprite_offset,如果需要可以叠加)
                    Some(k) => SortKey(k.0.wrapping_add(sprite.local_offset as u32)),
                    // 自动键:Y + sprite_offset 编码
                    None => SortKey::from_y_and_sprite(e.y, sprite.local_offset),
                };
                self.entries.push(RenderEntry {
                    sort_key: key,
                    entity_idx: idx,
                    sprite_name: sprite.name,
                    pos_y: e.y,
                });
            }
        }
    }
    
    /// 排序并"画"(用打印模拟)
    fn render(&mut self) {
        // 稳定排序:同 key 保持 push 顺序,防闪烁
        self.entries.sort_by_key(|e| e.sort_key);
        println!("=== Cross-entity render order ===");
        for (drawn, e) in self.entries.iter().enumerate() {
            println!("[{}] entity={} y={:6.1} sprite={} key={:#010x}",
                     drawn, e.entity_idx, e.pos_y, e.sprite_name, e.sort_key.0);
        }
    }
}

fn main() {
    let entities = vec![
        Entity {
            y: 0.0,
            sprites: vec![
                Sprite { name: "P-feet", local_offset: 0 },
                Sprite { name: "P-body", local_offset: 1 },
            ],
            manual_sort_key: None,
        },
        Entity {
            y: 50.0,
            sprites: vec![
                Sprite { name: "B-feet", local_offset: 0 },
                Sprite { name: "B-body", local_offset: 1 },
            ],
            manual_sort_key: None,
        },
        // 特效 entity:强制最前(爆炸在所有东西上面)
        Entity {
            y: -999.0,
            sprites: vec![
                Sprite { name: "Explosion", local_offset: 0 },
            ],
            manual_sort_key: Some(SortKey::FRONT),
        },
    ];
    
    let mut group = RenderGroup::new();
    group.collect_from(&entities);
    group.render();
}
```

**预期输出**:

```
=== Cross-entity render order ===
[0] entity=0 y=   0.0 sprite=P-feet key=0x80000000
[1] entity=0 y=   0.0 sprite=P-body key=0x80000001
[2] entity=1 y=  50.0 sprite=B-feet key=0x9d700000
[3] entity=1 y=  50.0 sprite=B-body key=0x9d700001
[4] entity=2 y=-999.0 sprite=Explosion key=0xffffffff
```

解读:Y=0 编码成 `0x8000`(中点),Y=50 编码成 `0x9d70`(略高于中点)。所以 P-feet < P-body < B-feet < B-body。Explosion 用 FRONT 哨兵(u32::MAX),永远最后画。

**Troubleshooting**:

- **SortKey 编码后排序反了** — 检查 Y 映射方向。今天 Y 越大越后画(越大越靠观察者),所以 Y 映射后应该越大
- **同 entity 的 sprite 顺序错** — 检查 `local_offset` 是否递增,SortKey 编码是否把 sprite_offset 放低位
- **`Option<SortKey>` 内存翻倍** — 实测 `Option<SortKey>` 是 8 字节,`SortKey` 是 4 字节。如果性能瓶颈在这里,改成 `SortKey(0)` 表示自动
