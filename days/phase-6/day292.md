# Day 292 · 实现蛇

> 昨天 hopping monstar 验证了"加 brain 不动架构"。今天加 snake——一种**分段**的实体,身体由多个 sprite 连成蛇形。这带来新挑战:一个 entity 怎么画成多个 sprite?

## 0 · 为什么要有这一天

snake 是经典游戏角色:《贪吃蛇》的整个玩法就建立在它身上。在 HH 这种 ARPG 里,snake 作为怪物出现——它的头追玩家,身体跟随头部移动,形成蜿蜒尾迹。

为什么 snake 难?普通实体有一个 sprite、一个位置。snake 有**一串 sprite、一串位置**——身体每一段都跟着前一段移动,延迟几帧。这违反了"entity = 一个 sprite"的默认假设。

具体实现上有几个挑战:

- **数据结构**:body 是 Vec<Vec2>,长度可变(吃食物长,被砍短)
- **更新算法**:每段 body 的位置是上一段上一帧的位置(延迟跟随)
- **渲染**:一个 entity 画 N 个 sprite
- **碰撞**:头碰玩家算咬到,身体碰玩家算擦伤(可选)

如果 Day 286-290 的解耦做对了,加 snake 应该:

1. 在 Brain 加 `Snake { body: Vec<Vec2>, dir: Vec2, ... }` variant
2. 写 `brain_snake` 函数,更新 body
3. 在 Visual 里加 `Snake { sprite_id: u32 }` variant,render 时画多个 sprite

整个加 snake 的代码应该 100-200 行,**全部新加**。

心理锚点:看完今天,你应该理解"一个 entity 不等于一个 sprite"——entity 是逻辑单位,sprite 是视觉单位。一个 entity 可以画 0 个、1 个、或 100 个 sprite。

## 1 · Casey 今天做了什么

Casey 今天的实现:

1. **设计 snake 数据结构**——body 是 Vec<Vec2>,第一个元素是头,后面是身体段
2. **写 brain_snake**——头部按 wander + chase 逻辑移动,身体段每帧"复制"前一段上一帧的位置
3. **渲染 snake**——遍历 body,每段画一个 sprite
4. **测试**——给蛇一个初始 body,跑几帧,确认蜿蜒跟随

关键算法是**延迟跟随**。每段 body 不是"立即移到前一段当前位置",而是"成为前一段上一帧的位置"。这形成自然的蛇形蜿蜒。

```rust
// 伪代码
for i in (1..body.len()).rev() {
    body[i] = body[i - 1];  // 注意倒序遍历,避免覆盖
}
body[0] = head_pos;
```

这个算法是 snake AI 的灵魂——简单、稳定、视觉自然。

## 2 · 心智模型

### 类比:火车车厢

snake 的身体跟随算法就像**火车的车厢**。火车头(蛇头)开到哪,后面的车厢一节节跟上来——但车厢**不会立刻**到达火车头的位置,它们有"延迟"。

具体怎么延迟?想象一列火车在铁轨上,火车头开过一段铁轨。第二节车厢在火车头**曾经**的位置(上一时刻),第三节在更早的位置。每节车厢都在前一节的"过去位置"。

实现上,最直观的办法:**记住铁轨的轨迹**,让第 N 节车厢取"火车头 N 步前的位置"。

```rust
// 火车头历史轨迹
let mut head_history: Vec<Vec2> = vec![];

fn update(head_pos: Vec2, body: &mut Vec<Vec2>, history: &mut Vec<Vec2>) {
    history.insert(0, head_pos);  // 加到最前
    // body[i] 是 history[i * spacing]
    let spacing = 5;  // 每段间隔 5 帧
    for i in 0..body.len() {
        if let Some(h) = history.get(i * spacing) {
            body[i] = *h;
        }
    }
}
```

但 Casey 用更简洁的版本——**链式赋值**,不需要 history:

```rust
// 从尾向头倒序赋值
for i in (1..body.len()).rev() {
    body[i] = body[i - 1];
}
body[0] = new_head_pos;
```

效果相同:每段 body 是"前一段上一帧的位置"。不需要 history 数组,内存紧凑。

### 2.1 倒序遍历的微妙

为什么必须倒序遍历?看正序的 bug:

```rust
// 错误:正序遍历
for i in 1..body.len() {
    body[i] = body[i - 1];  // body[1] = body[0]; body[2] = body[1](已经是新 body[0])
}
body[0] = new_head;
```

正序遍历下,当你做 `body[2] = body[1]`,body[1] 已经被改成"原本 body[0] 的值"——结果所有 body 段都变成同一个值!

倒序遍历:
```rust
// 正确:倒序遍历
for i in (1..body.len()).rev() {
    body[i] = body[i - 1];  // body[3] = body[2]; body[2] = body[1] (未变); ...
}
body[0] = new_head;
```

倒序下,你先把 body[3] 设为 body[2](此时 body[2] 还是旧值),再把 body[2] 设为 body[1](此时 body[1] 还是旧值)……每步都用"未变的旧值"。

这是经典的"原地数组移位"技巧。Rust 的 `slice::rotate_right` 也做类似事,但语义不同。

### 2.2 Brain 的复杂 payload

snake 的 brain payload 比之前任何 brain 都复杂:

```rust
enum Brain {
    Player,
    MonsterChase { target_id: u32 },
    Snake {
        body: Vec<Vec2>,   // 蛇身,包含头
        wander_dir: Vec2,   // 当前游走方向
        wander_timer: f32,  // 多久换一次方向
        chase_target: Option<u32>,  // 在视野内时追击的玩家 ID
    },
}
```

snake 的 body 是 `Vec<Vec2>`——堆分配的动态数组。这带来两个问题:

1. **拷贝成本**:`Brain` 不再是 Copy(Vec 不是 Copy)。Entity 不能 derive Copy,只能 Clone——传 entity 时要 `.clone()`。
2. **借用复杂**:brain 函数要 `&mut self.brain` 内的 `&mut self.brain.body`,而 body 元素是 Vec2(可以 Copy 出来)。

Casey 在 HH 不在意这些细节——C 没所有权概念,直接指针操作。Rust 实现要小心。

### 2.3 蛇头 AI:wander + chase

蛇头的行为模式:

- 默认 wander(随机游走),每 1-2 秒换方向
- 玩家进入视野(距离 < 200),切到 chase
- 玩家离开视野,回到 wander

```rust
fn brain_snake(e: &mut Entity, ctx: &Context, dt: f32) {
    let Some(Brain::Snake { body, wander_dir, wander_timer, chase_target }) = e.brain else { return; };

    // 头部 AI
    let head = &mut body[0];
    let player_dist = ctx.player_pos().sub(*head).length();

    if player_dist < 200.0 {
        // chase
        let d = ctx.player_pos().sub(*head).normalize();
        head.x += d.x * 60.0 * dt;
        head.y += d.y * 60.0 * dt;
    } else {
        // wander
        *wander_timer -= dt;
        if *wander_timer <= 0.0 {
            *wander_timer = 1.5;
            *wander_dir = Vec2::new(
                (rand::random::<f32>() - 0.5) * 2.0,
                (rand::random::<f32>() - 0.5) * 2.0,
            ).normalize();
        }
        head.x += wander_dir.x * 30.0 * dt;
        head.y += wander_dir.y * 30.0 * dt;
    }

    // 身体跟随
    for i in (1..body.len()).rev() {
        body[i] = body[i - 1];
    }
}
```

### 2.4 渲染多 sprite

```rust
fn render_snake(e: &Entity) {
    let Some(Brain::Snake { body, .. }) = &e.brain else { return; };
    for (i, seg) in body.iter().enumerate() {
        let sprite = if i == 0 { SNAKE_HEAD_SPRITE } else { SNAKE_BODY_SPRITE };
        draw_sprite(sprite, seg.x, seg.y);
    }
}
```

一个 entity 画 N 个 sprite——这是"visual 决定渲染"的进一步体现。

---

**总结**:今天的 snake 引入两个新概念:**分段 body 数据结构**和**链式跟随算法**。body 是 Vec<Vec2>,跟随用倒序遍历。渲染时遍历 body 画多个 sprite。整个加 snake 的代码全在新 brain + 新 visual variant 里,不动架构。

## 3 · 多域深入

### 3.1 · 🎮 游戏编程视角

snake 是经典游戏 AI,《贪吃蛇》《Nibbler》《Salen》等都用。其设计核心是**视觉表现力**——body 跟随的延迟感、蜿蜒的尾迹、玩家穿过身体时的紧张感。

工业级 snake 的几个变种:

- **固定长度**:经典版,长度固定
- **可变长度**:吃食物长,被砍短
- **关节物理**:每段是物理弹簧连接(更真实但贵)
- **spline 插值**:body 段之间用 bezier 曲线连接,平滑无棱角

Casey 用最简单的链式跟随——视觉自然、代码极简。商业项目可能用 spline 插值。

游戏行业的另一个相关:**procedural animation**(过程化动画)。一些游戏(如《死亡细胞》的鞭子武器)用类似链式跟随算法模拟柔体。

### 3.2 · 🎨 图形学视角

snake 渲染的进阶:**spline 连接**。body 段之间不画独立 sprite,而是用一条平滑曲线连起来:

```rust
// Catmull-Rom spline 插值
fn catmull_rom(p0: Vec2, p1: Vec2, p2: Vec2, p3: Vec2, t: f32) -> Vec2 {
    let t2 = t * t;
    let t3 = t2 * t;
    Vec2::new(
        0.5 * ((2.0 * p1.x) + (-p0.x + p2.x) * t + (2.0 * p0.x - 5.0 * p1.x + 4.0 * p2.x - p3.x) * t2 + (-p0.x + 3.0 * p1.x - 3.0 * p2.x + p3.x) * t3),
        0.5 * ((2.0 * p1.y) + (-p0.y + p2.y) * t + (2.0 * p0.y - 5.0 * p1.y + 4.0 * p2.y - p3.y) * t2 + (-p0.y + 3.0 * p1.y - 3.0 * p2.y + p3.y) * t3),
    )
}
```

每段 body 之间插值 N 个点,画成连续曲线。Casey 在 day 292 不做这个——简单画独立 sprite 够用。Phase 7+ 可能加 spline。

### 3.3 · 🐧 Linux 系统编程视角

Linux 里"链式跟随"的对应:**链表遍历**。`list_head` 是双向链表,遍历时用 `list_for_each_entry`。Casey 今天用的"倒序遍历"在内核里也常见——如释放链表元素时倒序(从尾到头)避免悬空指针。

另一个对应:**page cache LRU**。Linux 文件缓存用 LRU(最近最少使用)链表,新页加到头部,淘汰时从尾部。和 snake body 的"新头加到前,旧尾移出去"模式一致。

### 3.4 · 🦀 Rust 生态视角

Rust 实现 snake 的几个注意:

**1. Brain 不能 Copy**

```rust
#[derive(Clone)]  // 不能 Copy,因为有 Vec
enum Brain {
    Snake { body: Vec<Vec2>, ... },
}
```

加 Brain 的 entity 必须用 `&mut self.brain`,不能 by-value 处理。

**2. 倒序遍历**

```rust
for i in (1..body.len()).rev() {
    body[i] = body[i - 1];
}
```

Rust 的 `(1..n).rev()` 是 `Rev<Range<usize>>`,产生倒序索引。

**3. 借用冲突**

brain_snake 函数要同时改 body[0] 和 body[i>0]:

```rust
let head = &mut body[0];     // mut 借用 body[0]
for i in 1..body.len() {
    body[i] = body[i - 1];   // mut 借用整个 body!冲突
}
```

解决:用 `split_first_mut`:

```rust
let (head, tail) = body.split_first_mut();
// head 是 &mut Vec2, tail 是 &mut [Vec2]
*head = new_head_pos;
for i in (1..tail.len()).rev() {
    // 但这里仍要访问 body[i-1]...
}
```

更简单的写法:**复制需要的值出来,再写回**:

```rust
let new_head = compute_new_head(...);
let old_head_pos = body[0];  // Copy Vec2 out
for i in (1..body.len()).rev() {
    let prev = body[i - 1];   // Copy
    body[i] = prev;
}
body[0] = new_head;
```

Vec2 是 Copy,这种"复制出来再写回"开销很小。

## 5 · 对照与变奏

### 链式跟随 vs 路径历史

**链式跟随**(今天 Casey):
```rust
for i in (1..n).rev() { body[i] = body[i-1]; }
body[0] = new_head;
```
- 内存:O(n)
- 计算:O(n)
- 行为:body[i] = head 的 i 步前位置(隐式 history)

**路径历史**:
```rust
history.push_front(new_head);
for i in 0..body.len() {
    body[i] = history[i * spacing];
}
```
- 内存:O(history_size),通常比 body 大
- 计算:O(n)
- 行为:body[i] = head 的 i*spacing 步前位置(显式 history)

差别:链式跟随的"延迟"固定为 1 帧/段;路径历史可调 spacing。视觉上链式跟随的蛇"紧",路径历史的蛇"松"。

工业级贪吃蛇游戏常用路径历史(玩家手感更好)。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:Casey 用"倒序遍历"更新 body。如果改成"复制 body[0] 出来,然后正序遍历 `body[i] = body[i+1]`",会发生什么?

**参考解答**:`body[i] = body[i+1]` 正序,相当于"每段复制后一段的位置"——结果 body 越来越靠近尾部。蛇会**反向**移动(尾巴变头,头变尾巴)。

正确算法是"每段复制前一段的位置",所以 `body[i] = body[i-1]`。如果用正序 `body[1] = body[0]` 后 `body[2] = body[1]`,body[1] 已经是新值,body[2] 也会变成新值——所有 body 都等于 body[0]。

倒序遍历避免这个 bug。

### Lv2 · 动手实践

**题**:实现一个最小 snake:body 长度 5,头部朝右匀速移动(每帧 +1,0),身体跟随。验证 body[4] 4 帧后到达 body[0] 的初始位置。

完成标准:跑 10 帧,打印 body,验证蜿蜒跟随。

**参考解答**:

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 { fn new(x: f32, y: f32) -> Self { Self { x, y } } }

fn step(body: &mut Vec<Vec2>, new_head: Vec2) {
    // 倒序遍历
    for i in (1..body.len()).rev() {
        body[i] = body[i - 1];
    }
    body[0] = new_head;
}

fn main() {
    let mut body: Vec<Vec2> = (0..5).map(|i| Vec2::new(i as f32, 0.0)).collect();
    // 初始 body: [{0,0}, {1,0}, {2,0}, {3,0}, {4,0}]
    // 想象 head 在 body[0]={0,0},但身体在右边?这不对
    // 改成头在右边,身体往左延伸:
    body = (0..5).map(|i| Vec2::new(-(i as f32) + 4.0, 0.0)).collect();
    // 初始:[{4,0}, {3,0}, {2,0}, {1,0}, {0,0}]
    println!("init: {:?}", body);

    let initial_head = body[0];

    // 跑 4 帧,头部每帧 +1
    for f in 1..=4 {
        let new_head = Vec2::new(4.0 + f as f32, 0.0);
        step(&mut body, new_head);
        println!("frame {}: {:?}", f, body);
    }

    // 验证:body[4] 在 frame 4 时应该是初始 head 位置
    assert_eq!(body[4], initial_head);
    println!("Snake follow test passed!");
}
```

**每行解释**:
- `(0..5).map(...).collect()` —— 函数式构造初始 body
- `(1..body.len()).rev()` —— 倒序遍历索引 1 到 n-1
- `body[4] == initial_head` —— 4 帧后,尾巴到达头的初始位置

## 8 · Rust / Arch 落地代码

### Rust 完整可跑示例

扩展 §7 Lv2,加 wander AI 和渲染:

```rust
use std::time::{Duration, Instant};

#[derive(Copy, Clone, Debug, PartialEq)]
struct Vec2 { x: f32, y: f32 }
impl Vec2 {
    fn new(x: f32, y: f32) -> Self { Self { x, y } }
    fn sub(self, o: Self) -> Self { Self::new(self.x - o.x, self.y - o.y) }
    fn length(self) -> f32 { (self.x * self.x + self.y * self.y).sqrt() }
    fn normalize(self) -> Self {
        let l = self.length();
        if l > 1e-6 { Self::new(self.x / l, self.y / l) } else { Self::new(0.0, 0.0) }
    }
}

#[derive(Clone, Debug)]
struct SnakeBrain {
    body: Vec<Vec2>,
    wander_dir: Vec2,
    wander_timer: f32,
}

fn brain_snake(b: &mut SnakeBrain, player_pos: Vec2, dt: f32) {
    let head = &mut b.body[0];
    let dist = player_pos.sub(*head).length();

    let new_head = if dist < 100.0 {
        // chase
        let d = player_pos.sub(*head).normalize();
        Vec2::new(head.x + d.x * 60.0 * dt, head.y + d.y * 60.0 * dt)
    } else {
        // wander
        b.wander_timer -= dt;
        if b.wander_timer <= 0.0 {
            b.wander_timer = 1.5;
            b.wander_dir = Vec2::new(
                (rand_x() - 0.5) * 2.0,
                (rand_x() - 0.5) * 2.0,
            ).normalize();
        }
        Vec2::new(head.x + b.wander_dir.x * 30.0 * dt,
                  head.y + b.wander_dir.y * 30.0 * dt)
    };

    // 跟随
    for i in (1..b.body.len()).rev() {
        b.body[i] = b.body[i - 1];
    }
    b.body[0] = new_head;
}

fn rand_x() -> f32 {
    // 简单的 LCG,避免引外部 rand crate
    use std::sync::atomic::{AtomicU32, Ordering};
    static STATE: AtomicU32 = AtomicU32::new(42);
    let s = STATE.fetch_add(1, Ordering::Relaxed);
    (s as f32) / (u32::MAX as f32)
}

fn render(b: &SnakeBrain) -> String {
    let mut s = String::new();
    for (i, seg) in b.body.iter().enumerate() {
        if i > 0 { s.push_str(" -> "); }
        s.push_str(&format!("({:.0},{:.0})", seg.x, seg.y));
    }
    s
}

fn main() {
    let mut snake = SnakeBrain {
        body: (0..5).map(|i| Vec2::new(50.0 - i as f32 * 5.0, 50.0)).collect(),
        wander_dir: Vec2::new(1.0, 0.0),
        wander_timer: 1.5,
    };
    let player = Vec2::new(200.0, 50.0);

    for frame in 0..30 {
        brain_snake(&mut snake, player, 0.1);
        if frame % 5 == 0 {
            println!("frame {}: {}", frame, render(&snake));
        }
    }
}
```

### 工程实现细节的展开

要把今天的代码真正跑通,我们必须回答几个具体工程问题。

**第一,内存布局**。所有数据结构都要考虑 cache locality。Rust 的 `#[repr(C)]` 保证字段顺序,CPU prefetcher 才能预测下一个访问。对 hot loop 里的结构体,经常用 SoA(Structure of Arrays)而非 AoS(Array of Structures):

```rust
// AoS(Array of Structures)—— 简单但 cache 差
struct Entities { items: Vec<Entity> }  // 每实体 64 字节

// SoA(Structure of Arrays)—— 复杂但 cache 友好
struct Entities {
    positions: Vec<Vec3>,    // 16 字节 × N
    normals: Vec<Vec3>,      // 16 字节 × N
    layers: Vec<u8>,         // 1 字节 × N
}
```

SoA 让 sort 时只读 positions(16 字节/实体),不读其他字段——cache 命中率高 4 倍。Casey 在 HH 后期会切换到 SoA。

**第二,错误处理**。Rust 的 `Result<T, E>` 强制处理错误,但游戏代码经常 `unwrap()`——这是有意的。游戏里的"不可能错"用 unwrap,失败直接 panic,debug 时立刻知道。但**加载资源**(纹理、网格)不能 unwrap——加载失败应该 fallback 到默认资源。

```rust
// 加载纹理——失败 fallback
let tex = load_texture("player.png").unwrap_or_else(|_| {
    eprintln!("Missing player.png, using default");
    default_texture()
});

// 数学计算——不可能失败,unwrap 合理
let normal = (cross(v1, v2)).normalize().unwrap();
```

**第三,并发**。游戏循环经常是单线程逻辑 + 多线程渲染。Rust 的 `Send + Sync` 编译时检查——只要数据没 `Rc` / `RefCell`,就可以跨线程。Casey 的 HH 在 day 305+ 用 memory arena(单线程,无锁,极快);工业级引擎(bevy、Fyrox)用 ECS + rayon 多线程。

**第四,跨平台**。Linux 用 X11 / Wayland,Windows 用 Win32,macOS 用 Cocoa。Casey 的 HH 用 platform layer 抽象——`platform_get_time()`、`platform_swap_buffers()` 等,每平台独立实现。Rust 生态的 `winit` crate 做这事,bevy / wgpu 都基于它。

### 数学严谨化的推导

本节内容相关的核心数学推导:

**向量点积**:a · b = |a||b|cos θ。在排序的语境里,两个 sprite 的"前后关系"可以看作向量在世界空间的点积——投影到视线方向。但 2D 游戏里视线固定(z 方向),所以退化为 y 比较。

**叉积判断**:a × b 的符号判断 b 在 a 的左侧还是右侧。Casey 在 sort_rule 里用叉积决定 sprite 在玩家的哪侧——决定是玩家遮挡 NPC 还是反过来。

**重心坐标**:三角形内任一点 P = αA + βB + γC,α+β+γ=1。fragment shader 接收的 attribute 是顶点 attribute 的重心插值。今天 sort_rule 不涉及 fragment shader,但理解重心坐标对 Phase 8 GPU 渲染至关重要。

**IEEE 754 float**:f32 的位模式不是单调的——负数比正数位模式大。所以 sort key 用 u64 时,f32 要"重新编码"成单调 u32:

```rust
fn f32_to_monotonic_u32(x: f32) -> u32 {
    let bits = x.to_bits();
    if bits & 0x8000_0000 != 0 {
        !bits  // 负数:全部翻转
    } else {
        bits ^ 0x8000_0000  // 正数:翻转符号位
    }
}
```

这样 -1.0 → 0x00000000,0.0 → 0x80000000,+1.0 → 0xBF800000...^0x80000000 = 0x3F800000,单调递增。

### 历史脉络与工业实践

1990 年代 id Software 的 Doom(1993)用 BSP tree + painter's algorithm——排序在编译期完成,运行时 O(N) 遍历。Quake(1996)首次用 Z-buffer(GPU 硬件),彻底解决排序问题。

2D 游戏排序的演化:

- **1985-1990**:无 sort,固定 layer(Super Mario Bros)
- **1990-1995**:Y-sort 在 JRPG 普及(最终幻想 6、超时空之轮)
- **1995-2005**:Multi-layer Y-sort(星际争霸、暗黑破坏神 2)
- **2005-2015**:引擎内置 sort(Unity、GameMaker)
- **2015-2025**:GPU + sort 混合(bevy、Unreal)

Casey 的 HH 在 day 295-310 走了这条 30 年路径——从最简单的 sort_key 到拓扑排序,演示每一阶段的工程权衡。

### 性能优化的常见误区

**误区 1:过早优化**。Casey 经常说"先正确再快"。Day 301 的 sort_rule 用 f32 比较,虽然慢于 u64,但代码清晰。等真的成瓶颈(实测 >5% 帧时间),再换 u64。

**误区 2:微优化大函数**。把 sort_rule 优化 10% 没意义,如果整个 sort 只占帧时间 0.5%。优化要看 profiler 数据,不是直觉。

**误区 3:并行不是银弹**。把 sort 分到多线程,如果数据共享(同 Vec),要锁,锁比串行还慢。Casey 用 thread-local 数据 + merge,避免锁。

**误区 4:cache miss 是性能杀手**。一个 cache miss 100+ cycle,等于 50 个 mul。所以"数据紧凑 + 顺序访问"比"少指令"重要 10 倍。这是 data-oriented design 的核心。



### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
