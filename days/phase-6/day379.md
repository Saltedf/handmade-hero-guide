## 2 · 心智模型

### 类比:渲染优化像"工厂流水线优化"

想象一个汽车工厂,生产 1000 辆车。两种生产模式:

**未优化(顺序无关)**:
```
红轿车 → 蓝SUV → 红轿车 → 绿轿车 → 蓝SUV → ...
```
每辆车换色要换喷漆罐,流水线频繁切换颜色,慢。

**优化(按色分组)**:
```
红轿车 × 300 → 蓝SUV × 200 → 绿轿车 × 500
```
换喷漆罐 3 次,而不是 1000 次。整体快得多。

**渲染优化的本质相同**:把同 shader / 同材质的几何分组,连续渲染,减少"换喷漆罐"(状态切换)。

### Render Group / Batching

**Batch(批次)**:同 shader + 同 texture + 同 uniform 设置的几何,可以一次性提交。一个 batch = 一个 draw call(或一个 multi-draw)。

**Batching 的几种形式**:

1. **Static batching**:静态几何(墙体)合并成单个大 VBO,一次 draw call
2. **Dynamic batching**:小 mesh(粒子)合并到临时 VBO,一次 draw call
3. **Instancing**:同 mesh 多实例,一次 `glDrawArraysInstanced` draw call
4. **GPU-driven**(Vulkan / DX12):GPU 自己合并,几乎零 CPU 开销

**Casey 现在没做 batching**,每帧大量 draw call。Phase 7+ 优化。

### 状态切换的开销

每次 OpenGL 状态切换,CPU 端:
- API 调用本身(微秒级)
- driver validation(微秒级)
- 命令缓冲追加(纳秒级)

GPU 端:
- pipeline 重新配置(微秒级)
- texture / uniform buffer 绑定(纳秒级)

**1000 个 draw call 各切换 shader** = 1000 次 pipeline 重新配置 = 几毫秒。这可能是 144 FPS → 60 FPS 的罪魁祸首。

### Rust 视角:render queue

```rust
pub struct RenderCommand {
    shader: GLuint,
    texture: GLuint,
    vao: GLuint,
    index_count: GLsizei,
    uniforms: Vec<(String, UniformValue)>,
}

pub struct RenderQueue {
    commands: Vec<RenderCommand>,
}

impl RenderQueue {
    pub fn submit(&mut self) {
        // 1. 按 shader / texture 排序
        self.commands.sort_by_key(|c| (c.shader, c.texture));

        // 2. 顺序执行,只在必要时切换状态
        let mut cur_shader = 0;
        let mut cur_texture = 0;
        for cmd in &self.commands {
            if cmd.shader != cur_shader {
                unsafe { gl::UseProgram(cmd.shader); }
                cur_shader = cmd.shader;
            }
            if cmd.texture != cur_texture {
                unsafe { gl::BindTexture(gl::TEXTURE_2D, cmd.texture); }
                cur_texture = cmd.texture;
            }
            // 上传 uniform
            // cmd.vao bind + DrawElements
        }
    }
}
```

这是工业 render queue 的简化版。优化点:
- sort 一次,所有 draw call 排序
- 切换 shader / texture 只在必要时
- uniform 缓存(避免重复 set)

## 3 · 四域深入

### 3.1 · 🎮 游戏编程视角

工业渲染优化层级:

| 优化 | 速度提升 | 实现复杂度 |
|---|---|---|
| Reduce draw calls | 50-100x | 中 |
| Sort by shader | 2-3x | 低 |
| Sort by texture | 1.5-2x | 低 |
| Instancing | 5-10x | 中 |
| GPU culling | 2-5x | 高 |
| GPU-driven rendering | 10-100x | 极高 |

**Draw call 是 CPU/GPU 通信单位**,减少 draw call 是优化核心。每次 draw call CPU 要发命令给 GPU,driver validation,数据传输,所以 draw call 太多 = CPU 瓶颈。

**Unity / Unreal 的 batching**:
- Unity:Static Baking(静态合并)+ Dynamic Batching(动态)+ GPU Instancing
- Unreal:Mesh Decals + Hierarchical Instanced Static Mesh(HISM)

Casey 暂不做 batching,Phase 7+ 加。

### 3.2 · 🎨 图形学视角

渲染管线的瓶颈定位:

**Vertex-bound**:vertex shader 太复杂 / 顶点太多
- 症状:减少 fragment shader 复杂度没用
- 解决:LOD(降低 mesh 精度)/ 优化 vertex shader

**Fragment-bound**:fragment shader 太复杂 / 屏幕大
- 症状:降分辨率显著提速
- 解决:简化 fragment shader / 早 depth pre-pass

**Geometry-bound**:三角形太小,大量像素位于三角形边缘,rasterizer 累
- 解决:LOD(远处用低 mesh)

**Draw-call-bound**(最常见):draw call 太多,driver validation 慢
- 解决:batching / instancing / GPU-driven

**Memory-bandwidth-bound**:texture 采样太多,GPU 显存带宽不够
- 解决:压缩纹理 / 减小 texture / mipmap

定位方法:**降一半某个资源,看帧时间**。降 mesh 精度变快 → vertex-bound。降 fragment shader 复杂度变快 → fragment-bound。

## 7 · 变式训练

### Lv1 · 概念辨析

**题**:为什么 "draw call 多" 是 CPU 瓶颈而不是 GPU 瓶颈?

**参考解答**:每个 draw call CPU 要做:
1. 验证 GL 状态(参数合法?)
2. 把命令追加到命令缓冲(发给 GPU)
3. driver 内部 bookkeeping

这些都在 CPU 端,driver 通常在用户态线程做。1000 个 draw call = 1000 次上述操作,CPU 时间累积。

GPU 端,每个 draw call 的工作(实际渲染)是流水的,GPU 一边接收命令一边执行。如果 GPU 比 CPU 快,GPU 等待 CPU 命令。这时瓶颈在 CPU。

测量:用 OpenGL timer query 测 GPU 时间,用 perf 测 CPU 时间。如果 CPU 时间 >> GPU 时间,CPU-bound。

工业解决:batching / instancing 减少 draw call 数,从而减少 CPU 工作量。

### Lv2 · 动手实践

**题**:实现 `RenderQueue`,支持 sort by shader。完成标准:
- 队列里 push 多个 RenderCommand
- submit() 时按 shader_id 排序
- 只在 shader 变时调 glUseProgram
- 验证:1000 个不同 shader 的命令,排序后 useProgram 调用 = shader 数量,而不是 1000

**参考解答**:

```rust
use gl::types::*;
use std::collections::HashMap;

pub struct RenderCommand {
    pub shader: GLuint,
    pub texture: GLuint,
    pub vao: GLuint,
    pub index_count: GLsizei,
    pub uniforms: Vec<(String, UniformValue)>,
}

pub enum UniformValue {
    Mat4([f32; 16]),
    Vec3([f32; 3]),
    F32(f32),
    I32(i32),
}

pub struct RenderQueue {
    commands: Vec<RenderCommand>,
}

impl RenderQueue {
    pub fn new() -> Self {
        Self { commands: Vec::new() }
    }

    pub fn push(&mut self, cmd: RenderCommand) {
        self.commands.push(cmd);
    }

    pub fn submit(&mut self) {
        // 1. 按 shader / texture 排序
        self.commands.sort_by_key(|c| (c.shader, c.texture));

        // 2. 顺序执行,最小化状态切换
        let mut cur_shader: GLuint = 0;
        let mut cur_texture: GLuint = 0;
        let mut use_program_count = 0;

        for cmd in &self.commands {
            // Shader 切换
            if cmd.shader != cur_shader {
                unsafe { gl::UseProgram(cmd.shader); }
                cur_shader = cmd.shader;
                use_program_count += 1;
            }

            // Texture 切换
            if cmd.texture != cur_texture {
                unsafe { gl::BindTexture(gl::TEXTURE_2D, cmd.texture); }
                cur_texture = cmd.texture;
            }

            // Uniforms
            for (name, value) in &cmd.uniforms {
                let c_name = std::ffi::CString::new(name.as_str()).unwrap();
                let loc = unsafe {
                    gl::GetUniformLocation(cur_shader, c_name.as_ptr())
                };
                if loc < 0 { continue; }
                unsafe {
                    match value {
                        UniformValue::Mat4(m) => {
                            gl::UniformMatrix4fv(loc, 1, gl::FALSE, m.as_ptr());
                        }
                        UniformValue::Vec3(v) => {
                            gl::Uniform3f(loc, v[0], v[1], v[2]);
                        }
                        UniformValue::F32(f) => {
                            gl::Uniform1f(loc, *f);
                        }
                        UniformValue::I32(i) => {
                            gl::Uniform1i(loc, *i);
                        }
                    }
                }
            }

            // Draw
            unsafe {
                gl::BindVertexArray(cmd.vao);
                gl::DrawElements(
                    gl::TRIANGLES, cmd.index_count,
                    gl::UNSIGNED_INT, std::ptr::null(),
                );
            }
        }

        println!("RenderQueue: {} commands, {} useProgram calls",
            self.commands.len(), use_program_count);
        self.commands.clear();
    }
}
```

**关键解释**:
- `sort_by_key` 稳定排序,相同 shader/texture 的命令保持插入顺序
- 只在 shader 变时调 `UseProgram`(driver 最贵的状态切换之一)
- uniform 上传每个 command 都做(可优化为 per-shader 缓存)
- 测量 useProgram 调用次数,验证优化效果

### Rust:Profile + RenderQueue + Debug Overlay

```rust
// Cargo.toml: gl = "0.14", glfw = "0.55"

use gl::types::*;
use std::collections::HashMap;
use std::time::{Duration, Instant};

// FPS 计数器
pub struct FpsCounter {
    last_update: Instant,
    frame_count: u32,
    fps: f32,
}

impl FpsCounter {
    pub fn new() -> Self {
        Self {
            last_update: Instant::now(),
            frame_count: 0,
            fps: 0.0,
        }
    }

    pub fn frame(&mut self) -> f32 {
        self.frame_count += 1;
        let now = Instant::now();
        let elapsed = now - self.last_update;
        if elapsed >= Duration::from_millis(500) {
            self.fps = self.frame_count as f32 / elapsed.as_secs_f32();
            self.frame_count = 0;
            self.last_update = now;
        }
        self.fps
    }
}

// GPU timer query
pub struct GpuTimer {
    query: GLuint,
}

impl GpuTimer {
    pub fn new() -> Self {
        let mut query = 0;
        unsafe { gl::GenQueries(1, &mut query); }
        Self { query }
    }

    pub fn measure<F: FnOnce()>(&self, f: F) -> f64 {
        unsafe {
            gl::BeginQuery(gl::TIME_ELAPSED, self.query);
            f();
            gl::EndQuery(gl::TIME_ELAPSED);

            let mut done = 0;
            while done == 0 {
                gl::GetQueryObjectiv(self.query, gl::QUERY_RESULT_AVAILABLE, &mut done);
            }
            let mut time_ns: GLuint = 0;
            gl::GetQueryObjectuiv(self.query, gl::QUERY_RESULT, &mut time_ns);
            time_ns as f64 / 1e6  // 返回 ms
        }
    }
}

impl Drop for GpuTimer {
    fn drop(&mut self) {
        unsafe { gl::DeleteQueries(1, [self.query].as_ptr()); }
    }
}

    loop {
        let fps_value = fps.frame();

        // GPU timer 测渲染时间
        let gpu_time = gpu_timer.measure(|| {
            // 把 draw 命令压入 queue
            // queue.push(RenderCommand { ... });
            queue.submit();
        });

        // Debug overlay
        overlay.line(format!("FPS: {:.1}", fps_value));
        overlay.line(format!("GPU time: {:.3} ms", gpu_time));
        overlay.line(format!("RenderQueue commands: ..."));
        overlay.render();
    }
}
```

### 深度推导:本日相关数学与算法

要真正掌握今天的内容,我们必须把背后的数学推导展开。这一节是"为什么这么做"的论证。

**算法复杂度的精确分析**。今天的代码涉及到对实体集合排序,基准复杂度:

- 最优比较排序下界:O(N log N)(决策树理论)
- Rust `sort_by`:TimSort,平均 O(N log N),最好 O(N)(已部分有序时)
- 拓扑排序:O(V + E),V 是节点数,E 是边数
- Radix sort:O(N × k),k 是 sort key 位数——非比较排序,可突破 O(N log N)

对一个 1000 sprite 的场景,TimSort 大约 10000 次比较,每次比较 5-10 个 cycle(分支少),总 50000-100000 cycle = 20-40 μs。在 60 FPS(16666 μs 预算)占 0.2%——可忽略。100K sprite 时升到 2 ms,开始有压力。Minecraft 这种规模的游戏必须用 radix sort 或 GPU sort。

**内存访问模式**。sort 是**非线性内存访问**的典型——每次比较都可能跳到 Vec 不同位置。CPU prefetcher 抓不到模式,cache miss 频繁。优化:

1. **Sort by index**:先 sort indices(u32 数组,4 字节/项,cache 友好),再 reorder 数据。indices 1000 个 = 4 KB,L1 cache 装得下。
2. **Batch reorder**:indices 排好后,顺序遍历 indices,顺序访问原数据(虽然是间接但 prefetcher 跟得上)。

```rust
let mut indices: Vec<u32> = (0..entities.len() as u32).collect();
indices.sort_by(|&a, &b| sort_rule(&entities[a as usize], &entities[b as usize]));
let sorted: Vec<&Entity> = indices.iter().map(|&i| &entities[i as usize]).collect();
```

100K sprite 的 sort 用这个技巧能加速 30%。

**位运算打包 sort key**。今天 sort_key 是 u64,可以塞进多个字段:

```
bits 63-56: layer (8 bits, 256 layers)
bits 55-40: bottom_y (16 bits, 65536 levels)
bits 39-24: x (16 bits)
bits 23-8: sub_layer (16 bits)
bits 7-0: spawn_id (8 bits, 256 entries per slot)
```

打包:`key = (layer << 56) | (bottom_y << 40) | (x << 24) | (sub << 8) | spawn`。一次 u64 比较,无分支,Rust `sort_by_key` 自动 inline。

**部分序的图论模型**。Day 304 会用拓扑排序处理真正的部分序。每个 sprite 是图节点,如果 A 应该在 B 前面,加边 A→B。拓扑排序给出节点的合法顺序(满足所有约束)。

拓扑排序算法:

1. **Kahn 算法**:每次找入度为 0 的节点,加入结果,删掉它的出边,重复。
2. **DFS 后序**:DFS 遍历,记录后序(post-order),反转得到拓扑序。

如果图有环(循环依赖),拓扑排序失败——意味着 sprite 排序无解,必须**人为拆解**(切开某个 sprite)。

**浮点数的稳定性**。Rust 的 `f32::partial_cmp` 处理 NaN 返回 `None`,sort 会 panic。所以游戏代码里要么保证所有 f32 都不是 NaN(数学保证),要么 `partial_cmp(...).unwrap_or(Equal)`(默认相等)。今天 sort_rule 用后者。

更稳妥的方法:**所有位置用整数**(像素单位)。`pos_y: i32` 没有 NaN 问题,比较无分支。但缩放和旋转要用浮点,所以游戏用 i32 + f32 混合。

### 真实代码片段

Casey 在 HH 视频里实际写的代码风格(简化伪代码):

```c
internal int32
SortRule(entity *A, entity *B)
{
    int32 Result = 0;

    // Layer 比较
    if (A->Layer != B->Layer) {
        Result = (int32)A->Layer - (int32)B->Layer;
    } else {
        // Bounds overlap 检查
        rectangle2 BoundsA = GetEntityBounds(A);
        rectangle2 BoundsB = GetEntityBounds(B);
        if (RectanglesOverlap(BoundsA, BoundsB)) {
            // Bottom y 比较
            real32 BottomA = BoundsA.Max.Y;
            real32 BottomB = BoundsB.Max.Y;
            if (BottomA != BottomB) {
                Result = (BottomA < BottomB) ? -1 : 1;
            } else {
                // x 比较
                Result = SignOf32(A->P.X - B->P.X);
            }
        } else {
            // 不重叠:任意顺序
            Result = A->SpawnID - B->SpawnID;
        }
    }

    return Result;
}
```

注意 Casey 的 C 风格:

- 直接返回 int32(而非 enum Ordering)
- 用 `SignOf32`(返回 -1/0/1)简化比较
- if-else 链而非 Rust 的 `then_with`

Rust 等价:

```rust
fn sort_rule(a: &Entity, b: &Entity) -> Ordering {
    a.layer.cmp(&b.layer)
        .then_with(|| {
            if bounds_overlap(a, b) {
                let ba = bounds(a).max.y;
                let bb = bounds(b).max.y;
                ba.partial_cmp(&bb).unwrap_or(Ordering::Equal)
                    .then(a.pos.x.partial_cmp(&b.pos.x).unwrap_or(Ordering::Equal))
            } else {
                a.spawn_id.cmp(&b.spawn_id)
            }
        })
}
```

### 跨学科联结:从游戏到数据库

sort_rule 的本质是"复杂比较函数",这在很多领域都出现:

- **数据库 ORDER BY**:SQL 的 `ORDER BY layer, y, x` 是同样的 multi-key sort,但 SQL 是声明式(数据库优化器选 sort 算法),Casey 是命令式(手写 sort_by)。
- **React diff**:React 用 sort + key 比较 virtual DOM,决定哪些 component 重渲染。Multi-key sort 决定 diff 顺序。
- **Linux kernel CFS**(Completely Fair Scheduler):按 vruntime 排序进程,选最小 vruntime 的运行。本质是 sort_rule。
- **Git log --sort**:Git commit 按 committer date + author date + subject 排序。

Casey 在 HH 反复说"很多算法本质相同,只是命名不同"。掌握一个领域的 sort_rule,就掌握所有领域。
