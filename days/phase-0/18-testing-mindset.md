
# 18 · 测试心智:为什么测、怎么测、游戏为什么难测

> 零基础阶段你刚学会 Rust 的所有权和 trait。在你写出第一个"大东西"之前,我们要先种下一颗种子:**测试的心智**。这不是为了"应付考试式的覆盖率",而是为了让你在未来 667 天 + Phase 9 里,**每次改代码都不心慌**。Handmade Hero 全程不写测试——那是 Casey 的选择,不是你的。你要比 Casey 更职业,从现在开始。

## 0 · 为什么要有这一篇

先说三个真实的痛点,看你中了几个:

1. **"我改了一行,怎么全崩了?"** —— 你改了碰撞检测的一个常数,角色开始穿墙。你不知道是这一行的问题,还是三天前那次重构埋的雷。**没有测试,你只能用肉眼和 git bisect 慢慢找。**
2. **"这个函数我上周写的时候是对的啊?"** —— 一个数学工具函数(比如向量归一化),你当时跑过、看着对。但这周别处调用它出 bug 了。**到底是调用方错了,还是函数本身在某个边界值(零向量)上错了?** 没有测试,你只能怀疑人生。
3. **"重构之后我都不敢动了。"** —— 你的代码能跑,但很乱。你想重构,又怕改坏。**于是代码越来越烂,因为你失去了"安全改代码"的信心。**

这三个痛点的根因是同一个:**你没有一张"安全网"。** 测试就是那张网。有了它,改代码时网会告诉你"这一改,这几件事坏了"——你立刻知道、立刻修。**测试不是负担,是让你敢动代码的自信来源。**

但游戏编程有个特殊困难:**游戏代码天生难测。** 游戏到处是"每帧变化的状态"、随机数、玩家输入、渲染输出——这些都不是"给个输入看个输出"那么简单。本篇给你**测试的心智地基**,而"怎么测难测的游戏代码"留到 Phase 9 的 9A 序列深讲(本篇埋下伏笔)。

## 1 · 概念地图:测试的四个层次

先把测试的全景图印在脑子里。测试不是"写个 assert 就完了",它分层次,每层抓不同的 bug:

```
                  ┌──────────────────────────┐
                  │   手动玩(Manual play)    │  ← 最贵,最不可重复
                  └──────────────────────────┘
                  ┌──────────────────────────┐
                  │  端到端(End-to-end)      │  ← 整个游戏跑一遍
                  └──────────────────────────┘
                  ┌──────────────────────────┐
                  │  集成(Integration)       │  ← 几个模块一起测
                  └──────────────────────────┘
          ┌──────────────────────────────────────┐
          │          单元(Unit)                  │  ← 一个函数,最快最细
          └──────────────────────────────────────┘
```

**金字塔**:底下宽(单元多,快、稳、便宜),顶上窄(手动玩少,慢、贵、不可重复)。**初学者常犯的错是倒过来——全靠手动玩,几乎没有自动测试。** Handmade Hero 就是这个状态:Casey 每天手动跑游戏看效果,零自动测试。教学上 OK,职业上致命。

| 层次 | 抓什么 bug | 速度 | 例子 |
|---|---|---|---|
| 单元 | 一个函数的逻辑错 | 毫秒 | `normalize(Vec3::zero())` 该返回什么? |
| 集成 | 模块协作的错 | 毫秒-秒 | 物理 + 碰撞一起跑,角色会穿墙吗? |
| 端到端 | 整体行为 | 秒-分钟 | 开局 → 玩 10 秒 → 存档 → 读档,存档对吗? |
| 手动玩 | "手感"、视觉、主观体验 | 分钟-小时 | 这个跳跃感觉对不对? |

**关键直觉**:能往下推就往下推。一个 bug 如果能在单元层抓到,就别留到手动玩才发现——**越往上,bug 越难定位(你得从"画面不对"反推回"哪个函数错了")。**

## 2 · 心智模型:测试是"可执行的规约"

### 2.1 费曼类比:测试是"给未来的自己写的便条"

想象你给同事(或三个月后的自己)留一张便条:

> "嘿,这个 `normalize` 函数,我承诺:给它任何非零向量,它返回单位向量(长度 = 1)。给它零向量,它返回零向量(不 panic)。"

**测试就是把这张便条写成代码,让电脑每次构建都自动检查一遍。** 你的"承诺"叫**规约(specification)**,测试是规约的**可执行版本**。函数实现可以变(重构、优化),但只要便条上的承诺没变,测试就该一直绿。

**这个视角颠覆了初学者的直觉**:初学者以为"测试是验证我的实现";职业视角是"测试是定义我的承诺"。**承诺先行,实现后变** —— 这就是为什么测试让你敢重构:只要承诺没破坏,你怎么改都行。

### 2.2 红绿循环(做中学的微缩版)

测试驱动的节奏叫**红-绿-重构**,它其实就是"做中学"在代码层面的微缩:

1. **红**:先写一个测试,描述你要的功能。它**必然失败**(功能还没写)。看到红条 → 你知道测试"在测一个不存在的东西",说明测试本身是有效的(不是永远绿的废测试)。
2. **绿**:写**最少**的代码让测试过。看到绿条 → 你知道功能"至少在这一点上对了"。
3. **重构**:现在有安全网了,放心把代码改干净。

**为什么先红?** 如果你写完功能再补测试,而测试一跑就绿,你永远不知道这个测试是不是"永远绿"的废测试(比如它根本没调用你的函数)。**先看到红,再看到绿,你才确信"这个测试真的在测这个东西"。** 这是测试里最重要的直觉之一,记住它。

## 3 · Rust 的测试基础设施(cargo test)

Rust 的测试是内建的,不用装任何东西。三种测试位置:

### 3.1 模块内的单元测试(`#[cfg(test)]`)

最常见。在你写函数的同一个文件里,放一个 `#[cfg(test)]` 的子模块:

```rust
// src/vec.rs
pub fn normalize(v: [f32; 3]) -> [f32; 3] {
    let len = (v[0]*v[0] + v[1]*v[1] + v[2]*v[2]).sqrt();
    if len == 0.0 { return [0.0, 0.0, 0.0]; }
    [v[0]/len, v[1]/len, v[2]/len]
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn normalize_unit_vector_is_unchanged() {
        let v = [1.0, 0.0, 0.0];
        let n = normalize(v);
        assert!((n[0] - 1.0).abs() < 1e-6);
    }

    #[test]
    fn normalize_zero_vector_returns_zero_no_panic() {
        let n = normalize([0.0, 0.0, 0.0]);
        assert_eq!(n, [0.0, 0.0, 0.0]);
    }
}
```

`#[cfg(test)]` 的意思是"这段代码只在跑测试时编译,正常构建不包含"——所以测试代码**不影响发布产物的体积**。

跑测试:

```bash
$ cargo test
   Compiling my_game v0.1.0
running 2 tests
test vec::tests::normalize_unit_vector_is_unchanged ... ok
test vec::tests::normalize_zero_vector_returns_zero_no_panic ... ok

test result: ok. 2 passed; 0 failed
```

看到 `2 passed` 就是绿。

### 3.2 浮点数的陷阱:不要用 `assert_eq!`

注意上面我用的是 `assert!((n[0] - 1.0).abs() < 1e-6)`,不是 `assert_eq!(n[0], 1.0)`。**浮点数不能直接相等比较**——`0.1 + 0.2 != 0.3` 在浮点里是常态。这是初学者最常踩的坑:

```rust
// ❌ 几乎必然失败
assert_eq!(0.1 + 0.2, 0.3);

// ✅ 用容差(epsilon)
assert!((0.1 + 0.2 - 0.3).abs() < 1e-6);
```

记住:**测浮点,永远测"足够接近",不测"完全相等"。** 你的游戏里几乎所有数学(位置、速度、颜色)都是浮点,这条规则会救你无数次。

### 3.3 集成测试(`tests/` 目录)

集成测试放在项目根的 `tests/` 目录,只测**公开 API**(从外部视角):

```
my_game/
├── src/
│   └── lib.rs      ← 你的库代码
└── tests/
    └── physics.rs  ← 集成测试:把物理模块当黑盒测
```

```rust
// tests/physics.rs
use my_game::physics;

#[test]
fn a_falling_object_gains_speed() {
    let mut obj = physics::Body::new_at([0.0, 10.0]);
    physics::step(&mut obj, 1.0); // 模拟 1 秒
    assert!(obj.velocity[1] < 0.0); // 应该往下加速
}
```

**单元测试 vs 集成测试的分工**:单元测一个函数的内部逻辑(可以测私有函数);集成测"从外面看,这几个模块配合得对不对"(只测公开 API)。

## 4 · 游戏代码为什么难测(伏笔)

现在说难点。为什么 Casey 不写测试?不全是懒——**游戏代码天生难测**。四个原因:

**① 状态随时间变化。** 游戏是"每帧更新状态"的循环。你要测"角色跳起来再落地",得模拟几百帧。不像 `normalize` 给个输入就出输出。

**② 有随机数。** 伤害是 `rand(10..20)`,你测"打一下扣多少血"结果每次不一样。**对策:测试里用固定种子的随机源**(让随机变确定)。这叫**确定性(determinism)**,是 Phase 8 的 `determinism-and-replay` 和 Phase 9 的 9A-4 的核心。

**③ 有 I/O 和外部依赖。** 读手柄、播声音、画像素——这些"副作用"让函数不再是纯函数,难测。**对策:把"决策"和"执行"分开**——决策是纯函数(给定状态和输入,返回新状态),执行才碰硬件。这叫**可测架构(testable architecture)**,是 9A-1 的主题。

**④ "对不对"有时是主观的。** "这个跳跃手感好不好"测不出来——那是手动玩的事。**对策:分清"可客观验证的"(物理对不对、存档读得回来吗)和"主观的"(手感),只测前者。**

本篇只给你**直觉**:意识到这四点。**真正系统地把游戏写得可测,是 Phase 9 的 9A 序列**——那里会教你把 HH 的过程式代码重构到可测,从单元爬到 property test 到 fuzz。你现在只要记住:**写每个函数时,问自己一句:"这个东西我能不跑整个游戏就验证它吗?"** 能,就顺手写个单元测试。这就是种子。

## 5 · 四域深入

### 5.1 🎮 游戏编程视角
游戏测试的金字塔顶部(端到端/手动)占比比一般软件高——因为"手感/视觉"测不出。但底座(单元/集成)同样该尽量宽。**职业游戏工作室的标准做法**:物理/数学/存档/网络这些"可客观验证"的子系统,测试覆盖率很高;玩法/手感靠"自动化冒烟测试 + 人工 QA"。

### 5.2 🎨 图形学视角
图形测试有特殊手段:**快照测试(snapshot testing)**——把渲染一帧的结果存成基准图,以后每次改 shader,自动对比新图和基准图,差异超过阈值就报警。这能在你不注意时抓住"改了光照,整个场景暗了一档"这种回归。详见 Phase 9 的 9A-3。

### 5.3 🐧 Linux 系统编程视角
`cargo test` 之外,Phase 9 会用到 `cargo nextest`(更快、更好 UI 的测试运行器)和 `cargo fuzz`(模糊测试,给解析器喂随机输入找崩溃)。Linux 的 `fork` 让"每个测试独立进程"成为可能——一个测试崩了不影响其他。这些都是 9A 的内容,现在知道有这工具即可。

### 5.4 🦀 Rust 生态视角
Rust 的类型系统让很多 bug **在编译期就消除**,所以 Rust 项目的测试负担比 C++ 低(空指针、数据竞争在 Rust 里很难写出来)。但**逻辑 bug 类型系统管不了**——`normalize` 返回的到底对不对,还得测试。Rust 测试生态:`cargo test`(内置)、`proptest`(property test)、`quickcheck`、`cargo fuzz`、`insta`(快照测试)。这些在 Phase 9 会逐一上手。

## 6 · 认知地图

- **上级(它属于哪个更大抽象?)** → 软件工程的"质量保证(QA)"实践,和版本控制、CI 一样是工程纪律。
- **同级(并行方案?)** → 类型驱动设计(让非法状态不可表达)、形式验证(数学证明程序正确,太重不常用)。测试是性价比最高的那档。

## 7 · 对照与变奏

- **TDD(测试驱动开发)**:先写测试再写实现。激进派;适合逻辑清晰的小模块,不适合探索性代码。
- **BDD(行为驱动)**:用自然语言描述行为。对游戏过度,多用于业务软件。
- **不写测试(Casey 派)**:HH 全程不写。教学叙事流畅,但产物不可职业化。**你的立场:取中——HH 式造轮子 + 职业式测试,两者都要。**

## 9 · 变式训练

### Lv1 · 概念辨析(读懂)
**Q**: 为什么"先写测试看到红,再写实现看到绿"比"先写实现再补测试"更可靠?
<details><summary>答</summary>先红证明测试"真的在测这个功能"(功能还没写它就失败了);先写实现再补测试若直接绿,你无法排除"测试永远绿、根本没生效"的可能(比如测试没调用该函数)。</details>

### Lv2 · 动手实践
给你的 HH 项目(或任意 Rust 项目)里的一个纯函数写两个单元测试:一个测正常输入,一个测边界输入(零、空、最大值)。跑 `cargo test` 看到绿。然后**故意把函数实现改错**(比如 `normalize` 漏除以 len),确认测试变红——这验证了你的测试有效。

### Lv3 · 迁移设计
浮点比较的"容差"该怎么选?如果一个函数涉及天文距离(1e20)又涉及纳米(1e-9),固定容差 `1e-6` 还合适吗?查阅"相对误差 vs 绝对误差",写一个 `assert_approx_eq` 宏,支持相对容差。

### Lv4 · 开源贡献(进阶)
去 Rust 生态找一个你用过的 crate(glam、nalgebra),看它的 `tests/` 目录。找一个没被测试覆盖的公开函数,给它补一个测试,提 PR。这是真实的开源贡献练习。
